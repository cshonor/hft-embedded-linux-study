# 4.3 编码、行尾与路径：不致命但天天烦人的差异

[← 4.2 头文件与 socket](./4.2-两套世界头文件与socket.md) · 下一节：[4.4 为什么 TLPI 必须在 Linux 上跑 →](./4.4-为什么TLPI必须在Linux上跑.md)

## 本节讲什么

三类差异：它们不会让你的逻辑出错，但会让你在跨 Windows ↔ macOS/Linux 协作时
反复遇到"在我机器上明明是好的"。

## 要点

### ① 源文件编码（MSVC 有个默认值坑）

Microsoft Learn 的 [`/utf-8`](https://learn.microsoft.com/cpp/build/reference/utf-8-set-source-and-executable-character-sets-to-utf-8) 文档原话：

> By default, Visual Studio detects a byte-order mark to determine if the source file is in
> an encoded Unicode format... **If no byte-order mark is found, it assumes that the source file
> is encoded in the current user code page**, unless you've specified a code page by using
> `/utf-8` or the `/source-charset` option.

也就是说：**没有 BOM 的 UTF-8 源文件，MSVC 会按当前系统代码页解读。**
在简体中文 Windows 上系统代码页是 **GBK (936)** —— 于是 UTF-8 写的中文注释和字符串
会变成乱码，甚至导致编译错误。

| 平台 | 默认行为 |
|------|----------|
| clang / gcc | 源文件一律按 **UTF-8** 处理（这是 POSIX 世界的事实标准） |
| MSVC | **看 BOM**：有 BOM 认 UTF-8，无 BOM 按当前代码页（会错） |

解法三选一：

| 方案 | 说明 |
|------|------|
| 编译时加 **`/utf-8`** | 等价于 `/source-charset:utf-8 /execution-charset:utf-8`，推荐 |
| 源文件存成 **UTF-8 with BOM** | 让 MSVC 自己认出来；但某些 Linux 工具看到多余 BOM 会抱怨 |
| 避免使用非 ASCII 字符 | 最保守，写英语注释 |

> ⚠️ 加 `/utf-8` 会**自动启用 `/validate-charset`**：源文件里出现执行字符集无法表示的字符时
> 会报警告。这通常是你想要的（早点发现问题），需要关掉用 `/validate-charset-`。

这条和你的现状直接相关：**你在 Mac 上用 clang 写的中文注释笔记/代码，
拿给别人用 VS 编译就可能乱码** —— 因为 Mac 上生成的 UTF-8 文件通常不带 BOM。

### ② 行尾符 CRLF vs LF

| | Windows | macOS / Linux |
|---|---------|---------------|
| 行尾 | `\r\n` (CRLF) | `\n` (LF) |
| 后果 | Linux shell 脚本带 CRLF 会报 `bad interpreter`；某些工具把 `^M` 当字符 | Windows 记事本打开 LF 文件不换行（新版记事本已改善） |

Git 的应对策略就是你现在正在配的那项（`core.autocrlf` / `.gitattributes`）：

| 配置 | 含义 |
|------|------|
| `core.autocrlf=true` | 检出时转 CRLF，提交时转 LF（Windows 本机开发推荐） |
| `core.autocrlf=input` | 提交时转 LF，检出不变（macOS/Linux 推荐） |
| `.gitattributes` + `text eol=lf` | **仓库层面**统一，团队成员各自 override —— 比个人 `core.autocrlf` 可靠 |

> 推荐做法是**用 `.gitattributes` 而不是依赖每个人的 `core.autocrlf`** ——
> 后者是本地设置，不会被提交，新人加入就得重踩一遍。

### ③ 路径分隔符与大小写（最后一个很隐蔽）

| 差异 | Windows | macOS / Linux |
|------|---------|---------------|
| 分隔符 | `\`（也可接受 `/`） | `/` |
| 盘符 | `C:\Users\...` | 无，`/` 是根 |
| 文件系统大小写敏感 | ❌ **不敏感** | macOS 默认不敏感，**Linux 敏感** |

前两条你一眼能看出来，第三条才是真正的坑：

```c
#include <Sys/Socket.H>     /* Windows: ✅ 能编过（文件系统不敏感）
                               Linux:   ❌ fatal error: No such file or directory */
```

**在 Windows / macOS 上写错大小写的代码，到 Linux CI 上会编译失败。**
而开发者的本机测试完全发现不了。

> 这和你长期要做的事直接相关 —— 你的学习产出经常是 Mac 本地写、
> 推到 Linux（树莓派）去编译。**在 Mac 上能编过不等于在 Pi 上能编过。**

### 一张表收尾

| 项目 | 建议做法 |
|------|----------|
| 源文件编码 | 统一 UTF-8 **without BOM**；MSVC 侧加 `/utf-8` |
| 中文注释 | 想跨平台就在 Windows 侧加 `/utf-8`，否则别写非 ASCII |
| 行尾 | 用 `.gitattributes` 定 `*.md text eol=lf`，别靠个人 `core.autocrlf` |
| `#include` 大小写 | 一律按标准写的**小写原样**抄（`sys/socket.h` 不是 `Sys/Socket.h`） |
| 路径 | C 代码里用 `/`，Windows API 也接受 |
