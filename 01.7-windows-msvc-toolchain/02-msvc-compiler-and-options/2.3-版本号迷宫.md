# 2.3 版本号迷宫：VS 版本 / MSVC 工具集 / `_MSC_VER`

[← 2.2 选项对照全表](./2.2-选项对照全表.md) · 下一节：[2.4 CRT 选型 →](./2.4-CRT选型.md)

## 本节讲什么

Windows 世界里 C/C++ 工具链的**版本号有三套独立命名**，互相不成比例：

```
Visual Studio 2022 版本 17.12      ← IDE 的版本
MSVC 工具集版本        14.42        ← 编译器的版本
Platform Toolset      v143         ← 你工程属性页里选的那个下拉框
_MSC_VER              1942         ← 代码里 #ifdef 判断用的宏
```

四个数字**描述同一件事**。这一节把它们互推的规律讲清楚。

## 要点

### 三套命名各自的规则

| 命名 | 谁的 | 规律 |
|------|------|------|
| **VS 版本** | IDE | 2019=16.x，2022=17.x，2026=18.0。和年份无关，别被 2022 ≠ 22 弄混 |
| **MSVC 版本** | 编译器本身 | 恒定 `14.x`，从 VS 2015 的 `14.0` 一路递增，跨 VS 大版本连续编号 |
| **Platform Toolset** | 项目属性里的选择 | `v140`(2015) / `v141`(2017) / `v142`(2019) / `v143`(2022) / `v145`(2026) |
| **`_MSC_VER`** | 预定义宏 | MSVC 版本去掉小数点：`14.42` → `1942`；`14.0` → `1900` |

### 完整对照表（✅ 依据 Microsoft 官方公告与生命周期页整理）

| Visual Studio | Platform Toolset | MSVC 版本 | `_MSC_VER` |
|---------------|------------------|-----------|------------|
| VS 2015 (14.0) | v140 | 14.00 | 1900 |
| VS 2017 (15.x) | v141 | 14.10 – 14.16 | 1910 – 1916 |
| VS 2019 (16.x) | v142 | 14.20 – 14.29 | 1920 – 1929 |
| VS 2022 (17.0 – 17.9) | v143 | 14.30 – 14.39 | 1930 – 1939 |
| VS 2022 (17.10 及以后) | v143 | 14.40+ | 1940+ |
| VS 2026 (18.0) | v145 | 14.50+ | 1950（推断，见下） |

官方来源：
- [MSVC Toolset Minor Version Number 14.40 in VS 2022 v17.10](https://devblogs.microsoft.com/cppblog/msvc-toolset-minor-version-number-14-40-in-vs-2022-v17-10/)（含 2022 各更新的完整映射表）
- [Microsoft C++ 生成工具生命周期 FAQ](https://support.microsoft.com/ja-jp/lifecycle/faq/visual-c-faq)（`V14.50 = 14.50.35710`，Visual Studio 2026 v18.0，起 2025-11-11）

> **`_MSC_VER = 1950` 这一格是我的推断**：按"14.50 → 1950"的一贯规律推得，
> 尚未见到官方明示。写代码时用 `#if _MSC_VER >= 1940` 这种边界判断更稳妥。

### 两个必须知道的坑

**① VS 2022 (17.10+) 版本号偷偷进位了，导致大量构建脚本判断失效**

微软在官方博客里专门警告过这件事：

> For example, code which checks the `_MSC_VER` predefined macro and assumes that
> all Visual Studio 2022 versions of MSVC having a value below 1940 will need to be updated.

也就是说，很多第三方构建脚本硬编码了"`_MSC_VER` 小于 1940 就不是 VS2022"这类判断，
14.40 一出来就全部失灵。这在 Windows 生态里当时是**大面积事故**。

**② 没有 v144**

从 `v143` 直接跳到 `v145`（VS 2026）。**中间不存在 v144**。
所以看到 `v144` 的教程或者 CI 配置，要么是笔误，要么是编的。

### 二进制兼容性：决定你能不能混着用

微软维护了 2015–2026 之间的**二进制兼容**（https://learn.microsoft.com/cpp/portability/binary-compat-2015-2022 ），
一句话概括：

> v140 / v141 / v142 / v143 / v145 编译出来的 `.lib` 和 `.obj` **可以互相链接**，
> 但**最终链接必须用你所用版本集合里最新的那一个**链接器。

实际含义：

| 场景 | 结论 |
|------|------|
| 你的工程用 v143，引入一个 v142 编的第三方静态库 | ✅ 可以链接 |
| 你的工程用 v142，引入一个 v143 编的静态库 | ❌ 不行——旧工具集不认识新编的 obj |
| 混合使用时 | 升级自己这边到集合里最新的版本 |

> 这点比 GCC/Clang 生态严格得多。GCC 的 libstdc++ ABI 也是向前兼容的，
> 但历史上变换 ABI 时（`_GLIBCXX_USE_CXX11_ABI`）是靠宏开关，不是靠工具链版本号。

### 和你熟悉的版本号体系对比

| | 你怎么查 | 版本长什么样 |
|--|---------|-------------|
| clang | `clang --version` | `clang version 23.1.0` ✅ 本机实测 |
| gcc | `gcc --version` | `gcc (Debian 14.2.0-19) 14.2.0` |
| lldb | `lldb --version` | `lldb-2103.0.34.103`（Xcode 自带）/ `lldb version 22.1.8`（cdev） ✅ 实测 |
| MSVC | `cl` 不带参数会打印版本横幅 | `Microsoft (R) C/C++ Optimizing Compiler Version 19.42.xxxxx` |

注意最后一行：`_MSC_VER` 是 1942，但 `cl.exe` 打印出来是 **19**.42 ——
它打印的是 "14.x → 19.x" 的历史遗留换算（VS2015 的 `14.0` → `1900`）。
所以看到 `19.42` 不要以为版本号错乱了，把它前两位减 5 就是 MSVC 版本：**19.42 ↔ 14.42 ↔ _MSC_VER 1942**。
