导读

这一章解决什么困惑： 我在 VS 里会用 F9 下断点、F10 单步、鼠标悬停看变量， 但一下命令行就抓瞎。其实两者是同一件事的两种外壳。

✅ 本整章在 macOS 全程实测（2026-09-26 · clang 23.1.0 · Xcode 自带 lldb-2103.0.34.103）。 本文所有终端输出均为真实输出，不是示意。

为什么这一章最值得先读

因为它是本模块唯一在你现在的机器上完全可复现的章节。 前两章讲 Windows 工具链，你只能读；这一章你读完就能敲一次试试。

而且它的迁移价值最高 —— 你在 VS 里建立的调试直觉， 在 Xcode、VS Code、Linux gdb、乃至 GDB 远程调试树莓派时全都成立。

一句话结论

调试 = 让程序在指定位置停住 + 看清它此刻的状态 + 知道它是怎么走到这里的。 剩下的所有功能（条件断点、监视、内存窗口、数据断点）都是这三件事的花式变体。

3.1

调试到底在做哪四件事

← CH3 调试器心智模型 · 下一节：3.2 命令对照表 →

本节讲什么

把调试这件事剥到第一性原理：四件事。任何调试器（VS / Xcode / VS Code / lldb / gdb） 都是这四件事的组合。认领这四件事，你就不会再问"这个 IDE 的调试功能怎么用"。

要点

四件事

# 做什么 回答的问题 VS 里的入口 lldb 命令
① 让它停下来 "第 34 行执行之前，程序是什么状态？" 行号左边点红点 / F9 breakpoint set / b
② 往前挪一点 "下一步执行完会变成什么？" F10（跳过函数）/ F11（进函数） next / step
③ 看当前状态 "变量现在的值是多少？内存里是什么？" 悬停、监视窗口、局部变量窗口 frame variable / p / x
④ 看怎么来的 "是谁调用了我、带着什么参数？" 调用堆栈窗口 bt / thread backtrace

第 ④ 件事是新手最缺、也最省时间的一件事。 printf 调试法永远看不到调用栈， 而调用栈往往直接告诉你答案。

每层解剖（对照同一个 demo）

本模块的 demo/ptrbug.c 长这样：

static int buf[N] = { 0, 0, 0, 0 };

static int sum_n(const int *a, int n)      /* N == 4，但调用方传了 8 */
{
    int s = 0;
    for (int i = 0; i < n; i++) {
        s += a[i];                          /* ← 第 34 行 */
    }
    return s;
}
四件事 在这个 demo 上怎么用
① 停下来 在 34 行下断点，每次进入循环都停一次
② 往前挪 next 逐次看 i 从 0 涨到 7
③ 看状态 frame variable 同时给出 a、n、s、i
④ 看来源 bt 告诉你它从 main 的哪一行来（区分 n=4 那次还是 n=8 那次）

第 ④ 件事在这里是决定性的：sum_n 被调用了两次，只有看调用栈才知道当前这次是 n=4 的正确调用，还是 n=8 的越界调用。✅ 实测输出见 3.3。

花式变体其实都是①的组合

听起来高级的功能 本质
条件断点（只在 n==8 时停） ① + 一个表达式判断
数据断点 / 观察点（某变量被改写时停） ① + 硬件 facilities / 内存页保护
命中次数断点（第 100 次才停） ① + 一个计数器
单步 / 步入 / 步出 ② 的三种粒度
监视窗口表达式求值 ③ 的扩展
反汇编窗口 ③ 但看的是汇编而非源码

认出这一点，你就不会因为某个 IDE 没有某按钮而焦虑 —— 它只是换个地方组合同样四件事。

一个容易被忽略的前提：这些能力依赖调试信息

调试器能显示变量名和源码行，靠的不是二进制本身，而是 2.5 节讲的 DWARF / PDB：

DW_AT_name  ("sum_n")     DW_AT_decl_line (30)
  DW_AT_name  ("a")       ← 参数名靠这里
  DW_AT_name  ("n")
  DW_AT_name  ("s")

✅ 实测（llvm-dwarfdump ptrbug.o）。所以：

编译方式 变量窗能不能显示名字
clang -g ✅ 能（DWARF 在 .o / dSYM 里）
clang（无 -g） ❌ 只能看汇编和地址
clang -O2 -g ⚠️ 部分变量会显示 <optimized out>

3.2

VS 操作 ↔ lldb ↔ gdb 命令对照表

← 3.1 调试的四件事 · 下一节：3.3 Mac 实测 →

本节讲什么

一张"翻译词典"。左边是你在 VS 里会做的动作，右边是命令行里的写法。 不要背，放在这里是为了用的时候来查。

标注 ⚠️ 的是我在本机实测中真的踩过的坑。

要点

断点

你想做的事 Visual Studio lldb gdb
在某行下断点 行号左边点一下 / F9 b ptrbug.c:34 b ptrbug.c:34
在函数入口下断点 断点窗口 (Ctrl+Alt+B) b sum_n b sum_n
条件断点 右键红点 → 条件 b ptrbug.c:34 -c 'n==8' b ptrbug.c:34 if n==8
列出所有断点 断点窗口 br list info breakpoints
删除断点 再点一次红点 br del 1 delete 1
禁用/启用 右键 → 禁用断点 br disable 1 / br enable 1 disable 1 / enable 1
观察点 / 数据断点（变量被改写时停） 右键变量 → 新建数据断点 watchpoint set variable buf watch buf

⚠️ 实测过的坑：lldb 的完整写法 --file / --line / --condition 和简写混用时要注意， b ptrbug.c:34 -c 'n==8' 这种短形式是能用的（我在 3.3 里用长形式写）。 条件表达式要加引号，不然 shell 会把 == 吃掉。

执行控制

你想做的事 Visual Studio lldb gdb
开始调试 F5（本地 Windows 调试器） run / r run / r
继续到下一个断点 F5 continue / c continue / c
单步跳过（不进函数） F10 next / n next / n
单步进入（进函数） F11 step / s step / s
步出当前函数 Shift + F11 finish finish
运行到光标处 Ctrl + F10 thread until 45 until 45
停止调试 Shift + F5 kill / quit kill / quit
重启 Ctrl + Shift + F5 run（会重新加载） run
带参数启动 项目属性 → 调试 → 命令参数 lldb -- ./app arg1 arg2 gdb --args ./app arg1

VS 的 F9/F10/F11 这套键位默认是 Visual C++ Developer 键位方案。 如果你的 Ctrl+F10 行为不对，多半是键盘映射方案选成了别的。

查看状态（对应 VS 的各种窗口）

你想做的事 Visual Studio lldb gdb
看当前所有局部变量 局部变量窗口 frame variable / fr v info locals
看某一个变量 鼠标悬停 / 快速监视 p n / print n p n
看函数参数 局部变量窗口（含参） frame variable（含参） info args
修改变量值 监视窗口里改 expr n = 5 set var n = 5
调用一个函数 即时窗口 expr printf("hi") call printf("hi")
看调用栈 调用堆栈窗口 bt / thread backtrace bt
切换栈帧 双击调用栈里的行 frame select 1 / f 1 frame 1 / f 1
看裸内存 调试 → 窗口 → 内存 x/12w &buf x/12w buf
看反汇编 反汇编窗口 disassemble / di disassemble
看寄存器 寄存器窗口 register read info registers
列源码 （编辑器本身就是） list / l list / l

⚠️ 实测过的坑：lldb 里对数组名取地址必须加 &，直接写数组名会类型不匹配：

(lldb) x/10w buf
error: address expression "buf" resulted in a value whose type can't be converted to an address: int[4]

(lldb) x/12w &buf          ← 这样才行
0x100008010: 0x0000000a 0x00000014 0x0000001e 0x00000028

理由是 lldb 把数组名当数组类型的值而不是指针（这点和 C 语言的隐式转换不同）。 gdb 里 x/12w buf 可以直接用 —— 这是两者日常调试最容易卡住的一处差异。

⚠️ 第二个实测坑：memory read -s 4 -c 10 buf 这种写法也会报错， 因为显示格式和字节数冲突：

(lldb) memory read -s 4 -c 10 buf
error: display format (bytes/bytes with ASCII) conflicts with the specified byte size 4
    consider using a different display format or don't specify the byte size.

用 x/12w &buf 最省事（它自动指定了按 word 显示）。

多线程

你想做的事 Visual Studio lldb gdb
列出线程 线程窗口 thread list info threads
切换线程 双击线程 thread select 2 thread 2
所有线程的调用栈 并行堆栈窗口 bt all thread apply all bt

3.3

Mac 实测：一次完整的 lldb 会话

← 3.2 命令对照表 · CH3 调试器心智模型

本节讲什么

把 3.1 的四件事在你这台 Mac 上真跑一遍。 下面所有终端输出都是 2026-09-26 本机真实输出，不是示意。

⚠️ 一个前置事实（实测确认）： 你 cdev 环境里的 lldb 22.1.8 不能用 —— 它缺 debugserver：

text $ lldb --version lldb version 22.1.8 $ lldb --batch -o "breakpoint set --file ptrbug.c --line 34" -o run -- ./ptrbug (lldb) run error: could not find 'debugserver'. Please ensure it is properly installed and available in your PATH

原因：macOS 上 lldb 依赖一个叫 debugserver 的调试服务端（负责真正操作进程）， 它由 Xcode 提供，不在 LLVM/conda 的分发里。好消息是你装了 Xcode 27.0， 它自带配套的 lldb 与 debugserver：

text /Applications/Xcode.app/Contents/Developer/usr/bin/lldb (lldb-2103.0.34.103) /Applications/Xcode.app/Contents/SharedFrameworks/LLDB.framework/Versions/A/Resources/debugserver

即使没同意 Xcode 许可协议，/Applications/Xcode.app/.../bin/lldb 这个二进制也能直接调用 （✅ 实测 —— 被挡的是 xcrun，不是 lldb 本体）。 所以下文用它。

⚠️ 另一个实测约束：进程附加会被沙箱拦住，报 attach failed (attached to process, but could not pause execution)。 在终端里正常执行不受影响。

要点

准备：编译带调试信息的靶子

$ cd demo
$ clang -g -O0 -Wall -Wextra -std=c11 ptrbug.c -o ptrbug
$ ./ptrbug
sizeof(buf)      = 16 bytes, 4 elems
sum_n(buf, 4)   = 100
sum_n(buf, 8)    = 100   <-- 越界读，值不确定但通常不崩
buf=0x1020d4010  buf[0]=10  *(p+3)=40

✅ 实测。注意最后第二行：越界读竟然返回了正确的 100。 一个也不崩、一个也不错 —— 这种"看起来没事"的 bug 才是最贵的那种。

第一次断点：看四件套里的①④

$ /Applications/Xcode.app/Contents/Developer/usr/bin/lldb --batch \
    -o "breakpoint set --file ptrbug.c --line 34" \
    -o "run" -o "frame variable" -o "bt" -o "continue" -- ./ptrbug

(lldb) run

Process 13057 stopped

       frame #0: 0x0000000100003ea4 ptrbug`sum_n(a=0x0000000100008010, n=4) at ptrbug.c:34:14

     frame #1: 0x0000000100003ddc ptrbug`main at ptrbug.c:48:15
     frame #2: 0x0000000192837e80 dyld`start + 6688

✅ 实测。四个关键观察：

  1. 断点信息里带了行号和列号：at ptrbug.c:34:14 —— 靠 DWARF 才能有
  2. 源码上下文自动打印，-> 指着当前行 —— 这就是 VS 里那个黄色箭头
  3. frame variable 一次给出全部局部变量 + 参数（a 是 int 常量指针、n、s、i）
  4. bt 显示三层栈：sum_n ← main:48 ← dyld start

对照 VS：这段输出 = 局部变量窗口 + 调用堆栈窗口 + 编辑器里的黄色箭头，三合一。

条件断点：直达越界那一刻

sum_n 被调用两次。用条件断点只看越界那次（n==8）：

$ lldb --batch \
    -o "breakpoint set --file ptrbug.c --line 34 --condition 'n==8'" \
    -o "run" -o "continue" -o "continue" -o "continue" -o "continue" -o "continue" \
    -o "frame variable" -o "x/12w &buf" -o "bt" -o "kill" -- ./ptrbug

(lldb) frame variable
(const int *) a = 0x0000000100008010
(int) n = 8
(int) s = 100
(int) i = 5
(lldb) x/12w &buf
0x100008010: 0x0000000a 0x00000014 0x0000001e 0x00000028
0x100008020: 0x00000000 0x00000000 0x00000000 0x00000000
0x100008030: 0x00000000 0x00000000 0x00000000 0x00000000
(lldb) bt
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
   * frame #0: 0x0000000100003ea4 ptrbug`sum_n(a=0x0000000100008010, n=8) at ptrbug.c:34:14
     frame #1: 0x0000000100003df0 ptrbug`main at ptrbug.c:49:15
     frame #2: 0x0000000192837e80 dyld`start + 6688
(lldb) kill
Process 13097 exited with status = 9 (0x00000009) killed

✅ 实测。这一段是整个模块的点睛之笔，把谜底解开了：

① i = 5 —— buf 只有 4 个元素（下标 0–3），程序正在读 buf[5]，早就越界了。

② s = 100 —— 前 4 个元素的和是 100，越界那几格没改变结果。为什么？看内存：

内存地址 值（十六进制） 含义
0x100008010 0x0a buf[0] = 10 ✓
0x100008014 0x14 buf[1] = 20 ✓
0x100008018 0x1e buf[2] = 30 ✓
0x10000801c 0x28 buf[3] = 40 ✓
0x100008020 0x00 ← 越界区开始，全是 0
0x100008024 0x00 ← 0，加进 s 不影响结果
… 0x00 全是 0

buf 后面那段内存恰好是 0，所以 sum_n(buf, 8) 碰巧返回了正确答案。 这不是"程序没 bug"，这是"这一次运气好"。换变量布局、换编译器、换优化级别，随时可能翻脸。

③ bt 的 main at ptrbug.c:49:15 —— 精确告诉你越界是从第 49 行发起的， 而不是 48 行（48 行是那次正确的调用）。这个数字是 printf 调试法永远给不了你的。

同一个 bug，换个优化级别就翻脸

把 -O0 换成 -O2，同一个源文件：

$ clang -g -O2 -Wall -Wextra -std=c11 ptrbug.c -o ptrbug_o2
$ ./ptrbug_o2
sizeof(buf)      = 16 bytes, 4 elems
（然后永久卡住，3 秒后被强制终止，status=9）

✅ 实测：-O0 下 4 行正常输出、exit=0；-O2 下只吐出第 1 行就再也不返回了。

看它生成了什么（截取 main 的关键部分，✅ 实测自 --batch 的 -S 输出）：

_main:
    .cfi_startproc
; %bb.0:
    sub sp, sp, #32
    stp x29, x30, [sp, #16]
    add x29, sp, #16
    mov w8, #4
    mov w9, #16
    stp x9, x8, [sp]
    adrp    x0, l_.str@PAGE
    add x0, x0, l_.str@PAGEOFF
    bl  _printf          ← 只调用了一次 printf（第 1 行输出）
LBB0_1:                                 ; =>This Inner Loop Header: Depth=1
    b   LBB0_1          ← 无条件跳回自己：无限空循环
    .cfi_endproc

汇编里 main 只剩下一次 printf 和一个跳向自己的无限循环。 其余所有代码（第二个第三个 printf、sum_n 的调用）全部被删除了。

发生了什么：

  1. clang 看见 sum_n(buf, 8) 会读 buf[4..7] → 判定为 UB（未定义行为）
  2. 优化器的基本公理是"UB 永远不会发生"，于是推断这条路径不可达
  3. 依赖它的返回值变成 poison（无意义），所有后续 printf 被常量折叠 / 消除
  4. 但控制流真的流到了那个"不可能到达"的点，需要兜底 → 生成一个无限空循环

这才是 UB 的真正含义：不是"偶尔算错"，是编译器有权按它的假设重写你的整个程序。 MSVC 遇到同样的 UB 也会做类似推断，只是表现形式不同。

让工具替你抓：ASan

$ clang -g -O1 -fsanitize=address -fno-omit-frame-pointer -Wall -std=c11 ptrbug.c -o ptrbug_asan
$ ./ptrbug_asan
=================================================================
==13007==ERROR: AddressSanitizer: global-buffer-overflow on address 0x0001042c41f0
READ of size 4 at 0x0001042c41f0 thread T0
    #0 0x0001042bfba4 in sum_n ptrbug.c:34
    #1 0x0001042bfba4 in main ptrbug.c:49
    #2 0x000192837e7c in start+0x1a1c (dyld:arm64e+0x31e7c)

0x0001042c41f0 is located 0 bytes after global variable 'buf' defined in 'ptrbug.c' (0x0001042c41e0) of size 16
SUMMARY: AddressSanitizer: global-buffer-overflow ptrbug.c:34 in sum_n
==13007==ABORTING
sizeof(buf)      = 16 bytes, 4 elems
$ echo $?
134

✅ 实测。ASan 给出的信息和 lldb 完全一致，而且更明确：

  • READ of size 4 —— 越界读取 4 字节
  • in sum_n ptrbug.c:34 ← in main ptrbug.c:49 —— 精确的行号链
  • 0 bytes after global variable 'buf' ... of size 16 —— 正好落在 buf 尾部之后第 0 字节， 和我们用 x/12w &buf 看到的那片 0x00 区域严丝合缝
  • exit=134（SIGABRT）

-O0 看不出来、-O2 直接卡死、ASan 一句话命中 —— 三种手段的成本收益一目了然。 系统化的工具清单见 03.6 用户态调试。

复现这些输出（本机）

cd demo
make            # 编译 -g 版本
make lldb       # 跑一次 lldb batch 会话
make asan       # ASan 版本，跑 ./ptrbug_asan

⚠️ make lldb 里的 lldb 默认会解析到 PATH 里的版本（你的 cdev lldb 缺 debugserver）。 建议直接敲 /Applications/Xcode.app/Contents/Developer/usr/bin/lldb， 或者先执行 sudo xcodebuild -license 把 Apple 整套工具链解锁。
