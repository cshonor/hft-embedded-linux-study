## ④ 内核开发的特点 · A Beast of a Different Nature

内核与用户态程序 **不是同一种 C 环境**。下列规则 **违反即 oops / 死锁 / 栈炸**。

---

### 一句话先钉死：内核的 C = GNU C，不是纯 ISO C

**ISO C** 是国际标准；**GCC** 在标准 C 之上额外加了一堆语法特性，叫 **GCC 扩展（GNU C / GNU dialect）**。  
Linux 内核大量使用这些 **不属于标准 C** 的扩展，所以：**内核的 C 不是纯粹标准 C，是 GCC 扩展版 C**。

---

### 官方结论：默认 `-std` 是什么？

| 主线内核版本 | 默认编译方言 |
|--------------|--------------|
| **≥ 5.18（2022）** | **`-std=gnu11`** |
| **≤ 5.17** | 长期 **`-std=gnu89`**（C89 + GCC 扩展） |

拆解 `gnu11`：

| 片段 | 含义 |
|------|------|
| `c11` | 基准是 **ISO C11**（2011） |
| `gnu` | **开启全部 GCC 扩展语法** |
| 合起来 | **GNU 方言版 C11** |

本机日常树 **linux-7.1.5** 顶层 `Makefile` 已写死：`CC_FLAGS_DIALECT := -std=gnu11`（与官方结论一致）。

#### 极易混淆的 flag

| flag | 含义 |
|------|------|
| `-std=c11` | **纯** 标准 C11，**禁用** GCC 扩展 |
| `-std=gnu11` | C11 + **全部** GCC 扩展（**现代内核默认**） |
| `-std=c99` | 纯标准 C99 |
| `-std=gnu99` | C99 + GCC 扩展 |

分界线刻死：

| | |
|--|--|
| `c99` / `c11` | 国际标准化语言规范（**无**编译器附加语法） |
| `gnu99` / `gnu11` | 标准 + **GCC 私自扩展**（内核用的方言） |

#### 算 C99 还是 C11？

底层基准是 **C11**，但有两个现实要点：

1. **日常写法大量像 C99**：混合位置声明、`stdint.h`、`inline`（C99 起普及）用得很多；C11 新增的 `_Atomic`、`_Thread_local`、VLA 等内核几乎不用（VLA 甚至 **明确禁止**）。所以会感觉「和 C99 差不多」。
2. **不等于纯标准 C11**：`gnu11` ≠ `c11`。带 `gnu` 就启用 `typeof`、`({})`、`__attribute__`、内嵌汇编、`##__VA_ARGS__` 等 —— 这才是教材说「内核 C 是 GCC 扩展」的来源。

#### 误区

| 误区 | 纠正 |
|------|------|
| `gnu11` = C11 | 错。`-std=c11` 下写 `({int a=1;a;})` 报错；`gnu11` 才过。 |
| 模块随便改成 `gnu99` | **不要**。模块须与内核本体 `-std` 一致，否则 inline/类型语义可能诡异不兼容。 |
| 用户态随便选 `-std=c17` 所以内核也能裸 `c11` | 用户态可以；内核 **离不开** GCC 扩展，裸 `-std=c11` 写不出操作系统内核。 |

#### 如何验证本机源码树用的 `-std`

在源码树根目录（Linux/WSL 上）：

```bash
# 直接看 Kbuild 写死的方言（最快）
grep -n 'std=gnu\|CC_FLAGS_DIALECT' Makefile

# 或让一次真实编译打印命令行里的 -std（需已配置过 .config）
make -C . V=1 kernel/sys.o 2>&1 | tr ' ' '\n' | grep '^-std='
```

本仓库对照路径示例：`C:\Users\12392\Desktop\linux-7.1.5\Makefile` 中可见 `-std=gnu11`。

### 三层概念（杜绝混淆）

| 层 | 是什么 | 边界 |
|----|--------|------|
| **1. 标准 C（ISO C：C89/C99/C11…）** | ISO 规定的通用语法；合规编译器都应支持 | **没有** 硬件段控制、类型推导等扩展 |
| **2. GNU C（GCC 扩展）** | GCC 在标准上 **私自增加** 的语法/关键字/特性 | **未写入** C 国际标准；`-std=c11 -pedantic-errors` 编内核相关代码会炸 |
| **3. Linux 内核（≥5.18）** | 默认 **`-std=gnu11`** | = C11 基准 + GNU 扩展 |

再钉死一对（常和上一章 libc 搞混）：

| | 属于哪一层 | 何时用 |
|--|-----------|--------|
| **glibc / libc** | **用户态标准库**（运行期） | 用户程序链接它 |
| **GNU C / GCC 扩展** | **语言方言**（编译期语法） | 编译器认不认这些写法 |

> **GNU C ≠ glibc。** 一个是语法扩展，一个是用户态运行时库。

```
用户程序：较标准的 C → 链接 glibc → glibc 封装 syscall
内核代码：GNU C（GCC 扩展语法）→ 编成内核镜像，无 libc
```

→ libc 细节：[Ch5 §5.1](../../chapter-05-system-calls/notes/section-5.1-与内核通信.md)

### 无标准 C 库（运行期）

| 用户态 | 内核态 |
|--------|--------|
| `printf` | **`printk`**（带 **日志级别**） |
| `malloc` | **`kmalloc` / `vmalloc` / slab**（Ch 12） |
| `string.h` 全套 | 内核 **`lib/`** 自实现子集 |
| 链接 glibc | **不能** 链接标准 C 库（`-nostdlib` 一类） |

内核 **完全不调用 glibc 里的函数**；`memcpy` / `strlen` 等在内核自己的 `lib/` 里。

### 内核最常见的 GCC 扩展（一眼能认出）

#### ① `typeof`

标准 C 没有。取表达式类型：

```c
#define min(a, b) ({ \
    typeof(a) _a = (a); \
    typeof(b) _b = (b); \
    _a < _b ? _a : _b; \
})
```

#### ② 语句表达式 `({ ... })`

大括号包代码块，**最后一表达式作「返回值」**。上面 `min` 依赖它。标准 C 不允许。

#### ③ `__attribute__((...))`（超级高频）

```c
__attribute__((packed))       /* 结构体取消填充对齐 */
__attribute__((aligned(8)))   /* 指定对齐 */
__attribute__((section(".init")))  /* 放到指定 ELF 段 */
__attribute__((weak))         /* 弱符号 */
```

驱动天天见：控内存布局、链接段、初始化段释放等。

#### ④ 可变参数宏与 `##__VA_ARGS__`

```c
#define pr_info(fmt, ...) printk(fmt, ##__VA_ARGS__)
```

`##` 处理「没有额外参数时多余逗号」——标准预处理不这么干。

#### ⑤ 省略中间值的三目：`a ?: b`

等价于 `a ? a : b`。标准 C 要求三目必须三个表达式。

#### ⑥ 内联汇编 `asm volatile(...)`

标准 C 无内嵌汇编语法；这是编译器扩展。

#### ⑦ 标签地址 `&&label`、零长/柔性数组成员

```c
struct { int len; char arr[]; };  /* 柔性数组成员；内核网络/缓冲常见 */
```

另有：`likely()` / `unlikely()`（基于 `__builtin_expect`）、`__builtin_constant_p` 等。

```c
if (likely(ptr != NULL)) {
    /* 常见路径 */
}
```

对比实验（示意）：

```c
int x = val ?: -1;
```

| 编译方式 | 结果 |
|----------|------|
| `gcc -std=gnu11` | 正常（GNU 扩展开启） |
| `gcc -std=c11 -pedantic` | 警告/报错：不符合标准 C |

本地小 demo：[`code/gnu_c_extension_demo.c`](../code/gnu_c_extension_demo.c)

### 为什么内核非要用扩展，不用纯标准 C？

内核跑在裸硬件上，**标准 C 能力不够**：

1. **精细控制 ELF 段、对齐** — 标准 C 管不了「函数放哪个段」；初始化函数进 `.init`、启动后释放，靠 `__attribute__((section))`。
2. **泛型宏（`min`/`max`/`container_of`）** — `container_of` 依赖 `typeof`；驱动模型极度依赖它。见 [Ch6 §6.2](../../chapter-06-kernel-data-structures/notes/section-6.2-链表.md)。
3. **硬件交互必须内嵌汇编** — 寄存器、syscall 入口、开关中断。
4. **编译期优化与检查** — `__builtin_*`、`likely/unlikely` 等。

### 误区澄清

#### 误区：内核用 GCC 扩展 = 内核依赖 glibc？

❌ 完全无关。

| | |
|--|--|
| **GNU C** | 编译器语法扩展（**编译期**） |
| **glibc** | 用户态运行时库（**运行期**） |

内核用 GNU C 语法写，但 **不链接 libc**。

#### 误区：只有 GCC 能编内核？

**Clang** 为能编 Linux，主动兼容绝大部分 GCC 扩展。可用 clang 构建，但代码仍是 **GNU C 方言**。

---

### 背诵版

1. 现代内核（**≥5.18**）：默认 **`gnu11` = C11 基准 + GCC 扩展**；老内核（**<5.18**）：**`gnu89`**。  
2. 基准规范是 C11，但代码习惯大量沿用 C99 特性；**几乎不用** 多数 C11 新特性，且 **禁 VLA**。  
3. **`gnuXX` ≠ 标准 `cXX`** —— 带 `gnu` 就启用 GCC 扩展语法。  
4. **GNU C（语法）≠ glibc（用户态库）** — 不要混淆。

### 无内存保护

| 现象 | 后果 |
|------|------|
| 非法访问 | 无 **SIGSEGV** — 往往 **oops / panic** |
| 内核内存 | **不可换页** — 每占 1 字节 = **真实物理内存 −1** |
| 泄漏 | 重启前 **不会** 还给系统 |

### 禁止浮点（通常）

用户态由内核 **惰性保存/恢复 FP 寄存器**；内核路径 **默认不处理 FP 状态** → **一般禁止浮点运算**（特殊代码需显式 `kernel_fpu_begin/end` 等）。

### 小而固定的栈

| 事实 | 开发约束 |
|------|----------|
| 内核栈常 **4KB 或 8KB** | **禁止** 栈上大数组/大结构体 |
| 每进程独立内核栈 | 深度递归、大 `alloca` → **栈溢出** |

### 同步与并发

并发来源多：**抢占**、**SMP**、**硬/软中断**、**内核线程** → 极易 **竞态**。

| 机制 | 场景（详见 Ch 9–10） |
|------|----------------------|
| **自旋锁** | 短临界区、不可睡眠 |
| **信号量 / mutex** | 可睡眠、较长临界区 |
| **RCU** | 读多写少 |

**HFT：** 用户态网关用 **无锁队列 + 绑核**；内核里对应的是 **关中断、per-CPU、原子、锁顺序** — 错一层就是 **微秒级抖动或整机卡死**。

### 可移植性

Linux **高度可移植** — 代码应：

| 原则 | 反例 |
|------|------|
| **字节序中立** | 假设 little-endian |
| **64 位兼容** | 假设 `int` = 指针宽度 |
| **不硬编码页大小** | 写死 4096 而不 `PAGE_SIZE` |
| **`arch/` 隔离** | 在通用代码里写 x86 汇编 |
