# blk-mq 多队列块层 — 替代传统单队列

> **原文:** [Multiqueue block layer](https://lwn.net/Articles/552904/) (LWN, 2013)
> **作者:** Jens Axboe, Shaohua Li
> **内核版本:** 3.13+ (引入), 5.x (成为默认)
> **对标旧书:** ULK3 Ch14 (单队列块层)

---

## 核心观点

传统块层单一请求队列在高 IOPS 设备（SSD 百万级 IOPS）上成为瓶颈。blk-mq 引入 per-CPU 软件队列 + 硬件队列，消除锁争用，适应现代高速存储。

### 传统单队列的问题

```
传统块层:
  CPU 0 ─┐
  CPU 1 ─┼──→ [单一请求队列 (一把锁)] ──→ 块设备
  CPU 2 ─┘
```

- 整个队列一把锁，多核争用严重
- 链表数据结构对 cache 不友好
- 设计于硬盘时代（数百 IOPS），无法扩展到 SSD

### blk-mq 多队列设计

```
blk-mq:
  CPU 0 → [SQ 0] ─┐
  CPU 1 → [SQ 1] ─┼──→ [硬件分发队列] ──→ 块设备
  CPU 2 → [SQ 2] ─┘
```

| 队列类型 | 数量 | 作用 |
|---------|------|------|
| **软件提交队列 (SQ)** | per-CPU 或 per-node | 每个 CPU 独立提交 I/O，无锁争用 |
| **硬件分发队列 (HQ)** | 1~N (由设备决定) | 驱动从硬件队列获取请求执行 |

### 关键设计决策

| 决策 | 理由 |
|------|------|
| **不在软件队列重排序** | SSD 无寻道开销，重排序无益 |
| **仍执行请求合并** | 合并相邻 I/O 减少总操作数 |
| **跨 CPU 合并放弃** | 不同 CPU 的请求难以高效合并 |
| **公平性可选** | 高速设备下公平性代价不值得 |

### I/O 调度器变化

传统调度器（deadline/cfq/noop）为单队列设计，blk-mq 引入了新调度器：

| 旧调度器 | blk-mq 调度器 | 说明 |
|---------|--------------|------|
| cfq | bfq | 按进程公平分配 I/O 带宽 |
| deadline | mq-deadline | deadline 算法的多队列版本 |
| noop | none | 不调度，直接透传（SSD/NVMe 常用） |
| - | kyber | 自适应限制队列深度 |

---

## 与旧书差异

| ULK3 讲的 | 6.x 现代实现 |
|-----------|-------------|
| 单一 `request_queue` | per-CPU SQ + 硬件 HQ |
| `request` + `bio` | `bio` 为主，`request` 仍存在但路径不同 |
| I/O 调度器：deadline/cfq/noop | mq-deadline/bfq/kyber/none |
| `elv_next_request()` | `blk_mq_queue_rq()` |
| 单队列锁 | per-CPU 无锁队列 |

---

## HFT 关联

| 场景 | blk-mq 影响 |
|------|------------|
| **磁盘 I/O 不在热路径** | HFT 交易线程不直接做磁盘 I/O |
| **日志写入** | blk-mq 多队列减少日志写入对系统延迟的影响 |
| **NVMe 设备** | NVMe 原生多队列，blk-mq 直接映射 |
| **PREEMPT_RT** | blk-mq 的 per-CPU 队列减少锁争用，间接改善实时性 |

> **HFT 实盘：** 磁盘 I/O 不在交易热路径上（交易数据在内存/共享内存），blk-mq 对 HFT 直接影响小。但减少辅助 I/O 的锁争用有助于系统整体延迟稳定性。

<summary>自测题（点击展开）</summary>

**Q1:** blk-mq 为什么不在软件队列做请求重排序？

> 传统硬盘有物理寻道开销，重排序（电梯算法）可以减少磁头移动。SSD/NVMe 没有寻道开销，随机访问性能与顺序访问相当，重排序无益。甚至分散请求有助于设备内部并行处理。

**Q2:** blk-mq 的 "none" 调度器为什么在 NVMe 上常用？

> NVMe 设备自身有内部调度和并行处理能力。内核层再调度只会增加延迟。"none" 调度器直接将 I/O 透传给设备，最小化内核开销。NVMe 的多硬件队列直接映射到 blk-mq 的硬件队列，实现高效并行。

**Q3:** 传统单队列的锁竞争为什么在大规模系统上严重？

> 单队列一把锁，所有 CPU 提交 I/O 时都要获取同一把锁。64+ 核系统上频繁的锁争用导致缓存行在 CPU 间弹跳 (cache line bouncing)，每次锁获取/释放都导致其他 CPU 的缓存行失效。blk-mq 的 per-CPU 队列消除了这种争用。

</details>
