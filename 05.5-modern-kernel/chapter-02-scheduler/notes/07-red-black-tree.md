# 红黑树 — CFS 的排序容器

> **定位:** 06 笔记里 `rb_root_cached` 的前置知识。为什么调度器选红黑树而不是 AVL 或堆。
> **对标:** 数据结构基础 + `include/linux/rbtree.h` / `rbtree_augmented.h`
> **内核实现视角**（NIL 哨兵到底存不存在 / 黑高口径歧义 / `lib/rbtree.c` 插入修复源码行号）→ [05 Ch6 §6.5](../../../05-linux-kernel/chapter-06-kernel-data-structures/notes/section-6.5-二叉树.md)

---

## 解决什么问题

二叉搜索树（BST）：左 < 根 < 右，查找 O(树高)。缺陷：**形状取决于插入顺序**——顺序插 1..5 直接退化成链表，查找变 O(n)。

红黑树 = BST + 5 条染色规则，强制"歪不到哪去"。

### 新手三步直觉

1. **它首先是一棵 BST**——左 < 根 < 右，中序遍历有序。这个性质永远优先，红黑规则只是"外观约束"，不能凌驾于 BST 之上。
2. **颜色只有一个 bit，是给修复算法看的记账位**，不是业务数据。
3. **颜色的真正含义是"算不算一层"**：黑边 = 下降一层，红边 = 横向停靠（下面"红与黑到底是什么"展开）。

---

## 五条性质

1. 每个节点非红即黑
2. 根节点黑
3. 叶子（NIL 空节点）黑 — ⚠️ 这里的"叶子"指**空孩子**，不存任何数据；且 NIL 哨兵**只是教科书约定**，内核 v6.6 的空孩子就是裸 `NULL`（详见 [05 Ch6 §6.5](../../../05-linux-kernel/chapter-06-kernel-data-structures/notes/section-6.5-二叉树.md)）
4. **红节点的孩子必黑**——禁止红红相连
5. **任一节点到每个叶子的路径，黑节点数量相同**（黑高一致）

## 为什么这就平衡了

| 推理 | 结论 |
|------|------|
| 1. 最短可能路径 | 全黑 |
| 2. **规则 4** 禁止连续红 | 最长路径上红节点数 ≤ 黑节点数 → 最长 ≤ 2 × 该路径黑节点数 |
| 3. **规则 5** 各路径黑节点数相同 | 上面那个黑节点数对**所有**路径一致 → **最长 ≤ 2 × 最短** |

> ⚠️ **别把 2 倍界归给规则 5 单独完成。** 它是 **④ + ⑤ 合力**，缺一不可：规则 5 只管"各路径黑节点数相等"，而**一条纯链的每层子树只有一条路径 → 规则 5 恒真、毫无约束力**。
> 反例（n = 3）：`B → R → R` 单链，四条根到 NIL 路径的黑节点数**全是 1**，规则 5 满足、规则 4 被违反；去掉规则 4 后最大高度随 n **线性增长**（n = 8 时高达 8），加上规则 4 才压到 4。
> 枚举验证与最小反例 → [05 Ch6 §6.5](../../../05-linux-kernel/chapter-06-kernel-data-structures/notes/section-6.5-二叉树.md)

→ 树高 ≤ 2·log₂(n+1)。10 亿节点高最多 ~60。查/插/删稳定 O(log n)，**无退化情况**。

#### 黑高的计数口径（易错点，附内核源码证据）

规则 5 只要求"各路径黑节点数相等"，所以**判定合法性时任意一致口径都行**；但推公式必须统一到 CLRS，否则定理对不上：

| 维度 | CLRS / 算法导论 | 常见"含起点"口径 | Linux 内核 |
|---|---|---|---|
| 计入**起点 x 自身**？ | **不计** | 计 | 无此概念 |
| 计入 **NIL**？ | **计**（NIL 是黑） | 计 | 无 NIL，空子树是 `NULL` |
| 有没有"黑高"这个量 | 有：`bh(x)` | — | **没有**，内核不计算也不存储 |

**为什么必须统一到 CLRS 口径**：核心定理"以 x 为根的子树至少含 `2^bh(x) − 1` 个内部节点"依赖 bh **不含 x**；换成"含起点"的口径，公式要改写成 `2^(bh−1) − 1`。

**内核侧硬事实**（`include/linux/rbtree_augmented.h`、`include/linux/rbtree.h`、`lib/rbtree.c`）：

1. `grep NIL rbtree.c rbtree.h rbtree_augmented.h` → **零命中**。内核没有 NIL 哨兵对象，也没有任何"黑高"计算。空子树就是 `NULL`，颜色语义上等价黑。⚠️ 所以"内核黑高不计 NIL"是错误表述 —— **这个量在内核里根本不存在**，不是口径差别。
2. `RB_RED = 0`、`RB_BLACK = 1`（`rbtree_augmented.h:171-172`）—— **与多数教材相反**，教材习惯写 RED=1。
3. `rb_link_node()` 里没有一句染色代码，颜色位取自 parent 指针对齐后恒为 0 的低位，而 0 就是 `RB_RED`：

```c
static inline void rb_link_node(struct rb_node *node, struct rb_node *parent,
                                struct rb_node **rb_link)
{
        node->__rb_parent_color = (unsigned long)parent;   /* 颜色位 = 0 = RB_RED */
        node->rb_left = node->rb_right = NULL;             /* 空子树 = NULL，无哨兵 */
        *rb_link = node;
}
```

4. `rb_red_parent(red)` 直接把 `__rb_parent_color` 当指针返回 —— 只有该节点确实是红（颜色位 0）时才成立，是个自检式 API。
5. `__rb_insert()` 循环的 `if (unlikely(!parent))` 分支 = 空树或 Case 1 递归到根，用 `rb_set_parent_color(node, NULL, RB_BLACK)` 强制染黑收尾 —— 规则 2（根必黑）就落在这里。

## 红与黑到底是什么

**物理层面：只是一个 bit。** 颜色没有任何独立语义，是给修复算法看的记账位。Linux 内核连这 1 位都不单独存——塞进父指针的低位：

```c
struct rb_node {
    unsigned long __rb_parent_color;  // 父指针 + 颜色打包：对齐保证低 2-3 位恒 0，bit0 放颜色
    struct rb_node *rb_right;
    struct rb_node *rb_left;
};
/* rb_is_red(n) 就是 !(__rb_parent_color & 1) —— 零额外内存 */
```

> 指针低 bits 藏标志是内核通用技巧：buddy allocator 的 page flags、slab freelist 都这么白嫖对齐填充。

> **常见误区（全错）：** 黑 = 重要、红 = 不重要；红节点数值更小；红黑代表优先级或冷热。
> 颜色只有一个目的 —— 标记"这算不算一层"，把最长路径压到最短路径的 2 倍以内，保证 O(log n)。
> 好用的比喻：黑色节点是**台阶骨架**，每条路的台阶数必须一样；红色节点是**插在台阶之间的缓冲**，可以拉长路径但不能连续拉长。

**直觉层面：颜色是"到父节点的边"的颜色。**

| 边 | 几何含义 |
|----|----------|
| 黑边 | 向下走一层（真下一层） |
| 红边 | 横向（还停在这一层） |

规则 5 翻译过来就是 **所有叶子同深度**——一棵真平衡树藏在红黑树里，红节点是同层挤不下、暂挂黑节点边上的成员。把红节点与黑父亲"粘"成超级节点，红黑树即 **2-3-4 B 树**，黑高 = B 树高；全部旋转/变色规则对应 B 树的节点分裂/合并。

**一句话：红黑不是内容，是坐标——标记"这算不算一层"。**

## 遍历顺序：先 / 中 / 后（"先中后" = 根何时被访问）

一棵二叉树只涉及三件事：**访问根**、**遍历左子树**、**遍历右子树**。名字里的先/中/后，指的就是**根在第几个被访问**：

| 顺序 | 访问次序 | 例子（根 5，左 3，右 7） |
|------|----------|--------------------------|
| 先序 | 根 → 左 → 右 | 5 → 3 → 7 |
| 中序 | 左 → 根 → 右 | **3 → 5 → 7（有序！）** |
| 后序 | 左 → 右 → 根 | 3 → 7 → 5 |

**关键结论：BST 的中序遍历 = 从小到大有序序列。** 红黑树继承 BST，中序同样有序。推论直接连回 CFS：

- 中序的第一个节点 = **树的最左节点** = key 最小
- CFS 缓存的 `rb_leftmost` / `rb_first()` 拿的就是它 → **下一个该跑的任务**

> 遍历顺序是旋转操作的"安全带"：旋转会改变树的形状，但**中序顺序恒定不变**，所以 BST 语义在旋转后依然成立。

## 坏了规矩怎么修：变色 + 旋转

插入默认染红（不动黑高），可能造出"红红相连"；删除可能让某路径少一个黑节点。

> **染红的唯一例外：空树。** 新节点成为根，规则 2 要求根必须黑 → 直接染黑，一条规则都没破（全树就它一个，黑高自然一致）。准确说法是 **"除空树外，新插入节点一律染红"**。内核 `rb_insert_color()` 开头判断无父节点即置黑，走的就是这条。

修复只有两招：

- **变色**：调整红黑分布，平衡两边的黑节点计数
- **旋转**：父子上位换位 + 中间子树过继。左旋/右旋 = **O(1) 的几次指针改写**，中序顺序不变（BST 性质保持）。展开见下。

### 旋转到底改了哪几个指针

记 `x = y->rb_left`，**右旋 y** 就是让 x 上位、y 降为 x 的右孩子，x 原来的右子树 B **过继**给 y 当左孩子：

```
        y                      x
       / \                    / \
      x   C    右旋 y  →     A   y
     / \                        / \
    A   B                      B   C
```

只动三个链接（父指针另算）：

```c
/* 概念伪代码，真实实现见 lib/rbtree.c: __rb_rotate_right() */
y->left  = x->right;               /* 1. B 过继给 y 当左孩子 */
x->right = y;                      /* 2. y 下降为 x 的右孩子 */
rb_set_parent(x, old_parent_of_y); /* 3. x 上位，接管 y 原来的位置 */
```

**左旋完全镜像** —— `y = x->rb_right` 上位，x 降为 y 的左孩子，y 原来的左子树 B 过继给 x 当右孩子：

```
      x                        y
     / \      左旋 x  →       / \
    A   y                    x   C
       / \                  / \
      B   C                A   B
```

```c
x->right = y->left;                /* 1. B 过继给 x 当右孩子 */
y->left  = x;                      /* 2. x 下降为 y 的左孩子 */
rb_set_parent(y, old_parent_of_x); /* 3. y 上位 */
```

两种旋转的中序都是 **A → x → B → y → C**，前后完全一致 —— **旋转重排形态，不重排顺序**，这是它敢被用在 BST 上的底气。

> 这也是"能变色就不旋转"的原因：变色一个指针都不动；旋转要改子树链接 + 父指针 + 祖父指向，cache 与指针 chase 都有成本。内核 `lib/rbtree.c` 里 `__rb_rotate_left()` / `__rb_rotate_right()` 共用 `__rb_rotate_set_parents()` 统一处理父指针与颜色。

策略：看叔叔节点——红叔叔 → 变色上移递归；黑叔叔 → 旋转 1-2 次收尾。
**插入最多 2 次旋转，删除最多 3 次**，其余靠变色。

### 插入修复的三个具体情形

记 N = 新插入节点（红）、P = 父、G = 祖父、**U = 叔叔（P 的兄弟）**。修复全靠看 U 的颜色和 N 的位置：

**① U 是红色 → 纯变色，把矛盾往上推**

```
        G(B)                    G(R)  ← 当新节点继续向上检查
       /    \       变色       /    \
     P(R)  U(R)    ───►     P(B)  U(B)
     /
   N(R)
```

P、U 一起染黑（局部黑高不变），G 染红补偿。G 若因此与它的父亲红红相连，就把 G 当新节点递归。一路传到根就染黑收尾。

**② U 是黑色 + N 在外侧（LL / RR）→ 旋转 1 次**

```
        G(B)                  P(B)
       /    \     右旋 G     /    \
     P(R)  U(B)   ───►    N(R)   G(R)
     /                              \
   N(R)                            U(B)
```

G 染红、P 染黑，然后对 G 右旋（RR 情形镜像左旋）。一次收尾，不再递归。

**③ U 是黑色 + N 在内侧（LR / RL）→ 先转成 ②，再旋转**

```
      G(B)            G(B)              N(B)
     /    \    左旋 P /    \   右旋 G   /    \
   P(R) U(B)  ───►  N(R) U(B)  ───►  P(R)  G(R)
     \              /                        \
     N(R)        P(R)                       U(B)
```

先对 P 左旋，把"内侧"掰成"外侧"，退化成情形 ②，再对 G 右旋 + 变色。**这就是"最多 2 次旋转"的来源。**

> 记忆：叔叔红 → 不动结构（变色上移）；叔叔黑 → 动结构（旋转）。能不能只变色不旋转，是修复成本的分水岭。
>
> 内核源码逐行对照（`lib/rbtree.c:110-217` 的 Case 1/2/3、`rb_link_node` 为什么"天然是红"、`RB_EMPTY_NODE` 自标未插入）→ [05 Ch6 §6.5](../../../05-linux-kernel/chapter-06-kernel-data-structures/notes/section-6.5-二叉树.md)

#### 四个容易漏的细节

1. **叔叔红要上溯，叔叔黑就地收工。** 叔叔红时祖父被染红，可能又和它父亲红红相连，得把祖父当新节点往上传；叔叔黑时旋转 + 染色后子树根是**黑色**的，该子树黑高已恢复原样，直接结束。
2. **最后一步恒为：根强制染黑。** 规则 2 是硬性的。叔叔红一路传到根时根会被染红，靠收尾那句 `rb_set_black(root->rb_node)` 拉回 —— 这也是唯一允许"整棵树黑高 +1"的时刻。
3. **情形 ③ 左旋后角色互换**：原父 P 沉下去成为"当前节点"，原新节点 N 升上去。进入情形 ② 时"新节点"已经不是刚插进去的那个了，画图画错多半栽在这里。
4. **染色与旋转谁先谁后无所谓** —— 旋转只改指针、不碰颜色，两种顺序结果完全相同（CLRS 的写法是先染色后旋转）。

> **插入的最好情况是 O(1)**：父节点是黑时规则 4 无从违反、规则 5 不受影响（红不贡献黑高），修复循环一次都不进。判据就是那句 `if (rb_is_black(parent)) break;`。CFS 的大部分 enqueue 走这条快路径。

#### 插入的黑高账本：只有"根染黑"那一步能动全局 bh

三个情形对**黑高**的实际影响，和"要不要往上传递"是两件事，容易混在一起：

| 情形 | 局部 bh | 结构 | 是否上溯 | 全局 bh |
|---|---|---|---|---|
| ① 叔叔红：P、U 染黑，G 染红 | **净不变**（+1 与 −1 抵消） | 不动 | ✅ 把 G 当新节点继续 | 仅当传到根时 +1 |
| ② 叔叔黑 + 内侧：左旋 P | 不变（旋转不碰黑高） | 动 | ❌ 直接转 ③ | 不变 |
| ③ 叔叔黑 + 外侧：右旋 G + P黑/G红 | 不变 | 动 | ❌ 收工 | 不变 |

一句话：**插入的每一步局部操作都不改变黑高**（① 是 +1/−1 抵消，②③ 是纯粹换形状）；
**唯一能让整棵树黑高变化的是收尾那句 `rb_set_black(root)`，且只有 Case 1 一路传到根时它才真的起作用。**

```
        G(B)              G(R)               G(B)      ← 强制染黑
       /    \   变色     /    \             /    \
     P(R)  U(R) ───►  P(B)  U(B)  ───►   P(B)  U(B)
     /                /                  /
   N(R)             N(R)               N(R)

 bh = 2            bh = 2              bh = 3  ← +1，但树高一点没变
```

⚠️ 注意这里有个反直觉的点：**bh +1 而树高不变** —— 一个节点都没加，只是根从红变回黑、P/U 由红变黑。
黑高不是高度，它是"路径上黑节点的计数"，会随重染色单独漂移。

**为什么根可以随便染黑而不破坏规则 5？** 因为根是**唯一位于所有路径上**的节点：改它的颜色给每条路统一 ±1，"各路黑高相等"这个等式不可能被打破。换任何其他节点都不行（只影响部分路径）。也正因如此，它不必引起后续修复 —— 变黑只会更保守，不可能造出新的红红相连。

内核源码里这一步连注释都写明了（`lib/rbtree.c` `__rb_insert()`）：

```c
if (unlikely(!parent)) {
        /*
         * The inserted node is root. Either this is the
         * first node, or we recursed at Case 1 below and
         * are no longer violating 4).
         */
        rb_set_parent_color(node, NULL, RB_BLACK);   /* 一条指令同时写父指针 + 颜色位 */
        break;
}
```

> 顺带一个常见误读：**"叔叔黑"里包含了"没有叔叔"**。内核判据是 `if (tmp && rb_is_red(tmp))` ——
> `tmp` 为 NULL 时直接落到 Case 2/3，即 **NULL 叔叔按黑处理**（与 NIL 哨兵等价）。
> 内核没有 NIL 对象，空子树就是 `NULL`，颜色语义上算黑。

## 删除：颜色为什么最难

插入最多只是"多出一对红红"；删除会**真的弄丢一个黑节点**，黑高实打实少 1。

### 先明确：被摘掉的不一定是"你要删的那个"

BST 删除时若节点有两个孩子，做法是**用中序后继的值覆盖它，然后摘掉后继**。所以下面说的"被删节点的颜色"，指的是**实际从树上摘下来的那个节点**的颜色。

### 三档代价

| 被摘掉的节点 | 后果 | 修复 |
|---|---|---|
| **红色** | 黑高不变 | **不用修**，直接摘 |
| **黑色 + 有红孩子** | 少一个黑 | 红孩子顶替并**染黑**，黑高补回，一步收工 |
| **黑色 + 无红孩子** | 少一个黑且无处补 | **双黑**，向上借，最多 3 次旋转 |

> **为什么"摘掉红色不用修"？** 红节点不可能只有单个孩子 —— 有孩子就必是黑的（规则 4），
> 而这个黑孩子会让本路径黑高 +1、另一侧 NIL 路径不变，当场违反规则 5。
> 所以红节点要么无孩子，要么有两个黑孩子（后者删除时摘的是后继）。
> **结论：实际被摘掉的红节点必然是叶子**，摘掉后黑高一个不变。

### 双黑是什么

黑色的 X 被摘掉后，顶替它的 NIL 节点"欠一个黑" —— 它本身是黑 NIL，又多背了一份黑，故称**双黑**。修复就是给这份多余的黑找地方安置，看兄弟（sibling）的颜色：

| 兄弟情况 | 动作 |
|---|---|
| 兄弟是**红** | 旋转让兄弟上位并染黑 → 转成"兄弟是黑"再处理 |
| 兄弟黑 + **有红侄子** | 借到了：旋转 + 染色，双黑消除，结束 |
| 兄弟黑 + **无红侄子** | 借不到：兄弟染红（两边各少一个黑），双黑**上移给父亲**，继续循环 |
| 一路传到根 | 根吸收这份多余的黑（整树黑高 −1），结束 |

> **反直觉对照**：插入是"叔叔黑就地收工、叔叔红才上溯"；删除正好反过来 —— **借得到就地收工，借不到才上溯**。这也是"删除最多 3 次旋转"的来源。

内核实现见 `lib/rbtree.c` 的 `rb_erase()` + `__rb_erase_color()`；CFS 的 `dequeue_task_fair()` 每次摘任务都会走到这里。

## 为什么内核选红黑树而不是 AVL

| | AVL | 红黑树 |
|---|------|--------|
| 平衡严格度 | 高（高度差 ≤1），树更矮 | 松（最长 ≤2×最短） |
| 查找 | 更快 | 略慢（树稍高） |
| 插入/删除 | 旋转可能一路传到根 | 最多 2/3 次旋转 |

内核容器是**写密集**的：CFS 每次 tick / 唤醒 / 休眠都插树删树。红黑树用"松一点的平衡"换"更低的修改成本"。工程取舍，不是谁绝对更好。

## 落回 CFS

```c
struct rb_root_cached {
    struct rb_root rb_root;        // 按 vruntime 排序的红黑树
    struct rb_node *rb_leftmost;   // 最左节点缓存 → pick_next O(1)
};
```

| 要点 | 说明 |
|------|------|
| **key = vruntime** | 中序遍历 = vruntime 升序；最左 = 最"饿"的任务 |
| **侵入式** | `rb_node` 内嵌在 `sched_entity` 里（同 `list_head` 设计），一个结构体可同时挂多个容器，零额外分配 |
| **增删时机** | `enqueue_task` 插树、`dequeue_task` 摘树、`update_curr` 改 key 后 reposition |

**内核其他红黑树用户：**

| 用户 | 场景 |
|------|------|
| VMA 查找（`find_vma`） | 每次 page fault / mmap 都走——6.1 起 maple tree 接班（cache locality 更好） |
| ext4 extent tree | 文件物理块区间 |
| CFQ I/O 调度器 | 请求按扇区排序 |
| `rbtree_augmented` | 带子树聚合信息的增强版 |

## HFT 关联

- 红黑树节点散布在堆上，**cache locality 一般**——这是 VMA 换 maple tree 的动机之一，也是 CFS 热路径上 `sched_entity` 尽量 per-CPU 级联缓存的原因
- 自研撮合/订单簿绝不用红黑树遍历——但理解内核为什么用它，是判断"自己场景该用什么容器"的参照系

<summary>自测题（点击展开）</summary>

**Q1:** 红黑树最长路径为什么最多是最短路径的 2 倍？

> 三件事合力，缺一不可：① 最短路径全黑；② **规则 4** 禁止连续红 → 最长路径上红节点数 ≤ 黑节点数，得"最长 ≤ 2 × 该路径黑节点数"；③ **规则 5** 保证所有路径黑节点数相同 → 那个数对每条路径都一样，于是上限收紧成 2 × 最短。
> 注意 ② 和 ③ 不能互相替代：光有规则 5 只说明"各路径黑节点数相等"，一条纯链也满足它（见上文 n = 3 反例），真正压住高度的是规则 4。

**Q2:** 插入新节点为什么默认染红而不是黑？

> 染黑必然破坏规则 5（该路径黑高 +1，其他路径没变），需要修复；染红不碰黑高，只有规则 4（红红相连）可能被破坏，修复面更小。

**Q3:** 旋转改变 BST 的中序遍历结果吗？为什么内核修复红黑树优先变色？

> 不改变——旋转只重排父子关系并过继中间子树，中序顺序恒定，BST 语义不变。变色不碰任何指针（纯写节点颜色），比旋转更便宜；策略上能变色解决就不旋转。

**Q4:** CFS 用堆（找最小 O(1)）替代红黑树行不行？

> 摘除任意中间节点（任务休眠 dequeue）在堆里是 O(n) 定位 + O(log n) 下沉，红黑树持有节点指针可 O(1) 定位、O(log n) 摘除。调度场景频繁摘任意节点，堆不合适。

**Q5:** 顺序插入 1、2、3，红黑树长什么样？走了哪个修复情形？

> 插 1 → 根，染黑。插 2 → 1 的右孩子，红（此时合法）。插 3 → 2 的右孩子，红，与 2 红红相连。此时 N=3、P=2、G=1、**U = 1 的左孩子 = NIL（黑）**，且 N 在外侧（RR）→ 情形 ②：1 染红、2 染黑、对 1 左旋。结果 **2 为根（黑），左孩子 1（红）、右孩子 3（红）**。一次旋转收尾，无需递归。

**Q6:** 新插入的节点如果染成**黑色**会怎样？为什么默认染红？

> 插黑必然破坏规则 5：插入点所在路径黑高 +1，其余路径一个数都没变，且从插入点到根的所有祖先的黑高都被破坏；没有任何局部操作能凭空减掉其他路径上的黑节点，修复要动到整棵树的结构。染红不碰黑高，最坏只是规则 4 的红红相连，变色或 1~2 次旋转就能在局部收尾。唯一例外是空树插入 —— 新节点就是根，按规则 2 必须染黑。

**Q7:** 旋转会不会破坏 BST 的性质？

> 不会。旋转只重排父子关系并把中间子树过继，中序遍历顺序（A → x → B → y → C）旋转前后完全一致，BST 的"左 < 根 < 右"语义保持。所以旋转是纯粹的几何操作：压低偏高的一侧，不动排序。

**Q8:** 插入新节点后，父节点是黑色，需要修改新节点的颜色吗？

> 不需要，一个 bit 都不用动。父是黑 → 规则 4 无从违反；红节点不贡献黑高 → 规则 5 不变；新节点的两个孩子是 NIL 本就算黑；根不是它。五条全满足，修复循环一次都不进 —— 判据就是 `while (parent && rb_is_red(parent))`。**插入的最好情况是 O(1)。**

**Q9:** 删除一个红色节点为什么不用修复？直接说"红不影响黑高"够不够？

> 结论对但理由不完整，还差一步：红节点**不可能只有单个孩子** —— 有孩子就必是黑的（规则 4），而这个黑孩子会让本路径黑高 +1、另一侧 NIL 路径不变，当场违反规则 5。所以红节点要么无孩子，要么有两个黑孩子（后者删除时真正被摘掉的是中序后继）。**被摘掉的红节点必然是叶子**，摘掉后黑高一个不变，因此无需修复。

**Q10:** 红色节点 A，左边挂一个黑孩子（再往下是 NIL），右边直接是 NIL。两条路径各几个黑？合法吗？

> 路径 1（A → 黑孩子 → NIL）= 黑孩子 + NIL = **2 个黑**；路径 2（A → NIL）= **1 个黑**。2 ≠ 1 → **违反规则 5**，不是合法红黑树。这正是"红节点不可能只有单侧孩子"的实例。（本题起点 A 是红色、不计入黑高，所以"含起点"口径与 CLRS 口径结果相同 —— 差异只在起点为黑时才体现。）

**Q11:** CLRS 的 `bh(x)` 计不计起点 x 自身？这个差别为什么重要？

> **不计**（但计入 NIL）。差别只在推公式时致命：定理"以 x 为根的子树至少含 `2^bh(x) − 1` 个内部节点"依赖这个口径；若改用"含起点"的口径，公式要写成 `2^(bh−1) − 1`。反过来，若只是判断一棵树是否合法（比的是各路径"相等"），任意一致口径都可以。另注：**内核里根本没有黑高这个量**（`grep NIL` 零命中、无 bh 字段），它靠修复算法隐式维持性质 5。

**Q12:** Case 1 一路把红冲突推到根、根被染红之后，为什么最后强制把根改成黑色？会影响什么？

> 三层理由：① 规则 2 是红黑树定义的一部分，硬性的；② **安全** —— 根是唯一位于所有路径上的节点，改它的颜色给每条路统一 ±1，规则 5 的"各路黑高相等"不可能被打破，换任何其他节点都只影响部分路径而破坏等式；③ 变黑只会更保守，不可能造出新的红红相连，因此它是**无条件可终止的收尾**，不需要再检查。
> 影响只有一个：整棵树黑高 **+1**。而且它不改变树高 —— 一个节点都没加，只是根由红变回黑、P/U 由红变黑，这是"bh +1 而高度不变"的典型例子（黑高不是高度）。每次插入最多发生一次，O(1)。内核落点：`__rb_insert()` 里那个 `if (unlikely(!parent))` 分支，注释原文 "Either this is the first node, or we recursed at Case 1 below"。

**Q13:** 插入三情形里，哪些会改变（局部/全局）黑高？

> **局部：一个都不改。** 情形 ① 是 +1（P、U 染黑）与 −1（G 染红）抵消，净零；情形 ② 旋转不碰黑高；情形 ③ 旋转 + 换色同样净零（G 侧路径由"G 黑 + U 黑"变成"P 黑 + G 红 + U 黑"，计数相同）。
> **全局：只有收尾那次根染黑**，且需 Case 1 真的传到根才生效。所以插入全程 bh 单调不减，且每次最多 +1。
> 对照删除：双黑传到根时由根**吸收**，全局 bh −1 —— 根是黑高的"总闸门"，增减都在这里结算。
