21.1

概述

Ch 20 广播 · 21.2 地址 · study.md

核心主旨

模式 问题
广播（Ch 20） 子网所有主机处理包；难跨 WAN
多播 仅 Join 的接收者收包；可经多播路由跨网

多播两大优势

  1. 精准分发：未加入组的主机，网卡硬件常直接丢弃多播帧
  2. 广域网：支持多播路由时可在 WAN 分发

重点结论

  • 仅 UDP（与广播相同），TCP 不支持
  • IPv6 用多播替代广播（Ch 20）

资料说明

上传资料截至第 8 章；第 21 章按 UNP 第 3 版体系整理，请与全本对照验证。

个人学习总结

组播 = 一对多——发送一次，感兴趣的接收者（组员）都收。比广播高效：只有加入组的主机才处理。

一句话：组播是 UDP 的扩展——用 D 类地址（224.0.0.0~239.255.255.255），靠 IGMP/MLD 管理组员。

HFT 关联：交易所行情组播是标准做法——一个网关发送，多个策略进程接收。

21.2

多播地址

逻辑组

多播地址标识组（Group），非单台主机。

IPv4（D 类）

项 内容
范围 224.0.0.0 – 239.255.255.255
全节点 224.0.0.1
全路由器 224.0.0.2

MAC 映射（IANA）

  • 以太网多播 MAC：01:00:5E:00:00:00 – 01:00:5E:7F:FF:FF
  • 低 23 位 来自 IPv4 多播地址低 23 位

32:1 碰撞

组 ID 有 28 位，MAC 只用 23 位 → 每 32 个 IPv4 多播 IP 映射到同一 MAC → IP 层须软件核对完整组地址。

IPv6

项 内容
前缀 ff00::/8
结构 Flags(4) + Scope(4) + Group ID(112)
Scope 节点/链路/站点/组织/全球等边界
MAC 低 32 位 → 前缀 33:33 后

个人学习总结

IPv4 组播地址：224.0.0.0/4。IPv6：ff00::/8。

MAC 映射：IPv4 组播 MAC = 01:00:5e + 低 23 位——导致 32 组地址映射到同一 MAC（碰撞）。

特殊范围：224.0.0.0/24 本地网络（TTL=1 不路由）；239.0.0.0/8 管理域专用。

MAC 碰撞意味着网卡可能收到不想要的组播包——需在 IP 层过滤。

21.3

局域网上多播和广播的比较

Ch 20.3

广播（回顾）

全子网网卡收帧 → 中断 → IP → UDP → 无监听端口才丢 → 无辜主机 CPU 浪费。

多播过滤

情况 行为
未 Join 该组 网卡未配置该多播 MAC → 硬件丢弃，CPU 无感
已 Join 网卡放行 → 因 32:1 MAC 碰撞，IP 层再比对完整多播 IP → UDP

重点结论

过滤从软件协议栈下推到网卡硬件 — 多播相对广播的核心优势（LAN 上）。

个人学习总结

LAN 组播：发送方无需加入组，只需 sendto 组播地址。接收方需 join（setsockopt IP_ADD_MEMBERSHIP）。

IGMP：接收方通过 IGMP 向路由器声明"我要加入这个组"——路由器据此决定是否转发组播。

一句话：LAN 组播 = 接收者 join + 发送者直接 sendto 组地址。

21.4

广域网上的多播

两层协议

1. 主机 ↔ 本地路由器（组管理）

协议 用途
IGMP（IPv4） 主机 Join 后向路由器报告
MLD（IPv6，ICMPv6） 同上

机制：宣告「本子网有接收者，请转发该组」。

2. 多播路由器之间

PIM、DVMRP、MOSPF 等 → 构建 多播分发树，避免环路，在分支复制报文。

与套接字 TTL

默认 TTL/hops=1 时多播不出子网；跨 WAN 须调大 TTL 且 路径上路由器支持多播路由。

个人学习总结

WAN 组播需要路由器支持组播路由协议（PIM）——跨子网传递组播流量。

TTL 控制：TTL=1 限本子网；TTL=64 到达组织内；TTL=255 可达全局。

一句话：WAN 组播 = IGMP（组员管理）+ PIM（路由器间传递）+ TTL（范围控制）。

HFT 关联：交易所行情通常在 LAN 内组播——不需要跨 WAN。

21.5

源特定多播

ASM（任意源多播）

传统模型：Join 组 G 后，接收任意源发往 G 的数据 → 易被伪造源/垃圾流量攻击。

SSM（源特定多播）

项 说明
绑定 组 G + 合法源 S
要求 IGMPv3（IPv4）或 MLDv2（IPv6）
优势 抗欺骗、简化路由（以 S 为根的源树）

套接字：IP_ADD_SOURCE_MEMBERSHIP 等（21.6）。

个人学习总结

SSM（Source-Specific Multicast）= (S, G) 模式——接收者指定"只收来自源 S 的组 G 的数据"。

优势：避免任意源注入伪造数据；无需全网组员发现协议；路由器只需维护 (S, G) 状态。

一句话：SSM = "只收指定源的组播"——更安全、更可扩展。

HFT 关联：交易所行情用 SSM——确保只收交易所网关的数据，防伪造。

21.6

多播套接字选项

Ch 7.2 setsockopt · 21.7 mcast_*

级别

IPPROTO_IP / IPPROTO_IPV6 + setsockopt。

1. 加入/离开组（接收必备）

族 加入 离开 结构
IPv4 IP_ADD_MEMBERSHIP IP_DROP_MEMBERSHIP ip_mreq（组 IP + 接口 IP）
IPv6 IPV6_JOIN_GROUP IPV6_LEAVE_GROUP ipv6_mreq（组 + 接口 index）
SSM IP_ADD_SOURCE_MEMBERSHIP 等 含源 IP

2. 外出接口（发送）

IP_MULTICAST_IF / IPV6_MULTICAST_IF — 强制从指定网卡发多播。

3. TTL / 跳数

IP_MULTICAST_TTL / IPV6_MULTICAST_HOPS

  • 默认常 1（仅本地子网）
  • 跨路由器须显式增大

4. 回环 Loopback

IP_MULTICAST_LOOP / IPV6_MULTICAST_LOOP

  • 默认 1：本机也 Join 时，收到自己发的多播
  • 设 0 可省本机处理

个人学习总结

组播套接字选项：IP_ADD_MEMBERSHIP（加入组）、IP_DROP_MEMBERSHIP（离开组）、IP_MULTICAST_TTL（设 TTL）、IP_MULTICAST_IF（指定发送接口）、IP_MULTICAST_LOOP（控制环回）。

一句话：加入组用 IP_ADD_MEMBERSHIP(imr_interface, imr_multiaddr)，发送用普通 sendto 组地址。

IP_MULTICAST_LOOP 默认开——本机发送的组播会回送到本机接收者。

21.7

mcast_join 和相关函数

Ch 11 getaddrinfo · 21.6

协议无关封装

屏蔽 ip_mreq / ipv6_mreq 与选项宏差异：

函数 作用
mcast_join(sockfd, grp, grplen, ifname, ifindex) 按 sockaddr 族自动 setsockopt 加入
mcast_leave 离开组
mcast_set_loop 回环
mcast_set_ttl TTL/hops

个人学习总结

Stevens 封装 mcast_join/leave/if/ttl/loop/set_if——统一 IPv4/IPv6 组播操作。

mcast_join 关键：自动处理 IPv4 (ip_mreq) vs IPv6 (ipv6_mreq) 差异 + 接口索引查找。

一句话：mcast_join 封装屏蔽了 v4/v6 结构体差异——协议无关组播编程。

多个接收者可同时加入同一组——内核维护组员计数。

21.8

使用多播的 dg_cli 函数

Ch 20.4 广播 dg_cli · Ch 8 UDP

发送端

与单播 UDP 客户几乎相同 — 目的地址改为 D 类 / ff00:: 多播地址即可 sendto。

易错细节

点 说明
发送方通常不必 Join 合法多播目的即可发出
跨子网 可能需 mcast_set_ttl 增大跳数
勿与广播混淆 不需要 SO_BROADCAST

个人学习总结

组播版 dg_cli：发送方 sendto 组地址（无需 join）；接收方 bind 组端口 + join 组 + recvfrom。

一句话：组播发送 = 普通 UDP sendto 组地址；组播接收 = bind + join + recvfrom。

bind 端口而非组地址——组地址通过 IP_ADD_MEMBERSHIP 加入。

21.9

接收 IP 多播基础设施会话声明

案例：SAP / SDP（MBone）

音视频会议会话经 SAP + SDP 多播宣告。

接收步骤

1. socket(UDP)
2. setsockopt(SO_REUSEADDR)   /* bind 前，多进程同端口 */
3. bind(多播端口，如 SAP 9875)
4. mcast_join(组 224.2.127.254 等)
5. recvfrom 循环，解析 SDP 文本

铁律

接收多播且 bind 固定端口 → 必须先 SO_REUSEADDR（Ch 7.5）。

个人学习总结

SAP（Session Announcement Protocol）= 在固定组播组 224.2.127.254:9875 上宣告组播会话。SDP（Session Description Protocol）描述会话内容。

一句话：SAP/SDP 是组播会话的"目录服务"——自动发现有哪些组播会话可用。

HFT 不用 SAP/SDP——行情组播地址和端口是预配置的。

21.10

发送和接收

21.6 loop · 21.8

同进程既发又收

  • 常共用一个 UDP 套接字
  • mcast_join 后 sendto 多播地址 → 内核组播发送
  • 默认 loop=1 → 本机 recvfrom 也能收到自己发的包

避免自己响应自己

应用层处理：

  • 包头带 UUID / 本机 IP
  • recvfrom 后若来源为自己 → 丢弃

个人学习总结

组播收发实战：发送方设 IP_MULTICAST_TTL + IP_MULTICAST_IF；接收方 bind + IP_ADD_MEMBERSHIP + SO_REUSEADDR。

关键：多个接收者 bind 同一端口必须设 SO_REUSEADDR——否则第二个 bind 失败。

SO_REUSEADDR 对 UDP 的语义不同于 TCP——允许多个 socket bind 同端口。

21.11

SNTP：简单网络时间协议

场景

模式 压力
单播 NTP 每台客户端请求 → 服务器并发巨大
多播 NTP/SNTP 服务器周期广播时间 → 客户端被动收

多播地址

  • IPv4：224.0.1.1
  • IPv6：ff02::101（链路本地等，以部署为准）

客户端设计

bind(NTP 端口 123) + mcast_join(上述组)
→ recvfrom 阻塞
→ 收到一包 → 校时 → 可退出

性能：服务器负载近似恒定低频多播，客户端规模理论上可极大扩展。

个人学习总结

SNTP（Simple NTP）= 简化版 NTP，常用组播模式：服务器周期性组播时间戳，客户端接收校准。

一句话：SNTP 组播 = 服务器 224.0.1.1:123 定期发时间戳 → 客户端被动接收校准。

HFT 关联：时间同步是 HFT 基础设施——组播 SNTP 比 PTP 简单但精度低（毫秒级 vs 微秒级）。

21.12

小结

study.md

章节核心提炼

1. 相对广播

硬件过滤 +（可选）WAN 多播树 — 降维打击广播的「全子网纳税」。

2. 收发不对等

角色 要求
发 向多播地址 sendto；调 TTL/接口/loop；通常不必 Join
收 IP_ADD_MEMBERSHIP / mcast_join + IGMP/MLD；bind 前 SO_REUSEADDR

3. 地址与碰撞

  • IPv4 D 类；IPv6 ff00::/8 + Scope
  • 32:1 MAC 映射 → IP 层二次过滤

4. 安全演进

ASM → SSM（IGMPv3 / MLDv2）绑定合法源。

广播 vs 多播速记

广播 多播
过滤 子网全体 仅 Join 者（+硬件）
WAN 一般不转发 多播路由
套接字 SO_BROADCAST ADD_MEMBERSHIP 等
IPv6 无 标准

个人学习总结

组播 = 一对多 UDP。接收方 join（IP_ADD_MEMBERSHIP），发送方直接 sendto 组地址。

关键选项：IP_ADD/DROP_MEMBERSHIP、IP_MULTICAST_TTL/IF/LOOP、SO_REUSEADDR（多接收者同端口）。

SSM = (S,G) 模式，更安全可扩展。IPv4 MAC 碰撞需 IP 层过滤。

HFT 关联：交易所行情组播 + SSM 是标准做法；DPDK 有 rte_eth 组播过滤支持。
