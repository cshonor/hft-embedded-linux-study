24.1

概述

Ch 14.3 MSG_OOB · 24.2 TCP OOB · study.md

核心主旨

带外数据（OOB, Out-of-Band）：独立于普通流、用于优先/快速传递控制信息的逻辑通道。

协议 实现
概念 优先通道
TCP 无独立通道 → 紧急模式（Urgent Mode）：头部 URG + 紧急指针

设计初衷：普通数据因流控阻塞时，仍能传递重要控制信息。

资料说明

上传资料截至第 8 章；目录含第 24 章但正文缺失。第 24 章按 UNP 第 3 版体系整理，请与全本对照验证。

个人学习总结

TCP 带外数据（OOB）= 紧急数据——通过 URG 标志 + 紧急指针在 TCP 头中标记，不占用数据流位置。

一句话：OOB 是 TCP 的"加急通道"——1 字节紧急数据可"跳过"普通数据被优先接收。

现代趋势：OOB 基本被废弃——应用层用独立连接或带内标记替代。

24.2

TCP 带外数据

Ch 7.9 TCP 选项

底层机制

TCP 头部：

字段 作用
URG 本段含紧急数据
紧急指针 16 位偏移 + 序号 → 紧急数据结束位置（带外字节序号）

发送

send(fd, "a", 1, MSG_OOB);

陷阱：send(..., "abc", 3, MSG_OOB) 时，标准上通常只有最后一字节（'c'）为带外字节，紧急指针指向它。

接收端通知

机制 说明
SIGURG 须 fcntl(F_SETOWN) 设套接字属主
select 异常 套接字进入 exceptset

可在 OOB 数据体到达前提前通知（仅 URG 头到达时）。

读取：SO_OOBINLINE

模式 SO_OOBINLINE 读法
分离（默认 0） 带外字节进单字节独立缓冲 recv(..., MSG_OOB)
线内（1） 带外字节留在普通流顺序中 普通 read/recv；用 sockatmark（24.3）

个人学习总结

TCP 紧急模式：send 带 MSG_OOB → 设 URG 标志 + 紧急指针指向下一字节。接收方收到 URG → 发 SIGURG（信号驱动）或可用 recv MSG_OOB 读取。

两种读取模式：①MSG_OOB 单独读 1 字节 ②SO_OOBINLINE 嵌入普通数据流。

一句话：OOB 只有 1 字节，多次 send MSG_OOB 只保留最后一个——前一个被覆盖。

TCP 紧急指针的语义在 RFC 793 和 1122 之间有历史差异。

24.3

sockatmark 函数

17.3 SIOCATMARK · 24.2

核心主旨

SO_OOBINLINE=1 时，须判断读指针是否到达带外标记处。

int sockatmark(int sockfd);
返回值 含义
1 下一字节为带外数据 / 正处于标记
0 否
-1 错误

POSIX 替代 ioctl(SIOCATMARK)。

字节流与标记

  • URG 头先到即可触发 SIGURG / select 异常（数据体未到）
  • 读到标记前：read 不跨越标记 — 即使请求 1024 字节，标记在第 5 字节则短读 5
  • 越过标记后才能读后续普通数据

个人学习总结

sockatmark(fd) — 检查当前读位置是否在 OOB 标记处。返回 1 表示下一个 read 的数据就在 OOB 标记之后。

一句话：sockatmark 用于确定"紧急数据之后"的位置——配合 SO_OOBINLINE 使用。

如果 OOB 标记还没到达，read 会阻塞或返回 EWOULDBLOCK（非阻塞时）。

24.4

TCP 带外数据小结

RFC 冲突（历史大坑）

RFC 紧急指针含义
793 指向紧急数据最后一字节的后一字节
1122 指向最后一字节本身

当今多数 Berkeley 系与 Windows 按 1122，并兼容老行为。

覆盖陷阱（Overwrite）

TCP 只有一个带外标记。

连续两次 MSG_OOB，接收端未读第一次 → 后一次覆盖前一次 → 第一个 OOB 字节沦为普通数据。

易错汇总

点 说明
非独立通道 仅 URG 补丁，不可靠、易覆盖
多字节 OOB send 通常仅最后一字节有效
双读模式 分离 vs inline 不可混用 MSG_OOB

个人学习总结

OOB 机制要点：①只有 1 字节 ②多次发送覆盖前一次 ③两种读法（MSG_OOB / SO_OOBINLINE）④sockatmark 定位标记。

一句话：OOB 在 TCP 头中用 URG 标记，不占数据流位置——但实际只 1 字节，用途有限。

多数应用不需要 OOB——telnet 用 OOB 发中断命令（Ctrl-C）是经典案例。

24.5

客户/服务器心搏函数

Ch 7.5 SO_KEEPALIVE · Ch 5 信号

实战场景

工业界 OOB 主要实用场景：应用层心搏（Heartbeat）。

机制 局限
SO_KEEPALIVE 常 ~2 小时 才探测 — 不适合秒级故障感知
OOB 心搏 高频交易、集群监控等

为何用 OOB 而非普通 write？

通告窗口为 0（对端接收缓冲满）时，普通数据发不出；紧急指针机制下 OOB 仍可能发出（绕过流量控制阻塞）。

客户端

SIGALRM 每 1s → send(fd, "1", 1, MSG_OOB)

服务端

F_SETOWN → SIGURG
→ recv(fd, &c, 1, MSG_OOB)
→ 记录最后心跳时间；超时无普通数据且无 SIGURG → 判定客户端死亡，清理

个人学习总结

OOB 心搏模式：定期 send 1 字节 OOB → 对端 SIGURG 或 select 异常事件 → 确认连接存活。

一句话：OOB 心搏 = "我还在"信号——1 字节紧急数据不占带宽，比 SO_KEEPALIVE 间隔可控。

替代方案：应用层心跳包更灵活——OOB 心搏是历史做法，现代用独立心跳消息。

24.6

小结

study.md · Ch 25 信号驱动 I/O

章节核心提炼

1. 逻辑机制 > 物理通道

TCP OOB = 字节流上的 URG + 紧急指针，非第二根线缆 → 易覆盖、语义混乱。

2. 双模式读取

模式 API
分离（默认） recv + MSG_OOB
线内 SO_OOBINLINE + sockatmark

3. 现代地位

除 Telnet 中断（Ctrl+C）、OOB 心搏 外，HTTP/gRPC 等多在应用层用独立控制帧/Stream，几乎不用 TCP 层 OOB。

个人学习总结

TCP OOB = 1 字节紧急数据，通过 URG 标志传输。两种读法：MSG_OOB / SO_OOBINLINE。sockatmark 定位标记。

现代趋势：OOB 基本废弃——应用层心跳、独立信号连接、带内标记都更灵活可移植。

HFT 关联：不用 OOB——行情/交易用应用层心跳+序号检测连接状态。
