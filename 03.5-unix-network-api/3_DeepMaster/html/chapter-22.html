22.2

接收标志、目的 IP 地址和接口索引

14.5 recvmsg · 14.6 辅助数据

业务痛点

bind(INADDR_ANY) 的 UDP 服：recvfrom 只知源地址，不知：

  • 数据报发往本机哪个 IP（多宿主回复）
  • 从哪块网卡收到（接口索引）

机制：recvmsg + 辅助数据

IPv4

选项 辅助数据
IP_RECVDSTADDR 目的 IPv4
IP_RECVIF 接口索引

遍历 cmsghdr：cmsg_level == IPPROTO_IP，类型 IP_RECVDSTADDR / IP_RECVIF。

IPv6

选项 内容
IPV6_RECVPKTINFO 单一 in6_pktinfo（目的地址 + 接口 index）

比 IPv4 分离选项更统一。

个人学习总结

IP_PKTINFO/IPV6_PKTINFO — 通过 recvmsg 辅助数据获取收包的目的 IP和入接口索引。

场景：服务器 bind INADDR_ANY + 多网卡 → 需知数据报到哪个 IP 才能正确回复。

一句话：IP_PKTINFO 告诉你"这个包是发给哪个本地 IP 的"——多网卡回复必须用同一 IP 做源。

用 recvmsg + cmsghdr 获取，不能用 recvfrom。

22.3

数据报截断

14.5 MSG_TRUNC · 14.7 FIONREAD

核心异常

UDP 报文长度 > 用户缓冲区 → 截断（超出部分丢弃）。

各平台差异（排错重灾区）

行为 说明
Berkeley 传统 静默截断，无错误
SVR4 返回错误，errno = EMSGSIZE
POSIX / 现代 用 recvmsg 时 msg_flags 含 MSG_TRUNC

重点结论

健壮 UDP 接收：recvmsg + 每次检查 MSG_TRUNC。

💡 后续拓展留白
- FIONREAD 先探测下一报文长度再分配缓冲

个人学习总结

UDP 数据报截断：如果接收缓冲区小于数据报 → 数据报被截断，超出部分永久丢弃（不像 TCP 留在缓冲区）。

MSG_TRUNC：recvmsg 标志，返回数据报的实际长度（即使只读了部分）。

一句话：UDP recvfrom 缓冲不够 → 截断丢数据 → 用 MSG_TRUNC 至少知道原始长度。

HFT 关联：行情包应预分配足够大的缓冲区（如 1500 MTU）防止截断。

22.4

何时用 UDP 代替 TCP

Ch 2 TCP/UDP · Ch 20–21

选型黄金法则

必须用 UDP

  • 广播、多播 — TCP 仅单播

可以使用 UDP

场景 理由
简单请求-应答 DNS、NTP：UDP 约 2 包 vs TCP 握手+挥手 ≥7 包
可丢包、低延迟 VoIP、实时游戏

坚决不用 UDP

  • 海量可靠传输（文件等）
  • 应用层须重做：序号、ACK、窗口、拥塞控制
  • 应用层难感知物理拥塞 → 易 拥塞崩溃

个人学习总结

UDP vs TCP 选型：

场景 选 理由
请求-应答 TCP 可靠+有序
组播/广播 UDP TCP 不支持
高频小包 UDP 无连接开销
文件传输 TCP 可靠+流控
HFT 行情 UDP 最低延迟，允许丢包

一句话：需要可靠性选 TCP，需要低延迟/组播选 UDP。

22.5

给 UDP 应用增加可靠性

Ch 8.7 丢包 · 14.2 超时

核心主旨

请求-应答型 UDP 须在应用层处理：丢包、乱序、重复。

1. 超时与 RTO（Jacobson）

  • 不能固定 2 秒 — LAN/WAN RTT 差 orders of magnitude
  • EWMA 平滑 RTT、RTT 方差 → RTO = SRTT + 4×RTTVAR
  • 超时重传：指数退避（RTO 翻倍），减轻拥塞时雪上加霜

2. 序列号

端 作用
客户 请求带序号；匹配应答，丢迟到旧应答
服务器 识别重复请求；非幂等操作（扣款）须去重

个人学习总结

UDP 可靠传输 = 应用层实现：超时重传 + 序号去重 + ACK 确认 + 流控。

两种模式：①请求-应答（停等协议，发一个等 ACK）②滑动窗口（发 N 个等批量 ACK）。

一句话：UDP 可靠 = 自己实现 TCP 的子集——按需实现，不引入 TCP 的多余开销。

HFT 关联：行情恢复用 NACK + 序号检测缺失 + 重传请求——比 TCP 全量重传高效。

22.6

捆绑接口地址

Ch 7.5 SO_REUSEADDR · Ch 8.14 外出接口

核心场景

bind 通配 0.0.0.0 还是具体网卡 IP？

UDP 端点匹配规则

内核选套接字时：越具体 bind 优先级越高。

并发绑定示例

套接字 A：bind(192.168.1.100)
套接字 B：SO_REUSEADDR + bind(0.0.0.0)

→ 发往 192.168.1.100 的报文 → A
→ 发往其他本地 IP 的报文   → B

个人学习总结

指定接口：bind 指定源 IP、IP_MULTICAST_IF（组播）、IP_PKTINFO 辅助数据（发送时指定接口）。

一句话：多网卡机器要精确控制从哪块网卡收发——bind 源 IP + setsockopt 指定接口。

HFT 关联：交易网卡与管理网卡分离——bind 指定交易网卡 IP 隔离流量。

22.7

并发 UDP 服务器

Ch 4.8 并发 TCP · Ch 26 线程

TCP vs UDP

TCP UDP
accept → 新已连接套接字 无 accept，全进同一套接字队列

fork 新端口模式（笨拙）

主进程 recvfrom → fork
子进程：新建 UDP 套接字 + 临时端口 → 从此套接字 sendto 应答

客户端限制：须接受应答源端口 ≠ 请求目的端口；严格 NAT/四元组校验会丢应答。

实践倾向

多数 UDP 服（如 DNS）：迭代或线程/Worker 池共享单套接字，而非 per-client fork 新端口。

💡 后续拓展留白
- 现代 DNS 多线程 + 单 fd 缓冲池

个人学习总结

UDP 并发服务器困境：UDP 无连接 → 无法像 TCP 那样 fork 一连接一子进程。每个 recvfrom 都可能是新客户。

方案：①迭代（适合短处理）②fork 后子进程用 connect 绑定客户地址（临时 TCP 化）③线程池。

一句话：UDP 并发 = 手动跟踪客户身份 → fork/线程 + 客户地址映射。

实际工程中 UDP 迭代服务器 + select 即可处理多数场景。

22.8

IPv6 分组信息

22.2 · 14.6 cmsghdr

IPV6_PKTINFO / RECVPKTINFO

通过 recvmsg / sendmsg 与 in6_pktinfo 辅助数据。

接收（recvmsg）

  • 目的 IPv6 地址
  • 到达接口索引

发送（sendmsg 控制信息）

可覆盖（在属于本机的前提下）：

  • 源 IPv6 地址
  • 外出接口索引（覆盖默认路由选路）

个人学习总结

IPv6 IPV6_PKTINFO — 类似 IPv4 IP_PKTINFO，通过 recvmsg 辅助数据获取目的地址和接口索引。

差异：IPv6 结构体是 in6_pktinfo（含 pi6_addr + pi6_ifindex），IPv4 是 in_pktinfo。

一句话：IPv6 pktinfo 与 IPv4 等价——协议无关代码需处理两种结构。

IPV6_RECVPKTINFO 需先 setsockopt 开启才能在 recvmsg 中收到。

22.9

IPv6 路径 MTU 控制

背景

IPv4 IPv6
路由器分片 可以 绝不（仅源主机分片）
PMTUD 重要 更关键

套接字选项

选项 作用
IPV6_USE_MIN_MTU = 1 不做 PMTUD，按最小 MTU 1280 分片；规避 ICMPv6 “Packet Too Big” 被防火墙丢导致的 PMTU 黑洞
IPV6_RECVPATHMTU 收到 “Packet Too Big” 时，将最新路径 MTU 经辅助数据通知应用

个人学习总结

PMTU（Path MTU）发现：发送大于路径 MTU 的包 → 路由器返回 ICMP "Fragmentation Needed" → 发送方减小包大小。

IPV6_MTU：getsockopt 获取发现的路径 MTU。IPv6 路由器不分片——超 MTU 直接丢 + ICMP 通知。

一句话：IPv6 不允许路由器分片——应用必须自己控制包大小 ≤ PMTU。

HFT 关联：行情包应 ≤ MTU（通常 1500）避免分片延迟和丢包风险。

章节核心提炼

1. 突破 recvfrom 信息黑洞

多宿主 UDP 服 → recvmsg + IP_RECVDSTADDR / IPV6_RECVPKTINFO 等辅助数据。

  • 勿用 UDP 扛大块可靠业务
  • 若请求-应答：Jacobson RTO、序号、退避

4. 并发窘境

无连接分路 → 优先迭代/线程池；fork 新端口模式罕见且客户端/NAT 苛刻。

Ch 8 → Ch 22 升级路径

recvfrom/sendto → recvmsg + 选项 + MSG_TRUNC
无超时 → 14章超时 + 22.5 RTO/序号

个人学习总结

高级 UDP 核心：IP_PKTINFO（收包目的 IP）、MSG_TRUNC（截断检测）、可靠传输（应用层 ACK）、指定接口、PMTU。

选型：可靠有序选 TCP，低延迟/组播选 UDP——HFT 行情选 UDP + 应用层可靠性补充。

IPv6 路由器不分片——包必须 ≤ PMTU。
