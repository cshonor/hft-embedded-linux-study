23.2

自动关闭的一到多式服务程序

Ch 10 一到多服 · Ch 7.10 SCTP 选项

核心痛点

一到多（SOCK_SEQPACKET）服务器单 fd 可维持成千上万关联。客户端异常断线或未发关闭 → 服务器堆积僵死关联，占内存。

解决方案：SCTP_AUTOCLOSE

setsockopt(sockfd, IPPROTO_SCTP, SCTP_AUTOCLOSE, &seconds, ...);
项 说明
机制 关联在指定空闲秒数内无收发 → 内核自动发起终止并清理
适用 仅一到多套接字
一到一 须手动 close（类 TCP）

应用层无需逐个扫关联超时。

个人学习总结

自动关闭（autoclose）：一到多服务器中设置 SCTP_AUTOCLOSE 选项，空闲关联在指定秒数后自动关闭。防止不活跃客户端占用资源。

一句话：autoclose=一到多服务器的"空闲超时"——N 秒无数据自动断关联，防资源泄漏。

易考点：autoclose 只适用于一到多 socket，一到一 socket 用 SO_KEEPALIVE 或应用层心跳。

23.3

部分递送（Partial Delivery）

Ch 9.10 sctp_recvmsg

核心主旨

SCTP 保留消息边界；理想情况 sctp_recvmsg 一次返回整条消息。

对端发送超大消息（大于接收缓冲）时，内核不能等整条拼完再交付（易死锁/耗尽缓冲）→ 部分递送 API。

如何判断

检查 sctp_recvmsg 的 msg_flags：

标志 含义
无 MSG_EOR 当前块仅为大消息片段
有 MSG_EOR 本条记录结束（End of Record）

锁定状态（易错）

关联进入部分递送后，套接字被该流/该递送过程锁定：

在收到带 MSG_EOR 的最后一块之前，内核不会在同一套接字上交错递送其他流或其他关联的数据。

应用须实现部分递送状态机。

个人学习总结

部分交付（partial delivery）：当单个消息超过接收缓冲区时，SCTP 进入部分交付模式——内核先交付部分数据，应用层需循环 recvmsg 直到 MSG_EOR。

一句话：消息太大放不进缓冲区→内核分批交付，应用层循环 recvmsg 直到看到 MSG_EOR。

易考点：部分交付期间该关联的其他流被阻塞，所以大消息应避免或用独立流。

23.4

通知（Notifications）

Ch 9.14 通知基础 · 23.9 路径变更

事件驱动深化

订阅 SCTP_EVENTS 后，内核将状态变更作为通知与数据混在 sctp_recvmsg 路径（MSG_NOTIFICATION）。

本节强调高级程序必须处理的类型：

通知 含义
SCTP_ASSOC_CHANGE 关联建立、正常/异常终止
SCTP_PEER_ADDR_CHANGE 多宿路径 不可达 / 恢复可达 — 监控、HA
SCTP_SEND_FAILED 消息穷尽重传仍失败 → 业务回滚

Ch 9.14 已列基础类型；本章侧重运维与多宿场景。

个人学习总结

SCTP 通知消息：通过 SCTP_EVENTS 订阅关联事件（SCTP_ASSOC_CHANGE、SCTP_PEER_ADDR_CHANGE、SCTP_SEND_FAILED 等）。通知和数据复用同一 socket，用 msg_flags 区分。

一句话：订阅 SCTP_EVENTS→recvmsg 看到 MSG_NOTIFICATION→解析 sctp_notification 联合体判断事件类型。

易考点：SCTP_SEND_FAILED 通知表示某消息发送失败（含原始数据），可用于应用层重传决策。

23.5

无序的数据（Unordered Data）

Ch 10.5 队头阻塞 · Ch 9.9 sctp_sendmsg

核心场景

默认同流内严格有序（避免队头阻塞的另一面：慢消息挡后面）。

部分业务（DNS、实时信令）要 可靠重传 但不在乎顺序。

机制

sctp_sendmsg 的 sinfo_flags 设 SCTP_UNORDERED：

发送 接收
消息标 “U” 片段到齐即交付，不为等前面丢失消息而排队

→ 可靠的 UDP 语义：可靠 + 无序。

与多流区别

手段 隔离粒度
多流 流间独立；流内仍有序
UNORDERED 同流内也可乱序交付

个人学习总结

无序数据传输：sctp_sendmsg 设 flags=SCTP_UNORDERED 发送无序消息——不按序到达，不阻塞有序消息。适合实时数据（最新值优先，旧值可丢弃）。

一句话：SCTP_UNORDERED=不保证顺序的消息，适合"最新值有效"的行情推送。

HFT 关联：行情推送用 SCTP_UNORDERED——最新行情到达即可用，不需要等前序消息排齐。

23.6

捆绑地址子集

Ch 9.3 sctp_bindx · Ch 2.5 SCTP 多宿

问题

bind 通配（如 INADDR_ANY / in6addr_any）时，SCTP 可能把主机所有活动网卡 IP 都作为多宿地址通告给对端。

需求

安全或路由策略：某些 IP（如内网 DB 专用）不应暴露给公网关联。

解决方案

sctp_bindx 显式传入允许公开的 IP 数组 — 控制多宿拓扑的可见子集。

个人学习总结

地址子集绑定：sctp_bindx 可在关联建立后动态增删本地地址（SCTP_BINDX_ADD_ADDR/REM_ADDR），内核通过 ASCONF 消息通知对端。实现运行时多宿地址变更。

一句话：bindx ADD/REM=运行时动态加减本地地址，ASCONF 消息自动同步给对端。

易考点：动态增地址需对端支持 ASCONF 扩展（SCTP 协商时确认），否则 ADD 被忽略。

23.7

确定本端与对端地址信息

Ch 9.5 getpaddrs · Ch 9.7 getladdrs · 23.8 assoc_id

核心主旨

一到多模型单 fd 多关联 — 需随时查询某关联的本端/对端 IP 列表（多宿健康诊断）。

API

函数 作用
sctp_getpaddrs 某关联的对端地址列表
sctp_getladdrs 某关联的本端地址列表

用完须 sctp_freepaddrs / sctp_freeladdrs（Ch 9.6、9.8）。

用途

路径监控、日志、与 SCTP_PEER_ADDR_CHANGE 通知联动。

个人学习总结

本地/远端地址查询：sctp_getladdrs/sctp_getpaddrs 获取关联的所有本地/远端地址。关联建立后地址可能因 ASCONF 动态变化，不应缓存。

一句话：getladdrs=本端地址列表，getpaddrs=对端地址列表，用完 free，别缓存。

易考点：多宿关联的对端地址列表包含 primary 和 alternate，primary 失败后内核自动切 alternate。

23.8

找出关联 ID

Ch 9.11 sctp_opt_info · 23.7 地址查询 · 23.10 peeloff

核心主旨

连接池中只知对端某个 IP → 需反查其 assoc_id，才能对该关联设选项或 sctp_peeloff。

API

sctp_opt_info + SCTP_GET_PEER_ADDR_INFO（及对端地址参数）→ 得到 Association ID 等。

与一到多管理

sctp_recvmsg → sndrcvinfo.sinfo_assoc_id
或 sctp_opt_info(对端 IP) → assoc_id
  → setsockopt / sctp_peeloff / 统计

个人学习总结

IP 地址与关联 ID 匹配：一到多模型中多个关联共享一个 socket，sctp_opt_info(SCTP_SOCKOPT_PEELOFF) 或 sctp_getpaddrs 按 assoc_id 区分。通过对端 IP+port 反查 assoc_id 需遍历。

一句话：一到多 socket 中 assoc_id 是关联的唯一标识，IP:port 可能重复（不同关联同 IP），必须用 assoc_id。

易考点：收到数据时 sctp_recvmsg 填充 rcvinfo.rcv_assoc_id，后续操作用这个 ID 定位关联。

23.9

心搏和地址不可达

23.4 SCTP_PEER_ADDR_CHANGE · Ch 2.5 SCTP

与 TCP Keep-Alive 对比

TCP 默认 Keep-Alive 可达 2 小时量级；SCTP 原生 心搏（Heartbeat） 管理多路径。

工作原理

状态 行为
备用路径空闲 周期性发 HEARTBEAT Chunk
多次超时无 HEARTBEAT ACK 该 IP 标 Inactive（不可达）
业务数据 切到其他健康路径

内核可发 SCTP_PEER_ADDR_CHANGE 通知应用。

应用层干预

SCTP_PEER_ADDR_PARAMS：调心搏间隔等（强行关闭心搏一般不推荐）。

个人学习总结

心跳与地址不可达检测：SCTP heartbeat 定期探测备用路径活性。SCTP_PEER_ADDR_PARAMS 可按地址配置 heartbeat 间隔。地址不可达时触发 SCTP_PEER_ADDR_CHANGE 通知。

一句话：heartbeat=定期 ping 备用路径，不可达→PEER_ADDR_CHANGE 通知→切 primary，可达→切回。

易考点：heartbeat 默认只对非 primary 地址开启，primary 用重传超时检测。可强制开启。

23.10

关联剥离（Peeling Off an Association）

Ch 9.12 sctp_peeloff · Ch 10 一到多

杀手级 API：sctp_peeloff

一到多下解决“轻量请求海量、个别长连接需独占线程”的架构问题。

int newfd = sctp_peeloff(sockfd, assoc_id);

场景

主线程：SOCK_SEQPACKET 快速处理大量短请求
某关联：大文件传输等长事务
  → peeloff(assoc_id) → newfd
  → 交给工作线程；主线程继续服务其他关联

结果

项 说明
newfd 独立一到一（SOCK_STREAM）描述符
原 fd 该关联从群集套接字剥离

类 UDP 并发 + 可对单连接做阻塞长 I/O。

个人学习总结

关联拆分（peeloff）：sctp_peeloff 将一到多 socket 上的某关联"剥离"为一到一 socket，可交给单独线程处理。相当于 accept + 迁移的合体。

一句话：peeloff=从一到多 socket 上"摘"一个关联变独立 fd，交给 worker 线程用普通 send/recv 处理。

易考点：peeloff 后该关联的事件通知仍在新 fd 上投递，需重新订阅 SCTP_EVENTS。

23.11

定时控制（Timing Control）

Ch 7.10 SCTP 选项

核心主旨

电信级信令（如 SS7 over IP）等对延迟敏感 — 可深入内核调重传与故障判定定时器。

常用选项

选项 调什么
SCTP_RTOINFO 初始 RTO、最小/最大 RTO
SCTP_ASSOCINFO 关联级最大重传（超限则断关联）、INIT 阶段最大尝试次数等

通过 setsockopt / sctp_opt_info 读写。

注意

过激缩短 RTO → 误判断线；需结合 SCTP_PEER_ADDR_PARAMS 与网络 RTT 实测。

个人学习总结

定时器参数控制：SCTP_PEER_ADDR_PARAMS 可配置 heartbeat 间隔、SCTP_RTO_INFO 配置 RTO 最小/最大/初始值、SCTP_ASSOCINFO 配置重传次数等。精细调优关联行为。

一句话：RTO_INFO 调重传超时，PEER_ADDR_PARAMS 调心跳间隔，ASSOCINFO 调重传次数——三大定时器参数。

HFT 关联：低延迟场景应减小 RTO_MIN 和 heartbeat 间隔，但太小会导致误重传，需实测调优。

23.12

何时改用 SCTP 代替 TCP

Ch 10.5 队头阻塞 · 23.13 小结

架构师选型（非全面替换 TCP）

SCTP 在以下场景有明显优势：

# 场景 原因
1 抗队头阻塞 多流：单包丢失不卡死整连接（HTTP/2 类需求；工业界公网多走 QUIC/UDP）
2 多宿高可用 单 IP 断链 → 路径 Failover，应用可无感（TCP 绑定单地址）
3 消息边界 无需应用层粘包/长度字段
4 无序可靠 SCTP_UNORDERED：类 UDP 速度 + 可靠重传

局限

因素 说明
NAT/防火墙 公网部署穿透差，普及度低于 TCP/QUIC
复杂度 状态机、通知、部分递送 — 开发与运维成本高
电信领域 4G/5G 核心网（如 Diameter over SCTP）仍为主流承载之一

设计思想影响 QUIC 等现代协议。

个人学习总结

SCTP vs TCP 场景选择：需要消息边界/多流/多宿→SCTP；需要最大兼容性/穿 NAT→TCP。SCTP 穿 NAT/防火墙困难（非标准端口+多宿 IP），TCP 生态更成熟。

一句话：SCTP 优势=消息边界+多流+多宿，劣势=穿 NAT 困难+生态小；TCP 优势=无处不在，劣势=HoL+无消息边界。

HFT 关联：交易所内网/专线可用 SCTP（无 NAT 问题），公网或跨机房用 TCP 更稳妥。

1. 微操与资源

个人学习总结

高级 SCTP 总结：autoclose（空闲清理）、部分交付（大消息分批）、通知（事件驱动）、无序数据（实时优先）、地址子集绑定（动态多宿）、heartbeat（路径检测）、peeloff（关联拆分）、定时器调优。全方位控制关联行为。

一句话：高级 SCTP=把 TCP 做不到的事情做精细——多流调度、路径冗余、事件通知、消息级控制。

HFT 关联：SCTP 的高级特性几乎为低延迟交易量身定做，但部署门槛（NAT/防火墙）限制了实际采用。
