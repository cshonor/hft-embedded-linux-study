31.1

概述

Ch 1.8 BSD 历史 · study.md

核心主旨与历史

STREAMS（流）：Dennis Ritchie 发明的高级 I/O 机制 → SVR3 集成 → SVR4 标准网络底层架构之一。

两套 Unix 网络栈传统

lineage 网络实现
Berkeley（FreeBSD、macOS、Linux） 协议栈紧耦合在内核；套接字 API 直接进内核
System V（如 Solaris） TCP/IP、甚至 socket API 常基于 STREAMS 模块化 堆叠

本章地位

理解 STREAMS → 维护 Solaris 等传统系统、厘清 Sockets vs XTI/TLI 标准史。

现代 Linux/FreeBSD 上 STREAMS 已基本淘汰（性能与生态）。

资料说明

上传资料截至第 8 章；第 31 章框架来自目录（约第 14 页），细节按 UNP 第 3 版整理，请与全本对照验证。

个人学习总结

STREAMS 概述：System V 的内核消息传递框架——模块化协议栈（head→module→module→driver）。用户态用 putmsg/getmsg 收发消息，内核中数据沿 STREAMS 链传递。Linux 不支持 STREAMS。

一句话：STREAMS=System V 的模块化内核通信框架，类似"管道+滤镜"，Linux 不支持。

易考点：STREAMS 是 SVR4 特性，Solaris/HP-UX 支持，Linux 从未实现。现代代码不应依赖。

31.2

概貌

31.3 putmsg/getmsg · 31.5 I_PUSH

全双工消息通道

用户进程 ↔ 设备驱动之间的全双工连接；传递单元均为消息（Message）。

自上而下组件

┌ 流头 Stream Head ┐  用户/内核边界；write/putmsg → 内核消息
├ 处理模块 (可选)  ┤  I_PUSH 压入；协议、加密、缓冲等流水线
└ 驱动 Driver     ┘  网卡 / 协议提供者（伪设备）

模块可堆叠 — “搭积木”式协议链。

消息类型

类 示例 用途
数据 M_DATA 用户载荷
控制 M_PROTO, M_PCPROTO 模块间控制（如发起连接）

个人学习总结

STREAMS 结构剖析：每个 stream = 一个队列对（read queue + write queue），每个队列有 put/service 过程。模块可动态压入（ioctl I_PUSH）和弹出（I_POP）。

一句话：stream=队列对链表，I_PUSH 压模块，I_POP 弹模块，数据沿队列链传递。

易考点：队列的 put 过程=同步调用（立即执行），service 过程=延迟调用（调度执行），用于流控。

31.3

`getmsg` 和 `putmsg` 函数

31.4 优先级 · Ch 14.5 sendmsg 对比

核心：控制与数据分离

read/write 只能传纯数据；STREAMS 需同时传 控制（Control） 与 数据（Data）。

int putmsg(int fd, const struct strbuf *ctlptr,
           const struct strbuf *dataptr, int flags);
int getmsg(int fd, struct strbuf *ctlptr,
           struct strbuf *dataptr, int *flagsp);
参数 内容
ctlptr 控制块（如绑定地址、TPI 原语）
dataptr 数据块（报文载荷）

strbuf：buf + len（及 maxlen 用于 get）。

与 Berkeley 套接字

Berkeley API 把许多控制塞进 setsockopt/ioctl；STREAMS 用 控制消息 显式分层。

个人学习总结

getmsg/putmsg 函数：STREAMS 的读写接口。putmsg 发送消息（控制+数据两部分），getmsg 接收消息。比 read/write 多了控制信息部分。

一句话：read/write=纯数据，getmsg/putmsg=控制+数据双通道，对应 sendmsg/recvmsg 的 ancillary data。

易考点：putmsg 的控制部分用于传递模块间命令（如设置协议参数），数据部分是实际 payload。

31.4

`getpmsg` 和 `putpmsg` 函数

Ch 24 带外数据 · 31.3 putmsg

优先级频带（Priority Bands）

频带 类型
0 普通数据（Normal Data）
1–255 优先数据（Priority Data）
高优先级 M_PCPROTO 等 — 近似带外，可绕过常规流控

API

putpmsg / getpmsg（带 p = Priority）：发送/接收时指定或获取频带号。

处理类似 TCP OOB 的语义时需精确控制优先级。

个人学习总结

getpmsg/putpmsg 函数：带优先级的 getmsg/putmsg。增加 band 参数指定优先级带（priority band），高优先级消息优先传递。

一句话：putmsg=普通消息，putpmsg=带优先级的消息（band 0=普通，band>0=优先，MSG_HIPRI=最高）。

易考点：高优先级消息（MSG_HIPRI）绕过流控直接送达队列头部，用于紧急控制消息。

31.5

`ioctl` 函数

Ch 17 ioctl · Ch 25 信号驱动 I/O

流的动态装配

STREAMS 下 ioctl 任务远比普通套接字繁重 — 组装/拆卸 流栈。

命令 作用
I_PUSH 将模块压入流头下方（如 bufmod 缓冲）
I_POP 弹出栈顶模块
I_SETSIG 流事件（可读、可写、高优先级消息等）→ SIGPOLL（同 SIGIO）

与 Ch 25

I_SETSIG + SIGPOLL = System V 上信号驱动 I/O 的核心（Berkeley 用 fcntl + SIGIO）。

个人学习总结

STREAMS ioctl 控制：ioctl 用于 STREAMS 管理——I_PUSH（压模块）、I_POP（弹模块）、I_LOOK（查看顶模块）、I_STR（发送 ioctl 消息）、I_FLUSH（刷新队列）等。

一句话：STREAMS ioctl=管理操作——压/弹模块、查状态、刷队列，I_STR 是万能 ioctl 消息通道。

易考点：I_STR 发送 strioctl 结构（含命令+超时+数据缓冲），内核转换为 M_IOCTL 消息沿 stream 传递。

31.6

TPI：传输提供者接口

Ch 3 socket API · 31.3 putmsg

核心主旨

TPI（Transport Provider Interface）：基于 STREAMS 消息的规范，抽象底层传输（TCP、UDP、OSI 等）。

符合 TPI 的驱动/提供者即可接入同一套上层服务。

通信方式

应用通过 M_PROTO 控制消息操作网络，例如：

TPI 消息 类比 Berkeley API
T_BIND_REQ bind()
T_CONN_REQ connect()
… listen / accept 等均有对应原语

由库或应用 putmsg 下发。

“套接字的错觉”（SVR4）

部分 System V 系统：

socket()  → 打开 STREAMS 设备 + 压入模块
connect() → 库封装为 T_CONN_REQ + putmsg

内核里可能根本没有传统 Berkeley socket 实现 — libc 翻译层。

与 XTI / TLI

TPI 之上曾有 TLI/XTI API — 商业上曾风光，终被 Sockets 生态击败。

个人学习总结

传输提供者接口（TPI）：STREAMS 传输层（如 TCP/UDP）的编程接口。用 T_BIND 绑定、T_CONN_REQ 连接、T_DATA_REQ 发数据等消息原语。是 socket 底层的 STREAMS 实现。

一句话：TPI=STREAMS 上的传输层协议接口，socket API→TPI 消息→TCP/UDP 模块。Solaris 的 socket 底层就是 TPI。

易考点：Linux 的 socket 不用 TPI，直接用内核 sock 结构。TPI 是 SVR4/Solaris 特有。

31.7

小结

study.md

章节核心提炼

1. 极致模块化

STREAMS = 用户与硬件间可堆叠模块的全双工消息管道；I_PUSH/I_POP 动态装配。

2. 控制/数据/优先级

putmsg/getmsg 分离控制与数据；putpmsg/getpmsg 处理优先级频带与类 OOB 语义。

3. TPI 与 socket 史

TPI 用流消息实现 bind/connect 等；SVR4 上 socket 可能是 libc 封装。

4. 现状

时代 胜者
标准竞争 Berkeley Sockets
现代 Linux/FreeBSD 内核内置协议栈，STREAMS 基本淘汰
仍相关 Solaris 维护、网络标准史

全书收束

Ch30 服务器范式 → Ch31 STREAMS（历史与 SVR4 视角）

个人学习总结

STREAMS 总结：System V 模块化内核通信框架——队列对链表+动态模块+getmsg/putmsg 接口+TPI 传输层。设计优雅但 Linux 不支持，现代 Unix 也逐渐弃用，已被 socket/netlink 取代。

一句话：STREAMS=优雅的模块化设计但已成历史，socket+netlink 是现代主流，TPI 仅存于 Solaris。

HFT 关联：STREAMS 对 HFT 无实际影响（Linux 不支持），但模块化思想影响了 DPDK 的 pipeline 架构设计。
