30.1

概述

Ch 4 并发服 · Ch 26 线程 · study.md

核心主旨

全书服务器架构的横向对比章：在迭代、fork 之外，用压测数据对比 9 种 TCP 服务器范式 的 CPU、内存与复杂度权衡。

背景

模型 局限
迭代 无并发
每客户一子进程 fork 在海量短连接下开销常超过业务本身

现代高并发 → 池化（Prefork / Prethread）、锁策略、描述符传递等。

个人学习总结

客户/服务器设计范式概述：UNP 定义了多种 TCP 服务器架构——迭代、并发 fork、pre-fork（无锁/文件锁/线程锁/fd 传递）、并发线程、pre-thread（主 accept/各 accept）。各有适用场景。

一句话：9 种服务器架构从"迭代→并发→pre-fork→pre-thread"逐步优化，核心权衡=进程/线程创建开销 vs 资源占用。

HFT 关联：HFT 服务器通常用 pre-thread + CPU 绑核，避免 fork/线程创建的微秒级抖动。

30.2

客户程序设计范式

30.3 测试客户 · Ch 5 客户

核心主旨

为公平对比各服务器架构，需统一的高并发测试客户设计范式。

典型模式

要素 说明
连接数 同时发起数千 TCP 连接
协议 发固定长度请求 → 收等量回射 → 关闭
指标 首连建立到末连断开的总耗时 → 吞吐

与 Ch 5 回射客户类似，但强调并发连接规模与可重复压测。

个人学习总结

TCP 客户端设计模式：基本模式=socket→connect→while(read stdin→send→recv→write stdout)→close。变种：select 同时监听 stdin 和 socket、非阻塞 connect 实现超时控制。

一句话：TCP 客户端=connect 后读写循环，进阶=select 多路复用+非阻塞 connect 超时。

易考点：客户端 recv 需处理 EOF（对端关闭）和 EINTR（信号中断）两种特殊情况。

30.3

TCP 测试程序

30.2 客户范式 · 30.4 迭代服

测试机制

N 个并发 TCP 连接
  → 每连接：写请求块 → 读应答块（长度一致）→ close
计时：从第一个 connect 完成到最后一个 close 结束

作用

消除业务逻辑差异，使 30.4–30.12 各服务器实现可在相同负载下对比 CPU/延迟。

个人学习总结

TCP 测试客户端：UNP 的测试客户端支持指定并发连接数、每连接请求数、数据量。用于压测不同服务器架构的性能。核心是 fork N 个子进程各自建立连接循环收发。

一句话：测试客户端=压测工具，fork N 进程×M 连接×K 请求，衡量不同服务器架构吞吐。

易考点：测试客户端的输出指标=总耗时、吞吐量(req/s)、每连接平均延迟。不同架构差距可达 10 倍。

30.4

TCP 迭代服务器程序

Ch 4 基本模型 · 30.5 fork 并发

运作机制

单进程死循环：

accept → 在同一线程 read/处理/write → close → 再 accept

致命缺陷

无并发：处理客户 1 秒 → 第 100 个客户可能多等 99 秒。

适用场景

极轻量、极快（如 daytime）、内网、连接极少。

压测中性能垫底。

个人学习总结

TCP 迭代服务器：accept→处理→close→循环。一次只服务一个客户端，处理完才 accept 下一个。最简单但无法并发，客户端排队等待。

一句话：迭代服务器=one-by-one，简单但不并发，只适合极短请求（如 daytime）。

易考点：迭代服务器在慢客户端时会阻塞所有其他客户端，生产环境基本不用。

30.5

TCP 并发服务器：每个客户一个子进程

Ch 4.7 fork · Ch 5 并发回射

运作机制

主进程：listen + accept 循环
  新连接 → fork
    子进程：处理已连接套接字
    父进程：close 已连接 fd，继续 accept

优势

点 说明
隔离 一客户崩溃不拖垮其他
简单 代码直观、安全

痛点

海量短连接（早期 HTTP/1.0）：fork CPU 开销 可超过网络 I/O 处理本身。

个人学习总结

TCP 并发 fork 服务器：accept→fork→子进程处理客户端→父进程继续 accept。经典 Unix 并发模型，每个客户端独立进程。

一句话：accept+fork=最经典的并发服务器模型，进程隔离安全但 fork 开销大。

易考点：fork 后父进程 close(connfd) 子进程 close(listenfd)，避免 fd 泄漏。SIGCHLD 需处理避免僵尸。

30.6

预先派生子进程：accept 无上锁保护

30.7 文件锁 · 30.5 fork

Prefork 思想

启动时主进程 fork N 个子进程（进程池），避免每连接再 fork。

运作机制

所有子进程在同一监听套接字上直接 accept 阻塞。

惊群（Thundering Herd）

新连接到达 → 所有阻塞在 accept 的子进程被唤醒 → 仅一个成功，其余 EAGAIN 再睡 → CPU 浪费。

兼容性

Berkeley 系内核尚可；部分 System V 上多进程并发 accept 可能内核混乱。

个人学习总结

Pre-fork 无锁服务器：启动时 fork N 个子进程共享 listenfd，各子进程独立 accept。实现简单但多进程同时 accept 会"惊群"（thundering herd）——一个连接到来唤醒所有进程。

一句话：pre-fork 无锁=N 个子进程争 accept，惊群导致 CPU 浪费，但 Linux 内核已优化（只唤醒一个）。

易考点：惊群问题=所有子进程被唤醒但只有一个 accept 成功，其余 EAGAIN 返回继续 sleep。Linux 3.9+ 支持 SO_REUSEPORT 彻底解决。

30.7

预先派生子进程：accept 使用文件上锁保护

30.6 无锁 · 30.8 线程锁

动机

消除 惊群 + 改善 System V 等系统上的 accept 竞争。

运作机制

子进程 accept 前 → fcntl 文件系统跨进程锁
  获锁者 accept → 处理 → 释锁

代价

文件锁 系统调用重 → 性能低于更轻量的锁实现。

个人学习总结

Pre-fork 文件锁服务器：子进程 accept 前先 flock 加锁，accept 后解锁。避免惊群——同一时刻只有一个子进程在 accept。

一句话：文件锁=用 flock 串行化 accept，消除惊群，但每次 accept 有锁开销。

易考点：flock(LOCK_EX/LOCK_UN) 对比无锁方案：吞吐略降但 CPU 利用率更合理（无惊群浪费）。

30.8

预先派生子进程：accept 使用线程上锁保护

30.7 文件锁 · 30.9 传 fd · Ch 26 互斥量

优化

弃文件锁 → mmap 共享内存中的 pthread_mutex_t（PTHREAD_PROCESS_SHARED）保护 accept。

结论（多进程范式）

Prefork + 共享内存互斥锁抢 accept = 多进程架构中性能最优的抢占模式；上锁开销极低。

Nginx 类思想：进程隔离容错 + 高效 accept 分发。

选型：稳定性

第三方库不可重入、需单客户崩溃不拖全网关 → 优选此范式。

个人学习总结

Pre-fork 线程锁服务器：用 pthread_mutex（进程间共享，PTHREAD_PROCESS_SHARED）替代文件锁。比 flock 快——内存操作 vs 系统调用。

一句话：线程锁=flock 的加速版——pthread_mutex 住共享内存，省去系统调用开销。

易考点：mutex 需放在 mmap(MAP_SHARED) 共享内存中 + pthread_mutexattr_setpshared(SHARED) 才能跨进程使用。

30.9

预先派生子进程：传递描述符

Ch 15.7 传 fd · 30.8 互斥锁

主从调度

子进程不抢 accept：

主进程：独占 accept
  → Unix 域 SCM_RIGHTS 将已连接 fd 派给空闲子进程
子进程：只处理已连接套接字

优缺点

优 劣
负载均衡清晰、架构优雅 sendmsg/recvmsg 传 fd 开销大
总体性能常略逊于 30.8 共享互斥锁

个人学习总结

Pre-fork fd 传递服务器：父进程 accept 后通过 Unix 域 socket（SCM_RIGHTS）将 connfd 传递给子进程。子进程不直接 accept，无惊群问题。

一句话：父 accept→SCM_RIGHTS 传 connfd 给子进程→子进程处理。无惊群但每次连接有 sendmsg/recvmsg 开销。

易考点：fd 传递的开销=两次 syscall（sendmsg+recvmsg），比 flock/mutex 更高，但完全消除惊群。nginx 用类似模型。

30.10

TCP 并发服务器：每个客户一个线程

Ch 26 线程 · 30.11 线程池

运作机制

主线程 accept → pthread_create 处理该客户
（非 fork）

优势

线程创建/销毁通常比进程快 一个数量级以上。

痛点

风险 后果
无内存隔离 一线程段错误或 exit() → 整进程崩溃
库要求 所用库须 线程安全

个人学习总结

TCP 并发线程服务器：accept→pthread_create→新线程处理客户端→主线程继续 accept。比 fork 轻量（线程创建快于进程创建），共享地址空间。

一句话：fork→pthread_create，进程→线程，共享内存省去 IPC，但需注意线程安全。

易考点：线程模型需处理临界区（mutex），但共享数据无需 IPC。线程创建比 fork 快 5-10 倍。

30.11

预先创建线程：每个线程各自 accept

30.10 每连接线程 · 30.12 主 accept

Prethread（线程池）

启动时预建 N 个工作线程，避免每连接 pthread_create。

运作机制

所有工作线程在互斥锁保护下，对同一监听套接字轮流 accept。

性能

共享内存廉价 → 锁开销极低 → 书中压测吞吐量顶尖范式之一。

前提：业务与第三方库线程安全。

个人学习总结

Pre-thread 单 accept 服务器：创建 N 个线程，所有线程共享 listenfd 各自 accept。惊群问题同 pre-fork，但线程创建开销已消除。

一句话：pre-thread 单 accept=N 线程争 accept，比 pre-fork 轻（无 fork 开销），但仍有惊群。

易考点：线程版惊群比进程版更轻——线程唤醒开销小，且共享地址空间无 IPC 需求。

30.12

预先创建线程：主线程统一 accept

30.11 线程抢 accept · Ch 6 I/O 多路复用

生产者-消费者

主线程：独占 accept → 已连接 fd 入全局队列
工作线程：阻塞在条件变量 → 有连接则唤醒取任务处理

对比 30.11

30.11 30.12
accept 多线程抢 主线程唯一
开销 更低 队列 + 条件变量略高
控制 弱 过滤、整形、优先级 强

企业级 Java/C++ 线程池常见模型。

个人学习总结

Pre-thread 主 accept 服务器：主线程 accept→将 connfd 放入队列→工作线程从队列取 fd 处理。主线程串行 accept（无惊群），工作线程并行处理。

一句话：主线程 accept+任务队列+工作线程消费=生产者-消费者模型，无惊群且解耦。

HFT 关联：这是 HFT 最常用的架构——主线程 accept，工作线程绑核处理，队列用 lock-free ring buffer 降延迟。

30.13

小结

study.md

终极选型（书中压测结论）

1. 池化是王道

Prefork / Prethread 在海量短连接下远超动态 fork / pthread_create。

2. 绝对吞吐

30.11：预建线程 + 互斥锁保护下各线程 accept（库须线程安全）。

3. 稳定性 / 容错

30.8：Prefork + 共享内存 pthread_mutex 抢 accept — 进程隔离，单客户 core 不拖全站（Nginx 思想）。

4. 勿过度设计

连接稀疏、长存活 → 30.5 每客户一子进程 往往足够。

个人学习总结

客户/服务器设计范式总结：9 种架构从简单到复杂——迭代（最简单不并发）→fork 并发（经典）→pre-fork（避免 fork 开销，锁/fd 传递消除惊群）→thread 并发（更轻量）→pre-thread 主 accept（最优：无惊群+无创建开销）。性能递增，复杂度递增。

一句话：迭代<fork<pre-fork<thread<pre-thread——演进方向=消除创建开销+消除惊群+共享地址空间。

HFT 关联：HFT 最优=pre-thread 主 accept + lock-free 队列 + CPU 绑核 + 非阻塞 I/O，微秒级延迟。DPDK 则完全绕过 accept，网卡直接轮询。
