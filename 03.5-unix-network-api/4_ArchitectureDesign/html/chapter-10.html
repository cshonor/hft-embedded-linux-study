10.1

概述

Ch 9 SCTP API · 10.2 服务器 · study.md

核心主旨

完整 SCTP 回射（Echo） 客户/服务器，实战第 9 章 API。

架构选择

刻意采用 一到多（One-to-Many，SOCK_SEQPACKET）：

优势 说明
单 fd 同时处理成百上千关联
展示 SCTP 特性 多流、消除 队头阻塞
状态机 比 per-连接 accept 更轻（类 UDP 服）

资料说明

上传资料截至第 8 章；第 10 章框架来自目录，细节按 UNP 第 3 版整理，请与全本对照验证。

个人学习总结

SCTP C/S demo 概览：使用一到多模型构建回射服务器，客户端用 sctp_sendmsg/sctp_recvmsg 交互。重点关注 stream 分配和通知处理。

一句话：一到多 SCTP 服务器=一个 socket 服务所有客户端，比 TCP 的 fork/thread 模型简洁。

易考点：一到多模型中服务器无需 accept/fork，直接 recvmsg 即可收新关联数据。

10.2

SCTP 一到多式流分回射服务器程序：main 函数

Ch 9.2 一到多 · 9.10 recvmsg

结构：类 UDP + 可靠传输

socket(AF_INET, SOCK_SEQPACKET, IPPROTO_SCTP)
→ bind(INADDR_ANY, port)  [可选 sctp_bindx 多宿]
→ setsockopt SCTP_EVENTS（sctp_data_io_event = 1）
→ listen
→ 循环 sctp_recvmsg → sctp_sendmsg 回射

关键：SCTP_EVENTS

必须订阅 sctp_data_io_event，内核才在每次数据时填充 sctp_sndrcvinfo（流号、assoc_id 等）。

无此步骤 → 无法按流/关联正确路由回射。

主循环要点

步 API
收 sctp_recvmsg + sctp_sndrcvinfo
判 数据 vs MSG_NOTIFICATION（见 Ch 9.14）
发 sctp_sendmsg 回同一客户（示例可递增流号或原样返回）

无 accept — 新关联由协议建立后直接在 recvmsg 上体现。

个人学习总结

一到多 SCTP 服务器：socket(SOCK_SEQPACKET) → bind+listen → sctp_recvmsg 循环。新关联的建立对服务器透明——首次 recvmsg 自动接受关联。

一句话：TCP 服务器=listen+accept+fork，SCTP 一到多服务器=listen+recvmsg 循环，内核自动管关联。

易考点：backlog 参数仍作用于 INIT 队列，但不需要 accept 逐个取出。

10.3

SCTP 一到多式流分回射客户程序：main 函数

10.4 sctpstr_cli · Ch 8 客户模型

核心主旨

一到多客户 不必 connect。

socket(SOCK_SEQPACKET, IPPROTO_SCTP)
→ setsockopt SCTP_EVENTS（sctp_data_io_event）
→ sctpstr_cli(sockfd, 服务器地址)

与服务器对称

同样依赖 sctp_sndrcvinfo 查验回射来自哪条流、哪个关联。

个人学习总结

一到多 SCTP 客户端：socket(SOCK_STREAM) → connect → sctp_sendmsg/sctp_recvmsg。客户端用一到一模型，指定目标 stream 发送。

一句话：客户端侧 SCTP 和 TCP 几乎一样——connect 后 send/recv，只是多了 stream 参数。

易考点：客户端 sendmsg 时 stream 号自由选择，服务器看到的 stream 号=客户端指定的。

10.4

SCTP 流分回射客户程序：sctpstr_cli 函数

9.9 sendmsg · 10.5 队头阻塞

核心逻辑：多流轮询

fgets(stdin) → sctp_sendmsg(..., sinfo_stream = 计数器++)
             → sctp_recvmsg → 打印 assoc / stream
策略 说明
流号 Round-Robin 非全部塞流 0；依次 0、1、2…
校验 从 sctp_sndrcvinfo 读回射的流与关联

演示应用层主动利用多流。

个人学习总结

sctp_str_cli 函数：客户端回射逻辑，从 stdin 读一行→sctp_sendmsg 发到 stream 0→sctp_recvmsg 收回射→输出 stdout。

一句话：SCTP 版回射客户端=sctp_sendmsg+sctp_recvmsg 替代 writen/readline。

易考点：stream 0 是默认流，未指定 stream 时所有数据走 stream 0。

10.5

探究头端阻塞（Head-of-Line Blocking）

Ch 2.4 TCP · Ch 2.5 SCTP

实验设置

客户/服务器间人为丢包（丢包路由器、dummynet 等），对比 TCP vs SCTP。

TCP：字节流队头阻塞

连续发消息 A、B、C（同一连接）：

A 丢失 → 虽 B、C 已到内核缓冲
       → 应用 read 仍阻塞，直到 A 重传成功

对彼此独立的消息（多图加载、信令）是性能浪费。

SCTP：多流隔离（本章核心）

消息 流
A 0
B 1
C 2 
流 0 的 A 丢 → 仅流 0 等待重传
流 1、2 的 B、C → 仍可 sctp_recvmsg 交付应用

一条流丢包不阻塞其他流 — 逻辑流隔离。

重点结论

差网络下 SCTP 多流可削减 TCP 式延迟长尾 — 适合信令、多媒体调度。

个人学习总结

队头阻塞（Head-of-Line Blocking）：TCP 中前一个包丢失会阻塞后续已到达的包；SCTP 多流机制中，一个流的阻塞不影响其他流。

一句话：TCP HoL=一个包丢全部等，SCTP 多流=stream 0 阻塞不影响 stream 1。

HFT 关联：多流是 SCTP 对 HFT 的核心价值——行情流和交易流分开，行情丢包不阻塞交易。

10.6

控制流的数目

Ch 7.10 SCTP 选项

协商时机

关联建立时在 INIT / INIT-ACK 中协商流数 — 须在首次发数据或 connect 之前设置。

SCTP_INITMSG

setsockopt(..., SCTP_INITMSG, &sctp_initmsg, ...);
字段 含义
sinit_num_ostreams 本端外出流数请求
sinit_max_instreams 本端允许入站流数上限

默认常较小（如各 10）— 高并行应用须调大。

木桶效应

实际流数 = min(本端请求, 对端允许)。

向不存在的流号发送 → 错误或被降级处理。

个人学习总结

流号控制：通过 sctp_sendmsg 的 stream 参数指定目标流。SCTP 协商的流数量在关联建立时确定（INIT/INIT-ACK 中协商），实际可用 = min(本端 out, 对端 in)。

一句话：流数量=INIT 协商，流号=sendmsg 指定，超范围返回 EINVAL。

易考点：默认协商流数通常为 1（如果不显式设置），需用 SCTP_INIT_MSG 选项设置请求流数。

10.7

控制终结

Ch 9.13 shutdown · 9.9 SCTP_EOF

陷阱：一到多不能 close 杀全部

TCP 一到一 SCTP 一到多
close(fd) → 断开该连接 close(fd) → 所有关联同时被关

优雅关闭单一关联

sctp_sendmsg(sockfd, NULL, 0, &dest, ..., 
             sinfo_flags = SCTP_EOF);
项 说明
长度 0 无用户数据
目的地址 要断开的该客户
SCTP_EOF 触发 SHUTDOWN，仅关此关联

其他关联不受影响。

强制中止

SCTP_ABORT — 类似 TCP RST 的异常中止。

个人学习总结

SCTP 连接终止控制：shutdown=优雅关闭（排空发送队列再三步挥手），close=立即关闭（可能丢未确认数据）。SCTP 无半关闭状态。

一句话：SCTP shutdown=优雅退出（等数据送达），close=强制退出（可能丢数据），没有 TCP 的 SHUT_WR 半关闭。

易考点：SCTP 的 ABORT（强制中止）类似 TCP 的 RST，通过 setsockopt(SCTP_ABORT) 触发。

个人学习总结

SCTP C/S demo 总结：一到多模型简化服务器代码，多流解决 HoL 阻塞，notification 提供关联生命周期事件。相比 TCP C/S 模型，SCTP 在消息边界和多流方面有天然优势。

一句话：SCTP C/S demo 三大要点——一到多免 fork、多流避 HoL、notification 事件驱动。

HFT 关联：如果交易平台选 SCTP，多流可分离行情/委托/回报，天然解耦，但 SCTP 穿 NAT/防火墙困难，实际部署受限。
