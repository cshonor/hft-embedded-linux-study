16.1

概述

Ch 14.2 超时 · Ch 7.11 fcntl · study.md

核心主旨

默认套接字为阻塞：操作不能立即完成时进程睡眠。

非阻塞 I/O：内核不睡眠，立即返回，通常 errno = EWOULDBLOCK（或 EAGAIN）。

设置：fcntl → O_NONBLOCK（见 Ch 7.11）。

四类可能阻塞的操作

1. 输入（read/recv/recvfrom/recvmsg…）

模式 行为
阻塞 接收缓冲区空 → 睡眠
非阻塞 无数据 → -1, EWOULDBLOCK

2. 输出（write/send…）

协议 非阻塞行为
TCP 发送缓冲区满 → EWOULDBLOCK；有部分空间 → 短写（返回实际写入字节）
UDP 通常无真正发送缓冲区阻塞 → 少见 EWOULDBLOCK

3. accept

模式 行为
阻塞 已完成连接队列空 → 睡眠
非阻塞 队列空 → EWOULDBLOCK

4. connect

模式 行为
阻塞 等待三路握手完成 → 睡眠
非阻塞 不能立刻建立 → -1, errno = EINPROGRESS（不是 EWOULDBLOCK），握手在后台继续

💡 后续拓展留白
- fcntl 获取/设置 O_NONBLOCK 模板

个人学习总结

非阻塞 I/O 四类操作：非阻塞 read/write（EWOULDBLOCK）、非阻塞 connect（EINPROGRESS）、非阻塞 accept（防 RST 后死锁）。

一句话：fcntl 设 O_NONBLOCK → 所有操作"能做就做，不能做就立即返回错误"。

非阻塞 + epoll = Linux 高并发网络编程标准模型。

16.2

非阻塞读和写：str_cli 函数（修订版）

Ch 6 str_cli · Ch 6.7 终版

核心主旨

Ch 6 用 select 同时监听 stdin 与套接字，仍不够健壮：

  • 恶意服务器灌数据 → stdout 阻塞
  • 发送窗口满 → write 阻塞
    → 整个 select 循环被挂起（DoS）

终极方案：stdin、stdout、套接字全部非阻塞。

用户态缓冲区管理

缓冲区 作用
to 从 stdin 读入、待发往套接字
fr 从套接字读入、待发往 stdout

每缓冲区维护 iptr（下次写入空闲位）、optr（下次读出有效数据）。

事件驱动逻辑

to 有空闲 → 才把 stdin 加入 select 读集
to 有待发数据 → 才把 sockfd 加入 select 写集
fr 同理（sock 读、stdout 写）
每次 I/O 后调整 iptr/optr；排空则指针归位

重点结论

收益 代价
更高吞吐、抗死锁 代码量剧增、指针/状态易错

这正是 Netty、libuv 等框架封装非阻塞状态机的原因。

个人学习总结

非阻塞 read/write + select 的缓冲状态机：to 缓冲（stdin→socket）+ fr 缓冲（socket→stdout），用 iptr/optr 指针驱动。

核心逻辑：read 返回 EWOULDBLOCK → 标记"暂无可读"→ select 等下次就绪 → 继续读。

一句话：非阻塞读写 = 自己管理缓冲 + select 驱动状态机——复杂但不会死锁。

这是 str_cli 的终极形态——全非阻塞 + 缓冲管理。

16.3

非阻塞 connect

Ch 4.3 connect · 14.2 select 超时

核心主旨

非阻塞 connect → 立即 EINPROGRESS，握手在内核后台进行。

三大优势

# 能力
1 重叠处理：RTT 等待期间可做其他计算
2 并发连接：单线程同时发起大量 connect（浏览器、爬虫）
3 精准超时：用 select 等待，短于默认 ~75s

完成后 select 行为

结果 套接字在 select 中
成功 可写
失败（拒绝、超时等） 可读且可写，并有 pending error

易错细节

不能仅凭「可写」断定成功 — 失败时也可能唤醒写集（见 16.4 getsockopt(SO_ERROR)）。

个人学习总结

非阻塞 connect 立即返回 EINPROGRESS → select 等可写 → getsockopt(SO_ERROR) 检查是否成功。

三大优势：①同时发起多个 connect ②connect 期间做其他事 ③自带超时控制（select timeout）。

关键：select 可写≠成功——必须 getsockopt(SO_ERROR)==0 才确认。

HFT 关联：并发建连是非阻塞 connect 的典型场景——同时连接多个交易所网关。

16.4

非阻塞 connect：时间获取客户程序

16.3 · Ch 7.2 getsockopt

核心演练

通用 connect_nonb（自定义超时）步骤：

1. fcntl → O_NONBLOCK
2. connect：
     返回 0 → 极少（如本机）→ 清理后成功
     返回 -1 且非 EINPROGRESS → 失败
3. fd 加入 select 读集+写集，带超时
4. select 返回 0 → ETIMEDOUT，close
5. select 唤醒后 → 必须用 getsockopt(SO_ERROR) 验证（见下）
6. 按需恢复阻塞模式

致命陷阱：验证是否真成功

select 显示可写（或可读可写）≠ 连接成功。

步骤 说明
getsockopt(fd, SOL_SOCKET, SO_ERROR, &error, …)
error == 0 真正成功
error != 0（如 ECONNREFUSED） 失败

跨平台（BSD vs 早期 Solaris）差异下，SO_ERROR 是最稳妥判定方式。

💡 后续拓展留白
- 各内核对失败 connect 唤醒 select 的差异

个人学习总结

非阻塞 connect 版时间客户端：connect_nonb 封装 → EINPROGRESS → select → getsockopt(SO_ERROR)。

一句话：connect_nonb = 非阻塞 connect + select 超时 + SO_ERROR 验证。

与阻塞 connect 对比：阻塞版无法设超时（除非用 alarm）；非阻塞版用 select timeout 控制。

16.5

非阻塞 connect：Web 客户程序

16.3 · 16.4

架构设计

简易 Web 客户端：并行拉取多张图片。

阻塞串行 非阻塞并发
总耗时 ≈ 各连接 RTT+传输累加 总耗时 ≈ 最慢一条（带宽够时）

状态机架构

结构体数组：{ fd, 状态, 缓冲 }
状态：待连接 → 连接中 → 读取中 → 完成

循环：
  多个非阻塞 connect → 全部加入 select
  可写 → 发 HTTP GET → 状态=读取中，只监听读
  可读 → read 直至 EOF → 完成

性能结论

并发非阻塞 connect 压榨管道闲置时间 — 压测工具、代理、浏览器内核的基础模式。

个人学习总结

非阻塞 connect 并发 Web 客户端：同时发起 N 个连接 → select 监听全部 → 逐个完成读写。

一句话：一个线程管理 N 个并发连接——非阻塞 + select 的威力。

这是从"一连接一进程"到"单线程多连接"的范式转变——Ch30 设计模式的基础。

16.6

非阻塞 accept

Ch 4.6 accept · Ch 6.8 TCP 服修订

核心主旨

即使用非阻塞读写，监听套接字也必须非阻塞 accept — 否则存在隐蔽死锁。

致命时序：被中止的连接（Aborted Connection）

1. 客户端 SYN 完成 → 进入已完成连接队列
2. select：listenfd 可读 → 唤醒服务器
3. 缝隙：客户端发 RST（进程被杀、SO_LINGER 等）
4. Berkeley 类实现：内核从队列中**悄悄移除**该连接
5. 服务器调用**阻塞** accept → 队列已空 → **永久睡眠**
6. 单线程服务器挂死，其他就绪 fd 永不处理

黄金法则

select/poll 处理 listenfd 时：

必须 O_NONBLOCK on listen socket

  • 队列为空时 accept → EWOULDBLOCK
  • 应用忽略该错误，回到 select 主循环

重点结论

非阻塞 accept 是应对 select 就绪与内核队列变化之间 竞态 的强制防御，高可用网关的底线。

个人学习总结

select 报 listenfd 可读后，如果客户在 accept 前 RST → 已完成队列清空 → accept 阻塞 → select 不再报就绪 → 死锁。

解法：listenfd 设非阻塞 → accept 返回 EWOULDBLOCK → continue。

一句话：select 版服务器必须把 listenfd 也设非阻塞——防 RST 竞态死锁。

这个 bug 极罕见但真实存在——生产代码中 listenfd 非阻塞是防御性编程。

16.7

小结

study.md

章节核心提炼

1. 范式跨越

从顺序阻塞 → 异步事件 + 用户态缓冲状态机（to/fr、iptr/optr）。

2. 非阻塞 connect

  • EINPROGRESS + 后台握手
  • 重叠、并发、select 超时
  • 成功判定：getsockopt(SO_ERROR)，不能只看可写

3. 非阻塞 accept

配合 select 的 listenfd：必须非阻塞，防 RST 幽灵连接 导致阻塞 accept 死锁。

错误码速记

操作 典型 errno
读/写/accept 无就绪 EWOULDBLOCK / EAGAIN
connect 进行中 EINPROGRESS
connect 失败（SO_ERROR） ECONNREFUSED 等
connect 超时 ETIMEDOUT（应用层）

与现代框架

UNP 手写 现代
select + 非阻塞 + 缓冲 epoll/kqueue + libuv/Netty 状态机

个人学习总结

非阻塞 I/O + select = 单线程管理多连接。四类操作：read/write（EWOULDBLOCK+缓冲）、connect（EINPROGRESS+SO_ERROR）、accept（防RST死锁）。

关键认知：非阻塞不是"更快"——单次操作可能更慢（重试），但能同时管理多连接 → 整体吞吐更高。

HFT 关联：epoll + 非阻塞 I/O 是 Linux C10K/C100K 的标准解法。
