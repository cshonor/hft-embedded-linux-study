13.1

概述

Ch 11 · 13.2 syslogd · study.md

核心主旨

如何让网络服务器在后台安静、稳定运行。

守护进程（Daemon）

属性 说明
定义 后台运行、无控制终端的进程
生命周期 常于系统引导启动，直至关机
无终端的意义 不收键盘信号（SIGINT、SIGTSTP）；错误不会打到用户屏幕

启动方式分类

方式 示例
引导脚本 /etc/rc 等；inetd、Web 服、syslogd（常 root）
inetd 超级服务器 按需派生具体服务
cron 定期执行 → 子进程亦为守护进程
at 指定时刻执行一次
用户后台 nohup 或命令末尾 &

资料说明

上传 PDF 可视内容截至第 8 章；第 13 章按 UNP 第 3 版体系整理，请与全本对照验证。

个人学习总结

守护进程 = 后台运行、无控制终端的进程。启动方式：引导脚本、inetd、cron、nohup。

一句话：守护进程的核心特征是"无控制终端"——不收键盘信号，错误不打到屏幕。

网络服务器几乎都以守护进程方式运行。

13.2

syslogd 守护进程

13.3 syslog · UDP 514：Ch 8

核心机制

守护进程无控制终端，不能用 printf/perror 打到 stderr。中心化日志由 syslogd 处理。

启动与配置

  • 系统启动时运行
  • 读 /etc/syslog.conf（或发行版等价路径）
  • 决定各类消息路由：文件、用户、远程主机等

三种消息接收渠道

渠道 说明
Unix 域数据报 常绑定 /dev/log，本地应用发日志
UDP 514 接收其他主机转发的 syslog
内核设备 如 /dev/klog，内核消息

逻辑脉络

应用 syslog() → /dev/log（本地）→ syslogd → 按配置落盘/转发

个人学习总结

syslogd = 中心化日志守护进程，监听 Unix domain socket + UDP 514。所有程序通过 syslog 接口统一写日志。

一句话：守护进程不能 printf 到终端——所有日志走 syslog。

syslog 支持分级（EMERG~DEBUG）和分类（auth, daemon, local0~7）。

13.3

syslog 函数

13.2 syslogd · 13.6 daemon_inetd

核心 API

void syslog(int priority, const char *message, ...);

应用通过 syslog 与 syslogd 通信。

priority：facility | level

设施（Facility）— 子系统分类

示例 含义
LOG_AUTH 安全/授权
LOG_DAEMON 系统守护进程
LOG_MAIL 邮件
LOG_USER 用户级（默认）
LOG_LOCAL0～LOG_LOCAL7 本地预留

级别（Level）— 严重程度（高→低）

LOG_EMERG → LOG_ALERT → LOG_CRIT → LOG_ERR → LOG_WARNING → LOG_NOTICE → LOG_INFO → LOG_DEBUG

辅助函数

函数 作用
openlog(ident, options, facility) 设日志前缀（常为程序名）；LOG_PID、LOG_CONS 等
closelog() 关闭与 syslogd 通信的描述符

易错细节

  • inetd 子服务：禁止 printf/fprintf(stderr) — 须用 syslog（见 13.6）
  • priority 用 LOG_MAKEPRI 或 facility+level 宏组合，勿手写错位数

个人学习总结

openlog(ident, option, facility) + syslog(priority, format, ...) — 向 syslogd 发日志。

一句话：openlog 设程序名+分类，syslog 发消息（类似 fprintf）。

HFT 关联：热路径不要 syslog（IO 开销）；用 lock-free ring buffer + 异步落盘。

13.4

daemon_init 函数

fork/setsid：Ch 4.7 · 信号：Ch 5.8

核心逻辑

从普通进程变为守护进程的 6 步黄金法则（书中 daemon_init 封装）。

步骤拆解

1. 第一次 fork，父进程 exit

目的 说明
归还 shell 前台启动时 shell 认为命令结束
非组长 子进程 不是进程组组长 → 下一步才能 setsid

2. setsid 创建新会话

  • 成为 会话首进程、新进程组组长
  • 彻底脱离原控制终端

3. 忽略 SIGHUP + 第二次 fork（SVR4 推荐）

  • 父进程（会话首进程）再 exit
  • 原因：SVR4 类系统上，无终端的会话首进程若打开终端设备，可能重新获得控制终端
  • 第二次 fork 后子进程 不再是会话首进程 → 杜绝日后误获控制终端

4. chdir("/")

  • 避免工作目录在可卸载文件系统上导致无法卸载

5. umask(0)

  • 清除继承的文件模式掩码，按守护进程自身策略建文件

6. 关闭 fd + 重定向 stdio

  • 关闭不需要的描述符
  • 0、1、2 → /dev/null

易错细节（灾难级）

若不重定向 0/1/2：

  • 库函数写 stdout 可能失败，或
  • 写到恰好占用 0/1/2 的套接字 → 破坏网络协议

个人学习总结

daemon_init 六步：①fork → 父退出 ②setsid（新会话组长，脱离终端）③再 fork（防止重新获取终端）④chdir("/") ⑤umask(0) ⑥close(0/1/2) 或重定向到 /dev/null。

一句话：双 fork + setsid 是守护进程标准创建流程。

第二次 fork 是防止通过 open(/dev/tty) 重新关联终端——SVR4 细节。

13.5

inetd 守护进程

select：Ch 6 · dup2/exec：Ch 4.7

核心主旨

早期每个网络服务（Telnet、FTP、TFTP）各有一个常驻守护进程阻塞在 accept/recvfrom → 进程表浪费。

inetd（Internet Superserver） 统一监听、按需派生。

工作流

1. 读 /etc/inetd.conf（服务名、类型、协议、wait/nowait、用户、程序路径）
2. 每项：socket → bind → 全部加入 select 集
3. 某 fd 就绪（如 TCP 23）：
   - nowait TCP → accept 得已连接套接字
4. fork 子进程：
   - dup2(已连接套接字, 0/1/2)
   - 关闭其余 fd
   - exec 具体程序（如 in.telnetd）
5. 父进程 close 已连接套接字 → 回到 select

wait vs nowait

配置 典型
nowait 并发 TCP；父不等待子
wait 部分 UDP/单实例服务；父可能等子结束再 accept 下一报

（以配置与实现为准，读 inetd.conf 注释。）

重点结论

由 inetd 启动 的服务程序：

不必 socket / bind / listen / accept — 从 fd 0 读、向 fd 1 写 即网络 I/O。

历史注记

现代系统多由 systemd/xinetd 等替代 classic inetd，但 dup2(0,1,2) 模型仍常见。

个人学习总结

inetd = 超级服务器：读 /etc/inetd.conf → 为每个服务创建 listen socket → select 等待 → accept → fork → dup2(0,1,2=connfd) → exec 服务程序。

一句话：inetd 把"监听+fork+exec"统一托管——服务程序只需读 stdin/写 stdout。

优点：省进程（空闲服务不占内存）；缺点：fork+exec 每连接开销大——不适合高频连接。

13.6

daemon_inetd 函数

13.4 daemon_init · 13.5 inetd · 13.3 syslog

适用场景

专为 inetd 拉起 的程序编写初始化 — 不要 再调 daemon_init（inetd 已脱离终端）。

书中封装：daemon_inetd（或等价逻辑）。

获取客户身份

无 accept 环节，仅有 0/1/2 = 网络套接字：

getpeername(0, ...);   /* 对 fd 0 查远程 IP/端口 */

日志输出陷阱

禁止 原因
printf / fprintf(stderr, ...) 1、2 已是网络套接字 → 文本发往客户，破坏协议
合法 说明
syslog 唯一安全的错误/调试出口

与 13.4 对比

自启动守护进程 inetd 子服务
初始化 daemon_init 仅 openlog + getpeername 等
套接字 API 自备 listen/accept 无；stdio = 网络
日志 syslog 必须 syslog

个人学习总结

inetd 托管的服务程序：fd 0/1/2 = 连接套接字，用 getpeername(0) 获客户地址，错误只能 syslog（禁止 stderr）。

一句话：inetd 服务不 socket/bind/listen/accept——直接 read(0)/write(1) 处理客户。

自守护进程 vs inetd 托管：前者自己管 socket，后者只管业务逻辑。

13.7

小结

study.md

章节核心提炼

1. 守护进程

  • 无控制终端的后台基石
  • 手写规范流程：fork → setsid → fork → chdir/umask → 关闭并重定向 I/O（daemon_init）

2. 日志隔离

  • 失去终端 = 失去屏幕
  • syslog 是守护进程合法、安全的输出

3. inetd 超级服务器

  • select 统一监听多服务
  • fork + dup2(0,1,2) + exec — 解释为何部分老服务源码里没有 accept

与现代部署

经典 UNP 常见现状
inetd systemd socket activation、独立守护进程
syslogd rsyslog/journald
daemon_init 步骤 仍适用于自写 C 守护进程；也可用 daemon(3)（非 POSIX）

个人学习总结

守护进程 = 无终端 + syslog 日志。创建用 daemon_init 六步。inetd 托管低频服务（省进程），高频服务自守护（避免 fork+exec 开销）。

一句话：自守护 = 自己 socket/listen/accept + syslog；inetd = 只管 read/write + syslog。

HFT 关联：交易系统是自守护进程——不能让 inetd 的 fork+exec 增加延迟。
