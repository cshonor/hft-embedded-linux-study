26.1

概述

Ch 4.7 fork · Ch 16 · study.md

核心主旨

传统并发服务器多用 fork；痛点：

痛点 说明
开销 进程创建/切换成本高（虽有 COW）
IPC 复杂 共享数据需管道、共享内存等

线程（Thread / LWP）：同进程内轻量并发。

共享 vs 私有

共享（进程级） 私有（每线程）
全局内存、套接字 fd、打开文件 线程 ID、寄存器、栈
信号处理、当前工作目录 errno

标准

本书统一 POSIX 线程（Pthreads）（IEEE 1003.1c-1995）重构网络并发。

资料说明

上传资料截至第 8 章；第 26 章按 UNP 第 3 版体系整理，请与全本对照验证。

个人学习总结

线程 vs fork：线程共享地址空间（更快创建、通信更简单），fork 隔离地址空间（更安全、可 exec）。

一句话：线程适合"同一程序并发处理多连接"，fork 适合"不同程序/隔离"。

HFT 关联：DPDK lcore 模型 = 每核一线程 + 共享地址空间 + 绑核轮询。

26.2

基本线程函数：创建和终止

Ch 5.10 wait

API 与进程 API 对照

线程 进程 原型要点
pthread_create fork int pthread_create(pthread_t *tid, const pthread_attr_t *attr, void *(*func)(void *), void *arg);
pthread_join waitpid int pthread_join(pthread_t tid, void **status); — 无 WNOHANG，须指定 tid
pthread_self getpid 当前线程 ID
pthread_detach — 分离态，终止时自动回收
pthread_exit exit（线程级） 结束当前线程

pthread_create

  • 新线程从 func(arg) 开始；多参数须 打包结构体 传指针

Joinable vs Detached

状态 说明
Joinable（默认） 终止后成 僵死线程，直到 pthread_join 才释放栈等
Detached 终止即回收

实践：不关心退出状态时，子线程启动后 pthread_detach(pthread_self())。

致命陷阱

任意线程调用 exit() → 整个进程及所有线程立即终止。

个人学习总结

pthread_create(&tid, attr, func, arg) 创建线程；pthread_join(tid, &retval) 等待结束；pthread_detach(tid) 分离（自动回收）。

一句话：join 等子线程结束（类似 waitpid），detach 让子线程自动回收（类似 daemon）。

子线程勿调 exit()——会终止整个进程！用 pthread_exit 或 return。

26.3

使用线程的 str_cli 函数

Ch 6 str_cli · Ch 6.6 shutdown

架构设计

用多线程替代 select 改造回射客户端。

线程 职责
主线程 stdin → write 到套接字
子线程 套接字 read → stdout

终止边界（核心难点）

主线程：stdin EOF → shutdown(sockfd, SHUT_WR) 发 FIN → return 结束
         （尚有子线程时进程不退出，main 可 pthread_join）

子线程：read 得 EOF（对端 FIN）→ 应结束
         若子线程调用 exit(0) → 整个进程退出

须明确 谁 join 谁、谁 detach、何时 shutdown，避免半关闭与进程过早 exit。

个人学习总结

线程版 str_cli：主线程读 stdin→writen，子线程读 socket→fputs。EOF 时 shutdown(SHUT_WR) 通知对端。

一句话：线程版 str_cli = 读写分离两线程——比 select 版更直观。

问题：子线程 fputs 与主线程 fgets 可能交错输出——需要同步或分开缓冲。

26.4

使用线程的 TCP 回射服务器程序

Ch 4.8 并发服 · Ch 5 SIGCHLD

核心主旨

每来一个客户 pthread_create 一线程，取代 fork 模型。

陷阱 1：connfd 指针竞争

connfd = accept(...);
pthread_create(&tid, NULL, doit, &connfd);  /* 错：传栈上地址 */

主线程很快再次 accept 覆盖 connfd → 子线程读到错误 fd。

方案 做法
A 动态分配 malloc 存 connfd，子线程用完 free
B 值强转 sizeof(int) <= sizeof(void*) 时 (void *)(intptr_t)connfd

陷阱 2：主线程不能 close(connfd)

模型 父/主线程 close？
fork 父进程 必须 close(connfd)（独立 fd 表）
线程 绝对不能 close — 共享 fd 表，子线程 fd 会失效

个人学习总结

线程版 TCP 服务器：accept → pthread_create(线程函数, connfd) → 主线程继续 accept。

关键陷阱：不能传 &connfd——accept 可能在子线程读 connfd 前就覆盖它。用 malloc(sizeof(int)) 或直接传 (void*)connfd。

一句话：传参用 malloc 或强转——禁止传栈地址（竞态）。

主线程不能 close(connfd)——与 fork 不同，线程共享 fd 表。

26.5

线程特定数据

Ch 11.18 不可重入 · Ch 3.9 readline

核心主旨

多线程调用不可重入函数（静态缓冲的 readline、gethostbyname 等）会互相覆盖。

若不能改函数签名传外部缓冲 → 用 线程特定数据（TSD）。

TSD 流程

1. pthread_key_create(&key, destructor)   /* 常配合 pthread_once 只建一次 */
2. ptr = malloc(...); pthread_setspecific(key, ptr)
3. 深处：pthread_getspecific(key) 得本线程副本
4. 线程结束：destructor 自动 free

重点结论

TSD = 每线程一份的「全局变量副本」，隔离遗留 API 的静态状态。

个人学习总结

TSD（Thread-Specific Data）：pthread_key_create + pthread_setspecific + pthread_getspecific。每线程有独立的私有数据副本。

一句话：TSD = 线程版的"全局变量"——名字全局可见，值每线程独立。

替代方案：_Thread_local（C11）/ __thread（GCC）更简洁，编译期完成。

26.6

Web 客户与同时连接

Ch 16.5 Web 客户 · 26.7 互斥锁

应用场景

多线程 Web 客户端：并行下载，但限制最大并发连接数（如 5），防防火墙/服务器封禁。

架构需求

主线程：扫描 URL 列表，活跃线程数 < MAX → pthread_create 新下载线程
全局 active_count：主线程与子线程并发读写 → 数据竞争

→ 引出 互斥锁（26.7）与 条件变量（26.8）。

个人学习总结

并发 Web 客户端：同时发起 N 个连接 → 限制并发数 → 满槽等待。

问题：如何让主线程知道"有空位了"？→ 条件变量。

这是 26.7-26.9 的铺垫——mutex + cond 完整方案。

26.7

互斥锁

26.6 · 26.8 条件变量

核心定义

互斥锁（Mutex）：保护多线程共享数据，避免并发读写不一致。

pthread_mutex_t mutex;
pthread_mutex_lock(&mutex);
/* 临界区：读-改-写 active_count 等 */
pthread_mutex_unlock(&mutex);

行为

  • 锁已被占用 → pthread_mutex_lock 阻塞直至释放
  • 将多步操作变为不可分割的 临界区

局限

仅 Mutex 无法让线程在「条件未满足」时高效休眠 — 自旋 lock→检查→unlock 浪费 CPU（见 26.8）。

个人学习总结

pthread_mutex_t — 互斥锁保护共享数据。pthread_mutex_lock / unlock。

一句话：mutex = "同一时间只有一个线程进入临界区"。

易错：忘记 unlock → 死锁；lock 后调 exit → 全进程退出。

HFT 关联：热路径避免 mutex——用 lock-free ring buffer（DPDK rte_ring）。

26.8

条件变量

26.7 Mutex · 26.9

核心主旨

活跃连接已满时，主线程应休眠等待槽位，而非 Mutex 自旋轮询。

条件变量（pthread_cond_t）必须与 Mutex 配合。

pthread_cond_wait

int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);

原子逻辑（调用前已持有 mutex）：

  1. 线程睡眠
  2. 自动解锁 mutex
  3. 被唤醒后返回前 自动重新加锁 mutex

虚假唤醒：必须用 while

pthread_mutex_lock(&mutex);
while (active_threads >= MAX_THREADS) {
    pthread_cond_wait(&cond, &mutex);
}
active_threads++;
pthread_mutex_unlock(&mutex);

禁止用 if 只等一次。

唤醒

API 作用
pthread_cond_signal 唤醒一个等待线程
pthread_cond_broadcast 唤醒全部等待线程

个人学习总结

pthread_cond_t — 条件变量：配合 mutex 实现"等待条件成立"。pthread_cond_wait(&cond, &mutex) 原子地解锁+睡眠，被唤醒后自动加锁。

铁律：cond_wait 必须在 while 循环中——防止虚假唤醒（spurious wakeup）。

一句话：mutex 保护数据，cond 通知"数据变了"——wait 时解锁让生产者能修改。

经典模式：生产者 lock→修改→signal→unlock；消费者 lock→while(!ok) wait→处理→unlock。

26.9

Web 客户与同时连接（续）

26.6 · 26.7 · 26.8

融合架构

Mutex + 条件变量 完善并发 Web 客户端（生产者-消费者式槽位控制）。

主线程

pthread_mutex_lock
while (active >= MAX)
    pthread_cond_wait(&cond, &mutex)
active++
pthread_create(...)   /* 新下载线程 */
pthread_mutex_unlock

子线程（下载结束）

pthread_mutex_lock
active--
pthread_cond_signal(&cond)   /* 唤醒可能等待的主线程 */
pthread_mutex_unlock
pthread_exit(NULL)

重点结论

主线程在槽位满时 零 CPU 空转 等待；子线程释放槽位即 signal — 经典并发 Web 客户模式。

个人学习总结

完整并发 Web 客户端：mutex 保护并发计数 → 满槽时 cond_wait → 子线程完成后 cond_signal → 主线程继续。

一句话：mutex + cond = "等待有空位" —— 生产者-消费者模式的经典实现。

这是线程同步的集大成——理解了这节，线程编程就过关了。

26.10

小结

study.md

章节核心提炼

优劣势

优势 代价
创建/切换快，共享 fd 与内存 无进程级内存隔离，竞态风险高

安全防范底线

  1. 传子线程：malloc 独立参数，或 (void*)connfd 值强转 — 禁止传栈上 &connfd
  2. 线程模型：主线程 勿 close 子线程正在用的 connfd
  3. 不需要 join 时：pthread_detach，防僵死线程耗尽资源
  4. 子线程慎用 exit() — 会杀掉全进程

同步三位一体

问题 手段
不可重入遗留 API TSD
共享计数器/全局状态 Mutex
等待「有空槽」 条件变量 + while

与 fork / select / 非阻塞对照

模型 典型场景
fork 简单并发服，隔离强
select 单线程多路复用
非阻塞 + epoll 高并发 C10K
pthread 每连接一线程；须严格同步

个人学习总结

Pthreads 核心：create/join/detach（生命周期）、mutex（互斥）、cond（同步）、TSD（私有数据）。

三大铁律：①子线程勿 exit() ②传参勿用栈地址 ③cond_wait 必须 while 循环。

与 fork 对比：线程快但共享地址空间（一个线程 crash 全进程死）；fork 慢但隔离（子进程 crash 不影响父）。

HFT 关联：DPDK lcore = 线程模型 + 绑核 + 轮询 + 无锁队列替代 mutex。
