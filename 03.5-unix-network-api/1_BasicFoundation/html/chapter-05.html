5.1

概述

章级索引：study.md · 上一章：Ch 4 · 下一节：5.2 服务器 main

核心主旨与关键论据

本章通过构建一个完整且可运行的 TCP 回射（Echo）客户/服务器程序，把前一章的基本套接字 API 组合成可运行系统。但在真实网络环境中，程序不仅要处理正常通信，更要应对各种网络异常和边界条件。

本章的核心目的：展示如何使程序变得 健壮（robust），以应对：

  • 进程崩溃、主机崩溃
  • 信号中断、僵死进程
  • 连接在半路上被 RST 中止
  • 单线程阻塞 I/O 无法同时感知键盘与网络

核心知识点与逻辑脉络

系统架构（三角色数据流）

步骤 行为
1 客户端从标准输入读入一行文本，经套接字发给服务器
2 服务器从网络接收数据，原样回射给客户端
3 客户端接收回射数据，输出到标准输出

这是全书第一个「端到端业务闭环」：不再是 Ch 1 的固定 26 字节时间串，而是任意长度的行文本双向流动。

边界条件防御（本章主线）

单纯实现收发极易在真实环境中死锁或崩溃。本章系统梳理：

类别 典型场景 对应小节
正常路径 启动、正常 EOF 终止 5.6、5.7
进程管理 僵尸、SIGCHLD、waitpid 5.8～5.10
连接异常 accept 前 RST、ECONNABORTED 5.11
对端终止 子进程 kill、FIN/RST、SIGPIPE 5.12～5.13
主机级故障 断电、重启、关机 5.14～5.16
数据表示 跨平台 struct 二进制 5.18
架构天花板 阻塞 stdin + 阻塞 socket 5.5、5.17 → Ch 6

与前后章关系

  • 依赖：Ch 4 的 socket/bind/listen/accept/connect/fork/close
  • 依赖：Ch 3 的 writen、readline、包裹函数
  • 引出：Ch 6 select/poll 解决「无法同时等键盘和网络」
  • 引出：Ch 7 SO_REUSEADDR、SO_KEEPALIVE 等选项

易错细节与重点结论

易混 纠正
Echo = 时间服务器？ 时间程序是定长读循环；Echo 服务器是 read+writen 回射，客户用 readline 按行
写完 Echo 就「会网络编程」？ 不加 5.8～5.16 的防御，生产环境必崩（僵尸、SIGPIPE、感知不到断线）
健壮 = 多写 try-catch？ Unix 网络健壮核心是 信号、waitpid、EINTR、忽略 SIGPIPE、多路复用

💡 后续拓展留白
- 全双工（Full-duplex）数据流图解：同一 TCP 连接上双向同时传是否阻塞
- 与 Ch 6 改造后 str_cli 的对比表（改造前/后）

个人学习总结

TCP Echo 程序是全书第一个"能跑"的完整 C/S。核心不是回射逻辑，而是边界条件：进程终止、信号中断、主机崩溃、数据格式。

一句话：Ch4 教 API 怎么调，Ch5 教 API 出错怎么办。

四象限异常：FIN（read=0）、RST（ECONNRESET/SIGPIPE）、超时（ETIMEDOUT）、僵尸（SIGCHLD）。

5.2

TCP 回射服务器程序：main 函数

5.1 概述 · 5.3 str_echo · 并发模型：Ch 4.8

核心主旨与关键论据

本节给出 并发 TCP 回射服务器 的标准 main 框架：在 Ch 4 的 bind/listen/accept 之上，用 fork 为每个客户派生子进程，父进程只负责接客，子进程负责 str_echo 业务。

核心知识点与代码拆解

初始化三件套

步骤 调用 要点
创建 Socket(AF_INET, SOCK_STREAM, 0) 得 listenfd
地址 填充 sockaddr_in INADDR_ANY（任意网卡）+ 本书约定端口（如 9877）
绑定监听 Bind → Listen(listenfd, LISTENQ) 套接字进入 LISTEN

主循环（并发模型核心）

for (;;) {
    connfd = Accept(listenfd, ...);   // 阻塞，得已连接套接字
    if ( (childpid = fork()) == 0) {  // 子进程
        Close(listenfd);              // 子不需要监听套接字
        str_echo(connfd);             // 处理该客户
        exit(0);
    }
    Close(connfd);                    // 父必须关闭！
}
角色 持有的 fd 职责
父进程 仅 listenfd（+ 已 close 的 connfd） 循环 accept
子进程 仅 connfd（已 close listenfd） str_echo 后 exit

为何子进程 close(listenfd)

  • 子进程继承了父进程所有打开 fd 的副本
  • 若不 close，子进程也「挂着」监听套接字，无意义且浪费
  • 更重要的是避免子进程误操作监听套接字

为何父进程 close(connfd)（全书铁律）

fork 后 connfd 引用计数 = 2（父+子各一份）：

  • 只有引用计数降为 0，内核才对 TCP 连接发 FIN、真正释放
  • 子进程 exit 会 close 子侧 connfd（计数 1）
  • 父若不 close，计数永不为 0 → 连接挂着、fd 泄漏、高并发下 EMFILE

逻辑脉络与因果关系

  1. 准备阶段：一个 listenfd 服务所有客户（知名端口）
  2. 接客阶段：accept 每次新建 connfd（四元组唯一）
  3. 分流阶段：fork — 父继续接客，子专服一客
  4. 资源阶段：父子各 close 不需要的 fd → 引用计数正确

易错细节与重点结论

陷阱 后果
父不 close(connfd) TCP 不断开、fd 耗尽、僵尸连接堆积
子不 close(listenfd) 多余 fd；极端情况下子误 accept
fork 失败未处理 应检查返回值，否则父当作子跑或逻辑错乱
先 str_echo 再 fork 变成迭代服务器，慢客户阻塞全员

考试一句：并发 TCP 服务器 = 一 listenfd 多 connfd + fork + 父关 connfd 子关 listenfd。

💡 后续拓展留白
- 对照 tcp_echo_serv.c 标注行号
- LISTENQ 与 Ch 4.5 双队列的关系
- 预 fork / prefork 模型预告（Ch 30）

个人学习总结

并发 TCP 服务器骨架：bind→listen→循环 accept→fork→父 close(connfd)→子 close(listenfd)→str_echo→exit。

铁律：fork 后 connfd 引用计数=2，父必须 close(connfd)，否则 fd 泄漏→EMFILE。

HFT 关联：fork 模型每连接一进程，上下文切换开销大；DPDK 用 lcore 线程池替代。

5.3

TCP 回射服务器程序：str_echo 函数

5.2 服务器 main · 5.4 客户 main · writen：Ch 3.9

核心主旨与关键论据

str_echo 是服务器子进程的业务核心：从已连接套接字读数据，原样写回。它体现了 TCP 字节流 在服务器侧的典型处理模式——读多少、回多少（直到对端关闭）。

核心知识点与代码拆解

典型逻辑（伪代码）

void str_echo(int sockfd)
{
    ssize_t n;
    char line[MAXLINE];

    again:
    while ( (n = read(sockfd, line, MAXLINE)) > 0)
        Writen(sockfd, line, n);    /* 把本次读到的 n 字节全部写回 */

    if (n < 0 && errno == EINTR)
        goto again;                 /* 被信号打断则重试（包裹函数常内置） */

    /* n == 0：对端关闭，正常返回 */
}

三个 API 的分工

调用 作用 为何这样选
read（循环） 从网络读入缓冲区 TCP 无记录边界；一次 read 可能小于可用数据，也可能一次读多行
writen 保证把本次 n 字节全部写回 避免短写（short write）
返回条件 n==0 对端发 FIN，半关闭读侧 EOF 子进程返回 → exit → 发 FIN

为何用 read 而非 readline

read + 循环 readline
语义 透传字节块 按 \n 取一行
适用 Echo、代理、隧道 文本行协议（FTP 命令等）
缓冲 每次最多 MAXLINE，可含半行 内部静态缓冲，见 Ch 3.9 线程安全问题

回射服务不关心行边界：客户发 "hello\n" 可能被拆成两次 read，服务器仍按读到的块回射，客户 readline 最终拼成一行。

逻辑脉络与因果关系

客户 writen 一行 → 网络（可能分片）→ 服务器 read 得 n 字节
→ writen 回射 n 字节 → 客户 readline 收齐
… 重复直到客户 close → 服务器 read 返回 0 → str_echo 返回 → 子 exit

易错细节与重点结论

易错 纠正
read 一次以为读完一行 服务器应用 while (n>0)，不是读一次就 writen 一次就结束函数（除非 n=0）
writen 换成 write 可能短写，协议错乱
n=0 当错误 0 = 正常 EOF，对端关闭
子进程 str_echo 里再 fork 每连接一线程/一进程，不要再 fork

💡 后续拓展留白
- 若客户发 64KB 单行，MAXLINE 不够怎么办（缓冲区设计）
- 与 UDP dg_echo（Ch 8）「一次 recvfrom 一个报文」对比

个人学习总结

str_echo = 循环 read + writen 回射。read 返回 0 表示客户端 FIN，退出循环。

一句话：writen 保证写满（TCP 短写），read 不需要循环因为读多少回射多少。

易错：用 readn 替代 read 会导致"对端发 5 字节，readn 等 8 字节"死锁。

5.4

TCP 回射客户程序：main 函数

5.3 str_echo · 5.5 str_cli · connect：Ch 4.3

核心主旨与关键论据

客户 main 负责：校验参数 → 构造服务器地址 → 建立 TCP 连接 → 把已连接套接字交给 str_cli。与 Ch 1.2 时间客户端同源，但目标端口与业务函数不同。

核心知识点与代码拆解

命令行参数

  • 典型：client <服务器IP>
  • 必须校验 argc：缺 IP 则用法提示并退出
  • IP 为 ASCII 点分十进制（或后续扩展域名，Ch 11）

地址结构装填

bzero(&servaddr, sizeof(servaddr));
servaddr.sin_family = AF_INET;
servaddr.sin_port = htons(SERV_PORT);
if (inet_pton(AF_INET, argv[1], &servaddr.sin_addr) <= 0)
    err_quit("inet_pton error for %s", argv[1]);
步骤 要点
bzero 清零整个 sockaddr_in（本书偏好，见 Ch 3.5）
htons 端口转网络字节序
inet_pton 比 inet_addr 安全，支持错误区分；返回 ≤0 则参数非法

连接与交接

sockfd = Socket(AF_INET, SOCK_STREAM, 0);
Connect(sockfd, (SA *)&servaddr, sizeof(servaddr));
str_cli(sockfd);   /* 阻塞在这里直到用户 EOF */
exit(0);           /* 触发四次挥手 */
  • Connect 包裹函数：失败则 err_sys 退出
  • connect 失败后不能对同一 sockfd 再 connect（Ch 4.3）：须 close 后重新 socket

逻辑脉络与因果关系

解析 IP → socket → connect（三次握手，阻塞）→ str_cli（交互循环）
→ main exit → close 套接字 → 客户发 FIN

易错细节与重点结论

易错 纠正
忘记 htons 端口 连到错误端口或连接失败
inet_pton 返回值未检查 非法 IP 仍去 connect
connect 失败后重试同一 fd 必须 close + 新 socket
在 main 里写读写循环 应分离到 str_cli 便于 Ch 6 改造

💡 后续拓展留白
- 改为 getaddrinfo 协议无关版本（Ch 11）
- 命令行同时传端口：argv[2] + htons(atoi(...))

个人学习总结

客户端 main：socket→inet_pton 填地址→Connect→str_cli→close。

一句话：inet_pton 把点分十进制转网络序二进制，Connect 触发三次握手。

与 Ch1.2 的区别：1.2 用 IPv4 硬编码，这里用 inet_pton 更规范。

5.5

TCP 回射客户程序：str_cli 函数

5.4 客户 main · Ch 6 改造：6.4

核心主旨与关键论据

str_cli 实现客户侧交互循环：键盘 → 网络 → 网络 → 屏幕。它暴露了单线程阻塞 I/O 的根本缺陷——进程同一时刻只能阻塞在一个描述符上（此处是 stdin），无法在对端已死时立刻感知。

核心知识点与代码拆解

数据流转（四步循环）

while (Fgets(sendline, MAXLINE, stdin) != NULL) {
    Writen(sockfd, sendline, strlen(sendline));
    if (Readline(sockfd, recvline, MAXLINE) == 0)
        err_quit("str_cli: server terminated prematurely");
    Fputs(recvline, stdout);
}
步骤 函数 说明
读键盘 Fgets(stdin) 含换行符的一行；阻塞直到用户敲回车或 EOF
发送 Writen 把整行（含 \n）发给服务器
收回射 Readline 从套接字读到 \n 或 EOF
显示 Fputs(stdout) 原样打印

终止条件

  • 用户输入 EOF（Unix 常见 Ctrl+D）
  • Fgets 返回 NULL → 跳出循环 → 回到 main → exit(0)
  • 客户内核 关闭套接字 → 向服务器发 FIN，开始正常四次挥手（见 5.7）

Readline 返回 0 的含义

  • 对端已关闭写方向（收到 FIN 且读尽数据）
  • 本书在 5.12 等节用此打印 "server terminated prematurely"

逻辑脉络与因果关系

正常交互：stdin → writen → 服务器 str_echo → readline → stdout，循环。

异常但本函数发现不了的路径（5.12）：

服务器子进程被 kill → 客户 TCP 收 FIN
但客户阻塞在 fgets(stdin)  ← 不知道网络已断
用户终于输入一行 → writen 成功 → 服务器回 RST
→ readline 返回 0 → 才退出

这就是 「感知延迟」。

易错细节与重点结论

阻塞陷阱（本章最重要动机之一）

现象 原因
服务器已崩，客户仍「活着」 阻塞在 stdin，未监听 sockfd
用户不敲键盘就永远不退 无 select/poll、无 alarm、无 keepalive 读

结论：当前模型 无法兼顾「等用户输入」与「等网络事件」→ Ch 6 I/O 多路复用。

其它易错

易错 纠正
strlen 忘记包含 \n Fgets 带 \n，一般应发送含换行的一行
Readline 与 writen 长度不一致 应用同一行缓冲逻辑；服务器回射的是字节块不是逻辑行（但通常仍含 \n）
用 scanf 读 stdin 不适合带空格的行协议

💡 后续拓展留白
- Ch 6：同时 select(stdin, sockfd) 的伪代码
- 非阻塞 + epoll 现代等价物对比

个人学习总结

str_cli = fgets 读 stdin → writen 发送 → readline 读回射 → fputs 输出。

致命缺陷：stdin 和 socket 都是阻塞的——在对端不发数据时 fgets 阻塞，无法感知连接断开。引出 Ch6 select。

一句话：阻塞 I/O 的天花板就是 str_cli 的死锁场景。

5.6

正常启动

5.5 str_cli · 5.7 正常终止

核心主旨与关键论据

通过 netstat 和 ps 在真实系统上观测：服务器启动后、客户连接后，套接字状态与进程树长什么样。把 Ch 2 状态图、Ch 4 listenfd/connfd 从纸面落到命令行输出。

核心知识点与观测步骤

服务器刚启动（尚未 accept）

观测 预期
netstat -an（或 ss -lnt） 一条 LISTEN，本地 *:9877（或你的端口）
进程 一个 服务器父进程，睡眠在 accept

一个客户连接后

观测 预期
netstat 1× LISTEN + 2× ESTABLISHED（客户一条、服务器子进程一条）
ps -ef / pstree 父进程（等 accept）+ 子进程（跑 str_echo）
四元组 服务器子进程：本地 IP:知名端口 ↔ 客户 IP:临时端口（如 42758）
客户侧 本地 临时端口 → 服务器 :9877

临时端口（ephemeral）

  • 客户 bind 未指定端口时，内核在 49152～65535（实现相关）选端口
  • 服务器子进程的「外地地址」= 该客户的 IP:临时端口
  • 与 Ch 2.9、2.10 四元组分路 一致：第二个客户必须用不同临时端口区分

逻辑脉络与因果关系

父 listen → 客户 connect（ESTABLISHED 两端）→ 父 accept 得 connfd → fork
→ 子 ESTABLISHED 服务，父回到 LISTEN

易错细节与重点结论

易错 纠正
以为有两个 LISTEN 只有 listenfd 在 LISTEN；connfd 是 ESTABLISHED
看到两个服务器进程以为重复启动 正常：一父一子
macOS/Linux netstat 列不同 以本机 man netstat / 用 ss 为准

💡 后续拓展留白
- 实验记录：连接前后 ss -tnp 截图
- 两个客户同时连接时的 1 LISTEN + 4 ESTABLISHED

个人学习总结

正常启动观察：服务器 LISTEN，客户 connect 后双方 ESTABLISHED，fork 出子进程。

工具：netstat -a 看连接状态，ps 看进程父子关系。

这是"正常路径"的基线——后续 5.7-5.16 都是在偏离这条基线时排查。

5.7

正常终止

5.6 正常启动 · TIME_WAIT：Ch 2.7 · 僵尸：5.9

核心主旨与关键论据

客户在终端输入 EOF（Ctrl+D） 触发正常 TCP 终止序列（四次挥手）。同时演示：子进程 exit 后若无父进程回收，会出现 僵死进程（Zombie） —— 为 5.8～5.10 埋钩子。

逻辑脉络：四路挥手逐步对应程序

步 谁 程序/内核行为 TCP 状态（典型）
1 客户 str_cli 结束 → main exit → 关闭套接字 → 发 FIN 客户 FIN_WAIT_1 → …
2 服务器 内核收 FIN → ACK；子进程 read 返回 0 服务器半关闭；str_echo 的 while 结束
3 服务器子 str_echo 返回 → exit(0) → 关闭 connfd → 发 FIN 客户收 FIN
4 客户 内核回 ACK 主动关闭方 TIME_WAIT（2MSL）

与代码的对应

  • 客户：主动关闭方（先 EOF → exit → FIN）
  • 服务器子：被动关闭方先 ACK 客户 FIN，处理完后再发自己的 FIN
  • 父进程通常仍在 accept，不参与该连接的四次挥手（已 close connfd）

核心知识点：僵死进程

  • 子进程 exit 后进入 Zombie（<defunct>，ps 状态 Z）
  • 仍占 进程表项（PID、退出状态），直到父 wait/waitpid
  • 父忽略 SIGCHLD 或从不 wait → 僵尸堆积 → 无法再 fork（5.9～5.10 解决）

易错细节与重点结论

易错 纠正
以为子 exit 后进程表立刻清空 需父 wait；否则僵尸
TIME_WAIT 在服务器 主动关连接的一方（此处常是客户）进 TIME_WAIT
read 返回 0 是错误 正常 EOF，表示对端关闭写方向
父 close connfd 导致无法挥手 父已 close 只减引用；子仍持有 connfd 完成子侧挥手

💡 后续拓展留白
- netstat 观察 TIME_WAIT 四元组
- 与 5.12「进程被 kill」对比（仍可能有 FIN，但时序不同）

个人学习总结

正常退出：客户 close→FIN→服务器 read=0→子进程 exit→父收 SIGCHLD。

问题：不处理 SIGCHLD → 子进程变僵尸（Z 状态） → ps 可见。

僵尸进程占用 PID 但不占内存——但积累会耗尽 PID 表。

5.8

POSIX 信号处理

5.9 SIGCHLD · 5.13 SIGPIPE

核心主旨与关键论据

信号（Signal） 通知进程「某事件发生」，也称软件中断。网络服务器必须用可靠方式注册处理函数，并在慢系统调用被中断后正确恢复 —— 否则 accept/read 随机失败或僵尸泛滥。

核心知识点

信号处置三种方式

处置 含义
捕获（自定义函数） 执行 sigaction 指定的 handler
SIG_IGN 忽略（SIGKILL、SIGSTOP 不可忽略）
SIG_DFL 默认，多数为终止进程

为何不用传统 signal()

  • 历史上各系统对 signal 语义不一致（是否自动重启、是否可靠递送）
  • POSIX 规定用 sigaction

本书 Signal() 包裹函数

  • 首字母大写，内部 sigaction
  • 提供可移植、可预期的 POSIX 语义

SA_RESTART 的关键作用

场景 无 SA_RESTART 有 SA_RESTART
阻塞在 accept/read 信号来 → 慢调用返回 -1, errno=EINTR 内核自动重启该调用
编程负担 须手动循环重试（Read/Accept 包裹常做） 减少 EINTR 散落

注意：SIGCHLD 处理函数里调用的 waitpid 不应被 SA_RESTART 无限重启 —— 通常 handler 很短，返回后 accept 继续。

易错细节与重点结论

易错 纠正
在信号处理函数里 printf 非异步信号安全，可能死锁
以为所有信号会排队 同类型信号可能丢失（5.10）
多线程程序用同一套 handler 应用 pthread_sigmask、sigwait（进阶）
Pthread 函数错用 errno 线程 API 错误在返回值，不是 errno（Ch 1.4）

💡 后续拓展留白
- sigaction 结构体各字段（mask、flags）
- 多线程服务器信号递送到哪条线程

个人学习总结

POSIX 信号：用 sigaction 替代 signal（行为不统一）。SA_RESTART 让被中断的系统调用自动重启。

一句话：sigaction 是可靠信号注册的唯一正确方式；signal 不可移植。

HFT 关联：信号处理要 async-signal-safe——只设 flag 或 write + _exit，不做复杂操作。

5.9

处理 SIGCHLD 信号

5.10 waitpid · 5.7 僵尸

核心主旨与关键论据

任何子进程终止时，内核向父进程发 SIGCHLD。若父进程不处理（默认在某些系统上可能表现为忽略或需显式设置），子进程退出状态无人取走 → 僵死进程。并发服务器的 main 在 Listen 之后必须注册 SIGCHLD 处理。

逻辑脉络

子进程 exit → 内核发 SIGCHLD 给父
→ 父的信号处理函数运行（异步，打断 accept）
→ 处理函数内 waitpid 回收（见 5.10 必须 while+WNOHANG）
→ 父返回 accept 循环

典型注册位置（与 5.2 结合）

Listen(listenfd, LISTENQ);
Signal(SIGCHLD, sig_chld);   /* 或 sigaction 等价 */
for (;;) {
    connfd = Accept(...);
    if (fork() == 0) { ... }
    Close(connfd);
}

易错细节与重点结论

规则 说明
handler 里禁止 printf 只用异步信号安全函数（write 到 fd 1、waitpid 等）
handler 里不能只 wait 一次 信号不排队，并发断开可能丢信号（5.10）
与 SA_RESTART 配合 accept 被中断后应能继续接客
不要 SIG_IGN SIGCHLD 若还要并发 忽略则子变僵尸（除非用 SIGCHLD+SA_NOCLDWAIT 等特例，本书不主打）

💡 后续拓展留白
- 标准 sig_chld 完整源码粘贴
- 线程服务器用 wait 线程代替信号

个人学习总结

注册 SIGCHLD 信号处理器回收子进程。信号是排队丢弃的——多个子同时退出可能只收到一个 SIGCHLD。

一句话：信号处理器里必须 while(waitpid(WNOHANG)) 循环回收，不能只 waitpid 一次。

经典 bug：只 wait 一次 → 漏回收 → 僵尸残留。

5.10

wait 和 waitpid 函数

5.9 SIGCHLD

核心主旨与关键论据

父进程必须通过 wait / waitpid 取走子进程终止状态，子进程才从僵尸变为完全释放。并发网关的 SIGCHLD 处理函数里，只调用一次 wait 是致命错误 —— 必须用 while + waitpid(-1, ..., WNOHANG) 清空所有已退出子进程。

核心知识点

wait

pid_t wait(int *statloc);
  • 阻塞直到任意一个子进程终止
  • 返回终止子进程的 PID，状态写入 statloc
  • 无子进程时行为依实现（错误）

waitpid

pid_t waitpid(pid_t pid, int *statloc, int options);
能力 说明
指定 pid 等待特定子进程
WNOHANG 若无已终止子进程，立即返回 0，不阻塞
组合 SIGCHLD handler 内循环非阻塞收割

标准 SIGCHLD 处理模板（铁律）

void sig_chld(int signo)
{
    pid_t pid;
    int   stat;

    while ( (pid = waitpid(-1, &stat, WNOHANG)) > 0)
        printf("child %d terminated\n", pid);
    return;
}

生产环境 handler 内 printf 仍不推荐（非异步信号安全）；学习版可保留，考试记 while+WNOHANG 逻辑。

逻辑脉络：信号不排队陷阱

场景：5 个客户几乎同时断开 → 5 个子 exit → 可能产生 5 次 SIGCHLD，但 Unix 不对 SIGCHLD 排队。

错误实现 后果
handler 里只 wait() 一次 只回收 1 个子，其余 4 个僵尸
父从不注册 SIGCHLD 每个子进程都僵尸
正确实现 行为
while (waitpid(-1, &stat, WNOHANG) > 0) 一次信号处理收割所有已就绪子进程，直到返回 0

易错细节与重点结论

考试默写：while (waitpid(-1, &stat, WNOHANG) > 0);

易混 纠正
wait 与 waitpid 在 handler 里阻塞 handler 应用 WNOHANG，避免长时间占着信号
父进程 fork 前 wait 应在 SIGCHLD 处理函数或专门收割逻辑里 wait
子进程 double fork 成孤儿 进阶技巧（daemon），本书 Ch 13

💡 后续拓展留白
- WIFEXITED / WIFSIGNALED 解析 stat
- 高并发 prefork 父进程批量 wait

个人学习总结

wait 阻塞等任意子进程；waitpid 可指定 PID + WNOHANG 非阻塞。

铁律：SIGCHLD 处理器中用 while ((pid = waitpid(-1, &stat, WNOHANG)) > 0) 循环到返回 0 或 -1。

waitpid(-1, ..., WNOHANG) 返回 0 表示"还有子进程但没退出"——继续等下次信号。

5.11

accept 返回前连接中止

5.2 服务器 main · 全连接队列：Ch 4.5

核心主旨与关键论据

极端时序：三次握手完成，连接已进入已完成连接队列，但在父进程 accept 取出之前，客户端发送 RST 中止连接。不同内核行为不同；服务器必须防御性编程，不能把 ECONNABORTED 当致命错误。

逻辑脉络

客户 SYN → 服务器 SYN+ACK → 客户 ACK（连接 ESTABLISHED，在队列里）
→ 客户立刻 RST（或崩溃发 RST）
→ 父进程仍在 accept() 睡眠
→ accept 返回：成功 / 或 错误

内核实现差异

实现族 行为
Berkeley 系 内核丢弃已中止连接，accept 不返回该连接，父继续睡
SVR4 / POSIX 系 accept 返回 -1，errno 常为 ECONNABORTED（软件导致的中止）或 EPROTO

易错细节与重点结论

服务器主循环必须这样写

for (;;) {
    clilen = sizeof(cliaddr);
    if ( (connfd = accept(listenfd, (SA *)&cliaddr, &clilen)) < 0) {
#ifdef EPROTO
        if (errno == EPROTO || errno == ECONNABORTED)
#else
        if (errno == ECONNABORTED)
#endif
            continue;          /* 忽略，重新 accept */
        else
            err_sys("accept error");
    }
    /* fork ... */
}
要求 原因
ECONNABORTED → continue 瞬时异常，不能 err_sys 退出整个服务器
与 EINTR 区分 EINTR 常由信号引起，包裹 Accept 可能重启；ECONNABORTED 是「坏连接」

💡 后续拓展留白
- Linux accept 与 TCP_DEFER_ACCEPT
- 用 tcpdump 观察 RST 在 accept 前后的时序

个人学习总结

accept 被信号中断时：旧 BSD 返回 EINTR（错误），POSIX with SA_RESTART 自动重启。

现代写法：if (errno == ECONNABORTED) continue;——连接被中断就重新 accept。

一句话：EINTR 不是真错，ECONNABORTED 也不是——continue 即可。

Linux accept 被 SIGCHLD 中断默认自动重启（SA_RESTART）。

5.12

服务器进程终止

5.5 str_cli 阻塞缺陷 · Ch 6：select

核心主旨与关键论据

模拟服务器子进程突然被 kill（如 kill -9 子进程 PID），观察客户端为何迟迟不知情，以及最终如何通过 RST + readline=0 退出。直接引出 I/O 多路复用 的必要性。

案例数据与网络机制（分步）

步 事件
1 子进程终止 → 内核关闭其所有 fd → 向客户发 FIN
2 客户 TCP 回 ACK → 服务器→客户方向关闭
3 客户应用阻塞在 fgets(stdin) → 对网络断开无感知
4 用户终于输入一行 → writen 成功（客户仍认为连接存在）
5 服务器侧无进程监听该连接 → 内核回 RST
6 客户 readline 返回 0（EOF）→ 打印 server terminated prematurely → 退出

逻辑脉络与因果关系

FIN 到达时应用在等键盘 ≠ 应用在等 socket
→ 应用层状态与 TCP 状态脱节
→ 直到再次使用 socket（writen+readline）才暴露 RST/EOF

重点结论：单线程阻塞式 I/O 无法实时响应底层 TCP 事件。

易错细节与重点结论

易错 纠正
以为 kill 服务器父进程等同 kill 子进程（服务该连接者）才对应「服务崩溃」
收到 FIN 后 fgets 会失败 不会；fgets 看的是终端，不是 socket
writen 失败才察觉 本书路径常是 writen 成功、readline 得 0（先 FIN 后 RST 组合）
加多线程 fgets 就够 仍需 select 同时监视 stdin 和 sockfd

💡 后续拓展留白
- 实验：连接后 kill 子 PID，记录从 kill 到客户退出延迟
- Ch 6 改造后：FIN 到达即唤醒 select

个人学习总结

服务器子进程被 kill → connfd 关闭 → 内核发 FIN → 客户端 readline 得 0。

问题：客户端在 fgets 阻塞时不知道连接已断——直到下次 write/read 才感知。

一句话：FIN 的感知有延迟，需要写后读才能发现。引出 select 同时监听 stdin+socket。

5.13

SIGPIPE 信号

前置：5.12 · RST：5.15

核心主旨与关键论据

接续 5.12：若客户端在收到 RST 之后，不 read 而继续 write，内核向进程发 SIGPIPE；默认行为是终止整个进程。高可靠服务必须在初始化时 SIG_IGN SIGPIPE。

核心机制

条件 结果
向已收到 RST 的套接字 write 内核发 SIGPIPE 给进程
默认处置 SIG_DFL 进程被杀死
捕获或忽略 SIGPIPE write 返回 -1，errno = EPIPE

与 5.12 的衔接

  • 5.12：用户输入后 writen → RST → readline 得 0 退出（未必触发 SIGPIPE）
  • 5.13：强调继续写已复位连接 → SIGPIPE / EPIPE

易错细节与重点结论

标准防线（服务器/客户端初始化处）：

Signal(SIGPIPE, SIG_IGN);   /* 或 signal(SIGPIPE, SIG_IGN) 在包裹里 */
若不忽略 风险
某一客户异常 整个 echo 服务器进程被 SIGPIPE 杀死，其它客户全断
易混 纠正
EPIPE 与 ECONNRESET EPIPE 在 write；ECONNRESET 多在 read（对端 RST 后读）
只对服务器设 客户端同样应忽略，避免写已关闭连接时自杀

💡 后续拓展留白
- MSG_NOSIGNAL（Linux send）替代忽略 SIGPIPE
- 多进程服务器是否每个子进程都要设 SIG_IGN

个人学习总结

向已收到 RST 的连接 write → 内核发 SIGPIPE → 默认终止进程。

铁律：服务器/客户端启动时 signal(SIGPIPE, SIG_IGN)，然后 write 返回 EPIPE。

一句话：SIGPIPE 是"写已关闭连接"的信号——忽略它，用 EPIPE 返回值处理。

HFT 关联：所有网络程序第一件事就是 SIG_IGN(SIGPIPE)。

5.14

服务器主机崩溃

5.15 重启 · keepalive：Ch 7

核心主旨与关键论据

与 5.12 进程崩溃（内核还能发 FIN）不同：整机断电、拔网线 时，连接变成黑洞 —— 无 FIN、无 RST，客户可能长时间无感知。

故障演进

阶段 行为
1 客户 write 发出数据
2 无 ACK → TCP 指数退避重传 SYN 段上的数据或后续段
3 重传多次后放弃（如总计约 9 分钟 量级，依实现）
4 应用层 write/read 最终失败

应用层错误码

情况 典型 errno
一直重传无 ICMP ETIMEDOUT
中间路由器 ICMP 目的不可达 EHOSTUNREACH / ENETUNREACH

盲区陷阱

  • 客户一直不发数据（一直阻塞 fgets）→ 可能永远不知道主机已死
  • 对策：SO_KEEPALIVE（Ch 7）或应用层 心跳（Heartbeat） 定时写/读探测

易错细节与重点结论

对比 5.12 进程死 5.14 主机死
内核发 FIN？ 通常 有 无
感知速度 下次 I/O 可能较快 可能 分钟级 超时
客户阻塞 fgets 仍不知 仍不知

💡 后续拓展留白
- 实验：虚拟机拔网卡 vs kill -9
- 心跳包协议设计草图

个人学习总结

服务器主机崩溃（断电/内核 panic）→ 不发 FIN → 客户端不知道 → write 成功（缓冲区）→ read 阻塞 → 内核重传 SYN/数据 → 最终 ETIMEDOUT。

一句话：主机崩溃=黑洞，TCP 不可检测，只能靠超时或 SO_KEEPALIVE。

HFT 关联：行情断线检测必须用心跳+超时，不能依赖 TCP 自身。

5.15

服务器主机崩溃后重启

5.14 崩溃 · RST

核心主旨与关键论据

主机崩溃后快速重启：内存中 TCP 连接状态全部丢失，但客户仍以为旧连接有效。客户再发数据 → 服务器协议栈无匹配连接 → 回 RST → 客户 read 得 ECONNRESET。

异常场景拆解

步 说明
1 重启后服务器无崩溃前的 TCB
2 客户认为连接仍在，write 或 keepalive 探测
3 服务器收到「陌生」四元组数据 → RST
4 客户阻塞在 read（或 readline）→ 返回 -1，errno = ECONNRESET（Connection reset by peer）

易错细节与重点结论

errno / 现象 典型场景
ETIMEDOUT 5.14 黑洞、无 ICMP
ECONNRESET 5.15 重启后 RST、5.12 后 writen 再 read
EPIPE 5.13 向 RST 连接 write

一句：重启 = 状态丢失 + RST，比纯超时更快暴露错误（一旦发数据）。

💡 后续拓展留白
- 四象限表：FIN / RST / 超时 / SIGPIPE

个人学习总结

服务器崩溃后重启 → 旧连接的 SYN/数据到达 → 服务器无此连接 → 回 RST → 客户端 read 返回 ECONNRESET。

一句话：主机重启后旧连接收到 RST，比"主机崩溃"（ETIMEDOUT）感知更快。

与 5.14 对比：崩溃=超时（慢），重启=RST（快）。

5.16

服务器主机关机

等同进程终止表现：5.12

核心主旨与关键论据

Unix 正常关机时，init 会清理用户进程：先 SIGTERM 给进程机会优雅退出，超时则 SIGKILL。服务器进程被终止 → 内核关闭其套接字 → 向仍连接的客户发 FIN —— 对客户侧表现与 5.12 服务器进程终止 同类。

核心机制

阶段 信号/行为
1 向用户进程发 SIGTERM（可捕获，做清理）
2 未退出则 SIGKILL（不可忽略，强杀）
3 进程消失 → 所有 fd 关闭 → TCP FIN

逻辑脉络

关机 → 服务器进程死 → FIN 到客户
→ 若客户阻塞 fgets：仍可能延迟感知（同 5.12）
→ 用户输入后 writen/readline 才退出

易错细节与重点结论

对比 关机 崩溃（5.14）
发 FIN？ 有（正常终止路径） 通常无
客户感知 类似 5.12 超时为主

💡 后续拓展留白
- 优雅关机：捕获 SIGTERM 关闭 listenfd、通知客户

个人学习总结

服务器被 shutdown -h → 内核发 FIN → 客户端 read 得 0。但服务器进程可能被 SIGKILL → 等同 5.12 进程终止。

一句话：优雅关闭发 FIN（read=0），强制杀死不发 FIN（等同主机崩溃）。

SIGTERM 可捕获做 cleanup；SIGKILL 不可捕获，等同断电。

5.18

数据格式

字节序：Ch 3.4 · LP64：Ch 1.11

核心主旨与关键论据

跨主机传递 C 结构体二进制（含 long、浮点、嵌套）会遭遇三重灾难。网络编程禁止假设「对方内存布局与我相同」。

案例：struct { long arg1; long arg2; }

三层问题

# 问题 后果
1 类型尺寸 long 32 位（ILP32）vs 64 位（LP64）→ 长度不同
2 字节序 大端 vs 小端 → 数值解析错误
3 对齐填充 编译器 padding → 成员偏移、sizeof 跨平台不一致

错误做法

write(sockfd, &struct_arg, sizeof(struct_arg));  /* 危险！ */

对端按自己的布局 read → 静默数据损坏。

重点结论与最佳实践

方案 做法 适用
推荐 1：文本 snprintf 格式化为 ASCII（如 " %ld %ld "）→ 发送 → 对端 sscanf/atoi 解析 教学、低吞吐、调试友好
推荐 2：标准二进制 XDR（RFC 1832）、Protocol Buffers、MessagePack 生产、高吞吐
自建打包 显式大端、定宽整数（uint32_t）、无 padding 的「线格式」 嵌入式、极致控制

htons/htonl 只解决字段内字节序，不解决 struct 布局与尺寸。

易错细节与重点结论

易混 纠正
同一台机两个进程就能发 struct 仍可能 32/64 位进程混用（大小端通常同机相同）
JSON 就不用关心字节序 JSON 是文本；二进制协议仍要规范
#pragma pack(1) 就安全 仍要定字节序与版本号

💡 后续拓展留白
- 手写 4 字节大端 uint32 打包函数
- protobuf .proto 与 unp 无关但工程常用

个人学习总结

禁止直接 write(fd, &struct, sizeof(struct))——padding、字节序、大小在不同平台不一致。

正确做法：序列化为文本（HTTP/JSON）或显式二进制格式（逐字段 htons/htonl + memcpy）。

HFT 关联：行情协议有 FIX（文本）和 SBE/FAST（二进制），都是显式序列化。
