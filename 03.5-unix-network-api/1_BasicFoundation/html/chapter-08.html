8.1

概述

上一章：Ch 7 · 8.2 recvfrom/sendto

核心主旨与关键论据

TCP 与 UDP 应用在底层机制上本质不同：

TCP UDP
模型 面向连接、可靠字节流 简单、不可靠数据报
开销 握手、状态、重传 无连接建立，轻量
典型场景 HTTP、SSH DNS、NFS、SNMP 等

逻辑脉络：UDP 调用时序（图 8-1）

服务器

socket → bind → recvfrom（阻塞等数据）
→ 处理 → sendto（用 recvfrom 得到的客户地址回复）

无 listen / accept。

客户

socket → sendto（带目标地址）→ recvfrom（等应答）

无 connect（初版）。

重点结论

UDP = 每次 sendto 封装目的地 + recvfrom 带回源地址 的松散「一问一答」，无长期绑定通道。

资料说明

若你手头 PDF 仅含 8.1，8.2～8.16 笔记按 UNP 第 3 版知识体系整理，建议与教材对照验证。

💡 后续拓展留白
- UDP 8 字节头 vs TCP 至少 20 字节头

个人学习总结

UDP = 无连接、不可靠数据报。服务器 socket→bind→recvfrom/sendto 循环；客户 socket→sendto→recvfrom。无 listen/accept/connect。

一句话：UDP 每次 sendto 带目标地址，recvfrom 带回源地址——松散一问一答。

HFT 关联：UDP 是组播/行情分发的基础协议——低延迟、允许丢包。

8.2

recvfrom 和 sendto 函数

8.4 dg_echo · 值—结果：Ch 3.3

核心主旨

UDP 无连接状态，read/write 不能在 I/O 时指定对端地址，须用 recvfrom / sendto。

函数原型

ssize_t recvfrom(int sockfd, void *buff, size_t nbytes, int flags,
                 struct sockaddr *from, socklen_t *addrlen);

ssize_t sendto(int sockfd, const void *buff, size_t nbytes, int flags,
               const struct sockaddr *to, socklen_t addrlen);

recvfrom

参数 说明
from, addrlen 值—结果；内核填入发送方 IP+端口
不关心来源 from / addrlen 可为 NULL

sendto

  • to + addrlen：目的地，须 网络字节序 装填好的 sockaddr

易错细节与重点结论

现象 与 TCP 区别
0 字节 UDP 报文 recvfrom 返回 0 = 空数据报，不是 EOF
TCP read 返回 0 对端关闭连接（FIN）
地址结构太小 内核可能截断 from 中地址（旧系统或不警告）

💡 后续拓展留白
- MSG_PEEK 等 flags

个人学习总结

recvfrom(fd, buf, len, flags, &fromaddr, &addrlen) / sendto(fd, buf, len, flags, toaddr, addrlen)。

关键：recvfrom 返回 0 不是 EOF——UDP 的 0 字节数据报是合法的（与 TCP 不同）。

一句话：recvfrom 的 fromaddr 带回发送方地址；sendto 的 toaddr 指定接收方。

8.3

UDP 回射服务器程序：main 函数

8.4 dg_echo · 对比 TCP：Ch 5.2

核心逻辑

UDP 服务器初始化极简：

Socket(AF_INET, SOCK_DGRAM, 0)
→ sockaddr_in(INADDR_ANY, 端口) → Bind
→ dg_echo(sockfd)    /* 无 listen/accept */
步骤 说明
socket IPv4 数据报套接字
bind 通配 IP + 业务端口（如 7 echo、13 daytime 等）
dg_echo 直接进入接收循环

与 TCP 服务器对比

TCP UDP
bind → listen → accept 循环 bind → recvfrom 循环
每连接一 connfd 同一 sockfd 服务所有客户

个人学习总结

UDP 服务器 main：socket→bind→循环 recvfrom+sendto。无 listen/accept/fork——天然迭代服务器。

一句话：UDP 服务器比 TCP 简单一半——没有连接管理。

单进程迭代即可处理多客户——每个数据报独立处理。

8.4

UDP 回射服务器程序：dg_echo 函数

8.3 main

核心机制

void dg_echo(int sockfd, struct sockaddr *pcliaddr, socklen_t clilen)
{
    int    n;
    socklen_t len;
    char   mesg[MAXLINE];

    for (;;) {
        len = clilen;
        n = Recvfrom(sockfd, mesg, MAXLINE, 0, pcliaddr, &len);
        Sendto(sockfd, mesg, n, 0, pcliaddr, len);
    }
}

迭代服务器模型（Iterative Server）

点 说明
单进程 while(1) 交替处理多个客户乱序到达的报文
多数 UDP 服务器 迭代，不必像 TCP 那样每连接 fork
原因 无 per-connection 状态独占；一报文一处理

易错细节

陷阱 说明
业务极慢 单进程阻塞在慢处理 → 接收队列满 → 丢包（8.13）
以为要 fork UDP 默认可迭代；高负载才要线程/进程池

💡 后续拓展留白
- UDP 并发工作池架构

个人学习总结

dg_echo = recvfrom 收数据报 → sendto 原路回射。用 recvfrom 得到的客户地址直接 sendto 回去。

一句话：UDP 回射服务器核心就两行——recvfrom + sendto，无状态。

与 TCP str_echo 对比：TCP 需要循环 read（字节流），UDP 一次 recvfrom 就是一个完整消息。

8.5

UDP 回射客户程序：main 函数

8.6 dg_cli

核心主旨

  • 校验命令行：服务器 IP
  • inet_pton → 填入 sockaddr_in（网络字节序）
  • socket → 将 sockfd 与地址交给 dg_cli

与 TCP 客户 main 类似，但无 Connect（初版）。

个人学习总结

UDP 客户 main：socket→dg_cli→close。无 connect——sendto 时内核临时绑源地址。

一句话：UDP 客户连 connect 都不需要——sendto 直接带目标地址。

与 TCP 客户对比：TCP 必须 connect 建连，UDP 直接发。

数据流转

for (;;) {
    Fgets(stdin) → Sendto(服务器地址) → Recvfrom → Fputs(stdout)
}
EOF(Ctrl+D) → 退出
步 API
读键盘 fgets

缺陷：sendto 发出后如果丢包，recvfrom 永远阻塞——没有超时机制。

一句话：dg_cli 的基本版和 TCP str_cli 一样有阻塞天花板。

8.7

数据报的丢失

8.12 connect 修订 · Ch 6 超时：6.5 · SO_RCVTIMEO：Ch 7.5

核心主旨

初版 UDP 回射在广域网上极度脆弱：UDP 无可靠性。

通信陷阱

情况 客户行为
请求丢包 recvfrom 永久阻塞
应答丢包 同上
无 TCP 定时器 无从得知是否丢失

单边盲区 — 不像 TCP 有重传。

重点结论

绝不能无限期阻塞在 recvfrom 上。

须加应用层超时：

手段 章节
alarm + 信号 经典
select/poll 超时 Ch 6
SO_RCVTIMEO Ch 7.5

高可靠 UDP 还须自建 ACK + 重传 状态机（TFTP 等）。

个人学习总结

UDP 不可靠——数据报可能丢失（网络拥塞/接收缓冲满）。dg_cli 的 recvfrom 无超时 → 丢包则永久阻塞。

解法：alarm 超时、select 超时、SO_RCVTIMEO。

一句话：UDP 应用层必须自己实现超时+重传——TCP 帮你做的 UDP 都没有。

8.8

验证接收到的响应

核心主旨与安全漏洞

8.6 若 recvfrom(..., NULL, NULL) 忽略来源 → 混杂接收风险。

案例

场景 后果
客户临时端口 1500 任意主机向 客户IP:1500 发 UDP
recvfrom 不校验来源 假冒报文被当作服务器回射打印

解决机制

recvfrom(..., &from, &fromlen)   /* 保留来源地址 */
if (from.sin_addr != servaddr.sin_addr || from.sin_port != servaddr.sin_port)
    continue;   /* 丢弃，继续 recvfrom */

源 IP + 源端口 必须与 sendto 目标 严格一致。

易错细节

  • connect 后（8.11）内核自动过滤非绑定源 — 更简单
  • 多服务器/多路径场景校验逻辑更复杂

个人学习总结

recvfrom 返回的地址可能是冒充者——任何人都能向你的端口发 UDP。

验证：比较 recvfrom 的源地址与预期服务器地址，不匹配则丢弃。

一句话：UDP 无连接 → 无法验证来源身份 → 必须应用层校验或用 connect 绑定对端。

HFT 关联：行情订阅用组播，不需要验源；但交易指令必须验源。

8.9

服务器进程未运行

8.11 UDP connect · ICMP：Ch 5.5

核心异常

客户向开机但无 UDP 服务进程的主机发报文：

步 行为
1 目标内核收 UDP，无进程 bind 该端口
2 生成 ICMP 端口不可达 回客户机
3 这是 异步错误 — sendto 已成功返回（数据已交 IP 层）

关键结论（反直觉）

未连接的 UDP 套接字在多数实现上收不到该 ICMP 映射的错误。

→ 客户仍阻塞在 recvfrom，对失败一无所知。

逻辑对比

套接字状态 ICMP 端口不可达
未 connect UDP 常不传递给应用
已 connect UDP（8.11） 后续 read/write 可得 ECONNREFUSED 等

个人学习总结

UDP 服务器端口无进程 → 内核回 ICMP "port unreachable" → 但 ICMP 是异步错误——sendto 已返回成功。

问题：未 connect 的 UDP socket 收不到 ICMP 错误 → recvfrom 永远阻塞。

解法：UDP connect 后，ICMP 错误延迟到 read/write 时返回 ECONNREFUSED。

8.10

UDP 程序例子小结

阶段性提炼

初版 UDP 回射说明：写「对」很难。

难点 对策方向
丢包/乱序 应用层超时、重传、序号
来源伪造 校验 recvfrom 地址 或 connect
ICMP 异步错误 UDP connect
无流量控制 应用层 ACK、限流（8.13）

个人学习总结

UDP 基础三问题：①丢包无超时 ②来源不可信 ③异步错误不可达。

一句话：UDP "不可靠"不仅是丢包——还包括来源伪造和异步错误不可见。

前半章（8.1-8.10）是"裸 UDP"的问题暴露，后半章（8.11-8.16）是解法。

8.11

UDP 的 connect 函数

8.12 修订 dg_cli · 解决：8.9、8.8

核心主旨

针对 8.9 异步错误盲区，可对 UDP 调用 connect — 不发任何网络包（无 TCP 式握手）。

内核实质

  • 本地检查（路由等）
  • 把对端 IP+端口绑定到套接字控制块 → 已连接 UDP 套接字

三大根本改变（高频）

# 变化
1 发送 用 write/send，不用 sendto（或 sendto 地址 NULL）
2 接收 用 read/recv；只收 connect 锁定地址的报文 → 解决 8.8 混杂
3 错误 ICMP 端口不可达 等可映射到套接字 → read 返回错误（如 ECONNREFUSED）

重新连接与断开

  • UDP 可多次 connect（改目的地址）
  • AF_UNSPEC 可断开绑定

适用场景

单播、固定对端、需简化 API 或异步错误 — 优先 connect。
广播/多播 不能用 connect 到单目的地。

💡 后续拓展留白
- 已连接 UDP 连续 write 性能（省每次 sendto 选路）

个人学习总结

UDP connect 不发握手——只绑定对端地址。之后用 read/write 替代 sendto/recvfrom。

三大好处：①收 ICMP 异步错误（ECONNREFUSED）②内核做源地址过滤③只发一次 connect 的开销（微优化）。

一句话：UDP connect = "指定唯一对端"，不发握手但获得异步错误感知。

HFT 关联：UDP connect 适合一问一答场景；组播不能用 connect（一对多）。

8.13

UDP 缺乏流量控制

SO_RCVBUF：Ch 7.5 · TCP 对比：Ch 2.4

案例：发送端狂发

客户 for 循环 2000 次 sendto，服务器处理慢或 SO_RCVBUF 很小：

层 行为
网卡 → UDP 接收队列满 悄悄丢弃新报文
无窗口通告 不告诉发送方「慢点」
sendto 不阻塞（除非本地队列满）

重点结论

UDP 无流量控制 → 高吞吐须应用层 ACK + 滑动窗口/限流。

个人学习总结

UDP 无流控——发送速度超过接收方处理能力 → 接收缓冲满 → 内核直接丢包（无声）。

一句话：TCP 有滑动窗口限速，UDP 没有——应用层必须自己 ACK 限流。

HFT 关联：行情组播用 UDP，接收方跟不上就丢包——靠序号检测+重传请求补偿。

8.14

UDP 中的外出接口的确定

核心主旨

多网卡/多 IP 主机：UDP 源 IP 如何选定？

机制对比

类型 源 IP 决定时机
未 connect + sendto 每次 sendto 时查路由表 → 选外出接口主 IP
已 connect + write connect 时查路由并固定，后续 write 不再选路
bind 指定本地 IP 强制以该 IP 为源（路由不符可能不通）

易错细节

多宿环境下 bind/connect 顺序 与策略路由影响连通性。

个人学习总结

UDP sendto 时源 IP 由内核路由表决定——多网卡机器可能走"错误"接口。

控制方式：bind 指定源 IP，或用 IP_PKTINFO 辅助数据（Ch22）。

一句话：UDP 无连接→内核选路由→源 IP 随路由走；要固定源 IP 就 bind。

8.15

使用 select 的 TCP 和 UDP 回射服务器

Ch 6 select：6.8

架构设计

单主循环同时服务 TCP + UDP（如 DNS 53 端口两协议独立 bind）。

listenfd (TCP) + udpfd (UDP) → 都 FD_SET 进 select

select 返回：
  listenfd 就绪 → accept → fork → TCP 子进程
  udpfd 就绪   → recvfrom → 计算 → sendto（主进程迭代，不 fork）

重点结论

点 说明
同端口不同协议 内核两套独立数据结构，可同端口
select 是胶水 统一事件分发
UDP 仍迭代 避免 fork 开销

个人学习总结

用 select 同时监听 TCP listenfd 和 UDP sockfd——一个服务器同时服务 TCP 和 UDP 客户。

一句话：TCP 和 UDP 端口空间独立——同号端口可同时 bind TCP+UDP。

典型场景：DNS 服务器 53 端口同时跑 TCP（区传送）和 UDP（查询）。

8.16

小结

study.md · 阶段一收束：Ch 1～8

章节核心提炼

1. 极简 vs 极难

  • API：recvfrom/sendto 即可，无握手挥手
  • 须直面：丢失、乱序、截断、无流控、异步 ICMP

2. 异步错误

未 connect UDP 对 ICMP 报错常免疫 → 易死锁在 recvfrom。

3. 高阶：UDP connect

单播优先 connect：

  • 简化 read/write
  • 过滤非法源（8.8）
  • 传递异步错误（8.9）

4. 工程清单

必做 手段
超时 select / SO_RCVTIMEO / alarm
验源 比对地址或 connect
可靠 应用层 ACK 重传
高负载 注意 RCVBUF、应用限流

TCP vs UDP 编程对照（阶段一）

TCP UDP
服务器 listen+accept(+fork) bind+recvfrom 循环
客户 connect sendto 或 connect
边界 字节流+readn 整报文
关闭 FIN/RST 无连接；0 字节≠EOF

💡 后续拓展留白
- 阶段二 Ch9 SCTP

个人学习总结

UDP 服务器比 TCP 简单（无连接管理）但问题更多：丢包、验源、异步错误、无流控。

解法清单：超时（alarm/select/SO_RCVTIMEO）、验源（比较地址/UDP connect）、异步错误（connect）、流控（应用层 ACK）。

HFT 关联：UDP 低延迟无连接开销，适合行情分发；但可靠性全靠应用层补。
