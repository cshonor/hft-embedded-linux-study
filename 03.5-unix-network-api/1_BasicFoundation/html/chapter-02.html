2.1

概述

下一节：2.2 总图 · UDP：2.3 · TCP：2.4

核心知识点

本章是网络编程的传输层基石：TCP、UDP、SCTP。须理解连接建立/终止、状态转换、缓冲机制，才能写出健壮的客户/服务器程序。

协议 定位
UDP 简单、不可靠的数据报
TCP 复杂、可靠的字节流
SCTP 消息边界 + 多宿 + 多流（减轻头端阻塞）

三者均建立在网络层 IPv4 / IPv6 之上。

2.3

用户数据报协议（UDP）

对比 TCP 字节流：2.4 · 服务器示例：Ch 8

核心知识点

无连接、不可靠的数据报服务：加端口号交给 IP，不保证到达。

关键特性

特性 说明
保留记录边界 发 2000 字节数据报 → 一次 recvfrom 收 2000 字节（若未丢）；无 TCP 粘包
无可靠性 不保证到达、顺序、唯一（可丢、乱序、重复）
应用层补偿 需可靠时须在应用层自实现 ACK、超时、重传

易错点与坑点

UDP 无内置流量控制：发送远快于接收 → 接收缓冲区溢出 → 数据报静默丢弃。

个人学习总结

💡 WebRTC、高频交易/游戏中 UDP 的现代用法。

2.4

传输控制协议（TCP）

握手/挥手：2.6 · 对比 UDP：2.3

核心知识点

面向连接、可靠、全双工字节流 — 互联网最核心的传输协议。

关键机制

机制 要点
面向连接 传数据前须建立 TCP 连接
确认与重传 发数据启定时器等 ACK；超时未 ACK 则重传
RTT 估算 动态估算往返时间，自适应重传超时
排序 / 去重 每字节有序列号；乱序重排、重复丢弃
流量控制 通告窗口 = 接收缓冲剩余；窗口 0 时发送端阻塞
无记录边界 应用写入块大小 ≠ 网络分节大小 → 拆包/粘包

易错点与坑点

「可靠」≠ 对端一定收到：TCP 尽最大努力递送；实在无法递送则放弃重传并可靠地通知应用（返回错误）。

个人学习总结

💡 与 read/write 循环读写的直接关联见 Ch 1.2。

2.5

流控制传输协议（SCTP）

关联建立/终止：2.8 · 套接字 API：Ch 9

核心知识点

较新的传输协议，弥补 TCP 在信令等场景的不足：面向消息的可靠传输。

关键特性

特性 说明
面向消息 TCP 可靠性 + UDP 式消息边界
关联（Association） 不叫「连接」而叫关联
多宿（Multihoming） 两端可各有多 IP；主路径故障时透明切换备用路径
多流（Multi-streaming） 一关联内多逻辑流；流内有序、流间不互相头端阻塞

个人学习总结

💡 独立网页资源、信令传输中多流的优势。

2.6

TCP 连接的建立和终止

2.7 TIME_WAIT · Ch 4.3 connect

核心主旨与关键论据

三次握手建立、四次挥手终止、11 种 TCP 状态 — 排查故障与理解 connect/accept/close 的理论核心。netstat 输出与状态图严格对应。

2.6.1 三次握手（Three-Way Handshake）

步 发送方 报文 说明
1 客户 SYN，ISN=J connect 触发
2 服务器 SYN+ACK，ACK J+1，ISN=K listen/accept 路径
3 客户 ACK K+1 进入 ESTABLISHED

2.6.2 常见 TCP 选项（SYN 中）

选项 作用
MSS 通告本端可收最大分节，避免 IP 分片
Window Scale 突破 65535 窗口上限（高 BDP）
Timestamp 精确 RTT；PAWS 防序列号回绕

2.6.3 四次挥手（Four-Way Teardown）

  1. 主动方 FIN（常 close）
  2. 被动方 ACK → 半关闭，应用 read 得 0
  3. 被动方 FIN
  4. 主动方 ACK → 主动方常进 TIME_WAIT

2.6.4 状态转换图（11 种）

CLOSED · LISTEN · SYN_SENT · SYN_RCVD · ESTABLISHED · FIN_WAIT_1/2 · CLOSE_WAIT · CLOSING · TIME_WAIT 等。

同时打开（双方 SYN）、同时关闭（双方 FIN）→ 特殊分支如 CLOSING。

💡 后续拓展留白
- Wireshark 抓 3+4 报文字段

个人学习总结

三次握手（SYN→SYN+ACK→ACK）建连，四次挥手（FIN→ACK→FIN→ACK）终止。11 种 TCP 状态与 netstat 输出严格对应。

必背：connect 触发 SYN，accept 从已完成队列取连接，close 触发 FIN。

HFT 关联：理解握手时延是为什么要用长连接——每次新建 TCP 连接至少 1.5 RTT（握手）+ 数据，微秒级场景不可接受。

2.7

TIME_WAIT 状态

SO_REUSEADDR：Ch 7

核心主旨

主动关闭方发完最后 ACK 后，须在 TIME_WAIT 停留 2MSL（常 1～4 分钟）。

存在两个理由

# 理由
1 最后 ACK 若丢失，对端重传 FIN；主动方仍在 TIME_WAIT 可重传 ACK；否则只能 RST
2 防止旧连接迷途分节进入同四元组新连接；2MSL 内旧报文应已消亡

易错细节

EADDRINUSE：TIME_WAIT 占用本地端口 → 服务器立即重启 bind 失败 → SO_REUSEADDR。

个人学习总结

TIME_WAIT 只出现在主动关闭方，持续 2MSL（通常 1~4 分钟）。两个理由：①重传末 ACK ②防旧分节进入新连接。

一句话：服务器重启 bind 失败 → SO_REUSEADDR 解决 TIME_WAIT 占端口。

HFT 关联：高频策略重连时频繁遇到 EADDRINUSE，生产代码必设 SO_REUSEADDR。

2.8

SCTP 关联的建立和终止

协议特性：2.5 · 对比 TCP 握手：2.6

核心知识点

SCTP 面向连接，但握手/终止在抗攻击与状态管理上与 TCP 不同。

执行流程原理

2.8.1 四路握手（Four-Way Handshake）

步 消息
1 客户 INIT
2 服务器 INIT ACK（含 状态 cookie，不分配内存）
3 客户 COOKIE ECHO（回射 cookie）
4 服务器验证后 COOKIE ACK，关联建立

防 SYN 泛洪：第 2 步服务器不建内部状态；状态加密签名在 cookie 中；第 3 步合法回传后才分配资源。

2.8.2 关联终止

  • 三消息：SHUTDOWN → SHUTDOWN ACK → SHUTDOWN COMPLETE
  • 不支持半关闭；一端关闭则关联整体消亡
  • 无 TIME_WAIT；用验证标签区分旧分节

2.9

端口号

并发分路：2.10

核心知识点

传输层用 16 位端口号区分同机不同应用进程。

IANA 三段划分

范围 名称 说明
0～1023 众所周知端口 HTTP 80、FTP 21 等；Unix 绑定常需 root（保留端口）
1024～49151 已登记端口 非系统级应用
49152～65535 动态/私用端口 临时端口（ephemeral）；客户端常由内核随机分配

套接字对（Socket Pair）

  • TCP 连接由 4 元组唯一确定：{本地 IP, 本地端口, 远端 IP, 远端端口}
  • 每端 (IP, 端口) 称为一个 套接字（socket）

2.10

TCP 端口号与并发服务器

端口分类：2.9 · 监听/已连接套接字：Ch 1.5 / Ch 4

核心知识点

并发服务器如何把到达的分节分到正确的进程/套接字？

执行流程原理

1. 服务器在知名端口（如 21）创建监听套接字
2. 客户1 (IP1:1500) 连接 → 三次握手 → fork → 已连接套接字绑定客户1 四元组
3. 客户2 (IP2:1501) 同样连到 :21
4. 分路：TCP 查 源IP、源端口、目的IP、目的端口
   - 精确匹配某已连接套接字 → 送入该套接字
   - 否则若目的端口为 21 且 LISTEN → 送入监听套接字排队

易错点与坑点

不能仅凭目的端口（如 21）分路 — 必须依赖完整 四元组 做上下文路由。

2.11

缓冲区大小及限制

MSS 选项：2.6 · 套接字缓冲选项：Ch 7

核心知识点

数据经应用 → 传输层缓冲 → 网络层 → 链路层，各层有大小限制。

关键定义

术语 说明
MTU 链路层单帧载荷上限；以太网常 1500 字节
路径 MTU 路径上最小 MTU（可不对称）
IP 分片 报文超 MTU 时 IP 切片
DF 位 禁止分片；超 MTU 则丢弃并 ICMP「fragmentation needed」→ 路径 MTU 发现
MSS TCP 通告单分节最大数据量

常见 MSS（IPv4/以太网）

MSS = 1500 - 20(IP) - 20(TCP) = 1460 字节

输出路径差异

协议 write 行为
TCP 拷贝到 SO_SNDBUF；满则阻塞；按 MSS 切块发送；收到 ACK 才释放已发数据
UDP 无真发送缓冲，仅上限；加 UDP 头交 IP；IP 接受则 write 立即返回（后续可能丢）

个人学习总结

💡 Linux tcp_wmem / tcp_rmem 与 TCP 自动调窗。

2.12

标准因特网服务

2.9 端口号·知名端口需 root · 1.2 客户 · 1.5 服

核心知识点

多数 Unix 由 inetd（超级守护进程）托管的简单诊断服务：

服务 端口 行为
echo 7 原样回写
discard 9 丢弃所有数据（/dev/null）
daytime 13 人类可读时间字符串（RFC 865，TCP/UDP）
chargen 19 持续发字符流（测吞吐）
time 37 自 1900 年起秒数（32 位二进制）

Daytime（13）：客户端连 IP:13，服务端 bind :13；13 为知名端口（<1024，绑定常需 root）。

易错点与坑点

项 说明
系统服务 现代 Linux 常默认关闭 自带 daytime；用 1.5 自写服务端 测
改端口 可改 10013 等便于普通用户 bind，但非标准 Daytime 端口，须客户端/服务端同改
安全 公网暴露 7/13/19 等易被滥用，生产一般关闭

个人学习总结

背：13=Daytime(RFC865)；7 Echo；19 Chargen；与 1.2/1.5 代码 htons(13) 一致。

2.14

小结

核心知识点

本章为套接字编程打下协议基础。

关键结论

主题 要点
TCP vs UDP 字节流 vs 数据报边界 → 直接影响 read/write 设计
TCP 状态机 三次握手、四次挥手、TIME_WAIT → 端口占用、高并发卡顿的钥匙
SCTP 多宿、多流 → 特定容错场景优于 TCP
MTU/MSS/缓冲 高性能、少分片编码的前提
