6.1

概述

上一章：Ch 5 · 下一节：6.2 I/O 模型

核心主旨与背景引入

本章直接回应 Ch 5 的致命缺陷：客户端既要等标准输入（键盘），又要等网络套接字时，若用阻塞 I/O 堵在其中一个源上（如 fgets 阻塞 stdin），就无法及时感知另一源事件（如服务器崩溃、对端 FIN）。

解决办法：I/O 多路复用（I/O Multiplexing） — 内核在多个 I/O 事件上等待，任一或多个就绪再唤醒进程。

核心机制

项 说明
核心 API select、poll（及 POSIX pselect）
本质 进程阻塞在 select/poll，而非阻塞在真正的 read/accept（就绪后再调用）

典型适用场景（5 类）

  1. 客户：多描述符 — stdin + sockfd（最常见）
  2. 客户：多个套接字（如 Web 客户端并发，较少见）
  3. TCP 服务器：listenfd + 多个 connfd
  4. 服务器：TCP + UDP 同时处理
  5. 服务器：多服务 / 多协议

逻辑脉络

Ch5 str_cli 只阻塞 fgets → 感知不到 FIN
→ Ch6 select 同时监听 stdin 与 sockfd
→ 6.5 批量输入暴露新问题 → 6.6 shutdown 半关闭
→ 6.7 终极 str_cli；6.8/6.11 单进程多路复用服务器

易错细节与重点结论

易混 纠正
多路复用 = 异步 I/O？ 本书口径下 select/poll 仍属同步 I/O（见 6.2）
用了 select 就高并发？ 单进程 + 阻塞 read 仍有 DoS 风险（6.8）

💡 后续拓展留白
- Linux epoll、BSD kqueue、Windows IOCP 对比表

个人学习总结

Ch5 暴露的问题：阻塞 I/O 无法同时监听多个 fd——str_cli 在 fgets 时不能感知 socket 数据。

一句话：select/poll 让一个线程同时监控多个 fd 的就绪状态——I/O 多路复用。

HFT 关联：epoll 是 Linux 高并发基石，但 API 模型源自 select/poll。

6.2

I/O 模型

6.3 select · 非阻塞：Ch 16

核心主旨与阶段划分

理解多路复用前，须厘清 Unix 5 种 I/O 模型。网络输入含两阶段：

阶段 含义
1 等待数据准备好 — 报文进内核接收缓冲区
2 内核 → 用户空间复制 — read/recvfrom 等

五种 I/O 模型详细拆解

6.2.1 阻塞式 I/O（Blocking I/O）

  • 最常见：recvfrom 直到数据就绪并复制到用户缓冲（或出错）才返回
  • 两阶段进程均阻塞

6.2.2 非阻塞式 I/O（Nonblocking I/O）

  • 套接字设非阻塞；不能立即完成 → 立即返回 EWOULDBLOCK
  • 应用须轮询 — 浪费 CPU，特殊场景用（Ch 16）

6.2.3 I/O 复用（Multiplexing）

  • 进程阻塞在 select/poll，而非 recvfrom
  • 就绪后再 recvfrom
  • 优势：一次 select 等多个描述符

6.2.4 信号驱动 I/O

  • 开启信号驱动；数据就绪（阶段 1）→ 内核发 SIGIO
  • 阶段 1 不阻塞主循环；在信号处理函数里 recvfrom（Ch 25）

6.2.5 异步 I/O（AIO）

  • 如 aio_read（POSIX）
  • 内核在整个操作（含阶段 2）完成后通知进程
对比 信号驱动 异步 I/O
通知含义 「可以开始」读 「已经完成」

6.2.6 & 6.2.7 同步 vs 异步（严格口径）

分类 包含模型
同步 I/O 阻塞、非阻塞、I/O 复用、信号驱动 — 因 recvfrom 复制时仍阻塞
异步 I/O AIO — 两阶段都不阻塞请求进程

考试一句：select + read = 同步；不是「异步网络编程」的 async/await 那种语义。

易错细节与重点结论

易混 纠正
select 两个 syscall 更慢？ 换来多 fd 一份等待，整体模型更对
非阻塞 = 多路复用？ 不同；可组合（6.8 + Ch16）

💡 后续拓展留白
- 五模型对照图（纵轴：阻塞点）

个人学习总结

五种 I/O 模型：阻塞 I/O、非阻塞 I/O、I/O 多路复用（select/poll）、信号驱动 I/O（SIGIO）、异步 I/O（aio）。

一句话：前四种都是"就绪后同步读写"，只有 aio 是"完成后通知"。

Linux 主流 = epoll（多路复用增强）；DPDK = 轮询（第六种，绕过内核）。

6.3

select 函数

6.4 str_cli 修订 · poll：6.10

核心主旨与关键定义

select：进程指示内核等待多个事件之一发生，在事件发生或超时后唤醒。

int select(int maxfdp1, fd_set *readset, fd_set *writeset,
           fd_set *exceptset, const struct timeval *timeout);
返回值 含义
> 0 就绪描述符数目
0 超时
-1 出错

参数解析

1. timeout

取值 行为
NULL 永远等，直到有就绪
正时间 最多等该时长
{0,0} 轮询，立即返回

2. fd_set 与四个宏

宏 作用
FD_ZERO(&fdset) 清空位图
FD_SET(fd, &fdset) 加入待测 fd
FD_CLR(fd, &fdset) 移出
FD_ISSET(fd, &fdset) 测试是否就绪（返回后由内核置位）

readset / writeset / exceptset：测读、写、异常。

3. maxfdp1

  • 最大 fd 编号 + 1
  • 内核只扫描 [0, maxfdp1)，降低开销

6.3.1 描述符就绪条件（排查 Bug 核心）

读就绪（满足其一）

  1. 接收缓冲字节 ≥ SO_RCVLOWAT（TCP/UDP 默认 1）→ read 不阻塞
  2. 读半关闭（收到 FIN）→ read 不阻塞，立即返回 0（EOF）
  3. 监听套接字且已完成连接队列非空 → accept 不阻塞
  4. 套接字错误待处理 → read 返回 -1 + errno

写就绪（满足其一）

  1. 发送缓冲可用空间 ≥ SO_SNDLOWAT（TCP 常 2048）且已连接（UDP 可无连接）
  2. 写半关闭 → 再写可能 SIGPIPE
  3. 非阻塞 connect 成功或已失败
  4. 套接字错误待处理 → write -1

异常就绪

  • 带外数据 OOB 或带外标记

6.3.2 select 的最大描述符数

  • 受 FD_SETSIZE 限制（常 1024，编译期静态位图）
  • 超 1024 并发 → 需 poll / epoll

易错细节与重点结论

陷阱 说明
每次循环忘记 FD_ZERO + 重新 FD_SET select 覆盖 fd_set，必须重建
FIN 到达即读就绪 不 read 会反复唤醒 select
maxfdp1 传错 漏测高编号 fd

💡 后续拓展留白
- SO_RCVLOWAT/SO_SNDLOWAT 调优

个人学习总结

select(maxfd+1, &rset, &wset, &eset, &timeout) — 监听三类 fd 集合，返回就绪数。

三步：FD_ZERO/FD_SET 设置 → select 阻塞 → FD_ISSET 检查。

缺陷：①fd_set 是位图，上限 FD_SETSIZE(1024) ②每次调用要全量传+全量扫 ③参数都是值-结果。

HFT 关联：select 的 O(N) 扫描在高并发下性能差，epoll 用红黑树+就绪列表解决。

6.4

str_cli 函数（修订版）

Ch 5 缺陷：5.5 · 批量输入：6.5

核心主旨与逻辑重构

用 select 重写客户主循环，同时监听 stdin 与 sockfd，解决 Ch 5「阻塞 fgets 不知网络断」问题。

执行流程原理

FD_ZERO(&rset)
FD_SET(sockfd, &rset)
FD_SET(fileno(stdin), &rset)    /* 通常 0 */

for (;;) {
    rset_save = rset
    nready = select(maxfd+1, &rset_save, NULL, NULL, NULL)

    if (FD_ISSET(sockfd, &rset_save)) {
        /* 网络可读：回射或 FIN */
        if (readline(...) == 0) exit;  /* 服务器 FIN */
        fputs(...)
    }

    if (FD_ISSET(fileno(stdin), &rset_save)) {
        if (fgets(...) == NULL) break; /* 键盘 EOF — 6.5 会暴露问题 */
        writen(sockfd, ...)
    }
}

重点结论

Ch 5 Ch 6.4
只阻塞 fgets select 任一就绪即处理
服务器 FIN 时可能仍在等键盘 FIN 使 sockfd 读就绪 → 立刻 readline=0 退出

已解决：远端进程异常 / 正常 FIN 的及时感知（在交互式键盘场景下）。

易错细节

  • 仍用 fgets/readline + select：stdio 缓冲与 select 混用有风险（6.7 改 read/write）
  • rset 必须用 rset_save 副本 — select 修改传入集合

💡 后续拓展留白
- 完整源码与 maxfd 计算

个人学习总结

select 版 str_cli：把 stdin(fd 0) 和 sockfd 都加入 readset → select 返回后 FD_ISSET 检查谁就绪。

改进：不再被 fgets 阻塞——socket 有数据时立即处理。

遗留：逐行 writen 仍不够高效 → 6.5 批量输入。

6.5

批量输入

6.6 shutdown · 6.4 select 版 str_cli

核心主旨与案例数据

6.4 在人敲键盘时完美；若输入重定向为文件（client < input.txt）批量输入，会暴露严重逻辑缺陷。

问题重现

现象 原因
fgets 极快读到 stdin EOF 文件读完
str_cli 立刻 return → exit 整个进程退出
在途数据丢失 已 writen 的请求 + 服务器回射仍在网络/服务器缓冲；客户端 close 掐断连接，回射被丢弃

核心诉求

stdin 遇到 EOF 时不能直接关掉整个 TCP 连接，需告诉对端：

「我发完了，但我还能继续收你的数据。」

→ 需要 半关闭写方向（shutdown(SHUT_WR)），见 6.6、6.7。

逻辑脉络

交互式：EOF = 用户不想聊了 → exit 合理
批量式：EOF = 输入文件结束 ≠ 不再接收回射
→ 须 shutdown 写半部 + 继续 select 读 sockfd

易错细节与重点结论

易混 纠正
stdin EOF 就 exit 批量场景应 shutdown 写，继续读
以为 writen 完就收到回射 TCP 有 RTT 与管道延迟

💡 后续拓展留白
- 实验：time client < big.txt 丢包率观察

个人学习总结

批量输入优化：用缓冲区积累 stdin 数据，select 就绪时一次 writen 发送多行。

问题：缓冲管理复杂——to 缓冲（stdin→socket）和 fr 缓冲（socket→stdout）。

这是从"逐行"到"缓冲驱动"的过渡，Ch16 非阻塞 I/O 的前奏。

6.6

shutdown 函数

6.7 终极 str_cli · close：Ch 4.9

核心主旨与对比分析

常规终止用 close，无法满足批量输入的半关闭需求。shutdown 精确切断全双工的一个方向。

int shutdown(int sockfd, int howto);

close 的两大局限

# 局限
1 引用计数 — close 只减计数；fork 后未必真发 FIN
2 全双工 — close 同时关掉读+写两个方向

shutdown 的突破

  • 无视引用计数，直接触发 TCP 终止序列（对指定方向）
  • howto 精确控制：
常量 含义
SHUT_RD (0) 关读半部；丢弃接收缓冲现有数据；后续对端数据被确认后丢弃
SHUT_WR (1) 半关闭写 — 发完发送缓冲 → FIN；不能再 write，仍可 read
SHUT_RDWR (2) 读写全关

批量输入关键：stdin EOF 后调用 Shutdown(sockfd, SHUT_WR) — 只关写，继续收服务器回射。

易错细节与重点结论

易混 纠正
shutdown = close shutdown 不关 fd，只影响连接方向
SHUT_WR 后还能 write？ 再写可能 SIGPIPE（若对端已 RST）
半关闭 = TCP 半关闭状态 应用层主动 SHUT_WR 触发协议层 FIN

💡 后续拓展留白
- FIN_WAIT_1/2 与仍可 read 的状态机图

个人学习总结

shutdown(fd, how) — 半关闭连接。SHUT_WR 停止发送（发 FIN）但继续接收。

与 close 区别：shutdown 不关 fd 不减引用计数，可只关一个方向。

用途：str_cli 终结版中 stdin EOF 后 shutdown(SHUT_WR) 通知对端"我发完了"，但仍可收对端剩余数据。

6.7

str_cli 函数（再修订版）

6.5 批量输入 · 6.6 shutdown

核心主旨

结合 select + shutdown，适应交互输入、批量重定向、服务器早/正常关闭。

核心逻辑

标志位 stdineof

  • 初值 0
  • stdin 真正 EOF（read 返回 0）→ stdineof = 1，不再监听 stdin

处理 stdin EOF（批量关键）

select 显示 stdin 可读 → read(stdin) 得 0
→ stdineof = 1
→ FD_CLR(stdin, &rset)      /* 不再 select stdin */
→ Shutdown(sockfd, SHUT_WR) /* 发 FIN，半关闭写 */
→ 继续循环，只读 sockfd

处理网络 EOF

select 显示 sockfd 可读 → read 得 0
→ 若 stdineof == 1：正常结束，return
→ 若 stdineof == 0：err_quit("server terminated prematurely")

废弃 stdio

  • 不用 fgets/readline — stdio 缓冲与 select 冲突（缓冲里已有数据但 select 不知）
  • 改用 read/write 原始 I/O

逻辑脉络（三种场景）

场景 行为
交互 Ctrl+D shutdown 写 + 收完回射 → 正常退出
< file 发完文件 → shutdown → 收齐回射
服务器先死 select 唤醒 → read=0 且 stdineof=0 → 报错退出

易错细节与重点结论

陷阱 说明
fgets + select 禁止混用（6.7 明确）
stdin EOF 直接 exit 6.5 的错
忘记 FD_CLR(stdin) shutdown 后仍 select stdin 可能忙等

💡 后续拓展留白
- 完整 str_cliselect02.c 对照

个人学习总结

str_cli 终极版：select + to/fr 双缓冲 + shutdown(SHUT_WR)。解决了所有阻塞和边界问题。

一句话：stdin EOF → shutdown 写端（发 FIN）→ 继续读对端剩余 → 对端 FIN → 退出。

这是从"能跑"到"正确"的完整演进——Ch16 非阻塞版是"高效"演进。

6.8

TCP 回射服务器程序（修订版）

fork 并发：Ch 5.2 · poll 版：6.11 · 非阻塞：Ch 16

核心主旨与架构演进

用 单进程 + select 替代 fork，一个进程管理 listenfd + 所有 connfd，避免每连接 fork 开销。

核心数据结构

变量 作用
client[] 长度 FD_SETSIZE，存活跃 connfd，空闲为 -1
maxfd 当前最大 fd 值 → select 的 maxfdp1
maxi client[] 最大使用下标 → 优化遍历

主循环工作流

1. FD_ZERO；FD_SET(listenfd)；对每个 client[i]>=0 → FD_SET
2. select(maxfd+1, &rset, ...) 阻塞
3. listenfd 就绪 → accept → 放入 client[] 第一个 -1 槽 → 更新 maxfd/maxi
4. 遍历 i=0..maxi：
     client[i] 就绪 → read
       n > 0  → writen 回射
       n == 0 → close；client[i]=-1；FD_CLR（下次重建 rset）

易错细节：DoS 与阻塞 read（重点结论）

攻击/缺陷 机制
恶意客户连接后少发数据即停 服务器 read 阻塞在该 connfd
后果 整个进程卡住，其他客户饿死

铁律：单进程 select 服务器中，read/write/accept 必须非阻塞（Ch 16），否则生产不可用。

对比 fork 服务器 select 单进程
慢客户 只阻塞该子进程 阻塞全体
开销 fork 贵 无 fork，但需非阻塞

💡 后续拓展留白
- prefork + epoll 架构草图

个人学习总结

select 版 TCP 服务器：把 listenfd 加入 readset，select 返回后如果是 listenfd 就绪则 accept 新 connfd，否则处理已有连接。

关键：每次循环重建 readset（select 会修改它），跟踪 maxfd。

单进程 select 服务器替代 fork 并发——无进程切换开销，适合短连接。

6.9

pselect 函数

6.3 select

核心主旨

POSIX 在 select 上演进为 pselect，解决超时精度与信号竞争。

int pselect(int maxfdp1, fd_set *readset, fd_set *writeset, fd_set *exceptset,
            const struct timespec *timeout, const sigset_t *sigmask);

核心差别

# 改进
1 超时用 timespec — 纳秒精度（select 用 timeval 微秒）
2 sigmask 参数 — 阻塞期间原子地替换信号掩码，返回后恢复

sigmask 解决什么问题

在「检查条件」与「调用 select 阻塞」之间的缝隙，若信号到达且处理函数也改 fd 状态 → 竞态。pselect 可在等待时屏蔽指定信号，避免丢失/重复逻辑。

易错细节

  • 与 select 一样仍受 FD_SETSIZE 限制（位图模型未变）
  • sigmask == NULL 时行为类似普通 select

💡 后续拓展留白
- 与 sigprocmask + select 手写等价性

个人学习总结

pselect = select + 信号屏蔽。在 select 期间用 sigset 临时屏蔽信号，避免信号与 select 竞态。

与 select 区别：①timeout 用 timespec（纳秒精度）②sigset 参数替代信号屏蔽操作。

pselect 解决"信号设置 flag → select 返回前信号到达 → select 永远阻塞"的竞态。

6.10

poll 函数

6.11 poll 服务器 · select：6.3

核心主旨

System V poll：功能类似 select，接口更现代，规避位图与 1024 硬上限。

int poll(struct pollfd *fdarray, unsigned long nfds, int timeout);

struct pollfd {
    int   fd;       /* 待检查描述符 */
    short events;   /* 关心的事件（输入） */
    short revents;  /* 实际发生（内核填） */
};
返回值 含义
> 0 就绪数
0 超时
-1 错误

核心事件宏

宏 用途
POLLIN 普通/优先级数据可读
POLLRDNORM 普通数据可读
POLLOUT / POLLWRNORM 可写
POLLERR 错误
POLLHUP 挂起 / 半关闭
POLLNVAL fd 无效

与 select 的三大优势

# poll select
1 无 FD_SETSIZE 天花板（数组大小由 nfds 决定） 常限 1024
2 events / revents 分离 — 不必每轮重建整个位图 返回覆盖 fd_set
3 fd == -1 自动忽略 — 踢掉连接只需置 -1 须 FD_CLR + 维护 maxfd

易错细节与重点结论

  • timeout：毫秒；-1 永久等
  • revents 须与 POLLERR | POLLHUP 等一起处理错误断开
  • 仍可能 O(nfds) 扫描 — 高并发用 epoll

- poll vs epoll 触发模式（LT/ET）

个人学习总结

poll(fds, nfds, timeout) — 用 struct pollfd 数组替代 fd_set 位图，无 FD_SETSIZE 上限。

优势：①无 1024 上限 ②分开监听 events/revents ③timeout 毫秒精度。

仍有的缺陷：每次调用全量传+全量扫——O(N) 不变。

poll 比 select 好用但不更快——epoll 才解决 O(N) → O(1)。

TCP 回射服务器程序（再修订版）

6.8 select 服务器 · 6.10 poll

核心主旨

将 6.8 的 select 单进程服务器 改写为 poll，体验更清晰的数组管理与无 1024 限制。

架构要点

项 做法
数组 struct pollfd client[OPEN_MAX] 替代 client[] + fd_set
监听槽 client[0].fd = listenfd，events = POLLRDNORM
空闲槽 fd = -1（poll 自动忽略）

工作流

1. poll(client, nfds, -1) 阻塞
2. client[0].revents & POLLRDNORM → accept → 填入第一个 fd==-1 的槽
3. 遍历 i>=1：
     revents & (POLLRDNORM | POLLERR) → read
       n>0  → writen
       n==0 → close；client[i].fd = -1

与 select 版对比

操作 select 版 poll 版
踢连接 close + client[i]=-1 + 下次 FD_ZERO/SET fd=-1 即可
监听 listen 每次 FD_SET(listenfd) client[0] 固定

易错细节

  • 与 6.8 相同：阻塞 read → DoS 挂死全进程 → 须 非阻塞（Ch 16）
  • nfds 应覆盖实际使用的最大下标+1

💡 后续拓展留白
- OPEN_MAX 与资源 limit

个人学习总结

poll 版服务器：用 pollfd 数组替代 select 的 fd_set，动态扩容无上限。

与 select 版区别：①无需 FD_SETSIZE 限制 ②无需每次重设（revents 是输出）③仍需线性扫描。

工程实践：小规模用 select/poll 足够，大规模（>1000 连接）必须 epoll。

核心主旨与章节提炼

1. I/O 复用的地位

需同时应对多数据源（stdin + socket、listen + 多 conn、TCP + UDP）时，select / poll 是最通用的中间层机制（本书范围内）。

API 特点
select 兼容性最强；FD_SETSIZE、每轮重建 fd_set
