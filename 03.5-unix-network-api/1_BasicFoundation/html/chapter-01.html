核心主旨与关键论据

网络应用由 客户（client） 与 服务器（server） 通过 协议（protocol） 通信。以 TCP/IP 说明 LAN/WAN 互连；应用层逻辑端到端，物理上经协议栈与介质到达对端。

核心知识点

概念 说明
C/S 模型 客户主动请求，服务器被动响应
TCP/IP TCP 可靠字节流 + IP 路由
LAN 同网通信通常无需路由器
WAN 跨网经路由器；最大 WAN = Internet（因特网）
逻辑 vs 物理 应用层端到端；实际经本地栈→介质→对端栈

易错细节

易混 纠正
Internet vs internet 专有全球网 vs 任意 TCP/IP 网络（普通名词）
HTTP vs TCP/IP HTTP 应用层；传输用 TCP，网络用 IP
C/S vs B/S C/S 要装专用客户端；B/S 用浏览器，走 HTTP/HTTPS

C/S → B/S 演进（与 UNP 套接字、HTTP 对齐）

UNP 全书在 C/S 模型 上教 socket API（1.2 客户、1.5 服务器 即经典 三层 C/S 里的客户机 ↔ 应用服务器）。下面把部署形态从老两层 C/S 讲到 B/S，便于和自顶向下 HTTP 章打通。

人话定义

你要装啥 例子
C/S 专用客户端 QQ、迅雷、老财务软件；UNP 时间客户端
B/S 浏览器 淘宝网页、网课；底层仍是 TCP + HTTP

演进时间线（必背）

① 两层 C/S     客户机 ──────────────► 数据库（DBMS）
② 三层 C/S     客户机 ──► 应用服务器 ──► 数据库   ← UNP 时间服务属此类
③ B/S          浏览器 ──► Web服务器 ──► 应用服务器 ──► 数据库

两层 C/S 结构图（胖客户端直连库）

  • 界面、业务逻辑、连库都在客户机；服务器侧主要是 DBMS。
  • 问题：逐台装客户端升级难；客户端握库账号 → 安全/并发差。

三层 C/S（UNP 起点）

客户机 ── TCP/socket ──► 应用服务器（如 daytime 守护进程）──► （可选）数据库
  • 1.2 socket + connect + read = 客户；1.5 bind + listen + accept = 服。
  • 协议常是 自定义 TCP 端口（如 13 号 daytime），不是 HTTP。

B/S 结构图（浏览器换客户端）

  • 浏览器极瘦；业务在服务器；应用层统一 HTTP/HTTPS。
  • 下面仍是 TCP → IP → 链路层（与 UNP 第 2～3 章、自顶向下一致）。

一句话对比

C/S（含 UNP 示例） B/S
安装/升级 要装/编译客户端 有浏览器即可
协议 私有或简单文本 over TCP HTTP/HTTPS
本书 全书 socket C/S 对照 §2.2 HTTP

两层直连库 → 三层加应用服（UNP socket）→ B/S 换浏览器走 HTTP。C/S 要装软件；B/S 好维护。

网络编程的核心模型就是 C/S：客户主动请求，服务器被动响应。UNP 全书都在这个模型上教 socket API。

一、五步法（第 2 步：IP 和端口分开看）

# 步骤 做什么
1 socket 创建 TCP/IPv4 套接字 → 得到 sockfd
2 填服务器地址 往 sockaddr_in servaddr 里写 IP + 端口（见下表）
3 connect 把地址交给内核 → 三次握手
4 while (read…) 循环读 TCP 字节流（可能分多次）
5 exit / close 关连接（发 FIN）

第 2 步必记：哪个是 IP？哪个是端口？

二、API 速查

socket() 三个参数（1.2 只用 IPv4，没写 IPv6）

sockfd = socket(AF_INET, SOCK_STREAM, 0);
参数 1.2 取值 什么意思
① 地址族 AF_INET 用 IPv4 地址（点分如 192.168.0.1）。告诉内核：后面 sockaddr_in / inet_pton 都按 4 字节 IPv4 来，不是 IPv6。
② 套接字类型 SOCK_STREAM 字节流、可靠、有序 → 就是 TCP。
③ 协议 0 默认：前面已选 TCP 流式时，由系统选 TCP 协议（一般不必手写 IPPROTO_TCP）。

什么叫「IPv4 地址族」？

  • 族（family） = 用哪一套地址格式。
  • AF_INET = Address Family, Internet = IPv4 那一套（32 位 IP）。
  • 你没写 IPv6，所以这里不是 AF_INET6；1.3 才会出现 IPv6 / 协议无关。

返回值 sockfd：

返回值 含义
≥ 0 成功，得到一个整数 套接字描述符（像"网络连接的句柄"），后面 connect / read 都用它
< 0 失败，查 errno（如资源不够）；不能拿这个 fd 去 connect
API 一句话 展开
connect(…) 交内核三次握手；失败须 close 再 socket 见下方折叠 API 精读
read / while TCP 无边界；n==0 为 FIN 见下方折叠 API 精读 
struct sockaddr_in {
    sin_family;   /* AF_INET */
    sin_port;     /* 端口 ← htons(13) */
    sin_addr;     /* IP   ← inet_pton(..., argv[1], ...) */
    sin_zero[8];  /* 填 0 */
};

附录 · API 精读（connect / read / 内核表）

connect() — 把「去哪台:哪个端口」交给内核

connect(sockfd, (SA *) &servaddr, sizeof(servaddr));
项 说明
sockfd socket() 成功返回的描述符
(SA *) &servaddr SA = #define SA struct sockaddr；把 sockaddr_in* 转成通用地址指针（BSD 惯例，以后 IPv6 / 别的族也用同一套 API 形状）
sizeof(servaddr) 必须传真实结构体大小，让内核知道是 IPv4 的 sockaddr_in
内核行为 读 servaddr 里的 目的 IP + 目的端口 → 路由 → 发 TCP SYN（三次握手）
返回值 < 0 失败；禁止对同一个 sockfd 再 connect
失败后正确做法 close(sockfd) → 重新 socket() → 再填地址 → 再 connect

read() 循环 — TCP 没有「一次读一包」

while ((n = read(sockfd, recvline, MAXLINE)) > 0) {
    recvline[n] = 0;
    fputs(recvline, stdout);
}
if (n < 0) err_sys("read error");
read 返回值 含义
> 0 本次读到的字节数 n（可能小于 MAXLINE）
== 0 对端 关闭写方向（常见：收到 FIN），数据流结束 → 正常退出循环
< 0 出错（查 errno；信号中断 EINTR 见 Ch 3.9）

为何必须 while？ TCP 是字节流，内核接收缓冲区没有应用层报文边界。Daytime 一次发 26 字节，你的进程可能被分成 10 + 16 两次 read 才拿全。

recvline[n] = 0：read 只写二进制，不带 '\0'；加 NUL 后 fputs 才能当 C 字符串打印（协议本身不需要 \0）。

应用层 ↔ 内核（一张表）

你调用的 API 内核 / 协议在干什么
socket 创建套接字，分配 fd
填 servaddr 仅在进程内存；须已是正确 IP + 端口（网络序）
connect 三次握手，建立连接控制块
read 从该连接的 TCP 接收缓冲区 拷贝到用户缓冲区
exit / close 关闭 fd，通常发 FIN，四次挥手

13 端口：IANA 标准 Daytime 服务，返回人类可读时间字符串（明文 TCP）。

附录 · C 新手与网络字节序

C 零基础 FAQ

argc != 2 是什么意思？

命令 argc
./daytimetcpcli 1 ❌ 没 IP
./daytimetcpcli 127.0.0.1 2 ✅
./daytimetcpcli 1.1.1.1 x 3 ❌ 参数太多
  • argc：参数个数；argv[0] 程序名，argv[1] 本程序的 IP 字符串。
  • 代码 if (argc != 2)：不是「不能等于 2」，而是 「不等于 2 就报错」。

bzero 是什么？

bzero(&servaddr, sizeof(servaddr));

把 servaddr 整块清零。未赋值成员若是随机值，connect 可能异常。 等价 memset(&servaddr, 0, sizeof(servaddr))；BSD/POSIX 提供，UNP 老代码常用。

inet_pton 三个参数

inet_pton(AF_INET, argv[1], &servaddr.sin_addr);
参数 作用
AF_INET 按 IPv4 解析
argv[1] 输入："192.168.0.1" 这种人看的字符串
&sin_addr 输出：4 字节二进制（已是网络序）

「转成二进制网络序」= 变成协议栈用的 C0 A8 00 01，不是再打印字符串。<=0 表示 IP 格式非法。

网络字节序（深化）

主机序 vs 网络序

术语 含义
主机字节序 你 CPU 存多字节数的习惯（x86 多为小端）
网络字节序 TCP/IP 规定线上用大端（高位字节在前）

端口为什么要 htons(13)？

端口在 sin_port 里占 2 字节。整数 13 = 0x000D：

存法 两字节 协议读到的端口
✅ htons(13) 网络序 00 0D 13
❌ 小端机直接 sin_port=13 0D 00 3328 等错误值

IP 和 192.168.0.1

形式 和大端的关系
字符串 "192.168.0.1" 给人看的，谈不上字节序
inet_pton 写入 sin_addr 4 字节网络序：C0 A8 00 01（与点分从左到右一致）

勿在 inet_pton 之后再 htonl(sin_addr)。

字节序易错（仅列主笔记未写的）

❌ ✅
以为 192.168.0.1 字符串本身是「大端」 字符串 → pton → 二进制
小端 PC 上端口不转 凡进 sin_port 必 htons

完整源码（书中逻辑）

#include    "unp.h"

int main(int argc, char **argv)
{
    int                 sockfd, n;
    char                recvline[MAXLINE + 1];
    struct sockaddr_in  servaddr;

    if (argc != 2)
        err_quit("usage: a.out <IPaddress>");

    if ((sockfd = socket(AF_INET, SOCK_STREAM, 0)) < 0)
        err_sys("socket error");

    bzero(&servaddr, sizeof(servaddr));
    servaddr.sin_family = AF_INET;
    servaddr.sin_port   = htons(13);
    if (inet_pton(AF_INET, argv[1], &servaddr.sin_addr) <= 0)
        err_quit("inet_pton error for %s", argv[1]);

    if (connect(sockfd, (SA *) &servaddr, sizeof(servaddr)) < 0)
        err_sys("connect error");

    while ((n = read(sockfd, recvline, MAXLINE)) > 0) {
        recvline[n] = 0;
        if (fputs(recvline, stdout) == EOF)
            err_sys("fputs error");
    }
    if (n < 0)
        err_sys("read error");

    exit(0);
}

附录 · 为何固定端口 13（Daytime / RFC 865）

没错：13 是 Daytime 的官方标准端口，TCP（及 UDP）均为 13。

依据 说明
RFC 865 定义 Daytime 服务 → TCP/UDP 端口 13
行为 客户端连上后，服务端返回人类可读的日期+时间字符串，发完常关连接
与 UNP 1.2/1.5 正是书上「时间获取」示例 
客户端：connect  目标 IP : 13
服务端：bind     0.0.0.0 : 13   （INADDR_ANY + htons(13)）

两端必须同一端口；改一端不改另一端会连不上。

2.12 标准因特网服务

关键细节

知名端口 / 特权端口（< 1024）

事实 影响
13 < 1024 Linux 上普通用户默认 不能 bind(13)（需 root 或 CAP_NET_BIND_SERVICE）
书上示例 常假设有权限，或 root 跑服务端

改成非标准端口（如 8888、10013）

项 说明
能否跑通 能 — 服务端 bind 某端口，客户端 connect 同一端口 即可
协议含义 不再是 IANA 标准 Daytime 端口，只是你自己的 TCP 时间服务
改法 C：htons(13) → htons(10013)；Rust："IP:13" → "IP:10013" 两边一起改

现代 Linux 与系统自带 Daytime

多数发行版默认不启系统 daytime（13）服务（安全/无用）。 因此 1.5 自写服务端监听 13 才能和 1.2 客户端 联调；与系统服务冲突时再换端口或停系统服务。

非 root 本地测试：改用 10013（可选）

仓库默认保持 13，与 UNP / RFC 一致。无 root 时可自行改端口：

位置 修改
C 客户端 1.2_daytimetcpcli.c htons(13) → htons(10013)；或 getaddrinfo 服务名 "10013"
C 服务端 1.5_daytimesrv.c htons(13) → htons(10013)
Rust 客户端 format!("{host}:13") → :10013
Rust 服务端 bind("0.0.0.0:13") → 0.0.0.0:10013

速记：RFC865 → 13/TCP → 人读时间串；客户端连 IP:13，服务端 bind :13；<1024 要权限；系统常无 daytime，自写 1.5 测。

层面 说法

{:?} repr(x) → __repr__ 调试用 ≈ Debug

Rust 刻意拆开 Display / Debug；Python 也拆 __str__ / __repr__，所以体感高度相似，但检查时机与约束方式不同。

核心三大区别：

  1. 检查时机：Python 运行时找方法；Rust 编译期检查是否 impl
  2. 约束范围：Python 碰巧有方法就行（鸭子）；Rust 泛型可 T: Trait，入参必须实现
  3. 实现归属：Python 写在类内部；Rust impl Trait for Type 可与类型定义解耦

背：{}→Display（常手写）；{:?}→Debug（常 derive）；Rust 编译查 Trait；Python 运行找魔法方法。

1.4

错误处理：包裹函数

Permalink · 1.4 错误处理：包裹函数
章级：study.md#ch1-4 · 前置裸写：1.2 源码 · 后章 EINTR：Ch 5 · Ch 6

本节要会什么

原生 socket / connect / read 失败返回 -1 并置 errno；裸写要处处 if (fd < 0) err_sys(...)。
UNP 约定：首字母大写 = 包裹函数，内部统一报错退出，业务代码只写一行 Socket(...)。

记法：socket() 小写 = 内核 API；Socket() 大写 = 本书封装。

一、核心主旨

痛点 包裹函数做法
每个系统调用后手写 if (<0) err_sys 大写函数内部做完，调用方只拿合法返回值
报错口径不统一 统一走 err_sys / err_quit / err_ret / err_dump
close 等常被忽略返回值 Close(fd) 强制检查（原书后文习惯）

二、标准包裹模板（图 1-7 · Socket 示例）

int Socket(int family, int type, int protocol)
{
    int fd;
    if ((fd = socket(family, type, protocol)) < 0)
        err_sys("socket error");
    return fd;
}

调用方：

int sockfd = Socket(AF_INET, SOCK_STREAM, 0);
/* 无需再 if (sockfd < 0) */

→ 仓库示例：1.4_wrapper_socket.c（含 Socket / Connect / Accept）

三、errno 三条铁律

# 规则
1 仅当函数返回失败（常 -1）时，errno 才有意义；成功后不要读 errno
2 现代 Linux 上 errno 多为 TLS（每线程一份），多线程不会互相踩
3 下一次失败调用会覆盖旧值 → 出错后立刻读（或在 err_sys 里立刻读）

四、UNP 四大错误输出函数（unp.h）

函数 作用 是否退出
err_sys 系统调用错；拼 errno + strerror exit(1)
err_quit 业务错（如 argc 不对）；不读 errno exit(1)
err_ret 只打印，不退出 返回调用方
err_dump 打印 + 栈回溯 abort()

err_sys 典型实现（教学简化，完整见 libunp）：

void err_sys(const char *msg)
{
    int err = errno;   /* 立刻保存 */
    fprintf(stderr, "%s: %s\n", msg, strerror(err));
    exit(1);
}

→ 示意源码：1.4_err_sys_demo.c

五、两类 API 错误范式（易错）

1. Unix 风格（socket / connect / read / write …）

结果 行为
失败 返回 -1，errno 有值 → 包裹里 err_sys
成功 返回 fd 或字节数 ≥0

2. Pthread 风格（pthread_create 等）— 不走 errno

结果 行为
成功 返回 0
失败 返回 错误码本身（非 0），不设置 errno 
void Pthread_create(pthread_t *tid, const pthread_attr_t *attr,
                    void *(*func)(void *), void *arg)
{
    int n;
    if ((n = pthread_create(tid, attr, func, arg)) != 0)
        err_exit(n, "pthread_create error");  /* 用返回值，不是 errno */
}

（书中常用 err_exit(errno, msg) 一类把 Pthread 返回值 当第一个参数传入。）

六、三大特殊错误（不能一律 exit）

标准大写包裹默认失败就退出；下面三类要自定义小写 + 分支（Ch 5/6 落地）。

errno 场景 处理思路
EINTR 阻塞 accept/read/connect 被信号打断 重试同一调用，不退出
EAGAIN / EWOULDBLOCK 非阻塞 I/O 暂无数据/缓冲区满 稍后重试或交事件循环
ECONNRESET 对端 RST，连接作废 close fd，退出读写循环

七、什么时候不用大写包裹？

需要捕获特定错误、不直接杀进程时，用小写原生 API + 手动判断：

场景 原因
accept 遇 EINTR 重试 Accept() 会直接 exit
忽略 ECONNABORTED 的 accept 要分支，不能一刀 err_sys
非阻塞 + EAGAIN 属正常空转，不是致命错

八、易错汇总

❌ ✅
成功后还判断 errno 只看返回值是否失败
pthread_create 失败读 errno 读返回值 + strerror(ret)
处处裸 if (fd<0) 与 Socket 混用同一 fd 统一风格：业务层优先 大写
所有错误都用 Accept() EINTR 等场景必须小写 + 重试

一、整体流程（服务端六步）

# 步骤 API / 行为
1 创建监听套接字 Socket → listenfd
2 绑定地址端口 Bind：INADDR_ANY + htons(13)
3 被动监听 Listen(listenfd, LISTENQ)
4 等客户连入 Accept 阻塞 → 返回 connfd
5 发时间字符串 time / ctime / snprintf → Write(connfd, …)

迭代：新连接必须等上一客户 close(connfd) 后，下一次 accept 才会处理它（排队）。

二、listenfd vs connfd（核心）

listenfd connfd
创建 Socket 一次 每次 Accept 一个新 fd
用途 只 Accept 新连接 只 本会话的 read/write
生命周期 进程全程不关 处理完该客户就 Close
❌ 禁止 在 listenfd 上 read/write 用 connfd 去 accept

绑定谁？ sin_addr = htonl(INADDR_ANY) → 0.0.0.0，本机所有网卡的 13 端口都可连（不必写死 192.168.x.x）。

附录 · listen 队列（半连接 / 全连接）

被动打开时内核有两类队列

客户端 connect（主动打开）后，服务端在 listen 之后、accept 之前，内核要为每个到来的连接维护状态。常分成：

队列 俗称 里有什么 何时离开
半连接队列 SYN 队列 收到 SYN，三次握手未完成 握手完成 → 移入全连接队列；或超时丢弃
全连接队列 accept 队列 三次握手已完成，等待应用 accept 取走 你的进程 Accept 成功 → 变成 connfd 
客户 SYN ──► [半连接队列] ──握手完成──► [全连接队列] ──accept()──► connfd（应用）

Listen(listenfd, LISTENQ) 里的 backlog 管什么？

要点 说明
LISTENQ（backlog） 应用传给 listen 的第二个参数；历史上各 OS 解释不一，现代 Linux 上主要限制「全连接队列」相关容量（与 somaxconn 等取 min）
半连接队列 长度常由 tcp_max_syn_backlog 等内核参数控制，不是你写 LISTENQ 单独设死的
1.5 迭代服务器的坑 你在 Write + Close 之前不会 accept 下一个 → 全连接队列里可以堆很多已完成握手、但还没被 accept 的连接；队列满 → 新连接可能被拒或丢弃

背一句：LISTENQ ≈ 「已完成握手、等着 accept 的客户」能排多长；半连接另由内核调。

和 1.5 迭代模型的关系

现象 原因
多客户同时连 握手可在内核队列里完成，但应用串行：一次只处理一个 connfd
处理很慢时客户「连不上」 全连接队列满 / 半连接 SYN 洪泛等 → 需 fork / 线程 / epoll（Ch 4/5）
listenfd 不能 read/write 数据路径在 connfd；队列在内核，不靠你在 listenfd 上 I/O

常见内核参数（了解即可）

参数（Linux 示例） 作用
net.core.somaxconn 与 listen backlog 共同 cap 全连接队列
net.ipv4.tcp_max_syn_backlog 半连接（SYN）队列相关上限

C 原版（UNP 标准 · 大写包裹）

#include "unp.h"

int main(int argc, char **argv)
{
    int listenfd, connfd;
    struct sockaddr_in servaddr;
    char buff[MAXLINE];
    time_t ticks;

    listenfd = Socket(AF_INET, SOCK_STREAM, 0);

    bzero(&servaddr, sizeof(servaddr));
    servaddr.sin_family      = AF_INET;
    servaddr.sin_addr.s_addr = htonl(INADDR_ANY); /* 0.0.0.0 全网卡 */
    servaddr.sin_port        = htons(13);

    Bind(listenfd, (SA *)&servaddr, sizeof(servaddr));
    Listen(listenfd, LISTENQ);

    for (;;) {
        connfd = Accept(listenfd, NULL, NULL);

        ticks = time(NULL);
        snprintf(buff, sizeof(buff), "%.24s\r\n", ctime(&ticks));
        Write(connfd, buff, strlen(buff));

        Close(connfd);
    }
}

Permalink · 1.7 OSI & TCP/IP 分层

本节要会什么

OSI 七层 ↔ TCP/IP 四层映射；Socket API 在哪一层；三类套接字能「穿透」到哪一层；收发时的封装 / 解封装。

一、分层映射速记

1. OSI 七层（上 → 下）

7 应用 → 6 表示 → 5 会话 → 4 运输 → 3 网络 → 2 数据链路 → 1 物理

2. TCP/IP 四层（工程实际标准 · 套接字依托此模型）

TCP/IP 涵盖 OSI 典型协议
应用层 7+6+5（应用、表示、会话合并） HTTP、DNS、Daytime(13)、FTP
传输层 4 运输层 TCP、UDP
网际层 3 网络层 IPv4、IPv6、ICMP
链路层（常含物理） 2+1 以太网、ARP

UNP 全书 Socket 编程默认工作在：应用层 ↔ 传输层之间的边界。

二、Socket API 的精准位置（核心）

层级 是什么
应用层（用户态） 你写的 C/Rust（如 1.2 / 1.5）：业务、read/write 的缓冲区
系统调用分界 socket / bind / connect / listen / accept / read / write：用户态 → 内核态的入口
内核协议栈 传输层（TCP/UDP）、网络层（IP 路由）、链路层（ARP、以太网帧）均由内核实现

一句话：应用程序通过 Socket 调用内核里的 TCP/IP 协议栈。

系统调用会带来 用户态↔内核态切换，是开销来源之一 → 后文 I/O 多路复用、零拷贝 的优化动机。

三、三类套接字与穿透层级（Ch28 / Ch29）

类型 示例 你能动到哪一层 说明
常规 SOCK_STREAM / SOCK_DGRAM 1.2/1.5 TCP Daytime 应用数据；头由内核填 内核自动加 TCP/UDP + IP + 链路 头，程序员只见载荷
原始套接字 RAW Ch28 常到 网络层 IP 可自写传输层头或发 ICMP 等；内核主要帮你处理 IP 首部
链路层套接字 Ch29 数据链路层帧 读写以太网帧（MAC + 载荷），抓包、自定义二层 
普通 TCP/UDP socket：应用数据 ──► 内核加 TCP/UDP + IP + 以太网
Raw socket (Ch28)：     应用可带头 ──► 内核加 IP（绕过常规 TCP/UDP 栈路径）
链路 socket (Ch29)：    应用构造帧 ──► 直达二层

四、封装与解封装（以 Daytime 回包为例）

发送（1.5 服务端 Write 时间字符串）

应用层：时间字符串
  → Socket(write)
  → 内核：+ TCP 头（传输层）
  →       + IP 头（网络层）
  →       + 以太网帧头（链路层）
  → 物理比特流

接收（1.2 客户端 read）

物理信号
  → 剥以太网头 → 剥 IP 头 → 剥 TCP 头
  → 净载荷进用户缓冲区（read）

抓包对照：Wireshark 中同一连接可见 Ethernet II → IPv4 → TCP → Data；应用载荷即 Daytime 文本。→ 拓展

五、易错

❌ ✅
以为 read 直接读「网线」 read 读的是内核已解封装后的 TCP 字节流
普通 socket 能改 TCP 序号/IP 地址 要 Raw / 链路 套接字（Ch28/29）
OSI 七层与 TCP/IP 四层一一同名 TCP/IP 合并了 OSI 上三层为应用层

七、个人学习总结

  1. TCP/IP 合并 OSI 上三层为应用层，是工程简化；Socket 隔离业务与内核协议栈。
  2. 常规 TCP/UDP 只在应用–传输边界；改 IP/TCP 头 → Raw（Ch28）；改 MAC 帧 → 链路（Ch29）。
  3. 系统调用 = 进内核，是性能与后续 select/epoll、零拷贝 的出发点。

30 字：OSI 七层；TCP/IP 四层；Socket 在用户态调内核栈；普通 socket 不见包头。

链路：1.2/1.5 普通 TCP → 1.7 分层 → Ch28 Raw → Ch29 链路。

1.10

Unix 标准

核心知识点

套接字 API 的跨平台性由 POSIX、The Open Group（SUS） 与 IETF RFC 共同塑造。

关键组织与规范

标准 要点
POSIX IEEE 可移植 OS 接口；POSIX.1 为核心 API
POSIX.1g（2000） 套接字 API 作为独立协议接口正式标准化
Single UNIX Specification (SUS) X/Open 等定义，后与 POSIX 趋同；现代 Unix 多宣称符合 POSIX.1
IETF TCP/IP 协议设计；标准以 RFC 发布（如 IPv6 套接字 API：RFC 3493、3542）

个人学习总结

💡 常查 RFC：TCP（RFC 793，现多引用 RFC 9293 等更新文档）。

1.11

64 位体系结构

核心知识点

32 位 → 64 位迁移中，数据模型变化影响套接字 API 长度参数类型。

关键定义

模型 int long pointer
ILP32（32 位） 32 32 32
LP64（64 位 Unix） 32 64 64

套接字 API 兼容策略

问题 说明
size_t 与指针同宽，表示内存块长度；64 位下为 64 位
历史 int 长度参数 早期 API 用 int 传长度，64 位下仍为 32 位，语义脱节
socklen_t（POSIX.1g） 专用于套接字地址结构长度；与 int/指针宽度解耦

易错点与坑点

向 bind、accept、recvfrom 等传地址长度时，必须用 socklen_t 变量，勿硬编码 int，否则 64 位下可能出现转换警告或栈破坏。

个人学习总结

💡 可拓展：LLP64（Windows 64 位）与 LP64 在网络编程中的差异。

一、服务器初始化与等待（图 1-9）

服务器先于客户端启动，并一直运行。

步骤 API / 行为
创建套接字 Socket → 得到 listenfd（监听套接字）
填地址 INADDR_ANY（0.0.0.0） + htons(13) → 接受本机任意网卡上发往 13 端口的连接
绑定 Bind(listenfd, …)
监听 Listen(listenfd, LISTENQ) → 普通套接字变为监听套接字，内核可为外来连接排队
等待 for (;;) 中 Accept 阻塞睡眠，直到有客户完成握手

listenfd 只用于 accept，不在此 fd 上 read/write。

二、客户端连接发起（图 1-5）

用户在命令行传入服务器 IP 后运行客户端。

步骤 API / 行为
创建套接字 socket / Socket → sockfd
构造地址 argv[1] 经 inet_pton → sin_addr；端口 htons(13)
主动打开 connect → 内核发起 TCP 三次握手

三、数据交互与连接终止

服务器侧（accept 返回之后）

顺序 动作
1 三次握手完成，阻塞的 Accept 返回 → 新 fd connfd（已连接套接字，专用于该客户）
2 time 取秒数 → snprintf + ctime 格式化为可读字符串（含 \r\n）
3 Write(connfd, …) 经 TCP 发出
4 Close(connfd) → 发 FIN，正常终止本会话
5 回到 Accept 阻塞，等下一客户 → 迭代服务器（串行，同时只服务一路）

客户端侧

顺序 动作
1 while (read > 0) 循环读应答（TCP 无记录边界，可能多次 read 才读全）
2 收到服务器 FIN 后 read 返回 0（EOF）→ 循环结束
3 fputs 打印 → exit(0) → 进程结束，套接字被回收

四、两套 fd 对照（背）

客户端 服务端
主 fd sockfd（connect 后读写） listenfd（只 accept，终身不关）
会话 fd 同上 connfd（每客户一个，写完即 close）
端口 连 对方 IP:13 bind 0.0.0.0:13

五、时间线（与 TCP 报文对应）

时刻 T0  服务端：socket → bind → listen → accept() 睡眠
时刻 T1  客户端：socket → connect → SYN…
时刻 T2  内核：三次握手完成
时刻 T3  服务端：accept 醒 → connfd；write 时间串 → close(connfd) [FIN]
时刻 T4  客户端：read 循环 → read=0 → 打印 → exit [FIN/关 fd]
时刻 T5  服务端：再次 accept 睡眠（若仍有 listenfd）
