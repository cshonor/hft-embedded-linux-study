4.1

概述

study.md · Ch 3 · 4.2 socket

核心主旨与关键论据

本章系统讲解编写完整 TCP 客户/服务器所需的基础套接字 API：从 socket 开始，沿时间线覆盖客户 connect、服务器 bind → listen → accept，并引入 fork 并发模型。

逻辑脉络与时间线

客户程序生命周期

socket → connect（三次握手）→ 数据读写 → close（四次挥手）

服务器程序生命周期

socket → bind（绑定知名端口）→ listen（被动监听）
→ accept（取已连接套接字）→ 读写 → close

与 Ch 5 的关系

  • Ch 4：API 语义与机制（本 chapter）
  • Ch 5：用 Echo 组合 API + 健壮性/信号/异常

核心知识点

API 角色
socket 创建端点
connect 客户主动建连
bind 服务器注册本地地址
listen 转监听套接字 + backlog
accept 取已完成连接
fork 并发派生子进程
close 减引用计数，可能触发 FIN

💡 后续拓展留白
- Ch 16 非阻塞下 API 调用时间线对比图

个人学习总结

TCP 客户：socket→connect→读写→close；TCP 服务器：socket→bind→listen→accept→读写→close。

一句话：Ch4 教 API 语义，Ch5 组合成完整 Echo 程序 + 健壮性。

API 矩阵：客户 2 步（socket+connect），服务器 4 步（socket+bind+listen+accept），fork 实现并发。

4.2

socket 函数

4.3 connect

核心主旨与关键论据

进程要进行网络 I/O，必须先 socket 指定期望的通信协议类型，获得 套接字描述符 sockfd。

关键函数与结构体

int socket(int family, int type, int protocol);
返回值 含义
≥ 0 sockfd（小非负整数）
-1 失败

family（协议族）

常量 用途
AF_INET IPv4
AF_INET6 IPv6
AF_LOCAL / AF_UNIX Unix 域（Ch 15）
AF_ROUTE 路由套接字（Ch 18）
AF_KEY 密钥管理（Ch 19）

type（套接字类型）

常量 对应传输
SOCK_STREAM 字节流（TCP / SCTP 流）
SOCK_DGRAM 数据报（UDP）
SOCK_SEQPACKET 有序分组（SCTP）
SOCK_RAW 原始（Ch 28）

protocol

  • 通常 0：由系统根据 family+type 选默认（STREAM→TCP）
  • 可显式：IPPROTO_TCP、IPPROTO_UDP、IPPROTO_SCTP

易错细节：AF_ 与 PF_

历史 现状
AF_ = Address Family，PF_ = Protocol Family 曾设想一对多，实际相等
标准建议 调用 socket 一律用 AF_ 前缀

💡 后续拓展留白
- socket + SOCK_CLOEXEC（Linux）

个人学习总结

socket(family, type, protocol) 创建通信端点，返回 sockfd。

一句话：family 选协议族（AF_INET/INET6），type 选传输类型（STREAM/DGRAM），protocol 通常填 0。

AF_ vs PF_ 历史上曾区分，实际相等，标准建议一律用 AF_。

4.3

connect 函数

Ch 2.6 握手

核心主旨与关键论据

TCP 客户通过 connect 主动发起连接，触发三次握手；调用可能长时间阻塞。

int connect(int sockfd, const struct sockaddr *servaddr, socklen_t addrlen);
  • servaddr 含服务器 IP + 端口
  • 状态：CLOSED → SYN_SENT → 成功则 ESTABLISHED

错误处理（三类典型）

errno 类型 含义
ETIMEDOUT — 发 SYN 无响应；内核多次重传（如 ~75s）后失败；主机宕机/防火墙
ECONNREFUSED 硬错误 收到 RST；主机可达但端口无 listen
EHOSTUNREACH / ENETUNREACH 软错误 中途 ICMP 不可达；内核暂存并继续重传，最终失败才返回

易错细节与重点结论

connect 失败后禁止对同一 sockfd 再次 connect — 套接字已损坏；必须 close + 新 socket 再试。

💡 后续拓展留白
- SYN 扫描与 connect 关系
- 非阻塞 connect（Ch 16）

个人学习总结

connect 触发三次握手，可能长时间阻塞。三类错误：ETIMEDOUT（无响应）、ECONNREFUSED（RST/端口未监听）、EHOSTUNREACH（ICMP 不可达）。

铁律：connect 失败后禁止对同一 fd 重试——必须 close + 新 socket。

HFT 关联：非阻塞 connect（Ch16）是并发建连的基础，EINPROGRESS 是正常返回。

4.4

bind 函数

4.5 listen · TIME_WAIT：Ch 2.7

核心主旨与关键论据

bind 把本地协议地址（IP + 端口）赋给套接字；服务器向系统注册身份的核心步骤。

int bind(int sockfd, const struct sockaddr *myaddr, socklen_t addrlen);

地址与端口捆绑组合

IP 端口 典型场景
不指定（0） 不指定（0） 客户端；内核选临时端口 + 外出源 IP
任意 0 内核选临时端口
通配（INADDR_ANY / in6addr_any） 指定 服务器；任意网卡上的连接
指定 IP 指定 只监听某块网卡（如内网 IP:80）

易错细节

EADDRINUSE：端口被占用或 TIME_WAIT 占用本地四元组 → SO_REUSEADDR（Ch 7）。

💡 后续拓展留白
- SO_REUSEPORT 多进程同端口监听

个人学习总结

bind 把本地 IP+端口赋给套接字。服务器通常 bind 通配地址 INADDR_ANY + 知名端口；客户端通常不 bind（内核选临时端口）。

一句话：EADDRINUSE → SO_REUSEADDR 解决 TIME_WAIT 占端口。

HFT 关联：多网卡机器可 bind 指定内网 IP 隔离交易流量与管理流量。

4.5

listen 函数

4.6 accept

核心主旨与关键论据

仅 TCP 服务器调用 listen：

  1. 套接字由主动变被动（CLOSED → LISTEN）
  2. 规定内核为该监听套接字排队的最大连接数（backlog）
int listen(int sockfd, int backlog);

两个连接队列（必背）

队列 TCP 状态 含义
未完成连接队列 SYN_RCVD 握手进行中
已完成连接队列 ESTABLISHED 握手完成，等 accept

总长度受 backlog 影响（现代 OS 还与 somaxconn 等有关）。

队列满的容错（重点结论）

新 SYN 到达且两队列总和已达 backlog 限制：

  • 内核忽略 SYN，不发 RST
  • 客户 connect 超时重传 SYN；服务器可能已腾出队列
  • 若回 RST → 客户立即 ECONNREFUSED（硬错误）

原因：队列满多为瞬时高负载；RST 会使客户立刻失败，不利于恢复。

💡 后续拓展留白
- Linux tcp_max_syn_backlog、somaxconn

个人学习总结

listen 做两件事：套接字变被动（LISTEN 状态）+ 设置 backlog 双队列上限。

一句话：队列满时内核丢 SYN 不回 RST——给客户恢复机会。

backlog = 未完成(SYN_RCVD) + 已完成(ESTABLISHED) 队列总和。Linux 受 somaxconn 限制。

4.6

accept 函数

4.8 并发

核心主旨与关键论据

accept 从已完成连接队列队头取下一个连接；队列为空则阻塞（除非非阻塞）。

int accept(int sockfd, struct sockaddr *cliaddr, socklen_t *addrlen);
  • cliaddr、addrlen：值—结果参数；成功填入客户 IP + 端口
  • 不关心客户 → 传 NULL

监听套接字 vs 已连接套接字（全书核心区分）

listenfd accept 返回值 connfd
数量 通常 1 个 每客户 1 个
生命周期 进程全程 服务该客户期间
用途 只 accept 只与该客户 read/write

💡 后续拓展留白
- accept4 + SOCK_NONBLOCK

个人学习总结

accept 从已完成队列取连接，返回新的 connfd。listenfd 唯一，connfd 每客户一个。

一句话：accept 是值-结果参数（socklen_t*）；不关心客户地址传 NULL。

HFT 关联：accept4（Linux）可一步设 O_NONBLOCK + SOCK_CLOEXEC，减少 fcntl 系统调用。

4.7

fork 和 exec 函数

4.8 并发服务器

核心主旨与关键论据

Unix 并发服务器传统实现：fork 派生子进程；必要时 exec 换程序映像。

fork

pid_t fork(void);
  • 调用一次，返回两次：父得子 PID，子得 0
  • 子获得父的数据空间、堆、栈副本
  • 所有已打开描述符（含套接字）被共享，引用计数 +1

exec 族

  • 用新程序替换当前进程映像；PID 不变
  • 默认：exec 前打开的套接字在 exec 后仍打开（inetd 场景，4.10）

💡 后续拓展留白
- vfork 历史
- 线程 vs 进程（Ch 26）

个人学习总结

fork 调用一次返回两次；子进程获得父进程数据副本，所有打开 fd 引用计数 +1。exec 替换程序映像但 PID 不变。

一句话：fork 后父子共享 fd 副本——这是并发服务器 close 规则的根基。

现代替代：线程（Ch26）比 fork 轻量，但 fd 共享语义相同。

4.8

并发服务器

5.2 回射 main

核心主旨与关键论据

标准 TCP 并发服务器流程 — Ch 5 Echo 的骨架。

执行流程（逐步）

  1. 父：socket → bind → listen
  2. 父：循环 accept → 得 connfd
  3. 父：fork
  4. 子：close(listenfd) → 处理 connfd（如 str_echo）→ exit
  5. 父：close(connfd) → 回到 accept

易错细节：描述符泄露（必考）

问题 机制
为何不关 connfd fork 后引用计数 2
子 exit 后 子侧 close → 计数 1
父若不 close 计数永不为 0 → TCP 不断开、fd 泄漏
表现 高并发 EMFILE、连接挂死

父必须 close(connfd) — 与 Ch 5.2 铁律同源。

重点结论

模型 特点
迭代 无 fork；一客户慢则全员阻塞
并发 fork 每连接一子进程；父只 accept

💡 后续拓展留白
- prefork（Ch 30）

个人学习总结

并发服务器标准流程：父 socket→bind→listen→循环 accept→fork→父 close(connfd)→子 close(listenfd)→子处理→exit。

必考铁律：父必须 close(connfd)，否则引用计数永不为 0 → fd 泄漏 → EMFILE。

一句话：迭代服务器一客户慢则全员阻塞；fork 并发每连接一子进程。

4.9

close 函数

引用计数：4.8

核心主旨与关键论据

close(sockfd) 释放描述符；对 TCP 还触发正常终止（四次挥手）。

int close(int sockfd);

底层机制

  • 套接字描述符引用计数 −1
  • 计数 > 0（如子进程仍持有）→ 直接返回，内核不终止 TCP
  • 计数 = 0 → 内核认为无进程使用 → 尽量发完发送缓冲 → 发 FIN

与 shutdown 区别（预告 Ch 6）

close shutdown
粒度 整个 fd 可半关闭读/写
引用计数 减 1 不关闭 fd

个人学习总结

close 减引用计数，计数为 0 时内核发 FIN 终止 TCP。与 shutdown 区别：close 减计数+关 fd，shutdown 不关 fd 但可半关闭。

一句话：fork 后 connfd 引用计数=2，父 close 只减到 1，子 exit 才真正断开。

shutdown(SHUT_WR) 可触发半关闭而不关 fd——Ch6 str_cli 终结版的关键。

4.10

getsockname 和 getpeername 函数

核心主旨与关键论据

运行时获取连接本地/远端协议地址。

函数 返回
getsockname 本地 IP + 端口
getpeername 远端 IP + 端口

典型应用场景

# 场景
1 bind 时端口为 0 → 用 getsockname 查内核分配的临时端口
2 bind INADDR_ANY → 对 accept 返回的 connfd 调 getsockname 知连接落在哪块网卡
3 inetd：父 accept+fork+exec 后，子程序无 cliaddr → 启动后 getpeername 获客户身份

易错细节

  • 对 listenfd 调 getpeername 无意义（无对端）
  • 参数仍是 值—结果 socklen_t*（Ch 3.3）

个人学习总结

运行时查连接本地/远端地址：getsockname 查本地，getpeername 查远端。

三个场景：bind 端口 0 查临时端口；bind INADDR_ANY 查实际网卡；inetd 子进程查客户身份。

参数仍是值-结果 socklen_t*（Ch3.3）。对 listenfd 调 getpeername 无意义。
