# 4.9 未使用函数与链接依赖

## 本节讲什么

声明/实现分离的基本规则（[4.1](./4.1-extern声明与定义.md)、[4.8](./4.8-头文件保护.md)）之后，藏着一个更细的陷阱：**一个没人调用的函数，它体内的外部依赖会不会拖垮链接？** 答案不是一句"会"或"不会"，而是取决于 **链接属性 × 编译器 × 优化级别** 三个变量。常见教程（以及 MSVC 的行为）说"加 `static` 且未调用就不会报错"——**这个说法在 GCC `-O0` 下是错的**，本节用实测把边界钉死。

先澄清一个术语混淆：`gcc -c math.c`（只编译）**永远不做链接检查**，无论函数用没用、依赖缺不缺都能过；只有产生可执行文件的**链接步骤**才去解析符号。`gcc math.c -o math` 是一条命令走完编译+链接，报错发生在链接阶段，不是"编译"阶段。

## 要点

### 声明与实现分离（30 秒回顾）

- 声明放 `.h`（或调用前手写 `extern` 声明，不推荐），实现放 `.c`
- 每个 `.c` 独立编译成 `.o`，**编译期只查"名字有没有声明"**；链接器统一把声明绑定到实现
- 没声明就用 → **编译错**；声明了但实现所在 `.o` 没参与链接 → **链接错**（`undefined reference`，见 [4.7](./4.7-未定义引用.md)）

### 未使用函数的三种情形

设 `math.c` 里有一个 `multiply`，**没有任何人调用它**，它体内调用了外部函数 `logmsg`（实现在 `log.c`）。现在链接时**故意不带 `log.o`**：

| 情形 | `multiply` 链接属性 | 结果 | 原因 |
|------|--------------------|------|------|
| A | 外部链接（无 `static`） | 🔴 **一定报** `undefined reference` | 外部符号必须发射进 `.o`——编译器不知道别的 TU 会不会调它 → 它对 `logmsg` 的引用一定进入符号表 → 链接器一定去查 |
| B | 内部链接（`static`），**未被消除** | 🔴 报错 | 函数体还在 `.o` 里，引用照样进符号表 |
| C | 内部链接（`static`），**被编译器消除** | 🟢 链接通过 | 没人调用的内部链接函数是死代码，编译器**有权**整个删掉，连带删掉对 `logmsg` 的引用 |

B 和 C 的分界线不在标准里——C 标准**允许**消除不可达的内部链接函数，但**不强制**。于是它变成编译器实现 + 优化级别的函数：

### 实测：clang vs gcc × -O0/-O2

同一份代码（`static int multiply` 未被调用，依赖外部 `logmsg`，链接不带 `log.o`）：

| 工具链 | `-O0` | `-O2` |
|--------|-------|-------|
| **clang 23.1.0**（macOS arm64） | 🟢 通过——`-O0` 就消除，`nm` 里连 `multiply` 都没有 | 🟢 通过 |
| **gcc 14.2**（Debian 13 / Pi 5） | 🔴 **报错**——`nm` 可见 `t multiply` + `U logmsg`，`undefined reference to 'logmsg'` | 🟢 通过（死代码消除后） |

gcc `-O0` 保留未使用的 static 函数（方便调试时下断点），clang 任何级别都直接不发射。**"static 未调用就不报错"只是优化开启后的经验，不是语言保证。**

情形 A 在任何编译器、任何优化级别都报错——外部链接函数必须导出，没有豁免。

### 被调用就回到常识

`static` 且**被调用**（情形 D）：函数必然保留，依赖的 `logmsg` 必须有实现参与链接，否则报错——与优化级别无关。

## 与 HFT/嵌入式

- **别把"能链接过"押在优化级别上**：同一份代码 Debug（`-O0`）挂、Release（`-O2`）过，是构建系统的大忌。嵌入式里想要确定性的死代码剔除，用 **`-ffunction-sections -fdata-sections` + 链接时 `--gc-sections`**——由链接器按 section 粒度回收，行为写在构建脚本里，不看编译器心情
- **条件编译的依赖同样适用**：`#ifdef` 关掉的函数体在预处理阶段就消失（连编译都不参与）；而"留着但没人调"的函数走的是本节这条路，两回事
- HFT 网关按模块部分链接（`ld -r`）时，情形 A 的外部符号引用会一路带到最终链接才爆，排查时先 `nm -u` 看未定义符号来自哪个 `.o`

## 代码自测

**题目 1：** `math.c` 中定义了 `static int square(int x){ return x*x; }`，全程序无人调用。链接时报 `undefined reference to 'square'` 可能吗？报 `undefined reference` 给 `square` 体内调用的外部函数可能吗？

<details>
<summary>参考答案</summary>

- 报 `square` 自己：**不可能**。内部链接符号不导出，外部 TU 引用不到它，链接器不会替别人找 `square`。
- 报 `square` 体内的外部依赖：**可能，看编译器和优化级别**。gcc `-O0` 会保留未使用的 static 函数，其体内的外部引用进入符号表 → 依赖缺实现就报错；gcc `-O2` / clang 任意级别会消除该函数 → 不报错。

</details>

**题目 2：** 把 `square` 的 `static` 去掉，仍然无人调用，链接时缺它依赖的外部实现，报不报错？为什么和 static 情形不同？

<details>
<summary>参考答案</summary>

**一定报错，与优化级别无关。** 外部链接函数必须发射并导出符号——编译器无法证明其他翻译单元不会调用它，所以函数体一定进 `.o`，体内的外部引用一定进未定义符号表，链接器一定去解析。static 情形的"豁免"恰恰来自内部链接允许编译器证明"无人可达"从而整体消除。

</details>
