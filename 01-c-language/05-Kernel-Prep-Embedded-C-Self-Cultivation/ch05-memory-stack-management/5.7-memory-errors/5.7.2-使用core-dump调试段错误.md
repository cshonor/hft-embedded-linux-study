# 5.7.2 使用 core dump 调试段错误

## 本节讲什么

进程因 **SIGSEGV/SIGABRT** 等异常终止时，内核可写 **core 文件**（进程内存快照）。用 **GDB 加载可执行文件 + core** 在崩溃点 **bt**、查变量、反汇编。

## 要点

### 开启 core

```bash
ulimit -c unlimited
cat /proc/sys/kernel/core_pattern    # core 路径模板
# systemd: /var/lib/systemd/coredump/ 或当前目录 core

gcc -g -O0 -o crash crash.c
./crash                            # SIGSEGV
gdb ./crash core                   # 或 core.crash.PID
(gdb) bt
(gdb) bt full
(gdb) frame 0
(gdb) list
(gdb) info registers
(gdb) x/16wx $sp
```

### 无 core 时

```bash
gdb ./crash
(gdb) run
# 崩溃后直接 bt
(gdb) bt
```

### 技巧

- 发布版保留 **未 strip** 符号或单独 **debuginfo** 包
- **ARM 交叉**：`arm-linux-gnueabihf-gdb` + `set sysroot`
- 内核：**kdump/vmcore** + `crash` 工具，思路相同

| 信号 | 常见原因 |
|------|----------|
| SIGSEGV | 非法地址读写 |
| SIGABRT | assert、heap corruption |

## 代码自测

**题目 1：** core dump 是什么？如何用 GDB 分析段错误？
```c
$ ulimit -c unlimited   # 允许生成 core
gcc -g buggy.c -o buggy   # 带调试信息
$ ./buggy
Segmentation fault (core dumped)
$ gdb buggy core
(gdb) bt                   # 查看调用栈
```
<details>
<summary>参考答案</summary>

core dump：进程崩溃时操作系统将进程的内存映像（含寄存器、栈、堆）保存到 core 文件。

调试流程：
1. `ulimit -c unlimited`：允许生成 core 文件（默认可能限制为 0）
2. `gcc -g`：编译时带调试信息（DWARF），GDB 才能显示源码行号
3. 运行程序触发段错误，生成 core 文件
4. `gdb ./buggy core`：加载可执行文件和 core dump
5. `bt`（backtrace）：查看崩溃时的调用栈，定位到具体函数和行号
6. `frame N`：切换到第 N 帧
7. `print var`：查看变量值
8. `x/16x addr`：查看内存

`/proc/sys/kernel/core_pattern` 设置 core 文件路径和命名格式。

</details>
