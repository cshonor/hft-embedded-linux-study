4.1

从源程序到二进制文件

本节讲什么

一条 C 源文件从 hello.c 到可执行文件，经历 预处理 → 编译 → 汇编 → 链接 四阶段。GCC 用 -E/-S/-c 停在中间产物，最后用 ld（经 gcc 驱动）生成 ELF 可执行文件。理解这条流水线，是读 .i/.s/.o、排查链接错误和做嵌入式交叉编译的前提。

要点

四阶段与 gcc 选项

阶段 输入 输出 gcc 选项
预处理 .c .i -E
编译 .i .s -S
汇编 .s .o -c
链接 .o + 库 可执行文件 / .so 无 -c 
gcc -E hello.c -o hello.i      # 预处理
gcc -S hello.c -o hello.s      # 生成汇编
gcc -c hello.c -o hello.o       # 生成目标文件
gcc hello.o -o hello           # 链接

ELF 文件类型

后缀 类型 说明
.o ET_REL 可重定位 含 .text/.data/.bss、符号表、重定位表
.a 静态库归档 ar 打包多个 .o
.so ET_DYN 共享库 运行期动态加载
无后缀可执行 ET_EXEC 或 PIE ET_DYN 含程序头、入口地址 
readelf -h hello.o hello       # 查看 ELF 头：Type、Machine、Entry
file hello.o hello libfoo.so   # 快速识别文件类型

常见段（Section）

  • .text：机器码
  • .data：已初始化全局/静态变量
  • .bss：未初始化全局/静态（不占文件空间，运行期清零）
  • .rodata：只读常量
  • .symtab / .strtab：符号表（4.3.3）
  • .rel.text 等：重定位表（4.4.3）
readelf -S hello.o             # 段头表
objdump -h hello.o             # 段摘要
size hello.o                   # .text/.data/.bss 大小

  • 4.2 预处理细节；4.3 编译与汇编；4.4 链接三步骤
  • 4.7/4.8 静/动态库；4.13 binutils 工具集
  • ch05 堆栈与段在运行期的布局；内核/DPDK 构建同样走此流水线

题目 1： C 源文件到可执行文件经历哪些阶段？以下命令各对应哪个阶段？

gcc -E hello.c -o hello.i    # ?
gcc -S hello.i -o hello.s    # ?
gcc -c hello.s -o hello.o    # ?
gcc hello.o -o hello         # ?
参考答案

四个阶段： 1. 预处理（-E）：展开 #include/#define/#ifdef，删除注释 → hello.i 2. 编译（-S）：C 代码 → 汇编代码 → hello.s 3. 汇编（-c）：汇编代码 → 目标文件（机器码） → hello.o 4. 链接：目标文件 + 库 → 可执行文件 hello

gcc hello.c -o hello 一步完成所有阶段。

4.2

预处理过程

本节讲什么

预处理在 编译之前 完成：展开 #include、处理 #define 宏、条件编译 #if/#ifdef、删除注释。输出仍是 C 源码（.i），但已是「单文件、无宏」的展开结果。内核/DPDK 大量用条件编译区分架构与特性。

要点

预处理任务

  1. 头文件展开：#include <stdio.h> 递归插入头文件内容
  2. 宏替换：#define MAX(a,b) ((a)>(b)?(a):(b)) 文本替换（注意副作用）
  3. 条件编译：#ifdef __KERNEL__、#if RTE_ARCH_X86 等
  4. 行号标记：#line 保留错误定位
  5. 删除注释与多余空白

常用指令

#define PI 3.14
#undef  PI
#ifdef DEBUG
#pragma once          // 防重复包含（非标准但广泛支持）
#endif

实战命令

gcc -E hello.c -o hello.i           # 完整展开
gcc -E hello.c | less               # 浏览（很长）
gcc -E -dM hello.c                  # 仅列出宏定义
gcc -E hello.c -D DEBUG=1           # 命令行注入宏

调试技巧

  • 链接错误常源于 宏展开后 的类型/声明不一致
  • 内核 make V=1 可看到实际 -D 选项
  • 用 -save-temps 保留 .i/.s/.o 对照：
gcc -save-temps -c foo.c
ls foo.i foo.s foo.o

与后续衔接

  • 4.3.1 编译器读 .i 生成汇编；宏不影响链接，但影响符号是否生成
  • 4.5.2 打包时 configure 注入 -D；ch06 GNU 扩展宏 likely/unlikely
  • DPDK rte_config.h、内核 autoconf.h 都是预处理产物

代码自测

题目 1： 预处理阶段做了哪些操作？以下代码预处理后输出什么？

#define SQUARE(x) ((x)*(x))
#define MAX 10

#if MAX > 5
int arr[MAX];
#endif
int y = SQUARE(3+2);
参考答案

预处理操作：宏展开、文件包含、条件编译、删除注释。

预处理后：

int arr[10];
int y = ((3+2)*(3+2));

注意 SQUARE(3+2) 展开为 ((3+2)*(3+2)) = 25，不是 SQUARE(5) = 25（结果相同但展开方式不同）。宏是文本替换，不先求值。

4.7

链接静态库

本节讲什么

静态库 .a 是多个 .o 的 归档（ar），链接时链接器 按需抽取 成员 .o 并入可执行文件，代码成为二进制一部分，运行期无 .so 依赖。适合嵌入式、内核部分场景；缺点是体积与升级成本。

要点

制作与使用

gcc -c foo.c bar.c
ar rcs libmy.a foo.o bar.o
ar t libmy.a                     # 列出成员
nm libmy.a
gcc main.o -L. -lmy -o prog      # -lmy 即 libmy.a

链接器搜索规则

  • -L/path 指定目录
  • -lname → libname.a 或 libname.so（默认先 so，可用 -static 强制静库）
  • 从左到右：未解析符号才拉入 .a 中对应 .o
gcc -static -o prog main.o -L. -lmy
ldd prog                         # not a dynamic executable

与符号决议（4.4.2）

  • 静库中未被引用的 .o 不会 进入最终 ELF（减小体积）
  • 循环依赖：gcc ... -lfoo -lbar -lfoo

常见错误

# undefined reference — 库顺序错或未 -l
gcc main.o -lmy -o prog          # 错：main.o 在后更好
gcc main.o -o prog -L. -lmy

# multiple definition — 同一符号在多个 .o 且都被拉入
nm libmy.a | grep duplicate_sym

查看最终是否编入

nm prog | grep my_func
readelf -s prog | grep my_func

与后续衔接

  • 4.8 动态库对比；4.4.2 符号决议
  • DPDK 静链大页驱动；内核子系统多为内置（.o 直接链入 vmlinux）
  • 4.13 ar、nm 工具

代码自测

题目 1： 静态库的创建和使用过程是什么？链接器如何决定从 .a 中提取哪些目标文件？

# 创建静态库
ar rcs libfoo.a foo.o bar.o
# 使用静态库
gcc main.o -L. -lfoo -o main
参考答案

创建：ar rcs libfoo.a foo.o bar.o - r：插入/替换，c：创建，s：写索引

使用：gcc main.o -L. -lfoo -o main - -L.：添加当前目录为库搜索路径 - -lfoo：链接 libfoo.a（或 libfoo.so）

链接器行为：按需提取。扫描 main.o 的未定义符号，在 libfoo.a 的索引中查找。只有定义了所需符号的 .o 文件才会被提取。若 foo.o 和 bar.o 在 .a 中顺序不对，可能需要 --start-group/--end-group 解决循环依赖。

nm libfoo.a 查看库中每个 .o 的符号。

4.9

插件的工作原理

本节讲什么

插件 本质是运行期用 dlopen/dlsym/dlclose 装入的 共享库，主程序在编译期不必链接插件，通过函数指针调用。Firefox/Nginx 模块、DPDK PMD 动态驱动 同属此模式。

要点

基本 API

void *h = dlopen("./libplugin.so", RTLD_LAZY);
int (*init)(void) = dlsym(h, "plugin_init");
init();
dlclose(h);

gcc -fPIC -shared -o libplugin.so plugin.c
gcc -o host host.c -ldl
LD_LIBRARY_PATH=. ./host

与 4.8 的关系

  • 插件必须是 PIC 的 .so
  • 符号须 导出（nm -D libplugin.so）
  • 延迟绑定同样适用（4.8.3）
readelf -d libplugin.so
ldd libplugin.so

常见约定

  • 固定入口符号：plugin_register、rte_pmd_init 等
  • 版本协商结构体，避免 ABI 不匹配

排错

dlerror()                        # 代码中打印
LD_DEBUG=bindings ./host       # 观察加载

与后续衔接

  • 4.8.4 共享库构建；4.5 插件安装路径
  • DPDK：--enable-shared、EAL 扫描 PMD；内核模块用 insmod 非 dlopen
  • ch09 C 模块化设计思想

代码自测

题目 1： 插件机制如何实现？以下代码中 dlopen/dlsym 各完成什么功能？

void *handle = dlopen("./plugin.so", RTLD_NOW);
if (!handle) { fprintf(stderr, "%s\n", dlerror()); return -1; }
typedef int (*func_t)(int);
func_t func = (func_t)dlsym(handle, "process");
func(42);
dlclose(handle);
参考答案

插件机制基于动态链接的运行时加载：

  • dlopen("./plugin.so", RTLD_NOW)：运行时加载共享库到进程地址空间。RTLD_NOW 立即解析所有符号（RTLD_LAZY 延迟解析）
  • dlsym(handle, "process")：在已加载的库中查找符号 process 的地址，返回函数指针
  • 调用 func(42)：通过函数指针调用插件函数
  • dlclose(handle)：卸载共享库（引用计数归零时真正卸载）

编译需 -ldl。插件 .so 必须用 -fPIC -shared 编译。

应用：浏览器插件、GStreamer 编解码器、Nginx 模块、编辑器扩展。

4.10

Linux内核模块运行机制

本节讲什么

内核模块（.ko）是运行期由 insmod 装入内核空间的 可重定位 ELF，与用户态 .so 类似但无 ld.so：由内核 module.c 负责分配内存、重定位、解析符号、注册导出表。读 LKD 驱动、DPDK 内核态 PMD 依赖的「装入」概念与此相通。

要点

与用户态动态链接对比

用户态 .so 内核模块 .ko
加载器 ld-linux.so kernel/module.c
入口 _init / 构造函数 module_init() 宏
符号 dlsym /proc/kallsyms、导出表
卸载 dlclose rmmod

构建与加载

make -C /lib/modules/$(uname -r)/build M=$PWD modules
file hello.ko
readelf -S hello.ko | head
sudo insmod hello.ko
lsmod | grep hello
dmesg | tail
sudo rmmod hello

模块 ELF 特征

readelf -s hello.ko | grep -E 'init|exit'
nm hello.ko
# module_init → __init 段；GPL 许可证符号等

内核钩子（DPDK/网络）

  • igb_uio、vfio-pci 等以模块形式提供用户态映射
  • 网络驱动 insmod 后注册 net_device；与用户态 DPDK poll 配合

与后续衔接

  • 4.8 动态装入概念；4.11 整内核链接与启动
  • 4.4 模块链接同样经历符号决议与重定位
  • ch10 内核模块与设备驱动；LKD 第 2 章

代码自测

题目 1： Linux 内核模块（.ko）和用户态共享库（.so）有什么本质区别？

// 内核模块 hello.c
#include <linux/module.h>
static int __init hello_init(void) {
    printk("Hello kernel\n");
    return 0;
}
static void __exit hello_exit(void) {
    printk("Goodbye\n");
}
module_init(hello_init);
module_exit(hello_exit);
参考答案

本质区别：

内核模块 (.ko) 共享库 (.so)
运行空间 内核态（Ring 0） 用户态（Ring 3）
加载方式 insmod/modprobe dlopen/ld-linux
链接方式 内核符号表 动态链接器
库依赖 只能用内核导出的符号 可用 libc 等用户库
出错影响 内核崩溃（Oops/Panic） 仅进程崩溃

module_init/module_exit 标记的函数在 insmod/rmmod 时被内核调用。printk 是内核的 printf（输出到 dmesg）。

__init 表示该函数只在加载时执行一次，完成后释放代码内存。

4.11

Linux内核编译和启动分析

本节讲什么

Linux 内核由数千 .o 经 特殊链接脚本 vmlinux.lds 链成 vmlinux，再压缩为 bzImage/Image。启动时 Bootloader 载入内核，入口 汇编 startup 建立页表、解压、自重定位，最后进入 start_kernel()——是 4.4 链接 + 4.6 运行 + 4.12 重定位 的大尺度实例。

要点

内核构建（简）

cd linux
make defconfig && make -j$(nproc)
readelf -h vmlinux | grep Entry
nm vmlinux | grep start_kernel

链接脚本

  • arch/x86/kernel/vmlinux.lds.S：定义内核虚拟地址布局（__start、__init 等段）
  • 与用户态 4.14 同属 SECTIONS 思想，规模更大
readelf -S vmlinux | grep -E 'text|init|data'
objdump -d vmlinux | head

启动链（x86 概念）

Bootloader → 实模式/保护模式入口
  → head_32/head_64 汇编
  → decompress_kernel（若压缩）
  → start_kernel()
      → setup_arch、mm_init、rest_init
      → kernel_init → 用户态 init

与 DPDK

  • 内核配置 Hugepage、IOMMU、VFIO 影响 DPDK 运行环境
  • uname -r 与 linux-headers 版本须与模块构建匹配（4.10）

与后续衔接

  • 4.12 U-Boot 重定位是 Bootloader 侧重定位
  • 4.14 链接脚本；4.6.2 裸机启动对比
  • ch10 OS 启动；读 LKD 启动流程

代码自测

题目 1： Linux 内核的编译过程和普通 C 程序有什么不同？vmlinux 和 bzImage 的关系是什么？

参考答案

内核编译流程： 1. make menuconfig：配置内核选项（生成 .config） 2. make：编译所有源文件 → .o → 链接为 vmlinux（ELF 格式，未压缩内核） 3. make bzImage：将 vmlinux 压缩 + 添加解压代码 → bzImage（可引导内核镜像） 4. make modules：编译可加载模块（.ko） 5. make modules_install：安装模块到 /lib/modules/

与普通程序区别： - 无 libc（用内核自带的 string/bitops 等） - 链接脚本 vmlinux.lds 自定义段布局（.init.text 可释放） - 入口是 _start（head.S），不是 main - 必须交叉编译：make ARCH=arm CROSS_COMPILE=arm-linux-

4.12

U-boot重定位分析

本节讲什么

U-Boot 常先由 ROM 加载到 低地址 SRAM/DRAM 临时区，再 自拷贝 到链接脚本指定的高地址并 修正重定位项——因为初始 PC 与链接 VMA 不一致。这是 4.4.3 重定位 在嵌入式 Bootloader 中的手工版，与内核解压后重定位同类。

要点

为何重定位

  • 链接时假设运行在 TEXT_BASE（如 0x40200000）
  • 上电时可能在 0x00000000 或另一 RAM 区执行
  • 必须拷贝代码/数据并修补 相对/绝对地址引用

典型步骤（概念）

  1. relocate_code：拷贝 .text/.data 到目标区
  2. 遍历 __rel_dyn_start…__rel_dyn_end 修补
  3. 跳转至重定位后地址继续执行
# 分析 U-Boot ELF（交叉工具链）
arm-linux-gnueabihf-readelf -S u-boot
arm-linux-gnueabihf-nm u-boot | grep relocate

代码自测

题目 1： U-Boot 为什么要做重定位（relocate）？以下代码完成什么操作？

/* U-Boot relocate */
ulong relocaddr = gd->relocaddr;
memcpy((void *)relocaddr, (void *)CONFIG_SYS_TEXT_BASE, gd->mon_len);
relocate_code(relocaddr, gd->reloc_off, relocaddr);
参考答案

U-Boot 重定位原因： - U-Boot 初始加载到固定地址（CONFIG_SYS_TEXT_BASE，如 0x87800000） - 但该地址可能被 Linux 内核占用，需将自身复制到更高地址运行 - 重定位后修正所有绝对地址引用（通过 reloc_off 偏移量）

流程： 1. memcpy：将整个 U-Boot 代码和数据复制到新地址 relocaddr 2. relocate_code：修正 GOT 表、所有绝对地址符号（加上 reloc_off） 3. 跳转到新地址继续执行

这是嵌入式启动的常见模式：Bootloader 先在低端地址运行，然后搬自己到高端地址，腾出空间给内核。

4.14

链接脚本

本节讲什么

链接脚本（Linker Script） 用 MEMORY 与 SECTIONS 告诉 ld：各段放入哪块物理存储、链接顺序、VMA/LMA。裸机/嵌入式把 .text/.rodata 放 Flash、.data/.bss 放 RAM 全靠脚本；Linux 内核 vmlinux.lds、U-Boot u-boot.lds 同理（4.11、4.12）。

要点

最小示例（ARM 裸机概念）

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .text : {
        KEEP(*(.isr_vector))
        *(.text*)
        *(.rodata*)
    } > FLASH

    .data : AT (ADDR(.text) + SIZEOF(.text)) {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > RAM

    .bss : {
        _sbss = .;
        *(.bss*) *(COMMON)
        _ebss = .;
    } > RAM
}
  • > 目标内存；AT 指定 LMA（Flash 中存放位置）
  • startup 用 _sdata/_edata 拷贝、_sbss/_ebss 清零（4.6.2）

使用方式

arm-none-eabi-gcc -nostdlib -T linker.ld -o firmware.elf startup.o main.o
arm-none-eabi-readelf -l firmware.elf
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
arm-none-eabi-nm firmware.elf | grep -E '_sdata|_sbss|main'

常用命令行

gcc -Wl,-T,linker.ld -Wl,-Map,out.map main.o
# 或
ld -T linker.ld -o out.elf *.o

与用户态默认脚本

  • ld 默认脚本：ld --verbose 查看
  • 一般 Linux 程序不显式写脚本；嵌入式几乎必须自定义

代码自测

题目 1： 链接脚本（.lds）的作用是什么？以下脚本定义了什么内存布局？

ENTRY(_start)
SECTIONS {
    . = 0x80000000;
    .text : { *(.text) }
    . = ALIGN(4);
    .data : { *(.data) }
    .bss : { *(.bss) *(COMMON) }
}
参考答案

链接脚本控制链接器如何合并段和分配地址：

  • ENTRY(_start)：指定程序入口为 _start（而非默认的 main）
  • . = 0x80000000：设置起始地址（裸机/嵌入式指定运行地址）
  • .text : { *(.text) }：合并所有输入文件的 .text 段
  • . = ALIGN(4)：4 字节对齐
  • .data/.bss：同理，COMMON 是链接器分配的公共符号

用途： - 嵌入式系统指定代码在 Flash/SRAM 中的位置 - 控制段顺序和对齐 - 定义符号（如 _text_start = .;）供 C 代码引用

gcc -T link.lds ... 或 ld -T link.lds 指定链接脚本。
