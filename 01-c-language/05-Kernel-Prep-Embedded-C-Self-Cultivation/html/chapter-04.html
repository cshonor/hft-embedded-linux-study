4.1

从源程序到二进制文件

本节讲什么

一条 C 源文件从 hello.c 到可执行文件，经历 预处理 → 编译 → 汇编 → 链接 四阶段。GCC 用 -E/-S/-c 停在中间产物，最后用 ld（经 gcc 驱动）生成 ELF 可执行文件。理解这条流水线，是读 .i/.s/.o、排查链接错误和做嵌入式交叉编译的前提。

要点

四阶段与 gcc 选项

阶段 输入 输出 gcc 选项
预处理 .c .i -E
编译 .i .s -S
汇编 .s .o -c
链接 .o + 库 可执行文件 / .so 无 -c 
gcc -E hello.c -o hello.i      # 预处理
gcc -S hello.c -o hello.s      # 生成汇编
gcc -c hello.c -o hello.o       # 生成目标文件
gcc hello.o -o hello           # 链接

ELF 文件类型

后缀 类型 说明
.o ET_REL 可重定位 含 .text/.data/.bss、符号表、重定位表
.a 静态库归档 ar 打包多个 .o
.so ET_DYN 共享库 运行期动态加载
无后缀可执行 ET_EXEC 或 PIE ET_DYN 含程序头、入口地址 
readelf -h hello.o hello       # 查看 ELF 头：Type、Machine、Entry
file hello.o hello libfoo.so   # 快速识别文件类型

常见段（Section）

  • .text：机器码
  • .data：已初始化全局/静态变量
  • .bss：未初始化全局/静态（不占文件空间，运行期清零）
  • .rodata：只读常量
  • .symtab / .strtab：符号表（4.3.3）
  • .rel.text 等：重定位表（4.4.3）
readelf -S hello.o             # 段头表
objdump -h hello.o             # 段摘要
size hello.o                   # .text/.data/.bss 大小

题目 1： C 源文件到可执行文件经历哪些阶段？以下命令各对应哪个阶段？

gcc -E hello.c -o hello.i    # ?
gcc -S hello.i -o hello.s    # ?

参考答案

4.2

预处理过程

本节讲什么

预处理在 编译之前 完成：展开 #include、处理 #define 宏、条件编译 #if/#ifdef、删除注释。输出仍是 C 源码（.i），但已是「单文件、无宏」的展开结果。内核/DPDK 大量用条件编译区分架构与特性。

要点

预处理任务

  1. 头文件展开：#include <stdio.h> 递归插入头文件内容
  2. 宏替换：#define MAX(a,b) ((a)>(b)?(a):(b)) 文本替换（注意副作用）
  3. 条件编译：#ifdef __KERNEL__、#if RTE_ARCH_X86 等
  4. 行号标记：#line 保留错误定位
  5. 删除注释与多余空白

常用指令

#define PI 3.14
#undef  PI
#ifdef DEBUG
#pragma once          // 防重复包含（非标准但广泛支持）
#endif

实战命令

gcc -E hello.c -o hello.i           # 完整展开
gcc -E hello.c | less               # 浏览（很长）
gcc -E -dM hello.c                  # 仅列出宏定义
gcc -E hello.c -D DEBUG=1           # 命令行注入宏

调试技巧

  • 链接错误常源于 宏展开后 的类型/声明不一致
  • 内核 make V=1 可看到实际 -D 选项
  • 用 -save-temps 保留 .i/.s/.o 对照：
gcc -save-temps -c foo.c
ls foo.i foo.s foo.o

与后续衔接

  • 4.3.1 编译器读 .i 生成汇编；宏不影响链接，但影响符号是否生成
  • 4.5.2 打包时 configure 注入 -D；ch06 GNU 扩展宏 likely/unlikely
  • DPDK rte_config.h、内核 autoconf.h 都是预处理产物

代码自测

题目 1： 预处理阶段做了哪些操作？以下代码预处理后输出什么？

#define SQUARE(x) ((x)*(x))
#define MAX 10

#if MAX > 5
int arr[MAX];
#endif
int y = SQUARE(3+2);
参考答案

预处理操作：宏展开、文件包含、条件编译、删除注释。

预处理后：

int arr[10];
int y = ((3+2)*(3+2));

注意 SQUARE(3+2) 展开为 ((3+2)*(3+2)) = 25，不是 SQUARE(5) = 25（结果相同但展开方式不同）。宏是文本替换，不先求值。

4.3

程序的编译

本节讲什么

「编译」在狭义上指 C → 汇编（gcc -S），广义上常把 汇编 → .o 也算入编译阶段。编译器为每个翻译单元生成独立 .o，外部符号先留空，由链接器后续决议（4.4）。单文件编译快、可并行，是大型内核/DPDK 工程的基础。

要点

编译器做什么

  • 词法/语法/语义分析、优化
  • 生成目标体系结构的汇编（x86/ARM 等）
  • 输出 ELF 可重定位文件 .o，含机器码 + 符号表 + 重定位项
gcc -c foo.c -o foo.o
gcc -c bar.c -o bar.o
gcc foo.o bar.o -o prog        # 链接阶段

与汇编器的分工

工具 输入 输出
cc1（编译器前端） .c/.i .s
as（汇编器） .s .o

gcc -c 一次完成两步；gcc -S 只到汇编。

并行与依赖

make -j$(nproc)               # 多 .c 并行 -c
gcc -MMD -MP -c foo.c         # 同时生成 foo.d 依赖文件

查看产物

file foo.o
readelf -S foo.o
nm foo.o
objdump -d foo.o

与后续衔接

  • 4.3.1–4.3.3 分步拆解 C→汇编→.o 与符号/重定位表
  • 4.4 链接多个 .o；4.7/4.8 链接库
  • ch03 汇编指令与 objdump -d 对照阅读

代码自测

题目 1： 编译阶段（C → 汇编）包含哪些子步骤？

参考答案

编译阶段包含： 1. 词法分析：源代码 → Token 流（标识符、关键字、常量、运算符） 2. 语法分析：Token → AST（抽象语法树），检查语法错误 3. 语义分析：类型检查、作用域检查 4. 中间代码生成：AST → IR（中间表示） 5. 优化：常量折叠、死代码消除、循环优化 6. 目标代码生成：IR → 汇编代码（寄存器分配、指令选择）

gcc -S 只到这一步。现代 GCC 默认开启 -O0（无优化），生产环境用 -O2/-O3。

4.3

.1 从C文件到汇编文件

本节讲什么

编译器核心输出是 汇编语言（.s），而非直接生成机器码。gcc -S 可单独停在汇编阶段，便于对照 C 语句与指令、理解优化与调用约定（ch03 AAPCS）。

要点

生成汇编

gcc -S hello.c -o hello.s
gcc -S -O2 hello.c -o hello.O2.s    # 对比优化级别
gcc -S -fverbose-asm hello.c        # 汇编中带 C 行号注释

典型汇编结构（x86-64）

    .file   "hello.c"
    .text
    .globl  main
main:
    pushq   %rbp
    movq    %rsp, %rbp
    ...
    call    puts
    popq    %rbp
    ret
  • .globl symbol：导出全局符号供链接
  • call foo：若 foo 在其他 .o，生成 重定位项（地址先填 0 或占位）

阅读要点

  • 函数序言/尾声：建立栈帧（ch05）
  • 参数传递：x86-64 用寄存器（rdi, rsi…）；ARM 用 r0–r3
  • 未定义符号：call 外部函数时出现 R_X86_64_PLT32 等重定位类型
objdump -d hello.o              # 若已 -c
objdump -S hello.o              # 混排 C 源码（需 -g 编译）

优化影响

  • -O0：变量多在栈上，便于调试
  • -O2：内联、寄存器分配、死代码消除；汇编行数可能变少或重排

与后续衔接

  • 4.3.2 as 把 .s 汇编成 .o
  • ch03 读懂 ARM/x86 指令；4.4.3 重定位修补 call 地址
  • 内核 make objdump、DPDK rte_pause 内联都可从 -S 入手

代码自测

题目 1： 以下 C 代码编译为 ARM 汇编后，局部变量如何分配？

int add(int a, int b) {
    int c = a + b;
    return c;
}
参考答案

编译后的 ARM 汇编（简化）：

add:
    ADD R0, R0, R1    @ R0 = a + b (a在R0, b在R1)
    BX LR             @ 返回, R0是返回值

c 是临时变量，编译器直接优化掉（不分配栈空间），结果留在 R0。

若 c 需要取地址（&c），编译器才会在栈上分配：SUB SP, SP, #4; STR R0, [SP]; ...。

优化原则：能放寄存器就不放栈。-O0 模式下可能不优化，所有局部变量都放栈。

4.3

.2 汇编过程

本节讲什么

汇编器 as 将助记符 .s 翻译成机器码，写入 .o 的 .text/.data 等段，并生成 符号表 与 重定位表。每条未解析的地址引用（跨文件调用、全局变量地址）都记录为重定位项，等链接器填正。

要点

汇编器输入输出

as -o hello.o hello.s           # 显式调用
gcc -c hello.c                  # 内部调用 as

段与符号

汇编伪操作决定段归属：

.section .text
.globl  func
func:
    ret

.section .data
.globl  counter
counter:
    .long 0

nm hello.o
# T func    — .text 中已定义（局部 Text）
# D counter — .data 中已定义（Data）
# U puts    — 未定义，待链接（Undefined）

重定位项诞生

对 call puts@PLT 或 movabs $msg, %rdi，若 puts/msg 地址未知，as 在 .rel.text 记录：

readelf -r hello.o              # 重定位表
objdump -r hello.o              # 另一种查看方式

常见类型（x86-64）：R_X86_64_PC32（相对调用）、R_X86_64_64（绝对地址）。

与编译器协作

  • 编译器负责生成正确伪操作（.cfi_* 栈展开信息等）
  • 手写汇编（ch03）须自己声明 .global、段对齐
gcc -c add_asm.S -o add_asm.o
readelf -S add_asm.o

与后续衔接

  • 4.4.1 链接器合并各 .o 的同名段；4.4.3 根据重定位表写最终地址

代码自测

题目 1： 汇编阶段（.s → .o）做了什么？目标文件中包含哪些内容？

参考答案

汇编阶段：汇编代码 → 机器码，生成目标文件（.o / ELF 格式）。

目标文件包含： - .text：代码段（编译后的机器指令） - .data：已初始化全局变量 - .bss：未初始化全局变量（只记录大小，不占文件空间） - .symtab：符号表（函数名、变量名、类型、地址） - .strtab：字符串表（符号名字符串） - .rel.text/.rel.data：重定位表（待链接时修正的地址）

readelf -S hello.o 查看所有节区。

4.3

.3 符号表与重定位表

本节讲什么

每个 .o 携带 符号表（有哪些函数/变量、定义还是引用）和 重定位表（哪些指令地址待修补）。链接器靠这两张表完成 符号决议 与 重定位（4.4）。读 nm/readelf -s 是排查 undefined reference 的必备技能。

要点

符号表（.symtab）

nm 列 含义
T/t 代码段已定义（全局/局部）
D/d 已初始化数据
B/b BSS 未初始化数据
U 未定义，需其他模块提供
C 公共符号（已废弃，现代链接器少见） 
nm -C foo.o                    # C++ demangle
readelf -s foo.o               # 完整符号：Bind、Type、Ndx
readelf --syms foo.o | grep UND

重定位表（.rel.*）

每条重定位记录：偏移、类型、符号索引、加数。

readelf -r foo.o
# Offset   Info    Type             Sym.Value  Sym.Name
# 0000000a 00000a R_X86_64_PC32      00000000  puts

含义：.text 偏移 0xa 处的 call 需相对 puts 的最终地址修补。

ELF 段与符号关系

readelf -S foo.o
# [Nr] Name    Type     ...
#  1   .text   PROGBITS ...
#  7   .symtab SYMTAB   ...
#  9   .rel.text REL     ...

.o / .a / .so / 可执行文件对比

文件 符号表 重定位
.o 完整 有 .rel.*
.a 各成员 .o 归档 成员内仍有
.so 有（动态符号 .dynsym） 链接时/加载时
可执行 可 strip 掉 通常已修补完 
ar t libfoo.a && nm libfoo.a
readelf -d libfoo.so             # 动态段

代码自测

题目 1： 以下目标文件的符号表中，U、T、D 分别表示什么？

$ nm hello.o
         U printf
00000000 T main
00000020 D global_var
参考答案
  • U（Undefined）：未定义符号，该文件引用但未定义（如 printf，需链接时从库中找到）
  • T（Text）：代码段符号，该文件定义的函数（如 main，在 .text 节）
  • D（Data）：数据段符号，已初始化全局变量（在 .data 节）

其他常见：B（BSS 段，未初始化全局变量）、W（弱符号）、t（局部函数，static）。

链接器的工作：将所有 U 符号在其他文件的 T/D/B 中找到定义并匹配。

4.4

链接过程

本节讲什么

链接把多个 .o 和库拼成最终 ELF，分三步：分段组装（合并 .text/.data 等）→ 符号决议（匹配 U 与 T/D/B）→ 重定位（修补代码中的地址引用）。静态链接在构建期完成；动态链接部分推迟到加载/运行（4.8）。

要点

链接器角色

  • 输入：.o、.a、.so（仅记录依赖）、链接脚本（4.14）
  • 输出：可执行文件、ET_DYN PIE、或 .so
  • 工具：ld（常由 gcc/g++ 调用）
gcc foo.o bar.o -o prog
ld -o prog foo.o bar.o -lc          # 显式调用
gcc -Wl,-Map=prog.map foo.o bar.o   # 生成链接映射

三步概览

步骤 小节 核心
分段组装 4.4.1 同名段合并、分配 VMA
符号决议 4.4.2 解析 undefined、处理冲突
重定位 4.4.3 按最终地址写指令/数据

静/动态链接选择

gcc -static -o prog foo.o bar.o     # 全静态，体积大
gcc -shared -fPIC -o libfoo.so foo.c
gcc -o prog main.o -L. -lfoo        # 动态链接 libfoo

与后续衔接

  • 4.4.1–4.4.3 各步细节；4.7 静态库；4.8 动态链接
  • 4.6 链接后 Entry point、_start；4.14 裸机链接脚本
  • 内核 vmlinux 链接、DPDK meson 最终都调用 ld

题目 1： 链接器的主要功能是什么？静态链接和动态链接的区别是什么？

参考答案

链接器两大功能： 1. 符号决议：将各目标文件中的未定义符号（U）与定义符号（T/D/B）匹配 2. 重定位：合并各目标文件的段（.text/.data/.bss），修正符号地址

静态：gcc main.o libfoo.a -o main；动态：gcc main.o -lfoo -o main（默认动态）。

4.4

.1 分段组装

本节讲什么

链接第一步：把各输入文件的 同名段 按规则拼接成输出文件的一个段，并为每段分配 虚拟地址（VMA） 和 加载地址（LMA）。可执行文件的段布局决定运行期内存映像；裸机由链接脚本指定 Flash/RAM 位置（4.14）。

要点

段合并规则

  • 所有 .text → 输出 .text（按链接顺序或脚本排序）
  • .data、.bss、.rodata 同理
  • COMDAT / 弱符号 去重（C++ 内联、模板）
gcc -c a.c b.c
readelf -S a.o b.o
gcc a.o b.o -o ab
readelf -S ab                 # 段合并后总大小

VMA 与 LMA

  • VMA：运行时的虚拟地址（Linux 用户态由 loader 建立映射）
  • LMA：加载到内存/Flash 的物理地址（嵌入式常 VMA≠LMA：代码在 Flash 运行或需拷贝到 RAM）
readelf -l ab                  # Program Headers：LOAD 段 VMA/Align
objdump -h ab

链接顺序影响

gcc -o prog main.o libfoo.a libbar.a   # 从左到右解析符号
# 静库放后面；循环依赖可： -lfoo -lbar -lfoo

查看布局

gcc -Wl,-Map=prog.map,-cref main.o foo.o
grep '\.text' prog.map
size prog                       # text/data/bss 汇总

  • 4.4.3 重定位引用合并后的段内偏移
  • 4.14 SECTIONS {} 精确控制 .text 放 Flash、.data 放 RAM
  • ch05 运行时段在进程地址空间中的位置

题目 1： 链接器如何合并多个目标文件的段？以下两个文件链接后的 .text 段布局是什么？

// a.o: int main() { return foo(); }
// b.o: int foo() { return 42; }
参考答案

链接器按段类型合并：

最终 .text: [a.o:.text] [b.o:.text]
最终 .data: [a.o:.data] [b.o:.data]
最终 .bss:  [a.o:.bss]  [b.o:.bss]

同名段按输入顺序拼接。每个段内的偏移地址被重新计算为最终虚拟地址。

a.o 中 call foo 的地址是占位符（0x00000000），链接器查 b.o 的符号表找到 foo 的实际地址，修正这条指令（重定位）。

readelf -S a.out 可以看到合并后的段布局。

4.4

.2 符号决议

本节讲什么

链接器扫描全部符号，为每个 未定义引用（U） 找到 唯一定义，或报错。规则涉及强/弱符号、COMMON 段、静库成员按需抽取。本节是理解 undefined reference 与 multiple definition 的核心。

要点

强符号 vs 弱符号

类型 示例 冲突时
强 普通全局定义 int x=1; 不能有两个强定义
弱 __attribute__((weak)) 或 int x;（ tentative） 强覆盖弱 
// a.c
int val = 10;           // 强
// b.c
int val;                // 弱 COMMON，链接合并到一处

常见错误

undefined reference to foo'

gcc main.o -o main
# main.o 中 U foo，但未链接定义 foo 的 .o 或库
gcc main.o foo.o -o main    # 补全
nm main.o | grep foo

multiple definition of bar'

# bar 在两个 .o 都有强定义
nm a.o b.o | grep bar
# 改 static、或只保留一处定义、或用 weak

静库符号抽取

ar 归档的 .a 按成员整包尝试：从左到右，仅当某 .o 能解析当前未定义符号时才装入（4.7）。

gcc main.o -L. -lfoo -lbar
nm -A libfoo.a | grep ' T '

C/C++ 注意

  • extern "C" 避免名字改编
  • 内联/static 函数不导出符号
  • 查看：
nm -C prog | less
c++filt _Z3foov

  • 4.4.3 决议后得到符号最终 VMA，才能重定位
  • 4.7 静库链接顺序；4.8 动态符号 .dynsym

代码自测

题目 1： 以下代码链接时会发生什么？为什么？

// file1.c
int x = 10;
// file2.c
int x = 20;
// file3.c
extern int x;
int main() { return x; }
参考答案

链接错误：多重定义（multiple definition）。

file1.c 和 file2.c 都定义了全局变量 x（强符号），链接器报错。

符号决议规则： - 强符号（已初始化全局变量/函数定义）：只能有一个 - 弱符号（未初始化全局变量 int x; 或 __attribute__((weak))）：可以多个 - 若强符号和弱符号同名，选强符号 - 若多个弱符号同名，任选一个

修复：将其中一个改为 __attribute__((weak)) 或 extern，或用 static 限制作用域。

4.4

.3 重定位

本节讲什么

符号决议完成后，链接器遍历各输入的 重定位表，按公式把 占位地址 改成最终 VMA 下的正确值，写回输出文件的 .text/.data。编译期未知的跨文件地址、全局指针、GOT 项都在此或加载期修补。

要点

重定位公式（概念）

对每条重定位项：*addr = S + A + P

  • S：符号最终值（地址）
  • A：加数（addend）
  • P：被修补位置的段内偏移
  • 具体因 重定位类型 而异（相对/绝对/PC 相对）
readelf -r foo.o                 # 链接前
readelf -r prog                  # 可执行文件通常为空（已修补）
objdump -d prog | grep call      # 已是正确目标

典型类型（x86-64）

类型 场景
R_X86_64_PC32 相对跳转 call
R_X86_64_64 64 位绝对地址
R_X86_64_GOTPCREL 经 GOT 访问（4.8）

链接前后对比

gcc -c main.c
objdump -d main.o                # call 目标可能为 0 或占位
gcc main.o -o main
objdump -d main                  # call 指向 libc 或 PLT

加载时重定位

  • PIE + ASLR：内核 loader 映射到随机基址，再做 动态重定位（.rela.dyn）
  • 内核/U-Boot：自拷贝与重定位（4.11、4.12）
readelf -d ./prog | grep RELA
ldd ./prog

与后续衔接

  • 4.8.2/4.8.3 GOT/PLT 延迟绑定也是重定位的一种
  • 4.14 链接脚本改变 S 的值（段起始地址）
  • 4.12 U-Boot 自搬移后手动重定位；ch05 指针指向已重定位地址

代码自测

题目 1： 以下代码中 call printf 的地址在链接前后分别是什么？

// main.c
int main() {
    printf("hello\n");
    return 0;
}
参考答案

链接前（main.o）：call printf 的目标地址是 0x00000000（占位符），重定位表中记录"此处需要 printf 的地址"。

链接后（main）：链接器查 libc 的符号表，找到 printf 的实际地址（如 0x400530），将指令中的 0x00000000 修正为 0x400530。

重定位类型： - R_ARM_CALL：分支指令（BL）的相对地址修正 - R_ARM_ABS32：绝对地址修正（如全局变量地址）

readelf -r main.o 查看重定位表，列出所有待修正的位置。

4.5

程序的安装

本节讲什么

「安装」是把 构建产物（可执行文件、库、配置、文档）按约定布局复制到目标系统目录（如 /usr/bin、/usr/lib），并更新缓存/包数据库。与 4.4 链接 不同：安装不改变 ELF 内容，只解决 交付与路径；运行期 loader 靠 RPATH、LD_LIBRARY_PATH、ldconfig 找到 .so。

要点

安装 vs 链接 vs 运行

阶段 产物位置 谁参与
链接 构建目录 build/prog ld
安装 /usr/local/bin/prog make install、包管理器
运行 进程地址空间 execve、loader（4.6）

典型前缀（FHS）

/usr/bin/        用户命令
/usr/lib/        共享库
/etc/            配置
/usr/share/      文档/数据

手工安装示例

gcc -o mytool main.c
sudo install -m 755 mytool /usr/local/bin/
sudo install -m 644 libmy.so /usr/local/lib/
sudo ldconfig                    # 更新动态库缓存

与包管理

  • 4.5.2 dpkg/源码包；4.5.3 apt；4.5.4 Windows 安装包
  • DPDK：ninja install 装 PMD 与头文件；内核：make modules_install

4.5

.1 程序安装的本质

本节讲什么

安装的本质是 文件部署 + 元数据登记：把 ELF 与资源放到标准路径，让 shell、ld.so、服务管理器能找到它们。不改变程序逻辑，但决定 动态库能否加载、配置是否生效、多版本能否共存。

要点

安装做了什么

  1. 复制/链接 二进制与 .so 到 bindir/libdir
  2. 权限（chmod）、属主（chown）
  3. 库缓存 ldconfig 扫描 /etc/ld.so.conf.d
  4. 包元数据（deb 的 control、文件清单）
make prefix=/usr/local install
DESTDIR=/tmp/stage make install   # 打包用暂存根
tree /tmp/stage/usr/local

动态库路径

readelf -d ./prog | grep -E 'RPATH|RUNPATH'
ldd ./prog
LD_LIBRARY_PATH=/opt/lib ./prog   # 临时覆盖

静态 vs 动态安装差异

类型 安装内容 运行依赖
静态链接 单个可执行文件 无外部 .so
动态链接 可执行 + .so 须安装库或设 RPATH 
gcc -static -o prog main.c
ldd prog                          # not a dynamic executable

嵌入式视角

  • 无包管理：整镜像烧录（U-Boot + kernel + rootfs）
  • 4.14 链接脚本决定 Flash 布局，与 PC「安装」类比为「烧录布局」

题目 1： 为什么安装后的程序能在任意目录执行？这涉及哪些机制？

参考答案

因为可执行文件被安装到 PATH 环境变量包含的目录中。

机制： 1. PATH 变量：echo $PATH 显示搜索路径（如 /usr/local/bin:/usr/bin:/bin） 2. shell 查找：输入 hello 时，shell 按 PATH 顺序查找 hello 可执行文件 3. 动态库搜索路径：运行时按 LD_LIBRARY_PATH → /etc/ld.so.cache → 默认路径查找 .so

4.5

.2 在Linux下制作软件安装包

本节讲什么

Linux 常用 dpkg（.deb） 或 RPM 分发：把 make install 的文件清单、依赖、脚本打包，由 dpkg/apt 解压到根文件系统并触发 postinst。开源项目常提供 autotools/cmake + checkinstall 或正式 debian/ 目录。

要点

基本流程

./configure --prefix=/usr
make -j$(nproc)
sudo make install               # 或 DESTDIR 暂存

DESTDIR 打包

make DESTDIR=/tmp/pkg install
find /tmp/pkg -type f
# 再用 fpm/checkinstall 生成 .deb

checkinstall 示例

sudo checkinstall --pkgname=mytool --pkgversion=1.0
# 跟踪 make install 写入的文件生成 deb

deb 结构（概念）

  • DEBIAN/control：包名、版本、依赖（libc6 等）
  • usr/bin/mytool：实际文件
  • 安装后：ldconfig 在 postinst 中调用
dpkg -L mytool                    # 列出安装文件
dpkg -s mytool                    # 包信息

与编译链接的关系

  • 构建阶段仍用 gcc/ld（4.1–4.4）
  • 打包只收录 usr/ 下产物；-dev 包另含头文件与 .a

与后续衔接

  • 4.5.3 apt 在线安装；4.8.4 包依赖 libc.so.6
  • DPDK：发行版 dpkg 或自编译 ninja install
  • 内核：make deb-pkg 生成内核 deb

代码自测

题目 1： deb 包和源码编译安装各有什么优缺点？

参考答案

deb/rpm 包安装： - 优点：自动处理依赖、统一卸载（apt remove）、版本管理 - 缺点：需要打包流程，灵活性低

本节讲什么

apt 从软件源下载 预构建 .deb，自动解决依赖并调用 dpkg 安装到系统路径。用户拿到的是已链接好的 ELF 与 .so，无需本地 gcc/ld（开发包装 -dev 才含头文件与静态库）。

apt-file search libfoo.so.1         # 查哪个包提供某库

方式 优点 缺点
apt 二进制包 快、依赖自动 版本受发行版限制
源码 make install 可定制 -D/优化 需自行处理依赖

开发工作流

readelf -h hello

题目 1： apt-get install 的工作流程是什么？与编译安装有什么区别？

参考答案

apt-get 工作流程： 1. 读取 /etc/apt/sources.list 获取软件源 URL 2. apt update：下载软件包索引（Packages.gz） 3. apt install foo：从索引中查找 foo，自动解析依赖 4. 下载 .deb 包到 /var/cache/apt/archives/ 5. dpkg 解包并安装到系统目录 6. 自动安装依赖包 7. 执行 postinst 脚本（配置服务、更新缓存等）

代码自测

题目 1： Windows 下静态链接和动态链接的 DLL 在安装时有何不同？

参考答案

静态链接：所有库代码编入 .exe，安装只需复制单个 .exe 文件。文件大但无依赖问题。

动态链接 DLL： - .exe 依赖 .dll 文件，安装时必须一起分发 - DLL 可被多个程序共享，节省内存 - 需注意 DLL Hell（版本冲突）：用 Side-by-Side Assembly 或 static linking 解决

安装包工具：NSIS（免费）、Inno Setup、WiX（MSI 格式）。

Windows 下制作安装包：将 .exe + .dll + 资源文件打包为单一安装程序。

4.6

.4 BSS段的小秘密

本节讲什么

BSS（Block Started by Symbol） 存放 未初始化全局/静态变量，在 ELF 中 不占文件磁盘空间（SHT_NOBITS），加载时由 loader 或启动代码 清零。static int buf[1024]; 若未显式初始化，全为 0——这是 C 标准保证，靠 BSS 机制实现。

要点

三段对比

段 初值 文件占用
.data 有（如 int x=1） 占
.bss 视为 0 不占（仅记录大小）
.text 机器码 占 
gcc -c foo.c
size foo.o                       # bss 列
readelf -S foo.o | grep -E 'data|bss'

示例

int uninit;                      // 进 .bss
int inited = 42;                 // 进 .data
static char buf[4096];           // .bss

nm foo.o | grep -E 'uninit|inited|buf'
# B uninit / D inited / b buf

谁清零

  • Linux：execve 映射 BSS 页为 零页（CoW）
  • 裸机：startup 汇编对 [__bss_start, __bss_end) 循环写 0（4.6.2）
readelf -l prog | grep LOAD       # BSS 常合并在最后一 LOAD
objdump -h prog

常见误区

  • BSS 过大占 运行期 RAM，不占镜像体积——嵌入式要关注 RAM 预算
  • char *p; 全局未初始化为 NULL（0），局部变量 不在 BSS，值不确定

与后续衔接

  • 4.4.1 链接合并各 .o 的 .bss
  • 4.14 链接脚本 *(.bss) 放 RAM
  • ch05 堆与 mmap 另算；DPDK rte_zmalloc 显式清零堆内存

代码自测

题目 1： 以下代码编译后的目标文件和可执行文件中，BSS 段有什么"秘密"？

    static int uninit_static;  // BSS

}
参考答案

原因：BSS 段的值全为 0，没必要在文件中存储一堆 0。ELF 只记录 BSS 段的大小（p_memsz > p_filesz），加载时内核分配匿名页并清零。

验证： - size hello.o：BSS 列显示字节数，但 ls -l hello.o 的文件大小不含 BSS - readelf -S hello.o：.bss 节的 FileSize 为 0，MemSize 为实际大小

好处：大量未初始化数组（如 int buf[10000]）不增大可执行文件体积。

4.7

本节讲什么

静态库 .a 是多个 .o 的 归档（ar），链接时链接器 按需抽取 成员 .o 并入可执行文件，代码成为二进制一部分，运行期无 .so 依赖。适合嵌入式、内核部分场景；缺点是体积与升级成本。

要点

制作与使用

gcc -c foo.c bar.c

  • 静库中未被引用的 .o 不会 进入最终 ELF（减小体积）

常见错误

gcc main.o -o prog -L. -lmy

# multiple definition — 同一符号在多个 .o 且都被拉入

nm prog | grep my_func
readelf -s prog | grep my_func

动态链接 把共享库 .so 在 运行期 由 ld.so 映射进进程，多进程 共享代码页，升级库无需重编主程序。实现依赖 PIC、GOT、PLT 与延迟绑定（4.8.1–4.8.4）。Linux 用户态程序、DPDK PMD 插件、内核模块（insmod）都属广义「运行时装入」。

4.8

.1 与地址无关的代码

本节讲什么

PIC（Position Independent Code） 使 .so 文本段可映射到 任意虚拟地址（ASLR），指令中不出现绝对地址，而通过 GOT/PC 相对 访问数据与函数。编译加 -fPIC（x86-64 常隐含于 -shared）。

要点

为何需要 PIC

  • 共享库只加载 一份物理代码，多进程映射到 不同基址
  • 非 PIC：重定位会修改 .text（Copy-on-Write，失去共享优势）
gcc -fPIC -c foo.c -o foo_pic.o
gcc -fno-PIC -c foo.c -o foo_nop.o
readelf -r foo_pic.o foo_nop.o

访问全局变量（x86-64）

  • 非 PIC：movabs $sym, %rax（绝对地址）
  • PIC：mov sym@GOTPCREL(%rip), %rax 经 GOT 间接加载
gcc -fPIC -S -O0 foo.c -o -
objdump -d foo_pic.o | grep -i got

编译选项

gcc -fPIC -shared -o libfoo.so foo.c
gcc -fPIE -pie -o prog main.c    # 可执行也可 PIE
readelf -h libfoo.so | grep Type  # DYN

ARM 注记

  • ARM/ARM64 通常默认 PIC；adr + GOT 访问（ch03）

与后续衔接

  • 4.8.2 GOT 存符号运行时地址
  • 4.8.3 函数经 PLT 跳转；4.4.3 重定位与 PIC 配合
  • DPDK 共享 PMD；内核模块必须为可重定位代码

代码自测

题目 1： 什么是位置无关代码（PIC）？为什么共享库必须使用 PIC？

// 非PIC代码 (静态链接)
movl global_var, %eax    @ 绝对地址

// PIC代码 (动态链接)
movl global_var@GOT, %eax @ 通过GOT间接访问
参考答案

PIC（Position Independent Code）：代码不包含绝对地址，所有地址引用都通过 PC 相对寻址或 GOT 间接访问。

为什么共享库需要 PIC： - 共享库被映射到不同进程的不同虚拟地址 - 若代码含绝对地址，每个进程都需要修改代码页（Copy-on-Write，失去共享优势） - PIC 代码只读，可被多进程共享；数据通过 GOT 间接访问

编译：gcc -fPIC -shared -o libfoo.so foo.c（-fPIC 生成 PIC 代码）

GOT（全局偏移表）存储全局变量/函数的实际地址，每个进程有自己的 GOT 副本。

4.8

.2 全局偏移表

本节讲什么

GOT（Global Offset Table） 是 .got/.got.plt 段中的 地址表：PIC 代码通过「基址 + 偏移」查表取得全局变量与函数的真实地址。链接时填部分项，加载时 ld.so 根据 重定位表 .rela.dyn 补全。

要点

GOT 作用

  • 数据访问：mov var@GOTPCREL(%rip), %rax
  • 与 PLT 配合解析外部函数地址（4.8.3）
gcc -fPIC -shared -o libfoo.so foo.c
readelf -S libfoo.so | grep got
objdump -d libfoo.so | grep -i got

查看动态重定位

readelf -r libfoo.so              # .rela.dyn / .rela.plt
readelf -d libfoo.so | grep REL

常见项：R_X86_64_GLOB_DAT、R_X86_64_JUMP_SLOT（函数 GOT/PLT 槽）。

链接前后

gcc -fPIC -c foo.c
readelf -r foo.o
gcc -shared -o libfoo.so foo.o
readelf --dyn-syms libfoo.so

性能注记

  • 经 GOT 多一次间接访存；static 内部函数可不走 GOT
  • -fno-plt 等优化可减少 PLT 层（高级话题）

代码自测

题目 1： GOT（Global Offset Table）的工作原理是什么？以下代码如何通过 GOT 访问全局变量？

// 共享库中的代码
extern int shared_var;
int get_var(void) {
    return shared_var;
}
参考答案

GOT 是一个数据表，存储全局符号的实际运行时地址。

访问流程： 1. 代码用 PC 相对寻址找到 GOT 中 shared_var 对应的槽位 2. 从 GOT 读取 shared_var 的实际地址 3. 通过该地址访问变量

get_var:
    LDR R0, [PC, #offset]  @ R0 = &GOT[n] (PC相对)
    LDR R0, [R0]            @ R0 = GOT[n] = shared_var的实际地址
    LDR R0, [R0]            @ R0 = *shared_var

GOT 在加载时由动态链接器填充实际地址。代码段只读可共享，GOT 在数据段每个进程独立。

4.8

本节讲什么

延迟绑定（Lazy Binding） 通过 PLT（Procedure Linkage Table） 实现：首次 call printf@plt 才由 ld.so 解析真实地址并写入 GOT，后续调用直达目标。加快启动、避免链接未用函数。可用 LD_BIND_NOW 关闭。

要点

PLT 桩（概念）

                              →  之后：GOT[n] 已是 printf 地址

强制立即绑定

代码自测

题目 1： 什么是延迟绑定（Lazy Binding）？它如何优化程序启动速度？

参考答案

延迟绑定：函数地址在第一次调用时才解析，而非启动时全部解析。

机制（PLT + GOT）： 1. 第一次调用 printf：跳转到 PLT 入口 → GOT 中地址指向 PLT 下一指令 → 调用 _dl_runtime_resolve 解析 printf 地址 → 修正 GOT → 执行 printf 2. 后续调用：直接从 GOT 获取已解析的地址，跳转到 printf

优点：启动快（只解析实际调用的函数），大型库可能只有少数函数被使用。

环境变量 LD_BIND_NOW=1：禁用延迟绑定，启动时解析所有符号（用于调试）。

PLT（过程链接表）在代码段，GOT 在数据段。

U-boot重定位分析

本节讲什么

U-Boot 常先由 ROM 加载到 低地址 SRAM/DRAM 临时区，再 自拷贝 到链接脚本指定的高地址并 修正重定位项——因为初始 PC 与链接 VMA 不一致。这是 4.4.3 重定位 在嵌入式 Bootloader 中的手工版，与内核解压后重定位同类。

要点

为何重定位

  • 链接时假设运行在 TEXT_BASE（如 0x40200000）
  • 上电时可能在 0x00000000 或另一 RAM 区执行
  • 必须拷贝代码/数据并修补 相对/绝对地址引用

典型步骤（概念）

  1. relocate_code：拷贝 .text/.data 到目标区
  2. 遍历 __rel_dyn_start…__rel_dyn_end 修补
  3. 跳转至重定位后地址继续执行
# 分析 U-Boot ELF（交叉工具链）

arm-linux-gnueabihf-nm u-boot | grep relocate
arm-linux-gnueabihf-objdump -d u-boot | grep relocate

与链接脚本

  • u-boot.lds 定义 TEXT_BASE、__image_copy_start

对照 Linux 启动

阶段 重定位者
U-Boot 自身 board_init_f / relocate
Linux 内核 head.S + 解压桩

代码自测

题目 1： U-Boot 为什么要做重定位（relocate）？以下代码完成什么操作？

U-Boot 重定位原因： - U-Boot 初始加载到固定地址（CONFIG_SYS_TEXT_BASE，如 0x87800000） - 但该地址可能被 Linux 内核占用，需将自身复制到更高地址运行 - 重定位后修正所有绝对地址引用（通过 reloc_off 偏移量）

4.14

链接脚本

本节讲什么

链接脚本（Linker Script） 用 MEMORY 与 SECTIONS 告诉 ld：各段放入哪块物理存储、链接顺序、VMA/LMA。裸机/嵌入式把 .text/.rodata 放 Flash、.data/.bss 放 RAM 全靠脚本；Linux 内核 vmlinux.lds、U-Boot u-boot.lds 同理（4.11、4.12）。

要点

最小示例（ARM 裸机概念）

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .text : {
        KEEP(*(.isr_vector))
        *(.text*)
        *(.rodata*)
    } > FLASH

    .data : AT (ADDR(.text) + SIZEOF(.text)) {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > RAM

    .bss : {
        _sbss = .;
        *(.bss*) *(COMMON)
        _ebss = .;
    } > RAM
}
  • > 目标内存；AT 指定 LMA（Flash 中存放位置）
  • startup 用 _sdata/_edata 拷贝、_sbss/_ebss 清零（4.6.2）

使用方式

arm-none-eabi-gcc -nostdlib -T linker.ld -o firmware.elf startup.o main.o
arm-none-eabi-readelf -l firmware.elf
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
arm-none-eabi-nm firmware.elf | grep -E '_sdata|_sbss|main'

常用命令行

# 或

  • ENTRY(_start)：指定程序入口为 _start（而非默认的 main）
  • . = 0x80000000：设置起始地址（裸机/嵌入式指定运行地址）
  • .text : { *(.text) }：合并所有输入文件的 .text 段
  • . = ALIGN(4)：4 字节对齐
  • .data/.bss：同理，COMMON 是链接器分配的公共符号

用途： - 嵌入式系统指定代码在 Flash/SRAM 中的位置 - 控制段顺序和对齐 - 定义符号（如 _text_start = .;）供 C 代码引用

gcc -T link.lds ... 或 ld -T link.lds 指定链接脚本。
