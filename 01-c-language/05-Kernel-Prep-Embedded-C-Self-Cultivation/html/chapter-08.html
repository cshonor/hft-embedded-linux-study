8.1

代码复用与分层思想

本节讲什么

嵌入式与内核代码规模庞大，重复逻辑与硬件耦合是维护噩梦。本节建立分层架构与代码复用的第一性原理：上层只依赖抽象接口，下层提供具体实现；同一套框架可覆盖 UART、SPI、以太网等不同硬件。这是后续 C 模拟 OOP（struct + 函数指针 + ops 表）的动机——用 C 写出可扩展、可测试的驱动骨架。

要点

三层驱动模型（demo06_layered）：

┌─────────────────────────────────┐
│  app/     应用层：open/read/write │
├─────────────────────────────────┤
│  abstract/ 抽象层：dev_ops 接口   │
├─────────────────────────────────┤
│  hw/      硬件层：寄存器/MMIO     │
└─────────────────────────────────┘
层次 职责 复用方式
抽象 定义 DevOps、生命周期 API 所有驱动共享同一套头文件
硬件 寄存器读写、中断 每颗芯片一份 .c
应用 业务逻辑、协议栈 通过 ops 调用，不直接碰寄存器

弱符号默认实现（衔接 ch06 6.9）：

/* abstract/dev_default.c */
void __attribute__((weak)) hw_uart_init(void) { /* stub */ }
void __attribute__((weak)) hw_uart_tx(char c) { (void)c; }

/* hw/uart_pl011.c — 强符号覆盖 */
void hw_uart_init(void) { /* 写 PL011 寄存器 */ }
  • 未链接 hw/ 时仍可编译运行 stub；链接真实 BSP 后自动选用强定义
  • 避免 #ifdef BOARD_XXX 散落各处

复用手段对照：

手段 C 实现 典型场景
函数指针 / ops struct file_operations 运行时多态
宏 / inline readl/writel 零开销抽象
不透明类型 typedef struct dev dev_t 隐藏内部字段
container_of 从 list_head 得宿主 struct 内核链表遍历
  • 单一职责：每层只暴露必要 API；应用层不应 #include 硬件寄存器头
  • 依赖方向：app → abstract ← hw，hw 不反向依赖 app
  • 测试友好：mock 层提供 weak/stub 实现，单测无需真实硬件

代码自测

题目 1： C 语言如何实现代码复用和分层？以下驱动分层结构中各层的职责是什么？

参考答案

C 代码复用方式：函数复用、模块化设计、分层架构、回调机制。

驱动分层结构示例： - 硬件层：直接操作寄存器（write_reg(addr, val)） - HAL 层（硬件抽象层）：封装寄存器操作（gpio_set(pin, val)） - 驱动层：实现设备逻辑（led_on()/led_off()） - 应用层：调用驱动接口

分层原则： 1. 上层依赖下层，不反向依赖 2. 层间通过函数指针/结构体指针通信 3. 下层不 include 上层头文件 4. 修改下层不影响上层（只要接口不变）

Linux 内核分层：应用 → VFS → 文件系统 → 块设备 → 驱动 → 硬件。每层有明确接口。

8.5

Linux内核中的OOP思想：多态

本节讲什么

多态是同一调用点根据对象类型执行不同代码。内核与 DPDK 中无处不在：VFS 根据打开的文件类型调用不同 read；网卡驱动填 net_device_ops；DPDK 用 eth_dev_ops 的 rx_pkt_burst/tx_pkt_burst 在 poll 模式驱动间切换。本节串联 8.2.3–8.2.4 的 ops 表与真实子系统。

要点

VFS：file_operations 虚表：

struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    /* ioctl, mmap, poll ... */
};

/* 系统调用层 */
static ssize_t vfs_read(struct file *file, ...) {
    if (file->f_op->read)
        return file->f_op->read(file, ...);
    return -EINVAL;
}

字符设备注册：

static struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .read  = my_read,
    .write = my_write,
    .open  = my_open,
};

cdev_init(&cdev, &my_fops);
cdev_add(&cdev, devno, 1);

DPDK eth_dev_ops（示意）：

struct eth_dev_ops {
    eth_rx_burst_t rx_pkt_burst;   /* 必填 — 纯虚 */
    eth_tx_burst_t tx_pkt_burst;
    eth_dev_configure_t dev_configure;
    eth_dev_start_t dev_start;
    /* stats, promiscuous, ... */
};

/* 应用统一入口 */
nb_rx = port->dev_ops->rx_pkt_burst(rx_queue, pkts, nb_pkts);
子系统 ops 结构 多态入口
VFS file_operations vfs_read/write/ioctl
Block block_device_operations submit_bio
Net net_device_ops ndo_start_xmit
DPDK eth eth_dev_ops rte_eth_rx_burst
Platform platform_driver bus probe

与用户态 demo 对应：

/* demo03 — 与内核同构 */
devices[i]->ops->send(devices[i], buf, len);
  • ops 表在 编译期 填好，运行期 仅间接调用 — 无 C++ vtable 指针 per object 开销（通常共享静态 ops）
  • RCU 替换 ops 需内核同步机制；DPDK 热路径避免运行时改 ops
  • module_get(THIS_MODULE) 防 ops 执行时模块卸载

常见陷阱

  1. ops 函数指针为 NULL 时直接调用 → NULL 指针解引用崩溃 file->f_op->read(...) 若 read 为 NULL（驱动未实现），直接调用即解引用 NULL 函数指针 → oops。VFS 框架在 vfs_read 中先判 NULL 再调用：if (file->f_op->read) return file->f_op->read(...); else return -EINVAL;。但自定义 ops 表没有这种保护——驱动作者忘了判 NULL 即崩。约定：ops 表必填字段用 WARN_ON(!ops->xxx) 在注册时检查；可选字段调用方判 NULL。

  2. ops 表被运行时修改 → 数据竞争 正常 ops 是 static const，编译期固定。若设计成"运行时切换 ops"（如协议状态机切换），多核并发调用 ops 时读到部分更新的指针——尤其在弱内存序架构（ARM/POWER）上。修复：用 RCU（rcu_assign_pointer + rcu_dereference）保护 ops 切换；或 ops 在 init 后不可变。DPDK 数据面热路径禁止运行时改 ops——切换 ops 在停队列后做。

  3. 模块卸载时 ops 仍在执行 → use-after-free 驱动模块卸载时，file_operations 代码段被释放，但若有进程正在 read 该设备文件，read 函数返回时访问已释放代码 → oops。框架用 module_get(THIS_MODULE)（fops->owner = THIS_MODULE）保护：open 时增加模块引用计数，release 时减少，卸载需等计数归零。但：内核其他路径（如内核线程、workqueue）调 ops 不一定走 open/release——驱动自己必须保证卸载前取消所有异步调用。

自测题

1.（选择） 内核 file_operations 与 C++ vtable 的关键区别？ - A. vtable 是每个对象一份，ops 是多个对象共享一份 - B. vtable 自动生成，ops 手动填 - C. vtable 性能更高 - D. ops 只能用于内核

答案

A。C++ 每个对象含一个 vptr 指向 vtable，多对象多 vptr；内核 file_operations 通常是 static const 结构，所有同类对象共享同一份 ops 表，对象自身不存指针——节省内存（每个 struct file 不含 ops 字段，只 f_op 一个指针）。性能上间接调用一次 vs 两次（vptr + vtable 偏移）几乎无差。B 错：vtable 由编译器生成，ops 也是编译期填好（ designated init）。

2.（判断） file->f_op->read(file, ...) 调用前必须判 file->f_op->read != NULL。

答案

对，在框架代码中。VFS 的 vfs_read 显式判 NULL：

if (file->f_op->read)
    return file->f_op->read(file, buf, count, pos);
else if (file->f_op->read_iter)
    return new_sync_read(file, ...);
else
    return -EINVAL;

驱动内部调用自家 ops 可省略判 NULL（自家 ops 一定填了），但跨子系统调用必须判——你不知道对方驱动是否实现了某回调。坑：新手照搬 file->f_op->read(...) 不判，遇字符设备未实现 read 即崩。

3.（踩坑） 驱动模块卸载后 5 秒，系统崩溃在 my_read 函数地址。fops.owner = THIS_MODULE 已设置。为什么没保护住？

答案

异步调用绕过了 owner 引用计数。fops->owner 保护的是通过 open/release 走的同步路径——open 时 try_module_get 增计数，卸载需等所有打开的 fd 关闭。但： 1. 内核线程/workqueue 直接调 f_op->read 不走 open，不增计数。 2. 卸载时模块代码被释放，但已 schedule 的 work 仍排队，worker 执行时跳到已释放地址 → oops。 3. remove 时若 cancel_work_sync 漏掉，work 在模块卸载后执行即 use-after-free。 修复：remove 中 cancel_work_sync 等所有 work 完成，再 unregister_xxx 让框架阻止新调用。fops.owner 不保护异步路径——驱动自己负责。

4.（应用） 用 ops 表实现一个"协议无关"网络发包接口：上层 net_send(skb) 根据网卡类型调不同驱动。给出 ops 定义和注册骨架。

答案 
/* netdev.h */
struct net_device;
struct netdev_ops {
    int (*open)(struct net_device *);
    int (*stop)(struct net_device *);
    int (*start_xmit)(struct net_device *, struct sk_buff *skb);
    struct net_device_stats *(*get_stats)(struct net_device *);
};

struct net_device {
    char name[16];
    const struct netdev_ops *ops;    /* 多态入口 */
    void *priv;
};

/* 上层统一入口 */
int net_send(struct net_device *dev, struct sk_buff *skb) {
    if (!dev->ops || !dev->ops->start_xmit)
        return -ENOTSUP;
    return dev->ops->start_xmit(dev, skb);
}

/* my_eth.c — Intel 网卡驱动 */
static int igb_open(struct net_device *dev) { /* ... */ }
static int igb_xmit(struct net_device *dev, struct sk_buff *skb) { /* DMA 描述符 */ }

static const struct netdev_ops igb_ops = {
    .open       = igb_open,
    .stop       = igb_stop,
    .start_xmit = igb_xmit,
    .get_stats  = igb_stats,
};

static int igb_probe(struct pci_dev *pdev, ...) {
    struct net_device *netdev;
    netdev = alloc_netdev(sizeof(struct igb_priv), "eth%d", ether_setup);
    netdev->ops = &igb_ops;            /* 注册 ops */
    register_netdev(netdev);
}

要点： - 上层 net_send 不知具体驱动——纯多态。 - ops 是 static const，所有同类网卡共享。 - priv 用 netdev_priv() 取，存硬件私有状态。 - 内核 net_device_ops 完全是这个模式，DPDK eth_dev_ops 同构。
