8.1

代码复用与分层思想

本节讲什么

嵌入式与内核代码规模庞大，重复逻辑与硬件耦合是维护噩梦。本节建立分层架构与代码复用的第一性原理：上层只依赖抽象接口，下层提供具体实现；同一套框架可覆盖 UART、SPI、以太网等不同硬件。这是后续 C 模拟 OOP（struct + 函数指针 + ops 表）的动机——用 C 写出可扩展、可测试的驱动骨架。

要点

三层驱动模型（demo06_layered）：

┌─────────────────────────────────┐
│  app/     应用层：open/read/write │
├─────────────────────────────────┤
│  abstract/ 抽象层：dev_ops 接口   │
├─────────────────────────────────┤
│  hw/      硬件层：寄存器/MMIO     │
└─────────────────────────────────┘
层次 职责 复用方式
抽象 定义 DevOps、生命周期 API 所有驱动共享同一套头文件
硬件 寄存器读写、中断 每颗芯片一份 .c
应用 业务逻辑、协议栈 通过 ops 调用，不直接碰寄存器

弱符号默认实现（衔接 ch06 6.9）：

/* abstract/dev_default.c */
void __attribute__((weak)) hw_uart_init(void) { /* stub */ }
void __attribute__((weak)) hw_uart_tx(char c) { (void)c; }

/* hw/uart_pl011.c — 强符号覆盖 */
void hw_uart_init(void) { /* 写 PL011 寄存器 */ }
  • 未链接 hw/ 时仍可编译运行 stub；链接真实 BSP 后自动选用强定义
  • 避免 #ifdef BOARD_XXX 散落各处

复用手段对照：

手段 C 实现 典型场景
函数指针 / ops struct file_operations 运行时多态
宏 / inline readl/writel 零开销抽象
不透明类型 typedef struct dev dev_t 隐藏内部字段
container_of 从 list_head 得宿主 struct 内核链表遍历
  • 单一职责：每层只暴露必要 API；应用层不应 #include 硬件寄存器头
  • 依赖方向：app → abstract ← hw，hw 不反向依赖 app
  • 测试友好：mock 层提供 weak/stub 实现，单测无需真实硬件

题目 1： C 语言如何实现代码复用和分层？以下驱动分层结构中各层的职责是什么？

参考答案

C 代码复用方式：函数复用、模块化设计、分层架构、回调机制。

驱动分层结构示例： - 硬件层：直接操作寄存器（write_reg(addr, val)） - HAL 层（硬件抽象层）：封装寄存器操作（gpio_set(pin, val)） - 驱动层：实现设备逻辑（led_on()/led_off()） - 应用层：调用驱动接口

分层原则： 1. 上层依赖下层，不反向依赖 2. 层间通过函数指针/结构体指针通信 3. 下层不 include 上层头文件 4. 修改下层不影响上层（只要接口不变）

Linux 内核分层：应用 → VFS → 文件系统 → 块设备 → 驱动 → 硬件。每层有明确接口。

8.2

面向对象编程基础

本节讲什么

面向对象编程（OOP） 用「对象」组织数据与行为，强调封装、继承、多态三大特性。C 语言没有 class 关键字，但 Linux 内核、DPDK、RTOS 驱动框架普遍用 struct + 函数指针 + ops 表 模拟 OOP。本节是 8.2.1–8.2.4 的总览：建立 C 与 C++/Java OOP 概念的映射表，为后续内核源码阅读打底。

要点

C ↔ OOP 概念映射：

OOP 概念 C 语言实现 内核/DPDK 示例
类（class） struct + 配套 API struct net_device
对象（object） struct 变量或 malloc 实例 struct uart_dev uart0
成员变量 struct 字段 int baudrate
成员方法 以对象指针为第一参数的函数 netdev->ops->ndo_open()
虚函数 / 多态 函数指针 / ops 结构体 file_operations
继承 基类 struct 作为首成员 UartDev 内嵌 Device base
接口 只含函数指针的 struct PowerOps、CommOps 
/* 最小「类」骨架 */
struct counter {
    int value;
};

void counter_inc(struct counter *self) {
    self->value++;
}
  • OOP 解决的是大规模代码的组织问题，不是语法糖；C 用约定与 discipline 达到同样目标
  • 首成员继承依赖 C 标准「struct 首地址 = 首成员地址」，可用 (Device *)&uart_dev 向上转型
  • ops 表把行为从数据分离，同一框架代码遍历 heterogeneous 设备列表

题目 1： C 语言（非 C++）如何模拟面向对象的封装、继承、多态？

// 封装
struct animal {
    int age;
    void (*speak)(struct animal *);
};
// 继承
struct dog {
    struct animal base;  // 第一个成员
    int breed;
};
// 多态
void make_speak(struct animal *a) { a->speak(a); }
参考答案

C 模拟 OOP 的方式：

封装：struct + 函数指针 + 头文件隐藏实现 - struct 放头文件（公开接口），实现放 .c 文件 - 函数指针模拟成员方法

继承：结构体嵌套（第一个成员是父类） - struct dog { struct animal base; ... } - struct animal *a = (struct animal *)&dog; 安全转换（C 标准保证首成员地址 = 结构体地址）

多态：函数指针表（vtable） - 不同子类设置不同的 speak 函数 - make_speak 通过函数指针调用，运行时决定调用哪个函数

这是 Linux 内核的核心设计模式：file_operations/device_driver/socket_ops 都是此模式。

8.2

.1 什么是 OOP

本节讲什么

面向对象编程以「对象」为中心：每个对象封装状态（数据）与行为（方法），对外只暴露有限接口。四大支柱——封装、抽象、继承、多态——在 C 驱动框架中均有对应实现。理解 OOP 术语有助于阅读 LKD、struct device、DPDK eth_dev_ops 等源码，即便你永远不写 C++。

要点

四大特性：

特性 含义 C 模拟
封装 隐藏内部实现，只暴露 API 不透明 struct + .c 内实现
抽象 提取共性，忽略细节 DevOps 只声明 open/read/write
继承 子类扩展/复用父类 基类 struct 作首成员
多态 同一接口，不同实现 函数指针运行时跳转 
/* 抽象：所有字符设备都能 read/write */
struct CharDevOps {
    int (*read)(void *ctx, char *buf, size_t len);
    int (*write)(void *ctx, const char *buf, size_t len);
};

/* 多态：uart 与 spi 各自填 ops */
static int uart_read(void *ctx, char *buf, size_t len) { /* ... */ }
static int spi_read(void *ctx, char *buf, size_t len) { /* ... */ }

struct CharDevOps uart_ops = { .read = uart_read, .write = uart_write };
struct CharDevOps spi_ops  = { .read = spi_read,  .write = spi_write };

/* 统一调用 */
dev->ops->read(dev->ctx, buf, len);

与面向过程对比：

  • 面向过程：uart_read()、spi_read() 分散，调用方需 switch(type)
  • 面向对象：调用方只认 ops->read，新增设备类型无需改框架

C 的局限与对策：

局限 对策
无访问控制 命名约定 _ 前缀 + 不透明类型
无单继承语法 首成员嵌入 + 强制转换
无多重继承 mixin：多个 ops 指针并列（demo05）
无析构自动调用 显式 xxx_destroy() + 配对 create
  • 对象 = 一块内存（struct 实例）+ 与之绑定的行为（函数或 ops）
  • 内核中「对象」常为静态全局（如 platform_device）或 kmalloc 分配

题目 1： 面向对象编程的三大特征是什么？C 语言如何分别实现？

参考答案

OOP 三大特征：

  1. 封装：数据和操作绑定，隐藏内部实现 - C 实现：struct + .h/.c 分离，头文件只暴露接口 - 不透明指针：typedef struct impl *Handle;（头文件不暴露 struct 定义）

  2. 继承：子类复用父类的数据和方法 - C 实现：结构体嵌套 c struct derived { struct base parent; int extra; }; - container_of 宏从父类指针获取子类指针

  3. 多态：同一接口不同实现 - C 实现：函数指针 c struct ops { void (*start)(void); void (*stop)(void); }; - 不同设备注册不同的 ops

C++ 有语言级支持（class/virtual/template），C 需要手动实现但更灵活、无运行时开销（vtable 手动管理）。

8.2

.2 类的封装与实例化

本节讲什么

封装把 struct 内部字段藏起来，头文件只暴露不透明类型与 create / destroy / get / set 等有限 API。调用方无法直接改 value，必须通过 counter_inc()，从而维护不变量（如不出现负数计数）。实例化即创建对象：栈上静态实例或堆上 malloc，对应 C++ 的栈对象与 new。

要点

不透明类型模式（demo01_encapsulation）：

/* counter.h — 公开接口 */
typedef struct counter counter_t;

counter_t *counter_create(int initial);
void         counter_destroy(counter_t *c);
int          counter_get(const counter_t *c);
void         counter_inc(counter_t *c);

/* counter.c — 隐藏实现 */
struct counter {
    int value;
};

counter_t *counter_create(int initial) {
    counter_t *c = malloc(sizeof *c);
    if (!c) return NULL;
    c->value = initial;
    return c;
}

void counter_destroy(counter_t *c) {
    free(c);
}
API 角色 函数命名惯例 说明
构造 xxx_create / xxx_new 分配并初始化，失败返回 NULL
析构 xxx_destroy / xxx_del 释放资源，接受 NULL 安全
读 xxx_get_* const 对象指针，不修改状态
写 xxx_set_* / xxx_inc 内部校验后修改

静态 vs 堆实例（demo04_lifecycle）：

/* 静态：生命周期 = 整个程序，零 malloc 开销 */
static counter_t sys_counter = { .value = 0 };

/* 堆：动态数量、运行期创建 */
counter_t *c = counter_create(0);
/* ... */
counter_destroy(c);
方式 优点 风险
静态/栈 无碎片、确定性 不可动态扩容；注意初始化顺序
堆 灵活、可传指针 必须配对 destroy；泄漏/双重释放
  • const counter_t * 承诺不通过该指针修改对象（仅 get 类 API）
  • 头文件不暴露 struct counter { ... } 完整定义 → 无法在外部 c->value = 999
  • 内核常用 kzalloc + kfree 替代 malloc/free；RTOS 用静态池

题目 1： 以下 C 代码如何模拟类的封装和实例化？与 C++ class 有什么区别？

// stack.h
typedef struct Stack Stack;
Stack *stack_create(int capacity);
void stack_push(Stack *s, int val);
int stack_pop(Stack *s);
void stack_destroy(Stack *s);

// stack.c
struct Stack { int *data; int top; int cap; };
参考答案

C 模拟类： - 头文件（stack.h）：暴露 typedef 和接口函数（相当于 class 的 public 声明） - 源文件（stack.c）：struct 定义和函数实现（相当于 class 的 private 实现） - 不透明指针：typedef struct Stack Stack; 头文件只有前向声明，用户不知道 struct 内部布局 - 实例化：stack_create() 等价于 new Stack() - 销毁：stack_destroy() 等价于 delete

与 C++ 区别： | | C 模拟 | C++ class | |---|---|---| | 封装 | 不透明指针 | private 成员 | | 方法 | 函数+首参 | 成员函数（隐含 this） | | 构造 | create 函数 | 构造函数 | | 析构 | destroy 函数 | 析构函数 | | 访问控制 | 编译期隔离（头文件） | 语言级 private/public | | 继承 | 手动嵌套 | 语言级支持 |

C 方式的优势：二进制 ABI 稳定，跨编译器兼容。

8.2

.3 继承与多态

本节讲什么

继承让子类型复用父类型字段与行为；C 通过把基类 struct 作为首成员模拟单继承。多态指通过统一接口调用不同实现——运行时根据对象绑定的 ops / 函数指针 跳转。UART 与 SPI 都「是」Device，框架遍历 Device * 列表并调用各自的 send()，无需 switch(dev_type)。

要点

单继承：首成员嵌入（demo02_inherit）：

struct Device {
    const char *name;
    struct DevOps *ops;
};

struct UartDev {
    struct Device base;   /* 必须第一个成员 */
    uint32_t    reg_base;
    int         baudrate;
};

struct SpiDev {
    struct Device base;
    int         cs_pin;
};

/* 向上转型：UartDev* → Device* */
struct UartDev uart = { .base = { .name = "uart0" }, .baudrate = 115200 };
struct Device *dev = (struct Device *)&uart;

多态：DevOps 虚表（demo03_polymorphism）：

struct DevOps {
    int (*init)(struct Device *dev);
    int (*send)(struct Device *dev, const void *buf, size_t len);
    int (*recv)(struct Device *dev, void *buf, size_t len);
};

static struct DevOps uart_ops = {
    .init = uart_init,
    .send = uart_send,
    .recv = uart_recv,
};

static struct DevOps spi_ops = {
    .init = spi_init,
    .send = spi_send,
    .recv = spi_recv,
};

/* 运行时分派 */
int device_send(struct Device *dev, const void *buf, size_t len) {
    if (!dev || !dev->ops || !dev->ops->send)
        return -1;
    return dev->ops->send(dev, buf, len);
}
步骤 操作
定义基类 struct Device + 公共字段
定义 ops struct DevOps 函数指针表
定义子类 首成员 struct Device base + 私有字段

8.2

.4 虚函数与纯虚函数

本节讲什么

C++ 虚函数允许子类覆盖父类方法；纯虚函数（= 0）强制子类实现，父类不可实例化——即抽象类。C 中对应物是 ops 结构体里的函数指针：有默认 stub 的为「虚函数」，置 NULL 且调用前检查的为「纯虚」；整个只定义 ops、不提供具体 send 实现的 Device 框架即抽象类。

要点

虚函数表（vtable）在 C 中的形态：

struct DevOps {
    int (*init)(struct Device *dev);      /* 可选：可有 weak 默认 */
    int (*send)(struct Device *dev, const void *buf, size_t len);
    int (*recv)(struct Device *dev, void *buf, size_t len);
    void (*shutdown)(struct Device *dev); /* 纯虚：必须子类实现或 NULL */
};
C++ 概念 C 实现
虚函数 ops 指针 + 默认 weak 实现
纯虚函数 ops 槽为 NULL，框架调用前检查
vtable 指针 dev->ops 指向静态 uart_ops
抽象类 只暴露 API，无具体 struct XxxDev 实例化

纯虚：调用前检查：

int device_shutdown(struct Device *dev) {
    if (!dev->ops || !dev->ops->shutdown) {
        fprintf(stderr, "shutdown not implemented\n");
        return -ENOTSUP;
    }
    dev->ops->shutdown(dev);
    return 0;
}

静态 ops 表 vs 每对象 ops：

/* 常见：所有 uart 实例共享 uart_ops */

/* 少见：每对象不同 ops（运行时替换策略） */

  • DPDK eth_dev_ops：rx_pkt_burst 必填，stats_reset 可选
  • ops 通常 const 静态全局，放 .rodata，多实例共享，节省内存
  • 函数指针调用无法内联，热路径可用 static inline 包装 + 直接调用已知类型

8.3

.2 链表的抽象与封装

本节讲什么

内核侵入式链表（intrusive list）把 struct list_head 嵌入宿主对象，通过 list_entry / container_of 遍历。链表操作被封装进 list_add、list_del、list_for_each_entry 宏，驱动作者无需手写 next/prev 指针逻辑——这是 C 里「容器类」的经典抽象。

要点

嵌入与遍历：

struct uart_port {
    struct list_head list;   /* 链表节点 — 「成员」 */
    int              port_id;
    void __iomem    *membase;
};

static LIST_HEAD(uart_ports);   /* 链表头 */

/* 注册：封装 add */
void uart_port_register(struct uart_port *port) {
    list_add_tail(&port->list, &uart_ports);
}

/* 遍历：封装 iterator */
struct uart_port *p;
list_for_each_entry(p, &uart_ports, list) {
    pr_info("port %d\n", p->port_id);
}

container_of 本质（ch06 6.4）：

#define list_entry(ptr, type, member) \
    container_of(ptr, type, member)

/* ptr 指向 list 成员 → 算出 uart_port 首地址 */
API 作用
INIT_LIST_HEAD 初始化空链
list_add / list_add_tail 头插 / 尾插
list_del 摘除节点（需再 INIT 或 add）
list_empty 判空
list_for_each_entry_safe 遍历中可删除

封装收益：

  • 同一套 list 代码驱动 task_struct、file、device 等所有子系统
  • 宿主 struct 可有多个 list_head 成员，挂到不同链表（如 device 的 bus_list 与 driver_list）

  • hlist（单指针哈希链）是变种，用于大哈希表

  • 摘除后节点：list_del + INIT_LIST_HEAD 防 use-after-free

  • 用户态 demo 可复刻 mini list.h 理解宏展开

内核 list_head 泛型链表的核心：

  1. 侵入式设计：链表节点 struct list_head 嵌入到任意结构体中，而非外部维护指针
  2. container_of：从 list_head * 反推包含它的结构体指针

    struct my_chip *chip = devm_kzalloc(dev, sizeof(*chip), GFP_KERNEL);

常见陷阱

  1. dev_set_drvdata 在 probe 失败路径未清理 → 悬垂指针 probe 中 devm_kzalloc 分配 chip 后 dev_set_drvdata(dev, chip)。若 probe 后续步骤失败返回错误码，框架不会自动清 drvdata——dev->driver_data 仍指向已释放的 chip。remove 或其他回调若取 dev_get_drvdata 即 use-after-free。正确：失败路径显式 dev_set_drvdata(dev, NULL)，或全程用 devm_* 确保自动释放。

  2. devm_* 资源在 probe 中途失败时不一定按期望顺序释放 devm_kzalloc、devm_ioremap、devm_request_irq 注册到设备 devres 链表，probe 失败时框架倒序释放。但有副作用的资源（如已使能的中断、已注册的 sysfs 节点）的逆操作可能不在 devres 中——必须用 devm_add_action 注册自定义清理。坑：request_irq 成功但后续 iounmap 失败，中断仍开 → 误以为 devm 全自动是错的。

  3. parent 层次误用导致 sysfs 死锁或电源管理顺序错乱 device_register 时设 parent 形成 /sys/devices/... 树。电源管理（suspend/resume）按树深度优先遍历——子设备先 suspend、后 resume。若把"逻辑设备"挂错 parent（如把虚拟网卡挂到 USB 设备下），会在 USB 父设备 suspend 后仍访问子设备 → 崩溃。约定：parent 必须是物理或电源控制关系上的上游设备，不能按"逻辑相关"随便挂。

自测题

1.（选择） devm_kzalloc 与 kzalloc 的关键区别？ - A. devm_* 性能更高 - B. devm_* 绑定设备生命周期，设备释放时自动释放 - C. devm_* 不能用于中断上下文 - D. devm_* 只能分配小内存

答案

B。devm_* 系列把分配的资源注册到 struct device 的 devres 链表，设备 device_unregister 或 probe 失败时自动逆序释放——避免手动 kfree 遗漏导致泄漏。性能略低（维护链表），但可靠性大幅提升，是驱动首选。中断上下文限制二者相同（都不能 sleep）。大小无限制，但极大块用 vmalloc / devm_vmalloc。

2.（判断） probe 返回非零错误码时，框架会自动调用 remove 清理。

答案

错。probe 失败时框架不会调 remove——remove 只在设备已绑定驱动后 unregister 时调用。probe 失败的清理责任在 probe 函数本身：必须逆序释放已申请的资源（或用 devm_* 让框架兜底）。误以为"框架会调 remove"导致资源泄漏是驱动开发常见坑。probe 成功后才会把设备加入 driver_bound 链表，remove 才会被触发。

3.（踩坑） 驱动 probe 中：

chip = devm_kzalloc(dev, sizeof(*chip), GFP_KERNEL);
dev_set_drvdata(dev, chip);
ret = devm_request_irq(dev, irq, handler, 0, name, chip);
if (ret) return ret;            /* ① 中断已注册 */
ret = register_chrdev(...);     /* ② 失败 */
if (ret) return ret;

probe 在 ② 失败后返回。设备移除时用户态已无引用，但中断仍会触发——为什么？如何修？

答案

register_chrdev 不是 devm 资源——probe 失败时 devm_* 链表逆序释放（devm_request_irq 会被注销），但 register_chrdev 不会自动注销。等等——题述"中断仍会触发"实际不会发生，因为 devm_request_irq 是 devm 的，会自动 free_irq。真正坑在：如果中断 handler 已触发并 schedule_work，probe 失败时 work 仍在队列里，worker 执行时访问已释放的 chip → use-after-free。 修复：

ret = register_chrdev(...);
if (ret) {
    devm_free_irq(dev, irq, chip);   /* 显式提前释放 */
    cancel_work_sync(&chip->work);    /* 等 work 完成 */
    return ret;
}

教训：devm_* 自动释放按设备生命周期，但异步任务（work/timer）可能在释放后仍访问资源——必须显式 cancel。

8.3

.4 总线设备模型

本节讲什么

总线（bus）是设备与驱动的匹配枢纽：struct bus_type 定义 match（是否配对）、probe（绑定后初始化）、remove（解绑）回调。设备挂 bus_list，驱动挂 driver_list，内核自动扫描配对——这是 Linux plug-and-play 的 OOP 核心：框架代码不变，新驱动只填 ops。

要点

总线结构（概念）：

struct bus_type {
    const char *name;
    int (*match)(struct device *dev, struct device_driver *drv);
    int (*probe)(struct device *dev);
    int (*remove)(struct device *dev);
    struct list_head devices;
    struct list_head drivers;
};

platform 总线典型 match：

/* 按 name 或 OF compatible 匹配 */
static int platform_match(struct device *dev, struct device_driver *drv) {
    struct platform_device *pdev = to_platform_device(dev);
    return strcmp(pdev->name, drv->name) == 0;
}
总线 典型设备 match 依据
platform SoC 内置 UART 设备名 / DT compatible
pci 网卡 Vendor/Device ID
usb U 盘 VID/PID + interface
i2c 传感器 7-bit 地址 + OF

注册时序：

platform_driver_register(drv)  ─┐
platform_device_register(dev) ─┼→ bus 核心 match → probe
                                ┘
driver_unregister / device_unregister → remove
  • struct device_driver 含 probe/remove，与 8.2.4 ops 同类：驱动填函数指针，核心调度
  • sysfs：/sys/bus/platform/devices/、/sys/bus/platform/drivers/ 反映链表状态
  • 模块卸载必须 remove 干净，否则 dangling device

常见陷阱

  1. probe 中分配的资源在 remove 不对应释放 → 泄漏 总线模型约定 probe/remove 配对：probe 申请什么，remove 必须释放什么。漏掉一个 iounmap、free_irq、cdev_del 即泄漏。devm_ 让大部分资源自动释放，但非 devm 资源*（如 register_chrdev_region、class_create）必须手动清理。代码 review 时数 probe 中的申请数 vs remove 中的释放数对账。

  2. match 返回值误用 → 永远不匹配或匹配错误驱动 bus_type.match 返回 0 表示不匹配，非 0 表示匹配——不是返回错误码。新手写成 return -ENODEV;（实际是负数，被当作"匹配成功"），导致所有设备都误绑定。正确：return strcmp(...) == 0 ? 1 : 0; 或直接 return !strcmp(...);。

  3. 模块卸载时 driver_unregister 不等 remove 完成 → use-after-free driver_unregister 触发已绑定设备的 remove 回调，但异步——driver_unregister 可能在 remove 完成前返回。若模块立即卸载（module_put 后），remove 仍在执行即 use-after-free。框架用 module_get(THIS_MODULE) 在 probe 时增加引用计数，remove 后释放——但自己注册的 work/timer 不在框架保护内，必须 cancel_work_sync。

自测题

1.（选择） platform_match 在以下哪种情况返回"匹配"？ - A. strcmp(pdev->name, drv->name) == 0 - B. pdev->id == drv->id - C. pdev->bus == drv->bus - D. 任意 OF compatible 字符串匹配

答案

A 和 D（实际内核支持多策略）。platform_match 优先级： 1. OF match（Device Tree compatible）——现代嵌入式首选 2. ACPI match（x86 / 服务器） 3. id_table 显式匹配表（传统） 4. name 字段 strcmp(pdev->name, drv->name) 返回 1 = 匹配，0 = 不匹配。返回负数被当作"匹配"是常见 bug——必须用 return X ? 1 : 0;。

2.（判断） platform_driver_register 后立即 platform_device_register，绑定顺序无关紧要。

答案

对——绑定是双向触发。无论先注册 driver 还是先注册 device，框架在每次注册后扫描对端链表尝试 match。driver_register 后扫描 bus 上的设备链表，device_register 后扫描 driver 链表。两次都会触发 probe。坑在模块加载顺序：若 driver 模块未加载时 device 已注册，device 处于"unbound"状态；driver 加载后自动 probe——但用户态可能在这间隙访问设备失败。

3.（踩坑） 驱动 remove 中忘了 free_irq，模块卸载后系统调用 handler 时崩溃。但 handler 代码已在 module_exit 时被释放。为何框架没保护？

答案

free_irq 必须由驱动自己调，框架不会代劳——IRQ 注册是设备行为，不是总线模型核心职责。remove 漏 free_irq： 1. IRQ 仍指向已释放的 handler 代码地址。 2. 中断触发时 CPU 跳到无效地址 → oops。 框架的保护仅覆盖 probe/remove 调用本身（通过 module_get），不覆盖驱动注册的 IRQ/timer/work。修复：用 devm_request_irq 替代 request_irq——devm 在设备释放时自动 free_irq。这是现代驱动推荐做法。

.1 继承与私有指针

本节讲什么

除首成员继承外，C 常用 PIMPL（pointer to implementation）：公开 struct 只含一个 void *priv 或 struct xxx_private *，真实字段在 .c 堆分配。子类「继承」时 priv 指向含基类状态的结构。内核 net_device 的 ml_priv、ieee80211_ptr 等即是把协议私有数据与通用 netdev 分离。

要点

私有指针模式：

/* public.h */
typedef struct widget widget_t;

widget_t *widget_create(void);
void      widget_destroy(widget_t *w);
int       widget_draw(widget_t *w);

/* widget.c */
struct widget_private {
    int x, y;
    struct theme *theme;   /* 「基类」状态也可放 priv */
};

struct widget {
    struct widget_private *priv;   /* 仅一个指针对外可见 */
};

widget_t *widget_create(void) {
    widget_t *w = kzalloc(sizeof(*w), GFP_KERNEL);
    w->priv = kzalloc(sizeof(*w->priv), GFP_KERNEL);
    return w;
}
方式 优点 缺点
首成员继承 零间接、可 container_of 子类布局暴露于同一头文件
私有指针 完全隐藏大小与字段 多一次间接；需配对 alloc/free
混合 公开基类 + priv 扩展 内核 netdev 常见

继承 + priv：

struct uart_dev {
    struct Device base;           /* 公开继承，框架可见 */
    struct uart_private *priv;    /* 寄存器映射等隐藏 */
};
  • dev_get_drvdata 等价于在 struct device 上挂 priv
  • 用户态 demo01 不透明类型是 priv 的极端形式（整个 struct 都隐藏）
  • 避免在头文件暴露 struct xxx_private，否则封装失效

常见陷阱

  1. priv 双重所有权 → 双 free 或泄漏 PIMPL 模式中 widget_create 分配 widget 和 priv 两块。widget_destroy 必须两步释放：先 priv->theme 等子资源、再 kfree(priv)、最后 kfree(w)。漏 kfree(priv) 泄漏；重复 kfree(priv)（如 priv 被 widget_destroy 释放后用户又调用 priv_free）双 free。约定：priv 生命周期严格由 owner 管理，外部代码只能通过 accessor 读取，不能持有 priv 指针。

  2. 首成员继承的 container_of 必须基类在前 → 改字段顺序即崩 struct platform_device { struct device dev; ... } 的 dev 必须是首成员，否则 container_of 算偏移时 dev 与"被当作基类"的语义不匹配。坑：有人重构时把 dev 移到中间位置——(struct device *)pdev 仍指向 pdev 首地址，但 dev 已不在那里，所有 dev->xxx 访问到错位字段。编译期不报错，运行时静默错乱。约定：基类成员永远在派生类首位置，且用 container_of 而非强转。

  3. priv 指针在多线程下被并发修改 → 数据竞争 widget->priv 通常 init 后只读，但若设计成"运行时切换 priv"（如运行时切换实现策略），需加锁。新手误以为"指针赋值原子"省略同步，在弱内存序架构（ARM/POWER）下读到部分更新的指针。正确：要么 init 后不可变（推荐），要么用 RCU 或 atomic_load 保护。

自测题

1.（选择） PIMPL 模式相比"首成员继承"的主要优势？ - A. 性能更高（少一次间接） - B. 完全隐藏内部字段，ABI 解耦 - C. 内存占用更小 - D. 不需要 container_of

答案

B。PIMPL 头文件只暴露 struct widget 前向声明 + void *priv（或不透明指针），具体字段在 .c 文件中——ABI 解耦：改 priv 内部字段不破坏二进制兼容（只需重编 .c，不影响使用方）。代价是多一次指针间接（性能略低）。首成员继承性能更好但子类布局暴露于头文件。现代 C 库（glib Qt 私有）大量用 PIMPL。

2.（判断） struct platform_device { struct device dev; int id; }; 后 (struct device *)pdev 等价于 &pdev->dev。

答案

对——但前提是 dev 是首成员。C 标准保证结构体首成员地址等于结构体地址，所以 (struct device *)pdev == &pdev->dev。坑：若有人把 dev 移到 int id; 之后，强转仍指向首地址（id 处），但 &pdev->dev 指向偏移 4——两者不再相等，强转版本访问到错位字段。约定：永远用 &pdev->dev 显式取地址，不用强转——表达意图更清楚，重构安全。

3.（踩坑） 头文件 struct widget { struct widget_private *priv; };，.c 中 struct widget_private { int x; struct theme *theme; };。用户拿到 widget_t *w 后想"直接访问 w->priv->x"——但 widget_private 在 .c 中定义，头文件不可见。用户改为 ((int *)w->priv)[0]。这种做法有什么风险？

答案

多重风险： 1. 耦合私有布局——访问方硬编码了 x 在 priv 首字段，一旦 priv 字段顺序调整立即崩。 2. 类型不安全——int * 强转绕过编译器类型检查，priv 若首字段是 struct theme *（指针），int 读到一半。 3. ABI 假象——看似能跑，实际依赖"priv 首字段是 int"这一未文档化约定，重构即破。 正确做法： - 在头文件提供 accessor：int widget_get_x(widget_t *w); - 若必须暴露性能敏感字段，用 static inline 包装，priv 仍隐藏。 - 内核 struct net_device 用 netdev_priv() 取 priv，但 priv 内部布局由协议代码独占——不鼓励跨模块直接访问。

4.（应用） 用"首成员继承 + 私有指针"设计一个 UART 驱动：基类 struct Device 由框架定义，子类 struct uart_dev 暴露给框架，priv 隐藏寄存器映射。给出代码骨架并说明封装边界。

答案 
/* device.h (框架公开) */
struct Device {
    const struct device_ops *ops;   /* 虚表 */
    const char *name;
};
struct device_ops {
    int (*init)(struct Device *);
    void (*shutdown)(struct Device *);
};

/* uart.h (驱动公开) */
#include "device.h"
struct uart_dev {
    struct Device base;              /* 首成员继承 */
    /* 公开字段：仅框架关心的 */
    int port_no;
    /* priv 隐藏寄存器细节 */
    struct uart_regs *regs;
};
extern const struct device_ops uart_ops;

/* uart.c (驱动私有) */
struct uart_regs {                   /* 不在头文件 */
    volatile uint32_t ctrl;
    volatile uint32_t data;
    volatile uint32_t status;
};

static int uart_init(struct Device *d) {
    struct uart_dev *u = container_of(d, struct uart_dev, base);
    u->regs->ctrl = CTRL_ENABLE;
    return 0;
}
static void uart_shutdown(struct Device *d) {
    struct uart_dev *u = container_of(d, struct uart_dev, base);
    u->regs->ctrl = 0;
}
const struct device_ops uart_ops = {
    .init = uart_init, .shutdown = uart_shutdown,
};

/* 框架调用：统一通过基类 */
struct Device *dev = get_device_by_name("uart0");
dev->ops->init(dev);   /* 多态：实际调 uart_init */

封装边界： - 框架只见 struct Device + ops——可换 SPI/I2C/USB 设备。 - 驱动通过 container_of 取回 uart_dev，访问自身 priv。 - 用户只能 dev->ops->init(dev)，碰不到 regs——寄存器细节完全隐藏。 - struct uart_regs 不在头文件——改寄存器布局只重编 uart.c，框架与用户零影响。

8.4

.3 继承与接口

本节讲什么

C 不支持多重继承，但可通过 多个 ops 指针（mixin / 接口分离）让对象实现多种能力：通信走 CommOps，电源走 PowerOps，与主 DevOps 并列。Linux dev_pm_ops、dma_ops 即独立接口 struct，挂到 device 上由子系统分别调用——避免一个巨型 ops 表。

要点

多接口布局（demo05_multi_iface）：

struct CommOps {
    int (*send)(void *ctx, const void *buf, size_t len);
    int (*recv)(void *ctx, void *buf, size_t len);
};

struct PowerOps {
    int (*suspend)(void *ctx);
    int (*resume)(void *ctx);
};

struct SmartSensor {
    struct Device  base;       /* 主继承线 */
    struct CommOps *comm;      /* 接口 1 */
    struct PowerOps *power;    /* 接口 2 */
    void           *ctx;
};

static struct CommOps i2c_comm_ops = { .send = i2c_send, .recv = i2c_recv };
static struct PowerOps generic_pm_ops = { .suspend = pm_suspend, .resume = pm_resume };

/* 初始化 */
sensor.comm  = &i2c_comm_ops;
sensor.power = &generic_pm_ops;
设计 说明
单一巨型 ops 简单驱动 OK；子系统交叉时臃肿
多 ops 指针 各子系统只依赖自己的接口头文件
首成员 + 多 ops 内核 device + driver + class 组合

内核示例：

struct device {
    struct dev_pm_ops *pm;      /* 电源管理接口 */
    struct dev_dma_ops *dma;    /* DMA 映射接口 */
    /* bus、driver、class 各管一块 */
};
  • 接口 struct 通常 只含函数指针，无数据 — 类似 Java interface
  • 同一 PowerOps 可被多种设备 共享（静态全局表）
  • 调用方检查：if (dev->pm && dev->pm->suspend) dev->pm->suspend(dev);

8.5

Linux内核中的OOP思想：多态

本节讲什么

多态是同一调用点根据对象类型执行不同代码。内核与 DPDK 中无处不在：VFS 根据打开的文件类型调用不同 read；网卡驱动填 net_device_ops；DPDK 用 eth_dev_ops 的 rx_pkt_burst/tx_pkt_burst 在 poll 模式驱动间切换。本节串联 8.2.3–8.2.4 的 ops 表与真实子系统。

要点

VFS：file_operations 虚表：

struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    /* ioctl, mmap, poll ... */
};

/* 系统调用层 */
static ssize_t vfs_read(struct file *file, ...) {
    if (file->f_op->read)
        return file->f_op->read(file, ...);
    return -EINVAL;
}

字符设备注册：

static struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .read  = my_read,
    .write = my_write,
    .open  = my_open,
};

cdev_init(&cdev, &my_fops);
cdev_add(&cdev, devno, 1);

DPDK eth_dev_ops（示意）：

struct eth_dev_ops {
    eth_rx_burst_t rx_pkt_burst;   /* 必填 — 纯虚 */
    eth_tx_burst_t tx_pkt_burst;
    eth_dev_configure_t dev_configure;
    eth_dev_start_t dev_start;
    /* stats, promiscuous, ... */

/* 应用统一入口 */

devices[i]->ops->send(devices[i], buf, len);
  • ops 表在 编译期 填好，运行期 仅间接调用 — 无 C++ vtable 指针 per object 开销（通常共享静态 ops）
  • RCU 替换 ops 需内核同步机制；DPDK 热路径避免运行时改 ops
  • module_get(THIS_MODULE) 防 ops 执行时模块卸载

常见陷阱

  1. ops 函数指针为 NULL 时直接调用 → NULL 指针解引用崩溃 file->f_op->read(...) 若 read 为 NULL（驱动未实现），直接调用即解引用 NULL 函数指针 → oops。VFS 框架在 vfs_read 中先判 NULL 再调用：if (file->f_op->read) return file->f_op->read(...); else return -EINVAL;。但自定义 ops 表没有这种保护——驱动作者忘了判 NULL 即崩。约定：ops 表必填字段用 WARN_ON(!ops->xxx) 在注册时检查；可选字段调用方判 NULL。

  2. ops 表被运行时修改 → 数据竞争 正常 ops 是 static const，编译期固定。若设计成"运行时切换 ops"（如协议状态机切换），多核并发调用 ops 时读到部分更新的指针——尤其在弱内存序架构（ARM/POWER）上。修复：用 RCU（rcu_assign_pointer + rcu_dereference）保护 ops 切换；或 ops 在 init 后不可变。DPDK 数据面热路径禁止运行时改 ops——切换 ops 在停队列后做。

  3. 模块卸载时 ops 仍在执行 → use-after-free 驱动模块卸载时，file_operations 代码段被释放，但若有进程正在 read 该设备文件，read 函数返回时访问已释放代码 → oops。框架用 module_get(THIS_MODULE)（fops->owner = THIS_MODULE）保护：open 时增加模块引用计数，release 时减少，卸载需等计数归零。但：内核其他路径（如内核线程、workqueue）调 ops 不一定走 open/release——驱动自己必须保证卸载前取消所有异步调用。

自测题

1.（选择） 内核 file_operations 与 C++ vtable 的关键区别？ - A. vtable 是每个对象一份，ops 是多个对象共享一份 - B. vtable 自动生成，ops 手动填 - C. vtable 性能更高 - D. ops 只能用于内核

答案

A。C++ 每个对象含一个 vptr 指向 vtable，多对象多 vptr；内核 file_operations 通常是 static const 结构，所有同类对象共享同一份 ops 表，对象自身不存指针——节省内存（每个 struct file 不含 ops 字段，只 f_op 一个指针）。性能上间接调用一次 vs 两次（vptr + vtable 偏移）几乎无差。B 错：vtable 由编译器生成，ops 也是编译期填好（ designated init）。

2.（判断） file->f_op->read(file, ...) 调用前必须判 file->f_op->read != NULL。

答案

对，在框架代码中。VFS 的 vfs_read 显式判 NULL：

if (file->f_op->read)
    return file->f_op->read(file, buf, count, pos);
else if (file->f_op->read_iter)
    return new_sync_read(file, ...);
else
    return -EINVAL;

驱动内部调用自家 ops 可省略判 NULL（自家 ops 一定填了），但跨子系统调用必须判——你不知道对方驱动是否实现了某回调。坑：新手照搬 file->f_op->read(...) 不判，遇字符设备未实现 read 即崩。

3.（踩坑） 驱动模块卸载后 5 秒，系统崩溃在 my_read 函数地址。fops.owner = THIS_MODULE 已设置。为什么没保护住？

答案

异步调用绕过了 owner 引用计数。fops->owner 保护的是通过 open/release 走的同步路径——open 时 try_module_get 增计数，卸载需等所有打开的 fd 关闭。但： 1. 内核线程/workqueue 直接调 f_op->read 不走 open，不增计数。 2. 卸载时模块代码被释放，但已 schedule 的 work 仍排队，worker 执行时跳到已释放地址 → oops。 3. remove 时若 cancel_work_sync 漏掉，work 在模块卸载后执行即 use-after-free。 修复：remove 中 cancel_work_sync 等所有 work 完成，再 unregister_xxx 让框架阻止新调用。fops.owner 不保护异步路径——驱动自己负责。

4.（应用） 用 ops 表实现一个"协议无关"网络发包接口：上层 net_send(skb) 根据网卡类型调不同驱动。给出 ops 定义和注册骨架。

/* netdev.h */
struct net_device;
struct netdev_ops {
    int (*open)(struct net_device *);
    int (*stop)(struct net_device *);

    struct net_device_stats *(*get_stats)(struct net_device *);
};

struct net_device {
    char name[16];
    const struct netdev_ops *ops;    /* 多态入口 */
    void *priv;
};

/* 上层统一入口 */
int net_send(struct net_device *dev, struct sk_buff *skb) {
    if (!dev->ops || !dev->ops->start_xmit)
        return -ENOTSUP;
    return dev->ops->start_xmit(dev, skb);
}

/* my_eth.c — Intel 网卡驱动 */
static int igb_open(struct net_device *dev) { /* ... */ }
