题目 1： 以下 Makefile 规则中 $@ 和 $< 分别代表什么？

prog: main.c util.c
    gcc -o $@ $<
参考答案

$@ 代表目标文件名（prog），$< 代表第一个依赖文件（main.c）。注意此 Makefile 只编译 main.c 而忽略 util.c——如果 util.c 有修改不会触发重新编译。正确的写法应该是 gcc -o $@ main.c util.c 或用变量。

题目 1： IDE（如 VS Code）和命令行编译各有什么优缺点？

1.2

.2 使用 gcc 编译 C 源程序

本节讲什么

GCC 四阶段与高频参数 —— ch04 前置；交叉编译入门。

要点

四阶段

gcc -E test.c -o test.i      # 预处理
gcc -S test.i -o test.s      # 编译 → 汇编
gcc -c test.s -o test.o      # 汇编 → 目标文件
gcc test.o -o test           # 链接 → 可执行文件

常用参数

参数 作用
-Wall -Wextra 全开警告（强制）
-std=c11 语言标准
-O0 / -O2 调试 / 发布
-g 调试符号（gdb）
-c 只编译不链接 
gcc -Wall -Wextra -std=c11 -g -O0 main.c -o app

交叉编译

arm-linux-gnueabihf-gcc -g main.c -o app.arm
file app.arm
  • 通过 buildenv.sh 设置 CROSS_COMPILE（1.6）

实操

对比 -O0 与 -O2 的 objdump -d 差异（1.4）。

与后续衔接

代码自测

题目 1： 以下 gcc 命令的四个阶段分别生成什么文件？

gcc -E main.c -o main.i    # 阶段1
gcc -S main.i -o main.s    # 阶段2
gcc -c main.s -o main.o    # 阶段3
gcc main.o -o main          # 阶段4
参考答案
  1. 预处理（-E）：展开宏、包含头文件、处理条件编译 → main.i
  2. 编译（-S）：C 代码翻译为汇编代码 → main.s
  3. 汇编（-c）：汇编代码翻译为机器码 → main.o（目标文件）
  4. 链接（无特殊标志）：目标文件 + 库 → 可执行文件 main

一步编译：gcc main.c -o main 等价于上面四步。

1.2

.3 使用 make 编译程序

本节讲什么

Makefile 语法：目标、依赖、自动变量 —— 多文件工程模板。

要点

CC      ?= gcc
CFLAGS  ?= -Wall -Wextra -std=c11 -g
LDFLAGS ?=

app: main.o util.o
    $(CC) $(LDFLAGS) -o $@ $^

main.o: main.c util.h
    $(CC) $(CFLAGS) -c $< -o $@

util.o: util.c util.h
    $(CC) $(CFLAGS) -c $< -o $@

.PHONY: clean
clean:
    rm -f *.o app
自动变量 含义
$@ 目标
$< 首依赖
$^ 全部依赖 
make all
make clean
  • .PHONY` 声明伪目标
  • 大型工程见 1.2.4 CMake

与后续衔接

Demo04 多文件 Makefile；内核 Kbuild 同依赖思想。

代码自测

题目 1： 以下 Makefile 的执行逻辑是什么？最终生成的可执行文件叫什么？

main: main.o utils.o
    gcc main.o utils.o -o main

main.o: main.c utils.h
    gcc -c main.c

utils.o: utils.c utils.h
    gcc -c utils.c
参考答案

执行 make 时： 1. 默认目标 main 依赖 main.o 和 utils.o 2. 检查 main.o：若 main.c 或 utils.h 比 main.o 新，则执行 gcc -c main.c 3. 检查 utils.o：同理 4. 若任一 .o 被更新，重新链接生成 main

关键：Makefile 通过时间戳判断是否需要重新编译。clean 目标需 make clean 显式调用。

.4 CMake 基础

本节讲什么

CMakeLists.txt 生成 Makefile —— 跨平台、大型工程标准入口。

要点

cmake_minimum_required(VERSION 3.16)
project(demo C)

set(CMAKE_C_STANDARD 11)

cmake ..

步骤 作用
cmake .. 生成构建文件
make 编译
  • 交叉编译：cmake -DCMAKE_C_COMPILER=arm-linux-gnueabihf-gcc ..
  • 产物放 build/，源码树干净

与后续衔接

DPDK/内核用自有构建系统；CMake 用于用户态练习工程。

代码自测

题目 1： 以下 CMakeLists.txt 的每一行各有什么作用？

cmake_minimum_required(VERSION 3.10)
project(hello C)
add_executable(hello main.c utils.c)
target_include_directories(hello PRIVATE include/)
参考答案
  • cmake_minimum_required：指定最低 CMake 版本
  • project(hello C)：项目名 hello，语言 C
  • add_executable(hello main.c utils.c)：编译 main.c 和 utils.c 生成可执行文件 hello
  • target_include_directories：添加头文件搜索路径 include/，PRIVATE 表示仅编译时可见

题目 1： 版本控制系统解决什么问题？集中式（SVN）和分布式（Git）有什么区别？

1.4

ELF 二进制分析工具

本节讲什么

nm / readelf / objdump / size / hexdump —— 查看符号、段布局、反汇编；DPDK & Linux 内核二进制必备三件套。

三者分工

工具 核心用途 主要看什么
nm 符号表 函数、全局变量，哪些导出、未定义
readelf ELF 元信息 程序头、节、符号表、重定位、dynamic 段
objdump 反汇编 机器码→汇编；段内容、重定位

关键：GDB 是运行时调试；nm/readelf/objdump 是静态分析，程序不用跑，直接分析磁盘上的二进制文件。

速查

# nm —— 查符号
nm -D libdpdk.so | grep rte_     # DPDK 导出 API
nm -u mod.ko                     # 内核模块依赖的外部符号

# readelf —— ELF 结构
readelf -h a.out                 # ELF 头（类型、架构、入口）
readelf -S a.out                 # 所有节 .text .data .bss
readelf -l a.out                 # 程序段（LOAD 视图）
readelf -r mod.ko                # 重定位信息（.ko 灵魂）
readelf -d libdpdk.so            # dynamic 段（依赖哪些 .so）

# objdump —— 反汇编
objdump -d a.out                 # 反汇编 .text
objdump -S a.out                 # 源码 + 汇编混排（需 -g）
objdump -d --disassemble=main a.out  # 只看指定函数

# 其他
size a.out                       # text data bss 十进制
hexdump -C a.out | head          # 原始字节

nm 符号类型速记

标记 含义
T/t 代码段函数（大写=全局，小写=static）
D/d 已初始化数据
B/b BSS 未初始化数据
U 未定义（需要外部链接提供）

.1 GDB 基础概念与启动

GDB 是什么

GDB（GNU Debugger）是 GNU 项目下的命令行程序调试器，主要用来调试 C/C++、汇编等编译型程序，在 Linux/Unix 环境用得最多。

能力概览

能力 说明
启动程序 可带上参数运行待调试程序
设置断点 程序跑到断点就暂停
单步执行 一条语句 / 一条汇编指令，观察程序怎么走
查看/修改内存 寄存器、变量、任意内存地址
崩溃分析 段错误 core dump，定位崩溃在哪一行
attach 进程 调试正在运行的进程（不停机排查）

GDB vs GDP：GDB 是 GNU 调试器（程序员工具）；GDP 是国内生产总值（经济指标）。完全无关，别搞混。

编译须 -g

gcc -g test.c -o test    # -g 把调试信息（DWARF）打进可执行文件
gdb ./test

不加 -g，GDB 看不到源码行号、变量名，只能看汇编。

-g 做了什么

-g 让 gcc 在可执行文件中嵌入 DWARF 调试信息：

信息 作用
源码行号 → 机器地址映射 断点能停在源码某一行
变量名 → 栈/寄存器位置映射 print var 能找到变量
类型信息（struct/union 定义） GDB 知道怎么解析 *ptr
函数名 → 地址映射 break main 能找到入口 
# 验证 DWARF 信息是否存在
readelf -S ./app | grep debug      # 有 .debug_info / .debug_line 段说明 -g 生效
objdump --dwarf=info ./app | head  # 查看具体调试信息

-g 与优化级别

gcc -g -O0 main.c -o app_debug    # 调试用：不优化，变量全在
gcc -g -O2 main.c -o app_release  # 生产用：优化但保留调试信息
组合 效果
-g -O0 最佳调试体验，变量全可查，行号准确
-g -O2 可调试但变量可能被优化掉，行号会跳跃
无 -g 只有汇编，无源码行号
-g -O3 激进优化，内联展开后基本不可读

启动 GDB 的几种方式

1. 直接启动

gdb ./app                       # 加载程序但不运行
(gdb) run                       # 在 GDB 内启动程序
(gdb) run arg1 arg2             # 带参数运行
(gdb) run < input.txt           # 重定向 stdin

2. 调试正在运行的进程

gdb -p <PID>                    # attach 到进程
# 或
gdb ./app <PID>

3. 调试 core dump

gdb ./app core                  # 加载可执行文件 + core 快照
(gdb) bt                        # 直接看崩溃栈

4. 启动时执行命令

gdb -ex "break main" -ex "run" ./app    # 启动时设断点并运行
gdb -batch -ex "bt" ./app core          # 批处理模式：打印栈后退出（脚本用）

基本调试流程

一个完整的调试会话：

$ gcc -g -O0 -Wall main.c -o app
$ gdb ./app

(gdb) break main          # 在 main 函数打断点

(gdb) run                 # 开始运行
Starting program: ./app
Breakpoint 1, main () at main.c:10
10      int *p = NULL;

(gdb) next                # 下一行（跳过函数调用）
11      *p = 42;          # 下一行

(gdb) step                # 单步进入函数内部（如果有函数调用）

0x0000555555555155 in main () at main.c:11

GDB 界面模式

1.5

.2 GDB 断点与单步调试

断点（Breakpoint）

基本断点

(gdb) break main              # 在函数 main 处设断点
(gdb) break main.c:42         # 在 main.c 第 42 行设断点
(gdb) b main.c:42             # 简写 b
(gdb) b 42                    # 当前文件第 42 行

临时断点（Temp Breakpoint）

(gdb) tbreak main.c:50        # 命中一次后自动删除

用途：只想在第一次经过时停一下，后续不再断。

条件断点（Conditional Breakpoint）

(gdb) break main.c:42 if i == 100     # 当 i == 100 时才断
(gdb) break loop if count > 50        # 函数 loop 中 count > 50 时断
(gdb) condition 1 i == 100            # 给已有断点 1 加条件
(gdb) condition 1                     # 删除断点 1 的条件

用途：循环里第 N 次才出 bug，不用手动 continue 几百次。

断点管理

(gdb) info breakpoints        # 查看所有断点（简写 info b）
(gdb) delete 1                # 删除 1 号断点
(gdb) delete                  # 删除所有断点
(gdb) disable 1               # 禁用 1 号断点（不删，暂不生效）
(gdb) enable 1                # 重新启用
(gdb) clear main.c:42         # 清除 main.c 第 42 行的断点
命令 简写 作用
break b 设置断点
tbreak tb 临时断点（命中后自动删除）
info breakpoints i b 查看所有断点
delete d 删除断点
disable dis 禁用断点
enable en 启用断点
condition cond 设置/清除条件
clear — 清除指定位置断点

运行控制

(gdb) run                     # 从头开始运行程序
(gdb) run arg1 arg2           # 带参数运行
(gdb) continue                # 继续运行到下一断点
(gdb) continue 3              # 继续运行，跳过接下来 3 次断点命中
(gdb) kill                    # 杀死当前运行的程序（不退出 GDB）
(gdb) quit                    # 退出 GDB

单步执行

next vs step

命令 简写 行为
next n 下一行，跳过函数调用（函数内部不停）
step s 下一行，进入函数内部（逐行执行被调函数） 
10  int result = calculate(a, b);   // next → 直接到第 11 行
                                     // step → 进入 calculate() 内部第一行
11  printf("%d\n", result);

汇编级单步

(gdb) nexti                   # ni：下一条汇编指令（跳过 call）
(gdb) stepi                   # si：下一条汇编指令（进入 call）

用途：调试无源码的库函数、或 -O2 优化后行号不准时。

until

(gdb) until                   # 运行到当前循环结束（跳出 for/while 体）
(gdb) until main.c:50         # 运行到第 50 行

用途：不想在循环里一步一步走，直接跳到循环之后。

监视点（Watchpoint）

Watchpoint 不在某一行断，而是当某个表达式的值发生变化时断。

(gdb) watch count             # 当 count 的值被修改时暂停
(gdb) watch count == 100      # 当 count 变为 100 时暂停
(gdb) watch *ptr              # 监视指针指向的内存
(gdb) rwatch count            # 当 count 被**读取**时暂停
(gdb) awatch count            # 当 count 被**读或写**时暂停

用途： - 变量被意外篡改，但不知道在哪里改的 → watch var - 内存被踩 → watch *addr

(gdb) info watchpoints        # 查看所有 watchpoint
(gdb) delete 2                # 删除 2 号 watchpoint（和断点统一编号）

捕获点（Catchpoint）

(gdb) catch throw             # C++ 抛异常时断
(gdb) catch syscall write     # 调用 write 系统调用时断
(gdb) catch fork              # 调用 fork 时断
(gdb) catch exec              # 调用 exec 时断

用途：调试系统调用、fork/exec、C++ 异常。

实操示例：空指针调试

#include <stdio.h>

int main(void)
{
    int *p = NULL;
    *p = 42;           // 第 5 行：段错误
    printf("%d\n", *p);
    return 0;
}

$ gcc -g -O0 -o demo demo.c
$ gdb ./demo
(gdb) break main
(gdb) run
(gdb) next              # 走到 int *p = NULL
(gdb) next              # 走到 *p = 42 → SIGSEGV
(gdb) bt                # 看调用栈
(gdb) print p           # p = 0x0 → 空指针
(gdb) quit

常用命令速查

命令 简写 作用

tbreak tb 临时断点
run r 开始运行
continue c 继续到下一断点
next n 单步跳过

nexti ni 汇编级跳过

until u 跳出循环

catch — 系统调用/事件时断

.3 GDB 查看内存与变量

print：打印变量/表达式

(gdb) print p                 # 打印变量 p 的值
(gdb) print *ptr              # 打印指针指向的值
(gdb) print arr[0]            # 打印数组元素
(gdb) print arr               # 打印数组（显示前几个元素）
(gdb) print *arr@10           # 打印 arr 指向的 10 个元素
(gdb) print sizeof(struct A)  # 打印类型大小
(gdb) print 1+2*3             # 算术表达式
(gdb) print/x 255             # 十六进制输出 → 0xff
(gdb) print (char)65          # → 'A'

print 格式修饰符

修饰符 格式 示例
/x 十六进制 print/x 255 → 0xff
/d 十进制 print/d 0xff → 255
/t 二进制 print/t 10 → 1010
/o 八进制 print/o 64 → 0100
/c 字符 print/c 65 → 'A'
/f 浮点 print/f 0x40490fdb → 3.14159...
/a 地址 print/a 0x555555555155 → main
/s 字符串 print/s ptr → "hello"

打印数组

(gdb) print arr                # 只显示前几个元素
(gdb) set print elements 50    # 设置显示上限为 50 个元素
(gdb) print *arr@10            # 从 arr 开始打印 10 个元素
(gdb) print arr[2]@5           # 从 arr[2] 开始打印 5 个元素

修改变量值

(gdb) set var count = 100      # 把 count 改成 100
(gdb) set var *ptr = 42        # 把 ptr 指向的内存改成 42
(gdb) set var i = i + 1        # 表达式赋值

调试时不用改代码重新编译，直接在 GDB 里改值验证猜测。

examine：检查内存

x 命令按地址查看原始内存，是最强大的内存检查工具。

语法

x/NFU addr
参数 含义 可选值
N 显示几个单位 数字，如 16
F 显示格式 x(十六进制) d(十进制) t(二进制) c(字符) s(字符串)
U 单位大小 b(1字节) h(2字节/半字) w(4字节/字) g(8字节/双字)

示例

(gdb) x/16xb &buf              # 16 字节，十六进制，逐字节显示
(gdb) x/8xw &buf               # 8 个字（32位），十六进制
(gdb) x/4xg &buf               # 4 个双字（64位），十六进制
(gdb) x/16cb &buf              # 16 字节，字符显示
(gdb) x/s str                  # 以字符串形式显示
(gdb) x/16i $pc                # 从当前 PC 开始反汇编 16 条指令
(gdb) x/8xw $sp                # 查看栈顶 8 个字

示例输出

(gdb) x/16xb &buf
0x7fffffffe3f0: 0x48 0x65 0x6c 0x6c 0x6f 0x00 0x00 0x00
0x7fffffffe3f8: 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00

这就是 "Hello" 的 ASCII（48 65 6c 6c 6f 00）。

常用组合

命令 用途
x/16xb &var 看变量的逐字节十六进制
x/8xw &arr 看 int 数组
x/s ptr 看字符串
x/16i $pc 反汇编当前位置
x/8xg $sp 看栈（64 位）
x/16xb $sp 看栈（逐字节）

寄存器 含义

实操：调试结构体内存布局

#include <stdio.h>
struct A {
    char  c;     // 1 byte + 3 padding
    int   i;     // 4 bytes
    double d;    // 8 bytes
};
int main(void)
{
    struct A a = {'X', 42, 3.14};
    return 0;
}

(gdb) break main
(gdb) run
(gdb) next                     # 走过初始化
(gdb) print a                  # {c = 88 'X', i = 42, d = 3.1400000000000001}
(gdb) print sizeof(a)          # 16
(gdb) x/16xb &a                # 逐字节看内存
0x7fffffffe3e0: 0x58 0x00 0x00 0x00  0x2a 0x00 0x00 0x00
                  ↑ c + 3字节padding     ↑ i = 0x2a = 42
0x7fffffffe3e8: 0x1f 0x85 0xeb 0x51  0xb8 0x1e 0x09 0x40
                  ↑ d = 3.14 (IEEE 754 double)

可以直观看到 char c 后面有 3 字节 padding，结构体大小 16 字节。

1.5

.4 GDB 调试 core dump

core dump 是什么

进程因 SIGSEGV（段错误）、SIGABRT 等异常信号终止时，内核可以把进程的内存映像、寄存器状态、栈信息写入一个 core 文件。这个文件就是进程崩溃瞬间的"现场快照"。

用 GDB 加载可执行文件 + core 文件，就能在崩溃点回溯调用栈、查看变量、分析根因——相当于事故调查的黑匣子。

开启 core dump

临时开启（当前 shell）

ulimit -c unlimited          # 允许生成不限大小的 core 文件
./app                         # 崩溃后生成 core

验证：

ulimit -c                     # 输出 unlimited 说明已开启

永久开启

编辑 /etc/security/limits.conf：

*  soft  core  unlimited
*  hard  core  unlimited

core 文件路径

cat /proc/sys/kernel/core_pattern    # 查看 core 文件命名/路径规则
core_pattern 效果
core 在程序工作目录生成 core 文件
core.%p 生成 core.<PID>
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h %e systemd 接管（Ubuntu/CentOS 默认）

手动设置：

echo "/tmp/core.%p" > /proc/sys/kernel/core_pattern    # 存到 /tmp/core.PID
echo "core" > /proc/sys/kernel/core_pattern             # 存到工作目录

systemd 系统（Ubuntu 16.04+ / CentOS 7+）：core 默认由 systemd-coredump 接管，存到 /var/lib/systemd/coredump/。用 coredumpctl list 查看，coredumpctl debug <PID> 直接调试。

调试 core dump

基本流程

gcc -g -O0 -o crash crash.c
ulimit -c unlimited
./crash                          # 崩溃，生成 core
gdb ./crash core                 # 加载可执行文件 + core

(gdb) bt                         # 调用栈回溯——直接看到崩溃在哪一行
(gdb) bt full                    # 带每个栈帧的局部变量
(gdb) frame 0                    # 切到崩溃帧
(gdb) list                       # 查看崩溃点源码
(gdb) info locals                # 崩溃帧的局部变量
(gdb) info registers             # 崩溃时寄存器状态
(gdb) x/16wx $sp                 # 崩溃时栈内存
(gdb) print *ptr                 # 查看导致崩溃的指针

bt 输出解读

(gdb) bt
#0  0x0000555555555155 in main () at crash.c:11
       ↑ 地址         ↑ 函数    ↑ 文件:行号
  • #0 是最内层（崩溃点），#1 是调用者，依次往外
  • 如果有 ?? 说明没有调试信息（没加 -g 或被 strip）
  • 地址 0x0000555555555155 可以用 info symbol 0x555555555155 查最近的符号

多线程 core dump

(gdb) info threads               # 查看所有线程
(gdb) thread 1                   # 切到 1 号线程
(gdb) bt                         # 看该线程的调用栈
(gdb) thread apply all bt        # 所有线程的调用栈一起打印

多线程程序崩溃时，core dump 会包含所有线程状态。崩溃线程通常带 SIGSEGV 标记。

无 core 文件时的调试

如果 core 没生成（忘了 ulimit -c、磁盘满、权限问题），可以直接在 GDB 里运行程序：

gdb ./crash
(gdb) run
# 程序崩溃后，GDB 自动停在崩溃点
(gdb) bt

区别：

方式 优势 劣势
core dump 事后分析，不用重现 需要 ulimit 配置
GDB run 不需要配置 必须能重现崩溃

常见崩溃信号

信号 含义 常见原因
SIGSEGV 段错误 空指针解引用、越界访问、写只读内存
SIGABRT 异常终止 assert 失败、abort()、堆损坏（double free）
SIGFPE 算术异常 除以零、整数溢出（部分平台）
SIGBUS 总线错误 内存对齐违规（ARM 上常见）
SIGILL 非法指令 函数指针被破坏、栈溢出覆盖返回地址

实操：空指针段错误

// crash.c
#include <stdio.h>
#include <string.h>

void write_data(char *buf)
{
    strcpy(buf, "hello");   // 第 6 行：buf 是 NULL → SIGSEGV
}

int main(void)
{
    char *buf = NULL;
    write_data(buf);          // 第 11 行
    printf("%s\n", buf);
    return 0;
}

$ gcc -g -O0 -o crash crash.c
$ ulimit -c unlimited
$ ./crash
Segmentation fault (core dumped)

$ gdb ./crash core
(gdb) bt
#0  write_data (buf=0x0) at crash.c:6
#1  0x0000555555555172 in main () at crash.c:11

(gdb) frame 0
(gdb) print buf
$1 = 0x0                      # → 空指针，根因找到

(gdb) frame 1
(gdb) print buf
$2 = 0x0                      # main 里的 buf 也是 NULL

分析：#0 显示崩溃在 write_data 第 6 行，buf=0x0 是空指针。#1 显示是 main 第 11 行调用时传入了 NULL。

实操：数组越界 → 堆损坏 → SIGABRT

// heap_crash.c
#include <stdlib.h>
#include <string.h>

int main(void)
{
    char *p = malloc(10);
    memset(p, 'A', 100);    // 越界写 100 字节，踩了堆元数据
    free(p);                  // glibc 检测到堆损坏 → abort() → SIGABRT
    return 0;
}

$ gdb ./heap_crash
(gdb) run
Program received signal SIGABRT, Aborted.
__GI_raise (sig=sig@entry=6) at ../sysdeps/unix/sysv/linux/raise.c:50

(gdb) bt
#0  __GI_raise (sig=6) at ../sysdeps/unix/sysv/linux/raise.c:50
#1  __GI_abort () at abort.c:79
#2  __libc_message (action=..., fmt=...) at ../sysdeps/posix/libc_fatal.c:155
#3  malloc_printerr (...) at malloc.c:5347     # ← glibc 堆检查
#4  _int_free (...) at malloc.c:4187
#5  __GI___libc_free (mem=0x5555555592a0) at malloc.c:3135
#6  0x0000555555555168 in main () at heap_crash.c:7

#3 malloc_printerr 说明 glibc 在 free 时检测到堆元数据被破坏，主动 abort。根因在 #6 main 第 6 行的 memset 越界。

1.5

.5 GDB 高级技巧与 HFT 实战

attach：调试正在运行的进程

程序已经在运行，不想重启，直接附着上去调试。

gdb -p <PID>                   # attach 到进程
# 或
gdb ./app <PID>

(gdb) break some_function      # 设断点
(gdb) continue                 # 让程序继续跑，到断点会停
(gdb) ...                      # 调试
(gdb) detach                   # 脱离进程，程序继续运行
(gdb) quit

attach 的本质

gdb -p <PID> 实际上： 1. 调用 ptrace(PTRACE_ATTACH, pid) → 内核给目标进程发 SIGSTOP，进程停住 2. GDB 读取目标进程的寄存器、内存 3. detach 时调 ptrace(PTRACE_DETACH) → 进程收到 SIGCONT 继续运行

生产环境慎用：attach 会让目标进程瞬间停住。HFT 交易引擎停 1ms 都可能丢单。只在维护窗口或非交易时段 attach。

HFT 场景：交易引擎排查

# 交易引擎 PID 12345 运行中，出现异常订单
$ gdb -p 12345
(gdb) info threads              # 看所有线程
(gdb) thread 3                  # 切到策略线程
(gdb) bt                        # 看策略线程在干什么
(gdb) print order_book->depth   # 查看订单簿状态
(gdb) detach                    # 排查完脱离，引擎继续运行

交叉调试：嵌入式 / 远程

嵌入式板子资源有限（跑不了完整 GDB），用 gdbserver + 交叉 GDB 远程调试。

架构

[开发板]                          [主机]
app (ARM)  ←──网络/串口──→  arm-linux-gnueabihf-gdb
gdbserver                      + app (带 -g 的 ARM 版)

操作步骤

板子上（启动 gdbserver）：

gdbserver :2345 ./app           # 监听 2345 端口
# 或附着到已有进程
gdbserver :2345 --attach <PID>

主机上（启动交叉 GDB）：

arm-linux-gnueabihf-gdb ./app
(gdb) target remote 192.168.1.100:2345    # 连接板子
(gdb) set sysroot /path/to/target/rootfs  # 指定目标板根文件系统（找 libc 等符号）
(gdb) set solib-search-path /path/to/libs # 额外库搜索路径
(gdb) break main
(gdb) continue

串口调试

没有网络时用串口：

# 板子
gdbserver /dev/ttyS0 ./app

# 主机
arm-linux-gnueabihf-gdb ./app
(gdb) target remote /dev/ttyUSB0

-O2 下的调试陷阱

HFT 生产代码通常 -O2 甚至 -O3，调试时会遇到：

问题 原因 应对
变量 <optimized out> 被优化进寄存器，栈上没了 关键变量加 volatile
行号跳跃 多行合并 / 指令重排 用 stepi 逐指令走
断点不命中 函数被内联 info inline，或对内联展开后的地址设断
参数显示错误 寄存器传参（ABI 变化） info args + info registers 对照
调用栈不完整 尾调用优化省略了栈帧 set backtrace past-main on 
// volatile 防优化示例
volatile int debug_flag = 0;    // GDB 可以随时查看/修改

混合编译策略

# 热点文件 -O2，调试文件 -O0 -g
CFLAGS_HOT = -O2 -g
CFLAGS_DEBUG = -O0 -g

main.o: main.c
    $(CC) $(CFLAGS_DEBUG) -c main.c

strategy.o: strategy.c
    $(CC) $(CFLAGS_HOT) -c strategy.c

watchpoint 高级用法

# 硬件 watchpoint（不拖慢程序，但数量有限）
(gdb) watch *ptr                # 内存被写时断
(gdb) rwatch *ptr               # 内存被读时断
(gdb) awatch *ptr               # 读或写都断

# 如果硬件 watchpoint 用完，GDB 自动降级为软件 watchpoint
# 软件 watchpoint 会单步执行每条指令检查值 → 程序慢 100 倍以上

HFT 场景：交易状态被意外修改 → watch order->status 定位谁改的。

多线程调试

(gdb) set scheduler-locking on  # 只让当前线程跑，其他停住
(gdb) set scheduler-locking off # 恢复（默认）

线程断点

(gdb) break main.c:42 thread 3  # 只对 3 号线程断

代码自测

题目 1： 以下 buildenv 脚本的作用是什么？为什么要 source 而不是直接执行？

#!/bin/bash
export PATH=/opt/arm-toolchain/bin:$PATH
export CROSS_COMPILE=arm-linux-gnueabihf-
export ARCH=arm
参考答案

脚本设置交叉编译环境变量： - PATH：将 ARM 交叉编译工具链加入搜索路径 - CROSS_COMPILE：指定交叉编译前缀（Makefile 用它拼接 $(CROSS_COMPILE)gcc） - ARCH：目标架构（内核/U-Boot 编译用）

必须 source buildenv 或 . buildenv 执行：因为 export 修改的是当前 shell 的环境变量，直接 ./buildenv 会在子 shell 中执行，变量不会传递到当前 shell。
