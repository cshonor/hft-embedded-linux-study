5.1

程序运行的「马甲」：进程

本节讲什么

进程 是操作系统给正在运行的程序穿上的「马甲」：同一 ELF 可多次 exec，每次得到独立 PID、虚拟地址空间、文件描述符表、堆/栈。用户态看到的 .text/.rodata/.data/.bss/heap/stack 五区，在 Linux 里由 VMA 映射到物理页；与 ch04 ELF 段一一对应。

要点

五段与进程地址空间

区域 ELF/来源 典型内容
.text PT_LOAD 机器码、main
.rodata PT_LOAD 字符串字面量、只读常量
.data PT_LOAD 已初始化全局/静态
.bss PT_LOAD（NOBITS） 未初始化全局/静态，加载时清零
heap brk/mmap malloc arena
stack 内核映射 局部变量、返回地址 
cd demo && make demo01_memory_zone && ./demo01_memory_zone
size demo01_memory_zone
readelf -S demo01_memory_zone | grep -E 'text|rodata|data|bss'
cat /proc/self/maps    # 运行中观察各段

进程 vs 程序

  • 程序：磁盘上的 ELF；进程：内存中的实例 + 内核 task_struct
  • 多进程共享 代码页（CoW）；堆/栈/私有数据各自独立
  • 内核/DPDK：内核无传统 malloc 用户堆，用 kmalloc/vmalloc；DPDK 用 hugepage mmap 预分配 pktmbuf 池

代码自测

题目 1： 程序和进程的关系是什么？以下代码 fork 后输出几次 "hello"？

#include <unistd.h>
#include <stdio.h>
int main(void) {
    fork();
    fork();
    printf("hello\n");

}
参考答案

程序是磁盘上的可执行文件（静态），进程是程序运行的实例（动态，含虚拟地址空间、PCB、页表等）。

fork 后输出 4 次 "hello"： - 第 1 个 fork：1→2 个进程 - 第 2 个 fork：2→4 个进程 - 每个进程执行一次 printf

进程的组成：代码段(.text)、数据段(.data/.bss)、堆、栈、PCB（task_struct，含 PID/状态/优先级/文件描述符表）。

5.2

Linux 环境下的内存管理

本节讲什么

Linux 用 MMU + 页表 为每个进程提供独立虚拟地址；内核以 VMA（vm_area_struct） 描述一段连续虚拟区间及其权限。用户态五段 + mmap 区都体现在 /proc/<pid>/maps；与裸机「物理地址直连」形成对比。

要点

VMA 与 maps

./demo01_memory_zone &
PID=$!
cat /proc/$PID/maps
# 典型行：r-xp .text  r--p .rodata  rw-p .data/.bss  rw-p [heap]  rw-p [stack]
pmap -x $PID
权限 含义
r-x 代码
r-- 只读数据
rw- 可读写数据/堆/栈

与 ch04 ELF 的对应

  • execve 按 Program Header 建立 LOAD 段 VMA
  • BSS 并入最后一 LOAD，占虚拟页、文件内 memsz > filesz 部分为零
  • ASLR：栈、heap、mmap 基址随机化

裸机 vs Linux MMU

裸机 Linux 进程
地址 常物理/固定链接 虚拟，经 MMU
保护 无或 MPU 页级 R/W/X
扩展 链接脚本定界 brk/mmap
  • 内核：copy_from_user/get_user 访问用户 VMA；缺页走 do_page_fault
  • DPDK：绕过内核协议栈，仍依赖 mmap hugepage 拿连续物理内存

代码自测

题目 1： Linux 进程的虚拟地址空间布局是什么？以下变量的地址分别在哪个段？

int global_init = 42;     // ?
int global_uninit;          // ?
static int s_init = 1;     // ?
char *p = malloc(100);      // p本身? *p指向?

    int local = 5;           // ?

}
参考答案

虚拟地址空间布局（高→低）： - 内核空间（1GB/128TB）：内核代码和数据 - 栈（向下生长）：local 局部变量 - mmap 区：mmap/共享库 - 堆（向上生长）：malloc 分配的空间，*p 指向此处 - .bss：global_uninit、未初始化 static - .data：global_init、s_init（已初始化全局/static） - .text：代码（只读）

5.3

栈的管理

本节讲什么

栈 是函数调用链的 LIFO 工作区：保存返回地址、旧帧指针、局部变量、部分参数。ARM 上由 SP/FP/LR 协作；理解栈帧是读 GDB bt、内核 oops 栈回溯、嵌入式定栈大小的基础。

要点

  • 栈通常 向低地址增长；ulimit -s 限制默认大小（常见 8MB）
  • 每次调用：入栈 保存 LR/FP → 分配局部 → 出栈 恢复并返回
  • AAPCS（ch03）：r0–r3 传参，其余入栈；返回值 r0
  • 工具链：-fno-omit-frame-pointer 便于 bt；-fstack-protector 防溢出
cd demo && make demo02_stack_frame
gdb -batch -ex 'break recurse' -ex run -ex bt ./demo02_stack_frame

代码自测

题目 1： 以下递归函数在 ARM 上调用 recurse(3) 时，栈帧中保存了哪些关键信息？为什么深递归会导致栈溢出？

void recurse(int n) {
    if (n == 0) return;
    int local = n * 2;
    recurse(n - 1);
}
参考答案

每次调用保存：返回地址（LR）、旧帧指针（FP）、局部变量 local 和参数 n。栈向低地址增长，每次递归分配一个栈帧。recurse(3) 需要 4 层栈帧。如果递归深度超过 ulimit -s（默认 8MB）限制，就会栈溢出。使用 -fno-omit-frame-pointer 便于 GDB bt 回溯。

5.3

.1 栈的初始化

本节讲什么

进程/线程创建时，内核在用户地址空间顶部（或 pthread 属性指定处）映射 栈区 并设置初始 SP。裸机则由启动代码在链接脚本定义的 __stack_top 写入 SP。

要点

Linux 进程栈

  • execve 后内核映射 [stack]，argc/argv/envp 与 辅助向量 压栈
  • 主线程 SP 指向栈顶；pthread_create 为每线程分配独立栈（默认 ~8MB，可 pthread_attr_setstacksize）
cat /proc/self/maps | grep stack
ulimit -a | grep stack

裸机 / RTOS

/* startup：SP 指向 RAM 栈顶 */
ldr sp, =__stack_top
  • uC/OS 等：任务控制块记录 栈底/栈顶，创建任务时 SP 指向栈顶
  • 嵌入式：静态定栈 或 _sstack/_estack 链接符号；栈水位用填充图案 0xDEADBEEF 检测

与 x86/ARM 差异

  • ARM AAPCS：SP 8 字节对齐；函数入口常 push {fp, lr} 建立帧链
  • 内核每个 task 有 内核栈（独立），与用户栈分开

与后续衔接

  • 5.3.2 在已初始化的 SP 上建栈帧
  • ch04 4.6.2 裸机 _start 设 SP 再调 main

代码自测

题目 1： 裸机环境下栈的初始化代码做了什么？为什么要先设置 SP？

_start:
    LDR SP, =_stack_top    @ 设置栈顶
    BL main                @ 调用 C 函数
参考答案

设置 SP 的原因：C 函数调用依赖栈（传参、保存返回地址、局部变量）。没有合法的 SP，BL main 后 main 中的任何 push/局部变量操作都会崩溃。

栈初始化要点： 1. SP 指向预留的栈内存区域顶部（ARM 栈满递减：SP 从高地址向低地址生长） 2. 栈大小需足够（至少几 KB，避免栈溢出） 3. 多任务时每个任务需要独立栈

裸机链接脚本中通常定义：

.stack : { _stack_bottom = .; . += 0x4000; _stack_top = .; }

4KB 栈足够简单裸机程序，复杂程序需更大。

5.3

.2 函数调用

本节讲什么

函数调用 = 保存现场 + 跳转 + 被调方建帧 + 返回恢复。ARM 经典序列：push {fp, lr} → mov fp, sp → 减 SP 留局部 → bl 写 LR → 返回 ldmfd sp!, {fp, pc}。本节是全书栈分析的 核心，配合 GDB 单步与 x 看内存。

要点

ARM 栈帧（A32 示例）

int callee(int a) {
    int local = a + 1;
    return local;
}
int caller(void) {
    return callee(42);
}

典型汇编骨架：

caller:
    push   {fp, lr}          @ 保存旧 fp、返回地址到栈
    mov    fp, sp            @ fp 指向本帧基址
    sub    sp, sp, #8        @ 给局部变量腾空间
    mov    r0, #42
    bl     callee            @ lr = 下一条指令地址
    mov    sp, fp
    pop    {fp, pc}          @ 等价 ldmfd sp!, {fp, pc}

callee:
    push   {fp, lr}
    mov    fp, sp
    sub    sp, sp, #4        @ int local
    ...
    mov    sp, fp
    pop    {fp, pc}          @ pc=lr，返回 caller
  • bl：Branch with Link，目标地址进 LR (r14)
  • ldmfd sp!, {fp, pc}：从栈弹 fp 和 pc（pc←原 lr），FD=Full Descending 栈向低址增
  • stmfd sp!, {…} 与 push 同类：先减 SP 再存

GDB 实战

gcc -g -O0 -fno-omit-frame-pointer -o demo demo02_stack_frame.c
gdb ./demo02_stack_frame

(gdb) run

(gdb) x/8i $pc              # 反汇编当前指令

(gdb) info locals

栈帧布局（概念）

高地址
  [caller 的 fp][caller 的 lr]
  [callee 局部变量...]
  [多余参数...]        ← fp 常指向 caller sp 快照
低地址 ← SP
  • FP 链：沿 fp → 上一帧 fp 可手动回溯（-fomit-frame-pointer 时 bt 变难）
  • 内核：dump_stack() / unwind 依赖 ORC/ftrace 或帧指针

DPDK / 性能注意

  • 热点路径避免深递归与大栈帧；DPDK 常 禁用递归、用 per-lcore 预分配
  • -O2 可能省略 FP；调栈问题时用 -O0 -fno-omit-frame-pointer

代码自测

题目 1： 函数调用时栈帧的创建和销毁过程是什么？以下函数调用后栈上有什么？

int add(int a, int b) {
    int c = a + b;
    return c;
}
参考答案

调用 add(1, 2) 的栈帧过程（ARM ATPCS）：

调用前（caller）： - R0=1, R1=2（参数），BL add（LR=返回地址）

函数入口（callee prologue）：

PUSH {FP, LR}     @ 保存帧指针和返回地址
MOV FP, SP        @ 设置新帧指针
SUB SP, SP, #4    @ 分配局部变量 c 的空间

函数体：STR R0, [SP] 存 c

函数返回（callee epilogue）：

MOV R0, [SP]      @ 返回值放 R0
MOV SP, FP        @ 恢复 SP
POP {FP, PC}      @ 恢复帧指针，PC=LR 返回

栈帧内容（高→低）：LR、旧FP、c。返回后栈帧被销毁。

5.3

.3 参数传递

本节讲什么

AAPCS 规定：前 4 个整型/指针参数用 r0–r3，第 5 个起 入栈；浮点另有 VFP 规则。返回值 r0（64 位用 r0+r1）。结构体过大则传指针或按规则拆寄存器。

要点

寄存器 vs 栈

void foo(int a, int b, int c, int d, int e) { /* e 在栈上 */ }

arm-linux-gnueabihf-gcc -S -O0 -o - foo.c   # 看 r0–r3 与 [sp, #offset]
# x86_64 不同：rdi, rsi, rdx, rcx, r8, r9 后入栈
类型 ARM 32（AAPCS）
int/pointer r0–r3，余者栈
返回值 r0
被调者保存 r4–r11, fp
调用者保存 r0–r3, lr

数组与指针

  • 数组作实参 退化为指针，传地址（4 字节），不拷贝整数组
  • 内核 拷贝用户缓冲区：copy_from_user()，避免直接解引用用户指针

(gdb) break foo
(gdb) run
(gdb) info args
(gdb) print/x $r0 $r1 $r2 $r3
(gdb) x/4wx $sp    # 栈上第 5 个参数

参考答案

ATPCS 参数传递规则： - 前 4 个参数通过 R0-R3 传递：a→R0, b→R1, c→R2, d→R3 - 第 5 个起压栈：e→[SP], f→[SP+4] - 返回值在 R0（64 位用 R0+R1）

调用 func(1,2,3,4,5,6)：

MOV R0, #1
MOV R1, #2
MOV R2, #3
MOV R3, #4
PUSH {R0}      @ 临时用R0存5
MOV R0, #6     @ 不对，应该先压第6个

实际：参数 5,6 逆序压栈（右到左）：

MOV R0, #6
PUSH {R0}      @ f=6
MOV R0, #5
PUSH {R0}      @ e=5
MOV R0, #1; MOV R1, #2; MOV R2, #3; MOV R3, #4
BL func
ADD SP, SP, #8 @ 清理栈上参数

浮点参数用 VFP 寄存器 S0-S15。

5.3

.4 形参与实参

本节讲什么

形参 是函数定义里的占位名，实参 是调用时的表达式。C 只有 值传递：形参是实参值的副本；若想改调用方变量，须传 指针 并在被调函数里解引用。

要点

值传递 vs 指针

void swap_wrong(int a, int b) { int t=a; a=b; b=t; }      /* 无效 */
void swap_ok(int *a, int *b)   { int t=*a; *a=*b; *b=t; } /* 有效 */
  • 修改 指针形参本身（p = NULL）不影响实参指针变量
  • 修改 *p 指向的内容 影响实参所指对象

栈上的副本

void bar(int x) { x = 99; }   /* 只改栈上副本 */
int n = 1;
bar(n);                       /* n 仍为 1 */

gdb -ex 'break bar' -ex run -ex 'print x' -ex 'finish' ./a.out

常见坑

  • scanf("%d", n) 应 scanf("%d", &n)
  • 返回栈上局部指针 → 悬空指针（UB）
  • 大结构体按值传递 → 拷贝开销；内核 API 多用指针

题目 1： 以下代码输出什么？形参和实参的关系是什么？

    int tmp = a; a = b; b = tmp;
}

原因：C 语言传值调用——形参 a/b 是实参 x/y 的副本。swap 交换的是栈上副本，不影响 main 中的 x/y。

题目 1： 裸机环境下如何实现简单的堆内存管理？以下代码有什么问题？

    void *p = &heap[offset];

}
参考答案

这是一个"分配不释放"的简单堆（bump allocator）。

问题： 1. 无法释放：offset 只增不减，内存用完就没了 2. 无对齐：size 可能不是 4/8 字节对齐，导致未对齐访问异常（ARM 上某些指令要求对齐） 3. 无边界检查：offset 超过 4096 会越界 4. 碎片化：即使能释放，频繁 alloc/free 会导致外部碎片

题目 1： Linux 中 malloc 如何向操作系统申请内存？brk 和 mmap 有什么区别？

参考答案

Linux malloc 分两层：

用户层（ptmalloc/jemalloc/tcmalloc）：管理已分配的堆空间，维护空闲链表/ bins。

系统调用层： - brk/sbrk：调整 program break，扩展堆顶。适合小分配（< 128KB）。分配的虚拟地址连续。 - mmap：匿名映射一块内存。适合大分配（>= 128KB）。地址不连续，释放时 munmap 归还。

题目 1： 实现一个简单的空闲链表堆管理器，分配和释放的核心逻辑是什么？

struct block {

参考答案

空闲链表法核心逻辑：

分配（malloc）： 1. 遍历 free_list 找到 size >= 请求大小的块 2. 若块远大于请求，分裂为两块（返回一块，剩余放回 free_list） 3. 从 free_list 移除该块，返回数据区指针

释放（free）： 1. 将释放的块加回 free_list 2. 检查相邻块是否空闲，合并（避免碎片）

关键问题： - 合并：free 时需检查前后块是否空闲，合并为大块 - 对齐：每块大小需对齐到 8/16 字节 - 线程安全：多线程需加锁或使用线程局部堆 - 元数据：block header 存 size 和 next，如何找到 header？（free 传入的是数据指针，往前偏移 sizeof(struct block) 即 header）

Linux glibc 的 ptmalloc 用 bins（按大小分桶）+ 合并策略。

题目 1： mmap 的内核实现机制是什么？为什么 mmap 不立即分配物理内存？

参考答案

mmap 内核机制：

  1. 建立虚拟映射：mmap 只在进程的 VMA（Virtual Memory Area）链表中记录一段虚拟地址范围的属性（权限、映射对象、偏移），不分配物理内存
  2. 缺页中断：首次访问该虚拟地址时触发缺页异常

  4. 建立页表映射：将虚拟地址映射到物理页

这就是延迟分配（demand paging）：只有实际访问时才分配物理内存，节省内存。

对于匿名 mmap（无文件）：缺页时分配零页（zero page）。

MAP_SHARED 的写入通过页缓存写回文件（write-back）。

代码自测

题目 1： 以下代码有两处内存泄漏，分别是什么？

void func(void) {
    char *p = malloc(100);
    p = malloc(200);  // 泄漏1
    char *q = malloc(50);
    if (some_error) {
        return;       // 泄漏2
    }
    free(p);
    free(q);
}
参考答案

泄漏 1：p = malloc(200) 覆盖了第一次 malloc(100) 的指针，100 字节的内存无法释放（原指针丢失）。

泄漏 2：some_error 为真时直接 return，p 和 q 都没 free。

修复：

void func(void) {
    char *p = malloc(100);
    // 使用 p...
    free(p);           // 先释放
    p = malloc(200);   // 再重新分配
    char *q = malloc(50);
    if (some_error) {
        free(p); free(q);  // 错误路径也要释放
        return;
    }
    free(p); free(q);
}

原则：每个 malloc 必须有对应的 free，包括所有 return 路径。用 goto cleanup 模式处理错误路径。

  5. 临时文件泄漏：tmpfile/mkdtemp 后忘记删除
  6. 缓存膨胀：无上限的 cache 导致内存持续增长
  7. dlopen 泄漏：dlopen 后没 dlclose

检测：ls /proc/PID/fd | wc -l 检查 fd 数量；ps -L 检查线程数；Valgrind 检查 fd 泄漏。

预防：为每类资源建立"获取-释放"配对约定，用 cleanup 模式处理错误路径。

题目 1： 以下代码有哪几种可能的内存错误？

四种内存错误：

  1. 缓冲区溢出（Heap Overflow）：strcpy(p, "Hello World!") 写入 13 字节（含 NUL），但 p 只有 10 字节。覆盖堆元数据，可能导致 crash 或被攻击。

5.7

.3 什么是内存踩踏

本节讲什么

内存踩踏（memory stomp）：写入 合法对象边界之外，破坏相邻对象、堆 metadata、返回地址。读踩踏可能 SIGSEGV；写踩踏可能 延迟崩溃（corruption 后才 abort）。

要点

典型场景

char buf[8];
strcpy(buf, "0123456789");     /* 越界写 */
int *p = malloc(16);
free(p);
*p = 1;                        /* use-after-free 写 */
free(p);                       /* double free */
  • 堆：覆盖相邻 chunk 的 size → malloc 后续崩溃
  • 栈：覆盖 saved LR（5.3.6）
  • 数组下标：a[-1]、a[n] 在循环 off-by-one
valgrind --tool=memcheck ./prog
# Invalid write of size 1 at 0x...
gcc -fsanitize=address -g -O0 -o prog prog.c

内核

  • buffer overrun in copy_from_user 长度检查不严
  • SLUB RED_ZONE / CONFIG_DEBUG_PAGEALLOC 辅助检测

内存踩踏：写入超出分配范围的数据，覆盖相邻内存区域。

本例：buf[8] 后面可能是： - 其他局部变量（栈上）→ 逻辑错误 - 保存的 FP/LR（栈帧）→ 函数返回时跳转到错误地址 - 堆元数据（堆上）→ 堆管理器崩溃

后果： - 立即崩溃：覆盖返回地址 → 段错误 - 延迟崩溃：覆盖堆元数据，下次 malloc/free 时才崩溃，难以定位 - 静默错误：覆盖其他变量，逻辑错误但不 crash

常见原因：strcpy/memcpy 无长度检查、数组越界、sprintf 缓冲区不够。

检测：ASan（编译时插桩，精确检测）、Valgrind（运行时检测）、mprotect 保护区（手动放置哨兵页）。

5.7

.4 内存踩踏监测：mprotect

本节讲什么

用 mprotect 在缓冲区两侧映射 PROT_NONE 保护页，越界访问立即 SIGSEGV，比静默损坏易定位。glibc guard malloc、调试分配器、部分 Electric Fence 思路同源。

要点

#include <sys/mman.h>
size_t page = sysconf(_SC_PAGESIZE);
void *base = mmap(NULL, 3*page, PROT_READ|PROT_WRITE,
                  MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
mprotect(base, page, PROT_NONE);                    /* 左 guard */
mprotect((char*)base + 2*page, page, PROT_NONE);  /* 右 guard */
char *buf = (char*)base + page;
/* buf 仅一页；越界 → SIGSEGV */

代码自测

题目 1： 如何用 mprotect 实现内存踩踏检测？以下代码的原理是什么？

void *p = mmap(NULL, 4096*3, PROT_READ|PROT_WRITE,
               MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
mprotect(p, 4096, PROT_NONE);           // 前一页禁用
void *user = p + 4096;                   // 中间页可用
mprotect(p + 4096*2, 4096, PROT_NONE);  // 后一页禁用
参考答案

mprotect 哨兵页原理：

  1. mmap 分配 3 页（12KB）：[Guard Page][User Page][Guard Page]
  2. 前后页设为 PROT_NONE（不可读写执行）
  3. 用户使用中间页
  4. 若用户越界访问前后页 → 触发 SIGSEGV（段错误），精确定位越界位置

优点： - 精确检测溢出和下溢 - 硬件级检测（MMU 页保护），无性能开销 - 适用于栈/堆保护

缺点： - 粒度粗（页对齐，4KB），浪费内存 - 只检测越出页边界的访问，页内越界检测不到

类似机制：Electric Fence 库、ASan 的 red zone（更细粒度）。

题目 1： Valgrind 的 Memcheck 能检测哪些内存错误？以下命令的输出含义是什么？

$ valgrind --leak-check=full ./a.out
==12345== Invalid read of size 4
==12345==    at 0x40053A: main (test.c:5)
==12345==  Address 0x5203040 is 0 bytes inside a block of size 40 free'd
参考答案

Valgrind Memcheck 检测的内存错误类型： - Invalid read/write：访问未分配/已释放的内存 - Use of uninitialized value：使用未初始化的变量 - Invalid free：重复释放或释放非堆指针 - Memory leak：malloc 没有 free（分 definitely lost / indirectly lost） - Syscall with invalid pointer：系统调用传入非法指针

输出解读： - Invalid read of size 4：在第 5 行读取了 4 字节（如 int）的无效内存 - Address ... is 0 bytes inside a block of size 40 free'd：该地址在一个已 free 的 40 字节块开头 → Use-After-Free

Valgrind 原理：JIT 翻译，在每条指令前插入检查代码。性能开销 10-20 倍。

替代方案：ASan（-fsanitize=address），编译时插桩，开销 2 倍，适合 CI 流水线。
