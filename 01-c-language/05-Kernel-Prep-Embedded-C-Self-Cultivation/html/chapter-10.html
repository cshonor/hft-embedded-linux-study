10.1

多任务的裸机实现

本节讲什么

在没有操作系统的 裸机（Bare Metal） 环境中，如何让多个「任务」看似同时运行？本节建立 并发（Concurrency） 与 并行（Parallelism） 的区分，对比 前后台（Foreground/Background） 与 RTOS 抢占式多任务 的差异，为 10.1.1–10.1.3 的模拟实现与 demo01_foreground 奠定概念框架。

要点

并发 vs 并行：

概念 含义 典型场景
并发 逻辑上「同时」推进多个任务，可能分时复用单核 前后台轮询、协作式 RTOS
并行 物理上同一时刻多核各跑一任务 SMP Linux、DPDK 多 lcore

单核 MCU 上常见的是 并发；多核 SoC 才谈 并行。

三种多任务形态：

┌─────────────────────────────────────────────────────────┐
│  前后台（Super Loop）                                     │
│  while(1) { 后台任务(); if(事件) 前台处理(); }            │
├─────────────────────────────────────────────────────────┤
│  协作式多任务（Cooperative）                              │
│  任务主动 yield；调度器在任务返回时切换                     │
├─────────────────────────────────────────────────────────┤
│  抢占式多任务（Preemptive RTOS）                          │
│  SysTick/中断强制切换；高优先级可打断低优先级               │
└─────────────────────────────────────────────────────────┘
  • 前后台：最简单，无 TCB、无独立栈；后台长循环会 饿死 前台响应（demo01_foreground 对比）
  • 协作式：需 每任务独立栈 + TCB（ch08 8.3 对象封装、demo02_tcb_coop）；任务不 yield 则他人无法运行
  • 抢占式：定时器中断触发 上下文切换（10.3、demo03_preempt）；更接近 FreeRTOS/uC/OS 行为

裸机多任务的最小要素（衔接 ch05 栈、ch08 TCB）：

要素 作用
任务控制块 TCB 保存栈指针、优先级、状态、入口函数
独立任务栈 每任务一份，避免局部变量互相覆盖
调度器 决定下一个运行的任务
上下文切换 保存/恢复 CPU 寄存器与 SP（ch03 stmfd/ldmfd）

常见陷阱（全书终章反复出现）：

  • 栈溢出：深递归或大数组在任务栈上 → 破坏相邻任务或 TCB（ch05 栈金丝雀）
  • 未保护的全局变量：多任务读写同一变量 → 竞态
  • 饿死（Starvation）：低优先级任务长期得不到 CPU

代码自测

题目 1： 以下裸机多任务调度代码有什么问题？如何改进？

void task1(void) { while(1) { work1(); } }
void task2(void) { while(1) { work2(); } }
int main(void) {
    while(1) {
        task1();
        task2();
    }
}
参考答案

task1 和 task2 内部都是 while(1) 死循环，永远不会返回，导致 task2 永远无法执行。

裸机多任务有两种方式： 1. 时间片轮转：每个任务不使用 while(1)，执行一轮后返回，由主循环轮询调度 2. 中断驱动：利用定时器中断切换任务上下文（需保存/恢复寄存器和栈指针）

改进为时间片方式：每个 task 不含 while(1)，main 的 while(1) 轮询调用即可。

10.1

.1 多任务的模拟实现

本节讲什么

在单线程、无 OS 的 C 程序里，如何用 状态机 或 setjmp/longjmp 模拟「多任务」切换？本节是 demo02_tcb_coop、demo03_preempt（主机端协作分支）的代码级基础，理解「保存现场、恢复现场」的本质，再过渡到真实 ARM 上下文切换。

要点

方法一：状态机 + 分步执行

typedef enum { TASK_A_STEP0, TASK_A_STEP1, TASK_B_STEP0 } task_step_t;
static task_step_t step_a, step_b;

void scheduler_tick(void) {
    switch (step_a) { case TASK_A_STEP0: /* ... */ step_a = TASK_A_STEP1; break; }
    switch (step_b) { /* 同理 */ }
}
  • 优点：无栈切换、可预测、适合极简前后台
  • 缺点：任务逻辑被拆成碎片，无法写「自然」的阻塞式代码

方法二：setjmp/longjmp 协作切换（demo03_preempt 主机端）

#include <setjmp.h>
jmp_buf task_a_env, task_b_env;

void task_a(void) {
    if (setjmp(task_a_env) == 0) {
        /* 首次进入 */
        while (1) {
            do_work();
            longjmp(task_b_env, 1);  /* 主动让出 */
        }
    }
    /* longjmp 返回点：恢复现场继续 */
}
对比项 状态机 setjmp
栈 共用主栈 共用主栈（不能真正并发）
局部变量 需 static 保存 跳转间局部变量未定义行为
教学价值 理解分时 理解「保存 PC/栈帧」概念

方法三：独立栈 + TCB（正路）（demo02_tcb_coop）

typedef struct {
    void (*entry)(void *arg);
    void *arg;
    uint32_t *stack_top;   /* 栈顶（向下增长） */
    uint32_t priority;
    enum { READY, RUNNING, BLOCKED } state;
} tcb_t;
  • 启动任务：伪造栈帧，使首次「返回」跳进 entry
  • 切换时：保存 R4–R11, SP, LR 到 TCB；加载下一任务寄存器（ch03 stmfd sp!, {r4-r11, lr} / ldmfd sp!, {r4-r11, pc}）

与真实 RTOS 的差距：

  • 模拟方案通常 无抢占、无中断栈分离（10.3.2）
  • 无 mutex/semaphore 时全局变量仍不安全（10.2.4、demo04_semaphore）

代码自测

题目 1： 以下代码用轮询方式模拟多任务，如果 task1 执行时间过长会有什么问题？

void main_loop(void) {
    while(1) {
        task1();  // 假设执行 50ms
        task2();  // 需要每 20ms 执行一次
        task3();
    }
}
参考答案

如果 task1 执行 50ms 而 task2 需要每 20ms 执行一次，task2 的实时性无法保证。

轮询调度的核心问题：各任务执行时间不确定，无法保证实时性。

解决方案： 1. 拆分长任务：把 task1 拆成多个短步骤，每次只执行一步 2. 定时器中断 + 标志位：定时器中断设置标志位，主循环检查标志位决定是否执行 3. 使用 RTOS：引入抢占式调度，高优先级任务可抢占低优先级任务

10.1

.2 改变任务的执行频率

本节讲什么

多任务系统中，不同任务往往 不需要 以相同速率运行：LED 500 ms 闪一次，传感器 10 ms 采一次。本节说明如何用 软件 tick 计数、时间片比例 控制各任务 被调度的频率，衔接前后台与协作式调度，并为 10.1.3 时间片 做铺垫。

要点

SysTick / 定时器 tick：

  • 硬件定时器每 1 ms（或 10 ms）触发一次中断 → tick_count++
  • 调度器在 tick 或主循环末尾检查：该任务本轮是否到期

按周期调度（Period-based）：

typedef struct {
    tcb_t base;
    uint32_t period_ms;    /* 期望周期 */
    uint32_t last_run_tick;
} task_period_t;

bool task_due(task_period_t *t, uint32_t now) {
    return (now - t->last_run_tick) >= t->period_ms;
}
任务 period_ms 含义
按键扫描 5 200 Hz
温度采集 100 10 Hz
日志上传 5000 0.2 Hz

按计数比例调度（协作式主循环）：

/* demo01_foreground 变体：每 N 次循环才跑一次慢任务 */
if ((loop_cnt % 100) == 0) slow_task();
fast_task();  /* 每圈都跑 */
  • 前后台里这是 改变执行频率 的唯一手段
  • 缺点：循环耗时不稳定 → 实际周期漂移

与优先级的区别（10.2.1）：

机制 回答的问题
频率/周期 这个任务 多久运行一次
优先级 多个任务同时就绪时 谁先运行

两者正交：高优先级任务也可以 period=1000 ms（偶尔运行但要及时响应）。

FreeRTOS 对应概念：

  • vTaskDelay() / vTaskDelayUntil() 控制 阻塞时间
  • 软件定时器 xTimerCreate 回调以指定频率执行

  • 10.2.1 抢占式调度中 tick 触发时间片耗尽

代码自测

题目 1： 以下代码试图让 LED 每 500ms 闪烁一次、按键每 50ms 扫描一次，有什么问题？

void main(void) {
    while(1) {
        led_toggle();
        delay_ms(500);
        key_scan();
        delay_ms(50);
    }
}
参考答案

问题：阻塞式 delay 期间 CPU 空转，无法执行其他任务。LED 闪烁和按键扫描的周期被串行叠加，实际 LED 周期变成 550ms，按键扫描间隔也变成 550ms。

正确做法：用定时器中断或系统 tick 计数实现非阻塞调度，每个任务独立计时，互不干扰。主循环用 tick 差值判断是否到执行时间，不用 delay 阻塞。

10.1

.3 改变任务的执行时间

本节讲什么

执行频率 决定任务被调度的次数；执行时间（时间片 Time Slice） 决定单次连续占用 CPU 多久。本节讲解 固定时间片轮转、协作式主动让出 与 抢占式时间片耗尽，是理解 demo03_preempt 与 10.2.1 调度器 的关键一环。

要点

时间片轮转（Round-Robin）：

Task A ████░░░░  Task B ░░████░░  Task C ░░░░████
       ↑ 时间片到，强制切换
  • 每个就绪任务分配 quantum 个 tick（如 5 ms）
  • 时间片用完 → 移到就绪队列尾部 → 切换下一任务
  • 同等优先级任务获得 公平 CPU 份额

协作式：任务自己决定占用多久：

void task_comm(void) {
    for (;;) {
        process_uart();
        os_yield();  /* 主动交出剩余时间片 */
    }
}
  • 某任务若从不 yield → 饿死 其他任务（协作式最大风险）
  • 适合已知短临界、无恶意长循环的嵌入式场景

抢占式：SysTick 强制切换（demo03_preempt ARM 路径）

SysTick_Handler:
    tick++
    if (--current->timeslice == 0) {
        current->timeslice = DEFAULT_QUANTUM;
        os_schedule();          /* PendSV 触发上下文切换 */
    }

ARM 上下文切换要点（衔接 ch03）：

  1. 保存：stmfd sp!, {r4-r11, lr} → 写入当前 TCB
  2. 切换 SP：sp = next->stack_ptr
  3. 恢复：ldmfd sp!, {r4-r11, pc} → 跳入下一任务

时间片大小的权衡：

时间片 效果
过小 切换开销占比高，吞吐下降
过大 交互响应差，低优先级等待久
按任务定制 高优先级短片、低优先级长片（高级调度）

阻塞 vs 时间片耗尽：

  • 时间片到：任务仍 就绪，只是换到队列后面
  • 阻塞（等 semaphore/queue）：任务进 BLOCKED，不占时间片（10.2.1、demo04/05）

题目 1： 以下代码通过状态机拆分长任务来减少单次执行时间，有什么优点？

typedef enum { S_IDLE, S_READ, S_PROCESS, S_WRITE } state_t;
void task_sensor(state_t *st) {
    switch (*st) {
        case S_IDLE:    *st = S_READ; break;
        case S_READ:    read_sensor(); *st = S_PROCESS; break;
        case S_PROCESS: process_data(); *st = S_WRITE; break;
        case S_WRITE:   write_result(); *st = S_IDLE; break;
    }
}
参考答案

状态机拆分的优点： 1. 每次只执行一个步骤，单次执行时间短，不会阻塞其他任务 2. 任务可被中断打断后恢复，不需要保存中间结果到栈（状态保存在 *st 中） 3. 天然支持优先级：高优先级任务可在低优先级任务的步骤间隙执行

关键点：状态变量 *st 必须声明为 static 或由调用者持有，保证跨调用保持值。如果在中断中修改状态，需用 volatile 修饰。

.1 调度器工作原理

本节讲什么

调度器决定 哪个任务在何时获得 CPU。本节对比 协作式与抢占式、就绪/阻塞状态、优先级与 bitmap 就绪表，并说明 blocking 如何释放 CPU，对应 demo02_tcb_coop、demo03_preempt、demo06_mini_rtos 的核心循环。

要点

任务状态机：

        create
          │
          ▼
    ┌──► READY ◄─── 时间片到/被唤醒
    │      │
    │      │ 被调度器选中
    │      ▼
    │   RUNNING ──► BLOCKED（等 sem/queue/delay）
    │      │              │
    │      │ exit         │ signal/post
    │      ▼              │
    └─ TERMINATED    ──────┘

协作式调度（demo02_tcb_coop）：

void os_schedule(void) {
    tcb_t *next = pick_next_ready();  /* 轮转或优先级 */
    if (next != current)
        context_switch(current, next);
}

void os_yield(void) {
    os_schedule();  /* 仅在主动调用点切换 */
}

抢占式调度（demo03_preempt）：

  • SysTick 或时间片定时器中断 → 标记 need_reschedule
  • PendSV（ARM）或软中断中执行真正的 context_switch，避免在 SysTick 里做重活（10.3.1）

优先级调度 + Ready Bitmap：

#define MAX_PRIO 32
uint32_t ready_bitmap;           /* bit i = 1 表示优先级 i 有就绪任务 */
tcb_t *ready_list[MAX_PRIO];     /* 每优先级一条链表 */

tcb_t *pick_highest(void) {
    int p = __builtin_clz(ready_bitmap);  /* 找最高位 1 */
    return ready_list[p]->head;
}
  • O(1) 找最高优先级；同优先级 时间片轮转
  • FreeRTOS：configMAX_PRIORITIES；uC/OS：0 最高或最低取决于移植

Blocking 释放 CPU：

void os_sem_wait(sem_t *s) {
    if (s->count == 0) {
        current->state = BLOCKED;
        current->wait_obj = s;
        ready_bitmap_clear(current->priority);
        os_schedule();   /* 立即切走 */
    }
    s->count--;
}
  • 阻塞任务 不参与 时间片竞争 → 提高 CPU 利用率
  • 唤醒：sem_post → 任务回 READY → 若优先级更高则 抢占（demo04_semaphore）

调度策略对比：

策略 延迟可预测性 实现复杂度 典型
协作 差（依赖 yield） 低 早期 uC/OS-I
抢占 + 优先级 好 中 FreeRTOS
完全公平 CFS 吞吐优 高 Linux 内核

DPDK 侧记：用户态 lcore 绑定 物理核，轮询模式避免内核调度，是 并行 而非 RTOS 式 并发——与 MCU RTOS 问题域不同，但「一核一线程」思想相通。

题目 1： 以下简化调度器代码有什么问题？

typedef struct task {
    void (*func)(void);

.2 函数栈与进程栈

本节讲什么

函数调用栈（单任务内的 call stack）与 任务/进程栈（每任务独立栈空间）是不同层次的概念。本节衔接 ch05 栈布局、ch03 ARM 栈指令，说明 TCB 如何持有栈顶、如何检测 栈溢出，以及多任务下 为何不能共用主栈。

要点

单任务函数栈（ch05）：

高地址
  │  参数、返回地址
  │  保存的 callee-saved 寄存器
  │  局部变量
  ▼ SP   栈向下增长（ARM/AAPCS）
低地址
  • 每次函数调用 压栈；返回 弹栈
  • 递归过深 → 栈溢出 覆盖 .bss/堆/其他区域

每任务独立栈（demo02_tcb_coop）：

#define TASK_STACK_SIZE 512
uint32_t task_a_stack[TASK_STACK_SIZE];
uint32_t task_b_stack[TASK_STACK_SIZE];

tcb_t task_a = {
    .stack_top = &task_a_stack[TASK_STACK_SIZE],  /* 栈顶（高地址端） */
    .entry = task_a_fn,
};
  • 上下文切换只改 该任务的 SP；任务 A 的局部变量与 B 完全隔离
  • 静态分配栈数组 vs malloc：嵌入式优先静态，便于链接脚本定址

TCB 中与栈相关字段（ch08 封装）：

typedef struct os_task {
    uint32_t *stack_ptr;      /* 当前 SP 快照 */
    uint32_t *stack_limit;    /* 栈底（最低合法地址） */
    uint32_t *stack_base;     /* 栈顶（初始化用） */
    size_t    stack_size;
    /* priority, state, name ... */
} os_task_t;

栈初始化（首次运行）：

  • 在栈顶 伪造 异常栈帧：xPSR, PC=entry, LR=task_exit_trap, R0=arg, ...
  • 首次 context_switch 恢复 后 CPU 从 entry 开始执行

栈溢出与 Canary（ch05）：

#define STACK_CANARY 0xDEADBEEF
void stack_init(uint32_t *base, size_t words) {
    base[0] = STACK_CANARY;
    base[1] = STACK_CANARY;
}

bool stack_check(uint32_t *limit) {
    return limit[0] == STACK_CANARY && limit[1] == STACK_CANARY;
}
检测方式 说明
Canary 调度前检查魔数
MPU guard region 栈底设不可访问页（10.9）
Hook FreeRTOS configCHECK_FOR_STACK_OVERFLOW

函数栈 vs 任务栈关系：

  • 任务运行时，其 函数调用栈 就在该 任务栈 空间内生长
  • 中断可能使用 独立中断栈（10.3.2），避免占任务栈深度

多任务陷阱：

  • 在 共用主栈 上做 setjmp 切换 → 后运行任务破坏先运行任务栈帧
  • 任务栈 估太小 → 静默破坏 TCB 或邻栈 → 极难调试

代码自测

题目 1： 以下代码在多任务环境下有什么危险？

int *get_ptr(void) {
    int local = 42;
    return &local;
}
void task_a(void) {
    int *p = get_ptr();
    schedule();  // 切换到 task_b
    printf("%d\n", *p);  // 切换回来后访问 p
}
参考答案

get_ptr() 返回局部变量 local 的地址，但 local 在函数返回后栈帧被释放。

单任务时这段代码已经是未定义行为。在多任务环境下更危险：schedule() 切换到 task_b 时，task_b 的栈帧可能复用 local 原来的地址，切换回来后 *p 读到的是 task_b 写入的值，不是 42。

每个任务有自己的栈空间，调度器切换时切换栈指针（SP）。函数栈是进程栈的一部分，局部变量的生命周期仅在函数执行期间。如果需要在函数返回后保持数据，应使用 static 或堆分配。

.3 可重入函数

本节讲什么

多任务与中断并发下，同一函数可能被 重入（在未执行完时再次被调用）。本节定义 可重入（Reentrant）、线程安全 与 可重入 的区别，给出嵌入式 C 的编写准则，衔接 10.2.4 临界区 与 demo04/05 中的共享资源保护。

要点

术语对比：

术语 含义
可重入 多个执行流 同时 进入同一函数，各自使用 独立数据，结果正确
线程安全 多线程调用不出错（常靠锁，允许串行化）
可重入 ⟹ 线程安全 是；反之不一定

不可重入的典型原因：

/* 坏：静态局部 → 所有调用者共享 */
void bad(void) {
    static int count;
    count++;
}

/* 坏：返回静态缓冲区指针 */
char *get_ip_str(void) {
    static char buf[16];
    sprintf(buf, "%d.%d.%d.%d", ...);
    return buf;
}

中断 + 任务重入场景：

任务调用 uart_send() ──► 执行到一半
        ▲
        │  UART 中断再次调用 uart_send()
        └─ 若共享静态状态 →  corruption

编写可重入代码的原则：

  1. 不使用 非 const 全局/静态变量（或进入前加锁）
  2. 只操作 参数与栈上局部变量
  3. 不调用 已知不可重入的库函数（如部分 strtok、rand 无锁版）
  4. 标准 C 库：用 strtok_r、reentrant 版 syscalls（Newlib _r 后缀）

RTOS 中的实践：

场景 做法
printf 用 mutex 包裹或专用日志任务 + queue（demo05_queue）
硬件寄存器 短 临界区 关中断或 mutex
纯计算 保持无状态即可重入

与 10.2.4 的关系：

  • 不可重入函数 + 共享资源 → 必须 临界区保护 或改为 每任务一份上下文
  • malloc 在多任务下需 重入锁（Newlib --enable-newlib-reent）

Linux 对比（10.10）：

  • 内核函数区分 _irqsave 版本；用户态 pthread 函数要求线程安全
  • errno：线程局部存储 __errno_location()

题目 1： 以下函数是可重入的吗？为什么？在信号处理函数中调用安全吗？

static int counter = 0;

不可重入。原因：使用了 static 变量 counter，多次调用共享同一变量。

10.2

.4 临界区与临界资源

本节讲什么

临界资源 同一时刻只允许一个执行流访问；访问它的代码段叫 临界区（Critical Section）。本节讲解 关中断、mutex、semaphore、queue、event group 的选型，以及 优先级反转 与 死锁，对应 demo04_semaphore、demo05_queue。

要点

临界资源示例：

  • 全局环形缓冲区、UART 硬件、共享配置文件、动态内存堆

保护手段层次：

关中断（最短、单核有效）
    ↓
自旋锁 spinlock（多核短临界，内核/DPDK）
    ↓
mutex（可能阻塞，RTOS/Linux 用户态）
    ↓
semaphore / queue（同步 + 资源计数）

关中断临界区（单核 MCU）：

uint32_t primask = __get_PRIMASK();
__disable_irq();
/* 临界区：几微秒内完成 */
shared_counter++;
__set_PRIMASK(primask);
  • 不能关太久 → 影响中断响应与调度 tick
  • 多核无效 → 需 spinlock + 内存屏障

Mutex（互斥量）（demo04）：

os_mutex_lock(&uart_mtx);
uart_write(buf, len);
os_mutex_unlock(&uart_mtx);
  • 优先级继承：持锁任务临时提升到等待者优先级，缓解 优先级反转
  • FreeRTOS：xSemaphoreCreateMutex() + configUSE_MUTEXES

Semaphore（信号量）：

类型 初值 典型用途
二进制 0/1 事件通知、同步
计数 N 资源池（N 个缓冲区） 
os_sem_wait(&rx_sem);   /* 无数据则 BLOCKED */
process(packet);
os_sem_post(&tx_sem);

Queue（消息队列）（demo05_queue）：

  • 传递 数据副本 或指针（需约定生命周期）
  • 天然解耦生产者/消费者；阻塞式 recv 触发调度（10.2.1）

Event Group（事件组）：

  • 多位标志：wait(TASK_A_BIT | TASK_B_BIT, AND/OR)
  • 适合「等多条件就绪」；FreeRTOS EventGroup

优先级反转（经典案例）：

L 持 mutex ──► M 抢占 L ──► H 等 mutex 被 M 间接阻塞

对策：优先级继承 mutex、避免 L/M 长时间占 CPU

死锁四条件（破坏任一即可）：

  1. 互斥 2. 持有并等待 3. 不可剥夺 4. 循环等待
  • 嵌入式对策：固定加锁顺序、trylock 超时、减少嵌套锁

选型速查：

需求 选用
保护短全局变量 关中断 / mutex
任务间传结构体 queue
通知「发生了一件事」 二进制 sem / event
限流 N 同类资源 计数 sem

常见陷阱

  1. 关中断临界区内调用阻塞 API → 死锁或丢 tick __disable_irq() 后调 os_sem_wait()、printf()（可能阻塞于 UART DMA）、malloc()（可能拿不到堆锁）——调度器被关，阻塞的任务永远等不到唤醒，系统死。约定：关中断临界区只做几条指令的纯内存操作（计数器自增、链表头插入），任何可能阻塞或调度的 API 都禁用。RTOS 文档明确写"ISR/临界区内禁调 FromISR 之外的 API"。

  2. 优先级反转未处理 → 高优先级任务被低优先级"间接阻塞" 经典场景：L 持 mutex，H 等 mutex，M 抢占 L 跑——L 没机会释放 mutex，H 被 M 间接阻塞。对策：用优先级继承 mutex（FreeRTOS xSemaphoreCreateMutex 默认开），持锁任务临时提升到 H 的优先级，L 跑完快速释放。坑：二进制 semaphore 没有优先级继承——用它做互斥会触发反转。优先级继承 mutex 性能略低，但实时性更可靠。

  3. 自旋锁临界区内睡眠/调度 → 死锁整个 CPU spin_lock 假设临界区极短、不阻塞——内核抢占被关，持锁 CPU 不会切走。但若临界区内 kmalloc(GFP_KERNEL)（可能睡眠）、copy_from_user（可能缺页睡眠）、schedule()——调度器切到其他任务，该任务若也尝试拿同一自旋锁即死锁（自旋等待永远不会前进）。约定：自旋锁内禁睡眠——用 spin_lock_irqsave + 仅做指针/标志操作；需要睡眠用 mutex。

1.（选择） 单核 Cortex-M 上保护 shared_counter++ 最合适的手段是？ - A. mutex - B. 自旋锁 - C. 关中断 - D. semaphore

答案

C。单核 MCU 上 ++ 操作几条指令，关中断最轻量——__disable_irq()/__set_PRIMASK() 几个时钟周期，无锁结构开销。mutex 需要任务调度（可能切走），杀鸡用牛刀；自旋锁在单核无意义（自旋等不到释放）；semaphore 同样过重。多核或 SMP Linux 上关中断无效（只关本核），必须自旋锁。原则：单核短临界区用关中断，多核短临界区用自旋锁，长临界区用 mutex。

2.（判断） 用二进制 semaphore 当 mutex 用是等价的。

答案

错。二者都能做"互斥"，但有关键差异： 1. 优先级继承：mutex 有，semaphore 没有——用 semaphore 做互斥会触发优先级反转。 2. 所有权：mutex 有 owner 概念（持锁者必须解锁），semaphore 任何人都能 post——错误代码误释放 semaphore 难以发现。 3. 递归：mutex 可设 recursive（同任务多次加锁），semaphore 不行。 约定：保护临界资源用 mutex，同步/通知用 semaphore。FreeRTOS 文档明确"用 mutex 做互斥，semaphore 做同步"。

3.（踩坑） 任务 A、B 都需要锁 L1、L2。A 先拿 L1 再拿 L2，B 先拿 L2 再拿 L1。某次 A 拿到 L1 后被 B 抢占，B 拿到 L2 后等 L1——两任务死锁。如何避免？

答案

死锁四条件：互斥、持有并等待、不可剥夺、循环等待。修复方式： 1. 固定加锁顺序——所有任务按相同顺序拿锁（如先 L1 后 L2），破坏循环等待。最常用。 2. trylock 超时——mutex_take(L2, timeout)；超时则释放 L1 重试，破坏持有并等待。 3. 降低嵌套——重构代码让一个任务不需同时持两把锁（拆分临界区）。 4. 避免持锁时调度——短临界区用关中断/自旋锁，不调度即不被抢占。 预防：code review 时画"锁依赖图"，发现环即重构。Linux 内核有 lockdep 自动检测潜在死锁。

4.（应用） 设计一个 ISR → 任务的环形缓冲区通信：ISR 收一个字节入 buffer，任务消费。给出加锁/同步方案。

答案 
/* 方案一：关中断 + ringbuf（单生产者单消费者，无锁即可） */
struct ring {
    uint8_t buf[256];
    volatile uint16_t head;   /* ISR 写 */
    volatile uint16_t tail;   /* task 读 */
};
static struct ring rx_ring;

void UART_ISR(void) {
    uint16_t h = rx_ring.head;
    rx_ring.buf[h & 255] = UART->DR;
    rx_ring.head = h + 1;
}

void consumer_task(void) {
    while (1) {
        while (rx_ring.head != rx_ring.tail) {
            uint8_t b = rx_ring.buf[rx_ring.tail & 255];
            rx_ring.tail++;
            process(b);
        }
        /* 阻塞等下次中断唤醒 */
        os_sem_wait(&rx_sem);
    }
}

关键点： - SPSC 无锁队列：单生产者单消费者下，head/tail 各自只被一方写，读对方变量用 volatile + 适当屏障即安全——无需关中断/锁。 - 唤醒：ISR 收数据后 os_sem_post_from_isr(&rx_sem) 通知任务。 - 溢出处理：head 超过 tail 太多即丢字节，需统计 drop count。 - 多生产者或多消费者则必须加锁——SPSC 无锁不适用。 - DPDK rte_ring 用完全相同的 SPSC 无锁模式，性能极高。

中断

本节讲什么

中断 是硬件异步打断 CPU 正常流程的机制，也是 抢占式 RTOS 的时间基准与外设驱动入口。本节总览中断与多任务的关系：谁可以打断谁、中断里能做什么，并指向 10.3.1–10.3.3 的流程、双栈与 ISR 编码规范。

要点

中断在多任务中的角色：

用途 示例
系统 tick SysTick → 时间片、delay
外设事件 UART RX、DMA 完成、GPIO
软件触发 PendSV 做上下文切换；SVC 进内核

中断 vs 轮询：

  • 轮询：CPU 空转查标志 → 前后台常见
  • 中断：事件驱动 → RTOS 任务可 阻塞等待，CPU 跑其他任务

中断优先级（NVIC）：

高 ── SysTick / 关键外设
中 ── UART、Timer
低 ── PendSV（刻意最低，最后执行切换）
  • ARM Cortex-M：数字越小优先级越高（与部分 MCU 相反，以手册为准）
  • PendSV 设最低 → SysTick 里只置位「需要切换」，在 PendSV 里做 stmfd/ldmfd（demo03_preempt）

ISR 设计铁律：

  1. 短：微秒～几十微秒级
  2. 不阻塞：不调 mutex_lock、malloc、printf
  3. Defer 到任务：ISR 里 sem_post_from_isr / queue_send_from_isr

与并发的关系：

  • ISR 可与 任意任务 并发 → 共享数据要临界区保护（10.2.4）
  • ISR 可能 重入 同一向量（若未清标志）→ 驱动要可重入或关同类中断

10.3

.1 中断处理流程

本节讲什么

从外设拉高中断线到 ISR 返回，CPU 与 NVIC 做了哪些硬件动作？本节梳理 Cortex-M 中断流程，说明 SysTick 触发抢占调度 与 PendSV 延迟切换 的分工，对应 demo03_preempt 的 ARM 路径。

要点

Cortex-M 硬件自动流程：

1. 完成当前指令（或异常点）
2. 硬件压栈：xPSR, PC, LR, R12, R3, R2, R1, R0  → 当前 SP（任务或 MSP）
3. 读向量表 → 跳 ISR
4. LR = EXC_RETURN（标记返回用哪个栈、是否 FPU）
5. ISR 执行 ...
6. BX LR  → 硬件弹栈 → 回到被打断代码

向量表：

/* startup 中 */
void (* const vector_table[])(void) = {
    stack_top,
    Reset_Handler,
    NMI_Handler,
    HardFault_Handler,
    /* ... */
    SysTick_Handler,
    PendSV_Handler,
};

SysTick + PendSV 协作（FreeRTOS 经典模式，demo03_preempt）：

void SysTick_Handler(void) {
    tick_count++;
    if (--current->timeslice == 0) {
        current->timeslice = QUANTUM;
        SCB_ICSR |= PENDSVSET;   /* 仅请求 PendSV，不在此切换 */
    }
}

void PendSV_Handler(void) {
    __asm volatile (
        "mrs r0, psp\n"
        "stmfd r0!, {r4-r11}\n"   /* 保存 callee-saved */
        "str r0, [current]\n"
        /* 选 next，加载 sp，ldmfd ... pc */
    );
}
  • 为何分两步：SysTick 优先级可较高保证 tick 准；上下文切换 放最低优先级 PendSV，避免嵌套切换混乱

中断嵌套：

  • 高优先级 ISR 可打断低优先级 ISR
  • 每层嵌套多占 一份硬件压栈帧 → 任务栈或 MSP 深度增加（10.3.2）

中断延迟组成：

延迟 = 当前指令完成 + 更高优先级 ISR + 临界区关中断时间 + 流水线
  • RTOS 中 taskENTER_CRITICAL() 会 抬 BASEPRI，屏蔽低于阈值的 IRQ

Bottom Half / 任务 defer：

UART ISR: 读 FIFO → 入 ringbuf → queue_send_from_isr → 唤醒解析任务
解析任务: 协议状态机、printf（可阻塞）

常见陷阱

  1. ISR 内调用阻塞 API → 死锁 ISR 不在任何任务上下文，调度器不能切到 ISR——调 os_sem_wait()、malloc()、printf() 等阻塞 API 永远等不到唤醒，系统死。约定：ISR 只做①读硬件寄存器②清中断标志③FromISR 版 API 唤醒任务，剩余逻辑放 bottom half（任务）。RTOS 提供 xQueueSendFromISR、xSemaphoreGiveFromISR 专为 ISR 用——非 FromISR 版在 ISR 调用是 UB。

  2. ISR 内忘了清中断标志 → 反复重入 外设中断标志需软件清除（写寄存器 bit）。若 ISR 末尾不清，退出瞬间 NVIC 看到标志仍 active，再次进 ISR——CPU 100% 在 ISR 歪循环，看门狗复位。坑：某些外设要求"先清标志再读数据"，"先读数据再清"会丢一字节。约定：进 ISR 第一件事清标志，再处理数据；或按芯片手册规定的顺序。

  3. volatile 误用 → 编译器优化掉 ISR 写的标志 int flag = 0; void ISR(void) { flag = 1; } 主循环 while (!flag);——编译器可能优化为"flag 已读为 0，循环不变"，永远转死。flag 必须 volatile：volatile int flag; 强制每次重新读。完整规则：ISR 写、主循环读的标志必须 volatile；但如果标志是 uint64_t 或结构体，volatile 不保证原子——仍需关中断或 __atomic_load。

自测题

1.（选择） Cortex-M 进入 ISR 时，硬件自动压栈的寄存器数量是？ - A. 4 个（R0-R3） - B. 8 个（R0-R3, R12, LR, PC, xPSR） - C. 16 个（全部） - D. 取决于 ISR 优先级

答案

B。Cortex-M 硬件自动压栈 8 个寄存器：R0, R1, R2, R3, R12, LR, PC, xPSR——这是 C ABI 的 caller-saved 寄存器集，保证 ISR 可像普通 C 函数调用。R4-R11（callee-saved）由 ISR 自己 push/pop。FPU 启用时额外压 S0-S15, FPSCR。坑：任务切换在 PendSV 里手动 stmdb r0!, {r4-r11} 保存 callee-saved——硬件不会自动做这步。

2.（判断） ISR 内可以调用 printf 调试输出。

答案

错——生产代码严禁。printf 通常： 1. 调 write 系统调用（Linux）或 UART 阻塞发送（裸机）——阻塞。 2. 内部用 malloc/缓冲——可能拿不到锁。 3. 执行时间长——ISR 应微秒级返回。 调试时可用专门的 ITM_SendChar（Cortex-M ITM 跟踪口）或 semihosting——非阻塞、专为 ISR 设计。生产代码用 ringbuf 缓存日志，ISR 入队、任务出队打印。

3.（踩坑） ISR 内 volatile int flag = 0; 改为 flag = 1;，主循环 while (flag == 0); 仍在某次编译后死循环。为什么？

答案

volatile int flag = 0; 是局部变量——每次进 ISR 重新初始化为 0，主循环读的是另一个变量（全局或堆栈）。正确：

static volatile int flag = 0;   /* 全局 + volatile */
void ISR(void) { flag = 1; }
void main_loop(void) { while (flag == 0); /* ... */ }

坑点： 1. static 保证全局生命周期，不会重置。 2. volatile 强制每次重新读，不被优化掉。 3. 仍不保证原子——若 flag 是 uint64_t，32 位 CPU 上读/写需多条指令，ISR 可能在中间打断。用 volatile sig_atomic_t（C 标准）或 __atomic_load_n(&flag, __ATOMIC_ACQUIRE)。 完整规则：ISR 与任务共享变量，必须 volatile + 类型 ≤ CPU 字长 + 必要时关中断/原子操作。

4.（应用） 设计一个 UART 接收驱动：ISR 收字节入 ringbuf，达到 64 字节或遇到 \n 时唤醒解析任务。给出 ISR 骨架和唤醒机制。

答案 
#define BUF_SZ 256
struct uart_rx {
    uint8_t  buf[BUF_SZ];
    volatile uint16_t head;
    uint16_t line_len;       /* 当前行长度（任务读，ISR 写） */
};
static struct uart_rx rx;
static os_sem_t rx_ready;

void UART_ISR(void) {
    uint8_t b = UART->DR;             /* 读数据同时清 RXNE 标志 */
    uint16_t h = rx.head;
    rx.buf[h & (BUF_SZ - 1)] = b;
    rx.head = h + 1;
    rx.line_len++;

    int wake = 0;
    if (b == '\n') wake = 1;
    else if (rx.line_len >= 64) wake = 1;
    /* 溢出保护 */
    if ((uint16_t)(rx.head - /*tail*/) >= BUF_SZ) wake = 1;

    if (wake) {
        rx.line_len = 0;
        os_sem_give_from_isr(&rx_ready, /*pxHigherPriorityTaskWoken=*/NULL);
    }
}

void parse_task(void *arg) {
    while (1) {
        os_sem_take(&rx_ready, OS_WAIT_FOREVER);
        /* 处理 rx.buf 中累积的一行/64 字节 */
        process_line(&rx);
    }
}

要点： - ISR 只做：读 DR、入 ringbuf、判唤醒条件、FromISR 唤醒——微秒级返回。 - 任务做：协议状态机、printf、malloc——任意阻塞。 - ringbuf 无锁：SPSC（ISR 写、task 读），volatile head 即可。 - 唤醒策略：行结束或长度阈值——兼顾延迟与吞吐。 - 溢出兜底：ringbuf 满强制唤醒，避免丢字节静默。

本节讲什么

任务在 任务栈（PSP） 上运行函数调用；中断发生时硬件往 当前栈指针 压寄存器。本节说明 MSP vs PSP、何时需要 独立中断栈，以及栈溢出在中断嵌套下的风险，衔接 10.2.2 与 ch05。

要点

Cortex-M 双栈指针：

栈指针 典型用途
MSP 复位、异常、内核、无 OS 裸机
PSP RTOS 任务用户栈
  • Thread 模式 + CONTROL.SPSEL=1 → 用 PSP 作任务栈
  • 进入异常 → 硬件用 当前 SP 压栈（RTOS 任务被打断时用 PSP）

独立中断栈（可选）：

部分 Cortex-A / RTOS 配置：
  任务 ──PSP──► 任务栈（函数调用）
  异常 ──MSP──► 独立 IRQ 栈（仅硬件帧 + ISR 局部变量）

好处：

  • 任务栈 不必 预留「最坏中断嵌套」深度
  • ISR 深调用不影响任务栈 canary 边界

Cortex-M 常见做法：

  • 不单独分 IRQ 栈；在 任务栈大小 里预留 configMINIMAL_STACK_SIZE + 嵌套裕量
  • FreeRTOS：configISR_STACK_SIZE（部分移植用于 MSP）

栈溢出在中断场景：

任务栈已满 ──► 中断压 8 字硬件帧 ──► 溢出到 TCB/邻任务

检测（10.2.2）：

  • 调度前检查 canary
  • HardFault 时读 CFSR/STKERR 位

Linux 对比（10.10）：

  • 每线程 内核栈 + 用户栈；中断用 per-CPU IRQ stack
  • 内核栈固定 8K/16K，与用户栈分离

估算任务栈 checklist：

  1. 最深调用链局部变量之和
    • 最大中断嵌套 × 硬件帧（~32–64 字节/层）
    • FPU 扩展帧（若用浮点 ISR）
    • 对齐 padding；再 ×1.5 安全系数

题目 1： 在 ARM Linux 中，中断处理使用的是内核栈还是用户进程的栈？为什么？

/* 用户态代码 */
void app(void) {
    char buf[64];
    read(fd, buf, 64);  // 触发系统调用
}

/* 中断在 read 执行期间到来 */
参考答案

在 ARM Linux 中，中断使用当前进程的内核栈（每个进程有独立的内核栈，通常 8KB）。

为什么不用用户栈？ 1. 安全：用户栈在用户空间，内核不能信任用户提供的栈指针 2. 隔离：中断处理是内核行为，不应污染用户栈 3. 可靠性：用户栈可能无效（如栈溢出、页面未映射），内核栈保证有效

在裸机/RTOS 中，中断可能使用独立的中断栈，与任务栈分离，避免中断嵌套时耗尽任务栈。ARM Cortex-M 默认使用 MSP（主栈）处理中断，PSP（进程栈）处理任务。

题目 1： 以下 ISR 实现有什么问题？

10.4

系统调用

本节讲什么

系统调用（System Call） 是用户程序请求 操作系统内核服务 的受控入口：打开文件、创建进程、映射内存等。本节对比 RTOS 无 syscall 直调内核 API 与 Linux 用户态/内核态边界，为 10.4.1–10.4.4 展开，并与 10.9 MMU、10.10 进程线程 呼应。

要点

为什么需要 syscall：

  • 硬件、内存、全局资源不能交给任意用户代码直接操作
  • 内核在 特权级 统一校验参数、拷贝缓冲区、维护内核数据结构

调用链对比：

RTOS 应用:
  xQueueSend() ──► 内核函数（同地址空间，可能仍用户/特权取决于 MPU）

Linux 应用:
  write() ──► libc ──► syscall 指令 ──► 内核 sys_write()

syscall 典型编号（Linux x86/ARM）：

  • 用户把 编号 + 参数 放寄存器 → svc/syscall → 内核查 syscall 表

与 API 的关系（10.4.1）：

层次 示例
系统调用 read, fork, mmap
C 库 API fopen, pthread_create（内部可能调 syscall）
POSIX 可移植接口规范，多种 OS 实现

RTOS 侧：

  • FreeRTOS API 不是 Linux syscall；任务与内核 共享地址空间
  • 有 MPU 时可通过 SVC 做特权切换（较少见）

性能：

  • syscall 涉及 模式切换 + 参数拷贝 → DPDK 等绕过内核 poll 模式
  • 嵌入式 RTOS API 调用 ≈ 普通函数 + 可能调度

  • 10.4.4 strace、man 2
  • 10.9 MMU 保证用户态不能乱访问内核

题目 1： 以下代码直接调用 read() 和通过内联汇编触发 syscall 有什么区别？

.2 操作系统的权限管理

本节讲什么

操作系统通过 权限管理 限制程序能访问的资源：哪些内存可读写的、哪些指令可执行、哪些设备节点可打开。本节从 用户/内核、UID/GID、MPU/MMU 角度建立模型，衔接 10.4.3 特权模式 与 10.9 MMU。

要点

权限的目标：

  • 隔离：进程 A 不能读进程 B 密码
  • 稳定：用户程序 bug 不拖垮内核
  • 安全：非授权不能操作硬件寄存器

Linux 用户态权限：

机制 作用
UID/GID 文件 rwx、进程身份
capability 细分 root 能力（CAP_NET_RAW 等）
seccomp 限制可用 syscall 集合
namespace/cgroup 容器资源边界 
ls -l /dev/mem          # 通常 root 才能 rw
getuid(); open("/etc/shadow", O_RDONLY);  # EACCES

RTOS / 裸机：

  • 通常 无 UID；所有任务 同一特权（或 TrustZone 分世界）
  • MPU（Cortex-M）：最多 8 区域，限制任务访问 RAM 范围
  • 权限靠 编码规范 + 模块划分（ch09），而非硬件进程隔离

内存权限（10.9.2）：

区域 典型权限
代码 .text RX
数据 .data/.bss RW
外设 仅内核/驱动 RW
用户栈 RW，不可执行（NX）

从 syscall 视角：

  • 用户传指针 → 内核 copy_from_user 验证地址是否在用户映射且可写
  • 非法指针 → EFAULT 而非内核崩溃

嵌入式 Linux 启动：

  • 应用以普通用户运行；驱动 内核模块 或 udev 规则授权设备节点

题目 1： 以下代码尝试直接访问物理地址 0x40000000 读取硬件寄存器，在 Linux 用户态会发生什么？

10.4

.3 CPU的特权模式

本节讲什么

CPU 特权级（Privilege Level） 决定当前代码能否执行敏感指令（访问页表、改时钟、关中断等）。本节对比 x86 Ring、ARM Exception Level、Cortex-M Handler/Thread 模式，说明 syscall/异常 如何触发级切换。

要点

x86 Ring 模型：

Ring 0 ── 内核
Ring 3 ── 用户程序
syscall / 中断 ──► 硬件切换到 Ring 0，换栈

ARM AArch64 Exception Level：

EL 典型
EL0 用户应用
EL1 OS 内核
EL2 Hypervisor（KVM）
EL3 Secure Monitor

ARM Cortex-M（嵌入式常见）：

  • 无 Ring 名，用 Thread / Handler 模式 + CONTROL.nPRIV
  • 特权 Thread：可访问 NVIC、部分系统寄存器
  • 非特权 Thread：MPU 限制；SVC 进 Handler 提权

敏感指令示例：

  • 写 TTBR（页表基址）、MSR PRIMASK、WFI/WFE、直接 MMIO（若无映射）

syscall 入口（ARM 32 Linux）：

/* 用户态 */
mov r7, #__NR_write
svc #0          /* 陷入内核 vector_swi */

内核：

  1. 保存用户寄存器到 内核栈
  2. 查 sys_call_table[r7]
  3. 执行 sys_write，copy_from_user
  4. 恢复寄存器返回用户态

RTOS 无 EL0/EL1 分离时：

  • 任务与内核同特权 → 一个野指针 可毁全局
  • 工业方案：MPU 分区 + SVC 网关 + TrustZone

与中断统一：

  • syscall、fault、IRQ 都经 异常向量 → 进入 Handler 模式
  • 10.3.1 硬件压栈与 syscall 压栈类似，返回用 EXC_RETURN

题目 1： ARM 处理器有哪些特权模式？以下哪种模式不能直接执行 MSR CPSR 修改 CPSR？

/* ARM 模式：
   User, FIQ, IRQ, Supervisor, Abort, Undefined, System
   以下在 User 模式执行： */
asm volatile("mrs r0, cpsr\n"
             "bic r0, r0, #0x80\n"

在 User 模式下，MSR CPSR 写 CPSR 的控制位会被忽略（不产生异常，但写入不生效），因为 User 模式没有修改 CPSR 控制位的权限。

syscall 作用 章节

RTOS Linux

  • DPDK user-space driver 避免 read/write 网络包

常见陷阱

  1. syscall(SYS_xxx, ...) 与 libc 包装返回值不一致 libc 包装（如 printf、malloc）失败通常返回 -1 并设 errno；裸 syscall() 返回内核原始值——成功返回 ≥0，失败返回负 errno（如 -EINVAL）。新手写 if (syscall(SYS_xxx, ...) == -1) perror(...) 永远不触发——实际返回是 -22。正确：long r = syscall(...); if (r < 0) { errno = -r; perror(...); }。生产代码用 libc 包装，裸 syscall 仅教学。

  2. strace 默认只追踪主线程 → 多线程漏 syscall strace ./app 只追主线程，多线程程序的子线程 syscall 漏掉。-f 选项跟随 fork/clone，追踪所有线程。坑：用户以为 strace 看到全部 syscall，实际只看 1/N。生产调试多线程必加 -f：strace -f -e trace=futex ./app。

  3. 系统调用号跨架构不同 → 移植崩 SYS_write 在 x86-64 是 1，在 x86-32 是 4，在 ARM 是 4，在 AArch64 是 64。代码硬编码 syscall(1, ...) 在 x86-64 是 write，移植到 ARM 即崩——1 在 ARM 是 exit！必须用 <sys/syscall.h> 的 SYS_xxx 宏，让头文件按架构展开正确编号。坑：BPF/seccomp 过滤规则也按系统调用号——跨架构 seccomp 配置必须每架构独立。

自测题

1.（选择） gettimeofday() 在现代 Linux 上通常不进入内核态，原因是？ - A. 内核不支持 - B. 通过 vDSO 在用户态完成 - C. 编译器优化掉了 - D. 时间不需要内核参与

答案

B。vDSO（virtual Dynamic Shared Object）是内核映射到每个进程用户态的共享页，包含 gettimeofday、clock_gettime、getcpu 等高频只读 syscall 的用户态实现。内核维护的时钟数据结构通过 vDSO 暴露给用户态，进程直接读共享页即得时间，无 syscall 开销。坑：旧内核或某些架构不支持 vDSO，回退到真 syscall。性能敏感代码不要假设一定走 vDSO——profile 验证。DPDK 等用户态轮询框架通常不用 gettimeofday，用 TSC 寄存器（rdtsc）直接读硬件计数器。

2.（判断） fork() 后子进程继承父进程所有打开的文件描述符。

答案

对。fork 复制进程地址空间（COW）和文件描述符表——子进程继承父进程所有打开的 fd，指向同一打开文件描述（struct file），共享文件偏移量。父子都 read(fd) 会互相推进偏移量。坑： 1. 父子都 close(fd) 才真正关闭底层文件。 2. 父子并发 write 同一 fd 会交错（除非用 O_APPEND 或 flock）。 3. execve 后未设 FD_CLOEXEC 的 fd 仍保留——安全漏洞。约定：所有 fd 默认设 O_CLOEXEC（open 时或 fcntl）。

3.（踩坑） 程序用 syscall(SYS_open, "/etc/cfg", O_RDONLY) 在 x86-64 编译运行正常，移植到 ARM 32 即崩。/etc/cfg 文件确实存在。为什么？

答案

系统调用号跨架构不同。SYS_open 在 x86-64 = 2，在 ARM 32 = 5；更糟的是 SYS_open 在某些新架构（AArch64）已被废弃，推荐 SYS_openat。但真坑常在：用户硬编码 syscall(2, ...) 而非 syscall(SYS_open, ...)——x86-64 上 2 是 open，ARM 上 2 是 fork！代码尝试把字符串当 fork 的参数，返回 -EFAULT 或 -ENOSYS。 修复： 1. 永远用 SYS_xxx 宏，不硬编码数字。 2. 优先用 libc 包装（open()），自动处理架构差异。 3. 新代码用 openat(AT_FDCWD, ...) 替代 open()——open 在新架构已废弃。 教训：syscall 是架构相关 ABI，跨架构代码必须用宏。

4.（应用） 用 strace 定位一个程序"卡住读文件"的问题：程序看似卡在 read，但文件其实没有数据可读。给出 strace 命令和解读方法。

答案 
# 1. 基础追踪
strace -f -e trace=open,openat,read,write,poll,select,epoll_wait ./app

# 2. 看时间戳找卡住点
strace -f -T -tt -e trace=read,poll ./app
# 输出：13:45:22.123456 read(3, ..., 4096) = -1 EAGAIN (资源暂时不可用) <0.000012>
#       13:45:22.123468 poll([{fd=3, events=POLLIN}], 1, -1) = 1 ([{fd=3, revents=POLLIN}]) <0.500123>
#       ↑ poll 等 0.5 秒才返回，说明无数据可读

# 3. 看文件描述符指向哪个文件
ls -l /proc/$(pidof app)/fd/3
# lrwx------ 1 user user 64 ... /proc/.../fd/3 -> /dev/uart0

解读： - -f：跟随子进程/线程。 - -T -tt：每个 syscall 打印耗时和精确时间戳——找出"卡住"的 syscall。 - -e trace=...：只看关心的 syscall，过滤噪音。 - EAGAIN + poll 组合：非阻塞读 + 等待——正常模式。 - poll(..., -1) 无限等：若长时间返回 0 或不返回，是文件无数据。 - /proc/PID/fd/N：看 fd 实际指向哪个文件——确认是 UART、socket 还是普通文件。 延伸：ltrace 追踪库函数调用，perf trace 是 strace 的高性能替代（基于 eBPF）。

本节讲什么

文件系统（FS） 是在存储介质上实现的 数据组织格式：如何找文件、存内容、管理空闲块与元数据。本节介绍 inode、目录项、超级块 及 常见嵌入式 FS 选型。

要点

mount -t ext4 /dev/mmcblk0p2 /mnt/data

  2. 内核 mount root
  3. init 脚本 mount /proc /sys /dev
  4. 再 mount data 分区 到 /var 或 /userdata

RTOS：

  • FatFs f_mount(&fs, "0:", 1) 类似逻辑，无内核 VFS

现象 可能原因

can't read superblock 分区偏移错、介质损坏

题目 1： 嵌入式系统中，CPU 如何区分访问的是 RAM、ROM 还是外设寄存器？

// 假设 ARM SoC 地址映射
// 0x00000000 - 0x0000FFFF: Boot ROM
// 0x40000000 - 0x4000FFFF: 外设寄存器 (UART/GPIO)
// 0x60000000 - 0x7FFFFFFF: DDR RAM

volatile uint32_t *ram = (uint32_t *)0x60000000;

工作原理：SoC 内部的总线矩阵根据地址范围将访问路由到不同设备。CPU 只发出地址+读/写信号，由硬件译码器决定目标。volatile 关键字确保编译器不优化掉对外设寄存器的读写。

两种 I/O 模式：Memory-Mapped I/O（ARM/x86，外设寄存器和内存统一编址，用 volatile 指针访问）和 Port-Mapped I/O（x86 独有，使用独立的 I/O 地址空间，通过 in/out 指令访问）。嵌入式 ARM 几乎都是 Memory-Mapped I/O。

题目 1： 以下代码对同一地址先写后读，但读到的值和写入的不一样，可能的原因是什么？

volatile uint8_t *reg = (uint8_t *)0x40000010;
*reg = 0xFF;          // 写入 0xFF
uint8_t val = *reg;   // 读回 0x10，不是 0xFF
参考答案

可能原因： 1. 寄存器是只写的：某些硬件寄存器只能写不能读，读操作返回未定义值 2. 读写寄存器不同：很多 UART 接口中，同一个地址写时是 THR（发送寄存器），读时是 RBR（接收寄存器） 3. 寄存器是只读状态寄存器：写入被忽略，读取返回硬件当前状态 4. 寄存器有副作用：读取操作会清除标志位（如中断状态寄存器读后自动清零） 5. 寄存器位宽不匹配：写 8 位但硬件寄存器是 32 位

题目 1： 以下链接脚本将变量放在特定地址，启动代码需要做什么？

/* 链接脚本片段 */
SECTIONS {
    . = 0x08000000;
    .data : { *(.data) }
    . = 0x20000000;
    .bss : { *(.bss) }
}

/* C 代码 */
int global_var = 42;    // .data 段
int uninit_var;         // .bss 段
参考答案

.data 和 .bss 在不连续的地址（.data 在 Flash 0x08000000，.bss 在 RAM 0x20000000），启动代码必须做两件事：

  1. 从 Flash 拷贝 .data 到 RAM：C 标准要求全局变量有初始值，但 .data 段的初始值存储在 Flash 中，运行时需要在 RAM 中，启动时要从 Flash 加载到 RAM。

  2. 清零 .bss 段：C 标准要求未初始化的全局变量为 0，但 .bss 段在 RAM 中，上电后内容随机，启动时必须清零。

启动代码通过链接脚本导出的符号（_data_load, _data_start, _data_end, _bss_start, _bss_end）来执行拷贝和清零操作，然后调用 main()。

10.6

本节讲什么

上电后 谁执行第一条指令、代码从 Flash 还是 RAM 跑、如何跳到 Linux 或 RTOS？本节对比 XIP、RAM 执行、U-Boot 链式加载，与 10.5.3 rootfs、demo03 qemu-arm 环境呼应。

要点

Cortex-M 复位流程：

1. PC = 向量表[1]（Reset_Handler）
2. 初始化 SP（向量表[0]）
3. startup：拷贝 .data、清零 .bss
4. SystemInit：时钟、可选 VTOR 重定位向量表
5. main() 或 os_start()

XIP（eXecute In Place）：

  • .text 链接在 Flash 地址；CPU 直接从 Flash 取指
  • .data 初值在 Flash，启动时 拷贝到 RAM
  • 优点：省 RAM；缺点：Flash wait state、不能原地改代码

Load to RAM：

  • Bootloader 把镜像 拷贝到 SRAM/SDRAM 再跳转
  • 适合 大程序、加密固件解密后运行

多级 Boot（Linux SoC）：

ROM BootROM
  → SPL（片上 SRAM，初始化 DDR）
  → U-Boot（Flash/eMMC）
  → fitImage: kernel + dtb + initramfs
  → Linux

U-Boot 常用：

setenv bootcmd 'mmc dev 0; fatload mmc 0:1 ${kernel_addr_r} zImage; bootz'
saveenv

RTOS 与 Linux 同芯片：

题目 1： XIP（就地执行）和 Load-and-Run（加载执行）两种启动方式的区别是什么？

// 方式A：XIP (eXecute In Place)
//   代码直接在 NOR Flash 中执行
//   0x00000000: NOR Flash (存放代码)
//   0x20000000: RAM (存放数据)

// 方式B：Load and Run
//   Bootloader 先将代码从 NAND Flash/SD卡 拷贝到 RAM
//   然后跳转到 RAM 执行

XIP（就地执行）：代码直接在 NOR Flash 中执行。优点：启动快（无需拷贝代码）、节省 RAM。缺点：NOR Flash 读取慢、写入慢、成本高。适合小代码量、快速启动场景（如 STM32 从内部 Flash XIP）。

Load-and-Run（加载执行）：代码从 NAND/SD 拷贝到 RAM 执行。优点：RAM 执行快、可用大容量廉价 NAND。缺点：启动慢、需要足够 RAM。适合大代码量、Linux 等操作系统。

关键区别：XIP 的代码段地址 = Flash 物理地址，CPU 直接取指执行；Load-and-Run 的代码段地址 = RAM 地址，但初始存储在 Flash，需 Bootloader 搬运。NOR Flash 支持随机读取可以 XIP，NAND Flash 只能按页读取不能 XIP。

题目 1： 以下代码操作 GPIO 点灯，为什么需要先使能时钟？

题目 1： 以下两种 I/O 访问方式的区别是什么？

本节讲什么

要点

寄存器操作三部曲：

  1. 读 当前值（若需保留其他位）
  2. 改 目标位（OR/AND/XOR）
  3. 写 回寄存器
uint32_t cr = UART->CR;
cr |= UART_CR_TX_EN;
cr &= ~UART_CR_RX_EN;
UART->CR = cr;

头文件组织（ch09）：

/* hw_uart_regs.h — 偏移与位掩码，无逻辑 */
#define UART_CR_TX_EN  (1u << 3)
#define UART_SR_RXNE   (1u << 5)

读清 vs 写 1 清：

  • 手册必须看清：读 DR 清 RXNE vs 写 1 清中断标志
  • 写错 → 丢数据或中断风暴

原子性与并发：

  • 单字段 RMW 非原子 → 多任务/ISR 同时改 → 关中断或 mutex 保护同一寄存器
  • 若硬件提供 SET/CLR 寄存器（写 1 置位/清位）→ 避免 RMW

与 Linux 内核：

  • readl/writel + regmap 抽象
  • 用户态通过 ioctl 间接配置，不直接摸 MMIO（安全）

题目 1： 以下代码操作 32 位寄存器（设置 bit3、清除 bit5、翻转 bit7），在中断环境下有什么问题？

volatile uint32_t *reg = (uint32_t *)0x4000000C;

*reg |= (1 << 3);   // 设置 bit3
*reg &= ~(1 << 5);  // 清除 bit5
*reg ^= (1 << 7);   // 翻转 bit7
参考答案

读-改-写的原子性问题：|= 和 &= 实际是"读->改->写"三步操作。如果在这三步之间发生中断，且中断中也修改了同一寄存器，会导致数据丢失。

例如：主程序读到 reg=0x00，正准备改写，此时中断发生并设置了 bit5（reg=0x20），中断返回后主程序写回 0x08，覆盖了中断的修改，bit5 丢失。

解决方案： 1. 关中断：disable_irq() -> 修改 -> enable_irq() 2. 硬件原子操作：如 ARM 的 bit-banding 或单指令 read-set-write 3. 某些寄存器有特殊行为：写1清零（W1C）的寄存器用 |= 设置其他位时可能意外清除标志位

本节讲什么

要点

常用宏：

#define BIT(n)          (1u << (n))
#define BITS(h, l)      (((1u << ((h)-(l)+1)) - 1u) << (l))
#define REG_SET(r, m)   ((r) |= (m))
#define REG_CLR(r, m)   ((r) &= ~(m))
#define REG_TOGGLE(r,m) ((r) ^= (m))
#define FIELD_GET(v,h,l) (((v) >> (l)) & BITS((h)-(l),0))
#define FIELD_PREP(val,h,l) (((val) << (l)) & BITS(h,l))

示例：配置 GPIO 模式：

/* MODER: 每 pin 2 bit，pin5 设为 AF(10) */
uint32_t moder = GPIO->MODER;
moder &= ~(3u << 10);      /* 清 pin5 */
moder |=  (2u << 10);      /* AF 模式 */
GPIO->MODER = moder;

提取状态：

if (UART->SR & UART_SR_RXNE)
    byte = UART->DR;

注意符号扩展：

/* 坏：1<<31 在 32 位 int 未定义 */
#define BIT31  (1u << 31)   /* 用 unsigned */

__builtin_popcount(flags);
__builtin_clz(ready_bitmap);   /* 10.2.1 调度 */

  • 宏放 hw_*_regs.h；逻辑放 driver .c

题目 1： 以下宏定义实现了什么功能？有什么潜在问题？

#define BIT(n) (1 << (n))

#define CLR_BIT(reg, n)  (reg &= ~BIT(n))

注意事项： 1. volatile 必须加：确保编译器不优化掉寄存器访问 2. 结构体对齐：编译器可能插入 padding，应使用 __packed 或手动确保对齐 3. 保留寄存器：硬件手册中某些地址保留不用，应加保留成员占位（如 RESERVED[2]） 4. 不保证原子性：结构体访问仍然是非原子的读-改-写，需要额外保护

10.8

.3 位域

本节讲什么

C 位域（bit-field） 可把 struct 成员映射到寄存器各位，读起来像手册表格。本节说明 语法、对齐/endian 陷阱 与 何时用手动掩码更可靠。

要点

语法示例：

typedef struct {
    volatile uint32_t enable : 1;
    volatile uint32_t mode   : 2;
    volatile uint32_t        : 5;   /* 保留 */
    volatile uint32_t div    : 8;
} __attribute__((packed)) clk_cr_bits_t;

/* 不推荐：对 MMIO 整 struct 赋值 */

问题 1：实现定义布局：

  • 位域 顺序、跨字节 由 ABI 决定
  • 不同编译器/优化 可能与硬件位序不一致

问题 2：非原子 RMW：

reg->mode = 2;  /* 可能编译成 读-改-写 整字 */
  • ISR 与任务并发改不同位域 → 互相覆盖

问题 3：volatile 位域：

  • C 标准对 volatile struct 位域 访问规则模糊
  • 行业惯例：MMIO 用 uint32_t + 宏掩码（10.8.1）

适用场景：

场景 建议
硬件 MMIO 宏 + 掩码
协议打包报文 位域或手动 shift（明确 endian）
内核 linux/bitfield.h GENMASK 风格

可接受模式：只读解析：

uint32_t raw = mmio_read32(REG);
unsigned mode = (raw >> 3) & 0x3;   /* 显式，可测 */

手册对照流程：

  1. 画表：位号、名称、RW、复位值
  2. #define REG_FOO_MASK 与 SHIFT
  3. 单元测试 golden value 与仿真器比对

与后续衔接

题目 1： 以下代码使用位域定义寄存器结构，有什么潜在问题？

typedef struct {
    uint32_t mode    : 2;  // bit[1:0]
    uint32_t pull    : 2;  // bit[3:2]
    uint32_t speed   : 2;  // bit[5:4]
    uint32_t reserved: 26; // bit[31:6]
} gpio_config_t;

参考答案

位域操作的严重问题：

  1. 不可移植：C 标准不规定位域的内存布局（位序、对齐），不同编译器/架构可能不同。ARM GCC 和 x86 GCC 的位域排列顺序可能相反。
  2. 非原子操作：cfg->mode = 1 编译后通常是读-改-写（读整个 32 位寄存器，修改 bit[1:0]，写回），在中断环境下有竞态条件。
  3. 某些寄存器有副作用：读操作可能清零标志位，位域的读-改-写会意外清除标志。

结论：硬件寄存器映射不要使用位域，用位操作（|=、&=）或位掩码宏。位域只适合用于纯软件结构体（如协议帧解析、内存紧凑存储）。

内存管理单元MMU

本节讲什么

MMU（Memory Management Unit） 实现 虚拟地址到物理地址 的转换，并附带 访问权限、cache 属性。本节说明 MMU 在 Linux 进程隔离 与 RTOS MPU 中的角色，对比 10.4 syscall 与 10.10 进程，是理解现代 OS 的硬件基础。

要点

无 MMU（多数 M0/M3）：

  • 平坦地址；任务共享整个空间 → 野指针全局后果
  • 保护靠 编码 + MPU（可选）

有 MMU（A 核 Linux）：

CPU 读 VA 0x00400000
  → MMU 查 TLB/页表
  → 得 PA 0x8fc00000
  → 检查 AP（用户只读？）→ 违例则 data abort

与多任务关系：

RTOS + MPU Linux + MMU

切换开销 改 MPU 寄存器 换页表 ASID/TTBR
栈保护 guard region guard page + NX

页 fault：

  • 合法：按需 分配物理页（匿名 mmap grow）
  • 非法：SIGSEGV 杀进程

与 10.4.2 权限：

  • 用户态不能写内核页 → syscall 必须 copy_from_user
  • NX bit：栈不可执行，缓解 shellcode

嵌入式 Linux：

  • mmap 映射 /dev/fb、dma-buf
  • 10.6.2 设备内存属性在页表设 Device

代码自测

题目 1： 如果没有 MMU，以下两个进程同时操作同一地址会发生什么？有 MMU 呢？

// 进程 A
int *p = (int *)0x1000;
*p = 42;

// 进程 B (同时运行)
int *q = (int *)0x1000;
*q = 99;

// 最后 *p 的值是？
参考答案

无 MMU：*p 的值是 99（或 42，取决于执行顺序）。因为没有 MMU，两个进程使用同一物理地址空间，地址 0x1000 指向同一块物理内存，后写入的覆盖先写入的。这就是无 MMU 系统中进程间不能有地址冲突（如 uClinux）。

有 MMU：两个进程的虚拟地址 0x1000 映射到不同的物理页，互不干扰。进程 A 写入自己的物理页，进程 B 写入另一个物理页，*p 的值仍然是 42。

MMU 的核心功能：地址翻译（虚拟->物理）、内存保护（每个进程独立页表）、权限控制（读/写/执行）、Cache 支持。无 MMU 系统无法实现进程隔离和 demand paging。

10.9

.1 地址转换

本节讲什么

虚拟地址（VA） 经 页表 转为 物理地址（PA）；TLB 缓存近期映射加速访问。本节介绍 两级/多级页表、段/页粒度 与 地址空间布局，衔接 10.6.2 与 Linux /proc/pid/maps。

要点

为何需要 VA：

  • 每个进程 以为 拥有从 0 开始的连续空间
  • 简化链接：PIE 可加载到任意基址
  • 共享库 映射到多个进程同一物理页

ARM 32 两级页表示意：

VA [31:22] → L1 项 → 指向 L2 表
VA [21:12] → L2 项 → 物理页框号 + 属性
VA [11:0]  → 页内偏移

常见页大小：4 KB；ARM 还支持 1 MB section（启动早期简化）

地址空间布局（Linux 32 位用户态典型）：

0x00000000  ──► 代码 text
            ──► heap ↑
            ──► mmap 区（共享库、文件映射）
0xBF000000  ──► 栈 ↓

查看映射：

cat /proc/self/maps

RTOS 无完整 MMU：

  • 链接脚本固定 物理地址；0x20000000 即 RAM
  • MPU：仅 8 区域，粗粒度保护任务栈

切换进程/任务：

  • Linux：switch_mm 换 TTBR0 + ASID 减 TLB flush
  • RTOS MPU：上下文切换时 重配 MPU 区域

与 DMA：

  • DMA 用 物理地址；CPU 用 VA → 驱动 dma_map_single 得到 bus addr

常见陷阱

  1. TLB 未在切换进程时 invalidate → 跨进程读到旧映射 切换进程时若不清 TLB，新进程的 VA 可能命中旧进程的 TLB 项，读到旧物理页——安全漏洞（跨进程数据泄露）。Linux 用 ASID（Address Space ID）避免每次切换都全清 TLB：每个进程有 8/16 位 ASID，TLB 项标记 ASID，查找时 VA + ASID 都匹配才命中。坑：ASID 溢出时仍需全局 flush——某些老旧 ARM 核 ASID 仅 8 位，进程多时频繁 flush 影响性能。x86 用 PCID 类似机制。

  2. DMA 用 VA 传地址 → 数据写到错误物理页 DMA 控制器不看页表，只认物理地址。代码 dma_start(buf_va, len) 把虚拟地址给 DMA，DMA 写到 buf_va 这个数值对应的物理地址——可能根本不是 buf_va 实际映射的物理页，踩内存。正确：dma_map_single(dev, va, len, dir) 返回 bus address（物理地址或 IOMMU 映射地址），DMA 用返回值。坑：virt_to_phys 在直接映射区可用，但 vmalloc / 用户态地址不行——必须走 DMA API。

  3. 大页（hugepage）与普通页混用 → TLB 压力反而上升 大页（2MB/1GB）减少 TLB 项数量，降低 TLB miss。但若程序随机使用大页（如部分 mmap 用大页、部分用普通页），TLB 反而碎片化——大页和普通页 TLB 通常分开缓存（ITLB/iTLB、L1/L2 dTLB、huge TLB），混用占满两种 TLB。约定：大页用于大块连续分配（数据库缓冲池、DPDK mempool），零散分配用普通页。madvise(MADV_HUGEPAGE) 提示内核透明大页（THP），但 THP 不是保证。

自测题

1.（选择） 32 位 ARM 二级页表中，4KB 页的 VA 拆分是？ - A. [31:20] L1 + [19:12] L2 + [11:0] offset - B. [31:22] L1 + [21:12] L2 + [11:0] offset - C. [31:12] L1 + [11:0] offset - D. [31:24] L1 + [23:16] L2 + [15:8] L3 + [7:0] offset

答案

B。32 位 ARM 二级页表： - L1 索引：VA[31:22]，共 10 位 → 1024 项 L1 表 - L2 索引：VA[21:12]，共 10 位 → 1024 项 L2 表 - 页内偏移：VA[11:0]，共 12 位 → 4KB 页 每项 L1 指向一个 L2 表（4KB），每个 L2 表 1024 项 × 4 字节 = 4KB——刚好一页。64 位 ARM（AArch64）用 4 级或 5 级页表，每级 9 位索引，VA 48/57 位。

2.（判断） RTOS（如 FreeRTOS on Cortex-M）通常不启用 MMU。

答案

对。Cortex-M 系列（M0/M3/M4/M7/M33）没有完整 MMU——只有 MPU（Memory Protection Unit），8 或 16 个区域，粗粒度保护。RTOS 通常： - 链接脚本固定物理地址（0x20000000 是 RAM，0x08000000 是 Flash）。 - 不做 VA→PA 转换，CPU 直接用物理地址。 - MPU 用于保护任务栈/特权区，但不提供"每进程独立地址空间"。 Linux on Cortex-A 才用完整 MMU——A 系列有 MMU，可跑 Linux；M 系列无 MMU，跑 RTOS 或裸机。坑：RTOS 代码移植到 Linux 时，"直接访问物理地址"需改为 mmap(/dev/mem) 或 ioremap。

3.（踩坑） 驱动代码：

void *buf = vmalloc(4096);           /* 内核虚拟地址 */
memset(buf, 0, 4096);
dma_start(phy_addr_of(buf), 4096);   /* 期望 DMA 写到 buf */

DMA 写完后 buf 内容没变。为什么？

答案

vmalloc 返回的虚拟地址不是直接映射——phy_addr_of(buf) 用 virt_to_phys 对 vmalloc 区是错误的，返回的物理地址可能任意（vmalloc 用非连续物理页拼成连续 VA）。DMA 写到该"物理地址"对应的任意物理页，不是 buf 实际映射的页。 修复：

/* 方案一：用 dma_alloc_coherent 分配 DMA 友好内存 */
void *cpu_addr;
dma_addr_t dma_handle;
cpu_addr = dma_alloc_coherent(dev, 4096, &dma_handle, GFP_KERNEL);
/* cpu_addr 给 CPU 用，dma_handle 给 DMA 用 */
dma_start(dma_handle, 4096);

/* 方案二：用 dma_map_single 映射已有内存 */
dma_handle = dma_map_single(dev, buf, 4096, DMA_TO_DEVICE);
dma_start(dma_handle, 4096);
/* 完成后 dma_unmap_single(dev, dma_handle, 4096, DMA_TO_DEVICE); */

关键：DMA 地址必须通过 DMA API 获取，不能用 virt_to_phys——后者只对直接映射区（__pa）有效。某些平台有 IOMMU，DMA 地址甚至不是物理地址，是 IOMMU 分配的总线地址。

4.（应用） 给定一个用户态地址 void *p，写代码：① 判断是否可读；② 获取其物理地址（若有权限）。说明限制。

答案 
#include <stdio.h>
#include <unistd.h>
#include <fcntl.h>
#include <stdint.h>
#include <sys/mman.h>

int main() {
    volatile char *p = (volatile char *)0x12345678;  /* 待测地址 */

    /* ① 判断是否可读：用 pipe + write 触发拷贝 */
    int pipefd[2];
    pipe(pipefd);
    char c = *p;                       /* 直接读：可能 segfault */
    /* 安全做法：mincore 判断是否驻留，但不验证权限 */

    /* ② 通过 /proc/self/pagemap 取物理地址 */
    uint64_t vaddr = (uint64_t)p;
    int fd = open("/proc/self/pagemap", O_RDONLY);
    lseek(fd, (vaddr / 4096) * 8, SEEK_SET);
    uint64_t entry;
    read(fd, &entry, 8);
    close(fd);

    if (entry & (1ULL << 63)) {        /* bit 63 = present */
        uint64_t pfn = entry & ((1ULL << 55) - 1);
        uint64_t paddr = (pfn << 12) | (vaddr & 0xFFF);
        printf("VA %p → PA %llx\n", p, (unsigned long long)paddr);
    } else {
        printf("VA %p not present\n", p);
    }
    return 0;
}

限制： 1. ① 判断可读：用户态无干净方法——mincore 只查驻留，不查权限；write(pipe, &p, 1) 若 p 不可读会返回 EFAULT，但仍是 syscall 开销。最可靠是 SIGSEGV handler + setjmp/longjmp，但侵入性强。 2. ② 物理地址：/proc/self/pagemap 需 root 或 CAP_SYS_ADMIN（内核 4.0+ 限制，防侧信道攻击）。物理地址对用户态程序几乎无用——不能直接 mmap 物理地址（需 /dev/mem），多进程下 VA→PA 映射随时变（swap、迁移）。 3. 生产代码几乎不需做这两件事——内核/驱动才关心物理地址，用户态用 VA 抽象即可。

10.9

.2 权限管理

本节讲什么

页表项中的 AP（Access Permission）、UXN/PXN 等位决定 谁能读写的、能否执行。本节把 MMU 权限 与 10.4.2 OS 权限、用户/内核态 统一起来。

要点

ARM 页表属性（简化）：

属性 含义
AP 特权/用户，读/写组合
UXN 用户态不可执行
PXN 特权不可执行（用户页）
TEX/CB cacheable / bufferable

典型映射策略：

内核代码：  特权 RX，用户不可访问
内核数据：  特权 RW
用户代码：  用户 RX
用户栈/堆：  用户 RW，NX
MMIO：      特权 RW，Device，无 cache

违规访问：

  • 用户读内核地址 → data abort → 内核发 SIGSEGV
  • 执行栈上代码 → NX fault

syscall 与权限：

  • 用户传指针 → 内核 access_ok + copy_from_user 验证映射且 可写
  • 避免 Time-of-check-time-of-use；内核直接 copy

MPU（Cortex-M）对比：

/* 区域：任务栈 RW，无 execute */
MPU->RBAR = stack_base | VALID;
MPU->RASR = SIZE | AP_FULL | XN;
  • 任务切换 重配 MPU；越界 → MemManage fault

安全扩展：

  • TrustZone：安全/非安全世界不同页表
  • SELinux：在 MMU 之上再加 MAC 策略

与多任务 bug：

  • RTOS 无 MMU：指针错误 立即破坏内核
  • Linux：多数越界 只杀自己进程

  • 10.10 线程共享地址空间 → 权限相同，靠同步

代码自测

题目 1： 以下代码尝试在用户态执行特权指令，会发生什么？

// x86-64 用户态尝试
asm volatile(
    "mov %%cr0, %%rax\n"  // 读取控制寄存器 CR0
    : "=a"(cr0)

原因：CPU 在用户态（Ring 3 / ARM User mode）时，特权指令被硬件拦截。用户态进入内核态的唯一合法途径是系统调用（syscall/svc 指令）。

MMU 的权限管理通过页表项属性实现：读/写/执行权限位、用户/特权位（U/S）、NX 位（No eXecute）等。这些权限由 MMU 在每次内存访问时检查，违规时触发缺页异常。

题目 1： 进程、线程和协程的根本区别是什么？以下代码各创建了什么？

// Linux 进程

if (pid == 0) {
    execlp("ls", "ls", NULL);

// Linux 线程

参考答案

三者根本区别： - 进程：独立地址空间，内核调度，切换开销大（切换页表/TLB刷新），通信需 IPC - 线程：共享进程地址空间，内核调度，切换开销中等（切换寄存器/栈），通信用共享变量（需同步） - 协程：用户态调度，不进入内核，切换开销小（切换栈指针），无法利用多核

适用场景：进程用于需要强隔离（如浏览器每个 tab）；线程用于 CPU 密集型并行计算；协程用于 I/O 密集型高并发（如 Web 服务器、Go 的 goroutine）。

.1 进程

本节讲什么

进程 是 Linux 中 资源分配与隔离 的基本单位：独立 虚拟地址空间、文件描述符表、PID。本节说明 fork/exec/wait、与 10.9 MMU、10.4 syscall 的关系，对比 RTOS 无进程 模型。

要点

进程拥有什么：

struct task_struct（内核）
  ├── mm_struct     → 页表、VMA（**10.9.1**）
  ├── files_struct  → fd 表
  ├── fs_struct     → cwd, root
  └── pid, 信号, 调度实体 ...

创建流程：

pid_t pid = fork();
if (pid == 0) {
    execl("/bin/child", "child", NULL);
} else {
    wait(NULL);
}
  • fork：复制地址空间（COW 优化，写时才复制物理页）
  • execve：替换当前进程镜像为新程序
  • wait：收尸，避免僵尸进程

与 syscall（10.4.4）：

fork  → sys_clone(flags=SIGCHLD)
exec  → sys_execve
exit  → sys_exit_group

隔离意义：

  • 进程 A 越界访问 → MMU fault，通常不影响 B
  • RTOS 任务：同地址空间，错误指针破坏全局（10.9 对比）

嵌入式 Linux：

  • init（PID 1）spawn 各 daemon
  • 容器 = namespace 限制后的「进程视图」

与 10.5 文件：

  • 每进程独立 fd；open 返回 int fd
  • fork 后 fd 共享引用计数；exec 常 FD_CLOEXEC

与后续衔接

  • 10.10.2 线程是共享 mm 的轻量进程
  • 10.4.2 UID/CAP 按进程
  • 全书：网关跑 Linux 多进程 vs MCU 跑 RTOS

代码自测

题目 1： fork() 之后父子进程的变量关系是什么？以下代码输出什么？

int global = 100;
int main(void) {
    int local = 200;
    pid_t pid = fork();
    if (pid == 0) {
        global++;
        local++;
        printf("child: global=%d local=%d\n", global, local);
    } else {
        sleep(1);
        printf("parent: global=%d local=%d\n", global, local);
    }
    return 0;
}
参考答案

输出： child: global=101 local=201 parent: global=100 local=200

原因：fork() 创建子进程，子进程获得父进程地址空间的副本（copy-on-write）。子进程修改 global 和 local 时触发 COW，分配新的物理页，不影响父进程。

fork() 的关键行为：返回值不同（父进程返回子进程 PID >0，子进程返回 0）；资源继承（文件描述符、信号处理）；COW（写时复制，不真正复制内存，只复制页表，写入时才复制对应页）。进程是资源分配的基本单位。

.2 线程

本节讲什么

线程 共享所属进程的 地址空间与 FD，独立 栈、寄存器、调度；是 Linux 与 RTOS 任务 最接近的概念。本节介绍 pthread、clone 标志、与 FreeRTOS 任务 的对照及 SMP 绑核。

要点

线程 vs 进程：

进程 P
 ├── 线程 1（主线程）─ 栈1
 ├── 线程 2         ─ 栈2  ─┐
 └── 线程 3         ─ 栈3   ├─ 共享 heap、全局、代码
                            └─ 需 mutex（**10.2.4**）

pthread 示例：

void *worker(void *arg) {
    /* 独立栈；共享 g_counter */
    pthread_mutex_lock(&mtx);
    g_counter++;
    pthread_mutex_unlock(&mtx);
    return NULL;
}

pthread_t t;
pthread_create(&t, NULL, worker, NULL);
pthread_join(t, NULL);

内核实现：

  • pthread_create → clone(CLONE_VM | CLONE_FILES | ...)
  • 与 fork 区别：不复制 mm，共享页表

RTOS 任务对照：

FreeRTOS Linux pthread
xTaskCreate pthread_create
任务栈 pthread_attr_setstacksize
vTaskDelay nanosleep
优先级 0–configMAX nice/ SCHED_FIFO
vApplicationStackOverflowHook guard page + valgrind

uC/OS-III / FreeRTOS Hook：

  • Idle Hook：低功耗 WFI
  • StackOverflowHook：调试栈（10.2.2 canary 互补）

SMP 与 DPDK：

/* DPDK：每 lcore 一线程，绑 CPU，无抢占式内核调度干扰 */
rte_eal_init(...);
RTE_LCORE_FOREACH_WORKER(lcore_id) {
    rte_eal_wait_lcore(lcore_id);
}
  • 并行 跑在物理核；与 10.1 并发 区分

陷阱（全书 recurring）：

  • 未保护全局 → 数据竞争
  • 栈过大 在进程内仍占虚拟空间
  • 线程频繁创建 → 用 10.10.3 线程池

与后续衔接

  • 10.10.3 线程池复用
  • 10.10.4 协程更轻
  • demo06 RTOS 任务 ≈ 单进程多 pthread 的裸机版

代码自测

题目 1： 以下多线程代码有什么问题？

int counter = 0;
void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;
    return NULL;
}
int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);  // 期望 2000000
    return 0;
}
参考答案

counter++ 不是原子操作，多线程并发执行会产生数据竞争，最终 counter 通常小于 2000000。

counter++ 实际是三步操作：读 counter 到寄存器 -> 寄存器 +1 -> 写回 counter。如果 t1 读到 counter=50，此时 t2 也读到 counter=50，两者各加 1 后写回 51，丢失了一次更新。

线程与进程的关键区别：线程共享进程地址空间，counter 是全局变量，两个线程同时读写没有同步保护。

解决方案：用互斥锁（pthread_mutex）保护临界区，或用原子操作（atomic_fetch_add）。线程是 CPU 调度的基本单位。

.3 线程池

本节讲什么

线程池 预先创建固定数量工作线程，从 任务队列 取活执行，避免 频繁 create/join 开销，并限制 并发度 防止资源耗尽。本节衔接 10.2.4 queue、demo05_queue 与服务器/网关常见架构。

要点

基本结构：

提交者 ──► [任务队列] ◄── worker 线程 1..N
              │ mutex + cond
              └─ 阻塞等待 / 唤醒

伪代码：

void pool_submit(pool_t *p, void (*fn)(void *), void *arg) {
    task_t t = { fn, arg };
    pthread_mutex_lock(&p->mtx);
    queue_push(&p->q, t);
    pthread_cond_signal(&p->cv);
    pthread_mutex_unlock(&p->mtx);
}

void *worker(void *arg) {
    for (;;) {
        pthread_mutex_lock(&p->mtx);
        while (queue_empty(&p->q))
            pthread_cond_wait(&p->cv, &p->mtx);
        task_t t = queue_pop(&p->q);
        pthread_mutex_unlock(&p->mtx);
        t.fn(t.arg);
    }
}

参数 tuning：

参数 考虑
线程数 CPU 核数、I/O 等待比例
队列长度 背压、拒绝策略
栈大小 与 10.2.2 同理

RTOS 对应：

  • 静态创建 N 个任务，queue 投递工作项（demo05_queue、demo06）
  • 无 pthread 开销；任务数编译期固定

与 10.2.1 阻塞：

  • worker 在 空队列 上 BLOCKED → 不占 CPU spin
  • 高优先级 ISR → queue_send_from_isr 唤醒（10.3.3）

反模式：

  • 无界队列 → 内存暴涨
  • 线程过多 → 上下文切换开销 > 计算

Linux 生态：

  • libpthread 自实现；或使用 thread pool 库、io_uring 异步

与后续衔接

  • 10.10.4 协程池处理更高并发 I/O
  • demo05_queue 生产者-消费者模型
  • 边缘节点：线程池跑协议解析，ISR 只入队

题目 1： 以下线程池实现有什么问题？

#define POOL_SIZE 4
pthread_t threads[POOL_SIZE];
void *task_queue[100];
int queue_head = 0, queue_tail = 0;

void *worker(void *arg) {
    while(1) {
        if (queue_head != queue_tail) {
            void (*task)(void) = task_queue[queue_head];
            queue_head = (queue_head + 1) % 100;
            task();
        }
    }
}
void submit(void (*task)(void)) {
    task_queue[queue_tail] = task;
    queue_tail = (queue_tail + 1) % 100;
}
参考答案

问题： 1. 忙等待：while(1) 内不断轮询，CPU 空转 2. 无同步保护：queue_head 和 queue_tail 被多线程同时读写，数据竞争 3. 队列满无处理：submit 不检查队列是否满，会覆盖未处理的任务 4. 无退出机制：worker 线程无法正常退出

改进：使用条件变量 + 互斥锁。worker 在无任务时 pthread_cond_wait 阻塞等待（不占 CPU），有任务时被唤醒。submit 加锁入队后 pthread_cond_signal 通知 worker。任务在锁外执行避免阻塞其他 worker。线程池的核心思想：预创建固定数量线程，复用线程避免频繁创建/销毁开销。

.4 协程

本节讲什么

协程（Coroutine） 是 用户态 轻量级执行单元，主动 yield 切换，无需内核参与。本节对比 线程/RTOS 任务，说明 适用场景与 C 语言实现思路（ucontext 已废弃，可提 libco/自建栈）。

要点

切换成本排序：

协程 yield  <  RTOS 任务切换  <  线程切换  <  进程切换
   用户态          内核/汇编          内核+TLB      fork/mm

协程 vs 线程：

协程 线程
调度 用户库 内核
并行 单核并发 可多核并行
阻塞 syscall 阻塞整个线程（需多线程+协程） 内核调度其他线程
栈 小栈或共享 内核分配

典型用途：

  • 高并发 网络服务器（C20 前 Nginx 用 伪协程 + 多进程）
  • 状态机 写异步逻辑像同步代码（async/await 语言内置）

C 实现思路（概念）：

  1. 独立栈 + 上下文切换（同 10.1.1 TCB，但在用户态）
  2. setjmp/longjmp 教学版（限制多）
  3. 编译器纤程（C++20 coroutine，C 需第三方）

与 RTOS 协作式调度（10.2.1）：

  • 协作 RTOS 任务 ≈ 内核态协程 + 独立栈
  • 协程缺 抢占；长计算需主动 yield

与 10.1 并发：

  • 单线程 + 多协程 = 并发 处理多连接
  • 多线程 × 每线程多协程 = 常见 M:N 模型

局限：

  • 不能利用多核（除非多线程各跑协程调度器）
  • 阻塞式 read 会卡住同线程内所有协程

  • 10.1.1 setjmp 模拟与协程思想同源

题目 1： 协程的 yield() 是如何实现切换的？与线程切换有何区别？

typedef struct {
    void *sp;           // 保存栈指针
    enum { READY, RUNNING, SUSPENDED } state;
} coroutine_t;

coroutine_t *current_co;

void yield(void) {
    current_co->state = SUSPENDED;
    save_stack(&current_co->sp);    // 保存当前栈
    restore_stack(&scheduler_sp);   // 切换到调度器栈
}
参考答案

协程切换的核心：保存/恢复栈指针（SP），不涉及内核。

yield() 的工作流程：保存当前协程的栈指针 -> 恢复调度器的栈指针 -> 调度器选下一个协程 -> resume() 恢复目标协程的栈指针 -> CPU 从协程上次 yield() 的位置继续执行。

与线程切换的区别：协程在用户态切换，只保存 SP 和少量寄存器（约几十 ns）；线程切换在内核态，需保存全部寄存器和页表/TLB（约几 us）。协程是非抢占式（需主动 yield），线程是抢占式（时钟中断）。协程无法利用多核（除非多线程+协程）。

// 场景：
A. Web 服务器处理 10000 个并发连接
