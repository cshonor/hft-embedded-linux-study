驱动向：GNU C 扩展学多少够用？

结论优先 · 对齐 ch06 GNU C 全章 · Primer 驱动 FAQ：8.1
速查表： DRIVER-GNU-C-CHEATSHEET.md

结论

必须了解 GNU C 扩展，但不必专门啃完整本 GNU C 手册。
标准 C 是根基；GNU 扩展是内核/驱动里的「附加语法」——高频就那几类，其余遇查即可。

1. 两个概念

标准 C（C89/C99…） GNU C 扩展（GCC）
是什么 变量、指针、结构体、函数、数组、控制流… GCC 额外语法；纯标准模式可能编不过
和驱动 必须熟练 内核基本只用 GCC；源码里到处是扩展
学法 系统练（K&R / 指针书 / 本仓库 01） 跟驱动源码认高频；冷门现查

Linux 内核：C + 少量 GNU 扩展；不用 C++，不用用户态 libc 那套（内核自有 API）。

2. 驱动里最高频的几类（范围很小）

详见速查表。口头名单：

  1. __attribute__ — 尤其 packed（寄存器布局）、section、unused
  2. 零长 / 柔性数组成员 — 缓冲尾随数据（内核多见 [0] 历史写法；C99 为 []）
  3. 语句表达式 + typeof — min/max/container_of 一类宏
  4. 指定初始化 — of_device_id、.probe =、.compatible =（驱动超高频；C99 已标准化，内核风格仍当「必会阅读」）
  5. asm 内嵌汇编 — 底层、原子、架构相关（先认得出，深挖按需）

3. 误区

❌「写驱动要系统学完全部 GNU 扩展」
✅ 标准 C ≫ 上表高频 ≫ 其余现查

笔试很少默写扩展名词；面试读驱动片段时，看不懂 .compatible = / packed 会立刻露馅。

4. 极简路线

  1. 夯实标准 C：指针、数组、结构体、内存布局
  2. 读简单 platform / of_device_id 驱动，对照 速查表
  3. 深挖时打开本目录 6.x 小节与 demo/，不要先通读全部冷门属性

代码自测

题目 1： 为什么 Linux 内核驱动代码中大量使用 GNU C 扩展？标准 C 不够用吗？

参考答案

Linux 内核只使用 GCC（和 Clang）编译，不追求标准 C 可移植性。内核需要：

  • container_of：需要 typeof 和 __builtin_offsetof（标准 C 没有）
  • 链表/红黑树泛型容器：需要 typeof 推导类型
  • __init/__exit：需要 __attribute__((section)) 自定义段
  • 原子操作/内存屏障：需要内联汇编和 __builtin_*
  • likely/unlikely：需要 __builtin_expect
  • 变长数组/零长数组：内核结构体末尾的柔性数组

标准 C 不够用的本质：内核需要精确控制内存布局、段属性、指令生成，这些超出标准 C 抽象范围。

所以学内核必须学 GNU C 扩展——这是标准 C 到内核的桥梁。

6.1

C语言标准和编译器

本节讲什么

C 语言由 ISO/IEC 标准 定义语法与语义，由 编译器（GCC/Clang） 实现并常附带 GNU 扩展。读 Linux 内核、U-Boot、DPDK 源码前，必须分清「标准 C99/C11」与「-std=gnu11 实际启用的扩展」。本章后续所有语法均建立在此认知之上。

要点

角色 说明
标准 C89/C99/C11/C17/C23，规定可移植子集
编译器 翻译源码 → 目标文件；-std= 选择方言
扩展 __attribute__、语句表达式、typeof 等，非 ISO 必选 
gcc --version
gcc -std=c99   -pedantic -Wall -c foo.c   # 严格标准，扩展报警
gcc -std=gnu11 -Wall        -c foo.c     # Linux 内核/DPDK 常用
  • 内核 Makefile 通常 -std=gnu11（或 gnu89），并依赖大量扩展
  • 移植到 MSVC/IAR 时需逐项替换扩展写法

题目 1： 以下代码在 C89、C99、C11 中分别是否合法？

// C89
for (int i = 0; i < 10; i++) { }  // (A)
int x = 3;  // 语句后声明 (B)
_Static_assert(sizeof(int) == 4, "int must be 4 bytes");  // (C)
参考答案

(A) C89 非法（变量必须在块开头声明），C99 起合法；(B) C89 非法，C99 起合法（允许在任意位置声明）；(C) C11 起合法，C89/C99 没有 _Static_assert。GNU C 扩展在 gcc 中往往超前实现 C99/C11 特性，但跨编译器时应确认标准版本。编译选项 -std=c89/-std=c99/-std=c11 控制标准。

6.1

.1 什么是C语言标准

本节讲什么

C 语言标准 是由 ISO/IEC JTC1 SC22 WG14 维护的规范文档，定义合法程序、库接口与实现约束。它不等于「K&R 书」或「某个编译器手册」——同一源码在不同标准模式下可能合法或非法。

要点

  • 实现（implementation）：编译器 + 标准库 + 运行环境
  • 严格符合（strictly conforming）：仅使用标准语法与标准头，无未定义扩展依赖
  • Hosted vs Freestanding：带 main 和用户态 libc 为 hosted；内核/Bootloader 常为 freestanding（仅 <stddef.h> 等子集）
/* C99 起合法 */
#include <stdint.h>
int main(void) {
    uint32_t x = 0;
    return (int)x;
}

man std    # 部分系统有 standards(7)
gcc -dM -E - < /dev/null | grep __STDC_VERSION__
# __STDC_VERSION__ 199901L → C99；201112L → C11
  • 未定义行为（UB）：标准允许编译器任意假设；优化可能「删掉」看似会执行的代码
  • 嵌入式读源码：看到 GNU 关键字先查是否被 -std=gnu* 打开

题目 1： C 语言标准的意义是什么？C89/C99/C11/C23 各有什么重要特性？

参考答案

C 标准定义了语言的语法、语义和标准库，保证不同编译器上的可移植性。

版本演进： - C89/C90：第一个正式标准。函数原型、void、const、标准库 - C99：// 注释、变长数组(VLA)、long long、stdint.h、__func__、 designated initializer - C11：_Generic、_Static_assert、原子操作、线程支持、_Noreturn - C17/C18：bug 修复版，无新特性 - C23：nullptr、true/false 关键字、#embed、属性语法 [[nodiscard]]

本节讲什么

一份 C 标准通常包含：语言语法与语义、诊断规则、标准库、可移植性限制 与 附录（常见缺陷、库概要）。理解章节划分有助于查「某特性从哪版标准开始合法」。

要点

题目 1： C 语言标准包含哪些部分？以下哪些是标准定义的，哪些是编译器扩展？

// A
int x = 3.14;          // 隐式转换
// B
int arr[n];             // VLA
// C
int *p = (int[])        // compound literal
// D
__attribute__((packed)) // ?
// E
_Static_assert(1, "ok") // ?
参考答案

C 标准包含：语法、语义、预处理、标准库（stdio/stdlib/string/math 等）。

  • A（隐式浮点→整型转换）：标准 C（C89 起）
  • B（VLA 变长数组）：C99 标准（C11 改为可选特性）
  • C（复合字面量 Compound Literal）：C99 标准
  • D（__attribute__）：GCC 扩展，非标准。C23 引入了 [[ ]] 属性语法作为标准替代
  • E（_Static_assert）：C11 标准

判断方法：查 ISO/IEC 9899 标准文档。GCC 文档中标注 "Extension" 的为扩展。gcc -std=c11 -pedantic 会警告非标准用法。

6.1

.3 C语言标准的发展过程

本节讲什么

C 从 K&R 方言演进为 C89 → C99 → C11 → C17 → C23。每版引入新特性；旧代码常混用「编译器扩展 + 后补进标准的特性」。内核与 DPDK 代码时间跨度大，同一树内可能并存多种写法。

要点

版本 年份 代表性新特性
C89/C90 1989/1990 原型、const/volatile
C99 1999 // 注释、stdint.h、inline、变长数组
C11 2011 _Generic、_Atomic、线程、Unicode
C17 2018 缺陷修复，少新特性
C23 2024 typeof、 #embed、attributes 标准化等

GNU 扩展 vs 标准吸收：

  • 指定初始化 [i]=、{.m=}：C99 进标准，GNU 更早有
  • 灵活数组成员 []：C99 标准；GNU 零长度数组 [0] 等价用法
  • 语句表达式 ({ })：仍为 GNU 扩展
  • __attribute__：C23 有 _Attribute，语法不同
gcc -std=c89 -pedantic -c old.c
gcc -std=c11 -c modern.c
  • Linux 内核 6.x： predominantly GNU C + gnu11
  • 新项目若需 MSVC：避免语句表达式与 __attribute__，用宏/portability 层

题目 1： C 语言从 K&R C 到 C89 到 C99 经历了哪些重大变化？

参考答案

K&R C（1978）→ C89（1989/1990）→ C99（1999）→ C11（2011）→ C23（2023）

K&R → C89 变化： - 函数原型：int func(int, char**) 替代 int func()（K&R 不检查参数类型） - void、const、volatile、signed/unsigned 关键字 - 标准库规范化（ANSI C 库）

C89 → C99 变化： - // 行注释（原来只有 /* */） - 变长数组、long long、stdint.h（int32_t 等） - designated initializer：int arr[10] = {[5] = 42}; - __func__ 预定义标识符 - snprintf、vsnprintf 标准化

这些变化直接影响现代 C 编程风格。

6.1

.4 编译器对C语言标准的支持

本节讲什么

编译器通过 -std= 选择语言方言；默认标准 随 GCC 主版本变化。-pedantic 关闭扩展或对其报警；-Wall 与标准合规是两回事。交叉编译 ARM 内核时，Kbuild 已替你选好 flags。

要点

# 查看默认与宏
gcc -dM -E -x c /dev/null | grep -E '__STDC_VERSION__|__GNUC__'

# 常用组合
gcc -std=c11   -pedantic -Wall -Wextra -c app.c
gcc -std=gnu11 -Wall -Werror          -c driver.c   # 允许 GNU 扩展
clang -std=gnu11 -Weverything -c driver.c
选项 效果
-std=c99 / c11 / c17 ISO 模式，扩展受限
-std=gnu99 / gnu11 ISO + GNU 扩展（默认常为此类）
-pedantic 严格 ISO，GNU 扩展产生 warning
-Wpedantic 同上（GCC 4.8+） 
# 某特性是否可用：试编译
echo 'int x[0];' | gcc -std=c99 -x c -c - 2>&1
echo 'int x[0];' | gcc -std=gnu11 -x c -c - 2>&1
  • Clang 在内核/DPDK 构建中 increasingly 使用，仍目标 gnu 方言
  • IAR/Keil：部分扩展不可用，需 #ifdef 隔离

6.3

宏构造「利器」：语句表达式

本节讲什么

语句表达式（statement expression） 语法 ({ statements; expr; }) 把多条语句打包成一个 有值的表达式，是 GNU 扩展。内核 min/max、container_of、原子操作宏都依赖它；没有语句表达式，很多 C 宏无法既安全又返回结果。

要点

#define min(a, b) ({                    \
    typeof(a) _a = (a);                 \
    typeof(b) _b = (b);                 \
    _a < _b ? _a : _b;                  \
})
  • 最后一项 分号前的表达式 为整个 ({}) 的值
  • 内部可声明临时变量，避免宏参数 多次求值
  • -std=gnu11 默认可用；纯 -std=c11 非法

本节讲什么

要点

种类 示例 能否出现在右值位置
表达式 a + b、func() 是
语句 if (x) y;、return 0; 否

6.3

本节讲什么

语句表达式 ({ ... }) 内可含声明、循环、分支；最后一个表达式（带分号）的值类型即为整个语句表达式的类型。GCC 扩展，Clang 兼容。

要点

int abs_diff(int a, int b)
{
    return ({
        int _a = a;
        int _b = b;
        _a > _b ? _a - _b : _b - _a;
    });
}

/* 指针版本 — typeof 配合 */
#define swap_ptr(a, b) do {             \
    typeof(a) _tmp = (a);               \
    (a) = (b);                          \
    (b) = _tmp;                         \
} while (0)

规则摘要：

  • 可有多条语句；最后一条必须是表达式 followed by ;
  • 内部变量作用域仅在 ({}) 内
  • 类型 = 最后表达式的类型（含 const/volatile）
  • 在 -pedantic 下可用 __extension__ ({ ... }) 压制警告

语句表达式：({ 语句序列 }) 的值是最后一个表达式的值。

特点： - 可以在表达式位置使用代码块（声明变量、多条语句） - 块内变量是局部的，不污染外部作用域 - 最后一个表达式的值作为整个语句表达式的值

用途：在宏中实现复杂逻辑，且引入临时变量不冲突。

标准 C 没有语句表达式。C11 的 _Generic 部分弥补了这个需求。

注意：最后一条语句必须是表达式（不能是声明/声明语句），否则值为 void。

6.3

.3 在宏定义中使用语句表达式

本节讲什么

编写「像函数一样返回值」的宏时，语句表达式 + typeof 是标准套路：临时变量保存参数、只求值一次、避免 side effect。本节给出 min/max 与带 if 的安全宏模板。

要点

错误示范

#define BAD_MAX(a, b) ((a) > (b) ? (a) : (b))
/* BAD_MAX(x++, y++)  → x/y 可能 ++ 两次 */

推荐写法

#define MAX(a, b) ({                        \
    typeof(a) __max_a = (a);                \
    typeof(b) __max_b = (b);                \
    __max_a > __max_b ? __max_a : __max_b;  \
})

/* 带分支的宏 */
#define CLAMP(val, lo, hi) ({               \
    typeof(val) __v = (val);                \
    typeof(lo)  __lo = (lo);                \
    typeof(hi)  __hi = (hi);                \
    __v < __lo ? __lo : (__v > __hi ? __hi : __v); \
})
技巧 目的
typeof 临时 类型安全、单求值
唯一变量名 __max_a 避免嵌套宏名冲突（内核用更复杂 token paste）
外层 ({}) 可用于 if (MAX(a,b) > 0) 
/* 语句表达式 + GNU 条件编译 */
#define IS_ERR_OR_NULL(ptr) ({              \
    const void *__p = (ptr);                \
    !__p || (unsigned long)__p >= (unsigned long)-4096UL; \
})

6.4

.3 Linux内核中的container_of宏

本节讲什么

container_of 实现「从成员指针得到结构体指针」，支撑 list_for_each_entry、device 嵌套 platform_device 等模式。定义在 include/linux/container_of.h（或经 kernel.h 间接包含）。

要点

#include <stddef.h>

#define container_of(ptr, type, member) ({              \
    void *__mptr = (void *)(ptr);                         \
    ((type *)((char *)__mptr - offsetof(type, member))); \
})

使用：

struct task t;
struct list_node *n = &t.link;
struct task *tp = container_of(n, struct task, link);
/* tp == &t */

/* 内核链表遍历宏（简化） */
#define list_for_each_entry(pos, head, member)              \
    for (pos = list_first_entry(head, typeof(*pos), member); \
         &pos->member != (head);                            \
         pos = list_entry(pos->member.next, typeof(*pos), member))
  • typeof(*pos)：pos 指针类型由编译器从变量推断
  • 空指针 / 野指针 传入 UB；使用前需保证 ptr 确实来自某 type 实例的成员
  • U-Boot、部分 DPDK 内部 list 宏同构

常见陷阱

  1. ptr 不是该 type 实例的成员指针 → UB 拿一个独立的 struct list_node n（不属于任何 task）调 container_of(&n, struct task, link)，得到的指针指向任意内存，解引用即踩内存。编译器无法检查——宏只做指针算术。 c struct list_node standalone; struct task *bad = container_of(&standalone, struct task, link); bad->id = 1; /* 不可预测的崩溃或静默踩内存 */

  2. 跨类型混用 → 偏移错位 两个结构体都含 struct list_node link，但 link 在各自结构体内的偏移不同。把 A 链表节点塞进 B 链表后再用 container_of(..., struct B, link) 取宿主，会算出错误的基地址。内核里 list_head 之所以能通用，靠的是"宿主类型必须一致"的约定，不是语言保证。

  3. container_of(NULL, ...) → 解引用 NULL 宏内部 (void *)(ptr) 不解引用，但回退后的指针被调用方解引用即 NULL+(-offset)。更隐蔽的是 ptr 本身为 NULL 时 offsetof 仍按编译期常量计算，运行时直接得到非零野指针，崩溃延迟到使用点，难以定位。

6.4

.4 container_of宏实现分析

本节讲什么

逐步展开 container_of 的指针运算与类型转换，理解为何用 char * 做字节级减法、offsetof 如何取得成员偏移，以及内核版本中的 const 检查 trick。

要点

布局

struct task 首地址 ──► [ id | name[16] | link | ... ]
                              ▲
                              └── ptr 指向 link
offset = offsetof(struct task, link)
task_addr = (char *)ptr - offset

/* 标准 C 版（无 typeof） */
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

/* 内核加强：const 成员指针检查（思路） */
#define container_of(ptr, type, member) ({                      \
    void *__mptr = (void *)(ptr);                               \
    static_assert(__builtin_types_compatible_p(                 \
        typeof(((type *)0)->member), typeof(*(ptr))),           \
        "pointer mismatch");                                   \
    ((type *)((char *)__mptr - offsetof(type, member)));       \
})
步骤 说明
(void *)(ptr) 抹除 const 便于中间变量（内核有 const 版本宏）
(char *) 减法 按 字节 回退，与对齐无关
转 (type *) 得到结构体首址 
/* 错误用法 */
struct task *bad = container_of(NULL, struct task, link);  /* UB */
  • list_entry = container_of 别名
  • DPDK RTE_CONTAINER 宏（若存在）同理，读源码时对照 demo 与 rte_ring 结构

常见陷阱

  1. offsetof 不能用在位域上 → 编译错误 offsetof(type, member) 要求 member 是普通成员，不能是位域。如果结构体含位域且想取位域指针，根本拿不到指针——位域不允许 &。误用 offsetof 会在编译期报错，但写代码时容易忘。

  2. __builtin_types_compatible_p 检查可能误判 内核加强版用 typeof(((type *)0)->member) 与 typeof(*(ptr)) 比对。但若 ptr 本身是 const 限定（如 const struct list_node *），而 member 在结构体内不是 const，类型不匹配会静态断言失败。内核为此有 container_of_const 包装。用户态移植要小心 const 传递。

  3. (type *)0 是编译期技巧，不能运行时解引用 typeof(((type *)0)->member) 中的 (type *)0 看起来像解引用 NULL，但仅用于类型推导，编译器不生成访问指令。然而，如果手写版忘了用 typeof 而写成 ((type *)0)->member 取地址，运行时即崩溃。区别在于"求值"还是"求类型"——前者 UB，后者安全。

自测题

1.（选择） offsetof(type, member) 在标准 C 中如何实现？ - A. 运行时计算 &(((type *)0)->member) 的地址 - B. 编译期常量，由编译器内置提供 - C. 调用 __builtin_offsetof 才能使用 - D. 链接器解析

答案

B。offsetof 在 <stddef.h> 中定义，标准要求是整型常量表达式。现代编译器（GCC/Clang/MSVC）都内置 __builtin_offsetof，编译期直接算出偏移，不生成运行时代码。古老的 &(((type *)0)->member) 写法是 GCC 早期实现技巧，运行时不会真解引用 NULL，但标准不保证这种写法安全，现代代码应直接用 offsetof。

2.（判断） container_of 用 (char *) 而非 (void *) 是因为 void * 算术在标准 C 中未定义。

答案

对。GNU C 扩展允许 void * 算术（按 1 字节），但 ISO C 标准不允许。为了在非 GCC 编译器也可移植，统一用 char *——它是标准保证按字节运算的唯一类型。

3.（踩坑） 下列代码在 32 位 ARM 上运行结果是什么？

struct s { char c; int i; } x;
struct s *p = container_of(&x.i, struct s, i);
printf("%p %p\n", (void*)p, (void*)&x);
答案

两个地址相等。offsetof(struct s, i) = 4（因 c 后 3 字节 padding），&x.i = &x + 4，回退 4 字节即 &x。这验证了 container_of 的正确性。但若结构体改为 __attribute__((packed))，offsetof(struct s, i) = 1，回退后仍是 &x，依然正确——offsetof 编译期算出的是真实偏移，无论是否 packed。坑在于未对齐访问：packed 后 &x.i 可能不在 4 字节边界，ARMv5 直接 *(&x.i) 会触发 alignment fault，需用 memcpy 或 get_unaligned。

4.（应用） 写一个带 const 安全检查的 container_of，使得 const T * 成员指针返回 const T_host *。

答案 
#define container_of(ptr, type, member) ({                  \
    const typeof(((type *)0)->member) *__mptr = (ptr);      \
    (type *)( (char *)__mptr - offsetof(type, member) );    \
})

#define container_of_const(ptr, type, member) ({            \
    const typeof(((type *)0)->member) *__mptr = (ptr);      \
    (const type *)( (const char *)__mptr                    \
                    - offsetof(type, member) );             \
})

关键：用 const typeof(...) 接住 ptr，编译器强制传入也必须 const——若传非 const 指针给 container_of_const 会触发 -Wdiscarded-qualifiers 警告。返回 const type * 防止调用方误修改。内核的 container_of 实际更复杂，会保留 const 性质。

常见陷阱

  1. 自定义 section 必须在链接脚本中"接住" → 否则被丢弃 __attribute__((section(".mydata"))) 只把符号放进 .mydata section。如果链接脚本里没有显式 *(.mydata)，链接器可能：丢弃该 section、合并到默认段、或发出 orphan section 警告。自定义 section 不"接住"等于数据丢失，且无编译错误，只在运行时发现读不到数据。

  2. section 名前缀有约定 → 用错前缀会被特殊处理 .text.*、.data.*、.rodata.*、.bss.* 等前缀链接器会按段属性（可执行/可写/只读/零初始化）自动归类。把可写数据放进 .text.mydata（看起来像代码段）会导致段属性错位，触发 segfault 或内存保护异常。自定义段应保持前缀语义一致：.boot.data、.init.text 这种命名是有意为之。

  3. __init 段运行后被释放 → 持有其指针 use-after-free 内核 __init 函数/数据在启动后 free_initmem() 回收。如果某 __init 函数的指针被存到全局变量、之后调用 → use-after-free。内核用 __ref 标注豁免段检查，但用户代码不会自动检查。__exit 段在非模块编译时同样会被丢弃，若静态编译进 vmlinux 又被运行时调用即崩溃。

错。默认链接脚本会处理已知前缀（.text/.data/.rodata/.bss），但任意命名的 .mydata 是"orphan section"。链接器会启发式归类（按属性匹配最接近的段），行为版本相关且不可靠。生产代码必须在链接脚本 SECTIONS 块显式 *(.mydata) 才能保证位置和属性。内核链接脚本 vmlinux.lds 显式处理了几十个自定义段。

答案

模块的 .init.data 在 probe 完成后被 free_module() 释放，模块卸载时该内存已归还。再次加载模块时，.init.data 重新分配、重新填入 42——理论上没问题。但如果驱动把 &cfg 存到了全局指针（如 static int *cfgp = &cfg;），且 cfgp 在 .data 段未被释放，二次加载时旧 cfgp 指向的 .init.data 可能已被其他模块占用——use-after-free。坑在跨段引用：.data 引用 .init.data 的指针，释放后即悬垂。

U-Boot 自复制机制：

  1. 链接脚本将自复制代码放入特殊段 .image_copy

6.7

.1 地址对齐：aligned

本节讲什么

对齐 指对象地址 mod N == 0。硬件要求 4 字节 int、8 字节 double、16 字节 SSE、64 字节 cache line 等于不同 N。编译器默认按 ABI 对齐；aligned 属性 提高 对齐要求。

要点

char c __attribute__((aligned(64)));   /* 64 字节对齐 — cache line */
int  x __attribute__((aligned(8)));

_Static_assert(__alignof__(x) >= 8, "align");

/* 栈/堆数组手动对齐 — C11 */
#include <stdalign.h>
alignas(64) char buf[128];
N 典型用途
4 ARM 32-bit 字
8 double / 指针
16 NEON / SSE
64 防 false sharing（DPDK per-lcore） 
gcc -std=gnu11 -O2 -c align.c
objdump -t align.o | grep -E 'buf|c '
  • __alignof__(type) / _Alignof：查询对齐
  • DMA buffer 常 posix_memalign(..., 4096, size) 或 aligned_alloc
  • 内核 kmalloc 保证 SMP_CACHE_BYTES 对齐变体

常见陷阱

  1. aligned 只能"提高"，不能"降低"对齐 __attribute__((aligned(N))) 中 N 必须 ≥ 类型自然对齐。对 char 用 aligned(1) 是无意义但合法；对 int 用 aligned(2) 会触发警告或忽略——编译器不会主动降低对齐，因为可能违反 ABI。要降低对齐用 packed，但代价是访问性能/原子性。

  2. 栈上变量 aligned 在某些 GCC 版本不可靠 char buf[128] __attribute__((aligned(64))); 在栈上要求 64 字节对齐，老版 GCC（< 4.6）或某些 ABI 下可能只保证到 16 字节。C11 alignas 是标准写法，更可靠。内核用 __aligned(N) 宏统一封装，但在栈上仍依赖编译器版本。

  3. aligned 不能修复已存在的 false sharing 对单个变量 aligned(64) 防止它与其他变量共享 cache line。但若结构体内多个成员被不同 CPU 频繁写，整体对齐结构体没用——成员间仍在同一 cache line。需要把每个 hot 字段拆到独立 aligned(64) 变量，或用 ____cacheline_aligned（内核）/ __rte_cache_aligned（DPDK）放在结构体内字段间。

自测题

1.（选择） 下列哪条对齐声明是合法且有意义的？ - A. char c __attribute__((aligned(1))); - B. int x __attribute__((aligned(2))); - C. char buf[128] __attribute__((aligned(64))); - D. double d __attribute__((aligned(4)));

答案

C。char 自然对齐 1，aligned(1) 无意义；int 自然对齐 4，aligned(2) 会被忽略或警告（不能降低）；double 自然对齐 8，aligned(4) 同理不能降低。只有 C 是"提高对齐"——char[128] 提到 64 字节对齐用于 cache line 对齐，常见且合法。

2.（判断） aligned(N) 保证了对象地址 mod N == 0，无论对象在栈、堆、全局段。

答案

对，但有 caveat。栈/全局段由编译器在编译期布局，保证对齐。堆需 posix_memalign / aligned_alloc / memalign——普通 malloc 不保证大于 alignof(max_align_t)（通常 16）的对齐。DPDK rte_malloc 也提供 rte_malloc_socket + 对齐参数。坑：对全局 aligned(64) 变量取地址可以，但 malloc 后强转 aligned 指针运行时仍是 malloc 的对齐——aligned 属性只对定义生效，不对指针类型生效。

3.（踩坑） 多线程程序中两个 int counter_a, counter_b; 被两个 CPU 频繁自增，性能远低于预期。perf c2c 显示 false sharing 严重。但加上 int counter_a __attribute__((aligned(64))); 后性能几乎没改善。为什么？

答案

坑在只对齐了单个变量：counter_a 在 64 字节边界，但 counter_b 紧跟其后（4 字节偏移），两者仍在同一 cache line。修复方式：

struct counters {
    int a __attribute__((aligned(64)));
    int b __attribute__((aligned(64)));
};

或独立结构体：

static int counter_a __aligned(64);
static int counter_b __aligned(64);

关键：false sharing 是多个变量在同 cache line 问题，必须每个变量独立对齐到 cache line，仅对齐其中一个无济于事。内核 ____cacheline_aligned / ____cacheline_internodealigned_in_smp 专治此症。

4.（应用） 给定 void *p（可能是栈/堆/全局），写一个可移植函数判断其是否 N 字节对齐。

答案 
#include <stdint.h>
#include <stdbool.h>

static inline bool is_aligned(const void *p, size_t n) {
    return ((uintptr_t)p & (n - 1)) == 0;
}

原理：N 是 2 的幂时 n-1 是掩码（低 log2(N) 位全 1），按位与为 0 即对齐。关键点： - 必须 uintptr_t（无符号，足以容纳指针），不能用 int（截断）。 - N 必须是 2 的幂——非 2 幂对齐无意义（硬件也不支持）。 - C11 后更标准：_Alignof(T) 取类型对齐，再 is_aligned(p, _Alignof(T))。

6.7

.2 结构体的对齐

本节讲什么

结构体布局 = 成员顺序 + 各成员对齐要求 + 尾部 padding。sizeof 可能大于成员 size 之和。读 wire 协议 与 硬件寄存器块 时必须显式控制；否则 #pragma pack / packed 与 aligned 混用。

要点

struct default_layout {
    char  a;   /* offset 0 */
    /* 3 bytes padding */
    int   b;   /* offset 4 */
    char  c;   /* offset 8 */
    /* 3 bytes tail padding → sizeof = 12 */
};

struct hw_reg {
    uint32_t ctrl;
    uint32_t status;
} __attribute__((aligned(4)));

  1. 每个成员 offset % align(member) == 0
  2. 结构体 align = max(成员 align)，size 补齐到 align 倍数
  3. packed 强制 align 1（6.7.4）

题目 1： attribute((aligned(N))) 一定能保证对齐吗？有什么限制？

__attribute__((aligned(8))) char c;  // c 对齐到 8 字节
int x __attribute__((aligned(3)));      // 合法吗？

aligned(N) 的限制：

  1. N 必须是 2 的幂：aligned(3) 非法，GCC 报错。合法值：1, 2, 4, 8, 16, 32, 64...

  2. 只能增大不能减小对齐：aligned(1) 对 int 无实际效果（int 天然 4 对齐）。要减小对齐用 packed。

常见陷阱

  1. 未对齐访问在 ARMv5 及以下触发 alignment fault packed 结构体去掉 padding，int 字段地址可能不在 4 字节边界。ARMv5 及更早架构硬件不支持未对齐 word 访问，直接 p->ethertype 触发异常（SIGBUS）。ARMv6+ 默认开启 unaligned access 支持，但性能差——硬件拆成两次访问。x86 永远支持但跨 cache line 仍慢。安全做法：用 memcpy 或 get_unaligned_be16()。

  2. packed 结构体不能整体赋值（部分情况） struct eth_hdr_packed a = b; 看起来合法，但若编译器优化下用了 SIMD load 指令（要求对齐）会触发对齐异常。packed 结构体的赋值、传参（按值）在某些 ABI 下行为未定义或低效。惯例：packed 结构体只通过指针操作，永远不按值传递。

  3. 取 packed 成员地址 → 指针类型对齐假设错位 uint16_t *p = &hdr->ethertype; 看似合法，但 p 的类型声明"承诺" 2 字节对齐，实际可能任意地址。指向 packed 成员的指针必须显式标 __packed 或转 void * 后用 memcpy。GCC 的 -Waddress-of-packed-member 警告（默认不开）专门查这个坑。

1.（选择） 以下哪种情况必须用 packed？ - A. 结构体用于跨平台文件存储 - B. 结构体映射网络协议头/硬件寄存器 - C. 想节省内存 - D. 想提高访问速度

2.（判断） struct s { char c; int i; } __attribute__((packed)); 后，sizeof(struct s) == 5。

答案

对。c 1 字节 + i 4 字节，packed 去掉 3 字节 padding，总和 5。但结构体尾部 padding 是否被去掉取决于编译器——GCC 的 packed 会去掉尾部 padding，所以 sizeof == 5。然而数组中 s[1] 仍要满足"下一元素起始对齐"（无 packed 数组对齐为 1），所以无额外 padding。坑：把这种结构体强转为 int * 取 s[0].i 即未对齐访问。

3.（踩坑） 代码：

struct pkt { uint8_t d[6]; uint16_t len; } __attribute__((packed));
struct pkt *p = (struct pkt *)buf;
uint16_t *lp = &p->len;        /* ① */
uint16_t v = *lp;              /* ② */

在 x86 上正常，移植到 ARMv5 后 ② 偶发 SIGBUS。为什么？如何修？

答案

&p->len 地址未对齐（packed 后 len 在偏移 6，非 2 字节边界）。uint16_t *lp 类型声明对齐 2，编译器在 ARMv5 上可能生成 ldrh（要求对齐）指令，访问未对齐地址触发异常。x86 硬件支持未对齐访问，所以"正常"——这是典型的"在 x86 上能跑，移植就崩"坑。 修复：

uint16_t v;
memcpy(&v, &p->len, sizeof(v));      /* 安全：memcpy 按字节拷贝 */
v = ntohs(v);                         /* 网络字节序转主机 */

或用内核/DPDK 提供的 get_unaligned_be16(&p->len)。原则：packed 结构体成员永远不要取地址给类型化指针，用 memcpy 或 get_unaligned。

6.9

.1 强符号和弱符号

本节讲什么

链接器规则：强符号 唯一定义；弱符号 可被强符号 覆盖 而不报 duplicate symbol。C 中 weak attribute 与 common block 行为不同。

要点

种类 典型来源
强符号 函数定义、已初始化全局
弱符号 __attribute__((weak)) 
/* a.c */
int counter __attribute__((weak)) = 0;
/* b.c — 强符号覆盖 */
int counter = 100;

gcc -c a.c -o a.o && gcc -c b.c -o b.o
gcc a.o b.o -o t && nm t | grep counter
  • 重复强符号 → 链接错误
  • 内核 __weak 宏广泛用于 arch hook

常见陷阱

  1. 强弱符号同名同类型才能覆盖 → 类型不匹配链接器静默选一个 weak int counter 与 strong long counter（不同类型）共存时，链接器不会报错，按"强优先"选 long 的存储，但访问代码按 int 解读——读到的是截断或异位的值。GCC 的 -Wl,--no-undefined 不查类型，-flto 才能跨编译单元类型检查。约定**：weak/strong 必须在头文件共享同一声明。

  2. 静态函数不能 weak → weak 只对全局符号有效 static void f(void) __attribute__((weak)); 看似合法但无意义——静态符号不参与链接，无"强弱"概念。weak 只对具有外部链接的符号生效。误用会导致 weak 静默失效，覆盖不会发生，运行时仍调原版。

  3. 动态链接中 weak 行为与静态不同 静态链接：strong 覆盖 weak，确定无疑。动态链接：weak 符号在 .so 中仍可被可执行文件的 strong 覆盖（默认符号解析规则），但若 dlopen(RTLD_LOCAL) 加载的 .so 含 strong 定义，不会**覆盖主程序的 weak——只在自己命名空间内有效。LD_PRELOAD 注入靠的是全局符号插序，与 weak 无直接关系。

自测题

1.（选择） 下列哪种符号是强符号？ - A. int x __attribute__((weak)) = 0; - B. int x;（未初始化全局） - C. int x = 1;（已初始化全局） - D. extern int x;

答案

C。已初始化全局是强符号；__attribute__((weak)) 显式声明弱；未初始化全局 int x; 是 common 符号（GCC -fcommon 默认开，GCC 10+ 改默认 -fno-common 后变强）；extern int x; 仅声明不是定义。坑：common 符号在链接时允许重复，行为类似弱但语义不同——不要把 common 当 weak 用。

2.（判断） 同一程序中两个 void f(void) {}（无 weak）一定链接报错。

答案

对，但有例外。两个强符号同名同类型，链接器报 multiple definition of 'f'。例外：GCC 10 之前默认 -fcommon，未初始化全局变量是 common 符号（不算强符号），多个 common 会被合并——但函数不是 common，仍报错。GCC 10+ 默认 -fno-common，未初始化全局也变强，更严格。函数永远是强符号（除非 weak），重复定义必报错。

3.（踩坑） 模块 A 头文件声明 void hook(void) __attribute__((weak));，A.c 中定义 weak 版 void hook(void) {}；模块 B.c 直接 #include "A.h" 后定义 void hook(void) { /* B 版 */ }。链接时 strong 选中 B 版——但B.c 中没加 weak 属性，A.h 声明带 weak，是否冲突？

答案

不冲突。C 标准允许同一符号多次声明，属性可不同。GCC 处理规则：只要有一个声明不带 weak，即为强。所以 B.c 看到的是 weak 声明，但其定义不写 weak，链接器视 B 的定义为强。这是惯用法：头文件统一声明 weak，提供方写 weak 实现，覆盖方写普通实现。 坑：如果 B.c 把声明复制为 void hook(void);（不带 weak），与头文件 weak 声明"冲突"——GCC 仍接受，但编译警告 -Wattributes。最佳实践：覆盖方#include 头文件即可，不重复声明。

4.（应用） 设计一个"板级可选初始化钩子"机制：默认实现是空函数，BSP 可覆盖。给出声明与用法。

/* board.h */

/* board_default.c (链接进所有镜像) */

常见陷阱

  1. weak 函数被内联后失去 weak 语义 如果 weak 函数在头文件中 inline 定义，调用方可能直接内联默认版，链接期 strong 覆盖失效。坑：static inline __attribute__((weak)) 几乎肯定是错的——static 已限定本编译单元，weak 无意义。weak 必须是具有外部链接的函数，定义在 .c 文件中。

  2. LTO 下 weak 行为变化 -flto 跨编译单元优化时，编译器可能"看穿" weak 函数调用，直接内联默认实现，绕过 strong 覆盖。GCC 10+ 修复了大部分场景，但边界情况仍有问题。生产代码用 LTO + weak 需测试覆盖确认。内核默认不开 LTO（部分架构可开 CONFIG_LTO）。

  3. weak 不能覆盖动态库符号（默认） 可执行文件调 printf，libc 中 printf 即使被声明 weak，运行时仍走 libc 实现——主可执行文件的符号优先级高于 .so，但反之不行：.so 中的 strong 定义不会覆盖主程序中的 weak 定义（除非 LD_PRELOAD 或 dlopen(RTLD_GLOBAL)）。误以为"weak 总能被覆盖"在动态链接下踩坑。

自测题

1.（选择） 以下哪种场景最适合用 weak 而不是 #ifdef？ - A. 编译时根据 CONFIG_SMP 决定是否启用自旋锁 - B. 不同 BSP 提供不同 board_early_init 实现 - C. 调试版本打开详细日志 - D. 64 位 vs 32 位平台差异

答案

B。BSP 差异在链接时通过替换 .o 文件实现，无需重新编译内核主体——正是 weak 的适用场景。A/C/D 都是编译期配置，#ifdef 更合适（编译时决定，运行时无开销）。weak 的代价是间接调用（无法内联），编译期配置零运行时开销。

2.（判断） static inline void f(void) __attribute__((weak)); 是合理的 weak 用法。

答案

错。static 限定符号为编译单元内部，无外部链接，weak 属性无意义（链接器看不到该符号）。inline 进一步暗示编译器内联，更削弱"链接期覆盖"语义。正确写法：weak 函数必须 extern（默认），定义在 .c 文件中，调用方通过头文件 extern 声明看到 weak 标记。

3.（踩坑） 单测中 mock 了 time_now（strong 覆盖 weak 默认实现），生产代码用 -O2 编译。单测跑过，但线上仍用默认实现。定位后发现 time_now 在头文件中 static inline 定义。为什么？

答案

static inline 函数无外部链接，weak 失效，调用方直接内联默认实现。链接期 strong 版本根本没机会被选中——编译器已在每个调用点展开默认代码。修复： 1. 默认实现移到 .c 文件，去掉 static inline，标 weak。 2. 头文件只留 extern 声明（带 weak 属性）。 3. 关键路径若性能敏感，用宏或 always_inline 内联版 + weak 兜底版双轨。 教训：weak 与 inline 是对立语义——inline 要求编译期展开，weak 要求链接期替换，二者不可兼得。

题目 1： __builtin_expect 的作用是什么？likely/unlikely 宏如何使用它？

6.11

.6 Linux内核中的likely和unlikely

本节讲什么

内核 likely/unlikely 包装 __builtin_expect，给分支预测器编译期提示：标记某分支"大概率/小概率"走，编译器据此重排代码——把 unlikely 错误路径移到函数末尾，保持 hot path 在 cache 内连续。本节讲原理、用法、误用代价。

要点

__builtin_expect 原理

long __builtin_expect(long exp, long c);

返回 exp 本身（运行时无副作用），但告诉编译器"运行时 exp == c 的概率高"。编译器据此： 1. 重排基本块——把"非 c 分支"移到远处（函数末尾或冷段）。 2. 优化指令 cache 局部性——hot path 连续。 3. 影响条件移动 vs 分支跳转指令选择。

内核 / DPDK 包装

/* include/linux/compiler.h */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

/* DPDK — rte_branch_prediction.h */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

!!(x) 把任意表达式归一化为 0/1，避免 __builtin_expect 第二参数被误用。

典型用法

/* 错误路径标 unlikely */
if (unlikely(!ptr))
    return -EINVAL;

if (unlikely(ptr->magic != MAGIC))
    goto corrupt;

/* 成功路径标 likely */
if (likely(nb_rx > 0)) {
    /* burst 处理收到的包 */
}

编译器生成的代码差异

int f(int *p) {
    if (unlikely(!p)) return -1;
    return *p;
}

编译后（ARM64 概览）：

cbz   x0, .Lerror      /* 错误路径跳远 */
ldr   w0, [x0]
ret
.Lerror:
mov   w0, #-1
ret

hot path（ldr/ret）连续在前面，.Lerror 在末尾——icache 友好。不标 unlikely 时编译器也可能猜（基于 profile 或静态启发式），但不可靠；显式 unlikely 强制。

使用条件

  • profile 验证后再加——猜错会降低性能。
  • 仅在热路径上有意义——冷函数加 likely 无用。
  • __builtin_expect 不影响正确性，只影响性能。
用法 说明
错误检查 if (unlikely(!ptr)) 错误路径移出 hot path
快速路径 if (likely(ret == 0)) 保持成功路径连续
switch 优化 标 unlikely case 移到末尾
DPDK 收包 if (likely(nb_rx > 0)) 数据面热路径
  • 不要在用户态盲目复制：profile 为准
  • GCC -fprofile-generate/-fprofile-use（PGO）可自动生成类似信息

常见陷阱

  1. 猜错方向 → 性能反而下降 unlikely(x) 标在实际大概率分支上，编译器把该分支移到冷区，每次跳转都破坏 icache。代价：5-20% 性能损失（视分支频率）。必须用 profile（perf record / gcov）确认概率再加，否则别加。某分支 50/50 时不要标——__builtin_expect 只在明显偏斜时有用。

  2. likely(unlikely(...)) 嵌套无意义 __builtin_expect 是编译期提示，嵌套调用最后只保留最外层。更隐蔽的是 if (likely(a) && unlikely(b))——编译器对复合条件分支预测有独立逻辑，likely/unlikely 标注会被部分忽略。惯例：每个 if 标注一个 likely 或 unlikely，作用于整体条件。

  3. 误以为 likely 改变语义 if (likely(p != NULL)) 与 if (p != NULL) 在语义上完全等价——likely 只影响代码生成，不影响判断结果。新手误以为 likely "强制走某分支"是错的：运行时若 p == NULL，仍进入 NULL 分支。__builtin_expect 返回值等于第一参数，无运行时副作用。

1.（选择） __builtin_expect(exp, c) 的运行时行为是？ - A. 强制 exp == c - B. 返回 exp，给编译器分支预测提示 - C. 调用硬件分支预测器 - D. 改变条件判断结果

答案

3.（踩坑） DPDK 收包循环：

uint16_t n = rte_eth_rx_burst(port, q, bufs, BURST);
if (likely(n == 0)) continue;     /* 标 likely */
process(bufs, n);

答案

方向标反了。rte_eth_rx_burst 在收包路径上通常有包（否则轮询浪费），n > 0 是大概率事件。标 likely(n == 0) 等于告诉编译器"通常没包"，把 continue（hot path）排到前面，但实际运行时 n == 0 为假，跳到 process——每次都跳转，icache 失效。正确：

if (unlikely(n == 0)) continue;  /* 空轮询是少数 */

教训：likely/unlikely 必须 profile 验证。DPDK 的 rte_branch_prediction.h 文档明确说"仅用于已 profile 的热路径"。

4.（应用） 给定函数：

int parse(const char *s) {

    return 0;

用 likely/unlikely 优化，并说明预期收益。

答案 
int parse(const char *s) {
    if (unlikely(s == NULL))    return -EINVAL;
    if (unlikely(*s == '\0'))   return -EINVAL;

    return 0;
}
