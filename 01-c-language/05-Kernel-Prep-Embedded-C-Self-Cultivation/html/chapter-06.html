Customizing the Toolchain for Embedded & Kernel Work

一句话概括这一章：代码写完之后，是谁把它变成在目标机上跑的东西。 前五章都在写 C 源代码；这一章决定它的地址、符号可见性、加载方式。

前置：CH2 的 section / weak——这一章是它们在工具链侧的兑现 配套：utility 环境见 1 工具链

本章讲什么

嵌入式和内核场景有个共同点：没有默认的东西。

  • 没有操作系统帮你加载你 → 你得告诉链接器代码放哪个物理地址（链接脚本）
  • 没有标准启动流程 → 你得决定 _start 是谁、栈指针初值是多少
  • 不能直接编译 → 得用交叉工具链（在 x86 上编出 ARM 的机器码）
  • 符号不能全都可见 → 得控制哪些导出、哪些静态化

前五章的答案都在源码里；这一章的答案在 .map / .ld / 编译选项 里。

Q1：链接脚本和 -Wl,-Ttext=0x8000 有什么区别？

答案

-Ttext 只是把 .text 的起始地址改了，其余段仍在默认布局里；链接脚本是完全接管——你能指定每个段的地址、对齐、加载地址(LMA)与运行地址(VMA) 分离（AT>），还能 PROVIDE 自定义符号。U-Boot 重定位就是靠 LMA ≠ VMA：先从 Flash(LMA) 加载进去，代码自己把自己搬到 RAM(VMA) 跑。详见 4.14 与 CH4 4.12 U-Boot 重定位。

Q2：为什么要交叉编译？在目标机上装个 gcc 不行吗？

答案

多数嵌入式目标机资源不足以跑编译器（几 MB 内存、无文件系统），而且没有标准库和目标头文件。交叉编译器在 x86 主机上跑，产出目标架构的机器码，配套的 sysroot 提供目标平台的头文件与库。所以命令名带了前缀——arm-none-eabi-gcc 里 none 表示无操作系统、eabi 表示嵌入式 ABI。详见 3.7。

Q3：静态库和一堆 .o 直接链接有什么本质区别？

答案

静态库是 .o 的打包，但链接器只会提取当前未解析符号需要的成员。这意味着：库里有强符号覆盖你的 weak 定义，但如果那个成员恰好没被提取，覆盖就不生效——这正是 CH2 6.9 实测的头号坑（六组对照）。用 -Wl,--whole-archive 或干脆直接链 .o 可绕开。

题目 1： 以下 gcc 命令的四个阶段分别生成什么文件？

gcc -E main.c -o main.i    # 阶段1
gcc -S main.i -o main.s    # 阶段2
gcc -c main.s -o main.o    # 阶段3
gcc main.o -o main          # 阶段4
参考答案
  1. 预处理（-E）：展开宏、包含头文件、处理条件编译 → main.i
  2. 编译（-S）：C 代码翻译为汇编代码 → main.s
  3. 汇编（-c）：汇编代码翻译为机器码 → main.o（目标文件）
  4. 链接（无特殊标志）：目标文件 + 库 → 可执行文件 main

一步编译：gcc main.c -o main 等价于上面四步。

hexdump -C a.out | head          # 原始字节

标记 含义

GDB 是什么

GDB（GNU Debugger）是 GNU 项目下的命令行程序调试器，主要用来调试 C/C++、汇编等编译型程序，在 Linux/Unix 环境用得最多。

能力概览

能力 说明
启动程序 可带上参数运行待调试程序
设置断点 程序跑到断点就暂停
单步执行 一条语句 / 一条汇编指令，观察程序怎么走
查看/修改内存 寄存器、变量、任意内存地址
崩溃分析 段错误 core dump，定位崩溃在哪一行
attach 进程 调试正在运行的进程（不停机排查）

GDB vs GDP：GDB 是 GNU 调试器（程序员工具）；GDP 是国内生产总值（经济指标）。完全无关，别搞混。

编译须 -g

gcc -g test.c -o test    # -g 把调试信息（DWARF）打进可执行文件
gdb ./test

不加 -g，GDB 看不到源码行号、变量名，只能看汇编。

-g 做了什么

-g 让 gcc 在可执行文件中嵌入 DWARF 调试信息：

信息 作用
源码行号 → 机器地址映射 断点能停在源码某一行
变量名 → 栈/寄存器位置映射 print var 能找到变量
类型信息（struct/union 定义） GDB 知道怎么解析 *ptr
函数名 → 地址映射 break main 能找到入口 
# 验证 DWARF 信息是否存在
readelf -S ./app | grep debug      # 有 .debug_info / .debug_line 段说明 -g 生效
objdump --dwarf=info ./app | head  # 查看具体调试信息

-g 与优化级别

gcc -g -O0 main.c -o app_debug    # 调试用：不优化，变量全在
gcc -g -O2 main.c -o app_release  # 生产用：优化但保留调试信息
组合 效果
-g -O0 最佳调试体验，变量全可查，行号准确
-g -O2 可调试但变量可能被优化掉，行号会跳跃
无 -g 只有汇编，无源码行号
-g -O3 激进优化，内联展开后基本不可读

启动 GDB 的几种方式

1. 直接启动

gdb ./app                       # 加载程序但不运行
(gdb) run                       # 在 GDB 内启动程序
(gdb) run arg1 arg2             # 带参数运行
(gdb) run < input.txt           # 重定向 stdin

2. 调试正在运行的进程

gdb -p <PID>                    # attach 到进程
# 或
gdb ./app <PID>

3. 调试 core dump

gdb ./app core                  # 加载可执行文件 + core 快照
(gdb) bt                        # 直接看崩溃栈

4. 启动时执行命令

gdb -ex "break main" -ex "run" ./app    # 启动时设断点并运行
gdb -batch -ex "bt" ./app core          # 批处理模式：打印栈后退出（脚本用）

1.5

.2 GDB 断点与单步调试

断点（Breakpoint）

基本断点

(gdb) break main              # 在函数 main 处设断点
(gdb) break main.c:42         # 在 main.c 第 42 行设断点
(gdb) b main.c:42             # 简写 b
(gdb) b 42                    # 当前文件第 42 行

临时断点（Temp Breakpoint）

(gdb) tbreak main.c:50        # 命中一次后自动删除

用途：只想在第一次经过时停一下，后续不再断。

条件断点（Conditional Breakpoint）

(gdb) break main.c:42 if i == 100     # 当 i == 100 时才断
(gdb) break loop if count > 50        # 函数 loop 中 count > 50 时断
(gdb) condition 1 i == 100            # 给已有断点 1 加条件
(gdb) condition 1                     # 删除断点 1 的条件

用途：循环里第 N 次才出 bug，不用手动 continue 几百次。

断点管理

(gdb) info breakpoints        # 查看所有断点（简写 info b）
(gdb) delete 1                # 删除 1 号断点
(gdb) delete                  # 删除所有断点
(gdb) disable 1               # 禁用 1 号断点（不删，暂不生效）
(gdb) enable 1                # 重新启用
(gdb) clear main.c:42         # 清除 main.c 第 42 行的断点
命令 简写 作用
break b 设置断点
tbreak tb 临时断点（命中后自动删除）
info breakpoints i b 查看所有断点
delete d 删除断点
disable dis 禁用断点
enable en 启用断点
condition cond 设置/清除条件
clear — 清除指定位置断点

运行控制

(gdb) run                     # 从头开始运行程序
(gdb) run arg1 arg2           # 带参数运行
(gdb) continue                # 继续运行到下一断点
(gdb) continue 3              # 继续运行，跳过接下来 3 次断点命中
(gdb) kill                    # 杀死当前运行的程序（不退出 GDB）
(gdb) quit                    # 退出 GDB

单步执行

next vs step

命令 简写 行为
next n 下一行，跳过函数调用（函数内部不停）
step s 下一行，进入函数内部（逐行执行被调函数） 
10  int result = calculate(a, b);   // next → 直接到第 11 行
                                     // step → 进入 calculate() 内部第一行
11  printf("%d\n", result);

汇编级单步

(gdb) nexti                   # ni：下一条汇编指令（跳过 call）
(gdb) stepi                   # si：下一条汇编指令（进入 call）

用途：调试无源码的库函数、或 -O2 优化后行号不准时。

until

(gdb) until                   # 运行到当前循环结束（跳出 for/while 体）
(gdb) until main.c:50         # 运行到第 50 行

用途：不想在循环里一步一步走，直接跳到循环之后。

监视点（Watchpoint）

Watchpoint 不在某一行断，而是当某个表达式的值发生变化时断。

(gdb) watch count             # 当 count 的值被修改时暂停
(gdb) watch count == 100      # 当 count 变为 100 时暂停
(gdb) watch *ptr              # 监视指针指向的内存
(gdb) rwatch count            # 当 count 被**读取**时暂停
(gdb) awatch count            # 当 count 被**读或写**时暂停

用途： - 变量被意外篡改，但不知道在哪里改的 → watch var - 内存被踩 → watch *addr

(gdb) info watchpoints        # 查看所有 watchpoint
(gdb) delete 2                # 删除 2 号 watchpoint（和断点统一编号）

捕获点（Catchpoint）

(gdb) catch throw             # C++ 抛异常时断
(gdb) catch syscall write     # 调用 write 系统调用时断
(gdb) catch fork              # 调用 fork 时断
(gdb) catch exec              # 调用 exec 时断

用途：调试系统调用、fork/exec、C++ 异常。

1.5

.4 GDB 调试 core dump

core dump 是什么

进程因 SIGSEGV（段错误）、SIGABRT 等异常信号终止时，内核可以把进程的内存映像、寄存器状态、栈信息写入一个 core 文件。这个文件就是进程崩溃瞬间的"现场快照"。

用 GDB 加载可执行文件 + core 文件，就能在崩溃点回溯调用栈、查看变量、分析根因——相当于事故调查的黑匣子。

开启 core dump

临时开启（当前 shell）

ulimit -c unlimited          # 允许生成不限大小的 core 文件
./app                         # 崩溃后生成 core

验证：

ulimit -c                     # 输出 unlimited 说明已开启

永久开启

编辑 /etc/security/limits.conf：

*  soft  core  unlimited
*  hard  core  unlimited

core 文件路径

cat /proc/sys/kernel/core_pattern    # 查看 core 文件命名/路径规则
core_pattern 效果
core 在程序工作目录生成 core 文件
core.%p 生成 core.<PID>
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h %e systemd 接管（Ubuntu/CentOS 默认）

手动设置：

echo "/tmp/core.%p" > /proc/sys/kernel/core_pattern    # 存到 /tmp/core.PID
echo "core" > /proc/sys/kernel/core_pattern             # 存到工作目录

systemd 系统（Ubuntu 16.04+ / CentOS 7+）：core 默认由 systemd-coredump 接管，存到 /var/lib/systemd/coredump/。用 coredumpctl list 查看，coredumpctl debug <PID> 直接调试。

调试 core dump

基本流程

gcc -g -O0 -o crash crash.c
ulimit -c unlimited
./crash                          # 崩溃，生成 core
gdb ./crash core                 # 加载可执行文件 + core

(gdb) bt                         # 调用栈回溯——直接看到崩溃在哪一行
(gdb) bt full                    # 带每个栈帧的局部变量
(gdb) frame 0                    # 切到崩溃帧
(gdb) list                       # 查看崩溃点源码
(gdb) info locals                # 崩溃帧的局部变量
(gdb) info registers             # 崩溃时寄存器状态
(gdb) x/16wx $sp                 # 崩溃时栈内存
(gdb) print *ptr                 # 查看导致崩溃的指针

bt 输出解读

(gdb) bt
#0  0x0000555555555155 in main () at crash.c:11
       ↑ 地址         ↑ 函数    ↑ 文件:行号
  • #0 是最内层（崩溃点），#1 是调用者，依次往外
  • 如果有 ?? 说明没有调试信息（没加 -g 或被 strip）
  • 地址 0x0000555555555155 可以用 info symbol 0x555555555155 查最近的符号

多线程 core dump

(gdb) info threads               # 查看所有线程
(gdb) thread 1                   # 切到 1 号线程
(gdb) bt                         # 看该线程的调用栈
(gdb) thread apply all bt        # 所有线程的调用栈一起打印

多线程程序崩溃时，core dump 会包含所有线程状态。崩溃线程通常带 SIGSEGV 标记。

无 core 文件时的调试

如果 core 没生成（忘了 ulimit -c、磁盘满、权限问题），可以直接在 GDB 里运行程序：

gdb ./crash
(gdb) run
# 程序崩溃后，GDB 自动停在崩溃点
(gdb) bt

区别：

方式 优势 劣势
core dump 事后分析，不用重现 需要 ulimit 配置
GDB run 不需要配置 必须能重现崩溃

常见崩溃信号

信号 含义 常见原因
SIGSEGV 段错误 空指针解引用、越界访问、写只读内存
SIGABRT 异常终止 assert 失败、abort()、堆损坏（double free）
SIGFPE 算术异常 除以零、整数溢出（部分平台）
SIGBUS 总线错误 内存对齐违规（ARM 上常见）
SIGILL 非法指令 函数指针被破坏、栈溢出覆盖返回地址

实操：空指针段错误

// crash.c
#include <stdio.h>
#include <string.h>

void write_data(char *buf)
{
    strcpy(buf, "hello");   // 第 6 行：buf 是 NULL → SIGSEGV
}

int main(void)
{
    char *buf = NULL;
    write_data(buf);          // 第 11 行
    printf("%s\n", buf);
    return 0;
}

$ gcc -g -O0 -o crash crash.c
$ ulimit -c unlimited
$ ./crash
Segmentation fault (core dumped)

$ gdb ./crash core
(gdb) bt
#0  write_data (buf=0x0) at crash.c:6
#1  0x0000555555555172 in main () at crash.c:11

(gdb) frame 0
(gdb) print buf
$1 = 0x0                      # → 空指针，根因找到

(gdb) frame 1
(gdb) print buf
$2 = 0x0                      # main 里的 buf 也是 NULL

分析：#0 显示崩溃在 write_data 第 6 行，buf=0x0 是空指针。#1 显示是 main 第 11 行调用时传入了 NULL。

实操：数组越界 → 堆损坏 → SIGABRT

// heap_crash.c
#include <stdlib.h>
#include <string.h>

int main(void)
{
    char *p = malloc(10);
    memset(p, 'A', 100);    // 越界写 100 字节，踩了堆元数据
    free(p);                  // glibc 检测到堆损坏 → abort() → SIGABRT
    return 0;
}

$ gdb ./heap_crash
(gdb) run
Program received signal SIGABRT, Aborted.
__GI_raise (sig=sig@entry=6) at ../sysdeps/unix/sysv/linux/raise.c:50

(gdb) bt
#0  __GI_raise (sig=6) at ../sysdeps/unix/sysv/linux/raise.c:50
#1  __GI_abort () at abort.c:79
#2  __libc_message (action=..., fmt=...) at ../sysdeps/posix/libc_fatal.c:155
#3  malloc_printerr (...) at malloc.c:5347     # ← glibc 堆检查
#4  _int_free (...) at malloc.c:4187
#5  __GI___libc_free (mem=0x5555555592a0) at malloc.c:3135
#6  0x0000555555555168 in main () at heap_crash.c:7

#3 malloc_printerr 说明 glibc 在 free 时检测到堆元数据被破坏，主动 abort。根因在 #6 main 第 6 行的 memset 越界。

.5 GDB 高级技巧与 HFT 实战

attach：调试正在运行的进程

程序已经在运行，不想重启，直接附着上去调试。

gdb -p <PID>                   # attach 到进程
# 或
gdb ./app <PID>

(gdb) break some_function      # 设断点
(gdb) continue                 # 让程序继续跑，到断点会停
(gdb) ...                      # 调试
(gdb) detach                   # 脱离进程，程序继续运行
(gdb) quit

attach 的本质

gdb -p <PID> 实际上： 1. 调用 ptrace(PTRACE_ATTACH, pid) → 内核给目标进程发 SIGSTOP，进程停住 2. GDB 读取目标进程的寄存器、内存 3. detach 时调 ptrace(PTRACE_DETACH) → 进程收到 SIGCONT 继续运行

生产环境慎用：attach 会让目标进程瞬间停住。HFT 交易引擎停 1ms 都可能丢单。只在维护窗口或非交易时段 attach。

HFT 场景：交易引擎排查

# 交易引擎 PID 12345 运行中，出现异常订单

(gdb) thread 3                  # 切到策略线程
(gdb) bt                        # 看策略线程在干什么
(gdb) print order_book->depth   # 查看订单簿状态
(gdb) detach                    # 排查完脱离，引擎继续运行

-O2 下的调试陷阱

HFT 生产代码通常 -O2 甚至 -O3，调试时会遇到：

问题 原因 应对
变量 <optimized out> 被优化进寄存器，栈上没了 关键变量加 volatile
行号跳跃 多行合并 / 指令重排 用 stepi 逐指令走
断点不命中 函数被内联 info inline，或对内联展开后的地址设断
参数显示错误 寄存器传参（ABI 变化） info args + info registers 对照
调用栈不完整 尾调用优化省略了栈帧 set backtrace past-main on 
// volatile 防优化示例
volatile int debug_flag = 0;    // GDB 可以随时查看/修改

混合编译策略

# 热点文件 -O2，调试文件 -O0 -g
CFLAGS_HOT = -O2 -g
CFLAGS_DEBUG = -O0 -g

main.o: main.c
    $(CC) $(CFLAGS_DEBUG) -c main.c

strategy.o: strategy.c
    $(CC) $(CFLAGS_HOT) -c strategy.c

题目 1： 分析以下 U-Boot 启动汇编代码的功能：它完成了什么操作？

_start:

    ORR R0, R0, #0x13

参考答案

该代码配置 ARM 的协处理器 CP15 来设置系统控制：

编译阶段包含： 1. 词法分析：源代码 → Token 流（标识符、关键字、常量、运算符） 2. 语法分析：Token → AST（抽象语法树），检查语法错误 3. 语义分析：类型检查、作用域检查 4. 中间代码生成：AST → IR（中间表示） 5. 优化：常量折叠、死代码消除、循环优化 6. 目标代码生成：IR → 汇编代码（寄存器分配、指令选择）

gcc -S 只到这一步。现代 GCC 默认开启 -O0（无优化），生产环境用 -O2/-O3。

4.3

.1 从C文件到汇编文件

本节讲什么

编译器核心输出是 汇编语言（.s），而非直接生成机器码。gcc -S 可单独停在汇编阶段，便于对照 C 语句与指令、理解优化与调用约定（ch03 AAPCS）。

要点

生成汇编

gcc -S hello.c -o hello.s
gcc -S -O2 hello.c -o hello.O2.s    # 对比优化级别
gcc -S -fverbose-asm hello.c        # 汇编中带 C 行号注释

典型汇编结构（x86-64）

    .file   "hello.c"
    .text
    .globl  main
main:
    pushq   %rbp
    movq    %rsp, %rbp
    ...
    call    puts
    popq    %rbp
    ret
  • .globl symbol：导出全局符号供链接
  • call foo：若 foo 在其他 .o，生成 重定位项（地址先填 0 或占位）

阅读要点

  • 函数序言/尾声：建立栈帧（ch05）
  • 参数传递：x86-64 用寄存器（rdi, rsi…）；ARM 用 r0–r3
  • 未定义符号：call 外部函数时出现 R_X86_64_PLT32 等重定位类型
objdump -d hello.o              # 若已 -c
objdump -S hello.o              # 混排 C 源码（需 -g 编译）

优化影响

  • -O0：变量多在栈上，便于调试
  • -O2：内联、寄存器分配、死代码消除；汇编行数可能变少或重排

代码自测

题目 1： 以下 C 代码编译为 ARM 汇编后，局部变量如何分配？

int add(int a, int b) {
    int c = a + b;
    return c;
}
参考答案

编译后的 ARM 汇编（简化）：

add:
    ADD R0, R0, R1    @ R0 = a + b (a在R0, b在R1)
    BX LR             @ 返回, R0是返回值

c 是临时变量，编译器直接优化掉（不分配栈空间），结果留在 R0。

若 c 需要取地址（&c），编译器才会在栈上分配：SUB SP, SP, #4; STR R0, [SP]; ...。

优化原则：能放寄存器就不放栈。-O0 模式下可能不优化，所有局部变量都放栈。

4.3

.2 汇编过程

本节讲什么

要点

汇编器输入输出

as -o hello.o hello.s           # 显式调用
gcc -c hello.c                  # 内部调用 as

段与符号

汇编伪操作决定段归属：

.section .text
.globl  func
func:
    ret

.section .data
.globl  counter
counter:
    .long 0

# T func    — .text 中已定义（局部 Text）
# D counter — .data 中已定义（Data）
# U puts    — 未定义，待链接（Undefined）

重定位项诞生

对 call puts@PLT 或 movabs $msg, %rdi，若 puts/msg 地址未知，as 在 .rel.text 记录：

readelf -r hello.o              # 重定位表
objdump -r hello.o              # 另一种查看方式

常见类型（x86-64）：R_X86_64_PC32（相对调用）、R_X86_64_64（绝对地址）。

与编译器协作

  • 编译器负责生成正确伪操作（.cfi_* 栈展开信息等）
  • 手写汇编（ch03）须自己声明 .global、段对齐

本节讲什么

要点

符号表（.symtab）

nm 列 含义
T/t 代码段已定义（全局/局部）
D/d 已初始化数据
B/b BSS 未初始化数据
U 未定义，需其他模块提供
C 公共符号（已废弃，现代链接器少见）

重定位表（.rel.*）

ELF 段与符号关系

#  1   .text   PROGBITS ...
#  7   .symtab SYMTAB   ...
#  9   .rel.text REL     ...

.o / .a / .so / 可执行文件对比

文件 符号表 重定位
.o 完整 有 .rel.*
.a 各成员 .o 归档 成员内仍有
.so 有（动态符号 .dynsym） 链接时/加载时
可执行 可 strip 掉 通常已修补完

4.4

.1 分段组装

本节讲什么

链接第一步：把各输入文件的 同名段 按规则拼接成输出文件的一个段，并为每段分配 虚拟地址（VMA） 和 加载地址（LMA）。可执行文件的段布局决定运行期内存映像；裸机由链接脚本指定 Flash/RAM 位置（4.14）。

要点

段合并规则

  • 所有 .text → 输出 .text（按链接顺序或脚本排序）
  • .data、.bss、.rodata 同理
  • COMDAT / 弱符号 去重（C++ 内联、模板）
gcc -c a.c b.c
readelf -S a.o b.o
gcc a.o b.o -o ab
readelf -S ab                 # 段合并后总大小

VMA 与 LMA

  • VMA：运行时的虚拟地址（Linux 用户态由 loader 建立映射）
  • LMA：加载到内存/Flash 的物理地址（嵌入式常 VMA≠LMA：代码在 Flash 运行或需拷贝到 RAM）
readelf -l ab                  # Program Headers：LOAD 段 VMA/Align
objdump -h ab

链接顺序影响

gcc -o prog main.o libfoo.a libbar.a   # 从左到右解析符号
# 静库放后面；循环依赖可： -lfoo -lbar -lfoo

查看布局

grep '\.text' prog.map
size prog                       # text/data/bss 汇总

4.4

.2 符号决议

本节讲什么

链接器扫描全部符号，为每个 未定义引用（U） 找到 唯一定义，或报错。规则涉及强/弱符号、COMMON 段、静库成员按需抽取。本节是理解 undefined reference 与 multiple definition 的核心。

要点

强符号 vs 弱符号

类型 示例 冲突时
强 普通全局定义 int x=1; 不能有两个强定义
弱 __attribute__((weak)) 或 int x;（ tentative） 强覆盖弱 
// a.c
int val = 10;           // 强
// b.c
int val;                // 弱 COMMON，链接合并到一处

常见错误

undefined reference to foo'

gcc main.o -o main
# main.o 中 U foo，但未链接定义 foo 的 .o 或库
gcc main.o foo.o -o main    # 补全
nm main.o | grep foo

multiple definition of bar'

# bar 在两个 .o 都有强定义
nm a.o b.o | grep bar
# 改 static、或只保留一处定义、或用 weak

静库符号抽取

ar 归档的 .a 按成员整包尝试：从左到右，仅当某 .o 能解析当前未定义符号时才装入（4.7）。

gcc main.o -L. -lfoo -lbar
nm -A libfoo.a | grep ' T '

C/C++ 注意

  • extern "C" 避免名字改编
  • 内联/static 函数不导出符号
  • 查看：
nm -C prog | less
c++filt _Z3foov

4.4

.3 重定位

本节讲什么

符号决议完成后，链接器遍历各输入的 重定位表，按公式把 占位地址 改成最终 VMA 下的正确值，写回输出文件的 .text/.data。编译期未知的跨文件地址、全局指针、GOT 项都在此或加载期修补。

要点

重定位公式（概念）

对每条重定位项：*addr = S + A + P

  • S：符号最终值（地址）
  • A：加数（addend）
  • P：被修补位置的段内偏移
  • 具体因 重定位类型 而异（相对/绝对/PC 相对）
readelf -r foo.o                 # 链接前
readelf -r prog                  # 可执行文件通常为空（已修补）
objdump -d prog | grep call      # 已是正确目标

典型类型（x86-64）

类型 场景
R_X86_64_PC32 相对跳转 call
R_X86_64_64 64 位绝对地址
R_X86_64_GOTPCREL 经 GOT 访问（4.8）

链接前后对比

gcc -c main.c
objdump -d main.o                # call 目标可能为 0 或占位
gcc main.o -o main
objdump -d main                  # call 指向 libc 或 PLT

加载时重定位

  • PIE + ASLR：内核 loader 映射到随机基址，再做 动态重定位（.rela.dyn）
  • 内核/U-Boot：自拷贝与重定位（4.11、4.12）
readelf -d ./prog | grep RELA
ldd ./prog

与后续衔接

题目 1： 以下代码中 call printf 的地址在链接前后分别是什么？

.1 程序安装的本质

本节讲什么

安装的本质是 文件部署 + 元数据登记：把 ELF 与资源放到标准路径，让 shell、ld.so、服务管理器能找到它们。不改变程序逻辑，但决定 动态库能否加载、配置是否生效、多版本能否共存。

要点

安装做了什么

  1. 复制/链接 二进制与 .so 到 bindir/libdir
  2. 权限（chmod）、属主（chown）
  3. 库缓存 ldconfig 扫描 /etc/ld.so.conf.d
  4. 包元数据（deb 的 control、文件清单）
make prefix=/usr/local install
DESTDIR=/tmp/stage make install   # 打包用暂存根
tree /tmp/stage/usr/local

动态库路径

readelf -d ./prog | grep -E 'RPATH|RUNPATH'
ldd ./prog
LD_LIBRARY_PATH=/opt/lib ./prog   # 临时覆盖

静态 vs 动态安装差异

类型 安装内容 运行依赖
静态链接 单个可执行文件 无外部 .so
动态链接 可执行 + .so 须安装库或设 RPATH 
gcc -static -o prog main.c
ldd prog                          # not a dynamic executable

嵌入式视角

  • 无包管理：整镜像烧录（U-Boot + kernel + rootfs）
  • 4.14 链接脚本决定 Flash 布局，与 PC「安装」类比为「烧录布局」

与后续衔接

  • 4.5.2–4.5.4 各平台打包方式
  • 4.6.1 execve 后 loader 按安装路径加载 .so
  • 4.8.4 SONAME 与版本化共享库

代码自测

题目 1： 为什么安装后的程序能在任意目录执行？这涉及哪些机制？

参考答案

因为可执行文件被安装到 PATH 环境变量包含的目录中。

机制： 1. PATH 变量：echo $PATH 显示搜索路径（如 /usr/local/bin:/usr/bin:/bin） 2. shell 查找：输入 hello 时，shell 按 PATH 顺序查找 hello 可执行文件 3. 动态库搜索路径：运行时按 LD_LIBRARY_PATH → /etc/ld.so.cache → 默认路径查找 .so

ldd hello 查看动态库依赖。ldconfig 更新库缓存（/etc/ld.so.cache）。

若库在非标准路径：export LD_LIBRARY_PATH=/opt/mylib:$LD_LIBRARY_PATH。

4.5

.2 在Linux下制作软件安装包

本节讲什么

Linux 常用 dpkg（.deb） 或 RPM 分发：把 make install 的文件清单、依赖、脚本打包，由 dpkg/apt 解压到根文件系统并触发 postinst。开源项目常提供 autotools/cmake + checkinstall 或正式 debian/ 目录。

要点

基本流程

./configure --prefix=/usr
make -j$(nproc)
sudo make install               # 或 DESTDIR 暂存

DESTDIR 打包

make DESTDIR=/tmp/pkg install
find /tmp/pkg -type f
# 再用 fpm/checkinstall 生成 .deb

checkinstall 示例

sudo checkinstall --pkgname=mytool --pkgversion=1.0
# 跟踪 make install 写入的文件生成 deb

deb 结构（概念）

  • DEBIAN/control：包名、版本、依赖（libc6 等）
  • usr/bin/mytool：实际文件
  • 安装后：ldconfig 在 postinst 中调用
dpkg -L mytool                    # 列出安装文件
dpkg -s mytool                    # 包信息

与编译链接的关系

  • 构建阶段仍用 gcc/ld（4.1–4.4）
  • 打包只收录 usr/ 下产物；-dev 包另含头文件与 .a

与后续衔接

  • 4.5.3 apt 在线安装；4.8.4 包依赖 libc.so.6

代码自测

题目 1： deb 包和源码编译安装各有什么优缺点？

参考答案

deb/rpm 包安装： - 优点：自动处理依赖、统一卸载（apt remove）、版本管理 - 缺点：需要打包流程，灵活性低

题目 1： apt-get install 的工作流程是什么？与编译安装有什么区别？

4.6

程序的运行

本节讲什么

链接/安装之后，运行 指 OS 或裸机把 ELF 载入内存、建立映射、清零 BSS、从 入口 _start 启动运行时，最终调用 main。Linux 上由内核 execve + ld-linux.so 完成；裸机由启动代码与链接脚本决定（4.6.2、4.14）。

要点

运行链路（Linux）

shell → execve() → 内核装载 ELF PT_LOAD
      → ld.so 加载 .so、重定位
      → _start → __libc_start_main → main(argc, argv)

readelf -l ./prog                  # LOAD 段
ldd ./prog

关键参与者

组件 作用
Loader 映射段、设权限、ASLR
ld.so 动态链接、解析 GOT/PLT
_start CRT 入口（非 main）
BSS 加载时清零未初始化全局（4.6.4）

调试入口

gdb ./prog
(gdb) break _start
(gdb) break main
(gdb) run
(gdb) info files

题目 1： 程序运行时操作系统做了哪些工作？以下命令执行后发生了什么？

$ ./hello
参考答案

操作系统执行 ./hello 的流程： 1. fork：shell 调用 fork() 创建子进程 2. execve：子进程调用 execve("./hello", argv, envp) 3. 加载：内核的 ELF 加载器解析 ELF 头，将 .text/.data 映射到虚拟地址空间 4. 4.6

.1 操作系统环境下的程序运行

本节讲什么

Linux 运行 ELF 可执行文件时，内核解析 程序头（Program Header），将 PT_LOAD 段映射到进程虚拟地址空间，物理页 按需分配；ld-linux.so 处理动态段、重定位与初始化，再跳转到用户入口。

要点

execve 装载

readelf -l ./prog
# LOAD 段：/bin 或 /lib 文件偏移 → 虚拟地址 VMA
strace -e execve,mmap ./prog 2>&1 | head -30

虚拟内存布局（典型 x86-64）

高地址  栈 ↓
        mmap / 堆 ↑
        共享库 .so
        .bss / .data / .rodata / .text
低地址

cat /proc/self/maps              # 运行中查看
pmap -x $(pidof prog)

动态链接器

  • .interp 段指定 /lib64/ld-linux-x86-64.so.2
  • ld.so 读取 .dynamic：NEEDED、REL、INIT
readelf -d ./prog
readelf --dyn-syms ./prog | head

ASLR 与 PIE

gcc -pie -fPIE -o prog main.c
readelf -h prog | grep Type       # DYN（位置无关可执行）

代码自测

题目 1： 在有 OS 的环境下，C 程序的 main 函数真的是第一个执行的代码吗？

参考答案

不是。_start（C 运行时库的启动代码）先于 main 执行。

启动流程： 1. 内核加载 ELF：设置虚拟内存映射 2. 跳转 _start（来自 crt1.o）：设置栈、清 BSS 3. __libc_start_main：初始化 C 库（stdio/malloc/locale），注册 atexit 4. 调用 main(argc, argv, envp) 5. main 返回后：exit() → atexit 回调 → _exit()（系统调用，回收进程）

readelf -h hello | grep Entry 查看入口地址，通常是 _start 而非 main。

裸机环境没有 C 运行时，需自己实现 _start → 直接调用 main 或业务逻辑。

4.6

.2 裸机环境下的程序运行

本节讲什么

无 OS 时，CPU 复位后从 向量表/Reset Handler 开始，启动代码负责 初始化时钟/内存控制器、把 .data 从 Flash 拷到 RAM、清零 .bss、设置栈指针，再跳转到 main（或永不返回的内核式循环）。布局由 链接脚本（4.14）与 startup .S 决定。

要点

与 Linux 运行的差异

项目 Linux 裸机
装载 execve + loader 烧录 Flash，复位直接执行
库 ld.so 通常静态链接
BSS loader 清零 startup 汇编循环清零
入口 _start（CRT） Reset_Handler / _start

典型启动顺序

  1. 设置 SP（栈）
  2. 拷贝 .data（LMA → VMA）
  3. 清零 .bss
  4. 调用 SystemInit()、.ctors
  5. bl main

链接脚本关联

arm-none-eabi-gcc -T linker.ld -nostdlib -o firmware.elf startup.o main.o
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
readelf -l firmware.elf

查看段地址

nm firmware.elf | grep -E '_start|main'
objdump -d firmware.elf | head

题目 1： 裸机环境下程序从哪里开始执行？以下启动代码做了什么？

.section .text
.global _start
_start:
    LDR SP, =stack_top    @ 设置栈
    BL main               @ 调用 C main
hang:
    B hang                @ 死循环
参考答案

裸机环境没有 OS，CPU 上电后从固定地址（如 0x00000000）取第一条指令。

4.6

.3 程序入口main()函数分析

本节讲什么

C 程序的 main 不是 ELF 入口。readelf -h 的 Entry point 指向 _start（C 运行时 CRT），由它准备 argc/argv/envp、调用全局构造函数，再调用 main，最后 exit。理解这条链对 gdb 调试、构造/析构顺序和嵌入式 nostdlib 至关重要。

要点

入口地址

readelf -h ./prog | grep 'Entry'
# 典型：0x... 指向 _start，非 main
nm ./prog | grep -E '_start|main'

调用链（glibc）

_start (crt1.o)
  → __libc_start_main(main, argc, argv, ...)
      → __libc_csu_init()   # .ctors 全局构造
      → main(argc, argv, envp)
      → exit(ret)

gcc -o prog main.c
objdump -d prog | grep -A5 '<_start>'
ldd prog                         # 依赖 libc

argc/argv 从哪来

  • 内核在栈上压入 argc、argv[]、envp[]（4.6.1）
  • _start 取栈顶传给 __libc_start_main

无 libc / 裸机

arm-none-eabi-gcc -nostdlib -e main ...   # 入口可直接指定 main（需自写 startup）
  • 内核：start_kernel() 替代 main；DPDK：main → rte_eal_init() → 业务
gdb ./prog
(gdb) break __libc_start_main
(gdb) run

题目 1： main 函数的完整签名是什么？argc 和 argv 的内容来自哪里？

int main(int argc, char *argv[], char *envp[]) {
    printf("argc=%d\n", argc);
    for (int i = 0; i < argc; i++)
        printf("argv[%d]=%s\n", i, argv[i]);
    return 0;
}
参考答案

4.6

.4 BSS段的小秘密

本节讲什么

BSS（Block Started by Symbol） 存放 未初始化全局/静态变量，在 ELF 中 不占文件磁盘空间（SHT_NOBITS），加载时由 loader 或启动代码 清零。static int buf[1024]; 若未显式初始化，全为 0——这是 C 标准保证，靠 BSS 机制实现。

要点

三段对比

段 初值 文件占用
.data 有（如 int x=1） 占
.bss 视为 0 不占（仅记录大小）
.text 机器码 占 
gcc -c foo.c
size foo.o                       # bss 列
readelf -S foo.o | grep -E 'data|bss'

示例

int uninit;                      // 进 .bss
int inited = 42;                 // 进 .data
static char buf[4096];           // .bss

nm foo.o | grep -E 'uninit|inited|buf'
# B uninit / D inited / b buf

谁清零

  • Linux：execve 映射 BSS 页为 零页（CoW）
  • 裸机：startup 汇编对 [__bss_start, __bss_end) 循环写 0（4.6.2）
readelf -l prog | grep LOAD       # BSS 常合并在最后一 LOAD
objdump -h prog

常见误区

  • BSS 过大占 运行期 RAM，不占镜像体积——嵌入式要关注 RAM 预算
  • char *p; 全局未初始化为 NULL（0），局部变量 不在 BSS，值不确定

  • 4.4.1 链接合并各 .o 的 .bss

  • ch05 堆与 mmap 另算；DPDK rte_zmalloc 显式清零堆内存

代码自测

题目 1： 以下代码编译后的目标文件和可执行文件中，BSS 段有什么"秘密"？

int uninit_global;      // BSS
int init_global = 42;    // data
int main(void) {
    static int uninit_static;  // BSS
    return 0;
}
参考答案

BSS 段的秘密：BSS 段在目标文件和可执行文件中不占空间，只在运行时由加载器分配内存。

原因：BSS 段的值全为 0，没必要在文件中存储一堆 0。ELF 只记录 BSS 段的大小（p_memsz > p_filesz），加载时内核分配匿名页并清零。

验证： - size hello.o：BSS 列显示字节数，但 ls -l hello.o 的文件大小不含 BSS - readelf -S hello.o：.bss 节的 FileSize 为 0，MemSize 为实际大小

好处：大量未初始化数组（如 int buf[10000]）不增大可执行文件体积。

4.7

链接静态库

本节讲什么

静态库 .a 是多个 .o 的 归档（ar），链接时链接器 按需抽取 成员 .o 并入可执行文件，代码成为二进制一部分，运行期无 .so 依赖。适合嵌入式、内核部分场景；缺点是体积与升级成本。

要点

制作与使用

gcc -c foo.c bar.c
ar rcs libmy.a foo.o bar.o
ar t libmy.a                     # 列出成员
nm libmy.a
gcc main.o -L. -lmy -o prog      # -lmy 即 libmy.a

链接器搜索规则

  • -L/path 指定目录
  • -lname → libname.a 或 libname.so（默认先 so，可用 -static 强制静库）
  • 从左到右：未解析符号才拉入 .a 中对应 .o
gcc -static -o prog main.o -L. -lmy
ldd prog                         # not a dynamic executable

  • 静库中未被引用的 .o 不会 进入最终 ELF（减小体积）
  • 循环依赖：gcc ... -lfoo -lbar -lfoo

常见错误

nm libmy.a | grep duplicate_sym

nm prog | grep my_func
readelf -s prog | grep my_func

4.8

动态链接

本节讲什么

动态链接 把共享库 .so 在 运行期 由 ld.so 映射进进程，多进程 共享代码页，升级库无需重编主程序。实现依赖 PIC、GOT、PLT 与延迟绑定（4.8.1–4.8.4）。Linux 用户态程序、DPDK PMD 插件、内核模块（insmod）都属广义「运行时装入」。

要点

构建与链接

gcc -fPIC -shared -o libfoo.so foo.c
gcc -o prog main.c -L. -lfoo
readelf -d prog | grep NEEDED
ldd prog

静 vs 动

静态 .a 动态 .so
链接时机 构建期 构建期记依赖 + 运行期加载
体积 可执行大 可执行小，库共享
升级 重链 换 .so（SONAME 兼容）

动态段

readelf -d libfoo.so
# SONAME、NEEDED、INIT、FINI、PLTGOT、JMPREL...
readelf --dyn-syms libfoo.so

加载流程（简述）

  1. execve 映射主程序
  2. ld.so 加载 NEEDED 库
  3. 重定位 GOT/PLT（4.8.2/4.8.3）
  4. 跳 _start → main

  • 4.8.1 PIC；4.8.2 GOT；4.8.3 PLT 延迟绑定；4.8.4 共享库实践
  • 4.9 插件即 dlopen 动态库
  • 4.10 内核模块类似动态装入（无 ELF 用户态 loader）

4.8

.1 与地址无关的代码

本节讲什么

PIC（Position Independent Code） 使 .so 文本段可映射到 任意虚拟地址（ASLR），指令中不出现绝对地址，而通过 GOT/PC 相对 访问数据与函数。编译加 -fPIC（x86-64 常隐含于 -shared）。

要点

为何需要 PIC

  • 共享库只加载 一份物理代码，多进程映射到 不同基址
  • 非 PIC：重定位会修改 .text（Copy-on-Write，失去共享优势）
gcc -fPIC -c foo.c -o foo_pic.o
gcc -fno-PIC -c foo.c -o foo_nop.o
readelf -r foo_pic.o foo_nop.o

访问全局变量（x86-64）

  • 非 PIC：movabs $sym, %rax（绝对地址）
  • PIC：mov sym@GOTPCREL(%rip), %rax 经 GOT 间接加载
gcc -fPIC -S -O0 foo.c -o -
objdump -d foo_pic.o | grep -i got

编译选项

gcc -fPIC -shared -o libfoo.so foo.c
gcc -fPIE -pie -o prog main.c    # 可执行也可 PIE
readelf -h libfoo.so | grep Type  # DYN

ARM 注记

  • ARM/ARM64 通常默认 PIC；adr + GOT 访问（ch03）

与后续衔接

  • 4.8.2 GOT 存符号运行时地址
  • 4.8.3 函数经 PLT 跳转；4.4.3 重定位与 PIC 配合
  • DPDK 共享 PMD；内核模块必须为可重定位代码

代码自测

题目 1： 什么是位置无关代码（PIC）？为什么共享库必须使用 PIC？

// 非PIC代码 (静态链接)
movl global_var, %eax    @ 绝对地址

// PIC代码 (动态链接)
movl global_var@GOT, %eax @ 通过GOT间接访问
参考答案

PIC（Position Independent Code）：代码不包含绝对地址，所有地址引用都通过 PC 相对寻址或 GOT 间接访问。

为什么共享库需要 PIC： - 共享库被映射到不同进程的不同虚拟地址 - 若代码含绝对地址，每个进程都需要修改代码页（Copy-on-Write，失去共享优势） - PIC 代码只读，可被多进程共享；数据通过 GOT 间接访问

编译：gcc -fPIC -shared -o libfoo.so foo.c（-fPIC 生成 PIC 代码）

GOT（全局偏移表）存储全局变量/函数的实际地址，每个进程有自己的 GOT 副本。

4.8

.2 全局偏移表

本节讲什么

GOT（Global Offset Table） 是 .got/.got.plt 段中的 地址表：PIC 代码通过「基址 + 偏移」查表取得全局变量与函数的真实地址。链接时填部分项，加载时 ld.so 根据 重定位表 .rela.dyn 补全。

要点

GOT 作用

  • 数据访问：mov var@GOTPCREL(%rip), %rax
  • 与 PLT 配合解析外部函数地址（4.8.3）
gcc -fPIC -shared -o libfoo.so foo.c
readelf -S libfoo.so | grep got
objdump -d libfoo.so | grep -i got

查看动态重定位

readelf -r libfoo.so              # .rela.dyn / .rela.plt
readelf -d libfoo.so | grep REL

常见项：R_X86_64_GLOB_DAT、R_X86_64_JUMP_SLOT（函数 GOT/PLT 槽）。

链接前后

gcc -fPIC -c foo.c
readelf -r foo.o
gcc -shared -o libfoo.so foo.o
readelf --dyn-syms libfoo.so

性能注记

  • 经 GOT 多一次间接访存；static 内部函数可不走 GOT
  • -fno-plt 等优化可减少 PLT 层（高级话题）

与后续衔接

  • 4.8.3 PLT 桩代码跳 GOT 槽；延迟绑定时首次调用才写槽

代码自测

题目 1： GOT（Global Offset Table）的工作原理是什么？以下代码如何通过 GOT 访问全局变量？

// 共享库中的代码
extern int shared_var;
int get_var(void) {
    return shared_var;
}
参考答案

GOT 是一个数据表，存储全局符号的实际运行时地址。

访问流程： 1. 代码用 PC 相对寻址找到 GOT 中 shared_var 对应的槽位 2. 从 GOT 读取 shared_var 的实际地址 3. 通过该地址访问变量

get_var:
    LDR R0, [PC, #offset]  @ R0 = &GOT[n] (PC相对)
    LDR R0, [R0]            @ R0 = GOT[n] = shared_var的实际地址
    LDR R0, [R0]            @ R0 = *shared_var

GOT 在加载时由动态链接器填充实际地址。代码段只读可共享，GOT 在数据段每个进程独立。

4.8

.3 延迟绑定

本节讲什么

延迟绑定（Lazy Binding） 通过 PLT（Procedure Linkage Table） 实现：首次 call printf@plt 才由 ld.so 解析真实地址并写入 GOT，后续调用直达目标。加快启动、避免链接未用函数。可用 LD_BIND_NOW 关闭。

要点

PLT 桩（概念）

call printf@plt  →  PLT[n]  →  首次：跳 ld.so 解析器
                              →  之后：GOT[n] 已是 printf 地址

gcc -o prog main.c
objdump -d prog | grep -A3 '<printf@plt>'
readelf -r prog | grep JUMP_SLOT

相关节

readelf -S prog | grep -E 'plt|got'
readelf -d prog | grep PLTGOT
  • .plt：桩代码
  • .got.plt：函数地址槽
  • .rela.plt：R_X86_64_JUMP_SLOT 重定位

强制立即绑定

LD_BIND_NOW=1 ./prog
# 或链接： gcc -Wl,-z,now ...
readelf -d prog | grep BIND_NOW

调试

ltrace ./prog                    # 观察首次解析
gdb ./prog
(gdb) break printf
(gdb) run

代码自测

题目 1： 什么是延迟绑定（Lazy Binding）？它如何优化程序启动速度？

参考答案

延迟绑定：函数地址在第一次调用时才解析，而非启动时全部解析。

机制（PLT + GOT）： 1. 第一次调用 printf：跳转到 PLT 入口 → GOT 中地址指向 PLT 下一指令 → 调用 _dl_runtime_resolve 解析 printf 地址 → 修正 GOT → 执行 printf 2. 后续调用：直接从 GOT 获取已解析的地址，跳转到 printf

优点：启动快（只解析实际调用的函数），大型库可能只有少数函数被使用。

环境变量 LD_BIND_NOW=1：禁用延迟绑定，启动时解析所有符号（用于调试）。

PLT（过程链接表）在代码段，GOT 在数据段。

题目 1： 如何创建共享库？soname 有什么作用？

# 创建

4.9

插件的工作原理

本节讲什么

要点

基本 API

常见约定

  • 固定入口符号：plugin_register、rte_pmd_init 等

排错

代码自测

题目 1： 插件机制如何实现？以下代码中 dlopen/dlsym 各完成什么功能？

void *handle = dlopen("./plugin.so", RTLD_NOW);
if (!handle) { fprintf(stderr, "%s\n", dlerror()); return -1; }
typedef int (*func_t)(int);
func_t func = (func_t)dlsym(handle, "process");
func(42);
dlclose(handle);
参考答案

插件机制基于动态链接的运行时加载：

  • dlopen("./plugin.so", RTLD_NOW)：运行时加载共享库到进程地址空间。RTLD_NOW 立即解析所有符号（RTLD_LAZY 延迟解析）
  • dlsym(handle, "process")：在已加载的库中查找符号 process 的地址，返回函数指针
  • 调用 func(42)：通过函数指针调用插件函数
  • dlclose(handle)：卸载共享库（引用计数归零时真正卸载）

编译需 -ldl。插件 .so 必须用 -fPIC -shared 编译。

应用：浏览器插件、GStreamer 编解码器、Nginx 模块、编辑器扩展。

4.14

链接脚本

本节讲什么

链接脚本（Linker Script） 用 MEMORY 与 SECTIONS 告诉 ld：各段放入哪块物理存储、链接顺序、VMA/LMA。裸机/嵌入式把 .text/.rodata 放 Flash、.data/.bss 放 RAM 全靠脚本；Linux 内核 vmlinux.lds、U-Boot u-boot.lds 同理（4.11、4.12）。

要点

最小示例（ARM 裸机概念）

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .text : {
        KEEP(*(.isr_vector))
        *(.text*)
        *(.rodata*)
    } > FLASH

    .data : AT (ADDR(.text) + SIZEOF(.text)) {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > RAM

    .bss : {
        _sbss = .;
        *(.bss*) *(COMMON)
        _ebss = .;
    } > RAM
}
  • > 目标内存；AT 指定 LMA（Flash 中存放位置）
  • startup 用 _sdata/_edata 拷贝、_sbss/_ebss 清零（4.6.2）

使用方式

arm-none-eabi-gcc -nostdlib -T linker.ld -o firmware.elf startup.o main.o
arm-none-eabi-readelf -l firmware.elf
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
arm-none-eabi-nm firmware.elf | grep -E '_sdata|_sbss|main'

常用命令行

gcc -Wl,-T,linker.ld -Wl,-Map,out.map main.o
# 或
ld -T linker.ld -o out.elf *.o

与用户态默认脚本

  • ld 默认脚本：ld --verbose 查看
  • 一般 Linux 程序不显式写脚本；嵌入式几乎必须自定义

题目 1： 链接脚本（.lds）的作用是什么？以下脚本定义了什么内存布局？

ENTRY(_start)
SECTIONS {
    . = 0x80000000;
    .text : { *(.text) }
    . = ALIGN(4);
    .data : { *(.data) }
    .bss : { *(.bss) *(COMMON) }
}
参考答案

链接脚本控制链接器如何合并段和分配地址：

  • ENTRY(_start)：指定程序入口为 _start（而非默认的 main）
  • . = 0x80000000：设置起始地址（裸机/嵌入式指定运行地址）
  • .text : { *(.text) }：合并所有输入文件的 .text 段
  • . = ALIGN(4)：4 字节对齐
  • .data/.bss：同理，COMMON 是链接器分配的公共符号

用途： - 嵌入式系统指定代码在 Flash/SRAM 中的位置 - 控制段顺序和对齐 - 定义符号（如 _text_start = .;）供 C 代码引用

gcc -T link.lds ... 或 ld -T link.lds 指定链接脚本。
