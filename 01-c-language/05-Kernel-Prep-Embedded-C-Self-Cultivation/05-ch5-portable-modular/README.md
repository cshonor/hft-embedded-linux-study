## 本章讲什么

模块化和跨平台不是两件事：

```text
模块化的目的是隔离变化 → 跨平台是最难的一种变化
```

所以「头文件怎么写」「模块之间怎么通信」「哪些东西可以写死、哪些必须抽象」——这三件事的答案，直接决定了你的代码能不能移植。

## 跨平台的三条硬规则

1. **不要用 `int`/`long` 表达宽度。** 用 `<stdint.h>` 的 `uint32_t` / `int64_t`。`long` 在 LP64（Linux）是 64 位，在 LLP64（Windows）是 32 位——这是最容易踩的一条。
2. **结构体跨 ABI 不可信。** 同一个 `struct` 在不同编译器/选项下布局可能变。要固化布局就用 **`packed` + 显式位序**（见 [CH2 6.7](../02-ch2-gnu-c-advanced/6.7-aligned/6.7-属性声明-aligned.md)），并**只用于协议/寄存器结构体**，不要用于内部数据结构。
3. **字节序在跨设备时永远要显式处理。** 网络序/总线序不等于主机序；用 `__builtin_bswap*`（见 [CH3 10.8](../03-ch3-embedded-driver/10.8-register/10.8-寄存器操作.md)），不要手写移位。

**Q1：为什么 `size_t` 要跟指针一样宽，而不是跟 `int` 一样宽？**

<details><summary>答案</summary>
因为它的语义是「内存对象的大小上限」，而理论上能分配的最大对象受地址空间限制。所以 LP64 下 `size_t` 是 `unsigned long`（64 位），32 位下是 `unsigned int`。这也是为什么打印它要用 `%zu`——用 `%d` 在 64 位上会截断。详见 [7.4](./7-data-and-pointers/7.4-Linux内核中的size_t类型.md)。
</details>

**Q2：`#ifdef MY_ARCH` 满天飞，为什么是跨平台设计的失败信号？**

<details><summary>答案</summary>
条件编译应该**收敛到一层**（通常是 port/ 或 hal/ 目录），上层只见统一接口。散落在业务代码里的 `#ifdef` 会让组合数爆炸——两个维度各 3 种实现就有 9 条路径要测。正确做法见 [9.8.1](./9-modular-c/9.8-advanced/9.8.1-跨平台设计.md)：抽象出接口，平台相关的实现放在各自的 .c 里，用构建系统选择编译哪一份。
</details>

**Q3：C 里怎么实现「虚函数」？**

<details><summary>答案</summary>
结构体里放一张**函数指针表**。每个子类在自己的实现里填这张表，调用方通过指针间接调用。这就是 C++ vtable 的手写版——内核的 `struct file_operations`、`struct device_driver` 全都是这个模式。见 [8.5](./8-oop-in-c/8.5-Linux内核中的OOP思想-多态.md)。
</details>
