# 6.6.1 GNU C编译器扩展关键字：__attribute__

[← 6.6 属性声明 section](6.6-属性声明-section.md) · [ch06 GNU C 扩展](../../README.md)

> **本篇是 `__attribute__` 的完整总纲**——覆盖全部常用属性（诊断类 / 优化类 / 链接类 / 布局类），每个都有可编译示例与本机实测结论。
> 单个属性的**深度实测与性能数据**在 [18.10 GCC 属性总览（Pointers on C ch18）](../../../02-Pointers-on-C/ch18-runtime-environment/18.10-GCC属性总览.md)；`packed`/`aligned` 的对齐计算在 [6.7](../6.7-aligned/6.7-属性声明-aligned.md)，`section` 在 [6.6.2](6.6.2-属性声明-section.md)，`weak`/`alias` 在 [6.9](../6.9-weak/6.9-属性声明-weak.md)，`noinline` 在 [6.10.1](../../01-ch1-gnu-c-basics/6.10-inline/6.10.1-属性声明-noinline.md)。

## 本节讲什么

**`__attribute__((...))`** 是 GCC/Clang 附着于**声明**的编译指示。它不改变 C 的类型系统，却影响四件事：**布局、链接、优化、诊断**。

一句话定性：**它是给编译器的"元信息通道"**——把你在源码里知道、但 C 语法表达不出来的事实（"这个函数不会返回"、"这块内存 32 字节对齐"、"这个指针可以和 float 别名"）告诉编译器，让它敢做原本不敢做的优化、或能报原本报不出的错。

| 关键事实 | 说明 |
|---|---|
| 不是 C 标准 | GNU 扩展。MSVC 不认，必须条件编译（见 [可移植写法](#可移植写法三种层次)） |
| Clang 支持绝大多数 | 但**不是全部**——`optimize` 在 Clang 上被静默忽略（实测见 [组 12](#6-optimizeargs的坑)） |
| C23 有标准替代 | `[[deprecated]]` / `[[nodiscard]]` / `[[fallthrough]]` / `[[maybe_unused]]` 等，见 [对照表](#c23-标准属性-vs-gnu-属性对照表) |
| 属性写错可能**静默失效** | 位置错、索引越界、被链接器覆盖，三种失效模式见 [坑点](#坑点清单) |

## 一、语法：写在三种对象上

```c
/* 变量：类型之后、变量名之前，或声明末尾 */
int x __attribute__((aligned(64)));
__attribute__((aligned(64))) int y;

/* 函数：声明前（推荐，可读性好）或声明后 */
__attribute__((noreturn)) void panic(void);
void foo(void) __attribute__((section(".text.foo")));

/* 类型：struct/union/enum */
struct __attribute__((packed)) msg { char c; int i; };
typedef int __attribute__((may_alias)) int_alias;
```

多个属性用逗号分隔：

```c
__attribute__((section(".init"), unused, noinline))
static void early_init(void) { }
```

### ⚠️ 位置写错 = 静默失效（实测三种写法）

这条最容易被 Python/Java 的装饰器习惯带偏。以 `[[gnu::packed]]` 为例（gcc 13.3 实测）：

| 写法 | `sizeof` | 是否生效 |
|------|----------|----------|
| `struct [[gnu::packed]] S { ... };` | **5** | ✅ 唯一正确 |
| `struct S { ... } [[gnu::packed]];` | 8 | ❌ `warning: attribute ignored` |
| `[[gnu::packed]] struct S { ... };` | 8 | ❌ `warning: empty declaration` |

**规则**：属性写在 `struct` 关键字**之后**、结构体名**之前**。后两种只是 warning，**不会拦住编译**——你以为生效了，其实没有。Clang 对后两种直接 error，所以"能过 gcc 不等于对"。

## A. 诊断与检查类

这类是**最实用**的——把"运行期偶发崩溃"变成"编译期必报"。

### 1. `format(archtype, m, n)`

```c
/* 单固定参：格式串在第 1 位，变参从第 2 位开始 */
void log_msg(const char *fmt, ...) __attribute__((format(printf, 1, 2)));

/* 两个固定参（你的 Quiz）：格式串在第 2 位，变参从第 3 位开始 */
void my_log(int prio, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));
```

**记忆法**：两个数字是**从 1 开始的位置编号，不是偏移量**。

能拦四类错误（实测）：

```c
log_msg("%d", 3.14);    /* -Wformat: expected 'int' but arg is 'double' */
log_msg("%s", 42);      /* -Wformat: expected 'char *' but arg is 'int' */
log_msg("%d %d", 1);    /* -Wformat: too few arguments */
log_msg("%d", 1, 2);    /* -Wformat: too many arguments */
```

> ⚠️ **必须开 `-Wformat`**（`-Wall` 已含）；`-Werror=format` 升级为错误。
> ⚠️ **索引写错 = 静默失效**：`test(const char *fmt, ...)` 上写 `2,3` 时报
> `warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1 [-Wattributes]`，
> 之后所有调用点**零报警**。排查索引越界的唯一开关是 **`-Wattributes`**。
> ⚠️ C++ 成员函数 `this` 隐式占第 1 位，所以要写 `2,3`（详见 7.6.2 / 18.10）。

### 2. `nonnull` / `returns_nonnull`

```c
__attribute__((nonnull(1)))
int str_len(const char *s) { int n = 0; while (s[n]) n++; return n; }

__attribute__((returns_nonnull))
void *alloc_never_null(void);
```

实测（gcc / clang 一致）：

```
warning: argument 1 null where non-null expected [-Wnonnull]
   42 |     str_len(NULL);
```

**局限**：只在你**传 NULL 常量**时静态发现。传一个运行时才为 NULL 的指针，它发现不了——所以它是"文档 + 常量检查"，不是运行时防护。

### 3. `sentinel`

变参必须以 NULL 结尾（呼应 [7.6.2 哨兵](../../../02-Pointers-on-C/ch07-functions/7.6-variable-argument-lists/7.6.2-可变参数的限制.md)）：

```c
__attribute__((sentinel))
int run_all(const char *first, ...);
```

实测 `run_all("a", "b", "c")`（漏 NULL）：

| 编译器 | 输出 |
|---|---|
| gcc | `warning: missing sentinel in function call [-Wformat=]` |
| clang | `warning: missing sentinel in function call [-Wsentinel]` |

注意 gcc 把它挂在 `-Wformat` 下——`sentinel` **没有自己的独立开关**。

### 4. `warn_unused_result` / `deprecated`

```c
__attribute__((warn_unused_result))
int must_check(void);

__attribute__((deprecated))
void old_api(void);

__attribute__((deprecated("use new_api2 instead")))
void old_api2(void);
```

实测（gcc 与 clang **完全一致**）：

```
warning: ignoring return value of 'must_check' declared with attribute 'warn_unused_result' [-Wunused-result]
warning: 'old_api' is deprecated [-Wdeprecated-declarations]
warning: 'old_api2' is deprecated: use new_api2 instead [-Wdeprecated-declarations]
```

`deprecated` 带消息的版本最有价值——**在调用点直接告诉你该换成什么**。

### 5. `error` / `warning`（编译期强制）

```c
/* error：调用即编译错误。内核常用它把"配置禁用的路径"钉死 */
extern void forbidden(void) __attribute__((error("forbidden: 此路径被配置禁用")));

/* warning：调用即警告，但仍生成代码 */
extern void risky(void) __attribute__((warning("risky: 建议改用 safe_api")));
```

实测 gcc：

```
error: call to 'forbidden' declared with attribute error: forbidden: 此路径被配置禁用
   13 |     forbidden();
```

Clang 18 同样支持（措辞 `'error' attribute`）。**这是唯一能把"不该调用的函数"在编译期拦住的手段**——比注释和 code review 可靠得多。

> ⚠️ 注意 `error`/`warning` 属性只在**调用点可达**时触发。若函数只有声明（如上面的 `extern`），且代码路径实际执行到，链接期会因找不到定义而失败——所以这两个属性通常配 `#ifdef` 或内联定义使用。

### 6. `fallthrough`

```c
switch (n) {
case 1:
    r = 10;
    __attribute__((fallthrough));   /* 告诉编译器：我是故意落空的 */
case 2:
    r += 20;
    break;
}
```

实测 `gcc -std=c11 -Wextra`：不加属性报 `warning: this statement may fall through [-Wimplicit-fallthrough=]`，加了就不报。

⚠️ **Clang 18 在 `-Wextra` 下默认不报 implicit fallthrough**（实测 0 条警告）——**别拿一个编译器的警告数当代码质量的度量**。C23 标准写法是 `[[fallthrough]];`。

## B. 优化提示类

### 1. `hot` / `cold`（段布局实测）

```c
__attribute__((hot))  int  hot_path(int n);
__attribute__((cold)) void cold_error(const char *msg);
```

`-O2` 实测段分布：

```
  0 .text           00000045        ← dispatch
  3 .text.hot       00000035        ← hot_path
  5 .text.unlikely  00000049        ← cold_error, cold_calc
  6 .text.startup   0000003f

符号表：
000000000000003c t dispatch.cold    ← gcc 自动把冷分支拆出主函数！
```

**关键证据是 `dispatch.cold`**——gcc 不只是把 cold 函数放进 `.text.unlikely`，还会**把热函数里的冷分支（错误处理）抽出来**单独放。收益是热路径的代码全挤在同一个页/cache 行附近，取指更集中。

对 HFT 的意义：`cold` 让错误处理路径不占热路径的 i-cache，比手写 `if (unlikely)` 更进一步。实测与 `__builtin_expect` 的对照见 [18.10](../../../02-Pointers-on-C/ch18-runtime-environment/18.10-GCC属性总览.md)。

### 2. `flatten`

```c
__attribute__((flatten))
int flatten_sum(int n)
{
    int s = 0;
    for (int i = 0; i < n; i++) s += helper_add(i);
    return s;
}
```

`-O2` 实测：`flatten_sum` 内 **`call` 数 = 0**（`helper_add` 被内联进来了），但 `helper_add` 的独立函数体仍保留（因为它是外部链接，可能被别处调用）。

与 `always_inline` 的区别：`always_inline` 是**指定某一个函数**必须内联；`flatten` 是**指定某个函数内**的所有调用都尽量内联——批量操作，适合"这一条路径我要全部展开"。

### 3. `malloc` / `alloc_size` / `assume_aligned`

```c
__attribute__((malloc))
void *my_alloc(size_t n);

__attribute__((malloc, alloc_size(1)))      /* 第 1 参数是字节数 */
void *my_alloc2(size_t n);

__attribute__((assume_aligned(32)))
void *my_aligned_alloc(size_t n);
```

- `malloc`：告诉编译器"返回的是全新内存，不与任何现存指针别名"——**省掉一次可能的重新加载**，与 `const`/`pure` 同类思路。
- `alloc_size(n)`：让 `__builtin_object_size` 能推断大小，`-D_FORTIFY_SOURCE` 的边界检查依赖它。
- `assume_aligned(32)`：实测返回地址 `c % 32 == 0`，调用方可以放心用对齐的 SIMD 指令访问。

> ⚠️ 这组属性是**承诺不是检查**。你标了 `assume_aligned(32)` 却返回未对齐地址，编译器不会报错，只会在生成对齐访问指令时让你 SIGBUS。

### 4. `optimize("args")` 的坑

```c
__attribute__((optimize("O0")))
int forced_o0(int n) { int s = 0; for (int i = 0; i < n; i++) s += i; return s; }
```

| 编译器 | 结果 |
|---|---|
| gcc 13.3 | 接受，输出 `10 10` |
| **clang 18** | `warning: unknown attribute 'optimize' ignored [-Wunknown-attributes]` —— **静默忽略** |

而且 gcc 文档自己也警告：`optimize` 属性会**重置该函数的所有其它优化选项**（不只是你指定的那个），行为难以预测。**工程上不要用**，需要不同优化级别就拆文件、用 `#pragma GCC optimize` 或单独编译。

## C. 符号与链接类

### `visibility`：.so 的 ABI 边界

```c
int public_add(int a, int b)                                    { return a + b; }

__attribute__((visibility("hidden")))
int hidden_add(int a, int b)                                    { return a + b; }

__attribute__((visibility("protected")))
int prot_add(int a, int b)                                      { return a + b; }
```

`gcc -shared -fPIC` 后实测：

```
$ nm -D libvis.so | grep add
0000000000001119 T public_add      ← 在动态符号表里
0000000000001149 T prot_add        ← 在
                                   ← hidden_add 不在！

$ readelf -sW libvis.so | grep add
public_add  GLOBAL
hidden_add  LOCAL                  ← 可见性被降级为 LOCAL
prot_add    GLOBAL

$ # 整体隐藏：-fvisibility=hidden
$ nm -D libvis2.so | grep add
0000000000001129 T prot_add        ← 只剩显式声明的
```

| 可见性 | 在 `.dynsym` | 能否被外部引用 | 能否被 LD_PRELOAD 抢占 |
|---|---|---|---|
| `default`（默认） | ✅ | ✅ | ✅ |
| `hidden` | ❌ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ❌（本模块内引用绑死） |

**工程实践**：编译 `.so` 时用 `-fvisibility=hidden` 全局隐藏，再对真正的导出 API 显式标 `__attribute__((visibility("default")))`。收益：

1. **ABI 收窄**——内部函数不会意外变成对外承诺
2. **加载更快**——动态符号表小了，符号解析的 hash 查找更少
3. **调用更快**——`hidden` 调用不经过 PLT，直接 PC 相对跳转（HFT 热路径上这是真实收益）
4. **防抢占**——内部工具函数不会被 LD_PRELOAD 的恶意同名符号截获

这也是为什么你看到的库代码里到处是 `__attribute__((visibility("default")))`。

## D. 内存布局类

### `cleanup` 专题：C 唯一像样的自动释放

`cleanup` 只修饰**局部变量**，变量离开作用域时自动调用指定函数，**参数是该变量的地址**。

```c
static void free_buf(void *p)
{
    void **pp = (void **)p;          /* 注意：收到的是变量地址，不是变量值 */
    if (*pp) { free(*pp); *pp = NULL; }
}

int main(void)
{
    {
        void *b1 __attribute__((cleanup(free_buf))) = malloc(64);
        void *b2 __attribute__((cleanup(free_buf))) = malloc(64);
        /* ... 用 b1 b2 ... */
    }   /* 离开作用域自动 free，不需要写 goto cleanup */
}
```

实测输出（`-O0` 与 `-O2` **完全一致**）：

```
=== 1. 基本 ===
  b1=0x55612a9382b0 b2=0x55612a938300
  [cleanup] free(0x55612a938300)     ← b2 先释放
  [cleanup] free(0x55612a9382b0)     ← b1 后释放
  已离开作用域

=== 2. 多个 cleanup 的顺序 ===
  [cleanup] close tag 3              ← z（最后声明）
  [cleanup] close tag 2              ← y
  [cleanup] close tag 1              ← x（最先声明）

=== 3. 提前 return ===
  early: b=0x55612a938350
  early: return -1 (提前返回)
  [cleanup] free(0x55612a938350)     ← 照样触发

=== 4. 嵌套作用域 ===
  外层 o=0x...380
  内层 i=0x...3a0
  [cleanup] free(0x...3a0)           ← 内层先结束
  内层已结束
  [cleanup] free(0x...380)           ← 外层后结束
```

三条确定结论：

| 特性 | 实测结果 |
|---|---|
| **执行顺序** | **逆序（LIFO）**——后声明的先清理，与 C++ 析构顺序一致 |
| **提前 `return`** | ✅ 照样触发（这正是它优于手写清理的地方） |
| **嵌套作用域** | 内层先清理，各管各的 |

**这是 C 里最接近 RAII 的东西**，而且是唯一一个"提前 return 也不会漏"的清理机制。用它替代 `goto cleanup` 模式能显著减少资源泄漏。

> ⚠️ 三个限制：
> 1. 只能修饰**自动变量**（局部变量），不能修饰全局/静态
> 2. `longjmp` 跳出作用域时**不保证**触发（GNU 文档明示）——有 setjmp 的代码别依赖它
> 3. 清理函数的参数是 `void*` 指向变量，所以释放指针要写成 `void **pp` 再 `*pp`

### `may_alias` 专题：严格别名的解药

这条直接回答 [6.11 / ch06 指针表达式](../../../02-Pointers-on-C/ch06-pointers/6.11-指针表达式.md) 里那个经典 UB：`*(uint32_t *)&f` 为什么是未定义行为，以及**怎么合法地做同样的事**。

```c
typedef int __attribute__((may_alias)) int_alias;

/* A：普通 int* —— 编译器可假设它与 float* 不别名 */
static int strict(int *ip, float *fp)
{
    *ip = 1;
    *fp = 2.0f;
    return *ip;          /* 编译器认为 fp 不会动 ip，直接返回 1 */
}

/* B：may_alias —— 编译器必须假定可能别名，每次重新加载 */
static int aliased(int_alias *ip, float *fp)
{
    *ip = 1;
    *fp = 2.0f;
    return *ip;
}

/* 调用时两者传同一个地址 */
float storage;
strict ((int *)      &storage, &storage);
aliased((int_alias *)&storage, &storage);
```

`2.0f` 的位模式是 `0x40000000` = 1073741824。实测：

| 编译选项 | A 普通 `int*` | B `may_alias` |
|---|---|---|
| `-O1` | 1073741824（重新加载） | 1073741824 |
| **`-O2`** | **1（读的是旧值！）** | **1073741824** |
| **`-O3`** | **1** | **1073741824** |
| `-O2 -fno-strict-aliasing` | 1073741824 | 1073741824 |
| **clang -O2** | **1** | **1073741824** |

**这就是严格别名 UB 的可观测后果**：`-O2` 下 A 返回 1（编译器省掉了重新加载，因为按 C11 6.5p7 它有权假设 `int*` 和 `float*` 不指向同一对象），而实际内存已被 `*fp = 2.0f` 改成 1073741824。加 `-fno-strict-aliasing` 就"修好"了——**但那是用放弃优化换来的**。

`may_alias` 是**精准解药**：只在这一个类型上声明"我就要别名"，其余代码照常享受严格别名优化。

> ⚠️ 适用边界：`may_alias` 解决的是**类型双关（type punning）**。日常读写还是应该用 `memcpy`——现代编译器会把小 `memcpy` 完全优化成一条 `mov`，零成本且绝对合法。`may_alias` 留给"我确实要长期用两个类型视角看同一块内存"的场景（如协议解析、SIMD 寄存器复用）。

### `transparent_union`

```c
typedef union __attribute__((transparent_union)) {
    int    i;
    float  f;
    void  *p;
} any_t;

void take(any_t a);      /* 调用方可以直接传 int / float / void*，无需显式构造 union */
take(42); take(3.14f); take(ptr);
```

主要用于消除旧 API 的调用噪音，新代码少见。

## 可移植写法（三种层次）

`__attribute__` 是 GNU 扩展，MSVC 完全不认。工程上按三层封装：

### 层次 1：条件编译宏（最通用）

```c
#ifdef __GNUC__
#  define FMT_PRINTF(a, b)  __attribute__((format(printf, a, b)))
#  define NORETURN          __attribute__((noreturn))
#  define UNUSED            __attribute__((unused))
#  define PACKED            __attribute__((packed))
#  define ALIGNED(n)        __attribute__((aligned(n)))
#  define EXPORT            __attribute__((visibility("default")))
#else
#  define FMT_PRINTF(a, b)
#  define NORETURN
#  define UNUSED
#  define PACKED
#  define ALIGNED(n)
#  define EXPORT
#endif

void log_msg(const char *fmt, ...) FMT_PRINTF(1, 2);
```

### 层次 2：`__has_attribute` 探测（GCC 10+ / Clang）

属性支持情况随编译器版本变化，用探测宏代替版本判断：

```c
#if defined(__has_attribute)
#  if __has_attribute(cleanup)
#    define AUTOFREE(fn) __attribute__((cleanup(fn)))
#  endif
#endif
#ifndef AUTOFREE
#  define AUTOFREE(fn)          /* 不支持就退化成无效果 */
#endif
```

实测 gcc 13.3 与 clang 18 的差异：

| 属性 | gcc 13.3 | clang 18 |
|---|---|---|
| `cleanup` | 1 | 1 |
| `format` | 1 | 1 |
| `may_alias` | 1 | 1 |
| **`counted_by`** | **0** | **1** |

`counted_by`（C23 柔性数组的计数绑定）gcc 14 才支持——**这就是探测宏存在的意义**，写版本判断会漏掉" gcc 13 vs 14 "这种细粒度差异。

### 层次 3：C23 标准属性（最推荐，能用就用）

C23 把最常用的几个属性纳入了标准语法 `[[...]]`。**新项目优先用标准写法**——MSVC 也认其中的 `[[deprecated]]` / `[[nodiscard]]` / `[[maybe_unused]]`，跨编译器零成本。

### C23 标准属性 vs GNU 属性对照表

| C23 标准 | GNU 等价 | 实测支持情况 |
|---|---|---|
| `[[deprecated("msg")]]` | `__attribute__((deprecated("msg")))` | gcc 13.3 在 **`-std=c11` 下也接受**（作为扩展）；gcc 13.3 **不认 `-std=c23`**（要写 `-std=c2x`）|
| `[[nodiscard]]` | `__attribute__((warn_unused_result))` | 同上，实测产生 3 条警告 |
| `[[maybe_unused]]` | `__attribute__((unused))` | 同上 |
| `[[fallthrough]]` | `__attribute__((fallthrough))` | 同上 |
| `[[gnu::packed]]` / `[[gnu::aligned(n)]]` | 同名 GNU 属性 | gcc 13.3 支持（注意[位置](#-位置写错--静默失效实测三种写法)）|
| `[[unsequenced]]` / `[[reproducible]]` | `const` / `pure` | C23 新增，编译器支持尚不完整 |

**结论**：新项目优先用 `[[ ]]` 标准语法（可移植、MSVC 也认几个），只在标准没有对应物时（如 `section`、`cleanup`、`visibility`、`format`）才退回 `__attribute__`。

## 内核 / DPDK 里的封装宏对照

内核从不裸写 `__attribute__`，一律封成短宏。认得这些宏 = 认得属性：

| 内核宏 | 展开 | 用途 |
|---|---|---|
| `__init` | `__attribute__((section(".init.text")))` | 启动后释放 |
| `__exit` | `__attribute__((section(".exit.text")))` | 模块卸载后释放 |
| `__initdata` | `__attribute__((section(".init.data")))` | 启动期数据 |
| `__packed` | `__attribute__((packed))` | 协议头紧凑排布 |
| `__aligned(n)` | `__attribute__((aligned(n)))` | cache 行对齐 |
| `__weak` | `__attribute__((weak))` | 可被覆盖的默认实现 |
| `__maybe_unused` | `__attribute__((unused))` | 抑制条件编译下的未使用警告 |
| `__printf(a, b)` | `__attribute__((format(printf, a, b)))` | 日志函数格式检查 |
| `__must_check` | `__attribute__((warn_unused_result))` | 返回值必须检查 |
| `__noreturn` | `__attribute__((noreturn))` | `panic` / `do_exit` |
| `__alias(name)` | `__attribute__((alias(name)))` | 符号别名 |
| `__visible` | `__attribute__((visibility("default")))` | 显式导出 |
| `__force` | `__attribute__((force))`（sparse 用）| 强制类型转换不被静态检查报 |

DPDK 同构：`__rte_packed`、`__rte_aligned(n)`、`__rte_cache_aligned`、`__rte_always_inline`、`__rte_noinline`、`__rte_format_printf`。

## 坑点清单

属性失效有三类，**都不会导致编译失败**：

| 失效模式 | 例子 | 症状 | 排查手段 |
|---|---|---|---|
| **位置写错** | `struct S {} [[gnu::packed]];` | 属性被忽略，`sizeof` 不变 | 看 `sizeof`；开 `-Wattributes` |
| **索引越界** | `format(printf, 2, 3)` 用在单参函数 | 检查静默消失，调用点零报警 | **`-Wattributes`** 是唯一会报的开关 |
| **被链接器覆盖** | `used` + `--gc-sections` | 编译器保留了 `t kept`，链接器照样 `removing unused section` | 需链接脚本 `KEEP()` |

其余高频坑：

| 坑 | 说明 |
|---|---|
| 不是 C 标准 | MSVC 下语法错误，必须条件编译 |
| 部分属性 Clang 不认 | `optimize` 被**静默忽略**（实测 warning 而已） |
| `packed` 的地址不能外传 | 直接访问成员安全（gcc 生成字节级代码）；把成员地址赋给普通 `int*` 再解引用 → UBSan `store to misaligned address`。要取值用 `memcpy` |
| `pure`/`const`/`noreturn` 撒谎是静默出错 | 与 `always_inline`（做不到直接 error）不同。实测谎称 `noreturn` → **SIGSEGV，退出码 139** |
| `format` 只做编译期检查 | 运行时传错类型照样崩，它管不了 |
| `assume_aligned` 是承诺不是检查 | 标了却返回未对齐地址，不报错，只会在对齐访问时 SIGBUS |

## HFT / 嵌入式关联

| 属性 | 场景 | 注意 |
|---|---|---|
| `visibility("hidden")` | `.so` 内部调用不过 PLT，直接 PC 相对跳转；收窄 ABI | 配合 `-fvisibility=hidden` 全局默认 |
| `hot` / `cold` | 错误处理路径不占热路径 i-cache | 实测会生成 `dispatch.cold`，自动拆冷分支 |
| `packed` | 行情协议头（交易所二进制协议）紧凑排布 | 别把成员地址外传 |
| `aligned(64)` | 每个 worker 的 ring buffer / 计数器独占 cache 行，消除伪共享 | 数组场景要让 `sizeof` 也是 64 的倍数 |
| `always_inline` | 热路径小函数（订单校验） | 做不到会 error，不像 `inline` 静默退化 |
| `cleanup` | 作用域自动释放，替代 `goto cleanup` | 有 `setjmp` 的地方不可靠 |
| `may_alias` | 协议解析 / SIMD 寄存器双视角 | 日常双关优先 `memcpy` |
| `format` | 日志函数必备 | 索引写错会静默失效 |
| **可变参 + `format`** | — | **即便加了 format，HFT 数据面仍不推荐可变参**（实测 4.26× 开销，见 7.6.2） |
| `optimize` | ❌ 不要用 | Clang 静默忽略，且 gcc 下会重置其它优化选项 |

## 完整示例（可直接编译）

```c
/* attr_demo.c: gcc -Wall -Wextra -O2 attr_demo.c -o attr_demo */
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>

/* --- 可移植封装 --- */
#ifdef __GNUC__
#  define FMT(a, b)   __attribute__((format(printf, a, b)))
#  define NORETURN    __attribute__((noreturn))
#  define EXPORT      __attribute__((visibility("default")))
#  define AUTOFREE(f) __attribute__((cleanup(f)))
#else
#  define FMT(a, b)
#  define NORETURN
#  define EXPORT
#  define AUTOFREE(f)
#endif

/* --- 诊断类 --- */
EXPORT void log_msg(const char *fmt, ...) FMT(1, 2);
void log_msg(const char *fmt, ...)
{
    va_list ap; va_start(ap, fmt); vprintf(fmt, ap); va_end(ap);
}

NORETURN void die(const char *msg) { fprintf(stderr, "fatal: %s\n", msg); exit(1); }

/* --- cleanup --- */
static void freep(void *p) { void **pp = p; if (*pp) { free(*pp); *pp = NULL; } }

int main(void)
{
    log_msg("hello %s, %d\n", "world", 42);

    int *buf  AUTOFREE(freep) = malloc(64);
    char *s   AUTOFREE(freep) = malloc(32);
    (void)buf; (void)s;

    if (!buf || !s) die("oom");   /* die 标了 noreturn，后面不需要 else */
    return 0;                      /* 离开 main 自动 free(s) 再 free(buf) */
}
```

（需要 `#include <stdarg.h>` 才能编译，此处略。）

## 代码自测

<details>
<summary>题目 1：下面这份声明有几个问题？逐个指出并给出正确写法</summary>

```c
struct Packet { char type; int len; char payload[8]; } __attribute__((packed));

void handle(const char *fmt, ...) __attribute__((format(printf, 2, 3)));

void must_use(void) __attribute__((warn_unused_result));

__attribute__((noreturn)) int parse(const char *s);
```

**问题 1：`packed` 位置错。** `[[gnu::packed]]` / `__attribute__((packed))` 对 struct 必须写在 `struct` 关键字之后、名字之前：

```c
struct __attribute__((packed)) Packet { char type; int len; char payload[8]; };
```

写在 `}` 之后 gcc 只给 `warning: attribute ignored`，**不拦编译**，`sizeof` 仍是 16 而不是 13。用 `sizeof` 验证是唯一可靠手段。

**问题 2：`format` 索引越界。** `handle` 只有 1 个具名参数，却说格式串在第 2 位：

```
warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1 [-Wattributes]
```

后果是**属性被丢弃、所有调用点不再检查**，实测 `handle("%d", 3.14)` 零报警。正确写法 `format(printf, 1, 2)`。`2,3` 只对 C++ 成员函数（`this` 占第 1 位）或两固定参函数成立。

**问题 3：`warn_unused_result` 用在 `void` 函数上无意义。** 返回值类型是 `void`，没什么可"忽略"的。该属性只对有返回值的函数生效——想表达"必须调用"应该用别的手段（静态分析或 `[[nodiscard]]` 同理）。

**问题 4：`noreturn` 撒谎。** 声明说永不返回，返回类型却是 `int`。若 `parse` 实际会返回，调用方编译器生成的代码会在调用后直接掉进未定义区域——实测谎称 `noreturn` 是 **SIGSEGV、退出码 139**。`noreturn` 函数的返回类型必须是 `void`。

</details>

<details>
<summary>题目 2：以下函数在 -O2 下输出什么？为什么？如何修？</summary>

```c
int f(int *ip, float *fp)
{
    *ip = 1;
    *fp = 2.0f;
    return *ip;
}

float storage = 0.0f;
printf("%d\n", f((int *)&storage, &storage));
```

**输出 `1`**（不是 1073741824）。

按 C11 6.5p7（严格别名），`int*` 与 `float*` 是不同类型，编译器有权假设它们不指向同一对象。于是它认为 `*fp = 2.0f` 不可能改动 `*ip`，优化时省掉了第二次加载，直接返回常量 1。

`-O1` 下实测返回 1073741824（还没做这个优化），`-O2`/`-O3` 返回 1，clang `-O2` 同样返回 1。加 `-fno-strict-aliasing` 后返回 1073741824——**但那是用放弃一类优化换来的**。

三种修法：

| 修法 | 写法 | 评价 |
|---|---|---|
| `may_alias` 类型 | `typedef int __attribute__((may_alias)) int_alias;` 参数改 `int_alias *` | 精准，只在这一个类型上放开别名假设，其余代码照常优化 |
| `memcpy` | 写入/读出都走 `memcpy` | **首选**。合法且小 `memcpy` 会被优化成一条 `mov`，零成本 |
| `-fno-strict-aliasing` | 全局关闭 | 全局性能倒退，只为局部一处不值 |

注意：这段代码在 `-O1` 或 debug 构建下"看起来是对的"——**这正是它危险的地方**，测试通过不代表没有 UB。

</details>

<details>
<summary>题目 3：设计一个资源获取函数，要求「任何返回路径都不泄漏」，并说明 cleanup 相比 goto 的取舍</summary>

```c
static void freep(void *p) { void **pp = p; if (*pp) { free(*pp); *pp = NULL; } }
static void closep(int *fd) { if (*fd >= 0) { close(*fd); *fd = -1; } }

int process(const char *path)
{
    int   fd  __attribute__((cleanup(closep))) = open(path, O_RDONLY);
    char *buf __attribute__((cleanup(freep)))  = malloc(4096);
    if (fd < 0 || !buf) return -1;          /* 提前 return 也清理 */

    ssize_t n = read(fd, buf, 4096);
    if (n <= 0) return -2;                  /* 第二个提前 return */

    if (buf[0] == '#') return -3;           /* 第三个 */

    process_data(buf, n);
    return 0;                               /* 正常路径也清理 */
}
```

**cleanup 的优势**

- **提前 return 不漏**：实测 `early(-5)` 的 `return -1` 照样触发清理函数。`goto cleanup` 模式每加一个 return 就要加一次跳转，最容易漏。
- 清理逻辑与声明写在一起，读代码时"这个变量怎么释放"就在眼前。
- 顺序**逆序 LIFO**（后声明的先清理），与 C++ 析构一致，天然满足"后获取的先释放"。

**取舍（什么时候仍该用 goto）**

| 场景 | 原因 |
|---|---|
| 代码里有 `setjmp`/`longjmp` | GNU 文档明示 `cleanup` 在 `longjmp` 跳出作用域时**不保证**触发 |
| 清理顺序需要非 LIFO | `cleanup` 固定逆序，goto 可以任意安排 |
| 需要跨函数/跨模块统一的错误处理 | `cleanup` 是编译期绑定，不好做运行时策略 |
| 要支持 MSVC | `cleanup` 是 GNU 扩展，MSVC 无对应物，goto 到处都能用 |

**结论**：Linux 内核与 GNU 系项目可以放心用 `cleanup`（它已是 glibc/gcc 生态的事实标准）；需要跨 MSVC 或对 `setjmp` 有依赖的代码，`goto cleanup` 仍是更稳的选择。

</details>

<details>
<summary>题目 4：为什么 .so 工程要全局 -fvisibility=hidden？给出四条实测支撑的理由</summary>

实测对照（同一个 `vis_lib.c`）：

```
默认：            nm -D → public_add, prot_add, entry   （hidden_add 不在）
-fvisibility=hidden: nm -D → 只剩 prot_add
```

四条理由：

1. **ABI 收窄**：默认可见性下，**每一个**非 `static` 函数都进入 `.dynsym`，等于向外界承诺"这些符号永远存在"。实测 `hidden_add` 标了 `hidden` 后从 `nm -D` 里消失（`readelf` 显示被降级为 `LOCAL`），不再是对外承诺。想改内部函数时不必担心破坏调用方。

2. **加载更快**：动态符号表小了，符号解析的 hash 查找次数下降。对有大量符号的库（如 DPDK、OpenSSL）这是可测量的启动收益。

3. **调用更快（HFT 最关心的一条）**：`hidden` 可见性的调用**不经过 PLT**，编译器直接生成 PC 相对跳转。默认可见性下，为了允许 LD_PRELOAD 抢占，每次跨模块调用都要走 PLT + GOT 间接跳转。热路径上这是实打实的分支与额外访存。

4. **防抢占**：`protected` 一档更进一步——它在 `.dynsym` 里（外部可引用），但**本模块内的引用绑死到本地定义**，不会被 LD_PRELOAD 的同名符号截获。实测 `-fvisibility=hidden` 后 `prot_add` 仍在 `.dynsym`，正是因为它显式声明了 `protected`。

**推荐写法**：

```bash
gcc -shared -fPIC -fvisibility=hidden -o libfoo.so *.c
```

#define EXPORT __attribute__((visibility("default")))
