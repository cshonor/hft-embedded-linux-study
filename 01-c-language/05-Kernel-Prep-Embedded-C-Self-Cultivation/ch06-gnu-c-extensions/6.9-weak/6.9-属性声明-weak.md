## 本节讲什么

`weak` 是**唯一一个语义完全发生在链接期**的 GNU C 属性。前面 6.3–6.7 的属性（`typeof`、语句表达式、柔性数组、`aligned`/`packed`）都作用于**编译期**——影响类型、代码生成或布局；`weak` 编译期什么都不做，它只往目标文件的符号表里写一个标记，剩下的交给链接器。

一句话概括：

> **同名符号有多个定义时，强的吃掉弱的；全是弱的，先到先得；只有弱声明没有定义，符号等于 NULL。**

它的价值在嵌入式和内核里无可替代——**一份内核镜像适配多块板子**，靠的就是 `weak`：

```c
/* core.c —— 框架代码，不认识任何具体板子 */
void __weak board_early_init(void) { }
int  __weak board_id(void)         { return -1; }

/* board_a.c —— 换块板子只需换一个 .o */
void board_early_init(void) { /* A 板专属时序 */ }
int  board_id(void)         { return 0xA1; }
```

框架代码里没有一行 `#ifdef`，调用点干干净净，换板子不重新编译主体。

本节把 weak 的**规则、代价、以及五个会静默出错的坑**全部用实测钉死。

## 一、先认清符号的"强弱"：`nm` 怎么读

所有 weak 问题最终都要回到符号表。先建立读 `nm` 的能力：

```c
/* types.c */
int  strong_data = 1;                       /* 已初始化强数据 */
int  strong_bss;                            /* 未初始化强数据 */
int  __attribute__((weak)) weak_data = 2;
int  __attribute__((weak)) weak_bss;
void strong_fn(void) {}
void __attribute__((weak)) weak_fn(void) {}
```

```
$ gcc -std=gnu11 -c types.c && nm types.o
0000000000000008 V ext_undef
0000000000000000 B strong_bss      <- B: 强 · 未初始化（bss）
0000000000000000 D strong_data     <- D: 强 · 已初始化（data）
0000000000000000 T strong_fn       <- T: 强 · 代码
0000000000000004 V weak_bss        <- V: 弱 · 对象（变量）
0000000000000004 V weak_data       <- V: 弱 · 对象（变量）
000000000000000b W weak_fn         <- W: 弱 · 函数
```

| 类型字母 | 含义 | 记忆法 |
|----------|------|--------|
| `T` / `t` | 强符号，代码段 | **T**ext |
| `D` / `d` | 强符号，已初始化数据 | **D**ata |
| `B` / `b` | 强符号，未初始化数据 | **B**ss |
| `C` | **common 符号**（未初始化的"试探性定义"，见第五节） | **C**ommon |
| `W` / `w` | **弱符号**，函数 | **W**eak |
| `V` / `v` | **弱符号**，对象（变量） | 排在 W 前面的 **V** |
| `U` | 未定义（本 TU 只引用） | **U**ndefined |

> **大写 = 外部链接，小写 = 局部（static）**。所以 `static + weak` 是自相矛盾——见第八节，那是**硬错误**。

**排查 weak 问题的第一步永远是 `nm`**：你以为的覆盖没生效，八成是那个符号压根不是 `W`/`V`，或者压根没进链接（见第四节静态库坑）。

## 二、强弱决议规则（实测矩阵）

### 2.1 规则表

| # | 情形 | 结果 | 实测 |
|---|------|------|------|
| 1 | **同一 TU** 内两个强定义 | **编译期 error**：`redefinition of 'g'` | ✅ |
| 2 | **跨 TU** 两个强定义 | **链接期 error**：`multiple definition of 'x'` | ✅ |
| 3 | 一强 + 一弱 | **强胜**，与链接顺序无关 | ✅ |
| 4 | 两弱 | **先出现者胜**，与链接顺序**有关** | ✅ |
| 5 | 只有弱**声明**（无定义） | 链接通过，符号地址 = `NULL` | ✅ |
| 6 | 只有强/弱声明且**无任何定义** | 强 → `undefined reference`；弱 → 通过 | ✅ |

### 2.2 实测数据（W2）

```c
/* wa.c */                          /* wb.c */
int sym_a __attribute__((weak)) = 111;
int sym_b __attribute__((weak)) = 222;   int sym_b = 2222;
int sym_c = 333;                         int sym_c __attribute__((weak)) = 3333;
int sym_d __attribute__((weak)) = 444;   int sym_d __attribute__((weak)) = 4444;
```

```
--- 链接顺序 wa.o 然后 wb.o ---
a(only weak)   = 111      <- 只有弱定义，用它
b(weak+strong) = 2222     <- 强胜
c(strong+weak) = 333      <- 强胜（顺序反过来也一样）
d(weak+weak)   = 444      <- 两弱：先出现者胜

--- 链接顺序 wb.o 然后 wa.o ---
a(only weak)   = 111
b(weak+strong) = 2222     <- 强胜，不受顺序影响
c(strong+weak) = 333      <- 强胜，不受顺序影响
d(weak+weak)   = 4444     <- 两弱：变成 wb 胜！

$ nm wa.o | grep sym_
0000000000000000 V sym_a     0000000000000004 V sym_b
0000000000000008 D sym_c     000000000000000c V sym_d
$ nm wb.o | grep sym_
0000000000000000 D sym_b     0000000000000004 V sym_c
0000000000000008 V sym_d
```

> ⚠️ **"两弱取第一个"是链接顺序依赖的**，而链接顺序在 Makefile 里往往是不稳定的（尤其用了 `wildcard` 或 `$(sort)`）。**同一符号在两处都用 weak 定义 = 埋雷**。正确做法是：默认实现标 weak，**覆盖方一律不标**（自动成强）。

**clang 18 行为一致**（实测 `cw1 first: w=1` / `cw2 first: w=2`）。

## 三、weak 声明但不定义：可选 hook

### 3.1 基本用法

```c
/* 只有声明，没有定义。没有 weak 会 undefined reference */
void __attribute__((weak)) optional_hook(void);

int main(void)
{
    if (optional_hook)          /* 必须判空！ */
        optional_hook();
    return 0;
}
```

```
--- 带 weak ---
link exit=0
optional_hook addr = (nil)
hook absent -> skipped safely

--- 去掉 weak（对照）---
link exit=1
undefined reference to `optional_hook'

--- 不判空直接调用 ---
Segmentation fault (core dumped)      run exit=139
```

这是 **SDK 的"可选功能"**标准写法：厂商库里声明一堆 hook，集成方按需实现，没实现的自动跳过。**不判空 = 空指针跳飞**。

### 3.2 但是：`if (hook)` 可能被优化掉

这是本节最反直觉的一条。看这两份代码在 `-O2` 下的差别：

```c
/* same.c —— weak 定义就在本 TU */        /* decl.c —— 本 TU 只有声明 */
int __weak hook(void) { return 1; }       int __weak hook(void);
int main(void){                           int main(void){
    if (hook) hook();                         if (hook) hook();
}                                         }
```

```
--- same.c -O2 的 main ---
   ...  call  ...     <- 没有 test / je！判空被删掉了

--- decl.c -O2 的 main ---
   10:  74 21   je     33 <main+0x33>     <- test + je 保留
```

**原因**：`same.c` 里 `hook` 有定义，编译器能证明它的地址非 NULL，于是 `if (hook)` 恒真，判定被删。`decl.c` 里编译器看不到定义，不敢删。

**这不影响正确性**（不是 NULL 就调用默认实现），但它说明一件事：

> **"用判空支持可选 hook"这个模式，前提是默认实现不能出现在调用点所在的 TU。**
> 一旦你把默认实现和 `if (hook)` 写进同一个 `.c`，语义就悄悄从"可选"退化成"总是存在"——而 strong 覆盖仍然生效，所以你不会发现。

**推荐写法**：默认实现放库里，调用点在业务代码里（天然不同 TU）。或者干脆**不提供定义、只声明**，让"未实现"真正可观测。

## 四、头号坑：weak **不会**触发静态库成员提取

这条坑死过无数人，也是最值得记住的一条。

| 链接方式 | 库里的 strong 生效吗 | 实测 `hook()` |
|----------|---------------------|---------------|
| A. main 有 weak 定义 + `libonly.a`（成员只含 `hook`） | ❌ | **0**（weak 胜） |
| B. main 有 weak 定义 + `libboth.a`（成员含 `hook` + `other`，`other` 未引用） | ❌ | **0** |
| C. 同 B，但业务代码引用了 `other`（成员被拉入） | ✅ | **42**（strong 胜） |
| D. main 只有 weak **声明** + `libonly.a` | ❌ | **`hook addr=(nil)`** |
| E. 同 D，加 `-Wl,--whole-archive` | ✅ | **42** |
| F. main 有 weak 定义 + 直接给 `hook.o`（不是 `.a`） | ✅ | **42** |

**机制**：链接器处理静态库时，**只有当某个未定义符号需要被解析时，才把定义它的成员拉进来**。而 weak 符号——

- 如果它**有定义**（A/B）：符号已解析，链接器根本不看库。
- 如果它**只有声明**、没有定义（D）：链接器认为"未定义的 weak 符号不需要解析"——这是 ELF 的规定——**同样不拉库**，于是符号留在 NULL。

所以 D 是最惨的：**你写了 hook，库里也有实现，结果程序跑起来发现 hook 是 NULL，静默跳过**。

### 解法

```bash
# 1) 强制拉入整个库
gcc main.o -Wl,--whole-archive libfoo.a -Wl,--no-whole-archive

# 2) 直接链 .o 而不是 .a（F 的做法）
gcc main.o hook.o

# 3) 让弱引用变成强引用：另有一个强引用的符号在该成员里（C 的做法）
```

> **工程建议**：用 weak + 静态库做插件架构时，**必须**在构建脚本里显式 `--whole-archive`，并且加一条启动自检：`if (!hook) log_warn("hook not linked");`。否则"忘了拉进来"会以"功能静默缺失"的形式出现，极难排查。

## 五、common 符号与 `-fno-common`（gcc 10 起的行为变化）

未初始化的全局变量 `int x;`（不带 `extern`、不带 `weak`）在 C 里叫**试探性定义（tentative definition）**。传统上它被编译成 **common 符号**，多个 TU 各写一个 `int x;` 是允许的，链接期合并。

**gcc 10 起默认 `-fno-common`**，这条老规则变了：

```
--- 默认（gcc 13 = -fno-common）：两个 TU 都有 int x; ---
exit=1
/usr/bin/ld: multiple definition of `x'; first defined here

--- 加 -fcommon ---
exit=0
x=0

--- 一个 int x=99(强) + 一个 int x;(common) ---
x=99            <- 强胜 common，与顺序无关

$ nm：
-fcommon     -> 0000000000000004 C x     <- common
-fno-common  -> 0000000000000000 B x     <- 变成强符号！
```

| 写法 | gcc 13 默认 | `-fcommon` |
|------|------------|-----------|
| `int x;`（试探性定义） | `B`（强）→ 两处就冲突 | `C`（common）→ 合并 |
| `int x = 0;` | `D`（强） | `D`（强） |
| `int __weak x;` | `V`（弱，**不是 common**） | `V` |

> 注意 `int __attribute__((weak)) x;` **不是 common，是 V**。所以它既能和别处的 strong 共存（被覆盖），又不受 `-fno-common` 影响（实测两种顺序都是 `cfg=5`）。

**实践**：老代码（gcc ≤ 9 时代）里满地的 `int x;` 在 gcc 10+ 会突然报 multiple definition。修复方式三选一：加 `-fcommon`（掩盖）、改成 `extern` 声明 + 单一定义（正确）、或者给默认定义加 `weak`（本节的方案）。

## 六、动态链接：全局符号介入、`-Bsymbolic`、`LD_PRELOAD`

### 6.1 可执行文件的符号优先级最高

```
libw.c:  int __attribute__((weak)) f(void) { return 1; }
         int call_f(void) { return f(); }        <- 库内部调用 f

main_strong.c:  int f(void) { return 100; }      <- 可执行文件 strong

--- 运行结果 ---
main f()=100
  lib call_f -> f()=100        <- 库内部的 f 也变成了 100！
```

**这就是"全局符号介入（global symbol interposition）"**：ELF 的符号查找顺序是 **可执行文件 → 预加载库 → 其他共享库**。所以共享库内部的调用**会被可执行文件的同名符号截胡**。

后果：你的 `.so` 里那个 weak 默认实现，对可执行文件的 strong 版本毫无抵抗力——连库内部调用都会被带走。

### 6.2 `-Bsymbolic` 锁死库内部绑定

```
--- 同一个 so 用 -Wl,-Bsymbolic 编译 ---
main f()=100
  lib call_f -> f()=1          <- 库用自己的 weak 实现了
```

`-Bsymbolic` 让库内部引用**优先绑定到自己的定义**，不再被外部介入。代价：库之间无法互相覆盖（失去 LD_PRELOAD 的一部分能力）。变种 `-Bsymbolic-functions` 只对函数生效，保留数据介入能力。

> **什么时候需要**：发布 SDK/中间件 `.so`，且内部有同名符号不希望被用户的可执行文件劫持时。发布给第三方的库，建议加。

### 6.3 `LD_PRELOAD` 覆盖不了可执行文件自己的符号

```
--- 可执行文件不定义 impl，只用 liba.so（impl=10）---
impl()=10
--- LD_PRELOAD=libb.so（impl=555）---
impl()=555                     <- 生效

--- 可执行文件自己定义了 impl=777 ---
no preload:  impl()=777
with preload: impl()=777       <- 无效！
```

**结论**：`LD_PRELOAD` 只能覆盖**库与库之间**的符号竞争，**覆盖不了可执行文件自己定义的符号**（因为可执行文件在查找顺序的最前面）。

这条在调试时极容易误判：你 `LD_PRELOAD` 了一个 mock，`main` 里的调用却还是真的——因为被测函数就定义在可执行文件里。解法：把被测函数挪进 `.so`，或用 `-Wl,--wrap=symbol`。

## 七、weak 的真实性能代价：3.2 倍

`weak` 不是免费的。因为编译器必须保留"链接期可能被替换"的能力，**weak 函数永远不会被内联**。

```c
volatile int sink;
int __attribute__((weak)) addw(int x) { return x + 1; }   /* weak   */
int adds(int x)                       { return x + 1; }   /* strong */
static int addi(int x)                { return x + 1; }   /* static */

for (int i = 0; i < 200000000; i++) sink = addw(i);   /* 2 亿次 */
```

```
--- gcc -O2 ---
weak   (not inlined) 0.131451 s
strong (inlined)     0.040835 s
static (inlined)     0.047370 s
                     -> weak 慢 3.2 倍
```

反汇编坐实了原因：

```
weak   循环体:  10c5:  call  1300 <addw>        <- 真实函数调用，2 亿次
strong 循环体:  1110:  lea   0x1(%rax),%edx     <- 内联 + 2 路展开
                1113:  add   $0x2,%eax
```

代码生成层面的对比（同一 TU、`-O2`）：

| 被调用函数 | `use()` 的反汇编 | 内联了吗 |
|-----------|-----------------|---------|
| `strong`（`T`） | `lea 0x1(%rdi),%eax; ret` | ✅ 甚至常量折叠 |
| `static` | `lea 0x1(%rdi),%eax; ret` | ✅ |
| **`weak`（`W`）** | `jmp <use+0x9>`（尾调用） | ❌ **永远不会** |

**而且声明带不带 weak 都一样**（实测 t1/t2 都是 `jmp`）——只要定义体上有 `__attribute__((weak))`，符号就是 `W`，编译器就不内联。

> **工程结论**：weak 适合**冷路径**——板级初始化、可选 hook、错误处理、测试替身。**热路径上不要用 weak**（行情处理循环、DMA 回调、ISR）。需要"可替换 + 高性能"时，用**函数指针 + 显式注册**，或者编译期 `#ifdef` + 内联。

## 八、`static + weak` 是硬错误（不是警告）

```c
static void __attribute__((weak)) sf(void) { }
```

```
gcc:   error: weak declaration of 'sf' must be public
clang: error: weak declaration cannot have internal linkage
```

两个编译器都是 **error**，直接编不过。理由很直白：`weak` 是给链接器的指令，而 `static` 符号链接器根本看不见。

**推论**：任何"链接期可替换"的诉求，符号必须有**外部链接**。所以：

| 写法 | 能否被覆盖 | 备注 |
|------|-----------|------|
| `void f(void) {}` + 调用方 | ❌（强，无法替换） | 默认 |
| `__weak void f(void) {}` | ✅ | 本节主角 |
| `static inline void f(void) {}` | ❌ **内联展开，weak 无从谈起** | 头文件小函数 |
| `static __weak ...` | ❌ **编译错误** | — |
| `inline __weak void f(void) {}` | ⚠️ 属性生效但语义混乱 | 见下 |

关于 `inline`：`inline` 要求编译期展开，`weak` 要求链接期替换，**语义对立**。如果同时写，实测 gcc 仍然生成 `jmp`（weak 优先），但代码让读者困惑。**别这么写**。

## 九、alias：给符号起别名

### 9.1 语法与铁律

```c
void impl(void) { puts("impl"); }
void pub(void) __attribute__((alias("impl")));   /* pub 与 impl 同一地址 */
```

**铁律（实测）**：

| 规则 | 违反后果 |
|------|---------|
| 目标必须在**同一 TU 且已定义** | `error: 'pub' aliased to undefined symbol 'target'` |
| 目标可以是 `static`（同 TU 内可见即可） | ✅ 实测 gcc/clang 都通过并正确执行 |
| 支持**链式** alias（a→b→c） | ✅ 实测 `a_alias()` 调到 `c_impl` |

```c
/* 实测：alias 到 static 是允许的 */
static void impl_static(void) { printf("  static impl\n"); }
void pub_static(void) __attribute__((alias("impl_static")));
-> exit=0，正确打印 "static impl"

/* 跨 TU alias：编译期就报错 */
extern void target(void);
void pub(void) __attribute__((alias("target")));
-> error: 'pub' aliased to undefined symbol 'target'
```

> 注意"跨 TU"报错发生在**编译期**，因为 gcc 在本 TU 找不到 `target` 的定义。这和 weak 的链接期语义完全不同。

### 9.2 `alias` + `weak`：一组符号共享默认实现

```c
static void default_log(int lvl, const char *msg) { fprintf(stderr, "[%d] %s\n", lvl, msg); }

void log_info(int lvl, const char *msg) __attribute__((weak, alias("default_log")));
void log_warn(int lvl, const char *msg) __attribute__((weak, alias("default_log")));
void log_err (int lvl, const char *msg) __attribute__((weak, alias("default_log")));
```

实测：

```
--- 无覆盖 ---
al:  impl
--- 另一 TU 提供 strong al ---
al:  STRONG al          <- 成功覆盖，其他 alias 不受影响
```

三个符号默认指向同一个实现，用户可以**只覆盖其中一个**。内核 `printk` 体系、glibc 的 `__libc_*` 别名都靠这个模式。

## 十、其他实测边界

### 10.1 头文件里放 weak 定义：合法但危险

```c
/* hdr.h —— 非 static 的函数定义直接放头文件 */
int __attribute__((weak)) hw(void) { return 3; }
```

```
--- 不加 weak（对照）---
multiple definition of `hw'          <- 链接错误

--- 加 weak ---
exit=0，hw()=3                        <- 两个 TU 各有一份 weak 定义，取第一个

--- 再加一个 TU 提供 strong ---
hw()=33                               <- 强胜，链接顺序不影响
```

**能编过，但别这么用**：每个包含该头文件的 TU 都会生成一份代码（体积膨胀），而且"取第一个"依赖链接顺序。头文件里放函数定义的正确姿势是 `static inline`。

### 10.2 `-z muldefs`：让两个强符号共存

```
--- 默认 ---
multiple definition of `dup'
--- -Wl,-z,muldefs ---
dup=1          <- 取第一个
--- 反序 ---
dup=2
```

等价于把强符号降级成"取第一个"。**仅在救急时用**（比如合并两个第三方库），日常代码里这是掩盖 bug。

### 10.3 `--gc-sections` 会回收没人引用的 weak stub

```
--- 不加 ---   0000000000001163 T keeper   0000000000001149 W unused_stub
--- 加 ---     0000000000001149 T keeper      （unused_stub 消失）
```

需要配合 `-ffunction-sections -fdata-sections`。**对嵌入式很有用**：一堆板级 stub 里没用到的自动被裁掉。

### 10.4 声明与定义的 weak 标记不必一致

```c
/* inc_a.c */
int __attribute__((weak)) g(void);   /* 声明带 weak */
int g(void) { return 1; }            /* 定义不带 */
-> nm: 0000000000000000 W g           <- 仍然是弱！strong 覆盖生效 g()=999

/* inc_d.c */
int __attribute__((weak)) h2(void) { return 7; }   /* 定义带 weak */
/* inc_m.c */
int h2(void);                                       /* 声明不带 */
-> h2()=777                                          <- strong 覆盖仍生效
```

**结论**：只要符号最终是 `W`/`V`，覆盖就生效，调用方看不看得到 weak 标记无所谓。但**声明不带 weak 会让读者误以为它不可替换**——写进去，为了可读性。

### 10.5 LTO **不会**破坏 weak 覆盖（证伪一条传言）

常见说法："`-flto` 跨模块优化会看穿 weak，直接内联默认实现，绕过 strong 覆盖。"

```
--- gcc -O0 ---            f()=100
--- gcc -O2 ---            f()=100
--- gcc -O2 -flto ---      f()=100     <- 覆盖仍生效
--- clang -O2 -flto ---    f()=100     <- 覆盖仍生效
```

**在 gcc 13.3 / clang 18.1.3 上未复现**。LTO 保留了 weak 语义（这也解释了为什么第七节里 weak 永远不内联——LTO 也救不回来，代价是实打实的）。

> 老版本 gcc（≈4.x–7.x）确实有过相关问题。现在的工具链是安全的，但**如果项目跨多版本编译器，weak + LTO 仍建议加一条集成测试**。

## 十一、实战：内核风格 BSP hook（完整可运行）

```c
/* bsp.h */
void board_early_init(void);
void board_late_init(void);
int  board_id(void);

/* core.c —— 框架代码，零 #ifdef */
#define __weak __attribute__((weak))
void __weak board_early_init(void) { puts("  [core] default early init"); }
void __weak board_late_init(void)  { puts("  [core] default late init");  }
int  __weak board_id(void)         { return -1; }

int main(void){
    puts("boot:");
    board_early_init();
    printf("  board_id=%d\n", board_id());
    board_late_init();
    return 0;
}

/* board_a.c */
void board_early_init(void) { puts("  [board A] early init"); }
int  board_id(void)         { return 0xA1; }
```

```
--- 只有 core.c ---
boot:
  [core] default early init
  board_id=-1
  [core] default late init

--- core + board_a ---
boot:
  [board A] early init        <- 被覆盖
  board_id=161                <- 0xA1 = 161，被覆盖
  [core] default late init    <- 未提供，走默认

$ nm core.o | grep board_
0000000000000000 W board_early_init
000000000000001a W board_late_init
0000000000000034 W board_id
```

### 但注意它的硬限制

```
--- core + board_a + board_b（两块板子都提供 board_id）---
multiple definition of `board_id'
```

**weak 只能被一个 strong 覆盖**。所以"一份镜像支持多板"靠的是**链接时只链一个板级 `.o`**，不是把全世界的板级文件都链进去。构建系统必须保证：

```
obj-y += core.o
obj-y += board_$(BOARD).o        <- 一次只有一个
```

## 十二、检查清单

| # | 检查项 | 为什么 |
|---|--------|--------|
| 1 | 覆盖方**不要**写 `weak` | 两弱取第一个，依赖链接顺序 = 埋雷 |
| 2 | 可选 hook 调用前**必须判空** | 不判空 = 空指针跳飞（实测 segfault 139） |
| 3 | 判空默认实现**不要**和调用点同 TU | 否则 `if (hook)` 被优化掉，语义悄悄改变 |
| 4 | weak + 静态库 → **必须 `--whole-archive`** | 否则库里的实现根本不进链接，hook 静默为 NULL |
| 5 | 热路径**不要**用 weak | 永不内联，实测慢 3.2 倍 |
| 6 | `static` + `weak` 是 error | 想要可替换就必须外部链接 |
| 7 | 发布第三方 `.so` 考虑 `-Bsymbolic` | 否则内部调用会被可执行文件的同名符号劫持 |
| 8 | `LD_PRELOAD` 覆盖不了可执行文件自己的符号 | 调试 mock 失效时先查这个 |
| 9 | `alias` 目标必须同 TU 已定义 | 跨 TU 是编译期 error |
| 10 | 老代码 `int x;` 在 gcc 10+ 变强符号 | `-fno-common`，两处定义直接冲突 |
| 11 | 起手式永远是 `nm` | 先看符号是不是 `W`/`V`，再看有没有进链接 |

## 十三、与 `#ifdef` 的取舍

| 维度 | `#ifdef` | `weak` |
|------|----------|--------|
| 决策时机 | 编译期 | **链接期** |
| 换实现 | 重新编译 | 换 `.o` 即可 |
| 调用点 | 可能被宏污染 | 干净 |
| 运行时开销 | 零（可内联） | **不可内联，3.2×（实测）** |
| 未实现时 | 编译不过 | 静默为 NULL（需判空） |
| 适用 | 编译期确定的差异（`CONFIG_SMP`、架构差异） | 链接期可替换（BSP hook、可选 feature、单测替身） |

**判据**：**差异在编译时就知道 → `#ifdef`；差异要等到链接/部署时才知道 → `weak`。**

## 代码自测

<details>
<summary><strong>题目 1：</strong>两个 TU 都写了 <code>int __attribute__((weak)) cfg = 1;</code> 和 <code>= 2;</code>，链接后值是多少？取决于什么？</summary>

取决于**链接顺序**：**先出现者胜**。

实测：
```
cw1.o 在前 -> w=1
cw2.o 在前 -> w=2
```

这与"一强一弱"完全不同——强符号无论顺序都胜。所以工程上**绝对不要**让同一符号在两处都是 weak 定义；默认实现标 weak，覆盖方不标。

</details>

<details>
<summary><strong>题目 2：</strong>库里用 <code>__weak</code> 提供了默认 <code>hook()</code>，主程序在另一个 <code>.c</code> 里实现了 strong 版，但库是 <code>.a</code> 静态库。运行发现走的还是默认实现，为什么？</summary>

**weak 定义已经满足了符号解析，链接器不会去静态库里提取成员。**

实测六种组合：
```
A. main 有 weak 定义 + 库成员只含 hook        -> hook()=0    （默认）
B. 库成员含 hook+other，other 未引用          -> hook()=0    （默认）
C. 业务代码引用了 other，成员被拉入           -> hook()=42   （strong）
D. main 只有 weak 声明 + 库                   -> addr=(nil)  （NULL！）
E. D + --whole-archive                        -> hook()=42
F. main 有 weak 定义 + 直接链 .o              -> hook()=42
```

解法：`-Wl,--whole-archive`（推荐，配合启动自检 `if (!hook) warn()`）、直接链 `.o`、或让成员里有别的符号被强引用。

</details>

<details>
<summary><strong>题目 3（判断）：</strong><code>LD_PRELOAD</code> 是万能的符号替换手段，连可执行文件自己定义的函数也能替换。</summary>

**错。**

```
可执行文件不定义 impl，只用 liba.so(10)  -> 10
LD_PRELOAD=libb.so(555)                  -> 555   <- 生效
可执行文件自己定义 impl=777              -> 777
+ LD_PRELOAD=libb.so(555)                -> 777   <- 无效
```

ELF 符号查找顺序：**可执行文件 → LD_PRELOAD 库 → 其他共享库**。可执行文件排在最前，所以 PRELOAD 只能覆盖**库与库之间**的竞争。

调试时 mock 不生效，先确认被测符号是不是就定义在可执行文件里。

</details>

<details>
<summary><strong>题目 4：</strong>为什么共享库内部的调用也会被可执行文件的同名符号劫持？怎么阻止？</summary>

这是 **ELF 全局符号介入（interposition）**：

```
libw.c:  __weak int f(void){return 1;}   int call_f(void){return f();}
main:    int f(void){return 100;}

输出：main f()=100    lib call_f -> f()=100      <- 库内部也被带走
```

**用 `-Wl,-Bsymbolic` 编译共享库**：

```
main f()=100    lib call_f -> f()=1              <- 库用自己的
```

`-Bsymbolic` 让库内部引用优先绑定自身定义。变种 `-Bsymbolic-functions` 只锁函数、保留数据介入。代价：失去部分 LD_PRELOAD 覆盖能力。发布给第三方的库建议加。

</details>

<details>
<summary><strong>题目 5：</strong><code>static void __attribute__((weak)) f(void) {}</code> 能通过编译吗？</summary>

**不能，两个编译器都是 error：**

```
gcc:   error: weak declaration of 'f' must be public
clang: error: weak declaration cannot have internal linkage
```

`weak` 是给链接器的指令，`static` 的符号链接器看不见，语义自相矛盾。想要"链接期可替换"，符号必须有外部链接。

</details>

<details>
<summary><strong>题目 6：</strong>热路径上有个函数调用 2 亿次，标了 weak 之后慢了多少？为什么？</summary>

**慢 3.2 倍**（实测 0.131 s vs 0.041 s）。

反汇编：
```
weak   循环体:  call  1300 <addw>          <- 2 亿次真实调用
strong 循环体:  lea   0x1(%rax),%edx       <- 内联 + 2 路展开
                add   $0x2,%eax
```

**weak 函数永远不会被内联**——编译器必须保留"链接期可能被替换"的可能。而且**声明带不带 weak 都一样**，只要定义体上有 `__attribute__((weak))`，符号就是 `W`。

所以：weak 用于冷路径（初始化、错误处理、可选 hook、测试替身）；热路径用 `static inline` 或函数指针显式注册。

</details>

<details>
<summary><strong>题目 7：</strong>老项目升级 gcc 后，多个 <code>.c</code> 里都有的 <code>int x;</code> 突然报 multiple definition，为什么？三种修法？</summary>

**gcc 10 起默认 `-fno-common`**，`int x;`（试探性定义）从 common 符号（`C`）变成强符号（`B`），两处就冲突。

```
默认(-fno-common):  multiple definition of `x'
-fcommon:           x=0
$ nm:  -fcommon -> C x      -fno-common -> B x
```

三种修法：
1. `-fcommon` —— 掩盖，回退到老行为（最快，不推荐）
2. **`extern int x;` + 单一定义** —— 正确做法
3. **默认定义加 `__attribute__((weak))`** —— 本节的方案，符号变 `V`，既不与 strong 冲突，又能被覆盖（实测两种链接顺序都被 `cfg=5` 覆盖）

注意 `int __weak x;` 是 `V` 不是 `C`，不受 `-fno-common` 影响。

</details>

<details>
<summary><strong>题目 8（应用）：</strong>用 weak + alias 写一组日志函数，默认全部转发到 <code>default_log</code>，允许只覆盖 <code>log_err</code>。</summary>

```c
/* log_default.c */
#include <stdio.h>
static void default_log(int lvl, const char *msg) {
    fprintf(stderr, "[%d] %s\n", lvl, msg);
}
void log_info(int lvl, const char *msg) __attribute__((weak, alias("default_log")));
void log_warn(int lvl, const char *msg) __attribute__((weak, alias("default_log")));
void log_err (int lvl, const char *msg) __attribute__((weak, alias("default_log")));
```
```c
/* app.c —— 只覆盖 log_err，不写 weak = 强 */
#include <stdio.h>
void log_err(int lvl, const char *msg) {
    fprintf(stderr, "ERROR: %s\n", msg);
    notify_ops_team(msg);
}
```

实测：
```
无覆盖:  al: impl
有覆盖:  al: STRONG al        <- 只替换这一个，其他仍走 alias
```

要点：
- `alias` 目标**必须同 TU 已定义**（可以是 `static`；跨 TU 是编译期 error `aliased to undefined symbol`）
- 支持链式 alias（a→b→c 实测通过）
- `weak` 允许单独覆盖某个别名，其他不受影响
- 覆盖方**不写 weak**

</details>
