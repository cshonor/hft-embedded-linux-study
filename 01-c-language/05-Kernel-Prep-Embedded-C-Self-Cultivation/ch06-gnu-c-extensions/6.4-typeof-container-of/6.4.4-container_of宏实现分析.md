# 6.4.4 container_of宏实现分析

## 本节讲什么

逐步展开 **container_of** 的指针运算与类型转换，理解为何用 **`char *`** 做字节级减法、**`offsetof`** 如何取得成员偏移，以及内核版本中的 **const 检查** trick。

## 要点

### 布局

```
struct task 首地址 ──► [ id | name[16] | link | ... ]
                              ▲
                              └── ptr 指向 link
offset = offsetof(struct task, link)
task_addr = (char *)ptr - offset
```

```c
/* 标准 C 版（无 typeof） */
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

```c
/* 内核加强：const 成员指针检查（思路） */
#define container_of(ptr, type, member) ({                      \
    void *__mptr = (void *)(ptr);                               \
    static_assert(__builtin_types_compatible_p(                 \
        typeof(((type *)0)->member), typeof(*(ptr))),           \
        "pointer mismatch");                                   \
    ((type *)((char *)__mptr - offsetof(type, member)));       \
})
```

| 步骤 | 说明 |
|------|------|
| `(void *)(ptr)` | 抹除 const 便于中间变量（内核有 const 版本宏） |
| `(char *)` 减法 | 按 **字节** 回退，与对齐无关 |
| 转 `(type *)` | 得到结构体首址 |

```c
/* 错误用法 */
struct task *bad = container_of(NULL, struct task, link);  /* UB */
```

- **`list_entry`** = `container_of` 别名
- DPDK `RTE_CONTAINER` 宏（若存在）同理，读源码时对照 **demo** 与 **rte_ring** 结构

## 常见陷阱

1. **`offsetof` 不能用在位域上 → 编译错误**
   `offsetof(type, member)` 要求 `member` 是普通成员，不能是位域。如果结构体含位域且想取位域指针，**根本拿不到指针**——位域不允许 `&`。误用 `offsetof` 会在编译期报错，但写代码时容易忘。

2. **`__builtin_types_compatible_p` 检查可能误判**
   内核加强版用 `typeof(((type *)0)->member)` 与 `typeof(*(ptr))` 比对。但若 `ptr` 本身是 `const` 限定（如 `const struct list_node *`），而 `member` 在结构体内不是 const，类型不匹配会**静态断言失败**。内核为此有 `container_of_const` 包装。用户态移植要小心 const 传递。

3. **`(type *)0` 是编译期技巧，不能运行时解引用**
   `typeof(((type *)0)->member)` 中的 `(type *)0` 看起来像解引用 NULL，但**仅用于类型推导**，编译器不生成访问指令。然而，如果手写版忘了用 `typeof` 而写成 `((type *)0)->member` 取地址，运行时即崩溃。区别在于"求值"还是"求类型"——前者 UB，后者安全。

## 自测题

**1.（选择）** `offsetof(type, member)` 在标准 C 中如何实现？
- A. 运行时计算 `&(((type *)0)->member)` 的地址
- B. 编译期常量，由编译器内置提供
- C. 调用 `__builtin_offsetof` 才能使用
- D. 链接器解析

<details><summary>答案</summary>

**B**。`offsetof` 在 `<stddef.h>` 中定义，标准要求是**整型常量表达式**。现代编译器（GCC/Clang/MSVC）都内置 `__builtin_offsetof`，编译期直接算出偏移，不生成运行时代码。古老的 `&(((type *)0)->member)` 写法是 GCC 早期实现技巧，运行时不会真解引用 NULL，但**标准不保证**这种写法安全，现代代码应直接用 `offsetof`。

</details>

**2.（判断）** `container_of` 用 `(char *)` 而非 `(void *)` 是因为 `void *` 算术在标准 C 中未定义。

<details><summary>答案</summary>

**对**。GNU C 扩展允许 `void *` 算术（按 1 字节），但 ISO C 标准不允许。为了在非 GCC 编译器也可移植，统一用 `char *`——它是**标准保证按字节运算**的唯一类型。

</details>

**3.（踩坑）** 下列代码在 32 位 ARM 上运行结果是什么？
```c
struct s { char c; int i; } x;
struct s *p = container_of(&x.i, struct s, i);
printf("%p %p\n", (void*)p, (void*)&x);
```

<details><summary>答案</summary>

**两个地址相等**。`offsetof(struct s, i)` = 4（因 `c` 后 3 字节 padding），`&x.i` = `&x + 4`，回退 4 字节即 `&x`。这验证了 `container_of` 的正确性。**但若结构体改为 `__attribute__((packed))`**，`offsetof(struct s, i)` = 1，回退后仍是 `&x`，依然正确——offsetof 编译期算出的是真实偏移，无论是否 packed。坑在于**未对齐访问**：packed 后 `&x.i` 可能不在 4 字节边界，ARMv5 直接 `*(&x.i)` 会触发 alignment fault，需用 `memcpy` 或 `get_unaligned`。

</details>

**4.（应用）** 写一个带 `const` 安全检查的 `container_of`，使得 `const T *` 成员指针返回 `const T_host *`。

<details><summary>答案</summary>

```c
#define container_of(ptr, type, member) ({                  \
    const typeof(((type *)0)->member) *__mptr = (ptr);      \
    (type *)( (char *)__mptr - offsetof(type, member) );    \
})

#define container_of_const(ptr, type, member) ({            \
    const typeof(((type *)0)->member) *__mptr = (ptr);      \
    (const type *)( (const char *)__mptr                    \
                    - offsetof(type, member) );             \
})
```
关键：用 `const typeof(...)` 接住 `ptr`，**编译器强制传入也必须 const**——若传非 const 指针给 `container_of_const` 会触发 `-Wdiscarded-qualifiers` 警告。返回 `const type *` 防止调用方误修改。内核的 `container_of` 实际更复杂，会保留 const 性质。

</details>
