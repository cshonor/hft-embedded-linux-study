# 6.6.2 属性声明：section

## 本节讲什么

**section 属性** 将符号放到指定 **ELF section**；链接器脚本把 `.init.text` 等在启动后 **释放或丢弃**，把 `.boot` 放到 RAM 运行地址。Bootloader 与内核启动代码核心技巧。

## 要点

```c
#include <stdio.h>

static int early_data __attribute__((section(".early.data"))) = 1;

__attribute__((section(".init.text")))
void init_once(void)
{
    printf("init_once\n");
}

__attribute__((section(".boot.text")))
void boot_copy_src(void)
{
    /* 链接脚本可能将此段 LMA 与 VMA 不同 */
}
```

```bash
gcc -c section_demo.c -o section_demo.o
objdump -t section_demo.o | grep -E 'early|init|boot'
readelf -S section_demo.o
```

```ld
/* 链接脚本片段示意 */
.early.data : { *(.early.data) } > SRAM
.init.text  : { *(.init.text)  } > DRAM
```

- **内核 `__init`**：启动完成后 `free_initmem()` 回收 `.init.*`
- **模块 `__init`/`__exit`**：加载/卸载段
- **demo02**：自定义 section 变量，**nm/objdump** 验证

```c
/* 函数指针表放入固定段 — 类似 U-Boot linker list */
struct driver __attribute__((section(".drivers")))
drv_instance = { .name = "demo" };
```

## 常见陷阱

1. **自定义 section 必须在链接脚本中"接住" → 否则被丢弃**
   `__attribute__((section(".mydata")))` 只把符号放进 `.mydata` section。如果链接脚本里**没有显式 `*(.mydata)`**，链接器可能：丢弃该 section、合并到默认段、或发出 `orphan section` 警告。自定义 section 不"接住"等于数据丢失，且**无编译错误**，只在运行时发现读不到数据。

2. **section 名前缀有约定 → 用错前缀会被特殊处理**
   `.text.*`、`.data.*`、`.rodata.*`、`.bss.*` 等前缀链接器会按段属性（可执行/可写/只读/零初始化）自动归类。把可写数据放进 `.text.mydata`（看起来像代码段）会导致**段属性错位**，触发 segfault 或内存保护异常。自定义段应保持前缀语义一致：`.boot.data`、`.init.text` 这种命名是有意为之。

3. **`__init` 段运行后被释放 → 持有其指针 use-after-free**
   内核 `__init` 函数/数据在启动后 `free_initmem()` 回收。如果某 `__init` 函数的指针被存到全局变量、之后调用 → use-after-free。内核用 `__ref` 标注豁免段检查，但用户代码不会自动检查。`__exit` 段在非模块编译时同样会被丢弃，若静态编译进 vmlinux 又被运行时调用即崩溃。

## 自测题

**1.（选择）** 内核 `__init` 宏最终展开为以下哪个？
- A. `__attribute__((section(".init.text")))`
- B. `__attribute__((aligned(4)))`
- C. `static inline`
- D. `__attribute__((weak))`

<details><summary>答案</summary>

**A**。`#define __init __section(".init.text") __cold notrace`，本质是把函数放到 `.init.text` 段。启动后 `free_initmem()` 释放该段所有页。`__cold` 提示分支预测器此函数"冷"，`notrace` 关 ftrace。

</details>

**2.（判断）** 自定义段 `.mydata` 即使链接脚本没显式处理，链接器也会自动保留它。

<details><summary>答案</summary>

**错**。默认链接脚本会处理**已知前缀**（.text/.data/.rodata/.bss），但任意命名的 `.mydata` 是"orphan section"。链接器会**启发式归类**（按属性匹配最接近的段），行为**版本相关**且不可靠。生产代码必须在链接脚本 `SECTIONS` 块显式 `*(.mydata)` 才能保证位置和属性。内核链接脚本 `vmlinux.lds` 显式处理了几十个自定义段。

</details>

**3.（踩坑）** 驱动里写了 `static int cfg __attribute__((section(".init.data"))) = 42;`，并在 `probe` 函数中读取 `cfg`。模块加载时正常，但**模块卸载后再次加载**会读到垃圾值。为什么？

<details><summary>答案</summary>

模块的 `.init.data` 在 `probe` 完成后被 `free_module()` 释放，模块卸载时该内存已归还。再次加载模块时，`.init.data` 重新分配、重新填入 `42`——**理论上没问题**。但如果驱动把 `&cfg` 存到了**全局指针**（如 `static int *cfgp = &cfg;`），且 `cfgp` 在 `.data` 段未被释放，二次加载时旧 `cfgp` 指向的 `.init.data` 可能已被其他模块占用——use-after-free。**坑在跨段引用**：`.data` 引用 `.init.data` 的指针，释放后即悬垂。

</details>

**4.（应用）** 设计一个"启动时自动注册驱动"的机制：所有标记 `__driver` 的结构体在 `main` 前被自动遍历调用其 `init` 函数。给出宏定义和链接脚本片段。

<details><summary>答案</summary>

```c
/* driver.h */
struct driver_desc {
    const char *name;
    int (*init)(void);
};
#define __driver __attribute__((used, section(".drivers")))
#define REGISTER_DRIVER(d) \
    static const struct driver_desc d __driver = d

/* main.c */
extern const struct driver_desc __drivers_start[];
extern const struct driver_desc __drivers_stop[];
int main(void) {
    for (const struct driver_desc *p = __drivers_start;
         p < __drivers_stop; ++p)
        p->init();
    /* ... */
}
```
```ld
/* link.ld */
.drivers : {
    __drivers_start = .;
    KEEP(*(.drivers))
    __drivers_stop = .;
} > ROM
```
关键点：
- `__attribute__((used))` 防止 `-ffunction-sections --gc-sections` 误删未引用符号。
- 链接脚本 `KEEP()` 显式保留 section，标记起止符号。
- 内核 `__initcall` / Linux driver model 用完全相同的模式（`.initcall6.init` 等多级段）。

</details>
