# 6.2.4 指定初始化的好处

## 本节讲什么

指定初始化提升 **可读性、可维护性、Review 安全性**；在大型结构体与配置表中收益最大。对比 positional 初始化，字段增删时 merge conflict 更小。

## 要点

### Positional vs Designated

```c
struct timer_cfg { int ms; int enabled; const char *name; };

/* 差：顺序错 silent bug */
struct timer_cfg bad = { 1, 1000, "watchdog" };  /* ms 与 enabled 反了？ */

/* 好：自文档化 */
struct timer_cfg good = {
    .name    = "watchdog",
    .ms      = 1000,
    .enabled = 1,
};
```

| 收益 | 说明 |
|------|------|
| **自描述** | 读代码无需对照 struct 定义顺序 |
| **稀疏** | 数组/表只写非零项 |
| **演进** | 中间插入新成员不破坏旧初始化 |
| **Review** | diff 一眼看出改了哪个字段 |

```c
/* 内核风格：宏生成表项仍保留 designated */
#define DEVICE_ENTRY(_compat, _data)     { .compatible = _compat, .data = (void *)(_data) }
```

- **缺点**：C++ 早期不兼容；跨编译器写库时需 `#ifdef`
- **DPDK**：静态 `rte_eth_conf` 等同理；热路径结构仍倾向运行时赋值 + 少量 static default

## 代码自测

**题目 1：** 指定初始化在什么场景下比位置初始化更安全？
<details>
<summary>参考答案</summary>

指定初始化更安全的场景：

1. **成员众多的结构体**：如 file_operations（20+成员）、socket（10+成员），位置初始化容易搞错顺序
2. **频繁演进的结构体**：内核版本升级时新增成员，指定初始化的旧代码不受影响
3. **只初始化少数成员**：大部分成员为 0，只需指定非零成员
4. **可读性要求高**：代码审查时 `.irq = 42` 比 `42` 更直观
5. **位域联合体**：指定初始化可以明确初始化哪个联合体成员

反例（位置初始化的危险）：
```c
struct config { int enabled; int timeout; };
struct config c = { 30 };  // 30 是 enabled 还是 timeout？
```

指定初始化：`struct config c = { .timeout = 30 };` 明确无歧义。

</details>
