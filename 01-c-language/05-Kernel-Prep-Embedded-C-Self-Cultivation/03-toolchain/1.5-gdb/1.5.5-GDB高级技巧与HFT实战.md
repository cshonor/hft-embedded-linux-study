# 1.5.5 GDB 高级技巧与 HFT 实战

## attach：调试正在运行的进程

程序已经在运行，不想重启，直接附着上去调试。

```bash
gdb -p <PID>                   # attach 到进程
# 或
gdb ./app <PID>
```

```
(gdb) break some_function      # 设断点
(gdb) continue                 # 让程序继续跑，到断点会停
(gdb) ...                      # 调试
(gdb) detach                   # 脱离进程，程序继续运行
(gdb) quit
```

### attach 的本质

`gdb -p <PID>` 实际上：
1. 调用 `ptrace(PTRACE_ATTACH, pid)` → 内核给目标进程发 **SIGSTOP**，进程停住
2. GDB 读取目标进程的寄存器、内存
3. `detach` 时调 `ptrace(PTRACE_DETACH)` → 进程收到 SIGCONT 继续运行

> **生产环境慎用**：attach 会让目标进程**瞬间停住**。HFT 交易引擎停 1ms 都可能丢单。只在维护窗口或非交易时段 attach。

### HFT 场景：交易引擎排查

```
# 交易引擎 PID 12345 运行中，出现异常订单
$ gdb -p 12345
(gdb) info threads              # 看所有线程
(gdb) thread 3                  # 切到策略线程
(gdb) bt                        # 看策略线程在干什么
(gdb) print order_book->depth   # 查看订单簿状态
(gdb) detach                    # 排查完脱离，引擎继续运行
```

## 交叉调试：嵌入式 / 远程

嵌入式板子资源有限（跑不了完整 GDB），用 **gdbserver + 交叉 GDB** 远程调试。

### 架构

```
[开发板]                          [主机]
app (ARM)  ←──网络/串口──→  arm-linux-gnueabihf-gdb
gdbserver                      + app (带 -g 的 ARM 版)
```

### 操作步骤

**板子上**（启动 gdbserver）：

```bash
gdbserver :2345 ./app           # 监听 2345 端口
# 或附着到已有进程
gdbserver :2345 --attach <PID>
```

**主机上**（启动交叉 GDB）：

```bash
arm-linux-gnueabihf-gdb ./app
(gdb) target remote 192.168.1.100:2345    # 连接板子
(gdb) set sysroot /path/to/target/rootfs  # 指定目标板根文件系统（找 libc 等符号）
(gdb) set solib-search-path /path/to/libs # 额外库搜索路径
(gdb) break main
(gdb) continue
```

### 串口调试

没有网络时用串口：

```bash
# 板子
gdbserver /dev/ttyS0 ./app

# 主机
arm-linux-gnueabihf-gdb ./app
(gdb) target remote /dev/ttyUSB0
```

## -O2 下的调试陷阱

HFT 生产代码通常 `-O2` 甚至 `-O3`，调试时会遇到：

| 问题 | 原因 | 应对 |
|------|------|------|
| 变量 `<optimized out>` | 被优化进寄存器，栈上没了 | 关键变量加 `volatile` |
| 行号跳跃 | 多行合并 / 指令重排 | 用 `stepi` 逐指令走 |
| 断点不命中 | 函数被内联 | `info inline`，或对内联展开后的地址设断 |
| 参数显示错误 | 寄存器传参（ABI 变化） | `info args` + `info registers` 对照 |
| 调用栈不完整 | 尾调用优化省略了栈帧 | `set backtrace past-main on` |

```c
// volatile 防优化示例
volatile int debug_flag = 0;    // GDB 可以随时查看/修改
```

### 混合编译策略

```makefile
# 热点文件 -O2，调试文件 -O0 -g
CFLAGS_HOT = -O2 -g
CFLAGS_DEBUG = -O0 -g

main.o: main.c
	$(CC) $(CFLAGS_DEBUG) -c main.c

strategy.o: strategy.c
	$(CC) $(CFLAGS_HOT) -c strategy.c
```

## GDB 脚本

### .gdbinit

在项目根目录或 `~/.gdbinit` 放自动执行的 GDB 命令：

```bash
# ~/.gdbinit
set print pretty on
set print elements 200
set disassemble-next-line on
set backtrace past-main on
```

### 命令脚本

```bash
# debug.gdb
break main
break crash.c:42 if i == 100
run
bt
info locals
```

```bash
gdb -x debug.gdb ./app          # 执行脚本
# 或
gdb ./app -ex "source debug.gdb"
```

### 批处理（CI/CD 用）

```bash
gdb -batch -ex "run" -ex "bt" -ex "info locals" ./app
# 运行程序，如果崩溃自动打印栈和变量，然后退出
```

## watchpoint 高级用法

```bash
# 硬件 watchpoint（不拖慢程序，但数量有限）
(gdb) watch *ptr                # 内存被写时断
(gdb) rwatch *ptr               # 内存被读时断
(gdb) awatch *ptr               # 读或写都断

# 如果硬件 watchpoint 用完，GDB 自动降级为软件 watchpoint
# 软件 watchpoint 会单步执行每条指令检查值 → 程序慢 100 倍以上
```

HFT 场景：交易状态被意外修改 → `watch order->status` 定位谁改的。

## 多线程调试

```bash
(gdb) info threads              # 列出所有线程
(gdb) thread 2                  # 切到 2 号线程
(gdb) thread apply all bt       # 所有线程都打 bt
(gdb) thread apply 2 3 bt       # 只对 2、3 号线程打 bt
(gdb) set scheduler-locking on  # 只让当前线程跑，其他停住
(gdb) set scheduler-locking off # 恢复（默认）
```

### 线程断点

```bash
(gdb) break main.c:42 thread 3  # 只对 3 号线程断
```

## 内核级调试

用户态 core dump 的思路完全适用于内核：

| 用户态 | 内核态 |
|--------|--------|
| core 文件 | vmcore（kdump 生成） |
| `gdb app core` | `crash vmlinux vmcore` |
| `bt` | `crash> bt` |
| `info registers` | `crash> regs` |
| `x/16xb addr` | `crash> rd addr` |

```bash
# kdump 配置
echo "crashkernel=256M" >> /boot/grub/grub.cfg   # 预留内存
systemctl enable kdump

# 内核 panic 后
crash /usr/lib/debug/vmlinux /var/crash/vmcore
crash> bt                      # 崩溃栈
crash> ps                      # 所有进程
crash> struct task_struct 0xffff8800xxxx
```

## HFT 调试检查清单

| 场景 | 工具/命令 |
|------|-----------|
| 交易引擎崩溃 | core dump + `bt` + `info locals` |
| 内存被踩 | `watch *addr` |
| 变量被意外改 | `watch var` |
| 多线程死锁 | `info threads` + `thread apply all bt` |
| 性能抖动 | `perf record` → `perf report`（GDB 不擅长性能） |
| 生产环境排查 | `gdb -p <PID>` attach（非交易时段） |
| ARM 板子调试 | `gdbserver` + 交叉 GDB |
| `-O2` 变量丢失 | `volatile` / 混合编译 / `stepi` |
| 批量验证 | GDB 脚本 + `-batch` |
