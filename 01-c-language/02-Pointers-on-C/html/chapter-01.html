简介

本节讲什么

全书开篇：用一个完整但极简的 C 程序（列宽排序示例）走通「写代码 → 编译 → 运行 → 退出」全链路。本章是铺垫章，不深入语法，只建立从源码到 CPU 执行的最小认知模型——这个模型是后续指针、内存、结构体、ABI 所有话题的地基。

为什么这一章对 HFT 学习者特别重要

很多写出过能跑的 C 程序的人，其实说不清下面这条链路的每一步：

.c 源文件
  │ 预处理 (-E)        ← 1.1.2 #include/#define 在此展开
  ▼
.i 纯 C 文本
  │ 编译 (-S)          ← 语法分析、优化、生成汇编
  ▼
.s 汇编文本
  │ 汇编 (-c)          ← 翻译成机器码，产物是 ELF 可重定位目标文件
  ▼
.o 目标文件
  │ 链接               ← 解析 printf 等未定义符号，合并各 .o 的段
  ▼
ELF 可执行文件
  │ 加载 (execve)      ← 内核建进程、映射虚拟内存、跳转入口
  ▼
进程运行 → main → return → 退出码

HFT 的现实：DPDK 应用、行情解析程序、内核模块，本质都走这条路。看懂这条链路，是看懂 meson/Makefile 构建系统、ld 链接错误、dlopen 动态加载、core dump 栈回溯的前提。本章不是"Hello World 练习"，而是把整条工具链摸一遍。

最简骨架（仓库标准模板）

#include <stdio.h>

int main(void)
{
    printf("Hello Low Latency & Kernel\n");
    return 0;
}
部分 底层含义（HFT/内核视角）
#include <stdio.h> 预处理阶段把头文件声明文本插入；printf 的实现在 libc，链接时解析
int main(void) 唯一入口；(void) 显式无参，工程规范——避免旧式 main() 的隐式参数陷阱
printf libc 封装，底层走 write(2) syscall，最终陷入内核
return 0 退出码；shell echo $? 可读；交易程序用退出码区分正常/异常退出

内存布局预览（整章贯穿）

程序加载后，虚拟地址空间大致如此（详见 ch03/ch18）：

高地址
┌──────────────┐
│ 栈 stack ↓    │  局部自动变量、调用帧（ch18.1.3 栈帧）
├──────────────┤
│              │
├──────────────┤
│ 堆 heap ↑    │  malloc 分配（ch11）
├──────────────┤
│ .bss         │  未初始化全局/静态，启动时清零
├──────────────┤
│ .data        │  已初始化全局/静态
├──────────────┤
│ .rodata      │  字符串字面量、const（写它 → SIGSEGV）
├──────────────┤
│ .text        │  机器码（只读、可执行）
└──────────────┘
低地址

口诀：局部变量在栈、全局/静态在 data/bss、malloc 在堆、代码在 text、字符串字面量在 rodata。现在记不住没关系，ch03/ch11/ch18 会逐一展开——但先有这张地图，后面读到"返回局部变量地址是悬垂指针"才不会懵。

本章程序结构（书中示例）

  1. main — 控制流程，调用读写与排序

1.1

.1 空白和注释

本节讲什么

C 的词法层忽略大部分空白；注释是文档化代码的工具。这两件事看似琐碎，但工业底层项目的格式规范、diff 可读性、/* */ 与 // 的取舍、以及"注释删除发生在预处理阶段"这件事——全都在这一节埋下伏笔。

空白：词法上的"自由形式"

规则

  • 空格、制表符、换行在词法分析阶段基本等同（preprocessor tokens 和字符串字面量内部除外）
  • C 是自由形式语言——理论上你可以把整个程序写在一行，或每个 token 一行
  • 但自由不等于随意——团队风格一致性 >> 个人偏好

历史背景

  • C 的自由形式源于 BCPL → B → C 的演进，早期 Unix 代码就有多种排版风格
  • 1979 年《C Programming Style》和后来 indent、gofmt 思想的流行，确立了"格式化交给工具"的传统
  • 今天 clang-format 是事实标准，内核有 clang-format 配置，DPDK 也有

为什么空白不是"小事"

场景 空白的影响
diff / review 统一缩进让改动一目了然；混用 tab/space 会让 diff 全文飘红
合并冲突 不一致格式是 merge conflict 的头号元凶
git blame 一次格式大改会让 blame 历史断裂，查不到真正作者
嵌入式受限编辑器 tab 宽度不一在某些老终端会错位

工程铁律：项目里要么全 tab，要么全 space（内核用 tab，DPDK/多数现代项目用 4-space），绝不混用，并用 .editorconfig + clang-format 强制。

注释：两种语法

/* 块注释：内核代码传统上仅推荐这种 */
// 行注释：C99 引入，用户态工程常用

/*
 * 多行说明：函数意图、不变量、返回值
 * 内核风格：每行以 " * " 开头
 */

/* */ vs // 的取舍

维度 /* */ //
标准 K&R 时代就有（非标准但广泛支持）→ C89/C90 正式 C99 引入
多行 原生支持 每行都要 //
嵌套 不能嵌套（/* /* */ */ 提前结束） 可在块注释内出现
内核偏好 主流（Linus 明确要求） 较少
用户态/HFT 两者并存，团队统一即可 团队统一即可
临时屏蔽代码块 #if 0 ... #endif 更安全（块注释不能嵌套会出错） —

嵌套陷阱（常见错误）

/* 临时屏蔽一大段
/* 内部本来就有块注释 */
*/

第一个 */ 就结束了外层注释，剩下的 */ 成了语法错误。临时屏蔽代码用 #if 0 ... #endif，不用 /* */。

好注释 vs 烂注释

好注释解释"为什么"

/* 必须按 little-endian 解析：交易所行情字段规定 LE */
uint32_t price = le32toh(*p);

烂注释复述代码

i++;          // increment i        ← 毫无价值
i = i + 1;    /* i 加一 */          ← 更糟
好注释写什么 烂注释长什么样
函数意图、不变量、边界条件 复述每一行代码做什么
为什么用这个算法/这个魔数 "这里加一"
参数、返回值、错误码语义 过时的设计文档（代码改了注释没改）
已知缺陷、TODO、性能假设 冗余的类型说明（类型一眼能看到）

口诀：注释回答 why，代码回答 how。能用函数名/变量名表达的，别靠注释。

注释的预处理阶段删除（底层细节）

注释在预处理阶段被删除（替换成单个空格），所以：

  • 注释不进入编译产物 —— .o 里没有注释，运行时也没有
  • gcc -E main.c 看到的 .i 文件里注释已经消失
  • 所以注释不影响性能（别担心"注释太多让程序变慢"）
  • 但注释影响编译后的 token 流：a/* */b 会被预处理成 a b（两个 token）还是 ab？C 标准规定替换成一个空格，所以是 a b。极少出错但要心里有数

字符串内的"伪注释"

char *s = "/* this is not a comment */";

字符串字面量内的 /* 不被当注释——词法分析先识别字符串，再识别注释。

工程规范（仓库配套）

  1. 统一缩进（4-space 或 tab，项目级 .clang-format）
  2. 大括号风格：K&R（{ 同行）或 Allman，统一即可
  3. 公共 API 注释：参数、返回值、错误码、线程安全性
  4. 避免无意义注释（i++ // increment i）
  5. 大段屏蔽用 #if 0，不用 /* */

常见误区

误区 纠正
"注释越多越好" 烂注释是噪声，比没注释还糟；好注释精而少
"注释会拖慢程序" 预处理就删了，零运行时影响
"// 是 C 一直就有的" C99 才标准化；C90 不保证，老嵌入式编译器可能不支持
"用 /* */ 屏蔽大段代码很方便" 不能嵌套，遇到内含块注释就出错；用 #if 0
"格式风格可以自由发挥" 团队必须统一，且交给工具强制

自测要点

  • C 的空白在词法层基本等同，有哪两个例外？（字符串字面量内部、preprocessor token 之间在某些情况）
  • /* /* */ */ 为什么是错的？正确屏蔽大段代码用什么？
  • 注释在哪个编译阶段被删除？这有什么现实推论？（不影响性能、.i 里看不到）
  • 字符串内的 /* 会被当注释吗？为什么？
  • "好注释写 why 不写 how"——举一个违反这条的烂注释例子。

1.1

.2 预处理指令

本节讲什么

以 # 开头的指令在编译前由预处理器处理。本章只讲最常用的 #include；完整的宏（#define）、条件编译（#ifdef）、文件包含路径、include guard 在 ch14 展开。这一节的价值是建立"预处理是独立的一阶段"这个认知——它只做文本操作，不懂 C 语法。

#include 的两种形式

#include <stdio.h>      /* 角括号：系统/标准库 */
#include "myhdr.h"       /* 双引号：本地头文件 */
形式 搜索路径（典型） 用途
<...> -I 目录 → 系统头目录（/usr/include）→ 标准库 标准库、第三方库（<rte_*.h>、<linux/*.h>）
"..." 当前源文件目录 → -I → 系统目录 项目内自家头文件

两种形式技术上只是搜索路径顺序不同，标准并未严格规定；但工程约定俗成：系统头用 <>，自家头用 ""。

路径控制的工程价值

gcc -I./include -I/opt/dpdk/include main.c
  • -I 把目录加入搜索路径——DPDK/内核构建系统的核心机制
  • meson/cmake 最终也是生成 -I 参数
  • 路径顺序决定同名头文件优先用哪个——这是"头文件遮蔽"bug 的根源

预处理只做文本操作（关键认知）

#include <stdio.h> 的全部语义就是：把 stdio.h 的文本内容原样插入到这一行的位置。它：

  • 不理解 C 语法 —— 只是文本拼接
  • 不检查类型 —— 类型检查在编译阶段（-S）才发生
  • 不链接实现 —— printf 的实现在 libc，链接阶段才解析
/* main.c 预处理前 */
#include <stdio.h>
int main(void) { printf("hi"); return 0; }

/* main.c 预处理后（main.i，简化示意）*/
extern int printf(const char *, ...);
int main(void) { printf("hi"); return 0; }

printf 的声明被 stdio.h 带进来了，但定义还在 libc.so 里——这就是为什么编译能过、链接可能失败（undefined reference）。

编译四阶段之「预处理」

gcc -E main.c -o main.i

预处理器在这一步做四件事：

  1. 展开 #include —— 把头文件内容插入
  2. 替换 #define 宏 —— 宏展开（ch14）
  3. 删除注释 —— 替换成单个空格（见 1.1.1）
  4. 处理 #ifdef / #if / #endif —— 条件编译，保留匹配分支

产物体积的现实

  • 一个 #include <stdio.h> 的 main.c，预处理后 .i 可能上千行
  • #include <rte_mbuf.h> 的 DPDK 文件，.i 可能上万行——宏展开是 DPDK 构建慢的原因之一
  • 内核头文件同理，linux/ 头依赖链深，.i 巨大
gcc -E main.c | wc -l    # 看预处理后的行数

头文件多为"声明"，不是"实现"

头文件给 实现在
函数原型 int printf(const char *, ...); libc.so（标准库）
结构体定义 struct rte_mbuf { ... }; 该库的 .c 文件
宏 #define RTE_MAX(x,y) ... 内联展开，无独立实现
extern 变量声明 某个 .c 文件的定义处

链接阶段才把"声明的符号"和"实现的符号"匹配上。匹配不上就是 undefined reference to xxx——这是初学者最常见的链接错误。

include guard：头文件被多次包含怎么办

/* myhdr.h */
#ifndef MYHDR_H
#define MYHDR_H
/* ... 实际内容 ... */
#endif
  • 同一个 .c 间接 #include 同一头多次（如 a.h 和 b.h 都 include stdio.h），预处理会插入两次 → 结构体重定义错误
  • include guard 用宏确保只展开一次
  • 替代方案 #pragma once（非标准但主流编译器都支持）

详见 ch14。

HFT / 内核 / DPDK 视角

场景 预处理的角色
DPDK 海量 rte_*.h + 宏，.i 巨大，构建慢；-I 路径要包含 DPDK 安装目录
内核模块 #include <linux/module.h> 触发内核构建系统（Kbuild）的复杂展开
跨平台 #ifdef __x86_64__ / #ifdef __aarch64__ 区分架构——同源码适配多 ISA
编译选项 #ifdef NDEBUG 区分调试/发布；HFT 常用宏切换低延迟与可观测模式

常见误区

误区 纠正
"#include 会把库的实现也带进来" 只带声明；实现在 .so/.a/.c，链接时才合并
"<> 和 "" 是不同的指令" 只是搜索路径顺序不同，标准未严格区分
"头文件改了不用重新编译" 头是文本插入，改了所有依赖它的 .c 都要重编——这正是增量构建系统的工作
"宏和函数差不多" 宏是文本替换，没有类型检查、有副作用陷阱（ch14.2.4）
"预处理能做条件判断如 if" 只能 #if/#ifdef，是编译时文本裁剪，不是运行时分支

实操

  1. gcc -E main.c -o main.i，用编辑器打开 .i，看 #include 展开后的规模

1.1

.3 main 函数

本节讲什么

main 是 C 程序的唯一入口：操作系统加载 ELF 后，跳转到一段叫启动代码（crt0）的胶水代码，它做初始化后才调用 main；main 的 return 值会交给父进程/shell 当作退出码。这一节把"程序怎么开始、怎么结束"讲清楚，为 ch18 运行时环境打前站。

函数签名

int main(void)            /* 无参数形式（推荐） */
{
    /* ... */
    return 0;
}

int main(int argc, char *argv[])   /* 带命令行参数形式 */
{
    /* ... */
    return 0;
}
要素 说明
int 返回类型固定 int——不是 void、不是 void*；返回值是退出状态
(void) 显式无参数；标准 C 推荐，避免旧式 main() 的隐式参数陷阱
argc/argv 命令行参数：argc 是参数个数（含程序名），argv 是参数字符串数组
return 0 0 表示成功；非 0 表示错误（约定俗成，POSIX 规范）
省略 return C99 起 main 可省略 return，等价 return 0；其他函数不能省

两种合法形式

C 标准只承认两种 main 签名：

  1. int main(void) —— 无参数
  2. int main(int argc, char *argv[]) —— 带命令行参数（也可写 char **argv）

其他形式（如 void main()、int main(int argc, char *argv[], char *envp[])）都是非标准扩展——某些编译器接受，但不可移植。HFT/嵌入式追求可移植，应坚持标准形式。

命令行参数示例

int main(int argc, char *argv[])
{
    for (int i = 0; i < argc; i++)
        printf("argv[%d] = %s\n", i, argv[i]);
    return 0;
}

$ ./prog --port 8000
argv[0] = ./prog
argv[1] = --port
argv[2] = 8000

argv[argc] 一定是 NULL——可以用来做循环终止条件。详见 ch13.4 命令行参数。

运行链路：从 shell 到 main

很多人以为"操作系统直接跳到 main"，实际中间有一段启动胶水代码：

1. shell 解析命令 → fork + execve("./main", argv, envp)
2. 内核 execve 系统调用：
   ├── 读取 ELF 头，检查 magic
   ├── 建新进程地址空间，映射各段（text/data/bss/堆/栈）
   ├── 设置 argc/argv/envp 压到栈顶
   └── 跳到 ELF 入口（不一定是 main！通常是 _start）
3. _start（crt0 启动代码，来自 crt1.o）：
   ├── 设置栈、对齐 ABI
   ├── 调用 __libc_start_main（glibc 内部）
   │     ├── 运行 .init 段的全局构造（C++ 全局对象构造）
   │     ├── 调用 main(argc, argv, envp)
   │     └── main 返回后调用 exit()
4. exit()：
   ├── 运行 atexit/on_exit 注册的清理函数
   ├── 刷新 stdio 缓冲、关闭流
   └── 调用 _exit() 系统调用 → 内核回收进程资源
5. 父进程（shell）通过 wait() 拿到退出码 → echo $?

关键认知：main 不是真正的入口，_start 才是 ELF 入口；main 也不是真正的出口，exit() 才负责清理。main 只是"用户代码的入口"。详见 ch18。

退出码语义

./main
echo $?          # main 的 return 值（0–255）
退出码 约定
0 成功（POSIX 通用约定）
1–125 程序自定义错误码
126 文件不可执行
127 命令未找到
128+N 被信号 N 杀死（如 139 = SIGSEGV，137 = SIGKILL）
  • shell 的 $? 只取低 8 位，所以 return 256 和 return 0 在 shell 看来一样
  • 交易程序常用退出码区分"正常退出/风控触发/数据异常"等，便于编排脚本判断
  • exit(n) 立即退出，绕过 main 的 return；_exit(n) 连 stdio 缓冲都不刷

HFT 与低延迟视角

printf 在热路径上的代价

  • 调试/日志：printf 够用，方便
  • 极致低延迟网关：printf 走 stdio 缓冲 + write syscall，有微秒级抖动 → 热路径直接用 write(2) 绕过 stdio，或用 lock-free ring + 后台线程异步落盘（ch15 深入）

main 启动延迟

  • 动态链接：启动时要加载 .so、解析符号、跑全局构造——首次行情到达前的延迟来源之一
  • 静态链接 + 裁剪：启动快、部署简单，HFT 离线机器和嵌入式常用
  • 启动顺序：HFT 进程常需"绑定 CPU、锁内存、预热 cache"后才开始收行情——这些在 main 开头做

main 之外的入口

场景 真正入口
普通可执行 _start（crt0）→ __libc_start_main → main
内核模块 module_init 宏注册的函数，内核加载时调用
DPDK 应用 DPDK 框架的 rte_eal_init 后再分核跑 worker loop
共享库 .so 无 main；提供被 dlopen 调用的函数

常见误区

误区 纠正
void main() 也行 非标准，旧编译器宽容，现代编译器 -Wall 会警告，不可移植
"main 是程序第一个执行的代码" _start 和 crt0 先执行；C++ 全局对象构造在 main 之前
"return 0 一定表示成功" 约定俗成，但要全程序一致；别让一个地方 0=成功、另一个地方 0=失败
"省略 return 是好习惯" 只有 main（C99+）可以省略且等价 return 0；其他函数省略 return 是 UB
"退出码越大越严重" shell 只看是否为 0；非 0 都是"失败"，大小无统一语义

实操

  1. 写 int main(void) { return 42; }，编译运行后 echo $? 看 42

  4. 写一个 void main()，用 gcc -Wall -Wextra 看警告
  5. gcc -static main.c -o main-static，对比 ldd 输出和启动行为

1.1

.4 read_column_numbers 函数

本节讲什么

书中示例 read_column_numbers：从标准输入循环读入一组整数（列宽），存入数组。这一节的核心价值不在于函数本身，而在于它第一次在工程代码里使用 & 取地址 —— 全书指针章的前置铺垫。同时引入 scanf 返回值校验、栈上数组、缓冲等关键概念。

第一个工程级 I/O 模式

#include <stdio.h>

int main(void)
{
    int val;
    if (scanf("%d", &val) == 1)
        printf("input = %d\n", val);
    else
        printf("invalid input\n");
    return 0;
}

这段代码浓缩了三个工程要点：

知识点 说明
&val 取 val 的内存地址；scanf 需要指针才能把读到的值写入 val 的内存
返回值校验 scanf 返回成功赋值的项数；不校验就用结果 → UB（读未初始化变量）
无 & 的后果 scanf("%d", val) 把 val 的值当指针解引用 → 几乎必崩

为什么 scanf 必须要指针

C 的函数参数是按值传递——函数内部拿到的是副本，无法修改调用者的变量。要修改调用者的变量，必须传地址：

void bad_set(int x)   { x = 42; }              /* 改的是副本，外面没变 */
void good_set(int *p) { *p = 42; }             /* 通过指针写回真实内存 */

scanf("%d", &val) 本质就是 good_set 模式：scanf 在 libc 内部不知道 val 的地址，必须由调用者用 & 告诉它。这是 C 指针存在意义的第一个体现——跨函数修改调用者的变量。

这里埋的伏笔：& 取地址、* 解引用、指针作为"输出参数"——将在 ch06 正式展开。

scanf 返回值：必须校验

int n = scanf("%d %d", &a, &b);
输入 返回值
"10 20" 2（两个都成功赋值）
"10 abc" 1（第一个成功，第二个失败）
"abc" 0（第一个就失败）
EOF（Ctrl-D） EOF（-1）

不校验返回值直接用 a、b，可能读到未初始化变量——C 不保证清零，是 UB。所有 scanf 都要检查返回值，这是工程铁律。

栈上数组与栈溢出

int read_column_numbers(int arr[], int max)
{
    int n = 0;
    while (n < max && scanf("%d", &arr[n]) == 1)
        n++;
    return n;
}
  • arr 是调用者传进来的（形参退化为指针，见 ch08），函数本身不分配数组内存
  • 如果在 read_column_numbers 内部声明 int arr[10000]，那是栈上分配——栈空间有限（默认 8MB），大数组易溢出

栈 vs 堆 vs 全局：什么时候用什么

位置 何时用 风险
栈（局部自动变量） 小、生命周期在函数内、确定大小 大数组 → 栈溢出；返回其地址 → 悬垂指针
堆（malloc，ch11） 大、生命周期跨函数、运行时才知大小 忘 free → 泄漏；free 后再用 → 悬垂
全局/静态 大缓冲、跨函数共享、整个进程生命周期 多线程并发访问要加锁；初始化时机晚

HFT 常见踩坑：在 main 里开 char buf[1024*1024]（1MB 局部数组），栈直接溢出 SIGSEGV。改用静态缓冲或 malloc，或用 ulimit -s 调大栈（治标不治本）。

stdio 缓冲：HFT 热路径的延迟源

scanf/printf 走 stdio 缓冲：

  • 终端是行缓冲（遇到 \n 才 flush）——交互时感觉"即时"
  • 重定向到文件是全缓冲（缓冲满才 flush）——批量高效但有延迟
  • HFT 热路径上 printf 的微秒级抖动来自这里：缓冲满 + syscall + 内核写 → 抖动

详见 ch15。热路径替代方案：直接 write(2)，或 lock-free ring + 后台落盘。

read_column_numbers 的工程要点小结

  • 循环 + 边界检查：n < max 防止数组越界
  • 循环 + 返回值检查：scanf == 1 处理非法输入和 EOF
  • main 协调、子函数单一职责：read_column_numbers 只负责读，不负责排序或输出
  • 错误传播：返回实际读到的个数 n，让调用者知道读了多少

常见误区

误区 纠正
scanf("%d", val) 不加 & 把 val 的值当地址解引用 → 段错误；%d 必须配 int *
不检查 scanf 返回值 读到未初始化变量 → UB，可能"恰好正常"数月后崩溃
scanf("%d", &arr[i]) 会越界 只要 i < max 守好边界就不会；忘了边界就 UB
在函数内开大局部数组 栈有限，大缓冲用 malloc 或静态
scanf 失败后直接重试 失败的输入会留在 stdin 缓冲，要 while (getchar()!='\n'); 清掉
指针是"高级特性" 第一章就在用 &；指针是 C 的基本运作方式，不是高级

.5 rearrange 函数

本节讲什么

书中 rearrange 函数：对读入的列宽数据重排，综合运用 if-else、for、while 三种控制流。本章只是让语法"混个眼熟"，正式规则在 ch04-statements；运算符优先级陷阱在 ch05 和《C 陷阱与缺陷》。这节真正的价值是引入"程序的控制结构组织"这个工程视角。

控制流（本章入门，正式见 ch04）

三种基本结构

/* 分支：if-else */
if (a[i] > a[j]) {
    int t = a[i]; a[i] = a[j]; a[j] = t;   /* 经典三变量交换 */
}

/* 循环：for —— 已知次数 */
for (i = 0; i < n; i++)
    /* ... */

/* 循环：while —— 条件驱动 */
while (i < n && scanf("%d", &a[i]) == 1)
    i++;

结构化编程的三种基本结构

任何可计算问题都能用三种控制结构表达——这是 1966 年 Böhm-Jacopini 定理的结论，也是结构化编程的基础：

结构 对应 C 语法 何时用
顺序 语句依次执行 默认
选择 if/else if/else/switch 根据条件走不同分支
迭代 for/while/do-while 重复执行直到条件不满足

goto 不在这三种里——Dijkstra 1968 年《Go To Statement Considered Harmful》主张少用。但内核/异常处理/状态机里 goto 有合理用途，ch04.9 详谈。

for vs while 的选择

/* for：循环次数已知，三个子句（init/cond/step）一目了然 */
for (int i = 0; i < n; i++) { ... }

/* while：条件驱动，次数不定，如读到 EOF */
while (scanf("%d", &x) == 1) { ... }

/* do-while：至少执行一次 */
do { ... } while (cond);

工程上：次数已知用 for，条件驱动用 while，至少一次用 do-while。乱用 while 写已知次数循环，可读性变差。

rearrange 在示例中的角色

┌─────────────────────┐
│ main                │  协调者：调用读入和重排
│  ├─ read_column_numbers  读入数据
│  └─ rearrange           重排数据
└─────────────────────┘
  • rearrange 接收数组 + 长度（指针形式 ch06/ch08 再 formalize）
  • 按题目要求调整列顺序（如升序），供后续格式化输出
  • 体现工程原则：main 协调，子函数单一职责——每个函数只做一件事，便于测试和复用

工程视角：程序的控制结构组织

这一节表面讲语法，实际在示范怎么组织程序的控制流：

  1. 入口校验：函数开头先检查参数合法性（n < 0? arr == NULL?），早返回
  2. 主循环明确：一个循环做一件事，不要在循环里塞过多逻辑
  3. 错误传播：失败时返回错误码或特殊值，让调用者决定怎么办
  4. 状态最小化：循环里用的临时变量越少越好，越少越不容易出 bug
/* 好的函数结构示意 */
int rearrange(int *arr, int n)
{
    if (arr == NULL || n <= 0)   /* 1. 入口校验 */
        return -1;

    for (int i = 0; i < n - 1; i++) {   /* 2. 主循环单一职责 */
        for (int j = i + 1; j < n; j++) {
            if (arr[j] < arr[i]) {     /* 3. 选择结构 */
                int t = arr[i];
                arr[i] = arr[j];
                arr[j] = t;
            }
        }
    }
    return 0;                          /* 4. 成功返回 0 */
}

这里用的是选择排序——简单但 O(n²)，不是高效算法。HFT 真正的排序需求走 qsort（ch16 标准库）或专用算法。本章只为练习控制流。

算法视角：为什么这节对 HFT 学习者是铺垫

  • 现实 HFT 代码极少手写排序——qsort、std::sort、或针对固定模式的专用算法
  • 但控制流组织是写一切代码的基础：状态机、解析器、事件循环都建立在 if/for/while 上
  • 真正影响 HFT 性能的不是"用了哪种循环"，而是数据布局、缓存局部性、分支预测——这些在 ch05/ch08/ch18 深入

常见误区

误区 纠正
if (a = b) 写成赋值 = 赋值、== 比较；这是经典 bug，-Wall -Wparentheses 会警告
for (int i=0; i<=n; i++) 多走一步 边界条件：< n 还是 <= n 要想清楚，差一是数组越界
while (i < n) ... 忘了 i++ 死循环，CPU 100%——调试时先看循环条件是否推进
三变量交换写错顺序 t=a; a=b; b=t; 顺序不能乱，否则两个都变成同一个值
在循环里做能移到循环外的事 比如 for (...) sum += arr[i] * magic_constant;，常量每次重算——编译器一般会提到循环外，但别依赖

实操

  1. 仿写一个循环求和函数，校验 scanf 返回值，处理 EOF
  2. 故意把 == 写成 =，用 -Wall -Wparentheses 看警告
  3. 故意写 for (i=0; i<=n; i++) 越界，看是否崩溃（不一定崩，UB）
  4. 写一个 while 忘了 i++，观察 CPU 满载（用 top）
  5. 把选择排序换成 qsort（ch16），对比代码量和可读性

踩坑：栈上大数组

    char buf[1024 * 1024];   /* 1MB 局部数组 */
    /* ... */

踩坑：返回栈变量地址

-Wall -Wextra -Werror 为什么是铁律

选项 作用 不开的后果
-Wall 常见问题警告（未用变量、= 写成 ==、格式串不匹配） 这些 bug 潜伏数月才爆发
-Wextra 更严格的额外警告（空参 ()、隐式转换） 默默引入可移植性 bug

编译

本节讲什么

编译四阶段（本章重中之重）

一个 .c 变成可执行文件，经历四个独立阶段，每个阶段都有对应的 gcc 选项：

阶段 命令 产物 作用
1. 预处理 gcc -E main.c -o main.i .i（纯 C 文本） 展开 #include/#define，删注释，处理 #ifdef
2. 编译 gcc -S main.i -o main.s .s（汇编文本） 语法分析、语义检查、优化、生成汇编
3. 汇编 gcc -c main.s -o main.o .o（ELF 可重定位） 翻译汇编成机器码，符号未解析
4. 链接 gcc main.o -o main ELF 可执行 解析 printf 等符号，合并各 .o 的段

一步到位：gcc main.c -o main 等价于串联四步。

为什么分这四步有意义

  • 能看每步产物：.i 看宏展开对不对，.s 看生成的汇编，.o 看符号表，链接看符号解析
  • 增量编译的基础：只改一个 .c，只需重做那一个的 .o，再链接——大型项目省巨量时间
  • 跨语言链接：C 和汇编、C 和 C++ 可以各自汇编成 .o 后链接
  • 理解链接错误：undefined reference to xxx 是第 4 阶段符号没找到；不是语法错误，是符号解析失败

验证每阶段产物

gcc -E main.c -o main.i    # 看预处理结果，宏展开是否正确
gcc -S main.i -o main.s     # 看汇编，理解代码生成的机器指令
gcc -c main.s -o main.o     # 生成目标文件
file main.o                  # → "ELF 64-bit LSB relocatable"
gcc main.o -o main           # 链接成可执行
file main                    # → "ELF 64-bit LSB executable"

ELF：链接产物是什么

ELF（Executable and Linkable Format）是 Unix 系可执行文件和 .o 的统一格式。.o 是 ELF Relocatable（段未定位），可执行是 ELF Executable（段已映射到固定虚拟地址）。

ELF 结构简览（详见 ch18）

┌─────────────────┐
│ ELF Header      │  magic (0x7f 'E' 'L' 'F')、入口地址、机器类型
├─────────────────┤
│ Program Headers │  描述运行时如何映射段（text/data/bss）
├─────────────────┤
│ .text           │  机器码（只读、可执行）
│ .rodata         │  字符串字面量、const
│ .data           │  已初始化全局/静态
│ .bss            │  未初始化全局/静态（不占文件空间，运行时清零）
├─────────────────┤
│ Section Headers │  描述每个 section 的位置/大小/属性
├─────────────────┤
│ Symbol Table    │  符号表：函数/全局变量的地址和绑定
├─────────────────┤
│ .strtab         │  符号名字字符串
└─────────────────┘

readelf -h main       # ELF 头：入口地址、机器类型
readelf -S main       # section headers：各段位置大小
readelf -s main       # 符号表：有哪些函数/变量、地址、绑定
objdump -d main       # 反汇编：机器码 → 汇编
nm main               # 符号表简表

学会 readelf/objdump/nm 是看懂 DPDK/内核二进制的必备技能，ch18 系统讲。

链接方式：静态 vs 动态

方式 命令/特点 体积 启动 部署
动态链接（默认） 依赖 libc.so，运行时加载 小 慢（加载 .so、符号重定位） 依赖目标机有同版本库
静态链接 gcc -static main.c -o main 大（库代码全打入） 快 独立，离线部署方便 
gcc main.c -o main           # 动态，默认
gcc -static main.c -o main   # 静态
ls -lh main main-static      # 静态版大一个数量级
ldd main                     # 列动态依赖
ldd main-static               # "not a dynamic executable"

HFT 视角：何时静态、何时动态

  • 静态链接：HFT 离线部署机器、嵌入式无 libc、内核模块（天然静态）、要求启动延迟稳定
  • 动态链接：开发期方便、库版本频繁更新、二进制要小
  • 混合：-Wl,-Bstatic -lc -Wl,-Bdynamic 指定部分库静态、部分动态

链接器在做什么

  1. 符号解析：把每个 .o 里"未定义的符号"（如 printf）和其他 .o/.a/.so 里的"定义"匹配
  2. 重定位：把相对地址换成运行时的绝对虚拟地址
  3. 合并段：把多个 .o 的 .text、.data、.bss 合并成一个
  4. （静态链接）把库代码打进二进制；（动态链接）记下"运行时去 .so 找"

匹配不上就是 undefined reference to xxx——最常见链接错误。

运行与退出码

./main
echo $?          # main 的 return 值（0–255）
  • main 的 return n → exit(n) → _exit(n) syscall → 内核回收 → 父进程 wait() 拿到 n
  • shell 只取低 8 位，所以 return 256 在 $? 里是 0
  • 被信号杀死：$? = 128 + 信号号（如 SIGSEGV=11 → 139）

-g 的本质

  • -g 把 DWARF 调试信息嵌入 ELF：源码行号、变量名、类型、栈帧布局
  • 不开 -g：函数名还在（符号表），但没有行号和局部变量映射——gdb 几乎没法用
  • HFT 工程：开发构建 -g -O0，生产构建常 -g -O2（保留调试信息，不影响运行性能）
  • -O2 + -g：源码和汇编可能错位（优化重排指令），调试要小心

核心调试场景

  1. 段错误定位：gdb ./main → run → 崩溃后 bt 看栈
  2. 逻辑 bug：断点 + print 逐步看变量变化
  3. 指针解引用错：print ptr 看是否 NULL、print *ptr 看指向的值
  4. 多线程：info threads、thread N、break 指定线程（HFT 常用）

Makefile 模板（工程习惯）

CC = gcc
CFLAGS = -Wall -Wextra -Wextra -g

main: main.o
    $(CC) -o $@ $^

main.o: main.c
    $(CC) $(CFLAGS) -c $<

prep:            # 预处理产物
    $(CC) -E main.c -o main.i

asm:             # 汇编产物
    $(CC) -S main.c -o main.s

clean:
    rm -f main main.o main.i main.s

.PHONY: clean prep asm
  • $@ = 目标名，$< = 第一个依赖，$^ = 所有依赖
  • .PHONY 声明"假目标"——同名文件存在时也执行
  • 加 prep/asm 目标方便教学对比四阶段产物
  • DPDK/内核的构建系统（meson/Kbuild）本质也是生成类似的编译/链接命令

  2. readelf -h main 看 ELF 头和入口地址，对比 objdump -d main | grep '<main>' 找到 main 汇编
  3. 对比 main 与 main-static 文件大小（ls -lh），ldd 看依赖差异
  4. gdb 断点 main，print &val 观察栈上地址；info frame 看栈帧
  5. scanf 去掉 &，gdb run + bt 定位崩溃
  6. 仿写循环求和，校验 scanf 返回值，故意制造 undefined reference（删一个函数实现）看链接错误
  7. 加 prep/asm 目标到 Makefile，对比四阶段产物

题目 1： 以下编译命令有什么问题？

gcc -o prog prog.c -lm
# 程序使用了 sqrt() 但没有 #include <math.h>
参考答案

两个问题：(1) 没有 #include ，编译器会对 sqrt() 产生隐式声明警告（C99 前允许，C99 起是错误），返回值默认按 int 处理，而 sqrt 返回 double——结果会被截断。(2) -lm 链接数学库是正确的，但如果头文件没包含，链接成功不代表运行正确。

题目 1： 以下代码在 C 语言中能编译吗？说明了 C 的什么特性？

#include <stdio.h>
int main() {
    printf("hello\n");
}
参考答案

能编译。C 是编译型语言——源代码经过预处理、编译、汇编、链接四个阶段生成可执行文件。这个程序体现了 C 的基本结构：包含头文件、main 函数入口、标准库函数调用。C 的设计哲学是"信任程序员"——它不会像 Java 那样强制检查很多东西。
