补充说明

本节讲什么

本章提到但未展开的主题的速览：变量与类型、存储位置、分支循环、工程规范。每个都是后续章节的引子——本节是"地图概览"，不是详细讲解。目的是让你在读后面章节前，先有一个全局坐标系。

基础类型（极简预览，详见 ch03）

类型 用途 HFT 关注点
char 字符/最小整型 1 字节；signed/unsigned 平台相关
short 短整型 2 字节；省内存用
int 整型（最自然宽度） 4 字节；循环计数、标志位
long 长整型 LP64 下 8 字节；指针/大数
long long 更长整型（C99） 8 字节；时间戳、计数器
float 单精度浮点 4 字节；HFT 几乎不用浮点
double 双精度浮点 8 字节；行情计算偶尔用
void 无类型 函数无返回值/无参声明/void * 通用指针

定宽整型（HFT 必备）

平台相关的 int/long 宽度不一，跨平台代码用 <stdint.h>（C99）：

#include <stdint.h>
int8_t   x;    /* 恰好 8 位有符号 */
uint32_t y;    /* 恰好 32 位无符号 */
int64_t  z;    /* 恰好 64 位有符号 */
  • DPDK/内核/HFT 代码大量用 uint32_t/uint64_t——宽度确定，行为可预测
  • size_t：sizeof 的返回类型，足以容纳任何对象大小（64 位下 8 字节）
  • ptrdiff_t：两指针相减的类型
  • 详见 ch03.1。

存储位置：内存布局速览

程序加载后，不同变量住在内存的不同区域：

高地址
┌──────────────┐
│ 栈 stack ↓    │  局部自动变量、函数调用帧
│              │  生命周期：函数返回即销毁
├──────────────┤
│ (空闲，向下生长)│
├──────────────┤
│ 堆 heap ↑    │  malloc/calloc 分配
│              │  生命周期：free 才回收
├──────────────┤
│ .bss         │  未初始化全局/静态，启动时清零
├──────────────┤
│ .data        │  已初始化全局/静态
├──────────────┤
│ .rodata      │  字符串字面量、const 全局（只读，写→SIGSEGV）
├──────────────┤
│ .text        │  机器码（只读、可执行）
└──────────────┘
低地址
声明方式 落在 生命周期 初始化
int x;（函数内） 栈 函数返回即销毁 未初始化（值不定，UB 读取）
static int x;（函数内/外） .bss/.data 整个进程 默认 0
int x;（函数外，全局） .bss/.data 整个进程 默认 0
int x = 5;（全局） .data 整个进程 5
malloc(sizeof(int)) 堆 free 才回收 未初始化
calloc(...) 堆 free 才回收 清零
"hello"（字符串字面量） .rodata 整个进程 "hello"，只读

踩坑：栈上大数组

void f(void) {
    char buf[1024 * 1024];   /* 1MB 局部数组 */
    /* ... */
}
  • 栈默认 8MB（ulimit -s 查看），1MB 数组 + 函数调用链 → 可能溢出 → SIGSEGV
  • DPDK/嵌入式：在 worker 栈小的场景更危险
  • 解法：大缓冲改 static（全局）或 malloc（堆）

踩坑：返回栈变量地址

int *bad(void) {
    int x = 42;
    return &x;   /* 悬垂指针！函数返回后 x 被销毁 */
}

栈帧在函数返回后被回收，返回的地址指向已失效的内存——读取是 UB，可能拿到垃圾值，可能恰好正常数月后崩溃。详见 ch06/ch11。

-Wall -Wextra -Werror 为什么是铁律

选项 作用 不开的后果
-Wall 常见问题警告（未用变量、= 写成 ==、格式串不匹配） 这些 bug 潜伏数月才爆发
-Wextra 更严格的额外警告（空参 ()、隐式转换） 默默引入可移植性 bug
-Werror 警告当错误，编译直接失败 警告被忽略，逐渐积累成系统性问题

HFT/内核代码库几乎都 -Werror。开发时嫌烦可以临时 -Wno-error=xxx，但提交前必须清零。

常见误区

误区 纠正
int 到处是 4 字节 LP64/ILP64/LLP64 模型下 long 宽度不同；定宽用 stdint.h
局部变量默认清零 只有 .bss 的全局/静态清零；局部自动变量不清零，读取是 UB
malloc 返回的内存清零 malloc 不清零，要清零用 calloc 或 memset
字符串字面量可修改 在 .rodata，修改是 UB，通常 SIGSEGV
栈很大随便用 默认 8MB，大数组/深递归容易溢出
void main() 也行 非标准，见 1.1.3

代码自测

题目 1： 以下代码在 32 位和 64 位系统上输出可能不同，为什么？

printf("%d\n", sizeof(int *));
参考答案

32 位系统上指针大小通常是 4 字节，64 位系统通常是 8 字节。sizeof 返回 size_t 类型，用 %d 打印在 64 位系统上可能截断（因为 size_t 是 8 字节而 %d 只读 4 字节）。正确做法是用 %zu（C99）或强制转换为 unsigned long 配合 %lu。

编译

本节讲什么

Linux 下完整编译四阶段 + 运行、退出码、gdb 入门 + Makefile 工程模板。这一节是 ch01 的重头戏，是后续 DPDK/内核构建系统的缩影；链接产物 ELF 是 ch18 运行时环境的前置。掌握这一节，你就有了一套从源码到运行的可操作工具链。

编译四阶段（本章重中之重）

一个 .c 变成可执行文件，经历四个独立阶段，每个阶段都有对应的 gcc 选项：

阶段 命令 产物 作用
1. 预处理 gcc -E main.c -o main.i .i（纯 C 文本） 展开 #include/#define，删注释，处理 #ifdef
2. 编译 gcc -S main.i -o main.s .s（汇编文本） 语法分析、语义检查、优化、生成汇编
3. 汇编 gcc -c main.s -o main.o .o（ELF 可重定位） 翻译汇编成机器码，符号未解析
4. 链接 gcc main.o -o main ELF 可执行 解析 printf 等符号，合并各 .o 的段

一步到位：gcc main.c -o main 等价于串联四步。

为什么分这四步有意义

  • 能看每步产物：.i 看宏展开对不对，.s 看生成的汇编，.o 看符号表，链接看符号解析
  • 增量编译的基础：只改一个 .c，只需重做那一个的 .o，再链接——大型项目省巨量时间
  • 跨语言链接：C 和汇编、C 和 C++ 可以各自汇编成 .o 后链接
  • 理解链接错误：undefined reference to xxx 是第 4 阶段符号没找到；不是语法错误，是符号解析失败

验证每阶段产物

gcc -E main.c -o main.i    # 看预处理结果，宏展开是否正确
gcc -S main.i -o main.s     # 看汇编，理解代码生成的机器指令
gcc -c main.s -o main.o     # 生成目标文件
file main.o                  # → "ELF 64-bit LSB relocatable"
gcc main.o -o main           # 链接成可执行
file main                    # → "ELF 64-bit LSB executable"

ELF：链接产物是什么

ELF（Executable and Linkable Format）是 Unix 系可执行文件和 .o 的统一格式。.o 是 ELF Relocatable（段未定位），可执行是 ELF Executable（段已映射到固定虚拟地址）。

ELF 结构简览（详见 ch18）

┌─────────────────┐
│ ELF Header      │  magic (0x7f 'E' 'L' 'F')、入口地址、机器类型
├─────────────────┤
│ Program Headers │  描述运行时如何映射段（text/data/bss）
├─────────────────┤
│ .text           │  机器码（只读、可执行）
│ .rodata         │  字符串字面量、const
│ .data           │  已初始化全局/静态
│ .bss            │  未初始化全局/静态（不占文件空间，运行时清零）
├─────────────────┤
│ Section Headers │  描述每个 section 的位置/大小/属性
├─────────────────┤
│ Symbol Table    │  符号表：函数/全局变量的地址和绑定
├─────────────────┤
│ .strtab         │  符号名字字符串
└─────────────────┘

readelf -h main       # ELF 头：入口地址、机器类型
readelf -S main       # section headers：各段位置大小
readelf -s main       # 符号表：有哪些函数/变量、地址、绑定
objdump -d main       # 反汇编：机器码 → 汇编
nm main               # 符号表简表

学会 readelf/objdump/nm 是看懂 DPDK/内核二进制的必备技能，ch18 系统讲。

链接方式：静态 vs 动态

方式 命令/特点 体积 启动 部署
动态链接（默认） 依赖 libc.so，运行时加载 小 慢（加载 .so、符号重定位） 依赖目标机有同版本库
静态链接 gcc -static main.c -o main 大（库代码全打入） 快 独立，离线部署方便 
gcc main.c -o main           # 动态，默认
gcc -static main.c -o main   # 静态
ls -lh main main-static      # 静态版大一个数量级
ldd main                     # 列动态依赖
ldd main-static               # "not a dynamic executable"

HFT 视角：何时静态、何时动态

  • 静态链接：HFT 离线部署机器、嵌入式无 libc、内核模块（天然静态）、要求启动延迟稳定
  • 动态链接：开发期方便、库版本频繁更新、二进制要小
  • 混合：-Wl,-Bstatic -lc -Wl,-Bdynamic 指定部分库静态、部分动态

链接器在做什么

  1. 符号解析：把每个 .o 里"未定义的符号"（如 printf）和其他 .o/.a/.so 里的"定义"匹配
  2. 重定位：把相对地址换成运行时的绝对虚拟地址
  3. 合并段：把多个 .o 的 .text、.data、.bss 合并成一个
  4. （静态链接）把库代码打进二进制；（动态链接）记下"运行时去 .so 找"

匹配不上就是 undefined reference to xxx——最常见链接错误。

运行与退出码

./main
echo $?          # main 的 return 值（0–255）
  • main 的 return n → exit(n) → _exit(n) syscall → 内核回收 → 父进程 wait() 拿到 n
  • shell 只取低 8 位，所以 return 256 在 $? 里是 0
  • 被信号杀死：$? = 128 + 信号号（如 SIGSEGV=11 → 139）

详见 1.1.3 和 ch18。

gdb 入门

gcc -g main.c -o main        # -g 保留调试符号（DWARF）
gdb ./main
命令 作用 使用场景
list / l 看源码 定位断点
break main / b main 设断点 程序暂停在指定函数
break 12 在第 12 行断点 行级断点
run / r 运行到断点 启动调试
next / n 单步（不进函数） 逐步执行
step / s 单步（进入函数） 进入子函数
print val / p val 打印变量值 查看状态
print &val 打印地址 衔接 & 取地址
print *ptr 解引用打印 指针指向的值
bt / backtrace 调用栈 崩溃后定位
info registers 寄存器 底层调试
x/10gx $rsp 查看栈内存 看栈帧（ch18）
quit / q 退出 —

-g 的本质

  • -g 把 DWARF 调试信息嵌入 ELF：源码行号、变量名、类型、栈帧布局
  • 不开 -g：函数名还在（符号表），但没有行号和局部变量映射——gdb 几乎没法用
  • HFT 工程：开发构建 -g -O0，生产构建常 -g -O2（保留调试信息，不影响运行性能）
  • -O2 + -g：源码和汇编可能错位（优化重排指令），调试要小心

核心调试场景

  1. 段错误定位：gdb ./main → run → 崩溃后 bt 看栈
  2. 逻辑 bug：断点 + print 逐步看变量变化
  3. 指针解引用错：print ptr 看是否 NULL、print *ptr 看指向的值
  4. 多线程：info threads、thread N、break 指定线程（HFT 常用）

Makefile 模板（工程习惯）

CC = gcc
CFLAGS = -Wall -Wextra -Wextra -g

main: main.o
    $(CC) -o $@ $^

main.o: main.c
    $(CC) $(CFLAGS) -c $<

prep:            # 预处理产物
    $(CC) -E main.c -o main.i

asm:             # 汇编产物
    $(CC) -S main.c -o main.s

clean:
    rm -f main main.o main.i main.s

.PHONY: clean prep asm
  • $@ = 目标名，$< = 第一个依赖，$^ = 所有依赖
  • .PHONY 声明"假目标"——同名文件存在时也执行
  • 加 prep/asm 目标方便教学对比四阶段产物
  • DPDK/内核的构建系统（meson/Kbuild）本质也是生成类似的编译/链接命令

专属价值（嵌入式 + HFT + DPDK）

  1. DPDK/内核模块构建本质同四阶段——看懂 meson/Makefile 不迷茫，因为底层就是 gcc -c + 链接
  2. 链接产物 ELF —— 行情程序、内核镜像、DPDK 应用同格式（ch18）
  3. gdb 是交易偶发崩溃、驱动内存损坏的核心工具——core dump 配合 bt 定位
  4. 静态 vs 动态影响启动延迟与部署依赖——HFT 选型常因这点
  5. 链接错误 undefined reference —— 看懂是符号解析失败，知道去哪找实现

常见误区

误区 纠正
"编译就一步" 是四步，能分阶段看产物是调试和优化的基础
.o 可以直接运行 .o 是可重定位，符号未解析，不能直接执行
undefined reference 是语法错误 是链接阶段的符号解析失败，不是编译错误
改了头文件不用重编 头是文本插入，所有依赖它的 .c 都要重编
-O2 和 -g 冲突 可以共存，但优化后源码行号可能不准
ldd 列的是编译时依赖 是运行时动态库依赖，目标机要都有
静态链接总是更好 体积大、库 bug 更新要重编；各有适用场景

实操清单

  1. 分别执行 -E/-S/-c，查看 .i / .s / .o（file main.o 看 ELF relocatable）
  2. readelf -h main 看 ELF 头和入口地址，对比 objdump -d main | grep '<main>' 找到 main 汇编
  3. 对比 main 与 main-static 文件大小（ls -lh），ldd 看依赖差异
  4. gdb 断点 main，print &val 观察栈上地址；info frame 看栈帧
  5. scanf 去掉 &，gdb run + bt 定位崩溃
  6. 仿写循环求和，校验 scanf 返回值，故意制造 undefined reference（删一个函数实现）看链接错误
  7. 加 prep/asm 目标到 Makefile，对比四阶段产物

代码自测

题目 1： 以下编译命令有什么问题？

gcc -o prog prog.c -lm
# 程序使用了 sqrt() 但没有 #include <math.h>
参考答案

两个问题：(1) 没有 #include ，编译器会对 sqrt() 产生隐式声明警告（C99 前允许，C99 起是错误），返回值默认按 int 处理，而 sqrt 返回 double——结果会被截断。(2) -lm 链接数学库是正确的，但如果头文件没包含，链接成功不代表运行正确。

题目 1： 以下代码在 C 语言中能编译吗？说明了 C 的什么特性？

#include <stdio.h>
int main() {
    printf("hello\n");
}
参考答案

能编译。C 是编译型语言——源代码经过预处理、编译、汇编、链接四个阶段生成可执行文件。这个程序体现了 C 的基本结构：包含头文件、main 函数入口、标准库函数调用。C 的设计哲学是"信任程序员"——它不会像 Java 那样强制检查很多东西。
