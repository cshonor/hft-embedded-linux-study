9.1

字符串基础

本节讲什么

C 字符串的定义只有一个约定：一段连续的 char，以 '\0'（值为 0 的字节）作为唯一结束标志。这个看似简单的约定是整个 <string.h> API 族的根基，也是 HFT/网络报文场景无数漏洞的源头——因为真实报文里 0x00 是合法数据字节，不是终止符。

二进制字节流则相反：边界由显式长度 pkt_len 决定，0x00 可以出现在任意位置。这两种数据模型互不兼容，混用即 UB。本章的核心主线就是划清这条界线。

历史背景

C 字符串约定继承自 1969 年 B 语言（Dennis Ritchie 在 PDP-7 上设计）。当时内存以字节编址、CPU 慢、无专门字符串指令，用 0 作为哨兵让扫描循环只需一条 cmpb $0,(%rax) 即可判定结束，无需维护长度字段。这个取舍在 1970s 合理，但在 2020s 的二进制协议场景成了系统性风险——Heartbleed（CVE-2014-0160）、 countless buffer overflows 都源于把 C 字符串 API 套到二进制数据上。

要点

内存布局

char str[] = "quote";   /* 'q''u''o''t''e''\0' → 6 字节 */

偏移  0    1    2    3    4    5
     +----+----+----+----+----+----+
     | q  | u  | o  | t  | e  | \0 |
     +----+----+----+----+----+----+
       0x71 0x75 0x6f 0x74 0x65 0x00
  • strlen("quote") = 5（不含 \0）
  • sizeof(str) = 6（数组总字节，含 \0）
  • str[5] == '\0'，str[6] 越界 UB

两种存储模型

char pkt_buf[128] = "order";      /* 数组，在栈/堆，可写 */
const char *proto = "heartbeat";  /* 指针，指向 .rodata 字面量 */
模型 存储位置 可写性 修改后果
char arr[] = "..." 栈/堆（拷贝） 可写 正常
const char *p = "..." .rodata 段 不可写 SIGSEGV（或 UB）

字面量 "heartbeat" 存放在 .rodata 段，由编译器合并相同字面量以节省空间（-fmerge-constants，默认开启）。修改字面量在带 NX 页保护的系统上触发段错误，在不带保护的嵌入式系统上是静默踩踏其他字面量。

$ gcc -O2 strlit.c -o strlit
$ objdump -s -j .rodata strlit   # 可见 "heartbeat" 仅一份

C 字符串 vs 二进制字节流

维度 C 字符串 二进制 buf
边界 第一个 \0 pkt_len 显式
0x00 字节 表示结束 合法数据
典型 API str* / printf %s mem* / read(fd, buf, n)
长度获取 strlen（O(n) 扫描） 已知字段，O(1)
长度上限 无内置 显式 size_t len
适用场景 文本、日志、命令行 网络报文、文件 I/O、序列化

关键铁律：DPDK mbuf payload、TCP 报文、FIX/SBE 编码字段、protobuf 二进制序列——全部用 uint8_t * + len，禁止 char * + \0。

遍历范式预告

/* 文本日志：扫到 \0 停 */
for (char *p = line; *p; p++) { /* ... */ }

/* 二进制 payload：扫到 end 停（9.9） */
uint8_t *p = payload, *end = p + pkt_len;
for (; p < end; p++) { /* ... */ }

后者是 HFT 报文解析的标准范式，end 是上界指针，即使中间出现 0x00 也继续解析。

HFT 关联

  • 报文偏移模型：DPDK rte_pktmbuf_mtod(m, uint8_t *) 返回的 payload 是二进制，长度由 rte_pktmbuf_data_len(m) 给出，绝不用 %s 打印
  • FIX/SBE：定长字段靠 offset + length，变长字段靠 length prefix，没有任何字段以 \0 终止
  • 日志格式化：可读日志里用 C 字符串，但日志 payload 本身（写入 ring/logfile）是 mem*
  • 协议头魔数：如 Ethernet 0xAAAAAAAAAAAA 前导、IP 0x45 版本+IHL，用 memcmp 比对，不是 strcmp
  • 配置文件：键值对文本可用 str*，但解析后转结构体字段，运行时不再碰字符串

9.2

字符串长度

本节讲什么

strlen(s) 与 sizeof(x) 是 C 字符串最高频的踩坑点，根因是二者语义完全不同但常被新手混用：前者是运行时函数，扫描到 \0 才停；后者是编译期运算符，求的是变量占用的字节数。混淆这两者在二进制报文场景会直接导致越界读或长度计算错误。

要点

核心区别

函数/运算符 含义 求值时机 含 \0？ 适用对象
strlen(s) 第一个 \0 前的字符数 运行时（O(n) 扫描） 否 C 字符串（必须含 \0）
sizeof(x) 对象占用的字节数 编译时 是（char 数组） 任意对象或类型

实例对比

char a[] = "quote";   /* 6 字节的数组：'q''u''o''t''e''\0' */
strlen(a);    /* 5 —— 扫描到 a[5] 的 \0 停 */
sizeof(a);    /* 6 —— 编译期数组大小 */

char *p = a;        /* 指针，指向数组首元素 */
strlen(p);    /* 5 —— 仍扫描内容 */
sizeof(p);    /* 8（x86-64）—— 指针本身宽度，与字符串无关 */

sizeof(p) == 8 而非 6，这是指针退化的典型表现（ch08 已详述）：数组名 a 作为 sizeof 操作数时不退化，但赋给指针 p 后 p 只是一个 8 字节的指针变量，sizeof(p) 求的是指针本身的大小，与它指向什么无关。

strlen 的实现与复杂度

glibc 的 strlen 用 SIMD（SSE2/AVX2）一次比对 16/32 字节，但仍必须扫到 \0 才返回，最坏 O(n)。在热路径上反复调用 strlen(s) 是经典性能陷阱：

/* 反例：每轮循环都重新 strlen */
for (size_t i = 0; i < strlen(s); i++) { /* ... */ }  /* O(n^2) */

/* 正例：缓存长度 */
size_t n = strlen(s);
for (size_t i = 0; i < n; i++) { /* ... */ }           /* O(n) */

致命风险：缓冲无 \0 → 越界读 UB

char buf[5] = { 'a', 'b', 'c', 'd', 'e' };  /* 无 \0 */
strlen(buf);   /* UB：扫描越过 buf，直到碰巧遇到 0x00 */
  • 栈上紧邻数据可能很快遇到 0，结果"看起来正常"
  • ASan 会报 stack-buffer-overflow
  • 二进制报文里 pkt_len 字段给出的字节流常常不含 \0，调 strlen 直接越界

安全替代：strnlen

POSIX 的 strnlen(s, maxlen) 最多扫描 maxlen 字节，找到 \0 或扫满 maxlen 即返回，有上界：

size_t len = strnlen(maybe_unterminated, sizeof(buf));

注意 MSVC 早期版本不支持 strnlen，跨平台代码需自写：

size_t my_strnlen(const char *s, size_t max) {
    size_t i = 0;
    while (i < max && s[i]) i++;
    return i;
}

二进制报文：始终显式 size_t len

HFT/DPDK 的报文长度永远不要靠 strlen 推断：

/* DPDK 报文：长度由 mbuf 元数据给出 */
size_t pkt_len = rte_pktmbuf_data_len(m);
uint8_t *p = rte_pktmbuf_mtod(m, uint8_t *);
/* 后续操作用 p 和 pkt_len，禁止 strlen(p) */

报文长度来自 IP 头 total_length 字段或 TCP 段长度，是协议字段而非字符串属性。

HFT 关联

  • FIX tag-value：变长字段靠 len prefix（SOH 分隔但 SOH=0x01 不是 \0），strlen 仍可用但效率低，生产解析器用偏移表
  • SBE 定长字段：长度由 schema 编译期确定，运行时根本不调 strlen
  • 日志缓冲：构建可读日志时 strlen(buf) 算 offset 是常见操作，但要确保 buf 始终 \0 终止（snprintf 自动补）
  • 性能：glibc strlen 在 64 字节内约 5-10 ns，但若每包调 10 次累计 50-100 ns，对 100ns 级 HFT 路径不可忽视
  • ASan 工程铁律：所有报文处理路径在 ASan 下必须零 stack-buffer-overflow 报错，否则上线即定时炸弹

9.3

不受限制的字符串函数

本节讲什么

<string.h> 中依赖 '\0' 作为扫描终点的经典函数族：strcpy、strcat、strcmp、strlen、strchr、strstr 等。它们没有任何长度参数，扫描到 \0 才停，因此得名"不受限制"（unrestricted）。这族函数是 UNIX 文本处理传统的产物，在文本场景尚可用（前提是数据确实 \0 终止），但在二进制报文场景是高危 API，生产环境基本禁用。

本章后续小节逐一展开各函数的细节，本节是总览。

要点

函数清单

函数 作用 返回值 风险等级
strcpy(dst, src) 拷贝 src（含 \0）到 dst dst 致命：dst 溢出
strcat(dst, src) 在 dst 末尾追加 src dst 致命：dst 溢出
strcmp(s1, s2) 字典序比较 <0/0/>0 低（只读）
strlen(s) 长度 size_t 中：无 \0 越界读
strchr(s, c) 查找字符 位置指针或 NULL 中：依赖 \0
strstr(s, sub) 查找子串 位置指针或 NULL 中：依赖 \0

共性特征

  1. 无长度参数：扫描边界完全由 \0 决定
  2. \0 必须存在：缓冲无 \0 → 越界读 UB
  3. 写函数不检查 dst 容量：strcpy/strcat 不知道 dst 多大
  4. 仅适用于 C 字符串：二进制数据含 0x00 时语义被破坏
  5. 多数返回 dst：便于链式写法，但也容易让人忽略返回值检查

与 mem* 系列的根本区别

维度 str* mem*
边界 \0 终止 显式 n 字节
0x00 处理 终止扫描 合法数据
长度参数 无 必须有
二进制适用 否 是
典型场景 文本、日志、命令行 报文、内存块、struct
HFT 角色 辅助（日志/配置） 主力

历史背景

这族函数源自 1970s UNIX V6/V7 的 <strings.h>，当时 C 还没有 size_t（1979 年 K&R 时期），字符串就是字符数组+哨兵的代名词。ANSI C89 将其标准化进 <string.h> 并新增了 strn* 限长版（9.4）。但 strn* 仍依赖 \0 语义，不是真正的二进制安全 API。

工程规范分层

场景 推荐 API 理由
文本日志、命令行参数 str* 可用，但优先 snprintf 数据有 \0，但仍需防溢出
配置文件解析 snprintf / strlcpy 数据有 \0，但用户输入不可信
二进制报文、mbuf payload mem* + len（9.9） 数据可能含 0x00
结构体字段拷贝 memcpy + sizeof 二进制语义，长度编译期已知
跨线程共享 避免 strerror/strtok 非线程安全（9.6/9.7）

典型漏洞模式

/* 经典栈溢出：strcpy 不检查 dst 大小 */
void bad(char *user_input) {
    char buf[16];
    strcpy(buf, user_input);   /* user_input > 15 字节即溢出 */
}

这正是 Morris 蠕虫（1986）、Code Red（2001）、无数 CVE 的根因。现代编译器在 -O2 -D_FORTIFY_SOURCE=2 下会对已知大小的 strcpy 插入边界检查，但仅限编译期能推断大小的场景，动态缓冲仍无保护。

编译期硬化选项

gcc -O2 -D_FORTIFY_SOURCE=2 -fstack-protector-strong ...
  • -D_FORTIFY_SOURCE=2：让 glibc 的 strcpy/memcpy 等在编译期能推断大小时插入 __strcpy_chk，运行时检测溢出
  • -fstack-protector-strong：栈 canary，防栈溢出覆盖返回地址
  • 但不替代正确的 API 选择——mem* + len 才是根治

HFT 关联

  • DPDK rte_memcpy：基于 memcpy 的优化版，按对齐和长度选择 SIMD 路径，HFT 报文拷贝主力
  • FIX 解析：tag-value 用 SOH(0x01) 分隔，不是 \0，所以 strtok(s, "\x01") 可用但低效，生产用偏移表
  • 日志拼接：rte_log 内部用 snprintf，不用 strcat
  • 协议头比较：Ethernet/IP/TCP 头部用 memcmp，不用 strcmp
  • 配置字符串：rte_eal_init 的 argv 是 C 字符串，可用 str*，但解析后转结构体

9.3

.1 复制字符串

本节讲什么

strcpy(dst, src) 是 C 字符串复制函数的"原始版"：从 src 逐字节拷贝到 dst，直到遇到 \0（含 \0 本身），完全不检查 dst 容量。它是 C 标准库里最高危的函数之一，几乎所有缓冲区溢出 CVE 的教科书案例都涉及 strcpy。本节剖析其机制、风险与替代方案。

要点

函数原型与行为

char *strcpy(char *dst, const char *src);
  • 从 src 拷贝到 dst，含终止 \0
  • 返回 dst（链式写法用）
  • 不检查 dst 大小——若 strlen(src) + 1 > sizeof(dst)，溢出 UB
  • 若 src 与 dst 重叠 → UB（应用 memmove）

简化实现

char *strcpy(char *dst, const char *src) {
    char *ret = dst;
    while ((*dst++ = *src++)) /* 括号内赋值，遇 \0 退出 */
        ;
    return ret;
}

整行就一个 while 头，C 代码 golf 的典范。但简洁背后是零防御。

汇编视角（x86-64）

strcpy:
    mov    rax, rdi            ; 保存 dst 作为返回值
.L1:
    movzx  edx, BYTE PTR [rsi] ; 读 src 字节
    mov    BYTE PTR [rdi], dl  ; 写 dst
    inc    rsi
    inc    rdi
    test   dl, dl              ; 是否 \0？
    jne    .L1                 ; 非零继续
    ret

glibc 实际用 SSE2/AVX2 一次比对 16/32 字节，但仍必须扫到 \0——SIMD 只是加速，不改变语义。

风险等级

风险 说明 后果
dst 溢出 dst 小于 src+1 栈/堆踩踏，控制流劫持
src 无 \0 越界读 src UB，可能泄露相邻内存（Heartbleed 模式）
重叠 dst 与 src 重叠 UB，结果不可预测
二进制 src 含 0x00 的报文 提前截断，语义错误

替代方案对比

/* 1. strncpy：限长但仍危险 —— 不保证补 \0 */
strncpy(dst, src, sizeof(dst) - 1);
dst[sizeof(dst) - 1] = '\0';   /* 必须手动补 */

/* 2. snprintf：安全，总是补 \0 */
snprintf(dst, sizeof dst, "%s", src);

/* 3. strlcpy：BSD/内核，返回需写总长，便于检测截断 */
strlcpy(dst, src, sizeof(dst));   /* 返回 strlen(src) */

/* 4. strscpy：Linux 内核 2016 引入，返回 -E2BIG 表示截断 */
strscpy(dst, src, sizeof(dst));

/* 5. memcpy：二进制，显式 n，HFT 首选 */
memcpy(dst, src, n);   /* n 已知，与 \0 无关 */

strncpy 的两个坑

char buf[8];
strncpy(buf, "hello world", sizeof(buf));
/* buf = {'h','e','l','l','o',' ','w','o'} —— 无 \0！ */
printf("%s", buf);   /* UB：越界读直到碰巧 \0 */
  1. src 长 ≥ n 时不补 \0——必须手动 buf[n-1]='\0'
  2. src 短时填充 \0 到 n 字节——浪费 CPU，strlcpy 不做这种填充

strlcpy 的优势（OpenBSD 1996）

size_t strlcpy(char *dst, const char *src, size_t dstsize);
  • 拷贝至多 dstsize-1 字节，总是补 \0
  • 返回 strlen(src)，便于调用方判断是否截断（if (ret >= dstsize) /* 截断 */）
  • 不做 strncpy 那种无意义填充
  • Linux 2016 年（4.3 起）引入内核，glibc 2.38（2023）终于加入用户态

实操：strcpy vs memcpy 对含 0x00 数据

uint8_t raw[] = { 'A', 'B', 0x00, 'C', 'D' };
char a[8], b[8];

strcpy(a, (const char *)raw);   /* a = "AB\0" —— 截断在 0x00 */
memcpy(b, raw, sizeof raw);     /* b = {'A','B',0,'C','D',0,0,0} —— 完整 */

strcpy 看到第三个字节 0x00 就停，丢失了 CD；memcpy 按 n=5 完整拷贝。这是 C 字符串与二进制字节流的本质区别。

HFT 关联

  • DPDK rte_memcpy：基于 memcpy 的优化版，按对齐和长度选择 SSE/AVX 路径，4-64 字节范围比 glibc memcpy 快 1.5-3 倍，HFT 报文拷贝主力
  • 报文头部拷贝：memcpy(hdr, pkt, sizeof(hdr)) 长度编译期已知，-O2 下常被展开为寄存器移动
  • 配置字符串拷贝：rte_eal_init 的 argv 处理可用 strlcpy，但运行时配置结构体字段拷贝用 memcpy + sizeof
  • FIX tag 拷贝：变长字段用 memcpy(dst, src, field_len)，field_len 由解析器算出
  • 严禁：在 mbuf payload 上调 strcpy——payload 可能含 0x00 且无 \0 终止

漏洞案例：Morris 蠕虫（1986）

fingerd 服务用 strcpy 拷贝用户输入到栈缓冲，Morris 蠕虫构造超长输入覆盖返回地址，感染约 6000 台机器（当时互联网的 10%）。这是 strcpy 漏洞的"零号病人"，直接催生了 CERT/CC。

漏洞案例：Heartbleed（2014）

OpenSSL 用 memcpy 但用了攻击者控制的长度而非真实长度，等价于"带了长度参数的 strcpy 溢出"。教训：长度参数本身必须来自可信源，不能信任协议字段。

9.3

.2 连接字符串

本节讲什么

strcat(dst, src) 在 dst 末尾的 \0 处追加 src（含新 \0）。它本质是"先 strlen(dst) 再 strcpy"，继承 strcpy 的所有溢出风险，且多一次扫描。本节剖析其机制、性能陷阱与安全替代。

要点

函数原型与行为

char *strcat(char *dst, const char *src);
  • 找到 dst 中第一个 \0，从该位置开始拷贝 src（含 \0）
  • 返回 dst
  • 不检查 dst 容量——若 strlen(dst) + strlen(src) + 1 > sizeof(dst)，溢出 UB
  • dst 必须已 \0 终止，否则 strcat 越界找末尾——UB on UB

简化实现

char *strcat(char *dst, const char *src) {
    char *p = dst;
    while (*p) p++;           /* 扫到 dst 末尾 \0 */
    while ((*p++ = *src++))   /* 从 \0 位置开始拷 src */
        ;
    return dst;
}

两次扫描：先扫 dst 找末尾，再扫 src 拷贝。复杂度 O(strlen(dst) + strlen(src))。

性能陷阱：链式 strcat 是 O(n²)

/* 反例：每次 strcat 都重新扫描整个已构建字符串 */
char buf[1024] = "";
for (int i = 0; i < argc; i++) {
    strcat(buf, argv[i]);      /* 第 i 次扫描 strlen(buf) 次 */
    strcat(buf, " ");
}
/* 总扫描次数 ≈ Σstrlen(buf_i) ≈ O(n²) */

正确范式：维护一个 offset 指针，O(n) 完成：

char buf[1024];
char *p = buf;
char *end = buf + sizeof(buf);
for (int i = 0; i < argc && p < end; i++) {
    int n = snprintf(p, end - p, "%s ", argv[i]);
    if (n < 0) break;
    p += (n < end - p) ? n : (end - p - 1);  /* 截断保护 */
}

替代方案对比

/* 1. strncat：限长但仍需保证 dst 容量，且 n 是 src 最多追加字符数 */
strncat(dst, src, sizeof(dst) - strlen(dst) - 1);
/* 注意：strncat 自己补 \0，n 不含 \0 */

/* 2. snprintf + offset：安全，推荐 */
size_t off = strlen(dst);
snprintf(dst + off, sizeof(dst) - off, "%s", piece);

/* 3. strlcat：BSD，返回尝试的总长度，便于检测截断 */
strlcat(dst, src, sizeof(dst));

/* 4. memcpy + offset：二进制，HFT 首选 */
size_t off = /* 已知 */;
memcpy(dst + off, src, piece_len);
off += piece_len;

strncat 的微妙之处

char d[8] = "abc";
strncat(d, "defghij", 3);
/* d = "abcdef\0?" —— 追加最多 3 字符，再补 \0，共写 4 字节 */
  • n 是最多从 src 取的字符数，不含 \0
  • strncat 总是在结果末尾补 \0
  • 所需 dst 容量 = strlen(dst) + min(strlen(src), n) + 1
  • 与 strncpy 不补 \0 形成对比——同族函数行为不一致，是 C 标准库的著名坑

重叠 UB

char s[10] = "abc";
strcat(s, s);   /* UB：src 与 dst 重叠 */

需要重叠操作时用 memmove（9.9）。

HFT 关联

  • 日志拼接：DPDK rte_log 内部用 vsnprintf，不用 strcat——格式化一次完成
  • 报文组装：构建 FIX 报文时用 memcpy + offset 累加，每段长度已知
  • 配置字符串拼接：snprintf 链式写入是标准范式
  • 性能：在 100ns 级热路径上任何 strcat 都是性能 bug——多一次 strlen 扫描就是 5-30ns
  • SBE 编码：长度编译期已知，直接 memcpy 到偏移位置，零扫描

实操：strcat 链 vs snprintf 链

/* 反例：1000 次 strcat，每次扫描越来越长 */
char buf[8192] = "";
for (int i = 0; i < 1000; i++)
    strcat(buf, "x");      /* 总扫描 O(1+2+...+1000) = O(500500) */

/* 正例：维护 offset */
char buf[8192];
size_t off = 0;
for (int i = 0; i < 1000 && off < sizeof(buf) - 1; i++)
    buf[off++] = 'x';
buf[off] = '\0';           /* 总写入 O(1000) */

实测在 1KB 字符串上，前者比后者慢 500 倍。

9.3

.3 函数的返回值

本节讲什么

<string.h> 各函数的返回值语义并不统一：写函数（strcpy/strcat/memcpy）多返回 dst（第一参数的副本），便于链式写法；查找函数（strchr/strstr）返回位置指针或 NULL；比较函数（strcmp/memcmp）返回 int。理解这些语义是正确使用 API、避免 NULL 解引用 UB 的前提。

要点

返回值语义总表

函数 返回值 含义 可能为 NULL？
strcpy(dst, src) dst 第一参数副本 否（除非 dst 本身为 NULL，UB）
strcat(dst, src) dst 第一参数副本 否（同上）
strncpy(dst, src, n) dst 第一参数副本 否
strncat(dst, src, n) dst 第一参数副本 否
strlen(s) size_t 长度 —
strcmp(s1, s2) <0/0/>0 字典序差 —
strncmp(...) <0/0/>0 限长字典序差 —
strchr(s, c) 指针或 NULL 找到则位置，否则 NULL 是
strrchr(s, c) 指针或 NULL 反向查找 是
strstr(s, sub) 指针或 NULL 子串位置 是
strpbrk(s, set) 指针或 NULL 字符集中任一字符位置 是
memcpy(dst, src, n) dst 第一参数副本 否
memmove(dst, src, n) dst 第一参数副本 否
memset(dst, c, n) dst 第一参数副本 否
memcmp(a, b, n) <0/0/>0 字节序差 —
memchr(s, c, n) 指针或 NULL 在前 n 字节中查找 是

返回 dst 的设计意图：链式写法

char buf[64];
size_t n = strlen(strcat(strcpy(buf, "ts="), "12345"));
/* 等价于：
 *   strcpy(buf, "ts=");
 *   strcat(buf, "12345");
 *   n = strlen(buf);
 */

这种链式风格源自 1970s UNIX 早期 C 代码，当时看起来优雅，但现代工程实践不推荐：

  • 可读性差，调试断点难放
  • 一旦中间步骤出错（如 strcat 溢出），后续操作放大错误
  • 编译器优化后链式与分步无性能差异

推荐范式：分步写，每步结果可检查。

查找函数的 NULL 陷阱

char *p = strchr(line, '=');
*p = '\0';   /* 若 line 无 '='，p == NULL，这里 SIGSEGV */

铁律：查找函数返回值必须先判 NULL再解引用：

char *p = strchr(line, '=');
if (p) {
    *p = '\0';
    value = p + 1;
} else {
    /* 无等号，处理错误或跳过 */
}

strcmp 返回值的细节

int r = strcmp("abc", "abd");
/* r < 0，但具体值不保证是 -1 */
  • 返回值的符号有意义（<0/0/>0），数值大小不保证
  • glibc 实现返回 (*s1 - *s2) 的差，但其他实现可能只返回 -1/0/1
  • 不要写 if (strcmp(a, b) == -1)，应写 if (strcmp(a, b) < 0)
  • C23 新增 strcasecmp/strncasecmp 标准化（原 POSIX 扩展）

errno 与 strerror 的返回值

char *msg = strerror(errno);   /* 返回静态存储指针 */
  • 返回的指针指向静态缓冲区，下次调用覆盖
  • 多线程下非线程安全，应改用 strerror_r（POSIX）或 strerror_s（C11 Annex K）
  • 见 9.7 详述

strtol/strtod 的指针返回值

char *end;
long v = strtol(s, &end, 10);
if (*end != '\0') /* 有非数字字符 */;
  • end 指向第一个未转换字符，可用于格式校验
  • 这是"输出参数 + 返回值"的混合范式，比纯返回值信息量大

HFT 关联

  • DPDK rte_strscpy/rte_strlcpy：返回值与 strlcpy 一致，便于检测截断
  • 协议字段查找：memchr(pkt, 0x01, pkt_len) 查找 FIX SOH 分隔符，必须判 NULL
  • 日志格式化：vsnprintf 返回需要的总长度（不含 \0），即使截断也返回完整长度，便于调用方分配足够缓冲
  • 错误处理：rte_errno + rte_strerror 模式与 POSIX 一致，同样需注意线程安全
  • 性能：返回 dst 的设计让链式写法省一次变量，但现代编译器 SSA 分析后无差异

snprintf 返回值的微妙之处

int r = snprintf(buf, sizeof(buf), "%s", long_str);
if (r < 0) { /* 错误 */ }
else if ((size_t)r >= sizeof(buf)) { /* 截断，需要 r+1 字节 */ }
else { /* 完整，写了 r 字节（不含 \0） */ }
  • 返回值是需要的总长度（不含 \0），不是实际写入长度
  • 这让调用方能判断是否截断并分配更大缓冲
  • 是 C 标准库少有的能检测截断的 API

9.3

.4 字符串比较

本节讲什么

strcmp(s1, s2) 是 C 字符串比较函数：按字节字典序逐字符比较，遇 \0 或首个不同字节停止。它依赖 \0 作为终止，因此不能用于二进制数据——中间的 0x00 会让比较提前结束，丢失后续字节。本节剖析其机制、与 memcmp 的对立、以及常量时间比较的安全需求。

要点

函数原型与行为

int strcmp(const char *s1, const char *s2);
  • 逐字节 unsigned char 比较（注意：不是 char，避免符号干扰）
  • 遇首个 \0 或首个不同字节停止
  • 返回 <0（s1 < s2）、0（相等）、>0（s1 > s2）
  • 返回值符号有意义，数值大小不保证（不一定是 -1/0/1）

简化实现

int strcmp(const char *s1, const char *s2) {
    while (*s1 && (*s1 == *s2)) {
        s1++;
        s2++;
    }
    return (unsigned char)*s1 - (unsigned char)*s2;
}

glibc 用 SSE2/AVX2 一次比 16/32 字节，但仍扫到 \0 或差异才停。

实例

strcmp("abc", "abc");   /* 0  —— 相等 */
strcmp("abc", "abd");   /* <0 —— 'c'(0x63) < 'd'(0x64) */
strcmp("abc", "ab");    /* >0 —— 'c' > '\0' */
strcmp("ab", "abc");    /* <0 —— '\0' < 'c' */
strcmp("ABC", "abc");   /* <0 —— 'A'(0x41) < 'a'(0x61) */

注意 strcmp("abc", "ab") 返回 >0，因为 'c' > '\0'。较长的字符串在公共前缀后"更大"。

strcmp vs memcmp

维度 strcmp memcmp
边界 \0 终止 显式 n 字节
0x00 处理 停止比较 继续比较
长度参数 无 必须有 n
二进制适用 否 是
典型场景 文本命令、配置键 协议头魔数、报文比对
返回值 <0/0/>0 <0/0/>0
性能 O(min(len1, len2)) O(n) 
/* 协议头魔数比较 —— 用 memcmp */
uint8_t magic[4] = { 'F', 'I', 'X', 0x01 };  /* FIX 4.4 起始 */
if (memcmp(pkt, magic, 4) == 0) { /* 是 FIX 报文 */ }

/* 若误用 strcmp，0x01 字节在 'X' 后但不是 \0... */
/* 但若 magic 含 0x00，strcmp 会在 0x00 处停止，丢后续字节 */

strncmp：限长但仍依赖 \0

strncmp(s1, s2, n);
  • 最多比较 n 字节
  • 遇 \0 或差异或满 n 字节停止
  • 仍依赖 \0 语义——若两串前 n 字节相同且都无 \0，返回 0
strncmp("foobar", "foobaz", 3);   /* 0 —— 前 3 字节相同 */
strncmp("foobar", "foo", 10);     /* >0 —— 'b' > '\0'（第 4 字节） */

字典序 vs 数值序的陷阱

字符串字典序与数值序不一致：

strcmp("10", "9");    /* <0 —— '1' < '9'，但数值 10 > 9 */
strcmp("100", "99");  /* <0 —— 字典序 100 < 99，但数值 100 > 99 */

排序数字字符串需先 atoi/strtol 再比，或用定长零填充格式（"%03d"）。

大小写不敏感：strcasecmp

strcasecmp("FIX", "fix");   /* 0 —— 大小写不敏感 */
  • POSIX 扩展，C23 标准化
  • 仅 ASCII 范围有效，Unicode 需 ICU 库
  • HFT 协议字段（FIX tag 名）通常大小写敏感，不用 strcasecmp

安全隐患：非常量时间比较

if (strcmp(user_token, secret) == 0) { /* 认证通过 */ }

strcmp 在首个不同字节立即返回，比较时间与公共前缀长度成正比——攻击者可计时侧信道逐字节猜解。认证场景必须用常量时间比较：

/* 常量时间比较（OpenSSL CRYPTO_memcmp 模式） */
int ct_memcmp(const void *a, const void *b, size_t n) {
    const uint8_t *pa = a, *pb = b;
    uint8_t diff = 0;
    for (size_t i = 0; i < n; i++)
        diff |= pa[i] ^ pb[i];   /* 不短路 */
    return diff != 0;
}
  • 始终遍历完 n 字节，时间与内容无关
  • memcmp 也不保证常量时间（glibc 实现短路返回）
  • OpenSSL 提供 CRYPTO_memcmp，Linux 内核 crypto_memneq

HFT 关联

  • 协议头魔数：Ethernet type、IP protocol、TCP flags 用 memcmp 比对定长字段
  • FIX 报文起始：8=FIX\x01 用 memcmp(pkt, "8=FIX\x01", 6) 检测
  • SBE 模板 ID：定长字段，memcmp 比对 schema 编译期 ID
  • 认证 token：HFT 系统间的 session key、API token 比较必须用常量时间函数
  • 订单 ID 去重：memcmp 比对定长 order ID，不用 strcmp（订单 ID 是二进制）
  • 性能：memcmp(pkt, magic, 4) 在 -O2 下常被编译为 4 字节整数比较，1-2 周期

实操：协议头分派

if (pkt_len < 14) return;
uint16_t eth_type = ntohs(*(uint16_t *)(pkt + 12));
if (eth_type == 0x0800) {
    /* IPv4 */
    if (pkt[14] >> 4 != 4) return;  /* IP 版本 */
    /* ... */
} else if (eth_type == 0x86DD) {
    /* IPv6 */
}

9.4

长度受限的字符串函数

本节讲什么

strncpy / strncat / strncmp 是 str 系列的"限长版"：多了一个 n 参数。但关键认知是：它们仍依赖 \0 语义，不是真正的二进制安全 API。n 只是上界，扫描仍可能在 \0 处提前停止。这族函数有行为不一致的著名坑（strncpy 不补 \0、strncat 补 \0），是 C 标准库被诟病的设计缺陷之一。

本节剖析三个函数的细节、与 strlcpy/strlcat 的对比、以及工程上的正确选择。

要点

函数清单

函数 原型 行为 补 \0？
strncpy char *strncpy(char *dst, const char *src, size_t n) 最多拷 n 字节 不一定
strncat char *strncat(char *dst, const char *src, size_t n) 最多追加 n 字符 总是
strncmp int strncmp(const char *s1, const char *s2, size_t n) 最多比 n 字节 —

strncpy 的两个坑

坑 1：src 长 ≥ n 时不补 \0

char d[5];
strncpy(d, "hello world", 5);
/* d = {'h','e','l','l','o'} —— 无 \0！ */
printf("%s", d);   /* UB：越界读直到碰巧 \0 */

必须手动补：

strncpy(d, src, sizeof(d) - 1);
d[sizeof(d) - 1] = '\0';   /* 铁律：strncpy 后手动终止 */

坑 2：src 短时填充 \0 到 n 字节

char d[8];
strncpy(d, "ab", 8);
/* d = {'a','b','\0','\0','\0','\0','\0','\0'} —— 填充 6 个 \0 */

这是性能浪费——拷贝 2 字节却写了 8 字节，且编译器优化难以消除（标准要求如此）。strlcpy 不做这种填充。

strncat 的微妙之处

char d[8] = "abc";
strncat(d, "defghij", 3);
/* d = "abcdef\0?" —— 追加最多 3 字符，再补 \0，共写 4 字节 */
  • n 是最多从 src 取的字符数，不含 \0
  • strncat 总是在结果末尾补 \0
  • 所需 dst 容量 = strlen(dst) + min(strlen(src), n) + 1
  • 与 strncpy 不补 \0 形成对比——同族函数行为不一致，是 C 标准库的著名设计缺陷

strncmp 的行为

strncmp("foobar", "foobaz", 3);   /* 0 —— 前 3 字节相同 */
strncmp("foobar", "foo", 10);     /* >0 —— 第 4 字节 'b' > '\0' */
strncmp("foobar", "foobaz", 10);  /* <0 —— 第 5 字节 'a' < 'z' */
  • 最多比较 n 字节
  • 遇 \0 或差异或满 n 停止
  • 仍依赖 \0——若两串前 n 字节相同且都无 \0，返回 0

strlcpy / strlcat：更安全的替代

OpenBSD 1996 年引入，Linux 内核 2016 年、glibc 2.38（2023）跟进。

size_t strlcpy(char *dst, const char *src, size_t dstsize);
size_t strlcat(char *dst, const char *src, size_t dstsize);

strlcpy 优势：

  • 拷贝至多 dstsize-1 字节，总是补 \0
  • 返回 strlen(src)，调用方可判断是否截断：if (ret >= dstsize) /* 截断 */
  • 不做 strncpy 那种无意义填充

strlcat 优势：

  • 在 dst 末尾追加，至多写 dstsize-1 字节（含已有 + 新增）
  • 返回尝试的总长度 strlen(dst) + strlen(src)
  • 总是补 \0
char d[8] = "abc";
size_t r = strlcat(d, "defghij", sizeof(d));
/* d = "abcdefg\0"（截断），r = 10（尝试的总长度） */
if (r >= sizeof(d)) { /* 截断了 */ }

strscpy：Linux 内核新版

ssize_t strscpy(char *dst, const char *src, size_t size);
  • 返回 -E2BIG 表示截断，否则返回已写长度
  • 比 strlcpy 更符合 POSIX 错误处理惯例
  • Linux 4.3（2016）引入内核，用户态尚未普及

工程选择决策表

场景 推荐 理由
文本拷贝（已知 dst 大小） strlcpy 或 snprintf 总是补 \0，可检测截断
文本拷贝（兼容旧系统） strncpy + 手动补 \0 唯一可移植选项
文本拼接 strlcat 或 snprintf + offset 安全
二进制拷贝 memcpy + n 与 \0 无关
文本比较 strncmp 限长防越界
二进制比较 memcmp 显式 n
跨平台安全 API snprintf C89 起标准，最可移植

snprintf：最可移植的安全选择

snprintf(dst, sizeof dst, "%s", src);
  • C89 起标准化，所有平台都有
  • 总是补 \0
  • 返回需要的总长度，可检测截断
  • 缺点：格式串解析有开销，热路径上不如 strlcpy 快

HFT 关联

  • DPDK rte_strlcpy：DPDK 18.11 起提供，行为与 strlcpy 一致
  • 配置字符串拷贝：rte_eal_init 的 argv 处理用 strlcpy 或 snprintf
  • 报文头部拷贝：定长字段用 memcpy，不用 strncpy（填充浪费周期）
  • FIX tag 拷贝：变长字段用 memcpy + 显式 field_len
  • 日志前缀拼接：snprintf 是标准范式，不用 strncat
  • 性能：strncpy 的 \0 填充在 64 字节缓冲上浪费约 10-20ns，HFT 热路径不可忽视

实操：strncpy 截断后 printf 乱码

/* buf 无 \0 */
printf("[%s]\n", buf);   /* 输出 "[hello???]" —— 越界读到栈上偶然 \0 */

/* ASan 报：stack-buffer-overflow */

修复：

char buf[5];
strncpy(buf, "hello world", sizeof(buf) - 1);
buf[sizeof(buf) - 1] = '\0';
printf("[%s]\n", buf);   /* "[hell]" */

9.5

字符串查找

本节讲什么

strchr / strrchr / strstr 在 \0 终止的 C 字符串中查找字符或子串。它们是文本解析的基础工具（配置 key=value、CSV 分隔、命令行 token 化），但完全依赖 \0 作为扫描终点，不能用于二进制缓冲——二进制场景需用 memchr（9.9）。本节剖析其机制、返回值陷阱与文本解析范式。

要点

函数清单

函数 原型 作用 返回值
strchr char *strchr(const char *s, int c) 正向找字符 c 位置指针或 NULL
strrchr char *strrchr(const char *s, int c) 反向找字符 c 位置指针或 NULL
strstr char *strstr(const char *s, const char *sub) 找子串 sub 位置指针或 NULL

strchr 行为细节

char *p = strchr("a,b,c", ',');   /* p 指向第一个 ',' */
char *q = strchr("abc", '\0');    /* q 指向终止 \0 —— 合法！ */
char *r = strchr("abc", 'z');     /* r == NULL */
  • c 被转为 unsigned char 后比较（与 is* 不同，这里 int 是历史原因）
  • 查找 \0 是合法的——返回指向终止 \0 的指针
  • 扫描到第一个匹配或 \0 停止

strrchr：反向查找

char *p = strrchr("/path/to/file.txt", '/');  /* p 指向最后一个 '/' */
  • 从字符串末尾（即 \0 处）向前扫描
  • 用于提取文件名、扩展名、URL 末段
  • glibc 实现：先 strlen 找末尾，再反向扫，O(n)

strstr：子串查找

char *p = strstr("hello world", "wor");   /* p 指向 'w' */
char *q = strstr("hello", "");            /* q 指向 'h' —— 空子串返回 s */
char *r = strstr("hello", "xyz");         /* r == NULL */
  • 空子串 "" 返回 s 本身（C 标准规定）
  • 复杂度 O(n*m) 朴素算法，glibc 用 Two-Way 算法 O(n+m)
  • 不用于二进制——sub 中的 \0 会提前截断

返回值 NULL 陷阱

char *p = strchr(line, '=');
*p = '\0';   /* 若无 '='，p == NULL，SIGSEGV */

铁律：查找函数返回值必须先判 NULL再解引用：

char *p = strchr(line, '=');
if (p) {
    *p = '\0';
    const char *value = p + 1;
    /* ... */
} else {
    /* 无等号，跳过或报错 */
}

文本解析经典范式

配置 key=value：

char line[] = "timeout = 30";
char *eq = strchr(line, '=');
if (eq) {
    *eq = '\0';
    char *key = line;
    char *val = eq + 1;
    /* trim 空白 */
    while (*val == ' ') val++;
    /* ... */
}

指针遍历文本：

for (char *p = line; *p; p++) {
    if (*p == ',') { /* 分隔符处理 */ }
    else { /* 字符处理 */ }
}

多分隔符分词（预告 9.6）：

char *tok = strchr(line, ',');

    *tok = '\0';
    process(line);
    line = tok + 1;
    tok = strchr(line, ',');
}
process(line);   /* 最后一段 */

strpbrk：字符集查找

char *p = strpbrk("hello world", "aeiou");  /* p 指向第一个 'e' */
  • 在 s 中查找 set 中任意字符的第一个出现
  • 返回位置指针或 NULL
  • 用于多分隔符检测（如 " \t,;" 任一即分隔）

strspn / strcspn：跨度查找

size_t strspn(const char *s, const char *accept);   /* 前缀中属于 accept 的字节数 */
size_t strcspn(const char *s, const char *reject);  /* 前缀中不属于 reject 的字节数 */

strspn("   hello", " \t");   /* 3 —— 前 3 个空白 */
strcspn("hello,world", ",;"); /* 5 —— 到 ',' 前 */
  • strspn：跳过前导字符集（如空白）
  • strcspn：找下一个分隔符前的长度
  • 二者配合实现 trim 和 tokenize（详见 9.6）

HFT 关联

  • FIX tag 分隔：FIX 用 SOH(0x01) 分隔 tag-value，memchr(pkt, 0x01, pkt_len) 查找，不用 strchr（报文无 \0）
  • 配置文件解析：rte_eal 参数、INI 文件可用 strchr 找 =
  • 日志字段提取：strchr(log, ' ') 找时间戳边界
  • 协议 ASCII 字段：HTTP/SMTP 等文本协议可用 strstr 查找 "\r\n\r\n" 头部结束标志
  • 二进制绝对禁用：报文含 0x00 时 strchr 在 0x00 处停止，丢失后续字节

实操：FIX 报文分隔

/* 错误：用 strchr 查 SOH */

/* 正确：用 memchr 显式长度 */
uint8_t *p = memchr(pkt, 0x01, pkt_len);
while (p && p < end) {
    /* 处理一个 tag-value */
    size_t field_len = p - pkt;
    /* ... */
    pkt = p + 1;
    p = memchr(pkt, 0x01, end - pkt);
}

/* HTTP 头部以 \r\n\r\n 结束 */
const char *hdr_end = strstr(buf, "\r\n\r\n");

    size_t hdr_len = hdr_end - buf + 4;

}

9.6

高级字符串查找

本节讲什么

strspn / strcspn / strpbrk / strtok 是 str 系列的"高级"查找函数：按字符集跳过、分隔、分词。它们仍是文本 API，依赖 \0，但提供了比 strchr/strstr 更强的模式匹配能力。strtok 是其中最危险的——它修改原字符串、非重入、用静态缓冲保存上下文，多线程场景必须用 strtok_r/strtok_s。

本节剖析各函数机制、组合使用范式与 strtok 的重入陷阱。

要点

函数清单

函数 原型 作用 返回值
strspn size_t strspn(const char *s, const char *accept) 前缀中属于 accept 的字节数 size_t
strcspn size_t strcspn(const char *s, const char *reject) 前缀中不属于 reject 的字节数 size_t
strpbrk char *strpbrk(const char *s, const char *set) set 中任一字符的首个位置 指针或 NULL
strtok char *strtok(char *s, const char *delim) 分词 token 指针或 NULL

strspn / strcspn：跨度查找

size_t strspn(const char *s, const char *accept);   /* 前缀属于 accept 的长度 */
size_t strcspn(const char *s, const char *reject);  /* 前缀不属于 reject 的长度 */

实例：

strspn("   hello", " \t");    /* 3 —— 前 3 个空白 */
strspn("hello", " \t");       /* 0 —— 第一个字符非空白 */
strcspn("hello,world", ",;"); /* 5 —— 到 ',' 前 */
strcspn("hello", ",;");       /* 5 —— 无分隔符，到 \0 */

经典组合：trim 前导空白 + 提取 token

char *p = line;
p += strspn(p, " \t");             /* 跳过前导空白 */
size_t len = strcspn(p, " \t,;");  /* token 长度 */
if (len) {
    char save = p[len];
    p[len] = '\0';
    process(p);
    p[len] = save;   /* 恢复或不恢复 */
}
p += len;

strspn 和 strcspn 是只读的，不修改 s，比 strtok 安全。

strpbrk：字符集查找

char *p = strpbrk("hello world", "aeiou");  /* p 指向第一个 'e' */
char *q = strpbrk("hello", "xyz");          /* q == NULL */
  • 在 s 中查找 set 中任意字符的第一个出现
  • 返回位置指针或 NULL
  • 与 strcspn 关系：strpbrk(s, set) == s + strcspn(s, set)（若找到）

strtok：分词（危险）

char *strtok(char *s, const char *delim);

机制：

  1. 首次调用传非 NULL 的 s
  2. 跳过前导分隔符，记录 token 起点
  3. 找到下一个分隔符，将其替换为 \0
  4. 保存下一个 token 的起点到静态缓冲
  5. 返回当前 token 指针
  6. 后续调用传 NULL 作为 s，从静态缓冲恢复
  7. 无更多 token 时返回 NULL
char buf[] = "a,b,,c";
char *tok = strtok(buf, ",");
while (tok) {
    printf("[%s]\n", tok);   /* [a] [b] [c] —— 注意空 token 被跳过 */
    tok = strtok(NULL, ",");
}
/* buf 已被改为 "a\0b\0\0c\0" */

strtok 的三个坑：

坑 说明 后果
修改原串 分隔符被替换为 \0 不可用于 const char * 或只读区
非重入 用静态缓冲保存上下文 多线程或递归调用混乱
跳过空 token 连续分隔符视为一个 "a,,c" 得到 [a][c] 而非 [a][][c]

strtok_r / strtok_s：重入版

char *strtok_r(char *s, const char *delim, char **saveptr);   /* POSIX */
char *strtok_s(char *s, rsize_t *smax, const char *delim, char **ptr); /* C11 Annex K */
  • 上下文由调用方提供（saveptr），无静态缓冲
  • 线程安全
  • 可重入——同一函数内可对多个字符串交替分词
char buf[] = "a,b,c";
char *save, *tok;
for (tok = strtok_r(buf, ",", &save); tok; tok = strtok_r(NULL, ",", &save)) {
    process(tok);
}

strsep：BSD 的分词替代

char *strsep(char **stringp, const char *delim);
  • BSD 起源，Linux 也支持
  • 不跳过空 token——"a,,c" 得到 [a][][c]
  • 不修改分隔符位置——通过移动 *stringp 指针
  • 上下文由 stringp 提供，重入
  • 比 strtok_r 更现代，但可移植性稍差（MSVC 无）
char *p = buf;
char *tok;
while ((tok = strsep(&p, ",")) != NULL) {
    process(tok);   /* 空 token 也处理 */
}

工程选择

场景 推荐 理由
单线程文本分词 strsep 或 strtok_r 重入安全
多线程文本分词 strtok_r / strsep 无静态缓冲
二进制分词 memchr 手动循环 与 \0 无关
跳过空白 strspn 只读，安全
提取 token 长度 strcspn 只读，安全

HFT 关联

  • FIX 报文分词：SOH(0x01) 分隔，但不用 strtok——报文可能含 0x00，且需保留空字段。用手动 memchr 循环：
uint8_t *p = pkt, *end = pkt + pkt_len;
while (p < end) {
    uint8_t *sep = memchr(p, 0x01, end - p);
    size_t field_len = sep ? (size_t)(sep - p) : (size_t)(end - p);
    process_field(p, field_len);
    if (!sep) break;
    p = sep + 1;
}
  • CSV 日志解析：文本，可用 strsep，但生产用 memchr 更可控
  • SBE 编码：定长字段，schema 编译期已知，根本不分词
  • 配置文件：strtok_r 可用，但 strsep 更现代

9.7

错误信息

本节讲什么

strerror(errno) 和 perror(prefix) 把 errno（系统调用失败的错误码）转换为可读文本，是 C 程序诊断系统调用失败的标准工具。但它们返回静态存储指针，默认非线程安全——多线程下并发调用会互相覆盖。POSIX 的 strerror_r 和 C11 的 strerror_s 提供了线程安全的重入版，但二者API 不一致，是 C 标准库著名的可移植性陷阱。

本节剖析机制、线程安全陷阱与工程上的正确选择。

要点

errno 机制

#include <errno.h>

extern int errno;   /* 实际是宏，常为 *(__errno_location()) */
  • errno 在系统调用失败时被内核设置为正值错误码（E* 宏）
  • 成功调用不清零——必须先检查返回值再读 errno
  • 每个线程有独立的 errno（glibc 用 __thread 实现）
  • 典型值：ENOENT(2)、EIO(5)、EBADF(9)、ENOMEM(12)、EAGAIN(11)、EINTR(4)

strerror：错误码转文本

#include <string.h>
char *strerror(int errnum);

int fd = open("/no/such/file", O_RDONLY);
if (fd < 0) {
    fprintf(stderr, "open: %s\n", strerror(errno));
    /* 输出：open: No such file or directory */
}
  • 返回指向静态存储的指针
  • 下次调用覆盖（单线程也无重入保证）
  • errnum 未知时返回 "Unknown error N"

perror：快捷诊断

#include <stdio.h>
void perror(const char *prefix);

if (open("/no/such", O_RDONLY) < 0)
    perror("open");   /* 输出：open: No such file or directory */
  • 等价于 fprintf(stderr, "%s: %s\n", prefix, strerror(errno))
  • prefix 为 NULL 或空串时只输出错误描述
  • 写到 stderr，无缓冲（立即刷出）

strerror 的线程安全陷阱

/* 线程 A */
char *msg_a = strerror(EIO);
/* msg_a 指向静态缓冲 */

/* 线程 B 同时调用 */
char *msg_b = strerror(ENOENT);
/* msg_a 现在可能变成 "No such file or directory"！ */
printf("%s\n", msg_a);   /* 数据竞争，输出不可预测 */

glibc 2.29+ 对 strerror 做了线程局部存储优化，使其在 glibc 上实际线程安全，但这不是标准保证——其他 libc（musl、MSVCRT）仍可能不安全。可移植代码必须用 strerror_r。

strerror_r：POSIX 重入版

int strerror_r(int errnum, char *buf, size_t buflen);
  • 错误码写入调用方提供的 buf
  • 返回 0 成功，或负的 -errno 失败
  • 完全线程安全

但有两个不兼容版本：

/* POSIX 版（_GNU_SOURCE 未定义时） */
int strerror_r(int errnum, char *buf, size_t buflen);
/* 返回 int，buf 写入消息 */

/* GNU 版（_GNU_SOURCE 定义时） */
char *strerror_r(int errnum, char *buf, size_t buflen);
/* 返回 char*，可能指向 buf 或内部静态串 */

这是 glibc 著名的API 陷阱：同一个函数名，_GNU_SOURCE 开关切换两种签名。可移植代码必须用宏检测：

#include <string.h>
#include <stdio.h>

void safe_strerror(int errnum, char *buf, size_t len) {
#if defined(_GNU_SOURCE) && defined(__GLIBC__)
    char *msg = strerror_r(errnum, buf, len);
    if (msg != buf) {
        strncpy(buf, msg, len - 1);
        buf[len - 1] = '\0';
    }
#else
    int rc = strerror_r(errnum, buf, len);
    if (rc != 0) snprintf(buf, len, "Unknown error %d", errnum);
#endif
}

strerror_s：C11 Annex K 版

errno_t strerror_s(char *buf, rsize_t bufsz, errno_t errnum);
  • C11 Annex K（边界检查 API）
  • MSVC 支持，glibc 未实现
  • 需要 __STDC_WANT_LIB_EXT1__=1
  • 可移植性差，不推荐

工程选择

场景 推荐 理由
单线程诊断 strerror 简单
多线程诊断 strerror_r + 宏检测 线程安全
Windows MSVC strerror_s 或 FormatMessage 平台 API
日志系统 strerror_r 缓冲 + 日志框架 避免静态存储
二进制协议 无关 errno 是本地系统错误，不进报文

HFT 关联

  • DPDK 错误码：rte_errno + rte_strerror，与 POSIX 模式一致，同样有线程安全考量
  • 系统调用失败：HFT 代码调 recvmsg、epoll_wait、mlock 等，失败时 strerror_r 诊断
  • 日志系统：异步日志线程单独格式化，工作线程用 strerror_r 写本地缓冲再投递
  • 网卡错误：DPDK rte_eth_dev 错误码用 rte_strerror，非 errno 体系
  • 二进制无关：errno 是本机概念，不进网络报文——协议有自己的错误码字段

实操： strerror 在多线程的陷阱

void *worker(void *arg) {
    int err = *(int *)arg;
    char *msg = strerror(err);
    /* 若多线程同时调用，msg 可能被覆盖 */
    printf("err %d: %s\n", err, msg);   /* 数据竞争 */
}

/* 修复 */
void *worker_safe(void *arg) {
    int err = *(int *)arg;
    char buf[64];
    safe_strerror(err, buf, sizeof(buf));   /* 线程安全 */
    printf("err %d: %s\n", err, buf);
}

实操：errno 不清零

/* 反例 */
int fd = open(path, O_RDONLY);
/* 假设上次调用失败，errno = ENOENT */
if (fd < 0 && errno == ENOENT) { /* 但 errno 可能是上次的值 */ }

/* 正例：只在返回值指示失败后才读 errno */
fd = open(path, O_RDONLY);
if (fd < 0) {
    if (errno == ENOENT) { /* 文件不存在 */ }
    else { perror("open"); }
}

铁律：errno 只在库函数返回失败时有效，成功调用不保证清零。

9.8

字符操作

本节讲什么

<ctype.h> 提供字符分类（isalpha/isdigit/isspace 等）和大小写转换（tolower/toupper）函数，用于 ASCII 文本解析（命令行 token、可读字段校验）。这族函数有一个隐藏 UB 陷阱：参数必须是 unsigned char 的值或 EOF，传 signed char 或 int 中带符号的 0x80-0xFF 会触发未定义行为。这个坑在处理 UTF-8 或扩展 ASCII 字节时尤其常见。

本节剖析机制、UB 陷阱与 HFT 文本场景的正确用法。

要点

函数清单

分类函数（返回非零为真，零为假）：

函数 判定
isalpha(c) 字母 [A-Za-z]
isdigit(c) 数字 [0-9]
isalnum(c) 字母或数字
isspace(c) 空白 \t\n\v\f\r
isupper(c) / islower(c) 大写 / 小写
isprint(c) 可打印（含空格）
isgraph(c) 可打印（不含空格）
ispunct(c) 标点
isxdigit(c) 十六进制 [0-9a-fA-F]
iscntrl(c) 控制字符
isblank(c) 空白（仅 和 \t，C99）

转换函数：

函数 行为
tolower(c) 若大写转小写，否则原值
toupper(c) 若小写转大写，否则原值

正确用法

#include <ctype.h>

if (isalpha((unsigned char)c))
    /* ... */;
if (isdigit((unsigned char)c))
    /* ... */;

int lower = tolower((unsigned char)c);

铁律：参数必须显式转 (unsigned char)，除非 c 已经是 int 且来自 getchar()（其值域已是 0..255 或 EOF）。

UB 陷阱：signed char 传入

char c = 0x80;          /* signed char，值 -128 */
isalpha(c);             /* UB！c 隐式提升为 int -128，不在 EOF 或 unsigned char 范围 */

根因：

  • is* 函数的参数要求是 int，值域为 0..UCHAR_MAX 或 EOF（通常 -1）
  • char 在 x86-64 Linux 上是 signed（-fsigned-char 默认）
  • char 值 0x80 提升为 int 是 -128，不在合法值域
  • glibc 实现用 __ctype_b_loc() 表查，负索引越界 UB
  • 实际可能：返回随机值、段错误、或静默错误

修复：

isalpha((unsigned char)c);   /* 0x80 作为 128 查表，安全 */

unsigned char 提升到 int 是 0..255，在合法值域内。

何时传 EOF

int c = getchar();   /* 返回 0..255 或 EOF(-1) */
if (c == EOF) break;
if (isalpha(c))      /* 这里 c 可能是 EOF 或 0..255，都合法 */
    /* ... */;

getchar/fgetc 返回 int 正是为了能区分 EOF 和 0xFF 字节——若存到 char 再判 EOF，0xFF 会被误判为 EOF：

char c = getchar();   /* 错误！0xFF 会被当作 EOF */
if (c == EOF) break;

toupper/tolower 的返回值陷阱

char c = 'a';
putchar(toupper(c));   /* 'A'，正确 */

/* 但若 c 已经是大写或非字母 */
toupper('A');   /* 'A'，原值返回 */
toupper('1');   /* '1'，原值返回 */
  • 返回 int，需存 int 或转 char
  • 同样需要 (unsigned char) 转换输入
  • 不要写 c += 'A' - 'a'——可移植性差，且对非字母 UB

大小写不敏感比较

int strcasecmp_safe(const char *a, const char *b) {
    while (*a && *b) {
        int ca = tolower((unsigned char)*a);
        int cb = tolower((unsigned char)*b);
        if (ca != cb) return ca - cb;
        a++; b++;
    }
    return (unsigned char)*a - (unsigned char)*b;
}

POSIX strcasecmp 已封装，但内部同样依赖 unsigned char。

locale 影响

is* 和 tolower/toupper 行为受 setlocale(LC_CTYPE, ...) 影响：

  • 默认 "C" locale：仅 ASCII 范围
  • setlocale(LC_CTYPE, "")：使用环境 locale，可能识别 UTF-8 字母
  • HFT 场景：协议解析应禁用 locale，固定 ASCII 语义，避免环境差异

性能特征

  • glibc is* 用查表（__ctype_b_loc()），约 2-3 ns/次
  • tolower/toupper 同样查表
  • 简单范围判断（如 '0' <= c && c <= '9'）约 1 ns，更快但不可移植
  • 热路径上批量分类可考虑手写内联

HFT 关联

  • 命令行 token 校验：rte_eal 参数解析用 isdigit 校验端口号
  • 可读 ASCII 字段：FIX tag 名是数字，用 isdigit 校验
  • 二进制 payload：严禁用 is* 判定 payload 字节——payload 不是字符，是数值
  • 大小写归一化：协议字段（如 HTTP method GET/get）归一化用 tolower
  • locale 隔离：HFT 进程启动时 setlocale(LC_ALL, "C")，确保 ASCII 语义
  • UTF-8 报文：现代协议（如 JSON over WebSocket）可能含 UTF-8，is* 仅对 ASCII 字节有效，多字节序列需 ICU 库

    printf("isalpha(0x80 as char) = %d\n", isalpha(c));           /* UB */
    printf("isalpha(0x80 as uchar) = %d\n", isalpha((unsigned char)c));  /* 0 */

9.9

内存操作

本节讲什么

<string.h> 中的 mem* 系列是 HFT/DPDK/内核报文处理的真正主力：memcpy、memmove、memset、memcmp、memchr。它们显式接受 size_t n 长度参数，不依赖 \0，因此完全二进制安全——0x00 是合法数据字节，扫描由 n 决定。这与 str* 系列（依赖 \0）形成根本对立。

本节剖析各函数机制、重叠处理原理、SIMD 优化、与 str* 的对比，以及 HFT 报文解析的标准范式。

要点

函数清单

函数 原型 作用 重叠处理
memcpy void *memcpy(void *dst, const void *src, size_t n) 拷贝 n 字节 不可重叠
memmove void *memmove(void *dst, const void *src, size_t n) 拷贝 n 字节 可重叠
memset void *memset(void *dst, int c, size_t n) 填充 n 字节为 c —
memcmp int memcmp(const void *a, const void *b, size_t n) 比较 n 字节 —
memchr void *memchr(const void *s, int c, size_t n) 前 n 字节中找 c —

核心特征

  1. 显式长度 n：与 \0 无关，二进制安全
  2. void * 参数：任意类型指针，按字节操作
  3. size_t 长度：无符号，最大支持 SIZE_MAX 字节
  4. 无 \0 依赖：0x00 是合法数据字节
  5. HFT 首选：报文长度由协议字段给出，不靠扫描

memcpy vs memmove：重叠处理

char buf[10] = "abcdef";
memcpy(buf + 2, buf, 4);     /* UB：重叠 */
memmove(buf + 2, buf, 4);    /* OK：结果 "ababcd" */

重叠 UB 的根因：

  • memcpy 假设 dst 和 src 不重叠，可按任意顺序拷贝（前向/后向/SIMD 块）
  • 若重叠，部分字节在拷贝前被覆盖，结果不可预测
  • glibc memcpy 用 SIMD 块拷贝，重叠时前向拷贝会导致源数据被破坏

memmove 的正确实现：

void *memmove(void *dst, const void *src, size_t n) {
    uint8_t *d = dst;
    const uint8_t *s = src;
    if (d < s) {
        /* dst 在 src 前，前向拷贝 */
        while (n--) *d++ = *s++;
    } else {
        /* dst 在 src 后，后向拷贝（避免覆盖未读字节） */
        d += n; s += n;
        while (n--) *--d = *--s;
    }
    return dst;
}

汇编视角：memmove 先比较 dst 和 src 地址，选择前向或后向拷贝方向。memcpy 无此检测，直接前向，故快约 5-10%。

工程铁律：

  • 不确定是否重叠时用 memmove
  • 性能敏感且确认不重叠时用 memcpy（或 rte_memcpy）
  • 编译器在 -O2 下对小区间 memcpy 常展开为寄存器移动

memset：填充

memset(buf, 0, sizeof(buf));          /* 清零 */
memset(buf, 0xFF, sizeof(buf));       /* 填 0xFF */
memset(&struct_val, 0, sizeof(struct_val));  /* struct 清零 */
  • c 被转为 unsigned char，填充 n 字节为该字节值
  • 不能用来设置 int 数组为非零值（memset(arr, 1, ...) 让每个 int 变成 0x01010101，不是 1）
  • struct 清零推荐 = {0} 初始化（编译期）或 memset（运行时）

memcmp：二进制比较

uint8_t magic[4] = { 'F', 'I', 'X', 0x01 };
if (memcmp(pkt, magic, 4) == 0) { /* 是 FIX 报文 */ }
  • 按字节 unsigned char 比较
  • 返回 <0/0/>0，符号有意义
  • 不保证常量时间（glibc 短路返回）——认证场景需手写
  • 性能：memcmp(pkt, magic, 4) 在 -O2 下常编译为 4 字节整数比较，1-2 周期

memchr：二进制查找

const uint8_t *p = memchr(pkt, 0x01, pkt_len);   /* FIX SOH 分隔符 */
  • 在前 n 字节中查找字节 c
  • 返回位置指针或 NULL
  • 与 strchr 对立：memchr 不受 0x00 影响，strchr 在 0x00 停
  • glibc 用 SIMD，约 1-2 ns/16 字节

指针遍历报文的标准范式

uint8_t *p = payload;
uint8_t *end = p + pkt_len;
for (; p < end; p++) {
    parse_byte(*p);
}
  • end 是上界指针，不是 \0
  • 即使中间出现 0x00 仍继续
  • p < end 是无符号比较，安全（size_t 无负值）

大小端铺垫

uint32_t net = 0x12345678;   /* 网络序（大端） */
uint8_t b0 = (net >> 24) & 0xFF;   /* 0x12 */
uint8_t b1 = (net >> 16) & 0xFF;   /* 0x34 */
uint8_t b2 = (net >> 8) & 0xFF;    /* 0x56 */
uint8_t b3 = net & 0xFF;           /* 0x78 */
  • 网络字节序是大端（高位在前）
  • x86-64 是小端（低位在前）
  • 转换：htonl/ntohl（32 位）、htons/ntohs（16 位）
  • 禁用 union 或指针强转做大小端转换——不可移植，且违反严格别名
  • 推荐用移位（如上），编译器优化为单条 bswap 指令

报文头部提取

struct eth_hdr {
    uint8_t dst[6], src[6];
    uint16_t type;
} __attribute__((packed));

struct eth_hdr eth;
memcpy(&eth, pkt, sizeof(eth));   /* 对齐安全拷贝 */

为什么用 memcpy 而非直接强转：

struct eth_hdr *bad = (struct eth_hdr *)pkt;   /* UB：未对齐访问 */

x86-64 允许未对齐访问但有性能惩罚，ARM/MIPS 上是 SIGBUS。memcpy 是唯一可移植的对齐安全结构体读取方式，编译器优化为单条 mov 或 movups。

实操：memcpy 重叠 UB

char buf[10] = "abcdef";
memcpy(buf + 2, buf, 4);
/* UB：glibc 前向拷贝，buf 可能变成 "abababef" 而非期望的 "ababcdef" */

memmove(buf + 2, buf, 4);   /* OK：后向拷贝，结果 "ababcd" */

ASan 检测：

ERROR: AddressSanitizer: memcpy-param-overlap

实操：memset 不能设 int 数组

int arr[10];
memset(arr, 1, sizeof(arr));
/* 每个 int 变成 0x01010101 = 16843009，不是 1 */

修复：

for (int i = 0; i < 10; i++) arr[i] = 1;

实操：结构体对齐安全读取

/* 反例：未对齐强转 */
uint16_t type = *(uint16_t *)(pkt + 12);   /* UB：未对齐 */

/* 正例：memcpy 让编译器处理对齐 */
uint16_t type;
memcpy(&type, pkt + 12, 2);
type = ntohs(type);

-O2 下 memcpy(&type, pkt+12, 2) 编译为单条 movzx 或 movups，零开销。

题目 1： 以下代码有什么问题？

char *s = "hello";
s[0] = 'H';
参考答案

未定义行为。字符串字面量 "hello" 存储在只读内存段（.rodata），修改它会导致 segfault（或某些系统上看似正常）。正确做法：用字符数组 char s[] = "hello"; 此时字符串存储在栈上，可修改。
