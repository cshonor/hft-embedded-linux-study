13.1

进一步探讨指向指针的指针

本节讲什么

一级指针 T * 让函数能改「T 类型的对象」；二级指针 T ** 让函数能改「指向 T 的指针」本身。这条递推听起来平凡，却是 C 工程里最易写错的一类声明——它的核心难点不是语法，而是「我到底在改谁的谁」的语义层级。

本节把多级指针的内存模型画清楚，给出「函数内改外部指针数组」的完整模板，并交代工程约束：生产代码控制在三级以内，超过三级基本可以认定设计出了问题。

要点

内存模型：三级视图

char *msg_table[32];    /* 32 个 char* 槽位，栈/静态 */
char **p = msg_table;   /* p 指向数组的第 0 个槽位 */
char ***pp = &p;        /* pp 指向 p 本身 */

栈/静态区:
  +-----------+      堆区(strdup):       .rodata:
  | msg_table |      +----------+        +---------+
  | [0] ------+----->| "QUOTE\0"|<-------+ "QUOTE" |
  | [1] ------+----->| "ORDER\0"|        +---------+
  | [2] = NULL|      +----------+
  | ...       |
  | [31]      |
  +-----------+
       ^
       |
  p = msg_table    （char**，存数组首地址）
       ^
       |
  pp = &p          （char***，存 p 的地址）
层级 类型 存什么 典型用途
0 char 字符本身 字符串内容
1 char * 字符串首地址 单个字符串
2 char ** 指针数组元素地址 字符串数组（如 argv）
3 char *** 改外部 char ** 头 函数内重分配数组（少用）

动态字符串数组

char **msg_table = calloc(32, sizeof(char *));
if (!msg_table) return -1;

msg_table[0] = strdup("QUOTE");   /* strdup 内部 malloc */
msg_table[1] = strdup("ORDER");
/* ... */

calloc 而非 malloc：保证未赋值的槽位是 NULL，后续遍历可 while (table[i]) 安全终止。strdup 失败时要回滚已分配的——见下文释放顺序。

函数内改外部指针数组

/* 把外部 char** 头替换为更大的数组（三级指针场景） */
int msg_table_grow(char ***ptable, size_t *cap, size_t need)
{
    char **old = *ptable;
    char **new = realloc(old, need * sizeof(char *));
    if (!new) return -1;
    /* realloc 成功后 old 已失效，但 new 可能 == old（原地扩展） */
    for (size_t i = *cap; i < need; i++)
        new[i] = NULL;            /* 清零新增槽位 */
    *ptable = new;                /* 改外部头 */
    *cap = need;
    return 0;
}

/* 调用 */
char **table = calloc(8, sizeof(char *));
size_t cap = 8;
msg_table_grow(&table, &cap, 64);  /* 传 &table，三级指针 */

&table 才是 char ***，不是 table。这是三级指针的合法场景之一：函数要改调用方的「指针数组头」本身。若只传 char **，函数改的是副本，调用方看到的还是旧头——与单链表头插必须传 Node ** 同理（见 ch12）。

释放顺序：自底向上

void msg_table_free(char **table, size_t n)
{
    for (size_t i = 0; i < n; i++)
        free(table[i]);    /* 先释放每个字符串 */
    free(table);           /* 再释放指针数组本身 */
}

顺序不可颠倒：若先 free(table)，每个 table[i] 的内存虽还在（free 不立刻清零），但访问已释放内存是 UB，ASan 会报「heap-use-after-free」。批量场景下漏释放任一层 = 内存泄漏。

失败回滚

char **msg_table_alloc(const char *src[], size_t n)
{
    char **t = calloc(n, sizeof(char *));
    if (!t) return NULL;

    for (size_t i = 0; i < n; i++) {
        t[i] = strdup(src[i]);
        if (!t[i]) {
            /* 回滚：释放已成功的 + 数组本身 */
            for (size_t j = 0; j < i; j++)
                free(t[j]);
            free(t);
            return NULL;
        }
    }
    return t;
}

goto cleanup 模式在更复杂的多资源场景下更清晰（见 ch11.6），这里循环回滚足够。

HFT 关联

报文批量处理

DPDK 收包的核心 API 签名：

uint16_t rte_eth_rx_burst(uint16_t port_id, uint16_t queue_id,
                          struct rte_mbuf **rx_pkts,
                          uint16_t nb_pkts);

rx_pkts 是 struct rte_mbuf **——一个 mbuf 指针数组的头。DPDK 一次拷贝最多 nb_pkts 个 mbuf 指针进来，调用方拿到的是一个指针数组，不是 mbuf 数组本身。这样设计的好处：

  1. mbuf 在 mempool 里原地不动，只是把指针填进数组，cache 友好。
  2. 调用方拿到指针后可批量处理，不需要逐个 dequeue。
  3. 释放时 rte_pktmbuf_free_bulk(rx_pkts, n)，一次归还。
struct rte_mbuf *pkts[32];
uint16_t n = rte_eth_rx_burst(port, q, pkts, 32);
for (uint16_t i = 0; i < n; i++) {
    process(pkts[i]);
    rte_pktmbuf_free(pkts[i]);   /* 或批量 free */
}

pkts 是栈上的指针数组（32 × 8 = 256 字节），DPDK 把 mbuf 指针填进来。这是 T ** 在 HFT 数据面最高频的用法。

订单池批量扩容

struct order **orders = calloc(cap, sizeof(struct order *));
/* ... 满了需要扩容 ... */
struct order **grown = realloc(orders, new_cap * sizeof(*grown));
if (grown) {
    orders = grown;       /* 注意：调用者要更新自己的头 */
    cap = new_cap;
}

realloc 失败时 orders 仍指向旧块，不能直接 orders = realloc(...)——失败会丢指针（见 ch11.3）。封装成函数时必须传 &orders（三级指针）或返回新指针。

多级指针与 cache 局部性

每多一级指针，访问数据就多一次内存间接。pkts[i] 需要：① 读 pkts 数组的第 i 项（一次访存）→ ② 沿指针读 mbuf 本体（又一次访存）。两级访存意味着 mbuf 必须在 L1/L2 cache 命中，否则延迟翻倍。DPDK 用 mempool 预热 + 同核复用保证 mbuf 常驻热 cache，是这种设计的工程基础。

UB 边界

情形 后果 防护
释放顺序颠倒（先 free 数组） 后续 free 元素是 UAF 自底向上：先元素后数组
realloc 失败直接 p = realloc(p, ...) 旧块泄漏，p 变 NULL 用临时变量接收，判空后再赋值
三级指针传错（传 p 而非 &p） 函数改副本，调用方看到旧头 类型即文档：char *** 必须 &p
calloc(0, ...) 或 realloc(p, 0, ...) 实现定义，可能返回 NULL 或特殊指针 避免零长度分配
未初始化的 char ** 当数组用 野指针，崩溃 calloc 保证零初始化，或显式 = NULL

三级指针的滥用警讯

char ****x;   /* 几乎必然是设计错误 */

四级以上指针在生产代码里出现，通常意味着：

  • 该用结构体封装却裸用指针（应改成 struct table *table）。
  • 该用返回值却用出参层层传递（应改成 char **grow(char **) 返回新头）。
  • 函数职责过重（应拆分）。

内核、DPDK、glibc 几乎找不到四级指针的合法用例。三级已是上限。

13.2

高级声明

本节讲什么

C 的声明语法被讽刺为「spiral rule（螺旋法则）」——标识符在中间，运算符按优先级向外螺旋展开。本节把这条规则拆成可操作的步骤，覆盖五大经典声明：指针数组、数组指针、函数指针、函数指针数组、多级指针，并给出 typedef 简化的工程必要性。

认知锚点：复杂声明不是炫技，而是阅读内核/DPDK/glibc 头文件的必备技能。int (*handler[16])(int, void *) 这类声明在 file_operations、sigaction、PMD 驱动表里随处可见，看不懂就无法读懂核心代码。

要点

右左法则（螺旋法则）步骤

  1. 找到标识符（变量名），从它开始。
  2. 看右边：若是 [] 是数组，若是 () 是函数，按优先级处理。
  3. 看左边：若是 * 是指针，若是类型修饰符则记录。
  4. 遇到括号 ()：先处理括号内，再向外。
  5. 类型名最后处理：最外层的类型是「最终指向/返回的类型」。

口诀：先找标识符 → 括号优先 → 先右后左 → 螺旋向外。

五大经典声明对照

声明 解读步骤 中文读法
int *arr[10]; arr → [10] → int * 指针数组：10 个 int *
int (*arr)[10]; arr → * → [10] → int 数组指针：指向含 10 个 int 的数组
int (*func)(int); func → * → (int) → int 函数指针：入参 int，返回 int
int (*table[16])(int); table → [16] → * → (int) → int 函数指针数组：16 个函数指针
char ***msg; msg → * → * → * → char 三级 char 指针

关键对比：int *arr[10] vs int (*arr)[10]

int *arr[10];       // arr 是数组，每个元素是 int*
                    // [] 优先级高于 *，所以 arr 先和 [] 结合
                    // sizeof(arr) = 10 * 8 = 80（x86-64）

int (*arr)[10];     // arr 是指针，指向 int[10]
                    // 括号强制 * 先结合
                    // sizeof(arr) = 8（一个指针）

混淆这两者会导致：

  • 用 int (*)[10] 接收 int *[10]：类型不匹配，编译警告（C 允许某些隐式转换，但行为未定义）。
  • 二维数组传参 int matrix[3][4] 退化为 int (*)[4]，若函数声明成 int ** 是错的——后者是指针数组，内存布局完全不同（见 ch08 多维传参）。

函数指针数组的精确解读

int (*table[16])(int, void *);

螺旋展开：

  1. table 是标识符。
  2. 右边 [16]：table 是 16 元素的数组。
  3. 左边 *：数组的每个元素是指针。
  4. 右边 (int, void *)：指针指向函数，入参 (int, void *)。
  5. 最外 int：函数返回 int。

合起来：table 是 16 元素数组，每个元素是「入参 (int, void*)、返回 int」的函数指针。

这正是 Linux 内核 struct file_operations 的字段类型，也是 DPDK eth_dev_ops 的核心。

typedef 简化：工程强制规范

/* 痛苦写法 */
int (*handlers[16])(int, void *);

/* typedef 简化 */
typedef int (*handler_fn_t)(int, void *);
handler_fn_t handlers[16];
维度 裸声明 typedef
可读性 低，需螺旋展开 高，名字即语义
修改成本 改签名要全文搜索替换 改 typedef 一处
强制规范 无 内核/DPDK 强制
错误信息 类型推导报错晦涩 类型名清晰

规则：函数指针、回调签名、复杂结构指针必须 typedef。glibc、Linux、DPDK、nginx 全部遵守此规则。

复杂声明的 typedef 拆解

/* 信号处理函数原型 */
void (*sig_t)(int);

/* typedef 化 */
typedef void (*sig_t)(int);
sig_t old_handler = signal(SIGINT, new_handler);

/* qsort 比较函数 */
typedef int (*cmp_fn_t)(const void *, const void *);
cmp_fn_t cmp = my_compare;
qsort(arr, n, sizeof(arr[0]), cmp);

实战：file_operations 字段

struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    long (*unlocked_ioctl)(struct file *, unsigned int, unsigned long);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    /* ... */
};

每个字段都是「函数指针」。驱动初始化时用指定初始化（C99）填入：

static const struct file_operations my_fops = {
    .read    = my_read,
    .write   = my_write,
    .open    = my_open,
    .release = my_release,
};

未指定的字段默认 NULL，内核 VFS 层调用时判空跳过。这是「声明即文档」的最佳范例——typedef 让字段名成为 API 描述。

HFT 关联

DPDK 报文处理表

struct rte_mbuf *pkts[32];                 /* 指针数组 */
int (*cmp)(const void *, const void *);    /* qsort 式比较函数指针 */

pkts 是栈上的 mbuf 指针数组，cmp 是比较函数指针，两者都是本节五大声明的实例。DPDK eth_dev_ops、rte_mempool_ops 全部用函数指针表实现多态。

策略插件热加载

typedef int (*strategy_fn_t)(struct market_state *, struct order *);

struct strategy {
    const char       *name;
    strategy_fn_t     on_quote;
    strategy_fn_t     on_trade;
    strategy_fn_t     on_depth;
};

策略模块以 .so 形式 dlopen 加载，通过 dlsym 拿到 struct strategy *，挂入策略表。所有多态分发都依赖函数指针声明，看不懂声明就无法设计插件系统。

内联函数指针调用的代价

handler(args);   /* 间接调用 */

间接调用比直接调用多一次访存（取函数地址）+ 一次跳转，且分支预测器对间接跳转的预测准确率较低。HFT 数据面优化时：

  1. PGO（profile-guided optimization）：让编译器看到热点分支，优化间接跳转预测。
  2. 手工展开热点：高频分支单独 if-else，低频走转移表。
  3. __builtin_expect 提示：辅助分支预测。

UB 边界

情形 后果 防护
int *arr[10] 误当 int (*)[10] 用 类型不匹配，UB 看清 [] 和 * 的优先级
函数指针赋值不同签名 调用时栈帧错乱，UB typedef 锁定签名，编译器警告
未初始化的函数指针调用 跳到野地址，崩溃 = NULL 初始化，调用前判空
把「函数」当「函数指针」直接赋值给 void * 标准不允许（POSIX 实践允许） 用对应函数指针类型中转
函数指针与数据指针互转 部分平台不兼容（哈佛架构） 不要互转，用 union 或专门类型

函数指针 ≠ 数据指针

C 标准不保证函数指针能转成 void * 再转回来——哈佛架构（代码与数据分离）上两者位数可能不同。POSIX 强制要求 void * 能容纳函数指针（为了 dlsym），但可移植代码应避免这种转换。dlsym 返回 void * 是 POSIX 妥协，使用时强转到正确函数指针类型。

空函数指针判空

handler_fn_t cb = NULL;       /* 显式初始化 */
if (cb) cb(args);             /* 调用前判空 */

NULL 函数指针调用是 UB，通常崩溃但不保证——某些嵌入式平台可能跳到 0 地址执行。判空是工程铁律。

13.3

函数指针

本节讲什么

函数指针是 C 实现运行时多态的唯一通用机制——把「调哪个函数」从编译期推迟到运行期。这一节给出函数指针的声明、调用、typedef 封装的完整模板，以及它在数据面分发、驱动表、回调机制里的三大实战形态。

认知锚点：函数指针本身只是「存函数入口地址的变量」，但它的工程意义远超语法。Linux VFS 的 file_operations、DPDK 的 eth_dev_ops、glibc 的 qsort、nginx 的模块链——所有 C 写的大型框架都用函数指针做扩展点。看不懂函数指针，就读不懂 C 工程的「多态」。

要点

从零理解：函数指针是什么

普通指针：存数据变量的内存地址（int、char、结构体）。 函数指针：存函数的内存地址。

C 语言里，函数本身也放在内存代码段（.text），它也有地址，可以存到指针变量里。

#include <stdio.h>

int add(int a, int b)
{
    return a + b;
}

/* fp：函数指针变量，只能存"返回int、接收两个int"的函数 */
int (*fp)(int, int);

int main(void)
{
    fp = add;           /* 把add的地址赋给fp，不用写& */
    int res = fp(3,5);  /* 通过函数指针调用，等价 add(3,5) */
    printf("%d\n", res);
    return 0;
}

关键易错点——括号不能少：

int *p(int a, int b);   /* 这是返回 int* 的函数声明，不是函数指针！ */
int (*p)(int a, int b); /* p 才是函数指针 */

typedef 封装（函数指针是 C 里唯一不写 typedef 基本没法维护的场景）：

typedef int (*fp_t)(int, int);
fp_t fp;                /* 等价 int (*fp)(int, int); */

fp_t 不是变量，是函数指针类型——就像 int 是整数类型。qsort 不知道你要怎么比较数据，它把比较逻辑写死在库里；你写比较函数，把函数地址通过函数指针传进去，qsort 内部回调你的逻辑——这就是回调函数，函数指针最大的现实用途。

声明与调用

int add(int x, int y) { return x + y; }

int (*calc)(int, int);    /* 函数指针变量 */
calc = add;               /* 函数名退化为函数指针 */
int res = calc(3, 5);     /* 等价 add(3, 5) */
int res2 = (*calc)(3, 5); /* 显式解引用，等价 */

函数名退化为函数指针与数组名退化为指针同构（见 ch08）：

表达式 类型 含义
add int (*)(int, int) 函数首地址
&add int (*)(int, int) 同上（函数无「整体」概念）
add(3, 5) int 调用
calc = add 赋值 函数指针赋值
calc(3, 5) int 间接调用

add 与 &add 在函数语境下等价（不像数组 arr 与 &arr 类型不同），这是 C 标准的特例。

标准依据：函数指示符转换（与数组退化平行）

C11 §6.3.2.1p4：函数指示符（function designator，具有函数类型的表达式）除了作为 sizeof、& 的操作数外，转换为指向函数的指针。这与数组退化（§6.3.2.1p3）是完全平行的机制——不是"函数名隐式取地址"，是标准规定的类型转换。

表达式 转换路径
add（函数指示符） → int (*)(int, int)（函数指针）
&add 不转换，& 直接得函数指针
*fp（解引用函数指针） 得函数类型 → 右值上下文又转回函数指针（循环）

所以 fp = add 和 fp = &add 等价——不是"两种写法效果一样"，是标准保证它们是同一个东西。

调用时为什么不用显式 *：C11 §6.5.2.2p1 规定函数调用表达式里，代表被调用函数的部分可以是函数类型或指向函数的指针；如果是指针，自动解引用。因此三种写法全部合法且等价：

fp(3, 5);        /* 指针 → 自动解引用 → 调用 */
(*fp)(3, 5);     /* 解引用得函数类型 → 直接调用 */
(**fp)(3, 5);    /* *fp 又转回指针 → 再自动解引用（合法但没必要） */

"解引用函数指针"和"函数指示符转指针"互相抵消，这就是函数指针调用不像数据指针那样需要显式 * 的原因。

底层视角：函数指针里到底存了什么

函数地址是代码段里函数第一条机器指令的地址：

.text 段（x86-64 示意）:
0x401000:  push   rbp          ← add 函数入口，add = 0x401000
0x401001:  mov    rbp, rsp
0x401004:  mov    edx, edi
0x401006:  add    edx, esi
...

fp = add 后，fp 的值就是 0x401000。fp(3,5) 编译成一条 call 指令，operand 是 fp 里存的地址——CPU 跳过去执行。

与普通数据指针的唯一本质区别：数据指针指向数据段（可读可写），函数指针指向代码段（只读，写就 segfault）。*fp = 42 是内存保护违例——这也解释了为什么不能给函数类型赋值（见下方 Quiz）。

速判 Quiz：

void hello(void) {}
void (*f)(void);
/* 哪条是把 hello 的地址存进 f？ */
/* A. f = hello;      */
/* B. *f = hello;     */
答案

A 正确：hello 是函数指示符 → 转换为函数指针 → 赋值给 f，类型匹配。

B 错误：*f 解引用函数指针得到函数类型 void(void)。函数类型不能作为赋值左值——转换只发生在右值上下文（读取值时），*f = hello 里 *f 在左值位置不发生转换，保持函数类型，约束违反。函数既不是对象也不是可修改的左值。

typedef：强制规范

/* 错误示范：裸函数指针 */
void register_cb(int (*cb)(int, void *));

/* 正确：typedef */
typedef int (*event_cb_t)(int, void *);
void register_cb(event_cb_t cb);

/* DPDK 报文处理函数类型 */
typedef void (*pkt_handler_t)(struct rte_mbuf *pkt);

pkt_handler_t handler = process_quote;
handler(mbuf);

typedef 的好处：① 可读性（名字即语义）；② 修改签名一处生效；③ 编译错误信息清晰；④ 团队强制规范。详见 13.2。

函数指针数组（分发器模式）

typedef void (*pkt_handler_t)(struct rte_mbuf *pkt);

static pkt_handler_t pkt_dispatch[] = {
    process_heartbeat,   /* type 0 */
    process_quote,       /* type 1 */
    process_order,       /* type 2 */
    process_cancel,      /* type 3 */
};

void on_packet(struct rte_mbuf *mbuf, uint8_t type)
{
    if (type < sizeof(pkt_dispatch) / sizeof(pkt_dispatch[0]))
        pkt_dispatch[type](mbuf);   /* O(1) 间接跳转 */
}

这是转移表（jump table）模式，详见 13.3.2。核心优势：

  1. O(1) 分发：一次数组索引 + 一次间接调用。
  2. 分支预测友好：固定索引的间接跳转，CPU 分支预测器可学习。
  3. 表驱动扩展：新增类型只需加表项，不改分发逻辑。

对比 if-else if 链：平均要 n/2 次比较，分支预测失败率高，HFT 数据面不可接受。

内核 file_operations 风格

struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    long (*unlocked_ioctl)(struct file *, unsigned int, unsigned long);
    /* ... */
};

static const struct file_operations my_fops = {
    .read    = my_read,
    .write   = my_write,
    .open    = my_open,
    .release = my_release,
};

设计要点：

  • 结构体里全是函数指针：每个字段是一个「操作槽位」。
  • 指定初始化（C99）：.read = my_read 只填关心的字段，其余默认 NULL。
  • VFS 层调用时判空：if (fops->read) fops->read(...)，未实现的操作返回 -ENOSYS。
  • const 修饰：操作表只读，放 .rodata，多进程共享一份物理页。

这是 C 实现「接口 + 实现」分离的标准范式。DPDK eth_dev_ops、rte_mempool_ops、nginx ngx_module_t 全部沿用。

函数指针的存储与对齐

sizeof(handler_fn_t) = 8;   /* x86-64，与数据指针同宽 */

x86-64 上函数指针与数据指针都是 8 字节，但对齐要求可能不同（函数地址通常 16 字节对齐，-falign-functions）。函数指针数组在 cache 上的表现：每个槽位 8 字节，8 个槽位占一个 cache 行，索引访问高效。

  2. 手工展开热点：高频类型单独 if-else，低频走转移表。
  3. __builtin_expect / likely/unlikely：辅助分支预测。

不同签名赋值的危险

typedef int (*cb_t)(int);
void f(long x);            /* 签名不同 */

cb_t cb = (cb_t)f;         /* 强转，编译通过 */
cb(42);                    /* UB：f 期望 long，收到 int 的位模式 */

强转能绕过编译器检查，但行为未定义。x86-64 上 int 和 long 都在寄存器传参，碰巧能跑，但 ARM、RISC-V 上参数传递规则不同，立刻崩。-Werror=incompatible-pointer-types 把这类隐患堵死在编译期。

void *sym = dlsym(handle, "my_function");

13.3

.1 回调函数

本节讲什么

回调（callback）的本质是「调用方把函数指针交给被调用方，由被调用方在合适时机反向调用」。这一节给出回调机制的三大要素——typedef 函数指针 + void *priv 私有数据 + 注册/触发分离——以及它在 DPDK、内核、事件引擎里的标准范式。

认知锚点：回调不是语法糖，而是解耦设计的核心工具。它让框架代码（被调用方）无需知道业务逻辑（调用方传入的函数），实现「控制反转」。C 没有闭包，void *priv 就是闭包捕获状态的等价物——这是 C 工程师必须建立的思维模型。

要点

回调三要素

/* 1. typedef 函数指针 */
typedef void (*event_cb_t)(uint32_t event_type, void *priv);

/* 2. void *priv 私有数据 */
struct event_mgr {
    event_cb_t  cb;
    void       *priv_data;
};

/* 3. 注册 / 触发分离 */
void event_register(struct event_mgr *mgr, event_cb_t cb, void *priv)
{
    mgr->cb        = cb;
    mgr->priv_data = priv;
}

void event_trigger(struct event_mgr *mgr, uint32_t type)
{
    if (mgr->cb)                          /* 判空再调 */
        mgr->cb(type, mgr->priv_data);    /* 把 priv 回传 */
}

三个要素缺一不可：

要素 作用 缺失后果
typedef 函数指针 锁定回调签名 签名漂移，UB
void *priv 传递上下文状态 回调拿不到业务数据，闭包失效
注册/触发分离 解耦「谁调」与「何时调」 强耦合，无法复用框架

void *priv 的闭包语义

C 没有闭包，但 void *priv 等价于「闭包捕获的状态」。回调函数收到 priv 后强转回真实类型，访问业务数据：

struct order_ctx {
    uint64_t  user_id;
    uint32_t  max_qty;
    FILE     *log;
};

static void on_quote_arrived(uint32_t type, void *priv)
{
    struct order_ctx *ctx = priv;            /* 强转回真实类型 */
    if (ctx->max_qty > 0) {
        fprintf(ctx->log, "quote type=%u user=%lu\n",
                type, ctx->user_id);
        /* ... 下单逻辑 ... */
    }
}

/* 注册 */
struct order_ctx ctx = { .user_id = 42, .max_qty = 100, .log = stderr };
event_register(&mgr, on_quote_arrived, &ctx);

priv 是 void *，框架代码完全不知道它指向什么——这就是类型擦除。回调函数自己负责强转回正确类型，类型约定由注册方和回调方私下保证。

判空再调：工程铁律

if (mgr->cb) mgr->cb(type, mgr->priv_data);

未注册回调时 cb == NULL，直接调用 NULL(type, priv) 是 UB，通常崩溃但不保证——某些平台可能跳到 0 地址执行。判空是工程铁律，所有框架代码必须遵守。

释放回调：函数指针 + void *

typedef void (*free_cb_t)(void *obj);

void pool_destroy(void **list, int cnt, free_cb_t free_func)
{
    if (!free_func) {                /* 允许调用方不提供 */
        free(list);
        return;
    }
    for (int i = 0; i < cnt; i++)
        free_func(list[i]);          /* 调用方决定怎么释放 */
    free(list);
}

/* 调用方提供释放函数 */
static void order_free_cb(void *obj) {
    struct order *o = obj;
    free(o->payload);
    free(o);
}

free_cb_t 让 pool_destroy 不需要知道元素是什么类型——调用方传入 order_free_cb，框架代码通用。这是 C 实现泛型容器的核心机制，详见 ch17。

多回调链表

struct listener {
    event_cb_t      cb;
    void           *priv;
    struct listener *next;
};

struct event_mgr {
    struct listener *head;
};

void event_notify_all(struct event_mgr *mgr, uint32_t type)
{
    for (struct listener *l = mgr->head; l; l = l->next) {
        if (l->cb)
            l->cb(type, l->priv);
    }
}

观察者模式的标准实现：多个监听者挂链表，事件触发时遍历调用。注意遍历中删除监听者要用 safe 版本（见 ch12.3.2）。

原则 说明

间接调用的性能考量

回调是间接调用，每次 2-4 ns 开销 + 分支预测风险。HFT 数据面对回调的使用原则：

  1. 批量回调：一次回调传一批事件，减少间接调用次数。
  2. 热路径内联：最高频的回调手工展开成直接调用，低频走回调。
  3. 回调表常驻 L1：函数指针数组对齐到 cache 行，避免 cache miss。
/* 批量回调示例 */
typedef void (*quote_batch_cb_t)(const struct quote *qts,
                                  int n, void *priv);

一次调用处理 N 个报价，比 N 次单报价回调高效得多。

13.3

.2 转移表

本节讲什么

转移表（jump table / dispatch table）是函数指针数组的工程化形态——用「数组索引 → 函数指针」的查表替代 if-else if 链，把 O(n) 的分支判断压缩成 O(1) 的间接跳转。这一节给出转移表的完整实现、边界检查、与 if-else 的性能对比，以及它在报文分发、状态机、PMD 驱动表里的实际部署。

认知锚点：转移表不是「炫技优化」，而是数据面代码的默认选择。HFT 报文分发、内核系统调用表、CPU 指令译码器——所有「类型 → 处理函数」的高频映射都用转移表。理解它就理解了 C 工程里「表驱动」的核心思想。

要点

基本形态：索引即类型

typedef void (*pkt_handler_t)(struct rte_mbuf *pkt);

static pkt_handler_t dispatch[] = {
    [0] = handle_heartbeat,   /* MSG_HEARTBEAT = 0 */
    [1] = handle_quote,       /* MSG_QUOTE     = 1 */
    [2] = handle_order,       /* MSG_ORDER     = 2 */
    [3] = handle_cancel,      /* MSG_CANCEL    = 3 */
};

void on_packet(struct rte_mbuf *mbuf, uint8_t type)
{
    if (type < sizeof(dispatch) / sizeof(dispatch[0]))
        dispatchtype;   /* O(1) 间接跳转 */
    else
        handle_unknown(mbuf);   /* 越界保护 */
}

三个关键设计：

  1. 指定初始化 [type] = handler（C99）：表项与类型显式绑定，新增类型只需加一行。
  2. 边界检查：type < sizeof(dispatch) / sizeof(dispatch[0])，防越界访问野指针。
  3. ARRAY_SIZE 宏：
#define ARRAY_SIZE(a) (sizeof(a) / sizeof((a)[0]))
if (type < ARRAY_SIZE(dispatch))
    dispatchtype;

转移表 vs if-else 链

维度 转移表 if-else 链
时间复杂度 O(1) O(n) 平均 n/2 次比较
分支预测 BTB 学习间接跳转 多级条件分支，失败率高
扩展性 表驱动加一行 改代码加 if-else
缺省处理 越界走 default 最后 else 兜底
表大小 占内存（每项 8 字节） 不占额外内存
调试 难（间接跳转） 易（直接看条件）
编译优化 难内联 易内联（编译器可见）
HFT 数据面 首选 少量分支可接受

选型口诀：类型数 ≥ 4 且高频 → 转移表；类型数 ≤ 3 或低频 → if-else。HFT 报文分发通常 4-16 种消息类型，转移表是标配。

性能量级（x86-64）

if-else 4 分支：  约 5-8 ns（含 1-2 次分支预测失败）
转移表 4 项：     约 3-5 ns（BTB 命中间接跳转）
转移表 16 项：    约 3-5 ns（与项数无关，O(1)）

转移表的延迟基本与项数无关，这是 O(1) 的本质。if-else 随分支数线性增长，4 分支以上转移表必胜。

状态机：枚举驱动转移表

typedef enum {
    ST_IDLE,
    ST_WAIT_ACK,
    ST_OPEN,
    ST_CLOSE_PENDING,
    ST_NUM
} state_t;

typedef enum {
    EV_SEND,
    EV_ACK,
    EV_TIMEOUT,
    EV_CLOSE,
    EV_NUM
} event_t;

typedef state_t (*transition_fn_t)(state_t, event_t, void *ctx);

/* 状态转移表：[当前状态][事件] = 转移函数 */
static transition_fn_t fsm[ST_NUM][EV_NUM] = {
    [ST_IDLE] = {
        [EV_SEND]   = idle_to_wait_ack,
        [EV_CLOSE]  = idle_stay,
    },
    [ST_WAIT_ACK] = {
        [EV_ACK]     = wait_ack_to_open,
        [EV_TIMEOUT] = wait_ack_to_idle,
    },
    [ST_OPEN] = {
        [EV_CLOSE]   = open_to_close_pending,
    },
};

state_t fsm_step(state_t cur, event_t ev, void *ctx)
{
    if (cur < ST_NUM && ev < EV_NUM && fsm[cur][ev])
        return fsm[cur][ev](cur, ev, ctx);
    return cur;   /* 无转移，保持当前状态 */
}

二维转移表是状态机的标准实现。fsm[cur][ev] 查表得到转移函数，未定义的转移为 NULL（保持原状态）。这种写法把状态机逻辑变成数据，新增状态/事件只需改表，不动代码。

三类转移表的共同点：

  1. 索引/字段名 → 函数指针：查表替代分支。
  2. const 修饰：只读放 .rodata，多进程共享。
  3. 指定初始化：未实现的槽位默认 NULL，调用方判空。
  4. 统一调用约定：所有函数指针同签名，框架代码通用。

二级函数指针表（插件热切换）

typedef void (*pkt_handler_t)(struct rte_mbuf *);

/* 切换策略表 */
void switch_strategy(pkt_handler_t *new_table)
{
    /* 内存屏障确保其他核看到完整表 */
    smp_wmb();
    table = new_table;
}

pkt_handler_t *table 是「指向函数指针数组的指针」，可以整体替换数组。用于策略热切换：新表预构建完成后，原子替换指针。这是 RCU 模式的简化形态——读端无锁，写端替换整个表。

字符串 key 的转移表

struct cmd_entry {
    const char  *name;
    handler_fn_t fn;
};

static const struct cmd_entry cmd_table[] = {
    {"buy",    cmd_buy},
    {"sell",   cmd_sell},
    {"cancel", cmd_cancel},
    {"query",  cmd_query},
};

void exec_cmd(const char *name, void *arg)
{
    for (size_t i = 0; i < ARRAY_SIZE(cmd_table); i++) {
        if (strcmp(cmd_table[i].name, name) == 0) {
            cmd_table[i].fn(arg);
            return;
        }
    }
    fprintf(stderr, "unknown command: %s\n", name);
}

字符串 key 无法用数组索引，只能线性查找或哈希表。命令分发、配置解析常用这种形态。高频场景下用哈希表（O(1) 平均），低频用线性查找（O(n)，但 n 通常很小）。

HFT 关联

报文分发

typedef void (*msg_handler_t)(const struct market_msg *);

static const msg_handler_t msg_dispatch[] = {
    [MSG_HEARTBEAT] = on_heartbeat,
    [MSG_QUOTE]     = on_quote,
    [MSG_TRADE]     = on_trade,
    [MSG_ORDER]     = on_order,
    [MSG_CANCEL]    = on_cancel,
    [MSG_DEPTH]     = on_depth,
};

static inline void dispatch_msg(const struct market_msg *m)
{
    uint16_t type = m->msg_type;
    if (type < ARRAY_SIZE(msg_dispatch) && msg_dispatch[type]) {
        msg_dispatchtype;
    } else {
        stats_inc(STATS_UNKNOWN_MSG);
    }
}

这是 HFT 数据面最热的代码路径。每个报文进来都要走一次转移表分发，延迟要求纳秒级。优化点：

  1. 表常驻 L1：msg_dispatch 数组 6 项 × 8 字节 = 48 字节，刚好一个 cache 行，热点必命中。
  2. msg_type 在报文头部固定偏移：取类型不需要解析变长字段，1 条 mov 指令。
  3. static inline：内联到调用点，消除函数调用开销。
  4. __builtin_expect：标记 type < ARRAY_SIZE 为 likely，分支预测器优化。

策略热切换

/* 双表 + 原子切换 */
static msg_handler_t *active_table = table_v1;

void switch_to_v2(void)
{
    /* 确保 table_v2 完全可见 */
    smp_wmb();
    active_table = table_v2;
    /* 旧表延迟释放（RCU 或 epoch） */
    synchronize_rcu();
    free(table_v1);
}

策略升级不停机：新表预构建 → 写屏障 → 原子换指针 → RCU 等待读者退出 → 释放旧表。读端完全无锁，写端承担同步成本。这是 HFT 高可用部署的核心机制。

CPU 指令译码器

CPU 的指令译码本质上是转移表：操作码作索引，查表得到执行函数。switch-case 长链（≥ 4 个 case 且密集）编译器会自动生成转移表（-foptimize-jump-tables）。理解这一点就能解释为什么 switch 在密集 case 下比 if-else 快——编译器帮你生成了转移表。

命令行参数

本节讲什么

main(int argc, char **argv) 是 char ** 的标准应用——一个字符串指针数组。这一节把 argv 的内存模型画清楚，给出 getopt 与自研解析的两种范式，以及 DPDK EAL 参数解析在 HFT 工程里的实际形态。

认知锚点：argv 不是「特殊语法」，而是 13.1 多级指针的标准实例。理解 argv 的内存布局，就理解了所有「指针数组 + 字符串字面量」的工程形态——配置表、命令表、错误码字符串表全部同构。

要点

argv 的内存模型

int main(int argc, char **argv)
{
    for (int i = 0; i < argc; i++)
        printf("%s\n", argv[i]);
    return 0;
}

执行 ./myapp -l 0-3 -n 4 -- -p 0x1 时，内存布局：

栈/内核缓冲区:

  argv[1] ----> "-l\0"
  argv[2] ----> "0-3\0"
  argv[3] ----> "-n\0"
  argv[4] ----> "4\0"
  argv[5] ----> "--\0"

argv 的可写性边界

部分 存储 可写
argv[i] 指向的字符串内容 内核传递的缓冲区 实现定义（POSIX 通常可写，但不要依赖）
argv[i] 指针本身 内核分配的指针数组 不可写（修改 argv[i] 是 UB）
argv 本身 栈上局部变量 可改（但无意义）

工程实践：把 argv 字符串视为只读。需要修改时先 strdup 到堆上再操作。部分嵌入式平台 argv 字符串在只读段，写入直接 SIGSEGV。

等价写法

int main(int argc, char **argv);     /* 指针形式 */
int main(int argc, char *argv[]);    /* 数组形式，等价 */
int main(int argc, char *argv[argc]);/* C99 大小标注，等价 */

三种写法完全等价——char *argv[] 作为函数参数退化为 char **（见 ch08 数组退化规则）。第三种 char *argv[argc] 是 C99 VLA 语法，标注大小但不改变语义，仅文档作用。

第三参数 envp（非标准扩展）

int main(int argc, char **argv, char **envp);

POSIX 扩展，第三个参数是环境变量数组，格式 "KEY=VALUE"，以 NULL 结尾。可移植代码不要用，应通过 extern char **environ; 或 getenv/setenv 访问环境变量。

getopt：标准参数解析

#include <unistd.h>

int main(int argc, char **argv)
{
    int opt;
    const char *optstr = "l:n:p::";
    /* l: 需要参数，n: 需要参数，p:: 可选参数 */

    while ((opt = getopt(argc, argv, optstr)) != -1) {
        switch (opt) {
            case 'l':
                printf("cores: %s\n", optarg);
                break;
            case 'n':
                printf("channels: %s\n", optarg);
                break;
            case 'p':
                printf("port mask: %s\n", optarg ? optarg : "(none)");
                break;
            default:
                fprintf(stderr, "Usage: %s -l cores -n channels [-p mask]\n", argv[0]);
                return 1;
        }
    }
    /* optind 指向第一个非选项参数 */
    for (int i = optind; i < argc; i++)
        printf("positional: %s\n", argv[i]);
    return 0;
}

getopt 的全局变量：optarg（当前选项参数）、optind（下一个待处理下标）、opterr（错误时打印）。非线程安全，多线程场景用 getopt_long 或自研解析。

getopt_long：长选项支持

#include <getopt.h>

static struct option long_opts[] = {
    {"cores",   required_argument, 0, 'l'},
    {"channels",required_argument, 0, 'n'},
    {"port",    optional_argument, 0, 'p'},
    {"help",    no_argument,       0, 'h'},
    {0, 0, 0, 0},
};

int main(int argc, char **argv)
{
    int opt, idx;
    while ((opt = getopt_long(argc, argv, "l:n:p::h",
                              long_opts, &idx)) != -1) {
        /* ... */
    }
}

支持 --cores 0-3 和 -l 0-3 两种形式。大型 HFT 应用的配置脚本常用这种。

自研解析：完全控制

struct app_cfg {
    char     core_list[32];
    uint32_t num_channels;
    uint32_t port_mask;
};

static int parse_args(int argc, char **argv, struct app_cfg *cfg)
{
    for (int i = 1; i < argc; i++) {
        if (strcmp(argv[i], "-l") == 0 && i + 1 < argc) {
            snprintf(cfg->core_list, sizeof(cfg->core_list),
                     "%s", argv[++i]);
        } else if (strcmp(argv[i], "-n") == 0 && i + 1 < argc) {
            cfg->num_channels = atoi(argv[++i]);
        } else if (strcmp(argv[i], "--") == 0) {
            /* DPDK EAL 分隔符，之后是应用参数 */
            return i + 1;   /* 返回应用参数起点 */
        } else {
            fprintf(stderr, "unknown arg: %s\n", argv[i]);
            return -1;
        }
    }
    return argc;
}

DPDK 框架自己实现了一套类似 getopt 的解析（rte_eal_init），因为需要支持双段参数（EAL 参数 + 应用参数，以 -- 分隔）。

DPDK EAL 参数解析

/* 典型启动命令 */
/* ./my_hft -l 0-3 -n 4 --log-level=8 -- -p 0x1 --strategy=alpha */

int main(int argc, char **argv)
{
    int ret = rte_eal_init(argc, argv);   /* 解析 EAL 参数 */
    if (ret < 0) rte_panic("EAL init failed\n");

情形 后果 防护

atoi vs strtol

/* 危险：失败返回 0，无法区分 "0" 和非法输入 */
int n = atoi(argv[i]);

/* 安全：endptr 检查是否完全解析 */
char *end;
long n = strtol(argv[i], &end, 10);
if (*end != '\0' || end == argv[i])
    fprintf(stderr, "invalid number: %s\n", argv[i]);

atoi("abc") 返回 0，与 atoi("0") 无法区分。HFT 配置解析必须用 strtol，否则一个 typo 可能让 num_channels = 0 触发后续除零或空分配。

getopt 的全局状态

extern char *optarg;
extern int   optind, opterr, optopt;

getopt 用全局变量传递状态，不可重入。多线程调用会互相覆盖。可移植代码在 main 单线程阶段完成所有 getopt，之后再启动工作线程。

13.5

字符串常量

本节讲什么

字符串字面量（"hello"）在 C 里有两种截然不同的存在形态：作为只读段中的常量（.rodata），和作为栈/堆上的字符数组（char buf[] = "hello"）。这一节把两者的存储、可写性、生命周期讲清楚，并给出指针数组 of 常量 vs 动态 strdup 数组的选型对比。

认知锚点：字符串字面量是 C 工程里最高频的 UB 来源之一——char *p = "hello"; p[0] = 'H'; 在某些平台崩溃、某些平台「能跑」，是典型的「实现定义 + UB」混合陷阱。理解字面量的存储位置，是写出可移植、无 UB 代码的前提。

要点

两种形态：只读引用 vs 栈拷贝

const char *p = "hello";   /* 字面量在 .rodata，p 指向它 */
char buf[]  = "hello";     /* 字面量在 .rodata，但 buf 是栈数组，拷贝一份 */
形态 存储 可写 sizeof 生命周期
const char *p = "x" .rodata 否 8（指针） 程序全程
char *p = "x" .rodata 否（但编译器允许写，UB） 8 程序全程
char buf[] = "x" 栈 是 6（含 \0） 函数返回即失效
char *p = malloc(6); strcpy(p, "x"); 堆 是 8（指针） free 前

关键区别：char buf[] = "x" 是用字面量初始化一个栈数组，字面量本身仍在 .rodata，但 buf 是独立拷贝，可写、sizeof 是数组大小（6 字节，含 \0）。char *p = "x" 是指针指向只读字面量，sizeof(p) 是指针大小（8 字节），写入是 UB。

.rodata 段与只读保护

const char *proto = "heartbeat";   /* 字面量在 .rodata */
char *bad = "text";                /* 旧代码；写 → SIGSEGV */

.rodata 段（read-only data）在程序启动时由操作系统映射为只读页。任何写入尝试触发硬件页错误，进程收到 SIGSEGV 崩溃。这是操作系统层面的保护，不依赖编译器检查。

进程虚拟地址空间:
  +------------------+
  | .text   (代码)    |  只读 + 可执行
  +------------------+
  | .rodata (常量)    |  只读          <-- 字面量在这里
  +------------------+
  | .data   (已初始化)|  读写
  +------------------+
  | .bss    (零初始化)|  读写
  +------------------+
  | heap             |  读写
  +------------------+
  | stack            |  读写
  +------------------+

字面量 "heartbeat" 编译后进入 .rodata，多个相同字面量通常合并（编译器去重，节省空间）。

char *p = "x" 的历史包袱

char *p = "hello";   /* C89 允许，C11 弃用，C23 移除 */
p[0] = 'H';          /* UB：写只读页，SIGSEGV */

C89 时代字面量存储区不一定只读（取决于实现），char *p = "x"; p[0] = 'H'; 在某些老旧系统上「能跑」。C99 起 char *p = "x"（非 const）被标记为弃用，C23 正式移除该隐式转换。现代代码必须用 const char *：

const char *p = "hello";   /* 正确 */

-Wwrite-strings 编译选项把 char *p = "x" 的警告升级为错误，强制 const。HFT 工程必开。

字面量拼接与相邻自动合并

const char *msg = "hello, "
                  "world";   /* 等价 "hello, world" */

相邻字符串字面量在编译期自动合并，常用于长字符串换行书写、宏定义字符串组合。运行期无拼接开销，纯编译期处理。

字面量与字符常量的区别

const char *s = "a";   /* 字符串字面量：'a' + '\0'，2 字节 */
char c = 'a';          /* 字符常量：int 类型，1 字节存储 */

'a' 是 int 类型（C 标准），不是 char。sizeof('a') == 4（x86-64）。这是 C 与 C++ 的差异之一——C++ 中 'a' 是 char。<ctype.h> 函数（isdigit 等）的参数是 int，正是为此设计（见 ch09 ctype）。

指针数组 of 常量

const char *msgs[] = {
    "QUOTE",
    "ORDER",
    "CANCEL",
};

/* 内存布局：
   msgs[0] --> "QUOTE\0"   (.rodata)
   msgs[1] --> "ORDER\0"   (.rodata)
   msgs[2] --> "CANCEL\0"  (.rodata)
   msgs[3] = NULL          (如果显式初始化加 NULL)
*/

msgs 数组本身在 .data 或栈（取决于声明位置），每个元素是 const char * 指向 .rodata 的字面量。这种结构无需分配堆内存，启动即就绪，是协议名表、错误码字符串表的标准形态。

指针数组 of 常量 vs 动态 strdup 数组

维度 const char *msgs[] char **table = calloc + strdup
存储 .rodata + .data 全堆
可写 否（字面量只读） 是（strdup 拷贝可改）
生命周期 程序全程 手动 free
初始化开销 0（编译期完成） 启动时 malloc + strcpy
释放 无需 逐元素 free + 数组 free
适用场景 固定常量表 动态构建的字符串集合

选型口诀：编译期已知的字符串表 → 指针数组 of 常量；运行期动态生成的字符串 → strdup 数组。HFT 协议名表、消息类型表用前者；订单日志、动态配置用后者。

字面量作函数参数

/* 字面量直接传参：传的是 .rodata 的地址 */
log_msg("connection reset by peer");

/* 等价于 */
const char *tmp = "connection reset by peer";
log_msg(tmp);

字面量作参数传递的是 .rodata 中的地址，零拷贝。这是 C 工程里最高效的字符串传递方式，比 std::string（C++）构造析构快得多。

错误码字符串表

    [ERR_OK]          = "ok",

const char *err_to_str(int err)
{

错误码 → 字符串的查表，零运行开销（编译期生成）。比 strerror（标准库但实现各异）更可控，HFT 工程倾向自建错误码表。

日志模板

#define LOG_FMT_QUOTE  "quote sym=%s bid=%u ask=%u"
#define LOG_FMT_ORDER  "order id=%lu side=%c qty=%u"

log_info(LOG_FMT_QUOTE, sym, bid, ask);

日志格式字符串是 .rodata 字面量，宏定义集中管理，便于统一修改。__attribute__((format(printf, ...))) 让编译器检查格式与参数类型匹配，防格式串漏洞。

配置默认值的字面量

static const char *const default_cfg = {

字面量与 ASan

char *p = "hello";
p[0] = 'H';   /* 写只读页 */

ASan 能在编译期或运行期捕获部分此类 UB（-fsanitize=address 配合 -Wwrite-strings）。但.rodata 只读保护是硬件级的，即使不开 ASan 也会触发 SIGSEGV。可移植代码必须 const char *，不依赖任何工具。

UB 边界

情形 后果 防护
char *p = "x"; p[0] = 'X'; SIGSEGV（写只读页） const char * + -Wwrite-strings
char buf[] = "x"; buf[1] = 'y'; 写到 \0 字符串变 "xy"，无 \0 终止 显式 buf[sizeof(buf)-1] = '\0'
char buf[3] = "abcd"; 截断为 "ab\0"（C 标准允许） 用 char buf[5] = "abcd" 或显式长度
字面量作 strtok 第一参数 写 .rodata，UB strtok 只用于可写字符串

修改字面量拼接结果 UB（拼接在 .rodata） 视为只读

strtok 的字面量陷阱

char *tok = strtok("a,b,c", ",");   /* UB：strtok 会写入第一参数 */

strtok 会修改输入字符串（插入 \0 分割 token）。字面量在 .rodata，写入 UB。必须先 strdup：

char *copy = strdup("a,b,c");
char *tok = strtok(copy, ",");
/* ... */
free(copy);

详见 ch09 strtok 的非重入性与 UB 分析。

char buf[3] = "abcd" 的截断

char buf[3] = "abcd";   /* C 标准允许，buf = {'a','b','\0'} */

数组太小放不下完整字面量，C 标准允许截断（与 char buf[3] = {'a','b','\0'} 等价）。这不是 UB，但容易引发字符串长度误判——strlen(buf) == 2，而字面量本意是 4 字符。-Wstringop-truncation 警告此类隐患。

字面量与 wide string

const wchar_t *w = L"hello";   /* 宽字符串字面量 */
const char8_t *u8 = u8"hello"; /* C23 UTF-8 字面量 */
const char16_t *c16 = u"hello";
const char32_t *c32 = U"hello";

不同前缀的字面量存储在不同段（编码不同），但可写性规则一致：全部只读。HFT 国际化场景（中文报错信息）用 UTF-8 字面量，但数据面极少涉及，主要在管理面。

题目 1： 以下代码有什么问题？

char *get_msg(void) {
    char msg[] = "hello";
    return msg;
}
参考答案

返回局部数组地址——未定义行为。msg 是局部数组，存储在栈上，函数返回后栈空间被回收。调用方得到的指针指向已失效的内存。正确做法：(1) 用 static char msg[]；(2) 动态分配 malloc；(3) 由调用方传入缓冲区。
