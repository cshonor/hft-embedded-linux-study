环境

本节讲什么

C 程序所处的两种环境：翻译环境（编译器+链接器把源码变成可执行文件）和执行环境（操作系统加载并运行程序）。这两个环境是两套完全不同的世界——翻译环境关心符号、类型、链接；执行环境关心内存段、进程、指令执行。本章从"环境"这个最高视角，说明词法/语法/链接/内存这些后续话题各自落在哪个环境里。

两种环境的本质区别

维度 翻译环境 执行环境
何时发生 编译期（开发机） 运行期（目标机）
主体 编译器 + 链接器 OS 内核 + CPU
处理对象 源码文本 → 机器码 进程地址空间 → 指令执行
关心的事 语法/语义正确、符号解析、优化 内存映射、栈/堆、调用约定、IO
错误表现 编译错误/链接错误 崩溃/段错误/逻辑错误
工具 gcc/ld/readelf gdb/strace/perf

核心认知：很多 bug 跨越这两个环境。比如"返回局部变量地址"在翻译环境完全合法（语法对、类型对、链接对），但在执行环境是悬垂指针 UB。理解两环境分工，才能定位 bug 属于哪一类。

经典示例：返回局部变量地址

int *fun(void)
{
    int tmp = 100;    /* tmp 是栈上局部变量 */
    return &tmp;      /* 返回局部变量地址 */
}

int main(void)
{
    int *p = fun();   /* p 指向已销毁的栈内存 */
    *p = 999;         /* UB：访问已释放内存 */
    return 0;
}
阶段 发生了什么 结果
翻译环境（编译+链接） 语法正确、int* 返回值与 &tmp 类型匹配、符号链接正常 ✅ 编译通过，生成可执行文件
执行环境（运行） fun() 栈帧创建 tmp → return 销毁栈帧 → p 指向已回收的栈内存 ❌ 悬垂指针，*p=999 是 UB

翻译环境只管语法/类型/符号，不管内存生命周期。栈帧销毁是执行环境的事，编译器不知道（也不负责）。

Rust 怎么解决同一个问题

Rust 的核心思路：把内存生命周期检查从执行环境搬到翻译环境（编译期）。

// 等价 Rust 代码 —— 编译直接拒绝
fn fun() -> &i32 {
    let tmp = 100;
    &tmp       // ❌ 编译错误：cannot return reference to local variable `tmp`
}

编译器报错核心：returns a reference to data owned by the current function。Rust 的借用检查器（borrow checker）在编译阶段就知道 tmp 归当前函数拥有，函数结束 tmp 销毁，返回引用生命周期不匹配 → 拒绝构建二进制。

维度 C Rust
返回局部变量引用 编译通过（可能警告），运行 UB 编译直接报错，无法生成程序
生命周期检查 执行环境（无保护，靠人脑） 翻译环境（借用检查器）
编译器知道什么 类型、符号 类型 + 所有权 + 生命周期

Rust 的合法替代写法：

// ① 返回所有权（move），不是引用
fn fun1() -> i32 {
    let tmp = 100;
    tmp        // 值被移动出去，无引用问题
}

// ② 堆分配 Box（类似 C 的 malloc）
fn fun2() -> Box<i32> {
    Box::new(100)   // 堆上分配，所有权转移给调用者
}

但 Rust 不是万能：unsafe 块里可以手动操作裸指针，绕过借用检查器，同样能制造悬垂指针——这部分交给程序员自己保证。

核心洞察：C 的翻译环境只做类型检查，不理解所有权/生命周期；Rust 在翻译环境新增了一套所有权+生命周期逻辑，把大量 C 中"运行才炸"的 bug 提前扼杀在编译阶段。

同类"编译没问题，运行爆炸"的 BUG

BUG 翻译环境 执行环境
返回局部变量地址 语法合法，类型匹配 悬垂指针，访问已销毁栈内存
野指针 语法合法 访问随机垃圾地址 → SIGSEGV
数组越界 编译器不检查边界 破坏栈/堆，随机崩溃
use-after-free 语法合法 访问已释放堆内存 → UB

口诀：翻译环境抓语法/类型错误；内存生命周期、栈销毁、越界、悬垂指针属于执行环境，是 UB，编译器不保证报错。

翻译环境速览（详见 2.1.1）

源码 → 可执行，分四阶段（与 ch01 一致）：

.c  ─预处理─→ .i  ─编译─→ .s  ─汇编─→ .o  ─链接─→ 可执行 ELF
  • 翻译环境的核心产物是 ELF（可执行文件）
  • 翻译环境的典型错误：undefined reference（符号没定义）、multiple definition（符号多处定义）、语法错误
  • 一个 .c + 它 include 的所有头，预处理后 = 一个翻译单元——这是链接的基本单位

执行环境速览（详见 2.1.2）

可执行 ELF 被 OS 加载成进程：

execve() → 内核映射 ELF 段 → crt0 初始化 → main() → return → exit() → 内核回收
  • 执行环境的核心是进程地址空间：text/data/bss/stack/heap
  • 执行环境的典型错误：段错误（访问非法地址）、栈溢出、悬垂指针、数据竞争
  • 执行环境的内存布局决定了变量的生命周期和可见性（ch03/ch18）

为什么"环境"对 HFT/内核/DPDK 至关重要

现实问题 属于哪个环境 根源
undefined reference to rte_mbuf_alloc 翻译 忘链接 librte_mbuf 或头路径不对
multiple definition of g_config 翻译 同一全局变量多处定义
程序启动就段错误 执行 全局构造或 init 段访问非法地址
跑了一段时间崩溃，栈指向已释放内存 执行 悬垂指针/堆损坏
多线程数据竞争 执行 共享变量无锁访问
DPDK worker 栈太小崩溃 执行 栈空间不足

口诀：编译/链接错误查翻译环境，运行崩溃查执行环境。先分清是哪一类，再选工具（readelf/ld vs gdb/valgrind）。

题目 1： C 程序的翻译阶段中，预处理发生在哪个阶段？以下代码经过预处理后会变成什么？

.1 翻译

本节讲什么

翻译：源码变成可执行文件的完整过程。承接 ch01 的四阶段实操，本节从概念层讲清楚每一步在做什么、翻译单元是什么、链接为什么是独立的一步、以及最常见的链接报错从何而来。理解翻译环境，是看懂 DPDK/内核多模块构建、解决符号冲突的前提。

翻译四阶段（概念版）

阶段 输入 → 输出 做什么 关键概念
1. 预处理 .c → .i 展开 #include/#define、删注释、处理 #ifdef 翻译单元在此形成
2. 编译 .i → .s 词法→语法→语义分析→优化→生成汇编 类型检查在此完成
3. 汇编 .s → .o 汇编翻译成机器码 产物是 ELF Relocatable，符号可能未定义
4. 链接 多 .o → 可执行 解析未定义符号、重定位、合并段 单定义规则

与 ch01 的关系

ch01 讲的是怎么操作（gcc -E/-S/-c 命令、看产物）；本节讲的是为什么（每步概念、翻译单元、链接规则）。两者互补：操作让你动手，概念让你理解报错。

翻译单元：链接的基本单位

一个 .c 文件，经过预处理后（所有 #include 展开、宏替换完成），就是一个翻译单元（translation unit）。

/* main.c */
#include <stdio.h>          /* stdio.h 内容被插入 */
#include "config.h"         /* config.h 内容被插入 */
int main(void) { ... }

预处理后，main.c + stdio.h + config.h 的所有内容拼成一个 .i 文件——这就是一个翻译单元。

翻译单元的规则

  • 每个翻译单元独立编译成 .o
  • 声明（extern、函数原型）可以多次出现，只要一致
  • 定义（分配存储或生成代码）在整个程序中只能一次（外部链接的符号）
  • static 修饰的定义是内部链接——只在当前翻译单元可见，不参与全局符号解析

这就是为什么"头文件放声明、.c 放定义"——头文件被多个 .c include，如果放定义就会多处定义。

声明 vs 定义：链接的核心

声明 定义
作用 告知类型/签名，不分配 分配存储或生成代码
可出现次数 多次（只要一致） 整个程序一次（外部链接）
变量 extern int g_val; int g_val = 10;
函数 void func(int x); void func(int x) { ... }
结构体 struct rte_mbuf;（不完整类型） struct rte_mbuf { ... }; 
/* config.h —— 放声明 */
#ifndef CONFIG_H
#define CONFIG_H
extern int g_port;              /* 声明：不分配，告知类型 */
void init_server(int port);     /* 声明：函数原型 */
#endif

/* config.c —— 放定义 */
#include "config.h"
int g_port = 8000;              /* 定义：分配存储 */
void init_server(int port) {    /* 定义：生成代码 */
    g_port = port;
}

/* main.c —— 用声明 */
#include "config.h"
int main(void) {
    init_server(g_port);        /* 链接时找到 config.c 的定义 */
    return 0;
}

链接：符号解析与单定义规则

链接器（ld）把多个 .o 合并成一个可执行文件，核心工作是符号解析：

  1. 收集所有 .o 的符号表（每个 .o 声明了哪些符号、引用了哪些符号）
  2. 把"引用的符号"和"定义的符号"匹配
  3. 匹配成功 → 重定位（填入地址）；匹配失败 → 报错

三种链接报错

报错 含义 常见原因
undefined reference to xxx 引用了符号但没有定义 忘写实现、忘链接 .o/库、static 导致不可见、C++ name mangling
multiple definition of xxx 同一符号多处定义 头文件放了定义、全局变量多处初始化、忘加 static
cannot find -lxxx 找不到库 -L 路径不对、库没安装、库名写错

暂定定义（tentative definition）与 -fcommon 陷阱

/* file1.c */ int counter;    /* 未初始化的全局——"暂定定义" */
/* file2.c */ int counter;    /* 又一个暂定定义 */
  • C 标准允许未初始化的文件作用域声明作为暂定定义：如果到翻译单元结束都没出现带初始化的定义，它就成为定义
  • 两个 .c 各有一个暂定定义 → 严格按标准是 UB
  • gcc 9 及以前默认 -fcommon：未初始化全局放进 common block，链接器合并成一个符号——不报错
  • gcc 10 起默认 -fno-common：各自进 .bss，直接 multiple definition
  • 教训：① 老代码"能跑"不代表合规，编译器收紧后突然集体报错就是这个原因；② 正确写法永远是一处定义 + 其余 extern 声明

修复链接报错的思路

  1. undefined reference：这个符号应该在哪定义？那个 .c/.o/.a/.so 链接进来了吗？
  2. multiple definition：哪个符号被定义了多次？是不是头文件里放了定义（应改 extern 声明）？
  3. cannot find -l：-L 路径对吗？pkg-config --libs xxx 看正确的链接参数。

DPDK/内核构建系统（meson/Kbuild）最终生成的就是一堆 gcc -c + ld 命令。看懂链接报错，是使用这些构建系统的基础。

多文件工程模型（DPDK/内核缩影）

app/
├── main.c          → main.o      （翻译单元 1）
├── net.c           → net.o       （翻译单元 2）
├── parser.c        → parser.o    （翻译单元 3）
└── Makefile

链接: gcc main.o net.o parser.o -lrte_mbuf -lrte_eal -o app
  • 每个 .c 独立编译——改一个只需重编一个 .o，再链接（增量编译）
  • .h 是翻译单元之间的接口契约——声明共享的函数和类型
  • static 函数/变量是翻译单元私有的，不暴露给其他 .o——封装机制

常见误区

误区 纠正
头文件放变量定义 头被多个 .c include → 多重定义；头只放 extern 声明
static 函数能被其他文件调用 static = 内部链接，只在本翻译单元可见
extern 分配内存 extern 只是声明，不分配；定义在某个 .c
改了 .h 不用重编 .h 是文本插入，所有 include 它的 .c 都要重编
链接错误是语法错误 链接是第 4 阶段，语法在第 2 阶段已检查完；链接错误是符号解析失败
C 和 C++ 可以直接互链 C++ 有 name mangling，C 函数要 extern "C" 包裹才不 mangle
两个 .c 都写未初始化全局"老代码能跑" 暂定定义 + -fcommon 的历史合并行为；gcc 10+ 默认 -fno-common 报 multiple definition

实操

  1. 写两个 .c + 一个 .h 的工程，故意把定义放头文件，看 multiple definition
  2. 故意删掉一个函数实现，看 undefined reference
  3. 用 nm main.o 看符号表，区分 U（未定义）、T（text 段已定义）、D（data 段）
  4. gcc -c a.c b.c 后 gcc a.o b.o -o app，体验增量编译
  5. DPDK 示例：看一个 meson 构建的链接命令（ninja -v），理解它生成了什么

题目 1： 以下代码经过翻译阶段后，注释和连续的空白字符会怎样处理？

int/* comment */x = 1  +  2;
参考答案

翻译阶段会把注释替换为一个空格，多个连续空白字符合并为一个。结果是：int x = 1 + 2;。所以 int/ comment /x 等价于 int x，不会粘连成 intx。

题目 2： gcc a.c b.c，两个文件里都只有一句 int g_count;（无初始化、无 extern），会怎样？

参考答案

两个都是暂定定义（tentative definition）。C 标准层面这是 UB；实际结果取决于编译器：

  • gcc 10+（默认 -fno-common）：报 multiple definition of 'g_count'
  • gcc 9 及以前（默认 -fcommon）：链接器合并成一个符号，不报错——所以老代码"能跑"纯属历史兼容

正确写法：一个 .c 里 int g_count;（定义），另一个写 extern int g_count;（声明）。

.2 执行

本节讲什么

执行环境：操作系统把可执行 ELF 加载成进程、划分虚拟内存段、调用 main、顺序执行直至 return。承接 ch01.1.3 的运行链路，本节从内存模型角度讲清楚每个变量住在哪个段、什么生命周期、为什么栈上变量不清零。这是理解悬垂指针、栈溢出、.bss 清零等问题的地基。

加载与入口链路

1. shell 解析命令 → fork + execve("./app", argv, envp)
2. 内核 execve：
   ├── 读 ELF 头，校验 magic (0x7f 'E' 'L' 'F')
   ├── 建新进程地址空间
   ├── 按 Program Headers 映射各段到虚拟地址
   │     ├── .text  → 可读可执行
   │     ├── .rodata → 只读
   │     ├── .data  → 可读写
   │     └── .bss   → 可读写（不占文件，运行时清零）
   ├── 设置栈：压入 argc/argv/envp/auxv
   ├── 设置入口指令地址（ELF e_entry，通常是 _start 而非 main）
   └── 跳转入口
3. _start（crt0 启动代码）：
   ├── 对齐栈、设置 ABI
   ├── 调用 __libc_start_main
   │     ├── 运行 .init / 全局构造（C++）
   │     ├── 调用 main(argc, argv, envp)
   │     └── main 返回后调用 exit()
4. exit() → atexit 清理 → 刷新 stdio → _exit() syscall → 内核回收

关键认知：main 不是真正的入口，ELF 的 e_entry 指向 _start；main 只是"用户代码的入口"。readelf -h app | grep Entry 能看到真实入口地址。详见 ch18。

.bss 清零机制（重要）

  • .bss 段在 ELF 文件里不占空间——只记录大小和起始地址
  • 加载时，内核/loader 把这片内存清零
  • 所以"未初始化的全局/static 变量是 0"——这是加载器保证的，不是编译器
  • 嵌入式裸机/某些 RTOS 不一定有这个清零步骤——所以嵌入式代码常显式初始化全局变量

栈上 auto 变量不清零（陷阱根源）

void f(void) {
    int x;        /* 栈上，未初始化 */
    printf("%d\n", x);   /* UB：值不定，可能是上次函数留下的脏数据 */
}
  • 栈内存被反复复用——这次 f 的 x 用的可能是上次某个函数用过的同一片栈
  • C 标准：读取未初始化 auto 变量是 UB（未定义行为）
  • 实际表现：可能恰好是 0、可能是垃圾值、可能每次不同
  • 报文解析、临时缓冲必须初始化——int x = 0; 或 memset

堆的真相：brk 与 mmap（malloc 的底层）

malloc 不是系统调用，是 glibc 在两个 syscall 之上做的分配器：

分配大小 底层机制 特点
小块（默认 < 128KB） brk/sbrk 抬高 program break 堆紧贴 .bss 连续生长，释放后内存留在 glibc free list 复用
大块（≥ 128KB） mmap(NULL, size, PROT_RW, MAP_ANON|MAP_PRIVATE) 独立映射，free 时直接 munmap 归还内核
  • "free 了 RSS 不降"的经典现象：小块走 brk，只有堆顶的内存才可能收缩归还；中间释放的块留在 glibc 空闲链表里，/proc/<pid>/status 的 VmRSS 不变——HFT 内存监控必知
  • 多线程：glibc 主 arena 用 brk，per-thread arena 用 mmap——减少 malloc 锁竞争的手段
  • 验证：strace ./app 观察 brk(NULL)/brk(0x...)/mmap 序列；阈值可用 MALLOC_MMAP_THRESHOLD_ 环境变量调整
  • DPDK/HFT 常直接绕开 malloc：启动时 mmap hugepage 预分配内存池，热路径零分配

执行模型：顺序执行

  • 默认顺序执行语句，一条接一条
  • 控制语句（if/for/while/switch/goto）改变执行流（ch04）
  • goto 的标签仅函数作用域——不能跨函数 goto
  • 函数调用：压返回地址、建新栈帧、跳转；return 销毁栈帧、恢复返回地址（详见 ch18.1.3）
  • 多线程：每个线程有自己的栈，但共享 .data/.bss/heap——这是数据竞争的根源

为什么"执行环境"对 HFT 至关重要

现实问题 执行环境机制

HFT 实战：内存位置的选择

  • 热路径缓冲：预分配静态/堆，避免运行时 malloc 抖动
  • per-CPU 数据：放结构体数组，按 CPU id 索引——避免跨核 cache line 共享（伪共享）
  • 栈上小对象：可以用，但别太大；注意不要返回其地址
  • 报文元数据：DPDK mbuf 池预分配在 hugepage，不是栈/普通堆

常见误区

返回栈地址 vs 返回堆地址

/* ❌ 返回栈上局部变量地址——悬垂指针 */
int *bad_fun(void)
{
    int tmp = 100;   /* 栈上，函数返回即销毁 */
    return &tmp;     /* 返回已销毁内存的地址 */
}

/* ✅ 返回堆上 malloc 地址——安全 */
int *good_fun(void)
{
    int *p = malloc(sizeof(int));  /* 堆上，不随函数返回销毁 */
    *p = 100;
    return p;       /* 安全：堆内存直到 free() 才释放 */
}
栈上局部变量 堆上 malloc
生命周期 函数返回即销毁 直到 free() 才释放
返回其地址 悬垂指针 安全
谁管理 编译器自动 程序员手动
翻译环境 语法合法，不报错 语法合法
执行环境 ❌ 访问已销毁内存 ✅ 内存仍有效

根本原因：栈帧是函数私有的，函数退出就还给栈；堆是进程级共享池，不归任何函数管，必须显式释放。返回 malloc 的指针安全，但调用者负责 free——忘了就是内存泄漏。

题目 1： 以下代码的行为是定义的还是未定义的？为什么？

int a = 1;
a = a++ + 1;
参考答案

未定义行为（UB）。a = a++ + 1 中，a 在同一个序列点内被修改两次（一次是 a++ 的副作用，一次是 a = ... 的赋值），C 标准没有规定这两个修改的顺序。不同编译器可能产生不同结果。正确写法是拆成两步。

题目 2： 程序里 malloc(1MB) 后立刻 free，/proc/self/status 的 VmRSS 一定下降吗？

参考答案

不一定，取决于分配走哪条路：

  • 1MB ≥ 默认阈值（128KB）→ 走 mmap，free 时 munmap 会归还，RSS 下降
  • 但如果分配的是很多小块（如 100 万个 1 字节 + 开销）→ 走 brk，释放后留在 glibc 空闲链表，RSS 不降
  • 另外 glibc 有 mmap 阈值动态调整：释放过大的 mmap 块会抬高阈值，之后同样大小改走 brk——"第一次 free 降、第二次不降"就是它

验证：strace 看 brk/mmap 调用序列。

词法规则

本节讲什么

编译器的词法分析（lexical analysis）是翻译的第一步：把源码字符流切成一个个 Token（记号）。C 有五类基础 Token；最长匹配（贪心法）原则决定如何切分。这一节是《C 陷阱与缺陷》ch01/ch02 的核心——很多"诡异"的 bug（a+++b 怎么切、06 为什么非法、/* 在字符串里算不算注释）都源于词法规则。

  ▼

  • 词法分析不懂类型——a + b 它只切出 a + b 三个 token，不管 a/b 是什么类型
  • 一个 token 是"不可分割的最小词法单元"——++ 是一个 token，不是两个 +

最长匹配（贪心法/Maximal Munch）

编译器在切 token 时，总是读尽可能长的合法 token。

这是词法分析的核心规则，也是很多"诡异"行为的根源：

经典例子

a+++b

怎么切？

切法 是否合法
a + ++ b ❌ + ++ 之间——贪心法先读 ++ 还是 +？
a ++ + b ✅ 贪心法从左到右读最长：先 a，再 ++（比 + 长），再 +，再 b

所以 a+++b = (a++) + b，不是 a + (++b)。

更多例子

表达式 实际切分 不是
a+++b a ++ + b a + ++ b
a---b a -- - b a - -- b
a+++++b a ++ ++ + b → ((a++)++) + b → 编译错误（a++ 不是左值） —
x/*y x /*y...（开始注释！） x / * y
n+++++m n ++ ++ + m → 错误 —

陷阱：除法和指针解引用

int a = 10;
int *p = &a;
int b = a/*p;    /* 想做 a / (*p)，但 /* 被当成注释开始！ */

/* 是注释起始 token，贪心法先匹配它。结果后面全被注释掉，b 成了 int b = a 后面什么都没有 → 语法错误。

修复：int b = a / *p;（加空格）或 int b = a / (*p);。

《C 陷阱与缺陷》ch1.3 的经典案例。贪心法不是"聪明"而是"机械"——它不懂你的意图。

陷阱：八进制字面量

int a = 0123;    /* 八进制！= 1*64 + 2*8 + 3 = 83，不是 123 */
int b = 09;      /* 错误：八进制不能有 9 */

前导 0 表示八进制——这是词法规则，不是"前导零被忽略"。详见 2.2.1。

贪心法的边界：空白的作用

空白（空格/制表/换行）是 token 分隔符——它强制词法分析器在空白处"断开"：

a + ++b      /* 空白断开：a + (++b) */

所以加空格能控制 token 切分——这是解决贪心法陷阱最简单的方法。

字符与编码

char 的本质

  • C 的 char 是最小整型，占 1 字节（8 bit）
  • char 是 signed char 还是 unsigned char？由实现定义——x86/gcc 默认 signed，ARM 默认 unsigned

  • 定宽用 <stdint.h>：int8_t/uint8_t

字符常量 'A'

要点 说明
'A' 的类型 int，不是 char！（C 标准规定）
'A' 的值 实现定义的字符编码值（ASCII 下为 65）
sizeof('A') 在 C 中是 sizeof(int) = 4；在 C++ 中是 sizeof(char) = 1（著名的 C/C++ 差异）
转义序列 '\n' '\t' '\0' '\\' '\'' '\x41'（十六进制）'\101'（八进制）

陷阱：'A' 是 int 不是 char。sizeof('A') 在 C 里是 4——这是 C/C++ 的一个经典差异，面试常考。

  • gcc 小端下后写的字符在高位：'ab' = 0x6162（注意和直觉相反）
  • 内核/DRM/v4l2 里常见 fourcc 魔数就这么写——读内核代码要认识
  • 自己代码里报文魔数建议用十六进制 + 注明端序，更可移植：0x4D5A /* "MZ", little-endian */

八进制陷阱（常见）

int c = 010;     /* 八进制 = 8，不是 10 */

  • HFT/硬件：硬件地址几乎都用十六进制 0x...，不会误用八进制；但"对齐前导零"是真实陷阱

  • 寄存器定义、内存地址、位掩码、报文魔数——全用十六进制

char *s = "hello";

  • "hello" 在 .rodata（只读）
  • s 指向 .rodata 的地址
  • s[0] = 'H' 试图写只读内存 → SIGSEGV

修复：用数组（栈上副本）：

char s[] = "hello";   /* 复制到栈上，可修改 */
s[0] = 'H';           /* OK */

这是 ch06/ch09 的重要前置：char *s = "..." 和 char s[] = "..." 的本质区别——前者指向只读 .rodata，后者在栈上复制一份。

题目 1： 以下哪个不是合法的 C 字符常量？为什么？

char a = '\\';

char d = '\x41';
参考答案

C 不合法。\0x41 不是标准的转义序列——\0 是八进制转义（值为 0），后面 x41 是普通字符。\x41 才是十六进制转义（值为 65，即 A）。\ 是反斜杠本身，\n 是换行。

题目 2： 以下判断哪里错了？

char buf[64] = "hello";
if (buf[5] == '0')     /* 判断字符串结尾 */
    return;
参考答案

'0' 是 ASCII 字符零，值为 48；字符串结尾是 NUL，应写 '\0'（值为 0）。buf[5] 是 NUL（0），48 == 0 永远为假——这个判断永远不成立。正确写法：if (buf[5] == '\0') 或 if (!buf[5])。

.2 注释

本节讲什么

从词法层看注释：两种语法、预处理阶段删除、不能嵌套、字符串内的"伪注释"。本节与 1.1.1 互补——1.1.1 讲工程规范（好注释写 why），本节讲词法机制（注释怎么被处理、为什么嵌套出错）。

两种注释语法

/* 块注释：可跨行，不能嵌套 */
// 行注释：C99+，到行尾
维度 /* */ //
标准 C89/C90 正式 C99 才标准化
多行 原生支持 每行都要 //
嵌套 不能 可在块注释内出现
屏蔽大段 不能（嵌套出错） —

预处理阶段删除（关键词法机制）

注释在预处理阶段被删除（替换成单个空格），发生在：

源码 → 预处理（删注释、展开宏/include） → 编译

推论：

  1. 注释不进入编译产物——.o 里没有注释，运行时也没有；注释不影响性能
  2. .i 文件里注释已消失——gcc -E main.c 看不到原注释
  3. 注释内的代码不生效——/* int x = 0; */ 的赋值不会执行
  4. 注释内的关键字/符号完全无效——/* if while for */ 不影响编译

不能嵌套（词法陷阱）

/* 外层注释开始
   /* 内层注释 */
   这一行已经不是注释了！*/   ← 第一个 */ 就结束了外层注释
  • 词法分析器从 /* 开始进入注释状态，遇到第一个 */ 就结束
  • 第二个 */ 成了多余的符号 → 语法错误，或者"恰好"被当成除法×指针解引用

屏蔽大段代码的正确方法

#if 0
/* ... 一大段代码，可能内含块注释 ... */
#endif
  • #if 0 ... #endif 是预处理指令，可以嵌套，屏蔽任何内容
  • 比 /* */ 安全——不会因为内含 */ 出错
  • 内核/工程代码屏蔽大段首选 #if 0

字符串内的"伪注释"

char *s = "/* this is not a comment */";
char *t = "// not a comment either";

词法分析器先识别字符串字面量，再识别注释。所以字符串内的 /* 和 // 不被当注释。

这也解释了 a/*p 陷阱：词法分析器不区分"你想表达除法×解引用"还是"开始注释"，它机械地匹配 /*。详见 2.2。

行注释的续行

// 这是一个行注释 \
继续注释（续行符 \ 把下一行接上）
  • 行注释遇到 \ + 换行会续到下一行——这是预处理行的续行规则
  • 容易踩：行注释末尾不小心有个 \，下一行也被注释掉

注释 vs 代码的边界场景

写法 结果
int x = 1 /* comment */ + 2; x = 3（注释替换成空格）
int x = 1/* */2; x = 12？还是 3？→ 标准规定替换成一个空格，所以是 1 2 → 两个 token → 语法错误
// comment 在 C89 非标准，老编译器可能报错或当 // 除法
/* */ 跨行 合法

工程规范差异

规范 偏好
Linux 内核 仅 /* */（Linus 明确要求）
DPDK 应用层 // 与 /* */ 均可，团队统一
C99+ 通用 两者并存
老嵌入式编译器 可能不支持 //（C89 模式）

工程铁律：项目内统一一种（或明确规则），用 clang-format/checkpatch 强制。详见 1.1.1 和 2.3。

常见误区

误区 纠正
注释会拖慢程序 预处理就删了，零运行时影响
/* */ 可以嵌套 不能，第一个 */ 就结束外层
用 /* */ 屏蔽大段代码很方便 内含 */ 就出错；用 #if 0

// 是 C 一直就有的 C99 才标准化，老编译器可能不支持

2.2

.3 自由形式的源代码

本节讲什么

C 是自由格式（free-form）语言：空白符（空格、制表、换行）仅用于分隔 Token，排版不影响语义。本节讲清楚空白在词法层的角色、什么时候不能省略空白、以及工程上为什么"自由不等于随意"。

空白的词法角色

规则

  • 空格、制表符、换行在词法分析中基本等同——都是 token 分隔符
  • 多个连续空白 ≡ 一个空白
  • 排版不影响语义——你可以把整个程序写在一行（理论上）
int    a    ;      /* 等价 */
int a;             /* 等价 */

空白的作用：分隔 Token

空白帮助词法分析器"断开"token：

int x;       /* 三个 token：int、x、; */
intx;        /* 一个 token：intx（非法标识符） */
  • 没有空白，intx 被当成一个标识符——不是 int + x
  • 空白在关键字与标识符之间、标识符与标识符之间不可省略

空白在操作符之间可省略

a+b    /* 等价 */
a + b  /* 等价 */
a +b   /* 等价，但可读性差 */

操作符本身就是独立 token，不需要空白分隔（贪心法会正确切分）。但加空白提升可读性。

什么时候空白不可省略

场景 不加空白的后果
int x; → intx; 变成一个非法标识符
return 0; → return0; 变成标识符 return0
a / *p → a/*p /* 被当成注释开始！（2.2.2）
#define F (x) → #define F(x) 宏参数 vs 整体括号（ch14）
a + ++b → a+++b 贪心法切成 (a++)+b 而非 a+(++b)（2.2）

关键：空白不只是"好看"，它控制 token 切分。a/*p 和 a / *p 是完全不同的程序。

预处理行的特殊规则

预处理指令（# 开头的行）有续行规则：

#define LONG_MACRO(a, b) \
    do { \
        (a) += (b); \
    } while (0)
  • 预处理行末尾的 \ + 换行 = 续行，下一行接上
  • 续行符后不能有任何字符（包括注释和空格）——\ 必须紧跟换行
  • 宏定义跨行必须用 \，否则宏在第一行换行处就结束了

字符串字面量跨行

/* C 自动拼接相邻字符串字面量 */
char *s = "hello "
          "world";    /* 等价 "hello world" */
  • 字符串字面量不能直接包含换行——"hello\n world" 的 \n 是转义，不是物理换行
  • 跨行字符串用相邻拼接，不用 \ 续行

自由格式的边界

自由格式有几个不自由的例外：

  1. 预处理指令：# 必须在逻辑行首（可以有前置空白），# 后跟指令名
  2. 字符串字面量内部：空白和换行是字符串内容的一部分（物理换行需用 \ 续行或相邻拼接）
  3. 字符常量内部：' ' 是空格字符，不是分隔符
  4. 续行符 \：必须紧跟换行，中间不能有空格
  5. 三字符组（trigraphs）：??= 表示 # 等（C99 有，实际几乎不用，C17 移除）

工程规范：自由不等于随意

"自由格式"意味着编译器不关心排版，但人类和团队关心：

格式规范

项 惯例

为什么混用 tab/space 是灾难

  • tab 宽度在不同编辑器/终端不同（4/8/2）
  • 混用 → 同级缩进对不齐 → diff 全文飘红 → merge conflict
  • 解决：.editorconfig + clang-format 强制，CI 检查

常见误区

误区 纠正
空白只是"好看" 空白控制 token 切分：a/*p 和 a / *p 是不同程序
可以省略所有空白 intx 是一个标识符，不是 int x

.4 标识符

本节讲什么

标识符（identifier）的命名规则、关键字（keyword）、保留标识符、以及内核/DPDK/HFT 的工程命名惯例。本节是词法层"什么能当名字"的规则——理解它，能避免"用了保留名导致诡异 bug"和"命名冲突导致链接失败"。

命名规则

合法标识符

  • 首字符：字母（a-z/A-Z）或下划线 _
  • 后续字符：字母、数字、下划线
  • 区分大小写：count、Count、COUNT 是三个不同的标识符
  • 不能是关键字：int、static、struct 等
int count;       /* 合法 */
int _count;      /* 合法 */
int count2;      /* 合法 */
int 2count;      /* 非法：数字不能开头 */
int count-2;     /* 非法：- 不是字母/数字/下划线 */
int class;       /* C 合法（class 是 C++ 关键字，不是 C 关键字） */
int int;         /* 非法：int 是关键字 */

长度限制

  • C89：保证前 31 个字符有效（外部链接前 6 个）
  • C99：保证前 63 个字符有效（外部链接前 31 个）
  • 现代编译器（gcc/clang）：无实际长度限制，全部有效
  • 但太长的标识符影响可读性——工程上控制在合理范围

保留标识符（不能用的名字）

这是最容易踩的坑——有些名字虽然不是关键字，但标准保留给实现，用了是 UB。权威出处：C11 7.1.3 Reserved identifiers，三条规则：

规则 1：__xxx 和 _Xxx —— 任何作用域都保留

  • __foo（双下划线开头）、_Foo（单下划线+大写）
  • 在任何作用域都保留——包括函数内部的局部变量，写了就是 UB，不是"风格问题"
  • 典型例子：__UINT32_TYPE__（编译器内置宏）、_Bool/_Alignof（C99/C11 关键字）、glibc 内部的 _IO_write_ptr
  • ⚠️ _GNU_SOURCE 不是反例：它是 glibc 留给用户定义的 feature-test macro，#define _GNU_SOURCE 再 include 头文件是标准用法（用它开启 strdup、pthread 等扩展）。它是"下划线+大写"规则下少见的合法用户宏——glibc 特意保留给用户的约定

规则 2：_xxx（单下划线+小写）—— 仅文件作用域保留

  • 只在文件顶层（全局变量/函数）保留，会和实现冲突
  • 函数内部局部变量 int _tmp; 是合法的——标准允许
  • 但工程上仍建议统一字母开头——"哪些位置能用"这种规则本身就是要背的负担，一刀切最省心

规则 3：库标识符 —— 外部链接名永远保留

  • 所有具有外部链接的标准库名（printf、malloc、strncpy...）保留
  • 比"include 头文件后不能重定义"更狠：即使不 include 任何头文件，自己定义一个全局函数叫 malloc 也是 UB——这些名字在语言层面就保留，和有没有 include 无关
  • 后果：链接诡异崩掉、和 glibc 的版本化符号（malloc 带特殊版本标记）冲突——HFT 程序出"谜之 bug"的高发来源

POSIX 的额外保留（Linux 工程必须知道）

ISO C 之外，POSIX 在其基础上又追加保留了一批：

保留模式 例子 说明
类型后缀 *_t pid_t、size_t 严格来说 tick_data_t 踩在 POSIX 保留线上——glibc 从不追究、全行业都在用，但要知道这条线存在
str* / mem* / wcs* 函数名前缀 自定义 str_fast_parse 有风险 POSIX 未来可能新增 str_ 开头的标准函数
E* + 数字、SIG*、SA_*、_POSIX_* EINVAL、SIGUSR1 errno/signal 命名空间

工程铁律：自己写的标识符一律字母开头（a-z/A-Z）——下划线开头的名字全部留给编译器和标准库。*_t 后缀可继续用（行业惯例），但不要定义 str_*/mem_* 开头的全局函数。

double    else     enum      extern   float    for       goto      if
int       long     register  return   short    signed    sizeof    static
struct    switch   typedef   union    unsigned void      volatile  while

C99 增加

_Bool  _Complex  _Imaginary  inline  restrict

注意 C99/C11 新增的关键字大多是 _ 开头 + 大写——这就是为什么 _ 开头的标识符要小心。

class 在 C 中合法

C++ 的 class、new、delete、template 等不是 C 关键字——在纯 C 中可以当标识符。但为了 C/C++ 混合代码的可移植性，工程上避免使用。

工程命名惯例（内核/DPDK）

对象 惯例 例子
函数 snake_case，动词开头，模块前缀 rte_mbuf_refcnt_update、read_column_numbers
变量 snake_case packet_count、order_id
全局变量 g_ 前缀或模块前缀 g_config、rte_config
宏 / 枚举 全大写 + 下划线 RTE_PKTMBUF_HEADROOM、MAX_ORDERS
类型 snake_case + _t 后缀 struct rte_mbuf、uint32_t
私有函数 static + snake_case static int parse_hdr(...)

命名的好习惯

  • 函数名动词开头：read_ init_ parse_ send_ alloc_
  • 布尔返回加 is_/has_/can_：is_valid()、has_data()
  • 避免缩写到歧义：cnt 是 count 还是 center？写全 count
  • 避免单字母（除循环计数 i/j/k）：o 和 0、l 和 1 容易混
  • 作用域越大名字越长：局部变量可以 i，全局变量要 g_packet_count

标识符与链接

标识符的链接属性（linkage）决定它在多个翻译单元中是否指同一个实体——这是 ch03.6 的核心，这里先建立直觉：

链接属性 含义 例子
外部链接 全程序唯一，其他 .o 可见 全局函数、非 static 全局变量
内部链接 仅本翻译单元可见 static 函数/全局变量
无链接 仅当前作用域 局部变量、函数参数

同名标识符在不同翻译单元：外部链接会冲突（multiple definition）；内部链接互不影响。static 是"隐藏"私有符号的关键。

常见误区

误区 纠正
_Foo 可以随便用 单下划线+大写是保留标识符，任何作用域（含局部）都是 UB
__foo 可以随便用 双下划线开头保留给实现，任何作用域都是 UB
不 include 头文件就能重定义 malloc 外部链接的标准库名在语言层面保留，与是否 include 无关
_foo（单下划线+小写）到处不能写 仅文件作用域保留；函数内部局部 int _tmp; 合法（但工程上统一字母开头更省心）
关键字当变量名 int if = 5 语法错误，if 是关键字
class 在 C 不能用 C 能用（不是 C 关键字），但混合 C++ 会出错
标识符大小写不敏感 C 区分大小写，Count ≠ count
命名不影响性能 不影响运行性能，但严重影响可维护性和review 效率

代码自测

题目 1： 以下哪些是合法的 C 标识符？

int 2val;    // A
int _count;  // B
int $amount; // C
int typedef; // D
参考答案

只有 B 合法。标识符必须以字母或下划线开头，后续可以是字母、数字、下划线。A 以数字开头非法；C 中的 $ 不是标准 C 标识符字符（某些编译器扩展允许）；D 中的 typedef 是关键字。

题目 2： 写 HFT demo 时，以下命名哪些是错误的（按 C11 7.1.3 / POSIX）？

int __tick_buf;          // A（全局变量）
void parse(void) {
    int _tmp = 0;        // B（函数内局部变量）
}
void _ParseTick(void) {} // C（全局函数）
int tick_queue_len;      // D（全局变量）
参考答案

A、C 错误；B 合法但不推荐；D 正确。

  • A：双下划线开头，任何作用域都保留给实现 → UB
  • C：单下划线+大写，任何作用域都保留 → UB
  • B：单下划线+小写只在文件作用域保留，函数内部局部变量合法——但工程上统一字母开头，免得记规则
  • D：字母开头，完全安全

记忆法：自己写的名字永远用字母 a-z/A-Z 开头，下划线开头全部留给编译器和标准库。

.5 程序的形式

本节讲什么

声明 vs 定义、语句分类、作用域、存储类——本章的核心，也是多文件 DPDK/内核工程和内存生命周期的理论基础。90% 的链接报错、符号冲突、变量生命周期 bug，根源都在本节没搞清楚。

声明 vs 定义（链接的核心）

声明 定义
作用 告知类型/签名，不分配 分配存储或生成代码
可出现次数 多次（只要一致） 整个程序一次（外部链接）
变量 extern int g_val; int g_val = 10;
函数 void func(int x);（原型） void func(int x) { ... }（带函数体）
结构体 struct rte_mbuf;（不完整类型） struct rte_mbuf { ... };（完整定义）

工程铁律：头文件放声明，.c 放定义

/* config.h —— 放声明 */
#ifndef CONFIG_H
#define CONFIG_H
extern int g_port;              /* 声明 */
void init_server(int port);     /* 声明：函数原型 */
struct rte_mbuf;                /* 声明：不完整类型 */
#endif

/* config.c —— 放定义 */
#include "config.h"
int g_port = 8000;              /* 定义：分配存储 */
void init_server(int port) {    /* 定义：生成代码 */
    g_port = port;
}

/* main.c —— 用声明 */
#include "config.h"
int main(void) {
    init_server(g_port);        /* 链接时找到 config.c 的定义 */
    return 0;
}

为什么头放声明：头被多个 .c include，放定义会多处定义→multiple definition。详见 2.1.1。

语句分类

C 的语句分四类：

类型 形式 例子
表达式语句 表达式 + ; a = 10;、printf("hi");、i++;
复合语句（块） { 语句列表 } if/for 的函数体
空语句 ; 循环体什么都不做
控制语句 if/for/while/do/switch/goto 改变执行流（ch04）

分号陷阱（《C 陷阱与缺陷》经典）

if (a > b);          /* ← 多了分号！这是空语句 */
{
    /* 这块永远执行，不受 if 控制 */
    printf("always\n");
}
  • if (a > b); 的 ; 是空语句——if 控制的是这个空语句
  • 后面的 { ... } 成了独立块，无条件执行
  • -Wall -Wparentheses 会警告空 body

空语句的合法用途

while (*dst++ = *src++);   /* 复制字符串，循环体是空语句 */
  • 这种"所有工作在条件里做完"的写法是合法的空语句用法
  • 但可读性差，现代代码倾向用显式循环体

作用域（Scope）

作用域决定标识符在哪段代码可见：

作用域类型 范围 例子
文件作用域 函数外声明，从声明点到文件末 全局变量、函数
块作用域 {} 内，从声明点到块末 局部变量、for 的 i
函数原型作用域 函数原型参数名，仅声明处 void f(int x); 的 x
函数作用域 整个函数，只有 label goto 的目标标签

嵌套与遮蔽

int a = 10;                /* 文件作用域 */
void test(void) {
    int a = 20;            /* 块作用域，遮蔽外层 */
    printf("%d\n", a);     /* 20 */
    {
        int a = 30;        /* 更内层，遮蔽中间层 */
        printf("%d\n", a); /* 30 */
    }
    printf("%d\n", a);     /* 20 */
}
  • 内层可访问外层
  • 内层同名遮蔽外层——内核/工程规范常禁止局部与全局同名，避免误用
  • C 没有作用域解析符（C++ 有 ::）——一旦遮蔽，无法访问外层同名

for 循环变量作用域（C99）

for (int i = 0; i < n; i++) { ... }
/* i 在这里不可见（C99+） */
  • C99 起 for 的 i 作用域限于循环体内
  • C89 的 i 必须在循环外声明——作用域到函数末

存储类（Storage Class）

存储类决定变量的存储位置、生命周期、链接属性：

说明符 存储位置 生命周期 链接 用途
auto（默认局部） 栈 块结束销毁 无 普通局部变量（现代几乎不写 auto）
register 建议寄存器 块结束销毁 无 优化提示；不能 & 取址；现代编译器忽略
static（局部） .data/.bss 整个进程 无 函数内"记忆"变量，只初始化一次
static（文件） .data/.bss 整个进程 内部 私有全局/函数，仅本 .c 可见
extern （声明，不分配） （引用外部定义） 外部 声明别处定义的符号

static 的双重含义（重要）

static 在局部和文件级语义不同：

/* 文件级 static —— 内部链接，仅本 .c 可见 */
static int g_private = 0;          /* 私有全局 */
static int helper(void) { ... }   /* 私有函数 */

void counter(void) {
    static int count = 0;          /* 局部 static —— 整个进程存活，只初始化一次 */
    count++;
    printf("%d\n", count);
}
static 用在哪 存储位置 生命周期 链接
局部变量 .data/.bss 整个进程（但作用域仍限块内） 无
文件级变量/函数 .data/.bss 整个进程 内部（仅本翻译单元）

两种 static 共同点：都改"默认行为"——局部改生命周期，文件级改链接可见性。

static 局部：只初始化一次

void init_pool(void) {
    static void *pool = NULL;       /* 只在第一次调用时初始化 */
    if (!pool)
        pool = alloc_hugepage();
}
  • static 局部变量的初始化在程序启动时完成（不是每次函数调用）
  • 默认初始化为 0（.bss 清零机制）
  • DPDK/内核常用于"一次性初始化"、"单例池"

extern：跨文件引用

/* a.c */ int g_cfg = 1;           /* 定义 */
/* b.c */ extern int g_cfg;        /* 声明：引用 a.c 的定义 */
  • extern 声明不分配内存——告诉编译器"这个符号在别处定义"
  • 链接时解析到真正的定义
  • 如果找不到定义 → undefined reference

陷阱：extern + 初始化器 = 定义

extern int g_cfg = 5;   /* 这不是声明，是定义！gcc 警告：
                           'g_cfg' initialized and declared 'extern' */

extern 只有不带初始化器时才是纯声明；一旦写 = 值 就退化成定义。把它放头文件 → 每个 include 的 .c 都生成一份定义 → multiple definition。头文件里的 extern 声明永远不要带初始化器。

内存生命周期对照表

声明方式 存储位置 创建 销毁 初始值
int x;（局部 auto） 栈 进入块 离开块 不定值（UB 读取）
static int x;（局部） .bss/.data 程序启动 程序结束 0
int x;（全局） .bss/.data 程序启动 程序结束 0
int x = 5;（全局） .data 程序启动 程序结束 5
extern int x; （引用） — — 引用别处
malloc(sizeof(int)) 堆 malloc 时 free 时 不定值

专属价值（内核/DPDK/HFT）

  1. 链接报错：90% 的 multiple definition/undefined reference 根源在本节——声明vs定义、extern、static
  2. 内存生命周期：static 单例池、一次性硬件 init、配置全局
  3. 符号隔离：static 私有 helper，不污染全局符号空间
  4. 隐蔽 bug：遮蔽、if 分号空语句、static 局部只初始化一次
  5. HFT 配置：全局配置变量 + extern 声明，多线程共享——注意加锁或用原子

常见误区

误区 纠正
extern 分配内存 只是声明，不分配；定义在别处
static 局部每次调用都初始化 只在程序启动时初始化一次
头文件放变量定义 被多处 include → 多重定义；改 extern 声明
static 函数能被其他文件调用 static = 内部链接，仅本翻译单元
if (a > b); 的分号无害 空语句陷阱，if 不控制后面的块
遮蔽外层变量没关系 内核规范常禁止，避免误用全局
register 还能优化 现代编译器忽略；不能 & 取址已无意义

实操

  1. 多文件 static vs 全局，故意制造 multiple definition 和 undefined reference
  2. static 局部循环调用多次，验证只初始化一次
  3. 制造局部遮蔽全局，打印内外层值
  4. if (a > b); { ... } 加分号，看块是否无条件执行
  5. readelf -S ./app 看 .text/.data/.bss，对照变量声明方式
  6. nm a.o 看符号表，区分 T（text 已定义外部）、t（text 已定义内部 static）、U（未定义）

题目 1： 以下代码有什么问题？

int main(void) {
    int x = f(3);
    return 0;

int f(int n) { return n * 2; }
参考答案

f 在调用前没有声明（C99 前的隐式声明会假设返回 int，但此处碰巧匹配；C99 起隐式声明是错误的）。更严格地说，如果 f 返回非 int 类型，隐式声明会导致 UB。正确做法是在 main 前加 int f(int n); 原型声明，或者把 f 的定义放在 main 之前。

程序风格

本节讲什么

可读、可维护、可 review 的编码习惯。语法正确 ≠ 工程合格——一段能编译通过的代码，如果没人看得懂、改不动、review 不出来问题，就是工程负债。本节把内核/DPDK/HFT 的风格规范系统化，让全书示例有统一的风格基准。

为什么程序风格是"真问题"

  • 代码读的次数远多于写的次数——review、维护、debug、扩展，全在读
  • Bug 的平均发现时间 >> 写代码时间——可读性差 → bug 潜伏久 → 爆发时代价大
  • 多人协作——风格不统一 → merge conflict、review 低效、指责游戏
  • HFT 特殊性——热路径代码微秒级延迟，常需"看代码就猜到性能特征"，可读性是优化的前提

Dijkstra："除了展示程序员自己的不足之外，计算机上的笨拙代码还能有什么用？"

命名（详见 2.2.4）

通用原则

  • 见名知意：packet_count 优于 n、cnt、pc
  • 动词开头：read_data、init_server、parse_header
  • 布尔加前缀：is_valid()、has_data()、can_send()
  • 避免缩写到歧义：cnt（count? center?）、idx（index 还好，但 i 够了）
  • 避免单字母（除循环 i/j/k）：o/0、l/1 混淆
  • 作用域越大名字越长：局部可 i，全局要 g_packet_count

格式

缩进

  • 4 空格（内核/DPDK 现代项目主流）或 tab（部分老项目）
  • 禁止 tab/space 混用——diff 飘红、merge conflict 的头号元凶
  • 用 .editorconfig + clang-format 强制

大括号

风格 形式 用谁
K&R（1TBS） { 同行，} 单独行 内核、DPDK、多数 C 项目
Allman { 单独行 部分系统级项目、C# 
/* K&R */
if (x > 0) {
    do_something();
}

/* Allman */
if (x > 0)
{
    do_something();
}

项目内统一一种，别争论哪种"更好"——一致性 > 个人偏好。

其他格式

  • 一行一事：不要 a=1; b=2; c=3;
  • 行宽：内核 80 列，DPDK 100 列，现代项目 120 列
  • 过长安达式换行：运算符放行首或行尾，项目统一
  • 指针 * 贴变量名：int *p 而非 int* p（C 风格，K&R）

注释（详见 1.1.1 / 2.2.2）

好注释写 why

/* 必须按 little-endian 解析：交易所行情字段规定 LE */
uint32_t price = le32toh(*p);

/* 不能用 spinlock：收包在中断上下文，不能睡眠 */
/* 用 trylock + 重试替代 */

烂注释复述代码

i++;              /* increment i */           ← 毫无价值
int x = 5;       /* x 等于 5 */              ← 更糟
好注释 烂注释
函数意图、不变量、边界条件 复述每一行代码
为什么用这个算法/魔数 "这里加一"
参数、返回值、错误码语义 过时的设计文档
已知缺陷、TODO、性能假设 冗余的类型说明

口诀：注释回答 why，代码回答 how。能用函数名/变量名表达的，别靠注释。

注释风格

  • 内核倾向 /* */
  • 公共 API 必须文档化：参数、返回值、错误码、线程安全性
  • TODO 格式统一：/* TODO(name): description */

防御性习惯

禁止空 body 误用

if (a > b);        /* ← 分号陷阱！空语句，if 不控制后面 */
{
    /* 永远执行 */
}

/* 正确：大括号紧跟，即使单语句也加大括号 */
if (a > b) {
    do_something();
}
  • 即使单语句也加大括号——防止后续添加语句时忘记加
  • -Wall -Wparentheses 会警告空 body

避免遮蔽

int count = 10;
void f(void) {
    int count = 20;   /* 遮蔽全局——内核规范禁止 */
}

多文件工程

  • 头文件声明，单点定义（2.2.5）
  • 头文件加 include guard 或 #pragma once
  • 私有函数加 static——不污染全局符号

栈上大数组

void f(void) {
    char buf[1024 * 1024];   /* 1MB 栈数组 → 栈溢出 */
}
  • 大缓冲改 static 或 malloc
  • 栈默认 8MB，DPDK worker 栈可能更小

初始化

  • 局部变量用前必须初始化——栈 auto 不清零
  • 报文解析缓冲用 memset 或 = {0} 清零
  • malloc 返回的内存不清零——要清零用 calloc

函数设计

  • 单一职责：一个函数做一件事
  • 短：内核规范单函数不超过一屏（约 50 行）
  • 入口校验：函数开头检查参数合法性（NULL？越界？）
  • 错误传播：失败返回错误码，让调用者决定怎么办
  • main 协调：main 调用子函数，子函数不反向调用 main

常见误区

误区 纠正
"能编译通过就行" 工程合格 ≠ 编译通过；可读、可维护、无警告才是合格
"风格是个人偏好" 个人偏好在团队里必须让位给一致性
"注释越多越好" 烂注释是噪声，比没注释还糟
"单语句不用大括号" 容易后续加语句时忘加→bug；一律加大括号
"tab 和 space 混用无所谓" 是 merge conflict 和 diff 飘红头号元凶
"性能优先于可读性" 先写对再写快；不可读的"优化"常是伪优化

代码自测

题目 1： 以下两种写法哪个更安全？为什么？

// A
if (x = 0) { ... }
// B
if (0 == x) { ... }
参考答案

B 更安全。if (0 == x) 如果误写成 if (0 = x) 编译器会报错（不能给常量赋值）。if (x = 0) 是赋值而非比较，条件永远为假，且修改了 x 的值——这是一个常见的 bug。Yoda 风格（常量在左）能被编译器捕获这种错误。

章节自测

题目 1： 以下代码在 C 语言中能编译吗？说明了 C 的什么特性？

#include <stdio.h>
int main() {
    printf("hello\n");
}
参考答案

能编译。C 是编译型语言——源代码经过预处理、编译、汇编、链接四个阶段生成可执行文件。这个程序体现了 C 的基本结构：包含头文件、main 函数入口、标准库函数调用。C 的设计哲学是"信任程序员"——它不会像 Java 那样强制检查很多东西。
