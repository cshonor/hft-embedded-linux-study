18.1

判断运行时环境

本节讲什么

Linux 进程的虚拟地址空间六大段：.text/.rodata/.data/.bss/堆/栈，以及它们在 ELF 加载后的真实布局。这是全书收尾——把 ch02 的变量存储类、ch11 的堆分配、ch07 的栈帧映射到运行时的真实内存布局。理解这一节，前面所有"变量在哪里"的疑问都有了具体答案。

要点

虚拟地址空间六大段

高地址 ┌────────────────────┐
       │ Stack (↓ 向下增长)   │  局部变量、栈帧、信号栈
       │                      │  默认 8MB (ulimit -s)
       │ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │
       │                      │
       │ mmap 区 (↓ 向下)     │  mmap/malloc 大块、共享库、DPDK hugepage
       │                      │
       │ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │
       │                      │
       │ Heap (↑ 向上增长)     │  malloc/brk，小块分配
       │                      │
       ├────────────────────┤
       │ .bss                │  未初始化全局/static (加载时清零)
       ├────────────────────┤
       │ .data               │  已初始化全局/static
       ├────────────────────┤
       │ .rodata             │  字符串字面量、const 全局 (只读)
       ├────────────────────┤
       │ .text               │  机器码 (读+执行)
低地址 └────────────────────┘

各段详解

段 内容 权限 加载来源
.text 函数编译后的机器码 读+执行 ELF 文件 .text 节
.rodata 字符串字面量、const 全局、跳转表 只读 ELF 文件 .rodata 节
.data 已初始化的全局/static 变量 读写 ELF 文件 .data 节
.bss 未初始化或初始化为 0 的全局/static 读写 加载时内核清零，不占 ELF 文件
Heap malloc/brk/mmap 分配 读写 运行时动态
Stack 局部变量、栈帧、返回地址 读写 运行时动态，向下增长

.bss 不占文件空间

int big[1000000];   /* 未初始化, 在 .bss, 占 4MB 内存但不占 ELF 文件 */

.bss 段在 ELF 文件里只记录大小和起始地址，实际内存在加载时由内核分配并清零。这就是为什么"未初始化全局数组"不会让可执行文件变大。

虚拟地址 vs 物理地址

进程看到的是虚拟地址，通过页表映射到物理地址：

  • 虚拟地址 0x400000 可能映射到物理地址 0x1F300000
  • 不同进程的同一虚拟地址映射到不同物理页
  • 访问未映射的虚拟地址 → 缺页 → 内核处理（分配物理页或 SIGSEGV）

缺页（page fault）是惰性分配的基础——malloc 只预留虚拟地址，真正访问时才分配物理页。

mmap 区：大块与共享

void *p = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
               MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);

mmap 在堆和栈之间分配独立映射区：

  • 大块 malloc（通常 > 128KB）用 mmap 而非 brk
  • 共享库 .so 加载到 mmap 区
  • DPDK hugepage 用 mmap(MAP_HUGETLB) 映射 2MB/1GB 大页
  • MAP_SHARED 让多进程共享同一物理页（DPDK 多进程模式）

堆与栈的增长方向

  • 堆向上增长（brk/sbrk 提升堆顶）
  • 栈向下增长（rsp 递减）
  • 中间是 free 空间，两者相向增长

栈默认 8MB（ulimit -s），堆可达 GB 级。栈溢出（深递归、大局部数组）→ SIGSEGV。

readelf 观察段布局

readelf -S ./a.out   # 列出所有 section
readelf -l ./a.out   # 列出 program headers (加载段)
objdump -h ./a.out   # 类似 readelf -S

输出示例：

Section Headers:
  [ 1] .text   PROGBITS  0000000000401000  001000  0001a0  00  AX  0   0 16
  [ 2] .rodata PROGBITS  0000000000402000  002000  000020  00   A  0   0  4
  [ 3] .data   PROGBITS  0000000000403000  003000  000010  00  WA  0   0  8
  [ 4] .bss    NOBITS    0000000000403010  003010  000008  00  WA  0   0  4
  • AX = Alloc + eXecute（.text）
  • A = Alloc（.rodata 只读）
  • WA = Write + Alloc（.data/.bss 可写）
  • NOBITS = 不占文件（.bss）

/proc/self/maps 观察运行时布局

cat /proc/self/maps

输出进程当前的内存映射，每行一个映射区：

00400000-00401000 r-xp 00000000 ...  /path/to/a.out   (.text)
00600000-00601000 r--p 00000000 ...  /path/to/a.out   (.rodata)
00601000-00602000 rw-p 00001000 ...  /path/to/a.out   (.data/.bss)
7f...           r-xp 00000000 ...  /lib/libc.so.6    (共享库)
7ffff7...
7ffff7fff000-rwxp 00000000 ...  [stack]              (栈)

这是调试内存问题、验证布局的利器。

DPDK 的内存布局特殊性

DPDK 用 hugepage + MAP_SHARED：

  • hugepage：2MB 或 1GB 大页，减少 TLB miss
  • MAP_SHARED：多进程共享同一物理大页（primary/secondary 模式）
  • 内存预分配：启动时一次性映射所有大页，运行时不再 mmap
  • 物理连续：DMA 要求物理连续，hugepage 提供大块连续物理内存

DPDK 进程的 /proc/<pid>/maps 会看到大量 hugepage 映射，这是与普通进程的最大区别。

HFT 关联

  • 地址空间布局理解：调试段错误、内存泄漏的基础
  • .bss 不占文件：大型静态查表（如合约表）放 .bss 不增可执行文件体积
  • .rodata 只读保护：字符串字面量、配置常量写修改触发 SIGSEGV，帮助捕获 bug
  • hugepage 减 TLB miss：DPDK 强制 hugepage，TLB miss 从微秒降到纳秒
  • MAP_SHARED 多进程：DPDK primary/secondary 共享订单簿、行情缓冲
  • mmap 区零拷贝：mmap 行情文件做内存映射，避免 fread 拷贝
  • 栈大小限制：数据面禁深递归、禁大局部数组，避免栈溢出 SIGSEGV
  • /proc/<pid>/maps 调试：OOM、内存泄漏、共享库加载问题的第一现场

代码自测

题目 1： 以下代码探测什么运行时特性？

int x = 1;
char *p = (char *)&x;
if (*p == 1) printf("little-endian\n");
else printf("big-endian\n");
参考答案

探测字节序（endianness）。int x = 1 在小端机器上内存布局是 01 00 00 00，p 指向第一个字节 01。大端机器上是 00 00 00 01，p 指向 00。通过检查首字节可以判断大小端。这在处理二进制数据（网络协议、文件格式）时很重要——网络字节序是大端。

18.1

.1 测试程序

本节讲什么

用打印地址 + readelf 实际观察进程各段的地址分布，以及 crt0 → main 的启动流程。这是把抽象的"段布局"变成可触摸的具体地址的实操——亲眼看到 main 在 .text、字符串字面量在 .rodata、malloc 在堆、局部变量在栈。

要点

测试程序

#include <stdio.h>
#include <stdlib.h>

int g_init = 42;        /* .data, 已初始化全局 */
int g_zero;             /* .bss, 未初始化全局, 加载时清零 */
static int s_init = 1;  /* .data, static 仍在 .data, 但不导出符号 */
static int s_zero;      /* .bss, static 仍在 .bss */

int main(void)
{
    int local = 0;                  /* 栈 */
    void *heap = malloc(16);        /* 堆 */

    printf("text   main   %p\n", (void *)main);
    printf("rodata \"str\"  %p\n", (void *)"quote");
    printf("data   g_init %p\n", (void *)&g_init);
    printf("data   s_init %p\n", (void *)&s_init);
    printf("bss    g_zero %p\n", (void *)&g_zero);
    printf("bss    s_zero %p\n", (void *)&s_zero);
    printf("stack  local  %p\n", (void *)&local);
    printf("heap   malloc %p\n", heap);

    free(heap);
    return 0;
}

典型输出（x86-64 Linux, PIE 关闭）

text   main   0x401000
rodata "str"  0x402004
data   g_init 0x404010
data   s_init 0x404014
bss    g_zero 0x404020
bss    s_zero 0x404024
stack  local  0x7fffffffe24c
heap   malloc 0x602010

观察规律：

  • .text（main）和 .rodata（字符串）地址最低，相近
  • .data 和 .bss 紧随其后，s_init/s_zero 与全局变量同段（static 只影响链接不影响存储）
  • 堆地址在 .bss 之上（brk 从 .bss 末尾向上扩展）
  • 栈地址最高（0x7fff...），接近用户态顶

PIE（Position Independent Executable）

现代 Linux 默认开启 PIE，每次运行地址不同（ASLR 地址空间随机化）：

$ ./a.out
text   main   0x555555555500
$ ./a.out
text   main   0x5555555550a0   ← 地址变了

PIE 是安全特性（防 ROP 攻击），但调试时地址变化不便。gcc -no-pie 关闭 PIE 固定地址。

readelf 观察段

$ readelf -S ./a.out
Section Headers:
  [ 1] .text   PROGBITS  0000000000401000  001000  0001a0  00  AX  0   0 16
  [ 2] .rodata PROGBITS  0000000000402000  002000  000020  00   A  0   0  4
  [ 3] .data   PROGBITS  0000000000403000  003000  000010  00  WA  0   0  8
  [ 4] .bss    NOBITS    0000000000403010  003010  000008  00  WA  0   0  4

字段含义：

  • Addr：段在虚拟地址空间的起始地址
  • Offset：段在 ELF 文件中的偏移
  • Size：段大小
  • Flags：AX(执行) A(只读) WA(可写) NOBITS(不占文件)

启动流程：crt0 → main

程序不是直接进 main。ELF 入口点 _start（由 crt0.o 提供）做一系列初始化：

1. 内核 execve(2) 加载 ELF
   → 分配虚拟地址空间
   → 映射 .text/.rodata/.data
   → .bss 清零
   → 设置 argc/argv/environ 在栈上
   → 跳到 ELF 入口点 _start

2. _start (crt0.o)
   → 设置栈帧
   → 调用 __libc_start_main
     → 初始化线程局部存储 (TLS)
     → 初始化 stdio (stdin/stdout/stderr)
     → 注册 atexit 回调
     → 解析环境变量
     → 加载动态库 (ld.so)
   → 调用 main(argc, argv, environ)

3. main 返回
   → __libc_start_main 调用 exit
     → 跑 atexit 回调 (逆序)
     → flush stdio
     → 删 tmpfile
     → _exit(返回码) 交给内核

启动链的工程意义

  • 静态变量在 main 前已初始化：.data 从 ELF 文件加载，.bss 由内核清零，main 开始时全局变量已就绪
  • stdio 在 main 前可用：printf 不需手动初始化
  • 动态库在 main 前加载：dlopen 之前，LD_PRELOAD 的库已就位
  • atexit 在 main 后执行：main return 触发完整退出链

退出路径

退出方式 atexit flush stdio tmpfile 删除 core dump
return from main ✓ ✓ ✓ ✗
exit(0) ✓ ✓ ✓ ✗
_exit(0) ✗ ✗ ✗ ✗
abort() ✗ 部分 ✗ ✓
SIGSEGV/SIGABRT ✗ ✗ ✗ ✓

异常退出（abort/信号）跳过 atexit 和 stdio flush，日志可能丢失。崩溃前 fflush(stderr) 保证错误信息输出。

ASLR 与地址随机化

$ cat /proc/sys/kernel/randomize_va_space
2   ← 0 关闭, 1 部分, 2 完全
  • 栈地址随机
  • 堆地址随机
  • mmap 区（共享库）随机
  • .text 地址随机（仅 PIE 编译时）

ASLR 防 ROP 攻击，但调试时地址变化不便。setarch -R 或 echo 0 > /proc/sys/kernel/randomize_va_space 关闭。

HFT 关联

  • 调试段错误：/proc/<pid>/maps + readelf 定位崩溃地址所在段
  • ASLR 与延迟：ASLR 增加首次访问缺页，HFT 启动后 warm-up 预热所有页
  • 静态链接：HFT 数据面用 -static 避免 ld.so 动态解析，启动快且确定
  • crt0 开销：动态链接程序启动需解析 .so，HFT 用静态链接减少启动时间
  • atexit 资源清理：HFT 注册 atexit 回调 dump 订单簿快照、关闭连接
  • 崩溃前 fflush：信号 handler 里 fflush(stderr) 保证栈帧输出不丢
  • hugepage 预留：启动前 sysctl vm.nr_hugepages 预留，避免运行时缺页

代码自测

题目 1： 以下代码探测栈的增长方向，原理是什么？

void sub(int *prev) {
    int curr;
    if (prev) {
        if (&curr > prev) printf("stack grows up\n");
        else printf("stack grows down\n");
    }
    sub(&curr);
}
参考答案

比较两次函数调用的局部变量地址。如果后调用的 curr 地址大于先调用的 prev 地址，栈向上增长；反之向下增长。大多数系统栈向下增长（地址递减）。注意：比较不同栈帧的局部变量地址在技术上是实现定义行为，但实际可行。

18.1

.2 静态变量

本节讲什么

static 关键字的双重含义（内部链接 + 持久存储）、extern 声明、跨文件初始化顺序陷阱、动态库符号可见性。这是 C 语言链接属性的核心——理解 static 才能写出模块化、无冲突的大型工程代码。

要点

static 的双重含义

static 在不同位置含义不同：

位置 作用
函数外 static int x; 内部链接（仅本 .c 可见）+ 持久存储（.data/.bss）
函数内 static int x; 持久存储（.data/.bss）+ 函数内作用域
函数前 static void f() 内部链接（仅本 .c 可调用）

注意：函数内 static 变量持久（跨调用保持值），但作用域仍局部（函数外不可见）。

int counter() {
    static int count = 0;   /* .bss, 持久, 仅 counter 内可见 */
    return ++count;
}

链接属性三分类

关键字 链接 例子
static（函数外） 内部链接 static int x; 仅本 .c
无 static（函数外） 外部链接 int x; 全局可见
extern 声明引用 extern int x; 定义在他处
函数内声明 无链接 int local; 栈上

extern 声明 vs 定义

/* a.c */
int g_counter = 0;   /* 定义, 分配存储 */

/* b.c */
extern int g_counter;   /* 声明, 不分配, 引用 a.c 的定义 */
void use() { g_counter++; }
  • 定义（definition）：分配存储，只能有一处
  • 声明（declaration）：声明类型和名字，可多处
  • extern 声明告诉编译器"这个符号在别处定义，链接时找"

链接时若找不到定义 → undefined reference 错误。

ODR（One Definition Rule）

C 标准：每个外部链接符号在程序中只能有一处定义。违反：

/* a.c */ int x;
/* b.c */ int x;   /* 重复定义 */

链接报 multiple definition of 'x'。C 比 C++ 宽松（C 允许"临时定义" tentative definition），但工程上仍应避免。

头文件放声明，.c 放定义

/* counter.h */
#pragma once
extern int g_counter;          /* 声明 */
void inc_counter(void);        /* 函数声明 */

/* counter.c */
#include "counter.h"
int g_counter = 0;             /* 定义 */
static int internal_state;     /* 内部链接, 不暴露 */
void inc_counter(void) { g_counter++; internal_state++; }

头文件放 extern 声明和函数原型，.c 放定义。static 变量和辅助函数只在 .c 内，不进头文件。

跨文件初始化顺序陷阱

/* a.c */
int buf_size = 1024;

/* b.c */
extern int buf_size;
int *buf = malloc(buf_size * sizeof(int));   /* 全局初始化调用 malloc */

C 标准不规定不同 .c 文件全局变量的初始化顺序。b.c 的 buf 初始化时 buf_size 可能还是 0（.bss 清零后未加载 .data）。

实际 glibc 行为：按链接顺序初始化，但仍不可依赖。根治方法：

  • 复杂初始化放 main 开头显式调用
  • 用"构造函数"属性 __attribute__((constructor))（GCC 扩展）指定优先级
  • 惰性初始化（首次访问时检查）
/* 惰性初始化 */
static int *buf = NULL;
static size_t buf_size = 0;

int *get_buf(size_t size) {
    if (!buf) {
        buf = malloc(size * sizeof(int));
        buf_size = size;
    }
    return buf;
}

attribute((constructor)) / destructor

void init_module(void) __attribute__((constructor(101)));
void cleanup_module(void) __attribute__((destructor(101)));

void init_module(void) {
    /* main 前执行, 优先级 101 (小先执行) */
}
void cleanup_module(void) {
    /* exit 后执行 */
}

GCC 扩展，在 main 前后执行。优先级数字小的先执行。用于库的自动初始化/清理，类似 C++ 全局对象构造/析构。

动态库符号可见性

/* 默认所有全局符号导出到 .so 动态符号表 */
int api_func(void);   /* 外部可见 */

/* 隐藏符号, 不导出 */
__attribute__((visibility("hidden"))) int internal_func(void);

/* 显式导出 (配合 -fvisibility=hidden) */
__attribute__((visibility("default"))) int api_func(void);

编译 .so 时用 -fvisibility=hidden 默认隐藏所有符号，只显式导出 API：

  • 减少动态符号表大小，加快 dlopen
  • 防止内部符号被外部覆盖
  • 优化器对隐藏符号能更激进优化

DPDK/内核模块大量用此特性。Linux 内核等价物是 EXPORT_SYMBOL/EXPORT_SYMBOL_GPL。

static 与 inline 配合

/* 头文件里定义 inline 函数, 用 static 避免多重定义 */
static inline int max(int a, int b) {
    return a > b ? a : b;
}

static inline 让每个 .c 包含头文件时都有自己的副本，链接时不冲突。编译器内联优化，无函数调用开销。C99 起标准支持。

内核 EXPORT_SYMBOL 对照

Linux 内核模块的符号导出：

/* 内核模块 */
int my_api(void) { ... }
EXPORT_SYMBOL(my_api);   /* 导出, 其他模块可调用 */

static int my_internal(void) { ... }   /* 不导出, 仅本模块 */

EXPORT_SYMBOL 把符号加入内核全局符号表，类似 .so 的 visibility("default")。static 函数不导出。

HFT 关联

  • 模块封装：static 辅助函数 + extern API 是 HFT 框架模块化基础
  • 内部链接防冲突：多个 .c 的辅助函数同名用 static 避免链接冲突
  • 符号可见性优化：-fvisibility=hidden 减小 .so，加快动态链接
  • 跨文件初始化避免：复杂初始化放 main 开头，不依赖全局构造
  • constructor 属性：HFT 框架模块自动注册（如策略注册表）
  • static inline：性能关键小函数放头文件，零调用开销
  • DPDK 符号导出：rte_ 前缀 + visibility 控制，版本化符号
  • 避免全局可变状态：static 全局变量是隐式耦合，HFT 数据面倾向 per-thread 状态

static int static_val = 42;

18.1

.3 堆栈帧布局

本节讲什么

x86-64 栈帧的物理布局：call/ret 指令、rbp/rsp 寄存器、局部变量在栈上的排列、ABI 对齐要求。这是理解函数调用开销、调试栈回溯、避免栈溢出的基础。HFT 场景里这一节直接决定"能不能用递归"、"局部数组多大安全"、"为什么返回局部变量地址是 UB"。

要点

栈帧的生命周期

调用者                    被调用者
─────                    ─────────
call func     ──────→    [返回地址]    ← rsp 指向
                          [旧 rbp]      ← rbp 指向 (push rbp; mov rbp,rsp)
                          [局部变量]
                          [保存的寄存器]
                          ...
                          [参数 7+]     (若有, 调用者压栈)
                          ───
                          leave         ← mov rsp,rbp; pop rbp
                          ret           ← pop 返回地址, 跳回
            ←──────

call/ret 指令

call func 等价于 push 返回地址; jmp func：

  • 把下一条指令地址压栈（rsp -= 8, [rsp] = 返回地址）
  • 跳转到 func

ret 等价于 pop 跳转地址; jmp：

  • 从栈顶取返回地址（跳转地址 = [rsp], rsp += 8）
  • 跳回调用者

函数 prologue / epilogue

func:
    push rbp              ; 保存调用者的 rbp
    mov rbp, rsp          ; rbp 指向当前栈帧
    sub rsp, 64           ; 开 64 字节局部变量空间

    ; ... 函数体 ...

    leave                 ; mov rsp, rbp; pop rbp (恢复调用者 rbp)
    ret                   ; 返回
  • rbp：基址指针，指向当前栈帧，用于定位局部变量（rbp-8 是第一个局部变量）
  • rsp：栈顶指针，随 push/pop/sub 移动
  • leave：恢复 rsp 和 rbp 到调用者状态
  • ret：返回调用者

局部变量在栈上的排列

void func() {
    int a = 1;      /* rbp-4 */
    char b = 'x';   /* rbp-8 */
    int c = 2;      /* rbp-16 (对齐到 4 字节, b 后 padding) */
    char d[10];     /* rbp-32 */
}

栈帧布局（从高地址到低地址）：

[rbp]     旧 rbp
[rbp-4]   a (int, 4 字节)
[rbp-8]   b (char, 1 字节) + padding
[rbp-16]  c (int, 4 字节)
[rbp-32]  d (char[10])

编译器按对齐要求排列，可能有 padding。-O0 时变量按声明顺序，-O2 可能重排优化 cache。

x86-64 System V ABI 要点

项 规则
整数/指针参数 前 6 个用 rdi, rsi, rdx, rcx, r8, r9
浮点参数 前 8 个用 xmm0-xmm7
多余参数 从右向左压栈
返回值 rax（及 rdx 用于 128 位返回）
浮点返回 xmm0
被调保存寄存器 rbx, rbp, r12-r15（被调函数需保存恢复）
调用者保存 其他所有（调用前若需保留，调用者保存）
栈对齐 call 前 rsp 必须 16 字节对齐
红区 叶子函数可用 rsp-128 到 rsp-128 临时空间（不调其他函数时）

寄存器保存约定

  • 被调保存（callee-saved）：rbx/rbp/r12/r13/r14/r15——被调函数若用这些寄存器，必须在 prologue 保存、epilogue 恢复
  • 调用者保存（caller-saved）：rax/rcx/rdx/rsi/rdi/r8-r11/xmm0-xmm15——调用其他函数前若需保留，调用者自己保存

这意味着：调用一个函数后，rbx 等被调保存寄存器保证不变，但 rax 等可能被改写。

栈对齐

x86-64 ABI 要求 call 指令执行前 rsp 是 16 字节对齐。call 压入 8 字节返回地址后，进入函数时 rsp 是 16k - 8（非对齐）。push rbp 后 rsp 是 16k - 16（对齐），sub rsp, N 的 N 通常补足到 16 的倍数。

某些 SIMD 指令（movdqa）要求 16 字节对齐，栈对齐保证局部数组能用对齐指令。

红区（Red Zone）

System V ABI 规定：叶子函数（不调用其他函数）可以使用 rsp-128 到 rsp-8 这 128 字节作为临时空间，不需 sub rsp 调整。这减少 prologue 开销。

/* 叶子函数, 利用红区 */
int leaf(int x) {
    int tmp = x * 2;   /* 可能放 rsp-4, 红区内 */
    return tmp + 1;
}

信号处理会破坏红区（信号 handler 在同栈运行），所以信号安全函数不能用红区。-mno-red-zone 禁用（内核代码必须禁用）。

工程结论：HFT 禁忌

禁止 原因
深递归 栈 ~8MB 耗尽 → SIGSEGV
大局部数组 char buf[1024*1024] 栈溢出
返回局部变量地址 函数返回后栈帧失效，悬垂指针 UB
写字符串字面量 "abc"[0]='x' .rodata 只读 → SIGSEGV

返回局部变量地址的 UB

int *bad_func() {
    int local = 42;
    return &local;   /* UB! 函数返回后栈帧失效 */
}

int *p = bad_func();
*p;   /* 悬垂指针, 读到的是栈上被覆盖的垃圾 */

ret 后 rsp 回到调用者，local 所在栈空间会被后续函数调用复用。访问 p 读到的是垃圾，写可能破坏其他函数的栈帧。

正确做法：

  • 返回值（非地址）
  • 调用者提供缓冲，函数填充
  • malloc 堆分配（调用者负责 free）
  • static 局部变量（但失去线程安全）

gdb 观察栈帧

(gdb) break func
(gdb) run
(gdb) info frame       # 当前栈帧信息
(gdb) info args        # 参数
(gdb) info locals      # 局部变量
(gdb) x/10gx $rsp      # 查看栈内存
(gdb) backtrace        # 栈回溯
(gdb) frame 2          # 切换到第 2 层栈帧

backtrace 依赖 rbp 链——每层栈帧的 [rbp] 指向上层 rbp，遍历这条链得到调用栈。-fomit-frame-pointer 优化会省略 rbp 保存，backtrace 依赖 .eh_frame 信息。

函数调用开销

一次函数调用的开销：

  • call：压返回地址 + 跳转（~2-3 周期）
  • prologue：push rbp + mov rbp,rsp + sub rsp（~3-5 周期）
  • 参数传递：寄存器传参零开销，栈传参有 push 开销
  • epilogue：leave + ret（~2-3 周期）

总计 ~10-15 周期。3GHz CPU 约 3-5ns。热路径高频小函数用 static inline 消除调用开销。

tail call optimization（TCO）

/* 尾递归, 编译器可优化成循环 */
int sum(int n, int acc) {
    if (n == 0) return acc;
    return sum(n - 1, acc + n);   /* 尾调用, 无需保留当前栈帧 */
}

尾调用：递归调用是函数最后操作，当前栈帧无需保留。编译器优化成 jmp 而非 call，复用当前栈帧，无栈增长。-O2 启用 TCO。

HFT 关联

  • 禁深递归：数据面报文解析用显式栈迭代，避免栈溢出
  • 禁大局部数组：大缓冲用堆或 mempool，局部数组控制在 KB 级
  • 禁返回栈地址：返回值或调用者提供缓冲
  • inline 消除调用开销：热路径小函数 static inline
  • 栈大小调优：ulimit -s 或 pthread_attr_setstacksize 按需调整
  • gdb 栈回溯：崩溃后 backtrace 定位调用链，依赖 rbp 链或 .eh_frame
  • 红区禁用：内核代码 -mno-red-zone，信号安全函数不能用红区
  • 栈对齐：SIMD 局部数组依赖 16 字节栈对齐
  • TCO：尾递归优化成循环，无栈增长，但不要依赖（优化选项可能关）

18.1

.4 寄存器变量

本节讲什么

register 关键字的历史与现状、x86-64 ABI 的寄存器传参、现代编译器的自动寄存器分配、以及 HFT 真正有效的寄存器优化手段（inline、likely/unlikely、__builtin_expect）。这一节澄清"手写 register 有用吗"的常见误解。

要点

register 关键字的历史

C 早期（K&R 时代）编译器简陋，寄存器分配靠人工：

register int hot_var;   /* 建议编译器放进寄存器 */
  • register 是提示，编译器可忽略
  • C89 限制：不能对 register 变量取地址（&）
  • C11 放宽：可以取地址，但效果未定义（可能从寄存器退回内存）
  • C17/C23 进一步弱化，register 几乎只剩历史意义

现代编译器（gcc/clang -O2）的寄存器分配远比人工聪明——基于寄存器分配算法（graph coloring / linear scan），考虑变量的生命周期、使用频率、调用约定。手写 register 通常无效甚至妨碍优化。

x86-64 寄存器一览

寄存器 用途 保存责任
rax 返回值、乘除结果 调用者
rbx 通用 被调
rcx 第 4 参数、循环计数 调用者
rdx 第 3 参数、乘除高位 调用者
rsi 第 2 参数、字符串源 调用者
rdi 第 1 参数、字符串目 调用者
rbp 栈帧基址 被调
rsp 栈顶 被调（隐式）
r8-r15 通用，r8-r11 调用者保存，r12-r15 被调保存 混合
xmm0-xmm15 浮点/SIMD 调用者（xmm6-15 被调保存部分）
rip 指令指针 隐式
rflags 标志位 调用者

ABI 寄存器传参

x86-64 System V ABI 前 6 个整数/指针参数用寄存器传递，无需压栈：

void func(int a, int b, int c, int d, int e, int f, int g);
/*            rdi  rsi  rdx  rcx  r8   r9   栈 */
  • 前 6 个参数：rdi/rsi/rdx/rcx/r8/r9
  • 第 7 个起：从右向左压栈
  • 浮点：xmm0-xmm7
  • 返回值：rax（128 位用 rdx:rax）

寄存器传参零开销（无 push/pop），这是 x86-64 比 x86-32 的重大改进。

为什么手写 register 无效

register int hot = compute();
/* 编译器 -O2 已经自动把 hot 放进寄存器, register 提示多余 */

现代编译器基于使用频率自动分配：

  • 高频局部变量优先进寄存器
  • 取地址的变量必须在内存（不能纯寄存器）
  • 生命周期不重叠的变量可复用同一寄存器

手写 register 的坏处：

  • 可能阻止编译器更优分配（如两个 register 变量强制占两个寄存器，但实际可复用）
  • C89 不能取地址，限制代码
  • 现代编译器直接忽略，代码噪音

真正有效的寄存器优化

1. inline 消除调用开销

static inline int max(int a, int b) {
    return a > b ? a : b;
}

static inline 让编译器内联展开，参数直接进寄存器，无 call/ret/prologue/epilogue 开销。这是 HFT 最有效的优化。

2. 减少间接调用

/* 间接调用, 无法内联, BTB 预测可能失败 */
for (int i = 0; i < n; i++) {
    result += func_ptrsi;   /* 函数指针数组 */
}

/* 直接调用, 编译器内联 */
for (int i = 0; i < n; i++) {
    result += concrete_func(data[i]);   /* 编译器可内联 */
}

函数指针调用无法内联，且分支预测代价高。热路径用直接调用或 switch + 内联。

3. likely / unlikely 分支提示

#include <linux/compiler.h>  /* 内核 */
/* 或自己定义 */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

if (unlikely(error_condition)) {
    /* 错误处理, 编译器放函数末尾, 不污染热路径 cache */
    handle_error();
}
/* 正常路径在前, cache 友好 */

__builtin_expect 告诉编译器分支的倾向，编译器重排代码——likely 路径在前，unlikely 路径跳到末尾。改善指令 cache 命中。

DPDK rte_likely/rte_unlikely、内核 likely/unlikely 都是此宏。

4. __builtin_prefetch 预取

/* 预取下一元素到 cache, 隐藏内存延迟 */
while (cur) {
    __builtin_prefetch(cur->next, 0, 1);   /* 读, 一级 cache */
    process(cur);
    cur = cur->next;
}

预取让 CPU 在处理当前元素时并行加载下一元素，隐藏 cache miss 延迟。链表遍历、数组扫描受益明显。

5. restrict 指针别名提示

void add_arrays(int *restrict a, const int *restrict b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}

restrict 承诺指针不重叠，编译器可向量化（SIMD）和重排。无 restrict 时编译器保守假设可能重叠，无法优化。

6. 数据布局优化

/* 数组结构 (AoS), cache 不友好 */
struct Particle { float x, y, z, vx, vy, vz; };
struct Particle particles[N];
for (i) sum += particles[i].x;   /* 每次 stride 24 字节, cache 浪费 */

/* 结构数组 (SoA), cache 友好 */
struct Particles { float x[N], y[N], z[N], vx[N], vy[N], vz[N]; };
struct Particles ps;
for (i) sum += ps.x[i];   /* 连续访问, cache 100% 利用 */

数据布局比 register 关键字有效百倍——连续访问 + SIMD 批量处理。

选项 效果
-O0 不优化，调试友好
-O1 基础优化
-O2 标准优化（HFT 推荐）
-O3 激进优化（向量化、内联更激进）
-Os 优化大小

PGO（Profile-Guided Optimization）

# 1. 编译带 profiling

# 3. 用 profile 重新编译

编译器根据实际运行 profile 优化：

  • 热路径内联更激进
  • 分支布局按实际概率
  • 函数重排让热代码在同一 cache line

PGO 对 HFT 价值大——行情解析热路径明显，profile 引导优化显著。

18.2

C 和汇编语言的接口

本节讲什么

C 与汇编的边界：System V x86-64 ABI 调用约定、内联汇编 __asm__、静态链接 vs 动态链接、符号解析。这是 C 程序员理解"代码到底怎么跑"的关键一节——HFT 的极致优化、内核互调、DPDK PMD 都需要懂 ABI。

要点

System V x86-64 ABI 调用约定

项 规则
整数/指针参数 rdi, rsi, rdx, rcx, r8, r9（顺序）
浮点参数 xmm0-xmm7
多余参数 从右向左压栈
返回值（整数/指针） rax（及 rdx 用于 128 位）
返回值（浮点） xmm0
被调保存寄存器 rbx, rbp, r12, r13, r14, r15
调用者保存 rax, rcx, rdx, rsi, rdi, r8-r11, xmm0-xmm15
栈对齐 call 前 rsp 16 字节对齐
红区 叶子函数可用 rsp-128 到 rsp-8

这是 Linux/macOS 通用约定。Windows x64 ABI 不同（前 4 参数用 rcx/rdx/r8/r9，shadow space 32 字节）。

ABI 参数传递实例

int func(int a, int b, int c, int d, int e, int f, int g);
/*        rdi  rsi  rdx  rcx  r8   r9   栈 */

编译后：

func:
    mov    DWORD PTR [rsp+8],  ecx   ; g 在栈上 (调用者压的)
    ; rdi=a, rsi=b, rdx=c, rcx=d, r8=e, r9=f
    ...
    ret

内联汇编

static inline uint64_t rdtsc(void) {
    unsigned hi, lo;
    __asm__ __volatile__("rdtsc" : "=a"(lo), "=d"(hi));
    return ((uint64_t)hi << 32) | lo;
}

__asm__ 基本格式：

__asm__ (
    "汇编指令"
    : 输出操作数     (C 变量绑定)
    : 输入操作数     (C 变量绑定)
    : clobber 列表   (被修改的寄存器)
);
  • "=a"：绑定到 rax，= 表示输出
  • "a"：输入绑定到 rax
  • "d"：绑定到 rdx
  • __volatile__：禁止编译器重排或删除

内联汇编典型用途

1. 特殊指令

/* CPU 暂停, 节能 */
static inline void cpu_relax(void) {
    __asm__ __volatile__("pause" ::: "memory");
}

/* 内存屏障 */
static inline void mfence(void) {
    __asm__ __volatile__("mfence" ::: "memory");
}

/* 读取 TSC */
static inline uint64_t rdtscp(uint32_t *cpu) {
    uint32_t a, d, c;
    __asm__ __volatile__("rdtscp" : "=a"(a), "=d"(d), "=c"(c));
    if (cpu) *cpu = c;
    return ((uint64_t)d << 32) | a;
}

2. 原子操作

static inline int atomic_cas(int *p, int old, int new) {
    int result;
    __asm__ __volatile__(
        "lock cmpxchg %3, %1"
        : "=a"(result), "+m"(*p)
        : "a"(old), "r"(new)
        : "memory");
    return result == old;   /* 成功返回 1 */
}

但实际工程用 __atomic_* 内建函数或 <stdatomic.h>（C11），不手写汇编。

3. 系统调用

/* 直接 syscall, 绕过 glibc */
static inline long sys_write(int fd, const void *buf, size_t n) {
    long ret;
    __asm__ __volatile__(
        "syscall"
        : "=a"(ret)
        : "a"(1),           /* SYS_write = 1 */
          "D"(fd),          /* rdi */
          "S"(buf),         /* rsi */
          "d"(n)            /* rdx */
        : "rcx", "r11", "memory");
    return ret;
}

绕过 glibc 减少开销，HFT 极致场景用。但可移植性差，通常不值得。

静态链接 vs 动态链接

维度 静态链接 -static 动态链接（默认）
可执行文件 大（库打进 ELF） 小
启动速度 快（无 ld.so 解析） 慢（解析 .so）
内存占用 每进程一份库 共享一份物理页
升级 需重新编译 换 .so 即可
依赖 无 .so 依赖 需 .so 在系统
HFT 数据面 首选 次选 
gcc -static -o app app.c         # 静态
gcc -o app app.c                  # 动态（默认）
ldd ./app                         # 查看动态依赖

动态链接的符号解析

/* dlopen 运行时加载 .so */
#include <dlfcn.h>
void *handle = dlopen("./plugin.so", RTLD_NOW);
if (!handle) { fprintf(stderr, "%s\n", dlerror()); exit(1); }

typedef int (*func_t)(int);
func_t func = (func_t)dlsym(handle, "plugin_func");
if (!func) { fprintf(stderr, "%s\n", dlerror()); exit(1); }

int result = func(42);

dlclose(handle);
  • dlopen：加载 .so 到进程地址空间
  • dlsym：按符号名找函数/变量地址
  • dlclose：卸载（引用计数为 0 时）

HFT 策略热加载用此机制——运行时加载新策略 .so，dlsym 获取函数指针切换。

符号版本化

/* .so 版本化符号 */
__asm__(".symver old_func_v1,func@v1");
__asm__(".symver new_func_v2,func@@v2");   /* @@ 默认版本 */

int old_func_v1(int x) { return x; }
int new_func_v2(int x) { return x * 2; }

glibc 用版本化符号实现向后兼容——新版本库仍能链接旧二进制。__symver 指令控制符号版本。

链接错误

undefined reference（链接时）

/* main.c */
int main() { return undefined_func(); }

$ gcc main.c

链接器找不到符号定义。原因：

  • 忘了 #include 对应头
  • 忘了链接库 -l<lib>
  • 函数名拼写错误（C++ 还有 name mangling）

undefined symbol（运行时）

$ ./app

动态链接程序运行时找不到符号。原因：

  • .so 版本不匹配
  • 编译时 .so 有符号，运行时 .so 被替换
  • LD_LIBRARY_PATH 指向旧库

nm / objdump 观察符号

objdump -T ./libplugin.so   # 动态符号表
objdump -d ./app | head     # 反汇编
readelf -s ./app            # 符号表
  • T：代码段定义的函数（外部链接）
  • t：代码段定义的函数（static，内部链接）
  • D：数据段定义的变量
  • U：未定义符号（需链接时找）
  • W：弱符号

弱符号 weak

__attribute__((weak)) void optional_hook(void) { /* 默认空实现 */ }

/* 其他 .c 可覆盖 */

弱符号允许"可选覆盖"——若其他地方定义了同名强符号，用强符号；否则用弱符号。库设计插件钩子用此机制。

C 与汇编互调的注意事项

  • ABI 一致：C 和汇编必须遵守同一调用约定（System V x86-64）
  • 寄存器保存：汇编函数若用被调保存寄存器，必须 prologue 保存、epilogue 恢复
  • 栈对齐：汇编函数入口 rsp 必须是 16k - 8（call 后）
  • DF 标志：调用方需保证方向标志位 DF=0（字符串指令方向），C ABI 要求
  • 名字修饰：C 函数名无修饰，C++ 有 name mangling，互调用需 extern "C"

HFT 关联

  • ABI 一致：DPDK PMD、内核模块、C 代码互调必须遵守同一 ABI
  • 静态链接：HFT 数据面用 -static 避免 ld.so 动态解析，启动快且确定
  • dlopen 策略热加载：运行时加载新策略 .so，dlsym 获取函数指针
  • 内联汇编：rdtsc/pause/mfence 等特殊指令用内联汇编封装
  • 绕过 glibc：极致场景直接 syscall，但可移植性差，通常不值得
  • 符号可见性：-fvisibility=hidden 减小 .so，加快动态链接
  • 弱符号插件钩子：HFT 框架用弱符号定义默认空钩子，策略模块覆盖
  • PGO + LTO：-flto 跨文件内联，PGO 引导热路径优化

代码自测

题目 1： 以下内联汇编实现了什么功能？

static inline int atomic_add(int *ptr, int val) {
    int result;
    __asm__ __volatile__(
        "lock xadd %0, %1"
        : "+r"(val), "+m"(*ptr)
        : : "memory");
    return val;
}
参考答案

实现了原子加法。lock xadd 是 x86 的原子交换加法指令——它原子地执行 ptr += val 并返回 ptr 的旧值。lock 前缀保证多核下的原子性。volatile 防止编译器优化掉这条指令。"memory" clobber 告诉编译器内存可能被修改。这是无锁编程的基础原语。

18.3

运行时效率

本节讲什么

HFT 性能收官：堆的底层（brk/mmap）、cache line 与伪共享、hugepage 与 TLB、信号与崩溃诊断、调试工具（gdb/valgrind/perf）、用户态与内核的内存对照。这是全书的工程收尾——把前面所有章节的知识点串成一套可落地的 HFT 性能与稳定性方法论。

要点

堆的底层：brk 与 mmap

malloc 不是系统调用，是 glibc 的用户态封装。底层两种机制：

机制 用途 特点
brk/sbrk 小块连续分配 调整堆顶，连续扩展
mmap(MAP_ANONYMOUS) 大块、独立映射 独立映射，可单独 munmap

glibc malloc 策略：

  • 小块（通常 < 128KB）：用 brk 扩展堆顶，分配在连续堆区
  • 大块（>= 128KB）：用 mmap 独立映射，free 时 munmap 归还内核
  • free 后内存不立即归还内核，留在 malloc 自由链表供下次复用

DPDK 的内存策略：rte_malloc / hugepage

/* DPDK 用 mmap 映射 hugepage, 完全绕过 brk */
void *buf = rte_malloc("my_buf", 4096, 64);   /* 64 字节对齐 */
rte_free(buf);
  • rte_malloc 底层是 hugepage mmap，物理连续
  • 预分配所有 hugepage 启动时映射，运行时不再 mmap
  • 每 lcore 独立 free_list，无锁分配
  • 避免 brk 碎片和 glibc malloc 全局锁

Cache Line 与伪共享

现代 CPU cache line 通常 64 字节。多线程改同 cache line 不同变量 → 互相使对方 cache line 失效 → 性能崩塌（伪共享）：

/* 伪共享: 两个计数器在同一 cache line */
struct {
    int counter_a;   /* 线程 A 改 */
    int counter_b;   /* 线程 B 改 */
} stats;             /* 两个 int 在同一 64 字节 cache line */

线程 A 改 counter_a 使整个 cache line 失效，线程 B 的 counter_b 也被迫重新加载。反之亦然。两个本应独立的变量互相干扰。

伪共享的解决

1. padding 强制不同 cache line

struct Stats {
    int counter_a;
    char pad_a[60];   /* 填充到 64 字节 */
    int counter_b;
    char pad_b[60];
};

2. alignas / attribute((aligned))

struct AlignedCounter {
    int value;
} __attribute__((aligned(64)));

struct AlignedCounter counters[NTHREADS];   /* 每个元素独占 cache line */

3. per-thread 独立变量

/* 每线程独立计数器, 避免 cache line 争用 */
__thread int my_counter;   /* 线程局部存储 */
my_counter++;
/* 汇总时才读所有线程的 my_counter */

DPDK per-lcore 变量用此模式——RTE_PER_LCORE 宏定义每核独立变量。

Hugepage 与 TLB

TLB（Translation Lookaside Buffer）缓存虚拟地址→物理地址映射。TLB miss 极慢（数百周期）。

页大小 1GB 内存需要 TLB 条目数
4KB 262144 页 远超 TLB 容量
2MB 512 页 适配 L1 TLB
1GB 1 页 极少 TLB 条目

hugepage 大幅减少 TLB miss，HFT 数据面强制使用：

# 预留 hugepage
echo 1024 > /proc/sys/vm/nr_hugepages   # 1024 个 2MB 页 = 2GB

# 挂载 hugetlbfs
mkdir /mnt/huge
mount -t hugetlbfs nodev /mnt/huge

# DPDK 启动用 hugepage
./dpdk-app -c 0xf -n 4 -- -huge

NUMA 与内存亲和

多路 CPU 系统，每 CPU 有本地内存。跨 NUMA 访问内存慢 2-3x：

/* NUMA 感知分配 */
#include <numa.h>
void *buf = numa_alloc_onnode(size, 0);   /* 分配在 NUMA 节点 0 */
numa_free(buf, size);

DPDK rte_malloc 接受 socket_id 参数，分配在指定 NUMA 节点。HFT 数据线程绑核 + 内存本地分配，避免跨 NUMA。

pthread_mutex spinlock/mutex 同步
pthread_create kthread_create 线程
stdio FILE* file/inode 文件抽象

HFT 数据面绕过所有用户态抽象，直接操作硬件（PMD + DMA + hugepage），类似内核性能模型。

性能优化的层次

层次 优化 收益

微优化 inline + restrict 1.2x

从上往下收益递减。先优化算法和数据结构，再 cache 和内存，最后才是编译选项和微优化。

  • core dump + gdb：崩溃诊断标配，ulimit -c unlimited + core_pattern
  • ASan CI：开发期必跑，查越界/UAF/double free

代码自测

题目 1： 以下两种实现在性能上有什么差异？为什么？

// A: 普通调用
for (int i = 0; i < n; i++)
    sum += arr[i];
// B: 循环展开
for (int i = 0; i < n; i += 4) {
    sum += arr[i];
    sum += arr[i+1];
    sum += arr[i+2];
    sum += arr[i+3];
}
参考答案

B 通过循环展开减少分支预测失败和循环开销。每次迭代处理 4 个元素，循环次数减少为 1/4。但现代编译器（GCC -O2）会自动做循环展开，手写展开通常没有额外收益且降低可读性。过度展开还可能损害指令缓存。注意 B 需要处理 n 不是 4 的倍数的情况。

18.4

ELF 文件回顾：sections vs segments

ELF 是什么

ELF（Executable and Linkable Format）是 Linux 上的标准二进制格式。编译器输出的 .o、链接器输出的可执行文件、共享库 .so、内核模块 .ko、内核镜像 vmlinux 都是 ELF 文件。

两种视角：Linking View vs Execution View

ELF 文件有两组头部，对应两种视角：

视角 头部 看到什么 谁用
Linking View（链接视角） Section Header Table（节头表） .text .data .bss .symtab .rel.text 等 编译器、链接器、nm、readelf -S
Execution View（执行视角） Program Header Table（程序头表） LOAD 段、INTERP、DYNAMIC 等 内核加载器、动态链接器 
  Linking View                Execution View
  ┌──────────┐                ┌──────────┐
  │ Section  │                │ Segment  │
  │ Header   │                │ Header   │
  │ Table    │                │ Table    │
  └────┬─────┘                └────┬─────┘
       │                           │
  ┌────▼───────────────────────────▼────┐
  │                                      │
  │  .text  ──────────────────►  LOAD(R) │
  │  .rodata ─────────────────►  LOAD(R) │
  │  .data  ──────────────────►  LOAD(RW)│
  │  .bss   ── (无文件内容) ───►  LOAD(RW)│
  │  .symtab (不加载)                   │
  │  .rel.text (不加载)                 │
  │                                      │
  └──────────────────────────────────────┘
  • Section（节）：给链接器看的，"代码放这、数据放那、符号表在这"
  • Segment（段）：给加载器看的，"这块读进来映射到 R，那块映射到 RW"

一个 LOAD segment 可以包含多个 section（.text + .rodata 合并到一个 R 段）。

常见 Section

Section 内容 加载?
.text 机器指令 是（R）
.rodata 只读数据（字符串常量、const 全局） 是（R）
.data 已初始化全局变量 是（RW）
.bss 未初始化全局变量（文件中不占空间） 是（RW，清零）
.symtab 符号表（编译时，可 strip） 否
.dynsym 动态符号表（运行时导出/导入） 是
.strtab 符号名字符串 否
.debug_* DWARF 调试信息（-g） 否
.rel.text .text 的重定位项 链接后清除
.note.* 备注（build-id 等） 视情况

ELF 文件类型

readelf -h a.out | grep Type
Type 含义 示例
REL 可重定位文件 .o、.ko
EXEC 可执行文件 /bin/ls
DYN 共享库 / PIE 可执行 libdpdk.so、现代 a.out
CORE core dump core

用 readelf 快速验证

# ELF 头：类型、架构、入口地址

# 所有节（Linking View）
readelf -S a.out

# 所有程序段（Execution View）
readelf -l a.out

18.5

nm：符号表查看

nm 是什么

nm 列出 ELF 文件中的符号表（.symtab 或 .dynsym），告诉你这个文件定义了哪些函数/变量、引用了哪些外部符号。是最常用的二进制排查工具。

基本用法

nm vmlinux                 # 内核符号
nm libdpdk.so              # DPDK 共享库符号
nm mod.ko                  # 内核模块符号
nm main.o                  # 目标文件符号

常用选项

选项 作用
-D 读动态符号表 .dynsym（看 .so 真正导出的 API）
-g 只看全局符号（排除 static 局部）
-u 只看未定义符号（U 类型，这个模块依赖哪些外部函数）
--defined-only 只看已定义符号
-n 按地址排序
-S 显示符号大小
-C demangle C++ 符号名（_Z3fooi → foo(int)）

符号类型标记

nm 输出每行三列：地址 类型 符号名

标记 大小写 含义
T / t 大写=全局，小写=static 代码段（.text）函数
D / d 已初始化全局数据（.data）
B / b BSS 段，未初始化全局变量
R / r 只读数据（.rodata）
U 无大小写区分 未定义——需要外部链接提供
W / w 弱符号（weak symbol）
A 绝对地址（不可重定位）
N 调试符号
- stabs/debug 格式

大写 = 全局（external linkage），小写 = 局部（static）

示例输出

$ nm main.o
                 U printf       # 未定义：需要链接 libc
0000000000000000 T main         # 全局函数：main，地址 0（可重定位）
0000000000000000 t helper       # static 函数：helper
0000000000000000 D global_var   # 全局变量：已初始化
0000000000000004 B uninit_var   # 全局变量：未初始化（BSS）

内核模块场景

$ cat /proc/kallsyms | grep platform_driver_register

nm vs readelf -s

nm readelf -s
输出 简洁（地址 类型 名字） 详细（绑定、可见性、size、ndx 等）
默认读 .symtab .symtab
动态符号 需要 -D readelf --dyn-syms
易读性 更好 更全但更冗长

日常排查用 nm，需要详细信息用 readelf -s。

1. inline 内联函数——源码看不到单独函数

源码里 add 是独立函数，但编译器内联后它消失了——只有反汇编能看到真实指令。

2. 没有调试符号的二进制

场景

你的 DPDK 应用链接报错 undefined reference to rte_eth_dev_configure，需要确认这个 API 在哪个 .so 里导出。

步骤

# 1. 找到 DPDK 库目录
ls /usr/lib/x86_64-linux-gnu/librte_eth*.so

# 2. 看动态符号表，确认 API 是否导出
nm -D librte_eth.so | grep rte_eth_dev_configure
00000000000012a0 T rte_eth_dev_configure    ← T = 已定义全局函数

# 3. 如果找不到，看是不是名字变了
nm -D librte_eth.so | grep rte_eth
# DPDK 22+ 改名为 rte_ethdev_*，老代码用 rte_eth_* 可能对不上

# 4. 看这个库依赖哪些其他库
readelf -d librte_eth.so | grep NEEDED
  NEEDED libnuma.so.1
  NEEDED librte_eal.so.22
  NEEDED librte_mbuf.so.22
  NEEDED librte_mempool.so.22

# 5. 如果 API 不在这个 .so，搜索所有 DPDK 库
for f in /usr/lib/x86_64-linux-gnu/librte_*.so; do
  echo "=== $(basename $f) ==="
  nm -D "$f" | grep rte_eth_dev_configure
done

# 6. 找到后看反汇编确认实现
objdump -d --disassemble=rte_eth_dev_configure librte_eth.so

常见问题

问题 原因 排查
undefined reference 链接时找不到符号 nm -D *.so \| grep <symbol>
符号在 .so 里但运行时报找不到 LD_LIBRARY_PATH 没设 ldd ./app 看依赖
DPDK 版本升级后 API 消失 版本不兼容 nm -D 对比新旧 .so
符号是 U 不是 T 这个 .so 也没定义，依赖别的 nm -u 追踪依赖链

案例 2：内核模块 .ko 排查

场景

insmod mydriver.ko 报错：Unknown symbol: platform_driver_register。

步骤

# 1. 看模块依赖哪些外部符号（U 类型）
nm -u mydriver.ko
                 U printk
                 U platform_driver_register
                 U devm_ioremap
                 U __register_chrdev

# 2. 确认内核是否导出了这个符号
# 方法 a：看 /proc/kallsyms（运行中的内核）
cat /proc/kallsyms | grep platform_driver_register
ffffffffc0001234 T platform_driver_register

# 方法 b：看 vmlinux 符号表
nm vmlinux | grep platform_driver_register
ffffffffc0001234 T platform_driver_register

# 3. 如果符号存在但模块还是加载不了，可能是 EXPORT_SYMBOL 问题
# 看内核是否用 EXPORT_SYMBOL 导出了它
grep "platform_driver_register" /lib/modules/$(uname -r)/build/Module.symvers
# 如果 Module.symvers 里没有，说明内核配置没开或者没 EXPORT

# 4. 看模块的重定位项，确认需要修补哪些地址
readelf -r mydriver.ko
Relocation section '.rela.text' at offset 0x3a8 contains 8 entries:
  Offset          Info           Type           Sym. Name
0000000000030  000a00000002 R_X86_64_PC32     printk - 4
0000000000040  000500000002 R_X86_64_PC32     platform_driver_register - 4
  ↑ call 指令的目标地址，insmod 时内核填入实际地址

# 5. 看模块的 ELF 头，确认架构匹配
readelf -h mydriver.ko
  Class:      ELF64
  Machine:    Advanced Micro Devices X86-64    ← 和内核架构一致？

常见问题

问题 原因 排查
Unknown symbol 内核没导出该符号 nm -u + /proc/kallsyms
架构不匹配 交叉编译用错工具链 readelf -h 看 Machine
版本不兼容 内核 ABI 变化 对比 Module.symvers
Invalid module format vermagic 不匹配 modinfo mydriver.ko

案例 3：分析 inline 函数的真实汇编

场景

DPDK 热路径里 rte_eth_rx_burst 是 inline 函数，性能分析需要看实际生成的汇编。

# DPDK 头文件里的 inline 函数会被展开到调用处
# 源码看不到独立函数体，只有反汇编能看到

# 方法 1：反汇编整个 .o
objdump -dS rte_ethdev.o | grep -A30 "rte_eth_rx_burst"

# 方法 2：如果链接进了 .so
objdump -d --disassemble=rte_eth_rx_burst librte_eth.so
# 如果是 inline 的，这个命令可能找不到——函数被内联到调用者里了

# 方法 3：反汇编调用者，看 inline 展开
objdump -dS librte_eth.so | grep -B5 -A20 "call.*rte_eth_rx_burst"
# 如果被完全内联，连 call 都没有——直接是内联展开的指令

18.9

静态分析 vs 动态调试边界

核心区分

静态分析 动态调试
工具 nm / readelf / objdump GDB / crash / strace / ltrace
程序状态 不用跑，分析磁盘上的文件 运行中 / 暂停 / core dump
能看到 符号、ELF 结构、重定位、汇编 内存值、寄存器、栈、变量、断点
看不到 运行时变量的值、动态分配的地址 —
适用场景 链接错误、符号缺失、编译器优化分析、逆向 运行时崩溃、逻辑错误、数据竞争

什么时候用静态分析

1. 链接错误

# 报 undefined reference to foo
nm -D libxxx.so | grep foo        # foo 在不在这个 .so？
nm -u main.o                      # main.o 期望的 foo 是什么名字？

2. 符号缺失 / 导出问题

# 内核模块加载报 Unknown symbol
nm -u mod.ko                      # 模块依赖什么？
cat /proc/kallsyms | grep <sym>   # 内核导出了吗？

3. 分析编译器优化

# -O2 后行为变了，看编译器做了什么
objdump -dS main_O2.o             # 源码+汇编混排

4. 没有源码的逆向

# 只有二进制，没有源码
objdump -d ./unknown_binary       # 反汇编看逻辑
readelf -s ./unknown_binary       # 看符号表找线索
nm -D ./unknown_binary            # 看动态符号，推测功能

5. ELF 布局 / 段大小

size a.out                        # text/data/bss 多大？
readelf -S a.out                  # 所有节的大小和地址
readelf -l a.out                  # 运行时 LOAD 段布局

什么时候用动态调试（GDB）

1. 运行时崩溃

gdb ./app core
(gdb) bt                          # 崩溃栈
(gdb) print *ptr                  # 崩溃时指针的值

静态分析看不到运行时的值——变量在运行时才被写入内存。

2. 逻辑错误（不崩溃但行为不对）

gdb ./app
(gdb) break loop_body
(gdb) run
(gdb) next
(gdb) print count                 # 看循环变量实际值

3. 多线程竞争

gdb -p <PID>
(gdb) info threads                # 所有线程在干什么
(gdb) thread apply all bt         # 全栈快照

4. 内存泄漏 / 踩内存

gdb ./app
(gdb) watch *corrupted_addr       # 谁在写这块内存？
# 或用 Valgrind（更适合内存泄漏）

完整排错工作流

遇到问题
    │
    ├── 编译/链接时错误 ──→ 静态分析
    │   ├── undefined reference → nm -D / nm -u
    │   ├── 符号冲突 → nm -g / readelf -s
    │   └── 段大小异常 → size / readelf -S
    │
    ├── 运行时崩溃 ──→ 动态调试 + 静态辅助
    │   ├── core dump → gdb bt
    │   ├── 崩溃地址 → objdump -d 找函数
    │   └── 依赖缺失 → readelf -d / ldd
    │
    ├── 运行时行为异常 ──→ 动态调试
    │   ├── 逻辑错误 → gdb 断点 + print
    │   ├── 多线程 → gdb info threads
    │   └── 性能问题 → perf（不是 gdb 强项）
    │
    └── 只有二进制 ──→ 静态分析
        ├── 反汇编 → objdump -d
        ├── 符号表 → nm / readelf -s
        └── 依赖 → readelf -d

思考题

静态工具能不能看到程序运行时变量的值？为什么？

不能。nm/readelf/objdump 分析的是磁盘上的 ELF 文件，变量值在进程运行时才写入内存。静态工具只能看到变量的地址/偏移和初始值（.data 段里），看不到运行时被修改后的值。运行时值要看 GDB（print var）或 /proc/<pid>/mem。
