11.1

为什么使用动态内存分配

本节讲什么

C 程序的内存分为栈、静态段（.data/.bss）、堆三大区域，各自有不同的分配方式、生命周期、容量上限。动态内存分配（malloc/free）是处理运行时才知道大小的数据、大容量对象、跨函数生命周期的对象的唯一选择。理解三区的差异是 HFT 性能优化的前提——栈最快但容量小，堆灵活但有 malloc 开销和碎片风险，DPDK 的 rte_mempool 是堆思想的工业优化。

历史背景

C 的动态内存分配源自 1970s UNIX 的 sbrk/brk 系统调用，ANSI C89 标准化为 malloc/free/calloc/realloc。POSIX 后来加入 mmap/munmap 用于大块映射。现代 glibc 的 malloc 用 brk 处理小对象、mmap 处理大对象，并维护 per-thread arena 减少锁竞争。Linux 内核用 kmalloc/vmalloc 提供类似服务。DPDK 用 rte_mempool 绕过 libc，预分配固定块池，无锁、无碎片、cache 友好。

要点

三大内存区域对比

区域 分配方式 生命周期 容量 速度 适用
栈 自动（mov sp） 块结束自动回收 ~1-8 MB（ulimit -s） 最快（1 周期） 小临时变量
静态 .data 编译期 进程全程 固定（编译期决定） 快 已初始化全局
静态 .bss 启动时清零 进程全程 固定 快 未初始化全局
堆 malloc/free 手动 GB 级（受虚拟地址限制） 慢（50-200 ns） 变长、大对象、跨函数

栈的特点

void f(void) {
    int x = 42;           /* 栈上，4 字节 */
    char buf[1024];       /* 栈上，1 KB */
    struct big b;         /* 栈上，sizeof(struct big) */
    /* 块结束自动回收 */
}
  • 分配：sub $size, %rsp，1 周期
  • 回收：add $size, %rsp，1 周期
  • 容量：Linux 默认 8 MB（ulimit -s），超出 → SIGSEGV
  • 无碎片：LIFO 分配，回收后立即可用

栈的限制：

  • 大数组（>1 MB）有栈溢出风险
  • VLA（变长数组）同样危险（ch08）
  • 生命周期限于函数块，不能跨函数返回

静态段的特点

static int config_val = 42;        /* .data，已初始化 */
static int counter;                 /* .bss，未初始化，启动时清零 */
int global_var = 100;               /* .data，全局 */
  • 编译期决定大小，运行时不可变
  • 生命周期 = 进程生命周期
  • 多线程共享，需同步
  • 适合全局配置、只读表

堆的特点

void f(void) {
    struct big *p = malloc(sizeof *p);   /* 堆上分配 */
    if (!p) return;
    /* ... 使用 ... */
    free(p);                              /* 手动回收 */
}
  • 运行时按需分配，大小可变
  • 生命周期手动控制——忘记 free 则泄漏
  • 容量大（受虚拟地址限制，通常 TB 级）
  • 有碎片风险（外部/内部）
  • malloc 开销：50-200 ns（glibc），DPDK mempool 约 10-30 ns

何时必须用堆

场景 原因 选择
运行时才知道大小 栈大小编译期固定 堆
单块 > 1 MB 栈容量限制 堆
跨函数生命周期 栈块结束回收 堆
变长缓冲（如报文） 大小随输入变化 堆
链表/树节点 动态增减 堆
大对象（>256 字节） 栈拷贝昂贵 堆（传指针）

HFT 栈 vs 堆选型

优先栈 强制堆
< 256 字节、块内短命 运行时变长
无手动释放需求 跨函数存活
编译期已知大小 单块 > 1 KB
临时解析缓冲 长生命周期订单/连接对象

HFT 铁律：热路径上避免 malloc/free——改用预分配内存池。栈适合小临时变量，堆适合大对象和长生命周期对象。

DPDK rte_mempool：堆的工业优化

struct rte_mempool *pool = rte_pktmbuf_pool_create(
    "mbuf_pool",      /* 名称 */
    8192,             /* 块数 */
    256,              /* cache 大小（每核） */
    0,                /* 私有大小 */
    RTE_MBUF_DEFAULT_BUF_SIZE,
    rte_socket_id()   /* NUMA 节点 */
);

struct rte_mbuf *m = rte_pktmbuf_alloc(pool);   /* 从池取 */
/* ... 使用 ... */
rte_pktmbuf_free(m);                             /* 归还池 */

DPDK mempool 的优势：

维度 malloc rte_mempool
分配开销 50-200 ns 10-30 ns
碎片 有 无（固定块大小）
多线程 全局锁 无锁（per-lcore cache）
NUMA 不感知 感知（每节点独立池）
cache 友好 不保证 块对齐 cache 行
生命周期 手动 free 手动 free，但池有上限

HFT 报文处理的核心设计：启动时预分配 mempool，运行时只 alloc/free，无 malloc 系统调用。

HFT 关联

  • 报文缓冲：DPDK mbuf 从 mempool 分配，不调 malloc
  • 订单池：订单对象预分配固定数量，运行时从池取/还
  • NUMA 感知：每 NUMA 节点独立 mempool，避免跨节点访问延迟
  • 大页：mempool 用 hugepage 映射，减少 TLB miss
  • 栈使用铁律：HFT 热路径的栈缓冲应 < 4 KB，避免栈溢出和 cache 污染

实操：栈溢出

void bad(void) {
    char big[10 * 1024 * 1024];   /* 10 MB，远超栈限制 */
    /* SIGSEGV：栈溢出 */
}

/* 修复：用堆 */
void good(void) {
    char *big = malloc(10 * 1024 * 1024);
    if (!big) return;
    /* ... */
    free(big);
}

实操：栈 vs 堆性能

/* 栈分配：1 周期 */
void stack_use(void) {
    struct small s;   /* 栈上 */
    s.x = 1;
}

/* 堆分配：约 100 ns */
void heap_use(void) {
    struct small *s = malloc(sizeof *s);   /* 堆上 */
    if (!s) return;
    s->x = 1;
    free(s);
}

100 万次调用，栈版本约 1 ms，堆版本约 100 ms——100 倍差距。

11.2

malloc 和 free

本节讲什么

malloc 和 free 是 <stdlib.h> 最基础的堆 API：malloc 分配指定字节数的原始内存，free 归还。二者看似简单，但有返回值检查、脏数据、双重释放、偏移 free 等多个致命陷阱。本节剖析 API 细节、内存布局、free 的规则、以及工业级使用模式。

要点

malloc 函数原型

#include <stdlib.h>
void *malloc(size_t size);
  • 参数：size 字节数
  • 返回：成功返回 void *（需转为目标类型），失败返回 NULL
  • 不清零：内存内容是脏数据（之前用过的数据）
  • 对齐：返回地址按 max_align_t 对齐（glibc 16 字节，适合所有标准类型）

基本用法

struct quote_hdr *pkt = malloc(sizeof *pkt);   /* 推荐写法 */
if (!pkt) {
    return -ENOMEM;   /* 内存耗尽容错 */
}
pkt->seq = 1001;
/* ... */
free(pkt);
pkt = NULL;

sizeof *pkt 的优势：

  • 不需要写 sizeof(struct quote_hdr)，类型名只出现一次
  • 改类型时只需改声明，sizeof 自动跟随
  • 是 C 代码的惯用法

malloc 的内存布局

返回地址 p
       ↓
+------+-------------------+------+
| 头部 |   用户可用区域     | padding |
+------+-------------------+------+
       |<---- size 字节 --->|
  • malloc 实际分配的块比 size 大：含头部元数据（块大小、空闲链表指针）
  • 用户拿到的是头部之后的地址
  • 头部对用户透明，但越界写会破坏它 → 延迟崩溃

free 函数原型

#include <stdlib.h>
void free(void *ptr);
  • 参数：malloc/calloc/realloc 返回的原始地址
  • 无返回值
  • free(NULL) 是安全空操作

free 的三条铁律

铁律 1：只能 free 原始地址

int *arr = malloc(10 * sizeof(int));
free(arr + 5);   /* UB：偏移后的地址 */
free(arr);       /* 正确 */
  • 偏移后的地址不是 malloc 返回的，free 无法找到头部
  • ASan 会报 attempting free on address which was not malloc()-ed

铁律 2：只能 free 一次

int *p = malloc(sizeof(int));
free(p);
free(p);   /* UB：双重释放，通常 SIGABRT */
  • 双重释放破坏 free list，导致堆损坏
  • 防御：if (p) { free(p); p = NULL; }

铁律 3：free(NULL) 安全

free(NULL);   /* 空操作，无副作用 */
  • C 标准保证 free(NULL) 是 no-op
  • 让"先判 NULL 再 free"模式可简化为 free(p); p = NULL;

free 后置 NULL

free(p);
p = NULL;   /* 防止悬垂指针 */
  • free 后 p 仍指向原地址（悬垂指针）
  • 若后续误用 *p = 1，可能：
  • 立即崩溃（若该页已归还内核）
  • 静默踩踏（若内存被复用）—— 更危险
  • p = NULL 让误用立即 SIGSEGV，快速暴露 bug

malloc 的失败模式

int *p = malloc(100 * 1024 * 1024 * 1024);   /* 100 GB */
if (!p) {
    /* 失败：内存不足 */
    perror("malloc");
    exit(1);
}
  • 大块分配可能失败（虚拟内存耗尽、ulimit 限制）
  • 铁律：每次 malloc 后必须判 NULL
  • OOM 处理：降级、报错、退出

Linux 的 OOM 行为

Linux 默认overcommit：malloc 即使物理内存不足也返回非 NULL，真正用时才 OOM killer 杀进程。这导致"malloc 成功不代表能用"的怪象。

echo 2 > /proc/sys/vm/overcommit_memory   /* 严格模式，禁止 overcommit */

HFT 服务器通常关闭 overcommit，确保 malloc 失败能被捕获。

malloc 的实现选择

分配器 特点 适用
glibc ptmalloc2 多线程 arena，全局锁 通用
tcmalloc Google，thread-local cache 多线程优化
jemalloc FreeBSD/Facebook，低碎片 长跑进程
mimalloc 微软，高性能 现代多核
DPDK rte_malloc 无锁，NUMA 感知 HFT
自研 mempool 固定块，零碎片 极致性能

HFT 通常用 jemalloc（低碎片）或 DPDK rte_malloc（无锁）替代 glibc malloc。

aligned_alloc / posix_memalign

/* C11 aligned_alloc */
void *p = aligned_alloc(64, size);   /* 64 字节对齐 */
free(p);

/* POSIX posix_memalign */
void *p;
posix_memalign(&p, 64, size);
free(p);
  • 用于 cache 行对齐（64 字节）、DMA 对齐、SIMD 对齐
  • DPDK 内部大量使用对齐分配
  • 仍用 free 释放

HFT 关联

  • DPDK rte_malloc：无锁分配器，per-lcore cache，约 10-30 ns（glibc malloc 约 50-200 ns）
  • mempool 替代 malloc：热路径不调 malloc，从预分配池取
  • NUMA 感知：rte_malloc_socket(numa_node) 在指定节点分配
  • 大页：DPDK 用 hugepage 映射，减少 TLB miss
  • OOM 处理：HFT 进程通常在启动时预分配所有内存，运行时不 malloc，避免 OOM

实操：malloc 脏数据

int *a = malloc(10 * sizeof(int));
/* a 的内容是脏数据 */
for (int i = 0; i < 10; i++) printf("%d ", a[i]);   /* 随机值 */
free(a);

/* calloc 清零 */
int *b = calloc(10, sizeof(int));
for (int i = 0; i < 10; i++) printf("%d ", b[i]);   /* 全 0 */
free(b);

实操：双重 free

int *p = malloc(sizeof(int));
free(p);
free(p);   /* SIGABRT: double free or corruption */

glibc 检测到双重 free 会调用 abort()，ASan 报 attempting double-free。

实操：偏移 free

int *arr = malloc(10 * sizeof(int));
free(arr + 2);   /* ASan: attempting free on address which was not malloc()-ed */

实操：free 后置 NULL

int *p = malloc(sizeof(int));
free(p);
p = NULL;     /* 防悬垂 */

if (p) {      /* 后续误用前判空 */
    *p = 42;
}

11.3

calloc 和 realloc

本节讲什么

calloc 是 malloc 的清零版——分配并初始化为 0，适合新数组和结构体池。realloc 扩缩容已分配的块，但有丢指针泄漏的高危写法。本节剖析二者的机制、与 malloc 的区别、realloc 的安全模式、以及 calloc 的乘法溢出陷阱。

要点

calloc 函数原型

#include <stdlib.h>
void *calloc(size_t nmemb, size_t size);
  • 参数：nmemb（元素数）× size（每元素字节数）
  • 返回：成功返回清零的内存，失败返回 NULL
  • 清零：所有字节初始化为 0
  • 等价 malloc(nmemb * size) + memset(0)，但 calloc 检测乘法溢出

calloc 基本用法

/* 分配 32 个 rte_mbuf，清零 */
struct rte_mbuf *pkts = calloc(32, sizeof *pkts);
if (!pkts) {
    return -ENOMEM;
}
/* pkts 的所有字节都是 0 */

calloc vs malloc + memset

维度 calloc malloc + memset
清零 是 需手动 memset
溢出检测 内置 需手动
性能 更快（OS 已清零页） 慢（实际写 0）
语义 元素数 × 大小 总字节数

calloc 更快的原因：

  • Linux 的零页（zero page）已是 0，calloc 用 mmap 映射零页时 COW（copy-on-write）
  • 首次写才分配物理页
  • malloc + memset 必须实际写 0，触发 COW

calloc 的乘法溢出保护

/* 危险：malloc 的乘法可能溢出 */
size_t n = SIZE_MAX;
int *p = malloc(n * sizeof(int));   /* 溢出，分配远小于预期 */
/* p 实际指向小块，写入越界 */

/* 安全：calloc 内置溢出检测 */
int *p = calloc(n, sizeof(int));   /* 检测到溢出，返回 NULL */
  • nmemb * size 若溢出，calloc 返回 NULL
  • malloc 无此检测，需手动：if (n > SIZE_MAX / sizeof(int)) return NULL;
  • 铁律：用户输入驱动的大块分配用 calloc

realloc 函数原型

#include <stdlib.h>
void *realloc(void *ptr, size_t size);
  • 参数：ptr（已分配块，或 NULL）、size（新大小）
  • 返回：成功返回新块地址（可能与 ptr 相同），失败返回 NULL
  • ptr == NULL 时等价 malloc
  • size == 0 且 ptr != NULL 时等价 free（C89）；C11 行为实现定义

realloc 的行为

ptr size 行为
NULL 任意 等价 malloc(size)
非 NULL > 原大小 可能新块 + 拷贝旧数据 + 释放旧块
非 NULL < 原大小 截断（实现相关，可能不移动）
非 NULL 0 等价 free(ptr)，返回 NULL（C89）

关键：realloc 可能返回不同地址——原块不够大时分配新块、拷贝、释放旧块。

realloc 的丢指针陷阱

/* 反例：丢指针泄漏 */
pkt_buf = realloc(pkt_buf, new_len);
/* 若 realloc 失败返回 NULL：
 * 1. pkt_buf 被赋值为 NULL
 * 2. 原块地址丢失，无法 free
 * 3. 内存泄漏
 */

安全模式：

/* 正例：临时变量保存 */
void *tmp = realloc(pkt_buf, new_len);
if (tmp != NULL) {
    pkt_buf = tmp;   /* 成功才更新 */
} else {
    /* 失败：pkt_buf 仍有效，业务降级或退出 */
    /* 原块仍需 free */
}

铁律：realloc 永远用临时变量接收，判成功后再更新原指针。

realloc 的性能

/* 逐个增长：O(n²) */
for (int i = 0; i < 1000; i++) {
    buf = realloc(buf, i + 1);   /* 每次可能拷贝 */
}

/* 倍增策略：O(n) amortized */
size_t cap = 16;
buf = malloc(cap);
for (int i = 0; i < 1000; i++) {
    if (i >= cap) {
        cap *= 2;
        void *tmp = realloc(buf, cap);
        if (!tmp) { free(buf); return -1; }
        buf = tmp;
    }
    buf[i] = /* ... */;
}
  • realloc 在原地扩展时 O(1)
  • 需要移动时 O(n)（拷贝旧数据）
  • 倍增策略让平均 O(1)（几何级数摊还）
  • C++ std::vector 的增长策略即此

realloc 的移动语义

int *p = malloc(10 * sizeof(int));
int *old = p;
p = realloc(p, 1000000 * sizeof(int));   /* 大概率移动 */
/* p 可能 != old，old 已释放，不能再访问 */
  • realloc 后所有指向原块的指针失效
  • 必须用返回的新地址
  • 若有其他指针指向原块内部，它们也失效——需更新

calloc/realloc 与 free

calloc 和 realloc 返回的内存都用 free 释放：

int *a = calloc(10, sizeof(int));
free(a);

int *b = malloc(10 * sizeof(int));
int *c = realloc(b, 20 * sizeof(int));
if (c) { b = c; }   /* b 指向新块 */
free(b);             /* 释放 */

HFT 关联

  • DPDK rte_calloc：DPDK 的 calloc 等价，清零分配
  • DPDK rte_realloc：DPDK 的 realloc，但通常用 mempool 避免
  • 订单池预分配：calloc(MAX_ORDERS, sizeof(struct order)) 启动时一次分配，运行时不 realloc
  • 报文缓冲扩容：HFT 报文通常定长，不用 realloc
  • mempool 替代：热路径用 rte_pktmbuf_alloc/free，不调 calloc/realloc

实操：calloc 清零 vs malloc 脏数据

#include <stdio.h>
#include <stdlib.h>

int main(void) {
    /* malloc：脏数据 */
    int *a = malloc(5 * sizeof(int));
    printf("malloc:");
    for (int i = 0; i < 5; i++) printf(" %d", a[i]);
    printf("\n");   /* 随机值 */
    free(a);

    /* calloc：清零 */
    int *b = calloc(5, sizeof(int));
    printf("calloc:");
    for (int i = 0; i < 5; i++) printf(" %d", b[i]);
    printf("\n");   /* 全 0 */
    free(b);
}

实操：realloc 丢指针

int *buf = malloc(100);
/* ... */
buf = realloc(buf, 1000000000);   /* 大概率失败 */
if (!buf) {
    /* 灾难：原 100 字节地址丢失，泄漏 */
    /* 无法 free 原块 */
}

/* 修复 */
int *tmp = realloc(buf, 1000000000);
if (!tmp) {
    free(buf);   /* 原块仍可访问 */
    return -1;
}
buf = tmp;

实操：倍增策略

struct vector {
    int *data;
    size_t size, cap;
};

int vec_push(struct vector *v, int x) {
    if (v->size >= v->cap) {
        size_t new_cap = v->cap ? v->cap * 2 : 16;
        int *tmp = realloc(v->data, new_cap * sizeof(int));
        if (!tmp) return -1;
        v->data = tmp;
        v->cap = new_cap;
    }
    v->data[v->size++] = x;
    return 0;
}

这是 C++ std::vector 的核心逻辑。

11.4

使用动态分配的内存

本节讲什么

堆内存的完整生命周期管理是工业级 C 代码的核心：分配判空、记录长度、用完 free、置 NULL。本节把这些规范总结为四条硬性规则，并剖析异常路径的资源释放、长度记录、封装模式等工程实践。掌握这些规则可避免 90% 的内存相关 bug。

要点

四条硬性规则

规则 1：分配后判 NULL

struct quote_hdr *pkt = malloc(sizeof *pkt);
if (!pkt) {
    return -ENOMEM;   /* 内存耗尽容错 */
}
  • malloc 可能失败（虚拟内存耗尽、ulimit 限制）
  • 每次 malloc 后必须立即判 NULL
  • 不判直接用 pkt->seq = 1 → NULL 解引用 → SIGSEGV

规则 2：free 只用原始返回地址

struct quote_hdr *pkt = malloc(sizeof *pkt);
/* ... */
free(pkt);   /* 正确：原始地址 */

free(pkt + 1);   /* UB：偏移后地址 */
free(&pkt->seq); /* UB：成员地址 */
  • malloc 返回的地址是 free 唯一能接受的
  • 偏移、成员地址都会让 free 找不到头部

规则 3：每条成功路径都要 free

int f(void) {
    struct obj *o = malloc(sizeof *o);
    if (!o) return -1;

    if (step1(o) < 0) {
        free(o);   /* 异常路径也要 free */
        return -2;
    }
    if (step2(o) < 0) {
        free(o);
        return -3;
    }

    /* ... 正常路径 ... */
    free(o);
    return 0;
}
  • 每个分支、异常 return 都要 free
  • 漏 free → 内存泄漏
  • 最佳实践：用 goto cleanup 模式统一释放
int f(void) {
    struct obj *o = NULL;
    int ret = -1;

    o = malloc(sizeof *o);
    if (!o) goto out;

    if (step1(o) < 0) goto out;
    if (step2(o) < 0) goto out;

    ret = 0;
out:
    free(o);   /* 统一释放点 */
    return ret;
}

规则 4：free 后立即 ptr = NULL

free(pkt);
pkt = NULL;
  • 防止悬垂指针误用
  • free(NULL) 安全，后续再 free 也无碍
  • 调试时 NULL 比 dangling 指针更易识别

记录分配长度

size_t cap = 1024;
uint8_t *buf = malloc(cap);
if (!buf) return -1;

size_t offset = 0;
/* 读写前：offset < cap */
if (offset + n <= cap) {
    memcpy(buf + offset, data, n);
    offset += n;
}
  • malloc 不记录用户长度——_msize（MSVC）/malloc_usable_size（glibc）不可移植且返回实际块大小（可能大于请求）
  • 铁律：分配时记录 cap，所有访问前校验 offset < cap
  • 堆越界会破坏分配器元数据 → 延迟崩溃（11.5）

封装模式

安全 free 宏：

#define SAFEFREE(p) do { free(p); (p) = NULL; } while (0)

int *p = malloc(sizeof(int));
/* ... */
SAFEFREE(p);

安全 alloc 宏：

#define SAFE_ALLOC(p, type, n) \
    do { \
        (p) = malloc((n) * sizeof(type)); \
        if (!(p)) { \
            fprintf(stderr, "OOM at %s:%d\n", __FILE__, __LINE__); \
            exit(1); \
        } \
    } while (0)

但工业代码更倾向用函数封装 + 错误码返回，而非宏。

所有权明确化

/* 借用：调用方拥有 */
void process(const struct obj *o) {
    /* 只读使用，不 free */
    printf("%u\n", o->seq);
}

/* 转移：被调方拥有，负责 free */
void consume(struct obj *o) {
    /* 用完后 free */
    free(o);
}

/* 制造：调用方获得所有权 */
struct obj *create(void) {
    struct obj *o = malloc(sizeof *o);
    if (!o) return NULL;
    /* 初始化 */
    return o;   /* 调用方负责 free */
}
  • C 没有所有权标注（C++ 有 unique_ptr）
  • 靠函数命名和注释表达所有权
  • create/make/alloc → 调用方拥有
  • consume/destroy/free → 被调方释放
  • process/print/get → 借用

内存池模式

/* 简易内存池 */
struct pool {
    struct obj *entries;
    size_t cap, used;
};

int pool_init(struct pool *p, size_t cap) {
    p->entries = calloc(cap, sizeof(struct obj));
    if (!p->entries) return -1;
    p->cap = cap;
    p->used = 0;
    return 0;
}

struct obj *pool_alloc(struct pool *p) {
    if (p->used >= p->cap) return NULL;
    return &p->entries[p->used++];   /* 不调 malloc */
}

void pool_free_all(struct pool *p) {
    free(p->entries);   /* 一次性释放 */
    p->entries = NULL;
    p->cap = p->used = 0;
}
  • 预分配固定块，运行时不 malloc
  • 一次性释放，无碎片
  • DPDK rte_mempool 是此模式的工业实现

RAII 风格（C 模拟）

C 没有 RAII，但可以用 __attribute__((cleanup))（GCC/Clang）模拟：

void cleanup_free(void **p) { free(*p); *p = NULL; }

void f(void) {
    __attribute__((cleanup(cleanup_free))) char *buf = malloc(1024);
    if (!buf) return;
    /* ... */
    /* 函数结束时自动 free(buf) */
}
  • 离开作用域自动调用 cleanup 函数
  • 异常路径也能释放
  • 是 C 代码的"半 RAII"

HFT 关联

  • DPDK mempool 生命周期：启动 rte_pktmbuf_pool_create，运行 rte_pktmbuf_alloc/free，退出 rte_mempool_free
  • goto cleanup 模式：HFT 代码大量使用，确保异常路径释放资源
  • 长度记录：HFT 缓冲必须显式 len/cap，禁止越界
  • 所有权约定：rte_pktmbuf_free(m) 明确释放语义，调用后 m 失效
  • 零 malloc 原则：热路径完全不调 malloc，所有内存预分配

实操：goto cleanup 模式

int process_request(const uint8_t *req, size_t req_len) {
    struct hdr *h = NULL;
    uint8_t *payload = NULL;
    int ret = -1;

    h = malloc(sizeof *h);
    if (!h) goto out;
    if (parse_hdr(h, req, req_len) < 0) goto out;

    payload = malloc(h->payload_len);
    if (!payload) goto out;
    if (read_payload(payload, h->payload_len) < 0) goto out;

    ret = 0;
out:
    free(payload);
    free(h);
    return ret;
}

所有路径都经过 out 标签统一释放，无泄漏。

实操：长度记录防越界

#define MAX_PKT 65536

int parse(const uint8_t *buf, size_t buf_len) {
    if (buf_len < 4) return -1;
    uint32_t field = ntohl(*(uint32_t *)buf);

    size_t needed = 4 + field;   /* field 是子段长度 */
    if (needed > buf_len) return -1;   /* 防越界 */
    if (needed > MAX_PKT) return -1;   /* 防整数溢出放大 */

    /* 安全访问 buf[4..needed] */
    return 0;
}

实操：内存池

struct order_pool {
    struct order *entries;
    size_t cap, used;
};

int pool_init(struct order_pool *p, size_t cap) {
    p->entries = calloc(cap, sizeof(struct order));
    if (!p->entries) return -1;
    p->cap = cap;
    p->used = 0;
    return 0;
}

struct order *pool_alloc(struct order_pool *p) {
    return (p->used < p->cap) ? &p->entries[p->used++] : NULL;
}

11.5

常见错误

本节讲什么

动态内存的四大故障——内存泄漏、悬垂指针、双重释放、堆越界——是 HFT/网关线上崩溃的主因。它们都是 UB，表现各异：泄漏导致 OOM 被杀，悬垂导致静默踩踏，双重释放立即 SIGABRT，堆越界延迟崩溃。本节剖析每种错误的成因、症状、检测工具、根治方法。

要点

1. 内存泄漏 Memory Leak

成因：malloc 后未 free，或指针丢失导致无法 free。

/* 泄漏 1：忘记 free */
void f(void) {
    char *buf = malloc(1024);
    /* ... 用完 ... */
    /* 忘记 free(buf) —— 泄漏 1024 字节 */
}

/* 泄漏 2：指针被覆盖 */
void f(void) {
    char *p = malloc(100);
    p = malloc(200);   /* 原 100 字节地址丢失，泄漏 */
    free(p);           /* 只释放了 200 字节块 */
}

/* 泄漏 3：异常路径漏 free */
int f(void) {
    char *buf = malloc(1024);
    if (step1() < 0) return -1;   /* 漏 free(buf) */
    free(buf);
    return 0;
}

症状：

  • 进程 RSS 持续增长
  • 长跑进程最终 OOM 被 kill
  • 短期可能无明显症状

检测：

valgrind --leak-check=full ./prog
# 或
ASAN_OPTIONS=detect_leaks=1 ./prog_asan

根治：

  • 每条 malloc 配对 free
  • 异常路径用 goto cleanup
  • 静态分析：clang-tidy、cppcheck

2. 悬垂指针 Dangling Pointer

成因：free 后仍通过原指针访问。

int *p = malloc(sizeof(int));
*p = 42;
free(p);
*p = 100;   /* UB：已释放 */
int x = *p; /* UB：读取已释放内存 */

症状：

  • 立即崩溃（若页已归还内核）—— 少见
  • 静默踩踏（若内存被复用）—— 更危险
  • 数据随机错乱，难复现

检测：

# ASan：use-after-free
ASAN_OPTIONS=detect_leaks=1 ./prog_asan
# ==12345==ERROR: AddressSanitizer: heap-use-after-free

# valgrind
valgrind ./prog
# Invalid write of size 4

根治：

free(p);
p = NULL;   /* 铁律：free 后置 NULL */

/* 后续误用时立即 SIGSEGV，而非静默踩踏 */
*p = 100;   /* NULL 解引用，SIGSEGV */

3. 双重释放 Double Free

成因：同一地址 free 两次。

int *p = malloc(sizeof(int));
free(p);
free(p);   /* UB：双重释放 */

症状：

  • glibc 检测到 double free or corruption → SIGABRT
  • 其他实现可能静默破坏 free list → 后续随机崩溃
  • 是安全漏洞（CVE）的常见根源

检测：

ASan: attempting double-free
valgrind: Invalid free

根治：

/* 模式 1：判 NULL */
if (p) {
    free(p);
    p = NULL;
}

/* 模式 2：SAFEREE 宏 */
#define SAFEREE(p) do { free(p); (p) = NULL; } while (0)

free(NULL) 是安全空操作，所以置 NULL 后再 free 也无碍。

4. 堆越界 Heap Out-of-Bounds

成因：读写超过 malloc 请求的大小。

int *arr = malloc(10 * sizeof(int));
arr[10] = 42;    /* UB：越界写 */
arr[15] = 100;   /* UB：越界写，可能破坏元数据 */
int x = arr[20]; /* UB：越界读 */

症状：

  • 延迟崩溃：越界写覆盖 malloc 头部元数据，下次 free/malloc 时崩溃
  • 数据错乱：越界写到相邻块，改了别人的数据
  • 静默：若越界落在 padding 区域，可能无症状
  • 是 Heartbleed（CVE-2014-0160）的根因

检测：

# ASan：堆越界
ASAN_OPTIONS=detect_leaks=1 ./prog_asan
# ==12345==ERROR: AddressSanitizer: heap-buffer-overflow

# valgrind
valgrind ./prog
# Invalid write of size 4

根治：

size_t cap = 10;
int *arr = malloc(cap * sizeof(int));
if (!arr) return;

/* 每次访问前校验 */
for (int i = 0; i < cap; i++) {   /* i < cap，非 i <= cap */
    arr[i] = i;
}

/* 或用带边界检查的抽象 */
typedef struct { int *data; size_t cap, size; } vec;
int vec_set(vec *v, size_t i, int x) {
    if (i >= v->cap) return -1;   /* 边界检查 */
    v->data[i] = x;
    return 0;
}

5. 整数溢出导致的小块分配

成因：n * sizeof(T) 溢出，malloc 分配远小于预期。

size_t n = 0x100000001;   /* 假设 32 位 size_t */
int *p = malloc(n * sizeof(int));   /* 溢出：n * 4 = 4，实际只分 4 字节 */
p[0] = 1;   /* 似乎正常 */
p[100] = 2; /* 越界，UB */

根治：

/* 用 calloc：内置溢出检测 */
int *p = calloc(n, sizeof(int));
if (!p) return;

/* 或手动检测 */
if (n > SIZE_MAX / sizeof(int)) return NULL;
int *p = malloc(n * sizeof(int));

6. use-after-scope

成因：返回栈地址或闭包捕获栈引用。

int *f(void) {
    int x = 42;
    return &x;   /* UB：返回栈地址，函数返回后栈帧失效 */
}

int *p = f();
*p;   /* UB：访问已失效的栈内存 */

根治：

  • 栈对象只在本函数内使用
  • 需返回对象用堆或输出参数

C vs Rust：四大故障的防御对比

C 的四大堆故障全部属于执行环境问题——翻译环境语法合法，运行时才爆发。Rust 把内存生命周期检查搬到编译期（翻译环境），从根源杜绝：

故障 C（执行环境爆炸） Safe Rust（翻译环境拦截）
内存泄漏 malloc 忘 free，运行 OOM 值有所有权，离开作用域自动 Drop（等价自动 free）
悬垂指针 / UAF free(p); *p=42; 编译合法，运行 UB drop(s); 后 s 不可用，编译报 borrow of moved value
双重释放 free(p); free(p); 运行 SIGABRT 所有权 move 后原变量不可用，第二次 drop 编译报错
堆越界 arr[10] 编译不检查，运行踩踏 编译期索引检查（arr[i] 运行时 panic）或 get(i) 返回 Option

use-after-free 在 Safe Rust 中写不出来：

fn main() {
    let mut s = String::from("hello");
    let r = &s;           // 借用 s
    drop(s);              // ❌ 编译错误：s 被 r 借用，不能 move/drop
    println!("{}", r);
}

fn main() {
    let s = String::from("hello");
    drop(s);              // s 所有权交出，值已销毁
    println!("{}", s);    // ❌ 编译错误：borrow of moved value `s`
}

C 的 free(p) 只是把内存还给分配器，p 这个指针变量还在——后续 *p 编译器不管。Rust 的 drop(s) 是语义层面的所有权终结：编译器知道 s 已经死了，后续任何访问都是编译错误。

唯一例外：unsafe 块里手动操作裸指针 *mut T，跟 C 一样不受保护，交给程序员自己保证。

核心差异：C 靠运行时工具（ASan/valgrind）发现内存 bug；Rust 在编译期用借用检查器从根源消灭它们。代价是 Rust 学习曲线陡峭、泛型生命周期标注复杂。

HFT 关联

  • DPDK mempool：固定块大小，无越界；alloc/free 配对，无泄漏
  • 零 malloc 原则：热路径不调 malloc，从根源避免四大故障
  • ASan CI：DPDK 单元测试在 ASan 下运行
  • 线上监控：RSS 监控、/proc/<pid>/status 的 VmRSS
  • CVE 教训：Heartbleed 是堆越界读，Morris 蠕虫是栈溢出——HFT 网关面向互联网，安全至关重要

内存分配实例

本节讲什么

本节是 ch11 的综合实践章：内存碎片（外部/内部）、对齐分配、多线程 malloc 的锁竞争、DPDK mempool 与标准堆的对照、链表释放模板、调试工具链、用户态与内核的内存 API 对照。通过这些实例，把前 5 节的概念落地为可操作的工程技能。

要点

内存碎片

类型 说明 示例
外部碎片 空闲块离散，无法拼成大块 1 MB 空闲但分散在 100 个 10 KB 块里，无法分配 1 MB
内部碎片 对齐向上取整浪费 请求 13 字节，malloc 返回 16 字节块，浪费 3 字节

外部碎片：

初始：|####|####|####|####|####|####|####|####|
反复 malloc/free 后：
     |    |####|    |####|    |####|    |####|
     ← 空闲 16 字节，但分散在 4 个 4 字节块里 →
     malloc(16) 失败：无连续 16 字节块

对策：

  • 预分配内存池，统一块大小
  • DPDK rte_mempool：固定块大小，零外部碎片
  • jemalloc/tcmalloc：按 size class 分桶，减少外部碎片
  • 避免频繁小块 malloc

对齐分配

#include <stdlib.h>

/* C11 aligned_alloc */
void *p = aligned_alloc(64, 1024);   /* 64 字节对齐，1024 字节 */
free(p);

/* POSIX posix_memalign */
void *p;
int rc = posix_memalign(&p, 64, 1024);
if (rc == 0) {
    /* p 是 64 字节对齐的 1024 字节 */
    free(p);
}

/* 旧式 memalign（不推荐，不可移植） */
void *p = memalign(64, 1024);
free(p);

用途：

  • cache 行对齐（64 字节）：避免 false sharing
  • DMA 对齐：网卡 DMA 要求缓冲对齐
  • SIMD 对齐：AVX-512 要求 64 字节对齐
  • 大页：2 MB 对齐的 mmap

DPDK 对齐分配：

/* DPDK rte_malloc 支持对齐参数 */
void *p = rte_malloc_socket("order", size, 64, numa_node);
rte_free(p);

多线程 malloc 的锁竞争

glibc ptmalloc2 用多 arena减少锁竞争，但仍有全局锁：

/* 线程 A */
void *p = malloc(100);   /* 可能阻塞等 arena 锁 */

/* 线程 B 同时 */
void *q = malloc(100);   /* 等 A 释放锁 */

性能影响：

  • 8 线程并发 malloc，吞吐约单线程的 30-50%
  • 延迟抖动：锁等待时间不确定，HFT 不可接受

对策：

方案 机制 适用
tcmalloc/jemalloc thread-local cache 通用多线程
mimalloc per-thread heap 现代多核
线程本地池 预分配 per-thread HFT
DPDK mempool per-lcore cache，无锁 HFT 极致

DPDK mempool 的无锁设计：

struct rte_mempool *pool = rte_pktmbuf_pool_create(
    "mbuf_pool", 8192, 256, 0,
    RTE_MBUF_DEFAULT_BUF_SIZE, rte_socket_id()
);

/* 每 lcore 有独立 cache（256 个 mbuf） */
/* alloc/free 操作 cache，无锁 */
struct rte_mbuf *m = rte_pktmbuf_alloc(pool);   /* ~10 ns，无锁 */
rte_pktmbuf_free(m);                             /* ~10 ns，无锁 */

cache 耗尽时才从共享池补充，此时有锁但频率低。

简易链表（防泄漏模板）

typedef struct node {
    uint64_t id;
    struct node *next;
} Node;

Node *head = NULL;

/* 插入若干节点 */
for (int i = 0; i < 1000; i++) {
    Node *n = malloc(sizeof *n);
    if (!n) goto cleanup;
    n->id = i;
    n->next = head;
    head = n;
}

/* 使用链表 */
for (Node *p = head; p; p = p->next) {
    process(p->id);
}

/* 释放整链 */
cleanup:
while (head) {
    Node *next = head->next;   /* 先保存 next */
    free(head);
    head = next;
}
head = NULL;

关键点：

  • 释放前先保存 next——free 后 head->next 是 UAF
  • 用 while 循环而非 for，因为 free 后不能访问 head->next
  • 释放后 head = NULL

用户态 vs 内核态内存 API

用户态 内核 用途
malloc/free kmalloc/kfree 小块，物理连续
calloc kzalloc 清零小块
posix_memalign kmalloc + GFP_DMA 对齐分配
mmap vmalloc 大块，虚拟连续
— __get_free_page 整页
— kmem_cache slab 分配器，固定大小
hugepage mmap hugetlbfs 大页，减少 TLB miss

内核 slab 分配器：

  • 类似用户态 mempool
  • 固定大小对象（如 task_struct、file）
  • 预分配 + 复用，无碎片
  • /proc/slabinfo 可查看

HFT 关联

  • DPDK mempool：固定块大小，无碎片，无锁，NUMA 感知
  • hugepage：DPDK 用 2 MB 大页 mmap，减少 TLB miss
  • NUMA 感知：每 NUMA 节点独立 mempool，避免跨节点访问（延迟差 2-3 倍）
  • 零 malloc 原则：热路径完全不调 malloc，所有内存启动时预分配
  • ASan CI：所有 DPDK 单元测试在 ASan 下运行

#include <rte_mempool.h>
#include <rte_cycles.h>

struct rte_mempool *pool = /* 创建 */;

uint64_t start = rte_rdtsc();

printf("glibc: %f ns/op\n", (double)(end - start) / 1000000 / 3.0);
/* 约 50-200 ns/op */

/* cache 行对齐，避免 false sharing */
struct counter {
    uint64_t value;
} __attribute__((aligned(64)));

struct counter counters[8];   /* 每 CPU 一个，64 字节对齐 */

void inc(int cpu) {
    counters[cpu].value++;   /* 无 false sharing */
}

实操：链表释放

Node *head = /* 已填充的链表 */;

/* 正确：先保存 next */
while (head) {
    Node *next = head->next;
    free(head);
    head = next;
}

/* 错误：free 后访问 head->next（UAF） */
for (Node *p = head; p; p = p->next) {
    free(p);   /* p->next 是 UAF */
}

章节自测

题目 1： 以下代码有什么问题？

int *p = malloc(10 * sizeof(int));
if (p == NULL) exit(1);
// 使用 p...
// 没有 free(p)
参考答案

内存泄漏。malloc 分配的内存必须用 free 释放，否则程序运行期间这块内存不会被回收。虽然程序退出时操作系统会回收所有内存，但长时间运行的程序（如服务器）中泄漏会累积导致 OOM。正确做法：使用完后 free(p); p = NULL;。
