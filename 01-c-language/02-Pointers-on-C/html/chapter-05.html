5.1

操作符

本节讲什么

C 全部运算符概览:算术、移位、位运算、关系、逻辑、一元、三元、赋值、逗号。这些是 DPDK mbuf 标志位、寄存器读写、报文解析的日常工具。本节给全景,5.4 系列再深挖求值顺序与 UB。HFT 里大半"数值错乱"事故的根因在这一章。

要点

算术 + - * / %

运算 规则 例子
整数 / 截断小数,向 0 取整 7/3=2,-7/3=-2
% 仅整型;符号随被除数 7%3=1,-7%3=-1
无符号溢出 模 2^N 环绕(定义良好) uint32_t 计数到 0xFFFFFFFF+1=0
有符号溢出 UB INT_MAX+1 行为未定义 
uint32_t seq = 0xFFFFFFFF;
seq++;                 /* 0, 定义良好 —— 序列号环绕合法 */
int32_t  v = INT_MAX;
v++;                   /* UB, 编译器可假定不溢出做激进优化 */

HFT 铁律:价格用 int64_t 定点(如 1e-7 精度),序列号/时间戳用 uint64_t。避免 double 精度分歧,避免有符号溢出 UB。

移位 << >>

运算 规则 陷阱
a << n 低位补 0,等价 ×2^n(正数/无符号安全) 左移负数是 UB;有符号溢出 UB
a >> n(无符号) 逻辑右移,补 0 安全
a >> n(有符号负数) 结果实现定义(实践中 x86/ARM 多为算术右移补符号位,标准不保证) 可移植性差,不要对负数做 >>
位数 ≥ 提升后左操作数位宽 UB 1 << 32(int 32 位)是 UB;注意是提升后类型,不是声明类型
位数 < 0 UB 移位量必须 ≥ 0 且 < 提升后位宽

两个易错点(标准原文 C11 §6.5.7)

(1) "位宽"看的是整型提升后的类型,不是声明类型。 uint8_t b; 做 b << 16 合法——b 提升为 int(32 位),16 < 32,不 UB。同理 b << 1 也合法,但结果类型是 int 不是 uint8_t,赋回窄类型会静默截断:

uint8_t b = 0x80;
uint8_t r = b << 1;    /* 0x80<<1 = 0x100, 截断回 uint8_t = 0x00, 静默丢数据 */

这是比符号位 UB 更常见的 bug——-Wconversion 能抓到这种隐式截断。

(2) 有符号右移的"实现定义"措辞要精确。 标准原文只说"结果实现定义",没规定必须算术右移——某编译器给逻辑右移也合规。x86 编 SAR(算术),无符号编 SHR(逻辑),都是 1 周期;但编译器不敢跨平台假设它是算术,所以你写 int x = -1; x >> 1; 在 x86 上得 -1,换平台可能得超大正数。

uint8_t b = pkt[0];
uint16_t len = (pkt[1] << 8) | pkt[2];   /* 大端读字段, 注意整型提升 */
uint32_t mask = 1u << 5;                  /* 第 5 位掩码, 用 1u 避免 UB */
uint32_t high = val >> 24;                /* 取最高字节(无符号安全) */

⚠️ 1 << 31(int 32 位)是 UB(1×2^31 在 int 中不可表示, C11 §6.5.7p4);要 1u << 31 或 1ULL << 63。pkt[1] << 8 中 pkt[1] 最大 255, 255<<8=65280 在 32 位 int 里安全(不碰符号位)——这一行本身不 UB, 注释提醒的是"运算发生在 int 上"这个事实。

HFT 视角:移位本身几乎零成本(1u << k 掩码常被编译器折叠成立即数, 热路径零指令);UB 真正可怕的不是慢, 而是编译器基于"有符号移位不溢出"的假设删掉你写的溢出检查——移位用 uintXX_t 不只是可移植, 是防编译器激进优化。

位运算 ~ & | ^

符 用途 例子
& 提取/过滤位 flags & PKT_ORDER
\| 置位 flags \|= PKT_ERR
^ 翻转位 flags ^= PKT_VLAN
~ 掩码取反 flags &= ~PKT_VLAN(清位) 
flags |=  PKT_ERR;          /* 置位 */
flags &= ~PKT_VLAN;         /* 清位 */
flags ^= PKT_DUP;           /* 翻转 */
if (flags & PKT_ORDER) {    /* 测试位 —— 注意是 & 不是 && */
    /* ... */
}

⚠️ if (flags & MASK) ≠ if (flags && MASK)。前者位与,得到掩码内的值;后者逻辑与,只给 0/1。测试位必须用 &。

关系与判等 < <= > >= == !=

  • 结果类型 int,值为 1 或 0
  • = vs ==:if (flag = 1) 恒真陷阱(4.2)
  • 比较无符号与有符号负数 → 提升为无符号,负数变超大正数(5.4.2)

逻辑 && ||(短路)

if (mbuf != NULL && mbuf->len > 0)   /* mbuf==NULL 时不解引用, 安全 */
    process(mbuf);
  • A && B:A 假则不求 B(短路)
  • A || B:A 真则不求 B
  • 短路是"安全空指针"模式的语义基础,不能重排序

一元 & * ! ~ sizeof ++ -- + -

符 语义
& 取址(左值 → 指针),ch06
* 解引用(指针 → 左值),ch06
! 逻辑非,!x 等价 x==0
~ 按位取反
sizeof 编译期字节数;数组传参后退化, sizeof(p) 是指针宽
++ -- 自增自减,前置先变后用,后置先用后变
+ - 一元正负 
int arr[10];
sizeof(arr);          /* 40, 数组大小 */
void f(int a[10]){ sizeof(a); }   /* 8, 退化成指针 */

int a = 5, b;
b = a++;              /* b=5, a=6(后置: 先用后变) */
b = ++a;              /* a=6, b=6(前置: 先变后用) */

同一表达式多次 ++/-- 同一变量 → UB(序列点规则,5.4.3):a = a++ + ++a;

三元 ?:

uint64_t price = (bid > 0) ? bid : ask;   /* 二选一 */
const char *s = (err == 0) ? "ok" : "err";
  • 条件非 0 取第二操作数,否则取第三
  • 短路:只求值被选中的分支
  • 三元是表达式,有值,可嵌套但可读性差

复合赋值 += -= *= /= %= <<= >>= &= ^= |=

a += b;     /* 等价 a = a + b, 但 a 只求值一次 */
a <<= 2;    /* 等价 a = a << 2 */
  • 复合赋值中左操作数只求值一次:对复杂左值(a[compute()] += b)避免重复计算
  • 与 a = a + b 在 a 是简单变量时等价;复杂左值时复合赋值更高效

逗号 ,

for (i = 0, j = n - 1; i < j; i++, j--)   /* 多变量循环 */
    swap(&a[i], &a[j]);

int x = (a, b);   /* 逗号表达式: 求值 a 丢弃, 取 b —— 几乎不用, 可读性差 */
  • 逗号运算符:左到右求值,结果取最右
  • 主要用途:for 循环多变量;其他场景少用

汇编证据:移位与位运算

uint32_t shift_demo(uint32_t a){
    return (a << 4) | (a >> 28);   /* 循环左移 4 位 */
}

        mov     eax, edi
        rol     eax, 4        ; x86 有 rol 指令, 直接循环移位
        ret
  • 移位常被编译器识别为更优指令(rol/ror 循环移位,shld/shrd 双精度移位)
  • *2/*4/*8 编译为 shl 而非 imul,更快

报文字段提取(大端/小端)

/* 网络字节序(大端)读 16 位字段 */
uint16_t len = (pkt[0] << 8) | pkt[1];
/* 读 32 位 */
uint32_t seq = ((uint32_t)pkt[0] << 24) |
               ((uint32_t)pkt[1] << 16) |
               ((uint32_t)pkt[2] <<  8) |
               ((uint32_t)pkt[3]);
  • 注意整型提升:pkt[0] << 8 中 pkt[0] 是 uint8_t,先提升为 int 再移位

代码自测

题目 1： 以下代码输出什么？为什么？

int x = 1, y = 2;
printf("%d\n", x << y);
printf("%d\n", x && y);
printf("%d\n", x & y);
参考答案

输出 4、1、0。x << y 是左移：1 左移 2 位 = 4。x && y 是逻辑与：两个非零值为真，结果 1。x & y 是按位与：01 & 10 = 00 = 0。注意区分逻辑运算符和按位运算符。

题目 2： 以下哪几句是 UB？为什么？

uint8_t b = 0x80;
uint8_t r1 = b << 1;        /* A */
int     r2 = b << 25;       /* B */
uint32_t r3 = 1u << 31;    /* C */
int     r4 = 1 << 31;      /* D */
参考答案
  • A 不 UB，但会截断丢数据：b 提升为 int，0x80<<1 = 0x100 = 256，结果类型是 int，赋回 uint8_t 静默截断为 0x00。-Wconversion 能抓。
  • B 是 UB：b 提升为 int，0x80<<25 = 2^32，在 32 位 int 中不可表示（碰符号位），C11 §6.5.7p4 明确未定义。即使 b 声明成 uint8_t 也没用——提升后是 int。
  • C 安全：1u 是 unsigned int，2^31 在 unsigned int 中可表示。
  • D 是 UB：1 是 int，1×2^31 在 int 中不可表示，符号位溢出未定义。 关键：移位的"位宽"和"结果类型"都看提升后的左操作数，不是声明类型。窄类型（uint8_t/uint16_t）做移位会先提升为 int，既可能 UB（碰符号位），也可能截断（赋回窄类型）。
5.2

布尔值

本节讲什么

C 用整型 0/1 表示真假,没有原生布尔类型(C99 才引入 _Bool)。关系、逻辑运算结果是 int 型的 1 或 0,而 if/while 条件接受"非 0 即真"。这种"整型当布尔用"的设计是 C 简洁的根源,也是 if (x = 1) 这类陷阱的温床。本节讲布尔语义、惯用写法、典型陷阱。

要点

真假规则

  • 0 → 假;非 0 → 真(不限于 1,任何非 0 整数、非空指针、非 0 浮点都为真)
  • 关系/逻辑表达式结果类型是 int,值为 1(真)或 0(假) —— 不是操作数的原值
  • NULL、0.0、'\0'、0 都是"假";其他都是"真"
int a = 5;
if (a)        /* a 非 0, 真 */
if (a == 5)   /* 表达式结果 1, 真 */
int r = (a > 3);   /* r = 1, 不是 a 的值 */

C99 的 _Bool 与 stdbool.h

#include <stdbool.h>      /* C99 */
bool ok = true;           /* _Bool, 真正的布尔类型 */
bool ready = false;
if (!ready) return;
  • _Bool 是 C99 引入的真布尔类型,只有 0/1 两个值
  • stdbool.h 提供 bool/true/false 宏(C++ 兼容)
  • 赋值时自动归一化:bool b = 5; → b = 1(任何非 0 变 1)
  • C23 把 bool/true/false 提升为关键字,不再需要 stdbool.h

惯用写法(HFT/驱动风格)

if (mbuf)           /* 指针非 NULL, 等价 mbuf != NULL */
if (!err)           /* err == 0 */
if (cnt)            /* cnt != 0 */
if (flags & X)      /* 位测试, 注意是 & 不是 && */
if (!*p)            /* *p == 0, 字符串结尾 */
  • 不必写 == 1 或 != 0;指针、整数均可直接作条件
  • 布尔语义的函数返回值用 bool 更清晰:bool is_valid(struct x *)

陷阱集

错误写法 实际语义 后果
if (x = 1) 赋值 1,条件恒真 意图 == 却写成 =,死循环/逻辑错
if (flags && MASK) 逻辑与,flags 非零则取 MASK 真值 测试位要用 &,不是 &&
if (a > -1),a 为 unsigned a 提升为 unsigned,-1 变超大正数 恒真,见 5.4.1
if (p = malloc()) 赋值,判断指针非空 合法但易误读,加括号注释
if (strlen(s)) 长度非零为真 合法但 strlen(s) > 0 更清晰

! 运算符

if (!ptr)        /* ptr == NULL */
if (!err)        /* err == 0 */
int zero = !5;   /* 0, 逻辑非把非 0 变 0, 0 变 1 */
  • !x 等价 x == 0,结果是 int 的 1 或 0
  • 双重否定 !!x 把任意非 0 归一化为 1:!!5 == 1,常用于"转布尔"

短路与布尔

if (p && p->len > 0)    /* p 为 NULL 时短路, 不解引用 */
  • && 和 || 短路是布尔语义的安全基础,见 5.1
  • 短路保证:左侧假/真时右侧不求值,可安全检查空指针

与 HFT/DPDK

状态标志的布尔化

bool is_trading_hours = (now >= open_ns && now < close_ns);
bool can_send = (ready && !paused && buffer_avail);
if (can_send) enqueue(order);
  • 多重条件用 bool 变量名承载语义,比一长串 && 更可读
  • C99 _Bool 占 1 字节(至少),节省结构体空间

位标志 vs 布尔数组

/* 位标志: 紧凑, 8 个状态 1 字节 */
uint8_t flags = 0;
flags |= RUNNING;        /* 置位 */
if (flags & RUNNING) ... /* 测试 */

/* 布尔数组: 可读, 但占空间 */
bool states[8];
states[RUNNING] = true;
if (states[RUNNING]) ...
  • HFT 协议头、设备寄存器用位标志(紧凑、对齐硬件)
  • 应用层状态多用 bool 数组或枚举(可读、可调试)

比较的显式化

/* 反例: 隐式布尔, 含义不清 */
if (strcmp(a, b))   /* 不等? 但读起来像"等" */

/* 正解: 显式 */
if (strcmp(a, b) != 0)   /* 明确: 不等 */
if (strcmp(a, b) == 0)   /* 明确: 相等 */
  • strcmp 返回 0 表示相等,直接 if (strcmp(...)) 易误读
  • 显式 == 0 / != 0 让意图清晰

常见误区

误区 真相
关系运算结果是操作数原值 不,是 int 的 1 或 0
if (x = 1) 和 if (x == 1) 等价 前者赋值恒真,后者判等
if (flags && MASK) 测试位 错,逻辑与;要用 &
C 没有布尔类型 C99 起有 _Bool/bool
bool b = 5; 后 b == 5 不,归一化为 1
if (strlen(s)) 清晰 合法但 > 0 更明确

5.3

左值和右值

本节讲什么

左值(lvalue) 是"有对象标识、可取址、命名了内存中某块存储"的表达式;右值(rvalue) 是"临时计算结果、无持久存储、常出现在赋值右侧"的表达式。这个区分决定了哪些表达式能被赋值、能取址、能做 ++ 操作数 —— 也解释了为什么 3 = x 非法、&(a+b) 非法、42++ 非法。本节讲 lvalue/rvalue 定义(含标准条款与底层视角)、可修改性、与指针/赋值/++/& 的关系,以及副作用与序列点如何产生 UB。

本节是 lvalue/rvalue 的唯一定义处。ch03 数据章、ch06 指针、ch08 数组、ch10 结构体凡涉及"这表达式是不是左值"都回这里。

核心定义

左值(lvalue) = 一个引用了内存中某个对象的表达式——也就是说,它有地址。

int x = 42;     // x 是左值——有存储位置
x = 10;         // ✅ 左值能放赋值左边

int *p = &x;    // & 要求操作数是左值——取地址必须有地方可指

42 = 10;        // ❌ 42 是右值(字面量),没地址,不能赋值
int y = x + 1;  // (x+1) 是右值——结果在寄存器里,没固定地址

名字来源:left value——能出现在赋值号左边的表达式。但这只是记忆法,不是定义——const 变量是左值但不能放赋值左边。更准确的理解是 "locator value":定位到一块内存。

标准定义(C11 §6.3.2.1)

An lvalue is an expression (with an object type or incomplete type other than void) that potentially identifies an object.

关键词 "potentially":

  • *p 是左值,即使 p 是野指针——标准说"potentially",不要求实际指向有效对象
  • 左值"转换为右值"(读取其值)时才要求对象真的存在且类型有效,否则 UB

左值 vs 右值

维度 左值(lvalue) 右值(rvalue)
例子 变量 x、*p、arr[i]、s.field 字面量 42、a+b、函数返回值
赋值左侧 合法 x = 1 非法 3 = x
取址 合法 &x 非法 &(a+b)
++/-- 操作数 合法 x++ 非法 (a+b)++
本质 命名了内存中的对象(可定位) 临时计算结果,无持久存储
  • lvalue = "locator value",指代一块内存(可定位)
  • rvalue = "read value",读取的值(临时)

哪些是左值

*p ✅ 解引用得到对象,指向的内存有了名字
arr[i] ✅ 等价 *(arr+i),数组元素有地址
s.field ✅ 结构体成员,可赋值
p->field ✅ 等价 (*p).field
arr(数组名) ✅(不可修改) 数组本身是左值,但不能整体赋值
s.bitfield ✅(不可取址) 位域是左值但 & 非法
42(字面量) ❌ 常量,无存储
a + b ❌ 算术结果,临时,在寄存器
a == b ❌ 比较结果,临时 int

关键: &x 不是左值——& 产生一个"地址值"(rvalue),你不能再对它取地址 &(&x)。

可修改 vs 不可修改左值

C 标准把 lvalue 细分为可修改左值(modifiable lvalue)和不可修改左值;只有可修改左值能被赋值、做 ++/-- 操作数。

const int ci = 5;
int arr[3];
struct { int f : 4; } s;

ci = 10;         // ❌ ci 是左值(有地址),但 const 不可修改
arr = NULL;      // ❌ arr 是左值(有地址),但数组不可整体赋值
arr[0] = 1;      // ✅ arr[0] 是可修改左值
s.f = 7;         // ✅ 位域是左值,可赋值
&s.f;            // ❌ 位域不可取址(地址最小粒度是字节)
左值 可修改? 原因
int x ✅ 普通变量
const int ci ❌ const 限定
int arr[3](整体) ❌ 数组不可整体赋值
arr[i] ✅ 元素是可修改左值
*p ✅ 解引用,目标可写
位域 s.f ❌(取址) 可赋值但不可取址
字符串字面量 "abc" ❌ .rodata 只读

左值规则——哪些操作要求左值

1. 赋值左边必须可修改左值

x = 10;           // ✅ x 是可修改左值
// (x + 1) = 10;  // ❌ (x+1) 不是左值
// 42 = 10;       // ❌ 42 不是左值

2. & 取地址——操作数必须左值

int x;
int *p = &x;          // ✅ x 是左值
// int *q = &(x + 1); // ❌ (x+1) 不是左值
// int *r = &42;      // ❌ 42 不是左值

3. ++ / --——操作数必须左值(要原地修改)

int i = 0;
i++;            // ✅ i 是左值
// (i + 1)++;   // ❌ (i+1) 不是左值

4. 三目运算符——两个分支都是左值,结果才是左值

int a, b;
(a > b ? a : b) = 10;   // ✅ 两边都是左值,整个表达式是左值
(a > b ? a : 0) = 10;   // ❌ 0 不是左值,整个表达式退化为右值

函数返回值与左值

int f(void){ return 42; }
int *g(void){ static int x; return &x; }

f() = 1;        /* 非法: f() 是右值 */
*g() = 1;       /* 合法: *g() 解引用返回的指针, 是左值 */
  • 函数返回非引用类型 → 右值,不能赋值
  • 函数返回指针 → 解引用后是左值,可赋值(C 没有引用,靠指针实现"返回可赋值对象")

底层视角

编译器把左值理解为"一个存储位置的描述":

  • 左值 = 编译器记录的"某块存储的地址"(可能需要运行时计算,如 arr[i] = base + i*4)
  • 右值 = 直接的数值,不需要地址计算
int arr[4];
int x = arr[2];   // 左值 arr[2] → 编译期算出 [rsp+8]
                   // 读值 → mov eax, [rsp+8]

int *p = arr;
int y = p[2];     // 左值 p[2] → 运行期 [rdi+8]
                   // 读值 → mov eax, [rdi+8]

所以左值本质上回答的是"这东西存在哪",右值回答的是"这东西值多少"。

与指针的关系

概念 左值角色

*p 解引用 结果是左值——p 指向的那块内存有了名字
*p = 10 赋值 *p 是左值,写入目标内存

               // 现在 x == 20

副作用(side effect)

副作用 = 求值过程中改变了环境状态:修改变量、写文件、改 volatile 对象等。

运算符 是否有副作用
= += 等 是(改左值)
++ -- 是(改左值)
*p = ... 是(通过指针改对象)

  • 无副作用的纯计算表达式会被编译器消除(死代码消除)
  • volatile 访问是有副作用的,编译器不能消除/合并 —— 见下方 HFT/DPDK

序列点与 UB(5.4.3 预告)

arr[i++] = i;        /* UB: i 被修改一次但读取一次, 顺序未定义 */
a = a++ + ++a;       /* UB: 两次修改, 无序列点隔开 */
printf("%d", a++ + a++);   /* UB */
  • 两个序列点之间,同一变量最多修改一次,且若修改则不能同时读取
  • 违反 → UB,编译器可任意处理(gcc/clang 结果常不同)
  • 详见 5.4.3

题目 1： 以下哪些是合法的左值？

表达式 左值？ 理由
A: x ✅ 变量，有地址
B: x + y ❌ 算术结果在寄存器
C: *p ✅ 解引用，指向 x 的内存
D: &x ❌ 取地址结果是"地址值"（指针右值），不是可定位的存储
E: arr[x] ✅ 数组元素，有地址

题目 2： 为什么 const int ci = 5; ci = 10; 编译报错？ci 不是左值吗？

参考答案

ci 是左值（它有地址，&ci 合法），但它是不可修改左值——const 限定符剥夺了可修改性。赋值号左边要求的是可修改左值（modifiable lvalue），不只是左值。

题目 3： *p++ 中 *p 和 p++ 分别是不是左值？

参考答案
  • *p 是左值（解引用 → 指向的内存）
  • p++ 的结果不是左值——p++ 是后缀自增，返回 p 增加前的旧地址值（rvalue）。但 p 本身是左值，p++ 修改了 p。
  • *p++ 整体等价于 *(p++)，先取 *p 的值，再 p++。*p++ 作为表达式是右值（取出的值）。
5.4

表达式求值

本节讲什么

表达式如何求值 —— 隐式转换、算术转换、优先级、结合性、副作用与序列点。这一节是 ch05 的核心,也是线上网关"逻辑错乱、数值溢出、死循环"的头号理论来源。三个小节分别讲隐式转换、算术转换、优先级与求值顺序。

要点

表达式的组成

表达式 = 运算符 + 操作数 + 求值规则。求值规则决定:

  1. 类型转换:操作数先转成共同类型(5.4.1 / 5.4.2)
  2. 结合顺序:优先级 + 结合性决定运算符如何配对(5.4.3)
  3. 求值顺序:操作数左右谁先求值(多数未指定!)、副作用何时生效(序列点)
  4. 溢出/UB:有符号溢出、序列点内多次修改 → 未定义行为

副作用与序列点(关键概念)

  • 副作用:求值过程中改变状态(=、++、--、函数调用写文件等)
  • 序列点(sequence point):程序执行的某些点,此前所有副作用已生效,此后尚未开始
  • ; 语句结尾
  • && || 左右操作数之间(短路保证)
  • ?: 第一与第二/三操作数之间
  • 逗号 , 左右操作数之间
  • 函数调用:参数求值完成、进入函数体前(C99 前);C11 改为"参数求值与函数体执行间有序列点"
  • 规则:两个序列点之间,同一对象最多修改一次,且若修改则不能在该区间内被读取(除计算新值)
  • 违反 → UB
arr[i++] = i;          /* UB: i 修改一次, 但读取一次, 顺序未定 */
a = a++ + ++a;         /* UB: 两次修改, 无序列点 */
printf("%d", a++ + a++);   /* UB */

常见 UB 速查

表达式 问题
a++ + a++ 序列点内两次修改 a
arr[i++] = i i 修改一次, 但读取顺序未定
a = a++ + ++a 两次修改
i = i++ 修改一次 + 赋值, UB
1 << 32(int 32 位) 移位 ≥ 位宽
INT_MAX + 1(signed) 有符号溢出
*(int *)0 空指针解引用

规范:单表达式内对同一变量最多一次修改,不依赖未指定求值顺序。复杂副作用拆成多语句。

求值顺序未指定的场景

int i = 1;
printf("%d %d\n", i, i++);    /* 求值顺序未指定, 输出可能是 "1 1" 或 "2 1" */

f(i, i++);                    /* 参数求值顺序未指定 */
a[i] + a[i++];                /* UB, 序列点问题 */
  • 函数参数求值顺序未指定(不是 UB,是未指定行为,结果任一合法)
  • 但若参数有副作用导致同一变量多次修改 → UB

与 HFT/DPDK

数值溢出的实战事故

/* 反例: 价格累加溢出 */
int32_t total = 0;
for (int i = 0; i < n; i++)
    total += prices[i];       /* 累加可能溢出 INT_MAX → UB */

/* 正解: 用 int64_t 或检查 */
int64_t total = 0;
for (int i = 0; i < n; i++) {
    if (total > INT64_MAX - prices[i]) {
        /* 溢出检查 */
        return -EOVERFLOW;
    }
    total += prices[i];
}
  • 有符号溢出是 UB,编译器可假定"不溢出"做激进优化 → 结果与预期差很远
  • HFT 价格累加用 int64_t 留足余量,或用 __int128 临时累加

序列号环绕

uint32_t seq = 0;
uint32_t next(void){ return ++seq; }   /* uint 溢出环绕, 定义良好 */

/* 比较序列号大小要考虑环绕 */
bool before(uint32_t a, uint32 b) {
    return (int32_t)(a - b) < 0;   /* 有符号差判断 */
}
  • TCP 序列号、报文序号常 uint32,会环绕;比较"先后"用有符号差
  • 无符号溢出是定义良好的环绕,不是 UB

移位 UB 的实战

/* 反例: 32 位 int 移 32 位 */
uint64_t mask = (1 << 32) - 1;    /* UB! 1 是 int, <<32 超出 */
/* 正解 */
uint64_t mask = (1ULL << 32) - 1;  /* 用 ULL 避免窄类型 */

/* 反例: 循环里移位变量 */
for (int s = 0; s <= 32; s++) {
    uint32_t v = 1u << s;          /* s==32 时 UB */
}
/* 正解: s < 32 或用 64 位 */
for (int s = 0; s < 32; s++) {
    uint32_t v = 1u << s;
}

5.4

.1 隐式类型转换

本节讲什么

编译器自动插入的类型转换:整型提升(integer promotion)、赋值转换、布尔转换。这些转换大多无害,但有几个是 HFT/驱动代码的经典 bug 源 —— 最典型的是"unsigned char 与 -1 比较"和"char 符号扩展"。本节讲转换规则、汇编证据、典型陷阱。

要点

整型提升(integer promotion)

规则:比 int 窄的整型(char/short/_Bool/枚举)在算术/逻辑运算前自动提升为 int(若 int 能容纳)或 unsigned int。

char a = 200;          /* 实现定义: signed char 时 a=-56, unsigned char 时 a=200 */
int  r = a + 1;        /* a 先提升为 int, 再加 */
原类型 提升为 符号处理
signed char int 符号扩展:0xFF → 0xFFFFFFFF(保持负值)
unsigned char int 零扩展:0xFF → 0x000000FF
signed short int 符号扩展
unsigned short int(若 int 能容纳) 零扩展
_Bool int 0/1

关键:char 的符号性是实现定义(见 3.1.1)。x86/ARM 默认 signed char,ARM 某些 DSP 默认 unsigned char。这导致同一份代码在不同平台行为不同。

汇编证据:符号扩展

int f(signed char c){ return c + 1; }       /* 符号扩展 */
int g(unsigned char c){ return c + 1; }     /* 零扩展 */

f:
        movsx   eax, dil      ; 符号扩展: 8 位 → 32 位, 高位补符号位
        add     eax, 1
        ret
g:
        movzx   eax, dil      ; 零扩展: 8 位 → 32 位, 高位补 0
        add     eax, 1
        ret
  • movsx(move sign-extend):符号扩展,signed char 提升
  • movzx(move zero-extend):零扩展,unsigned char 提升
  • 这是"为什么 char 符号性影响行为"的底层原因

赋值转换

uint8_t b = 0x123;     /* 截断: 0x123 → 0x23 */
int32_t i = 3.14;      /* 截断: 3.14 → 3 */
double d = 5;          /* 提升: 5 → 5.0 */
uint32_t u = -1;       /* 模转换: -1 → 0xFFFFFFFF */
  • 右侧值转为左侧类型:可能截断(宽→窄)、提升(窄→宽)、符号转换(signed↔unsigned)
  • 截断丢高位;unsigned 与 signed 互转用模 2^N
  • -Wconversion 警告可能丢信息的隐式转换

布尔转换

if (ptr) ...           /* 指针 → bool: 非空为真 */
if (count) ...         /* 整数 → bool: 非 0 为真 */
bool b = 3.14;         /* 浮点 → bool: 非 0 为真, b=1 */
int n = true;          /* bool → int: 0 或 1 */
  • 任何标量(整/浮/指针)在布尔上下文(if/while/&&/||/!)自动转 bool
  • 非 0 → 真(1),0 → 假(0)

经典陷阱:unsigned char 与 -1

unsigned char a = 200;
if (a > -1)            /* 看似恒真? */
    printf("always\n");

分析:

  1. a 是 unsigned char,值为 200
  2. 比较前 a 整型提升为 int(200,零扩展)
  3. -1 是 int(-1)
  4. 200 > -1 → 真

所以这次恰好恒真成立。但换 signed char:

signed char a = 200;   /* 实现定义, 常为 -56 */
if (a > -1)            /* -56 > -1 → 假 */

更经典的版本(5.4.2 详):

unsigned int u = 5;
if (u > -1)            /* -1 转 unsigned = 0xFFFFFFFF, 5 > 4294967295 → 假! */
    printf("never runs\n");
  • 这是"无符号与有符号比较"的陷阱:负数变超大无符号正数
  • -Wsign-compare 警告

陷阱:sizeof 与 char

char c = 'A';
sizeof(c);             /* 1, char 1 字节 */
sizeof(c + 1);         /* 4, c+1 中 c 提升为 int, 表达式是 int */
  • sizeof(c) 得 1(char 本身)
  • sizeof(c + 1) 得 4(c 提升为 int 后运算,结果是 int)

与 HFT/DPDK

报文字段提取的整型提升

uint8_t pkt[4] = {0x12, 0x34, 0x56, 0x78};

/* 反例: 隐式提升导致意外 */
uint32_t v = (pkt[0] << 24) | (pkt[1] << 16) | (pkt[2] << 8) | pkt[3];
/* pkt[0] 是 uint8_t, 提升为 int, <<24 若 int 是 32 位 → 符号位问题 */

/* 正解: 显式 cast */
uint32_t v = ((uint32_t)pkt[0] << 24) |
             ((uint32_t)pkt[1] << 16) |
             ((uint32_t)pkt[2] <<  8) |
             ((uint32_t)pkt[3]);
  • 大端读 32 位字段:每个字节先 cast 到 uint32_t 再移位,避免窄类型提升 UB
  • 0x80 << 24(signed)符号位溢出 UB;(uint32_t)0x80 << 24 安全

定宽类型避免符号性意外

/* 反例: char 符号性实现定义 */
char c = 0x80;
if (c < 0) ...         /* x86: 真(signed), ARM 某些: 假(unsigned) */

/* 正解: 用 uint8_t/int8_t 明确 */
uint8_t c = 0x80;      /* 一定 128, 一定非负 */
int8_t  s = 0x80;      /* 一定 -128 */
  • 报文字节一律 uint8_t,不用 char(符号性不定)
  • HFT/嵌入式工程规范:char 只用于字符,uint8_t/int8_t 用于字节

缓冲区长度比较

size_t len = 10;
int offset = -1;
if (offset < len)      /* -1 转 size_t = 巨大值, 真! 但意图是"offset 合法" */
    buf[offset] = 0;   /* 越界写, 崩溃 */
  • 有符号负数与无符号(size_t)比较 → 负数变巨大正数
  • 规范:长度用 size_t,偏移先检查 offset >= 0 再比

常见误区

误区 真相
char 一定有符号 实现定义;x86 默认 signed,某些 ARM 默认 unsigned
pkt[0] << 24 安全 uint8_t 提升为 int,符号位可能 UB;要 cast uint32_t
sizeof(c + 1) == 1 不,c 提升为 int,sizeof 是 4
unsigned char > -1 恒真 这次是;但 unsigned int > -1 是假(负数变巨大)
-Wconversion 默认开 不,要显式加;HFT 工程必开

实操

cat > t.c <<'EOF'
#include <stdio.h>
#include <stdint.h>
int main(void){
  unsigned char a = 200;
  printf("uc 200 > -1: %d\n", a > -1);          /* 1, 恒真 */
  unsigned int u = 5;
  printf("uint 5 > -1: %d\n", u > -1);          /* 0! 负数变巨大 */
  uint8_t b = 0x80;
  printf("sizeof(b)=%zu, sizeof(b+1)=%zu\n", sizeof(b), sizeof(b+1));  /* 1, 4 */
  uint8_t pkt[2] = {0x80, 0x01};
  /* 反例: 0x80 << 8, signed int 符号位 */
  int bad = (pkt[0] << 8) | pkt[1];
  printf("bad = 0x%x\n", bad);                    /* 可能负数 */
  uint32_t good = ((uint32_t)pkt[0] << 8) | pkt[1];
  printf("good = 0x%x\n", good);                  /* 0x8001 */
  return 0;
}
EOF

5.4

.2 算术转换

本节讲什么

二元算术/关系运算前,两操作数要转成共同类型 —— 这套规则叫寻常算术转换(usual arithmetic conversions)。它解释了为什么 unsigned + signed 常被当无符号算、负数变巨大正数,这是 HFT 代码里隐蔽数值 bug 的主要根源。本节讲转换层级、陷阱、HFT 防御写法。

要点

寻常算术转换规则(自上而下)

若有一边 long double  → 两边 long double
否则若有一边 double   → 两边 double
否则若有一边 float    → 两边 float
否则(整型):
   1. 先整型提升(char/short → int)
   2. 按整数转换等级向更宽类型提升
   3. 同宽时:若一边 unsigned → 两边 unsigned

整数转换等级(自高到低):

unsigned long long, long long
unsigned long,    long
unsigned int,     int
unsigned short,   short
unsigned char,    char
_Bool(最低)

浮点优先

int i = 1;
double d = 2.5;
double r = i + d;      /* i 转 double, 结果 3.5(double) */
  • 任何一边是浮点 → 两边转该浮点类型
  • 浮点转整型会截断小数;整型转浮点可能丢精度(int64 → double 低 11 位可能丢)

整型的"signed → unsigned"陷阱

int          a = -1;
unsigned int b = 5;

if (a < b)              /* a 转 unsigned = 0xFFFFFFFF, 4294967295 < 5 → 假! */
    printf("runs\n");    /* 不打印 */

分析:

  1. a 是 int(-1),b 是 unsigned int(5)
  2. 同宽(都 32 位),一边 unsigned → 两边 unsigned
  3. a 转为 unsigned int:模 2^32,即 0xFFFFFFFF = 4294967295
  4. 4294967295 < 5 → 假

这是"unsigned 吞噬负数"的经典场景:-1 比任何 unsigned 都"大"。

常见陷阱表

表达式 预期 实际 原因
-1 < 5u 真 假 -1 转 unsigned = 0xFFFFFFFF
sizeof(int) < -1 假 真 sizeof 返回 size_t(unsigned),-1 转 size_t = 巨大
5u - 8u -3 4294967293 unsigned 减法环绕
int + unsigned 有符号算 unsigned 算 同宽 signed→unsigned

铁律:有符号与无符号混合比较/运算前,显式 cast 到同一类型,别靠隐式转换。

算术转换与 HFT 类型选择

HFT 数据 推荐类型 理由
价格 int64_t 定点 避免浮点精度、避免 unsigned 比较陷阱
序列号/时间戳 uint64_t 环绕定义良好、足够大
长度 size_t 与库 API 一致,但偏移先检查 ≥0
报文字节 uint8_t 不用 char(符号不定)
计数 uint64_t 防溢出,环绕可控

与 HFT/DPDK

时间戳与序列号统一 uint64

uint64_t now = rte_get_tsc_cycles();      /* uint64 时间戳 */
uint64_t seq = next_seq();                 /* uint64 序列号 */
uint64_t elapsed = now - start;            /* uint64 减法, 环绕定义良好 */
  • uint64 范围足够大(584 年纳秒级),实战不会环绕
  • uint64 减法即便环绕也定义良好,不像有符号溢出 UB

价格定点运算

/* 价格用 int64 定点, 1 单位 = 1e-7 */
int64_t price = 1234567;       /* = 0.1234567 */
int64_t qty = 100;
int64_t notional = price * qty;   /* int64 乘法, 检查溢出 */

if (notional / price != qty) {   /* 溢出检查 */
    return -EOVERFLOW;
}
  • 避免浮点:精度可控、比较确定
  • int64 乘法溢出是 UB,要检查(或用 __int128 临时)

长度与偏移

size_t len = get_len();
int off = get_offset();
/* 反例 */
if (off < len) {                 /* off<0 时变巨大, 真 */
    buf[off] = 0;                /* 越界写 */
}
/* 正解 */
if (off >= 0 && (size_t)off < len) {
    buf[off] = 0;
}
  • 有符号偏移与无符号长度比较 → 负偏移变巨大正数 → 越界
  • 规范:先检查 off >= 0 再 cast 比较,或用 ptrdiff_t

比较的显式 cast

int32_t x = -1;
uint32_t y = 5;

/* 反例 */
if (x < y) ...                  /* x 转 unsigned = 0xFFFFFFFF, 假 */

/* 正解 */
if ((int64_t)x < (int64_t)y) ...   /* 显式 cast 到同类型 */

常见误区

int + unsigned 按 int 算 按 unsigned 算,负数变巨大

5u - 8u == -3 不,等于 4294967293(环绕)
浮点转整型四舍五入 不,截断小数

实操

本节讲什么

优先级决定运算符谁先结合;结合性决定同级从左还是从右;求值顺序决定操作数左右谁先算、副作用何时生效。三者里求值顺序是最坑的 —— C 故意不指定多数运算符的求值顺序,导致 a++ + a++ 这类 UB。本节讲优先级表、结合性、序列点与 UB,以及工程上"不背表加括号"的规范。

一元、赋值、?: 右 a=b=c = a=(b=c),*p++ 中 ++ 先
后缀 () [] . -> 左 a.b.c = (a.b).c 
a = b = c = 0;        /* 右结合: a = (b = (c = 0)) */
*p++;                 /* *(p++), 后置 ++ 先, 不是 (*p)++ */
*++p;                 /* *(++p) */
arr[i++];             /* arr[(i++)] */

求值顺序(关键)

C 不指定多数运算符的操作数求值顺序(除少数例外):

运算符 求值顺序
&& || 左到右,短路(保证)
?: 条件先,再求被选分支
,(逗号) 左到右(保证)
函数调用 参数求值顺序未指定,但都在调用前完成
+ - * / 等双目 未指定左右谁先
赋值 = 右操作数先求?未指定;副作用何时生效靠序列点 
int i = 1;
printf("%d %d\n", i, i++);   /* 参数求值顺序未指定, 输出可能是 "1 1" 或 "2 1" */

f(g(), h());                 /* g/h 谁先未指定 */
a[i] + i++;                  /* UB: 序列点内修改+读取 i */

序列点与 UB(5.4 详)

序列点(sequence point)是"此前副作用全生效、此后未开始"的执行点:

  • ; 语句结尾
  • && || ?: , 操作数之间
  • 函数调用:参数求值完成、进入函数体前(C99);C11 改为"完整表达式求值"

规则:两序列点间,同一对象最多修改一次,且若修改则不能同时被读取(除计算新值)。违反 → UB。

a++ + a++;            /* UB: 两次修改, 无序列点隔开 */
arr[i++] = i;          /* UB: 修改 i 一次, 读取一次, 顺序未定 */
a = a++;               /* UB: 修改两次(自增 + 赋值) */
i = i++ + 1;           /* UB */
printf("%d", a++ + a++);   /* UB */

规范:单表达式内对同一变量最多一次修改;有依赖顺序的副作用拆成多语句。

短路求值

if (p && p->len > 0)   /* p==NULL 时短路, 不解引用 p->len */
if (q || cached)        /* q 真时短路, 不求 cached */
  • && 左假 → 不求右;|| 左真 → 不求右
  • 短路是"安全空指针检查"的语义基础,不能重排序
  • 这是 &&/|| 求值顺序被保证的原因(其他双目未保证)

与 HFT/DPDK

复杂表达式加括号

/* 反例: 位与比判等低 */
if (flags & MASK == EXPECTED)   /* 实为 flags & (MASK == EXPECTED) */

/* 正解: 显式括号 */
if ((flags & MASK) == EXPECTED)
  • HFT 协议字段提取常 flags & MASK,与 == 比较时必须加括号
  • 规范:位运算、移位、三元混用时一律加括号,不靠背优先级表

短路保障安全

if (pkt && pkt->len >= HDR_MIN && pkt->data[0] == SYNC) {
    parse(pkt);
}
  • 链式 && 短路:任一假则后面不求值,安全
  • 顺序:从便宜到昂贵(指针非空 < 长度检查 < 字节比较)

序列点 UB 的真实事故

/* 反例: 日志里 i 被两次修改 */
log("port %d queue %d", port++, queue++);   /* 参数求值顺序未定, port/queue 哪个先 ++ 不确定 */

/* 正解: 先取值再自增 */
int p = port++, q = queue++;
log("port %d queue %d", p, q);
  • 函数参数有副作用时,顺序未定 → 行为不可预测
  • 拆成多语句,显式控制顺序

5.4

.4 词法贪心（maximal munch）

补充节 · 承接 5.4.3 优先级和求值顺序——优先级管不了"字符怎么切成 token"

本节讲什么

词法贪心和运算符优先级发生在编译的不同阶段，顺序固定：

源码字符流 → [词法分析: 切 token] → [语法分析: 优先级/结合性] → ...
                ↑ 词法贪心在这里         ↑ 优先级在这里

先切符号，再算优先级。优先级管不了字符怎么切。

词法贪心规则

C11 §6.4p4：

If the input stream has been parsed into preprocessing tokens up to a given character, the next preprocessing token is the longest sequence of characters that could constitute a preprocessing token.

从左向右，每次吃掉能构成合法 token 的最长一串字符。

例 1：A+++B

字符流:  A + + + B
切分:    A      ++      +      B
         标识符  自增   加    标识符
token 序列: A ++ + B
表达式:      (A++) + B
  • 读到 A → 标识符
  • 接下来连续三个 +：贪心取最长合法运算符 ++，消耗两个
  • 剩一个 +，取为加法
  • B → 标识符

人眼容易看成 A + (++B)，但词法阶段 token 已切死，后面的优先级救不了。

例 2：a---b

字符流: a - - - b
切分:   a    --     -     b
表达式: (a--) - b

边界：最长且合法，不是无限拉长

贪心的前提是"能构成合法 token"。C 没有 +++ 这个运算符，所以连续三个 + 最多吃两个组成 ++，剩下单独一个 +。不是无脑取最长字符串，是最长且合法。

一句话概括

词法贪心只负责把源码的一串字符切割成变量、运算符、数字。只看字符，不懂表达式逻辑——它根本不知道什么叫优先级；优先级是后面语法阶段才有的知识。

优先级只能操作已切好的 token

a + b * c     /* token 已切好; * 高于 +, 先算 b*c */

A++ + B       /* token: A ++ + B; 后置++ 高于 +, 先算 A++ */

假如 token 切出来是 A + ++ B（即 A + ++B），那 ++ 优先级高，先算 ++B 再加法——但那是另一套 token 了。

关键点：优先级只能操作已经切好的 token，不能改变 token 怎么切。

项目 词法贪心 max-munch 运算符优先级

误区：❌ 编译器看到 A+++B 会用优先级去猜是 A + ++B 真相：✅ 先贪心切 token，切完才轮到优先级按这套符号计算。

更多词法贪心陷阱

// 注释吃掉除法（C99 行注释陷阱）

int b = c//*comment*/d;

贪心把 // 之后整行当注释——*comment*/d; 连同分号一起被吃掉，剩 int b = c 缺分号 → 编译错误。想写"c 除以 d"必须让 / / 分开：c /*comment*/ / d（注释在前，除号在后）。

n-->0（"goes to" 运算符）

while (n-- > 0)   /* 常写成 n-->0, 看着像个运算符, 其实是 (n--) > 0 */

i+++++j 直接编译错误

字符流: i + + + + + j        (连续 5 个 +)
贪心切: i  ++  ++  +  j      (++ ++ +, 不是 + ++)
表达式: ((i++)++) + j

i++ 的结果是右值（临时值），对它再 ++ 需要左值 → gcc 报 error: lvalue required as increment operand。想表达 (i++) + (++j) 必须写空格：i++ + ++j。

0x1E+2 十六进制陷阱

0x1E+2  →  贪心切成 0x1E+  (一个 pp-number!)  然后 2

十六进制浮点/后缀规则会把 +2 吞进数字 token，想表达"0x1E 加 2"必须加空格：0x1E + 2。

老代码 a=-1 的历史事故

早期 K&R C 支持 =- 作为复合赋值，a=-1 被切成 a =- 1（减 1）而非 a = -1。C89 移除了这种写法，改成 -=,但词法切分的历史教训留了下来——这也是《C 陷阱与缺陷》ch01 词法陷阱的开篇故事。

宏展开不会重切 token

预处理 token 的边界在词法阶段已确定，宏展开只是 token 替换，不会把相邻 token 重新拼接：

#define P +
int x = a P+ b;    /* a + + b ?? 不: 词法已切成 'a' 'P' '+' 'b' */
                    /* 宏展开后是 a + + b 两个token, 不是 a ++ b */

反过来，想让 token 粘合需要显式 ## 运算符——这正是 ## 存在的原因。

代码自测

题目 1： x---y 经过词法贪心得到什么 token 序列？

参考答案

x -- - y，即 (x--) - y。贪心先吃最长的 --，剩下单个 -。

题目 2： 若 token 序列是 a + ++ b，此时靠什么决定先算 ++？

参考答案

运算符优先级（语法分析阶段）。前置 ++ 是一元运算符（优先级第 2 级），高于加法（第 4 级），所以先算 ++b 再加法。token 已定，优先级只决定运算次序。

题目 3： 能用运算符优先级改变词法贪心切出来的 token 吗？

参考答案

不能。两个阶段严格先后：词法切分（max-munch）完成后才进入语法分析。优先级只能作用于已切好的 token 序列。想改变切分只能改源码写法——加空格或括号。

题目 4： +++i 词法贪心切出来是什么 token？能编译吗？

参考答案

token 序列：++ + i（C 没有 +++ 运算符，最多吃两个 + 组成 ++，剩下单独的 +）。

不能编译。语法分析只能按这套 token 解析为 ++(+i)——前置 ++ 作用于 (+i)，而一元 + 的结果不是左值，gcc 报 error: lvalue required as increment operand。注意它不可能被解析成 +(++i)（那样就能编译了），因为第一个 token 已经是 ++ 而非 +，token 切死了语法救不了。想表达"正的 ++i"必须写空格：+ ++i。
