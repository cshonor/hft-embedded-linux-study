本章讲什么

编译第一阶段纯文本处理：#include、#define、条件编译、#/##、可变参数日志。DPDK/内核源码半数逻辑在宏里；调试开关与跨平台依赖本章。

  • include guard / #pragma once
  • __FILE__ / __LINE__ / __func__
  • #if DEBUG 零开销关日志
  • 复杂计算用 inline，常量/日志/拼接用宏

14.0

`gcc -E`：只做预处理

《Pointers on C》第 14 章配套 · 预处理器实操
ch14 README · 14.4 文件包含 · 14.3 条件编译

命令含义

gcc -E main.c -o main.i
-E 只做预处理，然后停止——不编译、不汇编、不链接
输入 main.c
输出 main.i（预处理后的 C 文本）

.i 仍是可读的 C 源码，不是汇编、不是二进制。
若 #include <stdio.h>，.i 常膨胀到几千行，属正常。

等价：cpp main.c -o main.i（效果几乎一样）。

预处理做哪些事

  1. 展开宏：#define 文本替换
  2. 展开头文件：#include 内容粘贴进来（递归）
  3. 条件编译：#ifdef / #if / #else / #endif，只留有效分支
  4. 删除注释：//、/* */ 默认去掉
  5. 生成 # 行号 "文件名" 标记（方便报错 / gdb 对回源码行）

常用变体

# 预处理结果打到屏幕（不写文件）
gcc -E main.c

# 保留注释（大写 -C），方便人读
gcc -E -C main.c -o main.i

# 命令行定义宏
gcc -E -DDEBUG=1 main.c -o main.i

GCC 四阶段对照

# 1. 预处理  c → i
gcc -E main.c -o main.i
# 2. 编译    i → s（汇编）
gcc -S main.i -o main.s
# 3. 汇编    s → o
gcc -c main.s -o main.o
# 4. 链接    o → 可执行
gcc main.o -o main

平时一条 gcc main.c -o main 是把四步串起来；出宏 / include 问题时，用 -E 单独看第一阶段。

典型使用场景

  • 宏展开结果不对：看实际被替换成了什么
  • 头文件重复包含、条件编译分支走错
  • 想确认系统头最终「喂」给编译器的是什么

排查 #include 时，常与 14.4 一起用：gcc -E a.c -o a.i。

代码自测

题目 1： 以下代码经过 gcc -E 预处理后，宏展开结果是什么？

#define SQUARE(x) ((x) * (x))
int result = SQUARE(3 + 1);
参考答案

展开为 int result = ((3 + 1) * (3 + 1));，结果为 16。注意宏参数必须加括号——如果写 #define SQUARE(x) x * x，展开为 3 + 1 * 3 + 1 = 7（优先级错误）。外层括号也很重要，防止宏与其他运算符组合时出错。

14.1

预定义符号

本节讲什么

预定义符号是编译器自动提供的内置宏，无需 #define 即可使用。它们覆盖三类信息：源码位置（__FILE__/__LINE__/__func__）、平台架构（__x86_64__/__aarch64__/__linux__）、编译器与标准版本（__GNUC__/__STDC_VERSION__）。这一节把这些宏分类讲清，并给出 HFT 工程里日志、跨平台编译、特性检测的实际用法。

认知锚点：预定义宏是 C 工程的编译期反射——在标准 C 没有运行时反射的情况下，这些宏是仅有的「让代码知道自己被谁、在哪、怎么编译」的机制。HFT 跨平台部署（x86 + ARM、Linux + FreeBSD）、日志定位、特性开关全部依赖它们。

要点

源码位置宏

#define ERR_LOG(fmt, ...) \
    fprintf(stderr, "[%s:%d %s] " fmt, \
            __FILE__, __LINE__, __func__, ##__VA_ARGS__)

ERR_LOG("order rejected: id=%lu\n", order_id);
/* 输出：[order_engine.c:142 process_order] order rejected: id=12345 */
宏 类型 含义 标准
__FILE__ const char * 当前源文件名（字符串字面量） C89
__LINE__ int 当前行号 C89
__func__ const char * 当前函数名（static const char __func__[]） C99
__DATE__ const char * 编译日期 "Jul 19 2026" C89
__TIME__ const char * 编译时间 "09:24:30" C89
__BASE_FILE__ const char * 主源文件名（GCC 扩展） GCC
__COUNTER__ int 每次使用递增（GCC/Clang 扩展） GCC

__func__ 与 __FUNCTION__ 的区别：__func__ 是 C99 标准，本质是 static const char __func__[] = "name";（编译器隐式注入）。__FUNCTION__ 是 GCC 老扩展，C99 后等价于 __func__。新代码用 __func__。

__DATE__/__TIME__ 的工程陷阱：这两个宏让构建不可复现——同一份源码不同时间编译出不同二进制。HFT 对账、监管审计要求二进制可复现，必须用 -Wdate-time 警告 + 构建系统注入固定时间戳。

平台与架构宏

#if defined(__x86_64__) && defined(__linux__)
    /* x86-64 Linux：强内存模型，可省部分屏障 */
#elif defined(__aarch64__) && defined(__linux__)
    /* ARM64 Linux：弱内存模型，需显式 smp_wmb/smp_rmb */
#elif defined(__powerpc64__)
    /* POWER：弱内存模型 */
#else
    #error "unsupported platform"
#endif
宏 含义
__x86_64__、__amd64__ x86-64 架构
__i386__ 32 位 x86
__aarch64__ 64 位 ARM
__arm__ 32 位 ARM
__powerpc__、__powerpc64__ PowerPC
__riscv RISC-V
__linux__ Linux 平台
__FreeBSD__、__OpenBSD__ BSD 系列
_WIN32、_WIN64 Windows（注意无前导下划线）
__APPLE__、__MACH__ macOS

内存模型差异是 HFT 跨平台的核心痛点：x86-64 是强内存模型（TSO），写-写天然有序，可省部分屏障；ARM64/POWER 是弱内存模型，多核同步必须显式 smp_wmb()/smp_rmb()。DPDK 的 rte_smp_wmb() 在 x86 上展开为空，在 ARM64 上展开为 dmb ishst——条件编译隐藏这种差异。

编译器与版本

宏 含义
__GNUC__ GCC 主版本号
__GNUC_MINOR__ GCC 次版本号
__clang__ Clang 编译器
__clang_major__ Clang 主版本
_MSC_VER MSVC 版本（无前导下划线）
__INTEL_COMPILER Intel 编译器 
#if defined(__clang__)
    #define COMPILER "clang " __clang_version__
#elif defined(__GNUC__)
    #define COMPILER "gcc " __VERSION__
#elif defined(_MSC_VER)
    #define COMPILER "msvc " _MSC_FULL_VER
#endif

GCC 与 Clang 的关系：Clang 定义 __clang__ 同时也定义 __GNUC__（兼容 GCC 扩展）。检测顺序必须先 Clang 后 GCC，否则 Clang 被误判为 GCC。

C 标准版本

宏 值 标准
__STDC__ 1 标准 C（C89 起）
__STDC_VERSION__ 199409L C89 + AMD1
199901L C99
201112L C11
201710L C17/C18
202311L C23 
#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 201112L
    /* C11 特性：_Static_assert、_Generic、<stdatomic.h> */
#elif defined(__STDC_VERSION__) && __STDC_VERSION__ >= 199901L
    /* C99 特性：变长数组、// 注释、声明在任意位置 */
#else
    /* C89：变量声明必须在块首 */
#endif

HFT 工程通常要求 C11 起步（<stdatomic.h>、_Static_assert、_Generic），部分前沿项目用 C17/C23。DPDK 最低要求 C99，推荐 C11。

C11/C23 特性检测宏

/* C11：__has_include 检测头文件是否存在 */
#if defined(__has_include)
    #if __has_include(<stdatomic.h>)
        #include <stdatomic.h>
        #define HAVE_STDATOMIC 1
    #endif
#endif

/* C23：__has_c_attribute 检测属性 */
#if defined(__has_c_attribute)
    #if __has_c_attribute(deprecated)
        #define DEPRECATED [[deprecated]]
    #endif
#endif

__has_include 让代码自适应不同环境——某些 libc 可能没有 <stdatomic.h>，运行时检测比硬编码平台更可靠。

HFT 关联

日志定位

#define LOG_ERR(fmt, ...) \
    rte_log(RTE_LOG_ERR, RTE_LOGTYPE_APP, \
            "[%s:%d %s] " fmt, \
            __FILE__, __LINE__, __func__, ##__VA_ARGS__)

__FILE__/__LINE__/__func__ 是 HFT 日志的三件套。生产环境关 DEBUG 日志但保留 ERROR，定位问题时一行日志就能找到源码位置。注意二进制大小：__FILE__ 是字符串字面量，每个使用点都存一份文件名，大型项目可能膨胀几 MB .rodata。优化方案：编译选项 -fmacro-prefix-map 裁剪路径前缀。

跨平台内存屏障

/* DPDK rte_smp_wmb 实现（简化） */
#if defined(RTE_ARCH_X86_64)
    #define rte_smp_wmb() do { } while (0)   /* x86 强模型，空操作 */
#elif defined(RTE_ARCH_ARM_64)
    #define rte_smp_wmb() asm volatile("dmb ishst" ::: "memory")
#elif defined(RTE_ARCH_PPC_64)
    #define rte_smp_wmb() asm volatile("lwsync" ::: "memory")
#endif

同一份 C 代码在不同架构上编译出不同的屏障指令，HFT 跨平台部署的基础。写屏障用宏而非函数——屏障必须内联到调用点，函数调用会引入额外的内存访问，破坏屏障语义。

编译期平台校验

#if !defined(__x86_64__) && !defined(__aarch64__)
    #error "HFT dataplane requires x86-64 or ARM64"
#endif

#if __SIZEOF_POINTER__ != 8
    #error "64-bit only"
#endif

#error 在编译期阻断不合法配置，优于运行期崩溃。__SIZEOF_POINTER__ 是 GCC/Clang 内置宏，比 sizeof(void*) 更早可用（预处理阶段）。

构建版本戳

const char *build_info(void)
{
    return "app=" APP_NAME
           " ver=" APP_VERSION
           " built=" __DATE__ " " __TIME__
           " compiler=" COMPILER
           " arch=" TARGET_ARCH;
}

启动时打印构建信息，便于运维确认部署的版本。监管场景下 __DATE__/__TIME__ 要替换为构建系统注入的固定时间戳，保证可复现构建。

UB 边界

情形 后果 防护
__func__ 在文件作用域使用 编译错误（只能在函数内） 仅函数内使用
__DATE__/__TIME__ 导致不可复现构建 审计失败 -Wdate-time + 注入固定时间
误用 __FUNCTION__ 当 __func__ 非标准，可移植性差 C99 起统一用 __func__
Clang 误判为 GCC 用错扩展特性 先检 __clang__ 再检 __GNUC__
__STDC_VERSION__ 未定义当 C89 某些编译器不定义 #if defined(__STDC_VERSION__) && ...

口述自测题

  1. __FILE__、__LINE__、__func__ 三个宏分别是什么类型？__func__ 在 C99 标准里的本质是什么（不是宏，而是什么）？它能在文件作用域使用吗？
  2. Clang 同时定义 __clang__ 和 __GNUC__。检测编译器时为什么必须先检 __clang__ 再检 __GNUC__？反过来检会出什么问题？
  3. __DATE__ 和 __TIME__ 让构建不可复现。HFT 监管审计为什么要求可复现构建？工程上怎么解决这个矛盾？

  5. __has_include(<stdatomic.h>) 检测头文件是否存在。这种检测相比硬编码 #if defined(__linux__) 有什么优势？什么场景下应该用哪种？
14.3

条件编译

本节讲什么

条件编译是预处理器的「编译期分支」——#if/#ifdef/#ifndef/#elif/#else/#endif 让代码块根据宏定义或常量表达式选择性编译。这一节给出条件编译的三大用途（调试开关、跨平台、特性裁剪）、指令对照表，以及 HFT 工程里线上关日志、跨架构编译、特性开关的实际形态。

认知锚点：条件编译不是「可选的预处理器特性」，而是 C 工程的基础设施。Linux 内核、DPDK、glibc 全部依赖条件编译适配不同架构、不同配置、不同编译器。理解条件编译，才能理解为什么同一份 C 代码能在 x86、ARM、PowerPC 上跑——靠的就是这套机制。

要点

指令对照表

指令 作用 示例
#if EXPR 表达式非 0 则编译 #if BURST_SIZE > 16
#ifdef NAME 宏已定义则编译 #ifdef DEBUG
#ifndef NAME 宏未定义则编译 #ifndef HEADER_H
#elif EXPR 否则若 #elif defined(__arm__)
#else 否则 #else
#endif 结束条件块 #endif

#ifdef vs #if defined

/* 等价 */
#ifdef DEBUG
    ...
#endif

#if defined(DEBUG)
    ...
#endif

/* 多条件时 #if defined 更清晰 */
#if defined(DEBUG) && defined(VERBOSE)
    ...
#endif

/* ifdef 不支持逻辑组合 */
#ifdef DEBUG && VERBOSE   /* 语法错误 */

#if defined(NAME) 是通用形式，支持 &&、||、! 逻辑组合。#ifdef NAME 是单宏判断的简写。复杂条件用 #if defined，单宏判断用 #ifdef。

#if 的常量表达式

#if BURST_SIZE > 0 && BURST_SIZE <= 256
    /* 合法范围 */
#elif BURST_SIZE > 256
    #error "BURST_SIZE too large"
#endif

#if 的表达式必须是预处理常量表达式：

  • 宏替换后是整型常量表达式。
  • defined(NAME) 判断宏是否定义。
  • 不能用 sizeof、不能调用函数（C99 起部分放宽）。
  • 未定义的宏在表达式中视为 0。
#if UNKNOWN_MACRO    /* UNKNOWN_MACRO 未定义，视为 0，条件为假 */
    ...
#endif

调试开关：HFT 线上关日志

/* debug.h */
#if HFT_DEBUG_LEVEL >= 2
    #define DBG_TRACE(fmt, ...)  log_trace(fmt, ##__VA_ARGS__)
#elif HFT_DEBUG_LEVEL >= 1
    #define DBG_TRACE(fmt, ...)  ((void)0)
#else
    #define DBG_TRACE(fmt, ...)  ((void)0)
#endif

/* 调用 */
DBG_TRACE("seq=%lu processing\n", seq);

关闭时零开销：((void)0) 展开为空操作，编译器完全删除调用。汇编中无 log_trace 调用，无参数准备，无分支判断。HFT 数据面要求生产环境日志零开销，条件编译是唯一手段。

编译期日志级别

# 开发环境
gcc -DHFT_DEBUG_LEVEL=2 ...

# 测试环境
gcc -DHFT_DEBUG_LEVEL=1 ...

# 生产环境
gcc -DHFT_DEBUG_LEVEL=0 ...

构建系统通过 -D 注入日志级别，同一份源码编译出不同行为的二进制。生产环境关掉 TRACE/DEBUG 日志，保留 ERROR。

跨平台编译

#if defined(__x86_64__) && defined(__linux__)
    /* x86-64 Linux */
    #define HFT_ARCH_X86_64 1
    #define HFT_CACHE_LINE 64
    #define HFT_MEMBAR()    asm volatile("" ::: "memory")  /* x86 强模型 */
#elif defined(__aarch64__) && defined(__linux__)
    /* ARM64 Linux */
    #define HFT_ARCH_ARM64 1
    #define HFT_CACHE_LINE 64
    #define HFT_MEMBAR()    asm volatile("dmb ish" ::: "memory")  /* ARM 弱模型 */
#elif defined(__powerpc64__)
    /* PowerPC 64 */
    #define HFT_ARCH_PPC64 1
    #define HFT_CACHE_LINE 128
    #define HFT_MEMBAR()    asm volatile("lwsync" ::: "memory")
#else
    #error "unsupported platform"
#endif

条件编译隐藏平台差异：调用方用 HFT_MEMBAR()，不关心是 x86 空操作还是 ARM dmb ish。这是 DPDK rte_smp_wmb、内核 smp_wmb 的设计原理。

特性开关

#ifdef HFT_ENABLE_TCP_FAST
    /* TCP Fast Open 快速路径 */
    int fast_send(struct sock *sk, ...) {
        /* ... */
    }
#else
    /* 兼容路径 */
    int fast_send(struct sock *sk, ...) {
        return compat_send(sk, ...);
    }
#endif

特性开关让同一份代码编译出「带特性」和「不带特性」两个版本。HFT 工程用于：

  • 实验特性：新策略默认关闭，灰度时开启。
  • 许可证特性：付费用户开启，免费用户关闭。
  • 硬件特性：某些网卡支持零拷贝，不支持则走传统路径。

头文件保护

#ifndef QUOTE_PROTO_H
#define QUOTE_PROTO_H

/* 头文件内容 */

#endif /* QUOTE_PROTO_H */

include guard 防止头文件重复包含。详见 14.4.2。

嵌套条件编译

#if defined(__linux__)
    #if defined(__x86_64__)
        /* Linux x86-64 */
    #elif defined(__aarch64__)
        /* Linux ARM64 */
    #endif
#elif defined(__FreeBSD__)
    /* FreeBSD */
    #if defined(__x86_64__)
        /* FreeBSD x86-64 */
    #endif
#endif

嵌套可读性差，深度超过 3 层应重构。用 #if defined(A) && defined(B) 合并条件，或拆分到不同头文件。

#elif defined 链

#if defined(__GNUC__)
    #define COMPILER_GCC 1
#elif defined(__clang__)
    #define COMPILER_CLANG 1
#elif defined(_MSC_VER)
    #define COMPILER_MSVC 1
#else
    #define COMPILER_UNKNOWN 1
#endif

#elif defined 链是编译器检测的标准写法。注意顺序敏感：Clang 同时定义 __clang__ 和 __GNUC__，必须先检 Clang。

HFT 关联

DPDK CONFIG_ 宏

/* DPDK 的配置宏，由 meson build 生成 */
#ifdef RTE_LIBRTE_MLX5_PMD

14.5

其他指令

本节讲什么

除了 #define、#include、#if 这些核心指令，预处理器还有一组补充指令：#error（编译期阻断）、#pragma（编译器扩展）、#line（重写行号）、#undef（取消宏）。这一节给出它们的用法和 HFT 工程里的实际场景。

认知锚点：这些指令看似边缘，却是 C 工程的「安全阀」与「调节器」。#error 让非法配置在编译期失败，优于运行期崩溃；#pragma 控制编译器行为（对齐、警告、优化）；#line 是代码生成器的工具；#undef 是宏作用域控制。理解它们，才能写出健壮的工程代码。

要点

#error — 编译期阻断

#if BURST_SIZE > 256
    #error "BURST_SIZE cannot exceed 256"
#endif

#if !defined(__x86_64__) && !defined(__aarch64__)
    #error "HFT dataplane requires x86-64 or ARM64"
#endif

#if RTE_VERSION < RTE_VERSION_NUM(21, 11, 0, 0)
    #error "DPDK >= 21.11 required, please upgrade"
#endif

#error 在预处理阶段打印消息并失败，编译立即停止。用途：

  1. 配置校验：非法配置编译期失败，优于运行期崩溃。
  2. 平台检测：不支持的架构直接拒绝编译。
  3. 版本检查：依赖库版本不够时拒绝编译。
  4. 特性冲突：互斥的特性同时开启时报错。

#error 是 HFT 工程的第一道防线——把运行期可能出现的错误前移到编译期，节省调试时间。

#warning — 编译期警告

#if defined(__GNUC__) && __GNUC__ < 8
    #warning "GCC < 8 may generate suboptimal code, consider upgrading"
#endif

#warning 是 GCC 扩展（非标准），打印警告但继续编译。用于提示性信息，不阻断编译。C23 引入标准 #warning。

#pragma — 编译器扩展

#pragma 是预处理器指令，但具体语义由编译器定义。主流用途：

用法 作用 示例
#pragma once 头文件保护 见 14.4.2
#pragma pack(push, n) 结构体对齐控制 #pragma pack(push, 1)
#pragma pack(pop) 恢复对齐
#pragma GCC diagnostic 局部警告控制 #pragma GCC diagnostic ignored "-Wxxx"
#pragma GCC push_options 编译选项压栈
#pragma GCC pop_options 恢复编译选项
#pragma GCC optimize 函数级优化控制 #pragma GCC optimize("O3")
#pragma GCC target 函数级目标平台 #pragma GCC target("avx2")
#pragma message 编译期打印消息 #pragma message("building for x86")

#pragma pack — 结构体对齐

#pragma pack(push, 1)   /* 保存当前对齐，设为 1 字节 */
struct eth_hdr {
    uint8_t  dst[6];
    uint8_t  src[6];
    uint16_t type;
};
#pragma pack(pop)        /* 恢复对齐 */

/* sizeof(struct eth_hdr) = 14，无 padding */

#pragma pack(1) 让结构体按 1 字节对齐，无 padding。用于网络协议头（必须按线上格式精确布局）。push/pop 配对保证对齐设置不泄漏到其他结构。

详见 ch10 packed 结构体的权衡。

#pragma GCC diagnostic — 局部警告控制

#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wunused-variable"
    int unused = 42;   /* 警告被抑制 */
#pragma GCC diagnostic pop

局部抑制警告：只在必要位置关闭特定警告，用完立即恢复。比全局 -Wno-xxx 更精确。

#pragma GCC diagnostic push
#pragma GCC diagnostic error "-Wformat"   /* 把格式警告升级为错误 */
    printf("%d\n", "hello");   /* 编译错误 */
#pragma GCC diagnostic pop

把特定警告升级为错误，强制代码质量。

#pragma GCC optimize — 函数级优化

#pragma GCC optimize("O3", "unroll-loops", "fast-math")
static void hot_path_function(struct rte_mbuf *m) {
    /* 强制 O3 + 循环展开 + 快速数学 */
}

函数级优化控制，让热点函数用更激进的优化，其他函数保持默认。HFT 数据面优化常用。

#pragma GCC target — 函数级指令集

#pragma GCC target("avx2,fma")
void vector_add(float *a, float *b, float *c, int n) {
    /* 此函数可用 AVX2 + FMA 指令 */
    for (int i = 0; i < n; i++)
        c[i] = a[i] + b[i];
}

让特定函数使用 AVX2/FMA 等指令集，其他函数不依赖这些指令。用于运行时 CPU 不一定支持新指令集的场景。

#line — 重写行号与文件名

#line 100 "generated_code.c"
/* 此后的 __LINE__ 从 100 开始，__FILE__ 是 "generated_code.c" */

#line 重写 __LINE__ 和 __FILE__，主要用于代码生成器——让生成的代码报错时指向源模板，而非生成结果。

/* 代码生成器示例 */
/* template: 行 50 是用户写的 */
/* generated: 行 200 是生成的 */
#line 50 "template.dt"
int generated_func(void) { return 0; }
/* 报错时显示 template.dt:50，而非 generated.c:200 */

HFT 工程极少用 #line，除非有代码生成器（如协议解析器生成器）。日常代码不要用——会干扰调试。

#undef — 取消宏定义

#define TEMP_DEBUG 1

/* ... 使用 TEMP_DEBUG ... */

#undef TEMP_DEBUG   /* 取消定义，后续不可见 */

#ifdef TEMP_DEBUG
    /* 此块不编译 */
#endif

#undef 的用途：

  1. 局部宏：只在某段代码用的宏，用完 #undef 避免泄漏。
  2. X-Macro 重定义：同一份 .def 文件用不同宏展开，每次包含后 #undef（见 14.2.3）。
  3. 重定义前取消：标准要求重定义前先 #undef（虽然允许相同重定义）。
  4. 屏蔽系统宏：某些库定义的宏与工程冲突，#undef 后重定义。
/* X-Macro 的 #undef 模式 */
#define DEFINE_EVT(name, val, str)  EVT_##name = val,
enum events {
    #include "events.def"
    EVT_NUM
};
#undef DEFINE_EVT

#define DEFINE_EVT(name, val, str)  [val] = str,
static const char *const evt_str[] = {
    #include "events.def"
};
#undef DEFINE_EVT

#、##、#pragma 的预处理顺序

/* 预处理阶段顺序：
   1. 三字符替换、行续接
   2. token 化、注释替换
   3. #include 嵌入
   4. #define 宏展开、# 操作符、## 操作符
   5. #if/#ifdef 条件裁剪
   6. #error 触发（若条件满足）
   7. #pragma 处理（编译器阶段）
   8. #line 重写行号
*/

#pragma 实际上在编译器阶段处理（不是预处理器），但语法上是预处理指令。这意味着 #pragma 受 #if 条件控制：

#if defined(__GNUC__)
    #pragma GCC optimize("O3")
#endif

_Pragma — #pragma 的宏形式

/* C99 _Pragma 操作符，等价 #pragma */
_Pragma("pack(push, 1)")
struct packed_hdr { ... };
_Pragma("pack(pop)")

/* 可在宏内使用 */
#define PACKED_STRUCT(name, body) \
    _Pragma("pack(push, 1)") \
    struct name body; \
    _Pragma("pack(pop)")

PACKED_STRUCT(eth_hdr, {
    uint8_t  dst[6];
    uint8_t  src[6];
    uint16_t type;
});

_Pragma 是 #pragma 的字符串形式，可在宏内使用。#pragma 不能在宏内（# 是预处理指令，宏体里只能用 # 字符串化）。C99 标准化。

#error 编译期配置校验

/* config_check.h */
#if BURST_SIZE < 1 || BURST_SIZE > 256
    #error "BURST_SIZE must be in [1, 256]"
#endif

#if MAX_CORES < 1 || MAX_CORES > 64
    #error "MAX_CORES must be in [1, 64]"
#endif

#if !defined(HFT_ARCH_X86_64) && !defined(HFT_ARCH_ARM64)
    #error "Unsupported architecture, need x86-64 or ARM64"
#endif

#if defined(HFT_ARCH_X86_64) && CACHE_LINE != 64
    #error "x86-64 cache line must be 64"
#endif

HFT 工程在编译期校验所有配置宏，非法配置立刻失败。比运行期检查早一个阶段，节省调试时间。

#pragma pack 协议头

#pragma pack(push, 1)
struct tcp_hdr {
    uint16_t src_port;
    uint16_t dst_port;
    uint32_t seq;
    uint32_t ack;
    uint16_t flags_offset;
    uint16_t window;
    uint16_t checksum;
    uint16_t urgent;
};
#pragma pack(pop)

_Static_assert(sizeof(struct tcp_hdr) == 20, "TCP header must be 20 bytes");

网络协议头必须按线上格式精确布局，#pragma pack(1) 消除 padding。_Static_assert 锁定大小，防止误改。详见 ch10。

#pragma GCC optimize 热点优化

/* 全局 -O2，热点函数 -O3 */
#pragma GCC optimize("O3", "unroll-loops", "no-semantic-interposition")
static inline void process_quote_fast(const struct quote *q)
{
    /* 报文处理热路径，强制 O3 + 循环展开 */
}

HFT 数据面热点函数单独优化到 -O3，其他函数保持 -O2 平衡编译时间与性能。

#pragma GCC diagnostic 局部警告

#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wcast-align"
    /* 某些场景必须做未对齐访问 */
    uint32_t val = *(uint32_t *)unaligned_ptr;
#pragma GCC diagnostic pop

在必须的未对齐访问处局部抑制 -Wcast-align 警告，其他位置仍保留警告。

#pragma message 构建信息

#pragma message("Building HFT engine for " HFT_ARCH)
#pragma message("DPDK version: " RTE_VERSION_STRING)
#pragma message("Compile date: " __DATE__)

编译时打印构建信息，便于确认配置。CI/CD 日志里可见。

#undef 屏蔽冲突宏

/* 某些库定义了 min/max，与工程冲突 */

    #undef min
#endif
#ifdef max
    #undef max
#endif

第三方库（特别是 Windows 头文件）可能定义 min/max 宏，与 C++ std::min/std::max 或工程自定义冲突。#undef 后重定义解决。

#pragma pack 的跨平台差异

/* GCC/Clang */
#pragma pack(push, 1)
struct foo { ... };
#pragma pack(pop)

/* MSVC */
#pragma pack(push, 1)
struct foo { ... };
#pragma pack(pop)
/* 语法相同，但某些选项不同 */

/* C11 标准方案（推荐） */
#include <stdalign.h>
struct __attribute__((packed)) foo { ... };   /* GCC 专用 */

#pragma pack 是事实标准但非 C 标准。跨平台用 __attribute__((packed))（GCC/Clang）和 #pragma pack（MSVC）条件编译，或用 C11 <stdalign.h> 的 alignas（但对齐到 1 字节需要 alignas(1)，标准支持有限）。

#pragma pack 忘 pop 的后果

#pragma pack(push, 1)
struct packed_hdr { ... };
/* 忘记 #pragma pack(pop) */

struct normal_struct {
    uint32_t a;   /* 本应 4 对齐，但被 pack(1) 影响，1 对齐 */
    uint64_t b;   /* 1 对齐，性能下降，部分平台未对齐访问 UB */
};

#pragma pack 的影响持续到下一个 #pragma pack 或文件末。push/pop 必须严格配对，否则后续结构意外被压缩。

题目 1： 以下宏有什么问题？如何修复？

#define MAX(a, b) a > b ? a : b
int x = MAX(1, 2) + 3;
参考答案

展开为 1 > 2 ? 1 : 2 + 3，由于运算符优先级，实际解析为 1 > 2 ? 1 : (2 + 3) = 5（而不是预期的 max(1,2)+3 = 5）。碰巧结果相同，但如果 MAX(2, 1) + 3 展开为 2 > 1 ? 2 : 1 + 3 = 2（错误，应为 5）。修复：#define MAX(a, b) ((a) > (b) ? (a) : (b))。
