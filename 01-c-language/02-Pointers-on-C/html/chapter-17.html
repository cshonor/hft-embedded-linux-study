17.1

内存分配

本节讲什么

ADT（抽象数据类型）容器的内存策略：不透明指针封装、节点分配模式、释放回调设计、预分配 vs 动态分配的工程取舍。这是 ch17 全章的工程基础——栈/队列/树的实现细节千差万别，但内存管理遵循同一套原则。HFT 场景里这套原则直接决定容器能否上数据面。

要点

ADT 两大工程原则

1. 封装隐藏（不透明指针）

头文件只暴露 typedef struct Queue Queue;，结构体定义藏在 .c 里：

/* queue.h */
typedef struct Queue Queue;
Queue *queue_create(size_t cap);
int    queue_enqueue(Queue *q, void *data);
void  *queue_dequeue(Queue *q);
void   queue_destroy(Queue **q, void (*free_cb)(void *));

/* queue.c */
#include "queue.h"
struct Queue {
    struct Node *head, *tail;
    size_t len;
    size_t cap;
};

收益：

  • 使用者无法直接访问 q->head，强制走 API
  • 内部实现可自由重构（链表换环形数组）而不破坏 ABI 的使用者
  • 编译依赖最小化——改 struct Queue 内部只需重编 queue.c，不用重编所有使用者

2. 接口隔离

create/destroy/enqueue/dequeue 四件套是容器标准接口。底层可以是链表、环形数组、甚至无锁结构——使用者无感知。这是 HFT"控制面用链表、数据面换 ring"的设计基础。

不透明指针的代价

  • 只能在堆上分配（栈分配需要编译期知道大小）
  • 每次操作都是间接访问（指针解引用）
  • 不能内联优化跨 .c 边界

HFT 数据面有时为极致性能牺牲封装，把结构体定义暴露在头里允许栈分配和内联。这是工程权衡，不是默认选择。

节点分配模式

容器节点本身和载荷（payload）是两层内存：

struct Node {
    void *payload;        /* 载荷指针, 用户数据 */
    struct Node *next;    /* 链接 */
};
  • 节点：容器自己 malloc/calloc 管理
  • 载荷：用户传入 void*，容器不关心它的来源（栈/堆/mempool）

calloc 优于 malloc + 手动清零——编译器能优化成一次操作。节点小（典型 16-24 字节）时 calloc 几乎无开销。

释放回调 free_cb

容器 destroy 时，节点内存由容器释放，但载荷的释放策略容器不知道——可能是 free、可能是 mempool_put、可能不该释放（外部所有）。所以 destroy 接受回调：

void list_destroy(List **lst, void (*free_cb)(void *))
{
    Node *cur = (*lst)->head;
    while (cur) {
        Node *next = cur->next;
        if (free_cb) free_cb(cur->payload);   /* 载荷由回调决定 */
        free(cur);                             /* 节点容器自己释放 */
        cur = next;
    }
    free(*lst);
    *lst = NULL;   /* 置空防止悬垂 */
}

不传 free_cb → 载荷泄漏。传 free → 标准 heap 释放。传 mempool_put → 归还 mempool。这是 HFT 容器与 mempool 协作的标准模式。

destroy 的二级指针

void list_destroy(List **lst, ...) 用二级指针是为了能在 destroy 后把调用者的 List* 置 NULL：

List *mylist = list_create();
/* ... */
list_destroy(&mylist, free);   /* mylist 被置 NULL */
/* 现在用 mylist 会立即段错误, 而不是用已释放内存 */

如果用一级指针 list_destroy(List *lst, ...)，调用者的 mylist 仍指向已释放内存，后续误用是 use-after-free。二级指针让悬垂指针立即变 NULL，降低 UAF 风险。

预分配 vs 动态分配

维度 链表 + malloc 预分配 Ring
分配时机 运行时按需 启动时一次
分配延迟 不确定（malloc 锁 + 碎片） 零（运行时无分配）
容量 无上限 固定
碎片 长跑易碎片 无碎片
cache 节点分散，局部性差 连续内存，cache 友好
多线程 malloc 全局锁 SPSC 可无锁
HFT 适用 控制面 数据面

HFT 数据面铁律：运行时零分配。所有容器必须预分配，运行时只做指针搬运。DPDK rte_ring/rte_mempool 就是这一原则的工业实现。

realloc 扩容的临时指针

动态数组容器扩容时：

void **newbuf = realloc(s->buf, newcap * sizeof(void *));
if (!newbuf) {
    /* 扩容失败, 原 buf 仍有效, 容器保持可用 */
    return -1;
}
s->buf = newbuf;   /* 成功后才赋值 */
s->cap = newcap;

直接 s->buf = realloc(...) 失败时原 buf 丢失，内存泄漏 + 容器损坏。必须用临时指针。详见 ch11。

容器与 mempool 的协作

HFT 容器常配合 mempool：

/* 预分配 mempool 存节点 */
rte_mempool *node_pool = rte_mempool_create("nodes", 4096,
    sizeof(struct Node), 0, NULL, NULL, NULL, NULL,
    SOCKET_ID_ANY, 0);

/* push 时从 mempool 取, 不 malloc */
struct Node *n = rte_mempool_get(node_pool);
n->payload = data;
n->next = s->head;
s->head = n;

/* pop 时归还 mempool, 不 free */
struct Node *old = s->head;
s->head = old->next;
rte_mempool_put(node_pool, old);

零运行时分配 + 无锁 per-lcore cache，这是 DPDK 容器的标准范式。

HFT 关联

  • 数据面零分配：所有容器预分配，运行时只指针搬运，rte_ring/rte_mempool 是工业实现
  • 控制面可用 malloc：配置加载、会话管理、慢路径处理用链表+malloc 容器可接受
  • free_cb 与 mempool：容器 destroy 回调传 rte_mempool_put 把载荷归还池，零泄漏
  • 二级指针防 UAF：长跑进程 destroy 后立即 NULL，避免偶发重用已释放内存
  • cache 局部性：预分配 Ring 连续内存，cache line 预取友好；链表节点分散，TLB miss 频繁
  • 无锁 SPSC：单生产者单消费者场景 ring 用原子 + 内存序实现无锁，避免 mutex 抖动
  • 订单簿容器选型：价格档位用有序数组（bsearch）或专用结构，挂单量用链表，整体是混合容器

代码自测

题目 1： 以下代码有什么问题？

int *p = malloc(sizeof(int));
if (p) {
    *p = 42;
    p = malloc(sizeof(int));
    *p = 99;
}
参考答案

内存泄漏。第一次 malloc 的地址被第二次 malloc 覆盖，原来的内存无法 free。正确做法：先 free(p) 再重新赋值，或用不同的指针变量。每次 malloc 都必须保存指针以便后续 free——丢失指针 = 泄漏。

题目 1： 以下代码在 C 语言中能编译吗？说明了 C 的什么特性？

#include <stdio.h>
int main() {
    printf("hello\n");
}
参考答案

能编译。C 是编译型语言——源代码经过预处理、编译、汇编、链接四个阶段生成可执行文件。这个程序体现了 C 的基本结构：包含头文件、main 函数入口、标准库函数调用。C 的设计哲学是"信任程序员"——它不会像 Java 那样强制检查很多东西。
