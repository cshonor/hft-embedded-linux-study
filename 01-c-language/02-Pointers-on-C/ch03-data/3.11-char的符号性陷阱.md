# 3.11 char 的符号性陷阱

> 补充小节 · 跨平台 / 内核 / 嵌入式高频坑点

## char 不是"字符"，是 1 字节整数

C 语言里 `char` 是**最小可寻址存储单元**，标准强制保证 `sizeof(char) == 1`（C11 §6.5.3.4p4）——"1 字节"的定义就是 `sizeof(char)`，这是 C 标准里唯一锁死大小的类型。它只是经常拿来存 ASCII 字符，本质上是 8 bit 的整数，符号性**由编译器实现定义**（implementation-defined），标准不规定它是 `signed` 还是 `unsigned`。

## char、signed char、unsigned char 是三种不同的类型

C 标准（C11 §6.2.5p15）明确规定这是**三种独立类型**：

```c
char        c1;  // 独立类型，符号性由实现定义
signed char c2;  // 明确有符号，-128 ~ 127
unsigned char c3; // 明确无符号，0 ~ 255
```

- 即使某个平台上 `char` 表现得和 `signed char` 一样，**类型上它们依然不同**
- 三者 `sizeof` 全部是 1，只是符号属性不同
- 实际影响：
  - `_Generic` 类型选择会区分三者（`_Generic(c1, char: 1, signed char: 2, unsigned char: 3)` 三个分支都有效）
  - 严格别名规则中三者都属于"字符类型"，`char *`、`signed char *`、`unsigned char *` 都可合法别名任何对象
  - C++ 重载 `f(char)` 和 `f(signed char)` 是两个不同函数
- 类似的独立类型还有：`int` / `signed int` 是同一类型，但 `char` 家族三兄弟不是

## 最大坑：char 的符号不固定

| 平台 | `char` 默认等价于 | 范围 |
|------|------------------|------|
| x86-64（gcc） | `signed char` | -128 ~ 127 |
| **ARM / AArch64（gcc）** | **`unsigned char`** | **0 ~ 255** |
| x86-64（MSVC） | `signed char` | -128 ~ 127 |

> 同一个 `char` 变量，在 x86 和 ARM 上符号位行为不一样，直接写跨平台代码会出现诡异 bug。内核大量跑在 ARM，这是真实踩坑点。

**树莓派 5 = AArch64 (ARM)**，`char` 默认无符号；PC 是 x86，默认有符号。

## 会出 bug 的例子

```c
char c = 0xFF;
if (c > 0) {
    // ARM：char 是 unsigned，0xFF = 255 > 0，条件成立 ✅
    // x86：char 是 signed，0xFF 是 -1，条件不成立 ❌
}
```

一模一样的代码，两个平台结果相反。内核、驱动、报文解析经常踩这个坑。

### 更隐蔽的版本：符号扩展

```c
char c = 0x80;       // ARM: 128   x86: -128
int  i = c;          // ARM: 128   x86: 0xFFFFFF80 = -128（符号扩展）

unsigned char uc = 0x80;
int  j = uc;         // 两平台都是 128（零扩展，行为一致）
```

`signed char` 在提升到 `int` 时做**符号扩展**，高位全填 1；`unsigned char` 做**零扩展**，高位全填 0。如果你在解析二进制报文时用裸 `char` 读字节，x86 上负值字节会符号扩展成一个巨大的负 int，**解析数据静默出错**——不 crash、不报错，但每个字段拿到的值都是错的。这比崩掉危险得多：你以为程序跑通了，实际在拿垃圾数据做决策。

## 工程正确写法

| 需求 | 应该写 | 不要写 |
|------|--------|--------|
| 有符号 1 字节 | `signed char` | `char` |
| 无符号 1 字节（缓冲区、寄存器、报文、硬件字节） | `unsigned char` | `char` |
| 跨平台定宽 1 字节 | `int8_t` / `uint8_t` | `char` |

```c
#include <stdint.h>

// 内核 / 嵌入式 / DPDK 标准写法
uint8_t  byte_val;    // 硬件字节、报文、缓冲区
int8_t   signed_val;  // 明确有符号
```

> 内核源码里，处理硬件缓冲区、寄存器字节，普遍用 `uint8_t`，不直接用 `char`。

## 内核源码中的实践

Linux 内核通过 `-funsigned-char` 编译选项强制 `char` 为无符号，消除跨平台歧义。但应用层和驱动代码没有这个保护，必须显式写 `unsigned char` 或 `uint8_t`。

```c
// DPDK rte_byteorder.h — 明确用 uint8_t
#include <stdint.h>
static inline uint8_t rte_bswap16(uint16_t v) {
    return (uint8_t)((v >> 8) | (v << 8));
}
```

## 为什么标准不规定 char 的符号

C 标准把 `char` 符号性留给实现定义，是因为不同 CPU 架构的"最自然"的字节加载指令不同：

- x86 的 `movsx`（带符号扩展）和 `movzx`（零扩展）都可用，但 gcc 选择了 `signed char`
- ARM 的 `ldrb`（零扩展加载）是最自然的字节加载指令，所以 gcc 选择 `unsigned char`

标准不强制，是为了让编译器在每个平台上生成最自然的代码。代价就是跨平台 bug。

## 赋值放不进范围：实现定义行为，不是 UB

一个容易混淆的点：`char c = 200;`（当 `char` 是 `signed char` 时）**不是溢出，也不是 UB**。

| 行为类别 | 标准出处 | 含义 | 例子 |
|---------|---------|------|------|
| **实现定义**（implementation-defined） | C11 6.3.1.3 | 值无法被目标类型表示时，结果由实现决定，但**必须文档化**、可预测 | `char c = 200;`（signed char 平台）→ gcc 补码回绕为 -56 |
| **未定义**（UB） | C11 3.4.3 | 标准不做任何保证，编译器可以为所欲为 | `INT_MAX + 1`（有符号算术溢出） |
| **明确行为**（well-defined） | C11 6.2.5p9 | 无符号运算溢出按 mod 2^N 回绕 | `unsigned char c = 200 + 200;` → 400 % 256 = 144 |

区别很重要：实现定义行为**每个实现都得文档化、可预测**，gcc 文档 `Implementation-defined behavior` 章节明确写了 signed 转换回绕规则。UB 是"编译器可以为所欲为"——`-O2` 下可能直接删掉你的代码。

所以 `char c = 200` 在 x86（signed）上**必然**输出 -56（gcc 文档保证），不是"碰巧"或"可能崩"。

## 自测题

### Q1: 树莓派 5 上的 char

```c
char x = 0xFE;
printf("%d\n", x);
```

> 在树莓派 5（AArch64）上输出什么？在 x86 PC 上呢？

<details>
<summary>答案</summary>

- **树莓派 5（ARM）**：`char` 默认 unsigned，`0xFE` = 254，输出 `254`
- **x86 PC**：`char` 默认 signed，`0xFE` = -2（254 - 256），输出 `-2`

同一行代码，两个平台输出不同。这就是为什么不能用裸 `char` 做跨平台字节操作。

</details>

### Q2: 报文解析 bug

```c
char buf[4] = {0x00, 0x01, 0x82, 0x03};
//                ↑     ↑     ↑     ↑
//              字段0  字段1  字段2  字段3

if (buf[2] > 0x80) {
    printf("字段2 超过 128\n");
}
```

> 这段代码在 x86 和 ARM 上行为一样吗？

<details>
<summary>答案</summary>

**不一样。**

- **ARM**：`buf[2]` = `0x82` = 130，`130 > 0x80(128)` → **成立**，打印
- **x86**：`buf[2]` = `0x82` = -126（signed char），`-126 > 128` → **不成立**，不打印

**修复**：把 `char buf[]` 改成 `unsigned char buf[]` 或 `uint8_t buf[]`。

</details>

### Q3: 符号扩展

```c
char c = 0xFF;
int i = (int)c;
```

> 在 x86 上 `i` 的值是多少？如何让两平台行为一致？

<details>
<summary>答案</summary>

- **x86**：`c` = -1（signed char），提升到 int 做**符号扩展** → `i` = `0xFFFFFFFF` = -1
- **ARM**：`c` = 255（unsigned char），提升到 int 做**零扩展** → `i` = 255

**统一方法**：用 `unsigned char` 或 `uint8_t`，两平台都做零扩展，`i` = 255。

</details>

### Q4: 三种 char 类型

```c
printf("%zu %zu %zu\n",
       sizeof(char), sizeof(signed char), sizeof(unsigned char));
```

> 输出什么？三者是同一类型吗？

<details>
<summary>答案</summary>

输出 `1 1 1`。

但三者**不是同一类型**——C11 §6.2.5p15 规定 `char`、`signed char`、`unsigned char` 是三种独立类型。`sizeof` 相同只是因为标准强制 `sizeof(char) == 1`，另两者同为 1 字节。

类型差异在 `_Generic`、C++ 重载、复合类型推导中都会体现。符号性上 `char` 与 `signed char` 或 `unsigned char` 之一**表现相同**，但类型上永不等同。

</details>

---

## 总结一句话

**裸 `char` 是跨平台炸弹。内核 / 嵌入式 / 报文解析一律用 `uint8_t`，需要负数用 `int8_t`。**
