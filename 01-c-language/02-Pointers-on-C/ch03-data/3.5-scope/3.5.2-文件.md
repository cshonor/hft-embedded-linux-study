# 3.5.2 文件

## 本节讲什么

**文件作用域(file scope)**:在所有函数外声明的标识符,从声明点到该翻译单元末尾可见。它是"全局变量"和"模块私有"的所在,也是 `extern` 跨文件共享、`static` 文件级隔离的主战场。本节讲文件作用域的边界、与链接的配合、以及工程上"头文件 extern + .c 定义"的规范根因。

## 要点

### 文件作用域的边界

```c
/* foo.c */
#include "foo.h"
int g_count = 0;              /* 文件作用域, 从此点到文件末可见, 外部链接 */
static int s_hidden = 0;      /* 文件作用域, 内部链接, 其他 .c 不可见 */
static void helper(void){}    /* 文件作用域函数, 内部链接 */

void foo_api(void){           /* 文件作用域函数, 外部链接 */
    g_count++;                /* 可见 */
}
/* 文件结束: 上述符号作用域终止 */
```

- 起点在"声明点",不是文件开头 —— 这是 `#include` 顺序敏感的根源
- 函数名也是文件作用域(或块作用域,块内声明)

### 修饰符与链接

| 写法 | 链接 | 可见性 |
|------|------|--------|
| `int g;`(文件域,无 static) | **外部**(external) | 其他 `.c` 可 `extern int g;` |
| `static int s;`(文件域) | **内部**(internal) | 仅本文件 |
| `extern int g;`(文件域) | 引用别处定义,链接同原定义 | 跨文件共享 |

- **extern 是声明不是定义**:不分配存储,只告诉编译器"这个名字在别处定义,链接器会找到"
- **定义全局唯一**:否则链接器报 `multiple definition of 'g'`(现代 ld `-fno-common` 默认)

### static 隔离的失败在哪一步?

static 变量是内部链接,别的 .c 访问不到。具体在编译还是链接阶段报错,取决于你写没写声明——口诀:**没声明 = 编译错;声明了但链接不到 = 链接错**。详见 [3.6.2 内部链接](./../3.6-linkage/3.6.2-内部链接.md)。

### 先声明后使用(Quiz 常考点)

文件作用域的可见性**从声明点开始**,不是从文件开头:

```c
static void helper(void);         /* 原型放文件顶部 —— 工程惯例 */

void early(void){
    helper();                     /* 合法: 原型已声明 */
}

static void helper(void){ ... }   /* 定义在后面 */
```

- 不放原型,写在 helper **定义之前**的函数直接调它 → 编译错(未声明的标识符)
- 所以 static 函数的原型统一放 .c 顶部(或模块私有头文件),定义顺序就自由了

### 两种 static 总对比(块内 vs 文件级)

| | 块内 static(函数里) | 文件级 static(函数外) |
|---|---|---|
| 作用域 | 仅函数 `{}` 内 | 整个 .c(翻译单元) |
| 链接 | 无(none) | **内部**(internal,别的 .c 链接不到) |
| 存储期 | 静态(.bss/.data) | 静态(.bss/.data) |
| 初始化 | 程序启动前,仅一次,必须常量表达式 | 同左 |
| static 改了什么轴 | **存储期**(自动→静态) | **链接**(外部→内部) |
| 作用域轴 | 没碰,仍是块 | 没碰,仍是文件 |
| 典型用途 | 函数级单例、跨调用计数器 | 模块私有函数/变量,防符号冲突 |
| 风险 | 多线程共享,数据竞争 | 同样多线程共享;还有"看似隔离实则全局状态"的设计味道 |

### 跨文件共享的规范模式

```c
/* foo.h —— 公共声明 */
#ifndef FOO_H
#define FOO_H
extern int g_count;            /* 声明, 不分配 */
void foo_api(void);
#endif

/* foo.c —— 定义 */
#include "foo.h"
int g_count = 0;               /* 定义, 唯一 */
void foo_api(void){ g_count++; }

/* bar.c —— 使用 */
#include "foo.h"               /* 拿到 extern 声明 */
void bar(void){ g_count++; }   /* 引用同一对象 */
```

> **铁律**:头文件只放 `extern` 声明,定义放 `.c`。这是 C 工程"防止重复定义/符号冲突"的标准模板,见 3.6。

### 与块作用域的区别(全/局部变量)

```c
int g = 1;                     /* 文件作用域, 静态存储期, 外部链接 */
void f(void){
    int x = 2;                 /* 块作用域, 自动存储期, 无链接 */
    g = x;                     /* 块内可见文件作用域的 g */
}
```

- 文件作用域对象**静态存储期**:活到程序结束,进 `.data/.bss`
- 文件作用域 + static = 内部链接(模块私有)

## 与 HFT/DPDK

### 模块私有(static 文件级)

```c
/* netdev.c */
static rte_spinlock_t g_tx_lock;        /* 模块私有, 不导出符号 */
static int tx_pending = 0;              /* 模块状态 */
static int tx_flush(void){ ... }        /* 私有实现 */

/* netdev.h —— 只暴露 API */
int netdev_send(const uint8_t *pkt, size_t len);
```

- DPDK/驱动靠 static 把实现细节藏在 `.c`,只头文件暴露 API —— "C 的对象式封装"
- `nm netdev.o` 看到 `t`(小写)而非 `T`(大写)= 内部链接符号

### 全局配置共享(extern)

```c
/* config.h */
extern struct config g_config;          /* 声明 */

/* config.c */
struct config g_config = {              /* 唯一定义 */
    .port = 8000,
    .workers = 4,
};

/* 任意 .c include config.h 后直接用 g_config */
```

### 全局变量的并发陷阱

```c
/* 反例: 全局可变状态 + 多线程 */
int g_seq = 0;
void on_pkt(void){ g_seq++; }   /* 数据竞争, UB —— 即使"看起来对" */

/* 正解: _Atomic 或 per-thread */
_Atomic int g_seq = 0;          /* C11 原子 */
thread_local int t_seq = 0;     /* 每线程独立 */
```

- 文件作用域全局可变状态是多线程 bug 头号源:HFT 多核收包场景必须 `_Atomic` / per-thread / 无锁结构
- 全局**只读**配置(const)安全,可全局共享

### 初始化顺序问题

```c
/* a.c */ int a_init = read_a();
/* b.c */ int b_init = read_b_based_on(a_init);  /* a_init 可能未初始化 */
```

- 跨翻译单元的全局 static 初始化**顺序未定义**(C 不像 C++ 有跨 TU 动态初始化,但 const 表达式顺序无关;有副作用的初始化要小心)
- HFT 工程倾向"启动时显式 init() 调用",不依赖全局构造顺序

## 常见误区

| 误区 | 真相 |
|------|------|
| `extern int g;` 分配存储 | 不,是声明,引用别处定义 |
| 全局变量所有 .c 自动可见 | 不,要 extern 声明或 include 头文件 |
| 头文件写 `int g;` 没事 | 多个 .c include 后重复定义,**链接器**报错(编译都能过) |
| 头文件写 `static int g;` 安全 | 合法不报错,但每个 .c 各一份独立副本,共享失败 |
| static 全局"更安全" | 只改链接,不改线程安全;并发仍需同步 |
| 函数默认无原型也能调 | C99 起隐式声明非法,见 3.2.4 |

## 实操

```bash
# 多文件 extern / static 链接实验
cat > a.c <<'EOF'
#include <stdio.h>
int shared = 42;            /* 定义, 外部链接 */
static int priv = 1;        /* 定义, 内部链接 */
void show(void){ printf("shared=%d priv=%d\n", shared, priv); }
EOF
cat > b.c <<'EOF'
extern int shared;          /* 引用 a.c 的 shared */
extern void show(void);
int main(void){ shared++; show(); return 0; }
EOF
gcc a.c b.c -o ab && ./ab          # shared=43 priv=1
nm a.o | grep -E 'shared|priv'    # T shared, t priv(大小写区分链接)
nm ab | grep -E 'shared|priv'     # priv 不出现在最终符号表(已被 strip 或 local)
```

## 代码自测

**题目 1：** 以下两个文件一起编译会有什么问题？
```c
// file1.c
static int count = 0;
// file2.c
static int count = 0;
```

<details>
<summary>参考答案</summary>

没有问题。static 修饰文件作用域变量时，该变量只在当前文件可见（内部链接）。两个文件各有一个独立的 count，互不影响。这正是 static 的文件作用域用途——实现信息隐藏，避免命名冲突。

</details>

**题目 2：** `static void helper(void)` 定义在 .c 文件中部，写在它**前面**的函数能不能直接调用 helper？为什么？怎么解决？

<details>
<summary>参考答案</summary>

不能。文件作用域的可见性从**声明点**开始，前面的函数调用 helper 时编译器还没见过这个名字，报 `'helper' undeclared`。解决：在 .c 文件顶部（或模块私有头文件）放原型 `static void helper(void);`，定义顺序就自由了。这正是工程惯例"static 函数原型统一放 .c 顶部"的根因。

</details>

**题目 3：** 头文件写 `static int g = 0;` 被 3 个 .c include，会报错吗？每个文件看到的 g 是同一个对象吗？

<details>
<summary>参考答案</summary>

不报错——每个翻译单元各拿一份独立副本，互不冲突。但"共享失败"：3 个文件各改各的 g，数据不互通。这是头文件写 static 定义的隐蔽坑。失败阶段详见 [3.6.2 内部链接](./../3.6-linkage/3.6.2-内部链接.md)。

</details>
