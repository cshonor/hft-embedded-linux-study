# 3.2.3 声明指针

## 本节讲什么

指针声明的语法本身不难,但**const 与指针的四种组合**、**restrict 的承诺语义**、**volatile 指针的访存语义**这三块是声明语法中最容易写错且最难调试的。本节把这些限定符在指针声明中的位置讲透,给出 HFT/驱动场景的标准写法和反例。

## 要点

### const 与指针:右左法则四种组合

```c
const int *p;           /* p 可改, *p 不可改 —— 指向 const int */
int *const q = &x;      /* q 不可改, *q 可改 —— const 指针指向 int */
const int *const r=&x;  /* 都不可改 */
int *p;                 /* 都可改 */
```

**记忆口诀**:"const 在 `*` 左边修饰**指向物**,在右边修饰**指针本身**"。`const int *p` 和 `int const *p` 完全等价。

> 没有顶层 const 的指针赋给顶层 const 指针是安全的(只读视角扩展);反过来要去掉 const 要显式强转且是 UB 倾向。

### 工程写法

```c
/* 只读报文入参 —— 标准 API 风格 */
void parse(const uint8_t *pkt, size_t len);

/* 只读配置表 —— 整表进 .rodata */
const struct cfg g_cfg;            /* const 数据 + 非 const 指针 */
const struct cfg *g_cfg_ptr;       /* 指针可改, 内容只读 */

/* 返回只读字符串: 调用者拿到 const char*, 改它即 UB */
const char *name(void);

/* 需要改指针本身又不改数据: int *const p = arr; */
```

### volatile 指针:每次必访存

```c
volatile uint32_t *reg = (volatile uint32_t *)0xFE000000U;
*reg = 1;            /* 每次"写"都真到内存, 不进寄存器, 不合并 */
uint32_t v = *reg;   /* 每次"读"都从硬件取, 不复用上次值 */
```

- 编译器对 volatile 访问:**禁止寄存器化、禁止消除冗余访问、禁止重排到该访问另一侧**(对单变量)
- **注意**:volatile **不保证**内存序 / 可见性 / 原子性。线程同步要 `_Atomic`(C11)或 `rte_atomic`/`stdatomic.h`,不要用 volatile

### restrict:唯一访问路径承诺(C99)

```c
void copy(uint8_t *restrict dst, const uint8_t *restrict src, size_t n);
```

- 程序员向编译器承诺:**在 n 范围内,通过 dst 写入和通过 src 读取的对象没有重叠**
- 编译器据此可:① 把循环向量化(SIMD) ② 重排读写顺序 ③ 复用寄存器,不必每次重新载入
- **承诺不成立 → UB**,数据损坏且难复现

### 何时该用 restrict

| 场景 | 该不该加 restrict |
|------|-------------------|
| 内存拷贝 / 加密 / 求和等"两缓冲独立"热点 | 该加 |
| 协议解析入参 `const uint8_t *pkt` 单指针 | 加价值不大(只读) |
| 同一指针既读又写(`*p += ...`) | 无意义(本来就同源) |
| 不确定是否别名 | **别加**,宁可慢也别 UB |

## 汇编证据:restrict 解锁向量化

```c
void add(int *restrict a, int *restrict b, int *restrict c, int n){
    for (int i=0;i<n;i++) c[i]=a[i]+b[i];
}
```

- 无 restrict:编译器假设 `c` 可能与 `a`/`b` 别名,每次循环要重新载入 a/b
- 有 restrict:`-O3 -march=native` 可向量化为 `paddd`(SSE/AVX)一次算 4/8 个 int

```bash
gcc -O3 -S -ftree-vectorize add.c   # 看 .LBB 里的 paddd 指令
# 无 restrict 版同样命令, 多见标量 addl 循环
```

## 与 HFT/DPDK

### restrict 在 DPDK rte_memcpy

```c
/* DPDK 简化版 */
static inline void rte_memcpy(void *restrict dst, const void *restrict src, size_t n);
```

- 报文拷贝是热路径,restrict 让编译器用宽寄存器(YMM/ZMM)向量化
- 自己写热路径聚合函数也应加 restrict,**前提是真的没别名**

### MMIO 寄存器映射(volatile)

```c
#define NIC_BASE 0xFB000000U
static volatile uint32_t * const NIC_TX = (volatile uint32_t *)NIC_BASE;
*NIC_TX = 0x1;          /* 触发发送: 必须真写设备, 不能合并 */
while (!(*NIC_RX_STAT & 0x10)) ;  /* 轮询完成位: 每次真读 */
```

- 设备寄存器必须 volatile,否则编译器会把轮询循环优化成"读一次存寄存器"
- 写顺序敏感时还需 `__sync_synchronize()` / `rte_smp_wmb()` 等内存屏障

### 函数指针与多级指针预告

```c
void (*handler)(const uint8_t *, size_t);   /* 函数指针, ch06/ch13 展开 */
int **pp;                                   /* 多级指针, ch06 */
```

## 常见误区

| 误区 | 真相 |
|------|------|
| `const int *p` 中 p 是 const | p 可改,指向物只读;const 在 `*` 左 |
| `int *const p = arr;` 之后 `p[0]=1` 是 UB | 不是,`*p` 可改;只是 p 不能改指向 |
| volatile 能做自旋锁 | 不能,只保证访存,不保证原子/序 |
| restrict 是性能开关,加了一定快 | 承诺成立才快;承诺不成立是 UB |
| `void *p; *p=...;` 合法 | void* 不能解引用,要先转具体类型 |
| const 指针解引用赋给非 const 指针安全 | 反向赋值要去 const,UB 倾向 |

## 实操

```bash
# 1. restrict 触发向量化对比
cat > t.c <<'EOF'
void add_r(int *restrict a,int *restrict b,int *restrict c,int n){
  for(int i=0;i<n;i++) c[i]=a[i]+b[i];
}
void add_n(int *a,int *b,int *c,int n){
  for(int i=0;i<n;i++) c[i]=a[i]+b[i];
}
EOF
gcc -O3 -S -ftree-vectorize t.c -o t.s
grep -E 'paddd|addl' t.s | head   # 看 restrict 版是否有 paddd

# 2. volatile 防止循环被消除
cat > v.c <<'EOF'
volatile int *flag = (int*)0x1000;
void wait(void){ while(!*flag) ; }
EOF
gcc -O2 -S v.c -o v.s
# 无 volatile: while(!flag) 会被简化为"读一次循环或死循环"
# 有 volatile: 每轮重新读 *flag
```

## 代码自测

**题目 1：** 以下代码有什么问题？
```c
int *p;
*p = 10;
```

<details>
<summary>参考答案</summary>

p 未初始化，指向随机地址。解引用未初始化的指针是未定义行为——可能 segfault，也可能修改了其他变量的值（更危险）。正确做法：先让 p 指向有效内存，如 int x; int *p = &x; *p = 10;。

</details>
