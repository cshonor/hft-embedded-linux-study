# 3.2.4 隐式声明

## 本节讲什么

**隐式声明(implicit declaration)** 是 K&R 时代的遗产:调用一个没有原型的函数时,编译器默认它"返回 int、参数类型从调用处推断"。C89 仍允许,C99 起**非法**。这一节短,但它是 C 历史中最阴险的 bug 来源之一 —— 现代 HFT 工程必须彻底杜绝,且工程上有具体的编译开关保证。

## 要点

### 历史与演进

| 时代 | 隐式声明 | 含义 |
|------|----------|------|
| K&R / C89 | 允许 | 调用无原型函数 → 默认返回 int、参数按整型提升 |
| C99 | **非法** | 调用前必须有可见原型,否则约束违反/报错 |
| C11/C17/C23 | 同 C99 | 隐式声明彻底退出标准 |

### 隐式声明的危害

```c
/* 旧式隐式声明灾难 */
double sqrt_x;            /* 漏写 #include <math.h> */
sqrt_x = sqrt(16.0);     /* 隐式假定返回 int → 截断/栈错乱 */
```

- 编译器假设 `sqrt` 返回 `int`,把 double 的位模式当 int 处理 → 数值错误甚至崩溃
- x86-32 时代:float/double 返回在 FPU 寄存器,而 int 返回在 EAX —— ABI 不匹配直接得到垃圾
- 参数同样:传 `double` 给"假定的 int 形参" → 栈布局错乱

### 为什么危险——追到 ABI 层面

隐式声明的真正危害不在"类型不匹配"这四个字,而在于**类型不匹配后,C 调用约定(ABI)在物理层面做了错误的事**。追到寄存器级别才能看清。

**函数返回值走哪条路,由返回类型决定:**

| 返回类型 | x86-64 返回位置 | x86-32 返回位置 |
|---------|----------------|----------------|
| `int` / `long` / 指针 | RAX | EAX |
| `double` / `float`(SSE) | XMM0 | FPU ST0(x87) |
| `struct` ≤ 16 字节 | RAX:RDX | EAX:EDX |
| `struct` > 16 字节 | 调用方分配内存,隐式传指针(RDI) | 同左 |

> 参考: System V AMD64 ABI §3.2.2; x86-32 System V ABI §3.2.2。

**隐式声明发生后,调用方和被调用方对"返回值在哪个寄存器"产生了分歧:**

```c
/* 漏 #include <math.h>，编译器隐式声明 sqrt 返回 int */
double x = sqrt(16.0);
```

| 角色 | 认为返回类型 | 去哪取返回值 | 实际拿到 |
|------|-------------|-------------|---------|
| 调用方(main) | `int`(隐式) | RAX | RAX 里的残留垃圾 |
| 被调用方(sqrt) | `double`(真实) | XMM0 | 4.0(正确) |

`sqrt` 把 4.0 写进 XMM0,但 main 去 RAX 取——RAX 里的内容是上一个函数调用留下的**随机位模式**,被当 `int` 读出来后再赋给 `double x`,结果完全不可预测。

**参数方向同理**——隐式声明下参数走"默认整型提升"(C89 §6.5.2.2¶6):
- `float` → 提升为 `double`
- `char` / `short` → 提升为 `int`

调用方按提升后的类型压栈(或放寄存器),被调用方按真实原型取值。如果真实函数期望 `float`,调用方却传了提升后的 `double` → **位宽和编码都不同**,取出来的值是垃圾。

**总结:隐式声明的危害不是"编译器报了个 warning",而是调用方和被调用方在 ABI 层面彻底对不上——返回值取错寄存器、参数布局错位,从二进制层面就是错的。** 只是碰巧在某些简单情况下(比如真实返回 int、参数都是 int)看起来能跑,一旦返回类型或参数类型不匹配,就是 UB。

### K&R 老式函数定义(顺手区分)

```c
/* K&R 老定义: 参数类型在函数头外单独声明 */
int add(a, b)
    int a, b;       /* 老式参数声明 */
{
    return a + b;
}
/* 现代(C89+)原型定义 */
int add(int a, int b){ return a+b; }
```

- K&R 定义不写原型,调用时整型提升 → 类型检查弱化
- 现代 HFT 代码**绝无**这种写法,但读老驱动(如早期 Linux 内核)会碰到

### 现代工程规范

```bash
# CFLAGS/CXXFLAGS 必备:
-Wall -Wextra -Wpedantic
-Werror=implicit-function-declaration   # 把隐式声明当错误
-Werror=implicit-int
-Wmissing-prototypes                      # 要求 static 函数有前置原型
-Wstrict-prototypes                       # 禁止 K&R 风格定义
```

- 每个 `.c` 包含自己对应的 `.h`(`foo.c` 第一行 `#include "foo.h"`)—— 让头文件原型与定义一致由编译器校验
- 头文件里写**完整原型**`void parse(const uint8_t *pkt, size_t len);`,别省参数名

## 与 HFT/DPDK

### 驱动 API 严格原型

```c
/* DPDK ethdev 头文件, 完整原型 + 参数名文档化 */
int rte_eth_rx_burst(uint16_t port_id, uint16_t queue_id,
                     struct rte_mbuf **rx_pkts, const uint16_t nb_pkts);
```

- 现代驱动框架靠**函数指针表**(`struct eth_dev_ops`)分发,每个回调都是带完整原型的 typedef
- 漏原型 → 函数指针类型不匹配,某些 ABI 下崩,某些下"恰好工作"难复现

### 跨 .c 文件调用

```c
/* module_a.c 调用 module_b.c 的函数 */
#include "module_b.h"     /* 必须包含, 让原型可见 */

/* 反例: 直接调用而不 include, 编译器隐式声明返回 int */
void use_b(void){ b_func(); }   /* C99 报错;旧版隐式 int */
```

### 警告升级为错误

HFT/嵌入式团队常在顶层 CMakeLists 写:

```cmake
add_compile_options(-Werror=implicit-function-declaration
                    -Werror=implicit-int
                    -Wmissing-prototypes)
```

让任何遗漏原型都直接构建失败,而不是"过几天偶发崩溃"。

## 常见误区

| 误区 | 真相 |
|------|------|
| 隐式声明只是警告,可忽略 | C99 起是约束违反,行为未定义;迟早出 bug |
| `printf(3.14)` 没事 | 漏 `#include <stdio.h>` 时 printf 隐式声明返回 int,传 double 给"假定的 int 形参"→ UB |
| 老式 K&R 定义和现代原型等价 | 不等价;K&R 不做参数类型检查,整型提升生效 |
| 函数返回 int 可以不写原型 | C99 起仍需原型;省原型=隐式声明,UB |
| `-Wall` 就够了 | 隐式声明默认只是 warning,要 `-Werror=implicit-function-declaration` 才会失败 |

## 实操

```bash
# 1. 观察隐式声明的危害
cat > t.c <<'EOF'
#include <stdio.h>
int main(void){
    printf("%g\n", sqrt(2.0));   /* 漏 #include <math.h> */
    return 0;
}
EOF
gcc -std=c11 t.c -o t -Wall      # 报 implicit declaration warning
gcc -std=c11 -Werror=implicit-function-declaration t.c   # 直接失败

# 2. 漏原型导致 ABI 错乱(x86-32 时代经典, 64 位仍可演示)
cat > k.c <<'EOF'
double half(double x){ return x/2; }   /* 定义 */
/* 漏原型 */
int main(void){ printf("%g\n", half(10)); }
EOF
gcc -std=c89 k.c -o k -Wall && ./k   # warning, 结果可能错误
# 加原型:
sed -i '1i double half(double);' k.c && gcc -std=c89 k.c -o k && ./k
```

## 代码自测

**题目 1：** 以下代码在 C89 和 C99 中分别会有什么结果？
```c
int x = f(3);
// f 未声明
```

<details>
<summary>参考答案</summary>

C89：编译器假设 f 返回 int，产生隐式声明警告。如果 f 确实返回 int 则能工作；否则是 UB。C99 起：隐式函数声明是错误的，编译会失败。正确做法：始终 #include 对应头文件或显式声明函数原型。

</details>
