# 3.1.3 指针

## 本节讲什么

指针作为一种**数据类型**：它存的是**地址**，有**指向类型**。本节只从类型层面预告指针——完整的指针体系（`&`/`*`、间接访问、指针运算、野指针）在 **ch06** 展开。这里建立三个基础认知：指针的位宽、指针类型决定什么、限定符与指针的组合。

## 指针的类型层面

```c
int *p;              /* 指向 int 的指针 */
const char *s;       /* 指向只读 char 的指针 */
void *generic;       /* 泛型指针，使用前需 cast */
struct rte_mbuf *mbuf; /* 指向 struct rte_mbuf 的指针 */
int **pp;            /* 指向 int 指针的指针（二级指针） */
```

### 指针的两个组成部分

| 组成 | 说明 |
|------|------|
| **地址值** | 一个整数，表示内存位置（64 位系统通常 48 位有效） |
| **指向类型** | 告诉编译器"这个地址存的是什么类型的对象" |

> `int *p` 和 `char *q` 都占 8 字节（64 位），存的地址值格式相同，但**指向类型不同**——这是它们行为不同的根本原因。

## `sizeof(指针)` 与指向类型无关

**核心原则：地址本身是一个数字，这个数字的宽度（32/64 位）和"指针指向什么类型"是两件完全不相干的东西。**

### 两个概念拆开

| 概念 | 决定什么 | 由什么决定 |
|------|---------|-----------|
| **指针变量本身的存储宽度** | 地址数字占几字节 | **编程模型（ABI）**：LP64/LLP64 = 8 字节，ILP32 = 4 字节 |
| **指向类型（`*` 前面的类型）** | 解引用读几字节、`p++` 步长多大 | 你写的类型名：`uint8_t*`→1、`uint32_t*`→4、`uint64_t*`→8 |

```c
/* 64 位系统：所有指针变量本身都是 8 字节，不管指向什么 */
uint8_t  *p8;
uint32_t *p32;
uint64_t *p64;

sizeof(p8)  == 8;   /* 不是 1！p8 本身存的是 64 位地址 */
sizeof(p32) == 8;   /* 不是 4！p32 本身存的是 64 位地址 */
sizeof(p64) == 8;   /* 不是 8 因为指向 uint64_t，而是所有指针都是 8 */
```

`uint32_t *p32` 的含义：
- `p32`：指针变量，64 位，存内存地址
- `uint32_t`：p32 指向的那块内存里期望是什么类型——解引用读 4 字节，`p32++` 步长 +4

**不是说指针本身是 32 位**，而是"指向 4 字节数据对象的指针"。指针自身的地址宽度由 ABI 决定。

### 常见误区

| 误区 | 纠正 |
|------|------|
| `uint32_t *` 代表地址是 32 位 | **错**。`uint32_t *` = 指向 4 字节对象的指针；指针自身宽度由 ABI 决定（64 位系统全部 8 字节） |
| `uint64_t *` 比 `uint8_t *` 大 | **错**。同平台上所有指针一样大 |
| 64 位 CPU 一定 64 位指针 | **不精确**。决定指针宽度的是编程模型（ABI），不是 CPU。x86-64 上可以跑 x32 ABI（ILP32），CPU 是 64 位但指针只有 32 位。工程上"64 位 OS = 64 位指针"作为速记没问题 |

### cast 不改变地址宽度

```c
uint32_t *p32 = (uint32_t *)0x1000;
```

- `0x1000` 是整数字面量，64 位环境扩展成 `0x0000000000001000`
- `(uint32_t *)` **不是把地址截断成 32 位**——只是标记"这是一个指向 uint32_t 的指针"
- 地址数字不变，改变的是编译器的解读规则：`*p32` 读 4 字节，`p32++` 加 4

### 指针宽度由 ABI 决定

| 编程模型 | 典型平台 | 指针宽度 | `long` 宽度 |
|---------|---------|---------|------------|
| LP64 | 64 位 Linux/macOS | 8 字节 | 8 字节 |
| LLP64 | 64 位 Windows | 8 字节 | 4 字节 |
| ILP32 | 32 位 Linux / x32 ABI | 4 字节 | 4 字节 |

> 严格说"指针宽度由 CPU 架构决定"不精确——决定的是**编程模型（ABI）**。但所有 64 位数据模型（LP64/LLP64）指针都是 8 字节，所以"64 位 OS = 64 位指针"工程上够用。

### 取地址数值用 `uintptr_t`

```c
uint32_t *p32 = (uint32_t *)0x1000;
uintptr_t addr = (uintptr_t)p32;   /* 标准写法，宽度匹配本机指针 */
```

- `uintptr_t` 宽度和本机指针完全匹配：32 位平台 = 32 bit，64 位平台 = 64 bit
- **不要用 `uint32_t` 存 64 位系统的指针**——会截断地址高位，严重 bug
- 保证 round-trip 保真：`(void *)(uintptr_t)p == p`（C11 7.20.1.4）

### `uint64_t` vs `uintptr_t` vs `uint64_t *` 三者区分

这三个名字看着像，实际是**完全不同的三类东西**：

| 维度 | `uint64_t` | `uintptr_t` | `uint64_t *` |
|------|-----------|-------------|-------------|
| **类别** | 整数类型 | 整数类型（专为存地址设计） | 指针类型 |
| **干什么** | 存一个 64 位数字 | 存一个地址数值 | 指向一块 8 字节的内存 |
| **宽度** | 固定 8 字节 | 随平台变（32 位机 4 字节，64 位机 8 字节） | 随 ABI 变（LP64/LLP64 = 8 字节，ILP32 = 4 字节） |
| **和地址的关系** | 可以装下 64 位地址，但**标准不保证 round-trip** | **标准保证**能完整存取指针 round-trip | 本身**就是**地址，存的是内存地址 |
| **`++` 步长** | +8（整数加法） | +1（整数加法，和普通整数一样） | +8（`sizeof(uint64_t)` 指针算术） |
| **能转成指针吗** | 能，但 32 位平台上 `uint64_t` 比指针宽，转换 implementation-defined | 能，**标准推荐的整数↔指针桥梁** | 本身就是指针，不用转 |

**关键区分**：

```c
uint64_t   val  = 0x1000;    // 整数，存数字 0x1000
uintptr_t  addr = 0x1000;    // 整数，存地址数值 0x1000（宽度匹配本机指针）
uint64_t  *ptr  = (uint64_t *)0x1000;  // 指针，指向地址 0x1000 处的 8 字节数据
```

- `val` 和 `addr` 都是**整数**，不是指针。区别：`uintptr_t` 宽度永远等于本机指针宽度，`uint64_t` 固定 8 字节——在 64 位 LP64 上两者恰好一样宽，但语义不同
- `ptr` 是**指针**，宽度由 ABI 决定（LP64 = 8 字节），它指向的内存按 `uint64_t`（8 字节）解读
- 整数→指针的转换：`(uint64_t *)addr` 把整数当地址用，**不改变地址位数**，只是打标签

**易混点**：

```c
/* ❌ 错误理解：以为只有 uint64_t 才能转成指针 */
uint64_t *p = (uint64_t *)some_uint32;   // 能编译，但不是"因为 uint64_t 够宽"

/* ✅ 正确理解：整数→指针看的是"整数够不够宽能装下地址"，跟转成哪种指针无关 */
uintptr_t addr = 0x1000;      // 用 uintptr_t 保证宽度匹配
uint8_t  *p8  = (uint8_t *)addr;   // 可以转成 uint8_t*
uint32_t *p32 = (uint32_t *)addr;  // 可以转成 uint32_t*
uint64_t *p64 = (uint64_t *)addr;  // 可以转成 uint64_t*
// 三种都合法，地址数字不变，区别只是解引用宽度和步长
```

> **一句话**：`uint64_t` 是整数负责存数字，`uintptr_t` 是整数负责存地址（宽度自动匹配），`uint64_t *` 是指针负责指向 8 字节数据。整数存地址要够宽（用 `uintptr_t`）；转成哪种指针随便选，二者互不绑定。

### 整数转指针的本质：把数字当地址，类型决定怎么读数据

```c
uintptr_t addr = 0x1000;          // addr 是整数，值 0x1000
uint32_t *p = (uint32_t *)addr;   // 把 0x1000 当地址，p 指向这个地址
```

转换做了什么：
1. **把整数值当地址**——指针 `p` 里存的就是 `0x1000` 这个地址值
2. **类型标签决定解读**——之后 `*p` = 去内存地址 `0x1000` 那个地方，读 4 字节当 `uint32_t` 解读

```
内存地址:    0x1000  0x1001  0x1002  0x1003
             ┌───────┬───────┬───────┬───────┐
内存内容:    │ 0x78  │ 0x56  │ 0x34  │ 0x12  │
             └───────┴───────┴───────┴───────┘
               ↑                               ↑
              p 指向这里              读 4 字节到这里
              (*p 读 0x12345678，小端)
```

- `p` 存的地址 = `addr` 的整数值（`0x1000`），比特不变
- `*p` = 去这个地址读数据，读几个字节由指针类型决定（`uint32_t *` → 4 字节）
- `p++` = 地址加 `sizeof(uint32_t)` = 4，指向下一个 4 字节块

> 指针本质就是"存了一个地址，告诉你去那个地址读多大、怎么解读数据"。整数转指针 = 把数字当地址用，类型标签决定解读规则。

### `uintptr_t` 实际工作场景

什么时候需要把地址存成整数？指针不是已经存了地址吗——因为**有些操作只能用整数做，指针做不了**：

#### 场景 1：地址对齐判断（DPDK / 内核最常见）

```c
/* DPDK mbuf 数据区要求 64 字节对齐，检查缓冲区地址是否满足 */
void *buf = rte_pktmbuf_mtod(m, void *);

/* ❌ 指针不能直接做位运算 */
if ((buf & 0x3F) == 0) { ... }       /* 编译错误：指针不能 & */

/* ✅ 转成 uintptr_t 做位运算，判断低 6 位是否为 0 */
if (((uintptr_t)buf & 0x3F) == 0) {
    /* 64 字节对齐，可直接走 SIMD 向量解析 */
}
```

指针不支持 `&`、`|`、`%` 等位运算。想检查对齐、做地址掩码，**必须先转成整数**。`uintptr_t` 保证转换无损。

#### 场景 2：MMIO 寄存器地址（嵌入式 / 驱动）

```c
/* UART 寄存器映射在物理地址 0x09000000（树莓派5 PL011） */
#define UART_BASE  0x09000000

volatile uint32_t *uart = (volatile uint32_t *)UART_BASE;
/* 等价于 */
uintptr_t uart_addr = UART_BASE;
volatile uint32_t *uart = (volatile uint32_t *)uart_addr;

*uart = 'A';   /* 写一个字节到串口 */
```

嵌入式裸机 / 内核驱动里，硬件寄存器的物理地址是固定的整数（芯片手册写死），必须用整数→指针转换来访问。`uintptr_t` 在这里是中转容器。

#### 场景 3：日志 / 调试打印地址

```c
/* 调试时打印指针地址，用 PRIuPTR 保证格式跨平台匹配 */
#include <inttypes.h>

void debug_ptr(void *p)
{
    /* ❌ %lu 在 LLP64(Windows) 上指针 8 字节但 long 4 字节 → 格式不匹配 */
    printf("ptr = 0x%lx\n", (unsigned long)p);

    /* ✅ PRIxPTR 自动匹配 uintptr_t 的宽度 */
    printf("ptr = 0x%" PRIxPTR "\n", (uintptr_t)p);
}
```

`%lx` 在 LP64 上碰巧对，但 LLP64（Windows 64 位）上 `long` 是 4 字节、指针是 8 字节，格式不匹配。`PRIxPTR` / `PRIuPTR` 永远和 `uintptr_t` 宽度一致。

#### 场景 4：地址做哈希 / 比较

```c
/* 把指针地址存进哈希表做去重，需要整数做哈希 */
uint32_t hash_pointer(void *p)
{
    uintptr_t addr = (uintptr_t)p;
    /* FNV-1a 哈希，要求操作数是整数 */
    uint32_t hash = 2166136261u;
    for (int i = 0; i < (int)sizeof(uintptr_t); i++) {
        hash ^= (addr >> (i * 8)) & 0xFF;
        hash *= 16777619u;
    }
    return hash;
}
```

哈希函数、排序比较、位掩码——这些算法只认整数，指针做不了。

#### 四个场景的共同点

| 场景 | 为什么需要整数 | `uintptr_t` 的角色 |
|------|--------------|------------------|
| 对齐判断 | 指针不能位运算（`&` `\|`） | 中转：指针→整数→位运算 |
| MMIO 寄存器 | 硬件地址是固定数字 | 容器：整数→指针 |
| 日志打印 | `printf` 格式要匹配宽度 | 保证 `%`PRIxPTR 宽度一致 |
| 哈希/比较 | 哈希算法只认整数 | 中转：指针→整数→哈希 |

> **核心**：指针只能存地址、解引用、加减步长。但凡需要位运算、哈希、格式化打印，就必须转成整数——`uintptr_t` 就是那个"安全的中转容器"，宽度永远等于本机指针，转换无损可逆。

### 指针地址的有效位

- 64 位 Linux/x86：用户态地址通常 48 位有效（高 16 位是符号扩展）
- `0x7fff...` 是典型用户态地址范围
- 内核态地址高 16 位全 1（`0xffff...`）
- 详见 ch18 虚拟地址空间

## 指针类型决定什么

### 1. 解引用宽度

```c
int *pi = (int *)0x1000;
char *pc = (char *)0x1000;

*pi;    /* 从 0x1000 读 4 字节（int 宽度） */
*pc;    /* 从 0x1000 读 1 字节（char 宽度） */
```

- `int *` 解引用读 4 字节，`char *` 读 1 字节——类型决定读几个
- 类型错 → 读错字节数 → 数据错位或越界

### 2. 指针算术步长

```c
int arr[5] = {10, 20, 30, 40, 50};
int *p = arr;

p + 1;     /* 地址增加 sizeof(int) = 4 字节 → 指向 arr[1] */
p + 2;     /* 增加 8 字节 → 指向 arr[2] */
```

- `p + 1` 不是地址加 1，而是加 `sizeof(指向类型)`
- `int *` 步长 4，`char *` 步长 1，`struct big *` 步长可能很大
- **步长由指向类型决定**——这是指针算术的核心（ch06.13 详解）

```c
char *pc = (char *)arr;
pc + 1;    /* 只加 1 字节 → 指向 arr 的第 2 个字节 */
```

### 三种指针同一地址，行为天差地别

```c
uint8_t  *p8  = (uint8_t  *)0x1000;
uint32_t *p32 = (uint32_t *)0x1000;
uint64_t *p64 = (uint64_t *)0x1000;

/* 指针变量存的地址值一模一样，但类型不同 → 行为不同 */
*p8;     /* 从 0x1000 读 1 字节 */
*p32;    /* 从 0x1000 读 4 字节 */
*p64;    /* 从 0x1000 读 8 字节 */

p8++;    /* 地址 += 1 → 0x1001 */
p32++;   /* 地址 += 4 → 0x1004 */
p64++;   /* 地址 += 8 → 0x1008 */
```

指针变量内存存的值完全相同，但指针类型决定了解引用读几个字节、加减 1 移动多远。

### 报文解析的双重 UB 陷阱

```c
/* ❌ DON'T — 双重 UB */
uint8_t buf[64];
uint32_t val = *(uint32_t *)(buf + 4);   // 直接 cast + 解引用
```

这写法在 HFT 语境下有两个问题：

1. **未对齐访存**：`buf + 4` 如果不是 4 字节对齐的地址（`buf` 来自 `malloc` + 偏移很常见），ARM 直接 `SIGBUS`，x86 吃缓存行 split 性能惩罚
2. **严格别名违例**（C11 6.5p7）：`uint8_t*` 指向的内存按 `uint32_t` 解引用，`-O3` 下编译器有权重排读写，经典"O2 能跑 O3 出鬼"

```c
/* ✅ 正确 — memcpy，零开销 */
uint32_t val;
memcpy(&val, buf + 4, 4);   // gcc -O2 编译成一条 mov，不比 cast 慢
val = ntohl(val);            // 网络序 → 主机序
```

`memcpy` 同时解决对齐和别名两个问题，定长 `memcpy` 在 `-O2` 以上被编译器优化成单条 `mov` 指令，**零额外开销**。

### 严格别名（Strict Aliasing）详解

上面提到"严格别名违例"，这里展开讲清楚。

**规则（C11 6.5p7）**：编译器有权假设——**不同类型的指针不会指向同一块内存**。

这不是 size 的问题，是**类型**的问题。`uint32_t` 和 `float` 都是 4 字节，但编译器认为 `uint32_t *p` 和 `float *q` 不可能指向同一地址。基于这个假设，编译器敢把读写重排——如果你违反假设，就是 UB。

**为什么存在这个规则**——为了编译器优化：

```c
int   *pi = &data;
float *pf = &data;   // 严格别名违例：不同类型指针指向同一内存

*pi = 1;
*pf = 2.0;
// 编译器认为 pi 和 pf 不可能指向同一地址
// 所以有权把 *pi=1 和 *pf=2.0 任意重排
// 如果实际指向同一地址 → 结果不可预测
```

`-O3` 下编译器可能把 `*pi = 1` 直接优化掉（认为没人通过 `pi` 读 `pf` 写的值），或者重排顺序——这就是"O2 能跑 O3 出鬼"的经典来源。

**不是看 size，是看类型**：

```c
/* ❌ 两者都是 4 字节，但类型不兼容 → 严格别名违例 → UB */
uint32_t *p = (uint32_t *)&some_float;
*p;   // UB

/* ❌ 同理 */
float *f = (float *)&some_uint32;
*f;   // UB
```

size 相同不能别名。规则看的是**类型兼容性**，不是位宽。

**例外：`char*` / `unsigned char*` 可以指向任意内存**

标准专门给了 `char*`、`unsigned char*` 特权——它们可以指向**任何类型**的对象并访问：

```c
/* ✅ 合法——unsigned char* 可以指向任何东西 */
unsigned char *bytes = (unsigned char *)&some_uint32;
bytes[0];  // 读第 1 字节，合法
```

**这就是 `memcpy` 能用的原因**——`memcpy` 内部通过 `unsigned char*` 逐字节拷贝，永远不违反严格别名。所以类型转换用 `memcpy` 而不是指针 cast：

```c
/* ✅ memcpy 走 unsigned char*，合法 */
uint32_t val;
memcpy(&val, buf + 4, 4);

/* ❌ 直接 cast + 解引用，违反严格别名 */
uint32_t val = *(uint32_t *)(buf + 4);
```

> 一句话：严格别名 = 编译器假设不同类型指针不指向同一内存，违反就是 UB。解法：**类型转换用 `memcpy`，不用指针 cast**。

### 3. 类型安全

```c
int x = 42;
float *pf = &x;    /* 编译警告/错误：int* → float* 不兼容 */
```

- 编译器用指针类型做**类型检查**——防止把 `int *` 当 `float *` 用
- `void *` 是例外：可以和任何指针互转，不做检查

## 强制类型转换（cast 运算符）

格式：`(类型)表达式`，例如 `(int *)raw`、`(int)3.9`。

**圆括号 + 类型名**是 cast 运算符，把后面表达式的值**强行按新类型解释**。但 cast 分两类，行为完全不同：

| 写法 | 类别 | 比特变不变 | 例子 |
|------|------|-----------|------|
| `(int)3.9` | **数值转换**（重新编码） | **变** | IEEE754 `0x40073333` → int `0x00000003`，截断 + 重编码 |
| `(double)42` | 数值转换 | 变 | int `0x2A` → IEEE754 `0x4045000000000000` |
| `(int *)raw`（raw 是 `void*`） | **指针 cast**（重新解读） | 不变 | 8 字节地址值原样保留，只换"怎么解读这块内存" |
| `(char *)buf` | 指针 cast | 不变 | 同上 |
| `(int *)addr`（addr 是整数） | **整数转指针** | 不变 | 整数值当地址用，比特原样 |

> **口诀**：数值转换 = 重新编码（比特变）；指针 cast / 整数转指针 = 重新解读（比特不变）。

笔记里常犯的错：把表格里 `(int)x` 和 `(int *)x` 放一起说"比特不变"——**只对指针 cast 成立，数值 cast 比特一定变**。`(int)3.9` 从 `0x40073333` 变成 `0x00000003`，完全是另一串比特。

### 整数 ↔ 指针转换（内核/MMIO 经典）

```c
long addr = 0xffff0000;
int *ptr = (int *)addr;          /* 整数 → 指针 */
```

`(int *)` 干了三件事：

1. 把 `long` 整数值 `0xffff0000` 当成内存地址解释
2. 改变编译器对这块内存的解读方式：之后通过 `ptr` 访问按 `int`（4 字节）读/写，步长也变 `sizeof(int)`
3. 比特没变：`addr` 里存的 `0x00000000ffff0000`，转成 `int*` 后指针变量里还是同一串地址

**标准定性**（C11 6.3.2.3p5）：

- 整数转指针的**转换本身是 implementation-defined**（编译器得文档化，不是 UB）
- 真正 UB 的是**解引用一个不指向有效对象的指针**

所以这行 `(int *)addr` 不是 UB，但 `*ptr` 在用户态是 UB（SIGSEGV），在内核态如果 0xffff0000 是有效 MMIO 映射就合法。

### `long` 宽度陷阱

64 位 LP64 上 `long` 8 字节、`int*` 8 字节，转换没问题。但搬到 32 位 ILP32：

- `long` 是 4 字节，`0xffff0000` 还能装下
- 如果 `addr` 超过 32 位（如 `0x1ffff0000`），`long`（4 字节）在 ILP32 上**装不下**——这连第一步赋值都出问题
- 32 位平台整数转指针，结果 implementation-defined，可能截断高位

这就是为什么跨平台代码地址转整数**一律用 `uintptr_t`**（3.1.1 已讲），不用 `long`/`uint64_t`。

### MMIO 寄存器访问的标准姿势

```c
/* ❌ 缺 volatile */
uint32_t *reg = (uint32_t *)0xFFFF0000;
while (*reg & BUSY) ;   /* 编译器可能只读一次，缓存到寄存器 → 死循环 */

/* ✅ 内核 MMIO 标准写法 */
volatile uint32_t *reg = (volatile uint32_t *)0xFFFF0000;
uint32_t v = *reg;      /* 每次都生成真实 load 指令，读硬件当前值 */
```

不加 `volatile`，编译器把 `while (*reg & BUSY)` 优化成"读一次存寄存器、循环判缓存值"——永远死循环或读到旧值。`volatile` 强制每次访问生成真实 load/store。内核 `readl`/`writel` 屏障内部就包了 volatile 访问。

### cast 不做安全检查

```c
int x = 42;
float *fp = (float *)&x;    /* 编译能过，但解引用 UB（严格别名） */
*fp;                         /* 垃圾值或崩溃 */
```

cast 是程序员对编译器的**单方面声明**——你说是什么类型，编译器就信。类型错了运行直接 UB，编译期不会拦你。这就是为什么"能编译过"不等于"正确"。

### 区分：定义 vs cast

```c
int *p;            /* 定义变量：声明 p 是 int 指针，分配存储 */
(int *)xxx;        /* cast：修改现有值的类型解释，不分配存储 */
```

前者是声明语句，后者是表达式。位置和含义完全不同，别混。

### 三种 cast 区分：整数↔指针 vs 指针↔指针

cast 看似都是 `(类型)值`，但按"跨类别"还是"同类别"分三种，行为和陷阱不同：

| 维度 | 整数→指针 `(uint32_t *)addr` | 指针→整数 `(uintptr_t)p` | 指针→指针 `(uint32_t *)raw` |
|------|------------------------------|--------------------------|-----------------------------|
| **C11 定性** | 6.3.2.3p5 **implementation-defined** | 6.3.2.3p6 implementation-defined（`uintptr_t` 保证 round-trip） | void*↔任意：合法；非兼容类型互转：转换合法，**解引用**才 UB |
| **比特变不变** | 不变 | 不变 | 不变 |
| **危险在哪** | 解引用：未对齐/无效地址 → UB | 宽度不匹配会截断 → 用 `uintptr_t` 规避 | 解引用违反严格别名 → UB |
| **跨平台要点** | 整数宽度 vs 指针宽度（LP64/ILP32） | **必须 `uintptr_t`**，不能用 `int`/`long` | 只有 `char*`/`unsigned char*` 可解引用任意内存 |
| **典型用途** | MMIO 寄存器地址、固定物理地址 | 地址存日志/哈希/序列化 | `void*` 具体化、`malloc` 返回值转类型 |

**核心区别**：

1. **前两种是"跨类别"**（整数 ↔ 指针）——整数和指针是两种不同的东西，标准用 implementation-defined 桥接，`uintptr_t` 是标准给的安全容器
2. **第三种是"同类别换指向类型"**——指针还是指针，只是换"怎么解读这块内存"。合法性看**类型兼容性**，不是宽度
3. **三种都"比特不变"**——cast 不做编码转换，只换标签。真正改比特的是数值转换 `(int)3.9`

**容易混的点**：`(uint32_t *)(void *)0x1001` 看起来有两层 cast，实际是先整数→void*（第一种），再 void*→uint32_t*（第三种合法子情况）。void* 是中转站，因为它和任意指针互转都不改变比特、也不触发严格别名。

## `void *`：泛型指针

```c
void *generic = &x;     /* int * → void *：隐式转换，安全 */
int *pi = generic;       /* void * → int *：需要显式 cast（C）或隐式（C++） */
```

| 要点 | 说明 |
|------|------|
| `void *` 存什么 | 任意地址，但**不知道指向什么类型** |
| 解引用 | **不能直接解引用**——编译器不知道读几个字节 |
| 算术 | **不能做算术**（C 标准未定义 `void *` 步长；GCC 扩展按 1 字节算） |
| 转换 | 可和任意指针互转；使用前必须 cast 到具体类型 |
| 用途 | `malloc` 返回值、`qsort` 比较函数、泛型容器 |

> `malloc` 返回 `void *`——"给你一块内存，你自己决定怎么解释"。`int *p = malloc(4)` 隐式转成 `int *`。

## 限定符与指针的组合

`const` 可以修饰"指针本身"或"指向的内容"——位置决定语义：

```c
const int *p;         /* 指向 const int：不能通过 p 改内容，但 p 可指向别处 */
int *const p = &x;    /* const 指针：p 本身不可改，但可以通过 *p 改 x */
const int *const p = &x;  /* 二者都只读 */
```

| 写法 | 指针可改？ | 内容可改？ | 记忆法 |
|------|----------|----------|--------|
| `const int *p` | ✅ | ❌ | const 在 * 前面 → 内容只读 |
| `int *const p` | ❌ | ✅ | const 在 * 后面 → 指针只读 |
| `const int *const p` | ❌ | ❌ | 两个 const → 都只读 |

### 阅读技巧

从右往左读：
- `const int *p` → p is pointer to const int
- `int *const p` → p is const pointer to int
- `const int *const p` → p is const pointer to const int

### HFT 常用

```c
/* 只读配置指针：函数不改配置 */
void process(const struct config *cfg);   /* cfg 指向的内容不可改 */

/* MMIO 寄存器：volatile 告诉编译器每次从内存读 */
volatile uint32_t *reg = (volatile uint32_t *)0x40000000;
```

## NULL：空指针

```c
int *p = NULL;     /* p 不指向任何有效对象 */
if (p == NULL) { /* 检查空指针 */ }
*p;               /* UB：解引用空指针 → 通常 SIGSEGV */
```

- `NULL` 在 C 中通常定义为 `((void *)0)`
- 解引用 NULL 是 **UB**——通常 SIGSEGV，但不保证
- **所有指针用前检查 NULL**——工程铁律
- C11 引入 `nullptr` 的前身，C23 正式有 `nullptr`

## 指针的指针（预告）

```c
int x = 42;
int *p = &x;       /* p 指向 x */
int **pp = &p;     /* pp 指向 p */

**pp;              /* 42：先解引用 pp 得到 p，再解引用 p 得到 x */
```

- 二级指针用于"修改调用者的指针"——如 `void alloc(int **pp)`
- 详见 ch06.10 和 ch13.1

## 常见误区

| 误区 | 纠正 |
|------|------|
| `int *` 和 `char *` 大小不同 | 指针大小与指向类型无关，64 位都是 8 字节 |
| `void *` 可以直接解引用 | 不能，编译器不知道读几个字节 |
| `void *` 可以做算术 | C 标准未定义；GCC 扩展按 1 字节 |
| `int *p = &x; float *f = p;` 安全 | 类型不兼容，编译警告，行为 UB |
| `const int *p` 表示指针不可改 | 不对，是内容不可改；指针可改 |
| 解引用 NULL 一定崩溃 | 是 UB，通常 SIGSEGV 但不保证 |
| 所有指针都是 8 字节 | 64 位系统是，32 位系统是 4 字节 |

## 实操

1. `printf("%zu\n", sizeof(int *))` 到 `sizeof(void *)`，看都是 8
2. `int arr[3]={1,2,3}; int *p=arr; printf("%p %p\n", p, p+1)` 看步长 4
3. `char *c=(char*)arr; printf("%p %p\n", c, c+1)` 看步长 1
4. 写 `const int *p` 和 `int *const p`，尝试修改，看编译错误
5. `void *v = &x; *v;` 看编译错误（不能解引用 void *）
6. `int *p = NULL; *p;` 看 SIGSEGV

**题目 1：** 以下代码有什么错误？
```c
int x = 42;
float *fp = &x;
*fp = 3.14f;
```

<details>
<summary>参考答案</summary>

类型不匹配。&x 的类型是 int*，赋给 float* 需要强制转换。不转换是编译错误。即使强制转换了，通过 float* 访问 int 变量违反了严格别名规则（strict aliasing），是未定义行为——可能导致垃圾值或程序崩溃。

</details>

### 题目 2：指针步长

```c
uint16_t *ptr = (uint16_t *)0x2000;
ptr++;
```

> `ptr` 最终地址等于多少？为什么？

<details>
<summary>参考答案</summary>

`0x2002`。`ptr++` 不是地址 +1，而是加上 `sizeof(uint16_t)` = 2 字节 → `0x2000 + 2 = 0x2002`。

指针加减的步长由**指向类型**决定：`uint8_t*` 步长 1，`uint16_t*` 步长 2，`uint32_t*` 步长 4，`uint64_t*` 步长 8。类型写错 → 步长错 → 读错内存。

</details>

### 题目 3：整数转指针

```c
long addr = 0xffff0000;
int *ptr = (int *)addr;
```

> `(int *)` 在这里干了什么？这行本身是 UB 吗？`*ptr` 呢？

<details>
<summary>参考答案</summary>

**`(int *)` 干了三件事**：把 `long` 整数值 `0xffff0000` 当成内存地址解释；改变编译器对这块内存的解读方式（之后通过 `ptr` 按int 4 字节读/写，步长也变 `sizeof(int)`）；比特没变，`addr` 里存的地址值原样搬到 `ptr` 里。

**这行 cast 本身不是 UB**，是 C11 6.3.2.3p5 的 **implementation-defined behavior**（编译器得文档化整数怎么映射成指针，不是"编译器可以为所欲为"的 UB）。

**`*ptr` 才是关键**：
- 用户态：0xffff0000 通常不是有效映射地址 → 解引用 UB，典型 SIGSEGV
- 内核态：如果 0xffff0000 是 MMIO 寄存器映射地址 → 合法，但**必须加 `volatile`**，否则编译器把连续读优化成读一次缓存 → 死循环或读旧值

所以内核 MMIO 标准写法是 `(volatile uint32_t *)0xFFFF0000`，不是裸 `(int *)`。

**额外陷阱**：`long` 宽度随平台变（LP64 是 8 字节，ILP32/LLP64 是 4 字节）。如果 `addr` 值超过 32 位，在 ILP32 平台上 `long` 装不下，或者整数转指针截断高位。跨平台地址转整数应该用 `uintptr_t`，不用 `long`。

</details>

### 题目 4：void* 中转 + 指针步长

```c
void *v = (void *)0x2000;
uint16_t *s = (uint16_t *)v;
s++;
```

> `s` 里存的地址变成多少？整个过程碰过内存吗？

<details>
<summary>参考答案</summary>

`s` 变成 **`0x2002`**。

过程拆解：
1. `(void *)0x2000`：整数 → void*（第一种 cast，比特不变），`v = 0x2000`
2. `(uint16_t *)v`：void* → uint16_t*（第三种 cast 的合法子情况，比特不变），`s = 0x2000`
3. `s++`：指针算术，`s += sizeof(uint16_t) = 2` → `0x2002`

**整个过程没碰过内存**——三步都是类型标签变化和指针算术，没有一次解引用。只有写 `*s` 才真正访问内存（此时若 0x2000 未对齐 uint16_t 或不是有效映射地址 → UB）。

两层 cast 看起来复杂，实际 void* 只是个中转站：它和任意指针互转都不改比特、也不触发严格别名，所以 `(uint16_t *)(void *)0x2000` 等价于直接 `(uint16_t *)0x2000`。

</details>

### 题目 5：指针宽度 vs 指向类型

```c
/* 64 位 Linux (LP64) */
uint8_t  *a;
uint32_t *b;
uint64_t *c;
```

> `sizeof(a)`、`sizeof(b)`、`sizeof(c)` 分别等于多少？为什么？

<details>
<summary>参考答案</summary>

**三个都是 8**。

```c
sizeof(a) == 8;   /* 不是 1 */
sizeof(b) == 8;   /* 不是 4 */
sizeof(c) == 8;   /* 不是 8"因为指向 uint64_t"，而是所有指针都是 8 */
```

指针变量本身的存储宽度由**编程模型（ABI）**决定，与指向类型无关。LP64 上所有指针都是 8 字节，不管指向 `uint8_t`（1 字节数据）还是 `uint64_t`（8 字节数据）。

指向类型只决定两件事：解引用读几个字节、`p++` 步长多大。它**不决定**指针本身占几字节。

</details>

### 题目 6：uint64_t vs uintptr_t vs uint64_t*

```c
/* 64 位 Linux (LP64) */
uintptr_t a = 0x2000;
uint8_t  *p = (uint8_t *)a;
p++;
```

> 1. `p` 这个指针变量本身是多少位？
> 2. `p++` 步长是多少？
> 3. `a` 和 `p` 在内存里存的数值，在 `p++` 之前是否相同？

<details>
<summary>参考答案</summary>

1. **64 位（8 字节）**。LP64 上所有指针都是 8 字节，不管指向什么类型。

2. **1 字节**。`sizeof(uint8_t) == 1`，指针 `++` 的步长等于指向类型的大小。

3. **相同**。在 `p++` 之前，`a` 是整数 `0x2000`，`p` 是指针指向地址 `0x2000`——两者内存里存的二进制都是 `0x0000000000002000`。区别只在类型标签：`a` 是整数（`++` 加 1），`p` 是指针（`++` 加 `sizeof(uint8_t)=1`）。本例恰好步长都是 1，但如果换成 `uint32_t *p`，`p++` 就加 4 而 `a++` 仍加 1。

**核心**：`uintptr_t` 是整数（存地址数字），`uint8_t *` 是指针（指向 1 字节数据）。整数存地址要够宽（`uintptr_t` 自动匹配），转成哪种指针只决定解引用宽度和步长，二者互不绑定。

</details>
