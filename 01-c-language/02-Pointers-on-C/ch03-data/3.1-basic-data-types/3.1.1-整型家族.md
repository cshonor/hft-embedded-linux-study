# 3.1.1 整型家族

## 本节讲什么

C 的整型按**符号 + 位宽**划分，但位宽**由实现定义**——同一关键字在不同平台宽度不同。本节讲清楚每种的典型宽度、隐式转换的隐蔽陷阱、为什么工程上一律用定宽类型。这是协议解析、寄存器操作、计数索引的数据基础。

## 整型家族全景

| 类型 | 典型位宽（LP64 Linux） | 取值范围 | 工程场景 |
|------|----------------------|---------|---------|
| `char` | 8 | signed: -128~127 / unsigned: 0~255 | 字节流、ASCII、寄存器单字节 |
| `signed char` | 8 | -128~127 | 明确有符号单字节 |
| `unsigned char` | 8 | 0~255 | 字节流、缓冲、位操作 |
| `short` | 16 | -32768~32767 | 协议字段、小计数 |
| `unsigned short` | 16 | 0~65535 | 端口号（0~65535） |
| `int` | 32 | -2^31~2^31-1 | 循环计数、标志、掩码 |
| `unsigned int` | 32 | 0~2^32-1 | 位掩码、无符号计数 |
| `long` | 64（LP64）/ 32（ LLP64 Windows） | — | 地址、大计数（平台相关！） |
| `unsigned long` | 64/32 | — | 同上 |
| `long long`（C99） | 64 | -2^63~2^63-1 | 纳秒时间戳、订单 ID |
| `unsigned long long` | 64 | 0~2^64-1 | 同上无符号 |

### 数据模型（决定 `long`/`pointer` 宽度）

| 模型 | int | long | pointer | 典型平台 |
|------|-----|------|---------|---------|
| **ILP32** | 32 | 32 | 32 | 32 位 Linux |
| **LP64** | 32 | 64 | 64 | 64 位 Linux/macOS |
| **LLP64** | 32 | 32 | 64 | 64 位 Windows |

> **关键**：`long` 在 Linux 64 位是 8 字节，在 Windows 64 位是 4 字节——这就是为什么不能用 `long` 存需要确定宽度的数据。用 `int64_t`。

### `char` 的符号性陷阱

- `char` 是 `signed` 还是 `unsigned`？**由实现定义**
- x86/gcc 默认 `signed char`，ARM 默认 `unsigned char`
- 跨平台代码用字节操作必须明确写 `unsigned char` 或 `signed char`

## 整数提升（Integer Promotion）

`char`/`short` 参与运算时，**先提升为 `int`**：

```c
unsigned char a = 200, b = 100;
int c = a + b;        /* a、b 先提升为 int(200)、int(100) → c = 300 */
unsigned char d = a + b;  /* 300 截断回 unsigned char → 44（300-256） */
```

- 提升的目的是"用 CPU 自然宽度运算更快"——早期 CPU 的 `char` 运算反而比 `int` 慢
- 提升后符号性可能改变——`unsigned char` 提升成 `int`（有符号），不是 `unsigned int`

## 有符号/无符号隐式转换（隐蔽 bug 重灾区）

### 规则

当表达式中同时有 `signed` 和 `unsigned` 同级整型时，**有符号转为无符号**运算。

### 经典陷阱

```c
unsigned char a = 200;
if (a > -1)   /* a 提升为 int(200)；-1 是 int；200 > -1 → 永远为真 */

if (sizeof(int) > -1)   /* sizeof 返回 size_t(unsigned)！-1 转成超大正数 → 永远为假 */
```

第二个是**最常见**的 `sizeof` 陷阱：

```c
/* 看起来合理，实际永远为假 */
if (sizeof(arr) > -1) { ... }   /* sizeof(arr) 是 size_t(unsigned)，-1 转 UINT_MAX → 真 */
/* 等等，实际上 size_t 最大值 > -1 转换后的值，所以这是真... */
/* 关键：if ((int)sizeof(arr) > -1) 才安全，因为 sizeof 是无符号 */
```

> **更准确**：`-1` 转成 `size_t`（无符号）后是 `SIZE_MAX`（巨大正数），所以 `sizeof(arr) > (size_t)(-1)` 几乎总是**假**——因为 `SIZE_MAX` 是最大值。这正是 bug 所在。

### 更多陷阱例子

```c
int len = -1;
unsigned int size = 10;
if (len < size) { ... }   /* len 转成 unsigned → UINT_MAX-... → 巨大正数 → 假！本该进却没进 */

for (unsigned i = 10; i >= 0; i--) { ... }  /* 死循环！unsigned 永远 >= 0 */
```

**防御**：
- 比较有符号和无符号时，显式 cast 到统一类型
- 循环计数用 `int` 或 `size_t`，别用 `unsigned` + `>= 0`
- `-Wsign-compare` 开启，编译器会警告

## 字面量后缀

| 后缀 | 含义 | 例子 |
|------|------|------|
| `U`/`u` | `unsigned` | `100U` |
| `L`/`l` | `long` | `100L` |
| `LL`/`ll` | `long long`（C99） | `100LL` |
| `UL`/`ull` 等 | 组合 | `0xFFFFFFFFULL` |

- 不加后缀：类型由值大小决定（`int` → `long` → `long long`）
- **64 位常量必须加 `ULL`**：`0xFFFFFFFFFFFFFFFFULL`
- 位掩码常加 `U`：`0xFFFFFFFFU` 防止算术移位变成有符号扩展

## 定长类型（推荐）

```c
#include <stdint.h>
uint8_t   byte;       /* 恰好 8 位无符号 */
uint16_t  port;        /* 恰好 16 位无符号 */
uint32_t  seq;         /* 恰好 32 位无符号 */
uint64_t  order_id;    /* 恰好 64 位无符号 */
int64_t   timestamp;   /* 恰好 64 位有符号 */
```

| 类型族 | 含义 |
|--------|------|
| `intN_t`/`uintN_t` | 恰好 N 位（不保证存在，但主流平台都有 8/16/32/64） |
| `int_leastN_t` | 至少 N 位的最小类型 |
| `int_fastN_t` | 至少 N 位的最快类型（x86-64 上 fast16/fast32 通常都是 64 位！） |
| `intptr_t`/`uintptr_t` | 能容纳指针的整型（宽度 = 指针宽度） |
| `intmax_t`/`uintmax_t` | 最大宽度 |

### `uintptr_t` vs `uint64_t`（地址转整数的正确选择）

两者都能存指针值，但语义和标准保证不同：

| 维度 | `uintptr_t` | `uint64_t` |
|------|------------|-----------|
| 宽度 | 跟指针走（32 位系统 32 bit，64 位系统 64 bit） | 固定 64 bit |
| round-trip 保证 | C11 7.20.1.4 保证 `(void*)(uintptr_t)ptr == ptr` | 标准不提供此保证 |
| 32 位系统 | 32 位，刚好 | 64 位，浪费且语义不对 |
| printf 格式 | `PRIuPTR`（跨平台一致） | `%lu`/`%llx`（LP64/LLP64 间会错） |

> `uint64_t` 存 32 位指针**不会溢出**（64 位容器装 32 位值绰绰有余），但用 `uintptr_t` 的理由是**语义正确 + round-trip 保真 + 跨平台宽度匹配**。真正会出事的是反方向：`(int)ptr` 或 `(uint32_t)ptr` 在 64 位上**截断**指针 → UB。

```c
void *ptr = &x;
uintptr_t addr = (uintptr_t)ptr;   /* ✅ 正确 */
void *restored = (void *)addr;     /* ✅ 标准保证 == ptr */

uint64_t bad = (uint64_t)ptr;      /* 实际能工作，但标准不保证 round-trip */
```

> HFT/DPDK/内核一律用 `uint8_t`..`uint64_t`——宽度确定，跨平台一致，行为可预测。

## HFT / 硬件视角

| 场景 | 类型选择 |
|------|---------|
| 报文字段 | `uint8_t`/`uint16_t`/`uint32_t`（按协议宽度） |
| 端口号 | `uint16_t`（0~65535） |
| 寄存器读写 | `volatile uint32_t *`（MMIO） |
| 纳秒时间戳 | `uint64_t` |
| 订单 ID | `uint64_t` |
| 循环计数 | `size_t` 或 `uint32_t` |
| 位掩码 | `uint32_t`/`uint64_t` + `U` 后缀 |

## 常见误区

| 误区 | 纠正 |
|------|------|
| `long` 一定是 64 位 | LP64 是 64，LLP64(Windows) 是 32；用 `int64_t` |
| `char` 一定有符号 | 实现定义；x86 默认 signed，ARM 默认 unsigned |
| `sizeof(arr) > -1` 是真 | `-1` 转 `size_t` 成 `SIZE_MAX`，几乎总是假 |
| `unsigned` 循环 `>= 0` | 死循环，unsigned 永远 >= 0 |
| 掩码 `0xFFFFFFFF` 是 64 位 | 是 `unsigned int`（32 位）；要 64 位加 `ULL` |
| 定长类型多余 | 跨平台必备；DPDK/内核全用 |

## 实操

1. `printf("%zu\n", sizeof(char))` 到 `sizeof(long long)`，在 32/64 位对比
2. `printf("%zu\n", sizeof('A'))`——C 里是 4（`int`），不是 1
3. 写 `if (sizeof(int) > -1)`，看是否进入分支（实际不进——陷阱）
4. 写 `for (unsigned i=3; i>=0; i--)`，看死循环
5. 写 `unsigned char a=200; if (a > -1)`，看永远为真
6. 在 Linux 和 Windows（如可得）对比 `sizeof(long)`

## 代码自测

**题目 1：** 以下代码在不同平台上输出可能不同，为什么？如何修复？
```c
long x = 100000;
printf("%d\n", x);
```

<details>
<summary>参考答案</summary>

long 的大小因平台而异（32 位 Linux 上是 4 字节，64 位 Linux 上是 8 字节，Windows 上始终 4 字节）。用 %d 打印 long 在 64 位 Linux 上会截断。应该用 %ld。更好的做法是用 <stdint.h> 的 int32_t/int64_t 配合 PRId32/PRId64 宏。

</details>
