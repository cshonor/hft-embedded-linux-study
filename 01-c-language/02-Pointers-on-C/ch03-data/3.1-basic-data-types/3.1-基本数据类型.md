# 3.1 基本数据类型

## 本节讲什么

C 的**内置类型体系**：整型家族、浮点类型、指针，以及配合它们的**限定符**（`const`/`volatile`/`restrict`）、**字节序**（endian）、**对齐**。这一节是 DPDK mbuf、内核 struct、交易二进制报文、寄存器读写的**数据地基**——选错类型，轻则精度丢失，重则协议错位、越界、未定义行为。

## 类型决定什么

声明一个变量时，类型同时决定了五件事：

| 维度 | 含义 | 选错的后果 |
|------|------|-----------|
| **位宽** | 占几个字节 | 赋值放不下 → unsigned 截断 / signed 实现定义（C11 6.3.1.3） |
| **取值范围** | 能表示的最小/最大值 | **算术溢出** → signed 是 UB / unsigned 是回绕（C11 6.2.5p9） |
| **内存布局** | 字节序、对齐 | 跨平台/跨机数据错位 |
| **运算规则** | 有符号/无符号、提升、转换 | 隐式转换 → 隐蔽 bug |
| **解引用语义**（指针） | 读几个字节、步长多大 | 指针类型错 → 读错内存 |

> **HFT 铁律**：硬件/协议相关的类型，一律用 `<stdint.h>` 定宽类型（`uint8_t`/`uint16_t`/`uint32_t`/`uint64_t`），不用平台相关的 `int`/`long`。

### 核心原则：内存只是比特流，类型决定解读

不管 `int` 还是 `uint32_t`，内存里都只是一串二进制比特。**内存本身没有"有符号/无符号"标记，没有"这是 4 字节还是 8 字节"的标签**。所有的位宽、取值范围、运算规则、指针步长——全部来自 C 语言给变量写的**类型**。

```
内存中的 1 字节: 0b11111111

类型是 int8_t  → CPU 按补码解读 → -1
类型是 uint8_t → CPU 按无符号解读 → 255
```

同一串比特，类型不同，解读完全不同。这是理解下面所有内容的前提。

## 三大类内置类型

```
基本类型
├── 整型家族（3.1.1）
│   ├── char / signed char / unsigned char     (8 bit)
│   ├── short / unsigned short                 (16 bit)
│   ├── int / unsigned int                     (32 bit)
│   ├── long / unsigned long                   (32 或 64，平台相关)
│   └── long long / unsigned long long         (64 bit，C99)
├── 浮点类型（3.1.2）
│   ├── float                                   (32 bit)
│   ├── double                                  (64 bit)
│   └── long double                             (扩展，平台相关)
└── 指针（3.1.3）
    ├── typed pointer (int *, struct rte_mbuf *)
    └── void *                                  (泛型地址)
```

## 限定符（修饰类型语义）

| 限定符 | 作用 | HFT 关注 |
|--------|------|---------|
| **`const`** | 只读——编译器保证不被修改 | 配置、字符串字面量 |
| **`volatile`** | 禁止编译器优化（每次从内存读） | MMIO 寄存器、信号处理、多线程标志 |
| **`restrict`**（C99） | 承诺无别名——允许向量化 | 热路径数组处理 |
| **`_Atomic`**（C11） | 原子类型——无锁编程 | 无锁队列、计数器 |

> `volatile` 是 HFT/嵌入式高频词——MMIO 寄存器必须 `volatile`，否则编译器把"读寄存器"优化成读缓存值。详见 ch03 后续小节。

## 字节序（Endian）

```
uint32_t x = 0x12345678;

大端 (big-endian, 网络序)：    小端 (little-endian, x86/ARM 默认)：
高地址 → 低地址                高地址 → 低地址
[12][34][56][78]               [78][56][34][12]
```

- **x86/ARM 默认小端**——CPU 内部用小端
- **网络字节序是大端**（TCP/IP 规定）——所以收发报文要转换
- 转换函数：`htonl`/`ntohl`（32 位）、`htons`/`ntohs`（16 位）
- **DPDK/交易所行情字段常自定义端序**——必须按协议规定解析，别假设和本机一致

### 为什么 endian 是 HFT 大事

- 报文解析：每个字段要 `ntohs`/`ntohl` 转换，漏了就数据错位
- 寄存器读写：MMIO 寄存器的字节序由硬件决定，和 CPU 可能不同
- 跨机序列化：行情程序可能在 x86 和 ARM 间迁移

## 对齐（Alignment）

- 每种类型有**对齐要求**：变量起始地址必须是类型大小的整数倍
- `uint32_t` 要求 4 字节对齐，`uint64_t`/`double` 要求 8 字节对齐
- 编译器自动在结构体里插入 **padding**（填充字节，垃圾值）满足对齐

### 结构体 padding 示例

```c
struct demo {
    uint8_t  a;   // 1 字节，偏移 0
    // ← 3 字节 padding（垃圾值）
    uint32_t b;   // 4 字节，偏移 4（满足 4 字节对齐）
};
// sizeof(struct demo) == 8，不是 1+4=5
```

`a` 占 1 字节后，`b` 要求 4 字节对齐，所以编译器插入 3 字节 padding，`b` 放在偏移 4 的位置。整个结构体大小是 8，不是 5。

**手动解析报文的坑**：如果你按"1+4=5"算偏移去读 `b`，直接读到 padding 垃圾值。这就是为什么报文解析要用 `memcpy` 按字节拷贝，而不是直接 cast 结构体指针。

### `_Alignof` / `alignof`

```c
_Alignof(uint32_t)   // 4
_Alignof(uint64_t)   // 8
_Alignof(char)       // 1
```

C11 引入 `_Alignof` 运算符（`<stdalign.h>` 提供 `alignof` 宏），可以查询任意类型的对齐要求。

- 跨缓存行（64 字节）的对象可能引发**伪共享**——HFT 性能杀手
- 详见 ch10 结构体的存储分配

## 定长类型（`<stdint.h>`，C99）

```c
#include <stdint.h>
uint8_t   byte;      /* 恰好 8 位无符号 */
uint16_t  port;      /* 恰好 16 位无符号 */
uint32_t  seq;       /* 恰好 32 位无符号 */
uint64_t  order_id;  /* 恰好 64 位无符号 */
```

| 类型 | 含义 |
|------|------|
| `intN_t` / `uintN_t` | 恰好 N 位（N=8/16/32/64） |
| `int_leastN_t` | 至少 N 位的最小类型 |
| `int_fastN_t` | 至少 N 位的最快类型 |
| `intptr_t` / `uintptr_t` | 能存指针的整型 |
| `intmax_t` / `uintmax_t` | 最大宽度整型 |

> DPDK/内核/HFT 代码大量用 `uint32_t`/`uint64_t`——宽度确定，行为可预测，跨平台一致。

## 代码自测

**题目 1：** 以下代码在大多数编译器上输出什么？为什么？
```c
char c = 200;
printf("%d\n", c);
```

<details>
<summary>参考答案</summary>

输出 -56。`char` 是否有符号是**实现定义**的——大多数编译器默认 `char` 为有符号，范围 -128~127。

关键：`char c = 200` 把 200 赋给 `signed char` **不是溢出，也不是 UB**，而是 **C11 6.3.1.3 实现定义行为**（implementation-defined behavior）：值无法被目标类型表示时，结果由实现定义。gcc 选择补码回绕 → 200 - 256 = -56。

三种行为的区别：
- **实现定义**（implementation-defined）：编译器自己决定，但**必须文档化**（gcc 文档 `Implementation-defined behavior` 章节有写），同一编译器上结果可预测
- **未定义**（UB）：标准不做任何保证，编译器可以为所欲为（有符号算术溢出 `INT_MAX + 1` 属于此类）
- **unsigned 回绕**：C11 6.2.5p9 明确定义，无符号运算溢出按 mod 2^N 回绕，合法且可预测

如果需要明确的行为，用 `unsigned char` 或 `signed char`。

</details>

### 题目 2：`uintptr_t` vs `uint64_t`

```c
void *ptr = &some_var;
uint64_t a = (uint64_t)ptr;     // (1)
uintptr_t b = (uintptr_t)ptr;   // (2)
```

> 两者都能编译过，为什么地址转整数应该用 `uintptr_t` 而不是 `uint64_t`？

<details>
<summary>参考答案</summary>

`uint64_t` 存 32 位指针**不会溢出**——64 位容器装 32 位值绰绰有余，`(uint64_t)ptr` 是安全的宽化转换。用 `uintptr_t` 的真正理由：

1. **round-trip 保真**：C 标准保证 `(void *)(uintptr_t)ptr == ptr`（C11 7.20.1.4）；`uint64_t` 不提供这个保证（实际能工作，但标准不背书）
2. **宽度匹配**：`uintptr_t` 宽度被定义为"刚好能装下一个指针"——32 位系统是 32 位、64 位系统是 64 位；`uint64_t` 在 32 位系统上浪费空间且语义不对
3. **printf 格式匹配**：`PRIuPTR` 跨平台一致；`%lu`/`%llx` 在 LP64/LLP64 间会错
4. **真正会出事的是反方向**：`(int)ptr` 在 64 位上**截断**指针 → UB，`(uint32_t)ptr` 同理

一句话：地址转整数一律用 `uintptr_t`，保证 round-trip 保真和跨平台宽度匹配。

</details>
