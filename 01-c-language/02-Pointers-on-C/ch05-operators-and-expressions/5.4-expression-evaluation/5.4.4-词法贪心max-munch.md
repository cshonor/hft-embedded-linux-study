# 5.4.4 词法贪心（maximal munch）

> 补充节 · 承接 [5.4.3 优先级和求值顺序](./5.4.3-优先级和求值顺序.md)——优先级管不了"字符怎么切成 token"

## 本节讲什么

**词法贪心**和**运算符优先级**发生在编译的**不同阶段**，顺序固定：

```
源码字符流 → [词法分析: 切 token] → [语法分析: 优先级/结合性] → ...
                ↑ 词法贪心在这里         ↑ 优先级在这里
```

**先切符号，再算优先级。优先级管不了字符怎么切。**

## 词法贪心规则

C11 §6.4p4：

> If the input stream has been parsed into preprocessing tokens up to a given character, the **next preprocessing token is the longest sequence of characters** that could constitute a preprocessing token.

从左向右，每次吃掉能构成**合法 token 的最长一串字符**。

### 例 1：`A+++B`

```
字符流:  A + + + B
切分:    A      ++      +      B
         标识符  自增   加    标识符
token 序列: A ++ + B
表达式:      (A++) + B
```

- 读到 `A` → 标识符
- 接下来连续三个 `+`：贪心取最长合法运算符 `++`，消耗两个
- 剩一个 `+`，取为加法
- `B` → 标识符

人眼容易看成 `A + (++B)`，但**词法阶段 token 已切死**，后面的优先级救不了。

### 例 2：`a---b`

```
字符流: a - - - b
切分:   a    --     -     b
表达式: (a--) - b
```

### 一句话概括

词法贪心只负责把源码的一串字符切割成变量、运算符、数字。**只看字符，不懂表达式逻辑。**

## 优先级只能操作已切好的 token

```c
a + b * c     /* token 已切好; * 高于 +, 先算 b*c */

A++ + B       /* token: A ++ + B; 后置++ 高于 +, 先算 A++ */
```

假如 token 切出来是 `A + ++ B`（即 `A + ++B`），那 `++` 优先级高，先算 `++B` 再加法——但那是**另一套 token** 了。

**关键点：优先级只能操作已经切好的 token，不能改变 token 怎么切。**

## 对比

| 项目 | 词法贪心 max-munch | 运算符优先级 |
|------|-------------------|--------------|
| 阶段 | 词法分析，编译最早阶段 | 语法分析，切完 token 之后 |
| 处理对象 | 原始字符文本 `+ + +` | 已切好的 token 符号 `++ +` |
| 做什么 | 切割源码，拆出变量、运算符 | 决定表达式运算先后顺序 |
| 受什么影响 | 只看字符，不看运算逻辑 | 优先级 + 结合性 |
| 例子 | `A+++B` 切成 `A ++ + B` | `A++ + B` 先执行 `A++`，再 `+` |

**误区**：❌ 编译器看到 `A+++B` 会用优先级去猜是 `A + ++B`
**真相**：✅ 先贪心切 token，切完才轮到优先级按这套符号计算。

## 更多词法贪心陷阱

### `//` 注释吃掉除法（C99 行注释陷阱）

```c
int b = c//*comment*/d;
```

贪心把 `//` 之后**整行**当注释——`*comment*/d;` 连同分号一起被吃掉，剩 `int b = c` 缺分号 → 编译错误。想写"c 除以 d"必须让 `/ /` 分开：`c /*comment*/ / d`（注释在前，除号在后）。

### `n-->0`（"goes to" 运算符）

```c
while (n-- > 0)   /* 常写成 n-->0, 看着像个运算符, 其实是 (n--) > 0 */
```

### `i+++++j` 直接编译错误

```
字符流: i + + + + + j        (连续 5 个 +)
贪心切: i  ++  ++  +  j      (++ ++ +, 不是 + ++)
表达式: ((i++)++) + j
```

`i++` 的结果是右值（临时值），对它再 `++` 需要**左值** → gcc 报 `error: lvalue required as increment operand`。想表达 `(i++) + (++j)` 必须写空格：`i++ + ++j`。

### `0x1E+2` 十六进制陷阱

```
0x1E+2  →  贪心切成 0x1E+  (一个 pp-number!)  然后 2
```

十六进制浮点/后缀规则会把 `+2` 吞进数字 token，想表达"0x1E 加 2"必须加空格：`0x1E + 2`。

### 老代码 `a=-1` 的历史事故

早期 K&R C 支持 `=-` 作为复合赋值，`a=-1` 被切成 `a =- 1`（减 1）而非 `a = -1`。C89 移除了这种写法，改成 `-=`,但**词法切分的历史教训**留了下来——这也是《C 陷阱与缺陷》ch01 词法陷阱的开篇故事。

## 宏展开不会重切 token

预处理 token 的边界在**词法阶段已确定**，宏展开只是 token 替换，不会把相邻 token 重新拼接：

```c
#define P +
int x = a P+ b;    /* a + + b ?? 不: 词法已切成 'a' 'P' '+' 'b' */
                    /* 宏展开后是 a + + b 两个token, 不是 a ++ b */
```

反过来，想让 token 粘合需要显式 `##` 运算符——这正是 `##` 存在的原因。

## 实操验证

```bash
cat > t.c <<'EOF'
int main(void){
  int A = 1, B = 2;
  int r = A+++B;        /* (A++) + B = 1 + 2 = 3, 然后 A=2 */
  /* int q = A+++++B;   */ /* error: lvalue required */
  int n = 3;
  while (n-- > 0) ;     /* goes-to 写法 */
  return r;
}
EOF
gcc -std=c11 -Wall t.c -o t && ./t; echo $?

# 看 token 切分(预处理之后就停):
gcc -E t.c | tail -5        # 宏层面
gcc -fsyntax-only -Wall t.c # 只做词法+语法检查
```

## 代码自测

**题目 1：** `x---y` 经过词法贪心得到什么 token 序列？

<details>
<summary>参考答案</summary>

`x -- - y`，即 `(x--) - y`。贪心先吃最长的 `--`，剩下单个 `-`。

</details>

**题目 2：** 若 token 序列是 `a + ++ b`，此时靠什么决定先算 `++`？

<details>
<summary>参考答案</summary>

运算符优先级（语法分析阶段）。前置 `++` 是一元运算符（优先级第 2 级），高于加法（第 4 级），所以先算 `++b` 再加法。token 已定，优先级只决定运算次序。

</details>

**题目 3：** 能用运算符优先级改变词法贪心切出来的 token 吗？

<details>
<summary>参考答案</summary>

不能。两个阶段严格先后：词法切分（max-munch）完成后才进入语法分析。优先级只能作用于已切好的 token 序列。想改变切分只能改源码写法——加空格或括号。

</details>
