# 2.3 程序风格

## 本节讲什么

**可读、可维护、可 review** 的编码习惯。语法正确 ≠ 工程合格——一段能编译通过的代码，如果没人看得懂、改不动、review 不出来问题，就是工程负债。本节把内核/DPDK/HFT 的风格规范系统化，让全书示例有统一的风格基准。

## 为什么程序风格是"真问题"

- **代码读的次数远多于写的次数**——review、维护、debug、扩展，全在读
- **Bug 的平均发现时间 >> 写代码时间**——可读性差 → bug 潜伏久 → 爆发时代价大
- **多人协作**——风格不统一 → merge conflict、review 低效、指责游戏
- **HFT 特殊性**——热路径代码微秒级延迟，常需"看代码就猜到性能特征"，可读性是优化的前提

> Dijkstra："除了展示程序员自己的不足之外，计算机上的笨拙代码还能有什么用？"

## 命名（详见 2.2.4）

### 通用原则

- **见名知意**：`packet_count` 优于 `n`、`cnt`、`pc`
- **动词开头**：`read_data`、`init_server`、`parse_header`
- **布尔加前缀**：`is_valid()`、`has_data()`、`can_send()`
- **避免缩写到歧义**：`cnt`（count? center?）、`idx`（index 还好，但 `i` 够了）
- **避免单字母**（除循环 `i/j/k`）：`o`/`0`、`l`/`1` 混淆
- **作用域越大名字越长**：局部可 `i`，全局要 `g_packet_count`

### 内核/DPDK 惯例

| 对象 | 风格 | 例子 |
|------|------|------|
| 函数 | snake_case + 模块前缀 | `rte_mbuf_refcnt_update` |
| 变量 | snake_case | `order_id` |
| 全局 | `g_` 前缀 | `g_config` |
| 宏/枚举 | **全大写** | `RTE_MAX_ETHPORTS` |
| 类型 | snake_case + `_t` | `uint32_t`、`struct rte_mbuf` |

## 格式

### 缩进

- **4 空格**（内核/DPDK 现代项目主流）或 **tab**（部分老项目）
- **禁止 tab/space 混用**——diff 飘红、merge conflict 的头号元凶
- 用 `.editorconfig` + `clang-format` 强制

### 大括号

| 风格 | 形式 | 用谁 |
|------|------|------|
| **K&R（1TBS）** | `{` 同行，`}` 单独行 | 内核、DPDK、多数 C 项目 |
| **Allman** | `{` 单独行 | 部分系统级项目、C# |

```c
/* K&R */
if (x > 0) {
    do_something();
}

/* Allman */
if (x > 0)
{
    do_something();
}
```

> 项目内统一一种，别争论哪种"更好"——一致性 > 个人偏好。

### 其他格式

- **一行一事**：不要 `a=1; b=2; c=3;`
- **行宽**：内核 80 列，DPDK 100 列，现代项目 120 列
- **过长安达式换行**：运算符放行首或行尾，项目统一
- **指针 `*` 贴变量名**：`int *p` 而非 `int* p`（C 风格，K&R）

## 注释（详见 1.1.1 / 2.2.2）

### 好注释写 why

```c
/* 必须按 little-endian 解析：交易所行情字段规定 LE */
uint32_t price = le32toh(*p);

/* 不能用 spinlock：收包在中断上下文，不能睡眠 */
/* 用 trylock + 重试替代 */
```

### 烂注释复述代码

```c
i++;              /* increment i */           ← 毫无价值
int x = 5;       /* x 等于 5 */              ← 更糟
```

| 好注释 | 烂注释 |
|--------|--------|
| 函数意图、不变量、边界条件 | 复述每一行代码 |
| 为什么用这个算法/魔数 | "这里加一" |
| 参数、返回值、错误码语义 | 过时的设计文档 |
| 已知缺陷、TODO、性能假设 | 冗余的类型说明 |

> **口诀**：注释回答 **why**，代码回答 **how**。能用函数名/变量名表达的，别靠注释。

### 注释风格

- 内核倾向 `/* */`
- 公共 API 必须文档化：参数、返回值、错误码、线程安全性
- TODO 格式统一：`/* TODO(name): description */`

## 防御性习惯

### 禁止空 body 误用

```c
if (a > b);        /* ← 分号陷阱！空语句，if 不控制后面 */
{
    /* 永远执行 */
}

/* 正确：大括号紧跟，即使单语句也加大括号 */
if (a > b) {
    do_something();
}
```

- 即使单语句也加大括号——防止后续添加语句时忘记加
- `-Wall -Wparentheses` 会警告空 body

### 避免遮蔽

```c
int count = 10;
void f(void) {
    int count = 20;   /* 遮蔽全局——内核规范禁止 */
}
```

### 多文件工程

- **头文件声明，单点定义**（2.2.5）
- 头文件加 **include guard** 或 `#pragma once`
- 私有函数加 `static`——不污染全局符号

### 栈上大数组

```c
void f(void) {
    char buf[1024 * 1024];   /* 1MB 栈数组 → 栈溢出 */
}
```

- 大缓冲改 `static` 或 `malloc`
- 栈默认 8MB，DPDK worker 栈可能更小

### 初始化

- 局部变量**用前必须初始化**——栈 auto 不清零
- 报文解析缓冲用 `memset` 或 `= {0}` 清零
- `malloc` 返回的内存不清零——要清零用 `calloc`

## 函数设计

- **单一职责**：一个函数做一件事
- **短**：内核规范单函数不超过一屏（约 50 行）
- **入口校验**：函数开头检查参数合法性（NULL？越界？）
- **错误传播**：失败返回错误码，让调用者决定怎么办
- **main 协调**：main 调用子函数，子函数不反向调用 main

## 工具链

### 编译选项

| 选项 | 作用 | 为什么必须开 |
|------|------|-------------|
| `-Wall` | 常见问题警告 | 未用变量、`=` vs `==`、格式串不匹配 |
| `-Wextra` | 额外严格警告 | 空参 `()`、隐式转换 |
| `-Werror` | 警告当错误 | 防止警告被忽略、逐渐积累 |
| `-Wpedantic` | 严格标准 | 拒绝非标准扩展 |
| `-g` | 调试符号 | gdb 能用 |
| `-O2` | 优化 | 生产构建 |

### 格式化与检查

| 工具 | 作用 |
|------|------|
| **`.editorconfig`** | 编辑器层面统一缩进/换行/编码 |
| **`clang-format`** | 自动格式化，内核/DPDK/LLVM 都有配置 |
| **`checkpatch.pl`** | 内核风格检查 |
| **`cppcheck`** | 静态分析 |
| **`clang-tidy`** | 现代静态分析与重构建议 |
| **`sanitizer`** | `-fsanitize=address,undefined` 运行时检测内存/UB |

> HFT/内核工程标配：`-Wall -Wextra -Werror -g -O2` + `clang-format` + CI 检查。

## 常见误区

| 误区 | 纠正 |
|------|------|
| "能编译通过就行" | 工程合格 ≠ 编译通过；可读、可维护、无警告才是合格 |
| "风格是个人偏好" | 个人偏好在团队里必须让位给一致性 |
| "注释越多越好" | 烂注释是噪声，比没注释还糟 |
| "单语句不用大括号" | 容易后续加语句时忘加→bug；一律加大括号 |
| "tab 和 space 混用无所谓" | 是 merge conflict 和 diff 飘红头号元凶 |
| "性能优先于可读性" | 先写对再写快；不可读的"优化"常是伪优化 |
