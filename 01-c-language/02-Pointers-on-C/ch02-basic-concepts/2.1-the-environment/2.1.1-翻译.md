# 2.1.1 翻译

## 本节讲什么

**翻译**：源码变成可执行文件的完整过程。承接 ch01 的四阶段实操，本节从**概念层**讲清楚每一步在做什么、**翻译单元**是什么、**链接**为什么是独立的一步、以及最常见的链接报错从何而来。理解翻译环境，是看懂 DPDK/内核多模块构建、解决符号冲突的前提。

## 翻译四阶段（概念版）

| 阶段 | 输入 → 输出 | 做什么 | 关键概念 |
|------|-------------|--------|---------|
| 1. 预处理 | `.c` → `.i` | 展开 `#include`/`#define`、删注释、处理 `#ifdef` | **翻译单元**在此形成 |
| 2. 编译 | `.i` → `.s` | 词法→语法→语义分析→优化→生成汇编 | 类型检查在此完成 |
| 3. 汇编 | `.s` → `.o` | 汇编翻译成机器码 | 产物是 **ELF Relocatable**，符号可能未定义 |
| 4. 链接 | 多 `.o` → 可执行 | 解析未定义符号、重定位、合并段 | **单定义规则** |

### 与 ch01 的关系

ch01 讲的是**怎么操作**（`gcc -E/-S/-c` 命令、看产物）；本节讲的是**为什么**（每步概念、翻译单元、链接规则）。两者互补：操作让你动手，概念让你理解报错。

## 翻译单元：链接的基本单位

**一个 `.c` 文件，经过预处理后（所有 `#include` 展开、宏替换完成），就是一个翻译单元（translation unit）。**

```c
/* main.c */
#include <stdio.h>          /* stdio.h 内容被插入 */
#include "config.h"         /* config.h 内容被插入 */
int main(void) { ... }
```

预处理后，`main.c` + `stdio.h` + `config.h` 的所有内容拼成一个 `.i` 文件——这就是一个翻译单元。

### 翻译单元的规则

- 每个翻译单元**独立编译**成 `.o`
- **声明**（`extern`、函数原型）可以多次出现，只要一致
- **定义**（分配存储或生成代码）在整个程序中**只能一次**（外部链接的符号）
- `static` 修饰的定义是**内部链接**——只在当前翻译单元可见，不参与全局符号解析

> 这就是为什么"头文件放声明、`.c` 放定义"——头文件被多个 `.c` include，如果放定义就会多处定义。

## 声明 vs 定义：链接的核心

| | 声明 | 定义 |
|---|------|------|
| 作用 | 告知类型/签名，不分配 | 分配存储或生成代码 |
| 可出现次数 | 多次（只要一致） | 整个程序**一次**（外部链接） |
| 变量 | `extern int g_val;` | `int g_val = 10;` |
| 函数 | `void func(int x);` | `void func(int x) { ... }` |
| 结构体 | `struct rte_mbuf;`（不完整类型） | `struct rte_mbuf { ... };` |

```c
/* config.h —— 放声明 */
#ifndef CONFIG_H
#define CONFIG_H
extern int g_port;              /* 声明：不分配，告知类型 */
void init_server(int port);     /* 声明：函数原型 */
#endif

/* config.c —— 放定义 */
#include "config.h"
int g_port = 8000;              /* 定义：分配存储 */
void init_server(int port) {    /* 定义：生成代码 */
    g_port = port;
}

/* main.c —— 用声明 */
#include "config.h"
int main(void) {
    init_server(g_port);        /* 链接时找到 config.c 的定义 */
    return 0;
}
```

## 链接：符号解析与单定义规则

链接器（`ld`）把多个 `.o` 合并成一个可执行文件，核心工作是**符号解析**：

1. 收集所有 `.o` 的**符号表**（每个 `.o` 声明了哪些符号、引用了哪些符号）
2. 把"引用的符号"和"定义的符号"匹配
3. 匹配成功 → 重定位（填入地址）；匹配失败 → 报错

### 三种链接报错

| 报错 | 含义 | 常见原因 |
|------|------|---------|
| `undefined reference to xxx` | 引用了符号但没有定义 | 忘写实现、忘链接 `.o`/库、`static` 导致不可见、C++ name mangling |
| `multiple definition of xxx` | 同一符号多处定义 | 头文件放了定义、全局变量多处初始化、忘加 `static` |
| `cannot find -lxxx` | 找不到库 | `-L` 路径不对、库没安装、库名写错 |

### 修复链接报错的思路

1. **undefined reference**：这个符号应该在哪定义？那个 `.c`/`.o`/`.a`/`.so` 链接进来了吗？
2. **multiple definition**：哪个符号被定义了多次？是不是头文件里放了定义（应改 `extern` 声明）？
3. **cannot find -l**：`-L` 路径对吗？`pkg-config --libs xxx` 看正确的链接参数。

> DPDK/内核构建系统（meson/Kbuild）最终生成的就是一堆 `gcc -c` + `ld` 命令。看懂链接报错，是使用这些构建系统的基础。

## 多文件工程模型（DPDK/内核缩影）

```
app/
├── main.c          → main.o      （翻译单元 1）
├── net.c           → net.o       （翻译单元 2）
├── parser.c        → parser.o    （翻译单元 3）
└── Makefile

链接: gcc main.o net.o parser.o -lrte_mbuf -lrte_eal -o app
```

- 每个 `.c` 独立编译——改一个只需重编一个 `.o`，再链接（增量编译）
- `.h` 是翻译单元之间的**接口契约**——声明共享的函数和类型
- `static` 函数/变量是**翻译单元私有**的，不暴露给其他 `.o`——封装机制

## 常见误区

| 误区 | 纠正 |
|------|------|
| 头文件放变量定义 | 头被多个 `.c` include → 多重定义；头只放 `extern` 声明 |
| `static` 函数能被其他文件调用 | `static` = 内部链接，只在本翻译单元可见 |
| `extern` 分配内存 | `extern` 只是声明，不分配；定义在某个 `.c` |
| 改了 `.h` 不用重编 | `.h` 是文本插入，所有 include 它的 `.c` 都要重编 |
| 链接错误是语法错误 | 链接是第 4 阶段，语法在第 2 阶段已检查完；链接错误是符号解析失败 |
| C 和 C++ 可以直接互链 | C++ 有 name mangling，C 函数要 `extern "C"` 包裹才不 mangle |

## 实操

1. 写两个 `.c` + 一个 `.h` 的工程，故意把定义放头文件，看 `multiple definition`
2. 故意删掉一个函数实现，看 `undefined reference`
3. 用 `nm main.o` 看符号表，区分 `U`（未定义）、`T`（text 段已定义）、`D`（data 段）
4. `gcc -c a.c b.c` 后 `gcc a.o b.o -o app`，体验增量编译
5. DPDK 示例：看一个 meson 构建的链接命令（`ninja -v`），理解它生成了什么
