# 2.1 环境

## 本节讲什么

C 程序所处的两种**环境**：**翻译环境**（编译器+链接器把源码变成可执行文件）和**执行环境**（操作系统加载并运行程序）。这两个环境是两套完全不同的世界——翻译环境关心**符号、类型、链接**；执行环境关心**内存段、进程、指令执行**。本章从"环境"这个最高视角，说明词法/语法/链接/内存这些后续话题各自落在哪个环境里。

## 两种环境的本质区别

| 维度 | 翻译环境 | 执行环境 |
|------|---------|---------|
| 何时发生 | 编译期（开发机） | 运行期（目标机） |
| 主体 | 编译器 + 链接器 | OS 内核 + CPU |
| 处理对象 | 源码文本 → 机器码 | 进程地址空间 → 指令执行 |
| 关心的事 | 语法/语义正确、符号解析、优化 | 内存映射、栈/堆、调用约定、IO |
| 错误表现 | 编译错误/链接错误 | 崩溃/段错误/逻辑错误 |
| 工具 | `gcc`/`ld`/`readelf` | `gdb`/`strace`/`perf` |

> **核心认知**：很多 bug 跨越这两个环境。比如"返回局部变量地址"在翻译环境完全合法（语法对、类型对、链接对），但在执行环境是悬垂指针 UB。理解两环境分工，才能定位 bug 属于哪一类。

## 翻译环境速览（详见 2.1.1）

源码 → 可执行，分四阶段（与 ch01 一致）：

```
.c  ─预处理─→ .i  ─编译─→ .s  ─汇编─→ .o  ─链接─→ 可执行 ELF
```

- 翻译环境的核心产物是 **ELF**（可执行文件）
- 翻译环境的典型错误：`undefined reference`（符号没定义）、`multiple definition`（符号多处定义）、语法错误
- **一个 `.c` + 它 include 的所有头，预处理后 = 一个翻译单元**——这是链接的基本单位

## 执行环境速览（详见 2.1.2）

可执行 ELF 被 OS 加载成进程：

```
execve() → 内核映射 ELF 段 → crt0 初始化 → main() → return → exit() → 内核回收
```

- 执行环境的核心是**进程地址空间**：text/data/bss/stack/heap
- 执行环境的典型错误：段错误（访问非法地址）、栈溢出、悬垂指针、数据竞争
- 执行环境的内存布局决定了变量的**生命周期和可见性**（ch03/ch18）

## 为什么"环境"对 HFT/内核/DPDK 至关重要

| 现实问题 | 属于哪个环境 | 根源 |
|---------|------------|------|
| `undefined reference to rte_mbuf_alloc` | 翻译 | 忘链接 librte_mbuf 或头路径不对 |
| `multiple definition of g_config` | 翻译 | 同一全局变量多处定义 |
| 程序启动就段错误 | 执行 | 全局构造或 init 段访问非法地址 |
| 跑了一段时间崩溃，栈指向已释放内存 | 执行 | 悬垂指针/堆损坏 |
| 多线程数据竞争 | 执行 | 共享变量无锁访问 |
| DPDK worker 栈太小崩溃 | 执行 | 栈空间不足 |

> **口诀**：编译/链接错误查翻译环境，运行崩溃查执行环境。先分清是哪一类，再选工具（`readelf`/`ld` vs `gdb`/`valgrind`）。

## 代码自测

**题目 1：** C 程序的翻译阶段中，预处理发生在哪个阶段？以下代码经过预处理后会变成什么？
```c
#define MAX 100
int arr[MAX];
```

<details>
<summary>参考答案</summary>

预处理是翻译的第一阶段（实际分为 8 个翻译阶段）。预处理后 MAX 被替换为 100：int arr[100];。预处理只做文本替换，不进行语法检查——所以宏定义的错误可能在编译阶段才暴露。

</details>
