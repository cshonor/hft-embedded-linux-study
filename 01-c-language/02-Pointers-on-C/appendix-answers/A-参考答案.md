## 一、本附录讲什么

## 二、要点：六组代表性问题

### G1 指针与数组语义

**Q（ch6 典型题）**：下面代码输出什么？

```c
int a[] = {1, 2, 3, 4, 5};
int *p = a;
int *q = &a[4];
printf("%ld\n", q - p);        /* ? */
printf("%ld\n", (char*)q - (char*)p);  /* ? */
```

**答案**：`4` 和 `13`（假设 `int` 4 字节）。

**关键点**：
- 指针减法按**指向类型**计数：`int*` 相减得元素个数，`char*` 相减得字节数。
- 这是**同一数组内**指针运算的唯一合法场景——跨数组相减是 UB。
- HFT 场景：`rte_mempool` 里常做 `obj = (char*)ring + idx * elt_size` 的字节级运算，必须先转 `char*` 再算，否则差值含义全错。

**常见错误**：以为 `q - p` 是字节数；或以为 `(char*)q - (char*)p` 还是元素数。记住——**减法结果的单位由左操作数（被减数）的类型决定**。

---

**Q（ch8 典型题）**：`&a`、`a`、`&a[0]` 三者值是否相同？类型是否相同？

**答案**：值相同（数组首元素地址），类型不同：
- `a` → `int[5]`，在多数上下文中退化为 `int*`；
- `&a[0]` → `int*`；
- `&a` → `int(*)[5]`（指向整个数组的指针）。

**陷阱**：`&a + 1` 跳过**整个数组**（20 字节），而 `a + 1` 只跳一个元素（4 字节）。HFT 里算 ring buffer 的环形地址时，混淆这两者会导致越界写。

### G2 字符串与字节流

**Q（ch9 典型题）**：以下哪个能正确计算二进制数据长度？

```c
size_t len1 = strlen((char*)buf);    /* A */
size_t len2 = sizeof(buf);           /* B */  /* buf 是数组 */
size_t len3 = nbytes;                /* C */  /* 从 read() 返回值得到 */
```

**答案**：只有 C 可靠。

- A 错：`strlen` 遇 `0x00` 就停，二进制数据里合法的零字节会被误判为结尾。
- B 错：`sizeof` 在数组形参上退化为指针大小（8 字节），且只给缓冲区容量而非实际数据长度。
- C 对：`read()` / `recv()` 的返回值才是真实字节数。

**HFT 关联**：DPDK `rte_eth_rx_burst` 返回收到的 mbuf 数量，协议解析时必须用这个返回值做长度，绝不能用 `strlen`。这是网络字节流与 C 字符串的根本分界——见 ch9 笔记。

### G3 结构体内存布局

**Q（ch10 典型题）**：给定结构体，求 `sizeof` 和各字段偏移。

```c
struct S {
    char  a;     /* offset 0 */
    int   b;     /* offset ? */
    char  c;     /* offset ? */
};
```

**答案**（x86-64，默认对齐）：
- `a` 在 offset 0；
- `b` 需 4 字节对齐，前面补 3 字节 padding，offset 4；
- `c` 在 offset 8；
- 结构体总大小按最大成员对齐（4）向上取整 → `sizeof(S) = 12`。

**优化重排**：改成 `int b; char a; char c;` 后，`sizeof = 8`，省 4 字节。

**验证工具**：`offsetof(struct S, b)` 编译期给出偏移；`_Static_assert(offsetof(S, b) == 4, "")` 锁死布局。HFT 跨进程共享内存结构必须 `_Static_assert` 所有字段偏移，防止不同编译选项下 padding 漂移。

**常见错误**：以为字段顺序不影响大小；或以为 `packed` 总是好的。`packed` 会降低访问性能（非对齐读），在 x86 上有性能惩罚，在某些 RISC 架构上直接 SIGBUS。HFT 默认**不 packed**，只对跨平台线上协议结构才用。

### G4 链表与 ADT

**Q（ch12 编程练习典型题）**：实现单链表的逆序（原地，O(1) 额外空间）。

**标准答案**：

```c
node_t *reverse(node_t *head) {
    node_t *prev = NULL, *cur = head, *next;
    while (cur) {
        next = cur->next;   /* 先存下一节点 */
        cur->next = prev;   /* 反转指针 */
        prev = cur;         /* 前进 */
        cur = next;
    }
    return prev;            /* 新头 */
}
```

**常见错误**：
1. 没存 `next` 就改 `cur->next`，导致后续节点丢失——这是最经典的 UAF/泄漏。
2. 忘记返回新头，调用方还用旧头（此时旧头是尾）。
3. 递归实现栈深度 O(n)，长链表栈溢出。

**HFT 关联**：订单簿撤单时要快速摘除节点，侵入式双向链表（`list_head` + `container_of`）的删除是 O(1)。逆序本身在 HFT 里少见，但**指针改写的三步式（存 next → 改指针 → 前进）**是所有链表操作的心法——漏一步就断链。见 ch12 / ch17 笔记。

### G5 函数指针与回调

**Q（ch13 典型题）**：解读声明 `void (*signal(int, void (*)(int)))(int);`

**答案**：`signal` 是一个函数，接收（int, 一个接受 int 返回 void 的函数指针），返回一个接受 int 返回 void 的函数指针。即**注册信号处理函数，返回旧的信号处理函数**。

**解读法（螺旋法则）**：
1. `signal` 是函数（向右看参数列表）；
2. 参数 1 是 `int`，参数 2 是 `void(*)(int)`（函数指针）；
3. `(*signal(...))` 说明返回值是指针；
4. 外层 `void (*)(int)` 说明这个指针指向"接受 int 返回 void 的函数"。

**现代写法**用 `typedef` 拆解：
```c
typedef void (*sighandler_t)(int);
sighandler_t signal(int sig, sighandler_t handler);
```

**铁律**：任何超过两层嵌套的函数指针声明都必须 `typedef`，否则没人读得懂，包括三个月后的你自己。HFT 里 `eth_dev_ops`、`file_operations` 这种 vtable 全靠 typedef 规范。见 ch13 / ch17.5 笔记。

### G6 UB 与可移植性

**Q（ch15/ch18 典型题）**：以下代码有哪些问题？

```c
char buf[64];
gets(buf);                       /* 1 */
sprintf(buf, "%s%d", str, n);    /* 2 */
int *p = malloc(n * sizeof *p);  /* 3 */
if (!p) return -1;
*p = 42;                         /* 4 */
/* 忘记 free(p) */               /* 5 */
```

**问题清单**：
1. `gets` 已在 C11 移除——缓冲区溢出元凶，**永远禁用**，用 `fgets(buf, sizeof buf, stdin)`。
2. `sprintf` 无法限制写入长度，`str` 过长会溢出 `buf`——用 `snprintf(buf, sizeof buf, ...)`，并检查返回值是否 >= `sizeof buf`（截断）。
3. `malloc` 后未检查返回值就解引用——`if (!p)` 这步对了，但顺序要紧跟 `malloc`，中间不能有任何解引用。
4. `*p = 42` 没问题（已检查非空）。
5. `free(p)` 缺失——内存泄漏。长期运行的服务进程（HFT 守护进程）泄漏会拖垮系统。

**进阶**：`n * sizeof *p` 若 `n` 来自外部且是 `int`，大值可能导致**有符号整数溢出**（UB）或乘法溢出产生很小的正数，`malloc` 分配一小块，后续访问越界——这是经典堆溢出攻击面。用 `calloc`（内置溢出保护）或 `size_t` + 显式溢出检查。见 ch11 笔记。

## 三、HFT 关联

参考答案的价值不在"对答案"，而在**暴露你以为对、其实是 UB 的盲区**。HFT 对 UB 零容忍，因为：

| UB 类型 | 普通程序后果 | HFT 后果 |
|---------|-------------|---------|
| 严格别名违反 | 看起来能跑，-O2 后结果错乱 | 回测与实盘不一致，策略亏钱 |
| 整数溢出 | 偶发错误 | 订单数量/价格计算错，直接资损 |
| 数据竞争 | 偶发崩溃 | 行情处理延迟尖峰，错过套利 |
| 未初始化读 | 偶发脏数据 | 订单簿状态错误 |
| 缓冲区溢出 | 段错误 | 可被利用，整个交易系统被攻陷 |

**对答案的 HFT 加码**：每道题做完，多问一句——"这段代码在 -O2 + 多线程 + 长时间运行下还安全吗？" 如果答案是"不一定"，那就还有坑。HFT 的代码标准是**确定性优先于正确性**——宁可显式慢一点（加 `volatile`、加内存屏障），也不要依赖编译器的"善意"。
