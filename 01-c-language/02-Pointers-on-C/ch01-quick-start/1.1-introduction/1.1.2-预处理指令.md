# 1.1.2 预处理指令

## 本节讲什么

以 **`#` 开头**的指令在**编译前**由预处理器处理。本章只讲最常用的 **`#include`**；完整的宏（`#define`）、条件编译（`#ifdef`）、文件包含路径、include guard 在 **ch14** 展开。这一节的价值是建立"预处理是独立的一阶段"这个认知——它**只做文本操作**，不懂 C 语法。

## `#include` 的两种形式

```c
#include <stdio.h>      /* 角括号：系统/标准库 */
#include "myhdr.h"       /* 双引号：本地头文件 */
```

| 形式 | 搜索路径（典型） | 用途 |
|------|------------------|------|
| `<...>` | `-I` 目录 → 系统头目录（`/usr/include`）→ 标准库 | 标准库、第三方库（`<rte_*.h>`、`<linux/*.h>`） |
| `"..."` | 当前源文件目录 → `-I` → 系统目录 | 项目内自家头文件 |

> 两种形式**技术上只是搜索路径顺序不同**，标准并未严格规定；但工程约定俗成：系统头用 `<>`，自家头用 `""`。

### 路径控制的工程价值

```bash
gcc -I./include -I/opt/dpdk/include main.c
```

- `-I` 把目录加入搜索路径——DPDK/内核构建系统的核心机制
- meson/cmake 最终也是生成 `-I` 参数
- 路径顺序决定**同名头文件优先用哪个**——这是"头文件遮蔽"bug 的根源

## 预处理只做文本操作（关键认知）

`#include <stdio.h>` 的全部语义就是：**把 `stdio.h` 的文本内容原样插入到这一行的位置**。它：

- **不理解 C 语法** —— 只是文本拼接
- **不检查类型** —— 类型检查在编译阶段（`-S`）才发生
- **不链接实现** —— `printf` 的实现在 libc，链接阶段才解析

```c
/* main.c 预处理前 */
#include <stdio.h>
int main(void) { printf("hi"); return 0; }

/* main.c 预处理后（main.i，简化示意）*/
extern int printf(const char *, ...);
int main(void) { printf("hi"); return 0; }
```

`printf` 的**声明**被 `stdio.h` 带进来了，但**定义**还在 libc.so 里——这就是为什么编译能过、链接可能失败（`undefined reference`）。

## 编译四阶段之「预处理」

```bash
gcc -E main.c -o main.i
```

预处理器在这一步做四件事：

1. **展开 `#include`** —— 把头文件内容插入
2. **替换 `#define` 宏** —— 宏展开（ch14）
3. **删除注释** —— 替换成单个空格（见 1.1.1）
4. **处理 `#ifdef / #if / #endif`** —— 条件编译，保留匹配分支

### 产物体积的现实

- 一个 `#include <stdio.h>` 的 `main.c`，预处理后 `.i` 可能上千行
- `#include <rte_mbuf.h>` 的 DPDK 文件，`.i` 可能上万行——宏展开是 DPDK 构建慢的原因之一
- 内核头文件同理，`linux/` 头依赖链深，`.i` 巨大

```bash
gcc -E main.c | wc -l    # 看预处理后的行数
```

## 头文件多为"声明"，不是"实现"

| 头文件给 | 实现在 |
|---------|-------|
| 函数原型 `int printf(const char *, ...);` | libc.so（标准库） |
| 结构体定义 `struct rte_mbuf { ... };` | 该库的 `.c` 文件 |
| 宏 `#define RTE_MAX(x,y) ...` | 内联展开，无独立实现 |
| `extern` 变量声明 | 某个 `.c` 文件的定义处 |

**链接阶段**才把"声明的符号"和"实现的符号"匹配上。匹配不上就是 `undefined reference to xxx`——这是初学者最常见的链接错误。

## include guard：头文件被多次包含怎么办

```c
/* myhdr.h */
#ifndef MYHDR_H
#define MYHDR_H
/* ... 实际内容 ... */
#endif
```

- 同一个 `.c` 间接 `#include` 同一头多次（如 `a.h` 和 `b.h` 都 include `stdio.h`），预处理会插入两次 → 结构体重定义错误
- **include guard** 用宏确保只展开一次
- 替代方案 `#pragma once`（非标准但主流编译器都支持）

详见 **ch14**。

## HFT / 内核 / DPDK 视角

| 场景 | 预处理的角色 |
|------|--------------|
| DPDK | 海量 `rte_*.h` + 宏，`.i` 巨大，构建慢；`-I` 路径要包含 DPDK 安装目录 |
| 内核模块 | `#include <linux/module.h>` 触发内核构建系统（Kbuild）的复杂展开 |
| 跨平台 | `#ifdef __x86_64__` / `#ifdef __aarch64__` 区分架构——同源码适配多 ISA |
| 编译选项 | `#ifdef NDEBUG` 区分调试/发布；HFT 常用宏切换低延迟与可观测模式 |

## 常见误区

| 误区 | 纠正 |
|------|------|
| "`#include` 会把库的实现也带进来" | 只带声明；实现在 `.so`/`.a`/`.c`，链接时才合并 |
| "`<>` 和 `""` 是不同的指令" | 只是搜索路径顺序不同，标准未严格区分 |
| "头文件改了不用重新编译" | 头是文本插入，改了所有依赖它的 `.c` 都要重编——这正是增量构建系统的工作 |
| "宏和函数差不多" | 宏是文本替换，没有类型检查、有副作用陷阱（ch14.2.4） |
| "预处理能做条件判断如 `if`" | 只能 `#if`/`#ifdef`，是编译时文本裁剪，不是运行时分支 |

## 实操

1. `gcc -E main.c -o main.i`，用编辑器打开 `.i`，看 `#include` 展开后的规模
2. `gcc -E main.c | wc -l` 对比不同头文件的展开行数
3. 写一个 `a.h`、`b.h` 都 include `stdio.h` 的例子，去掉 guard 看重定义报错，加回 guard 看通过
4. DPDK 工程：`gcc -E` 一个 `rte_mbuf.h` 引用，感受 `.i` 体积

## 代码自测

**题目 1：** 以下预处理指令有什么问题？
```c
#include <stdio.h>
#include "stdio.h"
```

<details>
<summary>参考答案</summary>

功能上都能引入 stdio.h，但语义不同：<stdio.h> 在系统目录搜索（标准库），"stdio.h" 先在当前目录搜索再搜索系统目录。对于标准库应该用 <>, 用 "" 虽然能工作但不符合惯例，且如果当前目录有同名文件会引入错误的头文件。

</details>
