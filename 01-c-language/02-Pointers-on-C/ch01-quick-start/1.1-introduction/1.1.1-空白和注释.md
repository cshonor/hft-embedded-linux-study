# 1.1.1 空白和注释

## 本节讲什么

C 的**词法层**忽略大部分空白；**注释**是文档化代码的工具。这两件事看似琐碎，但工业底层项目的格式规范、diff 可读性、`/* */` 与 `//` 的取舍、以及"注释删除发生在预处理阶段"这件事——全都在这一节埋下伏笔。

## 空白：词法上的"自由形式"

### 规则

- **空格、制表符、换行**在词法分析阶段**基本等同**（preprocessor tokens 和字符串字面量内部除外）
- C 是**自由形式语言**——理论上你可以把整个程序写在一行，或每个 token 一行
- 但**自由不等于随意**——团队风格一致性 >> 个人偏好

### 历史背景

- C 的自由形式源于 **BCPL → B → C** 的演进，早期 Unix 代码就有多种排版风格
- 1979 年《C Programming Style》和后来 `indent`、`gofmt` 思想的流行，确立了"格式化交给工具"的传统
- 今天 **`clang-format`** 是事实标准，内核有 `clang-format` 配置，DPDK 也有

### 为什么空白不是"小事"

| 场景 | 空白的影响 |
|------|-----------|
| **diff / review** | 统一缩进让改动一目了然；混用 tab/space 会让 diff 全文飘红 |
| **合并冲突** | 不一致格式是 merge conflict 的头号元凶 |
| **`git blame`** | 一次格式大改会让 blame 历史断裂，查不到真正作者 |
| **嵌入式受限编辑器** | tab 宽度不一在某些老终端会错位 |

> **工程铁律**：项目里要么全 tab，要么全 space（内核用 tab，DPDK/多数现代项目用 4-space），**绝不混用**，并用 `.editorconfig` + `clang-format` 强制。

## 注释：两种语法

```c
/* 块注释：内核代码传统上仅推荐这种 */
// 行注释：C99 引入，用户态工程常用

/*
 * 多行说明：函数意图、不变量、返回值
 * 内核风格：每行以 " * " 开头
 */
```

### `/* */` vs `//` 的取舍

| 维度 | `/* */` | `//` |
|------|---------|------|
| 标准 | K&R 时代就有（非标准但广泛支持）→ **C89/C90** 正式 | **C99** 引入 |
| 多行 | 原生支持 | 每行都要 `//` |
| 嵌套 | **不能嵌套**（`/* /* */ */` 提前结束） | 可在块注释内出现 |
| 内核偏好 | 主流（Linus 明确要求） | 较少 |
| 用户态/HFT | 两者并存，团队统一即可 | 团队统一即可 |
| 临时屏蔽代码块 | `#if 0 ... #endif` 更安全（块注释不能嵌套会出错） | — |

### 嵌套陷阱（常见错误）

```c
/* 临时屏蔽一大段
/* 内部本来就有块注释 */
*/
```

第一个 `*/` 就结束了外层注释，剩下的 `*/` 成了语法错误。**临时屏蔽代码用 `#if 0 ... #endif`**，不用 `/* */`。

## 好注释 vs 烂注释

### 好注释解释"为什么"

```c
/* 必须按 little-endian 解析：交易所行情字段规定 LE */
uint32_t price = le32toh(*p);
```

### 烂注释复述代码

```c
i++;          // increment i        ← 毫无价值
i = i + 1;    /* i 加一 */          ← 更糟
```

| 好注释写什么 | 烂注释长什么样 |
|-------------|---------------|
| 函数意图、不变量、边界条件 | 复述每一行代码做什么 |
| 为什么用这个算法/这个魔数 | "这里加一" |
| 参数、返回值、错误码语义 | 过时的设计文档（代码改了注释没改） |
| 已知缺陷、TODO、性能假设 | 冗余的类型说明（类型一眼能看到） |

> **口诀**：注释回答 **why**，代码回答 **how**。能用函数名/变量名表达的，别靠注释。

## 注释的预处理阶段删除（底层细节）

注释在**预处理阶段**被删除（替换成单个空格），所以：

- 注释**不进入编译产物** —— `.o` 里没有注释，运行时也没有
- `gcc -E main.c` 看到的 `.i` 文件里注释已经消失
- 所以注释**不影响性能**（别担心"注释太多让程序变慢"）
- 但注释**影响编译后的 token 流**：`a/* */b` 会被预处理成 `a b`（两个 token）还是 `ab`？C 标准规定替换成一个空格，所以是 `a b`。极少出错但要心里有数

### 字符串内的"伪注释"

```c
char *s = "/* this is not a comment */";
```

字符串字面量内的 `/*` 不被当注释——词法分析先识别字符串，再识别注释。

## 工程规范（仓库配套）

1. **统一缩进**（4-space 或 tab，项目级 `.clang-format`）
2. **大括号风格**：K&R（`{` 同行）或 Allman，统一即可
3. **公共 API 注释**：参数、返回值、错误码、线程安全性
4. **避免无意义注释**（`i++ // increment i`）
5. **大段屏蔽用 `#if 0`**，不用 `/* */`

## 常见误区

| 误区 | 纠正 |
|------|------|
| "注释越多越好" | 烂注释是噪声，比没注释还糟；好注释精而少 |
| "注释会拖慢程序" | 预处理就删了，零运行时影响 |
| "`//` 是 C 一直就有的" | C99 才标准化；C90 不保证，老嵌入式编译器可能不支持 |
| "用 `/* */` 屏蔽大段代码很方便" | 不能嵌套，遇到内含块注释就出错；用 `#if 0` |
| "格式风格可以自由发挥" | 团队必须统一，且交给工具强制 |

## 自测要点

- C 的空白在词法层基本等同，有哪两个**例外**？（字符串字面量内部、preprocessor token 之间在某些情况）
- `/* /* */ */` 为什么是错的？正确屏蔽大段代码用什么？
- 注释在哪个编译阶段被删除？这有什么现实推论？（不影响性能、`.i` 里看不到）
- 字符串内的 `/*` 会被当注释吗？为什么？

## 代码自测

**题目 1：** 以下代码输出什么？为什么？
```c
int a = 1, b = 2;
// printf("%d %d\n", a, b);
    printf("%d\n", a + b);
```

<details>
<summary>参考答案</summary>

输出 3。// 注释从 // 到行尾，所以 printf("%d %d\n", a, b); 被注释掉，只有 printf("%d\n", a + b); 执行。注意：// 是 C99 才引入的行注释，C89 不支持。

</details>
