# 9.3.1 复制字符串

## 本节讲什么

**`strcpy(dst, src)`** 是 C 字符串复制函数的"原始版"：从 `src` 逐字节拷贝到 `dst`，**直到遇到 `\0`（含 `\0` 本身）**，**完全不检查 `dst` 容量**。它是 C 标准库里最高危的函数之一，几乎所有缓冲区溢出 CVE 的教科书案例都涉及 `strcpy`。本节剖析其机制、风险与替代方案。

## 要点

### 函数原型与行为

```c
char *strcpy(char *dst, const char *src);
```

- 从 `src` 拷贝到 `dst`，**含终止 `\0`**
- 返回 `dst`（链式写法用）
- **不检查 `dst` 大小**——若 `strlen(src) + 1 > sizeof(dst)`，溢出 UB
- 若 `src` 与 `dst` 重叠 → UB（应用 `memmove`）

### 简化实现

```c
char *strcpy(char *dst, const char *src) {
    char *ret = dst;
    while ((*dst++ = *src++)) /* 括号内赋值，遇 \0 退出 */
        ;
    return ret;
}
```

**整行就一个 `while` 头**，C 代码 golf 的典范。但简洁背后是零防御。

### 汇编视角（x86-64）

```
strcpy:
    mov    rax, rdi            ; 保存 dst 作为返回值
.L1:
    movzx  edx, BYTE PTR [rsi] ; 读 src 字节
    mov    BYTE PTR [rdi], dl  ; 写 dst
    inc    rsi
    inc    rdi
    test   dl, dl              ; 是否 \0？
    jne    .L1                 ; 非零继续
    ret
```

glibc 实际用 SSE2/AVX2 一次比对 16/32 字节，但**仍必须扫到 `\0`**——SIMD 只是加速，不改变语义。

### 风险等级

| 风险 | 说明 | 后果 |
|------|------|------|
| **dst 溢出** | `dst` 小于 `src+1` | 栈/堆踩踏，控制流劫持 |
| **src 无 `\0`** | 越界读 src | UB，可能泄露相邻内存（Heartbleed 模式） |
| **重叠** | `dst` 与 `src` 重叠 | UB，结果不可预测 |
| **二进制 src** | 含 0x00 的报文 | 提前截断，语义错误 |

### 替代方案对比

```c
/* 1. strncpy：限长但仍危险 —— 不保证补 \0 */
strncpy(dst, src, sizeof(dst) - 1);
dst[sizeof(dst) - 1] = '\0';   /* 必须手动补 */

/* 2. snprintf：安全，总是补 \0 */
snprintf(dst, sizeof dst, "%s", src);

/* 3. strlcpy：BSD/内核，返回需写总长，便于检测截断 */
strlcpy(dst, src, sizeof(dst));   /* 返回 strlen(src) */

/* 4. strscpy：Linux 内核 2016 引入，返回 -E2BIG 表示截断 */
strscpy(dst, src, sizeof(dst));

/* 5. memcpy：二进制，显式 n，HFT 首选 */
memcpy(dst, src, n);   /* n 已知，与 \0 无关 */
```

### strncpy 的两个坑

```c
char buf[8];
strncpy(buf, "hello world", sizeof(buf));
/* buf = {'h','e','l','l','o',' ','w','o'} —— 无 \0！ */
printf("%s", buf);   /* UB：越界读直到碰巧 \0 */
```

1. **src 长 ≥ n 时不补 `\0`**——必须手动 `buf[n-1]='\0'`
2. **src 短时填充 `\0` 到 n 字节**——浪费 CPU，`strlcpy` 不做这种填充

### strlcpy 的优势（OpenBSD 1996）

```c
size_t strlcpy(char *dst, const char *src, size_t dstsize);
```

- 拷贝至多 `dstsize-1` 字节，**总是补 `\0`**
- 返回 `strlen(src)`，便于调用方判断是否截断（`if (ret >= dstsize) /* 截断 */`）
- 不做 `strncpy` 那种无意义填充
- Linux 2016 年（4.3 起）引入内核，glibc 2.38（2023）终于加入用户态

### 实操：strcpy vs memcpy 对含 0x00 数据

```c
uint8_t raw[] = { 'A', 'B', 0x00, 'C', 'D' };
char a[8], b[8];

strcpy(a, (const char *)raw);   /* a = "AB\0" —— 截断在 0x00 */
memcpy(b, raw, sizeof raw);     /* b = {'A','B',0,'C','D',0,0,0} —— 完整 */
```

`strcpy` 看到第三个字节 0x00 就停，丢失了 `CD`；`memcpy` 按 `n=5` 完整拷贝。这是 C 字符串与二进制字节流的本质区别。

## HFT 关联

- **DPDK rte_memcpy**：基于 `memcpy` 的优化版，按对齐和长度选择 SSE/AVX 路径，4-64 字节范围比 glibc `memcpy` 快 1.5-3 倍，HFT 报文拷贝主力
- **报文头部拷贝**：`memcpy(hdr, pkt, sizeof(hdr))` 长度编译期已知，`-O2` 下常被展开为寄存器移动
- **配置字符串拷贝**：`rte_eal_init` 的 argv 处理可用 `strlcpy`，但运行时配置结构体字段拷贝用 `memcpy` + `sizeof`
- **FIX tag 拷贝**：变长字段用 `memcpy(dst, src, field_len)`，`field_len` 由解析器算出
- **严禁**：在 mbuf payload 上调 `strcpy`——payload 可能含 0x00 且无 `\0` 终止

### 漏洞案例：Morris 蠕虫（1986）

`fingerd` 服务用 `strcpy` 拷贝用户输入到栈缓冲，Morris 蠕虫构造超长输入覆盖返回地址，感染约 6000 台机器（当时互联网的 10%）。这是 `strcpy` 漏洞的"零号病人"，直接催生了 CERT/CC。

### 漏洞案例：Heartbleed（2014）

OpenSSL 用 `memcpy` 但**用了攻击者控制的长度**而非真实长度，等价于"带了长度参数的 strcpy 溢出"。教训：**长度参数本身必须来自可信源**，不能信任协议字段。
