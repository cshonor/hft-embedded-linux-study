# 6.11 指针表达式

## 本节讲什么

**指针与数组的等价关系**、**指针数组 vs 数组指针**、**字符串与字符指针**——这三组概念是"数组 ≠ 指针"误区的总根源，也是协议解析、字符串处理正确性的前提。本节把它们一次讲透。

## 要点

### `arr[i]` ≡ `*(arr + i)`（核心等价）

```c
char buf[64];
buf[3] == *(buf + 3);     /* 永远相等 */
3[buf] == *(3 + buf);     /* 也合法但禁止写 —— 交换律的副产品 */
```

C 标准把 `E1[E2]` 定义为 `*((E1)+(E2))`，加法可交换，所以 `3[buf]` 合法。工程上从不这么写，但理解它揭示了下标的本质。

### 数组名的三种语义（最易错）

| 表达式 | 含义 | 类型 |
|--------|------|------|
| `buf`（多数上下文） | 首元素地址 `&buf[0]` | `char *` |
| `sizeof(buf)` | 整个数组的大小 | 编译期常量 64 |
| `&buf` | "指向整个数组的指针" | `char (*)[64]` |
| `&buf[0]` | 首元素地址 | `char *` |

```c
char buf[64];
char *p = buf;            /* buf 退化为 &buf[0]，char* */
char (*arrptr)[64] = &buf;/* &buf 是"指向 64 元数组的指针" */
size_t n = sizeof(buf);   /* 64，不退化 */
```

数组名在 `sizeof`、`&`、字符串字面量初始化的 `[]` 之外，**都退化为首元素指针**。

### 指针数组 vs 数组指针（经典区分）

```c
struct rte_mbuf *pkts[32];        /* 指针数组：32 个 mbuf*，pkts 是 struct rte_mbuf**(退化后) */
struct rte_mbuf (*row)[32];       /* 数组指针：1 个指针，指向 32 元数组 */
```

| 声明 | 类型 | 含义 |
|------|------|------|
| `T *arr[N]` | `T *[N]` → 退化为 `T **` | N 个 T* 摆一起 |
| `T (*p)[N]` | `T (*)[N]` | 一个指针，指向 T[N] |

读法（**螺旋法则**，ch13 详）：从变量名出发，先右后左，遇 `()` 跳出。

### 字符串与字符指针

```c
char *s = "rodata";        /* 字符串字面量在 .rodata，只读 */
s[0] = 'R';                /* SIGSEGV —— 改只读段 */

char t[] = "writable";     /* t 是栈数组，字面量被拷贝进来 */
t[0] = 'W';                /* OK */

const char *proto = "FIX.4.2";  /* 推荐：const 标记只读意图 */
```

| 形式 | 存储 | 可改 | 用途 |
|------|------|------|------|
| `char *s = "abc"` | `.rodata` | 否（改崩） | 只读常量 |
| `char t[] = "abc"` | 栈/全局 | 是 | 可改缓冲 |
| `const char *s = "abc"` | `.rodata` | 否（编译器拦） | 只读常量（推荐） |

`char *s = "abc"` 在 C89 合法但 C11 起 deprecated，C23 起 UB——应一律用 `const char *`。

### 拆解 `*(uint32_t *)&f`：从右往左一步一块

**指针表达式的通读法：从右往左，一步一个操作。** 以"偷看 float 位模式"的经典写法为例：

```c
float f = 1.0f;                /* f 是 float，占 4 字节 */
uint32_t bits = *(uint32_t *)&f;
```

画符号拆分：

```c
uint32_t bits =  *  (uint32_t *)  &f;
                 ↑        ↑         ↑
                 │        │         │
              解引用    强制转换   取 f 的地址
```

| 步骤 | 表达式 | 做了什么 | 结果类型 |
|------|--------|----------|----------|
| ① | `&f` | 取地址符 `&`：拿变量 f 的内存地址 | `float *` |
| ② | `(uint32_t *)&f` | 强制转换 cast：让编译器把**这个地址**强行解释成"指向 `uint32_t` 的指针"。**只改指针类型，地址本身一个字节都没动**，还是 f 原来那块内存 | `uint32_t *` |
| ③ | `*(uint32_t *)&f` | 最前面的 `*` 解引用：顺着指针去内存，读 4 个字节，**当作 `uint32_t` 整数** | `uint32_t`（右值） |

整句翻译成人话：**拿到 f 的地址，假装那里存的不是 float 而是 uint32_t，把 4 字节原样读出来，赋给 bits。** 得到的就是 IEEE 754 位模式：`f = 1.0f` 时 `bits == 0x3F800000`。

#### 为什么这个写法是 UB（严格别名规则）

内存里真实存放的是 `float`，却用 `uint32_t *` 类型的指针去访问它——**C 标准的严格别名规则（strict aliasing）禁止用不匹配类型的指针解引用一块内存**（有效类型规则，C11 6.5p7）。合法的别名例外只有：完全同类型、`signed/unsigned` 配对、`char *` 可以别名任何对象。

后果的诡异之处在于"看场合发作"：

| 编译条件 | 表现 |
|----------|------|
| `-O0` 调试 | 大多数时候跑着"正常"——没触发别名相关优化 |
| `-O2` 优化 | 编译器基于"不同类型指针不会指向同一内存"的假设重排/删除代码，这行可能被整个干掉，或读出错误数值——**灵异 bug** |

#### 安全写法：memcpy

```c
#include <string.h>                      /* 头文件 */
void *memcpy(void *dest, const void *src, size_t n);
```

**直译：内存拷贝——把 `src` 指向的内存复制 `n` 个字节，写到 `dest` 的内存。它只搬运原始字节，完全不管里面存的是什么 C 类型。**

| 参数 | 含义 |
|------|------|
| `dest` | 目标内存地址（复制写到这里） |
| `src` | 源内存地址（从这里读字节） |
| `n` | 复制多少**字节**（不是元素个数！） |

回到 float → uint32_t 的例子：

```c
float f = 1.0f;
uint32_t bits;
memcpy(&bits, &f, sizeof(bits));   /* sizeof(bits) = 4 字节 */
```

动作：把 f 的 4 个原始字节**一字不差复制**到 bits 的内存。memcpy 只看字节，它不懂什么叫 float、什么叫 uint32_t——不做数值转换，只搬运二进制比特。

#### 为什么 memcpy 合法而指针强转 UB：读的是谁的内存

| 写法 | 内存访问路径 | 判定 |
|------|--------------|------|
| ❌ `*(uint32_t *)&f` | 用 `uint32_t *` **直接访问 f 本身那块内存**——类型不匹配，违反严格别名，编译器优化时可乱改代码 | UB |
| ✅ `memcpy(&bits, &f, 4)` | **从不用别的类型指针读 f**——先把字节拷一份到新变量 bits，之后读的是 **bits 自己的内存**，bits 本来就是 `uint32_t`，类型完全匹配 | 合规 |

**生活化比喻**：float 是个装了 4 个字节的盒子。
- 指针强转 = 不搬家，拿另一把钥匙强行撬开 float 盒子直接读——C 规则不允许。
- memcpy = 把盒子里 4 块东西完整复制一份放进全新的 uint32_t 盒子，之后只操作新盒子，原盒子不动——合法。

**编译器优化小知识**：`-O2` 下编译器识别这段定长 memcpy，**不会真的产生函数调用开销**，直接优化成寄存器移动指令（一条 `mov`）——性能和指针强转一模一样。

> 同族合法工具：union 类型双关（C11 起明确合法：写一个成员、读另一个是允许的）；`char *`/`unsigned char *` 别名任何类型读字节也合法——memcpy 的标准语义正是"按 `unsigned char` 逐字节访问"，所以天然落在别名例外里。`*(uint32_t *)&f` 是三者中唯一踩 UB 的。

#### memcpy 的两个坑

1. **按字节计数，不是按元素个数**：`memcpy(dst, src, count)` 若 count 写成元素个数，只拷了零头。
2. **源和目标不能重叠**：重叠必须用 `memmove`（先比地址选拷贝方向）。ASan 能检测：`memcpy-param-overlap`。

→ 机制、`memmove` 实现、SIMD 性能数字详见 **ch09 9.9 内存操作**。

## 底层映射

### `buf[3]` 的汇编

```c
char buf[64];
char c = buf[3];
```

```
; x86-64 -O2
movsx   eax, BYTE PTR [rsp+3]    ; 直接 [rsp+3]，编译期算好偏移
```

数组在栈上，`buf[3]` 编译期已知偏移 = 3 字节，直接 `[rsp+3]`。若是指针：

```c
char *p = ...;
char c = p[3];
```

```
movsx   eax, BYTE PTR [rdi+3]    ; p 在 rdi，运行期地址 + 3
```

差异：数组偏移编译期定，指针偏移运行期加。`-O2` 后两者常归一，但数组大小信息会丢（退化）。

### 数组退化的边界

```c
void f(int arr[10]) { sizeof(arr); }   /* 退化成 int*，sizeof = 8，不是 40 */
```

函数参数里的 `int arr[10]` 完全等价于 `int *arr`，长度信息丢失——这是 `sizeof(arr)` 在函数内返回指针大小的根因。所以数组函数必须**额外传长度**。

## HFT / DPDK

| 场景 | 用法 |
|------|------|
| 批量收包 | `rte_eth_rx_burst(port, q, pkts, BURST)`：`pkts` 是指针数组 |
| 协议字面量 | `const char *proto = "FIX.4.2";` 只读 |
| 可改报文缓冲 | `char buf[N]` 或 malloc，可改 |
| 报文头部访问 | `*(uint16_t *)(pkt + 12)` 取以太类型（DPDK 保证对齐/字节序，独立处理） |
| 行情字段位模式 | 查 NaN payload、快速 float 格式化前先取位模式——**用 `memcpy`，不用指针 cast** |

## 常见误区

| 误区 | 事实 |
|------|------|
| "数组就是指针" | 不是——数组有大小信息，多数表达式里退化为指针 |
| "`sizeof(arr)` 在函数内能拿数组大小" | 退化成指针，拿到 8 |
| "`char *s = "abc"; s[0]='X';` 没事" | `.rodata` 只读，`SIGSEGV` |
| "`3[buf]` 是错的" | 标准合法（`*(3+buf)`），但禁止写 |
| "`T *a[N]` 和 `T (*a)[N]` 一样" | 完全不同：前者 N 个指针，后者 1 个指向数组的指针 |
| "`(uint32_t *)&f` 这一步就 UB 了" | 不是——cast 只改指针类型不碰内存，**解引用那一刻才 UB** |
| "`*(uint32_t *)&f` 一直能跑就没事" | 违反严格别名是 UB，`-O0` 正常 `-O2` 出灵异 bug |
| "改类型转换太丑，cast 写法更快" | 定长 `memcpy` 会被优化成一条 `mov`，零开销且合法 |

## 代码自测

**题目 1：** 以下表达式中哪些可以作为左值？
```c
char ch = 'a';
char *cp = &ch;
// A: *cp
// B: cp + 1
// C: *(cp + 1)
// D: ++cp
```

<details>
<summary>参考答案</summary>

A 和 C 可以是左值。A *cp 解引用指针，得到 ch，可赋值。C *(cp + 1) 解引用 cp+1 处的地址，语法上是左值（虽然此处可能越界）。B cp + 1 是指针运算结果，是右值。D ++cp 修改 cp 本身，表达式结果是右值。

</details>

**题目 2：** 逐行标注，哪一行出错？
```c
float f = 1.0f;
float *pf = &f;                 // 行 1
uint32_t *pu = (uint32_t *)&f;  // 行 2
uint32_t x = *pu;               // 行 3
```

<details>
<summary>参考答案</summary>

**行 1、行 2 都合法，UB 发生在行 3（解引用那一行）。**

- 行 2 只是定义一个指针并赋值：cast 改变的是**指针变量的类型**，让它合法地持有这个地址——不读也不写 f 的内存，没有任何内存访问发生，所以不出错。
- 行 3 `*pu` 才真正顺着指针去**访问内存**。此时用 `uint32_t *` 读一块有效类型为 `float` 的对象，违反严格别名规则（C11 6.5p7），UB 在这一刻触发。

教训：**指针 cast 本身无罪，解引用才是分水岭。**（另外 `pf` 没被使用，只是示例对照。）

</details>

**题目 3：** memcpy 版会触发严格别名 UB 吗？
```c
int a = 0x12345678;
char buf[4];
memcpy(buf, &a, 4);
```

<details>
<summary>参考答案</summary>

**不会。** 两层原因：

1. **memcpy 的标准语义就是"按字符（字节）逐个拷贝"**——C 标准定义 memcpy 从 src 拷 n 个字符到 dest，等价于用 `unsigned char` 访问内存。而 `char`/`unsigned char` 正是严格别名规则（C11 6.5p7）里明确的合法例外：**字符类型指针可以访问任何类型对象的内存**。所以读 `a` 的字节这一步合规。
2. **写和读也类型匹配**：字节写进 `char buf[4]`，之后用 `char` 类型读 `buf`——char 数组被 char 访问，天然合法。全程没有任何"不匹配类型的解引用"发生。

对比上一题：UB 的本质是"**用什么类型的 lvalue 去访问内存**"，不是"碰了别的类型对象的字节"。memcpy 全程只以字符类型身份访问，所以永远不踩别名雷。

附带收获：小端机上拷完 `buf[0]=0x78, buf[1]=0x56, buf[2]=0x34, buf[3]=0x12`——这正是检测大小端的经典手法（注意 `buf` 没有 `\0`，不能当字符串用，详见 ch09）。

</details>
