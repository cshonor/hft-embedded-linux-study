# 18.10 GCC 属性总览（`__attribute__`）

> **两篇的分工**：本篇是**深度实测篇**——`noreturn` / `pure` / `const` / `used` / `constructor` / `packed` 撒谎与失效的实测后果与性能数据。
> **完整属性总纲（全表 + 诊断类 + `cleanup` + `may_alias` + `visibility` + 可移植封装）** 在
> [6.6.1 GNU C 编译器扩展关键字 `__attribute__`](../../../05-Kernel-Prep-Embedded-C-Self-Cultivation/ch06-gnu-c-extensions/6.6-section/6.6.1-GNU-C编译器扩展关键字-__attribute__.md)（第 5 本书 ch06 GNU C 扩展）。

## 本节讲什么

`__attribute__((...))` 是 **GCC/Clang 编译器扩展**，不属于 C 标准。它给**函数、变量、类型**附加元信息：要求编译器做额外检查、改变优化决策、修改内存布局或 ELF 段布局。

语法：`__attribute__((属性1, 属性2, ...))`——**双层括号**，多个属性逗号分隔。可修饰三类对象：

| 修饰对象 | 典型属性 | 本节小节 |
|----------|---------|---------|
| 函数 | `format` `noreturn` `used` `unused` `pure`/`const` `noinline`/`always_inline` | [函数属性](#函数属性) |
| 全局/局部变量 | `aligned` `section` `used` `unused` | [变量与内存布局属性](#变量与内存布局属性) |
| struct / union 类型 | `packed` `aligned` | [变量与内存布局属性](#变量与内存布局属性) |

> **注意**：`packed` / `aligned` 的对齐计算与协议头写法 **10.3** 已经讲透，本节只补那里没有的部分——`section` 段布局，以及"未对齐访问到底会不会崩"的实测真相。

本节全部结论用 **gcc 13.3 + clang 18.1（WSL Ubuntu 24.04, x86-64）** 实测坐实。三个发现与流行说法不同，先列出来<｜hy_place▁holder▁no▁813｜>口径：

- ⚠️ **谎称 `noreturn` 不是"可能有 UB"，实测直接 SIGSEGV（退出码 139）**，`-O0` 与 `-O2` 都崩
- ⚠️ **`packed` 直接访成员不会崩**（gcc 生成安全字节访问）；真正 UB 的是**用 `int*` 强转再解引用**——这条才有 UBSan 证据
- ⚠️ **`used` 拦不住链接器 `gc-sections`**：`-O2` 保住了符号，`--gc-sections` 照样把它删了

## 要点

### 语法位置与三点前提

```c
/* 属性写在声明处，通常紧贴对象之前或之后 */
void die(void) __attribute__((noreturn));
struct __attribute__((packed)) msg { char c; int i; };
__attribute__((aligned(16))) int buf16;
```

**前提 1：它不是标准。** C 标准没有它，MSVC 完全不认——Windows 上直接语法报错（见[可移植写法](#可移植写法宏封装)）。

**前提 2：GCC 与 Clang 都支持，但诊断措辞与强度不同。** 同一个错位写法（见 `format` 小节），gcc 说 `refers to parameter type 'int'`，clang 说 `format argument not a string type`；两者都判 `error`。

**前提 3：多数属性是"允许"，少数是"要求"。** `inline` 是提示（`-O0` 下不管用），`always_inline` 是要求（做不到直接 `error`）。后面逐个标注。

## 函数属性

### `format`——编译期检查格式串

```c
void log_msg(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
/*                                                    ↑       ↑  ↑
                                              printf 语义  fmt第1参  可变参从第2参起 */
```

**Quiz 回答：**

```c
void my_log(int prio, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));
```

- **`2`**：格式字符串是**第 2 个**函数参数（`fmt`），从 1 开始数
- **`3`**：可变参数 `...` 从**第 3 个**参数开始——也就是编译器从第 3 个实参起逐个对照 `%` 占位符

这次的 `2,3` 是**对的**（第 1 参是 `prio`，跳过它才轮到格式串）。实测 gcc 13.3（`-Wall -Wformat -Wattributes`）：

```
fm.c:23:17: warning: format '%d' expects argument of type 'int', but argument 3 has type 'double' [-Wformat=]
fm.c:24:20: warning: format '%s' expects a matching 'char *' argument [-Wformat=]
```

clang 18.1 同场景同样抓到（措辞略异）：

```
warning: format specifies type 'int' but the argument has type 'double' [-Wformat]
warning: more '%' conversions than data arguments [-Wformat-insufficient-args]
```

**⚠️ 与上一节的对照（重点）**：同一个 `2,3` 写在**只有一个固定参数**的 `test(const char *fmt, ...)` 上就错了——那里正确的本应是 `1,2`。而如果把 `1,2` 写在 `my_log(int prio, const char *fmt, ...)` 上：

```
fm_bad.c:11:1: error: 'format' attribute argument 2 value '1' refers to parameter type 'int'
                                                              ↑ 第 1 参是 int(prio) 不是 char*
exit=1            ← gcc：直接 error
```

clang 侧：`error: format argument not a string type`。

> **同一个属性值，换个函数签名就从"正确"变成"编译失败"**——它永远是"第 m 个参数是 `const char *`、第 n 个参数开始是可变参"，只对当前这个函数有意义。

**为什么值得较真？看属性没生效时的运行时代价。** 上面三条调用在**属性失效后**的真机输出：

```
1                 ← my_log(1, "%d\n", 3.14)：double 塞给 %d，读出 leading garb
1 (null)          ← my_log(2, "%d %s\n", 1) ：少一个实参，%s 从寄存器垃圾里拿到 NULL
ok yes            ← 唯一正确的一条
```

退出码 0，**不崩、不报警、静默输出错值**。这就是为什么 `-Wattributes` 必须开——它是唯一会指出"属性索引越界/类型不符"的开关（详细用法与 C++ 成员函数场景见 **7.6.2**）。

### `noreturn`——函数永不返回

```c
void die(void) __attribute__((noreturn));
```

给编译器做**控制流分析**：这条路径之后到不了，不必再准备返回值/恢复代码。

**作用 1：消除假告警。** 实测 `-Wall`：

```c
extern void die(void);              /* 未标注 */
int check(int x) { if (x < 0) die(); else return 1; }
```
```
nr1.c:12:1: warning: control reaches end of non-void function [-Wreturn-type]
```

加上 `__attribute__((noreturn))` 后**零告警**。

**作用 2：删死代码，连 `-O0` 都删。** `void after1(void){ real_die(); puts("UNREACHABLE"); }` 的 `-O0` 汇编：

```asm
after1:
    endbr64
    pushq   %rbp
    movq    %rsp, %rbp
    call    real_die          ← 整段到此为止，puts 的 call 连影子都没有
    .cfi_endproc
```

注意这是 **`-O0`**：删掉尾部的 `puts` 不是优化器干的事，而是 `noreturn` 本身改变了可达性判断——编译器认为那条路径永远走不到，代码根本不生成。

**⚠️ 谎称 noreturn = 实测崩。** `__attribute__((noreturn)) void liar(void){ fprintf(stderr,...); }`（没有 `exit`/`abort`，会正常返回）：

```
[liar] I return anyway
Segmentation fault (core dumped)
exit=139
```

`-O0` 与 `-O2` **都崩**。原因：编译器认为 `liar()` 之后不可达，于是 `main` 尾部没生成正常收尾指令，返回时落到未知地址。`noreturn` 是**你和编译器签的合同**，撒谎的代价是 UB——实测表现为 SIGSEGV。

```c
/* 正确：noreturn 函数必须真的不返回 */
__attribute__((noreturn)) void die(const char *msg)
{
    fprintf(stderr, "fatal: %s\n", msg);
    abort();            /* 或 exit(1) / _exit(1) / longjmp 到别处 */
}
```

### `used`——不许删符号

```c
static void kept(void) __attribute__((used));
static void kept(void) { ... }
```

典型用途：函数**只被汇编代码引用**、或只作为回调指针写进某个段（后面 `section` 小节的 initcall 就是）。

实测 `-O2` 编译后 `nm`：

```
-O2 无 used:                     -O2 有 used:
  nm uu.o | grep plain_unused      nm uu.o | grep kept
  (空 —— 符号被删干净了)            0000000000000000 t kept   ← 保住了
```

`-Wall` 还会同时给出 `warning: 'plain_unused' defined but not used [-Wunused-function]`——`used` 属性顺带把这个告警也消掉了。

**⚠️ `used` 只对编译器有效，拦不住链接器。** 加上 `-ffunction-sections` 并在链接时开 `--gc-sections`：

```
/usr/bin/ld: removing unused section '.text.kept' in file 'uu3.o'
                                        ↑ 明明标了 used，照样删
```

这与前面 7.4 记的那条规律完全一致：**管代码/符号存在的活儿分两类——编译器删还是链接器删**。`used` 只管前者；要连后者一起管，得在 linker script 里写 `KEEP(*(.text.kept))`（内核 `__initcall` 段就是这么处理的）。

### `unused`——显式声明"故意不用"

```c
int handler(int code, const char *msg __attribute__((unused)))
{
    __attribute__((unused)) int scratch;
    return code + 1;
}
```

实测 `-Wall -Wextra` 对照：

```
未加：handler_plain.c:11:41: warning: unused parameter 'unused_msg' [-Wunused-parameter]
加了：零告警
```

优于 `(void)msg;` 的强转写法——意图明确，也方便 grep 统计。三种写法对照：

| 写法 | 消除告警 | 表达意图 |
|------|---------|---------|
| `(void)msg;` | ✓ | ✗（看起来像随手加的） |
| `__attribute__((unused))` | ✓ | ✓ |
| 参数只留类型 `f(const char *)`（定义里） | ✓ | △ 可读性差 |

### `pure` / `const`——告诉编译器"可以缓存调用结果"

| 属性 | 允许 | 编译器可以做什么 |
|------|------|----------------|
| `const` | 只依赖入参，**不读也不写**任何 Memory | 公共子表达式消除、循环外提、随意重排 |
| `pure` | 可以**读**全局内存，但**不产生副作用** | 同样允许 CSE / 循环外提 |
| （无属性） | — | 每次调用都老实执行 |

**⚠️ 这是本批最阴险的一个坑——实测：结果看上去是对的，业务逻辑悄悄少执行了。**

为了让属性成为编译器的**唯一信息来源**，把被测函数放到另一个 TU（函数体不可见）：

```c
/* side.c —— 表面纯函数，实际偷偷累加全局计数 */
int g_counter = 0;
int query(int x) { g_counter++; return x + 1; }
```

调用方循环 3 次求和：

```c
for (int i = 0; i < 3; i++) s += query(10);
printf("sum=%d g_counter=%d\n", s, g_counter);
```

| `#PC_MODE` | `query` 的声明属性 | 输出 |
|------------|-------------------|------|
| 1 | 无 | `sum=33  g_counter=3` ← 正确 |
| 2 | `__attribute__((const))` | `sum=33  g_counter=1` ❌ |
| 3 | `__attribute__((pure))` | `sum=33  g_counter=1` ❌ |

**`sum` 三个都对（33），只有 `g_counter` 暴露了问题**。原因是 3 次调用被合并/外提为 1 次——返回值不依赖状态，所以肉眼看到的"结果"毫无异常；真正被跳过的是你以为会执行的副作用。想想这是哪类代码的形状：**计数、埋点、日志、时间戳、硬件寄存器读**。

> **`const` 是断言，不是优化开关。** 函数只要读了一个全局变量，就不能是 `const`；只要写了任何一个字节（含全局状态、DMA 寄存器），连 `pure` 都不能加。

### `noinline` / `always_inline`

```c
static int add_plain(int x)  { return x + 1; }                                  /* -O2 会内联 */
static __attribute__((noinline)) int add_noinline(int x) { return x + 1; }
static __attribute__((always_inline)) inline int add_always(int x){ return x+1; }
```

实测 `objdump -d`（"是否还存在独立函数体"=能否 grep 到 `<函数名>:`）：

| 函数 | `-O0` | `-O2` |
|------|-------|-------|
| `add_plain` | 保留（1） | 内联（0） |
| `add_noinline` | 保留（1） | **保留（1）** ← 属性强制生效 |
| `add_always` | **内联（0）** ← `-O0` 也展开 | 内联（0） |

对照组（普通 `inline` **关键字**，不带属性）：`-O0` 保留、`-O2` 内联。这正好证明了口头常说的那句话——

> **`inline` 是"建议"，`always_inline` 是"要求"。** 前者 `-O0` 下完全无效，后者 `-O0` 下也会展开。

**⚠️ `always_inline` 做不到时会怎样？不是静默放弃，是 `error`。** 把函数体放到另一个 TU（不用 LTO），编译 `main`：

```
ai.c:4:12: warning: 'always_inline' function might not be inlinable [-Wattributes]
ai.c:4:12: error: inlining failed in call to 'always_inline' 'far_fn': function body not available
exit=1
```

所以前面说"多数属性只是提示"这句话要打折：**有一部分属性是真·强制，gcc 宁可编译失败也不背着你妥协。**

| 属性 | 强度 | 失败时 |
|------|------|--------|
| `inline` 关键字 | 提示 | 静默不内联 |
| `noinline` | 强制 | 不会失败（总能做到） |
| `always_inline` | 强制 | **`error`（函数体不可见/递归/变长数组等）** |
| `pure` / `const` | 强制（编译器照做） | **静默错**（你撒谎 → 副作用消失） |

最后一列才是关键：**有些属性撒谎会编译报错，有些撒谎会静默出错**。`noreturn`、`pure`、`const` 属于后者。

## 变量与内存布局属性

### `packed`——取消 padding

```c
struct Plain             { char c; int i; };   /* sizeof = 8  */
struct __attribute__((packed)) Packed
                         { char c; int i; };   /* sizeof = 5  */
```

实测输出：

```
sizeof  Plain=8  Packed=5
offsetof Packed.i=1   _Alignof(Packed)=1
```

对齐规则、`#pragma pack`、以及协议头上的系统做法都在 **10.3 结构的存储分配**，这里不重复。

#### ⚠️ 「packed 会触发未对齐访问，ARM 上直接崩」——这句话只对一半

这句流传很广的话需要拆成**两条访问路径**看。实测（`-fsanitize=alignment -fno-sanitize-recover=all`）：

**路径 1：直接通过 packed struct 成员访问（`p_pad->i`）**

```c
struct P *p_pad = (struct P *)(rawp + 1);   /* 地址故意错位 1 字节 */
p_pad->i = 22;
printf("%d\n", p_pad->i);                    /* 输出 22，UBSan 零报告 */
```

**UBSan 一声不吭。** 因为编译器**看得见 `packed` 标记**，它知道这个成员可能不对齐，于是不生成 `movl $22, (%rax)`，而是拆成一串字节级存取。路径 1 是**定义良好的**，不会因为 CPU 架构而崩。

**路径 2：地址强转成普通指针（`&p_bad->i` → `int*`）**

```c
struct P *p_bad = (struct P *)(rawp + 1);
int *pi = &p_bad->i;                         /* 类型信息在这里丢失 */
*pi = 33;
```

```
pa_ub.c:28:9: runtime error: store to misaligned address 0x7fff0c22f2f2 for type 'int',
              which requires 4 byte alignment
exit=1
```

**这条才是 UB**——你把地址交给 `int*` 的一瞬间，编译器就再也不知道它可能未对齐了，会按对齐假设生成单条读写指令。gcc 也提前提醒过：

```
pa.c:23:15: warning: taking address of packed member of 'struct Packed' may result in
            an unaligned pointer value [-Waddress-of-packed-member]
```

> **规则**：packed struct 的成员可以放心访问；**不许把 packed 成员的地址赋给普通指针**。需要指针时有安全写法——`memcpy` 到局部变量：

```c
struct __attribute__((packed)) P { char c; int i; };
int  read_i_safe(const struct P *p) { int v; memcpy(&v, &p->i, sizeof v); return v; }
void write_i_safe(struct P *p, int v) { memcpy(&p->i, &v, sizeof v); }
```

内核里有专门的 `get_unaligned()/put_unaligned()`，本质就是这套 memcpy，还处理了大小端。

**架构差异（诚实边界）**：x86-64 硬件容忍未对齐访问，所以路径 2 在本机**打印出 33 且 exit 0**（UBSan 单独跑才报）。本机**没有 aarch64 交叉工具链、没有 qemu、Pi 5 不连**，ARM 侧行为**未经实测**。可以确定的是：不要指望编译器帮你兜底——写好 `memcpy` / `get_unaligned`，就不需要争论某颗 CPU 到底崩不崩。

### `aligned(N)`——强制对齐

```c
__attribute__((aligned(64))) int cache_slot;   /* 伪共享治理，见 18.3 */
__attribute__((aligned(16))) int buf16;        /* SIMD / DMA 缓冲区常用 */
```

实测运行时打印地址取模，确认真的对齐了：

```
&cache_slot % 64 = 0
&buf16      % 16 = 0
```

`N` 必须 **2 的正幂**，不是就编译失败：

```
pa3.c:1:1: error: requested alignment '3' is not a positive power of 2
```

**两个易混点**：

| 属性 | 作用 | 典型值 |
|------|------|--------|
| `packed` | 压缩**内部**：去掉成员间 padding，`sizeof` 变小 | 1 字节粒度（协议头） |
| `aligned(N)` | 放大**外部**：抬高整体对齐要求，`sizeof` 通常**变大** | 16 / 64（SIMD、cache 行） |

两者可以叠加：`struct __attribute__((packed, aligned(4))) hdr {...}` —— 成员紧凑排布（`sizeof` 最小），但结构体起点仍 4 字节对齐，便于批量数组与直接 DMA 搬运。

### `section(".name")`——放进自定义 ELF 段

```c
int custom_var __attribute__((section(".mysec"))) = 42;
void my_fn(void) __attribute__((section(".mysec"))) { }
```

**最经典的工程用法是"召集式初始化"**——把一批函数指针写进同一个段，`main` 里遍历执行，没有任何中心注册表。这正是 Linux 内核 `initcall`、DPDK 驱动注册、各类测试框架自动注册用例的做法。实测（段名用 **C 标识符**，见下方坑）：

```c
typedef void (*fn_t)(void);

/* 每定义一个函数，就把它的指针塞进 myinit 段 */
#define INITFN(name)                                                     \
    static void name(void);                                              \
    static fn_t __p_##name __attribute__((used, section("myinit"))) = name; \
    static void name(void)

INITFN(a_init) { fprintf(stderr, "  [a_init] ran\n"); }
INITFN(b_init) { fprintf(stderr, "  [b_init] ran\n"); }
INITFN(c_init) { fprintf(stderr, "  [c_init] ran\n"); }

/* 链接器为名字是 C 标识符的段自动生成边界符号 */
extern fn_t __start_myinit[], __stop_myinit[];

int main(void)
{
    for (fn_t *p = __start_myinit; p < __stop_myinit; ++p)
        (*p)();
}
```

运行结果与 ELF 佐证：

```
main begin
found 3 entries
  [c_init] ran            ← 注意顺序！源码里写的是 a, b, c
  [b_init] ran
  [a_init] ran
main end

$ objdump -h sec | grep myinit
 25 myinit   00000018  0000000000004010  0000000000004010  00003010  2**3  CONTENTS, ALLOC, LOAD, DATA
                   ↑ 24 字节 = 3 个 8 字节指针

$ nm sec | grep -E "myinit|__p_"
0000000000004010 d __p_c_init
0000000000004018 d __p_b_init
0000000000004020 d __p_a_init
0000000000004010 D __start_myinit      ← 链接器给的
0000000000004028 D __stop_myinit       ← 链接器给的
```

**⚠️ 坑 1：段名必须是 C 标识符才拿得到边界符号。** 上面用的是 `myinit` 而不是 `.myinit`——因为带有点的名字生成出的符号是 `__start_.myinit`，C 里根本写不出来。要习惯性不用点，或者老实写 linker script。

**⚠️ 坑 2：段内顺序不由你决定，实测是反的。** 同一份代码把 4 个初始化函数写成 `f1,f2,f3,f4`，运行结果：

```
run in SECTION order:
  f4    ← nm 显示 __p_f4 @0x4010（地址最低的位置）
  f3
  f2
  f1
（连续跑 3 次，顺序稳定）
```

源码顺序完全颠倒。这是链接器/装载自己决定的（本例与 ELF 段在 `.o` 里的反向布局有关），**不要依赖它**。初始化有先后依赖时必须：

- 用显式的优先级字段参与排序（把每个条文写成 `{ prio, fn }` 结构体，运行时排序）；或
- 干脆回到手写注册表 `_Static_assert` 顺序 + 显式调用

顺便：这也解释了为什么内核 `*_initcall(fn)` 要分 `early/core/postcore/arch/subsys/fs/device/late` 那么多级——**顺序，就只能靠"段的分层 + 链接脚本里排好的段顺序"来规定，段内顺序不可靠**。

## `constructor` / `destructor`——main 之外自动执行

```c
__attribute__((constructor(101))) static void c101(void) { ... }
__attribute__((constructor(102))) static void c102(void) { ... }
__attribute__((constructor))      static void c_plain(void) { ... }

__attribute__((destructor(101)))  static void d101(void) { ... }
__attribute__((destructor(102)))  static void d102(void) { ... }
__attribute__((destructor))       static void d_plain(void) { ... }
```

实测执行顺序（完整输出）：

```
ctor 101
ctor 102
ctor no-prio        ← 无优先级的 constructor 最后执行
-- main --
dtor no-prio        ← 无优先级的 destructor 最先执行
dtor 102
dtor 101            ← 析构整体逆序
exit=0
```

规律：

| 阶段 | 顺序 |
|------|------|
| constructor | 优先级**升序**（数字小的先跑）；无优先级的一律排在**最后**（默认 65535） |
| destructor | 优先级**降序**（数字大的先跑）；无优先级的一律排在**最前** |

优先级范围 0–65535（`0`–`100` 保留给实现内部用，自己写建议从 101 起）。典型用途：库的隐式初始化、插件注册、测试用例自动注册、以及**依赖注入式的 mock**（在构造期替换函数指针表）。代价是它属于"看不见的控制流"——调试时很难看出为什么某段代码跑了。

## 可移植写法：宏封装

`__attribute__` 是 GNU 扩展，**MSVC 不认**。工程里的标准做法是拿宏包一层：

```c
#ifdef __GNUC__
#  define FMT_PRINTF(a, b) __attribute__((format(printf, a, b)))
#  define NORETURN         __attribute__((noreturn))
#  define NOINLINE         __attribute__((noinline))
#  define ALIGNED(n)       __attribute__((aligned(n)))
#  define PACKED           __attribute__((packed))
#  define SECTION(s)       __attribute__((section(s)))
#  define UNUSED           __attribute__((unused))
#  define USED             __attribute__((used))
#else
#  define FMT_PRINTF(a, b)
#  define NORETURN
#  define NOINLINE
#  define ALIGNED(n)       __declspec(align(n))    /* MSVC 的等价物，另行处理 */
#  define PACKED
#  define SECTION(s)
#  define UNUSED
#  define USED
#endif

void my_log(int prio, const char *fmt, ...) FMT_PRINTF(2, 3);
```

几个细节：

- `__GNUC__`：GCC **与 Clang 都定义**（clang 也会定义 `__GNUC__`），所以这一个宏把两家都包了
- 只有 `format` / `noreturn` / `unused` 这类"不影响 ABI"的属性可以在 MSVC 下直接空着；`packed` / `aligned` 是**布局属性**，空掉会导致跨平台结构体布局不一致——必须提供 MSVC 对应物（`#pragma pack` / `__declspec(align)`），否则共享内存/协议头会在 Windows 上错位
- 更细致的判断可以用 `__has_attribute(x)`（gcc 14+/clang 都支持）

### C23 / C++11 的标准属性语法 `[[...]]`

C23 起有了标准属性语法，GNU 属性可以写成 `[[gnu::packed]]`。**位置很讲究，写错了会被静默忽略**——实测三种位置：

| 写法 | `-std=c2x` 结果 |
|------|----------------|
| `struct [[gnu::packed]] S { ... };` | ✅ `sizeof=5`（生效） |
| `struct S { ... } [[gnu::packed]];` | ❌ `sizeof=8` + `warning: 'packed' attribute ignored for type 'struct S' [-Wattributes]` |
| `[[gnu::packed]] struct S { ... };` | ❌ `sizeof=8` + `warning: empty declaration` |

**第三种是最容易顺手写出来的**（Python 装饰器 / Java 注解的位置习惯），而它错得最彻底：gcc 把它当成一条**空声明**，`packed` 完全无效——而且只是 `warning`，不会拦住编译。

注意两点：

- `-std=c11` 下 `[[gnu::packed]]` 会被忽略（`warning: 'gnu' attribute ignored`）——要有 `-std=c2x` 及以上
- clang 18 对**第二种、第三种**位置直接 `error: misplaced attributes`（比 gcc 严格），**只有第一种位置两家都接受**

> 所以写 C23 属性时，**位置：`struct` 关键字之后、结构体名之前**。

## HFT / 嵌入式关联

| 属性 | HFT / 嵌入式中的典型用法 | 注意 |
|------|---------------------------|------|
| `packed` | 行情协议头（UDP 二进制线格式）必须与字节流一致 | 只许成员访问，**禁止 `&hdr->field` 转普通指针**；用 memcpy 读写 |
| `aligned(64)` | 每个 worker 的 ring buffer / 计数器各占一个 cache 行，消除伪共享（**18.3**） | 数组的每个元素都要落在 64 边界上，所以 `sizeof` 也要凑成 64 的倍数 |
| `always_inline` | 订单簿关键路径小函数（解析、比较价格level） | 失败是 error，热路径上要能兑现 |
| `noinline` | 把错误路径、日志格式化这类冷代码挤出热函数，让热路径代码块紧凑 | 冷代码调 `noinline` 函数，gcc 会把主逻辑留在前面，减少热路径取指 |
| `pure` / `const` | 纯计算（checksum 之外的 hash、价差计算）可以加，让编译器缓存 | **绝不撒谎**：函数里碰了一个全局计数器就不能叫 const |
| `noreturn` | `panic()` / 风控熔断退出 | 必须真的不返回，否则实测 SIGSEGV |
| `section` | 构造自动注册表、内核风格 initcall | 顺序不可靠，需要顺序就加优先级字段 |
| `used` | 回调指针表、汇编入口 | 拦不住 `--gc-sections` |
| `format` | 日志库、风控报错 | 配 `-Werror=format` 进 CI；换了参数表记得同步改 `m,n` |

### 一句你没提到但很重要的话

> 属性**改变编译器的假设**。假设错时，最危险的不是编译失败，而是**编译通过、结果看着也对、内部悄悄少执行业务**（`pure`/`const`）或者**运行时崩在别处**（`noreturn`）。

所以加入任何一个"优化向"属性前，先自问：**这个函数 100% 符合它的契约吗？未来改的时候会不会有人往里加一行全局状态？** 如果没有 `_Static_assert`/单测兜底，宁可不标。

### 一个都不加错的日志+自检模板

```c
#include <stdio.h>
#include <stdarg.h>

#ifdef __GNUC__
#  define FMT_PRINTF(a, b) __attribute__((format(printf, a, b)))
#else
#  define FMT_PRINTF(a, b)
#endif

void log_msg(int prio, const char *fmt, ...) FMT_PRINTF(2, 3);
void log_msg(int prio, const char *fmt, ...)
{
    if (prio > 3) return;                     /* 级别过滤：注意它不破坏 format */
    va_list ap; va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
}

__attribute__((noreturn)) void fatal(const char *fmt, ...) FMT_PRINTF(1, 2);
__attribute__((noreturn)) void fatal(const char *fmt, ...)
{
    va_list ap; va_start(ap, fmt);
    vfprintf(stderr, fmt, ap); va_end(ap);
    abort();                                  /* 满足 noreturn 契约 */
}

/* 协议头：紧凑布局 + 安全读写 */
struct __attribute__((packed)) quote_hdr {
    uint8_t  type;
    uint32_t seq;
    uint64_t ts;
};
static uint32_t hdr_seq(const struct quote_hdr *h)   /* 安全读取：memcpy */
{
    uint32_t v; memcpy(&v, &h->seq, sizeof v); return v;
}
_Static_assert(sizeof(struct quote_hdr) == 13, "wire layout changed");
```

`_Static_assert` 那一行建议随 packed struct 一同写：谁以后动了成员，`sizeof` 就会变，编译立刻失败——比跑起来发现数据错位便宜太多。

## 常见误区

| 误区 | 事实 |
|------|------|
| "`__attribute__` 是 C 标准的一部分" | GNU 扩展；MSVC 不认，必须宏封装 |
| "属性只是提示，不强制" | 部分是（`inline`）；`always_inline` 做不到直接 `error`；`pure/const/noreturn` 是**撒谎就静默出错** |
| "packed struct 访问会触发未对齐访问" | 直接访问成员不会，gcc 生成安全字节码；**转 transfusion `int*` 后才是 UB**（UBSan 有证据） |
| "packed 在 ARM 上一定会崩溃" | 未经实测（本机无 aarch64 工具链，Pi 不连）。正确做法是不用它去赌：`memcpy` / `get_unaligned` 解决所有路径 |
| "`used` 能保住符号" | 只能保住**编译器**不删；链接器 `--gc-sections` 照样删，要 `KEEP()` |
| "`inline` 会内联" | `-O0` 完全无效（`inline` 是建议）；要强制用 `always_inline` |
| "`const` 就是给纯计算加个优化标签" | 它是**契约**：写了函数就不能读任何全局；撒谎 → 副作用被合并掉（`g_counter` 3→1 实测） |
| "noreturn 只是消 warning" | 它改变可达性判断，-O0 就删掉后置代码；撒谎 → 实测 SIGSEGV(139) |
| "format 属性写错了会报警" | 只有 `-Wattributes` 报；不开就**静默失效**，错误一路带到运行期 |
| "同一批 attribute 可以照抄到别的函数" | 必须按每个函数的签名重新数 m/n（`my_log` 是 2/3，`test` 是 1/2） |
| "section 里的顺序跟源码一致" | 实测**反序**（f4,f3,f2,f1）；需要顺序必须加优先级字段或显式表 |

<summary>题目 1：下面这份声明的 2、3 各是什么意思？如果去掉 <code>prio</code> 参数写成 <code>void test(const char *fmt, ...) FMT_PRINTF(2,3)</code>，会发生什么？</summary>

```c
void my_log(int prio, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));
```

**答案：**

形参从 1 开始数：`1=prio(int)`、`2=fmt(const char*)`、`3=...`。所以

- **`2`** = 第 2 个参数是格式字符串
- **`3`** = 可变参数从第 3 个实参开始，编译器从这里起逐个对照 `%`

这条声明是**正确**的。实测 `my_log(1, "%d\n", 3.14)` 被 gcc 抓到：

```
warning: format '%d' expects argument of type 'int', but argument 3 has type 'double' [-Wformat=]
```

clang 同样抓到。

**去掉 prio 后（也就是借用同一个 `2,3`）**：参数表变成 `1=fmt`、`2=... 起点`，只有 1 个具名参数却说格式串在第 2 位——

```
error: 'format' attribute argument 2 value '1' refers to parameter type 'int'   (gcc, exit=1)
error: format argument not a string type                                        (clang)
```

上面这条报错是**另一种错位写法**：把 `1,2` 用到 `my_log` 上（第 1 参 `prio` 是 `int`，不是 `char*`）。如果改成对**单参数**的 `test` 沿用 `2,3`，gcc 的措辞就是 **7.6.2** 里记过的那条：

```
warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1
```

注意它的级别更低——只有 `warning`，不开 `-Wattributes` 就看不见，属性**静默失效**，`test("%d", 3.14)` 零告警、退出码 0、打印垃圾值。

**结论**：`m,n` 永远是对**当前这个函数**计数的，不能凭另一处代码照抄。

</details>

<details>
<summary>题目 2：以下代码 <code>-O2</code> 下 <code>g_counter</code> 是多少？为什么"看起来结果是对的"？</summary>

```c
/* 另一个 TU */
int g_counter = 0;
int query(int x) { g_counter++; return x + 1; }

/* 本 TU */
extern int query(int x) __attribute__((const));
int s = 0;
for (int i = 0; i < 3; i++) s += query(10);
printf("sum=%d g_counter=%d\n", s, g_counter);
```

**答案：**

```
sum=33   g_counter=1        ← 正确值应该是 sum=33 g_counter=3
```

`sum` 是 33，看起来完全正常；但 `g_counter` 从 3 变成 1——**3 次调用被 `const` 合并成了 1 次**。

原因：`const` 向编译器保证"返回值只依赖入参、不读不写任何状态"，于是同一个 `query(10)` 在三次迭代里结果必然相同，编译器把它当成循环不变量外提（或直接 CSE 掉）。

返回值不依赖状态，所以**表面结果与正确版本一致**，真正的伤害是"你以为执行了三次副作用"。

改造后排查方向：

- 函数读了全局 → 不是 `const`，最多 `pure`
- 函数写了全局 / 埋点 / 计数 / 时间戳 / 硬件寄存器 → `pure` 也不能要，**一个属性都不加**
- 真想要优化：把纯计算部分和副作用部分拆成两个函数，纯的那个加 `const`

</details>

<details>
<summary>题目 3：指出下面 4 处误用各自的可观测后果</summary>

```c
__attribute__((noreturn)) void liar(void) { fprintf(stderr, "x\n"); }   /* ① */
static void cb(void) __attribute__((used));                             /* ② */
static void cb(void) { }
static __attribute__((always_inline)) inline int f(int x);              /* ③ */
extern int f(int x);
struct __attribute__((packed)) P { char c; int i; };
int *pi = &p.i;                                                         /* ④ */
```

**答案：**

**① `noreturn` 撒谎**：`liar` 没有 `exit`/`abort`，会正常返回。编译器认为它之后的代码不可达，`main` 尾部不再生成正常收尾 → 实测

```
Segmentation fault (core dumped)     exit=139     (-O0 与 -O2 都崩)
```

修：函数体最后必须 `abort()` / `exit(1)`，或者干脆别写这个属性。

**② `used` 被高估**：它在 `-O2` 下确实保住了 `.o` 里的符号（`nm` 里能看到 `t cb`），但链接时若开了 `-ffunction-sections -Wl,--gc-sections`：

```
/usr/bin/ld: removing unused section '.text.cb'
```

照样删除。要真的保住得在 linker script 里 `KEEP(*(.text.cb))`。

**③ `always_inline` 不可兑现**：函数体在别的 TU（没开 LTO）时，编译器拿不到函数体：

```
warning: 'always_inline' function might not be inlinable [-Wattributes]
error: inlining failed in call to 'always_inline' 'f': function body not available
exit=1
```

`always_inline` 是**真强制**——编译器宁可编译失败也不悄悄忽略。修：体必须在本 TU（`static inline` 定义在头文件里），或改用 `-flto`。

**④ packed 成员地址转普通指针**：编译器在此丢失"它未对齐"的信息，会按对齐假设生成单条读写。gcc 提前警告：

```
warning: taking address of packed member of 'struct P' may result in an unaligned pointer value
         [-Waddress-of-packed-member]
```

加上 `-fsanitize=alignment` 运行：

```
runtime error: store to misaligned address 0x7fff0c22f2f2 for type 'int',
which requires 4 byte alignment
```

对照组——**直接访问 `p.i` 是安全的**（UBSan 零报告），因为编译器看得见 packed，会拆成字节级存取。修：要指针就用 `memcpy` 到局部变量。

</details>

<details>
<summary>题目 4：源码里按 f1、f2、f3、f4 的顺序定义，为什么实际执行顺序是 f4、f3、f2、f1？</summary>

**答案：**

这是**段在目标文件/可执行文件里的实际字节布局**决定的，`main` 里的遍历是按地址从 `__start_myinit` 递增走到 `__stop_myinit`。实测 `nm`：

```
0000000000004010 d __p_f4     ← 地址最低，最先被执行
0000000000004018 d __p_f3
0000000000004020 d __p_f2
0000000000004028 d __p_f1     ← 地址最高，最后执行
```

链接器/链接顺序（而非源码书写顺序）决定各个 `__p_fN` 落到哪个地址。连续跑 3 次顺序稳定，但**这不属于任何保证**——换工具链、换链接顺序、换链接脚本都可能变。

所以要表达依赖有两种可靠做法：

1. **优先级字段**：段里每个条目写成 `{ int prio; fn_t fn; }`，`main` 里先排序再执行（最常用）
2. **分层 + 链接脚本**：像内核 `early_initcall` … `late_initcall` 那样拆成多个段，在 linker script 里显式排好段顺序；**段内**顺序仍然不可靠——这正是内核为什么要分那么多等级，而不是在一个段里靠书写顺序

</details>

<details>
<summary>题目 5：把 <code>[[gnu::packed]]</code> 写成下面三种位置，各自的 <code>sizeof</code> 是多少？</summary>

```c
struct [[gnu::packed]] A { char c; int i; };        /* ① */
struct B { char c; int i; } [[gnu::packed]];        /* ② */
[[gnu::packed]] struct C { char c; int i; };        /* ③ */
```

**答案（gcc 13.3，-std=c2x）：**

| | 位置 | `sizeof` | 诊断 |
|---|------|---------|------|
| ① | `struct` 之后、名字之前 | **5** | 无 → **唯一正确写法** |
| ② | 右花括号之后 | 8 | `warning: 'packed' attribute ignored for type 'struct B'` |
| ③ | `struct` 之前 | 8 | `warning: empty declaration` |

③ 是最容易顺手写出来的（像 Python 装饰器 / Java 注解那样前置），结果 gcc 把它当成一条**空声明**，`packed` 完全无效，而且只有 `warning`——不去 grep 就发现不了布局其实是带 padding 的 8 字节。

补充：

- clang 18 对 ② ③ 直接 `error: misplaced attributes`（更严格），只有 ① 两家都接受 → **统一按 ① 写**
- `-std=c11` 下 `[[gnu::packed]]` 会被忽略（`warning: 'gnu' attribute ignored`），需要 `-std=c2x` 及以上
