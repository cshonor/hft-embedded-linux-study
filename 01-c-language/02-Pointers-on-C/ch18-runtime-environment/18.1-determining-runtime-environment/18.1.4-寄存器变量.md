# 18.1.4 寄存器变量

## 本节讲什么

`register` 关键字的历史与现状、x86-64 ABI 的寄存器传参、现代编译器的自动寄存器分配、以及 HFT 真正有效的寄存器优化手段（`inline`、`likely`/`unlikely`、`__builtin_expect`）。这一节澄清"手写 register 有用吗"的常见误解。

## 要点

### register 关键字的历史

C 早期（K&R 时代）编译器简陋，寄存器分配靠人工：

```c
register int hot_var;   /* 建议编译器放进寄存器 */
```

- `register` 是**提示**，编译器可忽略
- C89 限制：不能对 `register` 变量取地址（`&`）
- C11 放宽：可以取地址，但效果未定义（可能从寄存器退回内存）
- C17/C23 进一步弱化，`register` 几乎只剩历史意义

现代编译器（gcc/clang `-O2`）的寄存器分配远比人工聪明——基于寄存器分配算法（graph coloring / linear scan），考虑变量的生命周期、使用频率、调用约定。手写 `register` 通常无效甚至妨碍优化。

### x86-64 寄存器一览

| 寄存器 | 用途 | 保存责任 |
|--------|------|----------|
| `rax` | 返回值、乘除结果 | 调用者 |
| `rbx` | 通用 | 被调 |
| `rcx` | 第 4 参数、循环计数 | 调用者 |
| `rdx` | 第 3 参数、乘除高位 | 调用者 |
| `rsi` | 第 2 参数、字符串源 | 调用者 |
| `rdi` | 第 1 参数、字符串目 | 调用者 |
| `rbp` | 栈帧基址 | 被调 |
| `rsp` | 栈顶 | 被调（隐式） |
| `r8`-`r15` | 通用，r8-r11 调用者保存，r12-r15 被调保存 | 混合 |
| `xmm0`-`xmm15` | 浮点/SIMD | 调用者（xmm6-15 被调保存部分） |
| `rip` | 指令指针 | 隐式 |
| `rflags` | 标志位 | 调用者 |

### ABI 寄存器传参

x86-64 System V ABI 前 6 个整数/指针参数用寄存器传递，无需压栈：

```c
void func(int a, int b, int c, int d, int e, int f, int g);
/*            rdi  rsi  rdx  rcx  r8   r9   栈 */
```

- 前 6 个参数：`rdi`/`rsi`/`rdx`/`rcx`/`r8`/`r9`
- 第 7 个起：从右向左压栈
- 浮点：`xmm0`-`xmm7`
- 返回值：`rax`（128 位用 `rdx:rax`）

寄存器传参零开销（无 push/pop），这是 x86-64 比 x86-32 的重大改进。

### 为什么手写 register 无效

```c
register int hot = compute();
/* 编译器 -O2 已经自动把 hot 放进寄存器, register 提示多余 */
```

现代编译器基于使用频率自动分配：

- 高频局部变量优先进寄存器
- 取地址的变量必须在内存（不能纯寄存器）
- 生命周期不重叠的变量可复用同一寄存器

手写 `register` 的坏处：

- 可能阻止编译器更优分配（如两个 `register` 变量强制占两个寄存器，但实际可复用）
- C89 不能取地址，限制代码
- 现代编译器直接忽略，代码噪音

### 真正有效的寄存器优化

#### 1. inline 消除调用开销

```c
static inline int max(int a, int b) {
    return a > b ? a : b;
}
```

`static inline` 让编译器内联展开，参数直接进寄存器，无 call/ret/prologue/epilogue 开销。这是 HFT 最有效的优化。

#### 2. 减少间接调用

```c
/* 间接调用, 无法内联, BTB 预测可能失败 */
for (int i = 0; i < n; i++) {
    result += func_ptrs[i](data[i]);   /* 函数指针数组 */
}

/* 直接调用, 编译器内联 */
for (int i = 0; i < n; i++) {
    result += concrete_func(data[i]);   /* 编译器可内联 */
}
```

函数指针调用无法内联，且分支预测代价高。热路径用直接调用或 `switch` + 内联。

#### 3. likely / unlikely 分支提示

```c
#include <linux/compiler.h>  /* 内核 */
/* 或自己定义 */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

if (unlikely(error_condition)) {
    /* 错误处理, 编译器放函数末尾, 不污染热路径 cache */
    handle_error();
}
/* 正常路径在前, cache 友好 */
```

`__builtin_expect` 告诉编译器分支的倾向，编译器重排代码——likely 路径在前，unlikely 路径跳到末尾。改善指令 cache 命中。

DPDK `rte_likely`/`rte_unlikely`、内核 `likely`/`unlikely` 都是此宏。

#### 4. __builtin_prefetch 预取

```c
/* 预取下一元素到 cache, 隐藏内存延迟 */
while (cur) {
    __builtin_prefetch(cur->next, 0, 1);   /* 读, 一级 cache */
    process(cur);
    cur = cur->next;
}
```

预取让 CPU 在处理当前元素时并行加载下一元素，隐藏 cache miss 延迟。链表遍历、数组扫描受益明显。

#### 5. restrict 指针别名提示

```c
void add_arrays(int *restrict a, const int *restrict b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}
```

`restrict` 承诺指针不重叠，编译器可向量化（SIMD）和重排。无 `restrict` 时编译器保守假设可能重叠，无法优化。

#### 6. 数据布局优化

```c
/* 数组结构 (AoS), cache 不友好 */
struct Particle { float x, y, z, vx, vy, vz; };
struct Particle particles[N];
for (i) sum += particles[i].x;   /* 每次 stride 24 字节, cache 浪费 */

/* 结构数组 (SoA), cache 友好 */
struct Particles { float x[N], y[N], z[N], vx[N], vy[N], vz[N]; };
struct Particles ps;
for (i) sum += ps.x[i];   /* 连续访问, cache 100% 利用 */
```

数据布局比 `register` 关键字有效百倍——连续访问 + SIMD 批量处理。

### 编译器优化选项

| 选项 | 效果 |
|------|------|
| `-O0` | 不优化，调试友好 |
| `-O1` | 基础优化 |
| `-O2` | 标准优化（HFT 推荐） |
| `-O3` | 激进优化（向量化、内联更激进） |
| `-Os` | 优化大小 |
| `-march=native` | 启用本机 CPU 指令（AVX/AVX-512） |
| `-flto` | 链接时优化，跨文件内联 |
| `-funroll-loops` | 循环展开 |
| `-fprofile-use` | PGO（profile-guided optimization） |

HFT 通常 `-O2 -march=native -flto`，配合 PGO 进一步优化热路径。

### PGO（Profile-Guided Optimization）

```bash
# 1. 编译带 profiling
gcc -fprofile-generate -o app_prof app.c
# 2. 运行收集 profile
./app_prof < typical_input
# 3. 用 profile 重新编译
gcc -fprofile-use -o app app.c
```

编译器根据实际运行 profile 优化：

- 热路径内联更激进
- 分支布局按实际概率
- 函数重排让热代码在同一 cache line

PGO 对 HFT 价值大——行情解析热路径明显，profile 引导优化显著。

## HFT 关联

- **手写 register 无效**：现代编译器自动分配，HFT 不依赖 `register` 关键字
- **static inline**：热路径小函数内联，消除调用开销，最有效优化
- **likely/unlikely**：错误路径移出热路径，改善指令 cache
- **__builtin_prefetch**：链表/数组遍历预取，隐藏内存延迟
- **restrict**：承诺指针不重叠，启用 SIMD 向量化
- **数据布局 SoA**：结构数组改数组结构，cache + SIMD 友好
- **-O2 -march=native -flto**：HFT 标准优化组合
- **PGO**：profile 引导优化热路径，HFT 收益显著
- **避免间接调用**：函数指针热路径用 switch + 内联替代
- **DPDK likely/unlikely**：`rte_likely`/`rte_unlikely` 宏同模式

## 代码自测

**题目 1：** 以下代码中 register 关键字的作用是什么？
```c
register int i;
for (i = 0; i < 1000000; i++) { ... }
int *p = &i;  // 合法吗？
```

<details>
<summary>参考答案</summary>

register 是建议编译器将变量存储在寄存器中以提高速度。现代编译器通常忽略 register——它们自己的寄存器分配优化更好。注意：register 变量不能取地址（&i 是错误的，C89）——C++ 放宽了这个限制，C 仍建议不要取地址。register 在现代 C 中基本无用。

</details>
