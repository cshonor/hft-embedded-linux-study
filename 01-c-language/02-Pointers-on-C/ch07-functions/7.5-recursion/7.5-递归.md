# 7.5 递归

## 本节讲什么

函数**调用自身**；每层调用占一层**栈帧**。递归是树/链表遍历的天然写法，但 HFT 数据面**禁止深递归**——栈深度不可控、call/ret 开销、cache 不友好。

本节除了总览，还下探到**机器层面**：

1. 函数调用指令的**架构差异**——x86-64 是 `call`/`ret`（返回地址压**栈**），AArch64（树莓派 5）是 `bl`/`ret`（返回地址优先进**寄存器 X30**，嵌套调用才备份到栈）
2. **递归吃栈的精确对账**（gcc 13.3 实测）：每帧 = 局部变量 + 48 字节固定开销；六档实测 `深度 × 每帧` 全部精确等于 7.99 MB
3. ⚠️ **反直觉**：`-O2` 能把**非尾**递归也整个变成循环（零 `call`），以及它给调试带来的坑

细节在 7.5.1（追踪）和 7.5.2（与迭代）。

## 要点

- 组成：**基线条件**（base case）+ 向基线推进的递归步
- 每层：局部变量、返回地址保存在栈上，占一栈帧
- 深度过大 → **栈溢出** `SIGSEGV`（栈区到栈/堆边界）
- 无基线或推进失败 → 无限递归 → 必爆栈

### 最小例子

```c
int sum(int n) {
    if (n <= 0) return 0;          /* 基线 */
    return n + sum(n - 1);          /* 推进 */
}
```

每层 `sum` 占一栈帧：`n`、返回地址、可能的对齐填充。`sum(10000)` = 10000 层栈帧。

### 栈帧叠加

```
sum(3) ──┐
         │  [n=3, ret=main]      ← 栈帧 1
sum(2) ──┐
         │  [n=2, ret=sum(3)]    ← 栈帧 2
sum(1) ──┐
         │  [n=1, ret=sum(2)]    ← 栈帧 3
sum(0) → return 0                  ← 基线，开始回退
```

回退时逐层 `ret` 销毁栈帧，返回值逐层累加。

### 适用 vs 不适用

| 适用 | 不适用（HFT 热路径） |
|------|---------------------|
| 内核树/目录遍历 | 报文收发主循环 |
| AST、配置树（深度有界） | 订单簿遍历 |
| 排序（教学，快排/归并） | 链表 walk（用迭代） |
| 非热路径工具代码 | 信号处理 |

HFT 数据面若需"栈式"处理，用**显式栈数组**模拟递归（**7.5.2**、**ch17**）。

## 底层映射

### 栈大小与溢出

```bash
$ ulimit -s        # 栈大小，单位 KB，典型 8192（8MB）
8192
```

实测（gcc 13.3 `-O0`，8 MB 栈，`PAD` = 每层的局部数组大小）：

| 每帧大小 | 能撑的层数 | 备注 |
|---------|-----------|------|
| 48 B（零局部变量） | 174,599 | 地板价：返回地址 + `rbp` + 对齐 |
| 112 B（64 B 局部） | 74,804 | 一个 `char buf[64]` 就用掉 1/3 |
| 1072 B（1 KB 局部） | 7,818 | |
| 4144 B（4 KB 局部） | 2,021 | ⚠️ 嵌入式常见栈才 8~16 KB |

**每帧多 1 KB，深度直接掉两个数量级。** 深递归爆栈时：

```
sum(1000000) → 栈帧叠加超过 8MB → 踩到栈保护区 → SIGSEGV
```

栈保护区（guard page）让溢出确定性崩溃，而非静默踩堆。

### 机器层面：函数调用在 x86-64 与 AArch64 上长什么样

递归在机器层面就是「反复调用自己」，但**不同架构的"调用"指令完全不同**。先把两个架构的指令名和机制拆开（这俩最容易记混）。

#### 一、x86-64：`call` / `ret`，返回地址在**栈内存**上

| 指令 | 干什么 |
|------|--------|
| `call label` | 把**返回地址压入栈内存**，`rip` 跳到目标函数 |
| `ret` | 从**栈内存弹出**返回地址，跳回去 |

实测（gcc 13.3，`-O0`）递归函数 `sum()` 的反汇编：

```
0000000000000000 <sum>:
   4:  push   %rbp              ← 建立栈帧
   8:  sub    $0x10,%rsp        ← 开出 16 字节局部空间
  1f:  sub    $0x1,%eax         ← n - 1
  24:  call   29 <sum+0x29>     ← 递归：就是 call 自己
  2c:  add    %edx,%eax         ← n + sum(n-1)
  2f:  ret                      ← 返回
```

**递归 = 反复执行 `call`**，一层一层往栈上压返回地址。

##### 硬证据：返回地址确实躺在栈上

拿 `__builtin_return_address(0)` 的值，去本层栈帧附近的内存里**把它搜出来**（实测输出）：

```
  层 2: 返回地址 0x5f97096112bc  存在 [&anchor +24] 处
  层 1: 返回地址 0x5f9709611271  存在 [&anchor +24] 处
  层 0: 返回地址 0x5f9709611271  存在 [&anchor -112] 处
```

每层都在**自己的栈帧内部固定偏移**处找到了自己的返回地址。这就是「x86 返回地址强制在栈上」的实证。

#### 二、AArch64（树莓派 5）：`bl` / `ret`，返回地址优先在**寄存器 X30**

| 指令 | 干什么 |
|------|--------|
| `bl func` | branch-and-link：把返回地址写入**寄存器 LR（X30，链接寄存器）**，跳转 |
| `ret` | 从 **X30** 取返回地址，跳回 |

> ⚠️ **澄清一个常见记混**：ARM/AArch64 里**没有叫 `node` 的指令**，不存在这个东西。
> 另外 `ret` 是 **AArch64 才正式有的助记符**——ARM32（老 32 位 ARM）做调用同样是 `bl`，
> 但返回通常写成 `bx lr` 或 `mov pc, lr`，没有标准的 `ret` 助记符。

##### 关键差异：X30 只有一个，嵌套调用必须"备份到栈"

`bl` 会把 X30 **覆盖掉**。所以只要这个函数**还要再调用别的函数**（递归正好就是！），
就必须在函数开头手动把 X30 存到栈上、结尾再取回来：

```asm
recurse:
    stp  x30, x29, [sp, #-16]   // prologue：把 LR(x30) 和 FP(x29) 压栈保存
    …
    bl   recurse                // 递归调用 —— 这一句会改写 x30
    …
    ldp  x30, x29, [sp], #16    // epilogue：把 LR 恢复回来
    ret                          // 用恢复后的 x30 返回
```

而**叶子函数**（不再调用任何函数的函数）完全不用碰栈——X30 一直好好待在寄存器里，直接 `ret` 就行。

> 🔑 所以「AArch64 返回地址在寄存器」这句话的完整版是：
> **第一层返回地址在 X30 寄存器；一旦发生嵌套调用，每一层的返回地址最终还是得落到栈上。**
> 递归是最典型的嵌套调用，所以 AArch64 上递归**照样吃栈**，只是路径比 x86 多绕一步。

#### 三、两架构对照

| | x86-64 | AArch64（Pi 5） |
|---|--------|-----------------|
| 调用指令 | `call` | `bl` |
| 返回指令 | `ret` | `ret` |
| 返回地址**首选位置** | **栈内存**（强制） | **寄存器 X30**（LR） |
| 嵌套调用时 | 每层的返回地址本来就在栈上 | 函数 prologue 把 X30 **压栈备份**，epilogue 恢复 |
| 叶子函数 | 仍可能建栈帧（`-O0` 下有） | **可以完全不碰栈** |
| 递归时 | 栈随深度线性增长 | **一样线性增长**（只是每层多一次 LR 存取） |

> 📌 关于"AArch64 更快"：**理论上**用寄存器存返回地址省了一次内存访问。
> 但**实际上**现代 x86-64 CPU 有专门的 **返回地址预测器（return stack buffer / RSB）**，
> `call`/`ret` 的返回地址访问基本被预测器消化掉了，真实差距远没有"寄存器 vs 内存"看起来那么大。
> **不要因为这条就在选型时偏向某个架构**——x86 的 `call` 并不比 AArch64 的 `bl` 慢多少。
>
> ⚠️ 本节 AArch64 部分为**架构知识 + 标准汇编模板**，未在 Pi 5 上实测
> （当前 WSL 环境无 aarch64 交叉工具链）。x86-64 部分全部为 gcc 13.3 实测。

#### 四、递归的本质：架构无关，都是栈帧累积

不管 x86 的 `call`/`ret` 还是 AArch64 的 `bl`/`ret`：

> **每递归一层，就要保存一个返回位置；保存的位置最终落到栈上，栈帧不断累积。**
> **栈溢出 = 递归太深，栈空间被耗尽。**

这条可以用实测精确对账。用 `SIGSEGV` handler（配 `sigaltstack`，因为栈已经耗尽、handler 自己也需要新栈）抓爆栈瞬间的深度，同一个程序里同时量出每帧字节数：

```
ulimit -s = 8192 KB（8 MB）

  PAD=0     每帧=   48 B   爆栈深度= 174599   乘积= 8380752 B (7.99 MB)
  PAD=16    每帧=   64 B   爆栈深度= 130871   乘积= 8375744 B (7.99 MB)
  PAD=64    每帧=  112 B   爆栈深度=  74804   乘积= 8378048 B (7.99 MB)
  PAD=256   每帧=  304 B   爆栈深度=  27559   乘积= 8377936 B (7.99 MB)
  PAD=1024  每帧= 1072 B   爆栈深度=   7818   乘积= 8380896 B (7.99 MB)
  PAD=4096  每帧= 4144 B   爆栈深度=   2021   乘积= 8375024 B (7.99 MB)
```

**六档全中 7.99 MB**——`深度 × 每帧字节数 = 栈容量`，误差不到 0.1%。两条规律：

1. **每帧 = 局部变量(PAD) + 48 字节固定开销**（x86-64 `-O0`：返回地址 8B + `push rbp` 8B + 对齐填充）
   —— 哪怕你一个局部变量都不写（PAD=0），每层也要吃掉 48 字节
2. **深度 ∝ 栈容量 ÷ 每帧大小**，精确线性。改 `ulimit -s` 立刻验证：

```
  ulimit -s 1024   → PAD=64：深度 9300　乘积 0.99 MB
  ulimit -s 32768  → PAD=64：深度 299499　乘积 31.99 MB
```

这就是 **7.5.2** 说"递归 vs 迭代"的物理根因：迭代的栈占用是 **O(1)**，递归是 **O(深度)**。

#### 五、⚠️ 反直觉实测：`-O2` 能把**非尾**递归也变成循环

教科书常说「只有尾递归才能被优化成循环」。实测打脸——gcc 13.3 `-O2` 下，**普通的非尾递归 `sum(n) = n + sum(n-1)` 也完全没有 `call` 了**：

```
0000000000000000 <sum>:          ← -O2，非尾递归！
   4:  xor    %eax,%eax          # acc = 0
   6:  test   %edi,%edi
   8:  jle    17                 # n <= 0 就退出
  10:  add    %edi,%eax          # acc += n
  12:  sub    $0x1,%edi          # n--
  15:  jne    10                 # ← 循环！没有 call，没有栈增长
  17:  ret
```

**`call` 出现次数：0。** 编译器认出这是等差数列求和的累加形式，直接转成了循环——栈占用从 O(n) 塌成 O(1)。

尾递归（`-O2`）同样零 `call`，而且还被**循环展开 2 次**：

```
  20:  lea    -0x1(%rax,%rdi,2),%eax    # 一次算两层（展开）
  24:  sub    $0x2,%edi                 # n -= 2
  27:  jne    20
  29:  ret
```

对照 `-O0`：尾递归 `call` 出现 **1** 次（真递归）。

最能说明问题的是**没有基线的无限尾递归**：

| 编译 | 行为 | 退出码 |
|------|------|--------|
| `-O0` | 真递归 → 爆栈 | **139**（SIGSEGV） |
| `-O2` | 被折叠成一条自跳转 `jmp` → 死循环，不崩 | **124**（timeout 杀掉） |

`-O2` 下 `main` 的汇编就剩一句 `jmp 1048 <main+0x8>`——**跳自己，永远不返回**。

> ⚠️ 这条对**调试**影响很大：debug 版（`-O0`）崩溃的递归 bug，release 版（`-O2`）可能变成**静默死循环**——
> 不再 `SIGSEGV`，而是 CPU 100% 挂死，更难排查。
>
> 但**不能依赖它**：C 标准**不保证**任何尾调用/递归优化，gcc 只对"足够简单"的情形下手。
> 数据结构一复杂（比如树递归、递归后还有操作），`call` 立刻回来。工程上仍按"递归 = 吃栈"来设计（**7.5.2**）。

### call/ret 开销（**7.1**）

每层递归 = 一次 `call` + 一次 `ret` + 栈帧建立/销毁。叶子函数优化（省栈帧）对递归有限——递归不是叶子。深度 N 的递归 = N 次 call/ret，远慢于一个循环。

补充上面实测的两个细节：

- **固定开销 48 字节/帧**是"什么都不放"的地板价，真实递归函数的局部变量直接往上加
- **`-O2` 可能把整个递归消掉**（见上一节），所以"递归一定慢/一定吃栈"只在**未优化或编译器放弃优化**时成立；
  **写程序时不能赌编译器会救你**

## HFT / DPDK

| 场景 | 选择 |
|------|------|
| 报文解析 | 迭代，显式游标 |
| 链表遍历 | 迭代 `for (; p; p=p->next)` |
| 树（限深） | 递归可接受，或显式栈 |
| 配置加载（启动期） | 递归无所谓，不在热路径 |
| 策略回测 | 迭代优先，避免爆栈 |

### 嵌入式：栈不是 8 MB，是几 KB

上面实测全是在 **8 MB 栈**（Linux 主线程默认）下做的。嵌入式 Linux 的默认线程栈常常只有 **8 KB**，
按实测的 `深度 = 栈容量 ÷ 每帧` 线性外推：

| 环境 | 栈大小 | `char buf[64]` 每帧 112 B 时能撑 |
|------|--------|--------------------------------|
| Linux 主线程（默认） | 8 MB | 74,804 层 |
| glibc pthread 默认线程 | 8 MB | 74,804 层 |
| 嵌入式 pthread（常见配置） | **8 KB** | **约 73 层** |
| RTOS 任务栈（常见） | 1~4 KB | **9~37 层** |

同一个递归函数，在开发机跑得好好的，**挪到板子上 70 多层就爆**。这就是为什么嵌入式领域几乎把递归当禁区——不是"风格问题"，是算得出来的硬约束。在 Pi 5 上写内核模块时更要小心：**内核栈只有 8 KB（ARM64 上是 16 KB）且不可动态增长**，递归几乎没有生存空间。

## 常见误区

| 误区 | 事实 |
|------|------|
| "递归一定优雅" | 爆栈、慢、cache 差，热路径禁用 |
| "深递归最多慢点" | 会 `SIGSEGV`，进程崩 |
| "尾递归和迭代一样" | C 标准不保证 TCO，gcc 常做但不总能（**7.5.2**） |
| "栈大小无限" | `ulimit -s` 限制，默认 8MB |
| "只有尾递归才能被优化成循环" | ❌ 实测 gcc `-O2` 把**非尾**递归 `n + sum(n-1)` 也变成了循环（`call` 数 = 0）。但**不能依赖**——C 标准不保证，复杂递归照样回来 |
| "ARM 的调用指令是 `node`" | ❌ 没有这条指令。AArch64 是 `bl`（调用）+ `ret`（返回）；ARM32 也是 `bl`，但返回写 `bx lr` |
| "AArch64 返回地址在寄存器，所以递归不吃栈" | ❌ X30 只有一个，**嵌套调用必须把 LR 压栈备份**——递归照样线性吃栈，只是多一步存取 |
| "AArch64 用寄存器存返回地址，函数调用明显更快" | ⚠️ 理论如此，但 x86-64 有**返回地址预测器（RSB）**抵消了大部分差距，别拿这条当选型依据 |
| "局部变量写小点，递归就能深很多" | ⚠️ 有用但有限：实测**地板价就是 48 字节/帧**（零局部变量），写再小也省不掉 |

## 实操

```bash
# 故意深递归看爆栈
cat > t.c << 'EOF'
int f(int n) { return n ? f(n-1) : 0; }
int main(void) { return f(100000000); }
EOF
gcc -O0 t.c -o t && ./t          # Segmentation fault
# ulimit 调栈大小
ulimit -s 65536 && ./t           # 撑更多层
# gdb 看递归深度
gdb ./t -ex r -ex bt | head -50  # 一长串 f 帧
```

## 代码自测

**题目 1：** 以下递归函数有什么问题？
```c
int factorial(int n) {
    if (n == 0) return 1;
    return n * factorial(n);
}
```

<details>
<summary>参考答案</summary>

递归调用传入的是 n 而非 n-1，导致无限递归直到栈溢出。正确写法：return n * factorial(n - 1);。此外还缺少对负数的处理——如果传入负数，n 永远不等于 0，也会无限递归。

</details>

**题目 2：** 判定下列说法，并说明机器层面的理由：

```c
// a. ARM/AArch64 的函数调用指令是 node
// b. x86-64 的 call 把返回地址压入栈内存
// c. AArch64 的 bl 把返回地址写入寄存器 X30，永远不碰栈
// d. AArch64 里 ret 和 x86-64 里 ret 是同一条指令
// e. 递归在两种架构上最终都会线性消耗栈空间
// f. 叶子函数在 AArch64 上可以完全不碰栈
```

<details>
<summary>参考答案</summary>

| 项 | 判定 | 理由 |
|----|------|------|
| a | ❌ | **不存在 `node` 指令**。AArch64 是 `bl`（branch-and-link）；ARM32 同样是 `bl`，返回写 `bx lr` 或 `mov pc, lr`（AArch64 才正式有 `ret` 助记符） |
| b | ✅ | `call` 把下一条指令地址**压栈**，`ret` 再弹出来跳回——x86-64 返回地址**强制在栈** |
| c | ❌ | 只说对一半。`bl` 确实写 X30，但 **X30 只有一个**，函数若还要再调用（递归正是），必须在 prologue 用 `stp x30, x29, [sp,#-16]` 把 LR **压栈备份**，epilogue `ldp` 恢复后才能 `ret` |
| d | ❌ | 助记符同名、语义相近，但**是两条不同的指令**（不同架构、不同编码、取返回地址的来源也不同：栈 vs 寄存器） |
| e | ✅ | 架构无关：**每层都要保存一个返回位置，最终都落到栈上**。x86 直接压栈；AArch64 先入 X30、嵌套时再转存栈，总量同样是 O(深度) |
| f | ✅ | 叶子函数不再调用别人，X30 不会被覆盖，全程待在寄存器里，`ret` 直接返回，**零栈操作** |

</details>

**题目 3：** 计算 + 设计题（用本节实测数据）

实测：x86-64 `-O0`，每帧 = 局部变量 + **48 字节**固定开销；`深度 × 每帧 = 栈容量`。

1. Linux 主线程 8 MB 栈，递归函数每层有一个 `char buf[256]`（即 304 B/帧），能撑多少层？
2. 同一函数搬到嵌入式板子（pthread 栈 8 KB），能撑多少层？
3. 你的策略代码必须在 8 KB 栈上处理深度为 500 的树，每层最多能留多少字节局部变量？
4. 如果改成 `-O2`，上面这些数字还成立吗？为什么？

<details>
<summary>参考答案</summary>

**1.** `8 × 1024 × 1024 ÷ 304 = 27,559` 层（实测值就是 27,559，误差 < 0.1%）

**2.** `8 × 1024 ÷ 304 = 26` 层 😬

**3.** `8192 ÷ 500 = 16.4` 字节，减去 48 字节固定开销 → **负数，根本放不下**。
即使一层局部变量都不写（48 B/帧），`8192 ÷ 48 = 170` 层 < 500 层。
→ **结论：8 KB 栈上做 500 层递归是不可能的**，必须改成显式栈的迭代写法（**7.5.2**、**ch17**），
或者把栈调大（需要改线程属性，且要有依据地算）。

**4.** **不一定成立**，这是最容易答错的一问：

- `-O2` 可能**完全消除递归**——实测非尾递归 `sum` 在 `-O2` 下 `call` 数为 0，被转成循环，
  栈占用从 O(n) 塌成 O(1)，上面的计算全部作废
- 但**不能依赖**：C 标准不保证任何递归/尾调用优化，gcc 只对"足够简单"的情形下手
  （树递归、递归后还有复杂操作的，立刻回到真 `call`）

**工程做法**：**按 `-O0` 的数字做设计**（也就是上面 1~3 的答案），把 `-O2` 的消除当作"可能拿到的额外红利"，
绝不当成设计依据。排障时反过来：debug 版崩 `SIGSEGV` 的递归，release 版可能变成**静默死循环**
（实测无基线尾递归 `-O0` 退出码 139、`-O2` 退出码 124 timeout），更难查。

</details>
