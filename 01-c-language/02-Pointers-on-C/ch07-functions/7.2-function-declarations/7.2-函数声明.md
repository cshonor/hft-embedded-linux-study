# 7.2 函数声明

## 本节讲什么

**声明（原型）** vs **定义**：声明告知签名，可重复多处；定义分配代码，外部符号全局唯一（ODR）。这一节讲清两者在编译/链接阶段的分工，以及"头文件 + 实现文件"工程模式的根因。

## 要点

| | 声明 | 定义 |
|---|------|------|
| 位置 | `.h` 或 `.c` 顶部 | 某一个 `.c` |
| 函数体 | 无 | 有 `{ }` |
| 链接 | `extern` 隐含 | 产生符号 |
| 可重复 | 是（多处声明须兼容） | 否（ODR，全局唯一） |

```c
/* header.h */
int rte_mbuf_refcnt_add(struct rte_mbuf *m, int delta);

/* mbuf.c */
int rte_mbuf_refcnt_add(struct rte_mbuf *m, int delta) { /* ... */ }
```

- 原型作用：**编译期**校验参数个数与类型
- 无原型 → 旧式隐式 `int` 规则（**7.2.2** 高危）
- 声明可重复，但所有声明的类型必须**兼容**（C99 "compatible types"）

### 头文件 + 实现文件模式

```
queue.h          ← 公共 API 原型、opaque typedef
  struct queue;  // 前向声明
  typedef struct queue queue_t;
  queue_t *queue_create(void);
  void queue_destroy(queue_t *q);

queue.c          ← 实现 + 私有 static helper
  #include "queue.h"
  struct queue { /* 内部布局 */ };
  static node *grow(queue_t *q) { /* 私有 */ }
  queue_t *queue_create(void) { /* ... */ }
```

`.c` 包含自己的 `.h` → 编译器同时校验"声明与定义一致"（**7.2.1**）。

### 全局变量的工程标准写法

声明 vs 定义的通用定义（不限于函数）：

- **声明**：告诉编译器符号名字、类型，**不分配内存、不生成机器码**——整个程序可写无数次
- **定义**：创建真实实体，分配内存 / 生成函数汇编代码——**整个程序只能有 1 处定义**（ODR）

全局变量三步走：

```c
/* xxx.h —— 第 1 步：只写 extern 声明，不分配内存 */
extern int g_val;

/* xxx.c —— 第 2 步：唯一的定义，真正分配内存 */
int g_val = 10;

/* 其他所有 .c —— 第 3 步：include 后直接读写 */
#include "xxx.h"
/* 所有 .c 操作的是同一块内存 */
```

> ⚠️ `extern` **不代表只读**——它只说明"内存不在当前文件"；想要只读要加 `const`：
> `extern const int g_val;`
>
> ❌ 禁止把 `int g_val = 10;`（定义）直接写进 `.h`：多文件 include → 多重定义链接报错。

#### 试探性定义：`int g_val;`（不带初始化）

C 标准里这叫**试探性定义（tentative definition）**：若翻译单元内始终没出现带初始化的定义，它就转正成"初始化为 0 的定义"。多文件各自写 `int g_val;` 时：

- 传统工具链（`-fcommon`）：合并成 common symbol，静默合并不报错——但哪个文件"赢"不可控
- **GCC 10 起默认 `-fno-common`**：直接 multiple definition 链接报错

**行为不可靠，不要使用**——全局变量永远写"`.h` extern + 唯一 `.c` 带初始化定义"的完整形式。

### #include 的本质：文本粘贴

`#include` 只是简单文本粘贴，头文件本身**不产生内存、不运行代码**：

| 粘进去的内容 | 后果 |
|--------------|------|
| `extern int g_val;`（声明） | 没事，可以无数次 |
| `int g_val = 10;`（定义） | 每个 `.c` 都生成实体 → 链接报错 |
| `static inline` 函数体 | 每个 TU 一份私有副本，不冲突 |

（#include 机制详解 → **ch14**）

### C 为什么没有函数重载（overload）

**直接结论：C 语言没有函数重载。函数名字就是全部——函数名必须独一无二，不看参数、不看返回值。**

C 的符号规则：函数符号**只由函数名字决定，参数列表、返回类型完全不参与符号生成**：

```c
void func(int a);
int  func(double b);   /* ❌ C：两者符号都叫 func，冲突 */
```

在 C 眼里：名字一样就是同一个函数，参数不一样也不行；返回值不一样也不行
（`void foo(void)` 和 `int foo(void)` 同样冲突）——**返回值不区分函数**。

> C++ 会做名字改编（name mangling）：把参数类型编码进符号名（`_Z4funci` / `_Z4funcd`），
> 所以允许重载。**C 没有 mangling，符号名就是函数名本身。**

#### 那两个 .c 分开写呢？（易错例）

```c
/* file1.c */ void calc(int a)    {}
/* file2.c */ int  calc(double a) {}
```

分开编译各自都能过；**链接时两个符号都叫 `calc` → multiple definition 报错**。
C 链接器根本不看参数，只看名字。若在同一翻译单元里写两个声明，编译期就报
`conflicting types for 'calc'`（类型不兼容，约束违反）——不用等到链接。

#### C 模拟"多态"的三种方案

| 方案 | 写法 | 场景 |
|------|------|------|
| ① 名字加后缀（工业界最常见） | `func_int()` / `func_double()` | 内核到处都是（`__u32`/`__u64` 系列） |
| ② `void*` + 类型标记（模拟动态多态） | `void print(void *data, int type)` | 传 void* 再传类型标记，函数内部分发；qsort 回调、很多库这么干 |
| ③ 结构体函数指针（**运行时多态**） | `struct ops { void (*read)(void); void (*write)(void); }` | Linux 内核 file_operations 大量使用；不同设备填不同实现，同一接口不同行为（→ **ch13.3** 函数指针） |

#### 两个概念不要混

| 概念 | 时机 | C 支持？ |
|------|------|----------|
| **函数重载**（编译期多态，C++） | 同名不同参，编译器自动选版本 | ❌ 不支持 |
| **运行时多态**（函数指针分发） | 结构体存函数指针，运行时切换实现 | ✅ 支持，内核大量使用 |

### 极简记忆口诀

1. `.h` 放**声明**；实体定义尽量写在 `.c`
2. 全局变量：h 写 extern，c 做唯一的定义
3. h 里面要带函数体，就用 `static inline`
4. **声明随便复制，定义只能一份**

## 底层映射

### 符号表视角

```bash
$ nm queue.o
0000000000000000 T queue_create       # T = external text（全局可见）
0000000000000040 T queue_destroy
0000000000000080 t grow                # t = local text（仅本 TU）
```

`T`（大写）= 外部链接符号，链接器可见；`t`（小写）= 内部链接，仅本 `.o`。这就是 `static` 函数的链接效果——封装的编译期保证。

### ODR（One Definition Rule）

C 标准要求：每个外部符号在程序里**有且仅有一个定义**。违反 → 链接报错：

```
$ gcc a.o b.o -o prog
a.o:(.text+0x0): multiple definition of `foo'; b.o:(.text+0x0): first defined here
```

`static` 函数不违反 ODR（每个 TU 是独立符号，不参与外部链接）——所以多个 `.c` 各有同名 `static helper` 不冲突。

### common symbol：试探性定义的痕迹

```bash
$ gcc -fcommon -c a.c && nm a.o
0000000000000000 C g_val          # C = common symbol（试探性定义产物）
$ gcc -c a.c && nm a.o            # GCC 10+ 默认 -fno-common
0000000000000000 B g_val          # 直接进 .bss（若唯一）或链接报错（若多处）
```

`C`（大写）= common：链接器允许合并多个同名 common，选一个分配。这是老式"未初始化全局变量不报错"的机制根源，也是"行为不可靠"的来源。

### name mangling：C vs C++ 符号实测

```bash
$ printf 'void test(int x){}\nvoid test(double x){}\n' > t.cc
$ g++ -c t.cc && nm t.cc
0000000000000000 T _Z4testd    # C++：double 版，类型编进符号名
0000000000000008 T _Z4testi    # C++：int 版，两个不同符号 → 重载合法

$ gcc -c t.c   # 同样两个定义
t.c:2:6: error: conflicting types for 'test'   # C：编译期直接拦
```

C 的符号表里函数名"裸奔"（`test` 就是 `test`）——这就是 `extern "C"` 存在的原因：
C++ 代码要被 C 链接器找到，必须关掉 mangling，副作用是**该函数不能重载**（符号只能有一个）。

## HFT / DPDK

| 模式 | 作用 |
|------|------|
| `.h` 放公共 API 原型 | 调用者只依赖签名，实现可换 |
| `.c` 用 `static` 藏私有 | 编译期封装，符号不外泄 |
| `static inline` 入头 | 跨 TU 共用的快路径 helper |
| opaque typedef | 隐藏内部布局（**7.4** ADT） |

## 常见误区

| 误区 | 事实 |
|------|------|
| "声明和定义一样" | 声明可重复，定义唯一（ODR） |
| "`extern int foo();` 必须写 extern" | 函数声明隐含 extern，可省 |
| "`static` 函数不能在头文件里" | 能写，但每个包含的 TU 各得一份副本（除非 `static inline`） |
| "声明和定义不一致没事" | UB，`-Werror=strict-prototypes` 拦 |
| "`extern` 表示只读" | extern 只说明内存不在本文件；只读要加 `const` |
| "`int g_val;` 不带初始化没事" | 试探性定义：-fcommon 静默合并不可靠，GCC 10+ 直接多重定义报错 |
| "#include 有什么链接语义" | 纯文本粘贴，头文件本身不产生内存不运行代码 |
| "C 里参数不同就是重载" | 符号只看函数名，同名不管参数都是同一个函数，冲突 |
| "返回值不同算两个函数" | 返回值不参与符号生成，`void f()` 和 `int f()` 同样冲突 |

## 实操

```bash
# 看符号表区分 T/t
gcc -c t.c -o t.o && nm t.o
# 故意定义两次看 ODR 报错
cat > a.c << 'EOF'
int foo(void) { return 1; }
EOF
cat > b.c << 'EOF'
int foo(void) { return 2; }
EOF
gcc a.c b.c -o prog   # multiple definition
# 强制声明与定义一致检查
gcc -Werror=strict-prototypes -c t.c
```

## 代码自测

**题目 1：** 以下代码在 C89 和 C99 中有什么区别？
```c
int f();
// ...
f(1, 2, 3);
```

<details>
<summary>参考答案</summary>

C89 中 int f(); 表示 f 接受未知数量的参数（不检查参数类型和数量），调用 f(1,2,3) 不会报错。C99 中空参数列表已被废弃，建议用 int f(void); 明确表示不接受参数。如果 f 实际定义为 int f(int a)，C89 下调用 f(1,2,3) 是 UB，C99 下仍可能不报错（因为声明没指定参数）。

</details>

**题目 2：** 逐项判定：声明还是定义？链接会不会出错？
```c
// a.h
extern int g_count;          // 行 1
int g_raw;                   // 行 2
static inline int sq(int x) { return x*x; }  // 行 3

// a.c
#include "a.h"
int g_count = 0;             // 行 4

// b.c
#include "a.h"
int g_count = 5;             // 行 5
```

<details>
<summary>参考答案</summary>

- 行 1 **声明**：extern，不分配内存——粘到多少个 TU 都没事。
- 行 2 **试探性定义**：不带初始化，不是声明！-fcommon 下两个 TU 的 g_raw 合并为 common symbol（静默合并，不可靠）；GCC 10+ 默认 -fno-common 直接 multiple definition 报错。
- 行 3 **定义**（static inline）：每个 TU 一份私有副本，内部链接，不违反 ODR，不冲突。
- 行 4 **定义**：g_count 唯一的带初始化定义，分配内存，✅ 正确。
- 行 5 **定义**：与行 4 重复——g_count 有了两处外部定义，multiple definition 链接报错 ❌。正确写法是 b.c 只 `#include "a.h"` 靠 extern 声明访问。

核心口诀：**声明随便复制，定义只能一份**；唯一例外是 `static`（内部链接不参与 ODR）。

</details>

**题目 3：** 同一份代码，C 和 C++ 各会怎样？
```c
void test(int x);
void test(double x);
```

<details>
<summary>参考答案</summary>

**C：编译期就报错。** 同一翻译单元内两个 `test` 声明类型不兼容——这是约束违反，
GCC/Clang 直接报 `error: conflicting types for 'test'`，根本活不到链接阶段。
（若拆到两个 .c 各自定义，则各自编译通过、链接期 multiple definition。）

**C++：完全合法。** name mangling 把两个版本编成不同符号：
`_Z4testi`（int 版）/ `_Z4testd`（double 版），重载决议按实参类型在**编译期**挑选版本。

根源：C 的符号名就是函数名本身，参数/返回值不参与；C++ 把参数类型编码进符号名。
这也是 `extern "C"` 的意义——C++ 函数要让 C 链接器找到必须关掉 mangling，
代价是该函数不能重载。

</details>
