# 8.1.4 指针的效率

## 本节讲什么

**指针访问数组 vs 下标访问数组**——这两种写法在历史上有性能差异，但在现代编译器（GCC/Clang `-O2` 以上）下**通常生成相同机器码**。本节拆解"指针更快"这个半世纪老观念是怎么来的、何时仍然成立、以及为什么在 HFT 场景下它根本不是性能瓶颈。

## 历史背景：为什么本书专门讨论这个

- **1970s–80s**：早期 C 编译器优化薄弱，`arr[i]` 真的会编译成"基址 + i×sizeof + 解引用"三步；而 `*p++` 在 PDP-11 上有**自增寻址**指令 `(R0)+`，一条指令完成取值和指针前移 → 指针遍历确实更快。
- **《C 和指针》成书的 90 年代**：作者仍在讨论这个差异，因为商业编译器优化参差不齐。
- **今天（GCC 13 / Clang 17 + `-O2`）**：下标循环和指针循环几乎总是被优化成**相同的中间表示**，差异消失。所以这节的价值不在"学会用指针提速"，而在**理解编译器怎么对待数组访问**，为后面 restrict、向量化打基础。

## 三种写法对比

```c
/* 写法 A：下标 */
int sum_a(const int *arr, int n) {
    int s = 0;
    for (int i = 0; i < n; i++)
        s += arr[i];
    return s;
}

/* 写法 B：指针 + 下标 */
int sum_b(const int *arr, int n) {
    int s = 0;
    const int *p = arr;
    for (int i = 0; i < n; i++)
        s += *(p + i);
    return s;
}

/* 写法 C：指针自增 */
int sum_c(const int *arr, int n) {
    int s = 0;
    const int *p = arr;
    for (int i = 0; i < n; i++)
        s += *p++;
    return s;
}
```

> 三个函数在 `gcc -O2` 下生成的核心循环汇编**完全一致**（见下一节）。

## 编译器视角：x86-64 汇编证据

`gcc -O2 -S` 后，三个函数的核心循环都是这样的形式（寄存器名可能不同）：

```asm
.L3:
    add    eax, DWORD PTR [rdi+rcx*4]   ; s += arr[i]
    add    rcx, 1
    cmp    edx, ecx
    jg     .L3
```

关键点：

| 观察 | 含义 |
|------|------|
| `[rdi + rcx*4]` | **基址 + 变址×比例寻址**，x86 单条指令完成 `arr[i]`，没有额外乘法 |
| 没有 `imul` | 比例因子 `4`（`sizeof(int)`）由寻址模式硬件处理，不是真乘法 |
| 三种写法归一 | 编译器前端把 `arr[i]`、`*(p+i)`、`*p++` 都降成相同的 GIMPLE/IR |

**结论**：在 `-O2` 下争论"指针快还是下标快"没有意义——它们是同一段机器码。

## 何时指针**真的**更快

差异只在以下场景重新出现：

1. **`-O0` 或 `-Og` 调试构建**：编译器不做归一化，下标写法可能多一条地址计算。HFT 生产环境从不这么编译，但单测覆盖率常在 `-O0` 跑，要注意基准测试别在 `-O0` 下做。
2. **指针链式遍历有状态**：如遍历链表/解析变长报文字段时，`p = (struct hdr *)p + 1` 这种"步进依赖前一步结果"的写法，下标表达不直观，指针更自然——但这其实是**可读性**优势，不是速度优势。
3. **`restrict` 配合**：`int *restrict p` 承诺无别名后，指针版有时能触发更激进的向量化（见后文）。

## 何时下标**更好**

- **随机访问** `arr[k]`：`k` 不是顺序递增时，下标语义清晰，指针要算偏移反而绕。
- **多维数组** `mat[i][j]`：下标可读性远胜 `*(*(mat+i)+j)`，且编译器一样优化得好。
- **调试**：下标在 gdb 里 `print arr[i]` 更直观，`print *(p+i)` 麻烦。
- **静态分析 / 边界检查**：很多 sanitizer 和静态工具对下标越界检查更友好。

## HFT 实战：真正的性能在哪里

这一节对 HFT 学习者的真正价值，是建立**性能直觉的优先级**：

```
影响数组访问性能的因素（由大到小）
┌──────────────────────────────────────┬──────────────┐
│ 缓存局部性（连续 vs 随机访问）         │ ~100x        │  ← 主战场
│ 对齐与缓存行边界（64B）                │ ~10x         │
│ restrict / __restrict__（允许向量化）  │ ~2-4x        │
│ 预取（sw prefetch / hw stream）        │ ~2x          │
│ 数据布局（SoA vs AoS）                 │ ~2x          │
├──────────────────────────────────────┼──────────────┤
│ 指针 vs 下标（-O2 下）                 │ ~1x（无差异）│  ← 本节
└──────────────────────────────────────┴──────────────┘
```

**口诀**：下标还是指针是**风格问题**；连续还是离散访问、对不对齐、有没有别名，才是**性能问题**。

具体场景：

- **DPDK 收包循环** `for (i=0; i<nb_rx; i++) bufs[i] = ...`——用下标，编译器向量化得很好；瓶颈在 DDR 带宽和 cache miss，不在写法。
- **解析定长报文头**：`struct eth_hdr *h = (void *)p; p += sizeof(*h);`——用指针步进，因为步长是变的、类型是变的，下标表达不了。
- **批量处理订单数组**：`orders[i].price`——用下标；但要注意 `orders` 是否紧凑（有无 padding）、是否跨缓存行，这比写法重要 100 倍。

## `restrict`：真正影响优化的关键字

`restrict`（C99）是**指针承诺无别名**——告诉编译器"我保证这段内存没有别的指针会改"，允许它做向量化、重排、省 reload：

```c
/* 无承诺：编译器保守，不能向量化（怕 aliased） */
void add(int *a, int *b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}

/* 有承诺：可向量化成 SIMD */
void add_r(int *restrict a, int *restrict b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}
```

`add_r` 在 `-O3 -mavx2` 下可能展开成 `vpadd` 一次处理 8 个 int；`add` 则不能（除非编译器做运行时别名检查）。这才是**指针写法能影响性能**的真正通道——通过 `restrict` 承诺，而不是通过 `*p++`。

> 违反 `restrict` 承诺是 **UB**（未定义行为），HFT 代码里用错会比"慢"严重得多。

## 常见误区

| 误区 | 纠正 |
|------|------|
| "用指针遍历数组一定比下标快" | 现代 `-O2` 下两者机器码相同，这是 70 年代观念 |
| "手动写 `*p++` 比让编译器优化 `arr[i]` 更聪明" | 编译器比你更懂目标 ISA 的寻址模式 |
| "`-O3` 总是更快" | `-O3` 会激进内联和向量化，但也可能触发代码膨胀、icache 压力，HFT 实战要**基准测试**而非盲信 |
| "下标越界只是慢" | 越界是 UB，可能恰好"正常"运行数月后某次崩溃——绝不能靠"没崩就没事"判断 |

## 实操

1. **godbolt.org**：把上面三个 `sum_*` 函数贴进去，`x86-64 gcc 13 -O2`，勾选"Filters → Directives"，肉眼比对核心循环是否一致。
2. 改 `-O0`，观察下标版是否多出 `mov`/`lea`。
3. 给 `add` 和 `add_r` 加 `-O3 -mavx2`，对比 `add_r` 是否出现 `vpadd`（向量化）。
4. 写一个 `int a[1024]`，分别顺序遍历和按 64 步跨步遍历，`perf stat -e cache-misses` 看差异——体验"局部性比写法重要 100 倍"。

## 代码自测

**题目 1：** 以下代码中 p2 - p1 的值是多少？
```c
int arr[5] = {1, 2, 3, 4, 5};
int *p1 = &arr[1];
int *p2 = &arr[3];
printf("%d\n", p2 - p1);
```

<details>
<summary>参考答案</summary>

输出 2。指针减法返回的是元素个数，不是字节数。p2 指向 arr[3]，p1 指向 arr[1]，相差 2 个 int。实际字节差是 2 * sizeof(int)，但指针减法自动除以 sizeof(int)。

</details>
