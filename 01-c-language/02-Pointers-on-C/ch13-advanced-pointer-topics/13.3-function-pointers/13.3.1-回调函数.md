# 13.3.1 回调函数

## 本节讲什么

回调（callback）的本质是**「调用方把函数指针交给被调用方，由被调用方在合适时机反向调用」**。这一节给出回调机制的三大要素——**typedef 函数指针 + `void *priv` 私有数据 + 注册/触发分离**——以及它在 DPDK、内核、事件引擎里的标准范式。

认知锚点：回调不是语法糖，而是**解耦设计的核心工具**。它让框架代码（被调用方）无需知道业务逻辑（调用方传入的函数），实现「控制反转」。C 没有闭包，`void *priv` 就是闭包捕获状态的等价物——这是 C 工程师必须建立的思维模型。

## 要点

### 回调三要素

```c
/* 1. typedef 函数指针 */
typedef void (*event_cb_t)(uint32_t event_type, void *priv);

/* 2. void *priv 私有数据 */
struct event_mgr {
    event_cb_t  cb;
    void       *priv_data;
};

/* 3. 注册 / 触发分离 */
void event_register(struct event_mgr *mgr, event_cb_t cb, void *priv)
{
    mgr->cb        = cb;
    mgr->priv_data = priv;
}

void event_trigger(struct event_mgr *mgr, uint32_t type)
{
    if (mgr->cb)                          /* 判空再调 */
        mgr->cb(type, mgr->priv_data);    /* 把 priv 回传 */
}
```

三个要素缺一不可：

| 要素 | 作用 | 缺失后果 |
|------|------|----------|
| typedef 函数指针 | 锁定回调签名 | 签名漂移，UB |
| `void *priv` | 传递上下文状态 | 回调拿不到业务数据，闭包失效 |
| 注册/触发分离 | 解耦「谁调」与「何时调」 | 强耦合，无法复用框架 |

### `void *priv` 的闭包语义

C 没有闭包，但 `void *priv` 等价于「闭包捕获的状态」。回调函数收到 `priv` 后强转回真实类型，访问业务数据：

```c
struct order_ctx {
    uint64_t  user_id;
    uint32_t  max_qty;
    FILE     *log;
};

static void on_quote_arrived(uint32_t type, void *priv)
{
    struct order_ctx *ctx = priv;            /* 强转回真实类型 */
    if (ctx->max_qty > 0) {
        fprintf(ctx->log, "quote type=%u user=%lu\n",
                type, ctx->user_id);
        /* ... 下单逻辑 ... */
    }
}

/* 注册 */
struct order_ctx ctx = { .user_id = 42, .max_qty = 100, .log = stderr };
event_register(&mgr, on_quote_arrived, &ctx);
```

`priv` 是 `void *`，框架代码完全不知道它指向什么——这就是**类型擦除**。回调函数自己负责强转回正确类型，类型约定由注册方和回调方私下保证。

### 判空再调：工程铁律

```c
if (mgr->cb) mgr->cb(type, mgr->priv_data);
```

未注册回调时 `cb == NULL`，直接调用 `NULL(type, priv)` 是 UB，通常崩溃但**不保证**——某些平台可能跳到 0 地址执行。判空是工程铁律，所有框架代码必须遵守。

### 释放回调：函数指针 + `void *`

```c
typedef void (*free_cb_t)(void *obj);

void pool_destroy(void **list, int cnt, free_cb_t free_func)
{
    if (!free_func) {                /* 允许调用方不提供 */
        free(list);
        return;
    }
    for (int i = 0; i < cnt; i++)
        free_func(list[i]);          /* 调用方决定怎么释放 */
    free(list);
}

/* 调用方提供释放函数 */
static void order_free_cb(void *obj) {
    struct order *o = obj;
    free(o->payload);
    free(o);
}
```

`free_cb_t` 让 `pool_destroy` 不需要知道元素是什么类型——调用方传入 `order_free_cb`，框架代码通用。**这是 C 实现泛型容器的核心机制**，详见 ch17。

### 多回调链表

```c
struct listener {
    event_cb_t      cb;
    void           *priv;
    struct listener *next;
};

struct event_mgr {
    struct listener *head;
};

void event_notify_all(struct event_mgr *mgr, uint32_t type)
{
    for (struct listener *l = mgr->head; l; l = l->next) {
        if (l->cb)
            l->cb(type, l->priv);
    }
}
```

观察者模式的标准实现：多个监听者挂链表，事件触发时遍历调用。注意遍历中删除监听者要用 safe 版本（见 ch12.3.2）。

### 回调签名的设计原则

| 原则 | 说明 |
|------|------|
| 入参明确 | 回调需要的状态都通过参数传，不依赖全局变量 |
| `void *priv` 最后 | 约定俗成，priv 作为「捕获状态」放最后 |
| 返回值统一 | 成功/失败码或 void，框架据此决定是否继续 |
| 线程安全声明 | 文档说明回调在哪个线程触发，调用方负责同步 |

## HFT 关联

### DPDK mempool 钩子

```c
struct rte_mempool {
    /* ... */
    rte_mempool_ctor_t  *ctor;   /* 对象初始化钩子 */
    void                *ctor_arg;
};
```

mempool 分配新对象时调用 `ctor(obj, ctor_arg)`，让调用方自定义初始化逻辑（例如填充订单号、时间戳）。这是回调 + `void *` 的典型应用——mempool 框架代码通用，业务初始化由回调决定。

### 订单事件回调

```c
typedef enum {
    EVENT_ORDER_NEW,
    EVENT_ORDER_ACK,
    EVENT_ORDER_FILLED,
    EVENT_ORDER_CANCELLED,
    EVENT_ORDER_REJECTED,
} order_event_t;

typedef void (*order_cb_t)(order_event_t evt,
                            const struct order *o,
                            void *priv);

struct order_engine {
    order_cb_t  callbacks[5];   /* 每种事件一个回调槽 */
    void       *privs[5];
};

void order_engine_dispatch(struct order_engine *e,
                           order_event_t evt,
                           const struct order *o)
{
    if (e->callbacks[evt])
        e->callbacks[evt](evt, o, e->privs[evt]);
}
```

这是**转移表 + 回调**的混合形态：事件类型作数组索引取回调，再调用。风控、日志、统计模块各自注册关心的回调，订单引擎只负责分发，不知道谁在监听。

### 定时器回调

```c
typedef void (*timer_cb_t)(void *priv);

struct timer {
    uint64_t    expire_ns;
    timer_cb_t  cb;
    void       *priv;
    struct list_head link;
};
```

定时器到期时调用 `cb(priv)`，`priv` 携带定时器关联的业务上下文（订单号、检查点等）。这是 HFT 定时器轮的核心数据结构。

### 间接调用的性能考量

回调是间接调用，每次 2-4 ns 开销 + 分支预测风险。HFT 数据面对回调的使用原则：

1. **批量回调**：一次回调传一批事件，减少间接调用次数。
2. **热路径内联**：最高频的回调手工展开成直接调用，低频走回调。
3. **回调表常驻 L1**：函数指针数组对齐到 cache 行，避免 cache miss。

```c
/* 批量回调示例 */
typedef void (*quote_batch_cb_t)(const struct quote *qts,
                                  int n, void *priv);
```

一次调用处理 N 个报价，比 N 次单报价回调高效得多。

## UB 边界

| 情形 | 后果 | 防护 |
|------|------|------|
| `priv` 类型与回调约定不符 | 强转读到错位字段 | 文档明确，单元测试覆盖 |
| 回调在错误线程触发 | 数据竞争 | 框架文档说明触发线程，调用方加锁 |
| 回调中销毁自己（mgr） | UAF，链表遍历崩溃 | 延迟到下一轮事件循环销毁 |
| 注册前触发 | `cb == NULL` 调用 UB | `if (cb) cb(...)` 判空 |
| 回调抛异常（C++） | C 框架 UB | C 回调禁止抛异常，`noexcept` |
| `priv` 指向已释放对象 | UAF | 注销回调与释放对象成对 |

### 回调中销毁自己的陷阱

```c
static void on_done(uint32_t type, void *priv)
{
    struct task *t = priv;
    free(t);                  /* 销毁 priv */
    /* 但 event_notify_all 还在遍历链表，t->link 已释放！ */
}
```

解决方案：

1. **延迟销毁**：标记 `t->pending_free = true`，事件循环下一轮再 free。
2. **safe 遍历**：`list_for_each_safe` 预存 next（见 ch12.3.2）。
3. **引用计数**：`t->refcnt--`，归零才 free。

这是事件驱动框架的经典陷阱，libevent、libev、DPDK 事件循环都遇到并解决过。

### `priv` 生命周期管理

```c
/* 正确：注册方管理 priv 生命周期 */
event_register(&mgr, on_event, &ctx);   /* ctx 在栈，必须比 mgr 活得久 */
/* ... */
event_unregister(&mgr);                 /* 先注销，再释放 ctx */
```

`priv` 的生命周期是注册方的责任，框架代码不负责释放。**注销回调与释放 priv 必须成对**，否则回调触发时 priv 已释放 = UAF。
