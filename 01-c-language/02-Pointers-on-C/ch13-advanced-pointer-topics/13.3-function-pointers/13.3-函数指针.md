# 13.3 函数指针

## 本节讲什么

函数指针是 C 实现**运行时多态**的唯一通用机制——把「调哪个函数」从编译期推迟到运行期。这一节给出函数指针的声明、调用、typedef 封装的完整模板，以及它在数据面分发、驱动表、回调机制里的三大实战形态。

认知锚点：函数指针本身只是「存函数入口地址的变量」，但它的**工程意义远超语法**。Linux VFS 的 `file_operations`、DPDK 的 `eth_dev_ops`、glibc 的 `qsort`、nginx 的模块链——所有 C 写的大型框架都用函数指针做扩展点。看不懂函数指针，就读不懂 C 工程的「多态」。

## 要点

### 声明与调用

```c
int add(int x, int y) { return x + y; }

int (*calc)(int, int);    /* 函数指针变量 */
calc = add;               /* 函数名退化为函数指针 */
int res = calc(3, 5);     /* 等价 add(3, 5) */
int res2 = (*calc)(3, 5); /* 显式解引用，等价 */
```

**函数名退化为函数指针**与数组名退化为指针同构（见 ch08）：

| 表达式 | 类型 | 含义 |
|--------|------|------|
| `add` | `int (*)(int, int)` | 函数首地址 |
| `&add` | `int (*)(int, int)` | 同上（函数无「整体」概念） |
| `add(3, 5)` | `int` | 调用 |
| `calc = add` | 赋值 | 函数指针赋值 |
| `calc(3, 5)` | `int` | 间接调用 |

`add` 与 `&add` 在函数语境下等价（不像数组 `arr` 与 `&arr` 类型不同），这是 C 标准的特例。

### typedef：强制规范

```c
/* 错误示范：裸函数指针 */
void register_cb(int (*cb)(int, void *));

/* 正确：typedef */
typedef int (*event_cb_t)(int, void *);
void register_cb(event_cb_t cb);
```

```c
/* DPDK 报文处理函数类型 */
typedef void (*pkt_handler_t)(struct rte_mbuf *pkt);

pkt_handler_t handler = process_quote;
handler(mbuf);
```

typedef 的好处：① 可读性（名字即语义）；② 修改签名一处生效；③ 编译错误信息清晰；④ 团队强制规范。详见 13.2。

### 函数指针数组（分发器模式）

```c
typedef void (*pkt_handler_t)(struct rte_mbuf *pkt);

static pkt_handler_t pkt_dispatch[] = {
    process_heartbeat,   /* type 0 */
    process_quote,       /* type 1 */
    process_order,       /* type 2 */
    process_cancel,      /* type 3 */
};

void on_packet(struct rte_mbuf *mbuf, uint8_t type)
{
    if (type < sizeof(pkt_dispatch) / sizeof(pkt_dispatch[0]))
        pkt_dispatchtype;   /* O(1) 间接跳转 */
}
```

这是**转移表（jump table）**模式，详见 13.3.2。核心优势：

1. **O(1) 分发**：一次数组索引 + 一次间接调用。
2. **分支预测友好**：固定索引的间接跳转，CPU 分支预测器可学习。
3. **表驱动扩展**：新增类型只需加表项，不改分发逻辑。

对比 `if-else if` 链：平均要 n/2 次比较，分支预测失败率高，HFT 数据面不可接受。

### 内核 file_operations 风格

```c
struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    long (*unlocked_ioctl)(struct file *, unsigned int, unsigned long);
    /* ... */
};

static const struct file_operations my_fops = {
    .read    = my_read,
    .write   = my_write,
    .open    = my_open,
    .release = my_release,
};
```

设计要点：

- **结构体里全是函数指针**：每个字段是一个「操作槽位」。
- **指定初始化（C99）**：`.read = my_read` 只填关心的字段，其余默认 NULL。
- **VFS 层调用时判空**：`if (fops->read) fops->read(...)`，未实现的操作返回 `-ENOSYS`。
- **`const` 修饰**：操作表只读，放 `.rodata`，多进程共享一份物理页。

这是 C 实现「接口 + 实现」分离的标准范式。DPDK `eth_dev_ops`、`rte_mempool_ops`、nginx `ngx_module_t` 全部沿用。

### 函数指针的存储与对齐

```c
sizeof(handler_fn_t) = 8;   /* x86-64，与数据指针同宽 */
```

x86-64 上函数指针与数据指针都是 8 字节，但对齐要求可能不同（函数地址通常 16 字节对齐，`-falign-functions`）。函数指针数组在 cache 上的表现：每个槽位 8 字节，8 个槽位占一个 cache 行，索引访问高效。

## HFT 关联

### PMD 驱动表

DPDK 物理网卡轮询驱动（PMD）的核心结构：

```c
struct eth_dev_ops {
    eth_dev_configure_t           dev_configure;
    eth_dev_start_t               dev_start;
    eth_dev_stop_t                dev_stop;
    eth_rx_queue_setup_t          rx_queue_setup;
    eth_tx_queue_setup_t          tx_queue_setup;
    eth_link_update_t             link_update;
    /* ... */
};
```

不同厂商（Intel、Mellanox、Netcope）各提供一份 `eth_dev_ops` 实例。DPDK 框架代码只调用函数指针，**不知道也不关心底层硬件**——这是 C 多态的极致体现。HFT 团队自研 FPGA 网卡驱动时，只需实现这套函数指针表即可接入 DPDK 框架。

### 策略回调

```c
typedef int (*strategy_on_quote_t)(struct strategy *, const struct quote *);
typedef int (*strategy_on_trade_t)(struct strategy *, const struct trade *);

struct strategy {
    const char                *name;
    strategy_on_quote_t        on_quote;
    strategy_on_trade_t        on_trade;
    void                      *priv;
};
```

策略模块以 `.so` 形式 `dlopen` 加载，通过 `dlsym` 拿到 `struct strategy *`。策略切换不停机——换函数指针即可。**热加载的核心机制就是函数指针**。

### qsort 与比较函数

```c
typedef int (*cmp_fn_t)(const void *, const void *);

void sort_orders(struct order *arr, size_t n, cmp_fn_t cmp)
{
    qsort(arr, n, sizeof(*arr), cmp);
}

/* 按价格升序 */
int cmp_price_asc(const void *a, const void *b) {
    return ((const struct order *)a)->price - ((const struct order *)b)->price;
}
```

`qsort` 是 C 标准库最经典的函数指针应用。HFT 场景下排序不常用（数据面追求 O(1)），但在初始化、风控批量处理时仍有用。

### 间接调用的性能代价

| 调用形式 | 延迟（x86-64，大致量级） | 分支预测 |
|----------|--------------------------|----------|
| 直接调用 `add(a,b)` | 1-2 ns | 100% 准确 |
| 内联后 | 0 ns（指令融合） | N/A |
| 间接调用 `(*fp)(a,b)` | 2-4 ns | 70-95%（依赖历史） |
| 间接跳转（转移表） | 3-5 ns | BTB 学习 |

间接调用的开销主要在**分支预测失败**：CPU 不知道下一条指令地址，必须等取指完成。现代 CPU 有 BTB（Branch Target Buffer）学习历史，但策略变化时仍会预测失败，导致流水线冲刷 10-20 周期。HFT 数据面优化：

1. **PGO**：让编译器基于 profile 优化间接跳转。
2. **手工展开热点**：高频类型单独 if-else，低频走转移表。
3. **`__builtin_expect` / `likely`/`unlikely`**：辅助分支预测。

## UB 边界

| 情形 | 后果 | 防护 |
|------|------|------|
| 未初始化的函数指针调用 | 跳野地址，崩溃或执行任意代码 | `= NULL` 初始化，调用前判空 |
| 赋值不同签名函数 | 栈帧错乱，UB | typedef 锁定签名，编译器 `-Werror=incompatible-pointer-types` |
| 函数指针与数据指针互转 | 哈佛架构不兼容 | 不要互转，POSIX 场景才用 `void *` 中转 |
| `NULL` 函数指针调用 | UB，可能跳 0 地址 | `if (cb) cb(...)` 判空 |
| 释放含函数指针的结构后调用 | UAF | free 后置 NULL |
| 通过 `dlsym` 拿到 `void *` 不强转直接调用 | 编译错误 | 强转到正确函数指针类型 |

### 不同签名赋值的危险

```c
typedef int (*cb_t)(int);
void f(long x);            /* 签名不同 */

cb_t cb = (cb_t)f;         /* 强转，编译通过 */
cb(42);                    /* UB：f 期望 long，收到 int 的位模式 */
```

强转能绕过编译器检查，但**行为未定义**。x86-64 上 `int` 和 `long` 都在寄存器传参，碰巧能跑，但 ARM、RISC-V 上参数传递规则不同，立刻崩。`-Werror=incompatible-pointer-types` 把这类隐患堵死在编译期。

### `dlsym` 的强制转换

```c
void *sym = dlsym(handle, "my_function");
my_fn_t fn = *(my_fn_t *)&sym;   /* 严格别名安全 */
/* 或 POSIX 风格 */
my_fn_t fn = (my_fn_t)sym;       /* POSIX 允许，C 标准不允许 */
```

C 标准不允许 `void *` 转函数指针，POSIX 强制允许（为了 `dlsym`）。可移植代码用 union 或 memcpy 桥接，工程代码直接强转。
