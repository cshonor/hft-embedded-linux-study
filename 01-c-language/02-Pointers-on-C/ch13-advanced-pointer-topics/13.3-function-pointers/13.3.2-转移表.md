# 13.3.2 转移表

## 本节讲什么

转移表（jump table / dispatch table）是函数指针数组的**工程化形态**——用「数组索引 → 函数指针」的查表替代 `if-else if` 链，把 O(n) 的分支判断压缩成 O(1) 的间接跳转。这一节给出转移表的完整实现、边界检查、与 `if-else` 的性能对比，以及它在报文分发、状态机、PMD 驱动表里的实际部署。

认知锚点：转移表不是「炫技优化」，而是**数据面代码的默认选择**。HFT 报文分发、内核系统调用表、CPU 指令译码器——所有「类型 → 处理函数」的高频映射都用转移表。理解它就理解了 C 工程里「表驱动」的核心思想。

## 要点

### 基本形态：索引即类型

```c
typedef void (*pkt_handler_t)(struct rte_mbuf *pkt);

static pkt_handler_t dispatch[] = {
    [0] = handle_heartbeat,   /* MSG_HEARTBEAT = 0 */
    [1] = handle_quote,       /* MSG_QUOTE     = 1 */
    [2] = handle_order,       /* MSG_ORDER     = 2 */
    [3] = handle_cancel,      /* MSG_CANCEL    = 3 */
};

void on_packet(struct rte_mbuf *mbuf, uint8_t type)
{
    if (type < sizeof(dispatch) / sizeof(dispatch[0]))
        dispatchtype;   /* O(1) 间接跳转 */
    else
        handle_unknown(mbuf);   /* 越界保护 */
}
```

三个关键设计：

1. **指定初始化 `[type] = handler`**（C99）：表项与类型显式绑定，新增类型只需加一行。
2. **边界检查**：`type < sizeof(dispatch) / sizeof(dispatch[0])`，防越界访问野指针。
3. **ARRAY_SIZE 宏**：

```c
#define ARRAY_SIZE(a) (sizeof(a) / sizeof((a)[0]))
if (type < ARRAY_SIZE(dispatch))
    dispatchtype;
```

### 转移表 vs if-else 链

| 维度 | 转移表 | if-else 链 |
|------|--------|------------|
| 时间复杂度 | O(1) | O(n) 平均 n/2 次比较 |
| 分支预测 | BTB 学习间接跳转 | 多级条件分支，失败率高 |
| 扩展性 | 表驱动加一行 | 改代码加 if-else |
| 缺省处理 | 越界走 default | 最后 else 兜底 |
| 表大小 | 占内存（每项 8 字节） | 不占额外内存 |
| 调试 | 难（间接跳转） | 易（直接看条件） |
| 编译优化 | 难内联 | 易内联（编译器可见） |
| HFT 数据面 | **首选** | 少量分支可接受 |

**选型口诀**：**类型数 ≥ 4 且高频 → 转移表**；**类型数 ≤ 3 或低频 → if-else**。HFT 报文分发通常 4-16 种消息类型，转移表是标配。

### 性能量级（x86-64）

```
if-else 4 分支：  约 5-8 ns（含 1-2 次分支预测失败）
转移表 4 项：     约 3-5 ns（BTB 命中间接跳转）
转移表 16 项：    约 3-5 ns（与项数无关，O(1)）
```

转移表的延迟基本与项数无关，这是 O(1) 的本质。`if-else` 随分支数线性增长，4 分支以上转移表必胜。

### 状态机：枚举驱动转移表

```c
typedef enum {
    ST_IDLE,
    ST_WAIT_ACK,
    ST_OPEN,
    ST_CLOSE_PENDING,
    ST_NUM
} state_t;

typedef enum {
    EV_SEND,
    EV_ACK,
    EV_TIMEOUT,
    EV_CLOSE,
    EV_NUM
} event_t;

typedef state_t (*transition_fn_t)(state_t, event_t, void *ctx);

/* 状态转移表：[当前状态][事件] = 转移函数 */
static transition_fn_t fsm[ST_NUM][EV_NUM] = {
    [ST_IDLE] = {
        [EV_SEND]   = idle_to_wait_ack,
        [EV_CLOSE]  = idle_stay,
    },
    [ST_WAIT_ACK] = {
        [EV_ACK]     = wait_ack_to_open,
        [EV_TIMEOUT] = wait_ack_to_idle,
    },
    [ST_OPEN] = {
        [EV_CLOSE]   = open_to_close_pending,
    },
};

state_t fsm_step(state_t cur, event_t ev, void *ctx)
{
    if (cur < ST_NUM && ev < EV_NUM && fsm[cur][ev])
        return fsm[cur][ev](cur, ev, ctx);
    return cur;   /* 无转移，保持当前状态 */
}
```

**二维转移表**是状态机的标准实现。`fsm[cur][ev]` 查表得到转移函数，未定义的转移为 NULL（保持原状态）。这种写法把状态机逻辑变成数据，新增状态/事件只需改表，不动代码。

### 内核与驱动：file_operations、sys_call_table、eth_dev_ops

```c
/* Linux 系统调用表（arch/x86/entry/syscalls） */
const sys_call_ptr_t sys_call_table[] = {
    [0]  = sys_read,
    [1]  = sys_write,
    [2]  = sys_open,
    /* ... */
    [__NR_execve] = sys_execve,
};

/* DPDK eth_dev_ops */
static const struct eth_dev_ops my_pmd_ops = {
    .dev_configure   = my_configure,
    .dev_start       = my_start,
    .dev_stop        = my_stop,
    .rx_queue_setup  = my_rx_setup,
    .tx_queue_setup  = my_tx_setup,
};
```

三类转移表的共同点：

1. **索引/字段名 → 函数指针**：查表替代分支。
2. **`const` 修饰**：只读放 `.rodata`，多进程共享。
3. **指定初始化**：未实现的槽位默认 NULL，调用方判空。
4. **统一调用约定**：所有函数指针同签名，框架代码通用。

### 二级函数指针表（插件热切换）

```c
typedef void (*pkt_handler_t)(struct rte_mbuf *);
pkt_handler_t *table;   /* 指向函数指针数组的指针 */

/* 切换策略表 */
void switch_strategy(pkt_handler_t *new_table)
{
    /* 内存屏障确保其他核看到完整表 */
    smp_wmb();
    table = new_table;
}
```

`pkt_handler_t *table` 是「指向函数指针数组的指针」，可以整体替换数组。用于策略热切换：新表预构建完成后，原子替换指针。这是 RCU 模式的简化形态——读端无锁，写端替换整个表。

### 字符串 key 的转移表

```c
struct cmd_entry {
    const char  *name;
    handler_fn_t fn;
};

static const struct cmd_entry cmd_table[] = {
    {"buy",    cmd_buy},
    {"sell",   cmd_sell},
    {"cancel", cmd_cancel},
    {"query",  cmd_query},
};

void exec_cmd(const char *name, void *arg)
{
    for (size_t i = 0; i < ARRAY_SIZE(cmd_table); i++) {
        if (strcmp(cmd_table[i].name, name) == 0) {
            cmd_table[i].fn(arg);
            return;
        }
    }
    fprintf(stderr, "unknown command: %s\n", name);
}
```

字符串 key 无法用数组索引，只能线性查找或哈希表。**命令分发、配置解析**常用这种形态。高频场景下用哈希表（O(1) 平均），低频用线性查找（O(n)，但 n 通常很小）。

## HFT 关联

### 报文分发

```c
typedef void (*msg_handler_t)(const struct market_msg *);

static const msg_handler_t msg_dispatch[] = {
    [MSG_HEARTBEAT] = on_heartbeat,
    [MSG_QUOTE]     = on_quote,
    [MSG_TRADE]     = on_trade,
    [MSG_ORDER]     = on_order,
    [MSG_CANCEL]    = on_cancel,
    [MSG_DEPTH]     = on_depth,
};

static inline void dispatch_msg(const struct market_msg *m)
{
    uint16_t type = m->msg_type;
    if (type < ARRAY_SIZE(msg_dispatch) && msg_dispatch[type]) {
        msg_dispatchtype;
    } else {
        stats_inc(STATS_UNKNOWN_MSG);
    }
}
```

这是 HFT 数据面最热的代码路径。每个报文进来都要走一次转移表分发，**延迟要求纳秒级**。优化点：

1. **表常驻 L1**：`msg_dispatch` 数组 6 项 × 8 字节 = 48 字节，刚好一个 cache 行，热点必命中。
2. **`msg_type` 在报文头部固定偏移**：取类型不需要解析变长字段，1 条 `mov` 指令。
3. **`static inline`**：内联到调用点，消除函数调用开销。
4. **`__builtin_expect`**：标记 `type < ARRAY_SIZE` 为 `likely`，分支预测器优化。

### 策略热切换

```c
/* 双表 + 原子切换 */
static msg_handler_t *active_table = table_v1;

void switch_to_v2(void)
{
    /* 确保 table_v2 完全可见 */
    smp_wmb();
    active_table = table_v2;
    /* 旧表延迟释放（RCU 或 epoch） */
    synchronize_rcu();
    free(table_v1);
}
```

策略升级不停机：新表预构建 → 写屏障 → 原子换指针 → RCU 等待读者退出 → 释放旧表。**读端完全无锁**，写端承担同步成本。这是 HFT 高可用部署的核心机制。

### 状态机：订单生命周期

```c
/* 订单状态转移表 */
static const transition_fn_t order_fsm[ORD_ST_NUM][ORD_EV_NUM] = {
    [ORD_NEW] = {
        [EV_ACK]      = new_to_pending,
        [EV_REJECT]   = new_to_rejected,
    },
    [ORD_PENDING] = {
        [EV_FILL]     = pending_to_filled,
        [EV_CANCEL]   = pending_to_cancelled,
        [EV_TIMEOUT]  = pending_to_expired,
    },
    /* ... */
};
```

订单从 NEW → PENDING → FILLED/CANCELLED 的转移用表驱动，新增状态/事件改表不改代码。这是订单引擎核心数据结构。

### CPU 指令译码器

CPU 的指令译码本质上是转移表：操作码作索引，查表得到执行函数。`switch-case` 长链（≥ 4 个 case 且密集）编译器会自动生成转移表（`-foptimize-jump-tables`）。理解这一点就能解释为什么 `switch` 在密集 case 下比 `if-else` 快——编译器帮你生成了转移表。

## UB 边界

| 情形 | 后果 | 防护 |
|------|------|------|
| 越界访问 `dispatch[type]` | 野指针，崩溃 | `if (type < ARRAY_SIZE(...))` 边界检查 |
| 未初始化的表项调用 | 跳野地址 | `static` 数组零初始化，调用前判空 `if (dispatch[type])` |
| 表项函数签名不一致 | 栈帧错乱，UB | typedef 锁定签名，编译器 `-Werror` |
| 多核读写表的同时切换 | 数据竞争 | RCU 或写屏障 + 延迟释放 |
| 表构建未完成就发布 | 读端看到半成品 | 写屏障 + 原子指针替换 |
| 转移表与枚举不同步 | 漏处理或越界 | `_Static_assert(MSG_NUM == ARRAY_SIZE(dispatch))` |

### 静态断言锁定表大小

```c
_Static_assert(ARRAY_SIZE(msg_dispatch) == MSG_TYPE_NUM,
               "dispatch table size mismatch with enum");
```

枚举新增类型但忘记加表项是经典 bug。`_Static_assert` 在编译期锁定两者一致，漏加立刻编译失败。这是 C11 引入的零成本防护。

### 越界检查的性能权衡

```c
/* 严格版：每次调用都检查 */
if (type < ARRAY_SIZE(dispatch) && dispatch[type])
    dispatchtype;

/* 信任版：报文已在上层校验 */
dispatchtype;   /* type 一定合法 */
```

HFT 数据面在报文入口已校验 `type` 合法，分发处可省略检查省 1-2 周期。但**省略检查的前提是上层 100% 可信**，外部协议解析层不能省。安全与性能的权衡。
