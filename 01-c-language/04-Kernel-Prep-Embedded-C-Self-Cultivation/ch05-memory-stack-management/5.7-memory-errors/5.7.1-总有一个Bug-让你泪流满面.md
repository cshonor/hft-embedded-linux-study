# 5.7.1 总有一个 Bug，让你泪流满面

## 本节讲什么

内存 Bug **复现难、定位慢**：时好时坏、Release 才崩、多线程竞态。本节建立 **系统化排查流程**：稳定复现 → 最小用例 → 工具（GDB/Valgrind/ASAN/core）→ 对照源码假设。

## 要点

### 排查顺序

1. **可复现吗？** 固定输入、`-O0 -g`、单线程先查
2. **哪类错误？** SIGSEGV/SIGABRT/glibc corruption message
3. **工具**：Valgrind > ASAN > mtrace > 肉眼
4. **ARM 板子**：无 Valgrind 时用 **JTAG/GDB**、`printk`、栈回溯

```bash
gcc -g -O0 -fno-omit-frame-pointer -o bug bug.c
ulimit -c unlimited
./bug
gdb ./bug core
(gdb) bt full
```

### 内核/DPDK

- **Kernel BUG/oops**：`call trace` + `addr2line` / `decode_stacktrace`
- **DPDK**：开启 `RTE_LIBRTE_MALLOC_DEBUG`、mbuf 断言

### 心态

- 假设 **自己的越界** 先于怀疑编译器
- Git bisect 找引入提交的 commit

## 代码自测

**题目 1：** 以下代码有哪几种可能的内存错误？
```c
char *p = malloc(10);
strcpy(p, "Hello World!");   // 问题1
char *q = NULL;
*q = 42;                     // 问题2
free(p);
printf("%s\n", p);           // 问题3
p[0] = 'X';                  // 问题4
```
<details>
<summary>参考答案</summary>

四种内存错误：

1. **缓冲区溢出**（Heap Overflow）：`strcpy(p, "Hello World!")` 写入 13 字节（含 NUL），但 p 只有 10 字节。覆盖堆元数据，可能导致 crash 或被攻击。
2. **空指针解引用**（NULL Dereference）：`*q = 42`，q 是 NULL，访问地址 0，段错误。
3. **Use-After-Free**：`printf("%s", p)` 在 `free(p)` 后访问已释放内存，未定义行为。
4. **Use-After-Free 写入**：`p[0] = 'X'` 在 free 后写入已释放内存，可能破坏堆管理结构。

防护：`strncpy(p, "Hello World!", 9); p[9] = 0;`；检查 NULL；free 后 `p = NULL;`；用 ASan/Valgrind 检测。

</details>
