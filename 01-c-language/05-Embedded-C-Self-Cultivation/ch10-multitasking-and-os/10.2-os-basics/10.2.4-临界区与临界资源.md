# 10.2.4 临界区与临界资源

## 本节讲什么

**临界资源** 同一时刻只允许一个执行流访问；访问它的代码段叫 **临界区（Critical Section）**。本节讲解 **关中断、mutex、semaphore、queue、event group** 的选型，以及 **优先级反转** 与 **死锁**，对应 **demo04_semaphore**、**demo05_queue**。

## 要点

**临界资源示例**：

- 全局环形缓冲区、UART 硬件、共享配置文件、动态内存堆

**保护手段层次**：

```
关中断（最短、单核有效）
    ↓
自旋锁 spinlock（多核短临界，内核/DPDK）
    ↓
mutex（可能阻塞，RTOS/Linux 用户态）
    ↓
semaphore / queue（同步 + 资源计数）
```

**关中断临界区**（单核 MCU）：

```c
uint32_t primask = __get_PRIMASK();
__disable_irq();
/* 临界区：几微秒内完成 */
shared_counter++;
__set_PRIMASK(primask);
```

- 不能关太久 → 影响中断响应与调度 tick
- 多核无效 → 需 spinlock + 内存屏障

**Mutex（互斥量）**（**demo04**）：

```c
os_mutex_lock(&uart_mtx);
uart_write(buf, len);
os_mutex_unlock(&uart_mtx);
```

- **优先级继承**：持锁任务临时提升到等待者优先级，缓解 **优先级反转**
- FreeRTOS：`xSemaphoreCreateMutex()` + `configUSE_MUTEXES`

**Semaphore（信号量）**：

| 类型 | 初值 | 典型用途 |
|------|------|----------|
| 二进制 | 0/1 | 事件通知、同步 |
| 计数 | N | 资源池（N 个缓冲区） |

```c
os_sem_wait(&rx_sem);   /* 无数据则 BLOCKED */
process(packet);
os_sem_post(&tx_sem);
```

**Queue（消息队列）**（**demo05_queue**）：

- 传递 **数据副本** 或指针（需约定生命周期）
- 天然解耦生产者/消费者；阻塞式 `recv` 触发调度（**10.2.1**）

**Event Group（事件组）**：

- 多位标志：`wait(TASK_A_BIT | TASK_B_BIT, AND/OR)`
- 适合「等多条件就绪」；FreeRTOS `EventGroup`

**优先级反转**（经典案例）：

```
L 持 mutex ──► M 抢占 L ──► H 等 mutex 被 M 间接阻塞
```

对策：优先级继承 mutex、避免 L/M 长时间占 CPU

**死锁四条件**（破坏任一即可）：

1. 互斥 2. 持有并等待 3. 不可剥夺 4. 循环等待

- 嵌入式对策：**固定加锁顺序**、**trylock 超时**、减少嵌套锁

**选型速查**：

| 需求 | 选用 |
|------|------|
| 保护短全局变量 | 关中断 / mutex |
| 任务间传结构体 | queue |
| 通知「发生了一件事」 | 二进制 sem / event |
| 限流 N 同类资源 | 计数 sem |

## 常见陷阱

1. **关中断临界区内调用阻塞 API → 死锁或丢 tick**
   `__disable_irq()` 后调 `os_sem_wait()`、`printf()`（可能阻塞于 UART DMA）、`malloc()`（可能拿不到堆锁）——调度器被关，阻塞的任务永远等不到唤醒，系统死。**约定**：关中断临界区**只做几条指令的纯内存操作**（计数器自增、链表头插入），任何可能阻塞或调度的 API 都禁用。RTOS 文档明确写"ISR/临界区内禁调 FromISR 之外的 API"。

2. **优先级反转未处理 → 高优先级任务被低优先级"间接阻塞"**
   经典场景：L 持 mutex，H 等 mutex，M 抢占 L 跑——L 没机会释放 mutex，H 被 M 间接阻塞。**对策**：用**优先级继承 mutex**（FreeRTOS `xSemaphoreCreateMutex` 默认开），持锁任务临时提升到 H 的优先级，L 跑完快速释放。**坑**：二进制 semaphore **没有**优先级继承——用它做互斥会触发反转。优先级继承 mutex 性能略低，但实时性更可靠。

3. **自旋锁临界区内睡眠/调度 → 死锁整个 CPU**
   `spin_lock` 假设临界区极短、不阻塞——内核抢占被关，持锁 CPU 不会切走。但若临界区内 `kmalloc(GFP_KERNEL)`（可能睡眠）、`copy_from_user`（可能缺页睡眠）、`schedule()`——调度器切到其他任务，该任务若也尝试拿同一自旋锁即死锁（自旋等待永远不会前进）。**约定**：自旋锁内**禁睡眠**——用 `spin_lock_irqsave` + 仅做指针/标志操作；需要睡眠用 mutex。

## 自测题

**1.（选择）** 单核 Cortex-M 上保护 `shared_counter++` 最合适的手段是？
- A. mutex
- B. 自旋锁
- C. 关中断
- D. semaphore

<details><summary>答案</summary>

**C**。单核 MCU 上 `++` 操作几条指令，**关中断**最轻量——`__disable_irq()`/`__set_PRIMASK()` 几个时钟周期，无锁结构开销。mutex 需要任务调度（可能切走），杀鸡用牛刀；自旋锁在单核无意义（自旋等不到释放）；semaphore 同样过重。**多核**或 SMP Linux 上关中断无效（只关本核），必须自旋锁。**原则**：单核短临界区用关中断，多核短临界区用自旋锁，长临界区用 mutex。

</details>

**2.（判断）** 用二进制 semaphore 当 mutex 用是等价的。

<details><summary>答案</summary>

**错**。二者都能做"互斥"，但有关键差异：
1. **优先级继承**：mutex 有，semaphore 没有——用 semaphore 做互斥会触发优先级反转。
2. **所有权**：mutex 有 owner 概念（持锁者必须解锁），semaphore 任何人都能 post——错误代码误释放 semaphore 难以发现。
3. **递归**：mutex 可设 recursive（同任务多次加锁），semaphore 不行。
**约定**：保护临界资源用 mutex，同步/通知用 semaphore。FreeRTOS 文档明确"用 mutex 做互斥，semaphore 做同步"。

</details>

**3.（踩坑）** 任务 A、B 都需要锁 L1、L2。A 先拿 L1 再拿 L2，B 先拿 L2 再拿 L1。某次 A 拿到 L1 后被 B 抢占，B 拿到 L2 后等 L1——两任务死锁。如何避免？

<details><summary>答案</summary>

**死锁四条件**：互斥、持有并等待、不可剥夺、循环等待。修复方式：
1. **固定加锁顺序**——所有任务按相同顺序拿锁（如先 L1 后 L2），破坏循环等待。最常用。
2. **trylock 超时**——`mutex_take(L2, timeout)`；超时则释放 L1 重试，破坏持有并等待。
3. **降低嵌套**——重构代码让一个任务不需同时持两把锁（拆分临界区）。
4. **避免持锁时调度**——短临界区用关中断/自旋锁，不调度即不被抢占。
**预防**：code review 时画"锁依赖图"，发现环即重构。Linux 内核有 `lockdep` 自动检测潜在死锁。

</details>

**4.（应用）** 设计一个 ISR → 任务的环形缓冲区通信：ISR 收一个字节入 buffer，任务消费。给出加锁/同步方案。

<details><summary>答案</summary>

```c
/* 方案一：关中断 + ringbuf（单生产者单消费者，无锁即可） */
struct ring {
    uint8_t buf[256];
    volatile uint16_t head;   /* ISR 写 */
    volatile uint16_t tail;   /* task 读 */
};
static struct ring rx_ring;

void UART_ISR(void) {
    uint16_t h = rx_ring.head;
    rx_ring.buf[h & 255] = UART->DR;
    rx_ring.head = h + 1;
}

void consumer_task(void) {
    while (1) {
        while (rx_ring.head != rx_ring.tail) {
            uint8_t b = rx_ring.buf[rx_ring.tail & 255];
            rx_ring.tail++;
            process(b);
        }
        /* 阻塞等下次中断唤醒 */
        os_sem_wait(&rx_sem);
    }
}
```
**关键点**：
- **SPSC 无锁队列**：单生产者单消费者下，head/tail 各自只被一方写，读对方变量用 `volatile` + 适当屏障即安全——无需关中断/锁。
- **唤醒**：ISR 收数据后 `os_sem_post_from_isr(&rx_sem)` 通知任务。
- **溢出处理**：head 超过 tail 太多即丢字节，需统计 drop count。
- **多生产者或多消费者**则必须加锁——SPSC 无锁不适用。
- DPDK `rte_ring` 用完全相同的 SPSC 无锁模式，性能极高。

</details>
