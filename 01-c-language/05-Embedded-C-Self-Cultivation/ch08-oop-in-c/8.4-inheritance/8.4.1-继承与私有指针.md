# 8.4.1 继承与私有指针

## 本节讲什么

除首成员继承外，C 常用 **PIMPL（pointer to implementation）**：公开 struct 只含一个 `void *priv` 或 `struct xxx_private *`，真实字段在 `.c` 堆分配。子类「继承」时 priv 指向含基类状态的结构。内核 **`net_device`** 的 `ml_priv`、`ieee80211_ptr` 等即是把协议私有数据与通用 netdev 分离。

## 要点

**私有指针模式**：

```c
/* public.h */
typedef struct widget widget_t;

widget_t *widget_create(void);
void      widget_destroy(widget_t *w);
int       widget_draw(widget_t *w);

/* widget.c */
struct widget_private {
    int x, y;
    struct theme *theme;   /* 「基类」状态也可放 priv */
};

struct widget {
    struct widget_private *priv;   /* 仅一个指针对外可见 */
};

widget_t *widget_create(void) {
    widget_t *w = kzalloc(sizeof(*w), GFP_KERNEL);
    w->priv = kzalloc(sizeof(*w->priv), GFP_KERNEL);
    return w;
}
```

| 方式 | 优点 | 缺点 |
|------|------|------|
| **首成员继承** | 零间接、可 container_of | 子类布局暴露于同一头文件 |
| **私有指针** | 完全隐藏大小与字段 | 多一次间接；需配对 alloc/free |
| **混合** | 公开基类 + priv 扩展 | 内核 netdev 常见 |

**继承 + priv**：

```c
struct uart_dev {
    struct Device base;           /* 公开继承，框架可见 */
    struct uart_private *priv;    /* 寄存器映射等隐藏 */
};
```

- **`dev_get_drvdata`** 等价于在 `struct device` 上挂 priv
- 用户态 **demo01** 不透明类型是 priv 的极端形式（整个 struct 都隐藏）
- 避免在头文件暴露 `struct xxx_private`，否则封装失效

## 常见陷阱

1. **`priv` 双重所有权 → 双 free 或泄漏**
   PIMPL 模式中 `widget_create` 分配 `widget` 和 `priv` 两块。`widget_destroy` 必须**两步释放**：先 `priv->theme` 等子资源、再 `kfree(priv)`、最后 `kfree(w)`。漏 `kfree(priv)` 泄漏；重复 `kfree(priv)`（如 `priv` 被 `widget_destroy` 释放后用户又调用 `priv_free`）双 free。**约定**：`priv` 生命周期严格由 owner 管理，外部代码只能通过 accessor 读取，不能持有 `priv` 指针。

2. **首成员继承的 `container_of` 必须基类在前 → 改字段顺序即崩**
   `struct platform_device { struct device dev; ... }` 的 `dev` 必须是首成员，否则 `container_of` 算偏移时 `dev` 与"被当作基类"的语义不匹配。**坑**：有人重构时把 `dev` 移到中间位置——`(struct device *)pdev` 仍指向 `pdev` 首地址，但 `dev` 已不在那里，所有 `dev->xxx` 访问到错位字段。编译期不报错，运行时静默错乱。**约定**：基类成员永远在派生类首位置，且用 `container_of` 而非强转。

3. **`priv` 指针在多线程下被并发修改 → 数据竞争**
   `widget->priv` 通常 init 后只读，但若设计成"运行时切换 priv"（如运行时切换实现策略），需加锁。新手误以为"指针赋值原子"省略同步，在弱内存序架构（ARM/POWER）下读到部分更新的指针。**正确**：要么 init 后不可变（推荐），要么用 `RCU` 或 `atomic_load` 保护。

## 自测题

**1.（选择）** PIMPL 模式相比"首成员继承"的主要优势？
- A. 性能更高（少一次间接）
- B. 完全隐藏内部字段，ABI 解耦
- C. 内存占用更小
- D. 不需要 `container_of`

<details><summary>答案</summary>

**B**。PIMPL 头文件只暴露 `struct widget` 前向声明 + `void *priv`（或不透明指针），具体字段在 `.c` 文件中——**ABI 解耦**：改 `priv` 内部字段不破坏二进制兼容（只需重编 `.c`，不影响使用方）。代价是多一次指针间接（性能略低）。首成员继承性能更好但子类布局暴露于头文件。现代 C 库（glib Qt 私有）大量用 PIMPL。

</details>

**2.（判断）** `struct platform_device { struct device dev; int id; };` 后 `(struct device *)pdev` 等价于 `&pdev->dev`。

<details><summary>答案</summary>

**对**——但**前提是 `dev` 是首成员**。C 标准保证结构体首成员地址等于结构体地址，所以 `(struct device *)pdev == &pdev->dev`。**坑**：若有人把 `dev` 移到 `int id;` 之后，强转仍指向首地址（`id` 处），但 `&pdev->dev` 指向偏移 4——**两者不再相等**，强转版本访问到错位字段。**约定**：永远用 `&pdev->dev` 显式取地址，不用强转——表达意图更清楚，重构安全。

</details>

**3.（踩坑）** 头文件 `struct widget { struct widget_private *priv; };`，`.c` 中 `struct widget_private { int x; struct theme *theme; };`。用户拿到 `widget_t *w` 后想"直接访问 `w->priv->x`"——但 `widget_private` 在 `.c` 中定义，头文件不可见。用户改为 `((int *)w->priv)[0]`。这种做法有什么风险？

<details><summary>答案</summary>

**多重风险**：
1. **耦合私有布局**——访问方硬编码了 `x` 在 priv 首字段，一旦 priv 字段顺序调整立即崩。
2. **类型不安全**——`int *` 强转绕过编译器类型检查，priv 若首字段是 `struct theme *`（指针），`int` 读到一半。
3. **ABI 假象**——看似能跑，实际依赖"priv 首字段是 int"这一**未文档化约定**，重构即破。
**正确做法**：
- 在头文件提供 accessor：`int widget_get_x(widget_t *w);`
- 若必须暴露性能敏感字段，用 `static inline` 包装，priv 仍隐藏。
- 内核 `struct net_device` 用 `netdev_priv()` 取 priv，但 priv 内部布局由协议代码独占——不鼓励跨模块直接访问。

</details>

**4.（应用）** 用"首成员继承 + 私有指针"设计一个 UART 驱动：基类 `struct Device` 由框架定义，子类 `struct uart_dev` 暴露给框架，`priv` 隐藏寄存器映射。给出代码骨架并说明封装边界。

<details><summary>答案</summary>

```c
/* device.h (框架公开) */
struct Device {
    const struct device_ops *ops;   /* 虚表 */
    const char *name;
};
struct device_ops {
    int (*init)(struct Device *);
    void (*shutdown)(struct Device *);
};

/* uart.h (驱动公开) */
#include "device.h"
struct uart_dev {
    struct Device base;              /* 首成员继承 */
    /* 公开字段：仅框架关心的 */
    int port_no;
    /* priv 隐藏寄存器细节 */
    struct uart_regs *regs;
};
extern const struct device_ops uart_ops;

/* uart.c (驱动私有) */
struct uart_regs {                   /* 不在头文件 */
    volatile uint32_t ctrl;
    volatile uint32_t data;
    volatile uint32_t status;
};

static int uart_init(struct Device *d) {
    struct uart_dev *u = container_of(d, struct uart_dev, base);
    u->regs->ctrl = CTRL_ENABLE;
    return 0;
}
static void uart_shutdown(struct Device *d) {
    struct uart_dev *u = container_of(d, struct uart_dev, base);
    u->regs->ctrl = 0;
}
const struct device_ops uart_ops = {
    .init = uart_init, .shutdown = uart_shutdown,
};

/* 框架调用：统一通过基类 */
struct Device *dev = get_device_by_name("uart0");
dev->ops->init(dev);   /* 多态：实际调 uart_init */
```
封装边界：
- **框架**只见 `struct Device` + `ops`——可换 SPI/I2C/USB 设备。
- **驱动**通过 `container_of` 取回 `uart_dev`，访问自身 priv。
- **用户**只能 `dev->ops->init(dev)`，碰不到 `regs`——寄存器细节完全隐藏。
- `struct uart_regs` 不在头文件——改寄存器布局只重编 uart.c，框架与用户零影响。

</details>
