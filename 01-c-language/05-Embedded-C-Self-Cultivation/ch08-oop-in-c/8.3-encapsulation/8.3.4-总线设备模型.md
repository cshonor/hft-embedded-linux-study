# 8.3.4 总线设备模型

## 本节讲什么

**总线（bus）**是设备与驱动的匹配枢纽：`struct bus_type` 定义 **match**（是否配对）、**probe**（绑定后初始化）、**remove**（解绑）回调。设备挂 `bus_list`，驱动挂 `driver_list`，内核自动扫描配对——这是 Linux **plug-and-play** 的 OOP 核心：**框架代码不变，新驱动只填 ops**。

## 要点

**总线结构（概念）**：

```c
struct bus_type {
    const char *name;
    int (*match)(struct device *dev, struct device_driver *drv);
    int (*probe)(struct device *dev);
    int (*remove)(struct device *dev);
    struct list_head devices;
    struct list_head drivers;
};
```

**platform 总线典型 match**：

```c
/* 按 name 或 OF compatible 匹配 */
static int platform_match(struct device *dev, struct device_driver *drv) {
    struct platform_device *pdev = to_platform_device(dev);
    return strcmp(pdev->name, drv->name) == 0;
}
```

| 总线 | 典型设备 | match 依据 |
|------|----------|--------------|
| **platform** | SoC 内置 UART | 设备名 / DT `compatible` |
| **pci** | 网卡 | Vendor/Device ID |
| **usb** | U 盘 | VID/PID + interface |
| **i2c** | 传感器 | 7-bit 地址 + OF |

**注册时序**：

```
platform_driver_register(drv)  ─┐
platform_device_register(dev) ─┼→ bus 核心 match → probe
                                ┘
driver_unregister / device_unregister → remove
```

- **`struct device_driver`** 含 `probe`/`remove`，与 **8.2.4 ops** 同类：驱动填函数指针，核心调度
- **sysfs**：`/sys/bus/platform/devices/`、`/sys/bus/platform/drivers/` 反映链表状态
- 模块卸载必须 `remove` 干净，否则 dangling `device`

## 常见陷阱

1. **`probe` 中分配的资源在 `remove` 不对应释放 → 泄漏**
   总线模型约定 `probe`/`remove` **配对**：`probe` 申请什么，`remove` 必须释放什么。漏掉一个 `iounmap`、`free_irq`、`cdev_del` 即泄漏。**devm_*** 让大部分资源自动释放，但**非 devm 资源**（如 `register_chrdev_region`、`class_create`）必须手动清理。代码 review 时数 `probe` 中的申请数 vs `remove` 中的释放数对账。

2. **`match` 返回值误用 → 永远不匹配或匹配错误驱动**
   `bus_type.match` 返回 **0 表示不匹配**，非 0 表示匹配——不是返回错误码。新手写成 `return -ENODEV;`（实际是负数，被当作"匹配成功"），导致**所有设备都误绑定**。正确：`return strcmp(...) == 0 ? 1 : 0;` 或直接 `return !strcmp(...);`。

3. **模块卸载时 `driver_unregister` 不等 `remove` 完成 → use-after-free**
   `driver_unregister` 触发已绑定设备的 `remove` 回调，但**异步**——`driver_unregister` 可能在 `remove` 完成前返回。若模块立即卸载（`module_put` 后），`remove` 仍在执行即 use-after-free。框架用 `module_get(THIS_MODULE)` 在 `probe` 时增加引用计数，`remove` 后释放——但**自己注册的 work/timer** 不在框架保护内，必须 `cancel_work_sync`。

## 自测题

**1.（选择）** `platform_match` 在以下哪种情况返回"匹配"？
- A. `strcmp(pdev->name, drv->name) == 0`
- B. `pdev->id == drv->id`
- C. `pdev->bus == drv->bus`
- D. 任意 OF `compatible` 字符串匹配

<details><summary>答案</summary>

**A 和 D**（实际内核支持多策略）。`platform_match` 优先级：
1. **OF match**（Device Tree `compatible`）——现代嵌入式首选
2. **ACPI match**（x86 / 服务器）
3. **id_table** 显式匹配表（传统）
4. **name 字段** `strcmp(pdev->name, drv->name)`
返回 **1 = 匹配**，**0 = 不匹配**。返回负数被当作"匹配"是常见 bug——必须用 `return X ? 1 : 0;`。

</details>

**2.（判断）** `platform_driver_register` 后立即 `platform_device_register`，绑定顺序无关紧要。

<details><summary>答案</summary>

**对**——绑定是**双向触发**。无论先注册 driver 还是先注册 device，框架在每次注册后扫描对端链表尝试 match。`driver_register` 后扫描 bus 上的设备链表，`device_register` 后扫描 driver 链表。两次都会触发 `probe`。坑在**模块加载顺序**：若 driver 模块未加载时 device 已注册，device 处于"unbound"状态；driver 加载后自动 probe——但用户态可能在这间隙访问设备失败。

</details>

**3.（踩坑）** 驱动 `remove` 中忘了 `free_irq`，模块卸载后系统调用 `handler` 时崩溃。但 `handler` 代码已在 `module_exit` 时被释放。为何框架没保护？

<details><summary>答案</summary>

**`free_irq` 必须由驱动自己调**，框架不会代劳——IRQ 注册是设备行为，不是总线模型核心职责。`remove` 漏 `free_irq`：
1. IRQ 仍指向已释放的 `handler` 代码地址。
2. 中断触发时 CPU 跳到无效地址 → oops。
**框架的保护**仅覆盖 `probe`/`remove` 调用本身（通过 `module_get`），不覆盖驱动注册的 IRQ/timer/work。**修复**：用 `devm_request_irq` 替代 `request_irq`——devm 在设备释放时自动 `free_irq`。这是现代驱动推荐做法。

</details>

**4.（应用）** 用 platform 总线模型实现一个虚拟设备驱动：① device 在 DT 中定义；② driver 匹配 `compatible`；③ probe 映射资源、注册 cdev；④ remove 全清理。给出代码骨架。

<details><summary>答案</summary>

```c
/* DT 节点：my_dev: mydev@0 { compatible = "vendor,mydev-v1"; reg = <...>; interrupts = <...>; }; */

static const struct of_device_id my_dt_ids[] = {
    { .compatible = "vendor,mydev-v1" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, my_dt_ids);

static int my_probe(struct platform_device *pdev) {
    struct device *dev = &pdev->dev;
    struct my_chip *chip;
    int ret;

    chip = devm_kzalloc(dev, sizeof(*chip), GFP_KERNEL);
    if (!chip) return -ENOMEM;
    platform_set_drvdata(pdev, chip);

    chip->base = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(chip->base)) return PTR_ERR(chip->base);

    chip->irq = platform_get_irq(pdev, 0);
    if (chip->irq < 0) return chip->irq;
    ret = devm_request_irq(dev, chip->irq, my_irq, 0, dev_name(dev), chip);
    if (ret) return ret;

    cdev_init(&chip->cdev, &my_fops);
    chip->cdev.owner = THIS_MODULE;
    ret = cdev_add(&chip->cdev, chip->devno, 1);
    if (ret) return ret;
    devm_add_action(dev, (void(*)(void*))cdev_del, &chip->cdev);

    return 0;
}

static int my_remove(struct platform_device *pdev) {
    /* devm_* 自动清理；cdev_del 通过 devm_add_action 自动调用 */
    return 0;
}

static struct platform_driver my_drv = {
    .probe  = my_probe,
    .remove = my_remove,
    .driver = {
        .name = "mydev",
        .of_match_table = my_dt_ids,
    },
};
module_platform_driver(my_drv);   /* init/exit 自动生成 */
```
要点：
- `of_match_table` 是 DT 匹配的核心。
- `module_platform_driver` 宏自动展开 `init`/`exit`，省样板代码。
- 几乎所有资源 devm 化，`remove` 为空——现代驱动风格。

</details>
