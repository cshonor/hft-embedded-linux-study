# 6.9.1 强符号和弱符号

## 本节讲什么

链接器规则：**强符号** 唯一定义；**弱符号** 可被强符号 **覆盖** 而不报 duplicate symbol。C 中 **weak attribute** 与 **common block** 行为不同。

## 要点

| 种类 | 典型来源 |
|------|----------|
| **强符号** | 函数定义、已初始化全局 |
| **弱符号** | `__attribute__((weak))` |

```c
/* a.c */
int counter __attribute__((weak)) = 0;
/* b.c — 强符号覆盖 */
int counter = 100;
```

```bash
gcc -c a.c -o a.o && gcc -c b.c -o b.o
gcc a.o b.o -o t && nm t | grep counter
```

- **重复强符号** → 链接错误
- 内核 **`__weak`** 宏广泛用于 arch hook

## 常见陷阱

1. **强弱符号**同名同类型**才能覆盖** → 类型不匹配链接器静默选一个**
   weak `int counter` 与 strong `long counter`（不同类型）共存时，链接器**不会报错**，按"强优先"选 long 的存储，但访问代码按 int 解读——读到的是**截断或异位**的值。GCC 的 `-Wl,--no-undefined` 不查类型，`-flto` 才能跨编译单元类型检查。**约定**：weak/strong 必须在头文件共享同一声明。

2. **静态函数不能 weak → weak 只对全局符号有效**
   `static void f(void) __attribute__((weak));` 看似合法但**无意义**——静态符号不参与链接，无"强弱"概念。`weak` 只对**具有外部链接**的符号生效。误用会导致 weak 静默失效，覆盖不会发生，运行时仍调原版。

3. **动态链接中 weak 行为**与静态不同**
   静态链接：strong 覆盖 weak，确定无疑。**动态链接**：weak 符号在 `.so` 中仍可被可执行文件的 strong 覆盖（默认符号解析规则），但若 `dlopen(RTLD_LOCAL)` 加载的 `.so` 含 strong 定义，**不会**覆盖主程序的 weak——只在自己命名空间内有效。LD_PRELOAD 注入靠的是全局符号插序，与 weak 无直接关系。

## 自测题

**1.（选择）** 下列哪种符号是**强符号**？
- A. `int x __attribute__((weak)) = 0;`
- B. `int x;`（未初始化全局）
- C. `int x = 1;`（已初始化全局）
- D. `extern int x;`

<details><summary>答案</summary>

**C**。已初始化全局是强符号；`__attribute__((weak))` 显式声明弱；未初始化全局 `int x;` 是 **common 符号**（GCC `-fcommon` 默认开，GCC 10+ 改默认 `-fno-common` 后变强）；`extern int x;` 仅声明不是定义。**坑**：common 符号在链接时**允许重复**，行为类似弱但语义不同——不要把 common 当 weak 用。

</details>

**2.（判断）** 同一程序中两个 `void f(void) {}`（无 weak）一定链接报错。

<details><summary>答案</summary>

**对，但有例外**。两个强符号同名同类型，链接器报 `multiple definition of 'f'`。**例外**：GCC 10 之前默认 `-fcommon`，未初始化全局变量是 common 符号（不算强符号），多个 common 会被合并——但**函数**不是 common，仍报错。GCC 10+ 默认 `-fno-common`，未初始化全局也变强，更严格。函数永远是强符号（除非 `weak`），重复定义必报错。

</details>

**3.（踩坑）** 模块 A 头文件声明 `void hook(void) __attribute__((weak));`，A.c 中定义 weak 版 `void hook(void) {}`；模块 B.c 直接 `#include "A.h"` 后定义 `void hook(void) { /* B 版 */ }`。链接时 strong 选中 B 版——但**B.c 中没加 weak 属性，A.h 声明带 weak，是否冲突？**

<details><summary>答案</summary>

**不冲突**。C 标准允许同一符号多次声明，**属性可不同**。GCC 处理规则：**只要有一个声明不带 weak，即为强**。所以 B.c 看到的是 weak 声明，但其定义不写 weak，链接器视 B 的定义为强。这是**惯用法**：头文件统一声明 weak，提供方写 weak 实现，覆盖方写普通实现。
**坑**：如果 B.c 把声明复制为 `void hook(void);`（不带 weak），与头文件 weak 声明"冲突"——GCC 仍接受，但**编译警告** `-Wattributes`。最佳实践：覆盖方`#include` 头文件即可，不重复声明。

</details>

**4.（应用）** 设计一个"板级可选初始化钩子"机制：默认实现是空函数，BSP 可覆盖。给出声明与用法。

<details><summary>答案</summary>

```c
/* board.h */
void board_early_init(void) __attribute__((weak));

/* board_default.c (链接进所有镜像) */
#include "board.h"
void __attribute__((weak)) board_early_init(void) {
    /* 默认空实现，可被 BSP 覆盖 */
}

/* board_rpi.c (特定板级，覆盖) */
#include "board.h"
void board_early_init(void) {       /* 不写 weak = 强 */
    /* Raspberry Pi 特定初始化 */
    mmu_init();
    clock_init();
}

/* main.c */
int main(void) {
    board_early_init();    /* 自动选到强版本 */
    /* ... */
}
```
要点：
- 头文件**声明带 weak**——BSP 不需要重复声明，直接定义即覆盖。
- 默认实现也带 weak（防止 BSP 全覆盖时"重复强符号"）。
- BSP 实现不带 weak（自动成强符号）。
- 链接顺序不影响：链接器全局扫描，strong 总是赢 weak。
- 内核 `__weak` 宏 + arch hook（如 `arch_setup()`）用完全相同的模式。

</details>
