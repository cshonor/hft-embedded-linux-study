# 6.4.3 Linux内核中的container_of宏

## 本节讲什么

**container_of** 实现「从成员指针得到结构体指针」，支撑 `list_for_each_entry`、`device` 嵌套 `platform_device` 等模式。定义在 `include/linux/container_of.h`（或经 `kernel.h` 间接包含）。

## 要点

```c
#include <stddef.h>

#define container_of(ptr, type, member) ({              \
    void *__mptr = (void *)(ptr);                         \
    ((type *)((char *)__mptr - offsetof(type, member))); \
})
```

使用：

```c
struct task t;
struct list_node *n = &t.link;
struct task *tp = container_of(n, struct task, link);
/* tp == &t */
```

```c
/* 内核链表遍历宏（简化） */
#define list_for_each_entry(pos, head, member)              \
    for (pos = list_first_entry(head, typeof(*pos), member); \
         &pos->member != (head);                            \
         pos = list_entry(pos->member.next, typeof(*pos), member))
```

- **`typeof(*pos)`**：pos 指针类型由编译器从变量推断
- **空指针 / 野指针** 传入 UB；使用前需保证 `ptr` 确实来自某 `type` 实例的成员
- U-Boot、部分 DPDK 内部 list 宏同构

## 常见陷阱

1. **ptr 不是该 type 实例的成员指针 → UB**
   拿一个独立的 `struct list_node n`（不属于任何 `task`）调 `container_of(&n, struct task, link)`，得到的指针指向**任意内存**，解引用即踩内存。编译器无法检查——宏只做指针算术。
   ```c
   struct list_node standalone;
   struct task *bad = container_of(&standalone, struct task, link);
   bad->id = 1;  /* 不可预测的崩溃或静默踩内存 */
   ```

2. **跨类型混用 → 偏移错位**
   两个结构体都含 `struct list_node link`，但 `link` 在各自结构体内的偏移不同。把 A 链表节点塞进 B 链表后再用 `container_of(..., struct B, link)` 取宿主，会算出**错误的基地址**。内核里 `list_head` 之所以能通用，靠的是"宿主类型必须一致"的约定，不是语言保证。

3. **`container_of(NULL, ...)` → 解引用 NULL**
   宏内部 `(void *)(ptr)` 不解引用，但回退后的指针被调用方解引用即 NULL+(-offset)。更隐蔽的是 `ptr` 本身为 NULL 时 `offsetof` 仍按编译期常量计算，**运行时直接得到非零野指针**，崩溃延迟到使用点，难以定位。

## 自测题

**1.（选择）** `container_of(ptr, type, member)` 中用 `(char *)` 做减法的关键原因是？
- A. `char *` 是 1 字节指针，可做字节级偏移
- B. `char *` 性能比 `void *` 高
- C. 编译器对 `void *` 算术不安全
- D. 标准要求必须用 `char *`

<details><summary>答案</summary>

**A**。C 标准中 `void *` 算术是 GCC 扩展（按字节），标准不可移植；`char *` 是**保证按 1 字节运算**的唯一类型，所以偏移回退必须转 `char *`。

</details>

**2.（判断）** 以下代码合法：
```c
struct list_node *p = NULL;
struct task *t = container_of(p, struct task, link);
```

<details><summary>答案</summary>

**错**。`offsetof` 是编译期常量，宏运算得到 `(char *)NULL - offset` = 非零野指针。**指针本身**的"运算"在标准上是 UB（空指针算术），且后续解引用必崩。内核代码中 `container_of` 前应先判 `ptr != NULL`。

</details>

**3.（踩坑）** 结构体 A 和 B 都含 `struct list_node node`，但 A 中 `node` 在偏移 16，B 中在偏移 8。某段代码误把 A 的节点指针传给 `container_of(p, struct B, node)`，会发生什么？编译器会报错吗？

<details><summary>答案</summary>

**不会报错**——宏不做类型校验（除非用内核版 `__builtin_types_compatible_p` trick）。运行时得到 `p - 8`，而正确宿主首址应是 `p - 16`，**差 8 字节**。访问"宿主"其他成员时读到的是 A 中**别的字段**，典型的**静默数据错位**——比崩溃更危险，往往跑很久才出问题。预防：宿主类型与链表严格绑定，封装 `list_entry_A` / `list_entry_B` 别名宏。

</details>

**4.（应用）** 写一个不依赖 `typeof` 的简化版 `container_of`，并解释三步运算。

<details><summary>答案</summary>

```c
#include <stddef.h>
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```
- 第一步 `(char *)(ptr)`：抹除原指针类型，转为字节指针。
- 第二步 `- offsetof(type, member)`：回退到宿主首址（字节级）。
- 第三步 `(type *)`：把字节指针重新解释为宿主类型指针。
注意此版**丢失了类型检查**：传入与 `member` 类型不匹配的指针不会报错。内核版用 `typeof` + `__builtin_types_compatible_p` 加了一道静态断言。

</details>
