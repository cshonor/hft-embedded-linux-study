7.1

函数定义

本节讲什么

函数定义 = 签名 + 函数体；产生 .text 段机器指令，外部链接符号全局唯一（static 除外）。函数是 C 工程的基本单元——DPDK API、内核驱动、HFT 策略模块都以函数为接口边界。这一节把"定义"落到 ABI、栈帧、链接三个层面。

要点

int rte_mbuf_refcnt_add(struct rte_mbuf *m, int delta)
{
    m->refcnt += delta;
    return m->refcnt;
}
  • 函数体 {} 是块作用域；局部 auto 变量在栈帧分配
  • static 修饰函数 → 内部链接，仅本 .c 可见（DPDK/内核私有 helper）
  • 函数名在表达式中退化为函数地址（ch13 函数指针）

return 与返回值

类型 规则 ABI 返回位置
整型 ≤ 64 位 return expr; rax
float/double return expr; xmm0
大 struct 隐式拷贝，调用者传隐式首参数 调用者缓冲（ch10）
void return; 或落到末尾 无
指针 return expr; rax

返回值隐式转为声明类型；转换若溢出是 UB。

禁止：返回局部栈指针

char *bad(void) {
    char buf[64] = "hello";
    return buf;   /* 悬垂指针：buf 随栈帧销毁 */
}

栈帧在 ret 时销毁，buf 地址被下一个函数复用。合法的返回指针来源： - malloc 堆内存（调用者 free） - static 缓冲（非线程安全） - 调用者提供的缓冲区（最干净）

返回指针安全的判定标准：看指向的内存，不看变量是不是 static

返回指针是否安全，不看变量带不带 static，看【指针指向那块内存的生命周期】：

  • 指向 static 局部 / 全局 / malloc 堆内存 → return 指针没问题
  • 指向函数栈上局部变量 → 千万不能 return，函数结束栈销毁，野指针 UB

static 局部指针的两种写法（易踩坑区分）

/* 写法 A：安全，可以返回 */
char *foo_a(void) {
    static char arr[64];   /* static 局部数组：整体在数据段，永久存在 */
    return arr;            /* ✅ 生命周期不随函数结束销毁 */
}

/* 写法 B：灾难，不能返回 */
char *foo_b(void) {
    static char *p;        /* static 只修饰指针变量 p 本身！ */
    char stack_buf[32];
    p = stack_buf;         /* p 存的是栈地址 */
    return p;              /* ❌ 函数退出 stack_buf 销毁，p 成野指针 */
}

static char *p 只是指针变量 p 自己活很久，它指向的对象不一定！ p 在数据段、存着一个栈地址——指向的栈内存照样随帧销毁。static 修饰的是变量本身，护不住它指向的目标。

速记表：能不能返回它的地址

变量 存放位置 生命周期 能否返回其地址
普通局部变量 栈 函数调用期间 ❌ 禁止返回地址
static 局部变量 数据段（.data/.bss） 整个程序运行 ✅ 可以返回地址
全局变量 数据段 整个程序运行 ✅ 可以返回地址
malloc 申请 堆 free 之前 ✅ 可以返回地址

static 局部变量：作用域在函数内，生命周期是全局

void test(void) {
    static int a = 10;   /* 不在栈上！ */
    a++;
    printf("%d\n", a);
}

test();   /* 输出 11 */
test();   /* 输出 12 */
test();   /* 输出 13 */
属性 普通局部变量 static 局部变量
存放位置 栈帧（随调用临时开辟） 全局数据段（.data/.bss）
生命周期 函数退出即销毁 程序整个运行期间存活
初始化 每次进入都初始化 只初始化 1 次（首次进入函数时）
作用域 本函数 本函数（别的函数不能直接访问）
值的延续 不保留 保留上次的值

本质：作用域是局部的，生命周期是全局的——数据段里给这个变量留了永久位置，只是名字只在函数内可见。

inline（C99）

static inline uint32_t get_flags(const struct rte_mbuf *m)
{
    return m->ol_flags;
}
  • 建议编译期展开，减少 call/ret 开销
  • 高频小函数放头文件（static inline 才能多处包含不冲突）
  • 过大函数勿 inline：I-cache 膨胀、代码段增大
  • DPDK/内核：static inline 是标配

头文件里能不能直接写函数体？

头文件可以写函数声明（只有签名没有函数体），不能直接写普通函数实现。

/* demo.h */
void func(void);      /* ✅ 声明，没问题 */

void func(void) { }   /* ❌ 普通函数体写进 .h！ */

多个 .c 都 #include "demo.h"，预处理后每个翻译单元都生成一份 func 实体，链接阶段报多重定义（multiple definition）。

头文件放函数体的两种合法写法：

static inline void func(void) { }   /* ① 最常用：内核头文件大量使用 */
inline void func(void) { }          /* ② 少用：C99 纯 inline 不发射外部符号，
                                       取地址/未内联时需在唯一 .c 里再提供
                                       一份外部定义（extern inline 配合） */

简单记：h 文件带函数体，优先 static inline——每个 TU 一份私有副本，永不撞符号。

底层映射

call/ret 栈帧（ch18 详）

调用者                 被调函数
  ┌────────┐
  | call f | → 压返回地址 → ┌────────────┐
  |        |               | prologue:  |
  |        |               |   push rbp |
  |        |               |   sub rsp,N | 局部变量空间
  |        |               | ... 函数体 |
  |        |               | epilogue:  |
  |        |               |   add rsp,N |
  |        | ← ret 弹返回 ← |   pop rbp  |
  └────────┘               |   ret      |
                            └────────────┘

call = push 返回地址; jmp f；ret = pop 返回地址; jmp 返回地址。每层调用占一栈帧，深度过大 → 栈溢出 SIGSEGV（7.5）。

ABI 寄存器传参与返回

x86-64 System V：前 6 个整数/指针参数 → rdi, rsi, rdx, rcx, r8, r9；浮点 → xmm0..xmm7；超出进栈。返回值：整数/指针 → rax；浮点 → xmm0。

int add(int a, int b) { return a + b; }

; x86-64 -O2
add:
    lea     eax, [rdi + rsi]   ; a 在 rdi, b 在 rsi, 返回值 eax
    ret

参数不走内存，直接寄存器算——这是 int 等小标量传值几乎零开销的原因（7.3）。

HFT / DPDK

用法 要点
static inline helper 高频小函数入头文件，避免 call 开销
PMD 私有函数 static 内部链接，不污染全局符号
返回错误码 int 返回值走 rax，零开销
避免热路径返回大 struct 改用输出指针参数

常见误区

误区 事实
"返回局部数组没事" 栈帧销毁即悬垂，UB
"inline 一定更快" 大函数 inline 反伤 I-cache
"函数调用零开销" 有 call/ret + 栈帧建立开销，深递归放大
"static 函数和普通函数一样" static 改链接属性，仅本 TU 可见
"static 局部变量在栈上" 在数据段（.data/.bss），程序全程存活
"static 修饰的指针返回就安全" static 只护指针变量本身，护不住它指向的目标（指向栈照样野）
"头文件里写函数体必须 static inline" 或者纯 inline + 唯一 .c 提供外部定义；但工程上首选 static inline

代码自测

题目 1： 以下函数定义有什么问题？

int max(int a, int b)
{
    if (a > b)
        return a;
    else
        return b;
    printf("never reached");
}
参考答案

printf 永远不会执行——两个分支都有 return，if-else 后的代码是死代码。编译器可能会警告 unreachable code。虽然语法合法，但说明逻辑可能有误——如果 printf 是有意写的，说明 if-else 逻辑写错了。

题目 2： 这个函数安全吗？多次调用返回的指针是同一个地址吗？

int *f(void)
{
    static int x = 100;
    return &x;
}
参考答案

返回本身安全，但共享是坑。

  1. 安全：x 是 static 局部变量，存在 .data 段（初值 100），生命周期覆盖整个程序——&x 在任何时刻解引用都有效，不会悬垂。

  2. 是同一个地址：x 在数据段只有一份实体，无论调用多少次 f()，返回的都是同一个 &x。

  3. 真正的坑在共享：所有调用者拿到的是同一个 x—— - 两次调用想各自持有一份独立结果？不可能，互相覆盖； - 多线程下无任何保护，竞态条件； - 不可重入：信号处理函数/递归里再调 f() 会破坏外层的值。

这就是 static 缓冲的固有代价——inet_ntoa() 的经典坑：两个返回值在同一条 printf 里互相覆盖。安全替代：调用者传入缓冲区（inet_ntop 的设计），或返回 malloc 堆内存由调用者释放。

7.2

函数声明

本节讲什么

声明（原型） vs 定义：声明告知签名，可重复多处；定义分配代码，外部符号全局唯一（ODR）。这一节讲清两者在编译/链接阶段的分工（声明管编译期类型检查、定义管链接期实体）、"头文件 + 实现文件"工程模式的根因，以及签名不一致时为什么定义不会修正错误声明。

要点

声明 定义
位置 .h 或 .c 顶部 某一个 .c
函数体 无 有 { }
链接 extern 隐含 产生符号
可重复 是（多处声明须兼容） 否（ODR，全局唯一） 
/* header.h */
int rte_mbuf_refcnt_add(struct rte_mbuf *m, int delta);

/* mbuf.c */
int rte_mbuf_refcnt_add(struct rte_mbuf *m, int delta) { /* ... */ }
  • 原型作用：编译期校验参数个数与类型
  • 无原型 → 旧式隐式 int 规则（7.2.2 高危）
  • 声明可重复，但所有声明的类型必须兼容（C99 "compatible types"）

头文件 + 实现文件模式

queue.h          ← 公共 API 原型、opaque typedef
  struct queue;  // 前向声明
  typedef struct queue queue_t;
  queue_t *queue_create(void);
  void queue_destroy(queue_t *q);

queue.c          ← 实现 + 私有 static helper
  #include "queue.h"
  struct queue { /* 内部布局 */ };
  static node *grow(queue_t *q) { /* 私有 */ }
  queue_t *queue_create(void) { /* ... */ }

.c 包含自己的 .h → 编译器同时校验"声明与定义一致"（7.2.1）。

全局变量的工程标准写法

声明 vs 定义的通用定义（不限于函数）：

  • 声明：告诉编译器符号名字、类型，不分配内存、不生成机器码——整个程序可写无数次
  • 定义：创建真实实体，分配内存 / 生成函数汇编代码——整个程序只能有 1 处定义（ODR）

全局变量三步走：

/* xxx.h —— 第 1 步：只写 extern 声明，不分配内存 */
extern int g_val;

/* xxx.c —— 第 2 步：唯一的定义，真正分配内存 */
int g_val = 10;

/* 其他所有 .c —— 第 3 步：include 后直接读写 */
#include "xxx.h"
/* 所有 .c 操作的是同一块内存 */

⚠️ extern 不代表只读——它只说明"内存不在当前文件"；想要只读要加 const： extern const int g_val;

❌ 禁止把 int g_val = 10;（定义）直接写进 .h：多文件 include → 多重定义链接报错。

试探性定义：int g_val;（不带初始化）

C 标准里这叫试探性定义（tentative definition）：若翻译单元内始终没出现带初始化的定义，它就转正成"初始化为 0 的定义"。多文件各自写 int g_val; 时：

  • 传统工具链（-fcommon）：合并成 common symbol，静默合并不报错——但哪个文件"赢"不可控
  • GCC 10 起默认 -fno-common：直接 multiple definition 链接报错

行为不可靠，不要使用——全局变量永远写".h extern + 唯一 .c 带初始化定义"的完整形式。

🔑 实测补刀（gcc 13.3，见 7.4）：-fcommon 是编译期选项，写在链接命令里完全无效。 gcc a.o b.o -fcommon 照旧报 multiple definition——因为 .o 里的符号早已定型 （-fno-common 编出来是 B，不会因为链接时加了 -fcommon 就变回 C）。 必须回到 gcc -fcommon -c a.c 才生效。老项目升到 gcc 10+ 突然冒出一堆 multiple definition，就是这个默认值翻转导致的，不是代码变了。

📌 延伸：变量的声明/定义 vs 结构体的声明/定义是两套规则（struct 类型定义不分配内存、 nm 里零符号，放头文件合法；但 struct S obj; 是变量定义，照样炸）。 完整对照表与实测见 7.4「变量的声明/定义 vs 结构体的声明/定义」。

#include 的本质：文本粘贴

#include 只是简单文本粘贴，头文件本身不产生内存、不运行代码：

粘进去的内容 后果
extern int g_val;（声明） 没事，可以无数次
int g_val = 10;（定义） 每个 .c 都生成实体 → 链接报错
static inline 函数体 每个 TU 一份私有副本，不冲突

（#include 机制详解 → ch14）

声明与定义的签名必须一致：定义不会修复错误的声明

职责分工——一句话记住：

声明负责编译期类型检查；定义负责链接期代码实体。两者签名必须一致，定义不会修复错误的声明。

声明 定义
干什么 告诉编译器"有这个函数，长这样" 给出函数体，产生真实机器码
谁用它 编译期：调用点按此处可见的声明做类型检查 链接期：提供符号实体（ODR 全局唯一）
能有几份 无数份（须全部兼容） 恰好 1 份

核心规则：同一个函数，不允许出现签名不一样的声明。所有声明的返回类型、参数类型必须完全匹配，否则是约束违反 → UB。

常见误解是"后面写对了定义，前面写错的声明会被自动修正"——C 语言不这么工作：

  • 定义是真实实现代码；
  • 但每个调用点用的是该位置可见的那份声明做类型检查；
  • 声明签名与定义签名不一致 → 行为未定义，不会自动对齐到定义。

情况一：同一翻译单元内——编译器当场拦下（error，不是警告）

void foo(void);                     /* 错误声明 */
int  foo(int x) { return x + 1; }   /* 真实定义 */
int main(void) { foo(); }

GCC 13 实测（gcc -std=c11 -Wall）：

demo1.c:6:5: error: conflicting types for 'foo'; have 'int(int)'
demo1.c:4:6: note: previous declaration of 'foo' with type 'void(void)'
demo1.c:9:5: error: too few arguments to function 'foo'
demo1.c:6:5: note: declared here

两个 error：第一个是声明/定义冲突（约束违反，标准强制要求诊断）；第二个 too few arguments 的 note 指向定义那一行——因为在同一 TU 里，定义本身就是一份声明，第 9 行的调用点看到的是第 6 行的定义，不是第 4 行的错误声明。

情况二：跨翻译单元——编译器和链接器全都沉默，运行期静默损坏（真正的雷）

/* bad.h        */  void foo(void);        /* 声明：无参、返回 void */
/* main_bad.c   */  #include "bad.h"
                    int main(void){ foo(); }        /* 按声明检查：不传参 */
/* foo_impl.c   */  int foo(int x){ printf("%d", x); return x+1; }  /* 故意不 include bad.h */

实现文件忘了 include 自己的头文件——这是真实工程里最常见的翻车方式。实测结果：

$ gcc -std=c11 -Wall -c main_bad.c   # 零输出
$ gcc -std=c11 -Wall -c foo_impl.c   # 零输出
$ gcc main_bad.o foo_impl.o -o prog  # 链接零报错
$ ./prog
calling foo()...
  inside foo: x = 654333712          # 读的是未初始化的寄存器垃圾
returned
$ ./prog ; ./prog ; ./prog
  inside foo: x = -1870637296
  inside foo: x = -1839180016
  inside foo: x = 1801475856         # 每次都不一样

零警告、零错误、退出码 0——调用点不传参，被调函数却去读 edi 寄存器，读到什么全看上一个函数留下的残留。注意它并不总是"崩溃"，更多时候是静默的数据损坏：某次侥幸读到 0 就"看起来正常"，换个编译选项/换个调用上下文立刻翻脸。这比崩溃更难查。

根因在符号表里一目了然：

$ nm prog | grep " T foo"
000000000000119b T foo          # C 符号只有名字，没有参数/返回值信息

链接器拿到的只是名字 foo，无从比对类型——这就是 C 无法在链接期发现签名不匹配的机制根源。

C++ 对照：同一份代码在 C++ 里是另一回事

把情况一的那段代码丢给 g++，编译通过——因为 void foo(void) 和 int foo(int) 参数不同，在 C++ 里构成一个合法的重载集；随后 foo() 重载决议选中了那个从未定义的版本：

$ g++ -std=c++17 demo1.cpp -o demo1pp

而只改返回值、不改参数时两边都拒绝（返回值不参与重载）：

代码 C（gcc） C++（g++）
int foo(int); + void foo(int); error: conflicting types for 'foo'; have 'void(int)' error: ambiguating new declaration of 'void foo(int)'

C 为什么没有函数重载（overload）

直接结论：C 语言没有函数重载。函数名字就是全部——函数名必须独一无二，不看参数、不看返回值。

C 的符号规则：函数符号只由函数名字决定，参数列表、返回类型完全不参与符号生成：

void func(int a);
int  func(double b);   /* ❌ C：两者符号都叫 func，冲突 */

在 C 眼里：名字一样就是同一个函数，参数不一样也不行；返回值不一样也不行 （void foo(void) 和 int foo(void) 同样冲突）——返回值不区分函数。

C++ 会做名字改编（name mangling）：把参数类型编码进符号名（_Z4funci / _Z4funcd）， 所以允许重载。C 没有 mangling，符号名就是函数名本身。

那两个 .c 分开写呢？（易错例）

/* file1.c */ void calc(int a)    {}
/* file2.c */ int  calc(double a) {}

分开编译各自都能过；链接时两个符号都叫 calc → multiple definition 报错。 C 链接器根本不看参数，只看名字。若在同一翻译单元里写两个声明，编译期就报 conflicting types for 'calc'（类型不兼容，约束违反）——不用等到链接。

② void* + 类型标记（模拟动态多态） void print(void *data, int type) 传 void* 再传类型标记，函数内部分发；qsort 回调、很多库这么干
③ 结构体函数指针（运行时多态） struct ops { void (*read)(void); void (*write)(void); } Linux 内核 file_operations 大量使用；不同设备填不同实现，同一接口不同行为（→ ch13.3 函数指针）

ODR（One Definition Rule）

C 标准要求：每个外部符号在程序里有且仅有一个定义。违反 → 链接报错：

$ gcc a.o b.o -o prog
a.o:(.text+0x0): multiple definition of `foo'; b.o:(.text+0x0): first defined here

static 函数不违反 ODR（每个 TU 是独立符号，不参与外部链接）——所以多个 .c 各有同名 static helper 不冲突。

common symbol：试探性定义的痕迹

$ gcc -fcommon -c a.c && nm a.o
0000000000000000 C g_val          # C = common symbol（试探性定义产物）
$ gcc -c a.c && nm a.o            # GCC 10+ 默认 -fno-common
0000000000000000 B g_val          # 直接进 .bss（若唯一）或链接报错（若多处）

C（大写）= common：链接器允许合并多个同名 common，选一个分配。这是老式"未初始化全局变量不报错"的机制根源，也是"行为不可靠"的来源。

name mangling：C vs C++ 符号实测

$ printf 'void test(int x){}\nvoid test(double x){}\n' > t.cc
$ g++ -c t.cc && nm t.cc
0000000000000000 T _Z4testd    # C++：double 版，类型编进符号名
0000000000000008 T _Z4testi    # C++：int 版，两个不同符号 → 重载合法

$ gcc -c t.c   # 同样两个定义
t.c:2:6: error: conflicting types for 'test'   # C：编译期直接拦

C 的符号表里函数名"裸奔"（test 就是 test）——这就是 extern "C" 存在的原因： C++ 代码要被 C 链接器找到，必须关掉 mangling，副作用是该函数不能重载（符号只能有一个）。

代码自测

题目 1： 以下代码在 C89 和 C99 中有什么区别？

int f();
// ...
f(1, 2, 3);
参考答案

C89 中 int f(); 表示 f 接受未知数量的参数（不检查参数类型和数量），调用 f(1,2,3) 不会报错。C99 中空参数列表已被废弃，建议用 int f(void); 明确表示不接受参数。如果 f 实际定义为 int f(int a)，C89 下调用 f(1,2,3) 是 UB，C99 下仍可能不报错（因为声明没指定参数）。

题目 2： 逐项判定：声明还是定义？链接会不会出错？

// a.h
extern int g_count;          // 行 1
int g_raw;                   // 行 2
static inline int sq(int x) { return x*x; }  // 行 3

// a.c
#include "a.h"
int g_count = 0;             // 行 4

// b.c
#include "a.h"
int g_count = 5;             // 行 5
参考答案
  • 行 1 声明：extern，不分配内存——粘到多少个 TU 都没事。
  • 行 2 试探性定义：不带初始化，不是声明！-fcommon 下两个 TU 的 g_raw 合并为 common symbol（静默合并，不可靠）；GCC 10+ 默认 -fno-common 直接 multiple definition 报错。
  • 行 3 定义（static inline）：每个 TU 一份私有副本，内部链接，不违反 ODR，不冲突。
  • 行 4 定义：g_count 唯一的带初始化定义，分配内存，✅ 正确。
  • 行 5 定义：与行 4 重复——g_count 有了两处外部定义，multiple definition 链接报错 ❌。正确写法是 b.c 只 #include "a.h" 靠 extern 声明访问。

核心口诀：声明随便复制，定义只能一份；唯一例外是 static（内部链接不参与 ODR）。

题目 3： 同一份代码，C 和 C++ 各会怎样？

void test(int x);
void test(double x);
参考答案

C：编译期就报错。 同一翻译单元内两个 test 声明类型不兼容——这是约束违反， GCC/Clang 直接报 error: conflicting types for 'test'，根本活不到链接阶段。 （若拆到两个 .c 各自定义，则各自编译通过、链接期 multiple definition。）

C++：完全合法。 name mangling 把两个版本编成不同符号： _Z4testi（int 版）/ _Z4testd（double 版），重载决议按实参类型在编译期挑选版本。

根源：C 的符号名就是函数名本身，参数/返回值不参与；C++ 把参数类型编码进符号名。 这也是 extern "C" 的意义——C++ 函数要让 C 链接器找到必须关掉 mangling， 代价是该函数不能重载。

题目 4： 三个文件，编译、链接、运行各会发生什么？

/* bad.h      */ void foo(void);
/* main_bad.c */ #include "bad.h"
                 int main(void) { foo(); return 0; }
/* foo_impl.c */ #include <stdio.h>
                 int foo(int x) { printf("x = %d\n", x); return x + 1; }
参考答案

编译：两个 TU 都零警告零错误通过。 main_bad.c 按 void foo(void) 检查 foo()， 完全合规；foo_impl.c 没有 include bad.h，编译器根本不知道还有另一份声明。

链接：零报错。 nm 里两边都只有一个裸符号 foo——C 符号不带参数/返回值信息， 链接器无从比对类型，直接配对成功。

运行：静默错误。 调用点不传参，被调函数却去读第一个整型参数寄存器（x86-64 的 edi），读到的是上一个函数留下的残留值。实测多次运行输出 x = 654333712、 x = -1870637296、x = -1839180016、x = 1801475856——每次都不同，退出码仍是 0。 它不一定崩溃，更多时候是静默数据损坏，比崩溃难查得多。

修复/防御： 1. foo_impl.c 加上 #include "bad.h" → 编译期立即 error: conflicting types for 'foo'; have 'int(int)'，把运行期灾难提前到编译期。这是唯一可靠的手段。 2. -flto -O2 -Werror=lto-type-mismatch 能让链接期优化阶段报出 type of 'foo' does not match original declaration——但默认只是 warning，必须升级成 error。 3. 靠"运行时会崩"来发现是不可靠的：本例就不崩。

7.2

.1 原型

本节讲什么

函数原型（prototype）：返回类型 + 函数名 + 参数类型列表（参数名可选）。原型是 C89 引入的"编译期类型契约"——有它编译器能校验调用，没它就是 K&R 时代的裸奔。这一节同时厘清声明 / 原型 / 定义三者的包含关系：所有原型都是声明，但旧式空括号 int f(); 是声明而非原型。

要点

int parse(const uint8_t *pkt, size_t len, struct quote *out);
void log_err(const char *fmt, ...);   /* 可变参 7.6 */
int f(void);                          /* 无参，f() 不能传参 */
  • 调用前可见原型 → 类型/个数检查
  • 头文件放原型；实现文件 #include 自己的 .h，让编译器校验声明与定义一致
  • extern 可省略：extern int foo(int); ≡ int foo(int);
  • 参数名在原型里可选，但写出来有文档作用（现代风格保留）

声明 / 原型 / 定义：三者的关系

所有函数原型都是函数声明，但不是所有函数声明都是函数原型。

函数声明 函数原型 函数定义
是什么 告知编译器"有这个函数，长这样" 带参数类型列表的声明 带函数体 { } 的实现
参数类型 可有可无 必须逐个写出 必须写出
生成机器码 否 否 是
可重复 是（签名须一致） 是 否（ODR，唯一）
例子 int add(); 或 int add(int,int); int add(int a, int b); int add(int a,int b){ return a+b; } 
int add(int a, int b);        /* ① 函数声明，同时是函数原型（现代 C，推荐） */
int add(int, int);            /* ② 仍是原型——参数名可省略，类型列表在就行 */
int add();                    /* ③ 旧式声明：是声明，但【不是】原型（K&R 遗留，禁止） */
int add(int a, int b) { return a + b; }   /* ④ 定义：有函数体，生成真实代码 */

③ 为什么不是原型：int add(); 只告诉编译器"返回 int"，不说明参数个数、不说明参数类型，编译器对调用不做任何参数检查，传错了直接 UB。这正是 7.2.2 讲的缺省认定，f() ≠ f(void)。

② 参数名可省略但依然完整有效（gcc 13 实测）：

int h(int, int);              /* 省略参数名，照样是原型 */
int h(int a, int b){ return a+b; }
int main(void){ return h(1); }        /* error: too few arguments to function 'h' */

原型是否成立只看参数类型列表，不看参数名——参数名仅供文档/IDE 使用（要点 一节）。

现代 C 的唯一正确姿势

  • 头文件 .h 里放的一律是函数原型，保证所有 .c 拿到统一签名
  • 无参一律写 (void)，绝不留空括号
  • 旧式 K&R 写法（f() 空括号 / 旧式定义）全部废弃

⚠️ C23 起：int f(); 的语义变了

C23（N2432）删除了旧式函数声明——int f(); 从此等价于 int f(void);（和 C++ 一致）。gcc 13 -std=c2x 实测：

int f();                   /* C11：旧式未指定参数 */
int f(int a, int b){...}   /* C11：与上者兼容      */
/* C11 -std=c11  : 编译通过（composite type 合并），调用点按 int(int,int) 检查 */
/* C23 -std=c2x  : error: conflicting types for 'f'; have 'int(int, int)'
                   note: previous declaration of 'f' with type 'int(void)'  */

也就是说同一个源文件，换了标准版本会从"通过"变成"编译错误"——这正是旧式声明必须淘汰的实证：它在 C17 和 C23 下是两种语义。K&R 旧式定义在 C23 下也降级为 -Wold-style-definition 告警。

反直觉：同 TU 内"旧式声明 + 带原型定义"，调用点仍会被检查

gcc 13 实测（-std=c11）：

int f();                            /* 旧式 */
int f(int a, int b){ return a+b; }  /* 定义带原型 */
int main(void){ return f(1,2,3); }  /* error: too many arguments to function 'f' */

注意报错的 note 指向定义那一行（declared here），不是第 1 行的旧式声明——因为同一作用域内旧式声明与后续原型会合并成复合类型（composite type），类型被补齐了。

旧式声明真正致命的场景是跨 TU：调用点只看得到 int f();，定义在别的 .c：

/* f_main.c */ int f();  int main(void){ return f(1,2,3); }   /* 3 个实参 */
/* f_impl.c */ int f(int a, int b){ return a+b; }             /* 2 个形参 */

$ gcc -std=c11 -Wall -Wextra -c f_main.c    # 零输出
$ gcc -std=c11 -Wall -Wextra -c f_impl.c    # 零输出
$ gcc f_main.o f_impl.o -o f_prog           # 链接零报错
$ ./f_prog ; echo $?
0

传 3 个参数给 2 参函数，零警告、链接通过、退出码 0。更极端的：旧式声明下给 int f(int,int) 传 ("hello", 3.14) 同样零警告（实测）；换成原型 int f(int,int); 立刻报 warning: passing argument 1 of 'f' makes integer from pointer without a cast。

原型的价值就在这一刻兑现：把运行期静默错误提前到编译期。 补一个诚实的边界：double → int 是合法隐式转换，原型+-Wall 也不报，要 -Wconversion 才拦 （warning: conversion from 'double' to 'int' changes value ... [-Wfloat-conversion]）。

与定义必须兼容

  • 声明与定义的返回类型、参数类型必须"兼容"（C99 术语）
  • const、指针层级都属于类型一部分，必须一致
  • 不一致 → UB，-Werror=strict-prototypes 拦
/* 声明 */
int f(const char *s);
/* 定义 — 忘了 const，类型不兼容，UB */
int f(char *s) { return 0; }

前向声明

struct queue;                       /* 不完整类型，前向声明 */
struct queue *queue_create(void);   /* 原型只需指针，不需完整布局 */

只用指针的函数原型不需要完整结构体定义——这是 opaque ADT 的基础（7.4）。

参考答案

题目 2： 下列四行，哪些是原型？哪些只是声明？

int add(int a, int b);     // 行 1
int add(int, int);         // 行 2
int add();                 // 行 3
int add(void);             // 行 4
参考答案
  • 行 1 是原型：返回类型 + 每个参数类型都明确。
  • 行 2 是原型：参数名省略不影响——原型只看参数类型列表是否存在。
  • 行 3 只是声明，不是原型：旧式 K&R 写法，参数未指定，编译器不做实参检查。C23 起语义改为 int add(void)。

7.2

.2 函数的缺省认定

本节讲什么

f() vs f(void)：旧式 C 的"缺省认定"与现代规范的分水岭。这一节讲清两写的语义差异、K&R 旧式定义的历史包袱、以及为什么现代工程一律用 (void)。

要点

写法 C 含义 C++ 含义
f(void) 无参数；调用 f(1) 报错 同 C，无参
f() 旧式：参数未指定（K&R），不检查实参 无参（与 f(void) 同）
无原型调用 C89 隐式返回 int，不检查 → C99 起非法 非法 
int f(void);   /* 现代：明确无参 */
int g();       /* 旧式：参数未指定，调用 g(1,2,3) 都不报错（仅告警） */

关键：在 C 里 f() 不等于 f(void)——f() 是"不检查参数"，f(void) 是"不要参数"。C++ 里两者等价。

⚠️ 但这条只对到 C17 为止。 C23（N2432）删除了旧式函数声明， f() 在 C23 起等价于 f(void)（与 C++ 一致）。gcc 13 -std=c2x 实测：

c int f(); int f(void) { return 0; } /* C17/C23 都 OK */ int main(void) { return f(1); } /* C23: error: too many arguments to function 'f' */

c int f(); int f(int a, int b) { return a+b; } /* C11 通过（composite type 合并）； C23: error: conflicting types for 'f' */

同一个文件换标准就可能从"通过"变"编译错误"——跨标准移植时的隐形地雷（→ 7.2.1）。

旧式 K&R 定义（了解即可）

/* K&R 风格：参数名列表 + 类型声明分开 */
int f(a, b)
    int a;
    float b;
{
    return a + (int)b;
}

读内核老代码可能遇到；新代码一律用 ANSI 原型：

int f(int a, float b) { return a + (int)b; }

无原型调用的灾难

/* 忘了 #include <stdlib.h>，调用 malloc */
char *p = malloc(64);   /* 隐式假定返回 int，截断 64 位指针！ */

C89：未声明函数 → 隐式假定返回 int。malloc 实际返回 void*（64 位），被当 int 截断 → 32 位平台上指针高位丢失 → 崩。C99 起非法，但很多编译器默认仍只告警。

底层映射

默认参数提升

无原型（或可变参 ...）调用时，实参做默认参数提升：

实参类型 提升后
char / signed char / short int
unsigned char / unsigned short int 或 unsigned int
float double

有原型时不做默认提升——按形参类型精确转换。这就是原型更安全的原因之一：f(float) 收到 3.14f 仍是 float，无精度损失。

有原型 → 编译器知道精确类型 → SSE 寄存器传 float（xmm0）；无原型 → 提升 double → 走 xmm0 但按 8 字节读。va_arg(ap, float) 在可变参里错的——必须 va_arg(ap, double)（7.6.2）。

7.3

.1 值拷贝无例外（传参必懂）

配套 7.3 函数的参数 · 入门对照 K&R 1.8
一句话：C 没有引用传递；所有参数一律值拷贝。传指针 = 拷贝地址数字。

核心结论

有人说「所有参数都是指针地址」——不准确。更精确：

说法 对不对
全部是值拷贝 ✅
传指针时拷贝的是地址值 ✅
普通 int / 结构体 / 数组「都是指针」 ❌ int、struct 按值拷贝数据本身；数组形参退化成指针

C 不存在引用传递、地址传递（作为独立机制）。
传指针时：拷贝的是指针里存的地址值，不是拷贝指针指向的那块对象。

1. 普通 int / char：拷贝数据本身

void f(int x) {
    x = 100;   /* 只改副本 */
}

int main(void) {
    int a = 10;
    f(a);      /* a 仍是 10 */
}

把 a 里的 07 复制给栈上形参 x；x 与 a 互相独立。

2. 指针参数：仍是值拷贝（拷贝地址数字）

void f(int *p) {
    *p = 100;   /* 用副本里的地址，改外部 a */
}

int main(void) {
    int a = 10;
    f(&a);      /* 把 &a 这个地址数字拷给 p */
}

流程：

  1. &a → 地址（如 0x4000）
  2. 该数字拷贝给形参 p（栈上新指针副本）
  3. *p = 100 → 解引用，改 main 里 a 的内存

拷贝的是地址，不是 a 的数据。
若只改指针本身：

void f(int *p) {
    p = NULL;   /* 只改函数内副本 p；外部指针不变 */
}

3. 结构体：整块字节值拷贝

struct S { int arr[1000]; };

void f(struct S s) { /* ... */ }

int main(void) {
    struct S obj;
    f(obj);   /* 整份 obj 拷进形参 —— 很贵 */
}

HFT / 嵌入式：传 struct S *s（或 const struct S *），只拷 8 字节地址（AArch64/x86-64）。

4. 数组形参：退化成指针

void f(int arr[]);   /* 等价于 void f(int *arr); */

不会把全部元素拷进函数；拷贝的是首元素地址。
这是函数参数特有的退化，不是处处「数组=指针」。

arr[0] = xxx / *(arr+0) 可改外部数组元素；arr = NULL 只改副本。

统一表

参数类型 拷贝的是什么 改副本本身影响外面？ 想改外部原数据
int x int 数值 ❌ 传 &x，int *p，*p = …
int *p 地址数字 ❌（p=NULL 无效） *p = …
struct S s 整结构体字节 ❌ 传 struct S *s
int arr[] 首地址 ❌（arr=… 无效） arr[i]=…

坑：想改外部「指针变量本身」

外面 int *ptr;，希望函数里让 ptr = NULL——一级指针形参做不到。

void f(int **pp) {
    *pp = NULL;   /* 改的是外部 ptr 变量 */
}

int main(void) {
    int *ptr;
    f(&ptr);      /* 传指针变量自己的地址 */
}

HFT / 嵌入式意义

传指针只复制地址宽度（常见 8 字节），避免拷巨大缓冲区 / 结构体 → 省内存带宽与 CPU 拷贝。底层 API 大量指针入参，根因在此。

思考题

void change(int *p)  { p = NULL; }
void change2(int *p) { *p = 999; }

int main(void) {
    int a = 10;
    int *ptr = &a;
    change(ptr);
    change2(ptr);
}
调用后 a 等于？ 原因
change(ptr) 仍是 10 只把副本 p 置 NULL，未碰 a
change2(ptr) 999 *p 解引用改了 a

（ptr 本身在两次调用后仍指向 a，因为一级指针形参改不了外部 ptr。）

7.4

ADT 和黑盒

本节讲什么

用函数接口隐藏实现细节——抽象数据类型（ADT）、黑盒。调用者只依赖 .h 里的原型与文档，内部数据结构、算法藏在 .c。

阅读顺序：

  1. 地基：C 是单文件编译模型，编译器看不到别的 .c，封装不是编译器全局统筹出来的
  2. 两个手段：不透明类型（靠编译器拦）+ static（靠链接器拦），以及"头文件本身不隐藏任何东西"这个易搞反的点
  3. 最小完整例子：list.h / list.c / main.c 三文件跑通，以及不完整类型到底禁止什么（实测五条报错）
  4. ⭐ 变量 vs 结构体的声明/定义：为什么 struct Foo {...}; 放头文件合法、struct Foo obj; 就炸；nm 实测证明"图纸零符号"，以及试探性定义的隐藏开关 -fcommon
  5. ADT 的回报：换实现（固定数组 → 动态数组）而 main.o 一个字节都不用重编
  6. ADT 的代价：⚠️ 跨 TU 无法内联，实测 1.19 ns vs 0.20 ns（5.9×），-flto 能补回大半——"opaque 零开销"是错的，这句话在 HFT 热路径上会让你付真金白银
  7. OOP 对照表：哪些行是强制的、哪些只是约定（构造/析构尤其脆弱）

这是 DPDK/HFT 分层架构与 ch17 经典 ADT 的函数观。

前提：C 是单文件编译模型

这是理解 C 封装机制的地基——封装不是编译器全局统筹出来的。

  • 每一个 .c 是一个独立的编译单元（translation unit），单独编译成 .o
  • 编译 a.c 的时候，编译器看不到 b.c 里的任何代码——它只看当前 .c + #include 展开后的头文件
  • 所有 .o 的合并、符号查重、同名函数冲突处理，是链接器 ld 的活，不是编译器
阶段 谁 能看到 负责
编译 编译器（cc1） 仅当前 TU（本 .c + 展开的 .h） 语法、类型检查、生成 .o
链接 链接器（ld） 所有 .o / .a / .so 符号解析、重名检测、地址重定位

编译器不知道整个项目的全貌——这是 C 非常核心的特征。gcc 13 实测：

=== 两个 TU 定义同名非 static 函数 dupfn ===
$ gcc -c d1.c   → exit 0   （编译器毫无意见）
$ gcc -c d2.c   → exit 0   （编译器毫无意见）
$ gcc d1.o d2.o -o prog
/usr/bin/ld: d2.o: in function `dupfn':
d2.c:(.text+0x0): multiple definition of `dupfn'; d1.o: first defined here

重名是链接器报的，不是编译器。 这也解释了为什么原型如此重要：另一个 TU 里的函数，编译器只凭 .h 里的原型做类型检查，完全信任它。

/* dmain.c：只靠原型就敢调用另一个 TU 的函数 */
int dupfn(void);            /* 原型 */
printf("%d\n", dupfn());    /* 编译通过、运行输出 1 —— 编译器从头到尾没见过 d1.c */

要点

C 实现 ADT 的两个手段（没有 class / private）

C 没有 class、private 关键字，信息隐藏只靠两招：

手段 做法 隐藏了什么 谁拦住你
A. 不透明类型（opaque / 不完整类型） 完整 struct 定义不写进 .h，只前置声明 + 给指针 数据布局、成员名、大小 编译器（编译期）
B. static 修饰函数/全局变量 .c 内部的辅助函数、全局变量加 static 内部实现、私有状态 链接器（链接期）

两招分工明确：A 靠编译器，B 靠链接器——正好对应上面那张分工表。

黑盒原则

  • 调用者只依赖 .h 原型与 documented 行为
  • 内部数据结构、算法藏在 .c（static 函数/变量）
  • 好处：替换实现、单元测试、减少耦合、缩短编译时间

最小完整例子：三个文件跑一遍（gcc 13.3 实测）

ADT 落地就是三个文件：.h 只给接口、.c 藏实现、main.c 只调函数。下面这份代码是真编译真跑过的。

/* list.h —— 对外，ADT 的接口 */
#ifndef LIST_H
#define LIST_H

/* 不完全类型：只说"有个 struct List"，不写里面的成员 */
typedef struct List List;

List *list_create(void);
void  list_destroy(List *l);
int   list_append(List *l, int val);   /* 返回 0 成功，-1 满 */
int   list_get_size(List *l);
int   list_get_at(List *l, int idx);   /* 返回 0 成功，-1 越界 */
#endif

/* list.c —— ADT 的真实实现，黑盒内部 */
#include "list.h"
#include <stdlib.h>

struct List {                 /* 真正定义只存在 .c，外部看不见 */
    int size;
    int buffer[128];
};

static int list_full(const List *l)   /* static：内部辅助，链接器不导出 */
{
    return l->size >= (int)(sizeof(l->buffer) / sizeof(l->buffer[0]));
}

List *list_create(void)
{
    List *obj = malloc(sizeof(List)); /* 只有这里知道 List 多大 */
    if (obj) obj->size = 0;
    return obj;
}
void list_destroy(List *l) { free(l); }

int list_append(List *l, int val)
{
    if (!l || list_full(l)) return -1;
    l->buffer[l->size++] = val;
    return 0;
}
int list_get_size(List *l) { return l ? l->size : -1; }
int list_get_at(List *l, int idx)
{
    if (!l || idx < 0 || idx >= l->size) return -1;
    return l->buffer[idx];
}

/* main.c —— 使用方：永远只拿 List*，只调函数 */
#include <stdio.h>
#include "list.h"

int main(void)
{
    List *mylist = list_create();
    for (int i = 0; i < 5; i++) list_append(mylist, 100 + i);
    printf("size = %d\n", list_get_size(mylist));
    printf("get_at(99) = %d  (越界被 ADT 拦下)\n", list_get_at(mylist, 99));
    list_destroy(mylist);
    return 0;
}

实测输出：

$ gcc -O2 -Wall -Wextra -c list.c && gcc -O2 -Wall -Wextra -c main.c && gcc list.o main.o -o prog && ./prog
size = 5
[0] = 100   [1] = 101   [2] = 102   [3] = 103   [4] = 104
get_at(99) = -1  (越界返回 -1)
再追加 123 个成功，第 128 个被拒（容量上限）
final size = 128

注意最后两行：越界和写满都不是崩溃，是 ADT 返回错误码。不变量（size 永远等于真实元素数、buffer 永不越界）由 list.c 独家维护——调用方没有能力破坏它，因为它连字段名都看不到。

⚠️ 封装只是把"破坏的可能"收拢到一处，不等于自动正确。 如果 list_append 照最常见的写法写成 l->buffer[l->size++] = val;（不检查 size 上界），那么第 129 个元素就会写穿 buffer、踏进相邻内存——黑盒只保证"只有 .c 能犯错"，不保证 .c 不犯错。不变量守不守得住，取决于实现方自己。

⭐ 变量的声明/定义 vs 结构体的声明/定义（最易混淆的一组）

上面 list.h 里那行 typedef struct List List; 为什么能堂而皇之地待在头文件里、被无数 .c include 却不报重复定义？因为「结构体」和「变量」是两套完全不同的规则，混在一起就会得出"头文件里不能放定义"这种以偏概全的结论。

一句话区分：

变量定义 = 造出一个实体（要内存、要符号）→ 全项目只能一处 struct 定义 = 画一张图纸（零内存、零符号）→ 复制一万份无所谓

一、全局变量：定义只能有一处，声明可以多处

/* foo.h */
extern int g_val;   /* 声明：只告诉编译器"有这东西"，不分配内存 */
/* foo.c */
int g_val = 100;    /* 定义：分配内存、产生符号，仅此一处 */

实测（gcc 13.3）：两个 .c 都 include 这个头，各自 g_val += 1 / += 2——

$ gcc -Wall -Wextra g_def.c v_ok_a.c v_ok_b.c v_ok_main.c -o prog && ./prog
g_val = 103        ← 三个 TU 操作的是同一个实体，exit=0

反例：把定义写进头文件 int g_val = 100;

$ gcc -Wall -Wextra -c v_a.c    → exit 0   ← 编译器毫无意见
$ gcc -Wall -Wextra -c v_b.c    → exit 0   ← 编译器毫无意见
$ gcc -Wall -Wextra -c v_main.c → exit 0   ← 编译器毫无意见
$ gcc v_a.o v_b.o v_main.o -o prog
/usr/bin/ld: multiple definition of `g_val'; v_a.o: first defined here

注意这个节奏：编译期三个文件全部 exit 0，是链接器报的。又一次印证「符号/重名归链接器」——编译器从头到尾不知道别人也定义了一份。

⚠️ 隐藏开关：试探性定义与 -fcommon

上面是 int g_val = 100;（带初始化，强定义）。如果写成 int g_val;（不带 extern、不带初始化），性质就变了——这是 试探性定义，行为取决于一个编译选项：

编译选项 nm 里的符号 多 TU 链接 备注
-fno-common（gcc 10+ 默认） B g_val（bss，强定义） ❌ multiple definition 现代默认
-fcommon（gcc 9 及更早默认） C g_val（common symbol） ✅ 静默合并成一份，通过 历史行为

实测同一份代码，只差一个编译选项：

$ gcc -fno-common -c tent_a.c && nm tent_a.o | grep g_val
0000000000000000 B g_val                      ← B：进了 .bss
$ gcc tent_a.o tent_b.o tent_main.o -o p
/usr/bin/ld: multiple definition of `g_val'; tent_a.o: first defined here

$ gcc -fcommon -c tent_a.c && nm tent_a.o | grep g_val
0000000000000004 C g_val                      ← C：common symbol
$ gcc -fcommon tent_a_c.o tent_b_c.o tent_main_c.o -o p2 && ./p2
g_val = 103                                   ← exit 0，居然过了

🔑 -fcommon 是编译期选项，不是链接期选项。 实测踩过：在 gcc a.o b.o -fcommon 这条链接命令里加它完全无效（.o 里符号早已定型，B 不会变回 C），必须回到 gcc -fcommon -c a.c。这也是为什么老项目升级编译器到 gcc 10+ 时会突然冒出一堆 multiple definition——不是代码变了，是默认值变了。

二、struct 类型定义不是变量定义

struct 定义只描述"这个类型长什么样、成员有哪些、占多少字节"，不分配内存、不产生符号、不占存储。它是一张图纸。

最硬的证据在 nm 里——实测 t_a.c（里面完整定义了 struct Foo {int a; int b;} 并用它建了对象）：

$ nm t_a.o
                 U printf
0000000000000000 T ta
$ nm t_a.o | grep -ci foo
0                          ← 零个符号！struct 定义连个影子都没留下

对照同一个实验里 v_a.o（头文件里写了 int g_val = 100;）：

$ nm v_a.o | grep g_val
0000000000000000 D g_val   ← D：稳稳占着 .data 的 4 个字节

情况 A：头文件写完整 struct 定义 → 合法

/* foo.h */
struct Foo { int a; int b; };

三个 TU 各 include 一次，实测编译链接运行全过，每个 TU 拿到同一张图纸、sizeof 都是 8。因为类型信息不创建任何变量、不占任何内存，#include 把它文本粘贴一万次也不会冲突。

情况 B：只前置声明 → 不完整类型

/* foo.h */
struct Foo;         /* 只有名字，没有布局 —— 见下一节的完整约束清单 */

情况 C：⚠️ 大坑 —— 紧跟在 } 后面的名字是变量，不是类型

/* foo.h —— 这两行看着像一家人，性质完全不同 */
struct Foo { int a; };   /* ① 类型定义（图纸）      → 重复 include 合法 */
struct Foo obj;          /* ② 定义一个全局变量 obj  → 重复 include 报错 */

实测：

$ gcc -c ov_a.c ov_b.c ov_main.c        # 三个都 exit 0
$ gcc ov_a.o ov_b.o ov_main.o -o p
/usr/bin/ld: multiple definition of `obj'; ov_a.o: first defined here

而且它完全吃试探性定义那一套规则（因为 obj 本来就是个变量，与 struct 无关）：

$ gcc -fcommon -c ov_a.c && nm ov_a_c.o | grep obj
0000000000000004 C obj          ← C：合并成功
$ gcc -fcommon ov_a_c.o ov_b_c.o ov_main_c.o -o p2 && ./p2
obj.a = 103                     ← exit 0，也过了

🔑 这个坑的本质：struct Foo obj; 里的 struct Foo 是类型说明符，obj 才是被定义的实体。判断标准很简单——看它会不会占内存：会占的就是变量定义，不占的就是类型定义。

三、极简对照表

代码 是什么 放在 .h 被多文件 include 会怎样
extern int g; 变量声明 ✅ 安全，到处可 include
int g = 10; 全局变量定义 ❌ multiple definition（编译期 exit 0，链接期才报）
int g; 试探性定义 ⚠️ gcc 10+ 默认 ❌ 报错；-fcommon 下 ✅ 静默合并
struct S { int x; }; 结构体类型定义 ✅ 安全，只是图纸，nm 里零符号
struct S; 结构体前置声明 ✅ 安全，不完整类型（ADT 黑盒用）
struct S obj; 定义全局结构体变量 ❌ 同 int g; 完全一致的一套规则

注意第 3、6 行：它们的行为一模一样——因为 struct S obj; 和 int g; 骨子里是同一件事（定义一个变量），struct 只是类型说明符。规则只按"是不是变量"分，不按"类型是不是结构体"分。

四、回到 ADT 场景

/* list.h */
typedef struct List List;   /* 只有名字，没有图纸 → 不完整类型 */

/* list.c */
struct List { int size; int buf[128]; };   /* 完整图纸，仅在 .c 内部 */

.h 不给图纸，外部只能拿指针、不知道布局，黑盒成立。注意这里两种合法手段的区别：

头文件里的写法 合法？ 封装？ 用在
struct List { ... }; 完整定义 ✅ 合法 ❌ 封装失效 内部模块、热路径（换内联，见下节）
struct List; 前置声明 ✅ 合法 ✅ 黑盒成立 对外接口、发布 .so

五、面试高频坑

问：头文件里可以放 struct 完整定义吗？

答：可以，因为这是类型定义，不是变量定义——不分配内存、不产生符号，不触发重复定义。但要做 ADT 封装就不能放，放了黑盒当场失效（上一节实测：-Wall -Wextra 全开也零警告放行 b->y = -1）。

常见追问与正解：

追问 正解
那为什么还是建议放 .c？ 不是怕重复定义，是怕 ABI 冻结 + 封装失效（改成员 = 所有 include 它的 .c 全重编）
头文件里能放全局变量吗？ 能放 extern 声明，不能放定义；定义放某一个 .c
static int g; 放头文件行不行？ ❌ 每个 include 的 TU 各得一份独立副本，不冲突但语义几乎一定错（以为是共享，实则各改各的）

六、⚠️ 图纸能复制一万份，但没人检查两份图纸是否一样

上面说"图纸复制一万份也没关系"——这句话有个重要前提被省掉了：复制出去的每一份必须一致。如果每个 .c 各自定义一份同名但不同布局的 struct Foo，编译器和链接器都不会管：

/* conf_a.c */  struct Foo { int a; int b; };   /* 8 字节，两个 int */
/* conf_b.c */  struct Foo { double d; };       /* 8 字节，一个 double */
/* 两个 TU 通过 struct Foo* 传递同一个对象 */

实测（-O2 -Wall -Wextra）：

a.c   : sizeof(struct Foo) = 8
a.c   : 写入 a=3 b=4
b.c   : sizeof(struct Foo) = 8
b.c   : 读出来 p->d = 8.487983e-314      ← 把 {3,4} 的位模式当 double 解释
编译+链接 exit=0，运行 exit=0，全程零警告

这是比 multiple definition 危险得多的故障：后者链接期就拦住了，前者一路绿灯跑到运行期，输出一个看似合理的垃圾数字（8.49e-314），exit 0。

能不能提前抓到？实测三种手段：

手段 能否抓到 实测结果
-Wall -Wextra ❌ 零警告
-flto（链接期优化） ⚠️ 基本不能 只给了一条误导性的 -Wuninitialized，exit 0（没报 type mismatch）
ASan ⚠️ 看运气 两份图纸同样大小（8 vs 8）时抓不到；只有大小不同导致越界访问时才报 heap-buffer-overflow

ASan 能抓到的那种情况实测（b2.c 定义成 char name[64]，对象实际只有 8 字节）：

==459==ERROR: AddressSanitizer: heap-buffer-overflow
READ of size 1 at 0x50200000004f
    #0 foo_show conf_b2.c:16
0x50200000004f is located 55 bytes after 8-byte region

🔑 这条规律的工程含义：C 把"两份图纸是否一致"这件事完全交给人。唯一的可靠防御是让图纸只有一份——放进共享的 .h（大家一起 include），或者做成 opaque（谁也不给看）。这正好是 ADT 的第三个理由：除了封装和 ABI，它还能消除"同名不同布局"这一类根本没法静态检查的 bug。

不完整类型到底禁止什么（实测五条报错）

typedef struct List List; 之后，调用方手里只有一个"名字"。实测把能想到的越界动作全试一遍：

List g_obj;                        /* ① 全局对象 */
int main(void) {
    List obj;                      /* ② 局部对象 */
    size_t n = sizeof(List);       /* ③ sizeof */
    List *q = malloc(sizeof(List));/* ④ 用 sizeof 去分配 */
    List *r = malloc(sizeof(*r));  /* ⑤ 换个写法也没用 */
}

gcc 13.3 逐条报错（全部是 error，不是 warning）：

error: storage size of 'obj' isn't known                              ← ②
error: storage size of 'g_obj' isn't known                            ← ①
error: invalid application of 'sizeof' to incomplete type 'List'      ← ③④⑤
error: 'g_obj' has an incomplete type 'List'                          ← ① 使用时

规律一句话：不完整类型 = 只有地址、没有尺寸。

操作 能不能 原因
List *p;（定义指针） ✅ 指针大小与所指类型无关，一律 8 字节
函数参数/返回值用 List * ✅ 同上
p->member ❌ 不知道成员名与偏移
sizeof(List)、sizeof(*p) ❌ 不知道大小
List obj;（栈/全局对象） ❌ 无法分配空间
malloc(sizeof(List)) ❌ 同上，所以 create() 必须住在 .c 里

🔑 最后一行是设计上的必然：分配内存的函数必须在能看见完整定义的地方，否则没人算得出该 malloc 多少字节。这就是为什么 ADT 一定有 xxx_create() / xxx_destroy() —— 不是风格偏好，是不完整类型的物理约束。

换实现不动调用方（ADT 最大价值的硬证据）

把 list.c 换成 list_dyn.c：固定数组 int buffer[128] → 堆上动态数组 int *buffer，满了 realloc 翻倍。list.h 一个字没改，main.c 一个字没改，main.o 一个字节都没重编，只是换了个 .o 去链接：

$ gcc -O2 -c list_dyn.c -o list_dyn.o
$ gcc list_dyn.o main.o -o prog_dyn     # main.o 复用的就是上面那份
$ ./prog_dyn
size = 5
[0] = 100   [1] = 101   [2] = 102   [3] = 103   [4] = 104
get_at(99) = -1  (越界返回 -1)
再追加 195 个成功，第 -1 个被拒（容量上限）
final size = 200          ← 容量上限从 128 变成"没有上限"

调用方代码零改动，行为从「最多装 128 个」变成「按需增长」。这就是 ADT 的回报：

  • 编译期：调用方只依赖 5 个函数原型，结构体怎么变都不触发重编
  • 链接期：结构体布局不进符号表，换 .o 即可（动态库场景连链接都不用，换 .so）
  • 运行期：不变量的守护责任 100% 在 .c，调用方破坏不了

反过来说，如果 struct List 写在 .h 里，这次改动会让每一个 include 它的 .c 全部重编，且已发布的 .so 二进制 ABI 直接断裂。

opaque pointer 模式

/* queue.h — 公共接口，只暴露不完整类型 */
struct queue;                       /* 前向声明，布局不暴露 */
typedef struct queue queue_t;

queue_t *queue_create(void);
void     queue_destroy(queue_t *q);
int      queue_push(queue_t *q, void *item);
void    *queue_pop(queue_t *q);

/* queue.c — 内部布局，调用者看不到 */
#include "queue.h"
#include <stdlib.h>

struct queue {
    node *head;
    node *tail;
    size_t size;
};

queue_t *queue_create(void) {
    queue_t *q = calloc(1, sizeof(*q));
    return q;
}
void queue_destroy(queue_t *q) { /* free 所有 node + q */ }
/* ... */

调用者只能拿 queue_t *，不能 q->head（编译期拦，因为 struct queue 不完整）。这是 C 的"封装"——等价于 C++ 的 PIMPL 模式。

实测（gcc 13）：调用者试图伸手进 opaque 结构体——

adt_caller_cheat.c:10:6: error: invalid use of incomplete typedef 'Foo'
   10 |     f->x = 42;
      |      ^~

编译期就死，连 .o 都生成不出来。这就是手段 A 的强制力：不完整类型不允许解引用、不允许 sizeof。

手段 B：static 把符号锁在本编译单元

/* foo.c */
static void internal_reset(Foo *p)   /* 只本 .o 内部可见 */
{
    p->x = 0;
    p->y = 0;
}

static 把符号变成内部链接——链接器根本不导出它，别的 .c 就算自己写个声明也调不到：

/* adt_static_link.c：自己声明一个同名的，想拿来用 */
void internal_reset(void *p);
internal_reset(NULL);
/* 结果：/usr/bin/ld: undefined reference to `internal_reset' */

nm 里的证据（同一份 adt_opaque.o）：

0000000000000000 t internal_reset     ← 小写 t：内部链接，仅本 .o
0000000000000024 T foo_create         ← 大写 T：外部链接，调用者可见
0000000000000050 T foo_destroy
000000000000006f T foo_set_x
000000000000008a T foo_get_x

static 的另一个副作用是避免符号污染：另一个 TU 里完全可以再有一个 static 的同名函数，互不干扰。实测 d1.o 的 T dupfn 与 d3.o 的 t dupfn 一起链接零冲突，main 调到的是全局那个（输出 1）。

头文件 .h 本身不隐藏任何东西

这是最容易搞反的一点。头文件只是文本拷贝粘贴（ch14），它粘进去的是：

  • 函数原型
  • typedef（含 opaque 的 typedef struct Foo Foo;）
  • 宏、extern 声明

它不隐藏任何实现代码，也不具备任何"保护"能力。 真正的隐藏靠前面那两件事：

  1. 结构体完整定义不放 .h
  2. 内部辅助函数用 static 锁在 .c

头文件的作用是统一对外暴露函数原型接口，让所有 .c 拿到一致声明、做编译期类型检查——它负责一致性，不负责隐藏。

前向声明为什么够用

函数原型里只出现 queue_t *（指针），指针大小与所指类型布局无关（都是 8 字节）。所以 .h 不需要完整 struct queue 定义，编译就能过；完整定义只在 .c 里，用于 sizeof、成员访问。

底层映射

符号可见性

$ nm queue.o
0000000000000000 T queue_create       # 全局：调用者可链接
0000000000000040 T queue_destroy
0000000000000080 T queue_push
00000000000000c0 T queue_pop
0000000000000100 t grow                # static 私有，不外泄
0000000000000140 t shrink              # static 私有

T 大写 = 外部链接，调用者链接器可见；t 小写 = 内部链接，仅本 .o。struct queue 的布局完全不在符号表里——调用者根本拿不到成员名。

⚠️ 踩坑：struct 完整定义写进 .h，黑盒当场失效

如果把 struct 的全部成员写进头文件，那么所有 include 这个头的 .c 全都看得见结构体全部字段：

/* exposed_bad.h —— 反例 */
typedef struct Bar Bar;
struct Bar { int x; int y; };     /* 布局公开了 */

/* 任意调用者 —— 全部编译通过、链接通过、运行通过 */
Bar *b = bar_create();
b->x = 42;        /* 绕过所有 setter，直接改内部状态 */
b->y = -1;        /* 不变量（invariant）形同虚设 */
printf("%zu", sizeof(Bar));   /* 调用方开始依赖大小 */

实测（gcc 13.3，-Wall -Wextra 全开）：

$ gcc -O2 -Wall -Wextra exposed.c exposed_main.c -o exposed_prog && ./exposed_prog
b->x=42 b->y=-1  sizeof(Bar)=8
exit=0                    ← 零警告零错误，约定被公然违反

编译器连一个警告都不给。 头文件里就算写满「y 必须 >= 0」的注释，也纯粹是给人看的——没有任何机制执行它。

❌ 这就不是 ADT。把完整 struct 写进 .h，你得到的是一个普通结构体 + 一组顺手提供的函数，黑盒根本不存在。判定标准很简单：调用方能不能 p->member？能，就不是 ADT。

后果是双重的：

  1. 封装被打破：外部代码可以随便修改内部成员，任何不变量（比如"y 必须 ≥ 0"、"size 必须等于链表长度"）都无法保证
  2. ABI 被冻住：调用方开始 sizeof、开始直接算偏移，此后改成员 = 破坏二进制兼容（见下）

对比 opaque 版本：同一行 f->x = 42 直接 error: invalid use of incomplete typedef。隐藏的强制力来自不完整类型，不来自头文件本身。

ABI 稳定性

opaque pointer 还带来 ABI 稳定：改 struct queue 内部布局（加成员、改顺序）不破坏调用者的二进制兼容——因为调用者从不 sizeof(struct queue)、从不访问成员。这是库（DPDK、libc）能升级而不重编用户代码的关键。

对比：若 .h 暴露完整 struct，改成员就改了 sizeof 和偏移，所有包含它的 .c 都要重编，二进制 ABI 也变。

⚠️ ADT 不是零成本：跨 TU 拿不到内联（HFT 必看）

很多资料（包括本节早先的版本）说"opaque pointer 零运行时开销"——这句话只对一半，必须修正。

  • 指针本身确实零开销：List* 和暴露布局的 struct List* 是同一个 8 字节地址
  • 但每次访问都要过函数，而函数在别的编译单元里 → 编译器看不见函数体 → 内联不了，每次 getter 都是一条真实的 call

实测（gcc 13.3 / -O2，2 亿次 inc + get 循环，同一份逻辑三种实现）：

实现 total per-iter 相对
opaque（struct 藏 .c，跨 TU 调用） 238.8 ms 1.194 ns 5.9×
opaque + -flto（链接期优化，跨 TU 后可内联） 71.8 ms 0.359 ns 1.8×
struct 暴露 .h + static inline 40.7 ms 0.204 ns 1.0×

反汇编坐实第一种确实在真调用：

$ objdump -d b_op | grep -n "counter_inc"
   1123:  e8 e8 01 00 00   call   1310 <counter_inc>    ← opaque -O2：真 call，没内联

这 1 ns 是什么：x86-64 上一次 call+ret 的开销，加上被调用者要重新从内存 load 结构体字段（寄存器分配跨不过函数边界）。单次看不出来，但在 HFT 里：

  • 行情回调里一个订单簿对象走 20 次 getter = 20 ns，而整条链路的延迟预算可能只有 1 µs
  • 这 1 ns 在 L1 命中时约等于 3~4 个 cycle，和一次 L2 hit 相当

HFT 上的取舍（不是"要不要封装"，而是"在哪一层付这个钱"）：

场景 建议 理由
热路径（撮合、风控判定、行情解析） 暴露 struct + static inline，或 opaque + -flto 每次访问 1 ns 是真实预算
冷路径（初始化、配置、日志、销毁） opaque ADT 这些路径一年跑不了几次，可维护性优先
要发布 .so 给外部、要保 ABI opaque ADT，别无选择 暴露布局 = 冻结布局
数据面结构（order_book、mempool） 内部暴露 + static inline，对外接口仍 opaque "对内不设防、对外设防"是 DPDK 的常见做法

🔑 -flto 是 opaque 的救星：不开 LTO 时编译器在编译 main.c 那一刻根本看不到 counter.c，开了 LTO 后 IR 保留到链接期，跨 TU 内联成为可能（实测 1.194 → 0.359 ns）。代价是编译时间变长、调试信息更难对。DPDK 的 meson 构建默认带 b_lto=true，部分原因就在这儿。

OOP → C 的 ADT 对照表

C 没有 class / private，但 ADT 的四个要素都能一一对应上：

OOP 概念 C 的 ADT 实现 强制力来源
private 成员 struct 完整定义放在 .c，.h 只前置声明 编译器（不完整类型不解引用）
成员方法 普通 C 函数，对象指针作第一个参数 无（约定）
构造函数 xxx_create() 不完整类型的物理约束（只有 .c 知道 sizeof）
析构函数 xxx_destroy() 无（约定，忘了调就是泄漏）
this 指针 显式的第一个参数 List *l 无
private 方法 .c 里 static 函数 链接器（内部链接不导出符号）
继承 结构体嵌套（第一个成员是"基类"） 无
多态 / 虚函数 结构体里放函数指针表 无

注意最后一列：C 的 ADT 只有两处有强制力（隐藏布局靠编译器、隐藏符号靠链接器），其余全是约定。构造/析构尤其脆弱——C 没有 RAII，没有析构自动调用，忘记 list_destroy() 就是泄漏。这是 C 版 ADT 与 C++ class 的本质差距，不要因为表格对得上就以为能力等价。

内核里的 opaque handle

内核子系统对外给的几乎全是不透明句柄，用户模块只拿到指针、看不见内部成员——这就是 C 语言版的 ADT：

struct file;          /* 只前置声明，布局在 fs.h 内部 */
struct sock;          /* socket 层的 opaque */
struct file_operations;   /* 函数指针表，ops 本身就是黑盒接口 */

struct file 的完整定义躺在 include/linux/fs.h 里，只有内核自己能看到；模块代码只能靠 f_op 里的函数指针操作它。"给指针、不给布局"是内核 API 设计的默认姿势——和 DPDK 的 rte_mempool/rte_ring 是同一个思路。

常见误区

误区 事实
"struct 必须在 .h 暴露完整定义" 只用指针的接口，前向声明即可（opaque）
"头文件里不能放 struct 定义" 反了——类型定义放 .h 完全合法（nm 零符号、不分配内存）；不能放的是变量定义
"struct S obj; 跟在 struct 定义后面，是类型的一部分" 那是全局变量定义，多 TU include 照样 multiple definition，和 int g; 规则完全相同
"两个 .c 各写一份同名 struct，链接器会检查布局一致" 不会——编译链接全过、零警告，运行才读出垃圾（实测 8.49e-314）；-flto 也基本抓不到，ASan 只在大小不同越界时能抓
"-fcommon 加在链接命令里能救 multiple definition" 无效——它是编译期选项，.o 里符号早已定型（B 变不回 C）
"opaque pointer 有运行时开销" ⚠️ 只对一半。指针本身零开销，但每次访问都要走函数、跨 TU 无法内联——实测 1.19 ns/次 vs static inline 0.20 ns/次（5.9×）。开 -flto 可降到 0.36 ns。详见上面「ADT 不是零成本」
"不完整类型只是不能解引用" 也不能 sizeof、也不能定义对象（栈/全局），连 malloc(sizeof(*p)) 都不行——没有尺寸
"ADT 只是把函数分到两个文件" 判定标准是调用方能否 p->member。能访问成员 = 黑盒不存在 = 不是 ADT
"static 函数也能被外部调用" 不能，内部链接，链接器找不到
"改 struct 成员不影响调用者" 暴露完整 struct 时影响 ABI；opaque 才不影响
"编译器扫描全部源码，保证没有同名函数" 编译器只看单个 TU；重名是链接器报 multiple definition
"头文件隐藏了实现" 头文件只是文本粘贴，零隐藏能力；隐藏靠 opaque struct（编译器）+ static（链接器）
"opaque 只是约定，外部想绕过能绕过" 绕不过——不完整类型解引用是编译期 error，连 .o 都生成不出
"static 函数另写个声明就能从外部调" 不能——内部链接不导出符号，链接期 undefined reference

体现了信息隐藏（封装）。struct Stack 的具体定义只在 stack.c 中可见，外部只能通过 StackHandle（不透明指针）和接口函数操作栈。好处：(1) 修改 Stack 的内部实现不影响调用方；(2) 防止外部直接访问内部成员导致不一致；(3) 这是 C 实现 OOP 封装的标准模式。

题目 4： 实测数据：opaque 版 1.194 ns/次、-flto 版 0.359 ns/次、暴露 struct + static inline 版 0.204 ns/次。回答：

  1. 这个差距的物理来源是什么？
  2. 你是 HFT 系统的设计者，订单簿 order_book 该怎么选？给出分层方案。
参考答案

1. 差距来源

opaque 版的函数体在另一个编译单元，编译 main.c 时 gcc 只看到原型、看不到函数体 → 只能生成真实的 call 指令（objdump 可证：call 1310 <counter_inc>）。一次 call+ret 加上被调用者重新从内存 load 字段，约 1 ns。

  • -flto：把 IR 保留到链接期，链接时两个 TU 都可见 → 跨 TU 内联成为可能（1.194 → 0.359 ns，补回约 70%）
  • static inline：函数体在头文件里，编译期直接可见 → 完全内联，字段访问被折叠成普通 load/store（0.204 ns）

注意：差距不是"封装本身"造成的，是"编译器看不见函数体"造成的。这也意味着它不是不可消除的——LTO 能拿回大半。

2. 分层方案（不是二选一，而是分层）

层 选什么 理由
热路径（行情解析、撮合、风控判定） 暴露 struct + static inline，或 opaque + -flto 每次访问 1 ns × 每笔 20 次 = 20 ns，占延迟预算 2%
冷路径（初始化、配置、销毁、日志） opaque ADT 一年跑不了几次，可维护性与 ABI 优先
对外发布的 .so 接口 opaque ADT，别无选择 暴露布局 = 永久冻结布局
数据面内部（order_book、mempool） 内部暴露 + static inline，对外仍 opaque "对内不设防、对外设防"——DPDK 就是这个做法

工程上的一句实话：先按 opaque 写，等 profile 出来再对热路径逐个放开。反过来（一开始全暴露）后期想收回来，代价是动 ABI。

题目 6： 两个 .c 各自写了一份同名 struct，布局不同：

/* a.c */  struct Foo { int a; int b; };  struct Foo *make(void){...malloc(sizeof(struct Foo))...}
/* b.c */  struct Foo { double d; };      void show(struct Foo *p){ printf("%e\n", p->d); }
/* main.c 通过 struct Foo* 把 a 制造的对象传给 b */
  1. 编译、链接、运行分别会发生什么？-Wall -Wextra、-flto 能拦住吗？
  2. 如果 b.c 改成 struct Foo { char name[64]; };，ASan 为什么又能抓到？
  3. 工程上怎么根除这一类 bug？
参考答案（gcc 13.3 实测）

1. 全程绿灯，运行出垃圾

编译+链接 exit=0（-Wall -Wextra 零警告），运行 exit=0
a.c   : sizeof(struct Foo) = 8
a.c   : 写入 a=3 b=4
b.c   : sizeof(struct Foo) = 8
b.c   : 读出来 p->d = 8.487983e-314      ← {3,4} 的位模式被当 double 解释
  • -Wall -Wextra：零警告
  • -flto：基本抓不到——只给了一条误导性的 -Wuninitialized，exit 0（没有 type mismatch 告警）
  • 比 multiple definition 危险得多：后者链接期就拦死，前者一路跑到运行期，输出一个"看起来像个数"的垃圾值，exit 0

2. ASan 为什么这回能抓

两份图纸同样大小（8 vs 8）时，所有访问都落在 malloc 出来的 8 字节内，ASan 看不到任何越界，自然抓不到——布局冲突不等于内存越界。

改成 char name[64] 后，foo_show 会去读第 64 字节，而对象只有 8 字节，于是触发真正的越界读：

==459==ERROR: AddressSanitizer: heap-buffer-overflow
READ of size 1 at 0x50200000004f
    #0 foo_show conf_b2.c:16
0x50200000004f is located 55 bytes after 8-byte region

ASan 抓的是"读越界"，不是"布局冲突"——能抓到纯属巧合（这回恰好大小不同）。

3. 根除办法

C 不提供任何跨 TU 的类型一致性检查，所以只能从源头消除"多份图纸"：

办法 做法 适用
图纸只留一份 struct 定义放进共享 .h，所有 TU 一起 include 内部模块、热路径
干脆不给图纸 opaque：.h 只前置声明，完整定义锁在 .c 对外接口、发布 .so
编译期自检 在共享 .h 里放 _Static_assert(sizeof(struct Foo) == N) 只防大小变化，防不了成员顺序/类型变化

🔑 这也是 ADT 的第三个理由（前两个是封装与 ABI 稳定）：opaque 让"同名不同布局"这类无法静态检查的 bug 从物理上不可能发生——因为根本不存在第二份图纸。

7.5

递归

本节讲什么

函数调用自身；每层调用占一层栈帧。递归是树/链表遍历的天然写法，但 HFT 数据面禁止深递归——栈深度不可控、call/ret 开销、cache 不友好。

本节除了总览，还下探到机器层面：

  1. 函数调用指令的架构差异——x86-64 是 call/ret（返回地址压栈），AArch64（树莓派 5）是 bl/ret（返回地址优先进寄存器 X30，嵌套调用才备份到栈）
  2. 递归吃栈的精确对账（gcc 13.3 实测）：每帧 = 局部变量 + 48 字节固定开销；六档实测 深度 × 每帧 全部精确等于 7.99 MB
  3. ⚠️ 反直觉：-O2 能把非尾递归也整个变成循环（零 call），以及它给调试带来的坑

细节在 7.5.1（追踪）和 7.5.2（与迭代）。

要点

  • 组成：基线条件（base case）+ 向基线推进的递归步
  • 每层：局部变量、返回地址保存在栈上，占一栈帧
  • 深度过大 → 栈溢出 SIGSEGV（栈区到栈/堆边界）
  • 无基线或推进失败 → 无限递归 → 必爆栈

最小例子

int sum(int n) {
    if (n <= 0) return 0;          /* 基线 */
    return n + sum(n - 1);          /* 推进 */
}

每层 sum 占一栈帧：n、返回地址、可能的对齐填充。sum(10000) = 10000 层栈帧。

栈帧叠加

sum(3) ──┐
         │  [n=3, ret=main]      ← 栈帧 1
sum(2) ──┐
         │  [n=2, ret=sum(3)]    ← 栈帧 2
sum(1) ──┐
         │  [n=1, ret=sum(2)]    ← 栈帧 3
sum(0) → return 0                  ← 基线，开始回退

回退时逐层 ret 销毁栈帧，返回值逐层累加。

适用 vs 不适用

适用 不适用（HFT 热路径）
内核树/目录遍历 报文收发主循环
AST、配置树（深度有界） 订单簿遍历
排序（教学，快排/归并） 链表 walk（用迭代）
非热路径工具代码 信号处理

HFT 数据面若需"栈式"处理，用显式栈数组模拟递归（7.5.2、ch17）。

底层映射

栈大小与溢出

$ ulimit -s        # 栈大小，单位 KB，典型 8192（8MB）
8192

实测（gcc 13.3 -O0，8 MB 栈，PAD = 每层的局部数组大小）：

每帧大小 能撑的层数 备注
48 B（零局部变量） 174,599 地板价：返回地址 + rbp + 对齐
112 B（64 B 局部） 74,804 一个 char buf[64] 就用掉 1/3
1072 B（1 KB 局部） 7,818
4144 B（4 KB 局部） 2,021 ⚠️ 嵌入式常见栈才 8~16 KB

每帧多 1 KB，深度直接掉两个数量级。 深递归爆栈时：

sum(1000000) → 栈帧叠加超过 8MB → 踩到栈保护区 → SIGSEGV

栈保护区（guard page）让溢出确定性崩溃，而非静默踩堆。

机器层面：函数调用在 x86-64 与 AArch64 上长什么样

递归在机器层面就是「反复调用自己」，但不同架构的"调用"指令完全不同。先把两个架构的指令名和机制拆开（这俩最容易记混）。

一、x86-64：call / ret，返回地址在栈内存上

指令 干什么
call label 把返回地址压入栈内存，rip 跳到目标函数
ret 从栈内存弹出返回地址，跳回去

实测（gcc 13.3，-O0）递归函数 sum() 的反汇编：

0000000000000000 <sum>:
   4:  push   %rbp              ← 建立栈帧
   8:  sub    $0x10,%rsp        ← 开出 16 字节局部空间
  1f:  sub    $0x1,%eax         ← n - 1
  24:  call   29 <sum+0x29>     ← 递归：就是 call 自己
  2c:  add    %edx,%eax         ← n + sum(n-1)
  2f:  ret                      ← 返回

递归 = 反复执行 call，一层一层往栈上压返回地址。

硬证据：返回地址确实躺在栈上

拿 __builtin_return_address(0) 的值，去本层栈帧附近的内存里把它搜出来（实测输出）：

  层 2: 返回地址 0x5f97096112bc  存在 [&anchor +24] 处
  层 1: 返回地址 0x5f9709611271  存在 [&anchor +24] 处
  层 0: 返回地址 0x5f9709611271  存在 [&anchor -112] 处

每层都在自己的栈帧内部固定偏移处找到了自己的返回地址。这就是「x86 返回地址强制在栈上」的实证。

二、AArch64（树莓派 5）：bl / ret，返回地址优先在寄存器 X30

指令 干什么
bl func branch-and-link：把返回地址写入寄存器 LR（X30，链接寄存器），跳转
ret 从 X30 取返回地址，跳回

⚠️ 澄清一个常见记混：ARM/AArch64 里没有叫 node 的指令，不存在这个东西。 另外 ret 是 AArch64 才正式有的助记符——ARM32（老 32 位 ARM）做调用同样是 bl， 但返回通常写成 bx lr 或 mov pc, lr，没有标准的 ret 助记符。

关键差异：X30 只有一个，嵌套调用必须"备份到栈"

bl 会把 X30 覆盖掉。所以只要这个函数还要再调用别的函数（递归正好就是！）， 就必须在函数开头手动把 X30 存到栈上、结尾再取回来：

recurse:
    stp  x30, x29, [sp, #-16]   // prologue：把 LR(x30) 和 FP(x29) 压栈保存
    …
    bl   recurse                // 递归调用 —— 这一句会改写 x30
    …
    ldp  x30, x29, [sp], #16    // epilogue：把 LR 恢复回来
    ret                          // 用恢复后的 x30 返回

而叶子函数（不再调用任何函数的函数）完全不用碰栈——X30 一直好好待在寄存器里，直接 ret 就行。

🔑 所以「AArch64 返回地址在寄存器」这句话的完整版是： 第一层返回地址在 X30 寄存器；一旦发生嵌套调用，每一层的返回地址最终还是得落到栈上。 递归是最典型的嵌套调用，所以 AArch64 上递归照样吃栈，只是路径比 x86 多绕一步。

三、两架构对照

x86-64 AArch64（Pi 5）
调用指令 call bl
返回指令 ret ret
返回地址首选位置 栈内存（强制） 寄存器 X30（LR）
嵌套调用时 每层的返回地址本来就在栈上 函数 prologue 把 X30 压栈备份，epilogue 恢复
叶子函数 仍可能建栈帧（-O0 下有） 可以完全不碰栈
递归时 栈随深度线性增长 一样线性增长（只是每层多一次 LR 存取）

📌 关于"AArch64 更快"：理论上用寄存器存返回地址省了一次内存访问。 但实际上现代 x86-64 CPU 有专门的 返回地址预测器（return stack buffer / RSB）， call/ret 的返回地址访问基本被预测器消化掉了，真实差距远没有"寄存器 vs 内存"看起来那么大。 不要因为这条就在选型时偏向某个架构——x86 的 call 并不比 AArch64 的 bl 慢多少。

⚠️ 本节 AArch64 部分为架构知识 + 标准汇编模板，未在 Pi 5 上实测 （当前 WSL 环境无 aarch64 交叉工具链）。x86-64 部分全部为 gcc 13.3 实测。

四、递归的本质：架构无关，都是栈帧累积

不管 x86 的 call/ret 还是 AArch64 的 bl/ret：

每递归一层，就要保存一个返回位置；保存的位置最终落到栈上，栈帧不断累积。 栈溢出 = 递归太深，栈空间被耗尽。

这条可以用实测精确对账。用 SIGSEGV handler（配 sigaltstack，因为栈已经耗尽、handler 自己也需要新栈）抓爆栈瞬间的深度，同一个程序里同时量出每帧字节数：

ulimit -s = 8192 KB（8 MB）

  PAD=0     每帧=   48 B   爆栈深度= 174599   乘积= 8380752 B (7.99 MB)
  PAD=16    每帧=   64 B   爆栈深度= 130871   乘积= 8375744 B (7.99 MB)
  PAD=64    每帧=  112 B   爆栈深度=  74804   乘积= 8378048 B (7.99 MB)
  PAD=256   每帧=  304 B   爆栈深度=  27559   乘积= 8377936 B (7.99 MB)
  PAD=1024  每帧= 1072 B   爆栈深度=   7818   乘积= 8380896 B (7.99 MB)
  PAD=4096  每帧= 4144 B   爆栈深度=   2021   乘积= 8375024 B (7.99 MB)

六档全中 7.99 MB——深度 × 每帧字节数 = 栈容量，误差不到 0.1%。两条规律：

  1. 每帧 = 局部变量(PAD) + 48 字节固定开销（x86-64 -O0：返回地址 8B + push rbp 8B + 对齐填充） —— 哪怕你一个局部变量都不写（PAD=0），每层也要吃掉 48 字节
  2. 深度 ∝ 栈容量 ÷ 每帧大小，精确线性。改 ulimit -s 立刻验证：
  ulimit -s 1024   → PAD=64：深度 9300　乘积 0.99 MB
  ulimit -s 32768  → PAD=64：深度 299499　乘积 31.99 MB

这就是 7.5.2 说"递归 vs 迭代"的物理根因：迭代的栈占用是 O(1)，递归是 O(深度)。

五、⚠️ 反直觉实测：-O2 能把非尾递归也变成循环

教科书常说「只有尾递归才能被优化成循环」。实测打脸——gcc 13.3 -O2 下，普通的非尾递归 sum(n) = n + sum(n-1) 也完全没有 call 了：

0000000000000000 <sum>:          ← -O2，非尾递归！
   4:  xor    %eax,%eax          # acc = 0
   6:  test   %edi,%edi
   8:  jle    17                 # n <= 0 就退出
  10:  add    %edi,%eax          # acc += n
  12:  sub    $0x1,%edi          # n--
  15:  jne    10                 # ← 循环！没有 call，没有栈增长
  17:  ret

call 出现次数：0。 编译器认出这是等差数列求和的累加形式，直接转成了循环——栈占用从 O(n) 塌成 O(1)。

尾递归（-O2）同样零 call，而且还被循环展开 2 次：

  20:  lea    -0x1(%rax,%rdi,2),%eax    # 一次算两层（展开）
  24:  sub    $0x2,%edi                 # n -= 2
  27:  jne    20
  29:  ret

对照 -O0：尾递归 call 出现 1 次（真递归）。

最能说明问题的是没有基线的无限尾递归：

编译 行为 退出码
-O0 真递归 → 爆栈 139（SIGSEGV）
-O2 被折叠成一条自跳转 jmp → 死循环，不崩 124（timeout 杀掉）

-O2 下 main 的汇编就剩一句 jmp 1048 <main+0x8>——跳自己，永远不返回。

⚠️ 这条对调试影响很大：debug 版（-O0）崩溃的递归 bug，release 版（-O2）可能变成静默死循环—— 不再 SIGSEGV，而是 CPU 100% 挂死，更难排查。

但不能依赖它：C 标准不保证任何尾调用/递归优化，gcc 只对"足够简单"的情形下手。 数据结构一复杂（比如树递归、递归后还有操作），call 立刻回来。工程上仍按"递归 = 吃栈"来设计（7.5.2）。

call/ret 开销（7.1）

每层递归 = 一次 call + 一次 ret + 栈帧建立/销毁。叶子函数优化（省栈帧）对递归有限——递归不是叶子。深度 N 的递归 = N 次 call/ret，远慢于一个循环。

补充上面实测的两个细节：

  • 固定开销 48 字节/帧是"什么都不放"的地板价，真实递归函数的局部变量直接往上加
  • -O2 可能把整个递归消掉（见上一节），所以"递归一定慢/一定吃栈"只在未优化或编译器放弃优化时成立； 写程序时不能赌编译器会救你

嵌入式：栈不是 8 MB，是几 KB

上面实测全是在 8 MB 栈（Linux 主线程默认）下做的。嵌入式 Linux 的默认线程栈常常只有 8 KB， 按实测的 深度 = 栈容量 ÷ 每帧 线性外推：

环境 栈大小 char buf[64] 每帧 112 B 时能撑
Linux 主线程（默认） 8 MB 74,804 层
glibc pthread 默认线程 8 MB 74,804 层
嵌入式 pthread（常见配置） 8 KB 约 73 层
RTOS 任务栈（常见） 1~4 KB 9~37 层

同一个递归函数，在开发机跑得好好的，挪到板子上 70 多层就爆。这就是为什么嵌入式领域几乎把递归当禁区——不是"风格问题"，是算得出来的硬约束。在 Pi 5 上写内核模块时更要小心：内核栈只有 8 KB（ARM64 上是 16 KB）且不可动态增长，递归几乎没有生存空间。

题目 1： 以下递归函数有什么问题？

int factorial(int n) {
    if (n == 0) return 1;
    return n * factorial(n);
}
参考答案

递归调用传入的是 n 而非 n-1，导致无限递归直到栈溢出。正确写法：return n * factorial(n - 1);。此外还缺少对负数的处理——如果传入负数，n 永远不等于 0，也会无限递归。

题目 2： 判定下列说法，并说明机器层面的理由：

// a. ARM/AArch64 的函数调用指令是 node
// b. x86-64 的 call 把返回地址压入栈内存
// c. AArch64 的 bl 把返回地址写入寄存器 X30，永远不碰栈
// d. AArch64 里 ret 和 x86-64 里 ret 是同一条指令
// e. 递归在两种架构上最终都会线性消耗栈空间
// f. 叶子函数在 AArch64 上可以完全不碰栈
参考答案
项 判定 理由
a ❌ 不存在 node 指令。AArch64 是 bl（branch-and-link）；ARM32 同样是 bl，返回写 bx lr 或 mov pc, lr（AArch64 才正式有 ret 助记符）
b ✅ call 把下一条指令地址压栈，ret 再弹出来跳回——x86-64 返回地址强制在栈
c ❌ 只说对一半。bl 确实写 X30，但 X30 只有一个，函数若还要再调用（递归正是），必须在 prologue 用 stp x30, x29, [sp,#-16] 把 LR 压栈备份，epilogue ldp 恢复后才能 ret
d ❌ 助记符同名、语义相近，但是两条不同的指令（不同架构、不同编码、取返回地址的来源也不同：栈 vs 寄存器）
e ✅ 架构无关：每层都要保存一个返回位置，最终都落到栈上。x86 直接压栈；AArch64 先入 X30、嵌套时再转存栈，总量同样是 O(深度)
f ✅ 叶子函数不再调用别人，X30 不会被覆盖，全程待在寄存器里，ret 直接返回，零栈操作

题目 3： 计算 + 设计题（用本节实测数据）

实测：x86-64 -O0，每帧 = 局部变量 + 48 字节固定开销；深度 × 每帧 = 栈容量。

  1. Linux 主线程 8 MB 栈，递归函数每层有一个 char buf[256]（即 304 B/帧），能撑多少层？
  2. 同一函数搬到嵌入式板子（pthread 栈 8 KB），能撑多少层？
  3. 你的策略代码必须在 8 KB 栈上处理深度为 500 的树，每层最多能留多少字节局部变量？
  4. 如果改成 -O2，上面这些数字还成立吗？为什么？
参考答案

1. 8 × 1024 × 1024 ÷ 304 = 27,559 层（实测值就是 27,559，误差 < 0.1%）

2. 8 × 1024 ÷ 304 = 26 层 😬

3. 8192 ÷ 500 = 16.4 字节，减去 48 字节固定开销 → 负数，根本放不下。 即使一层局部变量都不写（48 B/帧），8192 ÷ 48 = 170 层 < 500 层。 → 结论：8 KB 栈上做 500 层递归是不可能的，必须改成显式栈的迭代写法（7.5.2、ch17）， 或者把栈调大（需要改线程属性，且要有依据地算）。

4. 不一定成立，这是最容易答错的一问：

  • -O2 可能完全消除递归——实测非尾递归 sum 在 -O2 下 call 数为 0，被转成循环， 栈占用从 O(n) 塌成 O(1)，上面的计算全部作废
  • 但不能依赖：C 标准不保证任何递归/尾调用优化，gcc 只对"足够简单"的情形下手 （树递归、递归后还有复杂操作的，立刻回到真 call）

工程做法：按 -O0 的数字做设计（也就是上面 1~3 的答案），把 -O2 的消除当作"可能拿到的额外红利"， 绝不当成设计依据。排障时反过来：debug 版崩 SIGSEGV 的递归，release 版可能变成静默死循环 （实测无基线尾递归 -O0 退出码 139、-O2 退出码 124 timeout），更难查。

7.5

.1 追踪递归函数

本节讲什么

手工 / 调试器追踪递归调用栈：每层参数、局部变量、返回点。理解栈帧如何叠加，是读递归代码、调试爆栈、看 Oops 的基本功。

要点

以链表打印为例：

void print_list(struct node *p)
{
    if (p == NULL)
        return;                  /* 基线 */
    printf("%d\n", p->data);
    print_list(p->next);         /* 先序：先打印再递归 */
}

先序 vs 后序

/* 先序：进入节点时处理 */
void pre(node *p) {
    if (!p) return;
    printf("%d\n", p->data);   /* 先处理当前 */
    pre(p->next);               /* 再递归 */
}

/* 后序：回退时处理 */
void post(node *p) {
    if (!p) return;
    post(p->next);              /* 先递归到底 */
    printf("%d\n", p->data);    /* 回退时打印 → 逆序输出 */
}

先序输出 1 2 3，后序输出 3 2 1（链表逆序）——后序在回退时处理，自然得到逆序。

追踪表（概念）

层 p 指向 进入时执行 待返回后执行
1 node1 printf(1) （回到调用者）
2 node2 printf(2) return 到层 1 末尾
3 node3 printf(3) return 到层 2 末尾
4 NULL return return 到层 3 末尾

每层有自己的 p 副本（值传递，7.3），互不干扰。回退按"后进先出"逐层 ret。

底层映射

  │  p=NULL, ret=层3      │

低地址（栈顶，向低增长）

每帧有独立的 p（参数副本）和返回地址。基线 return 后，逐帧 ret 弹出，栈收缩。

7.5

.2 递归与迭代

本节讲什么

同一问题递归 vs 循环实现的权衡。HFT 与内核热路径偏好迭代——栈深度可控、无 call/ret 开销、cache 友好。这一节还讲"尾递归优化"在 C 里的真实情况：标准不保证，gcc 常做但不总能。

要点

递归 迭代
代码 简洁、贴近数学定义 常多几行状态变量
栈 O(深度) O(1)
性能 call/ret 开销 + 栈帧 常更快
可控性 栈深度难预估 显式
HFT 避免 首选

链表遍历：递归 vs 迭代

/* 递归版 */
void print_list_rec(struct node *p) {
    if (!p) return;
    printf("%d\n", p->data);
    print_list_rec(p->next);
}

/* 迭代版 */
void print_list_iter(struct node *p) {
    for (; p != NULL; p = p->next)
        printf("%d\n", p->data);
}

迭代版：一个游标指针 p，O(1) 栈，无 call/ret。链表遍历几乎总是迭代更优。

尾递归与 TCO

尾递归：递归调用是函数最后一步（返回值就是递归调用的返回值，无后续运算）。

/* 非尾递归：n + sum(n-1)，递归返回后还要加 n */
int sum(int n) { return n <= 0 ? 0 : n + sum(n - 1); }

/* 尾递归：acc 累加，递归调用是最后一步 */
int sum_tail(int n, int acc) {
    return n <= 0 ? acc : sum_tail(n - 1, acc + n);
}

尾递归可优化成循环（TCO，Tail Call Optimization）：复用同一栈帧，O(1) 空间。

但 C 标准不保证 TCO。gcc/clang 在 -O2 通常会做（叶子函数 + 尾调用），但不总能——尤其有调试信息、复杂栈帧、或非纯尾调用时。不要依赖 TCO 保证不爆栈，要 O(1) 就显式写循环。

# 看尾递归是否被优化成循环（jmp 而非 call）
gcc -O2 -S t.c -o -
# 尾递归优化后：sum_tail 内是 jmp（循环），无 call

⚠️ 实测修正（gcc 13.3）：这里原先写着"非尾递归 sum 仍是 call sum"——这句话是错的，已实测推翻。

-O2 下 int sum(int n){ return n<=0 ? 0 : n + sum(n-1); }（非尾递归）的汇编里 call 出现 0 次——gcc 认出它是累加形式，直接转成了循环：

4: xor %eax,%eax # acc = 0 10: add %edi,%eax # acc += n 12: sub $0x1,%edi # n-- 15: jne 10 # ← 循环，没有 call 17: ret

也就是说："非尾递归一定保留 call"不成立。能否消除取决于编译器能否识别， 光看"是不是尾递归"猜不准。完整实测见 7.5。

但本节结论不变——C 标准不保证任何这类优化，不能依赖。

可靠的判定方法：别猜，直接数 call。

gcc -O2 -c t.c -o t.o
objdump -d --no-show-raw-insn t.o | sed -n '/<sum>:/,/^$/p' | grep -c call
# 0 = 已被转成循环（栈 O(1)）；>=1 = 仍是真递归（栈 O(深度)）

显式栈模拟递归

深度不可控但需要"栈式"处理时，用显式栈数组替代：

void walk_tree_iter(node *root) {
    node *stack[64];              /* 限深 64 */
    int sp = 0;
    stack[sp++] = root;
    while (sp > 0) {
        node *n = stack[--sp];
        if (!n) continue;
        visit(n);
        stack[sp++] = n->right;   /* 先压右，后压左 → 左先访问 */
        stack[sp++] = n->left;
    }
}

栈深度显式可控（数组大小），爆栈变成可预测的"栈满"错误。ch17 详。

何时仍用递归

  • 深度有界且小（AST、配置树）
  • 非热路径工具代码（启动期配置加载）
  • 代码清晰度远胜迭代（数学递归定义）

（严格说：未经优化、或编译器未能迭代化时才如此。-O2 有可能把整个递归消掉，见上面修正块与 7.5。 但设计上仍按"递归 = 每层一次 call + 一帧栈"来算，因为你不能赌编译器会救你。）

7.6

可变参数列表

本节讲什么

... 可变参数函数：printf、rte_log、printk 等的基础。可变参是 C 的"灵活陷阱"——能写通用接口，但类型不检查、靠格式串或 count 约定。这一节是总览：语法与最小示例、四个 stdarg 宏、与"原型"概念的衔接，以及 C23 对 void f(...) 的解禁；实现细节在 7.6.1（stdarg 宏），限制在 7.6.2。

要点

  • 至少一个固定参数（常为 format 或 count），作为 va_start 的锚点
  • 编译器不检查可变部分类型 → 传错 → UB
  • 底层优先固定签名 API；日志/格式化场景再用可变参

典型签名

int printf(const char *format, ...);              /* C 标准库 */
void rte_log(uint32_t level, const char *format, ...); /* DPDK 日志 */
void err(int status, const char *format, ...);    /* 自定义错误 */

语法规则

#include <stdarg.h>

void foo(int last, ...);   /* last 是固定参数，... 代表可变数量参数 */
  • ... 必须放在参数列表最后
  • ... 前面至少要有 1 个固定参数（C17 及以前的硬性要求——C23 有变化，见下）
  • ... 前后可有逗号可无：foo(int a, ...) ≡ foo(int a, ...)
  • 标准库最典型的例子：int printf(const char *fmt, ...);

最小可运行示例

#include <stdio.h>
#include <stdarg.h>

void sum(int count, ...)
{
    va_list ap;
    va_start(ap, count);            /* 从最后一个固定参数 count 启动 */

    for (int i = 0; i < count; i++) {
        int val = va_arg(ap, int);  /* 取出下一个 int 参数 */
        printf("%d ", val);
    }
    va_end(ap);                     /* 清理 */
}

int main(void)
{
    sum(3, 10, 20, 30);   /* 输出: 10 20 30 */
    return 0;
}

四个核心宏（7.6.1 详）：

宏 作用
va_list ap 可变参数的迭代变量（不透明类型）
va_start(ap, 固定参数名) 初始化，必须传紧邻 ... 前面的那个固定参数
va_arg(ap, 类型) 取下一个参数，要显式指定类型
va_end(ap) 结束清理，必须与 va_start 配对

与"原型"的关联（→ 7.2.1）

void sum(int count, ...);   /* ✅ 这是完整原型——编译器知道后面是可变参数 */
void sum();                 /* ❌ 这不是可变参数，是"参数信息完全未知"的旧式声明 */

两码事，别混为一谈。void sum(); 只是说"返回 void，参数未知"，它既不是原型也不声明可变参。

带 ... 的原型检查范围是不对称的（gcc 13 实测 -Wall -Wextra）：

void sum(int count, ...);
sum("not-an-int", 1, 2);   /* 固定参数类型错 → warning: passing argument 1 of 'sum'
                              makes integer from pointer without a cast */
sum(2, 3.14, 9.9);         /* 可变部分传 double → 零警告（不检查） */

固定参数照常检查，可变部分完全不检查——这是 ... 型原型的真实语义，不是"整个函数都不检查"。

C 没有重载，所以靠 ... 处理参数数量变化

C++ 可以写多个同名不同参的重载；C 里函数名全局唯一（7.2），要接受"参数数量不定"只能用 ...。代价就是放弃编译期类型检查——这是语言层面的取舍，不是用法问题。

为什么需要至少一个固定参数

va_start(ap, last) 需要 last 作为"最后一个固定参数"来定位可变参在栈/寄存器里的起始位置（7.6.1）。没有固定参数就找不到起点——所以 ... 不能是唯一的参数。

⚠️ 但 C23 改了这条：可以不要固定参数了

C23（N2975 "Relax requirements for va_start"）允许 void f(...) 这种完全无固定参数的写法，配套 va_start(ap, ...) 的新形式：

c void sum_all(...) /* C23 起合法：没有任何固定参数 */ { va_list ap; va_start(ap, ...); /* C23 新形式：第二个参数直接写 ... */ for (int i = 0; i < 3; i++) printf("%d ", va_arg(ap, int)); va_end(ap); }

gcc 13.3 -pedantic-errors 逐标准实测：

写法 C99 C11 C17 C2X (C23)
void f(...); 仅声明 ❌ ❌ ❌ ✅
void f(...) {} + va_start(ap, ...) ❌ ❌ ❌ ✅ 且正确运行
void sum(int count, ...) 传统写法 ✅ ✅ ✅ ✅ 行为不变

拒绝信息本身就是证据：error: ISO C requires a named argument before '...' **before C2X**—— 措辞里的 "before C2X" 说明 C2X 起这条约束被撤掉了。

注意 gcc/clang 在不加 -pedantic 时默认把它当扩展静默接受（-Wall -Wextra 也零警告）， 所以"我的 C11 项目里 void f(...) 也能编过"不代表它合法——加上 -pedantic-errors 就现形。

C23 没改的：默认参数提升、va_arg 无类型检查、必须 va_end 配对——这些老规则全部保留。 所以"至少一个固定参数"在 C17 及以前是硬性要求，在 C23 只是可选项；写可移植代码仍应保留固定参数。

count 说谎：可变参最典型的运行期 UB

va_arg 不会告诉你"还有没有下一个"。count 写大了就往栈/寄存器残留区继续读：

sum(3, 10, 20);   /* count 说 3 个，实际只传 2 个 */

实测三次运行（-O0）：

10 20 -619250256
10 20 1228213680
10 20 1531653552

第三次读的是上一个函数留下的寄存器残留——每次都不一样，退出码 0，零警告。 这也是为什么可变参的"个数约定"必须由调用方严格履行：格式串（printf）、NULL 哨兵（execl）、显式 count，本质都是同一个问题的不同解法。

内核 printk

/* Linux 内核 —— printk 本身就是可变参函数 */
asmlinkage int printk(const char *fmt, ...);
/* 驱动里的典型包装 */
#define dev_err(dev, fmt, ...) ...

内核大量使用 <stdarg.h>，printk 族、dev_err/dev_info、seq_file 的 seq_printf 全是变参接口。内核的规则是：热路径（数据面/中断上半部）不用变参，因为它类型不安全、格式串解析有开销。

可变参 vs 数组传参

/* 可变参：类型异质，不检查 */
void logf(const char *fmt, ...);          /* %d 给 int，%f 给 double */

/* 数组传参：类型同质，有 count，安全 */
void log_n(int n, const struct evt *evs); /* 每个元素都是 evt */

可变参适合"异质类型 + 格式化"；同质批量用数组 + count 更安全。

底层映射

寄存器 + 栈混合传递

x86-64 ABI：固定参数和可变参前 6 个走寄存器（rdi..r9），超出进栈。va_list 实现是"寄存器保存区 + 栈溢出区"的抽象——va_arg 按类型从对应位置取。

调用 logf("level=%d price=%f", 3, 9.9):
  rdi = "level=%d price=%f"   (固定参数 fmt)
  rsi = 3                      (可变参 1, int)
  xmm0 = 9.9                   (可变参 2, double)
  栈上可能还有保存区

va_arg(ap, int) 从 rsi 区取，va_arg(ap, double) 从 xmm 区取。类型错了就读错位置 → 垃圾或崩。

既然参数在寄存器里，能不能手动拿 &last 往后偏移去够可变参？ 不能——实测 -O0/-O2 全是垃圾，gp/fp 两个游标还得各走各的。完整实测与 va_list 四个字段的真实数值见 7.6.1。

默认参数提升（7.6.2 详）

可变参里 float → double，char/short → int。所以 va_arg(ap, float) 是错的，要 va_arg(ap, double)。固定参数不做这个提升。

int sum_all(int first, ...) {

7.6

.1 stdarg 宏

本节讲什么

va_list / va_start / va_arg / va_end（C99 另有 va_copy）—— <stdarg.h> 提供的可变参迭代宏。这一节讲清五个宏的精确用法、它们在栈/寄存器层面的实现，以及最关键的一问：

能不能不用这套宏，直接拿 &last 往后偏移去够可变参？实测：不能，而且差得离谱。

原因是 C 语言把"参数怎么传"完全甩给了 ABI——x86-64 上前 6 个整数参数在寄存器里，压根不在栈上。这套宏的本质是把调用约定的细节封进编译器内建（__builtin_va_start / __builtin_va_arg），让同一份 C 源码在寄存器传参和栈传参的机器上都能跑。下面全部用 gcc 13.3 x86-64 实测坐实。

要点

#include <stdarg.h>

void log_msg(const char *fmt, ...)
{
    va_list ap;
    va_start(ap, fmt);          /* 初始化，从 fmt 之后开始 */
    vprintf(fmt, ap);           /* 把整组可变参转给 vprintf */
    va_end(ap);                 /* 清理 */
}
宏 作用 关键约束
va_list ap 遍历状态（不透明类型） 不要直接访问其内部
va_start(ap, last) 初始化，last = ... 前最后一个固定参数 last 不能是寄存器变量、不能是数组
va_arg(ap, type) 取下一个参数，按 type 读 type 必须与实际提升后类型匹配
va_end(ap) 结束遍历，清理 必须配对 va_start
va_copy(dest, src) 复制遍历状态（C99） 用于多次遍历同一组参

默认参数提升：只提升可变参，不提升固定参数

提升不是对所有参数生效，只对 ... 里的实参生效。实测（-O0）：

调用方实参的真实大小：  sizeof(char)=1  sizeof(float)=4
固定参数：sizeof(c)=1  sizeof(f)=4          ← 原样，没提升
可变参数：用 int/double 接 -> 65 / 1.500    ← 已提升
实参声明类型 作固定参数时 作可变参时（提升后） va_arg 该写
char / signed char / unsigned char char(1B) int va_arg(ap, int)
short short(2B) int va_arg(ap, int)
_Bool _Bool(1B) int va_arg(ap, int)
float float(4B) double va_arg(ap, double)
int / long / 指针 / double 不变 不变 原类型

为什么要提升？ 调用点编译到 ... 就丢掉了类型信息——被调函数没有原型可查，调用方只能按一套"谁都装得下"的通用规则把实参塞进去（整型统一到 int，浮点统一到 double）。固定参数有完整原型，调用方知道精确类型，不需要这套保守规则。

顺带一个常见误解：C 里字符常量 'A' 的类型本身就是 int（sizeof('A') == 4，C++ 里才是 char），所以它进可变参根本没"被提升"，它生来就是 int。

va_arg 类型写错：gcc 不是读垃圾，是直接 abort

对 char/short/float 这类"提升后类型"写错，gcc 13.3 实测：

warning: 'char' is promoted to 'int' when passed through '...'
note: (so you should pass 'int' not 'char' to 'va_arg')
note: if this code is reached, the program will abort

汇编里 wrong_char 的第 37 条指令是 ud2（未定义指令），运行直接 Illegal instruction (core dumped)。

标准只说 UB；gcc 选择插一条陷阱指令当场 SIGILL，而不是让你读到一个错值、然后再查三小时。这是编译器的善意，不是标准的保证。

但别指望这个保护兜住所有类型错误——它只覆盖"提升规则"这一类。传 int 却用 double 读，不属于提升错误，而是读错了区（下面 gp/fp 双游标会解释），gcc 一声不吭：

=== 同一个实参 42，两种读法 ===
  va_arg(double) 读一个 int 实参 = 2.42843e-319   ← 读的是 xmm 区残留
  va_arg(int)    读同一个实参    = 42

零警告、退出码 0、输出一个"看起来像个数"的垃圾。这才是可变参最危险的地方：真实类型错误往往不报错。

包装 printf 的标准模式

#include <stdarg.h>
#include <stdio.h>

void err(const char *fmt, ...)
{
    va_list ap;
    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);   /* vfprintf 接 va_list，不重新解包 */
    va_end(ap);
}

/* 调用 */
err("bad magic: 0x%x at %s:%d\n", magic, file, line);

vprintf/vfprintf/vsprintf/vsnprintf 是 printf 族的 va_list 版——包装层把可变参原样转发，不重新解包。

为什么非得有 v 版：可变参不能二次转发

想把一组 ... 原样转交给另一个 ... 函数，最直觉的写法是：

void outer_bad(const char *fmt, ...) { inner(fmt, ...); }   /* 想直接转发 */

实测（gcc 13.3）：

error: expected expression before '...' token

... 是声明语法，不是能当实参传递的运行时对象——进入函数体时它已经展开成若干个独立实参，而 C 没有任何语法让你"把这批实参整体交给下家"。

唯一出路是先把 ... 收进 va_list，再交给 v 版函数：

void outer_ok(const char *fmt, ...) {
    va_list ap; va_start(ap, fmt); vprintf(fmt, ap); va_end(ap);
}
/* outer_ok("x=%d y=%s\n", 42, "ok");  →  x=42 y=ok */

v 版函数存在的唯一理由，就是让可变参能被二次转发。 没有它，任何日志包装、错误上报、格式化缓冲都写不出来。

内核原样照搬这套分层（典型写法；本次未逐行比对 v6.6 源码）：

pr_info(fmt, ...)        →  printk(KERN_INFO fmt, ...)  →  vprintk(fmt, ap)
dev_err(dev, fmt, ...)   →  dev_printk(...)             →  vprintk(fmt, ap)
seq_printf(m, fmt, ...)  →                                 seq_vprintf(m, fmt, ap)

规律一致：对外接口收 ...，内部一律转成收 va_list 的 v 版。你写自己的日志层时照抄这个分层就行。

va_copy：多次遍历

int count_and_print(const char *fmt, ...) {
    va_list ap1, ap2;
    va_start(ap1, fmt);
    va_copy(ap2, ap1);           /* 复制状态，ap2 独立遍历 */

    int n = 0;
    while (...) { va_arg(ap1, int); n++; }   /* 第一次遍历计数 */

    /* 用 ap2 重新遍历打印 */
    vprintf(fmt, ap2);

    va_end(ap1);
    va_end(ap2);
    return n;
}

实测（-O0）：

  第一次遍历: 7 abc 3.14
  第二次遍历: 7 abc 3.14     ← 两个游标互不干扰

直接 ap2 = ap1 会怎样？x86-64：根本编译不过

va_list ap1, ap2;
va_start(ap1, n);
ap2 = ap1;          /* ← 实测：error: assignment to expression with array type */

assign_probe.c:8:9: error: assignment to expression with array type

因为 x86-64 上 va_list 是 __va_list_tag[1]——数组类型，而 C 里数组不可赋值。所以在这台机器上你连"碰巧能跑"的机会都没有，编译期就死了。

ABI va_list 是什么 ap2 = ap1 的下场
x86-64 SysV __va_list_tag[1]（数组） 编译错误（数组不可赋值）
x86-32 cdecl char *（标量） 编译过，但两个名字共享同一游标位置 → 第二次遍历从第一次停下的地方接着走，不是从头
AArch64 (AAPCS64) __va_list（结构体） 结构体浅拷贝，行为"看似正常"但不可移植

三种 ABI 三种失败模式，唯一共同点是都不对。这就是必须 va_copy 的原因——它是 C99 起唯一可移植的写法。（AArch64 一行未在 Pi 5 实测，依据 AAPCS64 文档。）

为什么不能手动指针偏移（Quiz 回答）★

最自然的想法：可变参不就跟在最后一个固定参数后面吗？那我 char *p = (char *)&count; p += 8; 一个个读不就行了？

实测（gcc 13.3，x86-64，sum(3,10,20,30) 正确值 60）：

读法 -O0 -O2
va_arg(ap, int) 60 ✅ 60 ✅
&count 按 8 字节走 55040 ❌ -2076147457 ❌
&count 按 4 字节走 961130009 ❌ -2076180224 ❌
8 个参数时（按 8 字节走） 32813 ❌ 2005195492 ❌

两个优化级别、两种步长，全是垃圾，一次都没碰巧对上。 把 &count 附近 64 字节打出来看，10/20/30 一个都不在：

    &count = 0x7ffd3949adfc
    [+ 0*8] = 0x0000001000000003   ← 低 4 字节是 count=3，高 4 字节是残留
    [+ 1*8] = 0x0000000300000001
    [+ 2*8] = 0x3949adfc00000003
    [+ 3*8] = 0xb8ecec0000007ffd
    ...

-O2 下 gcc 还会直接诊断：

warning: array subscript 2 is outside array bounds of 'int[1]'
note: at offset 8 into object 'count' of size 4

编译器很清楚 count 只有一个 int 那么大——你往外走就是越界，它连对象大小都报给你了。

三条根本原因

① 参数根本不在栈上。

x86-64 System V：前 6 个整数/指针参数走 rdi rsi rdx rcx r8 r9，前 8 个浮点走 xmm0–xmm7。sum(3,10,20,30) 里 3/10/20/30 四个全在寄存器里，栈上连影子都没有。你去 &count 后面翻，翻到的是被调者自己的栈帧内容——返回地址、被保存的寄存器、局部变量的邻居、栈金丝雀——跟实参毫无关系。

这个错误写法在 x86-32 cdecl（全栈传参）上确实能碰巧跑通，这正是它至今还在流传的原因。它在一个架构上"能用"，换个架构就废了。C 标准从没保证过参数在栈上——是各 ABI 自己定的，而 ABI 可以（且已经）把它挪进寄存器。

② 就算在栈上，类型决定你该读哪个区，不是"下一个槽"。

整数和浮点存在两个互不相干的区域里（gp 区 / fp 区）。同一个"下一个参数"，va_arg(ap, int) 和 va_arg(ap, double) 读的是两个不同的地址，两个游标各走各的。单纯往后挪一个固定步长，没有任何一种步长能同时满足两种类型——见下面游标实测。

③ 寄存器保存区是编译器看到 va_start 才建的，手写代码拿不到。

看 prologue 实测：subq $240, %rsp + 5 条 movq + testb %al,%al + 8 条 movaps。这些指令是编译器检测到你在用 va_start 后专门生成的，普通函数完全没有。你手写偏移，这块区域压根不存在。

其中 testb %al, %al 是 SysV ABI 给可变参开的特例：调用可变参函数时，调用方必须把所用向量寄存器个数放进 al（0–8），被调方据此决定要不要存 xmm。这套"调用方/被调方协作"是你手写几行 C 复现不出来的。

一句话回答 Quiz：手动偏移的写法把"参数在栈上连续排列"当成了事实，但那只是某个老 ABI 的巧合。真实情况由 ABI 决定（寄存器 / 栈 / 双区 / 调用约定协作），<stdarg.h> 的宏是编译器内建（__builtin_va_start / __builtin_va_arg）——编译器知道目标机器的 ABI，你不知道。

va_list 游标实测：那四个字段到底怎么动

x86-64 上 va_list 是 __va_list_tag[1]（sizeof = 24）。直接把成员打出来看（-O0）：

整数参数——gp_offset 每次 +8：

  va_start 后        gp_offset= 8 fp_offset=48 overflow=0x7ffea1359b90 reg_save=0x7ffea1359ad0
    va_arg(int) -> 10
    取完一个 int 后  gp_offset=16 fp_offset=48 ...
    va_arg(int) -> 20
    取完一个 int 后  gp_offset=24 fp_offset=48 ...

注意起点是 8 不是 0——count 占了寄存器保存区的第一个 8 字节槽，va_start(ap, count) 就把游标设到它之后。这就是"最后一个固定参数"这个名字的物理含义：它决定游标初值。

混合类型——两个游标各走各的：

动作 gp_offset fp_offset
va_start 后 8 48
va_arg(int) → 42 16 48
va_arg(double) → 3.140 16 64
va_arg(long) → 999 24 64

取 double 时 gp_offset 纹丝不动——它在 fp_offset 区里走，两者互不干扰。fp_offset 起点 48 = 6×8，即整数区之后才是浮点区。

9 个 long——寄存器耗尽后 overflow_arg_area 接管：

  va_start 后   gp_offset= 8  overflow=0x...b70
    ... 取到第 5 个后 gp_offset=48（到顶，6 个整数寄存器用完）
    va_arg(long) -> 6   gp_offset=48  overflow=0x...b78   ← +8
    va_arg(long) -> 7   gp_offset=48  overflow=0x...b80   ← +8
    va_arg(long) -> 8   gp_offset=48  overflow=0x...b88   ← +8

gp_offset 卡在 48 不动，overflow_arg_area 每次 +8 往栈溢出区走。"游标"不是一根指针在一条直线上走，而是"两个区 + 两个偏移 + 一个溢出指针"的状态机——这就是为什么你没法用一个 char* 模拟它。

va_list 在 x86-64 的实现

x86-64 System V：va_list 是一个结构：

typedef struct {
    unsigned int gp_offset;     /* 下一个整数寄存器参数的偏移 */
    unsigned int fp_offset;     /* 下一个浮点寄存器参数的偏移 */
    void *overflow_arg_area;    /* 栈溢出区起点 */
    void *reg_save_area;        /* 寄存器保存区起点 */
} __va_list_tag;

va_arg(ap, int) 按 gp_offset 从寄存器保存区取（用完转栈溢出区）；va_arg(ap, double) 按 fp_offset 从 xmm 保存区取。类型决定了从哪个区取——错类型读错位置。

为什么 last 不能是寄存器变量

va_start 需要 last 的地址来定位保存区。若 last 在寄存器（如 register int），无地址 → va_start 行为未定义。现代代码几乎不会显式用 register，但仍要避免。

可变参函数的无条件开销：写不写 va_arg 都得付

实测三个函数的 -O0 prologue：

int v1(int n, ...) { va_start(ap,n); va_arg(ap,int); va_end(ap); }  /* 只读 1 个 */
int v0(int n, ...) { va_start(ap,n); va_end(ap); }                  /* 一个都不读 */
int p1(int a, int b) { return a + b; }                              /* 普通函数 */
函数 栈预留 关键 prologue 指令
v1 subq $240 movq %rsi/%rdx/%rcx/%r8/%r9 + testb %al + movaps %xmm0..7（8 条）
v0 subq $224 同上（一个可变参都不读，照样全溢出）
p1 无 只有 4 条 movl 到自己的栈槽

编译器看到 va_start 就把六个整数寄存器和八个向量寄存器无条件溢出到栈上的 register save area——因为它不知道运行时会传几个、什么类型。这是约 224 字节栈 + 14 条 store 指令，每次调用都付。

HFT 视角：这是"数据面禁用可变参"的第二个物理理由。第一个是格式串解析与类型不安全，第二个就是这个——哪怕你只传一个 int，prologue 也把 6+8 个寄存器全写进内存。热路径日志要么走编译期开关彻底关掉，要么用无格式的定长二进制（binlog）。

（对照组：-O2 下编译器能裁掉未使用的溢出，但这属于优化，不是 ABI 保证。）

va_end 到底做了什么？x86-64 上：什么都没做

写两个只差一个 va_end 的函数，看 -O0 汇编：

int sum_with_end(int count, ...) { ...; va_end(ap);  return t; }
int sum_no_end  (int count, ...) { ...; /* 不调 */   return t; }
函数 指令数 尾部
sum_with_end 59 leave; ret
sum_no_end 59（完全相同） leave; ret（逐字节一致）

在 x86-64 glibc 上 va_end 展开成空操作，忘记它在这台机器上没有任何可观测后果。所以"忘了 va_end 就会出错"是不准确的说法——准确说法是：

  • 标准规定 va_start 必须配对 va_end，否则未定义行为（UB 不等于"必然出错"，而是"不保证"）
  • 在这个 ABI 上 va_end 恰好无事可做；在另一些 ABI 上它可能要释放资源或恢复状态，那时漏掉就是真泄漏
  • 静态分析器和代码审查靠这个配对关系确认遍历已结束

结论照旧：必须写。 但理由是可移植性与可维护性，不是"不写就会崩"。

常见误区

误区 事实
"手动拿 &last 往后偏移就能读可变参" ❌ 实测 -O0/-O2 全是垃圾。x86-64 前 6 个参数在寄存器里，栈上根本没有；&count 后面是被调者自己的栈帧
"参数在栈上连续排列" 只是 x86-32 cdecl 的巧合。x86-64 / AArch64 都是寄存器传参，ABI 说了算，C 标准没保证过
"va_arg 类型写错只是读错值" 提升类错误（char/short/float）gcc 插 ud2 当场 SIGILL；但 int/double 读错区是零警告 + 垃圾值，更危险
"忘了 va_end 会崩" x86-64 上 va_end 是空操作（实测两函数汇编逐字节相同）。仍必须写——理由是 UB 与可移植性，不是"不写就崩"
"可变参只是语法糖，零开销" prologue 无条件 subq $224~240 + 5 条 movq + 8 条 movaps，一个可变参都不读也照付
"固定参数也会默认提升" 不提升。实测固定参数 sizeof(c)=1；只有 ... 里的才提升
"va_arg(ap, float) 取 float" 错——可变参 float 提升为 double，要 va_arg(ap, double)
"ap2 = ap1 复制遍历状态" x86-64 上编译错误（va_list 是数组类型）；其他 ABI 能编译过但语义错。用 va_copy
"last 可以是 register 变量" 不行，va_start 要地址
"手动 va_arg 循环比 vprintf 灵活更好" 优先 vprintf，手动遍历易错

  8. 可变参函数的 prologue 无条件付出什么代价？数据面禁用变参的物理理由是什么？
  9. va_end 在 x86-64 上展开成什么？既然是空操作，为什么还是必须写？

代码自测

题目 1： 以下代码中 va_start 的第二个参数为什么必须是最后一个有名参数？

void log_msg(int level, const char *fmt, ...) {
    va_list args;
    va_start(args, fmt);
    // ...
    va_end(args);
}
参考答案

va_start 需要通过最后一个有名参数的地址来定位可变参数在栈上的起始位置。不同调用约定下，参数压栈方向和布局不同，va_start 的实现依赖这个参数来找到可变参数区域。如果传错参数名，va_start 的行为是未定义的。

题目 2： 下面两种写法，-O0 和 -O2 下分别输出什么？为什么？

static int sum_va(int count, ...) {
    va_list ap; va_start(ap, count);
    int t = 0;
    for (int i = 0; i < count; i++) t += va_arg(ap, int);
    va_end(ap); return t;
}
static int sum_manual(int count, ...) {
    int t = 0;
    char *p = (char *)&count;
    for (int i = 0; i < count; i++) { p += sizeof(long); t += *(int *)p; }
    return t;
}
/* main: printf("%d %d\n", sum_va(3,10,20,30), sum_manual(3,10,20,30)); */
参考答案

实测（gcc 13.3 x86-64）：

-O0:  60  55040
-O2:  60  -2076147457

sum_va 恒为 60；sum_manual 在两个优化级别下都是垃圾，且值还不一样。

原因不是"偏移步长算错了"，而是那块内存里根本没有参数：x86-64 SysV 规定前 6 个整数参数用 rdi/rsi/rdx/rcx/r8/r9 传，sum(3,10,20,30) 的四个实参全在寄存器里。&count 后面是被调者自己的栈帧（返回地址、被保存寄存器、局部变量、栈金丝雀），跟实参毫无关系。

补充证据：-O2 下 gcc 会给出 warning: array subscript 2 is outside array bounds of 'int[1]' / note: at offset 8 into object 'count' of size 4——它知道 count 只有一个 int 大。

（这个写法在 x86-32 cdecl 全栈传参时能碰巧跑通，这正是它流传至今的原因。但 C 标准从未保证参数在栈上。）

题目 3： 在 x86-64 上执行下面这段，gp_offset / fp_offset 各是多少？

void probe(int n, ...) {
    va_list ap;
    va_start(ap, n);            /* A */
    int    a = va_arg(ap, int); /* B */
    double d = va_arg(ap, double); /* C */
    long   l = va_arg(ap, long);   /* D */
    va_end(ap);
}
/* 调用: probe(3, 42, 3.14, 999L); */
参考答案
位置 gp_offset fp_offset 说明
A（va_start 后） 8 48 n 占第一个 8 字节槽，游标设在它之后
B（取完 int 42） 16 48 整数走 gp 区，+8
C（取完 double 3.140） 16 64 浮点走 fp 区，+16；gp 区纹丝不动
D（取完 long 999） 24 64 回到 gp 区，+8

关键点三个：

  1. 起点 8 而非 0——va_start(ap, n) 的 n 决定了游标初值，这就是"最后一个固定参数"的物理含义
  2. fp_offset 起点 48 = 6×8，整数区之后才是浮点区
  3. 取 double 时 gp_offset 不变——两个游标独立推进，所以"一个游标往后挪"的模型从根上就是错的

题目 4： 以下三行分别会怎样？（x86-64 / x86-32 / AArch64）

va_list ap1, ap2;
va_start(ap1, n);
ap2 = ap1;
参考答案
ABI va_list 的真实类型 ap2 = ap1 的下场
x86-64 SysV __va_list_tag[1]（数组） 编译错误 assignment to expression with array type——C 里数组不可赋值
x86-32 cdecl char *（标量） 编译过，但两个名字共享同一游标状态：第二次遍历从第一次停下的地方接着走，不是从头
AArch64 AAPCS64 __va_list（结构体） 浅拷贝，本机"看似正常"，但不可移植

三种 ABI 三种失败模式，唯一共同点是都不对。C99 的 va_copy(ap2, ap1) 是唯一可移植写法，且必须各自 va_end。

7.6

.2 可变参数的限制

本节讲什么

可变参的类型安全、可移植性、默认参数提升限制——《C 陷阱与缺陷》里库函数陷阱的集中地。这一节讲清三大限制，并给出 __attribute__((format)) 让编译器帮你检查格式串的工程利器。

三个容易想当然、实测才准的点，本节用 gcc 13.3 实测钉死：

  • va_arg(args, float) 到底怎么个 UB？ 实测是编译器插 ud2 当场 SIGILL（退出码 132），不是"读个错值"。
  • __attribute__((format(printf, 2, 3))) 的 2 和 3 是什么？ 用在普通函数上是索引越界、属性静默失效；它真正对应的是 C++ 非静态成员函数（this 隐式占第 1 位）。
  • "没有元信息"到底会错成什么样？ 实测 printf("%d %d", 1, 2.0) 打出 1 1068962088——不是值偏一点，是走了另一个寄存器区；而且格式串类有 -Wformat 兜底，open 漏写 mode 这类连一个警告都没有（实测建出带 setuid 位的文件）。
  • void sum(...) 能自动知道传了几个吗？ 两层坑：① 这行声明在 C99/C11/C17 下根本不合法（before C2X），C2X 才解禁；② 即使 C2X 下合法，sum(1,2) 读出 3 也是巧合——污染寄存器后同一次调用得到 303 / 603。根因：变参调用点唯一多传的元信息是 al（向量寄存器个数），不是参数个数。

要点

限制 1：无类型检查

void log_msg(const char *fmt, ...);
log_msg("%d", 3.14);    /* UB：期望 int 给了 double */
log_msg("%s", 42);      /* UB：期望 char* 给了 int */
log_msg("%d", &x);      /* UB：期望 int 给了指针 */

编译器不检查可变参与格式串的匹配——除非你加 __attribute__((format))（见下）。运行时取错类型 → 读错位置 → 垃圾值或崩。

注意检查范围的不对称性：带 ... 的原型仍然检查固定参数。实测 -Wall -Wextra 下 sum("not-an-int", 1, 2) 会报 -Wint-conversion，而 sum(2, 3.14, 9.9) 的可变部分零警告。 也就是说"可变参不检查"只针对 ... 覆盖的那一段（→ 7.6）。

限制 0：至少一个固定参数（C23 起不再强制）

C17 及以前硬性要求 ... 前必须有具名参数；C23（N2975）解禁了 void f(...) 并引入 va_start(ap, ...) 新形式（→ 7.6 的实测矩阵）。这一条是限制也是语言演进的样本： 写需要跨 C17/C23 移植的代码时，保留固定参数仍是唯一稳妥选择。

限制 2：默认参数提升

可变参里实参做默认参数提升（7.2.2 同规则）：

实参类型 提升后 va_arg 必须用
char / short int int
unsigned char / unsigned short int/unsigned int 或 unsigned
float double double 
void f(...);
f('a');          /* 实参提升为 int，va_arg(ap, int) */
f(3.14f);        /* 实参提升为 double，va_arg(ap, double) —— 不是 float！ */

va_arg(ap, float) 永远错——可变参里没有 float，都是 double。

提升的物证：同一个 3.14，两种位模式

实测（小端，x86-64）：

  float  3.14f : 4 字节  c3 f5 48 40
  double 3.14  : 8 字节  1f 85 eb 51 b8 1e 09 40

注意 double 3.14 不是"float 3.14 后面补 4 个零"——浮点格式完全不同（指数的位数和偏移都不一样）。所以"提升"对浮点而言不是零扩展，是重新编码。这也解释了为什么拿 4 字节 float 当 8 字节 double 读，必然连吃后面 4 字节邻居。

提升会让调用"合法"还是"UB"？看你怎么取

print_all("ddf", 1, 2, 3.14f);
写法 判定 实测
va_arg(args, double) 取 3.14f ✅ 合法、定义明确 输出 123.140000
va_arg(args, float) 取 3.14f ❌ UB ud2 → SIGILL，退出码 132

关键点：3.14f 本身不是问题，取法才是。实参提升成 double 之后，用 double 取是完全正当的——这是 printf 里 %f 能同时吃 float 和 double 实参的原因。

限制 3：无法获知个数与类型

可变参不携带"有几个、什么类型"的元信息——va_start 之后你手里的 va_list 只是几个游标字段（x86-64 上是 gp_offset / fp_offset / overflow_arg_area / reg_save_area，见 7.6.1 的实测），里面没有任何"还剩几个"的计数。函数看到的确实只是一串原始字节 + 一个不知道终点在哪的游标。所以必须靠外部渠道告诉它：

  • 格式串（printf 的 %d %s %f）
  • 显式 count + 约定（void log_n(int n, ...) 约定每个都是 int）
  • 哨兵（execl(path, arg0, arg1, ..., NULL)）
/* 更安全：固定类型数组 + count */
void log_events(int n, const struct evt *evs);   /* 同质批量 */

上面三条是"元信息外挂"的三种渠道。严格说还漏了两类同样常见的：

  • 类型标签流（tag list）：每个实参前面自带一个类型码，本质是"自描述 count"
  • 元信息编码在固定参数里：不额外传描述，而是让固定参数本身的取值决定可变段长什么样

渠道 4：类型标签流（自描述）

enum { T_INT, T_STR, T_DBL, T_END };
void emit(int tag, ...);          /* 用法：emit(T_INT, 1, T_STR, "a", T_DBL, 2.5, T_END) */

va_list ap; va_start(ap, tag);
for (int t = tag; t != T_END; t = va_arg(ap, int)) {
    switch (t) {
    case T_INT: printf("%d", va_arg(ap, int));    break;
    case T_STR: printf("%s", va_arg(ap, char *)); break;
    case T_DBL: printf("%f", va_arg(ap, double)); break;
    }
}
va_end(ap);

把"有几个"升级成"每个是什么"，代价是每个实参多传一个 tag（8 字节）和一次 switch。它和格式串是同一思路的两端：格式串是紧凑的字符串编码，tag list 是展开的二进制编码。

渠道 5：固定参数自带元信息（内核最爱的做法）

这一类最容易被忽略，但它是 POSIX / 内核里出现频率最高的：

例子 固定参数 如何描述可变段
open(path, flags, ...) flags 仅当 flags 含 O_CREAT（某些实现含 O_TMPFILE）时，才存在第 3 个 mode 参数
ioctl(fd, cmd, arg) cmd cmd 的位域里编码了方向（_IOC_DIR）和实参大小（_IOC_SIZE）
fcntl(fd, cmd, ...) cmd 不同 cmd 决定第 3 参是 int、指针还是 struct
printf(fmt, ...) fmt 格式串 = 元信息（渠道 1，归入同一族）

ioctl 的 cmd 是"自描述"的教科书样本——实测（gcc 13.3，WSL）：

#include <linux/ioctl.h>
struct big   { char b[64]; };
struct small { int x; };
#define CMD_BIG   _IOWR(0x6d, 3, struct big)
#define CMD_SMALL _IOWR(0x6d, 4, struct small)
/* CMD_BIG   = 0xc0406d03  dir=3 size=64
   CMD_SMALL = 0xc0046d04  dir=3 size=4   */

size 被 _IOC 宏直接编进 cmd 的 30 位里，内核侧 copy_from_user 用 _IOC_SIZE(cmd) 就知道拷多少字节——类型信息从来没走可变参，它藏在固定参数的位里。这也是为什么内核里 ioctl 的第三个参数看起来"什么都能传"。

👉 这条线索后面会反复遇到：TLPI 的 fcntl / ioctl、内核 struct file_operations::unlocked_ioctl 都建立在这个"cmd 自描述"约定上。

底层：ABI 层面为什么元信息必然缺失

x86-64 SysV 下实参分布在两个互不相干的区域（→ 7.6.1 实测过 gp_offset / fp_offset）：

寄存器保存区：  [ gp 槽 0..5 各 8B ][ fp 槽 0..7 各 16B ]   栈溢出区：超出的实参
va_arg(ap,int)    → 走 gp 区，gp_offset += 8
va_arg(ap,double) → 走 fp 区，fp_offset += 16   ← 两个游标互不干扰

槽位里只有值，没有 tag 字段。所以 va_arg 完全按你给的类型"结账"：类型说错 = 走错区，不是"值偏了一点"，而是读到另一个实参甚至残留垃圾。实测（-O0，gcc 13.3）：

printf("A: %d %d\n", 1, 2.0);        /* A: 1 1068962088 */
printf("B: %d %d\n", 1, 2.0, 3);     /* B: 1 3          */
printf("C: %d %d %d\n", 1, 2.0, 3);  /* C: 1 3 0        */

逐个拆：

调用 现象 原因
A 第二个 %d 打出 1068962088 2.0 进了 fp 区，gp 区第二个槽没人写，va_arg(ap,int) 读的是寄存器残留垃圾
B 打出 3 第二个 %d 从 gp 区取，正好取到实参 3——double 被彻底跳过，后面所有实参"前移一格"
C 第三个 %d 打出 0 gp 区第三个槽同样没人写，读残留

这就是元信息缺失最狠的地方：错位会接力。 一个类型不匹配，后续所有实参的解读全部错位一路到底，而且没有 EOF 标记，va_arg 会一直读到栈上去。

调用点汇编：被调方能拿到的唯一元信息是 al

会有人问："编译器明明知道我传了几个，为什么不能顺手塞个个数进去？"——它没塞。看 -O0 下 4 个调用点的实测汇编（gcc 13.3）：

# fixed3(1, 2, 3)                  定参：个数编译期已知
mov $0x3,%edx
mov $0x2,%esi
mov $0x1,%edi
call fixed3                  ← 没有任何"共 3 个"的信息

# fixed3(1, 2, 0)                  第 3 个是 0 也得老老实实写
mov $0x0,%edx                ← 编译器不会替你省

# varf(3, 1, 2, 3)                 变参：edi=3 是源码里自己写的 count
mov $0x3,%ecx
mov $0x2,%edx
mov $0x1,%esi
mov $0x3,%edi                ← 这个 3 是第一个实参 n，不是编译器生成的
mov $0x0,%eax                ← al = 0
call varf

# varf(2, 1, 2)
mov $0x2,%edx
mov $0x1,%esi
mov $0x2,%edi                ← edi=2 同样是源码里那个 n
mov $0x0,%eax
call varf

两件事值得记住：

  1. 变参调用点唯一多出来的元信息是 mov $0x0,%eax——也就是 al 寄存器。x86-64 SysV 规定：变参调用时 al = 实际用到的向量寄存器（SSE）个数。这是给被调方的优化提示（决定要不要把 8 个 xmm 全存进保存区），不是参数个数。
  2. varf(3,1,2,3) 里那个 3 是你自己写的第一个实参。写 sum(1,2,3)（不传 count）时这个位置就没有值，被调方于是一个字节的元信息都拿不到。

这也从根上解释了为什么 printf 必须有格式串：除了 % 占位符，ABI 里没有任何字段写着"这次传了几个"。

小思考题：void sum(...) 能自动知道传了 3 个 int 吗？

int sum(...);
sum(1, 2, 3);

答案：不能。而且这道题有两层坑。

第一层：这行声明在 C99/C11/C17 下根本不合法。

$ gcc -std=c11 -pedantic-errors -c t.c
error: ISO C requires a named argument before '...' before C2X [-Wpedantic]

c99 / c17 同样报错（措辞里那句 before C2X 就是标准自己给出的时间线），只有 -std=c2x 通过——C23 的 N2975 解禁了无固定参数形式（详见 7.6.1）。不加 -pedantic-errors 时 gcc 会当扩展默默接受，所以你可能从没见过这个报错；但换个编译器或在 CI 里开 -pedantic-errors，它就是硬错误。

第二层：即使 C2X 下合法，函数内部也拿不到个数。

C2X 配套允许了 va_start(ap, )（省略 last 参数），但没有配套任何"查询个数"的接口。所以只能硬编码读几次：

int sum(...)
{
    va_list ap; va_start(ap, );
    int t = 0;
    for (int i = 0; i < 3; i++)          /* ← 这个 3 只能写死 */
        t += va_arg(ap, int);
    va_end(ap);
    return t;
}

实测（gcc 13.3，-std=c2x）：

调用 -O0 说明
sum(1,2,3) 6 唯一正确的用法
sum(1,2) 3 看着像"自动知道没有第 3 个"——纯属巧合
sum(1,2,3,4) 6 第 4 个 4 被丢掉，零警告

sum(1,2) 那个 3 是假的。 让它现形：先在旁边调一个函数把第 3 个参数寄存器（edx）污染掉，再调 sum(1,2)：

A) poison3(100,200,777)    之后： sum(1,2) = 303   ← 1 + 2 + 300（残留）
B) poison4(100,200,300,555) 之后： sum(1,2) = 603  ← 1 + 2 + 600（残留）
   -O2 下同一份代码：        4 和 3                  ← 换优化级别，残留也跟着变

多读出来的那个"实参"是上一个函数调用留下的寄存器残留，值随上下文和优化级别变化。第一次测出 3 只是因为那个时刻 edx 恰好是 0——巧合到像设计过一样，而这正是它危险的地方：错的代码在最简单的测试里表现正常。

限制 3 的完整说法：不是"元信息不好拿"，而是 ABI 里压根没有这个字段。va_arg 是一个完全靠你报数记账的游标——多报一个就往后多读一格垃圾，少报一个就悄悄丢掉尾部实参，两种方向编译器都一声不吭。

三类失败模式汇总

元信息错在哪 后果 能否被编译器发现
个数（count 说谎 / 哨兵漏写 / 格式串转换符多） 越界 va_arg → 读栈上返回地址、金丝雀、上一个栈帧 仅格式串类可被 -Wformat 发现
类型（%d 给了 double、float 当 double 取） 走错 gp/fp 区 → 垃圾值 + 后续连锁错位 同上；裸 va_arg 完全不管
生命周期（va_arg 出来的指针指向 caller 的临时对象） 悬垂指针 不能

哨兵不是语言机制，只是约定 + 编译器善意

execl 要求以 NULL 结尾，这不是 C 语言的规定，是 POSIX 的约定。gcc 会帮你查，但查的方式很绕——实测：

#include <unistd.h>
execl("/bin/echo", "echo", "hi");    /* 故意漏 NULL */

$ gcc -Wall -Wextra -c t.c
warning: missing sentinel in function call [-Wformat=]      ← 报了
$ gcc -Wall -Wextra -fno-builtin -c t.c
（零警告）                                                   ← 关掉 builtin 就没了

-fno-builtin 一关警告就消失，说明这份知识来自 gcc 编译器内建，不是头文件：/usr/include/unistd.h 里 execl 的声明只有 __THROW __nonnull((1,2))，sentinel 这个词在 unistd.h 里出现 0 次。

自定义函数默认完全没人管——想让 gcc 帮你查，得自己声明：

void exec_like(const char *p, ...) __attribute__((sentinel));
/* exec_like("a","b","c");   → warning: missing sentinel in function call
   exec_like("a","b",NULL);  → 干净                                      */

⚠️ 注意 sentinel 检查挂在 -Wformat 下（不是自己的 -Wsentinel），且只是 warning。CI 里要兜底就加 -Werror=format。

哨兵的两个实测后果

① 中间出现 NULL 会被当成"到此结束"。 哨兵的本质是"拿某个值当终止符"，那业务数据里就不能出现这个值：

static void run_all(const char *first, ...)
{
    va_list ap; va_start(ap, first);
    int n = 0;
    for (const char *s = first; s != NULL; s = va_arg(ap, const char *))
        fprintf(stderr, "    arg[%d] = %s\n", n++, s);
    va_end(ap);
    fprintf(stderr, "    total = %d\n", n);
}

实测（gcc 13.3，-O0 与 -O2 结果一致）：

[case1] run_all("ls", "-l", "-a", NULL)
    arg[0] = ls   arg[1] = -l   arg[2] = -a      total = 3     ← 正常

[case2] run_all("ls", NULL, "-a", NULL)
    arg[0] = ls                                  total = 1     ← "-a" 整段丢失

零警告、退出码 0，-a 就这么没了。 这正是"哨兵不能当业务数据用"的具体代价。选型判据很简单：你的数据集合里允不允许出现那个终止值？

场景 能否用哨兵 原因
execl 的 argv 字符串列表 ✅ argv 元素本身不会是 NULL
fd 列表用 -1 当哨兵 ✅ -1 不是合法 fd
价格/数量列表用 0 当哨兵 ❌ 0 是合法业务值
指针列表用 NULL 当哨兵，但允许"空槽" ❌ 空槽会被当成终止
长度可变的二进制数据 ❌ 任意字节都可能出现，用 count

② 漏写哨兵不一定崩，可能只是多读一个。 实测 run_all("ls", "-l")（故意不写末尾 NULL）：

[case3] 完全忘记写末尾 NULL：
    arg[0] = ls
    arg[1] = -l
    total = 2        ← 停下来了，exit=0

它停住是因为第 3 次 va_arg 恰好读到一个 0。这绝不意味着安全——换个调用上下文残留值就非 0，循环会继续往下扫，拿到的野指针被当字符串解引用就是段错误。用污染寄存器的方式逼它现形：漏写哨兵时读到 3 个才停（正确是 2 个），多出来的那个是残留值，不崩溃、退出码 0、静默多处理一个野指针。

两个方案的失败形状不同：count 说大了 → 多读垃圾，说小了 → 丢尾部实参；哨兵漏写 ≡ count 说大了。三种情况都没有任何诊断。

反面实测：open 漏写 mode 是零警告 + 真实权限漏洞

open 是 int open(const char *, int, ...)——O_CREAT 时必须有第三个参数。实测漏写：

int fd = open("/tmp/va_probe", O_CREAT | O_WRONLY);   /* 故意漏 mode */
  • 编译期：零警告（fcntl.h 里 open 只有 __nonnull((1))，gcc 也没有为它内建 sentinel/格式知识）
  • 运行期：用垃圾值当 mode 建了文件 → ls -l 显示 --ws--x---

--ws--x--- 里的 s 是 setuid 位被置上了。漏写 mode 不是"权限随机"这么轻，而是可能造出一个带 setuid 的文件——这是历史上真实出现过的一类漏洞。也正因如此，现代代码应该用 open(path, flags, mode) 三参全写，或改用 openat + 显式 mode。

一句话：格式串类有编译器兜底（-Wformat），count 和哨兵类只在你自己加属性之后才有兜底，而 open 这类连属性都没人给你加。

底层映射

__attribute__((format)) 让编译器检查格式串

void log_msg(const char *fmt, ...)
    __attribute__((format(printf, 1, 2)));
/*           ↑              ↑     ↑
         printf 语义   fmt 是第 1 参  可变参从第 2 参开始 */

声明后，编译器会检查格式串与可变参类型匹配：

log_msg("%d", 3.14);    /* -Wformat: expected 'int' but arg is 'double' */
log_msg("%s", 42);      /* -Wformat: expected 'char *' but arg is 'int' */
log_msg("%d %d", 1);    /* -Wformat: too few arguments */
log_msg("%d", 1, 2);    /* -Wformat: too many arguments */

实测（-Wall -Wextra）：log_msg("%d", 3.14) 报 warning: format '%d' expects argument of type 'int', but argument 2 has type 'double' [-Wformat=]

Quiz：format(printf, 2, 3) 里的 2 和 3 是什么？

void test(const char *fmt, ...) __attribute__((format(printf, 2, 3)));

如果这个 test 是普通函数（上面这种写法），那 2 和 3 是错的。 实测：

warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1 [-Wattributes]

它只有 1 个具名参数（fmt），你却说格式串在第 2 位——索引越界，gcc 直接把这条属性丢掉，而且不会检查 test 的任何调用点（实测 test("%d", 3.14) 零报警）。

⚠️ 这是最阴险的失效方式：属性写错不会让编译失败，只会让检查静默消失。你以为有保护，其实一点都没有。

那 2 和 3 什么时候才对？

两种场景：

① C++ 非静态成员函数——this 隐式占第 1 位，所以 fmt 是 2、... 是 3：

struct Log {
    void good(const char *fmt, ...) __attribute__((format(printf, 2, 3)));  /* ✅ */
    void bad (const char *fmt, ...) __attribute__((format(printf, 1, 2)));  /* ❌ */
};

实测（g++ 13.3）：

写法 结果
format(printf, 2, 3) ✅ 生效，L.good("%d", 3.14) 报 argument 3 has type 'double'
format(printf, 1, 2) ❌ 编译错误：'format' attribute argument 2 value '1' refers to parameter type 'Log*'

gcc 的报错直接说出了答案——第 1 个参数的类型是 Log*，也就是 this。

② 有两个（及以上）固定参数的函数——格式串不在第 1 位：

void two(int lvl, const char *fmt, ...) __attribute__((format(printf, 2, 3)));  /* ✅ */
/*                                                                    ↑   ↑
                                                             fmt 是第 2 参  ... 从第 3 参开始 */

实测：two(1, "%d", 3.14) 报 argument 3 has type 'double' ✅

四种场景对照（全部实测）

场景 正确写法 写错会怎样
普通函数 f(fmt, ...) format(printf, 1, 2) 写 2,3 → -Wattributes 越界警告 + 检查静默失效
两个固定参 f(a, fmt, ...) format(printf, 2, 3) 写 1,2 → 把 a 当格式串，误报一堆
C++ 成员函数 C::f(fmt, ...) format(printf, 2, 3)（this=1） 写 1,2 → 编译错误，提示参数类型是 Log*

记忆法：这两个数字是从 1 开始的位置编号，不是偏移量。先数清楚"格式串前面站了几个参数"——普通函数 0 个（fmt 就是 1），成员函数多一个 this，前置参数各自 +1。

格式串安全漏洞

printf(user_input) 是格式串漏洞——攻击者控制 %n（写内存）、%x（泄漏栈）：

printf(buf);            /* 危险：若 buf 含 %n 可改内存 */
printf("%s", buf);      /* 安全：buf 是数据不是格式 */

实测：%x 真的把栈读出来了

user_input = "%x %x %x %x"
  危险写法 printf(buf)      :  596045c0 0 0 25      ← 栈上的原始值，每次运行都不同
  安全写法 printf("%s", buf):  %x %x %x %x          ← 原样打印，只是普通字符

同一份输入，两种写法，一个把栈内容吐出来、一个老实当字符串。这就是"数据"和"代码"混淆的经典形态——printf 的第一个参数不是数据，是一段被解释的程序。

实测：%n 是写入，不是打印

int written = 0;
printf("hello%n world\n", &written);
printf("written = %d\n", written);   /* written = 5 */

%n 把"到目前为止已输出的字符数"写进指针参数。hello 是 5 个字符 → written == 5。它不打印任何东西，它是往内存里写。 攻击者控制格式串时，就能让这个"写入"落到可控地址上。

关于防护：实测在 -O2 -D_FORTIFY_SOURCE=2 下，字面量格式串的 %n 仍然照写不误（w=5，退出码 0）。不要以为开了 _FORTIFY_SOURCE 就万事大吉——真正的防线是永远不让外部输入当格式串。

⚠️ 但"压栈开销"这个说法不准确

常见解释是"可变参要压栈所以慢"——恰恰相反：x86-64 上前 6 个整数参数本来就在寄存器里，根本不压栈。可变参慢在两处（→ 7.6.1 实测）：

  1. prologue 无条件建寄存器保存区——subq $240 + 5 条 movq + testb %al + 8 条 movaps，约 14 条 store，哪怕一个可变参都不读也照付
  2. va_arg 每次都要判断 gp_offset 有没有越界、要不要切到 overflow_arg_area——这是运行时分支，不是编译期算好的偏移

所以准确的结论是：可变参的代价是"把编译期能定的事推到了运行期"，而不是"多压了几个栈"。这个区别在优化时很关键——减少参数个数救不了你，因为 prologue 开销与参数个数无关。

DPDK RTE_LOG 的做法

#define RTE_LOG(l, t, ...) \
    rte_log(RTE_LOG_##l, RTE_LOGTYPE_##t, ##__VA_ARGS__)

RTE_LOG(INFO, "pkt=%p len=%zu\n", pkt, len);

rte_log 内部用 vfprintf，宏展开转 __VA_ARGS__（ch14 详）。带 format 属性，编译期检查。

常见误区

误区 事实
"va_arg(ap, float) 只是读错值" gcc 实测插 ud2 → SIGILL，退出码 132。但这是编译器善意，标准仍只说 UB
"format(printf, 2, 3) 是"两参函数"专用" 也对（两个固定参时），但典型用途是 C++ 成员函数（this 占 1）。用在普通函数上不报错，只静默失效
"属性写错了编译会失败" 不会——只有 -Wattributes 一条警告，检查悄悄消失
"开了 _FORTIFY_SOURCE 就不怕 %n" 实测字面量格式串的 %n 照写（w=5，退出码 0）
"可变参慢是因为要压栈" 恰恰相反：x86-64 前 6 个参数在寄存器里不压栈。慢在 prologue 无条件建保存区 + va_arg 运行时分支
"可变参开销随参数个数增长" 不随：subq $240 与个数无关，一个可变参都不读也照付
"va_arg(ap, float) 取 float" 错，可变参 float 提升为 double
"可变参类型编译器会检查" 不检查，除非 __attribute__((format))
"printf(buf) 没事" 格式串漏洞，%n 可写内存、%x 泄栈（实测读出 596045c0 0 0 25）
"可变参能传任意类型" 能传但取回要匹配，否则 UB
"char/short 在可变参里保持原类型" 提升为 int
"类型不匹配就是读错一个值" 实测 printf("%d %d",1,2.0) → 1 1068962088：走错 gp/fp 区，且后续实参连锁错位（1 2.0 3 打 1 3 0）
"execl 的哨兵是 C 语言规定" 是 POSIX 约定。unistd.h 里 sentinel 出现 0 次，gcc 的检查来自编译器 builtin——-fno-builtin 一开警告就没
"自定义哨兵函数漏 NULL 编译器会提醒" 不会，得自己加 __attribute__((sentinel))（检查还挂在 -Wformat 下）
"漏写 open 的 mode 顶多权限随机" 实测零警告，建出 --ws--x--- —— setuid 位可能被置上，是真实漏洞类型
"可变参的元信息只能靠格式串 / count / 哨兵" 还有类型标签流（tag list）和编码进固定参数（ioctl 的 _IOC_SIZE 实测 = 64）

void print_all(const char *fmt, ...) {
    va_list args;
    va_start(args, fmt);
    while (*fmt) {
        if (*fmt == 'd') printf("%d", va_arg(args, int));
        if (*fmt == 'f') printf("%f", va_arg(args, double));
        fmt++;
    }
    va_end(args);
}
// 调用
print_all("ddf", 1, 2, 3.14f);
参考答案

实测输出：123.140000。本调用合法、行为定义明确。

拆解：

  1. 3.14f 是 float，但作为可变参传入时触发默认参数提升 → 变成 double
  2. va_arg(args, double) 取的类型 == 提升后的类型 → 匹配，无 UB
  3. "ddf" 前两个 d 各取一个 int（1 和 2），第三个 f 取 double（3.14）
  4. printf("%f") 本来就期待 double → 输出 3.140000

位模式证明了提升不是"补零"：

  float  3.14f : 4 字节  c3 f5 48 40
  double 3.14  : 8 字节  1f 85 eb 51 b8 1e 09 40

推广规律：va_arg 的 type 必须写"提升之后"的类型——char/short/_Bool → int，float → double。

题目 2： 把上题的 'f' 分支改成 va_arg(args, float)，会发生什么？请给出可观测后果，不要只说"UB"。

if (*fmt == 'f') printf("%f", va_arg(args, float));   /* ★ 改这一行 */
参考答案

实测（gcc 13.3，x86-64）：

warning: 'float' is promoted to 'double' when passed through '...'
note: (so you should pass 'double' not 'float' to 'va_arg')
note: if this code is reached, the program will abort
  • 反汇编里 print_bad 的第 70 条指令是 ud2（未定义指令）
  • 运行：Illegal instruction (core dumped)，退出码 132（128+SIGILL）

所以可观测后果是当场 SIGILL 崩溃，不是"读到一个错值"。

⚠️ 但要分清两层：

层面 说法
C 标准 UB——没规定编译器该怎么做
gcc/Clang 实测 插 ud2 主动 abort（善意陷阱，省得你查三小时）

别把 gcc 的善意当成保证。 换个编译器（或 va_arg 类型不是"提升类"错误，比如传 int 却用 double 读），就是真的静默读垃圾——那种情况零警告、退出码 0（→ 7.6.1）。

另注：printf("%f", ...) 本身期待 double，所以即使 va_arg 返回了 float，它也会再被提升成 double 传进去——错误发生在 va_arg 那一步，与 printf 无关。

题目 3： 下面这个声明有什么问题？2 和 3 到底代表什么？

void test(const char *fmt, ...) __attribute__((format(printf, 2, 3)));
参考答案

问题：索引越界，属性静默失效。

test 只有 1 个具名参数 fmt，却说格式串在第 2 位。实测 gcc 13.3：

warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1 [-Wattributes]

后果不是"报错"，而是属性被丢掉，所有调用点都不再检查——实测 test("%d", 3.14) 零报警。你以为有保护，其实没有。

正确写法取决于场景：

场景 正确写法
普通函数 test(fmt, ...) format(printf, 1, 2)
两个固定参 test(a, fmt, ...) format(printf, 2, 3)
C++ 成员函数 C::test(fmt, ...) format(printf, 2, 3)——this 隐式占第 1 位
C++ static 成员函数 format(printf, 1, 2)——无 this

gcc 对成员函数写 1,2 的报错直接点破了原因：

error: 'format' attribute argument 2 value '1' refers to parameter type 'Log*'

第 1 个参数的类型是 Log*，就是 this。

记忆法：两个数字是从 1 开始的位置编号，不是偏移量。数清楚"格式串前面站了几个参数"。而排查"属性写了却没生效"，唯一线索是 -Wattributes。

题目 4（小思考题）：int sum(...); sum(1,2,3); —— 函数内部能不能自动知道"传了 3 个 int"？为什么？

参考答案：不能。分两层回答。

第一层：这行声明在 C99/C11/C17 下根本不合法。

$ gcc -std=c11 -pedantic-errors -c t.c
error: ISO C requires a named argument before '...' before C2X [-Wpedantic]

c99/c17 同样报错，只有 -std=c2x 通过（C23 N2975 解禁无固定参数形式）。不加 -pedantic-errors 时 gcc 当扩展默默接受，所以很多人没见过这条报错——但它在 CI 里就是硬错误。

注意报错措辞自带时间线：before C2X。

第二层：即使 C2X 下合法，也拿不到个数。

va_start(ap, ) 允许省略 last 参数，但没有任何配套接口能查询"还剩几个"。你只能硬编码读几次：

int sum(...)
{
    va_list ap; va_start(ap, );
    int t = 0;
    for (int i = 0; i < 3; i++)
        t += va_arg(ap, int);       /* 这个 3 只能写死 */
    va_end(ap);
    return t;
}

实测（gcc 13.3，-std=c2x）：

调用 结果 说明
sum(1,2,3) 6 唯一正确用法
sum(1,2) 3 看着像"自动知道没有第 3 个"——巧合
sum(1,2,3,4) 6 第 4 个被丢掉，零警告

为什么 sum(1,2) 那个 3 不能信？ 把第 3 个参数寄存器（edx）先用另一个函数污染掉：

poison3(100,200,777)      之后： sum(1,2) = 303   ← 1 + 2 + 300（残留）
poison4(100,200,300,555)  之后： sum(1,2) = 603   ← 1 + 2 + 600（残留）
-O2 下同一份代码：          4 和 3                  ← 换优化级别，残留也变

多读出来的那个"实参"是上一个函数调用留下的寄存器残留。第一次测出 3 只是因为那一刻 edx 恰好是 0。

第三层（根因）：调用点汇编里，变参调用唯一多传的一条元信息是 mov $0x0,%eax（即 al），它表示用到的向量寄存器个数——是给被调方的优化提示，不是参数个数。varf(3,1,2,3) 里 edi=3 是源码自己写的第一个实参 n，编译器没有额外生成任何"还有 N 个"的标记。

结论：C 的 ... 从 ABI 到语言都没有"个数"字段。va_arg 完全靠你报数记账——多报一个读垃圾，少报一个丢实参，两个方向都无诊断。

正确写法（三选一）：

int sum_n(int n, ...);                        /* 显式 count */
int sum_arr(int n, const int *a);             /* 数组 + count（工程首选） */
#define sum3(a,b,c) sum_n(3,(a),(b),(c))      /* 或者干脆用宏固定个数 */

Q3static inline 头文件
// math_utils.h
static inline int max(int a, int b) {
    return a > b ? a : b;
}

// 被 10 个 .c 文件 #include
// 会产生 multiple definition 吗？
答案与复习指引

答案： 不会。static 使每个编译单元有自己的副本（内部链接），不产生全局符号冲突。inline 建议编译器内联展开。

权衡： 多份副本增加代码体积，但 inline 展开后没有函数调用开销。内核大量使用 static inline 在头文件中定义小函数。

Q4va_list 陷阱
int sum(int count, ...) {
    va_list ap;
    va_start(ap, count);
    int total = 0;
    for (int i = 0; i < count; i++)
        total += va_arg(ap, int);
    va_end(ap);

}

sum(3, 1, 2);         // (2) 会怎样？

答案与复习指引
