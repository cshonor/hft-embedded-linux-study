# 2.1.2 执行

## 本节讲什么

**执行环境**：操作系统把可执行 ELF 加载成进程、划分虚拟内存段、调用 `main`、顺序执行直至 `return`。承接 ch01.1.3 的运行链路，本节从**内存模型**角度讲清楚每个变量住在哪个段、什么生命周期、为什么栈上变量不清零。这是理解悬垂指针、栈溢出、`.bss` 清零等问题的地基。

## 加载与入口链路

```
1. shell 解析命令 → fork + execve("./app", argv, envp)
2. 内核 execve：
   ├── 读 ELF 头，校验 magic (0x7f 'E' 'L' 'F')
   ├── 建新进程地址空间
   ├── 按 Program Headers 映射各段到虚拟地址
   │     ├── .text  → 可读可执行
   │     ├── .rodata → 只读
   │     ├── .data  → 可读写
   │     └── .bss   → 可读写（不占文件，运行时清零）
   ├── 设置栈：压入 argc/argv/envp/auxv
   ├── 设置入口指令地址（ELF e_entry，通常是 _start 而非 main）
   └── 跳转入口
3. _start（crt0 启动代码）：
   ├── 对齐栈、设置 ABI
   ├── 调用 __libc_start_main
   │     ├── 运行 .init / 全局构造（C++）
   │     ├── 调用 main(argc, argv, envp)
   │     └── main 返回后调用 exit()
4. exit() → atexit 清理 → 刷新 stdio → _exit() syscall → 内核回收
```

> **关键认知**：`main` 不是真正的入口，ELF 的 `e_entry` 指向 `_start`；`main` 只是"用户代码的入口"。`readelf -h app | grep Entry` 能看到真实入口地址。详见 **ch18**。

## ELF 段与变量住在哪里

```
高地址
┌──────────────┐
│ 栈 stack ↓    │  局部 auto 变量、调用帧（向下生长）
├──────────────┤
│ (空闲)        │
├──────────────┤
│ 堆 heap ↑    │  malloc/calloc 分配（向上生长）
├──────────────┤
│ .bss         │  未初始化全局/静态，加载时清零（不占文件空间）
├──────────────┤
│ .data        │  已初始化全局/静态
├──────────────┤
│ .rodata      │  字符串字面量、const 全局（只读，写→SIGSEGV）
├──────────────┤
│ .text        │  机器码（只读可执行）
└──────────────┘
低地址
```

| 声明方式 | 落在哪个段 | 生命周期 | 初始值 |
|---------|-----------|---------|--------|
| `int x;`（函数内 auto） | **栈** | 函数返回即销毁 | **未初始化（不定值）** |
| `static int x;`（函数内） | .bss/.data | 整个进程 | **0** |
| `int x;`（全局） | .bss/.data | 整个进程 | **0** |
| `int x = 5;`（全局） | .data | 整个进程 | 5 |
| `const int x = 5;`（全局） | .rodata | 整个进程 | 5（只读） |
| `malloc(...)` | **堆** | `free` 才回收 | **未初始化** |
| `"hello"`（字符串字面量） | .rodata | 整个进程 | "hello"（只读） |

### `.bss` 清零机制（重要）

- `.bss` 段在 **ELF 文件里不占空间**——只记录大小和起始地址
- 加载时，内核/loader 把这片内存**清零**
- 所以"未初始化的全局/static 变量是 0"——这是**加载器保证的**，不是编译器
- 嵌入式裸机/某些 RTOS 不一定有这个清零步骤——所以嵌入式代码常显式初始化全局变量

### 栈上 auto 变量不清零（陷阱根源）

```c
void f(void) {
    int x;        /* 栈上，未初始化 */
    printf("%d\n", x);   /* UB：值不定，可能是上次函数留下的脏数据 */
}
```

- 栈内存被反复复用——这次 `f` 的 `x` 用的可能是上次某个函数用过的同一片栈
- C 标准：读取未初始化 auto 变量是 **UB**（未定义行为）
- 实际表现：可能恰好是 0、可能是垃圾值、可能每次不同
- **报文解析、临时缓冲必须初始化**——`int x = 0;` 或 `memset`

### 堆的真相：brk 与 mmap（malloc 的底层）

malloc 不是系统调用，是 glibc 在两个 syscall 之上做的分配器：

| 分配大小 | 底层机制 | 特点 |
|---------|---------|------|
| 小块（默认 < 128KB） | `brk`/`sbrk` 抬高 program break | 堆紧贴 .bss **连续生长**，释放后内存留在 glibc free list 复用 |
| 大块（≥ 128KB） | `mmap(NULL, size, PROT_RW, MAP_ANON|MAP_PRIVATE)` | 独立映射，`free` 时直接 `munmap` **归还内核** |

- **"free 了 RSS 不降"的经典现象**：小块走 `brk`，只有堆顶的内存才可能收缩归还；中间释放的块留在 glibc 空闲链表里，`/proc/<pid>/status` 的 VmRSS 不变——HFT 内存监控必知
- 多线程：glibc 主 arena 用 `brk`，per-thread arena 用 `mmap`——减少 malloc 锁竞争的手段
- 验证：`strace ./app` 观察 `brk(NULL)`/`brk(0x...)`/`mmap` 序列；阈值可用 `MALLOC_MMAP_THRESHOLD_` 环境变量调整
- DPDK/HFT 常直接绕开 malloc：启动时 `mmap` hugepage 预分配内存池，热路径零分配

## 执行模型：顺序执行

- 默认**顺序执行**语句，一条接一条
- 控制语句（`if`/`for`/`while`/`switch`/`goto`）改变执行流（ch04）
- `goto` 的标签**仅函数作用域**——不能跨函数 goto
- 函数调用：压返回地址、建新栈帧、跳转；`return` 销毁栈帧、恢复返回地址（详见 ch18.1.3）
- 多线程：每个线程有自己的栈，但共享 .data/.bss/heap——这是数据竞争的根源

## 为什么"执行环境"对 HFT 至关重要

| 现实问题 | 执行环境机制 |
|---------|------------|
| 程序跑一段时间崩溃，栈指向已释放内存 | 堆/栈生命周期错配 → 悬垂指针 |
| 大局部数组崩溃 | 栈空间有限（默认 8MB）→ 栈溢出 SIGSEGV |
| 多线程数据竞争 | 栈独立但 .data/heap 共享 → 需锁/原子 |
| 修改字符串字面量崩溃 | .rodata 只读 → SIGSEGV |
| 全局变量"莫名是 0" | .bss 加载清零机制 |
| 局部变量"莫名是垃圾" | 栈 auto 不清零 |
| DPDK worker 栈太小 | DPDK 给 worker 的栈可能远小于 8MB → 需配置 |

### HFT 实战：内存位置的选择

- **热路径缓冲**：预分配静态/堆，避免运行时 malloc 抖动
- **per-CPU 数据**：放结构体数组，按 CPU id 索引——避免跨核 cache line 共享（伪共享）
- **栈上小对象**：可以用，但别太大；注意不要返回其地址
- **报文元数据**：DPDK mbuf 池预分配在 hugepage，不是栈/普通堆

## 查看工具

```bash
readelf -S ./app          # 看所有 section（.text/.data/.bss 位置大小）
readelf -l ./app          # 看 Program Headers（运行时如何映射）
size ./app                # 看 text/data/bss 大小概览
cat /proc/<pid>/maps      # 看运行时进程的内存映射
pmap <pid>                # 进程内存映射的可读版
```

- `size ./app` 输出 `text data bss dec hex`——快速判断哪段大
- `/proc/<pid>/maps` 看运行时实际映射，能发现 hugepage、mmap 区域

## 常见误区

### 返回栈地址 vs 返回堆地址

```c
/* ❌ 返回栈上局部变量地址——悬垂指针 */
int *bad_fun(void)
{
    int tmp = 100;   /* 栈上，函数返回即销毁 */
    return &tmp;     /* 返回已销毁内存的地址 */
}

/* ✅ 返回堆上 malloc 地址——安全 */
int *good_fun(void)
{
    int *p = malloc(sizeof(int));  /* 堆上，不随函数返回销毁 */
    *p = 100;
    return p;       /* 安全：堆内存直到 free() 才释放 */
}
```

| | 栈上局部变量 | 堆上 malloc |
|---|---|---|
| 生命周期 | 函数返回即销毁 | 直到 `free()` 才释放 |
| 返回其地址 | **悬垂指针** | **安全** |
| 谁管理 | 编译器自动 | 程序员手动 |
| 翻译环境 | 语法合法，不报错 | 语法合法 |
| 执行环境 | ❌ 访问已销毁内存 | ✅ 内存仍有效 |

**根本原因**：栈帧是函数私有的，函数退出就还给栈；堆是进程级共享池，不归任何函数管，必须显式释放。返回 `malloc` 的指针安全，但**调用者负责 `free`**——忘了就是内存泄漏。

### 其他常见误区

| 误区 | 纠正 |
|------|------|
| 局部变量默认是 0 | 只有 .bss 的全局/static 清零；栈 auto 不清零 |
| `malloc` 返回的内存清零 | `malloc` 不清零；要清零用 `calloc` 或 `memset` |
| 字符串字面量可以修改 | 在 .rodata，修改是 UB，通常 SIGSEGV |
| `main` 是程序第一个执行的代码 | `_start` 和 crt0 先执行；全局构造更早 |
| 栈很大随便开大数组 | 默认 8MB，DPDK worker 栈可能更小 |
| 堆和栈会"相遇" | 现代系统有 ASLR 和 guard page，相遇会段错误而非默默覆盖 |

## 实操

1. `readelf -S ./app` 看 .text/.data/.bss 的位置和大小
2. `readelf -l ./app` 看 Program Headers，理解运行时映射
3. `size ./app` 对比不同程序的段大小
4. 写一个读未初始化局部变量的程序，多跑几次看值是否变化

7. `cat /proc/self/maps` 看当前进程的内存映射

## 代码自测

**题目 1：** 以下代码的行为是定义的还是未定义的？为什么？
```c
int a = 1;
a = a++ + 1;
```

<details>
<summary>参考答案</summary>

未定义行为（UB）。a = a++ + 1 中，a 在同一个序列点内被修改两次（一次是 a++ 的副作用，一次是 a = ... 的赋值），C 标准没有规定这两个修改的顺序。不同编译器可能产生不同结果。正确写法是拆成两步。

</details>

**题目 2：** 程序里 `malloc(1MB)` 后立刻 `free`，`/proc/self/status` 的 VmRSS 一定下降吗？

<details>
<summary>参考答案</summary>

不一定，取决于分配走哪条路：

- 1MB ≥ 默认阈值（128KB）→ 走 `mmap`，`free` 时 `munmap` **会归还**，RSS 下降
- 但如果分配的是很多小块（如 100 万个 1 字节 + 开销）→ 走 `brk`，释放后留在 glibc 空闲链表，**RSS 不降**
- 另外 glibc 有 mmap 阈值动态调整：释放过大的 mmap 块会抬高阈值，之后同样大小改走 `brk`——"第一次 free 降、第二次不降"就是它

验证：`strace` 看 `brk`/`mmap` 调用序列。

</details>
