# 3.5.3 原型

## 本节讲什么

**函数原型作用域(function prototype scope)**:函数原型(声明)参数列表里的参数名,只在该原型声明的括号内有效,与函数体无关。这是 C 四种作用域里范围最窄、最容易被忽视的一种,但它影响 API 风格、头文件文档化、以及"参数名省不省"的工程决策。

## 从零讲起:原型是什么,为什么参数名只是摆设

**第一步:原型是给编译器的"名片"。** 编译器从上往下读代码,规矩是用一个名字前必须先见过它:

```c
int main(void)
{
    int result = add(1, 2);   /* 报错! 编译器还没见过 add */
    return 0;
}
int add(int a, int b){ return a + b; }   /* 定义在下面, 已经晚了 */
```

解决办法:在用之前先打招呼——

```c
int add(int a, int b);        /* ← 原型: "后面有个 add, 吃两个 int, 吐一个 int" */

int main(void)
{
    int result = add(1, 2);   /* 编译器: 打过招呼了, 放行 */
    return 0;
}
int add(int a, int b){ return a + b; }
```

**第二步:原型里的 a、b 不是变量,是摆设。** 编译器看原型只数"两个 int 进、一个 int 出",名字根本不看:名字删掉(`int add(int, int);`)合法,换名字(`int add(int x, int y);`)也合法。真正干活的参数是**定义**那行的 a、b(它们属于块作用域,跟着函数体走)。

**第三步:"原型作用域"说的就是摆设的寿命。** 摆设名字的有效范围 = 那一对括号,右括号一关立刻人间蒸发——不出现在内存里、不占空间、函数运行时与它们毫无关系。

一句话:**原型括号里的名字是写在名片上的花名,名片看完就扔;C 专门给这些花名定了个作用域,叫原型作用域。**

## 要点

### 原型作用域的边界

```c
void swap(int a, int b);          /* a, b 仅在此括号内有效, 出括号即销 */

void swap(int x, int y)           /* 定义处的 x, y 是新的块作用域参数 */
{
    /* 这里用 x, y, 不是 a, b */
}
```

- 原型里的参数名与定义里的参数名**可以不同**(甚至省略)—— 它们是不同作用域的不同标识符
- 原型参数名的作用域"原型括号内",出括号即不可见,也不与函数体内同名冲突

### 参数名可省

```c
void parse(const uint8_t *, size_t);    /* 省略参数名, 合法 */
void parse(const uint8_t *pkt, size_t len);   /* 保留参数名, 文档化 */
```

- 两种写法**语义完全等价**,编译器只看类型
- 省略适合"类型本身已自解释"的简单 API;保留适合"类型名不足以表达语义"的复杂 API

### 原型作用域的边界场景

```c
/* 参数名作用域极窄: 这两个原型参数名重复也合法 */
void f(int x, int x);     /* 约束违反? 实际: 同一作用域重名, 报错 */
void g(int x);            /* ok */
void g(int y);            /* ok, 不同原型参数名独立 */
```

- **同一原型里**两个参数同名 → 约束违反报错
- **不同原型**参数名可不同,各自独立作用域

### 原型 vs 定义

```c
/* 原型 */
int max(int a, int b);

/* 定义 —— 参数名可与原型不同 */
int max(int lhs, int rhs) {
    return lhs > rhs ? lhs : rhs;
}
```

- 编译器只校验**类型签名**匹配,参数名不校验
- 这意味着头文件原型和 `.c` 定义的参数名可以不一致 —— 但工程上**应当一致**,避免文档与实现脱节

## 与 HFT/DPDK

### 头文件文档化(保留参数名)

```c
/* DPDK 风格: 头文件保留参数名, 配合注释做 API 文档 */
/**
 * 收包爆发式拉取
 * @param port_id   端口 ID
 * @param queue_id  收队列 ID
 * @param rx_pkts   输出 mbuf 数组
 * @param nb_pkts   最多拉取个数
 * @return 实际拉到的包数
 */
uint16_t rte_eth_rx_burst(uint16_t port_id, uint16_t queue_id,
                          struct rte_mbuf **rx_pkts, const uint16_t nb_pkts);
```

- 现代驱动框架文档生成(Doxygen)依赖参数名注释
- 类型名 `uint16_t` 不能表达"端口 ID"语义,参数名 + 注释才能

### 省略参数名的场景

```c
/* 内部简单回调签名, 类型自解释 */
typedef void (*free_fn)(void *);       /* 省略参数名, 强调"释放任意对象" */
typedef int  (*cmp_fn)(const void *, const void *);
```

- 类型已自解释的通用回调,省略参数名让签名更"抽象"
- 工程惯例:**对外 API 保留参数名**,**通用回调 typedef 可省略**

### 函数指针 typedef 的原型作用域

```c
typedef void (*pkt_cb)(const uint8_t *pkt, size_t len, void *user);
/* pkt, len, user 仅在此 typedef 括号内有效, 后续用 pkt_cb 时它们已不可见 */
```

- typedef 里的参数名也只作文档,不影响类型

## 常见误区

| 误区 | 真相 |
|------|------|
| 原型参数名必须与定义一致 | 不必,编译器只看类型 |
| 省略参数名的原型不合法 | 合法,语义与保留完全等价 |
| 同一原型两个参数同名合法 | 不,约束违反报错 |
| 原型参数名在函数体内可见 | 不,原型作用域仅括号内 |
| 头文件省参数名更"干净" | 取舍:可读性下降,API 文档生成困难 |

## 实操

```bash
cat > t.c <<'EOF'
#include <stdio.h>
void f(int, int);              /* 省参数名 */
void f(int a, int b){ printf("%d %d\n", a, b); }  /* 定义参数名 a,b */
int main(void){ f(1, 2); return 0; }
EOF
gcc -std=c11 -Wall t.c -o t && ./t   # 1 2

# 同一原型两个参数同名会报错:
cat > bad.c <<'EOF'
void g(int x, int x);
EOF
gcc -std=c11 -c bad.c   # error: redefinition of parameter 'x'
```

## 代码自测

**题目 1：** 以下函数声明中，参数名 n 的作用域是什么？
```c
int factorial(int n);
```

<details>
<summary>参考答案</summary>

n 的作用域仅限于这个原型声明，出了声明就不可用。原型中的参数名只是文档作用，编译器会忽略它。所以 int factorial(int); 和 int factorial(int n); 完全等价。但写上参数名是好习惯——提高可读性。

</details>
