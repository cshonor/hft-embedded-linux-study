# 14.4.1 函数库文件

## 本节讲什么

`#include <header.h>` 用尖括号包含系统头文件和第三方库头。这一节给出 `<...>` 的搜索路径机制、头文件与库链接的关系、HFT 工程里 DPDK/内核 UAPI 头文件的实际部署形态。

认知锚点：`<...>` 不是「特殊的 include」，而是**搜索路径不同**的 include。理解搜索路径，才能理解为什么 `#include <rte_mbuf.h>` 需要 `-I/opt/dpdk/include`，才能排查「找不到头文件」的编译错误。

## 要点

### `<...>` 的搜索路径

```c
#include <stdio.h>          /* C 标准库 */
#include <stdint.h>         /* C99 标准整数类型 */
#include <pthread.h>        /* POSIX 线程 */
#include <linux/if_ether.h> /* 内核 UAPI */
#include <rte_mbuf.h>       /* DPDK 第三方库 */
```

搜索顺序（典型 Linux/GCC）：

1. **`-I` 指定的路径**（命令行 `-I/opt/dpdk/include`）
2. **系统标准路径**：`/usr/include`、`/usr/local/include`、`/usr/include/x86_64-linux-gnu/`
3. **编译器内置路径**：`/usr/lib/gcc/x86_64-linux-gnu/13/include/`

```bash
# 查看系统 include 路径
gcc -E -Wp,-v - < /dev/null
# 输出类似：
# #include "..." search starts here:
# #include <...> search starts here:
#  /usr/include
#  /usr/local/include
#  /usr/lib/gcc/...

# 查找特定头文件位置
gcc -M foo.c | grep rte_mbuf   # 显示依赖路径
locate rte_mbuf.h
dpkg -L libdpdk-dev | grep rte_mbuf.h
```

### `<...>` vs `"..."` 的本质区别

```c
#include <stdio.h>      /* 系统头：不搜当前目录 */
#include "my_header.h"  /* 本地头：先搜当前目录 */
```

| 维度 | `<...>` | `"..."` |
|------|---------|---------|
| 当前目录 | 不搜 | 先搜 |
| `-I` 路径 | 搜 | 搜（当前目录之后） |
| 系统路径 | 搜 | 搜（最后） |
| 语义暗示 | 「这是外部库/系统头」 | 「这是工程内部头」 |
| 工程实践 | libc、DPDK、第三方库 | 工程私有头文件 |

**语义暗示**是工程约定——`<...>` 告诉读者「这是外部依赖」，`"..."` 告诉读者「这是工程内部」。虽然技术上 `<...>` 也能搜当前目录（用 `-I.` 配合），但破坏约定。

### 系统标准库头文件

```c
#include <stdio.h>      /* I/O：printf、fopen */
#include <stdlib.h>     /* 通用：malloc、exit、atoi */
#include <string.h>     /* 字符串：memcpy、strcpy */
#include <stdint.h>     /* C99 整数类型：uint32_t、int64_t */
#include <stdbool.h>    /* C99 bool 类型 */
#include <stddef.h>     /* size_t、ptrdiff_t、NULL */
#include <errno.h>      /* 错误码 */
#include <math.h>       /* 数学函数 */
```

这些头文件提供 C 标准库的声明，链接时自动连接 libc（`-lc` 通常默认）。位置在 `/usr/include/`，由 libc-dev 包提供。

### POSIX 头文件

```c
#include <pthread.h>    /* 线程：pthread_create */
#include <unistd.h>     /* UNIX 标准：read、write、fork */
#include <fcntl.h>      /* 文件控制：open、O_RDONLY */
#include <sys/socket.h> /* 套接字 */
#include <netinet/in.h> /* 网络地址 */
#include <arpa/inet.h>  /* inet_pton、htonl */
#include <sys/mman.h>   /* 内存映射：mmap */
#include <sys/epoll.h>  /* epoll */
```

POSIX 头文件在 `/usr/include/` 和 `/usr/include/x86_64-linux-gnu/`，由 glibc-dev / libc-dev 提供。`<sys/*.h>` 是系统相关的 POSIX 头。

### 内核 UAPI 头文件

```c
#include <linux/if_ether.h>   /* ETH_P_ALL、ethhdr */
#include <linux/ip.h>         /* iphdr */
#include <linux/tcp.h>        /* tcphdr */
#include <linux/udp.h>        /* udphdr */
#include <linux/if_packet.h>  /* sockaddr_ll */
#include <linux/version.h>    /* LINUX_VERSION_CODE */
```

**内核 UAPI（Userspace API）头文件**在 `/usr/include/linux/`，提供内核对用户态的稳定接口。HFT 报文解析直接用这些头，不需要手写协议结构。这些头由 `linux-libc-dev` 包提供，与内核版本对应。

```c
/* 使用内核 UAPI 头解析报文 */
#include <linux/if_ether.h>
#include <linux/ip.h>

const uint8_t *pkt = rte_pktmbuf_mtod(mbuf, const uint8_t *);
const struct ethhdr *eth = (const struct ethhdr *)pkt;
const struct iphdr *ip = (const struct iphdr *)(pkt + sizeof(*eth));

if (eth->h_proto == htons(ETH_P_IP)) {
    /* 处理 IP 报文 */
}
```

### 第三方库头文件

```c
#include <rte_mbuf.h>       /* DPDK mbuf */
#include <rte_ethdev.h>     /* DPDK 以太网设备 */
#include <rte_mempool.h>    /* DPDK 内存池 */
#include <jansson.h>        /* JSON 解析 */
#include <openssl/sha.h>    /* SHA 哈希 */
```

第三方库头文件通过 `-I` 指定搜索路径：

```bash
gcc -I/opt/dpdk/include -I/usr/local/include -c foo.c
```

或用 `pkg-config` 自动获取路径：

```bash
gcc $(pkg-config --cflags libdpdk) -c foo.c
gcc $(pkg-config --cflags jansson) -c foo.c
```

### 头文件 vs 库链接

```c
/* 头文件：声明 */
#include <rte_mbuf.h>
struct rte_mbuf *m = rte_pktmbuf_alloc(pool);
```

**头文件提供声明，库链接提供实现**：

| 阶段 | 工具 | 作用 |
|------|------|------|
| 预处理 | cpp | 把 `#include` 展开，得到完整翻译单元 |
| 编译 | gcc -c | 翻译单元 → 目标文件（`.o`），只检查声明 |
| 链接 | ld | 把目标文件 + 库（`.a`/`.so`）合并成可执行文件 |

```bash
# 编译阶段：只需要头文件
gcc -I/opt/dpdk/include -c foo.c -o foo.o

# 链接阶段：需要库文件
gcc foo.o -lrte_mbuf -lrte_eal -o foo
# 或用 pkg-config
gcc foo.o $(pkg-config --libs libdpdk) -o foo
```

**「找不到头文件」是编译期错误**，**「找不到符号」是链接期错误**。前者用 `-I` 解决，后者用 `-L` + `-l` 解决。

### 静态库 vs 动态库

```bash
# 静态库：libfoo.a，链接时把代码拷贝进可执行文件
gcc foo.o -lfoo -o foo     # 链接 libfoo.a

# 动态库：libfoo.so，运行时动态加载
gcc foo.o -lfoo -o foo     # 优先链接 .so，找不到则 .a
ldd foo                    # 查看运行时依赖的 .so
```

| 维度 | 静态库 `.a` | 动态库 `.so` |
|------|-------------|---------------|
| 链接方式 | 代码拷贝进可执行 | 运行时加载 |
| 可执行文件大小 | 大 | 小 |
| 启动速度 | 快 | 稍慢（需加载 .so） |
| 升级 | 需重新链接 | 替换 .so 即可 |
| HFT 偏好 | **静态库**（避免运行时解析开销） | 管理面可用 |

HFT 数据面倾向静态链接——避免动态库的 PLT/GOT 间接跳转开销，减少启动依赖。DPDK 通常静态链接到应用里。

## HFT 关联

### DPDK 头文件部署

```bash
# DPDK 安装后的头文件位置
ls /opt/dpdk/include/rte_*.h
# rte_mbuf.h、rte_ethdev.h、rte_mempool.h、rte_ring.h、...

# 编译时指定
gcc -I/opt/dpdk/include -c my_app.c

# 或用 pkg-config
gcc $(pkg-config --cflags libdpdk) -c my_app.c

# 链接
gcc my_app.o $(pkg-config --libs libdpdk) -o my_app
```

DPDK 通过 `pkg-config --cflags libdpdk` 自动给出 `-I` 路径和必要宏定义，是工程标准做法。

### 内核 UAPI 直接使用

```c
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/tcp.h>

static inline void parse_packet(struct rte_mbuf *m)
{
    const uint8_t *data = rte_pktmbuf_mtod(m, const uint8_t *);
    const struct ethhdr *eth = (const struct ethhdr *)data;
    const struct iphdr *ip = (const struct iphdr *)(data + ETH_HLEN);
    /* ... */
}
```

HFT 报文解析直接用内核 UAPI 头定义的结构，避免手写协议结构出错。`ETH_HLEN`、`IPPROTO_TCP` 等常量也来自这些头。

### 系统头版本的编译期检查

```c
#include <linux/version.h>

#if LINUX_VERSION_CODE < KERNEL_VERSION(5, 4, 0)
    #error "Linux kernel >= 5.4 required"
#endif

#include <linux/if_ether.h>
/* 使用 5.4+ 才有的特性 */
```

跨内核版本部署时，编译期检查版本号，避免运行时崩溃。

### DPDK 版本检查

```c
#include <rte_version.h>

#if RTE_VERSION < RTE_VERSION_NUM(21, 11, 0, 0)
    #error "DPDK >= 21.11 required"
#endif

#include <rte_mbuf.h>
/* 使用 21.11+ 的 API */
```

DPDK 不同版本 API 有变化，编译期检查版本号保证兼容性。

### 头文件与 ABI 稳定性

```c
/* 内核 UAPI 头文件承诺 ABI 稳定：用户态代码不会因内核升级而失效 */
#include <linux/if_ether.h>   /* 结构布局跨内核版本稳定 */

/* DPDK 头文件不承诺 ABI 稳定：版本升级可能破坏二进制兼容 */
#include <rte_mbuf.h>          /* 结构布局可能随版本变化 */
```

**内核 UAPI 是 ABI 稳定的**——结构布局、常量值跨版本不变，用户态代码不需重编译。**DPDK 不承诺 ABI 稳定**——升级 DPDK 版本通常需要重新编译应用。HFT 升级 DPDK 时必须全量重编译。

## UB 边界

| 情形 | 后果 | 防护 |
|------|------|------|
| 找不到头文件 | 编译错误 | 检查 `-I` 路径、安装依赖包 |
| 头文件版本不匹配 | 编译通过但行为异常 | 编译期版本检查 |
| 头文件声明与库实现不一致 | 链接错误或运行时崩溃 | 头库版本对齐 |
| 系统头被本地头覆盖 | 非预期行为 | 不要在工程内建与系统同名的头 |
| 多版本库共存 | 链接到错误版本 | 显式 `-I` 和 `-L` 路径 |

### 头文件覆盖陷阱

```c
/* 工程内建了 string.h（错误做法） */
/* my_project/string.h */
size_t strlen(const char *s) { /* 错误实现 */ }

/* foo.c */
#include "string.h"   /* 意图包含系统 string.h，却包含本地 */
strlen("hello");      /* 错误实现，UB */
```

**不要在工程内建与系统/标准库同名的头文件**。如果必须，用子目录隔离（`#include "myproject/string.h"`）。
