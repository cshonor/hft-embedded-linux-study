7.1

基础整型宽度不固定

本节讲什么

C 标准只保证 char ≤ short ≤ int ≤ long ≤ long long 及 sizeof(char)==1，不 规定各类型固定字节数。同一份代码在 32/64 位、MCU 与服务器上，int/long 宽度可能不同，导致溢出、截断、结构体布局变化。

要点

平台 典型 int 典型 long
32 位 x86 4 4
64 位 Linux LP64 4 8
部分 16 位 MCU 2 4 
long timestamp;   /* 32 位 long 存不下 64 位时间戳 */

移植规范

跨平台固定位宽 一律 <stdint.h>：

#include <stdint.h>
uint8_t   u8;
int32_t   i32;
uint64_t  ts;

size_t / ptrdiff_t 用于大小与指针差；不要 假设 int 与指针同宽。

题目 1： 以下代码在不同平台上行为如何？

int x = 100000;
参考答案

16 位 int 平台上溢出（INT_MAX = 32767）。C 标准只保证 int 至少 16 位。可移植代码应使用 <stdint.h> 的固定宽度类型：int32_t（恰好 32 位）、int_least32_t（至少 32 位）。或用 long（至少 32 位）。不要假设 int 的大小——用 sizeof 或 UINTPTR_WIDTH 检查。

7.2

char 默认 signed / unsigned 差异

本节讲什么

char 的 符号性由实现定义：x86 GCC 多为 signed char；部分 ARM 工具链默认 unsigned char。用裸 char 存二进制字节、串口数据时，跨平台比较 c < 0、扩展为 int 的结果可能相反。

要点

char c = 0x80;
if (c < 0) { }   /* x86 signed char：真；unsigned char 平台：假 */
类型 0x80 作为 int 提升后（典型）
signed char 负数（-128）
unsigned char 128

规范

  • 文本字符：可用 char
  • 二进制字节：unsigned char 或 uint8_t
  • 需要负数语义：显式 signed char

与 ch05 5.4 isprint((unsigned char)ch) 一致。

代码自测

题目 1： 以下代码在不同平台上行为如何？

char c = 200;
if (c > 128) { ... }
参考答案

char 的符号性是实现定义的——可能是 signed char（-128~127）或 unsigned char（0~255）。如果 char 是 signed，c = 200 回绕为 -56，c > 128 为 false。如果 unsigned，c = 200，c > 128 为 true。可移植代码应显式声明 unsigned char 或 signed char。<limits.h> 中 CHAR_BIT 是每字节位数。

7.3

大小端（字节序）

本节讲什么

多字节整数在内存中的 字节排列顺序 因 CPU 而异：x86/x86_64 多为 小端（低字节在低地址）；网络协议、部分 PowerPC/ARM 配置为 大端。直接把 uint8_t buf[] 强转为 uint32_t* 读取，跨架构数值颠倒。

要点

uint8_t buf[4] = { 0x12, 0x34, 0x56, 0x78 };
uint32_t val = *(uint32_t *)buf;   /* 结果依赖本机字节序 */

规范

跨设备二进制协议：

#include <arpa/inet.h>   /* POSIX */
uint32_t net = htonl(host);
uint32_t host = ntohl(net);

Windows 用 winsock2.h 同名函数。Wire format 永远按协议字节序 逐字段解析，勿 memcpy 到结构体指望布局一致。

代码自测

题目 1： 以下代码在大端和小端机器上输出什么？

int x = 1;
char* p = (char*)&x;
if (*p == 1) printf("little-endian");
else printf("big-endian");
参考答案

小端（x86/ARM 默认）：低位字节存在低地址，*p == 1 为 true。 大端（PowerPC/SPARC）：高位字节存在低地址，*p == 0。 网络字节序是大端（htonl/ntohl 转换）。文件格式和数据协议需要指定字节序。ARM 可配置大小端。用 union 或指针转换检测字节序。

7.4

结构体对齐与 padding

本节讲什么

编译器按 对齐要求 在结构体成员间插入填充字节；规则因 CPU（x86 宽松 vs ARM/MIPS 严格）、编译器、#pragma pack 而异。用结构体 直接映射 硬件寄存器或网络报文，换平台后偏移错位、未对齐访问崩溃。

要点

struct Test {
    char a;
    int  b;
};
/* 常见 LP64：sizeof=8，offsetof(b)=4，a 后填充 3 字节 */

风险

  • #pragma pack(1) 取消填充 → ARM 上 int 未对齐加载 SIGBUS
  • 不同编译器 pack 默认值不同 → 二进制不兼容

规范

  • 硬件寄存器：显式 uint32_t 字段 + static_assert(offsetof(...) == 期望)
  • 网络协议：逐字节 解析，或 memcpy + ntoh* 逐字段
  • 序列化格式文档化 padding，不依赖「自然对齐」

代码自测

题目 1： 以下结构体在不同编译器上大小可能不同，为什么？

struct S {
    char a;     // 1 byte
    int b;      // 4 bytes
    char c;     // 1 byte
};
sizeof(struct S);  // ?
参考答案

可能是 12 字节（常见）或 6 字节（packed）。编译器在成员之间插入填充字节（padding）保证对齐——a 后填 3 字节让 b 对齐到 4 字节边界，c 后填 3 字节让结构体大小是 4 的倍数。__attribute__((packed)) 或 #pragma pack(1) 禁止填充。对齐影响性能和 ABI 兼容性。跨平台协议结构体应显式指定对齐或用序列化。

7.5

指针宽度随架构变化

本节讲什么

32 位系统指针 4 字节，64 位 8 字节。用 int 保存指针在 32 位「碰巧能跑」，64 位 截断高 32 位，句柄/回调/内核 user pointer 全面失效。

要点

void *buf = malloc(64);
int addr = (int)(uintptr_t)buf;   /* 64 位：截断，灾难 */

规范

#include <stdint.h>
uintptr_t u = (uintptr_t)ptr;
void *p = (void *)u;
  • 指针 ↔ 整数：uintptr_t / intptr_t
  • 不要用 unsigned long 代替（LP64 下 long 8 字节但 Windows LLP64 下 4 字节）

代码自测

题目 1： 以下代码在 32 位和 64 位平台上有什么不同？

int* p = malloc(100);
printf("%d\n", (int)p);  // 把指针转 int
参考答案

32 位平台：指针 4 字节，转 int 安全。64 位平台：指针 8 字节，int 4 字节——截断高位，指针值错误。应使用 intptr_t/uintptr_t（<stdint.h>）：

printf("%" PRIdPTR "\n", (intptr_t)p);

intptr_t 保证能安全存放指针值的整数类型。

7.6

有符号右移未标准化

本节讲什么

对 负整数 右移，标准 未规定 算术右移（高位补符号位）还是逻辑右移（高位补 0）。GCC/Clang 对 int 多为算术右移；不可移植代码依赖 -1 >> 1 == -1 在陌生编译器上可能失败。

要点

int x = -1;
x >> 1;
/* GCC x86：常仍为 -1（算术右移）
   假设逻辑右移：可能变成 INT_MAX 量级正数 */

规范

需要可移植位操作时：

uint32_t u = (uint32_t)(int32_t)x;
u >>= 1;

或显式掩码、无符号类型完成逻辑移位；避免 对 signed 类型做依赖符号扩展的 >>。

代码自测

题目 1： 以下代码在不同平台上结果可能不同，为什么？

int x = -8;
int y = x >> 1;  // 结果是？
参考答案

有符号数右移行为是实现定义：1) 算术右移（符号位填充）：-8 >> 1 = -4（保持符号）；2) 逻辑右移（0 填充）：-8 >> 1 = 2147483644（大正数）。x86 通常用算术右移。无符号数右移总是逻辑右移（0 填充），行为确定。可移植代码应避免依赖有符号右移的行为——用除法或无符号操作替代。

7.7

信号、库函数与 OS 差异

本节讲什么

「C 标准库」与 POSIX / Win32 / RTOS API 边界模糊。直接调用 fork、mmap、sigaction、路径分隔符、换行符等 Linux 专属 接口，代码无法编译或运行在 Windows、裸机、裁剪 libc 的嵌入式环境。

要点

能力 Linux/POSIX Windows 裸机/RTOS
进程 fork 有 无 无
mmap 有 不同 API 无
换行 \n \r\n 文本模式 视终端
完整 libc 通常有 MSVC/UCRT 常裁剪

规范

  • 可移植层：仅依赖 C 标准 + 明确抽象的平台头（my_os.h）
  • 条件编译：#ifdef _WIN32 / __linux__ 隔离平台代码
  • 嵌入式：确认 malloc/printf 是否链接、是否线程安全

代码自测

题目 1： 以下代码在 Windows 和 Linux 上有什么区别？

// Windows
#include <windows.h>
Sleep(1000);  // 毫秒
// Linux
#include <unistd.h>
sleep(1);     // 秒
usleep(1000000); // 微秒
参考答案

平台 API 不同——Windows 用 Sleep（毫秒），Linux 用 sleep/usleep/nanosleep。可移植做法：1) 用条件编译 #ifdef _WIN32；2) 用跨平台库（如 SDL/Boost）。其他常见差异：文件路径分隔符（\ vs /）、换行符（\r\n vs \n）、线程 API（pthread vs Windows threads）。

7.8

浮点实现差异

本节讲什么

float/double 的 精度、舍入、异常 partly 由 IEEE 754 与实现决定；无 FPU 的 MCU 用软件浮点，性能与误差与 x86 硬件 FPU 不同。跨平台用 == 比较浮点、依赖 NaN/Inf 比较顺序，易静默失败。

要点

  1. 精度：float 约 7 位有效十进制；累积误差
  2. 无 FPU：double 运算慢数个数量级
  3. NaN / Inf：x != x 为真（NaN）；不同 lib 对 printf 输出可能不同
int x = sqrt(4);   /* 截断小数，见 ch05 5.6 */

规范

  • 比较：fabs(a-b) < epsilon 或整数定点运算
  • 关键路径：嵌入式优先 定点 / 整数
  • 链接 -lm 见 ch05 5.6

与后续衔接

  • ch05：sqrt、-lm
  • ch03：有符号/无符号与转换

代码自测

题目 1： 以下代码在不同平台上结果可能不同，为什么？

double x = 0.1 + 0.2;
if (x == 0.3) printf("equal");
else printf("not equal");
参考答案

浮点精度问题——0.1 + 0.2 在 IEEE 754 double 中不精确等于 0.3（约为 0.30000000000000004）。不同平台/编译器的浮点运算顺序可能不同（如 x87 80 位 vs SSE 64 位），导致微小差异。正确比较：if (fabs(x - 0.3) < EPSILON)。HFT 场景对浮点精度和一致性要求高，应固定编译器选项和运算顺序。

7.9

内存地址空间与 NULL

本节讲什么

标准规定 NULL 是 空指针常量（实现为 (void*)0 等）。但 解引用 NULL 是否崩溃、地址 0 是否可用于映射，由 操作系统与 MMU 决定。在「0 地址可读」的老式系统上通过的 bug，移植到 Linux/x86 才变成 SIGSEGV。

要点

int *p = NULL;
*p = 1;   /* 现代 Linux：SIGSEGV；极少数嵌入式：可能不崩 */

规范

  • 从不 解引用 NULL；不假设「NULL 访问必崩」来做逻辑（防御性编程仍要判空）
  • 内核/驱动：用户态指针与 NULL 检查是安全边界
  • 函数指针、句柄与数据指针统一判空

与后续衔接

  • ch05 5.1：printf("%s", NULL)

代码自测

题目 1： NULL 在 C 中是什么？以下代码有什么问题？

#define NULL ((void*)0)
int* p = NULL;
if (p == 0) { ... }   // 合法吗？
参考答案

NULL 在 C 中通常定义为 ((void*)0)。p == 0 合法——0 是空指针常量，可以与任何指针比较。但 memset(ptr, 0, sizeof(ptr)) 把指针清零不等于设为 NULL（虽然绝大多数平台上 NULL 的位模式全零）。C 标准不保证空指针的位模式是全零——它只保证 NULL 不等于任何有效指针。用 p = NULL 而非 memset(&p, 0, sizeof(p))。

7.10

预处理器平台宏差异

本节讲什么

识别 CPU/OS 的预定义宏 无单一标准；直接写死 __x86_64__ 在 MSVC 上不存在，写 _WIN32 在 Linux 上无效。 scattered #ifdef 导致维护噩梦。

要点

编译器/平台 常见宏
GCC x86_64 __x86_64__, __GNUC__
GCC ARM __arm__, __aarch64__
MSVC _MSC_VER, _WIN64, _WIN32
Linux __linux__
Apple __APPLE__, __MACH__

规范

集中封装 platform.h：

#if defined(_WIN32)
#  define MY_PLATFORM_WIN 1
#elif defined(__linux__)
#  define MY_PLATFORM_LINUX 1
#else
#  error "unsupported platform"
#endif

业务代码只 include platform.h，不直接散落架构宏。

章节自测

可移植性陷阱：换 CPU/OS 后行为突变。看代码 → 想答案 → 点开验证。

Q1整型宽度不固定
long timestamp = 1700000000;  // Unix 时间戳

// 32 位 Linux (ILP32)：sizeof(long) = ?
// 64 位 Linux (LP64)：sizeof(long) = ?
// 64 位 Windows (LLP64)：sizeof(long) = ?

printf("%ld\n", timestamp);

三个平台上 sizeof(long) 分别是多少？哪个可能出问题？

答案与复习指引

答案： - 32 位 Linux (ILP32)：long = 4 字节 - 64 位 Linux (LP64)：long = 8 字节 - 64 位 Windows (LLP64)：long = 4 字节

2038 年问题：time_t 在 32 位系统上是 long（4 字节）→ 2038-01-19 溢出。64 位 Linux 上 time_t = 8 字节，安全。

规则： 协议/寄存器用 int32_t/int64_t（stdint.h 定宽类型），不用 int/long。

复习： → 7.1 整型宽度

Q2char 符号性
char c = 0x80;
if (c < 0)
    printf("negative\n");
else
    printf("non-negative\n");

在 x86 和 ARM 上输出可能不同吗？

答案与复习指引

答案： 是的。char 的符号性是实现定义的： - x86（gcc 默认）：char 是 signed → c = 0x80 = -128 → 输出 negative - ARM（gcc 默认）：char 是 unsigned → c = 0x80 = 128 → 输出 non-negative

规则： 处理二进制数据用 unsigned char 或 uint8_t；处理 ASCII 字符也用 unsigned char 传给 ctype 函数。

复习： → 7.2 char 符号性

Q3大小端
uint32_t val = 0x01020304;
char *p = (char *)&val;

printf("%02x %02x %02x %02x\n", p[0], p[1], p[2], p[3]);

在小端机和大端机上分别输出什么？

答案与复习指引

答案： - 小端（x86）：04 03 02 01（低位字节在低地址） - 大端（网络字节序/某些 ARM）：01 02 03 04（高位字节在低地址）

网络通信： 发送方必须用 htonl()/htons() 转为网络字节序（大端），接收方用 ntohl()/ntohs() 转回。禁止 *(uint32_t*)buf 直接读取网络缓冲区。

复习： → 7.3 大小端

Q4结构体对齐 padding
struct Packed {
    char a;     // 1 byte
    int b;      // 4 bytes
    char c;     // 1 byte
};

struct Aligned {
    char a;
    char c;
    int b;
};

printf("%zu %zu\n", sizeof(struct Packed), sizeof(struct Aligned));

两个 sizeof 分别是多少？（假设 4 字节对齐）

答案与复习指引

答案： 12 8。

struct Packed（a + 3padding + b + c + 3padding = 12）：

[a][pad][pad][pad][b][b][b][b][c][pad][pad][pad]

struct Aligned（a + c + 2padding + b = 8）：

[a][c][pad][pad][b][b][b][b]

规则： 按对齐要求从大到小排列成员（double → int → short → char），减少 padding。协议头用 __attribute__((packed)) 但注意可能引发未对齐访问。

复习： → 7.4 结构体对齐

Q5有符号右移
int x = -8;           // 0xFFFFFFF8
int y = x >> 1;       // 算术右移？逻辑右移？

unsigned z = 0xFFFFFFF8u;
unsigned w = z >> 1;  // 逻辑右移

printf("y=%d w=%u\n", y, w);

y 和 w 分别是多少？y 的行为是 UB 吗？

答案与复习指引

答案： - w = 0x7FFFFFFC = 2147483644（无符号右移是逻辑右移，高位补 0，标准保证） - y：实现定义（不是 UB）。大多数编译器对有符号数做算术右移（高位补符号位 1）→ y = -4。但标准允许逻辑右移。

规则： 需要确定性行为时用 unsigned 做位移，或用显式掩码。

复习： → 7.6 有符号右移
