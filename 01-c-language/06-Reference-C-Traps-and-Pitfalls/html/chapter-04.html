4.1

外部变量：声明与定义

本节讲什么

多文件工程中，声明（declaration） 与 定义（definition） 混淆是链接阶段第一坑。extern 只引入名字；定义 才分配存储，且全局对象 整个程序只能有一处定义。

要点

写法 作用
声明 extern int val; 告诉编译器「别处有定义」，不 分配内存
定义 int val; / int val = 0; 分配 存储，链接器导出符号

经典错误

/* bad.h — 每个 #include 的 .c 都生成一份定义 */
int val;

链接：multiple definition of 'val'。

正确模式

/* good.h */
extern int val;

/* good.c（唯一） */
int val = 0;

与 ch03 衔接

ch03 3.9 + 本章 4.4：extern 类型必须与定义 完全一致。

代码自测

题目 1： 以下两个文件能正确链接吗？

// file1.c
int x = 42;
// file2.c
extern int x;
参考答案

能正确链接。file1.c 定义了 x（分配存储），file2.c 声明 x 为 extern（引用外部定义）。extern 表示「此变量在别处定义」，不分配存储。常见错误：file2.c 写成 int x;（ tentative definition），某些链接器会当作第二个定义。规则：定义只有一处，声明用 extern。

4.2

未初始化与已初始化全局变量

本节讲什么

全局/静态对象在链接合并后进入 .bss（未初始化） 或 .data（已初始化）；行为不同，依赖「默认全零」时要明确哪些对象在 .bss。

要点

int g;        /* .bss，加载时清零 */
int h = 10;   /* .data，占 ELF 初始值 */
存储 特点
.bss ELF 常 NOBITS；运行时分配并 清零
.data 文件中带初值拷贝

逻辑坑

  • 以为「所有全局都会清零」—— 只有未显式初值的全局/静态 进 .bss 清零；static int x = 0 也在 .data（初值为 0 但仍占 .data 条目，实现可优化到 bss）
  • 多文件 不会 因一个 .bss 一个 .data 同名冲突—— 同名才是灾难（4.1、4.6）

工具

readelf -S a.out | grep -E '\.bss|\.data'
nm a.out | grep ' g'

见 Expert C ch05/ch06。

与后续衔接

  • ch03 3.1：全局生命周期
  • 4.6：未初始化 tentative 与弱符号

代码自测

题目 1： 以下两个全局变量在内存中有什么区别？

int a = 42;    // ?
int b;         // ?
参考答案

a → data 段（已初始化全局变量，占可执行文件空间） b → BSS 段（未初始化全局变量，不占可执行文件空间，启动时清零） BSS 的优势：可执行文件更小。大量未初始化全局数组不会增加文件大小。static 变量同理。局部变量不区分（在栈上，不初始化时值未定义）。

4.3

static 与符号可见性

本节讲什么

文件作用域 static 全局变量/函数 → 内部链接（internal linkage）：符号 不导出 给其他 .o，仅本翻译单元可见。

要点

/* file_a.c */
static int counter;      /* 仅 file_a.o 可见 */
static void helper(void) { }

/* file_b.c */
static int counter;      /* 不同符号，不冲突 */
链接属性 写法 其他文件
外部链接 全局 int g; / 非 static 函数 extern 可引用
内部链接 static 全局 / static 函数 不可 访问

工程场景

  • 驱动、内核：模块私有 全局与工具函数一律 static
  • 避免 同名符号 在多个 .o 冲突
  • 与 C++ anonymous namespace 类似意图

勿与 static 局部混淆

函数内 static int x 是 静态存储期、块作用域（ch03），仍在本 .o 有符号（通常 local 符号）。

与后续衔接

  • 4.6：非 static 全局的弱符号共享
  • Embedded ch09：模块化与头文件

代码自测

题目 1： 以下代码中 static 的作用是什么？

// file1.c
static int counter = 0;
static void helper(void) { ... }
参考答案

static 修饰全局变量/函数时，表示「内部链接」——只在当前文件可见，其他文件不能 extern 引用。这实现了文件级封装（类似 private）。不加 static 的全局变量/函数是外部链接（其他文件可见）。注意：static 修饰局部变量时含义不同（持久存储 + 块作用域）。

4.4

跨文件类型不一致（最危险静默 bug）

本节讲什么

链接器按 符号名 合并引用，不做 C 类型检查。定义与 extern 声明类型不一致时，编译各自通过，运行 内存解释完全错误。

要点

/* file1.c */
char msg[] = "hello";

/* file2.c */
extern char *msg;
符号 file1 视角 file2 视角
msg 数组，内容在 .rodata/.data 指针变量，应存地址

file2 把 字符串首字节 当 指针值 解引用 → 段错误或乱码。

同类陷阱

/* file1 */ int buf[100];
/* file2 */ extern char *buf;  /* 同样灾难 */

见 Expert C ch04 demo02。

为何链接不报错

  • 各 .o 的符号表只有 名字 + 地址/段，无完整 C 类型
  • 同一名字 即可匹配

工程规范

  • 共享对象 统一头文件 声明
  • 数组：extern char msg[]; 或 #define MSG_LEN + extern char msg[MSG_LEN];
  • 禁止 .c 之间口头约定类型

代码自测

题目 1： 以下代码在链接时会发生什么？

// file1.c
int x = 42;
// file2.c
double x;  // 类型不同
参考答案

链接器通常不检查类型——它只看符号名。x 在两个文件中符号名相同，链接通过。但 file2.c 中 x 被当作 double（8 字节）访问，实际存储的是 int（4 字节）——读取越界，值错误。这是 C 弱类型链接的经典陷阱。防范：用头文件统一声明，确保所有文件看到相同的类型。

4.5

静态库链接顺序

本节讲什么

.a 是 .o 归档；链接器按命令行 从左到右 扫描，仅当 当前未解析符号 需要 库中某成员时才提取该 .o。顺序错误 → undefined reference。

要点

# 典型：主程序 .o 在前，库在后
gcc main.o -L. -lfoo -o prog

# 错误示例（老链接器/严格环境）：
gcc -lfoo main.o   # 扫描 libfoo 时尚无 undefined，库可能被跳过

规则

被依赖的库写在依赖它的目标文件之后；循环依赖时 重复 -lfoo。

现代 GCC

gcc main.c -lm 常仍能工作（链接器多次扫描），嵌入式/交叉工具链 仍可能严格；Makefile 应显式：OBJS ... -lfoo -lbar。

代码自测

题目 1： 以下链接命令为什么报「未定义引用」？

gcc main.o -lfoo -lbar
# main.o 调用 libbar 的函数，libbar 调用 libfoo 的函数
参考答案

链接器从左到右处理库——处理 -lbar 时已经过了 -lfoo，libbar 对 libfoo 的引用找不到。正确顺序：依赖者在前，被依赖者在后：

gcc main.o -lbar -lfoo

如果循环依赖，可能需要重复库：gcc main.o -lfoo -lbar -lfoo。或用 --start-group/--end-group。

4.6

强符号与弱符号

本节讲什么

GNU ld 规则：强符号 不能重复；弱符号 可与强符号共存；多弱同名取其一。多个文件 int cnt;（tentative） 可能 合并为同一全局——模块间 静默共享 计数器。

要点

符号 示例
强 int x = 1;、函数定义
弱 __attribute__((weak)) int x;；传统 tentative int x;（GCC 10+ -fno-common 行为见 Expert C ch05）

规则：

  1. 两 强 同名 → multiple definition
  2. 一 强 多 弱 → 用 强
  3. 全 弱 → 任选一个

坑

多 .c 各写 int event_cnt;（无 static）→ 可能 链接成一份，你以为每模块独立计数。

修复

  • 模块私有：static int event_cnt;
  • 真共享：头文件 extern int event_cnt;，一个 .c 定义

代码自测

题目 1： 以下代码中哪个 x 是强符号，哪个是弱符号？

// file1.c
int x = 42;   // ?
// file2.c
int x;        // ?
参考答案

file1.c 的 x = 42 是强符号（有初始化）。file2.c 的 x 是弱符号（无初始化，tentative definition）。链接器选择强符号——最终 x = 42。如果两个都是强符号（都有初始化），链接器报多重定义错误。GCC __attribute__((weak)) 可显式声明弱符号。

4.7

未定义引用

本节讲什么

编译期只需 声明；定义 必须在某个 .o 或库成员中，并在链接命令行 被拉入。漏 .o、漏 -lfoo → undefined reference to 'symbol'。

要点

main.o: undefined reference to `foo'

常见原因：

原因 修复
只声明未定义 某 .c 实现 foo
实现 .o 未加入链接 Makefile 加 foo.o
实现在 .a 但库顺序/扫描问题 调整 -l 顺序（4.5）
C/C++ 混编未 extern "C" 包装 C 接口

与编译错误区别

  • 编译错误：单文件内语法/类型
  • 链接错误：全程序符号表 拼不齐

题目 1： 以下错误通常是什么原因？

参考答案

4.8

头文件保护与循环包含

本节讲什么

头文件被多次 #include 会 重复展开 声明/定义，引发 重复定义 或类型冲突。Include guard 或 #pragma once 必需。

要点

#ifndef PROJECT_FOO_H
#define PROJECT_FOO_H
/* 声明、inline、宏 */
#endif

循环包含

a.h → b.h → a.h：第二次进入 a.h 时 guard 已定义，内容跳过—— 前提是有 guard。

无 guard 时：

  • 同一 struct 定义两次 → 编译错误
  • 头文件里误写 int g; → 多 .o 多重定义（4.1）

最佳实践

  1. 头文件 只放声明、inline、宏
  2. Include guard 或 #pragma once
  3. 减少头文件互相依赖；前置声明 struct X;

与后续衔接

  • ch06 预处理器：#include 机制
  • 4.1：头文件勿定义全局变量

代码自测

题目 1： 以下头文件被重复 include 会怎样？如何修复？

// header.h
typedef struct { int x; } Point;
参考答案

重复 include 导致 Point 重复定义——编译错误。修复：加头文件保护（include guard）：

#ifndef HEADER_H
#define HEADER_H
typedef struct { int x; } Point;
#endif

或用 #pragma once（非标准但被主流编译器支持，更简洁）。保护宏名应唯一（通常基于文件路径）。

章节自测

连接陷阱：编译通过、链接或运行才暴露。看代码 → 想答案 → 点开验证。

Q1extern 类型不匹配灾难
// file_a.c
char name[] = "hello world";

// file_b.c
extern char *name;
#include <stdio.h>
int main() {
    printf("%s\n", name);
    return 0;
}

编译链接能通过吗？运行时发生什么？

答案与复习指引

答案： 链接可能成功（C 链接器不做类型检查），但运行时崩溃。

file_a.c 中 name 是 char[12]（12 字节连续数据）。file_b.c 中 extern char *name 把它当指针——读取 name 的前 8 字节（64 位指针）当作地址值，即把 "hello wo" 的字节解释为一个内存地址去解引用 → SIGSEGV。

规则： 跨文件 extern 声明必须与定义类型完全一致。char[] ≠ char *。

复习： → 4.4 类型不匹配链接

Q2static 隐藏符号
// counter.c
static int count = 0;
int get_count(void) { return ++count; }

// main.c
#include <stdio.h>
extern int count;   // 尝试访问 counter.c 的 count
int main() {
    printf("%d\n", count);
    return 0;
}

链接结果如何？

答案与复习指引

答案： 链接失败——undefined reference to 'count'。static 全局变量是内部链接，只在本 .c 文件可见，其他文件无法 extern 访问。

用途： 模块私有变量和工具函数用 static 封装，避免命名冲突——内核大量使用。

复习： → 4.3 static 内部链接

Q3静态库链接顺序
// liba.a 调用 libb.a 的函数
// main.c 调用 liba.a 的函数

// 命令1：gcc main.o -la -lb   →  ?
// 命令2：gcc main.o -lb -la   →  ?

两条命令哪个能链接成功？为什么？

答案与复习指引

答案： 命令1成功，命令2失败（undefined reference）。

静态库（.a）链接器从左到右扫描：只提取满足当前未解析符号的 .o。命令2先扫 libb.a，此时没有未解析符号引用 libb，所以 libb 被跳过；扫到 liba.a 时发现需要 libb 的符号，但 libb 已经过去了。

规则： 被依赖的库放右边——调用者 → 被调用者 的顺序。

复习： → 4.5 静态库链接顺序

Q4bss vs data
int a = 42;       // 初始化为非零
int b = 0;        // 初始化为零
int c;            // 未初始化

#include <stdio.h>
int main() {
    printf("%d %d %d\n", a, b, c);
    return 0;
}

a、b、c 分别在哪个段？用 nm 查看是什么字母？

答案与复习指引

答案： - a = 42：.data 段（初始化非零）— nm 显示 D - b = 0：.bss 段（初始化为零）— nm 显示 B - c（未初始化）：.bss 段（C 标准规定未初始化全局变量默认 0）— nm 显示 B（或 C，取决于编译器）

区别： .data 占可执行文件空间；.bss 不占（运行时由 OS 清零）——大量零初始化全局变量用 .bss 省空间。

复习： → 4.2 bss 与 data

Q5头文件重复包含
// types.h
struct Point { int x, y; };

// a.h
#include "types.h"

// b.h
#include "types.h"

// main.c
#include "a.h"
#include "b.h"
#include <stdio.h>
int main() { struct Point p = {1, 2}; printf("%d,%d\n", p.x, p.y); }

编译结果如何？如何修复？

答案与复习指引

答案： 编译失败——struct Point 被重复定义。types.h 被通过 a.h 和 b.h 两次包含。

修复： 加 include guard：

#ifndef TYPES_H
#define TYPES_H
struct Point { int x, y; };
#endif

或 #pragma once（非标准但广泛支持）。
