# 2.3.1 字符常量的类型与整型提升

## 本节讲什么

把 [2.3 §3](./2.3-常量.md) 里那一行「字符常量类型是 **`int`**」拆到底：**变量本身的类型** 和 **整数提升（integer promotion）** 是两件事，而 `sizeof('c')` 正是钉死这个区分的那根钉子 —— 它等于 **4**，不是 1。

本节做三件事：给出 **取证手段**（`_Generic` / `static_assert` / 编译器告警），划清「提升发生 / 不发生」的 **边界表**，并现场复现 `char ch = 0xFF` 这个在网络与内核代码里反复出现的经典 bug。

**前置**：[2.3 常量 §3](./2.3-常量.md)、[2.2 数据类型及长度](./2.2-数据类型及长度.md)、[2.2.3 stdint.h](./2.2.3-stdint.h.md)。  
**后续**：[2.7 类型转换](./2.7-类型转换.md)（提升的完整规则 + signed/unsigned 混算）、[2.9 按位运算符](./2.9-按位运算符.md)、[ch07 输入输出](../ch07-input-and-output/)（`getchar` 返回 `int` 的原因）。

> **配套 demo**：[`demo/demo02_char_promotion`](./demo/demo02_char_promotion/main.c)。本节所有数字均为 **双平台实测**，两边 `-Wall -Wextra -std=c11` 均 **零告警**：
>
> | 平台 | 编译器 | 目标三元组 | `char` |
> |------|--------|-----------|--------|
> | Mac（arm64） | clang 23.1.0 | `arm64-apple-darwin` | **signed** |
> | Raspberry Pi 5（aarch64） | gcc 14.2.0 / Debian 13 | `aarch64-linux-gnu` | **unsigned** |
>
> 两个平台在 §5 给出 **相反** 的结论 —— 这不是笔误，正是本节的靶心。

## 要点

### 0. 先把两件事分开（本节最重要的一句）

| 问题 | 答案 |
|------|------|
| `'x'` 这个 **字符常量** 是什么类型？ | **`int`** —— 标准硬性规定，C89 到 C23 都一样 |
| `char c` 这个 **变量** 是什么类型？ | **`char`** —— 1 字节；**有无符号是实现定义** |
| `sizeof('c')` | **4**（= `sizeof(int)`） |
| `sizeof(c)` | **1** |
| `c` 用于表达式 / 传参时 | 提升为 **`int`** 后再算 |

**关键区分**：

- **类型** 是 **静态属性**，声明那一刻就定了，编译期可见；
- **提升** 是 **表达式求值时的临时转换** —— 求值完就没了，**不会改变变量自己的类型**。

所以「`c` 参与运算会变成 `int`」这句话，严格说是：**`c` 参与运算时，使用的是一个提升后的 `int` 临时值；`c` 本身仍然是 `char`（`sizeof(c)` 依旧 1）。**

### 1. 标准怎么说（出处别记混）

| 标准 | 章节号 | 标题 |
|------|--------|------|
| C89/C90 | §3.1.3.4 | Character constants |
| C99 / C11 / C17 | **§6.4.4.4** | Character constants |
| C23 | §6.4.4.5 | （编号后移） |

**规定原文**（单字节整数字符常量）：

> Such constant **has type `int`** and a value equal to the representation of c-char in the execution character set as a value of type `char` mapped to `int`.

同一节里还有一句经常被忽略、但后面那个坑全靠它的话：

> a character constant may have a **negative value if `char` is signed**: on such implementations **`'\xFF'` is an `int` with the value `-1`**.

**完整的字符常量类型表**：

| 写法 | 类型 | 备注 |
|------|------|------|
| `'a'` / `'\n'` / `'\x41'` | **`int`** | 值 = 执行字符集里的字节值；**始终是 int** |
| `u8'a'`（**C23 起**） | `char8_t` | 值 = ISO 10646 码点；**唯一不是 `int` 的单字符常量** |
| `u'a'`（C11 起） | `char16_t` | 值 = UTF-16 码元 |
| `U'a'`（C11 起） | `char32_t` | 值 = UTF-32 码元 |
| `L'a'` | `wchar_t` | Linux 4 字节，Windows 2 字节 —— 平台相关 |
| `'AB'` 多字符 | **`int`** | 类型仍是 `int`，**值实现定义**（clang 按大端拼接字节） |

**双平台实测的 `sizeof`**（`'a'` / `u'a'` / `U'a'` / `L'a'` / `'ab'`）：

| 常量 | clang 23.1.0 (macOS arm64) | gcc 14.2.0 (Linux aarch64) | clang 19.1.7 (Linux aarch64) |
|------|:---:|:---:|:---:|
| `'a'` | 4 | 4 | 4 |
| `u8'a'` | 1 | **1** | 1 |
| `u'a'` | 2 | 2 | 2 |
| `U'a'` | 4 | 4 | 4 |
| `L'a'` | 4 | 4 | 4 |
| `'ab'` | 4 | 4 | 4 |

> 多字符常量 `'ab'` 三处都是 4（类型仍是 `int`，值实现定义）。告警方面：clang **默认**就报 `-Wmultichar`，gcc 要加 `-Wall -Wextra` 才报（两平台均实测）。

多字符常量最常见的正当用途是 **FourCC 魔法数**——文件格式与协议里的 4 字节标识（如 `'RIFF'`），源码里一眼可读。但正因为值实现定义（拼接顺序不保证），**写进协议的数值应该用显式常量**（`0x52494646` 或移位表达式），跨平台代码不依赖 `'RIFF'` 的具体值。

> **⚠ `__STDC_VERSION__` 的坑**：gcc 14.2 的 `-std=c23` 报的是 **`202000L`** 而不是标准最终的 `202311L`
> （gcc 15 才改成 `202311`）。所以写特性探测时 **`#if __STDC_VERSION__ >= 202311L` 在 gcc 14 上会误判成「不是 C23」**。
> 我自己的探针就踩了这个坑，最后是直接编译 `u8'a'` 确认 gcc 14.2 **支持** `u8` 字符常量与 `char8_t`（`sizeof(char8_t)` = 1、值 97）。
> 更稳的写法是 `#if defined(__STDC_VERSION__) && __STDC_VERSION__ > 201710L`，或者用 `__has_include(<uchar.h>)` 之类的编译器特性宏。

**C++ 对照**：普通字符字面量类型是 **`char`**，不是 `int` —— 这是同一个语法在两种语言里唯一的硬差异，见文末对照表。
（g++ 14.2 `-std=c++17` 实测 `sizeof('c')` = **1**，与 clang++ 23.1.0 一致。）

### 2. 三种「取证」手段

推断「这个表达式是什么类型」时，别靠背 —— 让编译器回答。

#### 2.1 `_Generic`：编译期问类型（C11）

```c
#define TYPEOF(x) _Generic((x),          \
        char: "char",                    \
        signed char: "signed char",      \
        unsigned char: "unsigned char",  \
        short: "short",                  \
        int: "int",                      \
        unsigned int: "unsigned int",    \
        long: "long",                    \
        default: "other")

char c = 'A';
printf("%s\n", TYPEOF('c'));    /* int  */
printf("%s\n", TYPEOF(c));      /* char */
printf("%s\n", TYPEOF(c + c));  /* int  */
```

**为什么它能区分？** `_Generic` 的控制表达式会做 **左值转换 / 数组转指针 / 函数转指针**，但 **不做整数提升**。所以 `TYPEOF(c)` 老老实实给出 `char`，`TYPEOF(c + c)` 给出 `int` —— 恰好就是本节要区分的这两件事。

本机实测（`demo02` §2）：

| 表达式 | 类型 |
|--------|------|
| `'c'` | `int` |
| `c` | `char` |
| `c + c` | `int` |
| `c << 1` | `int` |
| `c == 0` | `int` |
| `~c` | `int` |

#### 2.2 `static_assert`：编译期断言（C11）

```c
#include <assert.h>
static_assert(sizeof('c') == sizeof(int), "C 语言里字符常量的类型就是 int");
```

这行编译得过，就说明「字符常量是 `int`」这条在本平台成立。想反过来验证 C++，同一个文件用 `clang++` 编译这行 **直接报错**。

#### 2.3 编译器告警：让编译器替你抓

```c
char ch = (char)0xFF;
if (ch == 0xFF) puts("eq");     /* clang: warning: result of comparison of
                                   constant 255 with expression of type 'char'
                                   is always false
                                   [-Wtautological-constant-out-of-range-compare] */
```

**双平台实测**：

| 平台 | `char` | 编译 `if (ch == 0xFF)` 的结果 |
|------|--------|------------------------------|
| Mac · clang 23.1.0 · arm64-apple-darwin | signed | **告警**：`result of comparison of constant 255 with expression of type 'char' is always false [-Wtautological-constant-out-of-range-compare]`（`-Wall` 即报） |
| Pi 5 · gcc 14.2.0 · aarch64-linux-gnu | **unsigned** | **完全无告警** —— 因为 `char` 是 unsigned 时这个比较恒 **真**，不是恒假 |

GCC 侧的告警文本（用 `-fsigned-char` 强制成有符号后测得）：

```
t2.c: In function ‘main’:
t2.c:6:12: warning: comparison is always false due to limited range of data type [-Wtype-limits]
    6 |     if (ch == 0xFF)
      |            ^~
```

- `-Wtype-limits` **已在 `-Wextra` 里**，不用单独加；`-Wall -Wextra` 即可看到。
- clang 用的是 `-Wtautological-constant-out-of-range-compare`，**GCC 不认识这个名字** —— 两边告警名不同，写构建脚本时别照抄。
- **最阴的地方**：这条告警能不能触发，本身就取决于 `char` 的符号性 —— 在 aarch64 Linux 上同一份错代码 **一个告警都不给**，而且行为是对的（恒真）。所以在 Pi 上写代码时，这类 bug 反而 **更难被发现**。

**结论**：这类「提升 + 符号性」的 bug，只有 **`-Wall -Wextra` + 显式 `uint8_t` 类型纪律** 才挡得住；指望编译器告警在跨平台代码里兜底是不成立的。

### 3. 边界表：什么时候提升，什么时候不提升

这是本节最实用的一张表 —— **「参与运算就提升」是粗略说法，`sizeof` 就是反例**：

| 上下文 | 整数提升 | 实测证据 |
|--------|:--------:|----------|
| 算术 `+ - * / %` | ✅ | `TYPEOF(c + c)` = `int` |
| 比较 `< > <= >= == !=` | ✅ | `TYPEOF(c == 0)` = `int` |
| 位运算 `& \| ^ ~`、逻辑 `!` | ✅ | `TYPEOF(~c)` = `int` |
| 移位 `<< >>` | ✅ | `TYPEOF(c << 1)` = `int` |
| 三元 `?:` 的两支 | ✅ | 见 [2.11](./2.11-条件表达式.md) |
| **函数传参**（含 `printf` 可变参数） | ✅ | 传进去的是 `int`，见 §6 |
| `switch (c)` 的整型条件 | ✅ | `case 'a':` 匹配的是 `int` 97 |
| **`sizeof` 的操作数** | ❌ | `sizeof(c)` = **1** |
| **`_Generic` 控制表达式** | ❌ | `TYPEOF(c)` = `char` |
| `&c` 取地址 / `_Alignof` | ❌ | 取的是 `char` 对象本身 |
| 赋值给更宽类型（`int x = c;`） | 效果类似，但严格说属 **转换** 不是提升 | 见 [2.7](./2.7-类型转换.md) |

**怎么把「不提升」的场合变成「提升」？自己造一个表达式就行**：

```c
sizeof(c)      /* 1 —— 变量本身 */
sizeof(+c)     /* 4 —— 一元 + 是表达式，提升发生 */
sizeof(c + 0)  /* 4 */
sizeof(c == 0) /* 4 */
sizeof(c << 0) /* 4 */
```

本机实测输出：

```
sizeof(c)      = 1   <- 变量本身，不提升
sizeof(+c)     = 4   <- 一元 + 是表达式，提升发生
sizeof(-c)     = 4
sizeof(c << 0) = 4
sizeof(c + 0)  = 4
sizeof(c == 0) = 4
```

**想要「1 字节的字符常量」怎么写？** 显式转：`sizeof((char)'c')` = 1。或者干脆用 `sizeof(char)`（语义更清楚）。

### 3.5 `if (c == 'a')` 逐步走一遍：比较的两个操作数各自提升

这个主题最常见的问题形式是「`char` 在 `if` 条件里比较，会不会变成 `int`」——**会，而且两边都按 `int` 比**。以 `if (c == 'a')` 为例：

| 步骤 | C 里的情况 | C++ 里的情况 |
|------|-----------|-------------|
| 左操作数 `c`（`char` 变量） | 提升为 `int`（符号扩展还是零扩展按目标 ABI，见 §5） | 同左 |
| 右操作数 `'a'` | **本身就是 `int` 97**（§1），无需提升 | 类型是 `char`，同样提升为 `int` 97 |
| 实际执行的比较 | `(int)c == 97` | `(int)c == 97` |

两种语言殊途同归：C 少一步提升（常量天生是 `int`），C++ 多一步（常量也是 `char`），**最终都是 `int` 与 `int` 比较，不存在「按 8 位比较」这回事**。提升次数不同（C 一次、C++ 两次），结果完全相同。

再由 §5 已实测的事实直接推出两个同族坑（纯逻辑推演，不需要新实测）：

```c
char c = (char)0x80;
if ((c >> 1) == 0x40) { ... }   /* signed char 平台上恒 false */
```

以为「右移一位等于除以 2 得 64」就掉进去了：**提升发生在移位之前** —— `c` 先提升为 `int` 的 `-128`（`0xFFFFFF80`），`>>` 算术右移得 `-64`（`0xFFFFFFC0`），与 `0x40`（64）不等。移的是 32 位的 -128，不是 8 位的 0x80。

```c
char c = ...;
if (c < 200) { ... }            /* signed char 平台上恒 true */
```

`char` 有符号时取值范围 -128~127，`c < 200` **恒真**；clang 会报 `-Wtautological-constant-out-of-range-compare`（与 §2.3 实测的同款告警），gcc 侧对应 `-Wtype-limits`。这类「跟一个永远够不着的常量比较」的写法，几乎都是把字节当成了 0–255。

### 4. 提升的**正收益**：窄类型算术不塌

提升不是纯麻烦，它是 C 里 **窄类型能参与算术**的前提：

```c
unsigned char x = 100, y = 200;
printf("%d\n", x - y);                      /* -100：先提升为 int 再减 */
printf("%d\n", (unsigned char)(x - y));     /*  156：截回 8 位才回绕 */
```

本机实测：

```
x=100, y=200  ->  x - y        = -100   <- 提升为 int，得到负数而非回绕
             ->  (unsigned char)(x - y) = 156    <- 截回 8 位才是回绕值
```

若 C 在 8 位里算，`100 - 200` 会悄悄回绕成 `156`，负差就永远判不出来。**「小减大得负数」这个直觉，是整型提升给的。**

（[2.7 §一.1](./2.7-类型转换.md) 里 `uint8_t a=200, b=100; a-b == 100` 是同一个机制的顺光面。）

### 5. 经典坑：`char ch = 0xFF`

```c
char ch = 0xFF;              /* 0xFF = 255，char 装不下！ */
if (ch == 0xFF) { ... }      /* 永远不成立 */
```

**这个坑有「两层」，而且两层都取决于实现定义的 `char` 符号性** —— 先是 `0xFF` 截成什么，再是提升后跟 `int` 常量 255 比。

**逐步拆解**（`char` 为 **signed** 的平台）：

1. `char ch = 0xFF;` —— `255` 是 `int`，赋给 8 位有符号 `char` → **实现定义**，按补码截断成 **`-1`**；
2. `ch` 参与比较 → 提升为 `int` → **`0xFFFFFFFF`（即 -1）**；
3. 另一边 `0xFF` 字面量本身就是 `int` → **`0x000000FF`（即 255）**；
4. `-1 == 255` → **false**。

**同一份 demo，双平台实测**（左边 Mac，右边 Pi 5）：

| 输出 / 现象 | Mac · clang 23.1.0 · `arm64-apple-darwin` | Pi 5 · gcc 14.2.0 · `aarch64-linux-gnu` |
|-------------|:---:|:---:|
| `char is ...` | **signed** | **unsigned** |
| `(int)ch` | **-1**（`0xFFFFFFFF`） | **255**（`0x000000FF`） |
| `ch == mask(0xFF)` | **false** | **true** |
| `ch == neg(-1)` | true | false |
| `(unsigned char)ch == 0xFF` | true | true |
| 编译器在 `-Wall -Wextra` 下 | **告警** | **无告警** |

> 唯一在两个平台上都稳定的是最后一行 —— **`(unsigned char)` 才是可移植写法**。

**`char` 的符号性由「目标 ABI」决定，不是编译器决定**。实测矩阵（clang 19，`-ffreestanding -fsyntax-only`，不需要 libc；判据是 `_Static_assert((char)-1 < 0)`）：

| 目标三元组 | `char` |
|------------|--------|
| `aarch64-linux-gnu` | **unsigned** |
| `armv7-linux-gnueabihf` | **unsigned** |
| `riscv64-linux-gnu` | **unsigned** |
| `x86_64-linux-gnu` | signed |
| `arm64-apple-darwin` | signed |
| `x86_64-apple-darwin` | signed |

同一个 `aarch64-linux-gnu` 上 gcc 14.2 与 clang 19 **结论一致**（都 unsigned）→ 说明这是 **ABI 层面** 的规定，与编译器无关。**同一块 arm64 芯片，macOS 下 signed、Linux 下 unsigned** —— 这是跨平台移植时最容易被忽略的一层。

**三条修法**（按推荐度排序）：

| # | 写法 | 说明 |
|---|------|------|
| 1 | `uint8_t ch = 0xFF;` | **首选** —— 用 `stdint.h` 定宽类型，语义明确「我是一个 8 位无符号字节」（[2.2.3](./2.2.3-stdint.h.md)） |
| 2 | `if ((unsigned char)ch == 0xFF)` | 比较前截回 8 位。**网络报文、寄存器**读出的字节必须这么写 |
| 3 | `if (ch == (char)0xFF)` 或 `ch == (char)-1` | 把常量也降到 `char` 语义。缺点：可读性差，别人看不出你在防什么 |

> 另有编译开关 `-fsigned-char` / `-funsigned-char` 可强制统一符号性（实测 `gcc -fsigned-char` 会让上面的坑立刻触发 `-Wtype-limits` 告警）。**只在你控制全部编译单元时**才可考虑 —— 混进任何第三方库都可能造成 ABI 不一致。

**为什么内核 / 网络代码里天天见**：协议字段、寄存器值天然是「8 位无符号字节」，而裸 `char` 的符号性由 **目标 ABI** 决定（见上表：arm64 与 x86_64 的 Linux 结论相反）—— 同一段代码在 Mac 上「碰巧能跑」，挪到 Pi 上结论直接翻面，而且 **在 Pi 上连告警都不给**。**跨平台代码里，字节就得写成 `unsigned char` / `uint8_t`。**

### 6. 同一个规则的另一面：为什么 `getchar()` 返回 `int`

标准库的原型是：

```c
int getchar(void);      /* 不是 char */
```

理由和内核对齐：它要返回 **256 个字符值 + 一个 `EOF`（-1）**，共 257 种可能 —— **`char` 装不下**。写成 `char c = getchar();` 之后，`EOF` 会被截成 `0xFF` 再提升为 `-1` 之外的形态，`while ((c = getchar()) != EOF)` 直接死循环。

```c
int c;                                   /* ✅ 必须 int */
while ((c = getchar()) != EOF) { ... }

char c;                                  /* ❌ EOF 判不出来 */
while ((c = getchar()) != EOF) { ... }
```

**同一条规则的两种面孔**：`'x'` 是 `int`（因为常量的类型是 int）；`getchar()` 返回 `int`（因为要让提升后的值装得下）。见 [ch07 输入输出](../ch07-input-and-output/)。

### 7. 那 `printf("%c", c)` 为什么没事

因为提升 **已经替你做完了**：`c`（`char`）→ 提升为 `int`（值 65）→ 传进 `printf` → `printf` 内部再按 `%c` 取低 8 位输出。

```c
char z = 'A';
printf("%c", z);    /* A   —— 传进去的是 int 65，按 %c 取低字节 */
printf("%d", z);    /* 65  —— 同一个 int，按 %d 打印 */
```

**⚠ 反例**：`printf("%s", z)` 是 **UB** —— 传进去的是 `int`（无论提升与否都不是指针），`%s` 却按 `char *` 解引用。可变参数函数 **没有原型保护**，类型错了编译器一般也不报，这是 [2.7](./2.7-类型转换.md) 特别强调「不依赖隐式规则」的场景。

本机实测：

```
printf("%c", z) = A      printf("%d", z) = 65
```

## 本节核心考点

1. **`'x'` 是 `int`**（C89–C23 皆然）；`char c` 是 `char`。`sizeof('c')` = **4**，`sizeof(c)` = **1**
2. **类型是静态的，提升是求值期的**。变量参与运算 **不会改变自身类型**
3. **`sizeof` 的操作数、`_Generic` 的控制表达式不做整数提升**；想让提升发生就造表达式（`sizeof(+c)` = 4）
4. **字符常量类型表**：`'a'`→`int`；`u8'a'`（C23）→`char8_t`；`u'a'`/`U'a'`/`L'a'` → `char16_t`/`char32_t`/`wchar_t`；多字符 `'AB'`→`int` 但值实现定义
5. **`'\xFF'` 在 `char` 有符号的实现上是值为 -1 的 `int`** —— 标准明写，这就是 `ch == 0xFF` 恒假的根源；**在 `char` 无符号的实现上恒真**
6. **修法**：字节一律 `uint8_t` / `unsigned char`；比较前先对齐符号性
7. **`char` 的符号性由目标 ABI 决定**（实测：aarch64/armv7/riscv64 **Linux unsigned**；x86_64 Linux 与 macOS signed），**与编译器无关**；且 unsigned 平台上这类 bug **连告警都不给**
8. **`getchar()` 返回 `int`** 和「字符常量是 `int`」是同一套规则的两种面孔
9. **`printf("%c", c)` 安全（提升已代为完成）**，`printf("%s", c)` 是 UB
10. **gcc 14 的 `-std=c23` 报 `__STDC_VERSION__ = 202000L`**（非 202311），特性探测别写 `>= 202311L`
11. **比较运算的两个操作数各自提升**：`if (c == 'a')` 在 C 里 1 次提升、C++ 里 2 次，殊途同归按 `int` 比；**提升发生在移位之前**（`(char)0x80 >> 1` 在 signed char 平台得 `-64` 不是 `0x40`）；指令层对应 `sxtb/uxtb`（ARM）、`movsx/movzx`（x86）；C++ 把 `'a'` 改成 `char` 的动机是重载决议

## HFT / 底层开发的用处

1. **协议字段解析**：帧头字段、状态码天然是「8 位无符号字节」。读进 `char` 再和 `0x80`、`0xFF` 这种掩码比，就是 §5 的坑 —— 一律 `uint8_t`（[2.2.3](./2.2.3-stdint.h.md)）
2. **寄存器位域**：`volatile uint8_t *reg` 读回的值参与运算必先提升为 `int`；显式 cast 到 `uint32_t` 后再移位/掩码，避免符号扩展把高位带进来
3. **`switch` 分发**：`case 'A':` 能工作正是因为 `case` 常量是 `int`、`switch` 条件也被提升 —— 但这也意味着 **`switch` 不会帮你发现 `char`/`int` 的符号性差异**
4. **热路径上的对齐成本**：提升本身是零成本（寄存器本来就是 32 位宽），编译器直接生成 32 位运算；**代价只在语义上**，不在指令数上。提升在指令层面有确定的名字：ARM 是 `sxtb`（sign-extend byte）/ `uxtb`（zero-extend byte），x86 是 `movsx` / `movzx`——**选哪条正好由 §5 那张 ABI 符号性矩阵决定**，反汇编里可以直接看到
5. **编译开关**：CI / 本地构建带 `-Wall -Wextra -Wconversion -Wsign-compare`，能把这一类问题挡在提交前；**但别指望它兜底** —— 在 `char` 为 unsigned 的 aarch64 Linux 上，§5 那份错代码一个告警都不会有
6. **跨平台移植的第一道体检**：换平台前先用 §5 的 `_Static_assert` 探针确认 `char` 符号性（Mac arm64 signed ≠ Pi aarch64 unsigned）；涉及字节一律 `uint8_t`，不靠 `char`

```c
/* 报文解析的安全写法：字段一律无符号定宽，比较前统一符号性 */
uint8_t flags = buf[3];
if ((flags & 0x80u) != 0u) { ... }          /* 掩码带 u，两边都走 unsigned */
if ((uint32_t)flags == 0xFFu) { ... }       /* 显式拓宽，语义清楚 */
```

## 与 C++ 的差异

| 主题 | C | C++ |
|------|---|-----|
| **普通字符字面量 `'a'` 的类型** | **`int`** | **`char`**（`sizeof('c')` = 1） |
| `sizeof('c')` | **4** | **1** |
| 多字符常量 `'AB'` | 类型 `int`，值实现定义 | 类型 `int`，值实现定义（C++17 起 `int`，语义收紧） |
| `printf("%c", c)` / 模板推导 | 提升后传 `int` | `char` 不提升时按 `char` 处理，模板里能看出差别 |
| 定宽字节 | `<stdint.h>` 的 `uint8_t` | `<cstdint>` 的 `std::uint8_t` |
| `u8'a'` | C23 起 `char8_t`（gcc 14.2 / clang 19 实测 `sizeof` = 1） | C++17 起 `char`，C++20 起 `char8_t` |
| `sizeof('c')` 实测 | clang 23.1.0 → 4；gcc 14.2 → 4 | g++ 14.2 → 1；clang++ 23.1.0 → 1 |

**C++ 为什么改这条规则**：直接动机是**重载决议**。若沿用 C 的规则（`'a'` 是 `int`），字符实参会被分派到 `int` 重载，与直觉相反：

```cpp
void f(char c);
void f(int i);

f('a');   // C++：'a' 是 char → 精确匹配 f(char)
          // 若 'a' 按 C 规则是 int，这里会调到 f(int)
```

让「字符字面量按字符处理」，`sizeof('c')` 从 4 变 1 只是这个决定的副产品。

**实践含义**：同一份「`sizeof('c')` 是几」的代码，C 里是 4、C++ 里是 1 —— 混合编译的工程里，凡是依赖这个值的断言/数组长度，**两边要分开写**。

**题目 1：** 下面每个输出分别是多少？（`char` 在本机是有符号）

```c
char c = 'A';
printf("%zu\n", sizeof('c'));
printf("%zu\n", sizeof(c));
printf("%zu\n", sizeof(+c));
printf("%zu\n", sizeof((char)'c'));
printf("%zu\n", sizeof("A"));
```

<details>
<summary>参考答案</summary>

```
4      sizeof('c')        —— 字符常量类型是 int
1      sizeof(c)          —— char 变量；sizeof 的操作数不做提升
4      sizeof(+c)         —— 一元 + 造出表达式，提升发生
1      sizeof((char)'c')  —— 显式降到 char
2      sizeof("A")        —— 字符串字面量是 char[2]，含 '\0'
```

**复习**：[2.3.1 §0 / §3](./2.3.1-字符常量的类型与整型提升.md)、[2.3 §4](./2.3-常量.md)。

</details>

**题目 2：** 这段代码输出什么？为什么？

```c
char ch = 0xFF;
printf("%d\n", ch);
printf("%d\n", (int)ch);
printf("%d\n", (unsigned char)ch);
printf("%s\n", (ch == 0xFF) ? "equal" : "not equal");
```

<details>
<summary>参考答案</summary>

```
-1          ch 的实际值：0xFF 装进 8 位有符号 char，按补码是实现定义 → -1
-1          (int)ch：提升为 int，符号扩展 → 0xFFFFFFFF
255         (unsigned char)ch：先截回 8 位无符号 255，再提升为 int 打印
not equal   ch 提升为 int 得 -1；0xFF 字面量是 int 255；-1 != 255
```

**修正**：把类型改成 `uint8_t ch = 0xFF;`，或比较时写 `(unsigned char)ch == 0xFF`。

**复习**：[2.3.1 §5](./2.3.1-字符常量的类型与整型提升.md)。用 `-Wall` 编译，clang 会直接告诉你「comparison is always false」。

</details>

**题目 3：** 用 `_Generic` 与 `static_assert` 各写一行，证明「C 里字符常量的类型是 `int`」。这两行的差别是什么？

<details>
<summary>参考答案</summary>

```c
#include <assert.h>

/* 1) 编译期「查出」类型：_Generic 控制表达式不做整数提升，所以能区分 'c' 与 c */
#define TYPEOF(x) _Generic((x), char: "char", int: "int", default: "other")
printf("%s\n", TYPEOF('c'));        /* int  */
printf("%s\n", TYPEOF((char)'c'));  /* char */

/* 2) 编译期「断言」：成立才编得过，不成立直接编译错误 */
static_assert(sizeof('c') == sizeof(int), "字符常量的类型必须是 int");
```

**差别**：`_Generic` 是 **取值**（运行时打印出来，能看见具体类型）；`static_assert` 是 **断言**（编译期判真伪，失败即中断编译）。**前者用来观察，后者用来防守。**

**复习**：[2.3.1 §2](./2.3.1-字符常量的类型与整型提升.md)、demo `demo02_char_promotion`。

</details>

**题目 4：** 不写任何运行时代码，在 **编译期** 判定「当前目标 ABI 下 `char` 是不是有符号」。然后在 Pi 上验证 aarch64 Linux 的结论。

<details>
<summary>参考答案</summary>

```c
/* 只测类型，不需要 libc，所以可以 -ffreestanding -fsyntax-only 快速刷多个目标 */
_Static_assert((char)-1 < 0, "char is UNSIGNED on this target");
```

**读法**：`(char)-1 < 0` 是常量表达式。编译 **通过** → `char` 是 signed；编译 **报错** → unsigned。

```bash
# 一次刷完所有关心的目标（clang 19 实测）
for t in aarch64-linux-gnu x86_64-linux-gnu armv7-linux-gnueabihf riscv64-linux-gnu \
         arm64-apple-darwin x86_64-apple-darwin; do
  if clang --target=$t -ffreestanding -fsyntax-only t6.c 2>/dev/null; then
    echo "$t -> SIGNED"
  else
    echo "$t -> UNSIGNED"
  fi
done
```

**实测结果**：`aarch64-linux-gnu` / `armv7-linux-gnueabihf` / `riscv64-linux-gnu` → **UNSIGNED**；`x86_64-linux-gnu` / `arm64-apple-darwin` / `x86_64-apple-darwin` → **SIGNED**。
在树莓派上 `gcc 14.2` 与 `clang 19` 对同一个 `aarch64-linux-gnu` 结论一致（都 unsigned）→ 这是 **目标 ABI** 的规定。

**复习**：[2.3.1 §5](./2.3.1-字符常量的类型与整型提升.md)。

</details>

**题目 5：** 两问。① `char c = 'a'; if (c == 'a')` 在 C 和 C++ 里各发生了**几次**整型提升？② `char c = (char)0x80; if ((c >> 1) == 0x40)` 在 `char` 有符号的平台上结果是什么？为什么？

<details>
<summary>参考答案</summary>

① C 里 **1 次**（只有 `c` 需要提升；`'a'` 的类型天生是 `int`，见 §1）。C++ 里 **2 次**（`'a'` 的类型是 `char`，左右两边都提升）。两种语言最终都按 `int` 比较，结果相同——提升次数不同，语义殊途同归。

② **false**。提升发生在移位**之前**：`c` 先提升为 `int` 的 `-128`（`0xFFFFFF80`），`>>` 算术右移一位得 `-64`（`0xFFFFFFC0`），与 `0x40`（64）不等。移的是 32 位的 -128，不是 8 位的 `0x80`。若预期「右移得 64」，应写 `((unsigned char)c >> 1)`——先截回 8 位无符号，再提升、再移。

**复习**：[2.3.1 §3.5](./2.3.1-字符常量的类型与整型提升.md)、[2.9 按位运算符](./2.9-按位运算符.md)。

</details>
