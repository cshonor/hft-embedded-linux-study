# 1.5.2 字符计数

## 本节讲什么

在文件复制循环上累加计数器，统计输入的字符总数。核心：`long` 计数防溢出 + `++nc` 的前缀/后缀选择。

## 核心代码

```c
long nc = 0;

while ((c = getchar()) != EOF)
    ++nc;
printf("%ld\n", nc);
```

### 逐行解析

| 代码 | 作用 |
|------|------|
| `long nc` | 用 `long` 而非 `int`，大文件时计数范围更大 |
| `++nc` | 前缀自增。K&R 风格偏好 `++nc`（虽然此处前后缀结果相同） |
| `%ld` | `printf` 格式说明符，对应 `long` 类型 |

### 为什么用 `long` 不用 `int`

| 类型 | 32 位平台最大值 | 能数多大文件 |
|------|---------------|-------------|
| `int` | ~2.1 亿 | 2 GB |
| `long` | ~21 亿（32 位）或 9.2 × 10¹⁸（64 位） | 2 GB / 9.2 EB |

K&R 时代 16 位机器 `int` 只有 32767，`long` 到 21 亿——差距巨大。现代 64 位平台 `long` 是 64 位，基本不会溢出。

### `++nc` vs `nc++`

```c
++nc;   /* 前缀：先加 1，再返回新值 */
nc++;   /* 后缀：先返回旧值，再加 1 */
```

单独使用时效果完全相同。在表达式中不同：`x = ++nc`（x 拿到加 1 后的值）vs `x = nc++`（x 拿到加 1 前的值）。K&R 建议循环中用前缀 `++nc`，习惯一致减少出错。

## HFT 关联

计数器溢出是 HFT 的真实风险——高频场景下计数器增长极快。`uint64_t` 是现代 HFT 的标准选择，但仍需考虑回绕。内核中 `jiffies` 计数器也有类似问题。

## 常见坑

1. **`int` 计数大文件溢出**：32 位 `int` 最大 ~21 亿，数 2GB 文本就溢出。用 `long` 或 `int64_t`。
2. **`%d` 打印 `long`**：`printf("%d", nc)` 在 `long` 比 `int` 宽的平台上输出错误。必须用 `%ld`。
3. **`nc++` 在复杂表达式中的副作用**：`a[i++] = a[i++]` 是未定义行为。单独使用无问题。

## 自测题

1. 如果字符数超过 `LONG_MAX` 会怎样？
<details><summary>答案</summary>

有符号整数溢出是未定义行为。实际上大多数实现回绕为负数，计数错误。应使用 `unsigned long` 或 `uint64_t`，至少能多撑一倍范围。

</details>

2. `++nc` 和 `nc++` 在本例中有区别吗？
<details><summary>答案</summary>

没有。单独作为语句使用时，前缀和后缀自增结果完全相同。区别只在表达式上下文：`x = ++nc` vs `x = nc++`。

</details>

3. 为什么 K&R 用 `long` 而不是 `int`？
<details><summary>答案</summary>

K&R 时代 16 位机器 `int` 只有 32767，数 32KB 文本就溢出。`long` 保证至少 21 亿，覆盖大多数文件。现代 C 用 `int64_t` 更精确。

</details>

4. `printf("%ld\n", nc)` 中 `%ld` 的 `l` 能省吗？
<details><summary>答案</summary>

不能（可移植性角度）。`long` 在 64 位 Linux 上是 64 位，`int` 是 32 位。用 `%d` 打印 `long` 会截断高位。`%ld` 告诉 `printf` 参数是 `long`。

</details>
