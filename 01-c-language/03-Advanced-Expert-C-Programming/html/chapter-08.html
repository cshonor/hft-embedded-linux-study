8.1

Portzebie 度量衡系统

本节讲什么

本章标题 「Why Programmers Can't Tell Halloween from Christmas」 是一句程序员圈内著名的 双关笑话：八进制 031 看起来像 10 月 31 日（万圣节），而 031 的十进制值恰好是 25——12 月 25 日（圣诞节）。程序员「分不清」的，不是日历，而是 同一串字面量在 C 里按八进制还是十进制解释。

本节以 Mad 杂志 虚构的 Portzebie 度量衡 开篇：荒诞的单位换算（如 1 Portzebie = 1.33 个标准单位）类比 C 语言里 看似合理、实则陷阱重重的「换算规则」——字面量进制、隐式类型转换、运算符优先级。全书第 8 章的核心命题：软件（语言规则）比硬件（位模式）更难推理；从 Portzebie 的胡闹到 031 vs 25，都是在提醒：不查规则就写代码，等于在用 Portzebie 做工程。

要点

万圣节 vs 圣诞节：八进制字面量陷阱

C 以 0 开头 的整数字面量是 八进制，不是十进制：

int halloween = 031;   /* 八进制：3×8 + 1 = 25 */
int christmas = 25;    /* 十进制：25 */

/* halloween == christmas  →  true */
printf("%d %d\n", 031, 25);  /* 输出：25 25 */
写法 程序员直觉 实际值
031 像「10 月 31 日」 25（八进制）
25 「12 月 25 日」 25（十进制）
0 前缀 有时当「填充零」 八进制标志

工程规则：

  • 除 位掩码、权限位 等明确场景外，禁止 用前导 0 写十进制数；008 甚至 编译错误（八进制无数字 8）。
  • 位常量用 0x 十六进制 或 (1u << n)，可读且无二义性。
  • Code review 看到 0\d+ 应警觉：是八进制还是手滑？

Portzebie 度量衡的寓意

书中 Portzebie 来自 Mad 杂志，是一套用 完全不合理换算 堆出来的单位体系。作者用它映射 C 的 「隐式规则」：

Portzebie 式胡闹 C 语言对应
单位名称听起来正经 unsigned 静默提升、usual arithmetic conversions（8.3）
换算表要背才能用 运算符优先级表（8.8、operator-precedence-cheatsheet.md）
混用单位出灾难 = vs ==、& vs &&（8.2、8.8）

题目 1： 以下代码有什么可移植性问题？

int x = 0x7FFFFFFF;

参考答案

有符号整数溢出是未定义行为——不同平台/编译器结果可能不同（可能回绕到 INT_MIN，可能优化掉相关检查）。可移植代码不应依赖有符号溢出的行为。其他可移植性问题：char 符号性、大小端、结构体对齐、指针宽度、右移行为。用 int32_t 等固定宽度类型和明确的符号性提高可移植性。

8.2

根据位模式构筑图形

本节讲什么

书中用 ASCII 位图（把字符矩阵当作像素）展示：同一块内存的位模式，在不同解释下可以是图形、整数或指令。这直接依赖 按位与 &、移位 << >> 和 掩码（mask）——而 & 的优先级低于 ==，引出了本章第一个经典 「万圣节问题」 的前奏：程序员以为在测 某位是否为 1，实际却在写 val & (mask == 1)。

要点

位模式与图形

/* 假设每个 char 是一行 8 像素，1 表示亮 */
unsigned char row = 0b10110100;  /* 或 0xB4 */
if (row & 0x80) putchar('#'); else putchar('.');
  • 硬件视角：内存是一串 bit；& 掩码 提取字段，| 合并， ^ 翻转， << >> 对齐。
  • 软件视角：必须 加括号 表达意图；不能依赖「读起来像数学」的直觉。

优先级陷阱：val & mask == 1（万圣节问题之一）

== 优先级高于 &（见 8.8 表、cheatsheet）：

/* 意图：测试 val 的某位（mask）是否为 1 */
if (val & mask == 1)   /* ❌ 实际：(val & (mask == 1)) */
    ...

/* mask == 1 为 0 或 1；val & 0/1 几乎永远不是「测位」 */
表达式 解析 常见后果
val & mask == 1 val & (mask == 1) 逻辑完全偏离
(val & mask) == 1 测 mask 覆盖的位 是否等于 1 ✅ 意图
val & mask 非零即真（测 任意被置位） 常用写法

万圣节问题（完整版，8.8）——= 与 == 混淆：

if ((a = b) == 0)   /* ✅ 赋值 b 给 a，再比较是否为 0 */
    ...

if (a = b == 0)     /* ❌ 解析：a = (b == 0)；a 只能是 0 或 1 */
    ...

工程规则 — Yoda 条件（把常量在左，防手滑成赋值）：

if (0 == a) { ... }           /* 写成 if (0 = a) 编译失败 */
if (1 == (val & mask)) { ... } /* 测位 */

位运算速查

运算 含义 典型用途
x & mask 保留 mask 为 1 的位 取字段、测位
x \| flags 置位 打开选项
x & ~mask 清位 关闭选项
x ^ mask 翻转 mask 位 切换标志
x << n / >> n 移位 乘除 2ⁿ、对齐

注意：>> 对有符号负数 可能是 算术右移（实现定义/ UB 边界，C11 对负值右移有明确规定）；位图代码优先 unsigned。

与 031 八进制笑话的联系（8.1）

位常量 0377（八进制）= 0xFF（十六进制）= 255——再次说明：前导 0 改变数值解释。写掩码时用 0xFF 或 (1u << 7) - 1，避免 Portzebie 式混乱。

8.3

在等待时类型发生了变化

本节讲什么

表达式求值时，操作数 在「你等待结果」的过程中已被隐式转换——这就是书名 「types changed while waiting」 的含义。本节讲 整型提升（integer promotion） 与 寻常算术转换（usual arithmetic conversions）： char 变 int、 unsigned 与 signed 混合 时 符号位被 reinterpret，导致比较、移位、位运算结果 与纸面推算不符。这是 8.8 求值顺序 之外的第二维陷阱：类型在变，值域也在变。

要点

整型提升（Integer Promotion）

C 标准：在 int 能表示原类型所有值 时， char/short/unsigned char/unsigned short 等 小于 int 的类型 在大多数表达式中 先提升为 int（若 int 不够则 unsigned int）。

char c1 = 0xFF, c2 = 0xFF;
if (c1 == c2) ...   /* 两操作数都提升为 int 0xFF，比较为真 */

unsigned char u = 0xFF;
int i = u;           /* u 提升为 int 255，赋值正确 */

** surprises**：

char c = -1;
unsigned u = 1;
if (c < u) ...       /* c 提升为 int(-1)；与 u 比较时 c 再转为 unsigned → 很大的数 → 假 */
场景 机制 结果
signed vs unsigned 比较 signed → unsigned 负数变超大 unsigned
混合运算 usual arithmetic conversions 两操作数变 同一类型
printf %d 传 char 可变参数 default argument promotions 必须 显式 (int)c 或匹配格式

寻常算术转换（Usual Arithmetic Conversions）

对二元算术/比较运算，编译器将操作数转为 「共同类型」：

  1. 若类型 等级不同，较低者 提升 到较高（ long double > double > float > 整型链 ）
  2. 若 signed / unsigned 同级， signed 变 unsigned（当 unsigned 能表示 signed 全范围时；否则两者都变 更大 signed——规则细节见标准，面试记 「unsigned 常赢 signed」 即可）
unsigned short a = 65535;
int b = -1;
if (a + b > 0) ...  /* a 提升为 int；65535 + (-1) = 65534 > 0 */

「等待时类型变化」与副作用

类型转换本身 不是 序列点，但会 改变副作用可见时的位宽：

char buf[4];
/* 假设某平台 int 为 4 字节；*(int*)buf 读写可能 UB（对齐 ch07） */

与 8.8 联动：即使 求值顺序 合法， 转换后的值 也可能与程序员 mental model 不一致—— i = i++ + ++i 在 UB 之外，还有大量 「合法但反直觉」 的 unsigned 环绕 行为（实现定义/模运算）。

整型常量与 031（8.1）

int x = 031;        /* 八进制 25，类型 int */
long y = 031L;      /* long */
unsigned z = 031u;  /* unsigned */

字面量 后缀 L/u/ll 与 前导 0 八进制 叠加时，review 要 双重核对。

工程规则

  • 比较 有符号与无符号 时 显式 cast 到同一宽度的 int64_t/uint64_t（ <stdint.h> ）
  • 位运算 操作数用 unsigned 或 uint32_t，避免符号扩展
  • 不要 假设 char 是有符号还是无符号——由实现定义（-funsigned-char）

8.4

原型之痛

本节讲什么

函数原型（function prototype） 是 ANSI C 最重要的改进之一：在 调用前 声明 参数个数与类型，使编译器能 检查实参、自动插入 默认参数提升（default argument promotions）。本节回顾 K&R C 时代 无原型 的写法及其痛苦——与 8.1 的 Portzebie 类似，靠约定而非编译器 维系类型正确；并梳理 隐式 int 历史、旧式声明 vs 原型声明 的语法差异。

要点

K&R 风格 vs ANSI 原型

K&R 定义（参数类型写在函数体 内）：

/* 旧式声明：编译器不检查实参类型 */
int foo();
foo(x, y);   /* 可能 silently wrong */

/* K&R 定义 */
int foo(a, b)
    int a;
    char *b;
{
    ...
}

ANSI 原型：

int foo(int a, char *b);   /* 原型：完整类型信息 */
int foo(int, char *);      /* 重复声明可省略参数名 */
特性 无原型 () 原型 (int, char*)
实参类型检查 ❌ ✅
() 含义（C++ 不同） 旧式：不检查 N/A
空参 void foo(void) foo() ≠ 无参保证 void 显式无参
链接 仍参与 外部链接 同左

C 规则：定义若用原型，声明也必须用原型；混用是 约束违规（constraint violation） 或 未定义行为（视标准版本与诊断）。

隐式 int 的历史

K&R 时代 未写类型 的函数返回值 默认为 int：

/*  ancient */
foo() { return 1; }   /* 返回 int — 现代编译器报错 */

C99 起 删除隐式 int；遗留代码、老教材是 面试 trivia。与 8.1 031 同属 「老 C 习惯在现代是坑」。

默认参数提升（Default Argument Promotions）

无原型调用 或 可变参数 ... 时， float → double， char/short → int/unsigned int：

void old();
old('a');        /* char 提升为 int 传递 */
printf("%c", c); /* 必须传 int（提升后） */

有原型 的普通调用 不做 这种提升到 int 的转换（类型必须 完全匹配或可赋值转换）—— short 实参给 short 形参 不会先变 int 再截断。

原型如何减轻「等待中类型变化」（8.3）

原型让 隐式转换发生在编译期可见处：

void bar(unsigned u);
bar(-1);   /* -1 转为 unsigned → 巨大值；有原型时编译器可能 warn */

-Wall 对 sign-conversion 的警告应打开（ch02 工具链习惯）。

工程规则

  • 头文件 放 完整原型；.c 中 定义与声明一致
  • 禁止 新代码使用 无原型 ()；用 (void) 表示无参
  • static 函数 也写原型（文件内 第一个定义前 或头文件）

与后续衔接

  • 8.5：原型 仍救不了 的情况——类型不匹配但宽度相同、varargs、链接可见性
  • 8.6–8.7： getchar() 返回 int 非 char（ EOF 与 0xFF）；FSM 函数 用原型 隔离状态
  • ch05：链接 时符号 类型必须匹配（5.3）；ch03：读 int (*signal(int, void (*)(int)))(int) 类声明
  • ch02：() 空参语义 与 C++ 差异（2.3 符号过载）

8.5

原型在什么地方会失败

本节讲什么

原型不是银弹。本节列举 编译器仍无法（或尚未）拦住 的错误：声明与定义不一致、结构体/指针混淆但 ABI 碰巧相同、可变参数 ...、跨翻译单元旧式声明、链接时符号涂改（linkage mismatch）。理解这些边界，才能明白为何 8.8 的 UB 与 8.9 的 cast 仍会在「有原型」的代码里出现——类型系统覆盖不到求值顺序。

要点

声明与定义不匹配

/* file1.c */
int foo(int x) { return x; }

/* file2.c — 错误声明 */
double foo(double x);   /* 链接可能仍成功（名字相同），调用约定/解释错误 → 灾难 */
失败模式 原因 后果
返回类型不同 C 不要求 跨 TU 返回类型诊断（旧链接） 返回值 按错误类型解释
指针 vs 整数 宽度相同（如 64 位） 静默错误
char* vs const char* 形参兼容规则 可能 const 丢失

现代编译器 -Wlto / 全程序优化 可抓部分跨 TU 错误；传统 .o 链接 仍可能 只报 warning 或不报。

可变参数：printf 的原型局限

int printf(const char *fmt, ...);
  • 编译器 仅检查 固定参数（ fmt ）
  • ... 部分无类型 → %d 配 long long、 %s 配非指针 → UB
  • 默认提升： float 必须写 %f 但传 double； char 传 int

工程规则： printf 格式串与实参一一核对；生产代码优先 snprintf + 静态检查（ __attribute__(format) ）。

旧式声明与混合风格

/* header 里旧式 */
double atof();

/* 调用 */
atof("3.14");   /* 现代：仍可能链接 libc 的 double atof(const char*) */

一个 TU 用原型、另一个无原型 → C 标准未定义（C99 约束）。维护 单一头文件 是唯一稳妥做法。

Linkage 与 static / inline

问题 说明
static 函数重复名 各 TU 独立，无链接冲突
inline 无外部定义 C99 extern inline 规则易踩坑
C 与 C++ 链接 extern "C" 与 重载 不匹配

原型救不了「表达式 UB」（8.8）

void f(int i);
f(i++ + ++i);   /* 原型正确；实参求值顺序仍 UB */

类型检查 ≠ 副作用顺序检查——这是 8.8 Christmas 问题 仍存在的根本原因。

与 ch05 链接错误对照

  • ch05：符号解析、强/弱符号、COMMON
  • 8.5：符号同名但类型语义不同 — 链接「成功」但运行错误，比 undefined reference 更阴险

与后续衔接

  • 8.8：求值顺序、序列点 — 原型完全不管
  • 8.9：程序员用 cast「骗过」原型 → void* 丢失类型
  • 8.6：getchar 返回 int — 用 char 接 是 原型正确用法 仍可能 逻辑错

8.6

不需要按回车键就能得到一个字符

本节讲什么

标准 getchar() 在 行缓冲（canonical） 终端上 必须读到换行才返回——与 FSM（8.7） 逐字符解析的需求冲突。本节介绍 终端 raw/cbreak 模式（ termios ）、getchar/getc 返回 int 而非 char（ EOF 与 0xFF** ）、以及 **ungetc` 把字符 推回流 的技巧。这是 原型正确（8.4）仍可能写错 的典型案例：类型用错一位，逻辑全毁。

要点

行缓冲 vs 即时输入

模式 行为 典型场景
Canonical（规范） 编辑到 Enter 才提交一行 shell、普通文本输入
Cbreak 关闭行编辑， 按键即达程序 vi、游戏
Raw 关闭 回显、信号字符处理 等 全屏 TUI

POSIX termios 骨架（Linux / WSL / macOS）：

#include <termios.h>
#include <unistd.h>

static struct termios saved;

void tty_raw(int enable)
{
    struct termios t;
    tcgetattr(STDIN_FILENO, &t);
    if (enable) {
        saved = t;
        t.c_lflag &= ~(ICANON | ECHO);  /* 关规范模式与回显 */
        t.c_cc[VMIN] = 1;
        t.c_cc[VTIME] = 0;
        tcsetattr(STDIN_FILENO, TCSAFLUSH, &t);
    } else {
        tcsetattr(STDIN_FILENO, TCSAFLUSH, &saved);
    }
}

Windows 注意：原生 Win32 用 SetConsoleMode；WSL 可用 termios。跨平台 库：ncurses、readline（行编辑专用）。

getchar() 返回 int，不是 char

int ch = getchar();   /* ✅ */
if (ch == EOF) ...

char c = getchar();   /* ❌ 若字节 0xFF，与 EOF 混淆（实现相关） */
值 含义
0–255 unsigned char 字节（提升为 非负 int ）
EOF（通常 -1） 流结束或错误

8.3/8.5 联动： char 可能 signed， 0xFF → -1，与 EOF 相等 → 循环提前结束。

ungetc：解析器「偷看」下一字符

int ch = getchar();
if (isdigit(ch)) {
    /* 读多了，退回 */
    ungetc(ch, stdin);
}
  • 标准保证：每流 至少一次 ungetc（实现常更多）
  • 与 FSM：状态机在 不消耗 字符的情况下 试探 下一输入

与 8.7 FSM 的配合

  按键 → getchar (int) → FSM switch / 表驱动
              ↑ ungetc 回退

工程规则：

  • 交互程序 退出前恢复终端（ atexit / signal handler 里 tty_raw(0)）
  • Ctrl+C 在 raw 下常需 自行处理 SIGINT
  • 单元测试 FSM 用 字符串缓冲 + 指针 代替 getchar

8.7

用 C 语言实现有限状态机

本节讲什么

有限状态机（FSM） 用 状态 + 输入 → 下一状态/动作 描述解析器、协议、词法分析。本节展示 C 中两种主流写法：switch 状态变量 与 表驱动（state table）——清晰、可测、无 goto spaghetti（除非刻意 Duff's device 优化）。FSM 代码 大量依赖 ==、&&、括号；是 8.8 优先级 与 8.6 逐字符输入 的 正面工程范例：规则写清楚，比硬件状态机还啰嗦，但可维护。

要点

状态变量 + switch

typedef enum { START, IN_NUM, IN_ID, DONE } State;

State st = START;
int ch;

while (st != DONE && (ch = getchar()) != EOF) {
    switch (st) {
    case START:
        if (isalpha(ch))      st = IN_ID;
        else if (isdigit(ch)) st = IN_NUM;
        else if (ch == ' ')     /* 保持 START */;
        else                    st = DONE;
        break;
    case IN_NUM:
        if (!isdigit(ch)) { ungetc(ch, stdin); st = DONE; }
        break;
    case IN_ID:
        if (!isalnum(ch)) { ungetc(ch, stdin); st = DONE; }
        break;
    default:
        st = DONE;
        break;
    }
}

要点：

  • switch 贯穿（fall-through） 必须 break 或 注释 /* FALLTHROUGH */（ch02）
  • 条件用 && 短路（8.8）： while (st != DONE && (ch = getchar()) != EOF) — 注意 = 在括号内 是 赋值，不是 Halloween 陷阱

表驱动 FSM

typedef void (*Action)(int ch);

typedef struct {
    State next;
    Action act;
} Transition;

/* current_state][input_class] → Transition */
static const Transition table[STATE_COUNT][CLASS_COUNT];
方式 优点 缺点
switch 直观、易 debug 状态多时臃肿
表驱动 数据与逻辑分离、易可视化 间接调用、表大小

与 8.8 运算符纪律

FSM 条件 反面教材（勿写）：

if (st & READY == 1)     /* == 高于 & → st & (READY==1) */
if (a = ch == 'x')       /* Halloween：a 只能是 0/1 */

正面写法：

if ((st & READY) != 0)
if (ch == 'x') { a = 1; } else { a = 0; }

测试策略

  • 表驱动：对 table[s][c] 单元测试， 不依赖 getchar
  • 输入串： const char *p = "123 abc"; 循环 *p++
  • 覆盖 ungetc 路径：输入 边界字符 后 断言状态回退

8.8

软件比硬件更困难

本节讲什么

书名双关的 技术内核 在本节集中爆发：硬件位模式 遵循布尔代数，可预测；C 表达式 还要叠加 运算符优先级、结合性、求值顺序、序列点、隐式转换——组合出 同一段代码不同编译器/优化级别不同结果 的 未定义行为（UB）。本节是全章 最重要 的小节：完整优先级表、Christmas 问题、Halloween 问题、短路 && ||、逗号运算符陷阱、函数实参中的多次修改、C11 sequenced-before 与旧 sequence point 术语对照，以及 工程防御规则。

要点

运算符优先级与结合性（概览）

从高到低（完整表见 operator-precedence-cheatsheet.md 与 README）：

级别 运算符 结合性 ⚠️ 易混
1 () [ -> . 左 . 与 *
2 ! ~ ++ -- + - * & (type) sizeof 右 ++ 后缀 vs 前缀
3 * / % 左
4 + - 左
5 << >> 左
6 < <= > >= 左
7 == != 左 ⚠️ == vs &
8 & 左 ⚠️ & vs &&
9 ^ 左
10 | 左
11 && 左 短路
12 || 左 短路
13 ?: 右
14 = += … 右 ⚠️ = vs ==
15 , 左 ⚠️ 逗号 vs 实参逗号

括号 不受优先级限制；怀疑时就加括号——可读性 > 炫技。

Halloween 问题：= 与 ==

if ((a = b) == 0)   /* ✅ 赋值后比较 */
    ...

if (a = b == 0)     /* ❌ 等价 a = (b == 0)；a ∈ {0,1} */
    ...

Yoda 条件：if (0 == a) — 手滑 0 = a 编译失败。

与 8.2 位运算：if (1 == (val & mask))。

Christmas 问题：同一标量多次修改 → UB

i = i++ + ++i;   /* ❌ UB：同一表达式对 i 修改不止一次且无序列点 */

C11 表述：i++ 与 ++i 的值计算 彼此 未 sequenced；对 i 的赋值 亦与它们 未 sequenced → UB。

类似 UB：

a[i++] = i;           /* UB */
f(i++, ++i);          /* UB：实参求值顺序未指定 */
x = x++ + 1;          /* UB */

合法写法（拆语句，每行 一个 副作用）：

int t = i;
i = i + 1;
i = t + i;

序列点 vs sequenced-before（C11）

术语 时代 含义
Sequence point C89/C99 教学用语 求值中的 完全结束点； && || ?: 首操作数后、分号 ; 前 等
Sequenced before / after C11 起 精确定义 若 A sequenced before B，则 A 的副作用对 B 可见
Unsequenced C11 同一对象 无顺序 的读写 → UB
Indeterminately sequenced C11 函数实参各参数之间

面试一句话：C11 用 sequenced-before 取代「序列点」口语； i=i++ + ++i 在 C99/C11 都是 UB。

仍有序列点语义的例子：

if (p && *p) ...      /* *p 仅在 p 非 0 时求值 — 短路 */
a ? b : c;             /* 仅求值 b 或 c 之一 */
i = 0, j = 1;          /* 逗号：左侧 i=0  sequenced before  j=1 */

短路求值 && 与 ||

if (ptr != NULL && ptr->len > 0)   /* ptr 空则不求值 ->len */
if (fd < 0 || (n = read(...)) < 0)
运算符 左侧为假/真时 右侧
&& 左 假 → 整个假 不求值
|| 左 真 → 整个真 不求值

⚠️ & 无短路：ptr & ptr->len 在 ptr==NULL 时仍 求值右操作数 → 崩溃。

demo04_short_circuit（README）：对比 && vs & 对 空指针 的行为。

逗号运算符 , vs 函数实参逗号

逗号运算符（优先级 最低之一）：

i = (j = 1, k = 2, j + k);   /* i == 3；逗号表达式值为最后一项 */
for (i = 0, j = n; i < j; i++, j--)  /* for 头里的逗号合法 */

函数调用：

f(a++, b++);   /* 这里的逗号 **不是** 逗号运算符；是语法分隔符 */
               /* a++ 与 b++ 求值顺序 **未指定** → 若共享状态则危险 */
逗号运算符 , 实参列表逗号
语义 先左后右，值为 右操作数 分隔实参
顺序 左 sequenced before 右 各实参 indeterminately sequenced
典型坑 if (a=1, b=2) 条件为 2（真） f(i++, ++i) UB

后缀 ++ 与优先级

*p++     /* *(p++)：先取 p 旧值所指，再 p++ */
(*p)++   /* 对 *p 自增 */
*++p     /* 先 ++p 再解引用 */

++ 后缀优先级高于 *，但 结合性 决定 后缀 ++ 绑定最近操作数。

工程规则（务必遵守）

  1. 一行一副作用：禁止 i=i++ + ++i、a[i++]=i
  2. 比较用 ==，赋值单独一行；防手滑用 Yoda：0 == x
  3. 位测用括号：(val & mask) == 1
  4. 逻辑条件用 &&/||，位合并用 &/|
  5. 函数实参 不含 同一变量的多次 ++/--
  6. 宏参数 若含副作用， 括号 + 避免多次求值（ch02 MAX）
  7. 开启 -Wall -Wsequence-point -Wparentheses（GCC）

如何进行强制类型转换，为何要进行类型强制转换

本节讲什么

强制转换（cast） (type)expr 告诉编译器：按另一种类型解释位模式或做数值转换。本节讲 何时必须 cast、何时 cast 是 UB 或 portability 陷阱、以及 cast 与运算符优先级 的交互——(int)*p++ 解析为 ((int)(*p))++ 还是 (int)((*p)++？ 理解 8.3 隐式转换 与 8.8 优先级 后，cast 是 程序员主动接管的「类型在等待中变化」。

要点

何时需要 cast

场景 示例 说明
显式窄化/符号变化 (uint8_t)x 文档化 只取低 8 位
void* 还原 (struct foo*)p malloc 返回 在 C 中 不需 cast；C++ 需要
算术混合 (double)num / den 强制 浮点除法
接口/旧 API (void*)cb 回调 擦除类型 — 尽量 少
位 reinterpret (unsigned)(signed)x 实现定义 部分场景

危险 cast（与 ch07 内存）

float f = 1.0f;
int *ip = (int *)&f;      /* 严格别名 violation → UB（除非 char* 字节访问） */
*(int *)&f = 0;           /* 类型双关 — 勿在生产代码使用 */

struct { int a; } s;
int *p = (int *)&s;       /* 可能违反对齐/别名 */

合法字节视角：unsigned char *cp = (unsigned char *)&obj — memcpy 语义，ch07 序列化。

cast 与优先级

Cast 属于一元运算符，优先级高、结合性右：

(int)*p++        /* (int)(*(p++))  — 先 p++ 再解引用再转 int */
(int)(*p)++      /* 非法：不能对 cast 结果 ++（非 lvalue） */

(void)(printf("hi\n"), 0);  /* 逗号表达式 cast 成 void 吞掉值 */

与 8.2 位运算：

(unsigned)val & mask   /* ((unsigned)val) & mask */
(unsigned)(val & mask) /* 先 & 再转 unsigned — 不同！ */

永远加括号 表达 cast 作用范围。

隐式 vs 显式（8.3 对照）

隐式 显式 cast
触发 整型提升、赋值转换 程序员 (type)
可见性 易忽略 代码里 显眼
责任 编译器 程序员保证合法

原型（8.4） 失败处常靠 cast silence warning — 掩盖问题：

foo((int)ptr);   /* 若 foo 期望 int 而传指针 — 灾难 */

工程规则

  • cast 不是万能胶；优先 改声明/改 API
  • 禁止 (type)ptr 解 不对齐 对象（ch07 SIGBUS）
  • const cast away — (char*)const_ptr 仅 与只读 API 对接 时用；写入 UB
  • 用 static_cast 等价思维：能否用更安全的 helper 代替？（C 无 static_cast，靠 函数）

万圣节与圣诞节：运算符优先级、序列点、UB。看代码 → 想答案 → 点开验证。

Q1八进制双关
int a = 031;
int b = 25;

if (a == b)
    printf("Halloween == Christmas\n");

输出什么？为什么？

答案与复习指引

答案： 输出 Halloween == Christmas。八进制 031 = 3×8 + 1 = 25 = 十进制 25。

双关： Oct 31（万圣节）= Dec 25（圣诞节）——程序员笑话指的是八进制 vs 十进制，不是日历。

教训： 不要用前导 0 写十进制数——编译器理解为八进制。

复习： → 8.1 Portzebie 度量衡系统

Q2Christmas 问题 — UB
int i = 1;
i = i++ + ++i;
printf("%d\n", i);

i 的值是多少？这段代码安全吗？

答案与复习指引

答案： 未定义行为（UB）——i 在同一表达式中被修改两次（i++ 和 ++i），且没有 sequenced-before 关系保证顺序。结果可能是 3、4、5 或任何值——编译器甚至可以删除整个表达式。

规则： 一行内一个变量最多修改一次。拆成多行：

int tmp1 = i++;   // i=1, tmp1=1, i→2
int tmp2 = ++i;   // i→3, tmp2=3
i = tmp1 + tmp2;  // i = 1+3 = 4

Q3位测优先级陷阱
int flags = 0x05;   // 0b101
int mask = 0x01;    // 测第 0 位

if (flags & mask == 1)
    printf("bit 0 is set\n");
else
    printf("bit 0 is not set\n");

输出什么？如何修正？

答案与复习指引

答案： 输出 bit 0 is not set。== 优先级高于 &，表达式被解析为 flags & (mask == 1) = flags & 1（true）= flags & 1...

等一下，mask == 1 为真（值 1），所以 flags & 1 = 0x05 & 0x01 = 1（真）→ 应该输出 bit 0 is set。

重新分析：mask == 1 → 0x01 == 1 → true → 值为 1。flags & 1 → 0x05 & 0x01 → 1 → 真。所以输出 bit 0 is set。

但如果 mask 不是 1，比如 mask = 0x04（测第 2 位）：mask == 1 → false → 值 0 → flags & 0 = 0 → 假 → 输出 bit 0 is not set，即使第 2 位确实设置了！

修正： if ((flags & mask) == mask) 或 if (flags & mask) — 位运算加括号。

复习： → 8.2 根据位模式构筑图形 · 8.8 软件比硬件更困难

Q4短路 vs 按位
struct Node *p = NULL;

// 版本 A
if (p && p->next)
    printf("has next\n");

// 版本 B
if (p & p->next)
    printf("has next\n");

版本 B 会发生什么？

答案与复习指引

答案： 版本 B 崩溃（SIGSEGV）。&& 是逻辑短路——p 为 NULL 时不再求值 p->next。& 是按位与——两边都求值，p->next 在 p=NULL 时解引用空指针 → 崩溃。

规则： 条件判断用 &&/||（短路）；位操作用 &/|。两者优先级也不同——&& 远低于 &。
