11.1

初识 OOP

本节讲什么

全书 ch1–ch10 在 C 层面建立了声明、链接、内存、指针与函数表等底层能力；ch11 在此基础上回答：「你懂 C，C++ 难在哪？」 本节先给出 OOP（面向对象编程） 的三块拼图——抽象、封装、继承/多态——并强调 C++ 与 C 的 血缘关系：C++ 早期几乎就是 「带类的 C」，绝大多数 C 程序可经 C 编译器子集 或 extern "C" 与 C++ 混编。同时预告 C++ 更严格 的规则（void*、链接、const 等），这些「陷阱」在 11.17 集中对照。

从 C 思维到 OOP 思维

C 常见模式（ch10 10.7）：

typedef struct {
    int (*draw)(void *self);
} ShapeOps;

C++ 等价方向（细节见 11.4, 11.13）：

class Shape {
public:
    virtual void draw() = 0;   /* 纯虚 → 接口类 */
    virtual ~Shape() = default;
};

关键转变：把 self 指针 + 函数表 交给编译器生成 vtable / vptr（11.14–11.16）。

严格性陷阱预览（C 程序员易踩）

  1. void*：C 里 int *p = malloc(...) 常见；C++ 中 malloc 返回值需 cast（更推荐 new，11.17）
  2. 链接：C++ name mangling — 同名函数因参数不同而符号不同；与 C 库链接必须用 extern "C"
  3. const 全局：C 中 const int x = 1 往往 外部链接；C++ 默认 内部链接（11.17）
  4. 未初始化：C++ 对 成员、局部对象 的初始化规则比 C 更细（ctor, 11.4）

题目 1： C++ 的引用和 C 的指针有什么本质区别？

int x = 42;
int &r = x;   // C++ 引用
int *p = &x;  // C 指针
参考答案

引用：必须初始化、不能为空、不能改绑、使用时无需解引用（r 直接就是 x 的别名）。指针：可以不初始化、可以为 NULL、可以改指向、使用时需解引用（*p）。引用更安全（不会悬空），但指针更灵活（可表达「无对象」）。C 没有引用，只能用指针。C++ 的函数参数推荐用引用——避免拷贝且语法更自然。

11.2

抽象——取事物的本质特性

本节讲什么

抽象（abstraction） 是 OOP 的第一块基石：只保留与当前问题相关的属性与行为，忽略无关细节。对 C 程序员而言，这并不全新—— FILE* 就是典型抽象：你只调用 fopen / fread / fclose，不必关心缓冲区、系统调用或内核页缓存。C++ 的 class 让你 自定义 这种「黑盒接口」，并在 编译期 用类型系统强制边界（比裸 struct + 约定 更硬）。

要点

抽象在 C 里已存在

C 抽象 隐藏的细节 暴露的接口
FILE* 缓冲区、fd、锁 stdio
void* 通用容器 具体类型 仅「一块内存地址」
设备驱动 ops 表 硬件寄存器 open/read/write/ioctl

ch07–ch10 讲的是 看清底层；抽象 讲的是 在合适层次故意不看底层。

C++ 抽象：类型即契约

class Stack {
public:
    void push(int x);
    int  pop();
    bool empty() const;
private:
    /* 实现可换：数组 / 链表 / vector — 用户不可见 */
    int  *data_;
    size_t top_;
};

用户代码 只依赖 push/pop/empty，不依赖 data_ 布局 — 这就是 11.3 封装 与 11.5 访问控制 要保护的东西。

抽象 vs 具体

具体（implementation）     抽象（interface）
─────────────────────     ─────────────────
数组下标、指针算术    →    「栈」：后进先出
寄存器位操作          →    「串口」：send/recv
红黑树节点旋转        →    「map」：insert/find

设计原则：接口 稳定，实现 可替换。C 用 不透明指针（typedef struct X X 不暴露定义）达到类似效果；C++ 用 private + 头文件最小暴露。

抽象层次与 ch04/ch08 的呼应

  • ch04：「数组 ≠ 指针」— 抽象层选错类型会穿透到底层
  • ch08：软件规则之难 — 抽象 不能 违背语言/ABI 真实规则
  • ch11：在 理解底层 的前提下，用 class 接口 把复杂度 关进盒子

抽象过头的风险（预告 11.18–11.19）

抽象不是免费午餐：虚函数、RTTI、模板 都有成本。内核/DPDK 等场景常 刻意不用 高级抽象，保留 C 风格 函数表 + 静态分配（见 11.15, c-to-cpp-migration-checklist.md §7）。

11.3

封装——把相关的类型、数据和函数组合在一起

本节讲什么

封装（encapsulation） 把 数据 与 操作该数据的函数 绑进 同一个用户定义类型（通常是 class）。C 里常见 struct Point { int x, y; } + 全局函数 point_move(&p, dx, dy)；C++ 写成 p.move(dx, dy)，编译器隐式传入 this（11.7）。封装 + 访问控制（11.5） 构成 不变量（invariant） 的防火墙：外部无法绕过 push 直接改 top_ 破坏栈语义。

要点

C 风格 vs C++ 封装

C C++
struct Account { double bal; }; class Account { ... };
account_deposit(&a, 100); a.deposit(100);
谁都能改 a.bal private 仅成员/友元可改 
class Account {
public:
    void deposit(double amount) {
        if (amount > 0)
            balance_ += amount;
    }
    double balance() const { return balance_; }
private:
    double balance_ = 0.0;   /* 不变量：余额非负由接口保证 */
};

class 与 struct 的唯一默认差异

在 C++ 中：

关键字 默认访问 典型用途
struct public POD、与 C 互操作、trait 标签
class private OOP 类型、不变量封装 
struct CCompat { int x; };      /* 默认 public — 类似 C struct */
class  Encapsulated { int x; }; /* 默认 private */

成员布局 与 C struct 规则兼容（无 virtual 时），便于 ABI 互操作（11.17 extern "C"）。

封装带来的工程收益

  1. 局部化修改：换内部表示（数组→vector）不影响调用方
  2. 强制入口：所有状态变更经 成员函数，便于断言/日志
  3. 文档即类型：Account 比「两个 double + 若干函数」更易读

  • ch05：符号可见性 — static 文件内函数 类似 private 实现细节

11.4

展示一些类——用户定义类型享有和预定义类型一样的权限

本节讲什么

C++ 的 用户定义类型（UDT） 与 int、double 一样，可以 在栈上声明、传参、返回、放数组、作结构成员。本节通过完整 class 示例引入 构造函数（ctor） 与 析构函数（dtor） — 对象 创建时自动初始化、销毁时自动清理，这是 C malloc/free + 手动 init 的 RAII 雏形。理解 ctor/dtor 是后续 继承、虚析构、多态（11.8, 11.13） 的前提。

要点

最小完整类示例

class String {
public:
    String(const char *s);     /* 构造函数 */
    ~String();                 /* 析构函数 */
    size_t length() const;
private:
    char *data_;
    size_t len_;
};

String::String(const char *s) {
    len_ = std::strlen(s);
    data_ = new char[len_ + 1];
    std::strcpy(data_, s);
}

String::~String() {
    delete[] data_;            /* 与 new[] 配对 */
}

栈上使用 与内置类型无异：

void foo() {
    String greeting("hello");  /* ctor */
    /* ... */
}                              /* dtor 自动调用 */

对比 C（ch07, ch10）：须 create_string + destroy_string 且易漏 free。

ctor / dtor 规则速查

11.5

访问控制

本节讲什么

C++ 用 public / private / protected 在 编译期 强制 谁能访问谁。C 只能靠 命名约定（_hidden）或 不透明指针 做「软封装」；C++ 把 接口与实现的分界 写进语言。protected 专为 继承（11.8） 设计：派生类可访问基类 protected 成员，外部仍不可。本节是 封装（11.3） 的语法保障。

要点

三级访问

说明符 类内 派生类 外部代码
public ✅ ✅ ✅
protected ✅ ✅ ❌
private ✅ ❌ ❌ 
class Base {
protected:
    int prot_ = 0;    /* 子类可用，外部不可 */
private:
    int priv_ = 0;    /* 仅 Base 成员/友元 */
public:
    int pub_ = 0;     /* 接口 */
};

class Derived : public Base {
    void f() { prot_ = 1; /* OK */  /* priv_ = 1; // 编译错误 */ }
};

继承方式与访问级别

继承写法 基类 public 成员在派生类中
class D : public B public
class D : protected B protected
class D : private B private

常用：public 继承 表达 「is-a」；private 继承 表达 「用实现」（较少见）。

class vs struct 再访

struct S { int x; };           /* 默认 public */
class  C { int x; };           /* 默认 private */

与 C 互操作时常用 struct 暴露 POD 字段；业务类型用 class 默认私有。

友元（friend）— 有意破坏封装

class Matrix {
    friend Matrix operator*(const Matrix &a, const Matrix &b);
private:
    double data_[4];
};

友元函数/类 可访问 private — 用于 运算符重载（11.11） 等需对称访问的场景。不要滥用。

与 C 模块边界的对比

C C++
static 函数 — 翻译单元内 private 成员 — 类型内
不透明 struct — 无完整定义 class + 前向声明 — pimpl 惯用法
头文件暴露全部字段 头文件只暴露 public 接口

pimpl 惯用法（降低编译依赖）：

class Widget {
public:
    Widget();
    ~Widget();
    void draw();
private:
    struct Impl;

};

private 只防 编译期误用，不加密内存；指针/布局 hack 仍可越界（ch07）。内核/DPDK 更依赖 约定 + review 而非 private。

11.7

如何调用成员函数

本节讲什么

obj.method(args) 在机器级近似 method(&obj, args) — 编译器隐式传入 this 指针，指向 当前对象。理解 this 是把 C 的 「第一个参数 self/ctx」 习惯 形式化 的关键一步；也是理解 多态（11.13–11.16） 中 vptr 位置 的基础。本节还对比 静态成员函数（无 this）与 普通成员函数。

要点

this 指针

class Counter {
public:
    void inc() { ++value_; }           /* 等价 ++this->value_ */
    int  get() const { return value_; }
private:
    int value_ = 0;
};

Counter c;
c.inc();   /* 编译器生成 Counter::inc(&c) */
概念 说明
this 类型 T*（非 const 成员）或 const T*（const 成员）
谁分配 this 调用方（栈/堆对象地址）
C 类比 void counter_inc(Counter *self)

成员函数调用机制（无虚函数）

对象内存布局（无 virtual）:
┌─────────────────┐
│  value_         │  ← this 指向此处
│  ...其他成员    │
└─────────────────┘

call c.inc():
  1. 取 c 的地址 → this
  2. 跳转 Counter::inc
  3. 通过 this 访问 value_

与 C 函数表区别：非虚成员 编译期绑定 固定地址；virtual 才走 vtable（11.13）。

    int id() const { return id_; }
private:
    static int seq_;
    int id_;
};

实例成员 ✅ ✅ obj.f()
静态成员 ❌ ❌（无实例） Class::f()

const 成员函数

承诺：对 const 对象 可调用；不修改 逻辑状态（mutable 例外，了解即可）。

11.8

继承——复用已经定义的操作

本节讲什么

继承（inheritance） 让 派生类 获得 基类 的成员与行为，在 不修改基类源码 的前提下 扩展或特化。public 继承 表达 「is-a」（圆是图形的特例）。C 里用 结构体嵌入 + 手动转发 模拟；C++ 用 语法 + 访问控制 固化。本节还涉及 构造/析构顺序 与 函数覆盖（override） — 多态的前奏（11.13）。

要点

基本继承语法

class Shape {
public:
    void move(int dx, int dy) { x_ += dx; y_ += dy; }
    virtual void draw() { /* 默认 */ }
protected:
    int x_ = 0, y_ = 0;
};

class Circle : public Shape {
public:
    void draw() override { /* 画圆 — 11.13 需 virtual */ }
    void set_radius(int r) { r_ = r; }
private:
    int r_ = 1;
};

Circle 自动拥有 x_, y_, move — 代码复用。

构造与析构顺序

构造: Base → Derived
析构: Derived → Base

Circle c;   /* 先 Shape 子对象 ctor，再 Circle 成员 */

规则：派生 ctor 必须（直接或委托）初始化基类；基类 无默认 ctor 时 显式 Circle(int r) : Shape(), r_(r) {}。

覆盖 vs 隐藏

术语 条件 绑定
覆盖 override 基类 virtual + 签名相同 运行时（11.13）
隐藏 hide 派生同名但 无 virtual 或参数不同 编译期 按静态类型 
Shape *p = &circle;
p->draw();   /* virtual → Circle::draw；非 virtual → Shape::draw */

C 模拟继承

typedef struct {
    Shape base;   /* 嵌入 — 类似继承子对象 */
    int radius;
} Circle;

void circle_draw(void *self) {
    Circle *c = (Circle *)self;
    /* ... */
}

Linux container_of 从 base 反推 Circle* — C 惯用法（11.15）。C++ 编译器自动做偏移。

继承的代价

  • 对象更大：含 基类子对象
  • 布局复杂：多继承时 多个基类子对象（11.9）
  • 耦合：基类改 protected 接口影响所有派生类

组合优于继承：若只是 「有一个」 而非 「是一个」，用 成员对象 而非继承。

虚析构（与 11.4 呼应）

class Base {
public:
    virtual ~Base() = default;
};

多态删除 Base* p = new Derived; delete p; 必须 virtual ~Base()，否则 UB/泄漏。

11.9

多重继承——从两个或更多的基类派生

本节讲什么

C++ 允许 从多个基类派生：class D : public B1, public B2。这带来 更强的复用，也带来 布局、歧义、菱形继承 等复杂度 — 本书以 坦诚警告 的笔调介绍：能用单继承 + 组合解决就不要多继承。C 程序员可把它类比为 一个 struct 里嵌多个基类子结构，但 C++ 还要处理 同名成员冲突 与 vtable 数量。

要点

多重继承语法

class Printable {
public:
    virtual void print() const = 0;
};

class Serializable {
public:
    virtual void serialize() const = 0;
};

class Document : public Printable, public Serializable {
public:
    void print() const override { /* ... */ }
    void serialize() const override { /* ... */ }
};

对象布局（简化）：

Document 对象:
┌──────────────┬──────────────┬─────────────┐
│ Printable    │ Serializable │ Document    │
│ 子对象(vptr?)│ 子对象       │ 自有成员    │
└──────────────┴──────────────┴─────────────┘

多虚基类 → 可能 多个 vptr（11.16 布局因编译器/ABI 而异）。

菱形继承问题

        Base
       /    \
   Left    Right
       \    /
        Join

Join 含 两份 Base 子对象 → Join::Base 歧义。

解决：虚继承 virtual public Base

class Left  : virtual public Base { };
class Right : virtual public Base { };
class Join  : public Left, public Right { };

代价：更复杂的对象布局 与 运行时偏移计算 — 本书观点：复杂，且多数场景不必。

名字歧义与作用域解析

class A { public: void f(); };
class B { public: void f(); };
class C : public A, public B {
    void g() {
        A::f();   /* 显式指定 */
        B::f();
    }
};

编译器不会 自动合并同名函数。

与 C / 内核的对比

C++ 多继承 C / 内核
语言级 is-a 多重 单继承嵌入链 + container_of
虚基类 手动 保证唯一基类实例
多个 vptr 一个 ops 表 或 多表（11.15）

Linux 内核 几乎不用 C++ 多继承；接口类 + 组合 或 C 表 更常见。

实用建议（Expert C 立场）

  1. 默认单继承 + 成员组合
  2. 多继承 主要用于 Mixin 式接口类（全 virtual 纯虚、无数据）
  3. 避免 菱形；若必须，虚继承 并 文档化 ABI
  4. DPDK/嵌入式：零多继承 — 可预测布局优先

重载——作用于不同类型的同一操作具有相同的名字

本节讲什么

函数重载（overloading）：同名函数 因 参数列表不同（个数或类型）而 共存；编译器在 调用点 按 最佳匹配 选择版本。C 不支持 — 须 print_int / print_double 或 void* + 类型标签。重载与 name mangling 直接相关：符号名编码参数类型（11.17 extern "C" 必须关闭 mangling 才能与 C 链接）。

要点

基本重载

void print(int x)    { std::cout << x; }
void print(double x) { std::cout << x; }
void print(const char *s) { std::cout << s; }

print(42);      /* print(int) */
print(3.14);    /* print(double) */
print("hi");    /* print(const char*) */

返回值类型 alone 不能 区分重载 — 必须参数不同。

重载决议（简化）

编译器按顺序 淘汰 不合法候选，再选 最精确转换：

优先级（高→低） 示例
精确匹配 int → int
提升 float → double
标准转换 int → double
用户定义转换 构造函数 / 转换运算符
可变参 ... 最差

二义性 → 编译错误（C 里往往 静默错调）。

与 C 的对比

/* C — 无重载 */
void draw_int(int x);
void draw_point(int x, int y);
/* 或 */
void draw(void *obj, enum type t);

/* C++ */
void draw(int x);
void draw(int x, int y);
void draw(const Shape &s);

类型安全：编译期检查；C 的 void* + enum 易 传错标签。

重载 vs 覆盖（易混）

重载 overload 覆盖 override
范围 同一作用域 多个函数 基类/派生类 同名 virtual
绑定 编译期 运行时（11.13）
参数 必须不同 通常相同

重载与链接 / extern "C"

extern "C" void foo(int);   /* C 链接 — 无 mangling，不能重载 foo */
void foo(int);
void foo(double);           /* C++ mangling: _Z3fooi, _Z3food */

C 可调用的接口 只能暴露 无重载 的 extern "C" 包装（demo01_extern_c）。

成员函数重载

class Buffer {
public:
    void append(char c);
    void append(const char *s);
    void append(const Buffer &other);
};

this 不参与 重载区分（所有实例成员隐含 this）。

pitfalls

  • typedef 别名 不 产生新类型用于重载（typedef int Integer; 与 int 同一 overload set）
  • 默认参数 可能造成 与另一 overload 冲突
  • 跨 extern "C" 边界 不要 依赖重载

11.11

C++ 如何进行操作符重载

本节讲什么

C++ 允许把 运算符（+、-、<<、[] 等） 重载为用户定义类型 的函数，使 UDT 用法接近内置类型。语法上 operator@ 是 特殊函数名，参与 普通重载规则（11.10）；常配合 友元（11.5） 实现 对称二元运算。本书态度：适度使用 — 算术/IO 直观；operator= 等须谨慎（自赋值、深拷贝）。

要点

成员 vs 友元形式

class Vec2 {
public:
    Vec2(double x, double y) : x_(x), y_(y) {}
    Vec2 operator+(const Vec2 &o) const {
        return Vec2(x_ + o.x_, y_ + o.y_);
    }
    friend std::ostream &operator<<(std::ostream &os, const Vec2 &v);
private:
    double x_, y_;
};

std::ostream &operator<<(std::ostream &os, const Vec2 &v) {
    return os << '(' << v.x_ << ',' << v.y_ << ')';
}

二元运算符：

形式 左操作数
成员 this（左）
友元/自由 任意一侧可隐式转换

a + b → a.operator+(b) 或 operator+(a, b)。

常见可重载运算符

类别 运算符 注意
算术 + - * / 返回 新对象 或 const
复合赋值 += -= 通常 成员，改 this
比较 == != C++20 可 <=>
下标 [] 须 一对 const/非 const
调用 () 仿函数 functor
IO << >> 几乎总是 友元

不可重载（语言保留）

:: . .* ?: sizeof typeid 等 — 不能 重载。

与 C 的对比

point_add(&a, &b, &out) c = a + b
strcmp(s1, s2) == 0 s1 == s2（string）

可读性 提升；滥用（如 operator+ 做字符串拼接业务逻辑）则 难调试。

赋值与拷贝（与 11.4 呼应）

IO 运算符与 printf（11.12）

类型安全 — 无需 %d/%f 格式串 不匹配；性能 上早期 C++ stream 较慢，现代已大幅改善。

11.12

C++ 的输入/输出 (I/O)

本节讲什么

要点

基本用法

#include <iostream>
#include <string>

int x;
std::string name;

std::cout << "enter name and age: ";
std::cin >> name >> x;
std::cout << name << " is " << x << " years old\n";
C C++
printf("%s %d", name, x) cout << name << ' ' << x

fgets(buf, N, stdin) std::getline(cin, line)

/* C — 格式错 → UB */
printf("%d", 3.14);        /* 错用 %d 打印 double */

/* C++ — 编译期/运行时类型匹配 */

11.13

多态——运行时绑定

本节讲什么

多态（polymorphism）：同一接口，不同具体类型 在 运行时 执行 不同实现。virtual 成员函数 + 基类指针/引用 触发 动态绑定 — 编译器生成 vtable（虚函数表） 与对象内 vptr（虚表指针）。C 程序员已在 ch10 10.7 与 11.15 见过 函数指针表；C++ 把表 自动化，代价是 内存与间接跳转。

要点

virtual 基本模型

class Shape {
public:
    virtual void draw() const { /* 默认 */ }
    virtual ~Shape() = default;
};

class Circle : public Shape {
public:
    void draw() const override { /* 画圆 */ }
};

void render(const Shape &s) {
    s.draw();   /* 运行时决定 Circle::draw 或 Shape::draw */
}

Circle c;
Shape *p = &c;
p->draw();      /* Circle::draw — 即使静态类型是 Shape* */

无 virtual → 编译期绑定（切片 slicing 风险：派生部分被截断）。

编译期 vs 运行时绑定

静态绑定 动态绑定
关键词 普通成员 / 重载 virtual
决定时机 编译期 运行期（vptr 查表）
C 类比 直接函数调用 ops->fn(ctx)

必要条件

  1. 基类函数声明 virtual
  2. 通过 指针或引用 调用（非 Shape s = circle; s.draw() 值语义 — 切片）
  3. 多态基类 虚析构（11.4, 11.8）

纯虚与抽象类

class Shape {
public:
    virtual void draw() const = 0;   /* 纯虚 — 无定义 */
    virtual ~Shape() = default;
};
/* Shape s;  // 错误 — 不能实例化抽象类 */

接口类 — 类似 C 的 只含函数指针的 ops 表，无 ops 指针 的实例。

对象切片（slicing）

Circle c;
Shape s = c;        /* 只拷贝 Shape 子对象 — 丢失 Circle 部分 */
s.draw();           /* Shape::draw — 非多态 */

应使用 Shape& 或 Shape* 或 std::unique_ptr<Shape>。

代价 说明

时间 间接调用 + 可能阻止内联
确定性 分支预测失败

11.14

解释

本节讲什么

本节是 11.13 多态 的 机制详解：编译器如何为 含 virtual 的类 生成 vtable，对象如何在 构造时 写入 vptr，以及 动态调用 在汇编级近似 (*(this->vptr[n]))(this, args...)。把 C++ 多态 去神秘化 — 它就是 结构化的函数指针表，与 ch10 10.7、11.15 内核 ops 同构，只是 编译器代劳。

要点

vtable 与 vptr

类 Circle（有 virtual draw）:

Circle vtable (只读,  per-class):
┌──────────────────┐
│ &Circle::draw    │
│ &Circle::~Circle │
└──────────────────┘

Circle 对象 (per-instance):
┌──────────┬─────────┬───────┐
│ vptr ────┼─→ vtable│ r_    │ ...
└──────────┴─────────┴───────┘
   ↑
  通常位于对象布局最前（Itanium ABI 等）
术语 粒度 存储
vtable 每个多态类一份 只读 段（.rodata 类似）
vptr 每个对象一份 对象 首地址 常见

动态调用步骤

Shape *p = new Circle();
p->draw();
  1. 加载 p 指向的对象
  2. 读对象 前若干字节 的 vptr
  3. 在 vtable 中 查 draw 槽位（编译期固定偏移）
  4. 间接跳转 到 Circle::draw, this = 对象地址

与 C 对比：

ops->draw(container);   /* ops 来自对象或类描述符 */
/* C++: vptr 来自对象，vtable 来自类 */

构造 / 析构期间 vptr 变化

构造 Circle:
  Shape 子对象 ctor → Shape vptr
  Circle ctor 完成 → Circle vptr

析构 Circle:
  ~Circle() 开始 → 可能仍 Circle vptr
  ~Shape()      → Shape vptr（为何 ctor 里 virtual 行为异常）

理解：vptr 随「当前构造阶段的有效类型」 更新 — 11.13「ctor 中 virtual 调派生无效」的根源。

单继承布局（典型）

class Base  { virtual void f(); int b; };
class Child : public Base { virtual void g(); int c; };

Child 对象:
[ vptr | b | c ]   /* Base 子对象在前，含 vptr */

多继承（11.9）：可能 多个 vptr — 布局 编译器相关，跨 DLL ABI 须小心。

与 C 函数指针表对照

C struct ops C++ virtual
表位置 常 全局模板 或 每实例 ops* 每类 vtable + 每对象 vptr
注册 手动赋值 编译器自动
类型 void* / 不透明 ctx this 强类型
可读性 内核源码常见 应用 OOP 常见

Linux file_operations 详见 11.15。

调试技巧

  • sizeof(Derived) 含 vptr（通常 +指针宽）
  • 无 virtual 的类 — 无 vptr，与 C struct 布局更接近
  • 反汇编 看 mov rax, [obj]; call [rax+offset] 模式

11.15

C++ 如何表现多态

本节讲什么

C 没有 virtual，但 处处是多态：函数指针表 让 同一调用 在 运行时 跳到 不同驱动实现。本书以 Linux 内核 struct file_operations 为 教科书级范例 — 与 C++ vtable 同构。理解 C 表驱动 = 理解 为何 C++ 要 vptr；也理解 内核为何坚持 C（显式、零隐藏成本）。

要点

file_operations 模式

struct file_operations {
    struct module *owner;
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    /* ... */
};

struct file {
    struct file_operations *f_op;
    /* ... */
};

/* 调用路径 */
f->f_op->read(f, buf, count, pos);
C 元素 C++ 对应
f_op 指针 vptr（指向 vtable）
file_operations 表 vtable（每类一份）
read 槽位 virtual read() 条目
struct file * this
驱动私有 struct 派生类成员

嵌入与 container_of

struct my_dev {
    struct cdev cdev;      /* 嵌入「基类」 */
    void *private_data;
};

/* 从 cdev 指针找回 my_dev — 内核宏 container_of */

类比 C++ 继承：基类子对象 在 派生对象前缀；C++ 编译器自动偏移，C 用 宏。

注册 ops — 手动 vtable 绑定

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .read    = my_read,
    .write   = my_write,
    .open    = my_open,
    .release = my_release,
};

/* 注册 */
filp->f_op = &my_fops;

C++ 等价概念：

class MyDev : public FileOps {
public:
    ssize_t read(...) override;
};
/* vptr 在 MyDev 构造时自动 = MyDev vtable */

11.16

新奇玩意——多态

本节讲什么

本书用 「新奇玩意（a novel approach）」 指：把 vptr 放进对象内存布局 这一 C++ 设计 — 对 C 程序员 直观又陌生。本节通过 内存视角 巩固 11.14 解释：有/无 virtual 时 sizeof 差异、对象地址与 vptr 地址、单继承/多继承 下 vptr 个数。建议配合 demo03_c_vs_cpp_polymorph 打印地址验证。

要点

有 virtual → 对象「开头是指针」

class NoVirt { int x; };
class WithVirt { virtual void f(); int x; };

/* 典型 64-bit:
   sizeof(NoVirt)    == 4 (或 8 对齐)
   sizeof(WithVirt)    == 16 (vptr 8 + int 4 + padding)
*/

WithVirt 对象 @ 0x1000:
0x1000: [ vptr = 0x4000 ]  → 指向 WithVirt vtable
0x1008: [ x = 42        ]

「新奇」之处：C struct 第一个字段通常是数据；C++ 多态对象 第一个字段常是 vptr — ABI 约定，非标准硬性文字但 事实 de facto（Itanium C++ ABI）。

打印布局（实验思路）

WithVirt obj;
void **slot = reinterpret_cast<void **>(&obj);
std::cout << "object: " << &obj << "\n";
std::cout << "vptr:   " << *slot << "\n";

demo03_c_vs_cpp_polymorph 对比：

C:  obj->ops  在对象内或外单独存储
C++: *(void**)obj == vtable 地址

继承下的 vptr

单继承（常见）：

Derived 对象 = [ vptr | Base 数据 | Derived 数据 ]
              一个 vptr，Derived vtable 含 Base virtual 槽

多继承（11.9）：

可能:
[ vptr_B1 | B1 数据 | vptr_B2 | B2 数据 | D 数据 ]

多个 vptr — static_cast/dynamic_cast 可能 调整指针（偏移 thunks）。

无虚函数 — 与 C 布局对齐

struct Pod { int a, b; };           /* C 兼容 */
class  PodClass { int a, b; };      /* 无 virtual → 通常同布局 */

与 C 互操作、DPDK mbuf 扩展 等要求 无 vptr — 禁止对 POD 加 virtual。

vtable 存放位置

  • 通常在 .rodata（只读）
  • 每类一份 — 不随对象数增长
  • vptr per object — N 个对象 = N 个 vptr，1 个 vtable

性能直觉

直接调用:  call FixedAddress
virtual:   mov rax, [obj]      ; vptr
           call [rax + off]    ; 间接

热路径（包转发）→ 避免 virtual 或 final + 去虚化；冷路径（插件架构）→ virtual 合理。

与 ch06/ch07 运行时布局

  • ch06：栈帧、argv
  • ch07：对齐、padding — vptr 引发对齐填充
  • ch11：OOP 在对象头加 indirection

要点

const / constexpr vs #define（ch02/ch08）

C C++ 原因
#define MAX 128 constexpr int MAX = 128; 类型、作用域、可调试
#define SQR(x) ((x)*(x)) inline 或模板 无 重复求值/优先级 UB

全局 const：

引用 vs 二级指针

}

malloc/free new/delete

    void init();
}

inline 与 bool

bool 非 int 0/1 — 与 C99 _Bool 类似；<cstdbool> 兼容 C。

void* 模板 template<typename T>

代码生成 一份函数 每类型实例化
性能 无法内联具体类型 可 特化/内联
二进制 小 可能 膨胀

STL vs C 标准库对照表

extern "C" 与 name mangling

C++ 重载 → 符号如 _Z3fooi、_Z3food；C 无 mangling → foo。

/* C++ 编译单元 */
extern "C" {
    void c_api_init(void);
    int  c_api_send(const char *buf, int len);
}

/* 或 */
extern "C" void c_api_init(void);

/* 头文件供 C/C++ 共用 */
#ifdef __cplusplus
extern "C" {
#endif
void my_init(void);
#ifdef __cplusplus
}
#endif

规则：

  • C 调 C++：C++ 侧 extern "C" 导出
  • C++ 调 C：声明 extern "C" 告诉 C++ 用 C 链接名
  • extern "C" 函数不能重载

11.18

如果我的目标是那里，我不会从这里起步

本节讲什么

本书 哲学小节之一：作者从 C 程序员视角 审视 C++ — 若最终目标是简洁、可预测、贴近机器的代码（如内核、协议栈），从 C++ OOP 这条路「起步」未必最优。不是说 C++ 无用，而是 目标函数不同：应用层要 抽象与复用；系统底层要 透明与可控。本节与 11.19 构成 Tradeoff 对话。

要点

「那里」指什么？

目标 更贴近的语言/风格
Linux 内核 / 驱动 C + ops 表（11.15）
DPDK / 线速转发 C、无 virtual、无堆
硬实时 / 固件 C / 受限 C++ 子集
业务应用 / 工具链 C++ / 现代 STL

Expert C 读者 多在做 「那里」 的工作 — ch1–10 整本书为此服务；ch11 是 桥梁，不是 换宗教。

C++ 从 OOP 起步的「绕路感」

C 程序员已有:
  struct + 函数指针 + 宏 + malloc
      ↓ 直接可进内核源码

若从 C++ 课堂起步:
  class → 继承 → 多继承 → 虚函数 → 模板元编程 → ...
      ↓ 很多层才回到「内存里到底发生什么」

本书立场：先懂 C 底层（ch1–10）再读 C++（ch11） — 顺序 正确；反过来 易浮在语法。

C++ 中「从这里起步」的具体痛点

  1. 隐藏成本：virtual、异常、RTTI、全局 ctor — 不在源码一眼可见
  2. 编译模型复杂：模板 编译慢、错误信息 难读
  3. ABI 脆弱：跨编译器/版本 布局与 mangling
  4. 过度抽象：设计模式堆叠 掩盖 简单数据流

与 ch08「软件规则之难」呼应

  • ch08：语言 规则与实现 有缝隙
  • C++：规则 更多层 — 学习曲线 与 踩坑面 更大
  • C：规则 少而硬 — 内核选型 原因 partly 在此

何时仍值得用 C++（即使目标是系统）

场景 理由
用户态驱动框架 RAII、类型安全
仿真 / 测试 harness 快速搭建
非热路径配置 std::map 可读性
与现有 C++ 生态集成 无法只用 C

c-to-cpp-migration-checklist.md §7：底层保留 C 风格 的 白名单。

11.19

它或许过于复杂，但却是唯一可行的方案

本节讲什么

与 11.18 相对，本节承认：大型软件 在 人力、时间、变更 约束下，纯 C + 手动纪律 往往 撑不住 — C++ 的复杂度 是 为管理更大复杂度 而付的 保险费。模板、类层次、STL 让 百万行代码 可维护；内核 选择 C 是 问题规模与发布节奏 不同，非 C++ 本质失败。

要点

复杂度的两种

类型 例子 应对
本质复杂 分布式协议、编译器 抽象 分割问题
偶然复杂 手动内存、宏、void* 语言/库 消除

C++ 同时增加 语言偶然复杂（语法）并 减少 工程偶然复杂（泄漏、类型错）。

「唯一可行」在何时成立

小模块 / 热路径 / 内核:
  → C + 函数表 足够（11.15）
  → 「唯一可行」常指 C 或 受限 C++

大应用 / GUI / 游戏 / 中间件:
  → 无 STL/OOP 则 **重复发明** vector/map/字符串
  → C++ 抽象 **成为唯一可行** 的工程路径

规模阈值：当 「手动 C 纪律」 成本 超过 「C++ 学习+编译」 成本。

C++ 换来的东西（11.1–11.17 汇总）

机制 管理的复杂度
class + RAII 资源泄漏（11.4）
virtual 扩展点爆炸（11.13）
模板/STL 容器/算法重复（11.17）
namespace 全局名冲突
类型系统 void 标签错误（ch10*）

与 C 哲学共存

不是二选一：

/* 热路径 — C 风格 */

/* 控制面 — C++ */

    std::map<std::string, std::string> kv_;

设计权衡表

维度 偏 C 偏 C++
团队熟悉度 内核背景 应用背景
性能可预测 高 需约束子集
交付速度 低（手写） 高（STL）
长期维护 依赖规范 依赖类型+RAII
调试透明 高 需懂 vtable/模板实例

Expert C 的平衡结论

  1. 懂 C 底层 是 用对 C++ 的前提（vtable = ops 表）
  2. 不懂底层 的 C++ 是 危险浮层
  3. 系统编程 默认 C 主 C++ 辅；应用 相反
  4. 用 c-to-cpp-migration-checklist.md 按模块迁移，非 全盘重写

Q1extern "C" 与 name mangling
// C++ 代码 (math.cpp)
int add(int a, int b) { return a + b; }

extern "C" {
#endif
int c_add(int a, int b);
#ifdef __cplusplus
}

Q2malloc/free vs new/delete
class Foo {
public:
    Foo()  { printf("ctor\n"); }
    ~Foo() { printf("dtor\n"); }
};

// 版本 A
Foo *a = (Foo*)malloc(sizeof(Foo));
free(a);

// 版本 B
Foo *b = new Foo();
delete b;

// 版本 C
Foo *c = new Foo();
free(c);

三个版本中构造函数和析构函数是否被调用？

答案与复习指引

答案： - A：构造/析构都不调用 — malloc 只分配内存，不调用构造函数；free 不调用析构函数 - B：构造/析构都调用 — new 分配内存 + 调用构造函数；delete 调用析构函数 + 释放内存 - C：构造调用，析构不调用 — new 调用构造函数，但 free 不调用析构函数 → 资源泄漏

规则： new 必须配 delete，malloc 必须配 free——禁止混用。

Q3vptr 内存布局
class Base {
public:
    int x;
    virtual void foo() {}
};

class Derived : public Base {
public:
    int y;
    void foo() override {}
};

printf("%zu %zu\n", sizeof(Base), sizeof(Derived));

两个 sizeof 分别是多少？（64 位，int=4）

答案与复习指引

答案： Base = 16（8 字节 vptr + 4 字节 x + 4 字节 padding）；Derived = 16（8 vptr + 4 x + 4 y）或 24（8 vptr + 4 x + 4 pad + 4 y + 4 pad，取决于 ABI）。

关键： 含 virtual 函数的对象首部有 vptr（虚表指针，8 字节），指向 .rodata 中的 vtable。每个类一份 vtable，存储虚函数地址。

对比 C： C 的 file_operations 是手动维护的 ops 表指针；C++ 的 vptr 是编译器自动注入的。

Q4引用 vs 指针
int x = 10;

int &r = x;    // A：引用
int *p = &x;   // B：指针

r = 20;
*p = 30;

int &r2;        // C
int *p2;        // D

A 和 B 有什么本质区别？C 和 D 哪个合法？

答案与复习指引

答案： - 引用（A）：必须绑定到对象，不能为空，不能重新绑定，语法像别名（不需要解引用） - 指针（B）：可以为 NULL，可以重新指向，需要 * 解引用

  • C：不合法 — 引用必须在声明时初始化
  • D：合法 — 指针可以不初始化（但未初始化指针危险）
