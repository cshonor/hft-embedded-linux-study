1.1

C语言的史前阶段

本节讲什么

C 不是凭空出现的语言，而是从 Multics → BCPL → B → C 这条「为写编译器/操作系统而造工具链」的脉络里长出来的。1972 年 Dennis Ritchie 在 B 的基础上加入类型系统，形成 C；1973 年 Unix 内核用 C 重写，把「高级语言写系统软件」从实验变成工业实践。理解这段历史，才能理解 C 编译器优先、贴近机器、极简内核 的设计哲学。

要点

时间线

年代 事件 意义
1960s Multics 大型分时系统 复杂、昂贵；Bell Labs 退出后催生 Unix
1967 Martin Richards 的 BCPL 无类型、编译器友好；Ken Thompson 参与
1969 Thompson 的 B BCPL 子集，为 PDP-7 上的 Unix 服务
1972 Ritchie 的 C 在 B 上加入 char/int/float 等类型
1973 Unix 内核用 C 重写 证明 C 可胜任系统编程；传播随 Unix 扩散

编译器优先（Compiler-first）

Ritchie 的设计目标不是「语法优雅」，而是 让编译器在有限内存的 PDP-11 上能跑起来：

  • 类型直接映射硬件：char 字节、int 字长、float 浮点单元——便于生成高效机器码
  • 语法极简：少关键字、少特殊规则，降低 parser 复杂度
  • 可移植编译器：C 编译器本身用 C 写（自举），换平台主要改后端
  • 内核 + 库分离：语言核心小，I/O 等放进 stdio 库（见 1.3），而非语言内置
Multics (复杂 OS)
    ↓ 简化
Unix (Thompson/Ritchie, 1969)
    ↓ 需要系统编程语言
BCPL → B (无/弱类型) → C (有类型, 1972)
    ↓
Unix 内核 C 重写 (1973) → C 随 Unix 传播到全世界

为什么是 C 而不是别的

  • 汇编：可移植性差，维护 Unix 成本过高
  • Fortran：科学计算导向，不适合系统编程
  • B：无类型，指针运算易错，难以表达结构体等抽象
  • C：在 B 的简洁与 BCPL 的类型之间取平衡——足够低层写内核，足够高层写应用

  • Expert C ch05：链接与可移植性——C 的「编译单元 + 链接」模型源于 Unix 工具链

题目 1： C89 和 K&R C 的主要区别是什么？为什么 K&R C 的函数声明方式不安全？

参考答案

K&R C 用老式声明 int f(a, b) int a, b;——不做参数类型检查，调用 f(1.5, 2.5) 编译通过但行为错误。C89（ANSI C）引入函数原型 int f(int a, int b)——编译期检查参数类型和数量。C89 还增加了 const、volatile、void、结构体赋值、size_t 等特性。现代代码必须用原型声明。

1.2

C语言的早期体验

本节讲什么

C 的许多「怪癖」不是设计失误，而是 1970 年代 PDP-11 硬件与编译器能力 的直接映射。本节梳理数组下标从 0 开始、类型与硬件对应、auto 存储类、数组到指针的衰变、float 提升、register 提示等早期体验——它们至今仍是 C 面试与 UB 讨论的高频来源。

要点

数组下标从 0 开始

  • C 继承自 B：指针 + 偏移 模型，a[i] 等价于 *(a + i)
  • 若下标从 1 开始，每次访问需多一次减法；从 0 开始代码生成更直接
  • 与数学下标习惯不同，但符合 地址算术 语义

类型映射硬件

C 类型 典型硬件映射 注意
char 8 位字节 CHAR_BIT 至少 8；signed/unsigned char 实现定义
int 机器「自然字长」 16/32/64 位随平台变；可移植代码用 <stdint.h>
short / long 更短/更长整数 仅保证相对关系，不保证绝对位数
float / double IEEE 754 浮点 运算中常 提升为 double（见下）

auto 存储类

  • 局部变量默认就是 auto：栈上分配，块结束即销毁
  • 显式写 auto 几乎只在 K&R 时代常见；现代代码通常省略
  • 对比：static（静态存储期）、register（寄存器提示）

数组衰变（array decay）

void f(int arr[]);   /* 形参实际类型是 int *，不是数组 */
int a[10];
f(a);                /* a 衰变为指向首元素的指针 */
sizeof(a);           /* 整个数组：40（假设 int 4 字节）*/
/* 传参后 sizeof 在 f 内对参数是 指针大小 */
  • 数组名在大多数表达式中 衰变为指向首元素的指针
  • Expert C ch04 专论「数组 ≠ 指针」；衰变是混淆根源

float 提升（default argument promotion）

float f;
double g = f + 1.0;   /* f 先提升为 double 再运算 */
printf("%f", f);      /* varargs 中 float 也会提升为 double */
  • K&R / ANSI 前：表达式中 float 常 提升为 double
  • 影响 可变参数（printf 等）与混合精度运算；C99 后部分规则有调整

register 建议

register int counter;   /* 仅 hint；编译器可忽略 */
  • 请求编译器尽量放入寄存器，不保证
  • 取 register 变量地址在 C89 中非法；现代编译器优化已很强，少用
  • 嵌入式/DPDK 热路径有时仍见，但 volatile、restrict（C99）更常见

编译器优先的连锁效应

硬件字长/寻址方式 → 类型宽度与对齐
    ↓
简单 parser → 数组衰变、隐式转换
    ↓
小内存编译器 → 宏而非 inline、stdio 外置库

  • Expert C ch02：隐式转换、整型提升、有符号溢出等「语言特性」
  • Expert C ch04/ch09/ch10：数组衰变 vs 数组语义、指针算术

1.3

标准I/O库和C预处理器

本节讲什么

C 语言故意保持 极小内核：输入输出不在语法里，而在 标准 I/O 库（stdio） 中；条件编译与文本替换则交给 C 预处理器（cpp）。本节理解 #include / #define / #ifdef 的设计意图，以及宏 纯文本替换 带来的经典陷阱——这与编译器优先、跨平台移植策略一脉相承。

要点

stdio 库：语言外的 I/O 层

设计选择 原因
I/O 不进语言语法 内核/嵌入式可无 stdio（freestanding）
FILE * 抽象 统一文件、终端、管道；缓冲由库管理
printf/scanf 家族 格式化 I/O；与 varargs、float 提升绑定
缓冲 I/O 减少系统调用；setbuf/fflush 控制行为 
#include <stdio.h>

int main(void)
{
    FILE *fp = fopen("data.txt", "r");
    if (fp) {
        int c;
        while ((c = fgetc(fp)) != EOF)
            putchar(c);
        fclose(fp);
    }
    return 0;
}
  • hosted 环境：必须有标准库；freestanding（内核、裸机）通常只提供 memcpy 等子集
  • Linux 用户态 printf 最终经 write 系统调用；内核用 printk 而非 stdio

预处理器：编译前的文本工具

#include <stdio.h>          /* 字面插入头文件内容 */
#include "local.h"          /* 先搜当前目录，再系统路径 */

#define PI 3.14159
#define MAX(a, b) ((a) > (b) ? (a) : (b))   /* 参数加括号 */

#ifdef DEBUG
#  define LOG(x) fprintf(stderr, x)
#else
#  define LOG(x) ((void)0)
#endif

#ifndef MYHDR_H
#define MYHDR_H
/* 头文件守卫，防重复包含 */
#endif
指令 作用
#include 文本包含
#define / #undef 宏定义/取消
#ifdef / #ifndef / #else / #endif 条件编译
#if / #elif 表达式条件（C99 起更强大）
#pragma 实现定义/编译器扩展（见 1.11）
#error / #warning 编译期报错/警告

宏陷阱（必考）

1. 缺少括号 — 运算符优先级

#define BAD_SQUARE(x) (x * x)
#define SQUARE(x)     ((x) * (x))

int a = 3;
BAD_SQUARE(a + 1);   /* 展开: a+1*a+1 → 3+3+1 = 7 */
SQUARE(a + 1);       /* 展开: ((a+1)*(a+1)) → 16 */

2. 多语句宏

#define INC_TWICE(x)  x++; x++   /* 危险：无 do-while(0) 包裹 */
/* 正确写法：*/
#define INC_TWICE_SAFE(x) do { (x)++; (x)++; } while (0)

3. 副作用重复求值

#define MAX(a, b) ((a) > (b) ? (a) : (b))
int i = 0;
MAX(i++, j++);   /* i/j 可能被增减多次 → 未定义行为 */
/* 应改用 inline 函数或 GCC statement expression */

4. 与类型系统无关

  • 宏不做类型检查；ANSI 原型 + inline/static inline（C99） 更安全
  • 运行 demo：demo/demo02_macro_trap.c
cd demo && make all && ./demo02_macro_trap

#define vs const / enum

方式 特点
#define 编译前替换；无类型；可 #ifdef
const 有类型；调试器可见；C 中仍可能当 compile-time 常量
enum 整型常量；作用域规则与普通标识符相同

1.4

K&R C

本节讲什么

K&R C（《The C Programming Language》1978 第一版所描述的语言）是 C 工业化的里程碑，但按今天标准看 极不安全：无函数原型、省略返回类型则默认为 int、实参类型在调用处 不做检查。本节对比 K&R 与 ANSI 声明写法，理解为何 C89 引入原型是 C 历史上最重要的安全改进之一。

要点

K&R 时代特征（1978 前主流）

特性 K&R C 后果
函数声明 仅 标识符列表，无参数类型 实参类型错误 编译通过、运行错乱
返回类型省略 默认为 int void 函数不存在；忘记写返回类型静默变 int
实参传递 default argument promotion float→double，char/short→int
原型 无 链接阶段才解析符号，类型信息丢失

声明写法对比

K&R 旧式定义（历史演示，禁止新代码使用）：

/* 声明：只告诉编译器「有个叫 add 的函数」*/
int add();

/* 定义：类型单独列在参数名之后 */
int add(a, b)
    int a;
    double b;
{
    return a + b;
}

ANSI C 原型（现代写法）：

/* 声明与定义合一，带完整类型 */
int add(int a, double b);

int add(int a, double b)
{
    return (int)(a + b);
}

/* 真正无参必须用 void */
int getchar(void);

类型检查缺失的灾难

/* K&R 风格 */
int mystery();          /* 编译器不知道参数是什么 */

main()                  /* 返回类型省略 → int */
{
    mystery("oops", 3.14);   /* 编译通过！ */
    return 0;
}
  • 调用 mystery(1, 2.5) 与 mystery("x", 1) 在 K&R 下 都能编译
  • 栈上按错误类型解释比特 → 崩溃或静默数据损坏
  • demo01 演示 ANSI 原型如何拒绝错误实参：
cd demo && make all && ./demo01_kr_vs_ansi
# 取消 demo01_kr_vs_ansi.c 中 add_ansi("x", 1) 注释后重编译 → 报错

int 的隐式默认

foo() { return; }       /* K&R：返回类型是 int，return; 值未定义 */
unsigned bar;             /* K&R 某些编译器：省略 int → unsigned int */
  • C89 起：无返回类型非法（旧代码需 -implicit-int 等扩展才能编过）
  • main 在 C99 起必须 int main(void) 或 int main(int argc, char *argv[])

K&R 第二版（1988）的过渡

  • 已引入 ANSI 原型，与第一版并存说明
  • 标志 K&R C → ANSI C 的正式过渡；考试常问「K&R 指哪一版」——通常指 无原型的第一版时代

与编译器优先设计的关系

  • Unix 源码 1970s 大量 K&R 风格；移植到 ANSI 是巨大工程（Linux 早期亦如此）

1.5

今日之ANSI C

本节讲什么

ANSI C（1989，ISO 称 C90/C89）是 C 第一次正式标准化，把 K&R 时代的惯例与编译器实践写进规范。核心变化：函数原型、void、const、标准库 清单、实现定义/未定义行为 分类。现代 -std=c11/c17/c23 均在此基础上演进；读内核/DPDK/嵌入式代码时，「符合哪个标准」决定你能用哪些语法。

要点

标准演进简表

标准 年份 别名 里程碑
C89/C90 1989/1990 ANSI C 原型、const、void、标准库
C99 1999 ISO C99 // 注释、long long、VLA、<stdint.h>
C11 2011 ISO C11 _Generic、_Atomic、threads（可选）
C17/C18 2018 缺陷修正，无大特性
C23 2024 #embed、attributes 等 逐步普及中

C89 核心语言特性

1. 函数原型（prototype）

double sqrt(double x);           /* 声明 */
int printf(const char *fmt, ...); /* varargs 用 ... */

void noop(void);                 /* 无参必须用 void，不是空括号 */

2. void 类型

void exit(int status);    /* 无返回值 */
void *malloc(size_t n);   /* 通用指针 */
  • 空括号 () 在 C89 中 不是「无参」，而是 旧式声明（参数未指定）——仍与 K&R 兼容

3. const

const int *p;       /* 指向常量的指针：*p 不可改 */
int *const p;       /* 指针本身是常量 */
const char *msg = "hello";
  • 增强接口契约；字符串字面量类型在 C89 为 char *，C++ 及良好 C 实践用 const char *

4. 标准库（hosted 环境）

头文件 主要功能
<stdio.h> I/O、FILE
<stdlib.h> malloc/free/exit/atoi
<string.h> memcpy/strlen
<math.h> 数学函数
<stddef.h> size_t、NULL、offsetof
<limits.h> / <float.h> 实现限制与浮点属性
  • freestanding 实现只需提供 <stddef.h>、<stdint.h>（C99 起）等最小集；无 malloc/stdio

与 K&R 的关键差异

/* K&R：危险 */
int func();

/* ANSI：明确 */
int func(int a, int b);
void func(void);

/* K&R：省略返回类型 → int */
foo() { return 1; }

/* ANSI/C99+：必须显式返回类型 */
int foo(void) { return 1; }

可移植性实践

#include <stdint.h>   /* C99：int32_t 等固定宽度类型 */
#include <stdbool.h>  /* C99：bool/true/false */

#if __STDC_VERSION__ >= 199901L
/* C99 及以上可用特性 */
#endif
  • Linux 内核用 GNU C 扩展 + 自有风格，不是严格 ISO C
  • DPDK 指定 GCC/Clang 版本与 -std=c11 等标志

编译示例

gcc -std=c89 -pedantic -Wall demo/demo01_kr_vs_ansi.c -o demo01
gcc -std=c11 -Wall demo/demo01_kr_vs_ansi.c -o demo01_c11
echo | gcc -E -dM -std=c11 - | grep __STDC_VERSION__

1.6

它很棒，但它符合标准吗

本节讲什么

「能编译、能跑」≠「符合 C 标准」。本节区分 严格符合（strictly conforming）、符合（conforming）、Hosted vs Freestanding 实现，以及 实现定义（implementation-defined）、未指定（unspecified）、未定义（undefined） 行为——写可移植 C、读内核/DPDK 代码、答面试题都绕不开这套分类。

要点

符合性层次

术语 含义
严格符合程序 不依赖扩展、不产生未定义行为；仅使用标准语法与库
符合程序 可能用实现扩展，但行为在标准允许范围内
Hosted 实现 完整 OS 环境：有 main、标准库、文件 I/O
Freestanding 实现 引导/内核/裸机：无完整库；启动方式由实现定义 
你的 .c 源文件
    ↓
编译器 + 标准库（hosted）  或  交叉工具链 + 最小运行时（freestanding）
    ↓
严格符合？ → 可移植   |   用扩展（GNU/Microsoft）→ 换编译器可能挂

行为四分类（必考）

分类 标准是否规定结果 典型例子
Defined 完全规定 1 + 2 == 3
Implementation-defined 标准列出备选，文档必须说明 sizeof(int)、char 有符号与否、右移负数
Unspecified 合法但未规定选哪种 i++ + i++ 求值顺序（C11 前更糟）、同一表达式内多个函数调用的顺序
Undefined 无保证，编译器可任意处理 越界访问、有符号溢出、NULL 解引用、违反有效类型规则

实现定义 vs 未定义 — 对比例子

Implementation-defined（换平台可能变，但合法）：

/* sizeof(int) 可能是 2/4/8，查 limits.h / 文档 */
printf("%zu\n", sizeof(int));

/* char 默认 signed 还是 unsigned — 编译器 -fsigned-char 决定 */
char c = 255;

/* 右移负数 — 算术右移还是逻辑右移，实现定义 */
int x = -1 >> 1;

Undefined（编译通过也可能随时炸）：

int a[10];
a[10] = 0;              /* 越界：UB */

int i = INT_MAX;
i + 1;                  /* 有符号溢出：UB */

int *p = NULL;
*p = 42;                  /* 空指针解引用：UB */

/* 未序列化的副作用 */
i = i++;                  /* UB */

编译器扩展：far / near（Microsoft）

/* 16 位 DOS / 早期 Windows 分段内存模型 — 非 ISO C */
char far  *fp;   /* 远指针：跨段 */
char near *np;   /* 近指针：段内 */

/* 现代 32/64 位 flat 模型下已废弃；面试问「见过 far/near 吗」→ DOS 时代 MS 扩展 */
  • GCC/Clang：__attribute__、__builtin_*
  • MSVC：__declspec、#pragma 段布局
  • 使用扩展 → 程序 不是严格符合，但可能是 符合的（若扩展不破坏标准语义）

如何判断「你的代码是否符合标准」

# 尽量严格：ISO C + 警告
gcc -std=c11 -pedantic -Wall -Wextra -Werror prog.c

# 查看实现定义文档
man gcc | less          # GCC 文档
info gcc "C Dialect Options"
场景 建议
可移植库 -std=c11 -pedantic，避免扩展
Linux 用户态 -std=gnu11 常用，知悉扩展边界
Linux 内核 GNU C，另有一套规范
嵌入式/DPDK 工具链文档 + -std=c11 + 禁用 UB

「很棒但不标准」的例子

  • Linux 内核：语句表达式、typeof、属性——强大但锁在 GCC/Clang

1.7

编译限制

本节讲什么

C 标准对 翻译环境（translation environment） 设下 最小编译限制（translation limits）：编译器至少能处理多长的标识符、多深的 #include 嵌套、多少宏参数等。实际编译器几乎总是 远超 下限，但跨平台工具、嵌入式编译器、或代码生成器仍可能撞线。本节记住典型下限与排查思路即可。

要点

为什么要有编译限制

  • 标准保证：符合实现 至少能编译「不太变态」的程序
  • 不限制编译器优化与内存：实现可支持更大，文档说明即可
  • 与 运行时限制（如 PATH_MAX）不同——那是标准库/OS 的事

C89 典型 translation limits（节选）

限制项 C89 最小要求 说明
标识符有效字符 31 个（C99 起外部 31、内部 63） 超长名称可能截断
#include 嵌套 8 层 头文件互相包含过深
条件编译 #if 嵌套 8 层
宏参数 31 个 巨型宏生成器注意
宏定义同一行替换 1024 次 防无限展开
枚举常量 127 个（单枚举）
块嵌套 15 层
函数参数 31 个
表达式嵌套括号 32 层
case 标签（单 switch） 257 个
结构/联合成员 127 个
翻译单元字符数 509（C89） 极老实现；现代无 practical 意义

完整列表见标准 Annex C（C99 起）或 <limits.h> 相关说明；GCC/Clang 实际限制大得多。

实际开发中的「撞线」场景

1. 头文件嵌套过深

/* a.h → b.h → c.h → ... → 超过实现限制 */
#include "a.h"   /* 间接包含链过长 */
  • 解决：前置声明、减少 transitive include、PCH

2. 宏爆炸

#define M0 1
#define M1 M0+M0
/* ... 自动生成数百层 */
  • 解决：改用 static inline、代码生成脚本输出 .c 而非宏

3. 标识符截断（古老/linker 限制）

void very_long_function_name_that_exceeds_old_linker_limit(void);
  • 外部链接名 C89 仅保证 前 6 字符唯一（已过时）；现代 ELF 无此问题

4. 单翻译单元过大

  • 内核「unity build」、自动生成巨型 .c 可能拖慢编译或 OOM——非标准限制，但真实

如何查看实现限制

# GCC 预定义宏
echo | gcc -E -dM - | grep -E 'IDENT|LIMIT'

# C99 起 <stdint.h> / Annex C 在标准 PDF 中
gcc -std=c11 -pedantic huge_file.c 2>&1 | head

与编译器优先设计的关系

  • PDP-11 时代编译器内存 几 KB～几十 KB → 标准下限反映当年可行规模
  • 现代 GCC 编译 Linux 内核单文件可达 数万行——靠实现质量，不靠标准下限
  • 嵌入式编译器（Keil/IAR 老版本）可能仍对宏/嵌套更敏感

1.8

ANSI C标准的结构

本节讲什么

ISO C 标准不是教程，而是一份 契约：规定编译器、标准库、程序三者边界。本节拆解标准文档的 层次结构——语法约束、语义规则、标准库描述、implementation-defined 清单、undefined behavior 条款——为 1.9 直接读标准打地图。

要点

标准文档主要部分（以 C11 为例）

部分 内容
1–4 章 引言与约定 术语、符合性、翻译/执行环境
5 章 语法（Grammar） 形式语法；与语义分离
6 章 约束（Constraints） 编译期必须诊断 的规则（如类型不匹配）
6 章 语义（Semantics） 合法程序的含义
7 章 库 每个头文件：宏、类型、函数、前置条件/UB
Annex C Translation limits
Annex J（C99 起） Library introduction、常见 UB 汇总
索引 按术语查条款号 
标准文档
├── 语言（第 5–6 章）
│   ├── Constraints → 违反则编译失败（符合实现须诊断）
│   └── Semantics   → Defined / Impl-defined / Undefined
├── 标准库（第 7 章）
│   └── 每个函数：参数、返回值、错误、UB（如 NULL 指针）
└── 附录
    ├── Annex C：编译限制
    └── Annex J：UB 示例索引

三层「规则强度」

1. 诊断规则（Constraints）

int x = "hello";     /* 约束违反：编译器必须报错 */
return 1.0;          /* int 函数返回 double：约束/警告 */

2. 语义 — 完全定义

/* 6.5.6 数组下标：定义良好 */
int a[5];
a[4] = 0;            /* OK */

3. 语义 — 灰色与黑色

类型 标准表述 程序员应对
Implementation-defined 「实现应文档化行为」 查编译器手册
Unspecified 「合法但未指定哪一种」 不依赖顺序
Undefined 「无限制」 绝对避免

标准库章节的读法

以 strcpy 为例，标准会写：

  • #include <string.h>
  • 原型：char *strcpy(char *restrict s1, const char *s2);
  • Preconditions：s1 指向足够空间；否则 undefined
  • Returns：s1

→ 库函数 UB 与语言 UB 同等重要（printf 格式串、free 二次释放等）。

Implementation-defined 在标准中的位置

  • 散落在语义条款中，以 「which is implementation-defined」 标注
  • 例如：sizeof(int)、CHAR_BIT、malloc(0) 的行为
  • Annex L（C11）等汇总 标准库实现定义 行为

Undefined behavior 在标准中的位置

  • 几乎每章都有 「undefined behavior」 脚注
  • C99 起 Annex J.2 列出 UB 示例（非 exhaustive）
  • 编译器对 UB 的利用：优化假设 UB 不发生 → 「删代码」类 bug
int len = strlen(s);
if (len > 0 && s[len] != '\0') { /* 若 len==strlen，s[len] 已是 '\0' 或越界 UB */
    /* 编译器可能认为 UB 路径不存在，整段优化掉 */
}

Hosted vs Freestanding 在标准中的划分

环境 必须提供的头文件（C11）
Freestanding <float.h>, <iso646.h>, <limits.h>, <stdalign.h>, <stdarg.h>, <stdbool.h>, <stddef.h>, <stdint.h>, <stdnoreturn.h>
Hosted 上述 + 完整标准库（stdio, stdlib, string, …）
  • 内核/DPDK 多数按 freestanding + 自有库 理解

1.10

「安静的改变」究竟有多少安静

本节讲什么

标准升级时，并非所有变化都会 编译报错。许多是 「安静的改变（quiet change）」：旧代码在新标准下 仍能编译，但 语义已变——可能从「碰巧能跑」变成 UB，或从 UB 变成 defined。本节列举 C89→C99→C11 典型 quiet change，建立升级编译选项时的警觉。

要点

什么是 quiet change

旧标准下编译 + 运行「看起来 OK」
    ↓ 换 -std=c99 / 换编译器
新标准下仍编译通过
    ↓
行为变了（更严 UB / 不同结果）— 无警告 = 「安静」
  • 与 ** loud change ** 相对：void func() 从「参数未声明」变为语法/约束问题（C++ 更严格）

典型 quiet change 清单

变化 旧行为/假设 新标准/现代编译器 风险
// 注释 C89 不支持 C99+ 支持 旧代码 a//b 可能被误解析
inline 非标准 / GNU C99 关键字 与 static 链接规则变化
变长数组 VLA 扩展 C99 标准；C11 可选 栈溢出、可移植性
long long 扩展 C99 标准 格式串 %lld
restrict C99 别名优化更激进 违反 restrict → UB
复合字面量 — C99 生命周期易错
for 循环声明 — C99 for (int i=0; …) 作用域变化
混合声明与代码 声明须在块首 C99 任意 旧 C 风格差异
printf 格式 较松 现代 -Wformat 类型不匹配变警告/UB
有符号整数表示 常假设二进制补码 C99 仍允许 one's complement 等 极少平台
指针 alias 较松 strict aliasing（C99 语义） -fno-strict-aliasing 掩盖问题

实例 1：strict aliasing

float f = 1.0f;
int *ip = (int *)&f;
*ip = 0;                    /* 违反 effective type → UB（C99 严格别名）*/
/* 「安静」：GCC -O2 可能优化掉看似无关的读写 */
  • 旧代码「类型双关」看内存；优化后出错 无编译错误
  • 合法做法：memcpy、union（C99 对 union 仍有争议，常用 memcpy）

实例 2：函数声明空括号

void foo();     /* C：旧式，参数未检查；C++：等价 void foo(void) */
void bar(void);

foo(1, 2, 3);   /* C 中可能仍编译；C++ 中 foo() 不接受参数 */
  • 从 K&R 迁移到 ANSI 时，最大 loud change 是原型；遗留 () 仍是 quiet 陷阱

实例 3：// 注释与 URL

#define URL http://example.com   /* C89：可能 token 化错误 */
/* C99 中 // 才是注释；老宏要小心 */

实例 4：链接与 inline

/* C99：inline 函数多个 TU 需规则一致，否则 ODR 式问题 */

轻松一下——由编译器定义的Pragmas效果

本节讲什么

本章最后用 #pragma 收束：标准故意留给编译器一片 「实现定义」 的游乐场。#pragma 指令可控制对齐、警告、优化、段布局等——不可移植，但在系统编程里随处可见。书中 anecdote：有人用 pragma 调文件系统参数，效果离谱——提醒 「编译器定义的 pragma 效果」 既强大又滑稽，别当真 portable。

要点

#pragma 是什么

  • 标准语法：#pragma implementation-defined behavior
  • 常见形式：#pragma pack、#pragma GCC diagnostic、#pragma once（非标准但广泛支持）
#pragma once              /* 非 ISO，但 MSVC/GCC/Clang 均支持 */

#pragma pack(push, 1)     /* MSVC / 部分 GCC：结构体 1 字节对齐 */
struct Header {
    uint16_t magic;
    uint32_t len;
};
#pragma pack(pop)

#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wunused-variable"
    int unused = 0;
#pragma GCC diagnostic pop

标准中的 #pragma

标准 pragma 作用
#pragma STDC C99：FP_CONTRACT、FENV_ACCESS、CX_LIMITED_RANGE
#pragma STDC FENV_ACCESS ON 浮点环境严格访问 
#pragma STDC FENV_ACCESS ON
#include <fenv.h>
/* 浮点异常检测更严格；影响优化 */

编译器扩展 pragma 示例

GCC / Clang

#pragma GCC optimize("O0")
#pragma clang diagnostic ignored "-Wdeprecated-declarations"

__attribute__((section(".mysection"))) int data;

MSVC（historical）

#pragma data_seg(".mydata")
#pragma intrinsic(memcpy)
/* 16 位时代还有 code_seg、far/near 相关 pragma */

轻松 anecdote：filesystem tuning

书中风格故事（意译）：某程序员发现编译器文档里有个 pragma allegedly 影响 I/O 性能，于是在关键循环上加 #pragma，结果 benchmark 波动巨大——有时是 ** placebo ，有时是 改变了代码生成间接影响缓存，与文件系统 毫无关系**。

    ↓

机制 可移植性 典型用途

章节自测

C 历史与标准：K&R vs ANSI、UB 分类、hosted/freestanding。看代码 → 想答案 → 点开验证。

Q1K&R 旧式声明
/* K&R 风格 */
int add(a, b)
    int a, b;
{
    return a + b;
}

/* ANSI 风格 */
int sub(int a, int b) {
    return a - b;
}

int main() {
    printf("%d\n", add(3, 4));      // A
    printf("%d\n", add(3.0, 4.0));  // B：传 double
    printf("%d\n", sub(3.0, 4.0));  // C：传 double
    return 0;
}

B 和 C 哪个更危险？为什么？

答案与复习指引

答案： B 更危险。K&R 旧式声明不做参数类型检查——add(3.0, 4.0) 传 double，但函数期望 int，编译器不警告。double 8 字节被当 int 4 字节读取 → 结果错误或 UB。

ANSI 原型 int sub(int, int) 会让编译器自动转换 3.0 → 3（截断），安全。

规则： 始终用 ANSI 原型；-Werror=implicit-function-declaration 禁止旧式声明。

复习： → 1.4 K&R C · 1.5 今日之 ANSI C

Q2implementation-defined vs undefined
int x = -1;
int shifted = x >> 1;       // A

int arr[5];
printf("%d\n", arr[3]);     // B（未初始化）

char c = 200;               // C（char 符号性实现定义）
printf("%d\n", c);

A、B、C 分别是 implementation-defined、unspecified 还是 undefined？

答案与复习指引

答案： - A：implementation-defined（有符号右移——编译器文档说明是算术还是逻辑右移） - B：unspecified/indeterminate value（未初始化自动变量——值不确定，读它是 UB 如果是 trap representation） - C：implementation-defined（char 是否有符号由实现定义——200 可能是 200 或 -56）

区别： implementation-defined = 编译器必须文档化选择；undefined = 标准不约束任何行为；unspecified = 标准提供多个选项但不要求文档化。

Q3hosted vs freestanding
// hosted 环境（Linux 用户态）
#include <stdio.h>
int main(void) {
    printf("hello\n");
    return 0;
}

// freestanding 环境（内核/裸机）
void kernel_main(void) {
    // 没有 main()，没有 stdio.h
    // 用自定义 UART 输出
    uart_puts("hello\n");
}

两种环境的主要区别是什么？Linux 内核属于哪类？

答案与复习指引

答案： - hosted：有完整标准库（stdio.h、stdlib.h 等），入口是 main()，OS 提供运行时 - freestanding：最小库集（<stddef.h>、<stdint.h> 等），入口自定义，无 OS 依赖

Linux 内核近似 freestanding + GNU C 扩展——不使用 stdio.h/stdlib.h，入口是 start_kernel()，自己管理内存和中断。

HFT 关联： DPDK 用户态驱动绕过内核，但仍在 hosted 环境；裸机 HFT 可能用 freestanding。

Q4数组下标为什么从 0 开始
int arr[5] = {10, 20, 30, 40, 50};
int *p = arr;

// C 语言中 arr[i] 等价于什么？
printf("%d\n", arr[2]);
printf("%d\n", *(p + 2));
printf("%d\n", 2[arr]);     // 这个合法吗？

三行 printf 分别输出什么？为什么 C 数组从 0 开始？

答案与复习指引

答案： 三行都输出 30。arr[i] 等价于 *(arr + i)，也等价于 *(i + arr) 即 i[arr]。

从 0 开始的原因： C 的数组下标本质是偏移量——arr[0] = *(arr + 0) = 首元素。PDP-11 时代地址算术直接映射硬件指令，偏移 0 = 基地址本身，最自然。

规则： i[arr] 合法但勿在生产代码使用——可读性差。
