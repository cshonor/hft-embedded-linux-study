6.1

a.out及其传说

本节讲什么

Unix 传统上把编译链接产物叫 a.out（assembler output，汇编器输出），这个名字比 ELF 古老得多。本节追溯 可执行文件命名 的历史、a.out 格式 与 ELF 的关系，并说明：无论后缀是 a.out、main 还是 kernel.elf，本质都是 带段表与入口地址的二进制映像——为 6.2–6.4 的段布局、载入与运行时启动打名词基础。

要点

a.out 这个名字从哪来

时代 习惯 说明
早期 Unix cc foo.c → 默认 a.out 链接器输出，assembler output
现代 Linux gcc -o myprog 后缀任意；file myprog 看 ELF
嵌入式 kernel.elf、app.bin 常配合 链接脚本（ch05 demo04） 
gcc hello.c              # 仍可能生成 a.out（取决于 -o）
gcc hello.c -o hello
file a.out hello         # "ELF 64-bit LSB executable"

传说：新手以为 a.out 是某种神秘格式；实际上它只是 默认文件名，与 ELF 内容 无矛盾——今天 Linux 上的 a.out 几乎总是 ELF，不是 1970 年代那种原始 a.out 结构。

6.2

段

本节讲什么

C 程序在内存里不是「一整块字节」，而是按 段（segment / section） 组织：代码、只读数据、可写全局数据、未初始化数据、堆、栈 各司其职。本节建立 Linux 典型进程虚拟地址布局（低地址 → 高地址），对照 ch05 的 ELF 节名，并用 demo01_memory_layout 打印各区域地址验证直觉。

要点

          │   .rodata 只读常量        │

堆与栈不是 ELF 里的「节」

对象 在 ELF 文件中？ 何时出现
.text/.data/.bss 有（或 bss 为 NOBITS） 链接时确定 大小/内容
堆 无 _start / crt 初始化 brk 或 mmap arena（6.4, 6.9）
栈 无 内核为进程建 栈映射，rsp 指向栈顶

权限与安全（预告）

  • .text / .rodata：读 + 执行 / 只读，防止代码被改写
  • .data / .bss / 堆 / 栈：可读写，不可执行（NX / W^X，6.3）
  • 把数据当函数跳转 → SIGSEGV（ch07 7.7 总线 / 段错误）

常见陷阱

  1. 以为字符串字面量 "hello" 在 .data：实际在 .rodata（只读），尝试 s[0] = 'H' 触发 SIGSEGV。常见写法 char *p = "hi"; p[0] = 'H'; 崩溃；而 char buf[] = "hi"; buf[0] = 'H'; 能改——因为 buf 是栈上数组，"hi" 只是初始化源，拷贝到栈。
  2. 以为函数内 static int s; 在栈上：实际在 .bss（未初始化）或 .data（有初值），程序生命周期存活，地址固定在数据段，不在栈。auto int x; 才在栈上，函数返回失效。
  3. 以为 .bss 占磁盘空间：.bss 是 NOBITS——ELF 文件里不占字节，只记录大小和位置；载入时内核分配并清零。所以 int big[1000000];（全局未初始化）几乎不增加可执行文件大小，但运行时占 4MB 内存。

自测题

1.（选择） char *s = "hello"; 中 "hello" 存在哪个段？ - A. .text B. .data C. .rodata D. 栈

答案

C。字符串字面量是只读常量，进 .rodata。s 这个指针变量本身在哪取决于声明位置（全局在 .data/.bss，局部在栈），但它指向的 "hello" 在 .rodata。改 s[0] 会 SIGSEGV。

2.（判断） int g;（全局未初始化）在 ELF 文件里占 4 字节。

答案

错。g 进 .bss，是 NOBITS 节——文件里不占字节，只记录大小。载入时内核清零分配。int g = 0; 才进 .data 占 4 字节。用 size a.out 看 bss 列能验证。

3.（踩坑） char buf[] = "hi"; buf[0] = 'H'; 能改，但 char *p = "hi"; p[0] = 'H'; 崩溃，为什么？

答案

buf[] 是栈上数组，"hi" 只是初始化源，内容被拷贝到栈，buf 可写。p 是指针，指向 .rodata 里的 "hi"（只读），p[0] = 'H' 写只读页 → SIGSEGV。写法上差一个 [] vs *，语义完全不同。

4.（应用） 画出 Linux x86-64 进程从低地址到高地址的内存区域布局，标出 .text/.rodata/.data/.bss/堆/栈的位置和增长方向。

答案

低地址→高地址：.text（代码）→ .rodata（只读常量）→ .data（已初始化全局）→ .bss（未初始化全局）→ 堆（向上增长，malloc）→ （映射区/空洞）→ 栈（向下增长，最高地址）。堆向上、栈向下相向生长。ASLR 下绝对地址每次变化，相对顺序稳定。用 demo01_memory_layout 打印各区域地址验证。

6.3

操作系统在a.out文件里干了些什么

本节讲什么

链接器生成 ELF 后，程序还未运行。本节描述 内核载入器（loader） 在 execve 路径上做什么：解析 ELF、mmap 映射段、设置 页权限、从文件 拷贝 .data、为 .bss 分配并清零、启用 ASLR，最后把控制权交给 用户态入口 _start（6.4）。

要点

execve 简化流程

  shell: execve("/bin/ls", argv, envp)
           │
           ▼
  ① 读 ELF 头，校验魔数、架构
  ② 解析 Program Headers (readelf -l)
  ③ 对每个 PT_LOAD：mmap 到虚拟地址（+ ASLR 偏移）
  ④ 按权限设置页：R / W / X
  ⑤ 从文件拷贝 p_filesz 字节到映射区（.data 等）
  ⑥ bss：p_memsz > p_filesz 部分在内存中 zero-fill
  ⑦ 建立栈、传递 argv/envp/auxv
  ⑧ 动态链接：若有 PT_INTERP，先跑 ld.so（5.2）
  ⑨ 跳转到 e_entry（通常 _start，不是 main）

Program Header 字段 含义

p_flags PF_R / PF_W / PF_X

5.1 要点：.bss 在 ELF 里常标 NOBITS，不占文件字节，但 占内存。

  文件:  [ .data 有初值字节 ][ (bss 无文件内容) ]

页权限与 W^X

现代内核倾向 可写页不可执行、可执行页不可写：

  • 栈溢出写 shellcode 到栈上 直接执行 → 常被 NX 拦截
  • ROP 等攻击转向 已有代码片段（超出本节）

  1. 内核映射 动态链接器
  2. ld.so 加载 NEEDED 共享库、重定位 GOT/PLT

6.5

当函数被调用时发生了什么：过程活动记录

本节讲什么

每次函数调用，编译器在 栈 上构造 活动记录（activation record），也称 栈帧（stack frame）：保存 返回地址（RA）、上一帧基址（saved RBP）、参数、局部变量。本节用 A → B → C 调用链（demo03_stack_frame）观察地址，并说明 缓冲区溢出 如何覆盖 RA 或相邻变量（demo04_buffer_overflow）。

要点

x86-64 System V 栈帧布局（典型）

栈向低地址增长（6.9）。一次 call foo 后，foo 的栈帧 大致（简化，省略对齐）：

  高地址
        ┌─────────────────────┐
        │  调用者栈帧 ...       │
        ├─────────────────────┤
        │  参数 n, ...         │  ← 可能部分在寄存器（rdi, rsi...）
        ├─────────────────────┤
        │  返回地址 RA         │  ← call 压入；ret 弹出到 RIP
        ├─────────────────────┤
        │  saved RBP (旧rbp)   │  ← push rbp; mov rbp, rsp
        ├─────────────────────┤
        │  局部变量、临时区     │  ← sub rsp, N
  低地址 └─────────────────────┘  ← 当前 RSP
成分 作用
参数 被调函数读取；x86-64 前 6 个整型参数常用寄存器
RA（Return Address） ret 跳回调用点；被篡改 → 控制流劫持
saved RBP 形成 帧指针链，便于调试器回溯
局部变量 auto 对象；离开函数即 逻辑失效 
cd demo/demo03_stack_frame && make && ./demo03
# main → A → B → C：栈地址递减，体现调用深度

A → B → C 调用链（demo03）

demo03_stack_frame：

  main(&main_local)
    └─ A(&a_local)
         └─ B(&b_local)
              └─ C(&c_local)
  • &main_local 地址 最高（先分配的栈帧外层）
  • 进入 C 时 &c_local 最低（栈顶附近）
  • 印证：后调用的函数栈帧更「低地址」

用 GDB：

gdb -batch -ex 'break C' -ex run -ex 'bt' -ex 'info frame' ./demo03

call / ret 与 RA

  call foo   →  push 下一条指令地址；jmp foo
  ... foo 内 ...
  ret        →  pop 到 RIP（跳回 RA）

RA 在栈上 → 经典攻击：超长 strcpy 覆盖 RA 指向 shellcode 或 ROP（现代 NX + ASLR + canary 缓解）。

缓冲区溢出（demo04）

特性 说明

常见陷阱

  1. 返回指向栈局部的指针：int *f(){ int x=42; return &x; } —— 函数返回后栈帧失效，x 的地址被后续调用复写，读到垃圾值。这是悬垂指针的经典来源。改法：用 static、或传参让调用者提供缓冲、或 malloc 堆上分配。
  2. 缓冲区溢出覆盖返回地址：char buf[8]; gets(buf); 输入超长 → 覆盖栈上相邻变量甚至 RA，轻则逻辑漏洞（覆盖 auth 标志），重则控制流劫持。缓解：-fstack-protector 插 canary、FORTIFY_SOURCE 检查边界、用 fgets 替 gets。
  3. 以为参数都在栈上：x86-64 System V 前 6 个整型参数用寄存器（rdi/rsi/rdx/rcx/r8/r9），浮点用 xmm0-7，只有超过 6 个或变参（printf）才入栈。看汇编常见 mov edi, ... 而非 push。

自测题

1.（选择） x86-64 函数调用，返回地址 RA 压在哪里？ - A. 堆 B. .data C. 栈 D. 寄存器

答案

C。call foo 把下一条指令地址（RA）压入栈，ret 弹出到 RIP。RA 在栈上是缓冲区溢出能劫持控制流的根源。栈向下增长，RA 在栈帧高地址侧。

2.（判断） 函数返回指向局部 auto 变量的指针是安全的。

答案

错。auto 局部在栈帧上，函数返回后栈帧失效、地址被复用 → 悬垂指针。编译器通常给 -Wreturn-local-addr 警告。安全做法：static、堆分配、或让调用者传缓冲区进来。

3.（踩坑） char buf[8]; gets(buf); 输入 20 字符，可能覆盖什么？后果？怎么缓解？

答案

覆盖 buf 之后的栈内容：相邻局部变量（逻辑漏洞，如 demo04 改 auth）、saved RBP、甚至 RA（控制流劫持）。缓解：① -fstack-protector 插 canary 检测；② FORTIFY_SOURCE 编译期检查；③ 根本上用 fgets(buf, sizeof buf, stdin) 替 gets（已从 C11 移除）。NX/ASLR 进一步提高攻击门槛。

4.（应用） main → A → B → C 调用链，谁的局部变量地址最高？为什么？用 GDB 怎么观察帧链？

答案

main 的局部最高，C 的最低。栈向下增长，先调用的函数栈帧在高地址，后调用的在低地址。GDB：break C → bt（backtrace 看调用链）→ info frame（当前帧）→ frame 1/2/3 切换帧看各层局部地址。demo03_stack_frame 直接打印各层 &local 验证递减。

6.7

控制线程

本节讲什么

多线程 在同一进程内 共享 地址空间的大部分：.text、.rodata、.data、.bss、堆 共用；每个线程有独立栈（及 TLS 线程局部存储）。本节说明这对 6.6 static 局部、6.9 堆、6.5 栈帧 的含义，以及 竞态 与 栈大小 问题。

要点

一进程多线程：谁共享、谁独立

  进程地址空间
  ┌──────────────────────────────────────┐
  │ .text / .rodata     ← 所有线程共享    │
  │ .data / .bss        ← 共享（需同步）  │
  │ heap (malloc)       ← 共享（需同步）  │
  ├──────────────────────────────────────┤
  │ 线程 1 栈            ← 独立           │
  │ 线程 2 栈            ← 独立           │

6.8

setjmp和longjmp

本节讲什么

setjmp / longjmp（<setjmp.h>）实现 非本地跳转：从深层调用 直接跳回 较早的 setjmp 标记点，绕过正常 return 链。本节说明其 栈帧失效 语义、与 6.5 活动记录 的冲突，以及 不可返回后仍使用 auto 局部 等陷阱。

要点

基本用法

#include <setjmp.h>
jmp_buf env;

void deep(void) {
    if (some_error)
        longjmp(env, 1);   /* 跳回 setjmp，返回值非 0 */
}

void caller(void) {
    if (setjmp(env) == 0) {
        deep();            /* 正常路径 */
    } else {
        /* longjmp 着陆：错误处理 */
    }
}
函数 行为
setjmp(env) 保存 寄存器 + 栈上下文 到 jmp_buf；首次返回 0
longjmp(env, val) 恢复上下文；setjmp 仿佛再次返回 val（非 0）

与栈帧的关系

  caller: setjmp ──► A() ──► B() ──► longjmp
                              │
                              └── 跳过 B、A 的正常 ret
                                  栈指针「弹回」setjmp 时快照
  • 6.5 中 B、A 的栈帧 在 longjmp 后不再按 C 规则销毁
  • RA / 局部变量 占用的栈空间可能被 后续调用复写
  • 因此：从 setjmp 到 longjmp 之间、在 longjmp 之后仍「存活」的 auto 局部变量，若未被 volatile，其值不确定**（C 标准）

必须遵守的规则（C / POSIX）

规则 原因
longjmp 不得跳转到其他线程的 setjmp 栈不属于同一线程（6.7）
jmp_buf 仅在 setjmp 作用域有效，直到 matching longjmp 栈上移后 缓冲内容无效
勿 longjmp 穿过 C++ 析构 / VLA 生命周期 C++ 中更危险；C 中 VLA 同理（6.13）
longjmp 后不可依赖未 volatile 的 auto 局部 编译器优化 + 栈复用 
void bad(void) {
    int x = 42;
    if (setjmp(env) == 0) {
        foo();              /* 可能 longjmp 跳出 */
    }
    printf("%d\n", x);      /* x 可能不是 42 — 未定义或不可靠 */
}

典型合法用途

场景 说明
统一错误处理 深层解析失败 longjmp 到顶层 cleanup（类似 goto done）
解释器 / 协程雏形 旧式；现代多用 异常 / 显式状态机
信号处理（慎用） sigsetjmp / siglongjmp 保存信号掩码（6.13）

与 return 的区别

return longjmp
销毁栈帧 按序 pop 一次性 恢复旧 SP
调用析构 / cleanup C 无析构；goto 出块 也跳过
可跨多少层 一层 多层

现代替代

  • goto err + 单函数内 cleanup（Linux 内核风格）
  • C++ exceptions（若可用）
  • coroutine / async 库

面试：setjmp 保存了什么？ → 至少 SP、PC、 callee-saved 寄存器 等足以恢复执行点的机器相关状态（jmp_buf 不透明）。

常见陷阱

  1. longjmp 后用未 volatile 的 auto 局部：int x=42; setjmp(env); foo(); printf("%d",x); 中 foo longjmp 跳回后，x 不一定还是 42——编译器优化可能把它放在寄存器，longjmp 只恢复 callee-saved 寄存器，且栈可能被复写。C 标准明确这是不确定值。修法：给跨 longjmp 存活的局部加 volatile。
  2. longjmp 跨线程：跳到别的线程的 setjmp 点——栈不属于本线程，jmp_buf 里的 SP/PC 指向别处，崩溃。jmp_buf 只能在同线程内配对使用。
  3. C++ 中 longjmp 跳过析构：longjmp 直接恢复 SP/PC，不调用栈上对象的析构函数 → 资源泄漏（文件未关、锁未释放、内存泄漏）。C++ 应用异常（throw/catch 会展开调用析构），禁用 longjmp。

自测题

1.（选择） setjmp(env) 首次返回的值是？ - A. 1 B. 0 C. -1 D. 随机

答案

B。setjmp 首次直接调用返回 0；longjmp(env, val) 跳回后，setjmp 仿佛再次返回 val（非 0，若传 0 会被改成 1）。这个双返回语义是区分"正常路径"和"错误着陆"的关键。

2.（判断） longjmp 可以跳到其他线程的 setjmp 点。

答案

错。jmp_buf 保存的是本线程的 SP/PC/寄存器，跨线程跳转会指向别线程的栈 → 崩溃或数据错乱。POSIX 明确规定 longjmp 必须在同一线程内配对使用。跨线程要用线程间通信机制。

3.（踩坑） int x=42; if(setjmp(env)==0) foo(); printf("%d",x); 中 foo longjmp 跳回后 x 一定是 42 吗？怎么办？

答案

不一定。C 标准规定：跨 longjmp 后，非 volatile 的 auto 局部值不确定。编译器可能把 x 优化进寄存器，而 longjmp 只恢复 callee-saved 寄存器。修法：volatile int x = 42; 强制每次从内存读。这正是"必须遵守的规则"表里强调的。

4.（应用） setjmp 保存了哪些机器状态？为什么 jmp_buf 要设计成不透明？现代 C 代码该用什么替代 longjmp 做错误处理？

答案

保存至少 SP、PC、callee-saved 寄存器等足以恢复执行点的机器相关状态（具体由实现定，jmp_buf 是不透明数组）。不透明是因为内容平台相关，暴露了程序员可能误用。现代替代：① Linux 内核风格 goto err + 单函数 cleanup；② 状态机/错误码返回；③ C++ 用异常（会正确析构）。longjmp 现在主要见于解释器和遗留代码。

6.10

MS-DOS中的堆栈段

本节讲什么

6.9 的 Unix 平坦虚拟地址 模型之前，Intel x86 实模式 / 16 位 MS-DOS 用 段寄存器（CS、DS、SS、ES） 把逻辑地址 段:偏移 转成 20 位物理地址。本节作 历史对照：near / far、堆栈段 SS:SP 与 6.5 栈帧 概念相通但 硬件寻址完全不同。

要点

段:偏移 寻址

  物理地址 = (段寄存器 << 4) + 偏移
  例：SS=0x9000, SP=0x0100 → 0x9000*16+0x0100 = 0x90100
寄存器 典型用途（DOS 时代）
CS:IP 代码
DS 或 SS 数据 / 栈（可重叠设置）
SS:SP 栈顶
ES 额外数据段（字符串操作等）

6.5 的 SP 仍在，但 没有 x86-64 的 RBP 链 那么统一；16 位 栈帧更 ** cramped**。

near 与 far

修饰 指针大小 跨段？
near 16 位偏移（同段） 否
far 16 位段 + 16 位偏移 是 
/* 老编译器扩展（示意） */
void near func_near(void);
void far  func_far(void);
  • call near：压 16 位 offset（或仅跳转同段）
  • call far：压 CS 与 IP —— 类似 跨代码段 的 RA

与 6.5 RA 类比：far call 保存 段 + 偏移，返回需 retf。

MS-DOS 内存布局（简化）

  高地址  ┌─────────────┐
          │  PSP / 环境  │
          ├─────────────┤
          │  栈 (SS:SP)  │  ← 向下增长
          ├─────────────┤
          │  堆 (brksize)│  ← 向高地址（与 Unix 概念类似）
          ├─────────────┤
          │  BSS / 数据  │
          ├─────────────┤
          │  代码 (CS)   │
  低地址  └─────────────┘

mmap + MMU 实模式 / 286 保护模式过渡

  • 栈段 SS 与其它段 可共享基址 → 栈 溢出 可 覆盖代码或数据（与 6.5 / demo04 精神相同，更易发生）

信号与独立信号栈

概念 说明
默认 信号 handler 在 当前线程用户栈 上运行
sigaltstack 注册 备用栈，深度用户栈很浅或 stack overflow 时 handler 仍安全

alloca：栈上「malloc」

#include <alloca.h>
void foo(size_t n) {
    char *buf = alloca(n);   /* 在 *当前栈帧* 上 bump SP */
    /* 函数 return 时自动「释放」—— 无 free */
}
对比 alloca malloc
位置 栈（6.5 帧内） 堆（6.9）
释放 return 即失效 free
失败 可能 栈溢出 NULL
可移植 谨慎（GNU 扩展 常见）

危险：n 很大 或 递归 alloca → 瞬间栈耗尽。

VLA（C99 可变长数组，C11 可选）

void bar(int n) {
    int vla[n];        /* sizeof 在运行时；占 *栈* */
    /* C11 后许多编译器仍支持；-std=c11 可能需 -VLA 或扩展 */
}
特性 说明
存储 栈，随 6.5 帧创建/销毁
sizeof vla 整个数组（ch04 不退化例外在 VLA 块内）
风险 n 过大 → 栈溢出；6.8 longjmp 跳过销毁 → 泄漏 无（栈收回）但 语义复杂

Linux 内核 禁用 VLA；用户态教学代码可用 malloc(n*sizeof *p) 替代。

内核栈 vs 用户栈

  用户态 thread                内核态（syscall / 中断）
  ┌─────────────┐              ┌─────────────┐
  │ 用户栈       │              │ 内核栈       │  ← 每线程固定大小（如 8KB–16KB）
  │ (MB 级)      │   syscall    │ (独立映射)   │
  └─────────────┘ ──────────► └─────────────┘
要点 说明
分离 内核 不 在用户栈上执行 内核 C 代码
大小 内核栈 小 → 内核代码 禁止大数组局部、无 deep recursion

Q2栈帧结构
// 调用 foo(3, 4) 时的栈帧（x86-64 简化）
void foo(int a, int b) {
    int local = a + b;
    // ...
}

栈帧里有哪些东西？返回地址存在哪？

答案与复习指引

栈帧内容（从高到低）： 1. 参数 a=3, b=4（x86-64 前几个参数用寄存器，多余的压栈） 2. 返回地址（call 指令自动压入，函数返回时 ret 弹出） 3. 保存的 RBP（上一帧的基址指针） 4. 局部变量 local

安全风险： 如果 local 是 char buf[8]，用户写入超过 8 字节 → 覆盖返回地址 → 缓冲区溢出攻击（经典 stack smashing）。

Q3setjmp/longjmp 栈帧失效
jmp_buf env;

void func_a(void) {
    if (setjmp(env) == 0) {
        printf("first call\n");
        func_b();
    } else {
        printf("jumped back\n");
    }
}

void func_b(void) {
    int big_array[1000];
    big_array[0] = 42;
    longjmp(env, 1);  // 跳回 setjmp
    // big_array 还在吗？
}

longjmp 跳回后 func_b 的 big_array 还有效吗？为什么不能返回栈局部？

答案与复习指引

答案： longjmp 回滚栈指针到 setjmp 时的位置。func_b 的栈帧被丢弃，big_array 不再有效。后续函数调用会复用那块栈内存。

关键： longjmp 不能跳回已返回的函数的栈帧——那块内存已被复用，跳过去读到的是垃圾数据。

用途： 异常处理（C 没有异常机制）、协程、深层递归快速退出。
