5.1

函数库、链接和载入

本节讲什么

从 「编译完 .c 之后发生了什么」 入手：目标文件如何 链接（link） 成可执行文件或共享库，载入器（loader） 如何把程序放进内存并启动。建立 四阶段编译流水线（预处理 → 编译 → 汇编 → 链接）、ELF 段布局（.text / .data / .bss）、符号解析与重定位 三件套，并区分 强符号 / 弱符号 / 静态符号。最后用 nm、readelf 读懂 .o 里有什么——demo01_four_stage 逐步演示。

要点

四阶段编译流水线

一条典型的 gcc main.c -o main 背后，工具链大致是：

main.c  →  cpp  →  cc1  →  as  →  ld  →  main (可执行文件)
          预处理   编译    汇编   链接
          .i       .s      .o
阶段 工具 输入 → 输出 做什么
预处理 cpp（gcc -E） .c → .i 展开 #include、宏替换、条件编译
编译 cc1（gcc -S） .i → .s 生成 汇编；语法/类型检查在此完成
汇编 as（gcc -c） .s → .o 生成 可重定位目标文件（ELF .o）
链接 ld（gcc 调用） .o + 库 → 可执行文件 符号解析 + 重定位 + 段合并

demo01_four_stage 的 Makefile 把四步拆开：main.i → main.s → main.o → main。

cd demo/demo01_four_stage
make all
make inspect    # nm main.o; readelf -S main.o; readelf -r main.o

目标文件里的段（Section）

每个 .o / 最终可执行文件按 段 组织，常见三类 可加载段：

段 内容 典型来源 特点
.text 机器码（函数体） 函数定义 只读、可执行
.data 已初始化 全局/静态变量 int g = 1; 映像里占空间，有初值
.bss 未初始化 全局/静态变量 int g; NOBITS：文件里不占字节，载入时 零初始化

demo01 中 g_init = 1 进 .data，g_bss 进 .bss；运行输出 g_bss=0 即 BSS 零初始化。

readelf -S main.o          # 看段表：.text .data .bss .rodata ...
readelf -S main.o | grep bss   # .bss 常带 NOBITS 标志

.rodata：只读常量（字符串字面量、const 全局等），与 5.2 动态链接的 PIC 相关。

符号解析（Symbol Resolution）

链接器维护 全局符号表，对每个 全局符号（函数名、全局变量名）决定：

  1. 定义在哪：哪个 .o / 库成员提供了 唯一 定义？
  2. 引用在哪：哪些 .o 有 未定义引用（undefined reference）？
符号类别 含义 示例
强符号（strong） 有初值的全局，或函数 int x = 1;、void foo(void){}
弱符号（weak） 未初始化 tentative，或显式 __attribute__((weak)) int x;（GCC 10+ 默认 -fno-common 时进 .bss 当强定义）；教学 demo 用 weak 属性
外部引用 本单元用、别处定义 extern int x; 后使用 x

强 vs 弱规则（GNU ld，面试高频）：

  • 不允许两个 强符号 同名（链接错误 multiple definition）。
  • 一个 强 + 一个 弱 → 选 强 的定义。
  • 多个 弱 同名 → 选 其中一个（通常第一个遇到的）。

demo03_weak_strong：weak.c 中 __attribute__((weak)) int g_val;，strong.c 中 int g_val = 20;（强），链接后 g_val == 20。

cd demo/demo03_weak_strong
make && ./demo_weak
nm demo_weak | grep g_val

静态符号（static）：

static int counter;      /* 文件内可见，不出现在全局链接 */
static void helper(void) { }
  • 链接器 不 把 static 全局/函数当作跨文件符号解析。
  • 不同 .c 里各有一个 static int x，不冲突——各自是不同符号（通常带 .o 名修饰）。

函数名的链接属性：全局 vs static（两分法速记）

C 里函数（以及文件作用域的变量）只有两种链接属性，一句话分清：

写法 链接属性 规则
int test(){...}（不带 static） 外部链接 external linkage 符号全局可见；整个项目只能有 1 份实现，声明（int test();）可以写无数份
static int test(){...} 内部链接 internal linkage 符号锁死在本 .c；不同 .c 可以随便重名，互不干扰 
/* a.c：唯一一份实现 */
int test(void) { return 1; }

/* b.c：只声明、不实现 */
int test(void);          /* ✅ 合法，声明想写几份写几份 */
/* b.c 里可直接调用 test()，链接器会找到 a.c 的实现 */

/* a.c */
static int test(void) { return 1; }
/* b.c */
static int test(void) { return 2; }   /* ✅ 完全不冲突！两个互不相干的函数 */

记忆锚点：static = "静悄悄关在家里"，不让别的 .c 看见。 全局函数 = "贴在门牌号上"，整栋楼（整个项目）只能有一个同名住户； 想被别的 .c 调用，只需对方写个声明（贴个"这里要住 X"的便签），实现仍只此一份。

inline 函数放进头文件：必须加 static（否则链接报错）

头文件里写带函数体的 inline 时，必须写成 static inline。原因：#include 本质是文本复制粘贴——头文件里放什么，每个 .c 里就各有一份什么。

/* tool.h —— ❌ 错：不带 static */
inline int test(void) { return 100; }
/* a.c 和 b.c 都 #include "tool.h"：预处理后各得到一份 inline test 的定义 */

/* tool.h —— ✅ 对：带 static */
static inline int test(void) { return 100; }
/* 复制进 a.c：a 私有；复制进 b.c：b 私有 */
/* 两份都是 static（内部链接），互不干涉，名字一样也没事 */
头文件写法 每个 .c 得到什么 链接结果
static inline int test(){...} 一份私有实现（内部链接） ✅ 各用各的，最省心
inline int test(){...} 一份 inline definition（不导出外部定义） ❌ 调用点报 undefined reference（-O2 可能侥幸通过）
extern inline int test(){...} 导出一份外部定义 ❌ 多个 .c 都有 → multiple definition

结论是「必须 static inline」，但报错原因要分版本（这是 C99 埋的坑）： inline 只是建议编译器内联展开，不改变"要不要导出外部符号"这件事。 - 现代 GCC（默认 -std=gnu17，C99 语义）：裸 inline 是 inline definition， 它不提供外部定义（nm 里是 U，不是 T）。于是 -O0 下每个调用点都变成 对 test 的外部引用、却没人提供 T test → undefined reference；-O2 下调用 被内联掉、不再需要符号 → 侥幸通过。一个纯优化开关就改变了链接成败。 - 老标准（-std=gnu89）：inline 语义对调，它导出外部定义，多个 .c 各一份 全局 T test → multiple definition（老教程里说的"重复定义"正是这个语境）。

工程铁律：头文件里的函数体，一律 static inline（三种 -std、两种 -O 全绿， 唯一代价是取地址不唯一）。需要"全项目唯一一份函数地址"时才用标准写法：头文件 inline + 恰好一个 .c 补 extern inline 声明。这两种语义的对调、取函数地址必挂、 -O0/-O2 差异等完整实测矩阵见 《Pointers on C》3.8.1 （../../02-Pointers-on-C/ch03-data/3.8-static/3.8.1-头文件里的inline与三态语义.md）。

重定位（Relocation）

编译单个 .c 时，编译器 不知道 最终地址，故在 .o 里留下 重定位条目：「此处 4 字节需填上符号 foo 的地址 + 偏移」。

链接阶段：

  1. 合并各 .o 的同名段（所有 .text 拼在一起……）。
  2. 分配 虚拟地址（或相对地址）。
  3. 回填 所有重定位槽位。
readelf -r main.o    # Relocation section：哪些偏移引用哪些符号

5.5 会用 map 文件、objdump -R 进一步查看。

函数库：静态 .a 与链接

静态库 = 若干 .o 的归档（archive），用 ar rcs 打包：

ar rcs libadd.a add.o    # demo02_static_lib

链接时 只拉入 解决 当前未定义符号 所需的 .o 成员（5.3 详述扫描顺序）。

cd demo/demo02_static_lib
make
./demo_static

用 nm 读符号

nm main.o

常见列含义：

列 含义
T / t 代码段符号（T 全局，t static）
D / d 已初始化数据
B / b BSS
U Undefined — 本文件引用、别处定义
W / w 弱符号

与 ch04 的衔接：链接不做类型检查

4.2 / 4.4 的经典 bug：char arr[] 定义 + extern char *arr 声明 —— 符号名 arr 匹配，类型 不匹配，链接器 不报错，运行崩溃。

链接器只认 符号名字节串，不做 C 类型等价检查。声明/定义匹配是 程序员 的责任。

载入（Loading）

可执行文件生成后，载入器（Linux 上常由内核 execve + 动态链接器配合）：

  1. 映射 PT_LOAD 段到进程地址空间；
  2. 为 BSS 分配并清零；
  3. 设置 入口点（ENTRY，见 demo04 的 kernel.lds）；
  4. 动态链接时还会加载 共享库（5.2）。

链接脚本预览（kernel.lds）

嵌入式 / 内核常用手写 .lds 规定段地址与边界符号：

ENTRY(_start)
_stext / _etext   — .text 起止
_sbss  / _ebss    — .bss  起止

demo04_linker_script 用 ld -T kernel.lds 生成 kernel.elf（无 libc），C 代码通过 extern char _stext, _ebss; 引用边界。

常见陷阱

  1. 把 int g; 和 int g = 0; 当一回事：前者进 .bss（NOBITS，文件里不占字节，载入时清零）；后者进 .data（映像里占 4 字节带初值）。运行后值都是 0，但文件大小和载入方式不同。size main.o 的 data/bss 两列能直接看出区别。
  2. 两个 .c 都写 int x;（未初始化全局）：老规则（-fcommon）下当作弱符号合并成一个；GCC 10+ 默认 -fno-common，变成强符号重复定义 → multiple definition 链接错误。旧 C 代码迁移到新工具链常踩。修法：加 __attribute__((weak)) 或改成 static。
  3. 以为链接器会检查类型：extern char *arr; 声明 + char arr[] 定义，符号名 arr 匹配，链接成功，但指针和数组取值方式不同 → 运行崩溃。链接器只认符号名字节串，类型匹配是程序员的责任（靠头文件）。
  4. 头文件里写 inline int f(){...}（漏了 static）：现代 GCC（C99 语义）下裸 inline 是 inline definition、不导出外部定义，-O0 报 undefined reference、-O2 可能侥幸通过；老标准 gnu89 下才是"多份全局实现 → multiple definition"。无论哪种，正确写法都是 static inline。见上"inline 函数放进头文件"，完整实测见《Pointers on C》3.8.1。

自测题

1.（选择） int g = 1; 进哪个 ELF 节？ - A. .text B. .data C. .bss D. .rodata

答案

B。有初值的全局进 .data；未初始化的进 .bss；只读常量进 .rodata；函数代码进 .text。

2.（判断） 两个 .c 各写 int x;（未初始化全局），GCC 12 默认下能链接成功。

答案

错。GCC 10+ 默认 -fno-common，两个都是强符号 → multiple definition of 'x'。要么加 __attribute__((weak))，要么改成 static 限制作用域。

3.（踩坑） gcc -lm main.c -o app 报 undefined reference to 'sin'，为什么？怎么改？

答案

链接器从左到右扫描：先扫 -lm 时 main.o 还没入链，没有 undefined sin，所以 libm.a 里 sin.o 没被拉入。改成 gcc main.c -o app -lm（库放对象后面）。见 5.3 秘密 1。

4.（应用） 函数内写 static int counter = 0;，它在 ELF 哪个节？和普通 auto int x; 在运行时位置有何不同？

答案

static int counter = 0; 进 .data（有初值；若是 static int counter; 则进 .bss）。它在程序生命周期存活，地址固定在数据段。普通 auto int x; 在栈帧上，函数返回后失效、地址被复用。见 6.6。

5.（踩坑） 头文件 tool.h 写了 inline int test(void){ return 1; }，a.c、b.c 都 #include 它，链接会怎样？怎么改？

答案

分版本，两个错误都真会发生： - 现代 GCC（默认 -std=gnu17，C99 语义）：裸 inline 是 inline definition、不导出外部定义。-O0 下每次调用变成对 test 的外部引用、没人提供 T test → undefined reference；-O2 下调用被内联掉 → 侥幸通过。 - 老标准 -std=gnu89：inline 语义对调、导出外部定义，两个 .c 各一份全局 T test → multiple definition。

无论哪种，改法一致：static inline int test(void){ return 1; }——展开后是各 .c 的私有函数（内部链接），三种 -std、两种 -O 全绿。完整实测见《Pointers on C》3.8.1。

5.2

动态链接的优点

本节讲什么

5.1 侧重静态链接与目标文件结构；本节说明 动态链接（dynamic linking） 为何成为现代 Unix/Linux 默认方案：共享库（shared library） 在磁盘与内存中 只存一份，多进程共享；位置无关代码（PIC） 使 .so 可加载到任意地址；延迟绑定（lazy binding） 推迟符号解析到 首次调用。介绍 ldd 查看依赖，并与 5.3 静态库、5.4 插桩 对比。

要点

静态链接 vs 动态链接

维度 静态链接（.a） 动态链接（.so）
链接时机 编译链接时把库代码 拷进 可执行文件 链接时只记录 依赖；运行时再解析
体积 每个程序一份库代码副本 磁盘上 一份 .so，多程序共享
更新 改库需 重新链接 所有程序 替换 .so（兼容 ABI）即可生效
内存 每进程独立代码副本 物理页可 共享（同版本 .so）
启动 无运行时链接开销 需 动态链接器（如 ld-linux-x86-64.so.2） 
gcc -static main.c -o main_static    # 尽量静态链接（体积大）
gcc main.c -o main_dyn               # 默认动态链接 libc 等
file main_dyn                        # "dynamically linked"

共享库是什么

  • Linux 上通常为 ELF 共享目标 libfoo.so（Windows 对应 DLL）。
  • 编译：gcc -shared -fPIC -o libfoo.so foo.c
  • 链接程序：gcc main.c -L. -lfoo → 可执行文件的 .dynamic / .got.plt 段记录依赖。

命名惯例：libm.so → 链接选项 -lm（5.3 讲顺序）。

位置无关代码（PIC）

共享库被 不同进程 映射到 不同虚拟地址，因此：

  • 库内 不能 写死绝对地址访问全局数据/函数；
  • 编译加 -fPIC，通过 全局偏移表（GOT） 与 过程链接表（PLT） 间接寻址。
  调用 printf@plt  →  第一次：动态链接器解析真实地址，写入 GOT
                     之后：  经 GOT 跳转到 libc 中的 printf

.text 中 PIC 代码可 只读映射多进程共享；可写数据在 .data / .bss 或 per-process 副本（取决于 RTLD 与链接方式）。

延迟绑定（Lazy Binding）

默认策略（如 GNU ld 的 PLT + lazy）：

  1. 程序启动时 不 解析每个 printf、malloc 的真实地址；
  2. 第一次 调用 某 PLT 槽位时，动态链接器 才解析并 补丁 GOT；
  3. 后续调用走 已解析 的快速路径。

优点：启动快；未用到的库函数 零解析成本。

LD_BIND_NOW=1 ./a.out    # 强制启动时全部解析（调试 / 安全场景）

动态链接器与 ldd

进程启动链（简化）：

kernel execve → 程序 PT_INTERP 指向 ld.so → ld.so 加载 .so、重定位、跳 _start

ldd 列出可执行文件需要的共享库及路径（注意：对不可信二进制勿盲目运行 ldd，有历史安全坑；教学环境可用）：

ldd ./main_dyn
# linux-vdso.so.1
# libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
# /lib64/ld-linux-x86-64.so.2

与 5.1 段布局的关系

动态可执行文件除 5.1 的 .text/.data/.bss 外，常见：

段 / 节 作用
.dynamic 依赖库名、重定位类型等 元数据
.got / .got.plt 全局偏移表（存解析后的地址）
.plt 过程链接表（调用共享函数的跳板）
.rel.dyn / .rela.dyn 动态重定位项

静态 .o 用 readelf -r（5.1）；已链接的动态可执行文件还可 objdump -R（5.5）。

何时仍用静态库

场景 原因
嵌入式 / 无 OS 无 ld.so，常 纯静态 或裸机 demo04
单文件分发 避免目标机缺 .so
性能敏感且库很小 避免 PLT 间接跳转（现代差距常很小）
内核模块 内核自有链接模型，非用户态 .so

demo02_static_lib 演示 ar rcs + -ladd；与 5.3 的扫描规则直接相关。

安全与插桩（预告 5.4）

动态链接使 运行时替换 共享库函数成为可能：

  • LD_PRELOAD 优先加载指定 .so，覆盖 malloc 等符号；
  • 调试、性能分析、（恶意）拦截都利用同一机制。

代码自测

题目 1： 静态链接和动态链接各有什么优缺点？

参考答案

静态链接：可执行文件自包含、启动快、不依赖库版本；但文件大、库更新需重新链接、多个进程各存一份库代码。动态链接：文件小、库更新只需替换 .so、多进程共享内存中的库代码；但启动稍慢（动态解析符号）、依赖库版本兼容性（ABI 稳定性）。HFT 场景通常用静态链接减少启动延迟和符号解析开销。

5.3

函数库链接的5个特殊秘密

本节讲什么

静态库链接有许多 反直觉 规则，导致「明明有 libfoo.a 却 undefined reference」或「加上 -lm 就好了」类问题。本节归纳书中 五个秘密：归档 从左到右扫描、未定义符号 才从 .a 拉 .o、循环依赖 的处理、-lm 必须放在对象后面、静态链接导致 重复代码。结合 demo02_static_lib 与 ch04 链接不做类型检查 一并理解。

要点

秘密 1：链接器按命令行从左到右扫描

gcc main.o -L. -ladd -o demo    # 常见正确顺序
gcc -ladd main.o -o wrong       # 错误：扫描 -ladd 时尚无 undefined，可能拉不到 add.o

链接器维护 可执行映像 + 当前未定义符号集合。处理每个输入时：

  • .o 文件：全部 链入（不管是否被引用——除非 --gc-sections 等优化）；
  • .a 归档：按需 提取成员（见秘密 2）。

规则：把 还没被满足的库 放在 引用它们的 .o 之后；若库 A 依赖库 B，常写：-lA -lB 且整体在 main.o 后。

秘密 2：只有未定义符号才会从 .a 里拉 .o

静态库 不是「一整块链接进去」，而是 符号索引的 .o 集合：

libadd.a = [ add.o ]     # ar rcs libadd.a add.o

链接 main.o 时若 main.o 有 U add（undefined add），扫描 libadd.a 时发现 add.o 定义了 add → 提取 add.o 并入链接。

若 main.c 从不调用 add()，且没有其它 undefined 指向 add.o 内符号 → add.o 不会进最终可执行文件（减小体积）。

cd demo/demo02_static_lib
make clean && make
nm main.o | grep add          # U add
nm demo_static | grep add     # T add（已定义）
ar t libadd.a                 # 列出归档成员

秘密 3：循环依赖要重复或分组

典型模式：

libA.a  需要  libB.a  中的 foo()
libB.a  需要  libA.a  中的 bar()

单次 gcc ... -lA -lB 可能失败：扫完 A 拉入部分成员，B 又需要 A 中新符号，但 A 不再扫描。

解法：

gcc ... -lA -lB -lA          # 重复扫描
# 或
gcc ... -Wl,--start-group -lA -lB -Wl,--end-group

内核 / 大型 C 项目 Makefile 里常见 group 或 重复 -l。

秘密 4：-lm 为什么常放最后

数学库 libm.so / libm.a** 中的sin、cos、pow` 等 不会** 在链接开始时自动参与扫描。

gcc main.c -lm -o ok           # 错：main 的 undefined 尚未出现时就扫了 -lm
gcc main.c -o ok -lm           # 对：main.o 先入，undefined sin 再由 -lm 满足
gcc main.o -o ok -lm           # 更明确

gcc 驱动有时会把 -l 重排，但 手写 ld 命令 或 静态链接 时必须自己保证顺序。与 秘密 1 同一原理。

秘密 5：静态链接造成重复代码

每个用 静态 .a 的可执行文件 各自拷贝 一份库 .o 代码：

  • 10 个程序都静态链 libcrypto.a → 10 份相同机器码占 磁盘与内存；
  • 动态 .so 则 一份物理页多进程共享（5.2）。

权衡：

选择 优点 缺点
静态 .a 部署简单、无 .so 依赖 体积大、更新需重链
动态 .so 共享、易更新 依赖 ABI、启动需 ld.so

与 ch04：链接器不检查 C 类型

秘密 2 只保证 符号名 一致，例如 arr 在 A 文件是数组、B 文件声明成指针 —— 仍可能 链接成功（4.2 demo02_wrong），运行才崩溃。

类型匹配 靠头文件与程序员；链接器 只拼 名字 + 地址。

实用命令速查

ar rcs libfoo.a foo.o bar.o    # 创建 / 更新静态库
ar t libfoo.a                  # 列出成员
nm -A libfoo.a                 # 看归档里各 .o 的符号
gcc main.o -L. -lfoo -o app    # 库放 main.o 后

常见链接错误解读

错误信息 常见原因
undefined reference to 'foo' 缺 .o、库顺序错、库未加入
multiple definition of 'foo' 两个 强符号 同名（5.1）
cannot find -lfoo -L 路径不对或库不存在

常见陷阱

  1. 库顺序写反：gcc -lfoo main.o -o app —— 扫描 -lfoo 时还没有 undefined，foo.o 没被拉入 → undefined reference to 'foo'。必须 main.o 在前、-lfoo 在后。这是 5 个秘密里最高频的坑。
  2. 循环依赖只写一次：libA.a 和 libB.a 互相引用，单次 gcc main.o -lA -lB 扫完 B 时又需要 A 的新符号，但 A 不再扫描 → 失败。要 -lA -lB -lA 重复，或 -Wl,--start-group -lA -lB -Wl,--end-group。
  3. 以为静态库所有 .o 都进去：静态库 .a 是按需提取——只有当存在未定义符号指向某成员 .o 时才拉入。如果 main.c 从不调 add()，add.o 不会进最终可执行文件。想看实际链入了哪些，用 -Wl,-Map=main.map（5.5）。

自测题

1.（选择） gcc main.o -L. -ladd 中，libadd.a 里的 add.o 何时被链入？ - A. 总是链入 B. 仅当 main.o 有 undefined add C. 看 -O 优化级别 D. 看链接顺序无关

答案

B。静态库按需提取：main.o 有 U add（undefined）才从 libadd.a 拉 add.o。从不引用则不链入。这是秘密 2。

2.（判断） 静态库 libfoo.a 里所有 .o 都会进最终可执行文件。

答案

错。只有满足当前 undefined 符号所需的成员 .o 才被提取。这是静态库减体积的关键机制。想全部链入得显式列每个 .o。

3.（踩坑） libA.a 和 libB.a 互相依赖，gcc main.o -lA -lB 报 undefined，怎么办？

答案

两种解法：① 重复写 gcc main.o -lA -lB -lA；② 用分组 gcc main.o -Wl,--start-group -lA -lB -Wl,--end-group（链接器在组内反复扫描直到稳定）。内核/大型 C 项目 Makefile 里常见。

4.（应用） 为什么 10 个程序静态链 libcrypto.a 比动态链 .so 占更多磁盘？动态链靠什么机制共享？

答案

静态链：每个可执行文件各自拷贝一份库代码（秘密 5），10 份相同机器码。动态链：磁盘上一份 .so，运行时内核将同一物理页映射到多个进程地址空间（共享，MAP_SHARED）。见 5.2。

5.4

警惕 Interpositioning

本节讲什么

Interpositioning（插桩 / 符号介入） 指在 正常目标函数之前 插入自己的实现，仍 调用原函数 或直接 替换 行为。Linux 上常用 LD_PRELOAD、链接器 --wrap、以及 malloc 调试钩子 实现。能力强大：性能分析、内存泄漏检测、安全审计；也 可被滥用 或 误用 导致诡异 bug。本节建立机制心智模型，并强调 生产环境警惕。

要点

什么是 Interpositioning

  应用调用 malloc()
        ↓
  [ 你的 my_malloc ]  — 记录、统计、加 fence
        ↓
  [ 真正的 malloc ]   — libc 实现

要求：你的符号在链接 / 加载顺序上「赢过」 libc 中的同名符号，且通常需要 保存原函数指针 以便转调。

手段 1：LD_PRELOAD

动态链接器加载共享库顺序中，预加载库 优先：

export LD_PRELOAD=/path/to/myhook.so
./my_program

myhook.so 中若 导出 malloc、free 等 全局函数，会 覆盖 libc.so 中的默认解析（同一进程内）。

典型合法用途：

用途 说明
内存调试 统计分配、检测 double-free、写越界 fence
I/O 追踪 记录 open/read/write
延迟加载故障注入 测试错误路径

风险：

  • 与 静态链接 程序 无效（无动态符号表可替换）；
  • 与 直接链接 -lmalloc 或 LTO 内联 组合时行为复杂；
  • 安全：不可信环境勿运行带陌生 LD_PRELOAD 的程序；
  • 性能：每次调用多一层间接。

最小示例思路（教学伪代码）：

#define _GNU_SOURCE
#include <dlfcn.h>
#include <stdlib.h>

static void *(*real_malloc)(size_t);

void *malloc(size_t n)
{
    if (!real_malloc)
        real_malloc = dlsym(RTLD_NEXT, "malloc");
    /* log: size n */
    return real_malloc(n);
}

编译：gcc -shared -fPIC myhook.c -o myhook.so -ldl

手段 2：--wrap 符号（链接期）

GCC / ld 支持 包装 指定符号：

gcc main.c wrap_malloc.o -Wl,--wrap=malloc -o app
  • 调用 malloc 的代码被改写成调用 __wrap_malloc；
  • 你在 wrap_malloc.o 里实现 __wrap_malloc，并用 __real_malloc 调回原函数。
符号 角色
__wrap_malloc 你的插桩实现
__real_malloc 链接器提供的 原 malloc 别名

适合 静态链接 或 不想依赖 LD_PRELOAD 的场景；需在 链接命令 中显式启用。

手段 3：malloc 调试钩子（历史 / 特定 libc）

部分环境提供 malloc_hook、mtrace/muntrace（glibc 文档中有说明，新版本可能变更或受限）：

#include <mcheck.h>
int main(void) {
    mtrace();   /* 写 MALLOC_TRACE 指定文件 */
    /* ... */
    muntrace();
}

与 5.2 延迟绑定 结合：钩子必须在 第一次 malloc 前 安装才有效。

与 5.1 / 5.2 符号规则的关系

机制 生效阶段 覆盖对象
强符号重复定义 静态链接 报错（5.1）
LD_PRELOAD 动态加载 同名 全局函数 优先
--wrap 链接重写 调用点改为 __wrap_*
dlsym(RTLD_NEXT, ...) 运行时 在预加载链中找到 下一个 定义

弱符号（5.1 demo03）与插桩不同：弱符号是 链接器合并规则，不是「拦截调用」。

开发中的正当 vs 危险用法

正当：

  • 本地调试内存；CI 里对测试二进制注入 trace .so；
  • 用 --wrap 在单元测试里替换 time() 返回固定值。

危险 / 警惕：

  • 生产服务器全局 LD_PRELOAD 未知 .so；
  • 插桩 非线程安全 的 libc 函数却用于多线程服务；
  • 假设插桩了 malloc 就能捕获 mmap/brk 等底层分配路径（不完整）；
  • 与 Sanitizer（ASan/LSan）同时用可能 冲突。

与 ch04 对比

4.2 的 bug 是 错误声明 导致 错误地址 被使用；Interpositioning 是 故意 替换符号实现。二者都说明：最终跑的是链接 / 加载后 谁 提供了该名字的定义。

常见陷阱

  1. LD_PRELOAD 对静态链接程序无效：gcc -static 出来的程序没有动态符号表，LD_PRELOAD 无处替换。想插桩静态程序要用链接期 --wrap。
  2. 插桩 malloc 忘了 dlsym(RTLD_NEXT)：直接在 my_malloc 里调 malloc → 递归调自己，栈溢出崩溃。必须先 real_malloc = dlsym(RTLD_NEXT, "malloc") 拿到原函数再转调。
  3. 生产环境全局 LD_PRELOAD 陌生 .so：安全风险——任何全局符号都能被替换（malloc/open/read），可能植入后门或窃取数据。只用于本地调试，不可信环境勿带陌生 LD_PRELOAD 运行。

自测题

1.（选择） LD_PRELOAD 能覆盖以下哪个？ - A. static 函数 B. libc 全局函数 C. 内联函数 D. 宏

答案

B。LD_PRELOAD 作用于动态符号表中的全局函数。static 函数符号不可见（A 错）；内联可能被优化无调用点（C 错）；宏是预处理替换，编译前就消失（D 错）。

2.（判断） --wrap=malloc 后，代码里的 malloc 调用被改写成 __wrap_malloc。

答案

对。链接器把对 malloc 的引用重写为 __wrap_malloc；你在 __wrap_malloc 里用 __real_malloc 调回原函数。适合静态链接或不想依赖 LD_PRELOAD 的场景。

3.（踩坑） 你用 LD_PRELOAD=./myhook.so ./app 注入 malloc 统计，但 app 是 gcc -static 编译的，没生效，为什么？怎么办？

答案

静态链接程序没有动态符号表，LD_PRELOAD 无法替换符号。改用链接期 --wrap：gcc app.c wrap_malloc.o -Wl,--wrap=malloc -o app，在 wrap_malloc.o 里实现 __wrap_malloc + __real_malloc。或者改用动态链接。

4.（应用） 写一个 --wrap=time 的 wrap，让 time() 在单测里总返回固定值 1000。

答案 
// wrap_time.c
#include <time.h>
time_t __wrap_time(time_t *t) {
    if (t) *t = 1000;
    return 1000;
}
// 链接：gcc app.c wrap_time.c -Wl,--wrap=time -o app
// app 里调 time() 实际进 __wrap_time，返回 1000

题目 1： 静态链接和动态链接各有什么优缺点？

参考答案

静态链接：可执行文件自包含、启动快、不依赖库版本；但文件大、库更新需重新链接、多个进程各存一份库代码。动态链接：文件小、库更新只需替换 .so、多进程共享内存中的库代码；但启动稍慢（动态解析符号）、依赖库版本兼容性（ABI 稳定性）。HFT 场景通常用静态链接减少启动延迟和符号解析开销。

章节自测

链接是 C 到可执行文件的最后一关。看代码 → 想答案 → 点开验证。

Q1链接器不做类型检查
// file_a.c
int get_value(void) { return 42; }   // 返回 int

// file_b.c
double get_value(void);              // 声明为返回 double!
int main(void) {
    double v = get_value();
    printf("%f\n", v);
    return 0;
}

链接器会报错吗？运行结果是什么？

答案与复习指引

答案： 链接器不报错——它只匹配符号名 get_value，不检查返回类型。

运行结果：UB——file_a.c 返回 int 42（通过 eax 寄存器），file_b.c 以为返回 double（从 xmm0 或 FPU 寄存器读），读到垃圾值。

教训： 头文件统一声明，让编译器在编译期发现不匹配。链接器只管符号名。

复习： → 5.1 函数库、链接和载入

Q2静态库链接顺序
# 为什么这条命令报 "undefined reference to sqrt"？
gcc main.c -lm -o app

# 而这条能通过？
gcc main.c -o app -lm

# 还有这条也能？
gcc -o app main.c -lm

-lm 放哪里有什么区别？

答案与复习指引

答案： 静态库（.a）链接时从左到右扫描。gcc 先处理 main.c（找到未定义的 sqrt），再扫描 -lm 找到 sqrt 的定义 → 成功。

如果 -lm 在 main.c 前面 → 链接器先扫描 -lm（此时没未定义符号需要它）→ 跳过 → 再编译 main.c（发现需要 sqrt）→ 已扫过的库不会再回头 → 报 undefined reference。

教训： 库放在目标文件后面。依赖关系：main.o → liba → libb 则顺序为 main.o -la -lb。

复习： → 5.3 函数库链接的5个特殊秘密

Q3强弱符号冲突
// file_a.c
int counter = 100;           // 强符号

// file_b.c
int counter = 200;           // 也是强符号！
// 链接会怎样？

// file_a.c
int counter = 100;           // 强符号

// file_b.c
int counter;                 // 弱符号（无初始化）
// 链接会怎样？counter 最终是多少？
答案与复习指引

第一组： 两个强符号 → 链接报错 multiple definition of 'counter'。

第二组： 一个强一个弱 → 链接器选择强符号（= 100），弱符号被忽略。不报错。

内核用途： weak 属性定义默认实现，板级代码用强符号覆盖。链接器自动选择强版本。

复习： → 5.1 函数库、链接和载入 — 强/弱符号规则

Q4LD_PRELOAD 拦截
// mymalloc.c
void *malloc(size_t sz) {
    // 统计分配次数
    static int count = 0;
    count++;
    return real_malloc(sz);  // 调真实 malloc
}

// 运行：LD_PRELOAD=./mymalloc.so ./myapp

LD_PRELOAD 做什么？这个技术在 HFT/调试中有什么用？

答案与复习指引

答案： LD_PRELOAD 让动态链接器优先加载指定库的符号，覆盖后续库中的同名符号（Interpositioning）。

用途： 1. 内存调试：覆盖 malloc/free 统计泄漏 2. 性能分析：覆盖 read/write 记录 I/O 3. 安全审计：拦截 open/connect 检查访问 4. HFT：覆盖 pthread_mutex_lock 检测锁竞争

风险： 可能破坏程序假设，引发隐蔽 bug。
