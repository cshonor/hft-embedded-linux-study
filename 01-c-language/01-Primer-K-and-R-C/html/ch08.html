导读

本章讲什么

从第 7 章 stdio 下沉到 fd + 系统调用：open/read/write/lseek/stat、目录与链接，以及 fopen 实现、目录列表、malloc 与 sbrk 三个实例。是 Linux 用户态、自制类 Unix OS、HFT 低延迟 I/O 的核心一章。

学习重点（K&R 正文）

  • fd 0/1/2 与 FILE* 关系；dup2 重定向
  • read/write 短读写循环；与 fread 缓冲/性能差异
  • open 标志、unlink/link 与 inode 计数
  • lseek 随机访问；stat 元数据
  • 三实例：stdio 封装、目录枚举、堆分配

延伸：进程、IPC、信号（面试高频）

K&R 第二版本章侧重 I/O；下列接口是完整 UNIX 用户态模型必备，与你提纲 8.8–8.11 对应：

pipe 管道

int pipe(int fd[2]);   /* fd[0] 读端, fd[1] 写端 */
  • 单向字节流；fork 后父子各关一端实现 IPC
  • Shell cmd1 | cmd2：dup2 把 stdout 接到 pipe 写端

fork / exec / wait

调用 作用
fork() 复制进程；子返回 0，父返回 pid
exec* 用新程序替换当前进程映像（path、argv、env）
wait/waitpid 父进程回收子进程，避免僵尸进程
  • 现代内核 写时复制（COW）：fork 不立即复制全部物理页
  • fd 继承：子进程复制 fd 表 → pipe、重定向基础

signal 信号

void (*signal(int sig, void (*handler)(int)))(int);
  • 异步通知：SIGINT（Ctrl+C）、SIGSEGV、SIGCHLD、定时器等
  • handler 中仅调 async-signal-safe 函数；复杂逻辑用 sigaction + 标志位
  • 易打乱执行流：竞态、可重入 —— 重难点

场景映射

方向 本章技能
自制 OS / 类 Unix fd、文件、目录、进程模型设计参考
HFT 无缓冲 read/write；pipe 转发；dup 分离日志
嵌入式 Linux 设备文件 fd；fork+pipe 采集进程

重难点

  1. stdio 缓冲 vs 原生 read/write
  2. fork 后 fd 共享、COW
  3. pipe 单向 + 同步
  4. 硬链接 / unlink 与 inode
  5. 信号异步安全

代码自测

题目 1： 以下代码用 read/write 替代 printf/fgets，有什么区别？

char buf[1024];
int n = read(0, buf, sizeof(buf));  // 0 = stdin
write(1, buf, n);                    // 1 = stdout
参考答案

read/write 是系统调用（POSIX），直接操作文件描述符——无缓冲、无格式化。printf/fgets 是标准库函数——有缓冲、类型安全。read 返回实际读取的字节数（可能小于请求），write 返回实际写入的字节数。系统调用比库函数开销大（用户态/内核态切换），但更底层。K&R ch08 是理解 Unix I/O 模型的基础。

8.1

文件描述符

本节讲什么

文件描述符（fd） 是内核为进程打开的 I/O 对象分配的小整数。第 7 章 FILE* 标准流建立在 fd 之上；本章从 stdio 下沉到系统调用，无用户态缓冲，延迟更低。

要点

标准 fd（固定）

fd 流 用途
0 stdin 标准输入
1 stdout 标准输出
2 stderr 标准错误
  • 进程启动时由 shell 或 init 打开；可 重定向（> 2>&1）
  • FILE *stdin 等是对 fd 0/1/2 的 stdio 封装（带缓冲）

fd vs FILE*

系统调用（fd） stdio（FILE*）
接口 read/write/open fread/fprintf/fopen
缓冲 内核缓冲，用户态无 stdio 缓冲 用户态缓冲
场景 HFT、驱动、精确控制 可移植工具、格式化

dup / dup2（IO 重定向底层）

dup(oldfd);              /* 复制 fd，返回新编号 */
dup2(oldfd, newfd);      /* 令 newfd 指向与 oldfd 同一打开文件 */
  • Shell cmd > log：dup2(fd, 1) 把 stdout 绑到文件
  • 2>&1：stderr 合并到 stdout
  • fork 后子进程继承 fd 表，配合 pipe 做 IPC（见章 README）

底层场景

  • Linux 一切皆文件：socket、epoll、设备节点也是 fd
  • HFT：热路径 read/write 绕过 stdio
  • 嵌入式：/dev/ttyS0 打开得 fd，串口读写

常见陷阱

  1. fd 泄漏导致 EMFILE：open 后忘记 close，进程 fd 表（默认 1024 个）逐渐耗尽，新 open 返回 -1 且 errno=EMFILE。长期运行的服务/守护进程尤其要防泄漏——用 valgrind --track-fds=yes 或 lsof -p <pid> 检查。
  2. close-on-exec 标志被忽略：fork + exec 后子进程默认继承父进程所有打开的 fd。若不希望某个 fd 被 exec 后的子进程持有（如管道写端泄漏导致读端不收 EOF），需设 FD_CLOEXEC 或 open 时加 O_CLOEXEC。这是产生僵尸 fd 和资源泄漏的常见原因。
  3. fd 0/1/2 被关闭后 open 复用其编号：守护进程关闭 stdin/stdout/stderr 后，open 返回的最小可用 fd 可能是 0/1/2。此时 printf（写 fd 1）会写到新打开的文件——这是重定向的原理，但也可能是意外（程序以为在写终端实际写文件）。

自测题

1. 选择：进程默认打开的三个标准 fd 是？ - A. 0=stdin, 1=stdout, 2=stderr - B. 0=stdout, 1=stdin, 2=stderr - C. 1=stdin, 2=stdout, 3=stderr - D. 0=stderr, 1=stdin, 2=stdout

答案

A。fd 0/1/2 固定对应 stdin/stdout/stderr，由 shell 或 init 在进程启动时打开。FILE *stdin/stdout/stderr 是对这三个 fd 的 stdio 封装（带缓冲）。dup2(fd, 1) 把 fd 1 重定向到新文件，printf 输出就改道了。

2. 判断：fork 后子进程和父进程的 fd 指向不同的打开文件。

答案

错。fork 后子进程继承父进程的 fd 表（副本），两个表的同一编号 fd 指向同一个内核打开文件对象（共享文件偏移量）。父读 10 字节后，子的读位置也前进 10 字节——这是 pipe/IPC 的基础。只有 open 才创建新的打开文件对象。

3. 踩坑：close(1); int fd = open("log.txt", O_WRONLY|O_CREAT, 0644); 后 printf("hi\n") 输出到哪了？

答案

输出到 log.txt。close(1) 释放了 fd 1（stdout），open 返回最小可用 fd = 1，于是 log.txt 绑定到 fd 1。printf 内部写 fd 1（stdout），实际写到了 log.txt。这就是 shell 重定向 prog > log.txt 的底层原理（dup2）。但注意：stdout 有缓冲，需 fflush(stdout) 才真正写入。

4. 应用：用 dup2 实现 prog 2> error.log——把 stderr 重定向到 error.log 文件。

答案 
#include <fcntl.h>
#include <unistd.h>

int fd = open("error.log", O_WRONLY|O_CREAT|O_TRUNC, 0644);
if (fd < 0) { perror("open"); return 1; }
dup2(fd, 2);     /* fd 2 (stderr) 现在指向 error.log */
close(fd);       /* 原 fd 不再需要，fd 2 已是同一打开文件 */
fprintf(stderr, "this goes to error.log\n");

dup2(oldfd, newfd) 让 newfd 指向与 oldfd 同一打开文件。shell 的 2> >& | 都靠 dup2 实现。守护进程常把 stdin/stdout/stderr 全部重定向到 /dev/null 或日志文件。

与后续衔接

8.2 read/write 使用 fd；8.5 展示如何用 fd 实现 fopen/getc。

8.2

低级 I/O：read 和 write

本节讲什么

read/write 是最底层的通用字节 I/O 系统调用，绕过 stdio 缓冲。高频交易、驱动、网络栈用户态封装的首选路径。

要点

#include <unistd.h>

ssize_t read(int fd, void *buf, size_t n);
ssize_t write(int fd, const void *buf, size_t n);

read

  • 从 fd 最多读 n 字节到 buf
  • 返回值：实际读到的字节数；0 表示 EOF；-1 出错（查 errno）
  • 可能少于 n：信号中断、管道无数据、接近 EOF 等 —— 循环读直到满足或 EOF

write

  • 写 n 字节；返回值实际写入数；-1 出错
  • 大缓冲也需循环写直至写完

与 fread/fwrite 对比

read/write fread/fwrite
缓冲 无 stdio 用户缓冲 有
文本 \r\n 无自动转换 Windows 文本模式可能转换
控制 每次 syscall 由应用决定 块大小与 flush 策略

示例

char buf[4096];
ssize_t n;
while ((n = read(fd, buf, sizeof buf)) > 0)
    /* 处理 buf[0..n-1] */
if (n < 0)
    perror("read");

重难点

  • 短 read / 短 write 必须处理，不能假设一次读满
  • 与 第 7 章性能差异：stdio 减少 syscall 次数；低延迟场景用 read + 自管缓冲

常见陷阱

  1. 短 read / 短 write 未处理：read(fd, buf, 100) 不保证读满 100 字节——可能因信号中断、管道暂无数据、接近 EOF 等只读到部分。假设一次读满是经典 bug，必须循环读直到凑够或遇 EOF。write 同理，大缓冲可能分多次写。
  2. read 返回 -1 时不区分 errno：EINTR（被信号中断）是可恢复的，应重试；EAGAIN/EWOULDBLOCK（非阻塞 fd 暂无数据）也应重试或稍后；只有 EBADF/EFAULT 等才是致命错误。直接把 -1 当致命错误退出，会让程序在信号频繁时无故退出。
  3. 写管道/socket 时对端关闭 → SIGPIPE 杀进程：write 到一个对端已关闭的 pipe/socket，内核发 SIGPIPE，默认动作是终止进程。服务程序必须 signal(SIGPIPE, SIG_IGN) 忽略，或 send 加 MSG_NOSIGNAL，否则一个客户端断连就挂掉整个服务。

自测题

1. 选择：read(fd, buf, 100) 返回 0 表示什么？ - A. 出错 - B. 读到 0 字节但未结束 - C. 到达文件末尾（EOF） - D. 缓冲区满

答案

C。read 返回 0 唯一表示 EOF（文件末尾或对端关闭连接）。出错返回 -1（查 errno）。返回正数表示实际读到的字节数（可能小于请求的 100，即短 read）。这是 read 语义的核心，必须牢记。

2. 判断：write(fd, buf, 1000) 一定写入 1000 字节。

答案

错。write 可能只写入部分（短 write）——尤其是管道、socket、磁盘接近满时。必须循环写直到凑够或出错：

ssize_t written = 0;
while (written < 1000) {
    ssize_t n = write(fd, buf + written, 1000 - written);
    if (n < 0) { if (errno == EINTR) continue; perror("write"); break; }
    written += n;
}

假设一次写满是网络编程的经典 bug。

3. 踩坑：read 返回 -1，errno==EINTR，直接 perror 并退出，对吗？

答案

不对。EINTR 表示 read 被信号中断，不是错误——只需重试即可。正确做法：

ssize_t n;
do { n = read(fd, buf, 100); } while (n < 0 && errno == EINTR);
if (n < 0) { perror("read"); /* 真正的错误 */ }

信号频繁的程序（如注册了定时器）若不处理 EINTR，会无故退出。EAGAIN（非阻塞 fd 暂无数据）同理应重试或稍后再试。

4. 应用：写一个 robust_read(fd, buf, n) 循环读直到读满 n 字节或遇 EOF，处理 EINTR。

答案 
#include <unistd.h>
#include <errno.h>

ssize_t robust_read(int fd, void *buf, size_t n) {
    size_t got = 0;
    while (got < n) {
        ssize_t r = read(fd, (char*)buf + got, n - got);
        if (r < 0) {
            if (errno == EINTR) continue;      /* 信号中断，重试 */
            return -1;                         /* 真正的错误 */
        }
        if (r == 0) break;                     /* EOF */
        got += r;
    }
    return (ssize_t)got;                       /* 实际读到的字节数 */
}

这是网络/文件 IO 的基础工具函数。HFT 和服务端代码里几乎每个 read 调用都该这样包装。write 同理写一个 robust_write。

与后续衔接

socket、pipe、设备文件同一套 read/write；DPDK 绕过内核直达网卡，但 Linux 用户态 IO 仍从此起步。

8.3

open、creat、close 和 unlink

本节讲什么

打开/创建/关闭文件，以及 unlink 删除目录项。配合 link 理解硬链接与引用计数。

要点

open

#include <fcntl.h>
int open(const char *path, int flags, /* mode_t mode */);

常用 flags（可 | 组合）：

标志 含义
O_RDONLY 只读
O_WRONLY 只写
O_RDWR 读写
O_CREAT 不存在则创建（需 mode）
O_TRUNC 存在则截断为 0
O_APPEND 追加写
  • 成功返回 fd；失败 -1

creat

int creat(const char *path, mode_t mode);
  • 等价 open(path, O_WRONLY | O_CREAT | O_TRUNC, mode)

close

close(fd);
  • 释放 fd 编号；内核在引用计数为 0 时释放文件对象
  • 进程 exit 时关闭所有 fd（除 FD_CLOEXEC 等例外）

unlink

unlink(path);
  • 删除目录项（文件名），不立刻删磁盘数据
  • 硬链接计数减 1；为 0 且无进程打开该 inode 时才释放空间
  • 文件仍被某 fd 打开时，unlink 后该 fd 仍可读写

link（硬链接）

link(oldpath, newpath);
  • 两个目录项指向同一 inode
  • 不能跨文件系统；目录一般不可硬链接

考点

  • unlink vs 删除数据：计数与 fd 仍打开
  • O_CREAT 必须写八进制 mode（如 0644），还受 umask 影响

与后续衔接

设备节点 open("/dev/xxx")；HFT 日志 O_APPEND 追加；ELF/镜像 O_RDONLY。

常见陷阱

  1. O_CREAT 忘传 mode 参数：open("log.txt", O_WRONLY | O_CREAT) ——少了第三个参数 mode。open 的第三个参数是可变参数，不传时读到栈上的垃圾值，可能创建权限奇怪的文件（如 0777 或 0000）。正确：open("log.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644)。注意：只有 flags 含 O_CREAT（或 O_TMPFILE）时才需要 mode，且 mode 受 umask 影响：实际权限 = mode & ~umask。

  2. unlink 后以为磁盘空间立即释放：unlink("big.dat") 只删目录项（文件名），不删 inode 和数据块。如果仍有进程打开该文件（持有 fd），空间不释放——直到最后一个 fd 关闭。利用这个特性可以做"临时文件"：open + unlink，文件在 /tmp 不可见但 fd 仍可读写，进程退出自动回收。但也可能导致磁盘被"已删除但仍打开"的大文件撑满。

  3. open 的 O_TRUNC 意外截断已有文件：open("config.txt", O_WRONLY | O_TRUNC) ——如果 config.txt 已存在且有内容，O_TRUNC 立即清零文件。这是 shell > 重定向的底层原理，但如果误操作会丢失数据。安全做法：先 open(O_RDONLY) 检查文件是否存在，或用 O_CREAT | O_EXCL（文件已存在则失败）保护。日志文件追加用 O_APPEND 而非 O_TRUNC。

自测题

1. 选择：open("f.txt", O_WRONLY | O_CREAT, 0644) 在 umask=022 下创建的文件权限是？ - A. 0644 - B. 0622 - C. 0640 - D. 0777

答案

B。实际权限 = mode & ~umask = 0644 & ~022 = 0644 & 0755 = 0644 - 0020 = 0622。具体：0644 = rw-r--r--，umask 022 去掉同组 w 和其他 w → 0622 = rw--w--w-。注意 umask 影响所有 O_CREAT 创建的文件。临时改 umask 用 umask(0) 创建后再恢复，或创建后用 fchmod(fd, 0644) 精确设置。

2. 判断：unlink 删除文件后，如果有进程仍持有该文件的 fd，磁盘空间会立即释放。

答案

错。unlink 只删除目录项（文件名到 inode 的映射），减少 inode 的硬链接计数。当链接计数为 0 且没有进程打开该文件（无 fd 指向 inode）时，内核才释放数据块。如果有进程仍持有 fd，空间不释放——直到最后一个 fd 关闭。这个特性常用于临时文件：fd = open(...); unlink(path); ——文件在文件系统中不可见，但 fd 仍可读写，进程退出自动回收。

3. 踩坑：以下代码在多进程同时写同一日志文件时，日志行交错混乱，为什么？

int fd = open("app.log", O_WRONLY | O_CREAT, 0644);
write(fd, "START\n", 6);
write(fd, "END\n", 4);
答案

没有 O_APPEND 标志时，每个进程的 write 从各自的文件偏移写入——多个进程同时写会互相覆盖或交错。加 O_APPEND 后，每次 write 前内核原子地把偏移移到文件末尾，保证追加不冲突。但 O_APPEND 只保证每次 write 原子追加，不保证单次 write 不被信号拆断（短 write）。大块写入仍需循环写或用 pwrite。

4. 应用：写一个安全的临时文件创建函数——文件不存在则创建，已存在则失败（防止覆盖），权限 0600。

答案 
int create_temp_file(const char *path) {
    /* O_CREAT | O_EXCL：文件已存在则 open 失败（EEXIST） */
    int fd = open(path, O_WRONLY | O_CREAT | O_EXCL, 0600);
    if (fd < 0 && errno == EEXIST) {
        fprintf(stderr, "%s already exists\n", path);
        return -1;
    }
    if (fd < 0) { perror("open"); return -1; }
    return fd;
}

关键：O_EXCL + O_CREAT 组合确保只在文件不存在时创建——防止符号链接攻击和意外覆盖。mkstemp 函数内部就是用这个模式生成随机文件名。权限 0600（仅 owner 读写）防止其他用户读取临时文件中的敏感数据。

8.4

随机访问：lseek

本节讲什么

lseek 移动 fd 的读写偏移，对应第 7 章 fseek/ftell 的底层实现。随机读 ELF 头、tick 文件某偏移、大镜像分片加载。

要点

#include <unistd.h>
off_t lseek(int fd, off_t offset, int whence);
whence 含义
SEEK_SET 相对文件开头
SEEK_CUR 相对当前位置
SEEK_END 相对文件末尾
  • 成功返回新的绝对偏移；失败 -1
  • 普通文件支持随机 seek；pipe/socket 一般不可 seek

与 ftell/fseek

  • stdio 在 FILE 结构里维护偏移 + 缓冲；fflush 后 lseek(fileno(fp), ...) 才与内核一致
  • 大文件：lseek64 / off_t 64 位

示例

lseek(fd, 0, SEEK_END);
off_t size = lseek(fd, 0, SEEK_CUR);
lseek(fd, offsetof(struct Elf64_Ehdr, e_phoff), SEEK_SET);
read(fd, &phoff, sizeof phoff);

重难点

  • 文本 vs 二进制 与 seek 无关，但 stdio 缓冲可能导致 ftell 不准
  • 并发写同一文件偏移需应用层同步

与后续衔接

内存映射 mmap 是另一种「随机访问」；Miniload 解析 ELF program header 常 lseek + read。

常见陷阱

  1. lseek 超过文件末尾后 write 创建"空洞文件"：lseek(fd, 1000000, SEEK_SET); write(fd, "x", 1); ——文件变成 1000001 字节，但中间 0–999999 字节是空洞（sparse file），不占磁盘块，读出来是 \0。这在处理大文件时有用（快速创建大文件），但也可能意外消耗 inode 配额或让其他程序误以为文件很大。du 显示实际磁盘占用，ls 显示逻辑大小。

  2. pipe/socket 上调用 lseek 返回 ESPIPE：管道、套接字、FIFO 是流式的，不支持随机访问。lseek(fd, 0, SEEK_SET) 返回 -1，errno = ESPIPE。检测一个 fd 是否可 seek：if (lseek(fd, 0, SEEK_CUR) < 0) { /* 不可 seek */ }——不移动位置但测试是否可 seek。

  3. stdio 缓冲导致 ftell 与实际内核偏移不一致：FILE* 内部维护自己的偏移和缓冲。fseek 改的是 stdio 的偏移，但底层内核的 fd 偏移可能不同（有未 flush 的读/写缓冲）。跨 stdio 和 fd 操作时（如 fileno(fp) + lseek），必须先 fflush(fp) 同步。用 fseek/ftell 管理同一个 FILE*，不要混用 fd 层的 lseek。

自测题

1. 选择：lseek(fd, 0, SEEK_END) 返回值的含义是？ - A. 0（成功移动到末尾） - B. 文件大小（从开头到末尾的字节数） - C. -1（不能 seek 到末尾） - D. 当前位置（不变）

答案

B。lseek 成功时返回新的文件偏移量（从文件开头算起的字节数）。SEEK_END + offset=0 → 移到文件末尾，返回值 = 文件大小。这是获取文件大小的经典手法：off_t size = lseek(fd, 0, SEEK_END);。注意：之后读写位置在末尾，如果要在开头读需 lseek(fd, 0, SEEK_SET) 回到开头。更可移植的获取大小方式是 fstat + st_size。

2. 判断：可以对管道（pipe）的 fd 调用 lseek 进行随机访问。

答案

错。管道是流式的 FIFO，不支持随机定位——数据只能顺序读。lseek 在管道 fd 上返回 -1，errno = ESPIPE。同理 socket、FIFO 也不可 seek。只有普通文件、块设备（磁盘）支持 lseek。检测方法：lseek(fd, 0, SEEK_CUR) 返回 -1 则不可 seek。

3. 踩坑：以下代码想获取文件大小，但返回值有时是负数，为什么？

long size = ftell(fp);
答案

ftell 返回 long，在 32 位系统上 long 是 32 位，最大约 2GB——大于 2GB 的文件 ftell 溢出返回负数。修复：用 64 位版本。POSIX 用 ftello（返回 off_t，大文件支持时为 64 位），或直接用 fseeko(fp, 0, SEEK_END); off_t size = ftello(fp);。底层 fd 方法更可靠：struct stat st; fstat(fd, &st); off_t size = st.st_size;。编译时加 -D_FILE_OFFSET_BITS=64 让 off_t 自动为 64 位。

4. 应用：用 lseek + read 解析 ELF 文件的 program header offset——从 ELF header 的 e_phoff 字段（偏移 32 字节，8 字节）读取值。

答案 
#include <unistd.h>
#include <stdint.h>

int fd = open("program", O_RDONLY);
if (fd < 0) { perror("open"); return -1; }

/* e_phoff 在 ELF64 header 的偏移 32，类型 Elf64_Off (uint64_t) */
uint64_t e_phoff;
lseek(fd, 32, SEEK_SET);
read(fd, &e_phoff, sizeof(e_phoff));

printf("program header offset: %lu\n", e_phoff);

/* 跳到 program header 表读取 */
lseek(fd, e_phoff, SEEK_SET);
/* read(fd, phdr, sizeof(Elf64_Phdr) * e_phnum); */
close(fd);

关键：lseek 定位到 ELF header 中 e_phoff 的位置，read 读 8 字节得到 program header 表的文件偏移，再 lseek 跳过去读。这是 ELF 加载器/链接器的基本操作。注意字节序（跨架构 ELF 需 ntoh 转换）。

8.5

实例：fopen 和 getc 函数的实现

本节讲什么

K&R 用 fd + read + 用户缓冲 手写简化版 fopen/getc，揭示第 7 章 stdio 的本质：在系统调用之上加缓冲与状态。

要点

典型 FILE 结构（概念）

struct io_buf {
    int fd;           /* 底层文件描述符 */
    char *buf;        /* 缓冲 */
    char *bufp;       /* 当前读指针 */
    int n;            /* 缓冲中剩余字符数 */
    /* 错误/EOF 标志等 */
};

getc 逻辑

  1. 若缓冲有字符 → 直接返回
  2. 否则 read(fd, buf, BUFSIZ) refill
  3. read 返回 0 → EOF；-1 → 错误

fopen 逻辑

  1. open(path, flags, mode) 得 fd
  2. 分配 FILE 结构与缓冲
  3. 返回指针供 getc/putc 使用

stdio vs 原生 read（重难点）

stdio 带缓冲 read 无 stdio 缓冲
减少 syscall，吞吐高 单次延迟可控
交互式可能行缓冲 适合 HFT、自管 ring
printf 需 flush 直接写内核

与后续衔接

理解后可读 glibc stdio 源码、实现简易日志库；fileno(fp) 在 fd 与 FILE* 间桥接。

FILE 结构的本质

K&R 展示的简化 FILE 结构揭示了 stdio 的核心思想——在 fd 之上加用户态缓冲：

typedef struct {
    int fd;           /* 底层文件描述符 */
    unsigned char *buf;  /* 缓冲区 */
    unsigned char *bufp; /* 当前读写位置 */
    int n;            /* 缓冲中剩余字节 */
    int flags;        /* EOF / 错误 / 读写模式 */
} FILE;

getc 的完整逻辑：

getc(fp):
  if (fp->n > 0)              ← 缓冲区还有数据？
      return *fp->bufp++;      ← 直接返回一个字符，不 syscall
  else                         ← 缓冲区空了
      n = read(fp->fd, fp->buf, BUFSIZ)  ← refill：一次 syscall 读一批
      if (n == 0) { fp->flags |= EOF; return EOF; }
      if (n < 0)  { fp->flags |= ERR;   return EOF; }
      fp->n = n; fp->bufp = fp->buf;
      return *fp->bufp++;

缓冲的意义：读一个字符如果不缓冲，每次都要 syscall（用户态→内核态切换约 1-2μs）。缓冲后 BUFSIZ（通常 4096 或 8192）个字符只需一次 syscall，平均每字符开销降到 ~0.25ns。这是 stdio 比裸 read 快的原因——以空间换时间。

常见陷阱

  1. 混用 stdio 和 fd 操作导致缓冲不一致：fgetc(fp) 读了一些数据到 stdio 缓冲，但内核 fd 的偏移已经前进了一整块（BUFSIZ 字节）。此时用 lseek(fileno(fp), ...) 改 fd 偏移，stdio 缓冲中的数据就失效了——下次 fgetc 读到的是旧缓冲内容，不是 lseek 后的新位置。混用前必须 fflush(fp)（写）或 fseek(fp, 0, SEEK_CUR)（读，丢弃缓冲）。

  2. getc 是宏还是函数：K&R 的 getc 实现为宏（#define getc(fp) ...），避免函数调用开销。glibc 的 getc 和 fgetc 的区别就是宏 vs 函数——getc 可能展开为宏（有副作用风险），fgetc 一定是函数。表达式 c = getc(fp) 中 fp 如果有副作用（如 getc(fp++)），宏展开可能多次求值。标准要求 getc 可以是宏，fgetc 必须是真正的函数。

  3. putc 的写缓冲未 flush 就 crash：fputc('x', fp) 只写到 stdio 缓冲，不一定立刻 write 到 fd。如果程序在此期间崩溃（SIGSEGV、_exit），缓冲区数据丢失。exit 会 flush 但 _exit 不会。调试时在关键点 fflush(fp) 或用 setvbuf(fp, NULL, _IONBF, 0) 关闭缓冲。日志文件用 setvbuf(fp, NULL, _IOLBF, 0) 设行缓冲，每行自动 flush。

自测题

1. 选择：getc/fgetc 读取一个字符时，什么时候会触发 read 系统调用？ - A. 每次调用 getc 都触发一次 read - B. 只在 stdio 缓冲区为空时触发一次 read（读取 BUFSIZ 字节） - C. 只在第一次调用时触发 read - D. 从不触发 read

答案

B。getc 先检查 stdio 内部缓冲区是否有剩余字符，有则直接返回（不 syscall）。缓冲区空时才调用 read 一次读入 BUFSIZ 字节（通常 4KB/8KB），之后后续 getc 从缓冲区取字符。这意味着读 N 个字符只需约 N/BUFSIZ 次 syscall，而非 N 次。这是 stdio 比裸 read 高效的核心原因。HFT 场景如果需要精确控制每次 syscall，则用裸 read + 自管缓冲。

2. 判断：getc 和 fgetc 在 C 标准中完全等价。

答案

对（语义上）。两者都从指定流读一个字符，返回值和错误处理完全相同。区别在实现：getc 可以是宏（标准允许），fgetc 必须是真正的函数。宏版本避免了函数调用开销（适合高频字符读取），但参数有副作用时会多次展开。getc(fp++) 如果 getc 是宏，fp 可能自增多次。安全做法：参数无副作用时用 getc（快），有副作用时用 fgetc。

3. 踩坑：以下代码先用 read 读了一些数据，再 fgetc(fp) 读，结果读到的字符不对，为什么？

int fd = open("data.txt", O_RDONLY);
read(fd, buf, 10);         /* 用 fd 直接读了 10 字节 */
FILE *fp = fdopen(fd, "r"); /* 包装成 FILE* */
char c = fgetc(fp);         /* 读到的不是第 11 个字符 */
答案

fdopen 把已打开的 fd 包装成 FILE*，但 fd 的当前偏移已经被 read 前进了 10 字节。fgetc 触发 read 从当前位置（第 11 字节）读一大块（BUFSIZ）到缓冲区，然后返回缓冲区第一个字符——这确实是第 11 个字符。但如果之前 read 读的不是 10 而是 BUFSIZ 的倍数，或者 fdopen 时 fd 偏移不在预期位置，结果就会混乱。混用 fd 和 FILE 的关键是理解：两者共享同一个 fd 偏移，但 FILE 有额外的用户态缓冲。先 lseek 确认偏移，或不要混用。

4. 应用：仿照 K&R 思路，写一个简化版 my_getc，用一个 4096 字节的缓冲区包装 read。

答案 
#include <unistd.h>
#include <stdlib.h>

typedef struct {
    int fd;
    unsigned char buf[4096];
    int pos;    /* 当前读取位置 */
    int len;    /* 缓冲中有效字节数 */
} MyFile;

int my_getc(MyFile *f) {
    if (f->pos >= f->len) {      /* 缓冲区空了 */
        f->len = read(f->fd, f->buf, sizeof f->buf);
        if (f->len <= 0) return -1;  /* EOF 或出错 */
        f->pos = 0;
    }
    return f->buf[f->pos++];
}

MyFile *my_fopen(const char *path, int flags) {
    int fd = open(path, flags);
    if (fd < 0) return NULL;
    MyFile *f = calloc(1, sizeof(MyFile));
    f->fd = fd;
    f->pos = f->len = 0;
    return f;
}

这就是 stdio 的核心机制——缓冲+refill。glibc 的 __GI__IO_file_underflow 做的是同样的事，只是更复杂（支持不同缓冲模式、错误处理、编码转换）。

遍历目录、打印文件名，综合运用 open/read/stat 与第 6 章 struct。并覆盖 stat 元数据、目录与权限 等 UNIX 文件模型核心。

stat / fstat

struct stat 常见字段：

  • K&R fstat + 目录项结构解析 ls 简化版

示例逻辑（ls 思想）

对每个目录项：
  stat → 打印 mode、大小、名字
  目录则递归或标记

  • 硬链接 同 inode 多名字（8.3 link）
  • 设备文件 S_ISCHR / S_ISBLK —— 嵌入式访问驱动

与后续衔接

自制 OS 用户态 ls、pwd；Linux /proc、 /sys 遍历；UEFI 无 POSIX 目录 API，但「元数据 + 枚举」思维相同。

常见陷阱

  1. readdir 返回的指针在下次调用时被覆盖：struct dirent *d; d = readdir(dir); printf("%s", d->d_name); d = readdir(dir); printf("%s", d->d_name); ——第二次 readdir 可能覆盖了第一次返回的 dirent 结构（静态/内部缓冲）。如果需要保存文件名，必须 strdup(d->d_name) 复制。glibc 的 readdir 用线程局部存储缓解了这个问题，但可移植代码仍应假设返回值在下一次调用后失效。

  2. 遍历目录时修改目录内容：在 readdir 循环中创建/删除文件，行为未定义——readdir 的内部状态可能被破坏，可能跳过文件、重复文件或崩溃。安全做法：先把文件名列表全部读入数组（strdup 保存），关闭目录后再操作文件。

  3. stat vs lstat 搞混——符号链接处理不同：stat(path, &st) 跟随符号链接获取目标文件的元数据；lstat(path, &st) 不跟随，获取符号链接本身的元数据。ls -l 用 lstat 显示符号链接信息，ls -L 用 stat 跟随。目录遍历如果用 stat 遇到指向父目录的循环符号链接，会无限递归——必须用 lstat 检测 S_ISLNK。

自测题

1. 选择：stat("link.txt", &st) 中 link.txt 是一个指向 real.txt 的符号链接，st.st_size 返回的是谁的文件大小？ - A. 符号链接文件本身的大小 - B. real.txt 的大小 - C. 0 - D. 链接路径字符串的长度

答案

B。stat 跟随符号链接获取目标文件的元数据，所以返回 real.txt 的大小。如果要获取符号链接本身的信息（如链接路径长度），用 lstat——它不跟随链接。lstat 返回的 st_mode 中 S_ISLNK 为真，stat 返回的不会。目录遍历防循环符号链接必须用 lstat 检查 S_ISLNK。

2. 判断：readdir 保证按文件名字母顺序返回目录项。

答案

错。readdir 返回顺序未定义——取决于文件系统内部结构（ext4 按哈希，FAT 按创建顺序，tmpfs 按插入顺序）。如果需要排序，必须先把所有文件名读入数组再 qsort。ls 默认排序就是在用户态做的。scandir 函数封装了"读取+排序"流程，但底层仍是 readdir。

3. 踩坑：以下递归遍历目录的代码在遇到符号链接时无限循环，为什么？

void walk(const char *path) {
    DIR *d = opendir(path);
    while ((de = readdir(d))) {
        stat(de->d_name, &st);
        if (S_ISDIR(st.st_mode))
            walk(de->d_name);
    }
    closedir(d);
}
答案

三个问题：1) stat 跟随符号链接——如果目录中有一个符号链接指向上级目录，stat 返回目录类型，递归进入 → 无限循环。修复：用 lstat 并检查 S_ISLNK 跳过符号链接。2) 没有跳过 . 和 ..——readdir 返回 .（当前目录）和 ..（上级目录），递归进入 .. 会无限循环。修复：if (strcmp(de->d_name, ".") == 0 || strcmp(de->d_name, "..") == 0) continue;。3) de->d_name 只是文件名，不是完整路径——递归时需拼接 path + "/" + de->d_name。

4. 应用：用 opendir/readdir/stat 写一个 list_dir 函数，打印目录下每个文件的名字和大小（字节），按大小降序排列。

答案 
#include <dirent.h>
#include <sys/stat.h>
#include <string.h>
#include <stdlib.h>
#include <stdio.h>

typedef struct { char name[256]; off_t size; } Entry;

int cmp_size(const void *a, const void *b) {
    return ((Entry*)b)->size - ((Entry*)a)->size;  /* 降序 */
}

void list_dir(const char *path) {
    DIR *d = opendir(path);
    if (!d) { perror("opendir"); return; }

    Entry entries[1024];
    int n = 0;
    struct dirent *de;
    while ((de = readdir(d)) && n < 1024) {
        if (de->d_name[0] == '.') continue;  /* 跳过隐藏文件 */
        char full[512];
        snprintf(full, sizeof full, "%s/%s", path, de->d_name);
        struct stat st;
        if (lstat(full, &st) == 0) {
            strncpy(entries[n].name, de->d_name, 255);
            entries[n].name[255] = '\0';
            entries[n].size = st.st_size;
            n++;
        }
    }
    closedir(d);

    qsort(entries, n, sizeof(Entry), cmp_size);
    for (int i = 0; i < n; i++)
        printf("%10ld  %s\n", entries[i].size, entries[i].name);
}

关键：路径拼接（path + "/" + name）、lstat 防符号链接、qsort 排序、opendir 失败检查。这是 ls -lS 的核心逻辑。

实例：存储分配程序

brk / sbrk

  • 移动 program break（堆顶）

底层场景

环境 堆
Linux 用户态 brk + mmap
内核 kmalloc /slab
UEFI AllocatePool
裸机 / OS 实验 自管物理页 + 空闲链表

与后续衔接

理解「堆 = 虚拟地址空间一段 + 系统扩展 break」为读 mmap、内存泄漏、ASLR 打基础；与 fork 的 COW 共享页（章 README）同一内存世界观。

K&R malloc 的设计

K&R 用空闲链表（free list）实现简化版 malloc，核心数据结构：

typedef union header {
    struct {
        size_t size;    /* 本块大小（含 header，单位：header 个数） */
        union header *next;  /* 空闲链表中的下一块 */
    } s;
    long _align;        /* 强制对齐：union 大小 = max(long, struct) */
} Header;

static Header *freep = NULL;  /* 空闲链表头 */

malloc 逻辑： 1. 遍历空闲链表找大小足够的块 2. 找到 → 可能分割（大块切成需要的 + 剩余空闲块） 3. 没找到 → 调用 sbrk 向内核申请更多内存，加入空闲链表

free 逻辑： 1. 找到被释放块在空闲链表中的位置（按地址排序） 2. 如果前后相邻空闲块 → 合并（减少碎片） 3. 插入空闲链表

常见陷阱

  1. sbrk 无法收缩已释放的内存：K&R 的 free 只把块标记为空闲并加入链表，不调用 sbrk(-n) 归还内存给内核。大量分配后全部 free，进程的堆顶（program break）仍不下降——top 显示内存占用不减少。现代 glibc malloc 对大块用 mmap 分配（free 后 munmap 归还），小块仍用 brk 但空闲到一定程度会 trim。HFT 进程常预分配大块池避免动态 sbrk。

  2. free 后继续使用（use-after-free）：free(p); p->next = NULL; ——free 把 p 加入空闲链表，后续 malloc 可能把这个块分给别人。通过 freed 指针读写到的是别人的数据。更危险：free 后的块被合并，指针指向的 header 已变。防御：free 后 p = NULL;，后续解引用 NULL 立即段错误而非静默腐败。ASan（AddressSanitizer）可检测 use-after-free。

  3. double free 破坏空闲链表：free(p); free(p); ——第一次 free 把 p 加入空闲链表，第二次 free 再次加入 → 链表中出现同一块两次。下次 malloc 可能把这个块分给两个调用者 → 数据腐败。现代 malloc（glibc ptmalloc2）有 double-free 检查，但不是所有实现都有。防御：free 后置 NULL，或用调试 malloc（dmalloc/ASan）。

自测题

1. 选择：K&R 的 free 实现中，为什么要在空闲链表中按地址顺序插入被释放的块？ - A. 为了快速查找 - B. 为了合并物理相邻的空闲块 - C. 为了按大小排序 - D. 没有特殊原因

答案

B。按地址排序插入后，可以检查前后相邻块是否也空闲——如果是就合并成一个更大的空闲块。这叫合并（coalescing），是减少外部碎片的关键。如果不按地址排序，无法知道物理相邻的块是否空闲，碎片会越来越严重——大量小碎片但无法满足大块请求。现代分配器（ptmalloc2/jemalloc）也做合并，只是用更高效的数据结构（bins/trees）。

2. 判断：调用 free(p) 后进程的堆内存（program break）会立即下降。

答案

错。K&R 的 free 只把块标记为空闲并加入空闲链表，不调用 sbrk(-n) 收缩堆顶。堆顶只在空闲块位于堆顶且足够大时才可能被 trim。现代 glibc 对小块用 brk（不收缩或延迟收缩），对大块用 mmap（free 后 munmap 立即归还）。所以 malloc(100MB); free(p); 后 top 可能仍显示 100MB 占用。HFT 进程通常预分配内存池，避免运行时 sbrk/mmap 的延迟抖动。

3. 踩坑：以下代码在循环运行一段时间后崩溃，但不是每次都复现，为什么？

char *p = malloc(100);
strcpy(p, data);
free(p);
printf("%s\n", p);   /* 打印已释放的内存 */
答案

这是 use-after-free（UAF）。free(p) 后 p 指向的块被加入空闲链表，后续 malloc 可能把它分给别人。printf 读 p 时可能读到：1) 旧数据（块还没被重分配，看似正常但不可靠）；2) 空闲链表指针（被 free 改写了 header）；3) 别人的新数据（块被重分配）。结果不确定所以崩溃不一定复现。防御：free 后 p = NULL;，解引用 NULL 立即段错误。编译时加 -fsanitize=address 可检测 UAF。

4. 应用：写一个简单的内存池 pool_alloc——预分配大块内存，按固定大小切片分配，不支持 free（整体释放），说明适用场景。

答案 
typedef struct {
    char *base;     /* 大块基址 */
    size_t offset;  /* 当前分配偏移 */
    size_t total;   /* 总大小 */
} Pool;

Pool *pool_create(size_t total) {
    Pool *p = malloc(sizeof(Pool));
    p->base = malloc(total);
    p->offset = 0;
    p->total = total;
    return p;
}

void *pool_alloc(Pool *p, size_t size) {
    /* 对齐到 8 字节 */
    size = (size + 7) & ~((size_t)7);
    if (p->offset + size > p->total) return NULL;
    void *ptr = p->base + p->offset;
    p->offset += size;
    return ptr;
}

void pool_destroy(Pool *p) {
    free(p->base);
    free(p);
}

适用场景：HFT 启动时预分配所有需要的内存，运行时只从池中切片（O(1)，无锁，无碎片），不逐个 free——整体销毁。游戏引擎、编译器 AST 节点分配也常用这个模式。优点：无 malloc/free 开销、无碎片、缓存友好（连续内存）。

Q1文件描述符
// fd 0/1/2 分别是什么？
// 以下程序输出什么？

int fd = open("test.txt", O_WRONLY | O_CREAT, 0644);
printf("fd = %d\n", fd);
write(fd, "hello", 5);
close(fd);

int fd2 = open("test2.txt", O_WRONLY | O_CREAT, 0644);
printf("fd2 = %d\n", fd2);

fd 和 fd2 各是多少？为什么不是 0 或 1？

答案与复习指引

答案： fd = 3，fd2 = 3（fd 回收复用）

解析： 进程启动时自动打开三个 fd： - 0 = stdin（标准输入） - 1 = stdout（标准输出） - 2 = stderr（标准错误）

open 返回最小可用 fd → 第一个新 fd 是 3。close(fd) 后 fd 3 被回收，下次 open 复用 3。

fd 生命周期： fork 后子进程继承父的 fd 表（COW）→ 管道和重定向的基础。

Q2read/write 短读写
char buf[100];
int n;
int fd = open("large.bin", O_RDONLY);

// 这样写有什么问题？
n = read(fd, buf, 100);
// 假设 buf 只装了一部分，n < 100 正常吗？

printf("read %d bytes\n", n);

read 返回 100 以下的值是错误吗？什么情况下 read 返回少于请求的字节？

答案与复习指引

答案： 不是错误。read 返回实际读到的字节数，可能少于请求量。

短读写原因： 1. 到达文件末尾（EOF）→ 返回剩余字节数 2. 读终端/管道 → 一行结束就返回 3. 被信号中断（EINTR）→ 返回已读量 4. 网络套接字 → 数据分片到达

正确写法（短读写循环）：

ssize_t total = 0;
while (total < want) {
    ssize_t n = read(fd, buf + total, want - total);
    if (n < 0) { if (errno == EINTR) continue; break; }
    if (n == 0) break; // EOF
    total += n;
}

教训： 永远不能假设 read(fd, buf, 100) 一次返回 100。

Q3open 标志
// (1)
int fd1 = open("file.txt", O_WRONLY);
// (2)
int fd2 = open("file.txt", O_WRONLY | O_CREAT, 0644);
// (3)
int fd3 = open("file.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
// (4)
int fd4 = open("file.txt", O_WRONLY | O_APPEND);

四种方式各有什么区别？哪种最常用？

答案与复习指引
写法 文件不存在时 文件存在时
(1) O_WRONLY 失败 打开，从头覆写
(2) +O_CREAT 创建 打开，从头覆写（不清空！）
(3) +O_TRUNC 创建 清空后打开
(4) O_APPEND 失败 追加到末尾

最常用： (3) 新建/覆盖文件用 O_WRONLY | O_CREAT | O_TRUNC，日志追加用 O_WRONLY | O_APPEND。

HFT 场景： 日志文件用 O_APPEND + O_WRONLY，多进程追加时 O_APPEND 保证原子性（不会交错写入）。

第三参数 0644 = 文件权限（rw-r--r--），仅在 O_CREAT 时生效。被 umask 修正后实际为 0644 & ~umask。

Q4lseek 随机访问
int fd = open("data.bin", O_RDONLY);

lseek(fd, 100, SEEK_SET);    // (1) 从头偏移 100
lseek(fd, 50, SEEK_CUR);     // (2) 从当前再偏 50
lseek(fd, -10, SEEK_END);    // (3) 从末尾回退 10
off_t pos = lseek(fd, 0, SEEK_CUR);  // (4) 查当前位置

四行各做什么？(4) 返回什么？lseek 能用于管道吗？

答案与复习指引

答案： 1. SEEK_SET — 从文件起始偏移 100 → 位置 = 100 2. SEEK_CUR — 从当前位置偏移 50 → 位置 = 150 3. SEEK_END — 从文件末尾回退 10 → 位置 = 文件大小 - 10 4. SEEK_CUR 偏移 0 → 返回当前偏移量（150... 等，是 文件大小-10）

lseek 不能用于管道/套接字/FIFO： 这些流没有"位置"概念，lseek 返回 -1 + errno = ESPIPE。

HFT 用途： 大型 tick 数据库按时间戳定位、固定大小记录的随机读取。

注意： lseek 只移动文件偏移量，不做实际 I/O。

Q5stdio 缓冲 vs 原生 I/O
// 方式 A: stdio
FILE *fp = fopen("log.txt", "w");
for (int i = 0; i < 10000; i++)
    fprintf(fp, "line %d\n", i);
fclose(fp);

// 方式 B: 原生 I/O
int fd = open("log.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
for (int i = 0; i < 10000; i++) {
    char buf[32];
    int len = snprintf(buf, sizeof(buf), "line %d\n", i);
    write(fd, buf, len);  // 每次 syscall
}
close(fd);

哪种方式更快？为什么？HFT 里选哪种？

答案与复习指引

答案： 方式 A（stdio）快得多。

解析： - fprintf → 写入 stdio 内部缓冲区（用户态），缓冲区满或 fclose 时才调 write syscall - 每次 write → 独立 syscall（用户态→内核态切换），10000 次 syscall 非常慢

性能差距： 在 10000 次小写入的场景下，stdio 可以快 10-100 倍。

HFT 选择： - 需要缓冲批量写 → stdio（fprintf + 偶尔 fflush） - 需要绝对无延迟 → 原生 write（自己管理缓冲，单次 syscall 批量写） - 不能接受任何缓冲延迟 → write 直接写 fd

教训： syscall 比函数调用贵 3-4 个数量级。能用缓冲就用缓冲。
