4.1

函数的基本知识

本节讲什么

C 程序由函数构成：main 是入口，其余函数把逻辑拆成可复用模块。掌握 返回类型写法、完整语法、值传递、声明 vs 定义，是多文件工程与内核代码的基础。

前置：1.7 函数、2.4 声明。

要点

1. 返回类型写在函数名 左边

C 里函数的 返回值类型 写在 函数名左侧：

int add(int a, int b)
/*↑ 返回类型   ↑ 函数名   ↑ 形参列表 */
{
    return a + b;
}
部分 位置 示例
返回类型 函数名 之前 int、void、float *、struct node
函数名 形参列表 之前 add、main、read_pkt
形参列表 () 内 (int a, int b)、(void)
函数体 { ... } 语句与 return

声明（原型） 与 定义 都遵循同一顺序 —— 返回类型始终在函数名左边：

int add(int a, int b);              /* 声明：末尾分号，无函数体 */

int add(int a, int b)               /* 定义：带函数体 */
{
    return a + b;
}

2. C89 及以前：省略返回类型 → 隐式 int；C99 起必须显式写出

标准 没写返回类型 没写 return 的 int 函数
C89 及以前 默认按 int 处理 仍视为返回 int，但值 未定义（寄存器/栈残留，相当于「随机」）
C99 及以后 编译错误 —— 必须显式写返回类型 非 void 函数应有 return；落到 } 不 return → 返回值 未定义（UB） 
/* C89 时代允许 —— 编译器当作 int f(void) */
f()
{
    printf("no return\n");
}   /* 调用方仍可能当 int 用返回值，但值是垃圾 —— 严禁 */

/* C99+：下面直接不过编译 */
/* f() { ... }   error: type defaults to 'int' in C99 */

现代规范：始终显式写出返回类型，不要依赖隐式 int：

int add(int a, int b);    /* 对 */
void log_msg(const char *s);
/* f() { ... }            C99 起：不写返回类型 → 报错 */

main 省略返回类型时老编译器默认 int main() —— 见 1.1 入门；新代码一律 int main(void) 或 int main(int argc, char *argv[])。

3. void 必须自己写在函数名左边 —— 才表示无返回值

C 不会 因为你不写 return 就自动变成「无返回值函数」。要在函数名左边 明确写 void：

void greet(const char *name)   /* void 在左边 → 无返回值 */
{
    printf("Hello, %s\n", name);
    /* return; 可写可不写；不能 return 1; */
}

int add(int a, int b)          /* int 在左边 → 有返回值 */
{
    return a + b;
}
左边写的 含义 调用方能拿返回值吗
int / float / 指针等 有返回值 能
void 无返回值 不能（写了 x = f(); 且 f 为 void → 编译错误）

无返回值 ≠ 省略返回类型。省略在 C89 里是隐式 int，在 C99 里是 错误。

3.1 别混：void（无返回值） vs void *（通用指针）

void 出现在函数名左边和出现在指针里 完全是两回事：

写法 角色 含义
void 单独作返回类型 函数左边 无返回值 —— void f(void);
void * / void *p 指针类型 通用指针 —— 可指向 任意类型 的对象地址 
void log_msg(const char *s);   /* void：函数不返回值 */

void *malloc(size_t n);        /* void *：返回「指向未知类型的指针」 */

void * 的规则（K&R 后几章、标准库 malloc/read 常见，详见 5.1 指针、2.4 声明围绕标识符）：

声明读法：*p 是 void → p 是 void 指针 —— 类型修饰 围绕标识符 p，与 int *a[10] 同一套规则。

能做什么 不能做什么
存放 任意 对象指针（int*、char*、struct* 赋给 void* 常 无需强转） 不能直接解引用 *p —— 编译器不知道读几个字节
与其他对象指针 比较（同地址）、相等判断 不能 p[i]、(*p).x 等，除非先转型
printf("%p", p) 打印地址 指针算术 p++ 在 void* 上 GCC 扩展/不推荐；先转成具体类型

使用前必须强转成具体类型指针：

void *raw = malloc(10 * sizeof(int));
int *arr = (int *)raw;       /* 强转回 int* */
arr[0] = 42;                 /* 现在才能解引用 */

char buf[128];
ssize_t n = read(fd, buf, sizeof buf);   /* read 要 void* 缓冲 —— 任意字节块 */
/* char* 可隐式传给 void* 形参 */

记忆：void = 「没有」；void * = 「有地址，但 暂不声明 指向哪种类型」—— 先存着，用时再 cast。

4. 完整形式与 return

返回类型 函数名(形参列表)
{
    语句;
    return 表达式;   /* 非 void：应保证有返回值路径 */
}
返回类型 return 用法
int 等整型/浮点/指针 return 表达式; — 表达式 转换为 声明的返回类型
void return; 或直接落到 } —— 无返回值
  • return 表达式; 结束函数并带回值
  • 非 void 函数执行到 } 却 没有 return → 返回值 未定义（C99 起常报 -Wreturn-type）；C89 隐式 int 函数同理，只是类型被默认成 int
  • return 表达式会转换为函数返回类型 —— 见 2.7 窄→宽/宽→窄、4.2：
  • 小转大（float→double）一般 无精度损失
  • 大转小（double→float、long→int）→ 截断低位/溢出
int max(int a, int b)
{
    return a > b ? a : b;
}

void greet(const char *name)
{
    printf("Hello, %s\n", name);
    return;          /* 可写可不写 */
}

5. 值传递（call by value）

C 默认 按值传递：形参是实参的 副本，函数内改形参 不影响 调用者的变量。

void swap_wrong(int x, int y)
{
    int t = x;
    x = y;
    y = t;           /* 只交换了副本 */
}

要在函数内修改调用者数据 → 传 指针（第 5 章）或 用返回值 带回结果。

调用时，实参副本和形参一起落在 栈帧 里（4.3.1 §6）；函数本身的机器指令 在 代码区，不随每次调用创建销毁。

6. 函数定义 vs 函数原型（声明）

口语记忆：定义 = 造零件，声明 = 贴标签。

比喻 对应 做什么
造零件 函数定义 把 所有细节 写出来，包括 具体怎么干活（函数体）
贴标签 函数原型（声明） 提前告诉编译器：这个零件 叫什么、能接收什么、返回什么
函数原型（声明）—— 贴标签 函数定义 —— 造零件
是什么 只列出函数的 模样 完整实现，写明 具体做什么
包含 返回类型 + 函数名 + 参数列表 同上 + { 函数体 }
函数体 不写 必须写 具体语句
末尾 分号 ; 花括号 { }
作用 让编译器 提前有个数，调用时做检查 生成机器码，实现逻辑
放哪 调用之前，或 头文件 .h 通常 .c 里
次数 可 多次 声明 全程序 一次 定义 
/* 贴标签 —— 原型，无函数体 */
int add(int a, int b);

int main(void)
{
    int m = add(3, 5);   /* 调用：编译器已见过标签 */
    return 0;
}

/* 造零件 —— 定义，写出怎么干活 */
int add(int a, int b)
{
    return a + b;
}

为何必须先贴标签？

C 编译器 从上到下 编译。若 调用写在定义前面，编译器还没见过这个函数的 标签（原型或完整定义），就不知道参数怎么传、返回值怎么处理 → 报错（C99 起）。

int main(void)
{
    foo(1, 2);           /* 错：此时编译器还不认识 foo */
}

void foo(int a, int b) { ... }

解决办法：在调用 之前 写原型，或把 定义 挪到调用之前（定义本身自带标签信息）。

头文件（4.5）：把一堆「标签」集中放在 .h，各 .c #include —— 多文件共享；造零件 留在对应 .c。

返回 float / double / 指针 等非整型时，标签上的返回类型 必须写对 —— 漏写原型老 C 会默认 int，浮点结果被截断错乱，见 4.2 §1。

易混点

# 要点
1 返回类型在函数名 左边：int add(...)、void f(...)
2 C89：省略返回类型 → 隐式 int，没 return 也有「int 返回值」但 值未定义
3 C99+：省略返回类型 → 编译报错；必须显式写
4 无返回值 须自己写 void 在左边；不是不写 return 就行
5 void（返回类型）≠ void *（通用指针）；后者解引用前须强转
6 非 void 函数应有 return 表达式；缺 return → 垃圾值
7 定义 = 造零件（有体）；声明 = 贴标签（无体，调用前让编译器有个数）
8 形参是 副本 —— 值传递

HFT / 内核提示

  • 头文件 .h：返回类型 + 函数名 + 参数列表 组成 API 契约；改返回类型 = 破坏 ABI，须版本化
  • 热路径：static inline int clamp(int x, int lo, int hi) —— 返回类型显式，便于内联
  • 禁用隐式 int：开 -Wimplicit-int / -Werror=implicit-int（GCC）在 CI 里拦遗留代码

4.2

返回非整型值的函数

本节讲什么

函数不必只返回 int：可返回 float、double、char、指针、结构体等。重点是 return 表达式 → 函数返回类型 的 隐式转换（与 2.7 类型转换 一致），以及 void 表示无返回值。

前置：4.1 函数基本知识、2.7 隐式转换。

要点

1. 返回 float 等：原型和定义 都要 写对返回类型

返回 非整型（float、double、指针等）时，贴标签（原型） 和 造零件（定义） 的返回类型 必须一致、必须显式写出 —— 不能省略，不能默认 int。

/* 原型（贴标签）—— 返回 float */
float calculate(float x);

/* 定义（造零件）—— 返回类型同样是 float */
float calculate(float x)
{
    return x * 1.5f;
}
位置 必须写什么
原型 float calculate(float x);
定义 float calculate(float x) { return x * 1.5f; }
调用 float y = calculate(2.0f); —— 编译器按 float 返回值 处理

两边返回类型不一致 → 编译错误（或严重警告）。只在一处写 float、另一处漏写 → C99 起定义处直接报错；老代码里更隐蔽。

没写原型时：默认当 int → 浮点结果被 截断（经典错）

C89 / 老编译器在 调用前没见过原型 时，会 隐式假定函数返回 int。若函数 实际定义 返回 float：

/* 错：调用在前，且无原型 */
int main(void)
{
    float y = calculate(2.0f);   /* 编译器以为 calculate 返回 int！ */
    return 0;
}

float calculate(float x)       /* 实际返回 float */
{
    return x * 1.5f;             /* 2.0f → 3.0f */
}

后果：

  1. 调用处按 int 返回值 从寄存器/栈 取值（通常只取低 32 位或按整型解释）
  2. 函数体内实际按 float 位模式 返回 3.0f
  3. 调用方把位模式当整数再赋给 float → 完全错乱；即便再窄化，也 不是 3.0f

这就是 K&R 时代 必须写原型 的核心原因之一：非 int 返回类型写错标签 = 静默错结果。

正确做法：

float calculate(float x);      /* 先贴标签：返回 float */

int main(void)
{
    float y = calculate(2.0f); /* y == 3.0f */
    return 0;
}

float calculate(float x)
{
    return x * 1.5f;
}

C99 起：调用前无原型 → 直接报错；但 原型返回类型写错（如原型写 int、定义写 float）仍可能链接通过、运行错乱 —— 原型与定义必须一致。

2. 其他非整型返回类型

float  atof(char s[]);
double square(double x);
char  *strdup(const char *s);
void   warn(char *msg);

规则相同：原型和定义的 返回类型 都要显式、一致。

3. return 会隐式转换为声明的返回类型

规则：return 表达式; 时，表达式类型 自动转换 为函数声明的返回类型 —— 与赋值、二元运算中的隐式转换 同一套规则（见 2.7 §2 常规算术转换）。

窄 → 宽（小转大）：一般安全

return 表达式 函数返回类型 结果
float double 精度保留，通常无损失
int long 值在 int 范围内 → 安全扩宽
short int 整型提升，安全 
double read_price(void)
{
    float tick = 123.45f;
    return tick;       /* float → double：小转大，OK */
}

宽 → 窄（大转小）：可能精度损失或溢出

return 表达式 函数返回类型 风险
double float 有效位截断，低位丢失
long / long long int 超出 int 范围 → 溢出
double / float int 截断小数；超大值溢出
int char / short 高位截断 
int truncate_pi(void)
{
    return 3.14;       /* double → int：砍掉小数 → 3，非四舍五入 */
}

int from_float(void)
{
    float x = -2.7f;
    return x;          /* → -2，不是 -3 */
}

float narrow(void) { double x = 1.23456789012345; return x; / double → float：精度损失 / }

int overflow_risk(void) { long L = 10000000000L; return L; / long → int：若装不下 → 截断/溢出 / }


编译器对 **宽→窄** 常给 **`-Wconversion`** 警告；工程上应 **让返回类型与表达式匹配**，或 **显式 cast** 并确认范围：

```c
float narrow_explicit(double x)
{
    return (float)x;   /* 意图明确：接受 float 精度 */
}

4. void：无返回值

void warn(char *msg)
{
    fprintf(stderr, "warning: %s\n", msg);
    return;            /* 可省略 */
}
  • 只能 return;，不能 return 表达式;
  • 调用方不能 x = warn(...);

5. 其他返回类型注意点

类型 注意
指针 返回 局部变量地址 → 悬垂指针（ch05）；malloc 返回的堆内存 OK
数组 不能 返回局部数组（数组不能整体按值返回）；返回指针或 struct 包装
结构体 按值复制返回，大结构体有拷贝开销 
double square(double x)
{
    return x * x;      /* 同类型，无转换 */
}

6. 旧式 K&R 函数定义（了解）

ANSI 原型 double f(double x) 是规范写法。遗留代码可见 K&R 风格无参数类型列表的定义 —— 读代码时对照 4.1。

易混点

# 要点
1 返回 float 等：原型 + 定义 都要写 float，不能只在一处写
2 无原型 调用 → 老 C 默认 int 返回，float 函数结果 截断/错乱
3 return 表达式 隐式转换 为函数返回类型
4 小转大（float→double）一般 无精度损失
5 大转小（double→float、long→int）→ 截断/溢出
6 不能返回局部数组；指针注意生命周期

HFT / 内核提示

  • 策略信号：统一 double 或 int64_t 返回，避免 float/double 来回窄化
  • 驱动错误码：int 返回 0/-EINVAL；纯副作用用 void
  • API 设计：返回类型与实现 同宽，减少隐式转换惊喜

4.3

外部变量

本节讲什么

外部变量在 所有函数之外 定义（K&R 语境下的「外部」= 函数外）。其中 无 static 的全局变量 带 外部链接，可被他文件 extern 引用；static 文件级变量 虽也在 全局/静态存储区、寿命贯穿全程，但 不能跨文件访问，不算严格意义上「可跨文件共享」的外部变量。理解 存储期、链接 与 工程风险，是读内核全局状态、多文件共享数据的前提。

前置：1.10 外部变量与作用域、4.1 函数、2.4 声明。

要点

1. 什么是外部变量

外部变量（K&R 用语）= 在 函数外面（文件顶层）定义的变量。日常说的「全局变量」 通常指其中 无 static、可跨文件共享的那一类 —— 全局变量本身就是外部变量；但 不能 把「外部变量」和「所有放在全局区的变量」画等号。

int bufpos = 0;        /* 外部变量 / 全局变量 —— 定义，外部链接 */
char buf[BUFSIZ];

void append(int c)
{
    if (bufpos < BUFSIZ)
        buf[bufpos++] = c;
}
对比 局部变量 外部变量（无 static 全局）
定义位置 函数或 {} 块 内 所有函数 外
何时创建 每次进入函数/块 程序 启动时 分配一次
何时销毁 离开函数/块 程序 结束
谁可见 当前块内 本文件从定义行到文件末；他文件 可 extern
初值 未初始化 → 垃圾值 未初始化 → 清零（0、'\0'）

核心：内存从 程序启动 分配到 程序结束 才释放 —— 一直在，不像局部变量函数结束就销毁；也 不用 每次调用函数重新创建。

1.1 术语辨析：外部变量 ≠ 全局区里的所有变量

口语里常把「函数外定义的变量」都叫 全局变量；和 链接 相关的 外部变量 则 narrower —— 指 能跨翻译单元（.c）共享 的那类。

种类 定义示例 存储区 存储期 链接 他文件 extern
全局变量（无 static） int g; 全局/静态区 静态（全程） 外部链接 ✅ 能 引用
文件级 const（默认） const int lim = 1500; 常量区 静态（全程） 内部链接 ❌ 不能（须 extern const 定义）
static 全局变量 static int s; 全局/静态区 静态（全程） 内部链接 ❌ 不能
static 局部变量 函数内 static int c; 全局/静态区 静态（全程） —（非文件级） ❌ 名仅函数内

要点（你的归纳）：

  1. 全局变量（无 static） 本身就是 外部变量：作用域可扩展到 整个程序（多文件工程下经 extern / 头文件），全程序一份内存。
  2. static 全局变量 也占 全局/静态存储区、也是 静态存储期，但被 static 锁在本 .c —— 他文件 就算写 extern 也访问不到；它是 静态存储期变量，但 不算 严格意义上 可跨文件 的外部变量（4.6）。
  3. 外部变量不完全等同于「全局变量 + static 变量」这一笼统说法 —— 要看 链接属性：能不能被别的 .c 绑定到同一份定义。
int packet_count;          /* 外部变量 + 全局变量：可跨文件 */
static int file_private;   /* 全局区 + 静态存储期，但非跨文件外部变量 */

1.2 完整对照：num / s_num / c_num（a.c + b.c）

三种 文件顶层 定义，一张表分清：

a.c 定义 存储区 链接 b.c 能否用 b.c 能否改
int num = 10; 全局/静态区 外部 ✅ extern int num; ✅ num++
static int s_num = 20; 全局/静态区 内部 ❌ extern 也无效 ✅ a.c 内可改
static const int sc = 40; 常量区 内部 ❌ ❌ 只读
const int c_num = 30; 常量区 内部（默认） ❌ 默认接不上 ❌ 只读
extern const int c_num = 30; 常量区 外部 ✅ extern const int c_num; ❌ 仍不能改 
/* ========== a.c ========== */
int num = 10;                    /* 非 static 全局：外部链接 */
static int s_num = 20;           /* static 全局：仅 a.c */
const int c_num = 30;            /* const 默认内部：仅 a.c，常量区 */

void use_in_a(void)
{
    num++;           /* OK */
    s_num++;         /* OK：只有 a.c 能碰 s_num */
    /* c_num = 40; */  /* 编译错误：只读 */
}

/* 若要跨文件共享只读常量，a.c 应写成： */
/* extern const int c_num = 30; */

/* ========== b.c ========== */
extern int num;                  /* ✅ 绑定 a.c 的 num，可读可写 */
/* extern int s_num; */          /* ❌ 链接不到 a.c 的 static s_num */
/* extern const int c_num; */    /* ❌ 若 a.c 是 const int c_num=30（无 extern） */

void use_in_b(void)
{
    printf("%d\n", num);         /* 输出 10；改 num 会影响 a.c 同一份 */
    num = 99;                    /* OK */
    /* s_num++; */               /* 编译错误：b.c 根本看不见 s_num */
    /* c_num = 40; */            /* 即使能 extern 引用，也不能改 const 值 */
}

跨文件共享 c_num 的写法（只读、可引用、不可改）：

/* a.c —— 唯一定义 */
extern const int c_num = 30;

/* common.h */
extern const int c_num;

/* b.c */
#include "common.h"
printf("%d\n", c_num);   /* OK：读可以 */
/* c_num = 40; */        /* 编译错误：const 不可写 */

gcc a.c b.c -o demo

一句话：num = 普通全局，extern 就能共享；s_num = static 锁死本文件、但在 a.c 内可改；c_num = const 默认文件私有只读；static const = 常量区 + 仅本文件 + 不可改；跨文件只读共享须 extern const 定义。

static const 叠加：const → 常量区、不可改；static → 他文件 extern 无效（4.6 §2）。

见 2.3 §0.1、4.4 §3。

关键不是「只在某一个 .c 里用」，而是：

只要变量定义在 所有函数外面，不管工程有 多少个 .c 文件，在 其他文件 里写 extern 声明，就能 跨文件 访问 同一块内存。

/* === shared.c：定义一次（造仓库） === */
int packet_count = 0;    /* 全程序只有这一份内存 */

void on_packet(void)
{
    packet_count++;
}

/* === main.c：extern 贴标签，引用 shared.c 里的对象 === */
extern int packet_count;   /* 不分配内存，只说「别处有一个 int」 */

int main(void)
{
    printf("%d\n", packet_count);
    return 0;
}

/* === stats.c：同样可以 extern === */
extern int packet_count;

void print_stats(void)
{
    printf("total: %d\n", packet_count);
}

编译链接（以 global_num 为例，见 4.5 §3）：

gcc -o app main.c shared.c stats.c
阶段 发生什么
编译 每个 .c 单独变 .o；含 extern 的 .c 只知道符号存在，不知道定义在哪
链接 链接器汇总符号表，把 引用 绑到 唯一定义 那份内存上

packet_count 在 shared.c 定义，main.c / stats.c 经 extern（或头文件）引用 —— 链接后 只有一份，三文件共享。

要点 说明
定义 某一个 .c 文件顶层 int x; —— 全程序只能一次
extern 声明 其他 .c（或本文件定义之前）extern int x; —— 可多次
内存 一份，从启动到结束；所有 .c 里的函数改的都是 同一个 x
头文件 常把 extern int packet_count; 放进 .h，各 .c #include（4.5）

与局部变量对比：局部变量在 栈 上，函数返回就销毁；外部变量在 静态存储区（见 4.3.1 五区总览），跨文件、跨函数调用 都存活。

3. 好处：函数间（跨文件）共享状态

  • 所有函数 都能 直接读写（同一翻译单元内）
  • 适合 跨多次调用 累积的状态：缓冲区位、计数器、配置标志
  • 比层层传参省事（小项目、K&R 最长行示例）
int max;               /* 当前最长行长度 */
char longest[1000];    /* 当前最长行内容 */

/* main、mgetline、copy 都直接访问 max、longest */

详见 1.10 最长行全局版。

4. 坏处：改的地方多，难追 bug

风险 说明
耦合高 任意函数都能改，接口不清晰
难追踪 出 bug 时不知道 谁最后写了 这个全局
难测试 函数依赖隐式全局状态，单测要 mock 全局
线程安全 多线程同时改 → 数据竞争（内核/HFT 要特别小心）
命名污染 全局名与局部名冲突时 遮蔽 规则易混

工程原则：

  • 首选 参数 + 返回值传递数据（1.8）
  • 必须全局时：用 static 限制本文件可见（4.6），或封装 访问函数
  • 大型项目：状态收进 struct + 显式传指针，少裸全局

5. 与局部自动变量对照

void counter(void)
{
    int local = 0;           /* 每次调用重新创建，每次从 0 开始（若未赋别的） */
    local++;
}

int global_count = 0;        /* 只分配一次 */

void bump(void)
{
    global_count++;          /* 多次调用累加，值一直保留 */
}
  • 局部 auto：栈上，作用域块内，调用结束销毁（2.4）
  • 外部全局：静态存储区，程序全程（除非 static 改链接属性，见 4.6）

6. 定义 vs extern 声明（再归纳）

定义 extern 声明
写法 int bufpos = 0; extern int bufpos;
内存 分配 不分配，引用别处定义
次数 全程序 一次 可 多次

其他 .c 通过 extern + 头文件访问本文件定义的全局 —— 见 4.4 作用域、4.5 头文件。

准则：Define once; declare many times（1.10）。

7. static 限制外部变量：只能本 .c 用

无 static 的全局变量：其他源文件里 extern 声明一下就能直接用（通常经头文件 #include）。
static 全局变量：只能在定义它的那个 .c 里生效；别的文件 哪怕写 extern 也访问不到。

这样区分的目的：控制变量的可见范围，避免不同 .c 之间的命名冲突 —— 多个文件可以各自拥有 static int count;，互不干扰；若都叫无 static 的 int count;，链接器会报 重复定义。

默认外部变量（无 static）带 外部链接 —— 他文件 extern 能访问。若在 定义时 加 static，则 内部链接：仅定义所在的那一个 .c 可见。

无 static：跨文件共享

/* === a.c：定义 === */
int num;                 /* 或 int num = 0; */

/* === b.c === */
extern int num;          /* 声明后可直接用 num */
void f(void) { num++; }

/* === c.c === */
extern int num;          /* b.c、c.c 访问的是 a.c 里同一份 num */
void g(void) { num--; }

链接：gcc a.c b.c c.c → 一份 num 内存，三文件共享。

有 static：锁在本文件（防命名冲突）

/* === a.c === */
static int num;          /* 仅 a.c 可见；符号不导出给链接器 */

void bump(void) { num++; }

/* === b.c === */
static int num;          /* ✅ 合法：另一份 num，与 a.c 的 static num 无关 */

extern int num;          /* ❌ 想引用 a.c 的 static num → 链接失败 */
场景 结果
a.c 与 b.c 各 static int helper_state; ✅ 允许 —— 各文件私有，名字可重复
a.c 与 b.c 各 int packet_count;（无 static） ❌ 重复定义 —— 全程序只能一处定义
b.c 对 a.c 的 static int x 写 extern int x; ❌ 无效 —— 链接器找不到可绑定的定义
定义写法 链接属性 本文件 其他 .c + extern
int num; 外部链接 ✅ ✅ 可 extern 共享
static int num; 内部链接 ✅ ❌ 访问不到

作用：把模块私有状态 藏在 .c 里，避免全局命名冲突、缩小可被乱改的入口 —— 见 4.6。

两个 .c 都定义 int num; → 链接 重复定义

/* a.c */
int num;          /* 定义 ① */

/* b.c */
int num;          /* 定义 ② —— 与 ① 冲突 */

编译各自 .o 可能通过，链接 时报 multiple definition of 'num'，程序 过不了。

C 没有 public / private，靠 static + 链接属性 控制谁能跨文件看见：

手段 效果
无 static 全局 外部链接 —— 全程序 只能定义一次
static 全局 内部链接 —— 每个 .c 可各有自己的 static int num;，互不冲突
extern 声明 不分配内存，引用 那一个 外部定义

若 a.c、b.c 都想 有自己的 num，又想让 c.c 的 extern 只指向 某一个：

/* a.c：对外共享的那份 */
int num;

/* b.c：本文件私有的那份，与 a.c 的 num 无关 */
static int num;

/* c.c */
extern int num;    /* 只可能指向 a.c 的非 static num */

extern 永远 找 外部链接 的那个定义；static 的那份 链接器不导出，c.c 看不见。

8. 规范做法：头文件 extern，只在一个 .c 定义

多文件工程 推荐 写法（4.5 头文件 §2.1 有 global_num 完整 walkthrough：b.c #include 后直接 printf("%d", global_num)，改类型只动 a.c + common.h）：

/* common.h */
#ifndef COMMON_H
#define COMMON_H
extern int num;      /* 声明：所有 .c 包含后都知道「有这么个 int」 */
#endif

/* a.c —— 唯一定义处 */
#include "common.h"
int num = 0;         /* 定义 + 初值；全程序仅此一处 */

/* b.c */
#include "common.h"
void f(void) { num++; }   /* 无需再写 extern，头文件已声明 */

/* c.c */
#include "common.h"
void g(void) { num--; }
规则 说明
.h 只放 extern int num;（声明）
某一个 .c 只放 一次 int num = 0;（定义）
其他 .c #include 头文件即可，不要 再写 int num; 或重复 extern

改类型：定义处（如 a.c）与 .h 里的 extern 两处 同步改即可；凡 include 该头的 .c 自动一致，不必逐个改声明。

禁止 在头文件里写 int num = 0; —— 多个 .c include 会变成 多份定义，链接同样炸。

4.4

作用域规则

本节讲什么

作用域（scope） 决定名字在 哪段代码里可见、能用（编译期规则）。与 存储期/生命周期（内存活多久）不同 —— 见 1.10。另讲 链接（linkage）：符号能否跨 .c 文件合并（extern / static）。

前置：3.1 块与 {}、4.3 外部变量、4.6 静态变量。

要点

1. 四种作用域（C 名字可见范围）

C 里名字的作用域 主要分四种：

种类 典型对象 可见范围
① 局部作用域 函数内定义的变量 该函数 / 花括号内；出了范围名字失效
② 文件作用域 函数 外 定义的外部变量 整个 .c 文件（从定义行到文件末）
③ 函数作用域 goto 标号 整个函数 内有效
④ 块作用域 for / if 等 {} 里 声明的变量 仅该块 内（块结束名字失效）

作用域 回答「名字在哪能写」；生命周期 回答「内存活多久」—— 二者相关但不相同（如 static 局部：块作用域 + 全程存储期）。

① 局部作用域

在 函数内部 或 花括号 {} 里 定义的变量，只在这个范围内 能用：

void f(void)
{
    int x = 10;        /* 局部：仅 f 内可见 */
    {
        int y = 20;    /* 也在 f 内，更小一层块 */
    }
    /* y 在这里不可见 */
}
  • 默认 auto 存储；离开函数通常销毁（栈）
  • 不同函数的同名局部变量 互不影响

见 1.10 §1、2.4 局部声明。

② 文件作用域（分两种情况）

外部变量：定义在 所有函数外面（文件顶层）。名字在 本 .c 从定义行到文件末都可见 —— 这是 文件作用域 的共同点。

是否加 static 决定 别的 .c 能不能用（链接属性），从而分成两种：

定义 链接 本 .c 其他 .c
int num; 外部链接 ✅ 直接用 ✅ extern int num; 后 整个项目 都能用 同一份 num
static int num; 内部链接 ✅ 直接用 ❌ 用不了，写 extern 也链接不到 
/* === a.c === */
int shared = 0;          /* 无 static：外部链接 */
static int hidden = 0;   /* 有 static：仅 a.c */

void fa(void) { shared++; hidden++; }

/* === b.c === */
extern int shared;       /* OK：shared 作用域「扩展到」整个工程的多文件 */
void fb(void) { shared++; }

extern int hidden;       /* ❌ 链接失败：hidden 被 static 锁在 a.c */

无 static（外部链接）：

  • 本文件：文件作用域，任意函数直接访问
  • 他文件：extern 声明后，名字在 那个 .c 全文件 也可写 —— 口语上说，实际作用域扩展到整个项目的多个文件（链接后共享 一份 对象）
  • 全程序 只能定义一次 —— 4.3、4.5

有 static（内部链接）：

  • 作用域仍限于当前 .c，别的文件 根本链接不到 这个符号
  • 每个 .c 可各有自己的 static int num;，互不冲突 —— 4.6
int bufpos = 0;        /* 外部链接：a.c 内文件作用域 + 他文件可 extern */

void append(int c)
{
    bufpos++;
}

③ 函数作用域

主要针对 goto 标号：标号从定义点到 函数末尾 都有效，不受 {} 块边界限制（与变量不同）：

void f(int n)
{
    if (n < 0)
        goto cleanup;

    for (int i = 0; i < n; i++) {
        if (i == 5)
            goto cleanup;    /* 可跳到函数内别处标号 */
    }

cleanup:
    printf("done\n");
}
  • 标号 不占存储，无类型；函数作用域 = 标号在 整个函数 内可 goto
  • 变量 不能 用函数作用域跨越块 —— 变量遵 块作用域
  • 详见 3.8 goto

④ 块作用域

与 局部作用域 类似，但更强调 {} 围起来的块；变量 只在块内生效，块结束即 不可见：

void g(void)
{
    int a = 1;                 /* 块：整个函数体 */

    for (int i = 0; i < 10; i++) {   /* C99：i 的块作用域 = 仅 for 循环体 */
        int t = i * 2;
        /* i、t 仅在此块内 */
    }
    /* i、t 在这里都未定义 —— 不能写 i */

    if (a > 0) {
        int b = 2;           /* b 仅 if 块内 */
    }
    /* b 不可见 */
}
对比 局部（口语） 块作用域（精确）
范围 函数里定义的变量 任意 {} 内声明的名字
典型 void f(){ int x; } for (int i=0; …)、if { int t; }
结束 出函数或出块 出 {} 即失效

遮蔽：内层块同名变量 遮住 外层（3.2 else 就近 是另一规则）：

int x = 1;             /* 文件作用域 */
void h(void)
{
    int x = 2;         /* 块作用域，遮住外面的 x */
    printf("%d\n", x); /* 2 */
}

2. 作用域 vs 链接：两句话分清

作用域 链接属性
管什么 在 当前 .c 文件里，哪能看到 / 能写 这个变量名 链接阶段 把多个 .c 合成一个程序时，同名符号能不能关联到同一份对象
谁管 编译器（看源码位置） 链接器（合并 .o 时）
典型问法 「这行代码能写 num 吗？」 「a.c 的 num 和 b.c 的 extern num 是同一个吗？」

简单说：

  • 作用域 → 「在当前文件里 哪能看到 这个名字」
    例：static int num; 在 本 .c 所有地方 都能看见；出了这个 .c 就看不见（别的文件源码里不能合法引用它）。

  • 链接属性 → 「多个 .c 合并成一个程序 时，能不能把 同名变量关联到一起」

  • 无 static 的外部变量 → 外部链接：合并时 能关联，全程序 一份 num
  • static 的外部变量 → 内部链接：合并时 各用各的，a.c 的 static num 与 b.c 的 static num 互不干扰
/* a.c */
static int hidden = 1;   /* 作用域：a.c 全文可见；链接：仅 a.c 这一份 */
int shared = 1;          /* 作用域：a.c 全文可见；链接：可与 b.c extern 合并 */

/* b.c */
extern int shared;       /* 作用域：b.c 全文可见该名字；链接：指向 a.c 那份 shared */
/* 不能 extern hidden —— 链接属性不允许 */

文件作用域的外部变量因此 分两种（§1②）：

  1. static —— 作用域：本 .c；链接：内部，他文件接不上
  2. 无 static —— 作用域：本 .c + 他文件经 extern 后也能写名；链接：外部，合并时 关联成一份

其他作用域（块、函数）的变量 不涉及跨文件链接 —— 只有 文件作用域 的全局/函数名才谈链接。

其他作用域对照：

概念 问什么 例子
块/局部作用域 名字在 {} 内 能写吗 for 里的 i 出了循环不能用
函数作用域 标号 在函数内哪都能 goto 吗 cleanup: 标号

3. 内部链接 vs 外部链接（编译单元 = 一个 .c）

编译单元（translation unit） ≈ 一个 .c 源文件（经 #include 预处理展开后）：

a.c  ──编译──→  a.o  ─┐
b.c  ──编译──→  b.o  ─┼── 链接器 ──→  a.out（最终程序）
c.c  ──编译──→  c.o  ─┘
  • 编译器 单独 把每个 .c 编成 目标文件 .o
  • 链接器 再把多个 .o 合并 成一个可执行程序
  • 谈「链接属性」时，编译单元 指的就是这个 .c（+ 它 include 进来的头文件内容）

内部链接（internal linkage）

符号只在当前编译单元内部有效。别的 .c 里就算有 同名 符号，也是 各自独立的个体，链接时 不会合并，互不影响。

典型 写法
文件级变量 static int num;
文件级 const（默认） const int limit = 1500; —— 未写 extern 时内部链接
函数 static void helper(void); 
/* a.c */
static int num = 1;      /* 内部链接：只有 a.o 里有这个 num */

/* b.c */
static int num = 2;      /* 另一个 num，属于 b.o —— 与 a.c 无关，不冲突 */

外部链接（external linkage）

链接器合并 .o 时，可以把不同编译单元里的同名符号关联到同一份对象（全程序通常 只能有一处定义）。

典型 写法
文件级变量 int num;（无 static）
跨文件 const extern const int limit = 1500;（定义）+ 他处 extern const int limit;
函数 void foo(void); / int main(void)
跨单元引用 他处 extern int num; 
/* a.c */
int shared = 0;          /* 外部链接：导出给链接器 */

/* b.c */
extern int shared;       /* 声明：链接时与 a.c 的 shared 绑成同一个 */
void f(void) { shared++; }

对照表

内部链接 外部链接
谁 static 全局、const 全局（默认）、static 函数 无 static 的全局变量、extern const 全局、普通函数
编译单元 符号 只在本 .c 的 .o 里 符号 可被其他 .o 引用
同名 各 .c 各有一份，互不干扰 全程序 一份定义，多处 extern 引用
口语 「各用各的」 「合并时关联到一起」

局部变量、函数参数 没有跨文件链接问题 —— 它们不在链接器符号表里争同名。

4. extern

  • 声明（不是定义）外部变量或函数：符号在 其他翻译单元 或本文件别处 定义
  • 扩展 链接 可见性，不扩大 文件内的块作用域
/* b.c */
extern int shared;     /* 用 a.c 的定义，b.c 全文件可见该名字 */

5. static 与链接（与 4.6 配合）

写法 作用域 链接
int x;（文件顶层） 文件 外部 —— 全程序一份定义
const int x = 1;（文件顶层，默认） 文件 内部 —— 仅本 .c；常量区、只读
extern const int x = 1;（文件顶层定义） 文件 外部 —— 可经头文件跨文件只读共享
static int x; 文件 内部 —— 仅本 .c
static void f(void); 文件 内部 —— 仅本 .c 可调用
函数内 static int s; 块（函数内） 无跨文件问题

易混点

# 要点
1 四种作用域：局部、文件、函数（标号）、块
2 文件作用域分两种：static→仅本 .c；无 static→extern 后扩到多文件
3 goto 标号 = 函数作用域，可跨 {}；变量不行
4 作用域 ≠ 生命周期；static 局部块内名、全程存储
5 内层块可 遮蔽 外层同名变量
6 作用域：本 .c 哪能见名；链接：合并 .c 时同名 能否关联
7 编译单元 ≈ 一个 .c；内部链接 = 各 .o 各用各的；外部链接 = 链接时合并

HFT / 内核提示

  • 缩小块作用域：C99 for (int i=0; …) 防 i 泄漏到循环外
  • 文件作用域 + static：驱动 .c 私有全局，等价于 C++ 里「翻译单元内 private」
  • 读内核：区分「这个名在本文件哪都能见」vs「别的 .c 能不能 extern」

题目 1： 以下代码中各变量的作用域和链接性是什么？

int x = 1;           // 全局
static int y = 2;    // 文件内
void f() {
    int x = 3;       // 局部，遮蔽全局 x

        int x = 4;   // 更内层，遮蔽外层 x

}
参考答案

4.5

头文件

本节讲什么

头文件（后缀 .h）专门放 声明 和可共享的 类型/宏，供多个 .c 通过 #include 复用。多文件工程不只是语法需要 —— 更为了 开发维护效率：代码复用、增量编译、模块化协作（§8）。每个 .c 单独编译成 .o，链接器合并；.h 保证大家用的是同一套声明。

前置：4.1 函数原型、4.3 外部变量、4.4 作用域与链接。

要点

1. 头文件是什么

头文件 = 后缀为 .h 的文件，专门用来放声明（以及宏、类型定义），一般不写函数体、不写全局变量定义。

常放内容 示例
变量的 extern 声明 extern int packet_count;
函数原型 int add(int a, int b);
宏定义 #define MAXLINE 1000
结构体 / 类型定义 struct node { ... };、typedef int bool_t;

不放（应放在 某一个 .c）：

  • 全局变量 定义 int num = 0;
  • 函数 实现 { ... }
  • static 模块私有符号（只在本 .c）

2. 为什么需要头文件：#include 复用声明

当 多个 .c 都要用 同一组声明 时：

  • 不好：每个 .c 手写一遍原型 → 易抄错、改一处漏改别处
  • 好：写在 一个 .h，各 .c #include 进来
/* math_utils.h */
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

extern int g_seed;
int add(int a, int b);
double square(double x);

#endif

/* main.c */
#include "math_utils.h"

int main(void)
{
    int s = add(1, 2);
    return 0;
}

/* math_utils.c */
#include "math_utils.h"

int g_seed = 0;              /* 唯一定义 */

int add(int a, int b)
{
    return a + b;
}

double square(double x)
{
    return x * x;
}

好处：

  1. 避免重复写 相同声明
  2. 保证一致 —— 所有 .c include 同一份 .h，编译器看到的 函数签名、类型、宏 相同
  3. 接口清晰 —— .h = 模块对外「菜单」，.c = 实现

预处理时 #include "math_utils.h" 等价于把 .h 内容 粘贴 进当前 .c 再编译（4.11 预处理器）。

2.1 完整例子：global_num（a.c 定义 + a.h 声明 + 其他 .c）

① 在 a.c 里定义（全程序唯一定义）

/* a.c */
int global_num = 0;

② 在 a.h 里写 extern 声明

/* a.h */
#ifndef A_H
#define A_H

extern int global_num;

#endif

③ 其他 .c 包含 a.h 即可用，不必再手写 extern

/* b.c */
#include <stdio.h>
#include "a.h"

void show_in_b(void)
{
    printf("%d\n", global_num);
}

/* c.c */
#include "a.h"

void bump_in_c(void)
{
    global_num++;    /* 改的是 a.c 里定义的那一份 */
}

gcc a.c b.c c.c -o demo
文件 写什么
a.c int global_num = 0; —— 定义（分配内存，仅此一处）
a.h extern int global_num; —— 声明
b.c / c.c #include "a.h" —— 自动带上声明

运行时：全工程 唯一一份 数据

链接完成后，不管哪个 .c 包含 a.h，大家操作的都是 同一块内存 里的 同一个 global_num：

行为 结果
a.c 里 global_num = 10 内存里那份变成 10
b.c 里 printf("%d", global_num) 读到 10
c.c 里 global_num++ 变成 11；a.c、b.c 再读都是 11

整个工程里只有这一份数据 —— 不是每个 .c 各拷贝一份。哪个文件 修改 了它，其他文件 再读取 时拿到的都是 修改后的最新值（进程运行期间一直有效，见 4.3）。

        a.c 定义
          │
          ▼
    ┌─────────────┐
    │ global_num  │  ← 全程序唯一实体（如地址 0x601000）
    └─────────────┘
       ▲    ▲    ▲
       │    │    │
    a.c读写 b.c读写 c.c读写   （链接后都指向同一地址）

头文件也可叫 common.h 等名字；关键是 一个 .c 定义 + 一个 .h 声明 + 其余 #include。

改类型时如何同步：若要把 global_num 从 int 改成 float：

  1. a.c 改定义：float global_num = 0.0f;
  2. a.h 改声明：extern float global_num;
  3. 所有 #include "a.h" 的 .c 自动 看到新类型 —— 不会出现 b.c 还当 int、a.c 已是 float 的 声明/定义不一致

若不用头文件、各 .c 自己抄 extern，极易漏改某一文件 → 链接通过或静默错行为。头文件 = 单一真相来源。

3. 编译链接流程：编译「认声明」，链接「绑定义」

a.c  ──→ a.o  ─┐
b.c  ──→ b.o  ─┼──→ 链接器 ──→ a.out
c.c  ──→ c.o  ─┘

编译阶段（每个 .c 单独 编译成 .o）：

文件 编译器看到什么 结果
a.c int global_num = 100; —— 定义 a.o 里 导出 符号 global_num（有实体、占内存）
b.c #include "a.h" → extern int global_num; —— 仅声明 b.o 里 引用 符号 global_num（知道「有这么个 int」，不知道 定义在哪）
c.c 同上 c.o 里同样是 未解析的引用

要点：b.c 包含 a.h 后，编译器只确认「存在一个外部链接的 global_num」，类型检查、printf("%d", global_num) 都能过；此时不必、也无法 知道它在哪个 .c 定义 —— 那是 链接器 的工作。链接绑定后，任一文件改写，他处读到的都是最新值（§2.1）。

链接阶段（链接器汇总 所有 .o 里的符号表）：

  1. 在 a.o 找到 global_num 的定义（分配好的那一份内存）
  2. 把 b.o、c.o 里对 global_num 的 引用 填成 同一地址
  3. 生成最终可执行文件 —— 三文件访问的是 同一块内存
a.o:  global_num  ← 定义（实体）
b.o:  global_num  ← 引用 ──┐
c.o:  global_num  ← 引用 ──┼── 链接器绑定到 a.o 那份

若 没有任何 .o 提供定义 → undefined reference to 'global_num'（未定义引用）。
若 多个 .o 都有定义 → multiple definition of 'global_num'（重复定义）。

  • 编译单元 = 一个 .c 文件（#include 展开后）单独编译 → .o
  • 链接器 合并 .o；外部链接 符号跨文件 定义一次、引用多处（4.4 §3）

§2.1 的 global_num 例子走的就是这条路径：common.h 保证各 .c 编译时声明一致；链接器保证 运行时只有一份实体。

4. 单定义规则：.h 只声明，.c 定义

放在 .h 放在 某一个 .c
extern int num; int num = 0;
int foo(int x); int foo(int x) { return x; }
struct point { int x, y; }; （类型定义可放 .h；带静态数据的定义放 .c）
  • 每个 外部链接 符号全程序 只能定义一次
  • .h 被多个 .c include 时，写 int num = 0; → 每个 .c 各一份定义 → 链接 重复定义
  • 正确：.h 写 extern int num;，一个 .c 写 int num = 0;

见 4.3。

5. include 守卫（防止重复展开）

#ifndef MATH_UTILS_H
#define MATH_UTILS_H
/* 头文件内容 */
#endif

同一 .c 多次 include 或链式 include 时，避免重复定义类型/宏。

6. #include "..." vs #include <...>

写法 查找路径 典型
#include "foo.h" 当前目录、工程路径优先 项目自己的 .h
#include <stdio.h> 系统/编译器 标准路径 标准库、第三方库

7. 组织方式：头文件 不必 与 .c 一一对应

没有「每个 .c 必须配一个同名 .h」的硬性规定。怎么拆头文件，完全看项目需求 —— 怎么方便维护就怎么来。

做法 适用场景 示例
公共头文件 多个 .c 共用 的声明、类型、宏 common.h 放 extern int global_num;，a.c / b.c / c.c 都 include
模块头文件（常与 .c 成对） 某个 .c 实现一个模块，对外暴露 API stack.h 声明 push/pop，stack.c 实现；main.c 只 include stack.h
混合 真实工程最常见 全局配置/错误码放 common.h；各子系统各有 xxx.h + xxx.c 
方式 A —— 公共头：
  common.h  ←── a.c, b.c, c.c 都 include（共享 extern、宏、类型）

方式 B —— 模块头：
  stack.h  ←── stack.c（实现）+ main.c（调用方）
  parser.h ←── parser.c + main.c

方式 C —— 混合：
  common.h + stack.h + parser.h + main.c

原则：

  • 谁需要这份声明，谁就 #include 对应 .h —— 不必为了「对称」硬造没用到的头文件
  • .h 描述的是「接口/契约」，不是「.c 的镜像」；一个 .h 可被很多 .c include，一个 .c 也可 include 多个 .h
  • 小项目：common.h 一把梭；变大后：按 功能模块 拆 net.h、file.h 等，边界更清晰

按功能模块划分头文件（常见工程做法）

通常会 按功能模块 来划分头文件 —— 同一子系统的 函数声明、相关类型、extern 全局 放在 同一个 .h：

头文件 放什么 谁 include
net.h 网络相关：套接字 API、extern int net_errno;、协议结构体 只做网络的 .c
file.h 文件 I/O：open_log、read_config、extern FILE *log_fp; 只做文件操作的 .c
common.h 全工程共用的错误码、基础类型 多数 .c 
/* net.h */
#ifndef NET_H
#define NET_H
extern int packets_sent;
int net_connect(const char *host, int port);
void net_close(int fd);
#endif

/* file.h */
#ifndef FILE_H
#define FILE_H
int load_config(const char *path);
void write_log(const char *msg);
#endif

/* server.c —— 只做网络 */
#include "net.h"

/* config_loader.c —— 只做文件 */
#include "file.h"

/* main.c —— 两者都要 */
#include "net.h"
#include "file.h"

好处（你的归纳）：

  1. 按需包含 —— 哪个 .c 需要哪块功能，只 #include 对应头文件，不引入 多余声明
  2. 减少耦合 —— config_loader.c 不必看见 net_connect 的原型，编译依赖更干净
  3. 缓解命名冲突 —— 各模块内部状态用 static 藏在 net.c / file.c；对外名字集中在各自 .h，比一个大杂烩 all.h 不易撞名
❌ 不好：everything.h 塞进所有声明 → 每个 .c 都 include → 改一行牵动全员重编

✅ 较好：net.h / file.h / ui.h 分模块 → 谁用谁 include

模块实现仍常见 net.c + net.h 成对；私有 helper 用 static 函数 不写进 net.h（4.6）。

8. 工程价值：提高开发与维护效率

多文件 + 头文件，主要不是为了「显得专业」，而是实实在在 省时间、好协作：

维度 怎么做 得到什么
① 代码复用 通用 函数原型、类型、宏、extern 声明 放进 .h；多个 .c #include 同一份 不用每个源文件抄一遍；改接口 只改一处 .h

① 代码复用

/* common.h —— 一份声明，多处 include */

② 编译效率（增量编译）

首次：  gcc -c main.c parser.c stack.c   → main.o parser.o stack.o
        gcc -o app main.o parser.o stack.o

只改了 parser.c：
        gcc -c parser.c                    → 新的 parser.o
        gcc -o app main.o parser.o stack.o  /* main.o stack.o 复用，不重编 */
改了什么 通常要重编谁
某个 .c 实现 该 .c + 重新链接
某个 .h 声明/结构体布局 所有 include 该 .h 的 .c（接口变了）

4.6

静态变量

本节讲什么

static 可修饰 文件级变量、函数内局部变量、函数定义（再叠 const 得只读）。从 变量 和 函数 两个层面，把符号 本地化 在本 .c 或本函数内，避免跨文件同名冲突；函数内 static 则额外保留 跨调用状态。

前置：4.3 外部变量、4.4 作用域规则。

要点

0. 总览：static 的四种修饰（一张表记住）

修饰对象 写法示例 主要效果 能否被他文件看见
文件级全局变量 static int s_num = 20; 仅本 .c；全局/静态区；本文件内可改 ❌ extern 无效
文件级 + const static const int sc = 40; 本文件只读；常量区 ❌ 不能改、不能 extern
函数内局部变量 函数里 static int count; 作用域 仅本函数；存 静态区；返回后不销毁，下次调用 保留上次值 ❌ 不涉及跨文件
函数 static void helper(void); 仅本 .c 可调用；防与他文件 同名函数 链接冲突 ❌ 不必写进对外 .h 
变量层面：  文件 static / static const  →  符号锁在本 .c
           函数内 static               →  跨调用记状态（仍只在本函数可见）

函数层面：  static 函数                →  调用入口锁在本 .c

一句话：static 的核心是 作用域/链接的本地化控制 —— 变量不让别的 .c extern；函数不让别的 .c 调用；函数内的 static 变量则让 数据活过多次调用。

static 不只用在文件顶层 —— 函数内部 也可以写。同一关键字，放哪、修饰谁 决定效果：

定义位置 static 主要改变什么
函数内 生命周期 / 存储区（作用域仍在本函数）
函数外（文件顶层） 链接属性（能否被他文件 extern）

1. 函数内的 static 局部变量

static 也可以在函数内部定义。和普通局部变量相比：

普通局部 int x; 函数内 static int x;
作用域 仅本函数 仅本函数（一样）
存储区 栈 全局/静态存储区（4.3.1）
函数返回后 栈帧销毁，值消失 值保留，对象 不销毁
下次再调用 重新分配，垃圾值/重新初始化 还能保留上次的结果
初始化 每次进入函数时（若写了初值） 仅首次 执行到声明时初始化一次 
int counter(void)
{
    static int count = 0;   /* 静态区；只初始化一次；名字仅 counter 内可见 */
    return ++count;
}

int main(void)
{
    counter();   /* 返回 1 */
    counter();   /* 返回 2 —— count 没随上次返回而清零 */
    counter();   /* 返回 3 */
    return 0;
}

要点（你的归纳）：

  1. 作用域 仍 仅限这个函数 —— 别的函数 不能 写 count。
  2. 存储 在 全局/静态存储区，不是栈 —— 所以函数调用结束后 值不会消失。
  3. 下次再调用 同一函数时，读到的是 上次留下的值（除非程序结束才释放）。
void demo(void)
{
    int auto_n = 0;         /* 栈：每次调用重建 */
    static int static_n = 0; /* 静态区：全程一份，跨调用保留 */

    auto_n++;
    static_n++;
    /* 返回后 auto_n 没了；static_n 仍是累加后的值 */
}

易混：函数内 static 不改链接（不会被他文件 extern）—— 它解决的是 跨多次调用保存状态，不是跨文件共享。跨文件仍看 §2 的文件级 static。

2. 文件级的 static 变量：限制 跨文件 作用域（≠ 跨文件外部变量）

在函数外（文件顶层）加 static，改变的是 链接属性，不是「函数返回后值还在」那套（那是 §1 函数内 static 局部的事）。表示 这个变量只能在本 .c 里用 —— 内部链接。它 存储在全局/静态区、静态存储期 与无 static 全局相同，但 不能被其他文件 extern 引用，因此 不算 严格意义上可跨文件共享的 外部变量（4.3 §1.1）。

对比：int num vs static int num（在 a.c 定义）

/* === a.c：普通外部变量 === */
int num;

/* b.c、c.c 使用前声明即可 */
extern int num;    /* ✅ 能访问 a.c 里的 num */

/* === a.c：static 外部变量 === */
static int num;

/* b.c */
extern int num;    /* ❌ 无效：链接器找不到可供外部的 num */
a.c 定义 b.c 里 extern int num;
int num; 可以 —— 跨文件共享一份内存
static int num; 不可以 —— num 被锁在 a.c，别的文件 就算写 extern 也访问不到

static 能否修改？看有没有 const

static 只管存储期/链接，不表示只读。能不能改值，要看 const 有没有一起出现：

写法 在作用域内能否赋值修改
static int a = 5; ✅ 能 —— a = 10; 合法（文件级或函数内均可）
static const int a = 5; ❌ 不能 —— 只读，常放 常量区；a = 10; 编译错误 
/* 文件级 */
static int s_num = 20;
static const int sc_num = 30;

void f(void)
{
    s_num = 21;        /* OK */
    /* sc_num = 31; */ /* 错误：const */

    static int count = 0;
    static const int max = 100;

    count++;           /* OK：static 局部，可改 */
    /* max = 200; */   /* 错误：static const */
}

记忆：static → 活多久、谁能跨文件看见；const → 能不能写。两者独立，叠在一起才是「静态存储的只读常量」。

static const 叠加：常量区 + 仅本文件 + 不可改

加了 const 的 static 变量（文件级），存放在 常量存储区 —— const 的只读属性 符合常量区规则；static 再把它 锁在当前 .c：

关键字 贡献什么
const 只读 → 进 常量区；运行期 不能修改
static（文件级） 内部链接 → 仅当前文件 能访问；他文件 extern 无效 
/* a.c */
static const int sc_num = 40;   /* 常量区；仅 a.c；不可 sc_num=41 */

void f(void) { printf("%d\n", sc_num); }   /* OK：本文件读 */

/* b.c */
extern const int sc_num;        /* ❌ 链接不到 */
/* sc_num = 50; */              /* 即使能见到也不能改 */

两者结合后：既不能修改，也不能被其他文件访问 —— 适合放 本模块私有的只读配置（表长上限、魔数、版本号），比 #define 有类型，又比 extern const 更 不暴露 给其他 .c。

函数内的 static const 同样进 常量区、不可改，但 名字作用域 在函数内（不涉及跨文件链接问题）。

记忆：static 加在 文件级变量定义 上 = 对外隐藏，只给 本翻译单元 用；与「全程不销毁」不矛盾 —— 生命周期仍是程序全程，只是 链接范围 缩小到单文件。

为什么要这样设计：多 .c 工程里，每个模块常有 count、state、buf 等 内部状态；用 static 全局 可让 同名变量在不同文件各有一份，既 避免链接时的命名冲突，又 不污染 其他文件的命名空间。需要 跨文件共享 的才用无 static 全局 + extern/头文件。

3. static 函数：仅本源文件可调用

/* a.c */
static void helper(void)   /* 内部链接：只有 a.c 能调用 */
{
    ...
}

void api(void)
{
    helper();              /* OK：同文件 */
}

/* b.c */
extern void helper(void);  /* ❌ 即使声明也链接不到 a.c 的 static helper */
void g(void) { helper(); }
  • 函数 定义 前加 static → 内部链接；只能在当前源文件里被调用
  • 目的：与文件级 static 变量一样 —— 避免和其他 .c 里的同名函数产生链接冲突；实现细节 不必 放进对外 .h
  • Linux 驱动、UEFI 模块中：对外 API 少数几个函数，其余 static 辅助函数 藏在本 .c

4.7

寄存器变量

本节讲什么

register 修饰的 局部变量（含形参），建议 编译器把它放在 CPU 寄存器 里而不是 栈/内存，以加快 频繁读写。现代编译器多自动分配寄存器，手写 register 已少见，但读 K&R、旧代码、理解「热变量」优化时仍会碰到。

前置：4.1 函数、4.3.1 内存布局 §1 栈区、2.4 声明。

要点

1. 什么是寄存器变量

寄存器变量 = 用 register 关键字修饰的 局部变量（或 形参）：

void sum_array(int n, register int *p)
{
    register int i;
    register int sum = 0;

    for (i = 0; i < n; i++)
        sum += p[i];
}
对比 普通局部 int i register int i
典型存放 栈（4.3.1 §1） 尽量 放 CPU 寄存器
访问速度 需访栈（可能再进缓存） 寄存器读写 更快
适用 一般局部量 频繁读写 的循环计数器、累加器等
取地址 &i ✅ 合法 ❌ 非法（未必有内存地址）

意图：把最热、最常用的变量放在 离 CPU 最近 的寄存器里，减少访栈/访内存次数。

2. 只是「建议」—— 编译器可以不照办

  • register 不是命令，是 给编译器的提示（hint）
  • CPU 寄存器数量有限；一个函数里 register 太多，或全局优化需要寄存器时，编译器会 忽略 部分 register
  • 寄存器不够 时，变量 退化成普通栈变量 —— 程序仍正确，只是未必更快
void f(void)
{
    register int a, b, c, d, e, f, g;  /* 未必都能进寄存器 */
    /* 编译器按优化策略挑选，其余放栈 */
}

现代实践：-O2/-O3 下编译器 自动 做 寄存器优化（见 4.7.1 §0），往往 不必 手写 register；写了也可能被忽略。

C17 起块作用域 register 已 弃用；C23 移除该存储类提示。K&R 时代语法仍大量出现在教材与旧代码中。

2.1 「寄存器优化」≠ 只指手写 register

口语里的 寄存器优化，多半指 编译器自己的优化，不全是程序员写 register：

编译器常做的事 目的
把 频繁使用 的局部变量 放进 CPU 寄存器 少访栈/少访内存，函数 跑得更快
某变量从内存 只读一次，之后在寄存器里 反复用旧值 省掉重复 load 
/* 源码 */
for (int i = 0; i < n; i++)
    sum += a[i];
/* 优化后概念上：i、sum 可能一直在寄存器里转 */

int x = g_flag;
foo(x);
bar(x);   /* 编译器可能不再读 g_flag，仍用寄存器里的 x */

手写 register 只是 提示「请优先把我放进寄存器」；真正干活的是 编译器优化器。与 volatile 的冲突见 4.7.1。

3. 不能取地址：& 与 register 互斥

寄存器里的值 不一定 对应某块固定内存地址，因此：

register int i = 0;
int *p = &i;    /* ❌ 编译错误：不能对 register 变量取地址 */
原因 说明
可能没有内存地址 变量只在寄存器中，链接器/栈帧里没有稳定槽位
与指针语义冲突 & 要求对象有 可寻址 的存储（ch05）

记忆：需要 传指针 给别的函数修改、或 & 取址 的变量，不要 声明成 register。

4. 只能是局部变量 / 形参 —— 不能写在函数外

register 只能修饰函数内部的局部变量，或函数的形参。 不能用于文件顶层的全局变量。

register int g;          /* ❌ 非法：不能在函数外 */

int main(void)
{
    register int i;      /* ✅ */
    ...
}
为什么全局不行 说明
寄存器与调用栈绑定 寄存器为 当前函数执行 服务；return 后寄存器内容 不再保留 给该变量
全局要长期存内存 全局/static 对象从 程序启动到结束 都在（4.3），必须落在 全局/静态区 或链接器管理的内存，不能 占着易失的 CPU 寄存器

一句话：register 变量本质是 局部变量 —— 生命周期跟 这一次函数调用 走，和栈上 auto 局部同类；只是 存放位置 优先尝试寄存器而非栈。

5. 与 auto、static 局部对比

存储类 作用域 典型存放 函数返回后 & 取址
auto（默认） 块/函数 栈 销毁 ✅
register 块/函数 寄存器（或退化为栈） 销毁 ❌
static（函数内） 块/函数 静态区 保留值 ✅

register 不改变作用域，只影响 尽量放哪、能否取址；与 4.6 static 局部（跨调用保留）是不同维度的优化。

示例

unsigned strlen_reg(register char *s)
{
    register char *p = s;
    while (*p)
        p++;
    return (unsigned)(p - s);
}

循环里 p 频繁自增、解引用 —— 典型 K&R 风格「建议放寄存器」的写法。

易混点

# 要点
1 register = 建议，编译器可忽略；寄存器不够 → 普通栈变量
2 不能 & —— 未必有内存地址
3 仅局部/形参；不能 修饰全局 —— 全局要长期占内存
4 仍是 局部变量：函数结束即失效，与栈局部同类生命周期

6 现代靠 编译器优化 多于手写 register

HFT / 内核提示

两个关键字在 高频量化 和 内核 里都有用，但 分工不同：

关键字 内核开发 高频量化（HFT）
volatile 必用：硬件寄存器对应的 MMIO 地址 必须 volatile，否则编译器 寄存器优化 可能让你读不到硬件 实时状态（状态位、FIFO 空满等） 用户态策略代码 较少 直接写；设备侧多在驱动/PMD；共享状态更常用 atomic/内存屏障
register C 源码里 几乎不写；靠编译器 + 必要时 汇编 可 标在高频循环的 计数变量 上，略 提速；但 -O3 下编译器常自动 把合适变量放进寄存器，手写往往多余

内核：volatile 是硬需求

/* 设备寄存器映射 —— 必须 volatile */
volatile uint32_t * const uart_dr =
    (volatile uint32_t *)(uintptr_t)0x40001000u;

uint32_t status = *uart_dr;   /* 每次读都真访问硬件，不能用缓存旧值 */
  • Linux：优先 readl/writel/ioread32 等 API（内部已带正确语义）
  • 不用 volatile 时，优化后的驱动可能 卡在旧状态，表现为 轮询不到中断、DMA 不前进

HFT：register 可选，瓶颈 seldom 在这

for (register int i = 0; i < n; i++)   /* 可写，但常不必写 */
    sum += book[i];
  • 热路径更应关注：缓存局部性、分支预测、少 syscall、对象池少 malloc
  • DPDK：寄存器访问走 PMD；策略循环靠 编译器自动寄存器分配 + SIMD/内联 居多

结论：内核侧 volatile 不能省；HFT 侧 register 可写可不写，现代编译器 优化能力很强，自动寄存器分配往往已够。

二、知识点拆解

1. 头文件与源文件分离（stack.c / stack.h）

  • stack.h：只写 函数声明、类型、宏 —— 没有 函数体；其他文件 #include "stack.h" 即可调用 push/pop。
  • stack.c：写 具体实现；栈缓冲区、栈顶指针用 static —— 仅本文件可见，外部 不能 直接改 buf/sp，只能通过 API 访问。
/* stack.h */
#ifndef STACK_H
#define STACK_H
void push(double val);
double pop(void);
#endif

/* stack.c */
#include "stack.h"

static double buf[100];   /* static：仅 stack.c；K&R 书中常用 val[] + sp */
static int sp = 0;

void push(double val)
{
    if (sp < 100)
        buf[sp++] = val;
}

double pop(void)
{
    if (sp > 0)
        return buf[--sp];
    return 0.0;
}

见 4.5 栈模块示例、4.6 §2 static 全局。

2. calc.h 统一全局共享

所有 .c 可 #include "calc.h"，集中管理 全工程共用 内容：

示例骨架：main.c

#include "calc.h"
#include <stdlib.h>

int main(void)
{
    int type;
    double op2;

    while ((type = getop()) != EOF) {
        switch (type) {
        case NUMBER:
            push(atof(/* 共享输入缓冲 s，见书中实现 */));
            break;
        case '+':
            push(pop() + pop());
            break;
        case '*':
            push(pop() * pop());
            break;
        case '-':
            op2 = pop();
            push(pop() - op2);   /* 减除顺序：后弹出的作右操作数 */
            break;
        case '/':
            op2 = pop();
            if (op2 != 0.0)
                push(pop() / op2);
            break;
        case '\n':
            printf("\t%.8g\n", pop());
            break;
        default:
            printf("error: unknown command %c\n", type);
            break;
        }
    }
    return 0;
}

4.9

初始化

本节讲什么

外部变量、静态变量、局部自动变量的 初值规则：谁默认零初始化、谁是未定义行为（UB）、数组与字符串如何初始化；以及 .data / .bss / 栈 在启动阶段的底层分工。直接影响全局配置表、静态缓冲区、内核/裸机启动代码。

前置：4.3 外部变量、4.3.1 程序内存布局、4.6 静态变量、4.5 头文件。

一、三类变量初始化核心规则对比

变量类型 存储分区 未手动初始化默认值 初始化时机
外部全局变量 / static 静态全局 .data / .bss（4.3.1 全局/静态区） 强制全零（int=0、浮点 0.0、char='\0'、指针 NULL） main() 执行前，CRT 启动代码完成清零/拷贝
static 局部变量（函数内 static） .data / .bss 强制全零 第一次调用该函数前完成；生命周期与程序一致（4.6 §1）
普通局部自动变量（无 static） 栈 stack 垃圾随机值（UB） 进入栈帧时分配，无自动清零 
有初值的全局/static  →  .data 段（加载时拷贝预设值）
无初值的全局/static  →  .bss  段（加载器整块清零）
普通局部 auto        →  栈帧（退出后空间可被复用，不保证清零）

二、分模块详细解读

1. 外部 / 静态变量（全局、static 局部）

规则

  1. 只要带 static 或定义在 函数外，无显式赋值时，编译器保证 自动置零；
  2. 所有类型统一 全比特置 0，对应各自类型的零值： - 整型：int a; → a = 0 - 浮点：static double x; → x = 0.0 - 字符：static char c; → c = '\0' - 指针：char *p; → p = NULL
  3. 显式初始化示例：
int global_num = 42;              /* 外部全局，有初值 → .data */
static int file_only_buf[1024];   /* 文件级 static，无初值 → .bss，全元素 0 */

void func(void)
{
    static int cnt = 0;           /* 函数内 static：仅首次执行到声明时赋 0，之后保留 */
    cnt++;
}

底层内存分段

写法 段 加载时行为
int g = 42; .data 直接把 42 拷进内存
static int buf[1024]; .bss 加载器 一次性整块清零，可执行文件里不必存 1024 个 0

.bss 清零节省镜像体积，是链接器/加载器的工程优化；语义上等价于「未写初值的全局/static 全是 0」。

2. 局部自动变量（普通栈变量）

核心风险点

栈内存 复用：函数退出后，这块栈空间会被其他调用覆盖，不会自动清零。不赋值直接读取属于 未定义行为（UB）。

void test(void)
{
    int a;
    printf("%d", a);   /* ❌ 垃圾随机值，UB */
    a = 10;            /* ✅ 使用前手动赋值 */
    int b = 20;        /* ✅ 声明时初始化（推荐） */
}
普通局部 int x; 函数内 static int x;
存储 栈 全局/静态区
未初始化 垃圾值，UB 保证 0
函数返回后 栈帧销毁 值保留

3. 数组初始化语法规则

1. 初始化列表少于数组长度 → 剩余元素自动置 0（与静态变量规则一致）

int arr[5] = {1, 2};
/* 等价于 {1, 2, 0, 0, 0} */

2. 省略数组长度 → 编译器按列表元素个数推算长度

int arr[] = {1, 2, 3};   /* 长度 = 3 */

3. 字符数组 + 字符串字面量 → 自动追加末尾 \0

char str[] = "hello";
/* 实际：h e l l o \0，长度 6 */

char buf[10] = "hi";
/* { 'h','i','\0', 0,0,0,0,0,0,0 } */

与 1.9 字符数组 的 char s[] = "..." 写法一脉相承；第 5 章会扩展到指针数组、多维数组、结构体数组。

4. 初始化时序 & 特殊环境（内核 / 裸机）

标准操作系统（Linux / Windows）

OS 加载程序 → CRT 启动代码 → 清零 .bss、拷贝 .data → 调用 main()

全局 / 静态变量在 main 执行前 就已经完成初始化。

裸机、操作系统内核（无 CRT 运行时库）

  • 没有标准 C 运行库的自动清零逻辑；
  • 必须 手动写启动/加载代码 清空 .bss 段，否则全局/static 变量会是内存里的 垃圾值；
  • 这是底层开发、HFT 固件、自制 OS 的 关键细节 —— 不能想当然依赖「C 保证全零」。
/* 内核启动伪代码示意 */
extern char __bss_start[], __bss_end[];
for (char *p = __bss_start; p < __bss_end; p++)
    *p = 0;
/* 再拷贝 .data，最后才跳 main 或内核入口 */

4.10

递归

本节讲什么

函数 直接调用自身（直接递归）或 通过其他函数间接调用自己（间接递归）。写法简洁、贴近分治定义，但每次调用在 程序栈 上占用独立 栈帧；必须有基线终止条件，否则无限递归 → 栈溢出（Stack Overflow）。

前置：4.1 函数、4.3.1 程序内存布局 §6（代码区 vs 栈帧）。

一、递归两大必备组成

组成 作用
基线条件（base case） 递归 终止出口，不再调用自身
递归递推步骤 把问题 缩小 / 向基线推进，逐步分解 
递归 = base case（停） + recursive step（更小的问题）
缺 base case → 无限 call → stack overflow

经典场景：快速排序、树/链表遍历、进制转换、表达式求值、目录树遍历。

二、底层内存执行原理（关联 4.3.1）

  1. 函数 机器指令 在 代码段（.text / 代码区）只有一份，所有递归层 共用同一段机器码；
  2. 每一次 递归调用在 程序栈 分配 独立栈帧，包含： - 当前层 局部变量 - 返回地址（ret 跳回哪） - 寄存器现场、形参副本
  3. 栈是 有限固定大小 内存： - 用户态进程栈通常 几 MB（可 ulimit -s 查看）； - Linux 内核栈 仅 约 8KB（每 CPU 一份），深递归极易崩溃； - 递归深度 ↑ → 栈帧数量 ↑ → 最终 栈溢出。
代码区：printd 的机器码 ── 全程一份
栈区：  printd(123) 栈帧 → printd(12) 栈帧 → printd(1) 栈帧 → 逐层 pop

详见 4.3.1 §6：溢出的是 栈，不是代码区。

三、示例拆解：printd 数字打印（含负号）

K&R 经典：先递归处理 高位，返回时再 putchar 低位，自然得到正序输出。

void printd(int n)
{
    if (n < 0) {           /* 处理负号 */
        putchar('-');
        n = -n;
    }
    if (n / 10)            /* 递推：还有高位 → 继续递归 */
        printd(n / 10);
    putchar(n % 10 + '0'); /* 基线触发后，逐层返回时打印当前位 */
}

调用 printd(123) 的执行流程：

步骤 动作 栈上状态
1 printd(123) → 123/10≠0 → 调 printd(12) 栈帧 1（n=123）
2 printd(12) → 调 printd(1) 栈帧 2（n=12）
3 printd(1) → 1/10=0，基线，打印 '1' 栈帧 3（n=1）
4 返回栈帧 2，打印 '2' pop
5 返回栈帧 1，打印 '3' pop

输出：123。

putchar 在 递推之后 执行，所以数字是 正序 而非逆序；这与「先压栈再弹栈」的 LIFO 语义一致。

四、递归 vs 迭代（工程取舍）

倾向 递归 倾向 迭代（循环）
树、AST、文件系统目录、天然分治（快排、表达式） HFT 热路径、内核调度、嵌入式实时
深度 固定且很小，可读性优先 栈深度 不可控、延迟敏感、硬栈受限
业务层解析、编译器前端 追求 常数开销小、栈占用 恒定

底层开销差异

递归 迭代
每次步骤 call 压栈 + 保存寄存器；ret 弹栈恢复 寄存器运算 + 分支跳转
空间 O(深度) × 栈帧大小 通常 O(1)（或手动栈在堆/静态区）
内核/HFT 8KB 内核栈，危险 首选

深递归替代：手动显式栈

内核/底层 禁止依赖深递归。用 数组模拟栈，数据放在 静态区/堆，不受 8KB 程序栈限制：

/* printd(123) 的迭代版：静态栈存待打印数字，再逆序输出 */
#define STK_SZ 32
void printd_iter(int n)
{
    static int stk[STK_SZ];   /* 静态区，非进程栈 */
    int top = 0;

    if (n < 0) {
        putchar('-');
        n = -n;
    }
    if (n == 0) {
        putchar('0');
        return;
    }
    while (n > 0) {
        stk[top++] = n % 10;
        n /= 10;
    }
    while (top > 0)
        putchar(stk[--top] + '0');
}

这是「递归改循环」的最简形态；树/图遍历则用 stk[] 存 待访问节点指针，逻辑与递归版一一对应。

五、关键考点

1. 复杂度

  • 时间：递归 总调用次数（与递推规模相关）；
  • 空间：最大递归深度 × 单栈帧大小（常被忽略的隐性成本）。

2. 递归 ↔ 循环等价改写

任何递归都可改成 「循环 + 手动栈」，没有 不可替代 的递归逻辑；差别在可读性与栈开销。

3. 尾递归（避坑）

尾递归：递归调用是函数 最后一条 可执行语句，理论上可 复用当前栈帧（尾调用优化 TCO），空间降为 O(1)。

/* 尾递归形式：return 前一步就是递归调用 */
int fact_tail(int n, int acc)
{
    if (n <= 1)
        return acc;
    return fact_tail(n - 1, n * acc);   /* 最后一句话 */
}

⚠️ C 标准不强制 TCO；GCC 在 -O2 下 可能 优化，不保证。生产代码（内核、HFT）绝对不能依赖尾递归，仍按有栈帧开销评估。

代码自测

题目 1： 以下递归函数有什么问题？

int factorial(int n) {
    return n * factorial(n - 1);
}
参考答案

缺少终止条件——无限递归直到栈溢出。必须加基准情况：

int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

递归的三个要素：1) 基准情况（终止条件）；2) 递归调用（向基准情况靠近）；3) 组合结果。栈深度有限（通常几 MB），递归过深会溢出。
