7.1

流模型与 FILE 对象

原 K&R 7.5「文件访问」的前半部分，提前到全章开头。stdio 的核心不是某个函数，而是 FILE 这个对象。

本节讲什么

C 标准 I/O 库（stdio）的核心抽象：FILE 结构体——它封装了文件描述符、缓冲区、读写位置指针、错误/EOF 标志。所有 stdio 函数（getchar、printf、fgets、fread…）都围绕 FILE* 展开。理解了 FILE，后续每一节都是在操作同一个对象的不同方法。

K&R 原书把这部分放在 7.5（文件访问），但 FILE* 是全章基础——getchar 底层操作的就是 stdin（一个 FILE*），printf 底层操作的就是 stdout（另一个 FILE*）。先讲对象，再讲方法，逻辑更清晰。

FILE 结构体

/* <stdio.h> 中的定义（简化，各实现不同） */
typedef struct _iobuf {
    int   fd;          /* 底层文件描述符 */
    char *buf;         /* 缓冲区指针 */
    char *ptr;         /* 当前读写位置 */
    char *end;         /* 缓冲区末尾 */
    int   mode;        /* 读/写模式 */
    int   flags;       /* EOF 标志、错误标志等 */
} FILE;
  • FILE 是不透明类型（opaque type）：标准只要求它能表示流，不暴露内部字段
  • 你永远不直接操作 FILE 的字段，只通过函数（fgetc、fclose…）间接操作
  • 对应的指针 FILE* 才是你实际使用的句柄

三个标准流

程序启动时自动打开三个 FILE*：

#include <stdio.h>

FILE *stdin;    /* 标准输入，fd=0 */
FILE *stdout;   /* 标准输出，fd=1 */
FILE *stderr;   /* 标准错误，fd=2，通常无缓冲 */
  • getchar() 等价于 fgetc(stdin)
  • putchar(c) 等价于 fputc(c, stdout)
  • printf(...) 等价于 fprintf(stdout, ...)

三个流是 3 个独立的 FILE* 对象，各自拥有独立的 buf 缓冲区内存，互不干扰。哪怕 stdout 和 stderr 输出到同一个屏幕，缓冲行为完全分开：

printf("A");           // stdout 行缓冲，无 \n → 留在缓冲区
fprintf(stderr, "B");  // stderr 无缓冲 → 立刻输出 B
printf("\n");          // \n 触发 stdout 刷新 → 输出 A
// 屏幕实际顺序：B A（B 先出来，A 后出来）

程序崩溃（段错误）时：stdout 缓冲区未刷的数据直接丢失；stderr 因为无缓冲，错误信息已经全部交给内核，能完整打印。这就是报错信息写 stderr 的根本原因。

缓冲模式

stdio 在用户态维护缓冲区，减少 read/write 系统调用次数：

模式 宏 刷新触发条件 典型场景
全缓冲 _IOFBF 缓冲区满 / fflush / fclose / 正常退出 磁盘文件、stdout 重定向到文件/管道
行缓冲 _IOLBF 遇 \n / 缓冲区满 / fflush / 从无缓冲流读输入时 终端上的 stdout、stdin
无缓冲 _IONBF 每个字符立即 write stderr

默认分配规则（isatty 判断）

glibc 在 fopen 时用 isatty(fd) 判断流是否连终端，动态决定缓冲模式：

fopen 返回 FILE*
  │
  ├─ isatty(fd)==1 (终端)?
  │    ├─ stdout / stdin → _IOLBF (行缓冲)
  │    └─ stderr        → _IONBF (无缓冲)
  │
  └─ isatty(fd)==0 (文件/管道)?
       └─ → _IOFBF (全缓冲)
流 连终端 重定向到文件/管道
stdin 行缓冲 全缓冲
stdout 行缓冲 全缓冲（最常踩坑）
stderr 无缓冲 无缓冲

关键陷阱：./a.out > log.txt 后 stdout 从行缓冲变成全缓冲，\n 也不再触发刷新。日志"卡住"不是因为程序没输出，而是数据还在用户态缓冲区里。

setvbuf — 手动设置缓冲模式

#include <stdio.h>

int setvbuf(FILE *stream, char *buf, int mode, size_t size);
void setbuf(FILE *stream, char *buf);   /* setvbuf 简化版 */
  • setbuf(fp, buf) ≡ setvbuf(fp, buf, buf ? _IOFBF : _IONBF, BUFSIZ)
  • setbuf(fp, NULL) ≡ setvbuf(fp, NULL, _IONBF, 0)（关闭缓冲）
  • setvbuf(stdout, NULL, _IOLBF, 0) — 强制 stdout 行缓冲（即使重定向）
  • fflush(stdout) — 主动刷新

fflush — 强制刷新缓冲区

int fflush(FILE *stream);
/* fflush(stdout): 刷标准输出 */
/* fflush(NULL):   刷新所有输出流 */
/* fflush(stdin):  未定义行为（C 标准），POSIX 允许但少用 */

fflush 不等换行、不等缓冲区满，立刻把 FILE 缓冲区的数据通过 write(fd) 交给内核。底层过程：

printf("hello")  → 数据写到 stdout 的用户态 buf（libc 内存，无系统调用）
fflush(stdout)   → libc 内部调 write(1, buf, len)，陷入内核，送到外设

经典场景：进度条（\r + fflush，无 \n）

for (int i = 0; i <= 100; i++) {
    printf("\r进度：%d%%", i);   /* \r 回到行首，不换行 */
    fflush(stdout);              /* 必须手动刷，否则全卡缓冲区 */
    usleep(50000);
}
printf("\n");

少写 fflush(stdout) 的话，行缓冲模式下没有 \n，整个循环跑完才一次性输出——进度条完全看不到动态效果。

stderr 无缓冲，不需要 fflush：fprintf(stderr, ...) 每次直接调 write(2, ...)，不经过用户缓冲。

fflush vs fsync 的层次区别：

printf("data") → [stdout 用户 buf]
fflush(stdout) → write(1, ...) → [内核 page cache]     ← fflush 到这里
fsync(fileno(stdout)) → 磁盘                            ← fsync 才落盘

fflush 只保证数据从用户缓冲区到内核，不保证落盘。全缓冲模式下 fflush 同样有效——缓冲模式只影响何时自动刷新，fflush 是手动强制，跨越所有模式。

\n fflush fsync
作用层 行缓冲自动触发 所有模式手动触发 内核→磁盘
全缓冲有效？ ❌（不触发） ✅ ✅
行缓冲有效？ ✅ ✅ ✅
落盘？ ❌ ❌（只到内核） ✅

调用规则： 1. 必须在 fopen 后、任何 fread/fwrite/fprintf 之前调用，否则 UB 2. buf 为 NULL 时库会自己分配缓冲区 3. buf 非 NULL 时，其生命周期必须覆盖 fp 的整个使用期，否则 UB 4. fflush 只对输出流有意义；fflush(stdin) 是未定义行为（C 标准），POSIX 允许但少用 5. 程序正常退出时 exit / return from main 会自动 flush 所有流；_exit 不会

三层抽象

用户空间:
  ┌─────────────────────────────────┐
  │  getchar / printf / fread / …   │  ← C 标准库 (stdio.h)
  │       操作 FILE* (带用户缓冲)    │
  └────────────┬────────────────────┘
               │ fileno(fp) → int fd
               │ fflush() → 刷到内核
               ▼
  ┌─────────────────────────────────┐
  │  read / write / open / close    │  ← Linux 系统调用 (unistd.h)
  │       操作 int fd (无用户缓冲)   │
  └────────────┬────────────────────┘
               │
               ▼
内核空间:    页缓存 (page cache) → 磁盘
  • FILE* 是用户态封装，内核完全不知道这块缓冲区存在
  • int fd 是内核视角，没有用户缓冲
  • fileno(fp) 从 FILE* 取出底层 fd，是两层之间的桥梁
  • 不要混用 fwrite(fp) 和 write(fd) 操作同一个文件——两套缓冲各自独立，数据顺序错乱
#include <stdio.h>
#include <unistd.h>

FILE *fp = fopen("data.txt", "w");
int fd = fileno(fp);    /* 从 FILE* 拿到 fd */

/* 以下两种写法不要混用！ */
fprintf(fp, "via stdio");   /* → 用户缓冲区 */
write(fd, "via syscall", 11); /* → 直接进内核页缓存 */
/* 两者数据顺序不可预测 */

fileno() — 从 FILE* 拿到底层 fd

#include <stdio.h>
int fileno(FILE *stream);     /* FILE* → int fd */
FILE *fdopen(int fd, const char *mode);  /* int fd → FILE* (反方向) */
  • fileno 是向下拆箱：从 C 标准库的 FILE* 取出底层 int fd
  • fdopen 是向上装箱：拿一个已有的 fd 包装成 FILE*（加用户缓冲）
fileno(fp) fdopen(fd, mode)
方向 FILE* → fd fd → FILE*
缓冲 不改变 新建一个用户缓冲区
所有权 fclose(fp) 会关闭 fd fclose(fp) 会关闭 fd
典型用途 对 stdio 流调系统调用 给 open() 返回的 fd 加缓冲

三个标准流的 fileno：

fileno(stdin)   → 0
fileno(stdout)  → 1
fileno(stderr)  → 2

什么时候需要 fileno：系统调用只认 fd，不认 FILE*。

场景 示例
强制落盘 fsync(fileno(fp))
设非阻塞 fcntl(fileno(fp), F_SETFL, O_NONBLOCK)
内存映射 mmap(NULL, len, PROT_READ, MAP_SHARED, fileno(fp), 0)
判断终端 isatty(fileno(stdout))
取文件属性 fstat(fileno(fp), &sb)

混用陷阱：fprintf 走用户缓冲区，write(fileno(fp)) 直接进内核，两者各走各的，数据顺序不可预测。混用前必须 fflush(fp) 同步。

FILE *fp = fopen("log.txt", "w");
fprintf(fp, "AAA");           /* 还在用户 buf 里 */
fflush(fp);                   /* 刷干净 */
write(fileno(fp), "BBB", 3); /* 现在顺序正确 */

详见 TLPI 13.2–13.3（stdio 缓冲与混用陷阱）。

fopen / fclose

打开文件

FILE *fp = fopen("data.txt", "r");
if (fp == NULL) {
    perror("fopen");    /* 打印错误原因 */
    exit(1);
}

打开模式

模式 读 写 位置 文件不存在时
r ✅ ❌ 开头 失败
w ❌ ✅ 开头 创建（清空已有）
a ❌ ✅ 末尾 创建
r+ ✅ ✅ 开头 失败
w+ ✅ ✅ 开头 创建（清空已有）
a+ ✅ ✅ 末尾 创建
  • 加 b（如 rb、wb）= 二进制模式：避免 Windows 文本模式下 \r\n ↔ \n 转换
  • Linux 不区分文本/二进制模式（"r" 和 "rb" 相同），但跨平台代码应始终加 b
  • 失败返回 NULL，必须检查

关闭文件

fclose(fp);    /* 刷新缓冲、释放资源、关闭 fd */
  • 每个 FILE* 占用一个 fd 和内部缓冲；忘记 fclose 会泄漏资源
  • 长期运行的服务进程泄漏 fd 最终触发 EMFILE（too many open files）
  • 多处 return 的函数用 goto cleanup 模式确保关闭

常见陷阱

  1. fopen 返回值未检查直接使用：FILE *fp = fopen("x.txt", "r"); fgets(buf, 100, fp); ——若文件不存在，fp 是 NULL，fgets 对 NULL 解引用即段错误。每次 fopen 必须检查 NULL，出错用 perror 或 strerror(errno) 打印原因。

  2. 忘记 fclose 导致资源泄漏：函数中多处 return 但只在末尾 fclose，提前 return 的路径泄漏。用 goto cleanup 模式或 GCC __attribute__((cleanup))。长期运行的服务进程泄漏 fd 最终触发 EMFILE。

  3. stdout 缓冲导致输出丢失：stdout 在终端是行缓冲，重定向到文件后变全缓冲。程序崩溃时缓冲区未 flush，末尾输出丢失。调试时在关键点 fflush(stdout) 或用 stderr（无缓冲）输出调试信息。

  4. "r" 读二进制文件在 Windows 上提前 EOF：Windows 文本模式把 0x1A（Ctrl-Z）当作 EOF，还会做 \r\n → \n 转换。读二进制文件必须用 "rb"。

自测题

1. 选择：getchar() 底层操作的是哪个 FILE*？ - A. stderr - B. stdin - C. stdout - D. 没有关联的 FILE*

答案

B。getchar() 等价于 fgetc(stdin)，putchar(c) 等价于 fputc(c, stdout)。printf 等价于 fprintf(stdout, ...)。理解了标准流，就明白前面几节的函数都在操作 FILE*——只是隐式使用了 stdin/stdout。

2. 判断：FILE 结构体的内部字段（如 fd、buf）可以直接访问。

答案

错。FILE 是不透明类型，标准不暴露内部字段。不同实现的字段名和布局不同（glibc 的 FILE 和 musl 的完全不同）。你只能通过函数（fgetc、fclose、feof…）间接操作。直接访问 fp->fd 是不可移植的，且可能在未来版本中编译失败。

3. 踩坑：程序输出到终端正常，prog > log.txt 后末尾几行丢失，为什么？

答案

stdout 在终端是行缓冲（遇 \n 自动 flush），重定向到文件后变全缓冲（缓冲区满才 flush）。程序正常退出时 exit 会 flush，但若异常崩溃（如 SIGSEGV、_exit）缓冲区未 flush，末尾输出丢失。修复：关键日志后 fflush(stdout)，或用 stderr（无缓冲）输出调试信息。

4. 应用：写一个安全的 open_file 函数——封装 fopen + 错误检查，失败时打印错误信息并返回 NULL。

答案 
FILE *open_file(const char *path, const char *mode) {
    FILE *fp = fopen(path, mode);
    if (fp == NULL) {
        fprintf(stderr, "cannot open '%s': %s\n",
                path, strerror(errno));
        return NULL;
    }
    return fp;
}
/* 调用：
 * FILE *fp = open_file("config.txt", "r");
 * if (fp == NULL) exit(1);
 * ... 使用 fp ...
 * fclose(fp);
 */

关键：fopen 检查 NULL、strerror(errno) 翻译错误码、错误信息输出到 stderr。这是文件操作的第一原则。

7.2

字符 I/O

本节讲什么

最底层的字符 I/O：getchar() / putchar()，以及 EOF 结束标记。第 1 章已用 getchar 做文件复制；本章系统展开流模型。

要点

  • getchar()：从 stdin 读一个 unsigned char 转为 int 返回；无更多数据时返回 EOF
  • putchar(c)：向 stdout 写一个字符
  • 字符流抽象：终端、管道、文件在 C 标准 I/O 层都是连续字节序列，区别在是否重定向、FILE* 绑定
  • EOF：通常为 -1，表示流结束或错误（需结合 feof/ferror 区分，见 7.5、7.6）
  • getchar/putchar 往往经 stdio 缓冲；fflush(stdout) 在交互提示后常用

示例

#include <stdio.h>

int c;
while ((c = getchar()) != EOF)
    putchar(c);

重定向：prog < in.txt > out.txt —— 程序不变，stdin/stdout 换绑文件。

底层映射

场景 对应
串口字符流 逐字节 read/write，概念同 getchar
UEFI ConOut 类 putchar 输出到 GOP/串口
HFT 日志 热路径少用 stdio，但调试仍靠字符流

常见陷阱

  1. char 类型存 getchar() 返回值：char c; while ((c = getchar()) != EOF) ——若 char 无符号（部分平台），EOF(-1) 被截断为 255，永不等于 -1，死循环；若 char 有符号，0xFF(合法字节)被当成 -1，提前结束。必须用 int 存 getchar 返回值。

为什么返回 int 而不是 char？ getchar 需要返回 257 种不同结果：字节值 0~255（unsigned char 范围）+ EOF（-1）。但 char 只有 8 位，最多表示 256 个值。无论 char 是有符号还是无符号，0xFF 和 -1 中必有一对碰撞。用 int 返回，257 个值轻松装下：0~255 是合法字节，-1 是 EOF，互不歧义。用 char 接收等于亲手制造歧义，把 int 重新塞回 8 位的坑里。

  1. fflush(stdin) 是未定义行为：标准只允许 fflush 输出流（如 stdout）。fflush(stdin) 在某些实现（如旧 VC++）能清输入缓冲，但不可移植。清输入缓冲用 while (getchar() != '\n'); 或 scanf("%*[^\n]"); getchar();。
  2. stdout 缓冲导致输出丢失：stdout 默认行缓冲（终端）或全缓冲（重定向到文件）。程序崩溃时缓冲区未 flush，最后几行输出丢失。调试时在关键点 fflush(stdout) 或 setvbuf(stdout, NULL, _IONBF, 0) 关缓冲。

自测题

1. 选择：getchar() 的返回类型是？ - A. char - B. int - C. unsigned char - D. void

答案

B。getchar() 返回 int——它要能表示所有 unsigned char 值（0–255）外加 EOF（通常 -1）。用 char 接收会丢失区分：0xFF 的合法字节和 EOF 都可能变成 -1。这是 K&R 反复强调的经典坑。

2. 判断：fflush(stdin) 可以清空输入缓冲区。

答案

错（标准层面）。C 标准只定义 fflush 用于输出/更新流，fflush(stdin) 是未定义行为。部分编译器（如 MSVC）作为扩展支持，但不可移植。可移植做法：int c; while ((c = getchar()) != '\n' && c != EOF); 清到行尾。

3. 踩坑：程序输出到终端正常，重定向到文件 prog > log.txt 后末尾几行丢失，为什么？

答案

stdout 在终端是行缓冲（遇 \n 自动 flush），重定向到文件后变全缓冲（缓冲区满才 flush，默认 4KB/8KB）。程序正常退出时 exit 会 flush，但若异常崩溃（如 SIGSEGV、_exit）缓冲区未 flush，末尾输出丢失。修复：关键日志后 fflush(stdout)，或用 stderr（无缓冲）输出调试信息。

4. 应用：写一个统计输入行数的程序，正确处理 EOF 和 char 类型陷阱。

答案 
#include <stdio.h>

int main(void) {
    int c;          /* 必须 int，不是 char */
    long lines = 0;
    while ((c = getchar()) != EOF) {
        if (c == '\n')
            lines++;
    }
    printf("%ld lines\n", lines);
    return 0;
}

关键点：int c（不是 char）、!= EOF 判断、%ld 匹配 long。这是 K&R 1.5 的经典例题。

ungetc：字符推回

ungetc(c, fp) 把字符 c 推回输入流，下次读会先读到它。实现「读多看一、再退回」的 parser 必备。

要点

  • 每个流通常只允许少量推回（常 1 个，实现定义）
  • 成功返回 c；失败返回 EOF
  • 与 fgetc/getchar 配合：试探下一字符，若非预期则 ungetc
int c = fgetc(fp);
if (c == '/')
    c = fgetc(fp);   // 看第二个字符
else {
    ungetc(c, fp);   // 不是 '/'，退回让上层处理
    /* 按其它规则处理 */
}

陷阱

  1. 只保证推回一个字符：ungetc('a', fp); ungetc('b', fp); — 标准只保证至少一个，第二个不保证成功。需要多字符 lookahead 时自己维护回退缓冲区。
  2. 推回的字符不必是之前读到的：ungetc('z', fp) 可以推回任意字符，不只是刚读的。可用作 parser「插入虚拟字符」，但也容易误用。
  3. fseek/rewind/fsetpos 会丢弃推回的字符：任何改变文件位置的操作都清除 ungetc 的推回缓冲区。
  4. ungetc 影响 ftell：推回后 ftell 返回值减一，反映逻辑位置后退。

自测题

1. 以下代码连续推回两个字符，可靠吗？

ungetc('a', stdin);
ungetc('b', stdin);  // 先读到 'b' 还是 'a'？
答案

不可靠。标准只保证至少能推回一个字符。如果实现支持多个，以 LIFO 顺序返回（先读 'b' 再读 'a'）。某些实现只保留最后一个，'a' 被丢弃。需要多字符 lookahead 应自建回退缓冲区。

2. fseek(fp, 100, SEEK_SET); fgetc(fp); ungetc('x', fp); 之后 ftell(fp) 返回多少？

答案

返回 100。fgetc 前进到 101，ungetc 后退到 100。ftell 考虑推回字符，返回逻辑位置。

3. 设计一个「读两个字符判断是否是 // 注释」的函数，如果不是就退回。

答案 
int is_comment(FILE *fp) {
    int c1 = fgetc(fp);
    if (c1 != '/') {
        if (c1 != EOF) ungetc(c1, fp);
        return 0;
    }
    int c2 = fgetc(fp);
    if (c2 != '/') {
        if (c2 != EOF) ungetc(c2, fp);
        ungetc(c1, fp);   // 退回第一个 '/' 也要退回！
        return 0;
    }
    return 1;  // 确认是 //
}

关键：不是注释时要逆序退回所有读到的字符。注意检查 EOF——ungetc(EOF, fp) 行为未定义。

EOF 的两种含义：feof vs ferror

EOF 返回后无法直接区分是读到文件末尾还是I/O 出错。需要两个函数进一步判断：

函数 返回真表示 典型场景
feof(fp) 真的读到流末尾 文件读完、管道对端关闭
ferror(fp) 流发生 I/O 错误 磁盘故障、网络断开 
int c;
while ((c = getchar()) != EOF) {
    putchar(c);
}
/* 循环退出后区分原因 */
if (ferror(stdin)) {
    fprintf(stderr, "I/O error occurred\n");
} else if (feof(stdin)) {
    /* 正常读完，无需额外处理 */
}

交互场景：fflush(stdout) + getchar

stdin/stdout 终端模式默认行缓冲。打印提示不带 \n 时，提示文字卡在 stdout 缓冲区，用户看不到：

/* ❌ 错误：提示不显示 */
printf("请输入：");        /* 没有 \n，卡在缓冲区 */
int c = getchar();         /* 用户不知道要输入什么 */

/* ✅ 正确：手动刷新 */
printf("请输入：");
fflush(stdout);            /* 强制刷 stdout，提示立刻显示 */
int c = getchar();         /* 用户看到提示后输入 */

7.3

行 I/O

本节讲什么

fgets/fputs 按行读写文本；gets 已废弃。安全读配置、日志行、协议文本行的首选 stdio 方式。

要点

fgets

char line[256];
if (fgets(line, sizeof line, fp) != NULL) {
    /* line 含内容，可能含 '\n' */
}
  • 最多读 size-1 个字符，保留 '\0'
  • 遇 '\n' 或 EOF 停止；超长行保留 \n 并截断
  • 返回值：NULL 表示 EOF 且无数据读入，或出错

fputs

fputs(line, fp);   /* 不自动追加换行 */
  • 与 fputs(str, stdout) 输出一行（若 str 已含 \n）

避免 gets

  • gets(buf) 无长度限制 → 永远不要用
  • 替代：fgets 或 POSIX getline

示例：读配置

while (fgets(line, sizeof line, cfg) != NULL) {
    if (line[0] == '#' || line[0] == '\n')
        continue;
    /* sscanf 或手工解析 */
}

与后续衔接

文本协议「一行一条」；二进制 tick 用 7.6 fread。嵌入式配置文件、串口 AT 指令行常用 fgets 模式。

常见陷阱

  1. fgets 保留 \n，忘记去除行尾换行：fgets(buf, 100, fp) 读入的行包含 \n（如果缓冲够大）。直接用 strcmp(buf, "quit") 比较会失败——因为 buf 是 "quit\n" 而非 "quit"。修复：buf[strcspn(buf, "\n")] = '\0'; 去掉换行。或者用 strcmp(buf, "quit\n") 但不通用。

  2. 超长行被 fgets 截断但无错误指示：fgets(buf, 10, fp) 读一个 100 字符的行——只读 9 个字符（+\0），返回非 NULL（成功），但行未读完。下次 fgets 继续读同一行的剩余部分。如果不检查 fgets 是否读到了 \n，可能把一行误当成多行。检查：if (strchr(buf, '\n') == NULL) { /* 行被截断，需继续读 */ }。

  3. fputs 不加换行，输出连成一行：fputs("hello", fp); fputs("world", fp); 输出 helloworld。与 puts（自动加 \n）不同，fputs 原样输出不加换行。如果需要每行一个 \n，必须手动 fputs("hello\n", fp) 或 fputc('\n', fp)。这是 puts 和 fputs 的关键区别。

自测题

1. 选择：fgets(buf, 10, fp) 读一个 50 字符的行，返回值和 buf 内容是？ - A. 返回 NULL，buf 未修改 - B. 返回 buf，buf 含 9 个字符 + \0（不含 \n） - C. 返回 buf，buf 含 50 个字符 - D. 返回 NULL，buf 含 9 个字符

答案

B。fgets 最多读 size-1（=9）个字符。50 字符的行只读前 9 个，buf = "123456789\0"（无 \n），返回值是 buf（非 NULL，表示成功读取）。剩余 41 字节留在流中，下次 fgets 继续读。检查 buf 是否含 \n 可以判断一行是否读完：if (strchr(buf, '\n') == NULL) { /* 行被截断 */ }。

2. 判断：puts(str) 和 fputs(str, stdout) 完全等价。

答案

错。puts(str) 在输出字符串后自动追加 \n，fputs(str, stdout) 不加换行。puts("hi") 输出 hi\n，fputs("hi", stdout) 输出 hi。如果需要换行，fputs 要手动加。另外 puts 只能输出到 stdout，fputs 可以输出到任意 FILE*。实践中推荐用 fputs + 手动 \n，行为更明确。

3. 踩坑：以下代码比较用户输入与 "quit"，但永远不匹配，为什么？

char input[100];
fgets(input, sizeof input, stdin);
if (strcmp(input, "quit") == 0)
    break;
答案

fgets 保留行尾 \n，所以 input 是 "quit\n" 而非 "quit"，strcmp 不等。修复：input[strcspn(input, "\n")] = '\0'; 去掉换行后再比较。strcspn(input, "\n") 返回 \n 在 input 中的位置（如果有的话），将其替换为 \0。这是处理 fgets 输入的标准套路。

4. 应用：写一个 read_line 函数——用 fgets 安全读取一行，自动去除 \n，处理超长行（丢弃超出部分），返回行长度。

答案 
int read_line(FILE *fp, char *buf, int size) {
    if (fgets(buf, size, fp) == NULL)
        return -1;  /* EOF 或出错 */

    int len = strlen(buf);
    if (len > 0 && buf[len-1] == '\n') {
        buf[len-1] = '\0';   /* 去掉换行 */
        return len - 1;
    }

    /* 行被截断（buf 满了但无 \n），丢弃剩余 */
    if (len == size - 1) {
        int c;
        while ((c = fgetc(fp)) != '\n' && c != EOF)
            ;
    }
    return len;
}

关键：fgets 返回值检查、\n 去除、超长行处理（读取并丢弃剩余字符直到 \n 或 EOF）。这是文本处理的基础工具函数。

7.4

格式化输出 printf

本节讲什么

printf 按格式串把各类型转为文本输出；fprintf 写到指定 FILE*，sprintf/snprintf 写到内存缓冲。日志、调试、配置生成的基础。

要点

常用转换说明符

符 类型
%d %i int
%u %o %x %X unsigned / 八进制 / 十六进制
%c char
%s 字符串
%f %e %g float/double
%p 指针（实现定义格式，常十六进制）
%% 字面 %

修饰

  • 宽度 / 精度：%8d、%.2f、%-10s（左对齐）
  • 长度修饰：%ld、%zu、%llx 等
  • 返回值：成功输出的字符数；出错返回负值

文件与内存变体

fprintf(stderr, "error: %s\n", msg);
fprintf(fp, "%d\n", n);

char buf[64];
snprintf(buf, sizeof buf, "tick=%lld", tick);  /* 推荐：有边界 */

考点

  • sprintf 无边界 → 缓冲区溢出；现代代码用 snprintf
  • 格式与实参类型不匹配 → 未定义行为
  • HFT 热路径避免 printf（锁 + 格式化开销），用预分配缓冲或二进制日志

常见陷阱

  1. 格式说明符与实参类型不匹配是 UB：printf("%d", 3.14)（double 用 %d）、printf("%s", 42)（int 用 %s）——编译器可能不报警告（变参无类型检查），运行时读到垃圾值甚至崩溃。64 位系统上 printf("%d", 1LL) 把 long long 当 int 读，高位/低位错位。用 -Wformat 编译选项让 GCC/Clang 检查。
  2. sprintf 缓冲区溢出：sprintf(buf, "...", data) 无边界检查，输出超过 buf 大小就栈溢出。现代代码一律用 snprintf(buf, sizeof buf, ...)，它的返回值是"本应写入的字符数"（可能大于 size，说明被截断）。
  3. %n 格式符是安全漏洞：printf("%n", &n) 会把已输出字符数写入 n 指向的内存——攻击者通过构造格式串可写任意地址。现代编译器（GCC/Clang）默认禁用 %n 支持。日志函数若接受用户输入作为格式串，用 printf("%s", user_input) 而非 printf(user_input)。

自测题

1. 选择：printf("%d\n", 3.14) 的行为是？ - A. 输出 3 - B. 输出 3.14 - C. 未定义行为，可能输出垃圾值 - D. 编译错误

答案

C。%d 期望 int，传入 double（8 字节）。变参函数不做类型检查，printf 按 int（4 字节）读 double 的低位字节，得到垃圾值。64 位系统上更混乱（寄存器传参规则不同）。开 -Wformat 编译选项可让编译器静态检查并报错。

2. 判断：snprintf(buf, 64, "x") 的返回值是 1（实际写入的字符数）。

答案

对（返回 1）。但注意 snprintf 的返回值是"本应写入的字符数"（不含 \0），不一定等于实际写入数。若返回值 ≥ 64，说明输出被截断。这个语义让调用方能判断是否需要更大缓冲——是 snprintf 比 sprintf 安全且有用的原因。

3. 踩坑：日志函数 void log_msg(char *fmt) 里直接 printf(fmt)，用户传入 %s%s%s%s 导致崩溃，为什么？

答案

这是格式串漏洞。printf(fmt) 把 fmt 当格式串，%s 会从栈上读指针参数——但没传任何参数，读到的是栈上的垃圾地址，解引用即崩溃（SIGSEGV）。攻击者可构造 %n 写任意内存。修复：printf("%s", fmt)——把 fmt 当普通字符串输出，不做格式解析。规则：永远不要把外部输入直接作为 printf 的格式串。

4. 应用：用 snprintf 安全拼接 "tick=12345 level=INFO msg=hello" 到 64 字节缓冲，并检查是否被截断。

答案 
char buf[64];
int n = snprintf(buf, sizeof buf, "tick=%d level=%s msg=%s",
                 12345, "INFO", "hello");
if (n < 0) {
    perror("snprintf");        /* 编码错误 */
} else if ((size_t)n >= sizeof buf) {
    /* 输出被截断，n 是本应写入的长度 */
    fprintf(stderr, "log truncated, need %d bytes\n", n);
}

关键：检查返回值，n >= sizeof buf 说明截断。这是安全日志拼接的标准模式。

7.5

格式化输入 scanf

本节讲什么

scanf 按格式从 stdin 解析并写入变量；fscanf 对文件，sscanf 对内存字符串。与 printf 对称，但更易出错。

要点

  • 除 %s %[] 等外，实参必须是指针：scanf("%d", &n);
  • 数组名已是地址：scanf("%s", buf) 无需 &buf
  • 返回值：成功匹配并赋值的项数；EOF 表示在读入前即结束
  • 空白：格式串中的空白匹配任意空白；%d 等前也会跳过 leading 空白

常用格式

符 含义
%d int
%f %lf float / double
%s 无空白字符串（无长度上限，危险）
%c 字符（不跳过空白，常需 " %c"）
%x 十六进制

变体

fscanf(fp, "%d %s", &n, name);
sscanf(pkt, "MD:%lf", &price);   /* 报文内解析，无磁盘 IO */

考点

  • %s 溢出 → 用 %63s 限宽或改用 fgets + 解析
  • 与 printf 类型不匹配 → UB
  • 留字符在流中未读 → 下次 scanf 行为诡异

常见陷阱

  1. %s 无长度限制导致溢出：scanf("%s", buf) 遇到超长输入直接写越界——和 gets 一样是经典安全漏洞。用 %63s（限 63 字符，留 1 给 \0）或改用 fgets(buf, sizeof buf, stdin) 再解析。
  2. 忘记传指针，传了值：scanf("%d", n) 而非 scanf("%d", &n)——把 n 的值当地址写入，轻则段错误，重则写穿内存。数组名已是地址（scanf("%s", buf) 无需 &），这是唯一例外。编译器开 -Wformat 可静态检查。
  3. %c 不跳过空白，读到遗留换行：scanf("%d", &n); scanf("%c", &c); ——第二个 scanf 读到的是第一个遗留的 \n 而非用户输入。修复：格式串加空格 scanf(" %c", &c)（空格匹配任意空白）。

自测题

1. 选择：scanf("%d %d", &a, &b) 输入 "10 20\n"，返回值是？ - A. 0 - B. 1 - C. 2 - D. EOF

答案

C。scanf 返回成功匹配并赋值的项数，这里 a=10、b=20 都成功，返回 2。若输入 "10 x\n"，a=10 成功但 b 匹配 int 失败，返回 1。检查返回值是健壮输入的必备——不能假设用户一定输入正确。

2. 判断：scanf("%s", buf) 是安全的输入方式。

答案

错。%s 无长度限制，遇到超长输入直接越界写——和 gets 一样是缓冲区溢出的经典来源。安全写法：scanf("%63s", buf)（限 63 字符）或 fgets(buf, sizeof buf, stdin)。C11 的 scanf_s 强制传缓冲大小，但可移植性差。

3. 踩坑：scanf("%d", &n); scanf("%c", &c); 输入 5\nx，c 的值是 '\n' 而非 'x'，为什么？

答案

%d 读 5 后停下，\n 留在输入流。%c 不跳过前导空白（和 %d/%s 不同），直接读走那个 \n，于是 c = '\n'。修复：scanf(" %c", &c)——格式串里的空格匹配任意空白（包括 \n、空格、Tab），跳过后再读真正的字符。这是 %c 最常见的坑。

4. 应用：用 sscanf 从 "MD:123.45" 解析出 double 价格，并检查是否成功。

答案 
const char *pkt = "MD:123.45";
double price;
int matched = sscanf(pkt, "MD:%lf", &price);
if (matched == 1) {
    printf("price = %f\n", price);   /* 123.450000 */
} else {
    fprintf(stderr, "parse failed\n");
}

关键：%lf 匹配 double（scanf 里 double 用 %lf，和 printf 的 %f 不同！）、检查返回值。sscanf 不做磁盘 IO，适合解析内存中的报文/配置字符串。

与后续衔接

HFT 简单文本协议可用 sscanf；二进制行情应用 fread + struct（7.6）而非 scanf。

7.6

二进制 I/O 与文件定位

原 K&R 7.5「文件访问」的后半部分。字符 I/O 和格式化 I/O 都是文本导向的；本节讲字节块读写和随机访问。

本节讲什么

fread/fwrite 按字节块读写——不受换行、编码影响，适合二进制数据（struct、数组、镜像）；fseek/ftell/rewind 在文件中随机定位——读取 ELF 头、跳转 tick 文件偏移的基础。

二进制块读写

fread / fwrite

size_t fread(void *ptr, size_t size, size_t nmemb, FILE *fp);
size_t fwrite(const void *ptr, size_t size, size_t nmemb, FILE *fp);
  • ptr：数据缓冲区
  • size：每个元素的字节数（如 sizeof(struct Record)）
  • nmemb：元素个数
  • 返回值：成功读写的元素数（不是字节数！）
/* 写一个 struct 到文件 */
struct Header { int magic; int version; int count; };
struct Header hdr = { 0x4D44, 1, 42 };
fwrite(&hdr, sizeof(hdr), 1, fp);

/* 从文件读 N 个 double */
double prices[100];
size_t got = fread(prices, sizeof(double), 100, fp);
/* got 可能 < 100（文件不够长或出错） */

返回值检查

size_t n = fread(buf, sizeof(buf[0]), count, fp);
if (n < count) {
    if (feof(fp))
        printf("读到 EOF，只读了 %zu 个\n", n);
    else if (ferror(fp))
        perror("fread 出错");
}
  • fread 返回值 < nmemb 时，用 feof/ferror 区分原因
  • 不要在读之前检查 feof——它是"事后"标志

struct 整块读写的跨平台风险

struct Record { int id; char name[8]; };

/* 机器 A 写入 */
fwrite(&r, sizeof(r), 1, fp);

/* 机器 B 读出 */
fread(&r, sizeof(r), 1, fp);   /* 可能得到错误数据！ */
风险 说明
padding struct Record 大小因对齐而异（可能 12 或 16 字节）
字节序 int id = 42 在小端机存 2A 00 00 00，大端机存 00 00 00 2A
类型宽度 int 在不同平台可能 2/4/8 字节

教训： struct 整块 fwrite/fread 不可移植。跨平台需用定宽类型（uint32_t）+ 手动序列化。

文件定位

fseek / ftell / rewind

long pos = ftell(fp);                    /* 当前位置 */
fseek(fp, offset, SEEK_SET);             /* 绝对定位 */
fseek(fp, 0L, SEEK_END);                 /* 跳到末尾 */
fseek(fp, -sizeof(hdr), SEEK_CUR);       /* 回退一个元素 */
rewind(fp);                              /* 等价 fseek(fp, 0L, SEEK_SET) + clearerr */
起点 宏 含义
文件开头 SEEK_SET offset 从 0 开始
当前位置 SEEK_CUR offset 可正可负
文件末尾 SEEK_END offset 通常为负

大文件：fseeko / ftello

/* POSIX，使用 off_t（32/64 位取决于编译选项） */
off_t pos = ftello(fp);
fseeko(fp, (off_t)offset, SEEK_SET);
  • ftell 返回 long，在 32 位系统上最大 2GB
  • 大文件用 fseeko/ftello（POSIX），或 fseeko64（glibc 扩展）
  • 在 _FILE_OFFSET_BITS=64 编译时，off_t 自动为 64 位

获取文件大小

fseek(fp, 0, SEEK_END);
long size = ftell(fp);
fseek(fp, 0, SEEK_SET);   /* 复位 */

常见陷阱

  1. fread 返回值是元素数不是字节数：fread(buf, 8, 10, fp) 返回最多 10（不是 80）。如果只读了 7 个完整元素，返回 7——可能第 8 个元素只读了一半，buf 中的剩余字节是未定义的。检查返回值，不要假设读满了。

  2. fseek 后忘记 ftell 的 long 限制：在 32 位系统上 long 是 4 字节，ftell 对 > 2GB 的文件返回 -1（错误）。大文件必须用 ftello/fseeko（off_t 类型）。或在 64 位系统上直接用 stat 获取文件大小。

  3. struct padding 导致读写不一致：同一程序在同一机器上读写没问题，但跨编译器/跨平台时 struct 大小可能不同（对齐选项不同）。用 __attribute__((packed)) 消除 padding 但降低性能，或手动序列化每个字段。

  4. feof 的误用——在读之前检查 feof：while (!feof(fp)) { fread(...); process(); } ——feof 只在读操作到达 EOF 后才返回真，不能预判。正确写法：while (fread(buf, size, 1, fp) == 1) { process(buf); }——用返回值判断。

自测题

1. 选择：fwrite(&hdr, sizeof(hdr), 1, fp) 返回 0，最可能的原因是？ - A. 内存不足 - B. 磁盘满或写入出错 - C. hdr 为空 - D. sizeof(hdr) 为 0

答案

B。fwrite 返回成功写入的元素数。请求写 1 个元素返回 0，说明写入失败——通常是磁盘满或 I/O 错误。应检查 ferror(fp) 确认。注意：如果请求写 10 个元素，只成功写了 7 个，返回 7——部分成功也算。

2. 判断：同一程序在同一机器上 fwrite 写入的 struct，用 fread 读回一定正确。

答案

对（在同一机器同一编译器下）。只要编译选项不变（如 -m32/-m64、对齐选项），struct 大小和布局一致，读写匹配。风险在于跨平台：不同编译器的 padding 不同、字节序不同、类型宽度不同。跨平台数据交换必须手动序列化。

3. 踩坑：用 fseek(fp, 0, SEEK_END); long sz = ftell(fp); 获取文件大小，但对一个 3GB 的文件返回 -1，为什么？

答案

32 位系统上 long 是 4 字节，最大表示 2^31-1 ≈ 2.1GB。3GB 超出 long 范围，ftell 返回 -1 表示错误。修复：用 ftello（返回 off_t，在 _FILE_OFFSET_BITS=64 时为 64 位），或用 stat/fstat 获取文件大小（st_size 是 off_t 类型）。64 位系统上 long 通常是 8 字节，问题较少。

4. 应用：写一个函数，用 fread 读取二进制文件中的 struct Tick 数组，返回实际读取的个数。

答案 
struct Tick { uint32_t ts; uint32_t symbol; double price; int32_t qty; };

size_t read_ticks(const char *path, struct Tick *buf, size_t max) {
    FILE *fp = fopen(path, "rb");
    if (!fp) { perror("fopen"); return 0; }

    size_t got = fread(buf, sizeof(struct Tick), max, fp);

    if (got < max) {
        if (ferror(fp))
            perror("fread");
        /* feof 是正常情况——文件读完 */
    }
    fclose(fp);
    return got;
}

关键："rb" 二进制模式、fread 返回元素数、ferror 区分错误和正常 EOF、fclose 释放资源。这是二进制数据读取的标准框架。

7.7

错误处理

本节讲什么

stderr 标准错误流与 stdout 分离；exit 终止进程；ferror/clearerr 管理流错误。日志分级与调试输出的基础。

要点

stderr

fprintf(stderr, "fatal: cannot open %s\n", path);
  • 通常无缓冲或行缓冲，错误信息及时可见
  • 可重定向：prog 2> err.log（stdout 仍走 1）
  • 正常结果走 stdout，诊断走 stderr —— grep、管道不误吞错误

exit

#include <stdlib.h>
exit(0);    /* 成功 */
exit(1);    /* 失败，返回给 shell */
  • 调用 atexit 注册的函数，刷新 stdio 缓冲
  • 与 return from main 等价于 exit(返回值)

流错误

  • 读写出错后 ferror(fp) 为真
  • clearerr(fp) 清除错误与 EOF 标志以便重试
  • 不要仅用 getchar() == EOF 判断错误类型

底层场景

场景 做法
UEFI 固件调试 错误码 + 串口/屏幕 Print
HFT 分级日志：trade → 文件，error → stderr
工具链 编译器 diagnostic 走 stderr

与后续衔接

第 8 章 perror 把 errno 转成字符串；系统调用失败常 perror("read") 写 stderr。

常见陷阱

  1. exit vs _exit 的区别被忽略：exit 刷新 stdio 缓冲、调用 atexit 注册的函数。_exit（POSIX）直接陷入内核，不刷新缓冲。fork 后子进程若用 exit，父进程的 stdio 缓冲被复制后再次刷新——同一输出写两遍。子进程应用 _exit（或 exec 后自然替换）。vfork 后尤其要注意。

  2. stderr 缓冲策略假设：标准说 stderr 默认不缓冲（unbuffered），但某些实现是行缓冲。如果你的错误信息没有 \n 结尾，行缓冲的实现可能延迟输出。关键路径上用 fflush(stderr) 确保立即输出，或写到底层 write(2, msg, len) 绕过 stdio。

  3. errno 不是清零的——只在出错后查：errno 只在库函数返回错误时被设置，成功调用不会清零。模式 errno = 0; x = strtoul(s, NULL, 0); if (errno != 0) error(); 是正确用法。if (errno) error(); 不行——之前的调用可能设了 errno 而本次成功。perror/ferror 也同理：先确认操作失败再查 errno。

自测题

1. 选择：exit(1) 和 _exit(1) 的关键区别是？ - A. 没有区别 - B. exit 刷新 stdio 缓冲并调用 atexit，_exit 不做 - C. _exit 刷新缓冲，exit 不做 - D. exit 给父进程发信号，_exit 不发

答案

B。exit 是 C 标准库函数：调用 atexit 注册的清理函数、刷新所有 stdio 缓冲、关闭 stdio 流，然后调用 _exit。_exit 是 POSIX 系统调用：直接陷入内核，不刷新任何用户态缓冲。fork 后子进程用 exit 会导致父进程 stdio 缓冲被复制后重复刷新——同一输出写两遍。子进程应用 _exit 或直接 exec。

2. 判断：errno 在成功的函数调用后会被自动清零。

答案

错。C 标准规定 errno 只在出错时被设置，成功调用不会清零。因此 if (errno) ... 在之前有错误发生时会误判。正确用法：调用前手动 errno = 0;，调用后检查返回值是否出错，出错时再查 errno。只有 strtol/strtoul 等少数函数要求这样做（因为它们返回的合法值可能与错误返回值重叠）。

3. 踩坑：程序崩溃（SIGSEGV）后，最后几行 fprintf(stderr, ...) 的输出丢失了，为什么？

答案

即使 stderr 默认无缓冲，某些实现仍是行缓冲。如果最后的 fprintf 没有 \n 结尾，行缓冲的输出未 flush 就被信号杀死。更严重的是：如果错误信息写到了 stdout（被重定向到文件，全缓冲），崩溃时缓冲区未 flush，末尾输出丢失。修复：1) 调试信息用 fprintf(stderr, ...) 加 \n；2) 关键路径 fflush(stdout)；3) 信号处理函数中只能调用异步信号安全函数（write 可以，printf 不行）。

4. 应用：写一个 die(const char *fmt, ...) 函数——输出到 stderr 并 exit(1)，要求带格式化输出和 errno 翻译。

答案 
#include <stdarg.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>

void die(const char *fmt, ...) {
    va_list ap;
    va_start(ap, fmt);
    fprintf(stderr, "fatal: ");
    vfprintf(stderr, fmt, ap);
    va_end(ap);
    if (errno)
        fprintf(stderr, ": %s", strerror(errno));
    fprintf(stderr, "\n");
    exit(1);
}
/* 调用：die("cannot open %s", path); */
/* 输出：fatal: cannot open config.txt: No such file or directory */

关键：vfprintf 封装变参、strerror(errno) 翻译错误码、最后 exit(1)。很多 CLI 工具（如 git 源码）都有类似的 die/usage 函数。

7.9

变长参数表（附录）

本节讲什么

printf(format, ...) 的 ... 表示变参；<stdarg.h> 提供 va_list / va_start / va_arg / va_end，用于实现或封装自定义格式化函数。

要点

#include <stdarg.h>

void warn(char *fmt, ...)
{
    va_list ap;
    va_start(ap, fmt);   /* fmt 为最后一个固定参数 */
    vfprintf(stderr, fmt, ap);
    va_end(ap);
}
  • va_start(ap, last_fixed)：last_fixed 必须是 ... 前最后一个具名参数
  • va_arg(ap, type)：按 type 取下一个实参（类型必须正确）
  • va_end(ap)：清理
  • C99 另有 va_copy

设计约束

  • 变参函数无法从 ... 自动得知参数个数 → 靠 format 串（如 printf）或约定
  • 封装日志时常用：log(level, fmt, ...) 内部 vfprintf

常见陷阱

  1. va_arg 类型必须与实参一致，且 float 提升为 double：传 float 参数时，默认参数提升把它变成 double，必须用 va_arg(ap, double) 而非 va_arg(ap, float)。同理 char/short 提升为 int。类型不匹配读到的是错位数据。
  2. 无法从 ... 自动得知参数个数：变参函数没有任何机制知道传了几个参数。printf 靠格式串里的 % 个数推断；如果调用者少传参数，va_arg 越界读栈垃圾。必须靠约定（format 串、哨兵值如 NULL 结尾、显式 count 参数）。
  3. 忘记 va_end 或 va_start 参数错：va_start(ap, last_fixed) 的 last_fixed 必须是 ... 前最后一个具名参数，写错会导致未定义行为。va_end 某些实现里做了资源清理（如栈指针恢复），不调可能栈异常。配对使用：va_start → va_arg → va_end。

自测题

1. 选择：va_start(ap, x) 中 x 必须是什么？ - A. 任意变量 - B. ... 前最后一个具名参数 - C. 第一个参数 - D. 参数个数

答案

B。va_start 需要知道 ... 前最后一个具名参数的地址，以此推算变参在栈/寄存器上的起始位置。写错参数名会导致 va_arg 读到错位数据。C99 起部分编译器支持 va_start(ap) 省略参数名，但为可移植性仍建议显式写。

2. 判断：变参函数可以自动知道 ... 里有几个参数。

答案

错。C 的变参机制无法从 ... 本身得知参数个数或类型。必须靠外部约定：printf 用格式串的 % 数量、execl 用 NULL 哨兵结尾、自定义函数常加 count 参数。少传参数时 va_arg 越界读栈——UB，可能崩溃或读到垃圾。

3. 踩坑：void f(int n, ...) { va_list ap; va_start(ap, n); double d = va_arg(ap, float); }，调用 f(1, 3.14)，d 的值不对，为什么？

答案

float 参数在变参函数中会默认提升为 double（default argument promotion）。调用 f(1, 3.14) 实际传入的是 double（8 字节），但 va_arg(ap, float) 按 float（4 字节）读，只读到一半数据。修复：用 va_arg(ap, double)。同理，char/short 提升为 int，要用 va_arg(ap, int)。

4. 应用：写一个 my_log(int level, const char *fmt, ...)，用 vfprintf 输出到 stderr，前面加 level 标签。

答案 
#include <stdarg.h>
#include <stdio.h>

void my_log(int level, const char *fmt, ...) {
    const char *tag[] = {"DEBUG", "INFO", "WARN", "ERROR"};
    fprintf(stderr, "[%s] ", tag[level & 3]);
    va_list ap;
    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
    fprintf(stderr, "\n");
}

/* 调用：my_log(1, "tick=%d price=%f", 12345, 3.14); */

关键：vfprintf 接受 va_list 而非 ...，是封装变参日志的标准手法。内核 printk、glibc syslog 都是这个模式。
