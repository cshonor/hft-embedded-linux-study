# 1.1 C 语言标准、编译器与 gnu11 方言

> **CH1 收官篇。** 前面 1.2–1.7 讲的每一个扩展，都建立在同一个前提上：**你在用哪种方言写代码**。
> 这一节把「标准 C」和「GNU C」的边界划清楚——它是整章的地基，也是最容易想当然的地方。

[← 返回 CH1 首页](../README.md) · [1.2 指定初始化](../1.2-designated-init/1.2-指定初始化.md) · [1.3 语句表达式](../1.3-statement-expr/1.3-宏构造-利器-语句表达式.md)

## 本节讲什么

C 语言有**三层东西**，混在一起谈就会吵架：

| 层 | 是谁 | 干什么 |
|----|------|--------|
| **标准** | ISO/IEC 9899 | 规定「可移植子集」：C89 / C99 / C11 / C17 / C23 |
| **编译器** | GCC / Clang | 实现标准，并额外提供**扩展** |
| **方言** | `-std=` 选项 | 决定「标准 + 哪几项扩展」生效 |

读 Linux 内核、U-Boot、DPDK 之前必须分清这三层。本节全部结论均来自 **WSL 实测**（gcc 13.3 / clang 18.1.3），demo 脚本在 `D:\.kernel-ref\demo-std\`（`run.sh` ~ `run6.sh`）。

## 一、`-std=cXX` 与 `-std=gnuXX` 的唯一分界：`__STRICT_ANSI__`

这是本节最该记住的一个宏。实测十个 `-std` 取值：

| `-std=` | `__STDC_VERSION__` | `__STRICT_ANSI__` | `__GNUC_STDC_INLINE__` |
|---------|-------------------|-------------------|------------------------|
| `c89`   | 未定义            | **1**             | 未定义（gnu89 inline 语义） |
| `c99`   | 199901            | **1**             | 1（C99 inline 语义） |
| `c11`   | 201112            | **1**             | 1 |
| `c17`   | 201710            | **1**             | 1 |
| `c2x`   | **202000**（gcc13）/ **202311**（clang18） | **1** | 1 |
| `gnu89` | 未定义            | 未定义            | 未定义（gnu89 inline 语义） |
| `gnu99` | 199901            | 未定义            | 1 |
| `gnu11` | 201112            | 未定义            | 1 |
| `gnu17` | 201710            | 未定义            | 1 |
| `gnu2x` | 202000 / 202311   | 未定义            | 1 |

三条推论：

1. **`__STRICT_ANSI__` 是判断方言的权威依据**，比看 `-std=` 字符串可靠得多。写条件编译就查它。
2. **`__STDC_VERSION__` 在 C89/gnu89 下根本未定义**。`#if __STDC_VERSION__ >= 199901L` 在 gnu89 下会被预处理成 `#if 0 >= 199901L`（未定义标识符视为 0），**静默走错分支**。正确写法是先 `#ifdef`。
3. **`__GNUC_STDC_INLINE__` 只在 C99 及以后定义**——这正好是 [1.6 inline](../1.6-inline/1.6-内联函数.md) 那节实测出的「C99 / gnu89 语义完全反转」在预处理器层面的开关。看到它没定义，就知道 `inline` 走的是 gnu89 语义。

**编译器默认方言**：gcc 13 和 clang 18 **都默认是 `gnu17`**（`__STDC_VERSION__=201710`、`__STRICT_ANSI__` 未定义）。也就是说，**不写 `-std=` 时你一直在用 GNU 方言**。

> ⚠️ **「gcc 和 clang 的默认方言是 `gnu11`」是过时说法。** 官方手册逐版对照：
>
> | 手册版本 | `'gnu11'` 条目的说明 | `'gnu17'` 条目的说明 |
> |---|---|---|
> | GCC 7.5.0 | GNU dialect of ISO C11. **This is the default for C code.** | （该版手册尚无 `gnu17` 条目） |
> | GCC 8.5.0 | GNU dialect of ISO C11.（**已删去默认句**） | GNU dialect of ISO C17. **This is the default for C code.** |
> | GCC 13.3.0 | GNU dialect of ISO C11. | GNU dialect of ISO C17. **This is the default for C code.** |
>
> 即**默认方言自 GCC 8 起由 `gnu11` 换成 `gnu17`**——对应 GCC 提交 `c76dc9c`，其 commit message 原话是
> *（new default version, replacing `-std=gnu11` as the default）*。clang 侧未找到等价的官方版本宣告，
> 但 CE 端 clang 18.1.3 实测结论与 gcc 完全一致（见下表）。
>
> CE 实测（`d_default_std.c`，不加任何 `-std=`，公共参数 `-O0 -Wall -Wextra`）：
>
> | 编译器 | `__STDC_VERSION__` | `__STRICT_ANSI__` | 结论 |
> |---|---|---|---|
> | gcc 13.3 | `201710L` | 未定义 | **gnu17** |
> | clang 18.1.3 | `201710L` | 未定义 | **gnu17** |
> | gcc 13.3 + 显式 `-std=gnu11` | `201112L` | 未定义 | 对照组：只有显式指定才是 gnu11 |
>
> 冻结日志：`D:\.kernel-ref\std_probe\log_pedantic.txt` 第 1–22 行。
> 实用推论：**内核 `Makefile` 里那句 `-std=gnu11` 不是「跟默认一样所以多余」**——它是在明确钉住方言，防止编译器默认值变化。

## 二、最大的误解：严格模式其实没关掉多少扩展

「`-std=c99` = 禁用所有 GNU 扩展」——这是流传最广的错误认知。实测十项内核惯用法：

| 内核惯用法 | `gcc -std=c11` | `gcc -std=gnu11` |
|-----------|----------------|------------------|
| `container_of`（裸 `typeof` + 语句表达式） | ❌ 2 个 error | ✅ |
| 裸 `asm` 关键字 | ❌ 2 个 error | ✅ |
| `case 1 ... 5` 范围 | ✅ | ✅ |
| `__attribute__((section(...)))` | ✅ | ✅ |
| 零长度数组 `char data[0]` | ✅ | ✅ |
| `##__VA_ARGS__` 变参宏 | ✅ | ✅ |
| `__builtin_expect`（likely/unlikely） | ✅ | ✅ |
| `&&label` 标号取地址 | ✅ | ✅ |
| `__int128` | ✅ | ✅ |
| 匿名 `union`（C11 标准特性） | ✅ | ✅ |

**十项里只有两项真的需要 GNU 方言。** 其余八项在 `-std=c11` 严格模式下畅通无阻。

### 为什么？

ISO C 把**双下划线开头的标识符全部保留给实现**。所以 `__attribute__`、`__typeof__`、`__asm__`、`__builtin_*`、`__int128` 这些形态，在任何方言下都是「合法使用保留字」，标准管不着。

> ⚠️ **补丁（CE 复核，2026-09-21）**：这句话对**方言**成立，对 `-pedantic` **不完全**成立 ——
> `-std=c17 -pedantic-errors` 下 `__attribute__` / `__typeof__` / `__asm__` / `__builtin_*` 全部 **0 诊断**，
> 但 **`__int128` 照样报 3 个 `error: ISO C does not support '__int128' types`**。
> 上表里 `__int128` 那两行 `✅` 是**不开 `-pedantic`** 时的结论。细节见「日志三」。

真正被关掉的，是**不带下划线的关键字形态**：`typeof`、`asm`、`inline`（语义变化）。

## 三、真正卡死内核的只有两个裸关键字

实测把这两个换成双下划线形式会怎样：

| 写法 | `c11` | `c17` | `c2x` | `gnu11` | clang `c11` |
|------|-------|-------|-------|---------|-------------|
| `container_of` 用裸 `typeof` | ❌ | ❌ | **✅** | ✅ | ❌（7 个 error） |
| `container_of` 用 `__typeof__` | **✅** | **✅** | ✅ | ✅ | **✅** |
| 裸 `asm` | ❌ | ❌ | ❌ | ✅ | ❌ |
| `__asm__` | **✅** | **✅** | ✅ | ✅ | **✅** |

三条硬结论：

1. **`container_of` 换成 `__typeof__` 后，`-std=c11` 也能编过。** 内核用裸 `typeof` 不是技术必需，是历史习惯（缓存里 `include/linux/compiler.h:158` 的 `extern typeof(sym) sym;`、`:169` 的 `(typeof(ptr))` 都是裸形态）。
2. **`asm` 在 C23 里也没转正**——`c2x` 下依然报错。它永远只能是 GNU 扩展。
3. **`typeof` 在 C23 转正了**：`-std=c2x` 下裸 `typeof` gcc/clang 双双通过，且 `-pedantic-errors` 下也干净。

于是得到一个反直觉的结论：

> **内核需要 `gnu11` 的真正原因，是它不肯给 `typeof` 和 `asm` 加下划线。**
> 把内核最核心的五个惯用法（container_of / section / 零长数组 / case range / 变参宏）全改成双下划线形态后，`-std=c11`、`-std=c17`、`-std=c2x` 在 gcc 和 clang 上**全部编得过**——只是 `-pedantic` 会唠叨 3 条语法糖警告。

这说明 GNU 方言的价值不在「开启扩展」（扩展在严格模式下大多还在），而在**让关键字的裸形态可用**。

## 四、比「关掉扩展」更常见的翻车：`-std=c99` 连 POSIX 一起关了

这是实战中最容易踩的一条，和 GNU 扩展无关：

```c
#include <string.h>
char *p = strdup("hello");     /* POSIX，不是 ISO C */
```

| 编译命令 | 结果 |
|---------|------|
| `gcc -std=c99` / `-std=c11` / `-std=c17` | ⚠️ **implicit declaration of function 'strdup'** |
| `gcc -std=gnu99` / `-std=gnu11` / `-std=gnu17` | ✅ 零警告 |
| `gcc -std=c11 -D_GNU_SOURCE` | ✅ 零警告 |
| 源码里 `#define _GNU_SOURCE`（在所有 `#include` 之前） | ✅ 零警告 |

机制：glibc 的 `features.h` 看到 `__STRICT_ANSI__` 就不默认打开 `_DEFAULT_SOURCE`，于是 POSIX / GNU 的函数声明被隐藏。

> 后果有多严重？隐式声明的返回类型按 `int` 猜。**在 64 位平台上，`strdup` 返回的指针被截断成 32 位 `int` 再转回指针**——高位全丢，直接段错误。这是 `-std=c99` 最经典的翻车姿势。

**推论：项目用 `-std=cXX` 时，必须显式 `-D_GNU_SOURCE`（或在每个 .c 第一行 `#define _GNU_SOURCE`）。** 反过来，用 `-std=gnuXX` 就已经隐式打开了。

### 顺带：隐式函数声明在各标准下的诊断等级

| `-std=` | gcc 13 的诊断 |
|---------|--------------|
| `c89` / `gnu89` | **无诊断**（C89 允许隐式声明） |
| `c99` 及以后 | ⚠️ warning（C99 已移除该特性，但 gcc 13 仍只警告） |

> gcc 14 起才升级为 error。**不要依赖它报错**——项目里应该主动加 `-Werror=implicit-function-declaration`（实测能把 warning 变成 error）。

## 五、标准演进矩阵：`-pedantic-errors` 下的真实可用性

gcc 13，同一份代码在五个标准下的表现（`OK` = 连 `-pedantic-errors` 都干净；`warn` = 能过但有诊断；`X` = 硬错误）：

| 特性 | c89 | c99 | c11 | c17 | c2x |
|------|-----|-----|-----|-----|-----|
| `//` 行注释 | **X** | OK | OK | OK | OK |
| 混合声明（语句后声明变量） | warn | OK | OK | OK | OK |
| `long long` | warn | OK | OK | OK | OK |
| VLA 变长数组 | warn | OK | OK | OK | OK |
| 指定初始化 | warn | OK | OK | OK | OK |
| 复合字面量 | warn | OK | OK | OK | OK |
| `_Static_assert` | warn | warn | OK | OK | OK |
| `<stdbool.h>` | OK | OK | OK | OK | OK |
| `__typeof__` | OK | OK | OK | OK | OK |
| **trigraph 三字符组** | OK | OK | OK | OK | **X** |
| K&R 老式函数定义 | OK | OK | OK | OK | **warn** |

两个值得单独说的：

- **`//` 注释在 C89 是硬错误**，不是警告。写要兼容老编译器的代码时注意。
- **trigraph 在 C23 被彻底移除**（`??!` 这类三字符组）。`c2x` 下 `a ??!??! 0` 直接报错。C17 及以前都还能用。
- **K&R 老式定义 `int add(a,b) int a; int b;` 在 C23 起只是警告**（gcc 13），但 C23 已经把它移除出标准。

### C23 带来的和带走的

| 方向 | 内容 | 实测 |
|------|------|------|
| **带来** | `bool` / `true` / `false` 成为关键字（不用 `<stdbool.h>`） | c2x 通过，c17 `unknown type name 'bool'` |
| **带来** | `static_assert` 关键字（不用 `_Static_assert`） | c2x 通过 |
| **带来** | 二进制字面量 `0b1010`、数字分隔符 `1'000'000` | c2x 通过 |
| **带来** | **`typeof` 转正**（`typeof` / `typeof_unqual`） | c2x 下 `-pedantic-errors` 也干净 |
| **带来** | 标准属性语法 `[[gnu::packed]]` | 见下节 |
| **带走** | trigraph 三字符组 | c2x 硬错误 |
| **带走** | K&R 老式函数定义 | c2x 警告 |
| **语义变更** | `int f()` 从「参数未指定」变成「等于 `int f(void)`」 | `f(1,2,3)` 在 c17 通过、c2x 报 `number of arguments doesn't match prototype` |

> **C23 的 `[[gnu::packed]]` 是个编译器分歧点**：gcc 在 `-std=c17` 下**直接报语法错误**（`expected ']' before ':' token`），必须 `c2x` 或 `gnu17` 才接受；而 **clang 在 `-std=c17` 下就接受**（作为扩展）。写跨编译器代码时，老老实实用 `__attribute__((packed))`。

## 六、`-pedantic` 与 `__extension__`：什么能压，什么压不住

`-pedantic` 的作用是「对非 ISO 语法发诊断」，`-pedantic-errors` 则把 **base standard 要求**的诊断升级为错误。
其中 **base standard** 四个字是整个 `-pedantic` 家族的判定依据——本节把它讲透。

> ⚠️ **口径说明**：下表是**早期的 WSL 探针**（另一份源文件，同一份代码里既有裸 `typeof` 又有裸 `asm`），
> 所以 error 主要来自那两个裸关键字。6.2 起改用 CE 冻结日志里的 `p1_strict.c`（五样**语法扩展**、无裸关键字），
> **两组数字不同源、不可互相比较**。下表保留，是为了说明「裸关键字」这一类的行为。

| 命令 | error | warning |
|------|-------|---------|
| `-std=gnu11`（无） | 0 | 0 |
| `-std=gnu11 -pedantic` | 0 | **2** |
| `-std=gnu11 -pedantic-errors` | **2** | 0 |
| `-std=c11`（无） | **2**（typeof 不可用） | 1 |
| `-std=c11 -pedantic-errors` | **5** | 0 |

这张表里已经藏着两条反直觉的事：第 2 行说明 **`-pedantic` 在 GNU 方言下一样出声**（`-std=gnu11` 默认 0 诊断，加 `-pedantic` 出 2 条）；
第 4 行与第 5 行对比说明 **`-pedantic-errors` 的覆盖面比 `-pedantic` 更宽**——`-std=c11` 下本来只有 2 error + 1 warning，
换成 `-pedantic-errors` 变成 **5 error**，多出来的 3 条就是 **base standard 要求、但不由 `-Wpedantic` 控制**的必需诊断。
下面逐条给官方依据。

### 6.1 三个拼写，一个选项

GCC 手册 §3.9 Warning Options 把 `-Wpedantic` / `-pedantic` / `--pedantic` **列在同一条目下**，即三者完全等价：

> `-Wpedantic`
>
> `-pedantic`
>
> Issue all the warnings demanded by strict ISO C and ISO C++; reject all programs that use forbidden extensions, and some other programs that do not follow ISO C and ISO C++. For ISO C, follows the version of the ISO C standard specified by any `-std` option used.
>
> Valid ISO C and ISO C++ programs should compile properly with or without this option (though a rare few require `-ansi` or a `-std` option specifying the required version of ISO C). However, without this option, certain GNU extensions and traditional C and C++ features are supported as well. With this option, they are rejected.
>
> —— GCC 13.3.0 手册 §3.9 Warning Options（[在线原文](https://gcc.gnu.org/onlinedocs/gcc-13.3.0/gcc/Warning-Options.html)）

CE 实测等价性（同一份 `p1_strict.c`，同为 `-std=c17`）：

| 写法 | 诊断 |
|---|---|
| `-Wall -Wextra -std=c17 -pedantic` | 4 warning |
| `-Wall -Wextra -std=c17 -Wpedantic` | **逐字相同的 4 warning** |

所以「`-pedantic` 和 `-Wpedantic` 有区别」是伪命题。

### 6.2 核心机理：它认的是 base standard，不是 `__STRICT_ANSI__`

这是本节**最反直觉、也最重要**的一条。手册原文（同一条目）：

> Where the standard specified with `-std` represents a GNU extended dialect of C, such as '`gnu90`' or '`gnu99`', there is a corresponding *base standard*, the version of ISO C on which the GNU extended dialect is based. **Warnings from `-Wpedantic` are given where they are required by the base standard.** (It does not make sense for such warnings to be given only for features not in the specified GNU C dialect, since by definition the GNU dialects of C include all features the compiler supports with the given option, and there would be nothing to warn about.)

翻译成可操作的结论：**`-std=gnu11` 的 base standard 就是 C11**，所以 `-std=gnu11 -pedantic` 的唠叨范围与 `-std=c11 -pedantic` **完全一样**。

CE 实测（同一份 `p1_strict.c`，六组命令，`-O0 -Wall -Wextra` 为公共前缀）：

| 附加参数 | warning | 说明 |
|---|---|---|
| `-pedantic`（**不写 `-std=`**） | 4 | 默认方言 `gnu17`，base standard = C17 |
| `-std=gnu17 -pedantic` | 4 | 同上 |
| `-std=c17 -pedantic` | **4** | 同上 |
| `-std=c17 -Wpedantic` | **4** | 同上 |
| `-std=gnu17`（无 pedantic） | **0** | —— |
| `-std=c17`（无 pedantic） | **0** | —— |

四组带 `-pedantic` / `-Wpedantic` 的输出**逐字相同**（连行号、`[-Wpedantic]` 后缀、`note:` 行都一致）：

```text
$ gcc -O0 -Wall -Wextra -std=c17 -pedantic ./p1_strict.c
<source>:12:24: warning: ISO C forbids zero-size array 'data' [-Wpedantic]
<source>:18:5: warning: range expressions in switch statements are non-standard [-Wpedantic]
<source>:19:5: warning: range expressions in switch statements are non-standard [-Wpedantic]
<source>:28:20: warning: ISO C forbids braced-groups within expressions [-Wpedantic]
<source>:55:43: note: in expansion of macro 'MAX'
# build code = 0
```

> ⚠️ **由此推翻一个常见说法**：「`-pedantic` 单独用（不带 `-std=cXX`）**意义不大**、警告会很多」。
> 实测三组配法（不写 `-std=` / `-std=gnu17` / `-std=c17`）诊断**逐字相同**，都是 4 条。
> 原因就是上面那段原文：`-pedantic` 看的是 **base standard**，而 `gnu17` 的 base standard 恰好是 C17；
> 它**与 `__STRICT_ANSI__` 是否定义无关**。**`-pedantic` 单独用不但有意义，而且与 `-std=c17 -pedantic` 等价。**

### 6.3 `-pedantic-errors` 的覆盖面比 `-pedantic` 更大

手册里 `-pedantic-errors` 是**独立条目**，不是 `-Wpedantic` 的附属。

GCC 13.3.0（与 CE 用的编译器同版）：

> `-pedantic-errors`
>
> Give an error whenever the *base standard* (see `-Wpedantic`) requires a diagnostic, in some cases where there is undefined behavior at compile-time and in some other cases that do not prevent compilation of programs that are valid according to the standard. **This is not equivalent to `-Werror=pedantic`**, since there are errors enabled by this option and not enabled by the latter and vice versa.

GCC 14.3.0 起把话说得更直白（这段 13.3 里还没有）：

> This is not equivalent to `-Werror=pedantic`: **the latter option is unlikely to be useful, as it only makes errors of the diagnostics that are controlled by `-Wpedantic`, whereas this option also affects required diagnostics that are always enabled or controlled by options other than `-Wpedantic`.**
>
> If you want the required diagnostics that are warnings by default to be errors instead, but don't also want to enable the `-Wpedantic` diagnostics, you can specify `-pedantic-errors -Wno-pedantic` …

两个方向都有差集（13.3 的 "and vice versa"），所以**「`-pedantic` 与 `-pedantic-errors` 检测范围相同、只是等级不同」是错的**——后者的诊断集合**严格更大**。

具体到最有用的那个问题「**能不能用 `-Werror` 卡住 GNU 扩展**」，CE 实测（`a_range.c`，全文核心就一行 `int a[10] = {[0 ... 3] = 1};`）：

| 命令 | 结果 |
|---|---|
| `gcc -std=gnu11 -Wall -Wextra ./a_range.c` | 0 诊断，通过 |
| `gcc -std=gnu11 -Wall -Wextra -pedantic ./a_range.c` | 1 warning，通过 |
| `gcc -std=gnu11 -Wall -Wextra -Werror ./a_range.c` | **0 诊断，通过** ❌ 抓不到 |
| `gcc -std=c11 -Wall -Wextra -Werror ./a_range.c` | **0 诊断，通过** ❌ 也抓不到 |
| `gcc -std=gnu11 -Wall -Wextra -pedantic-errors ./a_range.c` | **1 error，`build code = 1`** ✅ |

```text
$ gcc -std=gnu11 -Wall -Wextra -pedantic-errors ./a_range.c
<source>:2:16: error: ISO C forbids specifying range of elements to initialize [-Wpedantic]
# build code = 1
$ clang -std=gnu11 -Wall -Wextra -pedantic-errors ./a_range.c
<source>:2:16: error: use of GNU array range extension [-Werror,-Wgnu-designator]
# build code = 1
```

**为什么 `-Werror` 抓不到？** 因为 GNU 扩展在 gnu 方言下**根本不产生警告**——`-Werror` 只是把「已发出的警告」升级为错误，没有警告就无从升级。所以想卡住 GNU 扩展，**只能上 `-pedantic-errors`**。

> ⚠️ **顺带推翻第二条说法**：「`-pedantic-errors` **通常配合 `-std=c11`**」。
> 上表第 5 行就是 `-std=gnu11 -pedantic-errors`，**照样把范围语法拦成硬错误**。
> **`-pedantic-errors` 可以配任何 `-std=`**——它认的还是 base standard（`gnu11` 的 = C11）。
> 「方言放开、标准收紧」这个组合是刻意可用的：GNU 的汇编 / 链接层扩展照用，ISO **语法层**的越界一律拒绝。

### 6.4 三条豁免通道：系统头、`__` 包裹、`__extension__`

手册在 `-Wpedantic` 条目里明说了三种「合法逃逸」：

> `-Wpedantic` does not cause warning messages for use of the alternate keywords whose names begin and end with '`__`'. This alternate format can also be used to disable warnings for non-ISO '`__intN`' types, i.e. '`__intN__`'. Pedantic warnings are also disabled in the expression that follows `__extension__`. **However, only system header files should use these escape routes; application programs should avoid them.**

逐条落到实测：

| 通道 | 形态 | 实测（`-std=c17 -pedantic-errors`，gcc 13.3） |
|---|---|---|
| 双下划线包裹**关键字** | `__typeof__` / `__asm__` / `__attribute__` / `__builtin_*` | ✅ 0 诊断（日志三） |
| 双下划线包裹**类型名** | `__int128__`（注意是**包住**，不是 `__int128`） | ✅ gcc 0 诊断；**clang 报 `unknown type name`**（日志四 ④） |
| `__extension__` 前缀 | `__extension__ ({ ... })` | ✅ 压掉语句表达式警告 |
| **不在这三条里** | 裸 `asm` / 裸 `typeof` | ❌ 硬错误 |
| **不在这三条里** | `__int128`（不带尾巴下划线） | ❌ `error: ISO C does not support '__int128' types` |

> **第三条通道是「应用代码不该用」的**——手册原话 *application programs should avoid them*。
> 原因是 `__extension__` 会把后面整段表达式交给编译器按 GNU 扩展处理，等于**关掉了那一段的全部 pedantic 检查**；
> 而第二、三条通道都只为「写系统头」准备。跨编译器可移植的代码，正确做法是**只用第一条**（写 `__typeof__` 这类双下划线关键字形态），
> 而不是靠 `__extension__` 去打补丁。

### 6.5 `__extension__` 的边界（实测）

| 场景 | 不加 | 加 `__extension__` |
|------|------|--------------------|
| 语句表达式，`-std=c99 -pedantic` | 1 warning | **0 warning** ✅ |
| `typeof`，`-std=c11` | error | **仍然 error** ❌ |

> **`__extension__` 只能压 warning，压不住 error。**
> 它能压的是「语法合法但非 ISO」的场景（语句表达式、long long）；`typeof` 在 c11 下是 `unknown type name`（硬错误），加多少 `__extension__` 都没用——这时候该做的是换成 `__typeof__`。

## 七、编译器分歧：gcc 13 vs clang 18

| 项目 | gcc 13.3 | clang 18.1.3 |
|------|----------|--------------|
| 默认方言 | `gnu17` | `gnu17` |
| `-std=c2x` 的 `__STDC_VERSION__` | **202000**（C2x 草案期值） | **202311**（正式 C23 值） |
| `[[gnu::packed]]` 在 `-std=c17` | ❌ 语法错误 | ✅ 接受 |
| `__GNUC__` 值 | 13 | **4**（clang 伪装成 gcc 4，兼容老代码） |
| 递归 `always_inline` | 硬 error | **静默降级**（见 [1.6](../1.6-inline/1.6-内联函数.md)） |
| `-std=c17 -pedantic` 对同一份 `p1_strict.c` 的诊断 | **4 warning** | **5 warning**（多一条 `##__VA_ARGS__`） |
| 同上换成 `-pedantic-errors` | **4 error** | **5 error** |

**`__STDC_VERSION__` 那条最坑**：写 `#if __STDC_VERSION__ >= 202311L` 判断 C23，在 gcc 13 的 `-std=c2x` 下**不成立**（因为它是 202000）。要判断 C23 就别用这个宏，或写成 `>= 202000L`。

**`__GNUC__ = 4` 那条**：clang 为了兼容「`#if __GNUC__ >= 3`」这类老判断，把自己伪装成 gcc 4。所以**识别编译器必须先查 `__clang__` 再查 `__GNUC__`**（clang 也定义 `__GNUC__`）。

**表末两行（`-pedantic` 覆盖度）也值得单说**：同一份 `p1_strict.c`，gcc 报 **4 warning**、clang 报 **5 warning**——
多出来的那条是 `token pasting of ',' and __VA_ARGS__ is a GNU extension [-Wgnu-zero-variadic-macro-arguments]`，
指向 [1.7 变参宏](../1.7-vararg-macro/1.7-可变参数宏.md) 里的 `##__VA_ARGS__`；gcc 对它**一言不发**。
也就是说：**「加 `-pedantic` 之后还剩几条扩展告警」本身就是编译器相关的**，
写可移植代码时别只在一台编译器上验证就收工。

## 八、内核为什么是 `gnu11`

缓存的 v6.x `Makefile` 里：

```makefile
KBUILD_CFLAGS += -std=gnu11        # Makefile:560
KBUILD_CFLAGS += -fshort-wchar
KBUILD_CFLAGS += -funsigned-char
KBUILD_CFLAGS += -fno-common       # 见 CH2 的 weak 那节
KBUILD_CFLAGS += -fno-strict-aliasing
```

三个要点：

1. **是 `gnu11` 不是 `c11`**——原因见第三节：只有两个裸关键字需要它。
2. **v5.18 之前是 `gnu89`**。这与 [1.2 指定初始化](../1.2-designated-init/1.2-指定初始化.md) 里那条实测直接相关，但**因果要写准**——指定初始化（`.member = value`）是 C99 特性，在 C90 模式下 GNU 把它当**扩展**提供，**默认静默可用**（GCC 手册原文：*GNU C allows this as an extension in C90 mode as well*），只有加 `-pedantic` 才警告。**所以「5.18 前的驱动里没有 `.member = value`」不能归因于方言禁止**——硬证据是 Linux **v3.10**（当时正是 `gnu89`）的 `drivers/char/mem.c` 里 **8 处 `file_operations` 初始化全部已经写成 `.member = value`**。真正的解释是**代码风格与维护者偏好**，不是编译不过。
3. **方言切换会连锁影响 inline 语义**。gnu89 → gnu11 意味着 `__GNUC_STDC_INLINE__` 从「未定义」变成「已定义」，`inline` 的链接语义整个反过来。这也是 [1.6](../1.6-inline/1.6-内联函数.md) 那节强调「读老内核要切方言脑模式」的原因。

## 九、可移植写法实战：一份在 12 种组合下全过的头文件

把本节所有结论攒成一个可直接抄的 `port.h`（实测 gcc/clang × c99/c11/c17/c2x/gnu11/gnu17 **12 组全部通过**）：

```c
#ifndef PORT_H
#define PORT_H

/* 1. 编译器识别：先 clang 后 gcc（clang 也定义 __GNUC__ = 4） */
#if defined(__clang__)
#  define COMP_CLANG  1
#  define COMP_GCC    0
#elif defined(__GNUC__)
#  define COMP_CLANG  0
#  define COMP_GCC    1
#else
#  define COMP_CLANG  0
#  define COMP_GCC    0
#endif

/* 2. 方言识别：__STRICT_ANSI__ 是 cXX 与 gnuXX 的唯一分界 */
#if defined(__STRICT_ANSI__)
#  define DIALECT_GNU 0
#else
#  define DIALECT_GNU 1
#endif

/* 3. typeof：C23 起是标准关键字，之前一律用双下划线形态 */
#if defined(__STDC_VERSION__) && __STDC_VERSION__ > 201710L
#  define my_typeof(x)   typeof(x)
#elif COMP_GCC || COMP_CLANG
#  define my_typeof(x)   __typeof__(x)   /* 严格方言下也能用 */
#else
#  error "no typeof support"
#endif

/* 4. 内联汇编：永远用双下划线，别用裸 asm */
#define my_barrier()  __asm__ __volatile__("" ::: "memory")

/* 5. 分支预测：双下划线内建，任何方言都可用 */
#define likely(x)     __builtin_expect(!!(x), 1)
#define unlikely(x)   __builtin_expect(!!(x), 0)

#endif /* PORT_H */
```

**这套写法的核心原则只有一条：优先用双下划线形态。** 双下划线形态在所有方言、所有编译器下都可用；裸形态（typeof / asm / inline）才需要挑方言。

网上流传最广的那篇「`__STRICT_ANSI__` 就是区分 ANSI C 和 GNU C 的宏」讲对了主线（分界宏确实是它、
`__STDC_VERSION__` 在 gnu89 下确实不存在），但**在推论上错了三处**，而且错的方向很危险——
它会让你以为「严格模式不能用 `__attribute__`」，于是在必须用 `-std=cXX` 的项目里绕远路去改方言。

### 官方原文（唯一依据）

GCC 手册 **6.12.23 Alternate Keywords**：

> `-ansi` and the various `-std` options disable certain keywords that are GNU C extensions.
> **Specifically, the keywords `asm`, `typeof` and `inline` are not available** in programs compiled
> with `-ansi` or a `-std=` option specifying an ISO standard that doesn't define the keyword.

注意 `-std=` 关掉的**只有这三个词**，而且手册紧接着给出的解法就是「给关键字前后各加 `__`」：

> The way to solve these problems is to put '`__`' at the beginning and end of each problematical
> keyword. For example, use `__asm__` instead of `asm`, and `__inline__` instead of `inline`.

**`__attribute__` 不在这个名单里**——它本来就是双下划线形态（GCC 手册 6.4.3 称它是
"the older GNU extension syntax using the `__attribute__` keyword"），落在 ISO C 保留给实现的
标识符空间内，任何方言下都合法。

### 逐条判定

| 网传说法 | 判定 | 实测 / 依据 |
|---|---|---|
| `-std=cXX` 定义 `__STRICT_ANSI__=1`，`-std=gnuXX` 不定义 | ✅ 对 | 本页第一节十行表 |
| `__STDC_VERSION__` 在 C89 / gnu89 下没有定义 | ✅ 对 | CE：`-std=gnu89` 下 `是否已定义 = 0` |
| `__GNUC_STDC_INLINE__` 控制 inline 语义（C99 vs GNU） | ✅ 对 | CE：`-std=gnu89` 未定义 / `-std=c17` = 1，与 [1.6](../1.6-inline/1.6-内联函数.md) 一致 |
| `typeof` 在严格模式不能用 | ⚠️ 半个对 | 裸 `typeof` ❌ 硬错误；**`__typeof__` ✅**（本页第三节） |
| **`__attribute__` 在 `__STRICT_ANSI__` 下不能用** | ❌ **错** | CE：`-std=c17` 下 `diagnostics = 0`；`sizeof(struct A) = 5`（packed 已生效） |
| 零长数组 / `case 1 ... 5` 在严格模式不能用 | ❌ 错 | CE：`-std=c17` 下平平通过；**只有加 `-pedantic-errors` 才升级为错误** |
| `#if __STDC_VERSION__ >= 199901L` 在 gnu89 下会**预处理报错** | ❌ **错** | CE：`diagnostics = 0`，**静默走 `#else`**；只有 `-Wundef` 才出声 |
| 「小测验：`-std=c17` 能不能用 `__attribute__((packed))`？答：不能」 | ❌ **错** | 同上，实测能用 |

**第二轮（编译器命令行写法对照表）追加：**

| 网传说法 | 判定 | 实测 / 依据 |
|---|---|---|
| 「`-std=c11` 严格按 ISO C11 编译，**禁用 GNU 扩展**」 | ⚠️ **只在两个裸关键字上成立** | CE：`-std=c17` 下 packed / 零长数组 / `case 1 ... 5` / `##__VA_ARGS__` / 语句表达式**全部 0 诊断**；只有裸 `typeof` / 裸 `asm` 报错（本页第二节、第三节） |
| 「`-std=gnu11` 是 **gcc 和 clang 的默认方言**」 | ❌ **过时** | CE：不写 `-std=` 时 gcc 13.3 与 clang 18.1.3 **双双报 `201710L`（`gnu17`）**；显式加 `-std=gnu11` 才变 `201112L` |
| 「`-pedantic` 单独用（不带 `-std=c11`）**意义不大**、警告会很多」 | ❌ **错** | CE：不写 `-std=` / `-std=gnu17` / `-std=c17` 三种配法下的 `-pedantic` 输出**逐字相同**（均 4 warning） |
| 「`-pedantic` 与 `-Wpedantic` 是两个有区别的选项」 | ❌ **错** | 手册把 `-Wpedantic` / `-pedantic` / `--pedantic` 列在**同一条目**；CE：两者输出逐字相同 |
| 「`-pedantic` 会检测『使用 GNU 扩展的写法』」 | ⚠️ **要精确化** | 手册原文：只对 **base standard 要求诊断**的那些出声（forbidden extensions + 少数其他），**不是全量 GNU 扩展检测器** |
| 「`-pedantic` 与 `-pedantic-errors` **检测范围相同**，只是等级不同」 | ❌ **错** | GCC 14.3 起手册说得更直白：*this option also affects required diagnostics that are **always enabled or controlled by options other than `-Wpedantic`*** —— 范围严格更大 |
| 「`-pedantic-errors` 等价于 `-Werror -pedantic`（或 `-Werror=pedantic`）」 | ❌ **错** | 手册明写 *This is not equivalent to `-Werror=pedantic`*；CE 旁证：`-std=gnu11 -Werror` 对 `[0 ... 3]` **0 诊断** |
| 「`-pedantic-errors` **通常配合 `-std=c11`**」 | ⚠️ **不必** | CE：`-std=gnu11 -pedantic-errors` 照样把范围语法拦成硬 error，`build code = 1`。**可配任何 `-std=`** |
| 「`gnu11` 最宽松……代码可能依赖 GNU 扩展而不跨编译器可移植」 | ✅ 对 | 但**要补一句**：真正卡移植的只有裸 `typeof` / 裸 `asm`；且 gcc / clang 对同一份扩展代码的诊断条数并不一致（本页第七节） |

### CE 复核日志一：五样「扩展」塞进一份 `-std=c17` 的代码

源码要点：`struct __attribute__((packed)) A { char c; int i; };`、零长数组 `char data[0]`、
`case 1 ... 5`、`##__VA_ARGS__` 变参宏、`({ __typeof__(a) ... })` 语句表达式。

```text
$ gcc -std=c17 -Wall -Wextra ./p1_strict.c && ./a.out
__STDC_VERSION__     = 201710L
__STRICT_ANSI__      = 1
__GNUC_STDC_INLINE__ = 1
sizeof(struct A)     = 5   (packed 生效则应 = 5)
sizeof(struct B)     = 4   (零长数组不占空间)
range(3) = 1..5   range(9) = 6..9   range(99) = other
LOG 变参宏            = 42
MAX(3, 7)            = 7
```

`build code = 0` / `didExecute = True` / **`diagnostics = 0`** —— 一条诊断都没有。

再把诊断旋钮拧到最紧，`gcc -std=c17 -Wall -Wextra -pedantic-errors`，`diagnostics = 17`：

```text
<source>:12:24: error: ISO C forbids zero-size array 'data' [-Wpedantic]
<source>:18:5:  error: range expressions in switch statements are non-standard [-Wpedantic]
<source>:19:5:  error: range expressions in switch statements are non-standard [-Wpedantic]
<source>:28:20: error: ISO C forbids braced-groups within expressions [-Wpedantic]
```

17 条（含 `note:` 行）**没有一条**指向 `struct __attribute__((packed)) A`。

> 两者的区别是**性质**不同：`__attribute__` 落在「保留标识符」空间里，是**合法**用法，
> 任何旋钮都挑不出毛病；零长数组 / case 范围 / 语句表达式是「语法合法但**非 ISO**」，
> 平时放行，`-pedantic` 才唠叨。

对照：**裸形态**在 `-std=c17` 下是硬错误（`build code = 1`，`diagnostics = 25`）：

```text
<source>:15:5: error: 'asm' undeclared (first use in this function)
<source>:9:21: error: expected declaration specifiers or '...' before '(' token
```

`asm` 报的是「未声明的标识符」——严格模式下它**根本不是关键字**，被当成普通函数名了。

### CE 复核日志二：那条「预处理报错」的真相

`gnu89` 下编这段（`gcc -std=gnu89 -Wall -Wextra`）：

```c
#if __STDC_VERSION__ >= 199901L
#  define BRANCH "走 #if 真分支"
#else
#  define BRANCH "走 #else 假分支"
#endif
```

```text
__STDC_VERSION__ 是否已定义 = 0
BRANCH = 走 #else 假分支（判定为 pre-C99）
__STRICT_ANSI__ = (未定义)
__GNUC_STDC_INLINE__ = (未定义)
```

`build code = 0` / **`diagnostics = 0`** —— **不报错**。未定义标识符在 `#if` 里一律当 0，
`0 >= 199901L` 就是假，于是安静地走 `#else`。

> ⚠️ **这比报错危险。** 报错你立刻知道；静默走错分支要等运行期才炸。
> 想让它出声得单独开 `-Wundef`（它**不在** `-Wall -Wextra` 里）——
> 实测 `gcc -std=gnu89 -Wall -Wextra -Wundef` → `diagnostics = 3`：
>
> ```text
> <source>:13:5: warning: "__STDC_VERSION__" is not defined, evaluates to 0 [-Wundef]
> ```

**所以「跨标准写条件编译先 `#ifdef` 包一层」是义务，不是风格。**
建议项目里默认加上 `-Wundef`。

### CE 复核日志三：双下划线形态逐项体检（`-std=c17 -pedantic-errors`）

「双下划线形态在严格模式下照样能用」这句话**有例外**，不能笼统地信。逐项实测：

| 写法 | `-std=c17 -pedantic-errors` |
|---|---|
| `__attribute__((unused))` | ✅ 0 诊断 |
| `__typeof__` | ✅ 0 诊断 |
| `__asm__ __volatile__` | ✅ 0 诊断 |
| `__builtin_expect` | ✅ 0 诊断 |
| `__builtin_offsetof` | ✅ 0 诊断 |
| **`__int128`** | ❌ **3 个 error** |

```text
$ gcc -std=c17 -Wall -Wextra -pedantic-errors ./p4_underscore_forms.c
<source>:17:8:  error: ISO C does not support '__int128' types [-Wpedantic]
<source>:17:24: error: ISO C does not support '__int128' types [-Wpedantic]
<source>:36:47: error: ISO C does not support '__int128' types [-Wpedantic]
# build code = 1 / diagnostics = 10
```

> **豁免的依据不是「有没有双下划线」，而是「ISO 是否承认这个构造」。**
> `__attribute__` 落在保留标识符空间里，是**合法**用法，`-pedantic` 无从下手；
> `__int128` 虽然也带双下划线，但 ISO 明确不认识这个类型，gcc 就照报不误。
> 换句话说：**双下划线免的是「非保留关键字」的死刑，不免「ISO 不认识」的死刑。**

### CE 复核日志四：`-pedantic` 三种配法 + `-Werror` 对照

源文件 `D:\.kernel-ref\std_probe\{d_default_std.c, p1_strict.c, p5_int128_escape.c}` 与 `desig_probe/a_range.c`；
冻结日志 `log_pedantic.txt`（21 组）/ `log_pedantic2.txt`（5 组）/ `log_pedantic3.txt`（4 组）；
编译器 gcc 13.3（`cg133`）、clang 18.1.3（`cclang1810`）。全部走 Compiler Explorer 公开 API，非本机编译。

**① `d_default_std.c` —— 默认方言**（不加任何 `-std=`）

| 编译器 | 参数 | `__STDC_VERSION__` | `__STRICT_ANSI__` |
|---|---|---|---|
| gcc 13.3 | `-O0 -Wall -Wextra` | `201710L` | 未定义 |
| clang 18.1.3 | `-O0 -Wall -Wextra` | `201710L` | 未定义 |
| gcc 13.3 | `-O0 -Wall -Wextra -std=gnu11` | `201112L` | 未定义 |

→ 两台编译器的**默认方言都是 `gnu17`**；`201112L` 只在显式写 `-std=gnu11` 时出现。

**② `p1_strict.c` —— `-pedantic` / `-Wpedantic` / base standard 三者**

| 命令 | 诊断分布 |
|---|---|
| `gcc -O0 -Wall -Wextra -pedantic`（不写 `-std=`） | 4 warning + 3 note |
| `gcc -O0 -Wall -Wextra -std=gnu17 -pedantic` | **同上，逐字相同** |
| `gcc -O0 -Wall -Wextra -std=c17 -pedantic` | **同上，逐字相同** |
| `gcc -O0 -Wall -Wextra -std=c17 -Wpedantic` | **同上，逐字相同** |
| `gcc -O0 -Wall -Wextra -std=gnu17` | 0 |
| `gcc -O0 -Wall -Wextra -std=c17` | 0 |

gcc 那 4 条 warning 原文：

```text
<source>:12:24: warning: ISO C forbids zero-size array 'data' [-Wpedantic]
<source>:18:5: warning: range expressions in switch statements are non-standard [-Wpedantic]
<source>:19:5: warning: range expressions in switch statements are non-standard [-Wpedantic]
<source>:28:20: warning: ISO C forbids braced-groups within expressions [-Wpedantic]
<source>:55:43: note: in expansion of macro 'MAX'
```

同文件 clang 侧是 **5 warning**（多一条 `##__VA_ARGS__`）：

```text
<source>:12:29: warning: zero size arrays are an extension [-Wzero-length-array]
<source>:18:12: warning: use of GNU case range extension [-Wgnu-case-range]
<source>:19:12: warning: use of GNU case range extension [-Wgnu-case-range]
<source>:25:36: warning: token pasting of ',' and __VA_ARGS__ is a GNU extension [-Wgnu-zero-variadic-macro-arguments]
<source>:55:43: warning: use of GNU statement expression extension from macro expansion [-Wgnu-statement-expression-from-macro-expansion]
<source>:28:21: note: expanded from macro 'MAX'
```

> **「诊断行数」与「warning 条数」不是一回事。** 冻结日志里 gcc 那组印的是「诊断行数 = 7」，
> 因为 `In function 'range':` 这类上下文行和 `note:` 行也各占一行；`log_pedantic2.txt` 起改用
> `分布 = {'warning': 4, 'note/other': 3}` 的口径。**本页所有表格里的条数一律只数 warning / error。**

**③ `a_range.c` —— `-Werror` 抓不到 GNU 扩展**

| 命令 | build code | 结果 |
|---|---|---|
| `gcc -std=gnu11 -Wall -Wextra -pedantic` | 0 | 1 warning：`ISO C forbids specifying range of elements to initialize` |
| `gcc -std=gnu11 -Wall -Wextra -Werror` | **0** | **0 诊断，通过** |
| `gcc -std=c11 -Wall -Wextra -Werror` | **0** | **0 诊断，通过** |
| `gcc -std=gnu11 -Wall -Wextra -pedantic-errors` | **1** | 1 error，编译失败 |
| clang `-std=gnu11 -Wall -Wextra -pedantic-errors` | **1** | 1 error：`use of GNU array range extension [-Werror,-Wgnu-designator]` |

→ `-Werror` **抓不到** GNU 扩展（gnu 方言下压根不出警告，没警告可升级）；`-pedantic-errors` 才拦得住，且**配 `gnu11` 一样管用**。

**④ `p5_int128_escape.c` —— 手册那条「双下划线包住类型名」的逃逸通道**

同一文件里三种写法：`__int128`（不带尾巴）/ `__int128__`（手册写法）/ `__int128_t`（glibc 定义的 typedef）。

| 命令 | 结果 |
|---|---|
| `gcc -std=c17 -pedantic` | **1 warning**，只指向 `typedef __int128 raw128;`（`:10:9`） |
| `gcc -std=c17 -pedantic-errors` | **1 error**，同上位置 |
| `gcc -std=gnu17 -pedantic-errors` | **1 error**，同上位置（base standard 仍是 C17） |
| clang `-std=c17 -pedantic-errors` | **1 error**，但指向**另一行**：`unknown type name '__int128__'; did you mean '__int128_t'?`（`:11:9`），并附 `note: '__int128_t' declared here` |

两条硬结论：

1. **gcc 里 `__int128__` 这条逃逸通道确实生效**——`typedef __int128__ esc128;` 一行 **0 诊断**，
   程序照常跑完（warning 那组 `build code = 0`，三个 `sizeof` 全是 16）。
2. **clang 根本没实现这条通道**——它把 `__int128__` 当**未声明的类型名**，还提示 `did you mean '__int128_t'?`。
   所以「非 ISO `__intN` 类型加双下划线包住可免诊断」是 **gcc 专属行为**；
   跨编译器要用 128 位整数，写 `__int128`（吃一条 warning）或 `__int128_t`（glibc 的 typedef，两个编译器都 0 诊断）。

## 误区表

| 误区 | 实测结论 |
|------|---------|
| 「`-std=c99` 会禁用所有 GNU 扩展」 | ❌ 只禁用**裸关键字形态**（typeof/asm）。`__attribute__`、`__builtin_*`、`case 1...5`、零长数组、`##__VA_ARGS__` 全部照用 |
| 「不写 `-std=` 就是标准 C」 | ❌ gcc13 / clang18 默认 `gnu17`，你一直在用 GNU 方言 |
| 「`-std=c99` 只是更严格的 C」 | ❌ 它顺带关掉了 glibc 的 POSIX 声明，`strdup` 变隐式声明 → 64 位下指针截断 |
| 「`__extension__` 能让我在严格模式用扩展」 | ⚠️ 只压 warning。`typeof` 在 c11 是硬错误，压不住 |
| 「内核到处是 GNU 扩展，所以必须 gnu11」 | ⚠️ 真正必需的只有 `typeof` 和 `asm` 两个裸关键字 |
| 「`__STDC_VERSION__` 能判断标准版本」 | ⚠️ C89/gnu89 下未定义；且 gcc13 的 c2x 报 202000、clang18 报 202311 |
| 「`__attribute__` 在 `-std=cXX` 下不能用」 | ❌ CE 复核：`-std=c17` **0 诊断**，`packed` 正常生效；连 `-pedantic-errors` 都挑不出它。官方手册只关了 `asm`/`typeof`/`inline` 三个词 |
| 「`#if __STDC_VERSION__ >= …` 在 gnu89 下会预处理报错」 | ❌ 不报错，**静默为假**走 `#else`。想让它出声得开 `-Wundef` |
| 「零长数组 / `case 1 ... 5` 在严格模式不能用」 | ⚠️ 能用。它们是「非 ISO 但语法合法」，只有 `-pedantic-errors` 才升级为错误 |
| 「`__GNUC__` 能区分 gcc 和 clang」 | ❌ clang 定义为 4。必须先查 `__clang__` |
| 「`int f()` 就是不检查参数」 | ⚠️ C23 起等于 `int f(void)`，多传参数报错 |
| 「C23 还很远，不用管」 | ⚠️ `typeof` 已转正、`trigraph` 已移除、`bool` 已是关键字；gcc13/clang18 的 `-std=c2x` 现在就能试 |
| 「`-std=c11` 严格按 ISO C11 编译，禁用 GNU 扩展」 | ⚠️ 只在**裸 `typeof` / 裸 `asm`** 两项上成立。`-std=c17` 下 packed、零长数组、`case 1 ... 5`、`##__VA_ARGS__`、语句表达式**全部 0 诊断** |
| 「`-std=gnu11` 是 gcc 和 clang 的默认方言」 | ❌ 过时知识。实测 gcc 13.3 / clang 18.1.3 不写 `-std=` 时都是 `201710L`（`gnu17`） |
| 「`-pedantic` 单独用意义不大、警告会很多」 | ❌ 实测与 `-std=c17 -pedantic` **逐字相同**（4 warning）。它认的是 base standard，与写不写 `-std=` 无关 |
| 「`-pedantic` 和 `-Wpedantic` 有区别」 | ❌ 手册列在同一条目，CE 实测输出逐字相同 |
| 「`-pedantic-errors` = `-Werror -pedantic`」 | ❌ 手册明写 *not equivalent to `-Werror=pedantic`*：它还升级一批 `-Wpedantic` 管不到的必需诊断 |
| 「`-Werror` 能卡住 GNU 扩展」 | ❌ gnu 方言下扩展不出警告，`-Werror` 无从升级。实测 `[0 ... 3]` 在 `-std=gnu11 -Werror` 下 **0 诊断**；要卡住只能上 `-pedantic-errors` |
| 「`-pedantic-errors` 只能配 `-std=cXX`」 | ⚠️ 可配任何 `-std=`。`-std=gnu11 -pedantic-errors` 照样把范围语法拦成硬 error |
| 「`__intN__`（双下划线包住）能免掉非 ISO 类型警告」 | ⚠️ **gcc 专属**。gcc 里确实生效（`__int128__` 0 诊断）；clang 把它当未声明类型名，直接 `unknown type name` |

## 代码自测

<details>
<summary><b>题 1：</b>下面这段代码在 <code>-std=c11</code> 和 <code>-std=gnu11</code> 下分别会怎样？为什么？</summary>

```c
#include <stddef.h>
#define container_of(ptr, type, member) ({                    \
    const typeof(((type *)0)->member) *__mptr = (ptr);         \
    (type *)((char *)__mptr - offsetof(type, member)); })
struct demo { int a; int b; };
struct demo *f(int *p){ return container_of(p, struct demo, a); }
```

**答**：`-std=c11` 失败（gcc 报 2 个 error，clang 报 7 个），`-std=gnu11` 通过。

原因不是语句表达式（它只是 `-pedantic` 警告），而是**裸 `typeof` 关键字在严格模式下不被识别**（gcc 报 `unknown type name 'typeof'`）。改成 `__typeof__` 后，`-std=c11` 也能通过；改成 `-std=c2x`，裸 `typeof` 也能通过（C23 已标准化 typeof）。

</details>

<details>
<summary><b>题 2：</b>项目用 <code>-std=c11 -Wall</code>，结果 <code>strdup</code> 报隐式声明。为什么？怎么修？</summary>

**答**：`__STRICT_ANSI__` 被定义后，glibc 的 `features.h` 不再默认打开 `_DEFAULT_SOURCE`，POSIX 函数声明被隐藏。

危险点不在警告本身，而在**隐式声明的返回类型按 `int` 猜**——64 位平台上 `strdup` 返回的指针被截断成 32 位，高位丢失，运行期段错误。

三种修法任一即可：
1. 加 `-D_GNU_SOURCE`
2. 每个 `.c` 文件**第一行**（所有 `#include` 之前）写 `#define _GNU_SOURCE`
3. 改用 `-std=gnu11`（已隐式打开）

另建议加 `-Werror=implicit-function-declaration`——gcc 13 只给 warning，gcc 14 才升级为 error。

</details>

<details>
<summary><b>题 3：</b>为什么内核非用 <code>-std=gnu11</code> 不可？换成 <code>-std=c11</code> 会挂在哪？</summary>

**答**：实测十项内核惯用法，只有两项在 `-std=c11` 下失败：

1. **裸 `typeof`** —— `container_of` 的基础，gcc 报 2 个 error
2. **裸 `asm`** —— 内核到处是 `asm volatile(...)`，gcc 报 2 个 error

其余八项（`section` 属性、`case 1...5`、零长度数组、`##__VA_ARGS__`、`__builtin_expect`、`&&label`、`__int128`、匿名 union）在严格模式下全部可用——因为双下划线开头的标识符是 ISO C 保留给实现的。

**内核不肯给这两个加下划线，所以必须是 GNU 方言。** 而且 `asm` 在 C23 里也不会转正（实测 `-std=c2x` 下裸 `asm` 仍报错），所以这个依赖是永久的。

</details>

<details>
<summary><b>题 4：</b>下面这个条件编译有什么问题？</summary>

```c
#if __STDC_VERSION__ >= 199901L
    /* 用 C99 特性 */
#endif
```

**答**：两个问题。

1. **`__STDC_VERSION__` 在 C89/gnu89 下根本未定义**。未定义标识符在 `#if` 中被当作 0，所以 `0 >= 199901L` 为假——看起来「正确」地跳过了，但如果条件是 `<=` 或者嵌套了 `#else`，逻辑就会静默反向。正确写法：
   ```c
   #if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 199901L
   ```

2. **想判断 C23 时用 `>= 202311L` 会在 gcc 13 上失效**——gcc 13 的 `-std=c2x` 报的是 202000（C2x 草案期的值），clang 18 报的才是 202311。判断 C23 建议写成 `>= 202000L`，或干脆查具体特性宏。

</details>

<details>
<summary><b>题 5：</b><code>__extension__</code> 是干什么的？它能在 <code>-std=c11</code> 下让你用 <code>typeof</code> 吗？</summary>

**答**：`__extension__` 的作用是**抑制 `-pedantic` 对非 ISO 语法的诊断**。

- 能压的：语句表达式、`long long` 这类「语法合法但非 ISO」的构造。实测 `int z = ({1+2;});` 在 `-std=c99 -pedantic` 下是 1 warning，加 `__extension__` 后变 0。
- **压不住的**：硬错误。`typeof` 在 `-std=c11` 下是 `unknown type name`（error），加 `__extension__` 仍然失败。

所以正确的应对是**换双下划线形态**（`__typeof__`），实测在 `-pedantic-errors` 下也干净。

</details>

<details>
<summary><b>题 6（反例题）：</b>「<code>-std=c17</code> 下 <code>__STRICT_ANSI__</code> 被定义，GNU 扩展被关闭，所以不能用 <code>__attribute__((packed))</code>」——这句话错在哪？</summary>

**答**：错在把「关掉扩展」理解成「关掉一切非 ISO 的东西」。

官方手册 6.12.23 明确**只穷举了三个**被 `-std=` 关掉的关键字：

> Specifically, the keywords `asm`, `typeof` and `inline` are not available …

`__attribute__` 不在其中，因为它是**双下划线形态**，落在 ISO C 保留给实现的标识符空间里，
是合法用法而不是「扩展语法糖」。

CE 复核（gcc 13.3）：

```text
$ gcc -std=c17 -Wall -Wextra ./p1_strict.c
__STRICT_ANSI__      = 1
sizeof(struct A)     = 5   (packed 生效则应 = 5)
# build code = 0 / diagnostics = 0

$ gcc -std=c17 -Wall -Wextra -pedantic-errors ./p1_strict.c
# diagnostics = 17 —— 四条 error 分别指向零长数组、两条 case 范围、语句表达式
# 没有一条指向 __attribute__((packed))
```

**正确的心智模型是二分法**：

| 类别 | 例子 | `-std=cXX` 下 | `-pedantic-errors` 下 |
|---|---|---|---|
| 保留标识符形态 | `__attribute__` `__typeof__` `__asm__` `__builtin_*` | ✅ 可用 | ✅ **仍然可用** |
| 裸关键字形态 | `asm` `typeof` `inline`（语义变） | ❌ 不可用 | ❌ |
| 非 ISO 但语法合法 | 零长数组、`case 1 ... 5`、语句表达式、`__int128` | ✅ 可用（无诊断） | ❌ 报错 |

⚠️ **`__int128` 归在第三类，不归第一类**——它虽然也是双下划线形态，
但 `-std=c17 -pedantic-errors` 下 gcc 报 `error: ISO C does not support '__int128' types`。
判据是 **ISO 是否承认这个构造**，不是「有没有下划线」（实测见本节「日志三」）。

所以**「想用扩展就切 `gnuXX`」是过度反应**。真正需要方言的只有第二类；第三类只需要别开 `-pedantic-errors`；
第一类在任何方言、任何 `-pedantic` 强度下都能用。

</details>

<details>
<summary><b>题 7（反例题）：</b>「<code>-pedantic</code> 单独用（不带 <code>-std=c11</code>）意义不大，因为默认方言是 <code>gnu11</code>，GNU 扩展本来就合法，警告会很多」——这句话里有几个坑？</summary>

**答**：**三个坑，每个都独立成立。**

**坑 1：默认方言不是 `gnu11`。** 实测 gcc 13.3 / clang 18.1.3 不写 `-std=` 时 `__STDC_VERSION__` 都是 `201710L`，即 **`gnu17`**。「`gnu11` 是默认」是旧知识；显式写 `-std=gnu11` 才拿到 `201112L`。

**坑 2：`-pedantic` 认的是 base standard，与 `__STRICT_ANSI__`、与写不写 `-std=` 都无关。** 手册原文：

> Warnings from `-Wpedantic` are given where they are required by the **base standard**.

`gnu11` 的 base standard 就是 C11，`gnu17` 的就是 C17。于是 `-pedantic` 单独用、`-std=gnu17 -pedantic`、`-std=c17 -pedantic` **三组输出逐字相同**——实测都是 4 warning，连行号与 `[-Wpedantic]` 后缀都一致（见「日志四」②）。

**坑 3：警告不会「很多」，而且「很多」也不是 `-pedantic` 的锅。** 同一份 `p1_strict.c` 在 `-Wall -Wextra -pedantic` 下只出 **4 条**，全部指向语法层的非 ISO 构造：

```text
$ gcc -O0 -Wall -Wextra -pedantic ./p1_strict.c
<source>:12:24: warning: ISO C forbids zero-size array 'data' [-Wpedantic]
<source>:18:5: warning: range expressions in switch statements are non-standard [-Wpedantic]
<source>:19:5: warning: range expressions in switch statements are non-standard [-Wpedantic]
<source>:28:20: warning: ISO C forbids braced-groups within expressions [-Wpedantic]
<source>:55:43: note: in expansion of macro 'MAX'
# build code = 0
```

真正会把诊断堆多的是 **`-pedantic-errors`**，因为它的覆盖面比 `-Wpedantic` 更大（手册明说不等价于 `-Werror=pedantic`）。同一行范围语法的四种强度对比：

| 命令（`a_range.c`，一行 `int a[10] = {[0 ... 3] = 1};`） | 结果 |
|---|---|
| `-std=gnu11 -Wall -Wextra` | 0 诊断，通过 |
| `-std=gnu11 -Wall -Wextra -pedantic` | 1 warning，通过 |
| `-std=gnu11 -Wall -Wextra -Werror` | **0 诊断，通过**（`-Werror` 抓不到扩展） |
| `-std=gnu11 -Wall -Wextra -pedantic-errors` | **1 error，`build code = 1`** |

**一句话修正**：`-pedantic` 任何时候单用都成立，它的行为只取决于**当前生效的 base standard**；要卡住 GNU 扩展得用 `-pedantic-errors`，`-Werror` 不管用。
