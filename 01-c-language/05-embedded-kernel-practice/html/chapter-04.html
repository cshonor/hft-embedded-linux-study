GNU C in the Linux Kernel

一句话概括这一章：把 CH1/CH2 的工具，放回它真正被用的地方去看。 CH3 是「没有 OS 的裸机」；这一章是「有内核的情况下，同一套扩展怎么被用到极致」。

前置：CH1 · CH2 配合阅读：CH3 嵌入式驱动实战（同一个 packed 结构体，在裸机和驱动里的用法差别）

本章讲什么

CH1/CH2 告诉你有这些工具。但你第一次打开 include/linux/list.h 或 kernel/module.c 时仍然会懵——因为它们是组合使用的。

这一章回答三个具体问题：

  1. 内核为什么几乎不用链表库而要 container_of 反推结构体？
  2. module_init() 没有任何地方调用它，它到底什么时候跑？
  3. 一个 .ko 从 insmod 到 .init 段被释放，中间发生了什么？

第 3 问的答案跟 CH2 的 6.6 section 是同一件事：用 __attribute__((section)) 把一批函数指针放进同一个段，链接器自动收集成一张表。

代码自测（点击展开）

Q1：module_init(fn) 展开后到底发生了什么？

答案

它不是函数调用，而是放置。展开后大致等价于：

static initcall_t __initcall_fn6 __used __attribute__((__section__(".initcall6.init"))) = fn;

也就是把 fn 的地址放进 .initcall6.init 这个段。链接脚本里把这个段的起止地址导出为 __initcall_start[]/__initcall_end[]，内核启动时用 for (call = __initcall_start; call < __initcall_end; call++) (*call)(); 依次执行。

所以 module_init 从来没有被谁显式调用过——它是被链接器和启动循环找出来的。这就是 CH2 所说的「链接期语义」。

Q2：为什么内核的链表是「链表节点嵌在结构体里」，而不是「结构体指针挂在链表上」？

答案

后者需要每种数据类型各写一份链表实现（或用 void* 丢掉类型）。前者只写一份 struct list_head 的通用操作，用 container_of 从成员地址反推宿主地址，同时保留完整类型信息。

代价：一个对象只能同时属于一条 list_head 链表（需要多条链表就要多个 list_head 成员——所以 struct task_struct 里有好几个）。

Q3：__init 修饰的函数/数据最后去哪了？

答案

它们被放进 .init.text / .init.data 段。内核启动完成后会调用 free_initmem() 把整个段的页释放掉，回收内存（嵌入式上能回收几百 KB 到几 MB）。

副作用：这些函数只能调用一次。已经释放的地址如果再被调到，就是踩野内存——这也是驱动里 __init 不能乱标的原因。

4.10

Linux内核模块运行机制

本节讲什么

内核模块（.ko）是运行期由 insmod 装入内核空间的 可重定位 ELF，与用户态 .so 类似但无 ld.so：由内核 module.c 负责分配内存、重定位、解析符号、注册导出表。读 LKD 驱动、DPDK 内核态 PMD 依赖的「装入」概念与此相通。

要点

与用户态动态链接对比

用户态 .so 内核模块 .ko
加载器 ld-linux.so kernel/module.c
入口 _init / 构造函数 module_init() 宏
符号 dlsym /proc/kallsyms、导出表
卸载 dlclose rmmod

代码自测

题目 1： Linux 内核模块（.ko）和用户态共享库（.so）有什么本质区别？

// 内核模块 hello.c
#include <linux/module.h>
static int __init hello_init(void) {
    printk("Hello kernel\n");
    return 0;
}
static void __exit hello_exit(void) {
    printk("Goodbye\n");
}
module_init(hello_init);
module_exit(hello_exit);
参考答案

本质区别：

内核模块 (.ko) 共享库 (.so)
运行空间 内核态（Ring 0） 用户态（Ring 3）
加载方式 insmod/modprobe dlopen/ld-linux
链接方式 内核符号表 动态链接器
库依赖 只能用内核导出的符号 可用 libc 等用户库
出错影响 内核崩溃（Oops/Panic） 仅进程崩溃

module_init/module_exit 标记的函数在 insmod/rmmod 时被内核调用。printk 是内核的 printf（输出到 dmesg）。

__init 表示该函数只在加载时执行一次，完成后释放代码内存。

4.12

U-boot重定位分析

本节讲什么

U-Boot 常先由 ROM 加载到 低地址 SRAM/DRAM 临时区，再 自拷贝 到链接脚本指定的高地址并 修正重定位项——因为初始 PC 与链接 VMA 不一致。这是 4.4.3 重定位 在嵌入式 Bootloader 中的手工版，与内核解压后重定位同类。

要点

为何重定位

  • 链接时假设运行在 TEXT_BASE（如 0x40200000）
  • 上电时可能在 0x00000000 或另一 RAM 区执行
  • 必须拷贝代码/数据并修补 相对/绝对地址引用

典型步骤（概念）

  1. relocate_code：拷贝 .text/.data 到目标区
  2. 遍历 __rel_dyn_start…__rel_dyn_end 修补
  3. 跳转至重定位后地址继续执行
# 分析 U-Boot ELF（交叉工具链）
arm-linux-gnueabihf-readelf -S u-boot
arm-linux-gnueabihf-nm u-boot | grep relocate
arm-linux-gnueabihf-objdump -d u-boot | grep relocate

  • u-boot.lds 定义 TEXT_BASE、__image_copy_start

代码自测

题目 1： U-Boot 为什么要做重定位（relocate）？以下代码完成什么操作？

/* U-Boot relocate */
ulong relocaddr = gd->relocaddr;
memcpy((void *)relocaddr, (void *)CONFIG_SYS_TEXT_BASE, gd->mon_len);
relocate_code(relocaddr, gd->reloc_off, relocaddr);
参考答案

U-Boot 重定位原因： - U-Boot 初始加载到固定地址（CONFIG_SYS_TEXT_BASE，如 0x87800000） - 但该地址可能被 Linux 内核占用，需将自身复制到更高地址运行 - 重定位后修正所有绝对地址引用（通过 reloc_off 偏移量）

流程： 1. memcpy：将整个 U-Boot 代码和数据复制到新地址 relocaddr 2. relocate_code：修正 GOT 表、所有绝对地址符号（加上 reloc_off） 3. 跳转到新地址继续执行

这是嵌入式启动的常见模式：Bootloader 先在低端地址运行，然后搬自己到高端地址，腾出空间给内核。

4.13

协议结构体的 packed 实践

← CH4 内核模块 · 4.12 container_of 与侵入式链表 · CH2 6.7 aligned 与 packed · CH3 10.8 寄存器操作

本篇把 CH2 6.7 aligned/packed 的 __attribute__((packed)) 放回它真正被用的地方——内核网络协议头。 你会发现一个反直觉的事实：TCP/IP 头根本不加 packed，真正加 packed 的是 USB 描述符和 Ethernet 头。 全部 v6.6 源码核对，WSL 实测 5 个 demo（gcc 13.3 / clang 18.1.3 双编译）。

本节讲什么

CH2 的 6.7 讲了 packed 的语法（取消 padding、降对齐到 1）。但真正打开 include/uapi/linux/tcp.h 时，你会看到三个互相缠绕的 C 语言话题：

话题 涉及的 GNU C 扩展 这篇的落点
线上格式怎么用 C struct 表达 __attribute__((packed))、位域 TCP/IP/USB/Ethernet 头
字节序怎么标注 __bitwise（sparse 标注）、__be16/__be32 htonl/ntohl → __builtin_bswap32
热路径怎么操作 flag union cast（绕过 strict-aliasing） tcp_flag_word() + TCP_FLAG_* 整字常量

它和 CH2 的分工：CH2 讲 packed 的语法和代价（伪共享、未对齐访问、UBSan 绕过），这篇讲内核为什么这么用它——哪些头该加、哪些不该加、为什么用位域双版本、热路径为什么用 union 整字操作。

一、反直觉的发现：TCP/IP 头不加 packed

很多人第一次看内核协议头代码时的预期是「网络头一定有 __attribute__((packed))，因为它要精确匹配线上格式」。但 v6.6 源码告诉你不是：

/* include/uapi/linux/tcp.h —— 注意：没有 __attribute__((packed)) */
struct tcphdr {
    __be16  source;
    __be16  dest;
    __be32  seq;
    __be32  ack_seq;
    __u16   res1:4, doff:4, fin:1, syn:1, ...;  /* 位域 */
    __be16  window;
    __sum16 check;
    __be16  urg_ptr;
};

/* include/uapi/linux/ip.h —— 同样没有 packed */
struct iphdr {
    __u8    ihl:4, version:4;  /* 位域 */
    __u8    tos;
    __be16  tot_len;
    ...
};

/* include/uapi/linux/udp.h —— 同样没有 packed */
struct udphdr {
    __be16  source;
    __be16  dest;
    __be16  len;
    __sum16 check;
};

T1 demo 实测（WSL gcc 13.3, x86-64 小端）打印了真实布局：

struct tcphdr    sizeof=20  align=4    <- 5 个 32 位字
struct iphdr     sizeof=20  align=4
struct udphdr    sizeof=8   align=2

为什么不加 packed 也不出问题？ 因为这三个头的设计有一个共同特征：

头 成员类型 位域所在单元
tcphdr 全 __be16/__be32（2/4 字节） res1+doff+8 flags = 16 bit = 1 个 __u16
iphdr __u8 + __be16/__be32 ihl+version = 8 bit = 1 个 __u8
udphdr 全 __be16/__sum16 无位域

结构体的对齐 = 所有成员对齐要求的最大值。这些头的成员都是 2/4 字节对齐，结构体对齐就是 4（或 2），而 sizeof 恰好是 4（或 2）的整数倍——没有 padding 需要消除，packed 多余。

CH2 6.7 的结论在这里得到了验证：packed 只在成员排列会产生 padding 时才需要。TCP/IP 头的设计者刻意让所有成员都落在自然对齐的偏移上，就是为了不用 packed。

那谁加了 packed？

/* include/uapi/linux/if_ether.h —— 加了 packed */
struct ethhdr {
    unsigned char h_dest[ETH_ALEN];     /* 6 字节，对齐 1 */
    unsigned char h_source[ETH_ALEN];   /* 6 字节，对齐 1 */
    __be16        h_proto;              /* 2 字节，对齐 2 */
} __attribute__((packed));

/* include/uapi/linux/usb/ch9.h —— USB 描述符全族都加了 packed */
struct usb_device_descriptor {
    __u8  bLength;
    __u8  bDescriptorType;
    __le16 bcdUSB;                      /* offset 2 */
    __u8  bDeviceClass;
    ...
} __attribute__((packed));

struct usb_ctrlrequest {
    __u8 bRequestType;
    __u8 bRequest;
    __le16 wValue;                      /* offset 2 */
    __le16 wIndex;
    __le16 wLength;
} __attribute__((packed));

T1 demo 对比了 packed 和不加 packed 的版本：

struct ethhdr        sizeof=14  align=1   <- packed
struct ethhdr_nopack sizeof=14  align=2   <- 不加 packed 也是 14 字节！
struct usb_device_descriptor      sizeof=18  align=1   <- packed
struct usb_device_descriptor_nopack sizeof=18  align=2 <- 不加也是 18 字节！

反直觉的发现：Ethernet 头和 USB 描述符在 gcc 上不加 packed 也恰好不产生 padding——因为这个排列下 2 字节成员都落在偶数偏移上。packed 唯一的效果是把 align 从 2 降到 1。

但这不代表 packed 多余——T1 加了一个「坏排列」的对比：

/* __u8 紧跟 __le16：不加 packed 就会产生 padding */
struct usb_bad_order_packed {
    __u8  bLength;
    __le16 wValue;   /* offset 1, 不对齐 2 -> packed 必须有 */
    __u8  bType;
} __packed;

struct usb_bad_order_nopack {
    __u8  bLength;
    __le16 wValue;   /* offset 2, 编译器自动 padding */
    __u8  bType;
};

实测：

struct usb_bad_order_packed   sizeof=4  align=1  wValue off=1
struct usb_bad_order_nopack   sizeof=6  align=2  wValue off=2

这才是 packed 不可省的场景：wValue 在 offset 1（不对齐 2），不加 packed 编译器会在 bLength 后插入 1 字节 padding 把 wValue 推到 offset 2。

packed 三档分类

场景 packed 作用 例子
不加也没 padding 防御性（保证所有编译器/排列下不出 padding） tcphdr、iphdr、udphdr
不加也有 padding 必须（否则 sizeof 不等于线上字节数） usb_bad_order、各种 USB 描述符
不加没 padding 但 align 不同 防御性 + 降 align ethhdr、usb_device_descriptor

结论：packed 的真正作用 = 消除 padding + 降 align 到 1。好排列时是防御性的，坏排列时是必须的。TCP/IP 头的设计者刻意排列成员使其不需要 packed，这是设计上的选择而非疏漏。

二、__be16/__be32：字节序的类型标注

你看到的 __be16、__be32、__sum16、__le16、__le32 不是编译器内置类型，而是内核的 typedef：

/* include/uapi/linux/types.h */
typedef __u16 __bitwise __le16;   /* little-endian 16-bit */
typedef __u16 __bitwise __be16;   /* big-endian (network order) 16-bit */
typedef __u32 __bitwise __le32;
typedef __u32 __bitwise __be32;
typedef __u16 __bitwise __sum16;  /* checksum 16-bit */
typedef __u32 __bitwise __wsum;   /* wide checksum */

__bitwise 是什么？看 include/linux/compiler_types.h：

#ifdef __CHECKER__
# define __bitwise     __attribute__((bitwise))
# define __force      __attribute__((force))
#else
# define __bitwise
# define __force
#endif
条件 __bitwise 展开 效果
sparse 运行时（__CHECKER__ 定义） __attribute__((bitwise)) sparse 把 __be16 和 __u16 当不同类型，直接赋值会报 warning
gcc/clang 编译时 空宏 __be16 就是 unsigned short，零运行时开销

所以 __be16 的意义是：给 sparse（内核静态检查工具）看的类型标注，提醒你「这个值是网络字节序，必须用 ntohs() 转成主机序才能用」。在编译器层面，__be16 和 __u16 完全相同。

CH2 6.8 format 讲了 format 属性让编译器在编译期检查 printf 格式串。__bitwise 是类似的设计哲学——用类型系统把容易犯的错变成可检测的。区别是 format 用 gcc/clang 内置支持，__bitwise 用 sparse 外部工具。

__force：允许「明知故犯」的转换

你会在内核代码里看到 (__force __be32) 这样的写法：

/* include/uapi/linux/byteorder/little_endian.h */
#define __constant_htonl(x) ((__force __be32)___constant_swab32((x)))

__force 告诉 sparse「我知道这是不同字节序的类型，但我有意要这么转换，别报警」。在 gcc/clang 层面 __force 也是空宏。

三、位域双版本：编译期解决字节序

TCP 头的 doff（4 bit）+ res1（4 bit）+ 8 个 flag（各 1 bit）合占 16 位。但这 16 位在大端和小端机器上的内存排列不同：

RFC 793 定义的线上格式（网络序 = 大端）：
  byte 12: [doff(4bit)] [reserved(4bit)]
  byte 13: [CWR ECE URG ACK PSH RST SYN FIN]

在大端机器上，位域 doff:4, res1:4 的内存排列自然和线上格式一致（高位在前）。 在小端机器上，同一个 __u16 的位域排列是反过来的（低位在前）。

内核的解法不是运行时判断，而是编译期用 #if 选两套位域定义：

/* include/uapi/linux/tcp.h */
struct tcphdr {
    ...
#if defined(__LITTLE_ENDIAN_BITFIELD)
    __u16   res1:4,          /* 低 4 bit */
            doff:4,          /* 高 4 bit */
            fin:1,           /* byte 13 最低位 */
            syn:1,
            rst:1,
            psh:1,
            ack:1,
            urg:1,
            ece:1,
            cwr:1;           /* byte 13 最高位 */
#elif defined(__BIG_ENDIAN_BITFIELD)
    __u16   doff:4,          /* 高 4 bit */
            res1:4,          /* 低 4 bit */
            cwr:1,           /* byte 13 最高位 */
            ece:1,
            urg:1,
            ack:1,
            psh:1,
            rst:1,
            syn:1,
            fin:1;           /* byte 13 最低位 */
#else
#error  "Adjust your <asm/byteorder.h> defines"
#endif
    ...
};

__LITTLE_ENDIAN_BITFIELD / __BIG_ENDIAN_BITFIELD 在 include/uapi/linux/byteorder/little_endian.h 或 big_endian.h 里定义，由 asm/byteorder.h 根据架构包含其中之一：

/* include/uapi/linux/byteorder/little_endian.h */
#ifndef __LITTLE_ENDIAN_BITFIELD
#define __LITTLE_ENDIAN_BITFIELD
#endif

T2 demo 验证了这一点（x86-64 小端）：

目标: version=4, ihl=5 -> 线上字节 0x45
位域写: ihl=5, version=4 -> 生成的字节: 45   <- LE 版本生成正确的线上字节
手动写: ihl=5, version=4 -> 0x45              <- 手动移位也一致
两者一致: YES

关键洞察：位域双版本保证无论本机什么字节序，用位域生成的线上字节都符合 RFC。这是编译期解决，不是运行时——零开销。

位域跨存储单元边界：C 标准的未定义行为

C 标准（C11 6.7.2.1）不保证位域跨存储单元边界的行为。内核的位域设计刻意让每个位域组不跨边界：

头 位域 总位数 所在单元 跨边界？
tcphdr res1:4 + doff:4 + 8x1bit 16 bit 1 个 __u16 否
iphdr ihl:4 + version:4 8 bit 1 个 __u8 否
tcp_info tcpi_snd_wscale:4, tcpi_rcv_wscale:4 8 bit 1 个 __u8 否

如果有人写 res1:4, doff:4, bigfield:9（共 17 bit 超过 __u16），C 标准未定义，gcc 和 clang 的行为可能不一致——不可移植。内核刻意把每段位域控制在单个存储单元内。

四、热路径的 union cast：一条指令设/清多个 flag

位域版本的可读性好（th->doff = 5; th->syn = 1; th->ack = 1;），但热路径上逐个访问位域效率不高——每个位域是独立的读-改-写。

内核的解法是 union cast：把整个 TCP 头看成一串 32 位字，对 flags 所在的那个字做整字 AND/OR：

/* include/uapi/linux/tcp.h */
union tcp_word_hdr {
    struct tcphdr hdr;
    __be32        words[5];     /* TCP 头 = 5 个 32 位字 */
};

/* 取第 4 个字（含 doff + 8 个 flag） */
#define tcp_flag_word(tp) (((union tcp_word_hdr *)(tp))->words[3])

/* TCP_FLAG_* 是 __constant_cpu_to_be32 常量 */
enum {
    TCP_FLAG_ACK = __constant_cpu_to_be32(0x00100000),
    TCP_FLAG_SYN = __constant_cpu_to_be32(0x00020000),
    TCP_FLAG_FIN = __constant_cpu_to_be32(0x00010000),
    ...
};

热路径用法：

/* 一次性设置 SYN + ACK（一条 OR 指令） */
tcp_flag_word(tp) |= (TCP_FLAG_SYN | TCP_FLAG_ACK);

/* 一次性清除 SYN + ACK + PSH + URG（一条 AND 指令） */
tcp_flag_word(tp) &= ~(TCP_FLAG_SYN | TCP_FLAG_ACK | TCP_FLAG_PSH | TCP_FLAG_URG);

T4 demo 验证了两种写法的结果一致性：

A (位域):   syn=1 ack=1 fin=0 rst=0
B (整字OR): syn=1 ack=1 fin=0 rst=0
一致: YES

清除前: syn=1 ack=1 psh=1 urg=1
清除后: syn=0 ack=0 psh=0 urg=0
-> 一条 AND 指令清除 4 个 flag（位域要 4 次写）

这个设计的精妙之处：TCP_FLAG_* 常量用 __constant_cpu_to_be32() 转换——在小端机器上编译期 bswap 成网络序。所以 tcp_flag_word(tp) |= TCP_FLAG_ACK 编译成一条 or 指令，常量已经在正确的字节序了。

union cast 与 strict-aliasing

tcp_flag_word(tp) 用 union tcp_word_hdr * 类型双关访问 struct tcphdr。在 -fstrict-aliasing 下，编译器可能认为这是 UB。内核的解法是全局 -fno-strict-aliasing：

# Linux 顶层 Makefile
KBUILD_CFLAGS += -fno-strict-aliasing

C 标准允许通过 union 访问任意成员（C11 6.5.2.3），但 gcc 的 strict-aliasing 优化可能不完全遵守这一点。内核选择全局关闭 -fstrict-aliasing 来让 union cast 安全。T4 demo 编译时也加了 -fno-strict-aliasing。

五、htonl/ntohl：__builtin_bswap32 的一条指令

字节序转换的本质是字节交换。内核的 htonl/ntohl 在小端机器上等于 __swab32：

/* include/uapi/linux/byteorder/little_endian.h */
#define __constant_htonl(x) ((__force __be32)___constant_swab32((x)))
#define __be32_to_cpu(x) __swab32((__force __u32)(__be32)(x))
#define ntohl(x) __be32_to_cpu(x)
#define htonl(x) __cpu_to_be32(x)

/* include/uapi/linux/swab.h */
#if defined(__has_builtin) && __has_builtin(__builtin_bswap32)
#define __swab32(x) (__u32)__builtin_bswap32((__u32)(x))
#else
/* 手动移位回退 */
#define ___constant_swab32(x) ((__u32)(        \
    (((__u32)(x) & (__u32)0x000000ffUL) << 24) | \
    (((__u32)(x) & (__u32)0x0000ff00UL) <<  8) | \
    (((__u32)(x) & (__u32)0x00ff0000UL) >>  8) | \
    (((__u32)(x) & (__u32)0xff000000UL) >> 24)))
#endif

三种实现：

实现 代码 编译结果（-O2）
__builtin_bswap32 编译器内置 1 条 bswap 指令（x86）/ rev（ARM）
手动移位 4 次 <</>> + 3 次 \| gcc 识别为 bswap 模式，也编译成 1 条 bswap
union 重解释 字节交换 多条 mov + 字节操作

T5 demo 验证（-O2）：

__builtin_bswap32: 0x78563412
手动移位:          0x78563412
union 重解释:      0x78563412
三者一致: YES

bswap 汇编指令验证 --
✓ 编译器生成了 3 条 BSWAP 指令:
    bswap  %ecx
    bswap  %ecx
    bswap  %ecx

关键洞察：__builtin_bswap32 和手动移位在 -O2 下编译成同一条 bswap 指令——gcc 的 pattern recognizer 能识别 (x<<24)|(x<<8&...)|(x>>8&...)|(x>>24) 就是 bswap。所以用哪个都行，但 __builtin_bswap32 更可读。

大端机器上的零开销

在大端机器上（如某些 PowerPC、SPARC），htonl/ntohl 是 no-op：

/* include/uapi/linux/byteorder/big_endian.h */
#define __be32_to_cpu(x) ((__force __u32)(__be32)(x))  /* 直接返回，不转换 */

编译器看到 (__force __u32)(__be32)(x) 就是一个空转换，优化后什么都不生成。

六、__struct_group：iphdr 的地址组

v6.6 的 struct iphdr 用了一个你可能没见过的特性——__struct_group：

struct iphdr {
    __u8    ihl:4, version:4;
    __u8    tos;
    __be16  tot_len;
    __be16  id;
    __be16  frag_off;
    __u8    ttl;
    __u8    protocol;
    __sum16 check;
    __struct_group(/* no tag */, addrs, /* no attrs */,
        __be32  saddr;
        __be32  daddr;
    );
};

__struct_group 是 Linux 5.16 引入的宏，展开为 C11 的匿名结构体成员：

/* 等价于 */
struct iphdr {
    ...
    struct {
        __be32  saddr;
        __be32  daddr;
    } addrs;   /* 有名子结构体 */
};

/* 访问方式 */
iph->saddr;          /* 直接访问（向后兼容） */
iph->addrs.saddr;    /* 通过子结构体访问 */

好处：可以用 memcpy(&iph->addrs, ...) 一次拷贝两个地址，或者用 iph->addrs 取地址做指针运算。__struct_group 让「既能直接访问字段，又能作为子组访问」成为可能。

这是 CH1 6.2 指定初始化 的一个进阶应用——__struct_group 让结构体的组合性更好，同时不破坏向后兼容的字段访问。

七、完整对照表：协议头用什么

头 packed 位域 位域双版本 __be/__le 标注 union cast 出处
tcphdr ❌ ✅ doff:4,flags:1*8 ✅ LE/BE ✅ __be16/__be32 ✅ tcp_word_hdr uapi/linux/tcp.h
iphdr ❌ ✅ ihl:4,version:4 ✅ LE/BE ✅ __be16/__be32 ❌ uapi/linux/ip.h
udphdr ❌ ❌ — ✅ __be16/__sum16 ❌ uapi/linux/udp.h
ethhdr ✅ ❌ — ✅ __be16 ❌ uapi/linux/if_ether.h
usb_* ✅ ❌ — ✅ __le16 ❌ uapi/linux/usb/ch9.h
tcp_info ❌ ✅ wscale:4,4 ❌ ❌ __u8 ❌ uapi/linux/tcp.h

设计规律

  1. 网络协议头（TCP/IP/UDP）：成员全 2/4 字节对齐 → 不加 packed；位域在单个存储单元内 → 用双版本
  2. USB/硬件描述符：__u8/__le16 混合 → 加 packed 确保紧凑；不用位域（USB 字段都是整字节）
  3. 热路径 flag 操作：用 union cast + 整字常量，而非逐个位域访问
  4. 字节序标注：用 __be/__le + __bitwise 给 sparse 看，编译器层面零开销
  5. __struct_group：让相邻字段既能直接访问又能作为子组操作

八、packed 的未对齐访问代价

packed 结构体的成员可能不在自然对齐地址上。访问未对齐成员的代价取决于架构：

架构 未对齐访问 后果
x86/x86-64 硬件支持 有性能代价（跨 cache line 可能慢 2x+），但不会异常
ARM (传统) 部分支持 ALIGN 模式下可能触发 SIGBUS；unaligned 模式下软件处理（很慢）
SPARC/Alpha 不支持 直接触发异常，内核需 fixup（极慢）

T3 demo 实测（x86-64，-O2）：

uint32_t 未对齐 (offset=1) vs 对齐 (offset=4):
  unaligned:  26.73 ms
  aligned:    30.48 ms
  ratio: 0.88x  <- x86 硬件支持，差异小（可能被预取抵消）

x86 的未对齐访问代价小是因为硬件有专门的未对齐支持逻辑。但在 ARM/SPARC 上代价可能大 10x 以上——这就是为什么内核在非 x86 架构上对 packed 结构体用 get_unaligned()/put_unaligned() 辅助函数。

内核的应对：get_unaligned / put_unaligned

/* include/asm-generic/unaligned.h */
/* 用 memcpy 辅助，编译器生成最优的未对齐访问指令 */
static inline u32 get_unaligned_le32(const void *p)
{
    return __get_unaligned_le32((const u8 *)p);
}

内核不直接 *(u32 *)p 访问未对齐地址，而是用 get_unaligned() 包装——在 x86 上编译成普通 mov，在 ARM 上编译成多条 ldrb + orr。

九、uapi：内核和用户态共用一份头文件

你注意到所有协议头都在 include/uapi/linux/ 目录下。uapi = User API，这些头文件：

  1. 被内核（C 代码）和用户态程序（如 tcpdump、wireshark）共用
  2. 通过 make headers_install 安装到 /usr/include/linux/
  3. 用户态 #include <linux/tcp.h> 和内核 #include <linux/tcp.h> 包含的是同一份文件

这解释了为什么协议头结构体要用 __be16 而不是 __u16——类型标注对用户态程序也有意义（用 sparse 检查用户态代码时）。而 __bitwise 在用户态的 gcc/clang 编译中是空宏，不影响编译。

这是 GNU C 扩展在系统编程层面的实践：用类型系统（即使是 sparse 这种外部工具的类型系统）来防止字节序错误，比靠注释和人肉审查可靠得多。

代码自测（点击展开）

Q1：为什么 struct tcphdr 不加 __attribute__((packed)) 也能正确匹配线上格式？

答案

因为 tcphdr 的所有成员都是 2 或 4 字节类型（__be16/__be32），它们的自然对齐就是 2 或 4。结构体布局时所有成员都落在自然对齐的偏移上——没有 padding 需要消除。位域部分（res1:4 + doff:4 + 8 个 flag）正好占满 1 个 __u16（16 bit），也不跨存储单元边界。

packed 的作用是取消 padding，但这里本来就没有 padding。加了反而会降低 align 到 1，可能导致某些场景下不必要的未对齐访问。TCP/IP 头的设计者刻意让成员排列不需要 packed——这是设计上的选择。

Q2：__be16 和 __u16 在编译器层面有什么区别？为什么要用 __be16？

答案

在 gcc/clang 编译器层面完全相同——__be16 就是 typedef __u16 __bitwise __be16，而 __bitwise 在非 sparse 编译时是空宏。

用 __be16 的意义是给 sparse（内核静态检查工具）看的：sparse 把 __be16 和 __u16 当不同类型，如果你直接 __u16 x = some_be16_var;（忘了 ntohs 转换），sparse 会报 warning。这把「忘了转字节序」这种运行时很难发现的 bug 变成了编译期可检测的问题。

Q3：内核为什么用位域双版本（#if __LITTLE_ENDIAN_BITFIELD）而不是运行时判断字节序？

答案

两个原因：

  1. 零开销：#if 是预处理期判断，编译后只有一套代码，没有运行时分支。
  2. 正确性：位域的内存排列依赖编译器实现，#if 保证选中的版本能生成正确的线上字节。运行时判断无法改变已编译的位域排列。

双版本的设计：小端机器选 LE 版（位域从低位排列），大端机器选 BE 版（位域从高位排列），两者生成的线上字节都符合 RFC。

Q4：tcp_flag_word(tp) |= TCP_FLAG_ACK 为什么能一条指令设置一个 flag？

答案

tcp_flag_word(tp) 通过 union tcp_word_hdr cast 取出 TCP 头的第 4 个 32 位字（words[3]），这个字包含 res1(4) + doff(4) + 8 个 flag(8) + window(16) 的原始字节。

TCP_FLAG_ACK = __constant_cpu_to_be32(0x00100000) 是一个编译期常量，已经在本机字节序下正确排列。words[3] |= TCP_FLAG_ACK 编译成一条 or 指令——读 32 位、OR 常量、写回 32 位。

对比位域写法 th->ack = 1：编译器要读整个 __u16（含 doff 和其他 flag）、用位掩码设置 ack 位、写回 __u16。如果只设一个 flag，两者差异不大；但如果要同时设/清多个 flag（如 SYN+ACK），整字 OR/AND 只需一条指令，位域要多次读-改-写。

Q5：usb_device_descriptor 的成员排列已经让 __le16 落在偶数偏移，为什么还要加 packed？

答案

三个理由：

  1. 防御性：不同编译器（非 gcc）可能给 __le16 不同的对齐策略。packed 保证所有编译器下 sizeof 都等于 18（线上字节数）。
  2. 降 align 到 1：USB 描述符可能出现在任意地址（不对齐的 USB 缓冲区），align=1 允许结构体指针指向任意地址。
  3. API 约定：include/uapi/linux/usb/ch9.h 开头明确注释：「Note all descriptors are declared 'attribute((packed))'」——这是 USB 子系统的约定，所有描述符统一加 packed，避免遗漏。
