GNU C in the Linux Kernel

一句话概括这一章：把 CH1/CH2 的工具，放回它真正被用的地方去看。 CH3 是「没有 OS 的裸机」；这一章是「有内核的情况下，同一套扩展怎么被用到极致」。

前置：CH1 · CH2 配合阅读：CH3 嵌入式驱动实战（同一个 packed 结构体，在裸机和驱动里的用法差别）

本章讲什么

CH1/CH2 告诉你有这些工具。但你第一次打开 include/linux/list.h 或 kernel/module.c 时仍然会懵——因为它们是组合使用的。

这一章回答三个具体问题：

  1. 内核为什么几乎不用链表库而要 container_of 反推结构体？
  2. module_init() 没有任何地方调用它，它到底什么时候跑？
  3. 一个 .ko 从 insmod 到 .init 段被释放，中间发生了什么？

第 3 问的答案跟 CH2 的 2.1 section 是同一件事：用 __attribute__((section)) 把一批函数指针放进同一个段，链接器自动收集成一张表。

代码自测（点击展开）

Q1：module_init(fn) 展开后到底发生了什么？

答案

它不是函数调用，而是放置。展开后大致等价于：

static initcall_t __initcall_fn6 __used __attribute__((__section__(".initcall6.init"))) = fn;

也就是把 fn 的地址放进 .initcall6.init 这个段。链接脚本里把这个段的起止地址导出为 __initcall_start[]/__initcall_end[]，内核启动时用 for (call = __initcall_start; call < __initcall_end; call++) (*call)(); 依次执行。

所以 module_init 从来没有被谁显式调用过——它是被链接器和启动循环找出来的。这就是 CH2 所说的「链接期语义」。

Q2：为什么内核的链表是「链表节点嵌在结构体里」，而不是「结构体指针挂在链表上」？

答案

后者需要每种数据类型各写一份链表实现（或用 void* 丢掉类型）。前者只写一份 struct list_head 的通用操作，用 container_of 从成员地址反推宿主地址，同时保留完整类型信息。

代价：一个对象只能同时属于一条 list_head 链表（需要多条链表就要多个 list_head 成员——所以 struct task_struct 里有好几个）。

Q3：__init 修饰的函数/数据最后去哪了？

答案

它们被放进 .init.text / .init.data 段。内核启动完成后会调用 free_initmem() 把整个段的页释放掉，回收内存（嵌入式上能回收几百 KB 到几 MB）。

副作用：这些函数只能调用一次。已经释放的地址如果再被调到，就是踩野内存——这也是驱动里 __init 不能乱标的原因。

4.1

内核模块的加载与符号决议：内核视角

← CH4 内核模块 · 4.2 initcall 机制 · 4.3 container_of 与侵入式链表

本篇讲一个 .ko 从 insmod 到 init_module() 被调用的全过程，但只从 C 语言 / GNU 扩展视角看。 它把 CH1/CH2 的工具放回内核真正用它的地方： - 4.2 讲了「内建版」module_init 用 __attribute__((section)) 把函数指针收进 .initcall6.init；本篇讲「模块版」module_init 用 __attribute__((alias)) 造出标准名 init_module，再由 modpost 生成的 .mod.c 用指定初始化填进嵌入的 struct module 实例——三件套（section + alias + 指定初始化）闭环。 - CH2 2.1 讲了 __attribute__((section)) 的语法；本篇讲它怎么撑起导出符号表、模块元信息、版本印章三张表。 - CH6 链接脚本 讲了 ELF 与链接概念；本篇讲内核怎么在运行期手写一个"动态链接器"：分配内存、拷贝段、解析未决符号、应用重定位。

全部结论有 WSL 实测（gcc 13.3 / clang 18.1.3 / x86-64）+ 内核 v6.6 源码核对（kernel/module/main.c、include/linux/export.h、include/linux/module.h、scripts/mod/modpost.c、arch/x86/kernel/module.c）。配套 demo 在 demo/4.1-module/。

本节讲什么

.ko 是一段「没有 ld.so 的可重定位 ELF」。用户态 dlopen 把脏活丢给 ld-linux.so；内核态没有这个帮手——kernel/module/main.c 的 load_module() 自己当动态链接器：读 ELF、分配可执行内存、拷段、把模块里那些未决的符号拿到内核的导出表里去查、拿到地址后手写重定位条目把 CALL 的位移 patch 上，最后调 mod->init()。

本篇回答一组具体问题：

问题 本篇回答
.ko 和 .so 本质差在哪？ .ko 是 ET_REL（可重定位），没有 PT_LOAD/INTERP/DYNAMIC；加载地址运行期才定，所以不能预链接
EXPORT_SYMBOL(fn) 到底「注册」了什么？ 一条记录进段里（v6.6 源码层是 .export_symbol 段的 asm 记录，modpost 转成 __ksymtab 段的 struct kernel_symbol）——和 initcall 同一个 section 套路
模块里 printk 这种「未决符号」怎么被找到？ resolve_symbol → find_symbol 在 __ksymtab 上 bsearch——不是 dlsym
重定位是谁做的？ 内核手写的 apply_relocate_add：val = S + A（绝对）/ S + A - P（PC 相对）逐条写到 loc，跟 ld 在链接期做的一模一样，只是挪到了运行期
为什么换内核就得重编模块？ vermagic 字符串和符号 CRC 两道门禁，防止 ABI 不兼容的模块被装进去
module_init(xxx_init) 之后，mod->init 怎么就有了？ __attribute__((alias)) 让 init_module 成为 xxx_init 的别名；modpost 生成的 .mod.c 用指定初始化 .init = init_module 填进 __this_module——编译期就定了，不是运行时查的
模块的 .init.text 加载完去哪了？ init 跑完 do_free_init 把 MOD_INIT_* 三段页释放掉（对应内建版的 free_initmem）

一句话：用户态的「链接」在编译期由 ld 做完；内核模块的「链接」在加载期由 module.c 重做一遍。 懂了这一点，insmod 就不再是黑魔法。

一、.ko 是什么：可重定位 ELF

1.1 与用户态动态库的根本差异

先看 file 和 readelf 怎么区分两者：

$ file hello.ko
hello.ko: ELF 64-bit LSB relocatable, x86-64, ...    ← relocatable（ET_REL）

$ file libfoo.so
libfoo.so: ELF 64-bit LSB shared object, x86-64 ...  ← shared object（ET_DYN）
用户态 .so 内核模块 .ko
ELF 类型 ET_DYN（可共享） ET_REL（可重定位）
程序头 PT_LOAD 有，划分段映射 无（只有段头 SHT_*）
入口定位 ld-linux.so 读 INTERP/DYNAMIC 没有 ld.so，module.c 自己来
加载地址 通常固定（或 PIC 可浮动） 运行期 module_alloc 才定，所以必须可重定位
符号决议 dlsym / _dl_runtime_resolve find_symbol 在 __ksymtab 上 bsearch
重定位 启动时 ld 应用 R_X86_64_RELATIVE 等 insmod 时 apply_relocate_add 手写应用
卸载 dlclose rmmod → cleanup_module

为什么 .ko 必须是可重定位的？ 因为模块的加载地址在 module_alloc 时才确定（vmalloc 区，地址每次都不同），链接器在编译期不可能知道最终地址，所以只能把所有「用到地址的地方」留成重定位条目，等加载时填。这跟用户态 .o（目标文件）是同一种东西——.ko 本质上就是一个带模块元信息的目标文件。

1.2 .ko 的关键段

readelf -S hello.ko 能看到的段，远比普通 .o 丰富——多了好几张「表」：

段 放什么 谁产生的
.text .data .rodata .bss 模块的代码/数据 gcc -c
.modinfo vermagic=... license=... 等元信息 MODULE_INFO 宏（→ __attribute__((section(".modinfo")))）
__ksymtab / __kcrctab 模块自己导出的符号表 + CRC modpost 由 .export_symbol 转换而来
__ksymtab_gpl / __kcrctab_gpl GPL-only 导出 同上
.gnu.linkonce.this_module 嵌入的 struct module __this_module 实例 modpost 生成的 .mod.c
__versions 模块引用的每个外部符号的 CRC modpost（CONFIG_MODVERSIONS）
__param .init_array __jump_table __tracepoints_ptrs … 参数表/构造函数/jump label/tracepoint 各自的宏

三、EXPORT_SYMBOL：符号注册的 section 魔法

3.1 v6.6 的两阶段设计（重要：已重构）

这是本篇最容易踩过时资料的地方。v6.4 之前，EXPORT_SYMBOL(fn) 长这样（旧版）：

struct kernel_symbol { unsigned long value; const char *name; const char *namespace; };
#define ___EXPORT_SYMBOL(sym, sec, ns) \
    static const char __kstrtab_##sym[] = #sym;          \
    static const char __kstrtabns_##sym[] = ns;          \
    __ksymtab sym: __attribute__((section("__ksymtab"+sec), used, aligned(4))) = \
        { (unsigned long)&sym, __kstrtab_##sym, __kstrtabns_##sym }

v6.6 起重构了（include/linux/export.h），源码层改用 asm() 直接往 .export_symbol 段塞扁平记录，不再用 C 级 struct：

/* include/linux/export.h — v6.6 */
#define ___EXPORT_SYMBOL(sym, license, ns)        \
    .section ".export_symbol","a"   ASM_NL         \   ← 一个统一段
    __export_symbol_##sym:          ASM_NL         \
        .asciz license               ASM_NL        \   ← 许可证
        .asciz ns                    ASM_NL        \   ← 命名空间
        __EXPORT_SYMBOL_REF(sym)     ASM_NL        \   ← 符号地址（.quad/.long）
    .previous

#ifdef CONFIG_64BIT
#define __EXPORT_SYMBOL_REF(sym)  .balign 8  ASM_NL  .quad sym
#else
#define __EXPORT_SYMBOL_REF(sym)  .balign 4  ASM_NL  .long sym
#endif

/* C 上下文入口 */
#define __EXPORT_SYMBOL(sym, license, ns)            \
    extern typeof(sym) sym;          /* 类型检查 */  \
    __ADDRESSABLE(sym)              /* 取地址，防优化 */ \
    asm(__stringify(___EXPORT_SYMBOL(sym, license, ns)))

源码层每条 EXPORT_SYMBOL(fn) 在 .export_symbol 段留下一条 [license][namespace][符号地址] 的扁平记录。但这还不是运行时查的表——

3.2 modpost 把 .export_symbol 转成 __ksymtab + __kcrctab

运行时，find_symbol()（main.c:302）查的是 __ksymtab / __kcrctab 这两个段名（旧名字）：

/* kernel/module/main.c:304 */
static const struct symsearch arr[] = {
    { __start___ksymtab, __stop___ksymtab, __start___kcrctab,        NOT_GPL_ONLY },
    { __start___ksymtab_gpl, __stop___ksymtab_gpl, __start___kcrctab_gpl, GPL_ONLY },
};

这说明 __ksymtab 是 build tool（scripts/mod/modpost）在链接期由 .export_symbol 记录汇总出来的。struct kernel_symbol 仍在用（定义在 kernel/module/internal.h:35），v6.6 还支持 PREL32 紧凑形态：

/* kernel/module/internal.h:35 */
struct kernel_symbol {
#ifdef CONFIG_HAVE_ARCH_PREL32_RELOCATIONS
    int value_offset;        /* 4 字节，相对偏移 */
    int name_offset;
    int namespace_offset;    /* 合计 12 字节，无指针 */
#else
    unsigned long value;
    const char *name;
    const char *namespace;   /* 直接指针形态，24 字节 */
#endif
};

PREL32 形态下整个 kernel_symbol 只有 12 字节，且不含绝对地址——value_offset 是「符号地址相对 value_offset 自身位置的偏移」，加载时不用再 patch（和 4.2 initcall 的 PREL32 同一个机制）。

3.3 运行时查找：bsearch（T1 实测）

find_exported_symbol_in_section（main.c:276）对排好序的 __ksymtab 做二分查找：

sym = bsearch(fsa->name, syms->start, syms->stop - syms->start,
              sizeof(struct kernel_symbol), cmp_name);

cmp_name 内部调 kernel_symbol_name(sym)——PREL32 时是 offset_to_ptr(&sym->name_offset)，直接形态时是 sym->name。

T1 demo 用 C 级 __attribute__((section("my_ksymtab"))) 直接模拟（跳过 PREL32，用直接指针，16 字节一条）。sizeof(struct ksym)=16 必须等于段步长，否则段对齐填充会让 __stop-__start 的计数错位（这是本批实测踩的第一个坑，见文末坑表）。

注意几个和内核一一对应的设计点：

  1. CRC 单独放（fake_crc 现算）——内核也是 __ksymtab 放 {name,value}、__kcrctab 单独放 s32 CRC 数组，两表下标一一对应（main.c:2106：mod->syms = section_objs(info,"__ksymtab",...); mod->crcs = section_addr(info,"__kcrctab")）。
  2. 加载时排序——__ksymtab 段里的条目顺序由链接顺序决定，是无序的；内核启动时（main.c 的 sort_symtab）排序后才能 bsearch。T1 的 qsort 就是这一步。
  3. GPL 分表——EXPORT_SYMBOL 进 __ksymtab（NOT_GPL_ONLY），EXPORT_SYMBOL_GPL 进 __ksymtab_gpl（GPL_ONLY）。非 GPL 模块查 GPL 表会被 find_exported_symbol_in_section 的 if (!fsa->gplok && syms->license == GPL_ONLY) return false; 挡掉。

四、符号决议：resolve_symbol + CRC

4.1 决议流程（main.c:1109）

模块里每个未决符号（st_shndx == SHN_UNDEF）都走一遍 resolve_symbol：

static const struct kernel_symbol *resolve_symbol(struct module *mod,
        const struct load_info *info, const char *name, char ownername[])
{
    struct find_symbol_arg fsa = { .name = name, ... };
    if (!find_symbol(&fsa))       goto unlock;        /* 1. 查 __ksymtab */
    if (fsa.license == GPL_ONLY)  mod->using_gplonly_symbols = true;
    if (!inherit_taint(mod, fsa.owner, name)) ...;     /* 2. 污染传播 */
    if (!check_version(info, name, mod, fsa.crc))       /* 3. CRC 校验 */
        return ERR_PTR(-EINVAL);
    err = verify_namespace_is_imported(info, fsa.sym, mod);  /* 4. 命名空间 */
    err = ref_module(mod, fsa.owner);                  /* 5. 引用计数 */
}
步骤 失败后果 对应什么
1 find_symbol -ENOENT，模块加载失败 符号根本没导出
2 inherit_taint 不传染污染标记 非 GPL 模块用了被污染内核的符号
3 check_version -EINVAL（CONFIG_MODVERSIONS） CRC 对不上，ABI 变了
4 verify_namespace -ENXIO 没声明 MODULE_IMPORT_NS(NS)
5 ref_module -EBUSY | 0 模块依赖计数

决议成功后，这个符号的 st_value（在 simplify_symbols 里）会被改成内核侧查到的真实地址，供下一步重定位使用。

4.2 CRC（CONFIG_MODVERSIONS）

不开 MODVERSIONS 时只比对 vermagic 字符串（见第六节）；开了之后，每个引用的符号都单独比对 CRC。__versions 段里每条是 { unsigned long crc; char name[MODULE_NAME_LEN]; }（include/linux/module.h 的 struct modversion_info）。

CRC 由 genksyms 工具在编译期对符号的「签名」（参数类型、结构体布局）求出。如果内核改了 printk 的签名，CRC 就变，旧模块装不进去——哪怕 vermagic 字符串一样。

五、重定位：apply_relocate_add 的真实公式

5.1 分派（main.c:1440）

apply_relocations 遍历所有段，按重定位段类型分派：

for (i = 1; i < info->hdr->e_shnum; i++) {
    unsigned int infosec = info->sechdrs[i].sh_info;
    if (info->sechdrs[i].sh_type == SHT_REL)
        err = apply_relocate(...);          /* 无 addend 的旧式 */
    else if (info->sechdrs[i].sh_type == SHT_RELA)
        err = apply_relocate_add(...);     /* 有 addend，x86-64 用这个 */
}

apply_relocate / apply_relocate_add 是 arch-specific 的——x86 定义在 arch/x86/kernel/module.c，arm64 在 arch/arm64/kernel/module.c。

5.2 x86-64 的核心公式（arch/x86/kernel/module.c:166）

val = sym->st_value + rel[i].r_addend;          /* val = S + A */
switch (ELF64_R_TYPE(rel[i].r_info)) {
case R_X86_64_NONE:   continue;
case R_X86_64_64:     size = 8; break;           /* 写 8 字节绝对地址 */
case R_X86_64_32:     if (val != *(u32*)&val) goto overflow; size = 4; break;
case R_X86_64_32S:    if ((s64)val != *(s32*)&val) goto overflow; size = 4; break;
case R_X86_64_PC32:
case R_X86_64_PLT32:  val -= (u64)loc; size = 4; break;   /* PC 相对，最常见 */
case R_X86_64_PC64:   val -= (u64)loc; size = 8; break;
}
write(loc, &val, size);

两种公式记住即可：

公式 含义 典型重定位 用在哪
val = S + A 绝对地址 R_X86_64_64/_32/_32S 取函数指针、全局变量地址
val = S + A - P PC 相对（P=loc，即被 patch 处） R_X86_64_PC32/_PLT32 CALL/JMP 指令的 disp32——模块里调 printk 走这个

R_X86_64_PLT32（type 4）在现代 gcc/clang 上是 CALL 未决符号的默认类型，和 R_X86_64_PC32（type 2）公式相同——PLT32 名字保留了用户态 PLT 的历史，在内核里没有 PLT，就是 PC 相对。

5.3 CALL 的 addend = -4 从哪来

一条 call disp32 是 e8 xx xx xx xx，5 字节。CPU 执行时 PC 已经指向下一条指令（call 地址 + 5）。但 ELF 的 r_offset 指向 disp32 字段（call 的第 2 字节），所以 P = r_offset 地址，而真正要算的相对量是 S - (call_addr + 5) = S - (P + 4)。所以 addend = -4，公式 S + A - P = S + (-4) - P = S - (P+4) = S - (call+5)。✓

5.4 实测：手搓 CALL + 应用 R_X86_64_PC32（T2）

T2 手写一段「模块 .text」（call 0; ret），构造一条 R_X86_64_PC32 addend=-4 指向 target_printk，应用公式后调用：

=== T2: 重定位公式 S+A / S+A-P ===
patch 前  disp32 = 0x00000000  (模块 call 未决议)
公式: val = S + A - P = 0x401236 + (-4) - 0x41ef1001 = 0xffffffffbe510231
patch 后  disp32 = 0xbe510231
运行期校验: call_addr+5+disp = 0x401236  == target_printk 0x401236 ? YES

--- 调用 patch 后的模块代码 ---
[resolved] module called printk via relocated call

disp = 0xbe510231 是负数（0xffffffffbe510231 的低 32 位）——因为 target_printk 在低地址、模块页在更高处，得往回跳。patch 后 call_addr + 5 + disp 精确等于 target_printk，调用成功。

demo 用 MAP_32BIT 把模块页放在低 2GB——这恰恰对应内核的 -mcmodel=kernel 约束：内核模块必须落在内核代码 ±2GB 内，否则 R_X86_64_PC32 的 32 位位移装不下，会触发内核 apply_relocate_add 里的 overflow 分支，打印 likely not compiled with -mcmodel=kernel 并拒绝加载。

5.5 压轴：真实 ELF 重定位加载器（T5）

T5 编一个 t5_module.c（extern void kernel_print(void); int module_entry(void){ kernel_print(); return 42; }）成可重定位 .o，加载器真解析 ELF：找 .text/.symtab/.strtab/.rela.text，把 .text 拷到可执行页，逐条 Elf64_Rela 应用公式，最后调 module_entry。

七、__this_module：指定初始化 + alias 闭环

这是本篇把 CH1/CH2 三件套串起来的关键。mod->init 不是运行时查表查出来的。

7.1 module_init 的模块版（include/linux/module.h）

#ifdef MODULE   /* 编译成可加载模块 */
#define module_init(initfn)                                \
    static inline initcall_t __maybe_unused __inittest(void) { return initfn; }  /* 编译期类型检查 */
    int init_module(void) __copy(initfn)                  \
        __attribute__((alias(#initfn)));                  /* ← alias 造标准名 */
    ___ADDRESSABLE(init_module, __initdata);

__attribute__((alias("initfn"))) 让 init_module 成为 initfn（你写的 xxx_init）的别名——同一个地址、同一个代码，只是挂了两个符号名。这样内核加载器只认标准名 init_module，不必知道你起的名。（内建版则走 __initcall 进 .initcall6.init 段，见 4.2。）

7.2 modpost 生成的 .mod.c 模板（scripts/mod/modpost.c:1930）

__visible struct module __this_module
__section(".gnu.linkonce.this_module") = {     /* ← section 放进专属段 */
    .name = KBUILD_MODNAME,
    .init = init_module,                       /* ← 指定初始化，填 alias */
    .exit = cleanup_module,                    /* ← 同理 */
    .arch = MODULE_ARCH_INIT,
};

这一段把三件套全用上了：

元素 出处 作用
__section(".gnu.linkonce.this_module") CH2 2.1 把 struct module 实例放进专属段，--gc-sections 不敢删（__used+被引用）
.init = init_module CH1 1.2 指定初始化，只填关心的字段，其余零值
init_module 是 xxx_init 的 alias CH2 2.4 标准名指向用户函数

所以 mod->init 在编译期就定好了：它就是 __this_module.init 这个函数指针字段，值为 init_module（== xxx_init）的地址。load_module 把 .gnu.linkonce.this_module 段 memcpy 到最终地址（move_module，main.c:2222），重定位只修正这个绝对地址（PREL32 形态下连这步都省了）。do_init_module 直接 mod->init() 即可。

Q1：module_init(xxx_init) 在模块版和内建版分别展开成什么？为什么模块版不用 section？

答案
  • 内建版（#ifndef MODULE）：module_init(x) → __initcall(x);，即把 x 的函数指针收进 .initcall6.init 段，boot 时 do_initcalls 遍历段调用。用 section（见 4.2）。
  • 模块版（#else）：module_init(x) → int init_module(void) __attribute__((alias(#x)));，造一个标准名 init_module 指向 x。不用 section，因为模块不需要 boot 时批量调用——它有自己的 struct module __this_module 实例，.init = init_module 在编译期就填好了，load_module 找到 __this_module 就能拿到入口。

两者殊途同归：内建靠链接器段收集（批量、boot 时），模块靠 alias+指定初始化（单个、加载时）。

Q2：模块里 printk 是未决符号，它什么时候、被谁、用什么算法找到的？

答案
  • 什么时候：load_module → simplify_symbols 阶段，遍历 .symtab，对每个 st_shndx == SHN_UNDEF 的符号调 resolve_symbol。
  • 被谁：resolve_symbol → find_symbol（main.c:302）。
  • 什么算法：bsearch 在排好序的 __ksymtab（普通）和 __ksymtab_gpl（GPL-only）上二分查找。找到后还要过 CRC（check_version）和命名空间（verify_namespace_is_imported）两关。
  • 之后该符号的 st_value 被改成查到的内核地址，供 apply_relocate_add 用。

Q3：R_X86_64_PC32 的 addend 为什么是 -4？为什么内核模块要用 -mcmodel=kernel 编？

答案

call disp32 是 5 字节，r_offset 指向 disp32（第 2 字节），P = r_offset 地址。CPU 算的目标是 S - (call_addr + 5) = S - (P + 4)。公式 val = S + A - P 要等于 S - (P+4)，故 A = -4。

-mcmodel=kernel：内核代码在地址空间高区（负地址区），模块必须落在内核 ±2GB 内，R_X86_64_PC32 的 32 位位移才装得下。否则 apply_relocate_add 走 overflow 分支，报 likely not compiled with -mcmodel=kernel 拒绝加载。本批 T2/T5 用 MAP_32BIT 复现了这个约束。

Q4：v6.6 的 EXPORT_SYMBOL 和旧版有什么不同？为什么 .export_symbol 段在 find_symbol 里看不到？

答案

v6.4 前用 C 级 __attribute__((section("__ksymtab"))) 直接放 struct kernel_symbol；v6.6 重构成 asm() 往 .export_symbol 段塞扁平 [license][namespace][符号地址] 记录。

.export_symbol 是源码层中间态，在 .o 里；find_symbol 查的 __ksymtab/__kcrctab 是 build tool（modpost）在链接期汇总出来的运行时表。两阶段：源码 .export_symbol（每条导出一记录）→ modpost 汇总成 __ksymtab（struct kernel_symbol 数组，PREL32 形态 12B）+ __kcrctab（s32 CRC 数组）。

Q5：mod->init 是运行时查表查出来的吗？为什么？

答案

不是。module_init(xxx_init) 用 __attribute__((alias)) 造出 init_module（== xxx_init）；modpost 生成的 .mod.c 用指定初始化 .init = init_module 把它填进 __this_module（.gnu.linkonce.this_module 段里的 struct module 实例）。所以 mod->init 在编译期就定了。load_module 只需把 __this_module 段 memcpy 到最终地址，do_init_module 直接 mod->init()。它不是未决符号，不需要 resolve_symbol。

三件套闭环：section（放专属段）+ 指定初始化（CH1 1.2）+ alias（CH2 2.4）。

4.2

initcall 机制全解：链接器替你写注册代码

归属：CH4 · 内核模块与子系统的 GNU C 应用 · ★★★ 优先 实测环境：WSL · gcc 13.3.0（GNU ld 2.42）/ x86-64 · 内核源码 v6.6 前置：CH2 2.1 section · CH2 2.4 weak/alias · CH2 2.2 aligned/packed 配合：4.1 模块加载与符号决议 · CH3 嵌入式驱动 · CH6 链接脚本 demo：demo/4.2-initcall/（11 个源文件 + 4 个链接脚本 + run.sh，一键复现全部结论）

本节讲什么

打开任何一个 Linux 驱动，你都会看到这样的代码：

static int __init my_driver_init(void) { ... }
module_init(my_driver_init);

这行 module_init 看起来像函数调用，但它从来不会被谁显式调用。它到底什么时候跑？答案是：链接器和启动循环替你找了它。

module_init 是一个宏，它的展开取决于一个编译开关 MODULE：

  • 编译成 .ko 模块时（MODULE 已定义）：它用 2.4 的 alias 属性把你的函数变成名为 init_module 的全局符号别名。内核的 load_module 从 ELF 符号表找到 init_module，存到 mod->init，insmod 时调用 do_one_initcall(mod->init)。
  • 编译进 vmlinux 内建时（MODULE 未定义）：它用 2.1 的 section 属性把函数指针放进 .initcall6.init 段。链接脚本把这个段的起止地址导出为 __initcall6_start/__initcall7_start，内核启动时用 for (fn = __initcall6_start; fn < __initcall7_start; fn++) (*fn)(); 依次执行。

同一个宏，两种完全不同的实现，由 #ifdef MODULE 切换。这是 CH1/CH2 学过的 section + alias 两个属性联合用到极致的地方。

本节用用户态模拟 + 内核 v6.6 源码核对把这条链路从头到尾钉死。

一、module_init 的两个版本

1.1 模块版：alias 属性

include/linux/module.h（v6.6，line 125-130）：

#define module_init(initfn)                    \
    int init_module(void) __copy(initfn)       \
        __attribute__((alias(#initfn)));       \
    ___ADDRESSABLE(init_module, __initdata);

展开 module_init(my_init) 后，等价于：

int init_module(void) __attribute__((alias("my_init")));

alias 属性（见 2.4.4）让 init_module 和 my_init 指向同一个地址。__copy 复制目标函数的属性（如 __init、noinline），___ADDRESSABLE 生成一个引用 init_module 符号的数据项，确保 --gc-sections 不会删掉它。

实测 T5（用户态用 dlsym 模拟内核的符号查找）：

static int my_driver_init(void) { printf("  my_driver_init\n"); return 0; }
int init_module(void) __attribute__((alias("my_driver_init")));

/* 模拟内核 load_module 从 ELF 符号表找 init_module */
void *handle = dlopen(NULL, RTLD_NOW);
initcall_t fn = (initcall_t)dlsym(handle, "init_module");
fn();   /* 实际执行 my_driver_init */

$ nm t5 | grep -E "init_module|my_driver_init"
0000000000001340 T init_module          ← 大写 T：全局可见
0000000000001340 t my_driver_init        ← 小写 t：局部，同地址

关键：init_module 和 my_driver_init 是同一个地址。内核不需要知道你写的函数叫什么名字——它只认 init_module 这个固定符号名。alias 属性帮你把任意名字的函数挂到这个固定符号上。

1.2 内建版：section 属性

include/linux/init.h（v6.6，line 88）：

#ifndef MODULE
...
#define __initcall(fn) device_initcall(fn)          /* device_initcall → __define_initcall(fn, 6) */
#define module_init(x)  __initcall(x);

展开 module_init(my_init) 后，等价于：

static initcall_t __initcall_my_init __used
    __attribute__((section(".initcall6.init"))) = my_init;

也就是把 my_init 的地址放进 .initcall6.init 段。这里没有 alias——函数本身还是 static，只是它的地址被一个段里的指针变量引用。

二、__define_initcall 宏链：从宏到段的全过程

内建版的 module_init(x) 展开成 __initcall(x) → device_initcall(fn) → __define_initcall(fn, 6)。完整的宏链在 include/linux/init.h（v6.6）：

__define_initcall(fn, 6)
  → ___define_initcall(fn, 6, .initcall6)
    → __unique_initcall(fn, 6, ".initcall6", __initcall_id(fn))
      → ____define_initcall(fn, stub, name, ".initcall6.init")
        → static initcall_t name __used
              __attribute__((section(".initcall6.init"))) = fn;

最终产物就是一行：

static initcall_t __unique_name __used
    __attribute__((section(".initcall6.init"))) = fn;

__used（即 __attribute__((used))）告诉编译器"这个变量看起来没被引用，但别删它"——因为引用它的代码在另一个文件（init/main.c 的 do_initcalls），编译器在单个文件里看不到引用。

2.2 模块版的级别退化

include/linux/module.h（v6.6，line 111-123）——模块版所有级别宏全部退化成 module_init(fn)：

#define early_initcall(fn)      module_init(fn)    /* 模块里没有 early */
#define core_initcall(fn)       module_init(fn)
#define subsys_initcall(fn)     module_init(fn)
#define device_initcall(fn)     module_init(fn)
#define late_initcall(fn)       module_init(fn)
/* ... 全部一样 */

为什么？ 模块是运行期加载的，不存在"启动顺序"概念——insmod 时刻就是它的"启动"。所有模块的 init 函数都在 do_init_module 里被直接调用，没有级别区分。

误区：在模块代码里写 subsys_initcall(fn) 以为能控制加载顺序——没用，它就是 module_init(fn)。模块的加载顺序由 insmod/modprobe 的调用顺序和依赖关系决定，与 initcall 级别无关。

2.3 LTO 的特殊处理

CONFIG_LTO_CLANG 开启时（init.h line 222-237），__initcall_section 会为每个 initcall 生成独立的段名（如 .initcall6.init.0、.initcall6.init.1），再由 scripts/link-vmlinux.sh 生成的链接脚本指定顺序。

原因：LTO（Link-Time Optimization）下编译器不保证链接顺序等于源码出现顺序。为了保留正确的 initcall 顺序，每个指针必须放在自己的段里，由链接脚本显式排序。

这是"链接顺序决定执行顺序"（见第六节）在 LTO 下的妥协——用更多段换确定性。

三、链接脚本：段是怎么被收集成表的

3.1 INIT_CALLS 宏

include/asm-generic/vmlinux.lds.h（v6.6，line 913-927）：

#define INIT_CALLS_LEVEL(level)                \
    __initcall##level##_start = .;             \  /* 导出段起始符号 */
    KEEP(*(.initcall##level##.init))            \  /* 收集该级别所有指针 */
    KEEP(*(.initcall##level##s.init))           \  /* 收集 sync 变体 */

#define INIT_CALLS                             \
    __initcall_start = .;                       \  /* 全局起始 */
    KEEP(*(.initcallearly.init))                \  /* early */
    INIT_CALLS_LEVEL(0)                          \  /* pure */
    INIT_CALLS_LEVEL(1)                          \  /* core */
    INIT_CALLS_LEVEL(2)                          \
    INIT_CALLS_LEVEL(3)                          \
    INIT_CALLS_LEVEL(4)                          \
    INIT_CALLS_LEVEL(5)                          \
    INIT_CALLS_LEVEL(rootfs)                     \  /* rootfs（在 5 和 6 之间） */
    INIT_CALLS_LEVEL(6)                          \  /* device */
    INIT_CALLS_LEVEL(7)                          \  /* late */
    __initcall_end = .;                           /* 全局结束 */

链接后，__initcall0_start 到 __initcall7_start 是 8 个地址，分别指向各级别段的起始。do_initcalls 用 __initcall_end 作为总结束。

3.2 KEEP() 不能省

KEEP() 告诉链接器"即使这个段看起来没被引用，也保留它"。如果没有 KEEP，--gc-sections 会把整个 initcall 段当死代码删掉——因为除了 do_initcalls 的循环，没有任何代码"直接"引用这些指针。

实测 T4（用户态模拟 --gc-sections 的陷阱）：

/* k1/k2/k3 只被 initcall 段引用，没有其他引用 */
static int k1(void) { printf("  k1\n"); return 0; }
SIM_KEEP(k1);  /* 把 k1 的指针放进 .initcall_keep 段 */

/* 链接脚本用了 KEEP */
.initcall_keep : {
    __initcall_keep_start = .;
    KEEP(*(.initcall_keep))
    __initcall_keep_end = .;
}

不带 --gc-sections 时，一切正常（count=3，k1/k2/k3 都打印了）。但加上 --gc-sections 后：

$ gcc -O2 -Wl,--gc-sections -T keep_test.lds t4_keep.c -o t4_gc_keep
$ ./t4_gc_keep
Segmentation fault (core dumped)

为什么崩？ KEEP 保留了 .initcall_keep 段里的指针，但 k1/k2/k3 的函数代码没有其他引用，被 --gc-sections 删掉了。段里指针还在，指向的代码已经没了 → 调用时 segfault。

$ nm t4_gc_keep | grep -E "k1|keep"
0000000000400210 D __initcall_keep_end     ← 段边界符号在
00000000004001f8 D __initcall_keep_start
0000000000400208 d __keep_k1               ← 指针变量在（值是 k1 的地址）
0000000000400000 t k1                      ← 但 k1 的代码已被 gc 删成空壳

这就是内核用 ___ADDRESSABLE(init_module, __initdata) 的原因——它生成一个引用 init_module 符号的数据项，让 --gc-sections 看到"这个符号被引用了"，不会删函数代码。

关键区分：KEEP 保留段内容（指针本身）；___ADDRESSABLE / __used 保留指针指向的目标（函数代码）。两者缺一不可。

4.1 分级遍历

{
    initcall_entry_t *fn;
    parse_args(initcall_level_names[level], ...);   /* 该级别的内核命令行参数 */
    trace_initcall_level(initcall_level_names[level]);
    for (fn = initcall_levels[level]; fn < initcall_levels[level+1]; fn++)
        do_one_initcall(initcall_from_entry(fn));
}

/* 依次执行所有级别 */
static void __init do_initcalls(void)
{
    int level;
    for (level = 0; level < ARRAY_SIZE(initcall_levels) - 1; level++)
        do_initcall_level(level, saved_command_line);
}

4.2 do_one_initcall 的容错

4.3 initcall_from_entry：PREL32 相对偏移

init.h（v6.6，line 122-135）——有两个版本：

#ifdef CONFIG_HAVE_ARCH_PREL32_RELOCATIONS
typedef int initcall_entry_t;    /* 32 位整数：存的是偏移 */

static inline initcall_t initcall_from_entry(initcall_entry_t *entry)
{
    return offset_to_ptr(entry);   /* (char*)entry + *entry */
}
#else
typedef initcall_t initcall_entry_t;  /* 直接存函数指针（8 字节） */

static inline initcall_t initcall_from_entry(initcall_entry_t *entry)
{
    return *entry;                 /* 直接解引用 */
}
#endif

CONFIG_HAVE_ARCH_PREL32_RELOCATIONS 在 ARM64、x86-64 等"支持 PC 相对寻址"的架构上开启。用 32 位相对偏移代替 64 位绝对地址：

绝对地址 PREL32 相对偏移
每项大小 8 字节 4 字节
重定位类型 R_X86_64_64（绝对） R_X86_64_PC32（PC 相对）
1000 项占用 8000 字节 4000 字节
位置无关 否（需重定位） 是（偏移不变）

实测 T8：

$ ./t8

  sizeof(int32_t)      = 4 (PREL32 offset)
  savings per entry    = 4 bytes

  on 1000 initcalls:
    absolute: 8000 bytes

内核有上千个 initcall，PREL32 能省几 KB。更重要的是 PREL32 是位置无关的——内核 KASLR（地址空间随机化）重定位时不需要修改这些条目，因为偏移量不随基址变化。

五、__init 段的生与死

5.1 段的划分

属性 段名 内容 释放时机
__init .init.text init 函数的代码 free_initmem()
__initdata .init.data init 用数据 free_initmem()
__initconst .init.rodata init 用只读数据 free_initmem()
__exit .exit.text exit 函数代码 内建时链接器可删；模块保留

free_initmem() 在启动完成后调用（init/main.c），把 .init.text/.init.data 整段的页还给 buddy allocator。嵌入式上能回收几百 KB 到几 MB。

5.2 释放后不能再用

实测 T6（模拟 free_initmem 后再调用）：

$ ./t6
--- boot phase ---
  late init       ← initcall 正常执行
  middle init
  early init
--- post-boot: free_initmem ---
  free_initmem: marking .init.text as freed
--- calling init again (should warn) ---

  BUG: accessing freed init memory at 0x400250!

误区：在驱动里把运行期也要调用的函数标了 __init——启动后该函数地址指向已释放的页，调用就是踩野内存。__init 只能标"启动时调用一次，之后永不再用"的函数。

六、链接顺序：同级别内的执行顺序

init.h 的注释（v6.6，line 196）：

Ordering inside the subsections is determined by link order.

同一级别内，链接器先收集到的指针先执行。 链接顺序由 Makefile 里 obj-y 的顺序决定。

实测 T10（多源文件链接顺序对照）：

/* t10_a.c */                          /* t10_b.c */                        /* t10_c.c */
int a_driver(void) { ... }              int b_driver(void) { ... }           int c_driver(void) { ... }
SIM_INIT(a_driver);                    SIM_INIT(b_driver);                  SIM_INIT(c_driver);

--- 链接顺序: a b c ---
  [0] 0x4000f0 ->   a_driver       ← a 先
  [1] 0x400110 ->   b_driver
  [2] 0x400130 ->   c_driver

--- 链接顺序: c b a ---
  [0] 0x4000f0 ->   c_driver       ← c 先
  [1] 0x400110 ->   b_driver
  [2] 0x400130 ->   a_driver

同一个源码，只是链接时 .o 的顺序不同，执行顺序就变了。 这就是为什么内核的 Makefile 里 obj-y 的顺序有时很重要——两个驱动如果有隐式依赖（A 必须在 B 前初始化），同级别内只能靠链接顺序保证。

跨级别有显式的级别保证（core 一定在 device 前），同级别内只有链接顺序。如果同级别内有依赖，要么提升到不同级别，要么在 Makefile 里调整 obj-y 顺序。

七、module_exit：卸载的镜像

模块版 module_exit 是 module_init 的镜像：

/* module.h v6.6 */
#define module_exit(exitfn)                     \
    static inline exitcall_t __maybe_unused __exittest(void) \
        { return exitfn; }                     \
    void cleanup_module(void) __copy(exitfn)   \
        __attribute__((alias(#exitfn)));        \
    ___ADDRESSABLE(cleanup_module, __exitdata);

cleanup_module 是 exitfn 的别名。rmmod 时内核调用 mod->exit（即 cleanup_module）。

内建版 module_exit 无效——内建代码不可卸载，__exit 函数在链接时会被删除（--gc-sections 或链接脚本 DISCARD）。

module_init module_exit
模块版别名 init_module cleanup_module
内建版 放进 .initcall6.init 段 无效（内建不可卸载）
调用时机 insmod / 启动循环 rmmod

八、完整链路：从源码到执行

把前面所有环节串起来，内建驱动的完整链路：

源码: module_init(my_init)
  ↓ 预处理 (#ifndef MODULE)
展开: static initcall_t __name __used __attribute__((section(".initcall6.init"))) = my_init;
  ↓ 编译
目标文件: .initcall6.init 段里有一个指向 my_init 的指针
  ↓ 链接 (vmlinux.lds 的 INIT_CALLS_LEVEL(6))
vmlinux: __initcall6_start..__initcall7_start 之间有这个指针
  ↓ 启动 (do_initcalls → do_initcall_level(6))
执行: (*fn)() → my_init()
  ↓ 启动完成 (free_initmem)
释放: .init.text 段（含 my_init 代码）被释放

模块驱动的完整链路：

源码: module_init(my_init)
  ↓ 预处理 (#ifdef MODULE)
展开: int init_module(void) __attribute__((alias("my_init")));
  ↓ 编译
hello.ko: ELF 符号表里有 init_module 符号（地址 = my_init）
  ↓ insmod (load_module)
内核: find_symbol("init_module") → mod->init = init_module
  ↓ do_init_module
执行: do_one_initcall(mod->init) → my_init()
  ↓ rmmod
卸载: mod->exit (= cleanup_module) → my_exit()

# 误区 真相 实测验证

HFT：模块化交易系统的初始化顺序

HFT 行情解析系统通常分多层：网卡抓包 → 协议解码 → 策略引擎 → 风控。它们的初始化有严格依赖：

/* 级别 4：子系统——协议解码框架注册 */

嵌入式设备内存紧张（如 64MB 的网关设备）。__init 段可能占几百 KB——这些代码只启动时跑一次，之后就是死空间。free_initmem 把这些页还给 buddy，可用于运行期分配。

/* 链接脚本收集所有 .myinit* 段 */

代码自测（点击展开）

Q1：module_init(fn) 编译成 .ko 和编译进 vmlinux 时，展开结果有什么不同？

答案
  • .ko（MODULE 已定义）：用 alias 属性，把 fn 变成名为 init_module 的全局符号别名。内核 load_module 从 ELF 符号表找 init_module。
  • vmlinux（MODULE 未定义）：用 section 属性，把 fn 的地址放进 .initcall6.init 段。链接脚本收集段，do_initcalls 遍历执行。

两者都不产生函数调用指令。module_init 从来没有被谁显式调用——它被链接器或符号查找找出来。

Q2：为什么链接脚本里 KEEP(*(.initcall6.init)) 不能省 KEEP？

答案

--gc-sections 会删除"没有被任何代码直接引用"的段。initcall 段里的函数指针只被 do_initcalls 的循环引用——循环在另一个文件（init/main.c），编译器在单个文件里看不到引用。没有 KEEP，整个 initcall 段会被当死代码删掉。

KEEP 保留段内容（指针），但不保留指针指向的函数代码——函数代码要靠 ___ADDRESSABLE 或 __used 保留（见 T4 的 segfault 教学点）。

Q3：在模块驱动里写 subsys_initcall(fn)，和写 device_initcall(fn) 有区别吗？

答案

没区别。模块版（#ifdef MODULE）所有级别宏都退化成 module_init(fn)（见 module.h:111-123）。模块是运行期加载的，不存在"启动顺序"——insmod 时刻就是它的"启动"。

级别只在内建时有效。如果你需要控制模块的加载顺序，只能靠 modprobe 的依赖关系（depends: in .modinfo）。

Q4：__init 修饰的函数在 free_initmem 之后被调用会怎样？

答案

该函数的代码在 .init.text 段，free_initmem 把整段的页释放给 buddy allocator。之后再调用该地址就是踩野内存——可能踩到新分配的数据，也可能触发 page fault（取决于页表是否还在）。

这就是 __init 只能标"启动时调用一次"的函数的原因。运行期也要调用的函数不能标 __init。

Q5：PREL32 相对偏移比绝对地址省了什么？

答案

两样：

  1. 空间：每项 4 字节 vs 8 字节，省一半。内核上千个 initcall，省几 KB。
  2. 重定位：绝对地址需要 R_X86_64_64 重定位项（KASLR 时要逐个修改）；PREL32 用 R_X86_64_PC32（PC 相对），偏移量不随基址变化，不需要重定位。内核 KASLR 重定位时少了几千个重定位项要处理。

Q6：两个同级别的 initcall 有依赖关系（A 必须在 B 前跑），怎么保证顺序？

答案

三种办法：

  1. 提升级别：把 A 放到更早的级别（如 subsys_initcall），B 保持 device_initcall。
  2. sync 变体：A 用 device_initcall，B 用 device_initcall_sync——sync 在该级别所有非 sync initcall 之后执行。
  3. 调整链接顺序：在 Makefile 里把 obj-y 里 A 的 .o 放到 B 前面——同级别内链接顺序决定执行顺序。

最推荐的是方法 1（显式级别）或方法 2（sync）。方法 3 脆弱——Makefile 顺序不直观，容易在重构时被破坏。

本节讲什么

container_of 是"从零件地址找回整机"的工具；侵入式链表是"零件长在整机里"的数据结构。两者结合，让内核用一套代码（list_head + container_of）服务所有结构体——device、task_struct、sk_buff、file、inode……都挂在同一套链表 API 上，零泛型、零虚函数、零运行时开销。

问题 本篇回答
内核的 list_head 只有 2 个指针，怎么挂住上万物种？ 靠 container_of 的 member 参数——同一份宏代码，调用方传不同成员名，回推到不同偏移
list_del 为什么要投毒（LIST_POISON1/2）？ 不投毒，use-after-del 是静默内存腐败；投毒后立刻 segfault，bug 无处藏身

list_for_each_entry_safe 比 list_for_each_entry 多了什么？ 多一个临时变量 n 预存下一个节点——删当前节点不会让遍历崩溃

一、设计哲学：侵入式 vs 外挂式

1.1 两种链表的根本差异

外挂链表（传统）              侵入式链表（内核）
┌──────────┐                 ┌──────────────────┐
│ list_node│ ─► data ─►      │ struct device     │
│  next    │   (malloc 节点)  │   id             │
│  data*   │                 │   name           │
└──────────┘                 │   node {next,prev}│ ◄── 节点内嵌
                             │   irq            │
                             └──────────────────┘
节点和数据分离                节点就是数据的一部分
插入要 malloc                插入零分配
遍历: node→data (2 次访存)   遍历: container_of (1 条 lea)

1.2 实测对比（T1）

sizeof(struct device)     = 40    (含 node 16 字节)
sizeof(struct ext_node)   = 16    (next + data*, 不含数据)
offsetof(node)            = 16
方案 每次插入 内存局部性 一个结构体挂多张链表 裸机/中断可用
外挂链表 malloc 一个节点 差（数据与节点分离，2 次 cache miss） 需要多套节点 ❌（无堆）
侵入式 无 好（节点与数据同 cache line） 多放几个 list_head 即可 ✅

1.3 一个结构体挂多张链表（T2）

这是侵入式链表最核心的能力。同一个 struct device 同时挂在"设备链表"和"IRQ 链表"上：

struct device {
    int              id;
    char             name[12];
    struct list_head node;        /* 挂在设备链表 (偏移 16) */
    unsigned         irq;
    struct list_head irq_node;   /* 同时挂在 IRQ 链表 (偏移 40) */
    int              priority;
};

同一份 list_for_each_entry 宏，member 参数不同，回推到不同偏移：

  via node      -> offsetof(node)      = 16
  via irq_node   -> offsetof(irq_node)  = 40
  d1 via irq_node = &d1 (yes)     d1 via node = &d1 (yes)

实测：设备链表按 id 排序（0→1→2），IRQ 链表按 priority 排序（2→1→0），同一组数据，两种遍历顺序，零额外内存。

CH1 已讲 container_of 宏的语法；这里讲的是"为什么 member 参数能区分回推偏移"——因为 offsetof(type, member) 是编译期常量，不同成员名产生不同常量，运行时只是一条 lea 指令的立即数不同。

二、list_head 的完整 API 设计

2.1 核心结构（v6.6 include/linux/types.h）

struct list_head {
    struct list_head *next, *prev;
};

只有两个指针，16 字节。头节点与普通节点同构——这是一个关键设计决策：遍历到头节点即终止，不需要 NULL 判断（NULL 判断在空链表时需要特判，自指不需要）。

2.2 初始化

#define LIST_HEAD_INIT(name) { &(name), &(name) }   /* 自指 */
#define LIST_HEAD(name) \
    struct list_head name = LIST_HEAD_INIT(name)      /* 静态初始化 */
static inline void INIT_LIST_HEAD(struct list_head *list) {  /* 运行时初始化 */
    list->next = list; list->prev = list;
}

空链表：head->next == head（自指）。list_empty() 就是判 head->next == head。

2.3 插入与删除

/* 核心插入: 4 个指针写入 */
static inline void __list_add(struct list_head *new,
                              struct list_head *prev,
                              struct list_head *next) {
    next->prev = new;
    new->next = next;
    new->prev = prev;
    prev->next = new;
}
static inline void list_add(struct list_head *new, struct list_head *head) {  /* 头插 */
    __list_add(new, head, head->next);
}
static inline void list_add_tail(struct list_head *new, struct list_head *head) {  /* 尾插 */
    __list_add(new, head->prev, head);
}

/* 删除: 先修指针, 再投毒 */
static inline void __list_del(struct list_head *prev, struct list_head *next) {
    next->prev = prev;
    prev->next = next;
}
static inline void list_del(struct list_head *entry) {
    __list_del_entry(entry);
    entry->next = LIST_POISON1;   /* 0x100 + POISON_POINTER_DELTA */
    entry->prev = LIST_POISON2;   /* 0x122 + POISON_POINTER_DELTA */
}
static inline void list_del_init(struct list_head *entry) {  /* 删除+重新初始化 */
    __list_del_entry(entry);
    INIT_LIST_HEAD(entry);          /* 自指, 可安全重用 */
}

2.4 POISON 技巧实测（T3）

LIST_POISON1 = (void *)0x100，LIST_POISON2 = (void *)0x122。

--- 删 b (list_del 投毒) ---
  b.node.next = 0x100 (LIST_POISON1=0x100? yes)
  b.node.prev = 0x122 (LIST_POISON2=0x122? yes)

--- 删 c (list_del_init 自指) ---
  c.node.next = &c.node (自指? yes)
  c.node.prev = &c.node (自指? yes)
  -> c 可以安全重用 (重新 list_add 不会崩)

为什么不直接 NULL 化？ 如果 next = NULL，后续 pos->next 遍历到 NULL 时，container_of(NULL, ...) 返回 NULL - offset = 非空地址（见 hlist 的坑），循环继续 → 读到垃圾内存但不崩溃，bug 静默存在。投毒 0x100 后，任何解引用立刻 page fault，bug 无处藏身。

list_del_init 删除后重新自指——节点可以安全重用（重新 list_add 不会崩）。内核里 list_del_init 比 list_del 更安全，优先用。

三、遍历宏家族

3.1 四层封装（从底层到高层）

/* 第 1 层: 遍历 list_head 指针 (需要手动 container_of 取宿主) */
#define list_for_each(pos, head) \
    for (pos = (head)->next; !list_is_head(pos, (head)); pos = pos->next)

/* 第 2 层: list_entry = container_of 的别名 */
#define list_entry(ptr, type, member) container_of(ptr, type, member)

/* 第 3 层: 直接遍历宿主指针 (最常用) */
#define list_for_each_entry(pos, head, member) \
    for (pos = list_first_entry(head, typeof(*pos), member); \
         !list_entry_is_head(pos, head, member); \
         pos = list_next_entry(pos, member))

/* 第 4 层: safe 版 —— 删当前节点不破坏遍历 */
#define list_for_each_entry_safe(pos, n, head, member) \
    for (pos = list_first_entry(head, typeof(*pos), member), \
         n = list_next_entry(pos, member); \
         !list_entry_is_head(pos, head, member); \
         pos = n, n = list_next_entry(n, member))

3.2 list_for_each_entry 展开实测（T8）

宏完全展开后：

for (pos = container_of(head->next, typeof(*pos), member);  // 初始化
     &pos->member != head;                                    // 条件: 回到头?
     pos = container_of(pos->member.next, typeof(*pos), member))  // 步进

每次步进 = 一次 container_of = typeof（编译期，不生成代码）+ offsetof（编译期常量）+ lea（运行期 1 条指令）。

3.3 safe 版 vs 非 safe 版（T4）

场景 非 safe safe
遍历时删除当前节点 ❌ pos->member.next 被 __list_del 改写，步进取到错误值 ✅ n 预存了下一个，删 pos 不影响 n
额外开销 无 多一个 struct list_head *n 局部变量（栈上，零运行时开销）
适用 只读遍历 需要边遍历边删除

实测（T4）：遍历 5 个节点，删偶数 id：

  visiting id=0, next will be id=1 -> deleting id=0
  visiting id=1, next will be id=2
  visiting id=2, next will be id=3 -> deleting id=2
  visiting id=3, next will be id=4
  visiting id=4, ...               -> deleting id=4
  删除后剩余: id=1 id=3

safe 版的关键：n 在循环初始化时赋值，每次步进时更新——删 pos 后 pos->member 可能已被改写，但 n 已经指向了正确的下一个。

四、零开销验证（T6 反汇编）

4.1 container_of = 一条 lea

struct device {
    char             pad[64];
    int              irq;
    struct list_head node;      /* offsetof = 72 = 0x48 */
    unsigned long long stamp;
};
struct device *get_host(struct list_head *node) {
    return container_of(node, struct device, node);
}

-O2 反汇编（gcc 13.3, x86-64）：

<get_host>:
   endbr64
   lea    -0x48(%rdi),%rax    ; 一条 lea: rax = rdi - 72
   ret

-O0 反汇编：

<get_host>:
   mov    %rdi,-0x18(%rbp)    ; 存 node 到栈
   mov    -0x18(%rbp),%rax    ; 读回
   mov    %rax,-0x8(%rbp)     ; 存 __mptr
   mov    -0x8(%rbp),%rax     ; 读 __mptr
   sub    $0x48,%rax          ; 减偏移

-O0 有 4 次栈上搬运 + 1 条 sub；-O2 全部折叠成 1 条 lea。typeof 的类型检查纯编译期，运行时开销为零。

4.2 list_for_each_entry 遍历循环展开（T6 sum_irqs）

<sum_irqs>:
   mov    (%rdi),%rdx          ; rdx = head->next (第一个节点)
   xor    %ecx,%ecx            ; sum = 0
   lea    -0x48(%rdx),%rax     ; rax = container_of(rdx) = 第一个 device
   cmp    %rdx,%rdi            ; &pos->member == head?
   je     48                  ; 是 -> 结束
.loop:
   mov    0x48(%rax),%rdx     ; rdx = pos->node.next (下一个节点)
   add    0x40(%rax),%ecx     ; sum += pos->irq (offsetof(irq)=0x40)
   lea    -0x48(%rdx),%rax    ; rax = container_of(next) = 下一个 device
   cmp    %rdx,%rdi            ; 回到头?
   jne    .loop
   mov    %ecx,%eax            ; return sum
   ret

关键观察： 1. 没有 call 指令——container_of、list_entry、list_next_entry 全部内联展开 2. 每次循环只有 mov + add + lea + cmp + jne = 5 条指令 3. offsetof 被折叠成常量（0x48、0x40），没有运行时计算

五、hlist：哈希链表与 pprev 的妙用

5.1 为什么要有 hlist

list_head 的头节点占 16 字节（next + prev）。哈希表有 N 个桶，头节点就占 N × 16 字节。对于一个有 65536 个桶的哈希表，头节点就要 1 MB——太浪费了。

hlist 把头节点缩小到 8 字节（只有 first 指针）：

struct hlist_head {
    struct hlist_node *first;    /* 只有 1 个指针, 8 字节 */
};
struct hlist_node {
    struct hlist_node *next;
    struct hlist_node **pprev;   /* 指向前驱的 next 字段的地址 */
};

头节点省一半，代价是节点里用 pprev（二级指针）代替 prev，且失去 O(1) 访问尾节点的能力。

5.2 pprev 的妙用：删头节点不需特判

普通双向链表删头节点：

/* list_head 删头节点: 需要特判 */
if (entry == head->next) {
    head->next = entry->next;   /* 改 head */
}
entry->next->prev = entry->prev;  /* 改后继 */
entry->prev->next = entry->next;

hlist 删任意节点（包括头节点）一条语句搞定：

static inline void __hlist_del(struct hlist_node *n) {
    struct hlist_node *next = n->next;
    struct hlist_node **pprev = n->pprev;
    WRITE_ONCE(*pprev, next);     /* 直接修改前驱的 next 字段 */
    if (next)
        WRITE_ONCE(next->pprev, pprev);
}

为什么 *pprev = next 就够了？ 因为 pprev 指向的是"指向 n 的那个 next 字段的地址"： - 如果 n 是头节点，pprev = &head->first，*pprev = next 直接改 head->first - 如果 n 是中间节点，pprev = &prev->next，*pprev = next 改前驱的 next

无论 n 在哪个位置，*pprev = next 都是正确的操作——不需要 if (n == head->first) 判断。

5.3 实测验证（T5）

sizeof(struct hlist_head) = 8 (只有 1 个指针)
sizeof(struct hlist_node) = 16 (next + pprev)

--- pprev 的妙用: 验证 ---
  bucket[0].first      = 0x7ffcf0a349d8
  first_node->pprev     = 0x7ffcf0a34950
  &buckets[0].first     = 0x7ffcf0a34950 (== pprev? yes)
  -> pprev 指向 head.first 的地址, 删除时 *pprev=next 直接改 head.first

--- 删 bucket[0] 的第一个节点 ---
  删前: first=0x7ffcf0a349d8
  删后: first=0x7ffcf0a34978 (被 *pprev=next 自动改写)
  -> 不需要 if (n == head->first) 判断!

5.4 hlist_entry_safe 的必要性

内核的 hlist_for_each_entry 用了 hlist_entry_safe（先判 NULL 再 container_of）：

#define hlist_entry_safe(ptr, type, member) ({ \
    typeof(ptr) ____ptr = (ptr); \
    ____ptr ? hlist_entry(____ptr, type, member) : NULL; })

为什么需要？ container_of(NULL, ...) = (char *)NULL - offsetof = 负数地址，这不是 NULL！如果不判 NULL，遍历到末尾（next = NULL）时，container_of(NULL) 产生非空地址，循环条件 pos 非 NULL → true → 解引用野指针 → segfault。

实测验证：T5 不加 hlist_entry_safe 时 segfault，加上后正常。

对比 list_head hlist
头节点大小 16 字节 (next+prev) 8 字节 (first)
节点大小 16 字节 16 字节 (next+pprev)
删头节点 需特判 (改 head) 不需特判 (*pprev)
访问尾节点 O(1) (head->prev) O(n)
典型用途 通用双向链表 哈希表桶

六、内核真实用例（T7）

1.1 三种典型用法

/* 1. 全局设备链表: list_head 挂所有设备 */
static struct list_head all_devices;
list_add_tail(&dev->dev_list, &all_devices);

/* 2. 从 file->private_data 取回 priv */
static int my_open(struct file *f) {
    struct mydrv_priv *priv = f->private_data;  /* 直接赋值 */
    /* 或: struct mydrv_priv *priv = container_of(some_member, struct mydrv_priv, member); */
}

/* 3. 按条件查找节点 */
struct mydrv_priv *find_device_by_id(int id) {
    struct mydrv_priv *pos;
    list_for_each_entry(pos, &all_devices, dev_list) {
        if (pos->device_id == id)
            return pos;   /* 找到就 break */
    }
    return NULL;          /* 没找到 */
}

1.2 从内嵌成员反推宿主

/* 从 fops 反推 priv */
struct mydrv_priv *via_fops = container_of(&found->fops, struct mydrv_priv, fops);
/* via_fops == found (yes) */

fops 在 priv 内部的偏移 = 16。container_of(&found->fops, ...) = &found - 16 = &found（因为 fops 在偏移 16 处，减 16 回到首地址）。任何内嵌成员都可以反推宿主——这是 container_of 的万能性。

1.3 netdev_priv：固定偏移加法 vs container_of

/* netdev_priv 用固定偏移加法 (更快, 但不够灵活) */
static inline void *netdev_priv(const struct net_device *dev) {
    return (char *)dev + ALIGN(sizeof(struct net_device), NETDEV_ALIGN);
}

netdev_priv 是加偏移（私有数据在 net_device 之后），container_of 是减偏移（从内嵌成员回退）。前者更快（不需要减），代价是私有数据只能在尾部、大小在分配时确定。

七、RCU 链表

7.1 写入顺序的意义

普通 list_add 写 4 个指针，顺序无所谓。list_add_rcu 的关键是写入顺序：

static inline void __list_add_rcu(struct list_head *new,
                                  struct list_head *prev,
                                  struct list_head *next) {
    new->next = next;      /* 1. 先建好 new->next */
    new->prev = prev;
    smp_wmb();             /* 2. 写屏障: 上面的必须在下面的之前可见 */
    next->prev = new;      /* 3. 修复后继 */
    prev->next = new;      /* 4. 最后才让链表"看到" new (原子点) */
}

为什么最后才写 prev->next？ 因为读者是顺 next 走的。在 prev->next 被修改之前，读者看到的还是旧链表（不包含 new）；修改之后，读者看到的是新链表（包含 new）。由于 smp_wmb 保证了 new->next 先于 prev->next 可见，读者永远不会看到"半插入"的节点（new 在链表上但 new->next 还没设好）。

7.2 读端

#define list_for_each_entry_rcu(pos, head, member) \
    for (pos = list_entry(rcu_dereference((head)->next), typeof(*pos), member); \
         &pos->member != (head); \
         pos = list_entry(rcu_dereference(pos->member.next), typeof(*pos), member))

rcu_dereference 的作用是防止编译器重排读操作——保证读到的 next 是"当前"值，不会被优化到寄存器里缓存。

7.3 删除的代价

list_del_rcu(entry);          /* 只摘链 (改指针), 不释放 */
synchronize_rcu();             /* 等所有读者结束 grace period */
kfree(entry);                  /* 现在才安全释放 */

RCU 删除分两步：先摘链，等所有读者离开（grace period）后才释放。读端零开销（无锁），代价是写端延迟回收。

场景 用 RCU 链表 用 spinlock 链表
读多写少（路由表、inode 缓存） ✅ 读端零开销 ❌ 每次读要加锁
读写都频繁 ❌ 写端 grace period 太长 ✅ 更简单
删除后立即释放 ❌ 要等 grace period ✅ 摘链即释放

八、性能对比（T11）

8.1 遍历 10000 个节点求和

N = 10000, 遍历求和:
  双向链表:   35235 ns  (每节点: 读 next + container_of + 读 id)
  单链表:     29584 ns  (每节点: 读 next + 读 id)

代码自测

题目 1： 为什么 list_head 的头节点用自指（next = prev = &head）而不是 NULL？

答案

自指让空链表的 list_empty() 判 head->next == head——不需要特判 NULL。遍历的终止条件 pos != head 也不需要特判——走到 head 即停。如果用 NULL，空链表的头节点 next = NULL，遍历时要先判 pos != NULL && pos != head，多一次比较。

题目 2： list_del 为什么把 next 设成 LIST_POISON1（0x100）而不是 NULL？

答案

如果设成 NULL，后续遍历到这个节点时 container_of(NULL, ...) = (char *)NULL - offsetof = 负数地址——这不是 NULL，循环条件 pos 非 NULL 为 true，继续执行，读到垃圾内存但不崩溃——bug 静默存在。

设成 0x100 后，任何解引用立刻 page fault——快速暴露 use-after-del，bug 无处藏身。这是"用 crash 换正确性"的设计哲学。

题目 3： hlist 为什么用 pprev（二级指针）而不是 prev（一级指针）？

答案

pprev 指向"前驱的 next 字段的地址"（而不是前驱节点本身）。删除时 *pprev = next 一步修改前驱的 next 指针——无论 n 是头节点还是中间节点都一样，不需要 if (n == head->first) 特判。

如果用 prev（指向 前驱节点），删头节点时要改 head->first，删中间节点要改 prev->next——两种情况，需要特判。

代价：失去 O(1) 访问尾节点（prev 指向前驱，但 head 没有 last 指针）。

题目 4： list_for_each_entry_safe 比 list_for_each_entry 多了什么？什么时候用它？

答案

多了临时变量 n，在循环初始化时预存 pos 的下一个节点。当 pos 被删除后，pos->member.next 可能已被改写（投毒或被其他线程修改），但 n 已经指向了正确的下一个——边遍历边删除不崩溃。

什么时候用：需要在遍历过程中删除当前节点时。只读遍历用普通版即可（safe 版多一个变量，虽然零运行时开销，但语义上不必要）。

题目 5： container_of 在 -O2 下生成几条指令？list_for_each_entry 遍历循环每次迭代几条指令？

答案

container_of 在 -O2 下只生成1 条 lea（lea -0x48(%rdi),%rax），因为 typeof 是编译期行为、offsetof 是编译期常量。

list_for_each_entry 每次迭代5 条指令：mov（读 next）+ add（累加业务字段）+ lea（container_of）+ cmp（判回到头）+ jne（循环）。没有 call——所有宏完全内联展开。

题目 6： RCU 链表的 list_add_rcu 为什么最后才写 prev->next？

答案

读者是顺 next 走的。在 prev->next 被修改之前，读者看到的还是旧链表（不包含 new）；修改之后，读者看到的是新链表（包含 new）。

由于 smp_wmb 保证了 new->next 先于 prev->next 可见，读者永远不会看到"半插入"的节点（new 在链表上但 new->next 还没设好）。如果先写 prev->next 再写 new->next，读者可能在两者之间读到 new，然后顺 new->next 走到未初始化的垃圾值。

题目 7： 侵入式链表比外挂链表好在哪三点？代价是什么？

答案

三点优势： 1. 零分配——节点内嵌在宿主里，插入不 malloc，裸机和中断上下文都能用 2. cache 友好——节点与业务字段同处一个结构体，遍历时一次 cache line 就能拿到判断所需的数据 3. 一个结构体挂多张链表——多放几个 list_head 成员即可，靠 container_of 的 member 参数区分

代价：类型安全弱——container_of 只检查成员类型，不检查宿主类型和成员名。两个 int 成员传错零警告。测试必须开 ASan/UBSan 兜底。

题目 8： 为什么遍历 10000 个节点的链表比遍历同样大小的数组慢 568 倍？

答案

不是算法复杂度的差距（都是 O(n)），而是 cache 局部性的差距。链表节点分散在堆各处，每次 next 都是一次 cache miss（要等 DRAM 返回数据，约 100 周期）。数组连续存放，CPU prefetcher 能预取后面的数据到 cache，每次访问只需几个周期。

HFT 启示：热路径上，如果数据量已知且不大，用数组 + 线性扫描比链表快得多。链表的优势在"频繁插入/删除中间节点"和"大小未知"的场景。

题目 9： hlist_for_each_entry 为什么用 hlist_entry_safe 而不是直接 hlist_entry？

答案

container_of(NULL, ...) = (char *)NULL - offsetof = 负数地址——这不是 NULL。如果直接用 hlist_entry（= container_of），遍历到末尾（next = NULL）时，container_of(NULL) 产生非空地址，循环条件 pos 非 NULL → true → 解引用野指针 → segfault。

hlist_entry_safe 先判 ptr 是否为 NULL，是则返回 NULL，否则才做 container_of——循环条件 pos == NULL → false → 正确终止。

实测：不加 hlist_entry_safe 时 T5 segfault，加上后正常。

题目 10： netdev_priv 用"固定偏移加法"取私有数据，container_of 用"减偏移"取宿主。两者有什么区别？

答案

netdev_priv：私有数据分配在 net_device 结构体之后，取私有数据 = dev + ALIGN(sizeof(net_device))——加偏移，一条 add 指令。代价：私有数据只能在尾部、大小在分配时确定。

container_of：从结构体内部的成员地址反推宿主首地址 = member_addr - offsetof——减偏移，一条 lea 指令。优势：成员可以在任意位置、可以有多个。

两者运行时开销相同（都是一条算术指令），适用场景不同：netdev_priv 适合"一个宿主 + 一个私有数据块"的固定模式；container_of 适合"一个宿主 + 多个链表节点/回调钩子"的灵活模式。

4.4

协议结构体的 packed 实践

← CH4 内核模块 · 4.3 container_of 与侵入式链表 · CH2 2.2 aligned 与 packed · CH3 3.1 寄存器操作

本篇把 CH2 2.2 aligned/packed 的 __attribute__((packed)) 放回它真正被用的地方——内核网络协议头。 你会发现一个反直觉的事实：TCP/IP 头根本不加 packed，真正加 packed 的是 USB 描述符和 Ethernet 头。 全部 v6.6 源码核对，WSL 实测 5 个 demo（gcc 13.3 / clang 18.1.3 双编译）。

本节讲什么

CH2 的 2.2 讲了 packed 的语法（取消 padding、降对齐到 1）。但真正打开 include/uapi/linux/tcp.h 时，你会看到三个互相缠绕的 C 语言话题：

话题 涉及的 GNU C 扩展 这篇的落点
线上格式怎么用 C struct 表达 __attribute__((packed))、位域 TCP/IP/USB/Ethernet 头
字节序怎么标注 __bitwise（sparse 标注）、__be16/__be32 htonl/ntohl → __builtin_bswap32
热路径怎么操作 flag union cast（绕过 strict-aliasing） tcp_flag_word() + TCP_FLAG_* 整字常量

它和 CH2 的分工：CH2 讲 packed 的语法和代价（伪共享、未对齐访问、UBSan 绕过），这篇讲内核为什么这么用它——哪些头该加、哪些不该加、为什么用位域双版本、热路径为什么用 union 整字操作。

一、反直觉的发现：TCP/IP 头不加 packed

很多人第一次看内核协议头代码时的预期是「网络头一定有 __attribute__((packed))，因为它要精确匹配线上格式」。但 v6.6 源码告诉你不是：

/* include/uapi/linux/tcp.h —— 注意：没有 __attribute__((packed)) */
struct tcphdr {
    __be16  source;
    __be16  dest;
    __be32  seq;
    __be32  ack_seq;
    __u16   res1:4, doff:4, fin:1, syn:1, ...;  /* 位域 */
    __be16  window;
    __sum16 check;
    __be16  urg_ptr;
};

/* include/uapi/linux/ip.h —— 同样没有 packed */
struct iphdr {
    __u8    ihl:4, version:4;  /* 位域 */
    __u8    tos;
    __be16  tot_len;
    ...
};

/* include/uapi/linux/udp.h —— 同样没有 packed */
struct udphdr {
    __be16  source;
    __be16  dest;
    __be16  len;
    __sum16 check;
};

T1 demo 实测（WSL gcc 13.3, x86-64 小端）打印了真实布局：

struct tcphdr    sizeof=20  align=4    <- 5 个 32 位字
struct iphdr     sizeof=20  align=4
struct udphdr    sizeof=8   align=2

为什么不加 packed 也不出问题？ 因为这三个头的设计有一个共同特征：

头 成员类型 位域所在单元
tcphdr 全 __be16/__be32（2/4 字节） res1+doff+8 flags = 16 bit = 1 个 __u16
iphdr __u8 + __be16/__be32 ihl+version = 8 bit = 1 个 __u8
udphdr 全 __be16/__sum16 无位域

结构体的对齐 = 所有成员对齐要求的最大值。这些头的成员都是 2/4 字节对齐，结构体对齐就是 4（或 2），而 sizeof 恰好是 4（或 2）的整数倍——没有 padding 需要消除，packed 多余。

CH2 2.2 的结论在这里得到了验证：packed 只在成员排列会产生 padding 时才需要。TCP/IP 头的设计者刻意让所有成员都落在自然对齐的偏移上，就是为了不用 packed。

那谁加了 packed？

/* include/uapi/linux/if_ether.h —— 加了 packed */
struct ethhdr {
    unsigned char h_dest[ETH_ALEN];     /* 6 字节，对齐 1 */
    unsigned char h_source[ETH_ALEN];   /* 6 字节，对齐 1 */
    __be16        h_proto;              /* 2 字节，对齐 2 */
} __attribute__((packed));

/* include/uapi/linux/usb/ch9.h —— USB 描述符全族都加了 packed */
struct usb_device_descriptor {
    __u8  bLength;
    __u8  bDescriptorType;
    __le16 bcdUSB;                      /* offset 2 */
    __u8  bDeviceClass;
    ...
} __attribute__((packed));

struct usb_ctrlrequest {
    __u8 bRequestType;
    __u8 bRequest;
    __le16 wValue;                      /* offset 2 */
    __le16 wIndex;
    __le16 wLength;
} __attribute__((packed));

T1 demo 对比了 packed 和不加 packed 的版本：

struct ethhdr        sizeof=14  align=1   <- packed
struct ethhdr_nopack sizeof=14  align=2   <- 不加 packed 也是 14 字节！
struct usb_device_descriptor      sizeof=18  align=1   <- packed
struct usb_device_descriptor_nopack sizeof=18  align=2 <- 不加也是 18 字节！

反直觉的发现：Ethernet 头和 USB 描述符在 gcc 上不加 packed 也恰好不产生 padding——因为这个排列下 2 字节成员都落在偶数偏移上。packed 唯一的效果是把 align 从 2 降到 1。

但这不代表 packed 多余——T1 加了一个「坏排列」的对比：

/* __u8 紧跟 __le16：不加 packed 就会产生 padding */
struct usb_bad_order_packed {
    __u8  bLength;
    __le16 wValue;   /* offset 1, 不对齐 2 -> packed 必须有 */
    __u8  bType;
} __packed;

struct usb_bad_order_nopack {
    __u8  bLength;
    __le16 wValue;   /* offset 2, 编译器自动 padding */
    __u8  bType;
};

实测：

struct usb_bad_order_packed   sizeof=4  align=1  wValue off=1
struct usb_bad_order_nopack   sizeof=6  align=2  wValue off=2

这才是 packed 不可省的场景：wValue 在 offset 1（不对齐 2），不加 packed 编译器会在 bLength 后插入 1 字节 padding 把 wValue 推到 offset 2。

packed 三档分类

场景 packed 作用 例子
不加也没 padding 防御性（保证所有编译器/排列下不出 padding） tcphdr、iphdr、udphdr
不加也有 padding 必须（否则 sizeof 不等于线上字节数） usb_bad_order、各种 USB 描述符
不加没 padding 但 align 不同 防御性 + 降 align ethhdr、usb_device_descriptor

结论：packed 的真正作用 = 消除 padding + 降 align 到 1。好排列时是防御性的，坏排列时是必须的。TCP/IP 头的设计者刻意排列成员使其不需要 packed，这是设计上的选择而非疏漏。

二、__be16/__be32：字节序的类型标注

你看到的 __be16、__be32、__sum16、__le16、__le32 不是编译器内置类型，而是内核的 typedef：

/* include/uapi/linux/types.h */
typedef __u16 __bitwise __le16;   /* little-endian 16-bit */
typedef __u16 __bitwise __be16;   /* big-endian (network order) 16-bit */
typedef __u32 __bitwise __le32;
typedef __u32 __bitwise __be32;
typedef __u16 __bitwise __sum16;  /* checksum 16-bit */
typedef __u32 __bitwise __wsum;   /* wide checksum */

__bitwise 是什么？看 include/linux/compiler_types.h：

#ifdef __CHECKER__
# define __bitwise     __attribute__((bitwise))
# define __force      __attribute__((force))
#else
# define __bitwise
# define __force
#endif
条件 __bitwise 展开 效果
sparse 运行时（__CHECKER__ 定义） __attribute__((bitwise)) sparse 把 __be16 和 __u16 当不同类型，直接赋值会报 warning
gcc/clang 编译时 空宏 __be16 就是 unsigned short，零运行时开销

所以 __be16 的意义是：给 sparse（内核静态检查工具）看的类型标注，提醒你「这个值是网络字节序，必须用 ntohs() 转成主机序才能用」。在编译器层面，__be16 和 __u16 完全相同。

CH2 2.3 format 讲了 format 属性让编译器在编译期检查 printf 格式串。__bitwise 是类似的设计哲学——用类型系统把容易犯的错变成可检测的。区别是 format 用 gcc/clang 内置支持，__bitwise 用 sparse 外部工具。

__force：允许「明知故犯」的转换

你会在内核代码里看到 (__force __be32) 这样的写法：

/* include/uapi/linux/byteorder/little_endian.h */
#define __constant_htonl(x) ((__force __be32)___constant_swab32((x)))

__force 告诉 sparse「我知道这是不同字节序的类型，但我有意要这么转换，别报警」。在 gcc/clang 层面 __force 也是空宏。

三、位域双版本：编译期解决字节序

TCP 头的 doff（4 bit）+ res1（4 bit）+ 8 个 flag（各 1 bit）合占 16 位。但这 16 位在大端和小端机器上的内存排列不同：

RFC 793 定义的线上格式（网络序 = 大端）：
  byte 12: [doff(4bit)] [reserved(4bit)]
  byte 13: [CWR ECE URG ACK PSH RST SYN FIN]

在大端机器上，位域 doff:4, res1:4 的内存排列自然和线上格式一致（高位在前）。 在小端机器上，同一个 __u16 的位域排列是反过来的（低位在前）。

内核的解法不是运行时判断，而是编译期用 #if 选两套位域定义：

/* include/uapi/linux/tcp.h */
struct tcphdr {
    ...
#if defined(__LITTLE_ENDIAN_BITFIELD)
    __u16   res1:4,          /* 低 4 bit */
            doff:4,          /* 高 4 bit */
            fin:1,           /* byte 13 最低位 */
            syn:1,
            rst:1,
            psh:1,
            ack:1,
            urg:1,
            ece:1,
            cwr:1;           /* byte 13 最高位 */
#elif defined(__BIG_ENDIAN_BITFIELD)
    __u16   doff:4,          /* 高 4 bit */
            res1:4,          /* 低 4 bit */
            cwr:1,           /* byte 13 最高位 */
            ece:1,
            urg:1,
            ack:1,
            psh:1,
            rst:1,
            syn:1,
            fin:1;           /* byte 13 最低位 */
#else
#error  "Adjust your <asm/byteorder.h> defines"
#endif
    ...
};

__LITTLE_ENDIAN_BITFIELD / __BIG_ENDIAN_BITFIELD 在 include/uapi/linux/byteorder/little_endian.h 或 big_endian.h 里定义，由 asm/byteorder.h 根据架构包含其中之一：

/* include/uapi/linux/byteorder/little_endian.h */
#ifndef __LITTLE_ENDIAN_BITFIELD
#define __LITTLE_ENDIAN_BITFIELD
#endif

T2 demo 验证了这一点（x86-64 小端）：

目标: version=4, ihl=5 -> 线上字节 0x45
位域写: ihl=5, version=4 -> 生成的字节: 45   <- LE 版本生成正确的线上字节
手动写: ihl=5, version=4 -> 0x45              <- 手动移位也一致
两者一致: YES

关键洞察：位域双版本保证无论本机什么字节序，用位域生成的线上字节都符合 RFC。这是编译期解决，不是运行时——零开销。

位域跨存储单元边界：C 标准的未定义行为

C 标准（C11 2.2.2.1）不保证位域跨存储单元边界的行为。内核的位域设计刻意让每个位域组不跨边界：

头 位域 总位数 所在单元 跨边界？
tcphdr res1:4 + doff:4 + 8x1bit 16 bit 1 个 __u16 否
iphdr ihl:4 + version:4 8 bit 1 个 __u8 否
tcp_info tcpi_snd_wscale:4, tcpi_rcv_wscale:4 8 bit 1 个 __u8 否

如果有人写 res1:4, doff:4, bigfield:9（共 17 bit 超过 __u16），C 标准未定义，gcc 和 clang 的行为可能不一致——不可移植。内核刻意把每段位域控制在单个存储单元内。

四、热路径的 union cast：一条指令设/清多个 flag

位域版本的可读性好（th->doff = 5; th->syn = 1; th->ack = 1;），但热路径上逐个访问位域效率不高——每个位域是独立的读-改-写。

内核的解法是 union cast：把整个 TCP 头看成一串 32 位字，对 flags 所在的那个字做整字 AND/OR：

/* include/uapi/linux/tcp.h */
union tcp_word_hdr {
    struct tcphdr hdr;
    __be32        words[5];     /* TCP 头 = 5 个 32 位字 */
};

/* 取第 4 个字（含 doff + 8 个 flag） */
#define tcp_flag_word(tp) (((union tcp_word_hdr *)(tp))->words[3])

/* TCP_FLAG_* 是 __constant_cpu_to_be32 常量 */
enum {
    TCP_FLAG_ACK = __constant_cpu_to_be32(0x00100000),
    TCP_FLAG_SYN = __constant_cpu_to_be32(0x00020000),
    TCP_FLAG_FIN = __constant_cpu_to_be32(0x00010000),
    ...
};

热路径用法：

/* 一次性设置 SYN + ACK（一条 OR 指令） */
tcp_flag_word(tp) |= (TCP_FLAG_SYN | TCP_FLAG_ACK);

/* 一次性清除 SYN + ACK + PSH + URG（一条 AND 指令） */
tcp_flag_word(tp) &= ~(TCP_FLAG_SYN | TCP_FLAG_ACK | TCP_FLAG_PSH | TCP_FLAG_URG);

T4 demo 验证了两种写法的结果一致性：

A (位域):   syn=1 ack=1 fin=0 rst=0
B (整字OR): syn=1 ack=1 fin=0 rst=0
一致: YES

清除前: syn=1 ack=1 psh=1 urg=1
清除后: syn=0 ack=0 psh=0 urg=0
-> 一条 AND 指令清除 4 个 flag（位域要 4 次写）

这个设计的精妙之处：TCP_FLAG_* 常量用 __constant_cpu_to_be32() 转换——在小端机器上编译期 bswap 成网络序。所以 tcp_flag_word(tp) |= TCP_FLAG_ACK 编译成一条 or 指令，常量已经在正确的字节序了。

union cast 与 strict-aliasing

tcp_flag_word(tp) 用 union tcp_word_hdr * 类型双关访问 struct tcphdr。在 -fstrict-aliasing 下，编译器可能认为这是 UB。内核的解法是全局 -fno-strict-aliasing：

# Linux 顶层 Makefile
KBUILD_CFLAGS += -fno-strict-aliasing

C 标准允许通过 union 访问任意成员（C11 1.5.2.3），但 gcc 的 strict-aliasing 优化可能不完全遵守这一点。内核选择全局关闭 -fstrict-aliasing 来让 union cast 安全。T4 demo 编译时也加了 -fno-strict-aliasing。

五、htonl/ntohl：__builtin_bswap32 的一条指令

字节序转换的本质是字节交换。内核的 htonl/ntohl 在小端机器上等于 __swab32：

/* include/uapi/linux/byteorder/little_endian.h */
#define __constant_htonl(x) ((__force __be32)___constant_swab32((x)))
#define __be32_to_cpu(x) __swab32((__force __u32)(__be32)(x))
#define ntohl(x) __be32_to_cpu(x)
#define htonl(x) __cpu_to_be32(x)

/* include/uapi/linux/swab.h */
#if defined(__has_builtin) && __has_builtin(__builtin_bswap32)
#define __swab32(x) (__u32)__builtin_bswap32((__u32)(x))
#else
/* 手动移位回退 */
#define ___constant_swab32(x) ((__u32)(        \
    (((__u32)(x) & (__u32)0x000000ffUL) << 24) | \
    (((__u32)(x) & (__u32)0x0000ff00UL) <<  8) | \
    (((__u32)(x) & (__u32)0x00ff0000UL) >>  8) | \
    (((__u32)(x) & (__u32)0xff000000UL) >> 24)))
#endif

三种实现：

实现 代码 编译结果（-O2）
__builtin_bswap32 编译器内置 1 条 bswap 指令（x86）/ rev（ARM）
手动移位 4 次 <</>> + 3 次 \| gcc 识别为 bswap 模式，也编译成 1 条 bswap
union 重解释 字节交换 多条 mov + 字节操作

✓ 编译器生成了 3 条 BSWAP 指令:

关键洞察：__builtin_bswap32 和手动移位在 -O2 下编译成同一条 bswap 指令——gcc 的 pattern recognizer 能识别 (x<<24)|(x<<8&...)|(x>>8&...)|(x>>24) 就是 bswap。所以用哪个都行，但 __builtin_bswap32 更可读。

大端机器上的零开销

在大端机器上（如某些 PowerPC、SPARC），htonl/ntohl 是 no-op：

/* include/uapi/linux/byteorder/big_endian.h */
#define __be32_to_cpu(x) ((__force __u32)(__be32)(x))  /* 直接返回，不转换 */

编译器看到 (__force __u32)(__be32)(x) 就是一个空转换，优化后什么都不生成。

六、__struct_group：iphdr 的地址组

v6.6 的 struct iphdr 用了一个你可能没见过的特性——__struct_group：

struct iphdr {
    __u8    ihl:4, version:4;
    __u8    tos;
    __be16  tot_len;
    __be16  id;
    __be16  frag_off;
    __u8    ttl;
    __u8    protocol;
    __sum16 check;
    __struct_group(/* no tag */, addrs, /* no attrs */,
        __be32  saddr;
        __be32  daddr;
    );
};

__struct_group 是 Linux 5.16 引入的宏，展开为 C11 的匿名结构体成员：

/* 等价于 */
struct iphdr {
    ...
    struct {
        __be32  saddr;
        __be32  daddr;
    } addrs;   /* 有名子结构体 */
};

/* 访问方式 */
iph->saddr;          /* 直接访问（向后兼容） */
iph->addrs.saddr;    /* 通过子结构体访问 */

好处：可以用 memcpy(&iph->addrs, ...) 一次拷贝两个地址，或者用 iph->addrs 取地址做指针运算。__struct_group 让「既能直接访问字段，又能作为子组访问」成为可能。

这是 CH1 1.2 指定初始化 的一个进阶应用——__struct_group 让结构体的组合性更好，同时不破坏向后兼容的字段访问。

设计规律

  1. 网络协议头（TCP/IP/UDP）：成员全 2/4 字节对齐 → 不加 packed；位域在单个存储单元内 → 用双版本
  2. USB/硬件描述符：__u8/__le16 混合 → 加 packed 确保紧凑；不用位域（USB 字段都是整字节）
  3. 热路径 flag 操作：用 union cast + 整字常量，而非逐个位域访问
  4. 字节序标注：用 __be/__le + __bitwise 给 sparse 看，编译器层面零开销
  5. __struct_group：让相邻字段既能直接访问又能作为子组操作

八、packed 的未对齐访问代价

packed 结构体的成员可能不在自然对齐地址上。访问未对齐成员的代价取决于架构：

架构 未对齐访问 后果
x86/x86-64 硬件支持 有性能代价（跨 cache line 可能慢 2x+），但不会异常
ARM (传统) 部分支持 ALIGN 模式下可能触发 SIGBUS；unaligned 模式下软件处理（很慢）
SPARC/Alpha 不支持 直接触发异常，内核需 fixup（极慢）

T3 demo 实测（x86-64，-O2）：

uint32_t 未对齐 (offset=1) vs 对齐 (offset=4):
  unaligned:  26.73 ms
  aligned:    30.48 ms
  ratio: 0.88x  <- x86 硬件支持，差异小（可能被预取抵消）

x86 的未对齐访问代价小是因为硬件有专门的未对齐支持逻辑。但在 ARM/SPARC 上代价可能大 10x 以上——这就是为什么内核在非 x86 架构上对 packed 结构体用 get_unaligned()/put_unaligned() 辅助函数。

内核的应对：get_unaligned / put_unaligned

/* include/asm-generic/unaligned.h */
/* 用 memcpy 辅助，编译器生成最优的未对齐访问指令 */
static inline u32 get_unaligned_le32(const void *p)
{
    return __get_unaligned_le32((const u8 *)p);
}

内核不直接 *(u32 *)p 访问未对齐地址，而是用 get_unaligned() 包装——在 x86 上编译成普通 mov，在 ARM 上编译成多条 ldrb + orr。

九、uapi：内核和用户态共用一份头文件

你注意到所有协议头都在 include/uapi/linux/ 目录下。uapi = User API，这些头文件：

  1. 被内核（C 代码）和用户态程序（如 tcpdump、wireshark）共用
  2. 通过 make headers_install 安装到 /usr/include/linux/
  3. 用户态 #include <linux/tcp.h> 和内核 #include <linux/tcp.h> 包含的是同一份文件

这解释了为什么协议头结构体要用 __be16 而不是 __u16——类型标注对用户态程序也有意义（用 sparse 检查用户态代码时）。而 __bitwise 在用户态的 gcc/clang 编译中是空宏，不影响编译。

这是 GNU C 扩展在系统编程层面的实践：用类型系统（即使是 sparse 这种外部工具的类型系统）来防止字节序错误，比靠注释和人肉审查可靠得多。

Q1：为什么 struct tcphdr 不加 __attribute__((packed)) 也能正确匹配线上格式？

答案

因为 tcphdr 的所有成员都是 2 或 4 字节类型（__be16/__be32），它们的自然对齐就是 2 或 4。结构体布局时所有成员都落在自然对齐的偏移上——没有 padding 需要消除。位域部分（res1:4 + doff:4 + 8 个 flag）正好占满 1 个 __u16（16 bit），也不跨存储单元边界。

packed 的作用是取消 padding，但这里本来就没有 padding。加了反而会降低 align 到 1，可能导致某些场景下不必要的未对齐访问。TCP/IP 头的设计者刻意让成员排列不需要 packed——这是设计上的选择。

Q2：__be16 和 __u16 在编译器层面有什么区别？为什么要用 __be16？

答案

在 gcc/clang 编译器层面完全相同——__be16 就是 typedef __u16 __bitwise __be16，而 __bitwise 在非 sparse 编译时是空宏。

用 __be16 的意义是给 sparse（内核静态检查工具）看的：sparse 把 __be16 和 __u16 当不同类型，如果你直接 __u16 x = some_be16_var;（忘了 ntohs 转换），sparse 会报 warning。这把「忘了转字节序」这种运行时很难发现的 bug 变成了编译期可检测的问题。

Q3：内核为什么用位域双版本（#if __LITTLE_ENDIAN_BITFIELD）而不是运行时判断字节序？

答案

两个原因：

  1. 零开销：#if 是预处理期判断，编译后只有一套代码，没有运行时分支。
  2. 正确性：位域的内存排列依赖编译器实现，#if 保证选中的版本能生成正确的线上字节。运行时判断无法改变已编译的位域排列。

双版本的设计：小端机器选 LE 版（位域从低位排列），大端机器选 BE 版（位域从高位排列），两者生成的线上字节都符合 RFC。

Q4：tcp_flag_word(tp) |= TCP_FLAG_ACK 为什么能一条指令设置一个 flag？

答案

tcp_flag_word(tp) 通过 union tcp_word_hdr cast 取出 TCP 头的第 4 个 32 位字（words[3]），这个字包含 res1(4) + doff(4) + 8 个 flag(8) + window(16) 的原始字节。

TCP_FLAG_ACK = __constant_cpu_to_be32(0x00100000) 是一个编译期常量，已经在本机字节序下正确排列。words[3] |= TCP_FLAG_ACK 编译成一条 or 指令——读 32 位、OR 常量、写回 32 位。

对比位域写法 th->ack = 1：编译器要读整个 __u16（含 doff 和其他 flag）、用位掩码设置 ack 位、写回 __u16。如果只设一个 flag，两者差异不大；但如果要同时设/清多个 flag（如 SYN+ACK），整字 OR/AND 只需一条指令，位域要多次读-改-写。

Q5：usb_device_descriptor 的成员排列已经让 __le16 落在偶数偏移，为什么还要加 packed？

答案

三个理由：

  1. 防御性：不同编译器（非 gcc）可能给 __le16 不同的对齐策略。packed 保证所有编译器下 sizeof 都等于 18（线上字节数）。
  2. 降 align 到 1：USB 描述符可能出现在任意地址（不对齐的 USB 缓冲区），align=1 允许结构体指针指向任意地址。
  3. API 约定：include/uapi/linux/usb/ch9.h 开头明确注释：「Note all descriptors are declared 'attribute((packed))'」——这是 USB 子系统的约定，所有描述符统一加 packed，避免遗漏。

U-Boot 重定位分析

本节讲什么

U-Boot 常先由 ROM 加载到 低地址 SRAM/DRAM 临时区，再 自拷贝 到链接脚本指定的高地址并 修正重定位项——因为初始 PC 与链接 VMA 不一致。这是 6.10.3 重定位 在嵌入式 Bootloader 中的手工版，与内核解压后重定位同类。

要点

为何重定位

  • 链接时假设运行在 TEXT_BASE（如 0x40200000）
  • 上电时可能在 0x00000000 或另一 RAM 区执行
  • 必须拷贝代码/数据并修补 相对/绝对地址引用

典型步骤（概念）

  1. relocate_code：拷贝 .text/.data 到目标区
  2. 遍历 __rel_dyn_start…__rel_dyn_end 修补
  3. 跳转至重定位后地址继续执行

题目 1： U-Boot 为什么要做重定位（relocate）？以下代码完成什么操作？

/* U-Boot relocate */
ulong relocaddr = gd->relocaddr;
memcpy((void *)relocaddr, (void *)CONFIG_SYS_TEXT_BASE, gd->mon_len);
relocate_code(relocaddr, gd->reloc_off, relocaddr);
参考答案

U-Boot 重定位原因： - U-Boot 初始加载到固定地址（CONFIG_SYS_TEXT_BASE，如 0x87800000） - 但该地址可能被 Linux 内核占用，需将自身复制到更高地址运行 - 重定位后修正所有绝对地址引用（通过 reloc_off 偏移量）

流程： 1. memcpy：将整个 U-Boot 代码和数据复制到新地址 relocaddr 2. relocate_code：修正 GOT 表、所有绝对地址符号（加上 reloc_off） 3. 跳转到新地址继续执行

这是嵌入式启动的常见模式：Bootloader 先在低端地址运行，然后搬自己到高端地址，腾出空间给内核。
