与 CH1 的呼应：inline vs weak

这两个是语义对立的一对，务必对照着读：

CH1 6.10 inline CH2 6.9 weak
对「谁能看见这个符号」 尽量摊平到调用点，希望消失 保留符号，允许被别人替换
编译器能不能内联 能 永远不能（实测热路径慢 3.2 倍）
多个定义怎么办 每个 TU 一份（static inline） 决议：强胜 / 两弱取第一个
典型场景 热路径小函数 冷路径可选钩子、测试替身

实测数据：2 亿次调用，weak 0.131 s vs strong(内联) 0.041 s。反汇编里 weak 的循环体是 call <addw>，strong 是 lea 0x1(%rax) 内联展开。 结论：热路径不要用 weak。

Q1：__attribute__((packed)) 之后取成员地址，为什么在某些平台上会崩？

答案

packed 取消了填充字节，成员可能落在未对齐地址。x86 容忍未对齐访问（只是慢），但部分 ARM 配置下会触发对齐异常（Bus Error/alignment fault）。而且一旦对该成员取地址传给 uint32_t*，ARM 编译器会假定指针自然对齐——见 6.7 实测。

Q2：为什么 if (weak_func) 判空有时会被优化掉？

答案

如果本翻译单元里 weak 函数有定义，编译器能证明它的地址必然非 NULL，-O2 下就直接删掉 test/je。只有「本 TU 里仅有 weak 声明」时才保留判空。推论：想做可选钩子，默认实现不能出现在调用点所在 TU——详情见 6.9。

Q3：likely(x) 和手写 if (x) 差别到底多大？

答案

它不改变逻辑，只给编译器一个分支概率提示，用来重排代码布局（把热分支放在 fall-through 路径上）并改善指令 Cache / 预取。收益取决于分支是否真的可预测——放错了会更慢。详见 6.11.6。

3.6

.1 ATPCS规则

本节讲什么

ATPCS（ARM-Thumb Procedure Call Standard），GNU/Linux 上即 AAPCS：规定函数调用时 寄存器分工、栈方向、栈帧布局——混合编程的核心契约。

要点

寄存器约定

寄存器 角色
R0–R3 参数 / 返回值（≤4 字）；多余参数入栈
R4–R11 被调者保存（callee-saved）
R12 (IP) 临时 / 跳板
R13 (SP) 栈指针，满递减（向下生长）
R14 (LR) 返回地址
R15 (PC) 程序计数器

栈帧示例：int add(int a, int b)（C 编译）

add:
    push    {fp, lr}        @ 保存帧指针与返回地址
    add     fp, sp, #4      @ fp 指向旧 sp
    sub     sp, sp, #8      @ 局部空间（若需要）
    str     r0, [fp, #-8]   @ 存参数 a（编译器可选）
    str     r1, [fp, #-12]  @ 存参数 b
    ldr     r2, [fp, #-8]
    ldr     r3, [fp, #-12]
    add     r0, r2, r3        @ 返回值 → r0
    sub     sp, fp, #4
    pop     {fp, pc}        @ 恢复并返回

手写 add_asm 极简版（demo）

add_asm:
    add r0, r0, r1    @ 参数已在 r0,r1；结果 r0
    bx  lr            @ 调用者保存 r0-r3，我们不碰 r4-r11
  • leaf 函数可不建立帧指针，不碰 callee-saved 即可 bx lr
  • 内核 __switch_to 等必须完整保存 callee-saved + SP

题目 1： ATPCS（ARM-Thumb Procedure Call Standard）的寄存器使用约定是什么？以下 C 函数的参数如何传递？

int add(int a, int b, int c, int d, int e) {
    return a + b + c + d + e;
}
参考答案

ATPCS 寄存器约定： - R0-R3：参数寄存器（传前 4 个参数），也是返回值寄存器（R0） - R4-R11：被调用者保存（callee-saved），函数内使用前必须 push - R12 (IP)：临时寄存器（caller-saved） - R13 (SP)：栈指针 - R14 (LR)：返回地址 - R15 (PC)：程序计数器

该函数 5 个参数：a→R0, b→R1, c→R2, d→R3, e→栈。返回值在 R0。超过 4 个参数用栈传递。

3.6

.2 在C程序中内嵌汇编代码

本节讲什么

GCC asm / __asm__ 把 ARM 指令嵌入 C；volatile 禁止优化删除/重排；约束 描述操作数与寄存器对应——内核 read_cpuid、wfe、dmb 的实现方式。

要点

int add_inline(int a, int b)
{
    int sum;
    asm volatile (
        "add %0, %1, %2"
        : "=r" (sum)           /* 输出 */
        : "r" (a), "r" (b)     /* 输入 */
        : "cc"                 /* 破坏标志位 */
    );
    return sum;
}
要素 含义
volatile 有副作用，勿删勿挪
"=r" 写寄存器输出
"r" 读寄存器输入
"cc" / "memory" clobber 标志 / 内存 
/* 内核风格：内存屏障 */
#define barrier() asm volatile("" ::: "memory")
  • 多语句用 \n\t 连接；勿随意写 clobber，否则优化错误
  • DPDK rte_rmb() 等平台屏障在 ARM 上常为 dmb ish 内联汇编

与后续衔接

  • ch06 扩展语法 asm goto、输入输出修饰符

题目 1： 以下内联汇编代码的作用是什么？输出操作数和输入操作数分别是什么？

int result;
__asm__ volatile (
    "MRS %[res], CPSR"  // 指令
    : [res] "=r" (result)  // 输出
    : // 输入
    : // clobber
);
参考答案

该代码读取当前程序状态寄存器（CPSR）到 C 变量 result。

  • MRS %[res], CPSR：将 CPSR 读入指定寄存器
  • [res] "=r" (result)：输出操作数，%[res] 是占位符，"=r" 表示输出到任意寄存器，(result) 绑定到 C 变量
  • volatile：禁止编译器优化掉这条汇编（读 CPSR 有副作用）

内联汇编格式：asm volatile("指令" : 输出 : 输入 : clobber)。内核中用于操作 CP15/系统寄存器。

3.6

.3 在汇编程序中调用C程序

本节讲什么

启动代码、异常向量或裸机 reset 里用 bl main 跳入 C 世界；须先初始化 栈 SP、BSS，并遵守 AAPCS 传参。

要点

    .global _start
    .type _start, %function
_start:
    ldr sp, =stack_top      @ 必须：C 需要有效栈
    bl  main                @ 进入 C
    b   .                   @ main 返回后死循环

    .bss
    .space 4096
stack_top:

    mov r0, #3              @ main(int argc, ...) 可设 r0
    mov r1, #0
    bl  main

  • 裸机链接脚本把 stack_top 放在 RAM 顶端
  • U-Boot 跳内核前设好寄存器（ATAGs/DTB 指针曾用 r0–r2）

代码自测

题目 1： 以下汇编代码如何调用 C 函数？需要遵守什么约定？

// C 函数
int add(int a, int b) { return a + b; }

// 汇编调用
    MOV R0, #10     @ 第一个参数
    MOV R1, #20     @ 第二个参数
    BL add          @ 调用
    // R0 现在是返回值 30
参考答案

汇编调用 C 函数必须遵守 ATPCS/ABI 约定： 1. 参数传递：前 4 个参数放 R0-R3，更多参数压栈 2. 调用：BL 函数名（自动保存返回地址到 LR） 3. 返回值：C 函数返回值在 R0 4. 寄存器保存：C 函数会自动保存 R4-R11，R0-R3 可能被修改

本例：R0=10, R1=20 传参 → BL add 调用 → 返回后 R0=30。

注意：调用前确保栈指针 SP 有效（如果 C 函数用到栈），R0-R3 的值调用后不保证保留。

6.6

.1 GNU C编译器扩展关键字：__attribute__

← 6.6 属性声明 section · ch06 GNU C 扩展

本篇是 __attribute__ 的完整总纲——覆盖全部常用属性（诊断类 / 优化类 / 链接类 / 布局类），每个都有可编译示例与本机实测结论。 单个属性的深度实测与性能数据在 18.10 GCC 属性总览（Pointers on C ch18）；packed/aligned 的对齐计算在 6.7，section 在 6.6.2，weak/alias 在 6.9，noinline 在 6.10.1。

本节讲什么

__attribute__((...)) 是 GCC/Clang 附着于声明的编译指示。它不改变 C 的类型系统，却影响四件事：布局、链接、优化、诊断。

一句话定性：它是给编译器的"元信息通道"——把你在源码里知道、但 C 语法表达不出来的事实（"这个函数不会返回"、"这块内存 32 字节对齐"、"这个指针可以和 float 别名"）告诉编译器，让它敢做原本不敢做的优化、或能报原本报不出的错。

关键事实 说明
不是 C 标准 GNU 扩展。MSVC 不认，必须条件编译（见 可移植写法）
Clang 支持绝大多数 但不是全部——optimize 在 Clang 上被静默忽略（实测见 组 12）
C23 有标准替代 [[deprecated]] / [[nodiscard]] / [[fallthrough]] / [[maybe_unused]] 等，见 对照表
属性写错可能静默失效 位置错、索引越界、被链接器覆盖，三种失效模式见 坑点

一、语法：写在三种对象上

/* 变量：类型之后、变量名之前，或声明末尾 */
int x __attribute__((aligned(64)));
__attribute__((aligned(64))) int y;

/* 函数：声明前（推荐，可读性好）或声明后 */
__attribute__((noreturn)) void panic(void);
void foo(void) __attribute__((section(".text.foo")));

/* 类型：struct/union/enum */
struct __attribute__((packed)) msg { char c; int i; };
typedef int __attribute__((may_alias)) int_alias;

多个属性用逗号分隔：

__attribute__((section(".init"), unused, noinline))
static void early_init(void) { }

⚠️ 位置写错 = 静默失效（实测三种写法）

这条最容易被 Python/Java 的装饰器习惯带偏。以 [[gnu::packed]] 为例（gcc 13.3 实测）：

写法 sizeof 是否生效
struct [[gnu::packed]] S { ... }; 5 ✅ 唯一正确
struct S { ... } [[gnu::packed]]; 8 ❌ warning: attribute ignored
[[gnu::packed]] struct S { ... }; 8 ❌ warning: empty declaration

规则：属性写在 struct 关键字之后、结构体名之前。后两种只是 warning，不会拦住编译——你以为生效了，其实没有。Clang 对后两种直接 error，所以"能过 gcc 不等于对"。

A. 诊断与检查类

这类是最实用的——把"运行期偶发崩溃"变成"编译期必报"。

1. format(archtype, m, n)

/* 单固定参：格式串在第 1 位，变参从第 2 位开始 */
void log_msg(const char *fmt, ...) __attribute__((format(printf, 1, 2)));

/* 两个固定参（你的 Quiz）：格式串在第 2 位，变参从第 3 位开始 */
void my_log(int prio, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));

记忆法：两个数字是从 1 开始的位置编号，不是偏移量。

能拦四类错误（实测）：

log_msg("%d", 3.14);    /* -Wformat: expected 'int' but arg is 'double' */
log_msg("%s", 42);      /* -Wformat: expected 'char *' but arg is 'int' */
log_msg("%d %d", 1);    /* -Wformat: too few arguments */
log_msg("%d", 1, 2);    /* -Wformat: too many arguments */

⚠️ 必须开 -Wformat（-Wall 已含）；-Werror=format 升级为错误。 ⚠️ 索引写错 = 静默失效：test(const char *fmt, ...) 上写 2,3 时报 warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1 [-Wattributes]， 之后所有调用点零报警。排查索引越界的唯一开关是 -Wattributes。 ⚠️ C++ 成员函数 this 隐式占第 1 位，所以要写 2,3（详见 7.6.2 / 18.10）。

实测（gcc / clang 一致）：

deprecated 带消息的版本最有价值——在调用点直接告诉你该换成什么。

5. error / warning（编译期强制）

/* error：调用即编译错误。内核常用它把"配置禁用的路径"钉死 */
extern void forbidden(void) __attribute__((error("forbidden: 此路径被配置禁用")));

/* warning：调用即警告，但仍生成代码 */

实测 gcc：

error: call to 'forbidden' declared with attribute error: forbidden: 此路径被配置禁用
   13 |     forbidden();

Clang 18 同样支持（措辞 'error' attribute）。这是唯一能把"不该调用的函数"在编译期拦住的手段——比注释和 code review 可靠得多。

⚠️ 注意 error/warning 属性只在调用点可达时触发。若函数只有声明（如上面的 extern），且代码路径实际执行到，链接期会因找不到定义而失败——所以这两个属性通常配 #ifdef 或内联定义使用。

6. fallthrough

    r = 10;
    __attribute__((fallthrough));   /* 告诉编译器：我是故意落空的 */
case 2:
    r += 20;
    break;
}

实测 gcc -std=c11 -Wextra：不加属性报 warning: this statement may fall through [-Wimplicit-fallthrough=]，加了就不报。

⚠️ Clang 18 在 -Wextra 下默认不报 implicit fallthrough（实测 0 条警告）——别拿一个编译器的警告数当代码质量的度量。C23 标准写法是 [[fallthrough]];。

B. 优化提示类

1. hot / cold（段布局实测）

__attribute__((hot))  int  hot_path(int n);
__attribute__((cold)) void cold_error(const char *msg);

-O2 实测段分布：

  0 .text           00000045        ← dispatch
  3 .text.hot       00000035        ← hot_path
  5 .text.unlikely  00000049        ← cold_error, cold_calc
  6 .text.startup   0000003f

符号表：
000000000000003c t dispatch.cold    ← gcc 自动把冷分支拆出主函数！

关键证据是 dispatch.cold——gcc 不只是把 cold 函数放进 .text.unlikely，还会把热函数里的冷分支（错误处理）抽出来单独放。收益是热路径的代码全挤在同一个页/cache 行附近，取指更集中。

对 HFT 的意义：cold 让错误处理路径不占热路径的 i-cache，比手写 if (unlikely) 更进一步。实测与 __builtin_expect 的对照见 18.10。

2. flatten

__attribute__((flatten))
int flatten_sum(int n)
{
    int s = 0;
    for (int i = 0; i < n; i++) s += helper_add(i);
    return s;
}

-O2 实测：flatten_sum 内 call 数 = 0（helper_add 被内联进来了），但 helper_add 的独立函数体仍保留（因为它是外部链接，可能被别处调用）。

与 always_inline 的区别：always_inline 是指定某一个函数必须内联；flatten 是指定某个函数内的所有调用都尽量内联——批量操作，适合"这一条路径我要全部展开"。

3. malloc / alloc_size / assume_aligned

__attribute__((malloc))
void *my_alloc(size_t n);

__attribute__((malloc, alloc_size(1)))      /* 第 1 参数是字节数 */
void *my_alloc2(size_t n);

__attribute__((assume_aligned(32)))
void *my_aligned_alloc(size_t n);
  • malloc：告诉编译器"返回的是全新内存，不与任何现存指针别名"——省掉一次可能的重新加载，与 const/pure 同类思路。
  • alloc_size(n)：让 __builtin_object_size 能推断大小，-D_FORTIFY_SOURCE 的边界检查依赖它。
  • assume_aligned(32)：实测返回地址 c % 32 == 0，调用方可以放心用对齐的 SIMD 指令访问。

⚠️ 这组属性是承诺不是检查。你标了 assume_aligned(32) 却返回未对齐地址，编译器不会报错，只会在生成对齐访问指令时让你 SIGBUS。

编译器 结果

visibility：.so 的 ABI 边界

__attribute__((visibility("hidden")))

gcc -shared -fPIC 后实测：

$ nm -D libvis.so | grep add
0000000000001119 T public_add      ← 在动态符号表里
0000000000001149 T prot_add        ← 在
                                   ← hidden_add 不在！

$ readelf -sW libvis.so | grep add
public_add  GLOBAL
hidden_add  LOCAL                  ← 可见性被降级为 LOCAL
prot_add    GLOBAL

$ # 整体隐藏：-fvisibility=hidden
$ nm -D libvis2.so | grep add

工程实践：编译 .so 时用 -fvisibility=hidden 全局隐藏，再对真正的导出 API 显式标 __attribute__((visibility("default")))。收益：

  1. ABI 收窄——内部函数不会意外变成对外承诺
  2. 加载更快——动态符号表小了，符号解析的 hash 查找更少
  3. 调用更快——hidden 调用不经过 PLT，直接 PC 相对跳转（HFT 热路径上这是真实收益）
  4. 防抢占——内部工具函数不会被 LD_PRELOAD 的恶意同名符号截获

这也是为什么你看到的库代码里到处是 __attribute__((visibility("default")))。

D. 内存布局类

cleanup 专题：C 唯一像样的自动释放

cleanup 只修饰局部变量，变量离开作用域时自动调用指定函数，参数是该变量的地址。

static void free_buf(void *p)
{
    void **pp = (void **)p;          /* 注意：收到的是变量地址，不是变量值 */
    if (*pp) { free(*pp); *pp = NULL; }
}

int main(void)
{
    {
        void *b1 __attribute__((cleanup(free_buf))) = malloc(64);
        void *b2 __attribute__((cleanup(free_buf))) = malloc(64);
        /* ... 用 b1 b2 ... */
    }   /* 离开作用域自动 free，不需要写 goto cleanup */
}

实测输出（-O0 与 -O2 完全一致）：

=== 1. 基本 ===
  b1=0x55612a9382b0 b2=0x55612a938300
  [cleanup] free(0x55612a938300)     ← b2 先释放
  [cleanup] free(0x55612a9382b0)     ← b1 后释放
  已离开作用域

=== 2. 多个 cleanup 的顺序 ===
  [cleanup] close tag 3              ← z（最后声明）
  [cleanup] close tag 2              ← y
  [cleanup] close tag 1              ← x（最先声明）

=== 3. 提前 return ===
  early: b=0x55612a938350
  early: return -1 (提前返回)
  [cleanup] free(0x55612a938350)     ← 照样触发

=== 4. 嵌套作用域 ===
  外层 o=0x...380
  内层 i=0x...3a0
  [cleanup] free(0x...3a0)           ← 内层先结束
  内层已结束
  [cleanup] free(0x...380)           ← 外层后结束

三条确定结论：

特性 实测结果
执行顺序 逆序（LIFO）——后声明的先清理，与 C++ 析构顺序一致
提前 return ✅ 照样触发（这正是它优于手写清理的地方）
嵌套作用域 内层先清理，各管各的

这是 C 里最接近 RAII 的东西，而且是唯一一个"提前 return 也不会漏"的清理机制。用它替代 goto cleanup 模式能显著减少资源泄漏。

⚠️ 三个限制： 1. 只能修饰自动变量（局部变量），不能修饰全局/静态 2. longjmp 跳出作用域时不保证触发（GNU 文档明示）——有 setjmp 的代码别依赖它 3. 清理函数的参数是 void* 指向变量，所以释放指针要写成 void **pp 再 *pp

may_alias 专题：严格别名的解药

这条直接回答 6.11 / ch06 指针表达式 里那个经典 UB：*(uint32_t *)&f 为什么是未定义行为，以及怎么合法地做同样的事。

typedef int __attribute__((may_alias)) int_alias;

/* A：普通 int* —— 编译器可假设它与 float* 不别名 */
static int strict(int *ip, float *fp)
{
    *ip = 1;
    *fp = 2.0f;
    return *ip;          /* 编译器认为 fp 不会动 ip，直接返回 1 */
}

/* B：may_alias —— 编译器必须假定可能别名，每次重新加载 */
static int aliased(int_alias *ip, float *fp)
{
    *ip = 1;
    *fp = 2.0f;
    return *ip;
}

/* 调用时两者传同一个地址 */
float storage;
strict ((int *)      &storage, &storage);
aliased((int_alias *)&storage, &storage);

2.0f 的位模式是 0x40000000 = 1073741824。实测：

编译选项 A 普通 int* B may_alias
-O1 1073741824（重新加载） 1073741824
-O2 1（读的是旧值！） 1073741824
-O3 1 1073741824
-O2 -fno-strict-aliasing 1073741824 1073741824
clang -O2 1 1073741824

这就是严格别名 UB 的可观测后果：-O2 下 A 返回 1（编译器省掉了重新加载，因为按 C11 6.5p7 它有权假设 int* 和 float* 不指向同一对象），而实际内存已被 *fp = 2.0f 改成 1073741824。加 -fno-strict-aliasing 就"修好"了——但那是用放弃优化换来的。

may_alias 是精准解药：只在这一个类型上声明"我就要别名"，其余代码照常享受严格别名优化。

⚠️ 适用边界：may_alias 解决的是类型双关（type punning）。日常读写还是应该用 memcpy——现代编译器会把小 memcpy 完全优化成一条 mov，零成本且绝对合法。may_alias 留给"我确实要长期用两个类型视角看同一块内存"的场景（如协议解析、SIMD 寄存器复用）。

transparent_union

typedef union __attribute__((transparent_union)) {
    int    i;
    float  f;
    void  *p;
} any_t;

void take(any_t a);      /* 调用方可以直接传 int / float / void*，无需显式构造 union */
take(42); take(3.14f); take(ptr);

主要用于消除旧 API 的调用噪音，新代码少见。

可移植写法（三种层次）

__attribute__ 是 GNU 扩展，MSVC 完全不认。工程上按三层封装：

层次 1：条件编译宏（最通用）

#else

#    define AUTOFREE(fn) __attribute__((cleanup(fn)))
#  endif
#endif

层次 3：C23 标准属性（最推荐，能用就用）

C23 把最常用的几个属性纳入了标准语法 [[...]]。新项目优先用标准写法——MSVC 也认其中的 [[deprecated]] / [[nodiscard]] / [[maybe_unused]]，跨编译器零成本。

题目 1：下面这份声明有几个问题？逐个指出并给出正确写法 
struct Packet { char type; int len; char payload[8]; } __attribute__((packed));

void handle(const char *fmt, ...) __attribute__((format(printf, 2, 3)));

void must_use(void) __attribute__((warn_unused_result));

__attribute__((noreturn)) int parse(const char *s);

问题 1：packed 位置错。 [[gnu::packed]] / __attribute__((packed)) 对 struct 必须写在 struct 关键字之后、名字之前：

struct __attribute__((packed)) Packet { char type; int len; char payload[8]; };

写在 } 之后 gcc 只给 warning: attribute ignored，不拦编译，sizeof 仍是 16 而不是 13。用 sizeof 验证是唯一可靠手段。

问题 2：format 索引越界。 handle 只有 1 个具名参数，却说格式串在第 2 位：

warning: 'format' attribute argument 2 value '2' exceeds the number of function parameters 1 [-Wattributes]

后果是属性被丢弃、所有调用点不再检查，实测 handle("%d", 3.14) 零报警。正确写法 format(printf, 1, 2)。2,3 只对 C++ 成员函数（this 占第 1 位）或两固定参函数成立。

问题 3：warn_unused_result 用在 void 函数上无意义。 返回值类型是 void，没什么可"忽略"的。该属性只对有返回值的函数生效——想表达"必须调用"应该用别的手段（静态分析或 [[nodiscard]] 同理）。

问题 4：noreturn 撒谎。 声明说永不返回，返回类型却是 int。若 parse 实际会返回，调用方编译器生成的代码会在调用后直接掉进未定义区域——实测谎称 noreturn 是 SIGSEGV、退出码 139。noreturn 函数的返回类型必须是 void。

题目 2：以下函数在 -O2 下输出什么？为什么？如何修？ 
int f(int *ip, float *fp)
{
    *ip = 1;
    *fp = 2.0f;
    return *ip;
}

float storage = 0.0f;
printf("%d\n", f((int *)&storage, &storage));

输出 1（不是 1073741824）。

按 C11 6.5p7（严格别名），int* 与 float* 是不同类型，编译器有权假设它们不指向同一对象。于是它认为 *fp = 2.0f 不可能改动 *ip，优化时省掉了第二次加载，直接返回常量 1。

-O1 下实测返回 1073741824（还没做这个优化），-O2/-O3 返回 1，clang -O2 同样返回 1。加 -fno-strict-aliasing 后返回 1073741824——但那是用放弃一类优化换来的。

三种修法：

修法 写法 评价
may_alias 类型 typedef int __attribute__((may_alias)) int_alias; 参数改 int_alias * 精准，只在这一个类型上放开别名假设，其余代码照常优化
memcpy 写入/读出都走 memcpy 首选。合法且小 memcpy 会被优化成一条 mov，零成本
-fno-strict-aliasing 全局关闭 全局性能倒退，只为局部一处不值

注意：这段代码在 -O1 或 debug 构建下"看起来是对的"——这正是它危险的地方，测试通过不代表没有 UB。

题目 3：设计一个资源获取函数，要求「任何返回路径都不泄漏」，并说明 cleanup 相比 goto 的取舍 
static void freep(void *p) { void **pp = p; if (*pp) { free(*pp); *pp = NULL; } }
static void closep(int *fd) { if (*fd >= 0) { close(*fd); *fd = -1; } }

int process(const char *path)
{
    int   fd  __attribute__((cleanup(closep))) = open(path, O_RDONLY);
    char *buf __attribute__((cleanup(freep)))  = malloc(4096);
    if (fd < 0 || !buf) return -1;          /* 提前 return 也清理 */

    ssize_t n = read(fd, buf, 4096);
    if (n <= 0) return -2;                  /* 第二个提前 return */

    if (buf[0] == '#') return -3;           /* 第三个 */

    process_data(buf, n);
    return 0;                               /* 正常路径也清理 */
}

cleanup 的优势

  • 提前 return 不漏：实测 early(-5) 的 return -1 照样触发清理函数。goto cleanup 模式每加一个 return 就要加一次跳转，最容易漏。
  • 清理逻辑与声明写在一起，读代码时"这个变量怎么释放"就在眼前。
  • 顺序逆序 LIFO（后声明的先清理），与 C++ 析构一致，天然满足"后获取的先释放"。

取舍（什么时候仍该用 goto）

场景 原因
代码里有 setjmp/longjmp GNU 文档明示 cleanup 在 longjmp 跳出作用域时不保证触发
清理顺序需要非 LIFO cleanup 固定逆序，goto 可以任意安排
需要跨函数/跨模块统一的错误处理 cleanup 是编译期绑定，不好做运行时策略
要支持 MSVC cleanup 是 GNU 扩展，MSVC 无对应物，goto 到处都能用

结论：Linux 内核与 GNU 系项目可以放心用 cleanup（它已是 glibc/gcc 生态的事实标准）；需要跨 MSVC 或对 setjmp 有依赖的代码，goto cleanup 仍是更稳的选择。

题目 4：为什么 .so 工程要全局 -fvisibility=hidden？给出四条实测支撑的理由

实测对照（同一个 vis_lib.c）：

默认：            nm -D → public_add, prot_add, entry   （hidden_add 不在）
-fvisibility=hidden: nm -D → 只剩 prot_add

四条理由：

  1. ABI 收窄：默认可见性下，每一个非 static 函数都进入 .dynsym，等于向外界承诺"这些符号永远存在"。实测 hidden_add 标了 hidden 后从 nm -D 里消失（readelf 显示被降级为 LOCAL），不再是对外承诺。想改内部函数时不必担心破坏调用方。

  2. 加载更快：动态符号表小了，符号解析的 hash 查找次数下降。对有大量符号的库（如 DPDK、OpenSSL）这是可测量的启动收益。

  3. 调用更快（HFT 最关心的一条）：hidden 可见性的调用不经过 PLT，编译器直接生成 PC 相对跳转。默认可见性下，为了允许 LD_PRELOAD 抢占，每次跨模块调用都要走 PLT + GOT 间接跳转。热路径上这是实打实的分支与额外访存。

  4. 防抢占：protected 一档更进一步——它在 .dynsym 里（外部可引用），但本模块内的引用绑死到本地定义，不会被 LD_PRELOAD 的同名符号截获。实测 -fvisibility=hidden 后 prot_add 仍在 .dynsym，正是因为它显式声明了 protected。

推荐写法：

gcc -shared -fPIC -fvisibility=hidden -o libfoo.so *.c

#define EXPORT __attribute__((visibility("default")))
EXPORT int  public_api(int);      /* 只有真正要导出的才标 */
int         internal_helper(void); /* 自动 hidden */

常见陷阱

  1. 自定义 section 必须在链接脚本中"接住" → 否则被丢弃 __attribute__((section(".mydata"))) 只把符号放进 .mydata section。如果链接脚本里没有显式 *(.mydata)，链接器可能：丢弃该 section、合并到默认段、或发出 orphan section 警告。自定义 section 不"接住"等于数据丢失，且无编译错误，只在运行时发现读不到数据。

  2. section 名前缀有约定 → 用错前缀会被特殊处理 .text.*、.data.*、.rodata.*、.bss.* 等前缀链接器会按段属性（可执行/可写/只读/零初始化）自动归类。把可写数据放进 .text.mydata（看起来像代码段）会导致段属性错位，触发 segfault 或内存保护异常。自定义段应保持前缀语义一致：.boot.data、.init.text 这种命名是有意为之。

  3. __init 段运行后被释放 → 持有其指针 use-after-free 内核 __init 函数/数据在启动后 free_initmem() 回收。如果某 __init 函数的指针被存到全局变量、之后调用 → use-after-free。内核用 __ref 标注豁免段检查，但用户代码不会自动检查。__exit 段在非模块编译时同样会被丢弃，若静态编译进 vmlinux 又被运行时调用即崩溃。

自测题

1.（选择） 内核 __init 宏最终展开为以下哪个？ - A. __attribute__((section(".init.text"))) - B. __attribute__((aligned(4))) - C. static inline - D. __attribute__((weak))

答案

A。#define __init __section(".init.text") __cold notrace，本质是把函数放到 .init.text 段。启动后 free_initmem() 释放该段所有页。__cold 提示分支预测器此函数"冷"，notrace 关 ftrace。

2.（判断） 自定义段 .mydata 即使链接脚本没显式处理，链接器也会自动保留它。

答案

错。默认链接脚本会处理已知前缀（.text/.data/.rodata/.bss），但任意命名的 .mydata 是"orphan section"。链接器会启发式归类（按属性匹配最接近的段），行为版本相关且不可靠。生产代码必须在链接脚本 SECTIONS 块显式 *(.mydata) 才能保证位置和属性。内核链接脚本 vmlinux.lds 显式处理了几十个自定义段。

3.（踩坑） 驱动里写了 static int cfg __attribute__((section(".init.data"))) = 42;，并在 probe 函数中读取 cfg。模块加载时正常，但模块卸载后再次加载会读到垃圾值。为什么？

答案

模块的 .init.data 在 probe 完成后被 free_module() 释放，模块卸载时该内存已归还。再次加载模块时，.init.data 重新分配、重新填入 42——理论上没问题。但如果驱动把 &cfg 存到了全局指针（如 static int *cfgp = &cfg;），且 cfgp 在 .data 段未被释放，二次加载时旧 cfgp 指向的 .init.data 可能已被其他模块占用——use-after-free。坑在跨段引用：.data 引用 .init.data 的指针，释放后即悬垂。

4.（应用） 设计一个"启动时自动注册驱动"的机制：所有标记 __driver 的结构体在 main 前被自动遍历调用其 init 函数。给出宏定义和链接脚本片段。

答案 
/* driver.h */
struct driver_desc {
    const char *name;
    int (*init)(void);
};
#define __driver __attribute__((used, section(".drivers")))
#define REGISTER_DRIVER(d) \
    static const struct driver_desc d __driver = d

/* main.c */
extern const struct driver_desc __drivers_start[];
extern const struct driver_desc __drivers_stop[];
int main(void) {
    for (const struct driver_desc *p = __drivers_start;
         p < __drivers_stop; ++p)
        p->init();
    /* ... */
}

/* link.ld */
.drivers : {
    __drivers_start = .;
    KEEP(*(.drivers))
    __drivers_stop = .;
} > ROM

题目 1： U-Boot 中 attribute((section)) 如何实现镜像自复制？以下代码的作用是什么？

__attribute__((section(".image_copy"))) 
void image_copy(void) { ... }
参考答案

U-Boot 自复制机制：

  1. 链接脚本将自复制代码放入特殊段 .image_copy
  2. 该段被链接到 Flash 的起始位置
  3. 上电后 CPU 从 Flash 起始地址执行 .image_copy 中的代码
  4. 代码将整个 U-Boot 从 Flash 复制到 RAM
  5. 跳转到 RAM 中继续执行

__attribute__((section(".image_copy"))) 确保该函数被放在正确的段中，不被链接器重排。

为什么需要自复制： - Flash 读取速度慢（Nor Flash 随机读快但写慢，Nand Flash 需要特殊控制器） - RAM 速度快，代码在 RAM 中执行更快 - 某些操作（如初始化 DDR）只能在 RAM 中进行

类似机制：Linux 内核的 .init.text 段（启动后释放）。

属性声明：aligned 与 packed

← ch06 GNU C 扩展 · 6.5 零长度数组与柔性数组 · 6.6.1 __attribute__ 总纲 · 10.8 嵌入式 C 开门

本篇是「对齐控制」的完整总纲：aligned(n) 与 packed 的语义、三种属性位置、六个真实陷阱、伪共享性能实测，全部有本机（WSL gcc 13.3 / clang 18.1.3）实测数据。 逐节细节见 6.7.1 地址对齐 · 6.7.2 结构体的对齐 · 6.7.3 编译器一定按你指定的对齐吗 · 6.7.4 packed · 6.7.5 内核中的 aligned/packed。

本节讲什么

对齐（alignment） 决定一个对象的首地址是不是某个数（2 / 4 / 8 / 16 / 64…）的倍数。GNU C 用两个属性控制它：

属性 作用 典型用途
__attribute__((aligned(n))) 抬高对齐要求到至少 n 字节 cache line 对齐（抗伪共享）、DMA 缓冲、SIMD、页对齐
__attribute__((packed)) 取消成员之间的 padding，把对齐压到 1 on-wire 报文格式、寄存器映射、省内存

它为什么值得单独一篇——因为它同时踩在四条线上：

关心对齐的原因 后果
原子性 跨 cache line 的访问不保证原子（实测见第 9 节）
SIMD movaps 要求 16 字节对齐，不对齐只能走 movups（或 fault）
DMA 多数 DMA 控制器要求缓冲按 cache line / 总线宽度对齐
cache line 伪共享能让多线程代码慢 1.6 倍（实测见第 8 节）

一、对齐的基本事实（先建立坐标）

_Alignof(T)        /* C11 标准运算符，返回 T 的对齐要求 */
__alignof__(T)     /* GNU 写法，功能相同 */
sizeof(T)          /* 一定是 _Alignof(T) 的整数倍 */
类型 x86-64 上 _Alignof
char / uint8_t 1
uint16_t 2
uint32_t / float 4
uint64_t / double / 指针 8
max_align_t 16 ← malloc 保证的下限

实测（gcc 13.3）：

200 次 malloc(1) 中观察到的最小对齐上界 = 16 字节
_Alignof(max_align_t) = 16
struct vec16 { float v[4]; } __attribute__((aligned(16)));  -> align=16

结构体的对齐 = 所有成员对齐要求的最大值（这也是 6.5 FAM 对齐传导 那条结论的来源）。

二、aligned(n)：三种写法，三种作用域

struct S64 { char c; } __attribute__((aligned(64)));        /* ① 类型级：改类型 */
struct Smem { char a; int x __attribute__((aligned(16))); char b; }; /* ② 成员级 */
__attribute__((aligned(64))) char gbuf[10];                 /* ③ 变量级 */

实测：

S0    : sizeof= 1 align= 1                      <- 原始
S64   : sizeof=64 align=64                      <- ① sizeof 被撑到 64
Smem  : sizeof=32 align=16 off(a)=0 off(x)=16 off(b)=20   <- ② 成员 x 被推到 16
Sdown : sizeof= 4 align= 4                      <- 想用 aligned(1) 降到 1：无效

gbuf     addr=0x63c188be5080  (%64 = 0)  已对齐
sbuf     addr=0x63c188be50a0  (%32 = 0)  已对齐
stackbuf addr=0x7fff7b145b80  (%64 = 0)  已对齐   <- 栈变量 gcc 也会调整栈指针

S64 arr[3]: sizeof(arr)=192   arr[0..2] 全部 %64=0

三条规则

  1. 只能增大，不能减小。实测 struct { int x; } 加 aligned(1) / aligned(2) 后 align 仍然是 4——属性被静默忽略（连警告都没有）。
  2. n 必须是 2 的正整数幂。实测 aligned(3) → error: requested alignment '3' is not a positive power of 2。
  3. 抬高了 align 就会抬高 sizeof：sizeof 必须是 align 的整数倍。所以 {char c;} 加 aligned(64) 后 sizeof 从 1 变成 64——这是你为对齐付的内存代价。

类型级 aligned 会改 sizeof，这一点很关键：它是让"数组每个元素都对齐"的唯一机制。 实测 static struct S arr[4]（sizeof(S)=64）→ 四个元素 %64 全为 0。

三、坑 1：aligned 对 malloc 返回的地址完全无效

这是最贵的一个误解。看实测：

struct big { uint64_t v[8]; } __attribute__((aligned(64)));

struct big *p = malloc(sizeof(*p));     /* 你以为它 64 对齐？ */

_Alignof(struct big) = 64
sizeof(struct big)   = 64

  malloc #0 -> 0x55848bfa22b0  %64=48  未对齐
  malloc #1 -> 0x55848bfa22b0  %64=48  未对齐
  ...
  malloc #9 -> 0x55848bfa22b0  %64=48  未对齐
  --> 10 次里对齐了 0 次

== 栈上对象呢 ==
  stack obj addr=0x7ffdd731dc80  %64=0 -> 已对齐
== 全局/静态对象呢 ==
  static obj addr=0x55844da67080  %64=0 -> 已对齐

结论表：

存储类别 aligned(64) 生效吗 原因
全局变量 / static ✅ 生效 链接器/加载器按对齐要求放置
栈上局部变量 ✅ 生效 gcc 会调整栈指针（实测 %64=0）
malloc 返回的堆块 ❌ 无效 malloc 只保证 _Alignof(max_align_t) = 16 字节，它不知道你的类型

正确做法：

/* 1) C11 aligned_alloc —— size 必须是 alignment 的整数倍 */
size_t sz = ((sizeof(struct big) + 63) / 64) * 64;
struct big *p = aligned_alloc(64, sz);

/* 2) POSIX posix_memalign —— 无整数倍限制，但要手动 free */
struct big *q;
if (posix_memalign((void **)&q, 64, sizeof(*q)) != 0) /* 处理失败 */;

/* 3) 内核：kmem_cache_create 时指定 align；或 __get_free_pages（页对齐） */

实测两者都返回 %64=0 的地址。

HFT 场景：订单簿、行情快照这类大数组，如果要用 aligned(64) 抗伪共享，必须从对齐分配器拿内存，别指望 malloc。

四、坑 2：属性放在 typedef 的位置上，两种写法效果不同

typedef struct { char a; int b; } __attribute__((packed))  TA;   /* 写法 A */
typedef struct { char a; int b; } TB __attribute__((packed));    /* 写法 B */

实测（gcc 13.3）：

TA: sizeof=5 off(b)=1     <- packed 生效
TB: sizeof=8 off(b)=4     <- packed 没生效！

warning: 'packed' attribute ignored [-Wattributes]

aligned 更微妙——它不是"被忽略"，而是半生效：

typedef struct { char a; int b; } __attribute__((aligned(64))) TA;
typedef struct { char a; int b; } TB __attribute__((aligned(64)));

TA: sizeof=64 align=64    <- sizeof 和 align 都改了
TB: sizeof= 8 align=64    <- 只改了 align，sizeof 还是 8 ！

TB 这种"align=64 但 sizeof=8"的状态是自相矛盾的——它意味着 TB arr[3] 根本无法构造（第二个元素不可能 64 对齐）。编译器会拦：

gcc:   error: alignment of array elements is greater than element size
clang: error: size of array element of type 'TB' (8 bytes) isn't a multiple of its alignment (64 bytes)

规则：属性一律放在 } 之后、typedef 名之前（写法 A）。写在变量名位置是给"变量"加属性，不是给"类型"加——typedef 里那个位置的含义很容易搞错。

顺带一个相关的：char * __attribute__((aligned(64))) pb[2]; 也会报 error: alignment of array elements is greater than element size（指针只有 8 字节）。

五、坑 3：aligned(1) 不等于 packed

这是面试和实战里最容易混淆的一对。实测：

struct normal  { char a; int b; char c; };                          /* 12 */
struct packed_ { char a; int b; char c; } __attribute__((packed));   /* 6  */
struct a1_     { char a; int b; char c; } __attribute__((aligned(1))); /* 12 ! */
struct a2_     { char a; int b; char c; } __attribute__((aligned(2))); /* 12 ! */
struct both_   { char a; int b; char c; } __attribute__((packed, aligned(8)));

normal   sizeof=12 align= 4  off(a)=0 off(b)=4 off(c)=8
packed_  sizeof= 6 align= 1  off(a)=0 off(b)=1 off(c)=5
a1_      sizeof=12 align= 4  off(a)=0 off(b)=4 off(c)=8   <- 完全没变
a2_      sizeof=12 align= 4  off(a)=0 off(b)=4 off(c)=8   <- 完全没变
both_    sizeof= 8 align= 8  off(a)=0 off(b)=1 off(c)=5   <- 内部紧凑 + 整体 8 对齐

--> aligned(1) 完全没去掉内部 padding
packed aligned(1)
去掉成员间 padding ✅ ❌
改变成员 offset ✅ ❌
把结构体 align 压到 1 ✅ ❌（只能增大，见第二节）

为什么：aligned(n) 只描述"这个整体对象该放在什么地址上"，它不碰内部布局；packed 描述"成员之间不要留空隙"。两件事。

packed + aligned(8) 是个有用的组合：内部紧凑（off(b)=1），但整个对象 8 字节对齐（sizeof=8）。适合"报文格式紧凑，但对象本身要对齐存放"的场景。

六、packed 的真实代价

6.1 成员会落在未对齐地址上

&p=0x7ffc3808b142  &p.b=0x7ffc3808b143  (%4 = 3)
p.b = 0xDEADBEEF  读取（未对齐！x86 能忍）

packed 数组: sizeof(arr)=18  每个元素=6
    arr[0] &arr[0].b %4=1
    arr[1] &arr[1].b %4=3     <- 每个元素的成员对齐都不一样
    arr[2] &arr[2].b %4=1

注意数组那一栏：因为元素大小 6 不是 4 的倍数，每个元素的 b 成员对齐都不一样（1、3、1…）。所以你连"手动加 padding 修正"都做不到。

6.2 x86 上零额外开销，但不代表安全

-O2 下三种读法生成完全一样的指令：

__attribute__((noinline)) uint32_t read_direct(const struct pk *p) { return p->v; }
__attribute__((noinline)) uint32_t read_memcpy(const struct pk *p) { uint32_t r; memcpy(&r,&p->v,4); return r; }
__attribute__((noinline)) uint32_t read_shift (const struct pk *p) { /* 逐字节移位 */ }

read_direct:  movl 1(%rdi), %eax ; ret
read_memcpy:  movl 1(%rdi), %eax ; ret     <- 一模一样
read_shift:   movl 1(%rdi), %eax ; ret     <- 一模一样

在 x86-64 上，手写 memcpy 或逐字节移位是纯粹的自我安慰——编译器和硬件都不需要它。

但架构差异：

架构 未对齐 32 位 load
x86 / x86-64 硬件支持，性能几乎无损
ARMv7 / Cortex-M 直接 UsageFault（除非 UNALIGN_TRP=0）
AArch64 普通 load 可以；原子操作、ldp/stp 仍然 fault

6.3 没有任何 sanitizer 会告诉你

实测把 packed 结构体放到 %4 = 2 的地址上读写：

&p->v %4 = 2
  p->v = 0xDEADBEEF
  • gcc UBSan：零输出
  • clang UBSan：零输出
  • ASan：也不管

原因（与 10.8 嵌入式 C 开门 那次结论一致）：编译器知道 packed 之后该成员对齐就是 1，所以它生成的就是"合法的、对齐要求为 1 的访问"——没有 UB 可报。

对比：如果是你手动强转出来的未对齐指针，UBSan 能抓： runtime error: load of misaligned address 0x7ffe3d45eee1 for type 'const uint64_t', which requires 8 byte alignment 也就是说：packed 让你绕过了 UBSan 的保护。这也是内核禁用 packed 描述硬件寄存器的原因之一。

6.4 唯一会响的警告：-Waddress-of-packed-member

int *pb = &p.b;    /* 取 packed 成员的地址 */

gcc:   warning: taking address of packed member of 'struct packed_' may result
       in an unaligned pointer value [-Waddress-of-packed-member]
clang: warning: taking address of packed member 'b' of class or structure 'packed_'
       may result in an unaligned pointer value [-Waddress-of-packed-member]

这是你唯一的自动防线——一旦把 packed 成员的地址传给外部函数（scanf("%d", &p.b)、pthread_mutex_init(&p.lock)），对齐信息就丢了，而编译器在这里会叫。别忽略它。

packed + 位域：packed 会让整个位域组的对齐变成 1。 实测 {uint32_t a:3; b:5; c:24;}：普通版 sizeof=4 align=4，packed 版 sizeof=4 align=1； 混一个 uint8_t x 在前，packed 版 sizeof=2 align=1（真正紧凑）。 详见 6.7.4。

七、packed 的正确用法：on-wire 格式，只做 memcpy

struct wire { uint8_t type; uint32_t seq; uint16_t len; } __attribute__((packed));

实测：

sizeof(wire)=7  (非 packed 会是 8)

序列化:   07 EF BE AD DE 2A 00
反序列化: type=7 seq=0xDEADBEEF len=42

规则：

操作 允许吗
memcpy(buf, &w, sizeof w) / 反向 ✅ 这才是 packed 的正当用途
w.type / w.seq 直接读写 ⚠️ x86 能跑，ARM 可能 fault；且 -Waddress-of-packed-member 会在取地址时叫
&w.seq 传给别的函数 ❌ 对齐信息丢失
packed 里的成员做原子操作 ❌ 跨 cache line 不保证原子

如果既要紧凑又要按成员访问，正确做法是两个结构体：

struct wire_packed { ... } __attribute__((packed));   /* 只用于 memcpy 收发 */
struct host_normal { ... };                            /* 解包后落到这个，正常访问 */

八、伪共享（false sharing）实测：aligned(64) 值多少

两个线程各自给一个 uint64_t 自增 2000 万次，volatile 防折叠，3 轮取最快：

struct shared_bad   { volatile uint64_t a; volatile uint64_t b; };                  /* 紧挨 */
struct shared_pad   { volatile uint64_t a; char pad[56]; volatile uint64_t b; };     /* 手动填 56 */
struct shared_align { volatile uint64_t a __attribute__((aligned(64)));
                      volatile uint64_t b __attribute__((aligned(64))); };

实测输出：

每线程 20000000 次自增（volatile，防折叠），3 轮取最快

  紧挨(伪共享)   0.0126 s   地址差=8 字节   <- 同一 cache line
  手动 padding   0.0079 s   地址差=64 字节
  aligned(64)    0.0091 s   地址差=64 字节

  sizeof: bad=16 pad=72 aligned=128
  相对紧挨版：padding = 1.60x   aligned(64) = 1.40x

两个计数器相差 8 字节（同一 cache line），就让两个线程互相把对方的 cache line 抢来抢去，慢了 1.6 倍。

写法 耗时 相对 sizeof
紧挨（伪共享） 0.0126 s 1.00× 16
手动 char pad[56] 0.0079 s 1.60× 72
aligned(64) 0.0091 s 1.40× 128

要点：

  • 这不是理论值——两千万次自增，差 4.7 毫秒。HFT 里这种计数器到处都是（消息序号、tick 计数、丢包计数）
  • 手动 padding 比 aligned(64) 略快，但 sizeof 小得多（72 vs 128）。要省内存就手动 padding，要省事就 aligned
  • aligned(64) 版本 sizeof=128 是因为两个成员各占一行（0 和 64）

别硬编码 64

#include <unistd.h>
long line = sysconf(_SC_LEVEL1_DCACHE_LINESIZE);   /* 实测本机 = 64 */

实测本机：L1D / L1I / L2 cache line 都是 64 字节，L1D cache size = 49152 字节。 内核用 SMP_CACHE_BYTES（ARM 上可能是 128，某些平台是 32），DPDK 用 RTE_CACHE_LINE_SIZE。

九、未对齐与原子性

/* 构造一个奇数地址上的 uint64_t */
const uint64_t *p = (const uint64_t *)(buf + 1);
return *p;                                    /* 未对齐 load */

实测：

buf=0x7ffc9dda2480  buf+1=0x7ffc9dda2481  (%8 = 1)
  直接解引用读取 = 0x0807060504030201
  memcpy 读取    = 0x0807060504030201     <- x86 上结果相同

== 未对齐地址上的原子加 ==
  执行前 buf[1..8] = 01 02 03 04 05 06 07 08
  执行后 buf[1..8] = 02 02 03 04 05 06 07 08
场景 x86-64 注意
普通未对齐 load/store ✅ 能跑 ARM 可能 fault；UBSan 能抓到手动强转的情况
未对齐地址上的 __atomic_add_fetch ⚠️ 能跑 一旦跨 cache line，就不保证原子；且 lock 前缀要求对齐才能走快路径
对齐地址上的多线程原子加 ✅ 实测 4 线程 × 20 万次 = 800000，正确

规则：给原子变量用 aligned(8) / aligned(16)（或让它落在自然对齐的位置），并且用 malloc 分的话记得 aligned_alloc。

十、C11 标准写法：_Alignas / _Alignof

aligned 是 GNU 扩展，C11 有标准等价物：

GNU C11 标准 备注
__attribute__((aligned(n))) _Alignas(n) / <stdalign.h> 的 alignas(n) 语法位置不同
__alignof__(T) _Alignof(T) / alignof(T) 完全等价

实测：

_Alignof(struct c11)         = 1
_Alignas(64) 后 sizeof       = 1   <- 结构体类型本身没被改！
_Alignas(64) 变量 addr%64    = 0   <- 只作用于那个变量
_Alignas(64) 成员: sizeof=64 align=64 off(d)=1
alignof(max_align_t)         = 16

关键差异：_Alignas 不能写在结构体定义末尾去改类型（那是 _Alignas 作用在声明的变量上）。要改类型本身，仍然得用 GNU 的 aligned——这也正是内核/DPDK 到处是 __aligned(n) 的原因。

十一、内核 / DPDK 的对齐宏（手写复刻与验证）

/* --- 内核 include/linux/cache.h + kernel.h 的最小复刻 --- */
#define SMP_CACHE_BYTES        64
#define ____cacheline_aligned  __attribute__((aligned(SMP_CACHE_BYTES)))
#define __aligned(n)           __attribute__((aligned(n)))
#define __packed               __attribute__((packed))

#define ALIGN(x, a)            (((x) + (a) - 1) & ~((a) - 1))    /* a 必须是 2 的幂 */

实测：

sizeof(hot_counter)=64 align=64

    ...
    spinlock_t      lock;
    ...

十二、与 6.5 柔性数组的联动

6.5 里说过 FAM 的对齐会传导到整个结构体。这里补两个相关实测：

12.1 想让 payload 对齐，要给 FAM 成员本身 加 aligned

struct fam_plain { uint32_t len; uint8_t data[]; };                        /* off(data)=4  */
struct fam_al64  { uint32_t len; uint8_t data[] __attribute__((aligned(64))); };

fam_plain: sizeof= 4 align= 4 off(data)= 4
fam_al64 : sizeof=64 align=64 off(data)=64   <- aligned 把 payload 起点推到 64
  aligned_alloc 对象 data 地址 %64 = 0

12.2 给结构体加 aligned，不会移动 FAM 起点 ⚠️

struct C { char a; char b; char c[0]; } __attribute__((aligned(8)));

A({char a; char b;})        : sizeof=2
B(同上 + aligned(8))        : sizeof=8  (尾部 padding 6 字节)
C(B + 零长数组 c[0])        : sizeof=8  off(c)=2   <- FAM 起点还在 2！

这正好复现了 6.5 那条"sizeof ≠ offsetof"：aligned 撑大了 sizeof，但 c 的偏移仍然是 2。如果你拿 sizeof（=8）当 payload 起点，就偏了 6 字节。

所以： - 想让 payload 对齐 → 给 FAM 成员 加 aligned(n) - 想让整个对象对齐 → 给 结构体 加 aligned(n)（但这会制造尾部 padding，进而制造 sizeof ≠ offsetof）

十三、检查清单

  1. ✅ 需要 > 16 字节对齐的堆内存，必须用 aligned_alloc / posix_memalign，malloc 只保证 16
  2. ✅ 属性放在 } 之后、typedef 名之前（放变量名位置会被忽略或半生效）
  3. ✅ 记住 aligned 只能增大不能减小，且会被静默忽略
  4. ✅ 要紧凑布局用 packed，不是 aligned(1)
  5. ✅ packed 结构体只做 memcpy，不做成员访问（尤其不要取成员地址外传）
  6. ✅ 别忽略 -Waddress-of-packed-member
  7. ✅ 多线程共享的计数器，间隔开一个 cache line（手动 padding 或 aligned(SMP_CACHE_BYTES)）
  8. ✅ 别硬编码 64：用 sysconf(_SC_LEVEL1_DCACHE_LINESIZE) 或 SMP_CACHE_BYTES
  9. ✅ 原子变量的地址要自然对齐，且不要跨 cache line
  10. ✅ SIMD 类型（float[4]、向量）别加 packed——会把 16 对齐压成 1
  11. ✅ 加了 aligned 就检查 sizeof，确认你付得起这个内存代价
  12. ✅ 给 struct 加 aligned 后如果里面有 FAM，重新核对 offsetof（会与 sizeof 分家）

不是，一次都没有。

全局变量 / static ✅

malloc 返回的堆块 ❌

题目 4：伪共享到底值多少钱？aligned(64) 怎么解决？

实测：两个线程各给一个 uint64_t 自增 2000 万次（volatile 防折叠，3 轮取最快）：

紧挨(伪共享)   0.0126 s   地址差=8 字节   <- 同一 cache line
手动 padding   0.0079 s   地址差=64 字节
aligned(64)    0.0091 s   地址差=64 字节

相对紧挨版：padding = 1.60x   aligned(64) = 1.40x

两个计数器只差 8 字节 → 落在同一 cache line → 两个核互相 invalidate 对方的 line → 慢 1.6 倍。

解法：

/* 手动 padding：省内存（sizeof=72） */
struct shared_pad { volatile uint64_t a; char pad[56]; volatile uint64_t b; };

/* aligned(64)：省事（sizeof=128，两个成员各占一行） */
struct shared_align {
    volatile uint64_t a __attribute__((aligned(64)));
    volatile uint64_t b __attribute__((aligned(64)));
};

别硬编码 64：sysconf(_SC_LEVEL1_DCACHE_LINESIZE)（本机实测 64）；内核用 SMP_CACHE_BYTES，DPDK 用 RTE_CACHE_LINE_SIZE。

题目 5：为什么 packed 结构体的未对齐访问，UBSan 抓不到？

因为编译器知道 packed 之后该成员的对齐就是 1，所以它生成的是"合法的、对齐要求为 1 的访问"——对 UBSan 来说没有 UB 可报。

实测（把 packed 结构体放到 %4 = 2 的地址）：

&p->v %4 = 2
  p->v = 0xDEADBEEF
gcc UBSan：零输出
clang UBSan：零输出

对比：如果是你手动强转出来的未对齐指针，UBSan 能抓：

runtime error: load of misaligned address 0x7ffe3d45eee1 for type 'const uint64_t',
               which requires 8 byte alignment

也就是说 packed 让你绕过了 UBSan 的保护。这在 x86 上无所谓，但 ARMv7 / Cortex-M 上未对齐 32 位 load 直接 UsageFault。

额外一条：在 -O2 下，packed 成员的直接访问、memcpy 读、逐字节移位生成完全相同的指令（都是 movl 1(%rdi), %eax）——x86 上手写 memcpy 是纯粹的自我安慰。

题目 6：给结构体加 aligned 后，如果里面有柔性数组，会发生什么？

struct A { char a; char b; };                                  /* sizeof=2 */

struct C { char a; char b; char c[0]; } __attribute__((aligned(8)));  /* sizeof=8  off(c)=2 */

down2 : sizeof= 4 align= 4   <- aligned(2) 无效

题目 9：SIMD 类型和 packed 有什么冲突？

packed 会把整个结构体的对齐压到 1，包括原本 16 字节对齐的向量类型。

实测：

struct vec16 { float v[4]; } __attribute__((aligned(16)));  /* sizeof=16 align=16 */
struct vec_p { float v[4]; } __attribute__((packed));       /* sizeof=16 align=1  <- 16 对齐没了 */

后果： - _mm_load_ps（对齐加载，要求 16 字节）在 vec_p 上会 fault - 编译器只能退到 _mm_loadu_ps（非对齐加载），或者直接拆成 4 次标量 load - 某些编译器在自动向量化时会因为对齐不确定而放弃向量化

规则：SIMD 类型、向量数组、任何要喂给 movaps 的缓冲区，绝不能加 packed。反过来应该显式加 aligned(16) / aligned(32) / aligned(64)（对应 SSE / AVX / AVX-512）。

6.7

.1 地址对齐：aligned

完整总纲与实测数据见 6.7 属性声明：aligned 与 packed。

本节讲什么

对齐 指对象地址 mod N == 0。硬件要求 4 字节 int、8 字节 double、16 字节 SSE、64 字节 cache line 等于不同 N。编译器默认按 ABI 对齐；aligned 属性 提高 对齐要求。

要点

char c __attribute__((aligned(64)));   /* 64 字节对齐 — cache line */
int  x __attribute__((aligned(8)));

_Static_assert(__alignof__(x) >= 8, "align");

/* 栈/堆数组手动对齐 — C11 */
#include <stdalign.h>
alignas(64) char buf[128];
N 典型用途
4 ARM 32-bit 字
8 double / 指针
16 NEON / SSE
64 防 false sharing（DPDK per-lcore） 
gcc -std=gnu11 -O2 -c align.c
objdump -t align.o | grep -E 'buf|c '
  • __alignof__(type) / _Alignof：查询对齐
  • DMA buffer 常 posix_memalign(..., 4096, size) 或 aligned_alloc
  • 内核 kmalloc 保证 SMP_CACHE_BYTES 对齐变体

常见陷阱

  1. aligned 只能"提高"，不能"降低"对齐 __attribute__((aligned(N))) 中 N 必须 ≥ 类型自然对齐。对 char 用 aligned(1) 是无意义但合法；对 int 用 aligned(2) 会触发警告或忽略——编译器不会主动降低对齐，因为可能违反 ABI。要降低对齐用 packed，但代价是访问性能/原子性。

  2. 栈上变量 aligned 在某些 GCC 版本不可靠 char buf[128] __attribute__((aligned(64))); 在栈上要求 64 字节对齐，老版 GCC（< 4.6）或某些 ABI 下可能只保证到 16 字节。C11 alignas 是标准写法，更可靠。内核用 __aligned(N) 宏统一封装，但在栈上仍依赖编译器版本。

  3. aligned 不能修复已存在的 false sharing 对单个变量 aligned(64) 防止它与其他变量共享 cache line。但若结构体内多个成员被不同 CPU 频繁写，整体对齐结构体没用——成员间仍在同一 cache line。需要把每个 hot 字段拆到独立 aligned(64) 变量，或用 ____cacheline_aligned（内核）/ __rte_cache_aligned（DPDK）放在结构体内字段间。

自测题

1.（选择） 下列哪条对齐声明是合法且有意义的？ - A. char c __attribute__((aligned(1))); - B. int x __attribute__((aligned(2))); - C. char buf[128] __attribute__((aligned(64))); - D. double d __attribute__((aligned(4)));

答案

C。char 自然对齐 1，aligned(1) 无意义；int 自然对齐 4，aligned(2) 会被忽略或警告（不能降低）；double 自然对齐 8，aligned(4) 同理不能降低。只有 C 是"提高对齐"——char[128] 提到 64 字节对齐用于 cache line 对齐，常见且合法。

2.（判断） aligned(N) 保证了对象地址 mod N == 0，无论对象在栈、堆、全局段。

答案

对，但有 caveat。栈/全局段由编译器在编译期布局，保证对齐。堆需 posix_memalign / aligned_alloc / memalign——普通 malloc 不保证大于 alignof(max_align_t)（通常 16）的对齐。DPDK rte_malloc 也提供 rte_malloc_socket + 对齐参数。坑：对全局 aligned(64) 变量取地址可以，但 malloc 后强转 aligned 指针运行时仍是 malloc 的对齐——aligned 属性只对定义生效，不对指针类型生效。

3.（踩坑） 多线程程序中两个 int counter_a, counter_b; 被两个 CPU 频繁自增，性能远低于预期。perf c2c 显示 false sharing 严重。但加上 int counter_a __attribute__((aligned(64))); 后性能几乎没改善。为什么？

答案

坑在只对齐了单个变量：counter_a 在 64 字节边界，但 counter_b 紧跟其后（4 字节偏移），两者仍在同一 cache line。修复方式：

struct counters {
    int a __attribute__((aligned(64)));
    int b __attribute__((aligned(64)));
};

或独立结构体：

static int counter_a __aligned(64);
static int counter_b __aligned(64);

关键：false sharing 是多个变量在同 cache line 问题，必须每个变量独立对齐到 cache line，仅对齐其中一个无济于事。内核 ____cacheline_aligned / ____cacheline_internodealigned_in_smp 专治此症。

4.（应用） 给定 void *p（可能是栈/堆/全局），写一个可移植函数判断其是否 N 字节对齐。

答案 
#include <stdint.h>
#include <stdbool.h>

static inline bool is_aligned(const void *p, size_t n) {
    return ((uintptr_t)p & (n - 1)) == 0;
}

原理：N 是 2 的幂时 n-1 是掩码（低 log2(N) 位全 1），按位与为 0 即对齐。关键点： - 必须 uintptr_t（无符号，足以容纳指针），不能用 int（截断）。 - N 必须是 2 的幂——非 2 幂对齐无意义（硬件也不支持）。 - C11 后更标准：_Alignof(T) 取类型对齐，再 is_aligned(p, _Alignof(T))。

aligned(N) 的限制：

  1. N 必须是 2 的幂：aligned(3) 非法，GCC 报错。合法值：1, 2, 4, 8, 16, 32, 64...

  2. 只能增大不能减小对齐：aligned(1) 对 int 无实际效果（int 天然 4 对齐）。要减小对齐用 packed。

  3. 栈变量对齐：局部变量 aligned 可能不生效——编译器保证栈帧对齐，但无法保证栈内每个变量。

  4. 动态分配：malloc 返回的指针对齐到 max_align_t（通常 16 字节）。要更大对齐用 aligned_alloc/posix_memalign。

  5. 链接器限制：链接器最大对齐通常 4096（页对齐），更大的可能被截断。

验证：_Static_assert((uintptr_t)&c % 8 == 0, "not aligned");（编译时检查全局变量）。

本节讲什么

__attribute__((packed)) 取消结构体成员间 padding，使 sizeof 等于成员紧凑之和（仍可能有位域规则）。用于 网络协议头、Flash 配置块、寄存器映射；代价是 未对齐访问 与 性能。

要点

    uint8_t  dst[6];
    uint8_t  src[6];

常见陷阱

  1. 未对齐访问在 ARMv5 及以下触发 alignment fault packed 结构体去掉 padding，int 字段地址可能不在 4 字节边界。ARMv5 及更早架构硬件不支持未对齐 word 访问，直接 p->ethertype 触发异常（SIGBUS）。ARMv6+ 默认开启 unaligned access 支持，但性能差——硬件拆成两次访问。x86 永远支持但跨 cache line 仍慢。安全做法：用 memcpy 或 get_unaligned_be16()。

  2. packed 结构体不能整体赋值（部分情况） struct eth_hdr_packed a = b; 看起来合法，但若编译器优化下用了 SIMD load 指令（要求对齐）会触发对齐异常。packed 结构体的赋值、传参（按值）在某些 ABI 下行为未定义或低效。惯例：packed 结构体只通过指针操作，永远不按值传递。

  3. 取 packed 成员地址 → 指针类型对齐假设错位 uint16_t *p = &hdr->ethertype; 看似合法，但 p 的类型声明"承诺" 2 字节对齐，实际可能任意地址。指向 packed 成员的指针必须显式标 __packed 或转 void * 后用 memcpy。GCC 的 -Waddress-of-packed-member 警告（默认不开）专门查这个坑。

自测题

1.（选择） 以下哪种情况必须用 packed？ - A. 结构体用于跨平台文件存储 - B. 结构体映射网络协议头/硬件寄存器 - C. 想节省内存 - D. 想提高访问速度

答案

B。网络协议头、硬件寄存器、Flash 配置块的二进制布局是外部约定（由协议/硬件 spec 决定），padding 会破坏 wire format。packed 去掉 padding 强制匹配 spec。A 错——跨平台存储应用文本或显式序列化（protobuf）；C 错——packed 节省几字节但牺牲性能，不值得；D 完全相反，packed 降低速度。

2.（判断） struct s { char c; int i; } __attribute__((packed)); 后，sizeof(struct s) == 5。

答案

对。c 1 字节 + i 4 字节，packed 去掉 3 字节 padding，总和 5。但结构体尾部 padding 是否被去掉取决于编译器——GCC 的 packed 会去掉尾部 padding，所以 sizeof == 5。然而数组中 s[1] 仍要满足"下一元素起始对齐"（无 packed 数组对齐为 1），所以无额外 padding。坑：把这种结构体强转为 int * 取 s[0].i 即未对齐访问。

3.（踩坑） 代码：

struct pkt { uint8_t d[6]; uint16_t len; } __attribute__((packed));
struct pkt *p = (struct pkt *)buf;
uint16_t *lp = &p->len;        /* ① */
uint16_t v = *lp;              /* ② */

在 x86 上正常，移植到 ARMv5 后 ② 偶发 SIGBUS。为什么？如何修？

答案

&p->len 地址未对齐（packed 后 len 在偏移 6，非 2 字节边界）。uint16_t *lp 类型声明对齐 2，编译器在 ARMv5 上可能生成 ldrh（要求对齐）指令，访问未对齐地址触发异常。x86 硬件支持未对齐访问，所以"正常"——这是典型的"在 x86 上能跑，移植就崩"坑。 修复：

uint16_t v;
memcpy(&v, &p->len, sizeof(v));      /* 安全：memcpy 按字节拷贝 */
v = ntohs(v);                         /* 网络字节序转主机 */

或用内核/DPDK 提供的 get_unaligned_be16(&p->len)。原则：packed 结构体成员永远不要取地址给类型化指针，用 memcpy 或 get_unaligned。

4.（应用） 设计一个网络协议头结构体，要求：① 二进制布局严格匹配 spec（14 字节）；② 安全访问 ethertype 字段；③ 不会触发未对齐访问。

答案 
#include <stdint.h>
#include <string.h>

struct eth_hdr {
    uint8_t  dst[6];
    uint8_t  src[6];
    uint16_t ethertype;   /* 偏移 12 */
} __attribute__((packed));
_Static_assert(sizeof(struct eth_hdr) == 14, "eth header size");

/* 安全读 ethertype */
static inline uint16_t eth_type(const struct eth_hdr *h) {
    uint16_t v;
    memcpy(&v, &h->ethertype, sizeof(v));
    return v;     /* 调用方按需 ntohs */
}

/* 安全写 ethertype */
static inline void eth_set_type(struct eth_hdr *h, uint16_t v) {
    memcpy(&h->ethertype, &v, sizeof(v));
}

要点： - packed + _Static_assert 保证 wire format。 - memcpy 是编译器允许内联为单条 load/store 的（如果目标支持未对齐），零开销且可移植。 - 不直接暴露 &h->ethertype 给外部，强制走 helper。 - DPDK rte_ether_hdr 就是类似设计，提供 rte_be_to_cpu_16() 包装。

6.8

属性声明：format

归属：A 档 · CH2 GNU C 高级特性（源码看不见，但真实发生） 实测环境：WSL · gcc 13.3.0（GNU ld 2.42）/ clang 18.1.3 · x86-64 · glibc 2.39 源码核对：Linux v6.6 include/linux/compiler_attributes.h:171、include/linux/printk.h:126/134/149 配套小节：6.8.1 变参函数的格式检查 · 6.8.2 变参函数的设计与实现 · 6.8.3 实现自己的日志打印函数 相关：6.6.1 __attribute__ 总纲 · 6.7 aligned/packed · 6.9 weak/alias · 6.12 变参宏 · 6.1 C 标准与 gnu11

本节讲什么

前面 6.3–6.7 的属性（typeof、语句表达式、柔性数组、aligned/packed）都作用于编译期可见的类型与布局。format 是第一个让编译器去读一个字符串的属性——它把「格式串」从「运行时的黑盒数据」变成「编译器能静态解析的微型程序」。

一句话概括：

format 属性告诉编译器：第 N 个参数是一段按 printf/scanf 规则书写的代码，请照着它检查后面的实参。

它的价值不在"少写几行"，而在把一类必崩的运行期错误搬到编译期：

log_err("order %d rejected: %s\n", reason_str, order_id);
/*              ^^^^                 ^^^^^^^^^^^  char* 喂给 %d */

没有 format 属性，这行代码编译通过、上线崩溃（x86-64 上 %d 读的是 esi，而传进去的是指针低 32 位，打印出一串垃圾；在 varargs 的 ABI 下更糟——va_arg 的取值位置会整体错位，后面的 %s 直接段错误）。

加了属性，它是这样：

warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’

而本节要钉死的，是书里没讲、但工程上天天踩的六件事：

  1. first-to-check = 0 才是 va_list 版本的正确写法，写成 2 在 gcc 下是硬错误；
  2. gcc 和 clang 支持的 archetype 完全不是同一套，内核为此只用 printf 不用 gnu_printf；
  3. -Wformat 家族里有一半是默认不开的；
  4. 属性写错位置，gcc 报 error 而 clang 只报 warning；
  5. 内核的 %pK/%pI4 这类扩展格式符，两个编译器都不检查；
  6. no_printk 那个 if (0) 技巧能同时拿到格式检查和零开销——这是日志系统设计的分水岭。

一、三个参数到底在说什么

__attribute__((format(archetype, string-index, first-to-check)))
参数 含义 常见误解
archetype 按哪套格式规则检查 以为只有 printf；以为 gnu_printf 到处都能用（见第三节）
string-index 格式串是第几个参数（从 1 开始） 按 C 习惯从 0 数
first-to-check 第一个待检查的可变参是第几个；0 = 本函数收的是 va_list 以为 0 表示"不检查"

先跑一遍基本盘（-Wall -Wformat=2）：

/* t1_basic.c */

void log_bad(const char *fmt, ...);                              /* 故意不加 */
void log_lvl(int level, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));                       /* 固定前缀 */

log_ok ("%d %s\n", "hello", 42);   /* A */
log_bad("%d %s\n", "hello", 42);   /* B */
log_ok ("%d\n");                   /* C  缺参 */
log_ok ("%d %d\n", 1);             /* D  缺参 */
log_ok ("%d\n", 1, 2);             /* E  多参 */

二、first-to-check = 0：va_list 版本才是重点

这是本节最容易被忽略、也最容易写错的地方。

任何一个成熟的日志层都有两个函数：

void  logf (const char *fmt, ...);        /* 对外：收 ...      */
void vlogf (const char *fmt, va_list ap); /* 对内：收 va_list  */

vlogf 的属性该怎么写？first-to-check 必须是 0——因为它没有可变参，参数已经打包进 va_list 了。写成 2 会怎样：

void vlog_wrong(const char *fmt, va_list ap) __attribute__((format(printf, 1, 2)));

$ gcc -std=gnu11 -Wall -Wformat=2 -c t2_valist.c
t2_valist.c:10: error: ‘format’ attribute argument 3 value ‘2’ does not refer to a variable argument list

$ clang -std=gnu11 -Wall -Wformat=2 -c t2_valist.c
t2_valist.c:10: warning: GCC requires a function with the 'format' attribute to be variadic [-Wgcc-compat]

gcc 是硬错误，clang 只是 warning。 同一份代码在 gcc 下直接编译失败，在 clang 下带着警告继续过——CI 只跑 clang 就会漏掉这个 bug。

内核 v6.6 就是这么写的（include/linux/printk.h）：

extern asmlinkage __printf(1, 2)
int vprintk_emit(int facility, int level, const char *dict, const char *fmt, va_list args);  /* 实际是 __printf(4, 0) */
asmlinkage __printf(1, 2) __cold
int printk(const char *fmt, ...);

asmlinkage __printf(1, 0)
int vprintk(const char *fmt, va_list args);      /* <- 0：收 va_list */

注意 vprintk_emit 是 __printf(4, 0)（第 144–145 行）：格式串排第 4（facility/level/dict 在前），0 表示后面跟的是 va_list。

-Wformat-y2k %y 两位数年份 ❌（-Wformat=2 才开）

两个要点：

  1. -Wformat-truncation / -Wformat-overflow 依赖优化：-O0 下 gcc 看不到目标缓冲区长度，不会报。CI 里用 -O0 跑 warning 检查等于没做。
  2. clang 不认 -Wformat-signedness：warning: unknown warning option '-Wformat-signedness'。跨平台构建脚本里要按编译器分流（-Wno-unknown-warning-option 也压不住这条诊断本身的刷屏）。

五、属性写在哪儿才生效（六个场景实测）

/* A */ void a_decl(...) __attribute__((format(printf,1,2)));  void a_decl(...) {}       /* 声明上 */
/* B */ void b_def (...) __attribute__((format(printf,1,2)));  void b_def (...) {}       /* 定义前（同上，实为声明） */
/* C */ void c_two (...) __attribute__((format(printf,1,2)));  void c_two (...);         /* 二次声明不带属性 */
        void c_two (...) {}
/* D */ void d_defonly(...) __attribute__((format(printf,1,2))) { }                      /* 写在定义体前 */
/* E */ #define LOG(fmt,...) a_decl(fmt, ##__VA_ARGS__)                                  /* 宏包装 */
/* F */ void (*fp)(const char*, ...) __attribute__((format(printf,1,2))); fp("%d\n","z");/* 函数指针 */
场景 gcc clang 结论
A 前置声明带属性 ✅ 检查 ✅ 推荐写法
B 定义（带独立声明） ✅ ✅ 同 A
C 二次声明丢掉属性 ✅ 仍检查 ✅ 属性在多次声明间累积保留
D 属性写在定义体前 ❌ error：attributes should be specified before the declarator in a function definition ⚠️ warning -Wgcc-compat 后接受 gcc 硬失败、clang 放行
E 宏包装 ✅ ✅ 宏展开后就是普通调用
F 函数指针带属性 ✅ ✅ 多数人不知道这个能用

D 是实战中最常踩的：图省事把属性跟着函数体一起写，gcc 直接编译失败而 clang 过，于是"本地能编、CI 挂了"。

F 很有用——回调表里的日志钩子也能检查：

struct log_ops {
    void (*info)(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
    void (*err )(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
};

以及一条反面实测：属性不能写进宏。

#define attr_log(fmt, ...) __attribute__((format(printf,1,2))) real_log(fmt, ##__VA_ARGS__)
attr_log("%d\n", "z");

gcc:  error: expected declaration specifiers or ‘...’ before string constant
clang: error: expected identifier or '('

属性是声明说明符的一部分，必须附着在声明上；宏展开到语句位置就成了语法错误。

六、内核扩展格式符 %pK / %pI4 / %pS 的真相

内核 printk 支持一大票标准 printf 没有的转换：%pK（哈希指针）、%pI4（IPv4）、%pS（符号名）、%ptT（时间戳）……它们由 lib/vsprintf.c 自己解析。那 -Wformat 会不会因它们误报？

void kprintf    (const char *fmt, ...) __attribute__((format(printf, 1, 2)));
void kprintf_gnu(const char *fmt, ...) __attribute__((format(gnu_printf, 1, 2)));

kprintf    ("%pK\n", p);   /* A */
kprintf_gnu("%pK\n", p);   /* B */
kprintf    ("%pI4\n", p);  /* C */
kprintf    ("%pS\n", p);   /* D */

$ gcc -std=gnu11 -Wall -Wformat=2 -c t7_kernel.c
（0 warning —— 完全静默）
$ clang ...
（只有一条 gnu_printf not supported，格式串本身无诊断）

两个编译器都不报。 原因是 %p 本身就是一个完整的转换说明符，编译器解析完 p 就结束了，后面的 K/I/S 被当成普通字符。

这是把双刃剑：

  • ✅ 好处：内核代码不会因为扩展格式符被 -Wformat 刷屏，所以内核才敢用 printf 而不是自己造 archetype；
  • ❌ 坏处：%pZ 这种拼错的扩展符也一样静默通过——编译器不会帮你抓。

内核对此的补偿是构建期的 scripts/checkpatch.pl 与运行时的 vsprintf 探测，不在编译器这边。

七、no_printk：把「检查」和「零开销」同时拿下

关掉调试日志时，有人这么写：

#define pr_debug(fmt, ...) do { } while (0)     /* 干净，但格式串错误从此没人管 */

代码是没了，格式检查也没了。内核 v6.6 printk.h:126 的写法是：

#define no_printk(fmt, ...)             \
({                                      \
        if (0)                          \
                printk(fmt, ##__VA_ARGS__); \
        0;                              \
})

if (0) 里的代码永远不执行、不生成指令，但编译器仍然会做语义分析和格式检查。实测（-O2）：

int  real_log(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
#define no_log(fmt, ...) ({ if (0) real_log(fmt, ##__VA_ARGS__); 0; })

int main(void) { no_log("%d\n", "x"); return 0; }

$ gcc -std=gnu11 -Wall -Wformat=2 -O2 -c t8_noprintk.c
warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’   <- 检查还在

$ objdump -d t8.o
0000000000000000 <main>:
   0:   f3 0f 1e fa     endbr64
   4:   31 c0           xor    %eax,%eax        <- 直接 return 0
   6:   c3              ret

$ objdump -s -j .rodata t8.o     -> （空：字符串 "%d\n" 与 "x" 都没进二进制）
$ nm -u t8.o                     -> （空：没有引用任何外部符号）

三条证据：

  1. 警告还在 —— 检查发生在语义分析阶段，早于优化；
  2. main 只剩 3 条指令 —— 调用被完全消除；
  3. .rodata 为空、无未定义符号 —— 连格式字符串都没留下。

再看一个更狠的：参数里的副作用还执行吗？

int side(void) { return ++counter; }
no_log("%d\n", side());                       /* 编译期死 */
if (g_level) real_log("%d\n", side());        /* 运行时门 */

$ gcc -std=gnu11 -O2 -c t9_sideeffect.c && objdump -d t9.o
   0:   mov  0x0(%rip),%eax        # 读 g_level
   a:   test %eax,%eax
   c:   je   15 <main+0x15>
   e:   addl $0x1,0x0(%rip)        # side() 被内联：counter++
  15:   xor  %eax,%eax
  17:   ret

no_log 那一行连 side() 的调用都不存在；运行时门那行则保留了 counter++（此处 gcc 把 side() 内联了）。

结论：编译期关闭的日志，参数不求值；运行时判断的日志，参数一定求值。 所以 LOG_DEBUG("price=%f", compute_expensive_thing()) 这种写法——只有编译期门才是真免费；运行时门照样把 compute_expensive_thing() 算完，只是不打印。这是 HFT 里最常见的"关了日志还是慢"的根因。

八、%n 与 -Wformat-security：编译器其实不管

%n 会把已输出字节数写进指针参数，是典型的格式化串攻击跳板。但实测：

printf(argv[0]);        /* A: 非常量格式串、无参数  */
printf(argv[0], 1);     /* B: 非常量格式串、有参数  */
printf("%n\n", &n);     /* C: 常量格式串里的 %n     */

$ gcc -std=gnu11 -Wall -Wformat=2 [-D_FORTIFY_SOURCE=2 -O2] -c t7_security.c
A: warning: format not a string literal and no format arguments   [-Wformat-security]
B: warning: format not a string literal, argument types not checked [-Wformat-nonliteral]
C: （无警告 —— 两个编译器、加不加 _FORTIFY_SOURCE 都没有）
  • -Wformat-security 只在"格式串非常量 且 没有参数"时触发；一旦带了参数，它降级成普通的 -Wformat-nonliteral。
  • 字面量里的 %n，gcc 和 clang 都不报警，_FORTIFY_SOURCE=2 也不管（glibc 的 fortify 检查的是缓冲区长度，不是 %n）。

所以 %n 只能靠代码审计 / 禁用策略挡住（内核的 checkpatch.pl 会提示；很多项目直接 -Werror=format-security + 禁止 %n）。

九、HFT 视角：日志的四级成本

把上面的实测叠起来，一条日志的成本可以分成四级，每一级都需要不同的手段才能消掉：

级别 成本 消除手段 实测证据
L1 调用点 一次 call + 参数装寄存器 编译期常量门 if (LEVEL <= MAX) T6：main 里只剩运行时门的那一个 call
L2 参数求值 side() / compute_x() 只有编译期门（或把昂贵表达式移出参数） T9：no_log 的 side() 消失，运行时门保留
L3 字符串与格式化 vsnprintf 遍历格式串 编译期门（字符串进不了 .rodata） T8：.rodata 为空
L4 函数体 日志函数自身的 .text static + 无引用（让链接器丢弃） T6：log_at 是外部链接，函数体仍在

要点：L1–L3 靠编译期门一次全消，L4 需要 static 或链接期 GC。

一个可直接用的模板（综合本节所有结论）：

/* log.h —— 纯 ASCII，跨 gcc/clang */
#ifndef MAX_LOG_LEVEL
#define MAX_LOG_LEVEL 2          /* 0:ERR 1:WARN 2:INFO 3:DEBUG */
#endif

enum { L_ERR = 0, L_WARN, L_INFO, L_DEBUG };

void log_emit(int level, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));        /* 对外：... 版本 */
void log_vemit(int level, const char *fmt, va_list ap)
    __attribute__((format(printf, 2, 0)));        /* 对内：va_list，0! */

/* 编译期门：LEVEL 是常量，整段（含参数求值）消失 */
#define LOG_AT(level, fmt, ...)                                  \
    do {                                                         \
        if ((level) <= MAX_LOG_LEVEL)                            \
            log_emit(level, fmt, ##__VA_ARGS__);                 \
    } while (0)

/* 关掉时仍保留格式检查：no_printk 同款 */
#define LOG_OFF(level, fmt, ...)                                 \
    ({                                                           \
        if (0)                                                   \
            log_emit(level, fmt, ##__VA_ARGS__);                 \
        0;                                                       \
    })

##__VA_ARGS__ 是 GNU 扩展，零参时吃掉前导逗号（详见 6.12）；C++20/C23 可用标准的 __VA_OPT__。

题目 1： 下面两个声明，哪个在 gcc 下会编译失败？为什么？

void va1(const char *fmt, va_list ap) __attribute__((format(printf, 1, 0)));
void va2(const char *fmt, va_list ap) __attribute__((format(printf, 1, 2)));
参考答案

va2 在 gcc 下硬失败：

error: ‘format’ attribute argument 3 value ‘2’ does not refer to a variable argument list

first-to-check 为 0 表示"本函数接收的是 va_list，没有可变参需要检查"。va2 明明收 va_list，却声明第 2 个参数起是可变参 → gcc 直接报错。

clang 只给 -Wgcc-compat 警告并继续编译 —— 这正是"本地 clang 通过、CI gcc 挂掉"的典型来源。

内核 v6.6 的正确写法：asmlinkage __printf(1, 0) int vprintk(const char *fmt, va_list args);

题目 2： 团队要求"debug 日志在 release 构建里零开销，但格式串写错仍要在编译期发现"。下面两种写法哪种满足？

/* 方案 A */
#if DEBUG
#define DBG(fmt, ...) real_log(fmt, ##__VA_ARGS__)
#else
#define DBG(fmt, ...) do { } while (0)
#endif

/* 方案 B */
#if DEBUG
#define DBG(fmt, ...) real_log(fmt, ##__VA_ARGS__)
#else
#define DBG(fmt, ...) ({ if (0) real_log(fmt, ##__VA_ARGS__); 0; })
#endif
参考答案

只有 B 满足，A 不满足。

  • A：release 下 DBG("%d\n", "str") 完全不展开成任何调用，格式检查也一起没了。开发期在 #if DEBUG 下没暴露的错误，release 构建里悄悄潜伏。
  • B：if (0) 分支在语义分析阶段就要做类型与格式检查（会报 -Wformat），但优化阶段整段被消除。

实测证据（gcc 13.3 -O2）：

warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’   <- 检查在

objdump -d:  main 只剩 endbr64 / xor eax,eax / ret                                      <- 代码没了
objdump -s -j .rodata:  (空)                                                            <- 字符串也没了
nm -u:       (空)                                                                       <- 无外部引用

这就是内核 v6.6 no_printk 的做法（printk.h:126）。

额外提醒：B 还有一个 A 没有的好处——参数不求值。DBG("x=%d", expensive()) 在 B 里 expensive() 不会被调用，在"运行时 if 判断"的写法里则一定会调用。

__attribute__((format(ms_printf, 1, 2)))

题目 4： 为什么这段内核代码在 gcc 下没有任何 -Wformat 警告？

printk("%pK %pI4 %pZ\n", ptr, addr, sym);   /* %pZ 是拼错的（内核没有这个） */

  • 坏处：拼错的 %pZ 也一样静默通过。编译器在这里帮不上忙，只能靠 code review 或 checkpatch.pl。

.1 变参函数的格式检查

本节讲什么

标准 printf 家族在 <stdio.h> 已带 format 属性；自定义 log_error(fmt, ...) 需显式声明，编译器才能比对 格式说明符 与 实参类型，在编译期发现 %d 与指针不匹配等问题。

要点

#include <stdio.h>
#include <stdarg.h>

void warn_user(const char *fmt, ...)
    __attribute__((format(printf, 1, 2)));

void warn_user(const char *fmt, ...)
{
    va_list ap;
    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
}

/* 固定前缀 + 可变 fmt 时，format 索引要跳过前缀 */
void log_err(const char *tag, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));
format 种类 用途
printf printf 规则
scanf scanf 规则
strftime 时间格式 
gcc -Wall -Wformat=2 -Werror=format -c log.c
# 故意写错实参类型，观察 -Wformat 诊断
  • -Wformat-nonliteral：format 非字符串常量时警告（函数指针表驱动 format 串）
  • 内核 __printf(a,b)、__scanf(a,b) 宏封装 attribute
  • __attribute__((format(gnu_printf, ...)))：GCC 扩展 printf 语义

题目 1： 以下代码有什么问题？attribute((format)) 如何帮助发现？

void log_msg(const char *fmt, ...) {
    va_list ap;
    va_start(ap, fmt);
    vprintf(fmt, ap);
    va_end(ap);
}
// 调用
log_msg("%d %s\n", "hello", 42);  // 类型不匹配
参考答案

问题：%d 期望 int 但传入 "hello"（char），%s 期望 char 但传入 42（int）。运行时行为未定义（可能崩溃或输出乱码）。

__attribute__((format(printf, 1, 2))) 让编译器检查格式字符串与参数类型：

void log_msg(const char *fmt, ...)
    __attribute__((format(printf, 1, 2)));
  • printf：按 printf 格式检查
  • 1：格式字符串是第 1 个参数
  • 2：可变参数从第 2 个参数开始

加此属性后，编译器会对 log_msg("%d %s\n", "hello", 42) 发出警告：format %d expects int but argument has char*。

内核中 printk/pr_debug 等都有此属性。

6.8

.2 变参函数的设计与实现

本节讲什么

C 变参函数 用 ... 与 stdarg.h（va_list / va_start / va_arg / va_end）实现。设计日志 API 时：固定前缀参数（level、tag）+ 可变 fmt/args；format 属性索引要 跳过固定参。

要点

#include <stdarg.h>
#include <stdio.h>

void vlog(int level, const char *tag,
          const char *fmt, ...)
    __attribute__((format(printf, 3, 4)));

void vlog(int level, const char *tag,
          const char *fmt, ...)
{
    va_list ap;
    va_start(ap, fmt);
    fprintf(stderr, "[%d][%s] ", level, tag);
    vfprintf(stderr, fmt, ap);
    fputc('\n', stderr);
    va_end(ap);
}
规则 说明
至少一个 named 参数在 ... 前 C 要求
default promotion char→int，float→double
va_end 必须调用 栈清理
  • 内核 printk 支持 %pV 等扩展格式

题目 1： 以下自定义 printf 实现，va_list 的使用流程是什么？

void my_printf(const char *fmt, ...) {
    va_list args;
    va_start(args, fmt);
    while (*fmt) {
        if (*fmt == '%') {
            fmt++;
            switch (*fmt) {
                case 'd': printf("%d", va_arg(args, int)); break;
                case 's': printf("%s", va_arg(args, char*)); break;
            }
        } else { putchar(*fmt); }
        fmt++;
    }
    va_end(args);
}
参考答案

va_list 使用流程： 1. va_list args;：声明参数列表变量 2. va_start(args, fmt);：初始化，从最后一个固定参数 fmt 之后开始读可变参数 3. va_arg(args, int)：取出下一个参数，指定类型为 int。每次调用后指针前移 4. va_end(args);：清理

关键点： - va_arg 必须知道参数类型（通过格式字符串推断） - 类型提升：char/short 自动提升为 int，float 提升为 double - 无法反向遍历或随机访问（只能顺序取） - 不同架构 va_list 实现不同（x86 栈上，ARM 寄存器+栈混合）

这就是为什么 printf 必须有格式字符串——编译器和运行时都依赖它来推断参数类型和数量。

6.9

属性声明：weak 与 alias

归属：A 档 · ch06 GNU C 扩展主线 实测环境：WSL · gcc 13.3.0（GNU ld 2.42）/ clang 18.1.3 · x86-64 配套小节：6.9.1 强符号与弱符号 · 6.9.2 函数的强弱符号 · 6.9.3 弱符号的用途 · 6.9.4 alias 相关：6.6.1 __attribute__ 总纲 · 6.7 aligned/packed · 10.8 嵌入式 C 开门

本节讲什么

weak 是唯一一个语义完全发生在链接期的 GNU C 属性。前面 6.3–6.7 的属性（typeof、语句表达式、柔性数组、aligned/packed）都作用于编译期——影响类型、代码生成或布局；weak 编译期什么都不做，它只往目标文件的符号表里写一个标记，剩下的交给链接器。

一句话概括：

同名符号有多个定义时，强的吃掉弱的；全是弱的，先到先得；只有弱声明没有定义，符号等于 NULL。

它的价值在嵌入式和内核里无可替代——一份内核镜像适配多块板子，靠的就是 weak：

/* core.c —— 框架代码，不认识任何具体板子 */
void __weak board_early_init(void) { }
int  __weak board_id(void)         { return -1; }

/* board_a.c —— 换块板子只需换一个 .o */
void board_early_init(void) { /* A 板专属时序 */ }
int  board_id(void)         { return 0xA1; }

框架代码里没有一行 #ifdef，调用点干干净净，换板子不重新编译主体。

本节把 weak 的规则、代价、以及五个会静默出错的坑全部用实测钉死。

一、先认清符号的"强弱"：nm 怎么读

所有 weak 问题最终都要回到符号表。先建立读 nm 的能力：

int  strong_data = 1;                       /* 已初始化强数据 */
int  strong_bss;                            /* 未初始化强数据 */
int  __attribute__((weak)) weak_data = 2;
int  __attribute__((weak)) weak_bss;

0000000000000004 V weak_bss        <- V: 弱 · 对象（变量）
0000000000000004 V weak_data       <- V: 弱 · 对象（变量）

三、weak 声明但不定义：可选 hook

3.1 基本用法

/* 只有声明，没有定义。没有 weak 会 undefined reference */
void __attribute__((weak)) optional_hook(void);

int main(void)
{
    if (optional_hook)          /* 必须判空！ */
        optional_hook();
    return 0;
}

--- 带 weak ---
link exit=0
optional_hook addr = (nil)
hook absent -> skipped safely

--- 去掉 weak（对照）---
link exit=1
undefined reference to `optional_hook'

--- 不判空直接调用 ---
Segmentation fault (core dumped)      run exit=139

这是 SDK 的"可选功能"标准写法：厂商库里声明一堆 hook，集成方按需实现，没实现的自动跳过。不判空 = 空指针跳飞。

3.2 但是：if (hook) 可能被优化掉

这是本节最反直觉的一条。看这两份代码在 -O2 下的差别：

/* same.c —— weak 定义就在本 TU */        /* decl.c —— 本 TU 只有声明 */
int __weak hook(void) { return 1; }       int __weak hook(void);
int main(void){                           int main(void){
    if (hook) hook();                         if (hook) hook();
}                                         }

--- same.c -O2 的 main ---
   ...  call  ...     <- 没有 test / je！判空被删掉了

--- decl.c -O2 的 main ---
   10:  74 21   je     33 <main+0x33>     <- test + je 保留

原因：same.c 里 hook 有定义，编译器能证明它的地址非 NULL，于是 if (hook) 恒真，判定被删。decl.c 里编译器看不到定义，不敢删。

这不影响正确性（不是 NULL 就调用默认实现），但它说明一件事：

"用判空支持可选 hook"这个模式，前提是默认实现不能出现在调用点所在的 TU。 一旦你把默认实现和 if (hook) 写进同一个 .c，语义就悄悄从"可选"退化成"总是存在"——而 strong 覆盖仍然生效，所以你不会发现。

推荐写法：默认实现放库里，调用点在业务代码里（天然不同 TU）。或者干脆不提供定义、只声明，让"未实现"真正可观测。

四、头号坑：weak 不会触发静态库成员提取

这条坑死过无数人，也是最值得记住的一条。

链接方式 库里的 strong 生效吗 实测 hook()
A. main 有 weak 定义 + libonly.a（成员只含 hook） ❌ 0（weak 胜）
B. main 有 weak 定义 + libboth.a（成员含 hook + other，other 未引用） ❌ 0
C. 同 B，但业务代码引用了 other（成员被拉入） ✅ 42（strong 胜）
D. main 只有 weak 声明 + libonly.a ❌ hook addr=(nil)
E. 同 D，加 -Wl,--whole-archive ✅ 42
F. main 有 weak 定义 + 直接给 hook.o（不是 .a） ✅ 42

机制：链接器处理静态库时，只有当某个未定义符号需要被解析时，才把定义它的成员拉进来。而 weak 符号——

  • 如果它有定义（A/B）：符号已解析，链接器根本不看库。
  • 如果它只有声明、没有定义（D）：链接器认为"未定义的 weak 符号不需要解析"——这是 ELF 的规定——同样不拉库，于是符号留在 NULL。

所以 D 是最惨的：你写了 hook，库里也有实现，结果程序跑起来发现 hook 是 NULL，静默跳过。

解法

# 1) 强制拉入整个库
gcc main.o -Wl,--whole-archive libfoo.a -Wl,--no-whole-archive

# 2) 直接链 .o 而不是 .a（F 的做法）
gcc main.o hook.o

# 3) 让弱引用变成强引用：另有一个强引用的符号在该成员里（C 的做法）

工程建议：用 weak + 静态库做插件架构时，必须在构建脚本里显式 --whole-archive，并且加一条启动自检：if (!hook) log_warn("hook not linked");。否则"忘了拉进来"会以"功能静默缺失"的形式出现，极难排查。

五、common 符号与 -fno-common（gcc 10 起的行为变化）

未初始化的全局变量 int x;（不带 extern、不带 weak）在 C 里叫试探性定义（tentative definition）。传统上它被编译成 common 符号，多个 TU 各写一个 int x; 是允许的，链接期合并。

gcc 10 起默认 -fno-common，这条老规则变了：

--- 默认（gcc 13 = -fno-common）：两个 TU 都有 int x; ---
exit=1
/usr/bin/ld: multiple definition of `x'; first defined here

--- 加 -fcommon ---
exit=0
x=0

--- 一个 int x=99(强) + 一个 int x;(common) ---
x=99            <- 强胜 common，与顺序无关

$ nm：
-fcommon     -> 0000000000000004 C x     <- common
-fno-common  -> 0000000000000000 B x     <- 变成强符号！
写法 gcc 13 默认 -fcommon
int x;（试探性定义） B（强）→ 两处就冲突 C（common）→ 合并
int x = 0; D（强） D（强）
int __weak x; V（弱，不是 common） V

注意 int __attribute__((weak)) x; 不是 common，是 V。所以它既能和别处的 strong 共存（被覆盖），又不受 -fno-common 影响（实测两种顺序都是 cfg=5）。

实践：老代码（gcc ≤ 9 时代）里满地的 int x; 在 gcc 10+ 会突然报 multiple definition。修复方式三选一：加 -fcommon（掩盖）、改成 extern 声明 + 单一定义（正确）、或者给默认定义加 weak（本节的方案）。

六、动态链接：全局符号介入、-Bsymbolic、LD_PRELOAD

6.1 可执行文件的符号优先级最高

libw.c:  int __attribute__((weak)) f(void) { return 1; }
         int call_f(void) { return f(); }        <- 库内部调用 f

main_strong.c:  int f(void) { return 100; }      <- 可执行文件 strong

--- 运行结果 ---
main f()=100
  lib call_f -> f()=100        <- 库内部的 f 也变成了 100！

这就是"全局符号介入（global symbol interposition）"：ELF 的符号查找顺序是 可执行文件 → 预加载库 → 其他共享库。所以共享库内部的调用会被可执行文件的同名符号截胡。

后果：你的 .so 里那个 weak 默认实现，对可执行文件的 strong 版本毫无抵抗力——连库内部调用都会被带走。

6.2 -Bsymbolic 锁死库内部绑定

--- 同一个 so 用 -Wl,-Bsymbolic 编译 ---
main f()=100
  lib call_f -> f()=1          <- 库用自己的 weak 实现了

-Bsymbolic 让库内部引用优先绑定到自己的定义，不再被外部介入。代价：库之间无法互相覆盖（失去 LD_PRELOAD 的一部分能力）。变种 -Bsymbolic-functions 只对函数生效，保留数据介入能力。

什么时候需要：发布 SDK/中间件 .so，且内部有同名符号不希望被用户的可执行文件劫持时。发布给第三方的库，建议加。

6.3 LD_PRELOAD 覆盖不了可执行文件自己的符号

--- 可执行文件不定义 impl，只用 liba.so（impl=10）---
impl()=10
--- LD_PRELOAD=libb.so（impl=555）---
impl()=555                     <- 生效

--- 可执行文件自己定义了 impl=777 ---
no preload:  impl()=777
with preload: impl()=777       <- 无效！

结论：LD_PRELOAD 只能覆盖库与库之间的符号竞争，覆盖不了可执行文件自己定义的符号（因为可执行文件在查找顺序的最前面）。

这条在调试时极容易误判：你 LD_PRELOAD 了一个 mock，main 里的调用却还是真的——因为被测函数就定义在可执行文件里。解法：把被测函数挪进 .so，或用 -Wl,--wrap=symbol。

七、weak 的真实性能代价：3.2 倍

weak 不是免费的。因为编译器必须保留"链接期可能被替换"的能力，weak 函数永远不会被内联。

volatile int sink;
int __attribute__((weak)) addw(int x) { return x + 1; }   /* weak   */
int adds(int x)                       { return x + 1; }   /* strong */
static int addi(int x)                { return x + 1; }   /* static */

for (int i = 0; i < 200000000; i++) sink = addw(i);   /* 2 亿次 */

--- gcc -O2 ---
weak   (not inlined) 0.131451 s
strong (inlined)     0.040835 s
static (inlined)     0.047370 s
                     -> weak 慢 3.2 倍

反汇编坐实了原因：

weak   循环体:  10c5:  call  1300 <addw>        <- 真实函数调用，2 亿次
strong 循环体:  1110:  lea   0x1(%rax),%edx     <- 内联 + 2 路展开
                1113:  add   $0x2,%eax

代码生成层面的对比（同一 TU、-O2）：

被调用函数 use() 的反汇编 内联了吗
strong（T） lea 0x1(%rdi),%eax; ret ✅ 甚至常量折叠
static lea 0x1(%rdi),%eax; ret ✅
weak（W） jmp <use+0x9>（尾调用） ❌ 永远不会

而且声明带不带 weak 都一样（实测 t1/t2 都是 jmp）——只要定义体上有 __attribute__((weak))，符号就是 W，编译器就不内联。

工程结论：weak 适合冷路径——板级初始化、可选 hook、错误处理、测试替身。热路径上不要用 weak（行情处理循环、DMA 回调、ISR）。需要"可替换 + 高性能"时，用函数指针 + 显式注册，或者编译期 #ifdef + 内联。

八、static + weak 是硬错误（不是警告）

static void __attribute__((weak)) sf(void) { }

gcc:   error: weak declaration of 'sf' must be public
clang: error: weak declaration cannot have internal linkage

两个编译器都是 error，直接编不过。理由很直白：weak 是给链接器的指令，而 static 符号链接器根本看不见。

推论：任何"链接期可替换"的诉求，符号必须有外部链接。所以：

写法 能否被覆盖 备注
void f(void) {} + 调用方 ❌（强，无法替换） 默认
__weak void f(void) {} ✅ 本节主角
static inline void f(void) {} ❌ 内联展开，weak 无从谈起 头文件小函数
static __weak ... ❌ 编译错误 —
inline __weak void f(void) {} ⚠️ 属性生效但语义混乱 见下

关于 inline：inline 要求编译期展开，weak 要求链接期替换，语义对立。如果同时写，实测 gcc 仍然生成 jmp（weak 优先），但代码让读者困惑。别这么写。

九、alias：给符号起别名

9.1 语法与铁律

void impl(void) { puts("impl"); }
void pub(void) __attribute__((alias("impl")));   /* pub 与 impl 同一地址 */

铁律（实测）：

规则 违反后果
目标必须在同一 TU 且已定义 error: 'pub' aliased to undefined symbol 'target'
目标可以是 static（同 TU 内可见即可） ✅ 实测 gcc/clang 都通过并正确执行
支持链式 alias（a→b→c） ✅ 实测 a_alias() 调到 c_impl 
/* 实测：alias 到 static 是允许的 */
static void impl_static(void) { printf("  static impl\n"); }
void pub_static(void) __attribute__((alias("impl_static")));
-> exit=0，正确打印 "static impl"

/* 跨 TU alias：编译期就报错 */
extern void target(void);
void pub(void) __attribute__((alias("target")));
-> error: 'pub' aliased to undefined symbol 'target'

注意"跨 TU"报错发生在编译期，因为 gcc 在本 TU 找不到 target 的定义。这和 weak 的链接期语义完全不同。

9.2 alias + weak：一组符号共享默认实现

static void default_log(int lvl, const char *msg) { fprintf(stderr, "[%d] %s\n", lvl, msg); }

void log_info(int lvl, const char *msg) __attribute__((weak, alias("default_log")));
void log_warn(int lvl, const char *msg) __attribute__((weak, alias("default_log")));
void log_err (int lvl, const char *msg) __attribute__((weak, alias("default_log")));

实测：

--- 无覆盖 ---
al:  impl
--- 另一 TU 提供 strong al ---
al:  STRONG al          <- 成功覆盖，其他 alias 不受影响

三个符号默认指向同一个实现，用户可以只覆盖其中一个。内核 printk 体系、glibc 的 __libc_* 别名都靠这个模式。

十、其他实测边界

10.1 头文件里放 weak 定义：合法但危险

/* hdr.h —— 非 static 的函数定义直接放头文件 */
int __attribute__((weak)) hw(void) { return 3; }

--- 不加 weak（对照）---
multiple definition of `hw'          <- 链接错误

--- 加 weak ---
exit=0，hw()=3                        <- 两个 TU 各有一份 weak 定义，取第一个

--- 再加一个 TU 提供 strong ---
hw()=33                               <- 强胜，链接顺序不影响

能编过，但别这么用：每个包含该头文件的 TU 都会生成一份代码（体积膨胀），而且"取第一个"依赖链接顺序。头文件里放函数定义的正确姿势是 static inline。

10.2 -z muldefs：让两个强符号共存

--- 默认 ---
multiple definition of `dup'
--- -Wl,-z,muldefs ---
dup=1          <- 取第一个
--- 反序 ---
dup=2

等价于把强符号降级成"取第一个"。仅在救急时用（比如合并两个第三方库），日常代码里这是掩盖 bug。

10.3 --gc-sections 会回收没人引用的 weak stub

--- 不加 ---   0000000000001163 T keeper   0000000000001149 W unused_stub
--- 加 ---     0000000000001149 T keeper      （unused_stub 消失）

需要配合 -ffunction-sections -fdata-sections。对嵌入式很有用：一堆板级 stub 里没用到的自动被裁掉。

10.4 声明与定义的 weak 标记不必一致

/* inc_a.c */
int __attribute__((weak)) g(void);   /* 声明带 weak */
int g(void) { return 1; }            /* 定义不带 */
-> nm: 0000000000000000 W g           <- 仍然是弱！strong 覆盖生效 g()=999

/* inc_d.c */
int __attribute__((weak)) h2(void) { return 7; }   /* 定义带 weak */
/* inc_m.c */
int h2(void);                                       /* 声明不带 */
-> h2()=777                                          <- strong 覆盖仍生效

结论：只要符号最终是 W/V，覆盖就生效，调用方看不看得到 weak 标记无所谓。但声明不带 weak 会让读者误以为它不可替换——写进去，为了可读性。

10.5 LTO 不会破坏 weak 覆盖（证伪一条传言）

常见说法："-flto 跨模块优化会看穿 weak，直接内联默认实现，绕过 strong 覆盖。"

--- gcc -O0 ---            f()=100
--- gcc -O2 ---            f()=100
--- gcc -O2 -flto ---      f()=100     <- 覆盖仍生效
--- clang -O2 -flto ---    f()=100     <- 覆盖仍生效

在 gcc 13.3 / clang 18.1.3 上未复现。LTO 保留了 weak 语义（这也解释了为什么第七节里 weak 永远不内联——LTO 也救不回来，代价是实打实的）。

老版本 gcc（≈4.x–7.x）确实有过相关问题。现在的工具链是安全的，但如果项目跨多版本编译器，weak + LTO 仍建议加一条集成测试。

题目 1：两个 TU 都写了 int attribute((weak)) cfg = 1; 和 = 2;，链接后值是多少？取决于什么？

取决于链接顺序：先出现者胜。

实测：

cw1.o 在前 -> w=1
cw2.o 在前 -> w=2

这与"一强一弱"完全不同——强符号无论顺序都胜。所以工程上绝对不要让同一符号在两处都是 weak 定义；默认实现标 weak，覆盖方不标。

题目 2：库里用 __weak 提供了默认 hook()，主程序在另一个 .c 里实现了 strong 版，但库是 .a 静态库。运行发现走的还是默认实现，为什么？

weak 定义已经满足了符号解析，链接器不会去静态库里提取成员。

实测六种组合：

A. main 有 weak 定义 + 库成员只含 hook        -> hook()=0    （默认）
B. 库成员含 hook+other，other 未引用          -> hook()=0    （默认）
C. 业务代码引用了 other，成员被拉入           -> hook()=42   （strong）
D. main 只有 weak 声明 + 库                   -> addr=(nil)  （NULL！）
E. D + --whole-archive                        -> hook()=42
F. main 有 weak 定义 + 直接链 .o              -> hook()=42

解法：-Wl,--whole-archive（推荐，配合启动自检 if (!hook) warn()）、直接链 .o、或让成员里有别的符号被强引用。

题目 3（判断）：LD_PRELOAD 是万能的符号替换手段，连可执行文件自己定义的函数也能替换。

错。

可执行文件不定义 impl，只用 liba.so(10)  -> 10
LD_PRELOAD=libb.so(555)                  -> 555   <- 生效
可执行文件自己定义 impl=777              -> 777
+ LD_PRELOAD=libb.so(555)                -> 777   <- 无效

ELF 符号查找顺序：可执行文件 → LD_PRELOAD 库 → 其他共享库。可执行文件排在最前，所以 PRELOAD 只能覆盖库与库之间的竞争。

调试时 mock 不生效，先确认被测符号是不是就定义在可执行文件里。

题目 4：为什么共享库内部的调用也会被可执行文件的同名符号劫持？怎么阻止？

这是 ELF 全局符号介入（interposition）：

libw.c:  __weak int f(void){return 1;}   int call_f(void){return f();}
main:    int f(void){return 100;}

输出：main f()=100    lib call_f -> f()=100      <- 库内部也被带走

用 -Wl,-Bsymbolic 编译共享库：

main f()=100    lib call_f -> f()=1              <- 库用自己的

-Bsymbolic 让库内部引用优先绑定自身定义。变种 -Bsymbolic-functions 只锁函数、保留数据介入。代价：失去部分 LD_PRELOAD 覆盖能力。发布给第三方的库建议加。

题目 5：static void attribute((weak)) f(void) {} 能通过编译吗？

不能，两个编译器都是 error：

gcc:   error: weak declaration of 'f' must be public
clang: error: weak declaration cannot have internal linkage

weak 是给链接器的指令，static 的符号链接器看不见，语义自相矛盾。想要"链接期可替换"，符号必须有外部链接。

题目 6：热路径上有个函数调用 2 亿次，标了 weak 之后慢了多少？为什么？

慢 3.2 倍（实测 0.131 s vs 0.041 s）。

反汇编：

weak   循环体:  call  1300 <addw>          <- 2 亿次真实调用
strong 循环体:  lea   0x1(%rax),%edx       <- 内联 + 2 路展开
                add   $0x2,%eax

weak 函数永远不会被内联——编译器必须保留"链接期可能被替换"的可能。而且声明带不带 weak 都一样，只要定义体上有 __attribute__((weak))，符号就是 W。

所以：weak 用于冷路径（初始化、错误处理、可选 hook、测试替身）；热路径用 static inline 或函数指针显式注册。

题目 7：老项目升级 gcc 后，多个 .c 里都有的 int x; 突然报 multiple definition，为什么？三种修法？

gcc 10 起默认 -fno-common，int x;（试探性定义）从 common 符号（C）变成强符号（B），两处就冲突。

默认(-fno-common):  multiple definition of `x'
-fcommon:           x=0
$ nm:  -fcommon -> C x      -fno-common -> B x

三种修法： 1. -fcommon —— 掩盖，回退到老行为（最快，不推荐） 2. extern int x; + 单一定义 —— 正确做法 3. 默认定义加 __attribute__((weak)) —— 本节的方案，符号变 V，既不与 strong 冲突，又能被覆盖（实测两种链接顺序都被 cfg=5 覆盖）

注意 int __weak x; 是 V 不是 C，不受 -fno-common 影响。

6.9

.1 强符号和弱符号

完整总纲与实测数据见 6.9 属性声明：weak 与 alias。

本节讲什么

链接器规则：强符号 唯一定义；弱符号 可被强符号 覆盖 而不报 duplicate symbol。C 中 weak attribute 与 common block 行为不同。

要点

种类 典型来源
强符号 函数定义、已初始化全局
弱符号 __attribute__((weak)) 
/* a.c */
int counter __attribute__((weak)) = 0;
/* b.c — 强符号覆盖 */
int counter = 100;

gcc -c a.c -o a.o && gcc -c b.c -o b.o
gcc a.o b.o -o t && nm t | grep counter
  • 重复强符号 → 链接错误
  • 内核 __weak 宏广泛用于 arch hook

常见陷阱

  1. 强弱符号同名同类型才能覆盖 → 类型不匹配链接器静默选一个 weak int counter 与 strong long counter（不同类型）共存时，链接器不会报错，按"强优先"选 long 的存储，但访问代码按 int 解读——读到的是截断或异位的值。GCC 的 -Wl,--no-undefined 不查类型，-flto 才能跨编译单元类型检查。约定**：weak/strong 必须在头文件共享同一声明。

  2. 静态函数不能 weak → weak 只对全局符号有效 static void f(void) __attribute__((weak)); 看似合法但无意义——静态符号不参与链接，无"强弱"概念。weak 只对具有外部链接的符号生效。误用会导致 weak 静默失效，覆盖不会发生，运行时仍调原版。

  3. 动态链接中 weak 行为与静态不同 静态链接：strong 覆盖 weak，确定无疑。动态链接：weak 符号在 .so 中仍可被可执行文件的 strong 覆盖（默认符号解析规则），但若 dlopen(RTLD_LOCAL) 加载的 .so 含 strong 定义，不会**覆盖主程序的 weak——只在自己命名空间内有效。LD_PRELOAD 注入靠的是全局符号插序，与 weak 无直接关系。

自测题

1.（选择） 下列哪种符号是强符号？ - A. int x __attribute__((weak)) = 0; - B. int x;（未初始化全局） - C. int x = 1;（已初始化全局） - D. extern int x;

答案

C。已初始化全局是强符号；__attribute__((weak)) 显式声明弱；未初始化全局 int x; 是 common 符号（GCC -fcommon 默认开，GCC 10+ 改默认 -fno-common 后变强）；extern int x; 仅声明不是定义。坑：common 符号在链接时允许重复，行为类似弱但语义不同——不要把 common 当 weak 用。

2.（判断） 同一程序中两个 void f(void) {}（无 weak）一定链接报错。

答案

对，但有例外。两个强符号同名同类型，链接器报 multiple definition of 'f'。例外：GCC 10 之前默认 -fcommon，未初始化全局变量是 common 符号（不算强符号），多个 common 会被合并——但函数不是 common，仍报错。GCC 10+ 默认 -fno-common，未初始化全局也变强，更严格。函数永远是强符号（除非 weak），重复定义必报错。

3.（踩坑） 模块 A 头文件声明 void hook(void) __attribute__((weak));，A.c 中定义 weak 版 void hook(void) {}；模块 B.c 直接 #include "A.h" 后定义 void hook(void) { /* B 版 */ }。链接时 strong 选中 B 版——但B.c 中没加 weak 属性，A.h 声明带 weak，是否冲突？

答案

不冲突。C 标准允许同一符号多次声明，属性可不同。GCC 处理规则：只要有一个声明不带 weak，即为强。所以 B.c 看到的是 weak 声明，但其定义不写 weak，链接器视 B 的定义为强。这是惯用法：头文件统一声明 weak，提供方写 weak 实现，覆盖方写普通实现。 坑：如果 B.c 把声明复制为 void hook(void);（不带 weak），与头文件 weak 声明"冲突"——GCC 仍接受，但编译警告 -Wattributes。最佳实践：覆盖方#include 头文件即可，不重复声明。

4.（应用） 设计一个"板级可选初始化钩子"机制：默认实现是空函数，BSP 可覆盖。给出声明与用法。

答案 
/* board.h */
void board_early_init(void) __attribute__((weak));

/* board_default.c (链接进所有镜像) */
#include "board.h"
void __attribute__((weak)) board_early_init(void) {
    /* 默认空实现，可被 BSP 覆盖 */
}

/* board_rpi.c (特定板级，覆盖) */

    /* Raspberry Pi 特定初始化 */
    mmu_init();
    clock_init();
}

/* main.c */
int main(void) {
    board_early_init();    /* 自动选到强版本 */
    /* ... */
}

参考答案

weak 函数优点：(1) 零间接调用开销（链接期绑定，直接跳转）；(2) 代码简洁。缺点：(1) 只能有一个最终实现；(2) 运行时不能切换。函数指针优点：(1) 运行时可动态切换；(2) 可有多套实现。缺点：(1) 每次调用间接寻址（多一次内存访问）；(2) 需要全局变量。嵌入式启动阶段用 weak（零开销、链接期决定），运行时需要多态用函数指针。

完整总纲与实测数据见 6.9 属性声明：weak 与 alias。

本节讲什么

Weak 典型场景：默认 stub、可选 feature、测试 mock、单内核多 BSP。避免 #ifdef 泛滥；链接时自动选最强定义。本节展开四种主流用法、alias + weak 组合、与 #ifdef 的取舍。

要点

用法一：默认 stub（BSP/驱动钩子）

/* 默认空实现，板级可覆盖 */
void __attribute__((weak)) pm_suspend(void) { }
void __attribute__((weak)) trace_irq(int irq) { (void)irq; }

调用方代码不变，链接时若 BSP 提供 strong 实现则自动选中。

用法二：Kconfig 可选 feature

/* kernel/panic.c */
void __attribute__((weak)) panic_handler(const char *msg) { /* 默认空 */ }

/* 如果 CONFIG_DEBUG_PANIC 开启，debug.c 提供 strong 版本打印栈 */

Kconfig 关闭 feature 时仍链 weak stub，无需 #ifdef 包裹调用点。

用法三：单测 mock

/* prod.c */
time_t time_now(void) { return real_clock(); }

/* test.c */
time_t time_now(void) { return fake_time; }   /* 强符号，单测链接时覆盖 */

测试程序链接 test.o + prod.o（去掉原 time_now 或保留 weak 版），mock 自动生效。无需改生产代码。

用法四：alias + weak 组合（默认实现可被部分覆盖）

static void default_log(int level, const char *msg) {
    fprintf(stderr, "[%d] %s\n", level, msg);
}
void log_info(int level, const char *msg)
    __attribute__((weak, alias("default_log")));

alias 让 log_info 默认指向 default_log，弱符号允许用户重写 log_info 而无需碰 default_log。内核 __weak + __alias 在 init/main.c 处处可见。

常见陷阱

  1. weak 函数被内联后失去 weak 语义 如果 weak 函数在头文件中 inline 定义，调用方可能直接内联默认版，链接期 strong 覆盖失效。坑：static inline __attribute__((weak)) 几乎肯定是错的——static 已限定本编译单元，weak 无意义。weak 必须是具有外部链接的函数，定义在 .c 文件中。

  2. LTO 下 weak 行为变化 -flto 跨编译单元优化时，编译器可能"看穿" weak 函数调用，直接内联默认实现，绕过 strong 覆盖。GCC 10+ 修复了大部分场景，但边界情况仍有问题。生产代码用 LTO + weak 需测试覆盖确认。内核默认不开 LTO（部分架构可开 CONFIG_LTO）。

  3. weak 不能覆盖动态库符号（默认） 可执行文件调 printf，libc 中 printf 即使被声明 weak，运行时仍走 libc 实现——主可执行文件的符号优先级高于 .so，但反之不行：.so 中的 strong 定义不会覆盖主程序中的 weak 定义（除非 LD_PRELOAD 或 dlopen(RTLD_GLOBAL)）。误以为"weak 总能被覆盖"在动态链接下踩坑。

自测题

1.（选择） 以下哪种场景最适合用 weak 而不是 #ifdef？ - A. 编译时根据 CONFIG_SMP 决定是否启用自旋锁 - B. 不同 BSP 提供不同 board_early_init 实现 - C. 调试版本打开详细日志 - D. 64 位 vs 32 位平台差异

答案

B。BSP 差异在链接时通过替换 .o 文件实现，无需重新编译内核主体——正是 weak 的适用场景。A/C/D 都是编译期配置，#ifdef 更合适（编译时决定，运行时无开销）。weak 的代价是间接调用（无法内联），编译期配置零运行时开销。

2.（判断） static inline void f(void) __attribute__((weak)); 是合理的 weak 用法。

答案

错。static 限定符号为编译单元内部，无外部链接，weak 属性无意义（链接器看不到该符号）。inline 进一步暗示编译器内联，更削弱"链接期覆盖"语义。正确写法：weak 函数必须 extern（默认），定义在 .c 文件中，调用方通过头文件 extern 声明看到 weak 标记。

3.（踩坑） 单测中 mock 了 time_now（strong 覆盖 weak 默认实现），生产代码用 -O2 编译。单测跑过，但线上仍用默认实现。定位后发现 time_now 在头文件中 static inline 定义。为什么？

答案

static inline 函数无外部链接，weak 失效，调用方直接内联默认实现。链接期 strong 版本根本没机会被选中——编译器已在每个调用点展开默认代码。修复： 1. 默认实现移到 .c 文件，去掉 static inline，标 weak。 2. 头文件只留 extern 声明（带 weak 属性）。 3. 关键路径若性能敏感，用宏或 always_inline 内联版 + weak 兜底版双轨。 教训：weak 与 inline 是对立语义——inline 要求编译期展开，weak 要求链接期替换，二者不可兼得。

4.（应用） 用 alias + weak 实现一组日志函数，默认全部转发到 default_log，但允许用户单独覆盖 log_err。

答案 
/* log_default.c */
#include <stdio.h>
static void default_log(int level, const char *msg) {
    fprintf(stderr, "[%d] %s\n", level, msg);
}

    __attribute__((weak, alias("default_log")));

    __attribute__((weak, alias("default_log")));

归属：A 档 · CH2 GNU C 高级特性（源码看不见，但真实发生） 实测环境：WSL · gcc 13.3.0（GNU ld 2.42）/ clang 18.1.3 · x86-64 · glibc 2.39 源码核对：Linux v6.6 include/linux/compiler.h、include/linux/log2.h、include/asm-generic/bitops/__fls.h 配套小节：6.11.1 什么是内建函数 · 6.11.2 常用的内建函数 · 6.11.3 C 标准库的内建函数 · 6.11.4 __builtin_constant_p · 6.11.5 __builtin_expect · 6.11.6 内核中的 likely/unlikely 相关：6.6 __attribute__ 总纲 · 6.8 format · 6.10 inline · 6.1 C 标准与 gnu11

本节讲什么

前面 6.6–6.9 讲的 __attribute__ 是告诉编译器某个声明有什么性质。内建函数（builtins）走的是另一条路——它本身就是编译器内置的伪函数：语法上像函数调用，编译期被编译器「拦截」，展开成零到多条目标指令。

一句话概括：

__builtin_* 是编译器「看得懂」的函数名。编译器遇到它，直接生成对应的目标平台指令（或编译期常量），不需要链接、不产生符号表条目。

但「直接映射到目标指令」这句话有一个致命陷阱——书里没讲、实测才暴露：

  1. __builtin_popcount 不加 -mpopcnt 根本不用 POPCNT 指令——它偷偷调用 __popcountdi2（libgcc 软件实现）。你以为零开销，其实有一个函数调用 + 30 条 SWAR 指令；
  2. __builtin_constant_p 在 -O0 下几乎全返回 0——连 static const 都不认。内核永远 -O2 没事，但你用 -O0 -g 调试时宏的行为会变；
  3. __builtin_expect 改变的是基本块排列顺序——标错方向会把 hot path 变成跳转目标，实测汇编一目了然；
  4. libc 函数被自动当 builtin 处理——strlen("hello") 在 -O2 下折叠成编译期常量 5，但加 -fno-builtin 后变成真实的 strlen@plt 调用。__builtin_strlen 不受 -fno-builtin 影响；
  5. __builtin_add_overflow 只需一条 add + 一条 seto（溢出标志读取）——比手写的溢出检查快且安全；
  6. __builtin_unreachable 让编译器删除不可能到达的分支——但如果你骗了它，函数返回的是寄存器里的垃圾值（UB）。

2.1 popcount 的陷阱

这是本节最反直觉的发现。很多人写 __builtin_popcount 时以为它在 x86 上一定生成 POPCNT 指令——错。

$ gcc -std=gnu11 -O2 -c t13_popcnt.c -o t13_def.o
$ objdump -d t13_def.o | sed -n '/<do_popcount_default>:/,/^\$/p'
0000000000000000 <do_popcount_default>:
   0:  endbr64
   4:  sub    $0x8,%rsp
   8:  mov    %edi,%edi
   a:  call   f <do_popcount_default+0xf>     # ← 调 __popcountdi2！
   f:  add    $0x8,%rsp
  13:  ret

$ gcc -std=gnu11 -O2 -mpopcnt -c t13_popcnt.c -o t13_popcnt.o
$ objdump -d t13_popcnt.o | sed -n '/<do_popcount_default>:/,/^\$/p'
0000000000000000 <do_popcount_default>:
   0:  endbr64
   4:  xor    %eax,%eax
   6:  popcnt %edi,%eax                        # ← 硬件指令！
   a:  ret

__popcountdi2 是什么？它是 libgcc 的运行时函数，用 SWAR（SIMD Within A Register）算法软件计算 popcount：

__popcountdi2:
    movabs $0x5555555555555555,%rdx    # 0x55 = 01010101...
    mov    %rdi,%rax
    shr    $1,%rax
    and    %rdx,%rax                    # 每 2 位一组
    sub    %rax,%rdi
    movabs $0x3333333333333333,%rax     # 0x33 = 00110011...
    ...（共 13 条指令）
    imul   %rdx,%rax
    shr    $0x38,%rax
    ret

总结：

编译选项 __builtin_popcount 生成的代码 开销
-O2（默认） call __popcountdi2 函数调用 + 13 条 SWAR 指令
-O2 -mpopcnt popcnt %edi,%eax 1 条指令
-O2 -march=native popcnt %edi,%eax 1 条指令（CPU 支持 POPCNT 时）

HFT/嵌入式教训：如果你的热点循环用 __builtin_popcount 做位图统计，一定要在 Makefile 里加 -mpopcnt（或 -march=native），否则你以为的一条指令其实是 14 条指令 + 一次函数调用。内核不担心这个——内核的 hweight32() 在编译时根据 CONFIG_ARCH_HAS_FAST_MULTIPLIER 等选项选择内联汇编或 builtin。

2.2 clang 的 popcount：直接内联 SWAR

clang 不调用 __popcountdi2，而是直接内联 SWAR 算法（不生成 popcnt 指令，但也不生成 call）：

$ clang -std=gnu11 -O2 -c t1_bitops.c -o t1_clang
$ objdump -d t1_clang | sed -n '/<do_popcount>:/,/^\$/p'
0000000000001150 <do_popcount>:
    1150:  mov    %edi,%eax
    1152:  shr    $1,%eax
    1154:  and    $0x55555555,%eax
    1159:  sub    %eax,%edi
    ...（内联 SWAR，约 12 条指令）
    1182:  ret

clang 也不加 -mpopcnt 就不生成 popcnt 指令。但至少它内联了，省了函数调用开销。加了 -mpopcnt 后 clang 也用 popcnt 指令。

2.3 clz/ctz/ffs/parity：直接硬件

这四个不加任何 flag 就映射到硬件指令：

int do_clz(uint32_t v)     { return __builtin_clz(v); }
int do_ctz(uint32_t v)     { return __builtin_ctz(v); }
int do_ffs(uint32_t v)     { return __builtin_ffs(v); }
int do_parity(uint32_t v)  { return __builtin_parity(v); }

do_clz:    bsr    %edi,%eax ; xor $0x1f,%eax        # Bit Scan Reverse + 补码
do_ctz:    tzcnt  %edi,%eax                         # Trailing Zero Count (BMI1)
do_ffs:    bsf    %edi,%eax ; cmove ; add $1        # Bit Scan Forward + 空值保护 + 1-based
do_parity: shr $16 ; xor ; xor %ah,%al ; setnp %al  # 用 x86 PF（奇偶）标志位！
函数 对应 x86 指令 输入为 0 的行为
__builtin_clz(0) bsr 0 → ZF=1，xor $0x1f 后返回 32 UB（返回 32，但标准未定义）
__builtin_ctz(0) tzcnt 0 → 返回 32（BMI1 语义） BMI1 下返回 32（非 UB）；无 BMI1 时 bsf 0 → UB
__builtin_ffs(0) bsf 0 + cmove $-1 → 返回 0 安全：返回 0
__builtin_parity(0) 算出 0 → setnp → 0 安全

安全规则：__builtin_ffs(0) 返回 0（安全）；__builtin_clz(0) 和 __builtin_ctz(0) 是 UB。内核 fls() 在 include/asm-generic/bitops/__fls.h 中先检查 v == 0 再调用 __builtin_clz。

2.4 clang 对比：生成完全相同的指令

$ objdump -d t1_clang | sed -n '/<do_clz>:/,/^\$/p'
do_clz:    bsr    %edi,%eax ; xor $0x1f,%eax        # 与 gcc 完全相同
do_ctz:    tzcnt  %edi,%eax                         # 与 gcc 完全相同
do_ffs:    bsf    %edi,%ecx ; cmove ; inc           # clang 用 inc 替代 add 1
do_parity: shr $16 ; xor ; xor %ch,%cl ; setnp      # 等价但寄存器分配不同

除了 popcount（gcc 调函数、clang 内联），其他五个位的 builtin 在两个编译器上生成的指令本质相同。

__builtin_bswap32 bswap %eax 专用指令
__builtin_bswap64 bswap %rax 专用指令

gcc 和 clang 生成完全相同的指令。常量参数时编译期折叠：__builtin_bswap32(0xAABBCCDDu) → 0xDDCCBBAA。

内核：include/linux/byteorder/generic.h 在大端机上 #define cpu_to_le32(x) ((__force __le32)__builtin_bswap32(x))，小端机上 #define cpu_to_le32(x) ((__force __le32)(x))（no-op）。

四、__builtin_constant_p：编译期常量检测器

int r1 = __builtin_constant_p(5);           // → 1
int r2 = __builtin_constant_p(volatile_var); // → 0
表达式 -O2 返回 -O0 返回 说明
__builtin_constant_p(5) 1 1 字面量永远是常量
__builtin_constant_p(volatile v) 0 0 volatile 永远不是常量
__builtin_constant_p(static const g) 1 0 static const 在 -O0 下不识别
__builtin_constant_p(&local) 0 0 栈地址不是编译期常量
__builtin_constant_p(local) 1 0 local=10 未被修改，-O2 能推断
__builtin_constant_p(n) (运行时变量) 0 0 运行时变量

4.1 -O0 的陷阱

=== gcc -O2 ===
constant_p(5) = 1
constant_p(volatile v) = 0
constant_p(static const g) = 1      ← -O2 识别
constant_p(&local) = 0
constant_p(local) = 1               ← -O2 推断出 local=10

=== gcc -O0 ===
constant_p(5) = 1
constant_p(volatile v) = 0
constant_p(static const g) = 0      ← -O0 不识别！
constant_p(&local) = 0
constant_p(local) = 0               ← -O0 不推断！

根因：__builtin_constant_p 依赖编译器的常量传播（constant propagation）能力。-O0 不做任何优化，不做常量传播，所以除了字面量以外几乎全返回 0。

工程教训：如果你写了一个用 __builtin_constant_p 做编译期分流的宏，在 -O0 -g 调试模式下走的永远是 else 分支。内核永远 -O2 编译，不会遇到；但用户态调试时要注意。

4.2 内核的用法

内核用 __builtin_constant_p 实现 memset/memcpy 的编译期大小分流：

/* 简化版，实际在 include/linux/string.h / lib/string.c */
#define __memset(s, c, n) ({                              \
    size_t _n = (n);                                      \
    if (__builtin_constant_p(_n) && _n <= 16) {           \
        /* 编译器内联展开：几条 mov 指令 */               \
        char *_p = (s);                                    \
        switch (_n) {                                      \
        case 16: _p[15] = c;                              \
        /* ... fall through ... */                         \
        case 1:  _p[0] = c;                               \
        }                                                 \
    } else {                                               \
        __real_memset(s, c, _n);  /* 调库函数 */            \
    }                                                     \
})

实测 my_memset(buf, 'X', 5) 在 -O2 下生成：

main:
    movl   $0x58585858,(%rsp)        # 4 个 'X'
    movb   $0x58,0x4(%rsp)           # 1 个 'X' = 共 5 字节
    # 无 call 指令！

而 my_memset(buf, 'Y', n)（n 是运行时变量）生成 call memset@plt。

4.3 __builtin_choose_expr

int y = __builtin_choose_expr(
    __builtin_constant_p(x),    // 编译期条件
    x * 2,                      // 真：编译期保留
    -1                          // 假：编译期丢弃
);

__builtin_choose_expr 像 ?:，但在编译期选择——非选中分支的代码完全不生成。与 __builtin_constant_p 配合，可以在宏里写「编译期分流」。

实测：

choose_expr(var x)  = -1     ← x 是运行时变量 → 走 else
choose_expr(const 10) = 20   ← 10 是常量 → 走 then，10*2=20

gcc 和 clang 都支持 __builtin_choose_expr（实测确认）。

五、__builtin_expect：分支布局，不是分支预测

#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

书里说了「告诉编译器分支大概率方向」，但没展示汇编。实测一目了然：

5.1 不标 expect

int check_plain(int *p) {
    if (!p) return -1;     // 没标
    return *p;
}

check_plain:
    test   %rdi,%rdi        # 检查 NULL
    je     .Lerr            # 为空 → 跳错误路径
    mov    (%rdi),%eax      # 成功路径（fall-through）
    ret
.Lerr:
    mov    $0xffffffff,%eax # 错误路径
    ret

gcc 猜对了：成功路径在 fall-through 位置。

5.2 标 unlikely（正确方向）

int check_unlikely(int *p) {
    if (__builtin_expect(!p, 0)) return -1;  // !p 大概率为 0（假）
    return *p;
}

check_unlikely:
    test   %rdi,%rdi
    je     .Lerr              # 错误跳走
    mov    (%rdi),%eax        # 成功路径（fall-through）
    ret
    nopl   0x0(%rax)          # ← padding！把错误路径推远
.Lerr:
    mov    $0xffffffff,%eax
    ret

与 plain 版的差异：多了 padding（nopl），把错误路径推到更远的地址。icache 中 hot path 更紧凑。

5.3 标 likely（故意标反方向）

int check_likely(int *p) {
    if (__builtin_expect(!p, 1)) return -1;  // 告诉编译器 !p 大概率为 1（真）= p 大概率为 NULL
    return *p;
}

check_likely:
    mov    $0xffffffff,%eax   # ← 预先加载错误返回值！
    test   %rdi,%rdi
    jne    .Lok               # p != NULL → 跳到成功路径
    ret                        # p == NULL → 返回 -1（fall-through）
.Lok:
    mov    (%rdi),%eax
    ret

完全反转：错误路径变成了 fall-through（hot），成功路径变成了跳转目标（cold）。如果实际运行中 p 经常非 NULL，每次都要跳转——icache miss。

5.4 clang 的行为

clang 生成的指令完全相同（test/je/mov/ret），但布局顺序一致。说明 __builtin_expect 对两个编译器的作用机制相同：重排基本块，不改指令选择。

5.5 !! 归一化

#define likely(x)   __builtin_expect(!!(x), 1)

!!(x) 把任意类型归一化为 0/1。为什么？因为 __builtin_expect 的第二参数是 long，如果 x 是指针或浮点，直接传会出类型问题。!! 强制转 int 0/1。

实测：likely(NULL) → 0、likely(42) → 1、likely((void*)0) → 0。归一化生效。

5.6 使用准则

准则 说明
profile 验证 先用 perf record / gcov 确认分支偏斜度。50/50 分支不要标
仅热路径 冷函数里标 likely 毫无意义
猜错代价 5-20% 性能损失（icache miss）
替代方案 PGO（-fprofile-generate/-fprofile-use）让编译器自己学

详见 6.11.5 和 6.11.6 内核中的 likely/unlikely。

六、__builtin_prefetch：缓存预取

__builtin_prefetch(ptr, rw, locality);
参数 取值 含义 x86 生成指令
rw 0 读预取 prefetcht0 / prefetchnta / prefetcht1 / prefetcht2
rw 1 写预取 prefetcht0（x86 不区分读写预取）
locality 0 无时间局部性 prefetchnta（Non-Temporal Access，不污染 cache）
locality 1 低时间局部性 prefetcht2（L2）
locality 2 中时间局部性 prefetcht1（L1）
locality 3 高时间局部性 prefetcht0（all levels）

实测 demo_prefetch_args：

demo_prefetch_args:
    prefetchnta (%rdi)        # (p, 0, 0) → Non-Temporal
    prefetcht2 (%rdi)         # (p, 0, 1) → L2
    prefetcht1 (%rdi)         # (p, 0, 2) → L1
    prefetcht0 (%rdi)         # (p, 0, 3) → all levels
    prefetcht0 0x4(%rdi)      # (p+1, 1, 3) → write, all levels
    ret

6.1 在 -O0 下也生成真指令

$ gcc -O0 -c t5_prefetch.c -o t5_O0.o
$ objdump -d t5_O0.o | sed -n '/<prefetch_at_O0>:/,/^\$/p'

    push   %rbp
    mov    %rsp,%rbp
    mov    %rdi,-0x8(%rbp)
    mov    -0x8(%rbp),%rax
    prefetcht0 (%rax)          # ← 真指令！
    nop
    pop    %rbp
    ret

与 __builtin_constant_p 在 -O0 下失效不同，__builtin_prefetch 在任何优化级别下都生成真实预取指令。

6.2 链表遍历中的实际效果

int sum_with_prefetch(struct node *head) {
    int sum = 0;
    struct node *p = head;
    while (p) {
        __builtin_prefetch(p->next, 0, 3);  // 预取下一个节点
        sum += p->val;
        p = p->next;
    }
    return sum;
}

sum_with_prefetch:
    xor    %eax,%eax
    test   %rdi,%rdi
    je     .Ldone
.Lloop:
    mov    %rdi,%rdx
    mov    0x8(%rdi),%rdi      # 加载 p->next
    add    (%rdx),%eax          # sum += p->val
    prefetcht0 (%rdi)           # ← 预取 p->next 指向的数据
    test   %rdi,%rdi
    jne    .Lloop
    ret

编译器把 prefetch 指令插在 p->next 加载之后、p = p->next 赋值之前——让 CPU 在处理当前节点时后台预取下一个节点的 cache line。

七、控制流内建：trap / unreachable / abort

内建函数 作用 gcc 生成 clang 生成
__builtin_trap() 触发非法指令异常 ud2 ud2
__builtin_unreachable() 告诉编译器此路径不可达 无指令（后续代码被删除） 无指令
__builtin_abort() 等价于 abort() call abort@plt call abort@plt

7.1 __builtin_trap → ud2

do_trap:
    push   %rax
    lea    "before trap\n",%rdi
    call   puts@plt
    ud2                          # ← __builtin_trap() = 一条指令，触发 SIGILL
    # "after trap" 那行 printf 被编译器删了（死代码消除）

ud2（0F 0B）是 x86 的「未定义指令」，CPU 执行到它时触发 SIGILL（非法指令信号）。ARM 上等价物是 UDF 或 BKPT。

7.2 __builtin_unreachable → 什么也不生成

int do_unreachable(int x) {
    switch (x) {
    case 0:  return 0;
    case 1:  return 1;
    case 2:  return 2;
    }
    __builtin_unreachable();  // 告诉编译器 x 只会是 0/1/2
}

do_unreachable:
    mov    %edi,%eax           # 直接返回 x（编译器知道只可能是 0/1/2）
    ret
    # 没有 switch 跳转表！编译器内联了所有 case。

7.3 骗编译器的代价

int lie_to_compiler(int x) {
    if (x > 0) return x;
    __builtin_unreachable();  // "x 永远 > 0"
}

lie_to_compiler:
    mov    %edi,%eax           # 直接返回 x
    ret

编译器删除了 x <= 0 分支。如果你传 lie_to_compiler(-5)，返回的是 %edi 寄存器里的值（即 -5 本身）——但标准说是 UB，什么结果都可能。

内核用法：BUG() → __builtin_trap()；BUG_ON(cond) → if (cond) __builtin_trap()。unreachable() 用于标注不可能到达的 default 分支。见 include/asm-generic/bug.h。

八、libc 折叠：strlen("hello") → mov $5, %eax

gcc 默认把很多 libc 函数当作 builtin 处理——当参数是编译期常量时，直接折叠成常量。

8.1 折叠演示

size_t do_strlen_const(void)  { return strlen("hello"); }  // 常量参数
size_t do_strlen_rt(const char *s) { return strlen(s); }  // 运行时参数

=== gcc -O2 ===
do_strlen_const:
    mov    $0x5,%eax           # ← strlen("hello") 编译期折叠成 5
    ret

do_strlen_rt:
    jmp    strlen@plt          # ← 运行时参数 → 调真实函数

同理：

libc 函数 常量参数（-O2） 运行时参数
strlen("hello") mov $5, %eax jmp strlen@plt
memcpy(dst, src, 5) 5 条 mov 指令内联 jmp memcpy@plt
memcpy(dst, src, 256) 16 条 movups（SSE 128 位） jmp memcpy@plt
strcmp("abc","abd") mov $-1, %eax jmp strcmp@plt
memset(buf, 0, 16) 1 条 movups %xmm0,(%rdi) jmp memset@plt

8.2 -fno-builtin 的效果

=== gcc -O2 -fno-builtin ===
my_strlen_const:
    lea    "hello",%rdi
    jmp    strlen@plt          # ← 不再折叠！调真实函数

my_builtin_strlen:
    mov    $0x5,%eax           # ← __builtin_strlen 不受影响
    ret

三层对照：

标志 strlen("hello") __builtin_strlen("hello") memcpy(dst, src, 5)
-O2（默认） mov $5, %eax mov $5, %eax 5 条 mov 内联
-O2 -fno-builtin jmp strlen@plt mov $5, %eax 5 条 mov 内联
-O2 -fno-builtin-strlen jmp strlen@plt mov $5, %eax 5 条 mov 内联

关键：-fno-builtin 关掉的是隐式识别（编译器看到 strlen 就当 builtin）；__builtin_strlen 是显式形式，永远不被 -fno-builtin 关掉。memcpy 的内联属于 tree-ssa 的 BUILTIN_MEMCPY 优化路径，与 -fno-builtin 独立——实测在 -fno-builtin 下 memcpy 仍然内联。

8.3 -ffreestanding 与内核

$ gcc -std=gnu11 -O2 -ffreestanding -c t7_libc.c -o t7_free.o
# 编译成功，无报错

-ffreestanding 告诉编译器「不假设有 hosted 环境（没有标准库）」。但它不关掉 __builtin_*——因为内建函数是编译器自带的，不依赖 libc。

内核 Makefile 里 -ffreestanding 一直开着，__builtin_* 照用。但 libc 隐式识别在 -ffreestanding 下会被关掉——内核自己实现了 memcpy/memset/strlen 等，不需要编译器隐式折叠。

8.4 C23：__builtin_stdc_* 标准化

C23（ISO/IEC 9899:2024）把一组 freestanding 安全的 libc 函数标准化为内建函数，前缀 __builtin_stdc_：

C23 内建 等价 libc
__builtin_stdc_memcmp memcmp
__builtin_stdc_memcpy memcpy
__builtin_stdc_memmove memmove
__builtin_stdc_memset memset
__builtin_stdc_strlen strlen
__builtin_stdc_strcmp strcmp
__builtin_stdc_strchr strchr

这些在 freestanding 模式下也可用，且不受 -fno-builtin 影响。GCC 14+ 和 Clang 19+ 支持。当前 WSL gcc 13.3 尚未完全支持，但 __builtin_memset 等旧形式仍可用。

九、溢出检查：__builtin_add_overflow 等

int __builtin_add_overflow(T1 a, T2 b, T3 *res);  // *res = a + b，返回是否溢出
int __builtin_sub_overflow(T1 a, T2 b, T3 *res);
int __builtin_mul_overflow(T1 a, T2 b, T3 *res);

9.1 硬件映射

int safe_add(int a, int b, int *result) {
    return __builtin_add_overflow(a, b, result);
}
int safe_mul(int a, int b, int *result) {
    return __builtin_mul_overflow(a, b, result);
}
int safe_add_u(uint32_t a, uint32_t b, uint32_t *r) {

}

safe_add:         add %esi,%edi ; mov %edi,(%rdx) ; seto %al ; ret
                  #                              ^^^ 溢出标志 → 布尔

safe_mul:         imul %esi,%edi ; mov %edi,(%rdx) ; seto %al ; ret
                  #                               ^^^ 溢出标志

9.3 常量折叠

当操作数是编译期常量时，结果在编译期确定：

test_all_overflow:

    mov    $0x1,%edx           # ← INT_MAX+1 overflow=1（编译期常量）

十、类型与对齐内建

10.1 __builtin_types_compatible_p

__builtin_types_compatible_p(type1, type2)  // 编译期返回 0 或 1

实测：

检查 返回 说明
types_compatible_p(int, int) 1 同类型
types_compatible_p(int, unsigned) 0 signed ≠ unsigned
types_compatible_p(int, long) 0 int ≠ long（LP64）

10.2 __builtin_assume_aligned

告诉编译器「p 至少 16 字节对齐」，编译器据此生成向量化指令（SSE/AVX）。

实测 sum_aligned vs sum_plain 在当前 gcc 版本下生成的代码相同（因为简单标量循环没有向量化机会）。但如果循环体适合向量化（如 s += p[i] * 2），assume_aligned 版本会使用 movdqa（对齐加载），而 plain 版本用 movdqu（未对齐加载，慢）。

10.3 __builtin_offsetof

等价于标准 <stddef.h> 的 offsetof，但 __builtin_offsetof 是编译器内建，不需要 #include。

十二、__builtin_return_address：调用链追踪

void *__builtin_return_address(unsigned int level);

返回 level 层调用者的返回地址。level=0 是当前函数的调用者，1 是调用者的调用者，以此类推。

level 返回 可靠性
0 直接调用者的返回地址 可靠
1 祖父调用者 依赖栈帧完整性
≥ 2 更深层 不可靠（可能因优化/内联导致栈帧不存在）

内核：include/linux/kallsyms.h 用 __builtin_return_address(0) 做 stack trace。dump_stack() 底层也依赖它。使用前提：函数不能被内联（否则没有独立栈帧）。

/* 内核 dump_stack 简化版 */
void dump_stack(void) {
    unsigned long sp = (unsigned long)__builtin_frame_address(0);
    void *ra = __builtin_return_address(0);
    printk("Call trace:\n");
    printk("  [<%p>] %pS\n", ra, ra);   /* %pS = 打印符号名 */
    /* 继续 unwind... */

常见陷阱

1. 以为 __builtin_popcount 一定用硬件指令

错。不加 -mpopcnt（或 -march=native），gcc 调用 __popcountdi2（13 条 SWAR 指令 + 函数调用），clang 内联 SWAR（12 条指令）。都不用 popcnt 指令。

解法：Makefile 里加 -mpopcnt 或 -march=native。

2. 在 -O0 -g 调试时宏行为变了

用了 __builtin_constant_p 的宏在 -O0 下走 else 分支（因为 __builtin_constant_p 几乎全返回 0）。

解法：知道这是预期的；要测宏行为用 -O2 -g。

3. __builtin_clz(0) / __builtin_ctz(0) 是 UB

__builtin_ffs(0) 返回 0（安全），但 clz/ctz 对 0 输入是 UB。内核先检查 v == 0。

4. __builtin_unreachable 骗了编译器

标了 __builtin_unreachable() 的路径如果真的被执行，返回值是寄存器里的垃圾。编译器还可能基于「不可达」假设做更激进的优化（删除其他分支的检查），导致更严重的 UB。

5. __builtin_expect 标错方向

likely 标在实际冷路径上，编译器把冷路径放 fall-through，hot path 变成跳转——每次都 icache miss。必须 profile。

6. -fno-builtin 不影响 __builtin_*

以为 -fno-builtin 能关掉 __builtin_strlen——不能。-fno-builtin 只关 libc 隐式识别。要关 __builtin_* 没有标准方法（也没必要——它们是编译器内建，不是库函数）。

软件函数调用（call __popcountdi2）。因为默认编译选项不包含 -mpopcnt，gcc 不知道目标 CPU 支持 POPCNT 指令，所以回退到 libgcc 的 __popcountdi2（SWAR 算法，13 条指令 + 一次函数调用）。

题目 2： 以下宏在 gcc -O0 和 gcc -O2 下行为有何不同？

#define OPT_MEMSET(s, c, n) do {                                  \
    if (__builtin_constant_p(n) && (n) <= 16)                     \
        /* 内联展开 */                                            \
    else                                                          \
        memset(s, c, n);                                         \
} while (0)
参考答案

-O0：__builtin_constant_p 几乎对所有非字面量表达式返回 0（包括 static const 和赋值后未修改的局部变量）。因此宏几乎总是走 else 分支调用 memset，即使 n 是 static const int = 5。

-O2：编译器做常量传播，能识别 static const、未修改的局部变量等为编译期常量。当 n 是编译期常量且 ≤ 16 时，走内联展开路径。

根因：__builtin_constant_p 依赖编译器的常量传播能力，-O0 不做任何优化传播。

题目 3： 以下三种方式检查溢出，哪个在 -O2 下生成的代码最优？

// A: 手写

// B: 编译器扩展

if (__builtin_add_overflow(a, b, &r)) { /* overflow */ }

// C: 内联汇编
int r, ovf;
asm("add %2, %1\n\tseto %0" : "=r"(ovf), "=r"(r) : "r"(a), "1"(b));
参考答案

B 最优。__builtin_add_overflow 生成 add; seto; ret（3 条指令），且编译器理解其语义，可以做常量折叠等优化。手写 A 需要额外比较和分支，且对无符号不适用。内联汇编 C 虽然也能用 seto，但编译器不理解 asm 的语义，不能做后续优化（如常量折叠、死代码消除），且不可移植。

实测 safe_add 的汇编：add %esi,%edi; mov %edi,(%rdx); seto %al; ret——干净利落。

题目 4： __builtin_unreachable() 标注的路径如果真的被执行了，会发生什么？

int f(int x) {
    if (x > 0) return x;
    __builtin_unreachable();  // "x 永远 > 0"
}
// 调用：f(-5)
参考答案

6.11

.6 Linux内核中的likely和unlikely

本节讲什么

内核 likely/unlikely 包装 __builtin_expect，给分支预测器编译期提示：标记某分支"大概率/小概率"走，编译器据此重排代码——把 unlikely 错误路径移到函数末尾，保持 hot path 在 cache 内连续。本节讲原理、用法、误用代价。

要点

__builtin_expect 原理

long __builtin_expect(long exp, long c);

返回 exp 本身（运行时无副作用），但告诉编译器"运行时 exp == c 的概率高"。编译器据此： 1. 重排基本块——把"非 c 分支"移到远处（函数末尾或冷段）。 2. 优化指令 cache 局部性——hot path 连续。 3. 影响条件移动 vs 分支跳转指令选择。

内核 / DPDK 包装

/* include/linux/compiler.h */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

/* DPDK — rte_branch_prediction.h */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

!!(x) 把任意表达式归一化为 0/1，避免 __builtin_expect 第二参数被误用。

典型用法

/* 错误路径标 unlikely */
if (unlikely(!ptr))
    return -EINVAL;

if (unlikely(ptr->magic != MAGIC))
    goto corrupt;

/* 成功路径标 likely */
if (likely(nb_rx > 0)) {
    /* burst 处理收到的包 */
}

编译器生成的代码差异

int f(int *p) {
    if (unlikely(!p)) return -1;
    return *p;
}

编译后（ARM64 概览）：

cbz   x0, .Lerror      /* 错误路径跳远 */
ldr   w0, [x0]
ret
.Lerror:
mov   w0, #-1
ret

hot path（ldr/ret）连续在前面，.Lerror 在末尾——icache 友好。不标 unlikely 时编译器也可能猜（基于 profile 或静态启发式），但不可靠；显式 unlikely 强制。

使用条件

  • profile 验证后再加——猜错会降低性能。
  • 仅在热路径上有意义——冷函数加 likely 无用。
  • __builtin_expect 不影响正确性，只影响性能。
用法 说明
错误检查 if (unlikely(!ptr)) 错误路径移出 hot path
快速路径 if (likely(ret == 0)) 保持成功路径连续
switch 优化 标 unlikely case 移到末尾
DPDK 收包 if (likely(nb_rx > 0)) 数据面热路径
  • 不要在用户态盲目复制：profile 为准
  • GCC -fprofile-generate/-fprofile-use（PGO）可自动生成类似信息

常见陷阱

  1. 猜错方向 → 性能反而下降 unlikely(x) 标在实际大概率分支上，编译器把该分支移到冷区，每次跳转都破坏 icache。代价：5-20% 性能损失（视分支频率）。必须用 profile（perf record / gcov）确认概率再加，否则别加。某分支 50/50 时不要标——__builtin_expect 只在明显偏斜时有用。

  2. likely(unlikely(...)) 嵌套无意义 __builtin_expect 是编译期提示，嵌套调用最后只保留最外层。更隐蔽的是 if (likely(a) && unlikely(b))——编译器对复合条件分支预测有独立逻辑，likely/unlikely 标注会被部分忽略。惯例：每个 if 标注一个 likely 或 unlikely，作用于整体条件。

  3. 误以为 likely 改变语义 if (likely(p != NULL)) 与 if (p != NULL) 在语义上完全等价——likely 只影响代码生成，不影响判断结果。新手误以为 likely "强制走某分支"是错的：运行时若 p == NULL，仍进入 NULL 分支。__builtin_expect 返回值等于第一参数，无运行时副作用。

自测题

1.（选择） __builtin_expect(exp, c) 的运行时行为是？ - A. 强制 exp == c - B. 返回 exp，给编译器分支预测提示 - C. 调用硬件分支预测器 - D. 改变条件判断结果

答案

2.（判断） 在所有 if 上加 likely 或 unlikely 是优化代码的好习惯。

答案

错。likely/unlikely 只在分支明显偏斜且位于热路径时有用。盲目标注： - 50/50 分支无益（编译器本就难猜）； - 猜错方向反而降低性能（icache 失效）； - 冷代码标注无意义（不在热路径，重排没意义）。 正确做法：先用 perf record / gcov 找出热路径上的偏斜分支，再针对性标注。或直接用 PGO（-fprofile-use）让编译器自动生成。

3.（踩坑） DPDK 收包循环：

uint16_t n = rte_eth_rx_burst(port, q, bufs, BURST);
if (likely(n == 0)) continue;     /* 标 likely */
process(bufs, n);

性能比不加 likely 还差。为什么？

答案

方向标反了。rte_eth_rx_burst 在收包路径上通常有包（否则轮询浪费），n > 0 是大概率事件。标 likely(n == 0) 等于告诉编译器"通常没包"，把 continue（hot path）排到前面，但实际运行时 n == 0 为假，跳到 process——每次都跳转，icache 失效。正确：

if (unlikely(n == 0)) continue;  /* 空轮询是少数 */
process(bufs, n);

教训：likely/unlikely 必须 profile 验证。DPDK 的 rte_branch_prediction.h 文档明确说"仅用于已 profile 的热路径"。

4.（应用） 给定函数：

int parse(const char *s) {
    if (s == NULL) return -EINVAL;
    if (*s == '\0') return -EINVAL;
    /* 解析... */
    return 0;
}

用 likely/unlikely 优化，并说明预期收益。

答案 
int parse(const char *s) {
    if (unlikely(s == NULL))    return -EINVAL;
    if (unlikely(*s == '\0'))   return -EINVAL;
    /* 解析 hot path... */
    return 0;
}

预期收益： 1. 两个错误检查标 unlikely，编译器把错误处理移到函数末尾，hot path（解析逻辑）连续在前面——icache 友好。 2. 错误路径不占 cache（除非真触发），减少 cache footprint。 3. 前提：调用方通常传合法字符串——这是 parse 这类 API 的典型契约。若 profile 显示 50% 调用传 NULL，标注反方向。 注意：在非热函数上标注收益微小——parse 若每秒被调用百万次才有意义，偶尔调用一次无差别。
