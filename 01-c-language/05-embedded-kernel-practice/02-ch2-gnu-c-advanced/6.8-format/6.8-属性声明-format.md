## 本节讲什么

前面 6.3–6.7 的属性（`typeof`、语句表达式、柔性数组、`aligned`/`packed`）都作用于**编译期可见的类型与布局**。`format` 是第一个**让编译器去读一个字符串**的属性——它把「格式串」从「运行时的黑盒数据」变成「编译器能静态解析的微型程序」。

一句话概括：

> **`format` 属性告诉编译器：第 N 个参数是一段按 printf/scanf 规则书写的代码，请照着它检查后面的实参。**

它的价值不在"少写几行"，而在**把一类必崩的运行期错误搬到编译期**：

```c
log_err("order %d rejected: %s\n", reason_str, order_id);
/*              ^^^^                 ^^^^^^^^^^^  char* 喂给 %d */
```

没有 `format` 属性，这行代码编译通过、上线崩溃（x86-64 上 `%d` 读的是 `esi`，而传进去的是指针低 32 位，打印出一串垃圾；在 varargs 的 ABI 下更糟——`va_arg` 的取值位置会整体错位，后面的 `%s` 直接段错误）。

加了属性，它是这样：

```
warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’
```

而本节要钉死的，是**书里没讲、但工程上天天踩**的六件事：

1. `first-to-check = 0` 才是 `va_list` 版本的正确写法，写成 2 在 gcc 下是**硬错误**；
2. **gcc 和 clang 支持的 archetype 完全不是同一套**，内核为此只用 `printf` 不用 `gnu_printf`；
3. `-Wformat` 家族里有一半是**默认不开**的；
4. 属性写错位置，gcc 报 error 而 clang 只报 warning；
5. 内核的 `%pK`/`%pI4` 这类扩展格式符，**两个编译器都不检查**；
6. `no_printk` 那个 `if (0)` 技巧能同时拿到**格式检查**和**零开销**——这是日志系统设计的分水岭。

## 一、三个参数到底在说什么

```c
__attribute__((format(archetype, string-index, first-to-check)))
```

| 参数 | 含义 | 常见误解 |
|------|------|----------|
| `archetype` | 按哪套格式规则检查 | 以为只有 `printf`；以为 `gnu_printf` 到处都能用（见第三节） |
| `string-index` | 格式串是**第几个参数**（**从 1 开始**） | 按 C 习惯从 0 数 |
| `first-to-check` | 第一个**待检查的可变参**是第几个；**0 = 本函数收的是 `va_list`** | 以为 0 表示"不检查" |

先跑一遍基本盘（`-Wall -Wformat=2`）：

```c
/* t1_basic.c */
void log_ok (const char *fmt, ...) __attribute__((format(printf, 1, 2)));
void log_bad(const char *fmt, ...);                              /* 故意不加 */
void log_lvl(int level, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));                       /* 固定前缀 */

log_ok ("%d %s\n", "hello", 42);   /* A */
log_bad("%d %s\n", "hello", 42);   /* B */
log_ok ("%d\n");                   /* C  缺参 */
log_ok ("%d %d\n", 1);             /* D  缺参 */
log_ok ("%d\n", 1, 2);             /* E  多参 */
log_ok ("%Q\n", 1);                /* F  非法转换 */
log_lvl(3, "%s\n", 42);            /* G  索引 2/3 生效 */
```

```
$ gcc -std=gnu11 -Wall -Wformat=2 -c t1_basic.c
t1_basic.c:28: warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’
t1_basic.c:28: warning: format ‘%s’ expects argument of type ‘char *’, but argument 3 has type ‘int’
t1_basic.c:30: warning: format ‘%d’ expects a matching ‘int’ argument
t1_basic.c:31: warning: format ‘%d’ expects a matching ‘int’ argument
t1_basic.c:32: warning: too many arguments for format            [-Wformat-extra-args]
t1_basic.c:33: warning: unknown conversion type character ‘Q’ in format
t1_basic.c:34: warning: format ‘%s’ expects argument of type ‘char *’, but argument 3 has type ‘int’
```

**B 行一声不响**——这就是"加不加属性"的全部区别。gcc 与 clang 的措辞对照：

| 情形 | gcc 13.3 | clang 18 |
|------|----------|----------|
| 类型不匹配 | `format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’` | `format specifies type 'int' but the argument has type 'char *'` |
| 缺参 | `format ‘%d’ expects a matching ‘int’ argument` | `more '%' conversions than data arguments [-Wformat-insufficient-args]` |
| 多参 | `too many arguments for format [-Wformat-extra-args]` | `data argument not used by format string` |
| 非法转换符 | `unknown conversion type character ‘Q’ in format` | `invalid conversion specifier 'Q'` |

clang 多报一条 gcc 没有的：包装函数体内 `vprintf(fmt, ap)` 会触发 `-Wformat-nonliteral`（`fmt` 不是字面量）。**这是 clang 的噪音**，抑制方式是在包装函数里改用 `#pragma` 局部关闭，或给内部实现另起一个不带属性的函数。

## 二、`first-to-check = 0`：va_list 版本才是重点

这是本节**最容易被忽略、也最容易写错**的地方。

任何一个成熟的日志层都有两个函数：

```c
void  logf (const char *fmt, ...);        /* 对外：收 ...      */
void vlogf (const char *fmt, va_list ap); /* 对内：收 va_list  */
```

`vlogf` 的属性该怎么写？**`first-to-check` 必须是 0**——因为它没有可变参，参数已经打包进 `va_list` 了。写成 2 会怎样：

```c
void vlog_wrong(const char *fmt, va_list ap) __attribute__((format(printf, 1, 2)));
```

```
$ gcc -std=gnu11 -Wall -Wformat=2 -c t2_valist.c
t2_valist.c:10: error: ‘format’ attribute argument 3 value ‘2’ does not refer to a variable argument list

$ clang -std=gnu11 -Wall -Wformat=2 -c t2_valist.c
t2_valist.c:10: warning: GCC requires a function with the 'format' attribute to be variadic [-Wgcc-compat]
```

> **gcc 是硬错误，clang 只是 warning。** 同一份代码在 gcc 下直接编译失败，在 clang 下带着警告继续过——**CI 只跑 clang 就会漏掉这个 bug**。

内核 v6.6 就是这么写的（`include/linux/printk.h`）：

```c
extern asmlinkage __printf(1, 2)
int vprintk_emit(int facility, int level, const char *dict, const char *fmt, va_list args);  /* 实际是 __printf(4, 0) */
asmlinkage __printf(1, 2) __cold
int printk(const char *fmt, ...);

asmlinkage __printf(1, 0)
int vprintk(const char *fmt, va_list args);      /* <- 0：收 va_list */
```

注意 `vprintk_emit` 是 `__printf(4, 0)`（第 144–145 行）：格式串排第 4（`facility`/`level`/`dict` 在前），`0` 表示后面跟的是 `va_list`。

**速记**：函数签名里有 `...` → 写第一个可变参的下标；签名里是 `va_list` → 写 `0`。

## 三、archetype：gcc 与 clang 根本不是同一套

书里会列一张"printf / scanf / strftime / strfmon"的表，但**实测支持矩阵完全不同**。逐个探测：

```c
void a1(...) __attribute__((format(printf, 1, 2)));
void a2(...) __attribute__((format(gnu_printf, 1, 2)));
void a3(...) __attribute__((format(scanf, 1, 2)));
void a4(...) __attribute__((format(gnu_scanf, 1, 2)));
void a5(...) __attribute__((format(strftime, 3, 0)));
void a6(...) __attribute__((format(strfmon, 1, 2)));
void a7(...) __attribute__((format(ms_printf, 1, 2)));
void a8(...) __attribute__((format(syslog, 1, 2)));
```

| archetype | gcc 13.3 (Linux) | clang 18 |
|-----------|------------------|----------|
| `printf` | ✅ | ✅ |
| `scanf` | ✅ | ✅ |
| `strftime` | ✅（要求 `first-to-check = 0`） | ✅ |
| `strfmon` | ✅ | ✅ |
| `gnu_printf` | ✅ | ❌ `'format' attribute argument not supported` |
| `gnu_scanf` | ✅ | ❌ 同上 |
| `ms_printf` | ❌ `unrecognized format function type` | ❌ not supported |
| `syslog` | ❌ `unrecognized format function type` | ❌ not supported |

```
$ gcc   ... → warning: ‘ms_printf’ is an unrecognized format function type [-Wformat=]
           → warning: ‘syslog’    is an unrecognized format function type [-Wformat=]
$ clang ... → warning: 'format' attribute argument not supported: gnu_printf [-Wignored-attributes]
           → warning: 'format' attribute argument not supported: gnu_scanf  [-Wignored-attributes]
```

**两个编译器正好互补地各缺一半。** 而且失败方式不同：

- gcc 对不认识的 archetype 报 **warning** 然后**忽略该属性**（静默失去检查）；
- clang 同样报 `-Wignored-attributes` 后**忽略**。

于是引出一个关键问题：内核同时要被 gcc 和 clang 编译，它用哪个？

v6.6 `include/linux/compiler_attributes.h:171`：

```c
#define __printf(a, b)   __attribute__((__format__(printf, a, b)))
#define __scanf(a, b)    __attribute__((__format__(scanf, a, b)))
```

**是 `printf`，不是 `gnu_printf`。** 因为 clang 不认后者——内核为了 clang 可编译，主动放弃了 `gnu_printf` 的额外检查能力。

> **实践结论**：跨编译器项目**只能用 `printf` / `scanf` / `strftime` / `strfmon` 这四个**。想用 `gnu_printf` 换更严的检查，必须确认工具链只有 gcc。

顺带一个反直觉的实测：**archetype 的检查规则与 `-std=` 方言无关**。

```
$ for std in c89 c99 c11 c17 gnu89 gnu11 gnu17; do gcc -std=$std -Wall -Wformat=2 -c t7_dialect.c; done
（全部 7 次：0 warning，包括 glibc 扩展 %m 与 GNU 千分位 %'d）
```

`printf` archetype 永远按 glibc/GNU 规则检查，不管你写 `-std=c99` 还是 `-std=gnu11`。这与 6.1 讲的"`-std=cXX` 会关掉裸 `typeof`/`asm`"是两回事——**方言管关键字，不管格式串检查**。

## 四、`-Wformat` 家族：哪些默认开

`-Wformat`(在 `-Wall` 里) 只是基础档，实用的一半要靠显式打开。实测逐个确认：

```c
/* t4_woptions.c */
logf(s, 1);                  /* A: 格式串是变量            */
printf("%d\n");              /* B: 缺参                    */
printf("");                  /* C: 空格式串                */
printf("%d\n", u);           /* D: unsigned 喂给 %d        */
printf("%n\n", &n);          /* E: %n                      */
snprintf(small, 8, "%s\n", "a very long string here");  /* F: 截断 */
sprintf (small,    "%s\n", "a very long string here");  /* G: 溢出 */
```

```
$ gcc -std=gnu11 -Wall -Wformat=2 -Wformat-signedness -Wformat-truncation -Wformat-overflow -O2 -c t4_woptions.c
A: warning: format not a string literal, argument types not checked        [-Wformat-nonliteral]
B: warning: format ‘%d’ expects a matching ‘int’ argument                 [-Wformat=]
C: warning: zero-length gnu_printf format string                          [-Wformat-zero-length]
D: warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘unsigned int’
F: warning: ‘%s’ directive output truncated writing 23 bytes into a region of size 8
                                                                          [-Wformat-truncation=]
G: warning: ‘%s’ directive writing 23 bytes into a region of size 8       [-Wformat-overflow=]
E: （无警告 —— 见第八节）
```

| 选项 | 作用 | 默认 | 备注 |
|------|------|------|------|
| `-Wformat` | 基础匹配检查 | ✅（`-Wall`） | |
| `-Wformat-extra-args` | 参数多于转换符 | ✅ | |
| `-Wformat-nonliteral` | 格式串非字面量 | ❌（`-Wformat=2` 才开） | 表驱动/国际化代码会刷屏 |
| `-Wformat-security` | 格式串非字面量**且无参数** | ❌ | **真·安全漏洞**，务必开 |
| `-Wformat-zero-length` | 空格式串 | ✅ | |
| `-Wformat-signedness` | `%d` 收 `unsigned` | ❌ | **clang 不认此选项** |
| `-Wformat-truncation` | `snprintf` 截断 | `-O1+` 隐式 | 需优化才生效 |
| `-Wformat-overflow` | `sprintf` 溢出 | `-O1+` 隐式 | 需优化才生效 |
| `-Wformat-y2k` | `%y` 两位数年份 | ❌（`-Wformat=2` 才开） | |

两个要点：

1. **`-Wformat-truncation` / `-Wformat-overflow` 依赖优化**：`-O0` 下 gcc 看不到目标缓冲区长度，不会报。**CI 里用 `-O0` 跑 warning 检查等于没做。**
2. **clang 不认 `-Wformat-signedness`**：`warning: unknown warning option '-Wformat-signedness'`。跨平台构建脚本里要按编译器分流（`-Wno-unknown-warning-option` 也压不住这条诊断本身的刷屏）。

## 五、属性写在哪儿才生效（六个场景实测）

```c
/* A */ void a_decl(...) __attribute__((format(printf,1,2)));  void a_decl(...) {}       /* 声明上 */
/* B */ void b_def (...) __attribute__((format(printf,1,2)));  void b_def (...) {}       /* 定义前（同上，实为声明） */
/* C */ void c_two (...) __attribute__((format(printf,1,2)));  void c_two (...);         /* 二次声明不带属性 */
        void c_two (...) {}
/* D */ void d_defonly(...) __attribute__((format(printf,1,2))) { }                      /* 写在定义体前 */
/* E */ #define LOG(fmt,...) a_decl(fmt, ##__VA_ARGS__)                                  /* 宏包装 */
/* F */ void (*fp)(const char*, ...) __attribute__((format(printf,1,2))); fp("%d\n","z");/* 函数指针 */
```

| 场景 | gcc | clang | 结论 |
|------|-----|-------|------|
| A 前置声明带属性 | ✅ 检查 | ✅ | **推荐写法** |
| B 定义（带独立声明） | ✅ | ✅ | 同 A |
| C 二次声明丢掉属性 | ✅ **仍检查** | ✅ | 属性在多次声明间**累积保留** |
| D 属性写在定义体前 | ❌ **error**：`attributes should be specified before the declarator in a function definition` | ⚠️ warning `-Wgcc-compat` 后接受 | **gcc 硬失败、clang 放行** |
| E 宏包装 | ✅ | ✅ | 宏展开后就是普通调用 |
| F **函数指针**带属性 | ✅ | ✅ | 多数人不知道这个能用 |

D 是实战中最常踩的：图省事把属性跟着函数体一起写，gcc 直接编译失败而 clang 过，于是"本地能编、CI 挂了"。

F 很有用——**回调表里的日志钩子也能检查**：

```c
struct log_ops {
    void (*info)(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
    void (*err )(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
};
```

以及一条反面实测：**属性不能写进宏**。

```c
#define attr_log(fmt, ...) __attribute__((format(printf,1,2))) real_log(fmt, ##__VA_ARGS__)
attr_log("%d\n", "z");
```

```
gcc:  error: expected declaration specifiers or ‘...’ before string constant
clang: error: expected identifier or '('
```

属性是**声明说明符**的一部分，必须附着在声明上；宏展开到语句位置就成了语法错误。

## 六、内核扩展格式符 `%pK` / `%pI4` / `%pS` 的真相

内核 `printk` 支持一大票标准 printf 没有的转换：`%pK`（哈希指针）、`%pI4`（IPv4）、`%pS`（符号名）、`%ptT`（时间戳）……它们由 `lib/vsprintf.c` 自己解析。那 `-Wformat` 会不会因它们误报？

```c
void kprintf    (const char *fmt, ...) __attribute__((format(printf, 1, 2)));
void kprintf_gnu(const char *fmt, ...) __attribute__((format(gnu_printf, 1, 2)));

kprintf    ("%pK\n", p);   /* A */
kprintf_gnu("%pK\n", p);   /* B */
kprintf    ("%pI4\n", p);  /* C */
kprintf    ("%pS\n", p);   /* D */
```

```
$ gcc -std=gnu11 -Wall -Wformat=2 -c t7_kernel.c
（0 warning —— 完全静默）
$ clang ...
（只有一条 gnu_printf not supported，格式串本身无诊断）
```

**两个编译器都不报。** 原因是 `%p` 本身就是一个完整的转换说明符，编译器解析完 `p` 就结束了，**后面的 `K`/`I`/`S` 被当成普通字符**。

这是把双刃剑：

- ✅ **好处**：内核代码不会因为扩展格式符被 `-Wformat` 刷屏，所以内核才敢用 `printf` 而不是自己造 archetype；
- ❌ **坏处**：`%pZ` 这种**拼错的**扩展符也一样静默通过——编译器不会帮你抓。

内核对此的补偿是构建期的 `scripts/checkpatch.pl` 与运行时的 `vsprintf` 探测，不在编译器这边。

## 七、`no_printk`：把「检查」和「零开销」同时拿下

关掉调试日志时，有人这么写：

```c
#define pr_debug(fmt, ...) do { } while (0)     /* 干净，但格式串错误从此没人管 */
```

代码是没了，**格式检查也没了**。内核 v6.6 `printk.h:126` 的写法是：

```c
#define no_printk(fmt, ...)             \
({                                      \
        if (0)                          \
                printk(fmt, ##__VA_ARGS__); \
        0;                              \
})
```

`if (0)` 里的代码永远不执行、不生成指令，但**编译器仍然会做语义分析和格式检查**。实测（`-O2`）：

```c
int  real_log(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
#define no_log(fmt, ...) ({ if (0) real_log(fmt, ##__VA_ARGS__); 0; })

int main(void) { no_log("%d\n", "x"); return 0; }
```

```
$ gcc -std=gnu11 -Wall -Wformat=2 -O2 -c t8_noprintk.c
warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’   <- 检查还在

$ objdump -d t8.o
0000000000000000 <main>:
   0:   f3 0f 1e fa     endbr64
   4:   31 c0           xor    %eax,%eax        <- 直接 return 0
   6:   c3              ret

$ objdump -s -j .rodata t8.o     -> （空：字符串 "%d\n" 与 "x" 都没进二进制）
$ nm -u t8.o                     -> （空：没有引用任何外部符号）
```

**三条证据**：

1. **警告还在** —— 检查发生在语义分析阶段，早于优化；
2. **`main` 只剩 3 条指令** —— 调用被完全消除；
3. **`.rodata` 为空、无未定义符号** —— 连格式字符串都没留下。

再看一个更狠的：参数里的**副作用**还执行吗？

```c
int side(void) { return ++counter; }
no_log("%d\n", side());                       /* 编译期死 */
if (g_level) real_log("%d\n", side());        /* 运行时门 */
```

```
$ gcc -std=gnu11 -O2 -c t9_sideeffect.c && objdump -d t9.o
   0:   mov  0x0(%rip),%eax        # 读 g_level
   a:   test %eax,%eax
   c:   je   15 <main+0x15>
   e:   addl $0x1,0x0(%rip)        # side() 被内联：counter++
  15:   xor  %eax,%eax
  17:   ret
```

`no_log` 那一行**连 `side()` 的调用都不存在**；运行时门那行则保留了 `counter++`（此处 gcc 把 `side()` 内联了）。

> **结论**：编译期关闭的日志，**参数不求值**；运行时判断的日志，**参数一定求值**。
> 所以 `LOG_DEBUG("price=%f", compute_expensive_thing())` 这种写法——只有编译期门才是真免费；运行时门照样把 `compute_expensive_thing()` 算完，只是不打印。**这是 HFT 里最常见的"关了日志还是慢"的根因。**

---

## 八、`%n` 与 `-Wformat-security`：编译器其实不管

`%n` 会把已输出字节数写进指针参数，是典型的格式化串攻击跳板。但实测：

```c
printf(argv[0]);        /* A: 非常量格式串、无参数  */
printf(argv[0], 1);     /* B: 非常量格式串、有参数  */
printf("%n\n", &n);     /* C: 常量格式串里的 %n     */
```

```
$ gcc -std=gnu11 -Wall -Wformat=2 [-D_FORTIFY_SOURCE=2 -O2] -c t7_security.c
A: warning: format not a string literal and no format arguments   [-Wformat-security]
B: warning: format not a string literal, argument types not checked [-Wformat-nonliteral]
C: （无警告 —— 两个编译器、加不加 _FORTIFY_SOURCE 都没有）
```

- **`-Wformat-security` 只在"格式串非常量 且 没有参数"时触发**；一旦带了参数，它降级成普通的 `-Wformat-nonliteral`。
- **字面量里的 `%n`，gcc 和 clang 都不报警**，`_FORTIFY_SOURCE=2` 也不管（glibc 的 fortify 检查的是缓冲区长度，不是 `%n`）。

所以 `%n` 只能靠**代码审计 / 禁用策略**挡住（内核的 `checkpatch.pl` 会提示；很多项目直接 `-Werror=format-security` + 禁止 `%n`）。

---

## 九、HFT 视角：日志的四级成本

把上面的实测叠起来，一条日志的成本可以分成四级，**每一级都需要不同的手段才能消掉**：

| 级别 | 成本 | 消除手段 | 实测证据 |
|------|------|----------|----------|
| L1 **调用点** | 一次 call + 参数装寄存器 | 编译期常量门 `if (LEVEL <= MAX)` | T6：`main` 里只剩运行时门的那一个 call |
| L2 **参数求值** | `side()` / `compute_x()` | **只有编译期门**（或把昂贵表达式移出参数） | T9：`no_log` 的 `side()` 消失，运行时门保留 |
| L3 **字符串与格式化** | `vsnprintf` 遍历格式串 | 编译期门（字符串进不了 `.rodata`） | T8：`.rodata` 为空 |
| L4 **函数体** | 日志函数自身的 `.text` | `static` + 无引用（让链接器丢弃） | T6：`log_at` 是外部链接，函数体仍在 |

**要点：L1–L3 靠编译期门一次全消，L4 需要 static 或链接期 GC。**

一个可直接用的模板（综合本节所有结论）：

```c
/* log.h —— 纯 ASCII，跨 gcc/clang */
#ifndef MAX_LOG_LEVEL
#define MAX_LOG_LEVEL 2          /* 0:ERR 1:WARN 2:INFO 3:DEBUG */
#endif

enum { L_ERR = 0, L_WARN, L_INFO, L_DEBUG };

void log_emit(int level, const char *fmt, ...)
    __attribute__((format(printf, 2, 3)));        /* 对外：... 版本 */
void log_vemit(int level, const char *fmt, va_list ap)
    __attribute__((format(printf, 2, 0)));        /* 对内：va_list，0! */

/* 编译期门：LEVEL 是常量，整段（含参数求值）消失 */
#define LOG_AT(level, fmt, ...)                                  \
    do {                                                         \
        if ((level) <= MAX_LOG_LEVEL)                            \
            log_emit(level, fmt, ##__VA_ARGS__);                 \
    } while (0)

/* 关掉时仍保留格式检查：no_printk 同款 */
#define LOG_OFF(level, fmt, ...)                                 \
    ({                                                           \
        if (0)                                                   \
            log_emit(level, fmt, ##__VA_ARGS__);                 \
        0;                                                       \
    })
```

`##__VA_ARGS__` 是 GNU 扩展，零参时吃掉前导逗号（详见 6.12）；C++20/C23 可用标准的 `__VA_OPT__`。

## 十、误区表

| # | 误区 | 实测事实 |
|---|------|----------|
| 1 | "`format` 属性加上就一定检查" | archetype 不被支持时**静默失效**，只有一个 `-Wignored-attributes` / `unrecognized` 警告 |
| 2 | "`gnu_printf` 比 `printf` 好，随时可用" | clang 完全不支持；内核 v6.6 因此只用 `printf` |
| 3 | "va_list 版本写 `format(printf, 1, 2)`" | gcc **硬错误**；必须写 `0` |
| 4 | "属性写在函数定义前就行" | gcc 报 error（`before the declarator`），clang 只警告 |
| 5 | "第二次声明不带属性就会丢" | 属性**累积保留**，仍然检查 |
| 6 | "`-Wall` 就够了" | `-Wformat-nonliteral`/`-security`/`-signedness` 都要显式加；`-truncation`/`-overflow` 还要 `-O1+` |
| 7 | "`%n` 会被编译器拦下" | 字面量里的 `%n` gcc/clang 都不报 |
| 8 | "`%pK` 会让 `-Wformat` 报错" | 不会——`%p` 后面的字符编译器不解析，**拼错也不报** |
| 9 | "关掉日志参数就不会算了" | 只有**编译期**门才不求值；运行时门照样算 |
| 10 | "`-std=c99` 下格式检查会变严" | 不会，format 检查与 `-std=` 方言无关 |

## 十一、速查：什么时候该加 format 属性

```
你的函数签名里有 const char *fmt 吗？
├── 有，且后面跟 ...        -> format(printf, fmt下标, 第一个可变参下标)
├── 有，且后面跟 va_list    -> format(printf, fmt下标, 0)
├── 是 scanf 风格           -> format(scanf,  同上)
├── 是 strftime 风格        -> format(strftime, fmt下标, 0)   <- 必须为 0
└── 格式串是运行时拼接的    -> 加也没用（会刷 -Wformat-nonliteral），
                               改为在入口处做一次显式校验
```

配套开关建议（Makefile）：

```make
# 开发期
CFLAGS += -Wall -Wextra -Wformat=2 -Wformat-signedness -Werror=format-security
# 发布期（-truncation/-overflow 需要优化）
CFLAGS += -O2 -Wall -Wformat=2 -Wformat-truncation -Wformat-overflow
```

## 代码自测

**题目 1：** 下面两个声明，哪个在 gcc 下会编译失败？为什么？

```c
void va1(const char *fmt, va_list ap) __attribute__((format(printf, 1, 0)));
void va2(const char *fmt, va_list ap) __attribute__((format(printf, 1, 2)));
```

<details>
<summary>参考答案</summary>

`va2` 在 gcc 下**硬失败**：

```
error: ‘format’ attribute argument 3 value ‘2’ does not refer to a variable argument list
```

`first-to-check` 为 0 表示"本函数接收的是 `va_list`，没有可变参需要检查"。`va2` 明明收 `va_list`，却声明第 2 个参数起是可变参 → gcc 直接报错。

clang 只给 `-Wgcc-compat` 警告并继续编译 —— **这正是"本地 clang 通过、CI gcc 挂掉"的典型来源**。

内核 v6.6 的正确写法：`asmlinkage __printf(1, 0) int vprintk(const char *fmt, va_list args);`

</details>

**题目 2：** 团队要求"debug 日志在 release 构建里零开销，但格式串写错仍要在编译期发现"。下面两种写法哪种满足？

```c
/* 方案 A */
#if DEBUG
#define DBG(fmt, ...) real_log(fmt, ##__VA_ARGS__)
#else
#define DBG(fmt, ...) do { } while (0)
#endif

/* 方案 B */
#if DEBUG
#define DBG(fmt, ...) real_log(fmt, ##__VA_ARGS__)
#else
#define DBG(fmt, ...) ({ if (0) real_log(fmt, ##__VA_ARGS__); 0; })
#endif
```

<details>
<summary>参考答案</summary>

**只有 B 满足**，A 不满足。

- A：release 下 `DBG("%d\n", "str")` 完全不展开成任何调用，**格式检查也一起没了**。开发期在 `#if DEBUG` 下没暴露的错误，release 构建里悄悄潜伏。
- B：`if (0)` 分支在**语义分析阶段**就要做类型与格式检查（会报 `-Wformat`），但**优化阶段**整段被消除。

实测证据（gcc 13.3 `-O2`）：

```
warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘char *’   <- 检查在

objdump -d:  main 只剩 endbr64 / xor eax,eax / ret                                      <- 代码没了
objdump -s -j .rodata:  (空)                                                            <- 字符串也没了
nm -u:       (空)                                                                       <- 无外部引用
```

这就是内核 v6.6 `no_printk` 的做法（`printk.h:126`）。

**额外提醒**：B 还有一个 A 没有的好处——**参数不求值**。`DBG("x=%d", expensive())` 在 B 里 `expensive()` 不会被调用，在"运行时 if 判断"的写法里则一定会调用。

</details>

**题目 3：** 一份代码要同时用 gcc 和 clang 编译，下列哪些 archetype 可以安全使用？

```c
__attribute__((format(printf, 1, 2)))
__attribute__((format(gnu_printf, 1, 2)))
__attribute__((format(scanf, 1, 2)))
__attribute__((format(ms_printf, 1, 2)))
__attribute__((format(strftime, 1, 0)))
__attribute__((format(syslog, 1, 2)))
```

<details>
<summary>参考答案</summary>

安全的只有 **`printf`、`scanf`、`strftime`**（`strfmon` 也可）。

| archetype | gcc 13.3 | clang 18 |
|-----------|----------|----------|
| `printf` | ✅ | ✅ |
| `scanf` | ✅ | ✅ |
| `strftime` | ✅ | ✅ |
| `strfmon` | ✅ | ✅ |
| `gnu_printf` | ✅ | ❌ not supported |
| `gnu_scanf` | ✅ | ❌ not supported |
| `ms_printf` | ❌ unrecognized | ❌ not supported |
| `syslog` | ❌ unrecognized | ❌ not supported |

两个编译器**各缺一半，且缺失的部分不重叠**。失败时都只给 warning 然后**静默忽略属性**——所以你以为有检查，其实没有。

内核 v6.6 `compiler_attributes.h:171` 因此定义 `#define __printf(a,b) __attribute__((__format__(printf, a, b)))`，用的是 `printf` 而不是检查更严的 `gnu_printf`——为了让 clang 也能编译内核。

</details>

**题目 4：** 为什么这段内核代码在 gcc 下没有任何 `-Wformat` 警告？

```c
printk("%pK %pI4 %pZ\n", ptr, addr, sym);   /* %pZ 是拼错的（内核没有这个） */
```

<details>
<summary>参考答案</summary>

因为编译器解析到 `%p` 就认为**转换说明符已经结束**了，后面的 `K`/`I4`/`Z` 被当成普通字符直接输出。

实测（gcc 13.3 与 clang 18，`-Wall -Wformat=2`）：`%pK`、`%pI4`、`%pS` 全部 0 警告。

这是**好处也是坏处**：

- 好处：内核那几十个扩展格式符（`%pK` 哈希指针、`%pI4` IPv4、`%pS` 符号名……）不会被 `-Wformat` 刷屏，内核才敢用标准 `printf` archetype；
- 坏处：**拼错的 `%pZ` 也一样静默通过**。编译器在这里帮不上忙，只能靠 code review 或 `checkpatch.pl`。

</details>
