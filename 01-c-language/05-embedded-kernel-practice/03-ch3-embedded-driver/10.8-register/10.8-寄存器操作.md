## 本节讲什么

嵌入式 C 与通用 C 的分水岭只有一句话：**你的程序里有一块内存不是内存**——它是设备的寄存器。写它会产生副作用，读它会返回变化的值，编译器对此一无所知。

于是 C 语言需要回答四个问题：

| 问题 | C 侧的答案 | 本节 |
|---|---|---|
| 怎么告诉编译器"这个地址会自己变"？ | `volatile` | [一](#一volatile唯一必须加的地方与三个它管不了的误解) |
| 怎么阻止编译器重排我的读写顺序？ | `barrier()` = `__asm__ __volatile__("" ::: "memory")` | [二](#二编译器屏障-barrier) |
| 怎么安全地改寄存器里的某几位？ | `BIT()` / `GENMASK()` / `FIELD_PREP()` | [四](#四位操作bit--genmask--field_prep--field_get) |
| 字节序、对齐不对怎么办？ | `__builtin_bswap*`、`get_unaligned()` | [六](#六未对齐访问packed-的三个真相) · [七](#七字节序builtin_bswap-与主机序探测) |

## 一、volatile：唯一必须加的地方，与三个它管不了的误解

### 1.1 硬件寄存器的三种 C 表达

```c
/* 写法一：宏，直接把地址强转成 volatile 指针后解引用（最常见） */
#define UART_BASE   0x40001000UL
#define UART_SR     (*(volatile uint32_t *)(UART_BASE + 0x00))
#define UART_DR     (*(volatile uint32_t *)(UART_BASE + 0x04))

/* 写法二：结构体映射（寄存器成组时更清爽） */
struct __attribute__((packed)) uart_regs {
    volatile uint32_t sr;      /* +0x00 */
    volatile uint32_t dr;      /* +0x04 */
    volatile uint32_t brr;     /* +0x08 */
    volatile uint32_t cr;      /* +0x0C */
};
#define UART ((struct uart_regs *)UART_BASE)

/* 写法三：内核风格 readl/writel（把 volatile + 屏障 + 字节序打包） */
static inline uint32_t readl(const volatile void *addr)
{
    uint32_t v = *(const volatile uint32_t *)addr;
    __asm__ __volatile__("" ::: "memory");   /* 或 rmb() */
    return v;
}
```

三个细节，写错一个就出事：

| 细节 | 说明 |
|---|---|
| 地址常量要写 `UL` 后缀 | `0x40001000` 在 32 位机上可能是 `int`，左移/加法会溢出 UB |
| `volatile` 放在 `*` **左边** | `volatile uint32_t *` = 指向 volatile 数据的指针（对）；`uint32_t * volatile` = volatile 的指针（错） |
| 结构体映射要 `packed` | 否则编译器可能按对齐插入 padding，与硬件寄存器布局错位 |

### 1.2 实测：不加 volatile 的轮询会被优化成死循环

```c
static uint32_t g_status;                       /* 假装它是硬件状态寄存器 */
#define STATUS_V    (*(volatile uint32_t *)&g_status)
#define STATUS_NV   (*(uint32_t *)&g_status)
#define FLAG        (1u << 3)

void wait_volatile(void)    { while (!(STATUS_V  & FLAG)) { } }
void wait_nonvolatile(void) { while (!(STATUS_NV & FLAG)) { } }
```

`-O2` 反汇编：

| 版本 | 生成的指令 |
|---|---|
| `wait_volatile` | `mov (%rdx),%eax` → `test $0x8,%al` → `je` 回跳 —— **每次循环都真的读一次** |
| `wait_nonvolatile` | `jmp <自己>` —— **无条件死循环，连读都不读** |

真跑一遍（另起线程 300 ms 后置位标志）：

| 版本 | 结果 |
|---|---|
| volatile | 0.308 s 后正常退出 |
| 非 volatile | **卡死**，`timeout 3` 判超时（exit 124） |

编译器推理得很"正确"：单线程程序里 `g_status` 没人改，那么"条件不满足"就永远不满足 → 直接退化成死循环。**它不知道硬件会改这块内存**——`volatile` 就是把这个事实告诉它。

### 1.3 volatile 管不了的三件事（最大误区）

| 误解 | 实测结论 |
|---|---|
| ❌ volatile 保证原子性 | **不保证**。两个线程各对 `volatile long` 做 20 万次 `++`，期望 400000，**实测只得到 276660**；换成 `__atomic_add_fetch` 才稳定得到 400000 |
| ❌ volatile 保证顺序（能当屏障） | **只保证"对 volatile 变量本身的访问不被删除/不与其他 volatile 访问重排"**，不保证非 volatile 访问的顺序，也不产生任何 CPU 屏障指令（见 [二](#二编译器屏障-barrier)） |
| ❌ volatile 解决 Cache / DMA 一致性 | **不解决**。Cache 维护要靠硬件指令或 `dma_sync_*` 系列 API；`volatile` 只影响编译器生成什么 load/store，不影响 Cache 硬件行为 |

**volatile 该用在哪**：① MMIO 寄存器映射；② 被中断服务程序（ISR）修改、主循环读取的全局标志；③ 被另一个核/线程修改且不用锁同步的变量（配合原子操作更好）。

**不该用在哪**：普通变量一律不加。加了会阻止一整类优化（寄存器缓存、常量传播、向量化），**而且会掩盖真正的并发 bug**——本该用原子量/锁的地方用 volatile，跑得"看起来没问题"只是运气。

## 二、编译器屏障 barrier()

```c
#define barrier() __asm__ __volatile__("" ::: "memory")
```

一条**空的内联汇编**，但带 `"memory"` clobber——它告诉编译器："这条语句之后，内存可能被别的东西改过了，别信你之前的假设。"（内联汇编的完整语法见 [ch03.6 C 与汇编混合编程](../../02-ch2-gnu-c-advanced/3.6-mixed-programming)）

### 2.1 实测：它阻止了死存储消除

```c
int g_x;                                     /* 外部链接，编译器不能整体消除 */
void store_nob(void) { g_x = 1; g_x = 2; }
void store_b(void)   { g_x = 1; barrier(); g_x = 2; }
```

`-O2` 反汇编：

| 函数 | 指令 |
|---|---|
| `store_nob` | `movl $0x2, g_x(%rip)` —— **第一次写入被当成死存储删掉了** |
| `store_b` | `movl $0x1, g_x(%rip)` + `movl $0x2, g_x(%rip)` —— **两次写入都在** |

在硬件场景里这就是全部意义：写 `g_x = 1` 可能是"启动设备"，写 `g_x = 2` 是"配置模式"——**少一次写，设备就不工作**。同样，`barrier()` 也阻止编译器把对同一个寄存器的多次读取合并成一次。

### 2.2 三种屏障的代码生成（实测）

| 屏障 | 语义 | x86-64 `-O2` 生成的指令 |
|---|---|---|
| `barrier()` | **编译屏障**：只约束编译器重排 | **0 条**（纯编译期效果） |
| `__atomic_thread_fence(__ATOMIC_ACQUIRE)` | 获取语义 | **0 条**（x86-64 的 TSO 内存模型天然满足 acquire） |
| `__sync_synchronize()` | 全硬件屏障 | `lock orq $0x0,(%rsp)` |
| `__atomic_thread_fence(__ATOMIC_SEQ_CST)` | 顺序一致 | `lock orq $0x0,(%rsp)` |

**记住两条**：
1. `barrier()` **不产生任何指令**，它管不了 CPU 的乱序执行——需要跨核/跨设备顺序时必须上 `__sync_synchronize()` 或内核的 `mb()/rmb()/wmb()`。
2. 反过来，x86 上 acquire 屏障是**免费的**，但 ARM 上要 `dmb ishld`——写可移植代码别指望"我这台机器跑对了"。

### 2.3 内核里的对应物

| 内核宏 | 展开（x86） | 用途 |
|---|---|---|
| `barrier()` | `__asm__ __volatile__("" ::: "memory")` | 编译屏障 |
| `smp_mb()` | `lock addl $0,(%esp)` 或 `mfence` | SMP 全屏障 |
| `READ_ONCE(x)` / `WRITE_ONCE(x,v)` | volatile 强转 + 编译屏障 | 单次访问，禁止编译器拆分/合并 |
| `readl()` / `writel()` | volatile 访问 + 屏障 | MMIO 访问标准方式 |

## 三、寄存器读写的三条铁律

### 3.1 读-改-写不是原子的

```c
volatile uint32_t *reg = (volatile uint32_t *)0x4000000C;
*reg |= (1u << 3);      /* 编译成：读 reg -> 或上 0x8 -> 写回 reg，三步 */
```

如果这三步之间来了中断，ISR 也改了同一个寄存器，主程序写回时会**覆盖掉 ISR 的修改**。解法按优先级：

1. **优先用硬件提供的原子寄存器**——很多外设给每个控制位配了 `SET`/`CLR` 寄存器（写 1 置位 / 写 1 清位），完全不需要 RMW；
2. 关中断 / 持自旋锁后做 RMW；
3. 单核且确定无 ISR 竞争时，才可以裸 RMW。

### 3.2 分清"读清"和"写 1 清"

手册里两种清标志的方式最容易搞混：

| 类型 | 行为 | 踩坑后果 |
|---|---|---|
| **读清（RC）** | 读状态寄存器（或读数据寄存器）即清除标志 | 轮询循环里读一次就清了，后面再判断永远为假 |
| **写 1 清（W1C）** | 必须**写 1** 才清除；写 0 无效 | 用 `reg |= BIT(n)` 清标志会**把同寄存器里其他 W1C 位一起清掉** |

W1C 的正确写法是 `reg = BIT(n);`（**直接写，不要 |=**）。

### 3.3 别在用户态直接摸 MMIO

Linux 用户态要先 `mmap("/dev/mem")` 或走 UIO/驱动，再通过 `ioctl` 配置。裸 MMIO 在用户态既不安全也不可移植；内核侧统一用 `readl/writel` + `regmap`。

## 四、位操作：BIT / GENMASK / FIELD_PREP / FIELD_GET

内核这四个宏是写寄存器的标准词汇表，底层靠 GNU 内建 `__builtin_ffsll` 支撑：

```c
#define BIT(n)              (1UL << (n))
#define GENMASK(h, l)       (((~0UL) << (l)) & (~0UL >> (63 - (h))))
#define FIELD_PREP(m, v)    (((v) << (__builtin_ffsll((long long)(m)) - 1)) & (m))
#define FIELD_GET(m, r)     (((r) & (m)) >> (__builtin_ffsll((long long)(m)) - 1))
```

实测输出（`gcc -O2`）：

```
BIT(0)=0x1  BIT(5)=0x20  BIT(31)=0x80000000
GENMASK(7,4)=0xf0   GENMASK(3,0)=0xf   GENMASK(63,60)=0xf000000000000000
reg=0xa3  mode=10  en=1  irq=1
```

用法套路：

```c
#define REG_EN    BIT(0)
#define REG_IRQ   BIT(1)
#define REG_MODE  GENMASK(7, 4)      /* bit4..bit7 */

reg |= REG_EN | REG_IRQ;                              /* 置位 */
reg &= ~REG_IRQ;                                      /* 清位 */
reg = (reg & ~REG_MODE) | FIELD_PREP(REG_MODE, 0xA);  /* 写一段字段 */
unsigned mode = FIELD_GET(REG_MODE, reg);             /* 读一段字段 */
```

**好处**：掩码和字段位置只写一次，改手册改一行；`FIELD_PREP` 自动帮你移位，不用手数 bit。

### GNU 位内建（实测）

| 内建 | 含义 | 实测（输入） | 结果 |
|---|---|---|---|
| `__builtin_popcount(x)` | 1 的个数 | `0xF0F0` | 8 |
| `__builtin_clz(x)` | 前导零个数 | `0x0000FFFF` | 16 |
| `__builtin_ctz(x)` | 尾随零个数 | `0x0000FF00` | 8 |
| `__builtin_ffs(x)` | 最低位 1 的位置（1 起，0 表示无） | `0x0000FF00` | 9 |
| `__builtin_parity(x)` | 1 的个数的奇偶 | `0xF0F0` | 0 |
| `__builtin_ffsll(m)` | 同上，64 位 | `GENMASK(7,4)` | 5 → 字段移位量 4 |

> 注意 `ffs` 从 **1** 开始计数（0 表示全零），`ctz` 从 **0** 开始——`FIELD_GET` 里用的是 `ffs - 1`。传 0 给 `ctz`/`clz` 是 UB。

## 五、位域：看起来最像寄存器，实际最不该用

```c
union reg {
    uint32_t raw;
    struct {
        uint32_t en   : 1;
        uint32_t irq  : 1;
        uint32_t mode : 3;
        uint32_t      : 3;    /* 保留位 */
        uint32_t baud : 8;
    } bits;
};
```

实测 bit 布局（gcc 13.3 与 clang 18 **一致**）：

| 操作 | `raw` 的值 |
|---|---|
| 只置 `en` | `0x000001` → bit 0 |
| 只置 `irq` | `0x000002` → bit 1 |
| `mode = 0x5` | `0x000014` → bit 2..4 |
| `baud = 0xAB` | `0x00ab00` → bit 8..15 |

### 为什么内核禁止用位域描述硬件寄存器

| 理由 | 说明 |
|---|---|
| **布局由 ABI 决定** | 位域的分配方向、跨存储单元的填充、位域能否跨越边界——**全部是实现定义**。本测 gcc/clang 一致只是因为它们遵循同一 ABI（x86-64 SysV）；换编译器、换 `-fpack-struct`、换大端机就未必 |
| **写位域 = 读-改-写** | 实测反汇编：位域版 `movzbl (%rdi)` → `and $0xffffffe3` → `or` → `mov %sil,(%rdi)`，**四步 RMW**，和手写掩码版一模一样。位域并没有"神奇地"变成单条位操作指令，它只是把掩码计算自动化了 |
| **volatile 位域语义模糊** | `volatile` 加在整个结构体、单个位域成员、还是联合体的 `raw` 上，效果不一样；一次位域写入编译器可能生成 8/16/32 位访问，硬件未必接受 |
| **拿不到地址、不能用 offsetof** | 位域没有地址，`&r.bits.en` 非法，`offsetof` 也直接编译错误（见 [6.4 offsetof](../../01-ch1-gnu-c-basics/6.4-typeof-container-of/6.4-typeof与container_of宏.md)） |

**那什么时候可以用位域**：纯内存中的紧凑结构（协议头、标志位打包）、不需要与硬件布局严格对齐、也不要求跨编译器可移植的地方。判据很简单——**这块数据会不会被 CPU 以外的东西读？会 → 用掩码；不会 → 位域可以。**

## 六、未对齐访问：packed 的三个真相

```c
struct __attribute__((packed)) pkt {
    uint8_t  type;
    uint32_t seq;      /* 偏移 1，未对齐！ */
    uint16_t len;      /* 偏移 5 */
};
```

实测：`sizeof = 7`（不 packed 会是 12），`offsetof(seq) = 1`。

| 真相 | 实测证据 |
|---|---|
| **x86 上能跑** | 直接读 `p->seq` 结果正确（x86 硬件容忍未对齐访问，代价是慢一点） |
| **sanitizer 抓不到** | gcc 与 clang 的 `-fsanitize=alignment` 对**结构体 packed 成员**访问**都不报错**——因为编译器知道该成员对齐要求是 1，生成的是安全的字节访问 |
| **真正的雷在"取地址"** | 把 `&p->seq` 传给不知情的代码（期望 4 字节对齐的 `uint32_t *`），那边一解引用就出事。`__attribute__((packed))` 成员取地址会触发 gcc 默认开的 `-Waddress-of-packed-member` 警告。**手动把 `buf+1` 强转成 `uint32_t *` 再解引用，clang 立刻报 `runtime error: store to misaligned address ... requires 4 byte alignment`** |

**ARM 上的后果（未实测，本机无 aarch64 工具链）**：ARMv5/ARMv6 直接触发 alignment fault；ARMv7 起多数情况硬件能处理（有性能代价），但 `LDM/STM`、原子指令、部分外设访问仍然要求对齐。这就是内核要提供 `get_unaligned()` 的原因。

```c
/* 内核做法：memcpy 按字节搬，语义正确且优化器认识它 */
static inline uint32_t get_unaligned32(const void *p)
{
    uint32_t v;
    memcpy(&v, p, sizeof v);
    return v;
}
```

实测：`-O2` 下这个 `memcpy` 被**完全折叠成一条 `mov`**（`objdump` 里已找不到 `memcpy` 调用）——**正确性和性能兼得**，这才是"零成本抽象"。

## 七、字节序：__builtin_bswap 与主机序探测

```c
uint32_t bswap32_builtin(uint32_t x) { return __builtin_bswap32(x); }
uint32_t bswap32_hand(uint32_t x)    /* 手写移位版 */
{
    return ((x & 0x000000FFu) << 24) | ((x & 0x0000FF00u) << 8) |
           ((x & 0x00FF0000u) >> 8)  | ((x & 0xFF000000u) >> 24);
}
```

| 场景 | `__builtin_bswap32` | 手写版 |
|---|---|---|
| `-O0` | `bswap %eax`（**1 条**） | 10 余条 `shl`/`shr`/`and`/`or` |
| `-O2` | `bswap %eax` | `bswap %eax`（被模式匹配识别） |

结论：**用内建**。`-O2` 下两者一样，但 `-O0`（调试构建）下内建版本快一个数量级，而且意图明确、不会写错。
`__builtin_bswap16` 生成 `rol $8,%ax`，`__builtin_bswap64` 生成 `bswap %rax`——都是单指令。

主机序探测（实测输出"小端 LE"）：

```c
uint16_t v = 0x0102;
unsigned char *p = (unsigned char *)&v;
printf("%s\n", p[0] == 0x02 ? "小端 (LE)" : "大端 (BE)");
```

**什么时候需要转换**：① 网络字节序（`htons/ntohl` 的背后就是它）；② 跨架构的持久化数据/固件头；③ 大端序外设接在小端 CPU 上（部分网络控制器、某些 SoC 的 DMA 描述符）。

## 八、嵌入式 C 开门：最小检查清单

写第一段裸机/驱动代码前，逐条对照：

| # | 检查项 | 常见错误 |
|---|---|---|
| 1 | 所有 MMIO 映射都带 `volatile`，且位置在 `*` 左侧 | 忘了加 → `-O2` 下轮询变死循环 |
| 2 | 地址常量带 `UL` 后缀 | 32 位机上溢出 UB |
| 3 | 寄存器成组映射时结构体 `packed` | padding 导致寄存器错位 |
| 4 | 用 `BIT()/GENMASK()` 而不是裸数字 | `1 << 31` 在 `int` 上是 UB |
| 5 | RMW 有并发保护，或改用硬件 SET/CLR 寄存器 | ISR 与主循环互相覆盖 |
| 6 | 分清 RC 与 W1C；W1C 用直接写而不是 `\|=` | 误清其他标志位 |
| 7 | 顺序敏感处有 `barrier()`（编译器）或 `mb()`（硬件） | 只加 volatile 不够 |
| 8 | 跨核/跨线程共享用 `__atomic_*`，不用 volatile | 实测 volatile 计数丢失 30% |
| 9 | 不用位域描述硬件寄存器 | ABI 绑定 + RMW 隐式 |
| 10 | packed 成员不取地址外传 | `-Waddress-of-packed-member` 警告别忽略 |
| 11 | 调试构建（`-O0`）也能跑 | 依赖 `-O2` 优化的代码藏着时序 bug |

## 九、坑点清单

| # | 坑 | 现象 | 规避 |
|---|---|---|---|
| 1 | 裸 MMIO 忘加 `volatile` | `-O2` 下 `jmp` 死循环，调试版（`-O0`）却正常 | 实测见 [1.2](#12-实测不加-volatile-的轮询会被优化成死循环) |

| 4 | 位域描述硬件寄存器 | 换编译器/ABI 就错位；写入是 RMW | 用掩码 + `FIELD_PREP` |
| 5 | `1 << 31` 溢出 | `int` 左移进符号位 = UB | `1UL << 31` 或 `BIT(31)` |

## 代码自测

**题目 1：** 下面这段轮询在 `-O2` 下会怎样？为什么？
```c
uint32_t *status = (uint32_t *)0x40001000;
while (!(*status & (1u << 3))) { }
```
<details>
<summary>答案</summary>

**变成无条件死循环**。实测反汇编只有 `jmp <自己>` 一条——编译器认为单线程下 `*status` 不变，条件永远不成立。
修法：`#define STATUS (*(volatile uint32_t *)0x40001000UL)`。加 `volatile` 后每次循环都会真的 load（实测 `mov`+`test`+`je`）。
注意地址常量还要加 `UL`，否则 32 位机上可能是 `int`。

</details>

**题目 2（判断）：** 给共享计数器加 `volatile` 就能保证多线程 `++` 正确。

<details>
<summary>答案</summary>

**错**。实测：两个线程各对 `volatile long` 做 20 万次 `++`，期望 400000，实际只得到 **276660**；换成 `__atomic_add_fetch(&c, 1, __ATOMIC_RELAXED)` 才稳定得到 400000。
`volatile` 只保证"每次都从内存读、每次都写回内存"，**不保证读-改-写的原子性**（`++` 是三步）。

</details>

**题目 3：** `barrier()` 展开成什么？它生成几条指令？

<details>
<summary>答案</summary>

`#define barrier() __asm__ __volatile__("" ::: "memory")` —— 空汇编 + memory clobber。
**生成 0 条指令**（实测 `-O2` 下函数体只有 `ret`）。它只约束编译器重排，不管 CPU 乱序。
实测效果：没有 barrier 时 `g_x = 1; g_x = 2;` 被优化成一条 `movl $0x2`；加了 barrier 后两次写入都保留。
需要硬件顺序时用 `__sync_synchronize()` 或 `__atomic_thread_fence(__ATOMIC_SEQ_CST)`（x86 上是 `lock orq $0x0,(%rsp)`）。

</details>

**题目 4：** 为什么内核不用位域描述硬件寄存器？

<details>
<summary>答案</summary>

三条：
1. **布局由 ABI 决定**——分配方向、跨存储单元填充都是实现定义，换编译器/架构就不一样；
2. **写入是读-改-写**——实测反汇编和手写掩码版一样是 load/and/or/store 四步，并不原子，也不比掩码快；
3. **volatile 位域语义模糊**——编译器可能生成 8/16/32 位访问，硬件未必接受。
另外位域拿不到地址，`offsetof` 对位域直接编译错误。
判据：**这块数据会不会被 CPU 以外的东西读？会（硬件寄存器/协议线格式）→ 用掩码；不会（纯内存结构）→ 位域可以。**

</details>

**题目 5：** `packed` 结构体的未对齐成员，sanitizer 能抓到吗？真正的风险在哪？

<details>
<summary>答案</summary>

**抓不到**。实测 gcc 与 clang 的 `-fsanitize=alignment` 对 packed 结构成员的直接访问都不报错——编译器知道它的对齐要求是 1，会生成安全的字节访问。
真正的风险是**把 `&p->seq` 传出去**：接收方拿到 `uint32_t *` 按 4 字节对齐访问。手动把 `buf+1` 强转成 `uint32_t *` 解引用，clang 立刻报 `runtime error: store to misaligned address ... requires 4 byte alignment`。
所以：packed 成员**不要取地址外传**；跨对齐边界读用 `memcpy`（`-O2` 下会被折叠成一条 `mov`，零成本）。

</details>

**题目 6：** 手写字节序转换和 `__builtin_bswap32` 差在哪？

<details>
<summary>答案</summary>

`-O2` 下一样（gcc 能把手写移位模式匹配成 `bswap` 指令），但**`-O0` 下差一个数量级**：内建版直接 `bswap %eax` 一条，手写版要 10 余条 `shl/shr/and/or`。
调试构建通常就是 `-O0`，所以用内建更稳，而且不会写错。

</details>

**题目 7：** 什么叫 W1C 寄存器？清标志该怎么写？

<details>
<summary>答案</summary>

W1C = Write 1 to Clear：**写 1 清除该位，写 0 无效果**。
清标志必须直接写：`reg = BIT(n);`——**不能用 `reg |= BIT(n)`**，因为 `|=` 会先读回整个寄存器（其中可能还有其他 W1C 位置 1），再写回去，等于顺手把那些标志也清了。
对照：读清（RC）型寄存器是"一读就清"，轮询循环里读一次就没了。

</details>

**题目 8：** 写一个"设置 UART 波特率字段（bit4..bit7）为 0xA，并使能 bit0"的寄存器操作，用内核宏风格。

<details>
<summary>答案</summary>

```c
#define BIT(n)            (1UL << (n))
#define GENMASK(h, l)     (((~0UL) << (l)) & (~0UL >> (63 - (h))))
#define FIELD_PREP(m, v)  (((v) << (__builtin_ffsll((long long)(m)) - 1)) & (m))

#define UART_CR_EN     BIT(0)
#define UART_CR_BAUD   GENMASK(7, 4)

volatile uint32_t *uart_cr = (volatile uint32_t *)(UART_BASE + 0x0C);

uint32_t v = *uart_cr;                                  /* 读（临界区内） */
v = (v & ~UART_CR_BAUD) | FIELD_PREP(UART_CR_BAUD, 0xA);
v |= UART_CR_EN;
*uart_cr = v;                                           /* 写 */
```

实测：`GENMASK(7,4)=0xf0`，`__builtin_ffsll(GENMASK(7,4))=5` → 移位量 4，`reg=0xa3`（mode=10、en=1、irq=1）。
若并发访问，这段 RMW 需要关中断或加锁——**优先看看芯片有没有 CR_SET/CR_CLR 寄存器**，有就完全不用 RMW。

</details>
