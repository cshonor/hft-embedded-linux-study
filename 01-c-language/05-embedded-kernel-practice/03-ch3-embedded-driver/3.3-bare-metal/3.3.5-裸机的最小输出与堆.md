# 3.3.5 裸机的最小输出与堆

[← 3.3 目录](./) · [3.3.4 从复位到 main](./3.3.4-从复位到main的启动代码.md) · [3.3.1 多任务的模拟实现](./3.3.1-多任务的模拟实现.md)

## 本节讲什么

没有 libc，`printf` 和 `malloc` 这两样宿主程序员视为空气的东西全部消失。调试要有输出、数据要动态分配，怎么办？本节给出**最小可用替身**——轮询 UART 的 `puts` 和十几行的 bump allocator，并说清它们各自砍掉了什么。堆的完整展开（裸机 malloc 实现、碎片）归 [91-ref-memory](../91-ref-memory/) 批次 A3，这里只立骨架。

## 要点

### 一、最小输出：轮询 UART 的 puts

```c
#define UART0_DR    (*(volatile uint32_t *)0x4000C000)  /* 数据寄存器 */
#define UART0_FR    (*(volatile uint32_t *)0x4000C018)  /* 标志寄存器 */
#define FR_TXFF     (1u << 5)                           /* 发送 FIFO 满 */

void uart_putc(char c) {
    while (UART0_FR & FR_TXFF)   /* 等 FIFO 有空位：volatile 逐字面读（3.1） */
        ;
    UART0_DR = (uint32_t)c;      /* 写一字节，硬件自动发出 */
}

void uart_puts(const char *s) {
    while (*s) {
        if (*s == '\n') uart_putc('\r');   /* 终端惯例：LF -> CRLF */
        uart_putc(*s++);
    }
}
```

三个 C 层面的要点：

- **`volatile` 不可省**（[3.1](../3.1-register/3.1-寄存器操作.md) 实测：`-O2` 下不加就是 `jmp <自己>` 死循环）——这里的轮询标志是硬件改的，编译器毫不知情。
- 这是**轮询（busy-wait）**发送：CPU 100% 消耗在等硬件。中断驱动 + 环形缓冲的版本才是正路，但那是 [3.2 中断](../3.2-interrupt/3.2-中断.md) 的地盘——先把"能打印"拿到手。
- `puts` 在裸机不是"格式化输出"，只是"字节搬运工"。需要格式化就自己写极简 `%x/%d`，或者直接放弃 printf（见下）。

**为什么裸机慎用真 printf**：完整 printf 连浮点格式化带缓冲管理，代码体积十几 KB、栈深度不可控，还会**隐性调用 malloc**（部分 newlib 实现）。启动早期（crt0 刚过、bss 才清完）printf 是经典死法。调试早期用 `uart_puts` + 手工转 hex：

```c
void uart_puthex(uint32_t v) {
    static const char hex[] = "0123456789abcdef";
    uart_puts("0x");
    for (int i = 28; i >= 0; i -= 4)
        uart_putc(hex[(v >> i) & 0xf]);
}
```

### 二、最小堆：bump allocator

```c
static uint8_t  heap_pool[4096] __attribute__((aligned(8)));
static uint8_t *heap_ptr = heap_pool;          /* 当前分配前沿 */

void *bump_alloc(size_t n) {
    n = (n + 7u) & ~(size_t)7u;                /* 8 字节对齐 */
    if ((size_t)(heap_pool + sizeof(heap_pool) - heap_ptr) < n)
        return NULL;                           /* 池满：裸机没有"扩容"这回事 */
    void *p = heap_ptr;
    heap_ptr += n;
    return p;
}
```

它砍掉了什么，换来什么：

| 换来的 | 砍掉的 |
|--------|--------|
| 分配 O(1)，几条指令 | `free` 永远失败（前沿只进不退） |
| 无碎片、无锁（单核裸机天然无竞争） | 任意次序释放、复用内存 |
| 行为完全确定（时间可预测） | 生命周期错配即泄漏，没有 GC/回收 |

**典型用法**：启动阶段一次性分配所有"永不释放"的对象（任务栈、静态缓冲、描述符表）。运行期反复分配/释放的需求，用**固定大小内存池**（每块同尺寸，free 即还链表）——FreeRTOS 的 `xQueueCreateSet` 底层就是这套路数。

**为什么裸机慎用真 malloc**：malloc/free 时间不确定（最坏情况不可预算）、长期运行产生碎片、"分配成功"不保证"使用时内存还在"（没有 MMU 兜底，越界直接踩别的块）。这三条在 HFT 里同样成立——热路径禁 malloc 不是风格洁癖，是同一条确定性逻辑。

## 嵌入式/HFT 关联

- bump allocator 是 DPDK `rte_malloc`/内存池、内核 slab（简化到极致）的公共祖先：**确定性 > 灵活性**。
- "先 static/池、后 bump、实在不行才 malloc"的优先级，在裸机、内核、HFT 低延迟路径里是同一条工程铁律。

## 代码自测

**题目 1：** `uart_putc` 里的 `while (UART0_FR & FR_TXFF);` 去掉 `volatile`，在 `-O0` 下能正常工作，刷成 `-O2` 后卡死。为什么？

<details>
<summary>参考答案</summary>

`-O0` 时编译器基本"逐句直译"，每次循环真的读一次 `UART0_FR`，硬件置位后循环能退出——bug 被低优化掩盖。

`-O2` 下编译器发现循环体没有任何东西修改这个地址，就把值缓存进寄存器，循环退化为 `jmp <自己>`——硬件把 FIFO 标志清了也没用，CPU 再也不读。[3.1](../3.1-register/3.1-寄存器操作.md) 的反汇编实测（非 volatile 轮询只剩 `jmp` 自身）就是这个场景。"-debug 能跑、-O2 就挂"是 MMIO 的经典 bug 形态。

</details>

**题目 2：** 以下用法哪一步先出问题？`bump_alloc(100)` 在请求 A 中拿到指针 p1，A 结束后 `bump_alloc(100)` 请求 B。

<details>
<summary>参考答案</summary>

B **不会**复用 p1 的内存——bump allocator 没有 free，第二次 `bump_alloc(100)` 返回的是 p1+104 处的新块（假设 8 字节对齐补 4 字节）。所以：

- 如果 A 期望"释放后内存可复用"：逻辑成立但内存被悄悄浪费，池只进不退，最终 `bump_alloc` 返回 NULL——**这是第一处问题：不支持 free 的分配器被当成 malloc 用**。
- 如果代码没检查 NULL 继续用：返回 NULL 后解引用，在无 MMU 裸机上从"分配失败"直接升级为"踩低地址内存"。

正确姿势：bump 只用于启动期一次性分配；运行期复用需求交给固定大小内存池，或在 A/B 之间用栈式分配（按 LIFO 次序回退前沿指针）。

</details>
