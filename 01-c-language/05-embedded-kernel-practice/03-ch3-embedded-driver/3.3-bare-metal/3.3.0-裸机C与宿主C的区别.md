# 3.3.0 裸机 C 与宿主 C 的区别

[← 3.3 目录](./) · [3.3.1 多任务的模拟实现](./3.3.1-多任务的模拟实现.md) · [3.3.4 从复位到 main](./3.3.4-从复位到main的启动代码.md)

## 本节讲什么

同样一门 C 语言，在有 OS 的**宿主环境**（hosted）和没有 OS 的**裸机环境**（freestanding / bare-metal）里，编译器怎么对待你、运行时给你什么、犯了错谁兜底，完全是两个世界。本节先把这两个世界的**边界**画清楚——后面 3.3.1–3.3.3 讲"裸机上怎么切上下文"、3.3.4 讲"复位到 main 之间发生什么"，都建立在这个边界上。

## 要点

### 一张表看清两个世界

| 维度 | 宿主 C（写 Linux 程序） | 裸机 C（无 OS） |
|------|------------------------|----------------|
| 入口 | `_start`（libc 提供）→ 初始化 libc → 调 `main` | 向量表复位项 → `Reset_Handler` → crt0 → 你自己的入口函数 |
| `main` 的地位 | 特殊：被运行时调用、返回值交给 OS | **普通函数名**，叫 `kmain` 还是别的都行 |
| libc | 完整（printf/malloc/pthread...） | 没有。printf、malloc 都不存在，除非自己写（[3.3.5](./3.3.5-裸机的最小输出与堆.md)） |
| 非法内存访问 | MMU 兜底 → segfault，进程死掉 | **没人兜底**，悄悄写坏别的变量，bug 玄学化 |
| 堆 | OS + libc 管理递增 brk/mmap | 自己管：固定池或 bump allocator（[3.3.5](./3.3.5-裸机的最小输出与堆.md)） |
| 栈 | OS 分配并自动扩展 | 链接脚本里定死的固定区域，溢出直接踩别的内存 |
| 崩溃现场 | coredump、dmesg | 单步断点、UART 打印，甚至毫无反应 |

### `-ffreestanding` 到底改了什么

裸机编译常用两个标志，语义完全不同：

```sh
clang --target=arm-none-eabi -ffreestanding -c main.c   # 编译层面
arm-none-eabi-ld -nostdlib ...                            # 链接层面
```

- **`-ffreestanding`（编译器）**：不再假定"标准库函数有标准语义、且程序运行环境符合标准"。`main` 不再特殊，编译器可以要求你自己提供一切运行时函数。
- **`-nostdlib`（链接器）**：不链接 libc/crt0，入口和符号全由你的链接脚本决定（[6.18 链接脚本](../../06-ch6-toolchain-custom/6.18-链接脚本.md)）。

**最容易踩的坑**：`-ffreestanding` 下编译器**仍然会生成对 `memcpy`/`memset`/`memmove`/`memcmp` 的隐式调用**——大结构体赋值变 `memcpy`、大数组清零变 `memset`。链接时报 `undefined reference to memcpy` 不是链接脚本写错了，是**你必须自己提供这四个函数**。这也是为什么内核、bootloader 里总有一份手写的 `memcpy`。

### 标准只保证这几个头文件可用：freestanding 头文件清单

`-ffreestanding` 之外，标准还写死了一份**头文件清单**。它说的是"一个 freestanding 实现**必须**给你什么"，**不是"你工程里必须放什么"**——读法要反过来：

- 这些头文件**装在编译器自己的安装目录里**（clang 是 `lib/clang/<ver>/include/`，GCC 是 `<prefix>/lib/gcc/.../include/`），**不用往工程里放**；
- **一个都不 `#include` 也完全合法**；
- 规则的本质是"除这些之外，标准**不保证**任何东西可用"。`printf`、`malloc` 属于标准不管的地带——链接时自己想办法。

清单直接引自标准正文 Clause 4：

| 标准 | 纯 freestanding 头文件 | 个数 |
|---|---|---|
| C99（N1256 §4p6） | `float.h` `iso646.h` `limits.h` `stdarg.h` `stdbool.h` `stddef.h` `stdint.h` | **7** |
| C11 = C17（N1570 §4p6） | 上面 7 个 + `stdalign.h` `stdnoreturn.h` | **9** |
| C23（N3220 §4p7） | 上面 9 个 + `stdbit.h` | **10** |

两处容易记错的：

1. **C23 只加了 `stdbit.h`，没有加 `stdckdint.h`**。不少二手资料把 `stdckdint.h` 也算进 freestanding —— 查 N3220 §4p7 原文，清单里没有它。
2. **C23 起"freestanding"分了三层**，不再只有一张清单：上面 10 个是"完全 freestanding"；`string.h`（除 `strcoll`/`strdup`/`strerror`/`strndup`/`strtok`/`strxfrm` 六个函数）与 `stdlib.h` 的 `memalignment` 属"部分 freestanding"；若实现定义了 `__STDC_IEC_60559_BFP__`/`_DFP__`，`fenv.h`、`math.h`、`stdlib.h` 的 `strto*` 也加入（有条件 freestanding）。

> 顺带一个 C99 的细节：C99 版本的措辞是"……且**不使用复数类型**的严格符合程序"。也就是说 C99 的 freestanding 承诺比 C11 更窄。

**本机实测**（clang 23.1.0，逐个 include 一遍）：

```sh
clang -target armv7m-none-eabi -ffreestanding -std=c23 -fsyntax-only probe.c
```

| 结果 | 头文件 |
|---|---|
| 通过（在标准清单里） | `float.h` `iso646.h` `limits.h` `stdalign.h` `stdarg.h` `stdbool.h` `stddef.h` `stdint.h` `stdnoreturn.h` |
| **不通过** | **`stdbit.h`** ← 标准要求给，clang 23.1.0 的资源目录里**没有** |
| 通过（**超出**标准清单） | `stdatomic.h` `stdckdint.h`（资源目录里还有 `stdcountof.h` `stddefer.h` 等扩展） |
| 不通过（hosted 头，理应没有） | `assert.h` `stdio.h` `stdlib.h` `string.h` `math.h` |

这张表正好说明两件事：**"工具链给的头文件" ≠ "标准保证的头文件"**（clang 多给了 `stdatomic.h`，反而少了 `stdbit.h`）；而 `<stdio.h>` 一个都拿不到 —— 这就是"标准不管、链接时自己想办法"的字面含义。

一句话记：**那是"工具链欠你的最少保障清单"，不是"你欠工程的必交作业"。**

### 什么变了、什么没变

语言本体一个字没变：指针、类型、`volatile`（[3.1](../3.1-register/3.1-寄存器操作.md)）在两个世界语义一致。变的是**标准库承诺的那部分"环境"**：

```c
/* 宿主环境：标准保证这行有效 */
int local;            /* 栈由 OS 给 */

/* 裸机：这行依然有效，但"栈在哪、多大"由链接脚本和 crt0 决定 */
int local;
```

> 判据沿用本章总纲：**CSAPP 讲硬件不讲 C，标准 C 教材讲 C 不讲硬件**。本节只写"环境差异在 C 里长什么样"，MMU/异常处理原理不展开。

## 嵌入式/HFT 关联

- DPDK、内核模块、eBPF 程序都是"**不完整宿主**"：C 语言正常写，但某部分标准环境被抽走（DPDK 大页绕过内核分配器、eBPF 没有 libc 只有 helper）。理解 freestanding 的边界，这类环境的"为什么"就全通了。
- 裸机里"非法访问没人兜底"对应 HFT 里"性能路径关掉保护"的取舍： protections 拿掉之后，错误从"崩溃可定位"变成"静默数据损坏"。

## 代码自测

**题目 1：** `-ffreestanding` 编译的裸机程序里写了 `struct big a = b;`（b 是 4 KB 的结构体），链接时报 `undefined reference to memcpy`。是链接脚本漏了 libc 吗？

<details>
<summary>参考答案</summary>

不是链接脚本的问题。`-ffreestanding` 只是不链接 libc，但编译器**照常**把大结构体赋值优化成对 `memcpy` 的调用（这在宿主环境由 libc 提供）。标准明确说 freestanding 环境下这四个函数（`memcpy`/`memmove`/`memset`/`memcmp`）由实现者自己提供。

正确做法：在裸机工程里手写这四个函数（不依赖任何库，逐字节或按字长拷贝），放进链接脚本管理的 .text 段。Linux 内核的 `lib/string.c` 就是这个角色。

</details>

**题目 2（判断）：** 裸机程序里 `main` 函数返回后，程序会像宿主环境一样正常退出。

<details>
<summary>参考答案</summary>

**错。** 裸机没有 OS 接收返回值。crt0 里 `bl main` 之后通常跟着 `b .`（死循环）或 `wfi`（睡眠等中断）——main 返回即"无路可走"。宿主环境 main 的返回值交给 C 运行时再转给 OS 退出码，这套机制在裸机里根本不存在。

顺带：`exit()` 在裸机同样没有意义——没有"进程"可以退出。

</details>

**题目 3：** 有人说"freestanding 工程必须把那 7 个头文件都拷进源码目录"。错在哪？另外：你在裸机工程里 `#include <stdatomic.h>` 编译通过，能说明标准保证它可用吗？

<details>
<summary>参考答案</summary>

**第一问两处错。** ① 头文件是**工具链自带**的（clang 在 `lib/clang/<ver>/include/`），不属于工程，拷一份进源码目录反而是自找版本漂移；② 数量不是 7 而是随标准变：C99=7、C11/C17=9、C23=10（见上表原文）。

**第二问：不能。** 标准清单里没有 `stdatomic.h`，clang 照样给了它（实测通过）。反过来 clang 23.1.0 又**缺**清单里要求的 `stdbit.h`。所以"我这儿能 include 成功"只是**这个工具链的实现细节**，既不是标准保证，也不能作为可移植性依据；要写可移植的裸机代码，只应依赖标准清单里的头文件。

</details>
