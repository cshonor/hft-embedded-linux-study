# 3.3.4 从复位到 main：启动代码做了什么

[← 3.3 目录](./) · [3.3.0 裸机C与宿主C的区别](./3.3.0-裸机C与宿主C的区别.md) · [3.3.5 裸机的最小输出与堆](./3.3.5-裸机的最小输出与堆.md)

## 本节讲什么

你按下复位键，到 `main` 的第一行 C 代码执行，中间隔着一段**谁写的代码**？答案是 crt0（startup code）。本节用 C 初始化语义反推它必须做的事——**你在 C 里写下的每一个全局变量初始化，都是有运行时代价的，这个代价 crt0 来付**。

> 链接脚本决定"各段放在哪个地址、`_sidata`/`_sdata` 这些符号从哪来"，属于 [6.18 链接脚本](../06-ch6-toolchain-custom/6.18-链接脚本.md) 的地盘。本节只回答"C 代码需要的初始化语义，谁来兑现"。

## 要点

### 一、先实测：你的变量到底落在哪个段

Mac clang 23.1.0，`--target=aarch64-linux-gnu -O2 -c` 交叉编译（`llvm-readelf -S` 看段）：

```c
uint32_t bss_arr[10000];            /* 零初始化        */
uint32_t data_arr[10000] = {1};     /* 有非零初值      */
const uint32_t ro_arr[10000] = {0}; /* 全零 const      */
```

| 写法 | 段 | ELF 类型 | 占用文件(flash) | 占用 RAM |
|------|-----|---------|----------------|----------|
| `bss_arr` | `.bss` | **NOBITS** | **0 B** | 40000 B |
| `data_arr = {1}` | `.data` | PROGBITS | 40000 B | 40000 B |
| `ro_arr = {0}` (const) | `.rodata` | PROGBITS | **40000 B** | 0（可留在 flash） |

两个反直觉结论：

1. **全零 const 数组不进 `.bss`**——`.bss` 是可写段，const 必须进只读段，于是 40 KB 实打实进了 flash。想省 flash，去掉 `const`（代价是放进可写的 bss，运行时被清零）。
2. **显式 `= {0}` 反而省 flash**：`uint32_t z[10000] = {0};`（非 const）被编译器识别为全零，直接丢进 `.bss`，文件体积 0 B——和不写初始化完全一样。

Mach-O 侧对照（同代码，本机编译）：零初始化进 `__DATA,__common (zerofill)`，语义与 `.bss` 相同；段归属是**平台约定**，但"全零免占用"的原理一致。

### 二、crt0 的四步（每一步对应一条 C 语义）

C 标准说"static 存储期对象：无初始化则清零、有初始化则取初值"。裸机上没人替你兑现，crt0 干：

```asm
Reset_Handler:                /* 向量表第 2 项指到这里 */
    ldr  sp, =_estack         /* 1. 设栈：没有栈，一条 C 函数都调不动 */

    ldr  r0, =_sidata         /* 2. 拷 .data：flash 初值 -> RAM */
    ldr  r1, =_sdata          /*    兑现 "int x = 5;" */
    ldr  r2, =_edata
1:  cmp  r1, r2
    bcs  2f
    ldr  r3, [r0], #4
    str  r3, [r1], #4
    b    1b

    ldr  r1, =_sbss           /* 3. 清 .bss：兑现 "static int y;" 隐含的 "= 0" */
    ldr  r2, =_ebss
    movs r3, #0
2:  cmp  r1, r2
    bcs  3f
    str  r3, [r1], #4
    b    2b

3:  bl   main                 /* 4. 跳 C 入口 */
    b    .                    /* main 返回即无路可走 */
```

四个符号（`_sidata/_sdata/_edata/_sbss/_ebss`）全部由链接脚本定义——这就是"链接脚本决定内存布局"在启动路径上的直接体现。

**为什么 `.data` 必须拷**：初值 `{1}` 这种非零数据要断电不丢，只能存 flash（只读）；但 C 语义要求变量**可写**，所以运行前必须搬到 RAM。`.bss` 不占 flash 正是因为"全零不用存，运行时补零"。

### 三、两件事容易想错

- **栈不是"清"出来的**：crt0 只设 SP 指针，栈里是内存上电的随机值。所以局部变量不初始化就读，在裸机上读到的就是这些随机值，且**每次复位可能不同**。
- **启动耗时和全局变量成正比**：`.data` 多大拷多长、`.bss` 多大清多长。启动时间敏感的系统（汽车 MCU、HFT 行情网关重启）会把大数据表从"初始化数组"改成"运行时从 flash 读"，就是躲开这段拷贝。

## 嵌入式/HFT 关联

- 理解 crt0 才能读懂任何 bootloader / RTOS 移植代码的前 50 行——它们都长上面这样。
- HFT 视角：**全局变量初始化 = 启动路径上的 memcpy/memset**。行情进程重启速度经常被"几百 MB 的 static 表"拖累，机制与此完全同构（宿主环境下由内核 anonymous bss 兜底，代价变成缺页）。

## 代码自测

**题目 1：** 把 `static const uint32_t lut[8192] = {0};` 改成 `static uint32_t lut[8192];`，flash 占用和 RAM 占用分别怎么变？

<details>
<summary>参考答案</summary>

- 改前（const 全零）：进 `.rodata`，**flash 占 32 KB**，RAM 0（直接从 flash 读）。
- 改后（非 const 无初始化）：进 `.bss`，**flash 0 B**，RAM 占 32 KB（crt0 清零）。

代价转移：32 KB flash → 32 KB RAM。前提是这张表**真的全零**——如果某天有人给它填了初值，`.bss` 会自动"升级"成 `.data`，flash 和 RAM 各占 32 KB（.data 既要存初值又要占 RAM），这正是"显式 `= {0}` 省不下任何东西、非零初值却翻倍成本"的原因。

</details>

**题目 2：** crt0 忘了清 `.bss`，程序在 main 里读一个未初始化的 `static int counter;`，行为会怎样？

<details>
<summary>参考答案</summary>

读到的不是 0，而是**该地址上电后的随机值**（可能是上次运行的残留、也可能是 RAM 初始态）。更阴险的是：如果这段 RAM 之前被 crt0 的 `.data` 拷贝或栈使用过，counter 的初值还**确定地**是那段残留数据——bug 呈现"看起来像有规律的错值"，非常难定位。

宿主环境下这一步由内核完成（新页映射为零页或清零页），所以写 Linux 程序的人没有机会见过这个 bug——这也是"裸机让 C 语义变得可见"的典型例子。

</details>
