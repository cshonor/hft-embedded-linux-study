## 本节讲什么

**`container_of` 是"从零件地址找回整机"的工具**；**侵入式链表是"零件长在整机里"的数据结构**。两者结合，让内核用**一套代码**（`list_head` + `container_of`）服务**所有结构体**——`device`、`task_struct`、`sk_buff`、`file`、`inode`……都挂在同一套链表 API 上，零泛型、零虚函数、零运行时开销。

CH1 讲了 `container_of` 宏本身的语法（`typeof` + `offsetof` + 语句表达式），本篇回答的是**工程问题**：

| 问题 | 本篇回答 |
|---|---|
| 内核的 `list_head` 只有 2 个指针，怎么挂住上万物种？ | 靠 `container_of` 的 `member` 参数——同一份宏代码，调用方传不同成员名，回推到不同偏移 |
| `list_del` 为什么要投毒（`LIST_POISON1/2`）？ | 不投毒，`use-after-del` 是静默内存腐败；投毒后立刻 segfault，bug 无处藏身 |
| `hlist`（哈希链表）为什么用 `pprev` 而不是 `prev`？ | `pprev` 指向"前驱的 next 字段的地址"，删头节点不用特判——`*pprev = next` 一步搞定 |
| `list_for_each_entry_safe` 比 `list_for_each_entry` 多了什么？ | 多一个临时变量 `n` 预存下一个节点——删当前节点不会让遍历崩溃 |
| 侵入式链表比"外挂链表"好在哪？ | 零分配（不 `malloc`）、cache 友好（节点和数据同处一个结构体）、一个结构体挂多张链表 |
| RCU 链表的写入顺序为什么重要？ | 先建好 `new->next`，`wmb`，再改 `prev->next`——读者要么看到旧链要么看到新链，不会看到"半插入" |

## 一、设计哲学：侵入式 vs 外挂式

### 1.1 两种链表的根本差异

```
外挂链表（传统）              侵入式链表（内核）
┌──────────┐                 ┌──────────────────┐
│ list_node│ ─► data ─►      │ struct device     │
│  next    │   (malloc 节点)  │   id             │
│  data*   │                 │   name           │
└──────────┘                 │   node {next,prev}│ ◄── 节点内嵌
                             │   irq            │
                             └──────────────────┘
节点和数据分离                节点就是数据的一部分
插入要 malloc                插入零分配
遍历: node→data (2 次访存)   遍历: container_of (1 条 lea)
```

### 1.2 实测对比（T1）

```
sizeof(struct device)     = 40    (含 node 16 字节)
sizeof(struct ext_node)   = 16    (next + data*, 不含数据)
offsetof(node)            = 16
```

| 方案 | 每次插入 | 内存局部性 | 一个结构体挂多张链表 | 裸机/中断可用 |
|---|---|---|---|---|
| 外挂链表 | `malloc` 一个节点 | **差**（数据与节点分离，2 次 cache miss） | 需要多套节点 | ❌（无堆） |
| **侵入式** | **无** | **好**（节点与数据同 cache line） | **多放几个 `list_head` 即可** | ✅ |

### 1.3 一个结构体挂多张链表（T2）

这是侵入式链表最核心的能力。同一个 `struct device` 同时挂在"设备链表"和"IRQ 链表"上：

```c
struct device {
    int              id;
    char             name[12];
    struct list_head node;        /* 挂在设备链表 (偏移 16) */
    unsigned         irq;
    struct list_head irq_node;   /* 同时挂在 IRQ 链表 (偏移 40) */
    int              priority;
};
```

**同一份 `list_for_each_entry` 宏，`member` 参数不同，回推到不同偏移**：

```
  via node      -> offsetof(node)      = 16
  via irq_node   -> offsetof(irq_node)  = 40
  d1 via irq_node = &d1 (yes)     d1 via node = &d1 (yes)
```

实测：设备链表按 id 排序（0→1→2），IRQ 链表按 priority 排序（2→1→0），**同一组数据，两种遍历顺序，零额外内存**。

> **CH1 已讲 `container_of` 宏的语法；这里讲的是"为什么 `member` 参数能区分回推偏移"——因为 `offsetof(type, member)` 是编译期常量，不同成员名产生不同常量，运行时只是一条 `lea` 指令的立即数不同。**

## 二、list_head 的完整 API 设计

### 2.1 核心结构（v6.6 `include/linux/types.h`）

```c
struct list_head {
    struct list_head *next, *prev;
};
```

只有两个指针，16 字节。**头节点与普通节点同构**——这是一个关键设计决策：遍历到头节点即终止，不需要 `NULL` 判断（`NULL` 判断在空链表时需要特判，自指不需要）。

### 2.2 初始化

```c
#define LIST_HEAD_INIT(name) { &(name), &(name) }   /* 自指 */
#define LIST_HEAD(name) \
    struct list_head name = LIST_HEAD_INIT(name)      /* 静态初始化 */
static inline void INIT_LIST_HEAD(struct list_head *list) {  /* 运行时初始化 */
    list->next = list; list->prev = list;
}
```

空链表：`head->next == head`（自指）。`list_empty()` 就是判 `head->next == head`。

### 2.3 插入与删除

```c
/* 核心插入: 4 个指针写入 */
static inline void __list_add(struct list_head *new,
                              struct list_head *prev,
                              struct list_head *next) {
    next->prev = new;
    new->next = next;
    new->prev = prev;
    prev->next = new;
}
static inline void list_add(struct list_head *new, struct list_head *head) {  /* 头插 */
    __list_add(new, head, head->next);
}
static inline void list_add_tail(struct list_head *new, struct list_head *head) {  /* 尾插 */
    __list_add(new, head->prev, head);
}

/* 删除: 先修指针, 再投毒 */
static inline void __list_del(struct list_head *prev, struct list_head *next) {
    next->prev = prev;
    prev->next = next;
}
static inline void list_del(struct list_head *entry) {
    __list_del_entry(entry);
    entry->next = LIST_POISON1;   /* 0x100 + POISON_POINTER_DELTA */
    entry->prev = LIST_POISON2;   /* 0x122 + POISON_POINTER_DELTA */
}
static inline void list_del_init(struct list_head *entry) {  /* 删除+重新初始化 */
    __list_del_entry(entry);
    INIT_LIST_HEAD(entry);          /* 自指, 可安全重用 */
}
```

### 2.4 POISON 技巧实测（T3）

`LIST_POISON1 = (void *)0x100`，`LIST_POISON2 = (void *)0x122`。

```
--- 删 b (list_del 投毒) ---
  b.node.next = 0x100 (LIST_POISON1=0x100? yes)
  b.node.prev = 0x122 (LIST_POISON2=0x122? yes)

--- 删 c (list_del_init 自指) ---
  c.node.next = &c.node (自指? yes)
  c.node.prev = &c.node (自指? yes)
  -> c 可以安全重用 (重新 list_add 不会崩)
```

**为什么不直接 `NULL` 化？** 如果 `next = NULL`，后续 `pos->next` 遍历到 `NULL` 时，`container_of(NULL, ...)` 返回 `NULL - offset` = 非空地址（见 [hlist 的坑](#五hlist-哈希链表pprev-的妙用)），循环继续 → 读到垃圾内存但**不崩溃**，bug 静默存在。投毒 `0x100` 后，任何解引用立刻 page fault，bug 无处藏身。

`list_del_init` 删除后重新自指——节点可以安全重用（重新 `list_add` 不会崩）。**内核里 `list_del_init` 比 `list_del` 更安全，优先用。**

## 三、遍历宏家族

### 3.1 四层封装（从底层到高层）

```c
/* 第 1 层: 遍历 list_head 指针 (需要手动 container_of 取宿主) */
#define list_for_each(pos, head) \
    for (pos = (head)->next; !list_is_head(pos, (head)); pos = pos->next)

/* 第 2 层: list_entry = container_of 的别名 */
#define list_entry(ptr, type, member) container_of(ptr, type, member)

/* 第 3 层: 直接遍历宿主指针 (最常用) */
#define list_for_each_entry(pos, head, member) \
    for (pos = list_first_entry(head, typeof(*pos), member); \
         !list_entry_is_head(pos, head, member); \
         pos = list_next_entry(pos, member))

/* 第 4 层: safe 版 —— 删当前节点不破坏遍历 */
#define list_for_each_entry_safe(pos, n, head, member) \
    for (pos = list_first_entry(head, typeof(*pos), member), \
         n = list_next_entry(pos, member); \
         !list_entry_is_head(pos, head, member); \
         pos = n, n = list_next_entry(n, member))
```

### 3.2 list_for_each_entry 展开实测（T8）

宏完全展开后：

```c
for (pos = container_of(head->next, typeof(*pos), member);  // 初始化
     &pos->member != head;                                    // 条件: 回到头?
     pos = container_of(pos->member.next, typeof(*pos), member))  // 步进
```

**每次步进 = 一次 `container_of` = `typeof`（编译期，不生成代码）+ `offsetof`（编译期常量）+ `lea`（运行期 1 条指令）。**

### 3.3 safe 版 vs 非 safe 版（T4）

| 场景 | 非 safe | safe |
|---|---|---|
| 遍历时删除当前节点 | ❌ `pos->member.next` 被 `__list_del` 改写，步进取到错误值 | ✅ `n` 预存了下一个，删 `pos` 不影响 `n` |
| 额外开销 | 无 | 多一个 `struct list_head *n` 局部变量（栈上，零运行时开销） |
| 适用 | 只读遍历 | 需要边遍历边删除 |

实测（T4）：遍历 5 个节点，删偶数 id：

```
  visiting id=0, next will be id=1 -> deleting id=0
  visiting id=1, next will be id=2
  visiting id=2, next will be id=3 -> deleting id=2
  visiting id=3, next will be id=4
  visiting id=4, ...               -> deleting id=4
  删除后剩余: id=1 id=3
```

**safe 版的关键**：`n` 在循环初始化时赋值，每次步进时更新——删 `pos` 后 `pos->member` 可能已被改写，但 `n` 已经指向了正确的下一个。

### 3.4 内核的完整遍历宏清单

| 宏 | 用途 |
|---|---|
| `list_for_each_entry` | **正向遍历**，最常用 |
| `list_for_each_entry_reverse` | 反向遍历 |
| `list_for_each_entry_safe` | **边遍历边删** |
| `list_for_each_entry_continue` | 从当前位置继续遍历 |
| `list_for_each_entry_from` | 从指定位置开始 |
| `list_for_each_entry_safe_reverse` | 反向安全遍历 |

## 四、零开销验证（T6 反汇编）

### 4.1 container_of = 一条 lea

```c
struct device {
    char             pad[64];
    int              irq;
    struct list_head node;      /* offsetof = 72 = 0x48 */
    unsigned long long stamp;
};
struct device *get_host(struct list_head *node) {
    return container_of(node, struct device, node);
}
```

**`-O2` 反汇编**（gcc 13.3, x86-64）：

```asm
<get_host>:
   endbr64
   lea    -0x48(%rdi),%rax    ; 一条 lea: rax = rdi - 72
   ret
```

**`-O0` 反汇编**：

```asm
<get_host>:
   mov    %rdi,-0x18(%rbp)    ; 存 node 到栈
   mov    -0x18(%rbp),%rax    ; 读回
   mov    %rax,-0x8(%rbp)     ; 存 __mptr
   mov    -0x8(%rbp),%rax     ; 读 __mptr
   sub    $0x48,%rax          ; 减偏移
```

`-O0` 有 4 次栈上搬运 + 1 条 sub；`-O2` 全部折叠成 1 条 `lea`。**`typeof` 的类型检查纯编译期，运行时开销为零。**

### 4.2 list_for_each_entry 遍历循环展开（T6 sum_irqs）

```asm
<sum_irqs>:
   mov    (%rdi),%rdx          ; rdx = head->next (第一个节点)
   xor    %ecx,%ecx            ; sum = 0
   lea    -0x48(%rdx),%rax     ; rax = container_of(rdx) = 第一个 device
   cmp    %rdx,%rdi            ; &pos->member == head?
   je     48                  ; 是 -> 结束
.loop:
   mov    0x48(%rax),%rdx     ; rdx = pos->node.next (下一个节点)
   add    0x40(%rax),%ecx     ; sum += pos->irq (offsetof(irq)=0x40)
   lea    -0x48(%rdx),%rax    ; rax = container_of(next) = 下一个 device
   cmp    %rdx,%rdi            ; 回到头?
   jne    .loop
   mov    %ecx,%eax            ; return sum
   ret
```

**关键观察**：
1. **没有 `call` 指令**——`container_of`、`list_entry`、`list_next_entry` 全部内联展开
2. 每次循环只有 `mov + add + lea + cmp + jne` = **5 条指令**
3. `offsetof` 被折叠成常量（`0x48`、`0x40`），没有运行时计算

## 五、hlist：哈希链表与 pprev 的妙用

### 5.1 为什么要有 hlist

`list_head` 的头节点占 16 字节（next + prev）。哈希表有 N 个桶，头节点就占 N × 16 字节。对于一个有 65536 个桶的哈希表，头节点就要 1 MB——太浪费了。

`hlist` 把头节点缩小到 8 字节（只有 `first` 指针）：

```c
struct hlist_head {
    struct hlist_node *first;    /* 只有 1 个指针, 8 字节 */
};
struct hlist_node {
    struct hlist_node *next;
    struct hlist_node **pprev;   /* 指向前驱的 next 字段的地址 */
};
```

头节点省一半，代价是节点里用 `pprev`（二级指针）代替 `prev`，且**失去 O(1) 访问尾节点**的能力。

### 5.2 pprev 的妙用：删头节点不需特判

普通双向链表删头节点：

```c
/* list_head 删头节点: 需要特判 */
if (entry == head->next) {
    head->next = entry->next;   /* 改 head */
}
entry->next->prev = entry->prev;  /* 改后继 */
entry->prev->next = entry->next;
```

hlist 删任意节点（包括头节点）**一条语句搞定**：

```c
static inline void __hlist_del(struct hlist_node *n) {
    struct hlist_node *next = n->next;
    struct hlist_node **pprev = n->pprev;
    WRITE_ONCE(*pprev, next);     /* 直接修改前驱的 next 字段 */
    if (next)
        WRITE_ONCE(next->pprev, pprev);
}
```

**为什么 `*pprev = next` 就够了？** 因为 `pprev` 指向的是"指向 `n` 的那个 next 字段的地址"：
- 如果 `n` 是头节点，`pprev = &head->first`，`*pprev = next` 直接改 `head->first`
- 如果 `n` 是中间节点，`pprev = &prev->next`，`*pprev = next` 改前驱的 `next`

**无论 `n` 在哪个位置，`*pprev = next` 都是正确的操作——不需要 `if (n == head->first)` 判断。**

### 5.3 实测验证（T5）

```
sizeof(struct hlist_head) = 8 (只有 1 个指针)
sizeof(struct hlist_node) = 16 (next + pprev)

--- pprev 的妙用: 验证 ---
  bucket[0].first      = 0x7ffcf0a349d8
  first_node->pprev     = 0x7ffcf0a34950
  &buckets[0].first     = 0x7ffcf0a34950 (== pprev? yes)
  -> pprev 指向 head.first 的地址, 删除时 *pprev=next 直接改 head.first

--- 删 bucket[0] 的第一个节点 ---
  删前: first=0x7ffcf0a349d8
  删后: first=0x7ffcf0a34978 (被 *pprev=next 自动改写)
  -> 不需要 if (n == head->first) 判断!
```

### 5.4 hlist_entry_safe 的必要性

内核的 `hlist_for_each_entry` 用了 `hlist_entry_safe`（先判 NULL 再 `container_of`）：

```c
#define hlist_entry_safe(ptr, type, member) ({ \
    typeof(ptr) ____ptr = (ptr); \
    ____ptr ? hlist_entry(____ptr, type, member) : NULL; })
```

**为什么需要？** `container_of(NULL, ...)` = `(char *)NULL - offsetof = 负数地址`，这**不是 NULL**！如果不判 NULL，遍历到末尾（`next = NULL`）时，`container_of(NULL)` 产生非空地址，循环条件 `pos` 非 NULL → true → 解引用野指针 → **segfault**。

**实测验证**：T5 不加 `hlist_entry_safe` 时 segfault，加上后正常。

| 对比 | list_head | hlist |
|---|---|---|
| 头节点大小 | 16 字节 (next+prev) | 8 字节 (first) |
| 节点大小 | 16 字节 | 16 字节 (next+pprev) |
| 删头节点 | 需特判 (改 head) | 不需特判 (*pprev) |
| 访问尾节点 | O(1) (head->prev) | O(n) |
| 典型用途 | 通用双向链表 | 哈希表桶 |

## 六、内核真实用例（T7）

### 6.1 三种典型用法

```c
/* 1. 全局设备链表: list_head 挂所有设备 */
static struct list_head all_devices;
list_add_tail(&dev->dev_list, &all_devices);

/* 2. 从 file->private_data 取回 priv */
static int my_open(struct file *f) {
    struct mydrv_priv *priv = f->private_data;  /* 直接赋值 */
    /* 或: struct mydrv_priv *priv = container_of(some_member, struct mydrv_priv, member); */
}

/* 3. 按条件查找节点 */
struct mydrv_priv *find_device_by_id(int id) {
    struct mydrv_priv *pos;
    list_for_each_entry(pos, &all_devices, dev_list) {
        if (pos->device_id == id)
            return pos;   /* 找到就 break */
    }
    return NULL;          /* 没找到 */
}
```

### 6.2 从内嵌成员反推宿主

```c
/* 从 fops 反推 priv */
struct mydrv_priv *via_fops = container_of(&found->fops, struct mydrv_priv, fops);
/* via_fops == found (yes) */
```

`fops` 在 `priv` 内部的偏移 = 16。`container_of(&found->fops, ...)` = `&found - 16` = `&found`（因为 `fops` 在偏移 16 处，减 16 回到首地址）。**任何内嵌成员都可以反推宿主**——这是 `container_of` 的万能性。

### 6.3 netdev_priv：固定偏移加法 vs container_of

```c
/* netdev_priv 用固定偏移加法 (更快, 但不够灵活) */
static inline void *netdev_priv(const struct net_device *dev) {
    return (char *)dev + ALIGN(sizeof(struct net_device), NETDEV_ALIGN);
}
```

`netdev_priv` 是**加偏移**（私有数据在 `net_device` 之后），`container_of` 是**减偏移**（从内嵌成员回退）。前者更快（不需要减），代价是私有数据只能在尾部、大小在分配时确定。

## 七、RCU 链表

### 7.1 写入顺序的意义

普通 `list_add` 写 4 个指针，顺序无所谓。`list_add_rcu` 的关键是**写入顺序**：

```c
static inline void __list_add_rcu(struct list_head *new,
                                  struct list_head *prev,
                                  struct list_head *next) {
    new->next = next;      /* 1. 先建好 new->next */
    new->prev = prev;
    smp_wmb();             /* 2. 写屏障: 上面的必须在下面的之前可见 */
    next->prev = new;      /* 3. 修复后继 */
    prev->next = new;      /* 4. 最后才让链表"看到" new (原子点) */
}
```

**为什么最后才写 `prev->next`？** 因为读者是顺 `next` 走的。在 `prev->next` 被修改之前，读者看到的还是旧链表（不包含 `new`）；修改之后，读者看到的是新链表（包含 `new`）。由于 `smp_wmb` 保证了 `new->next` 先于 `prev->next` 可见，读者**永远不会看到"半插入"的节点**（`new` 在链表上但 `new->next` 还没设好）。

### 7.2 读端

```c
#define list_for_each_entry_rcu(pos, head, member) \
    for (pos = list_entry(rcu_dereference((head)->next), typeof(*pos), member); \
         &pos->member != (head); \
         pos = list_entry(rcu_dereference(pos->member.next), typeof(*pos), member))
```

`rcu_dereference` 的作用是**防止编译器重排读操作**——保证读到的 `next` 是"当前"值，不会被优化到寄存器里缓存。

### 7.3 删除的代价

```c
list_del_rcu(entry);          /* 只摘链 (改指针), 不释放 */
synchronize_rcu();             /* 等所有读者结束 grace period */
kfree(entry);                  /* 现在才安全释放 */
```

RCU 删除分两步：先摘链，等所有读者离开（grace period）后才释放。**读端零开销（无锁），代价是写端延迟回收。**

| 场景 | 用 RCU 链表 | 用 spinlock 链表 |
|---|---|---|
| 读多写少（路由表、inode 缓存） | ✅ 读端零开销 | ❌ 每次读要加锁 |
| 读写都频繁 | ❌ 写端 grace period 太长 | ✅ 更简单 |
| 删除后立即释放 | ❌ 要等 grace period | ✅ 摘链即释放 |

## 八、性能对比（T11）

### 8.1 遍历 10000 个节点求和

```
N = 10000, 遍历求和:
  双向链表:   35235 ns  (每节点: 读 next + container_of + 读 id)
  单链表:     29584 ns  (每节点: 读 next + 读 id)
  数组:       62 ns     (连续内存, prefetcher 友好)

  数组/链表 ≈ 568.3x  (cache 局部性差距)
```

**数组比链表快 568 倍**——这不是算法复杂度的差距（都是 O(n)），而是 **cache 局部性**的差距。链表节点分散在堆各处，每次 `next` 都是一次 cache miss；数组连续存放，CPU prefetcher 能预取。

### 8.2 操作复杂度对比

| 操作 | 双向 list_head | 单链表 slist | 数组 |
|---|---|---|---|
| 头插 | O(1) | O(1) | O(n) |
| 尾插 | O(1) (head.prev) | O(n) | O(1) 摊还 |
| 任意位置插 | O(1) (有指针) | O(1) | O(n) |
| 删中间节点 | O(1) (有指针) | O(n) 找前驱 | O(n) |
| 反向遍历 | O(1) (head.prev) | 不支持 | O(1) |
| 查找 | O(n) | O(n) | O(log n) 排序 |
| 内存局部性 | 差 (节点分散) | 差 | 好 |
| 每节点开销 | 16 字节 | 8 字节 | 0 |

> **HFT 视角**：链表遍历的 568 倍差距意味着——在热路径上，如果数据量已知且不大，**用数组 + 线性扫描比链表快得多**。链表的优势在"频繁插入/删除中间节点"和"大小未知"的场景。HFT 订单簿通常用数组（预分配）+ 索引，不用链表。

| # | 坑 | 现象 | 规避 |
|---|---|---|---|
| 1 | 成员名写错（同类型） | **零警告**，地址算错 | CH1 6.4 已详述；代码审查 + ASan |

## 代码自测

**题目 1：** 为什么 `list_head` 的头节点用自指（`next = prev = &head`）而不是 `NULL`？

<details>
<summary>答案</summary>

自指让空链表的 `list_empty()` 判 `head->next == head`——不需要特判 NULL。遍历的终止条件 `pos != head` 也不需要特判——走到 `head` 即停。如果用 NULL，空链表的头节点 `next = NULL`，遍历时要先判 `pos != NULL && pos != head`，多一次比较。

</details>

**题目 2：** `list_del` 为什么把 `next` 设成 `LIST_POISON1`（`0x100`）而不是 `NULL`？

<details>
<summary>答案</summary>

如果设成 `NULL`，后续遍历到这个节点时 `container_of(NULL, ...)` = `(char *)NULL - offsetof = 负数地址`——这不是 NULL，循环条件 `pos` 非 NULL 为 true，继续执行，读到垃圾内存但**不崩溃**——bug 静默存在。

设成 `0x100` 后，任何解引用立刻 page fault——**快速暴露 use-after-del**，bug 无处藏身。这是"用 crash 换正确性"的设计哲学。

</details>

**题目 3：** `hlist` 为什么用 `pprev`（二级指针）而不是 `prev`（一级指针）？

<details>
<summary>答案</summary>

`pprev` 指向"前驱的 next 字段的地址"（而不是前驱节点本身）。删除时 `*pprev = next` 一步修改前驱的 next 指针——**无论 n 是头节点还是中间节点都一样**，不需要 `if (n == head->first)` 特判。

如果用 `prev`（指向 前驱节点），删头节点时要改 `head->first`，删中间节点要改 `prev->next`——两种情况，需要特判。

代价：失去 O(1) 访问尾节点（`prev` 指向前驱，但 `head` 没有 `last` 指针）。

</details>

**题目 4：** `list_for_each_entry_safe` 比 `list_for_each_entry` 多了什么？什么时候用它？

<details>
<summary>答案</summary>

多了临时变量 `n`，在循环初始化时预存 `pos` 的下一个节点。当 `pos` 被删除后，`pos->member.next` 可能已被改写（投毒或被其他线程修改），但 `n` 已经指向了正确的下一个——**边遍历边删除不崩溃**。

什么时候用：需要在遍历过程中删除当前节点时。只读遍历用普通版即可（safe 版多一个变量，虽然零运行时开销，但语义上不必要）。

</details>

**题目 5：** `container_of` 在 `-O2` 下生成几条指令？`list_for_each_entry` 遍历循环每次迭代几条指令？

<details>
<summary>答案</summary>

`container_of` 在 `-O2` 下只生成**1 条 `lea`**（`lea -0x48(%rdi),%rax`），因为 `typeof` 是编译期行为、`offsetof` 是编译期常量。

`list_for_each_entry` 每次迭代**5 条指令**：`mov`（读 next）+ `add`（累加业务字段）+ `lea`（container_of）+ `cmp`（判回到头）+ `jne`（循环）。**没有 `call`**——所有宏完全内联展开。

</details>

**题目 6：** RCU 链表的 `list_add_rcu` 为什么最后才写 `prev->next`？

<details>
<summary>答案</summary>

读者是顺 `next` 走的。在 `prev->next` 被修改之前，读者看到的还是旧链表（不包含 new）；修改之后，读者看到的是新链表（包含 new）。

由于 `smp_wmb` 保证了 `new->next` 先于 `prev->next` 可见，读者**永远不会看到"半插入"的节点**（new 在链表上但 new->next 还没设好）。如果先写 `prev->next` 再写 `new->next`，读者可能在两者之间读到 new，然后顺 `new->next` 走到未初始化的垃圾值。

</details>

**题目 7：** 侵入式链表比外挂链表好在哪三点？代价是什么？

<details>
<summary>答案</summary>

三点优势：
1. **零分配**——节点内嵌在宿主里，插入不 `malloc`，裸机和中断上下文都能用
2. **cache 友好**——节点与业务字段同处一个结构体，遍历时一次 cache line 就能拿到判断所需的数据
3. **一个结构体挂多张链表**——多放几个 `list_head` 成员即可，靠 `container_of` 的 `member` 参数区分

代价：**类型安全弱**——`container_of` 只检查成员类型，不检查宿主类型和成员名。两个 `int` 成员传错零警告。测试必须开 ASan/UBSan 兜底。

</details>

**题目 8：** 为什么遍历 10000 个节点的链表比遍历同样大小的数组慢 568 倍？

<details>
<summary>答案</summary>

不是算法复杂度的差距（都是 O(n)），而是 **cache 局部性**的差距。链表节点分散在堆各处，每次 `next` 都是一次 cache miss（要等 DRAM 返回数据，约 100 周期）。数组连续存放，CPU prefetcher 能预取后面的数据到 cache，每次访问只需几个周期。

**HFT 启示**：热路径上，如果数据量已知且不大，用数组 + 线性扫描比链表快得多。链表的优势在"频繁插入/删除中间节点"和"大小未知"的场景。

</details>

**题目 9：** `hlist_for_each_entry` 为什么用 `hlist_entry_safe` 而不是直接 `hlist_entry`？

<details>
<summary>答案</summary>

`container_of(NULL, ...)` = `(char *)NULL - offsetof = 负数地址`——这**不是 NULL**。如果直接用 `hlist_entry`（= `container_of`），遍历到末尾（`next = NULL`）时，`container_of(NULL)` 产生非空地址，循环条件 `pos` 非 NULL → true → 解引用野指针 → **segfault**。

`hlist_entry_safe` 先判 `ptr` 是否为 NULL，是则返回 NULL，否则才做 `container_of`——循环条件 `pos == NULL` → false → 正确终止。

**实测**：不加 `hlist_entry_safe` 时 T5 segfault，加上后正常。

</details>

**题目 10：** `netdev_priv` 用"固定偏移加法"取私有数据，`container_of` 用"减偏移"取宿主。两者有什么区别？

<details>
<summary>答案</summary>

`netdev_priv`：私有数据分配在 `net_device` 结构体**之后**，取私有数据 = `dev + ALIGN(sizeof(net_device))`——**加偏移**，一条 `add` 指令。代价：私有数据只能在尾部、大小在分配时确定。

`container_of`：从结构体**内部**的成员地址反推宿主首地址 = `member_addr - offsetof`——**减偏移**，一条 `lea` 指令。优势：成员可以在任意位置、可以有多个。

两者运行时开销相同（都是一条算术指令），适用场景不同：`netdev_priv` 适合"一个宿主 + 一个私有数据块"的固定模式；`container_of` 适合"一个宿主 + 多个链表节点/回调钩子"的灵活模式。

</details>
