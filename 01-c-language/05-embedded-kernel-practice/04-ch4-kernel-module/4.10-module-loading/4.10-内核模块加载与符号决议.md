# 4.10 内核模块的加载与符号决议：内核视角

[← CH4 内核模块](../README.md) · [4.11 initcall 机制](../4.11-initcall/4.11-initcall机制全解.md) · [4.12 container_of 与侵入式链表](../4.12-container-of-list/4.12-container_of与侵入式链表.md)

> **本篇讲一个 `.ko` 从 `insmod` 到 `init_module()` 被调用的全过程，但只从 C 语言 / GNU 扩展视角看。** 它把 CH1/CH2 的工具放回内核真正用它的地方：
> - [4.11](../4.11-initcall/4.11-initcall机制全解.md) 讲了「内建版」`module_init` 用 `__attribute__((section))` 把函数指针收进 `.initcall6.init`；本篇讲「**模块版**」`module_init` 用 `__attribute__((alias))` 造出标准名 `init_module`，再由 modpost 生成的 `.mod.c` 用**指定初始化**填进嵌入的 `struct module` 实例——三件套（section + alias + 指定初始化）闭环。
> - [CH2 6.6](../../02-ch2-gnu-c-advanced/6.6-section/6.6.1-GNU-C编译器扩展关键字-__attribute__.md) 讲了 `__attribute__((section))` 的语法；本篇讲它怎么撑起**导出符号表**、**模块元信息**、**版本印章**三张表。
> - [CH6 链接脚本](../../06-ch6-toolchain-custom/4.14-链接脚本.md) 讲了 ELF 与链接概念；本篇讲内核怎么在**运行期**手写一个"动态链接器"：分配内存、拷贝段、解析未决符号、应用重定位。
>
> 全部结论有 WSL 实测（gcc 13.3 / clang 18.1.3 / x86-64）+ 内核 v6.6 源码核对（`kernel/module/main.c`、`include/linux/export.h`、`include/linux/module.h`、`scripts/mod/modpost.c`、`arch/x86/kernel/module.c`）。配套 demo 在 `demo/13-module/`。

## 本节讲什么

**`.ko` 是一段「没有 `ld.so` 的可重定位 ELF」**。用户态 `dlopen` 把脏活丢给 `ld-linux.so`；内核态没有这个帮手——`kernel/module/main.c` 的 `load_module()` 自己当动态链接器：读 ELF、分配可执行内存、拷段、把模块里那些**未决的**符号拿到内核的导出表里去查、拿到地址后手写重定位条目把 `CALL` 的位移 patch 上，最后调 `mod->init()`。

本篇回答一组具体问题：

| 问题 | 本篇回答 |
|---|---|
| `.ko` 和 `.so` 本质差在哪？ | `.ko` 是 `ET_REL`（可重定位），没有 `PT_LOAD`/`INTERP`/`DYNAMIC`；加载地址运行期才定，所以不能预链接 |
| `EXPORT_SYMBOL(fn)` 到底「注册」了什么？ | 一条记录进段里（v6.6 源码层是 `.export_symbol` 段的 asm 记录，modpost 转成 `__ksymtab` 段的 `struct kernel_symbol`）——和 initcall 同一个 `section` 套路 |
| 模块里 `printk` 这种「未决符号」怎么被找到？ | `resolve_symbol` → `find_symbol` 在 `__ksymtab` 上 `bsearch`——不是 `dlsym` |
| 重定位是谁做的？ | 内核手写的 `apply_relocate_add`：`val = S + A`（绝对）/ `S + A - P`（PC 相对）逐条写到 `loc`，跟 `ld` 在链接期做的一模一样，只是挪到了运行期 |
| 为什么换内核就得重编模块？ | `vermagic` 字符串和符号 CRC 两道门禁，防止 ABI 不兼容的模块被装进去 |
| `module_init(xxx_init)` 之后，`mod->init` 怎么就有了？ | `__attribute__((alias))` 让 `init_module` 成为 `xxx_init` 的别名；modpost 生成的 `.mod.c` 用指定初始化 `.init = init_module` 填进 `__this_module`——**编译期就定了，不是运行时查的** |
| 模块的 `.init.text` 加载完去哪了？ | init 跑完 `do_free_init` 把 `MOD_INIT_*` 三段页释放掉（对应内建版的 `free_initmem`） |

> 一句话：**用户态的「链接」在编译期由 `ld` 做完；内核模块的「链接」在加载期由 `module.c` 重做一遍。** 懂了这一点，`insmod` 就不再是黑魔法。

## 一、`.ko` 是什么：可重定位 ELF

### 1.1 与用户态动态库的根本差异

先看 `file` 和 `readelf` 怎么区分两者：

```
$ file hello.ko
hello.ko: ELF 64-bit LSB relocatable, x86-64, ...    ← relocatable（ET_REL）

$ file libfoo.so
libfoo.so: ELF 64-bit LSB shared object, x86-64 ...  ← shared object（ET_DYN）
```

| | 用户态 `.so` | 内核模块 `.ko` |
|---|---|---|
| ELF 类型 | `ET_DYN`（可共享） | **`ET_REL`（可重定位）** |
| 程序头 `PT_LOAD` | 有，划分段映射 | **无**（只有段头 `SHT_*`） |
| 入口定位 | `ld-linux.so` 读 `INTERP`/`DYNAMIC` | **没有 `ld.so`**，`module.c` 自己来 |
| 加载地址 | 通常固定（或 PIC 可浮动） | **运行期 `module_alloc` 才定**，所以必须可重定位 |
| 符号决议 | `dlsym` / `_dl_runtime_resolve` | `find_symbol` 在 `__ksymtab` 上 `bsearch` |
| 重定位 | 启动时 `ld` 应用 `R_X86_64_RELATIVE` 等 | **`insmod` 时 `apply_relocate_add` 手写应用** |
| 卸载 | `dlclose` | `rmmod` → `cleanup_module` |

**为什么 `.ko` 必须是可重定位的？** 因为模块的加载地址在 `module_alloc` 时才确定（vmalloc 区，地址每次都不同），链接器在编译期不可能知道最终地址，所以只能把所有「用到地址的地方」留成**重定位条目**，等加载时填。这跟用户态 `.o`（目标文件）是同一种东西——`.ko` 本质上就是一个**带模块元信息的目标文件**。

### 1.2 `.ko` 的关键段

`readelf -S hello.ko` 能看到的段，远比普通 `.o` 丰富——多了好几张「表」：

| 段 | 放什么 | 谁产生的 |
|---|---|---|
| `.text` `.data` `.rodata` `.bss` | 模块的代码/数据 | `gcc -c` |
| `.modinfo` | `vermagic=...` `license=...` 等元信息 | `MODULE_INFO` 宏（→ `__attribute__((section(".modinfo")))`） |
| `__ksymtab` / `__kcrctab` | 模块自己导出的符号表 + CRC | modpost 由 `.export_symbol` 转换而来 |
| `__ksymtab_gpl` / `__kcrctab_gpl` | GPL-only 导出 | 同上 |
| `.gnu.linkonce.this_module` | 嵌入的 `struct module __this_module` 实例 | modpost 生成的 `.mod.c` |
| `__versions` | 模块引用的每个外部符号的 CRC | modpost（`CONFIG_MODVERSIONS`） |
| `__param` `.init_array` `__jump_table` `__tracepoints_ptrs` … | 参数表/构造函数/jump label/tracepoint | 各自的宏 |

后面几节就按这几张表展开。先看加载总流程。

## 二、内核是「手写动态链接器」：`load_module` 全流程

### 2.1 `insmod` 到 `init_module` 的调用链

```
用户态: insmod hello.ko
   ↓ syscall init_module(umod, len, uargs)        [main.c:3038]
              或 finit_module(fd, uargs, flags)  [main.c:3169]
内核态:
   load_module(info, uargs, flags)              [main.c:2828]
     ├── module_sig_check        签名校验
     ├── elf_validity_cache_copy ELF 头/段合法性 + 缓存有用段
     ├── early_mod_check         vermagic / MODVERSIONS 预检
     ├── layout_and_allocate     排版各段大小 + module_alloc 分配 + move_module 拷段
     ├── add_unformed_module     进模块链表
     ├── percpu_modalloc        per-CPU 数据
     ├── find_module_sections    找 __ksymtab/__param/__jump_table 等可选段
     ├── check_export_symbol_versions  检查导出符号的 CRC
     ├── setup_modinfo           把 .modinfo 里的属性挂到 sysfs
     ├── simplify_symbols        把每个符号的 st_value 改成最终地址
     ├── apply_relocations  ← 本篇重头戏之一：手写应用 RELA
     ├── post_relocation         排序异常表、拷 percpu、加 kallsyms
     ├── flush_module_icache     改了代码要刷 I-cache
     ├── complete_formation      状态转 FORMED
     ├── prepare_coming_module   调模块的 notif（livepatch 等）
     ├── parse_args              解析模块参数
     ├── mod_sysfs_setup         sysfs 挂载
     └── do_init_module(mod)     [main.c:2501]
           ├── do_mod_ctors      构造函数
           ├── do_one_initcall(mod->init)  ← 真正调你的 init
           ├── state = MODULE_STATE_LIVE
           └── do_free_init      异步释放 MOD_INIT_* 三段
```

注意最后一步：`mod->init` 不是被「查找」出来的——它在 `__this_module` 里早就被指定初始化填好了（见第七节）。`do_init_module` 只是直接调用它。

### 2.2 与用户态 `dlopen` 的对照

| 阶段 | 用户态 `dlopen` | 内核 `load_module` |
|---|---|---|
| 读文件 | `ld.so` 自己读 | `copy_chunked_from_user` 拷到 vmalloc |
| 分配内存 | `mmap` 各 `PT_LOAD` | `module_memory_alloc` 给 7 类段各分一页对齐区 |
| 拷段 | `mmap` 时映射 | `move_module` 里 `memcpy` 逐段拷 |
| 符号决议 | `_dl_relocate_object` + `dlsym` | `simplify_symbols` + `resolve_symbol`（`bsearch` `__ksymtab`） |
| 重定位 | `ld.so` 应用 `R_X86_64_*` | `apply_relocate_add` 应用 `R_X86_64_*`（公式完全相同） |
| 调入口 | `.init`/构造函数 | `do_one_initcall(mod->init)` |
| 卸载释放 | `dlclose` + `munmap` | `rmmod` → `module_memfree`（init 段更早释放） |

> **结论：`module.c` 就是一个写在内核里的、精简版的 `ld-linux.so`。** 它没有 `PT_LOAD`/`DYNAMIC`/`PLT`/`GOT` 那套用户态机制——因为模块就在内核自己家里，不需要跨进程、不需要延迟绑定，加载时一次性 resolve 完即可。

## 三、`EXPORT_SYMBOL`：符号注册的 section 魔法

### 3.1 v6.6 的两阶段设计（重要：已重构）

这是本篇最容易踩过时资料的地方。**v6.4 之前**，`EXPORT_SYMBOL(fn)` 长这样（旧版）：

```c
struct kernel_symbol { unsigned long value; const char *name; const char *namespace; };
#define ___EXPORT_SYMBOL(sym, sec, ns) \
    static const char __kstrtab_##sym[] = #sym;          \
    static const char __kstrtabns_##sym[] = ns;          \
    __ksymtab sym: __attribute__((section("__ksymtab"+sec), used, aligned(4))) = \
        { (unsigned long)&sym, __kstrtab_##sym, __kstrtabns_##sym }
```

**v6.6 起重构了**（`include/linux/export.h`），源码层改用 `asm()` 直接往 `.export_symbol` 段塞扁平记录，不再用 C 级 `struct`：

```c
/* include/linux/export.h — v6.6 */
#define ___EXPORT_SYMBOL(sym, license, ns)        \
    .section ".export_symbol","a"   ASM_NL         \   ← 一个统一段
    __export_symbol_##sym:          ASM_NL         \
        .asciz license               ASM_NL        \   ← 许可证
        .asciz ns                    ASM_NL        \   ← 命名空间
        __EXPORT_SYMBOL_REF(sym)     ASM_NL        \   ← 符号地址（.quad/.long）
    .previous

#ifdef CONFIG_64BIT
#define __EXPORT_SYMBOL_REF(sym)  .balign 8  ASM_NL  .quad sym
#else
#define __EXPORT_SYMBOL_REF(sym)  .balign 4  ASM_NL  .long sym
#endif

/* C 上下文入口 */
#define __EXPORT_SYMBOL(sym, license, ns)            \
    extern typeof(sym) sym;          /* 类型检查 */  \
    __ADDRESSABLE(sym)              /* 取地址，防优化 */ \
    asm(__stringify(___EXPORT_SYMBOL(sym, license, ns)))
```

**源码层**每条 `EXPORT_SYMBOL(fn)` 在 `.export_symbol` 段留下一条 `[license][namespace][符号地址]` 的扁平记录。但这**还不是运行时查的表**——

### 3.2 modpost 把 `.export_symbol` 转成 `__ksymtab` + `__kcrctab`

运行时，`find_symbol()`（`main.c:302`）查的是 `__ksymtab` / `__kcrctab` 这两个段名（旧名字）：

```c
/* kernel/module/main.c:304 */
static const struct symsearch arr[] = {
    { __start___ksymtab, __stop___ksymtab, __start___kcrctab,        NOT_GPL_ONLY },
    { __start___ksymtab_gpl, __stop___ksymtab_gpl, __start___kcrctab_gpl, GPL_ONLY },
};
```

这说明 **`__ksymtab` 是 build tool（`scripts/mod/modpost`）在链接期由 `.export_symbol` 记录汇总出来的**。`struct kernel_symbol` 仍在用（定义在 `kernel/module/internal.h:35`），v6.6 还支持 PREL32 紧凑形态：

```c
/* kernel/module/internal.h:35 */
struct kernel_symbol {
#ifdef CONFIG_HAVE_ARCH_PREL32_RELOCATIONS
    int value_offset;        /* 4 字节，相对偏移 */
    int name_offset;
    int namespace_offset;    /* 合计 12 字节，无指针 */
#else
    unsigned long value;
    const char *name;
    const char *namespace;   /* 直接指针形态，24 字节 */
#endif
};
```

PREL32 形态下整个 `kernel_symbol` 只有 12 字节，且**不含绝对地址**——`value_offset` 是「符号地址相对 `value_offset` 自身位置的偏移」，加载时不用再 patch（和 [4.11 initcall](../4.11-initcall/4.11-initcall机制全解.md) 的 PREL32 同一个机制）。

### 3.3 运行时查找：`bsearch`（T1 实测）

`find_exported_symbol_in_section`（`main.c:276`）对排好序的 `__ksymtab` 做**二分查找**：

```c
sym = bsearch(fsa->name, syms->start, syms->stop - syms->start,
              sizeof(struct kernel_symbol), cmp_name);
```

`cmp_name` 内部调 `kernel_symbol_name(sym)`——PREL32 时是 `offset_to_ptr(&sym->name_offset)`，直接形态时是 `sym->name`。

**T1 demo** 用 C 级 `__attribute__((section("my_ksymtab")))` 直接模拟（跳过 PREL32，用直接指针，16 字节一条）。`sizeof(struct ksym)=16` 必须等于段步长，否则段对齐填充会让 `__stop-__start` 的计数错位（这是本批实测踩的第一个坑，见文末坑表）。

```
=== T1: EXPORT_SYMBOL section 收集 ===
my_ksymtab       收集到 4 个符号（NOT_GPL_ONLY）
my_ksymtab_gpl   收集到 1 个符号（GPL_ONLY）
sizeof(struct ksym) = 16（name+value，crc 分离）

--- 排序后的普通导出表（对应排序后的 __ksymtab） ---
  [0] kfree_core       @ 0x4012ff  crc=0x5cc7f876
  [1] kmalloc_core     @ 0x4012d6  crc=0xe6c1bc80
  [2] printk_core      @ 0x4012ad  crc=0x1adf95e5
  [3] schedule_core    @ 0x40131e  crc=0xfef5d8f2
--- 排序后的 GPL 导出表（对应 __ksymtab_gpl） ---
  [0] gpl_only_helper  @ 0x401333  crc=0xb4e1a67e

=== bsearch 查找（模拟模块 resolve_symbol） ===
  resolve printk_core      -> 0x4012ad  crc=0x1adf95e5
  resolve schedule_core    -> 0x40131e  crc=0xfef5d8f2
  resolve gpl_only_helper  -> 0x401333  crc=0xb4e1a67e
  resolve missing_symbol   -> NOT FOUND (ENOENT)

=== license 检查：非 GPL 模块查 GPL-only 符号 ===
  非 GPL 模块查 gpl_only_helper -> 拒绝（GPL_ONLY）

=== 通过决议的符号调用内核函数 ===
[kernel] hello from resolved printk_core
  kmalloc -> 0x176b9310, kfree 回收
```

注意几个和内核一一对应的设计点：

1. **CRC 单独放**（`fake_crc` 现算）——内核也是 `__ksymtab` 放 `{name,value}`、`__kcrctab` 单独放 `s32` CRC 数组，两表下标一一对应（`main.c:2106`：`mod->syms = section_objs(info,"__ksymtab",...); mod->crcs = section_addr(info,"__kcrctab")`）。
2. **加载时排序**——`__ksymtab` 段里的条目顺序由链接顺序决定，是无序的；内核启动时（`main.c` 的 `sort_symtab`）排序后才能 `bsearch`。T1 的 `qsort` 就是这一步。
3. **GPL 分表**——`EXPORT_SYMBOL` 进 `__ksymtab`（`NOT_GPL_ONLY`），`EXPORT_SYMBOL_GPL` 进 `__ksymtab_gpl`（`GPL_ONLY`）。非 GPL 模块查 GPL 表会被 `find_exported_symbol_in_section` 的 `if (!fsa->gplok && syms->license == GPL_ONLY) return false;` 挡掉。

## 四、符号决议：`resolve_symbol` + CRC

### 4.1 决议流程（`main.c:1109`）

模块里每个**未决符号**（`st_shndx == SHN_UNDEF`）都走一遍 `resolve_symbol`：

```c
static const struct kernel_symbol *resolve_symbol(struct module *mod,
        const struct load_info *info, const char *name, char ownername[])
{
    struct find_symbol_arg fsa = { .name = name, ... };
    if (!find_symbol(&fsa))       goto unlock;        /* 1. 查 __ksymtab */
    if (fsa.license == GPL_ONLY)  mod->using_gplonly_symbols = true;
    if (!inherit_taint(mod, fsa.owner, name)) ...;     /* 2. 污染传播 */
    if (!check_version(info, name, mod, fsa.crc))       /* 3. CRC 校验 */
        return ERR_PTR(-EINVAL);
    err = verify_namespace_is_imported(info, fsa.sym, mod);  /* 4. 命名空间 */
    err = ref_module(mod, fsa.owner);                  /* 5. 引用计数 */
}
```

| 步骤 | 失败后果 | 对应什么 |
|---|---|---|
| 1 `find_symbol` | `-ENOENT`，模块加载失败 | 符号根本没导出 |
| 2 `inherit_taint` | 不传染污染标记 | 非 GPL 模块用了被污染内核的符号 |
| 3 `check_version` | `-EINVAL`（`CONFIG_MODVERSIONS`） | CRC 对不上，ABI 变了 |
| 4 `verify_namespace` | `-ENXIO` | 没声明 `MODULE_IMPORT_NS(NS)` |
| 5 `ref_module` | `-EBUSY | 0` | 模块依赖计数 |

决议成功后，这个符号的 `st_value`（在 `simplify_symbols` 里）会被改成内核侧查到的真实地址，供下一步重定位使用。

### 4.2 CRC（`CONFIG_MODVERSIONS`）

不开 `MODVERSIONS` 时只比对 `vermagic` 字符串（见第六节）；开了之后，**每个引用的符号都单独比对 CRC**。`__versions` 段里每条是 `{ unsigned long crc; char name[MODULE_NAME_LEN]; }`（`include/linux/module.h` 的 `struct modversion_info`）。

CRC 由 `genksyms` 工具在编译期对符号的「签名」（参数类型、结构体布局）求出。如果内核改了 `printk` 的签名，CRC 就变，旧模块装不进去——**哪怕 `vermagic` 字符串一样**。

## 五、重定位：`apply_relocate_add` 的真实公式

### 5.1 分派（`main.c:1440`）

`apply_relocations` 遍历所有段，按重定位段类型分派：

```c
for (i = 1; i < info->hdr->e_shnum; i++) {
    unsigned int infosec = info->sechdrs[i].sh_info;
    if (info->sechdrs[i].sh_type == SHT_REL)
        err = apply_relocate(...);          /* 无 addend 的旧式 */
    else if (info->sechdrs[i].sh_type == SHT_RELA)
        err = apply_relocate_add(...);     /* 有 addend，x86-64 用这个 */
}
```

`apply_relocate` / `apply_relocate_add` 是 **arch-specific** 的——x86 定义在 `arch/x86/kernel/module.c`，arm64 在 `arch/arm64/kernel/module.c`。

### 5.2 x86-64 的核心公式（`arch/x86/kernel/module.c:166`）

```c
val = sym->st_value + rel[i].r_addend;          /* val = S + A */
switch (ELF64_R_TYPE(rel[i].r_info)) {
case R_X86_64_NONE:   continue;
case R_X86_64_64:     size = 8; break;           /* 写 8 字节绝对地址 */
case R_X86_64_32:     if (val != *(u32*)&val) goto overflow; size = 4; break;
case R_X86_64_32S:    if ((s64)val != *(s32*)&val) goto overflow; size = 4; break;
case R_X86_64_PC32:
case R_X86_64_PLT32:  val -= (u64)loc; size = 4; break;   /* PC 相对，最常见 */
case R_X86_64_PC64:   val -= (u64)loc; size = 8; break;
}
write(loc, &val, size);
```

两种公式记住即可：

| 公式 | 含义 | 典型重定位 | 用在哪 |
|---|---|---|---|
| `val = S + A` | 绝对地址 | `R_X86_64_64`/`_32`/`_32S` | 取函数指针、全局变量地址 |
| `val = S + A - P` | PC 相对（P=`loc`，即被 patch 处） | `R_X86_64_PC32`/`_PLT32` | **`CALL`/`JMP` 指令的 disp32**——模块里调 `printk` 走这个 |

`R_X86_64_PLT32`（type 4）在现代 gcc/clang 上是 `CALL` 未决符号的默认类型，和 `R_X86_64_PC32`（type 2）公式相同——`PLT32` 名字保留了用户态 PLT 的历史，在内核里没有 PLT，就是 PC 相对。

### 5.3 CALL 的 `addend = -4` 从哪来

一条 `call disp32` 是 `e8 xx xx xx xx`，5 字节。CPU 执行时 `PC` 已经指向下一条指令（`call` 地址 + 5）。但 ELF 的 `r_offset` 指向 `disp32` 字段（`call` 的第 2 字节），所以 `P = r_offset 地址`，而真正要算的相对量是 `S - (call_addr + 5) = S - (P + 4)`。所以 `addend = -4`，公式 `S + A - P = S + (-4) - P = S - (P+4) = S - (call+5)`。✓

### 5.4 实测：手搓 CALL + 应用 R_X86_64_PC32（T2）

T2 手写一段「模块 .text」（`call 0; ret`），构造一条 `R_X86_64_PC32 addend=-4` 指向 `target_printk`，应用公式后调用：

```
=== T2: 重定位公式 S+A / S+A-P ===
patch 前  disp32 = 0x00000000  (模块 call 未决议)
公式: val = S + A - P = 0x401236 + (-4) - 0x41ef1001 = 0xffffffffbe510231
patch 后  disp32 = 0xbe510231
运行期校验: call_addr+5+disp = 0x401236  == target_printk 0x401236 ? YES

--- 调用 patch 后的模块代码 ---
[resolved] module called printk via relocated call
```

`disp = 0xbe510231` 是负数（`0xffffffffbe510231` 的低 32 位）——因为 `target_printk` 在低地址、模块页在更高处，得往回跳。patch 后 `call_addr + 5 + disp` 精确等于 `target_printk`，调用成功。

> demo 用 `MAP_32BIT` 把模块页放在低 2GB——这恰恰对应内核的 `-mcmodel=kernel` 约束：**内核模块必须落在内核代码 ±2GB 内**，否则 `R_X86_64_PC32` 的 32 位位移装不下，会触发内核 `apply_relocate_add` 里的 `overflow` 分支，打印 `likely not compiled with -mcmodel=kernel` 并拒绝加载。

### 5.5 压轴：真实 ELF 重定位加载器（T5）

T5 编一个 `t5_module.c`（`extern void kernel_print(void); int module_entry(void){ kernel_print(); return 42; }`）成可重定位 `.o`，加载器**真解析 ELF**：找 `.text`/`.symtab`/`.strtab`/`.rela.text`，把 `.text` 拷到可执行页，逐条 `Elf64_Rela` 应用公式，最后调 `module_entry`。

`readelf -r t5_module.o` 显示那条 `CALL` 的重定位：

```
Relocation section '.rela.text' contains 1 entry:
  Offset  Info           Type            Sym.Value  Sym.Name + Addend
  000009  000900000004 R_X86_64_PLT32   0000000000 kernel_print - 4
```

加载器跑出来：

```
=== T5: ELF 重定位加载器，加载 t5_module.o ===
ELF: e_type=1 (1=ET_REL 可重定位) e_shnum=22 e_shstrndx=21
section: .text#1 .symtab#19 .strtab#20 .rela.text#2

--- 符号表（10 个）---
  [ 8] module_entry     st_shndx=1            （定义在 .text）
  [ 9] kernel_print     st_shndx=0 (UNDEF 未决) ← 要 resolve

.text 复制到可执行页 0x41753000，size=20

--- apply_relocate_add：1 条重定位 ---
  [0] R_X86_64_PLT32 kernel_print(UNDEF) -> 内核 resolve S=0x401376
      -> 写 0xffffffffbecae369 到 loc=0x41753009 (A=-4)

--- do_init_module：调 module_entry @ 0x41753000 ---
[kernel_print] 模块通过 ELF 重定位成功调到了我
module_entry 返回 42
```

这就是「内核当动态链接器」的最小可信实例：**未决符号 → 查内核符号表 → 算位移 → patch → 调用**，全在用户态复现，没有任何 `dlopen`。

## 六、vermagic 与版本校验

### 6.1 `vermagic` 字符串怎么拼（`include/linux/vermagic.h`）

```c
#define VERMAGIC_STRING                       \
    UTS_RELEASE " "                           \   ← 内核版本，如 "6.6.0"
    MODULE_VERMAGIC_SMP MODULE_VERMAGIC_PREEMPT \
    MODULE_VERMAGIC_MODULE_UNLOAD MODULE_VERMAGIC_MODVERSIONS \
    MODULE_ARCH_VERMAGIC MODULE_RANDSTRUCT
```

每个宏在对应 `CONFIG` 开时拼上一个标记，关时为空串：

| 标记 | 开启条件 | 值 |
|---|---|---|
| `SMP` | `CONFIG_SMP` | `"SMP "` |
| `preempt` | `CONFIG_PREEMPT_BUILD` | `"preempt "` |
| `preempt_rt` | `CONFIG_PREEMPT_RT` | `"preempt_rt "` |
| `mod_unload` | `CONFIG_MODULE_UNLOAD` | `"mod_unload "` |
| `modversions` | `CONFIG_MODVERSIONS` | `"modversions "` |
| arch 自定义 | `MODULE_ARCH_VERMAGIC` | 各架构 |

### 6.2 `.modinfo` 段收集（`MODULE_INFO` 宏）

modpost 生成的 `.mod.c` 头几行（`scripts/mod/modpost.c:1927`）：

```c
MODULE_INFO(vermagic, VERMAGIC_STRING);   ← 版本印章进 .modinfo
MODULE_INFO(name, KBUILD_MODNAME);
```

`MODULE_INFO(tag, info)` 展开成 `__attribute__((section(".modinfo")))` 的字符串 `"tag=info"`。加载时 `get_modinfo(info, "vermagic")` 线性扫描 `.modinfo` 段，取出值，跟内核自己的 `VERMAGIC_STRING` 比对——不一致直接 `-ENOEXEC`。

### 6.3 实测（T3）

T3 用 `section("modinfo")`（无点，方便 GNU ld 给边界符号）模拟 `.modinfo` 段收集 + vermagic 门禁：

```
--- 原始 .modinfo 段内容（按 entry 遍历） ---
  vermagic=6.6.0 SMP preempt mod_unload modversions
  name=mymod
  license=GPL
  ...
--- vermagic 门禁检查 ---
  内核 vermagic : 6.6.0 SMP preempt mod_unload modversions
  模块 vermagic : 6.6.0 SMP preempt mod_unload modversions
  结果: 匹配，允许加载

--- 模拟一个版本不符的模块 ---
  模块 vermagic : 6.5.0 SMP mod_unload
  结果: 不匹配，拒绝（防止 ABI 不兼容）
```

> vermagic 是**粗粒度**门禁（整串比对，SMP/preempt/modversions 任何一个变了都拒），CRC 是**细粒度**门禁（每个符号单独判）。两者叠加，才能在「内核重编了某个符号」时精确拒绝而不是一刀切。

## 七、`__this_module`：指定初始化 + alias 闭环

这是本篇把 CH1/CH2 三件套串起来的关键。`mod->init` **不是运行时查表查出来的**。

### 7.1 `module_init` 的模块版（`include/linux/module.h`）

```c
#ifdef MODULE   /* 编译成可加载模块 */
#define module_init(initfn)                                \
    static inline initcall_t __maybe_unused __inittest(void) { return initfn; }  /* 编译期类型检查 */
    int init_module(void) __copy(initfn)                  \
        __attribute__((alias(#initfn)));                  /* ← alias 造标准名 */
    ___ADDRESSABLE(init_module, __initdata);
```

`__attribute__((alias("initfn")))` 让 `init_module` 成为 `initfn`（你写的 `xxx_init`）的**别名**——同一个地址、同一个代码，只是挂了两个符号名。这样内核加载器只认标准名 `init_module`，不必知道你起的名。（内建版则走 `__initcall` 进 `.initcall6.init` 段，见 [4.11](../4.11-initcall/4.11-initcall机制全解.md)。）

### 7.2 modpost 生成的 `.mod.c` 模板（`scripts/mod/modpost.c:1930`）

```c
__visible struct module __this_module
__section(".gnu.linkonce.this_module") = {     /* ← section 放进专属段 */
    .name = KBUILD_MODNAME,
    .init = init_module,                       /* ← 指定初始化，填 alias */
    .exit = cleanup_module,                    /* ← 同理 */
    .arch = MODULE_ARCH_INIT,
};
```

这一段把三件套全用上了：

| 元素 | 出处 | 作用 |
|---|---|---|
| `__section(".gnu.linkonce.this_module")` | [CH2 6.6](../../02-ch2-gnu-c-advanced/6.6-section/6.6.1-GNU-C编译器扩展关键字-__attribute__.md) | 把 `struct module` 实例放进专属段，`--gc-sections` 不敢删（`__used`+被引用） |
| `.init = init_module` | [CH1 6.2](../../01-ch1-gnu-c-basics/6.2-designated-init/6.2-指定初始化.md) | 指定初始化，只填关心的字段，其余零值 |
| `init_module` 是 `xxx_init` 的 alias | [CH2 6.9](../../02-ch2-gnu-c-advanced/6.9-weak/6.9.4-属性声明-alias.md) | 标准名指向用户函数 |

**所以 `mod->init` 在编译期就定好了**：它就是 `__this_module.init` 这个函数指针字段，值为 `init_module`（== `xxx_init`）的地址。`load_module` 把 `.gnu.linkonce.this_module` 段 `memcpy` 到最终地址（`move_module`，`main.c:2222`），重定位只修正这个绝对地址（PREL32 形态下连这步都省了）。`do_init_module` 直接 `mod->init()` 即可。

### 7.3 实测（T4）

```
=== T4: __this_module 指定初始化 + alias ===
--- 地址对照（alias 让两个名指向同一处） ---
  my_driver_init  @ 0x401156
  init_module    @ 0x401156  (alias) -> 与 my_driver_init 相同
  my_driver_exit @ 0x40116f
  cleanup_module @ 0x40116f  (alias) -> 与 my_driver_exit 相同

--- __this_module 内容（编译期指定初始化的结果） ---
  name = my_driver
  init = 0x401156  exit = 0x40116f

--- do_init_module 调 mod->init()（经 alias 回到用户函数） ---
[my_driver_init] 模块初始化
  init 返回 0
--- rmmod 调 mod->exit() ---
[my_driver_exit] 模块卸载
```

`init_module` 和 `my_driver_init` 地址完全相同（alias 生效）。`__this_module.init` 存的就是这个地址，调它等于调用户写的 `my_driver_init`。

## 八、模块的内存布局与 `.init` 释放

### 8.1 v6.6 的 7 类段（`enum mod_mem_type`）

v6.6 把旧版 `struct module_layout { core, init }` 两段拆成了 **7 类**（`include/linux/module.h`）：

```c
enum mod_mem_type {
    MOD_TEXT = 0,        /* 核心代码（常驻） */
    MOD_DATA,            /* 核心数据（可写） */
    MOD_RODATA,          /* 核心只读数据 */
    MOD_RO_AFTER_INIT,   /* init 后变只读（如 __jump_table） */
    MOD_INIT_TEXT,       /* init 代码（用完释放） */
    MOD_INIT_DATA,
    MOD_INIT_RODATA,
    MOD_MEM_NUM_TYPES,
};
```

`struct module` 里 `struct module_memory mem[MOD_MEM_NUM_TYPES]`，每类 `{ void *base; unsigned int size; }`。`module_get_offset_and_type`（`main.c:1481`）排版时按 `sh_addralign` 对齐每个段，`move_module`（`main.c:2229`）给每类各 `module_memory_alloc` 一页对齐区，再 `memcpy` 各段过去。

### 8.2 init 段的释放（`do_init_module`，`main.c:2501`）

```c
freeinit->init_text   = mod->mem[MOD_INIT_TEXT].base;    /* 存起来 */
freeinit->init_data   = mod->mem[MOD_INIT_DATA].base;
freeinit->init_rodata = mod->mem[MOD_INIT_RODATA].base;
...
if (mod->init != NULL)
    ret = do_one_initcall(mod->init);                     /* 调你的 init */
...
/* 异步释放 init 三段（对应内建版的 free_initmem） */
```

`do_free_init` 走 workqueue 异步 `module_memfree`（`vfree`）这三个区——这就是 `__init` 修饰的函数/数据「只能调一次」的根因：init 跑完，`MOD_INIT_TEXT` 的页就还回去了，再调就是踩野内存。这点和 [4.11 内建版 `__init` 段释放](../4.11-initcall/4.11-initcall机制全解.md) 完全同构，只是内建版在 boot 后一次性 `free_initmem`，模块版在每次 `rmmod`... 不，模块版 init 段在**加载完成就立即释放**（不等 rmmod）。

| | 内建 `__init` | 模块 `__init` |
|---|---|---|
| 段名 | `.init.text`（合并进 vmlinux 的 `.init`） | `.init.text`（模块自己）→ `MOD_INIT_TEXT` |
| 释放时机 | boot 结束 `free_initmem` | `do_init_module` 跑完 init 后异步 `do_free_init` |
| 释放单位 | 整个 `.init` 段 | 模块的 3 个 `MOD_INIT_*` 区 |

<details><summary>代码自测（点击展开）</summary>

**Q1：`module_init(xxx_init)` 在模块版和内建版分别展开成什么？为什么模块版不用 `section`？**

<details><summary>答案</summary>

- **内建版**（`#ifndef MODULE`）：`module_init(x) → __initcall(x);`，即把 `x` 的函数指针收进 `.initcall6.init` 段，boot 时 `do_initcalls` 遍历段调用。用 `section`（见 [4.11](../4.11-initcall/4.11-initcall机制全解.md)）。
- **模块版**（`#else`）：`module_init(x) → int init_module(void) __attribute__((alias(#x)));`，造一个标准名 `init_module` 指向 `x`。**不用 `section`**，因为模块不需要 boot 时批量调用——它有自己的 `struct module __this_module` 实例，`.init = init_module` 在编译期就填好了，`load_module` 找到 `__this_module` 就能拿到入口。

两者殊途同归：内建靠链接器段收集（批量、boot 时），模块靠 alias+指定初始化（单个、加载时）。
</details>

**Q2：模块里 `printk` 是未决符号，它什么时候、被谁、用什么算法找到的？**

<details><summary>答案</summary>

- **什么时候**：`load_module` → `simplify_symbols` 阶段，遍历 `.symtab`，对每个 `st_shndx == SHN_UNDEF` 的符号调 `resolve_symbol`。
- **被谁**：`resolve_symbol` → `find_symbol`（`main.c:302`）。
- **什么算法**：`bsearch` 在排好序的 `__ksymtab`（普通）和 `__ksymtab_gpl`（GPL-only）上二分查找。找到后还要过 CRC（`check_version`）和命名空间（`verify_namespace_is_imported`）两关。
- 之后该符号的 `st_value` 被改成查到的内核地址，供 `apply_relocate_add` 用。
</details>

**Q3：`R_X86_64_PC32` 的 `addend` 为什么是 `-4`？为什么内核模块要用 `-mcmodel=kernel` 编？**

<details><summary>答案</summary>

`call disp32` 是 5 字节，`r_offset` 指向 `disp32`（第 2 字节），`P = r_offset 地址`。CPU 算的目标是 `S - (call_addr + 5) = S - (P + 4)`。公式 `val = S + A - P` 要等于 `S - (P+4)`，故 `A = -4`。

`-mcmodel=kernel`：内核代码在地址空间高区（负地址区），模块必须落在内核 ±2GB 内，`R_X86_64_PC32` 的 32 位位移才装得下。否则 `apply_relocate_add` 走 `overflow` 分支，报 `likely not compiled with -mcmodel=kernel` 拒绝加载。本批 T2/T5 用 `MAP_32BIT` 复现了这个约束。
</details>

**Q4：v6.6 的 `EXPORT_SYMBOL` 和旧版有什么不同？为什么 `.export_symbol` 段在 `find_symbol` 里看不到？**

<details><summary>答案</summary>

v6.4 前用 C 级 `__attribute__((section("__ksymtab")))` 直接放 `struct kernel_symbol`；v6.6 重构成 `asm()` 往 `.export_symbol` 段塞扁平 `[license][namespace][符号地址]` 记录。

`.export_symbol` 是**源码层中间态**，在 `.o` 里；`find_symbol` 查的 `__ksymtab`/`__kcrctab` 是 **build tool（modpost）在链接期汇总**出来的运行时表。两阶段：源码 `.export_symbol`（每条导出一记录）→ modpost 汇总成 `__ksymtab`（`struct kernel_symbol` 数组，PREL32 形态 12B）+ `__kcrctab`（`s32` CRC 数组）。
</details>

**Q5：`mod->init` 是运行时查表查出来的吗？为什么？**

<details><summary>答案</summary>

不是。`module_init(xxx_init)` 用 `__attribute__((alias))` 造出 `init_module`（== `xxx_init`）；modpost 生成的 `.mod.c` 用**指定初始化** `.init = init_module` 把它填进 `__this_module`（`.gnu.linkonce.this_module` 段里的 `struct module` 实例）。所以 `mod->init` 在编译期就定了。`load_module` 只需把 `__this_module` 段 `memcpy` 到最终地址，`do_init_module` 直接 `mod->init()`。它**不是未决符号**，不需要 `resolve_symbol`。

三件套闭环：`section`（放专属段）+ 指定初始化（CH1 6.2）+ alias（CH2 6.9）。
</details>
