## 本节讲什么

打开任何一个 Linux 驱动，你都会看到这样的代码：

```c
static int __init my_driver_init(void) { ... }
module_init(my_driver_init);
```

这行 `module_init` 看起来像函数调用，但它**从来不会被谁显式调用**。它到底什么时候跑？答案是：**链接器和启动循环替你找了它**。

`module_init` 是一个宏，它的展开取决于一个编译开关 `MODULE`：

- **编译成 `.ko` 模块时**（`MODULE` 已定义）：它用 [6.9 的 `alias` 属性](../../02-ch2-gnu-c-advanced/6.9-weak/6.9.4-属性声明-alias.md)把你的函数变成名为 `init_module` 的全局符号别名。内核的 `load_module` 从 ELF 符号表找到 `init_module`，存到 `mod->init`，`insmod` 时调用 `do_one_initcall(mod->init)`。
- **编译进 `vmlinux` 内建时**（`MODULE` 未定义）：它用 [6.6 的 `section` 属性](../../02-ch2-gnu-c-advanced/6.6-section/6.6.1-GNU-C编译器扩展关键字-__attribute__.md)把函数指针放进 `.initcall6.init` 段。链接脚本把这个段的起止地址导出为 `__initcall6_start`/`__initcall7_start`，内核启动时用 `for (fn = __initcall6_start; fn < __initcall7_start; fn++) (*fn)();` 依次执行。

同一个宏，两种完全不同的实现，由 `#ifdef MODULE` 切换。这是 CH1/CH2 学过的 `section` + `alias` 两个属性联合用到极致的地方。

本节用**用户态模拟 + 内核 v6.6 源码核对**把这条链路从头到尾钉死。

## 一、`module_init` 的两个版本

### 1.1 模块版：`alias` 属性

`include/linux/module.h`（v6.6，line 125-130）：

```c
#define module_init(initfn)                    \
    int init_module(void) __copy(initfn)       \
        __attribute__((alias(#initfn)));       \
    ___ADDRESSABLE(init_module, __initdata);
```

展开 `module_init(my_init)` 后，等价于：

```c
int init_module(void) __attribute__((alias("my_init")));
```

`alias` 属性（见 [6.9.4](../../02-ch2-gnu-c-advanced/6.9-weak/6.9.4-属性声明-alias.md)）让 `init_module` 和 `my_init` **指向同一个地址**。`__copy` 复制目标函数的属性（如 `__init`、`noinline`），`___ADDRESSABLE` 生成一个引用 `init_module` 符号的数据项，确保 `--gc-sections` 不会删掉它。

**实测 T5**（用户态用 `dlsym` 模拟内核的符号查找）：

```c
static int my_driver_init(void) { printf("  my_driver_init\n"); return 0; }
int init_module(void) __attribute__((alias("my_driver_init")));

/* 模拟内核 load_module 从 ELF 符号表找 init_module */
void *handle = dlopen(NULL, RTLD_NOW);
initcall_t fn = (initcall_t)dlsym(handle, "init_module");
fn();   /* 实际执行 my_driver_init */
```

```
$ nm t5 | grep -E "init_module|my_driver_init"
0000000000001340 T init_module          ← 大写 T：全局可见
0000000000001340 t my_driver_init        ← 小写 t：局部，同地址
```

**关键**：`init_module` 和 `my_driver_init` 是**同一个地址**。内核不需要知道你写的函数叫什么名字——它只认 `init_module` 这个固定符号名。`alias` 属性帮你把任意名字的函数挂到这个固定符号上。

### 1.2 内建版：`section` 属性

`include/linux/init.h`（v6.6，line 88）：

```c
#ifndef MODULE
...
#define __initcall(fn) device_initcall(fn)          /* device_initcall → __define_initcall(fn, 6) */
#define module_init(x)  __initcall(x);
```

展开 `module_init(my_init)` 后，等价于：

```c
static initcall_t __initcall_my_init __used
    __attribute__((section(".initcall6.init"))) = my_init;
```

也就是把 `my_init` 的地址放进 `.initcall6.init` 段。**这里没有 `alias`**——函数本身还是 `static`，只是它的地址被一个段里的指针变量引用。

**实测 T1**：

```c
#define SIM_INIT(fn) \
    static initcall_t __attribute__((used)) \
        __attribute__((section(".initcall6.init"))) __sim_##fn = fn

SIM_INIT(early_console);
SIM_INIT(device_probe);
```

```
$ readelf -S t1.o | grep initcall
  [ 9] .initcall6.init   PROGBITS   0000000000000000  00000280
       0000000000000020  0000000000000000   WA       0     0     8
$ nm t1.o | grep sim
0000000000000000 d __sim_initcall_late_policy
0000000000000008 d __sim_initcall_device_probe
0000000000000010 d __sim_initcall_core_driver
0000000000000018 d __sim_initcall_early_console
```

段大小 `0x20 = 32 字节 = 4 × 8`（4 个指针，每个 8 字节）。**链接器自动按出现顺序排列**——不需要你手工写注册表。

### 1.3 双版本对比

| | 模块版（`.ko`） | 内建版（`vmlinux`） |
|---|---|---|
| 编译开关 | `MODULE` 已定义 | `MODULE` 未定义 |
| 核心属性 | `alias`（6.9.4） | `section`（6.6） |
| 函数可见性 | `init_module` 是全局符号（大写 T） | 函数仍 `static`（小写 t），只有段内指针引用它 |
| 谁来找函数 | 内核 `load_module` 用 `find_symbol("init_module")` | 链接器收集段，启动循环遍历 |
| 何时执行 | `insmod` 时 `do_one_initcall(mod->init)` | 启动时 `do_initcalls()` 遍历段 |
| 级别参数 | **无效**——所有 `xxx_initcall` 宏退化成 `module_init` | **有效**——不同宏放进不同级别段 |
| 卸载 | `rmmod` 时 `mod->exit`（`cleanup_module` 别名） | 不可卸载（`__init` 段已释放） |

> **模块版的关键**：`module_init` 不关心你的函数名，它只认 `init_module` 这个固定符号。`alias` 属性把任意名字的函数挂到这个固定符号上——这就是模块的"约定优于配置"。
>
> **内建版的关键**：函数指针被链接器自动收集进段，不需要注册代码——这就是"链接期语义"（见 [6.6](../../02-ch2-gnu-c-advanced/6.6-section/6.6.1-GNU-C编译器扩展关键字-__attribute__.md)）。

## 二、`__define_initcall` 宏链：从宏到段的全过程

内建版的 `module_init(x)` 展开成 `__initcall(x)` → `device_initcall(fn)` → `__define_initcall(fn, 6)`。完整的宏链在 `include/linux/init.h`（v6.6）：

```
__define_initcall(fn, 6)
  → ___define_initcall(fn, 6, .initcall6)
    → __unique_initcall(fn, 6, ".initcall6", __initcall_id(fn))
      → ____define_initcall(fn, stub, name, ".initcall6.init")
        → static initcall_t name __used
              __attribute__((section(".initcall6.init"))) = fn;
```

最终产物就是一行：

```c
static initcall_t __unique_name __used
    __attribute__((section(".initcall6.init"))) = fn;
```

`__used`（即 `__attribute__((used))`）告诉编译器"这个变量看起来没被引用，但别删它"——因为引用它的代码在另一个文件（`init/main.c` 的 `do_initcalls`），编译器在单个文件里看不到引用。

### 2.1 级别宏全家福

`init.h`（v6.6，line 289-321）定义了所有级别宏：

| 宏 | 段名 | 级别 | 典型用途 |
|---|---|---|---|
| `early_initcall(fn)` | `.initcallearly.init` | SMP 前 | 极早期，只用于内建 |
| `pure_initcall(fn)` | `.initcall0.init` | 0 | 纯初始化（无依赖） |
| `core_initcall(fn)` | `.initcall1.init` | 1 | 核心子系统 |
| `core_initcall_sync(fn)` | `.initcall1s.init` | 1s | 同级别 sync（在该级别所有 initcall 之后） |
| `postcore_initcall(fn)` | `.initcall2.init` | 2 | post-core |
| `postcore_initcall_sync(fn)` | `.initcall2s.init` | 2s | |
| `arch_initcall(fn)` | `.initcall3.init` | 3 | 架构相关 |
| `arch_initcall_sync(fn)` | `.initcall3s.init` | 3s | |
| `subsys_initcall(fn)` | `.initcall4.init` | 4 | 子系统 |
| `subsys_initcall_sync(fn)` | `.initcall4s.init` | 4s | |
| `fs_initcall(fn)` | `.initcall5.init` | 5 | 文件系统 |
| `fs_initcall_sync(fn)` | `.initcall5s.init` | 5s | |
| `rootfs_initcall(fn)` | `.initcallrootfs.init` | rootfs | rootfs 挂载 |
| `device_initcall(fn)` | `.initcall6.init` | 6 | **设备驱动（最常用）** |
| `device_initcall_sync(fn)` | `.initcall6s.init` | 6s | |
| `late_initcall(fn)` | `.initcall7.init` | 7 | 最晚期 |
| `late_initcall_sync(fn)` | `.initcall7s.init` | 7s | |
| `console_initcall(fn)` | `.con_initcall` | con | 控制台（特殊段） |

`__initcall(fn)` 是 `device_initcall(fn)` 的别名——也就是**默认级别 6**。

### 2.2 模块版的级别退化

`include/linux/module.h`（v6.6，line 111-123）——**模块版所有级别宏全部退化成 `module_init(fn)`**：

```c
#define early_initcall(fn)      module_init(fn)    /* 模块里没有 early */
#define core_initcall(fn)       module_init(fn)
#define subsys_initcall(fn)     module_init(fn)
#define device_initcall(fn)     module_init(fn)
#define late_initcall(fn)       module_init(fn)
/* ... 全部一样 */
```

**为什么？** 模块是运行期加载的，不存在"启动顺序"概念——`insmod` 时刻就是它的"启动"。所有模块的 init 函数都在 `do_init_module` 里被直接调用，没有级别区分。

> **误区**：在模块代码里写 `subsys_initcall(fn)` 以为能控制加载顺序——**没用**，它就是 `module_init(fn)`。模块的加载顺序由 `insmod`/`modprobe` 的调用顺序和依赖关系决定，与 initcall 级别无关。

### 2.3 LTO 的特殊处理

`CONFIG_LTO_CLANG` 开启时（`init.h` line 222-237），`__initcall_section` 会为每个 initcall 生成**独立的段名**（如 `.initcall6.init.0`、`.initcall6.init.1`），再由 `scripts/link-vmlinux.sh` 生成的链接脚本指定顺序。

原因：LTO（Link-Time Optimization）下编译器**不保证链接顺序**等于源码出现顺序。为了保留正确的 initcall 顺序，每个指针必须放在自己的段里，由链接脚本显式排序。

> 这是"链接顺序决定执行顺序"（见第六节）在 LTO 下的妥协——用更多段换确定性。

## 三、链接脚本：段是怎么被收集成表的

### 3.1 `INIT_CALLS` 宏

`include/asm-generic/vmlinux.lds.h`（v6.6，line 913-927）：

```
#define INIT_CALLS_LEVEL(level)                \
    __initcall##level##_start = .;             \  /* 导出段起始符号 */
    KEEP(*(.initcall##level##.init))            \  /* 收集该级别所有指针 */
    KEEP(*(.initcall##level##s.init))           \  /* 收集 sync 变体 */

#define INIT_CALLS                             \
    __initcall_start = .;                       \  /* 全局起始 */
    KEEP(*(.initcallearly.init))                \  /* early */
    INIT_CALLS_LEVEL(0)                          \  /* pure */
    INIT_CALLS_LEVEL(1)                          \  /* core */
    INIT_CALLS_LEVEL(2)                          \
    INIT_CALLS_LEVEL(3)                          \
    INIT_CALLS_LEVEL(4)                          \
    INIT_CALLS_LEVEL(5)                          \
    INIT_CALLS_LEVEL(rootfs)                     \  /* rootfs（在 5 和 6 之间） */
    INIT_CALLS_LEVEL(6)                          \  /* device */
    INIT_CALLS_LEVEL(7)                          \  /* late */
    __initcall_end = .;                           /* 全局结束 */
```

链接后，`__initcall0_start` 到 `__initcall7_start` 是 8 个地址，分别指向各级别段的起始。`do_initcalls` 用 `__initcall_end` 作为总结束。

### 3.2 `KEEP()` 不能省

`KEEP()` 告诉链接器"即使这个段看起来没被引用，也保留它"。如果没有 `KEEP`，`--gc-sections` 会把整个 initcall 段当死代码删掉——因为除了 `do_initcalls` 的循环，没有任何代码"直接"引用这些指针。

**实测 T4**（用户态模拟 `--gc-sections` 的陷阱）：

```c
/* k1/k2/k3 只被 initcall 段引用，没有其他引用 */
static int k1(void) { printf("  k1\n"); return 0; }
SIM_KEEP(k1);  /* 把 k1 的指针放进 .initcall_keep 段 */

/* 链接脚本用了 KEEP */
.initcall_keep : {
    __initcall_keep_start = .;
    KEEP(*(.initcall_keep))
    __initcall_keep_end = .;
}
```

不带 `--gc-sections` 时，一切正常（`count=3`，`k1`/`k2`/`k3` 都打印了）。但加上 `--gc-sections` 后：

```
$ gcc -O2 -Wl,--gc-sections -T keep_test.lds t4_keep.c -o t4_gc_keep
$ ./t4_gc_keep
Segmentation fault (core dumped)
```

**为什么崩？** `KEEP` 保留了 `.initcall_keep` 段里的**指针**，但 `k1`/`k2`/`k3` 的函数代码没有其他引用，被 `--gc-sections` 删掉了。段里指针还在，指向的代码已经没了 → 调用时 segfault。

```
$ nm t4_gc_keep | grep -E "k1|keep"
0000000000400210 D __initcall_keep_end     ← 段边界符号在
00000000004001f8 D __initcall_keep_start
0000000000400208 d __keep_k1               ← 指针变量在（值是 k1 的地址）
0000000000400000 t k1                      ← 但 k1 的代码已被 gc 删成空壳
```

这就是内核用 `___ADDRESSABLE(init_module, __initdata)` 的原因——它生成一个引用 `init_module` 符号的数据项，让 `--gc-sections` 看到"这个符号被引用了"，不会删函数代码。

> **关键区分**：`KEEP` 保留**段内容**（指针本身）；`___ADDRESSABLE` / `__used` 保留**指针指向的目标**（函数代码）。两者缺一不可。

### 3.3 用户态复刻 `do_initcalls`

**实测 T2**——完整复刻链接器段收集 + 启动循环：

```c
/* 链接脚本 initcall.lds */
.initcall : {
    __initcall_start = .;
    KEEP(*(.initcall6.init))
    __initcall_end = .;
}
```

```c
/* C 代码 */
extern initcall_t __initcall_start[];
extern initcall_t __initcall_end[];

static void do_initcalls(void) {
    initcall_t *fn;
    for (fn = __initcall_start; fn < __initcall_end; fn++)
        (*fn)();
}
```

```
$ ./t2

  [0] calling 0x400170 ...   device drivers  ret=0
  [1] calling 0x400150 ...   filesystems     ret=0
  [2] calling 0x400130 ...   network stack   ret=0
  [3] calling 0x400110 ...   irq subsystem   ret=0
  [4] calling 0x4000f0 ...   console up      ret=0
```

段大小 `0x28 = 40 字节 = 5 × 8`，正好 5 个函数指针。`readelf -S` 显示 `.initcall` 段的地址范围跟运行时打印的 `__initcall_start`/`__initcall_end` 完全一致。

## 四、启动循环：`do_initcalls` 的真面目

### 4.1 分级遍历

`init/main.c`（v6.6）的核心结构：

```c
/* 各级别段的起始地址表 */
static initcall_entry_t *initcall_levels[] __initdata = {
    __initcall0_start, __initcall1_start, __initcall2_start, __initcall3_start,
    __initcall4_start, __initcall5_start, __initcall6_start, __initcall7_start,
    __initcall_end,
};

/* 各级别的名字（用于日志） */
static const char *initcall_level_names[] __initdata = {
    "pure", "core", "postcore", "arch", "subsys", "fs", "device", "late",
};

/* 执行某一级别的所有 initcall */
static void __init do_initcall_level(int level, char *command_line)
{
    initcall_entry_t *fn;
    parse_args(initcall_level_names[level], ...);   /* 该级别的内核命令行参数 */
    trace_initcall_level(initcall_level_names[level]);
    for (fn = initcall_levels[level]; fn < initcall_levels[level+1]; fn++)
        do_one_initcall(initcall_from_entry(fn));
}

/* 依次执行所有级别 */
static void __init do_initcalls(void)
{
    int level;
    for (level = 0; level < ARRAY_SIZE(initcall_levels) - 1; level++)
        do_initcall_level(level, saved_command_line);
}
```

**实测 T3**（8 级别模拟）：

```
$ ./t3
level 0 (pure):   [pure]   ret=0
level 1 (core):   [core]   ret=0
level 2 (postcore): [post] ret=0
level 3 (arch):   [arch]   ret=0
level 4 (subsys): [subsys] ret=0
level 5 (fs):     [fs]     ret=0
level 6 (device): [device] ret=0
level 7 (late):   [late]   ret=0
```

### 4.2 `do_one_initcall` 的容错

`init/main.c`（v6.6，line 1222）：

```c
int __init_or_module do_one_initcall(initcall_t fn)
{
    int count = preempt_count();
    int ret;

    if (initcall_blacklisted(fn))    /* 黑名单检查 */
        return -EPERM;

    do_trace_initcall_start(fn);
    ret = fn();                      /* 真正调用 */
    do_trace_initcall_finish(fn, ret);

    /* 检查 initcall 是否破坏了抢占计数和中断状态 */
    if (preempt_count() != count) {
        sprintf(msgbuf, "preemption imbalance ");
        preempt_count_set(count);
    }
    if (irqs_disabled()) {
        strlcat(msgbuf, "disabled interrupts ", sizeof(msgbuf));
        local_irq_enable();           /* 帮你恢复中断 */
    }
    WARN(msgbuf[0], "initcall %pS returned with %s\n", fn, msgbuf);
    return ret;
}
```

**实测 T7**（失败处理）：

```
$ ./t7
  ok_init: success              ret=0   → 正常
  warn_init: ret=1              → WARNING ret=1 (kernel: suspicious but continues)
  err_init: ret=-ENODEV          → ERROR -19 (kernel: continues boot)
  after_err: still runs!        → 失败后同级别的 initcall 照样执行
  total=4 failed=2 (boot continues regardless)
```

| 返回值 | 内核行为 | 模块行为 |
|---|---|---|
| `0` | 正常，继续 | 正常，模块加载成功 |
| `>0` | `pr_warn` "suspicious"，继续 | `pr_warn`，但模块**仍然加载** |
| `<0` | `pr_warn` + 继续启动 | `goto fail`，**卸载模块**，返回错误码 |

> **内核不因 initcall 失败而中止启动**——因为一个驱动初始化失败不应该让整个系统无法启动。但模块加载是显式请求，失败就该回滚。

### 4.3 `initcall_from_entry`：PREL32 相对偏移

`init.h`（v6.6，line 122-135）——有两个版本：

```c
#ifdef CONFIG_HAVE_ARCH_PREL32_RELOCATIONS
typedef int initcall_entry_t;    /* 32 位整数：存的是偏移 */

static inline initcall_t initcall_from_entry(initcall_entry_t *entry)
{
    return offset_to_ptr(entry);   /* (char*)entry + *entry */
}
#else
typedef initcall_t initcall_entry_t;  /* 直接存函数指针（8 字节） */

static inline initcall_t initcall_from_entry(initcall_entry_t *entry)
{
    return *entry;                 /* 直接解引用 */
}
#endif
```

`CONFIG_HAVE_ARCH_PREL32_RELOCATIONS` 在 ARM64、x86-64 等"支持 PC 相对寻址"的架构上开启。用 32 位相对偏移代替 64 位绝对地址：

| | 绝对地址 | PREL32 相对偏移 |
|---|---|---|
| 每项大小 | 8 字节 | 4 字节 |
| 重定位类型 | `R_X86_64_64`（绝对） | `R_X86_64_PC32`（PC 相对） |
| 1000 项占用 | 8000 字节 | 4000 字节 |
| 位置无关 | 否（需重定位） | 是（偏移不变） |

**实测 T8**：

```
$ ./t8
  sizeof(initcall_t)   = 8 (absolute addr)
  sizeof(int32_t)      = 4 (PREL32 offset)
  savings per entry    = 4 bytes

  on 1000 initcalls:
    absolute: 8000 bytes
    PREL32:   4000 bytes
    saved:    4000 bytes
```

> 内核有上千个 initcall，PREL32 能省几 KB。更重要的是 PREL32 是**位置无关**的——内核 KASLR（地址空间随机化）重定位时不需要修改这些条目，因为偏移量不随基址变化。

## 五、`__init` 段的生与死

### 5.1 段的划分

| 属性 | 段名 | 内容 | 释放时机 |
|---|---|---|---|
| `__init` | `.init.text` | init 函数的代码 | `free_initmem()` |
| `__initdata` | `.init.data` | init 用数据 | `free_initmem()` |
| `__initconst` | `.init.rodata` | init 用只读数据 | `free_initmem()` |
| `__exit` | `.exit.text` | exit 函数代码 | 内建时链接器可删；模块保留 |

`free_initmem()` 在启动完成后调用（`init/main.c`），把 `.init.text`/`.init.data` 整段的页还给 buddy allocator。嵌入式上能回收几百 KB 到几 MB。

### 5.2 释放后不能再用

**实测 T6**（模拟 `free_initmem` 后再调用）：

```
$ ./t6
--- boot phase ---
  late init       ← initcall 正常执行
  middle init
  early init
--- post-boot: free_initmem ---
  free_initmem: marking .init.text as freed
--- calling init again (should warn) ---
  BUG: accessing freed init memory at 0x400270!   ← 野指针
  BUG: accessing freed init memory at 0x400250!
  BUG: accessing freed init memory at 0x400230!
```

> **误区**：在驱动里把**运行期也要调用的函数**标了 `__init`——启动后该函数地址指向已释放的页，调用就是踩野内存。`__init` 只能标"启动时调用一次，之后永不再用"的函数。

## 六、链接顺序：同级别内的执行顺序

`init.h` 的注释（v6.6，line 196）：

> Ordering inside the subsections is determined by link order.

**同一级别内，链接器先收集到的指针先执行。** 链接顺序由 `Makefile` 里 `obj-y` 的顺序决定。

**实测 T10**（多源文件链接顺序对照）：

```c
/* t10_a.c */                          /* t10_b.c */                        /* t10_c.c */
int a_driver(void) { ... }              int b_driver(void) { ... }           int c_driver(void) { ... }
SIM_INIT(a_driver);                    SIM_INIT(b_driver);                  SIM_INIT(c_driver);
```

```
--- 链接顺序: a b c ---
  [0] 0x4000f0 ->   a_driver       ← a 先
  [1] 0x400110 ->   b_driver
  [2] 0x400130 ->   c_driver

--- 链接顺序: c b a ---
  [0] 0x4000f0 ->   c_driver       ← c 先
  [1] 0x400110 ->   b_driver
  [2] 0x400130 ->   a_driver
```

**同一个源码，只是链接时 `.o` 的顺序不同，执行顺序就变了。** 这就是为什么内核的 `Makefile` 里 `obj-y` 的顺序有时很重要——两个驱动如果有隐式依赖（A 必须在 B 前初始化），同级别内只能靠链接顺序保证。

> **跨级别**有显式的级别保证（`core` 一定在 `device` 前），**同级别内**只有链接顺序。如果同级别内有依赖，要么提升到不同级别，要么在 `Makefile` 里调整 `obj-y` 顺序。

## 七、`module_exit`：卸载的镜像

模块版 `module_exit` 是 `module_init` 的镜像：

```c
/* module.h v6.6 */
#define module_exit(exitfn)                     \
    static inline exitcall_t __maybe_unused __exittest(void) \
        { return exitfn; }                     \
    void cleanup_module(void) __copy(exitfn)   \
        __attribute__((alias(#exitfn)));        \
    ___ADDRESSABLE(cleanup_module, __exitdata);
```

`cleanup_module` 是 `exitfn` 的别名。`rmmod` 时内核调用 `mod->exit`（即 `cleanup_module`）。

内建版 `module_exit` 无效——内建代码不可卸载，`__exit` 函数在链接时会被删除（`--gc-sections` 或链接脚本 `DISCARD`）。

| | `module_init` | `module_exit` |
|---|---|---|
| 模块版别名 | `init_module` | `cleanup_module` |
| 内建版 | 放进 `.initcall6.init` 段 | 无效（内建不可卸载） |
| 调用时机 | `insmod` / 启动循环 | `rmmod` |

## 八、完整链路：从源码到执行

把前面所有环节串起来，**内建驱动**的完整链路：

```
源码: module_init(my_init)
  ↓ 预处理 (#ifndef MODULE)
展开: static initcall_t __name __used __attribute__((section(".initcall6.init"))) = my_init;
  ↓ 编译
目标文件: .initcall6.init 段里有一个指向 my_init 的指针
  ↓ 链接 (vmlinux.lds 的 INIT_CALLS_LEVEL(6))
vmlinux: __initcall6_start..__initcall7_start 之间有这个指针
  ↓ 启动 (do_initcalls → do_initcall_level(6))
执行: (*fn)() → my_init()
  ↓ 启动完成 (free_initmem)
释放: .init.text 段（含 my_init 代码）被释放
```

**模块驱动**的完整链路：

```
源码: module_init(my_init)
  ↓ 预处理 (#ifdef MODULE)
展开: int init_module(void) __attribute__((alias("my_init")));
  ↓ 编译
hello.ko: ELF 符号表里有 init_module 符号（地址 = my_init）
  ↓ insmod (load_module)
内核: find_symbol("init_module") → mod->init = init_module
  ↓ do_init_module
执行: do_one_initcall(mod->init) → my_init()
  ↓ rmmod
卸载: mod->exit (= cleanup_module) → my_exit()
```

## 九、常见误区

| # | 误区 | 真相 | 实测验证 |
|---|---|---|---|
| 1 | "`module_init(fn)` 是函数调用" | 不是。模块版是 `alias` 声明，内建版是 `section` 放置。两者都不产生调用指令 | T1/T5/T9 |
| 2 | "initcall 按源码定义顺序执行" | 同级别内按**链接顺序**执行，不是源码顺序 | T10 |
| 3 | "`KEEP` 会保留函数代码" | `KEEP` 只保留段内容（指针）。函数代码要靠 `___ADDRESSABLE` 或 `__used` 保留 | T4 segfault |
| 4 | "`__init` 函数可以多次调用" | `free_initmem` 后段被释放，再调用就是野指针 | T6 |
| 5 | "模块里写 `subsys_initcall` 能控制加载级别" | 模块版所有级别宏退化成 `module_init`，级别参数无效 | 源码 module.h:111-123 |
| 6 | "initcall 失败会中止启动" | 内核继续启动，只是 `pr_warn`。模块加载失败才回滚 | T7 |
| 7 | "PREL32 只省空间" | 还省**重定位表项**（PC 相对不需要绝对重定位），KASLR 时不用修改 | T8 |
| 8 | "`early_initcall` 在模块里也能用" | 只用于内建，且在 SMP 初始化前跑 | 源码 init.h:289 |
| 9 | "所有架构都用 8 字节存 initcall 指针" | ARM64/x86-64 用 PREL32（4 字节偏移） | T8 |
| 10 | "`console_initcall` 和 `device_initcall` 在同一段" | `console_initcall` 放在独立的 `.con_initcall` 段 | 源码 init.h:321 |

## HFT / 嵌入式关联

### HFT：模块化交易系统的初始化顺序

HFT 行情解析系统通常分多层：网卡抓包 → 协议解码 → 策略引擎 → 风控。它们的初始化有严格依赖：

```c
/* 级别 3：架构相关——映射网卡 BAR、注册 MSI-X */
arch_initcall(nic_bar_map);

/* 级别 4：子系统——协议解码框架注册 */
subsys_initcall(protocol_decoder_register);

/* 级别 6：设备——策略引擎挂接到解码框架 */
device_initcall(strategy_engine_init);

/* 级别 7：最晚——风控（依赖前面所有层就绪） */
late_initcall(risk_control_init);
```

级别保证了依赖顺序，不需要手工维护初始化表。如果用裸机（CH3），你得自己写 `init_fn_t init_table[] = {...}` 并手工排序——`initcall` 机制让链接器替你做这件事。

### 嵌入式：`__init` 释放回收内存

嵌入式设备内存紧张（如 64MB 的网关设备）。`__init` 段可能占几百 KB——这些代码只启动时跑一次，之后就是死空间。`free_initmem` 把这些页还给 buddy，可用于运行期分配。

```c
/* 查看释放了多少 */
$ dmesg | grep "Memory:.*available"
Memory: 500000K/524288K available (8000K kernel code, 1200K rwdata, 3000K rodata, 1200K init, ...)
                                                              ↑ 这 1200K 启动后被释放
```

### 嵌入式：自定义 initcall 级别

某些嵌入式框架（如 buildroot 的 rootfs init script）会自定义初始化级别。理解了 `__define_initcall` 的展开机制，你可以用同样的模式构建自己的初始化框架：

```c
/* 自定义初始化框架 */
typedef int (*my_init_t)(void);
#define MY_INIT(fn, prio) \
    static my_init_t __used __attribute__((section(".myinit" #prio))) \
        __myinit_##fn = fn

/* 链接脚本收集所有 .myinit* 段 */
```

这就是 initcall 机制的通用化——**链接器替你写注册代码**。

<summary>代码自测（点击展开）</summary>

**Q1：`module_init(fn)` 编译成 `.ko` 和编译进 `vmlinux` 时，展开结果有什么不同？**

<details>
<summary>答案</summary>

- **`.ko`（`MODULE` 已定义）**：用 `alias` 属性，把 `fn` 变成名为 `init_module` 的全局符号别名。内核 `load_module` 从 ELF 符号表找 `init_module`。
- **`vmlinux`（`MODULE` 未定义）**：用 `section` 属性，把 `fn` 的地址放进 `.initcall6.init` 段。链接脚本收集段，`do_initcalls` 遍历执行。

两者都不产生函数调用指令。`module_init` 从来没有被谁显式调用——它被链接器或符号查找找出来。
</details>

**Q2：为什么链接脚本里 `KEEP(*(.initcall6.init))` 不能省 `KEEP`？**

<details>
<summary>答案</summary>

`--gc-sections` 会删除"没有被任何代码直接引用"的段。initcall 段里的函数指针只被 `do_initcalls` 的循环引用——循环在另一个文件（`init/main.c`），编译器在单个文件里看不到引用。没有 `KEEP`，整个 initcall 段会被当死代码删掉。

`KEEP` 保留段内容（指针），但**不保留指针指向的函数代码**——函数代码要靠 `___ADDRESSABLE` 或 `__used` 保留（见 T4 的 segfault 教学点）。
</details>

**Q3：在模块驱动里写 `subsys_initcall(fn)`，和写 `device_initcall(fn)` 有区别吗？**

<details>
<summary>答案</summary>

**没区别**。模块版（`#ifdef MODULE`）所有级别宏都退化成 `module_init(fn)`（见 `module.h:111-123`）。模块是运行期加载的，不存在"启动顺序"——`insmod` 时刻就是它的"启动"。

级别只在**内建**时有效。如果你需要控制模块的加载顺序，只能靠 `modprobe` 的依赖关系（`depends:` in `.modinfo`）。
</details>

**Q4：`__init` 修饰的函数在 `free_initmem` 之后被调用会怎样？**

<details>
<summary>答案</summary>

该函数的代码在 `.init.text` 段，`free_initmem` 把整段的页释放给 buddy allocator。之后再调用该地址就是踩野内存——可能踩到新分配的数据，也可能触发 page fault（取决于页表是否还在）。

这就是 `__init` 只能标"启动时调用一次"的函数的原因。运行期也要调用的函数不能标 `__init`。
</details>

**Q5：`PREL32` 相对偏移比绝对地址省了什么？**

<details>
<summary>答案</summary>

两样：

1. **空间**：每项 4 字节 vs 8 字节，省一半。内核上千个 initcall，省几 KB。
2. **重定位**：绝对地址需要 `R_X86_64_64` 重定位项（KASLR 时要逐个修改）；PREL32 用 `R_X86_64_PC32`（PC 相对），偏移量不随基址变化，**不需要重定位**。内核 KASLR 重定位时少了几千个重定位项要处理。
</details>

**Q6：两个同级别的 initcall 有依赖关系（A 必须在 B 前跑），怎么保证顺序？**

<details>
<summary>答案</summary>

三种办法：

1. **提升级别**：把 A 放到更早的级别（如 `subsys_initcall`），B 保持 `device_initcall`。
2. **sync 变体**：A 用 `device_initcall`，B 用 `device_initcall_sync`——sync 在该级别所有非 sync initcall 之后执行。
3. **调整链接顺序**：在 `Makefile` 里把 `obj-y` 里 A 的 `.o` 放到 B 前面——同级别内链接顺序决定执行顺序。

最推荐的是方法 1（显式级别）或方法 2（sync）。方法 3 脆弱——`Makefile` 顺序不直观，容易在重构时被破坏。
</details>

</details>
