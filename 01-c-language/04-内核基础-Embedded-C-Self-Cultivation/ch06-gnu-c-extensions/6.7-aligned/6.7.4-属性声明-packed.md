# 6.7.4 属性声明：packed

## 本节讲什么

**`__attribute__((packed))`** 取消结构体成员间 **padding**，使 `sizeof` 等于成员紧凑之和（仍可能有位域规则）。用于 **网络协议头、Flash 配置块、寄存器映射**；代价是 **未对齐访问** 与 **性能**。

## 要点

```c
struct eth_hdr_packed {
    uint8_t  dst[6];
    uint8_t  src[6];
    uint16_t ethertype;
} __attribute__((packed));

_Static_assert(sizeof(struct eth_hdr_packed) == 14, "");
```

```c
/* 仅 packed 单个成员 — 较少用 */
struct mix {
    int a;
    short b __attribute__((packed));
};
```

| 风险 | 说明 |
|------|------|
| 未对齐 load/store | ARMv7 需 `__attribute__((aligned(1)))` 或 memcpy |
| 原子性 | packed 内 int 可能跨 cache line |
| ABI | 勿跨模块混用 packed/非 packed 同一 layout |

```bash
gcc -std=gnu11 -o demo01 demo01_packed.c
./demo01
# 对比 packed vs 默认 struct 的 sizeof 与 offsetof
```

```c
/* 安全读 unaligned — 内核/ DPDK 常用 */
uint16_t get_be16(const void *p)
{
    uint16_t v;
    memcpy(&v, p, sizeof(v));
    return rte_be_to_cpu_16(v);
}
```

- **demo01** 直观打印布局
- 能不用 packed 则优先 **手动 padding + static assert**

## 常见陷阱

1. **未对齐访问在 ARMv5 及以下触发 alignment fault**
   `packed` 结构体去掉 padding，`int` 字段地址可能不在 4 字节边界。ARMv5 及更早架构**硬件不支持**未对齐 word 访问，直接 `p->ethertype` 触发异常（SIGBUS）。ARMv6+ 默认开启 unaligned access 支持，但**性能差**——硬件拆成两次访问。x86 永远支持但跨 cache line 仍慢。**安全做法**：用 `memcpy` 或 `get_unaligned_be16()`。

2. **`packed` 结构体不能整体赋值（部分情况）**
   `struct eth_hdr_packed a = b;` 看起来合法，但若编译器优化下用了 SIMD load 指令（要求对齐）会触发对齐异常。`packed` 结构体的赋值、传参（按值）在某些 ABI 下行为未定义或低效。**惯例**：packed 结构体只通过**指针**操作，永远不按值传递。

3. **取 `packed` 成员地址 → 指针类型对齐假设错位**
   `uint16_t *p = &hdr->ethertype;` 看似合法，但 `p` 的类型声明"承诺" 2 字节对齐，实际可能任意地址。**指向 packed 成员的指针必须显式标 `__packed` 或转 `void *` 后用 memcpy**。GCC 的 `-Waddress-of-packed-member` 警告（默认不开）专门查这个坑。

## 自测题

**1.（选择）** 以下哪种情况**必须**用 `packed`？
- A. 结构体用于跨平台文件存储
- B. 结构体映射网络协议头/硬件寄存器
- C. 想节省内存
- D. 想提高访问速度

<details><summary>答案</summary>

**B**。网络协议头、硬件寄存器、Flash 配置块的**二进制布局是外部约定**（由协议/硬件 spec 决定），padding 会破坏 wire format。packed 去掉 padding 强制匹配 spec。A 错——跨平台存储应用文本或显式序列化（protobuf）；C 错——packed 节省几字节但牺牲性能，不值得；D 完全相反，packed **降低**速度。

</details>

**2.（判断）** `struct s { char c; int i; } __attribute__((packed));` 后，`sizeof(struct s) == 5`。

<details><summary>答案</summary>

**对**。`c` 1 字节 + `i` 4 字节，packed 去掉 3 字节 padding，总和 5。但**结构体尾部 padding** 是否被去掉取决于编译器——GCC 的 `packed` 会**去掉尾部 padding**，所以 `sizeof == 5`。然而数组中 `s[1]` 仍要满足"下一元素起始对齐"（无 packed 数组对齐为 1），所以无额外 padding。**坑**：把这种结构体强转为 `int *` 取 `s[0].i` 即未对齐访问。

</details>

**3.（踩坑）** 代码：
```c
struct pkt { uint8_t d[6]; uint16_t len; } __attribute__((packed));
struct pkt *p = (struct pkt *)buf;
uint16_t *lp = &p->len;        /* ① */
uint16_t v = *lp;              /* ② */
```
在 x86 上正常，移植到 ARMv5 后 ② 偶发 SIGBUS。为什么？如何修？

<details><summary>答案</summary>

**`&p->len` 地址未对齐**（packed 后 `len` 在偏移 6，非 2 字节边界）。`uint16_t *lp` 类型声明对齐 2，编译器在 ARMv5 上可能生成 `ldrh`（要求对齐）指令，访问未对齐地址触发异常。x86 硬件支持未对齐访问，所以"正常"——这是**典型的"在 x86 上能跑，移植就崩"坑**。
修复：
```c
uint16_t v;
memcpy(&v, &p->len, sizeof(v));      /* 安全：memcpy 按字节拷贝 */
v = ntohs(v);                         /* 网络字节序转主机 */
```
或用内核/DPDK 提供的 `get_unaligned_be16(&p->len)`。**原则**：packed 结构体成员**永远不要取地址给类型化指针**，用 `memcpy` 或 `get_unaligned`。

</details>

**4.（应用）** 设计一个网络协议头结构体，要求：① 二进制布局严格匹配 spec（14 字节）；② 安全访问 `ethertype` 字段；③ 不会触发未对齐访问。

<details><summary>答案</summary>

```c
#include <stdint.h>
#include <string.h>

struct eth_hdr {
    uint8_t  dst[6];
    uint8_t  src[6];
    uint16_t ethertype;   /* 偏移 12 */
} __attribute__((packed));
_Static_assert(sizeof(struct eth_hdr) == 14, "eth header size");

/* 安全读 ethertype */
static inline uint16_t eth_type(const struct eth_hdr *h) {
    uint16_t v;
    memcpy(&v, &h->ethertype, sizeof(v));
    return v;     /* 调用方按需 ntohs */
}

/* 安全写 ethertype */
static inline void eth_set_type(struct eth_hdr *h, uint16_t v) {
    memcpy(&h->ethertype, &v, sizeof(v));
}
```
要点：
- `packed` + `_Static_assert` 保证 wire format。
- `memcpy` 是编译器**允许内联为单条 load/store** 的（如果目标支持未对齐），零开销且可移植。
- 不直接暴露 `&h->ethertype` 给外部，强制走 helper。
- DPDK `rte_ether_hdr` 就是类似设计，提供 `rte_be_to_cpu_16()` 包装。

</details>
