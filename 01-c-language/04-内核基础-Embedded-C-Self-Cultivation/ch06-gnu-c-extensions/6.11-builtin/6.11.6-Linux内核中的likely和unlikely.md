# 6.11.6 Linux内核中的likely和unlikely

## 本节讲什么

内核 **`likely`/`unlikely`** 包装 **`__builtin_expect`**，给分支预测器**编译期提示**：标记某分支"大概率/小概率"走，编译器据此重排代码——把 unlikely 错误路径移到函数末尾，保持 hot path 在 cache 内连续。本节讲原理、用法、误用代价。

## 要点

### `__builtin_expect` 原理

```c
long __builtin_expect(long exp, long c);
```

返回 `exp` 本身（运行时无副作用），但**告诉编译器"运行时 `exp == c` 的概率高"**。编译器据此：
1. 重排基本块——把"非 c 分支"移到远处（函数末尾或冷段）。
2. 优化指令 cache 局部性——hot path 连续。
3. 影响条件移动 vs 分支跳转指令选择。

### 内核 / DPDK 包装

```c
/* include/linux/compiler.h */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)
```

```c
/* DPDK — rte_branch_prediction.h */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)
```

`!!(x)` 把任意表达式归一化为 0/1，避免 `__builtin_expect` 第二参数被误用。

### 典型用法

```c
/* 错误路径标 unlikely */
if (unlikely(!ptr))
    return -EINVAL;

if (unlikely(ptr->magic != MAGIC))
    goto corrupt;

/* 成功路径标 likely */
if (likely(nb_rx > 0)) {
    /* burst 处理收到的包 */
}
```

### 编译器生成的代码差异

```c
int f(int *p) {
    if (unlikely(!p)) return -1;
    return *p;
}
```
编译后（ARM64 概览）：
```
cbz   x0, .Lerror      /* 错误路径跳远 */
ldr   w0, [x0]
ret
.Lerror:
mov   w0, #-1
ret
```
hot path（`ldr/ret`）连续在前面，`.Lerror` 在末尾——icache 友好。**不标** `unlikely` 时编译器也可能猜（基于 profile 或静态启发式），但**不可靠**；显式 `unlikely` 强制。

### 使用条件

- **profile 验证**后再加——猜错会**降低**性能。
- 仅在**热路径**上有意义——冷函数加 `likely` 无用。
- `__builtin_expect` 不影响正确性，只影响性能。

| 用法 | 说明 |
|------|------|
| 错误检查 `if (unlikely(!ptr))` | 错误路径移出 hot path |
| 快速路径 `if (likely(ret == 0))` | 保持成功路径连续 |
| `switch` 优化 | 标 unlikely case 移到末尾 |
| DPDK 收包 `if (likely(nb_rx > 0))` | 数据面热路径 |

- **不要**在用户态盲目复制：profile 为准
- GCC `-fprofile-generate/-fprofile-use`（PGO）可自动生成类似信息

## 常见陷阱

1. **猜错方向 → 性能反而下降**
   `unlikely(x)` 标在**实际大概率**分支上，编译器把该分支移到冷区，每次跳转都**破坏 icache**。代价：5-20% 性能损失（视分支频率）。**必须**用 profile（`perf record` / `gcov`）确认概率再加，否则别加。某分支 50/50 时**不要标**——`__builtin_expect` 只在明显偏斜时有用。

2. **`likely(unlikely(...))` 嵌套无意义**
   `__builtin_expect` 是编译期提示，嵌套调用最后只保留**最外层**。更隐蔽的是 `if (likely(a) && unlikely(b))`——编译器对复合条件分支预测有独立逻辑，`likely`/`unlikely` 标注会被部分忽略。**惯例**：每个 `if` 标注**一个** `likely` 或 `unlikely`，作用于整体条件。

3. **误以为 `likely` 改变语义**
   `if (likely(p != NULL))` 与 `if (p != NULL)` 在**语义上完全等价**——`likely` 只影响代码生成，不影响判断结果。新手误以为 `likely` "强制走某分支"是错的：运行时若 `p == NULL`，仍进入 NULL 分支。`__builtin_expect` 返回值等于第一参数，无运行时副作用。

## 自测题

**1.（选择）** `__builtin_expect(exp, c)` 的运行时行为是？
- A. 强制 `exp == c`
- B. 返回 `exp`，给编译器分支预测提示
- C. 调用硬件分支预测器
- D. 改变条件判断结果

<details><summary>答案</summary>

**B**。`__builtin_expect(exp, c)` 运行时返回 `exp` 本身，**无任何副作用**——只是编译器内置函数，告诉优化器"`exp == c` 概率高"，据此重排代码。运行时**不强制**任何行为，分支仍按真实条件走。误以为它能"强制走某分支"是常见错误。

</details>

**2.（判断）** 在所有 `if` 上加 `likely` 或 `unlikely` 是优化代码的好习惯。

<details><summary>答案</summary>

**错**。`likely`/`unlikely` 只在**分支明显偏斜**且**位于热路径**时有用。盲目标注：
- 50/50 分支无益（编译器本就难猜）；
- 猜错方向反而降低性能（icache 失效）；
- 冷代码标注无意义（不在热路径，重排没意义）。
正确做法：先用 `perf record` / `gcov` 找出热路径上的偏斜分支，再针对性标注。或直接用 PGO（`-fprofile-use`）让编译器自动生成。

</details>

**3.（踩坑）** DPDK 收包循环：
```c
uint16_t n = rte_eth_rx_burst(port, q, bufs, BURST);
if (likely(n == 0)) continue;     /* 标 likely */
process(bufs, n);
```
性能**比不加 likely 还差**。为什么？

<details><summary>答案</summary>

**方向标反了**。`rte_eth_rx_burst` 在收包路径上**通常有包**（否则轮询浪费），`n > 0` 是大概率事件。标 `likely(n == 0)` 等于告诉编译器"通常没包"，把 `continue`（hot path）排到前面，但实际运行时 `n == 0` 为假，跳到 `process`——**每次都跳转**，icache 失效。正确：
```c
if (unlikely(n == 0)) continue;  /* 空轮询是少数 */
process(bufs, n);
```
**教训**：`likely`/`unlikely` 必须 profile 验证。DPDK 的 `rte_branch_prediction.h` 文档明确说"仅用于已 profile 的热路径"。

</details>

**4.（应用）** 给定函数：
```c
int parse(const char *s) {
    if (s == NULL) return -EINVAL;
    if (*s == '\0') return -EINVAL;
    /* 解析... */
    return 0;
}
```
用 `likely`/`unlikely` 优化，并说明预期收益。

<details><summary>答案</summary>

```c
int parse(const char *s) {
    if (unlikely(s == NULL))    return -EINVAL;
    if (unlikely(*s == '\0'))   return -EINVAL;
    /* 解析 hot path... */
    return 0;
}
```
预期收益：
1. 两个错误检查标 `unlikely`，编译器把错误处理移到函数末尾，hot path（解析逻辑）连续在前面——icache 友好。
2. 错误路径不占 cache（除非真触发），减少 cache footprint。
3. **前提**：调用方通常传合法字符串——这是 `parse` 这类 API 的典型契约。若 profile 显示 50% 调用传 NULL，标注反方向。
**注意**：在非热函数上标注收益微小——`parse` 若每秒被调用百万次才有意义，偶尔调用一次无差别。

</details>
