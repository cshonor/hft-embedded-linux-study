# 10.4.4 Linux系统调用接口

## 本节讲什么

如何在 Linux 上 **查看、调用、追踪系统调用**？本节介绍 **`syscall()` 直调**、**man 2**、**strace** 与常见编号，帮助从 RTOS 思维过渡到 **10.10 进程/线程** 与 **10.5 文件系统** 的 Linux 实践。

## 要点

**man 页面分区**：

| 节 | 内容 |
|----|------|
| **man 2** | 系统调用 |
| **man 3** | libc 函数 |
| **man 7** | 概述（如 `man 7 syscalls`） |

**直接 syscall 示例**（教学用，生产用 libc）：

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <sys/syscall.h>

long n = syscall(SYS_write, 1, "hi\n", 3);
```

**strace 追踪**：

```bash
strace -f ./demo_app          # 列出实际 syscall
strace -e trace=open,read,write ./demo_app
```

典型输出解读：

```
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY) = 3
mmap(NULL, 8192, PROT_READ|PROT_WRITE, ...) = 0x...
write(1, "hello\n", 6)                  = 6
```

**常见 syscall 与 **10.5/10.10** 映射**：

| syscall | 作用 | 章节 |
|---------|------|------|
| `open/read/write/close` | 文件 I/O | **10.5** |
| `fork/execve/wait` | 进程 | **10.10.1** |
| `clone` | 线程 | **10.10.2** |
| `mmap/munmap/brk` | 内存 | **10.9** |
| `ioctl` | 设备控制 | **10.7** |

**错误码**：

- 失败返回 `-1`，`errno` 为 `EAGAIN`、`EINVAL`、`EACCES` 等
- 内核与用户约定 **负返回值** 转 errno（架构相关）

**与 RTOS 对照**：

| RTOS | Linux |
|------|-------|
| `xTaskCreate` | `clone` + pthread 库 |
| `xQueueSend` | `pipe`/`socket`/`eventfd` |
| `vTaskDelay` | `nanosleep` |
| 无 | 每进程独立 FD 表、VMA |

**性能注意**：

- 高频路径用 **vDSO**（`gettimeofday` 无 syscall）
- DPDK **user-space driver** 避免 `read/write` 网络包

## 常见陷阱

1. **`syscall(SYS_xxx, ...)` 与 libc 包装返回值不一致**
   libc 包装（如 `printf`、`malloc`）失败通常返回 -1 并设 `errno`；**裸 `syscall()`** 返回**内核原始值**——成功返回 ≥0，失败返回**负 errno**（如 -EINVAL）。新手写 `if (syscall(SYS_xxx, ...) == -1) perror(...)` 永远不触发——实际返回是 -22。**正确**：`long r = syscall(...); if (r < 0) { errno = -r; perror(...); }`。生产代码用 libc 包装，裸 syscall 仅教学。

2. **`strace` 默认只追踪主线程 → 多线程漏 syscall**
   `strace ./app` 只追主线程，多线程程序的子线程 syscall 漏掉。**`-f`** 选项跟随 fork/clone，追踪所有线程。坑：用户以为 strace 看到全部 syscall，实际只看 1/N。生产调试多线程必加 `-f`：`strace -f -e trace=futex ./app`。

3. **系统调用号跨架构不同 → 移植崩**
   `SYS_write` 在 x86-64 是 1，在 x86-32 是 4，在 ARM 是 4，在 AArch64 是 64。代码硬编码 `syscall(1, ...)` 在 x86-64 是 write，移植到 ARM 即崩——`1` 在 ARM 是 `exit`！**必须**用 `<sys/syscall.h>` 的 `SYS_xxx` 宏，让头文件按架构展开正确编号。**坑**：BPF/seccomp 过滤规则也按系统调用号——跨架构 seccomp 配置必须每架构独立。

## 自测题

**1.（选择）** `gettimeofday()` 在现代 Linux 上**通常不**进入内核态，原因是？
- A. 内核不支持
- B. 通过 vDSO 在用户态完成
- C. 编译器优化掉了
- D. 时间不需要内核参与

<details><summary>答案</summary>

**B**。vDSO（virtual Dynamic Shared Object）是内核映射到每个进程用户态的共享页，包含 `gettimeofday`、`clock_gettime`、`getcpu` 等高频只读 syscall 的用户态实现。内核维护的时钟数据结构通过 vDSO 暴露给用户态，进程**直接读共享页**即得时间，无 syscall 开销。**坑**：旧内核或某些架构不支持 vDSO，回退到真 syscall。性能敏感代码不要假设一定走 vDSO——profile 验证。DPDK 等用户态轮询框架通常不用 `gettimeofday`，用 TSC 寄存器（`rdtsc`）直接读硬件计数器。

</details>

**2.（判断）** `fork()` 后子进程继承父进程所有打开的文件描述符。

<details><summary>答案</summary>

**对**。`fork` 复制进程地址空间（COW）和文件描述符表——子进程继承父进程所有打开的 fd，**指向同一打开文件描述**（`struct file`），共享文件偏移量。父子都 `read(fd)` 会互相推进偏移量。**坑**：
1. 父子都 `close(fd)` 才真正关闭底层文件。
2. 父子并发 `write` 同一 fd 会交错（除非用 `O_APPEND` 或 `flock`）。
3. `execve` 后未设 `FD_CLOEXEC` 的 fd 仍保留——安全漏洞。**约定**：所有 fd 默认设 `O_CLOEXEC`（`open` 时或 `fcntl`）。

</details>

**3.（踩坑）** 程序用 `syscall(SYS_open, "/etc/cfg", O_RDONLY)` 在 x86-64 编译运行正常，移植到 ARM 32 即崩。`/etc/cfg` 文件确实存在。为什么？

<details><summary>答案</summary>

**系统调用号跨架构不同**。`SYS_open` 在 x86-64 = 2，在 ARM 32 = 5；更糟的是 `SYS_open` 在某些新架构（AArch64）已被废弃，推荐 `SYS_openat`。但**真坑**常在：用户硬编码 `syscall(2, ...)` 而非 `syscall(SYS_open, ...)`——x86-64 上 `2` 是 `open`，ARM 上 `2` 是 `fork`！代码尝试把字符串当 fork 的参数，返回 -EFAULT 或 -ENOSYS。
**修复**：
1. 永远用 `SYS_xxx` 宏，不硬编码数字。
2. 优先用 libc 包装（`open()`），自动处理架构差异。
3. 新代码用 `openat(AT_FDCWD, ...)` 替代 `open()`——`open` 在新架构已废弃。
**教训**：syscall 是架构相关 ABI，跨架构代码必须用宏。

</details>

**4.（应用）** 用 `strace` 定位一个程序"卡住读文件"的问题：程序看似卡在 `read`，但文件其实没有数据可读。给出 strace 命令和解读方法。

<details><summary>答案</summary>

```bash
# 1. 基础追踪
strace -f -e trace=open,openat,read,write,poll,select,epoll_wait ./app

# 2. 看时间戳找卡住点
strace -f -T -tt -e trace=read,poll ./app
# 输出：13:45:22.123456 read(3, ..., 4096) = -1 EAGAIN (资源暂时不可用) <0.000012>
#       13:45:22.123468 poll([{fd=3, events=POLLIN}], 1, -1) = 1 ([{fd=3, revents=POLLIN}]) <0.500123>
#       ↑ poll 等 0.5 秒才返回，说明无数据可读

# 3. 看文件描述符指向哪个文件
ls -l /proc/$(pidof app)/fd/3
# lrwx------ 1 user user 64 ... /proc/.../fd/3 -> /dev/uart0
```
解读：
- `-f`：跟随子进程/线程。
- `-T -tt`：每个 syscall 打印耗时和精确时间戳——找出"卡住"的 syscall。
- `-e trace=...`：只看关心的 syscall，过滤噪音。
- `EAGAIN` + `poll` 组合：非阻塞读 + 等待——正常模式。
- `poll(..., -1)` 无限等：若长时间返回 0 或不返回，是文件无数据。
- `/proc/PID/fd/N`：看 fd 实际指向哪个文件——确认是 UART、socket 还是普通文件。
**延伸**：`ltrace` 追踪库函数调用，`perf trace` 是 strace 的高性能替代（基于 eBPF）。

</details>
