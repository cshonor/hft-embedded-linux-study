# 8.3.3 设备管理模型

## 本节讲什么

Linux **设备模型**用 `struct device` 统一表示物理或逻辑设备：名称、父设备、总线、驱动绑定、电源状态、sysfs 节点。驱动不直接操作全局表，而是通过 **`device_register`**、**`dev_set_name`**、**`dev_set_drvdata`** 等 API 与核心交互——设备对象是对硬件的**封装**。

## 要点

**`struct device` 核心字段（简化）**：

```c
struct device {
    struct device      *parent;
    struct bus_type    *bus;
    struct device_driver *driver;
    struct list_head    bus_list;
    void               *platform_data;  /* 或 dev_get_drvdata */
    /* ... 电源、DMA、of_node 等 */
};
```

| API | 作用 |
|-----|------|
| `device_initialize` | 初始化内嵌 kobject/list |
| `device_add` / `device_register` | 加入层次，触发 uevent |
| `device_unregister` | 反注册 |
| `dev_set_drvdata` / `dev_get_drvdata` | 绑定驱动私有数据 |
| `devm_*` | 设备生命周期托管内存（自动释放） |

**驱动绑定流程**：

```
device_register(dev)
    → 挂到 bus 的设备链表
    → bus_match(dev, driver)?
    → driver.probe(dev)  /* 驱动「构造」完成 */
```

```c
static int my_probe(struct device *dev) {
    struct my_chip *chip = devm_kzalloc(dev, sizeof(*chip), GFP_KERNEL);
    dev_set_drvdata(dev, chip);
    /* 映射 MMIO、注册 irq */
    return 0;
}
```

- **`parent` 指针**形成 `/sys/devices/...` 树形层次（PCI → USB → interface）
- **`platform_data` / DT**：板级数据与设备树通过 `device` 传入，驱动保持与板级解耦
- 用户态类比：**demo02** 中 `Device` 基类 + 设备列表管理

## 常见陷阱

1. **`dev_set_drvdata` 在 `probe` 失败路径未清理 → 悬垂指针**
   `probe` 中 `devm_kzalloc` 分配 chip 后 `dev_set_drvdata(dev, chip)`。若 `probe` 后续步骤失败返回错误码，**框架不会自动清 drvdata**——`dev->driver_data` 仍指向已释放的 chip。`remove` 或其他回调若取 `dev_get_drvdata` 即 use-after-free。**正确**：失败路径显式 `dev_set_drvdata(dev, NULL)`，或全程用 `devm_*` 确保自动释放。

2. **`devm_*` 资源在 `probe` 中途失败时不一定按期望顺序释放**
   `devm_kzalloc`、`devm_ioremap`、`devm_request_irq` 注册到设备 devres 链表，`probe` 失败时框架倒序释放。但**有副作用**的资源（如已使能的中断、已注册的 sysfs 节点）的逆操作可能不在 devres 中——必须用 `devm_add_action` 注册自定义清理。坑：`request_irq` 成功但后续 `iounmap` 失败，中断仍开 → 误以为 devm 全自动是错的。

3. **`parent` 层次误用导致 sysfs 死锁或电源管理顺序错乱**
   `device_register` 时设 `parent` 形成 `/sys/devices/...` 树。**电源管理**（suspend/resume）按树深度优先遍历——子设备先 suspend、后 resume。若把"逻辑设备"挂错 parent（如把虚拟网卡挂到 USB 设备下），会在 USB 父设备 suspend 后仍访问子设备 → 崩溃。**约定**：parent 必须是**物理或电源控制关系**上的上游设备，不能按"逻辑相关"随便挂。

## 自测题

**1.（选择）** `devm_kzalloc` 与 `kzalloc` 的关键区别？
- A. `devm_*` 性能更高
- B. `devm_*` 绑定设备生命周期，设备释放时自动释放
- C. `devm_*` 不能用于中断上下文
- D. `devm_*` 只能分配小内存

<details><summary>答案</summary>

**B**。`devm_*` 系列把分配的资源注册到 `struct device` 的 devres 链表，设备 `device_unregister` 或 `probe` 失败时**自动逆序释放**——避免手动 `kfree` 遗漏导致泄漏。性能略低（维护链表），但可靠性大幅提升，是驱动首选。中断上下文限制二者相同（都不能 sleep）。大小无限制，但极大块用 `vmalloc` / `devm_vmalloc`。

</details>

**2.（判断）** `probe` 返回非零错误码时，框架会自动调用 `remove` 清理。

<details><summary>答案</summary>

**错**。`probe` 失败时框架**不会调 `remove`**——`remove` 只在设备已绑定驱动后 unregister 时调用。`probe` 失败的清理责任在 `probe` 函数本身：必须**逆序释放已申请的资源**（或用 `devm_*` 让框架兜底）。误以为"框架会调 remove"导致资源泄漏是驱动开发常见坑。`probe` 成功后才会把设备加入 `driver_bound` 链表，`remove` 才会被触发。

</details>

**3.（踩坑）** 驱动 `probe` 中：
```c
chip = devm_kzalloc(dev, sizeof(*chip), GFP_KERNEL);
dev_set_drvdata(dev, chip);
ret = devm_request_irq(dev, irq, handler, 0, name, chip);
if (ret) return ret;            /* ① 中断已注册 */
ret = register_chrdev(...);     /* ② 失败 */
if (ret) return ret;
```
`probe` 在 ② 失败后返回。设备移除时用户态已无引用，但**中断仍会触发**——为什么？如何修？

<details><summary>答案</summary>

**`register_chrdev` 不是 devm 资源**——`probe` 失败时 `devm_*` 链表逆序释放（`devm_request_irq` 会被注销），但 `register_chrdev` **不会自动注销**。等等——题述"中断仍会触发"实际不会发生，因为 `devm_request_irq` 是 devm 的，会自动 `free_irq`。**真正坑在**：如果中断 handler 已触发并 `schedule_work`，`probe` 失败时 work 仍在队列里，worker 执行时访问已释放的 chip → use-after-free。
修复：
```c
ret = register_chrdev(...);
if (ret) {
    devm_free_irq(dev, irq, chip);   /* 显式提前释放 */
    cancel_work_sync(&chip->work);    /* 等 work 完成 */
    return ret;
}
```
**教训**：`devm_*` 自动释放**按设备生命周期**，但异步任务（work/timer）可能在释放后仍访问资源——必须显式 cancel。

</details>

**4.（应用）** 设计一个 platform 驱动框架：① `probe` 分配 chip、映射 MMIO、注册 IRQ、注册 cdev；② 失败路径全部清理；③ `remove` 干净退出。给出代码骨架。

<details><summary>答案</summary>

```c
static int my_probe(struct platform_device *pdev) {
    struct device *dev = &pdev->dev;
    struct my_chip *chip;
    int ret;

    chip = devm_kzalloc(dev, sizeof(*chip), GFP_KERNEL);
    if (!chip) return -ENOMEM;
    platform_set_drvdata(pdev, chip);

    chip->base = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(chip->base)) return PTR_ERR(chip->base);

    chip->irq = platform_get_irq(pdev, 0);
    if (chip->irq < 0) return chip->irq;

    ret = devm_request_irq(dev, chip->irq, my_irq, 0, "my", chip);
    if (ret) return ret;

    cdev_init(&chip->cdev, &my_fops);
    chip->cdev.owner = THIS_MODULE;
    ret = cdev_add(&chip->cdev, chip->devno, 1);   /* 非 devm */
    if (ret) return ret;                            /* devm_* 自动释放 */

    /* 用 devm_add_action 兜底 cdev_del */
    ret = devm_add_action(dev, (void(*)(void*))cdev_del, &chip->cdev);
    if (ret) { cdev_del(&chip->cdev); return ret; }

    return 0;
}

static int my_remove(struct platform_device *pdev) {
    /* devm_* 自动释放；自定义 action 自动调 cdev_del */
    return 0;
}
```
要点：
- **devm 资源**（kzalloc/ioremap/request_irq）失败路径零清理。
- **非 devm 资源**（cdev_add）用 `devm_add_action` 注册清理回调，统一进 devres。
- `remove` 几乎为空——所有清理委托给 devres。
- 这是现代 Linux 驱动推荐写法，老驱动大量手动 goto cleanup 是历史包袱。

</details>
