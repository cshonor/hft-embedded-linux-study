# 8.7 实例：存储分配程序

## 本节讲什么

K&R 用 **`sbrk`/`brk`** 向内核申请堆空间，实现简化版 **`malloc`/`free`**，把 **用户态堆** 与 **系统接口** 连起来。

## 要点

### brk / sbrk

```c
#include <unistd.h>
void *sbrk(intptr_t increment);
```

- 移动 **program break**（堆顶）
- **`malloc`** 经典实现：维护空闲链表，不足时 **`sbrk`** 扩展
- 现代 glibc 用 **`mmap`** 大块分配，但模型仍相关

### 分配器设计要素

- **空闲块链表**（边界标记或链表头）
- **对齐**：返回指针满足 `max_align_t`
- **`free`** 合并相邻空闲块，减少碎片
- **线程安全**：生产 `malloc` 需锁；HFT 热路径用 **预分配池**

### 与第 6、7 章关系

- 6.5 链表节点在堆上
- `malloc` 标准 API 底层即此类分配器 + 系统调用

## 底层场景

| 环境 | 堆 |
|------|-----|
| Linux 用户态 | brk + mmap |
| 内核 | kmalloc /slab |
| UEFI | AllocatePool |
| 裸机 / OS 实验 | 自管物理页 + 空闲链表 |

## 与后续衔接

理解「堆 = 虚拟地址空间一段 + 系统扩展 break」为读 **mmap**、**内存泄漏**、**ASLR** 打基础；与 fork 的 COW 共享页（章 README）同一内存世界观。

## K&R malloc 的设计

K&R 用**空闲链表**（free list）实现简化版 malloc，核心数据结构：

```c
typedef union header {
    struct {
        size_t size;    /* 本块大小（含 header，单位：header 个数） */
        union header *next;  /* 空闲链表中的下一块 */
    } s;
    long _align;        /* 强制对齐：union 大小 = max(long, struct) */
} Header;

static Header *freep = NULL;  /* 空闲链表头 */
```

**malloc 逻辑**：
1. 遍历空闲链表找大小足够的块
2. 找到 → 可能分割（大块切成需要的 + 剩余空闲块）
3. 没找到 → 调用 `sbrk` 向内核申请更多内存，加入空闲链表

**free 逻辑**：
1. 找到被释放块在空闲链表中的位置（按地址排序）
2. 如果前后相邻空闲块 → **合并**（减少碎片）
3. 插入空闲链表

## 常见陷阱

1. **sbrk 无法收缩已释放的内存**：K&R 的 free 只把块标记为空闲并加入链表，不调用 `sbrk(-n)` 归还内存给内核。大量分配后全部 free，进程的堆顶（program break）仍不下降——`top` 显示内存占用不减少。现代 glibc malloc 对大块用 `mmap` 分配（free 后 munmap 归还），小块仍用 brk 但空闲到一定程度会 trim。HFT 进程常预分配大块池避免动态 sbrk。

2. **free 后继续使用（use-after-free）**：`free(p); p->next = NULL;` ——free 把 p 加入空闲链表，后续 malloc 可能把这个块分给别人。通过 freed 指针读写到的是别人的数据。更危险：free 后的块被合并，指针指向的 header 已变。防御：free 后 `p = NULL;`，后续解引用 NULL 立即段错误而非静默腐败。ASan（AddressSanitizer）可检测 use-after-free。

3. **double free 破坏空闲链表**：`free(p); free(p);` ——第一次 free 把 p 加入空闲链表，第二次 free 再次加入 → 链表中出现同一块两次。下次 malloc 可能把这个块分给两个调用者 → 数据腐败。现代 malloc（glibc ptmalloc2）有 double-free 检查，但不是所有实现都有。防御：free 后置 NULL，或用调试 malloc（dmalloc/ASan）。

## 自测题

**1. 选择**：K&R 的 free 实现中，为什么要在空闲链表中按地址顺序插入被释放的块？
- A. 为了快速查找
- B. 为了合并物理相邻的空闲块
- C. 为了按大小排序
- D. 没有特殊原因

<details><summary>答案</summary>
B。按地址排序插入后，可以检查前后相邻块是否也空闲——如果是就合并成一个更大的空闲块。这叫**合并（coalescing）**，是减少外部碎片的关键。如果不按地址排序，无法知道物理相邻的块是否空闲，碎片会越来越严重——大量小碎片但无法满足大块请求。现代分配器（ptmalloc2/jemalloc）也做合并，只是用更高效的数据结构（bins/trees）。
</details>

**2. 判断**：调用 `free(p)` 后进程的堆内存（program break）会立即下降。

<details><summary>答案</summary>
错。K&R 的 free 只把块标记为空闲并加入空闲链表，**不调用 sbrk(-n)** 收缩堆顶。堆顶只在空闲块位于堆顶且足够大时才可能被 trim。现代 glibc 对小块用 brk（不收缩或延迟收缩），对大块用 mmap（free 后 munmap 立即归还）。所以 `malloc(100MB); free(p);` 后 `top` 可能仍显示 100MB 占用。HFT 进程通常预分配内存池，避免运行时 sbrk/mmap 的延迟抖动。
</details>

**3. 踩坑**：以下代码在循环运行一段时间后崩溃，但不是每次都复现，为什么？
```c
char *p = malloc(100);
strcpy(p, data);
free(p);
printf("%s\n", p);   /* 打印已释放的内存 */
```

<details><summary>答案</summary>
这是 **use-after-free**（UAF）。free(p) 后 p 指向的块被加入空闲链表，后续 malloc 可能把它分给别人。printf 读 p 时可能读到：1) 旧数据（块还没被重分配，看似正常但不可靠）；2) 空闲链表指针（被 free 改写了 header）；3) 别人的新数据（块被重分配）。结果不确定所以崩溃不一定复现。防御：free 后 `p = NULL;`，解引用 NULL 立即段错误。编译时加 `-fsanitize=address` 可检测 UAF。
</details>

**4. 应用**：写一个简单的内存池 `pool_alloc`——预分配大块内存，按固定大小切片分配，不支持 free（整体释放），说明适用场景。

<details><summary>答案</summary>
```c
typedef struct {
    char *base;     /* 大块基址 */
    size_t offset;  /* 当前分配偏移 */
    size_t total;   /* 总大小 */
} Pool;

Pool *pool_create(size_t total) {
    Pool *p = malloc(sizeof(Pool));
    p->base = malloc(total);
    p->offset = 0;
    p->total = total;
    return p;
}

void *pool_alloc(Pool *p, size_t size) {
    /* 对齐到 8 字节 */
    size = (size + 7) & ~((size_t)7);
    if (p->offset + size > p->total) return NULL;
    void *ptr = p->base + p->offset;
    p->offset += size;
    return ptr;
}

void pool_destroy(Pool *p) {
    free(p->base);
    free(p);
}
```
适用场景：HFT 启动时预分配所有需要的内存，运行时只从池中切片（O(1)，无锁，无碎片），不逐个 free——整体销毁。游戏引擎、编译器 AST 节点分配也常用这个模式。优点：无 malloc/free 开销、无碎片、缓存友好（连续内存）。
</details>
