# 9.10 UTF-8 与多字节字符（补充节）

> 第 9 章补充节（原书无此节）· 承接 [9.1 字符串基础](./9.1-字符串基础.md)、[9.2 字符串长度](./9.2-字符串长度.md)、[9.8 字符操作](./9.8-字符操作.md)

## 本节讲什么

前九节默认处理的是 **ASCII 单字节字符**——`char` 刚好一个字符一个字节。一旦碰上汉字、emoji，这个"一个 `char` = 一个字符"的直觉就全面失效：同一个汉字占 **3 个 `char`**，emoji 占 **4 个**，`strlen` 返回的是**字节数不是字符数**，而把汉字塞进单引号在 clang 里是**硬错误**不是警告。

本节把 `char` / `char[]` / 码点 / UTF-8 字节流四者的边界一次划清，全部数字为**本机实测**（clang 23.1.0，macOS arm64，UTF-8 执行字符集）。

## 要点

### 1. `char` 装得下什么、装不下什么

| 内容 | 占用 | 能否放进单个 `char` |
|------|------|------------------|
| ASCII `'A'` | 1 字节（0x41） | ✅ |
| 汉字 `汉`（U+6C49） | **3 字节**（UTF-8：`e6 b1 89`） | ❌ |
| emoji 😀（U+1F600） | **4 字节**（UTF-8：`f0 9f 98 80`） | ❌ |
| 拉丁扩展 `é` | 2 字节 | ❌ |

**实测**：

```c
const char *han = "汉";
sizeof("汉");      /* 4 —— 3 字节 + '\0' */
strlen(han);       /* 3 —— 字节数，不是字符数！ */
/* 字节序列：e6 b1 89 */

const char *s = "a汉😀";
strlen(s);         /* 8 —— 1 + 3 + 4，但只有 3 个"字符" */
```

**关键一句**：`char` 是 **1 字节存储单元**，不是"一个字符"。UTF-8 下"字符"是**变长的字节序列**，只能整体放进 `char[]`。

### 2. UTF-8 用 `char[]` 存：长度是字节数，不是字符数

```c
char msg[] = "交易完成";   /* 12 字节 + '\0' = 13 */
```

- `strlen(msg)` = **12**（字节数）
- 实际字符数 = **4**

✅ **好消息**：UTF-8 编码除 `U+0000` 外**不含 0x00 字节**（这是 UTF-8 的设计保证），所以对合法 UTF-8 串用 `strlen` 求**字节长度是安全的**，不会像二进制 payload 那样提前截断。

⚠️ **坏消息**：`strlen` 给不了字符数。要数字得自己解码——数**非连续字节**（`0xxxxxxx` 单字节 或 `11xxxxxx` 首字节，跳过 `10xxxxxx` 后续字节）：

```c
/* 统计 UTF-8 字符数（不校验合法性） */
size_t utf8_chars(const char *s) {
    size_t n = 0;
    for (const unsigned char *p = (const unsigned char *)s; *p; p++)
        if ((*p & 0xC0) != 0x80)   /* 不是 10xxxxxx 后续字节 */
            n++;
    return n;
}
```

> 传参时转成 `unsigned char *`：UTF-8 字节值 ≥ 0x80，若 `char` 是 signed，直接位运算会得到负数，掩码判断全错。

### 3. 汉字写进单引号：clang 是**硬错误**，不是警告

```c
int mc = '汉';     /* ❌ error */
char c = '汉';     /* ❌ error */
```

**实测报错**：

```
error: character too large for enclosing character literal type
```

对比一下 ASCII 多字符常量的待遇：

| 写法 | clang 的反应 | 类型 / 值 |
|------|-------------|----------|
| `'AB'` | ⚠️ warning `-Wmultichar` | `int`，实测 **0x4142**（首字符在高字节） |
| `'汉'` | ❌ **error** | 编译不过——单个 c-char 映射出 3 字节，超出字符字面量容量 |

**正确写法**：

```c
const char *s = "汉";        /* ① 字符串：char[4]，最常用 */
/* 码点另说，见 §4 */
```

> 用户手册里"多字节字符写进单引号是未推荐的多字符字面量、行为不确定"这句话，对 ASCII 多字符（`'AB'`）成立；
> 但对**汉字**，clang 直接拒绝编译——比"行为不确定"更早一步被拦住。

### 4. 码点（code point）用什么装

Unicode 码点范围 `U+0000`–`U+10FFFF`，需要 **21 位**：

| 类型 | 大小 | 能装 |
|------|------|------|
| `int` / `uint32_t` | 4 字节 | ✅ 所有码点 |
| `char32_t`（`U'x'`，C11 起） | **实测 4** | ✅ 所有码点 |
| `char16_t`（`u'x'`，C11 起） | **实测 2** | ⚠️ **只有 BMP（≤ U+FFFF）** |

**实测**：

```
U'汉'   = 0x6c49   sizeof=4    ← char32_t，直接是码点
u'汉'   = 0x6c49   sizeof=2    ← BMP 内，一个 UTF-16 码元够
U'😀'   = 0x1f600  sizeof=4    ← char32_t OK
u'😀'   = ❌ error: character too large for enclosing character literal type
```

最后一行是关键：**emoji 码点 > U+FFFF，UTF-16 需要代理对（两个码元），`char16_t` 装不下，clang 直接报错。** 所以跨 BMP 的场景一律用 `char32_t` / `uint32_t`。

> C11 的 `char16_t` / `char32_t` 定义在 `<uchar.h>`。本机 micromamba `cdev` 环境的 clang 在 **C 模式下没有 `<uchar.h>`**（`/usr/include` 不存在），
> 但 `sizeof(u'x')` / `sizeof(U'x')` 这类**不需要头文件**（类型由字面量本身决定）。需要 `mbrtoc32` 等转换函数时，换有完整 libc 头文件的环境（或 Pi 上的 gcc）。

### 5. `%c` 的真实语义：转换为 `unsigned char`，不是"取低字节"

```c
printf("%c", 321);      /* 实测输出 'A' */
printf("%c", 0x141);    /* 同上：0x141 的 "低 8 位" = 0x41 = 'A' */
```

标准（C11 §7.21.6.1p8）的说法是：

> the `int` argument is **converted to an `unsigned char`**, and the resulting character is written.

所以严格讲是**转换到 `unsigned char`**（等价于取低 8 位按**无符号**解释），而不是保留符号的截断。这个区别在下面这个例子里能看出来：

```c
char neg = (char)0xFF;    /* 本机 char 为 signed，值 -1 */
printf("%d",   neg);      /* -1 */
printf("%hhd", neg);      /* -1  （C99 hh 长度修饰符，按 signed char 解释） */
printf("%c",   neg);      /* 写出 0xFF 这个字节（不是 -1） */
```

`%d` 看到的是提升后的 `int`（-1）；`%c` 把它转回 `unsigned char`（255）后写出字节 `0xFF`——在 UTF-8 终端上它不是合法 UTF-8，显示为替换符 `�`。

### 6. 数组退化与长度丢失（和 UTF-8 的交叉点）

```c
char msg[] = "交易完成";
process(msg);            /* 退化为 char *，长度信息全丢 */
```

- 退化后只剩**首字节地址**，长度只能靠 `\0` 反推（`strlen`，O(n)）或**显式传 len**；
- 退化**不发生**在 `sizeof(msg)`、`&msg`、以及用字符串字面量初始化数组时；
- UTF-8 场景下"长度"有两个含义——**字节数**（`strlen` / `sizeof-1`）和**字符数**（需解码），函数签名里必须写明是哪一个。

**HFT 铁律**：`process(const char *s, size_t len)` 里 `len` 指**字节数**；需要字符数就在函数内解码，别让调用方猜。

### 7. 按字节截断会切出半个汉字

```c
char dst[4];
snprintf(dst, sizeof(dst), "%s", "交易完成");   /* 只留 3 字节 = 一个"交"，安全 */
memcpy(dst, "交易完成", 4);                     /* 4 字节 = "交" + "易"的 1/3 → 半个汉字 */
```

`memcpy` / `strncpy` 按**字节**截断，切在多字节序列中间会留下**非法 UTF-8**（终端显示 `�` 或乱码）。协议字段定长截断时必须按**字符边界**对齐：

```c
/* 截断到不超过 max_bytes，且不切断 UTF-8 字符 */
size_t utf8_trunc(const char *s, size_t max_bytes) {
    size_t i = 0;
    while (i < max_bytes && s[i]) {
        size_t w = utf8_seq_len((unsigned char)s[i]);   /* 首字节推断序列长度 */
        if (i + w > max_bytes) break;
        i += w;
    }
    return i;
}
```

## HFT / 内核关联

1. **协议里的 UTF-8 字段**：现代协议（JSON over WebSocket、FIX 的某些自定义域）可能带 UTF-8。解析时一律 **ptr + 字节长度**，不用 `strlen`（后者在 payload 含 `0x00` 时会提前截断——虽然合法 UTF-8 不含，但**不可信输入**不受此保证）。

2. **日志**：`write(2)` / `fwrite` 按**字节**写，不做任何编码解释。UTF-8 日志直接写字节即可，无需转码；但 `snprintf` 的 `%.*s` 精度是**字节数**，截断同样有切半风险。

3. **别用 `is*` 判断 UTF-8 字节**：`isalpha` 只对 ASCII 有意义，且参数必须 `(unsigned char)c`（见 [9.8](./9.8-字符操作.md)）。判定"是不是汉字"要做码点解码 + Unicode 区间判断，标准库帮不了，得上 ICU。

4. **内核侧**：内核只用 ASCII（`printk` 格式串、dmesg），UTF-8 只出现在用户态数据里，内核不做解码——所以驱动里看到 UTF-8 就当**字节流**处理。

5. **性能**：UTF-8 解码是逐字节分支，热路径上如果需要按字符处理，先评估能否退化成"按字节匹配前缀"（如只比对 ASCII 关键字），省掉解码。

**1（字节 vs 字符）** `char s[] = "a汉😀";` 的 `sizeof(s)`、`strlen(s)`、字符数各是多少？

**2（%c）** `printf("%c", 321);` 输出什么？为什么？

**3（单引号）** `int mc = '汉';` 在 clang 下是什么结果？和 `int x = 'AB';` 的待遇有何不同？

**4（码点）** `u'😀'` 能编译吗？为什么？跨 BMP 的码点应该用什么类型？

**5（截断）** 想把 "交易完成" 截断到 4 字节，用 `memcpy` 直接拷贝会出什么问题？怎么处理才安全？

**6（符号性）** 统计 UTF-8 字符数时为什么要把指针转成 `unsigned char *`？

<details><summary>参考答案</summary>

**1.** `sizeof(s)` = **11**（1+3+4 字节 + `'\0'`）；`strlen(s)` = **10**（字节数）；字符数 = **3**。
`strlen` 数的是字节，UTF-8 下它**不等于**字符数。

**2.** 输出 **`A`**。标准规定 `%c` 把 `int` 实参**转换为 `unsigned char`** 后写出——321 = 0x141，低 8 位 0x41 = `'A'`。注意是转为**无符号** char，不是保留符号的截断。

**3.** ❌ **编译错误**：`error: character too large for enclosing character literal type`。
而 `int x = 'AB';` 只是 **warning**（`-Wmultichar`），能通过，实测值 `0x4142`。差别在于 `'汉'` 的单个 c-char 映射出 3 个 UTF-8 字节，字符字面量容不下。

**4.** ❌ 不能，`error: character too large for enclosing character literal type`。
因为 U+1F600 > U+FFFF，UTF-16 需要**代理对（2 个码元）**，单个 `char16_t` 装不下。跨 BMP 一律用 `char32_t`（`U'😀'`，实测 0x1f600，sizeof=4）或 `uint32_t`。

**5.** 会切出**半个汉字**：4 字节 = "交"（3 字节）+ "易"的第 1 个字节，剩下的 `e4` 序列残缺，终端显示 `�` 或乱码。
安全做法：按 UTF-8 字符边界对齐截断（见 §7 的 `utf8_trunc`），或者干脆按**字符数**截断再回填字节数。

**6.** UTF-8 字节值 ≥ 0x80。若 `char` 是 **signed**（x86-64 Linux、arm64 macOS 都是），`0xE6` 会被解释成 **-26**，`(*p & 0xC0) != 0x80` 这类掩码判断全部失效（负数按补码参与位运算，结果完全不同）。
同理，`is*` / `memcmp` 之外的所有字节级判断都该用 `unsigned char` 或 `uint8_t`。
