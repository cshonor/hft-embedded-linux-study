# 9.1 字符串基础

## 本节讲什么

**C 字符串**的定义只有一个约定：一段连续的 `char`，以 **`'\0'`**（值为 0 的字节）作为**唯一**结束标志。这个看似简单的约定是整个 `<string.h>` API 族的根基，也是 HFT/网络报文场景**无数漏洞的源头**——因为真实报文里 0x00 是合法数据字节，不是终止符。

**二进制字节流**则相反：边界由**显式长度** `pkt_len` 决定，0x00 可以出现在任意位置。这两种数据模型**互不兼容**，混用即 UB。本章的核心主线就是划清这条界线。

### 历史背景

C 字符串约定继承自 1969 年 B 语言（Dennis Ritchie 在 PDP-7 上设计）。当时内存以字节编址、CPU 慢、无专门字符串指令，**用 0 作为哨兵**让扫描循环只需一条 `cmpb $0,(%rax)` 即可判定结束，无需维护长度字段。这个取舍在 1970s 合理，但在 2020s 成了**系统性风险**——`gets`/`strcpy` 一族的缓冲区溢出（Morris 蠕虫、无数栈溢出 CVE）都源于把 C 字符串 API 套到不受控输入上。

> ⚠ 归因要分清：**Heartbleed（CVE-2014-0160）不是 C 字符串模型的锅**——心跳报文本来就是"显式长度"的二进制协议，漏洞是 OpenSSL 信任了报文里的 2 字节 `payload_length` 却没校验它 ≤ 实际收到的字节数，一次 `memcpy` 越读 64KB。它的教训恰好相反：**显式长度模型必须校验长度**（信任输入的长度字段 = 信任攻击者）。别把两个模型的坑记混。

## 要点

### 内存布局

```c
char str[] = "quote";   /* 'q''u''o''t''e''\0' → 6 字节 */
```

```
偏移  0    1    2    3    4    5
     +----+----+----+----+----+----+
     | q  | u  | o  | t  | e  | \0 |
     +----+----+----+----+----+----+
       0x71 0x75 0x6f 0x74 0x65 0x00
```

- `strlen("quote")` = **5**（不含 `\0`）
- `sizeof(str)` = **6**（数组总字节，含 `\0`）
- `str[5] == '\0'`，`str[6]` 越界 UB

### 两种存储模型

```c
char pkt_buf[128] = "order";      /* 数组，在栈/堆，可写 */
const char *proto = "heartbeat";  /* 指针，指向 .rodata 字面量 */
```

| 模型 | 存储位置 | 可写性 | 修改后果 |
|------|----------|--------|----------|
| `char arr[] = "..."` | 函数内：栈拷贝；全局/静态：`.data` 初始化拷贝 | **可写** | 正常 |
| `const char *p = "..."` | 字面量在只读段 | **不可写** | Linux：**SIGSEGV**；macOS 实测：**SIGBUS**（exit 138）；裸机：**静默踩踏** |

字面量 `"heartbeat"` 存放在只读段——**ELF 是 `.rodata`，Mach-O（macOS）是 `__TEXT,__cstring`**（名字不同，别在 macOS 上 objdump `.rodata` 扑空）。相同字面量由编译器合并以节省空间（`-fmerge-constants`，优化开启时默认启用）。实测（clang 23, macOS arm64）：两处 `"heartbeat"` 字面量地址相同（合并为一份）；`p[0]='H'` 写字面量当场 SIGBUS。

```bash
# Linux/ELF：
$ gcc -O2 strlit.c -o strlit
$ objdump -s -j .rodata strlit        # 可见 "heartbeat" 仅一份
# macOS/Mach-O：
$ otool -l strlit | grep -A2 __cstring   # 字面量在 __TEXT,__cstring
```

#### 为什么字面量改不了：四层原因叠起来

不是"编译器不让改"，而是**从标准到 MMU 四层都把它定死了**：

| 层 | 依据 / 实测 |
|---|---|
| ① **标准层** | C11 6.4.5p6：字面量用来初始化一个 **静态存储期**的数组，元素类型是 `char`（注意**不是** `const char`）；p7：*"It is unspecified whether these arrays are distinct … If the program attempts to modify such an array, the behavior is undefined."* —— 改就是 **UB**，标准不保证它可写 |
| ② **实现层** | 编译器把这个静态数组放进**只读段**：ELF 是 `.rodata`，Mach-O 是 `__TEXT,__cstring` |
| ③ **OS/MMU 层** | 段保护位不含写位，硬件兜底：macOS `otool -l` 显示 `__TEXT` 的 `initprot`/`maxprot = 0x5`（= r-x，**没有 write 位 2**）——连 `mprotect(…PROT_READ\|PROT_WRITE)` 提权都被拒（实测 `Permission denied`，因为 `maxprot` 就是上限）；Linux `.rodata` 映射为只读 → 写触发 **SIGSEGV（11）**；macOS arm64 → **SIGBUS（10）**（实测 signal handler 捕获） |
| ④ **合并层** | p7 说"各数组是否独立 unspecified"，于是 `-fmerge-constants` 把相同字面量合成一份（实测两处 `"heartbeat"` 同地址）。**一旦能改，改一处会污染所有引用**——这就是为什么语言宁可一刀切禁掉 |

**语言层的陷阱**：因为 p6 定的元素类型是 `char` 而非 `const char`，`char *p = "abc";` 在 **C 里默认不警告**（clang 要 `-Wwrite-strings` 才报 `discards qualifiers`）；而 **C++11 起**直接报 `ISO C++11 does not allow conversion from string literal to 'char *' [-Wwritable-strings]`。所以 C 里"能不能写"全靠自觉——**写法一律 `const char *`**，把类型层这道提醒先立起来。

#### 常见误解：不可写不是 const 的功劳（const 与段保护正交）

**`const` 修饰符和"这块内存能不能被写"是两套独立机制**——前者是编译期的类型约束（管"你能不能**通过这个名字**写"），后者是段的页保护位（管"这块物理内存**能不能被写**"）。四格对照实测（clang 23, macOS arm64）：

| | 内存可写（栈 / `__DATA`） | 内存只读（`__TEXT` / `.rodata`） |
|---|---|---|
| **无 const** | ✅ 随便写：`char buf[]="abc"` | ❌ **运行期崩**：`char *p="abc"; p[0]='A';` → SIGBUS（①无 const 照样不可写！） |
| **有 const** | ⚠️ 编译期拦（`arr[0]` 报错），但**强转绕过后改写成功**：`memcpy((void*)stack_arr,"xyz",3)` 真的改成 "xyz"；`*(int*)&volatile_const = 42` 真的变 42 | ❌ 编译期拦 + **强转绕过后运行期也崩**：`memcpy((void*)g_arr,…)` → SIGBUS（④const 救不了只读段） |

两个方向各堵死一半误解：

- **① 证明"不可写≠const 的功劳"**：`char *p = "abc"` **一个 const 都没有**，照样 SIGBUS——因为字面量躺在 `__TEXT`（`initprot`/`maxprot = 0x5` = r-x，无写位）
- **②③ 证明"const 也不是物理保证"**：`const char stack_arr[]` 在**栈**上（内存本来就可写），强转 `memcpy` 一写一个准；`volatile const int` 同理
- **地址佐证**：字面量 `0x…ff17`、全局 `const g_arr 0x…ff10` 同挤在 `__TEXT` 段尾；全局非 const `g_rw 0x…4050` 在 `__DATA`（`0x3` = rw-）——**可写与否完全由地址落在哪个段决定**

一句话：**const 防的是诚实的代码（编译期报错），段保护防的是强转和野指针（运行期崩）**。字面量不可写靠的是后者；你写 `const char *` 只是把前者的提醒也装上，双保险的第一层。

**想可写就用数组模型**：`char buf[] = "heartbeat";` 在数据段/栈上做一份**拷贝**，随便改。这也解释了两种模型存在的原因——字面量是"共享的只读常量"，数组是"私有的可写副本"。

> 裸机无 MMU 时第③层不存在：`p[0]='H'` **静默写入**，还会因为合并把别处的同名常量一起改掉，且毫无征兆。

### C 字符串 vs 二进制字节流

| 维度 | **C 字符串** | **二进制 buf** |
|------|--------------|----------------|
| 边界 | 第一个 `\0` | **`pkt_len`** 显式 |
| 0x00 字节 | 表示结束 | **合法数据** |
| 典型 API | `str*` / `printf %s` | `mem*` / `read(fd, buf, n)` |
| 长度获取 | `strlen`（O(n) 扫描） | 已知字段，O(1) |
| 长度上限 | 无内置 | 显式 `size_t len` |
| 适用场景 | 文本、日志、命令行 | **网络报文、文件 I/O、序列化** |

**关键铁律**：DPDK mbuf payload、TCP 报文、FIX/SBE 编码字段、protobuf 二进制序列——**全部**用 `uint8_t * + len`，**禁止** `char * + \0`。

### 遍历范式预告

```c
/* 文本日志：扫到 \0 停 */
for (char *p = line; *p; p++) { /* ... */ }

/* 二进制 payload：扫到 end 停（9.9） */
uint8_t *p = payload, *end = p + pkt_len;
for (; p < end; p++) { /* ... */ }
```

后者是 HFT 报文解析的标准范式，**end 是上界指针**，即使中间出现 0x00 也继续解析。

## HFT 关联

- **报文偏移模型**：DPDK `rte_pktmbuf_mtod(m, uint8_t *)` 返回的 payload 是二进制，长度由 `rte_pktmbuf_data_len(m)` 给出，**绝不用 `%s` 打印**
- **FIX/SBE**：定长字段靠 offset + length，变长字段靠 length prefix，**没有任何字段以 `\0` 终止**
- **日志格式化**：可读日志里用 C 字符串，但日志 payload 本身（写入 ring/logfile）是 `mem*`
- **协议头魔数**：如 Ethernet `0xAAAAAAAAAAAA` 前导、IP `0x45` 版本+IHL，用 `memcmp` 比对，**不是** `strcmp`
- **配置文件**：键值对文本可用 `str*`，但解析后转结构体字段，运行时不再碰字符串

3. 为什么说把 `strlen` 用在 DPDK mbuf payload 上是 UB？给出一个 payload 含 0x00 的具体例子。
4. 字面量 `"abc"` 和 `"abc"` 在同一翻译单元内是否一定占两份存储？编译器哪个选项控制？
5. 写一段代码：给定 `uint8_t *payload, size_t len`，安全打印其前 16 字节的十六进制（**禁用** `%s`）。
6. `char *p = "abc"; p[0] = 'A';` 在 C 里 `gcc -Wall` **不报任何警告**、能编过，但运行时崩。为什么类型系统没拦住？标准（C11 6.4.5）到底在哪一条把它定为 UB？想改这个字符串该怎么写？

<details>
<summary>答案</summary>

因为 C11 6.4.5p6 规定字面量数组的元素类型是 **`char`**（不是 `const char`），所以 `char *p` 赋值是合法的指针类型匹配，类型系统无从判断；真正判它死刑的是 **p7**：*"If the program attempts to modify such an array, the behavior is undefined."*——即修改行为本身 UB，与类型标注无关。`-Wwrite-strings`（C）/ C++11 起的 `-Wwritable-strings` 是编译器的善意提醒，不是语言强制。

运行时崩是 MMU 兜底：字面量落在只读段（ELF `.rodata` / Mach-O `__TEXT,__cstring`），段保护位无写位 → Linux SIGSEGV(11)、macOS arm64 SIGBUS(10)。

想改就改用数组拷贝模型：`char p[] = "abc"; p[0] = 'A';`——私有可写副本。

</details>
