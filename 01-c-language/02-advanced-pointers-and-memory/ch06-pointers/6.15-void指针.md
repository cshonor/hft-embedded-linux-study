# 6.15 void 指针：只持地址、不持类型的通用指针

## 本节讲什么

原书 6.7 只给 `void*` 留了一段话，但它是 C 里**唯一的泛型机制**，值得单独展开。本节回答四个问题：

1. `void*` 到底存了什么、丢了什么？
2. 为什么解引用和算术在标准 C 里是非法的，GNU 扩展却放行？
3. C 和 C++ 在 `void*` 转换规则上差在哪？
4. `void*` 和函数指针能不能互转？

核心结论一句话：**`void*` 保存的是一个地址，外加一个承诺——"我现在不解释这块内存，谁来用谁自己负责解释"。类型信息丢了，编译器就再也救不了你。**

文中所有编译行为均为本机实测（clang 23.1.0，macOS arm64，cdev 环境）。

## 要点

```c
int x = 57;
void *q = &x;    /* 合法：任何对象指针隐式转 void*，方向一 */
```

- **三条铁律**：① 任何**对象**指针都能隐式转 `void*`；② 不能解引用 `*q`；③ 不能指针运算 `q + 1`
- 后两条的根因相同：**类型决定读几个字节、怎么解释、步长多少**（**6.2**），`void*` 三者皆无
- `void*` 本身有确定大小：`sizeof(void*)` = 8（64 位），它存地址这件事没有任何特殊
- C 里 `void*` ↔ `T*` **双向隐式**；C++ 只放行 `T*` → `void*`，回来必须显式 cast
- 用 `void*` 的代码必须**自己跟踪真实类型**——标准库靠文档约定（`qsort` 传元素大小），内核靠约定字段（`private_data`）

## C vs C++ 转换规则（实测对照）

| 操作 | C11 `-pedantic-errors` | C++17 |
|------|------------------------|-------|
| `int*` → `void*` | 隐式合法 | 隐式合法 |
| `void*` → `int*` | **隐式合法**（exit=0） | error: cannot initialize a variable of type 'int *' with an lvalue of type 'void *' |
| `*q` 解引用 | error: ISO C does not allow indirection on operand of type 'void *' | error |
| `q + 1` 算术 | error: arithmetic on a pointer to void is a GNU extension | error |
| `sizeof(void)` | error: invalid application of 'sizeof' to a void type | error |

直接后果：

```c
/* C：malloc 返回值不用强转，强转反而掩盖"忘了 include <stdlib.h>"的警告 */
int *p = malloc(sizeof *p);          /* 推荐 */

/* C++：必须显式，Cherno 视频里的写法 */
int *p = (int*)malloc(sizeof(int));  /* C 风格 */
int *p2 = static_cast<int*>(malloc(sizeof(int)));  /* C++ 风格 */
```

## 底层映射

### 为什么 GNU 扩展敢放行 `q + 1`

ISO C 没有 `void` 对象，所以"指向 void 的指针"在语义上没有步长。GNU 扩展干脆**把 `void` 当成 1 字节类型**处理——本机实测：

```
sizeof(void)  = 1      # -std=gnu11 下编译通过并打印
sizeof(void*) = 8
```

`-std=gnu11` 下 `q + 1` 静默等价于 `(char*)q + 1`，步长 1 字节。这不是标准行为：同一份代码加 `-std=c11 -pedantic-errors` 立刻变 error。**内核代码大量使用这个扩展**（内核以 GNU C 编译，见 05-embedded-kernel-practice 的 GNU C 扩展笔记），用户态可移植代码不要依赖。

### `void*` 的别名特权

6.2 讲过严格别名：`char*` / `unsigned char*` / `void*` 可以别名任意类型。这就是 `memcpy`/`memset` 能用 `void*` 做参数的合法性来源——它们可以读写任何对象的底层字节而不违反别名规则。

### `void*` ≠ 函数指针

ISO C **不保证**函数指针与 `void*` 能互转（某些架构函数指针比数据指针大）。实测本机两者都是 8 字节、cast 能编译：

```c
void *q = (void*)f;   /* 函数指针 -> void*：本机可行，标准不保证 */
```

但跨平台只有 POSIX 兜底：POSIX 要求 `dlsym` 返回的 `void*` 能安全转回函数指针，所以动态加载场景这么写是合法的；裸 ISO C 场景不要互换。这也是 C 泛型回调传"上下文"时用 `void*` 参数、而不是把函数指针塞进 `void*` 的原因。

### 谁在用 `void*`：泛型接口全景

| 接口 | `void*` 的角色 |
|------|----------------|
| `malloc`/`calloc`/`realloc` | 返回原始内存，类型由调用者决定 |
| `memcpy`/`memmove`/`memset`/`memcmp` | 按字节操作，不问类型（别名特权） |
| `qsort`/`bsearch` | 比较回调 `int cmp(const void*, const void*)` + 显式传元素大小 |
| `pthread_create` | 线程入口 `void* (*)(void*)`，参数即上下文 |
| 内核 `file->private_data`、netdev `priv` | 驱动私有数据的通用挂点 |
| `dlsym` | 符号地址的统一返回类型（POSIX 保证可转函数指针） |

注意 `qsort` 的模式：**`void*` + 元素大小 + 比较函数**，三件套合起来把"类型"这件事从编译期挪到了运行期约定——C 泛型的全部代价与全部能力都在这。

## HFT / 嵌入式关联

| 场景 | 要点 |
|------|------|
| 内存池 / slab | 池分配器返回 `void*`（DPDK `rte_mempool_get` 就是 `void**` 出参），类型由调用者 cast 回收 |
| ring buffer / 报文解析 | 收到 `void*`/`uint8_t*` 基址 → cast 成 `packed` 协议头结构体（**6.2** 的合法路径） |
| 零拷贝回调 | 网卡/库回调统一 `void *ctx` 传用户上下文，热路径上零类型开销——cast 本身不生成任何指令 |
| 寄存器 / DMA | MMIO 地址、`ioremap` 返回值是 `void __iomem *`（内核用 `__iomem` 稀疏注解防止误解引用） |
| 裸机无 MMU | `void*` 指错类型不会崩，只会静默读错字节——和 **6.14** 的 NULL 解引用一样，裸机上这类 bug 没有硬件兜底 |

关键性能事实：**cast 是编译期概念，`void*` ↔ `T*` 转换在汇编层面是零指令**。用 `void*` 做通用接口不花一分钱运行时成本，代价全在"类型错了没人拦"。

## 常见误区

| 误区 | 事实 |
|------|------|
| "`void*` 是'空指针'" | 空指针是**值**（NULL，**6.6**），`void*` 是**类型**；两者正交，`void *q = NULL` 才把它们凑一起 |
| "`void*` 没有大小" | 指针本身有大小（8 字节）；没有大小的是它指向的 `void` |
| "`q + 1` 在所有编译器都是 1 字节" | 那是 GNU 扩展；`-pedantic-errors` 下是 error，MSVC 直接拒绝 |
| "C 里 `malloc` 必须强转返回值" | 恰好相反：隐式转换合法，强转会掩盖缺少 `malloc` 声明的警告（C++ 才必须转） |
| "`void*` 能存函数指针" | ISO C 不保证；只有 POSIX（`dlsym`）场景合法 |
| "cast 有运行时开销" | 指针 cast 零指令；它只改变编译器对位模式的解释方式（**6.2**） |

## 实操

```bash
# 本机（cdev 环境 clang 23.1.0）复现本文全部结论
CLANG=/Users/a0000/micromamba/envs/cdev/bin/clang

# 1. 解引用 void*：标准下 error
cat > t.c <<'EOF'
int main(void) {
    int x = 57;
    void *q = &x;
    char c = *q;
    return c;
}
EOF
$CLANG -std=c11 -pedantic-errors -c t.c -o /dev/null
# error: ISO C does not allow indirection on operand of type 'void *'

# 2. void* 算术：gnu11 放行，pedantic 报错
cat > t2.c <<'EOF'
int main(void) {
    int x = 57;
    void *q = &x;
    q = q + 1;
    return 0;
}
EOF
$CLANG -std=gnu11 -c t2.c -o /dev/null && echo "gnu11: OK"
$CLANG -std=c11 -pedantic-errors -c t2.c -o /dev/null
# error: arithmetic on a pointer to void is a GNU extension

# 3. C 隐式转、C++ 必须显式 cast
cat > t3.c <<'EOF'
int main(void) {
    int x = 57;
    void *q = &x;
    int *p = q;
    *p = 58;
    return x;
}
EOF
$CLANG -std=c11 -pedantic-errors -c t3.c -o /dev/null && echo "C11: OK"
cp t3.c t3.cpp
/Users/a0000/micromamba/envs/cdev/bin/clang++ -std=c++17 -c t3.cpp -o /dev/null
# error: cannot initialize a variable of type 'int *' with an lvalue of type 'void *'

# 4. GNU 扩展的 sizeof(void) == 1
echo '#include <stdio.h>
int main(void){ printf("%zu %zu\n", sizeof(void), sizeof(void*)); }' > t4.c
$CLANG -std=gnu11 t4.c -o t4 && ./t4        # 输出: 1 8
```

## 代码自测

**题目 1：** 下面这行代码里发生了几次类型转换，分别在谁身上？

```c
void *q = malloc(4);
((int*)q)[0] = 57;
```

<details>
<summary>参考答案</summary>

**两次显式/隐式转换，外加一次数组-指针等价：**

1. `malloc(4)` 返回 `void*`，赋给 `q`——同类型，无转换。
2. `(int*)q`：**显式 cast**，`void*` → `int*`，零指令，只改变解释方式。
3. `((int*)q)[0]`：`p[0]` 等价于 `*(p + 0)`（**6.13** 的数组-指针等价），这里 `+ 0` 步长为 `sizeof(int)=4`，但加 0 所以地址不变；解引用后写入 4 字节。

容易漏算的一点：`malloc` 的参数 `4` 是 `int`，函数原型要求 `size_t`，这里还有一次**隐式整型转换**——如果算上传参，共三处转换。

核心：`void*` 本身什么都没做，全部语义都是 cast 之后由 `int*` 赋予的。

</details>

**题目 2：** 下面代码在 `-std=gnu11` 下能编译运行，移植到 MSVC 直接报错。问题在哪两行？怎么改可移植？

```c
void advance(void **p, size_t n) {
    *p = *p + n;
}
```

<details>
<summary>参考答案</summary>

问题行就是函数体这一行（展开成两处错误）：

1. `*p + n`：对 `void*` 做算术——GNU 扩展按 1 字节步长放行，ISO C / MSVC 非法。
2. 整个表达式依赖"void 大小为 1"这个非标准假设。

可移植改法——**在函数内部显式转成 `char*` 再算**：

```c
void advance(void **p, size_t n) {
    *p = (char *)*p + n;
}
```

`char*` 算术是标准行为（步长恒 1 字节），效果与 GNU 扩展完全一致，但任何编译器都接受。这也是内核以外可移植代码处理"按字节推进通用指针"的标准写法。

</details>

**题目 3：** 为什么 `memcpy` 的签名是 `void *memcpy(void *dst, const void *src, size_t n)` 而不是给每种类型各写一份？它内部实现为什么合法？

<details>
<summary>参考答案</summary>

两个层面：

1. **接口层**：`void*` 是 C 唯一的泛型手段。任何对象指针都能隐式转 `void*`，所以一个签名服务所有类型——`memcpy(&a, &b, sizeof a)` 对 `int`、结构体、数组都成立。若按类型各写一份，新类型就无法复用。

2. **实现层**：严格别名规则给 `char` 类型开了特例——`char*`/`unsigned char*` 可以别名任何对象（**6.2**）。`memcpy` 内部把参数转回 `unsigned char*` 按字节拷贝，对任何类型都合法，编译器也不会因别名假设而优化错。

所以这个签名是"`void*` 泛型进、`char*` 别名出"的组合拳：`void*` 负责接口通用，`char*` 负责实现合法。

</details>
