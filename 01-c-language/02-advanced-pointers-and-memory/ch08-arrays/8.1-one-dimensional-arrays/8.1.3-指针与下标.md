# 8.1.3 指针与下标

## 本节讲什么

**`arr[i]` 和 `*(arr+i)` 不是"效果差不多"，是同一件事。** 这一节做五件事：

1. 把 `arr[i] ≡ *(arr+i)` 追到标准的**定义**上（不是语法糖，是定义本身）；
2. 把指针版 `for` 循环**逐段拆开**，每段给出标准依据；
3. 把最容易踩的边界讲清楚——**尾后指针可以比较、不能解引用**，以及**哪些指针比较是 UB**；
4. 破掉"指针内部就是一个整数"这个直觉（第七节）；
5. 讲清指针相减为什么返回 `ptrdiff_t`、为什么它与 `<` 受**同一条限制**（第八节）。

> 本节管**语法与语义**；"指针快还是下标快"是性能问题，归 [8.1.4 指针的效率](./8.1.4-指针的效率.md)。

---

## 一、恒等式是定义，不是"糖"

> **C11 §6.5.2.1p2**：A postfix expression followed by an expression in square brackets `[]` is a subscripted designation of an element of an array object. The definition of the subscript operator `[]` is that `E1[E2]` is identical to `(*((E1)+(E2)))`. Because of the conversion rules that apply to the binary `+` operator, if `E1` is an array object (equivalently, a pointer to the initial element of an array object) and `E2` is an integer, `E1[E2]` designates the `E2`-th element of `E1` (counting from zero).

标准用的词是 **identical to**（"等同于"），不是"等价于"或"化简为"。这条定义有三个直接推论，都值得记住：

| 推论 | 说明 |
|------|------|
| `arr[i]` 与 `*(arr+i)` **永远**可以互相替换 | 包括取地址：`&arr[i]` ≡ `&*(arr+i)` |
| **`3[arr]` 合法** | 因为 `+` 可交换：`3[arr]` → `*(3+arr)` → `*(arr+3)` → `arr[3]` |
| 下标运算符的左边**不必须是数组** | 只要是"指向某数组元素的指针"就行，这正是 `p[i]` 合法的原因 |

```c
int arr[5] = {10,20,30,40,50};
int *p = arr;

arr[2]   /* == *(arr+2) == 30 */
p[2]     /* == *(p+2)   == 30   ← p 是指针，一样合法 */
2[arr]   /* == *(2+arr) == 30   ← 合法但禁止写 */
```

**反向也成立**：`*(p+i)` 里 `p` 是数组名时，先退化再相加——所以 `*(arr+i)` 的第一步其实就是 `&arr[0] + i`。

## 二、指针版 for 循环：三段逐拆

```c
int arr[5] = {10,20,30,40,50};
int *p;
int n = 5;

for (p = arr;  p < arr + n;  p++)
{
    printf("%d\n", *p);
}
```

| 段 | 表达式 | 发生了什么 | 类型 | 标准依据 |
|---|--------|-----------|------|---------|
| **初始化** | `p = arr` | `arr` 退化成 `&arr[0]`，把首元素地址写进 `p` | `int *` | §6.3.2.1p3 |
| **条件** | `p < arr + n` | `arr + n` 算出**尾后指针**；关系比较见第五节 | `int` | §6.5.6p8、§6.5.8p5 |
| **迭代** | `p++` | `p = p + 1`，按 `sizeof(*p)` = 4 字节缩放 | `int *` | §6.5.6p8 |
| **循环体** | `*p` | 取出 `p` 所指的那个 `int` | `int` | §6.5.3.2 |

### 三个反直觉点

**① `p++` 不是"地址加 1"**

`p` 的类型是 `int *`，`p + 1` 的语义是"指向**下一个 int 元素**"，编译器把它算成"地址 + `sizeof(int)`"。换成 `double *` 就是 +8，`char *` 才是 +1。

```c
(char*)(p+1) - (char*)p   /* == 4，不是 1 */
```

> ⚠️ 缩放因子来自**指针所指类型**，不是指针自己的类型。`int **pp` 的 `pp+1` 跳 8 字节（8 字节的指针），跟 `int` 的 4 无关。

**② `arr + n` 不指向任何元素，但它是合法值**

`arr` 有 5 个元素，`arr + 5` 指向"第 5 个元素的后面"，那个位置**没有对象**。标准专门为它开了口子（见第五节）。

**③ 循环条件用 `<` 而不是 `<=`**

`p <= arr + n` 也能让循环正确跑完，但一旦 `p` 因为别的原因越过 `arr+n`，`<=` 会一直为假而退出、`<` 却可能一直为真——**边界表达式的选法决定了越界时的行为**。惯用 `<` 是因为它把"还没到尾部"写成了半开区间 `[arr, arr+n)`。

## 三、下标版与指针版：一一对应

```c
/* 下标版 */
for (int i = 0; i < n; i++)
    printf("%d\n", arr[i]);

/* 指针版 */
for (int *p = arr; p < arr + n; p++)
    printf("%d\n", *p);
```

| 下标版 | 指针版 | 角色 |
|--------|--------|------|
| `i` | `p` | 游标（一个是序号，一个是地址） |
| `i = 0` | `p = arr` | 起点 |
| `arr[i]` | `*p` | 取当前元素 |
| `i < n` | `p < arr + n` | 终止条件 |
| `i++` | `p++` | 前进一格（**都是前进一个元素**） |

**记住这张表的读法**：`i < n` 里的 `n` 是元素个数；`p < arr + n` 里的 `arr + n` 是"从 `arr` 出发走 `n` 个元素"的地址。两者都是**半开区间**。

## 四、走一遍内存

`int arr[5] = {10,20,30,40,50};`，实测地址（demo `t5_pointer_iter.c`）：

```
  &arr[0]=0x404030   arr+0=0x404030   值 10
  &arr[1]=0x404034   arr+1=0x404034   值 20
  &arr[2]=0x404038   arr+2=0x404038   值 30
  &arr[3]=0x40403c   arr+3=0x40403c   值 40
  &arr[4]=0x404040   arr+4=0x404040   值 50
  arr+5  =0x404044   ← 尾后 one-past-the-end，不存在的元素
```

循环逐步（实测输出）：

```
  p=0x404030  *p=10  p<(arr+5)=1   ← 第五次迭代：最后一个合法元素
  p=0x404034  *p=20  p<(arr+5)=1
  p=0x404038  *p=30  p<(arr+5)=1
  p=0x40403c  *p=40  p<(arr+5)=1
  p=0x404040  *p=50  p<(arr+5)=1
  退出时 p=0x404044，p<(arr+5)=0
```

注意最后一次迭代：`p = 0x404040`（**最后一个元素，仍可解引用**）→ 执行完 `p++` 得 `0x404044` → 比较为假 → 退出。**`arr+5` 这个值被计算出来了，但从未被解引用。**

> **验证环境**：本节 demo 最初在 WSL（gcc 13.3 / clang 18.1.3）上跑；后因本机 WSL 被安全策略拦截，改用 Compiler Explorer 复核（gcc 13.2 / clang 18.1.0）。两边输出一致——全局数组在 `-no-pie` 下的地址都从 `0x404030` 起，`(char*)(p+1)-(char*)p` 都是 4。唯一有差异的是第六节 T5.7 的 UB 比较方向（见该节）。

## 五、尾后指针：能比较，不能解引用

标准原文两句话讲完：

> **C11 §6.5.6p8**：If both the pointer operand and the result point to elements of the same array object, or one past the last element of the array object, the evaluation shall not produce an overflow; otherwise, the behavior is undefined. **If the result points one past the last element of the array object, it shall not be used as the operand of a unary `*` operator that is evaluated.**

拆成两条规则：

| 操作 | 合法性 |
|------|--------|
| **计算** `arr + n`（尾后） | ✅ 合法，不算 overflow |
| **计算** `arr + n + 1`（越过尾后） | ❌ UB——连"算出来"都不行 |
| **解引用** `*(arr + n)` | ❌ UB |
| **比较** `p < arr + n` | ✅ 合法（§6.5.8p5） |
| **取地址** `&arr[n]` | ✅ 合法（`&` 与 `[]` 隐含的 `*` 相互抵消，只有加法被求值） |

> `&arr[n]` 这一条容易被忽略：cppreference 对此的说法是"`&a[N]` 对大小为 N 的数组是有效的（取得尾后指针没问题，解引用不行，但在这个表达式里解引用被抵消了）"。

### 解引用尾后的实测代价

`int g[5] = {1,2,3,4,5};` 读 `g[5]`（下标退化成 `*(g+5)`），两种编译方式对比：

```
=== 挂 ASan（clang 18.1.3, -fsanitize=address）===
==463==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x740770f00034
READ of size 4 at 0x740770f00034 thread T0
    #0 0x503860 in main /tmp/t5_oob.c:5:13

=== 不挂 ASan（gcc 13.3, -O0）===
读到 = 32767
exit=0
```

**同一个程序，不挂 ASan 时读到一个"看起来像垃圾但程序照常退出"的值。** 这就是越界最危险的地方——它不保证崩，只保证没有语义。

> 注意：这里读到的 `32767` 是**栈上残留数据**——同一二进制两次运行分别得到 `32764` 和 `32767`，数值本身毫无意义。UB 的表现形式由编译器、优化级别、栈布局、甚至环境变量共同决定。

## 六、关系比较的合法边界（本节最重要）

> **C11 §6.5.8p5**：When two pointers are compared, the result depends on the relative locations in the address space of the objects pointed to. If two pointers to object types both point to the same object, or both point one past the last element of the same array object, they compare equal. ... If the expression `P` points to an element of an array object and the expression `Q` points to the last element of the same array object, the pointer expression `Q+1` compares greater than `P`. **In all other cases, the behavior is undefined.**

| 比较对象 | `<` `>` `<=` `>=` | `==` `!=` |
|---------|------------------|----------|
| 同一数组的两个元素 | ✅ 下标大的更大 | ✅ 有定义 |
| 元素 vs **同一数组的尾后** | ✅ 元素 < 尾后 | ✅ 有定义 |
| **两个不同数组**的元素（含各自的尾后） | ❌ **UB** | ✅ **有定义**（除非恰好首尾相接，见下） |
| 结构体不同成员 | ✅ 声明靠后的更大 | ✅ |
| 联合体成员之间 | ✅ 全部相等 | ✅ |

**这张表最容易背错的是第 4 行**——"指针不能比较"是半对半错：

- **关系运算符**（`<` `>` `<=` `>=`）：不同数组之间**未定义**。
- **相等运算符**（`==` `!=`）：不同数组之间**有定义**。C11 §6.5.9p6 说两个指针相等当且仅当：都是空指针 / 指向同一对象或函数 / 都指向同一数组的尾后 / 一个是某数组的尾后而另一个**恰好紧接其后**的另一个数组的首元素。

所以 `if (p == q)` 是安全的（结果多半是"不等"），`if (p < q)` 在跨数组时不是。

### 实测：UB 长得像"正常工作"，还会随编译器翻脸

demo `t5_pointer_iter.c` 的 T5.7 把两个不同数组的指针传进一个 `noinline` 函数做 `<` 比较。**同一份源码，两个编译器给出互为相反的答案**：

```
=== gcc 13.2, -O0 ===          === clang 18.1.0, -O2 ===
  raw_lt(x, y) = 0               raw_lt(x, y) = 1
  raw_lt(y, x) = 1               raw_lt(y, x) = 0
```

两边都"看起来完全符合直觉"——总有某个数组的地址更小，所以总有一个方向为真。**方向却恰好相反**：`x`、`y` 在栈上谁前谁后由编译器决定，不由标准决定。这就是 UB 的教科书形态——**结果可复现、可解释，但不可依赖**。

> 更糟的是 **ASan/UBSan 都抓不到它**（实测 `-fsanitize=address` + `ASAN_OPTIONS=detect_invalid_pointer_pairs=2` 无输出，gcc `-fsanitize=undefined` 全程序 exit 0）。**"工具没报"从来不等于"合法"。**

工程结论只有一条：**别拿 `<` 比较无关的指针**。要判断两个指针谁在前，先问"它们属于同一个数组吗"——不属于就别比。

## 七、先破一个直觉：指针不是整数

> **C11 §6.3.2.3p6**：Any pointer type may be converted to an integer type. Except as previously specified, the result is **implementation-defined**. If the result cannot be represented in the integer type, the behavior is undefined. The result **need not be in the range of values of any integer type**.

"指针里面存的本质就是一个 `uint64` 地址数字"——这句话在 x86-64 / aarch64 的平坦地址空间上是**观察结果**，但它不是标准保证，也不能当推理前提。标准只承诺三件事：转换是 **implementation-defined**；转不下就是 UB；**指针可以比任何整数类型能表达的范围更大**（最后半句尤其反直觉，等于承认"指针 ≅ 整数"这个模型本身不完备）。

| 平台 | 为什么指针 ≠ 整数 |
|------|------------------|
| x86 实模式 / 16 位分段 | far pointer 是 `seg:off` 两个数，没有唯一的线性数值可比 |
| CHERI（能力指针硬件） | 指针 128 位，低 64 位是地址、高位是边界与权限 tag，任意整数转换会破坏 tag |
| 带 provenance 的实现（C23 起标准正式引入） | 数值相同但"来历"不同的指针可以表现不同 |

### 那"转成整数再比大小"算绕过 UB 吗？

```c
/* 想判断两个缓冲的先后，绕开指针比较 */
if ((uintptr_t)p < (uintptr_t)q) { ... }
```

**严格说它绕开了 §6.5.8p5**——被比较的是两个整数，不是指针，所以不触发那条约束。但它并没有变"合法"，只是把**未定义行为**换成了**实现定义的结果**：转换本身就 implementation-defined，你依赖的仍然是没人向你承诺的东西。

> 工程结论只有一句：**指针的比较与加减，语义层在"它指向哪个数组的哪个元素"，不在"地址数字谁大"。** 要比较先后，比的是**下标 / 序号**，不是指针本身。

## 八、指针相减：`ptrdiff_t`

> **C11 §6.5.6p9**：When two pointers are subtracted, **both shall point to elements of the same array object, or one past the last element of the array object**; the result is **the difference of the subscripts** of the two array elements. The size of the result is implementation-defined, and its type (a signed integer type) is `ptrdiff_t` defined in the `<stddef.h>` header. If the result is not representable in an object of that type, the behavior is undefined. In other words, if the expressions `P` and `Q` point to, respectively, the i-th and j-th elements of an array object, the expression `(P)-(Q)` has the value `i-j` provided the value fits in an object of type `ptrdiff_t`.

| 项 | 说明 |
|---|------|
| **前提** | 双方都必须指向**同一个数组**（或尾后）—— 与 `<` 是同一条限制 |
| **结果语义** | **下标之差 `i - j`**，不是字节差 |
| **类型** | `ptrdiff_t`：**有符号**整数类型，定义在 `<stddef.h>` |
| **大小** | implementation-defined（x86-64 上是 8 字节） |
| **溢出** | 结果放不进 `ptrdiff_t` → UB |

### 三个量别混

```c
const int *p1 = &g[1], *p2 = &g[4];

p2 - p1                     /*  3  ← 下标差（元素个数） */
(const char*)p2 - (const char*)p1   /* 12  ← 字节差 = 3 × sizeof(int) */
sizeof(ptrdiff_t)           /*  8  ← 有符号，所以结果可以是负数 */
```

demo T5.5 实测到 `p2 - p1 = 3`。**指针相减自动除以元素大小**，所以你拿到的是"隔了几个元素"，不是"隔了几个字节"；想要字节差必须先转成 `char *`。

### 相减也受"同数组"限制（常被漏掉）

很多人记住了"比较受限"，却忘了**相减受同一条锁约束**：

```c
int a[4], b[4];
ptrdiff_t d = &b[0] - &a[0];   /* ❌ UB —— 跨数组相减 */
```

把三条规则放一起看：

| 操作 | 要求同数组？ |
|------|-------------|
| `p + n` / `p - n`（指针 ± 整数） | 结果须落在 `[首元素, 尾后]` 内 |
| `p < q`（关系比较） | ✅ 必须同数组（含尾后） |
| `p - q`（指针相减） | ✅ **必须同数组**（含尾后） |
| `p == q`（相等比较） | ❌ 不要求（§6.5.9p6） |

### `ptrdiff_t` vs `size_t`

| | `ptrdiff_t` | `size_t` |
|---|---|---|
| 符号 | **有符号** | 无符号 |
| 用途 | 指针相减、可能为负的偏移 | `sizeof`、元素个数、下标 |
| 经典坑 | — | `size_t n = 0; if (n - 1 > 0)` **恒真**（无符号下溢成巨大值） |

> 一句话记法：**做减法用 `ptrdiff_t`，做计数用 `size_t`。** 混用时的下溢/符号提升问题，是这类面试题的主要来源。

## 九、`<` 还是 `!=`？

数组范围内 `p != end` 和 `p < end` 等价，但**容错性不同**：

```c
/* 游标每次前进 1：两者都对 */
for (p = arr; p != arr + n; p++) ...

/* 游标可能一次跳多个：!= 有死循环风险 */
for (p = arr; p != arr + n; p += step)   /* step=3, n=5 时永远踩不到 arr+5 */
```

| 条件 | 步长可控时 | 游标可能跳过终点时 |
|------|-----------|------------------|
| `p < end` | 正确 | **安全退出**（虽然可能提前/不完整） |
| `p != end` | 正确 | **死循环 + 越界**（一直加下去） |

惯用 `<` 是因为它把"越过终点"当成了终止条件而不是"永远到不了"。

## 十、底层映射：为什么两种写法最终一样

```c
int sum_idx(const int *arr, int n) {           int sum_ptr(const int *arr, int n) {
    int s = 0;                                     int s = 0;
    for (int i = 0; i < n; i++) s += arr[i];       const int *p;
    return s;                                      for (p = arr; p < arr + n; p++) s += *p;
}                                                  return s;
                                               }
```

`gcc -O2 -S` 后**核心循环完全相同**：

```asm
.L1:
    add     eax, DWORD PTR [rdi + rcx*4]   ; 下标版：基址 + 变址×4
    inc     rcx
    cmp     ecx, edx
    jl      .L1
```

编译器前端把 `arr[i]`、`*(p+i)`、`*p++` 都降成同一份 IR，后端按 x86 的比例变址寻址模式生成指令，**没有额外乘法**。所以"指针遍历一定更快"是 1970 年代的直觉，不是 2020 年代的事实——完整论证（含 `restrict` 这条真正影响性能的通道）见 [8.1.4](./8.1.4-指针的效率.md)。

## 何时指针风格更清晰

- **遍历连续区间**：`for (p = begin; p < end; p++)` 的"游标"语义 —— 两个指针夹出一个半开区间
- **字符串**：`while (*s) s++;`
- **报文偏移**：`uint8_t *p = pkt; p += parse_hdr(p);`

## 何时下标更清晰

- **多维访问**：`tbl[i][j]` 比 `*(*(tbl+i)+j)` 易读
- **随机访问**：`arr[rand_idx]`
- **固定位置**：`header->fields[3]`

## HFT / DPDK

| 场景 | 写法 | 为什么 |
|------|------|--------|
| 连续报文遍历 | `for (p = buf; p < buf + len; p++)` | 半开区间，边界清晰 |
| 边界校验 | `if (p + need > end) return -1;` | 依赖"尾后指针可用作比较"这一条 |
| 解析变长头 | `p += sizeof(*h);` | 步长由类型决定，天然正确 |
| 多维表 | `tbl[i][j]` | 可读性 |
| 批量收包 | `pkts[i]` | 下标 + 固定数组 |

> ⚠️ **两个独立缓冲的指针不要用 `<` 比大小**。HFT 里常见"比较两个 mbuf 谁先入队"，如果它们来自不同内存池，`<` 就是 UB。用序号 / 时间戳代替指针比较。

## 常见误区

| 误区 | 事实 |
|------|------|
| "`p++` 就是地址加 1" | 按 `sizeof(*p)` 缩放；`int *` 是 +4 |
| "`arr+n` 指向最后一个元素" | 指向最后一个元素的**后面**，是尾后指针 |
| "只要不解引用，指针随便算" | `arr+n+1` 连**形成**都是 UB（§6.5.6p8） |
| "任何两个指针都能比大小" | 关系运算符只对同数组（含尾后）有定义；`==`/`!=` 宽松得多 |
| "能跑出正确结果就是对的" | UB 常常"结果正确"；实测 T5.7 的跨数组 `<` 在 gcc / clang 上**答案相反**，却两边都看着正常 |
| "ASan 没报就没问题" | 实测跨数组比较 ASan/UBSan 均无输出 |
| "`arr[i]` 只是 `*(arr+i)` 的语法糖" | 标准用 "identical to"，它就是**定义** |
| "下标比指针慢，因为有乘法" | 比例变址是硬件寻址模式，无 `imul`；见 [8.1.4](./8.1.4-指针的效率.md) |
| "`3[arr]` 是错的" | 标准合法（`*(3+arr)`），但工程里禁止写 |

## 自测要点

1. `arr[i] ≡ *(arr+i)`：标准用的是"等价"还是"等同于"？在哪一条？
2. 指针版循环的三段各自依据哪条标准？`p++` 为什么不是 +1 字节？
3. `arr + n` 是合法值吗？它能不能被解引用？标准原文怎么说？
4. `arr + n + 1` 呢？它和 `*(arr + n)` 的非法性有区别吗？
5. 两个不同数组的指针：用 `<` 比较会怎样？用 `==` 比较呢？为什么两者不同？
6. 为什么循环条件惯用 `p < end` 而不是 `p != end`？
7. "指针内部就是一个 `uint64` 地址"——这句话在标准层面哪里站不住？转成 `uintptr_t` 再比大小，算绕过 UB 吗？

9. 同一份跨数组比较的代码，为什么 gcc 和 clang 能给出**相反**的结果？这说明"跑对了"和"合法"是什么关系？

## 代码自测

**题目 1：** 下面 `*p` 的结果是什么？

```c
int arr[3] = {1, 2, 3};
int *p = arr;
p = p + 2;
/* *p = ? */
```

<details>
<summary>参考答案</summary>

**`3`**（即 `arr[2]`）。

拆解：`p = arr` 时 `p == &arr[0]`；`p + 2` 按 `sizeof(int)` 跳 2 格，落到 `&arr[2]`；解引用得 `arr[2] == 3`。

`p + 2` 仍在数组内（合法），所以这一步没有任何 UB。**但再走一格就是边界了**：`p + 3 == &arr[3]` 是尾后指针（可以比较，不能解引用），`p + 4` 连形成都是 UB。

实测（demo `t5_pointer_iter.c` T5.4）：

```
  a[3]={1,2,3}, p=a, p=p+2  ->  *p = 3   （即 a[2]）
  验证 p == &a[2] : 1
```

</details>

**题目 2：** 这段循环有什么问题？

```c
int a[6] = {1,2,3,4,5,6};
for (int *p = a; p != a + 6; p += 2)
    printf("%d ", *p);
```

<details>
<summary>参考答案</summary>

**死循环 + 越界**。

`p` 的取值依次是 `a+0, a+2, a+4, a+6`——第四步就撞上了 `a+6`，循环正常退出。但把数组改成 5 个元素（奇长度）时：`p` 走 `a+0, a+2, a+4, a+6, a+8, ...`，**永远踩不到 `a+5`**，`p != a+5` 恒为真。

更糟的是 `a+6` 之后每步都在形成越界指针——按 C11 §6.5.6p8，`a+7` 及以上全是 UB。

改正：用 `<` 或让步长整除长度。

```c
for (int *p = a; p < a + 6; p += 2)   /* ✅ 安全退出 */
```

</details>

**题目 3：** 结果是 `1` 还是 `0`？合法吗？

```c
int arr[4];
int *p = arr + 3;
int *q = arr + 4;
printf("%d", p < q);
```

<details>
<summary>参考答案</summary>

**输出 `1`，合法。**

三段拆开看：

1. `q = arr + 4` 是**尾后指针**——§6.5.6p8 明确允许**形成**它（不算 overflow），只是不能解引用。
2. `p`（即 `&arr[3]`，最后一个元素）与 `q`（尾后）**同属 `arr`**，满足 §6.5.8p5 的前提条件。
3. 结果不是"机器上凑巧比出来的数字大小"，而是标准**明确规定**的。§6.5.8p5 末句：

> If the expression `P` points to an element of an array object and the expression `Q` points to the last element of the same array object, the pointer expression `Q+1` compares greater than `P`.

这里取 `P = arr+3`、`Q = arr+3`（最后一个元素）、`Q+1 = arr+4` → 必然 `arr+3 < arr+4`，即输出 `1`。

由此展开的三个结论：

| 表达式 | 结果 | 依据 |
|--------|------|------|
| `p < q` | `1` | 同数组的「元素 vs 尾后」，标准保证 |
| `*q` | ❌ UB | 尾后指针不可解引用（§6.5.6p8） |
| `q - p` | `1` | 同数组可相减，返回下标差（§6.5.6p9） |

**对照记忆**：这里 `p < q` 合法，而题目 2 里两个无关数组比较是 UB——**差别不在"能不能算出地址数字"，而在"是否属于同一个数组"。**

</details>
