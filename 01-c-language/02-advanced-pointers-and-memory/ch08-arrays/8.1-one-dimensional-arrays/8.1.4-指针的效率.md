# 8.1.4 指针的效率

## 本节讲什么

**指针访问数组 vs 下标访问数组**——这两种写法在历史上有性能差异，但在现代编译器（GCC/Clang `-O2` 以上）下**通常生成相同机器码**。本节拆解"指针更快"这个半世纪老观念是怎么来的、何时仍然成立、以及为什么在 HFT 场景下它根本不是性能瓶颈。

## 历史背景：为什么本书专门讨论这个

- **1970s–80s**：早期 C 编译器优化薄弱，`arr[i]` 真的会编译成"基址 + i×sizeof + 解引用"三步；而 `*p++` 在 PDP-11 上有**自增寻址**指令 `(R0)+`，一条指令完成取值和指针前移 → 指针遍历确实更快。
- **《C 和指针》成书的 90 年代**：作者仍在讨论这个差异，因为商业编译器优化参差不齐。
- **今天（GCC 13 / Clang 17 + `-O2`）**：下标循环和指针循环几乎总是被优化成**相同的中间表示**，差异消失。所以这节的价值不在"学会用指针提速"，而在**理解编译器怎么对待数组访问**，为后面 restrict、向量化打基础。

## 三种写法对比

```c
/* 写法 A：下标 */
int sum_a(const int *arr, int n) {
    int s = 0;
    for (int i = 0; i < n; i++)
        s += arr[i];
    return s;
}

/* 写法 B：指针 + 下标 */
int sum_b(const int *arr, int n) {
    int s = 0;
    const int *p = arr;
    for (int i = 0; i < n; i++)
        s += *(p + i);
    return s;
}

/* 写法 C：指针自增 */
int sum_c(const int *arr, int n) {
    int s = 0;
    const int *p = arr;
    for (int i = 0; i < n; i++)
        s += *p++;
    return s;
}
```

> 三个函数在 `gcc -O2` 下生成的核心循环汇编**完全一致**（见下一节）。

## 编译器视角：x86-64 汇编证据

`gcc -O2 -S` 后，三个函数的核心循环都是这样的形式（寄存器名可能不同）：

```asm
.L3:
    add    eax, DWORD PTR [rdi+rcx*4]   ; s += arr[i]
    add    rcx, 1
    cmp    edx, ecx
    jg     .L3
```

关键点：

| 观察 | 含义 |
|------|------|
| `[rdi + rcx*4]` | **基址 + 变址×比例寻址**，x86 单条指令完成 `arr[i]`，没有额外乘法 |
| 没有 `imul` | 比例因子 `4`（`sizeof(int)`）由寻址模式硬件处理，不是真乘法 |
| 三种写法归一 | 编译器前端把 `arr[i]`、`*(p+i)`、`*p++` 都降成相同的 GIMPLE/IR |

**结论**：在 `-O2` 下争论"指针快还是下标快"没有意义——它们是同一段机器码。

## 何时指针**真的**更快

差异只在以下场景重新出现：

1. **`-O0` 或 `-Og` 调试构建**：编译器不做归一化，下标写法可能多一条地址计算。HFT 生产环境从不这么编译，但单测覆盖率常在 `-O0` 跑，要注意基准测试别在 `-O0` 下做。
2. **指针链式遍历有状态**：如遍历链表/解析变长报文字段时，`p = (struct hdr *)p + 1` 这种"步进依赖前一步结果"的写法，下标表达不直观，指针更自然——但这其实是**可读性**优势，不是速度优势。
3. **`restrict` 配合**：`int *restrict p` 承诺无别名后，指针版有时能触发更激进的向量化（见后文）。

## 何时下标**更好**

- **随机访问** `arr[k]`：`k` 不是顺序递增时，下标语义清晰，指针要算偏移反而绕。
- **多维数组** `mat[i][j]`：下标可读性远胜 `*(*(mat+i)+j)`，且编译器一样优化得好。
- **调试**：下标在 gdb 里 `print arr[i]` 更直观，`print *(p+i)` 麻烦。
- **静态分析 / 边界检查**：很多 sanitizer 和静态工具对下标越界检查更友好。

## HFT 实战：真正的性能在哪里

这一节对 HFT 学习者的真正价值，是建立**性能直觉的优先级**：

```
影响数组访问性能的因素（由大到小）
┌──────────────────────────────────────┬──────────────┐
│ 缓存局部性（连续 vs 随机访问）         │ ~100x        │  ← 主战场
│ 对齐与缓存行边界（64B）                │ ~10x         │
│ restrict / __restrict__（允许向量化）  │ ~2-4x        │
│ 预取（sw prefetch / hw stream）        │ ~2x          │
│ 数据布局（SoA vs AoS）                 │ ~2x          │
├──────────────────────────────────────┼──────────────┤
│ 指针 vs 下标（-O2 下）                 │ ~1x（无差异）│  ← 本节
└──────────────────────────────────────┴──────────────┘
```

**口诀**：下标还是指针是**风格问题**；连续还是离散访问、对不对齐、有没有别名，才是**性能问题**。

具体场景：

- **DPDK 收包循环** `for (i=0; i<nb_rx; i++) bufs[i] = ...`——用下标，编译器向量化得很好；瓶颈在 DDR 带宽和 cache miss，不在写法。
- **解析定长报文头**：`struct eth_hdr *h = (void *)p; p += sizeof(*h);`——用指针步进，因为步长是变的、类型是变的，下标表达不了。
- **批量处理订单数组**：`orders[i].price`——用下标；但要注意 `orders` 是否紧凑（有无 padding）、是否跨缓存行，这比写法重要 100 倍。

## 编译器向量化：`restrict` 到底在放开什么

上面那张优先级表把 `restrict` 记作「允许向量化」（~2-4x）。**这个说法需要修正**——实测下来
`restrict` 并不决定"能不能"向量化。先补上向量化是什么，再回来看它到底值多少。

**定义**：编译器向量化（auto-vectorization）= 编译器**自动**把"循环里一次算 1 个元素"改写成"一条 SIMD 指令一次算 N 个"。你一行 SIMD 代码都没写，是它替你改的。

> 区别于 **intrinsic 手动向量化**：那是你自己写 `_mm256_add_epi32(...)`。本节的落点是前者——**你不写 SIMD，但你要写"编译器敢向量化"的代码**。

它之所以可能，是因为 CPU 有**向量寄存器**（一个寄存器装好几个数，一条指令同时算）：

| 指令集 | 寄存器宽度 | 一条指令算几个 `int32` | 开法 |
|--------|-----------|----------------------|------|
| SSE2 | 128 bit | 4 | x86-64 基线，一定可用 |
| **AVX2** | 256 bit | **8** | `-mavx2` / `-march=x86-64-v3` |
| AVX-512 | 512 bit | 16 | 需确认 CPU 型号，HFT 云主机要问清楚 |
| NEON | 128 bit | 4 | ARM64（Pi 5 / Graviton） |

### 同一段循环的两种下场

```c
void add(int n, int *a, int *b, int *c) {
    for (int i = 0; i < n; i++) c[i] = a[i] + b[i];
}
```

```
标量：循环 n 遍                    向量化（AVX2）：循环 n/8 遍
  c[0] = a[0] + b[0]                 load  a[0..7] -> ymm0
  c[1] = a[1] + b[1]                 load  b[0..7] -> ymm1
  ...                                vpaddd ymm0, ymm1 -> ymm2
  c[7] = a[7] + b[7]                 store c[0..7] <- ymm2
  ↑ 8 条 add + 8 次循环判断           ↑ 1 条 vpaddd + 1 次循环判断
```

### ⭐ 实测：先过「代价模型」这一关，才轮到 `restrict`

这里有个**反直觉的事实**——要靠实测（Compiler Explorer，x86-64 **gcc 13.3**）才看得出来：

```c
void add  (int n, int *a,          int *b,          int *c)          { for (int i=0;i<n;i++) c[i]=a[i]+b[i]; }
void add_r(int n, int *restrict a, int *restrict b, int *restrict c) { for (int i=0;i<n;i++) c[i]=a[i]+b[i]; }
```

| 编译选项 | `add`（无 `restrict`） | `add_r`（有 `restrict`） |
|---------|----------------------|------------------------|
| `-O2 -mavx2` | ❌ 纯标量，一条向量指令都没有 | ❌ 同样纯标量 |
| `-O3`（SSE2 基线） | ✅ `movdqu` + `paddd`（4 个 int / 次） | ✅ 同样 |
| `-O3 -mavx2` | ✅ `vpaddd ymm`（8 个 int / 次）+ **运行时别名检查** | ✅ `vpaddd ymm`，**无别名检查** |
| `-O2 -fvect-cost-model=dynamic` | ✅ `vpaddd ymm` | ✅ |

**结论：`restrict` 不是"能不能向量化"的开关，而是"要不要多付一段运行时检查"的开关。**

#### 为什么 `-O2` 不向量化，`-O3` 才行

不是 `-O2` 关掉了向量化 pass——问编译器自己（`gcc -Q --help=optimizers`）：

| 选项 | `-ftree-loop-vectorize` | `-fvect-cost-model` | 实测结果 |
|------|------------------------|--------------------|---------|
| `-O2` | enabled | **very-cheap** | ❌ 拒绝 |
| `-O2 -ftree-vectorize` | enabled | cheap | ✅ 通过 |
| `-O3` | enabled | **dynamic** | ✅ 通过 |

卡点是**代价模型**：`very-cheap` 太保守，这个循环它算不过账 → 直接放弃；
换成 `dynamic`（`-O3` 的默认）就放行。

> **`-O2` 下"我写了向量友好的代码"可能白写**——这是 HFT 里性能关键模块要单独上 `-O3`
> （或显式 `-ftree-vectorize`）而不全局 `-O2` 的一个现实理由。

#### `restrict` 到底省了什么

`-O3 -mavx2` 下，无 `restrict` 的 `add` **多带一段运行时别名检查**：

```asm
; add（无 restrict）：先检查 a、b 与 c 会不会重叠
        lea     r10, [rdi+4]      ; a + 1
        sub     rcx, r10          ; c - (a+1)
        cmp     rcx, 24
        jbe     .L3               ; ← 可能重叠 → 退回标量循环
        lea     r10, [r8+4]       ; b + 1
        mov     rcx, rsi
        sub     rcx, r10          ; c - (b+1)
        cmp     rcx, 24
        jbe     .L3               ; ← 可能重叠 → 退回标量循环
```

`add_r` 里**没有这几条**——编译器信了你的承诺，直接进 `vpaddd ymm` 循环。
所以 `restrict` 的收益是**每次调用省几条比较跳转 + 少一套代码**（代码更小 → icache 更友好），
**不是"从标量变向量"**。这也解释了它在开头优先级表里为什么只值 ~2-4x。

#### 真正挡路的障碍

| 障碍 | 例子 | 能救吗 |
|------|------|-------|
| 迭代间有数据依赖 | 前缀和 `a[i] += a[i-1]` | ❌ 换算法（如两遍扫描） |
| 访问不连续 | `a[i * 8]` 跨步 | ❌ 改数据布局（AoS → SoA） |
| 循环内有分支 | `if (a[i] > 0) ...` | 部分可用掩码 / 条件传送 |
| **代价模型不批** | `-O2` 默认配置 | ✅ 上 `-O3` / `-fvect-cost-model=dynamic` |
| 潜在别名 | `add` vs `add_r` | ✅ `restrict`（不决定"能否"，只决定"多付多少"） |

### 怎么确认到底向量化了没有

```bash
gcc -O3 -march=native -fopt-info-vec-optimized -c t.c   # 打印哪些循环被向量化
gcc -O3 -march=native -S t.c                            # 汇编里找 vpaddd / vfmadd / vmovdqu
gcc -O3 -Q --help=optimizers | grep -i vect             # 确认代价模型是 dynamic 还是 very-cheap
```

`-fopt-info-vec-optimized` 会打出 `t.c:3:5: optimized: loop vectorized using 32 byte vectors` 这类行。
**"我加了 `restrict` 应该就向量化了吧"不算结论**——上面那张实测表正是反例：
`-O2` 下加了 `restrict` 照样一条向量指令都没有。

> ⚠️ **搜汇编时两种编码都要覆盖**：AVX 下是 `vpaddd`，SSE2 基线（不加 `-mavx2`）下是 `paddd`
> ——只搜 `vpadd` 会把后者的向量化整个漏掉。

### HFT 视角：别本末倒置

本页开头那张优先级表里，向量化标的是 **~2-4x**，但它排在**缓存局部性（~100x）下面整整一档**。
所以正确用法**不是**手写 SIMD 提速，而是：

1. **先确认编译选项对**——`-O2` 下很多循环压根不向量化（见上表）；
2. **写成编译器容易向量化的形状**——连续访问、循环内无分支、该加 `restrict` 的地方加上；
3. **用汇编或 `-fopt-info` 确认它真的发生了**（不要假设）；
4. **基准测试验证收益**——`-O3` 不总更快，激进向量化会带来代码膨胀和 icache 压力。

> ⚠️ **违反 `restrict` 承诺不是"慢"，是 UB。** 编译器按"无别名"前提生成的向量代码，
> 在真出现别名时行为不由标准定义——这比性能问题严重得多。

**延伸**：《CSAPP》ch5「优化程序性能」把循环展开、向量化、缓存友好讲成一套系统方法论，是本节的学术升级版。

## `restrict`：真正影响优化的关键字

`restrict`（C99）是**指针承诺无别名**——告诉编译器"我保证这段内存没有别的指针会改"，允许它做向量化、重排、省 reload：

```c
/* 无承诺：编译器保守，不能向量化（怕 aliased） */
void add(int *a, int *b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}

/* 有承诺：可向量化成 SIMD */
void add_r(int *restrict a, int *restrict b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}
```

`add_r` 在 `-O3 -mavx2` 下展开成 `vpaddd ymm`，一次处理 8 个 int（上一节实测）。
**但要注意：`add` 也会被向量化**——`-O3` 会自己插入运行时别名检查（见上节的汇编原文），
`restrict` 省掉的是**那段检查**，不是"从标量变向量"。
这才是**指针写法能影响性能**的真正通道——通过 `restrict` 承诺，而不是通过 `*p++`。

> 违反 `restrict` 承诺是 **UB**（未定义行为），HFT 代码里用错会比"慢"严重得多。

## 常见误区

| 误区 | 纠正 |
|------|------|
| "用指针遍历数组一定比下标快" | 现代 `-O2` 下两者机器码相同，这是 70 年代观念 |
| "手动写 `*p++` 比让编译器优化 `arr[i]` 更聪明" | 编译器比你更懂目标 ISA 的寻址模式 |
| "`-O3` 总是更快" | `-O3` 会激进内联和向量化，但也可能触发代码膨胀、icache 压力，HFT 实战要**基准测试**而非盲信 |
| "下标越界只是慢" | 越界是 UB，可能恰好"正常"运行数月后某次崩溃——绝不能靠"没崩就没事"判断 |
| "优化就是手写 SIMD" | 编译器会**自动**向量化。先写"它敢向量化"的代码（连续访问 + 无别名 + 循环内无分支），再谈要不要手写 intrinsic |
| "加了 `restrict` 就会向量化" | 实测反例：`-O2` 下加了 `restrict` 照样不向量化（代价模型 `very-cheap` 拒绝）；`-O3` 下不加 `restrict` 也照样向量化。`restrict` 省的是**运行时别名检查**，不是"开不开启向量化" |

## 实操

1. **godbolt.org**：把上面三个 `sum_*` 函数贴进去，`x86-64 gcc 13 -O2`，勾选"Filters → Directives"，肉眼比对核心循环是否一致。
2. 改 `-O0`，观察下标版是否多出 `mov`/`lea`。

## 代码自测

**题目 1：** 以下代码中 p2 - p1 的值是多少？
```c
int arr[5] = {1, 2, 3, 4, 5};
int *p1 = &arr[1];
int *p2 = &arr[3];
printf("%d\n", p2 - p1);
```

<details>
<summary>参考答案</summary>

输出 2。指针减法返回的是元素个数，不是字节数。p2 指向 arr[3]，p1 指向 arr[1]，相差 2 个 int。实际字节差是 2 * sizeof(int)，但指针减法自动除以 sizeof(int)。

</details>
