# 7.2.5 不用 #include，手写 extern 声明行不行

## 本节讲什么

**直接结论：行。编译器只要求"调用点可见一份声明"，`#include` 不是调用的必要条件——但头文件的真正职责不是"让编译通过"，而是保证所有翻译单元手里的声明是同一份。** C 和 C++ 都能这么干，但声明写错时的下场完全不同：C 静默链接成功、运行期损坏（→ **7.2.3**）；C++ 靠 name mangling 在**链接期直接报错**（→ **7.2.4**）。本节把这条链路一次收口。

## 要点

### 先拆误解：#include 与链接器无关

`#include` 是**预处理器**的文本粘贴（→ 7.2 主节"include 的本质"），它只决定"编译这个 TU 时声明可不可见"。链接器根本不知道头文件存在——它拿到的是 `.o`，配对的依据是**符号**。所以：

```
编译器管的：调用点有没有声明可看（没有 → 隐式声明/报错，见 7.2.2）
链接器管的：未定义符号 U 能不能找到同名 T 定义（见 6.10.2）
#include 管的：把声明文本贴进来，仅此而已
```

手写 `extern int add(int, int);` 和把这句话写进 `.h` 再 include，**对编译器来说一字不差**。

### 实测一：C，手写声明直接调（clang 23, macOS arm64）

```c
/* b.c */                          /* a.c */
int add(int a, int b)              extern int add(int, int);
{ return a + b; }                  int main(void) { return add(1, 2); }
```

```bash
$ clang a.c b.c -o c_ok && ./c_ok; echo $?    # 3 —— 不 include 任何东西，全链路通过
$ clang -c b.c && nm b.o
0000000000000000 T _add            # Mach-O 符号带前导下划线；Linux 上是 T add
```

两个细节：

- 对函数，`extern` 可以省——函数声明默认外部链接（→ 7.2 主节"声明隐含 extern"）；**全局变量才必须写** `extern`（→ 7.2 主节三步走）。
- 另一个 TU 的函数**必须**有可见声明，不写会触发旧式隐式声明（C99 起违法，→ **7.2.2**）。

### 实测二：C，声明写错了——编译链接全静默

```c
/* a_bad.c */ extern int add(double);   /* 真实定义是 add(int, int) */
```

```bash
$ clang -Wall -c a_bad.c -o a_bad.o    # 零警告——每个 TU 独立编译，互相看不见
$ clang a_bad.o b.o -o c_bad           # 链接成功！C 符号只叫 _add，没有类型信息
```

链接器只认名字 `_add`，两侧类型信息在符号表里**根本不存在**，无从比对 → 配对成功 → 运行期按错误签名传参，静默损坏（完整运行期实测 → **7.2.3**）。这就是"手写声明"的代价：**声明与定义一致性从编译器的职责变成了你的记忆**。

### 实测三：C++，同样能调，但错了会当场暴毙

```cpp
/* b.cpp */ int add(int a, int b) { return a + b; }
/* a.cpp */ extern int add(int, int);  int main() { return add(1, 2); }
```

```bash
$ clang++ a.cpp b.cpp -o cpp_ok && ./cpp_ok; echo $?   # 3
$ clang++ -c b.cpp && nm bcpp.o
0000000000000000 T __Z3addii       # C++ 符号 = 函数名 + 参数类型编码（name mangling）
```

把声明改成 `extern int add(double);` 再试：

```bash
$ clang++ -Wall -c a_bad.cpp        # 编译照样通过（mangling 是链接期的概念）
$ clang++ a_badcpp.o bcpp.o -o cpp_bad
Undefined symbols for architecture arm64:
  "add(double)", referenced from:   # 声明编出 __Z3addd，定义只有 __Z3addii → 对不上
      _main in a_badcpp.o
```

签名不一致 → mangled name 不同 → **链接期 undefined reference，当场报错**。C++ 的 mangling 把"声明类型"编进了符号名，相当于给每个声明盖了类型指纹——错误声明找不到定义，而不是带着错误继续跑。**这是 C++ 比 C 安全的地方，不是"更麻烦"。**

### C vs C++ 对照总表

| | C | C++ |
|---|---|---|
| 不 include、手写声明能调 | ✅ 能 | ✅ 能 |
| 链接器匹配依据 | 函数名本身（`add` / Mach-O `_add`） | 修饰符号（`_Z3addii`：名字+参数类型） |
| 声明与定义签名不一致 | **编译链接全静默 → 运行期 UB**（7.2.3） | **链接期 undefined reference 当场报错** |
| 同名不同签名（重载） | 同一符号，冲突 | 各自独立符号，天然支持 |
| 调 C 编译的函数 | — | 声明要加 `extern "C"` 关掉 mangling |
| 一致性由谁保证 | 你自己（或头文件） | mangling 兜底一半（名字+参数，不含返回值） |

注意 C++ 兜底的边界：mangling 编码**参数类型不编码返回值**（返回值不同照样是"ambiguating new declaration"编译错误，见 7.2.4 表格），类成员函数还要连 namespace/类名/const 一起编——所以手写 C++ 声明的容错空间比 C 更小，错一个 `const &` 就 undefined reference。

### 跨语言实战：C++ 调 C 编译的函数

```c
/* c_api.c  —— 用 C 编译器编译，符号是 _add */
int add(int a, int b) { return a + b; }
```

```cpp
/* cpp_call_c.cpp */
extern "C" int add(int, int);      // 不加的话声明编出 __Z3addii，找不到 _add
int main() { return add(1, 2); }
```

```bash
$ clang -c c_api.c && clang++ cpp_call_c.cpp c_api.o -o mixed && ./mixed; echo $?   # 3
```

工程上这句 `extern "C"` 声明就是头文件该干的活（`#ifdef __cplusplus` 包起来，→ 04-cpp M4 item34），没人手写在调用点。

### 那头文件到底保证了什么？

手写 extern 声明"能用"，但每多一处手写声明，就多一份**和定义漂移的机会**。头文件的职责链：

1. **单一事实来源**：声明写一处，所有 TU include 同一份 → 改签名时编译器在所有调用点当场报错，而不是等到链接（C++）或运行期（C）
2. **定义文件也 include 自己的头** → 声明/定义冲突变成**同一 TU 内的编译错误**，C 语言里唯一可靠的防御（→ **7.2.3** 防御表）
3. 全局变量、opaque typedef、`static inline` helper 各就各位（→ 7.2 主节工程模式）

一句话：**链接器只解决"找到符号"，头文件解决"符号两边说的是同一个东西"。** 手写声明是把后一半责任从工具链手里接过来。

## HFT / 嵌入式关联

| 场景 | 用法 |
|------|------|
| 内核 `asmlinkage long sys_xxx(...)` 手写原型 | 汇编入口/系统调用表没有正常头文件，**刻意**手写声明（知道自己在干什么） |
| DPDK `rte_*` API | 全走头文件——百处调用点绝不手写声明，签名一改就是灾难 |
| C/C++ 混编（历史 C 库 + C++ 策略层） | `extern "C"` 包头文件，`__cplusplus` 宏双保险 |
| `-fvisibility=hidden` 符号收敛 | 手写声明调不到 hidden 符号，链接期 undefined reference |

## 常见误区

| 误区 | 事实 |
|------|------|
| "不用 include 就调不了" | 能调——编译器只要调用点可见声明；include 只是贴声明的机械手段 |
| "extern 是调用外部函数的关键字" | 函数声明默认隐含 extern；extern 在全局变量上才不可省 |
| "链接器会自动去找" | 链接器找的是 `.o`/库里的**符号**，前提是链接命令里给了那个 `.o`（`clang a.c b.c` 两个都得给）；它不知道头文件，也不会翻源码 |
| "C++ 也和 C 一样，错了静默通过" | 反了——mangling 让签名不一致在**链接期**就报 undefined reference |
| "C++ 兜底万无一失" | mangling 只编码参数不编码返回值；错返回值仍可能静默（由编译器在别处拦截） |

## 实操

```bash
# C：手写声明全链路（注意 macOS 符号带前导下划线）
clang a.c b.c -o prog && nm b.o | grep add
# C：错误声明静默通过——复现 7.2.3 的雷
clang -Wall -c a_bad.c && clang a_bad.o b.o -o prog
# C++：mangling 符号实测 + 错误声明当场暴毙

clang++ a_bad.o bcpp.o -o prog       # Undefined symbols: "add(double)"
# 反查修饰名
c++filt _Z3addii                     # add(int, int)
# C++ 调 C：extern "C" 桥接
clang -c c_api.c && clang++ cpp_call_c.cpp c_api.o -o prog
```

## 代码自测

**题目 1：** 以下两个 C++ 文件，编译、链接、运行各会发生什么？

```cpp
/* b.cpp */
double add(int a, int b) { return a + b; }      // 返回类型 double

/* a.cpp */
extern int add(int, int);                        // 声明返回类型 int
int main() { return add(1, 2); }
```

<details>
<summary>参考答案</summary>

**编译：两个 TU 都通过。** Itanium mangling 只把**参数类型**编进符号名，
**返回值不参与**——`a.o` 里引用的是 `__Z3addii`，`b.o` 里导出的也是
`__Z3addii`，**参数相同则符号相同，返回值差异在符号层不可见**。

**链接：成功。** 两边符号名一模一样，链接器配对成功。注意这与"undefined reference"
不同：undefined reference 出现在参数列表不同时；返回值不同时 C++ 编译器通常在
看到两份声明的地方报 `ambiguating new declaration`——但这两个 TU 互相看不见，
所以没人报。

**运行：UB。** `add` 实际返回 `double`（放在 xmm0 / 浮点寄存器），调用点却按
`int` 返回值去读通用寄存器——读到的不是 3，是垃圾。这正说明 C++ 的 mangling
兜底有边界：**只保护参数类型，不保护返回类型**。防御手段和 C 相同：定义文件
include 自己的头文件，让冲突变成同一 TU 的编译错误（→ **7.2.3**）。

</details>

**题目 2：** 解释为什么 `clang a.c b.c -o prog` 能通过，而"链接器自动去找"这个说法哪里不对？

<details>
<summary>参考答案</summary>

能通过的原因：两个 `.c` 都被**显式**列在了链接命令里，各自编成 `.o` 后，
`a.o` 的未定义符号 `add` 恰好在 `b.o` 有 `T` 定义，配对成功。

"自动去找"不对在三处：
1. 链接器**只搜命令行上给出的** `.o`/`.a`/`.so`——把 `b.c` 换成没参与链接的
   `c/d/e.c`，照样 undefined reference，它不会翻目录找源码；
2. 链接器匹配的是**符号名**（C 里就是函数名），与"函数"这个语言概念无关——
   所以错误签名也能配上（7.2.3 的雷）；
3. 头文件从不参与链接——`#include` 的影响早在预处理阶段就结束了。

"声明放头文件"解决的是**符号两边类型一致**的问题，"链接时给出定义所在的
`.o`"解决的是**符号存在**的问题——两件事，都缺一不可。

</details>
