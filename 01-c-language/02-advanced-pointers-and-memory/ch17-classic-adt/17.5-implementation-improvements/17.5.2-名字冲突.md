# 17.5.2 名字冲突

## 本节讲什么

ADT 库的命名空间隔离：模块前缀、`static` 内部函数、不透明类型、头文件 guard。C 语言没有命名空间（C++ 的 `namespace`），全局符号必须用前缀防冲突。本节重点讲大型工程的命名规范、符号可见性控制、以及 DPDK/内核的命名惯例。

## 要点

### C 的命名空间问题

C 所有全局符号（函数、全局变量、typedef）在链接时共享一个扁平命名空间。两个 `.c` 定义同名函数 → 链接错误。两个头文件定义同名 `typedef` → 编译错误。

```c
/* a.c */
void push(int x) { ... }   /* a 模块的 push */

/* b.c */
void push(int x) { ... }   /* b 模块的 push */

/* 链接: multiple definition of `push' */
```

C++ 用 `namespace` 解决，C 只能靠前缀。

### 模块前缀规范

```c
/* hft_queue.h */
typedef struct hft_queue hft_queue_t;

hft_queue_t *hft_queue_create(size_t cap);
int          hft_queue_enqueue(hft_queue_t *q, void *data);
void        *hft_queue_dequeue(hft_queue_t *q);
void         hft_queue_destroy(hft_queue_t **q);
```

前缀 `hft_queue_` 让符号全局唯一。命名规范：

| 库 | 前缀 | 例子 |
|----|------|------|
| DPDK | `rte_` | `rte_ring_enqueue` |
| Linux 内核 | `linux_`/`__` | `list_for_each` |
| glibc | `__`/无 | `malloc` |
| OpenSSL | `SSL_`/`BIO_` | `SSL_new` |
| 自研 HFT | `hft_` | `hft_queue_create` |

模块内函数也加模块名前缀：`hft_queue_create`、`hft_list_push`、`hft_hash_find`。

### static：文件作用域隔离

```c
/* queue.c */
static struct Node *alloc_node(void *data)
{
    struct Node *n = malloc(sizeof *n);
    if (n) { n->payload = data; n->next = NULL; }
    return n;
}

static void free_node(struct Node *n)
{
    free(n);
}
```

`static` 修饰函数 → 只在本 `.c` 可见，不导出到全局符号表。好处：

- 内部辅助函数不占全局命名空间
- 编译器能内联优化（跨 .c 边界不能内联）
- 链接时不会被其他 `.c` 的同名 static 函数冲突

`static` 修饰全局变量 → 文件作用域，类似效果。

### 不透明类型防成员访问

```c
/* queue.h */
typedef struct hft_queue hft_queue_t;   /* 只有前向声明 */

/* queue.c */
struct hft_queue {
    struct Node *head, *tail;
    size_t len;
};
```

结构体定义藏在 `.c`，使用者只能通过 `hft_queue_t *` 句柄操作，无法直接访问 `q->head`。好处：

- 强制封装，防止误用
- 内部结构可重构不改 ABI
- 编译依赖最小化

### 头文件 guard

```c
/* hft_queue.h */
#ifndef HFT_QUEUE_H
#define HFT_QUEUE_H

/* ... 内容 ... */

#endif /* HFT_QUEUE_H */
```

或 `#pragma once`：

```c
#pragma once

/* ... 内容 ... */
```

防止头文件被重复包含。详见 ch14。

### 命名规范约定

#### 函数命名

```
<模块前缀>_<动词>_<对象>
```

- `hft_queue_create` ✓
- `hft_queue_enqueue` ✓
- `queue_create` ✗（太短，易冲突）
- `create` ✗（绝对冲突）

#### 类型命名

```
<模块前缀>_<名词>_t
```

- `hft_queue_t` ✓
- `hft_order_t` ✓
- `queue_t` ✗（POSIX 已有 `queue` 相关）

#### 宏命名

全大写 + 下划线：

- `HFT_MAX_ORDERS` ✓
- `HFT_QUEUE_DEFAULT_CAP` ✓
- `hft_max_orders` ✗（宏应全大写）

#### 全局变量

`g_` 前缀 + 模块前缀：

- `g_hft_stats` ✓
- `g_hft_log_fp` ✓

或单例风格：

- `hft_stats`（无 g_，靠模块前缀）

### 避免短名

```c
/* 禁用 */
int push(int);        /* 与任何其他 push 冲突 */
int pop(void);
int top(void);
int create(void);

/* 改用 */
int hft_stack_push(hft_stack_t *, void *);
void *hft_stack_pop(hft_stack_t *);
```

短名在大型工程必然冲突。即使当前不冲突，未来引入新库也可能撞。

### 符号可见性控制（GCC 扩展）

```c
/* 默认所有全局符号可见, 链接时全局 */
__attribute__((visibility("hidden"))) int internal_func(void);
__attribute__((visibility("default")))  int api_func(void);
```

- `hidden`：符号不导出到动态符号表，.so 外不可见
- `default`：正常导出

Linux 编译 `.so` 时用 `-fvisibility=hidden` 默认隐藏，只显式导出 API。减少符号污染 + 加载速度 + 优化空间。

### C++ 的 namespace 对比

```cpp
// C++
namespace hft {
    class Queue {
    public:
        void enqueue(void *data);
    };
}

hft::Queue q;
q.enqueue(data);
```

C++ `namespace` 是真正的命名空间，可嵌套、可别名、可 `using`。C 没有等价物，只能靠前缀模拟。C23 也没引入 namespace。

### 头文件自包含

每个头文件应自包含——包含它需要的所有依赖头，不依赖使用者预先包含其他头：

```c
/* hft_queue.h */
#ifndef HFT_QUEUE_H
#define HFT_QUEUE_H

#include <stddef.h>   /* size_t */

typedef struct hft_queue hft_queue_t;
hft_queue_t *hft_queue_create(size_t cap);
/* ... */

#endif
```

不依赖"使用者必须先 `#include <stddef.h>`"。这让头文件可被任意顺序包含。

### 前向声明减少依赖

```c
/* hft_order.h */
typedef struct hft_order hft_order_t;   /* 前向声明 */

/* 不 include hft_queue.h, 只用指针 */
void hft_order_enqueue(hft_queue_t *q, hft_order_t *o);
```

只用到指针的类型，前向声明即可，不必 `#include` 完整定义。减少编译依赖、加快编译。

## HFT 关联

- **模块前缀 `hft_`**：自研 HFT 框架统一前缀，避免与 DPDK `rte_`、内核 `linux_` 冲突
- **static 内部函数**：模块内辅助函数 static，不污染全局符号
- **不透明类型**：`hft_queue_t`/`hft_order_t` 等不透明指针，强制封装
- **DPDK `rte_` 惯例**：所有 DPDK API 用 `rte_` 前缀，`rte_ring`/`rte_mempool`/`rte_hash`
- **内核 `list_` 惯例**：`list_head`/`list_for_each`/`list_add` 等
- **符号可见性**：编译 `.so` 用 `-fvisibility=hidden`，只导出 API
- **头文件自包含**：每个 `hft_*.h` 自包含，任意顺序包含不报错
- **前向声明**：减少头文件依赖，加快 HFT 框架编译

## 代码自测

**题目 1：** 以下两个库都定义了 Stack 类型，如何解决冲突？
```c
// libA.h
typedef struct Stack Stack;
// libB.h
typedef struct Stack Stack;
```

<details>
<summary>参考答案</summary>

解决方案：(1) 命名空间前缀——libA 用 A_Stack, libB 用 B_Stack；(2) 不同结构体标签——struct A_Stack vs struct B_Stack，typedef 也可以不同；(3) 不透明指针——两个库都只暴露 typedef struct Stack *StackHandle，只要不在同一编译单元包含两个头文件就不会冲突。C 没有命名空间，前缀是最常用的方案。

</details>
