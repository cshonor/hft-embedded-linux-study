# 17.2.1 堆栈的接口

## 本节讲什么

栈 ADT 的对外 API 设计：不透明 `Stack *` 句柄、push/pop/peek/destroy 四件套、错误处理约定、载荷所有权规则。这是 ADT 接口设计的范式——同样的模式会出现在队列、树、哈希表等所有容器上。掌握这一节等于掌握了 C 语言 ADT 接口设计的方法论。

## 要点

### 完整接口

```c
/* stack.h */
#ifndef HFT_STACK_H
#define HFT_STACK_H

#include <stddef.h>

typedef struct Stack Stack;

/* 创建栈, cap=0 表示动态扩容 */
Stack *stack_create(size_t cap);

/* 入栈, 成功返回 0, 失败返回 -1 */
int    stack_push(Stack *s, void *data);

/* 出栈并返回载荷, 空栈返回 NULL */
void  *stack_pop(Stack *s);

/* 读栈顶不弹出, 空栈返回 NULL */
void  *stack_peek(const Stack *s);

/* 元素个数 */
size_t stack_len(const Stack *s);

/* 是否为空 */
int    stack_empty(const Stack *s);

/* 销毁栈, free_cb 非空时对每个载荷调用, q 置 NULL */
void   stack_destroy(Stack **s, void (*free_cb)(void *));

#endif
```

### 接口设计原则

#### 1. 不透明指针

`typedef struct Stack Stack;` 在头文件，`struct Stack {...}` 在 .c。使用者只能通过 `Stack *` 句柄操作，无法直接访问成员。

#### 2. 一致的生命周期

`create` → 多次 `push`/`pop` → `destroy`。每个 `create` 必须配一个 `destroy`，否则泄漏。

#### 3. 错误返回约定

- 返回 `int` 的操作：0 成功，负数失败
- 返回指针的操作：成功返回指针，失败返回 NULL
- `errno` 用于诊断，不依赖它判断成功失败

#### 4. const 正确性

`stack_peek(const Stack *s)` 和 `stack_len(const Stack *s)` 标 `const`——不修改栈的只读操作。这让 const Stack* 仍能调用这些接口，编译期保证安全。

#### 5. 载荷所有权

容器只持有 `void*` 指针，不拥有载荷内存：

- `push` 后，载荷的生命周期由容器"引用"，调用者不能在 pop 前释放它
- `pop` 后，所有权回到调用者，调用者负责释放
- `destroy(free_cb)` 时，对每个仍在栈内的载荷调用 `free_cb`，统一释放

这是 C 语言 ADT 的标准所有权模型——容器不管载荷怎么来的，只管 destroy 时按调用者指定的方式清理。

### 空栈与错误的区分

`stack_pop` 空栈返回 NULL，但 NULL 也可能是合法的载荷指针（用户主动 push 了 NULL）。两种区分方式：

#### 方案 A：先检查再 pop

```c
if (stack_empty(s)) {
    /* 真的空了 */
} else {
    void *data = stack_pop(s);
    /* data 可能是 NULL（用户 push 的 NULL）, 但栈确实非空 */
}
```

#### 方案 B：pop 带输出参数

```c
int stack_pop(Stack *s, void **out);   /* 返回 0 成功, -1 空栈 */
```

`out` 输出载荷，返回值区分成功失败。彻底无歧义。

HFT 生产代码倾向方案 B，避免 NULL 歧义。但方案 A 更符合 stdio 风格（`fgetc` 返回 EOF 类似）。

### peek 与 pop 的关系

`peek` 是 `pop` 的只读版本——读栈顶但不移除。常用于"看一眼再决定要不要 pop"：

```c
void *top = stack_peek(s);
if (should_process(top)) {
    stack_pop(s);   /* 确认处理才 pop */
    process(top);
}
```

注意 peek 后 pop 是两次操作，多线程下可能中间被其他线程修改——共享栈必须加锁。

### destroy 的 free_cb 语义

```c
void stack_destroy(Stack **s, void (*free_cb)(void *));
```

- `free_cb == NULL`：只释放栈结构，不碰载荷（载荷由外部管理）
- `free_cb == free`：标准堆释放
- `free_cb == custom`：自定义释放（如 mempool_put、close fd 等）

调用者根据载荷来源选择：

```c
/* 载荷是 malloc 的 */
stack_destroy(&s, free);

/* 载荷是 mempool 来的 */
stack_destroy(&s, mempool_put_wrapper);

/* 载荷是栈上变量, 不该释放 */
stack_destroy(&s, NULL);
```

### 接口与实现分离的收益

```c
/* 控制面: 用链表栈 */
#include "stack_list.h"
Stack *s = stack_create(0);

/* 数据面: 换数组栈, 接口完全一样 */
#include "stack_array.h"
Stack *s = stack_create(4096);
```

业务代码不变，编译时切换头文件即可换实现。这是 ADT 的核心价值——接口稳定，实现可替换。

## HFT 关联

- **统一容器接口**：HFT 框架的栈/队列/树都遵循 create/push/pop/destroy 范式，降低学习成本
- **不透明指针 ABI 稳定**：`Stack *` 是稳定 ABI，内部重构不需重编使用者
- **free_cb 与 mempool**：数据面栈 destroy 传 `rte_mempool_put` 把载荷归还池
- **const 正确性**：只读操作标 const，编译期防止误改，便于静态分析
- **错误返回约定**：0/负数风格与 DPDK `rte_` 系列、Linux 内核一致
- **线程局部栈**：每线程独占栈，接口无需考虑锁，性能最优
- **接口切换**：控制面链表栈、数据面数组栈，同一套业务代码

## 代码自测

**题目 1：** 以下栈接口设计中 push 返回 bool 有什么好处？
```c
bool stack_push(StackHandle s, int val);
```

<details>
<summary>参考答案</summary>

调用方可以检查 push 是否成功（栈满时返回 false）。如果 push 返回 void，调用方无法知道操作是否成功——要么假设总是成功（危险），要么每次调用前单独检查 stack_is_full（冗长）。返回 bool 是简洁的错误报告方式。好的接口设计应该让错误难以被忽略。

</details>
