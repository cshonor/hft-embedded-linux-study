# 14.1 预定义符号

## 本节讲什么

预定义符号是编译器**自动提供**的内置宏，无需 `#define` 即可使用。它们覆盖三类信息：**源码位置**（`__FILE__`/`__LINE__`/`__func__`）、**平台架构**（`__x86_64__`/`__aarch64__`/`__linux__`）、**编译器与标准版本**（`__GNUC__`/`__STDC_VERSION__`）。这一节把这些宏分类讲清，并给出 HFT 工程里日志、跨平台编译、特性检测的实际用法。

认知锚点：预定义宏是 C 工程的**编译期反射**——在标准 C 没有运行时反射的情况下，这些宏是仅有的「让代码知道自己被谁、在哪、怎么编译」的机制。HFT 跨平台部署（x86 + ARM、Linux + FreeBSD）、日志定位、特性开关全部依赖它们。

## 要点

### 源码位置宏

```c
#define ERR_LOG(fmt, ...) \
    fprintf(stderr, "[%s:%d %s] " fmt, \
            __FILE__, __LINE__, __func__, ##__VA_ARGS__)

ERR_LOG("order rejected: id=%lu\n", order_id);
/* 输出：[order_engine.c:142 process_order] order rejected: id=12345 */
```

| 宏 | 类型 | 含义 | 标准 |
|----|------|------|------|
| `__FILE__` | `const char *` | 当前源文件名（字符串字面量） | C89 |
| `__LINE__` | `int` | 当前行号 | C89 |
| `__func__` | `const char *` | 当前函数名（`static const char __func__[]`） | C99 |
| `__DATE__` | `const char *` | 编译日期 `"Jul 19 2026"` | C89 |
| `__TIME__` | `const char *` | 编译时间 `"09:24:30"` | C89 |
| `__BASE_FILE__` | `const char *` | 主源文件名（GCC 扩展） | GCC |
| `__COUNTER__` | `int` | 每次使用递增（GCC/Clang 扩展） | GCC |

**`__func__` 与 `__FUNCTION__` 的区别**：`__func__` 是 C99 标准，本质是 `static const char __func__[] = "name";`（编译器隐式注入）。`__FUNCTION__` 是 GCC 老扩展，C99 后等价于 `__func__`。新代码用 `__func__`。

**`__DATE__`/`__TIME__` 的工程陷阱**：这两个宏让构建不可复现——同一份源码不同时间编译出不同二进制。HFT 对账、监管审计要求二进制可复现，必须用 `-Wdate-time` 警告 + 构建系统注入固定时间戳。

### 平台与架构宏

```c
#if defined(__x86_64__) && defined(__linux__)
    /* x86-64 Linux：强内存模型，可省部分屏障 */
#elif defined(__aarch64__) && defined(__linux__)
    /* ARM64 Linux：弱内存模型，需显式 smp_wmb/smp_rmb */
#elif defined(__powerpc64__)
    /* POWER：弱内存模型 */
#else
    #error "unsupported platform"
#endif
```

| 宏 | 含义 |
|----|------|
| `__x86_64__`、`__amd64__` | x86-64 架构 |
| `__i386__` | 32 位 x86 |
| `__aarch64__` | 64 位 ARM |
| `__arm__` | 32 位 ARM |
| `__powerpc__`、`__powerpc64__` | PowerPC |
| `__riscv` | RISC-V |
| `__linux__` | Linux 平台 |
| `__FreeBSD__`、`__OpenBSD__` | BSD 系列 |
| `_WIN32`、`_WIN64` | Windows（注意无前导下划线） |
| `__APPLE__`、`__MACH__` | macOS |

**内存模型差异是 HFT 跨平台的核心痛点**：x86-64 是强内存模型（TSO），写-写天然有序，可省部分屏障；ARM64/POWER 是弱内存模型，多核同步必须显式 `smp_wmb()`/`smp_rmb()`。DPDK 的 `rte_smp_wmb()` 在 x86 上展开为空，在 ARM64 上展开为 `dmb ishst`——条件编译隐藏这种差异。

### CE 实测：五个目标的预定义宏长什么样

同一份源码把二十来个平台宏逐个字符串化打印（技巧：未定义时 `#m` 得到名字本身，已定义时得到其值），
在 Compiler Explorer 上换目标 / 编译器重跑，`-std=gnu17`：

| 目标 · 编译器 | OS 宏 | 架构宏 | 编译器宏 |
|---|---|---|---|
| x86-64 Linux · gcc 13.3 | `__linux__=1` `__unix__=1` `__unix=1` | `__x86_64__=1` `__SIZEOF_POINTER__=8` | `__GNUC__=13` `__GNUC_MINOR__=3` |
| x86-64 Linux · clang 18.1.0 | 同上 | 同上 | `__GNUC__=4` `__GNUC_MINOR__=2` `__clang__=1` `__clang_major__=18` |
| ARM64 Linux · gcc 13.3 | 同上 | `__aarch64__=1` `__ARM_ARCH=8` 指针 8 字节 | `__GNUC__=13` |
| ARM32 Linux · gcc 13.3 | 同上 | `__arm__=1` `__ARM_ARCH=7` | `__GNUC__=13` |
| x86-64 Windows · MinGW-w64 gcc 13.1 | `_WIN32=1` `_WIN64=1` `__MINGW64__=1`；`__linux__` / `__unix__` **均未定义** | `__x86_64__=1` | `__GNUC__=13` |

三条从表里直接读出来的结论：

1. **`_WIN32` 在 64 位目标下照样定义**（实测 MinGW x86-64：`_WIN32=1` 且 `_WIN64=1`）。判断"是否 Windows"只看 `_WIN32`，判断"是否 64 位 Windows"才追加 `_WIN64`。
2. **gcc 系同时定义 `__unix` 与 `__unix__`**，可移植代码用带尾下划线的 `__unix__`。
3. **`__STDC_VERSION__` 在 `-std=gnu17` 下同样是 `201710L`**——gnu 方言改的是 `__STRICT_ANSI__`，不是标准版本号。

#### Clang 的 `__GNUC__` 是 4，不是 18

实测 clang 18.1.0：`__GNUC__=4`、`__GNUC_MINOR__=2`。这是 clang 上游硬编码的伪装版本（对应 GCC 4.2.1），
**与 clang 自身版本无关**——clang 18 和 clang 3.4 报的是同一个数。

后果比"Clang 也定义 `__GNUC__`"严重得多：任何按 GCC 版本号开特性的写法都会把 clang 整体排除。

```c
#if defined(__GNUC__) && __GNUC__ >= 5     /* clang 在这里恒为假 */
#  define HAVE_BUILTIN_EXPECT 1
#endif
```

正解是**能力探测优先于版本探测**：

```c
#if defined(__clang__)
#  if __has_builtin(__builtin_expect)
#    define HAVE_EXPECT 1
#  endif
#elif defined(__GNUC__)
#  if __GNUC__ >= 3
#    define HAVE_EXPECT 1
#  endif
#endif
```

`__has_builtin` / `__has_attribute` / `__has_feature` / `__has_include` 才是跨平台判断编译器能力的正路，版本号只当兜底。

#### Apple clang：`__aarch64__` 照样有定义

流传较广的说法是"Apple clang 只给 `__arm64__` 不给 `__aarch64__`，移植要换宏"——这与实测输出不符。
llvm/llvm-project#73313 贴出的 `-dM` 原文（Apple clang 14.0.3，`arm64-apple-darwin22.6.0`，M2 / macOS 13.4）：

```text
#define __aarch64__ 1
#define __arm64 1
#define __arm64__ 1
#define __APPLE__ 1
#define __MACH__ 1
#define __ARM_ARCH 8
```

`__aarch64__` 与 `__arm64__` **同时存在**，所以 `#if defined(__aarch64__)` 在 Apple Silicon 上照样成立，不需要为 macOS 单独换宏。
真正需要额外信息的是"同为 Apple、系统不同"的细分（iOS / 模拟器 / macOS），那归 `<TargetConditionals.h>` 的 `TARGET_OS_*` 管，与架构宏是两回事。

#### 身份宏 vs 特性测试宏：两个方向相反的东西

TLPI 里最容易和平台宏混在一起的另一类宏是 `_GNU_SOURCE`、`_POSIX_C_SOURCE`、`_DEFAULT_SOURCE`：

| | 平台身份宏 `__linux__` / `__aarch64__` / `__GNUC__` | 特性测试宏 `_GNU_SOURCE` / `_POSIX_C_SOURCE` |
|---|---|---|
| 谁定义 | 编译器，在预处理开始前自动注入 | 你：源码第一行 `#define`，或编译选项 `-D` |
| 方向 | 编译器 → 你（只读的"我是谁"） | 你 → C 库（主动"请暴露哪些 API"） |
| 怎么用 | `#if defined(...)` 查询 | 不查询，只影响头文件展开后的内容 |
| 用错的后果 | 拼错 → 静默走 `#else` | 漏写 → Linux 专有 API **没有原型** → 隐式声明 |

CE 实测（调用 `accept4` / `ppoll`，查询 `O_DIRECT` / `strdup`，Linux + glibc）：

| 编译命令 | `accept4`、`ppoll` | `O_DIRECT` | `strdup` |
|---|---|---|---|
| `gcc 13.3 -std=gnu17` | 隐式声明（warning） | **未定义** | OK |
| `gcc 13.3 -std=gnu17 -D_GNU_SOURCE` | OK | `040000` | OK |
| `gcc 13.3 -std=c17` | 隐式声明（warning） | 未定义 | 隐式声明（warning） |
| `gcc 13.3 -std=c17 -D_GNU_SOURCE` | OK | `040000` | OK |
| `gcc 14.3 -std=gnu17`（不带） | **error**：implicit declaration of function 'accept4' | 未定义 | OK |
| `clang 18.1.0 -std=gnu17`（不带） | **error**：call to undeclared function 'accept4' | 未定义 | OK |

关键区分：**`-std=gnu17` 只解锁 glibc 的 `_DEFAULT_SOURCE`（POSIX / BSD / misc，如 `strdup`），不解锁 `_GNU_SOURCE`**
（`accept4`、`ppoll`、`O_DIRECT` 这批 Linux 专有接口）。想要后者必须显式 `-D_GNU_SOURCE`。

顺带一条：`#if __linix__`（故意拼错）在 `-Wall -Wextra` 下 **0 诊断、静默走 `#else`**；加上 `-Wundef` 才出声——
gcc 报 `"__linix__" is not defined, evaluates to 0`，clang 报 `'__linix__' is not defined, evaluates to 0`。
这就是"判断平台一律写 `defined(...)`"的理由（`14.3 条件编译` 有完整的边界表）。

#### 看不到 `-dM` 输出时怎么办

```bash
gcc -dM -E - < /dev/null                                         # 本机全部预定义宏
aarch64-linux-gnu-gcc -dM -E - < /dev/null | grep -E 'aarch64|ARM_ARCH|linux'
```

交叉编译一般仍能跑 `-dM`（只需要驱动能启动预处理器）。真正跑不了的是"能编译、不能执行"的目标
（CE 上的 ARM32、MinGW 都属此类），此时改用 `#pragma message` 把宏值在**编译期**打出来：

```c
#define TOSTR(m)     TOSTR_I(m)
#define TOSTR_I(m)   #m
#define DO_PRAGMA(x) _Pragma(#x)
#define SHOW(m)      DO_PRAGMA(message("MACRO " #m " => " TOSTR(m)))

SHOW(_WIN32)
SHOW(__aarch64__)
SHOW(__ARM_ARCH)
```

MinGW-w64 gcc 13.1 实测输出（`note:` 行）：

```text
#pragma message: MACRO _WIN32 => 1
#pragma message: MACRO __aarch64__ => __aarch64__
#pragma message: MACRO __ARM_ARCH => __ARM_ARCH
```

未定义的宏得到的就是它自己的名字，一眼可辨。`DO_PRAGMA` 那层间接不能省——`_Pragma` 的操作数必须是**字符串字面量**。

### 编译器与版本

| 宏 | 含义 |
|----|------|
| `__GNUC__` | GCC 主版本号 |
| `__GNUC_MINOR__` | GCC 次版本号 |
| `__clang__` | Clang 编译器 |
| `__clang_major__` | Clang 主版本 |
| `_MSC_VER` | MSVC 版本（无前导下划线） |
| `__INTEL_COMPILER` | Intel 编译器 |

```c
#if defined(__clang__)
    #define COMPILER "clang " __clang_version__
#elif defined(__GNUC__)
    #define COMPILER "gcc " __VERSION__
#elif defined(_MSC_VER)
    #define COMPILER "msvc " _MSC_FULL_VER
#endif
```

**GCC 与 Clang 的关系**：Clang 定义 `__clang__` 同时也定义 `__GNUC__`（兼容 GCC 扩展）。检测顺序必须先 Clang 后 GCC，否则 Clang 被误判为 GCC。

### C 标准版本

| 宏 | 值 | 标准 |
|----|----|------|
| `__STDC__` | `1` | 标准 C（C89 起） |
| `__STDC_VERSION__` | `199409L` | C89 + AMD1 |
| | `199901L` | C99 |
| | `201112L` | C11 |
| | `201710L` | C17/C18 |
| | `202311L` | C23 |

```c
#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 201112L
    /* C11 特性：_Static_assert、_Generic、<stdatomic.h> */
#elif defined(__STDC_VERSION__) && __STDC_VERSION__ >= 199901L
    /* C99 特性：变长数组、// 注释、声明在任意位置 */
#else
    /* C89：变量声明必须在块首 */
#endif
```

HFT 工程通常要求 C11 起步（`<stdatomic.h>`、`_Static_assert`、`_Generic`），部分前沿项目用 C17/C23。DPDK 最低要求 C99，推荐 C11。

### C11/C23 特性检测宏

```c
/* C11：__has_include 检测头文件是否存在 */
#if defined(__has_include)
    #if __has_include(<stdatomic.h>)
        #include <stdatomic.h>
        #define HAVE_STDATOMIC 1
    #endif
#endif

/* C23：__has_c_attribute 检测属性 */
#if defined(__has_c_attribute)
    #if __has_c_attribute(deprecated)
        #define DEPRECATED [[deprecated]]
    #endif
#endif
```

`__has_include` 让代码自适应不同环境——某些 libc 可能没有 `<stdatomic.h>`，运行时检测比硬编码平台更可靠。

## HFT 关联

### 日志定位

```c
#define LOG_ERR(fmt, ...) \
    rte_log(RTE_LOG_ERR, RTE_LOGTYPE_APP, \
            "[%s:%d %s] " fmt, \
            __FILE__, __LINE__, __func__, ##__VA_ARGS__)
```

`__FILE__`/`__LINE__`/`__func__` 是 HFT 日志的三件套。生产环境关 DEBUG 日志但保留 ERROR，定位问题时一行日志就能找到源码位置。**注意二进制大小**：`__FILE__` 是字符串字面量，每个使用点都存一份文件名，大型项目可能膨胀几 MB `.rodata`。优化方案：编译选项 `-fmacro-prefix-map` 裁剪路径前缀。

### 跨平台内存屏障

```c
/* DPDK rte_smp_wmb 实现（简化） */
#if defined(RTE_ARCH_X86_64)
    #define rte_smp_wmb() do { } while (0)   /* x86 强模型，空操作 */
#elif defined(RTE_ARCH_ARM_64)
    #define rte_smp_wmb() asm volatile("dmb ishst" ::: "memory")
#elif defined(RTE_ARCH_PPC_64)
    #define rte_smp_wmb() asm volatile("lwsync" ::: "memory")
#endif
```

同一份 C 代码在不同架构上编译出不同的屏障指令，HFT 跨平台部署的基础。**写屏障用宏而非函数**——屏障必须内联到调用点，函数调用会引入额外的内存访问，破坏屏障语义。

### 编译期平台校验

```c
#if !defined(__x86_64__) && !defined(__aarch64__)
    #error "HFT dataplane requires x86-64 or ARM64"
#endif

#if __SIZEOF_POINTER__ != 8
    #error "64-bit only"
#endif
```

`#error` 在编译期阻断不合法配置，优于运行期崩溃。`__SIZEOF_POINTER__` 是 GCC/Clang 内置宏，比 `sizeof(void*)` 更早可用（预处理阶段）。

### 构建版本戳

```c
const char *build_info(void)
{
    return "app=" APP_NAME
           " ver=" APP_VERSION
           " built=" __DATE__ " " __TIME__
           " compiler=" COMPILER
           " arch=" TARGET_ARCH;
}
```

启动时打印构建信息，便于运维确认部署的版本。**监管场景下 `__DATE__`/`__TIME__` 要替换为构建系统注入的固定时间戳**，保证可复现构建。

## UB 边界

| 情形 | 后果 | 防护 |
|------|------|------|
| `__func__` 在文件作用域使用 | 编译错误（只能在函数内） | 仅函数内使用 |
| `__DATE__`/`__TIME__` 导致不可复现构建 | 审计失败 | `-Wdate-time` + 注入固定时间 |
| 误用 `__FUNCTION__` 当 `__func__` | 非标准，可移植性差 | C99 起统一用 `__func__` |
| Clang 误判为 GCC | 用错扩展特性 | 先检 `__clang__` 再检 `__GNUC__` |
| `__STDC_VERSION__` 未定义当 C89 | 某些编译器不定义 | `#if defined(__STDC_VERSION__) && ...` |
| 用 `#if __GNUC__ >= 5` 判断编译器能力 | clang 实测 `__GNUC__=4`，恒为假 | 改用 `__has_builtin` / `__has_attribute` 能力探测 |
| 以为 `-std=gnuXX` 已解锁 GNU 专有 API | `accept4` / `O_DIRECT` 仍无原型，gcc 14+ 直接 error | 显式 `-D_GNU_SOURCE` |
| 平台宏拼写错误 | 静默走 `#else`，选错分支 | `-Wundef`（不在 `-Wall -Wextra` 里，需单独开） |
