# `gcc -E`：只做预处理

> 《Pointers on C》第 14 章配套 · 预处理器实操  
> [ch14 README](./README.md) · [14.4 文件包含](./14.4-file-inclusion/14.4-文件包含.md) · [14.3 条件编译](./14.3-条件编译.md)

---

## 命令含义

```bash
gcc -E main.c -o main.i
```

| | |
|---|---|
| **`-E`** | **只做预处理，然后停止**——不编译、不汇编、不链接 |
| 输入 | `main.c` |
| 输出 | `main.i`（预处理后的 **C 文本**） |

> `.i` 仍是可读的 C 源码，**不是**汇编、不是二进制。  
> 若 `#include <stdio.h>`，`.i` 常膨胀到几千行，属正常。

等价：`cpp main.c -o main.i`（效果几乎一样）。

---

## 预处理做哪些事

1. **展开宏**：`#define` 文本替换  
2. **展开头文件**：`#include` 内容粘贴进来（递归）  
3. **条件编译**：`#ifdef` / `#if` / `#else` / `#endif`，只留有效分支  
4. **删除注释**：`//`、`/* */` 默认去掉  
5. 生成 `# 行号 "文件名"` 标记（方便报错 / gdb 对回源码行）

---

## 常用变体

```bash
# 预处理结果打到屏幕（不写文件）
gcc -E main.c

# 保留注释（大写 -C），方便人读
gcc -E -C main.c -o main.i

# 命令行定义宏
gcc -E -DDEBUG=1 main.c -o main.i

# 去掉 # 行号标记，只留纯代码（机器处理 / 精确比对时用）
gcc -E -P main.c -o main.i
```

`-P` 会连 linemarker 一起删掉，输出行号与源码不再对应，**人肉排查时别加**，
但要做文本比对或喂给脚本时很好用（见下方 CE 实测）。

---

## GCC 四阶段对照

```bash
# 1. 预处理  c → i
gcc -E main.c -o main.i
# 2. 编译    i → s（汇编）
gcc -S main.i -o main.s
# 3. 汇编    s → o
gcc -c main.s -o main.o
# 4. 链接    o → 可执行
gcc main.o -o main
```

平时一条 `gcc main.c -o main` 是把四步串起来；出宏 / include 问题时，用 `-E` 单独看第一阶段。

---

## 典型使用场景

- 宏展开结果不对：看实际被替换成了什么  
- 头文件重复包含、条件编译分支走错  
- 想确认系统头最终「喂」给编译器的是什么  

排查 `#include` 时，常与 [14.4](./14.4-file-inclusion/14.4-文件包含.md) 一起用：`gcc -E a.c -o a.i`。

## CE 实测：`gcc -E` 的真实输出长什么样

源文件 `m2_hashpaste.c`（一个 `#`/`##` 演示文件），Compiler Explorer / gcc 13.3 跑 `gcc -E`：

```text
# 0 "/app/example.c"
# 1 "/app//"
# 0 "<built-in>"
# 0 "<command-line>"
# 1 "/usr/include/stdc-predef.h" 1 3 4
# 0 "<command-line>" 2
# 1 "/app/example.c"
# 15 "/app/example.c"
const char *s_raw = "VERSION";
const char *s_expand = "1.2";

int v_N = 1;
int w_7 = 2;

int line_12 = 0;

int main(void) { return 0; }
```

三个可验证的点：

1. **`# 数字 "文件"` 就是 linemarker**（文中「预处理做哪些事」第 5 条）。它把 `.i` 的每一行
   对回原始源码位置，报错和 gdb 靠它定位。加 `-P` 可以全部去掉，只留纯代码。
2. **注释确实被删了**——源码里 `/* ① 直接字符串化 */` 等注释一行都没留下（第 4 条）。
3. **源码没写 `#include`，`.i` 里却出现了 `stdc-predef.h`**——gcc 会隐式包含它。

⭐ **第 3 点的连锁结论**：`stdc-predef.h` 的头注释原文（`-E -C` 保留注释后可见）：

```text
/* This header is separate from features.h so that the compiler can
   include it implicitly at the start of every compilation.  It must
   not itself include <features.h> or any other header that includes
   <features.h> because the implicit include comes before any feature
   test macros that may be defined in a source file before it first
   explicitly includes a system header.  */
```

⇒ **这就是为什么 `_GNU_SOURCE` / `_POSIX_C_SOURCE` 必须写在任何 `#include` 之前**
（或改用 `-D_GNU_SOURCE` 命令行传）——隐式包含发生在你的第一行代码之前，
等到 `#include <features.h>` 被拉进来时，再 `#define` 已经晚了。详见
[1.1 C 语言标准和编译器](../../05-embedded-kernel-practice/01-ch1-gnu-c-basics/1.1-c-standard/1.1-C语言标准和编译器.md)。

### 用 `-E` 现场验证「`#`/`##` 旁的参数不展开」

`-E -P`（去掉 linemarker）是排查宏的第一手工具，输出干净到可以直接当结论用：

| 源码 | `-E -P` 输出 | 说明 |
|---|---|---|
| `STR(VERSION)` | `"VERSION"` | `#` 取实参**原文**，不展开 |
| `XSTR(VERSION)` | `"1.2"` | 套一层间接后，参数先展开 |
| `NAKED(v_, N)` | `int v_N = 1;` | `##` 操作数**不展开**，得到假标识符 `v_N` |
| `CAT(w_, N)` | `int w_7 = 2;` | 间接层让 `N` 先展开成 7，再粘贴 |

`N` 被 `#define N 7` 定义过，但 `NAKED(v_, N)` 粘出来的是 `v_N` 而不是 `v_7`——
**一条命令就把「`##` 不展开操作数」从记忆变成了可见事实**。脑内推演展开顺序时，
一律用 `gcc -E -P` 代替。

> `-E -C`（大写 C）保留注释，代价是 `.i` 会塞进系统头的整段版权声明——
> 上面那段 `stdc-predef.h` 注释就是这么来的。人读用 `-C`，脚本处理用 `-P`。

## 代码自测

**题目 1：** 以下代码经过 gcc -E 预处理后，宏展开结果是什么？
```c
#define SQUARE(x) ((x) * (x))
int result = SQUARE(3 + 1);
```

<details>
<summary>参考答案</summary>

展开为 int result = ((3 + 1) * (3 + 1));，结果为 16。注意宏参数必须加括号——如果写 #define SQUARE(x) x * x，展开为 3 + 1 * 3 + 1 = 7（优先级错误）。外层括号也很重要，防止宏与其他运算符组合时出错。

</details>
