# 3.1.3 指针

## 本节讲什么

指针作为一种**数据类型**：它存的是**地址**，有**指向类型**。本节只从类型层面预告指针——完整的指针体系（`&`/`*`、间接访问、指针运算、野指针）在 **ch06** 展开。这里建立三个基础认知：指针的位宽、指针类型决定什么、限定符与指针的组合。

## 指针的类型层面

```c
int *p;              /* 指向 int 的指针 */
const char *s;       /* 指向只读 char 的指针 */
void *generic;       /* 泛型指针，使用前需 cast */
struct rte_mbuf *mbuf; /* 指向 struct rte_mbuf 的指针 */
int **pp;            /* 指向 int 指针的指针（二级指针） */
```

### 指针的两个组成部分

| 组成 | 说明 |
|------|------|
| **地址值** | 一个整数，表示内存位置（64 位系统通常 48 位有效） |
| **指向类型** | 告诉编译器"这个地址存的是什么类型的对象" |

> `int *p` 和 `char *q` 都占 8 字节（64 位），存的地址值格式相同，但**指向类型不同**——这是它们行为不同的根本原因。

## `sizeof(指针)` 与指向类型无关

**核心原则：地址本身是一个数字，这个数字的宽度（32/64 位）和"指针指向什么类型"是两件完全不相干的东西。**

### 两个概念拆开

| 概念 | 决定什么 | 由什么决定 |
|------|---------|-----------|
| **指针变量本身的存储宽度** | 地址数字占几字节 | **编程模型（ABI）**：LP64/LLP64 = 8 字节，ILP32 = 4 字节 |
| **指向类型（`*` 前面的类型）** | 解引用读几字节、`p++` 步长多大 | 你写的类型名：`uint8_t*`→1、`uint32_t*`→4、`uint64_t*`→8 |

```c
/* 64 位系统：所有指针变量本身都是 8 字节，不管指向什么 */
uint8_t  *p8;
uint32_t *p32;
uint64_t *p64;

sizeof(p8)  == 8;   /* 不是 1！p8 本身存的是 64 位地址 */
sizeof(p32) == 8;   /* 不是 4！p32 本身存的是 64 位地址 */
sizeof(p64) == 8;   /* 不是 8 因为指向 uint64_t，而是所有指针都是 8 */
```

`uint32_t *p32` 的含义：
- `p32`：指针变量，64 位，存内存地址
- `uint32_t`：p32 指向的那块内存里期望是什么类型——解引用读 4 字节，`p32++` 步长 +4

**不是说指针本身是 32 位**，而是"指向 4 字节数据对象的指针"。指针自身的地址宽度由 ABI 决定。

### 常见误区

| 误区 | 纠正 |
|------|------|
| `uint32_t *` 代表地址是 32 位 | **错**。`uint32_t *` = 指向 4 字节对象的指针；指针自身宽度由 ABI 决定（64 位系统全部 8 字节） |
| `uint64_t *` 比 `uint8_t *` 大 | **错**。同平台上所有指针一样大 |
| 64 位 CPU 一定 64 位指针 | **不精确**。决定指针宽度的是编程模型（ABI），不是 CPU。x86-64 上可以跑 x32 ABI（ILP32），CPU 是 64 位但指针只有 32 位。工程上"64 位 OS = 64 位指针"作为速记没问题 |

### cast 不改变地址宽度

```c
uint32_t *p32 = (uint32_t *)0x1000;
```

- `0x1000` 是整数字面量，64 位环境扩展成 `0x0000000000001000`
- `(uint32_t *)` **不是把地址截断成 32 位**——只是标记"这是一个指向 uint32_t 的指针"
- 地址数字不变，改变的是编译器的解读规则：`*p32` 读 4 字节，`p32++` 加 4

### 指针宽度由 ABI 决定

| 编程模型 | 典型平台 | 指针宽度 | `long` 宽度 |
|---------|---------|---------|------------|
| LP64 | 64 位 Linux/macOS | 8 字节 | 8 字节 |
| LLP64 | 64 位 Windows | 8 字节 | 4 字节 |
| ILP32 | 32 位 Linux / x32 ABI | 4 字节 | 4 字节 |

> 严格说"指针宽度由 CPU 架构决定"不精确——决定的是**编程模型（ABI）**。但所有 64 位数据模型（LP64/LLP64）指针都是 8 字节，所以"64 位 OS = 64 位指针"工程上够用。

### 取地址数值用 `uintptr_t`

```c
uint32_t *p32 = (uint32_t *)0x1000;
uintptr_t addr = (uintptr_t)p32;   /* 标准写法，宽度匹配本机指针 */
```

- `uintptr_t` 宽度和本机指针完全匹配：32 位平台 = 32 bit，64 位平台 = 64 bit
- **不要用 `uint32_t` 存 64 位系统的指针**——会截断地址高位，严重 bug
- 保证 round-trip 保真：`(void *)(uintptr_t)p == p`（C11 7.20.1.4）

### `uint64_t` vs `uintptr_t` vs `uint64_t *` 三者区分

这三个名字看着像，实际是**完全不同的三类东西**：

| 维度 | `uint64_t` | `uintptr_t` | `uint64_t *` |
|------|-----------|-------------|-------------|
| **类别** | 整数类型 | 整数类型（专为存地址设计） | 指针类型 |
| **干什么** | 存一个 64 位数字 | 存一个地址数值 | 指向一块 8 字节的内存 |
| **宽度** | 固定 8 字节 | 随平台变（32 位机 4 字节，64 位机 8 字节） | 随 ABI 变（LP64/LLP64 = 8 字节，ILP32 = 4 字节） |
| **和地址的关系** | 可以装下 64 位地址，但**标准不保证 round-trip** | **标准保证**能完整存取指针 round-trip | 本身**就是**地址，存的是内存地址 |
| **`++` 步长** | +8（整数加法） | +1（整数加法，和普通整数一样） | +8（`sizeof(uint64_t)` 指针算术） |
| **能转成指针吗** | 能，但 32 位平台上 `uint64_t` 比指针宽，转换 implementation-defined | 能，**标准推荐的整数↔指针桥梁** | 本身就是指针，不用转 |

**关键区分**：

```c
uint64_t   val  = 0x1000;    // 整数，存数字 0x1000
uintptr_t  addr = 0x1000;    // 整数，存地址数值 0x1000（宽度匹配本机指针）
uint64_t  *ptr  = (uint64_t *)0x1000;  // 指针，指向地址 0x1000 处的 8 字节数据
```

- `val` 和 `addr` 都是**整数**，不是指针。区别：`uintptr_t` 宽度永远等于本机指针宽度，`uint64_t` 固定 8 字节——在 64 位 LP64 上两者恰好一样宽，但语义不同
- `ptr` 是**指针**，宽度由 ABI 决定（LP64 = 8 字节），它指向的内存按 `uint64_t`（8 字节）解读
- 整数→指针的转换：`(uint64_t *)addr` 把整数当地址用，**不改变地址位数**，只是打标签

**易混点**：

```c
/* ❌ 错误理解：以为只有 uint64_t 才能转成指针 */
uint64_t *p = (uint64_t *)some_uint32;   // 能编译，但不是"因为 uint64_t 够宽"

/* ✅ 正确理解：整数→指针看的是"整数够不够宽能装下地址"，跟转成哪种指针无关 */
uintptr_t addr = 0x1000;      // 用 uintptr_t 保证宽度匹配
uint8_t  *p8  = (uint8_t *)addr;   // 可以转成 uint8_t*
uint32_t *p32 = (uint32_t *)addr;  // 可以转成 uint32_t*
uint64_t *p64 = (uint64_t *)addr;  // 可以转成 uint64_t*
// 三种都合法，地址数字不变，区别只是解引用宽度和步长
```

> **一句话**：`uint64_t` 是整数负责存数字，`uintptr_t` 是整数负责存地址（宽度自动匹配），`uint64_t *` 是指针负责指向 8 字节数据。整数存地址要够宽（用 `uintptr_t`）；转成哪种指针随便选，二者互不绑定。

### 整数转指针的本质：把数字当地址，类型决定怎么读数据

```c
uintptr_t addr = 0x1000;          // addr 是整数，值 0x1000
uint32_t *p = (uint32_t *)addr;   // 把 0x1000 当地址，p 指向这个地址
```

转换做了什么：
1. **把整数值当地址**——指针 `p` 里存的就是 `0x1000` 这个地址值
2. **类型标签决定解读**——之后 `*p` = 去内存地址 `0x1000` 那个地方，读 4 字节当 `uint32_t` 解读

```
内存地址:    0x1000  0x1001  0x1002  0x1003
             ┌───────┬───────┬───────┬───────┐
内存内容:    │ 0x78  │ 0x56  │ 0x34  │ 0x12  │
             └───────┴───────┴───────┴───────┘
               ↑                               ↑
              p 指向这里              读 4 字节到这里
              (*p 读 0x12345678，小端)
```

- `p` 存的地址 = `addr` 的整数值（`0x1000`），比特不变
- `*p` = 去这个地址读数据，读几个字节由指针类型决定（`uint32_t *` → 4 字节）
- `p++` = 地址加 `sizeof(uint32_t)` = 4，指向下一个 4 字节块

> 指针本质就是"存了一个地址，告诉你去那个地址读多大、怎么解读数据"。整数转指针 = 把数字当地址用，类型标签决定解读规则。

### `uintptr_t` 实际工作场景

什么时候需要把地址存成整数？指针不是已经存了地址吗——因为**有些操作只能用整数做，指针做不了**：

#### 场景 1：地址对齐判断（DPDK / 内核最常见）

```c
/* DPDK mbuf 数据区要求 64 字节对齐，检查缓冲区地址是否满足 */
void *buf = rte_pktmbuf_mtod(m, void *);

/* ❌ 指针不能直接做位运算 */
if ((buf & 0x3F) == 0) { ... }       /* 编译错误：指针不能 & */

/* ✅ 转成 uintptr_t 做位运算，判断低 6 位是否为 0 */
if (((uintptr_t)buf & 0x3F) == 0) {
    /* 64 字节对齐，可直接走 SIMD 向量解析 */
}
```

指针不支持 `&`、`|`、`%` 等位运算。想检查对齐、做地址掩码，**必须先转成整数**。`uintptr_t` 保证转换无损。

#### 场景 2：MMIO 寄存器地址（嵌入式 / 驱动）

```c
/* UART 寄存器映射在物理地址 0x09000000（树莓派5 PL011） */
#define UART_BASE  0x09000000

volatile uint32_t *uart = (volatile uint32_t *)UART_BASE;
/* 等价于 */
uintptr_t uart_addr = UART_BASE;
volatile uint32_t *uart = (volatile uint32_t *)uart_addr;

*uart = 'A';   /* 写一个字节到串口 */
```

嵌入式裸机 / 内核驱动里，硬件寄存器的物理地址是固定的整数（芯片手册写死），必须用整数→指针转换来访问。`uintptr_t` 在这里是中转容器。

#### 场景 3：日志 / 调试打印地址

```c
/* 调试时打印指针地址，用 PRIuPTR 保证格式跨平台匹配 */
#include <inttypes.h>

void debug_ptr(void *p)
{
    /* ❌ %lu 在 LLP64(Windows) 上指针 8 字节但 long 4 字节 → 格式不匹配 */
    printf("ptr = 0x%lx\n", (unsigned long)p);

    /* ✅ PRIxPTR 自动匹配 uintptr_t 的宽度 */
    printf("ptr = 0x%" PRIxPTR "\n", (uintptr_t)p);
}
```

`%lx` 在 LP64 上碰巧对，但 LLP64（Windows 64 位）上 `long` 是 4 字节、指针是 8 字节，格式不匹配。`PRIxPTR` / `PRIuPTR` 永远和 `uintptr_t` 宽度一致。

#### 场景 4：地址做哈希 / 比较

```c
/* 把指针地址存进哈希表做去重，需要整数做哈希 */
uint32_t hash_pointer(void *p)
{
    uintptr_t addr = (uintptr_t)p;
    /* FNV-1a 哈希，要求操作数是整数 */
    uint32_t hash = 2166136261u;
    for (int i = 0; i < (int)sizeof(uintptr_t); i++) {
        hash ^= (addr >> (i * 8)) & 0xFF;
        hash *= 16777619u;
    }
    return hash;
}
```

哈希函数、排序比较、位掩码——这些算法只认整数，指针做不了。

#### 四个场景的共同点

| 场景 | 为什么需要整数 | `uintptr_t` 的角色 |
|------|--------------|------------------|
| 对齐判断 | 指针不能位运算（`&` `\|`） | 中转：指针→整数→位运算 |
| MMIO 寄存器 | 硬件地址是固定数字 | 容器：整数→指针 |
| 日志打印 | `printf` 格式要匹配宽度 | 保证 `%`PRIxPTR 宽度一致 |
| 哈希/比较 | 哈希算法只认整数 | 中转：指针→整数→哈希 |

> **核心**：指针只能存地址、解引用、加减步长。但凡需要位运算、哈希、格式化打印，就必须转成整数——`uintptr_t` 就是那个"安全的中转容器"，宽度永远等于本机指针，转换无损可逆。

### 指针地址的有效位

- 64 位 Linux/x86：用户态地址通常 48 位有效（高 16 位是符号扩展）
- `0x7fff...` 是典型用户态地址范围
- 内核态地址高 16 位全 1（`0xffff...`）
- 详见 ch18 虚拟地址空间

## 指针类型决定什么

### 1. 解引用宽度

```c
int *pi = (int *)0x1000;
char *pc = (char *)0x1000;

*pi;    /* 从 0x1000 读 4 字节（int 宽度） */
*pc;    /* 从 0x1000 读 1 字节（char 宽度） */
```

- `int *` 解引用读 4 字节，`char *` 读 1 字节——类型决定读几个
- 类型错 → 读错字节数 → 数据错位或越界

### 2. 指针算术步长

```c
int arr[5] = {10, 20, 30, 40, 50};
int *p = arr;

p + 1;     /* 地址增加 sizeof(int) = 4 字节 → 指向 arr[1] */
p + 2;     /* 增加 8 字节 → 指向 arr[2] */
```

- `p + 1` 不是地址加 1，而是加 `sizeof(指向类型)`
- `int *` 步长 4，`char *` 步长 1，`struct big *` 步长可能很大
- **步长由指向类型决定**——这是指针算术的核心（ch06.13 详解）

```c
char *pc = (char *)arr;
pc + 1;    /* 只加 1 字节 → 指向 arr 的第 2 个字节 */
```

### 三种指针同一地址，行为天差地别

```c
uint8_t  *p8  = (uint8_t  *)0x1000;
uint32_t *p32 = (uint32_t *)0x1000;
uint64_t *p64 = (uint64_t *)0x1000;

/* 指针变量存的地址值一模一样，但类型不同 → 行为不同 */
*p8;     /* 从 0x1000 读 1 字节 */
*p32;    /* 从 0x1000 读 4 字节 */
*p64;    /* 从 0x1000 读 8 字节 */

p8++;    /* 地址 += 1 → 0x1001 */
p32++;   /* 地址 += 4 → 0x1004 */
p64++;   /* 地址 += 8 → 0x1008 */
```

指针变量内存存的值完全相同，但指针类型决定了解引用读几个字节、加减 1 移动多远。

### 报文解析的双重 UB 陷阱

```c
/* ❌ DON'T — 双重 UB */
uint8_t buf[64];
uint32_t val = *(uint32_t *)(buf + 4);   // 直接 cast + 解引用
```

这写法在 HFT 语境下有两个问题：

1. **未对齐访存**：`buf + 4` 如果不是 4 字节对齐的地址（`buf` 来自 `malloc` + 偏移很常见），ARM 直接 `SIGBUS`，x86 吃缓存行 split 性能惩罚
2. **严格别名违例**（C11 6.5p7）：`uint8_t*` 指向的内存按 `uint32_t` 解引用，`-O3` 下编译器有权重排读写，经典"O2 能跑 O3 出鬼"

```c
/* ✅ 正确 — memcpy，零开销 */
uint32_t val;
memcpy(&val, buf + 4, 4);   // gcc -O2 编译成一条 mov，不比 cast 慢
val = ntohl(val);            // 网络序 → 主机序
```

`memcpy` 同时解决对齐和别名两个问题，定长 `memcpy` 在 `-O2` 以上被编译器优化成单条 `mov` 指令，**零额外开销**。

### 严格别名（Strict Aliasing）详解

上面提到"严格别名违例"，这里展开讲清楚。

**规则（C11 6.5p7）**：编译器有权假设——**不同类型的指针不会指向同一块内存**。

这不是 size 的问题，是**类型**的问题。`uint32_t` 和 `float` 都是 4 字节，但编译器认为 `uint32_t *p` 和 `float *q` 不可能指向同一地址。基于这个假设，编译器敢把读写重排——如果你违反假设，就是 UB。

**为什么存在这个规则**——为了编译器优化：

```c
int   *pi = &data;
float *pf = &data;   // 严格别名违例：不同类型指针指向同一内存

*pi = 1;
*pf = 2.0;
// 编译器认为 pi 和 pf 不可能指向同一地址
// 所以有权把 *pi=1 和 *pf=2.0 任意重排
// 如果实际指向同一地址 → 结果不可预测
```

`-O3` 下编译器可能把 `*pi = 1` 直接优化掉（认为没人通过 `pi` 读 `pf` 写的值），或者重排顺序——这就是"O2 能跑 O3 出鬼"的经典来源。

**不是看 size，是看类型**：

```c
/* ❌ 两者都是 4 字节，但类型不兼容 → 严格别名违例 → UB */
uint32_t *p = (uint32_t *)&some_float;
*p;   // UB

/* ❌ 同理 */
float *f = (float *)&some_uint32;
*f;   // UB
```

size 相同不能别名。规则看的是**类型兼容性**，不是位宽。

**例外：`char*` / `unsigned char*` 可以指向任意内存**

标准专门给了 `char*`、`unsigned char*` 特权——它们可以指向**任何类型**的对象并访问：

```c
/* ✅ 合法——unsigned char* 可以指向任何东西 */
unsigned char *bytes = (unsigned char *)&some_uint32;
bytes[0];  // 读第 1 字节，合法
```

**这就是 `memcpy` 能用的原因**——`memcpy` 内部通过 `unsigned char*` 逐字节拷贝，永远不违反严格别名。所以类型转换用 `memcpy` 而不是指针 cast：

```c
/* ✅ memcpy 走 unsigned char*，合法 */
uint32_t val;
memcpy(&val, buf + 4, 4);

/* ❌ 直接 cast + 解引用，违反严格别名 */
uint32_t val = *(uint32_t *)(buf + 4);
```

> 一句话：严格别名 = 编译器假设不同类型指针不指向同一内存，违反就是 UB。解法：**类型转换用 `memcpy`，不用指针 cast**。

### 3. 类型安全

```c
int x = 42;
float *pf = &x;    /* 编译警告/错误：int* → float* 不兼容 */
```

- 编译器用指针类型做**类型检查**——防止把 `int *` 当 `float *` 用
- `void *` 是例外：可以和任何指针互转，不做检查
