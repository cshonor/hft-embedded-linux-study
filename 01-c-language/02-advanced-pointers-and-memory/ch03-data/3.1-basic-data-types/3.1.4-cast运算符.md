# 3.1.4 cast 运算符与指针进阶

> 从 3.1.3 拆分。指针的类型层、sizeof、uintptr_t、指针类型决定什么、严格别名见 3.1.3。

## 强制类型转换（cast 运算符）

格式：`(类型)表达式`，例如 `(int *)raw`、`(int)3.9`。

**圆括号 + 类型名**是 cast 运算符，把后面表达式的值**强行按新类型解释**。但 cast 分两类，行为完全不同：

| 写法 | 类别 | 比特变不变 | 例子 |
|------|------|-----------|------|
| `(int)3.9` | **数值转换**（重新编码） | **变** | IEEE754 `0x40073333` → int `0x00000003`，截断 + 重编码 |
| `(double)42` | 数值转换 | 变 | int `0x2A` → IEEE754 `0x4045000000000000` |
| `(int *)raw`（raw 是 `void*`） | **指针 cast**（重新解读） | 不变 | 8 字节地址值原样保留，只换"怎么解读这块内存" |
| `(char *)buf` | 指针 cast | 不变 | 同上 |
| `(int *)addr`（addr 是整数） | **整数转指针** | 不变 | 整数值当地址用，比特原样 |

> **口诀**：数值转换 = 重新编码（比特变）；指针 cast / 整数转指针 = 重新解读（比特不变）。

笔记里常犯的错：把表格里 `(int)x` 和 `(int *)x` 放一起说"比特不变"——**只对指针 cast 成立，数值 cast 比特一定变**。`(int)3.9` 从 `0x40073333` 变成 `0x00000003`，完全是另一串比特。

### 整数 ↔ 指针转换（内核/MMIO 经典）

```c
long addr = 0xffff0000;
int *ptr = (int *)addr;          /* 整数 → 指针 */
```

`(int *)` 干了三件事：

1. 把 `long` 整数值 `0xffff0000` 当成内存地址解释
2. 改变编译器对这块内存的解读方式：之后通过 `ptr` 访问按 `int`（4 字节）读/写，步长也变 `sizeof(int)`
3. 比特没变：`addr` 里存的 `0x00000000ffff0000`，转成 `int*` 后指针变量里还是同一串地址

**标准定性**（C11 6.3.2.3p5）：

- 整数转指针的**转换本身是 implementation-defined**（编译器得文档化，不是 UB）
- 真正 UB 的是**解引用一个不指向有效对象的指针**

所以这行 `(int *)addr` 不是 UB，但 `*ptr` 在用户态是 UB（SIGSEGV），在内核态如果 0xffff0000 是有效 MMIO 映射就合法。

### `long` 宽度陷阱

64 位 LP64 上 `long` 8 字节、`int*` 8 字节，转换没问题。但搬到 32 位 ILP32：

- `long` 是 4 字节，`0xffff0000` 还能装下
- 如果 `addr` 超过 32 位（如 `0x1ffff0000`），`long`（4 字节）在 ILP32 上**装不下**——这连第一步赋值都出问题
- 32 位平台整数转指针，结果 implementation-defined，可能截断高位

这就是为什么跨平台代码地址转整数**一律用 `uintptr_t`**（3.1.1 已讲），不用 `long`/`uint64_t`。

### MMIO 寄存器访问的标准姿势

```c
/* ❌ 缺 volatile */
uint32_t *reg = (uint32_t *)0xFFFF0000;
while (*reg & BUSY) ;   /* 编译器可能只读一次，缓存到寄存器 → 死循环 */

/* ✅ 内核 MMIO 标准写法 */
volatile uint32_t *reg = (volatile uint32_t *)0xFFFF0000;
uint32_t v = *reg;      /* 每次都生成真实 load 指令，读硬件当前值 */
```

不加 `volatile`，编译器把 `while (*reg & BUSY)` 优化成"读一次存寄存器、循环判缓存值"——永远死循环或读到旧值。`volatile` 强制每次访问生成真实 load/store。内核 `readl`/`writel` 屏障内部就包了 volatile 访问。

### cast 不做安全检查

```c
int x = 42;
float *fp = (float *)&x;    /* 编译能过，但解引用 UB（严格别名） */
*fp;                         /* 垃圾值或崩溃 */
```

cast 是程序员对编译器的**单方面声明**——你说是什么类型，编译器就信。类型错了运行直接 UB，编译期不会拦你。这就是为什么"能编译过"不等于"正确"。

### 区分：定义 vs cast

```c
int *p;            /* 定义变量：声明 p 是 int 指针，分配存储 */
(int *)xxx;        /* cast：修改现有值的类型解释，不分配存储 */
```

前者是声明语句，后者是表达式。位置和含义完全不同，别混。

### 三种 cast 区分：整数↔指针 vs 指针↔指针

cast 看似都是 `(类型)值`，但按"跨类别"还是"同类别"分三种，行为和陷阱不同：

| 维度 | 整数→指针 `(uint32_t *)addr` | 指针→整数 `(uintptr_t)p` | 指针→指针 `(uint32_t *)raw` |
|------|------------------------------|--------------------------|-----------------------------|
| **C11 定性** | 6.3.2.3p5 **implementation-defined** | 6.3.2.3p6 implementation-defined（`uintptr_t` 保证 round-trip） | void*↔任意：合法；非兼容类型互转：转换合法，**解引用**才 UB |
| **比特变不变** | 不变 | 不变 | 不变 |
| **危险在哪** | 解引用：未对齐/无效地址 → UB | 宽度不匹配会截断 → 用 `uintptr_t` 规避 | 解引用违反严格别名 → UB |
| **跨平台要点** | 整数宽度 vs 指针宽度（LP64/ILP32） | **必须 `uintptr_t`**，不能用 `int`/`long` | 只有 `char*`/`unsigned char*` 可解引用任意内存 |
| **典型用途** | MMIO 寄存器地址、固定物理地址 | 地址存日志/哈希/序列化 | `void*` 具体化、`malloc` 返回值转类型 |

**核心区别**：

1. **前两种是"跨类别"**（整数 ↔ 指针）——整数和指针是两种不同的东西，标准用 implementation-defined 桥接，`uintptr_t` 是标准给的安全容器
2. **第三种是"同类别换指向类型"**——指针还是指针，只是换"怎么解读这块内存"。合法性看**类型兼容性**，不是宽度
3. **三种都"比特不变"**——cast 不做编码转换，只换标签。真正改比特的是数值转换 `(int)3.9`

**容易混的点**：`(uint32_t *)(void *)0x1001` 看起来有两层 cast，实际是先整数→void*（第一种），再 void*→uint32_t*（第三种合法子情况）。void* 是中转站，因为它和任意指针互转都不改变比特、也不触发严格别名。

## `void *`：泛型指针

```c
void *generic = &x;     /* int * → void *：隐式转换，安全 */
int *pi = generic;       /* void * → int *：需要显式 cast（C）或隐式（C++） */
```

| 要点 | 说明 |
|------|------|
| `void *` 存什么 | 任意地址，但**不知道指向什么类型** |
| 解引用 | **不能直接解引用**——编译器不知道读几个字节 |
| 算术 | **不能做算术**（C 标准未定义 `void *` 步长；GCC 扩展按 1 字节算） |
| 转换 | 可和任意指针互转；使用前必须 cast 到具体类型 |
| 用途 | `malloc` 返回值、`qsort` 比较函数、泛型容器 |

> `malloc` 返回 `void *`——"给你一块内存，你自己决定怎么解释"。`int *p = malloc(4)` 隐式转成 `int *`。

## 限定符与指针的组合

`const` 可以修饰"指针本身"或"指向的内容"——位置决定语义：

```c
const int *p;         /* 指向 const int：不能通过 p 改内容，但 p 可指向别处 */
int *const p = &x;    /* const 指针：p 本身不可改，但可以通过 *p 改 x */
const int *const p = &x;  /* 二者都只读 */
```

| 写法 | 指针可改？ | 内容可改？ | 记忆法 |
|------|----------|----------|--------|
| `const int *p` | ✅ | ❌ | const 在 * 前面 → 内容只读 |
| `int *const p` | ❌ | ✅ | const 在 * 后面 → 指针只读 |
| `const int *const p` | ❌ | ❌ | 两个 const → 都只读 |

### 阅读技巧

从右往左读：
- `const int *p` → p is pointer to const int
- `int *const p` → p is const pointer to int
- `const int *const p` → p is const pointer to const int

### HFT 常用

```c
/* 只读配置指针：函数不改配置 */
void process(const struct config *cfg);   /* cfg 指向的内容不可改 */

/* MMIO 寄存器：volatile 告诉编译器每次从内存读 */
volatile uint32_t *reg = (volatile uint32_t *)0x40000000;
```

## NULL：空指针

```c
int *p = NULL;     /* p 不指向任何有效对象 */
if (p == NULL) { /* 检查空指针 */ }
*p;               /* UB：解引用空指针 → 通常 SIGSEGV */
```

- `NULL` 在 C 中通常定义为 `((void *)0)`
- 解引用 NULL 是 **UB**——通常 SIGSEGV，但不保证
- **所有指针用前检查 NULL**——工程铁律
- C11 引入 `nullptr` 的前身，C23 正式有 `nullptr`

## 指针的指针（预告）

```c
int x = 42;
int *p = &x;       /* p 指向 x */
int **pp = &p;     /* pp 指向 p */

**pp;              /* 42：先解引用 pp 得到 p，再解引用 p 得到 x */
```

- 二级指针用于"修改调用者的指针"——如 `void alloc(int **pp)`
- 详见 ch06.10 和 ch13.1

## 常见误区

| 误区 | 纠正 |
|------|------|
| `int *` 和 `char *` 大小不同 | 指针大小与指向类型无关，64 位都是 8 字节 |
| `void *` 可以直接解引用 | 不能，编译器不知道读几个字节 |
| `void *` 可以做算术 | C 标准未定义；GCC 扩展按 1 字节 |
| `int *p = &x; float *f = p;` 安全 | 类型不兼容，编译警告，行为 UB |
| `const int *p` 表示指针不可改 | 不对，是内容不可改；指针可改 |
| 解引用 NULL 一定崩溃 | 是 UB，通常 SIGSEGV 但不保证 |
| 所有指针都是 8 字节 | 64 位系统是，32 位系统是 4 字节 |

## 实操

1. `printf("%zu\n", sizeof(int *))` 到 `sizeof(void *)`，看都是 8
2. `int arr[3]={1,2,3}; int *p=arr; printf("%p %p\n", p, p+1)` 看步长 4
3. `char *c=(char*)arr; printf("%p %p\n", c, c+1)` 看步长 1
4. 写 `const int *p` 和 `int *const p`，尝试修改，看编译错误
5. `void *v = &x; *v;` 看编译错误（不能解引用 void *）
6. `int *p = NULL; *p;` 看 SIGSEGV

## 代码自测

**题目 1：** 以下代码有什么错误？
```c
int x = 42;
float *fp = &x;
*fp = 3.14f;
```

<details>
<summary>参考答案</summary>

类型不匹配。&x 的类型是 int*，赋给 float* 需要强制转换。不转换是编译错误。即使强制转换了，通过 float* 访问 int 变量违反了严格别名规则（strict aliasing），是未定义行为——可能导致垃圾值或程序崩溃。

</details>

### 题目 2：指针步长

```c
uint16_t *ptr = (uint16_t *)0x2000;
ptr++;
```

> `ptr` 最终地址等于多少？为什么？

<details>
<summary>参考答案</summary>

`0x2002`。`ptr++` 不是地址 +1，而是加上 `sizeof(uint16_t)` = 2 字节 → `0x2000 + 2 = 0x2002`。

指针加减的步长由**指向类型**决定：`uint8_t*` 步长 1，`uint16_t*` 步长 2，`uint32_t*` 步长 4，`uint64_t*` 步长 8。类型写错 → 步长错 → 读错内存。

</details>

### 题目 3：整数转指针

```c
long addr = 0xffff0000;
int *ptr = (int *)addr;
```

> `(int *)` 在这里干了什么？这行本身是 UB 吗？`*ptr` 呢？

<details>
<summary>参考答案</summary>

**`(int *)` 干了三件事**：把 `long` 整数值 `0xffff0000` 当成内存地址解释；改变编译器对这块内存的解读方式（之后通过 `ptr` 按int 4 字节读/写，步长也变 `sizeof(int)`）；比特没变，`addr` 里存的地址值原样搬到 `ptr` 里。

**这行 cast 本身不是 UB**，是 C11 6.3.2.3p5 的 **implementation-defined behavior**（编译器得文档化整数怎么映射成指针，不是"编译器可以为所欲为"的 UB）。

**`*ptr` 才是关键**：
- 用户态：0xffff0000 通常不是有效映射地址 → 解引用 UB，典型 SIGSEGV
- 内核态：如果 0xffff0000 是 MMIO 寄存器映射地址 → 合法，但**必须加 `volatile`**，否则编译器把连续读优化成读一次缓存 → 死循环或读旧值

所以内核 MMIO 标准写法是 `(volatile uint32_t *)0xFFFF0000`，不是裸 `(int *)`。

**额外陷阱**：`long` 宽度随平台变（LP64 是 8 字节，ILP32/LLP64 是 4 字节）。如果 `addr` 值超过 32 位，在 ILP32 平台上 `long` 装不下，或者整数转指针截断高位。跨平台地址转整数应该用 `uintptr_t`，不用 `long`。

</details>

### 题目 4：void* 中转 + 指针步长

```c
void *v = (void *)0x2000;
uint16_t *s = (uint16_t *)v;
s++;
```

> `s` 里存的地址变成多少？整个过程碰过内存吗？

<details>
<summary>参考答案</summary>

`s` 变成 **`0x2002`**。

过程拆解：
1. `(void *)0x2000`：整数 → void*（第一种 cast，比特不变），`v = 0x2000`
2. `(uint16_t *)v`：void* → uint16_t*（第三种 cast 的合法子情况，比特不变），`s = 0x2000`
3. `s++`：指针算术，`s += sizeof(uint16_t) = 2` → `0x2002`

**整个过程没碰过内存**——三步都是类型标签变化和指针算术，没有一次解引用。只有写 `*s` 才真正访问内存（此时若 0x2000 未对齐 uint16_t 或不是有效映射地址 → UB）。

两层 cast 看起来复杂，实际 void* 只是个中转站：它和任意指针互转都不改比特、也不触发严格别名，所以 `(uint16_t *)(void *)0x2000` 等价于直接 `(uint16_t *)0x2000`。

</details>

### 题目 5：指针宽度 vs 指向类型

```c
/* 64 位 Linux (LP64) */
uint8_t  *a;
uint32_t *b;
uint64_t *c;
```

> `sizeof(a)`、`sizeof(b)`、`sizeof(c)` 分别等于多少？为什么？

<details>
<summary>参考答案</summary>

**三个都是 8**。

```c
sizeof(a) == 8;   /* 不是 1 */
sizeof(b) == 8;   /* 不是 4 */
sizeof(c) == 8;   /* 不是 8"因为指向 uint64_t"，而是所有指针都是 8 */
```

指针变量本身的存储宽度由**编程模型（ABI）**决定，与指向类型无关。LP64 上所有指针都是 8 字节，不管指向 `uint8_t`（1 字节数据）还是 `uint64_t`（8 字节数据）。

指向类型只决定两件事：解引用读几个字节、`p++` 步长多大。它**不决定**指针本身占几字节。

</details>

### 题目 6：uint64_t vs uintptr_t vs uint64_t*

```c
/* 64 位 Linux (LP64) */
uintptr_t a = 0x2000;
uint8_t  *p = (uint8_t *)a;
p++;
```

> 1. `p` 这个指针变量本身是多少位？
> 2. `p++` 步长是多少？
> 3. `a` 和 `p` 在内存里存的数值，在 `p++` 之前是否相同？

<details>
<summary>参考答案</summary>

1. **64 位（8 字节）**。LP64 上所有指针都是 8 字节，不管指向什么类型。

2. **1 字节**。`sizeof(uint8_t) == 1`，指针 `++` 的步长等于指向类型的大小。

3. **相同**。在 `p++` 之前，`a` 是整数 `0x2000`，`p` 是指针指向地址 `0x2000`——两者内存里存的二进制都是 `0x0000000000002000`。区别只在类型标签：`a` 是整数（`++` 加 1），`p` 是指针（`++` 加 `sizeof(uint8_t)=1`）。本例恰好步长都是 1，但如果换成 `uint32_t *p`，`p++` 就加 4 而 `a++` 仍加 1。

**核心**：`uintptr_t` 是整数（存地址数字），`uint8_t *` 是指针（指向 1 字节数据）。整数存地址要够宽（`uintptr_t` 自动匹配），转成哪种指针只决定解引用宽度和步长，二者互不绑定。

</details>
