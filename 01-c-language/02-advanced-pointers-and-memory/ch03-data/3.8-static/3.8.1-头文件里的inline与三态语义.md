# 3.8.1 头文件里的 inline：三态语义与 -std 断崖

## 本节讲什么

从一个高频疑问出发：

> 头文件里写 `inline int test(){ return 100; }`，被两个 `.c` include，为什么链接报错？加 `static` 就好了？

**你得到的"加 static"这个结论完全正确，但"因为生成了两份全局实现所以重复定义"这个理由，只在老标准下成立。** 现代 GCC（默认 `-std=gnu17`）下报的根本不是 `multiple definition`，而是 **`undefined reference`**——而且在 `-O2` 下它甚至能正常链接通过。

这不是咬文嚼字。理由错了，你就无法解释这三个真实会撞上的现象：

- 同一份代码 **`-O0` 链接失败，`-O2` 却通过**——纯优化开关改变了链接成败
- 代码跑得好好的，某天有人**取了这个函数的地址**，立刻链接失败
- 同一份代码换了个 `-std` 参数就翻车

本节用**实测矩阵**（gcc 13.3.0，Ubuntu 24.04 / WSL）把 `inline` 的三种形态一次讲清，并给出头文件放函数体的唯一稳妥写法。

> 本节一切结论都有实测支撑，实验脚本见文末「实操」，可自行复现。

## 要点

### 一、先立前提：`#include` 就是复制粘贴

预处理阶段 `#include "tool.h"` 会被替换成头文件的**完整内容**。所以：

```
tool.h:  ILK int test(void){ return 100; }
              ↓ 预处理
a.c:  ILK int test(void){ return 100; }   ← 完整一份
b.c:  ILK int test(void){ return 100; }   ← 完整一份
```

**"头文件里放什么" 等价于 "每个 .c 里都会有一份什么"。** 这是理解后面一切的前提。

### 二、基线复盘：普通函数（无 inline）

先确认最基础的规则（你的第 1、2 点）。三种写法实测：

| 情形 | a.o 符号 | b.o 符号 | 链接结果 |
|------|---------|---------|---------|
| 两个 `.c` 各写 `int test(){return 1;}` / `{return 2;}` | `T test` | `T test` | ❌ `multiple definition of 'test'` |
| a.c 写实现，b.c 只写声明 `int test(void);` | `T test` | `U test` | ✅ 链接通过，运行正常 |
| 两个 `.c` 各写 `static int test(){...}` | `t test` | `t test` | ✅ 链接通过，运行正常 |

实测输出（第 3 行是真实报错原文）：

```bash
# 情形 1：两份实现
b.c:(.text+0x0): multiple definition of `test'; a.o:a.c:(.text+0x0): first defined here

# 情形 2：一份实现 + 一份声明
nm a.o | grep test    # 0000000000000000 T test    ← 大写 T = 外部链接，导出
nm b.o | grep test    #                  U test    ← U = 未定义，等链接器找
# LINK-OK, run OK

# 情形 3：两份 static
nm a.o | grep test    # 0000000000000000 t test    ← 小写 t = 内部链接，不导出
nm b.o | grep test    # 0000000000000000 t test    ← 同名，但是两个不相干的函数
# LINK-OK, run OK —— a.c 的 test 返回 1，b.c 的 test 返回 2，各用各的
```

**结论（你的理解完全正确）**：

- **全局函数**：实现（`T`）全项目只能一份，声明（`U`）可以写无数份
- **`static` 函数**：符号是小写 `t`，链接器根本不把它放进共享符号表，所以不同 `.c` 随便重名

### 三、⭐ 补丁：头文件放 `inline`（不加 static）到底报什么错

现在给上面的直觉打个补丁。同一个实验（两个 `.c` 都 include 同一头文件），把 `ILK` 换成三种写法、切换 `-std` 和优化级别，实测结果：

| 头文件写法 | `-std=gnu89` | `-std=gnu17`（现代 GCC 默认） |
|-----------|-------------|------------------------------|
| `inline` | ❌ **MULTIPLE-DEFINITION**（a.o/b.o 都是 `T test`） | `-O0` ❌ **UNDEFINED-REFERENCE**（都是 `U test`）<br>`-O2` ✅ **链接通过**（符号 absent） |
| `static inline` | ✅ 通过（`t test`） | ✅ 通过（`-O0` 是 `t`，`-O2` 符号消失） |
| `extern inline` | `-O0` ❌ UNDEF-REF<br>`-O2` ✅ 通过 | ❌ **MULTIPLE-DEFINITION**（都是 `T test`） |

**关键差异在第 1 行**：现代 GCC 下，头文件里的 `inline` **不是**"两份全局实现"，而是"**零份**全局实现"。

#### 为什么？看标准原文

C11 §6.7.4（Function specifiers，p.125-127）的规定（cppreference 表述）：

> If a non-static function is declared `inline`, then it must be defined in the same translation unit. **The inline definition that does not use `extern` is not externally visible** and does not prevent other translation units from defining the same function.

> If a function is declared `inline` in some translation units, it does not need to be declared `inline` everywhere: **at most one translation unit** may also provide a regular, non-inline non-static function, or a function declared `extern inline`. This one translation unit is said to provide the *external definition*. In order to avoid undefined behavior, one external definition must exist in the program **if the name of the function with external linkage is used in an expression**.

翻成大白话：

**文件域所有声明都只带 `inline`、不带 `extern` → 这叫「inline definition」（内联定义）。它只是一个"内联候选"，编译器可以拿它去内联展开，但它不提供任何外部符号。**

所以 `nm` 里看不到 `T test`——它没有导出任何东西。

#### ⭐ `-O0` 挂、`-O2` 过：一个纯优化开关改变了链接成败

这是本节最反直觉的现象，也是 inline definition 语义的直接后果：

```
-O2：编译器把所有 test() 调用都内联展开 → 根本不需要 test 这个符号 → 链接通过
-O0：GCC 默认不做任何内联 → 每个调用变成对 test 的外部引用 → a.o 里出现 U test
     → 但没有任何 .o 提供 T test → undefined reference to 'test'
```

GCC 文档原话佐证：`GCC does not inline any functions when not optimizing unless you specify the 'always_inline' attribute`。

**副作用**：一个纯性能优化开关改变了代码能否链接。这在 CI 里表现为"debug 构建挂了，release 构建好的"——排查方向极易跑偏（会误以为是编译选项的 bug，实际是 inline 语义）。

顺带一提：这个坑**在只有一个 `.c` 时也会触发**（实测）：

```bash
# 只有一个 solo.c，include 了 inline 头文件
gnu17 -O0 inline        -> undefined reference   ← 单个文件照样挂
gnu17 -O2 inline        -> LINK-OK
gnu89 -O0/-O2 inline    -> LINK-OK               ← gnu89 下单文件永远不挂
```

这进一步证明：**问题不是"多文件冲突"，而是"根本没人提供外部定义"**。

### 四、⭐ 更狠的：取函数地址时 `-O2` 也救不了

函数指针没法内联。实测（`-std=gnu17`，头文件 `inline`）：

```c
/* a.c */
#include "tool.h"
int (*fp)(void) = test;      /* 取地址 → 必须存在真实符号 */
int a_get(void){ return test(); }
```

```
-O0  nm a.o:  U test   -> undefined reference
-O2  nm a.o:  U test   -> undefined reference   ← -O2 也挂！
```

换成 `static inline`（头文件改一个词）：

```
-O0  nm a.o:  0000000000000000 t test   -> LINK-OK, run-OK
-O2  nm a.o:  0000000000000000 t test   -> LINK-OK, run-OK
```

这正好对应标准那句 **"if the name of the function with external linkage is used in an expression"** —— 取地址就是把函数名用在表达式里，此时**必须**存在外部定义，标准明确规定这点。

**实践后果**：一个用得好好的 inline 工具函数，某天有人把它塞进函数指针表（回调、转移表、`qsort` 比较函数），链接立刻炸。这类回归的排查成本很高，因为改动点（加了个 `&`）看起来完全无害。

### 五、三态速查表（C99/C11/C17 语义，现代 GCC 默认）

| 写法 | 导出外部符号? | nm 符号 | 语义 | 头文件用法 |
|------|:---:|:---:|------|------|
| `static inline` | 否 | `t`（或不出现） | 每个 TU **一份私有副本**，内部链接 | ✅ **首选**，最省心 |
| `inline` | **否** | `U` / absent | inline definition，**只是内联候选，不提供外部定义** | ⚠️ 必须另找**恰好一个** `.c` 提供外部定义 |
| `extern inline` | **是** | `T` | 这个 TU 的定义**就是**外部定义 | ⚠️ 只能出现在**恰好一个** `.c` |

### 六、C99 标准推荐写法（实测验证）

头文件放 `inline`，然后挑**恰好一个** `.c` 补一行 `extern inline` 声明，让它成为那个提供外部定义的 TU：

```c
/* tool.h —— 所有 .c 都 include */
#ifndef TOOL_H
#define TOOL_H
inline int test(void) { return 100; }
#endif

/* tool.c —— 全项目只能有这一个文件写下面这行 */
#include "tool.h"
extern inline int test(void);     /* 提供外部定义 */
```

实测（`-std=gnu17`）：

```
-O0   a.o: U test         b.o: 0000000000000000 T test   -> LINK-OK, run-OK
-O2   a.o: (absent)       b.o: 0000000000000000 T test   -> LINK-OK, run-OK
```

两种优化级别都通过，且**取地址也正常**。这是标准钦定的写法，但**多一个文件要维护**，且"恰好一个"这个约束没有任何机制帮你检查——写两个就是 `multiple definition`，一个都不写就是 `undefined reference`。

> 同样的效果也可以用 `extern int test(void);`（不带 inline）达成，实测同样通过。

### 七、⭐ gnu89 与 C99：`inline` 和 `extern inline` 语义完全对调

这是本节最该记住的一张表。GCC 文档原文：

> GCC implements **three different semantics** of declaring a function inline. One is available with `-std=gnu89` or `-fgnu89-inline` or when `gnu_inline` attribute is present on all inline declarations, another when `-std=c99`, `-std=gnu99` or an option for a later C version is used (without `-fgnu89-inline`), and the third is used when compiling C++.

两种语义下，两个关键字的含义**正好互换**：

| 写法 | gnu89 含义 | C99/C11/C17 含义 |
|------|-----------|-----------------|
| `inline` | **导出**外部定义（≈ C++ 行为） | **不导出**（inline definition） |
| `extern inline` | **不导出**（只用于内联，地址变外部引用） | **导出**（这就是外部定义） |

**所以你在老教程里看到的"头文件放 inline 会重复定义"，在 gnu89 时代是对的**；只是现代 GCC 默认不再是 gnu89。

自查当前编译器行为（实测 gcc 13.3.0 输出）：

```bash
gcc -dM -E -x c /dev/null | grep -E '__STDC_VERSION__|__GNUC_STDC_INLINE__|__GNUC_GNU_INLINE__'
#define __STDC_VERSION__ 201710L       # 默认 C17
#define __GNUC_STDC_INLINE__ 1         # ← 1 表示 C99 语义
```

`__GNUC_STDC_INLINE__` 为 1 = C99 语义；若为 `__GNUC_GNU_INLINE__` 则是 gnu89 语义。**想知道自己的代码按哪套规则跑，查这个宏最可靠**，比查 GCC 版本号快。

### 八、inline 的两条硬限制（实测：GCC 只警告不报错）

标准规定，非 static 的 inline 函数：

1. **不能定义非 const 的函数内 static 变量**
2. **不能引用文件域的 static 变量**

```c
static int x = 5;
inline int f(void){ static int n = 1; return n++ + x; }   /* 两条都犯 */
```

实测 GCC 13.3（`-std=gnu17 -O2 -Wall -Wextra`）：

```
j1.c:2:28: warning: 'x' is static but used in inline function 'f' which is not static
i1.c:1:32: warning: 'n' is static but declared in inline function 'f' which is not static
```

⚠️ **GCC 只给 warning，不报错**。而标准写的是 "cannot"。原因不难理解：inline definition 可能被内联到任意 TU，每个 TU 一份 static 副本，语义会变得无法预测（对比下节：C++ 里所有 TU 的 inline 函数局部 static 是同一个，C 里是各 TU 独立的）。

有趣的是 `-std=gnu89` 下**连警告都没有**（gnu89 语义下 inline 就是普通外部函数，没有这个问题）。

→ 实践：**编译器没报警不等于合法**。要用 `-Wall -Wextra` 才能看到这两条。

### 九、`static inline` 的唯一代价：取地址时每个 TU 一份副本

`static inline` 近乎完美，但有一个实测可见的代价：**函数地址在不同 TU 里不同**。

```c
/* tool.h */  static inline int test(void){ return 100; }
/* a.c    */  int (*a_fp)(void) = test;
/* b.c    */  int (*b_fp)(void) = test;
```

实测输出：

```
static inline:  a_fp=0x62cc22192190 b_fp=0x62cc221921a0 same=0   ← 差 0x10，两份副本
标准写法:      a_fp=0x5c4d1d1e4190 b_fp=0x5c4d1d1e4190 same=1   ← 唯一副本
```

影响：

- 用函数指针做 **identity 比较**（如"这个回调是不是那个函数"）会失效
- 用函数指针做 **哈希表 key**、去重、统计会出错
- 每个 TU 一份代码副本，**函数体大时会造成代码膨胀**

→ 小工具函数（clamp、min/max、字节序转换）用 `static inline` 完全没问题；**需要唯一地址语义的函数别用 static inline**。

### 十、结论：头文件放函数体，该怎么写

| 需求 | 写法 | 理由 |
|------|------|------|
| 通用小工具函数（默认选择） | **`static inline`** | 三种 `-std`、两种 `-O` 全绿；唯一代价是取地址不唯一 |
| 必须保证函数地址全局唯一 | 头 `inline` + **恰好一个** `.c` 写 `extern inline` | C99 标准写法，但"恰好一个"靠人维护 |
| 函数体很大 | **别放头文件**，走 `.h` 声明 + `.c` 实现 | 避免每个 TU 一份副本导致膨胀 |

**一句话收尾**：头文件里放带函数体的函数，`static inline` 是默认答案；`inline` 单独用是 C 语言里最容易被误用的关键字之一，它的真实语义（不提供外部定义）和直觉恰好相反。

## 与 HFT/DPDK

### DPDK / 内核头文件为什么满屏 `static inline`

```c
/* rte_mbuf.h —— DPDK 报文操作几乎全是 static inline */
static inline uint16_t rte_pktmbuf_data_len(const struct rte_mbuf *m)
{
    return m->data_len;
}
```

- 这些函数在收包热路径上每包调用几十次，**内联省掉函数调用开销**（HFT 里一次调用约 1–2 ns，一秒几百万包就是毫秒级）
- 放头文件是为了**让编译器在调用点看见函数体**——跨 TU 内联需要 LTO，头文件系统最省事
- 用 `static` 是为了**避免本节讲的链接地雷**

### 低延迟代码的构建配置

- HFT 生产构建一律 `-O2`/`-O3`，**很少用 `-O0`** —— 这恰好掩盖了 inline 的 undefined reference 问题
- 但 **debug 构建（`-O0 -g`）会突然链接失败**，CI 里这是典型的"只在某些 profile 下挂"
- 排查命令：`nm a.o | grep test` 看是 `U` 还是 `T`，一条命令就能区分本节所有情形

### 函数指针与转移表

ch13 高级指针的**转移表**（jump table）是本节第 4 点的重灾区：

```c
static inline int handle_new_order(struct msg *m){ ... }
int (*handlers[])(struct msg *) = { handle_new_order, ... };  /* 取地址 */
```

- `static inline` 能过，但**每个 TU 一份副本**，指针不唯一
- 纯 `inline` **直接链接失败**
- → 转移表里的 handler 若是小函数，用 `static inline` 可接受；若需要跨 TU 唯一性，改普通函数或标准 `extern inline` 写法

## 常见误区

| 误区 | 真相 |
|------|------|
| 头文件放 `inline` 函数会"重复定义" | 只在 `-std=gnu89` 下成立；C99+ 下报的是 `undefined reference`，`-O2` 甚至能通过 |
| 加了 `inline` 编译器就一定内联 | 不一定。`-O0` 下 GCC 完全不内联（除非 `always_inline`） |
| `inline` 和 `static inline` 只差个链接属性 | 差的是**是否提供外部定义**——`inline` 根本不提供，这是三态语义的核心 |
| `-O0` 挂了是编译器的 bug | 是 inline definition 语义 + 不内联的必然结果 |
| 取函数地址和调用函数是一回事 | 不是。取地址强制要求存在外部定义（标准明文），`-O2` 也救不了 |
| `extern inline` 是"外部声明" | C99 下恰恰相反：它**就是**那个外部定义，写两个 TU 会 `multiple definition` |
| 编译器没警告就是合法 | 非 static inline 用 static 变量标准说 "cannot"，GCC 只给 warning 且需 `-Wall` |
| `static inline` 的函数地址全局唯一 | 不唯一，每个 TU 一份副本（实测相差 0x10） |

## 实操

把下面的脚本存成 `inline_probe.sh` 在 Linux/WSL 下跑一遍，本节所有表格都能复现：

```bash
#!/bin/bash
set -u
cd /tmp && rm -rf ilab && mkdir ilab && cd ilab

cat > tool.h <<'EOF'
#ifndef TOOL_H
#define TOOL_H
ILK int test(void) { return 100; }
#endif
EOF

cat > a.c <<'EOF'
#include "tool.h"
int a_get(void){ return test(); }
EOF
cat > b.c <<'EOF'
#include "tool.h"
int b_get(void){ return test(); }
EOF
cat > main.c <<'EOF'
int a_get(void); int b_get(void);
int main(void){ return (a_get() + b_get()) == 200 ? 0 : 1; }
EOF

for ilk in "inline" "static inline" "extern inline"; do
  for std in gnu89 gnu17; do
    for opt in -O0 -O2; do
      rm -f *.o prog
      gcc -std=$std $opt -DILK="$ilk" -c a.c -o a.o 2>/dev/null
      gcc -std=$std $opt -DILK="$ilk" -c b.c -o b.o 2>/dev/null
      gcc -std=$std $opt           -c main.c -o main.o 2>/dev/null
      lo=$(gcc a.o b.o main.o -o prog 2>&1); rc=$?
      if   [ $rc -eq 0 ];                                then r="LINK-OK"
      elif echo "$lo" | grep -q "multiple definition";   then r="MULTIPLE-DEFINITION"
      elif echo "$lo" | grep -q "undefined reference";   then r="UNDEFINED-REFERENCE"
      else r="OTHER"; fi
      sym=$(nm a.o | grep -E '(^| )[TtUu] test$' | sed 's/^ *//')
      [ -z "$sym" ] && sym="(absent)"
      printf '%-14s %-7s %-4s | %-22s | a.o: %s\n' "$ilk" "$std" "$opt" "$r" "$sym"
    done
  done
done
```

单个命令速查：

```bash
# 1. 我这段代码按哪套 inline 语义跑？
gcc -dM -E -x c /dev/null | grep -E '__GNUC_STDC_INLINE__|__GNUC_GNU_INLINE__'
# __GNUC_STDC_INLINE__ = C99 语义（现代 GCC 默认）
# __GNUC_GNU_INLINE__  = gnu89 语义

# 2. 链接报 undefined reference —— 确认符号类型
nm a.o | grep test          # U = 没人提供外部定义（本节第三点）
                            # T = 有外部定义，多个 T 就是重复定义

# 3. 看 inline 是否真的被内联
gcc -O2 -S a.c -o a.s && grep -c 'call.*test' a.s    # 0 = 全部内联

# 4. 复现"取地址导致链接失败"
cat > fp.c <<'EOF'
inline int test(void){ return 100; }
int (*fp)(void) = test;
int main(void){ return fp(); }
EOF
gcc -std=gnu17 -O2 fp.c -o fp     # undefined reference to 'test'
gcc -std=gnu89 -O2 fp.c -o fp     # 通过（gnu89 语义下 inline 会导出）
```

## 代码自测

**题目 1：** 三个文件如下，链接结果是什么？

```c
/* a.c */ int test(void){ return 1; }
/* b.c */ int test(void){ return 2; }
/* main.c */ int test(void); int main(void){ return test(); }
```

<details>
<summary>参考答案</summary>

链接失败：`multiple definition of 'test'`（a.o 先定义，b.o 再定义时冲突）。

`nm a.o` 和 `nm b.o` 里都是大写 `T test` —— 两个外部链接符号同名，链接器不允许。

改成「一份实现 + 若干声明」即通过：a.c 保留实现，b.c 改成只写 `int test(void);`（不写函数体）。此时 b.o 里是 `U test`。

</details>

**题目 2：** 两个 `.c` 各写一份 `static int test(void)`，返回值不同。会链接冲突吗？程序运行时调用的是哪一份？

<details>
<summary>参考答案</summary>

不会冲突。`static` 让符号变成内部链接，`nm` 里是小写 `t test`，链接器不把 local 符号放进共享符号表，所以两个同名符号互不干扰。

运行时各用各的：a.c 里的调用走 a.c 的 `test`，b.c 里的调用走 b.c 的 `test` —— 它们是**两个完全不相干的函数，只是名字恰好一样**。

</details>

**题目 3：** 头文件 `tool.h` 写 `inline int test(void){ return 100; }`，被 a.c、b.c 同时 include。以下说法哪个对？

1. 生成两份全局实现，链接报 `multiple definition`
2. 不生成任何全局实现，`-O0` 时报 `undefined reference`，`-O2` 时可能通过

<details>
<summary>参考答案</summary>

**在现代 GCC（默认 `-std=gnu17`，C99 语义）下，说法 2 对。**

C11 §6.7.4：文件域所有声明只带 `inline` 不带 `extern` → 这是 **inline definition**，它**不提供外部定义**，也不禁止别的 TU 提供外部定义。所以 `nm a.o` 里根本看不到 `T test`。

- `-O2`：调用被内联展开，不需要 `test` 符号 → 链接通过
- `-O0`：GCC 不内联，每次调用变成外部引用 → a.o/b.o 里都是 `U test` → 没人提供 `T test` → `undefined reference`

说法 1 只在 `-std=gnu89`（或 `-fgnu89-inline`）下成立 —— GCC 早期默认就是 gnu89，这正是老教程这么写的原因。

</details>

**题目 4：** 接上题，`-O2` 下链接通过了。某天有人加了这行代码，又挂了，为什么？

```c
int (*fp)(void) = test;
```

<details>
<summary>参考答案</summary>

**取函数地址意味着"函数名被用在表达式里"，标准要求此时必须存在外部定义**（C11 §6.7.4：one external definition must exist "if the name of the function with external linkage is used in an expression"）。

函数指针没法内联，所以 `-O2` 也救不了 —— 实测 `-O0` 和 `-O2` 都报 `undefined reference`，`nm a.o` 里都是 `U test`。

解法二选一：

- 头文件改成 `static inline`（此时符号是 `t test`，各 TU 私有副本，取地址合法）
- 保留 `inline`，在**恰好一个** `.c` 里补 `extern inline int test(void);` 提供外部定义

</details>

**题目 5：** 把下面两张表补完（gnu89 vs C99 语义）：

| 写法 | gnu89 | C99/C11/C17 |
|------|-------|-------------|
| `inline` | 导出外部定义 | ? |
| `extern inline` | ? | 导出外部定义 |

<details>
<summary>参考答案</summary>

| 写法 | gnu89 | C99/C11/C17 |
|------|-------|-------------|
| `inline` | 导出外部定义（≈ C++） | **不导出**（inline definition，只是内联候选） |
| `extern inline` | **不导出**（只用于内联，取地址变外部引用） | 导出外部定义 |

**两者正好对调**，这是最容易记混的一组。

自查当前编译器用哪套：

```bash
gcc -dM -E -x c /dev/null | grep -E '__GNUC_STDC_INLINE__|__GNUC_GNU_INLINE__'
```

`__GNUC_STDC_INLINE__` → C99 语义（现代 GCC 默认，实测 gcc 13.3 输出 `__STDC_VERSION__ 201710L` + `__GNUC_STDC_INLINE__ 1`）；`__GNUC_GNU_INLINE__` → gnu89 语义。

</details>

**题目 6：** `static inline` 是不是完美方案？它有什么代价？

<details>
<summary>参考答案</summary>

不完美，有两个代价：

**代价 1：函数地址在 TU 间不唯一。** 每个 TU 一份私有副本，实测两个 TU 取地址得到的指针相差 0x10：

```
a_fp=0x62cc22192190  b_fp=0x62cc221921a0  same=0
```

→ 用函数指针做 identity 比较、哈希表 key、去重统计都会出错。对比标准 `inline` + 单一 `extern inline` 写法：`same=1`。

**代价 2：代码膨胀。** 每个 TU 一份副本，函数体大时二进制明显变大。

所以：小工具函数（clamp / min / max / 字节序转换）用 `static inline` 是默认答案；函数体大、或需要唯一地址语义时，改用 `.h` 声明 + `.c` 实现，或标准 `inline` + `extern inline` 组合。

</details>

**题目 7：** 下面这段代码 GCC 会报错吗？

```c
static int x = 5;
inline int f(void){ static int n = 1; return n++ + x; }
```

<details>
<summary>参考答案</summary>

**不会报错，只有两条 warning，而且需要 `-Wall`/`-Wextra` 才看得到：**

```
warning: 'n' is static but declared in inline function 'f' which is not static
warning: 'x' is static but used in inline function 'f' which is not static
```

标准（C11 §6.7.4）写的是 **"cannot"**：非 static 的 inline 函数 **不能**定义非 const 的函数内 static 变量，也 **不能**引用文件域 static 变量。GCC 选择了宽松处理（只警告），`-std=gnu89` 下连警告都没有。

语义上的原因：inline definition 可能被内联到任意 TU，每个 TU 一份 static 副本，行为变得无法预测。（对比：C++ 里所有 TU 的 inline 函数局部 static 是同一个对象，C 里是各 TU 独立。）

→ 教训：**编译器没报警不等于合法**，构建要开 `-Wall -Wextra`。

</details>
