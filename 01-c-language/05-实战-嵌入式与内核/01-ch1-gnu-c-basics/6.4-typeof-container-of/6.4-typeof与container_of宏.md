# 6.4 typeof 与 container_of 宏

[← ch06 GNU C 扩展](../README.md) · [6.3 语句表达式](../6.3-statement-expr/6.3-宏构造-利器-语句表达式.md) · [6.5 零长度数组](../6.5-zero-length-array/6.5-零长度数组.md)

> **本篇是 `typeof` + `container_of` 的完整总纲**：从语法、编译期语义、代码生成，到侵入式链表的完整可运行实现，全部有本机（WSL gcc 13.3 / clang 18.1.3）实测数据。
> 逐行拆解见 [6.4.1 typeof 关键字](6.4.1-typeof关键字.md) · [6.4.2 typeof 使用示例](6.4.2-typeof使用示例.md) · [6.4.3 内核中的 container_of](6.4.3-Linux内核中的container_of宏.md) · [6.4.4 宏实现分析](6.4.4-container_of宏实现分析.md)。

## 本节讲什么

**`typeof`** 在编译期取出一个表达式的类型；**`container_of`** 从"结构体某成员的地址"反推出"宿主结构体的首地址"。

一句话定性：**它们是 C 语言里唯一的"泛型"机制**。C 没有模板、没有 `decltype`（C23 之前）、没有反射，`typeof` 让宏能"看见"实参的类型，`container_of` 让一份链表代码能挂住任意宿主结构体——这正是 Linux 内核里 `list_head`、`device`、`work_struct`、`sk_buff` 能在不知道宿主类型的情况下工作的原因。

| 关键事实 | 说明 |
|---|---|
| 都是 GNU 扩展 | `typeof` 在 C23 才进标准；`container_of` 从来不是标准，是内核/DPDK 自己定义的宏 |
| `container_of` 运行时**零开销** | `offsetof` 是编译期常量，`-O2` 下只剩一条 `lea`（见 [零开销实测](#33-零开销实测-o0-vs-o2-的反汇编)） |
| 类型检查**很弱** | 只检查"成员类型是否匹配"，**完全不检查宿主类型**（见 [类型检查边界](#34-类型检查的能力边界实测)） |
| 会**丢掉 const** | 从 `const` 对象的成员反推，得到的是**可写**指针，默认开 `-Wextra` 也抓不到（见 [const 陷阱](#35-const-丢失陷阱实测)） |
| 位域、柔性数组是禁区 | 位域 `offsetof` 直接编译错误；柔性数组成员会触发类型不匹配警告（见 [坑点](#六坑点清单)） |

## 一、typeof：在编译期问一句"你是什么类型"

### 1.1 四种拼写，别用错

| 拼写 | 来源 | 说明 |
|------|------|------|
| `typeof(x)` | GNU 老扩展 / **C23 标准关键字** | 在 `-std=c2x` 下是标准；在老 ISO 模式下是 GNU 扩展 |
| `__typeof__(x)` | GNU 保留标识符 | **最安全**：带下划线前缀，任何 `-std` 下都可用，不与用户标识符冲突 |
| `__typeof(x)` | GNU 老拼写 | 等价于 `__typeof__`，历史兼容用 |
| `typeof_unqual(x)` | C23 | 去掉限定符的版本（`const int` → `int`） |
| `__auto_type` | GCC 4.9+ / Clang | 只能用于**带初始化**的声明，比 `typeof` 更省字 |

#### 实测：裸 `typeof` 在哪些 `-std` 下会挂

同一份代码 `typeof(x) a = 2;`（WSL gcc 13.3 / clang 18.1.3）：

| 编译器 + `-std` | 结果 |
|---|---|
| gcc `-std=c99` / `c11` / `c17`（`-pedantic`） | ❌ **编译失败**：`typeof` 不被当作关键字，被解析成隐式函数调用，随后 `expected ';' before 'a'` |
| gcc `-std=gnu99` / `gnu11` / `gnu17` | ✅ 通过，无警告 |
| gcc `-std=c2x` / `gnu2x` | ✅ 通过（C23 关键字） |
| clang `-std=c99` / `c11` / `c17` | ❌ `error: call to undeclared function 'typeof'` |
| clang `-std=gnu99` | ⚠️ 通过但有 `warning: extension used [-Wlanguage-extension-token]` |
| clang `-std=c2x` | ✅ 通过，无警告 |

而 `__typeof__(x) b = 3;` 在 **gcc `-std=c99 -pedantic` 下干净通过**，零警告。

> **结论**：写库代码/头文件一律用 `__typeof__`；只有在确定编译环境是 C23 或 GNU 模式时才用裸 `typeof`。

```c
/* 推荐的可移植写法 */
#if defined(__STDC_VERSION__) && __STDC_VERSION__ > 201710L && !defined(__GNUC__)
#  define my_typeof(x)  typeof(x)        /* C23 标准拼写 */
#else
#  define my_typeof(x)  __typeof__(x)    /* GNU 保留拼写，任何模式都行 */
#endif
```

`typeof_unqual` 实测：gcc 13.3 与 clang 18 在 `-std=c2x` 下都支持，`const int ci` 的 `typeof_unqual(ci)` 得到可写的 `int`。

### 1.2 typeof 的操作数**不被求值**

这是最容易踩的一条，也是它能安全用在宏里的前提。

```c
int i = 0;
typeof(i++) j;      /* 会不会让 i 变成 1？ */
(void)j;
printf("i=%d\n", i);          /* 实测输出：i=0 */

static int side;
static int bump(void) { side++; return 42; }
typeof(bump()) k = 0;         /* 会不会调用 bump()？ */
(void)k;
printf("side=%d\n", side);    /* 实测输出：side=0 */
```

实测结论：**`typeof` 与 `sizeof` 一样只做类型推导，不生成任何运行时代码**，副作用不会发生。

### 1.3 typeof 保留什么：限定符、数组、函数类型

| 场景 | 写法 | 实测结果 |
|------|------|----------|
| const 限定符 | `const int ci=5; typeof(ci) v = 7;` | **保留**：后续 `v = 8;` → `error: assignment of read-only variable 'v'` |
| 数组 | `int arr[5]; typeof(arr) arr2;` | **保留数组类型**：`sizeof(arr2)` = **20**，不是指针的 8 |
| VLA | `int n=4; int vla[n]; typeof(vla) v2;` | 保留 VLA 类型：`sizeof(v2)` = 16 |
| 数组参数 | `void f(int n, int a[n]) { typeof(a) b; }` | **退化成指针**：`sizeof` = 8（参数本就是指针，与 `typeof` 无关） |
| 函数 | `int func(int); typeof(func) *pf = func;` | 保留函数类型，只能用来声明**函数指针** |
| 多变量声明 | `int *p; typeof(p) a, b;` | `a`、`b` **都是 `int *`**（`sizeof` 都是 8） |

最后一行是 `typeof` 相对手写类型的真正价值：

```c
int *p;
typeof(p)  a, b;   /* 两个都是 int* —— 类型是"一块"的 */
int       *c, d;   /* c 是 int*，d 只是 int —— 经典的星号陷阱 */
```

### 1.4 typeof 的头号用途：让宏只求值一次

`typeof` + [语句表达式](../6.3-statement-expr/6.3.2-语句表达式.md) 是 GNU C 的"宏两件套"，解决朴素宏重复求值的老毛病。

```c
#define MAX_naive(a,b) ((a) > (b) ? (a) : (b))
#define MAX_gnu(a,b)  ({ __typeof__(a) _a = (a); __typeof__(b) _b = (b); _a > _b ? _a : _b; })

static int calls;
static int tick(void) { calls++; return 1; }
```

| 表达式 | `tick()` 被调用次数（实测） | `i++` 后 `i` 的值（初值 5） |
|---|---|---|
| `MAX_naive(tick(), 0)` | **2** | — |
| `MAX_gnu(tick(), 0)` | **1** | — |
| `MAX_naive(i++, 0)` | — | **7**（自增执行了两次） |
| `MAX_gnu(i++, 0)` | — | **6** |

**但 `typeof` 救不了整型提升**：`MAX_gnu(-1, 1u)` 实测输出 `4294967295`——因为 `_a` 是 `int`、`_b` 是 `unsigned`，比较时 `int` 被提升为 `unsigned`，`-1` 变成 `UINT_MAX`。**宏不会替你做类型检查，它只保证不求值两次。**

**typeof 宏的两个硬边界**（实测）：

| 实参类型 | 结果 |
|---|---|
| 结构体（`struct big`） | `error: invalid operands to binary >` —— 结构体不能比较 |
| 数组（`int a1[4]`） | `error: invalid initializer` —— `__typeof__(a) _a = (a)` 里数组不能用数组初始化 |

所以内核的 `max()` 才会在 C 里写得那么复杂（`__careful_cmp` + `__cmp_once` + `__builtin_types_compatible_p`）。

### 1.5 __auto_type：更短但有约束

```c
int i = 3;
__auto_type  a = i;    /* OK：自动推导 */
__typeof__(i) b = i;   /* OK */
__typeof__(i) c;       /* OK：可以先声明后赋值 */
/* __auto_type x; */   /* error: '__auto_type' requires an initialized data declaration */
```

gcc 与 clang 表现一致。写宏里想少打一个括号可以用它，但**不能声明未初始化的变量**，作用域比 `typeof` 窄。

## 二、offsetof：成员偏移是编译期常量

```c
#include <stddef.h>
offsetof(type, member)   /* 返回 size_t，是整型常量表达式 */
```

**"常量表达式"这一点可以直接验证**——拿它当数组维度：

```c
struct s { char c; int i; double d; };
static char arr[offsetof(struct s, d)];   /* 编译通过 = 它确实是常量表达式 */
```

实测（`gcc -std=c99 -pedantic -Wall`）：`sizeof(arr)=8`，`offsetof(struct s, d)=8`。

### 位域是禁区

```c
struct s { unsigned a:3; unsigned b:5; unsigned :4; int c; };
offsetof(struct s, c);   /* OK */
offsetof(struct s, b);   /* error */
```

| 编译器 | 报错信息 |
|---|---|
| gcc 13.3 | `error: attempt to take address of bit-field structure member 'b'` |
| clang 18 | `error: cannot compute offset of bit-field 'b'` |

原因很实在：位域**没有地址**，`&s.b` 本身就非法，偏移无从谈起。

## 三、container_of：从成员地址回到宿主

### 3.1 三步推导

```
宿主结构体 struct dev 在内存里的样子：

 &d ──► ┌─────────┐
        │   id    │  offset 0
        ├─────────┤
        │  name   │  offset 8
        ├─────────┤
        │   irq   │  offset 24   ◄── ptr 指向这里
        └─────────┘

已知 ptr = &d.irq，求 &d：
    &d = (char *)ptr - offsetof(struct dev, irq)
```

1. 用 `offsetof` 拿到成员在结构体内的**字节偏移**（编译期常量）；
2. 把成员指针转成 `char *`，按**字节**往回退这么多；
3. 转回 `struct dev *`。

### 3.2 内核版逐字拆解

```c
#define offsetof(TYPE, MEMBER)  __builtin_offsetof(TYPE, MEMBER)

#define container_of(ptr, type, member) ({                      \
    const typeof(((type *)0)->member) *__mptr = (ptr);          \
    (type *)((char *)__mptr - offsetof(type, member)); })
```

每一处都不是随手写的：

| 片段 | 为什么这么写 |
|---|---|
| `({ ... })` | **语句表达式**（[6.3](../6.3-statement-expr/6.3.2-语句表达式.md)）：让宏能先声明局部变量 `__mptr`，并把最后一句当返回值。普通宏做不到 |
| `((type *)0)->member` | **只用于取类型，不求值**。`typeof` 的操作数不生成代码，所以这里没有真的解引用 NULL（见 [1.2](#12-typeof-的操作数不被求值)） |
| `typeof(...)` | 取出"成员自身的类型"，后面加 `*`，得到**成员指针类型** |
| `const` | 让 `__mptr` 能同时接住 `const` 与非 `const` 实参（代价见 [3.5](#35-const-丢失陷阱实测)） |
| `*__mptr = (ptr)` | **这一句是类型检查的全部**：如果 `ptr` 的类型和成员类型不兼容，编译器在这里报警。同时保证 `ptr` **只求值一次** |
| `(char *)` | 按字节做减法。不能用 `void *`——`void *` 的算术是 GNU 扩展，ISO C 未定义；`char *` 是标准保证 1 字节步进的唯一类型 |
| `__mptr` 的双下划线 | 避免与调用方作用域里的变量撞名 |

`ptr` 只求值一次，可以直接验证：

```c
static int *next_irq(void) { return &devs[idx++].irq; }   /* 有副作用 */
struct dev *d = container_of(next_irq(), struct dev, irq);
/* 实测：idx 从 0 变成 1 —— 只调用了一次 */
```

### 3.3 零开销实测：-O0 vs -O2 的反汇编

```c
struct big {
    char             pad[64];
    int              irq;
    struct list_head { struct list_head *n, *p; } node;  /* offsetof = 72 */
    unsigned long long stamp;
};
struct big *get_host(struct list_head *node) {
    return container_of(node, struct big, node);
}
```

| 优化级别 | 生成的 x86-64 指令 |
|---|---|
| `-O0` | `mov %rdi,-0x18(%rbp)` / `mov -0x18(%rbp),%rax` / `mov %rax,-0x8(%rbp)` / `mov -0x8(%rbp),%rax` / `sub $0x48,%rax`（0x48 = 72） |
| `-O2` | `lea -0x48(%rdi),%rax` + `ret` |

**`-O2` 下只剩一条 `lea`**——`typeof` 的类型检查完全发生在编译期，`offsetof` 被折叠成常量，运行时开销为零。这是 `container_of` 能在内核热路径（网络协议栈、调度器）里到处用的底气。

### 3.4 类型检查的能力边界（实测）

这是本节最该记住的表。四种典型误用，只有一种会被编译器拦下：

| 误用 | gcc `-Wall -Wextra` 的反应 | 实际后果 |
|---|---|---|
| **成员名写错，但两个成员类型相同**<br>`container_of(&d.id, struct dev, irq)`（`id`、`irq` 都是 `int`） | **无任何警告** | 地址算错，读到相邻成员/越界内存 |
| **宿主类型写错，成员类型相同**<br>`container_of(&o.irq, struct dev, irq)`（`o` 是别的 struct） | **无任何警告** | 读到另一个对象的内存；若宿主更大则**越界** |
| **成员类型不同**<br>`container_of(&d.name, struct dev, irq)`（`char[16]` vs `int`） | ⚠️ `warning: initialization of 'const int *' from incompatible pointer type 'char (*)[16]'` | 地址算错，但**只是警告**，`-Werror` 才会拦 |
| **传 NULL / 0** | 无告警 | UBSan 才抓：`runtime error: applying non-zero offset 18446744073709551612 to null pointer`，结果 `0xfffffffffffffffc` |

**结论：`container_of` 检查的是"成员类型"，不是"宿主类型"。** 两个 `int` 成员、或两份布局相同的 struct，编译器一律放行——它无法替你确认"这个指针真的来自你说的那个结构体"。

越界这条可以实锤：把 8 字节 `struct small` 的成员当成 72 字节 `struct big` 的成员传进去，普通编译**零警告**，`-fsanitize=address` 立刻报 `stack-buffer-overflow READ of size 1`。

### 3.5 const 丢失陷阱（实测）

```c
const struct dev d = { 1, 2 };
struct dev *p = container_of(&d.irq, struct dev, irq);
p->id = 99;                 /* 从 const 对象里"洗"出了一个可写指针 */
printf("d.id=%d\n", d.id);  /* 实测输出：d.id=99 */
```

| 开关 | 是否报警 |
|---|---|
| `gcc -Wall -Wextra`（默认） | ❌ 静默 |
| `gcc -Wcast-qual` | ✅ `warning: cast discards 'const' qualifier from pointer target type` |
| `clang -Wcast-qual` | ✅ `warning: cast from 'const int *' to 'char *' drops const qualifier` |

宏里的 `(char *)__mptr` 就是那个丢 `const` 的转型——`(char *)` 而不是 `(const char *)`。**默认编译选项抓不到**，必须显式加 `-Wcast-qual`。内核为此在新版本引入了 `container_of_const()`，返回 `const type *`，让 const 性质传递下去：

```c
#define container_of_const(ptr, type, member) ({                     \
    const __typeof__(((type *)0)->member) *__mptr = (ptr);           \
    (const type *)((const char *)__mptr - offsetof(type, member)); })
```

实测：非 `const` 指针传给 `container_of_const` 不会报错（加 const 是安全的），`const` 对象的成员也只能得到 `const` 宿主指针——写操作在编译期就被挡住。

## 四、嵌入式与内核里的实战

### 4.1 侵入式链表：完整可运行实现

普通链表是"链表节点装着数据指针"；**侵入式链表是"数据里嵌一个链表节点"**，一份链表代码服务所有结构体。

```c
struct list_head { struct list_head *next, *prev; };

#define container_of(ptr, type, member) ({                      \
    const __typeof__(((type *)0)->member) *__mptr = (ptr);      \
    (type *)((char *)__mptr - offsetof(type, member)); })
#define list_entry(ptr, type, member) container_of(ptr, type, member)

#define list_for_each(pos, head) \
    for (pos = (head)->next; pos != (head); pos = pos->next)

static void list_add(struct list_head *new, struct list_head *head)
{
    new->next = head->next;
    new->prev = head;
    head->next->prev = new;
    head->next = new;
}

/* 宿主：一个"设备" */
struct device {
    int              id;
    char             name[16];
    struct list_head node;      /* 挂在设备链表上 */
    unsigned         irq;
    struct list_head irq_node;  /* 同时挂在 IRQ 链表上 */
};
```

实测输出（`gcc -std=gnu11 -Wall -Wextra`）：

```
sizeof(struct device)=64 offsetof(node)=24 offsetof(irq_node)=48
--- dev_list (逆序，头插) ---
  id=2 name=i2c2 irq=32
  id=1 name=spi1 irq=31
  id=0 name=uart0 irq=30
--- irq_list ---
  id=2 name=i2c2 irq=32
  id=1 name=spi1 irq=31
  id=0 name=uart0 irq=30
via_irq: id=1 name=spi1 (==&d1 ? yes)
```

**关键观察**：`node` 和 `irq_node` 是同一个 `struct device` 里的两个节点，偏移分别是 24 和 48。同一份 `list_add`/`list_for_each` 代码，靠调用方传入的 **`member` 参数**决定回推到哪个偏移——`container_of` 把"链表算法"和"宿主类型"彻底解耦。这就是内核 `struct list_head` 只有两个指针却能挂住上万物种结构体的原因。

对比一下传统做法的代价：

| 方案 | 每次插入的分配 | 内存局部性 | 一个结构体挂多张链表 |
|---|---|---|---|
| 传统链表（节点持有 `void *data`） | 额外 `malloc` 一个节点 | 差（数据与控制块分离，多一次 cache miss） | 需要多套节点 |
| **侵入式链表（`list_head` 内嵌）** | **无** | **好**（节点就在宿主结构体里，与热点数据同 cache line） | **同一个结构体多放几个 `list_head` 即可** |

对 HFT/嵌入式都是决定性的：前者少一次内存分配、少一次指针追逐；后者**根本用不了 malloc**的场景（裸机、中断上下文）也能用链表。

### 4.2 驱动里的 private data

`container_of` 在内核里最常见的另一处用法，是把"通用对象"还原成"具体设备对象"：

```c
/* 内核里的典型形态（示意） */
struct platform_device *pdev = ...;
struct mydrv_priv *priv = container_of(pdev->dev, struct mydrv_priv, dev);

/* 网络设备：netdev 后面紧跟私有数据 */
static inline void *netdev_priv(const struct net_device *dev)
{
    return (char *)dev + ALIGN(sizeof(struct net_device), NETDEV_ALIGN);
}
```

前者是 `container_of`（成员在结构体内），后者是**固定偏移加法**（私有数据分配在 `net_device` 之后）——后者更快，因为不需要减偏移，代价是私有数据只能在尾部、且大小在分配时确定。

### 4.3 与 packed / 柔性数组的边界

| 场景 | 实测结果 |
|---|---|
| `packed` 结构体的成员做 `container_of` | 地址算得**对**（`offsetof` 拿到的是真实偏移），但 `&p.seq` 未对齐 → gcc 默认开 `-Waddress-of-packed-member` 警告；**x86 上访问正常，ARMv5/ARMv7 上未对齐访问会触发 alignment fault** |
| 柔性数组 `unsigned char data[]` 做 `member` | ⚠️ `warning: initialization of 'const unsigned char (*)[]' from incompatible pointer type 'unsigned char *'`——`typeof` 取出的是**数组类型**，加 `*` 后变成"指向数组的指针"。能编译、结果也对，但类型不匹配；**不要这么写** |

### 4.4 HFT / 嵌入式视角

| 维度 | 意义 |
|---|---|
| **零分配** | 数据结构内嵌节点，热路径上不碰 allocator，尾延迟可控 |
| **cache 友好** | 节点与业务字段同处一个结构体，遍历时一次 cache line 就能拿到判断所需的数据 |
| **零运行时开销** | `-O2` 下是一条 `lea`，可以放心放在行情回调、订单簿遍历里 |
| **裸机可用** | 没有 OS、没有堆也能用侵入式容器，这是嵌入式选它而不是 glib 的根本原因 |
| **代价** | 类型安全弱（见 [3.4](#34-类型检查的能力边界实测)），单元测试里必须开 ASan/UBSan 兜底 |

## 五、没有 typeof 怎么办（可移植写法）

| 方案 | 适用 | 说明 |
|---|---|---|
| `__typeof__` | 任何 GCC/Clang + 任何 `-std` | **首选**，见 [1.1](#11-四种拼写别用错) |
| C23 `typeof` | `-std=c2x` / `gnu2x` | 标准拼写，gcc 13+ / clang 都支持 |
| `__auto_type` | GCC 4.9+ / Clang | 更短，但必须带初始化 |
| 标准 C 版 `container_of` | 任何 C 编译器 | 丢掉类型检查，见下 |
| MSVC | — | 不支持 `typeof`，需要用 `_Generic` 或放弃检查 |

退而求其次的标准 C 版本（没有 `typeof`，也就**没有类型检查**）：

```c
/* 无 typeof：能编译、能算对，但传错指针类型不会有任何提示 */
#define container_of_unsafe(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

工程上的三层封装建议：

```c
#if defined(__GNUC__) || defined(__clang__)
#  define CT_TYPEOF(x)      __typeof__(x)
#  define HAVE_TYPEOF       1
#elif defined(__STDC_VERSION__) && __STDC_VERSION__ > 201710L
#  define CT_TYPEOF(x)      typeof(x)
#  define HAVE_TYPEOF       1
#else
#  define HAVE_TYPEOF       0        /* 退化到无检查版本 */
#endif
```

## 六、坑点清单

| # | 坑 | 现象 | 规避 |
|---|---|---|---|
| 1 | 裸 `typeof` 在严格 ISO 模式下不认 | clang `-std=c11` 直接 `error` | 一律写 `__typeof__` |
| 2 | 位域做 `offsetof` | 编译错误（`attempt to take address of bit-field`） | 位域不能做 `container_of` 的成员，也没法取地址 |
| 3 | 同类型成员/同布局宿主传错 | **零警告**，静默读错内存 | 代码审查；测试开 ASan |
| 4 | `const` 被丢弃 | `-Wall -Wextra` 抓不到，真能改写 const 对象 | 加 `-Wcast-qual`；用 `container_of_const` |
| 5 | 传 NULL | 静默得到 `0xfffffffffffffffc` 之类的野地址 | 开 UBSan；入口处判空 |
| 6 | 柔性数组成员做 `member` | `incompatible pointer types` 警告（数组类型 + `*`） | 用结构体起始成员或显式 `(char *)` 偏移 |
| 7 | `packed` 成员取地址 | `-Waddress-of-packed-member`；ARM 上未对齐访问 fault | 用 `memcpy`/`get_unaligned` 读写，不要直接解引用 |
| 8 | `typeof` 宏遇上数组/结构体实参 | `invalid initializer` / `invalid operands to binary >` | `typeof` 宏只用于标量；数组场景用函数或 `min_t/max_t` 风格（显式传类型） |
| 9 | 手动写 `((type *)0)->member` 取地址 | 真解引用 NULL，运行期崩溃 | 记住 `typeof(...)` 只取类型；取地址要用 `offsetof` |
| 10 | 以为 `container_of` 检查了宿主类型 | — | 它只检查成员类型，见 [3.4](#34-类型检查的能力边界实测) |

## 代码自测

**题目 1：** 下面这段在 `gcc -std=c11` 下会怎样？为什么？
```c
int x = 1;
typeof(x) a = 2;
```
<details>
<summary>答案</summary>

**编译失败**（clang 下是硬性 `error`，gcc 下 `typeof` 被当成隐式函数声明，随后语法错误）。`-std=c11` 是严格 ISO 模式，`typeof` 不是关键字；它在 C23 才进标准。
改成 `__typeof__(x)` 即可在任何 `-std` 下通过；或者改用 `-std=gnu11` / `-std=c2x`。

</details>

**题目 2：** `typeof(i++)` 会不会让 `i` 自增？`typeof(bump())` 会不会调用 `bump()`？
<details>
<summary>答案</summary>

**都不会**。`typeof` 与 `sizeof` 一样，操作数只参与类型推导，不生成运行时代码。实测：`i` 保持 0，副作用计数 `side` 保持 0。
这也是 `((type *)0)->member` 这种写法安全的原因——它没有真的解引用 NULL。

</details>

**题目 3：** `int *p; typeof(p) a, b;` 与 `int *c, d;` 里，`b` 和 `d` 分别是什么类型？
<details>
<summary>答案</summary>

`b` 是 `int *`（`typeof(p)` 展开成完整类型 `int *`，修饰后面所有变量）；`d` 是 `int`（星号只绑定 `c`）。
实测 `sizeof`：a=8、b=8、c=8、d=4。这是用 `typeof` 声明多个同类型变量的好处。

</details>

**题目 4：** 为什么 `container_of` 里用 `(char *)` 而不是 `(void *)` 做减法？
<details>
<summary>答案</summary>

`void *` 的指针算术在 ISO C 中**未定义**（GNU C 把它当 1 字节扩展，但不可移植）。`char *` 是标准保证 `sizeof(char) == 1`、按字节步进的类型，所以在所有编译器上行为一致。

</details>

**题目 5：** 下面代码有没有问题？编译器会报什么？
```c
struct dev { int id; int irq; };
struct dev d = { .id = 7, .irq = 30 };
struct dev *q = container_of(&d.id, struct dev, irq);
```
<details>
<summary>答案</summary>

**编译器什么都不报**。因为 `id` 和 `irq` 都是 `int`，`typeof` 检查通过。
但地址算错了：`&d.id` 回退 `offsetof(struct dev, irq)`，得到 `&d - 4`，落在结构体之前的内存。实测 `q != &d`，读 `q->irq` 实际读到 `d.id`。
`container_of` 只检查**成员类型**，不检查**成员是不是你以为的那个**。

</details>

**题目 6：** 如何从 `const` 对象安全地做 `container_of`？
<details>
<summary>答案</summary>

标准 `container_of` 会**丢掉 const**（`(char *)__mptr` 是去 const 的转型），默认 `-Wall -Wextra` 抓不到，实测能把 `const struct dev d` 的字段改写成功。
两个办法：
1. 编译时加 `-Wcast-qual`——实测 gcc/clang 都能报出 `cast discards 'const' qualifier`；
2. 用 `container_of_const()`（返回 `const type *`），让 const 性质传递到结果指针上，写操作在编译期就被拦。

</details>

**题目 7（判断）：** `offsetof` 可以用于位域成员。

<details>
<summary>答案</summary>

**错**。位域没有独立地址，`&s.bitfield` 本身就非法。
实测：gcc 报 `error: attempt to take address of bit-field structure member`；clang 报 `error: cannot compute offset of bit-field`。

</details>

**题目 8：** 为什么侵入式链表在嵌入式和 HFT 里比传统链表更受欢迎？
<details>
<summary>答案</summary>

三点：
1. **零分配**——节点内嵌在宿主结构体里，插入不需要 `malloc`，裸机和中断上下文都能用；
2. **cache 友好**——遍历时节点与业务字段在同一块内存，少一次指针追逐（传统链表要跳到别处取数据）；
3. **一个结构体能挂多张链表**——多放几个 `list_head` 成员即可，靠 `container_of` 的 `member` 参数区分（实测同一个 `struct device` 用 `node` 和 `irq_node` 同时挂两张链表，都能正确回推）。

代价是类型安全弱，所以测试要开 ASan/UBSan。

</details>

**题目 9：** `container_of` 在 `-O2` 下的运行时开销是多少？
<details>
<summary>答案</summary>

**零**。实测 `-O2` 下 `get_host()` 只剩两条指令：`lea -0x48(%rdi),%rax` + `ret`（`-0x48` = `offsetof` 算出的常量偏移 72）。
`-O0` 下还有几次栈上搬运和一条 `sub $0x48,%rax`，优化后全部折叠。`typeof` 的检查是纯编译期行为。

</details>

**题目 10：** 写一个 `container_of` 的简化版，并说明它相对内核版少了什么保护。
<details>
<summary>答案</summary>

```c
#define container_of_unsafe(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

相对内核版少了三样：
1. **类型检查**——没有 `typeof`，传任何指针都能编译；
2. **只求值一次**——`ptr` 在表达式里出现一次所以这条其实也满足，但一旦有人改写宏引入第二处 `ptr` 就会重复求值；内核版用 `__mptr` 局部变量强制只求值一次；
3. **const 处理**——内核版的 `const typeof(...)` 能接住 `const` 指针，简化版直接 `(char *)(ptr)` 会在传 `const` 指针时报 `discards qualifiers`（也算一种提醒，但表达不了 `container_of_const` 的语义）。

</details>
