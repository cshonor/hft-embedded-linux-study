# 4.11.1 文件包含

## 本节讲什么

**`#include`** 在预处理阶段把指定文件**原样插入**当前位置，实现声明共享与模块化。

## 要点

```c
#include <stdio.h>    /* 系统/标准库头：编译器搜索系统目录 */
#include "myhdr.h"    /* 本地头：通常先搜当前目录，再搜系统路径 */
```

- `#include` 可嵌套；重复包含同一头会导致重复声明 → 用 **include guard** 或 `#pragma once`
- 尖括号 vs 引号：约定上 **系统 API 用 `<>`**，项目头用 `""`
- 预处理仅做文本替换，**不进行类型检查**

## 工程习惯

- 每个 `.c` 先 include 自己的 `.h`（验证头文件自洽）
- 头文件尽量 **只放声明**，减少编译依赖

## 常见陷阱

1. **循环包含导致无限递归**：`A.h` 包含 `B.h`，`B.h` 又包含 `A.h`，预处理器无限展开。解决：每个头加 **include guard**（`#ifndef A_H` / `#define A_H` / `#endif`）或 `#pragma once`。
2. **头文件放定义导致重复定义**：头文件里写 `int g_count = 0;`（定义而非声明），多个 `.c` 包含后链接报"multiple definition"。规则：**头文件只放声明**（`extern int g_count;`），定义放 `.c`。内联函数和 `static const` 例外。
3. **include 顺序掩盖头文件不自洽**：`.c` 里先 include 系统头再 include 自己的 `.h`，如果自己的 `.h` 依赖系统类型却没 include，恰好被前面的系统头"喂到"而不报错。规范：**每个 `.c` 先 include 自己的 `.h`**，暴露依赖缺失。

## 自测题

**1. 选择**：`#include <stdio.h>` 和 `#include "stdio.h"` 的主要区别是？
- A. 没有区别
- B. `<>` 只搜系统目录，`""` 先搜当前目录再搜系统目录
- C. `""` 只搜当前目录
- D. `<>` 比 `""` 快

<details><summary>答案</summary>
B。尖括号搜系统/标准库路径，引号先搜当前目录再回退系统路径。这是约定，具体由编译器实现（`-I` 可改变搜索路径）。
</details>

**2. 判断**：`#pragma once` 是 C 标准的一部分。

<details><summary>答案</summary>
错。`#pragma once` 不是 C 标准，但被 GCC/Clang/MSVC 等主流编译器普遍支持。跨编译器项目（如某些嵌入式工具链）仍推荐标准 include guard 以保证可移植性。
</details>

**3. 踩坑**：`A.h` 和 `B.h` 互相 `#include`，编译报"struct Node 重定义"，如何修复？

<details><summary>答案</summary>
两个头都缺 include guard。给 `A.h` 加 `#ifndef A_H / #define A_H / #endif`，`B.h` 同理。若确有循环依赖（A 的定义需要 B、B 的定义需要 A），需前向声明打破：在 `B.h` 里 `struct A;`（前向声明）而非 include `A.h`，把真正的 `#include "A.h"` 移到 `.c`。
</details>

**4. 应用**：为一个链表节点头文件 `list_node.h` 写完整的 include guard。

<details><summary>答案</summary>
```c
#ifndef LIST_NODE_H
#define LIST_NODE_H

struct Node {
    int data;
    struct Node *next;
};

#endif /* LIST_NODE_H */
```
guard 宏名用文件名全大写加下划线，避免与其他头冲突。
</details>

## 与后续衔接

内核 `#include <linux/...>`、UEFI `#include <Uefi.h>` 与 user space `#include <stdio.h>` 机制相同，搜索路径由构建系统（Makefile、CMake）指定。
