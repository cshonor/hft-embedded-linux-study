1.1

what-is-async

Demo：1.1-what-is-async/1.1-what-is-async-join-demo.rs

一、核心梳理（详细展开）

1.1.1 高视角：并发的本质

现代操作系统通过在少量 CPU 核心上快速切换执行流（线程/任务），让你感觉「成千上万个程序在同时跑」。

但 CPU 同一时刻只能真正执行一个逻辑流（单核视角）。所谓「并发」，本质是：

  • 切得快 → 看起来并行
  • 等待多 → 切换收益大（I/O 密集最合适）

1.1.2 同步阻塞（Synchronous Blocking）

定义：发起 I/O 后，线程原地阻塞，什么都不干，直到 I/O 完成。

  • 比喻：烧水时，你站在水壶旁边死等，水不开不走，这段时间不能做别的事。
  • 代码特征：
// 同步读文件（std::fs）
let content = std::fs::read_to_string("data.txt").unwrap();
// 这一行没读完，下一行不会执行
println!("done");
  • 问题：I/O 等待时线程被浪费；要高并发就得开很多线程，内存与上下文切换成本都很高。

1.1.3 异步非阻塞（Asynchronous Non-blocking）

定义：发起 I/O 后先让出执行权，去跑其它任务；I/O 就绪后再从断点继续。

  • 比喻：烧水时点火后去洗菜；水开（事件就绪）再回来关火。
  • 核心：利用 Dead Time（等待时间） 做有用的事。
  • Rust / Tokio 特征：
async fn read_file() -> String {
    tokio::fs::read_to_string("data.txt").await.unwrap()
}
  • .await：在 I/O 未就绪时协作式让出，运行时去 poll 其它任务。
  • 就绪后：任务被 Waker 唤醒，从 .await 之后继续执行。

1.1.4 tokio::join!：并发等待多个异步操作

作用：在不额外为每个任务开 OS 线程的前提下，同时推进多个异步任务，并等待全部完成。

行为 说明
启动 括号内各 Future 同时开始 poll
结束 全部 Ready 后 join! 才返回
墙钟时间 ≈ 最慢 那个任务的耗时，而非相加

示例：task_a sleep 1s、task_b sleep 2s：

  • 串行 await：约 3s
  • join!(task_a(), task_b())：约 2s

二、摩尔定律与 I/O 现实（为什么异步越来越重要）

2.1 摩尔定律放缓

  • 2010 年后，单核频率提升明显放缓（常见 ~3GHz 量级）。
  • 算力增长更多靠多核，但核心数仍有限。
  • 结论：不能指望「CPU 越来越快」单独解决服务端扩展问题。

2.2 服务端的真实负载：I/O 密集

现代后端大量时间花在等 I/O：

  • HTTP / RPC
  • 数据库
  • 磁盘与缓存（Redis 等）

这些操作CPU 占用低，但延迟高（毫秒～秒级）。

2.3 异步的目标

不是让 CPU 算得更快，而是：

  • 在 I/O 密集场景下，用少量线程（常接近 CPU 核数）承接海量并发连接/请求；
  • 提高吞吐（单位时间完成请求数）；
  • 改善响应（减少排队与空等）。

一句话：

线程很贵，I/O 等待很闲 → 异步把闲时间变成有效工作量。

1.2

Introduction to Processes（进程简介）

核心梳理

  • 定义：进程是 OS 分配资源的边界，独立虚拟地址空间，有 PID。
  • 硬隔离：一进程崩溃通常不直接破坏另一进程内存（如 PostgreSQL 每连接一进程的模式）。
  • 局限：
  • 创建/销毁昂贵（页表、句柄、内核结构）；
  • 扩展性差（大量连接时进程数爆炸）；
  • IPC 需序列化 + 内核中转，延迟与复杂度高。

与异步的关系

标准 async 服务端多为单进程 + 多线程/async 运行时，在同地址空间用 Arc/通道共享状态；多进程用于隔离部署，而非每个请求一进程。

1.3

What Are Threads?（什么是线程？）

核心梳理

  • 调度单元：线程是 OS 调度的常见最小执行序列；thread::spawn + JoinHandle 分发计算任务。
  • 四种生命周期（API 视角）：可连接 / 分离 / 终止 / main 退出强杀 — 精读见 atomic §1.1.7（Rust 无与内核一一对应的线程状态枚举）。
  • 共享内存：同进程线程共享地址空间；传数据可用 Arc<T>（比跨进程 IPC 轻）。
  • 同步原语：Mutex 互斥、Condvar 在条件不满足时挂起线程，状态就绪后唤醒——这是理解 async 里 park/Waker 的 OS 层对照。

上下文切换

线程过多时，保存/恢复寄存器、缓存失效带来开销。async 用少量 OS 线程 multiplex 大量「等 I/O」任务，减少「为等而开线程」。

数据竞争

多线程改同一数据需纪律；Rust 编译期拦截部分 Data Race，逻辑设计仍须 Mutex/消息传递。

1.4

Where Can We Utilize Async?（在哪里利用异步？）

核心梳理

  • 最佳场景：存在潜在延迟的操作——文件 I/O、网络、用户输入等。
  • 数量级：内存 ~ns vs 网络 RTT ~ms（差 10⁴～10⁶）→ I/O 常是瓶颈；async 把等待期 CPU 让给其它任务。
  • 不适用：CPU-bound（加密、转码、大规模数值）——靠更多核、更好算法、SIMD；套 async 不会魔法加速。

决策简表

类型 是否优先 async
等网络/磁盘 是
纯计算 否（用线程池/并行库）

2.1

Understanding Tasks（理解任务）

Demo：2.1-understanding-tasks/2.1-understanding-tasks-join-demo.rs

核心梳理

  • Task（任务）：由执行器驱动、直至完成的异步工作单元；async fn 被调用时往往先得到 Future，再被包装成 Task 入队调度。
  • 协作式多任务（cooperative multitasking）：任务在 await / 返回 Pending 时主动让出线程，同一线程上可切换去 poll 其它任务——不是 OS 抢占式「硬切」每个 async 块。
  • tokio::join!：在同一任务内并发等待多个子 Future（例如多个 tokio::time::sleep），总耗时接近最慢那个，而不是顺序相加。

与线程的区别（直觉）

OS 线程 async Task
调度 内核抢占 运行时协作式 poll
阻塞 sleep 占满线程 tokio::time::sleep 不占线程干等
数量级 过多线程贵 大量 I/O 等待任务更划算

2.2

Futures（Future 特型）

Demo：2.2-futures/2.2-futures-counter-demo.rs

核心梳理

  • Future：尚未完成的异步操作的占位符；完成后产出 Output。
  • 惰性：只创建 Future 而不 await / 不 poll，体内逻辑往往不会执行。
  • poll：同步调用；返回 Poll::Ready(T) 或 Poll::Pending。执行器在 Pending 时去跑别的任务，而不是空转占满 CPU。
fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;

计数器 Future（书中主线）

CounterFuture 每次 poll 将计数 +1；未满 5 次则 wake_by_ref() 并返回 Pending（教学用「立刻再调度」）；满 5 返回 Ready。与书中「理解 Pending/Ready」一致。

为什么是轮询而不是回调？

Rust 将 async 编译为状态机 + poll，减少回调链上的分配与生命周期负担，贴近零成本抽象（具体仍受 Box、动态分发影响）。

2.3

Pinning in Futures（Future 中的 Pin）

核心梳理

  • async fn 展开为状态机；跨 await 的局部变量可能形成自引用（字段指针指向同结构体另一字段）。
  • 移动即 UB：若该状态机被移动（传参、Vec 重分配），内部指针仍指向旧地址 → 段错误 / 未定义行为。
  • Pin<&mut T>：约定在 poll 期间不能安全移动 T，从而固定自引用目标的地址。
  • Unpin：无自引用需求的类型（如本仓库 CounterFuture 仅 u32）可 Unpin，在 Pin 内仍可用 get_mut() 安全改字段。

现象 含义
到处见 Pin 保护编译器生成的 async 状态机
CounterFuture 不用复杂 Pin API 无自引用，教学简化

2.4

Context in Futures（Future 中的 Context）

核心梳理

  • Context 的核心作用：在 poll 时提供 Waker 句柄。
  • 流程：Future 发现未就绪 → Pending → 把 Waker 交给 I/O/通道/定时器 → 就绪时 wake → 执行器再次 poll。
  • 避免忙等：不应在 Pending 上自旋；应依赖事件 + Waker（教学里 wake_by_ref() 立即再 poll 仅用于理解控制流）。

超时与取消安全（Cancel Safety）

  • select! / 超时：被取消的分支可能未完成；须保证无半初始化资源、无持锁跨取消。
  • 持 std::sync::MutexGuard 再 .await：危险——让出时锁未释放，易死锁；用 tokio::sync::Mutex 或缩小临界区。

与第 1 章衔接

不要在 async 任务里 std::thread::sleep；用 tokio::time::sleep 等返回 Pending 的 API。

2.5

Waking Futures Remotely（远程唤醒 Future）

Demo：2.5-waking-futures-remotely/2.5-waking-futures-remotely-demo.rs

核心梳理

  • 问题：对外部事件（网络、通道、另一线程）若盲目轮询 Future，浪费 CPU。
  • 做法：在 poll 返回 Pending 前，把 cx.waker().clone() 存到共享槽位；外部在数据就绪时调用 wake()。
  • 本仓库：mpsc 收到消息后由另一任务取出保存的 Waker 并唤醒；Future 再次 poll 时 try_recv 成功 → Ready。

与真实栈的对应

生产里由 epoll/IOCP、Tokio driver、定时器 wheel 等在就绪点调用 wake，而不是手写通道槽位；本节建立「谁保存 Waker、谁在何时 wake」直觉。

Sharing Data Between Futures（Future 之间共享数据）

Demo：2.6-sharing-data-between-futures/2.6-sharing-data-try-lock-demo.rs

核心梳理

  • 需求：多个 Future 读写同一份状态 → 需要 Arc 共享所有权 + Mutex 互斥。
  • 手写 poll 的铁律：必须用 try_lock()（或非阻塞路径）；禁止在 poll 里阻塞式等锁，否则会卡住整个运行时线程上的所有任务。

与 std::sync::Mutex + .await 的区别

3.4

Task Stealing（任务窃取）

核心梳理

  • 问题：高优队列空转、低优队列堆积 → 浪费 CPU。
  • 窃取：某 worker 主队列空时，尝试从其他通道（常为低优）拉取任务执行。
  • 流程： 1. recv 自己的主通道； 2. 若空，尝试低优（或其它）通道； 3. 仍空则 park / sleep 短间隔后重试。

Creating Our Own Join Macro（自定义 Join 宏）

Demo：3.6-creating-join-macro/3.6-creating-join-macro-demo.rs

核心梳理

  • 痛点：主函数里多次 block_on 等待多个任务，样板代码多。
  • 做法：自写 join! / try_join!，一次传入多个 Future 并收集结果。

本仓库宏语义（重要）

macro_rules! join {
    ($($future:expr),*) => {{
        let mut results = Vec::new();
        $( results.push(futures_lite::future::block_on($future)); )*
        results
    }};
}

这是对每个 Future 依次 block_on，不是 Tokio join! 在同一执行器上的真并发。对照书中「自建队列 + worker」时，应让多个任务先入队再由线程池推进。

5.1

Introducing Coroutines（协程简介）

什么是协程

协程可在执行中暂停，之后从断点恢复——不同于跑到底的普通函数，也不同于 OS 抢占式调度的线程。

对比 行为
子例程 一次跑完
线程 OS 抢占
协程 协作式主动让出

为什么使用协程

  • 单线程追加写文件：保留状态、多次写入，比反复 open/close 快（书中约 6× 量级，视 I/O 而定）。
  • 无需 Mutex：同一线程内协程交替执行，无数据竞争。
  • 有状态 + 非阻塞：暂停时不占满 CPU（由外部循环决定何时 resume）。

Rust 现状

语言级 #[coroutine] / Coroutine 仍在 nightly；本仓库用 状态机 在 stable 上对照 Yield/Resume 语义（见 §5.2 demo）。

代码对数据值或事件的变化做出动态响应，而不是一次性算完就结束。本章从手写加热器系统入手，不依赖庞大外部框架。

观察者模式 (Observer Pattern)

角色 职责
Subject（主题） 持有状态，变化时通知订阅方
Observer（观察者） 订阅变化并执行副作用（控温、刷新 UI 等）

7.2

Processing Tasks with Local Pools（使用本地池处理任务）

LocalPoolHandle 做什么

在 Tokio 生态内（相对第 3 章「从零写执行器」）用 tokio_util::task::LocalPoolHandle：

  • 将任务绑定到指定本地线程池，甚至 spawn_pinned_by_idx 固定到某索引 worker。
  • 运行 未实现 Send 的 Future（线程局部、Rc 等）。
  • 利用线程亲和性：数据留在同一 worker 缓存，减少多线程争用全局 Mutex。

与默认工作窃取对比

特性 默认 Tokio 工作窃取 本地池 + pinned
负载均衡 自动窃取 无窃取，可能单线程过载
!Send 不可跨线程 spawn 可在固定线程跑
锁竞争 可能争用全局结构 可本地化状态

示例代码

use tokio_util::task::LocalPoolHandle;

#[tokio::main]
async fn main() {
    let pool = LocalPoolHandle::new(4);
    let handle = pool.spawn_pinned_by_idx(
        || async { 42 },
        0, // worker 索引 < num_threads
    );
    let result = handle.await.unwrap();
}

7.3

Getting Unsafe with Thread Data（不安全地访问线程数据）

动机

在单线程本地池中，若仍用 RefCell，运行时要做借用检查。为榨取性能，书中用 UnsafeCell 无锁访问线程内数据。

安全边界（必须同时满足）

  1. 任务跑在 单线程本地池，数据不跨线程 Send。
  2. 持有裸指针访问期间 不 await——避免任务挂起后同线程跑别的任务破坏别名规则。
  3. 自行证明无数据竞争；否则为 UB。

与 §7.2 的关系

spawn_pinned 提供「固定线程」语义；UnsafeCell 提供「同步块内无借用检查」语义——二者组合才是书中完整优化路径。

常见陷阱

  • 在 unsafe 块中 await → 可能切换任务并破坏独占访问。
  • 把 UnsafeCell 包装的类型 Send 到别的线程 → 竞争。

7.4

Graceful Shutdowns（优雅停机）

覆盖默认强制退出

用户 Ctrl+C 或 SIGHUP 等信号不应立刻 exit，而应触发收尾流水线：

  1. 停止接受新请求；
  2. await 未完成句柄（各本地池上的任务）；
  3. 汇总状态（如书中 get_complete_count 一类接口）并持久化；
  4. 再退出进程。

信号监听

use tokio::signal;

signal::ctrl_c().await.expect("ctrl_c");
// 向各 LocalPool 发 shutdown 任务，刷盘…

与本地池结合

向各独立本地线程 spawn 专用异步任务，提取线程局部数据并汇总——避免主线程一把抓导致遗漏 pinned 状态。

  • 独占文件句柄，将 KV Actor 的变更异步写入 data.json（或 WAL）；
  • KV 处理事务时把指令转发给 Writer，避免多 Actor 争用同一文件。

启动恢复

Actor / 系统启动时 读取 data.json，重建内存 HashMap，实现崩溃或重启后的状态恢复。

注意

  • 写盘频率 vs 性能：批量、定时刷盘；
  • 与 §8.5 监督配合：Writer 卡死时心跳超时触发重启。

章节索引：本章学习笔记.md · 本书详细目录

8.5

Creating Actor Supervision（Actor 监控）

心跳 (Heartbeat)

子 Actor 定期向路由（或主管）发送 Heartbeat；主管用 tokio::time::timeout 检测（书中阈值约 0.5s / 笔记常写 200ms 量级，以书为准）。

超时未收到 → 判定卡死或崩溃。

Supervisor Actor

  • 监控所有子 Actor 健康；
  • 触发 Reset：中止旧任务、清理通道、重建 Actor 与邮箱；
  • 实现自我修复（策略：重启、退避、降级由业务定）。

陷阱

  • mpsc 容量过大掩盖背压；
  • 心跳 recv 无 timeout 导致监督任务自身死等；
  • 全栈 Actor 成本高 → 混合架构更常见（见 §8.6）。

9.2

Waterfall Design Pattern（瀑布 / 责任链）

核心

又称 Chain of Responsibility：多个异步步骤用 ? 串联，上一步输出 = 下一步输入。

  • 流程清晰、可预测；
  • 单一组件可在不同流水线中复用。

Rust 写法

async fn pipeline() -> Result<Response, Error> {
    let a = step_one().await?;
    let b = step_two(a).await?;
    step_three(b).await
}

失败时 ? 提前返回，避免嵌套 match 地狱。

9.5

The Retry Pattern（重试模式）

核心

网络失败、503、数据库过载时，按策略重试；配合 指数退避（Exponential backoff） + 抖动，避免对故障方「请求轰炸」。

示例逻辑

    match perform_async_call().await {
        Ok(v) => return Ok(v),
        Err(e) => {
            sleep(backoff(i)).await; // 如 1 << i，生产应加上限与 jitter
        }
    }
}

9.6

The Circuit-Breaker Pattern（熔断器模式）

核心

重试无望时（依赖已崩溃），继续 spawn 任务只会浪费 CPU。熔断器用 AtomicBool / AtomicUsize 记录失败次数：

  • 未达阈值：Closed，正常放行；
  • 越界：Open，快速失败，不再生成注定失败的 Future；
  • 冷却后：Half-Open 探测恢复（策略由业务定）。

与 §9.5 配合

先 Retry + Backoff 处理瞬时故障；持续失败则 Open 保护下游与自身。

11.5

Testing Channel Capacity（测试通道容量）

Demo：11.5-testing-channel-capacity/11.5-testing-channel-capacity-demo.rs

有界 mpsc

tokio::sync::mpsc::channel(cap)：cap == 0 为 rendezvous；cap > 0 为缓冲。发送在满时：

  • send().await → 阻塞直到有空间；
  • try_send() → 立即返回 Err(TrySendError::Full)。

要测的行为

  1. 背压：生产者不能无限超前；
  2. 恢复：消费者 recv 后，阻塞的发送应完成；
  3. 超时：若发送在 timeout 内未完成，说明背压符合预期（或死锁）。

测试骨架

let (tx, mut rx) = tokio::sync::mpsc::channel(2);
tx.send(1).await.unwrap();
tx.send(2).await.unwrap();
let send_more = tokio::spawn(async move { tx.send(3).await });
let blocked = timeout(Duration::from_millis(100), send_more).await.is_err();
assert!(blocked);
let _ = rx.recv().await;
// 此时 send(3) 应能完成

与生产

通道过大 → 掩盖背压问题；过小 → 吞吐下降。测试应锁定业务承诺（满时阻塞还是丢弃）。
