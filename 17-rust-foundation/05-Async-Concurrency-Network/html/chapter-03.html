3.1

simple-tcp-server-client

书 §3.1 · 理论：Ch01 TCP 状态机 · 贯通稿：notes/Ch03-… · 线程模型：atomic §1.1

一、本章在学什么

把 Ch1 的 TCP 客户端—服务器 模型落到 Rust 标准库 std::net：

  • 服务端：TcpListener 监听 → accept 得到 TcpStream
  • 客户端：TcpStream::connect 建立连接
  • 并发：每连接一个 OS 线程（阻塞 I/O 的最小模型）

异步版见 stage07 Tokio。

二、TCP 服务器：TcpListener

一句话：bind 本地地址 → 进入 LISTEN → incoming() / accept() 拿到已连接的 TcpStream。

步骤 API / 做法
监听 TcpListener::bind("127.0.0.1:PORT")?
接受连接 listener.incoming() 迭代，或单次 accept()
得到 TcpStream（已 ESTABLISHED 的连接）
并发 每接受一个客户端 → thread::spawn(move \|\| …) 处理 
use std::io::{Read, Write};
use std::net::{TcpListener, TcpStream};
use std::thread;

fn handle_client(mut stream: TcpStream) -> std::io::Result<()> {
    let mut buf = [0u8; 1024];
    let n = stream.read(&mut buf)?;
    stream.write_all(&buf[..n])?;
    Ok(())
}

fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:8080")?;
    for stream in listener.incoming() {
        let stream = stream?;
        thread::spawn(move || {
            let _ = handle_client(stream);
        });
    }
    Ok(())
}

要点

  1. incoming() 等价于循环 accept()；每次成功返回一条新连接。
  2. 工作线程里必须 move 拿走 TcpStream 所有权（同 JoinHandle / spawn）。
  3. 本书 demo 为回显：读多少写回多少；生产还需优雅退出、连接上限、日志、join/线程池等。

仓库对应：3.1-simple-tcp-server-client-echo-server-demo.rs · 监听 127.0.0.1:38081

三、TCP 客户端：TcpStream

一句话：connect 完成三次握手 → 对 TcpStream impl Read + Write。

步骤 API
连接 TcpStream::connect("127.0.0.1:8080")?（域名也可，见 3.3）
写 write_all（保证写满缓冲区）
读 read（可能短读；流式协议需自己组帧）
缓冲 BufReader / BufWriter 减少 syscall，按行读更方便 
use std::io::{Read, Write};
use std::net::TcpStream;

fn main() -> std::io::Result<()> {
    let mut stream = TcpStream::connect("127.0.0.1:8080")?;
    stream.write_all(b"hello")?;
    let mut buf = [0u8; 1024];
    let n = stream.read(&mut buf)?;
    println!("{}", String::from_utf8_lossy(&buf[..n]));
    Ok(())
}

仓库对应：3.1-simple-tcp-server-client-echo-client-demo.rs

四、读超时：set_read_timeout

阻塞 read 在对端无响应时可能永远卡住。

use std::net::TcpStream;
use std::time::Duration;

let stream = TcpStream::connect("127.0.0.1:8080")?;
stream.set_read_timeout(Some(Duration::from_secs(5)))?;
// 超时后 read 返回 Err，kind 常为 TimedOut
API 作用
set_read_timeout 单次 read 最长阻塞时间
set_write_timeout 单次 write 最长阻塞时间

连接阶段超时：connect 本身无标准库超时参数，需非阻塞 connect + poll 或第三方 crate；书上以已连接流上的读超时为主。

五、对照：阻塞多线程 vs 异步

本章（std::net + thread::spawn） stage07 Tokio
I/O 阻塞；一线程等一条连接/读 非阻塞 + reactor；单线程可管大量连接
模型 简单直观 需 async/.await
适用 学习、连接数少 高并发网络服务

六、新手易错

  1. TCP 是字节流：一次 read 不一定等于一条「消息」；要换行、长度前缀或 HTTP 等分帧。
  2. 先起 server 再起 client；端口被占用时 bind 失败。
  3. write vs write_all：前者可能只写出部分字节。
  4. spawn 后不 join：demo 里 server 主线程卡在 incoming() 循环，子线程处理连接；生产要管线程生命周期。

3.2

simple-udp-server-client

书 §3.2 · 多播见 3.2.1-udp-multicasting.md · TCP 对照 3.1 · 贯通稿：notes/Ch03-…

一、UDP 与 TCP 的心智差异

一句话：UDP 无连接，不建立「会话」；每个报文（datagram）独立，带目标地址，保留报文边界。

TCP UDP
连接 listen / accept / connect 无；bind 即可收发包
语义 字节流（需自己分帧） 独立 datagram
可靠/有序 协议保证 不保证
典型 API read / write recv_from / send_to
每包地址 连接建立后隐含 每包显式 SocketAddr

二、UdpSocket 基本用法

服务端

use std::net::UdpSocket;

let socket = UdpSocket::bind("127.0.0.1:9000")?;
let mut buf = [0u8; 1500];
let (len, src) = socket.recv_from(&mut buf)?;
socket.send_to(&buf[..len], src)?;

客户端

客户端通常也 bind 本地地址；端口 0 表示由 OS 分配临时端口（ephemeral）：

let socket = UdpSocket::bind("127.0.0.1:0")?;
socket.send_to(b"hello", "127.0.0.1:9000")?;
let mut buf = [0u8; 1500];
let (len, src) = socket.recv_from(&mut buf)?;

API 精读

方法 返回 含义
recv_from(&mut buf) (usize, SocketAddr) 收到字节数 + 来源地址
send_to(buf, addr) usize 向指定地址发一个 datagram
bind — 绑定本地 IP:端口，开始收包

缓冲区大小常取 1500 左右（以太网 MTU 量级）；更大报文会被 IP 层分片，应用层仍按一次 recv_from 收一整 UDP 载荷（在未超 MTU 时）。

三、回显服务器模型

本书 demo：单线程循环 recv_from → send_to 回原地址（比 TCP 版简单，无需 thread::spawn 也能跑通；高负载时可同样多线程或 mio/Tokio）。

仓库对应：

文件 Bin
echo-server-demo.rs demo_3_2_udp_echo_server · 127.0.0.1:39090
echo-client-demo.rs demo_3_2_udp_echo_client

四、何时选 UDP

适合 UDP 适合 TCP
可丢包、可乱序（实时音视频、游戏状态） 必须可靠交付（HTTP、文件、RPC）
请求—响应短报文（DNS、DHCP） 长连接、流式传输
局域网广播/多播（见 3.2.1） 需要背压与流量控制

五、新手易错

  1. 用 read/write 思维写 UDP：必须用 recv_from/send_to（或 connect 后用 send/recv，本书先不展开）。
  2. 忘记 bind 客户端：未 bind 时部分平台行为不一致；127.0.0.1:0 最稳妥。
  3. 假设 send_to 一次必达：UDP 无重传；丢包要应用层处理。
  4. 报文大于 MTU：可能 IP 分片，增加丢包概率；大 payload 用 TCP 或应用层分片。

3.2

.1-udp-multicasting

书 §3.2.1 · 单播 UDP 见 3.2 · 地址类型见 3.3 · 贯通稿：notes/Ch03-…

一、什么是 UDP 多播

一句话：向 组播 IP 发一个 UDP 报文，同一组播组内所有已「加入」该组的 socket 都能收到——一对多，无需逐个 send_to 每个客户端。

单播（3.2） 多播（本节） 广播
目标 单个 SocketAddr 组播地址（一组接收者） 子网所有主机（如 255.255.255.255）
典型 API send_to(addr, …) send_to(239.x.x.x:port, …) + 接收端 join_multicast_v4 受限多、路由器常不转发
场景 客户端—服务器 服务发现、日志汇聚、局域网通知 老式发现协议（少用）

与 TCP 无关：多播建立在 UDP datagram 之上。

二、组播地址（IPv4）

IANA 为 IPv4 多播保留 224.0.0.0～239.255.255.255：

范围 用途
224.0.0.0/24 本地链路（路由不转发）
239.0.0.0/8 管理范围（私网组播，类似私网单播；本书 demo 用此段）

本书 demo：239.0.0.1:39191（仅局域网/本机学习；勿与生产组播冲突）。

IPv6 对应 Ipv6Addr 组播 + join_multicast_v6；本书以 IPv4 为主。

三、核心 API：join_multicast_v4

接收方必须显式加入组播组，内核才会把发往该组播地址的包交给你的 socket：

use std::net::{Ipv4Addr, SocketAddrV4, UdpSocket};

let bind = SocketAddrV4::new(Ipv4Addr::UNSPECIFIED, 39191); // 0.0.0.0:39191
let socket = UdpSocket::bind(bind)?;
socket.join_multicast_v4(
    &Ipv4Addr::new(239, 0, 0, 1),  // 组播组地址
    &Ipv4Addr::UNSPECIFIED,        // 从哪块网卡加入（0.0.0.0 = 由 OS 选）
)?;
参数 含义
multicast 要加入的组播 IP（如 239.0.0.1）
interface 本地接口地址；UNSPECIFIED 表示默认网卡

加入之后，对该 IP:端口 的 UDP 报文会进入 recv_from，与单播用法相同。

离开组播组（可选）：leave_multicast_v4。

四、接收端流程（recv demo）

use std::net::{Ipv4Addr, SocketAddrV4, UdpSocket};
use std::time::Duration;

const MULTICAST: Ipv4Addr = Ipv4Addr::new(239, 0, 0, 1);
const PORT: u16 = 39191;

let socket = UdpSocket::bind(SocketAddrV4::new(Ipv4Addr::UNSPECIFIED, PORT))?;
socket.join_multicast_v4(&MULTICAST, &Ipv4Addr::UNSPECIFIED)?;
socket.set_read_timeout(Some(Duration::from_secs(30)))?;

let mut buf = [0u8; 1500];
let (len, src) = socket.recv_from(&mut buf)?;
println!("from {src}: {}", String::from_utf8_lossy(&buf[..len]));

要点：

  1. bind 端口须与发送方 send_to 的端口一致（39191）。
  2. bind 到 0.0.0.0 表示在所有接口上监听该端口。
  3. 学习 demo 设 30s 读超时，避免无发送方时一直阻塞。

仓库对应：3.2.1-udp-multicasting-recv-demo.rs

五、发送端流程（send demo）

发送方不必 join_multicast_v4（除非也要收同组报文）；向组播地址 send_to 即可：

use std::net::{Ipv4Addr, SocketAddrV4, UdpSocket};

let socket = UdpSocket::bind("0.0.0.0:0")?;
let target = SocketAddrV4::new(Ipv4Addr::new(239, 0, 0, 1), 39191);
socket.send_to(b"hello multicast", target)?;

TTL（生存时间）：跨路由器转发组播时，可用 set_multicast_ttl_v4 限制跳数；本机/局域网 demo 通常默认即可。

仓库对应：3.2.1-udp-multicasting-send-demo.rs

七、典型应用场景

  • 局域网服务发现（mDNS 等用不同地址，思路类似）
  • 日志 / 指标汇聚（多生产者 → 多分析器）
  • 流媒体（常配合 RTP；本书只到 UDP 组播 API）

八、对照：3.2 单播回显 vs 3.2.1 多播

3.2 UDP echo 3.2.1 多播

发送 send_to(服务器地址) send_to(组播地址)

九、新手易错

  1. 只 bind 不 join：收不到组播包。
  2. 端口不一致：发送 239.0.0.1:39191，接收也必须 bind 39191。
  3. 把组播地址当普通单播 bind：应对 0.0.0.0:port bind，组播 IP 只出现在 join / send_to 目标。
  4. 期望跨公网组播：多数互联网路径不支持；限局域网或专用网络。
  5. Windows 上 demo 失败就怀疑代码：先确认 recv 终端已启动、防火墙、权限。

3.3

std-net-utilities

书 §3.3 · 地址用于 3.1 TCP / 3.2 UDP · 完整 DNS 见 3.4 · 贯通稿：notes/Ch03-…

一、为什么需要类型化的地址

bind / connect / send_to 都要 IP + 端口。std::net 用枚举区分 IPv4 / IPv6，避免字符串拼错、便于校验「是否回环、是否公网」等。

二、IpAddr 与 SocketAddr

类型 含义
IpAddr V4(Ipv4Addr) | V6(Ipv6Addr)
SocketAddr SocketAddrV4 | SocketAddrV6：IP + 端口

常用方法

方法 含义
is_loopback() 127.0.0.1 / ::1
is_global() 是否全球单播（非公网/组播等特殊用途）
is_ipv4() / is_ipv6() 协议族分支

解析字符串

use std::net::SocketAddr;

let addr: SocketAddr = "192.168.1.10:8080".parse()?;
let loopback: SocketAddr = "127.0.0.1:8080".parse()?;
println!("loopback? {}", loopback.ip().is_loopback());

use std::net::IpAddr;

let ip: IpAddr = "::1".parse()?;
println!("ipv6? {}", ip.is_ipv6());

仓库对应：3.3-std-net-utilities-demo.rs

三、DNS 与 ToSocketAddrs

稳定用法（推荐）

TcpStream::connect("example.com:80")? 接受任何实现 ToSocketAddrs 的类型：字面量、SocketAddr、(主机名, 端口) 等；标准库在底层解析 DNS（通常 A / AAAA）。

use std::net::TcpStream;

let _ = TcpStream::connect("example.com:443")?;
let _ = TcpStream::connect(("127.0.0.1", 8080))?;

书中 lookup_host

历史上 std::net::lookup_host 曾为 nightly API，底层类似 C 的 getaddrinfo。日常开发：

  • 连上去就行 → connect("host:port")
  • 要 MX / TXT / NS 或异步解析 → 3.4 hickory-dns / trust-dns

四、IPv4 专用类型（多播等）

类型 用途
Ipv4Addr 四个 u8；UNSPECIFIED = 0.0.0.0
SocketAddrV4 IPv4 + 端口；3.2.1 多播 绑定 0.0.0.0:PORT

五、对照：字面量 vs 解析 vs DNS

写法 何时用
"127.0.0.1:8080".parse() 配置里已知 IP
connect("domain:443") 生产客户端
第三方 DNS crate 自定义解析逻辑、非 A 记录

六、新手易错

  1. 忘记端口：SocketAddr 必须带 :port。
  2. IPv6 地址要方括号：如 [::1]:8080（connect 字符串形式）。
  3. 把 0.0.0.0 当目标地址：它是「本机所有网卡」绑定用，不是发给某台远程机器。
  4. DNS 每次 connect 都可能解析：高频场景可缓存 SocketAddr。

serde-serialization

书 §4.1 · 贯通稿：notes/Ch04-… · 传输层：Ch03 TCP/UDP · 自定义 Serde：4.1.1

一、本节在学什么

Ch3 用 TcpStream 传的是原始字节流；本节解决「字节 ↔ 应用层结构体」：

  • 序列化：Point3D 等结构 → JSON / 二进制 Vec<u8>
  • 反序列化：收到的字节 → 还原为 Rust 类型
  • Serde 是 Rust 生态里做这件事的事实标准；网络服务里 JSON（人机可读）和二进制（体积小）最常见

下一节 4.1.1 讲字段名不一致、手写 Visitor 等进阶；4.2 / 4.3 讲不用 Serde 的协议解析。

二、Serde 是什么

Serde = Serialize / Deserialize：一套 trait + 格式适配 crate，同一套 #[derive] 可换输出格式。

格式 常见 crate 网络场景
JSON serde_json REST API、调试、人机可读消息
MessagePack / Bincode rmp-serde、bincode 服务间 RPC、游戏同步
YAML / TOML / CSV serde_yaml、toml、csv 配置、批处理（较少直接上 wire）

本 stage 的 Cargo.toml 已包含 serde（derive）与 serde_json。

三、基本用法：#[derive(Serialize, Deserialize)]

一句话：在结构体上派生两个 trait，即可 to_vec / from_slice 往返。

# Cargo.toml（节选）
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize, PartialEq)]
struct Point3D {
    x: f64,
    y: f64,
    z: f64,
}

fn main() -> serde_json::Result<()> {
    let p = Point3D { x: 1.0, y: 2.0, z: 2.0 };
    let json = serde_json::to_vec(&p)?;              // 序列化 → Vec<u8>
    let back: Point3D = serde_json::from_slice(&json)?; // 反序列化
    assert_eq!(p, back);
    Ok(())
}

常用 API

方向 函数 输出 / 输入
序列化 serde_json::to_vec Vec<u8>（直接 write_all）
序列化 serde_json::to_string String（打印、日志）
反序列化 serde_json::from_slice &[u8]
反序列化 serde_json::from_str &str

过程宏自动生成实现，无需手写 impl Serialize for Point3D。

四、配合 TCP：书中典型流程

与 3.1 TcpStream 组合时的消息流：

客户端                          服务器
  读控制台输入 (x,y,z)
  构建 Point3D
  serde_json::to_vec → write_all

Serde 只负责「这一段字节 ↔ 结构体」；如何把多条消息从字节流里切出来要在 I/O 层设计（见下一节）。

五、TCP 粘包与分帧

TcpStream 是字节流，一次 read 不一定对应一条完整 JSON。

分帧方式 做法 适用
长度前缀 先读 4 字节 len（常大端 u32），再读 len 字节 body 二进制友好、通用 RPC
换行分隔 read_line / \n 结尾，每行一条 JSON 简单 CLI、日志流
HTTP 式 Content-Length 头 + body 应用层协议（见 stage06） 
use serde::Serialize;
use std::io::Write;
use std::net::TcpStream;

// 示例：长度前缀（u32 大端）+ JSON body
fn send_json(stream: &mut TcpStream, msg: &impl Serialize) -> std::io::Result<()> {
    let body = serde_json::to_vec(msg)?;
    let len = (body.len() as u32).to_be_bytes();
    stream.write_all(&len)?;
    stream.write_all(&body)?;
    Ok(())
}

完整 nom 解析长度前缀见 4.3 的 demo_4_3_binary_length_prefix。

六、对照：Serde vs 手写解析

本节（Serde + JSON） 4.2 nom 文本 4.3 nom 二进制

跨语言 JSON 易对接 文本协议通用 需文档约定布局

三者常组合：固定头用 nom，负载用 Serde。

七、新手易错

  1. 只序列化不设计分帧：from_slice 在粘包/半包时会失败或解析错对象；必须先定「一条消息」边界。
  2. write vs write_all：JSON 体要用 write_all 保证写满（同 Ch3）。
  3. 浮点与 JSON：f64 序列化可能有精度展示差异；金融场景考虑 Decimal 或整数分。
  4. 字段名与协议不一致：优先 #[serde(rename = "...")]（见 4.1.1），再考虑手写 trait。
  5. Result 传播：serde_json::Result 与 std::io::Result 不同，可用 ? 或 map_err 统一错误类型。

4.1

.1-custom-serde

书 §4.1.1 · 贯通稿：notes/Ch04-… · 上一节：4.1 Serde 基础 · 下一节：4.2 文本解析

一、本节在学什么

#[derive(Serialize, Deserialize)] 覆盖绝大多数结构体；以下情况需要自定义：

  • wire 字段名与 Rust 字段名不一致（也可用属性宏解决）
  • 枚举的 JSON 形态（externally / internally / adjacently tagged）
  • 与遗留二进制布局逐字段对齐
  • 跳过字段、默认值、扁平化嵌套等特殊规则

本节路径：先属性宏 → 再手写 trait → 用 serde_test 验证。

二、首选：#[serde(...)] 属性

多数「改名 / 忽略 / 默认值」不必手写 trait。

属性 作用
rename = "wire_name" JSON 键与 Rust 字段不同
rename_all = "camelCase" 整结构体字段统一风格
skip_serializing / skip_deserializing 某字段不参与某一方向
default 缺失字段用 Default::default()
tag / content 枚举序列化形态（adjacent 等）

示例：rename（本仓库 demo）

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Point {
    #[serde(rename = "custom_x")]
    x: f64,
    #[serde(rename = "custom_y")]
    y: f64,
}

fn main() -> serde_json::Result<()> {
    let p = Point { x: 3.0, y: 4.0 };
    let json = serde_json::to_string(&p)?;
    // 输出形如 {"custom_x":3.0,"custom_y":4.0}
    let back: Point = serde_json::from_str(&json)?;
    Ok(())
}

仓库对应：4.1.1-custom-serde-rename-demo.rs

三、手写 Serialize

宏无法表达时，实现 serde::Serialize，调用序列化器的结构化 API：

use serde::ser::{Serialize, SerializeStruct, Serializer};

struct MyType {
    x: f64,
    y: f64,
}

impl Serialize for MyType {
    fn serialize<S: Serializer>(&self, serializer: S) -> Result<S::Ok, S::Error> {
        let mut st = serializer.serialize_struct("MyType", 2)?;
        st.serialize_field("custom_x", &self.x)?;
        st.serialize_field("custom_y", &self.y)?;
        st.end()
    }
}

要点：

  1. serialize_struct(name, len) 的 len 是字段个数，错填可能导致格式错误。
  2. 也可用 serialize_tuple、serialize_map 等，取决于目标格式。
  3. 与 #[serde(rename)] 等价场景优先用属性，减少维护成本。

四、手写 Deserialize 与 Visitor

反序列化更复杂：输入可能是 map、seq、字符串、数字 等，需实现 Visitor，在回调里逐步构造目标类型。

JSON/二进制输入 → Deserializer → Visitor::visit_* → 你的 Struct

常见回调：

方法 何时调用
visit_map JSON 对象 { "k": v }
visit_seq JSON 数组 [ ... ]
visit_str 字符串字段
visit_f64 / visit_i64 数值字段 
// 概念骨架（完整实现需处理 map 的 key/value 状态机）
use serde::de::{self, Deserialize, Deserializer, Visitor};

impl<'de> Deserialize<'de> for MyType {
    fn deserialize<D: Deserializer<'de>>(deserializer: D) -> Result<Self, D::Error> {
        deserializer.deserialize_struct("MyType", &["custom_x", "custom_y"], MyVisitor)
    }
}

struct MyVisitor;

impl<'de> Visitor<'de> for MyVisitor {
    type Value = MyType;
    fn expecting(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "struct MyType")
    }
    // visit_map / visit_seq ... 组装 MyType
}

书中通过 visit_map 读键值对、visit_str 读字符串，是理解 Serde 插件式格式的关键。

五、单元测试：serde_test

parsing-textual

书 §4.2 · 贯通稿：notes/Ch04-… · Serde 消息体：4.1 · 二进制解析：4.3 · PEG 深化：stage09

一、本节在学什么

并非所有协议都适合「整包 serde_json::from_slice」：

  • HTTP 请求行、SMTP 命令、自定义文本命令 → 用 切分 + 模式匹配 更自然
  • PEG（Parsing Expression Grammar） 无歧义、可组合；Rust 里 nom 是常用的解析器组合子库

本节目标：能读懂并写出最小文本解析器（书中：HTTP 请求行），并知道如何调试失败输入。

二、PEG 与 nom 模型

一句话：把大语法拆成小解析器函数，用组合子顺序拼接或分支选择。

输入 &str / &[u8]
  → 子解析器 A：消费前缀，返回 (剩余, 值)
  → 子解析器 B：在剩余上继续
  → …
  → Ok((剩余, 组装好的结果)) 或 Err(失败位置)

本仓库使用 nom 7（函数式组合子为主；书上部分示例为 macro 风格，概念相通）。

Cargo.toml：nom = "7"。

三、常用组合子

宏 / 函数 作用 示例场景
tag 匹配固定字面量 tag("GET ")、tag(" HTTP/1.1")
take_until1 读到分隔符前（至少 1 字节） 方法名读到空格、路径读到空格
tuple 顺序执行多个解析器 方法 + 空格 + 路径 + …
alt 多分支选一 GET | POST
many0 / many1 重复 0 次 / 至少 1 次 重复 header 行

返回类型 IResult<I, O>：

  • Ok((remaining_input, output)) — 成功
  • Err(...) — 失败，含失败偏移与剩余输入

四、HTTP 请求行（书中示例）

解析目标：

GET /api/users HTTP/1.1

得到：方法、URL 路径、HTTP 版本；行尾常为 \r\n。

仓库实现

use nom::{
    bytes::complete::{tag, take_until1},
    sequence::tuple,
    IResult,
};

fn parse_request_line(input: &str) -> IResult<&str, (&str, &str, &str)> {
    let (input, (method, _, path, _, version)) = tuple((
        take_until1(" "),
        tag(" "),
        take_until1(" "),
        tag(" "),
        take_until1("\r\n"),
    ))(input)?;
    Ok((input, (method, path, version)))
}

// 用法
let line = "GET /api/users HTTP/1.1\r\n";
let (rest, (method, path, version)) = parse_request_line(line).unwrap();
// method=GET  path=/api/users  version=HTTP/1.1  rest=""

4.3

parsing-binary

书 §4.3 · 贯通稿：notes/Ch04-… · TCP 分帧背景：4.1 · 文本解析：4.2 · 下一节：4.4 总结

一、本节在学什么

底层与自定义协议常是定长字段或按位布局的二进制，不适合整包 JSON：

  • IP/TCP/UDP 首部、自定义帧头
  • 长度前缀 + payload（与 Ch3 TCP 粘包方案一致）
  • 位域（如 IPv6 首部：版本 4 bit + 流量类别 8 bit + …）

本节用 nom 解析 &[u8]（be_u32、take 等）；书中 IPv6 示例用 bits! / take_bits! 切比特流。

二、长度前缀分帧（TCP 常见形态）

4.1 提到：先传 4 字节长度，再传 body。发送与解析应对称。

发送侧（概念）

let payload = b"hello binary frame";
let mut buf = Vec::new();
buf.extend_from_slice(&(payload.len() as u32).to_be_bytes()); // 大端 u32
buf.extend_from_slice(payload);
// buf → write_all 到 TcpStream

解析侧（本仓库 demo）

use nom::{bytes::complete::take, number::complete::be_u32, IResult};

fn parse_frame(input: &[u8]) -> IResult<&[u8], &[u8]> {
    let (input, len) = be_u32(input)?;  // 读 4 字节大端长度
    take(len)(input)                     // 再读 len 字节 payload
}

match parse_frame(&buf) {
    Ok((rest, body)) => {
        // body 即 payload；rest 为帧后剩余字节（粘包时下一条帧）
    }
    Err(e) => { /* 数据不足或长度非法 */ }
}

五、对照：二进制解析 vs Serde

方式 适用 本 stage 关联
Serde + bincode / postcard 双方都是 Rust（或共享 schema），结构体直接映射 4.1 换格式 crate

[ u32 len ][ JSON body ]     ← 头 nom，体 Serde（常见 RPC）
[ IPv6 fixed header ][ ... ] ← 头 bits!，体可能再分层

六、流式读取注意

TCP 上 read 可能只拿到半帧：

情况 nom complete 行为 做法
缓冲区少于 4+len 字节 Err（数据不足） 累积到 Vec，或改用 streaming 解析器
一次 read 多帧 第一帧 Ok((rest, body))，rest 继续解析 循环 parse_frame

生产代码常在连接层维护 read buffer，而不是假设一次 read 刚好一帧。

七、新手易错

  1. 字节序不一致：发送 to_be_bytes 却用 le_u32 解析，长度会错到离谱，可能 OOM 或 panic。
  2. len 不信任对端：应对 len 设上限，防止恶意超大分配。
  3. take(len) 与 usize：len 来自 u32，在 32 位平台注意转换；非法 len 要返回协议错误。
  4. 把 JSON 当二进制帧：JSON 是文本 UTF-8；长度前缀里可以是 JSON 字节，但解析 JSON 内容仍用 serde_json（4.1）。
  5. 混淆 complete 与半包：demo 在内存 Vec 上跑；真实 socket 要处理 Incomplete。

5.1

introduction-to-rpc

书 §5.1 · 传输层基础：Ch03 TCP/UDP · 序列化：Ch04 Serde · 贯通稿：notes/Ch05-… · 线程模型：atomic §1.1

一、本节在学什么

Ch03 用套接字传原始字节；本节把视角升到应用层的第一类协议——RPC（Remote Procedure Call）：

  • 调用方像调本地函数一样，通过网络调用远端过程
  • 不再手写「第 3 字节是命令号」，而是按接口定义（IDL）生成客户端/服务端代码
  • 书中重点 gRPC = HTTP/2 + Protocol Buffers + .proto 代码生成

本章 demo 用 JSON over TCP 演示 RPC 的 stub → 网络 → skeleton 形状，避免引入 protoc / tonic 完整工具链；完整 gRPC 按原书在独立项目练习。

二、RPC 是什么

一句话：客户端 stub 序列化参数、发请求；服务端 skeleton 收请求、执行业务、返回结果；调用方只看见「函数返回值」。

角色 职责
调用方（客户端 stub） 序列化参数 → 发请求 → 收响应 → 反序列化
服务方（服务端 skeleton） 收请求 → 调用真实业务逻辑 → 序列化结果并返回
价值 微服务拆分、语言无关接口（配合 IDL）、隐藏网络细节

与「自己定义 TCP 字节协议」的区别：

手写 TCP 协议 RPC / gRPC
接口 文档 + 约定偏移量 IDL（.proto） 有 schema
代码 手写编解码 生成 client stub / server trait
演进 字段变更易踩坑 protobuf 字段号 + 向后兼容规则
传输 任意 gRPC 默认 HTTP/2 on TCP

三、gRPC 与 Protocol Buffers

gRPC 是 Google 推出的 RPC 框架，本书重点技术栈：

层次 技术
传输 默认 HTTP/2（跑在 TCP 上）
能力 一元调用、服务端流 / 客户端流 / 双向流
IDL Protocol Buffers（.proto）
载荷 protobuf 二进制编码（比 JSON 更紧凑、有 schema） 
// 概念示例：打车应用

  double latitude = 1;
  double longitude = 2;
  string cab_id = 3;
}

  rpc GetNearbyCabs(NearbyRequest) returns (NearbyResponse);

.proto  →  build.rs + protoc  →  生成的 Rust 模块
                                    ↓
                          server impl / client stub
                                    ↓
                          HTTP/2 上 gRPC 帧（TCP）

与现代生态对照（书外补充）

书中 / 较老栈 当前常见栈
protoc-rust-grpc tonic + prost（Rust gRPC 主流）
手写 HTTP/2 仍由库处理；你主要写 .proto 与业务 impl

学习本节重在 IDL → 代码生成 → 客户端/服务端分工；具体 crate 名可随项目选型替换。

四、书中 Rust 实现流程（protoc-rust-grpc）

  1. 编写 .proto：定义 message 类型 + service 与 rpc 方法。
  2. 构建时生成代码：build.rs 调用 protoc-rust-grpc（或同类工具）+ protoc，在 cargo build 时生成 Rust 模块。
  3. 实现服务端：为生成的 trait 编写具体逻辑（如记录位置、查询附近车辆）。
  4. 实现客户端：调用生成的 stub 发起 RPC。

你写的业务代码只关心「实现 trait / 调 stub」，帧格式、HTTP/2 多路复用由框架处理。

fn handle(mut stream: TcpStream) -> std::io::Result<()> {
    let mut buf = [0u8; 1024];
    let n = stream.read(&mut buf)?;
    let req: RpcRequest = serde_json::from_slice(&buf[..n])?;
    let resp = if req.method == "add" {
        RpcResponse { result: req.a + req.b }
    } else {
        RpcResponse { result: -1 }
    };
    stream.write_all(&serde_json::to_vec(&resp)?)?;

}

introduction-to-smtp

书 §5.2 · 传输层：Ch03 TCP · 贯通稿：notes/Ch05-… · TLS 发信：stage08

一、本节在学什么

SMTP（Simple Mail Transfer Protocol） 是互联网发信的标准文本协议，跑在 TCP 上。本节要点：

  • 理解 SMTP 命令/响应形态（HELO、MAIL FROM、RCPT TO、DATA 等）
  • 用 Rust 生态 lettre 组装 MIME 邮件，配置 TLS 与凭据后 send
  • 不必手写 SMTP 状态机；生产场景还需 SPF/DKIM、限流与反垃圾

本章 demo 只构建 Message 对象，不真实连接 SMTP（避免硬编码密码、依赖外网）。

二、SMTP 协议要点

一句话：客户端与邮件服务器用一行行文本命令交互，在 DATA 之后提交邮件正文（含 MIME 头与 body）。

项目 说明
用途 互联网投递 / 转发邮件（本章侧重发）
传输 通常 TCP
常见端口 25（MTA 间转发）、587（客户端提交 + STARTTLS）、465（SMTPS，TLS 从头建立）
形态 文本命令 / 三位数响应码（250、354 等）
收信 用户收信常用 POP3 / IMAP，不在本章 SMTP 发信主线内

典型会话（概念）：

客户端 → 服务器: HELO client.example.com

introduction-to-ftp-and-tftp

书 §5.3 · TCP/UDP 基础：Ch03 · 贯通稿：notes/Ch05-…

一、本节在学什么

文件传输有两类经典应用协议：

  • FTP：TCP、双连接（控制 + 数据）、有登录认证，年代久但有助于理解「命令通道 vs 数据通道」
  • TFTP：UDP、极简、无认证，用于嵌入式、PXE 网络启动

书中分别用 rust-ftp（客户端）与 tftp_server（本机 UDP 服务）演示；本章仓库 demo 为协议步骤速查（无 live 服务器），完整联调按书在独立项目练习。

二、FTP（文件传输协议）

一句话：控制连接上发文本命令，数据连接上传/下载文件；登录后执行 LIST、RETR、STOR 等。

项目 说明
模型 基于文本的命令 / 响应
控制连接 常 TCP 21，全程保持
数据连接 传文件与目录列表；主动（PORT） 或 被动（PASV） 模式
能力 登录、列目录、上传/下载、改名、断点续传（扩展）
Rust（书中） rust-ftp 客户端

双连接示意

客户端                          FTP 服务器
   │──── TCP 21 控制连接 ────────────│  USER / PASS / PWD / CWD ...
   │                                 │
   │──── TCP 数据连接（另开端口）────│  LIST / RETR / STOR 的载荷

书中客户端流程（rust-ftp）

连接 ftp.example.com:21
→ 登录（用户名 / 密码）
→ 打印当前目录（PWD / LIST）
→ put：用 std::io::Cursor 作内存缓冲区上传文件

// 概念流程（crate API 以文档为准）

主动 vs 被动

模式 谁监听数据端口 NAT/防火墙
主动 PORT 服务端连回客户端告知的 IP:端口 客户端后侧 NAT 常失败
被动 PASV 服务端告知 IP:端口，客户端去连 现代环境更常用

特点：协议年代久，防火墙/NAT 下 PASV 仍可能踩坑；新项目更常用 SFTP、S3、HTTPS 传文件，但读 FTP 有助于理解「控制通道 vs 数据通道」分离设计。

三、TFTP（简单文件传输协议）

一句话：在 UDP 上用固定块大小读写文件，无登录，适合引导与固件场景。

对比项 FTP TFTP
传输 TCP UDP
连接 控制 + 数据双 TCP 无连接；请求 / 数据块 / ACK 报文
认证 用户名 / 密码 无
复杂度 命令集丰富 极简（RRQ/WRQ、DATA、ACK、ERROR）
典型场景 传统文件交换 嵌入式、PXE/BOOTP 启动、设备固件
Rust（书中） rust-ftp tftp_server 
TFTP 客户端  --UDP-->  tftp_server（Rust）
              读请求 RRQ / 数据块 DATA / 确认 ACK

书中用 tftp_server 在本机绑定 UDP 端口，向 TFTP 客户端提供文件下载。

与 Ch3：直接对应 UdpSocket 上的无连接、有报文边界模型；比 FTP 更接近「最小文件传输」。

introducing-hyper

一、本节在学什么

把 Ch3 的 TCP 字节流 之上，加上 HTTP 语义（方法、头、状态码、Body），并认识 Hyper —— Rust 生态里偏底层的 HTTP 实现，常与 Tokio 组合写高并发服务器。

层次 本章关注点
应用 HTTP/1.1（及 H2 概念）
传输 TCP（常见）或 TLS（HTTPS，见 stage08）
Socket Ch3 TcpListener / TcpStream

二、HTTP 在栈中的位置（复习）

应用：HTTP 语义（方法、头、状态码、Body）
  ↓
传输：TCP（常见）或 TLS（HTTPS）
  ↓
… Ch1 分层、Ch3 Socket …
版本 特点

三、最小 HTTP 响应：理解 Hyper 之下是什么

在引入 Hyper 之前，先用 Ch3 的 std::net 手写一条 HTTP/1.0 响应，看清报文形态：

HTTP/1.0 200 OK\r\n
Content-Type: text/plain\r\n
Content-Length: 42\r\n
\r\n
Hello from raw TCP HTTP demo\n
部分 含义
状态行 HTTP/1.0 200 OK
头字段 Content-Type、Content-Length 等，以 \r\n 结尾
空行 \r\n 分隔头与体
Body 实际载荷字节

仓库 demo 在 127.0.0.1:18080 监听，读入请求（demo 不解析）、写回固定响应：

// 概念（见 6.1-introducing-hyper-raw-tcp-demo.rs）

    body.len(),

要点：生产环境不要手写拼报文 —— 交给 Hyper（或 Rocket/reqwest 等更高层库）处理分帧、keep-alive、H2 等细节。

四、Hyper 简介

Hyper 是 Rust 生态里成熟、底层的 HTTP 实现/库（偏框架基石，而非「自带路由的全家桶」）。

特点 说明
角色 解析/生成 HTTP、驱动连接；常与 Tower 中间件组合
并发模型 服务端基于 Tokio + async/await
适用 高并发、需精细控制连接与协议的场景（网关、代理、自建服务）

现代对照：书内可能仍出现 tokio-core、net2、futures 0.1 等旧名；新项目用 **tokio 1.x + hyper 1.x**，心智模型不变（事件循环、非阻塞 I/O、Service/Handler`）。

客户端请求 → Hyper 解析 HTTP → 你的 service 返回 Response

五、单线程 Hyper 服务器

一句话：一个 Tokio 运行时线程处理 accept + 读写的 poll。

说明
优点 模型简单，便于理解 Service 回调链与异步 I/O
缺点 单核 CPU 打满后吞吐受限，无法吃满多核

这与 Ch3「每连接一线程 + 阻塞 read」不同：Hyper 侧是 单线程多连接 + 非阻塞 I/O（详见 stage07）。

六、多核扩展：SO_REUSEPORT 与多监听

书中扩展路径（概念仍适用）：

  1. 多个 Tokio 运行时 / 多线程 runtime：在多个线程上跑异步任务。
  2. SO_REUSEPORT（书中用 net2 等设置）：多个线程/进程在同一端口 bind，内核把新连接分摊到不同监听套接字 → 连接级负载均衡。
  3. 结果：书中示例吞吐可近翻倍（视硬件与负载而定）。
         ┌─ thread 1 ─ Hyper + Tokio
:8080 ───┼─ thread 2 ─ Hyper + Tokio   （REUSEPORT）
         └─ thread N ─ …
模型 Ch3 阻塞多线程 Hyper + Tokio（单 reactor） Hyper + REUSEPORT
I/O 阻塞 非阻塞 poll 非阻塞 + 多监听
吃多核 连接数 ≈ 线程数 单核为主 多 reactor 分摊连接
复杂度 低 中 较高

延伸：仓库 02-async_tokio/、stage07 继续深化 Tokio 与并发 HTTP。

七、Hyper vs 其它「写服务」选型

Crate 层级 典型场景
Hyper 底层 HTTP + 异步 I/O 网关、精细协议控制
Rocket 全栈 Web（§6.2） 路由宏、REST、模板
axum / actix-web 生产常用框架 与 Hyper/Tokio 生态衔接

不做网关时：先掌握 §6.3 reqwest 调 API，Hyper 可与 stage07 一起后移。

八、新手易错

  1. HTTP 仍是字节流：在 TCP 上可能一次 read 只收到半条头；必须按 \r\n\r\n 与 Content-Length/chunked 组帧（Hyper 替你做了）。
  2. 混淆 HTTP 版本与 TLS：HTTPS = HTTP over TLS，不是另一个应用协议名；TLS 见 stage08。
  3. 单 reactor 打满 CPU ≠ 程序「慢」：可能是单核瓶颈，需多线程 runtime 或 REUSEPORT。
  4. 书内旧 crate 名：对照官方 hyper + tokio 1.x 示例阅读，勿照抄 tokio-core API。

三、同步客户端（阻塞）

适合 CLI、一次性脚本、测试；阻塞当前线程直到响应返回。

use reqwest::blocking::Client;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = Client::new();
    let resp = client.get("https://httpbin.org/get").send()?;
    println!("status: {}", resp.status());
    let body = resp.text()?;
    Ok(())
}
步骤 API
建客户端 Client::new()（可复用，连接池在内部）
发请求 .get(url).send()?
读体 .text()? / .bytes()?
状态码 resp.status()

仓库 demo 打印状态码与 body 前 200 字符；需可访问外网。

四、JSON + Serde（与 Ch04 一致）

POST 序列化 + 响应反序列化 用同一套 Serialize / Deserialize：

use serde::{Deserialize, Serialize};

#[derive(Serialize)]
struct Payload { name: String }

#[derive(Deserialize)]
struct ApiResult { ok: bool }

let client = reqwest::blocking::Client::new();
let res: ApiResult = client
    .post("https://api.example.com/items")
    .json(&Payload { name: "a".into() })
    .send()?
    .json()?;
链式调用 作用
.json(&payload) 序列化 body，设 Content-Type: application/json
.send()? 发出请求
.json()? 将响应体反序列化为 ApiResult

无需手写 header 拼接与 body 字符串 —— 与 Ch04 边界一致。

五、异步客户端（Tokio）

书中从 tokio_core + Future 链演进；现代写法：

#[tokio::main]
async fn main() -> Result<(), reqwest::Error> {
    let body = reqwest::get("https://httpbin.org/get")
        .await?
        .text()
        .await?;
    Ok(())
}
阻塞 blocking 异步 async
运行时 无需 Tokio（blocking feature 自带） 需 #[tokio::main] 等
并发多 URL 多线程或顺序阻塞 join! / try_join! 单线程并发 I/O
学习顺序 本章 demo 先用这个 与 stage07 一起练

仓库交叉

  • 根 workspace / async_tokio：ch01_reqwest_join 等 — 并发发多个 HTTP 请求，可与本节 API 对照。

7.1

looking-into-the-future

书 §7.1 · 阻塞对照：Ch03 · 贯通稿：notes/Ch07-… · 主线笔记：async_tokio/

一、本节在学什么

把 Ch3 的阻塞 I/O（线程在 read/accept 上卡住）换成 Future + 事件循环：

  • Future：尚未完成的计算；惰性，不会自己跑
  • Executor：在 reactor 里反复 poll，直到 Poll::Ready
  • async/await：编译器把 async fn 展开为状态机，现代写法替代手写组合子

目标：理解「为什么 read().await 不阻塞线程池里其它任务」。

二、Future 与 Poll

一句话：Future 是占位符；poll 返回 Ready(v) 或 Pending（稍后再试）。

书中（较旧 futures） 现代 std::task::Poll 含义
Async::Ready(v) Poll::Ready(v) 完成，得到 v
Async::NotReady Poll::Pending I/O 未就绪，让出线程
错误 Output = Result<…> 或 Ready(Err) 失败路径 
// async fn 编译后就是实现 Future 的状态机
async fn fetch() -> String {
    // ...
    todo!()
}

三种执行方式（书中）

方式 行为 适用
当前线程阻塞执行 卡住线程直到完成 测试、block_on 桥接
线程池（CPU pool） offload 计算 CPU 密集，非 I/O 主路径
Reactor / 事件循环 Pending 时调度其它 task 网络服务主流

Tokio = Reactor（mio）+ task 调度 + 可选 spawn_blocking。

底层栈：

tokio（运行时 + tokio::net）
  → mio（Poll / epoll，Ch3 已介绍）
  → 非阻塞 fd + 事件循环

三、组合子与 async/await

多层 and_then 易成回调地狱；现代以 线性 async/await 为主，宏仍用于并发：

工具 作用
.await 顺序 上一步完成再执行下一步
map / then 变换结果（组合子或 async 块内处理）
join! 多个 future 全部完成（并发等待）
select! 多路竞争，谁先完成用谁
timeout 超时取消或分支 
use tokio::time::{sleep, Duration};

async fn step1() -> u32 {
    sleep(Duration::from_millis(50)).await;
    1
}

async fn step2(v: u32) -> u32 {
    sleep(Duration::from_millis(50)).await;
    v + 2
}

// 现代等价于 and_then 链
async fn work() -> u32 {
    let a = step1().await;
    step2(a).await
}

join! 让两个 sleep 并行计时（总耗时 ≈ 最慢那个，而非相加）：

tokio::join!(task("A", 1), task("B", 2));
// A 1s + B 2s 并行 → 约 2s，不是 3s

仓库对应：7.1-looking-into-the-future-join-demo.rs

四、对照：阻塞 vs 异步

Ch3 std::net + thread::spawn 本章 Future + Tokio
等待 I/O 线程卡住 task Pending，线程干别的
并发模型 每连接一线程 单/少线程管大量连接
API read / accept 阻塞 read().await / accept().await
心智负担 低 需理解 async、Send、生命周期

五、新手易错

  1. Future 惰性：创建了不 .await / 不 spawn，里面代码可能根本不跑。
  2. .await 会 yield：持 std::sync::Mutex 锁跨越 .await 可能死锁；见 7.1.1。
  3. join! vs 顺序 .await：前者并发，后者串行；别混用概念。
  4. 阻塞 syscall 在 async 里：会卡住整个 worker 线程；用 tokio::task::spawn_blocking 或专用 crate。

7.1

.1-streams-and-sinks

书 §7.1.1 · 贯通稿：notes/Ch07-… · 阻塞线程对照：atomic §1.2 scoped threads

一、本节在学什么

Future 处理单次结果；网络 I/O 常是连续多帧。本节引入：

  • Stream：异步版 Iterator（.next().await）
  • Sink：异步版「写入端」，消化一系列项
  • 异步同步原语：tokio::sync::mpsc 等，替代阻塞版 std::sync

二、Stream：异步 Iterator

一句话：一系列异步产生的项；None 表示流结束。

Iterator Stream
next() → Option<Item> poll_next / .next().await → Option<Item>
同步拉取 未就绪时 Pending
for x in iter while let Some(x) = stream.next().await

用途：TCP 连续读帧、WebSocket 消息、定时器 tick、从 channel 消费消息。

// 概念：从 Stream 读帧
while let Some(frame) = stream.next().await {
    process(frame);
}

套接字侧常用 AsyncRead + AsyncWrite（tokio::io）或 Framed<IO, Codec>（tokio_util::codec）把字节流拆成帧级 Stream。

三、Sink：异步写入端

一句话：异步接收项并发送出去（socket、channel、协议编码器）。

Stream  ←── 读路径（入站数据）
Sink    ──→  写路径（出站数据）
场景 典型类型
task 间传消息 mpsc::Sender（send().await）
编码后写 socket Framed 的 Sink 侧
背压 bounded channel 容量、poll_ready

与 Ch4：Codec 解码后 often 得到 Stream<Item = Frame>；编码走 Sink。

四、异步同步原语

标准库 std::sync::Mutex、std::sync::mpsc 在 async 里 .lock().await 会阻塞 worker 线程（或死锁），需 async 感知类型：

原语 说明
oneshot 单次完成通知
mpsc（tokio） 多生产者单消费者，task 间 message passing
tokio::sync::Mutex 持锁期间让出线程（.lock().await）
watch / broadcast 状态广播、多订阅者

原则：在 .await 点之间少持锁；优先 message passing 划分 task 边界。

use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel(4);
    for i in 0..3 {
        tx.send(format!("frame-{i}")).await.unwrap();
    }
    drop(tx); // 关闭发送端，rx 才能结束
    while let Some(item) = rx.recv().await {
        println!("sink got: {item}");
    }
}

仓库 demo 用 mpsc::recv 模拟 Stream 消费：7.1.1-streams-and-sinks-mpsc-demo.rs

五、对照：std::sync::mpsc vs tokio::sync::mpsc

std::sync::mpsc tokio::sync::mpsc
send / recv 阻塞 .await 异步
使用场景 OS 线程间 async task 间
在 async fn 里 阻塞 worker 正确让出

书中 BiLock：两 future 间仲裁共享状态；现代多直接用 tokio::sync::Mutex + 短临界区。

六、新手易错

  1. 忘记 drop(tx)：多个 producer 时，最后一个 sender drop 后 receiver 才收到 None 结束循环。
  2. 无界 channel 掩盖背压：生产远快于消费会 OOM；网络协议应配合 bounded channel 或 flow control。
  3. std::sync::Mutex 跨 .await：易死锁；换 tokio::sync::Mutex 或把锁内逻辑改成 message passing。
  4. Stream 与字节流混淆：TCP 是字节流，Stream 的「项」是你协议定义的帧，需 Codec 分帧（见 7.2.2）。

一、本节在学什么

把 Ch3 的多线程阻塞 echo 换成 Tokio 异步 echo：

  • #[tokio::main]：启动运行时（Reactor + 线程池）
  • tokio::net::TcpListener / TcpStream：与 std::net 同名，API 加 .await
  • tokio::spawn：每连接一个 task（不是 OS 线程）

理解 accept().await 不阻塞其它连接 是本章核心。

二、Tokio 网络栈架构

一句话：mio 注册 fd → poll 就绪 → wake task → 再 poll Future。

层（书中 tokio-proto 概念） 职责 现代近似
Codec 字节流 ↔ 帧 tokio_util::codec::Framed、bytes::BytesMut
Protocol 分帧 + 状态机、多路复用 自定义 state machine、hyper
Service 业务：请求 → 异步响应 async fn handler(req) -> Response 
Socket 字节
   ↓ Codec（分帧）
   ↓ Protocol（状态机、多路复用）
   ↓ Service（业务逻辑）
   ↓ 响应编码回去

书中 tokio-core Reactor → 现为 tokio::runtime::Runtime。

三、最小异步 echo 服务器

与 Ch3 结构一一对应：bind → 循环 accept → spawn 处理。

use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::TcpListener;

const ADDR: &str = "127.0.0.1:37082";

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind(ADDR).await?;
    loop {
        let (mut socket, addr) = listener.accept().await?;
        tokio::spawn(async move {
            let mut buf = [0u8; 1024];
            match socket.read(&mut buf).await {
                Ok(0) => return,
                Ok(n) => {
                    let _ = socket.write_all(&buf[..n]).await;
                    println!("echoed {n} bytes for {addr}");
                }
                Err(e) => eprintln!("read error: {e}"),
            }
        });
    }
}

监听 TcpListener::bind bind(...).await
接受 incoming() / accept() accept().await
并发 thread::spawn tokio::spawn
读写 Read / Write AsyncReadExt / AsyncWriteExt

7.2

.1-socket-multiplexing

书 §7.2.1 · Collatz 服务器示例 · 贯通稿：notes/Ch07-…

一、本节在学什么

单连接上多个请求同时在飞时，响应顺序不必与到达顺序一致。书中 Collatz 服务器用 RequestId 做关联：

  • 客户端发 req(id=1)、req(id=2)、req(id=3)
  • 服务器并行处理；id=2 可能先于 id=1 返回
  • 客户端按 id 匹配响应，而非假设 FIFO

思想类似 HTTP/2 Stream ID、RPC 的 call id。

二、为何需要多路复用

问题（串行处理） 多路复用做法
长任务阻塞后续短任务 每请求独立 task
吞吐差、延迟高 短任务先完成先返回
单连接只能一问一答 单连接多 in-flight 请求 
Client A  req id=1 ─┐
Client B  req id=2 ─┼→ Server 并行 spawn 处理
Client C  req id=3 ─┘
         ← resp 2 可能先于 resp 1 返回

三、Tokio 中的实现要点

组件 作用
RequestId 请求/响应配对键（u32、UUID 等）
tokio::spawn 每请求一个 task，互不阻塞
mpsc / 写锁 多 task 安全写回同一 socket（需串行化写或分 channel）
协议层 帧头带 id；Codec 解码后 dispatch 
use tokio::time::{sleep, Duration};

async fn handle(id: u32, delay_ms: u64) {
    sleep(Duration::from_millis(delay_ms)).await;
    println!("response id={id} (delay {delay_ms}ms)");
}

#[tokio::main]
async fn main() {
    let mut handles = vec![];
    for (id, delay) in [(1, 300), (2, 100), (3, 200)] {
        handles.push(tokio::spawn(handle(id, delay)));
    }
    for h in handles {
        let _ = h.await;
    }
}

Demo 模拟：id=2（100ms）先于 id=3（200ms）先于 id=1（300ms） 打印完成顺序。

仓库对应：7.2.1-socket-multiplexing-demo.rs

四、与 HTTP/2 / gRPC 对照

机制 多路复用方式
HTTP/1.1 通常多连接或 pipelining（受限）
HTTP/2 单 TCP 多 stream id
gRPC（Ch5） HTTP/2 上多并发 RPC
书中 Collatz 自定义二进制/文本协议 + RequestId

五、新手易错

  1. 响应乱序 ≠ 错误：协议必须带 id；客户端不能假设「第二个发的第二个回」。
  2. 多 task 写同一 TcpStream：需 Mutex 或 dedicated writer task，避免写交错。
  3. 无上限 spawn：恶意客户端可打满 task 数；需连接级/全局并发限制。
  4. 与 7.2.2 流式 混淆：多路复用是多请求；流式是单请求分 Header/Body 阶段。

7.2

.2-streaming-protocols

书 §7.2.2 · 分帧与解析：Ch04 · 贯通稿：notes/Ch07-…

一、本节在学什么

大 payload 不必全部收完才开始处理：

  • Header 完整 → 立刻路由、鉴权、开管道
  • Body 仍在传输 → Stream 继续 read，边收边处理

配合 长度前缀（或定长头）分帧，与 Ch4 Codec / nom 思路一致。

二、流式 vs 缓冲整包

模式 行为 适用
缓冲整包 收齐 Body 再 dispatch 小消息、简单 API
流式 Header/Body Header 一到就决策 大上传、实时管道
长度前缀帧 先读 4 字节 len，再读 body 通用二进制协议 
[ Header 已完整 ] → 可先 dispatch（鉴权、选 handler）
[ Body  仍在传输 ] → AsyncRead 继续 read，可选 Stream 消费

三、长度前缀分帧

线格式：[ u32 BE length ][ payload bytes… ]

fn decode_frame(buf: &[u8]) -> Option<(&[u8], &[u8])> {
    if buf.len() < 4 {
        return None; // 头不完整
    }
    let len = u32::from_be_bytes(buf[..4].try_into().ok()?) as usize;
    if buf.len() < 4 + len {
        return None; // body 未收齐
    }
    Some((&buf[4 + len..], &buf[4..4 + len]))
}

编码侧：

let payload = b"{\"header\":\"ok\",\"body\":\"streaming...\"}";
let mut wire = Vec::new();
wire.extend_from_slice(&(payload.len() as u32).to_be_bytes());
wire.extend_from_slice(payload);
步骤 说明
读 4 字节 解析大端 u32 得 len
读 len 字节 得到一帧 payload
剩余 buffer 可能含下一帧（粘包）

生产环境用 tokio_util::codec::LengthDelimitedCodec 或自定义 Decoder 处理半包/粘包；demo 为离线 buffer 演示。

仓库对应：7.2.2-streaming-length-prefix-demo.rs

四、与 Tokio Codec 层衔接

TcpStream (AsyncRead)
    ↓ Framed + LengthDelimitedCodec
    ↓ Stream<Item = Bytes>  每项一帧
    ↓ 首帧当 Header 解析 → spawn 处理 Body 流
Ch4 概念 Tokio 7.2 对应
nom 解析 HTTP 行 首帧 JSON/二进制 Header
长度前缀（4.3） LengthDelimitedCodec
serde 反序列化 Header 帧 serde_json::from_slice

五、新手易错

  1. u32 长度无上限：恶意对端发 len=0xFFFFFFFF 会 OOM；需 max frame size。
  2. 短读：一次 read 不一定凑齐一帧；Decoder 要维护 BytesMut 累积 buffer。
  3. 字节序：协议固定 BE/LE；与主机序混用会错。
  4. JSON 里嵌长度：长度前缀是传输层分帧；JSON 内部字段长度由 JSON 语法决定，两层不要混。

二、X.509 证书主要字段

字段 含义
Version 证书版本
Serial Number 序列号
Signature Algorithm 如 SHA256withRSA
Issuer 颁发者 DN
Validity 生效 / 过期时间

rust-openssl  →  与系统 OpenSSL 库绑定

8.2

cryptography-using-ring

书 §8.2 · TLS 握手：8.1-securing-the-web.md · 贯通稿：notes/Ch08-…

一、本节在学什么

TLS 握手内部已含 ECDH 密钥协商；本章用 ring 单独演示 X25519 Diffie-Hellman，理解「共享密钥从哪来」。

ring：底层原语（agreement、哈希、AEAD）— 不是完整 TLS 栈。生产 Web/API 用 rustls 即可。

二、DH / ECDH 要解决的问题

在不安全信道上，如何让双方得到相同的对称密钥，且窃听者无法从公开信息推导？

步骤 客户端 服务器
1 生成 ephemeral 私钥 c_priv 生成 s_priv
2 计算公钥 c_pub 计算 s_pub
3 交换公钥（明文可传） 同左
4 shared = DH(c_priv, s_pub) shared = DH(s_priv, c_pub)
5 两端 shared 相同 用于 AEAD 加密

前向保密：每次握手 ephemeral 密钥，长期私钥泄露不危及历史会话（TLS 1.3 默认 ECDHE）。

三、ring X25519 示例

use ring::agreement::{self, EphemeralPrivateKey, UnparsedPublicKey, X25519};
use ring::rand::SystemRandom;

let rng = SystemRandom::new();
let client_priv = EphemeralPrivateKey::generate(&X25519, &rng)?;
let server_priv = EphemeralPrivateKey::generate(&X25519, &rng)?;
let client_pub = client_priv.compute_public_key()?;
let server_pub = server_priv.compute_public_key()?;

let client_shared = agreement::agree_ephemeral(
    client_priv,
    &UnparsedPublicKey::new(&X25519, server_pub.as_ref()),
    |key| key.to_vec(),
)?;

let server_shared = agreement::agree_ephemeral(
    server_priv,
    &UnparsedPublicKey::new(&X25519, client_pub.as_ref()),
    |key| key.to_vec(),
)?;

assert_eq!(client_shared, server_shared);
API 作用
EphemeralPrivateKey::generate 临时密钥对
compute_public_key 公开部分
agree_ephemeral 双方得到相同 shared secret

仓库对应：8.2-cryptography-ring-x25519-demo.rs

四、ring vs TLS

应用层自定义协议（少见）：
    ring X25519 + ChaCha20-Poly1305 — 需密码学专家审查

生产 Web/API：
    TLS（rustls）— 内部已含 ECDHE、证书校验、AEAD

与 Ch5 gRPC：常默认 TLS；不必手写 X25519。

五、新手易错

  1. 重复发明 TLS：自定义「加密协议」极易出错；优先 rustls。
  2. shared secret 当最终密钥：通常还要 KDF 派生 AEAD 密钥与 nonce 策略。
  3. 静态 DH：无 ephemeral 则无前向保密；TLS 1.3 禁用静态 RSA 密钥传输。
  4. 公钥不验证：MITM 可替换公钥；TLS 用证书绑定身份，裸 DH 不行。
  5. 打印 shared secret：调试后勿泄露到日志。

书 §9.2 · Ch7 Future：7.1 · futures-await → 语言内置 · 贯通稿：notes/附录-…

一、本节在学什么

futures 0.1 时代手写 and_then 链 → 回调地狱 + 复杂关联类型。

书中 futures-await 用宏预研 async/await；Rust 1.39+ 语言内置，futures-await 已被取代。

读附录时：把本节当作 async/await 的历史与动机。

二、问题：and_then 时代

step1().and_then(|a| {
    step2(a).and_then(|b| {
        step3(b).and_then(|c| {
            ...
        })
    })
})
痛点 async/await 解法
嵌套深 线性代码
错误传播麻烦 函数内直接用 ?
类型推断困难 async fn 返回 impl Future

三、现代：语言内置 async/await

书中 futures-await 现代 Rust
#[async] async fn
await!(future) future.await
crate 宏 编译器内置 
use tokio::time::{sleep, Duration};

async fn step1() -> u32 {
    sleep(Duration::from_millis(50)).await;
    1
}

async fn step2(v: u32) -> u32 {
    sleep(Duration::from_millis(50)).await;
    v + 2
}

#[tokio::main]
async fn main() {
    let result = step2(step1().await).await;
    println!("linear async result: {result}");
}

等价于顺序 and_then，但可读性接近同步代码。

仓库对应：9.2-awaiting-future-linear-demo.rs

四、谁 poll 你的 Future？

机制 说明
#[tokio::main] 创建 runtime，跑 main 的 Future
.await 当前 task 注册 waker，Pending 时 yield
block_on 当前线程阻塞直到 Future 完成

深入理解 executor：async_tokio/ch10_noop_waker_block_on/ — 无依赖 server + noop waker。

五、新手易错

  1. 在文档里找 futures-await：已过时，用标准 async/await。
  2. .await 在 non-async 上下文：须 block_on 或包在 async fn 里。
  3. 忘记 ? 需要 async fn 返回 Result：错误类型要一致。
  4. 把 .await 当成阻塞 OS 线程：只阻塞当前 task，不阻塞其它 task。

9.3

data-parallelism

书 §9.3 · I/O 异步：Ch07 · 对照 atomic/rayon/ · 贯通稿：notes/附录-…

一、本节在学什么

任务并行（多连接、多 async task）≠ 数据并行（同一数据集分块独立处理）。

任务并行 数据并行
划分 不同任务 同一数据分块
典型 Tokio、OS 线程 rayon
等待 I/O CPU 计算

网络服务：I/O 用 Tokio；解析大文件、批量校验、压缩等 CPU 密集 可用 rayon 或 spawn_blocking。

二、rayon 核心 API

API 用途
rayon::scope 分叉子任务，作用域结束自动 join
par_iter() 并行迭代器，替代 iter()
par_sort 等 并行排序、划分 
use rayon::prelude::*;

let data: Vec<i32> = (0..10_000).collect();
let seq: i32 = data.iter().map(|x| x * x).sum();
let par: i32 = data.par_iter().map(|x| x * x).sum();
assert_eq!(seq, par);

书中示例还包括：并行 二分查找（scope 分治）、criterion 基准对比顺序 vs 并行。

仓库对应：9.3-data-parallelism-pariter-demo.rs

三、与 async 组合

Tokio task 收到大 payload
    ↓
tokio::task::spawn_blocking(|| {
    data.par_iter().map(expensive).collect()
})
    ↓
.await 拿回结果，继续 async 写 socket
做法 适用
纯 par_iter 在 sync main CLI、批处理
spawn_blocking + rayon async 服务内 CPU 密集
纯 async 里 par_iter ❌ 阻塞 worker，应用 blocking 池

四、新手易错

  1. 小数据用 rayon：线程开销可能大于收益。
  2. 在 Tokio worker 上直接 par_iter：占满线程池，拖慢 I/O。
  3. 数据竞争：par_iter 要求闭包无共享可变；用 map/reduce 模式。
  4. 与 Ch7 混淆：rayon 不替代 async 网络 I/O。

9.4

parsing-using-pest

书 §9.4 · nom 对照：Ch04 · 贯通稿：notes/附录-…

一、本节在学什么

Ch04 用 nom（组合子 + 宏）；附录给出 PEG 路线 pest：

  • 规则写在独立 .pest 文法文件
  • pest_derive 生成解析器
  • 书中称 失败提示更友好、文法集中易读

用 Pest 重写 HTTP 请求行，与 Ch4 nom 示例对照风格差异。

二、nom vs pest

nom pest
规则写法 Rust 宏 / 组合子函数 独立 .pest 文件
生成 编译期展开宏 pest_derive
错误信息 依赖调试技巧 往往更直观
维护 复杂协议拆子解析器 文法集中
二进制 bits! 等 更偏文本 PEG

三、工作流

1. 文法 http_line.pest：

method = { "GET" | "POST" }
path = @{ (ASCII_ALPHANUMERIC | "/" | "_" | "-")+ }
version = { "HTTP/" ~ ASCII_DIGIT+ ~ "." ~ ASCII_DIGIT+ }
request = { method ~ " " ~ path ~ " " ~ version }

2. 派生解析器：

use pest::Parser;
use pest_derive::Parser;

#[derive(Parser)]
#[grammar = "9.4-parsing-using-pest/http_line.pest"]
struct HttpLineParser;

3. 遍历 pair 树取语义：

let input = "GET /api/users HTTP/1.1";
let mut pairs = HttpLineParser::parse(Rule::request, input)?;
let request = pairs.next().unwrap();
let mut inner = request.into_inner();
let method = inner.next().unwrap().as_str();
let path = inner.next().unwrap().as_str();
let version = inner.next().unwrap().as_str();
println!("pest: {method} {path} {version}");

仓库对应：9.4-parsing-pest-http-line-demo.rs + http_line.pest

四、选型建议

场景 倾向
团队熟 PEG 文法 pest
纯 Rust 组合、嵌入式、二进制 nom
JSON/MessagePack serde（Ch4）
完整 HTTP httparse / hyper（Ch6）

五、新手易错

  1. grammar 路径：#[grammar = "..."] 相对 crate 根或模块，改目录要同步。
  2. 静默规则 @ vs _：影响 AST 是否包含中间节点。
  3. PEG 贪婪与优先级：文法顺序影响匹配，需读 pest 文档。
  4. 只解析不验证：请求行合法 ≠ 整个 HTTP 消息合法。

9.5

miscellaneous-utilities

书 §9.5 · TCP 标志：Ch01 · URL 与 HTTP：Ch06 · 贯通稿：notes/附录-…

一、本节在学什么

网络代码里两个高频小工具：

  • bitflags：类型安全的 位标志（TCP 头、socket 选项、自定义协议）
  • url：解析/构造 URL（scheme、host、path、query）

二、bitflags

协议常出现 C 风格位标志（2 的幂）：

use bitflags::bitflags;

bitflags! {
    struct TcpFlags: u8 {
        const FIN = 0b001;
        const SYN = 0b010;
        const ACK = 0b100;
    }
}

let flags = TcpFlags::SYN | TcpFlags::ACK;
println!("bits: {:b}, has ACK? {}", flags.bits(), flags.contains(TcpFlags::ACK));
能力 说明
\| & 组合、掩码
contains() 是否含某位
bits() 原始整数，可写入报文

对照 TCP 首部：FIN/SYN/RST/PSH/ACK/URG 即典型 bitflags 场景。

三、url

use url::Url;

let u = Url::parse("https://example.com:8443/path?q=1#frag")?;
println!("scheme={} host={:?} path={}", u.scheme(), u.host(), u.path());
字段 示例
scheme https
host example.com
port 8443（可选，默认随 scheme）
path /path
query q=1
fragment #frag（通常不发 HTTP 请求）
username / password 可选（避免明文存密码）

与 reqwest：可先 Url::parse 再 join 路径、改 query，比字符串拼接安全。

四、典型网络用途

crate 用途
bitflags TCP 标志、IP 头、setsockopt、自定义协议头
url 爬虫起始 URL、重定向解析、API 客户端基址

五、新手易错

  1. 字符串拼 URL：特殊字符未 encode → 用 Url::parse_with_params 等 API。
  2. bitflags 宽度：与协议字段一致（u8 vs u32）。
  3. 把 fragment 当服务端路由：# 段不发送到服务器。
  4. URL 里明文密码：日志/Referer 可能泄露。
