1.1

`core` 库（语言核心库）

章索引：第 1 章 · 后：1.2 alloc 库

一句话

core 是与 CPU 架构无关的可移植库 — 同时服务于 OS 内核 与 用户态；承载 intrinsics、基本 trait/类型、alloc/mem/ptr 内存模块 及 Option/Result 等语言根基，不依赖堆与操作系统。

原书定位

Rust 被设计为可编写 OS 内核 的系统级语言；标准库最底层 core 必须能在 无 OS、无堆 环境独立运行。日常 std 程序通过重导出使用同一套类型，但读源码、写 no_std、做 HFT 热路径优化时，要会 下钻到 core。

在三层架构中的位置

                    ┌─────────────────────────────────────┐
                    │  std（用户态 · SYSCALL）               │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │  alloc（堆 · 仅依赖 core）              │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │  core ← 本节                          │
                    │  内核态 ✅  用户态 ✅  无 OS ✅         │
                    └─────────────────────────────────────┘
属性 说明
硬件 与具体 CPU 架构解耦的可移植抽象（intrinsic 由编译器按目标 codegen）
堆 ❌ 无 Vec / String / Box
OS ❌ 无文件、网络、线程
源码 library/core/src/

核心内容（原书 §1.1）

1. 编译器内置（intrinsic）函数

类别 示例方向
内存操作 copy_nonoverlapping、write_bytes 等 — 常 unsafe
数学 平台相关优化、浮点/整数原语
原子 atomic_* 系列 — 与 CPU 内存序硬件相关

→ 由 编译器实现，非普通 Rust 函数；读 core 时会频繁见到 intrinsics 模块。

2. 基本特征（Trait）

类别 代表
运算符 ops Add、Sub、BitAnd …
Marker Send、Sync、Sized、Copy …
迭代器 iter Iterator、IntoIterator、ExactSizeIterator …
类型转换 From / Into、AsRef / AsMut、TryFrom …

Trait 定义在 core；具体容器实现多在 alloc / std。

3. 基本数据类型与内嵌类型

类型 说明
整数 / 浮点 / bool / char 语言内置
Option<T> / Result<T, E> 视为 Rust 语法不可或缺的 代数类型 — 在 core 定义

4. 内存操作模块（原书重点）

模块 职责
core::alloc Layout 等 — 布局与分配 契约（非堆分配器本身）
core::mem size_of、align_of、replace、forget …
core::ptr 裸指针 *const T / *mut T 的安全抽象边界

原书：Rust 中约 90% 的 unsafe 语法都可归结到 alloc、mem、ptr 三个模块（此处 alloc 指 core::alloc 布局模块，与 crate alloc 不同名同质不同层 — 读源码勿混）。

→ 第 3 章 内存操作 会展开。

5. 其他基础结构

领域 内容
数组 / 切片 / Range [T; N]、[T]、Range/RangeInclusive
字符串与格式化 str（DST）、fmt（Display、Debug、Write）
内部可变性 UnsafeCell<T>、Cell<T>、RefCell<T>（单线程） — 第 7 章专章 
core（原书地图）
├── intrinsics ─────── 编译器内置
├── ops / marker / iter / convert ── Trait 根基
├── option / result ── 和与积类型
├── mem / ptr / alloc::Layout ── unsafe 主战场
├── slice / array / str / range
├── fmt ────────────── 格式化
└── cell / pin ─────── 内部可变与自引用

core 不做什么

  • 不分配堆 — 动态容器在 alloc crate。
  • 不碰 SYSCALL — 线程/文件/网络在 std。
  • 不等于「只能嵌入式」 — 普通程序每天都在用 core 类型，只是经 std:: 重导出。

intrinsics intrinsics/mod.rs

场景 与 core 的关系

1.2

`alloc` 库（智能指针与集合库）

章索引：第 1 章 · 前：1.1 core 库 · 后：1.3 std 库

一句话

alloc 中 所有类型都基于堆内存，仅依赖 core — 同样可用于 OS 内核 与 用户态；提供 Allocator / Global、智能指针与 Vec / 集合等动态结构。

原书定位

在已有 core 的前提下，只需实现 全局分配器（GlobalAlloc），即可在内核态或嵌入式中使用 Box / Vec / String，而仍不必链接完整 std（无 SYSCALL）。

在三层架构中的位置

                    ┌─────────────────────────────────────┐
                    │  std（用户态 · 重导出 + OS）            │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │  alloc ← 本节（堆 · 仅依赖 core）       │
                    │  内核态 ✅（自备分配器）  用户态 ✅       │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │  core                                 │
                    └─────────────────────────────────────┘
属性 说明
依赖 仅 core
堆 ✅ 全部类型基于堆
OS ❌ 仍无 fs / net / thread
源码 library/alloc/src/

核心内容（原书 §1.2）

1. 内存申请与释放

项 说明
Allocator trait 分配器抽象（Rust 较新版本分配器 API 体系）
Global 单元类型 默认全局分配入口的实现者之一
对接 用户态 std 默认 GlobalAlloc；no_std 需 #[global_allocator] 自备

→ Nomicon 08 实现 Vec / 自定义分配器

2. 智能指针体系

类型 用途
Box<T> 独占堆所有权
Rc<T> 单线程共享所有权
Arc<T> 并发安全 引用计数（原子计数；与 std::sync::Arc 关系见源码）
String 堆上 UTF-8 字符串

→ 第 8 章 智能指针

3. 动态数据结构

类型 说明
RawVec<T> Vec 底层容量管理（未稳定公开 API，读源码关键）
Vec<T> 动态数组
LinkedList<T> 链表
VecDeque<T> 双端队列（原书「VecQueue」即此类）
BTreeSet<T> / BTreeMap<K, V> 有序集合 / 映射 
alloc（原书地图）
├── alloc / GlobalAlloc / Allocator ── 分配接口
├── boxed ── Box
├── rc / sync ── Rc / Arc
├── string ── String
├── vec / raw_vec ── Vec / RawVec
└── collections ── LinkedList / VecDeque / BTree*

1.3

`std` 库（用户态标准库）

章索引：第 1 章 · 前：1.2 alloc 库 · 后：1.4 回顾

一句话

std 建立在 操作系统 SYSCALL 之上 — 仅适用于用户态；在 core + alloc 之上整合重导出，并针对 OS 资源 提供线程、文件、标准 I/O、网络等 API。

原书定位

层 运行环境
core / alloc 内核态 ✅ · 用户态 ✅ · 可脱离 OS 独立运行
std 用户态 only — 必须依赖 OS 系统调用

在三层架构中的位置

                    ┌─────────────────────────────────────┐
                    │  std ← 本节                           │
                    │  SYSCALL · 线程 · 文件 · 网络 · stdio  │
                    └──────────────────┬──────────────────┘
                                       │ 映射整合 core + alloc
                    ┌──────────────────▼──────────────────┐
                    │  alloc                                │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │  core                                 │
                    └─────────────────────────────────────┘
属性 说明
默认入口 普通 cargo 二进制隐式链接 std
no_std ❌ 不能同时使用完整 std
源码 library/std/src/

核心内容（原书 §1.3）

1. 对 core 与 alloc 的映射整合

  • 业务代码通常 use std::… — 不必区分 crate。
  • std::vec::Vec 等即 alloc 类型的再导出 + 平台 glue。
  • 读性能/实现时仍要 下钻 alloc / core。

2. 针对 OS 资源的类型、Trait 与函数

领域 原书要点 主要模块
线程管理 临界区 / 互斥锁、消息通信 thread、sync（Mutex、RwLock、mpsc）
文件与目录 路径、读写、metadata fs、path
标准输入输出 stdin / stdout / stderr io（Read / Write）
网络通信 TCP/UDP 等 net

→ 本仓库延伸：第 9～13 章 · 05-atomic · 05-network stage03/07

3. 相对 alloc 额外能力（归纳）

  1. 操作系统抽象 — 统一跨平台 SYSCALL 封装（内部 sys 模块）。
  2. 运行时 glue — panic、栈展开、rt 启动、默认 GlobalAlloc。
  3. 平台扩展 — std::os::unix / windows 等。

模块地图

std
├── 重导出 ──────── core / alloc 类型（Vec / String / Arc …）
├── 并发 ─────────── thread / sync / atomic
├── I/O ──────────── io / fs / net / process / env
├── 错误 ─────────── io::Error · Error trait（Result 在 core）
└── FFI ──────────── ffi · os::raw

1.4

回顾

章索引：第 1 章 · 前：1.3 std 库 · 后：第 2 章 Rust 特征小议

一句话

core → alloc → std 分层解耦：底层可在无 OS 环境运行（内核态），std 为日常用户态应用提供 SYSCALL 之上的丰富系统能力 — 使 Rust 适配各 CPU 架构与 OS 平台。

原书总结（三层对照）

库 定位 依赖 典型场景
core 与 CPU 架构无关的可移植 语言核心 无 内核 · 嵌入式 · 一切程序的基础类型
alloc 堆上 智能指针与集合 仅 core 内核+分配器 · 无完整 OS 的动态内存
std 用户态 标准库 · SYSCALL core + alloc 线程 · 文件 · 网络 · 普通应用 
         内核态 / 用户态
core  ────────────────────  可移植 · 无堆 · 无 OS
alloc ────────────────────  +堆 · 仍无 OS
std   ─── 仅用户态 ───────  +OS 资源 · 重导出整合

设计哲学（原书）

要点 含义
解耦 写 OS 不必拖入 std；写应用不必重复实现 Option
可移植 core/alloc 跨架构；std 按平台封装 SYSCALL
unsafe 集中 约 90% unsafe 与 core::mem / core::ptr / core::alloc::Layout（及 alloc 分配实现）相关 — 第 3 章深入
读源码路径 应用 API → std → alloc → core

依赖关系（读源码时）

  1. 算法下沉 — Vec 遍历、比较在 core::slice；容量在 alloc::raw_vec。
  2. I/O 上浮 — TcpStream::read 在 std::sys 调平台 API。
  3. Trait 统一 — Send/Sync/Drop 在 core；Mutex 在 std 包 OS 锁。

选型速查（HFT / 系统编程）

需求 选层
固件、内核、零堆热路径 core（± 自备 alloc）
内存池、Vec、无文件网络 no_std + alloc
行情接入、多线程、mpsc、落盘 std
Wasm 模块（07 专题） 多为 wasm32 + 精简 std/alloc — 对照 07-Wasm

读完后应能回答

  1. 为何 alloc 能用于内核 而 std 不能？
  2. core::alloc::Layout 与 alloc crate 名称相近 — 各管什么？
  3. 原书说 90% unsafe 落在哪三个模块方向？
  4. 读 Vec::push 应打开哪两个 crate 的源码？
