# 20.3 优雅停机与清理

← [20.2 多线程与线程池](./20.2-多线程与线程池.md) · → [20 章节导读](./20-章节导读.md)

配套代码：[`20.2-thread-pool-demo/`](./20.2-thread-pool-demo/)（`Drop` 实现）

## 核心结论

1. `Drop` 里**不能等** worker 干完活——它可能永远不返回；只能**发信号**
2. 停机信号的实现很取巧：**`drop(sender)`**，让 worker 的 `recv()` 返回 `Err`
3. 顺序必须是 **先 `drop(sender)` → 再 `join()`**；反过来必死锁
4. 取 `JoinHandle` 的所有权要用 `Option::take()`，因为 `Drop::drop` 只有 `&mut self`

---

## 实现

```rust
impl Drop for ThreadPool {
    fn drop(&mut self) {
        // ① 发信号：丢掉 sender，channel 的另一端会收到 Err
        drop(self.sender.take());

        // ② 收工：等每个 worker 真正退出
        for worker in &mut self.workers {
            if let Some(thread) = worker.thread.take() {
                thread.join().unwrap();
            }
        }
    }
}
```

### 为什么 `drop(sender)` 就能当停机信号

`mpsc` channel 的语义：**只要 sender 全部被 drop，`recv()` 立即返回 `Err(RecvError)`**。

```text
sender 存在        → recv() 阻塞等待下一个 Job
sender 全部 drop   → recv() 立刻返回 Err → worker 跳出循环 → 线程结束
```

这是一个零成本的广播：不需要额外定义 `Shutdown` 消息，也不需要标志位。

### 为什么不能先 join 再 drop

```rust
// 死锁版本（错误示范）
for worker in &mut self.workers {
    worker.thread.take().unwrap().join().unwrap();  // ← 永远卡在这
}
drop(self.sender.take());                            // ← 永远执行不到
```

worker 还在 `recv()` 上阻塞，而唤醒它的唯一条件是 sender 被销毁。
主线程却在等 worker 退出 —— **循环等待，死锁**。

> 这条规则适用于所有"停机"场景：
> **先关闭入口（不再收新任务），再等待存量处理完**。

## `Drop` 的约束

| 约束 | 应对 |
|------|------|
| `fn drop(&mut self)` 拿不到所有权 | 字段包 `Option<T>`，用 `take()` 取出 |
| `Drop` 里不能返回 `Result` | 只能 `unwrap()` 或忽略；`join` 失败通常直接 panic 或记录 |
| `Drop` 里 panic 很危险 | 正在 unwind 时再次 panic 会 abort；尽量不做可能失败的操作 |

## HFT 视角：优雅停机的真实含义

交易系统的「停机」不是关掉进程，而是**一个状态机**：

```text
1. 停止接收新订单（撤掉行情订阅 / 关闭监听端口）
      ↓  ← 这一步等价于 drop(sender)
2. 等待在途订单处理完（flush OMS、确认回报）
      ↓  ← 这一步等价于 join()
3. 落盘状态（持仓、资金、序号）
      ↓
4. 退出
```

| 步骤 | 本章对应 | 生产上的额外要求 |
|------|----------|------------------|
| 停收新单 | `drop(sender)` | 还要对网关返回"不接受新单"，不能静默丢 |
| 等在途完成 | `join()` 所有 worker | 必须有**超时**，否则一个卡死的任务能拖住整个下线流程 |
| 落盘 | — | 序号/seq 必须持久化，重启后能续传 |
| 退出 | 进程结束 | 记录退出原因，便于复盘 |

> **关键差异**：本章的 `join()` 是**无限等待**。生产实现必须加超时
> （比如 `recv_timeout` + 最多等 30 s），超时后强制终止并告警——
> 「下不了线」和「丢单」一样是事故。

## 速记

```text
impl Drop for ThreadPool:
    ① drop(self.sender.take())        // 发停机信号 → worker 的 recv() 返 Err
    ② for w in workers { w.thread.take().join() }   // 等所有 worker 退出
顺序反了 = 死锁（worker 等信号，主线程等 worker）
```

**易错点**

| 现象 | 原因 |
|------|------|
| 程序退出时卡住 | `join` 在 `drop(sender)` 之前 |
| `cannot move out of type` | `Drop` 里没用 `Option::take()` |
| worker 不退出 | `recv()` 的 `Err` 分支没 `break` |
| 部分任务没执行完 | `drop(sender)` 后剩余任务仍会被消费完——这是 `mpsc` 的保证，不会丢 |
