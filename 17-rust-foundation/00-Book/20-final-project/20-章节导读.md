## 三节的核心结论

### 20.1 单线程

- `TcpListener::bind` 返回的 `incoming()` 是**阻塞迭代器**：`for stream in listener.incoming()`
- 请求行以 `\r\n` 结尾，用 `BufReader::lines()` 读到空行即为 header 结束
- **致命缺陷**：单线程下慢请求会**队头阻塞**（head-of-line blocking）——
  一个慢客户端能把后面所有请求拖死

### 20.2 线程池

- 不要「每连接一线程」：线程创建有成本，且连接数暴涨会耗尽资源（C10K 问题的雏形）
- 池化：启动时建 N 个 worker，任务通过 channel 分发
- **难点**：`Receiver` 不能共享 → 用 `Arc<Mutex<Receiver>>`，
  每个 worker 循环 `lock().unwrap().recv()`
- 任务类型必须是 `FnOnce() + Send + 'static`，所以装箱为 `Box<dyn FnOnce() + Send + 'static>`
  （这就是 ch19 `?Sized` / trait object 的实际用处）

### 20.3 优雅停机

- `Drop` 里不能等 worker（可能永不返回），只能**发信号**：`drop(sender)` 让 `recv()` 返回 `Err`
- worker 收到 `Err` 就跳出循环退出；主线程再 `join` 收工
- 顺序很关键：**先 drop sender，再 join**；反过来会死锁

## HFT / 嵌入式关联

| 本章机制 | 在 HFT 里的对应 |
|----------|------------------|
| 线程池 + 通道分发 | 行情网关的**扇出模型**：一个 I/O 线程收包，多个 worker 线程解码 |
| 队头阻塞 | 单线程撮合/风控里最典型的延迟毛刺来源 |
| `Arc<Mutex<T>>` | 共享订单簿的朴素方案；生产上会换成无锁队列或分片（见 `05-Async/01-atomic`） |
| 优雅停机 | 交易日结束/策略热切换时必须**不丢单**：先停收新单，再等存量处理完 |
| 线程数 = CPU 核数 | 与 `pin` 到核（`14-hft-engineering`）配合，才是真正的低延迟部署 |

> **局限**：`std::thread` 线程池适合理解原理，**不适合直接上生产**。
> 真实低延迟服务用 `tokio` + `LocalSet`/`spawn_blocking`（见 `05-Async/02-async_tokio`），
> 或者干脆绑核 busy-poll（见 `13-dpdk`）。本章的价值是**把并发骨架讲透**。

## 速记

```text
TcpListener::bind → incoming() 阻塞迭代 → BufReader 读请求行
   ↓ 单线程会队头阻塞
ThreadPool::new(n) → mpsc::channel + Arc<Mutex<Receiver>> → N 个 Worker 循环 recv()
   ↓ 任务类型
Box<dyn FnOnce() + Send + 'static>
   ↓ 停机
impl Drop: drop(sender) → worker recv() 得 Err → 退出循环 → 主线程 join()
```

**易错点**

| 现象 | 原因 |
|------|------|
| `Receiver` 不能跨线程共享 | 它不是 `Sync`；包 `Arc<Mutex<..>>` |
| `move` 闭包里用了 `&self` | 生命周期不够；需要 `'static`，改用 `Arc` 克隆 |
| `Drop` 里 `join` 卡死 | 还没 `drop(sender)`，worker 一直在 `recv()` 阻塞 |
