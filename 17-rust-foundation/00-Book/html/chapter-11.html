一、测试三段式（AAA：Arrange · Act · Assert）

所有测试函数固定三步：

步骤 英文 做什么
1 Arrange 构造数据、初始化对象
2 Act 调用待测业务代码
3 Assert 校验输出是否符合预期 
#[test]
fn larger_can_hold_smaller() {
    // Arrange
    let larger = Rectangle { width: 8, height: 7 };
    let smaller = Rectangle { width: 5, height: 1 };
    // Act + Assert（简单场景可合并）
    assert!(larger.can_hold(&smaller));
}

二、测试模块与注解：#[cfg(test)] / #[test]

基础模板

#[cfg(test)] // 条件编译：仅 cargo test 时编译，cargo build 正式打包忽略
mod tests {
    use super::*; // 引入当前文件上层所有代码

    #[test] // 标记为测试用例；独立线程运行；panic → 失败
    fn it_works() {
        assert_eq!(2 + 2, 4);
    }
}

注解说明

注解 作用
#[cfg(test)] 单元测试标配；减小正式产物体积、缩短编译
#[test] 测试器自动执行；每个用例独立线程，互不干扰
panic 测试函数 panic → 该用例失败；无 panic → 通过

→ 拆碎讲 cfg vs test、模拟输入：11.1.1

三、三大断言宏

1. assert!(布尔表达式)

表达式必须为 true，否则 panic 失败。

assert!(big.can_hold(&small));
assert!(!small.can_hold(&big));

2. assert_eq!(预期, 实际)

左右相等；失败时自动打印两边值。

约束：类型须实现 PartialEq + Debug；自定义 struct 加 #[derive(PartialEq, Debug)]。

assert_eq!(add_two(2), 4);

3. assert_ne!(A, B)

左右不相等（与 assert_eq! 相反）。

assert_ne!(add_two(2), 5);

4. 自定义报错（format! 占位）

三个断言宏都支持追加文案，{} 填充变量：

assert!(
    res.contains("Carol"),
    "名字匹配失败，实际字符串：{}",
    res
);

四、预期 panic：#[should_panic]

校验入参非法时必须 panic 才算通过。

基础：只要 panic 就过

#[test]
#[should_panic]
fn test_overflow() {
    Guess::new(200); // 限制 ≤100，传 200 必 panic
}

精准匹配（推荐）：expected = "关键字"

限定 panic 信息须包含指定字符串，避免非预期 panic 误通过：

#[test]
#[should_panic(expected = "less than or equal to 100")]
fn test_overflow() {
    Guess::new(200);
}

五、返回 Result 的测试

测试函数签名可为 -> Result<(), E>：Err = 失败，Ok(()) = 通过。

优势：测试内部可直接用 ? 传播错误。

⚠️ 不能与 #[should_panic] 共用，二选一。

#[test]
fn test_with_result() -> Result<(), String> {
    if add_two(2) == 4 {
        Ok(())
    } else {
        Err("计算错误".to_string())
    }
}

六、常用 cargo test 指令

cargo test                          # 全部用例
cargo test it_adds_two              # 只跑函数名匹配的用例
cargo test -- --test-threads=1      # 单线程串行（排查并发问题）
cargo test -- --nocapture           # 显示 println! 输出

→ 更多过滤、忽略、并行控制见 11.2。

11.2

控制测试如何运行

← 11.1 如何编写测试 · 11.3 测试的组织结构 · demo：11.2-control-tests-demo/

cd 00-Book/11-testing/11.2-control-tests-demo
cargo test

一、核心规则：cargo test 两套参数，-- 做分隔

cargo test [cargo 自身参数] -- [传给测试程序的参数]
# -- 左边：cargo 管理编译、筛选用例
# -- 右边：测试运行时配置（线程、打印输出、ignored）

二、控制测试并发（多线程 / 串行）

规则

cargo test 默认多线程并行跑所有用例。

缺点：多个测试操作同一文件、全局环境变量时，会互相篡改数据、随机报错。

命令：指定单线程串行

# --test-threads 属于测试二进制参数，放 -- 右侧
cargo test -- --test-threads=1
  • =1：只用 1 个线程，从上到下串行跑
  • 也可写 --test-threads=4 指定 4 线程

demo 代码（文件竞争）

#[cfg(test)]
mod tests {
    #[test]
    fn test_a() {
        std::fs::write("tmp.txt", "A").unwrap();
    }
    #[test]
    fn test_b() {
        let s = std::fs::read_to_string("tmp.txt").unwrap();
        println!("{}", s);
    }
}

并行：a、b 随机先后，文件内容错乱；串行 --test-threads=1 顺序执行无异常。

demo 里 test_file_a / test_file_b 默认 #[ignore]，避免 cargo test 随机失败；串行演示：

cargo test file -- --test-threads=1 --include-ignored

三、控制控制台打印：--show-output

默认行为

  • 测试通过：自动吞噬 println!，控制台看不见
  • 测试失败：自动打出所有 println!

通过的测试也要打印

cargo test -- --show-output

#[test]
fn show_print() {
    println!("我是测试内部打印内容");
    assert_eq!(1, 1);
}

不加 --show-output：无打印；加参数：控制台输出字符串。

四、按函数名筛选（只跑部分测试）

cargo test 关键字：cargo 侧参数，写在 -- 左边，匹配测试函数名（模糊匹配，包含即执行）。

① 精准匹配单个函数

cargo test one_hundred

② 模糊匹配名字含 add 的所有测试

cargo test add
# 匹配 add_two、add_two_and_two 等

测试全路径形如 tests::add_two_and_two，搜索匹配全名子串。

#[test]
fn add_two() { assert_eq!(2 + 2, 4); }
#[test]
fn add_two_and_two() { assert_eq!(2 + 2, 4); }
#[test]
fn one_hundred() { assert_eq!(100, 100); }
  • cargo test add → 前两个
  • cargo test one_hundred → 只第三个

五、#[ignore] 忽略耗时测试

#[test]
#[ignore] // 默认跳过
fn expensive_test() {
    std::thread::sleep(std::time::Duration::from_secs(2));
    assert!(true);
}

三条常用命令

场景 命令
默认（跳过 #[ignore]） cargo test
只跑被 ignore 的 cargo test -- --ignored
普通 + ignore 全跑 cargo test -- --include-ignored

六、速查命令清单

需求 命令
单线程串行 cargo test -- --test-threads=1
通过用例也打印 println cargo test -- --show-output
只跑名字带 add 的测试 cargo test add
只跑被 #[ignore] 的测试 cargo test -- --ignored
全部测试（普通 + 忽略） cargo test -- --include-ignored

在 11.2-control-tests-demo/ 目录下：

# 串行文件竞争演示

# 看 println
cargo test show_print -- --show-output

# 名字过滤

11.3

测试的组织结构

← 11.2 控制测试运行 · demo：11.3-test-organization-demo/

Rust 测试固定二分：单元测试（unit）+ 集成测试（integration） — 目录、位置、权限、写法完全不同。

cd 00-Book/11-testing/11.3-test-organization-demo
cargo test
cargo test --test integ_case

一、单元测试 Unit Test（写在 src/**.rs 内部）

1. 存放位置

和源码同文件，源码末尾用 #[cfg(test)] mod tests {} 包裹。

// src/lib.rs
fn private_add(a: i32, b: i32) -> i32 { a + b }
pub fn pub_add(a: i32, b: i32) -> i32 { a + b }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_private() {
        // ✅ 单元测试可以直接测私有函数
        assert_eq!(private_add(1, 2), 3);
    }

    #[test]
    fn test_pub() {
        assert_eq!(pub_add(2, 3), 5);
    }
}

2. #[cfg(test)] 核心作用

  • cargo build：整块 tests 不编译进最终产物
  • cargo test：编译并执行里面所有 #[test]

3. 单元测试特点

  1. 和源码同文件，粒度小，针对单个函数/模块
  2. use super::* → 能访问私有方法、私有字段
  3. cargo test 自动全部执行

二、集成测试 Integration Test（项目根 tests/，与 src/ 同级）

项目根目录
├── src/
│   └── lib.rs
├── tests/          ← 集成测试全部放这里
│   └── integ_case.rs
└── Cargo.toml

1. 关键规则

  1. tests/ 下每个 .rs 是一个独立测试 crate
  2. 站在外部使用者视角，只能 use 库名; 引入
  3. 只能调用 pub API，访问不到私有函数
// tests/integ_case.rs
// Cargo.toml 里 name = "test_organization_demo"
use test_organization_demo::pub_add;

#[test]
fn test_inte_pub() {
    assert_eq!(pub_add(10, 20), 30);
    // private_add() 编译报错
}

2. 单独跑某一个集成测试文件

cargo test --test integ_case

3. 集成测试抽取公共代码（踩坑）

❌ 错误：tests/common.rs

Cargo 会把 common.rs 当成独立集成测试 crate，输出里出现 running 0 tests 冗余日志。

✅ 标准：tests/common/mod.rs

tests/
├── common/
│   └── mod.rs
└── integ_case.rs

// tests/common/mod.rs
pub fn helper() -> i32 { 10 }

// tests/integ_case.rs
mod common;
use common::helper;

#[test]
fn use_common() {
    assert_eq!(helper(), 10);
}

目录形式不会被 Cargo 识别成独立测试 crate。

三、二进制项目（main-only）特殊问题

问题

只有 src/main.rs、无 src/lib.rs 时，tests/ 无法 use main 里的代码 — 二进制 crate 不能被外部引用。

工程标准拆分

src/
├── lib.rs   // 业务逻辑、pub API
└── main.rs  // 入口：参数解析、调用 lib

// src/lib.rs
pub fn calc(a: i32) -> i32 { a * 2 }

// src/main.rs
use test_organization_demo::calc;
fn main() {
    println!("{}", calc(5));
}

此时 tests/*.rs 可正常 use test_organization_demo::calc;。

四、单元 vs 集成对比表

项目 单元测试 集成测试
存放位置 src 同文件内部 项目根 tests/
访问权限 私有 + 公有 仅 pub
编译控制 #[cfg(test)] 打包剔除 仅 cargo test 编译
测试目标 单模块/函数细节 整体链路、多模块配合
执行 cargo test 自动 全部：cargo test；单文件：cargo test --test xxx

demo 目录

11.3-test-organization-demo/
├── Cargo.toml
├── src/
│   ├── lib.rs      # private_add / pub_add / calc + 单元测试
│   └── main.rs     # 二进制入口，调用 lib
└── tests/
    ├── common/
    │   └── mod.rs  # helper()
    └── integ_case.rs
命令 说明
cargo test 单元 + 全部集成
cargo test --test integ_case 只跑 tests/integ_case.rs
cargo run 运行 main，打印 calc(5) → 10
