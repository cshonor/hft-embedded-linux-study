三节的核心结论

20.1 单线程

  • TcpListener::bind 返回的 incoming() 是阻塞迭代器：for stream in listener.incoming()
  • 请求行以 \r\n 结尾，用 BufReader::lines() 读到空行即为 header 结束
  • 致命缺陷：单线程下慢请求会队头阻塞（head-of-line blocking）—— 一个慢客户端能把后面所有请求拖死

20.2 线程池

  • 不要「每连接一线程」：线程创建有成本，且连接数暴涨会耗尽资源（C10K 问题的雏形）
  • 池化：启动时建 N 个 worker，任务通过 channel 分发
  • 难点：Receiver 不能共享 → 用 Arc<Mutex<Receiver>>， 每个 worker 循环 lock().unwrap().recv()
  • 任务类型必须是 FnOnce() + Send + 'static，所以装箱为 Box<dyn FnOnce() + Send + 'static> （这就是 ch19 ?Sized / trait object 的实际用处）

20.3 优雅停机

  • Drop 里不能等 worker（可能永不返回），只能发信号：drop(sender) 让 recv() 返回 Err
  • worker 收到 Err 就跳出循环退出；主线程再 join 收工
  • 顺序很关键：先 drop sender，再 join；反过来会死锁

HFT / 嵌入式关联

本章机制 在 HFT 里的对应
线程池 + 通道分发 行情网关的扇出模型：一个 I/O 线程收包，多个 worker 线程解码
队头阻塞 单线程撮合/风控里最典型的延迟毛刺来源
Arc<Mutex<T>> 共享订单簿的朴素方案；生产上会换成无锁队列或分片（见 05-Async/01-atomic）
优雅停机 交易日结束/策略热切换时必须不丢单：先停收新单，再等存量处理完
线程数 = CPU 核数 与 pin 到核（14-hft-engineering）配合，才是真正的低延迟部署

局限：std::thread 线程池适合理解原理，不适合直接上生产。 真实低延迟服务用 tokio + LocalSet/spawn_blocking（见 05-Async/02-async_tokio）， 或者干脆绑核 busy-poll（见 13-dpdk）。本章的价值是把并发骨架讲透。

速记

TcpListener::bind → incoming() 阻塞迭代 → BufReader 读请求行
   ↓ 单线程会队头阻塞
ThreadPool::new(n) → mpsc::channel + Arc<Mutex<Receiver>> → N 个 Worker 循环 recv()
   ↓ 任务类型
Box<dyn FnOnce() + Send + 'static>
   ↓ 停机

Receiver 不能跨线程共享 它不是 Sync；包 Arc<Mutex<..>>
move 闭包里用了 &self 生命周期不够；需要 'static，改用 Arc 克隆
Drop 里 join 卡死 还没 drop(sender)，worker 一直在 recv() 阻塞
20.1

单线程 Web 服务器

← 20 章节导读 · → 20.2 多线程与线程池

核心结论

  1. TcpListener::bind("127.0.0.1:7878") 拿到监听器；incoming() 返回阻塞迭代器
  2. 每个 TcpStream 用 BufReader 包一层，lines() 逐行读到空行即 header 结束
  3. 响应格式必须是 HTTP/1.1 200 OK\r\n\r\n + body，回车换行一个都不能少
  4. 单线程的天花板：队头阻塞

最小骨架

use std::io::prelude::*;
use std::net::TcpListener;

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let mut stream = stream.unwrap();
        let mut buf = [0; 1024];
        stream.read(&mut buf).unwrap();

        let response = "HTTP/1.1 200 OK\r\n\r\n<html>hi</html>";
        stream.write_all(response.as_bytes()).unwrap();
        stream.flush().unwrap();
    }
}

为什么要用 BufReader

TcpStream::read 不保证一次读满，TCP 是字节流没有消息边界。 按行解析必须用 BufReader::lines()：它内部缓冲，直到遇到 \n 才返回一行。

let mut reader = BufReader::new(&mut stream);
let request: Vec<String> = reader
    .by_ref()
    .lines()
    .map(|l| l.unwrap())
    .take_while(|l| !l.is_empty())   // 空行 = header 结束
    .collect();

HTTP 请求行以 \r\n 结束，lines() 会顺带把 \r 也吃掉。

致命缺陷：队头阻塞

客户端A（慢，sleep 10s）──┐
客户端B ──────────────────┼──> 单线程服务器：串行处理
客户端C ──────────────────┘        B、C 必须等 A 处理完

handle_connection 是同步阻塞调用，只要有一个连接不返回， 后面所有连接全部卡住。这不是吞吐问题，是延迟尾部分布问题—— P99 会被最慢的那个请求拖爆。

HFT 视角：这正是为什么低延迟系统里「任何一个 handler 都不允许阻塞」。 单线程事件循环（如 Redis、或 tokio 的单线程 runtime）能避免上下文切换， 但代价是该线程上任何阻塞操作都会毁掉整个循环的延迟。 生产上的两种选择： - 单线程 + 严格无阻塞（busy-poll、绑核） - 多线程/线程池 + 任务切分（本章 20.2 的路子）

易错点

现象 原因 / 修法
浏览器一直转圈 响应缺少结尾的 \r\n\r\n，或没 flush()
lines() 报 InvalidData 请求含非 UTF-8 字节；改用 read_until(b'\n') 处理字节
读完 body 后卡住 lines() 会一直等；用 take_while(|l| !l.is_empty()) 停在空行
端口被占用 上一进程没退出；SO_REUSEADDR 或换端口

速记

bind → incoming() 阻塞迭代 → BufReader::lines() → take_while 非空行 → 拼响应 → write_all + flush
                    ↑
              单线程 = 队头阻塞（P99 被最慢请求拖垮）
20.2

多线程与线程池

← 20.1 单线程 Web 服务器 · → 20.3 优雅停机

配套可运行代码：20.2-thread-pool-demo/

核心结论

  1. 不要每连接一线程：线程创建有成本，连接数暴涨会耗尽内存与调度预算
  2. 线程池 = 启动时建 N 个 worker + 用 channel 分发任务
  3. Receiver 不是 Sync，共享必须 Arc<Mutex<Receiver>>
  4. 任务类型：Box<dyn FnOnce() + Send + 'static>——这是 ch19 trait object 的真实用武之地

为什么不能每连接一线程

// 反例：连接一多就爆
for stream in listener.incoming() {
    thread::spawn(|| handle_connection(stream));
}
问题 说明
创建成本 每次 spawn 都要分配栈（默认 2 MB 虚拟内存）+ 内核线程对象
调度压力 10000 个连接 = 10000 个线程，上下文切换吃光 CPU
无背压 来多少接多少，OOM 是迟早的事

线程池的思路反过来：先固定 N 个 worker，任务排队。连接数可以远超 N， 多出来的只是排队等待。

线程池骨架

use std::sync::{mpsc, Arc, Mutex};
use std::thread;

type Job = Box<dyn FnOnce() + Send + 'static>;

pub struct ThreadPool {
    workers: Vec<Worker>,
    sender: Option<mpsc::Sender<Job>>,
}

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        let (sender, receiver) = mpsc::channel();
        let receiver = Arc::new(Mutex::new(receiver));  // 关键：让 receiver 可共享

        let workers = (0..size)
            .map(|id| Worker::new(id, Arc::clone(&receiver)))
            .collect();

        ThreadPool { workers, sender: Some(sender) }
    }

    pub fn execute<F>(&self, f: F)
    where
        F: FnOnce() + Send + 'static,
    {
        self.sender.as_ref().unwrap().send(Box::new(f)).unwrap();
    }
}

三个关键点

① 为什么是 Arc<Mutex<Receiver>>

mpsc::Receiver<T> 实现了 Send 但没有实现 Sync—— 多个 worker 不能同时持有 &Receiver。包一层 Mutex 提供互斥， 再包 Arc 提供共享引用计数。

struct Worker { id: usize, thread: Option<thread::JoinHandle<()>> }

impl Worker {
    fn new(id: usize, receiver: Arc<Mutex<mpsc::Receiver<Job>>>) -> Worker {
        let thread = thread::spawn(move || loop {
            // 注意作用域：guard 必须在 recv 结束后立刻释放，
            // 否则会一直占着锁，其他 worker 拿不到任务。
            let job = {
                let lock = receiver.lock().unwrap();
                lock.recv()
            };
            match job {
                Ok(job) => job(),
                Err(_) => break,   // sender 被 drop → 停机信号
            }
        });
        Worker { id, thread: Some(thread) }
    }
}

lock() 的作用域是个经典坑：如果写成 while let Ok(job) = receiver.lock().unwrap().recv()， 临时 MutexGuard 会活到整个语句结束，锁的粒度从「一次 recv」变成「执行完整任务」， 线程池直接退化成单线程。

② 为什么任务必须是 FnOnce() + Send + 'static

约束 原因
FnOnce 任务只执行一次，允许它消耗捕获的变量
Send 要跨线程移动到 worker
'static worker 线程活得比提交者可能更久，不能有借用
Box<dyn ...> 大小未知 → trait object（ch19 ?Sized）

③ Option<T> 包 JoinHandle 和 Sender

Drop 里要把它们 take() 出来才能 join/drop—— Drop::drop(&mut self) 拿不到所有权，Option::take 是标准解法。

局限与替代方案

方案 适用
std::thread 线程池（本章） 理解原理、CPU 密集任务
tokio + spawn_blocking I/O 密集 + 少量阻塞操作
rayon 数据并行（见 05-Async/01-atomic/rayon/）
绑核 busy-poll 真正的低延迟（见 14-hft-engineering、13-dpdk）

Arc<Mutex<Receiver>> 在高并发下是全局锁竞争点：所有 worker 抢同一把锁。 生产级实现会用 crossbeam 的无锁队列，或每 worker 一个队列 + 任务窃取 （本仓 05-Async/02-async_tokio/ch03_custom_task_queue/3.4-task-stealing 有对应 demo）。

HFT 视角

线程池本质是吞吐优先的设计：接受排队换取资源可控。 但 HFT 关心的是延迟而非吞吐，所以：

  • 队列长度 = 延迟。排队 100 个任务时，最后那个的延迟是前 99 个的执行时间之和
  • 因此低延迟系统宁愿拒绝（过载保护）也不愿排队
  • 若必须池化，通常做成每核一个队列 + 无锁 + 绑核，避免跨核竞争

速记

ThreadPool::new(n): channel + Arc<Mutex<Receiver>> + n 个 Worker
Worker: loop { let job = { lock().recv() }; match job { Ok=>执行, Err=>break } }
                        ↑ 大括号是为了让 guard 尽早释放
execute(f): sender.send(Box::new(f))   f: FnOnce() + Send + 'static

易错点

现象 原因
池子退化成单线程 MutexGuard 没在 recv() 后立刻释放
编译报 Receiver cannot be shared 少了 Arc<Mutex<..>>
expected 'static 闭包借用了局部变量；改用 move + Arc 克隆
Drop 里拿不到 JoinHandle 用 Option::take()
20.3

优雅停机与清理

← 20.2 多线程与线程池 · → 20 章节导读

配套代码：20.2-thread-pool-demo/（Drop 实现）

核心结论

  1. Drop 里不能等 worker 干完活——它可能永远不返回；只能发信号
  2. 停机信号的实现很取巧：drop(sender)，让 worker 的 recv() 返回 Err
  3. 顺序必须是 先 drop(sender) → 再 join()；反过来必死锁
  4. 取 JoinHandle 的所有权要用 Option::take()，因为 Drop::drop 只有 &mut self

实现

impl Drop for ThreadPool {
    fn drop(&mut self) {
        // ① 发信号：丢掉 sender，channel 的另一端会收到 Err
        drop(self.sender.take());

        // ② 收工：等每个 worker 真正退出
        for worker in &mut self.workers {
            if let Some(thread) = worker.thread.take() {
                thread.join().unwrap();
            }
        }
    }
}

为什么 drop(sender) 就能当停机信号

mpsc channel 的语义：只要 sender 全部被 drop，recv() 立即返回 Err(RecvError)。

sender 存在        → recv() 阻塞等待下一个 Job
sender 全部 drop   → recv() 立刻返回 Err → worker 跳出循环 → 线程结束

这是一个零成本的广播：不需要额外定义 Shutdown 消息，也不需要标志位。

为什么不能先 join 再 drop

// 死锁版本（错误示范）
for worker in &mut self.workers {
    worker.thread.take().unwrap().join().unwrap();  // ← 永远卡在这
}
drop(self.sender.take());                            // ← 永远执行不到

worker 还在 recv() 上阻塞，而唤醒它的唯一条件是 sender 被销毁。 主线程却在等 worker 退出 —— 循环等待，死锁。

这条规则适用于所有"停机"场景： 先关闭入口（不再收新任务），再等待存量处理完。

Drop 的约束

约束 应对
fn drop(&mut self) 拿不到所有权 字段包 Option<T>，用 take() 取出
Drop 里不能返回 Result 只能 unwrap() 或忽略；join 失败通常直接 panic 或记录
Drop 里 panic 很危险 正在 unwind 时再次 panic 会 abort；尽量不做可能失败的操作

HFT 视角：优雅停机的真实含义

交易系统的「停机」不是关掉进程，而是一个状态机：

1. 停止接收新订单（撤掉行情订阅 / 关闭监听端口）
      ↓  ← 这一步等价于 drop(sender)
2. 等待在途订单处理完（flush OMS、确认回报）
      ↓  ← 这一步等价于 join()
3. 落盘状态（持仓、资金、序号）
      ↓
4. 退出
步骤 本章对应 生产上的额外要求
停收新单 drop(sender) 还要对网关返回"不接受新单"，不能静默丢
等在途完成 join() 所有 worker 必须有超时，否则一个卡死的任务能拖住整个下线流程
落盘 — 序号/seq 必须持久化，重启后能续传
退出 进程结束 记录退出原因，便于复盘

关键差异：本章的 join() 是无限等待。生产实现必须加超时 （比如 recv_timeout + 最多等 30 s），超时后强制终止并告警—— 「下不了线」和「丢单」一样是事故。

速记

impl Drop for ThreadPool:
    ① drop(self.sender.take())        // 发停机信号 → worker 的 recv() 返 Err
    ② for w in workers { w.thread.take().join() }   // 等所有 worker 退出
顺序反了 = 死锁（worker 等信号，主线程等 worker）

易错点

现象 原因
程序退出时卡住 join 在 drop(sender) 之前
cannot move out of type Drop 里没用 Option::take()
worker 不退出 recv() 的 Err 分支没 break
部分任务没执行完 drop(sender) 后剩余任务仍会被消费完——这是 mpsc 的保证，不会丢
