panic! 与不可恢复的错误

触发 panic 后：打印错误信息（可选 backtrace）→ 进程退出。可恢复错误应优先用 Result → 9.3 策略。

结论（先看这三句）

  1. 默认 unwind：栈回溯 + 逐层 Drop；abort：直接退出、不跑 Drop，二进制更小、开销更低。
  2. panic 分主动（panic!）与被动（越界、unwrap 遇 None 等运行时检查）。
  3. HFT 生产 release 常用 panic = "abort" → 完整 profile 对照：9.1.2

一、两种 panic 策略

策略 行为 默认 特点
unwind（展开） 从当前函数逐层回溯栈，执行各层 Drop 再退出 debug / release 默认 能析构释放堆资源；开销偏大
abort（终止） SIGABRT 直接杀进程，不展开、不跑 Drop 需手动配置 体积更小、运行更快 
# Cargo.toml — release 启用 abort
[profile.release]
panic = "abort"

HFT 生产标配 panic = "abort"：致命故障直接销毁进程重启，避免 unwind 耗时、残留脏内存导致订单错乱。

与 catch_unwind 的关系

→ 完整版：9.1.3 catch_unwind 与 panic 模式

  • unwind：catch_unwind 可拦截栈展开
  • abort：catch_unwind 无效，进程直接退出

二、panic 触发分类

1. 主动：panic!

panic!("致命错误：{}", code);

手动抛出不可恢复错误。

2. 被动：运行时逻辑错误

Rust 运行时检查自动 panic，例如：

场景 示例
数组越界 v[99]
unwrap 遇 None / Err opt.unwrap()
空切片切分 split_at 越界
整数溢出 debug 默认 panic 
cargo run -- oob      # Vec 越界
cargo run -- unwrap   # None.unwrap()

release 整数溢出

模式 溢出行为
debug panic
release 默认 环绕溢出（wrapping，不 panic）

如需 release 也 panic：

[profile.release]
overflow-checks = true

.1 Backtrace 完整调试用法

← 主笔记：9.1 panic! · demo：9.1.1-backtrace-demo/（含 .cargo/config.toml 示例）

三种场景：panic 自动堆栈 · 手动打印栈 · catch 后自定义打印 · 配置文件永久开栈（§1.2）。

结论先说

RUST_BACKTRACE=1/full 不能写在 Cargo.toml [profile] 里 — profile 只管编译期参数；backtrace 是运行时环境变量。

配置位置 管什么
Cargo.toml [profile.*] debug / panic / overflow-checks（编译期）
.cargo/config.toml [env] 注入 RUST_BACKTRACE 等（运行时，不用 .env、不用每次 export）
Shell $env: / export 临时覆盖

一、环境变量：panic 自动堆栈

1.1 临时：Shell 导出

export RUST_BACKTRACE=full   # Linux / macOS
cargo run -- oob

$env:RUST_BACKTRACE = "full"
cargo run -- oob

1 vs full

值 效果
0 关闭
1 精简堆栈（常用，输出较短）
full 完整堆栈（含更多帧，调试首选）

1.2 永久：.cargo/config.toml（推荐）

不是 Cargo.toml，是项目根 .cargo/config.toml — cargo 运行/测试时自动注入：

# .cargo/config.toml
[env]
RUST_BACKTRACE = "full"
RUST_LIB_BACKTRACE = "1"   # 手动 Backtrace::capture 解析用
  • cargo run / cargo test 自动带 backtrace，无需 shell export
  • demo 已含此文件：9.1.1-backtrace-demo/.cargo/config.toml

注意：Cargo 没有 [env.dev] / [env.release] 官方语法 — [env] 对所有 cargo 子命令生效。若只想 dev 开栈：release 前注释掉该行，或 dev 专用分支 config。

1.3 release 要打栈：编译 + 运行缺一不可

光开 RUST_BACKTRACE 不够 — release 默认 debug = false 无符号，栈只有地址：

[profile.release]
debug = "line-tables-only"   # 保留行号，体积远小于 debug=true
panic = "unwind"             # abort 直接杀进程，无栈回溯
编译期（profile） 运行时（env） 结果
debug = false RUST_BACKTRACE=1 多半只有地址
debug = line-tables-only RUST_BACKTRACE=full 可有行号
panic = "abort" 任意 无栈展开，catch/backtrace 受限

1.4 代码内强制开启（脱离 shell / config）

fn main() {
    std::env::set_var("RUST_BACKTRACE", "full");
    // …
}

适合临时调试；HFT 生产勿硬编码。

示例：越界自动打栈

let arr = vec![1, 2, 3];
arr[10]; // 配合 RUST_BACKTRACE + debug 符号

二、手动打印当前调用栈（不 panic）

方案 1：std::backtrace（Rust 1.65+，无需第三方）

use std::backtrace::Backtrace;

fn func_b() {
    let bt = Backtrace::capture();
    println!("当前调用堆栈:\n{bt}");
}

fn func_a() {
    func_b();
}

fn main() {
    func_a();
}
API 作用
Backtrace::capture() 捕获当前栈（按需解析）
Backtrace::force_capture() 强制全量捕获

手动栈解析常配合：

RUST_LIB_BACKTRACE=1 cargo run -- manual

release 要行号：debug = true 或 debug = "line-tables-only" → 9.1.2。

方案 2：第三方 backtrace crate（老版本 Rust）

backtrace = "0.3"

use backtrace::Backtrace;

fn test() {
    let bt = Backtrace::new();
    println!("{bt:?}");
}

三、catch_unwind + 自定义打印堆栈

panic = "abort" 时无效 — 进程直接退出，无法捕获。

use std::backtrace::Backtrace;
use std::panic::catch_unwind;

fn risky_code() {
    let v = vec![1];
    v[5];
}

fn main() {
    let res = catch_unwind(risky_code);
    if res.is_err() {
        println!("异常，手动堆栈:\n{}", Backtrace::force_capture());
    }
}

→ panic 策略见 9.1 §一。

9.1

.2 dev / release · panic · 溢出检查（HFT 编译配置）

← 主笔记：9.1 panic! · 9.1.1 Backtrace

一次性讲清：只有 dev / release 两大 profile · debug 是配置项不是模式 · panic · overflow · backtrace 搭配。

先纠正：只有两大类内置 Profile

Cargo 内置两种编译方案，没有第三种叫「debug」的模式：

[profile.dev]     # cargo build / cargo run 默认
[profile.release] # cargo build --release 默认

debug 不是独立 profile，而是 profile 里的配置字段：debug = true/false（是否生成调试符号）。dev / release 里都能改。

容易混淆 是什么
dev / release Cargo 两种编译 profile（日常只关心这两个）
debug = true/false profile 内开关，控制符号表；release 也可设 debug = true
cargo debug ❌ 没有这条命令；只有 cargo build（dev）和 cargo build --release

额外：还可自定义 [profile.bench]、[profile.test] 等，极少手写；HFT 日常 dev + release 足够。

结论先说：出厂 dev / release 全是 panic = "unwind"

不写 [profile.*] 的 panic 项 = dev、release 默认都是 unwind。 只有手动在 Cargo.toml 里写 panic = "abort" 才会变成终止模式。

# Cargo 原厂默认（两行等价，通常省略不写）
# [profile.dev]     panic = "unwind"
# [profile.release] panic = "unwind"
Profile 出厂 panic 溢出（裸运算）
dev unwind 检查开启 → 溢出 panic
release unwind 检查关闭 → 环绕，不 panic
  1. 不写配置 → dev / release 全是 unwind
  2. 想要 abort → 必须手动改 Cargo.toml（HFT release 常见）

→ unwind / abort 一行对比 demo：9.1.3-catch-unwind-demo

一句话

场景 配置
写代码调试 dev + unwind + RUST_BACKTRACE=full
HFT 上线 release + panic = "abort" + debug = false

一、两种编译 profile

命令 Profile 用途
cargo build / cargo run dev 开发调试
cargo build --release release 发行 / 上线

1. [profile.dev]（cargo build / cargo run 默认）

[profile.dev]
opt-level = 0           # 无优化
debug = true            # 带符号 → backtrace 显示行号
panic = "unwind"        # 栈展开，可 catch_unwind
overflow-checks = true  # 整数溢出 → panic
  • 编译快、运行慢，方便断点 / backtrace
  • 只开发用，HFT 绝不上线 dev

2. [profile.release]（cargo build --release 默认）

出厂默认：

[profile.release]
opt-level = 3            # 最高优化
debug = false            # 无符号 → 堆栈只有地址
panic = "unwind"
overflow-checks = false  # 整数溢出 → 环绕 wrapping，不 panic

HFT 上线只改一项（常见）：

[profile.release]
panic = "abort"          # ← 关键；其余保持出厂默认即可

二、panic：unwind（出厂默认）vs abort（手动改）

unwind 做什么？（dev / release 出厂默认）

panic 触发后：

  1. 从出错位置逐层回溯栈
  2. 栈上变量自动 Drop 释放资源
  3. 可被 catch_unwind 拦截，程序未必直接退出
  4. 子线程 panic 通常只崩该线程，主线程可继续（abort 则整进程退出）

abort：只有手动配置才有（HFT release 常用）

[profile.release]
panic = "abort"
  • 直接 abort() 杀进程 · 不展开、不 Drop · catch_unwind 无效
  • 任意线程 panic → 整程序退出
unwind（出厂默认） abort（手动改）
Drop 执行 不执行
catch_unwind ✅ ❌
子线程 panic 通常只崩该线程 整进程退出
适用 开发、普通服务 HFT 实盘

HFT 逻辑

致命错误 → 立刻杀进程重启，远比带病运行、脏内存破坏订单簿稳妥。

→ 细节：9.1 §一 · 9.1.3 catch_unwind + demo

三、overflow-checks 整数溢出

→ 完整说明：9.1.4 整数溢出与 wrapping

结论：release 默认溢出 ≠ panic（环绕）；只有手动 overflow-checks = true 才 panic。

场景 裸运算溢出
dev 默认 panic
release 默认 环绕，不崩溃

9.1

.3 catch_unwind 与 panic 模式

← 9.1 panic! · 9.1.2 dev/release 配置 · demo：9.1.3-catch-unwind-demo/

一、核心结论

Cargo 原厂：dev、release 默认都是 panic = "unwind" — abort 须手动改 Cargo.toml → 9.1.2 结论先说。

std::panic::catch_unwind 只在 panic = "unwind" 下生效；panic = "abort" 完全失效。

模式 panic 时 catch_unwind
unwind（dev 默认、release 出厂） 逐层回溯 + 执行 Drop ✅ 可拦截，返回 Result<T, Box<dyn Any + Send>>，程序继续
abort（HFT 生产常用） OS abort()，不展开、不 Drop ❌ 无捕获机会，进程直接被杀死

二、unwind 下完整流程

use std::panic;

fn inner() {
    let _s = String::from("临时资源"); // 实现 Drop
    panic!("出错了");
}

fn main() {
    let ret = panic::catch_unwind(inner);
    if ret.is_err() {
        println!("捕获 panic，程序继续运行");
    }
}

执行顺序（unwind）：

  1. inner 触发 panic → 从 inner 栈帧向上展开
  2. _s 自动 Drop 释放内存
  3. 展开到 catch_unwind 边界 → 停止回溯
  4. panic 信息装入 Err，main 继续执行

catch_unwind = 栈展开的拦截锚点，依赖 LLVM 异常展开（类似 C++ eh_frame）。

三、为什么 abort 下没用？

[profile.release]
panic = "abort"
  1. panic → 跳过全部栈展开，不 Drop、不找捕获锚点
  2. 进程直接系统终止，OS 回收内存
  3. catch_unwind 的拦截代码永远没有执行时机

四、三个拓展

1. 子线程 panic

模式 行为
unwind 子线程 panic 通常只崩该线程（运行时隐式 catch），主线程可继续
abort 任意线程 panic → 整进程崩溃

2. UnwindSafe 约束

被 catch_unwind 包裹的闭包须满足 UnwindSafe：panic 中途对象可能半销毁，Rust 防止捕获后拿到残缺状态引发 UB。

3. 开发 / 生产对照（HFT）

编译配置 catch_unwind Drop 场景
dev (unwind) ✅ 执行 单测、调试、捕获打日志
release (unwind) ✅ 执行 普通后端
release (abort) ❌ 不执行 HFT 实盘、嵌入式

→ profile 总表：9.1.2

debug = true

cargo build --release
RUST_BACKTRACE=full ./target/release/程序

.4 整数溢出：wrapping · panic · saturating

← 9.1.2 dev/release 配置 · demo：9.1.4-overflow-demo/

结论先说

默认 release：整数溢出 ≠ panic，不会崩溃，走环绕回卷；只有手动开 overflow-checks = true，release 溢出才会 panic。

场景 overflow-checks 裸运算溢出
dev 默认 true（默认，常省略不写） panic
release 默认 false（默认，常省略不写） 环绕 wrapping，程序继续跑
release 手动开 true true panic（与 dev 一致）

一、release 出厂默认（overflow-checks = false）

[profile.release]
# overflow-checks = false  ← 默认隐藏，不写也是 false

let mut a: u8 = 0;
a -= 1; // release → a = 255，不崩溃、不 panic

无符号 / 有符号整数加减：默默绕回，等价于 mod 2ⁿ。

示例：u8（0～255）

let mut y: u8 = 255;
y += 1; // release → 0

有符号 i32（补码）

运算 release 环绕结果
-2147483648 - 1 2147483647
2147483647 + 1 -2147483648

二、手动开启溢出检查

[profile.release]
overflow-checks = true

此时 release 与 dev 一致：裸运算溢出 → 直接 panic。

三、三种溢出行为 + 显式 API

# 配置 裸运算溢出
1 dev 默认 panic
2 release 默认 环绕，无 panic
3 release + overflow-checks = true panic

不改全局 Cargo 时，单点控制：

模式 API 行为
wrapping .wrapping_add/sub 强制环绕
saturating .saturating_add/sub 触界停在最值
checked .checked_add/sub 溢出 → None 
0u8.wrapping_sub(1)    // 255
0u8.saturating_sub(1)  // 0
255u8.saturating_add(1) // 255

四、HFT 重点

  1. 生产不要开 overflow-checks = true（性能损耗）。
  2. 订单量、Tick 计数 用 .checked_add() / .checked_sub()，溢出得 None，走风控 — 不靠 panic，也不靠默认绕回。
let x = 1u32;
match x.checked_add(u32::MAX) {
    Some(v) => { /* 正常 */ }
    None => { /* 溢出 → 告警 / 拒单 */ }
}

Result 与可恢复的错误

← 9.1 panic! · 9.3 panic vs Result · demo：9.2-result-demo/

可恢复错误用 Result<T, E>，调用者决定如何处理 — 不必立刻 panic。

一、File::open 返回类型

// File::open("hello.txt") → Result<成功类型, 错误类型>
// 完整：Result<std::fs::File, std::io::Error>
分支 含义
Ok(File) 打开成功，携带文件句柄
Err(io::Error) 失败（不存在 / 权限 / 路径非法等）

Result 标准定义：

enum Result<T, E> {
    Ok(T),
    Err(E),
}

二、单层 match（最简）

use std::fs::File;

let res = File::open("hello.txt");
let file = match res {
    Ok(f) => f,
    Err(e) => panic!("打开失败: {e:?}"),
};

match 必须穷尽 Ok / Err 两分支，编译器强制校验。

三、嵌套 match + error.kind()（书本经典）

需求：不存在 → 自动创建；其余错误 → panic

use std::fs::File;
use std::io::ErrorKind;

let file = match File::open("hello.txt") {
    Ok(f) => f,
    Err(e) => match e.kind() {
        ErrorKind::NotFound => match File::create("hello.txt") {
            Ok(new_f) => new_f,
            Err(create_err) => panic!("创建失败: {create_err:?}"),
        },
        other => panic!("未知打开错误: {other:?}"),
    },
};

e.kind() 是什么？（先搞清这个）

Err(e)  // e 的类型是 std::io::Error（具体 IO 失败信息）
e.kind() // 调用方法 → 返回 std::io::ErrorKind（错误「大类」枚举）
层次 类型 例子
io::Error 完整错误（含 OS 原始码、路径等） "No such file or directory"
.kind() 把上面归类成跨平台统一枚举 ErrorKind::NotFound

为什么用 kind() 而不是直接比字符串？—— Windows / Linux 报错文案不同，ErrorKind::NotFound 在各平台一致，适合写 match。

use std::io::{Error, ErrorKind};

fn show(e: Error) {
    match e.kind() {
        ErrorKind::NotFound => println!("文件不存在"),
        ErrorKind::PermissionDenied => println!("没权限"),
        _ => println!("其它 IO 错误: {e:?}"),
    }
}

关键点

  1. io::Error.kind() -> ErrorKind：系统错误归类为枚举
  2. ErrorKind 带 #[non_exhaustive] → 必须写 other 兜底，不能穷举所有变体

常用 ErrorKind

不是位标志：不是 C 里 errno 那种按位 OR；是 enum 变体，一次 kind() 只返回其中一个类别。

也不是「带数据的变体」：NotFound、PermissionDenied … 都是空标签（unit variant），没有像 Ok(T) 那样括号里再塞数据；表里这些就是固定几种错误大类名字。

谁 有没有详细数据
e: io::Error ✅ OS 错误码、系统文案、{e:?} 里的完整信息
e.kind() → ErrorKind::NotFound ❌ 只表示「属于找不到文件这一类」 
// ErrorKind 大致结构 —— 全是空变体，无附加字段
enum ErrorKind {
    NotFound,
    PermissionDenied,
    AlreadyExists,
    // ...
}

Err(e) => {
    e.kind();              // → 只要类别：NotFound（空标签）
    e.to_string();         // → 具体报错文字
    format!("{e:?}");      // → Debug 完整信息
}
值 含义
NotFound 文件 / 路径不存在
PermissionDenied 无读写权限
AlreadyExists 创建时已存在
TimedOut IO 超时
UnexpectedEof 意外读到 EOF
Other 未归类错误 
// ✅ 一次 match 一个变体
match e.kind() {
    ErrorKind::NotFound => { /* ... */ }
    other => { /* ... */ }
}

// ❌ 不是位运算：ErrorKind::NotFound | ErrorKind::PermissionDenied

四、简化：unwrap_or_else（减少嵌套）

let file = File::open("hello.txt").unwrap_or_else(|e| {
    if e.kind() == ErrorKind::NotFound {
        File::create("hello.txt").unwrap()
    } else {
        panic!("打开异常: {e:?}");
    }
});

Err 时执行闭包 — 生产里比三层 match 更常见。

五、unwrap / expect / ? 对比

写法 行为 适用
match 穷尽分支，完全控制 要区分错误类型
unwrap() Err → panic（固定信息） demo / 确定不会失败
expect("msg") Err → panic（自定义前缀） 同上，信息更清晰
? Err → 提前返回给调用者 函数返回 Result 时传播错误 
fn read() -> Result<String, io::Error> {
    let mut s = String::new();
    File::open("hello.txt")?.read_to_string(&mut s)?;
    Ok(s)
}

9.3

使用 panic! 还是不用 panic!

决定用 panic! 还是返回 Result，本质是在决定：这个失败是“调用者可预期并可能恢复”的，还是“代表 bug / 有害状态，继续运行更危险”的。

对应 demo 项目：00-Book/09-error-handling/9.3-panic-or-result-demo/

默认选择：返回 Result

当错误是“预期可能发生”的（例如用户输入格式错误、文件不存在、网络限流等），更合适的做法是返回 Result，把处理方式交给调用者。

什么时候 panic! 更合适

  • 示例 / 原型 / 测试：用 unwrap / expect 作为占位符，或让测试直接失败
  • 你比编译器知道更多：逻辑上保证必然是 Ok，但编译器无法推断（例如硬编码的合法 IP）
  • 有害状态（harmful state）：假设/契约/不变量被破坏，继续运行可能产生更严重问题
  • 典型例子：越界索引导致标准库 panic（避免潜在安全漏洞）

用类型系统把“有效性”编码进去：Guess

与其在每个地方重复检查 “1..=100”，不如创建一个新类型：

  • 只能通过 Guess::new(value) 构造
  • 构造时统一验证范围
  • 之后函数签名接收 Guess，就能相信值一定合法

如果越界代表调用者的 bug，可以选择在 new 里 panic!，并在 API 文档里说明契约。
