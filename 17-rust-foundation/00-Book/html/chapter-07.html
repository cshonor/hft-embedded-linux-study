一、一个 Package 必备三样东西

# 组成 说明
1 项目根文件夹 整个项目目录
2 Cargo.toml 清单配置，Package 身份证，必填
3 src/ 源码目录，放各类 .rs

附带自动生成：Cargo.lock — Cargo 写入，不用手动建，锁定依赖精确版本；也算 Package 内文件。

Package = 项目根文件夹 + Cargo.toml + src/ 源码 + Cargo.lock

二、Package 和 Crate 别混（层级）

Package Crate
谁管 Cargo rustc
是什么 项目包（构建管理单位） 编译单元（最小编译单位）
数量关系 1 个项目 = 1 个 Package 1 个 Package 里 ≥ 1 个 Crate

Package 里能装几个 Crate

  • 0 或 1 个库 crate（src/lib.rs）
  • 任意多个二进制 crate（src/main.rs、src/bin/*.rs）

Crate 二选一（每个 crate 本身）

入口 类型 产物
src/main.rs binary crate exe
src/lib.rs library crate 库文件，供 use

代码举例 → 7.1.1

标准举例：一个 Package，两个 Crate

my_project/          ← 这整个文件夹 = 1 个 Package = 1 个 Project
├ Cargo.toml         ← Package 配置
├ Cargo.lock         ← 自动生成
└ src/
   ├ lib.rs          ← 库 crate
   └ main.rs         ← 二进制 crate

文件夹 = Package = Project；里面装了 2 个 Crate。

demo → bin_plus_lib/

三、Cargo 硬性规定（官方，必记）

种类 数量限制 来源
library crate 0 或 1 个 仅 src/lib.rs（全局唯一，不能多个）
binary crate 不限 src/main.rs（默认主 bin，至多 1 个）+ src/bin/*.rs（每个文件 = 1 个 exe）

另：至少 1 个 crate（全是 bin、全是 lib、或 lib+bin 均可）。

1. 库 crate：只能 0 个或 1 个

  • 有 src/lib.rs → 本 Package 唯一 1 个 lib crate
  • 不能建第二个 lib.rs，Cargo 不支持一个 Package 多个库 crate
❌ 一个 Package 里多个 lib crate
✅ lib 要么没有、要么仅此一个

想要多个库 → 拆成多个独立 Package，在各自 Cargo.toml 里 path 依赖（如 only_lib/ + user_demo/）。不能在同一 Package 放多个 lib.rs → 7.1.6

2. 二进制 crate：数量不限

三种来源：

来源 说明
src/main.rs 默认主二进制（至多 1 个）
src/bin/xxx.rs 每个 .rs = 独立 exe；10 个文件 = 10 个 bin crate
（无 lib 时）仅上述 bin 纯 exe 项目也合法 
proj/
├ Cargo.toml
└ src/
   ├ lib.rs          // 唯一库 crate（0/1 二选一）
   ├ main.rs         // 主二进制 1 号
   └ bin/
       ├ cli1.rs     // 二进制 2 号
       ├ cli2.rs     // 二进制 3 号
       └ tool.rs     // 二进制 4 号

cargo run              # 多个 bin 时需 default-run 或 --bin（见 multi_bin/Cargo.toml）
cargo run --bin cli1   # 单独跑 cli1，互不干扰

demo → multi_bin/（1 lib + main.rs + bin/cli1 + bin/cli2）

src/bin/ 语义、多工具 vs 微服务、HFT workspace → 7.1.4

一句话

  • Lib：0 或最多 1 个（全局唯一 lib.rs）
  • Bin：≥ 0 个，随便加；main.rs 只是默认的那一个

四、两种最简 Package + 一种扩展

① 只有 exe（无 lib.rs）

demo/
├ Cargo.toml
├ Cargo.lock
└ src/main.rs

→ 1 个 Package，1 个二进制 crate。demo → only_bin/

② 只有库（无 main.rs）

mylib/
├ Cargo.toml
├ Cargo.lock
└ src/lib.rs

→ 1 个 Package，1 个库 crate。demo → only_lib/

③ 扩展：多二进制（src/bin/）

demo/
├ Cargo.toml
└ src/
   ├ lib.rs
   └ bin/cli1.rs …

→ 1 lib + 多 bin。cargo run --bin cli1。demo → multi_bin/

五、Crate Root

crate root = 编译入口，自动成为该 crate 根模块 crate::。

文件 角色
src/main.rs 主 binary crate root；名 = package 名
src/lib.rs library crate root；名 = package 名

六、层级一句话

Package（Project 文件夹）≥ 1 个 Crate → 每个 Crate 从 Crate Root 编译整棵模块树

my_project/  （Package = Project）
 ├── Cargo.toml / Cargo.lock
 └── src/
      ├── main.rs  → binary crate  → exe
      └── lib.rs   → library crate → 库（至多一个）

七、为什么要区分 crate

crate 把能力放在独立命名空间，避免冲突：rand::Rng 与自建 struct Rng 互不混淆。

八、精简笔记

  1. Package = Project 文件夹 + Cargo.toml + src/ + Cargo.lock
  2. Lib crate：0 或 1（只有一份 lib.rs；要多库 → 多 Package）
  3. Bin crate：不限（main.rs 至多 1 个 + src/bin/*.rs 每个文件 1 个 exe）
  4. 一个 Package ≥ 1 个 Crate（编译产物总和）

私有性（privacy）：默认私有，pub 才公开

规则 说明
默认私有 模块内项同模块可访问；模块外不能直接访问
pub 模块或函数标记公有后，才可通过路径从外部访问 
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() { /* … */ }
        fn seat_at_table() {}  // 私有：仅 hosting 内部
    }
}
  • add_to_waitlist：pub → crate 外可 use / 路径调用
  • seat_at_table：无 pub → 只有 hosting 内部能调

模式：对外 pub fn eat_at_restaurant()，内部调私有实现，不暴露细节。

demo：lib 模块树 + main 调公开 API

文件 Crate 内容
src/lib.rs lib root 餐厅 mod front_of_house { … } + pub fn eat_at_restaurant()
src/main.rs bin root use 包名::eat_at_restaurant()

两棵独立模块树；main 不重复声明 front_of_house，只调 lib 已 pub 的 API。

7.3

路径用于引用模块树中的项

← 模块树基础：7.2.1 Crate Root 与模块树 · 私有性：7.2 · 字段 pub：7.2.2 · 分文件 → 7.5

对应 demo（分文件 + 绝对/相对/super/self）：00-Book/07-packages-modules/7.3-paths-demo/

一、核心类比（最容易记）

把 模块树 = 电脑文件夹目录，:: = / 斜杠。

前缀 等价目录符号 含义 路径类型
crate:: /（磁盘根） 从当前 crate 根出发，全局绝对路径 绝对
super:: ../ 跳到父模块 相对
self:: ./ 留在本模块内部 相对
直接写模块名（front_of_house::） 同级文件夹 与当前模块平级的子模块 相对

规则：绝对永远从 crate 根起步；相对永远从当前所在模块起步。

外部 crate 的绝对路径：直接写 库名::，例如 std::collections::HashMap（std 是标准库 crate 名）。

二、模块树（官方 front_of_house 示例）

crate（根）
├── front_of_house
│   └── hosting → add_to_waitlist()
├── back_of_house
│   └── fix_incorrect_order() → cook_order() + super::serve_order()
└── serve_order()              ← crate 根上的函数

三、两种路径详细拆分

1. 绝对路径：crate::xxx::xxx

固定写法：永远 crate:: 开头，不受当前代码所在位置影响。

// 任意文件、任意模块里都能这么写，换目录层级后代码不用改
crate::front_of_house::hosting::add_to_waitlist();

2. 相对路径（随当前代码位置变化）

① 同级直接写模块名

当前代码在 crate 根同级（lib.rs / main.rs 顶层）时，front_of_house 与当前模块同级：

front_of_house::hosting::add_to_waitlist();

换到 back_of_house 模块内部就不能直接写 front_of_house::…，层级变了，需 super::front_of_house::… 或 crate::…。

② super:: 向上找父模块（../）

back_of_house 里的 fix_incorrect_order 要调用根上的 serve_order()：

fn fix_incorrect_order() {
    cook_order();
    super::serve_order(); // super = back_of_house 的父 = crate 根
    // 等价绝对路径：crate::serve_order();
}

多层父：super::super::xxx 往上跳两层祖先模块。

③ self:: 当前模块内找（./）

// 在 back_of_house 内部
self::cook_order(); // 等价直接写 cook_order()

日常几乎可省略 self::，只有同名冲突时才显式加。

四、工程目录 + mod.rs（文件夹写法）

src/
├── lib.rs              // crate 根
├── front_of_house/
│   ├── mod.rs          // pub mod hosting;
│   └── hosting.rs      // pub fn add_to_waitlist() {}
└── back_of_house/
    └── mod.rs          // fix_incorrect_order + 路径示例
  1. lib.rs：pub mod front_of_house; · mod back_of_house;
  2. front_of_house/mod.rs：pub mod hosting;

在 back_of_house/mod.rs 里调用 hosting

// 1. 绝对（万能，换位置不变）
crate::front_of_house::hosting::add_to_waitlist();

// 2. 相对：先 super 到 crate 根，再进同级 front_of_house
super::front_of_house::hosting::add_to_waitlist();

五、pub 隐私与路径联动（衔接 7.2 / 7.2.2）

路径能定位 ≠ 能访问，沿途每一项的可见性都要满足：

写法 效果
mod front_of_house; 无 pub 外部 crate 路径找不到这个模块
pub mod hosting; hosting 对外暴露，路径能索引到
fn add_to_waitlist() 无 pub 路径能定位也调不了（私有）
pub fn add_to_waitlist() 跨模块可调用

结构体字段沿用同一套

pub struct User {
    pub id: u32,   // pub → 跨模块可 u.id 读写
    name: String,  // 私有 → 同模块随便改，跨模块不可见
}

→ 详解 7.2.2 结构体与字段私有性

pub struct vs pub enum

  • pub struct：类型公有，字段默认仍私有（字段须单独 pub）
  • pub enum：类型公有时，变体默认全公有

六、实战怎么选

场景 建议
库项目 lib.rs 优先 crate:: 绝对路径 — 后续调整目录层级不易崩
内部子模块互调 优先 super:: / 相对路径 — 更简洁
main 二进制 两种混用均可

七、跨 Package：无 super / 无相对路径

super、self、相对模块名只在本 crate 内有效。 跨 Package（含 Workspace 成员之间）必须用：

  1. A 的 Cargo.toml 声明 path / 版本依赖
  2. B 的 lib.rs pub mod … 导出
  3. A 里 包名::模块::函数（如 pkg_b::b_mod::hello_b()）

文档 内容
本篇（7.4） 惯用写法 · as · pub use · 嵌套路径 · glob
7.4.1 use 作用域 没有全局 use；lib.rs 不继承；pub use 是模块出口

一、use 核心作用

use = 把完整路径引入当前作用域，生成路径别名，后续简写调用 —— 解决 crate::xxx::yyy::func() 全路径冗长的问题。

// 原始全路径
crate::front_of_house::hosting::add_to_waitlist();

// use 简写
use crate::front_of_house::hosting;
hosting::add_to_waitlist();
要点 说明
use 只改名字可见性 不编译代码、不引入文件；文件进模块树靠 mod
权限 路径上任意节点非 pub，无法 use 导入
作用域 use 仅限当前文件 — 子模块不继承 → 7.4.1

二、Rust 惯用 use 编码规范

1. 函数：导入父模块，保留 模块::函数()

// ✅ 推荐：一眼看出不是本地函数
use crate::front_of_house::hosting;
hosting::add_to_waitlist();

// ❌ 不推荐：add_to_waitlist() 分不清来源
use crate::front_of_house::hosting::add_to_waitlist;
add_to_waitlist();

2. 结构体 / 枚举 / 类型：直接导入类型名

use std::collections::HashMap;
let map = HashMap::new();

三、同名冲突：as 别名

场景：不同模块同名类型（最常见 std::io::Result vs std::fmt::Result）。

方案 1：导入父模块区分（优先）

use std::fmt;
use std::io;

fn a() -> fmt::Result { Ok(()) }
fn b() -> io::Result<()> { Ok(()) }

方案 2：as 自定义别名

use std::io::Result as IoResult;
fn test() -> IoResult<()> { Ok(()) }

四、pub use：重导出（re-export，企业级 lib 必备）

作用域
普通 use 仅当前模块内可用
pub use 对外暴露路径，外部 crate 可直接 use 
// lib.rs 内部
pub use crate::front_of_house::hosting;

// 外部依赖本包时，不必知道 front_of_house 内部结构
use your_crate::hosting;
hosting::add_to_waitlist();

跨 Package（A 调 B）：B 的 lib.rs 用 pub use 导出 API → A 的 Cargo.toml 依赖 B → A 里 use b_crate::xxx。
→ 完整链路 7.3.1 · demo 7.3-cross-package-paths-demo/

五、嵌套路径合并导入

同前缀路径合并；{ self, … } 中 self = 父模块自身：

// 拆分
use std::cmp::Ordering;
use std::io;
use std::io::Write;

// 合并
use std::{cmp::Ordering, io};
use std::io::{self, Write}; // self = std::io 模块本身

六、glob 通配符 *：全量导入公有项

use std::collections::*;
适用 单元测试、脚本、小作用域块
禁止 正式业务代码 — 易冲突、难溯源

demo 在 main.rs 里用 { … } 块演示 glob，限制作用域。

本篇（7.5） mod { } 内嵌 vs mod; 分文件、文件对应规则
7.5.1 mod.rs 里的 mod 与 use mod 挂文件 vs use 简写；domain 三场景

一句话分清两种写法

写法 1：内嵌（书本示例） 写法 2：分文件（工程常用）
语法 mod xxx { … 代码 … } mod xxx; + 独立 .rs / 文件夹
物理 全挤在一个 .rs 文件夹 + 零散 .rs
模块树 完全一样 完全一样

逻辑一模一样，只是代码放在磁盘上的方式不同。

写法 1：全写在同一个文件里（书本，了解即可）

// lib.rs 或 main.rs（crate root）内
mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
    }
    mod serving {
        fn take_order() {}
    }
}

纯 mod 名字 { } 大括号嵌套，不拆磁盘文件。

→ 餐厅完整树见 7.2.1

写法 2：拆成文件夹 + 零散 .rs（日常项目）

src/
├ lib.rs              // crate root
└ front_of_house/
   ├ mod.rs           // front_of_house 模块入口
   ├ hosting.rs
