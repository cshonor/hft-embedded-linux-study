一、一个 Package 必备三样东西

# 组成 说明
1 项目根文件夹 整个项目目录
2 Cargo.toml 清单配置，Package 身份证，必填
3 src/ 源码目录，放各类 .rs

附带自动生成：Cargo.lock — Cargo 写入，不用手动建，锁定依赖精确版本；也算 Package 内文件。

Package = 项目根文件夹 + Cargo.toml + src/ 源码 + Cargo.lock

二、Package 和 Crate 别混（层级）

Package Crate
谁管 Cargo rustc
是什么 项目包（构建管理单位） 编译单元（最小编译单位）
数量关系 1 个项目 = 1 个 Package 1 个 Package 里 ≥ 1 个 Crate

Package 里能装几个 Crate

  • 0 或 1 个库 crate（src/lib.rs）
  • 任意多个二进制 crate（src/main.rs、src/bin/*.rs）

Crate 二选一（每个 crate 本身）

入口 类型 产物
src/main.rs binary crate exe
src/lib.rs library crate 库文件，供 use

代码举例 → 7.1.1

标准举例：一个 Package，两个 Crate

my_project/          ← 这整个文件夹 = 1 个 Package = 1 个 Project
├ Cargo.toml         ← Package 配置
├ Cargo.lock         ← 自动生成
└ src/
   ├ lib.rs          ← 库 crate
   └ main.rs         ← 二进制 crate

文件夹 = Package = Project；里面装了 2 个 Crate。

demo → bin_plus_lib/

三、Cargo 硬性规定（官方，必记）

种类 数量限制 来源
library crate 0 或 1 个 仅 src/lib.rs（全局唯一，不能多个）
binary crate 不限 src/main.rs（默认主 bin，至多 1 个）+ src/bin/*.rs（每个文件 = 1 个 exe）

另：至少 1 个 crate（全是 bin、全是 lib、或 lib+bin 均可）。

1. 库 crate：只能 0 个或 1 个

  • 有 src/lib.rs → 本 Package 唯一 1 个 lib crate
  • 不能建第二个 lib.rs，Cargo 不支持一个 Package 多个库 crate
❌ 一个 Package 里多个 lib crate
✅ lib 要么没有、要么仅此一个

想要多个库 → 拆成多个独立 Package，在各自 Cargo.toml 里 path 依赖（如 only_lib/ + user_demo/）。不能在同一 Package 放多个 lib.rs → 7.1.6

2. 二进制 crate：数量不限

三种来源：

来源 说明
src/main.rs 默认主二进制（至多 1 个）
src/bin/xxx.rs 每个 .rs = 独立 exe；10 个文件 = 10 个 bin crate
（无 lib 时）仅上述 bin 纯 exe 项目也合法 
proj/
├ Cargo.toml
└ src/
   ├ lib.rs          // 唯一库 crate（0/1 二选一）
   ├ main.rs         // 主二进制 1 号
   └ bin/
       ├ cli1.rs     // 二进制 2 号
       ├ cli2.rs     // 二进制 3 号
       └ tool.rs     // 二进制 4 号

cargo run              # 多个 bin 时需 default-run 或 --bin（见 multi_bin/Cargo.toml）
cargo run --bin cli1   # 单独跑 cli1，互不干扰

demo → multi_bin/（1 lib + main.rs + bin/cli1 + bin/cli2）

src/bin/ 语义、多工具 vs 微服务、HFT workspace → 7.1.4

一句话

  • Lib：0 或最多 1 个（全局唯一 lib.rs）
  • Bin：≥ 0 个，随便加；main.rs 只是默认的那一个

四、两种最简 Package + 一种扩展

① 只有 exe（无 lib.rs）

demo/

mylib/

③ 扩展：多二进制（src/bin/）

demo/
├ Cargo.toml
└ src/
   ├ lib.rs
   └ bin/cli1.rs …

→ 1 lib + 多 bin。cargo run --bin cli1。demo → multi_bin/

五、Crate Root

crate root = 编译入口，自动成为该 crate 根模块 crate::。

文件 角色
src/main.rs 主 binary crate root；名 = package 名
src/lib.rs library crate root；名 = package 名

六、层级一句话

Package（Project 文件夹）≥ 1 个 Crate → 每个 Crate 从 Crate Root 编译整棵模块树

my_project/  （Package = Project）
 ├── Cargo.toml / Cargo.lock
 └── src/
      ├── main.rs  → binary crate  → exe
      └── lib.rs   → library crate → 库（至多一个）

七、为什么要区分 crate

crate 把能力放在独立命名空间，避免冲突：rand::Rng 与自建 struct Rng 互不混淆。

八、精简笔记

  1. Package = Project 文件夹 + Cargo.toml + src/ + Cargo.lock
  2. Lib crate：0 或 1（只有一份 lib.rs；要多库 → 多 Package）
  3. Bin crate：不限（main.rs 至多 1 个 + src/bin/*.rs 每个文件 1 个 exe）
  4. 一个 Package ≥ 1 个 Crate（编译产物总和）

7.1

.2 main 如何调用 `a.rs` 里的函数

← 主笔记：7.1 · 前置：7.1.1 bin/lib · demo：7.1-packages-crates-demo · 分文件 → 7.5

口诀

有 lib 过 lib，无 lib 直接 mod 在 main。

一、两种结构对照

结构 1（推荐） 结构 2（纯 bin）
文件 lib.rs + main.rs + a.rs main.rs + a.rs
注册模块 lib.rs 里 mod a; main.rs 里 mod a;
导出 lib.rs 里 pub use a::hello; 不需要
main 调用 use 包名::hello; a::hello();
demo via_lib/ via_main_only/

二、结构 1：lib.rs 中转（工业标准）

proj/
├ Cargo.toml
└ src/
   ├ a.rs
   ├ lib.rs
   └ main.rs
步骤 文件 代码
① 实现 a.rs pub fn hello() { … }
② 注册+导出 lib.rs mod a; · pub use a::hello;
③ 调用 main.rs use proj::hello; · hello(); 
// a.rs
pub fn hello() {
    println!("来自 a.rs");
}

// lib.rs
mod a;
pub use a::hello;

// main.rs
use proj::hello;
fn main() { hello(); }

也可 pub mod a;，则 main 写 use proj::a::hello;。

原因：main.rs 是 bin crate root，不能直接 mod lib 侧的模块树；必须经 lib crate 的 pub 导出。

三、结构 2：纯 binary，main 直接注册

proj/
├ Cargo.toml
└ src/
   ├ a.rs
   └ main.rs

// main.rs — bin crate root
mod a;

fn main() {
    a::hello();
}

无 lib.rs → 只有 一个 bin crate，mod a; 写在 main.rs 即可。

四、三条铁则

# 规则
1 有 lib.rs → lib 里 mod + pub 导出，main 从包名导入
2 无 lib.rs → main 里 mod a;，路径 a::hello()
3 a.rs 函数无 pub → 无论哪种结构都访问不了

五、与 crate 的关系

结构1（两个 crate）                 结构2（一个 crate）
┌──────── bin: main.rs ────┐       ┌── bin: main.rs ──┐
│  use 包名::hello         │       │  mod a;          │
└──────────┬───────────────┘       │  a::hello()      │
           │ use                   └────────┬─────────┘
┌──────── lib: lib.rs ─────┐                │
│  mod a; pub use a::hello │       ┌────────▼─────────┐
└──────────┬───────────────┘       │  a.rs            │
           │                       └──────────────────┘
┌──────────▼───────────────┐
│  a.rs                    │
└──────────────────────────┘

mod a; 对应 src/a.rs 的文件规则 → 7.5

demo

cd ../via_main_only && cargo run # 结构2

一、整体属性

整个 webserver/ = 1 个 Package：

Crate 入口 作用
1 个 lib crate src/lib.rs 业务、路由、工具；统一 pub 导出

│  │  ├ mod.rs
│  │  └ …
│  └ routes/
│     └ mod.rs

└ tests/
   ├ api.rs
   └ api/…

demo → webserver_layout/（无 Actix，结构相同）

二、Crate vs Module（domain 不是独立 crate）

✅ domain 不是独立 crate，只是当前 lib crate 内部的子模块。

层级（从上到下）

Package（webserver/）
└ lib crate（src/lib.rs = 整箱，编译单元）
   └ domain（箱内一格 = 模块，不是箱子）
      └ domain/mod.rs + 各业务 .rs
概念 比喻 说明
crate 整箱 编译最小单元；lib.rs = 1 个 lib 箱，main.rs = 1 个 bin 箱
module 箱内格子 domain / routes / utils 全是 crate 内代码分组

module 永远升不成独立 crate；要独立 crate → 拆成新 Package（新文件夹 + 新 Cargo.toml）。

模块私有性条文 → 7.2

三、三步生效流程（mod + pub）

第一步：domain/mod.rs 收拢文件夹内文件

// src/domain/mod.rs
pub mod email_client;
pub mod new_subscriber;
pub mod subscriber_email;
pub mod subscriber_name;

→ 告诉编译器：这些零散 .rs 都属于 domain 模块。

第二步：lib.rs 把 domain 挂进 lib crate

// src/lib.rs
mod domain;      // 收录进 crate，仅 lib 内部可访问
pub mod domain;  // 加 pub → main / tests / 外部依赖可 use
写法 效果
mod domain; domain 私有 → 只有 lib crate 内部能用
pub mod domain; domain 公开 → main、tests、use 包名::domain

第三步：main.rs / tests 调用

use webserver::domain::email_client::EmailClient;

包名 = Cargo.toml 的 name；路径从 lib 导出的公开模块 进入。

口诀

文件夹成模块靠 mod.rs 收拢内部文件；lib.rs 里 mod 收录进 crate，加 pub 才能外面调用。
mod.rs 里 mod vs use → 7.5.1

四、各目录职责（简表）

路径 角色
lib.rs lib crate root；pub mod domain; 等统一导出
main.rs bin crate root；只组装启动，不写业务
domain/mod.rs 文件夹模块入口；注册 email_client 等
routes/ HTTP 层；调 domain 业务
tests/ 集成测试；use 包名::… 测 lib 公开 API

lib.rs 导出模板

pub mod configuration;
pub mod domain;
pub mod routes;
pub mod startup;
pub mod utils;

pub use startup::run;

五、为什么没有 src/bin/？

写法 何时用
src/main.rs 只要 1 个 exe（单体 REST 后端）→ 常态
src/bin/*.rs 要多个独立 exe 时才建

本项目：1 lib + 1 main，无 src/bin 完全合规。多 bin 范例 → 7.1 §三 · multi_bin/

六、完整调用链

email_client.rs …
      ↑ pub mod …（domain/mod.rs）
domain 模块
      ↑ pub mod domain;（lib.rs / lib crate）
main.rs / tests
      use webserver::domain::email_client::…
      ↓
cargo run → webserver.exe（bin crate 链接 lib crate）

七、何时把 domain 拆成独立 Package（独立 lib crate）？

默认不用拆——同项目内 pub mod domain; 即可。

考虑新 Package（如 domain_core/ + path 依赖）当：

场景 原因
多项目复用 多个 web / CLI Package 共用同一套 domain
独立发布 要上 crates.io，版本与主服务分开
编译隔离 domain 极大，希望单独 cargo test / 单独 CI
依赖边界 domain 不应依赖 Actix/HTTP，物理隔离防循环依赖

拆法：新建文件夹 + Cargo.toml + src/lib.rs → 原项目 [dependencies] domain_core = { path = "../domain_core" }。

日常单体 web：domain 留在 lib 内当模块即可（本笔记范例）。

7.1

.4 `src/bin/`：多 exe、多工具 vs 微服务 vs HFT

← 主笔记：7.1 包与 Crate · demo：multi_bin/ · HFT 架构 → 14.3 Cargo 工作空间

一、.rs 是什么

.rs = Rust 源文件后缀（Rust Source）。
Cargo 按路径规则决定它是 lib、main 还是 src/bin/ 下的独立二进制——不要求文件名叫 main.rs。

二、src/bin/ 目录：每个 .rs → 一个 exe

只要放在 src/bin/ 下，每个 .rs 文件 = 一个独立的 binary crate，编译出各自的 exe：

src/bin/
 ├ cli.rs      → cli.exe     cargo run --bin cli
 ├ migrate.rs  → migrate.exe cargo run --bin migrate
 └ report.rs   → report.exe  cargo run --bin report
要点 说明
文件名 不必叫 main.rs；文件名 = 二进制 crate 名（cli.rs → --bin cli）
入口 每个文件里仍要有 fn main()
共用代码 同 Package 的 lib.rs 可被各 bin use 包名::…

demo → 7.1-packages-crates-demo/multi_bin/

三、没有 src/bin/ 时：默认只有一个 exe

情况 结果
只有 src/main.rs，无 src/bin/ 默认唯一二进制入口 → 编译 1 个 exe
典型例子 Actix-web 后端：只跑一个 web 服务，不必建 src/bin/

→ 见 7.1.3

四、src/bin/ 是干什么的？（不是微服务）

✅ 正确理解：一个 Package 里的「多工具 / 多命令行程序」

集中管理多个独立可执行程序，共用同一套 lib 代码，各自单独运行：

exe 用途示例
main.rs Web 服务 / 主程序
bin/migrate.rs 数据库迁移工具
bin/report.rs 离线报表生成
bin/replay.rs 日志回放调试

→ 像一套工具箱：同一仓库、同一 lib、多个入口，不是按服务拆部署。

❌ 不是：微服务架构

src/bin/（同 Package） 微服务（多 Package 部署）
部署 多个 exe，常在同一机器 / 同一发布包 独立进程、独立部署单元，常不同机器/容器
边界 共享 lib，编译期绑在一起 网络 API、独立生命周期
典型场景 CLI + 服务端 + 批处理脚本 订单服务、行情服务、用户服务各自一个项目

微服务通常 = 多个独立 Package / 仓库 + 独立部署；不是靠在一个项目里多加几个 src/bin/*.rs 就算微服务。

五、HFT 场景：更常用 Workspace，而不是堆 src/bin/

高频交易更倾向 Cargo Workspace：把核心拆成多个独立 Package（crate），统一根 Cargo.toml 管理：

hft-workspace/
├ Cargo.toml          # [workspace] members = [...]
├ hft-core/           # 基础类型、协议、零拷贝工具
├ hft-market-data/    # 行情接入、解码
├ hft-trading-engine/ # 撮合 / 发单引擎（独立 exe）
└ hft-gateway/        # 对外网关（独立 exe）
对比 src/bin/（单 Package 多 exe） Workspace（多 Package）
隔离 弱：同一 Package、同一 lib 边界 强：crate 级依赖边界、可单独编译测试
延迟 / 可靠 适合小工具共用 lib 引擎、行情、核心类型物理拆分，避免无关代码进热路径
依赖 所有 bin 共享同一 Cargo.toml 依赖 各 crate 按需声明依赖（引擎不必拉 web 框架）

HFT 常见做法：

  • 热路径引擎 → 独立 Package，release 优化、依赖最小化
  • 工具链（回放、对账、配置生成）→ 可同 workspace 其他 member，或单独 Package
  • 少用大 Package + 很多 src/bin/ 扛架构拆分；用 workspace + 多 crate 做模块解耦与编译隔离

详解 → 14.3 Cargo 工作空间 · Workspace ≠ 微服务 → 14.3.1 · demo 14.3-hft-workspace-demo/ · demo 14.3-workspace-demo/

7.1

.5 `lib.rs` = 库 Crate 的出口（不是 Package 的出口）

← 主笔记：7.1 · 前置：7.1.1 bin/lib · Workspace 可见性 → 14.3.1

精准结论

lib.rs = 当前这个「库 Crate」的对外接口总出口，不是 Package 的出口。

层级 定义
Package 文件夹 + Cargo.toml（打包 / 构建单位）
Library Crate 一个 Package 最多 1 份 src/lib.rs
lib.rs 只管 本 lib crate 内部 哪些模块/项 pub 对外开放

一、一句话理解

lib.rs 是 库箱子的大门：

  • 箱子内部（order/、domain/、各 .rs 子模块）藏在 crate 模块树里；
  • 想让 crate 外面（同 Package 的 bin、别的 Package、tests）拿到函数/结构体 → 必须在 lib.rs 用 pub / pub use 放行。

示例

mylib/                 ← Package
├ Cargo.toml
└ src/
   ├ lib.rs            ← **lib crate** 出入口（不是 Package 出入口）
   └ order/
      └ mod.rs

src/order/mod.rs：

pub fn create_order() {}

src/lib.rs：

mod order;                       // 收进本 crate，外部不可见
pub use order::create_order;     // 放行：对外暴露
// 或：pub mod order;

外部依赖 mylib 后：

use mylib::create_order;

order/ 文件夹本身不能直接对外——全靠 lib.rs 导出链。

二、lib.rs 只管 Crate，不管 Package 里的二进制

一个 Package 可同时有：

文件 Crate 作用
lib.rs Library crate 代码导出、可被 use
main.rs Binary crate 独立 exe，自有 crate root，不受 lib.rs「管控」

同 Package 里 main 要用 lib 代码：

use 包名::create_order; // bin crate 去引入同 Package 的 lib crate

→ bin 与 lib 是 两个 crate；bin 只能看见 lib 里 pub 出来的项（同 7.1.1 §五）。

三、精简总结
✅ lib.rs → Library Crate 的对外接口清单
❌ lib.rs 不代表 Package 接口；Package 只是文件夹 + Cargo 配置
规则 不加 pub → crate 外不可见；pub / pub use → 对外开放

四、联动 Workspace（A lib ← B bin 依赖）

workspace/
├ package_a/    lib only（lib.rs）
└ package_b/    bin（main.rs，path 依赖 a）

package_b/Cargo.toml：

[dependencies]
package_a = { path = "../package_a" }

B 能用的内容，严格限于 A 的 lib.rs 里 pub 导出的项——A 内部未 pub 的函数/模块，B 完全看不见（编译期报错，不是运行时限制）。

demo → 14.3-packaging-demo（common lib 被 app_bin / feed / trade 链接）

形态 1（链进单 exe）vs 形态 2（多 exe + IPC）→ 14.3.1

五、与 module 的关系（补一句）

  • domain/mod.rs → 收拢 domain 模块内部（见 7.1.3）
  • lib.rs → 收拢 整个 lib crate 对谁公开

三层都要 pub 才能从 crate 外 use 包名::domain::…。

多库误区 → 7.1.6 一个 Package 一个 lib.rs · mod vs pub mod 分文件 → 7.5.3

谁问 答

main.rs 呢？ 另一个 bin crate，不是 lib.rs 的子模块

7.1

.6 一个 Package 只能有一个 `lib.rs`

← 主笔记：7.1 · 7.1.5 lib.rs 是 Crate 出口 · 多库 → 14.3 Workspace

核心死规则（Cargo 硬性语法）

1 个 Package：最多 1 份 src/lib.rs → 最多 1 个 Library Crate。
✅ src/lib.rs — 固定路径、固定文件名，唯一 lib crate 入口
❌ 同一 Package 不能有第二个 lib.rs；Cargo 不识别第二个 lib crate
❌ src/lib2.rs、src/other_lib.rs 不会自动变成第二个 Library Crate

不能塞在同一个 Package 里。 拆成 3 个独立 Package，放进 Workspace：

├ lib_order/          # Package1 → 唯一 src/lib.rs → 库 1
├ lib_market/         # Package2 → 唯一 src/lib.rs → 库 2
└ lib_common/         # Package3 → 唯一 src/lib.rs → 库 3

三个文件夹 = 三个 Package，各自 一份 lib.rs = 三个独立 Library Crate。

# gateway/Cargo.toml 示例
[dependencies]
lib_order = { path = "../lib_order" }
lib_common = { path = "../lib_common" }

二、最大误区：「库模块」≠「库 Crate」

❌ 错：项目里建 order/、market/、common/ 三个文件夹 = 三个库 crate

✅ 对：三个文件夹只是 同一个 lib crate 内部的子模块，全由 唯一 src/lib.rs 管控 → 编译只出 1 个 .rlib。

mypackage/              ← 1 个 Package
├ Cargo.toml
└ src/
   ├ lib.rs             ← 全局唯一 lib 入口 = 只生成 1 个 Library Crate
   ├ order/mod.rs       ← 模块（格子），不是 crate
   ├ market/mod.rs
   └ common/mod.rs

lib.rs：

pub mod order;
pub mod market;
pub mod common;
是什么 编译产物
order / market / common module，代码分组 合在 同一个 lib crate 里
整个 mypackage 的 lib 1 个 Library Crate 1 个 .rlib

外部 use mypackage::order::… — 用的是 一个库 里的 一个模块，不是「第二个库 crate」。

数量 / Package 0 或 1 不限

四、若「强行」加 src/lib2.rs 会怎样？

Cargo 只认 src/lib.rs 为 lib crate root。

若在 lib.rs 写 mod lib2; → 只是 crate 内又一个模块文件，仍是 1 个 lib crate。

7.2

.1 Crate Root 与模块树（Module Tree）

← 主笔记：7.2 模块与私有性 · 餐厅 demo：7.2-modules-privacy-demo · 分文件 → 7.5

Rust 官方教材餐厅案例完整梳理。

一、核心定义

1. Crate Root（箱子根）

src/lib.rs（库 crate）或 src/main.rs（bin crate）= 当前 Crate 的根文件 = 模块树顶层隐形根模块 crate

入口 Crate 类型
src/lib.rs Library crate root
src/main.rs 默认 Binary crate root
src/bin/xxx.rs 独立 Bin crate，各自是自己的 crate root
  • 编译器 从 crate root 扫描整棵模块树
  • root 里代码默认挂在顶层虚拟模块 crate 下
  • 一个 Crate 只有 1 个 crate root

2. Module Tree（模块树）

用 mod 名字 { … } 嵌套声明；所有模块从 crate 向下分叉，像目录树；用 :: 寻址函数 / 结构体 / 子模块。

餐厅代码（写在 crate root，如 src/lib.rs）

mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
        fn seat_at_table() {}
    }
    mod serving {
        fn take_order() {}
        fn serve_order() {}
        fn take_payment() {}
    }
}

生成的模块树

crate                          ← 顶层根（来自 crate root 文件）
 └── front_of_house            ← 一级子模块
     ├── hosting
     │   ├── add_to_waitlist
     │   └── seat_at_table
     └── serving
         ├── take_order
         ├── serve_order
         └── take_payment

二、三条规则（Package / Crate / Module）

# 规则
1 Package：Cargo.toml 项目夹；最多 1 lib + 多 bin；每个 Crate 各自 1 个 crate root、各自 1 棵模块树
2 Crate = 一棵完整模块树；树根 = crate（由 crate root 生成）
3 Module = 树上的节点；不能脱离 Crate；写了 .rs 但不 mod xxx; → 不会进树，编译器忽略

同 Package：lib + main = 两棵树

Package
├ lib crate  → root: lib.rs  → 模块树 A
└ bin crate  → root: main.rs → 模块树 B（互不干扰）

→ 7.1.7 lib + main 双 crate

bin 要用 lib 的模块：不能直接在 main 树里 mod front_of_house，而 use 包名::… 引入 lib 那棵树 里 pub 出来的 API。

三、路径寻址

绝对路径（从 crate::）

crate::front_of_house::hosting::add_to_waitlist();

相对路径（从当前模块）

// 在 front_of_house 模块内部
hosting::add_to_waitlist();

默认私有

模块内函数默认 私有；加 pub 才能跨模块调用 → 7.2 私有性

demo 中 eat_at_restaurant() 通过 front_of_house::hosting::add_to_waitlist() 调用 已 pub 的 函数。

四、拆分到单独文件（逻辑树不变）

  1. src/lib.rs（crate root）：mod front_of_house;

7.2

.2 结构体与字段私有性

← 主笔记：7.2 模块与私有性 · demo：7.2-modules-privacy-demo · 结构体基础 → 5.1

一句话结论

结构体、字段默认全私有：同模块内能读写；跨模块必须字段加 pub 才能访问、修改。

1. 规则拆开讲

Rust 权限最小原则：

# 规则
1 struct 无 pub → 结构体类型仅本模块可见
2 字段天生默认私有，与 struct 是否 pub 无关 
struct User {
    id: u64,
    name: String,
}

① 同一模块内：私有字段随便改

struct User {
    id: u64,
    name: String,
}

fn test() {
    let mut u = User { id: 1, name: "abc".into() };
    u.id = 999;              // ✅ 同模块
    u.name = "新名字".into();
}

私有只限制跨模块；本模块内部无额外限制。

② 跨模块：字段无 pub 不能读写

pub mod user_mod {
    pub struct User {
        id: u64,      // 私有字段
        name: String,
    }
}

fn outer() {
    let mut u = user_mod::User { id: 1, name: "".into() };
    u.id = 100; // ❌ E0616：字段私有
}

字段单独 pub 才允许跨模块读写：

pub struct User {
    pub id: u64,   // 跨模块可读可改
    name: String,  // 仍私有
}

2. 两个高频误区

误区 1：pub struct ≠ 字段 pub

pub struct User 只表示 别的模块能写类型名、能构造（若字段也可见或可 new）；字段默认仍私有，不能直接 u.id = …。

误区 2：封装 — 能读不能改

不公开字段，用 impl 方法 控制：

pub struct User {
    id: u64,
}

impl User {
    pub fn set_id(&mut self, val: u64) {
        self.id = val;
    }
    pub fn get_id(&self) -> u64 {
        self.id
    }
}

外部：u.set_id(123) ✅ · u.id = 123 ❌

→ 方法语法 5.3

3. 与项目分层

层 做法
domain 内部 同模块私有字段随便改
routes 外层 字段 pub，或只暴露 get / set 方法

4. 精简总结

场景 私有字段
同模块 随便读、写、改
跨模块 看不见 / 不能改；字段 pub 才允许外部读写

一、核心类比（最容易记）

把 模块树 = 电脑文件夹目录，:: = / 斜杠。

前缀 等价目录符号 含义 路径类型
crate:: /（磁盘根） 从当前 crate 根出发，全局绝对路径 绝对
super:: ../ 跳到父模块 相对
self:: ./ 留在本模块内部 相对
直接写模块名（front_of_house::） 同级文件夹 与当前模块平级的子模块 相对

规则：绝对永远从 crate 根起步；相对永远从当前所在模块起步。

外部 crate 的绝对路径：直接写 库名::，例如 std::collections::HashMap（std 是标准库 crate 名）。

二、模块树（官方 front_of_house 示例）

crate（根）
├── front_of_house
│   └── hosting → add_to_waitlist()
├── back_of_house
│   └── fix_incorrect_order() → cook_order() + super::serve_order()
└── serve_order()              ← crate 根上的函数

三、两种路径详细拆分

1. 绝对路径：crate::xxx::xxx

固定写法：永远 crate:: 开头，不受当前代码所在位置影响。

// 任意文件、任意模块里都能这么写，换目录层级后代码不用改
crate::front_of_house::hosting::add_to_waitlist();

2. 相对路径（随当前代码位置变化）

① 同级直接写模块名

当前代码在 crate 根同级（lib.rs / main.rs 顶层）时，front_of_house 与当前模块同级：

front_of_house::hosting::add_to_waitlist();

换到 back_of_house 模块内部就不能直接写 front_of_house::…，层级变了，需 super::front_of_house::… 或 crate::…。

② super:: 向上找父模块（../）

back_of_house 里的 fix_incorrect_order 要调用根上的 serve_order()：

fn fix_incorrect_order() {
    cook_order();
    super::serve_order(); // super = back_of_house 的父 = crate 根
    // 等价绝对路径：crate::serve_order();
}

多层父：super::super::xxx 往上跳两层祖先模块。

③ self:: 当前模块内找（./）

// 在 back_of_house 内部
self::cook_order(); // 等价直接写 cook_order()

日常几乎可省略 self::，只有同名冲突时才显式加。

src/
├── lib.rs              // crate 根
├── front_of_house/

│   └── hosting.rs      // pub fn add_to_waitlist() {}
└── back_of_house/

  2. front_of_house/mod.rs：pub mod hosting;

// 2. 相对：先 super 到 crate 根，再进同级 front_of_house

五、pub 隐私与路径联动（衔接 7.2 / 7.2.2）

7.3

.1 跨 Package 路径与 Workspace 依赖

← 同 crate 内路径：7.3 路径 · path 依赖：7.1.1 · Workspace：14.3 · 字段 pub：7.2.2

对应 demo：00-Book/07-packages-modules/7.3-cross-package-paths-demo/

一句话结论

跨 Package 不能用 super::、不能用相对路径！super、self 只限制在【当前同一个 Crate 内部】；跨包靠「Cargo 依赖 + 对方包 pub 导出 + 包名:: 绝对路径」调用。

范围 可用路径
同 crate 内 crate:: · super:: · self:: · 相对模块名
跨 Package / 跨 crate 包名::（如 std:: · pkg_b::）— 无 super

场景：Workspace 里 A 调 B

workspace/
├── Cargo.toml          ← members = ["pkg_a", "pkg_b"]
├── pkg_b/              ← Package B（被依赖的库）
│   ├── Cargo.toml
│   └── src/
│       ├── lib.rs      ← lib crate 出口
│       └── b_mod.rs
└── pkg_a/              ← Package A（调用方）
    ├── Cargo.toml
    └── src/main.rs

pkg_a 与 pkg_b 是两个独立 Crate、两棵互不连接的模块树 — 不在同一棵树下，super 摸不到对方。

步骤 1：pkg_b 向外暴露（lib.rs 做 pub 导出）

pkg_b/src/b_mod.rs：

pub fn hello_b() {}

pub struct Data {
    pub val: i32,
}

pkg_b/src/lib.rs（只有在这里 pub，外面才能看见）：

pub mod b_mod;
写法 结果
pub mod b_mod; pkg_a 可 pkg_b::b_mod::…
mod b_mod;（无 pub） pkg_a 永远找不到 b_mod → 编译报错

零散 .rs 文件不会自动对外 — 必须在 B 的 lib.rs 用 pub mod 放行。

步骤 2：pkg_a 的 Cargo.toml 声明依赖

[dependencies]
pkg_b = { path = "../pkg_b" }

没有这行，Rust 不会链接 pkg_b，代码里写 pkg_b::… 也无效。

Workspace 根 Cargo.toml 还需：

[workspace]
members = ["pkg_a", "pkg_b"]
resolver = "2"

步骤 3：pkg_a 里调用 — 只用 包名:: 绝对路径

pkg_a/src/main.rs：

fn main() {
    pkg_b::b_mod::hello_b();
    let d = pkg_b::b_mod::Data { val: 1 };
    println!("{}", d.val);
}

或先 use 再短名：

use pkg_b::b_mod::{hello_b, Data};

fn main() {
    hello_b();
    let d = Data { val: 1 };
}

关键纠正

❌ 跨 Package 不能这样写

super::pkg_b::b_mod::hello_b();  // 编译错误

super = 找当前 Crate 的父模块。pkg_a、pkg_b 是两棵独立模块树，不是父子关系。

同理：front_of_house::… 这类相对模块名也只在本 crate 内有效。

✅ 跨包统一写法

来源 路径前缀
标准库 std::collections::HashMap
Workspace 成员 pkg_b::b_mod::hello_b()
crates.io serde::Serialize

完整规则三条

  1. B 包内部：零散 *.rs → 在 B 的 lib.rs pub mod xxx; 对外放行
  2. A 包配置：A 的 Cargo.toml 加 path / 版本依赖 B
  3. A 包调用：use pkg_b::b_mod; 或直接 pkg_b::b_mod::func()

同 Package 内 bin 调 lib（use 包名::…）→ 7.1.7
非 Workspace 的跨项目 path 依赖 → 7.1.1 §六（user_demo/）

结构体跨包：沿用 7.2.2 的 pub 链

// pkg_b/b_mod.rs
pub struct Data {
    pub val: i32,   // 字段也要 pub，A 才能 Data { val: 1 }
    name: String,   // 私有 → A 不能直读，需 getter
}

必须同时满足：

  • struct 加 pub
  • 需要外部读写的字段加 pub
  • 模块经 lib.rs 的 pub mod b_mod; 导出

同 crate super / self / 相对路径 / crate::
跨 Package Cargo 依赖 + 包名:: 绝对路径

7.4

.1 `use` 作用域：仅限当前文件，没有全局 `use`

← 主笔记：7.4 use / pub use · use vs pub use 场景：7.4.2 · mod.rs 场景：7.5.1

对应 demo：7.5-split-modules-demo/（lib.rs 与 domain/ 注释对照）

一句话

所有 use 只作用在「当前写 use 的这个文件」的作用域；没有全局生效的 use；lib.rs 里的 use 也不能自动全项目通用。

1. 在某个文件夹的 mod.rs 写 use

只在 这个 mod.rs 文件内部 生效；同目录别的 .rs 用不了这个别名。

src/domain/
├── mod.rs
└── user.rs

domain/mod.rs：

pub mod user;
use self::user::UserEntity; // 仅限 mod.rs 本文件能简写 UserEntity

user.rs 里面 不能直接写 UserEntity 当别名（若指的是 mod.rs 导入的那个简写），必须在本文件自己 use 或写全路径。

2. 根目录 lib.rs 写 use

也 只在 lib.rs 自身生效，子模块全部不继承。

lib.rs：

pub mod domain;
use std::collections::HashMap; // 只有 lib.rs 本文件能用 HashMap 这个短名

domain/mod.rs、user.rs 想用 HashMap，必须各自再 use std::collections::HashMap;。

3. 唯独 pub use 不一样（企业项目重点）

作用
普通 use 仅限本文件内部简写
pub use 把名字提升到当前模块的对外 API；别的文件/别的包可通过模块路径引入 
// domain/mod.rs
pub mod user;
pub use user::UserEntity;

外层 lib.rs 或别的模块：

use crate::domain::UserEntity; // 得益于 pub use，不用写 domain::user::UserEntity

pub use 不是全局 — 是把类型挂到当前模块的出口；外部仍须自己 use crate::domain::UserEntity。

4. 不存在「一处 use 全工程受用」

Rust 没有 C 语言 #include 式全局导入。没有任何写法在一处 use 后让整个 Package 自动可用。

极简总结

# 规则
1 use xxx：仅限当前文件简写，出了文件失效
2 pub use xxx：暴露到本模块出口，别人经模块路径 use
3 没有 Package 级全局 use

pub mod user;

// domain/user.rs

// 或 use crate::domain::user::UserEntity;（若在本文件引用自己模块的类型用全路径）

一、核心区分

写法 当前模块内 同 crate 其他 mod crate 外 / 别的 Package
use …; ✅ 简写可用 ❌ 看不到这个别名 ❌
pub use …; ✅ 简写可用 ✅ 经模块路径 use（如 crate::scanner::Token） ✅ 经 包名::… 路径 use

1. use（不带 pub）

只在当前文件 / 当前模块内简化路径、导入名字；外部模块、其他 crate 看不到这个简写。

2. pub use（带 pub）

不仅当前模块能用，还把名字提升到当前模块的出口（重导出 re-export）—— 外部可通过模块路径访问，同时起到「路径上浮、少写一层」的作用。

普通 use = 拿过来自己用；pub use = 拿过来，再转手分享给别人用。

7.5

.1 `mod.rs` 里的 `mod` 与 `use`

← 分文件语法：7.5 · use 详解：7.4 · 工程范例：7.1.3 Actix 目录

对应 demo：7.5-split-modules-demo/src/domain/（与 front_of_house/ 并列）

一句话

mod.rs 里写 use = 在当前模块内部偷懒简写路径，不用每次写一长串全路径。

关键字 管什么
mod 挂靠子文件、搭建模块树（没有它，.rs 不会被纳入编译）
use 在本文件省事调用代码（只优化写法，不改变模块树）

两件事互不冲突，所以 mod.rs 里经常同时出现 pub mod xxx; + use xxx::yyy;。

工程真实例子：domain/mod.rs

目录：

src/domain/
├── mod.rs
├── user.rs
└── order.rs

domain/mod.rs

// 第一步：mod 把同目录文件挂进模块树（必写）
pub mod user;
pub mod order;

// 第二步：use 在当前 domain 模块内简写（方便本 mod.rs 里的代码）
// 若同时要对外导出，一条 pub use 即可（内部 + 外部都能用短名）：
pub use user::UserEntity;
pub use order::OrderEntity;

pub fn check() {
    let u = UserEntity::new();
    let o = OrderEntity::new();
    let _ = (u, o);
}
行 作用
pub mod user; 加载 user.rs，注册子模块 — 没有这行 user.rs 等于作废
pub use user::UserEntity; 本 mod.rs 内简写 + 对外重导出 — 不必再写 use self::user::UserEntity（两者同名会冲突）

仅内部用、不对外导出时，写普通 use self::user::UserEntity; 即可。

两个关键字本质

mod use
职责 文件 ↔ 模块绑定，建模块树 当前文件的名字简写
影响编译单元 ✅ 决定哪些 .rs 进树 ❌ 不引文件、不改树结构
可见性 配合 pub mod 控制对外暴露 路径须全 pub 才能 use

三种常见在 mod.rs 写 use 的场景

场景 1：子模块互相调用（最常用）

domain/user.rs 要引用 order 里的类型：

use crate::domain::order::OrderEntity;

pub struct UserEntity;

impl UserEntity {
    pub fn new() -> Self {
        let _ = OrderEntity::new();
        Self
    }
}

场景 2：pub use 对外收拢 API（lib / mod.rs 高频）

// domain/mod.rs
pub mod user;
pub mod order;

pub use user::UserEntity;
pub use order::OrderEntity;

pub use 同时在本 mod.rs 内提供短名、对外重导出 — 不必再写 use self::user::UserEntity（同名会 E0252 冲突）。

外部：use your_crate::domain::{UserEntity, OrderEntity}; — 不必知道内部 user.rs / order.rs 文件夹结构。

→ 重导出详解 7.4 §四

场景 3：引入第三方 Package

// domain/mod.rs
use serde::Serialize;

crates.io 依赖的 Package，靠 use 拉进当前文件作用域。

破除误区
❌ 写了 pub mod a;，当前文件就能直接用 a 里的类型名
✅ pub mod a; 只是注册模块；想要简写，必须额外 use（或写全路径 a::Type）

极简总结

  • mod：建档、挂文件
  • use：拿名字、省代码

所有 .rs（包括各个 mod.rs）里 既有 mod 又有 use 是常态。

use 不跨文件 → 7.4.1 use 作用域 · pub mod ≠ 自动导入 → 7.5.2 · 逐个 mod vs 批量宏 → 7.5.4

7.5

.2 `pub mod user;` ≠ `use`：登记 vs 收拢

← 7.5.1 mod.rs 里的 mod 与 use · 7.4.1 use 仅限当前文件

对应 demo：7.5-split-modules-demo/src/domain/

两句大白话

写法 干什么
pub mod user; 登记注册 — 把 user.rs 挂进模块树，生成路径 domain::user
pub use user::UserEntity; 名字上浮 — 把类型提到 domain 出口，外面可 domain::UserEntity

二者都不能替同目录别的 .rs 自动导入名字。

目录

domain/
├── mod.rs
├── user.rs
└── order.rs

1. pub mod user;（登记注册）

写在 domain/mod.rs：

pub mod user;
# 作用
1 告诉编译器：把同目录 user.rs 编入 domain 模块树
2 pub → 外部可通过 crate::domain::user 访问该子模块
3 只注册文件、生成路径 — 不会给同文件夹所有 .rs 自动导入名字

order.rs 想用 user 里的类型，必须自己手写 use：

use crate::domain::user::UserEntity;

pub mod user; = 挂靠文件、建档；≠ 给兄弟文件发通行证。

2. pub use user::UserEntity;（提升到 domain 出口）

pub mod user;
pub use user::UserEntity;
路径
原本 domain::user::UserEntity
pub use 后 名字上浮到 domain 一级 → use crate::domain::UserEntity;

企业项目常用：内部层级藏起来，对外收拢 API。

pub use 是把名字挂到当前模块（domain）的出口；别的文件仍须自己 use crate::domain::UserEntity — 不是全局自动可用（→ 7.4.1）。

3. 最大误区纠正
❌ pub mod user; 写完，本文件夹所有 .rs 自动能 use user::…
✅ 每个 .rs 都是独立作用域 — 谁想用谁自己 use
  • mod.rs：可以 use self::user::UserEntity; 或靠 pub use 短名
  • user.rs / order.rs：不受 mod.rs 里 pub mod 影响，不会自动导入

极简总结

# 规则
1 pub mod user;：挂载 user.rs 进模块树（建档）
2 pub use user::X;：把 X 提到当前 domain 模块出口（收拢接口）
3 同目录别的 .rs，二者都不能帮它省掉自己的 use

实操：order.rs

// 哪怕 mod.rs 写了 pub mod user，这里仍要手写路径
use crate::domain::user::UserEntity;

pub struct OrderEntity;

impl OrderEntity {
    pub fn with_user(_user: &UserEntity) -> Self {
        Self
    }
}

若 mod.rs 还有 pub use user::UserEntity，order.rs 仍可选择：

  • use crate::domain::user::UserEntity;（走子模块路径），或
  • use crate::domain::UserEntity;（走 pub use 上浮后的出口）

两种都对；都必须在本文件自己写 use。

7.5

.3 `lib.rs` 里 `mod` vs `pub mod`：私有登记 vs 对外开放

← 7.5 分文件 · 7.1.5 lib.rs 是 Crate 出口 · 7.5.2 登记 vs 收拢

对应 compile-fail demo：7.1-packages-crates-demo/bin_plus_lib/compile_fail/private_mod/

结论（先给你）

完全没错。 术语用 crate、mod；在 lib.rs 写 mod 名字; 还是 pub mod 名字;，就是在区分「只给本 crate 内部用」和「允许 crate 外访问」。

一、核心规则

在 lib.rs（lib crate 的 root） 里：

写法 编译器 本 crate 内其他 mod crate 外（bin / 别的 Package / tests）
mod 文件夹名; ✅ 识别、正常编译 ✅ 可访问（路径如 crate::helper::…） ❌ 看不见
pub mod 文件夹名; ✅ 识别、正常编译 ✅ 可访问 ✅ 可 use 包名::文件夹名::…

1. 只写 mod 名字;（不带 pub）

  • 作用：告诉编译器把该文件夹/文件挂进模块树，代码正常编译；同 crate 里的 scanner、parser 等可以调用。
  • 限制：外部（其他 crate、依赖你的 bin）访问不到 — 相当于「crate 内私有模块」。

2. 写 pub mod 名字;（带 pub）

  • 编译器同样识别、正常编译。
  • 允许 crate 外 通过 use 包名::模块名::… 访问该子模块。

这和 7.1.5 一致：lib.rs 是 library crate 的大门；不加 pub 的 mod，外面永远进不来。开门之后还要在子模块里 pub 成员 — 见 7.5.6。

二、clox 风格举例

目录（单 Package、一个 lib crate）：

src/
├── scanner/mod.rs
├── helper/mod.rs    # 工具辅助，只想内部用，不对外暴露
└── lib.rs

示例 1：私有模块（只内部用，对外隐藏）

lib.rs：

mod helper;        // 不带 pub — crate 内可见，crate 外不可见

pub mod scanner;   // 对外公开 scanner 子模块
✅ 编译器识别 helper；同 crate 的 scanner、parser 等可 use crate::helper::util_func
❌ 外部代码、别的 crate 无法 use my_clox::helper::…

示例 2：公开模块（允许外部使用）

pub mod helper;
pub mod scanner;
✅ 编译器识别 + crate 外 可 use my_clox::helper::…

三、模块内部的可见性（避坑）

父模块在 lib.rs 里写成 mod helper;（私有） 时，helper/mod.rs 里还要再分两层：

成员写法 谁能用
fn inner_func() {} 仅 helper 内部
pub fn util_func() {} 同 crate 任意 mod（须写路径 / use）
子模块 mod inner; 仅 helper 内；要跨 mod 用 → 子模块里再 pub

helper/mod.rs 示例：

// 同 crate 里其他模块可以调用（scanner 等）
pub fn util_func() {}

// 仅 helper 模块内部能用
fn inner_func() {}

要点：lib.rs 的 mod / pub mod 管的是 子模块整棵子树是否对 crate 外开放；子树里每个函数、结构体、字段仍各自遵守默认私有 + pub 规则 → 7.2、7.2.2。

四、和 pub use 联动

情况 结果
lib.rs 里 mod helper;（私有） 即使 helper/mod.rs 里写 pub use xxx::Y，crate 外依旧看不到 — pub use 只能把名字抬到 当前模块出口；父模块若私有，出口在 crate 边界外不可达
想对外只暴露一个函数、不暴露整个 helper 模块 lib.rs：mod helper; + pub use helper::util_func; → 7.1.5 示例

pub use 详解 → 7.4.2 use vs pub use · 与 pub mod 分工 → 7.5.2

五、compile-fail 验证

compile_fail/private_mod/：

lib.rs：

mod math;   // 私有 — 不 pub

math/mod.rs 里有 pub fn add(…)，但 模块 math 本身未从 lib 出口放出。

main.rs（另一个 bin crate，依赖本 lib）：

use private_mod_fail::math::add;  // ❌ 编译错误：math 是私有模块

→ 函数 add 在 math 里虽是 pub，子模块未 pub mod 登记到 crate 根，crate 外仍不可见。

一句话总结

目标 lib.rs 写法
只让编译器识别、仅本 crate 内部用、不让外部访问 mod 名字;
需要对外开放，允许别处 use 包名::名字::… pub mod 名字;

分文件时 mod 名字; 只登记路径、不自动 use → 7.5.2 · 顶层 vs 子 mod.rs 何时 pub mod → 7.5.5 · 解释器多模块工程 → Crafting Interpreters clox 笔记

7.5

.4 `mod.rs` 逐个声明 vs 宏批量：没有标准魔法

← 7.5 分文件 · 7.5.1 mod 与 use · 7.4.2 use vs pub use

结论（先给你）

Rust 标准语法没有「一行批量导入所有 .rs」的魔法，只能一个个写 mod 文件名;。 想少写重复代码，要靠第三方宏（automod、mods）—— 可选，生产代码仍以手写 mod 为主。

一、标准写法：mod.rs 里逐个声明（99% 项目）

目录（clox scanner 风格）：

src/scanner/
├── mod.rs
├── token.rs
├── lex.rs
└── error.rs

scanner/mod.rs

// 1. 逐个声明同级 .rs（必须写，否则编译器不纳入模块树）
mod token;   // → token.rs
mod lex;     // → lex.rs
mod error;   // → error.rs

// 2. 内部简写（可选，仅本文件）
use self::token::{Token, TokenType};
use self::lex::scan;

// 3. 对外重导出（可选，推荐）
pub use token::{Token, TokenType};
pub use lex::scan;
要点 说明
每个 .rs 一行 mod 名字; 没有例外；编译器不会自动扫描目录
顺序 无所谓
mod vs pub mod 不加 pub = 子模块仅 crate 内经路径访问；pub mod = 外部可 scanner::token → 7.5.3
最佳实践 优先 pub use 暴露 API，少 pub mod 内部文件（封装更好）→ 7.4.2

二、可复制 mod.rs 模板（照着填）

把 scanner / token / lex / error 换成你的模块名即可：

//! scanner 模块入口 — 登记子文件 · 内部 use · 对外 pub use

// ── 1. 登记：每个同级 .rs 一行 mod（标准写法，必会）──
mod token;
mod lex;
mod error;

// ── 2. 内部：简化本 mod.rs 里的路径（可选）──
use self::token::{Token, TokenType};
use self::lex::scan;

// ── 3. 对外：重导出必要 API（推荐，不暴露文件结构）──
pub use token::{Token, TokenType};
pub use lex::scan;

// ── 4. 模块级入口（可选）──
pub fn scan_source(source: &str) -> Vec<Token> {
    scan(source)
}

子文件 token.rs 等 里要用兄弟模块的类型，仍须各自 use crate::scanner::lex::… 或全路径 — mod.rs 的 use 不继承 → 7.4.1

1. mods — 批量写 mod，仍要列名字

    // 私有（默认）— 展开为 mod token; mod lex; mod error;

    // pub token, lex;

mod token;
mod lex;
mod error;

2. automod — 按目录自动发现 .rs（常见于测试）

不用逐个列名字；宏扫描目录下所有 .rs（排除 mod.rs / lib.rs / main.rs），展开成一堆 mod xxx;。

Cargo.toml（测试目录常用 dev-dependency）：

[dev-dependencies]
automod = "1.0"

// 展开 → mod issue1; mod issue2; …

automod::dir!(pub "tests/regression");
优点 缺点
丢新 .rs 进目录即参与编译，适合回归测试集 需依赖；精细控制每个模块可见性较难；路径相对 Cargo 根，和 mod.rs 同目录场景要设计好包一层

→ crates.io/automod（dtolnay）

结论（先给你）

pub mod 语法到处都能写，合法。 但写在哪儿、推不推荐，取决于位置：

  • 顶层 lib.rs：pub mod 文件夹; → 高频、必备
  • 子目录 mod.rs 里对同级 .rs：mod 名字; + pub use 收拢 → 标准；pub mod token; → 极少用、破坏封装

基础目录

一、核心问题：pub mod 能不能在子 mod.rs 里写？

能写，完全合法。 只是和顶层 lib.rs 场景不同、推荐度不同。

二、位置 1：顶层 lib.rs — pub mod 目录名; 非常常用，必写

作用

把一整个文件夹模块挂进 crate 树，并决定是否对 crate 外 开放。

clox 标准写法

// src/lib.rs
pub mod scanner;   // 公开 scanner 整棵子树
pub mod parser;
// pub mod ast;
// pub mod chunk;
// pub mod vm;

解读

写法 效果
pub mod scanner; 本 crate 内外都能走 crate::scanner::… / 包名::scanner::…
mod scanner;（无 pub） 仅 crate 内 可访问；外部 crate、依赖你的 bin 进不来

→ 业务一级模块（scanner / parser / vm…）在 lib.rs 大量 pub mod 是正常标配 → 详见 7.5.3

内部只想 crate 自用、不对外暴露的辅助模块（如 helper）→ mod helper; 即可。

三、位置 2：子目录 mod.rs — 对同级 .rs 尽量不用 pub mod

语法合法，但不推荐

// src/scanner/mod.rs
pub mod token;   // 合法，但日常少这么写

效果

外部可以直接摸到内部文件名：

use crate::scanner::token::Token;   // 多一层 token，且绑死文件结构

为什么不推荐？

问题 说明
破坏封装 token.rs、lex.rs 是内部实现细节；pub mod token 等于把目录结构暴露出去
重构成本高 改文件名、合并/删除 token.rs，所有 scanner::token::… 调用方全炸
路径啰嗦 调用方多写一层 .token::

四、子 mod.rs 的正确做法（业界规范）

规则

  1. 同级 .rs → mod 名字;（不带 pub），隐藏内部文件
  2. 要对外的类型/函数 → pub use 重导出到当前模块顶层

标准示例（照着写）

// src/scanner/mod.rs

// 第一步：登记同级文件 — 私有，外部看不到 token、lex 这两个子模块路径
mod token;
mod lex;

// 第二步：只导出 API，不导出文件结构
pub use token::{Token, TokenType};
pub use lex::scan_source;

外部使用

use crate::scanner::Token;        // 简洁
use crate::scanner::scan_source;

看不到内部有 token.rs 这件事 — 以后随便改内部拆分，只要 pub use 不变，外部不用动。

→ pub use 详解 7.4.2 · 模板 7.5.4

五、子 mod.rs 里什么时候才真的写 pub mod？

少数场景：当前目录下还有嵌套子文件夹，且这个子文件夹本身要对外当作独立模块。

scanner/
├── mod.rs
├── token.rs
└── utils/           # 嵌套子文件夹
    ├── mod.rs
    └── format.rs

若希望外部能直接 crate::scanner::utils::…：

// scanner/mod.rs
mod token;
mod lex;

pub mod utils;       // 嵌套文件夹要对 crate 外当独立模块 → 才用 pub mod
pub use token::{Token, TokenType};
pub use lex::scan_source;
情况 写法
同级单个 .rs（token.rs、lex.rs） mod 即可，不要 pub mod
嵌套子文件夹且要对 crate 外开放子树 pub mod 子文件夹;
嵌套子文件夹仅 scanner 内部用 mod utils;

普通单层级拆文件，不要在子 mod.rs 里 pub mod 单个rs文件名。

六、背诵表

书写位置 写法 频率 适用场景
顶层 lib.rs pub mod 文件夹; 🔴 高频必写 开放一级业务模块（scanner / parser / vm…）
顶层 lib.rs mod 文件夹; 🟡 偶尔 仅 crate 内用的 helper / internal
子 mod.rs（同级 .rs） mod 文件名; 🟢 标准 管理内部拆分，隐藏实现
子 mod.rs（同级 .rs） pub mod 文件名; ⚫ 极少、不推荐 暴露内部文件结构
子 mod.rs（嵌套子文件夹） pub mod 子文件夹; 🟡 偶尔 多层目录，子文件夹对外也是独立模块
子 mod.rs（任意） pub use …; 🟢 标准 对外暴露内容，不暴露文件路径

7.5

.6 `pub mod` 只开门：`pub` 成员 / `pub use` 才拿物

← 7.5.3 lib.rs mod vs pub mod · 7.5.5 两位置何时 pub mod · 7.4.2 use vs pub use

对应 compile-fail：7.1-packages-crates-demo/bin_plus_lib/compile_fail/private_mod/（模块私有 vs 项 pub）

结论（先给你）

  1. lib.rs 里 pub mod xxx; 只是「开放模块入口」 — 允许别人进入这个模块路径，不等于里面任何东西都能调。
  2. 想让外部调用函数 / 结构体 / 枚举，必须在子模块里用 pub 修饰该项（或 pub use 重导出）；只开门、内部全私有 → 编译不报错，但外部调用时报错（私有项）。
  3. 模块内部完全不对外暴露任何东西时，pub mod 失去实际意义（合法空壳）。

一、层级权限：开门 vs 拿物

层级 写法 比喻
crate 根 lib.rs pub mod scanner; 开门 — 外部能走到 scanner 这一层
子模块内 pub fn scan() / pub struct Token 把东西拿出来 — 外部能调用具体 API
子模块内 pub use token::Token; 把子文件里的东西提到门口 — 同上，路径更短

只开门、不放东西：门能打开，里面啥也用不了 — 无「多余」编译错误，仅无实用价值。

三、pub mod 与内部 pub / pub use 的关系

1. 两层权限要都满足

外部要 use crate::scanner::Token，需要：

lib.rs:     pub mod scanner;     ← 子模块对 crate 外可见（若从别的 crate 用，还要这一层 pub mod）
scanner:    pub struct Token      ← 或 pub use token::Token
token.rs:   pub struct Token      ← 源头也要 pub（pub use 只能重导出已是 pub 的项）

任一层缺 pub，路径在那一层就断掉。

2. 两种暴露内容的方式（可单独用、可组合）

方式 写法 何时用
A. 直接 pub 成员 pub fn scan() / pub struct X 写在 mod.rs 简单模块、逻辑集中在一个文件
B. pub use 重导出 mod token; + pub use token::Token; 拆多个 .rs，隐藏文件结构

不是「写了 pub mod 就必须 pub use」— pub use 只是拆文件后的便捷收拢方案。

3. 误区纠正
❌ pub mod scanner 一开，里面自动全公开
❌ 必须用 pub use，不能直接 pub fn
✅ 只 pub mod、内部全私有：编译通过，外部调私有项才报错
✅ 想让模块有实际用途，必须在模块内 pub 项或 pub use

4. 反向：mod 私有模块 + 内部 pub 项

lib.rs：mod math;（私有模块）

math/mod.rs：pub fn add() { … }

  • 同 crate 内：crate::math::add() ✅
  • 别的 crate：use mylib::math::add ❌ — 模块本身未从 lib.rs pub mod 放出

→ 7.5.3 §五 compile-fail

标准搭配（有实际意义）

lib.rs — 开放一级目录：

各子 mod.rs：

// lib.rs

// helper/mod.rs
mod inner;

  • ✅ 整个 crate 能编译
  • ❌ 外部永远调不到 helper 里任何东西 — pub mod helper 纯属多余

若 helper 仅 crate 内用 → lib.rs 写 mod helper; 更合适。
