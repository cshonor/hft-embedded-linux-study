二、递归类型报错 + Cons 链表（完整）

1. 报错原因：无限递归，算不出大小

Rust 要求栈上类型必须 Sized，编译期要确定占用字节数。

错误代码

enum List {
    Cons(i32, List), // ❌
    Nil,
}

拆解：

  • Cons = i32 + List
  • 内层 List 又可能是 Cons(i32, List) …
  • 大小无限膨胀 → 编译器永远算不出 → 报错

形象理解：盒子套盒子，没有尽头，没法确定单个盒子多大。

2. 用 Box<T> 修复（标准解法）

enum List {
    Cons(i32, Box<List>), // ✅ 指针宽固定
    Nil,
}

use List::{Cons, Nil};
let list = Cons(1, Box::new(Cons(2, Box::new(Nil))));

为什么 Box 能解决？

  1. 指针本身大小固定（64 位下 8 字节）
  2. Cons = i32 + Box<List> → 整体 Sized
  3. 下一节点在堆上，栈上只留指针

内存分布

栈：Cons 实例（i32 + 指向堆的指针）
堆：指针 → 下一个 List 节点（可能又是 Cons…）

层层节点在堆上，打破栈上无限递归。

业务列表优先 Vec<T>；Cons 链表用于学习递归、Box、内存布局。→ demo：cargo run

← 15.1 Box hub · 15.2 Deref 全解 · demo：cargo run -- deref

核心结论（先背）

  1. Box<T> 的 deref 返回 &T，标准库写法核心是 &**self（从 &Box<T> 穿透到堆上 T 的引用）。
  2. 递归 List 必须 Box<List> —— 栈上 Sized 指针 + 堆上节点。
  3. Box = Deref（怎么用）+ Drop（怎么收） —— 智能指针链的起点。

一、Box<T> 的 Deref 实现（逐行）

impl<T> Deref for Box<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &**self
    }
}

1. type Target = T

关联类型：声明解引用后的目标类型。
Box<i32> → Target = i32；Box<String> → Target = str（若写成 Box<str> 则 unsized，此处不展开）。

2. fn deref(&self) -> &Self::Target

部分 含义
&self 接收 Box 的不可变引用（self 的类型是 &Box<T>）
返回值 堆上 T 的不可变引用 &T

3. 核心：&**self（从右往左）

在 deref 方法体内，self 的类型是 &Box<T>（不是 Box<T> 本体）。

步骤 表达式 类型 / 含义
起点 self &Box<T>
第一个 * *self 对 &Box<T> 解引用 → 经 Deref 强制 → &T（指向堆上数据）
第二个 * **self 对 &T 再解引用 → T（i32 等 Copy 类型可复制；非 Copy 则 move）
最前 & &**self 对 T 取借用 → 最终返回 &T ✅ 
&Box<T>  --*-->  &T  --*-->  T  --&-->  &T   （返回）

精度补充：第一个 * 不是「拿出 Box<T> 本体」，而是 Deref 语义的解引用——&Box<T> 上写 * 会直接得到 &T。第二个 * 才是从引用读到值。教学口诀：穿透盒子，借堆上数据。

4. 等价写法（理解用）

// 与 deref() 返回值同一思路（b 是 Box<T> 变量）
let b = Box::new(10);
let r: &i32 = &*b;           // 日常最常用
let r2: &i32 = b.deref();    // 显式调 trait 方法

// 标准库 impl 方法体内 self: &Box<T>，故写 &**self：
fn peel(bx: &Box<i32>) -> &i32 {
    &**bx  // 与 Box::deref 体内同形；外部变量 b 请用 &*b
}

易混点：&**self 出现在 fn deref(&self) 内部（self 是 &Box<T>）。若 b 已是 Box<T>，外部写 &*b 即可，不要写 &**b（第二个 * 会对 i32 解引用而报错）。

→ demo：cargo run -- deref

5. 隐式解引用（日常写法）

let b = Box::new(10);

// 编译器自动走 Deref：&b → &i32，再交给 println!
// 手动写：println!("{}", *b);

口诀：Deref 让智能指针像普通引用一样用，少写 *。→ 15.2 §四

一、基础定义

Deref / DerefMut 是 Rust 解引用重载 trait：让自定义类型支持 * 解引用，并参与自动解引用强制转换（Deref coercion）。

// 不可变解引用
pub trait Deref {
    type Target: ?Sized;
    fn deref(&self) -> &Self::Target;
}

// 可变解引用（必须先实现 Deref）
pub trait DerefMut: Deref {
    fn deref_mut(&mut self) -> &mut Self::Target;
}

关键点：

  1. DerefMut 必须先实现 Deref
  2. deref / deref_mut 永远返回引用，不会转移所有权
  3. Target 唯一（与 AsRef 可多目标不同）→ coercion 无歧义 → ER Item 8 §2

二、最简示例：MyBox

元组结构体默认不能用 *（cannot be dereferenced）。实现 Deref 后：

use std::ops::Deref;

struct MyBox(String);

impl Deref for MyBox {
    type Target = String;
    fn deref(&self) -> &Self::Target {
        &self.0
    }
}

fn main() {
    let b = MyBox("hello".to_string());

    // 手动解引用：*b ⇔ *(b.deref())
    let s: &String = &*b;
    println!("{s}");

    // 自动解引用强制转换（Deref coercion）
    fn take_str(s: &str) {}
    take_str(&b); // &MyBox → &String → &str，编译期链式转换
}

书写 *y 时 Rust 展开为：

*y  ⇔  *(y.deref())

deref 返回引用而非按值 T，避免把内部值从 self 移出；最外层 * 再得到目标类型的值/引用。

→ demo：cargo run §MyBox · 无 coercion 时的冗长写法 hello(&(*m)[..])

三、两大核心能力

1. 手动解引用 *

对实现 Deref 的类型，*T 等价于 *(T.deref())。

let b = MyBox(String::from("test"));
let inner: String = (*b).clone(); // deref 得 &String，再 clone 得 String
// Box<String> 上 *box 则直接 move 出内部 String（见 15.2.1 §一）

2. 自动解引用强制转换（高频考点）

场景：传参、方法调用时，编译器循环解包直到类型匹配。

两条路线（详见 15.2.2 §一）： - &T / &mut T：语言原生剥 & — 无 Deref trait - 智能指针等：T: Deref → 调用 deref() 得到 &U

下表仅描述 Deref trait 路径（不含原生剥 &）：

规则 条件 转换
不可变 T: Deref<Target = U> &T → &U
可变 T: DerefMut<Target = U> &mut T → &mut U
降级 T: Deref<Target = U> &mut T → &U（可变→不可变 ✅；反向 ❌）

可连续多层：&MyBox<String> → &String → &str。

方法调用自动补 *

let b = MyBox(String::from("abc"));
b.len();
// 编译器展开 ≈ (*b).len() 或 String::len(&*b)

因此 Box<T>、Rc<T>、Arc<T>、锁守卫可直接调用内部类型方法。

五、重要规则 & 坑（Effective Rust）

1. 解引用与所有权

  • deref() 返回引用 → *&T 得到 T（复制或移动取决于 T）
  • Box<T>：*box move 出堆上 T，盒子随后通常不可再用
  • coercion 只借看，不转移所有权

2. 自动解引用只发生在引用上下文

会触发 不会触发
函数/方法传参 &T 赋值 let x = smart_ptr
方法调用 smart_ptr.method() 多数模式匹配
部分索引场景 期望值类型却给智能指针

3. 不要滥用 Deref（Effective Rust 核心）

只有智能指针 / 守卫 / 透明包装器才应实现 Deref。
普通业务结构体、领域模型不要随便 Deref 到内部类型。

✅ 适合 ❌ 不适合
Box / Rc / 锁守卫 用户实体、配置 struct
透明缓冲区包装 带校验的 DB 封装（会绕过 API）

→ 反例 demo：ER LeakyDb · Item 6 newtype

更稳妥：显式方法（get / insert）、AsRef、或 Deref 到更窄视图而非整个内部容器。

4. Deref 与生命周期

fn deref(&self) -> &Self::Target;

返回引用生命周期与 &self 绑定，自动继承，绝大多数场景无需手写。

七、一句话总结（背诵版）

  1. Deref / DerefMut = 解引用重载，支持 * 与自动 coercion。
  2. 核心价值：智能指针、锁守卫、String→str 透明访问内部数据。
  3. 编译器自动解引用：传参、方法调用最常用；编译期完成，零运行时开销。
  4. 原则：只给智能指针类实现；业务 struct 别乱用（Effective Rust 重点）。
  5. 并发、锁、自定义内存包装（HFT/底层方向）重度依赖这套机制。

一、多层嵌套 coercion 链

编译器在需要 &U 的地方对 &T 反复应用 deref()，直到类型匹配或失败。

典型链：&MyBox<String> → &str

use std::ops::Deref;

struct MyBox<T>(T);

impl<T> Deref for MyBox<T> {
    type Target = T;
    fn deref(&self) -> &T { &self.0 }
}

fn takes_str(s: &str) {}

let m = MyBox(String::from("hi"));
takes_str(&m);
// 展开等价思路：
// &MyBox<String>  --MyBox::deref-->  &String
//                 --String::deref-->  &str   ✓ 匹配

再套一层：Box<MyBox<String>>

let nested = Box::new(MyBox(String::from("deep")));
takes_str(&nested);
// &Box<MyBox<String>> → &MyBox<String> → &String → &str

手动 vs 自动

// 自动（日常写法）
takes_str(&nested);

// 手动（理解用，等价）
takes_str(&nested.as_ref().0.as_str());
// 或
takes_str(&(*(*nested).deref()).deref());

底层视角：每一步仍是「取地址 + 读指针」，coercion 不分配、不拷贝字符串内容，只调整引用类型的编译期视图。

→ demo：cargo run -- nested

二、DerefMut 完整规则

# 条件 转换 说明
1 T: Deref<Target = U> &T → &U 只读链
2 T: DerefMut<Target = U> &mut T → &mut U 可变链，可改内部
3 T: Deref<Target = U> &mut T → &U 可变借用降级为不可变视图
✗ 仅 Deref、无 DerefMut &T ↛ &mut U 不可从共享引用 coerce 出可变

示例：MyBox + DerefMut

use std::ops::{Deref, DerefMut};

struct MyBox<T>(T);

impl<T> Deref for MyBox<T> {
    type Target = T;
    fn deref(&self) -> &T { &self.0 }
}

impl<T> DerefMut for MyBox<T> {
    fn deref_mut(&mut self) -> &mut T { &mut self.0 }
}

fn main() {
    let mut b = MyBox(vec![1, 2, 3]);
    b.push(4);              // 方法调用：&mut MyBox → &mut Vec（DerefMut）
    (*b)[0] = 99;           // 手动可变解引用
    println!("{:?}", *b);   // [99, 2, 3, 4]
}

Box<T> 的特殊点

let b = Box::new(String::from("own"));
let s: String = *b; // move 出堆上 String；b 此后不可用（除非 T: Copy）

* 对 Box 是取值/移出，不是普通「解引用看一眼」；这是 Box 作为唯一所有权容器的语义，不是 Deref trait 本身规定的。

→ demo：cargo run -- mut

六、一句话总结

  1. 多层 coercion：编译期链式 deref，&Box<MyBox<String>> 一路到 &str，零运行时成本。
  2. DerefMut：&mut T → &mut U；仅有 Deref 时 &mut T 最多降到 &U，不能升可变。

  4. 编译报错多半是没 DerefMut、在非 coercion 上下文用、或滥用 Deref。
  5. 业务封装用显式方法；透明指针用 Deref。

.2 Deref 自动解引用 · `&mut` 与 `*` · unsafe 辨析

← 15.2 Deref hub · 15.2.1 嵌套/可变/坑点 · 15.2.3 引用 vs Target · RFR Ch09 §02 裸指针

核心结论（先纠正误区）

普通引用 &T 并不靠 Deref trait 做点号自动解引用 — 那是语言原生剥 & 层。

智能指针（Box / Rc / …）是普通结构体，必须 impl Deref 才参与点调用 / 传参时的自动解包。

日常标准库智能指针都已实现 Deref，所以 &s 和 Box::new(s) 点调用手感一样 — 底层机制不同。

一、. 点号自动解引用（Deref 强制转换）

调用 xxx.method() 时，编译器循环解包，直到找到匹配方法（不限层数）。每一步只有两条路：

当前包装 解包方式
&T / &mut T 原生引用 语言内置剥一层 & — 不调用 Deref
实现了 Deref 的类型（Box / Rc / 自定义 MyBox…） 调用 Deref::deref → &内部类型

官方术语：Deref coercion — 既包含 trait 解包，也包含方法查找时对引用的原生剥离（二者在方法解析里交替进行）。

1. 原生引用：没有 Deref，语法自带剥 &

let s = String::from("hi");
let r1 = &s;    // &String
let r2 = &&s;   // &&String
let r3 = &&&s;  // &&&String

r1.len();  // ✅
r2.len();  // ✅
r3.len();  // ✅

&&&String  → 剥 &  →  &&String  → 剥 &  →  &String  → 剥 &  →  String  →  len()

👉 &String 未实现 Deref — 全是语言内置逻辑。

2. 智能指针：必须 impl Deref 才参与点解包

let b = Box::new(String::from("hi"));
b.len();

Box<String>  →  无 len  →  Deref::deref  →  &String
              →  剥 &（原生）  →  String  →  len()

没实现 Deref 的自定义包装 — 点号不会自动拆：

struct RawWrap<T>(T);
let w = RawWrap(String::from("abc"));
// w.len();  // ❌ 编译报错 — RawWrap 无 Deref

补上 impl Deref for RawWrap<T> { type Target = T; … } 后 w.len() 才通。

→ demo：MyBox 有 Deref vs 无 Deref 对比见 15.2 §二

3. 多层混搭：&&Box<Rc<String>>.len() 完整链

use std::rc::Rc;

let nested = &&Box::new(Rc::new(String::from("deep")));
nested.len();

逐步拆解（方法查找循环）：

&&Box<Rc<String>>     无 len
  → 剥 &              &Box<Rc<String>>
  → Deref (Box)       &Rc<String>
  → 剥 &              Rc<String>   （或保持 &Rc，视自动引用步骤）
  → Deref (Rc)        &String
  → 剥 &              String
  → len()             ✅

→ demo：cargo run -- dot-paths

4. 手动 * 同样分两条路

表达式 机制
*(&s) / *rx 原生剥引用
*box_val 语法糖 ≈ *(box_val.deref()) — 走 Deref

5. 何时发生 / 何时不发生

✅ 会自动解包 ❌ 不会随便解包
. 方法调用 赋值 let x = smart_ptr
函数传参需要 &T 多数模式匹配
字段访问（配合 deref） 非引用上下文期望精确类型

可变场景配套 DerefMut — 规则与 Deref 对称 → 15.2.1 §二

6. 日常常识

  1. 标准库 Box / Rc / Arc / Ref / RefMut / 锁守卫 都已实现 Deref — 无感使用。
  2. 自己造的封装才要考虑要不要 impl Deref。
  3. 两种路线混用时，观感都是「点一下就行」，记住底层不一样。

二、&mut T 修改值：何时要手动 *？

✅ 不用手动 *（点语法走 §一 两条路线）

let mut p = Box::new(Point { x: 0, y: 0 });
p.x = 10;           // 字段：deref_mut + 原生
let mut v = Box::new(vec![1, 2]);
v.push(3);          // 方法：DerefMut 链

⚠️ 必须手动 *（整体赋值）

let mut b = Box::new(10);
*b = 20;            // 必须 * — 改堆上 i32，不是改 Box 变量

let mut r = &mut 42;
*r = 100;           // 原生 &mut 同理
写法 含义
ref.field = v / ref.method() §一 自动解包
*ref = new_value 整体替换 — 必须 *

三、unsafe 与解引用的关系

操作 unsafe？
&T / &mut T 手动 * ❌
智能指针 * / . / Deref coercion ❌
裸指针 *const T / *mut T 手动 * ✅ 必须
误区 正解
「解引用都要 unsafe」 只有裸指针手动 *
「只有裸指针才 unsafe」 还有 unsafe fn、trait、static mut、union 等

四、一句话速记

点号自动拆包装：原生 & 靠语言自带，智能指针靠 Deref；标准库已写好 Deref，手感与普通引用一致。

  1. 整体赋值 → *ref = 必写。
  2. 安全引用 + 智能指针 → 与 unsafe 无关。
  3. 裸指针 * → 必须 unsafe。

第一部分：借用 & 解引用（都能用 *、.，底层不一样）

两个基础概念

普通引用 &T / &mut T 智能指针 Box / Rc / Arc / …
是什么 语言原生的借用标记 — 栈上地址，不拥有数据 拥有堆数据所有权的结构体（堆指针 + 元数据/计数）
所有权 无，仅临时借 有（独占或共享）

1. 解引用 * 分别干了啥

① 普通引用 — 原生剥一层

let s = String::from("hello");
let r: &String = &s;
// *r 若 T 非 Copy 会 move — 日常多用 . 或 &*r 借看
let x = 42;
let rx = &x;
assert_eq!(*rx, 42); // 原生：* 直接穿透引用层
  • &T 是语法层「地址包裹」，只有一层。
  • 不经过 Deref trait。

② 智能指针 — 走 Deref trait

let b = Box::new(String::from("hello"));
let inner: String = *b; // *b ⇔ *(b.deref()) → 先 &String 再 move 出 String

Box 结构体存堆地址
  → *b 调用 Deref::deref(&self)
  → &Box<String> 变成 &String（Target 类型）
  → 再 * 得到 String（若 move）
对比 普通 &T Box<T> 等
* 来源 语言原生 impl Deref 语法糖
本质 借用标记 自定义结构体 + trait

→ 速记 · unsafe：15.2.2

2. 点号 . 自动解引用 — 两条路线（最易混）

方法调用 / 传参时，编译器循环解包。包装是 &T → 语言原生剥 &（无 Deref）；包装是 Box / Rc / … → 必须 impl Deref。

let s = String::from("hi");
let r3 = &&&s;
r3.len(); // 原生：&&&String → … → String → len

let b = Box::new(String::from("hi"));
b.len();  // Deref：Box → &String → 剥 & → len

// 没 impl Deref 的 struct — mb.len() 编译失败
struct RawWrap<T>(T);

混搭多层链 → 15.2.2 §一.3 &&Box<Rc<String>> · demo：cargo run -- dot-paths

3. 对照表

类型 所有权 * / . 来源 用途
&T 无，只读借 原生引用 临时只读，生命周期约束
&mut T 无，排他借 原生引用 临时可变借
Box<T> 独占堆上 Deref / DerefMut 堆分配
Rc<T> / Arc<T> 共享 Deref 多所有者
RefCell<T> 独占 + 内部可变性 Deref（通过 .borrow() 守卫时） 运行时借用检查

第一部分一句话

  1. 普通引用：* 与 . 剥 & 是语言原生 — 不靠 Deref。
  2. 智能指针：必须 impl Deref 才参与 * 语法糖与点调用解包。
  3. 标准库已全实现 — 手感一致，机制不同 → 15.2.2 §一

第二部分：trait / impl 里的 type — 关联类型

典型写法

trait MyTrait {
    type Target; // 类型占位符 — 定义时不指定具体类型
    fn get(&self) -> Self::Target;
}

impl MyTrait for i32 {
    type Target = String; // impl 时把占位填成具体类型
    fn get(&self) -> Self::Target {
        self.to_string()
    }
}
位置 写法 含义
trait 内 type Target; 声明：此 trait 绑定一个叫 Target 的类型，以后再定
impl 内 type Target = SomeType; 落地：此 (Self, Trait) 的 Target 就是 SomeType
使用 Self::Target / <i32 as MyTrait>::Target 当前 impl 填好的那个类型

→ 系统讲解：RFR Ch02 §06.1 关联类型 vs 泛型

1. 关联类型 vs 泛型 trait

方案 A：泛型 <T> — 可多次 impl

trait MyTrait<T> {
    fn get(&self) -> T;
}
impl MyTrait<String> for i32 {}
impl MyTrait<i32> for i32 {}  // 同一类型，不同 T，多份 impl

方案 B：关联 type — 通常只 impl 一次

trait MyTrait {
    type Target;
    fn get(&self) -> Self::Target;
}
impl MyTrait for i32 {
    type Target = String; // i32 对 MyTrait 只能有一份，Target 唯一
}
关联类型 泛型参数
同一 Self + trait 一种配套类型 多种 T / Rhs
典型 Iterator::Item、Deref::Target PartialEq<Rhs>、From<T>

2. 标准库联动：Deref::Target（串起第一部分）

pub trait Deref {
    type Target: ?Sized;           // 关联类型：解引用后是什么
    fn deref(&self) -> &Self::Target;
}

impl<T> Deref for Box<T> {
    type Target = T;              // Box 剥完包装 → 里面的 T
    fn deref(&self) -> &T {
        &*self.as_ref()            // 标准库实现略
    }
}

串联记忆：

智能指针能 * 和 . 自动解引用
  ← 因为实现了 Deref
  ← Deref 用 type Target 规定「剥完是什么类型」
  ← Box<T> 写 type Target = T
  ← 所以 *Box<T> 最终面向 T

普通 &T 不走这套 trait + Target — 只是语言原生借用。

3. 何时用关联类型 vs 泛型

场景 选用
一种 impl 固定唯一配套类型（Box 解引用永远是内部 T） 关联类型
同一类型要对多种外部类型 impl（PartialEq<u32>、PartialEq<u64>） 泛型

第二部分极简总结

  1. trait 里 type Target; = 开类型空位。
  2. impl 里 type Target = X; = 填空。
  3. Self::Target = 当前 impl 的 X。
  4. Deref::Target = 智能指针剥完露出的类型。

整体复盘（两个问题合在一起）

普通 &T     →  原生借用，* 剥一层，无 Deref trait
智能指针     →  结构体 + impl Deref { type Target = …; fn deref … }
              →  * / . 的语法糖根源在这里
关联类型     →  trait 里 type 占位，impl 里落地
              →  Deref::Target 决定 *Box<T> 面向 T

}
形式 谁实现 做什么
隐式默认 编译器自动生成 递归释放字段、归还栈/堆内存（i32/String/Vec/普通 struct…）
手写自定义 开发者 impl Drop 关文件、释放 socket、解锁、FFI free、mmap 解除映射…

👉 默认只管内存；手写管一切外部资源。 它是 RAII 在 Rust 的载体，和内存安全、并发、系统编程强绑定，不是 C++ 析构函数的简单翻版。

2. 硬性规则：Copy 与自定义 Drop 互斥

一个类型不能同时 Copy + 手写 Drop。

  • Copy 语义 = 按位复制、旧值仍有效
  • Drop 语义 = 销毁时释放资源、旧值不可再用

二者矛盾 → 设计类型时要先想清楚「能不能 Copy」。→ 15.3.1 §三

二、默认 Drop vs 手写 Drop：替换，不是叠加

一句话：没错，默认 Drop 只管内存；一旦手写 impl Drop，编译器用你的逻辑替换默认版本，自动调用时优先执行你的代码。

1. 不手写 impl Drop（编译器默认）

编译器自动生成析构逻辑：

  • 逐个递归销毁 struct / enum / tuple 的每个字段
  • 只做内存回收：栈出栈、堆释放
  • 不会关文件、解锁、断 socket 等额外操作

适合：i32、Vec、String、纯数据业务 struct。

2. 手写 impl Drop（完全替换默认路径）

阶段 发生什么
① 变量出作用域 调用你写的 fn drop(&mut self)（关 fd、解锁、FFI free…）
② 你的 drop 返回后 编译器仍自动 drop 各字段（Vec/String 等内存照常释放） 
变量出作用域 → 你的 drop（外部资源）→ 编译器 drop 各字段（内存）

没有「默认 + 自定义一起跑」的叠加模式 —— 只有「全默认」或「先你的、再字段」。

3. 代码验证：FileHandle

struct FileHandle {
    fd: i32,           // 模拟 fd（外部资源）
    buf: Vec<u8>,      // 纯内存字段
}

impl Drop for FileHandle {
    fn drop(&mut self) {
        println!("手动执行：关闭 fd = {}", self.fd);
        // 只处理外部资源；不要手动 drop self.buf
    }
}

fn main() {
    let _fh = FileHandle { fd: 10, buf: vec![1, 2, 3] };
    println!("变量创建完成");
} // → 打印关闭 fd → 编译器自动释放 buf

→ demo：cargo run -- custom

4. 三个必记规则

  1. 不要在 drop 里手动 drop 字段 —— 编译器会后补；手动调用 → double free
  2. 替换，非叠加 —— 不手写 = 全走默认；手写 = 先你的逻辑，再字段内存
  3. MutexGuard 同理 —— 手写 Drop 解锁 → 返回后回收守卫自身内存 → 16.3

三、drop：调用时机与调用方式

核心：永远被动调用，禁止主动调 drop()

1. 正常触发（最主流）

变量离开当前作用域时，编译器自动调用 drop(&mut self)。

作用域边界：{} 块、函数结束、if/while/for 块结束。

struct Foo;

impl Drop for Foo {
    fn drop(&mut self) {
        println!("Foo 被销毁");
    }
}

fn main() {
    {
        let f = Foo;
    } // 离开作用域 → 自动 drop
    println!("作用域结束");
}
// 输出：Foo 被销毁 → 作用域结束

2. 其他自动触发

场景 行为
所有权 move 走 原变量位失效 → drop 原值（若未 Copy）
容器销毁 Vec/Box 先 drop 元素，再释放容器自身
panic! + unwind 栈展开时仍逐层 drop（除非 abort）→ 9.1 panic

3. 为什么不能写 f.drop()？

let mut f = Foo;
f.drop(); // ❌ explicit call to destructor `drop` is disallowed
  1. 防止双重释放 —— 手动调一次，出作用域再调一次 → double free
  2. 防止僵尸对象 —— drop 是 &mut self，对象还在作用域里却已清理，后续使用 = 未定义行为

→ demo：cargo test explicit_drop_disallowed（编译失败用例，见 lib 注释）

四、提前释放：合法替代方案

既然不能 self.drop()，Rust 提供：

方案 1：std::mem::drop（标准用法）

唯一合法的「提前触发销毁」：拿走所有权 → 值立刻失效 → 运行 Drop。

use std::mem;

let f = Foo;
println!("开始");
mem::drop(f); // 提前销毁
println!("结束");
// 再用 f → 编译错误

mem::drop 是函数（prelude 里），不是 trait 方法；通过 move 结束生命周期。

方案 2：缩小 {} 作用域

{
    let guard = lock();
    // 仅此处持锁
} // guard drop → 解锁
// 耗时逻辑放外面

五、关键细节（底层/系统路线）

1. 同一作用域：后进先出（LIFO）

后创建的变量先被 drop（栈式）。

2. 嵌套类型与容器

  • struct Outer(Inner)：先 Outer::drop，再 Inner::drop
  • Vec<T>：元素按声明顺序（正序）drop，再释放堆缓冲区

3. 与 Deref / 锁联动

MutexGuard / RwLockGuard 手写 Drop：守卫出作用域 → 自动解锁。

    *guard += 1;
} // Drop → unlock

5. Drop 里不能 Result / 不能 .await

  • 释放失败 → 提供 release() -> Result 让用户主动调；Drop 只做防泄漏兜底
  • 异步关闭 → 专门模式（Item 11 §5）

六、一句话总结

  1. 默认 Drop = 仅内存；手写 = 先你的外部资源清理，再自动 drop 字段。

  3. 替换非叠加；drop 里不要手动 drop 字段。
  4. Drop + RAII = 锁自动解、文件自动关 —— 并发与系统编程的安全基石。

核心关系（先背）

术语 含义
RAII Resource Acquisition Is Initialization — 经典范式：构造拿资源，析构放资源
OBRM Ownership-Based Resource Management — Rust/Nomicon：带严格所有权规则的 RAII 
RAII = 思想（C++ 起源）
OBRM = Rust 用所有权 + 借用 + 编译期检查 锁死的 RAII 落地形态

日常说「Rust 的 RAII」，本质指的就是 OBRM。

一、RAII：经典基础范式

全称

Resource Acquisition Is Initialization — 资源获取 = 初始化。

核心逻辑（C++）

  1. 构造时申请资源（堆、文件、锁、Socket…）
  2. 析构（出作用域）自动释放 — 不用手动 free / close / unlock
  3. 资源生命周期 绑定对象生命周期

C++ 极简例子

struct FileGuard {
    FILE* fp;
    FileGuard(const char* path) { fp = fopen(path, "r"); }
    ~FileGuard() { if (fp) fclose(fp); }
};

void demo() {
    FileGuard f("test.txt");
} // 出作用域 → 析构 → 关文件
优点 缺点（无所有权体系时）
确定性释放、无 GC、性能高 浅拷贝 → double free；悬垂 → use-after-free

二、OBRM：Rust 升级版

全称

Ownership-Based Resource Management — Nomicon 明确：规范化、加了所有权约束的 RAII。

在 RAII 上追加的三条（= 所有权三规则）

# OBRM 规则 对应 Rust
1 资源绑定唯一所有者 同一时刻一个变量负责 drop
2 所有权可转移、默认不可浅拷贝 move 语义；非 Copy 禁止隐式复制
3 所有者出作用域 → Drop 释放 impl Drop { fn drop(&mut self) } 自动调用

Rust 文件示例（对比 C++）

use std::fs::File;
use std::io;

fn main() -> io::Result<()> {
    let f = File::open("test.txt")?; // 获取资源，f 是唯一所有者
    Ok(())
} // f 出作用域 → Drop → 关闭 fd

智能指针全是 OBRM 实现

类型 OBRM 语义
Box<T> 独占；出作用域 Drop 释堆
Rc<T> / Arc<T> 共享；计数归零才 Drop
MutexGuard 锁 RAII；Guard Drop 解锁
Vec / String 堆缓冲 OBRM

→ 15.1 Box · 15.3 Drop · 15.2 Deref 访问 vs Drop 释放

三、RAII vs OBRM 对照

维度 RAII（C++ 原版） OBRM（Rust）
核心 构造拿、析构放 继承 RAII + 唯一所有权
拷贝 可浅拷贝，多对象管一份资源 编译期禁止；只能 move
安全 运行时才暴雷 编译期拦违规
释放 析构函数 Drop trait
借用 无规范 &T / &mut T 规则
与 GC 无关（确定性释放） 无关

一句话：RAII 是思想；OBRM 是 Rust 把 RAII 锁死、规范化、编译期强制安全的形态。

四、与借用、Deref、智能指针串联

let b = Box::new(100); // b：所有者，OBRM 管控堆内存
let r = &*b;           // 借用访问；r 消失 **不会** Drop
// 只有 b 出作用域才 Drop 释放
机制 作用 是否改变所有权 / 释放时机
所有权 + Drop 谁负责、何时释放 ✅ 核心
&T 借用 临时只读/可变访问 ❌ 不转移、不触发所有者 Drop
Deref / . 像引用一样访问内部 ❌ 只访问数据，不改变归属

→ 点号两条路线：15.2.2 §一

五、常见误区

误区 正解
RAII = GC ❌ — RAII/OBRM 是作用域结束立刻确定性释放
Rust 只有 OBRM 没有 RAII OBRM 就是 Rust 语境下的 RAII 全称
借用多了会提前 Drop ❌ — 只有所有者出作用域才 Drop；& 再多也不释放
Deref 会把所有权转走 ❌ — 解引用只是访问；move 才转移所有权

一、同一作用域：LIFO（后进先出）

1. 示例：Tag 与 self.0 是什么？

struct Tag(&'static str);  // 元组结构体：一个无名字段

impl Drop for Tag {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

self.0 到底是什么？

概念 说明
struct Tag(&'static str) 元组结构体 — 只有一个字段，类型 &'static str，没有字段名
.0 访问第 0 个（唯一）字段的语法；多字段则 .1、.2…
drop(&mut self) 里的 self 正在被销毁的 Tag 实例，类型 &mut Tag
self.0 该实例里包裹的 &'static str（如 "a"、"b"）

若改成命名字段的普通 struct，则写 self.value：

struct Tag { value: &'static str }

impl Drop for Tag {
    fn drop(&mut self) {
        println!("drop {}", self.value);
    }
}

元组 struct 在 Drop / Deref 演示里很常见（MyBox(T) → self.0）→ 15.2 §二 · 15.1.1 &**self

2. LIFO 销毁顺序

{
    let a = Tag("a"); // 先创建
    let b = Tag("b"); // 后创建
}
// 输出：drop b → drop a

原因：局部变量在栈上按创建顺序排列，销毁时逆序 —— 与 C++ 局部对象析构一致。

→ demo：cargo run -- lifo · cargo test drop_order_lifo

二、嵌套类型与容器

1. 带 Drop 的嵌套 struct

struct Inner;
struct Outer(Inner);

impl Drop for Inner { fn drop(&mut self) { println!("Inner"); } }
impl Drop for Outer { fn drop(&mut self) { println!("Outer"); } }

let _o = Outer(Inner);
// 输出：Outer → Inner

规则：外层类型的 drop 先执行（此时字段仍有效，可访问 self.xxx）；drop 返回后，字段按声明逆序依次 drop。

→ 与 15.3 §二 一致：先你的外部资源逻辑，再字段内存。

2. 无自定义 Drop 的 struct

字段按声明逆序 drop：

struct Pair { first: Tag, second: Tag }
// drop second → drop first

3. Vec<T> / Box<[T]>

  • 元素：从第一个到最后一个依次 drop（与数组一致）
  • 容器自身：元素全部 drop 后，释放堆缓冲区
struct E(u32);
impl Drop for E { fn drop(&mut self) { println!("E({})", self.0); } }

let v = vec![E(1), E(2), E(3)];
// drop E(1) → E(2) → E(3) → 释放 Vec 堆内存

4. Box<T>

  • drop 顺序：先 T::drop，再释放 Box 堆内存
  • *box move 出 T 后，空壳 Box 仍会在出作用域时 drop（不再重复 drop 已移走的 T）

→ demo：cargo run -- nested · cargo test vec_drop_reverse

三、Copy 与自定义 Drop 互斥

struct Handle(i32);

impl Drop for Handle {
    fn drop(&mut self) { /* 关 fd */ }
}

// impl Copy for Handle {}  // ❌ 不能：Copy 类型不能有自定义 Drop
Copy 自定义 Drop
旧值 after 赋值 仍有效 各自独立 drop
适用 纯数据、无资源 管 fd/锁/堆所有权

设计口诀：要管资源 → 别 Copy；要 Copy → 别手写 Drop。

四、ManuallyDrop（底层 / 高性能）

std::mem::ManuallyDrop<T> 包裹后，不会在出作用域时自动调用 T::drop。

use std::mem::ManuallyDrop;

struct Resource;
impl Drop for Resource {
    fn drop(&mut self) { println!("Resource freed"); }
}

let mut slot = ManuallyDrop::new(Resource);
// 出作用域前不会打印

let taken = unsafe { ManuallyDrop::take(&mut slot) }; // take 为 unsafe：须保证不 double-drop // 取出 Resource
drop(taken); // 此时才手动触发 Drop
// slot 已是空壳，不再 drop Resource

典型场景：

场景 为何需要
FFI / 自管内存 自己决定何时 free
内存池 / arena 批量回收，单块不单独 drop
无锁数据结构 避免并发路径上意外 drop
Pin + 自引用 控制销毁时机

⚠️ 泄漏风险：忘记 take + drop → 资源永不释放。只在明确需要时用。

→ demo：cargo run -- manual

五、panic 与 Drop

panic 策略 Drop 行为
unwind（默认） 栈展开，逐层 drop 局部变量 → 9.1
abort 进程直接终止，不跑 Drop

Drop 里再 panic

若 drop 执行中又 panic! → double panic → abort（无法安全展开）。
Drop 实现应保持简单，避免 panic。

六、常见坑

现象 原因 修法
explicit destructor calls not allowed 写了 x.drop() 用 mem::drop(x)
锁持有过久 guard 作用域太大 缩小 {}
释放失败无处报告 drop 无返回值 提供 release() -> Result
异步关闭 Drop 不能 .await 专门 shutdown 模式
在 drop 里手动 drop(field) 编译器已会 drop 字段 删掉；只写外部资源清理

不能主动调 vs 可以 mem::drop

// x.drop();        // ❌ trait 方法，对象仍在作用域
mem::drop(x);       // ✅ move 走 x，生命周期结束，再 drop

七、一句话总结

  1. LIFO：同作用域后建先毁；嵌套 struct 外层 drop 先于字段。
  2. 容器：Vec 元素正序 drop，再释堆。
  3. Copy ⊥ 自定义 Drop —— 类型设计二选一。
  4. ManuallyDrop：禁用自动 drop，自管销毁（FFI/池化/HFT 进阶）。
  5. panic unwind 仍 drop；abort 不 drop；Drop 里别 panic。

核心结论（先背）

网络编程里大量和 Socket、连接、fd 相关的结构体，基本都要手动实现 Drop（或嵌套已实现 Drop 的标准库类型）—— Rust 网络代码的标配，靠 RAII 自动关套接字、防 fd 泄漏。

类型 要不要手写 Drop
标准库 TcpStream / UdpSocket / TcpListener ❌ 官方已实现
仅包装 TcpStream + Vec 缓冲区的业务 Conn ❌ 默认 drop 字段即可
独立 fd、epoll/kqueue 句柄、SSL 上下文、连接池节点 ✅ 必须手写

一、为什么 Socket 必须关心 Drop

Socket 在 OS 层就是文件描述符（fd），属于操作系统级外部资源：

  1. 只释放 Rust 内存 ≠ 关闭 Socket → fd 泄漏
  2. fd 有上限 → 泄漏多了 → Too many open files → 进程崩溃
  3. 需求：连接变量出作用域自动 close(fd)

默认 Drop 只管内存 → 持有裸 fd 的类型必须手写 Drop，在里头调 close（或封装好的 close()）。

二、最简实战：封装 TcpSocket

pub struct TcpSocket {
    fd: i32,
    peer_addr: String,
}

impl TcpSocket {
    pub fn new(fd: i32, addr: &str) -> Self {
        Self { fd, peer_addr: addr.to_string() }
    }

    pub fn close(&mut self) {
        if self.fd != -1 {
            println!("关闭 Socket fd: {}, 对端: {}", self.fd, self.peer_addr);
            // 实际：libc::close(self.fd)
            self.fd = -1; // 防重复 close
        }
    }
}

impl Drop for TcpSocket {
    fn drop(&mut self) {
        self.close();
    }
}

let sock = TcpSocket::new(1001, "127.0.0.1:8080");
println!("连接正常使用中");
// 出作用域 → drop → close(fd)

→ demo：cargo run -- socket §1

三、哪些结构体要写 Drop？

1. 标准库 Socket 类型（不用写）

std::net::{TcpStream, TcpListener, UdpSocket} 内部已实现 Drop → 变量销毁自动 close fd，开箱即用。

use std::rc::Rc;

// a、b、c 都出作用域 → 计数 0 → 释放堆

核心结论（先背）

  1. Rc 强计数 > 0 就不释放；两个 Rc 互指 → 计数永 ≥ 1 → 内存泄漏（仍 memory safe，无 UAF）。
  2. Weak<T> 不增加强计数，只做观察；需 upgrade() → Option<Rc<T>>。
  3. 规则：正向/所有权边用 Rc，回边/父指针用 Weak。

一、为什么会出现循环引用？

Rc 靠 strong_count 管理堆内存：

  • > 0 → 数据保留
  • = 0 → Drop 释放

若 A 强引用 B 且 B 强引用 A，变量出作用域后各自 -1，但内部仍互相持有，计数永远 ≥ 1 → 泄漏。

Rust 允许泄漏（不算 UB），但不会自动帮你破环。

二、实战：双向节点（经典环）

use std::rc::Rc;
use std::cell::RefCell;

#[derive(Debug)]
struct Node {
    val: i32,
    prev: Option<Rc<RefCell<Node>>>,
}

let a = Rc::new(RefCell::new(Node { val: 1, prev: None }));
let b = Rc::new(RefCell::new(Node {
    val: 2,
    prev: Some(Rc::clone(&a)), // B → A，a 计数 2
}));

a.borrow_mut().prev = Some(Rc::clone(&b)); // A → B，b 计数 2 → 成环！

计数拆解

步骤 a 强计数 b 强计数
创建 a 1 —
创建 b（prev 指 a） 2 1
a.prev = Some(b) 2 2
变量 a、b 出作用域各 -1 1 1
结果 永不归 0 → 泄漏

→ demo：cargo run -- node §泄漏

三、解法：Weak<T> 弱引用

Rc（强） Weak（弱）
计数 strong_count +1 weak_count +1，不影响释放
访问数据 直接 Deref 须 upgrade() → Option<Rc<T>>
释放判定 strong = 0 即释堆 weak 可残留，upgrade 得 None

修正：前驱用 Weak

use std::rc::{Rc, Weak};

struct Node {
    val: i32,
    prev: Option<Weak<RefCell<Node>>>, // 弱引用，不增 strong
}

let a = Rc::new(RefCell::new(Node { val: 1, prev: None }));
let b = Rc::new(RefCell::new(Node {
    val: 2,
    prev: Some(Rc::downgrade(&a)),
}));

a.borrow_mut().prev = Some(Rc::downgrade(&b)); // A 弱指 B，不成环

// 出作用域：a、b strong 归 0 → 正常释放

常用 API

  • Rc::downgrade(&rc) → Weak<T>
  • weak.upgrade() → Some(Rc) 或 None

→ demo：cargo run -- node §Weak · cargo run §Weak 树（weak_tree.rs）
