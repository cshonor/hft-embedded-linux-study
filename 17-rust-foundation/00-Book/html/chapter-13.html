一、核心定义

闭包是可存入变量、可作为函数参数的匿名函数。与普通 fn 的核心区别：能捕获定义处外层作用域的变量 → 行为延后执行、惰性求值。

fn 闭包
捕获环境 ❌ ✅
类型 函数指针 / 具名 匿名类型，编译器推导
参数/返回类型 通常须标注 可选，上下文推断

基础语法

→ 四段式演变详解：13.1.1

let add = |x: i32| -> i32 { x + 1 }; // 完整标注
let add = |x| x + 1;                 // 最简：单行可省略 {}
add(5);
  1. 参数：|参数列表|``（不是()`）
  2. 体：单语句可省略 {}；多语句必须 {}
  3. 类型可选 — 不像 fn 强制标注

类型锁定（易错）

→ 完整讲解 · 速查表：13.1.3 类型推导易错点

同一闭包首次调用推导参数类型后永久锁定；只定义不调用且无标注 → E0282：

let cl = |x| x;
cl(5);      // 推导 x: i32
// cl("abc"); // ❌ 编译报错

二、业务场景：惰性 + 缓存（Cacher）

1. 提前存变量 — 浪费

let res = simulated_expensive_calc(10); // 立刻算，无用分支也白跑
if flag { println!("{}", res); }

2. 闭包存行为 — 惰性

let calc = |n| simulated_expensive_calc(n); // 只存逻辑
if flag { calc(10); }                          // 需要才算

3. Cacher — 泛型 + Fn trait

闭包是匿名类型，结构体字段不能直接写类型 → T: Fn(...) 约束。

简易版：只缓存一次结果

struct Cacher<T>
where
    T: Fn(u32) -> u32,
{
    calc: T,
    val: Option<u32>,
}

缺陷：只缓存第一次入参；换参数仍返回旧值 → demo CacherOnce。

通用版：HashMap 多参数缓存

struct Cacher<T, Arg, Ret>
where
    T: Fn(Arg) -> Ret,
    Arg: Eq + Hash,
{
    calc: T,
    cache: HashMap<Arg, Ret>,
}

→ demo CacherMap。

三、三大捕获 Trait：Fn / FnMut / FnOnce

→ 完整讲解 · 推导规则 · 传参铁律 · 速查表：13.1.4 Fn / FnMut / FnOnce

由闭包如何使用捕获变量自动决定 impl 哪几个；所有闭包至少实现 FnOnce — 不是三个都自动 impl。

→ 完整讲解：13.1.4 Fn / FnMut / FnOnce

Trait 捕获 闭包实际 impl
Fn 只读 &T Fn + FnMut + FnOnce
FnMut &mut T FnMut + FnOnce（无 Fn）
FnOnce move / 消耗 至少 FnOnce；消耗时往往仅 FnOnce

层级：Fn ⊂ FnMut ⊂ FnOnce（继承 · bound 由严到宽）→ 13.1.4 §二

四、move 闭包

→ 详解 · 默认捕获 vs move · 线程：13.1.5 move 闭包

move |args| { /* ... */ }

强制把捕获变量 move 进闭包，绑定闭包自身生命周期。

经典：跨线程

use std::thread;

let s = String::from("hello");
let handle = thread::spawn(move || println!("{s}"));
handle.join().unwrap();
// s 已 move，此处不可用（非 Copy 类型）
类型 move 后原变量
Copy（i32） 仍可用（拷贝）
非 Copy（String） 失效

五、易错点汇总

  1. 闭包类型不能显式书写 → 编译器自动 impl Fn 系列；API 用 bound 限定 → 13.1.4 §三
  2. 只定义不调用 → E0282；首次调用锁定类型 → 13.1.3
  3. CacherOnce 只缓存单参数；多参数要 HashMap
  4. move = 强制所有权，不是借用 → 13.1.5
  5. FnMut 不能降级为 Fn 传参 → 13.1.4

一、概念

迭代器：实现了 Iterator trait 的类型，逐个产生序列元素。

  • 是 Rust 处理集合的零成本抽象
  • 核心：只定义规则，不立即执行（惰性）

二、要点总览（先背这几句）

  • 惰性：map/filter 只存规则；collect/sum/for 才真正跑
  • Iterator trait：只必须实现 next + 关联类型 Item
  • 适配器：返回新迭代器，仍然惰性（map/filter/zip…）
  • 消费器：拿走迭代器、用完作废（collect/sum/count/for…）
  • iter / iter_mut / into_iter：对应 &T / &mut T / T，所有权不同
  • 返回迭代器：
  • 单一类型：impl Iterator<Item = T>
  • 分支异构：Box<dyn Iterator<Item = T>>

三、惰性（Lazy）——最关键

定义迭代器 ≠ 执行；只有消费时才计算。

let v = vec![1, 2, 3];
let it = v.iter().map(|x| x * 2);
// ⚠️ 惰性：此时什么都不算，只存「乘 2」规则

// 到这里才真正遍历、计算
let res: Vec<_> = it.collect();
  • 适配器（map/filter/skip）：不干活，只包一层规则
  • 消费器（collect/sum/for/while let … next()）：触发 next()，真正执行

→ Filter 伪实现 · 更多例子：13.2.1 §一–§三 · 分步打印 demo：13.2.4（cargo run -- lazy）

四、Iterator Trait（极简）

pub trait Iterator {
    type Item;                // 关联类型：元素类型
    fn next(&mut self) -> Option<Self::Item>;
}
  • 唯一必须实现：next()
  • next()：每次调用推进状态，返回 Some(值) 或 None（结束）
  • 所有其他方法（map/filter/fold…）都是默认实现，基于 next

→ next 须 mut · Item 与 iter 三件套：13.2.1 §二

五、适配器 vs 消费器（对照表）

1）迭代器适配器（返回新迭代器，惰性）

方法 作用
map(f) 每个元素应用 f，映射新值
filter(f) 保留 f 返回 true 的元素
zip(it2) 与另一个迭代器配对
take(n) 只取前 n 个
enumerate() 产出 (索引, 值)

2）消费器（拿走迭代器，立即执行）

方法 作用
collect::<C>() 收集到集合 C（Vec/HashSet…）
sum() 求和
count() 计数
for x in it 循环遍历（本质：反复 next）
while let Some(x) = it.next() 手动逐个 next()（最底层消费）
fold(init, f) 自定义累加

一句话：适配器 = 链式加工；消费器 = 收尾出结果。

→ 详解：13.2.2 · 调用链路：13.2.3 · demo：13.2.4

六、iter / iter_mut / into_iter（所有权核心）

方法 元素类型 所有权 原集合还能用？
iter() &T 不可变借用 ✅ 可以继续用
iter_mut() &mut T 可变借用 ✅ 可以继续用（但不能同时借用）
into_iter() T 拿走所有权 ❌ 原集合失效 
let v = vec![1, 2, 3];

// iter：只读借用
for x in v.iter() {
    println!("{}", x);
}
println!("{:?}", v); // ✅ 还能用

// into_iter：拿走所有权
for x in v.into_iter() {
    println!("{}", x);
}
// println!("{:?}", v); // ❌ 报错，所有权已转移

for x in v 默认等价 for x in v.into_iter()（move 所有权）。

→ 签名 · 踩坑 · IntoIterator：13.2.5 · 结构体类型：13.2.6

七、返回迭代器怎么写

1）单一类型（推荐：impl Trait）

fn double_it(v: &[i32]) -> impl Iterator<Item = i32> {
    v.iter().map(|x| x * 2)
}
  • 优点：静态分发、零成本
  • 适用：返回确定、单一迭代器类型

2）分支 / 多种迭代器（必须 Box<dyn …>）

fn make_it(flag: bool) -> Box<dyn Iterator<Item = i32>> {
    if flag {
        Box::new((1..=5).into_iter())
    } else {
        Box::new(vec![10, 20, 30].into_iter())
    }
}
  • 适用：不同分支返回不同迭代器类型
  • 代价：堆分配、动态分发（小开销）

→ 10.2.5 impl vs dyn · demo get_iter / get_dyn

八、一句话总结（背下来）

  • 惰性：map/filter 只记规则，collect/for 才跑
  • Iterator：只有 next + Item 是必须的
  • 适配器：返回新迭代器、不消费
  • 消费器：拿走迭代器、算出结果
  • 三迭代方法：iter = &、iter_mut = &mut、into_iter = 拿走
  • 返回迭代器：单一用 impl，异构用 Box<dyn>

改进 I/O 项目（minigrep）

对应 demo 项目：00-Book/13-iterators-closures/13.3-minigrep-iterators-demo/

这一节用“迭代器”改进第 12 章的 minigrep，使代码更简洁，并去掉不必要的 clone()。

1) Config::new：接收 env::Args，移动 String，去掉 clone

旧版常见写法是先 collect::<Vec<String>>()，然后 Config::new(&args) 再用索引 args[1].clone() / args[2].clone()。

改进点： - main 直接把 env::args() 的 迭代器所有权 传给 Config::new - Config::new(mut args: env::Args) 用 next() 逐个取值 - 这样 String 可以 move 进 Config，无需 clone

2) search：用迭代器适配器 filter + collect 简化实现

旧版： - 手动 for line in contents.lines() + results.push(...)

迭代器版：

contents
    .lines()
    .filter(|line| line.contains(query))
    .collect()

迭代器是惰性的：filter 本身不做事，直到 collect()（消费适配器）才真正遍历并生成结果。

3) 顺手补上大小写敏感开关（环境变量）

按书中习惯： - 默认大小写敏感 - 如果设置了 CASE_INSENSITIVE，则改为大小写不敏感搜索

13.4

性能对比：循环 VS 迭代器

对应 demo 项目：00-Book/13-iterators-closures/13.4-iterators-performance-demo/

本节关心一个现实问题：写 for 循环更快，还是写迭代器链更快？

结论（从 Rust 的设计目标与实际基准结果看）：迭代器通常不会比手写循环慢，很多情况下还可能一样快甚至略快。原因是 Rust 的迭代器属于 零成本抽象（zero-cost abstractions）：抽象层在编译期会被优化掉，不引入额外运行时开销。

为什么迭代器不慢：零成本抽象

迭代器看起来“高级”，但编译器会把它们优化成与手写循环非常接近的底层代码： - 迭代器适配器（map/filter/zip/skip）是惰性的，本质上描述“做什么”，而不是“怎么写循环控制” - LLVM 会进行内联、消除边界检查、常量传播等优化 - 在某些固定长度循环里，编译器甚至可能 展开（unroll）循环，移除循环控制开销

这和 C++ 领域常说的 zero-overhead 原则一致：不用的就不付费；用到的也很难手写得更好。

基准测试结果怎么解读

书中举了一个例子：在大文本里搜索单词 "the"，for 循环与迭代器版的 search 性能非常接近，迭代器版甚至略快。

你不需要把结果理解成“迭代器永远更快”，更关键的是： - 两者通常等价或非常接近 - 选择迭代器风格往往能获得更清晰的表达，同时不牺牲性能

现实例子：迭代器链表达数学计算（音频解码器风格）

在一些对性能敏感的场景，也常用迭代器链表达“配对、映射、求和”等模式，例如： - coefficients.iter().zip(window).map(...).sum()

这类写法通常同样能被编译器优化成高效的机器码。
