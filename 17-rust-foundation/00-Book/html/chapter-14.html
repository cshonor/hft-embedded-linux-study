14.1

采用发布配置自定义构建

在 Rust 里，发布配置（release profiles） 是预定义、可定制的一组编译选项；不同配置彼此独立，用来在「开发时快速迭代」和「发布时优化运行」之间做权衡。

对应 demo 项目：00-Book/14-cargo-crates/14.1-profiles-demo/

Cargo 的两个主要配置

命令 使用的配置 典型用途
cargo build / cargo run dev 开发：默认不追求最高优化，编译更快
cargo build --release / cargo run --release release 发布：更高优化，运行更快，编译更慢

构建日志里的 dev / release 就是在标明当前用的是哪套配置。

默认与覆盖：[profile.*]

若 Cargo.toml 里没有 [profile.*]，Cargo 对每种 profile 使用内置默认值。

常见默认值（概念上）：

  • [profile.dev]：opt-level = 0（几乎不优化，编译快）
  • [profile.release]：opt-level = 3（较高优化，运行快）

opt-level 取值一般为 0～3：数值越大，优化越多，编译时间越长，通常 运行越快。

在 Cargo.toml 里增加对应小节即可只覆盖你想改的那几项，其余仍用默认。例如希望在 dev 下也用一点优化（比 0 强、比 release 弱）：

[profile.dev]
opt-level = 1

之后 cargo build 会沿用 dev 的其它默认，只把 opt-level 从默认的 0 改成 1。

完整选项与默认值以 Cargo 手册：Profiles 为准。

demo 说明

14.1-profiles-demo/Cargo.toml 里演示了在 dev 中设置 opt-level = 1。若你希望恢复「完全默认的 dev」，删掉 [profile.dev] 整段即可。

验证构建使用的 profile：

cd 00-Book/14-cargo-crates/14.1-profiles-demo
cargo build
cargo build --release
14.2

将 crate 发布到 Crates.io

crates.io 用来分发 crate 的源代码，通常面向开源。发布前需要：写好文档与对外 API、补全 Cargo.toml 元数据、登录账号，再用 cargo publish 上传。

对应 demo 项目：00-Book/14-cargo-crates/14.2-crates-io-publish-demo/（本地学习用，请勿随意 cargo publish）

文档注释：/// 与 //!

  • ///：写在紧挨着的下一个项之前，为该函数/类型等生成文档；支持 Markdown。
  • //!：为包含这段注释的容器写文档（常见于 src/lib.rs 或模块文件开头），用于描述 crate 或整个模块 的用途。

运行 cargo doc 生成 HTML 到 target/doc；cargo doc --open 会在浏览器中打开（含依赖文档）。

文档里常用小节

在 /// 中可用 Markdown 标题组织内容，例如：

  • Examples：用法示例
  • Panics：可能 panic! 的条件
  • Errors：若返回 Result，可能出现的错误
  • Safety：unsafe 相关约定（本书后文）

文档示例即测试：cargo test

文档注释里用 ** fenced code block（```） 写的示例会被当作 doc test** 运行。这样文档与代码不易脱节。

pub use 与对外 API

内部可以按模块拆分（kinds、utils），对外却可以用 pub use 重导出，让用户写成 use crate_name::Type 而不是深层路径。内部组织与对外展示可以解耦。

发布前：账号与 cargo login

  1. 在 crates.io 用 GitHub 登录
  2. 在账户页获取 API token
  3. 本地执行：cargo login <token>（token 会写入凭据文件，勿泄露）

Cargo.toml 元数据

发布时至少需要 description 与 license（或 license-file）。license 常用 SPDX 标识符，例如 MIT、Apache-2.0，或组合 MIT OR Apache-2.0。

还需全局唯一的 name（先到先得）。更多字段见 Cargo 手册：The package section。

cargo publish

  • 会打包并上传某一版本；已发布版本不可删除、不可覆盖（保证依赖长期可解析）。
  • 新版本：修改 version（建议遵循语义化版本）后再 cargo publish。

cargo yank

  • 撤回（yank）：阻止新项目把该版本写进依赖；已有 Cargo.lock 的项目仍可解析到该版本。
  • 示例：cargo yank --vers 1.0.1，撤销：cargo yank --vers 1.0.1 --undo
  • yank 不会删除已上传源码；误传密钥等需轮换密钥，不能指望“删掉版本”。

demo 命令

cd 00-Book/14-cargo-crates/14.2-crates-io-publish-demo
cargo test          # 含单元测试与 doc test
cargo run --example use_reexports   # 演示从 crate 根重导出后的 use 路径
cargo doc --open    # 查看渲染后的文档（可选）

Cargo 工作空间（Workspace）

← 前置：7.1 Package 与 Crate · 7.1.4 src/bin vs Workspace

一句话：Workspace = 一个大文件夹统一管好多个独立 Package；HFT、大型量化项目标配。

回顾：单个 Package 最多 1 个 lib、若干 bin；Workspace 可装 N 个 Package。

一、三层级（再也不混）

层级 是什么 例子
Workspace 最外层大容器；无 src/，只收纳多个 Package hft_workspace/
Package 子项目；各自 Cargo.toml + src/ engine/、gateway/
Crate Package 内部编译单元 engine/src/lib.rs（lib）· gateway/src/main.rs（bin） 
Workspace（hft_workspace/）
├ Cargo.toml          ← [workspace] members = [...]
├ Cargo.lock          ← 全工作区唯一一份
├ engine/             ← Package1
│  ├ Cargo.toml
│  └ src/lib.rs       ← lib crate
├ gateway/            ← Package3
│  ├ Cargo.toml
│  └ src/main.rs      ← bin crate
└ tools/              ← Package4
   ├ Cargo.toml
   └ src/bin/replay.rs

二、HFT 目录样板

hft_workspace/        ← 工作区根（无 src！）
 ├ Cargo.toml         ← 工作区总配置
 ├ Cargo.lock
 ├ engine/            ← Package1：交易引擎（lib）
 ├ market_data/       ← Package2：行情（lib）
 ├ gateway/           ← Package3：券商网关（bin exe）
 └ tools/             ← Package4：辅助 CLI（bin/*.rs）

顶层 Cargo.toml

[workspace]
members = [
    "engine",
    "market_data",
    "gateway",
    "tools",
]
resolver = "2"

写上 members，Cargo 认定这些文件夹都是受管控的子 Package。

三、核心三大好处（HFT 向）

1. 子 Package 之间轻松互相依赖

gateway/Cargo.toml：

[dependencies]
engine = { path = "../engine" }
market_data = { path = "../market_data" }

gateway/src/main.rs：

use engine::on_tick;
use market_data::decode;

fn main() {
    let tick = decode(b"BID 100");
    on_tick(tick);
}

2. 统一版本、共用一份 Cargo.lock

  • 全工作区只生成一个 Cargo.lock
  • 各成员依赖同一外部 crate 时解析为同一版本（HFT 对依赖一致性要求高）
  • 各成员仍须在自己的 Cargo.toml 声明依赖后才能 use

3. 批量编译 / 测试 / 指定运行

在工作区根目录：

命令 作用
cargo build 编译全部 member
cargo run -p gateway 只运行 gateway 这个 Package 的默认 bin
cargo test 跑全工作区测试
cargo test -p engine 只测 engine

产物在 workspace-root/target/（成员目录下通常不再各自一份 target/）。

四、和 src/bin/ 的区别（重点）

src/bin/（单 Package） Workspace（多 Package）
边界 同一项目内多个 exe，共用一套 lib 引擎 / 行情 / 网关 独立 Package
部署 多工具同仓库 进程可分开部署（低延迟隔离）
适用 迁移脚本、报表等小工具 HFT 多组件拆分

→ 详见 7.1.4

五、The Book 原版要点（demo 14.3-workspace-demo）

[workspace]
members = ["adder", "add-one", "add-two"]
  • adder 的 main 通过 path 依赖 add-one、add-two
  • crate 名 add-one → 代码里 add_one::…（连字符变下划线）

向 crates.io 发布时，每个 Package 单独 cargo publish；没有一次发布整个 workspace 的 --all。

场景 结构
小项目、单体 web 单个 Package + src/main.rs
同项目多 CLI 小工具 单 Package + src/bin/*.rs

14.3

.1 两种打包形态：单 exe vs 多 exe

← 主笔记：14.3 Cargo 工作空间 · demo：14.3-packaging-demo · 7.1.4

结论前置

Workspace 里每个 Package 都是独立项目，但打包结果分两种，完全分开：

形态 结构 产物 运行时
形态 1 lib Package + bin 依赖 lib 1 个 exe 单进程，函数调用，无通信
形态 2 多个 bin Package（各有 main.rs） N 个 exe 多进程，必须 IPC / 网络

Workspace 多 Package ≠ 天然微服务——取决于最后出几个 exe、开几个进程。

一、形态 1：lib + bin 依赖 → 只产出【单个 exe】

workspace/
├ Cargo.toml
├ core_lib/          ← Package A：仅 lib.rs，**无 main，不出 exe**
│  ├ Cargo.toml
│  └ src/lib.rs
└ app_bin/           ← Package B：main.rs，二进制 crate
   ├ Cargo.toml
   └ src/main.rs

app_bin/Cargo.toml：

[dependencies]
core_lib = { path = "../core_lib" }

编译逻辑

  1. 编译 core_lib → 生成库（.rlib 等）
  2. 编译 app_bin 时 把 core_lib 链接进来
  3. 最终只有 app_bin.exe 一个可执行文件

运行时

  • core_lib 永远不会单独出 exe（没有 main.rs）
  • core_lib + app_bin 代码 全在同一进程
  • 互相调用 = 普通函数调用，内存直接访问，不需要 socket / IPC

B 能用的内容，严格限于 A 的 lib.rs 里 pub 导出的项 → 7.1.5

demo → 14.3-packaging-demo（common lib + app_bin）

二、形态 2：多个 bin Package → 【N 个 exe】= N 个进程

workspace/
├ Cargo.toml
├ market_server/     ← main.rs → market_server.exe
└ strategy_app/      ← main.rs → strategy_app.exe

cargo build -p market_server   # exe 1
cargo build -p strategy_app    # exe 2

两个 exe 分开启动 → 两个 OS 进程，地址空间隔离，不能直接 use 函数调用。

跨进程通信（HFT 常用）

# 方式 场景
1 IPC（Unix 套接字、共享内存 mmap、本机 MQ） 同机，微秒级，HFT 本机内部
2 TCP/UDP / tonic(gRPC) 多机 RPC、UDP 行情广播
3 Kafka / Redis 中低频解耦、配置与持仓落地

demo → 14.3-packaging-demo/feed/ + trade/（各 1 exe，注释标明 IPC 位）

三、一句话区分

打包结果 进程 调用
Lib + Bin 依赖 1 个 exe 单进程 函数调用，无通信
Bin + Bin N 个 exe 多进程 IPC / 网络

四、补充：同一 Package 的 src/bin/

同一 Package 里 src/main.rs + src/bin/*.rs → 也是 多个 exe、多进程，同样需要 IPC。

区别只是 没拆成独立 Package，逻辑与 Workspace 多 bin 一致 → 7.1.4

五、HFT 组合范例

workspace/
├ common/        ← lib：结构体、工具，**永不出 exe**，被链接
├ feed/          ← bin → feed.exe
└ trade/         ← bin → trade.exe
  • common 被 feed、trade 各自链接进各自 exe（编译期）
  • feed.exe ↔ trade.exe：两个进程，本机用 共享内存 等发盘口（运行时）
// feed/src/main.rs（形态 2：进程内可调 common，跨进程需 IPC）
use common::format_tick;
fn main() {
    println!("{}", format_tick("BID", 100.0));
    // TODO: 写入共享内存 / Unix socket → trade 进程
}

六、与「微服务」的关系

层面 算不算微服务
Workspace + path 链接（形态 1） ❌ 代码组织
多 exe 分开部署 + 跨进程通信（形态 2） ✅ 微服务运行时

tonic RPC 示意 → 见旧版扩展；形态 1 内不要上 RPC。

demo 命令

cd 00-Book/14-cargo-crates/14.3-packaging-demo

# 形态 1：只有 app_bin.exe（common 被链进去）
cargo run -p app_bin

# 形态 2：两个独立 exe（需分别启动，进程间需 IPC）
cargo run -p feed
cargo run -p trade

14.4

使用 `cargo install` 从 Crates.io 安装二进制文件

cargo install 用于在本机安装并运行已在 crates.io 上发布的二进制 crate（带可执行目标的包）。它不是系统包管理器（如 apt、Homebrew）的替代品，而是方便 Rust 开发者快速安装别人发布的命令行工具。

本小节为工具与路径说明，无需单独 demo 项目；可在本机联网后自行尝试。

能装什么：二进制目标

只有 crate 里存在二进制目标时才能安装，例如：

  • 默认的 src/main.rs，或
  • [[bin]] 等配置出的可执行文件

纯库（只有 src/lib.rs、供别的程序依赖）不能通过 cargo install 变成“可运行程序”。具体是库、二进制或两者兼有，通常见 crate 的 README。

安装到哪里

用 rustup 默认安装时，二进制一般会装到 Rust 工具链根目录下的 bin：

平台 典型路径
Linux / macOS $HOME/.cargo/bin
Windows %USERPROFILE%\.cargo\bin

安装过程末尾会打印实际路径与可执行文件名（例如 ripgrep 包提供的命令往往是 rg）。

如何直接运行：加入 PATH

把上述 bin 目录加入系统的 PATH，才能在任意终端里直接输入命令名（如 rg --help），而不用写全路径。

示例：安装 ripgrep

cargo install ripgrep

成功后若 PATH 已包含 ~/.cargo/bin（或 Windows 下对应目录），即可：

rg --help

（包名是 ripgrep，可执行文件常见名为 rg，以安装输出为准。）

说明

  • 会从 registry 下载并编译指定版本，首次可能较久。
  • 与项目内 [dependencies] 不同：cargo install 面向全局/用户级工具安装；项目依赖仍写在各 crate 的 Cargo.toml 中。
14.5

Cargo 自定义扩展命令

Cargo 支持在不改 Cargo 源码的前提下扩展子命令：若在 PATH 中存在名为 cargo-<子命令> 的可执行文件，则可在终端里像内置子命令一样执行：

cargo <子命令>

例如磁盘上有 cargo-watch（具体名称以实际 crate 为准），则可直接运行：

cargo watch

实现方式：该可执行文件需以 cargo- 为前缀，Cargo 会把后面的部分当作子命令名转发执行。

与 cargo --list 的关系

安装或放置好自定义命令后，部分扩展会出现在 cargo --list 列出的一览中（具体以当前 Cargo 版本行为为准），便于发现本机已可用的扩展命令。

安装扩展

与安装其它二进制 crate 一样，通常可用 cargo install <crate名> 将提供 cargo-xxx 的工具装到 ~/.cargo/bin（Windows 多为 %USERPROFILE%\.cargo\bin），并确保该目录在 PATH 中。

本章小结

通过 Cargo 与 crates.io 分享代码，是 Rust 生态能覆盖多种任务的重要一环：标准库刻意保持小而稳定，而 crate 可以独立演进、版本节奏灵活。若在 crates.io 上发布对你有用的库或工具，也很可能同样惠及他人。
