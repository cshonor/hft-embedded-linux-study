Memory Terminology（内存术语）

所属：Talking About Memory · ← 章索引

进阶开发里若混淆 值 / 变量 / 指针，复杂借用错误会很难读懂。

值 (Value)

类型与该类型定义域内某个元素的组合。

  • 例如：u8 的 6 是一个值。
  • 意义独立于存储位置；可对应字节序列（如 0x06），但本质是逻辑对象。

变量 (Variable)

存放值的地方（容器 / 标签 / 具名内存区域）。

变量本身是一块（或一组）有名字的存储；值放在哪由类型 + 声明方式决定：

写法 变量（控制块）在哪 值 / payload 在哪
let x = 5 通常 栈 槽位 数字就在槽里
let b = Box::new(10) 栈 上的 Box 结构体 10 在堆；栈上存「指向堆的指针 + 元数据」
let s = String::from("hi") 栈 上的 String 结构体 字节在堆；栈上是 { ptr, len, cap }
static N: i32 = 0 Data / BSS（进程生命周期） 与变量同一静态区
&"hello" 里的 "hello" 无 let 变量名 字面量在 只读段（Text 旁 rodata）

→ 分区细节见 03 内存区域（Safe Rust → 03.1；OS/LLVM → 03.2）。

注意：说「变量在栈上」有时指这个 let 绑定的槽在栈上；若类型内含指针，它指向的数据可能在堆上（Box、String 都是这种「栈上控制块 + 堆上 payload」）。

指针 (Pointer)

其存储的值是内存地址的变量。

Rust 里的 &T / &mut T 在机器层面可理解为指针，但附加了语言规定的协议：

  • 别名规则（共享 vs 独占）
  • 对齐与有效性 (validity)
  • 生命周期约束

借用、Box、裸指针 — 是不是「都是指针」？

机器层面：很多类型内部都存地址或就是地址，可以宽泛地说「和指针有关」。

类型层面：Rust 不会把「指针」和「借用」画等号 — 它们是不同概念：

是什么 所有权 编译器约束
裸指针 *const T / *mut T 纯地址 无 几乎无；操作在 unsafe
借用 &T / &mut T 带协议的指针 不拥有数据；临时查看/修改 生命周期 + 别名规则（共享 / 独占）
Box<T> 拥有堆内存的智能指针 拥有堆上 T；drop 时释放 独占所有权，可移动
String / Vec 比 Box 更复杂的智能指针 拥有堆上 buffer 同上 + len/cap 等语义

串起来记：

裸指针     = 只有地址，自己负责合法
借用       = 地址 + 「我不能抢所有权、不能乱别名」
Box        = 地址 + 「这块堆归我，到期我释放」
String     = 地址 + len/cap + 「这块堆归我，到期我释放」

所以：借用是指针的一种安全用法，但不是「指针 ≡ 借用」；Box 也是指针类抽象，但是拥有型，不是借用。

赋值在说什么

要点：= 把右侧表达式的值写入左侧命名的位置 (place)。

区分「槽里换了什么比特」与「引用仍指向同一槽位」——后文在 02 变量深入 用双模型展开。

你平时看到的 vs 底层真正是什么

Rust 里指针相关可以分成三层理解（由安全到裸）：

层级 例子 是什么
安全包装 Box<T>、String、Vec<T>、&T / &mut T 编译器 enforced 的所有权 / 生命周期 / 别名规则
标准库内部 String 里的 ptr: *mut u8 + len + cap 用 unsafe + 裸指针 + Drop 自己实现「类似 Box + 扩容」
裸指针 *const T、*mut T 和 C 的 const T* / T* 同级的地址；几乎无安全协议

结论：String 不是 Box<str> 类型，也不是借用；它是栈上的结构体，三个字段里只有 ptr 是指针，len/cap 是普通 usize。

// 概念上等价于标准库内部（简化，非逐字源码）
struct String {
    ptr: *mut u8, // 裸指针 → 堆上 UTF-8 字节
    len: usize,
    cap: usize,
}
  • String::from("hello")：堆上分配字节 → 把地址、len=5、cap=5 写进栈上的 String。
  • let s = String::from("hello") 创建的是 String 结构体实例（类型就是 String），不是「某种神秘指针类型」；只是这个结构体设计得像智能指针。
  • 离开作用域：Drop 按 ptr/cap 释放堆 — 和 Box drop 释放内存同一类逻辑，只是 String 多管了 len/cap 与 UTF-8 语义。

Vec<T> 同样是 { ptr, len, cap } + 自定义 Drop，不是 Box<[T]>。

裸指针 *const T / *mut T

Rust 近似 C/C++ 含义
*const T const T* 只读裸指针
*mut T T* 可写裸指针
  • 所有数据类型的裸指针都是这两类泛型实例：*mut i32、*const u8、*mut String ……
  • 运行时它们通常就是一个 地址（64 位下 often 8 字节），T 是编译期注解；和 void* 再强转类似，但 Rust 要求显式类型。
  • 创建、解引用裸指针要在 unsafe 里（或位于 unsafe fn 中），因为编译器不帮你保证：非 null、对齐、生命周期、无数据竞争。
let mut x = 42_i32;
let p: *mut i32 = &mut x as *mut i32; // 借用 → 裸指针（coerce 常在此步）
unsafe {
    *p += 1; // 像 C 一样解引用
}

和 &mut T 的区别：借用带生命周期 + 别名规则；裸指针没有，全靠你自己保证合法。

只有这两种吗？

指向数据的标准裸指针类型就是 *const T 和 *mut T 两个家族（泛型参数换 T 即可）。

其它相关、但不算「多一种数据裸指针」的：

类型 说明
fn(...) -> R / fn(...) -> R 函数指针 指向代码（Text 段），不是指向堆/栈数据的 *mut T
NonNull<T> 封装「非 null 的 *mut T」，仍基于裸指针，便于 niche 优化
usize 存地址 纯整数，不是指针类型；和裸指针可 as 互转，更易踩 UB

日常业务用 Box / String / Vec / 借用；HFT / 驱动 / 共享内存 / FFI 才在 unsafe 里用 *mut T，并自己承担 C 级内存责任。

Variables in Depth（变量深入）

所属：Talking About Memory · ← 章索引

同一套「变量」概念，在不同问题下用两个互补模型思考 — Rust 给开发者的「双重视角」。

新手从哪一层入门？

从高层（数据流）开始。 Book、所有权、& / &mut、生命周期、函数传参、迭代器 — 全是这一层：

  • 你写 let r = &x，不必先想「r 指向栈上哪条地址」
  • 只需理解：借来了读/写权限；编译器检查生命周期、有没有和 &mut 冲突

高层模型故意屏蔽地址、槽大小、堆栈细节，让你先建立「值怎么流动、谁能在何时访问」的安全思维。

等你写 unsafe、看 LLVM IR、做布局/低延迟优化时，再切底层（内存槽）：变量 = 固定地址的一块存储，改值常是改槽内比特、地址不变。

高层 · 数据流 底层 · 内存槽
视角 逻辑 / 编译器安全 硬件 / 物理存储
变量是什么 数据流里的节点 栈或静态区里固定大小的块
引用是什么 带规则的读/写权限 往往涉及地址（机器上像指针）
典型场景 日常业务、学语法、HFT 业务逻辑 unsafe、裸指针、FFI、06_Compilers-and-LLVM-Learning/04_Learn-LLVM-17、极致优化
你要关心的 谁拥有、谁借用、能借多久 槽在哪、多大、地址变不变、比特怎么变

两层不矛盾：同一行 let mut x = 5; x = 10; 在高层是「绑定可变、重新赋值」；在底层是「同一槽、改里面存的数」。HFT 常见路径：高层保安全 → 热点路径再切底层抠性能。

高层模型：数据流 (Data Flow)

何时用：生命周期、借用、跨函数传引用。

  • 变量是数据流的节点；借用检查器追踪值如何经引用在节点间流动。
  • 冲突规则：同一数据上若同时存在违反协议的独占流（&mut）与共享流（&），编译拒绝。

底层模型：内存槽 (Slots)

何时用：unsafe、原始指针、布局、06_Compilers-and-LLVM-Learning/04_Learn-LLVM-17 读 IR。

内存槽到底是什么？（纯 Rust，一句话）

内存槽 = 编译器为某个 let 绑定划出的 固定地址 + 固定大小 的一块存储；从声明到离开作用域，槽的位置和大小不变，变的只是槽里存的比特。

let mut x: u32 = 5;
// 栈上开 4 字节槽，假设地址 0x1000
println!("{:p}", &x); // 0x1000
x = 10;               // 槽还在 0x1000，只是把里面的 5 改成 10
println!("{:p}", &x); // 还是 0x1000
  • 槽 = 那块 4 字节的物理存储（place / location）
  • 变量名 x = 编译器符号表里「名字 → 这个槽」的标签（不是运行时指针）
  • mut = 允许改写这个槽里的内容（不是移动槽、不是改槽的大小）

String 同理：let mut s = String::from("hi") 在栈上占一个固定大小的槽（64 位下通常 24 字节：ptr + len + cap）。s.push('!') 时 s 这个槽的地址不变，变的是槽里的 len（以及可能触发的堆扩容）。

  • 变量对应栈（或静态区等）上的槽位，大小由类型在编译期确定。
    例：let x: usize → 栈上固定大小槽位。
  • 重新赋值通常不改变「&x 指向该槽位」的地址语义（槽位仍在），变化的是槽内比特。
  • 与「引用指向的对象整体被移动/替换」要在具体语境下区分——见 04 所有权。

两模型如何配合

问题 优先模型
「为什么这里不能同时有 & 和 &mut？」 数据流
「这个 *const T 指向的地址还合法吗？」 槽位 + 有效性
「优化器能否合并两次 *r 读取？」 数据流上的别名协议 → 05 共享引用

mut 与 &mut：都是在「开修改槽位的权限」

先回答最常见的问题：改槽里的内容，要不要 mut？

改法 写法 需要什么
直接改变量 let mut x = 5; 然后 x = 10; 声明时 let mut x
通过借用改 let mut x = 5; 然后 *(&mut x) = 10; 声明时 let mut x + 借用时 &mut
遮蔽（换一个新槽） let x = 5; 然后 let x = 10; 不要 mut（这不是改旧槽，是开新槽换绑名字）

所以：只要你是「改同一个槽里的内容」，无论直接写变量名还是走 &mut，原变量都必须先 let mut 解锁。
&mut 不是 mut 的替代品，而是「在仍需要 let mut 的前提下，多一条临时修改路径」。

作用
let mut x 允许直接改这个槽（x = 10），也允许借出 &mut x
let x（不可变） 槽内比特焊死：不能 x = 10，也不能 &mut x
&mut T（可变借用） 允许通过这条借用路径改它指向的那个槽；前提是原变量已是 mut 
let mut s = String::from("a");
s.push('b'); // 需要 s 是 mut：push 要改栈上 {ptr,len,cap}，可能还要改堆

常见误区：「不可变变量只能借 &mut 来改」——不对。&mut 的前提是 let mut 已解锁；若只有 let x，连 &mut x 都拿不到。

想「变」：三种不同机制

机制 写法 改的是啥 要 mut 吗
变量遮蔽 (shadowing) let x = 5; 再 let x = 10; 新开一个槽，符号表把名字 x 改绑到新槽 不要
重新赋值 let mut x = 5; 再 x = 10; 同一个槽里的比特 要
可变借用改槽 let mut y = 5; 再 *(&mut y) = 10 同一个槽里的比特 要（原变量） 
// 遮蔽：新槽位，地址会变
let x = 5;
let p1 = &x as *const i32;
let x = 10;              // 新 let → 新槽；旧槽还在栈帧里，只是名字 x 不再指向它
let p2 = &x as *const i32;
// p1 != p2（通常）

// 可变引用：同一槽位，地址不变
let mut y = 5;
let p3 = &y as *const i32;
let r = &mut y;
*r = 10;
let p4 = &y as *const i32;
// p3 == p4

遮蔽后若还持有指向旧槽的引用，借用检查器会拒绝（生命周期/遮蔽规则）：

let x = 5;
let r = &x;
let x = 10;   // 遮蔽
// println!("{r}"); // 编译错误：r 仍指向已被遮蔽的旧绑定

→ 可变借用细节见 06 可变引用；内部可变性（无 mut 也能改）见 07。

变量名是什么？像指针吗？

不像运行时指针。 变量名是编译器符号表里的条目：名字 → 当前作用域内生效的那个槽位。

  • let x = 5：在栈上开槽 1，符号表 x → 槽 1
  • let x = 10（遮蔽）：在栈上开槽 2，符号表 x → 槽 2（不是改槽 1 里的数）

可以想成字典：key = 变量名，value = 当前绑定的槽；遮蔽是换绑 value，不是改旧槽里的比特。

被遮蔽的旧槽何时释放？

不会马上释放。 栈按栈帧 / 作用域整块回收：遮蔽只让名字不再指向旧槽，旧槽仍占着栈空间，直到整个 { ... } 或函数结束才和帧内其它槽一起弹栈。

这对性能是利好：遮蔽几乎零分配成本；也配合借用检查，避免「名字已换绑、旧引用仍指向旧槽」的悬垂访问（能编译过的代码里这类情况会被拦住）。

→ 内存分区见 03 内存区域（03.1 Rust 三分类 · 03.2 OS 五分区）；术语见 01 内存术语。

为什么 Rust 只分三类？

RFR / Book 把进程内存收成 栈 / 堆 / 静态，是因为 safe Rust 的规则按这三类管：

Rust 分类 典型内容 Safe Rust 怎么管
栈 (stack) let 局部变量、函数参数、调用帧 进函数分配、出函数销毁；与作用域对齐
堆 (heap) Box / Vec / String 的 payload 所有权 + Drop；无 GC

OS 还有 Text / Data / BSS / mmap 等 — 那是 03.2 的事。日常写 safe 代码，三分类足够。

栈：自动、快、有上限

fn foo() {
    let x = 42;           // x 在 foo 的栈帧里
    let arr = [0u8; 1024]; // 数组也在栈（若太大可能改放栈外，见下方）
} // foo 返回 → 整帧弹出，x、arr 自动销毁
分配 / 释放 编译器 + 调用约定：压栈 / 弹栈
速度 极快（改栈指针）
大小 每线程固定上限 → 递归过深 stack overflow
和借用的关系 借用检查里的「作用域」多与栈帧生命周期对齐

大对象：非常大的栈数组可能触发 stack overflow；超大缓冲常放堆（Vec）或静态。

堆：动态、句柄在栈、实体在堆

fn main() {
    let b = Box::new(100);              // b（句柄）在栈；100 在堆
    let s = String::from("hello");      // s（{ptr,len,cap}）在栈；字节在堆
    let v = vec![1, 2, 3];              // 同理
} // drop 顺序：先释放堆 payload，再弹栈
栈上的「句柄」 堆上的 payload
Box<T> Box 结构体（指针） T
String { ptr, len, cap } UTF-8 字节
Vec<T> { ptr, len, cap } T 元素数组

所有权在做什么：栈上变量（如 b: Box<i32>）拥有堆块；离开作用域 → Drop 释放堆，避免泄漏。→ 04 所有权

栈 堆

速度 极快 较慢（分配器、可能向 OS 要页）
典型 Rust let x = 42; Box::new(100) 里的 100

静态：static 与 'static

static GLOBAL: i32 = 100;       // 进程全程存活
static mut COUNTER: i32 = 0;    // 可改须 unsafe

fn main() {
    let r: &'static str = "hi"; // 字面量；数据常在只读段（见 03.2）
}

static mut 须 unsafe；多线程还要防数据竞争 → 优先 OnceLock 等

为什么要分区？（OS 逻辑）

04.2

· Move / Copy / Clone（一次讲透）

← 04 所有权索引 · 上一节：04.1-three-rules.md · 下一节：04.3-drop.md

核心：不是「堆 Move、栈 Copy」，而是 Copy trait

Rust 不按栈/堆决定 Move 还是 Copy，而看类型是否实现 Copy：

实现了 Copy 未实现 Copy（默认）
赋值 / 传参 自动按位复制栈上表示；原绑定仍有效 Move：所有权转移；原绑定失效
堆上 payload Copy 类型通常没有需 drop 的堆（或整值在栈） Move 不复制堆数据，只转移所有权

反例 — 栈上也可以 Move：

let a = Box::new(10);  // 句柄在栈，数据在堆；Box 无 Copy
let b = a;             // Move，a 失效

struct Point { x: i32, y: i32 }  // 全在栈，默认仍无 Copy
let p1 = Point { x: 1, y: 2 };
let p2 = p1;           // Move，p1 失效

为何有「栈 Copy、堆 Move」的错觉？
大部分小标量默认 Copy（在栈）；String / Vec / Box 等带堆或自定义 Drop 的类型默认不 Copy — 相关，但不是因果。

典型 Copy 类型

  • 整数 / 浮点：i32、u64、f64 …
  • bool、char
  • [T; N]（T: Copy 时）
  • (T1, T2, …)（各元素均 Copy 时）
  • &T（共享引用是 Copy）
  • 不是 Copy：&mut T、String、Vec、Box<T>、多数自定义 struct/enum
let a: i32 = 10;
let b = a;              // Copy：复制 4 字节，a、b 都有效
println!("{a} {b}");

Move 的本质：转移所有权，不是复制堆

let s2 = s1;（String）时：

  1. 栈上 { ptr, len, cap } 按位复制一份给 s2（机器层面像 memcpy）
  2. 堆上字节只有一份 — 所有权从 s1 转到 s2，不做堆深拷贝
  3. 编译器标记 s1 失效，不能再访问
  4. 作用域结束时只有 s2 负责 Drop 堆
let s1 = String::from("hello");
let s2 = s1;   // Move
// println!("{s1}"); // ❌

→ 需要两份堆数据时用 clone()，不是赋值。

Copy vs Clone

Copy Clone
何时发生 赋值、传参时隐式 必须显式 .clone()
语义 按位复制栈上表示（浅拷贝） 可自定义；String::clone() 会复制堆
开销 极小（几个字节） 可能很大（整段堆分配 + 拷贝）
实现 Copy + Clone（通常 derive）；不能自定义 Copy 逻辑 impl Clone 可手写
与 Drop 有自定义 Drop 则不能 Copy 与 Drop 可共存 
let a = 10;
let b = a;                    // Copy

let s1 = String::from("hello");
let s2 = s1.clone();          // Clone：堆上完整复制一份
println!("{s1} {s2}");         // 两者都有效

let s3 = s1;                    // Move（若写这句则 s1 失效）

记忆：Copy = 隐式、便宜、原变量还在；Clone = 显式、可能贵、两份独立数据。

一句话

Move / Copy 由 Copy trait 决定，不由栈/堆决定：
有 Copy → 赋值时自动按位复制，原绑定有效；
无 Copy → Move，原绑定失效，堆数据不复制、只转移所有权；
要 duplicate 堆内容 → .clone()。

let v = vec![1, 2];
let w = v;           // Move
// let u = v.clone(); // 若先要 v 再用，先 clone 再分别 move

let x = 5;
let y = x;           // Copy
println!("{x} {y}");

速记

三句背诵

  1. 三条规则：唯一所有者 · 出作用域 drop · 非 Copy 则 move。
  2. Move/Copy 看 Copy trait，不看栈/堆；要两份堆 → .clone()。
  3. 局部变量 drop 逆声明；struct 字段 drop 正定义 — 方向相反。

04.3

· Drop 是什么 · `Box` · 自定义 Drop

← 04 所有权索引 · 上一节：04.2-move-copy-clone.md · 下一节：04.4-drop-order.md

Drop 基础

  • 类型可实现 Drop trait：离开作用域时编译器插入 drop() 调用。
  • String / Vec / Box：drop 时释放堆（见 03.1）。
  • 引用 &T / &mut T：不拥有值，drop 引用不会释放被指向的数据；只有所有者 drop 时才释放。
let x = String::from("hi");
let k = &x;     // k 是借用，不是所有者
// 作用域结束：只 drop x（释放堆）；k 作为引用无堆责任

Box<T>、嵌套类型的 drop

let b = Box::new(String::from("hi"));
// drop 时：先 drop Box 管理的堆上 String，再清理 Box 自身（栈上句柄）
  • Box<String>：栈上 Box 句柄 + 堆上 String；drop Box 时按 Box 的规则释放堆上 T。
  • struct 多字段：外层 struct 按字段正序 drop；每个字段再按自己的类型规则 drop（如 String 释堆）。

自定义 Drop：亲眼看到逆序

局部变量按逆声明 drop（见 04-4）：

struct Custom {
    name: String,
}

impl Drop for Custom {
    fn drop(&mut self) {
        println!("Dropping Custom: {}", self.name);
    }
}

fn main() {
    let a = Custom { name: "A".into() };
    let b = Custom { name: "B".into() };
}
// 输出：
// Dropping Custom: B
// Dropping Custom: A
04.4

· Drop 顺序（重点 · 易混）

← 04 所有权索引 · 上一节：04.3-drop.md · 下一节：04.5-refs-and-panic.md

核心结论：局部变量的销毁遵循栈 LIFO（后进先出） — 后声明 → 先 Drop；先声明 → 后 Drop。这和声明顺序正好相反。

复合类型（struct / 元组）内部字段则按定义正序 Drop — 与局部变量方向相反，最易混。

1. 局部变量、函数参数：栈 LIFO → 逆声明顺序

后压栈的先出栈：后声明的先 drop。

fn main() {
    let a = String::from("A"); // 先声明，先入栈（栈底侧）
    let b = String::from("B"); // 后声明，后入栈（栈顶侧）
} // 出栈：Drop(b) → Drop(a)

原因：后声明的绑定可能依赖先声明的（let a = ...; let r = &a;）。若先 drop a，r 可能悬垂 → 故先结束 / drop 后声明的，再 drop 先声明的所有者。

let x = String::from("x");
let r = &x;   // r 后声明 → r 先结束 → 再 drop x

引用 &T / &mut T：无所有权，不触发对被指向值的 Drop；只影响「借用何时结束」，不改变所有者 drop 的时机。

2. 嵌套作用域：内层先于外层（仍是 LIFO）

内层块里的变量在外层之前销毁：

fn main() {
    let outer = String::from("外");

    {
        let inner = String::from("内");
    } // 块结束：Drop(inner) — 立刻

} // 函数结束：Drop(outer)

执行顺序：Drop(inner) → … → Drop(outer)。

3. 复合类型内部字段：正序（定义顺序）

结构体、元组、数组元素等：先定义的字段先 drop（与 §1 局部变量相反）。

struct Foo {
    x: String, // 先定义
    y: String, // 后定义
}

fn main() {
    let f = Foo { x: "X".into(), y: "Y".into() };
} // Drop(x) → Drop(y)

对照（面试常考）

场景 Drop 顺序 记忆
函数内多个局部变量 逆声明（栈 LIFO） 后声明先死
嵌套 { } 块 内层先于外层 小块先结束
同一 struct / 元组字段 正定义序 先定义先死
函数参数 逆参数列表顺序 同局部变量

⚠️ 局部变量（逆）vs struct 字段（正）— 方向相反。

一句话区分

  1. 函数里单独的 let：栈 LIFO → 逆声明顺序销毁
  2. struct / 元组成员：按源码定义顺序 → 正序销毁
  3. &T：不拥有、不 Drop 目标，只结束借用

3.1

Shared References（共享引用 `&T`）

所属：Borrowing and Lifetimes · ← 章索引

前置 → 04 所有权 · Move/Copy/Drop · 术语 → 01 内存术语

核心语义：共享引用是什么

共享引用 &T = 只读借用 — 在引用存活期内：

  • 可以同时存在多个 &T 指向同一数据（多读）
  • 不能同时存在 &mut T 指向同一数据
  • 不能通过所有者或其它合法路径直接修改该内存（除非走 07 内部可变性）

这就是 单写多读（Single Writer, Multiple Readers） 规则的一部分 — Rust 内存安全与优化的基石。

let x = 42;
let r1 = &x;
let r2 = &x;     // ✅ 多个 &T 共存
println!("{r1} {r2}");
// let m = &mut x; // ❌ 已有共享借用时不能再 &mut

大白话：&T 是「我借来看，大家都可以看，但谁也不能在这段时间里改（常规路径）」。

别名组合规则（一眼表）

对同一内存位置在同一时刻：

组合 是否允许
多个 &T ✅
一个 &mut T ✅
&T + &mut T ❌
多个 &mut T ❌

→ 可变借用详见 06 可变引用

引用不重叠：编译期借用检查器 enforcement；违反则编译失败。

与 LLVM / 优化器

共享引用不只是语法 — 也是给优化器的契约：

借用 向优化器承诺 LLVM 可做什么
&T 存活期内不会被突变（no-mutation / readonly 语义） 重复读可合并、缓存到寄存器；死代码消除、循环不变量提升等
&mut T 独占、无别名冲突（noalias） 更激进的指针别名分析与 store/load 优化 
fn sum_twice(r: &i32) -> i32 {
    *r + *r   // 优化器可能只从内存读一次 *r
}

为何重要（HFT / 性能）：安全 Rust 里写 &T，编译器能假定「这段期间没人改」— 不必每次读都当成可能 alias 的 wild pointer。读 IR 时见 06_Compilers-and-LLVM-Learning/04_Learn-LLVM-17 ch04。

与内部可变性的关系：RefCell / Mutex 等刻意 opt-out 普通 &T 的 no-mutation 假设 — 见 07，否则 LLVM 会按「只读」做错误优化。

&T vs C 的 const T*

&T（Rust） const T*（C）
只读访问 ✅ ✅
生命周期 ✅ 编译期检查 ❌ 无
别名规则 ✅ 与 &mut 互斥 ❌ 可随意 cast 成 T*
悬垂 能编译通过则通常安全 全靠程序员

Rust 的 &T 不是「带类型的 const 裸指针」— 还编码能借多久、能和谁共存。

内部可变性：看起来是例外

外表可以是 &RefCell<T>（共享引用），内部仍可在运行时借 mut — 规则由 RefCell 自己检查，违反则 panic。

use std::cell::RefCell;

let data = RefCell::new(5);
let r = &data;              // 共享引用 RefCell 容器本身

*r.borrow_mut() += 1;       // 运行时独占 borrow，改内部
println!("{}", r.borrow()); // 6

// 多个 & 指向同一 RefCell 可以，但不能同时 borrow_mut
let data = RefCell::new(5);
let r1 = &data;
let r2 = &data;

{
    let _a = r1.borrow_mut(); // 持有 mut borrow
    // let _b = r2.borrow_mut(); // ❌ 运行时 panic：已有 mut borrow
}
  • 编译期：多个 &RefCell<T> 合法
  • 运行时：borrow / borrow_mut 仍互斥 — 与 07 内部可变性 一致

多线程 → Mutex<T> / RwLock<T> 等同理，见 第 10 章 并发。

常见误区

误区 纠正
「有 &T 就完全不能改」 直接改不行；内部可变性（RefCell / Mutex / Cell）是显式例外
「有 &mut 就完全不能改」 &mut 就是改的路径；不能的是同时再有冲突的 & / &mut
「&T = C 的 const T*」 还有生命周期 + 别名协议
「多个读者 = 可以随便改内部」 只有 UnsafeCell 系封装在规则内改；普通 &T 到 i32 不能改
「优化与借用无关」 &T / &mut T 的假设直接喂给 LLVM

和所有权的关系

所有者 T 共享引用 &T
拥有数据 ✅ ❌（只借看）
触发 Drop ✅ ❌（只结束借用）
赋值 / move 转移所有权 Copy（复制指针 + 生命周期）

3.2

Mutable References（可变引用 `&mut T`）

所属：Borrowing and Lifetimes · ← 章索引

前置 → 05 共享引用 &T · 04 所有权

一、核心语义

可变引用 &mut T 的两条硬性规则，是借用检查器的核心约束：

  1. 独占借用
    同一块内存，在同一时间点，不能同时存在任何冲突引用： - 不能同时有第二个 &mut T； - 不能同时存在任意数量共享引用 &T。

  2. 唯一可变路径保证
    强制任何时刻只有一条合法途径修改目标数据，从语法层面杜绝数据竞争，实现内存安全。

let mut x = 10;
let r = &mut x;
*r += 1;   // ✅ 通过独占路径修改

大白话：&mut T 是「这段时间只有我能改，别人既不能看（&T）也不能改（另一个 &mut）」。

二、对编译器优化的作用（no-aliasing）

&mut T 向编译器承诺：当前不存在其他指向同一块数据的有效引用，即 no-aliasing（无别名）。

基于该假设，编译器可以做激进优化：

  • 指令重排、循环向量化；
  • 消除重复读写内存操作（冗余 load / store）。

这是 Rust 兼顾内存安全、同时逼近 C 运行性能的关键特性之一。

fn double(r: &mut i32) {
    *r = *r * 2;   // 优化器可假定 r 无其它别名，不必保守重读内存
}

为何重要（HFT / 性能）：热路径里写 &mut T，LLVM 能按 noalias 做 store/load 优化 — 读 IR 见 LLVM ch04。

与内部可变性的关系：RefCell / Mutex 等会 opt-out 部分假设 — 见 07 内部可变性。

三、&T 共享引用 vs &mut T 可变引用

特性 共享引用 &T 可变引用 &mut T
别名规则 允许多个同时共存 同一内存仅允许一个独占借用
修改数据权限 默认禁止修改内部数据 允许修改引用指向的数据
编译器优化假设 存活期内不会被突变（readonly） 无其它别名，可激进优化（noalias）
赋值时 Copy（复制指针 + 生命周期） Copy（同上）

对同一内存位置在同一时刻：

组合 是否允许
多个 &T ✅
一个 &mut T ✅
&T + &mut T ❌
多个 &mut T ❌

四、典型非法代码（违反独占规则）

let mut x = 10;
let r1 = &mut x;
let r2 = &mut x; // ❌ 编译报错：同一内存存在两个可变引用

let r3 = &x;     // ❌ 编译报错：可变借用期间不能再有共享引用

编译器在编译期拒绝，不会留到运行时才发现数据竞争。

五、合法场景：借用生命周期分离

只要可变引用作用域结束（最后一次使用之后），就可以重新创建其它引用：

let mut x = 10;
{
    let r1 = &mut x;
    *r1 += 1;
} // r1 生命周期结束，独占借用释放

let r2 = &mut x; // ✅ 合法
let s1 = &x;     // ✅ 合法（多个 &T 也可）

记忆：冲突的是同一时刻的重叠借用，不是「曾经借过就永远不能借」。

六、no-aliasing 与 C restrict

C restrict Rust &mut T
无别名保证 程序员手动声明 借用检查器强制校验
违反后果 UB（编译器仍可能优化） 编译失败（常规 Safe 代码）
优化收益 可能获得 noalias 类优化 同等优化假设，且默认安全

Rust 把「这段期间无其它别名」写进类型系统，不必像 C 那样靠约定和审查。

七、常见误区

误区 纠正
「&mut 不能 Copy」 &mut T 赋值/传参是 Copy（复制指针），复制的是借用权，不是数据所有权
「出了块就能随便 &mut」 须等所有冲突借用结束；嵌套作用域要逐层分析
「&mut 和 C 的 T* 一样」 &mut 有生命周期 + 独占协议；裸指针无
「noalias 与性能无关」 热循环里 &mut 直接影响 LLVM 是否消除冗余内存访问
「有 &mut 就能绕过内部规则」 &mut RefCell 等仍受运行时 borrow 规则约束（见 07）

八、和所有权的关系

所有者 T 可变引用 &mut T
拥有数据 ✅ ❌（只借改）
触发 Drop ✅ ❌（只结束借用）
修改数据 通过绑定本身 通过解引用 *r

规则

要点 说明

struct User {

}

    fn into_id(self) -> u32 {
        self.id
    }
}

fn main() {
    let u = User { id: 100 };
    let num = u.into_id();
    // println!("{}", u.id); // ❌ u 所有权已移走

规则

要点 说明

修改 方法内只能读字段，不能直接改
并发借用 同一实例可同时存在多份 &self

查询、读取属性，不改动数据 — 默认首选。

五、与内部可变性：&self 签名下仍能改字段

方法签名是 &self（整体只读借用）时，若某字段包了 Cell / RefCell，仍可在方法内修改该字段 — 内部可变性的经典入口。

use std::cell::RefCell;

struct User {
    id: u32,
    visit_cnt: RefCell<u32>,
}

impl User {
    // 签名仍是 &self
    fn add_visit(&self) {
        *self.visit_cnt.borrow_mut() += 1;
    }
}
层面 看到什么
方法签名 &self — 结构体绑定层只读
字段层 RefCell 在运行时借出 RefMut，改盒内计数

外部看方法是只读调用；内部改的是容器里的数据 — 详见 07.4 应用场景。

  3. 调用完实例没用了 → self（消耗型）
  4. 签名被钉死 &self 却要改状态 → 字段包 Cell / RefCell → 07

一、外部可变性（前置）

let / let mut 控制绑定层能不能改 — 编译期静态检查：

3.3

.3 · Cell\<T\> 与 RefCell\<T\> · 计数器与底层原理

所属：Borrowing and Lifetimes · 内部可变性 · ← 07 hub

← 07.2 UnsafeCell · 下一节 07.4 应用场景

本节只讲 Cell / RefCell 本身（不涉及 Rc 组合；多所有者场景见 07.4）。

零、三条核心结论

  1. Cell 内部没有任何计数器；只有 RefCell 才有读写借用计数器。
  2. 二者都没有打破「多读 互斥 单写」的安全铁律：
    - 普通 let mut + &mut → 编译期检查；
    - RefCell → 同一套规则，改由运行时计数器检查（冲突 panic）；
    - Cell → 不产生引用、只拷贝，从根源避开读写共存，不需要计数器。
  3. 二者能实现内部可变性的共同根基：UnsafeCell<T> + 标准库内部的 unsafe 裸指针操作，对外暴露 Safe 的 get/set 或 borrow/borrow_mut。

一、共同底层：UnsafeCell + 库内 unsafe

正常情况下，通过 &T 不能改背后的 T。内部可变容器在内部持有：

// 概念结构（简化）
struct UnsafeCell<T> {
    value: T,  // 编译器允许通过 &self 拿到 *mut T 修改（仅 unsafe 块内）
}
层 谁做
UnsafeCell opt-out「&T 永不修改」的优化假设
标准库 unsafe 块 用 *mut T 在 get/set/borrow_mut 里读写 value
对外 API Cell::get / RefCell::borrow 等 — 调用方 Safe 
你调用 .borrow_mut()  →  Safe 接口
        ↓
RefCell 内部 unsafe { *UnsafeCell::get_mut(...) }
        ↓
同时 borrow_flag 保证：此刻没有其它活跃 Ref/RefMut

→ 详述 07.2 · Nomicon 五种 unsafe 能力

二、RefCell<T>：带借用计数器，运行时管控互斥

1. 内部结构（简化）

struct RefCell<T> {
    borrow: BorrowFlag,      // ← 唯一的「计数器」状态机
    value: UnsafeCell<T>,
}

BorrowFlag 在实现上常编码为 有符号整数（概念上）：

状态 含义
> 0 当前有 n 个活跃 Ref（只读借用）
0 无活跃借用
-1 有 1 个活跃 RefMut（独占写）

2. 计数器规则（与编译期借用同一条铁律）

同一时刻：要么多个只读，要么至多一个可变写 — 绝不能共存。

.borrow() → Ref<T>

1. 若当前为写状态（-1）→ panic
2. 否则读计数 +1
3. 返回 Ref<T>（守卫：Drop 时计数 -1）

.borrow_mut() → RefMut<T>

1. 若读计数 ≠ 0，或已有写 → panic
2. 标记为写状态（-1）
3. 返回 RefMut<T>（Drop 时恢复 0）

关键点：计数归零才能写

let c = RefCell::new(10);
let r = c.borrow();       // 读计数 = 1
// let w = c.borrow_mut(); // ❌ panic：读计数 ≠ 0
drop(r);                  // 读计数 = 0
let mut w = c.borrow_mut(); // ✅
*w = 20;

一句话：RefCell 只是把编译报错换成运行时计数器 panic；读写互斥规则一点没变。

3. 为何能透过 &RefCell 改内部

外层是 let x = RefCell::new(...) 或 &RefCell — 编译器眼里没有 &mut T 指向内部 T。
RefCell 在 borrow_mut 内部用 UnsafeCell::get 拿到 *mut T，在 unsafe 里写入；计数器保证不会有两个 RefMut 或 Ref+RefMut 同时活跃 → 无数据竞争 UB。

4. API 与示例

方法 说明
.borrow() Ref<T>，多读共存
.borrow_mut() RefMut<T>，独占写
.try_borrow() / .try_borrow_mut() 冲突返回 Err，不 panic 
use std::cell::RefCell;

let s = RefCell::new(String::from("hello"));
let r1 = s.borrow();
let r2 = s.borrow();
println!("{} {}", r1, r2);
drop(r1);
drop(r2);
let mut w = s.borrow_mut();
w.push_str(" world");

5. 适用与代价

优点 缺点
任意 T，borrow_mut 原地改 计数器维护 + 冲突 panic
可分段修改（push、field） 仅单线程（非 Sync）

三、Cell<T>：无计数器，拷贝规避冲突

1. 内部结构（简化）

struct Cell<T> {
    value: UnsafeCell<T>,   // 无 borrow_flag，无计数器
}

从头到尾不存在借用计数器。

2. 设计逻辑：不产生引用，全程拷贝

仅 T: Copy（i32、bool、char 等）— 无借用计数器，永不 panic，与 RefCell 运行时计数完全不同。

操作 行为
.get() 拷贝一份 T 给你 — 不是 &T
.set(v) 用新副本整体覆盖盒内
.replace(v) 先拷贝出旧值，再原地覆盖 
读：拿走副本，盒内仍在
写：整体覆盖，没有「悬浮的 &T」指向旧数据
→ 不需要计数器 → 永不 panic

3. .get() / .set() / .replace() 内存怎么变？

Cell 本体（含 UnsafeCell<T>）常在栈上（let c = Cell::new(10)）；下面「Cell 内部」指 托管 T 的那块内存，不是另开一层堆。

.get() — 拷贝出新副本，内部原值不动

let c = Cell::new(10);
let a = c.get();
步骤 内存
1 Cell 内仍是 10，原地不动
2 .get() 按位拷贝一份 10 到栈上新变量 a
3 a 与 Cell 内是两份独立的 T；改 a 不影响 Cell

✅ .get() = 复制出新空间（新变量），Cell 内部不变。

let mut a = c.get();  // 要改副本须 mut
a = 99;               // 只改 a，c 里仍是 10

.set(新值) — 原地覆盖 Cell 内部，不保留旧值副本

let c = Cell::new(10);
c.set(20);
步骤 内存
1 参数 20 是传入的 Copy 副本
2 标准库在 unsafe 里对 UnsafeCell 内内存 原地写入 20
3 旧值 10 被覆盖销毁（Copy 类型无 drop 副作用）；不会另开一块存旧值

✅ .set() = 原地覆盖 Cell 内 T 的内存，无旧值留存。

.replace(新值) — 覆盖 + 返回旧值副本

let old = c.replace(20);
  1. 先 get 式拷贝出旧值 10 → 赋给 old
  2. 再 set 式原地覆盖内部为 20

4. 一眼看懂：完整流程

use std::cell::Cell;

fn main() {
    // Cell 内：10
    let cell = Cell::new(10);

    // get：拷贝 10 → x；cell 内仍是 10
    let mut x = cell.get();
    println!("x={}, cell={}", x, cell.get()); // 10, 10
    x = 99;                                    // 只改副本
    println!("x={}, cell={}", x, cell.get()); // 99, 10

    // set：cell 内原地 10 → 20
    cell.set(20);
    println!("cell={}", cell.get()); // 20
}

5. 为何这么设计就能不要计数器

  1. 不返回引用 — get 只给副本，外部没有指向 Cell 内部的 &T
  2. set 原地覆盖 — 覆盖时没有活跃引用指着旧位，无悬垂、无读写共存
  3. 无引用 → 无借用冲突 → 不需要 BorrowFlag

6. 底层同样 UnsafeCell + 库内 unsafe

set / replace 在标准库 unsafe 块里写 UnsafeCell 内 T；get 读拷贝亦经 unsafe 读内部；对外 API 仍 Safe。

7. 一句话

  • .get()：复制出新副本，Cell 内原值不变。
  • .set()：原地覆盖 Cell 内内存，旧值被覆盖掉。
  • .replace()：先拷贝旧值给你，再 set 新值。

8. 适用与代价

优点 缺点
零 panic（无借用冲突） 只能 Copy
无计数器，极轻 不能 borrow 分段改
读写皆拷贝，大数据可能贵 不能存 String/Vec

四、对照表（聚焦计数器与读写规则）

特性 Cell<T> RefCell<T>
内部计数器 ❌ 无 ✅ BorrowFlag 读写状态
如何保证互斥 无引用，只拷贝 运行时计数：读活跃则禁止写
读写铁律 天然无引用冲突 与 &/&mut 相同：多读 XOR 单写
违规后果 无此类违规 panic（非 UB）
底层 UnsafeCell + 库内 unsafe 同上 + 计数器
读写内存语义 get=拷贝副本；set=原地覆盖 borrow=共享读；borrow_mut=独占写
T 限制 Copy 任意

五、答疑四条（对应常见疑惑）

  1. 只有 RefCell 有借用计数器，Cell 没有。
  2. RefCell 计数器：有活跃 Ref 时禁止 borrow_mut；必须全部 Ref/RefMut 释放、状态归零才能写 — 没有放开读写互斥。
  3. 内部可变性根源：UnsafeCell 让库在 unsafe 里改数据；Cell/RefCell 用不同上层策略（拷贝 vs 计数器）保证 Safe API。
  4. 内部可变 ≠ 随便冲突读写：RefCell 用计数器拦；Cell 用拷贝消灭引用 — 都守内存安全底线。

六、选型（本节不涉及 Rc）

小 Copy 值，get/set 够用           →  Cell
String / Vec / 结构体，要借用修改  →  RefCell
能 let mut + &mut，无 &self 约束    →  优先外部可变，不用 cell

→ &self、多句柄等场景 07.4

七、误区

误区 纠正
Cell 也有借用计数 没有
RefCell 可以读写同时进行 不行，冲突 panic
RefCell 放松了借用规则 规则相同，检查时机从编译期→运行时
内部可变 = unsafe 给用户用 unsafe 在标准库内部；你调的是 Safe API
Cell 的 get 返回引用 返回 Copy 副本

八、速记

  1. Cell：无计数器，get/set 拷贝，永不 panic。
  2. RefCell：有计数器，规则同 &/&mut，冲突 panic。
  3. 底层都是 UnsafeCell；互斥铁律没变。

.4 · 内部可变性应用场景

所属：Borrowing and Lifetimes · 内部可变性 · ← 07 hub

← 07.3 Cell/RefCell · 下一节 07.5 对比与误区

本节先对比普通借用与 RefCell（不涉及 Rc；多所有者见文末「延伸阅读」）。Rc 只是多所有权工具，与读写规则无关。

零、核心矛盾（一句话）

普通引用（编译期检查）：只要有活跃共享引用，编译阶段直接不让写修改逻辑。
RefCell（运行时检查）：允许你拿着共享引用去「尝试」修改 — 代码能编译跑起来，冲突只在运行时报错。

底层安全规则（多读互斥单写）没变；变的是约束时机、写法、能实现的业务模式。这就是内部可变性的真正用途。

一、普通借用 vs RefCell：规则一致，门槛天差地别

1. 普通外部借用（let / & / &mut）— 编译期锁死

let mut data = 10;
let r1 = &data; // 共享只读引用
data = 20;      // ❌ 编译报错，代码跑不起来
要点 说明
规则 有活跃 &T → 禁止修改
检查时机 编译期全局扫描借用生命周期
痛点 哪怕你能保证运行时 r1 马上销毁、根本不会并发读写，编译器也不认 — 语法上生命周期重叠就报错

2. RefCell 内部可变性 — 编译放行，运行时校验

use std::cell::RefCell;

let data = RefCell::new(10);
let r1 = data.borrow(); // 活跃读借用，Ref 守卫

// 修改代码可以正常编译
let res = data.try_borrow_mut();
// 运行时：有活跃读 → Err；无冲突则 Ok
match res {
    Ok(mut w) => *w = 20,
    Err(_) => { /* 读仍活跃，安全拒绝 */ }
}
drop(r1); // 读计数归零
*data.borrow_mut() = 20; // ✅ 无冲突，正常运行
要点 说明
规则 一模一样：读活跃不能写、写活跃不能读
检查时机 运行时 BorrowFlag 计数
关键区别 修改逻辑能写进源码并编译通过；真冲突才 panic / Err 
普通借用：语法上可能重叠 → 编译器宁可错杀，直接禁止写
RefCell：  编译器不扫生命周期 → 运行时只看计数器，只杀真冲突

→ 计数器原理 07.3 §二

二、RefCell 不可替代的三大用途（普通借用做不到）

用途 1 · 签名固定 &self，却要改内部状态

trait、框架回调、标准库接口常把方法签名钉死在 fn func(&self) — 不能改成 &mut self。

普通借用 RefCell
&self 含义 整个结构体冻结，一个字段都改不了 外层 &self 共享；字段包 RefCell，运行时改
能否实现 ❌ ✅ 
use std::cell::RefCell;

struct Logger {
    print_count: RefCell<u32>,
}

impl Logger {
    // 签名必须是 &self，不能加 mut
    fn print(&self, msg: &str) {
        println!("{}", msg);
        // 普通借用：&self 下绝对改不了成员
        *self.print_count.borrow_mut() += 1;
    }
}

为何普通借用做不到：借用检查绑在方法签名上 — &self 静态锁死全部修改权。RefCell 把修改权下沉到运行时，绕开签名带来的静态约束。→ 三种接收者形式 06.1

小整数计数可用 Cell<u32> + set(get() + 1)，不必上 RefCell。

用途 2 · 运行时动态决定借用生命周期

普通借用的引用何时创建、何时销毁，必须在编译期被完整分析。若逻辑由运行时动态决定（缓存、事件回调、分支），编译器分析不清 — 哪怕你清楚逻辑安全，也会报生命周期冲突。

use std::cell::RefCell;

let cache = RefCell::new(50);

if some_runtime_condition() {
    let r = cache.borrow();
    println!("{}", *r);
} // r 销毁，读计数归零

// 你自己知道：上面读已结束，此处读写不会并发
*cache.borrow_mut() = 100; // ✅ 运行时计数器同意
普通借用 RefCell
动态分支 + 不确定活跃引用 编译器分析不清 → 报错 编译放行；运行时看计数器
引用已销毁后的写 编译器未必能证明 计数归零 → 允许写

用途 3 · 细粒度可变：整体不可变，只开放个别字段

普通外部可变是粗粒度：一个字段要改 → 整个结构体 let mut，所有字段都能动，容易误改核心数据。

RefCell 实现字段级内部可变：

use std::cell::RefCell;

struct User {
    id: u64,                      // 核心：永远不可改
    name: String,                 // 核心：永远不可改
    login_times: RefCell<u32>,    // 仅统计字段可内部修改
}

let user = User {
    id: 1,
    name: "张三".into(),
    login_times: RefCell::new(0),
};

// user.id = 2;              // ❌ 编译报错
*user.login_times.borrow_mut() += 1; // ✅ 只改统计字段

let mut user 会把 id、name 也放开 — 管控粗糙；RefCell 精准只开放辅助状态。

三、规则一样，凭啥不一样？

维度 普通借用 RefCell
安全底线 多读 XOR 单写 相同
约束时机 编译期；语法上可能重叠 → 禁止写 运行时；真冲突才报错
能力边界 受签名 + 静态生命周期分析限制 突破静态约束，实现上面三类架构
代价 零运行时开销 计数维护；冲突 panic

RefCell 的真正用处：不是打破读写互斥，而是打破编译期静态借用检查带来的语法限制。

选型原则：能用 let mut + 普通借用解决的，优先普通借用；只有静态规则阻碍你写合理、安全的代码时，才上 RefCell。

四、补充场景（仍不涉及 Rc）

多句柄共享同一 RefCell

let data = RefCell::new(5);
let r1 = &data;
let r2 = &data;

{
    let _a = r1.borrow_mut();
    // let _b = r2.borrow_mut(); // ❌ panic
}
let _c = r2.borrow(); // ✅ mut 借用已结束

编译期：多个 &RefCell 合法；运行时：borrow / borrow_mut 仍互斥。

RefCell + 非 Copy 原地修改

let cell = RefCell::new(vec![1, 2, 3]);
let mut w = cell.borrow_mut();
w.push(4);

Cell 做不到 push — 只能整体 set 新 Vec。

五、选型速查

需求 选型
默认、无 &self 约束 let mut + &mut
&self + 小 Copy 计数 Cell<u32>
&self + String / Vec RefCell<T>
动态分支、细粒度字段 RefCell 包目标字段
多线程 Arc<Mutex<T>> 等 — 见 07.2

六、延伸阅读 · Rc<RefCell<T>>

多所有者场景：Rc 只给 &T，无法静态拿 &mut；叠 RefCell 在运行时提供内部可变 — 单线程图/树经典组合。详见 Book 15.5。

use std::rc::Rc;
use std::cell::RefCell;

let data = Rc::new(RefCell::new(100));
let p1 = Rc::clone(&data);
*p1.borrow_mut() = 200;

四句话总结

  1. 底层规矩：有活跃读就不能写、有活跃写就不能读 — 两者一模一样。
  2. 普通引用编译期卡死修改入口；RefCell 允许写出修改代码，运行时再校验。
  3. 用处是突破静态借用限制：&self 改状态、动态生命周期、细粒度字段。
  4. 能 let mut 就 let mut；静态规则挡路时才上 RefCell。

二、常见误区

误区 纠正
「有 &T 就完全不能改」 直接改不行；内部可变是显式例外
「RefCell 绕过所有借用规则」 规则仍在，推迟到运行时
「RefCell::new 一定在堆上」 单独 let x = RefCell::new(10) 常在栈；Rc/Box 才常见堆
「let x 锁死盒内数字」 锁的是绑定；盒内用 borrow_mut
「Cell = 小 RefCell」 Cell 仅 Copy、get/set；无 borrow
「Mutex = 多线程 RefCell」 类似互斥，但还有 Send/Sync、中毒、阻塞

三、一句话总纲

  1. 外部可变性：编译器看 mut；有活跃 &T 时修改逻辑编译期写不出来。
  2. 内部可变性：外层 let 不动，盒内由容器运行时管（或 Cell 拷贝规避）。
  3. RefCell：没打破读写互斥，打破的是静态借用检查带来的语法限制；违规 panic，非 UB。
  4. 优先 let mut；&self、动态生命周期、细粒度字段 — 才上 RefCell。

Lifetimes（生命周期）

所属：Borrowing and Lifetimes · ← 章索引

前置 → 05 共享引用 · 06 可变引用 · 07 内部可变性

一、核心定义

生命周期是约束引用保持合法有效的代码区间的命名规则，不等同于变量词法作用域。

变量作用域 引用生命周期
是什么 从 let 到 } 的文本范围 编译器追踪的逻辑使用区间
结束时机 离开花括号（drop 所有者） 最后一次使用之后可提前结束（NLL）
要求 — 使用引用时底层数据必须仍存活 
{
    let x = 5;
    let r = &x;
    println!("{r}");  // 使用 r
}   // r 的生命周期在此前已结束；随后 x 被 drop

大白话：生命周期回答「这条借用能活到哪一行还在用」，不是「变量写在哪个 {} 里」。

二、NLL 非线性生命周期（Non-Lexical Lifetimes）

核心规则

只要一条引用在后续代码路径中不再被读取、写入，它的生命周期约束可以提前终止，不必等到词法作用域末尾。

带来的直观收益：同一块数据，可以在旧引用「逻辑死亡」后立刻创建可变引用，大幅放宽旧版 Rust 的借用限制。

关键区分（排坑要点）

读编译报错、分析生命周期时，务必分清两件事：

  1. 值的所有权销毁：变量离开作用域、执行 Drop、内存回收。
  2. 引用生命周期结束：仅代表该指针不再使用，原数据依然存活，可重新借用。

NLL 示例

let mut s = String::from("test");
let r = &s;
println!("{r}");      // r 在此处最后一次使用 → 生命周期提前结束
let r_mut = &mut s;   // ✅ NLL 允许，不与 r 冲突
r_mut.push('!');

若无 NLL（旧模型）：r 要到 } 才结束，其间不能 &mut s — 许多今天合法的代码会报错。

与借用规则的关系

NLL 不废除独占/共享规则，只让「借用结束点」更精确。

三、生命周期方差 Variance（本章难点）

方差控制泛型类型在生命周期/类型参数上的子类型替换规则，根本目的是杜绝悬垂引用、保证类型安全（soundness）。

→ 深入 + 源码：Nomicon 03 · 型变

1. 协变 Covariant

子类型关系同向传递：若 A 是 B 的子类型，则 F<A> 也是 F<B> 的子类型（在型变允许的方向上）。

  • 典型：&'a T 对生命周期 'a 协变
  • 直观：长生命周期引用可当作短生命周期使用（在共享引用语境下仍受借用规则约束）
let static_ref: &'static i32 = &0;
let local: i32 = 1;
{
    let short: &i32 = &local;
    // 'static 比 'short 长 → 协变允许把更长寿命当更短用（在合法借用内）
    let _use: &i32 = static_ref;
}

例：&'static i32 可赋给需要 &'a i32 的位置（'a 更短）。

2. 不变 Invariant

完全不允许子类型替换。

  • 典型：&mut T 对类型参数 T 不变
  • 安全逻辑：若 &mut T 对 T 协变，可把短寿命对象写入被误认为长寿命的可变槽 → 悬垂引用

最小反例（为何 &mut 对 T 必须不变）：

// 假设 &mut T 对 T 协变（实际不允许）—— 则可写：
let short = String::from("hi");
let long_slot: &mut &'static str = ...; // 误以为能存 'static
*long_slot = &short;                    // short 离开作用域后 → 悬垂

编译器通过不变禁止这类替换。详见 Nomicon 04-variance。

3. 逆变 Contravariant

子类型关系反向传递；常见于函数参数位置。

  • 示例：fn(T) 对 T 逆变 — 能接收「更宽」参数的函数，不能随意替换为「更窄」参数的函数。

日常写业务代码较少手写逆变，但理解 Fn trait、高阶生命周期时会碰到。

常见类型方差速查

类型构造 对 'a 对 T
&'a T 协变 协变（多数 T）
&'a mut T 协变 不变
Box<T> — 协变
Vec<T> — 协变
Cell<T> / RefCell<T> — 不变
Mutex<T> — 协变

概念 一句话核心概括
所有权 Ownership 谁最终负责销毁、释放内存

误区 纠正
「生命周期 = 作用域」 生命周期常早于 } 结束（NLL）
