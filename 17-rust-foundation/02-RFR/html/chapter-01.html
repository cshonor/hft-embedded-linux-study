1.1

Memory Terminology（内存术语）

所属：Talking About Memory · ← 章索引

进阶开发里若混淆 值 / 变量 / 指针，复杂借用错误会很难读懂。

值 (Value)

类型与该类型定义域内某个元素的组合。

  • 例如：u8 的 6 是一个值。
  • 意义独立于存储位置；可对应字节序列（如 0x06），但本质是逻辑对象。

变量 (Variable)

存放值的地方（容器 / 标签 / 具名内存区域）。

变量本身是一块（或一组）有名字的存储；值放在哪由类型 + 声明方式决定：

写法 变量（控制块）在哪 值 / payload 在哪
let x = 5 通常 栈 槽位 数字就在槽里
let b = Box::new(10) 栈 上的 Box 结构体 10 在堆；栈上存「指向堆的指针 + 元数据」
let s = String::from("hi") 栈 上的 String 结构体 字节在堆；栈上是 { ptr, len, cap }
static N: i32 = 0 Data / BSS（进程生命周期） 与变量同一静态区
&"hello" 里的 "hello" 无 let 变量名 字面量在 只读段（Text 旁 rodata）

→ 分区细节见 03 内存区域（Safe Rust → 03.1；OS/LLVM → 03.2）。

注意：说「变量在栈上」有时指这个 let 绑定的槽在栈上；若类型内含指针，它指向的数据可能在堆上（Box、String 都是这种「栈上控制块 + 堆上 payload」）。

指针 (Pointer)

其存储的值是内存地址的变量。

Rust 里的 &T / &mut T 在机器层面可理解为指针，但附加了语言规定的协议：

  • 别名规则（共享 vs 独占）
  • 对齐与有效性 (validity)
  • 生命周期约束

借用、Box、裸指针 — 是不是「都是指针」？

机器层面：很多类型内部都存地址或就是地址，可以宽泛地说「和指针有关」。

类型层面：Rust 不会把「指针」和「借用」画等号 — 它们是不同概念：

是什么 所有权 编译器约束
裸指针 *const T / *mut T 纯地址 无 几乎无；操作在 unsafe
借用 &T / &mut T 带协议的指针 不拥有数据；临时查看/修改 生命周期 + 别名规则（共享 / 独占）
Box<T> 拥有堆内存的智能指针 拥有堆上 T；drop 时释放 独占所有权，可移动
String / Vec 比 Box 更复杂的智能指针 拥有堆上 buffer 同上 + len/cap 等语义

串起来记：

裸指针     = 只有地址，自己负责合法
借用       = 地址 + 「我不能抢所有权、不能乱别名」
Box        = 地址 + 「这块堆归我，到期我释放」
String     = 地址 + len/cap + 「这块堆归我，到期我释放」

所以：借用是指针的一种安全用法，但不是「指针 ≡ 借用」；Box 也是指针类抽象，但是拥有型，不是借用。

赋值在说什么

要点：= 把右侧表达式的值写入左侧命名的位置 (place)。

区分「槽里换了什么比特」与「引用仍指向同一槽位」——后文在 02 变量深入 用双模型展开。

你平时看到的 vs 底层真正是什么

Rust 里指针相关可以分成三层理解（由安全到裸）：

层级 例子 是什么
安全包装 Box<T>、String、Vec<T>、&T / &mut T 编译器 enforced 的所有权 / 生命周期 / 别名规则
标准库内部 String 里的 ptr: *mut u8 + len + cap 用 unsafe + 裸指针 + Drop 自己实现「类似 Box + 扩容」
裸指针 *const T、*mut T 和 C 的 const T* / T* 同级的地址；几乎无安全协议

结论：String 不是 Box<str> 类型，也不是借用；它是栈上的结构体，三个字段里只有 ptr 是指针，len/cap 是普通 usize。

// 概念上等价于标准库内部（简化，非逐字源码）
struct String {
    ptr: *mut u8, // 裸指针 → 堆上 UTF-8 字节
    len: usize,
    cap: usize,
}
  • String::from("hello")：堆上分配字节 → 把地址、len=5、cap=5 写进栈上的 String。
  • let s = String::from("hello") 创建的是 String 结构体实例（类型就是 String），不是「某种神秘指针类型」；只是这个结构体设计得像智能指针。
  • 离开作用域：Drop 按 ptr/cap 释放堆 — 和 Box drop 释放内存同一类逻辑，只是 String 多管了 len/cap 与 UTF-8 语义。

Vec<T> 同样是 { ptr, len, cap } + 自定义 Drop，不是 Box<[T]>。

裸指针 *const T / *mut T

Rust 近似 C/C++ 含义
*const T const T* 只读裸指针
*mut T T* 可写裸指针
  • 所有数据类型的裸指针都是这两类泛型实例：*mut i32、*const u8、*mut String ……
  • 运行时它们通常就是一个 地址（64 位下 often 8 字节），T 是编译期注解；和 void* 再强转类似，但 Rust 要求显式类型。
  • 创建、解引用裸指针要在 unsafe 里（或位于 unsafe fn 中），因为编译器不帮你保证：非 null、对齐、生命周期、无数据竞争。
let mut x = 42_i32;
let p: *mut i32 = &mut x as *mut i32; // 借用 → 裸指针（coerce 常在此步）
unsafe {
    *p += 1; // 像 C 一样解引用
}

和 &mut T 的区别：借用带生命周期 + 别名规则；裸指针没有，全靠你自己保证合法。

只有这两种吗？

指向数据的标准裸指针类型就是 *const T 和 *mut T 两个家族（泛型参数换 T 即可）。

其它相关、但不算「多一种数据裸指针」的：

类型 说明
fn(...) -> R / fn(...) -> R 函数指针 指向代码（Text 段），不是指向堆/栈数据的 *mut T
NonNull<T> 封装「非 null 的 *mut T」，仍基于裸指针，便于 niche 优化
usize 存地址 纯整数，不是指针类型；和裸指针可 as 互转，更易踩 UB

日常业务用 Box / String / Vec / 借用；HFT / 驱动 / 共享内存 / FFI 才在 unsafe 里用 *mut T，并自己承担 C 级内存责任。

Variables in Depth（变量深入）

所属：Talking About Memory · ← 章索引

同一套「变量」概念，在不同问题下用两个互补模型思考 — Rust 给开发者的「双重视角」。

新手从哪一层入门？

从高层（数据流）开始。 Book、所有权、& / &mut、生命周期、函数传参、迭代器 — 全是这一层：

  • 你写 let r = &x，不必先想「r 指向栈上哪条地址」
  • 只需理解：借来了读/写权限；编译器检查生命周期、有没有和 &mut 冲突

高层模型故意屏蔽地址、槽大小、堆栈细节，让你先建立「值怎么流动、谁能在何时访问」的安全思维。

等你写 unsafe、看 LLVM IR、做布局/低延迟优化时，再切底层（内存槽）：变量 = 固定地址的一块存储，改值常是改槽内比特、地址不变。

高层 · 数据流 底层 · 内存槽
视角 逻辑 / 编译器安全 硬件 / 物理存储
变量是什么 数据流里的节点 栈或静态区里固定大小的块
引用是什么 带规则的读/写权限 往往涉及地址（机器上像指针）
典型场景 日常业务、学语法、HFT 业务逻辑 unsafe、裸指针、FFI、06_Compilers-and-LLVM-Learning/04_Learn-LLVM-17、极致优化
你要关心的 谁拥有、谁借用、能借多久 槽在哪、多大、地址变不变、比特怎么变

两层不矛盾：同一行 let mut x = 5; x = 10; 在高层是「绑定可变、重新赋值」；在底层是「同一槽、改里面存的数」。HFT 常见路径：高层保安全 → 热点路径再切底层抠性能。

高层模型：数据流 (Data Flow)

何时用：生命周期、借用、跨函数传引用。

  • 变量是数据流的节点；借用检查器追踪值如何经引用在节点间流动。
  • 冲突规则：同一数据上若同时存在违反协议的独占流（&mut）与共享流（&），编译拒绝。

底层模型：内存槽 (Slots)

何时用：unsafe、原始指针、布局、06_Compilers-and-LLVM-Learning/04_Learn-LLVM-17 读 IR。

内存槽到底是什么？（纯 Rust，一句话）

内存槽 = 编译器为某个 let 绑定划出的 固定地址 + 固定大小 的一块存储；从声明到离开作用域，槽的位置和大小不变，变的只是槽里存的比特。

let mut x: u32 = 5;
// 栈上开 4 字节槽，假设地址 0x1000
println!("{:p}", &x); // 0x1000
x = 10;               // 槽还在 0x1000，只是把里面的 5 改成 10
println!("{:p}", &x); // 还是 0x1000
  • 槽 = 那块 4 字节的物理存储（place / location）
  • 变量名 x = 编译器符号表里「名字 → 这个槽」的标签（不是运行时指针）
  • mut = 允许改写这个槽里的内容（不是移动槽、不是改槽的大小）

String 同理：let mut s = String::from("hi") 在栈上占一个固定大小的槽（64 位下通常 24 字节：ptr + len + cap）。s.push('!') 时 s 这个槽的地址不变，变的是槽里的 len（以及可能触发的堆扩容）。

  • 变量对应栈（或静态区等）上的槽位，大小由类型在编译期确定。
    例：let x: usize → 栈上固定大小槽位。
  • 重新赋值通常不改变「&x 指向该槽位」的地址语义（槽位仍在），变化的是槽内比特。
  • 与「引用指向的对象整体被移动/替换」要在具体语境下区分——见 04 所有权。

两模型如何配合

问题 优先模型
「为什么这里不能同时有 & 和 &mut？」 数据流
「这个 *const T 指向的地址还合法吗？」 槽位 + 有效性
「优化器能否合并两次 *r 读取？」 数据流上的别名协议 → 05 共享引用

mut 与 &mut：都是在「开修改槽位的权限」

先回答最常见的问题：改槽里的内容，要不要 mut？

改法 写法 需要什么
直接改变量 let mut x = 5; 然后 x = 10; 声明时 let mut x
通过借用改 let mut x = 5; 然后 *(&mut x) = 10; 声明时 let mut x + 借用时 &mut
遮蔽（换一个新槽） let x = 5; 然后 let x = 10; 不要 mut（这不是改旧槽，是开新槽换绑名字）

所以：只要你是「改同一个槽里的内容」，无论直接写变量名还是走 &mut，原变量都必须先 let mut 解锁。
&mut 不是 mut 的替代品，而是「在仍需要 let mut 的前提下，多一条临时修改路径」。

作用
let mut x 允许直接改这个槽（x = 10），也允许借出 &mut x
let x（不可变） 槽内比特焊死：不能 x = 10，也不能 &mut x
&mut T（可变借用） 允许通过这条借用路径改它指向的那个槽；前提是原变量已是 mut 
let mut s = String::from("a");
s.push('b'); // 需要 s 是 mut：push 要改栈上 {ptr,len,cap}，可能还要改堆

常见误区：「不可变变量只能借 &mut 来改」——不对。&mut 的前提是 let mut 已解锁；若只有 let x，连 &mut x 都拿不到。

想「变」：三种不同机制

机制 写法 改的是啥 要 mut 吗
变量遮蔽 (shadowing) let x = 5; 再 let x = 10; 新开一个槽，符号表把名字 x 改绑到新槽 不要
重新赋值 let mut x = 5; 再 x = 10; 同一个槽里的比特 要
可变借用改槽 let mut y = 5; 再 *(&mut y) = 10 同一个槽里的比特 要（原变量） 
// 遮蔽：新槽位，地址会变
let x = 5;
let p1 = &x as *const i32;
let x = 10;              // 新 let → 新槽；旧槽还在栈帧里，只是名字 x 不再指向它
let p2 = &x as *const i32;
// p1 != p2（通常）

// 可变引用：同一槽位，地址不变
let mut y = 5;
let p3 = &y as *const i32;
let r = &mut y;
*r = 10;
let p4 = &y as *const i32;
// p3 == p4

遮蔽后若还持有指向旧槽的引用，借用检查器会拒绝（生命周期/遮蔽规则）：

let x = 5;
let r = &x;
let x = 10;   // 遮蔽
// println!("{r}"); // 编译错误：r 仍指向已被遮蔽的旧绑定

→ 可变借用细节见 06 可变引用；内部可变性（无 mut 也能改）见 07。

变量名是什么？像指针吗？

不像运行时指针。 变量名是编译器符号表里的条目：名字 → 当前作用域内生效的那个槽位。

  • let x = 5：在栈上开槽 1，符号表 x → 槽 1
  • let x = 10（遮蔽）：在栈上开槽 2，符号表 x → 槽 2（不是改槽 1 里的数）

可以想成字典：key = 变量名，value = 当前绑定的槽；遮蔽是换绑 value，不是改旧槽里的比特。

被遮蔽的旧槽何时释放？

不会马上释放。 栈按栈帧 / 作用域整块回收：遮蔽只让名字不再指向旧槽，旧槽仍占着栈空间，直到整个 { ... } 或函数结束才和帧内其它槽一起弹栈。

这对性能是利好：遮蔽几乎零分配成本；也配合借用检查，避免「名字已换绑、旧引用仍指向旧槽」的悬垂访问（能编译过的代码里这类情况会被拦住）。

→ 内存分区见 03 内存区域（03.1 Rust 三分类 · 03.2 OS 五分区）；术语见 01 内存术语。

.1 Rust 内存模型（Safe Rust 三分类）

所属：Talking About Memory · ← 03 索引 · 03.2 OS / LLVM 布局 →

视角：Safe Rust + 所有权 / 借用 — 学 Book、写业务、理解 Box / String / 作用域时用。

与 02 变量深入 · 高层数据流模型 同一层：关心值在哪一类存储、谁拥有、何时 drop，不必先画 OS 五分区图。

为什么 Rust 只分三类？

RFR / Book 把进程内存收成 栈 / 堆 / 静态，是因为 safe Rust 的规则按这三类管：

Rust 分类 典型内容 Safe Rust 怎么管
栈 (stack) let 局部变量、函数参数、调用帧 进函数分配、出函数销毁；与作用域对齐
堆 (heap) Box / Vec / String 的 payload 所有权 + Drop；无 GC
静态 (static) static 全局；'static 引用可指向的数据 进程全程；static mut 要 unsafe

OS 还有 Text / Data / BSS / mmap 等 — 那是 03.2 的事。日常写 safe 代码，三分类足够。

栈：自动、快、有上限

fn foo() {
    let x = 42;           // x 在 foo 的栈帧里
    let arr = [0u8; 1024]; // 数组也在栈（若太大可能改放栈外，见下方）
} // foo 返回 → 整帧弹出，x、arr 自动销毁

速度 极快（改栈指针）
大小 每线程固定上限 → 递归过深 stack overflow
和借用的关系 借用检查里的「作用域」多与栈帧生命周期对齐

大对象：非常大的栈数组可能触发 stack overflow；超大缓冲常放堆（Vec）或静态。

堆：动态、句柄在栈、实体在堆

fn main() {
    let b = Box::new(100);              // b（句柄）在栈；100 在堆
    let s = String::from("hello");      // s（{ptr,len,cap}）在栈；字节在堆
    let v = vec![1, 2, 3];              // 同理
} // drop 顺序：先释放堆 payload，再弹栈
栈上的「句柄」 堆上的 payload
Box<T> Box 结构体（指针） T
String { ptr, len, cap } UTF-8 字节
Vec<T> { ptr, len, cap } T 元素数组

所有权在做什么：栈上变量（如 b: Box<i32>）拥有堆块；离开作用域 → Drop 释放堆，避免泄漏。→ 04 所有权

3.1

Shared References（共享引用 `&T`）

所属：Borrowing and Lifetimes · ← 章索引

前置 → 04 所有权 · Move/Copy/Drop · 术语 → 01 内存术语

核心语义：共享引用是什么

共享引用 &T = 只读借用 — 在引用存活期内：

  • 可以同时存在多个 &T 指向同一数据（多读）
  • 不能同时存在 &mut T 指向同一数据
  • 不能通过所有者或其它合法路径直接修改该内存（除非走 07 内部可变性）

这就是 单写多读（Single Writer, Multiple Readers） 规则的一部分 — Rust 内存安全与优化的基石。

let x = 42;
let r1 = &x;
let r2 = &x;     // ✅ 多个 &T 共存
println!("{r1} {r2}");
// let m = &mut x; // ❌ 已有共享借用时不能再 &mut

大白话：&T 是「我借来看，大家都可以看，但谁也不能在这段时间里改（常规路径）」。

别名组合规则（一眼表）

对同一内存位置在同一时刻：

组合 是否允许
多个 &T ✅
一个 &mut T ✅
&T + &mut T ❌
多个 &mut T ❌

→ 可变借用详见 06 可变引用

引用不重叠：编译期借用检查器 enforcement；违反则编译失败。

与 LLVM / 优化器

共享引用不只是语法 — 也是给优化器的契约：

借用 向优化器承诺 LLVM 可做什么
&T 存活期内不会被突变（no-mutation / readonly 语义） 重复读可合并、缓存到寄存器；死代码消除、循环不变量提升等
&mut T 独占、无别名冲突（noalias） 更激进的指针别名分析与 store/load 优化 
fn sum_twice(r: &i32) -> i32 {
    *r + *r   // 优化器可能只从内存读一次 *r
}

为何重要（HFT / 性能）：安全 Rust 里写 &T，编译器能假定「这段期间没人改」— 不必每次读都当成可能 alias 的 wild pointer。读 IR 时见 06_Compilers-and-LLVM-Learning/04_Learn-LLVM-17 ch04。

与内部可变性的关系：RefCell / Mutex 等刻意 opt-out 普通 &T 的 no-mutation 假设 — 见 07，否则 LLVM 会按「只读」做错误优化。

&T vs C 的 const T*

&T（Rust） const T*（C）
只读访问 ✅ ✅
生命周期 ✅ 编译期检查 ❌ 无
别名规则 ✅ 与 &mut 互斥 ❌ 可随意 cast 成 T*
悬垂 能编译通过则通常安全 全靠程序员

Rust 的 &T 不是「带类型的 const 裸指针」— 还编码能借多久、能和谁共存。

内部可变性：看起来是例外

外表可以是 &RefCell<T>（共享引用），内部仍可在运行时借 mut — 规则由 RefCell 自己检查，违反则 panic。

use std::cell::RefCell;

let data = RefCell::new(5);
let r = &data;              // 共享引用 RefCell 容器本身

*r.borrow_mut() += 1;       // 运行时独占 borrow，改内部
println!("{}", r.borrow()); // 6

// 多个 & 指向同一 RefCell 可以，但不能同时 borrow_mut
let data = RefCell::new(5);
let r1 = &data;
let r2 = &data;

{
    let _a = r1.borrow_mut(); // 持有 mut borrow
    // let _b = r2.borrow_mut(); // ❌ 运行时 panic：已有 mut borrow
}
  • 编译期：多个 &RefCell<T> 合法
  • 运行时：borrow / borrow_mut 仍互斥 — 与 07 内部可变性 一致

多线程 → Mutex<T> / RwLock<T> 等同理，见 第 10 章 并发。

常见误区

误区 纠正
「有 &T 就完全不能改」 直接改不行；内部可变性（RefCell / Mutex / Cell）是显式例外
「有 &mut 就完全不能改」 &mut 就是改的路径；不能的是同时再有冲突的 & / &mut
「&T = C 的 const T*」 还有生命周期 + 别名协议
「多个读者 = 可以随便改内部」 只有 UnsafeCell 系封装在规则内改；普通 &T 到 i32 不能改
「优化与借用无关」 &T / &mut T 的假设直接喂给 LLVM

和所有权的关系

所有者 T 共享引用 &T
拥有数据 ✅ ❌（只借看）
触发 Drop ✅ ❌（只结束借用）
赋值 / move 转移所有权 Copy（复制指针 + 生命周期）

.1 · 方法接收者：`self` / `&self` / `&mut self`

所属：Borrowing and Lifetimes · ← 章索引

← 06 可变引用 · 下一节 07 内部可变性

前置 → 04 所有权 · 05 &T · 06 &mut T

impl 里的关联方法，对实例有三种接收形式 — 对应所有权转移 / 不可变借用 / 可变借用三种权限：

写法 本质
self 拿走所有权（消耗型）
&self 不可变共享借用（只读，最常用）
&mut self 可变独占借用（可读可写）

一、self — 拿走所有权（消耗型方法）

参数直接写 self，没有 &、没有 mut。

规则

要点 说明
调用时 实例所有权移入方法
方法结束 self 随栈帧销毁；外部原变量失效
方法内 可随意修改、拆解、销毁结构体

典型场景

消费资源、收尾销毁、转换成别的类型 — 调用后实例不再可用。

struct User {
    id: u32,
}

impl User {
    fn into_id(self) -> u32 {
        self.id
    }
}

fn main() {
    let u = User { id: 100 };
    let num = u.into_id();
    // println!("{}", u.id); // ❌ u 所有权已移走
}

命名惯例：消耗型转换常带 into_ 前缀（如 into_inner、into_boxed_slice）。

→ 所有权复习 04.2 Move/Copy

二、&self — 不可变借用（只读方法）

参数：&self — 共享只读引用。

规则

要点 说明
所有权 不转移；方法结束外部变量仍可用
修改 方法内只能读字段，不能直接改
并发借用 同一实例可同时存在多份 &self

典型场景

查询、读取属性，不改动数据 — 默认首选。

impl User {
    fn get_id(&self) -> u32 {
        self.id
    }
}

fn main() {
    let u = User { id: 100 };
    let a = u.get_id();
    let b = u.get_id();
    println!("{}", u.id); // ✅ 所有权仍在
}

→ 共享借用 05

三、&mut self — 可变借用（修改方法）

参数：&mut self — 独占可变引用。

规则

要点 说明
所有权 不转移；只临时拿到修改权
修改 方法内可读可写所有字段
独占 同一时刻至多一份 &mut self；不能与任何 &self / &mut self 共存

典型场景

更新结构体内部字段。

struct User {
    id: u32,
    name: String,
}

impl User {
    fn rename(&mut self, new_name: &str) {
        self.name = new_name.to_string();
    }
}

fn main() {
    let mut u = User { id: 1, name: "tom".into() };
    u.rename("jerry");
    println!("{}", u.name); // jerry
}

注意：调用方绑定须 let mut u — 外部可变绑定才能借出 &mut self。

四、三者对比

写法 所有权 能否改字段 同一时刻几份 典型用途
self 转移；外部变量失效 能改、能销毁 调用即消耗 into_*、消费、析构收尾
&self 保留，仅借用 只读 多份共享 查询、读取
&mut self 保留，独占可变借用 可读可写 至多 1 份 更新内部状态 
self      → 04 所有权：move 进方法
&self     → 05 共享借用：多读
&mut self → 06 可变借用：单写

五、与内部可变性：&self 签名下仍能改字段

方法签名是 &self（整体只读借用）时，若某字段包了 Cell / RefCell，仍可在方法内修改该字段 — 内部可变性的经典入口。

use std::cell::RefCell;

struct User {
    id: u32,
    visit_cnt: RefCell<u32>,
}

impl User {
    // 签名仍是 &self
    fn add_visit(&self) {
        *self.visit_cnt.borrow_mut() += 1;
    }
}
层面 看到什么
方法签名 &self — 结构体绑定层只读
字段层 RefCell 在运行时借出 RefMut，改盒内计数

外部看方法是只读调用；内部改的是容器里的数据 — 详见 07.4 应用场景。

六、选型口诀

  1. 只读不改 → 优先 &self
  2. 要改字段、签名能改 → &mut self（调用方 let mut）
  3. 调用完实例没用了 → self（消耗型）
  4. 签名被钉死 &self 却要改状态 → 字段包 Cell / RefCell → 07

  • [ ] &self 方法里 RefCell 字段能改、普通 u32 字段不能改 — 各是什么规则在管？

3.4

Lifetimes（生命周期）

所属：Borrowing and Lifetimes · ← 章索引

前置 → 05 共享引用 · 06 可变引用 · 07 内部可变性

一、核心定义

生命周期是约束引用保持合法有效的代码区间的命名规则，不等同于变量词法作用域。

变量作用域 引用生命周期
是什么 从 let 到 } 的文本范围 编译器追踪的逻辑使用区间
结束时机 离开花括号（drop 所有者） 最后一次使用之后可提前结束（NLL）
要求 — 使用引用时底层数据必须仍存活 
{
    let x = 5;
    let r = &x;
    println!("{r}");  // 使用 r
}   // r 的生命周期在此前已结束；随后 x 被 drop

大白话：生命周期回答「这条借用能活到哪一行还在用」，不是「变量写在哪个 {} 里」。

二、NLL 非线性生命周期（Non-Lexical Lifetimes）

核心规则

只要一条引用在后续代码路径中不再被读取、写入，它的生命周期约束可以提前终止，不必等到词法作用域末尾。

带来的直观收益：同一块数据，可以在旧引用「逻辑死亡」后立刻创建可变引用，大幅放宽旧版 Rust 的借用限制。

关键区分（排坑要点）

读编译报错、分析生命周期时，务必分清两件事：

  1. 值的所有权销毁：变量离开作用域、执行 Drop、内存回收。
  2. 引用生命周期结束：仅代表该指针不再使用，原数据依然存活，可重新借用。

NLL 示例

let mut s = String::from("test");
let r = &s;
println!("{r}");      // r 在此处最后一次使用 → 生命周期提前结束
let r_mut = &mut s;   // ✅ NLL 允许，不与 r 冲突
r_mut.push('!');

若无 NLL（旧模型）：r 要到 } 才结束，其间不能 &mut s — 许多今天合法的代码会报错。

与借用规则的关系

NLL 不废除独占/共享规则，只让「借用结束点」更精确。
→ 06 可变引用 · 05 共享引用

三、生命周期方差 Variance（本章难点）

方差控制泛型类型在生命周期/类型参数上的子类型替换规则，根本目的是杜绝悬垂引用、保证类型安全（soundness）。

→ 深入 + 源码：Nomicon 03 · 型变

1. 协变 Covariant

子类型关系同向传递：若 A 是 B 的子类型，则 F<A> 也是 F<B> 的子类型（在型变允许的方向上）。

  • 典型：&'a T 对生命周期 'a 协变
  • 直观：长生命周期引用可当作短生命周期使用（在共享引用语境下仍受借用规则约束）
let static_ref: &'static i32 = &0;
let local: i32 = 1;
{
    let short: &i32 = &local;
    // 'static 比 'short 长 → 协变允许把更长寿命当更短用（在合法借用内）
    let _use: &i32 = static_ref;
}

例：&'static i32 可赋给需要 &'a i32 的位置（'a 更短）。

2. 不变 Invariant

完全不允许子类型替换。

  • 典型：&mut T 对类型参数 T 不变
  • 安全逻辑：若 &mut T 对 T 协变，可把短寿命对象写入被误认为长寿命的可变槽 → 悬垂引用

最小反例（为何 &mut 对 T 必须不变）：

// 假设 &mut T 对 T 协变（实际不允许）—— 则可写：
let short = String::from("hi");
let long_slot: &mut &'static str = ...; // 误以为能存 'static
*long_slot = &short;                    // short 离开作用域后 → 悬垂

编译器通过不变禁止这类替换。详见 Nomicon 04-variance。

3. 逆变 Contravariant

子类型关系反向传递；常见于函数参数位置。

  • 示例：fn(T) 对 T 逆变 — 能接收「更宽」参数的函数，不能随意替换为「更窄」参数的函数。

日常写业务代码较少手写逆变，但理解 Fn trait、高阶生命周期时会碰到。

常见类型方差速查

四、四大核心概念记忆锚点

概念 一句话核心概括
所有权 Ownership 谁最终负责销毁、释放内存

五、常见误区

误区 纠正
