1.1

Synchronous Interfaces（同步接口）

所属：What's the Deal with Asynchrony? · ← 章索引

CPU 很快，程序大量时间在 等待（I/O、网络、磁盘、事件）。

同步模型：调用线程阻塞直到 I/O 完成。

优点 代价
心智简单、栈上局部变量自然 每连接一线程 → 阻塞成本放大

适合低并发、原型、CPU bound 短任务。

1.2

Multithreading（多线程）

所属：What's the Deal with Asynchrony? · ← 章索引

多线程模型：某线程阻塞时，OS 调度其他线程运行。

优点 代价
仍用阻塞式 API 线程栈、切换、同步（锁、原子、数据竞争）

→ 第 10 章 · Book 16.1 线程

1.3

Asynchronous Interfaces（异步接口）

所属：What's the Deal with Asynchrony? · ← 章索引

异步模型：等待时让出线程给其他任务；I/O 就绪后再继续。

优点 代价
少量线程高并发 状态机、Pin、取消、背压

Rust 核心仍是 Future::poll：未就绪 → Poll::Pending，就绪 → Ready。

→ 04 标准化轮询

1.4

Standardized Polling（标准化轮询）

所属：What's the Deal with Asynchrony? · ← 章索引

Future::poll(&mut self, cx: &mut Context<'_>) -> Poll<Output> 是生态统一接口：

  • Context 携带 Waker
  • 执行器反复 poll 直到 Ready 或任务挂起

不同运行时（Tokio、async-std 等）共享此契约，差异在调度与 I/O 驱动实现。

→ 08 Poll 契约 · 07 唤醒

2.1

async/await

所属：Ergonomic Futures · ← 章索引

手写 Future = 手写 enum 状态机 + 跨 .await 保存局部 — 易错。

语法糖

  • async fn / .await：编译期降阶为实现 Future 的匿名类型。
  • 让出点：子 Future 未就绪 → 返回 Pending；局部变量打包进状态结构体字段。

性能注意

嵌套 .await 使状态结构体变大（内嵌子 Future）→ 栈压力 / memcpy。

缓解：Box::pin 把大 Future 放堆并固定地址（与 06 Pin/Unpin 配合）。

2.2

Pin and Unpin

所属：Ergonomic Futures · ← 章索引

自引用

async 体内可能出现「某字段引用另一字段」；.await 后布局须跨 poll 有效。

移动 = 灾难

若 Future 整体 move，内嵌指针仍指向旧地址 → UB。

Pin<P<Pointer<T>>>

对 !Unpin 的 T：约束「poll 期间不非法移动 T」（精确规则见官方文档）。

Unpin

类型不依赖地址不变 → 自动/可标为 Unpin；Pin 约束大多无负担。

常见报错

Future 不是 Unpin → 需 Box::pin 或运行时提供的 pinned spawn API。

→ 第 9 章 · Unpin 与 unsafe

3.1

Waking Up（唤醒）

所属：Going to Sleep · ← 章索引

Pending 后若忙轮询，CPU 烧干。

Reactor + Waker

  • I/O 层（epoll / kqueue / IOCP）监听就绪事件。
  • 就绪时调用 Waker::wake()，通知执行器「某任务可再 poll」。

Context

poll(cx, …) 中的 cx 提供注册 waker 的路径；子 Future 把 waker 传给底层 I/O。

→ 09 唤醒的误称

3.2

Fulfilling the Poll Contract（Poll 契约）

所属：Going to Sleep · ← 章索引

契约

返回 Pending 时，必须确保将来某处会 wake（除非任务被永久取消且协议允许）—— 否则任务饿死。

不要在 executor 上阻塞

在 worker 上 thread::sleep、长 CPU 死算、同步阻塞 I/O → 占用 worker，同池任务饥饿。

经验法则：poll 路径避免长时间独占线程（阈值依运行时与 SLA 而定）。

异步里持 std::sync::Mutex 跨 .await 同理 → 第 10 章 · 异步与锁

3.3

Waking Is a Misnomer（唤醒的误称）

所属：Going to Sleep · ← 章索引

wake() ≠ 立即运行该任务。

典型语义：

  1. 把任务标为 runnable
  2. 推进执行器就绪队列
  3. 调度器在合适时机再次 poll

因此「唤醒」更像是登记可运行，而非 OS 线程意义上的 instant resume。

理解这一点有助于排查「已 wake 但延迟很大」类问题。

3.4

Tasks and Subexecutors（任务与子执行器）

所属：Going to Sleep · ← 章索引

运行时把 Future 包装为 Task，由 executor / worker 池 调度。

层级

  • 顶层任务 — 可被 spawn 独立调度
  • 子 Future — 嵌在父 poll 内，由父驱动

子执行器 (subexecutor)

部分运行时允许在任务内嵌局部调度逻辑；细节因 Tokio / async-std 等而异 — 读文档时对照「task / join handle / LocalSet」等概念。

→ 与 11 spawn 衔接

4

. Tying It All Together with spawn

← 章索引

若在单循环里顺序 .await 每个连接，并发度为 1。

spawn

把每个连接的 Future 变成独立顶层任务，由运行时线程池调度 → accept 与业务处理重叠。

Send 约束

跨线程 spawn 通常要求 Future: Send（捕获的数据须 Send）。

Pin + Send 组合是 Tokio 报错高频区 → 06 Pin/Unpin · 第 10 章 Send/Sync
