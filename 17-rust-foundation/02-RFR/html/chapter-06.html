1.1

The Test Harness（测试脚手架）

所属：Rust Testing Mechanisms · ← 章索引

cargo test 驱动 rustc 以 --test 等方式生成测试二进制：内置 main 发现并运行 #[test]。

自定义脚手架

[[test]]
name = "integration"
harness = false
path = "tests/custom.rs"
  • harness = false — 自行实现 main，控制顺序、集成测试、模糊测试入口等。

Book → 11.1 如何编写测试

1.2

`#[cfg(test)]`

所属：Rust Testing Mechanisms · ← 章索引

不仅「不把测试编进 release」，更是隔离与可观测性。

常见用法

用途 说明
Mock / 替身 测试下替换网络、DB（可配合 mockall）
测试专用 API #[cfg(test)] pub fn inspect_invariant() 不污染公开 API
测试记账 仅测试配置下增加计数字段

与模块组织

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn it_works() { ... }
}

Doctests（文档测试）

所属：Rust Testing Mechanisms · ← 章索引

/// 中 fenced 代码块会编译并运行。

隐藏行

行首 # 的代码参与测试，但不出现在渲染文档 — 适合隐藏样板。

compile_fail

断言代码必须不能编译 — 验证 API 边界（如某类型非 Send）。

no_run / ignore

  • no_run — 只编译不运行（需外部资源时）。
  • ignore — 跳过（慎用，易腐化）。

2.2

Test Generation（测试生成）

所属：Additional Testing Tools · ← 章索引

模糊测试 (Fuzzing)

对解析器等喂随机 / 变异输入直至 panic。

  • cargo-fuzz + libFuzzer 等后端。
  • 适合输入空间巨大、手写用例难覆盖的 API。

基于属性的测试 (PBT)

  • proptest 等生成大量输入。
  • 对照朴素参考实现或不变量 (invariant)，发现边界 bug。

与单元测试分工

  • 单元测试 — 已知关键路径。
  • Fuzz / PBT — 探索未知输入空间。

Test Augmentation（测试增强）

所属：Additional Testing Tools · ← 章索引

Miri

MIR 解释器：cargo miri test 较慢，但可检测：

  • 未初始化读、悬垂解引用
  • 违反 stacked borrows / 别名规则等 UB

把 unsafe 问题从「生产偶现」拉到「测试可复现」。

→ ER Item 16 demo

Loom

并发 bug 依赖线程交错。Loom 接管 Mutex、原子等语义，系统化探索调度顺序，暴露极端交错下的竞争与死锁。
