section-1-本章定位

ULK Ch 15 The Page Cache · 用 RAM 缓存磁盘数据

一、本章讲什么

页高速缓存 (Page Cache) 是 Linux 主要磁盘缓存 — 几乎所有文件读写都经它：

主题 要点
读 先查缓存；命中则 零磁盘
写 先改缓存页 → 标 脏 → 延迟 写回
组织 address_space + 基数树 索引页
回写 pdflush 内核线程池
持久化 sync / fsync / fdatasync

section-2-页缓存与address_space

一、页高速缓存做什么

操作 行为
读文件 数据读入 页缓存；后续相同偏移 内存命中
写文件 修改 缓存页 — 不必立刻落盘
共享 多进程映射同一文件 → 共享同一缓存页

→ 缺页读入文件页：Ch 9 section-5

二、页与「拥有者」

缓存中每一 页 的数据属于某个 拥有者 — 通常是文件的 inode。

内核用 address_space 对象连接 页 ↔ 拥有者：

内容 说明
拥有者指针 指向 inode 等
a_ops 操作表 readpage、writepage、write_begin/write_end … — 该拥有者 的页 I/O 方法
页索引结构 基数树（→ section-3）

→ inode 对象：Ch 12 section-3

三、与 Ch 14 块层的关系

层 职责
页缓存 文件 偏移 ↔ 内存页
块层 bio 缓存 未命中 或 写回 时，按 扇区 与磁盘交换

读路径：查页缓存 → 命中返回 / 未命中 readpage → bio → 磁盘。

→ Ch 14

section-3-基数树与标签

大文件缓存 — 按页索引 O(1) 量级 查找

一、为何不用链表扫描

大文件可能有 成千上万 缓存页 — 顺序扫描 不可接受。

Linux 2.6 为每个 address_space 维护一棵 基数树 (Radix Tree)：

  • 键：页在文件内的 索引（偏移 / 页号）
  • 值：对应 struct page *

→ struct page：Ch 8

Modern 对照： 新内核多用 XArray 替代 Radix Tree；ULK 概念仍为「索引 → 页」。

二、基数树标签 (Tags)

在庞大缓存中快速找 特定状态 的页 — 树节点为子节点维护 标签位图：

标签 含义
PAGECACHE_TAG_DIRTY 脏页 — 内存已改、尚未写回磁盘
PAGECACHE_TAG_WRITEBACK 正在写回 的页

查找脏页时可 跳过整棵无脏子树 — 写回与 sync 路径大幅加速。

→ 写回机制：section-5

深潜可选： radix_tree_tagged()、tag_pages_for_writeback — 见 lib/radix-tree.c（historic）。

section-4-缓冲页与buffer_head

一页内 多个块 在磁盘上 不连续 时的细粒度描述

一、块 vs 页

单位 层级
页 (Page) 页缓存、MMU — 通常 4KB
块 (Block) VFS / FS 逻辑单位 — 常为 1KB 等

一页可含 多个块；理想情况下页内块在磁盘 连续 — 一个 bio 即可。

二、何时需要缓冲页

当页内各块在磁盘 物理不连续 时（碎片、文件空洞 等）：

  • 仍用 一页 存数据
  • 额外为 每个块 挂 buffer_head（缓冲区头）

三、buffer_head 记录什么

字段类 内容
磁盘位置 所属 块设备 + 逻辑块号
状态 是否脏、是否正在 I/O …
链接 页内多块之间的链表关系

缓冲页 = 数据页 + 一组 buffer_head — 块层可对 单块 构造 I/O。

四、与普通页缓存的区别

普通页缓存页 缓冲页
索引 address_space 基数树 — 文件偏移 同上 + 块级 buffer_head
I/O 粒度 常 整页 readpage/writepage 可能 按块 分散 I/O
典型 顺序大文件 碎片化 Ext 类 FS（ULK 2.6 常见）

Modern 对照： 新 FS（如 ext4 部分路径）减少 buffer_head 依赖，多用 bio 直挂页；读 ULK 理解 页/块不对齐 问题即可。

section-5-回写脏页与pdflush

延迟写 — 合并多次修改，提高响应速度

一、脏页 (Dirty Pages)

进程 写 页缓存 → 页标为 dirty：

  • 不立即 写磁盘
  • 多次写同一页 → 一次 物理更新
  • 系统响应更快

脏页统计影响 内存回收 决策（→ Ch 17）。

二、pdflush 内核线程池

ULK 2.6 用 pdflush — 2～8 个 动态内核线程，后台 刷新脏页：

唤醒条件 说明
脏页比例超阈值 通常 > 总页数 ~10%（背景写回）
脏页停留过久 周期性 超时 — 防止脏页长期占内存

线程从 address_space / 全局脏页列表取页 → writepage → bio → 块层。

→ 块 I/O：Ch 14

Modern 对照： pdflush 已由 per-backing-device flush 线程（bdi_writeback）取代；机制仍为 阈值 + 周期写回。

深潜可选： pdflush_operation、background_writeout — 2.6 mm/page-writeback.c。

三、与基数树标签配合

写回前用 PAGECACHE_TAG_DIRTY 快速 定位脏页，跳过干净子树 — section-3。

section-6-同步系统调用

用户态 强制 持久化 — 绕过纯延迟写

一、三个 syscall 对比

调用 范围 行为
sync() 全局 刷新系统中 所有 脏缓冲区到磁盘（粗粒度、可能很重）
fsync(fd) 单个打开文件 该文件 数据块 + inode 元数据 均落盘
fdatasync(fd) 单个打开文件 仅 数据块 — 不 强制 inode 块（除非 FS 需 inode 才能读数据）

→ syscall 路径：Ch 10 · TLPI

二、典型使用场景

场景 选择
数据库 事务提交 fsync / fdatasync 保证 WAL 持久
关机 / 卸载前 sync
仅需数据、可接受部分元数据延迟 fdatasync（可能更快）

HFT：日志/fsync 延迟 是 tail latency 常见来源 — 专用盘、顺序写、减少 sync 频率。

三、本章小结

read  → 查 address_space 基数树 → 命中 / readpage → 页缓存
write → 改页 → dirty 标签
    ↓ 后台 pdflush 或 sync/fsync
writepage → bio → Ch 14 块层 → 磁盘
