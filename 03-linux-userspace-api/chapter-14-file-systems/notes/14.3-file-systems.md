## 本节讲什么

分区（§14.2）只是「一段连续扇区」。要在上面放文件，得先**造一个文件系统**：把这段扇区划成「元数据区 + 数据区」。这一节钉四件事：

1. **任何文件系统都有同一个骨架**：超级块（描述整个卷）+ inode 表（每个文件的元数据）+ 数据块（内容）。`statfs()` 拿到的就是**超级块的用户态投影**。
2. **ext2/3/4 是「块组」结构**：整个卷被切成等大的块组，每组自带一份位图和 inode 表 —— 目的是让元数据分散到全盘、缩短寻道。这是 TLPI 特意用 ext2 讲布局的原因。
3. **`/proc/fs/ext4/` 与 `/proc/fs/jbd2/` 是运行时的窗口**：不用读裸设备、不用装 `dumpe2fs`，就能看一个 ext4 实例的运行时参数与日志层状态。
4. **能算的和不能算的要分开说**：本容器 `/dev` 下**没有任何块设备**（§14.1 实测）⇒ 块组在盘上的物理排布**不可实测**，只有「组数」能按官方文档公式推算。

## 1. 文件系统的通用骨架

| 段 | 内容 | 用户态能怎么看 |
|----|------|--------------|
| **引导块** | 给 x86 引导扇区留的 1024 字节 | 读裸设备，本容器做不到 |
| **超级块** | 卷的总参数：块大小、总块数、inode 总数、magic、计数器 | **`statfs()` / `statvfs()`（§14.11）** ← 本节 ① |
| **inode 表** | 每个文件一条记录（类型/权限/属主/大小/时间/数据块指针） | `stat()`（§14.4） |
| **数据块** | 文件内容；**目录的内容就是「名字 → inode 号」表** | `read()` |

> **文件名不在 inode 里**，在目录的数据块里。这一条是理解硬链接的钥匙（§14.4）。

TLPI 用 ext2 讲布局，因为它结构最干净：`ext2 → ext3`（加日志）`→ ext4`（加 extent、flex_bg、延迟分配…），**骨架没变**。看懂 ext2 的块组，ext4 的 `dumpe2fs` 输出也就看懂了。

`statfs()` 返回的结构体里，`f_type` 是**识别「这是哪个文件系统」的唯一硬判据**：

| 文件系统 | `f_type` | 常量名 |
|----------|----------|--------|
| ext2 / ext3 / ext4 | `0xef53` | `EXT4_SUPER_MAGIC` |
| tmpfs / ramfs | `0x01021994` | `TMPFS_MAGIC` |
| proc | `0x9fa0` | `PROC_SUPER_MAGIC` |
| sysfs | `0x62656572`（`"seer"` 小端读） | `SYSFS_MAGIC` |
| squashfs | `0x73717368` | `SQUASHFS_MAGIC` |
| nfs | `0x6969` | `NFS_SUPER_MAGIC` |

> `f_type` 是 **Linux 特有**的（POSIX 的 `statvfs` 里本来没有，glibc 又给加回来了，详见 §14.11）。

## 2. ext2/3/4 的块组布局（照官方文档，不凭印象）

「一个块组从上到下是什么」这件事**不要凭印象写**。v6.6 自带的 `Documentation/filesystems/ext4/blockgroup.rst:6-28` 给了官方表格：

| 段 | 大小 |
|----|------|
| `Group 0 Padding` | `1024 bytes` |
| `ext4 Super Block` | `1 block` |
| `Group Descriptors` | `many blocks` |
| `Reserved GDT Blocks` | `many blocks` |
| `Data Block Bitmap` | `1 block` |
| `inode Bitmap` | `1 block` |
| `inode Table` | `many blocks` |
| `Data Blocks` | `many more blocks` |

（上表逐行照抄 `blockgroup.rst:6-28` 的官方表格，只是改成了 Markdown 表格以便排版。）

三个必须记住的细节：

1. **`Group 0 Padding` 只存在于 0 号组**（`blockgroup.rst:28`）：ext2 起源于 x86，0 号块的**前 1024 字节要留给引导扇区**，所以超级块只能从 offset 1024 开始。别的组开头本来就在卷内部，不需要这段填充。
2. **超级块与组描述符只在「部分」块组里有冗余副本**（`blockgroup.rst:37-43`），不是每组一份；`mkfs` 还会额外预留 **reserved GDT blocks**，用途是将来把文件系统扩到 1024 倍时能就地扩展组描述符表。
3. **位图与 inode 表不一定在自己的组里**（`blockgroup.rst:50-60`）：每组的位置由 `grp.bg_inode_table_*` 明确给出，而 **ext4 的 `flex_bg` 允许把多个组的位图/inode 表打包塞进同一个组**（`blockgroup.rst:62-75`，ext4 独有）。所以「第 N 组的数据块紧跟第 N 组的 inode 表」**只对纯 ext2 成立**。

为什么要有「块组」？一句话：**把元数据摊到全盘**。如果 inode 表只有一份，每次创建文件都要跳到盘上同一片区域，机械盘上就是反复长寻道。切组之后，同一目录下的新文件尽量进同一个组，元数据更新就集中在少数几个柱面上。

## 3. `statfs()`：超级块的用户态投影

`statfs(2)` / `fstatfs(2)` 是本节唯一「真能看到东西」的 API：

<!--OUT:c14_3_fs_layout|after=① statfs,until=② /proc-->

```text
  f_type   = 0xef53        ← magic 0xef53 = ext2/3/4（superblock 第一眼）
  f_bsize  = 4096          块大小（superblock 的核心参数，块组的粒度）
  f_blocks = 3789825       总块数 × 块大小 = 卷容量 15523123200 字节
  f_files  = 1966080       inode 总数（inode table 的总容量）
  f_ffree  = 1816192       空闲 inode
  f_namelen= 255           单个文件名上限
  → 已用 inode 149888 个，占 7.624%
```

逐字段对账（`/app` 这个 ext4 实例）：

| 字段 | 实测值 | 它是超级块里的什么 |
|------|--------|------------------|
| `f_type` | `0xef53` | ext2/3/4 的 `s_magic`，**第一眼判类型** |
| `f_bsize` | `4096` | 逻辑块大小（`s_log_block_size` → `1 << (10 + n)`）。**块组粒度的分母** |
| `f_blocks` | `3789825` | 总块数 `s_blocks_count`；× `f_bsize` = 卷容量 |
| `f_files` | `1966080` | inode 总数 `s_inodes_count`（inode 表容量，**建卷时定死**） |
| `f_ffree` | `1816192` | 空闲 inode |
| `f_namelen` | `255` | 单个文件名上限（`NAME_MAX`） |

`f_files` 在 HFT 里特别值得看一眼：**inode 总数是 `mkfs` 时按「多少字节一个 inode」算出来的**（ext4 默认 `bytes-per-inode = 16384`），**建完之后改不了**。所以「要放 1 亿个行情快照文件」这件事必须在 `mkfs` 阶段就把 `-i` 调小 —— 「容量够、inode 不够」是运维上非常常见的翻车方式。

## 4. `/proc/fs/ext4/<dev>/`：不读裸设备也能看运行时参数

`/proc/fs/ext4` 是 ext4 注册的 **per-fs 接口**（`fs/ext4/sysfs.c` 里 `ext4_register_sysfs()` 建的，sysfs 与 procfs 双份）。每个已挂载实例一个目录，目录名是**设备名**：

<!--OUT:c14_3_fs_layout|after=② /proc,until=③ /proc/fs/jbd2-->

```text
  > /proc/fs/ext4：
    nvme0n1p1
    nvme0n1p16
  > 第一个 ext4 实例：nvme0n1p1
  > /proc/fs/ext4/nvme0n1p1：
    fc_info
    options
    mb_stats
    mb_groups
    es_shrinker_info
    mb_structs_summary
```

| 文件 | 看什么 |
|------|--------|
| `options` | 这个实例生效的挂载选项（`delalloc`、`journal_checksum`…）。排查「为什么我和别人性能不一样」第一个看它 |
| `mb_stats` / `mb_groups` / `mb_structs_summary` | **mballoc**（多块分配器）统计。`mb_groups` 会**逐组**打印还有多少空闲块 —— 这是不读裸设备就能看到块组信息的一条捷径 |
| `fc_info` | fast commit 状态 |
| `es_shrinker_info` | extent status tree 的回收器状态 |

> ⚠️ 目录名是**设备名**，来自「这个超级块挂在哪个块设备上」。容器里看到的是**宿主**的设备名（`/proc` 无命名空间隔离），跨宿主机比较无意义。

## 5. `/proc/fs/jbd2/<dev>-<n>/`：日志层是独立的一层

`jbd2` 是 ext4 用的日志实现（**J**ournaling **B**lock **D**evice 2，来自 ext3 的 `jbd`）。它注册了 `/proc/fs/jbd2/<device>-<journal_number>/`：

<!--OUT:c14_3_fs_layout|after=③ /proc/fs/jbd2,until=④ 块组-->

```text
  > /proc/fs/jbd2：
    nvme0n1p1-8
    nvme0n1p16-8
  > 第一个 jbd2 实例：nvme0n1p1-8
  > /proc/fs/jbd2/nvme0n1p1-8：
    info
    --- /proc/fs/jbd2/nvme0n1p1-8/info ---
    212 transactions (212 requested), each up to 5461 blocks
    average: 
      0ms waiting for transaction
      0ms request delay
      6985ms running transaction
      0ms transaction was being locked
      0ms flushing data (in ordered mode)
      2ms logging transaction
      1264us average transaction commit time
      3589 handles per transaction
      140 blocks per transaction
      143 logged blocks per transaction
```

**目录名尾巴上的 `-8` 是什么？** 是**日志编号**：ext4 把日志放在固定的 **inode #8** 里，`jbd2_journal_init_dev()` 的 journal number 参数就是它。所以「哪个日志属于哪个文件系统」看**前缀设备名**，`-N` 只区分同一设备上的多条日志。

`info` 的读法与「只能看增量」的坑，见 §14.6（那里有 590 → 591 → 592 的实测对照）。

## 6. 块组的物理布局：本容器只能算「组数」

这一节的**诚实边界**必须写清楚：

- 要验证「块组在盘上怎么排」，必须**读裸设备**（`dumpe2fs(8)` / `debugfs(8)` 就是干这个的）。
- 本容器 `/dev` 下**没有任何块设备**（§14.1 实测：4 个字符设备 + 5 个 `nvidia*` 普通文件，块设备 0 个），`/proc/partitions` 里的盘全在宿主上 ⇒ `dumpe2fs` 无从下手。

能做的只有**按官方公式算组数**：

<!--OUT:c14_3_fs_layout|after=④ 块组-->

```text
  按 v6.6 自带文档 Documentation/filesystems/ext4/blockgroup.rst:6-28，
  一个「标准块组」从上到下是这些段：
    Group 0 Padding(1024 字节，只有 0 号组有) / ext4 Super Block /
    Group Descriptors / Reserved GDT Blocks / Data Block Bitmap /
    inode Bitmap / inode Table / Data Blocks
  其中超级块与组描述符只在**部分**块组里有冗余副本
  （blockgroup.rst:37-43）；位图与 inode 表的位置由
  grp.bg_inode_table_* 给出，ext4 的 flex_bg 还可以把它们挪到别的组
  （blockgroup.rst:50-60）。
  要验证这些必须读裸设备（dumpe2fs 那种工具），而本容器 /dev 下只有
  4 个字符设备、没有任何块设备 —— 所以这一段只有「概念正确性」而
  没有本机实测数字。
  能算的只有**组数**：文档说组大小 = 8 × 块大小，4 KiB 块 =>
  32768 块/组 = 128 MiB（ext4/overview.rst:9-13）。
    /app 的 f_bsize   = 4096 字节
    /app 的 f_blocks  = 3789825 块（来自 statfs，见 ①）
    每组的块数        = 8 × 4096 = 32768 块 = 134217728 字节
    组数 ≈ 3789825 / 32768 = 115.66  → 向上取整 116 组
    ⚠ 这是拿**文档公式**推出来的，不是实测块组表；
      「这些组到底怎么排」只能读裸设备才知道。

=== c14_3 done ===
```

依据是 v6.6 自带的 `Documentation/filesystems/ext4/overview.rst:9-13`：

> The size of a block group is specified in `sb.s_blocks_per_group` blocks, though it can also calculated as 8 * `block_size_in_bytes`. With the default block size of 4KiB, each group will contain 32,768 blocks, for a length of 128MiB. **The number of block groups is the size of the device divided by the size of a block group.**

于是：`3789825 / 32768 = 115.66 → 116 组`。

> ⚠️ 这是**推算**，不是实测块组表。程序自己在输出里也标了这句话。

## 完整源码

完整源码 [`code/c14_3_fs_layout.c`](../code/c14_3_fs_layout.c)：

```c
/* c14_3_fs_layout.c —— TLPI §14.3 File Systems（传统布局：以 ext2/ext4 为范例）
 *
 *  §14.3 讲的是「块组」布局：boot block + superblock + group descriptor +
 *  block bitmap + inode bitmap + inode table + data blocks。要看这套东西
 *  通常得用 dumpe2fs 读裸设备 —— **容器里没有裸设备，做不了**。
 *
 *  所以本 demo 改成「用能拿到的东西反推」：
 *    ① statfs() 的字段就是 superblock 在用户态的那一面
 *       （块大小、总块数、总 inode 数……）
 *    ② /proc/fs/ext4/<dev>/ ：内核把每个已挂载 ext4 的运行时参数挂在这里，
 *       这才是「不读裸设备也能看 ext4」的入口
 *    ③ /proc/fs/jbd2/ ：ext4 的日志层（jbd2）的运行时接口
 *
 *  ⚠️ 诚实标注：本 demo **不能**验证块组的物理布局（那需要 dumpe2fs + 裸设备），
 *    只能验证「superblock 在用户态的投影」与「内核暴露的运行时参数」。
 *
 *  编译：gcc -O0 -Wall -Wextra -o c14_3 c14_3_fs_layout.c
 */
#define _GNU_SOURCE
#include <sys/statfs.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <dirent.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void sec(const char *t)
{
    printf("\n== %s ==\n", t);
}

/* 列出目录条目（最多 maxn 个），返回 0 表示成功 */
static int list_dir(const char *path, int maxn)
{
    DIR *d = opendir(path);
    struct dirent *e;
    int n = 0;

    if (d == NULL) {
        printf("  opendir(%s) -> errno=%d (%s)\n", path, errno, strerror(errno));
        return -1;
    }
    printf("  > %s：\n", path);
    while ((e = readdir(d)) != NULL && n < maxn) {
        if (e->d_name[0] == '.' &&
            (e->d_name[1] == '\0' || (e->d_name[1] == '.' && e->d_name[2] == '\0')))
            continue;
        printf("    %s\n", e->d_name);
        n++;
    }
    closedir(d);
    return 0;
}

/* 取目录里第一个非 . 条的条目名（用于找 /proc/fs/ext4 下的设备名）*/
static int first_entry(const char *path, char *out, size_t cap)
{
    DIR *d = opendir(path);
    struct dirent *e;

    out[0] = '\0';
    if (d == NULL)
        return -1;
    while ((e = readdir(d)) != NULL) {
        if (e->d_name[0] == '.' &&
            (e->d_name[1] == '\0' || (e->d_name[1] == '.' && e->d_name[2] == '\0')))
            continue;
        snprintf(out, cap, "%s", e->d_name);
        break;
    }
    closedir(d);
    return out[0] == '\0' ? -1 : 0;
}

/* 打一个文件的前 maxlines 行 */
static void dump_file(const char *path, int maxlines)
{
    FILE *fp = fopen(path, "r");
    char line[512];
    int n = 0;

    if (fp == NULL) {
        printf("    %-40s 打不开（errno=%d）\n", path, errno);
        return;
    }
    printf("    --- %s ---\n", path);
    while (fgets(line, sizeof(line), fp) != NULL && n < maxlines) {
        size_t len = strlen(line);
        if (len > 0 && line[len - 1] == '\n')
            line[len - 1] = '\0';
        printf("    %s\n", line);
        n++;
    }
    fclose(fp);
}

int main(void)
{
    /* ---------- ① superblock 在用户态的投影 ---------- */
    sec("① statfs() 字段 = superblock 的用户态投影（ext4 示例）");
    {
        struct statfs sfs;

        if (statfs("/app", &sfs) == -1) {
            printf("  statfs(/app) errno=%d (%s)\n", errno, strerror(errno));
        } else {
            printf("  f_type   = %#-12lx  ← magic 0xef53 = ext2/3/4（superblock 第一眼）\n",
                   (unsigned long) sfs.f_type);
            printf("  f_bsize  = %-12lu  块大小（superblock 的核心参数，块组的粒度）\n",
                   (unsigned long) sfs.f_bsize);
            printf("  f_blocks = %-12llu  总块数 × 块大小 = 卷容量 %llu 字节\n",
                   (unsigned long long) sfs.f_blocks,
                   (unsigned long long) sfs.f_blocks * sfs.f_bsize);
            printf("  f_files  = %-12llu  inode 总数（inode table 的总容量）\n",
                   (unsigned long long) sfs.f_files);
            printf("  f_ffree  = %-12llu  空闲 inode\n",
                   (unsigned long long) sfs.f_ffree);
            printf("  f_namelen= %-12lu  单个文件名上限\n", (unsigned long) sfs.f_namelen);
            printf("  → 已用 inode %llu 个，占 %.3f%%\n",
                   (unsigned long long) (sfs.f_files - sfs.f_ffree),
                   100.0 * (double) (sfs.f_files - sfs.f_ffree) / (double) sfs.f_files);
        }
    }

    /* ---------- ② /proc/fs/ext4 ---------- */
    sec("② /proc/fs/ext4/<dev>/：不读裸设备也能看 ext4 的运行时参数");
    list_dir("/proc/fs/ext4", 8);
    {
        char dev[128];
        char path[512];

        if (first_entry("/proc/fs/ext4", dev, sizeof(dev)) == 0) {
            printf("  > 第一个 ext4 实例：%s\n", dev);
            snprintf(path, sizeof(path), "/proc/fs/ext4/%s", dev);
            list_dir(path, 20);
        } else {
            printf("  /proc/fs/ext4 里没有条目\n");
        }
    }

    /* ---------- ③ /proc/fs/jbd2 ---------- */
    sec("③ /proc/fs/jbd2/<dev>-<n>/：ext4 的日志层（jbd2）");
    list_dir("/proc/fs/jbd2", 8);
    {
        char dev[128];
        char path[512];

        if (first_entry("/proc/fs/jbd2", dev, sizeof(dev)) == 0) {
            snprintf(path, sizeof(path), "/proc/fs/jbd2/%s", dev);
            printf("  > 第一个 jbd2 实例：%s\n", dev);
            list_dir(path, 20);
            snprintf(path, sizeof(path), "/proc/fs/jbd2/%s/info", dev);
            dump_file(path, 14);
        }
    }

    /* ---------- ④ 块组结构只能在笔记里讲 ---------- */
    sec("④ 块组的物理布局——本容器无法实测（只有组数能算）");
    printf("  按 v6.6 自带文档 Documentation/filesystems/ext4/blockgroup.rst:6-28，\n"
           "  一个「标准块组」从上到下是这些段：\n"
           "    Group 0 Padding(1024 字节，只有 0 号组有) / ext4 Super Block /\n"
           "    Group Descriptors / Reserved GDT Blocks / Data Block Bitmap /\n"
           "    inode Bitmap / inode Table / Data Blocks\n"
           "  其中超级块与组描述符只在**部分**块组里有冗余副本\n"
           "  （blockgroup.rst:37-43）；位图与 inode 表的位置由\n"
           "  grp.bg_inode_table_* 给出，ext4 的 flex_bg 还可以把它们挪到别的组\n"
           "  （blockgroup.rst:50-60）。\n"
           "  要验证这些必须读裸设备（dumpe2fs 那种工具），而本容器 /dev 下只有\n"
           "  4 个字符设备、没有任何块设备 —— 所以这一段只有「概念正确性」而\n"
           "  没有本机实测数字。\n");
    {
        struct statfs sfs;
        if (statfs("/app", &sfs) == 0) {
            unsigned long long per_group = 8ULL * (unsigned long long) sfs.f_bsize;
            unsigned long long nblk = (unsigned long long) sfs.f_blocks;
            unsigned long long ng = (nblk + per_group - 1) / per_group;

            printf("  能算的只有**组数**：文档说组大小 = 8 × 块大小，4 KiB 块 =>\n"
                   "  32768 块/组 = 128 MiB（ext4/overview.rst:9-13）。\n");
            printf("    /app 的 f_bsize   = %ld 字节\n", (long) sfs.f_bsize);
            printf("    /app 的 f_blocks  = %llu 块（来自 statfs，见 ①）\n", nblk);
            printf("    每组的块数        = 8 × %ld = %llu 块 = %llu 字节\n",
                   (long) sfs.f_bsize, per_group, per_group * (unsigned long long) sfs.f_bsize);
            printf("    组数 ≈ %llu / %llu = %.2f  → 向上取整 %llu 组\n",
                   nblk, per_group, (double) nblk / (double) per_group, ng);
            printf("    ⚠ 这是拿**文档公式**推出来的，不是实测块组表；\n"
                   "      「这些组到底怎么排」只能读裸设备才知道。\n");
        } else {
            printf("  statfs(/app) errno=%d (%s)\n", errno, strerror(errno));
        }
    }

    printf("\n=== c14_3 done ===\n");
    return 0;
}
```

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 以为「块」= 512 字节 | **扇区**才是 512 字节。文件系统的「块」由超级块决定，就是 `f_bsize`（ext4 常见 4096）。差 8 倍 |
| 2 | 以为每组都有一份超级块 | 只有**部分**组有冗余副本（`blockgroup.rst:37-43`） |
| 3 | 以为 inode 表一定紧跟位图 | 只对纯 ext2 成立。ext4 的 `flex_bg` 会把多个组的位图/inode 表打包进同一组（`blockgroup.rst:62-75`） |
| 4 | 以为 0 号组那段填充是「对齐用」 | 是给 x86 **引导扇区**留的 1024 字节（`blockgroup.rst:28`），所以超级块在 offset 1024 |
| 5 | 用 `f_bfree`/`f_ffree` 算「还剩百分之几」 | 这两个数是**别的进程也在改**的活值（宿主上还有别的容器）。`f_blocks`/`f_files` 才稳定 |
| 6 | 以为 `f_files` 可以事后调大 | inode 表在 `mkfs` 时定死，`tune2fs` 只能看不能加 —— 只能重建文件系统 |
| 7 | 以为 `statfs().f_type` 到处都有 | 它是 **Linux 特有**字段（POSIX 标准里没有） |
| 8 | 以为 `dumpe2fs` 输出的「每组一段」全都必需 | 可以用 `dumpe2fs -g` 只看组描述符。容器里连这条都跑不了 —— 没有块设备 |
| 9 | 拿 `/proc/fs/ext4/<dev>` 的目录名当「自己的」设备 | 那是**宿主**的设备名。容器里看到的可能是宿主上所有 ext4 实例 |

## HFT / 嵌入式关联

| 场景 | 结论怎么用 |
|------|-----------|
| **inode 预算 = 文件数预算** | 行情系统常按「每天每标的每个快照一个文件」设计。ext4 默认一个 inode 摊 16384 字节，1 TiB 卷只有约 6700 万 inode。**要在 `mkfs` 阶段按目标文件数反算 `-i`**，否则写满后 `ENOSPC` 但 `df` 显示还有空间 |
| **`f_type` 是最可靠的「这条路是什么」判据** | 用路径名判断「这是不是内存盘」不可靠（谁都能 `mkdir /data`）。`statfs("/data").f_type == 0x01021994` 才能断定是 tmpfs |
| **块组分散 = 元数据抖动被摊平** | 机械盘上是寻道；SSD 上是**通道/裸片并行度**。HFT 落盘盘上用 `-O flex_bg` 把元数据聚到少数几个组，反而能减少写放大 |
| **嵌入式 flash 与块组** | eMMC / SD 卡的 FTL 会做磨损均衡，「块组布局在物理上是否连续」已不由文件系统决定。所以相同的块组参数在 flash 上收益不同 —— UBIFS / F2FS 就是为这个问题重新设计的 |
| **`mb_groups` 是只读诊断的金矿** | 最小化嵌入式 rootfs 上没有 `dumpe2fs` 时，`cat /proc/fs/ext4/mmcblk0p2/mb_groups` 能直接看每组剩余空间，判断是不是「某些组被写爆了」 |
| **别把两个「日志」搞混** | TLPI 这里讲的日志是**同一文件系统内部**的 jbd2；HFT 说的「日志盘」通常是**另一个文件系统**。前者靠 `fsync` 语义，后者靠 `st_dev` 不同（§14.2） |

<summary>代码自测（Q&A）</summary>

**Q1：`f_type = 0xef53` 是从哪来的？为什么 ext2/3/4 是同一个值？**

A：它是 ext 系列超级块的 `s_magic`。ext3 只是在 ext2 上加了 jbd 日志、ext4 又加了 extent/flex_bg 等**可选特性位**，超级块前半部分（含 magic）保持不变 —— 所以三者 `f_type` 相同。要区分具体是哪个版本，得看**特性位**（`tune2fs -l` 的 `Filesystem features`），而 `statfs()` 拿不到这些位。

**Q2：为什么 0 号块组比别的组多一段 1024 字节填充？**

A：`blockgroup.rst:28`。x86 的引导扇区占 0 号块的**前 1024 字节**（MBR + 分区表），所以超级块必须从 offset 1024 开始。只有 0 号组的开头落在设备起点，所以只有它需要 padding。

**Q3：`f_bsize` 和 `st_blksize` 是同一个东西吗？**

A：不是。`f_bsize`（`statfs`）是**文件系统逻辑块大小**（卷级参数）；`st_blksize`（`stat`）是**这个文件推荐的 I/O 大小**（对象级建议）。本容器两者都是 4096，容易混。

**Q4：本机怎么知道 `/app` 是 ext4？**

A：两条路交叉验证。① `statfs("/app").f_type == 0xef53`（① 段实测）；② `/proc/fs/ext4` 下的实例名里有 `nvme0n1p1`，而 §14.2 的 ② 段证明 `/app` 的 `st_dev` = `259:1` → 对应 `nvme0n1p1`。

**Q5：为什么说「组数只能是推算」？**

A：真正的组数写在**组描述符表**里，而它在盘上（要读裸设备）。我们只有 `statfs` 的 `f_blocks` 和文档给的「组大小 = 8 × 块大小」，两个公式相除得到 116 —— 是推算。程序输出里明确标了 `⚠ 这是拿文档公式推出来的`。

**Q6：`/proc/fs/jbd2/nvme0n1p1-8` 里的 `-8` 是什么？**

A：**日志编号**，在 ext4 里就是日志所在的 inode 号（ext4 固定用 inode #8 存日志）。同一块设备可以有多条日志，`-N` 用来区分；判断归属看**前缀设备名**。

**Q7：为什么 `/proc/fs/ext4` 里的目录名是设备名而不是挂载点？**

A：因为 ext4 的这套接口是**按超级块**注册的，而超级块的天然标识就是它所在的块设备。一个超级块可以被 bind mount 到很多挂载点（本容器 `/lib`、`/usr/lib`、`/app` 都是同一个 `259:1`，见 §14.7），用挂载点命名会撞车。

</details>
