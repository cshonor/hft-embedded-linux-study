## 本节讲什么

`open("/dev/null")` 与 `open("/etc/passwd")` 走的是**同一套** `open` → VFS → inode 的路径。区别只在最后一步：VFS 一看 inode 的类型位是「字符设备」，就把后续的 `read`/`write` 交给**设备驱动**，而不是交给文件系统的数据块。这一节要钉住三件事：

1. **设备特殊文件仍然是 inode** —— 它住在某个文件系统里、有 inode 号、有权限位；只是它没有数据块，取而代之的是一个**设备号**（`st_rdev`）。
2. **`st_dev` 与 `st_rdev` 是两个完全不同的字段** —— 前者说「这个 inode 住在哪个文件系统实例上」，后者说「这个节点代表哪个设备」。混淆这两个是本节最大的坑。
3. **类型由 `st_mode` 的类型位决定，不由路径名决定** —— 本容器 `/dev` 下就躺着 5 个名字像设备、实际是**普通文件**的条目。

这三件事在 `c14_1_device_files.c` 里各有一段可运行的验证。

## 1. 设备特殊文件在 inode 里的位置

`stat(2)` 给出的 `st_mode` 不是一个「权限八进制数」，而是 **`S_IFMT`（4 位类型）+ 权限位**。类型位一共七种，与「要不要设备号」的关系如下：

| 类型 | 判定宏 | `st_rdev` 有意义？ | 典型用途 |
|------|--------|-------------------|----------|
| 普通文件 | `S_ISREG` | 否 | 数据 |
| 目录 | `S_ISDIR` | 否 | 名字映射（§14.4） |
| 符号链接 | `S_ISLNK` | 否 | 间接寻址 |
| **块设备** | `S_ISBLK` | **是** | 可随机、按块访问；经页缓存（`/dev/nvme0n1`） |
| **字符设备** | `S_ISCHR` | **是** | 流式；一般不做块缓冲（`/dev/tty`、`/dev/null`） |
| FIFO | `S_ISFIFO` | 否 | 管道文件（§44） |
| 套接字 | `S_ISSOCK` | 否 | Unix 域套接字（§57） |

> **关键区分**：只有块/字符设备**带设备号**。FIFO 和套接字虽然也是「特殊文件」，但它们在 inode 里不带 `st_rdev` —— 这一点决定了 `mknod(2)` 的权限行为（造 FIFO 不要特权，造设备节点要）。

「字符」与「块」的差别不在**能不能**随机访问，而在**内核走哪条路**：块设备在 VFS 之下还有一层缓冲区（页缓存 / 块 I/O 层），字符设备直接把 `read`/`write` 交给驱动的 `file_operations`。所以同一个存储介质既可以出字符设备节点也可以出块设备节点。

## 2. `dev_t` 是怎么编码的

`dev_t` 是**不透明类型**，必须用 `<sys/sysmacros.h>` 的 `makedev()` / `major()` / `minor()` 操作它 —— 手写位运算会在 32/64 位、大端/小端之间出错。

Linux 的编码是 **12 位 major + 20 位 minor**，拼成 32 位。程序里把上限也打出来：

<!--OUT:c14_1_device_files|until== ② st_dev-->

```text
== ① dev_t 的编码：makedev() 与 major()/minor() ==
  makedev(1, 3)         = 259          0x103 -> 1:3
  makedev(259, 1)       = 66305        0x10301 -> 259:1
  makedev(0xfff, 0xfffff) = 4294967295   -> 4095:1048575  （12 位 major + 20 位 minor 的上限）
  sizeof(dev_t) = 8（glibc 侧 64 位，内核编码只用低 32 位）
```

读这张表的三个要点：

| 输入 | 结果 | 说明 |
|------|------|------|
| `makedev(1, 3)` | `259` = `0x103` | `minor` 占低 8 位，`major` 占低 12 位之外的高位；所以 `1:3` 编成 `0x103`，不是 `0x13` |
| `makedev(259, 1)` | `66305` = `0x10301` | 还原出 `259:1` —— 与 `/proc/partitions` 里分区的写法一致 |
| `makedev(0xfff, 0xfffff)` | `4294967295` = `0xffffffff` | **12 + 20 = 32 位全用满**。这是 Linux 的上限，不是 glibc 的 |

`sizeof(dev_t) = 8`：glibc 在 x86-64 上把它定义成 64 位，但**内核编码只用低 32 位**。这解释了为什么 `st_dev` 的习惯打印格式是 `major:minor` 而不是一个整数 —— 直接打整数会看到 `66305` 这种和 `259:1` 对不上的数。

## 3. `st_dev` 与 `st_rdev`：本节的核心

| 字段 | 回答的问题 | 对哪些文件有意义 | 谁提供 |
|------|-----------|-----------------|--------|
| `st_dev` | 这个 inode **住在哪个文件系统实例**上 | **所有**文件（reg/dir/chr/blk/…） | inode 的 `i_sb->s_dev` |
| `st_rdev` | 这个节点**代表哪个设备** | **只有**块设备与字符设备 | `i_rdev` |

程序对 7 个路径并排打印这两个字段：

<!--OUT:c14_1_device_files|after=① dev_t,until== ③ 扫-->

```text
  makedev(1, 3)         = 259          0x103 -> 1:3
  makedev(259, 1)       = 66305        0x10301 -> 259:1
  makedev(0xfff, 0xfffff) = 4294967295   -> 4095:1048575  （12 位 major + 20 位 minor 的上限）
  sizeof(dev_t) = 8（glibc 侧 64 位，内核编码只用低 32 位）

== ② st_dev（在哪个文件系统上）vs st_rdev（是哪个设备） ==
  /dev                 dir  mode=0041777 st_dev=0:80   st_rdev 无意义
  /dev/null            chr  mode=0020666 st_dev=0:7    st_rdev=1:3
  /dev/zero            chr  mode=0020666 st_dev=0:7    st_rdev=1:5
  /dev/random          chr  mode=0020666 st_dev=0:7    st_rdev=1:9
  /dev/urandom         chr  mode=0020666 st_dev=0:7    st_rdev=1:9
  /etc/passwd          reg  mode=0000644 st_dev=0:77   st_rdev 无意义
  /app                 dir  mode=0040700 st_dev=202:1    st_rdev 无意义
  ↑ /dev/null 的 st_dev 是它所在文件系统的设备号，st_rdev 才是字符设备 1:3
  ↑ 把 /dev 与 /dev/null 的 st_dev 对一下：**不一样** ⇒ /dev/null 并不是
    「/dev 这个目录里的一个成员」，而是**另一个文件系统上的文件被挂到这个名字上**
    （mountinfo 里它是一条 `root=/null` 的独立记录 —— 见 §14.9.4 的单文件 bind）。
    「同一个目录下的条目 st_dev 却不同」是纯靠 stat 就能看出来的硬证据。
```

这张表里有两个**只看 `stat` 就能得出的硬结论**：

1. **`/dev/null` 的 `st_dev` 是 `0:7`，而 `/dev` 自己的 `st_dev` 不是 `0:7`**（见输出的前两行）。同一个目录下的条目 `st_dev` 却不同 —— 这只能是**挂载**造成的：`/dev/null` 是**另一个文件系统**上的一个文件被挂到这个名字上。在 `/proc/self/mountinfo` 里它对应一条独立记录 `root=/null … - devtmpfs devtmpfs`，也就是 §14.9.4 的**单文件 bind 挂载**。
   > 这条判断的价值在于：它不需要 `mount` 的输出、不需要特权、不需要读 `/proc`，只用**一个 `stat` 系统调用**就能发现「这里发生过一次挂载」。
2. **`st_rdev` 只对设备节点有意义**：`/dev/null` 是 `1:3`（`/proc/devices` 里 `1` 号主设备是 `mem`，即内存设备驱动），而 `/etc/passwd`、`/app` 这些普通文件/目录打印出来的是「无意义」——在它们的 inode 里这个字段根本没被赋过值。

## 4. `/dev` 下到底有什么

「名字像设备就是设备」是错的。程序扫 `/dev` 一遍，**只按类型位分类**：

<!--OUT:c14_1_device_files|after=③ 扫,until=④ /proc/devices-->

```text
  /dev/nvidia-uvm-tools  oth  mode=0000644
  /dev/nvidia-uvm        oth  mode=0000644
  /dev/nvidia-modeset    oth  mode=0000644
  /dev/nvidiactl         oth  mode=0000644
  /dev/nvidia0           oth  mode=0000644
  /dev/urandom           chr  mode=0020666 st_rdev=1:9
  /dev/random            chr  mode=0020666 st_rdev=1:9
  /dev/zero              chr  mode=0020666 st_rdev=1:5
  /dev/null              chr  mode=0020666 st_rdev=1:3
  小计：字符设备 4 个、块设备 0 个、其它 5 个
```

这里最值得记的是 `nvidia*` 那几行：名字带 `nvidia`、看着像显卡设备节点，但 `st_mode` 显示 `mode=0000644`、类型是**普通文件**（`oth`）—— 它们是 NVIDIA 容器运行时塞进来的**标记文件**，不是设备节点。容器里没有真显卡设备节点，因为设备节点的创建要 `CAP_MKNOD`。

> 判决标准永远是 `S_ISCHR`/`S_ISBLK`，不是「文件名看着像」，也不是「`stat` 输出里有个类似设备号的东西」。

## 5. 这些节点是谁创建的：`mknod(2)` 与 `CAP_MKNOD`

`mknod(2)` 是唯一能在用户态创建「带类型位的 inode」的系统调用（`open` 出来的永远是普通文件，`mkdir` 出来的是目录）。它的权限要求有个反直觉的例外：

<!--OUT:c14_1_device_files|after=⑤ mknod,until=⑥ /dev/null-->

```text
  mknod(FIFO)   -> 0  **成功**（FIFO 与普通文件不走设备号）
  mknod(chr 1:3) -> -1 errno=1 (Operation not permitted)  ← 缺 CAP_MKNOD
```

| 调用 | 结果 | 为什么 |
|------|------|--------|
| `mknod(path, S_IFIFO \| 0600, 0)` | **成功** | FIFO 的 inode **不带设备号**，只是一个「带特殊类型位的普通对象」，不碰硬件命名空间 |
| `mknod(path, S_IFCHR \| 0666, makedev(1, 3))` | `EPERM(1)` | 设备节点会把「一个新的 major/minor」引入系统，等于扩大能触达硬件的面，所以内核要求 `CAP_MKNOD` |

本容器的 `CapEff` 是全 0（第 [14.8](14.8-mounting-and-unmounting.md) 节给出完整读数），所以字符设备节点造不出来。这条对嵌入式有意义：`/dev` 的初始化在真实板子上要么靠 `devtmpfs`（内核自动填、自动删），要么靠 `mdev`/`udev` 调 `mknod` —— 只有**静态** `/dev` 方案才需要人手动维护节点，而那正是最容易「权限位打错、major 打错」的地方。

`/proc/devices` 是「major ↔ 驱动名」的权威对照表，分成字符设备段与块设备段两节（下一节 14.2 会看块设备段）：

<!--OUT:c14_1_device_files|after=④ /proc/devices,until=⑤ mknod-->

```text
  /proc/devices: 主设备号 1 -> mem
  /proc/devices: 主设备号 5 -> /dev/tty
  /proc/devices: 主设备号 259 -> blkext
```

## 6. `/dev/null` 与 `/dev/zero`：读语义完全不同

两者都对写**无限吸收**，但读的行为相反：

<!--OUT:c14_1_device_files|after=⑥ /dev/null,until==== c14_1-->

```text
  write(/dev/null, 3 字节)  = 3
  read(/dev/null, 16 字节)  = 0  （0 = EOF）
  read(/dev/zero, 16 字节)  = 16，首字节 = 0x00（永远读到 0，不会 EOF）
  read(/dev/zero, 0 字节)   = 0  errno=0
```

| 设备 | `write` | `read` |
|------|---------|--------|
| `/dev/null` | 丢弃（返回字节数，不作任何检查） | **EOF**（返回 0） |
| `/dev/zero` | 丢弃 | 无限个 `0x00`，**永不 EOF** |

`read(fd, buf, 0)` 返回 0 是**标准行为**（POSIX：`nbyte = 0` 时 `read` 可以检测错误但**不读数据**），与设备无关 —— 所以那一行不能用来说明 `/dev/zero` 的语义。

## 完整源码

完整源码 [`code/c14_1_device_files.c`](../code/c14_1_device_files.c)：

```c
/* c14_1_device_files.c —— TLPI §14.1 设备特殊文件（Device Special Files）
 *
 *  演示「设备号三件套」：makedev() 造、major()/minor() 拆、st_rdev 读。
 *
 *    ① dev_t 的编码：Linux 用 32 位编 major/minor（12 + 20 位）
 *    ② st_dev（文件所在的文件系统）vs st_rdev（设备本身）—— 最容易被混淆的一对，
 *       并且用「/dev 与 /dev/null 的 st_dev 不同」坐实「单文件 bind 挂载」
 *    ③ 扫 /dev：**只看 st_mode 的类型位**，不看文件名
 *    ④ /proc/devices：主设备号 → 驱动名 的权威对照
 *    ⑤ mknod(2)：造 FIFO 免特权，造设备节点要 CAP_MKNOD
 *    ⑥ /dev/null 与 /dev/zero 的行为差异
 *
 *  编译：gcc -O0 -Wall -Wextra -o c14_1 c14_1_device_files.c
 */
#define _GNU_SOURCE
#include <sys/stat.h>
#include <sys/sysmacros.h>
#include <sys/types.h>
#include <dirent.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void sec(const char *t)
{
    printf("\n== %s ==\n", t);
}

/* 打一个路径的设备信息：类型位是唯一判据，名字不算数 */
static void show_dev(const char *path)
{
    struct stat st;
    const char *kind;

    if (stat(path, &st) == -1) {
        printf("  %-20s stat 失败 errno=%d (%s)\n", path, errno, strerror(errno));
        return;
    }
    kind = S_ISCHR(st.st_mode) ? "chr" : S_ISBLK(st.st_mode) ? "blk" :
           S_ISDIR(st.st_mode) ? "dir" : S_ISREG(st.st_mode) ? "reg" :
           S_ISLNK(st.st_mode) ? "lnk" : S_ISSOCK(st.st_mode) ? "sock" : "???";
    printf("  %-20s %-4s mode=%07o st_dev=%u:%-4u", path, kind,
           (unsigned) st.st_mode & 077777, major(st.st_dev), minor(st.st_dev));
    if (S_ISCHR(st.st_mode) || S_ISBLK(st.st_mode))
        printf(" st_rdev=%u:%u", major(st.st_rdev), minor(st.st_rdev));
    else
        printf(" st_rdev 无意义");
    printf("\n");
}

/* 在 /proc/devices 里找「主设备号 → 驱动名」*/
static void lookup_major(unsigned int want)
{
    FILE *fp = fopen("/proc/devices", "r");
    char line[256];

    if (fp == NULL) {
        printf("  /proc/devices: errno=%d (%s)\n", errno, strerror(errno));
        return;
    }
    while (fgets(line, sizeof(line), fp) != NULL) {
        unsigned int maj;
        char name[128];
        if (sscanf(line, " %u %127s", &maj, name) == 2 && maj == want) {
            printf("  /proc/devices: 主设备号 %u -> %s\n", maj, name);
            fclose(fp);
            return;
        }
    }
    fclose(fp);
    printf("  /proc/devices: 没找到主设备号 %u\n", want);
}

int main(void)
{
    /* ---------- ① dev_t 的编码 ---------- */
    sec("① dev_t 的编码：makedev() 与 major()/minor()");
    {
        dev_t d1 = makedev(1, 3);
        dev_t d2 = makedev(259, 1);
        dev_t d3 = makedev(0xfff, 0xfffff);

        printf("  makedev(1, 3)         = %-12llu 0x%llx -> %u:%u\n",
               (unsigned long long) d1, (unsigned long long) d1,
               major(d1), minor(d1));
        printf("  makedev(259, 1)       = %-12llu 0x%llx -> %u:%u\n",
               (unsigned long long) d2, (unsigned long long) d2,
               major(d2), minor(d2));
        printf("  makedev(0xfff, 0xfffff) = %-12llu -> %u:%u  （12 位 major + 20 位 minor 的上限）\n",
               (unsigned long long) d3, major(d3), minor(d3));
        printf("  sizeof(dev_t) = %zu（glibc 侧 64 位，内核编码只用低 32 位）\n",
               sizeof(dev_t));
    }

    /* ---------- ② st_dev vs st_rdev ---------- */
    sec("② st_dev（在哪个文件系统上）vs st_rdev（是哪个设备）");
    show_dev("/dev");
    show_dev("/dev/null");
    show_dev("/dev/zero");
    show_dev("/dev/random");
    show_dev("/dev/urandom");
    show_dev("/etc/passwd");
    show_dev("/app");
    printf("  ↑ /dev/null 的 st_dev 是它所在文件系统的设备号，st_rdev 才是字符设备 1:3\n");
    printf("  ↑ 把 /dev 与 /dev/null 的 st_dev 对一下：**不一样** ⇒ /dev/null 并不是\n");
    printf("    「/dev 这个目录里的一个成员」，而是**另一个文件系统上的文件被挂到这个名字上**\n");
    printf("    （mountinfo 里它是一条 `root=/null` 的独立记录 —— 见 §14.9.4 的单文件 bind）。\n");
    printf("    「同一个目录下的条目 st_dev 却不同」是纯靠 stat 就能看出来的硬证据。\n");

    /* ---------- ③ 扫 /dev ---------- */
    sec("③ 扫 /dev：类型位说了算，名字说了不算");
    {
        DIR *dir = opendir("/dev");
        struct dirent *e;
        int nchr = 0, nblk = 0, nother = 0;

        if (dir == NULL) {
            printf("  opendir(/dev) errno=%d (%s)\n", errno, strerror(errno));
        } else {
            while ((e = readdir(dir)) != NULL) {
                char p[512];
                struct stat st;
                const char *kind;

                if (e->d_name[0] == '.' && (e->d_name[1] == '\0' ||
                                            (e->d_name[1] == '.' && e->d_name[2] == '\0')))
                    continue;
                snprintf(p, sizeof(p), "/dev/%s", e->d_name);
                if (lstat(p, &st) == -1)
                    continue;
                kind = S_ISCHR(st.st_mode) ? "chr" : S_ISBLK(st.st_mode) ? "blk" : "oth";
                if (S_ISCHR(st.st_mode)) nchr++;
                else if (S_ISBLK(st.st_mode)) nblk++;
                else nother++;
                printf("  %-22s %-4s mode=%07o", p, kind, (unsigned) st.st_mode & 077777);
                if (S_ISCHR(st.st_mode) || S_ISBLK(st.st_mode))
                    printf(" st_rdev=%u:%u", major(st.st_rdev), minor(st.st_rdev));
                printf("\n");
            }
            closedir(dir);
            printf("  小计：字符设备 %d 个、块设备 %d 个、其它 %d 个\n",
                   nchr, nblk, nother);
        }
    }

    /* ---------- ④ /proc/devices ---------- */
    sec("④ /proc/devices：主设备号 ↔ 驱动名");
    lookup_major(1);      /* mem：/dev/null, /dev/zero, /dev/random 都挂在这里 */
    lookup_major(5);      /* tty：/dev/tty, /dev/console, /dev/ptmx */
    lookup_major(259);    /* nvme 块设备 */

    /* ---------- ⑤ mknod(2) ---------- */
    sec("⑤ mknod(2)：造 FIFO 不需要特权，造设备节点要 CAP_MKNOD");
    {
        unlink("/app/c14_1_fifo");
        errno = 0;
        if (mknod("/app/c14_1_fifo", S_IFIFO | 0666, 0) == -1)
            printf("  mknod(FIFO)   -> -1 errno=%d (%s)\n", errno, strerror(errno));
        else
            printf("  mknod(FIFO)   -> 0  **成功**（FIFO 与普通文件不走设备号）\n");

        unlink("/app/c14_1_node");
        errno = 0;
        if (mknod("/app/c14_1_node", S_IFCHR | 0666, makedev(1, 3)) == -1)
            printf("  mknod(chr 1:3) -> -1 errno=%d (%s)  ← 缺 CAP_MKNOD\n",
                   errno, strerror(errno));
        else
            printf("  mknod(chr 1:3) -> 0  **成功**\n");

        unlink("/app/c14_1_fifo");
        unlink("/app/c14_1_node");
    }

    /* ---------- ⑥ /dev/null vs /dev/zero ---------- */
    sec("⑥ /dev/null（写丢弃、读 EOF）vs /dev/zero（写丢弃、读无穷个 0）");
    {
        char buf[16];
        ssize_t n;
        int fd;

        fd = open("/dev/null", O_RDWR);
        if (fd == -1) {
            printf("  open(/dev/null) errno=%d (%s)\n", errno, strerror(errno));
        } else {
            n = write(fd, "abc", 3);
            printf("  write(/dev/null, 3 字节)  = %zd\n", n);
            n = read(fd, buf, sizeof(buf));
            printf("  read(/dev/null, 16 字节)  = %zd  （0 = EOF）\n", n);
            close(fd);
        }

        fd = open("/dev/zero", O_RDONLY);
        if (fd == -1) {
            printf("  open(/dev/zero) errno=%d (%s)\n", errno, strerror(errno));
        } else {
            memset(buf, 0xAA, sizeof(buf));
            n = read(fd, buf, sizeof(buf));
            printf("  read(/dev/zero, 16 字节)  = %zd，首字节 = 0x%02x（永远读到 0，不会 EOF）\n",
                   n, (unsigned char) buf[0]);
            errno = 0;
            n = read(fd, buf, 0);
            printf("  read(/dev/zero, 0 字节)   = %zd  errno=%d\n", n, errno);
            close(fd);
        }
    }

    printf("\n=== c14_1 done ===\n");
    return 0;
}
```

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 拿 `st_dev` 当「设备号」用来 `open` 设备 | `st_dev` 是**文件系统实例**的号，与设备驱动无关。要打开设备得自己拼 `/dev/...` 路径 |
| 2 | 以为 `st_rdev` 对所有文件都有值 | 只有 `S_ISCHR`/`S_ISBLK` 才有意义。对普通文件读它得到的是 0（或未赋值的垃圾） |
| 3 | 手写位运算拆 `dev_t` | 用 `major()`/`minor()`/`makedev()`。Linux 的编码不是「高 16 位 / 低 16 位」，而是 **12 + 20**（`makedev(0xfff,0xfffff)` = `0xffffffff`） |
| 4 | 把 `major:minor` 直接当整数打印 | `1:3` 编码成 `259`，打整数只会得到一个和「1 和 3」对不上的数。两个字段要分开打 |
| 5 | 以为 `/dev` 下的条目都在同一个文件系统上 | 本容器 `/dev/null` 的 `st_dev` 与 `/dev` 自己的 `st_dev` **不同** —— 它是从 devtmpfs **单文件 bind** 过来的。一条 `stat` 就能看出来 |
| 6 | 靠文件名判断是不是设备节点 | `/dev/nvidia0` 等 5 个条目是**普通文件**（`mode=0644`）。必须看 `S_ISCHR`/`S_ISBLK` |
| 7 | 以为 `mknod` 一律需要特权 | 造 **FIFO** 不需要（`S_IFIFO` 免特权，实测成功）；造**块/字符设备**需要 `CAP_MKNOD` |
| 8 | 以为容器里能看到宿主的块设备 | 本容器 `/dev` 下**一个块设备都没有**（`S_ISBLK` 计数为 0），所以 `dumpe2fs`/`fsck`/`mkfs` 这类工具全部用不了；分区表只能从 `/proc/partitions` 看（下一节） |

## HFT / 嵌入式关联

| 场景 | 结论怎么用 |
|------|-----------|
| **低延迟网络 / 用户态驱动** | 网卡的用户态入口往往是字符设备（`/dev/uioN`、`/dev/infiniband/uverbsN`）。**判断一个 `/dev` 条目到底是不是设备节点、它的 `st_rdev` 是多少，是写这类程序的第一步**（错一个 major 就 open 到别的驱动上） |
| **`/dev/null` 的性能陷阱** | 写 `/dev/null` 仍然走完整的 `write` → VFS → 驱动路径，**并不比写文件快**。要做「零成本对照组」应该用内存 buffer，不是 `/dev/null` |
| **块设备与 `O_DIRECT`** | 块设备节点上 `open(O_DIRECT)`（在真机上）才是 direct I/O，对齐要求由队列参数决定；字符设备上多半 `EINVAL`。同一段代码换个设备类型就可能失效（Ch13 §13.6 实测过） |
| **嵌入式静态 `/dev`** | 只读 rootfs + 精简内核时常常没有 `devtmpfs`，`/dev` 是构建时用 `mknod` 静态生成的。这时**节点表就是板级定义的一部分**（内核 Kconfig 决定哪个 major 存在），必须跟 `CONFIG_*` 一起进版本控制 |
| **容器里的设备白名单** | Docker/k8s 用 device cgroup 控制能访问哪些设备；`CapEff` 里没有 `CAP_MKNOD` 时容器内**无法自行造节点**。所以「容器里 `/dev` 有什么」是运行时配置，不是标准 —— 同一个程序在不同编排下能看到完全不同的 `/dev` |
| **`/sys/dev/block` 与设备节点互补** | 想按 major:minor 反查设备（而不是硬编码 `/dev/sda`）应该走 `/sys/dev/block/<maj>:<min>`；⚠️ 本容器 `/sys` **没有挂 sysfs**（第 [14.10](14.10-tmpfs.md) 节用 fsid 实证），所以这条路径不存在 —— 这正是 Ch12 讲的「`/sys` 里有没有东西取决于挂没挂」 |

<summary>代码自测（Q&A）</summary>

**Q1：`st_dev` 和 `st_rdev` 有什么区别？**

A：`st_dev` 回答「这个 inode 住在哪个**文件系统实例**上」，对所有文件都有意义；`st_rdev` 回答「这个设备节点代表**哪个设备**」，只对块设备与字符设备有意义。本节实测：`/dev/null` 的 `st_dev` 是 `0:7`（它住在 devtmpfs 上），`st_rdev` 是 `1:3`（它代表内存设备驱动的第 3 号）；而 `/etc/passwd` 只有 `st_dev`，`st_rdev` 无意义。

**Q2：本节说「只用一条 `stat` 就能发现一次挂载」，依据是什么？**

A：`/dev` 与 `/dev/null` 的 `st_dev` **不相同**（见 ② 段输出的前两行）。如果 `/dev/null` 只是 `/dev` 目录里的一个普通成员，它的 `st_dev` 必然等于 `/dev` 自身的 `st_dev`（`st_dev` 来自 `i_sb->s_dev`，同一个超级块给出同一个值）。两个不同的值只能说明它们**属于不同的文件系统实例** —— 这正是挂载的定义。对照 `/proc/self/mountinfo`，`/dev/null` 确实是一条独立的 `root=/null … - devtmpfs devtmpfs` 记录。

**Q3：为什么 `mknod` 造 FIFO 不需要特权，造字符设备节点却 `EPERM`？**

A：因为 FIFO 的 inode **不带设备号**。设备节点会把「一个新的 major/minor」引入系统的设备命名空间，等于扩大能触达硬件的面，所以内核要求 `CAP_MKNOD`。FIFO 只是一个带特殊类型位的对象，不碰硬件命名空间。

**Q4：`makedev(1, 3)` 为什么等于 259 而不是 0x13？**

A：Linux 的 `dev_t` 编码是 **12 位 major + 20 位 minor**：`minor` 占低 8 位，`major` 占低 12 位之外的高位部分。所以 `(1,3)` → `(1 << 8) | 3` = `0x103` = 259。上限也可以自己推：`makedev(0xfff, 0xfffff)` = `0xffffffff`（实测），即 32 位用满。

**Q5：`/dev` 下的 `nvidia0` 为什么不是设备节点？**

A：本节实测它的 `st_mode = 0000644`，`S_ISCHR`/`S_ISBLK` 都不成立 —— 它是一个**普通文件**（NVIDIA 容器运行时放的标记）。判决永远看 `st_mode` 的类型位，不看文件名。

**Q6：`read(fd, buf, 0)` 返回 0，说明 `/dev/zero` 会 EOF 吗？**

A：不能这么推。`nbyte = 0` 时 `read` 按标准**不读数据**就返回 0，和设备无关。要验证 `/dev/zero` 的语义必须给非 0 长度 —— 本节实测 `read("/dev/zero", 16)` 返回 **16** 且首字节是 `0x00`（永不 EOF），而 `read("/dev/null", 16)` 返回 **0**（EOF）。

</details>
