## 本节讲什么

「同一个 `open()` 能打开 ext4 文件、`/proc` 伪文件、`/dev/null` 设备」这件事不是免费的。内核在中间插了一层**抽象的中间层**：VFS。它定义四类对象与一套操作表，任何文件系统只要实现这些操作表就能被 `open/read/write` 使用。这一节钉三件事：

1. **四类对象的职责边界**：superblock / inode / dentry / file。其中**只有 `dentry` 是纯内存对象**（磁盘上没有 dentry 这个结构），这是最容易搞错的一点。
2. **`struct file` ≠ `struct inode`**：前者是「一次打开」的上下文（含**文件偏移**），后者是「文件本身」。`open()` 两次 → 两个 `struct file`（偏移各自独立）；`dup()` → 两个 fd 指向**同一个** `struct file`（偏移共享）。
3. **这套区分在用户态**都能观测到，不需要写内核模块：用 `/proc/self/fd/N`、`fcntl(F_GETFL)`、`lseek` 就能把四种情形一一分开。

## 1. 四个对象与它们的用户态投影

| 对象 | 内核结构 | 生命周期 | 用户态能看到什么 |
|------|---------|---------|----------------|
| **superblock** | `struct super_block` | 一次挂载实例（`mount` 时创建） | `statfs()` 的字段（§14.3）；`/proc/self/mountinfo` 的一行 |
| **inode** | `struct inode` | 一个文件对象（磁盘 inode 的内存副本） | `stat()` 的 `st_ino`/`st_mode`/…（§14.4） |
| **dentry** | `struct dentry` | **纯内存**，名字→inode 的缓存 | **没有直接 API**；`/proc/self/fd/N` 的 `readlink` 是最接近的投影 |
| **file** | `struct file` | **一次 open** 的上下文，含文件偏移与 flags | `fd` + `fcntl(F_GETFL)` + `lseek(fd, 0, SEEK_CUR)` |

<!--OUT:c14_5_vfs|after=① VFS 四对象-->

```text
  superblock -> statfs("/etc/passwd").f_type = 0x1021994
              （同一个 superblock 的另一个投影在 /proc/self/mountinfo 的一条里）
  inode      -> fstat(fd).st_ino = 2, st_mode = 0000644
  file       -> fd = 3, fcntl(F_GETFL) = 0x8000
  dentry     -> 无用户态 API；/proc/self/fd/3 的 readlink 是最接近的投影
  /proc/self/fd/3            -> /etc/passwd (deleted)

== ② open() 两次同一路径 → 两个 struct file，偏移各自独立 ==
  open 之前：
  fd1 (=open #1)             fd=3  offset=0    ino=2 flags=0x8000
  fd2 (=open #2)             fd=4  offset=0    ino=2 flags=0x8000
  对 fd1 read 3 字节（返回 3）之后：
  fd1                        fd=3  offset=3    ino=2 flags=0x8000
  fd2                        fd=4  offset=0    ino=2 flags=0x8000
  → fd1 移到 3，fd2 仍在 0：**两个独立的 struct file**
    （但两者指向同一个 inode —— 见上面的 ino 相同）

== ③ dup() → 两个 fd 共用同一个 struct file（偏移共享） ==
  dup 之前：
  fd1 (=open)                fd=3  offset=0    ino=2 flags=0x8000
  fd2 (=dup(fd1))            fd=4  offset=0    ino=2 flags=0x8000
  对 fd1 read 3 字节（返回 3）之后：
  fd1                        fd=3  offset=3    ino=2 flags=0x8000
  fd2                        fd=4  offset=3    ino=2 flags=0x8000
  → 两个偏移**一起**移到 3：fd1 与 fd2 是同一个 struct file
    这正是 dup2() 之后 close() 一个不影响另一个的原因（refcount）

== ④ 硬链接的两个路径 → 两个 struct file，但同一个 inode ==
  写入 10 字节
  fd1 -> /app/c14_5_a  ino=316405
  fd2 -> /app/c14_5_b  ino=316405
  → inode 相同，但两个 struct file 各自有偏移
  lseek(fd1, 7) 之后：fd1 offset=7，fd2 offset=0

=== c14_5 done ===
```

这段输出里有两处要特别注意：

1. **`dentry` 那一行写着「无用户态 API」**。磁盘上**没有** dentry 结构 —— 目录数据块里存的是 `(名字, inode号)`，内核读进来之后在内存里造 `struct dentry` 放进 dcache。所以「目录项缓存」是一种**纯内存的加速结构**，`drop_caches` 能把它清掉而不影响磁盘上的任何数据。
2. **`/proc/self/fd/3 -> /etc/passwd (deleted)`**。`readlink` 一个 fd 得到的是**那个 `struct file` 的 dentry 路径**，而尾巴上的 `(deleted)` 是内核 `d_path()` 在「dentry 已经被 unlink」时加的后缀。这就是 §14.4 里 `nlink=0` 现象的可视化。

四对象的**关系**（一句话一个）：

```
fd 表  ->  fd  --+
                 +--> struct file  --+
fd 表  ->  fd  --+                   +--> struct dentry --> struct inode --> struct super_block
（另一个 fd）--------------------------+
```

- 一个 `struct file` 只指向**一个** dentry（同一次打开只有一个目标）。
- 一个 dentry 指向一个 inode（正数 dentry），一个 inode 可以有**多个** dentry（硬链接）。
- 一个 inode 属于一个 superblock。

## 2. `open()` 两次同一路径：两个 `struct file`

<!--OUT:c14_5_vfs|after=② open-->

```text
  open 之前：
  fd1 (=open #1)             fd=3  offset=0    ino=2 flags=0x8000
  fd2 (=open #2)             fd=4  offset=0    ino=2 flags=0x8000
  对 fd1 read 3 字节（返回 3）之后：
  fd1                        fd=3  offset=3    ino=2 flags=0x8000
  fd2                        fd=4  offset=0    ino=2 flags=0x8000
  → fd1 移到 3，fd2 仍在 0：**两个独立的 struct file**
    （但两者指向同一个 inode —— 见上面的 ino 相同）

== ③ dup() → 两个 fd 共用同一个 struct file（偏移共享） ==
  dup 之前：
  fd1 (=open)                fd=3  offset=0    ino=2 flags=0x8000
  fd2 (=dup(fd1))            fd=4  offset=0    ino=2 flags=0x8000
  对 fd1 read 3 字节（返回 3）之后：
  fd1                        fd=3  offset=3    ino=2 flags=0x8000
  fd2                        fd=4  offset=3    ino=2 flags=0x8000
  → 两个偏移**一起**移到 3：fd1 与 fd2 是同一个 struct file
    这正是 dup2() 之后 close() 一个不影响另一个的原因（refcount）

== ④ 硬链接的两个路径 → 两个 struct file，但同一个 inode ==
  写入 10 字节
  fd1 -> /app/c14_5_a  ino=316405
  fd2 -> /app/c14_5_b  ino=316405
  → inode 相同，但两个 struct file 各自有偏移
  lseek(fd1, 7) 之后：fd1 offset=7，fd2 offset=0

=== c14_5 done ===
```

`fd1` 读走 3 字节后偏移变 3，`fd2` 仍在 0。**两个 `struct file`，同一个 inode**。

这是最容易「感觉上知道、实际会写错」的一条。它的工程含义：**`open()` 的代价不只是查 dentry**，还要分配 `struct file` 与 fd；反过来，**多线程各自 `open()` 同一个文件是安全的**，因为偏移不共享。

| 想让偏移共享 | 想各自独立 |
|-------------|-----------|
| `dup()` / `dup2()` / `fork()`（继承 fd） | 各自 `open()` |

## 3. `dup()`：两个 fd 共用一个 `struct file`

<!--OUT:c14_5_vfs|after=③ dup,until=④ 硬链接-->

```text
  dup 之前：
  fd1 (=open)                fd=3  offset=0    ino=2 flags=0x8000
  fd2 (=dup(fd1))            fd=4  offset=0    ino=2 flags=0x8000
  对 fd1 read 3 字节（返回 3）之后：
  fd1                        fd=3  offset=3    ino=2 flags=0x8000
  fd2                        fd=4  offset=3    ino=2 flags=0x8000
  → 两个偏移**一起**移到 3：fd1 与 fd2 是同一个 struct file
    这正是 dup2() 之后 close() 一个不影响另一个的原因（refcount）
```

`dup(fd1)` 之后，读 `fd1` 走 3 字节，**`fd2` 的偏移也跟着变 3** —— 两个 fd 指向**同一个 `struct file`**（内核里只是把 fd 表的两格指向同一个 `file` 对象，并给它的引用计数 +1）。

三条推论：

1. `close(fd1)` 不会让 `fd2` 失效（`struct file` 的 refcount 还 >0）。
2. **`O_APPEND` 是 per-`struct file` 的**：`dup` 出来的两个 fd 共享它；各自 `open` 的则各自独立。
3. **`fork()` 继承的 fd 也是如此**：父子进程共享偏移。这在「父子同时往一个日志文件写」时非常关键 —— 如果两个进程各自 `open`，写入位置会互相覆盖；共享同一个 `struct file` 才会正确接续。
4. `fd` 上的锁（`fcntl` 记录锁）与 `struct file`/进程相关，而 `flock()` 是 per-`struct file` 的 —— 也是这层结构带来的差别。

## 4. 硬链接的两个路径：两个 `struct file`，一个 inode

<!--OUT:c14_5_vfs|after=④ 硬链接-->

```text
  写入 10 字节
  fd1 -> /app/c14_5_a  ino=316405
  fd2 -> /app/c14_5_b  ino=316405
  → inode 相同，但两个 struct file 各自有偏移
  lseek(fd1, 7) 之后：fd1 offset=7，fd2 offset=0

=== c14_5 done ===
```

这一组和 ② 对比着看最清楚：

| | ② `open` 两次同一路径 | ④ `open` 两个硬链接路径 |
|---|---|---|
| dentry | 两个（其实 dcache 里同一个，但每次 open 各自拿引用） | **两个不同的 dentry** |
| inode | 同一个 | 同一个（`ino` 相同） |
| `struct file` | 两个，偏移独立 | 两个，偏移独立 |
| 为什么 | 每次 `open` 都造新的 `struct file` | 同左 |

**所以「硬链接」在 VFS 层的表现就是「多个 dentry 指向同一个 inode」** —— `struct file` 并不会因为 inode 相同而合并。换句话说：**「是不是同一个打开」由 `struct file` 决定，与 inode 无关。**

## 5. VFS 的代价：抽象层的开销落在哪

既然 VFS 是一层中间层，那么「多一层」的开销具体是什么？

| 开销 | 位置 | 能不能省 |
|------|------|---------|
| 路径解析（逐级 lookup） | `fs/namei.c`，每级查 dcache | **dcache 命中就基本免费**；不命中要走文件系统自己的 `lookup`（可能读磁盘） |
| 分配 `struct file` + 装 fd | `fs/open.c` / `fs/file.c` | 省不掉，但可以用 `openat2()` + `RESOLVE_*` 减少解析、或长期持有 fd |
| 权限检查 | inode 权限位 + `security_inode_permission` | 省不掉 |
| 每个文件系统自己的 read/write 实现 | `file_operations` | 这是「抽象换来的可扩展性」，也是 `io_uring` 想绕开的固定成本之一 |

> TLPI 的书里强调：**VFS 的意义在于「统一」，代价是「至少多一次间接调用」**。HFT 场景下这条链上的每一环都要能在测量里看见（`perf` 看 `dentry`/`vfs_*` 符号），否则「系统调用很慢」这种结论会归错因。

## 完整源码

完整源码 [`code/c14_5_vfs.c`](../code/c14_5_vfs.c)：

```c
/* c14_5_vfs.c —— TLPI §14.5 The Virtual File System (VFS)
 *
 *  §14.5 那张「四对象」表（superblock / inode / dentry / file）是内核态概念，
 *  用户态没有直接 API。本 demo 做的是**找到每个对象的用户态投影**，
 *  再用实验把最容易混淆的一对拆开：
 *
 *    superblock ↔ statfs()/statvfs() 的整组字段 + /proc/self/mountinfo 的一条
 *    inode      ↔ stat() 的 st_ino / st_mode / st_nlink / st_size
 *    dentry     ↔ 无用户态 API；mountinfo 的 root=/mount_point= 是它最接近的投影
 *    file       ↔ fd（+ fcntl(F_GETFL) / F_GETFD）
 *
 *  核心实验：**「两个 fd」不等于「两个 file」**
 *    ① open() 两次同一个路径 → 两个结构性独立的 struct file（偏移各自独立）
 *    ② dup()  同一个 fd        → 两个 fd 指向**同一个** struct file（偏移共享）
 *    ③ open() 两个硬链接路径   → 两个 struct file，但指向**同一个 inode**
 *  判据用 lseek() 观察偏移，而不是猜。
 *
 *  编译：gcc -O0 -Wall -Wextra -o c14_5 c14_5_vfs.c
 */
#define _GNU_SOURCE
#include <sys/stat.h>
#include <sys/statfs.h>
#include <sys/types.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void sec(const char *t)
{
    printf("\n== %s ==\n", t);
}

/* 打一个 fd 的三件套：fd 号、它自己的偏移、它指向的 inode */
static void show_fd(const char *tag, int fd)
{
    struct stat st;
    off_t off = lseek(fd, 0, SEEK_CUR);

    if (fstat(fd, &st) == -1) {
        printf("  %-26s fstat 失败 errno=%d\n", tag, errno);
        return;
    }
    printf("  %-26s fd=%d  offset=%-4lld ino=%llu flags=%#x\n",
           tag, fd, (long long) off, (unsigned long long) st.st_ino,
           (unsigned) fcntl(fd, F_GETFL));
}

/* 走一遍「fd → 路径」的反向投影（/proc/self/fd/N 是符号链接） */
static void show_fd_link(int fd)
{
    char p[64], buf[512];
    ssize_t n;

    snprintf(p, sizeof(p), "/proc/self/fd/%d", fd);
    n = readlink(p, buf, sizeof(buf) - 1);
    if (n < 0)
        printf("  %-26s readlink 失败 errno=%d\n", p, errno);
    else {
        buf[n] = '\0';
        printf("  %-26s -> %s\n", p, buf);
    }
}

int main(void)
{
    /* ---------- ① 四对象的用户态投影 ---------- */
    sec("① VFS 四对象的用户态投影");
    {
        struct statfs sfs;
        struct stat st;
        int fd = open("/etc/passwd", O_RDONLY);

        printf("  superblock -> statfs(\"/etc/passwd\").f_type = %#lx\n",
               statfs("/etc/passwd", &sfs) == 0 ? (unsigned long) sfs.f_type : 0UL);
        printf("              （同一个 superblock 的另一个投影在 /proc/self/mountinfo 的一条里）\n");

        if (fd == -1) {
            printf("  open(/etc/passwd) 失败 errno=%d (%s)\n", errno, strerror(errno));
            printf("\n=== c14_5 done ===\n");
            return 0;
        }
        if (fstat(fd, &st) == 0)
            printf("  inode      -> fstat(fd).st_ino = %llu, st_mode = %07o\n",
                   (unsigned long long) st.st_ino, (unsigned) st.st_mode & 077777);
        printf("  file       -> fd = %d, fcntl(F_GETFL) = %#x\n",
               fd, (unsigned) fcntl(fd, F_GETFL));
        printf("  dentry     -> 无用户态 API；/proc/self/fd/%d 的 readlink 是最接近的投影\n", fd);
        show_fd_link(fd);
        close(fd);
    }

    /* ---------- ② open 两次 = 两个 struct file ---------- */
    sec("② open() 两次同一路径 → 两个 struct file，偏移各自独立");
    {
        int fd1, fd2;
        ssize_t n;

        fd1 = open("/etc/passwd", O_RDONLY);
        fd2 = open("/etc/passwd", O_RDONLY);
        if (fd1 == -1 || fd2 == -1) {
            printf("  open 失败 errno=%d (%s)\n", errno, strerror(errno));
            if (fd1 != -1) close(fd1);
            if (fd2 != -1) close(fd2);
        } else {
            char buf[8];
            printf("  open 之前：\n");
            show_fd("fd1 (=open #1)", fd1);
            show_fd("fd2 (=open #2)", fd2);

            n = read(fd1, buf, 3);      /* 只推进 fd1 的偏移 */
            printf("  对 fd1 read 3 字节（返回 %zd）之后：\n", n);
            show_fd("fd1", fd1);
            show_fd("fd2", fd2);
            printf("  → fd1 移到 3，fd2 仍在 0：**两个独立的 struct file**\n");
            printf("    （但两者指向同一个 inode —— 见上面的 ino 相同）\n");
            close(fd1);
            close(fd2);
        }
    }

    /* ---------- ③ dup = 同一个 struct file ---------- */
    sec("③ dup() → 两个 fd 共用同一个 struct file（偏移共享）");
    {
        int fd1, fd2;
        ssize_t n;

        fd1 = open("/etc/passwd", O_RDONLY);
        fd2 = dup(fd1);
        if (fd1 == -1 || fd2 == -1) {
            printf("  open/dup 失败 errno=%d (%s)\n", errno, strerror(errno));
            if (fd1 != -1) close(fd1);
            if (fd2 != -1) close(fd2);
        } else {
            char buf[8];
            printf("  dup 之前：\n");
            show_fd("fd1 (=open)", fd1);
            show_fd("fd2 (=dup(fd1))", fd2);

            n = read(fd1, buf, 3);
            printf("  对 fd1 read 3 字节（返回 %zd）之后：\n", n);
            show_fd("fd1", fd1);
            show_fd("fd2", fd2);
            printf("  → 两个偏移**一起**移到 3：fd1 与 fd2 是同一个 struct file\n");
            printf("    这正是 dup2() 之后 close() 一个不影响另一个的原因（refcount）\n");
            close(fd1);
            close(fd2);
        }
    }

    /* ---------- ④ 两个路径 / 一个 inode ---------- */
    sec("④ 硬链接的两个路径 → 两个 struct file，但同一个 inode");
    {
        struct stat sa, sb;
        int fd1, fd2;

        unlink("/app/c14_5_a");
        unlink("/app/c14_5_b");

        fd1 = open("/app/c14_5_a", O_WRONLY | O_CREAT | O_TRUNC, 0644);
        if (fd1 == -1) {
            printf("  open errno=%d (%s)\n", errno, strerror(errno));
        } else {
            ssize_t n = write(fd1, "0123456789", 10);
            printf("  写入 %zd 字节\n", n);
            close(fd1);

            if (link("/app/c14_5_a", "/app/c14_5_b") == 0) {
                fd1 = open("/app/c14_5_a", O_RDONLY);
                fd2 = open("/app/c14_5_b", O_RDONLY);
                fstat(fd1, &sa);
                fstat(fd2, &sb);
                printf("  fd1 -> /app/c14_5_a  ino=%llu\n", (unsigned long long) sa.st_ino);
                printf("  fd2 -> /app/c14_5_b  ino=%llu\n", (unsigned long long) sb.st_ino);
                printf("  → inode %s，但两个 struct file 各自有偏移\n",
                       sa.st_ino == sb.st_ino ? "相同" : "不同");
                if (lseek(fd1, 7, SEEK_SET) != (off_t) -1)
                    printf("  lseek(fd1, 7) 之后：fd1 offset=%lld，fd2 offset=%lld\n",
                           (long long) lseek(fd1, 0, SEEK_CUR),
                           (long long) lseek(fd2, 0, SEEK_CUR));
                close(fd1);
                close(fd2);
            }
            unlink("/app/c14_5_a");
            unlink("/app/c14_5_b");
        }
    }

    printf("\n=== c14_5 done ===\n");
    return 0;
}
```

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 以为磁盘上有 dentry | dentry 是**纯内存**对象（dcache），磁盘上只有目录数据块里的 `(名字, inode号)` |
| 2 | 以为 `fd` 就是文件 | `fd` 只是**当前进程 fd 表的下标**；真正的对象是 `struct file`。`fd` 号在不同进程里完全无关 |
| 3 | 以为 `dup()` 会复制偏移 | `dup` 后两个 fd **共享同一个 `struct file`**，偏移一起动（本节 ③ 实测） |
| 4 | 以为两次 `open()` 会共享偏移 | 各自独立的 `struct file`，偏移独立（本节 ② 实测） |
| 5 | 以为 `O_APPEND` 是 fd 级属性 | 是 `struct file` 级；`dup`/`fork` 出的 fd 共享它，独立 `open` 的各自有 |
| 6 | 以为同一 inode 的两次打开会合并 | 不会。合并的判据是 `struct file`，不是 inode（本节 ④） |
| 7 | 以为 `/proc/self/fd/N` 的存在意味着文件还在 | 尾巴带 `(deleted)` 说明 dentry 已被 unlink，只是这个 `struct file` 还抱着 inode |
| 8 | 拿 `fcntl(F_GETFL)` 的返回当权限判断 | `F_GETFL` 只回**状态标志**（`O_RDONLY`=0、`O_LARGEFILE`、`O_APPEND`…）。实测 `0x8000` = `O_LARGEFILE`，**读权限表现为 0**，不是「没标志」 |
| 9 | 以为 VFS 会缓存 read/write 的内容 | 内容缓存是**页缓存**（Ch13），不是 VFS。VFS 只管「对象与分发」 |

## HFT / 嵌入式关联

| 场景 | 结论怎么用 |
|------|-----------|
| **共享偏移是 bug 来源** | 多处代码各自 `open` 同一个日志文件再写，会因为各自维护偏移而互相覆盖。要么共享 fd（`dup`/继承），要么用 `O_APPEND` 让内核保证「写在尾」 |
| **预热 = 把 dcache/inode 打热** | 冷路径 `open()` 要逐级 lookup，可能触发元数据 I/O。开盘前对关键文件做一遍 `stat`/`open` 能把这部分开销挪出关键路径 |
| **`dup` 的语义决定了 fd 传递** | `SCM_RIGHTS` 传递 fd 时，接收进程拿到的是**同一个 `struct file`** —— 偏移共享、`O_APPEND` 共享。分布式的「日志接力」写法必须知道这一点 |
| **`O_LARGEFILE` 的真相** | x86-64 上 `off_t` 本来就是 64 位，`O_LARGEFILE` 是 no-op（本机实测 `F_GETFL = 0x8000` 只有它一个位）。嵌入式 32 位 ARM 上它才是真的（不做就限制 2 GiB） |
| **`/proc/self/fd` 是排查「谁攥着旧文件」的入口** | 磁盘不释放的经典故障，扫一遍 `/proc/*/fd` 找 `(deleted)` 就定位了（§14.4 的 `nlink=0` 现象） |
| **dcache 是可丢弃的** | 嵌入式内存紧张时 `echo 2 > /proc/sys/vm/drop_caches` 会扔掉 dentry+inode 缓存（`echo 3` 连页缓存一起扔）。扔掉之后性能回落是**预期行为**，不是内核坏了 |

<summary>代码自测（Q&A）</summary>

**Q1：VFS 四对象里哪一个磁盘上并不存在？**

A：**dentry**。磁盘上目录数据块里存的是 `(文件名, inode号)` 的列表；`struct dentry` 是内核读目录后在内存里造出来放进 dcache 的加速结构。所以清 dcache（`echo 2 > /proc/sys/vm/drop_caches`）**不改磁盘上任何数据**，只是让下次 lookup 变慢。

**Q2：两次 `open()` 同一路径，偏移为什么不共享？**

A：因为每次 `open()` 都会新建一个 `struct file`，而**文件偏移存在 `struct file` 里**（`f_pos`），不在 inode 里。本节 ② 的实测：`fd1` 读 3 字节后偏移 3，`fd2` 仍是 0。

**Q3：`dup()` 之后 `close(fd1)`，`fd2` 还能用吗？为什么？**

A：能。`dup()` 让 fd 表的两格指向**同一个 `struct file`**，并把它的引用计数 +1。`close(fd1)` 只把计数 -1（同时释放 fd 表那一格），对象本身还在，`fd2` 照常工作。这也解释了为什么 `dup` 出来的两个 fd 偏移共享。

**Q4：怎么用用户态 API 区分「同一个 `struct file`」和「同一个 inode」？**

A：看**偏移会不会一起动**。`open` 两次 → 偏移各自独立（两个 `struct file`）；`dup` → 偏移一起动（一个 `struct file`）。再把 `fstat(fd).st_ino` 拿出来比，就能把「同一 inode 不同 `struct file`」（两个硬链接）也分开 —— 本节 ②③④ 三段正好是这三组对照。

**Q5：`fcntl(F_GETFL)` 返回 `0x8000` 是什么？为什么不是 `O_RDONLY`？**

A：`0x8000` 是 `O_LARGEFILE`。而 `O_RDONLY` 的值是 **`0`**（`O_WRONLY`=1、`O_RDWR`=2），所以「只读」在 flags 里表现为**没有位**。看 `F_GETFL` 不能按「有没有 1」判断，必须先 `& O_ACCMODE`。

**Q6：`(deleted)` 后缀是谁加的？**

A：内核 `d_path()` 在把一个 dentry 转成路径字符串（`readlink /proc/self/fd/N` 走的就是它）时，如果发现 dentry 已被 unlink，就在末尾加 ` (deleted)`。它只是**显示层的标记**，说明这个对象正处在「没有名字但还有引用」的状态（§14.4 的 `nlink=0`）。

**Q7：VFS 这层抽象在性能上「贵」在哪？**

A：主要是**路径解析**（逐级 lookup，`fs/namei.c`）与**每层的函数指针间接调用**（`file_operations`/`inode_operations`）。dcache 命中时解析基本免费；不命中要走文件系统的 `lookup`，可能读磁盘。这也是 `openat2()`（带 `RESOLVE_*` 限制解析范围）与长期持有 fd 这两种优化存在的原因。

</details>
