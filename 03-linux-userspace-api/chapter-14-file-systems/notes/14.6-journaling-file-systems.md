## 本节讲什么

「日志文件系统」这四个字最容易被误解成「写了就不会丢」。这一节钉三件事：

1. **日志（journal）保护的是「文件系统结构的一致性」，不是「你的数据不丢」**。崩溃后不必全盘 `fsck`，靠的是日志重放；你 `write()` 过但没 `fsync()` 的那几百字节，**日志不负责**。
2. **jbd2 是可观测的**：`/proc/fs/jbd2/<dev>-<n>/info` 里有一个累计事务计数，能看到「一次 `fsync` 让计数 +1」。
3. **一个极容易忘的硬事实**：ext4 **数据区是小端、日志区（jbd2）是大端**。同一个文件系统内部字节序相反。

---

## 1. 日志要解决什么问题

ext2 的做法是「就地改元数据」。考虑「创建一个文件」这件事在磁盘上要动的位置：

| 要动的地方 | 改什么 |
|-----------|--------|
| 块位图 | 标一个 inode 已用 |
| inode 表 | 写一条 inode |
| 目录数据块 | 加一条目录项 |
| 超级块 | 空闲计数器 +1 |

这四处**必须一起生效**。如果在改到一半时掉电，磁盘上就是「位图说这个 inode 用了，但目录里没这个名字」这种**自相矛盾**的状态。ext2 的出路是 `fsck` 全盘扫描 —— 卷越大越慢（TLPI 里说得很直白：大盘上 `fsck` 要几十分钟到几小时）。

解决的思路是**先写意图、再改现场**（write-ahead logging）：

| 阶段 | 做什么 |
|------|--------|
| 1 | 把「这次要改哪些元数据块」写进日志区 |
| 2 | 日志写完后打一个 **commit record** —— 这一刻算「事务提交」 |
| 3 | 把元数据块真正写到最终位置（checkpoint） |
| 4 | 之后这批日志可以重用 |

掉电后：日志里有 commit record → **重放**（把日志里的块写到最终位置）；没有 commit record → **丢弃**。两种情况磁盘上的文件系统结构都自洽，**不必全盘 `fsck`**。

## 2. jbd2 的运行时窗口

`/proc/fs/jbd2/<dev>-<n>/info` 就是这个日志层暴露出来的状态（`fs/jbd2/journal.c` 里用 `proc_create_single` 挂的）：

<!--OUT:c14_6_journaling|after=① /proc/fs/jbd2,until=② 写文件-->

```text
  > /proc/fs/jbd2：
    xvda1-8
    xvda16-8
  > 第一个 jbd2 实例：xvda1-8
  --- /proc/fs/jbd2/xvda1-8/info ---
  590 transactions (590 requested), each up to 5461 blocks
  average: 
    0ms waiting for transaction
    0ms request delay
    8128ms running transaction
    0ms transaction was being locked
    0ms flushing data (in ordered mode)
    3ms logging transaction
    2879us average transaction commit time
    2279 handles per transaction
    99 blocks per transaction
    102 logged blocks per transaction
  ↑ 两条容易忘的硬事实（v6.6 Documentation/filesystems/ext4/overview.rst:15-17）：
      "All fields in ext4 are written to disk in little-endian order.
       HOWEVER, all fields in jbd2 (the journal) are written to disk in
       big-endian order." —— 同一个文件系统，数据区与日志区**字节序相反**。
    另外：首行那个 N 是**整机累计**事务数，只能看增量方向（见 ②）。
```

逐行读：

| 行 | 含义 |
|----|------|
| `N transactions (N requested), each up to 5461 blocks` | **累计**已完成事务数。`5461` 是**每批事务的块数上限**（`JBD2_DEFAULT_MAX_COMMIT_AGE` 之外的另一半：`journal->j_max_transaction_buffers`） |
| `Nms running transaction` | 事务被打开的时长（等待新的 handle 加入） |
| `Nms flushing data (in ordered mode)` | **ordered 模式**下「先把数据写出去」所花的时间 —— 这一行只在这个模式下有 |
| `Nus average transaction commit time` | 提交（写日志 + 等落地）的平均耗时。**这就是 `fsync()` 延迟的主要成分** |
| `N handles per transaction` | 每批事务平均多少 handle（一个 handle ≈ 一次「我要改元数据」的申请） |
| `N blocks per transaction` / `N logged blocks per transaction` | 每批事务的平均块数 / 其中进日志的块数 |

> ⚠️ **`info` 的首行是「整机累计」值**，宿主上所有进程、所有文件系统的活动都算在里面（`/proc/fs/jbd2/<dev>-<n>` 是按**这一个实例**统计的，但计数在整个实例的生命周期里只增不减）。所以**只能看增量方向，不能看绝对值**。

## 3. 实测：一次 `fsync` 让事务计数 +1

② 段做了一个最小实验：写 4096 字节，然后在「未 `fsync`」和「`fsync` 之后」分别读一次计数。

<!--OUT:c14_6_journaling|after=② 写文件,until=③ 日志保护-->

```text
  info 的首行（计数的出处）：590 transactions (590 requested), each up to 5461 blocks
  写之前   transactions = 590
  write(4096 字节) 后（未 fsync）transactions = 590
  fsync 返回 0（元数据已经过日志落盘）
  fsync 之后 transactions = 591   （比未 fsync 时 +1）
  第二次 close 后 transactions = 592   （比写之前 +2）
  ↑ 该计数是**整机（宿主）累计值**，只能看增量方向，不能当绝对量。
```

读数（**只看增量，不看绝对值**）：

| 时刻 | 计数 | 增量 |
|------|------|------|
| 写之前 | 590 | — |
| `write(4096)` 之后（未 `fsync`） | 590 | **+0** |
| `fsync()` 返回 0 之后 | 591 | **+1** |
| 第二次 `close()` 之后 | 592 | **+1** |

三条结论：

1. **`write()` 本身不产生事务** —— 它只是往页缓存里拷贝。这一点和 Ch13 的结论完全一致。
2. **`fsync()` 会让计数 +1** —— 它把「这次写」对应的元数据（`i_size`、mtime、块位图、extent 树）打包进一个 jbd2 事务提交。这就是 `fsync()` 的延迟来源：**写日志 + 等日志落盘**。
3. **`close()` 也可能 +1** —— ext4 在「最后一个引用关闭」时会做一次 flush（把 `O_CREAT` 这类延迟的元数据操作落下去）。

> ⚠️ 数字本身**会随宿主变化**（本轮的 `590` 在上一轮是 `348`、再上一轮是 `349/350`）。**只有「+1 / +0」这种增量方向是常数**，绝对值不要写进任何断言。

## 4. 日志不保证什么

③ 段的输出把边界一句话说清了：

<!--OUT:c14_6_journaling|after=③ 日志保护-->

```text
  /app 是 ext4（f_type=0xef53）；② 里那个 /proc/fs/jbd2/<dev>-<n>/
  就是**这一个实例**的日志层 —— 有没有日志，看那一栏在不在，
  别只看文件系统类型（ext4 也可以用 mke2fs -O ^has_journal 造出
  没有日志的实例，那种连 /proc/fs/jbd2 下都不会出现）。
  但日志只能保证：崩溃后**文件系统结构**仍自洽（不必全盘 fsck）。
  它不保证：你 write() 过、但没 fsync() 的那几百字节还在。
  → 要「数据落盘」必须显式 fsync/fdatasync（见 Ch13 §13.3）。

=== c14_6 done ===
```

**日志保证**：崩溃后文件系统的**结构**自洽（位图、inode 表、目录条目、超级块计数器互相不矛盾），不必全盘 `fsck`。

**日志不保证**：

- 你 `write()` 过但没有 `fsync()` 的**数据**还在。它可能只存在于页缓存里，机器一掉电就没了。
- 你已经 `fsync()` 了**数据**但没 `fsync()` **目录**时，新建的文件名还在。这是「文件内容在、名字不见了」的经典场景（`fsync` 目录才能保证目录项落盘）。

> 关于「数据 vs 元数据」的三种模式，TLPI 讲的是 ext3 时代的三档：

| 模式 | 日志里记什么 | 保证 | 代价 |
|------|-------------|------|------|
| `journal` | 元数据 **+ 数据**都进日志 | 最稳 | 数据写两遍，最慢 |
| `ordered`（ext4 默认） | 只记元数据，但**先写数据、再提交元数据事务** | 不会出现「元数据指向未初始化块」 | 中 |
| `writeback` | 只记元数据，数据顺序不管 | 最快 | 崩溃后可能读到**旧数据**或**垃圾数据** |

`ordered` 之所以是默认：它避免了「分配了块、块里还是上一个文件的残留内容」这种**信息泄露**（安全）与**数据错乱**（正确性），代价比 `journal` 小得多。

## 5. 两条容易忘的硬事实

### 5.1 ext4 数据区小端、jbd2 日志区大端

v6.6 自带的 `Documentation/filesystems/ext4/overview.rst:15-17` 逐字：

> All fields in ext4 are written to disk in little-endian order. HOWEVER, all fields in jbd2 (the journal) are written to disk in big-endian order.

也就是说：**同一个文件系统，数据区与日志区的字节序相反**。这不是笔误 —— jbd2 的磁盘格式沿用了它自己的历史（从 ext3 的 jbd 继承），改不动。写「读日志的工具」时必须按大端解析，否则字段全是乱的。

### 5.2 「ext4 一定有日志」是错的

日志是**可选的特性位**：

- `mke2fs -O ^has_journal` 能造出**没有日志的 ext4**（这时连 `/proc/fs/jbd2/` 下都不会出现它）。
- 判断「这个实例有没有日志」，**看 `/proc/fs/jbd2/<dev>-<n>/` 在不在**，而不是看 `f_type == 0xef53`。程序 ③ 段特意把这句话打出来了。

## 完整源码

完整源码 [`code/c14_6_journaling.c`](../code/c14_6_journaling.c)：

```c
/* c14_6_journaling.c —— TLPI §14.6 Journaling File Systems
 *
 *  §14.6 讲「日志文件系统为什么能免 fsck」：先把**元数据更新**写进一块
 *  循环使用的日志区（journal），落盘成功后再写回家（checkpoint），
 *  崩溃后只要重放日志尾部即可回到一致状态。
 *
 *  这一节的书上内容大量依赖 ext3 的时代背景，但**可观测的入口在今天还在**：
 *      /proc/fs/jbd2/<dev>-<n>/   ← ext4 的日志层（jbd2 = journal block device 2）
 *      /proc/fs/ext4/<dev>/       ← ext4 本体
 *
 *  本 demo 做三件事：
 *    ① 把 jbd2 暴露的文件列出来，读它的 info（提交/事务计数）
 *    ② 在 ext4 上做一次「写 → 不 fsync → 再写 → fsync」，观察事务计数怎么走
 *    ③ 用 statfs 的差异说明「日志保护的是元数据，不是用户数据」
 *
 *  ⚠️ 诚实标注：本容器**没有** `mount -o data=journal|ordered|writeback` 的权限
 *    （缺 CAP_SYS_ADMIN），所以「三种日志模式」只能讲机制、不能在本机对比实测；
 *    /proc/fs/ext4/<dev>/ 里的 `journal_*` 参数能间接证明当前用的是写回模式。
 *
 *  编译：gcc -O0 -Wall -Wextra -o c14_6 c14_6_journaling.c
 */
#define _GNU_SOURCE
#include <sys/statfs.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <dirent.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void sec(const char *t)
{
    printf("\n== %s ==\n", t);
}

/* 取目录里第一个非 . 条目名 */
static int first_entry(const char *path, char *out, size_t cap)
{
    DIR *d = opendir(path);
    struct dirent *e;

    out[0] = '\0';
    if (d == NULL)
        return -1;
    while ((e = readdir(d)) != NULL) {
        if (e->d_name[0] == '.' &&
            (e->d_name[1] == '\0' || (e->d_name[1] == '.' && e->d_name[2] == '\0')))
            continue;
        snprintf(out, cap, "%s", e->d_name);
        break;
    }
    closedir(d);
    return out[0] == '\0' ? -1 : 0;
}

static void list_dir(const char *path, int maxn)
{
    DIR *d = opendir(path);
    struct dirent *e;
    int n = 0;

    if (d == NULL) {
        printf("  opendir(%s) -> errno=%d (%s)\n", path, errno, strerror(errno));
        return;
    }
    printf("  > %s：\n", path);
    while ((e = readdir(d)) != NULL && n < maxn) {
        if (e->d_name[0] == '.' &&
            (e->d_name[1] == '\0' || (e->d_name[1] == '.' && e->d_name[2] == '\0')))
            continue;
        printf("    %s\n", e->d_name);
        n++;
    }
    closedir(d);
}

/* jbd2 的 info 文件的**首行**形如：
 *     2623 transactions (2623 requested), each up to 5461 blocks
 * 也就是说**没有 `Transactions:` 这样的 key** —— 计数就是首行的第一个整数。
 * 所以取数函数必须「读首行、取第一个整数」，不能按 key 找行。
 * 返回 -1 表示打不开或首行不是那个格式。 */
static long long jbd2_txn_count(const char *file, char *firstline, size_t nfl)
{
    FILE *fp = fopen(file, "r");
    char line[512];
    long long v = -1;

    if (firstline != NULL && nfl > 0)
        firstline[0] = '\0';
    if (fp == NULL)
        return -1;
    if (fgets(line, sizeof(line), fp) != NULL) {
        if (firstline != NULL && nfl > 0)
            snprintf(firstline, nfl, "%s", line);
        if (sscanf(line, "%lld", &v) != 1)
            v = -1;
    }
    fclose(fp);
    return v;
}

int main(void)
{
    char jdev[128] = {0};
    char jinfo[512] = {0};

    /* ---------- ① jbd2 的运行时接口 ---------- */
    sec("① /proc/fs/jbd2/<dev>/：ext4 的日志层");
    list_dir("/proc/fs/jbd2", 8);
    if (first_entry("/proc/fs/jbd2", jdev, sizeof(jdev)) == 0) {
        printf("  > 第一个 jbd2 实例：%s\n", jdev);
        snprintf(jinfo, sizeof(jinfo), "/proc/fs/jbd2/%s/info", jdev);

        FILE *fp = fopen(jinfo, "r");
        if (fp != NULL) {
            char line[512];
            int n = 0;
            printf("  --- %s ---\n", jinfo);
            while (fgets(line, sizeof(line), fp) != NULL && n < 24) {
                size_t len = strlen(line);
                if (len > 0 && line[len - 1] == '\n')
                    line[len - 1] = '\0';
                printf("  %s\n", line);
                n++;
            }
            fclose(fp);
        } else {
            printf("  打不开 %s（errno=%d）\n", jinfo, errno);
        }
    }

    printf("  ↑ 两条容易忘的硬事实（v6.6 Documentation/filesystems/ext4/overview.rst:15-17）：\n"
           "      \"All fields in ext4 are written to disk in little-endian order.\n"
           "       HOWEVER, all fields in jbd2 (the journal) are written to disk in\n"
           "       big-endian order.\" —— 同一个文件系统，数据区与日志区**字节序相反**。\n"
           "    另外：首行那个 N 是**整机累计**事务数，只能看增量方向（见 ②）。\n");

    /* ---------- ② 写文件时事务计数怎么走 ---------- */
    sec("② 写文件 → 观察 jbd2 的事务计数");
    if (jinfo[0] != '\0') {
        long long t0, t1, t2;
        int fd;
        char buf[4096];
        char first[512];

        t0 = jbd2_txn_count(jinfo, first, sizeof(first));
        printf("  info 的首行（计数的出处）：%s", first);
        printf("  写之前   transactions = %lld\n", t0);

        memset(buf, 'J', sizeof(buf));
        fd = open("/app/c14_6_journal", O_WRONLY | O_CREAT | O_TRUNC, 0644);
        if (fd == -1) {
            printf("  open errno=%d (%s)\n", errno, strerror(errno));
        } else {
            ssize_t n = write(fd, buf, sizeof(buf));
            t1 = jbd2_txn_count(jinfo, NULL, 0);
            printf("  write(%zd 字节) 后（未 fsync）transactions = %lld\n", n, t1);

            if (fsync(fd) == -1)
                printf("  fsync -> -1 errno=%d (%s)\n", errno, strerror(errno));
            else
                printf("  fsync 返回 0（元数据已经过日志落盘）\n");

            t2 = jbd2_txn_count(jinfo, NULL, 0);
            printf("  fsync 之后 transactions = %lld   （比未 fsync 时 %+lld）\n",
                   t2, t2 - t1);

            n = write(fd, buf, sizeof(buf));
            if (fsync(fd) == -1)
                printf("  第二次 write(%zd) + fsync -> -1 errno=%d\n", n, errno);
            close(fd);
            printf("  第二次 close 后 transactions = %lld   （比写之前 %+lld）\n",
                   jbd2_txn_count(jinfo, NULL, 0), jbd2_txn_count(jinfo, NULL, 0) - t0);
            unlink("/app/c14_6_journal");
        }
        printf("  ↑ 该计数是**整机（宿主）累计值**，只能看增量方向，不能当绝对量。\n");
    }

    /* ---------- ③ 日志护的是元数据 ---------- */
    sec("③ 日志保护「元数据一致性」，不是「用户数据不丢」");
    {
        struct statfs sfs;
        if (statfs("/app", &sfs) == 0) {
            printf("  /app 是 ext4（f_type=%#lx）；② 里那个 /proc/fs/jbd2/<dev>-<n>/\n",
                   (unsigned long) sfs.f_type);
            printf("  就是**这一个实例**的日志层 —— 有没有日志，看那一栏在不在，\n"
                   "  别只看文件系统类型（ext4 也可以用 mke2fs -O ^has_journal 造出\n"
                   "  没有日志的实例，那种连 /proc/fs/jbd2 下都不会出现）。\n");
            printf("  但日志只能保证：崩溃后**文件系统结构**仍自洽（不必全盘 fsck）。\n");
            printf("  它不保证：你 write() 过、但没 fsync() 的那几百字节还在。\n");
            printf("  → 要「数据落盘」必须显式 fsync/fdatasync（见 Ch13 §13.3）。\n");
        }
    }

    printf("\n=== c14_6 done ===\n");
    return 0;
}
```

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 以为「有日志」=「写了不会丢」 | 日志保**结构一致**，不保**你的数据**。要数据必须 `fsync`/`fdatasync` |
| 2 | 以为 `write()` 返回就产生事务 | `write` 只进页缓存；本节实测「未 `fsync` 时计数 +0」 |
| 3 | 把 `/proc/fs/jbd2/*/info` 的绝对值当断言 | 它是**整机累计**值，随宿主变化（本轮 590、上一轮 348）。**只看增量方向** |
| 4 | 以为 `fsync(fd)` 之后文件名就安全了 | 新建文件的**目录项**要靠 `fsync` **目录**（`open(dir, O_RDONLY)` + `fsync`）才能保证 |
| 5 | 以为 ext4 必然有日志 | `mke2fs -O ^has_journal` 可以没有。判据是 `/proc/fs/jbd2/<dev>-<n>/` 在不在 |
| 6 | 按小端去解析 jbd2 的磁盘结构 | **日志区是大端**（`ext4/overview.rst:15-17`）。数据区才是小端 |
| 7 | 以为 `writeback` 模式和 `ordered` 的差别只是性能 | `writeback` 崩溃后可能读到**未初始化/残留**的块内容（信息泄露风险）。这也是 `ordered` 成为默认的安全理由 |
| 8 | 以为 `data=journal` 最快（「都在日志里，顺序写」） | 数据要写两遍（日志 + 最终位置），是最慢的一档。它赢在一致性，不赢在吞吐 |
| 9 | 以为 `jbd2` 是「第 2 代」 | 名字来自 ext3 的 `jbd`（Journaling Block Device）；`2` 表示这套代码在 ext4 时代被重写过，与「两个日志」无关 |
| 10 | 混淆内核日志（jbd2）与 HFT 的「日志盘」 | 前者是**同一文件系统内部**的事务日志（靠 `fsync` 语义）；后者通常是**另一个文件系统**（靠 `st_dev` 不同，§14.2） |

## HFT / 嵌入式关联

| 场景 | 结论怎么用 |
|------|-----------|
| **`fsync()` 延迟 = 提交一笔 jbd2 事务** | `info` 里的 `average transaction commit time` 就是这条路径的实测口径。调优「落盘延迟」应当从**合并事务**（一次 `fsync` 带更多数据）入手，而不是减少 `fsync` 次数（次数减少就丢一致性） |
| **批量落盘的正确形态** | 一个 `write` 循环 + **一次** `fsync`：N 条消息进同一个事务，平摊提交成本。逐条 `fsync` 是最贵的写法 |
| **ext4 上「数据落盘」的完整顺序** | `write` → **`fsync(文件)`** → `fsync(目录)`（新建/改名时）。少了第三步，崩溃后可能「数据在、名字没了」 |
| **嵌入式掉电与只读 rootfs** | 只读 rootfs 不受日志影响（没写就没事务）。可写分区若是 eMMC，`data=ordered` + 定期 `sync` 是常见折中；极端可靠场景要上 `data=journal` 或干脆用带掉电保护的数据结构（如直接写裸分区 + 校验） |
| **writeback 模式的隐性风险** | 产品上如果为了吞吐把 ext4 改成 `data=writeback`，崩溃后可能读到残留数据 —— 对含密钥/凭据的嵌入式设备是**信息泄露**，不只是数据错乱 |
| **日志区在裸设备上** | `mke2fs -J device=/dev/sdX` 可以把日志放到**另一个设备**上（独立盘/独立 flash 分区）。这是「元数据抖动不污染数据盘」的做法，也是 HFT 落盘盘常见的配置 |
| **观测口径** | `/proc/fs/jbd2/<dev>-<n>/info` 是**只读、零成本**的诊断入口。容器/嵌入式上没有 `iotop`/`blktrace` 时，靠它能判断「延迟是提交慢还是等待长」（比较 `running transaction` 与 `commit time`） |

<summary>代码自测（Q&A）</summary>

**Q1：为什么「有日志」不等于「数据不会丢」？**

A：日志记录的是**元数据块的改动意图**（`ordered`/`writeback` 模式）或元数据+数据（`journal` 模式）。掉电后重放日志能让文件系统**结构**自洽，但「你 `write()` 过、还没 `fsync()`」的数据可能只存在于页缓存。所以「日志」与「数据持久性」是两件事，后者要显式 `fsync`。

**Q2：为什么 `write()` 之后事务计数不变，`fsync()` 之后 +1？**

A：因为 `write()` 只把数据拷进**页缓存**并把 inode 标脏，不产生任何需要写日志的元数据变更。`fsync()` 强制把脏页与相关元数据（`i_size`、mtime、块分配位图、extent 树）打包成一个 jbd2 事务提交 —— 这就是 +1 的来源。

**Q3：`close()` 为什么也可能让计数 +1？**

A：ext4 在「最后一个引用关闭」时会做一次 flush：把该次打开期间**延迟的元数据操作**（比如 `O_CREAT` 的目录项/位图更新）真正提交。所以 close 也可能产生一个事务。注意这不是 POSIX 保证，而是 ext4 的实现行为 —— 所以**不能把 `close()` 当 `fsync()` 用**。

**Q4：ext4 的默认日志模式是什么？为什么？**

A：`ordered`。它只把元数据写进日志，但**强制数据先于元数据落盘**。这样崩溃后不会出现「元数据（extent/块指针）指向还没写过的块」——那种情况会让用户读到**上一个文件残留的内容**（既错又可能泄露信息）。`journal` 最稳但数据写两遍，`writeback` 最快但有上述风险。

**Q5：ext4 和 jbd2 的字节序为什么不一样？**

A：`Documentation/filesystems/ext4/overview.rst:15-17` 明确写了：ext4 的字段一律**小端**，但 jbd2（日志）的字段一律**大端**。原因是 jbd2 的磁盘格式继承了 ext3 `jbd` 的历史定义，为了不破坏已有卷的兼容性保持原样。所以读 jbd2 的日志头必须按大端解析。

**Q6：怎么判断一个 ext4 实例有没有日志？**

A：看 `/proc/fs/jbd2/<dev>-<n>/` 这个目录在不在。日志是**可选特性位**（`has_journal`），`mke2fs -O ^has_journal` 造出来的 ext4 没有日志，`/proc/fs/jbd2` 下不会出现它。程序 ③ 段输出里就写了这句话。

**Q7：`info` 首行的 `each up to 5461 blocks` 是什么意思？**

A：是**单个事务能包含的最大块数**（`journal->j_max_transaction_buffers`）。内核会把一段时间内累积的元数据改动合并进一个事务，但不会无限合并 —— 上限就是为了控制「一笔事务的提交最坏要写多少数据」以及恢复时重放的工作量。
