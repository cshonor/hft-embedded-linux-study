## 本节讲什么

TLPI 把 `statvfs()` 作为「可移植的」文件系统信息 API 介绍。这一节要钉一件**容易讲错的核心事实**：

> **`statvfs()` 在 Linux/glibc 上不是系统调用，而是 `statfs()` 的一层包装。** 一次 `statvfs()` 全程只有 **一次**进入内核。

由此推出四条能观察到、也能用源码证实的结论：

1. **`statvfs` 能给你的信息不会多于 `statfs`**，反而在某些字段上更窄（`f_type` 是 `unsigned int`）。
2. **`statvfs.f_flag` 与 `statfs.f_flags` 差一个 `0x20` 位**，而且是**异或**掉的，不是过滤掉的。
3. **`f_favail` 在 Linux 上是假的** —— glibc 直接照抄 `f_ffree`，它的源码里还留着 `/* XXX I have no idea how to compute f_favail.  Any idea???  */`。
4. **`f_frsize ?: f_bsize` 的回退分支在本机不可达**（v6.6 的内核一律填 `f_frsize`），所以这一支**只能讲、不能观测**。

## 1. glibc 的包装链：从 `statvfs()` 到 `statfs()`

glibc 2.39 的 `sysdeps/unix/sysv/linux/statvfs64.c`（关键行）：

```c
int __statvfs64 (const char *file, struct statvfs64 *buf)          /* :28 */
{
  struct statfs64 fsbuf;

  if (__statfs64 (file, &fsbuf) < 0)                                /* :32 */
    return -1;

  __internal_statvfs64 (buf, &fsbuf);      /* 纯字段搬运，不再进内核 */  /* :36 */
  return 0;                                                         /* :38 */
}
weak_alias (__statvfs64, statvfs64)                                 /* :40 */
#if STATFS_IS_STATFS64                                              /* :45 */
weak_alias (__statvfs64, __statvfs)                                 /* :46 */
weak_alias (__statvfs64, statvfs)         /* x86-64 上 statvfs 就是别名 */  /* :47 */
#endif
```

x86-64 上 `STATFS_IS_STATFS64` 为真，所以**`statvfs` 就是 `__statvfs64` 的一个弱别名**（连包装函数层的调用都省掉了）。`statvfs.c` 里另有一段 `#if !STATFS_IS_STATFS64` 的 32 位版本（`__statvfs` → `__statfs` + `__internal_statvfs`）。

`internal_statvfs.c` 里的字段映射（`*64` 版在 `:75-102`，非 64 版在 `:33-68`，两段逐行相同）：

```c
#define ST_VALID 0x0020                                  /* :26，glibc 内部位值 */
buf->f_frsize = fsbuf->f_frsize ?: fsbuf->f_bsize;        /* :36/:79 老内核补丁 */
buf->f_fsid   = ((fsbuf->f_fsid.__val[0] & 0xffffffff)
              | ((unsigned long long)fsbuf->f_fsid.__val[1] << 32));  /* :47-51/:90-94 */
buf->f_namemax= fsbuf->f_namelen;                         /* :59/:102 */
buf->f_type   = fsbuf->f_type;   /* :60 —— glibc 扩展，POSIX 没有 */
/* XXX I have no idea how to compute f_favail.  Any idea???  */   /* :65 */
buf->f_favail = buf->f_ffree;                             /* :66/:109 */
buf->f_flag   = fsbuf->f_flags ^ ST_VALID;                /* :68 **异或**，不是过滤 */
```

而内核侧 `fs/statfs.c` 的 `calculate_f_flags()`（`:49-52`，调用于 `:92`）返回的是：

```c
	return ST_VALID | flags_by_mnt(mnt->mnt_flags) | ...;
```

**`ST_VALID` 的语义就是「本内核支持 `f_flags` 这个字段」**，glibc 用异或把它从结果里剔掉，好让 `f_flag` 里只剩真正的挂载标志。

## 2. 两个结构体的尺寸与偏移（x86-64 / glibc 2.39）

<!--OUT:c14_11_statvfs|after=① 两个结构体,until=② 同一条路径-->

```text
  sizeof(struct statfs)   = 120
  sizeof(struct statfs64) = 120   （x86-64 上与 statfs 同布局）
  sizeof(struct statvfs)  = 112
  sizeof(struct statvfs64)= 112   （x86-64 上与 statvfs 同布局）
  offsetof(statfs , f_type) = 0   offsetof(statfs , f_flags) = 80   offsetof(statfs , f_spare) = 88
  offsetof(statvfs, f_bsize)= 0   offsetof(statvfs, f_flag)  = 72   offsetof(statvfs, f_type)  = 88
  ↑ 两个结构体都是「11 个 8 字节字段 = 88 字节」打头，后面各自留尾巴：
    statfs  = 88 + f_spare[4]×8 = 88 + 32 = 120
    statvfs = 88 + f_type(4) + __f_spare[5]×4 = 88 + 4 + 20 = 112
    statvfs 的尾巴里那个 f_type 是 **glibc 扩展**（POSIX 没有），
    而 statfs 的 f_flags 在 statvfs 里叫 f_flag（少一个 s）—— 两个名字都要记。
```

| 结构体 | 大小 | 布局 |
|--------|------|------|
| `struct statfs` / `statfs64` | **120** | 11 个 8 字节字段（88 字节）+ `f_spare[4]` × 8 = **120** |
| `struct statvfs` / `statvfs64` | **112** | 11 个 8 字节字段（88 字节）+ `f_type`(4) + `__f_spare[5]`(20) = **112** |

三个容易记错的名字：

| `statfs` 里的名字 | `statvfs` 里的名字 | 备注 |
|------------------|-------------------|------|
| `f_flags` | **`f_flag`** | **少一个 `s`** |
| `f_namelen` | **`f_namemax`** | 语义相同 |
| （没有） | `f_type` | **glibc 扩展**，POSIX 里没有 |

> `bits/statvfs.h` 里 `f_fsid` 是 `unsigned long int`（:48）、`f_flag` 是 `unsigned long int`（:52）、`f_type` 是 `unsigned int`（:54）。**`statvfs` 确实有 `f_type`** —— 「`f_type` 只有 `statfs` 有」这种说法是错的（本仓库旧笔记里就有这个错误，此处纠正）。

## 4. `f_flag` 逐位分解：与 `mountinfo` 的 per-mount 选项对账

<!--OUT:c14_11_statvfs|after=③ f_flag,until=④ 实证-->

```text
  [/]
    statvfs.f_flag                = 0x1001
    拆成 ST_* 名字                = ST_RDONLY|ST_RELATIME
    mountinfo 的 per-mount options= ro,relatime
    ↑ 两者是**同一件事的两种写法**：ro ↔ ST_RDONLY 的**出现**，
      rw ↔ ST_RDONLY 的**缺席**；nosuid/nodev/noexec/relatime 一一对应。
      注意 mountinfo 里**没有**对应 ST_VALID 的选项 —— 它是 glibc 造出来的。

  [/app]
    statvfs.f_flag                = 0x1000
    拆成 ST_* 名字                = ST_RELATIME
    mountinfo 的 per-mount options= rw,relatime
    ↑ 两者是**同一件事的两种写法**：ro ↔ ST_RDONLY 的**出现**，
      rw ↔ ST_RDONLY 的**缺席**；nosuid/nodev/noexec/relatime 一一对应。
      注意 mountinfo 里**没有**对应 ST_VALID 的选项 —— 它是 glibc 造出来的。

  [/tmp]
    statvfs.f_flag                = 0x100e
    拆成 ST_* 名字                = ST_NOSUID|ST_NODEV|ST_NOEXEC|ST_RELATIME
    mountinfo 的 per-mount options= rw,nosuid,nodev,noexec,relatime
    ↑ 两者是**同一件事的两种写法**：ro ↔ ST_RDONLY 的**出现**，
      rw ↔ ST_RDONLY 的**缺席**；nosuid/nodev/noexec/relatime 一一对应。
      注意 mountinfo 里**没有**对应 ST_VALID 的选项 —— 它是 glibc 造出来的。
```

对账表（三个路径）：

| 路径 | `statvfs.f_flag` | 拆成 `ST_*` | `mountinfo` per-mount |
|------|------------------|------------|----------------------|
| `/` | `0x1001` | `ST_RDONLY\|ST_RELATIME` | `ro,relatime` |
| `/app` | `0x1000` | `ST_RELATIME` | `rw,relatime` |
| `/tmp` | `0x100e` | `ST_NOSUID\|ST_NODEV\|ST_NOEXEC\|ST_RELATIME` | `rw,nosuid,nodev,noexec,relatime` |

**两者是「同一件事的两种写法」**：

- `ro` ↔ `ST_RDONLY` 的**出现**；`rw` ↔ `ST_RDONLY` 的**缺席**（没有「ST_RW」这种东西）。
- `nosuid`/`nodev`/`noexec`/`relatime` 一一对应。
- **`mountinfo` 里没有对应 `ST_VALID` 的选项** —— 因为它不是挂载选项，是 glibc 的内部标记。

`bits/statvfs.h` 里的定义有个细节值得记：`ST_RDONLY = 1`（:84）与 `ST_NOSUID = 2`（:86）**不需要 `__USE_GNU` 就能用**；而 `ST_NODEV`（:90）起的 11 个要在 `__USE_GNU` 下才可见。`ST_NOSYMFOLLOW = 8192`（:110-111）也在其中。

## 5. 实证：`f_flag == statfs.f_flags ^ 0x20`

<!--OUT:c14_11_statvfs|after=④ 实证,until=⑤ f_favail-->

```text
  /      statfs.f_flags=0x1021   statvfs.f_flag=0x1001   异或=0x0020   f_flags ^ 0x20 == f_flag ? 是 ✔
  /app   statfs.f_flags=0x1020   statvfs.f_flag=0x1000   异或=0x0020   f_flags ^ 0x20 == f_flag ? 是 ✔
  /tmp   statfs.f_flags=0x102e   statvfs.f_flag=0x100e   异或=0x0020   f_flags ^ 0x20 == f_flag ? 是 ✔
  ↑ 内核在 f_flags 里放了 ST_VALID(0x0020) 这一位（来自 vfs_statfs() 里的
    calculate_f_flags()，见 fs/statfs.c），意思是「本内核支持 f_flags」。
    glibc 用**异或**把它去掉，于是 f_flag 里只剩下真正的挂载标志位。
    所以 statvfs 的 f_flag 永远**看不到 0x20 这一位** —— 不是内核没给，是被抹了。
```

三个路径全部满足，**异或的那个常数就是 `0x0020 = ST_VALID`**：

| 路径 | `statfs.f_flags` | `statvfs.f_flag` | 异或 |
|------|------------------|------------------|------|
| `/` | `0x1021` | `0x1001` | `0x0020` ✔ |
| `/app` | `0x1020` | `0x1000` | `0x0020` ✔ |
| `/tmp` | `0x102e` | `0x100e` | `0x0020` ✔ |

**推论**：`statvfs.f_flag` **永远看不到 `0x20` 这一位**。所以拿 `f_flag & ST_VALID` 去判断「内核支不支持 `f_flags`」是没意义的 —— 那一位已经被抹掉了。要判断内核支持度，应该用 `statfs` 的 `f_flags`。

## 6. `f_favail` 在 Linux 上是假的

<!--OUT:c14_11_statvfs|after=⑤ f_favail,until=⑥ f_frsize-->

```text
  /      f_ffree=1949354    f_favail=1949354    相等?是 ✔
  /app   f_ffree=1816190    f_favail=1816190    相等?是 ✔
  /tmp   f_ffree=99         f_favail=99         相等?是 ✔
  ↑ 内核的 statfs 结构里**根本没有 f_favail 这个字段**；
    glibc internal_statvfs.c:109 那两行自己写着：
      /* XXX I have no idea how to compute f_favail.  Any idea???  */
      buf->f_favail = buf->f_ffree;
    所以「非特权用户可用 inode 数」在 Linux 上是**假的** —— 它等于特权用户可用数。
    （对比：f_bavail 才是真的，它来自内核 statfs 的 f_bavail；
      ext4 上默认保留 5% 给 root，所以 f_bavail < f_bfree 是正常现象。）
```

`internal_statvfs.c:65` 那行注释是**上游源码里逐字存在的**：

```c
      /* XXX I have no idea how to compute f_favail.  Any idea???  */
      buf->f_favail = buf->f_ffree;
```

所以「非特权用户可用 inode 数」在 Linux 上==特权用户可用 inode 数。

**对比 `f_bavail` 是真的**：它来自内核 `statfs` 的 `f_bavail`（ext4 上默认保留 5% 给 root，所以 `f_bavail < f_bfree` 是正常现象）。本机 `/app` 的 `f_bavail = 2683405` 小于 `f_bfree = 2687501`，差值 `4096` 块 ≈ 16 MiB —— 就是那份保留。

| 字段 | Linux 上是否可信 | 原因 |
|------|-----------------|------|
| `f_bavail` | ✅ 真值 | 内核 `statfs` 直接给 |
| `f_favail` | ❌ 假的（= `f_ffree`） | glibc 承认不会算 |
| `f_frsize` | ✅（但回退分支不可达） | 见第 7 节 |
| `f_flag` | ✅（少一位 `0x20`） | glibc 异或掉了 `ST_VALID` |

## 7. `f_frsize ?: f_bsize` 的回退分支：本机不可达

<!--OUT:c14_11_statvfs|after=⑥ f_frsize,until=⑦ f_fsid-->

```text
  /      statfs.f_frsize=4096     statfs.f_bsize=4096     → 走的是 「取 f_frsize」那一支
  /app   statfs.f_frsize=4096     statfs.f_bsize=4096     → 走的是 「取 f_frsize」那一支
  /tmp   statfs.f_frsize=4096     statfs.f_bsize=4096     → 走的是 「取 f_frsize」那一支
  ↑ internal_statvfs.c 的 `buf->f_frsize = fsbuf->f_frsize ?: fsbuf->f_bsize;`
    是为「老内核不填 f_frsize」准备的补丁。本机内核 v6.6 一律填值，
    所以**回退那一支在本容器里观察不到** —— 只能说代码在那里，不能说它被走到。
```

`buf->f_frsize = fsbuf->f_frsize ?: fsbuf->f_bsize;`（`internal_statvfs.c:36/:79`）是给**老内核**准备的补丁 —— 那些内核的 `statfs` 结构里没有 `f_frsize`，或者填 0。

本机内核 v6.6 在 `statfs()` 里一律填 `f_frsize`（三个路径都是 `4096`），所以**「`f_frsize` 为 0 时取 `f_bsize`」这一支永远不会被走到**。

> 诚实标注：**代码在那里 ≠ 那一支被走过**。这一条只能讲源码，不能声称「实测验证过回退」。要实测得找一台老内核（< 2.6 之类的年代），本容器做不到。

## 8. `f_fsid` 是「两个 32 位半字」的重组

<!--OUT:c14_11_statvfs|after=⑦ f_fsid,until=⑧ 结论-->

```text
  /      statfs=(cf9cdff6,1c2535b2) → 拼起来=0x1c2535b2cf9cdff6   statvfs.f_fsid=0x1c2535b2cf9cdff6  一致 ✔
  /app   statfs=(f6569d42,e03f8c9f) → 拼起来=0xe03f8c9ff6569d42   statvfs.f_fsid=0xe03f8c9ff6569d42  一致 ✔
  /tmp   statfs=(4460ab04,3a5ed7e8) → 拼起来=0x3a5ed7e84460ab04   statvfs.f_fsid=0x3a5ed7e84460ab04  一致 ✔
  ↑ 所以 `statvfs.f_fsid` 与 `statfs.f_fsid.__val[]` 是**同一个数**，
    只是一个按 64 位整数看、一个按两个 32 位半字看。
```

`statfs.f_fsid` 是 `struct { int __val[2]; }`（两个 32 位半字），而 `statvfs.f_fsid` 是 `unsigned long`（64 位）。glibc 的拼法（`internal_statvfs.c:47-51`）：

```c
  buf->f_fsid = ((fsbuf->f_fsid.__val[0] & 0xffffffff)
                 | ((unsigned long long) fsbuf->f_fsid.__val[1] << 32));
```

即「**低 32 位放 `__val[0]`、高 32 位放 `__val[1]`**」。所以三者一致：`(f6569d42, e03f8c9f) → 0xe03f8c9ff6569d42`。

**注意 `f_fsid` 的坑**：它**不是** `st_dev`，也不保证跨机器唯一（它只是「这个超级块在这一次挂载里的随机标识」）。判断「是不是同一个文件系统实例」可以用它（§14.10 就是靠 `fsid` 认出 `/sys` 是 `/`）；但拿它做持久化标识会翻车。

## 9. 结论

<!--OUT:c14_11_statvfs|after=⑧ 结论-->

```text
  · statvfs() 全流程 = 一次 statfs**系统调用** + 一大段用户态字段搬运。
    没有第二个系统调用，也没有第二次进内核。
  · 所以 statvfs 能给你的信息**不会多于** statfs；反而少了 f_type 的宽度
    （statvfs 是 unsigned int，statfs 是 __fsword_t=long）。
  · 工程上：只用 Linux 就调 statfs()（字段更全、少一层包装）；
    要可移植才用 statvfs()（POSIX 标准接口，其他 Unix 也有）。
  · 反过来说：看到 f_flag 少一位、f_favail 与 f_ffree 相等，
    别怀疑内核 —— 那是 glibc 干的。

=== c14_11 done ===
```

工程建议一句话：**只用 Linux 就调 `statfs()`**（字段更全、少一层包装、`f_type` 更宽）；**要可移植才用 `statvfs()`**。看到 `f_flag` 少一位、`f_favail` 与 `f_ffree` 相等，**别怀疑内核 —— 那是 glibc 干的**。

### 10.3 从这六段输出里能读出什么

| 观察 | 结论 |
|------|------|
| `/proc` 的 `Total data blocks = 0`、`Total i-nodes = 0` | procfs **没有「容量」这个概念**。所以对伪文件系统问「还剩多少空间」是没有意义的 |
| `/proc` 的 `File system ID = 0x50, 0` | procfs 的 `fsid` 是**常量**（`0x50`），不是随机值 —— 它与「pid 命名空间」相关。对 `/` 那种 tmpfs 则是每次挂载随机生成 |
| `/tmp` 的 `Total i-nodes = 100` | 就是挂载选项 `nr_inodes=100`（§14.10 已对账） |
| `Flags 0x1001`（`/`）vs `0x1000`（`/app`） | 差的那一位是 `ST_RDONLY`。`/` 是从这个挂载点看是只读的，`/app` 可写（per-mount 选项，§14.9.3） |
| `Free blocks for unpriv. proc.` 在 `/proc` 上是 0 | 同上：procfs 没有容量概念 |

> ⚠️ **这六段输出不是同一次运行** —— `t_statfs_root` 与 `t_statvfs_root` 的 `Total blocks` 分别是 `1949384` 与 `2009890`，`File system ID` 也不同。CE 每个作业独立调度，可能落在不同宿主上。**所以同一张表里跨作业比较容量/ID 是无效的**（§14.2 的「环境会变」）。

完整源码 [`code/c14_11_statvfs.c`](../code/c14_11_statvfs.c)：

```c
/* c14_11_statvfs.c —— TLPI §14.11 Obtaining Information About a File System: statvfs()
 *
 *  ⭐ 本节最容易搞错的一件事：**statvfs() 不是系统调用**，它是 glibc 对 statfs() 的包装。
 *     源码坐标（glibc 2.39）：
 *       sysdeps/unix/sysv/linux/statvfs64.c:29-44
 *         __statvfs64() { struct statfs64 fsbuf;
 *                         if (__statfs64(file, &fsbuf) < 0) return -1;
 *                         __internal_statvfs64(buf, &fsbuf);   <-- 纯字段搬运
 *                         return 0; }
 *         并且文件末尾有：
 *           #if STATFS_IS_STATFS64
 *           weak_alias (__statvfs64, __statvfs)
 *           weak_alias (__statvfs64, statvfs)    <-- x86-64 上 statvfs 就是它的别名
 *           #endif
 *       sysdeps/unix/sysv/linux/internal_statvfs.c:73-112（*64 版）里只有 4 处**变换**，
 *       其余都是逐字段赋值。那 4 处就是本 demo 要逐条验的东西：
 *         f_frsize  = fsbuf.f_frsize ?: fsbuf.f_bsize   (36 行 / 79 行)
 *         f_fsid    = (val[0] & 0xffffffff) | (val[1] << 32)   (90-94 行)
 *         f_namemax = fsbuf.f_namelen                   (102 行)
 *         f_favail  = buf->f_ffree                      (109 行，上一行注释自认 "I have no idea"）
 *         f_flag    = fsbuf.f_flags ^ ST_VALID          (111 行，ST_VALID = 0x0020 见 26 行)
 *
 *  本 demo 分七段：
 *    ① 两个结构体的**尺寸与偏移**（为什么一个是 120、一个是 112）
 *    ② 同一条路径上 statfs() 与 statvfs() 并排打印，逐字段对照
 *    ③ f_flag 逐位分解，并与 /proc/self/mountinfo 的 per-mount options **对账**
 *    ④ 实证 f_flag == f_flags ^ 0x20（ST_VALID 被异或掉）
 *    ⑤ 实证 f_favail == f_ffree（glibc 照抄，不是内核给的）
 *    ⑥ f_frsize ?: f_bsize 这一支在本机**不可达**（两个 FS 都给了非 0 的 f_frsize）——诚实标注
 *    ⑦ f_fsid 是两个 32 位半字的**重组**
 *
 *  编译：gcc -O0 -Wall -Wextra -o c14_11 c14_11_statvfs.c
 */

struct fl {

static void sec(const char *t)
{
    printf("\n== %s ==\n", t);
}

/* 把 f_flag 拆成 "ST_RELATIME|ST_NOEXEC|..."；未知位另报 */
static void flags_str(unsigned long f, char *out, size_t n)
{
    size_t used = 0;

    out[0] = '\0';
    for (size_t i = 0; i < sizeof(FLAGS) / sizeof(FLAGS[0]); i++) {
        if ((f & FLAGS[i].bit) == 0)
            continue;
        if (used > 0 && used + 1 < n)
            out[used++] = '|';
        size_t L = strlen(FLAGS[i].name);
        if (used + L >= n)
            L = n - used - 1;
        memcpy(out + used, FLAGS[i].name, L);
        used += L;
        out[used] = '\0';
    }
    if (used == 0)
        snprintf(out, n, "(无)");
}

/* 取 /proc/self/mountinfo 里某挂载点的 per-mount options（第 6 个字段） */
static int mi_opts(const char *mp, char *out, size_t n)
{
    FILE *fp = fopen("/proc/self/mountinfo", "r");
    char line[MAXLINE];
    int found = -1;

    if (fp == NULL)
        return -1;
    while (fgets(line, sizeof(line), fp) != NULL) {
        char *tok[16];
        int nt = 0;
        char *p = line;
        size_t L = strlen(line);

        if (L > 0 && line[L - 1] == '\n')
            line[L - 1] = '\0';
        while (*p != '\0' && nt < 16) {
            while (*p == ' ')
                p++;
            if (*p == '\0')
                break;
            tok[nt++] = p;
            while (*p != '\0' && *p != ' ')
                p++;
            if (*p != '\0')
                *p++ = '\0';
        }
        if (nt < 6 || strcmp(tok[4], mp) != 0)
            continue;
        snprintf(out, n, "%s", tok[5]);
        found = 0;
        break;
    }
    fclose(fp);
    return found;
}

int main(void)
{
    static const char *PATHS[] = { "/", "/app", "/tmp", NULL };

    /* ---------- ① 尺寸与偏移 ---------- */

    printf("  sizeof(struct statfs)   = %zu\n", sizeof(struct statfs));
    printf("  sizeof(struct statfs64) = %zu   （x86-64 上与 statfs 同布局）\n",
           sizeof(struct statfs64));
    printf("  sizeof(struct statvfs)  = %zu\n", sizeof(struct statvfs));
    printf("  sizeof(struct statvfs64)= %zu   （x86-64 上与 statvfs 同布局）\n",
           sizeof(struct statvfs64));
    printf("  offsetof(statfs , f_type) = %zu   offsetof(statfs , f_flags) = %zu   offsetof(statfs , f_spare) = %zu\n",
           offsetof(struct statfs, f_type), offsetof(struct statfs, f_flags),
           offsetof(struct statfs, f_spare));
    printf("  offsetof(statvfs, f_bsize)= %zu   offsetof(statvfs, f_flag)  = %zu   offsetof(statvfs, f_type)  = %zu\n",
           offsetof(struct statvfs, f_bsize), offsetof(struct statvfs, f_flag),
           offsetof(struct statvfs, f_type));
    printf("  ↑ 两个结构体都是「11 个 8 字节字段 = 88 字节」打头，后面各自留尾巴：\n");
    printf("    statfs  = 88 + f_spare[4]×8 = 88 + 32 = 120\n");
    printf("    statvfs = 88 + f_type(4) + __f_spare[5]×4 = 88 + 4 + 20 = 112\n");
    printf("    statvfs 的尾巴里那个 f_type 是 **glibc 扩展**（POSIX 没有），\n");
    printf("    而 statfs 的 f_flags 在 statvfs 里叫 f_flag（少一个 s）—— 两个名字都要记。\n");

    /* ---------- ② 并排 ---------- */
    sec("② 同一条路径上 statfs() 与 statvfs() 并排，逐字段对账");
    for (int i = 0; PATHS[i] != NULL; i++) {
        struct statfs sf;
        struct statvfs sv;
        int r1, r2;

        errno = 0;
        r1 = statfs(PATHS[i], &sf);

        errno = 0;
        r2 = statvfs(PATHS[i], &sv);
        int e2 = errno;

        printf("\n  [%s]\n", PATHS[i]);
        if (r1 == -1 || r2 == -1) {

               (unsigned long long)sf.f_blocks, (unsigned long long)sf.f_bfree,
               (unsigned long long)sf.f_bavail);

               (unsigned)sf.f_fsid.__val[0], (unsigned)sf.f_fsid.__val[1],
               (unsigned long)sf.f_flags);

               sv.f_bsize, sv.f_frsize, sv.f_namemax);
        printf("             f_blocks=%llu  f_bfree=%llu  f_bavail=%llu\n",

        printf("      f_blocks == statfs.f_blocks           : %s\n",
               (unsigned long long)sv.f_blocks == (unsigned long long)sf.f_blocks ? "是" : "否");
        printf("      f_ffree  == statfs.f_ffree            : %s\n",

               (unsigned)sv.f_type == (unsigned)sf.f_type ? "是" : "否");

               (unsigned long long)sv.f_favail == (unsigned long long)sv.f_ffree ? "是" : "否");

        struct statfs sf;

            snprintf(opts, sizeof(opts), "(mountinfo 里没有精确匹配的挂载点)");

        printf("    statvfs.f_flag                = %#lx\n", sv.f_flag);

        printf("    mountinfo 的 per-mount options= %s\n", opts);

        printf("      注意 mountinfo 里**没有**对应 ST_VALID 的选项 —— 它是 glibc 造出来的。\n");
    }

    sec("④ 实证 f_flag == statfs.f_flags ^ 0x20");

        struct statvfs sv;
        struct statfs sf;

        if (statvfs(PATHS[i], &sv) == -1 || statfs(PATHS[i], &sf) == -1)
            continue;
        printf("  %-6s statfs.f_flags=%#06lx   statvfs.f_flag=%#06lx   异或=%#06lx   "
               "f_flags ^ 0x20 == f_flag ? %s\n",
               PATHS[i], (unsigned long)sf.f_flags, (unsigned long)sv.f_flag,
               (unsigned long)(sf.f_flags ^ sv.f_flag),
               ((unsigned long)sf.f_flags ^ C14_ST_VALID) == (unsigned long)sv.f_flag

    printf("  ↑ 内核在 f_flags 里放了 ST_VALID(0x0020) 这一位（来自 vfs_statfs() 里的\n");
    printf("    calculate_f_flags()，见 fs/statfs.c），意思是「本内核支持 f_flags」。\n");
    printf("    glibc 用**异或**把它去掉，于是 f_flag 里只剩下真正的挂载标志位。\n");

            continue;
        printf("  %-6s f_ffree=%-10llu f_favail=%-10llu 相等?%s\n",
               PATHS[i], (unsigned long long)sv.f_ffree, (unsigned long long)sv.f_favail,
               sv.f_favail == sv.f_ffree ? "是 ✔" : "否");
    }
    printf("  ↑ 内核的 statfs 结构里**根本没有 f_favail 这个字段**；\n");
    printf("    glibc internal_statvfs.c:109 那两行自己写着：\n");
    printf("      /* XXX I have no idea how to compute f_favail.  Any idea???  */\n");
    printf("      buf->f_favail = buf->f_ffree;\n");
    printf("    所以「非特权用户可用 inode 数」在 Linux 上是**假的** —— 它等于特权用户可用数。\n");
    printf("    （对比：f_bavail 才是真的，它来自内核 statfs 的 f_bavail；\n");
    printf("      ext4 上默认保留 5%% 给 root，所以 f_bavail < f_bfree 是正常现象。）\n");

    /* ---------- ⑥ f_frsize ?: f_bsize ---------- */
    sec("⑥ f_frsize ?: f_bsize —— 这一支在本机**不可达**（诚实标注）");
    for (int i = 0; PATHS[i] != NULL; i++) {
        struct statfs sf;

        if (statfs(PATHS[i], &sf) == -1)
            continue;
        printf("  %-6s statfs.f_frsize=%-8ld statfs.f_bsize=%-8ld → 走的是 %s\n",
               PATHS[i], (long)sf.f_frsize, (long)sf.f_bsize,
               sf.f_frsize != 0 ? "「取 f_frsize」那一支" : "「回退到 f_bsize」那一支");
    }
    printf("  ↑ internal_statvfs.c 的 `buf->f_frsize = fsbuf->f_frsize ?: fsbuf->f_bsize;`\n");
    printf("    是为「老内核不填 f_frsize」准备的补丁。本机内核 v6.6 一律填值，\n");
    printf("    所以**回退那一支在本容器里观察不到** —— 只能说代码在那里，不能说它被走到。\n");

    /* ---------- ⑦ f_fsid 重组 ---------- */
    sec("⑦ f_fsid 是两个 32 位半字的重组");
    for (int i = 0; PATHS[i] != NULL; i++) {
        struct statfs sf;
        struct statvfs sv;
        unsigned long long recomb;

        if (statfs(PATHS[i], &sf) == -1 || statvfs(PATHS[i], &sv) == -1)
            continue;
        recomb = ((unsigned long long)(unsigned)sf.f_fsid.__val[0])
               | ((unsigned long long)(unsigned)sf.f_fsid.__val[1] << 32);
        printf("  %-6s statfs=(%08x,%08x) → 拼起来=%#018llx   statvfs.f_fsid=%#018lx  %s\n",
               PATHS[i], (unsigned)sf.f_fsid.__val[0], (unsigned)sf.f_fsid.__val[1],
               recomb, sv.f_fsid, recomb == sv.f_fsid ? "一致 ✔" : "不一致");
    }
    printf("  ↑ 所以 `statvfs.f_fsid` 与 `statfs.f_fsid.__val[]` 是**同一个数**，\n");
    printf("    只是一个按 64 位整数看、一个按两个 32 位半字看。\n");

    /* ---------- ⑧ 结论 ---------- */
    sec("⑧ 结论");
    printf("  · statvfs() 全流程 = 一次 statfs**系统调用** + 一大段用户态字段搬运。\n");
    printf("    没有第二个系统调用，也没有第二次进内核。\n");
    printf("  · 所以 statvfs 能给你的信息**不会多于** statfs；反而少了 f_type 的宽度\n");
    printf("    （statvfs 是 unsigned int，statfs 是 __fsword_t=long）。\n");
    printf("  · 工程上：只用 Linux 就调 statfs()（字段更全、少一层包装）；\n");
    printf("    要可移植才用 statvfs()（POSIX 标准接口，其他 Unix 也有）。\n");
    printf("  · 反过来说：看到 f_flag 少一位、f_favail 与 f_ffree 相等，\n");
    printf("    别怀疑内核 —— 那是 glibc 干的。\n");

    printf("\n=== c14_11 done ===\n");
    return 0;
}
```

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 以为 `statvfs()` 是一个独立的系统调用 | 它是 glibc 对 `statfs()` 的**包装**（`statvfs64.c:28-38`）。全程只进内核一次 |
| 2 | 以为 `statvfs` 信息「更全」 | 不会更多。`f_type` 在 `statvfs` 里是 `unsigned int`（更窄），`f_flags` 还少一位 |
| 3 | 说「`f_type` 只有 `statfs` 有」 | **错**。`bits/statvfs.h:54` 就有 `unsigned int f_type`（glibc 扩展） |
| 4 | 把 `statfs.f_flags` 直接当挂载标志用 | 它含 `ST_VALID(0x20)`。glibc 的 `f_flag` 是 `^ 0x20` 之后的结果 |
| 5 | 拿 `f_flag & ST_VALID` 判断内核支持度 | 恒为 0。要判支持度看 **`statfs.f_flags`** |
| 6 | 以为 `f_favail` 是「非特权用户可用 inode」 | Linux 上它**等于 `f_ffree`**（glibc `internal_statvfs.c:65-66` 自己写着 XXX 不会算） |
| 7 | 以为 `f_bavail` 也是假的 | **`f_bavail` 是真值**（来自内核）。ext4 上它小于 `f_bfree` 是正常的（保留了 5% 给 root） |
| 8 | 把 `f_fsid` 当 `st_dev` 或持久标识 | 它是「这一次挂载的随机标识」。可以用来判「是不是同一个超级块」（§14.10），不能做持久 ID |
| 9 | 以为 `f_frsize ?: f_bsize` 的回退在真机上用过 | 本机 v6.6 一律填 `f_frsize`，那一支**不可达**。只能说代码在那里 |
| 10 | 对 `/proc` 问「还剩多少空间」 | procfs 的 `f_blocks`/`f_files` 都是 **0**。伪文件系统没有容量语义 |
| 11 | 把 `statvfs.f_flag` 与 `statfs.f_flags` 当成同一个字段 | 名字差一个 `s`，值差一个 `0x20` 位。写代码时对照手册 |
| 12 | 跨作业比较 `f_fsid`/`f_blocks` | 每个作业可能不同宿主（本机 `t_statfs_root` 与 `t_statvfs_root` 的 blocks 分别是 1949384 / 2009890） |

## HFT / 嵌入式关联

| 场景 | 结论怎么用 |
|------|-----------|
| **落盘前查空间：用 `statfs` 而不是 `statvfs`** | 少一层包装、字段更全，且能拿到 `f_type` 的完整宽度。只有要跨 Unix 移植时才用 `statvfs` |
| **`f_flag` 是「这个挂载点是不是只读」的便宜判据** | 一次 `statvfs` 就能知道（`ST_RDONLY`）。比读 `mountinfo` 解析字符串省事，也比 `access(W_OK)` 准确（后者受权限影响） |
| **别信 `f_favail`** | 监控脚本里用 `f_favail` 判断「inode 是否快满」会得到与 `f_ffree` 完全相同的数 —— 在 ext4 上这不是问题（本来就一样），但在**有 inode 保留**的设计上就是错的。用 `f_ffree` |
| **`f_bavail` 才是「我能写多少」** | ext4 默认保留 5% 给 root。HFT 的非特权写盘进程应该用 `f_bavail` 判断余量，用 `f_bfree` 会高估 |
| **`f_bsize` vs `f_frsize`** | `f_bsize` 是「推荐 I/O 大小」，`f_frsize` 是「计算容量用的基本块」。本机两者都是 4096，但在某些文件系统（支持片段的）上不同 —— 算容量必须用 **`f_frsize`** |
| **伪文件系统没有容量** | 对 `/proc`、`/sys` 调 `statfs` 得到全 0，这不代表「盘满」。写通用监控时要把 `f_blocks == 0` 视为「跳过」而不是「告警」 |
| **嵌入式最小 rootfs 的体积检查** | 用 `statfs` 的 `f_blocks × f_frsize` 得到卷容量，再用 `f_bfree` 算占用 —— 但**别忘 inode**（§14.10 的 100 inode 例子）。只读 squashfs 的 `f_bfree` 恒为 0，这也不是「满了」 |

<summary>代码自测（Q&A）</summary>

**Q1：`statvfs()` 在 Linux 上是不是系统调用？**

A：**不是**。glibc 的 `statvfs64.c:28-38` 显示它内部调用 `__statfs64()`（那才是系统调用），然后由 `__internal_statvfs64()` 在**用户态**做字段搬运。x86-64 上 `statvfs` 甚至是 `__statvfs64` 的**弱别名**（`statvfs64.c:45-47`），连一层函数调用都没有。所以「一次 `statvfs` 只进内核一次」，能拿到的信息不会多于 `statfs`。

**Q2：`statvfs.f_flag` 与 `statfs.f_flags` 差在哪？**

A：差**一个 `0x20` 位**，而且是**异或**掉的：`buf->f_flag = fsbuf->f_flags ^ ST_VALID`（`internal_statvfs.c:68`），`ST_VALID = 0x0020`（同文件 `:26`）。内核在 `calculate_f_flags()`（`fs/statfs.c:49-52`）里把 `ST_VALID` 置位表示「本内核支持 `f_flags`」，glibc 把它抹掉好让 `f_flag` 只剩真正的挂载标志。本机实测：`0x1021^0x20=0x1001`、`0x1020^0x20=0x1000`、`0x102e^0x20=0x100e`，三个全对。

**Q3：Linux 上 `f_favail` 可不可信？**

A：**不可信**。`internal_statvfs.c:65-66` 逐字写着 `/* XXX I have no idea how to compute f_favail.  Any idea???  */` 然后 `buf->f_favail = buf->f_ffree;`。所以本机三个路径的 `f_favail` 都恰好等于 `f_ffree` —— 不是巧合，是照抄。对比之下 `f_bavail` 是**真值**（来自内核，ext4 保留了 5% 给 root，所以 `f_bavail < f_bfree`）。

**Q4：`statvfs` 有没有 `f_type`？**

A：**有**。`bits/statvfs.h:54` 是 `unsigned int f_type;`。它是 **glibc 扩展**（POSIX 的 `statvfs` 里没有），`internal_statvfs.c:60` 从 `fsbuf->f_type` 直接拷过来。所以「`f_type` 只有 `statfs` 有」是错的 —— 但它的宽度是 `unsigned int`，比 `statfs` 的 `__fsword_t`（x86-64 上是 `long`）窄。

**Q5：`f_frsize ?: f_bsize` 这个回退什么时候会被走到？**

A：当内核的 `statfs` 不填 `f_frsize`（或填 0）时。本机内核 v6.6 一律填值（三个路径都是 `4096`），所以**回退分支在本容器不可达**。这是「老内核兼容补丁」的典型形态 —— 只能说代码在那里，不能声称实测过。

**Q6：为什么 `/proc` 的 `Total data blocks` 是 0，`File system ID` 是 `0x50, 0`？**

A：procfs 没有「容量」概念（没有数据块、没有 inode 表），所以 `f_blocks`/`f_files` 全 0。它的 `fsid` 是一个**常量**（本机实测 `0x50, 0`），与 pid 命名空间相关；而 tmpfs 的 `fsid` 是**每次挂载随机生成**的（本机 `/` 是 `7c6ce3ea,05539714`，重启/重挂会变）。

**Q7：算「文件系统容量」该用 `f_bsize` 还是 `f_frsize`？**

A：**`f_frsize`**。`f_bsize` 是「推荐 I/O 大小」（数据块大小），`f_frsize` 是「计算容量用的基本块大小」。本机两者都是 `4096` 所以看不出差别，但在支持「片段」（fragment）的文件系统上，`f_blocks × f_frsize` 才是真实容量 —— 这也是 glibc 要专门做 `f_frsize ?: f_bsize` 的原因。
