## 二、四个 API 的分工（不要用错）

| API | 问什么 | 返回什么 | 归谁管 |
|-----|--------|---------|--------|
| `stat(2)` | 「这个文件」 | `st_dev`/`st_ino`/`st_mode`/`st_nlink`/`st_size`/`st_blocks` | inode（§14.4） |
| `statfs(2)` | 「这个路径所在的**文件系统**」 | `f_type`/`f_bsize`/`f_blocks`/`f_files`/`f_flags` | 超级块（§14.3） |
| `statvfs(3)` | 同上，但**可移植** | POSIX 字段子集 + glibc 的 `f_type` | **glibc 包装**（§14.11） |
| `/proc/self/mountinfo` | 「**挂了什么**、怎么挂的」 | mount ID / parent ID / `root` / per-mount 选项 / optional fields | 挂载命名空间（§14.7/14.9） |

**一句话**：`stat` 问对象，`statfs` 问卷，`mountinfo` 问「挂载关系」。

## 三、全章最值得背的 10 条

1. **`/proc/partitions` 的 `#blocks` 是 1 KiB**（`block/genhd.c:862` 的 `>> 1`）。
2. **分区名的 `p` 由「父设备名末字符是不是数字」决定**（`block/partitions/core.c:349`），不是 NVMe 专有。
3. **inode 号必须配 `st_dev`** —— 本机 `/` 与 `/proc` 的 `st_ino` 都是 `1`。
4. **数据释放条件 = `nlink == 0` 且无打开的 fd** —— 本机 `/etc/passwd` 就是活着的 `nlink=0`。
5. **`st_blocks` 单位固定 512 字节**；写 1 字节 → `st_size=1, st_blocks=8`（占 4096）。
6. **`dup` 共享偏移、`open` 两次不共享** —— 判据是 `struct file`，不是 inode。
7. **日志保结构、`fsync` 保数据** —— `write` 之后 jbd2 计数不变，`fsync` 之后 +1。
8. **bind mount 的判据是 `mountinfo` 的 `root != /`**；同一设备出现多次**不**足以判定。
9. **tmpfs 的 `size=` = `f_blocks × f_frsize`、`nr_inodes=` = `f_files`**；没写 `size=` 时上限是内存的一半。
10. **`statvfs` 不是系统调用**；`f_flag = f_flags ^ 0x20`（`ST_VALID`）；`f_favail == f_ffree` 是 glibc 的「不会算」。

## 四、四套位值（同一件事的四层编码）

| 层 | 前缀 | 处所 | `nosuid` 的值 |
|----|------|------|--------------|
| `mount(2)` ABI | `MS_*` | `include/uapi/linux/mount.h` | `MS_NOSUID = 2` |
| 内核 per-mount | `MNT_*` | `include/linux/mount.h` | `MNT_NOSUID = 0x01` |
| statfs/statvfs | `ST_*` | `include/linux/statfs.h` / glibc `bits/statvfs.h` | `ST_NOSUID = 2` |
| `mount_setattr` | `MOUNT_ATTR_*` | `include/uapi/linux/mount.h` | `MOUNT_ATTR_NOSUID = 0x02` |

**判据**：`MS_*` 是入参、`MNT_*` 是内核存储、`ST_*` 是给用户态看的、`MOUNT_ATTR_*` 是「只改一个属性」的新接口。**看到 `0x20` 就知道是 `ST_VALID`（glibc 内部位）。**

## 五、⚠️ 会漂的数字 vs 稳定的数字

**这一节比结论本身更重要**：CE 每个作业是独立容器、宿主也可能换（本轮跑过 `nvme` 与 `xvda` 两个家族），所以引用数字前必须先分类。

### 一定会漂（不要写进断言）

| 量 | 观察到的变化 |
|----|-------------|
| 设备号（`st_dev`、`/proc/partitions` 的 major:minor） | 本轮 `259:1`/`259:2`、另一作业 `202:1`；更早一轮整盘家族是 `xvda`/`202:x` |
| `/proc/partitions` 条目数 | 29~31 |
| `/proc/devices` 块设备 major 数 | 上一轮被截断成 11，本轮 23 |
| `/proc/self/mountinfo` 条数 | 61 / 62 / 65 / 66（不同作业不同宿主） |
| `f_ffree` / `f_bfree` / `f_bavail` | 宿主机上别的容器也在写 |
| `f_fsid` | 每次挂载随机生成（procfs 的 `0x50` 是例外） |
| jbd2 的 `N transactions` 首行 | 上一轮 `348`、本轮 `590` —— **只能看增量** |
| `/cefs/**` 的具体名字与 `master:N` 的 N | 编译器镜像滚动更新 |
| 所有耗时（`us/个`） | 不同宿主、不同负载 |

### 相对稳定（可以引用）

| 量 | 值 | 依据 |
|----|----|------|
| `f_type` 的 magic | ext4 `0xef53`、tmpfs `0x01021994`、proc `0x9fa0` | ABI |
| `MS_*` / `MNT_*` / `ST_*` / `MOUNT_ATTR_*` 的值 | 见第四节 | ABI |
| `sizeof(struct statfs)` / `statvfs` | 120 / 112（x86-64 / glibc 2.39） | ABI |
| `ST_VALID` | `0x0020` | glibc 内部常量 |
| `MINORBITS` / `BLKDEV_MAJOR_MAX` | 20 / 512 | 内核常量 |
| `BLOCK_EXT_MAJOR` | `259` | 由 `register_blkdev(..., "blkext")` + `/proc/devices` 交叉确认 |
| ext4 块组大小 | `8 × block_size`（4 KiB → 128 MiB） | 官方文档公式 |
| 「+1 / +0」这类**增量方向** | `fsync` +1、`write` +0 | 机制决定 |

> **纪律**：这条分界线决定了一个数字能不能写成断言。写成断言的那些（`0xef53`、`120`、`259`、`ST_VALID`）都是 ABI 或常量；会漂的那些（设备号、容量、计数、耗时）一律只作**同一次运行内**的比较。

<summary>代码自测（Q&A）</summary>

**Q1：一句话说清 `stat` / `statfs` / `statvfs` / `mountinfo` 的分工。**

A：`stat` 问**对象**（inode：`st_dev`/`st_ino`/`st_size`…）；`statfs` 问**卷**（超级块：`f_type`/`f_blocks`/`f_files`…）；`statvfs` 是 `statfs` 的可移植包装（同一次内核查询 + glibc 字段搬运）；`mountinfo` 问**挂载关系**（谁挂在哪儿、怎么挂的、是不是 bind、有没有传播）。

**Q2：本章哪几个数字是「绝对不能写进断言」的？**

A：所有**由环境决定**的量：设备号、`/proc/partitions` 条目数、`/proc/devices` 的 major 数、`mountinfo` 条数、`f_ffree`/`f_bfree`、`f_fsid`、jbd2 的累计计数、`/cefs/**` 的名字、所有耗时。它们在同一次运行内自洽，跨运行必然漂（本机实测 `/proc/partitions` 有 29 和 31 两种，`mountinfo` 有 61/62/65/66 四种）。

**Q3：哪几个数字可以放心写成断言？**

A：**ABI 与常量**：`f_type` 的 magic（`0xef53`/`0x01021994`/`0x9fa0`）、四套位值的定义、`sizeof(struct statfs)=120`/`statvfs=112`、`ST_VALID=0x20`、`MINORBITS=20`、`BLKDEV_MAJOR_MAX=512`、`BLOCK_EXT_MAJOR=259`、ext4 块组公式「8 × block_size」。以及**增量方向**（`fsync` 让 jbd2 +1、`write` 不产生事务）。

**Q4：为什么本章反复出现「同一次运行内比较」这句话？**

A：因为 CE 每个作业是**独立的一次编译+执行**，可能落在不同容器/宿主上。本机实测同一个作业里 `/app` 的 `st_dev` 是 `259:1`，另一个作业里是 `202:1`；`t_statfs_root` 与 `t_statvfs_root` 的 `Total blocks` 分别是 `1949384` 与 `2009890`。所以「跨作业比设备号/容量/耗时」是**无效比较**，必须把「相对量」（同一作业内的比值、增量）与「绝对量」分开。

**Q5：拿到一个陌生环境，判断「这个目录是内存盘还是磁盘」的最快路径？**

A：`statfs(path).f_type`。`0x01021994` = tmpfs（内存），`0xef53` = ext 系（磁盘），`0x6969` = nfs（网络）。**不要**看路径名（谁都能 `mkdir /data`）、**不要**看 `df` 的挂载点名称、**不要**看目录是否存在。

**Q6：如何判断「两个挂载点是不是同一个文件系统实例」？**

A：比 `fsid`（`statfs().f_fsid`），不是 `f_type`、不是路径。本机 `/` 与 `/sys` 的 `fsid` 完全相同 ⇒ `/sys` 只是 `/` 上的空目录（sysfs 没挂）。要判断「是不是 bind mount」则用 `mountinfo` 的 `root != /`。

**Q7：本章哪一条结论最容易「知道但写错代码」？**

A：**`st_blocks` 的单位是 512 字节**。它和 `f_bsize`/`st_blksize` 都不同，所以「`st_blocks × st_blksize`」是错的（本机写 1 字节得 `st_size=1 st_blocks=8`，`8 × 512 = 4096 = f_bsize` 才自洽）。第二容易的是 `statvfs.f_flag` 与 `statfs.f_flags` 的名字与值都差一点（少一个 `s`、差 `0x20`）。
