## 本节讲什么

这是全章最容易出**线上事故**的一节。前面几节讲的都是「单独用一层会怎样」；这一节讲**同时用两层会怎样**：

```c
fprintf(fp, "AAAA");              /* 走 stdio：先进用户态缓冲 */
write(fileno(fp), "BBBB", 4);     /* 走 syscall：直接进内核 */
```

两句话指向**同一个文件、同一个偏移**，但数据走的路径完全不同。这一节回答：

1. 这样写文件里最终是什么？**顺序为什么一定是错的**？
2. 有哪几种修法？各自代价是什么？
3. 换个 `fd`（`dup`）能躲开吗？
4. 反过来，如果先用裸 `fd` 挪动偏移、再用 stdio 写，会怎样？
5. 原书的两个配图程序（`mix23io.c`、`mix23_linebuff.c`）在演示什么？

## 1. 问题的根源：两套缓冲「互不可见」

```text
            fprintf          write(fileno(fp), ...)
               │                      │
               ▼                      │
      [stdio 用户态缓冲]               │        ← 这一层 write 完全不知道
               │ fflush               │
               ▼                      ▼
      ┌────────────────────────────────────┐
      │        内核页缓存 / 文件偏移        │      ← 只有一个 f_pos，两者共用
      └────────────────────────────────────┘
```

关键事实：

| 事实 | 后果 |
|------|------|
| `FILE*` 有自己的用户态缓冲，`fd` **没有** | `fprintf` 的字节可能还留在内存里，而 `write` 已经落到文件里了 |
| 两者**共享**同一个内核文件偏移（`struct file` 的 `f_pos`） | 谁先到内核，谁就占低位 |
| `FILE*` **不自带**「当前位置」变量，它依赖底层 `fd` 的偏移 | 所以外部 `lseek` 会直接影响接下来 `fflush` 的落点（见 §4） |

于是「先 `fprintf` 后 `write`」的结果必然是：**`write` 的字节先到，`fprintf` 的字节等到 `fflush`/`fclose` 才追上去**——文件里就成了 `BBBBAAAA`。

## 2. 把「乱序」物化到文件里：五轮实测

`c13_7_mixing.c` 的聪明之处：它**不依赖肉眼观察 stdout 的先后顺序**（那在 socket 上完全不可靠），而是每一轮都：

1. 用 `fprintf` 写 `"AAAA"`、用 `write()` 写 `"BBBB"`；
2. 关闭后**把文件读回来**，与期望的 `"AAAABBBB"` 做 `strcmp`；
3. 打印「实际内容 / 期望内容 / 判定」。

这样得到的是**可判定的结论**，而不是「看起来好像是……」。五轮结果：

```text
== 把「两层缓冲打架」物化到文件里 ==
  每次实验：先用 fprintf 写 "AAAA"，再用 write() 写 "BBBB"，最后读回来看顺序。
  期望的正确顺序是 [AAAABBBB]。

-- ① 反面教材：fprintf 之后直接 write 同一个 fd --
  ① debug 乱序（未 fflush）   文件内容 = [BBBBAAAA]（文件 8 字节，读回 8 字节）
                                     期望 = [AAAABBBB]  → ✗ 顺序错了
                                     → write() 先到内核先落位；fprintf 的字节一直等到 fclose 才出去

-- ② 修法一：混用前先 fflush --
  ② fflush 之后再 write         文件内容 = [AAAABBBB]（文件 8 字节，读回 8 字节）
                                     期望 = [AAAABBBB]  → ✓ 顺序正确
                                     → 标准做法：**每次切换接口前 fflush**（读方向则要处理 lseek）

-- ③ 修法二：干脆关掉 stdio 缓冲 --
  ③ setvbuf(_IONBF) 后混用      文件内容 = [AAAABBBB]（文件 8 字节，读回 8 字节）
                                     期望 = [AAAABBBB]  → ✓ 顺序正确
                                     → 顺序对，但每次 fprintf 都变成一次 write()：混用不再危险，代价是性能

-- ④ 换一个 fd 不解决问题（dup 出来的 fd 共享同一个文件偏移） --
  ④ 用 dup 出来的 fd 去 write 文件内容 = [BBBBAAAA]（文件 8 字节，读回 8 字节）
                                     期望 = [AAAABBBB]  → ✗ 顺序错了
                                     → **照样乱序**：dup 出来的 fd 与原来共享文件偏移，避开的是 fd 不是缓冲

-- ⑤ 反向的坑：用另一个 fd 去 lseek，会让 stdio 写错位置 --
  ⑤ 外部 lseek 后继续 fprintf 文件内容 = [~100~AAAA]（文件 104 字节，读回 104 字节）
                                     期望 = [AAAABBBB]  → ✗ 顺序错了
                                     → 写进去了，但落在偏移 100：前面 ~100~ 是空洞（全 NUL 字节）
```

五轮逐条解读：

| 轮次 | 现象 | 结论 |
|------|------|------|
| ① | `[BBBBAAAA]` | 反面教材：`write` 的 4 字节先到，`fprintf` 的 4 字节在 `fclose` 时才追上去 |
| ② | `[AAAABBBB]` ✓ | **标准修法**：切换接口前 `fflush(fp)`，把用户态缓冲清空 |
| ③ | `[AAAABBBB]` ✓ | 另一种修法：`setvbuf(fp, NULL, _IONBF, 0)` —— 顺序对了，代价是失去 stdio 的全部缓冲收益 |
| ④ | `[BBBBAAAA]` ✗ | **`dup` 没用**：新 `fd` 与原来**共享同一个 `struct file`**（因此共享 `f_pos` 和状态）。要躲开必须用**独立的 `open`**（那会得到独立的偏移） |
| ⑤ | `[~100~AAAA]` | **反方向的坑**：用裸 `fd` `lseek` 到 100，然后 `fprintf` —— 数据真的写到了偏移 100 处，前面 100 字节是**空洞**（全 NUL） |

### ⑤ 那一行的 `~100~` 是怎么来的

第 ⑤ 轮输出里的 `~100~` 不是原始字节，而是程序对「连续 NUL 字节」的**压缩显示**（`sanitize()`）：把 N 个连续的 `\0` 显示成 `~N~`。因为空洞文件的前 100 字节全是 NUL，直接用 `%s` 打印会在第一个 `\0` 处截断、显示成空——那会掩盖真相。

真实的文件是 **104 字节**（100 字节空洞 + 4 字节 `"AAAA"`），`st_size = 104` 这件事本身就证明了「stdio 的写入跟着 `fd` 的偏移走了」。

### 机制说明：`FILE*` 没有「自己的位置」

一个常见误解是「stdio 记着自己的位置，所以外部 `lseek` 不会影响它」。**在 glibc 里不是这样**：`FILE` 结构里那些 `_IO_read_ptr` / `_IO_write_ptr` 只描述**用户态缓冲区内**的位置；对**内核**而言，写出去时用的就是底层 `fd` 的当前偏移（`vfs_write()` 推进 `f_pos`）。所以：

- 外部 `lseek` 之后，下一次 `fflush` 会把字节写到**新位置**；
- 如果缓冲里**已经有**未刷出的数据，那些数据也会一起写到新位置——于是可能**覆盖**原有内容。

**因此混用不只是「顺序」问题，还有「位置」问题。** 这也是下面「读方向」更麻烦的原因。

## 3. 修法汇总

```text
== 结论：什么时候能混、怎么混 ==
  ┌ 做法   判定
  ├ 只用一套 ✅ 首选。要么全程 stdio，要么全程 read/write
  ├ fflush 过渡 ✅ 每次从 stdio 切到 write 之前 fflush(fp)
  ├ 关缓冲 ✅ setvbuf(fp, NULL, _IONBF, 0)，代价是没了缓冲收益
  ├ fdopen 包装 ✅ 给 fd 套一个 FILE*，之后**全走 stdio**
  ├ 换 fd   ❌ 没用，dup 出来的 fd 共享文件偏移
  └ 直接混 ❌ 乱序 / 覆盖 / 丢数据，且**难以复现**
```

| 做法 | 要点 | 代价 |
|------|------|------|
| **只用一套** | 最简单也最可靠：要么全 stdio，要么全 `read`/`write` | 无（唯一要放弃的是「混着用更顺手」） |
| **`fflush` 过渡** | 每次「stdio → syscall」之前 `fflush(fp)`；**读**方向还要额外处理 `lseek`（因为 stdio 预读会让 `fd` 偏移跑在前头） | 每切换一次多一次 `write` 系统调用 |
| **关掉缓冲** | `setvbuf(fp, NULL, _IONBF, 0)` 或 `setbuf(fp, NULL)` | 每次 `fprintf` 都变成一次 `write` —— 小块输出性能暴跌 |
| **`fdopen` 包装** | 给已有的 `fd` 套 `FILE*`，之后**只用 stdio**；不要再直接碰那个 `fd` | 无（但要注意 `fclose` 会关掉 `fd`） |
| **换 `fd`（`dup`）** | —— | **无效**。`dup` 出来的 fd 与原 fd 共享同一个 `struct file`，因此共享 `f_pos` |
| **直接混** | —— | 乱序 / 覆盖 / 丢数据，且**难以复现**（依赖缓冲是否恰好满、是否恰好切换） |

> **`fflush` 过渡为什么对「读方向」不够？** 因为 stdio 的读缓冲是**预读**的：它已经把 `fd` 的偏移推到缓冲区末尾了。你在应用层看到的「文件当前位置」和 `fd` 的真实偏移不一致。所以「先 `fgets` 再 `read`」需要在中间做一次 `lseek(fd, -pending, SEEK_CUR)` 之类的补偿（glibc 没有可移植的「告诉我预读了多少」的接口），**这正是为什么「只用一套」是首选**。

## 4. 原书的两个配图程序

原书在 §13.7 用两个小程序把「两层缓冲互不可见」画成了可观察的现象。本仓库把两个文件都逐字镜像在 `code/` 下。

### 4.1 `mix23io.c`：同一段文字，两种输出方式交错

```text
in accordance with his twofold attitude.
To man the world is twofold, 
```

程序先 `printf` 一句、再用 `write(STDOUT_FILENO, ...)` 写另一句，然后 `fflush`。在 CE 上（stdout 是 socket → 全缓冲）看到的顺序是：**`write` 的那句先出，`printf` 的那句后出**。这正是「`write` 直接进内核、`printf` 卡在用户态缓冲」的直接后果。

原书在第 13.7 节把该文件的用途标为「**This file is not printed in the book**」（配图程序，不印全文），本仓库仍逐字镜像以便复现。

### 4.2 `mix23_linebuff.c`：习题 13-4 的官方解答

```text
I would have written you a shorter letter.
If I had more time, 
```

这个程序的输出**顺序正好相反**，因为它把 `stdout` 设成了**行缓冲**（`_IOLBF`）——于是 `printf` 那句带 `'\n'` 的内容**先**出去了。它演示的是**同一个坑在两种缓冲模式下的两种表现**：

| 环境 | `printf` 与 `write` 谁先出 |
|------|--------------------------|
| `stdout` 是**终端**（行缓冲） | `printf` 先出（`'\n'` 触发 flush） |
| `stdout` 是**文件/管道/socket**（全缓冲） | `write` 先出（`printf` 还卡在缓冲里） |

> ⚠️ **CE 上的观察限制（必须诚实标注）**：本容器里 `stdout` 是 **socket**（`probe13` 实测 `S_ISSOCK=1`、`isatty=0`），而且**没有 pty**（`probe13b` 实测 `/dev/ptmx` 不存在、`posix_openpt()` 返回 `ENOENT`）。所以：
>
> - `mix23io.c` 跑出来的是「**全缓冲**那一半」的现象（`write` 先出）；
> - 【终端下行缓冲、`printf` 先出】那一半**在 CE 里观察不到** —— `mix23_linebuff.c` 只能通过**显式** `setvbuf(_IOLBF)` 间接复现。
>
> [13.2](13.2-stdio-file.md) 的 ③ 段就是为此设计的：把 stdout 临时接到管道、用 `write` 当参照物，从而在无 pty 的环境里也拿到**可判定的**行缓冲证据。

完整源码 [`code/c13_7_mixing.c`](../code/c13_7_mixing.c)：

```c
/* c13_7_mixing.c — Ch13 §13.7：混用 stdio 函数与 I/O 系统调用
 *
 * TLPI §13.7（p.248）的结论很硬：
 *   **在同一文件上混用 stdio 与 read/write，如果不加保护，就会乱序甚至丢数据。**
 * 原因是两层缓冲互不可见（13.4 讲的那张图），而且两者**都要推进文件偏移**。
 *
 * 原书用两个小程序演示（`filebuff/mix23io.c`、`filebuff/mix23_linebuff.c`，
 * 后者是习题 13-4 的官方解答），它们的现象**只在 stdout 是终端时**才看得全。
 * 本程序换一个不依赖终端的做法：**把顺序"物化"到文件里** ——
 *   每次实验都往一个真实文件写，写完把文件读回来，用内容比对判断顺序对不对。
 * 这样无论 stdout 是终端、管道还是 socket，结论都一样，而且在 CE 上可复现。
 *
 * 编译： gcc -O0 -Wall -Wextra -o c13_7_mixing c13_7_mixing.c
 * 取材： TLPI §13.7（混用的三种后果与两种修法；File 13-1/13-2 的演示程序）
 *       man-pages 6.19 stdio(3)（"the stream and the file descriptor share the
 *         file offset"；混用时的位置同步要求）
 *                      fflush(3)（把用户态缓冲交给内核）
 *                      fdopen(3) / fileno(3)（两层之间的桥）
 *       Linux v6.6 fs/read_write.c（ksys_write / vfs_write 对 f_pos 的推进）
 *       C99 7.19.5.3/7.21.5.3（fflush / lseek 对流的语义要求）
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

#define A "AAAA"      /* 走 stdio */
#define B "BBBB"      /* 走 write() */
#define WANT A B      /* 期望的正确顺序 */

/* 把读回来的原始字节转成「看得懂」的形式：
   连续 NUL（外部 lseek 造成空洞时留下的）压成 ~N~，换行写成 \n，其余不可打印写成 ?。
   注意：顺序判定仍然用**原始字节**做 strcmp，这里只改变**显示**。 */
static void sanitize(const char *in, size_t n, char *out, size_t cap)
{
    size_t i = 0, j = 0;

    while (i < n && j + 24 < cap) {
        if (in[i] == '\0') {
            size_t k = i;

            while (k < n && in[k] == '\0')
                k++;
            j += (size_t) snprintf(out + j, cap - j, "~%zu~", k - i);
            i = k;
        } else if (in[i] == '\n') {
            out[j++] = '\\';
            out[j++] = 'n';
            i++;
        } else if ((unsigned char) in[i] < 0x20 || (unsigned char) in[i] > 0x7e) {
            out[j++] = '?';
            i++;
        } else {
            out[j++] = in[i++];
        }
    }
    out[j] = '\0';
}

/* 把结果读回来，并判定顺序 */
static void verdict(const char *tag, const char *path, const char *detail)
{
    char got[128];
    char shown[512];
    struct stat st;
    FILE *fp = fopen(path, "r");
    size_t n;

    memset(got, 0, sizeof(got));
    memset(&st, 0, sizeof(st));
    st.st_size = -1;
    if (fp == NULL) {
        printf("  %-34s 读回失败 errno=%d(%s)\n", tag, errno, strerror(errno));
        return;
    }
    n = fread(got, 1, sizeof(got) - 1, fp);
    got[n] = '\0';
    (void) fstat(fileno(fp), &st);
    fclose(fp);
    sanitize(got, n, shown, sizeof(shown));

    printf("  %-34s 文件内容 = [%s]（文件 %ld 字节，读回 %zu 字节）\n",
           tag, shown, (long) st.st_size, n);
    printf("  %-34s 期望 = [%s]  → %s\n", "", WANT,
           strcmp(got, WANT) == 0 ? "✓ 顺序正确" : "✗ 顺序错了");
    printf("  %-34s %s\n", "", detail);
}

int main(void)
{
    printf("== 把「两层缓冲打架」物化到文件里 ==\n");
    printf("  每次实验：先用 fprintf 写 \"%s\"，再用 write() 写 \"%s\"，最后读回来看顺序。\n", A, B);
    printf("  期望的正确顺序是 [%s]。\n\n", WANT);

    printf("-- ① 反面教材：fprintf 之后直接 write 同一个 fd --\n");
    {
        const char *p = "/app/c13_7_a.txt";
        FILE *fp = fopen(p, "w");
        int fd;

        if (fp == NULL) {
            printf("  fopen 失败 errno=%d(%s)\n", errno, strerror(errno));
            return EXIT_FAILURE;
        }
        fd = fileno(fp);
        fprintf(fp, "%s", A);                       /* 进 stdio 缓冲 */
        if (write(fd, B, strlen(B)) != (ssize_t) strlen(B))
            printf("  write 失败 errno=%d(%s)\n", errno, strerror(errno));
        fclose(fp);                                 /* 这时才隐式 fflush */
        verdict("① debug 乱序（未 fflush）", p,
                "→ write() 先到内核先落位；fprintf 的字节一直等到 fclose 才出去");
        unlink(p);
    }

    printf("\n-- ② 修法一：混用前先 fflush --\n");
    {
        const char *p = "/app/c13_7_b.txt";
        FILE *fp = fopen(p, "w");
        int fd;

        if (fp == NULL) {
            printf("  fopen 失败 errno=%d(%s)\n", errno, strerror(errno));
            return EXIT_FAILURE;
        }
        fd = fileno(fp);
        fprintf(fp, "%s", A);
        fflush(fp);                                 /* ← 关键的一行 */
        if (write(fd, B, strlen(B)) != (ssize_t) strlen(B))
            printf("  write 失败 errno=%d(%s)\n", errno, strerror(errno));
        fclose(fp);
        verdict("② fflush 之后再 write", p,
                "→ 标准做法：**每次切换接口前 fflush**（读方向则要处理 lseek）");
        unlink(p);
    }

    printf("\n-- ③ 修法二：干脆关掉 stdio 缓冲 --\n");
    {
        const char *p = "/app/c13_7_c.txt";
        FILE *fp = fopen(p, "w");
        int fd;

        if (fp == NULL) {
            printf("  fopen 失败 errno=%d(%s)\n", errno, strerror(errno));
            return EXIT_FAILURE;
        }
        fd = fileno(fp);
        setvbuf(fp, NULL, _IONBF, 0);               /* 无缓冲，写一个走一个 */
        fprintf(fp, "%s", A);
        if (write(fd, B, strlen(B)) != (ssize_t) strlen(B))
            printf("  write 失败 errno=%d(%s)\n", errno, strerror(errno));
        fclose(fp);
        verdict("③ setvbuf(_IONBF) 后混用", p,
                "→ 顺序对，但每次 fprintf 都变成一次 write()：混用不再危险，代价是性能");
        unlink(p);
    }

    printf("\n-- ④ 换一个 fd 不解决问题（dup 出来的 fd 共享同一个文件偏移） --\n");
    {
        const char *p = "/app/c13_7_d.txt";
        FILE *fp = fopen(p, "w");
        int dupfd;

        if (fp == NULL) {
            printf("  fopen 失败 errno=%d(%s)\n", errno, strerror(errno));
            return EXIT_FAILURE;
        }
        dupfd = dup(fileno(fp));
        fprintf(fp, "%s", A);
        if (write(dupfd, B, strlen(B)) != (ssize_t) strlen(B))
            printf("  write 失败 errno=%d(%s)\n", errno, strerror(errno));
        close(dupfd);
        fclose(fp);
        verdict("④ 用 dup 出来的 fd 去 write", p,
                "→ **照样乱序**：dup 出来的 fd 与原来共享文件偏移，避开的是 fd 不是缓冲");
        unlink(p);
    }

    printf("\n-- ⑤ 反向的坑：用另一个 fd 去 lseek，会让 stdio 写错位置 --\n");
    {
        const char *p = "/app/c13_7_e.txt";
        FILE *fp = fopen(p, "w");
        int fd;

        if (fp == NULL) {
            printf("  fopen 失败 errno=%d(%s)\n", errno, strerror(errno));
            return EXIT_FAILURE;
        }
        fd = fileno(fp);
        fflush(fp);                              /* 先清空，免得把「续写」和「空洞」混在一起看 */
        if (lseek(fd, 100, SEEK_SET) == -1)       /* 用裸 fd 把偏移挪到 100 */
            printf("  lseek 失败 errno=%d(%s)\n", errno, strerror(errno));
        fprintf(fp, "%s", A);                      /* FILE 没有自己的偏移 → 就写到 100 处 */
        fflush(fp);
        fclose(fp);
        verdict("⑤ 外部 lseek 后继续 fprintf", p,
                "→ 写进去了，但落在偏移 100：前面 ~100~ 是空洞（全 NUL 字节）");
        unlink(p);
    }

    printf("\n== 结论：什么时候能混、怎么混 ==\n");
    printf("  ┌ %-8s %s\n", "做法", "判定");
    printf("  ├ %-8s %s\n", "只用一套", "✅ 首选。要么全程 stdio，要么全程 read/write");
    printf("  ├ %-8s %s\n", "fflush 过渡", "✅ 每次从 stdio 切到 write 之前 fflush(fp)");
    printf("  ├ %-8s %s\n", "关缓冲", "✅ setvbuf(fp, NULL, _IONBF, 0)，代价是没了缓冲收益");
    printf("  ├ %-8s %s\n", "fdopen 包装", "✅ 给 fd 套一个 FILE*，之后**全走 stdio**");
    printf("  ├ %-8s %s\n", "换 fd", "❌ 没用，dup 出来的 fd 共享文件偏移");
    printf("  └ %-8s %s\n", "直接混", "❌ 乱序 / 覆盖 / 丢数据，且**难以复现**");
    printf("\n  原书两个演示程序在本目录：`mix23io.c`、`mix23_linebuff.c`（习题 13-4 的官方解答）。\n");
    printf("  ⚠️ 在 CE 上跑它们时，stdout 是 **socket**（不是终端）→ 一律全缓冲，\n");
    printf("     所以只能观察到「重定向」那一半现象（write 先出、printf 后出）。\n");
    printf("     「终端下行缓冲、printf 先出」那一半在 CE 里**观察不到** ——\n");
    printf("     要看那一半得用真终端，或者用 13.2 里「显式 setvbuf(_IOLBF)」的办法间接验证。\n");
    return EXIT_SUCCESS;
}
```

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 「先 `fprintf` 再对同一 fd `write`」 | 顺序必然错：`write` 先落位，`fprintf` 等 `fclose`。切换前必须 `fflush(fp)` |
| 2 | 用 `dup` 出来的 fd 来「躲开 stdio」 | **无效**。`dup` 共享同一个 `struct file`（含 `f_pos`）。要独立偏移必须重新 `open` |
| 3 | 混用后只检查「内容对不对」，不检查**顺序** | 顺序错的内容**长度通常是对的**，很容易在测试里漏过。判据要包含顺序（`strcmp`） |
| 4 | 用裸 `fd` `lseek` 之后继续 `fprintf` | 数据会写到**新位置**（stdio 用 `fd` 的偏移），可能造成**文件空洞**（本程序 ⑤ 轮实测：104 字节、前 100 是 NUL）或**覆盖**已有内容 |
| 5 | 以为 `FILE*` 记着自己独立的位置 | glibc 的 `FILE` 只描述用户态缓冲内的位置；对内核用的是底层 `fd` 的偏移。**这是全节最容易误解的一条** |
| 6 | 「读方向」只 `fflush` 就以为安全了 | 读方向要处理**预读**：stdio 已经把 `fd` 偏移推到缓冲区末尾。`fflush` 对输入流是未定义行为 |
| 7 | 在混用场景里用 `setvbuf(_IONBF)` 又嫌慢 | 那就改成「只在一处切换」：把整个模块统一成 stdio 或统一成 syscall。`_IONBF` 是**正确但有代价**的修法 |
| 8 | 用 `strace` 看不到 `write` 就以为没写 | stdio 缓冲还没满时确实没有 `write`。看 `__fpending(fp)` 或 `ftell` 更直接 |

## HFT / 嵌入式关联

| 场景 | 结论怎么用 |
|------|-----------|
| **日志模块的两套接口** | 最常见的事故模式：底层用 `write(fd)` 写二进制帧，上层用 `fprintf(fp)` 写文本行，两者指向同一文件。必须**隔离到不同 fd**（各自 `open`），或统一到 stdio |
| **跨进程/跨线程日志交错** | 即使在同一进程内只用 `write`，超过 `PIPE_BUF`（本机实测 **4096**）的单次写也不再原子。混用 stdio 会让「原子性」彻底失控 |
| **`dup2` 重定向后混用** | 把 `stdout` `dup2` 到文件之后，`printf` 从行缓冲变全缓冲——此时如果还有代码在直接 `write(1, ...)`，输出顺序会「忽前忽后」，取决于缓冲是否刚好满 |
| **`fdopen` 是干净的出路** | 需要 stdio 的便利（格式化）+ syscall 的控制力时，用 `fdopen` 把 fd 包装成 `FILE*`，之后**只**用 stdio。要拿回控制权就在 `fflush` 之后 `fileno` |
| **嵌入式调试口** | 串口日志（字符设备 → 行缓冲）更容易掩盖这个问题：终端下顺序看着正常，一到重定向文件就乱。CI 里必须有一条「输出到文件」的用例 |
| **`fflush` 的性能账** | `fflush` 过渡每切换一次多一次系统调用。热路径里「每写一条就 `fflush`」的代价与「直接 `write`」相当——既然如此就不如全程 `write`，别绕 stdio |

<summary>代码自测（Q&A）</summary>

**Q1：`fprintf(fp, "AAAA")` 之后立刻 `write(fileno(fp), "BBBB", 4)`，文件里是什么？**

A：`"BBBBAAAA"`。`write` 的 4 字节直接进内核、占据了偏移 0~3；`fprintf` 的 4 字节留在用户态缓冲里，直到 `fclose`（隐式 `fflush`）才追加到偏移 4。本程序 ① 轮实测 `文件内容 = [BBBBAAAA]`，与期望 `[AAAABBBB]` 不符。

**Q2：有哪几种修法？各自的代价？**

A：① **只用一套**（首选，无代价）；② **切换前 `fflush(fp)`**（每次多一次系统调用）；③ **`setvbuf(fp, NULL, _IONBF, 0)` 关缓冲**（每次 `fprintf` 都变成一次 `write`）；④ **`fdopen` 包装后全走 stdio**（推荐给「需要格式化 + 需要 fd」的场景）。

**Q3：用 `dup` 出来的新 fd 去 `write`，能避免乱序吗？**

A：**不能**。`dup` 得到的新 fd 与原 fd 指向**同一个 `struct file`**，因此共享 `f_pos`。实测 ④ 轮仍然是 `[BBBBAAAA]`。要独立偏移必须**重新 `open`** 文件（那会有独立的偏移，但也要注意 O_APPEND 等标志的影响）。

**Q4：反过来，先用裸 `fd` `lseek`、再用 `fprintf` 会怎样？**

A：数据会写到**新位置**。实测 ⑤ 轮：`lseek(fd, 100, SEEK_SET)` 之后 `fprintf(fp, "AAAA")`，文件变成 **104 字节**，前 100 字节是**空洞（全 NUL）**，`"AAAA"` 在偏移 100 处。原因是 glibc 的 `FILE` 在写出时用的是底层 `fd` 的偏移，它**没有**独立的位置变量。

**Q5：为什么程序里要把连续的 NUL 显示成 `~100~`？**

A：因为空洞文件用 `%s` 打印会在第一个 `\0` 处截断、显示成空字符串——那会让人误判为「什么都没写」。`sanitize()` 把 N 个连续 NUL 压成 `~N~`，于是 `[~100~AAAA]` 一眼就能看出「100 字节空洞 + 4 字节数据」。

**Q6：`mix23io.c` 和 `mix23_linebuff.c` 的区别是什么？**

A：同一个坑的两种表现。`mix23io.c` 在默认（全）缓冲下跑，结果是 `write` 的内容**先**出；`mix23_linebuff.c` 把 stdout 设成**行缓冲**，于是 `printf` 里带 `'\n'` 的内容**先**出。在 CE 沙箱里（stdout 是 socket、无 pty），只能观察到全缓冲那一半；行缓冲那一半需要显式 `setvbuf(_IOLBF)` 或真终端。

**Q7：为什么「读方向」比「写方向」更难处理？**

A：因为 stdio 的读缓冲是**预读**的——它已经把 `fd` 的偏移推到缓冲区的末尾，而应用层看到的位置还在中间。要混用就必须把这个差值补回来（`lseek(fd, -pending, SEEK_CUR)`），而 glibc 没有可移植接口告诉你 `pending` 是多少。所以读方向更应当「只用一套」。
