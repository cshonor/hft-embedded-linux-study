# libc ≠ 普通 Rust crate（桥 vs 积木）

> 词纠正：是 **crate**（Rust 包/库单元），不是 kate。  
> 承接：[系统调用对外是 C](./1.x-syscall-interface-is-c.md) · TLPI = libc 暴露的 POSIX C 接口

---

## 表层为什么像

| | Rust crate | libc |
|--|------------|------|
| 程序员感觉 | `use xxx` 拿来就用 | 直接调 `open`/`read`/`fork`… |
| 角色 | 预制函数/类型，免手写底层 | 预制 C 函数，免手写陷入内核的汇编 |

从**应用层视角**：都是「预制库」——联想合理。

---

## 本质差别（关键）

| | **普通 Rust crate** | **libc（glibc/musl…）** |
|--|---------------------|-------------------------|
| 跑在哪 | 纯用户态积木 | 用户态，但是 **syscall 薄包装 + 部分用户态实现** |
| 核心职责 | 自己的逻辑；需要 OS 时再调别人 | 把 C 调用 **翻译成** `syscall` / `svc` 等，**陷入内核** |
| 「打开文件」谁做 | 不做（除非内部再调 libc/std） | **内核做**；libc **发起** syscall，**不包含**内核里的 open 实现 |
| 另外还做 | 各异 | `malloc`、`printf` 缓冲、字符串等（可完全不碰或不总碰 syscall） |

**记住：** libc 的 `open` **依旧跑在用户态**；它只写胶水陷阱指令，不拥有内核代码。详拆 → [1.x-syscall](./1.x-syscall-interface-is-c.md)。

### Rust 里的 `libc` crate

- **不实现** 打开文件 / 分配堆  
- 只是把系统 **C libc 接口** 做成 FFI 绑定，让 Rust 能调到同一座桥  

---

## 更准的类比

| 概念 | 像什么 |
|------|--------|
| **POSIX** | 接口契约（≈ trait：签名 + 行为） |
| **libc（glibc/musl）** | 该契约的 **C 侧实现**（桥） |
| **Rust `libc` crate** | 对那套 C 接口的 **绑定声明**，不重写内核逻辑 |
| **普通 crate** | 用户态上层积木，默认不直接碰 syscall |

**一句话：** libc 感觉像「系统自带的超级底层 crate」，但特殊在于它是 **用户程序 ↔ 内核** 的桥；普通 crate 只是用户态积木。

## 并排伪栈（C vs Rust）

```
【C 应用】                         【Rust 应用】
  main / 你的业务                    main / 你的业务
       │                                  │
       ▼                                  ▼
  libc: open()                       std 或 某 crate
       │                             （可能再调）
       │                                  ▼
       │                             libc crate（FFI 声明）
       │                                  │
       ▼                                  ▼
  真正的 C libc（glibc/musl…） ←─────────┘
       │
       ▼
  syscall / svc  （陷入内核）
       │
       ▼
  Linux 内核：sys_open 等实现
```

- **TLPI**：桥的这一侧 — libc 暴露的 POSIX/Linux **C 接口**怎么用  
- **LKD / ULK**：桥的另一侧 — 内核里怎么实现
