## 本节讲什么

进程间内存隔离，所以「通信」和「同步」必须借助内核提供的专门机制。本节回答三个问题：

1. IPC 要解决哪三类问题？
2. Linux 有哪些 IPC 机制？各自适合什么场景？
3. 一个 HFT 场景（如行情分发、订单撮合）该怎么选型？

这是全书 IPC 部分的「地图」——Ch43 概览、Ch44-55 逐机制详解，都从这张图出发。

## 1. IPC 的三大用途

| 用途 | 要解决什么 | 典型机制 |
|------|-----------|---------|
| **传数据** | 把字节/消息从一个进程搬到另一个 | 管道、消息队列、共享内存、socket |
| **同步** | 协调「谁先谁后」，防止竞争 | 信号量、文件锁、互斥量、条件变量 |
| **通知** | 只发「发生了某事件」的信号，不带数据 | 信号、eventfd、inotify |

> **「共享内存 + 同步机制」是性能最高、也最易错的组合**：共享内存负责「零拷贝传数据」，但不提供任何同步——必须配信号量/锁。很多并发 bug 就出在「以为共享内存自带同步」。

## 2. 机制全景

| 机制 | 类别 | 传数据 | 同步 | 通知 | 内核形态 | 章节 |
|------|------|:---:|:---:|:---:|---------|------|
| 管道 / FIFO | 字节流 | ✅ | ❌ | ❌ | 内核缓冲区 | Ch44 |
| SysV 消息队列 | 消息 | ✅ | ❌ | ❌ | id + 内核对象 | Ch46 |
| POSIX 消息队列 | 消息 | ✅ | ❌ | ✅ | mqd_t（≈fd） | Ch52 |
| SysV 共享内存 | 共享 | ✅ | ❌ | ❌ | id + 内核段 | Ch48 |
| POSIX 共享内存 | 共享 | ✅ | ❌ | ❌ | fd（/dev/shm） | Ch54 |
| mmap | 共享 | ✅ | ❌ | ❌ | VMA | Ch49 |
| SysV 信号量 | 同步 | ❌ | ✅ | ❌ | id + 信号量集 | Ch47 |
| POSIX 信号量 | 同步 | ❌ | ✅ | ❌ | 命名/匿名 | Ch53 |
| 文件锁 | 同步 | ❌ | ✅ | ❌ | inode 锁 | Ch55 |
| 信号 | 通知 | ❌ | ❌ | ✅ | sighand | Ch20-22 |
| eventfd | 通知 | ❌ | ❌ | ✅ | fd | Ch63 |
| socket | 网络 | ✅ | ❌ | ✅ | fd | Ch56-61 |

**两条关键分界线**：

1. **fd 型 vs id 型**：POSIX IPC / socket / eventfd 用 **fd**，能塞进 `epoll` 统一多路复用；SysV IPC 用 **id**（整数），**不能 epoll**。工程上「要统一事件循环」就选 fd 型。
2. **是否内核持久**：SysV 和 POSIX 命名 IPC 对象在**所有进程关闭后仍残留内核**，须显式 `IPC_RMID` / `unlink` 清理，否则累积泄漏。

## 3. 选型决策

```
同一台机器？ ──否──► socket（TCP/UDP，跨机唯一选择）
      │是
      ▼
要传大量数据、低延迟？ ──是──► 共享内存（mmap/POSIX shm）+ 信号量/锁同步
      │否
      ▼
要消息边界、按优先级消费？ ──是──► 消息队列（POSIX mq 优先，可 epoll）
      │否
      ▼
简单字节流、亲缘进程？ ──是──► 管道 / FIFO
      │否
      ▼
只需「发生了」的通知？ ──是──► eventfd / 信号
```

性能排序（传数据）：**共享内存 > 管道 > 消息队列 > socket**（共享内存零拷贝，socket 有协议栈 + 内核缓冲双重开销）。

## 4. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 行情进程 → 策略进程零拷贝分发 | 共享内存 + 无锁环形队列（配内存屏障），避免 socket 拷贝 |
| 撮合引擎多进程协作 | 共享内存存订单簿，信号量/锁保护临界区 |
| 阻塞在 epoll 上的交易主循环 | 选 fd 型 IPC（eventfd/POSIX mq/socket），统一 epoll，避免「轮询 + SysV id」 |
| IPC 对象泄漏 | SysV/POSIX 命名对象进程退出不自动清理，崩溃后残留，须启动时 `IPC_RMID`/`unlink` |

## 5. 代码示例

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
/* 管道：最简 IPC，父子进程传字节流 */
int main(void) {
    int fd[2];
    pipe(fd);                       /* fd[0] 读端，fd[1] 写端 */

    if (fork() == 0) {              /* 子进程写 */
        close(fd[0]);
        write(fd[1], "hello", 5);
        close(fd[1]);
        return 0;
    } else {                        /* 父进程读 */
        char buf[16];
        close(fd[1]);
        int n = read(fd[0], buf, sizeof(buf));
        close(fd[0]);
        wait(NULL);
        printf("parent got: %.*s\n", n, buf);
    }
    return 0;
}
```

<summary>代码自测（Q&A）</summary>

**Q1：管道和消息队列的核心区别？**
A：管道是**无边界字节流**——写入的字节流到读端是连续的，读 5 字节不知道它们是「一条消息」；消息队列是**有边界消息**——每条消息独立，读端一次读一条，还能按 `mtype` 选优先级（POSIX mq 数值大先出）。要「消息边界/优先级」选消息队列，要「简单字节流」选管道。

**Q2：为什么共享内存是最快的 IPC？它有什么代价？**
A：数据直接在内存共享，**没有内核拷贝**（管道/socket 都要经过内核缓冲区搬一次）。代价是**没有同步**——两个进程同时读写同一块内存会竞态，必须额外配信号量/锁/原子操作，而这恰恰是最容易出错的地方。

**Q3：SysV 消息队列和 POSIX 消息队列，工程上优先哪个？为什么？**
A：POSIX。因为 POSIX mq 是 **fd 型**（`mqd_t` 可塞进 `epoll`），能和其他 fd 统一多路复用；SysV mq 是 **id 型**，无法 epoll，只能阻塞读或轮询。且 POSIX mq 有 `mq_notify` 异步通知。SysV 的唯一优势是「多锁原子性」（`SEM_UNDO`）和更老的兼容性。

**Q4：「IPC 对象内核持久」意味着什么？会有什么坑？**
A：SysV 信号量/共享内存、POSIX 命名 mq/sem，创建后即使所有进程都退出，对象**仍留在内核**（`ipcs` 能看到），直到显式 `IPC_RMID`/`unlink`。崩溃的程序会留下孤儿对象，累积耗尽内核限额。所以「创建者要负责清理」，或在启动时先清理同名对象。

**Q5：一个进程要同时等「网络 socket」和「子进程管道」有数据，该怎么设计？**
A：用 **fd 型 IPC + epoll**——把 socket fd 和管道读端 fd 一起加入 epoll，统一阻塞在 `epoll_wait`。这就是「事件循环」模型。若混用了 SysV 消息队列（id 型），它进不了 epoll，只能另开线程轮询，复杂度陡增。

</details>
