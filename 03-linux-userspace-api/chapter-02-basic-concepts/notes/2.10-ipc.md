## 本节讲什么

进程间内存隔离，所以「通信」和「同步」必须借助内核提供的专门机制。本节回答三个问题：

1. IPC 要解决哪三类问题？
2. Linux 有哪些 IPC 机制？各自适合什么场景？
3. 一个 HFT 场景（如行情分发、订单撮合）该怎么选型？

这是全书 IPC 部分的「地图」——[Ch43](../../chapter-43-ipc-overview/README.md) 概览、[Ch44](../../chapter-44-pipes-fifos/README.md)-[55](../../chapter-55-file-locking/README.md) 逐机制详解，都从这张图出发。

本节要补的是**四种「字节通道」的可测量差异**：管道的容量与原子写上限分别是多少、**写端全关后 `read` 返回 0 而不是阻塞**（这条是很多日志/管道 bug 的根因）、以及 `socketpair` 与 `FIFO` 各在什么情况下更好用。

## 要点

### 一、IPC 的三大用途

| 用途 | 要解决什么 | 典型机制 |
|------|-----------|---------|
| **传数据** | 把字节/消息从一个进程搬到另一个 | 管道、消息队列、共享内存、socket |
| **同步** | 协调「谁先谁后」，防止竞争 | 信号量、文件锁、互斥量、条件变量 |
| **通知** | 只发「发生了某事件」的信号，不带数据 | 信号、eventfd、inotify |

> **「共享内存 + 同步机制」是性能最高、也最易错的组合**：共享内存负责「零拷贝传数据」，但不提供任何同步——必须配信号量/锁。很多并发 bug 就出在「以为共享内存自带同步」。

### 二、机制全景

| 机制 | 类别 | 传数据 | 同步 | 通知 | 内核形态 | 章节 |
|------|------|:---:|:---:|:---:|---------|------|
| 管道 / FIFO | 字节流 | ✅ | ❌ | ❌ | 内核缓冲区 | [Ch44](../../chapter-44-pipes-fifos/README.md) |
| SysV 消息队列 | 消息 | ✅ | ❌ | ❌ | id + 内核对象 | [Ch46](../../chapter-46-sysv-message-queues/README.md) |
| POSIX 消息队列 | 消息 | ✅ | ❌ | ✅ | mqd_t（≈fd） | [Ch52](../../chapter-52-posix-message-queues/README.md) |
| SysV 共享内存 | 共享 | ✅ | ❌ | ❌ | id + 内核段 | [Ch48](../../chapter-48-sysv-shared-memory/README.md) |
| POSIX 共享内存 | 共享 | ✅ | ❌ | ❌ | fd（/dev/shm） | [Ch54](../../chapter-54-posix-shared-memory/README.md) |
| mmap | 共享 | ✅ | ❌ | ❌ | VMA | [Ch49](../../chapter-49-memory-mappings/README.md) |
| SysV 信号量 | 同步 | ❌ | ✅ | ❌ | id + 信号量集 | [Ch47](../../chapter-47-sysv-semaphores/README.md) |
| POSIX 信号量 | 同步 | ❌ | ✅ | ❌ | 命名/匿名 | [Ch53](../../chapter-53-posix-semaphores/README.md) |
| 文件锁 | 同步 | ❌ | ✅ | ❌ | inode 锁 | [Ch55](../../chapter-55-file-locking/README.md) |
| 信号 | 通知 | ❌ | ❌ | ✅ | sighand | [Ch20-22](../../chapter-20-signals-fundamentals/README.md) |
| eventfd | 通知 | ❌ | ❌ | ✅ | fd | [Ch63](../../chapter-63-alternative-i-o-models/notes/63.4-the-epoll-api.md) |
| socket | 网络 | ✅ | ❌ | ✅ | fd | [Ch56-61](../../chapter-56-sockets-intro/README.md) |

**两条关键分界线**：

1. **fd 型 vs id 型**：POSIX IPC / socket / eventfd 用 **fd**，能塞进 `epoll` 统一多路复用；SysV IPC 用 **id**（整数），**不能 epoll**。工程上「要统一事件循环」就选 fd 型。
2. **是否内核持久**：SysV 和 POSIX 命名 IPC 对象在**所有进程关闭后仍残留内核**，须显式 `IPC_RMID` / `unlink` 清理，否则累积泄漏。

### 三、选型决策

```
同一台机器？ ──否──► socket（TCP/UDP，跨机唯一选择）
      │是
      ▼
要传大量数据、低延迟？ ──是──► 共享内存（mmap/POSIX shm）+ 信号量/锁同步
      │否
      ▼
要消息边界、按优先级消费？ ──是──► 消息队列（POSIX mq 优先，可 epoll）
      │否
      ▼
简单字节流、亲缘进程？ ──是──► 管道 / FIFO
      │否
      ▼
只需「发生了」的通知？ ──是──► eventfd / 信号
```

性能排序（传数据）：**共享内存 > 管道 > 消息队列 > socket**（共享内存零拷贝，socket 有协议栈 + 内核缓冲双重开销）。

## 代码

### c2_10 pipe / socketpair / FIFO 的四个可测量事实

[`../code/c2_10_ipc.c`](../code/c2_10_ipc.c) 分六段：

| 段 | 做什么 | 钉死什么 |
|----|--------|----------|
| ① | `pipe()` + `fork`，子写父读 | 两个 fd 就是普通 fd |
| ② | `fcntl(F_GETPIPE_SZ)` / `PIPE_BUF` / `F_SETPIPE_SZ` | **容量 65536、原子写上限 4096**，且容量可改 |
| ③ | 写端**全部关闭**后父进程再 `read` | 返回 **0**（EOF），**不阻塞** |
| ④ | `socketpair(AF_UNIX, SOCK_STREAM)` | 一对 fd 就能双向 |
| ⑤ | `mkfifo` + 父进程打开读 | FIFO 在文件树里有名字 |
| ⑥ | 四种通道的 ASCII 对照表 | 怎么选 |

```c
/* TLPI 第 2 章 §2.10 —— IPC 与同步：pipe / socketpair / FIFO 三种最小通道
 *
 * 编译：gcc -O0 -Wall -Wextra c2_10_ipc.c -o c2_10
 * 运行：./c2_10
 *
 * 本节要钉死的事实：
 *   ① pipe() 不经过文件系统，返回两个 fd：fd[0] 读端、fd[1] 写端，单向字节流。
 *   ② 读端全关后再写 → SIGPIPE（默认终止进程）；写端全关后读 → read 返回 0（EOF）。
 *   ③ FIFO 是「有名字的管道」，出现在文件树里，能被不相关的进程 open。
 *   ④ socketpair 天生双向，比 pipe 省一半 fd。
 *   ⑤ PIPE_BUF 是「保证原子」的单次写上限，超过就可能与其他写者交错。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <signal.h>
#include <limits.h>
#include <sys/wait.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <sys/stat.h>

int main(void)
{
    printf("=== ① pipe：最简单向通道 ===\n");
    int pfd[2];
    if (pipe(pfd) < 0) { perror("pipe"); return 1; }
    printf("  pipe() -> 读端 fd=%d  写端 fd=%d\n", pfd[0], pfd[1]);
    printf("  （两个 fd 都是普通 fd，能用在 select/poll/epoll 里）\n");

    fflush(NULL);
    pid_t pid = fork();
    if (pid == 0) {
        close(pfd[0]);                              /* 子进程只写 */
        const char *msg = "hello through pipe";
        ssize_t n = write(pfd[1], msg, strlen(msg));
        printf("  [child]  write(%d, \"%s\", %zu) = %zd 字节\n",
               pfd[1], msg, strlen(msg), n);
        close(pfd[1]);
        fflush(NULL);                               /* 子进程要打印就得自己 flush */
        _exit(0);
    }
    close(pfd[1]);                                  /* 父进程只读 */
    char buf[128];
    ssize_t n = read(pfd[0], buf, sizeof(buf) - 1);
    if (n < 0) { perror("read"); }
    else {
        buf[n] = '\0';
        printf("  [parent] read(%d, ...) = %zd 字节，内容 \"%s\"\n", pfd[0], n, buf);
    }
    int st; waitpid(pid, &st, 0);
    printf("  → 连 write 都不用调就用完了：字节流 + 内核里的环形缓冲区。\n");

    printf("\n=== ② pipe 的两个数字：容量与原子写上限 ===\n");
    int sz = fcntl(pfd[0], F_GETPIPE_SZ);
    printf("  fcntl(fd, F_GETPIPE_SZ) = %d 字节   （管道缓冲区容量）\n", sz);
    printf("  PIPE_BUF                = %d 字节   （保证原子性的单次写上限）\n", PIPE_BUF);
    printf("  → 单次 write ≤ PIPE_BUF 时，多个写者不会互相插入；\n");
    printf("     超过 PIPE_BUF 就可能被切开、与其他写者的数据交错。\n");
    printf("  → 容量可以改（写 /proc/sys/fs/pipe-max-size 以内）：\n");
    printf("     实测 fcntl(fd, F_SETPIPE_SZ, %d) = %d\n",
           16384, fcntl(pfd[0], F_SETPIPE_SZ, 16384));
    close(pfd[0]);

    printf("\n=== ③ 写端全关之后再读，得到 EOF 而不是阻塞 ===\n");
    int q[2];
    pipe(q);
    close(q[1]);                                    /* 立刻把写端关掉 */
    n = read(q[0], buf, sizeof(buf));
    printf("  写端已关闭，read() 返回 %zd  → 0 表示 EOF\n", n);
    printf("  → 这就是「管道对端退出了」的可靠信号，比轮询 PID 靠谱。\n");
    close(q[0]);

    printf("\n=== ④ socketpair：天生双向，只要一对 fd ===\n");
    int sv[2];
    if (socketpair(AF_UNIX, SOCK_STREAM, 0, sv) < 0) { perror("socketpair"); return 1; }
    printf("  socketpair(AF_UNIX, SOCK_STREAM) -> fd %d 与 %d\n", sv[0], sv[1]);
    fflush(NULL);
    pid_t p2 = fork();
    if (p2 == 0) {
        close(sv[1]);
        char r[64];
        ssize_t k = read(sv[0], r, sizeof(r) - 1);
        if (k > 0) { r[k] = '\0'; printf("  [child]  收到: \"%s\"\n", r); }
        const char *reply = "got it, thanks";
        write(sv[0], reply, strlen(reply));
        close(sv[0]);
        fflush(NULL);
        _exit(0);
    }
    close(sv[1]);
    const char *ask = "ping from parent";
    write(sv[0], ask, strlen(ask));
    char r2[64];
    ssize_t k = read(sv[0], r2, sizeof(r2) - 1);
    if (k > 0) { r2[k] = '\0'; printf("  [parent] 收到: \"%s\"\n", r2); }
    close(sv[0]);
    waitpid(p2, NULL, 0);
    printf("  → 一对 fd 就能来回说话，不用像 pipe 那样开两条。\n");

    printf("\n=== ⑤ FIFO：有名字的管道，能出现在文件树里 ===\n");
    const char *fpath = "/tmp/c2_10.fifo";
    unlink(fpath);
    if (mkfifo(fpath, 0644) < 0) { perror("mkfifo"); return 1; }
    struct stat fst;
    stat(fpath, &fst);
    printf("  mkfifo(\"%s\", 0644) 成功，st_mode=%04o  S_ISFIFO=%d\n",
           fpath, fst.st_mode & 07777, S_ISFIFO(fst.st_mode));
    printf("  → 它现在是一个「文件」，无关进程都能 open 它来会合。\n");

    fflush(NULL);
    pid_t p3 = fork();
    if (p3 == 0) {
        int w = open(fpath, O_WRONLY);               /* 会阻塞到有读者 */
        if (w < 0) { _exit(1); }
        const char *m = "via FIFO";
        write(w, m, strlen(m));
        close(w);
        _exit(0);
    }
    int rfd = open(fpath, O_RDONLY);                 /* 会阻塞到有写者 */
    if (rfd >= 0) {
        char r3[64];
        ssize_t k2 = read(rfd, r3, sizeof(r3) - 1);
        if (k2 > 0) { r3[k2] = '\0'; printf("  父进程从 FIFO 读到: \"%s\"\n", r3); }
        else printf("  读失败/空 (%zd)\n", k2);
        close(rfd);
    } else perror("open FIFO");
    waitpid(p3, NULL, 0);
    unlink(fpath);

    printf("\n=== ⑥ 四种通道对照 ===\n");
    printf("  %-14s %-10s %-18s %-16s %s\n", "mechanism", "direction",
           "named?", "cross-process?", "typical use");
    printf("  %-14s %-10s %-18s %-16s %s\n", "--------------", "----------",
           "------------------", "----------------", "-------------------");
    printf("  %-14s %-10s %-18s %-16s %s\n", "pipe", "one-way", "no",
           "via fork", "parent <-> child");
    printf("  %-14s %-10s %-18s %-16s %s\n", "FIFO", "one-way", "yes (path in fs)",
           "any process", "shell named pipe");
    printf("  %-14s %-10s %-18s %-16s %s\n", "socketpair", "two-way", "no",
           "via fork", "parent <-> child, duplex");
    printf("  %-14s %-10s %-18s %-16s %s\n", "UNIX socket", "two-way",
           "yes (path/abstract)", "any process", "local client/server");
    printf("\n  → 四者共用同一个底层结构：内核里的一对缓冲区 + 两个 fd。\n");
    printf("     「一切皆文件」在这里的兑现就是：它们都能 read/write/select。\n");
    return 0;
}
```

```bash

```

**解读**

1. **段 ② 的两个数字是「管道能塞多少」的完整答案，而且它们回答的是**两个不同的问题**：
   - `F_GETPIPE_SZ = 65536` —— **容量**：管道缓冲区总共能存 64KB，写满之后 `write` 会阻塞（或 `O_NONBLOCK` 时返回 `EAGAIN`）。
   - `PIPE_BUF = 4096` —— **原子写上限**：单次 `write` **≤ 4096 字节**时，内核保证这条数据不会被其他写者插入切开；超过这个数就可能交错。
   工程含义很直接：**多个写者共用一个管道时，每条消息不超过 4096 字节才能保证不被切开。** 这也是为什么很多日志管道/多进程日志聚合的缓冲区取 4KB。
2. **`F_SETPIPE_SZ` 实测返回 `16384`**，说明容量**可以调小也可以调大**（上限由 `/proc/sys/fs/pipe-max-size` 管，本环境是 `1048576`，见 [2.19](./2.19-proc-filesystem.md)）。调小常用于**背压**：缓冲区小，生产者就必须等消费者，天然限速。
3. **段 ③ 是本节最该记住的一条，也是很多诡异 bug 的答案**：写端**全部关闭**之后，读端 `read()` 返回 **0**（EOF），**不是阻塞、也不是错误**。
   - `read` 返回 0 是**唯一可靠的「对端走了」信号**——比 `kill(pid, 0)` 探活、比轮询 `/proc/<pid>` 都靠谱（那些都有竞态）。
   - 反过来，**如果 fd 泄漏导致写端没关干净，`read` 会永远阻塞**。这是「管道读不结束」这类 bug 的第一嫌疑：**检查写端是否真的都关了**（包括 fork 出来的子进程、以及被 `dup` 过的副本）。
4. **段 ④ 的 `socketpair` 解决了 `pipe` 的一个硬限制**：`pipe` 是**单向**的（要双向得开两条），而 `socketpair` 一对 fd 就双向。段 ⑥ 的表把四种通道对齐了，但真正要记的是最后那句：**四者共用同一个底层结构（内核里的一对缓冲区 + 两个 fd）**。所以它们都能 `read`/`write`/`select`/`epoll`——这正是「一切皆文件」在 IPC 上的兑现。
5. **段 ⑤ 的 `mkfifo` 是「有名字的管道」**。实测 `st_mode=0644 S_ISFIFO=1`（对应 [2.4](./2.4-directory-hierarchy.md) 的 7 种文件类型里的 `p`），文件树上出现了一个**名字**。因此它能把两个**毫无亲缘关系**的进程连起来——`pipe` 只能靠 `fork` 继承 fd，`FIFO` 靠路径名会合。shell 里的 `mkfifo /tmp/f && cmd1 > /tmp/f & cmd2 < /tmp/f` 就是靠这个。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 行情进程 → 策略进程零拷贝分发 | 共享内存 + 无锁环形队列（配内存屏障），避免 socket 拷贝 |
| 撮合引擎多进程协作 | 共享内存存订单簿，信号量/锁保护临界区 |
| 阻塞在 epoll 上的交易主循环 | 选 fd 型 IPC（eventfd/POSIX mq/socket），统一 epoll，避免「轮询 + SysV id」 |
| IPC 对象泄漏 | SysV/POSIX 命名对象进程退出不自动清理，崩溃后残留，须启动时 `IPC_RMID`/`unlink` |
| **`PIPE_BUF=4096` 决定多写者的消息尺寸上限** | 段 ② 实测。多进程往同一管道写日志时，**单条超过 4KB 就会被切开交错**——日志里出现的「半行拼接」怪象就是它 |
| **`read` 返回 0 = 对端退出，这是零成本的存活检测** | 段 ③ 实测。比 `kill(pid,0)` 更可靠（无竞态）。**但前提是写端真的关干净了**——fd 泄漏会让它永远不返回 0 |
| **管道容量 64KB 是天然的背压阀** | 段 ② 实测 65536。生产者写得比消费者快时，写满即阻塞 → 自动限速。要「更早限速」就 `F_SETPIPE_SZ` 调小；要「更晚阻塞」就调大（段 ② 实测可调到 16384，也可往上） |
| **`socketpair` 是父子进程双向通信的首选** | 段 ④。比「两条 pipe」少一半 fd，且天然 `epoll` 友好（[Ch63](../../chapter-63-alternative-i-o-models/notes/63.4-the-epoll-api.md)） |
| **FIFO 在嵌入式里常被 init 脚本用** | `mkfifo /var/run/xxx.fifo` 让互不相关的服务（如日志采集器与业务进程）会合。**注意 `open` 会阻塞**——忘了 `O_NONBLOCK` 会让启动卡住 |

## 自测题

<details>
<summary>1. 管道和消息队列的核心区别？</summary>

管道是**无边界字节流**——写入的字节流到读端是连续的，读 5 字节不知道它们是「一条消息」；消息队列是**有边界消息**——每条消息独立，读端一次读一条，还能按优先级消费（SysV 的 `mtype`、POSIX 的 `mq_prio`）。

本节段 ② 的 `PIPE_BUF = 4096` 是字节流模型下能拿到的最好保证：**单次写 ≤ 4096 时不会被切开**。要真正的消息边界，就得换消息队列。
</details>

<details>
<summary>2. 为什么共享内存是最快的 IPC？它有什么代价？</summary>

数据直接在内存共享，**没有内核拷贝**（管道/socket 都要经过内核缓冲区搬一次）。代价是**没有同步**——两个进程同时读写同一块内存会竞态，必须额外配信号量/锁/原子操作，而这恰恰是最容易出错的地方。

本节段 ⑥ 的表格里，「共享内存」这一类在传数据上都是 ✅，同步上都是 ❌——**它天生只管搬数据，不管谁先谁后**。
</details>

<details>
<summary>3. 管道的容量和「原子写上限」分别是多少？为什么是两个不同的数？</summary>

本节段 ② 实测：

```text
  fcntl(fd, F_GETPIPE_SZ) = 65536 字节   （管道缓冲区容量）
  PIPE_BUF                = 4096 字节   （保证原子性的单次写上限）
```

**它们回答两个不同的问题**：

- **65536 = 能存多少**。写满就阻塞（或 `O_NONBLOCK` 下 `EAGAIN`）。这是**背压**的数。
- **4096 = 一次写多少才不会被切开**。多个写者共用管道时，单次写 ≤ 4096 内核保证原子；超过就可能交错。这是**消息完整性**的数。

所以「多进程写同一管道」的设计约束是：**每条消息不超过 4096 字节**。段 ② 还实测了容量可改：`F_SETPIPE_SZ, 16384` 返回 `16384`。
</details>

<details>
<summary>4. 管道读到 0 字节是什么意思？为什么说它比轮询 PID 靠谱？</summary>

**意思是「写端全部关闭了」（EOF）**，不是错误、也不是阻塞。

本节段 ③ 实测：

```text
  写端已关闭，read() 返回 0  → 0 表示 EOF
  → 这就是「管道对端退出了」的可靠信号，比轮询 PID 靠谱。
```

`pipe(2)` NOTES 原文："If all file descriptors referring to the **write end** … have been closed, then `read()` will see **end-of-file (read() will return 0)**."

**为什么比轮询 PID 靠谱**：`kill(pid, 0)` 探活会受 PID 复用影响（旧进程死了、PID 被别人拿去，探活就误判为「还活着」）；`/proc/<pid>` 也存在「刚检查完就退出」的竞态。而 `read` 返回 0 是内核对**文件描述符**的直接判断——**只要还有任何一个写端 fd 开着，就不会是 0**。

⚠️ **反过来也是最常见的坑**：「管道读不结束」多半是**写端没关干净**——fork 出的子进程留了一个副本、或者某个 fd 被 `dup` 过没关。段 ①④ 的父子进程代码里那些 `close()` 不是装饰。
</details>

<details>
<summary>5. <code>socketpair</code> 比 <code>pipe</code> 好在哪？什么时候还是该用 <code>pipe</code>？</summary>

**好处是双向**：`pipe` 是单向的，要双向通信得开两个；`socketpair` 一对 fd 就双向（段 ④ 实测 `fd 3 与 4`）。两者都是 fd 型，都能进 `epoll`。

**还是该用 `pipe` 的情况**：

1. 只需要单向（如「子进程输出 → 父进程读取」）——`pipe` 语义更清晰，少一半 fd；
2. 想要 `PIPE_BUF` 这条**原子性保证**（`AF_UNIX` 的 `SOCK_STREAM` 语义更接近普通字节流；要消息边界得用 `SOCK_SEQPACKET` 或 `SOCK_DGRAM` 的 `socketpair`）；
3. 需要 `splice()` 这类**零拷贝管道操作**（[Ch63](../../chapter-63-alternative-i-o-models/notes/63.4-the-epoll-api.md)）。

段 ⑥ 的表格就是拿来按这四个维度（方向 / 有没有名字 / 能否跨无亲缘进程 / 典型用途）选的。
</details>

<details>
<summary>6. <code>mkfifo</code> 创建的 FIFO 和 <code>pipe</code> 有什么本质区别？</summary>

**FIFO 在文件树里有一个名字**——本节段 ⑤ 实测 `st_mode=0644 S_ISFIFO=1`，对应 [2.4](./2.4-directory-hierarchy.md) 的 7 种文件类型里的 `p`。

名字带来的关键能力：**让毫无亲缘关系的进程会合**。

| | `pipe` | `FIFO` |
|---|--------|--------|
| 有无名字 | ❌ 只能靠 `fork` 继承 fd | ✅ 路径名 |
| 谁能用 | 亲缘进程（或 `SCM_RIGHTS` 传 fd） | **任何进程**，只要能 `open` 那个路径 |
| 方向 | 单向 | 单向 |
| 底层 | 内核一对缓冲区 + 两个 fd | **同一个结构**（段 ⑥ 的结论） |

⚠️ **`open` 一个 FIFO 会阻塞**，直到另一端也 `open`（`mkfifo(3)` NOTES）。所以在嵌入式启动脚本里用 FIFO 必须考虑这一点——忘了 `O_NONBLOCK` 会让服务启动卡死在 `open` 上。
</details>

<details>
<summary>7. 我要同时等「网络 socket」和「子进程管道」有数据，该怎么设计？</summary>

用 **fd 型 IPC + epoll**——把 socket fd 和管道读端 fd 一起加入 `epoll`，统一阻塞在 `epoll_wait`。这就是「事件循环」模型。

本节的两条依据：

1. **段 ① 实测** `pipe() -> 读端 fd=3 写端 fd=4`，并明确写了「两个 fd 都是普通 fd，能用在 select/poll/epoll 里」；
2. **段 ⑥ 的结论**：`pipe`/`FIFO`/`socketpair`/`UNIX socket`**共用同一个底层结构**，因此都能 `read`/`write`/`select`。

**反过来**：若混用了 SysV 消息队列（**id 型**，不是 fd），它进不了 `epoll`，只能另开线程轮询，复杂度陡增。这就是「要统一事件循环就选 fd 型」的原因。
</details>
