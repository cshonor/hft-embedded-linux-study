## 本节讲什么

程序除了自己的代码，还依赖库（glibc、数学库、第三方 SDK）。本节回答三个问题：

1. 静态库（`.a`）和共享库（`.so`）有什么区别？
2. 程序启动时，动态链接器（`ld-linux.so`）做了什么？
3. 为什么共享库能「多进程共享一份物理内存」？

完整机制在 [Ch41](../../chapter-41-shared-libraries/README.md)-[42](../../chapter-42-shared-libraries-advanced/README.md)，这里建立「静态 = 编译时拷入 vs 共享 = 运行时映射」的核心区分。

本节要补的是**能在最小容器里做出来的验证**：**不靠 `ldd`、不靠 `readelf`，直接从 `/proc/self/maps` 数出加载了哪些 `.so`**，以及 `dlopen`/`dlsym`/`dlerror` 三个调用的真实错误文本。

## 要点

### 一、静态库 vs 共享库

| 维度 | 静态库（`.a`） | 共享库（`.so`） |
|------|---------------|----------------|
| 链接时机 | **编译链接时**拷入 | **运行时**由动态链接器映射 |
| 代码位置 | 每个可执行文件里各有一份 | 磁盘/内存**共享一份** |
| 文件体积 | 大（每个程序都嵌入） | 小（只存引用） |
| 更新 | 重编译所有程序 | 替换 `.so` 即可（ABI 兼容前提下） |
| 启动速度 | 快（无运行时解析） | 稍慢（要加载 + 符号重定位） |
| 依赖 | 无（自包含） | 需 `.so` 在运行时能找到 |

**编译对照**：

```bash
gcc -static  main.c -o main_static    # 静态：把所有库拷进 main_static
gcc          main.c -o main_dynamic   # 动态：只记录「依赖 libc.so.6」
```

### 二、动态链接器（`ld-linux.so`）

动态链接程序的可执行文件里，`ELF` 的 `DT_NEEDED` 项记录了「依赖哪些 .so」。启动时：

```
execve(dynamic_program)
   │
   ▼
内核读 ELF → 发现 PT_INTERP（解释器段）→ 加载 /lib64/ld-linux-x86-64.so.2
   │
   ▼
ld-linux.so 按 DT_NEEDED 逐个加载 .so → 用 mmap 映射进进程地址空间
   │
   ▼
符号重定位（PLT/GOT 填充）→ 跳转程序入口 main()
```

> **共享库靠 `mmap` 加载**（回接 [2.8](./2.8-memory-mappings.md)）：多个进程映射**同一个 `.so` 文件的同一物理页**，所以「N 个进程共享一份 libc 的物理内存」——这就是共享库省内存的本质。每个进程的 Data/BSS 段仍各自 COW 私有。

**注意加载顺序**：先跑起来的是 `ld-linux`，**不是 `main`**。`/proc/self/maps` 里 `ld-linux-x86-64.so.2` 出现在列表末尾，但它其实是最早被内核映射进来的（段 ① 实测可见）。

### 三、三级命名与工具

| 名称 | 形式 | 用途 |
|------|------|------|
| real name | `libfoo.so.1.2.3` | 真实文件，含完整版本 |
| soname | `libfoo.so.1` | 主版本（ABI 不变则稳定） |
| linker name | `libfoo.so` | 编译时 `-lfoo` 找的链接名（软链） |

工具：`ldd` 看依赖、`nm -D` 看导出符号、`readelf -d` 看 `DT_NEEDED`、`ldconfig` 维护 soname 软链缓存。

> 容器里常缺 `ldd`（它是个 shell 脚本，依赖 `bash`）。**不依赖任何外部命令的替代方案**就是本节 demo 段 ①：**读 `/proc/self/maps`，把 `.so` 路径去重**。

## 代码

### c2_9 从 `/proc/self/maps` 数 `.so` + `dlopen`/`dlsym`/`dlerror`

[`../code/c2_9_shared.c`](../code/c2_9_shared.c) 分三段：

1. **启动时已经加载了哪些共享库** —— `collect_sos()` 扫 `/proc/self/maps`，把 `.so` 路径**去重**收集起来（**不用 `ldd`、不用 `readelf`**），然后按名字逐个说明用途；顺便验证「libc 加载了 → `malloc` 一定可用」。
2. **运行时才决定加载谁** —— `dlopen("libm.so.6", RTLD_NOW)` + `dlsym("sqrt")`，调用拿到的函数指针；并演示两个关键细节：**`dlsym` 返回 NULL 不一定是错**（必须用 `dlerror()` 判）、以及**加载不存在的库时的错误文本长什么样**。
3. **静态 vs 动态对照表**（ASCII 表）+ 嵌入式/HFT 的取舍建议。

```c
/* TLPI 第 2 章 §2.9 —— 静态库与共享库：进程启动时到底加载了什么
 *
 * 编译：gcc -O0 -Wall -Wextra c2_9_shared.c -o c2_9 -ldl
 *      （glibc 2.34+ 里 dlopen/dlsym 已并入 libc，-ldl 只是兼容写法）
 * 运行：./c2_9
 *
 * 本节要钉死的事实：
 *   ① 可执行文件里不存 libc 的代码，只存一个「依赖清单」（DT_NEEDED）。
 *   ② 真正的加载由 ld-linux（动态链接器）在 exec 之后完成，
 *      所以 /proc/self/maps 里能直接看到一排 .so 的映射段。
 *   ③ dlopen/dlsym/dlerror 让程序在运行时才决定加载哪个库、调哪个符号 ——
 *      这是插件体系的底座。
 *   ④ 静态链接把库代码拷进可执行文件：启动快、无 .so 依赖，但体积大、无法共享内存页。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <dlfcn.h>

/* 收集 /proc/self/maps 里出现的 .so 路径（去重） */
static int collect_sos(char paths[][256], int max)
{
    FILE *f = fopen("/proc/self/maps", "r");
    if (!f) return 0;
    char line[512];
    int n = 0;
    while (fgets(line, sizeof(line), f)) {
        char *p = strchr(line, '/');
        if (!p) continue;
        char *nl = strchr(p, '\n');
        if (nl) *nl = '\0';
        if (!strstr(p, ".so")) continue;
        int dup = 0;
        for (int i = 0; i < n; i++)
            if (strcmp(paths[i], p) == 0) { dup = 1; break; }
        if (dup) continue;
        if (n < max) snprintf(paths[n++], 256, "%s", p);
    }
    fclose(f);
    return n;
}

int main(void)
{
    printf("=== ① 程序启动时已经加载了哪些共享库 ===\n");
    static char sos[64][256];
    int n = collect_sos(sos, 64);
    printf("  /proc/self/maps 里出现的 .so（已去重，共 %d 个）：\n", n);
    for (int i = 0; i < n; i++)
        printf("    [%d] %s\n", i, sos[i]);
    printf("  → 这些段在 exec 之后就由动态链接器 ld-linux 建好了，\n");
    printf("     不是程序自己 mmap 的。\n");

    printf("\n  逐个说明（按名字判断，不靠外部命令）：\n");
    for (int i = 0; i < n; i++) {
        const char *role =
            strstr(sos[i], "ld-linux")     ? "动态链接器本体（先跑起来的那个）" :
            strstr(sos[i], "libc.so")      ? "C 运行时：syscall 薄封装、malloc、stdio" :
            strstr(sos[i], "libm.so")      ? "数学库：sqrt/pow/sin…" :
            strstr(sos[i], "libpthread")   ? "线程库（glibc 2.34 起已并入 libc）" :
            strstr(sos[i], "libdl")        ? "dlopen/dlsym（glibc 2.34 起已并入 libc）" :
            strstr(sos[i], "libgcc_s")     ? "GCC 运行时（异常展开、除法辅助）" : "其他";
        printf("    %-46s %s\n", sos[i], role);
    }

    printf("\n  libc 一被加载，malloc 就一定也在：验证一下\n");
    void *m = malloc(16);
    printf("    malloc(16) = %p   %s\n", m, m ? "成功" : "失败");
    free(m);

    printf("\n=== ② 运行时才决定加载谁：dlopen / dlsym / dlerror ===\n");
    printf("  dlopen(\"libm.so.6\", RTLD_NOW) ...\n");
    void *h = dlopen("libm.so.6", RTLD_NOW);
    if (!h) {
        printf("    失败：%s\n", dlerror());
    } else {
        printf("    成功，handle = %p\n", h);

        double (*my_sqrt)(double) = (double (*)(double))dlsym(h, "sqrt");
        const char *err = dlerror();
        if (err) {
            printf("    dlsym(\"sqrt\") 失败：%s\n", err);
        } else {
            printf("    dlsym(\"sqrt\") = %p\n", (void *)my_sqrt);
            printf("    调用 my_sqrt(2.0) = %.15f\n", my_sqrt(2.0));
            printf("    调用 my_sqrt(16.0) = %.15f\n", my_sqrt(16.0));
            printf("    → 符号地址是运行时才拿到的，可执行文件里没有这个地址。\n");
        }

        /* 故意找一个不存在的符号 */
        dlerror();                      /* 先清空错误状态 */
        void *bad = dlsym(h, "no_such_symbol_xyz");
        err = dlerror();
        printf("    dlsym(\"no_such_symbol_xyz\") = %p\n", bad);
        printf("    dlerror() = \"%s\"\n", err ? err : "(null)");
        printf("    → dlsym 返回 NULL 不一定是错（符号值可能真是 0），\n");
        printf("       所以必须用 dlerror() 判错 —— 这是 dl 系列的标准姿势。\n");

        printf("    dlclose(h) = %d\n", dlclose(h));
    }

    printf("\n  再试一个不存在的库，看错误文本：\n");
    void *h2 = dlopen("libdefinitely_not_here.so.99", RTLD_NOW);
    printf("    dlopen(...) = %p\n", h2);
    printf("    dlerror() = \"%s\"\n", dlerror());
    printf("    → 错误文本里通常带「cannot open shared object file」和该库名，\n");
    printf("       排「缺 .so」类线上事故就看这一行。\n");

    printf("\n=== ③ 静态链接 vs 动态链接 ===\n");
    printf("  %-16s %-34s %s\n", "aspect", "dynamic (default)", "static (-static)");
    printf("  %-16s %-34s %s\n", "----------------", "----------------------------------",
           "----------------------------------");
    printf("  %-16s %-34s %s\n", "where is the code", "in separate .so, shared",
           "copied into the executable");
    printf("  %-16s %-34s %s\n", "startup cost", "ld-linux does relocation",
           "almost none");
    printf("  %-16s %-34s %s\n", "deploy deps", "must ship .so (glibc-version sensitive)",
           "single file, no deps");
    printf("  %-16s %-34s %s\n", "binary size", "small", "large");
    printf("  %-16s %-34s %s\n", "upgrade a library", "drop in a new .so (no rebuild)",
           "must rebuild everything");
    printf("  %-16s %-34s %s\n", "memory", "code pages shared across processes",
           "one copy per process");
    printf("\n  嵌入式/HFT 的取舍：\n");
    printf("    · 固件体积敏感、启动时间敏感 → 静态链接（或 musl 静态）；\n");
    printf("    · 要在多个进程间共享几 MB 的库代码页 → 动态链接；\n");
    printf("    · HFT 里更在意的是「首包前的加载抖动」，静态可把这部分确定性拉满。\n");

    printf("\n  静态链接会把 libc 一起塞进来，所以链接命令要显式写 -static：\n");
    printf("    gcc -O2 -static c2_9_shared.c -o c2_9_static\n");
    printf("  之后 file / ldd 会显示 \"not a dynamic executable\"，\n");
    printf("  /proc/self/maps 里也只剩匿名段，看不到 .so。\n");
    return 0;
}
```

编译与运行（**注意 `-ldl`**）：

```bash
gcc -O0 -Wall -Wextra -ldl -o c2_9_shared c2_9_shared.c && ./c2_9_shared
```

**解读**

1. **段 ① 的方法论价值大于数字本身**：只用 **2 行 `readline` + 一个去重** 就从 `/proc/self/maps` 数出了加载的库。这在**没有任何工具的最小容器/initramfs** 里特别有用——`ldd` 是个 shell 脚本（依赖 `bash`），`readelf` 在裁剪的 busybox 里也常没有，而 `/proc/self/maps` 永远在。实测结果只有 **2 个 `.so`**：`libc.so.6` 和 `ld-linux-x86-64.so.2`。
2. **`ld-linux-x86-64.so.2` 出现在列表里，是「它比 main 先跑」的直接证据**。内核读 ELF 时看到 `PT_INTERP` 段，就把动态链接器映射进来并跳过去；`main` 是**动态链接器准备完环境之后**才被调用的。所以「程序一启动就崩，连 `main` 的第一行都没打印」这类问题，根因往往在动态链接阶段（缺 `.so`、ABI 不匹配）。
3. **段 ② 的第一个细节是最容易写错的代码习惯**：`dlsym` 返回 `NULL` **不一定是错**——某个符号的值真的可能是 0（比如一个值为 0 的常量）。所以标准姿势是**先 `dlerror()` 清空、调用、再 `dlerror()` 判**。demo 实测 `dlerror()` 给出的原文是
   ```text
   "/lib/x86_64-linux-gnu/libm.so.6: undefined symbol: no_such_symbol_xyz"
   ```
   它同时告诉了你**是哪一行查询、哪个库、哪个符号**——比任何自造的日志都好用。
4. **段 ② 的第二个细节给出一条排障钥匙**：加载不存在的库时 `dlerror()` 的文本是
   ```text
   "libdefinitely_not_here.so.99: cannot open shared object file: No such file or directory"
   ```
   **认这几个关键词**：`cannot open shared object file` = 缺库；`undefined symbol` = 有库但符号不匹配；`version 'GLIBC_2.xx' not found` = 有库但版本太老。线上「启动即崩」的三类根因就靠这一行分流。
5. **段 ③ 的静态链接那两行值得真去跑一遍**。demo 里写了方法：`gcc -O2 -static ...`，之后 `file`/`ldd` 会说 "not a dynamic executable"，**`/proc/self/maps` 里再也看不到 `.so`**。这就是段 ① 的方法给出的「静态链接确实是自包含」的可验证结论——不用信文档，自己数一遍。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 启动延迟 | 动态链接要加载 N 个 .so + 重定位，冷启动慢；可 `LD_BIND_NOW` 或静态链接减少运行期解析抖动 |
| 符号重定位毛刺 | 默认**延迟绑定**（首次调用才解析 PLT），热路径首次调库函数会有一次解析开销 |
| 插桩观测 | `LD_PRELOAD` 注入自定义 .so 拦截库调用（ltrace/性能打点原理，见 [03.6/Ch5](../../../03.6-userspace-debugging/chapter-05-behavior/notes/03-ltrace-library-calls.md)） |
| 部署一致性 | 目标机 `.so` 版本与编译机不一致 → ABI 不兼容崩溃，需 soname 管版本 |
| **`/proc/self/maps` 是「无工具环境」的唯一出口** | 段 ① 只用 2 个系统调用就替代了 `ldd`。嵌入式 rootfs 常常没有 `ldd`/`readelf`/`bash`，这个手法能直接查「到底加载了什么」 |
| **静态链接消除「首包抖动」** | 段 ③ 的 `startup cost: ld-linux does relocation` vs `almost none`。HFT 交易进程常见的做法正是**静态链接或 musl 静态**，把「加载阶段的不确定性」压掉 |
| **`LD_PRELOAD` 是嵌入式抓 bug 的利器** | 在目标机上 `LD_PRELOAD=./trace.so ./app` 就能拦截 `malloc`/`open`/`send`。**注意它对静态链接程序无效**（没有 PLT/GOT）——这正反两面都由本节段 ③ 的机制解释 |
| **`GLIBC_2.xx not found` 是交叉编译的高频事故** | 段 ② 教了认错误文本。用较新 SDK 交叉编译、拷到较旧的 ARM 设备上跑，报的就是这个——**和「文件不存在」是两回事**，解法是换旧 sysroot 或静态链接 |
| **musl vs glibc 的 soname 不兼容** | 二者都叫 `libc.so.6` 但**符号集不同**。把 glibc 编的 `.so` 拷进 Alpine（musl）容器，症状就是段 ② 那类 `undefined symbol` |

## 自测题

<details>
<summary>1. 静态链接的程序能在目标机上独立运行吗？共享库呢？</summary>

静态链接**能**——所有库代码已拷进可执行文件，目标机不需要任何 `.so`；共享库**不能**——目标机必须有对应的 `.so`（且版本兼容），否则启动时 `ld-linux.so` 报「error while loading shared libraries」。

本节段 ① 给了一个**不用工具就能验证**的方法：静态链接后 `/proc/self/maps` 里**再也看不到 `.so`**（demo 段 ③ 末尾写了验证命令）。这就是「自包含」的可观测定义。
</details>

<details>
<summary>2. 为什么共享库能「多进程共享一份物理内存」？</summary>

因为 `.so` 的 Text 段（代码）是只读的，内核用 `mmap` 把多个进程的虚拟地址映射到**同一个物理页**（文件的页缓存）。所以 100 个进程跑起来，libc 代码在物理内存里只有一份。各进程的全局变量（Data/BSS）则 COW 各自私有。

这与 [2.8](./2.8-memory-mappings.md) 段 ③ 的「两个 `MAP_SHARED` 映射互相可见」是**同一个机制**——只是 `.so` 用的是 `MAP_PRIVATE`（写时 COW），所以**共享的是读、隔离的是写**。

本节段 ① 实测：本环境进程里只有 **2 个 `.so`**（`libc.so.6` + `ld-linux`），跨进程共享的就是这两份代码页。
</details>

<details>
<summary>3. <code>-static</code> 和动态链接，启动速度哪个快？为什么？</summary>

**静态快。** 动态链接启动时要：加载 `ld-linux.so` → 逐个打开 `DT_NEEDED` 的 `.so` → 符号重定位（PLT/GOT）→ 才进 `main`。

代价是文件大、无法享受 `.so` 的安全更新、也不能 `LD_PRELOAD` 插桩。

本节段 ③ 的对照表把六个维度并排了，其中 startup 一栏就是 `ld-linux does relocation` vs `almost none`。`ld.so(8)` 的 `LD_BIND_NOW` 能把「延迟绑定」取消，从而把重定位集中到启动阶段（见下题）。
</details>

<details>
<summary>4. 什么是「延迟绑定」（lazy binding）？它带来什么副作用？</summary>

默认情况下，共享库函数在**首次被调用时**才通过 PLT/GOT 解析真实地址（`ld-linux.so` 的 `_dl_runtime_resolve`）。好处是启动快；副作用是**首次调用有额外解析开销**。

HFT 热路径若不能接受这个抖动，用 `-Wl,-z,now`（等价于 `LD_BIND_NOW=1`）在启动时一次性全部绑定。`ld.so(8)` 原文："**LD_BIND_NOW** … causes the dynamic linker to resolve all symbols at program startup instead of deferring."

⚠️ 「一次性绑定」会把开销从「散落在运行期」变成「集中在启动期」——**总开销差不多，但确定性变好了**。这正是 HFT 愿意换的。
</details>

<details>
<summary>5. <code>LD_PRELOAD</code> 是什么原理？对静态链接程序有效吗？</summary>

`LD_PRELOAD=/path/my.so ./prog` 让动态链接器**优先加载** `my.so`，它导出的同名符号（如 `malloc`、`open`）会「覆盖」后续 `.so` 的同名符号（**符号介入 / symbol interposition**）。所以能拦截库调用做打点/追踪——`ltrace` 的 PLT 拦截、性能分析工具都基于类似机制。

**对静态链接程序无效**——静态链接没有 PLT/GOT、也没有 `ld-linux.so` 介入的机会。这条边界正好由本节段 ③ 的机制解释。
</details>

<details>
<summary>6. 启动时报 <code>error while loading shared libraries</code>，怎么快速定位缺哪个库？</summary>

本节段 ② 的实测给了一条捷径——**看 `dlerror()` / 加载器的错误文本关键词**：

```text
    dlerror() = "libdefinitely_not_here.so.99: cannot open shared object file: No such file or directory"
```

三类文本对应三类根因：

| 错误文本关键词 | 根因 | 解法 |
|----------------|------|------|
| `cannot open shared object file` | **缺库** | 装上或 `LD_LIBRARY_PATH` 指到目录 |
| `undefined symbol` | 有库但**符号不匹配**（ABI 变了 / musl vs glibc） | 用配套版本重建 |
| `version 'GLIBC_2.xx' not found` | 有库但**版本太老** | 换旧 sysroot 编译，或静态链接 |

定位「到底加载了哪些库」用本节段 ① 的方法（读 `/proc/self/maps`），**不依赖 `ldd`**——在缺库的破系统上 `ldd` 本身可能就跑不起来。
</details>

<details>
<summary>7. <code>dlopen</code> 之后忘记 <code>dlclose</code>，会怎样？</summary>

`dlclose` 会把该 `.so` 的**引用计数**减一，减到 0 才真正卸载（`munmap` 它的段）。忘记 `dlclose` 等于永久多持有一份库代码页的引用——**对于「加载一次、一直用」的服务进程其实无所谓**（进程退出时一起释放），但如果是在循环里反复 `dlopen` 不同版本/插件的场景（**插件系统、热更新**），就会稳定泄漏地址空间。

本节段 ② 实测 `dlclose(h) = 0`（成功）。更值得记住的是括号里的那组数字——`handle = 0x2d47b8f0`、`dlsym("sqrt") = 0x7e7eb14296d0`——**符号地址是运行期才确定的，可执行文件里根本没有这个常量**，这就是「运行时链接」四个字的字面含义。
</details>
