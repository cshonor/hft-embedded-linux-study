# 2.9 静态库与共享库（Static & Shared Libraries）

> 本章：[TLPI 第 02 章 — Fundamental Concepts](../README.md)

## 本节讲什么

程序除了自己的代码，还依赖库（glibc、数学库、第三方 SDK）。本节回答三个问题：

1. 静态库（`.a`）和共享库（`.so`）有什么区别？
2. 程序启动时，动态链接器（`ld-linux.so`）做了什么？
3. 为什么共享库能「多进程共享一份物理内存」？

完整机制在 Ch41-42，这里建立「静态 = 编译时拷入 vs 共享 = 运行时映射」的核心区分。

---

## 1. 静态库 vs 共享库

| 维度 | 静态库（`.a`） | 共享库（`.so`） |
|------|---------------|----------------|
| 链接时机 | **编译链接时**拷入 | **运行时**由动态链接器映射 |
| 代码位置 | 每个可执行文件里各有一份 | 磁盘/内存**共享一份** |
| 文件体积 | 大（每个程序都嵌入） | 小（只存引用） |
| 更新 | 重编译所有程序 | 替换 `.so` 即可（ABI 兼容前提下） |
| 启动速度 | 快（无运行时解析） | 稍慢（要加载 + 符号重定位） |
| 依赖 | 无（自包含） | 需 `.so` 在运行时能找到 |

**编译对照**：

```bash
gcc -static  main.c -o main_static    # 静态：把所有库拷进 main_static
gcc          main.c -o main_dynamic   # 动态：只记录「依赖 libc.so.6」
```

## 2. 动态链接器（`ld-linux.so`）

动态链接程序的可执行文件里，`ELF` 的 `DT_NEEDED` 项记录了「依赖哪些 .so」。启动时：

```
execve(dynamic_program)
   │
   ▼
内核读 ELF → 发现 PT_INTERP（解释器段）→ 加载 /lib64/ld-linux-x86-64.so.2
   │
   ▼
ld-linux.so 按 DT_NEEDED 逐个加载 .so → 用 mmap 映射进进程地址空间
   │
   ▼
符号重定位（PLT/GOT 填充）→ 跳转程序入口 main()
```

> **共享库靠 `mmap` 加载**（回接 2.8）：多个进程映射**同一个 `.so` 文件的同一物理页**，所以「N 个进程共享一份 libc 的物理内存」——这就是共享库省内存的本质。每个进程的 Data/BSS 段仍各自 COW 私有。

## 3. 三级命名与工具

| 名称 | 形式 | 用途 |
|------|------|------|
| real name | `libfoo.so.1.2.3` | 真实文件，含完整版本 |
| soname | `libfoo.so.1` | 主版本（ABI 不变则稳定） |
| linker name | `libfoo.so` | 编译时 `-lfoo` 找的链接名（软链） |

工具：`ldd` 看依赖、`nm -D` 看导出符号、`readelf -d` 看 `DT_NEEDED`、`ldconfig` 维护 soname 软链缓存。

## 4. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 启动延迟 | 动态链接要加载 N 个 .so + 重定位，冷启动慢；可 `LD_BIND_NOW` 或静态链接减少运行期解析抖动 |
| 符号重定位毛刺 | 默认**延迟绑定**（首次调用才解析 PLT），热路径首次调库函数会有一次解析开销 |
| 插桩观测 | `LD_PRELOAD` 注入自定义 .so 拦截库调用（ltrace/性能打点原理，见 03.6 Ch5） |
| 部署一致性 | 目标机 `.so` 版本与编译机不一致 → ABI 不兼容崩溃，需 soname 管版本 |

## 5. 代码示例

```c
/* main.c —— 依赖 glibc（动态链接） */
#include <stdio.h>
#include <math.h>
int main(void) {
    printf("sqrt(2)=%f\n", sqrt(2.0));  /* sqrt 在 libm.so.6，需 -lm */
    return 0;
}
```

```bash
gcc main.c -lm -o main            # 动态链接 libc + libm
ldd main                          # 查看依赖的 .so
readelf -d main | grep NEEDED     # 看 DT_NEEDED 项
```

<details>
<summary>代码自测（Q&A）</summary>

**Q1：静态链接的程序能在目标机上独立运行吗？共享库呢？**
A：静态链接**能**——所有库代码已拷进可执行文件，目标机不需要任何 .so；共享库**不能**——目标机必须有对应的 `.so`（且版本兼容），否则启动时 `ld-linux.so` 报「error while loading shared libraries」。

**Q2：为什么共享库能「多进程共享一份物理内存」？**
A：因为 `.so` 的 Text 段（代码）是只读的，内核用 `mmap` 把多个进程的虚拟地址映射到**同一个物理页**（文件的页缓存）。所以 100 个进程跑起来，libc 代码在物理内存里只有一份。各进程的全局变量（Data/BSS）则 COW 各自私有。

**Q3：`-static` 和动态链接，启动速度哪个快？为什么？**
A：静态快。动态链接启动时要：加载 `ld-linux.so` → 逐个打开 `DT_NEEDED` 的 .so → 符号重定位（PLT/GOT）→ 才进 `main`。静态链接跳过了这些，但代价是文件大、无法享受 .so 的安全更新、也不能 `LD_PRELOAD` 插桩。

**Q4：什么是「延迟绑定」（lazy binding）？它带来什么副作用？**
A：默认情况下，共享库函数在**首次被调用时**才通过 PLT/GOT 解析真实地址（`ld-linux.so` 的 `_dl_runtime_resolve`）。好处是启动快；副作用是**首次调用有额外解析开销**。HFT 热路径若不能接受这个抖动，用 `-Wl,-z,now`（`LD_BIND_NOW`）在启动时一次性绑定。

**Q5：`LD_PRELOAD` 是什么原理？**
A：`LD_PRELOAD=/path/my.so ./prog` 让动态链接器**优先加载** `my.so`，它导出的同名符号（如 `malloc`、`open`）会「覆盖」后续 .so 的同名符号（符号介入）。所以能拦截库调用做打点/追踪——`ltrace` 的 PLT 拦截、性能分析工具都基于类似机制。静态链接程序无 PLT，故 `LD_PRELOAD` 无效。

</details>
