## 本节讲什么

会话（session）是「进程组之上的容器」，把一组进程组与一个**控制终端**绑定。本节回答三个问题：

1. 会话（SID）和进程组（PGID）是什么关系？`setsid()` 到底做了什么？
2. 「控制终端」为什么会发出 `Ctrl+C` / `SIGHUP`，信号到底发给谁？
3. 守护进程为什么要 `fork()` + `setsid()` 两步脱离终端？

完整机制在 [Ch34](../../chapter-34-process-groups-sessions/README.md)，这里建立「**会话 = 终端关联单位**」的核心心智。

本节要补的是**「有终端」和「在终端上」是两回事的实测**：`ctermid()` 打印 `"/dev/tty"`，但 `access("/dev/tty")` 返回 `-1`——**标准答案路径不等于设备存在**。判断「是不是终端」只有 `isatty()` 一个可靠依据。

## 要点

### 一、三层结构：会话 > 进程组 > 进程

```
会话（session, SID = 会话首领的 PID）
 ├── 前台进程组  ←─ 唯一能读终端输入、接收 Ctrl+C 的组
 ├── 后台进程组 1
 ├── 后台进程组 2
 └── ...
```

| 概念 | 说明 |
|------|------|
| **SID** | 会话 ID，**= 会话首领的 PID** |
| **会话首领** | 调用 `setsid()` 创建会话的进程 |
| **控制终端** | 会话可（可选）关联一个终端设备；`/dev/tty` 是它的**别名路径** |
| **控制进程** | 会话首领（若它有控制终端，就叫控制进程） |
| **前台进程组** | 会话内**至多一个**，终端输入与终端信号都归它 |

```c
pid_t setsid(void);          /* 新建会话，调用者成为会话首领 */
pid_t getsid(pid_t pid);     /* 取会话 ID；getsid(0) = 取自己的 */
```

### 二、内核里的 session：`task->signal->pids[PIDTYPE_SID]`

会话 ID 和进程组 ID 一样，存在进程的 `signal_struct` 里，按 `PIDTYPE_*` 索引取：

```c
/* include/linux/sched/signal.h:697 */
static inline struct pid *task_session(struct task_struct *task)
{ return task->signal->pids[PIDTYPE_SID]; }

/* include/linux/sched/signal.h:692 */
static inline struct pid *task_pgrp(struct task_struct *task)
{ return task->signal->pids[PIDTYPE_PGID]; }
```

取**数值** ID 走 `task_session_vnr()`（`include/linux/sched.h:1626`，内部是 `__task_pid_nr_ns(tsk, PIDTYPE_SID, NULL)`）。

**关键理解**：`pids[]` 是一个**数组**——`PIDTYPE_PID` / `PIDTYPE_TGID` / `PIDTYPE_PGID` / `PIDTYPE_SID` 各存一份 `struct pid` 引用。所以一个进程**同时**「属于」某个进程组和某个会话，但这是**两套独立的归属标签，不是树形嵌套**：

```
task_struct
 └── signal_struct
      └── pids[4]  ──┬─[PIDTYPE_PID ]→ struct pid(自己的 tid)
                     ├─[PIDTYPE_TGID]→ struct pid(线程组)
                     ├─[PIDTYPE_PGID]→ struct pid(进程组)   ← 2.13
                     └─[PIDTYPE_SID ]→ struct pid(会话)     ← 本节
```

这解释了一个常见困惑：**「进程组属于会话」在 C 代码里找不到指针**——它们的父子关系是通过「成员集合」隐含的（会话的成员 = 那些 `SID` 相同的进程），不是通过结构体嵌套。也就顺带解释了为什么 `setsid()` 要**同时**新建进程组：否则新会话会挂在旧会话的某个组上，层级就乱了。

### 三、`setsid()` 做三件事，且**拒绝**组长调用

| 动作 | 结果 |
|------|------|
| ① 新建会话 | 调用者成为**会话首领**，`SID == 自己的 PID` |
| ② 新建进程组 | 调用者成为**新组组长**，`PGID == 自己的 PID`（新组里只有它） |
| ③ 断开控制终端 | 若原本有控制终端，**断开**且不再拥有 |

但有一个硬前提，`setsid(2)` 原文：

> **EPERM** The process group ID of any process equals the PID of the calling process. **Thus, in particular, `setsid()` fails if the calling process is already a process group leader.**

**为什么禁止组长？** 若允许，调用者的 PGID 会同时成为「一个进程组 ID」和「一个新会话 ID」——同一个数字在两层结构里各指一物，内核的 `struct pid` 引用关系会产生歧义。于是内核直接禁止（`EPERM`）。

**连带后果**：`setsid()` 之后自己就是新组组长了，所以**再调一次必然 `EPERM`**（本节段 ④ 实测了这一点）。

### 四、控制终端：信号的源头

控制终端**不是「进程的属性」，而是「会话的属性」**。终端驱动（tty）收到按键后，把字符转成信号发给**会话的前台进程组**：

| 按键 / 事件 | 产生的信号 | 发给谁 |
|-------------|-----------|--------|
| `Ctrl+C`（intr） | SIGINT | 前台进程组 |
| `Ctrl+Z`（susp） | SIGTSTP | 前台进程组（暂停） |
| `Ctrl+\`（quit） | SIGQUIT | 前台进程组（默认 core） |
| 终端断开（hangup） | **SIGHUP** | **会话首领（控制进程）** |

> **SIGHUP 是关键**：终端关闭（ssh 断开、串口拔出、pty 主端关闭）时，内核向会话的**控制进程**发 SIGHUP。默认动作是终止——这就是「ssh 一断，前台任务全挂」的根因。要躲开，得用 `nohup`（只是忽略信号）/ `setsid`（彻底脱离）/ `tmux`（另起会话托管）。

### 五、一个必须记住的判据：`ctermid()` 不是证据

`ctermid()` 返回的是**「控制终端的标准路径」`/dev/tty`**——这是**规范定的常量字符串**，它**不检查设备是否存在**。要判断「当前进程有没有终端」，只有两个可靠手段：

| 手段 | 语义 |
|------|------|
| `isatty(fd)` | 该 fd 是否指向终端（`1` = 是，`0` = 不是，且置 `errno=ENOTTY`） |
| `ttyname(fd)` | 该 fd 对应终端的**真实路径**；不是终端则返回 `NULL` |

本节段 ② 的实测就是这条：`ctermid()` 打印 `"/dev/tty"`，但 `access("/dev/tty", F_OK) = -1`（`ENOENT`），`isatty(0) = 0`。**在脚本里用 `ctermid()` 判断「有没有终端」是错的**。

## 代码

### c2_14 会话：三层 ID / 控制终端 / setsid 的成败条件 / daemon 六步

[`../code/c2_14_setsid.c`](../code/c2_14_setsid.c) 分六段：

| 段 | 做什么 | 钉死什么 |
|----|--------|----------|
| ① | 打印 `pid`/`ppid`/`pgid`/`sid` 并做两个相等判断 | `pid==pgid` ⇒ 组长；`pid==sid` ⇒ 会话首领 |
| ② | `ttyname()` / `ctermid()` / `access("/dev/tty")` / `isatty()` 四连 | **`ctermid()` 是常量路径，不是证据** |
| ③ | 本进程（组长）直接调 `setsid()` | **`EPERM(1)`** |
| ④ | `fork` 出子进程（非组长）→ `setsid()` → **再调一次** | 成功建会话；第二次 `EPERM` |
| ⑤ | daemon 化的六步流程 + 每步目的 | 为什么要 double fork |
| ⑥ | 探测 `/dev/tty` / `/dev/ptmx`，划清容器实测边界 | 诚实报告「哪些验不到」 |

```c
/* TLPI 第 2 章 §2.14 —— 会话、控制终端：daemon 化的三步
 *
 * 编译：gcc -O0 -Wall -Wextra c2_14_setsid.c -o c2_14
 * 运行：./c2_14
 *
 * 本节要钉死的事实：
 *   ① 层级是「会话 > 进程组 > 进程」：sid、pgid、pid 三个数字定位一个进程。
 *   ② 会话首领（session leader）拥有控制终端（controlling terminal）。
 *   ③ setsid() 新建会话 + 新进程组并丢掉控制终端；但**进程组组长调它会 EPERM**。
 *   ④ 所以 daemon 的标准姿势是「先 fork 让子进程不再是组长，再 setsid」。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/wait.h>
#include <sys/types.h>

int main(void)
{
    printf("=== ① 三组 ID：这个进程站在哪一层 ===\n");
    printf("  pid        = %d\n", (int)getpid());
    printf("  ppid       = %d\n", (int)getppid());
    printf("  pgid       = %d   （进程组）\n", (int)getpgrp());
    printf("  sid        = %d   （会话）\n", (int)getsid(0));
    printf("  pid==pgid  ? %s  → 本进程是进程组组长\n", getpid() == getpgrp() ? "YES" : "no");
    printf("  pid==sid   ? %s  → 本进程是会话首领\n", getpid() == getsid(0) ? "YES" : "no");

    printf("\n=== ② 控制终端：有还是没有 ===\n");
    printf("  ttyname(STDIN_FILENO) = %s\n",
           ttyname(STDIN_FILENO) ? ttyname(STDIN_FILENO) : "(null)  → 没有控制终端");
    char ct[64];
    ctermid(ct);
    printf("  ctermid()             = \"%s\"\n", ct);
    printf("    ↑ 注意：这只是「标准答案路径」，不代表它真的存在。实测：\n");
    printf("    access(\"/dev/tty\")   = %d", access("/dev/tty", F_OK));
    if (access("/dev/tty", F_OK) < 0) printf("  （%s）", strerror(errno));
    printf("\n");
    errno = 0;
    printf("    isatty(0) = %d   isatty(1) = %d   （0 = 不是终端）\n",
           isatty(0), isatty(1));
    printf("  -> 本环境下 stdin/stdout 是管道/套接字，所以没有终端语义。\n");
    printf("     「是不是终端」用 isatty() 判断，不要拿 ctermid() 当证据。\n");

    printf("\n=== ③ 进程组组长调 setsid() 会 EPERM ===\n");
    fflush(NULL);
    errno = 0;
    pid_t r = setsid();
    printf("  本进程（pid==pgid，是组长）调 setsid() → 返回 %d", (int)r);
    if (r < 0) printf("  errno=%d (%s)", errno, strerror(errno));
    printf("\n");
    printf("  -> EPERM(%d)：内核拒绝「组长新建会话」，否则组和会话的对应关系会乱。\n", EPERM);
    errno = 0;

    printf("\n=== ④ 正确姿势：先 fork，让子进程当「非组长」再 setsid ===\n");
    fflush(NULL);
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }

    if (pid == 0) {
        /* ---- 子进程：此刻不是组长（它的 pid 是新号，但 pgid 还是父的） ---- */
        printf("  [child] fork 后：pid=%d  pgid=%d  sid=%d\n",
               (int)getpid(), (int)getpgrp(), (int)getsid(0));

        errno = 0;
        pid_t ns = setsid();
        if (ns < 0) {
            printf("  [child] setsid() 失败 errno=%d (%s)\n", errno, strerror(errno));
        } else {
            printf("  [child] setsid() = %d  → 新会话成立了\n", (int)ns);
        }
        printf("  [child] setsid 之后：pid=%d  pgid=%d  sid=%d\n",
               (int)getpid(), (int)getpgrp(), (int)getsid(0));
        printf("  [child] 三者相等 → 我既是会话首领又是组长，且已脱离原控制终端\n");

        /* 再调一次会怎样？此刻已经是组长了 */
        errno = 0;
        pid_t again = setsid();
        printf("  [child] 再调一次 setsid() → %d", (int)again);
        if (again < 0) printf("  errno=%d (%s)", errno, strerror(errno));
        printf("\n  [child] -> 连会话首领自己也改不了自己所在的会话，语义上说得通。\n");
        errno = 0;

        printf("  [child] ttyname(0) = %s\n",
               ttyname(0) ? ttyname(0) : "(null)  → 确实没有控制终端了");
        fflush(NULL);
        _exit(0);
    }

    int st;
    if (waitpid(pid, &st, 0) < 0) perror("waitpid");
    else printf("  父进程：子进程 %d 退出码 %d\n", (int)pid, WEXITSTATUS(st));

    printf("\n=== ⑤ daemon 化标准流程（为什么是这几步）===\n");
    printf("  ① fork() 后父进程 _exit(0)\n");
    printf("     目的：让子进程变成孤儿，被 init 收养，且**不再是进程组组长**\n");
    printf("  ② setsid()\n");
    printf("     目的：新会话 + 新进程组 + 丢掉控制终端 → Ctrl+C/SIGHUP 再也找不到它\n");
    printf("  ③ （可选）再 fork 一次\n");
    printf("     目的：确保永远不是会话首领，也就永远拿不到控制终端\n");
    printf("  ④ chdir(\"/\")\n");
    printf("     目的：不占住某个挂载点，免得 umount/文件系统维护被卡\n");
    printf("  ⑤ 把 0/1/2 重定向到 /dev/null\n");
    printf("     目的：免得某个已关闭的终端 fd 被误用，或输出把磁盘写爆\n");
    printf("  ⑥ 关掉继承来的、不需要的 fd（多进程环境下应该用 O_CLOEXEC 预防）\n");

    printf("\n=== ⑥ 本环境的实测边界 ===\n");
    errno = 0;
    int tty_ok = access("/dev/tty", F_OK);
    printf("  · access(\"/dev/tty\", F_OK) = %d", tty_ok);
    if (tty_ok < 0) printf("  errno=%d (%s)", errno, strerror(errno));
    printf("\n");
    errno = 0;
    int ptmx_ok = access("/dev/ptmx", F_OK);
    printf("  · access(\"/dev/ptmx\", F_OK) = %d", ptmx_ok);
    if (ptmx_ok < 0) printf("  errno=%d (%s)", errno, strerror(errno));
    printf("\n");
    errno = 0;
    printf("  · 所以「终端」这类实验只能验到语义层：\n");
    printf("    pid/pgid/sid 三个数字的关系、setsid 的成败与 EPERM 条件，都是真的；\n");
    printf("    但「Ctrl+C 打到哪个组」需要真终端，容器里无法复现。\n");
    return 0;
}
```

**解读**

1. **段 ② 的四行输出是本节的「思维疫苗」**，四行合起来讲一件事：

   | 调用 | 输出 | 说明什么 |
   |------|------|----------|
   | `ttyname(0)` | `(null)` | **没有**终端 |
   | `ctermid()` | `"/dev/tty"` | 只是**规范常量**，与是否存在无关 |
   | `access("/dev/tty")` | `-1` `ENOENT` | **设备确实不存在** |
   | `isatty(0)` / `isatty(1)` | `0` / `0` | 唯一可靠的「是不是终端」判据 |

   所以「`ctermid()` 返回了路径」**完全不意味着**有终端。写启动脚本时判断交互性，用 `test -t 0`（等价 `isatty`）而不是比对 `ctermid()` 的输出。

2. **段 ① 中 `pid == pgid == sid == 2` 三者全等**，说明 CE 容器里这个测试程序**本身就是会话首领**——它是被 `setsid()` 出来的。这也是它能直接触发段 ③ `EPERM` 的**前提**：只有「组长」调 `setsid()` 才 `EPERM`。若容器换了启动方式（比如直接从 shell `fork` 出来），段 ③ 可能就成功了，整节结论会变。**读实测输出时要问「这个结论依赖什么前提」**——这里的前提就是 `pid == pgid`。

3. **段 ④ 的「再调一次 `EPERM`」是本节的隐藏彩蛋**，它证明了一个非平凡的语义：

   ```
   fork 后      : pid=3  pgid=2  sid=2   ← 非组长（pgid≠pid），setsid 可用
   setsid 之后  : pid=3  pgid=3  sid=3   ← 自己成了新组组长，pgid==pid
   再调 setsid  : EPERM                  ← 因为现在自己是组长了
   ```

   **`setsid()` 自己把自己变成了「不能调 `setsid()` 的进程」**。这不是 bug，是「组长不能建会话」这条规则的一致推论——也正是 daemon 流程里**必须先 `fork`** 的根本原因（不能再靠「自己再调一次」补救）。

4. **段 ⑤ 的六步里，只有前两步是「内核要求」，后四步是「工程惯例」**：

   | 步骤 | 类别 | 不做会怎样 |
   |------|------|-----------|
   | ① `fork`（让子进程非组长） | **内核要求**（否则 `EPERM`） | `setsid` 失败，daemon 化失败 |
   | ② `setsid()` | **内核要求**（脱离终端） | ssh 一断就被 `SIGHUP` 杀 |
   | ③ 再 `fork` 一次 | 工程惯例 | 会话首领可能在后续打开 tty 时**重新获得**控制终端 |
   | ④ `chdir("/")` | 工程惯例 | 占住某挂载点，`umount` / 文件系统维护被卡 |
   | ⑤ 0/1/2 → `/dev/null` | 工程惯例 | 误用已关闭的终端 fd；或输出把磁盘写爆 |
   | ⑥ 关掉无关 fd | 工程惯例 | 泄漏 fd（更高明的做法是起源于 `O_CLOEXEC`/`closefrom`） |

5. **段 ⑥ 是「实测边界」的诚实标注**——本节**测不到**「`Ctrl+C` 打到哪个组」（需要真 tty 与真按键），所以没有伪造这部分输出。但**测到了**：三层 ID 的数值关系、`setsid` 的成败、`EPERM` 的两个触发条件（自己是组长 / 已是会话首领）、`/dev/tty` 与 `/dev/ptmx` 不存在。**「哪些是真的、哪些是语义推断」分开写**，这是笔记可信度的底线。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 交易服务 daemon 化 | `fork` + `setsid` 脱离控制终端，避免运维误按 `Ctrl+C` 打断策略主循环（段 ⑤ 前两步） |
| ssh 断开导致策略进程被杀 | 终端关闭 → `SIGHUP` 发给**控制进程**（会话首领）→ 默认终止。生产环境必须 `setsid` 或 `tmux` 托管，**`nohup` 只是忽略信号、仍留在原会话** |
| **启动脚本用 `ctermid()` 判断交互性会出错** | 段 ② 实测：`ctermid()` 返回 `"/dev/tty"` 但设备 `ENOENT`。**用 `test -t 0` / `isatty()`** |
| **`setsid` 后仍可能重新拿到控制终端** | 段 ⑤ 第 ③ 步的原因：会话首领打开 tty 会**自动绑定**为新控制终端。**必须 double fork** 才是结构上彻底摆脱 |
| 嵌入式 init（PID 1）行为 | PID 1 自成会话、无控制终端、**负责收养孤儿**。所以它**默认忽略未注册的信号**（包括 `SIGTERM`）——自己写的 init 必须显式注册 `SIGTERM`/`SIGCHLD` 处理器，否则停不掉、收不了僵尸 |
| 串口控制台（`/dev/ttyS0`）是嵌入式唯一终端 | 拔串口 = hangup → 内核给会话首领发 `SIGHUP`。**串口一拔，挂在它会话上的进程全挂**——工业设备必须让业务进程 `setsid` 或由 init 直接 `exec` 启在**独立会话**里 |
| 日志必须重定向，不能依赖终端 | 段 ⑤ 第 ⑤ 步：daemon 后 0/1/2 指向 `/dev/null`。**交易/嵌入式服务应在 daemon 化前就把日志 fd 打开好**（或用 syslog / journald socket），否则日志凭空消失 |

## 自测题

<details>
<summary>1. 会话和进程组是什么关系？为什么说「不是树形嵌套」？</summary>

会话是「进程组的容器」，一个会话里有多个进程组，其中**至多一个是前台进程组**。会话 ID（SID）= 会话首领的 PID。

但**「嵌套」只在逻辑上成立，结构体里没有指针**——进程组归属用 `signal->pids[PIDTYPE_PGID]` 标记，会话归属用 `signal->pids[PIDTYPE_SID]` 标记，是**两套独立的标签**（要点二的四行数组图）。所谓「进程组属于会话」，实际含义是「该组成员的 `SID` 都相同」。

这解释了为什么 `setsid()` 要**同时**新建进程组：只换 `SID` 的话，新会话会挂在旧会话的某个组上，层级就乱了（要点三）。
</details>

<details>
<summary>2. <code>setsid()</code> 到底做了什么？为什么组长不能调用？</summary>

做**三件事**：① 调用者成为新会话的**首领**（`SID == 自己的 PID`）；② 调用者成为新进程组的**组长**（`PGID == 自己的 PID`，新组里只有它）；③ 与旧控制终端**断开**。

**组长不能调用**（`setsid(2)` 原文：*"fails if the calling process is already a process group leader"*）的原因：若允许，调用者的 PGID 会**同时**成为「一个进程组 ID」和「一个新会话 ID」——同一数字在两层结构里各指一物，`struct pid` 的引用关系产生歧义。

本节段 ③ 实测：`pid==pgid`（是组长）→ `setsid()` 返回 `-1`，`errno=1 (EPERM)`。
</details>

<details>
<summary>3. <code>setsid()</code> 之后紧接着再调一次会怎样？为什么？</summary>

**`EPERM`。** 因为 `setsid()` 成功时**自己就成了新进程组的组长**（`pgid == pid`），于是撞上「组长不能调 `setsid()`」这条规则。

本节段 ④ 实测：

```text
  [child] fork 后：pid=3  pgid=2  sid=2     ← 非组长，setsid 可用
  [child] setsid() = 3  → 新会话成立了
  [child] setsid 之后：pid=3  pgid=3  sid=3 ← pgid==pid，成了组长
  [child] 再调一次 setsid() → -1  errno=1 (Operation not permitted)
```

**`setsid()` 自己把自己变成了「不能调 `setsid()` 的进程」**——这不是 bug，是规则的必然推论。也正因为此，daemon 流程里**必须先 `fork`**（让子进程当非组长），而不能指望「再调一次试试」。
</details>

<details>
<summary>4. 控制终端什么时候会发 SIGHUP？为什么 <code>nohup</code> 和 <code>setsid</code> 效果不同？</summary>

**触发时机**：终端设备断开（ssh 掉线、串口拔出、pty 主端关闭）时，tty 驱动检测到挂机（hangup），向该会话的**控制进程（会话首领）**发 `SIGHUP`。默认动作是终止 → 「ssh 一断前台全挂」。

**两者区别**：

| | 做法 | 后果 |
|---|---|---|
| `nohup` | 只是让进程**忽略 `SIGHUP`** | 仍在原会话、仍挂控制终端；**`SIGINT`/`SIGTSTP` 照收** |
| `setsid` | **彻底脱离**：新会话、无控制终端 | 终端驱动产生的任何信号**从根源上找不到它** |

要点四的表格就是这条。要真正「后台常驻」，优先 `setsid`（或 `tmux`/`screen` 托管）而不是 `nohup`。
</details>

<details>
<summary>5. 为什么 <code>ctermid()</code> 不能用来判断「有没有终端」？正确做法是什么？</summary>

`ctermid()` 返回的是**规范定的常量路径字符串** `"/dev/tty"`（`ctermid(3)` 原文只说是 "the pathname of the controlling terminal"），它**不检查设备是否存在**。

本节段 ② 的实测四行：

```text
  ttyname(STDIN_FILENO) = (null)  → 没有控制终端
  ctermid()             = "/dev/tty"
    access("/dev/tty")   = -1  （No such file or directory）
    isatty(0) = 0   isatty(1) = 0
```

**正确做法**：

| 目的 | 用什么 |
|------|--------|
| 判断 fd 是不是终端 | `isatty(fd)`（shell 里 `test -t 0`） |
| 拿到终端的真实路径 | `ttyname(fd)`（非终端返回 `NULL`） |

在启动脚本里用 `ctermid()` 比对输出判断交互性，是会出错的。
</details>

<details>
<summary>6. 守护进程为什么要「两次 fork」？只 fork 一次会怎样？</summary>

**一次 `fork` + `setsid` 不够**，因为 `setsid` 之后子进程成为**会话首领**，而**会话首领只要打开一个 tty 就会自动把该 tty 绑定为控制终端**（`/dev/tty` 指向它）。所以它仍然可能被终端信号打扰——只要代码里某处 `open("/dev/tty", ...)` 或打开了一个终端设备。

**第二次 `fork`** 产生孙进程，它既不是会话首领也不是组长，**结构上就永远无法获取控制终端**（内核规则：只有会话首领能获得控制终端）。这才是彻底摆脱。

段 ⑤ 的六步里，**只有前两步（`fork` + `setsid`）是内核强制要求**，后四步（再 fork / `chdir("/")` / 重定向 0-1-2 / 关 fd）都是**工程惯例**——不做不会报错，但会分别带来「可能重获终端」「占住挂载点」「误用坏 fd / 写爆磁盘」「fd 泄漏」四类问题。
</details>

<details>
<summary>7. 嵌入式设备用串口控制台时，拔掉串口会发生什么？</summary>

**拔串口 = hangup**，内核 tty 驱动向该会话的**控制进程（会话首领）**发 `SIGHUP`，默认动作终止。所以：

- 如果业务进程和串口控制台在**同一个会话**里（比如 init 脚本里直接 `./server &`），**串口一拔，业务进程就被 `SIGHUP` 干掉**——这不是「断电」，进程是被信号杀的；
- 工业设备必须让业务进程 `setsid` 脱离，或由 init 直接 `exec` 启在**独立会话**里。

这与 HFT 的「ssh 一断策略全挂」是**同一个机制**（要点四的 `SIGHUP` 行），只是触发的设备从网络 pty 换成了串口。

⚠️ 另外注意：如果进程**忽略**了 `SIGHUP`（例如 `nohup` 过），它不会被杀，但随后读/写已断的终端会得到 **`EIO`**——问题从「进程消失」变成「读写报错」，更难排查。
</details>
