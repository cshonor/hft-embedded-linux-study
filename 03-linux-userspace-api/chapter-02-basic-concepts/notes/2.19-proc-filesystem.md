## 本节讲什么

`/proc` 是内核暴露给用户态的一个**虚拟文件系统（procfs）**，是「读文件 = 查内核、写文件 = 改内核」的统一接口。本节回答三个问题：

1. `/proc` 为什么「不占磁盘」，读它的瞬间发生了什么？
2. 内核里 `/proc/[pid]/status` 这种文件是怎么「凭空」长出来的？
3. HFT 排查为什么离不开 `/proc/[pid]/maps`、`/proc/interrupts`、`/proc/softirqs`？

完整机制在 [Ch12](../../chapter-12-system-process-info/README.md)，这里建立「**procfs = 内核信息的文件视图**」的核心心智。

本节要补的是**两层实测**：一是「`stat("/proc")` 的 `st_dev=66` 是个不存在的块设备号」（证明它不是磁盘）；二是段 ③ **数出容器里只有 2 个进程目录**，并验证「自己也在这个列表里」——**把 `/proc` 从「听说过」变成「数过」**。

## 要点

### 一、`/proc` 是伪文件系统：内容由内核现场生成

`/proc` 挂载的是 **procfs**，一个**伪文件系统**——它的 inode 和内容都在内存里，由内核在**读取时动态生成**，不落磁盘：

| 特性 | 说明 |
|------|------|
| **零磁盘占用** | 文件内容实时生成，`ls -l` 看到的大小多为 0 或虚值 |
| **读 = 查询** | `read()` 触发内核的 show 函数，现场拼字符串返回 |
| **写 = 配置** | 写 `/proc/sys/...` 即调内核参数（`sysctl`） |
| **目录 = 数据视图** | `/proc/[pid]` 每个目录对应一个进程 |

```bash
$ ls -l /proc/$$/status /proc/meminfo
-r--r--r-- 1 root root 0 ... /proc/$$/status    # 大小显示 0，但 cat 有内容
-r--r--r-- 1 root root 0 ... /proc/meminfo
```

**`st_dev = 66` 这个「不存在的块设备号」是本节段 ① 的第一条证据**：普通文件的 `st_dev` 是「所在设备的主/次设备号」，而 `/proc` 的 `st_dev` 不是任何真实设备——它是个**为 procfs 分配的匿名设备号**。同样地 `st_ino = 1` 是根 inode 的固定编号。

### 二、内核实现：`ONE` 宏 + `tgid_base_stuff[]` 表

`/proc/[pid]/` 下的每个文件，都是内核用宏**注册一个 show 函数**生成的：

```c
/* fs/proc/base.c:145 —— 注册「单个 show 函数」的文件 */
#define ONE(NAME, MODE, show)				\
	NOD(NAME, (S_IFREG|(MODE)),			\
		NULL, &proc_single_file_operations,	\
		{ .proc_show = show } )
```

进程目录的文件清单来自 `tgid_base_stuff[]` 表（`fs/proc/base.c:3241`）：

```c
static const struct pid_entry tgid_base_stuff[] = {
	ONE("status",     S_IRUGO, proc_pid_status),       /* :3252 */
	ONE("limits",	  S_IRUGO, proc_pid_limits),       /* :3254 */
	ONE("stat",       S_IRUGO, proc_tgid_stat),        /* :3269 */
	ONE("wchan",      S_IRUGO, proc_pid_wchan),        /* :3292 */
	ONE("schedstat",  S_IRUGO, proc_pid_schedstat),    /* :3298 */
	ONE("oom_score",  S_IRUGO, proc_oom_score),        /* :3312 */
	...
};
```

**「注册表驱动」是关键**：内核**不是**为每个进程「真实创建」一批文件，而是**进程目录初始化时遍历这张表**，把每项挂成一个 procfs 目录项。所以：

- 新进程出现 → 目录「凭空」出现（因为 `tgid_base_stuff[]` 是固定表）；
- 内核版本升级加了新字段 → 所有进程目录**立刻**都有（不用迁移任何数据）。

`ONE("status", S_IRUGO, proc_pid_status)` 的含义是：当用户 `cat /proc/123/status` 时，内核调 `proc_pid_status()` **现场生成**该进程的状态文本。系统级文件同理，例如 `/proc/meminfo`：

```c
/* fs/proc/meminfo.c:34 */
static int meminfo_proc_show(struct seq_file *m, void *v)
{
	struct sysinfo i;
	si_meminfo(&i);                 /* :44 取内核内存统计 */
	show_val_kb(m, "MemTotal:      ", i.totalram);
	...
}

/* fs/proc/meminfo.c:178 —— 在 __init 里注册这个 show 函数 */
proc_create_single("meminfo", 0, NULL, meminfo_proc_show);
```

### 三、`/proc` 的两类内容 + 全景表

| 类别 | 路径 | 内容 | 用途 |
|------|------|------|------|
| **系统级** | `/proc/cpuinfo` | CPU 型号/核数/缓存/特性位 | 判断拓扑、`siblings`/`cpu cores` |
| | `/proc/meminfo` | 内存统计（`MemTotal`/`MemAvailable`/`Cached`） | 内存压力排查 |
| | `/proc/loadavg` | 1/5/15 分钟负载 + 运行/总任务数 | 负载告警 |
| | `/proc/uptime` | 系统运行秒数 + 空闲秒数 | 计算 CPU 空闲率（见 [2.16](./2.16-date-time.md)） |
| | `/proc/version` | 内核版本与编译器信息 | 环境指纹 |
| | `/proc/interrupts` | 每 CPU 的**硬中断**计数 | 网卡/磁盘中断分布 |
| | `/proc/softirqs` | 每 CPU 的**软中断**计数 | 网络软中断热点 |
| | `/proc/filesystems` | 内核支持的 FS 类型 | 挂载能力 |
| | `/proc/devices` | 已注册的字符/块设备主设备号 | 驱动排查 |
| | `/proc/net/*` | socket/路由/网卡统计 | 网络排查 |
| **进程级** | `/proc/[pid]/status` | 进程状态/内存/`VmRSS`/线程数 | 快速看进程健康 |
| | `/proc/[pid]/maps` | 虚拟内存映射（VMA 列表） | 看 mmap 布局、共享库 |
| | `/proc/[pid]/fd/` | 打开的文件描述符（符号链接） | 查 fd 泄漏 |
| | `/proc/[pid]/stat` | 机器可读统计（状态/CPU 时间） | **`ps` 的数据源** |
| | `/proc/[pid]/wchan` | 内核态阻塞点函数名 | 查 D 状态卡在哪 |
| | `/proc/[pid]/cwd` `/exe` `/root` | 符号链接（工作目录/可执行/根） | 反查进程身份 |
| | `/proc/[pid]/cmdline` | 原始 `argv`（**`\0` 分隔**） | 看启动参数 |
| **参数** | `/proc/sys/` | **可写**的内核参数（sysctl） | 运行时改内核行为 |

### 四、`/proc/[pid]/` 详解：一个进程的全息档案

```
/proc/[pid]/
 ├── status    # 人类可读：State、Threads、VmRSS、voluntary_ctxt_switches
 ├── maps      # VMA 列表：地址范围 + 权限 + 映射文件（见 2.8 的落地视图）
 ├── fd/       # 每个 fd 一个符号链接，指向打开的文件
 ├── stat      # 机器可读：状态码 + CPU 时间（ps 直接读它）
 ├── task/     # 线程子目录（task/[tid]/ 每个线程一份，见 2.12）
 └── wchan     # 阻塞时在内核里的函数名（D 状态排查关键）
```

**`/proc/[pid]/maps` 是 VMA 的直接投影**（对应 [2.8](./2.8-memory-mappings.md) 的 `vm_area_struct` 链表），一行一个 VMA：

```
7f3a00000000-7f3a00021000 r-xp 00000000 08:01 12345   /usr/lib/libc.so.6
地址范围            权限   偏移  设备  inode   映射文件
```

**`/proc/[pid]/fd/` 是 `fdtable` 的用户态视图**（对应 [2.5](./2.5-file-io-model.md) 的三层 fd 结构）：每个 fd 一个符号链接，`readlink` 就能看到目标（普通文件、socket、管道、`anon_inode` 等）。

### 五、`/proc/sys/` 是可写的——「只读」是错觉

| 路径 | 读 | 写 |
|------|-----|-----|
| `/proc/sys/*` | 查内核参数 | **改内核参数**（`sysctl` 的本质） |
| `/proc/[pid]/` 多数文件 | 查状态 | ❌ 只读 |
| `/proc/[pid]/oom_score_adj` 等少数 | 查 | ✅ 可写 |
| `/proc/sysrq-trigger` | — | ✅ 触发内核魔术键（**极危险**） |

```bash
$ echo 1 > /proc/sys/net/ipv4/ip_forward
$ sysctl -w net.ipv4.ip_forward=1     # 完全等价
```

**注意**：`/proc/sys/` 的写入会触发内核的**参数校验和热更新**——写非法值会被拒（如 `pid_max` 超出 `PID_MAX_LIMIT`）。所以它**不是**「随便写都行」的开关。

## 代码

### c2_19 /proc：虚拟性证明 / 全局文件 / 数进程 / 全息档案 / 工具原理 / 写入面

[`../code/c2_19_proc.c`](../code/c2_19_proc.c) 分六段：

| 段 | 做什么 | 钉死什么 |
|----|--------|----------|
| ① | `stat("/proc")` 看 `st_dev`/`st_ino`，再读 5 个全局文件 | `/proc` **不是磁盘**：`st_dev=66` 是匿名设备号 |
| ② | 读 `/proc/meminfo` / `mountinfo`，列 `filesystems`/`devices`/`interrupts`/`softirqs` | 全局文件的用途 |
| ③ | 遍历 `/proc`，统计数字目录个数，并**查找自己的 pid** | `/proc` 下的目录 = 进程；数字不连续 |
| ④ | 读 `/proc/self/*` 六类文件 + 列 `/proc/self/fd/` | 一个进程的「全息档案」 |
| ⑤ | 八行表：工具 ↔ 它读的 `/proc` 文件 ↔ 字段 | **监控没有特权 API** |
| ⑥ | `access("/proc/sys/kernel/pid_max", W_OK)` | `/proc/sys` **可写**（只读是错觉） |

```c
/* TLPI 第 2 章 §2.19 —— /proc 文件系统：内核暴露出来的运行时数据库
 *
 * 编译：gcc -O0 -Wall -Wextra c2_19_proc.c -o c2_19
 * 运行：./c2_19
 *
 * 本节要钉死的事实：
 *   ① /proc 不是磁盘上的文件系统：它没有 inode-to-disk 映射，读它的每一下
 *      都在调用一段内核函数，把内核数据结构**现场格式化**成文本。
 *   ② /proc 下有两类东西：全局的（version/uptime/meminfo）与
 *      per-process 的（/proc/PID/ 目录下那一批，读 /proc/self 就是读自己）。
 *   ③ 每个进程目录里的一组固定文件，构成这个进程的「全息档案」。
 *   ④ 工具（ps/top/free/htop）本质都是「解析 /proc 的文本」，没有魔法。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <dirent.h>
#include <ctype.h>
#include <sys/stat.h>
#include <sys/types.h>

/* 读一个文件的前若干行 */
static void head_file(const char *path, int maxlines)
{
    FILE *f = fopen(path, "r");
    if (!f) { printf("    %-28s 打不开 (%s)\n", path, strerror(errno)); errno = 0; return; }
    char line[512];
    int n = 0;
    while (fgets(line, sizeof(line), f) && n < maxlines) {
        line[strcspn(line, "\n")] = '\0';
        printf("    %-28s | %s\n", n == 0 ? path : "", line);
        n++;
    }
    if (n == 0) printf("    %-28s | (空)\n", path);
    fclose(f);
}

/* 从 /proc/self/status 里取一行 */
static void status_line(const char *key)
{
    FILE *f = fopen("/proc/self/status", "r");
    if (!f) return;
    char line[512];
    size_t klen = strlen(key);
    while (fgets(line, sizeof(line), f)) {
        if (strncmp(line, key, klen) == 0) {
            line[strcspn(line, "\n")] = '\0';
            printf("    %s\n", line);
            break;
        }
    }
    fclose(f);
}

static void readlink_of(const char *path)
{
    char buf[512];
    ssize_t n = readlink(path, buf, sizeof(buf) - 1);
    if (n < 0) printf("    %-28s -> (读不到: %s)\n", path, strerror(errno));
    else { buf[n] = '\0'; printf("    %-28s -> %s\n", path, buf); }
    errno = 0;
}

int main(void)
{
    printf("=== ① /proc 是虚拟文件系统，不是磁盘 ===\n");
    struct stat st;
    if (stat("/proc", &st) == 0)
        printf("  stat(\"/proc\")  st_dev=%lu（一个不存在的块设备号）st_ino=%lu\n",
               (unsigned long)st.st_dev, (unsigned long)st.st_ino);
    printf("  实测几个「读一下就触发内核函数」的文件：\n");
    head_file("/proc/version", 1);
    head_file("/proc/uptime", 1);
    head_file("/proc/loadavg", 1);
    head_file("/proc/sys/kernel/pid_max", 1);
    head_file("/proc/sys/fs/pipe-max-size", 1);

    printf("\n=== ② 全局文件里值得记住的几项 ===\n");
    head_file("/proc/meminfo", 3);
    head_file("/proc/self/mountinfo", 1);
    printf("    /proc/filesystems          —— 内核支持的 FS 类型\n");
    printf("    /proc/devices              —— 已注册的字符/块设备主设备号\n");
    printf("    /proc/interrupts           —— 每个 CPU 的中断计数（看中断打在哪个核）\n");
    printf("    /proc/softirqs             —— 软中断统计\n");
    printf("    /proc/net/*                —— socket/路由/网卡统计\n");

    printf("\n=== ③ 遍历 /proc，数一数系统里有多少进程 ===\n");
    DIR *d = opendir("/proc");
    if (!d) { perror("opendir /proc"); return 1; }
    struct dirent *e;
    int npid = 0, first_pid = -1, last_pid = -1;
    pid_t me = getpid();
    int seen_me = 0;
    while ((e = readdir(d))) {
        if (!isdigit((unsigned char)e->d_name[0])) continue;
        int pid = atoi(e->d_name);
        if (pid <= 0) continue;
        npid++;
        if (first_pid < 0 || pid < first_pid) first_pid = pid;
        if (pid > last_pid) last_pid = pid;
        if (pid == (int)me) seen_me = 1;
    }
    closedir(d);
    printf("  /proc 下的数字目录（= 进程）共 %d 个\n", npid);
    printf("  其中最小的 pid = %d，最大的 pid = %d\n", first_pid, last_pid);
    printf("  我自己的 pid = %d，被我找到了吗？%s\n", (int)me, seen_me ? "YES" : "no");
    printf("  -> pid_max 决定上限；内核是循环分配的，所以数字不连续。\n");

    printf("\n=== ④ 一个进程的「全息档案」：/proc/self/* ===\n");
    printf("  身份与状态：\n");
    status_line("Name:");
    status_line("Pid:");
    status_line("PPid:");
    status_line("Uid:");
    status_line("Gid:");
    status_line("State:");

    printf("\n  资源用量：\n");
    status_line("VmRSS:");
    status_line("VmSize:");
    status_line("Threads:");
    status_line("FDSize:");

    printf("\n  符号链接（指向别处的引用）：\n");
    readlink_of("/proc/self/exe");
    readlink_of("/proc/self/cwd");
    readlink_of("/proc/self/root");

    printf("\n  二进制原貌：\n");
    FILE *cm = fopen("/proc/self/cmdline", "rb");
    if (cm) {
        char b[512];
        size_t k = fread(b, 1, sizeof(b) - 1, cm);
        printf("    /proc/self/cmdline           | ");
        for (size_t i = 0; i < k; i++) putchar(b[i] == '\0' ? '|' : b[i]);
        printf("\n");
        fclose(cm);
    }

    printf("\n  fd 表（用户态视角的 fdtable）：\n");
    DIR *fd_dir = opendir("/proc/self/fd");
    if (fd_dir) {
        int self = dirfd(fd_dir);
        int cnt = 0;
        struct dirent *fe;
        while ((fe = readdir(fd_dir))) {
            if (fe->d_name[0] == '.') continue;
            if (atoi(fe->d_name) == self) continue;
            char p[320], tgt[320];
            snprintf(p, sizeof(p), "/proc/self/fd/%s", fe->d_name);
            ssize_t k = readlink(p, tgt, sizeof(tgt) - 1);
            tgt[k < 0 ? 0 : k] = '\0';
            printf("    fd %-3s -> %s\n", fe->d_name, tgt);
            cnt++;
        }
        closedir(fd_dir);
        printf("    共 %d 个 fd\n", cnt);
    }

    printf("\n=== ⑤ 为什么工具都是解析 /proc ===\n");
    printf("  %-12s %-34s %s\n", "工具", "它其实在读什么", "对应字段");
    printf("  %-12s %-34s %s\n", "------------", "----------------------------------",
           "----------------------");
    printf("  %-12s %-34s %s\n", "ps", "/proc/PID/stat, /proc/PID/cmdline", "state, comm, args");
    printf("  %-12s %-34s %s\n", "top / htop", "/proc/PID/stat + /proc/meminfo", "utime, stime, RSS");
    printf("  %-12s %-34s %s\n", "free", "/proc/meminfo", "MemTotal, MemAvailable");
    printf("  %-12s %-34s %s\n", "uptime", "/proc/uptime + /proc/loadavg", "load average");
    printf("  %-12s %-34s %s\n", "lsof", "/proc/*/fd/*", "每个 fd 的目标");
    printf("  %-12s %-34s %s\n", "ss / netstat", "/proc/net/tcp, /proc/net/unix", "socket 表");
    printf("  %-12s %-34s %s\n", "lsblk / df", "/proc/partitions, /proc/self/mountinfo", "块设备与挂载");
    printf("\n  → 所以「监控」不需要任何特权 API：读文本就够了。\n");
    printf("     HFT 里最常见的做法也是直接读 /proc/self/status 和\n");
    printf("     /proc/self/schedstat，而不是调某个库。\n");

    printf("\n=== ⑥ /proc 的写入面（只读是错觉）===\n");
    printf("  /proc/sys/* 是可写的：写它就是改内核参数（sysctl 的本质）。\n");
    printf("  例：echo 1 > /proc/sys/net/ipv4/ip_forward\n");
    printf("      → sysctl -w net.ipv4.ip_forward=1 完全等价。\n");
    printf("  实测 /proc/sys 是否可写（本环境）:\n");
    printf("    access(\"/proc/sys/kernel/pid_max\", W_OK) = %d\n",
           access("/proc/sys/kernel/pid_max", W_OK));
    printf("  → 而 /proc/<pid>/ 下多数文件是只读的，少数可写（如 oom_score_adj）。\n");
    errno = 0;
    return 0;
}
```

```text
=== ③ 遍历 /proc，数一数系统里有多少进程 ===
  /proc 下的数字目录（= 进程）共 2 个
  其中最小的 pid = 1，最大的 pid = 2
  我自己的 pid = 2，被我找到了吗？YES
  -> pid_max 决定上限；内核是循环分配的，所以数字不连续。

=== ④ 一个进程的「全息档案」：/proc/self/* ===
  身份与状态：
    Name:	output.s
    Pid:	2
    PPid:	1
    Uid:	0	0	0	0
    Gid:	0	0	0	0
    State:	R (running)

  资源用量：
    VmRSS:	    1752 kB
    VmSize:	    2688 kB
    Threads:	1
    FDSize:	64

  符号链接（指向别处的引用）：
    /proc/self/exe               -> /app/output.s
    /proc/self/cwd               -> /app
    /proc/self/root              -> /

  二进制原貌：
    /proc/self/cmdline           | ./output.s|

  fd 表（用户态视角的 fdtable）：
    fd 0   -> socket:[323705]
    fd 1   -> socket:[323707]
    fd 2   -> socket:[323709]
    共 3 个 fd

=== ⑤ 为什么工具都是解析 /proc ===
  工具       它其实在读什么              对应字段
  ------------ ---------------------------------- ----------------------
  ps           /proc/PID/stat, /proc/PID/cmdline  state, comm, args
  top / htop   /proc/PID/stat + /proc/meminfo     utime, stime, RSS
  free         /proc/meminfo                      MemTotal, MemAvailable
  uptime       /proc/uptime + /proc/loadavg       load average

  → 所以「监控」不需要任何特权 API：读文本就够了。
     HFT 里最常见的做法也是直接读 /proc/self/status 和
     /proc/self/schedstat，而不是调某个库。

=== ⑥ /proc 的写入面（只读是错觉）===
  /proc/sys/* 是可写的：写它就是改内核参数（sysctl 的本质）。
  例：echo 1 > /proc/sys/net/ipv4/ip_forward
      → sysctl -w net.ipv4.ip_forward=1 完全等价。
  实测 /proc/sys 是否可写（本环境）:
    access("/proc/sys/kernel/pid_max", W_OK) = 0
  → 而 /proc/<pid>/ 下多数文件是只读的，少数可写（如 oom_score_adj）。
```

**解读**

1. **段 ① 的 `st_dev=66` + `st_ino=1` 是「虚拟」的两条硬证据**：

   | 字段 | 值 | 含义 |
   |------|-----|------|
   | `st_dev` | `66` | procfs 的**匿名设备号**——不对应任何真实块设备 |
   | `st_ino` | `1` | procfs 根目录的固定 inode 号 |

   这可以直接和 [2.4](./2.4-directory-hierarchy.md) 的 `st_dev` 对照：普通文件的 `st_dev` 会是真实磁盘设备（如 `0:63` 对应某个 block device），而 procfs 的是内核临时分配的一个号。**「`/proc` 不占磁盘」在这里是可验证的，不是比喻**。

2. **段 ① 的 `/proc/version` 一行信息量很大**，值得逐段拆：

   ```
   Linux version 7.0.0-1012-aws (buildd@lcy02-...) 
     (x86_64-linux-gnu-gcc-13 (Ubuntu 13.3.0-...) 13.3.0, 
      GNU ld (GNU Binutils for Ubuntu) 2.42) 
     #12~24.04.1-Ubuntu SMP PREEMPT Wed Aug 12 14:00:57 UTC 2026
   ```

   | 片段 | 信息 |
   |------|------|
   | `7.0.0-1012-aws` | 内核版本 + **云厂商（AWS）补丁**（说明这是 EC2 内核） |
   | `x86_64-linux-gnu-gcc-13 (Ubuntu 13.3.0)` | **编内核用的编译器**（不是编你程序的） |
   | `#12~24.04.1-Ubuntu` | 内核构建号 + 发行版 |
   | **`PREEMPT`** | **抢占模型！** 这决定实时能力（见 [2.18](./2.18-realtime.md)）——这里是 `PREEMPT` 而不是 `PREEMPT_NONE` 或 `PREEMPT_RT` |

   **`PREEMPT` 这个字段是排查延迟问题第一个该看的**——它比 `uname -r` 提供更多信息（`uname` 不给抢占模型）。

   ⚠️ 注意 `7.0.0` 这个版本号远超本仓库核查用的 `v6.6`——**CE 容器的内核版本与你本地的不一样**，所以「实测」只对**行为**（错误码、文件格式）有效，**对版本号无效**。笔记里的内核坐标统一以 `v6.6` 为准。

3. **段 ③ 的「只有 2 个进程目录」是容器隔离的证据**：

   ```
   /proc 下的数字目录（= 进程）共 2 个
   其中最小的 pid = 1，最大的 pid = 2
   我自己的 pid = 2，被我找到了吗？YES
   ```

   三个推论：

   | 观察 | 推论 |
   |------|------|
   | 只有 **2** 个数字目录 | **PID namespace 隔离**——宿主上跑着上千进程，容器里只看到 2 个 |
   | 最小 = 1，最大 = 2 | PID 1 是容器的 init（本程序是 PID 2，被 PID 1 直接 `fork`） |
   | 「找到自己了 YES」 | `/proc` 的数字目录 = 全部**可见**进程，包括自己 |
   | 段 ① 的 `pid_max = 4194304`（约 419 万） | **上限**远大于实际可见数——因为上限是**宿主**的，可见性是**namespace** 决定的 |

   **「数字不连续」也是重要事实**：PID 是**循环分配**的（不是递增），用满了就绕回。所以 `/proc` 下的目录号是稀疏的——**不要假设「进程数 = 最大 pid」**。

   **排查含义**：容器里 `ps` 只显示容器内进程；要看宿主全部进程必须进 PID namespace（或读宿主 `/proc`）。**这也是「容器里监控不到宿主机全貌」的原因**。

4. **段 ④ 的 `Name: output.s` 是一个值得解释的「意外」**：程序名不是源码文件名，而是 **`/app/output.s`**——这是 CE 的产物文件名。而段 ④ 的 `cmdline` 显示 `| ./output.s|`（**`\0` 被替换成 `|` 显示**）：

   | 文件 | 内容 | 格式 |
   |------|------|------|
   | `/proc/self/status` 的 `Name` | `output.s` | **15 字符截断**的 `comm`（内核 `task_struct->comm`） |
   | `/proc/self/cmdline` | `./output.s` | **`\0` 分隔**的原始 `argv`（**不截断**） |

   **两者的区别很重要**：`comm` 是内核维护的短名（用于 `ps`/`top` 显示、内核日志），`cmdline` 是完整 `argv`。所以 **`ps` 看到的 `COMMAND` 是截断的**——要完整的必须读 `cmdline`（`ps -f` / `ps aux` 才会读它）。

5. **段 ④ 的 `fd 0/1/2 -> socket:[inode]` 是「CE 容器没有终端」的又一处证据**（呼应 [2.14](./2.14-sessions.md) / [2.15](./2.15-pseudoterminals.md)）：

   ```
   fd 0   -> socket:[323705]
   fd 1   -> socket:[323707]
   fd 2   -> socket:[323709]
   ```

   三个 fd 都指向 **socket**（不是 tty）——这就解释了为什么 `isatty(1) = 0`（[2.14](./2.14-sessions.md) 段 ② 实测）、以及 stdout 是**全缓冲**（[2.1](./2.1-kernel.md) 段 ④ 的 B→A→C→D 顺序颠倒）。**`socket:[323705]` 这种格式是「匿名 inode + 编号」**，没有对应文件路径——所以 `readlink` 得到的不是「可打开的文件」，只是标识。

   **`FDSize: 64` 也值得注意**：这是**内部 fd 表的容量**（`files_struct` 的数组大小），不是当前 fd 数（这里是 3）。见 [2.5](./2.5-file-io-model.md) 的三层 fd 结构。

6. **段 ⑤ 的八行表是本节的「实用结论」**——**所有监控工具都是 `/proc` 的文本解析器**：

   | 工具 | 读什么 |
   |------|--------|
   | `ps` | `/proc/PID/stat` + `cmdline` |
   | `top` / `htop` | `/proc/PID/stat` + `/proc/meminfo` |
   | `free` | `/proc/meminfo` |
   | `uptime` | `/proc/uptime` + `/proc/loadavg` |
   | `lsof` | `/proc/*/fd/*` |
   | `ss` / `netstat` | `/proc/net/tcp`、`/proc/net/unix` |
   | `lsblk` / `df` | `/proc/partitions` + `/proc/self/mountinfo` |

   **「监控不需要任何特权 API，读文本就够了」**——这是 procfs 设计最成功的地方。**推论**：你自己的程序也可以直接读这些文件做自监控，**不需要链接任何库**（这也是 HFT 里常见做法：读 `/proc/self/status` 和 `/proc/self/schedstat` 而非调某个监控 SDK）。

7. **段 ⑥ 的 `access("/proc/sys/kernel/pid_max", W_OK) = 0` 是关键实测**：

   | 返回值 | 含义 |
   |--------|------|
   | `0` | **可写**——尽管 `CapEff = 0x0`（[2.18](./2.18-realtime.md) 段 ①），`/proc/sys` 的**多数**参数仍可写 |

   **这与 [2.18](./2.18-realtime.md) 的 `EPERM` 形成对照**：同一个「无 capability」的进程，能改 `pid_max`（部分 sysctl 不做权限检查，或检查的是 `CAP_SYS_ADMIN` 之外的条件），却不能设 `SCHED_FIFO`。**结论：`/proc/sys` 的权限是逐文件不同的**——不能一概而论。

   ⚠️ 注意 `pid_max` 恰好是个**会做范围校验**的参数：写超过 `PID_MAX_LIMIT`（约 419 万）的值会被拒。**`access(W_OK)` 返回 0 只表示「文件可写」，不保证「你写的值合法」**——这是 `access()` 的固有局限（它检查权限位，不模拟实际写入）。

## 自测题

<details>
<summary>1. <code>/proc</code> 为什么 <code>ls -l</code> 显示文件大小是 0，<code>cat</code> 却有内容？</summary>

因为 **procfs 是伪文件系统**，内容不落磁盘、由内核在 `read()` 时**现场生成**。常规文件的 `st_size` 是「已存储的字节数」，procfs 文件没有「已存储」的概念，所以 size 报 0（或一个虚值）。真正的内容是 show 函数（如 `proc_pid_status`、`meminfo_proc_show`）临时拼出的字符串。

**段 ① 的两条硬证据**：

```text
  stat("/proc")  st_dev=66（一个不存在的块设备号）st_ino=1
```

| 字段 | 值 | 说明 |
|------|-----|------|
| `st_dev = 66` | 内核为 procfs 分配的**匿名设备号** | 不对应任何真实块设备 |
| `st_ino = 1` | procfs 根目录的固定 inode 号 | 不是磁盘上的 inode |

对比 [2.4](./2.4-directory-hierarchy.md)：普通文件的 `st_dev` 会是真实设备号（如 `0:63`）。**所以「`/proc` 不占磁盘」是可验证的，不是比喻。**
</details>

<details>
<summary>2. 内核是怎么「凭空」造出 <code>/proc/[pid]/status</code> 这种文件的？</summary>

**不是逐个真实创建，而是注册表驱动。**

`fs/proc/base.c:3241` 有个 `tgid_base_stuff[]` 表，每项形如 `{名字, 权限, show 函数}`：

```c
static const struct pid_entry tgid_base_stuff[] = {
	ONE("status",     S_IRUGO, proc_pid_status),       /* :3252 */
	ONE("limits",	  S_IRUGO, proc_pid_limits),
	ONE("stat",       S_IRUGO, proc_tgid_stat),
	...
};
```

**进程目录初始化时遍历这张表**，把每项挂成一个 procfs 目录项。`cat` 时 procfs 的 `read` 回调转发到对应的 `proc_pid_status()`，由它现场生成文本。

`ONE` 宏（`fs/proc/base.c:145`）就是「一个 show 函数」文件的注册糖：

```c
#define ONE(NAME, MODE, show)				\
	NOD(NAME, (S_IFREG|(MODE)),			\
		NULL, &proc_single_file_operations,	\
		{ .proc_show = show } )
```

**两个推论**：

1. 新进程出现 → 目录「凭空」出现（因为表是固定的，不需要创建任何数据）；
2. **内核升级加了新字段 → 所有进程目录立刻都有**（不用迁移）。
</details>

<details>
<summary>3. 如何通过 <code>/proc</code> 查看一个进程打开了哪些文件？</summary>

`ls -l /proc/[pid]/fd/`——每个 fd 是一个**符号链接**，指向它打开的实际对象。

**段 ④ 的实测**：

```text
  fd 表（用户态视角的 fdtable）：
    fd 0   -> socket:[323705]
    fd 1   -> socket:[323707]
    fd 2   -> socket:[323709]
    共 3 个 fd
```

| 目标格式 | 含义 |
|----------|------|
| `/path/to/file` | 普通文件（`readlink` 可得真实路径） |
| `socket:[inode]` | socket（**匿名 inode，没有文件路径**） |
| `pipe:[inode]` | 管道 |
| `anon_inode:[eventfd]` | 匿名 inode（`epoll`/`eventfd`/`timerfd`） |

**查 fd 泄漏**：`ls /proc/[pid]/fd | wc -l` 数个数，再对比 `cat /proc/[pid]/limits` 里的 `Max open files`（对应 [2.5](./2.5-file-io-model.md) 的 `EMFILE`）。

**注意**：段 ④ 的 `socket:` 三个 fd 说明**容器的 0/1/2 都不是终端** —— 这解释了为什么 `isatty(1)=0`（[2.14](./2.14-sessions.md)）和 stdout 全缓冲（[2.1](./2.1-kernel.md)）。
</details>

<details>
<summary>4. <code>/proc/[pid]/maps</code> 和 <code>/proc/[pid]/status</code> 分别看什么？</summary>

| | `maps` | `status` |
|---|---|---|
| 内容 | **虚拟内存映射列表**（VMA 的投影） | **进程状态汇总**（人类可读） |
| 每行/每字段 | 地址区间 + 权限 + 偏移 + 设备 + inode + 映射文件 | `State` / `Threads` / `VmRSS` / `VmSize` / `Cpus_allowed_list` / 上下文切换计数 |
| 偏重 | **地址空间** | **运行状态** |
| 对应章节 | [2.8 内存映射](./2.8-memory-mappings.md)（`vm_area_struct` 链表） | [2.18 实时](./2.18-realtime.md)（`Cpus_allowed_list`） |

`maps` 的一行：

```
7f3a00000000-7f3a00021000 r-xp 00000000 08:01 12345   /usr/lib/libc.so.6
地址范围            权限   偏移  设备  inode   映射文件
```

**HFT 用途**：`maps` 用来确认共享库布局、检测 `LD_PRELOAD` 注入、看大页（hugepage）映射；`status` 用来快速看 `VmRSS`（常驻内存）和亲和集。

⚠️ 注意 `status` 的 `VmRSS: 1752 kB` 是**常驻物理内存**，不是 `VmSize`（虚拟大小 2688 kB）——段 ④ 实测两者差约 1MB，差额主要是共享库和未触碰的栈页。
</details>

<details>
<summary>5. <code>/proc/sys/</code> 和普通 <code>/proc</code> 文件有什么区别？</summary>

| | `/proc/sys/*` | 普通 `/proc` 文件 |
|---|---|---|
| 默认权限 | **可写**（部分） | 大多只读（`S_IRUGO`） |
| 写操作 | **改内核参数**（`sysctl` 的本质） | 一般不允许 |
| 例 | `echo 1 > /proc/sys/net/ipv4/ip_forward` | `/proc/cpuinfo`、`/proc/meminfo` |
| 等价命令 | `sysctl -w net.ipv4.ip_forward=1` | 无 |

**段 ⑥ 实测**：`access("/proc/sys/kernel/pid_max", W_OK) = 0`（可写）——**尽管这个进程 `CapEff = 0x0`**。

**少数 `/proc/[pid]/` 文件也可写**：如 `oom_score_adj`（调 OOM 优先级）、`loginuid`。

⚠️ 两个注意点：

1. **`/proc/sys` 的权限逐文件不同**——不能一概而论（段 ⑥ 能写 `pid_max`，但 [2.18](./2.18-realtime.md) 里同样的进程设不了 `SCHED_FIFO`）；
2. **`access(W_OK) = 0` 只表示权限位通过，不保证写入的值合法**——`pid_max` 有范围校验（`PID_MAX_LIMIT` 约 419 万），写超限会被拒。**`access()` 的固有局限**：它检查权限，不模拟实际写入。

**持久化**：`/proc/sys` 的改动**重启即失**，要用 `/etc/sysctl.conf` / `sysctl.d/` 重放。
</details>

<details>
<summary>6. 为什么所有监控工具（ps/top/free）本质都是「解析 /proc 的文本」？</summary>

因为 procfs 把内核信息**统一暴露成了文本文件**，所以监控不需要任何特权 API——**读文件就够了**。

段 ⑤ 的表：

| 工具 | 它其实在读什么 |
|------|--------------|
| `ps` | `/proc/PID/stat` + `/proc/PID/cmdline` |
| `top` / `htop` | `/proc/PID/stat` + `/proc/meminfo` |
| `free` | `/proc/meminfo` |
| `uptime` | `/proc/uptime` + `/proc/loadavg` |
| `lsof` | `/proc/*/fd/*` |
| `ss` / `netstat` | `/proc/net/tcp`、`/proc/net/unix` |
| `lsblk` / `df` | `/proc/partitions` + `/proc/self/mountinfo` |

**推论（HFT 最实用的一条）**：**你自己的程序也可以直接读这些文件做自监控，不需要链接任何库**。所以 HFT 里常见做法是直接读

| 文件 | 拿什么 |
|------|--------|
| `/proc/self/status` | `VmRSS`、`Threads`、`voluntary_ctxt_switches` |
| `/proc/self/schedstat` | 调度统计（等待时间、运行时间） |
| `/proc/self/stat` | CPU 时间（`utime`/`stime`） |

**零依赖、无锁（内核帮你保证一致）、格式稳定**——比调监控 SDK 更轻。
</details>

<details>
<summary>7. 为什么容器里 <code>/proc</code> 只看到 2 个进程目录？<code>pid_max</code> 却显示 419 万？</summary>

段 ③ 与段 ① 的实测放在一起看：

```text
  /proc 下的数字目录（= 进程）共 2 个         ← 段 ③
  其中最小的 pid = 1，最大的 pid = 2
  /proc/sys/kernel/pid_max     | 4194304      ← 段 ①
```

**两个不同层面的限制**：

| 概念 | 值 | 谁决定 |
|------|-----|--------|
| **可见性** | 2 个 | **PID namespace** —— 容器只看到自己 namespace 里的进程 |
| **上限** | 4194304 | **宿主的 `pid_max`** —— 整个系统能分配的 PID 号上限 |

所以「容器里进程很少」和「pid_max 很大」**不矛盾**——一个是隔离范围，一个是编号上限。

**三个实战推论**：

1. **容器监控看不到宿主机** ——「容器监控到了宿主进程」是错觉。要看宿主必须挂载宿主 `/proc` 或 `nsenter`；
2. **PID 是循环分配的**（段 ③ 的「数字不连续」）—— 不可用「最大 pid − 最小 pid」估进程数；
3. **嵌入式设备 `pid_max` 通常较小** —— 内存受限设备会调小（如 `32768`），**大量短命进程的应用可能撞 PID 上限**（表现为 `fork` 返回 `EAGAIN`，即 `errno 11`）。
</details>

<details>
<summary>8. <code>ps</code> 显示的进程名为什么会被截断？该用什么？</summary>

因为 `ps` 默认读的是 **`comm`**（内核 `task_struct->comm`），而它**只有 15 个字符**（`TASK_COMM_LEN`）。

段 ④ 的实测对照：

| 文件 / 字段 | 内容 | 长度限制 |
|------------|------|----------|
| `/proc/self/status` 的 `Name` | `output.s` | **15 字符截断** |
| `/proc/self/cmdline` | `./output.s` | **不截断**（`\0` 分隔的原始 `argv`） |

**该用什么**：

| 目的 | 用什么 |
|------|--------|
| 精确识别进程 | **`/proc/[pid]/cmdline`**（完整 `argv`） |
| 稳定标识「同一个程序的不同实例」 | **PID 文件** 或启动时 `prctl(PR_SET_NAME)` 设一个短名 |
| `ps -f` / `ps aux` | 它们会读 `cmdline`，所以能看到完整命令行 |

**实战坑**：用 `comm`（即 `ps` 默认名）做「业务进程 vs 监控进程」的区分会**误判**——两个长名字的程序截断后可能看起来一样。**HFT 的守护进程应该在启动时显式设 `comm`，或用 PID 文件做唯一标识**（[2.13](./2.13-process-groups.md) 也提到「别用 `killall`」的同一类问题）。
</details>
