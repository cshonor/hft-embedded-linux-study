## 本节讲什么

Shell 是「用户与内核之间的命令行解释器」。本节回答三个问题：

1. Shell 是内核的一部分吗？它的核心循环是什么？
2. 内置命令（builtin）和外部命令有什么区别？`system()` 为什么危险？
3. Shell 的「作业控制」和进程组/会话有什么关系？

本节要补的是**那三句话说不到的部分**：`exec` 成功为什么永不返回、`exit 127` 这个惯例从哪来、以及「`system()` 在最小容器里整条路都断了」的实测证据。

## 要点

### 一、Shell 的本质：一个普通用户态进程

Shell **不是内核的一部分**，它只是一个跑在用户态的程序（`/bin/bash`、`/bin/dash` 等），做的事就是循环：

```c
/* shell 核心循环（极度简化） */
while (1) {
    printf("$ ");                        /* 打印提示符 */
    if (fgets(cmd, sizeof(cmd), stdin) == NULL) break;  /* 读一行命令 */

    pid_t pid = fork();                  /* ① fork 出子进程 */
    if (pid == 0) {
        execvp(argv[0], argv);           /* ② 子进程 exec 成目标程序 */
        perror("execvp"); _exit(127);    /* exec 失败才走到这 */
    }
    waitpid(pid, &status, 0);            /* ③ 父进程等待子进程结束 */
}
```

「读命令 → fork → exec → wait」就是 shell 的全部秘密。**每敲一条外部命令，就 fork 一个新进程 + exec 掉它**——这也是「为什么 shell 里循环启动进程有开销」的根源。

### 二、常见 Shell 与「内置 vs 外部」

| Shell | 路径 | 特点 |
|-------|------|------|
| bash | `/bin/bash` | GNU 默认，功能最全 |
| dash | `/bin/dash` | Debian/Ubuntu 轻量，`/bin/sh` 常软链到它 |
| zsh | `/usr/bin/zsh` | 交互补全强 |
| fish | `/usr/bin/fish` | 现代，**非 POSIX 兼容**（脚本会跑挂） |

**内置命令 vs 外部命令**是关键区分：

| 类型 | 例子 | 是否 fork |
|------|------|-----------|
| **内置命令（builtin）** | `cd`、`export`、`echo`(bash)、`ulimit` | ❌ 不 fork，直接改 shell 自身状态 |
| **外部命令** | `ls`、`grep`、`cat` | ✅ fork + exec 子进程 |

`cd` 必须是内置命令——因为它要改的是 **shell 进程自己的工作目录**；若 fork 子进程去 `chdir`，改的是子进程、父 shell 的工作目录根本不变。同理 `ulimit` 改的是 shell 的 rlimit。

### 三、`exec` 的两条铁律

| 铁律 | 含义 | 代码后果 |
|------|------|----------|
| **成功即永不返回** | `execve` 把当前进程的内存整个换掉，原来那条指令流已经不存在了 | `exec*()` 之后的任何代码只在**失败**时执行 |
| **失败惯例退出码 127** | 不是内核规定，是 shell / glibc 约定俗成的「命令找不到」 | `perror("execvp"); _exit(127);` |

**为什么是 127 而不是 1**：`126` = 找到了但不能执行（权限/格式），`127` = 找不到。这组数字是 POSIX 给 shell 定的，写自己的 `exec` 包装时跟着用，调试时一眼能分清两类失败。

> 还有一条容易忽略的：`_exit()` 而**不是** `exit()`。`exit()` 会跑 `atexit` 处理器、flush stdio；在 `exec` 失败的分支里这些都无所谓，但在 fork 出的子进程里，**`_exit()` 不 flush 会让 printf 的输出全丢**（见 [2.7](./2.7-processes.md)）。

### 四、`system()`：隐式的 `/bin/sh -c`

C 程序里执行 shell 命令用 `system()`，但它是**隐式 fork 三层**：

```c
system("ls -l");
/* 等价于： fork → execl("/bin/sh", "sh", "-c", "ls -l", NULL) → waitpid */
```

| 隐患 | 说明 |
|------|------|
| **阻塞** | `system()` 会 `wait`，调用线程卡住直到命令结束 |
| **信号干扰** | 期间 SIGINT/SIGQUIT 被屏蔽，SIGCHLD 被忽略，容易漏处理 |
| **命令注入** | 拼接字符串传给 `sh -c`，用户输入含 `;`/`$()` 即被解析执行 |
| **依赖 `/bin/sh`** | 不同系统 `/bin/sh` 指向不同（bash/dash），行为可能不同；**没有 `/bin/sh` 就是彻底不可用** |

所以：**生产代码里能用 `fork`+`exec`+`wait` 就别用 `system()`**，尤其别把不可信输入拼进 `system()` 字符串。本节 demo 段 ③ 给出了「没有 `/bin/sh` 时 `system()` 返回什么」的实测值。

### 五、Shell 的作业控制

Shell 之所以能实现 `Ctrl+C` 杀整条管道、`Ctrl+Z` 挂起、`fg`/`bg` 切换，靠的是它作为「会话首领 + 前台进程组管理者」的身份：

- shell 启动时是**会话首领**，拥有控制终端（见 [2.14](./2.14-sessions.md)）
- 每条管道命令放进**一个进程组**（见 [2.13](./2.13-process-groups.md)）
- `Ctrl+C` → 终端驱动给**前台进程组**发 SIGINT
- `Ctrl+Z` → 发 SIGTSTP，shell 把该组移到后台，打印 `[1]+ Stopped`
- `fg`/`bg` → shell 调 `tcsetpgrp()` 切换前台进程组 + 发 SIGCONT

所以「作业控制」本质是 shell 对**进程组 + 会话**这两套内核机制的编排，不是 shell 自创的魔法。

## 代码

### c2_2 迷你 shell：read → fork → exec → wait 的完整骨架

[`../code/c2_2_minishell.c`](../code/c2_2_minishell.c) 是一个**不依赖外部命令**的迷你 shell（所以能在只有 libc 的容器里跑起来）。它只认 4 个内置命令：

| 命令 | 干什么 | 演示哪条路 |
|------|--------|-----------|
| `self` | `fork` + `execve(/proc/self/exe, ["--child"], ...)` 自举自己 | **成功路径** + `argv`/`envp` 怎么传 |
| `nosuchcmd` | `execvp` 一个不存在的命令 | **经典 `exit 127`** 路径 |
| `sys` | `system("true")` 对照实验 | `system()` 依赖 `/bin/sh` |
| `help` / `exit` | 打印帮助 / 退出 | 内置命令**不 fork** |

```c
/* TLPI 第 2 章 §2.2 —— 迷你 shell：read → fork → exec → wait 循环
 *
 * 编译：gcc -O0 -Wall -Wextra c2_2_minishell.c -o c2_2
 * 运行：printf 'self\nnosuchcmd\nbuiltin\nsys\nhelp\nexit\n' | ./c2_2
 *
 * 这个 shell 只认 4 个内置命令（不依赖外部命令，便于在最小容器里跑）：
 *   self        fork + execve(/proc/self/exe) 自举一个新程序  → 成功路径
 *   nosuchcmd   execvp 一个不存在的命令                       → 经典 exit 127 路径
 *   sys         system("true") 对照：验证它必须依赖 /bin/sh
 *   help/exit   打印帮助 / 退出
 *
 * 本节要钉死的事实：
 *   ① shell 是普通用户态进程，核心就是「读 → fork → exec → wait」。
 *   ② 内置命令不 fork（要改 shell 自身状态），外部命令必须 fork+exec。
 *   ③ exec 成功就永不返回；走到 perror 一定是失败，惯例 _exit(127)。
 *   ④ system() 是隐式的 fork + /bin/sh -c + wait，没有 /bin/sh 就整个失败。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <sys/wait.h>
#include <sys/types.h>

#define MAXLINE 512

/* 把 wait status 翻译成人话 */
static void report_status(const char *tag, int status)
{
    if (WIFEXITED(status))
        printf("  %s: 正常退出 WEXITSTATUS=%d\n", tag, WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("  %s: 被信号杀死 WTERMSIG=%d (%s)%s\n", tag, WTERMSIG(status),
               strsignal(WTERMSIG(status)),
               WCOREDUMP(status) ? " + core" : "");
    else if (WIFSTOPPED(status))
        printf("  %s: 被暂停 WSTOPSIG=%d\n", tag, WSTOPSIG(status));
    else
        printf("  %s: 其他 status=0x%x\n", tag, status);
}

/* 外部命令路径：fork + exec + wait */
static void run_external(const char *cmd)
{
    fflush(NULL);                       /* fork 前清缓冲，否则子进程会重复输出 */
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return; }

    if (pid == 0) {
        /* ---- 子进程：把自己替换成目标程序 ---- */
        if (strcmp(cmd, "self") == 0) {
            static char exe[512];
            ssize_t n = readlink("/proc/self/exe", exe, sizeof(exe) - 1);
            if (n < 0) { perror("readlink"); _exit(127); }
            exe[n] = '\0';
            char *av[] = { exe, "--child", NULL };
            char *ev[] = { "C2_ROLE=child", NULL };
            printf("  [child] 即将 execve 自己：%s\n", exe);
            fflush(NULL);
            execve(exe, av, ev);
            perror("execve");           /* 只有失败才会走到这里 */
            _exit(127);
        }
        /* nosuchcmd：走 execvp，让它去 PATH 里搜 */
        printf("  [child] execvp(\"%s\") ...\n", cmd);
        fflush(NULL);
        errno = 0;
        execvp(cmd, (char *[]) { (char *)cmd, NULL });
        printf("  [child] execvp 失败 errno=%d (%s) -> 惯例 _exit(127)\n",
               errno, strerror(errno));
        fflush(NULL);
        _exit(127);
    }

    /* ---- 父进程：等它 ---- */
    int status = 0;
    if (waitpid(pid, &status, 0) < 0) { perror("waitpid"); return; }
    printf("  [parent] 子进程 %d 结束\n", (int)pid);
    report_status("child", status);
}

static void cmd_sys(void)
{
    printf("  system(\"true\") —— 它的内部是 fork + /bin/sh -c + waitpid\n");
    errno = 0;
    int rc = system("true");
    printf("  system() 返回值 = %d", rc);
    if (rc == -1)
        printf("   errno=%d (%s)\n", errno, strerror(errno));
    else
        printf("   WIFEXITED=%d WEXITSTATUS=%d\n", WIFEXITED(rc), WEXITSTATUS(rc));
    printf("  -> 本环境没有 /bin/sh，所以 system() 整条路都断了；\n");
    printf("     这正是「别在热路径依赖 system()」的最硬证据。\n");
}

int main(int argc, char **argv)
{
    /* 被 exec 出来的那个「自己」走这个分支 */
    if (argc > 1 && strcmp(argv[1], "--child") == 0) {
        printf("  [child] 我是被 execve 出来的新程序：pid=%d argv[0]=%s\n",
               (int)getpid(), argv[0]);
        printf("  [child] 环境变量 C2_ROLE=%s\n",
               getenv("C2_ROLE") ? getenv("C2_ROLE") : "(丢失)");
        return 7;                       /* 用退出码 7 给父进程一个信号 */
    }

    char line[MAXLINE];
    printf("=== 迷你 shell（TLPI §2.2）===\n");
    printf("内置：self / nosuchcmd / sys / help / exit\n\n");

    for (;;) {
        printf("$ ");
        fflush(stdout);                 /* 提示符必须立刻可见 */
        if (fgets(line, sizeof(line), stdin) == NULL) {
            printf("\n(EOF，shell 退出)\n");
            break;
        }
        line[strcspn(line, "\n")] = '\0';
        if (line[0] == '\0') continue;

        if (strcmp(line, "exit") == 0) { printf("bye\n"); break; }
        if (strcmp(line, "help") == 0) {
            printf("  self       fork + execve 自己（成功路径，退出码 7）\n");
            printf("  nosuchcmd  execvp 找不到命令（失败路径，exit 127）\n");
            printf("  sys        system(\"true\") 对照实验\n");
            printf("  exit       退出\n");
            continue;                   /* 内置：不 fork */
        }
        if (strcmp(line, "sys") == 0) { cmd_sys(); continue; }

        run_external(line);             /* 其余当外部命令处理 */
    }
    return 0;
}
```

编译与运行（命令通过管道喂给它的 stdin）：

```bash
gcc -O0 -Wall -Wextra -o c2_2_minishell c2_2_minishell.c
printf 'self\nnosuchcmd\nsys\nhelp\nexit\n' | ./c2_2_minishell
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3.0 / x86-64 / Ubuntu 24.04 容器）：

```text
=== 迷你 shell（TLPI §2.2）===
内置：self / nosuchcmd / sys / help / exit

$   [child] 即将 execve 自己：/app/output.s
  [child] 我是被 execve 出来的新程序：pid=3 argv[0]=/app/output.s
  [child] 环境变量 C2_ROLE=child
  [parent] 子进程 3 结束
  child: 正常退出 WEXITSTATUS=7
$   [child] execvp("nosuchcmd") ...
  [child] execvp 失败 errno=2 (No such file or directory) -> 惯例 _exit(127)
  [parent] 子进程 4 结束
  child: 正常退出 WEXITSTATUS=127
$   system("true") —— 它的内部是 fork + /bin/sh -c + waitpid
  system() 返回值 = 32512   WIFEXITED=1 WEXITSTATUS=127
  -> 本环境没有 /bin/sh，所以 system() 整条路都断了；
     这正是「别在热路径依赖 system()」的最硬证据。
$   self       fork + execve 自己（成功路径，退出码 7）
  nosuchcmd  execvp 找不到命令（失败路径，exit 127）
  sys        system("true") 对照实验
  exit       退出
$ bye
```

**解读**

1. **`self` 那一段是「exec 换掉整个进程」的直接证据**。父 shell `fork` 出子进程后，子进程 `execve("/proc/self/exe", ...)` —— **用自己可执行文件的路径再执行自己**。所以第二段输出里的 `pid=3` 和第一段的 `pid=3` 是**同一个 PID**，但里面的程序已经换了一遍：它打印 `argv[0]=/app/output.s`、环境变量 `C2_ROLE=child`，然后 `_exit(7)` 退出。父进程 `waitpid` 拿到 `WEXITSTATUS=7`——**7 是子程序自己给的，不是内核给的**。
2. **`nosuchcmd` 钉死了 `exit 127` 这个惯例**。`execvp("nosuchcmd")` 返回 `-1`、`errno=2`（`ENOENT`），子进程随后 `_exit(127)`。父进程打印 `WEXITSTATUS=127`。注意这条路径上 `execvp` **返回了**——而成功路径上它永不返回（见「要点三」）。
3. **`sys` 是全 demo 信息量最大的一条**：`system("true")` 返回 **`32512`**。把 `32512 >> 8` 就得到 `127`，`WIFEXITED=1`、`WEXITSTATUS=127`。原因是 CE 容器里**没有 `/bin` 目录**（没有 `/bin/sh`），`system()` 内部 `fork` 出的子进程 `execl("/bin/sh", "sh", "-c", "true")` 直接失败，于是按惯例 `_exit(127)`。这不是 bug，是「`system()` 无条件依赖一个外部 shell」的实证——**在裁剪过的嵌入式 rootfs 里，`/bin/sh` 常常也是缺的**，同一个坑会原样复现。
4. **`help` 走的是「内置命令不 fork」那条路**：它只打印内置命令清单，不创建任何进程。对照 `self`/`nosuchcmd` 都各自有一个「`[parent] 子进程 N 结束`」——**内置与外部命令的区别在输出里就能数出来**（有没有那行 `[parent] 子进程 N 结束`）。
5. **一个能立刻上手的推论**：想让脚本或程序「不依赖 shell 也能跑」，就必须自己 `fork`+`exec`+`wait`（像本 demo 的 `self` 分支）。这也是容器/嵌入式里 `ENTRYPOINT` 常写成 `exec "$@"` 的原因——省掉一层 shell，少一个依赖。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 启动编排 | shell 脚本负责拉起/重启交易进程、设置环境变量、ulimit（`RLIMIT_MEMLOCK`、`NOFILE`） |
| `system()` 慎用 | 交易热路径用 `fork`+`exec`+`wait` 或直接 IPC，避免 `system()` 的阻塞 + 注入风险 |
| **裁剪 rootfs 里没有 `/bin/sh`** | 段 ③ 实测：`system()` 返回 `32512`、`WEXITSTATUS=127`。嵌入式/BusyBox 镜像若精简掉 shell，所有依赖 `system()`/`popen()` 的代码会**整条路断掉** |
| 循环 fork 开销 | 脚本里 `for` 循环大量外部命令 = 大量 fork/exec，编排脚本应内置化或用 `xargs` 批量 |
| `/bin/sh` 可移植性 | 部署脚本写 `#!/bin/sh` 需守 POSIX 子集，别用 bash 专属语法（`[[ ]]`、数组） |
| **容器 ENTRYPOINT 用 `exec "$@"`** | 省掉一层 shell，PID 1 直接是目标进程，**信号才能正确送达**——否则 shell 会吞掉 SIGTERM，`docker stop` 只能等超时 |
| 监控脚本 | `ps`/`top`/`grep` 组合做进程存活监控，`kill -0 pid` 探活 |

## 自测题

<details>
<summary>1. Shell 是内核的一部分吗？它的核心循环是什么？</summary>

不是。Shell 是**普通用户态进程**（`/bin/bash` 等），核心循环是「读命令 → `fork` → `exec` → `wait`」四步。每执行一条外部命令就 fork 一个新进程、exec 成目标程序，父 shell 等待其结束。

本节实测可以数出这个结构：`self` 和 `nosuchcmd` 两条外部路径都各有一行 `[parent] 子进程 N 结束`，而 `help`（内置）没有。
</details>

<details>
<summary>2. 为什么 <code>cd</code> 必须是内置命令，不能是外部命令？</summary>

因为 `cd` 要改的是 **shell 进程自己的当前工作目录**（`chdir`）。若做成外部命令，`fork` 出的子进程执行 `chdir` 只改子进程的工作目录，父 shell 的目录不变——命令返回后「什么都没发生」。同理 `export`（改环境）、`ulimit`（改 rlimit）都必须是内置命令。

这正是「内置命令不 fork」这条规则的根源：**凡是要改调用者自身状态的，都不能在子进程里做**。
</details>

<details>
<summary>3. <code>execve()</code> 成功之后会返回吗？为什么失败惯例用 127？</summary>

**不会返回。** `execve(2)` 原文是 "**execve() does not return on success**"——它把当前进程的地址空间、`argv`、`envp` 整个换成新程序，原来那条指令流已经不存在了。所以 `exec*()` 之后的代码**只在失败时执行**。

**127 不是内核规定**，是 POSIX 给 shell 定的惯例：`126` = 找到了但不可执行（权限/格式），`127` = 命令找不到。`system(3)` 的 RETURN VALUE 也写明了："If `/bin/sh` could not be executed, the exit status will be that of **a command that exits with the value 127**"。

本节实测两处都是 127：
- `execvp("nosuchcmd")` 失败 → 我们 `_exit(127)` → 父进程看到 `WEXITSTATUS=127`；
- `system("true")` → 返回 `32512`（`= 127<<8`）、`WEXITSTATUS=127`。
</details>

<details>
<summary>4. <code>system("ls -l")</code> 背后发生了什么？为什么说它危险？</summary>

它隐式执行 `fork` → `execl("/bin/sh", "sh", "-c", "ls -l", NULL)` → `waitpid` 三步。危险在于：

1. **阻塞**当前线程直到命令结束；
2. 若命令字符串由用户输入拼接，会被 `sh` 解析执行（**命令注入**，如 `"; rm -rf /"`）；
3. 期间信号处理被扰动（SIGINT/SIGQUIT 被屏蔽、SIGCHLD 被忽略）；
4. **无条件依赖 `/bin/sh`** —— 本节实测：没有 `/bin/sh` 时 `system()` 返回 `32512`（`WEXITSTATUS=127`），整条路直接断掉。

生产代码应改用 `fork` + `exec` + `wait`。
</details>

<details>
<summary>5. <code>Ctrl+C</code> 能杀掉一条管道里的所有命令，是 shell 的魔法吗？</summary>

不是魔法，是「进程组」机制。shell 把 `ls | grep | wc` 这条管道里的进程放进**同一个进程组**（前台进程组），`Ctrl+C` 时终端驱动向该组广播 SIGINT，整组全收（见 [2.13](./2.13-process-groups.md)）。

shell 只是编排者，机制来自内核的进程组/会话。`Ctrl+Z` 同理：发 SIGTSTP，shell 收到状态变化后打印 `[1]+ Stopped`，`fg`/`bg` 时再调 `tcsetpgrp()` 切前台组 + 发 SIGCONT。
</details>

<details>
<summary>6. 脚本里 <code>for</code> 循环调几百次外部命令，为什么慢？怎么优化？</summary>

每次外部命令都要 `fork` + `exec` 一个新进程（创建进程 + 加载程序 + 复制页表），几百次循环就是几百次进程创建开销。

优化：**①** 用 shell 内置命令/参数展开替代循环外部命令；**②** 用 `xargs` 批量；**③** 把循环逻辑写进单个 `awk`/`sed`/`python` 进程一次处理；**④** 对性能敏感的编排改用编译型程序。

本 demo 的 `self` 分支就是「编译型程序自己 fork+exec」的标准形态——一次 `fork` 换一个完整程序，比 `system()` 少了中间那层 shell。
</details>
