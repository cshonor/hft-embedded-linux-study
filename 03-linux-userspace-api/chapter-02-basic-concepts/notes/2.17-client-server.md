## 本节讲什么

客户端-服务器（C/S）是分布式系统最基础的架构模式。本节回答三个问题：

1. C/S 模型的本质是什么？请求-响应循环长什么样？
2. 同机和跨机的 C/S 分别用什么 IPC 机制？
3. 迭代服务器和并发服务器有什么区别？HFT 为什么偏爱事件驱动？

---

## 1. C/S 模型的本质

```
客户端               服务器
   │  ① 发送请求         │
   ├──────────────────→ │
   │                     │  ② 处理请求
   │  ③ 返回响应         │
   │ ←──────────────────┤
   │                     │  ④ 继续监听下一个请求
```

- **服务器**：长期运行的进程，**监听**某个通信端点（socket、FIFO、共享内存），收到请求后处理并返回响应。
- **客户端**：主动**发起连接/请求**，拿到响应后可能继续或退出。

「服务器」不是某种特殊进程，只是**角色**——一个进程在 A 交互里是服务器，在 B 交互里可能是客户端。核心特征是「**被动等待请求 → 处理 → 响应 → 再等待**」这个循环。

## 2. IPC 选择：同机 vs 跨机

| 场景 | 首选 IPC | 原因 |
|------|----------|------|
| **同机** | Unix domain socket / 管道 / 共享内存 | 零网络栈开销、零校验和、零路由 |
| **跨机** | TCP/UDP socket | 唯一能跨主机的方式 |

同机通信的排序（性能从高到低，详见 Ch43/44）：

| 机制 | 性能 | 特点 |
|------|------|------|
| 共享内存 | 最快 | 零拷贝，但需自己同步（信号量/锁） |
| Unix domain socket（`AF_UNIX`） | 快 | 有 fd 语义、可 epoll、可靠流 |
| FIFO/管道 | 快 | 字节流，仅亲缘/命名 |
| TCP loopback | 慢 | 走完整 TCP/IP 栈，同机也耗 |

**HFT 同机通信优先 `AF_UNIX` 或共享内存**——`AF_UNIX` 跳过网络栈（无 IP 头、无校验和、无路由），比 TCP loopback 快得多；共享内存最快但要自己管同步。

## 3. 服务器类型：迭代 vs 并发 vs 事件驱动

| 类型 | 处理方式 | 优点 | 缺点 |
|------|----------|------|------|
| **迭代服务器** | 逐个处理，处理完一个才接下一个 | 简单，无并发问题 | 一个慢请求阻塞所有后续请求 |
| **并发服务器（fork/线程）** | 每个请求 fork 子进程/线程 | 隔离性好，能并行 | 进程/线程创建开销大，连接多时撑不住 |
| **事件驱动** | 单线程 + I/O 多路复用（epoll） | 高并发、低开销 | 编程复杂度高（状态机） |

```
迭代：  req1 → 处理 → req2 → 处理 → req3 ...
并发：  req1 → fork 子进程处理（并行）
         req2 → fork 子进程处理（并行）
事件：  单线程 epoll 监听 N 个连接，谁有数据就处理谁（非阻塞）
```

**HFT 选型**：热路径（行情/下单）用**事件驱动**（epoll，见 Ch63），因为单线程 + 非阻塞能扛住成千上万连接、零进程切换开销；隔离性要求高、处理逻辑重的（风控引擎）用**多进程/线程池**。

## 4. HFT 中的 C/S 架构

```
交易所（服务器）          本地交易系统
      │                       │
      │  行情流（组播/UDP）     │
      ├──────────────────────→│ 行情网关（客户端）
      │                       │     │
      │                       │     │  订单簿更新（共享内存/AF_UNIX）
      │                       │     ▼
      │                       │  策略引擎
      │                       │     │
      │  下单请求（TCP）        │     │  信号（AF_UNIX）
      │ ←──────────────────────┤     ▼
      │                       │  风控/执行网关
```

典型的多级 C/S：

| 组件 | 角色 | 通信 |
|------|------|------|
| 行情网关 | 交易所的客户端 | 接收行情（组播/UDP） |
| 行情网关 → 策略 | 服务器/客户端 | 共享内存或 `AF_UNIX` 广播订单簿 |
| 策略引擎 | 风控的客户端 | `AF_UNIX` 发交易信号 |
| 风控/执行网关 | 策略的服务器 | `AF_UNIX` 收信号，再作为客户端连交易所 |

## 5. 连接 vs 无连接

| 维度 | 面向连接（TCP/`SOCK_STREAM`） | 无连接（UDP/`SOCK_DGRAM`） |
|------|------------------------------|----------------------------|
| 可靠性 | 有序、可靠、不丢 | 尽力而为，可能丢/乱序 |
| 延迟 | 有握手、确认开销 | 低，无连接建立 |
| 场景 | 下单（必须可靠） | 行情（丢一帧无所谓，快更重要） |

**HFT 的经典取舍**：行情用 UDP/组播（快、丢帧可容忍，下一帧马上来），下单用 TCP（必须可靠、有序）。这也解释了为什么行情链路和交易链路常常分开设计。

## 6. 代码示例

```c
/* 迭代服务器骨架：单连接逐个处理（教学用，生产用 epoll 事件驱动） */
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <sys/un.h>

int main(void) {
    int sfd = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr = { .sun_family = AF_UNIX };
    strcpy(addr.sun_path, "/tmp/cs_demo.sock");
    unlink(addr.sun_path);

    bind(sfd, (struct sockaddr *)&addr, sizeof(addr));
    listen(sfd, 8);
    printf("server listening on /tmp/cs_demo.sock\n");

    for (;;) {
        int cfd = accept(sfd, NULL, NULL);   /* 等一个客户端 */
        char buf[256];
        ssize_t n = read(cfd, buf, sizeof(buf) - 1);  /* 读请求 */
        buf[n] = '\0';
        printf("got request: %s", buf);
        write(cfd, "pong\n", 5);             /* 回响应 */
        close(cfd);
    }
}
```

这是最简单的**迭代服务器**（`AF_UNIX` 域，同机通信），一次只服务一个客户端。它清晰展示了 C/S 的「监听 → 收请求 → 处理 → 回响应 → 再监听」循环；生产环境要并发处理，就把 `accept` 后的处理交给子进程/线程池或改用 epoll。

<summary>代码自测（Q&A）</summary>

**Q1：客户端-服务器模型的基本流程是什么？**
A：服务器长期运行、监听通信端点，收到客户端请求后处理并返回响应，然后继续等待下一个请求；客户端主动发起请求、接收响应。核心是「被动等待 → 处理 → 响应 → 再等待」的循环。「服务器」只是角色，不是特殊进程——一个进程可在不同交互里既当服务器又当客户端。

**Q2：迭代服务器和并发服务器的区别是什么？**
A：迭代服务器**逐个处理**请求，处理完一个才 `accept` 下一个——简单无并发问题，但一个慢请求会阻塞所有后续请求。并发服务器为每个请求 **fork 子进程或起线程**并行处理——隔离好、能并行，但进程/线程创建开销大、连接多时撑不住。两者之上还有「事件驱动」（单线程 + epoll 多路复用），HFT 热路径的首选。

**Q3：同机和跨机通信分别用什么 IPC？为什么？**
A：同机优先 **Unix domain socket / 管道 / 共享内存**——`AF_UNIX` 跳过网络栈（无 IP 头、无校验和、无路由），比 TCP loopback 快得多；共享内存最快但需自己同步。跨机只能 **TCP/UDP socket**（唯一能跨主机的方式）。所以「同机用 TCP loopback」是常见浪费，应改 `AF_UNIX`。

**Q4：HFT 里为什么行情用 UDP、下单用 TCP？**
A：因为两者可靠性需求不同：行情是**高频、可容忍丢帧**的数据流（丢一帧下一帧马上来），用 UDP/组播换更低延迟、无连接建立开销；下单是**必须可靠有序**的关键指令（丢一单可能造成损失），用 TCP 保证不丢、有序。所以行情链路和交易链路常分开设计。

**Q5：HFT 交易系统里「共享内存」和「Unix domain socket」分别用在什么场景？**
A：**共享内存**用于「零拷贝高频数据共享」——如行情网关把订单簿写进共享内存，多个策略进程 `mmap` 同一块物理页直接读（见 2.8），最快但需信号量/锁同步；**`AF_UNIX`** 用于「需要 fd 语义 + 可 epoll 的消息通信」——如策略给风控发交易信号，有连接管理、可多路复用、可靠流。一句话：极致性能的裸数据用共享内存，要可靠消息/多路复用用 `AF_UNIX`。
