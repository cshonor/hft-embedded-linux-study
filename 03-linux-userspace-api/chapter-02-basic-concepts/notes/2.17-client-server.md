## 本节讲什么

客户端-服务器（C/S）是分布式系统最基础的架构模式。本节回答三个问题：

1. C/S 模型的本质是什么？请求-响应循环长什么样？
2. 同机和跨机的 C/S 分别用什么 IPC 机制？
3. 迭代服务器和并发服务器有什么区别？HFT 为什么偏爱事件驱动？

本节要补的是**四步循环的真实跑通**：`socket → bind → listen → accept → read/write`，而且**用两套完全不同的地址（`AF_UNIX` 文件路径 / `AF_INET` IP:端口）各跑一遍**，证明「换地址不换代码形状」。

## 要点

### 一、C/S 的本体就是一个循环

```
客户端               服务器
   │  ① 发送请求         │
   ├──────────────────→ │
   │                     │  ② 处理请求
   │  ③ 返回响应         │
   │ ←──────────────────┤
   │                     │  ④ 继续监听下一个请求
```

- **服务器**：长期运行的进程，**先 `bind` 到一个已知地址**（这是「已知」的来源），再循环 `accept`。
- **客户端**：主动 `connect` 发起，拿到响应后可能继续或退出。

**「服务器」不是某种特殊进程，只是角色**——一个进程在 A 交互里是服务器，在 B 交互里可能是客户端（HFT 里的网关进程就是典型的「双重身份」：对交易所是客户端，对策略进程是服务器）。核心特征是「**被动等待请求 → 处理 → 响应 → 再等待**」这个循环。

### 二、服务器端的四个系统调用，顺序不能乱

```c
int sfd = socket(AF_UNIX, SOCK_STREAM, 0);   /* ① 建一个「通信端点」 */
bind(sfd, addr, addrlen);                     /* ② 给它一个已知地址 */
listen(sfd, backlog);                         /* ③ 转为「被动监听」——内核开始排队连接 */
int cfd = accept(sfd, NULL, NULL);            /* ④ 取出一个已建立的连接（阻塞） */
read(cfd, buf, n);  write(cfd, resp, m);      /* ⑤ 收请求 / 回响应 */
close(cfd);                                   /* ⑥ 关掉这个连接 */
```

| 步骤 | 关键点 |
|------|--------|
| `socket()` | **只创建端点，还没有地址**；此时 `connect` 会失败 |
| `bind()` | 给端点绑地址。`AF_UNIX` 走**文件系统路径**（会在磁盘上留一个 socket 文件）；`AF_INET` 走 `IP:port` |
| `listen()` | **这一步之后内核才开始排队连接**。`backlog` 是已完成/待完成连接队列的上限 |
| `accept()` | 返回**一个新的 fd**（`cfd`），专属于这一个连接；`sfd` 继续用于接受下一个 |
| 客户端 | **不需要 `bind`**——内核自动分配临时端口（本节段 ② 实测拿到 `57302`） |

⚠️ **`accept` 返回的是新 fd，不是 `sfd` 本身**——这是最常见的理解错误。`sfd` 是「门」，`cfd` 是「进来的那个人」。

### 三、同机 vs 跨机：两套地址，一种代码形状

| 场景 | 地址族 | 地址是什么 | 首选机制 |
|------|--------|-----------|----------|
| **同机** | `AF_UNIX` | **文件系统路径**（`/tmp/x.sock`） | Unix domain socket / 管道 / 共享内存 |
| **跨机** | `AF_INET` / `AF_INET6` | **`IP:port`** | TCP / UDP |

同机通信的性能排序（详见 [Ch43](../../chapter-43-ipc-overview/README.md)/[44](../../chapter-44-pipes-fifos/README.md)）：

| 机制 | 性能 | 特点 |
|------|------|------|
| 共享内存 | **最快** | 零拷贝，但需自己同步（信号量/锁），见 [2.8](./2.8-memory-mappings.md) |
| `AF_UNIX` socket | 快 | 有 fd 语义、可 `epoll`、可靠流 |
| FIFO / 管道 | 快 | 字节流，仅亲缘或具名 |
| TCP loopback | **慢** | 走完整 TCP/IP 栈——**同机也耗** |

**关键**：`connect` / `accept` / `read` / `write` 的代码形状**在 `AF_UNIX` 和 `AF_INET` 下完全一样**（本节段 ① 和段 ② 就是同一段逻辑跑两遍），只有 `struct sockaddr` 的具体类型不同：

| | `AF_UNIX` | `AF_INET` |
|---|---|---|
| 地址结构 | `struct sockaddr_un` | `struct sockaddr_in` |
| 字段 | `.sun_family` / `.sun_path` | `.sin_family` / `.sin_port` / `.sin_addr` |
| 端口字节序 | — | **`htons()`**（网络字节序 = 大端） |

所以「同机用 TCP loopback 是浪费」——改成 `AF_UNIX` **几乎只改地址结构体**，性能立刻上一个档次。

### 四、五种服务器形态：从「够用」到「能扛」

| 形态 | 一句话思路 | 代价 / 上限 | 归属章节 |
|------|-----------|------------|----------|
| **迭代（iterative）** | `accept` → 处理 → 再 `accept` | 一次一个客户端；慢客户端**阻塞所有后续** | 本节 demo |
| **fork-per-conn** | `accept` 后 `fork` | 简单；进程创建开销 + N × 内存 | [Ch60](../../chapter-60-server-design/README.md) |
| **thread-per-conn** | `accept` 后 `pthread_create` | 更轻；共享状态要加锁 | [Ch60](../../chapter-60-server-design/README.md) |
| **process/thread pool** | 预先建一批 worker，在 worker 里 `accept` | 资源有界；仍有 per-conn 开销 | [Ch60](../../chapter-60-server-design/README.md) |
| **event loop（epoll）** | 单线程 + 多 fd + 非阻塞 | **吞吐/延迟最优**；回调地狱 | [Ch63.4](../../chapter-63-alternative-i-o-models/notes/63.4-the-epoll-api.md) |
| **io_uring** | 批量提交、批量收割 | **系统调用最少**；最新、可移植性差 | [Ch63.4 epoll](../../chapter-63-alternative-i-o-models/notes/63.4-the-epoll-api.md)（io_uring 是 TLPI 之后的新机制，书里没有） |

**HFT 的选型**：行情/下单服务器几乎都落在**最后两行**——单线程 + `epoll` / `io_uring`，把「每次请求的上下文切换」压到零。隔离性要求高、逻辑重的（风控引擎）才用多进程。

### 五、必须处理 `SIGPIPE`，否则一个异常客户端能打挂服务器

若客户端**提前 `close`**，服务器再 `write()` 会收到 **`SIGPIPE`**，而它的**默认动作是终止整个进程**——一个异常客户端就能打挂服务器。

两条标准做法（**一般两条都上**）：

| 做法 | 代码 | 特点 |
|------|------|------|
| 全局忽略 | `signal(SIGPIPE, SIG_IGN)` 或 `sigaction` | 之后靠 `write` 的返回值（`EPIPE`）判错 |
| 单次屏蔽 | `send(fd, buf, n, MSG_NOSIGNAL)` | **只对本次调用**生效，不影响全局 |

> 注意 `send()` 与 `write()` 的差别就在这里：`write` **没有** `MSG_NOSIGNAL` 这种参数，只能靠全局忽略。

### c2_17 最小 C/S：`AF_UNIX` 与 `AF_INET` 各跑一遍

[`../code/c2_17_client_server.c`](../code/c2_17_client_server.c) 分四段：

| 段 | 做什么 | 钉死什么 |
|----|--------|----------|
| ① | `AF_UNIX`：`bind("/tmp/c2_17.sock")` + `stat()` 看类型 + `listen` + `fork` 客户端 `connect` | `socket` 文件真的存在（`st_mode=0775`、`S_ISSOCK=1`） |
| ② | `AF_INET`：`bind(127.0.0.1:47123)` + 同一套逻辑 | **换地址不换代码形状**；客户端源端口由内核分配 |
| ③ | 六种服务器形态对照表 | 从「够用」到「能扛」的谱系 |
| ④ | 讲清 `SIGPIPE` 与两条对策 | **不制造断连**（会终止进程），只讲机制 |

```c
/* TLPI 第 2 章 §2.17 —— 客户端/服务器架构：最小的请求-响应回路
 *
 * 编译：gcc -O0 -Wall -Wextra c2_17_client_server.c -o c2_17
 * 运行：./c2_17
 *
 * 本节要钉死的事实：
 *   ① C/S 的本体是四步循环：socket → bind+listen → accept → read/write。
 *      「服务器」不是特殊的进程，只是先 bind 到一个已知地址、再循环 accept。
 *   ② 这里的「迭代服务器」一次只服务一个连接；生产要么多进程/多线程，
 *      要么用 epoll 做事件驱动。
 *   ③ AF_UNIX（同机，走文件系统路径）与 AF_INET（跨机，走 IP:port）是两套地址，
 *      但 accept/read/write 的代码形状完全一样。
 *   ④ 客户端只要 connect 成功就能收发 —— 不需要 bind。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <signal.h>
#include <sys/wait.h>
#include <sys/stat.h>
#include <sys/socket.h>
#include <sys/un.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <sys/types.h>

#define UNIX_PATH "/tmp/c2_17.sock"
#define TCP_PORT  47123

/* ---------- 通用：把一条请求处理掉（server 侧） ---------- */
static void serve_one(int cfd, const char *tag)
{
    char buf[256];
    ssize_t n = read(cfd, buf, sizeof(buf) - 1);
    if (n <= 0) { printf("  [%s] 读请求失败/为空 (n=%zd)\n", tag, n); return; }
    buf[n] = '\0';
    printf("  [%s] 收到请求: \"%s\"\n", tag, buf);

    char resp[300];
    snprintf(resp, sizeof(resp), "ACK:%.*s", (int)n, buf);
    if (write(cfd, resp, strlen(resp)) < 0) perror("write response");
    printf("  [%s] 已回响应: \"%s\"\n", tag, resp);
}

/* ================= AF_UNIX：同机 ================= */
static void demo_unix(void)
{
    printf("=== ① AF_UNIX：同一台机器上的 C/S ===\n");
    unlink(UNIX_PATH);

    int sfd = socket(AF_UNIX, SOCK_STREAM, 0);
    if (sfd < 0) { perror("socket"); return; }

    struct sockaddr_un addr;
    memset(&addr, 0, sizeof(addr));
    addr.sun_family = AF_UNIX;
    strncpy(addr.sun_path, UNIX_PATH, sizeof(addr.sun_path) - 1);

    if (bind(sfd, (struct sockaddr *)&addr, sizeof(addr)) < 0) { perror("bind"); close(sfd); return; }
    printf("  server: bind(\"%s\") 成功 —— 这个路径现在是个 socket 文件\n", UNIX_PATH);

    /* 看一眼它真的变成了文件树上的 socket 类型 */
    struct stat st_buf;
    if (stat(UNIX_PATH, &st_buf) == 0)
        printf("  server: stat() 看到 st_mode=%04o  S_ISSOCK=%d\n",
               st_buf.st_mode & 07777, S_ISSOCK(st_buf.st_mode));

    if (listen(sfd, 8) < 0) { perror("listen"); close(sfd); return; }
    printf("  server: listen(backlog=8) —— 这一步之后内核才开始排队连接\n");

    /* 客户端另起一个进程，模拟"另一个程序" */
    fflush(NULL);
    pid_t pid = fork();
    if (pid == 0) {
        close(sfd);
        int c = socket(AF_UNIX, SOCK_STREAM, 0);
        if (c < 0) _exit(1);
        if (connect(c, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
            printf("  [client] connect 失败: %s\n", strerror(errno));
            fflush(NULL);
            _exit(1);
        }
        printf("  [client] connect 成功 —— 我没 bind，直接连就行\n");
        const char *req = "GET /price/AAPL";
        if (write(c, req, strlen(req)) < 0) perror("write");
        char rb[256];
        ssize_t k = read(c, rb, sizeof(rb) - 1);
        if (k > 0) { rb[k] = '\0'; printf("  [client] 收到响应: \"%s\"\n", rb); }
        close(c);
        fflush(NULL);
        _exit(0);
    }

    int cfd = accept(sfd, NULL, NULL);
    if (cfd < 0) { perror("accept"); }
    else { serve_one(cfd, "server"); close(cfd); }

    int st; waitpid(pid, &st, 0);
    close(sfd);
    unlink(UNIX_PATH);
    printf("  -> 四步走完：socket -> bind -> listen -> accept -> read/write\n");
}

/* ================= AF_INET：跨机（这里用 loopback） ================= */
static void demo_inet(void)
{
    printf("\n=== ② AF_INET：换一套地址，代码形状不变 ===\n");
    int sfd = socket(AF_INET, SOCK_STREAM, 0);
    if (sfd < 0) { printf("  socket(AF_INET) 失败: %s\n", strerror(errno)); return; }

    int on = 1;
    setsockopt(sfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));

    struct sockaddr_in sa;
    memset(&sa, 0, sizeof(sa));
    sa.sin_family = AF_INET;
    sa.sin_port = htons(TCP_PORT);
    sa.sin_addr.s_addr = htonl(INADDR_LOOPBACK);        /* 127.0.0.1 */

    if (bind(sfd, (struct sockaddr *)&sa, sizeof(sa)) < 0) {
        printf("  bind(127.0.0.1:%d) 失败: %d (%s)\n", TCP_PORT, errno, strerror(errno));
        printf("  -> 本环境不允许建 INET socket（无网络命名空间权限），如实记录\n");
        close(sfd);
        return;
    }
    if (listen(sfd, 8) < 0) { perror("listen"); close(sfd); return; }
    printf("  server: bind(127.0.0.1:%d) + listen 成功\n", TCP_PORT);

    fflush(NULL);
    pid_t pid = fork();
    if (pid == 0) {
        close(sfd);
        int c = socket(AF_INET, SOCK_STREAM, 0);
        if (c < 0) _exit(1);
        if (connect(c, (struct sockaddr *)&sa, sizeof(sa)) < 0) {
            printf("  [client] connect 127.0.0.1:%d 失败: %s\n", TCP_PORT, strerror(errno));
            fflush(NULL);
            _exit(1);
        }
        /* 看看连上之后本地地址是什么：内核自动分配了源端口 */
        struct sockaddr_in peer;
        socklen_t plen = sizeof(peer);
        if (getsockname(c, (struct sockaddr *)&peer, &plen) == 0)
            printf("  [client] 连接成功，内核给我分配的源端口 = %u\n",
                   ntohs(peer.sin_port));
        const char *req = "PING";
        if (write(c, req, strlen(req)) < 0) perror("write");
        char rb[128];
        ssize_t k = read(c, rb, sizeof(rb) - 1);
        if (k > 0) { rb[k] = '\0'; printf("  [client] 收到响应: \"%s\"\n", rb); }
        close(c);
        fflush(NULL);
        _exit(0);
    }

    int cfd = accept(sfd, NULL, NULL);
    if (cfd < 0) perror("accept");
    else { serve_one(cfd, "server"); close(cfd); }
    int st; waitpid(pid, &st, 0);
    close(sfd);
}
```

**解读**

1. **段 ① 的 `bind` 成功意味着磁盘上多了一个文件**——`AF_UNIX` 的地址就是文件系统路径，所以：

   | 现象 | 含义 |
   |------|------|
   | `bind` 成功 | 内核在 `/tmp/c2_17.sock` 建了一个类型为 **socket** 的 inode |
   | `stat()` 看到 `st_mode=0775` | 权限位 0775（属主/组可读写、其他可读执行——注意 socket 的权限语义见 [2.3](./2.3-users-and-groups.md)） |
   | `S_ISSOCK=1` | 类型判定为 **socket**（对照 [2.4](./2.4-directory-hierarchy.md) 的 7 种文件类型） |
   | 程序退出后文件**残留** | 所以 demo 开头要 `unlink(UNIX_PATH)`——**否则第二次运行 `bind` 会 `EADDRINUSE`** |

   **最后这条是生产事故高发点**：`AF_UNIX` 的 socket 文件**不会随进程退出自动删除**（除非挂载时加 `auto_unlink` 或显式 `unlink`）。所以服务端启动脚本必须**先 `unlink` 再 `bind`**，或者用「抽象命名空间」（`sun_path[0] == '\0'`，Linux 特有，无名、不占文件）。

2. **段 ② 的「源端口 = 57302」证明了「客户端不需要 `bind`」**：

   ```
   服务器：bind(127.0.0.1:47123)   ← 显式端口
   客户端：没有 bind → 内核分配 57302（临时端口）
   ```

   这个 `57302` 来自内核的**临时端口范围**（`/proc/sys/net/ipv4/ip_local_port_range`，通常 32768–60999）。**客户端唯一需要知道的只有服务器的地址**——这是 C/S 非对称性的体现。

   ⚠️ 服务端用固定端口（`47123`）来确保「客户端能找到我」；客户端用随机端口是因为「没有别人需要找我」。

3. **「代码形状不变」是本段最值钱的结论**，对比两张表：

   | | `AF_UNIX`（段 ①） | `AF_INET`（段 ②） |
   |---|---|---|
   | `socket()` | `AF_UNIX` | `AF_INET` |
   | 地址结构 | `struct sockaddr_un` | `struct sockaddr_in` |
   | 地址内容 | `.sun_path = "/tmp/c2_17.sock"` | `.sin_addr = 127.0.0.1` + `.sin_port = htons(47123)` |
   | `bind`/`listen`/`accept`/`read`/`write` | **完全相同** | **完全相同** |

   所以**性能优化可以只换地址层**：把 `AF_INET` + `127.0.0.1` 换成 `AF_UNIX`，业务代码一行不改，就省掉了整个 TCP/IP 栈的开销（IP 头、校验和、拥塞控制、`TIME_WAIT`）。**这是同机通信最划算的一处改动**。

4. **段 ③ 的六行是「服务器形态」的完整谱系**，值得按「代价随什么增长」来读：

   | 形态 | 代价随什么增长 |
   |------|--------------|
   | iterative | **客户端等待时间**（线性增长，最差） |
   | fork / thread-per-conn | **连接数 × 内存/线程栈**（[2.12](./2.12-threads.md)：每线程 8MB 虚拟栈） |
   | pool | **固定**（有界资源，但请求排队） |
   | epoll / io_uring | **几乎不增长**（单线程、无 per-conn 上下文切换） |

   **表末那句「HFT 里几乎都在最后两行，把每次请求的上下文切换压到零」是全表结论**——延迟敏感系统的第一原则是**消除上下文切换**，不是「多开线程」。

5. **段 ④ 是本 demo **故意不跑**的部分，也是重要的一课**：不制造断连是因为**那会真的终止进程**（`SIGPIPE` 默认动作），演示会失败。所以这里只能讲机制。这体现了两点：

   - **`SIGPIPE` 的危险性**：它**不是「返回错误」而是「杀进程」**——新手常以为 `write` 会返回 `EPIPE`，实际是进程**先死了**；
   - **`MSG_NOSIGNAL` 是更精细的控制**：`send()` 独有的参数，可以「只对这次调用忽略 `SIGPIPE`」，不影响全局。**库代码里不要随便改全局信号处理**（会破坏调用方的预期），所以库常加 `MSG_NOSIGNAL`。

   ⚠️ 更隐蔽的是：**`SIGPIPE` 也可能发生在 `read` 之外的路径**（比如 `epoll` 里对端半关闭后写）。所以事件驱动服务器**必须在启动时 `signal(SIGPIPE, SIG_IGN)`**，否则一个客户端异常断连就能打挂整个服务。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 同机通信应改用 `AF_UNIX` | 段 ① vs ②：只换地址结构体，省掉整个 TCP/IP 栈（无 IP 头/校验和/路由/`TIME_WAIT`）。**「同机用 TCP loopback」是最常见的浪费** |
| **`AF_UNIX` socket 文件不自动删，重启报 `EADDRINUSE`** | 段 ① 的 `unlink` 不是装饰。**交易服务的 systemd 单元必须处理这个**（或改用**抽象命名空间**：`sun_path[0]='\0'`，无名、随进程消失） |
| 🚨 **不处理 `SIGPIPE` 会被一个客户端打挂** | 段 ④：`SIGPIPE` 默认动作是**终止进程**。事件驱动服务器**必须在启动时 `signal(SIGPIPE, SIG_IGN)`**；库代码用 `MSG_NOSIGNAL` 更克制 |
| 行情用 UDP / 组播，下单用 TCP | `SOCK_DGRAM` 无连接建立、丢帧可容忍（下一帧马上来）；`SOCK_STREAM` 可靠有序（丢一单就是损失）。**行情与交易链路因此常分开设计** |
| 单线程 `epoll` 而非线程池 | 段 ③ 表的末两行：**消除上下文切换**是延迟敏感系统的第一原则。Thread-per-conn 在延迟上是灾难（每次唤醒都要调度） |
| 客户端端口是内核分配的 | 段 ② 实测 `57302`。**防火墙/路由规则要按「服务端固定端口 + 客户端临时端口范围」双向放行**，只开一个方向会导致随机失败 |
| 嵌入式设备端口耗尽 | 同机大量短连接会耗尽**临时端口范围**（`ip_local_port_range`，默认约 28k 个）。用完 → `connect` 报 `EADDRNOTAVAIL`。**长期运行的嵌入式服务用长连接或 `AF_UNIX`** 规避 |
| **`io_uring` 要较新内核** | 段 ③ 最后一行「最新、可移植性差」——嵌入式用的内核常常较旧（`4.19`/`5.4` LTS），此时 `io_uring` 不可用，`epoll` 才是现实选择 |
| 嵌入式调试常用「单进程既当服务器又当客户端」 | 要点一：服务器只是**角色**。设备自检程序常这样：既连自己的端口发探测包，又监听回包 |

## 自测题

<details>
<summary>1. 客户端-服务器模型的基本流程是什么？为什么说「服务器」不是特殊进程？</summary>

流程（要点二的四步）：

```
服务器：socket → bind（已知地址）→ listen → 循环 { accept → read → write → close }
客户端：socket → connect → write → read → close
```

核心是「**被动等待 → 处理 → 响应 → 再等待**」的循环。

**「服务器」不是特殊进程，只是角色**：

| 依据 | 说明 |
|------|------|
| 内核侧 | 服务器进程和普通进程**都是 `task_struct`**，没有「服务器」这种类型 |
| 判别标准 | 只是「**先 `bind` 到一个已知地址**」——这才是它「能被找到」的原因 |
| 可互换 | 一个进程可在不同交互里既当服务器又当客户端（HFT 网关：对交易所是客户端，对策略是服务器） |

**`bind` 是「服务器身份」的唯一技术标志**——客户端正因为不 `bind`，所以没有别人能找它。
</details>

<details>
<summary>2. <code>listen()</code> 做了什么？不调它会怎样？</summary>

`listen(sfd, backlog)` 把 socket 从「主动」转为「**被动监听**」状态，**这一步之后内核才开始排队进来的连接**。

**不调 `listen()` 会怎样**：`accept()` 会失败，`connect()` 会被拒绝（`ECONNREFUSED`）。因为 socket 还处于「可主动 `connect`」的状态，没有监听队列。

段 ① 的实测：

```text
  server: bind("/tmp/c2_17.sock") 成功 —— 这个路径现在是个 socket 文件
  server: listen(backlog=8) —— 这一步之后内核才开始排队连接
```

**`backlog` 的语义**：已完成三次握手的连接队列（`accept` 队列）长度上限。队列满时，新的 `connect` 表现取决于 `/proc/sys/net/ipv4/tcp_abort_on_overflow`——默认**丢弃**（客户端会重试），开启后直接 `RST`。

**顺序不能乱**：`socket → bind → listen → accept`。**颠倒 `bind` 和 `listen` 会 `EINVAL`**。
</details>

<details>
<summary>3. <code>accept()</code> 返回什么？为什么返回新 fd 而不是用原来的？</summary>

`accept()` 返回**一个新的 fd**（通常叫 `cfd` / `connfd`），专属于**这一个连接**；原来的监听 fd（`sfd`）**继续留在监听状态**用于接受下一个连接。

段 ① 的输出里 `[client]` 和 `[server]` 的消息交替出现，就是两个 fd 在协作：

```
sfd  (监听 fd)        ← 一直存在，被 accept 反复使用
 └─ cfd (连接 fd) 1   ← 处理完就 close
 └─ cfd (连接 fd) 2   ← 下一个连接
```

**为什么必须是新 fd**：

| 理由 | 说明 |
|------|------|
| **并发** | 多个连接要能**同时**存在，各自有独立的读写缓冲和连接状态 |
| **生命周期不同** | `sfd` 活到服务结束；`cfd` 随单个连接结束而 `close` |
| **`close(cfd)` 不等于停止服务** | 若用 `sfd` 处理，一个 `close` 就把服务关了 |

**这是最常见的理解错误**——「`accept` 之后还用 `sfd` 收发」在测试里可能碰巧工作（单连接），一并发就崩。
</details>

<details>
<summary>4. 同机和跨机通信分别用什么？为什么 <code>AF_UNIX</code> 比 TCP loopback 快？</summary>

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| **同机** | `AF_UNIX` / 共享内存 / 管道 | 跳过网络栈 |
| **跨机** | `AF_INET`（TCP/UDP） | 唯一能跨主机的方式 |

**`AF_UNIX` 比 TCP loopback 快的原因**（要点三）：

| 省掉的 | 说明 |
|--------|------|
| IP 头 / TCP 头 | 不做封装解析 |
| 校验和计算 | 不用逐包算 checksum |
| 路由查找 | 不需要路由表 |
| 拥塞控制 / `TIME_WAIT` | 没有三次握手、没有状态机 |
| 拷贝层数 | `AF_UNIX` 常能走更少的缓冲 |

而**代码几乎不用改**（段 ① vs ② 对比）：只换 `struct sockaddr` 类型和 `socket()` 的第一个参数。

**同机通信性能排序**：共享内存（最快）> `AF_UNIX` > FIFO/管道 > TCP loopback（最慢，同机也走完整栈）。

**结论**：同机「用 TCP loopback」是常见浪费。**改这一处，性能立刻上一个档次，业务代码一行不改**。
</details>

<details>
<summary>5. 迭代服务器和并发服务器的区别？为什么 HFT 偏爱事件驱动？</summary>

| 形态 | 处理方式 | 代价增长维度 |
|------|----------|-------------|
| **迭代** | 逐个处理，`accept` → 处理 → 再 `accept` | **客户端等待时间**（线性增长） |
| **并发（fork/线程）** | 每个请求 `fork` / `pthread_create` | **连接数 × 内存**（每线程 8MB 虚拟栈，见 [2.12](./2.12-threads.md)） |
| **线程/进程池** | 预建 worker | 固定（有界，但请求排队） |
| **事件驱动（epoll）** | 单线程 + 多 fd + 非阻塞 | **几乎不增长** |

段 ③ 的表就是这六行的完整谱系。

**HFT 偏爱事件驱动的原因**（段 ③ 末两行 + 结论句）：

1. **消除上下文切换**——「把**每次请求的上下文切换**压到零」是延迟敏感系统的第一原则。Thread-per-conn 每个请求都要唤醒一个线程（调度开销微秒级），在纳秒级竞争里是灾难；
2. **零 per-conn 固定开销**——单线程处理 N 个连接，没有 N × 栈、没有 N 个调度实体；
3. **回调写法可用状态机化解**——「callbacks get hairy」是真的，但 HFT 通常用**有限状态机 + 手写解析**，复杂度可控。

**隔离性要求高、逻辑重的（风控）才用多进程**——用进程做隔离买安全，用 epoll 买延迟。
</details>

<details>
<summary>6. 为什么服务器必须处理 <code>SIGPIPE</code>？两条对策有什么区别？</summary>

**原因**：若客户端提前 `close`，服务器再 `write()` 会收到 `SIGPIPE`，而它的**默认动作是终止整个进程**——**一个异常客户端就能打挂服务器**。段 ④ 强调的危险性在于：它**不是「返回错误」而是「杀进程」**，新手常以为 `write` 会返回 `EPIPE`，实际是进程**先死了**。

| 对策 | 代码 | 特点 |
|------|------|------|
| **全局忽略** | `signal(SIGPIPE, SIG_IGN)` / `sigaction` | 之后靠 `write` 返回值（`errno == EPIPE`）判错；**影响整个进程** |
| **单次屏蔽** | `send(fd, buf, n, **MSG_NOSIGNAL**)` | 只对本次调用生效；**不影响全局** |

**两条一般都要上**，原因不同：

- **全局忽略**是服务器的**启动必备**——因为 `SIGPIPE` 可能从很多地方触发（`epoll` 里对端半关闭后写、`write` 到已断的管道等），逐个 `send` 加 `MSG_NOSIGNAL` 容易漏；
- **`MSG_NOSIGNAL`** 适合**库代码**——库不该擅自改全局信号处理（会破坏调用方的预期），所以用 `MSG_NOSIGNAL` 更克制。

⚠️ 注意：`write()` **没有** `MSG_NOSIGNAL` 这种参数（它是 `send` 独有的），所以对用 `write` 的代码只能走全局忽略。
</details>

<details>
<summary>7. <code>AF_UNIX</code> 的 socket 文件在进程退出后会自动消失吗？怎么办？</summary>

**不会自动消失。** 段 ① 实测 `bind("/tmp/c2_17.sock")` 成功之后，磁盘上就多了一个 **socket 类型的 inode**（`st_mode=0775`、`S_ISSOCK=1`）。进程退出后这个文件**仍然留在文件系统上**。

**后果**：第二次启动服务时 `bind` 同一个路径会报 **`EADDRINUSE`**（`Address already in use`）——这是**生产事故高发点**。

**三种解法**（要点二/关联表）：

| 解法 | 做法 | 适用 |
|------|------|------|
| **启动前 `unlink`** | `unlink(path)` 再 `bind`（本节 demo 的做法） | 简单直接；**要小心别删掉别的实例正在用的 socket** |
| **抽象命名空间** | `sun_path[0] = '\0'`，用名字而不是文件 | **Linux 特有**；不占文件、随进程消失、无需 `unlink` |
| 挂载选项 | `devpts`/`tmpfs` 的 `auto_unlink`（部分场景） | 依赖挂载配置 |

**实战提醒**：

- systemd 单元要处理这个（`ExecStartPre=-/bin/rm -f /run/xxx.sock`，前面的 `-` 表示「失败也继续」）；
- 嵌入式只读根文件系统（见 [2.3](./2.3-users-and-groups.md) 的 `EROFS`）**必须**用抽象命名空间——因为 `/tmp` 可能就是只读的。

**顺带一个相关坑**：`TCP` 的 `TIME_WAIT` 是**同类问题在网络侧的版本**——服务重启时端口还被旧连接占着。用 `SO_REUSEADDR` 规避（`AF_UNIX` 没有这个问题，因为它根本不占端口）。
</details>

<details>
<summary>8. 客户端为什么不需要 <code>bind()</code>？</summary>

因为**客户端只需要「能找到服务器」，不需要「被服务器找到」**。

`connect()` 时，内核会**自动为客户端分配一个临时端口**（来自 `/proc/sys/net/ipv4/ip_local_port_range`，通常 32768–60999）。段 ② 实测：

```text
  server: bind(127.0.0.1:47123) + listen 成功
  [client] 连接成功，内核给我分配的源端口 = 57302
```

**C/S 的非对称性**就在这里：

| | 需要 `bind` 吗 | 原因 |
|---|---|---|
| **服务器** | ✅ 必须（固定端口） | 客户端要知道连哪里 |
| **客户端** | ❌ 不需要 | 没有别人需要找它 |

**推论**（HFT/嵌入式关联表）：

- **防火墙规则要双向看**：「服务端固定端口」入方向 + 「客户端临时端口范围」出方向。只开一个方向会导致**随机失败**（这次能连、下次不能）；
- **端口耗尽**：同机大量短连接会耗尽临时端口（约 28k 个），用完 → `connect` 报 `EADDRNOTAVAIL`。**长期运行的嵌入式服务该用长连接或 `AF_UNIX`**。

`AF_UNIX` 下同理：客户端不 `bind`（不创建文件），但注意**匿名 `AF_UNIX` 客户端无法被服务端 `getpeername` 拿到地址**——需要身份识别的话要显式 `bind` 或传 `SO_PASSCRED`。
