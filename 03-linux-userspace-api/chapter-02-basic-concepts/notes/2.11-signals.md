## 本节讲什么

信号是内核向进程投递的**异步通知**（软件中断）。本节回答三个问题：

1. 信号在内核里怎么表示？（`sighand_struct`）
2. `kill` 和 `tgkill` 有什么区别？（进程级 vs 线程级）
3. 为什么 HFT 热路径要小心信号？

完整展开在 Ch20-22，这里先建立「信号 = 异步抢占」的核心心智。

---

## 1. 信号的本质与内核表示

信号不是「数据通道」，而是**一个编号 + 一个待处理标志**。标准信号（1-31）**不排队**——同一信号连发多次，进程可能只看到一次（实时信号 34-64 才排队，见 Ch22）。

内核侧，每个进程的 `task_struct` 挂一个 `sighand_struct`：

```c
struct sighand_struct {              /* include/linux/sched/signal.h:20 */
    ...
    struct k_sigaction action[_NSIG];  /* :24 每个信号一个处理动作 */
};
```

`action[SIGINT]` 存的就是「SIGINT 该怎么处理」：默认动作 / 忽略 / 自定义处理器（`sigaction` 注册的那个）。

## 2. 发送信号的三个系统调用

```c
SYSCALL_DEFINE2(kill,  pid_t, pid, int, sig)                       /* kernel/signal.c:3807 */
SYSCALL_DEFINE3(tgkill, pid_t, tgid, pid_t, pid, int, sig)         /* :3988 线程级 */
SYSCALL_DEFINE2(tkill, pid_t, pid, int, sig)                       /* :4004 线程级(旧) */
```

| 调用 | 目标 | 说明 |
|------|------|------|
| `kill(pid, sig)` | **整个进程组** | `pid>0` 发该进程；`pid==0` 发同进程组；`pid==-1` 发所有（有权限的） |
| `tgkill(tgid, pid, sig)` | **指定线程** | `tgid` 是进程（线程组），`pid` 是具体线程（tid） |
| `tkill(pid, sig)` | 指定线程 | 老接口，等价 `tgkill` 但少了线程组校验，已不推荐 |

> 多线程进程里，`kill` 投递的信号由**任意一个未屏蔽该信号的线程**处理（内核挑一个）；`tgkill` 才能精确投给某个 tid。这正是「要定向通知某个工作线程」时必须用 `tgkill` 的原因。

## 3. 信号生命周期

```
发送方: kill(pid, sig) ──► 内核: 置目标 pending 标志
                                    │ 目标阻塞该信号？ ──是──► 挂起，等解除阻塞
                                    │否
                                    ▼
                         目标进程: 从内核态返回用户态时，检查 pending
                                    │ 有自定义 handler
                                    ▼
                         切换到用户态 handler 执行 → 返回中断点继续
```

**关键**：信号的**处理时机**是「目标进程下一次从内核态返回用户态」——不是发送那一刻立即执行。所以：
- 一个正在「纯用户态死循环」的进程，能收到信号（因为时钟中断会周期性把它拉进内核再返回）
- 一个卡在 D 状态（不可中断睡眠）的进程，`kill -9` 也打不断（信号投递被推迟到 I/O 返回）

## 4. 常见信号速览

| 信号 | 编号 | 默认动作 | 来源 | 可否捕获/阻塞 |
|------|:---:|---------|------|:---:|
| SIGINT | 2 | 终止 | Ctrl+C | ✅ |
| SIGSEGV | 11 | 终止 + core | 非法内存访问 | ✅ |
| SIGTERM | 15 | 终止 | `kill` 默认 | ✅ |
| SIGKILL | 9 | 终止 | `kill -9` | ❌ 不可捕获/阻塞 |
| SIGSTOP | 19 | 停止 | 作业控制 | ❌ 不可捕获/阻塞 |
| SIGCHLD | 17 | 忽略 | 子进程状态变化 | ✅ |

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 信号造成延迟毛刺 | 信号是**异步抢占**——handler 执行时打断主循环，热路径应 `pthread_sigmask` 屏蔽，让信号只在专用线程处理 |
| 优雅停机 | `SIGTERM` handler 置「停止」标志，主循环看到后刷缓冲、释放资源再退出（比 `kill -9` 安全） |
| 段错误溯源 | `SIGSEGV` 默认 dump core，配合 03.6 模块的 coredump 分析定位崩溃点 |
| 处理信号首选 | HFT 用 `sigwaitinfo`（同步等信号，无 handler 抢占）而非异步 handler（见 Ch22） |

## 6. 代码示例

```c
#include <stdio.h>
#include <signal.h>
#include <unistd.h>
/* sigaction: 可移植的信号注册（替代 signal） */
static void handler(int sig) {
    /* 异步上下文：只做信号安全操作，写系统调用 */
    const char msg[] = "got signal\n";
    write(STDOUT_FILENO, msg, sizeof(msg) - 1);
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;         /* 自动重启被中断的慢系统调用 */
    sigaction(SIGINT, &sa, NULL);

    for (;;) pause();                 /* 挂起等信号 */
    return 0;
}
```

<details>
<summary>代码自测（Q&A）</summary>

**Q1：信号是同步还是异步的？**
A：**异步**。发送方 `kill` 立即返回，信号由内核「稍后」投递——具体是目标进程下一次从内核态返回用户态时。发送方和目标进程的执行时间线是解耦的（这区别于「同步」的函数调用或 `sigwaitinfo` 这种同步等信号）。

**Q2：`kill` 和 `tgkill` 有什么区别？什么时候必须用 `tgkill`？**
A：`kill` 以「进程（线程组）」为粒度，信号由内核挑一个未屏蔽该信号的线程处理；`tgkill` 以「具体线程（tid）」为粒度，精确投递。多线程程序要通知**特定工作线程**时，`kill` 做不到定向，必须 `tgkill(tgid, tid, sig)`。

**Q3：为什么 SIGKILL 和 SIGSTOP 不能被捕获或阻塞？**
A：这是内核的「保底」设计——必须保证「任何进程都能被无条件杀死/停止」，否则一个故意屏蔽/捕获所有信号的进程会变成无法杀死的僵尸。`sigaction` 对这两个信号注册 handler 会直接返回错误。

**Q4：标准信号「不排队」是什么意思？会造成什么问题？**
A：连发 3 次 SIGINT，进程可能只处理 1 次（内核只记一个 pending 位，不记次数）。所以标准信号**不能用来计数**。要可靠计数用实时信号（`SIGRTMIN`+，排队投递，`sigqueue` 还能携带 `si_value`）或改用 `eventfd`/管道。

**Q5：进程卡在 D 状态时 `kill -9` 为什么无效？**
A：D = `TASK_UNINTERRUPTIBLE`，进程在内核态等 I/O 完成。信号只是置 pending 标志，真正处理要等进程**从内核态返回用户态**。D 状态的进程不返回用户态（一直睡在内核里等 I/O），所以信号永远没机会处理。只有 I/O 完成（或驱动超时）进程醒来，信号才生效。

</details>
