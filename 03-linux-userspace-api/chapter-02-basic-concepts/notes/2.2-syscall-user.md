## 本节讲什么

**系统调用**：用户程序进入内核的 **唯一正规入口**。 例：`open` / `read` / `write` / `mmap` / `fork` 用户程序 → glibc 封装 → CPU 陷入（syscall 等）

---

## 要点

| 空间 | 谁 | 权限 |
|------|-----|------|
| **用户空间 User Space** | 普通应用 | 受限；不能直接碰硬件 |
| **内核空间 Kernel Space** | 内核代码 | 全权 |

**系统调用**：用户程序进入内核的 **唯一正规入口**。  
例：`open` / `read` / `write` / `mmap` / `fork`

```
用户程序 → glibc 封装 → CPU 陷入（syscall 等）
         → 内核态执行服务 → 返回用户态
```

> **面试 / HFT 高频：** 系统调用有 **上下文切换开销**；低延迟路径要 **尽量少 syscall**。

### glibc 角色

| | |
|--|--|
| 作用 | 封装原始 syscall，提供友好接口 |
| 注意 | 有的函数内部会 **多次** syscall；少数纯用户态（不进内核） |

## 与 C 语言学习的关系

本节区分**用户态**和**内核态**——这是 C 程序员从 K&R 跨入系统编程的第一个概念转变。

K&R 教你的 C 程序运行在用户态（受限权限），而 `open`/`read`/`write`/`fork`/`mmap` 这些系统调用是**唯一正规入口**，让用户态程序请求内核干活。C 标准库函数（`fopen`/`printf`）内部也是通过系统调用进入内核的。

关键认知：用户态代码**不能**直接访问硬件、内核内存或其他进程的内存。一切特权操作必须通过系统调用。对照 K&R 第 8 章，那章讲的文件描述符、read/write 就是系统调用的入门实例。

## 常见陷阱

1. **误以为用户态可以直接访问硬件**

```c
/* ❌ 用户态不能直接读写硬件端口或内核内存 */
/* ✅ 必须通过系统调用（open/read/write/ioctl）请求内核代劳 */
/* /dev 设备文件是内核暴露给用户态的接口，不是直接硬件访问 */
```

用户态程序运行在 ring 3（x86）或 EL0（ARM），权限受限。任何硬件操作都要通过系统调用进入内核（ring 0 / EL1）完成。

2. **低估系统调用开销**

```c
/* HFT 热路径：逐字节 read，每次都上下文切换 */
for (int i = 0; i < n; i++)
    read(fd, &buf[i], 1);  /* n 次用户态→内核态切换！ */

/* 优化：批量读 */
read(fd, buf, n);  /* 1 次系统调用 */
```

系统调用涉及模式切换、保存现场、权限校验，开销远贵于普通函数调用（数百 ns 级）。HFT 热路径要尽量少 syscall，或用 `mmap` / 批量 I/O。

3. **混淆 glibc 库函数与系统调用**

```c
/* strcpy / atoi / strlen → 纯用户态，不进内核 */
/* open / read / write  → glibc 薄封装，陷入内核 */
/* fopen / fread        → glibc 多层封装（缓冲 + 调用 open/read） */
```

区分方法：`man 2` = 系统调用，`man 3` = 库函数。有的库函数是薄封装（一次 syscall），有的是纯用户态（不进内核），有的是多层（缓冲 + syscall）。

## 自测题

**题目 1（选择）：** 用户态程序想要读取硬盘上的文件，必须通过什么方式？

A. 直接访问硬盘内存地址
B. 通过系统调用请求内核代劳
C. 通过 C 语言 `fopen` 函数（不涉及内核）
D. 通过 DMA 直接传输

<details>
<summary>参考答案</summary>

B。用户态程序不能直接访问硬件，必须通过系统调用（`open`/`read`）请求内核代劳。C 选项错误：`fopen` 内部也会调用 `open` 系统调用进入内核。

</details>

**题目 2（判断）：** 用户态和内核态运行在同一个地址空间，只是权限不同。

<details>
<summary>参考答案</summary>

正确（Linux 的虚拟内存模型）。用户态和内核态共享同一个虚拟地址空间，但用户态代码只能访问用户空间部分（低地址），内核空间（高地址）受硬件保护。系统调用时不需要切换页表，只是 CPU 特权级变化（ring 3 → ring 0）。

</details>

**题目 3（踩坑）：** 以下代码有什么性能问题？

```c
char buf[4096];
for (int i = 0; i < 4096; i++)
    read(fd, &buf[i], 1);
```

<details>
<summary>参考答案</summary>

每次 `read(fd, &buf[i], 1)` 触发一次系统调用（用户态→内核态上下文切换），4096 次循环 = 4096 次上下文切换，开销巨大。应一次读完：`read(fd, buf, 4096)`，只有 1 次系统调用。系统调用开销远贵于普通函数调用，批量操作是基本优化手段。

</details>

**题目 4（应用）：** 解释为什么 HFT 低延迟系统要尽量减少系统调用，并列出两种替代方案。

<details>
<summary>参考答案</summary>

系统调用需要用户态→内核态切换（保存寄存器、切换栈、权限检查），开销在数百 ns 级别，对 HFT 微秒级延迟敏感的场景影响显著。

替代方案：
1. **`mmap`**：把文件/设备内存映射到用户态地址空间，后续读写不需要 syscall，直接访问内存
2. **批量 I/O**：一次 `read`/`write` 传输大量数据，减少 syscall 次数；或用 `io_uring` 异步批量提交

</details>
