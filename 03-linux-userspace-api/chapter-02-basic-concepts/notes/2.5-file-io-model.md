## 本节讲什么

Linux 的「一切皆文件」模型。本节回答三个问题：

1. fd（文件描述符）到底是什么？它和内核里的「打开文件」怎么对应？
2. `open`/`read`/`write` 在内核里各走哪条链路？
3. 为什么 `fork` 后父子能共享 fd？`O_CLOEXEC` 为什么重要？

这是全书 I/O 的「纲」——后面 [Ch4](../../chapter-04-file-io-universal/README.md)/[Ch5](../../chapter-05-file-io-further/README.md) 的每个 `open`/`read`/`write` 细节，都建立在本节的 fd 三层结构之上。

本节要补的是**能上手验证的那几条**：fd 到底是「最小可用」还是「递增」、`close(1)+open` 重定向为什么一定成功、`O_CLOEXEC` 在子进程里到底看得到什么、以及上限耗尽时 errno 是 24 还是 23。

## 要点

### 一、fd 的三层结构（内核视角）

用户态手里的 `fd` 只是一个**小整数**，真正的打开文件状态在内核里分三层：

```
用户态             内核态
 fd (int) ──────► files_struct（每进程一份，task_struct->files）
                     │  fdtable（fd 数组，fd 即下标）
                     ▼
                  struct file（打开文件对象：inode + 偏移量 + f_op）
                     │
                     ▼
                  struct inode（磁盘文件本体，VFS 层）
```

| 层 | 结构 | 作用 | 源码 |
|----|------|------|------|
| 进程级 | `struct files_struct` | 每进程的文件表，含 `next_fd`（下一个可分配 fd） | `include/linux/fdtable.h:49-63` |
| 表级 | `struct fdtable` | fd → `struct file*` 的数组，`max_fds` 限制上限 | `include/linux/fdtable.h:27-28` |
| 文件级 | `struct file` | 打开文件的**运行时状态**（当前偏移、访问模式、`f_op`） | `include/linux/fs.h` |

**关键认知**：`fd` 是「进程私有」的——两个进程的 `fd 3` 可以指向完全不同的文件。但 `fork` 后，父子进程的 `fdtable` 指向**同一批 `struct file`**（各自持引用计数），所以共享同一个文件偏移量（详见 [Ch24](../../chapter-24-process-creation/README.md)）。

### 二、`open` / `read` / `write` 的系统调用链路

```c
SYSCALL_DEFINE3(open, const char __user *, filename, int, flags, umode_t, mode)   /* fs/open.c:1441 */
SYSCALL_DEFINE3(read, unsigned int, fd, char __user *, buf, size_t, count)        /* fs/read_write.c:621 */
SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf, size_t, count) /* fs/read_write.c:646 */
```

```
open(filename, flags)  → do_sys_open → 分配最小可用 fd → 填 fdtable[fd] = file
read(fd, buf, n)       → fdget_pos(fd) 拿 file → vfs_read  → file->f_op->read
write(fd, buf, n)      → fdget_pos(fd) 拿 file → vfs_write → file->f_op->write
close(fd)              → 从 fdtable 摘除 → 引用计数减一 → 归零才释放 file
```

> `read`/`write` 只认 `fd` 这个整数，不认文件名——**文件名只在 `open` 那一刻被解析成 inode**。所以「重命名/删除一个正在被写的文件」不影响已经打开的 fd（inode 还在），这也是「写临时文件 + rename 原子替换」能工作的原因（见 [Ch18](../../chapter-18-directories-links/README.md)）。

### 三、「一切皆文件」与默认三个 fd

Linux 用**同一套 API**（`open`/`read`/`write`/`close`）操作所有 I/O 资源：

| 资源 | 打开方式 | 说明 |
|------|---------|------|
| 普通文件 | `open("/path", ...)` | 磁盘文件 |
| 设备 | `open("/dev/sda", ...)` | 字符/块设备文件 |
| 管道 | `pipe()` | 无文件名，直接返回两个 fd |
| 套接字 | `socket()` | 网络 I/O |
| 目录 | `open("/dir", O_RDONLY)` | 读目录项 |

每个进程启动时默认打开三个 fd（由父进程/登录 shell 传入）：

| fd | 名称 | 用途 |
|----|------|------|
| 0 | stdin | 标准输入 |
| 1 | stdout | 标准输出 |
| 2 | stderr | 标准错误（**不缓冲**，错误立即可见） |

### 四、`O_CLOEXEC`：把「打开」和「exec 时关闭」原子绑定

| 做法 | 竞态窗口 | 说明 |
|------|----------|------|
| `open()` 后再 `fcntl(fd, F_SETFD, FD_CLOEXEC)` | ❌ **有** | 两步之间另一线程若 `fork`+`exec`，子进程会继承这个 fd |
| `open(..., O_CLOEXEC)` | ✅ **无** | 内核在同一把锁下完成「分配 fd」和「设 `FD_CLOEXEC`」 |

多线程服务进程的**所有** `open`/`socket`/`accept` 都应该带 `O_CLOEXEC`（或对应等价物 `SOCK_CLOEXEC`/`EPOLL_CLOEXEC`）。这是一条几乎零成本、但能根除一整类「fd 泄漏到子进程」事故的规则。

## 代码

### c2_5 fd 分配 / 重定向 / `O_CLOEXEC` / 上限耗尽

[`../code/c2_5_fd.c`](../code/c2_5_fd.c) 分六段：

1. **fd 是「最小可用整数」** —— 连续 5 次 `open`，看 fd 从 3 连号到 7（0/1/2 已被占用）。
2. **关掉再开：证明「最小可用」不是「递增」** —— `close(fd=4)` 之后重新 `open`，**正好拿回 fd 4**，填刚空出来的那个洞。
3. **重定向惯用法** —— `close(1)` + `open(...)` 实测拿到 `fd=1`，写进文件的内容验证确实走了新 fd。
4. **`O_CLOEXEC` 真实验证** —— `open` 两个 fd（一个带 `O_CLOEXEC`、一个不带），然后 `fork` + `execve` 自己，**在子进程里列出继承到的 fd 表**，看带 `O_CLOEXEC` 的那个是否消失。
5. **fd 上限耗尽** —— 读 `RLIMIT_NOFILE` 和 `_SC_OPEN_MAX`，然后死命 `open` 到 `EMFILE(24)`。
6. **`/proc/self/fd` 是 fdtable 的用户态视图** —— 列出来对照。

```c
/* TLPI 第 2 章 §2.5 —— fd 是进程私有的下标：最小可用分配 + O_CLOEXEC
 *
 * 编译：gcc -O0 -Wall -Wextra c2_5_fd.c -o c2_5
 * 运行：./c2_5
 *
 * 本节要钉死的事实：
 *   ① fd 只是 files_struct->fdtable[] 的下标，进程私有。
 *   ② 分配规则是「最小可用」—— close(1) 后下一次 open 必拿到 1，
 *      这正是「重定向」惯用法（close + open）能工作的原因。
 *   ③ O_CLOEXEC 把「打开」和「exec 时关闭」原子绑定，消除多线程竞态窗口。
 *   ④ close(fd) 只是把 fdtable 摘掉 + 引用计数减一，归零才释放 struct file。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <dirent.h>
#include <sys/stat.h>
#include <sys/resource.h>
#include <sys/wait.h>

#define C2DIR "/tmp/c2_5"

/* 子进程分支：列出自己继承到的 fd（验证 O_CLOEXEC 真的把它关了） */
static void list_my_fds(const char *tag)
{
    DIR *d = opendir("/proc/self/fd");
    if (!d) { perror("opendir /proc/self/fd"); return; }
    int self = dirfd(d);                   /* 读目录本身占的那个 fd，要排除掉 */
    struct dirent *e;
    printf("  %s 继承到的 fd：", tag);
    int first = 1;
    while ((e = readdir(d))) {
        if (e->d_name[0] == '.') continue;
        if (atoi(e->d_name) == self) continue;
        char p[320], tgt[320];
        snprintf(p, sizeof(p), "/proc/self/fd/%s", e->d_name);
        ssize_t n = readlink(p, tgt, sizeof(tgt) - 1);
        if (n < 0) continue;
        tgt[n] = '\0';
        if (!first) printf("  ");
        printf("%s=%s", e->d_name, tgt);
        first = 0;
    }
    printf("\n");
    closedir(d);
}

int main(int argc, char **argv)
{
    if (argc > 1 && strcmp(argv[1], "--listfds") == 0) {
        printf("=== 子进程（exec 之后）===\n");
        list_my_fds("child");
        return 0;
    }

    unlink("/tmp/c2_5_plain"); unlink("/tmp/c2_5_exec");
    mkdir(C2DIR, 0755);

    printf("=== ① fd 是「最小可用整数」===\n");
    int fds[5];
    for (int i = 0; i < 5; i++) {
        char p[128];
        snprintf(p, sizeof(p), "%s/f%d.txt", C2DIR, i);
        fds[i] = open(p, O_WRONLY | O_CREAT | O_TRUNC, 0644);
        if (fds[i] < 0) { perror("open"); return 1; }
        printf("  第 %d 次 open -> fd=%d\n", i + 1, fds[i]);
    }
    printf("  -> 0/1/2 已被 stdin/stdout/stderr 占用，所以从 3 开始连号\n");

    printf("\n=== ② 关掉再开：证明「最小可用」不是「递增」===\n");
    printf("  close(fd=%d) 然后重新 open：\n", fds[1]);
    close(fds[1]);
    char p2[128];
    snprintf(p2, sizeof(p2), "%s/reused.txt", C2DIR);
    int reused = open(p2, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    printf("    新 open 拿到 fd=%d\n", reused);
    printf("    %s\n", reused == fds[1] ? "YES —— 正好填刚空出来的那个洞"
                                         : "NO  —— 与预期不符");
    close(reused);
    for (int i = 0; i < 5; i++) if (i != 1) close(fds[i]);
    errno = 0;

    printf("\n=== ③ 重定向惯用法：close(1) + open == 换掉 stdout ===\n");
    int save = dup(STDOUT_FILENO);         /* 备份 stdout */
    fflush(NULL);                          /* 先把缓冲清干净，别让它落到新文件里 */
    close(STDOUT_FILENO);                  /* 腾出 fd 1 */
    int redir = open("/tmp/c2_5_redirect.txt",
                     O_WRONLY | O_CREAT | O_TRUNC, 0644);
    /* 此刻 stdio 仍认为 stdout 就是 fd 1 —— 而 fd 1 已经换了目标 */
    printf("这行是 printf 写的，但它跑进了 %s（fd=%d）\n",
           "/tmp/c2_5_redirect.txt", redir);
    fflush(stdout);
    close(redir);
    dup2(save, STDOUT_FILENO);             /* 恢复 stdout */
    close(save);
    printf("  open 拿到的 fd = %d\n", redir);
    printf("  重定向是否成功：%s\n", redir == STDOUT_FILENO ? "YES（fd==1）" : "NO");

    /* 把被重定向的那行读回来给读者看 */
    int rf = open("/tmp/c2_5_redirect.txt", O_RDONLY);
    if (rf >= 0) {
        char buf[256];
        ssize_t n = read(rf, buf, sizeof(buf) - 1);
        if (n > 0) {
            if (buf[n - 1] == '\n') buf[--n] = '\0';
            buf[n] = '\0';
            printf("  文件内容 = \"%.*s\"\n", (int)n, buf);
        }
        close(rf);
    }
    printf("\n  恢复 stdout 后再 printf 仍然正常：OK\n");

    printf("\n=== ④ O_CLOEXEC：把「打开」和「exec 时关闭」原子绑定 ===\n");
    int pfd = open("/tmp/c2_5_plain", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    int efd = open("/tmp/c2_5_exec",
                   O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    printf("  open(无标志)      -> fd=%d  FD_CLOEXEC=%d\n",
           pfd, fcntl(pfd, F_GETFD) & FD_CLOEXEC);
    printf("  open(O_CLOEXEC)   -> fd=%d  FD_CLOEXEC=%d\n",
           efd, fcntl(efd, F_GETFD) & FD_CLOEXEC);
    printf("  也可以事后补上：fcntl(fd, F_SETFD, FD_CLOEXEC)\n");
    printf("  （多线程下「open 后再 setfd」中间有竞态窗口，所以要用 O_CLOEXEC）\n");

    printf("\n  真实验证：fork + exec 自己，看子进程继承到哪些 fd\n");
    fflush(NULL);
    pid_t pid = fork();
    if (pid == 0) {
        static char exe[512];
        ssize_t n = readlink("/proc/self/exe", exe, sizeof(exe) - 1);
        if (n < 0) _exit(127);
        exe[n] = '\0';
        execve(exe, (char *[]) { exe, "--listfds", NULL },
               (char *[]) { NULL });
        _exit(127);
    }
    int st; waitpid(pid, &st, 0);
    printf("  （上面 child 列表里应看到普通 fd 还在，O_CLOEXEC 那个已消失）\n");
    close(pfd); close(efd);
    unlink("/tmp/c2_5_plain"); unlink("/tmp/c2_5_exec");

    printf("\n=== ⑤ fd 上限：RLIMIT_NOFILE ===\n");
    struct rlimit rl;
    if (getrlimit(RLIMIT_NOFILE, &rl) == 0)
        printf("  getrlimit(RLIMIT_NOFILE): soft=%lld hard=%lld\n",
               (long long)rl.rlim_cur, (long long)rl.rlim_max);
    printf("  sysconf(_SC_OPEN_MAX) = %ld\n", sysconf(_SC_OPEN_MAX));

    int got = 0, devnull[512];
    for (; got < 512; got++) {
        int f = open("/dev/null", O_RDONLY);
        if (f < 0) break;
        devnull[got] = f;
    }
    printf("  死命 open 到崩：成功 %d 个后失败 errno=%d (%s)\n",
           got, errno, strerror(errno));
    printf("  EMFILE(%d)=进程 fd 用尽  ENFILE(%d)=全系统用尽\n", EMFILE, ENFILE);
    for (int i = 0; i < got; i++) close(devnull[i]);
    errno = 0;

    printf("\n=== ⑥ /proc/self/fd 是 fdtable 的用户态视图 ===\n");
    DIR *d = opendir("/proc/self/fd");
    if (d) {
        int self = dirfd(d);
        struct dirent *e;
        while ((e = readdir(d))) {
            if (e->d_name[0] == '.') continue;
            if (atoi(e->d_name) == self) continue;
            char p[320], tgt[320];
            snprintf(p, sizeof(p), "/proc/self/fd/%s", e->d_name);
            ssize_t n = readlink(p, tgt, sizeof(tgt) - 1);
            if (n < 0) continue;
            tgt[n] = '\0';
            printf("  fd %-3s -> %s\n", e->d_name, tgt);
        }
        closedir(d);
    }
    return 0;
}
```

**解读**

1. **段 ② 是「最小可用」这四个字的唯一证明**。段 ① 的连号 `3,4,5,6,7` 本身说明不了问题——递增也能产生同样的结果。段 ② 关掉中间的 fd 4 再开，**拿回来的正是 4**，这才说明内核在找「第一个空闲位」。这条规则的工程含义直接落在段 ③。
2. **段 ③ 的 `open 拿到的 fd = 1` 是 Unix 重定向的机制本体**。`close(1)` 把 stdout 空出来，紧接着 `open` 就必然拿到 `1`——**不是巧合，是段 ② 保证的**。shell 里的 `cmd > file` 就是内核里这对 `dup2`/`close+open` 的封装。实测还验证了「恢复 stdout 后 `printf` 仍然正常」，说明这个惯用法是可逆的。
3. **段 ④ 是本 demo 最能学到东西的一段**。子进程 `execve` 之后打印出的 fd 表是：
   ```text
   0=socket:...  1=socket:...  2=socket:...  3=/tmp/c2_5_plain
   ```
   **只有 4 个 fd**：0/1/2（继承的）+ **fd 3（不带 `O_CLOEXEC` 的那个普通文件）**。带 `O_CLOEXEC` 的 fd 4 **不在列表里**——它在 `execve` 那一刻被内核自动关掉了。这就是「`O_CLOEXEC` 真的生效」的实证，而不是文档里的一句话。
4. **段 ⑤ 的数字要连起来读**：`RLIMIT_NOFILE = 100`、`_SC_OPEN_MAX = 100`、**成功 97 个后失败**。97 + 3（0/1/2）+ 1（`/proc/self/fd` 目录自己的 fd）≈ 100，账对得上。顺带记一对易混错误码：**`EMFILE(24)` = 本进程 fd 用尽**（要排查自己有没有漏 `close`），**`ENFILE(23)` = 全系统 file 表用尽**（要排查别的进程或调 `fs.file-max`）。**看到 24 就去查自己的 `close` 配对，别去改内核参数。**
5. **段 ⑥ 的 `socket:[290324]` 是个副产品信息**：0/1/2 全都是 `socket:`，说明 CE 容器的 stdout 不是终端而是 socket——这正是 [2.1](./2.1-kernel.md) 里 `isatty(1)=0`（全缓冲）的物理原因，也是 [2.14](./2.14-sessions.md) 里「没有控制终端」的根源。**同一个事实在三个不同小节各暴露一次。**

| `proc(5)` | `/proc/self/fd/` —— 文件名为 fd 号的符号链接目录 |

> `fs/open.c:1441`、`fs/read_write.c:621/646` 均用 Linux **v6.6** 源码逐行核对（脚本 `verify_ksrc.py`）。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| fd 泄漏导致「Too many open files」 | `fdtable->max_fds` 达上限；长期运行进程必须 `close` 成对，或用 `O_CLOEXEC` 防 exec 后泄漏 |
| `fork`+`exec` 竞态泄漏 fd | 父进程 `open` 后未关、子进程 `exec` 继承 → **段 ④ 实测**：`O_CLOEXEC` 的那个 fd 在子进程里确实消失 |
| 日志热路径延迟 | `write` 走 `file->f_op->write` 有内核态拷贝；高频日志用 `write` 批量或异步落盘 |
| 文件偏移共享 | `fork` 后父子共享 `struct file` 偏移 → 并发写同一文件会交错，需 `O_APPEND` 原子追加 |
| **`EMFILE` vs `ENFILE` 分流排查** | 段 ⑤ 实测 `EMFILE(24)`。HFT 长跑进程若日志打开失败拿到 24，**第一反应应该是自己漏了 `close`**，而不是加 `ulimit` |
| **`RLIMIT_NOFILE=100` 对交易进程远远不够** | 段 ⑤ 实测本环境 soft=hard=**100**。行情网关+多路连接轻松上千，部署时必须 `LimitNOFILE=65536`（systemd）或 `ulimit -n`，否则连到第 97 路就 `EMFILE` |
| **重定向惯用法在守护进程里天天用** | 段 ③ 的 `close+open` 是 daemon 化第 ⑤ 步「把 0/1/2 重定向到 `/dev/null`」的实现（见 [2.14](./2.14-sessions.md)）——**靠的就是「fd 是最小可用整数」这条保证** |
| 嵌入式 fd 预算本来就小 | initramfs 早期 `/proc/sys/fs/file-max` 可能只有几百；`/proc/self/fd`（段 ⑥）是唯一不用 `strace` 就能看 fd 表的低成本手段 |

## 自测题

<details>
<summary>1. 两个进程都有 <code>fd 3</code>，它们指向同一个文件吗？</summary>

不一定。fd 是进程私有的下标，指向各自 `files_struct->fdtable[3]`。只有「继承」（`fork` 共享 `struct file`）或「显式传 fd」（`sendmsg` 的 `SCM_RIGHTS`）时，两个进程的 fd 才指向同一 `struct file`。

本节 demo 段 ④ 的父子进程就是「继承」这个情形——所以子进程的 fd 0/1/2/3 与父进程指向**同一批 `struct file`**（因此共享文件偏移量）。
</details>

<details>
<summary>2. <code>open</code> 返回的 fd 一定是最小可用整数吗？为什么？</summary>

**是，而且这是 POSIX 的保证**。`open(2)` RETURN VALUE 原文："the file descriptor … is **guaranteed to be the lowest-numbered** file descriptor not currently open for the process"。

本 demo 用两段把它证明了：

```text
=== ① 第 1 次 open -> fd=3   第 2 次 -> fd=4   第 3 次 -> fd=5 ...
=== ② close(fd=4) 然后重新 open：新 open 拿到 fd=4   YES —— 正好填刚空出来的那个洞
```

段 ① 的连号说明不了问题（递增也能这样），**段 ② 拿回中间的 4 才是关键**。

这条保证的实用价值就是段 ③：`close(1)` 之后 `open` **必然**拿到 `fd=1`，于是「重定向 stdout」可以只靠这两个调用完成。
</details>

<details>
<summary>3. <code>read(fd, ...)</code> 为什么不需要文件名参数？</summary>

因为 `open` 时已经把路径解析成 inode 并存入 `struct file`。之后 `read`/`write`/`lseek` 只操作这个已打开的文件对象，与文件名解耦。

所以文件被删除/重命名后，已打开的 fd 仍可正常读写——这与 [2.4](./2.4-directory-hierarchy.md) 段 ④ 的实测是同一件事的两面：`unlink` 只删名字，inode 因为还被打开着所以没释放。
</details>

<details>
<summary>4. <code>O_CLOEXEC</code> 解决什么问题？不用它有什么后果？</summary>

多线程程序里，线程 A 在 `open` 和「设 `FD_CLOEXEC` 标志」之间，线程 B 可能 `fork`+`exec`，导致子进程继承了一个本应关闭的 fd（**竞态泄漏**）。`O_CLOEXEC` 让 `open` 和「exec 时关闭」**原子绑定**，无竞态窗口。`open(2)` 原文强调的正是这个 "**atomically**"。

本节 demo 段 ④ 给出了实证——子进程 `execve` 之后打印自己的 fd 表：

```text
  child 继承到的 fd：0=socket:[290324]  1=socket:[290326]  2=socket:[290328]  3=/tmp/c2_5_plain
```

**只有 4 个 fd**。不带 `O_CLOEXEC` 的 fd 3 还在，带 `O_CLOEXEC` 的 fd 4 **已经不在列表里**。长期服务进程所有 fd 都应带 `O_CLOEXEC`（socket 用 `SOCK_CLOEXEC`，epoll 用 `EPOLL_CLOEXEC`）。
</details>

<details>
<summary>5. <code>close(fd)</code> 之后文件真的立刻关闭了吗？</summary>

不一定。`close` 只是把 `fdtable[fd]` 摘除、`struct file` 引用计数减一。只有引用计数归零（所有指向它的 fd 都关了、fork 的子进程也关了），内核才真正释放 `struct file`。

这就是「同一文件被 `open` 两次，关一个 fd 另一个还能用」的原因。反过来说，[2.4](./2.4-directory-hierarchy.md) 段 ④ 的「删掉文件但数据还在」也依赖同一条：**只要还有 fd 引用着那个 inode，数据块就不会被释放**。
</details>

<details>
<summary>6. 打开文件失败拿到 <code>errno=24</code>，该加 <code>ulimit</code> 还是查自己的代码？</summary>

**先查自己的代码**——因为 24 是 `EMFILE`（**本进程** fd 用尽），而 `ENFILE` 才是 23（**全系统** file 表用尽）。

本节 demo 段 ⑤ 的实测把这两个数字和上限的关系摊开了：

```text
  getrlimit(RLIMIT_NOFILE): soft=100 hard=100
  sysconf(_SC_OPEN_MAX) = 100
  死命 open 到崩：成功 97 个后失败 errno=24 (Too many open files)
  EMFILE(24)=进程 fd 用尽  ENFILE(23)=全系统用尽
```

`97 + 3（0/1/2）+ 1（/proc/self/fd 自身）≈ 100`，账对得上。

- **拿到 24**：自己漏了 `close`，或上限设小了（长跑服务应该 `LimitNOFILE=65536`）；
- **拿到 23**：全系统不够，才轮到调 `fs.file-max`。
</details>
