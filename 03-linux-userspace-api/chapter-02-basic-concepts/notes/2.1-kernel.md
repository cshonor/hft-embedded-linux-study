## 本节讲什么

内核是操作系统中**始终驻留内存、掌握全部硬件**的核心部分。本节回答三个问题：

1. 内核是什么？宏内核和微内核差在哪，Linux 为什么选宏内核？
2. 「用户态 / 内核态」到底是什么？程序凭什么只能通过**系统调用**进入内核？
3. `man 2` 和 `man 3` 各是什么？系统调用和 glibc 是不是「两个独立的库」？

原书把「内核」和「用户态/内核态/系统调用」连在一起讲，本节合并为一篇，把「内核边界」这个抽象落到 `sys_call_table` 上，为后面所有系统调用学习打底。

## 要点

### 一、内核是什么

| 职责 | 说明 | HFT/嵌入式视角 |
|------|------|----------------|
| **CPU 调度** | 决定哪个任务占用 CPU、上下文切换 | 实时调度策略 `SCHED_FIFO`（见 [2.18](./2.18-realtime.md)） |
| **内存管理** | 虚拟地址空间、页表、换页、mmap | `mlockall` 防换页毛刺（见 [2.18](./2.18-realtime.md)） |
| **文件系统** | VFS 抽象层，对接 ext4/proc 等 | `/proc` 虚拟文件系统（见 [2.19](./2.19-proc-filesystem.md)） |
| **设备驱动** | 磁盘、网卡、串口…… | 网卡驱动零拷贝是延迟关键 |
| **网络协议栈** | TCP/IP、socket 层 | 行情/下单的网络通路 |
| **安全** | 权限检查、capabilities、namespace | 最小权限部署 |

内核代码编译成 `vmlinux`（可启动镜像），驱动可以**编进内核**，也可以动态加载为 `.ko` 模块（`insmod`/`modprobe`）。

### 二、宏内核 vs 微内核

| 架构 | 内核态放什么 | 特点 | 代表 |
|------|-------------|------|------|
| **宏内核（monolithic）** | 调度、驱动、FS、网络全在内核态 | 性能高，但一处崩溃拖垮全系统 | **Linux**、Unix |
| **微内核（microkernel）** | 只留 IPC + 调度，驱动跑用户态 | 更安全/隔离好，但 IPC 开销大、慢 | QNX、MINIX |
| **混合内核** | 折中 | 兼顾 | Windows NT、macOS XNU |

Linux 选宏内核是为**性能**：系统调用直接陷入内核处理，没有微内核那种「用户态服务进程 ↔ 内核」的额外 IPC 消息往返。代价是内核态代码量大、驱动 bug 可能 panic 整个系统——所以嵌入式才需要「内核裁剪」（`make menuconfig` 只保留用得到的子系统）。

### 三、用户态 vs 内核态

```
┌──────────────────────────────────────────────────┐
│ 用户态 (User Space)    ring 3 (x86) / EL0 (ARM)   │
│  应用程序 + glibc，权限受限，不能直接碰硬件        │
│        │  syscall 指令（主动陷入）                │
│        ▼  （硬件中断 / 缺页异常也会强制切换）      │
│ 内核态 (Kernel Space)  ring 0 (x86) / EL1 (ARM)   │
│  内核代码 + 驱动，特权模式，可访问任何内存         │
└──────────────────────────────────────────────────┘
```

- **用户态**：CPU 处于低特权级（ring 3 / EL0），不能执行特权指令、不能直接访问硬件端口、不能读写内核内存。
- **内核态**：CPU 处于最高特权级（ring 0 / EL1），任何指令、任何内存都可访问。
- **切换**：用户程序通过 `syscall`（x86-64）或 `svc`（AArch64）指令主动陷入内核；硬件中断、缺页异常也会强制切换。

> 关键认知：用户态和内核态**共享同一个虚拟地址空间**（Linux 设计），内核占据高地址段（`0xffff...`），用户态占据低地址段，两者被页表权限隔离。所以系统调用**不需要切换页表**（省了 TLB 刷新），只是 CPU 特权级变化——这也是 Linux 系统调用快的原因之一。

### 四、系统调用：进入内核的「唯一正规入口」

```
C 代码 write(1, "hi", 2)
      │  glibc 封装：把参数塞寄存器，rax = syscall 号
      ▼
syscall 指令（用户态 → 内核态，CPU 特权级切换）
      │  内核入口读 rax 得到系统调用号（如 write=1）
      ▼
sys_call_table[nr] 查表分发        arch/x86/entry/syscall_64.c:16
      ▼
__x64_sys_write(...)              内核态真正干活
      ▼
返回用户态，继续执行
```

系统调用号是**固定的 ABI**，写死在 `arch/x86/entry/syscalls/syscall_64.tbl`：

| 系统调用号 | 名字 | 内核实现 |
|-----------|------|----------|
| 0 | `read` | `sys_read` |
| 1 | `write` | `sys_write` |
| 2 | `open` | `sys_open` |
| 3 | `close` | `sys_close` |
| 9 | `mmap` | `sys_mmap` |
| 39 | `getpid` | `sys_getpid` |
| 57 | `fork` | `sys_fork` |
| 59 | `execve` | `sys_execve` |
| 228 | `clock_gettime` | `sys_clock_gettime` |
| 257 | `openat` | `sys_openat` |

内核用这张表把「用户态传来的号码」映射到「内核函数」：

```c
/* arch/x86/entry/syscall_64.c:16 —— 系统调用分发表 */
asmlinkage const sys_call_ptr_t sys_call_table[] = {
#include <asm/syscalls_64.h>   /* 展开成 [0]=__x64_sys_read, [1]=__x64_sys_write, ... */
};
```

### 五、man 2 和 man 3 到底是什么

`man` 手册按「类别」分节（section），同一个名字可能同时出现在好几节。最常见的几节：

| 节号 | 内容 | 例子 |
|------|------|------|
| 1 | 用户命令（shell 里直接跑的程序） | `man 1 ls`、`man 1 mkdir` |
| **2** | **系统调用**（内核提供的接口） | `man 2 open`、`man 2 fork` |
| **3** | **库函数**（glibc 等用户态库提供的接口） | `man 3 printf`、`man 3 strlen` |
| 4 | 设备文件（/dev 下的特殊文件） | `man 4 null` |
| 5 | 文件格式与约定 | `man 5 passwd`、`man 5 proc` |
| 7 | 杂项/概览性文档 | `man 7 signal`、`man 7 epoll` |
| 8 | 系统管理命令（多半要 root） | `man 8 mount` |

- **`man 2`**：查的是**系统调用**。手册页里的函数原型（如 `ssize_t write(int fd, const void *buf, size_t count);`）描述的是**内核对外承诺的能力**——你调它，CPU 就会陷入内核执行。
- **`man 3`**：查的是**库函数**。原型（如 `int printf(const char *format, ...);`）描述的是 **glibc 在用户态实现的函数**——它可能内部再调系统调用，也可能根本不进内核。
- 同名冲突时必须**带节号**：`mkdir` 既是 shell 命令（man 1）又是系统调用（man 2）；`printf` 既是命令（man 1）又是库函数（man 3）。`man 1 mkdir` 和 `man 2 mkdir` 是两页完全不同的东西；不带节号时 man 按节号顺序给第一个命中（通常是 man 1）。
- 想列出一个名字出现在哪些节：`man -k write`（等价 `apropos write`），或 `whatis write`。

一句话记住：**man 2 = 内核的菜单，man 3 = glibc 的菜单**。

### 六、系统调用和 glibc 是「两个独立的库」吗？

**不是。这俩根本不在同一层，也不存在「两个库」的关系。**

- **系统调用不是库，也不是用户态函数**。它是**内核（vmlinux）里的函数集合**，跑在特权态（ring 0 / EL1）。磁盘上不存在一个 `libsyscall.so` 供你链接——想用它的唯一正规入口是执行 `syscall`（x86-64）/ `svc`（ARM64）指令陷入内核，把「系统调用号 + 参数」交进去查 `sys_call_table`（见上节）。
- **glibc（GNU C Library）才是库**：一个用户态共享库 `/lib/x86_64-linux-gnu/libc.so.6`，提供两类东西——①对系统调用的**封装函数**（`open`/`read`/`write`/`fork`……）；②**纯用户态函数**（`strcpy`/`strlen`/`memcpy`……）。
- 两者是**上下层依赖**，不是并列：glibc 的 I/O 类函数**内部**靠系统调用落地；而内核实现系统调用时**完全不依赖** glibc——内核甚至不知道 glibc 的存在。

```
你的代码 ──→ glibc 库函数（man 3：printf/fopen/strlen）──→ 纯用户态的到此为止
   │                                                              │（如 printf 凑满缓冲）
   │                                                              ▼
   ├────→ glibc 薄封装（man 2：write/open/fork）──→ syscall 指令 ──→ 内核 sys_write ...
   ├────→ glibc 的 syscall(SYS_write, ...) ──────→ syscall 指令 ──→ 内核（绕开逐个封装，
   │                                                                但本体仍是 glibc 函数）
   └────→ 手写汇编直接发 syscall 指令 ─────────────────────────────→ 内核（连 glibc 都没有）
```

**「绕开」要拆成两层，别混**：

| 写法 | 函数本体在哪 | 依赖 glibc？ | 说明 |
|------|-------------|-------------|------|
| `write(1, buf, len)` | glibc 薄封装 | ✅ | 封装里可能带取消点等额外逻辑 |
| `syscall(SYS_write, 1, ...)` | **glibc 的通用小封装**（注意：它自己也是 glibc 函数） | ✅（但绕开了 `write()` 这个**逐个**封装） | 只做「号码 + 参数 → 寄存器」的整理，几乎零业务逻辑 |
| 手写汇编 `syscall`/`svc` 指令 | **没有函数**——`_start` 里直接摆寄存器发指令 | ❌ 零 glibc | `gcc -nostdlib -static`，`ldd` 显示 *not a dynamic executable*；见下面代码 `c2_1_nolibc` |

所以准确的说法是：`syscall(SYS_write, ...)` 绕开的是 **glibc 对各个系统调用的单独包装**（`write()`/`open()` 那些），**并没有绕开 glibc 本身**——链接时照样要 `libc.so.6`。想**完全脱离 glibc**，连 `syscall()` 都不能用，只能手写汇编直接发陷入指令（下面 `c2_1_nolibc` 就是实证：strace 全程只有 `write` + `exit` 两次系统调用，二进制 1296 字节，是 glibc 版的 1/54）。

再按「调一次函数，进不进内核」分三档——这是排查「热路径为什么有这么多 syscall」的基本功：

| 类型 | 例子 | 手册节 | 是否进内核 |
|------|------|--------|-----------|
| **薄封装**（一次 syscall） | `open`/`read`/`write`/`fork` | man 2 | ✅ 直接陷入 |
| **多层封装**（缓冲 + syscall） | `fopen`/`fread`/`printf` | man 3 | ✅ 内部调 open/read/write |
| **纯用户态**（零 syscall） | `strcpy`/`atoi`/`strlen`/`memcpy` | man 3 | ❌ 不进内核 |

> 易混点：`write` 的手册在 **man 2**，但你实际调到的 `write()` 函数体却在 **glibc** 里——man 2 描述的是它「直通内核」这层语义。所以「man 2 还是 man 3」判的是**这个接口的本体在哪**（内核 or 用户态库），不是「函数体编译在哪个 .so」。

## 代码

### c2_1 三条写路径 + 缓冲时机

[`../code/c2_1_syscall.c`](../code/c2_1_syscall.c) 做四件事：

1. **三条路径写同一句话** —— `write()`（glibc 薄封装）、`syscall(SYS_write, ...)`（绕开 `write()` 这层逐个封装，直接按号发；`syscall()` 本体仍是 glibc 函数）、`printf()`（进 stdio 缓冲）。三条最终都落在同一个 `fd 1`，但时机不同。
2. **证明 `strlen`/`sizeof` 是纯用户态** —— 顺便对比「运行期循环数到 `\0`」和「编译期常量」。
3. **打印 8 个系统调用号** —— 直接引用 `<sys/syscall.h>` 里的 `SYS_*` 宏，看它们和 `syscall_64.tbl` 是否对得上。
4. **缓冲时机实验（本节关键）** —— 先打一行 `printf("[A]...")`，**不 flush**，紧接着 `write("[B]...")`，再补齐 `[C]`/`[D]`，最后统一 `fflush`。实测顺序会是 **B 跑到 A/C/D 前面**。

```c
/* TLPI 第 2 章 §2.1 —— 库函数 vs 系统调用：三条写路径 + 缓冲时机
 *
 * 编译：gcc -O0 -Wall -Wextra c2_1_syscall.c -o c2_1
 * 运行：./c2_1
 *
 * 本节要钉死的事实：
 *   ① write() 是 glibc 对 sys_write 的薄封装，printf() 是「缓冲 + 多次 syscall」。
 *   ② strlen()/sizeof 是纯用户态，一次系统调用都不发。
 *   ③ 系统调用号是固定 ABI，写死在 arch/x86/entry/syscalls/syscall_64.tbl。
 *   ④ stdio 默认全缓冲（stdout 接管道/文件时），printf 的输出会「迟到」——
 *      与 write 混用时顺序会颠倒，这是真实可复现的现象。
 *
 * ⚠️ 注意 write() 的第三个参数是**字节数**，不是字符数。
 *    下面一律用 strlen() 算，硬编码长度会在多字节字符（中文）上截断成乱码。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/syscall.h>

int main(void)
{
    /* ---------- ① 三条路径写同一句话 ---------- */
    printf("=== ① 三条路径写同一句话 ===\n");
    fflush(stdout);                     /* 先清干净，下面好观察顺序 */

    const char *m1 = "[write]    hello from write()\n";
    write(STDOUT_FILENO, m1, strlen(m1));          /* glibc 薄封装 → sys_write */

    const char *m2 = "[syscall]  hello from syscall(SYS_write)\n";
    syscall(SYS_write, STDOUT_FILENO, m2, strlen(m2));   /* 绕开 write() 这层封装；syscall() 本体仍是 glibc 函数 */

    printf("[printf]   hello from printf()\n");
    printf("  三条都落在同一个 fd 1；前两条立即进内核，第三条先入用户态缓冲。\n");
    fflush(stdout);

    /* ---------- ② 纯用户态函数：一次 syscall 都不发 ---------- */
    printf("\n=== ② 纯用户态函数（不进内核）===\n");
    printf("  strlen(\"hello\")  = %zu   <- 运行期循环数到 '\\0'\n", strlen("hello"));
    printf("  sizeof(\"hello\")  = %zu   <- 编译期常量，连循环都不用\n", sizeof("hello"));
    printf("  strlen 和 sizeof 都可能有 0 次系统调用。\n");
    printf("  区分方法：man 2 = 系统调用，man 3 = 库函数\n");

    /* ---------- ③ 系统调用号是固定 ABI ---------- */
    printf("\n=== ③ 系统调用号（x86-64，固定 ABI）===\n");
    printf("  SYS_read     = %d\n", SYS_read);
    printf("  SYS_write    = %d\n", SYS_write);
    printf("  SYS_open     = %d\n", SYS_open);
    printf("  SYS_close    = %d\n", SYS_close);
    printf("  SYS_mmap     = %d\n", SYS_mmap);
    printf("  SYS_fork     = %d\n", SYS_fork);
    printf("  SYS_execve   = %d\n", SYS_execve);
    printf("  SYS_getpid   = %d\n", SYS_getpid);
    printf("  <- 号码写死在 arch/x86/entry/syscalls/syscall_64.tbl，\n");
    printf("     内核用 sys_call_table[nr] 查表分发（见本节正文）\n");

    /* ---------- ④ 缓冲时机：printf 会「迟到」 ---------- */
    printf("\n=== ④ 缓冲时机实验（本节关键）===\n");
    printf("  isatty(STDOUT_FILENO) = %d  (0 = stdout 接的是管道/文件 → 全缓冲)\n",
           isatty(STDOUT_FILENO));
    fflush(stdout);

    printf("  [A] 这行由 printf 写入 stdio 缓冲，此刻还没进内核\n");
    const char *mb = "  [B] 这行由 write 直接落到 fd 1\n";
    write(STDOUT_FILENO, mb, strlen(mb));
    printf("  [C] 又一行 printf\n");
    printf("  [D] 还是 printf\n");
    fflush(stdout);                     /* 手动把缓冲推下去 */

    printf("  -> 实际顺序是 B 跑到 A/C/D 前面：stdio 这一层缓冲在「骗」你。\n");
    printf("     排查别人的输出顺序怪事时，先看 isatty() 和 fflush()。\n");
    printf("  -> 反过来，printf 的缓冲也是性能手段：凑满一块再发一次 syscall。\n");

    printf("\n=== ⑤ 一个可以直接量出来的数字 ===\n");
    printf("  BUFSIZ            = %d  (stdio 默认缓冲大小)\n", BUFSIZ);
    printf("  一次 1000 字节的 printf 只发 1 次 write；\n");
    printf("  1000 次 1 字节的 write 要发 1000 次 syscall。\n");
    printf("  差别 = 999 次「用户态↔内核态」模式切换。\n");
    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c2_1_syscall c2_1_syscall.c && ./c2_1_syscall
```


**解读**

1. **段 ③ 是「号码是 ABI」的硬证据**：`SYS_read=0`/`SYS_write=1`/`SYS_open=2`/`SYS_close=3`/`SYS_mmap=9`/`SYS_getpid=39`/`SYS_fork=57`/`SYS_execve=59`——这八个数字**就是** `syscall_64.tbl` 里的前几行（`open` 在表里是 2，`openat` 才是 257，别混）。它们**不能改**，改一个就破坏所有已编译程序的用户态兼容。
2. **段 ④ 是本节的硬证据**：源码里的书写顺序是 A → B → C → D，但实测输出是 **B → A → C → D**。原因写在打印里：`isatty(STDOUT_FILENO) = 0`，说明 stdout 不是终端（CE 容器里它是 socket），于是 stdio 采用**全缓冲**——`printf` 的字先躺在用户态 8KB 缓冲里，而 `write()` 是系统调用、立刻落到 `fd 1`。所以**「printf 和 write 混用时顺序颠倒」不是玄学，是缓冲策略的必然**。
3. **段 ⑤ 的 `BUFSIZ = 8192`** 把「缓冲省的是什么」量化了：一次 1000 字节的 `printf` 只发 1 次 `write`；1000 次 1 字节的 `write` 要发 1000 次 syscall。**差值 999 次「用户态↔内核态」往返**——这正是 [2.5](./2.5-file-io-model.md) 里 fd 三层结构存在的意义，也是 HFT 里「批量 I/O」的物理依据。
4. **段 ② 对照了「编译期」和「运行期」**：`sizeof("hello") = 6`（含结尾 `\0`）是编译期算出来的**常量**，运行期一个指令都不用；`strlen("hello") = 5` 需要在运行期循环到 `\0`。两者**都不发系统调用**，所以「库函数 vs 系统调用」的分界线不在「是不是函数」，而在**有没有越过特权级边界**。
5. **自己动手时的一个坑**（本 demo 已避开）：`write()` 的第三个参数是**字节数**，不是字符数。硬编码长度遇到中文（UTF-8 多字节）就会把字符截断成乱码。本 demo 一律用 `strlen(msg)` 算——这条在嵌入式日志输出里也是高频事故。

### c2_1_nolibc 纯汇编裸调 syscall：连 glibc 都没有

[`../code/c2_1_nolibc_arm64.S`](../code/c2_1_nolibc_arm64.S)（AArch64，Pi 5 实测）与 [`../code/c2_1_nolibc_x64.S`](../code/c2_1_nolibc_x64.S)（x86-64，Compiler Explorer 复核）是同一件事的两个 ISA 版本：**不用 C、不用任何库**，`_start` 里手工把「系统调用号 + 参数」摆进寄存器，直接执行陷入指令。`write()` 和 `syscall()` 这两个 glibc 函数一个都不用——因为它们本身也是 glibc 的代码，要证明「零 glibc」就必须连它们一起扔掉。

```asm
/* TLPI 第 2 章 §2.1 —— 完全不依赖 glibc：手写 svc 指令裸调 write/exit（AArch64）
 *
 * 编译运行（Linux arm64，如 Raspberry Pi 5）：
 *   gcc -nostdlib -static c2_1_nolibc_arm64.S -o c2_1_nolibc_arm64
 *   ./c2_1_nolibc_arm64
 *   ldd ./c2_1_nolibc_arm64      # 期望：not a dynamic executable
 *   strace ./c2_1_nolibc_arm64   # 期望：整个进程只有 write + exit 两次系统调用
 *
 * 与 x86-64 版的三点差异（ABI 不同，语义相同）：
 *   ① 陷入指令：x86-64 用 syscall，AArch64 用 svc #0
 *   ② 号码寄存器：x86-64 用 rax，AArch64 用 x8
 *   ③ 系统调用号不同：AArch64 没有 write=1，而是 write=64 / exit=93
 *     （arch/arm64 走 asm-generic 表：include/uapi/asm-generic/unistd.h）
 *
 * 已实测：Raspberry Pi 5（Debian 13，kernel 6.18，gcc 14.2）——见笔记正文输出。
 */
    .section .rodata
msg:
    .ascii "[nolibc-arm64] hello from raw svc instruction, zero glibc\n"
    .set msg_len, . - msg

    .text
    .globl _start
_start:
    /* write(1, msg, msg_len) */
    mov     x8, 64              /* __NR_write = 64（asm-generic/unistd.h） */
    mov     x0, 1               /* fd = STDOUT_FILENO */
    adrp    x1, msg
    add     x1, x1, :lo12:msg   /* buf */
    mov     x2, msg_len         /* count */
    svc     #0                  /* EL0 → EL1 陷入内核 */

    /* exit(0) */
    mov     x8, 93              /* __NR_exit = 93 */
    mov     x0, 0
    svc     #0
```

**Pi 5 实测**（Debian 13，kernel 6.18.34+rpt-rpi-2712，gcc 14.2）——三个数字把「零 glibc」钉死：

```text
$ gcc -nostdlib -static c2_1_nolibc_arm64.S -o c2_1_nolibc_arm64 && ./c2_1_nolibc_arm64
[nolibc-arm64] hello from raw svc instruction, zero glibc

$ ldd ./c2_1_nolibc_arm64
        not a dynamic executable          <- 连 libc.so.6 都没链接，进程里压根没有 glibc

$ strace ./c2_1_nolibc_arm64
execve("./c2_1_nolibc_arm64", ...) = 0
write(1, "[nolibc-arm64] hello from raw sv"..., 58) = 58
exit(0)                                  = ?
+++ exited with 0 +++                    <- 全程只有 write + exit，再无其他

$ ls -l c2_1_nolibc_arm64 three_ways     <- 对比：同输出的 glibc 版（write()+syscall()）
1296   c2_1_nolibc_arm64                 <- 1.3 KB
70496  three_ways                        <- 69 KB（动态链接 glibc），体积 54 倍
```

同一个「往 stdout 写一句话」的需求，**glibc 版 strace 计数 29 次系统调用**（ld.so 映射 libc、`mprotect`/`brk`/`set_tid_address`/`rseq` 等启动开销），**裸汇编版只有 2 次**（`write` + `exit`）——那 27 次之差，就是「glibc 这层库」的具象化成本。

x86-64 版在 Compiler Explorer 复核通过（gcc 14.2 / x86-64，`-x assembler -nostdlib -static`，实际执行）：输出 `[nolibc-x64] hello from raw syscall instruction, zero glibc`，退出码 0。两版语义完全一致，只有 ISA 三处差异：陷入指令（`syscall` vs `svc #0`）、号码寄存器（`rax` vs `x8`）、调用号（x86-64 `write=1/exit=60` 查 `syscall_64.tbl`；arm64 `write=64/exit=93` 查 `asm-generic/unistd.h`——arm64 **没有** `open` 只有 `openat`，这也是为什么 `c2_1_syscall.c` 里的 `SYS_open` 在 arm64 上编译不过）。

> 嵌入式视角：这就是裸机/bootloader 的思维——没有 CRT、入口是 `_start` 不是 `main`、退出必须发 `SYS_exit` 而不能 `return`。`-nostdlib` 下的每一个字节都得自己负责，和 STM32 裸机写启动代码是同一套心智。

## 源码坐标

| 位置 | 内容 |
|------|------|
| Linux `arch/x86/entry/syscall_64.c:16` | `asmlinkage const sys_call_ptr_t sys_call_table[] = {` —— 分发数组本体 |
| Linux `arch/x86/entry/syscalls/syscall_64.tbl` | x86-64 系统调用号 → 名字 → 实现入口的**唯一权威表**（`0 common read` / `1 common write` / `2 common open` …） |
| Linux `include/uapi/asm-generic/unistd.h` | arm64/riscv 等新架构的通用系统调用号表：`__NR_write 64`、`__NR_exit 93`、`__NR_openat 56`——**没有 `__NR_open`**（arm64 只有 `openat`，故 `SYS_open` 在 arm64 编译不过） |
| Linux `include/linux/syscalls.h` | `SYSCALL_DEFINE0..6` 宏，把 `sys_write` 生成为 `__x64_sys_write`（加 `asmlinkage` 与 ptrace 包装） |
| glibc `<sys/syscall.h>` | `SYS_write` 等宏，由内核的 `syscall_64.tbl` 生成（`make headers_install`） |
| glibc `<bits/stdio.h>` / `stdio.h` | `BUFSIZ=8192`、`isatty`、`fflush` 的声明；缓冲策略由 `_IO_file_doallocate` 决定 |

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 每次系统调用都有陷入开销 | 模式切换 + 保存现场 + 权限校验，约数百 ns；热路径要**少 syscall** |
| 逐字节 `read` 是灾难 | n 字节 = n 次上下文切换；批量 `read(fd, buf, n)` 只 1 次 |
| `mmap` 免系统调用 | 把文件/设备映射进用户态地址空间，后续读写直接访存（见 [2.8](./2.8-memory-mappings.md)） |
| `io_uring` 异步批量提交 | 减少 syscall 往返，高性能 I/O 首选 |
| 嵌入式内核裁剪 | `make menuconfig` 只留必要驱动/子系统，减小内核体积与攻击面 |
| 裸二进制 = 裸机思维 | `c2_1_nolibc`：`-nostdlib -static` 出 1296 字节可执行文件，`_start` 自摆寄存器、退出靠 `SYS_exit`——与 STM32 裸机启动代码同一套心智 |
| vDSO 免陷入 | `clock_gettime`/`gettimeofday` 走 vDSO，用户态直接读内核映射的只读数据，不切换特权级（见 [2.16](./2.16-date-time.md)） |
| **stdio 缓冲「骗」你** | 段 ④ 的 B→A→C→D：延迟敏感路径上**别用 stdio**，要 write 就 `write()`，要顺序确定就 `fflush()` |
| **printf 在信号处理器里不安全** | 它是「多层封装 + 共享缓冲」，不可重入；handler 里只能用 `write()`（见 [2.11](./2.11-signals.md)） |

## 自测题

<details>
<summary>1. 宏内核和微内核的本质区别是什么？Linux 为什么选宏内核？</summary>

区别在「驱动/文件系统/网络跑在哪」：宏内核全部塞进内核态，微内核只留 IPC+调度、其余跑用户态。Linux 选宏内核是为**性能**——系统调用直接陷入内核处理，没有微内核「用户态服务进程↔内核」的额外 IPC 往返。代价是内核代码量大、驱动 bug 可能 panic 全系统，所以嵌入式要靠 `make menuconfig` 裁剪内核。
</details>

<details>
<summary>2. 用户态和内核态运行在同一个地址空间吗？系统调用要切换页表吗？</summary>

**是同一个地址空间**（Linux 虚拟内存模型）：内核占高地址段、用户态占低地址段，靠页表权限隔离。所以系统调用**不需要切换页表**（不用刷新 TLB），只是 CPU 特权级从 ring 3/EL0 升到 ring 0/EL1。这是 Linux 系统调用快于部分其他 OS 设计的原因之一。
</details>

<details>
<summary>3. 系统调用号（如 write=1）是怎么变成内核函数的？</summary>

内核维护一张 `sys_call_table[]`（`arch/x86/entry/syscall_64.c:16`），下标就是系统调用号：

```c
asmlinkage const sys_call_ptr_t sys_call_table[] = {
#include <asm/syscalls_64.h>
};
```

用户态 `syscall` 指令陷入后，内核入口从 `rax` 读号码，然后 `sys_call_table[nr]` 查到对应的 `__x64_sys_write` 等实现。号码是**固定 ABI**（写死在 `syscall_64.tbl`），不能乱改，否则破坏用户态兼容。

本节实测把这张表的前几项打了 出来：`SYS_read=0`、`SYS_write=1`、`SYS_open=2`、`SYS_close=3`、`SYS_mmap=9`、`SYS_getpid=39`、`SYS_fork=57`、`SYS_execve=59`。
</details>

<details>
<summary>4. <code>fopen</code>、<code>write</code>、<code>strlen</code> 三者谁是系统调用？</summary>

只有 `write` 是系统调用（`man 2`，glibc 薄封装、直接陷入）。`fopen` 是库函数（`man 3`，内部调用 `open` 系统调用 + 建立缓冲），`strlen` 是纯用户态函数（不进内核）。区分靠 `man 2`（syscall）vs `man 3`（库函数）。

实测佐证：`strlen("hello") = 5` 和 `sizeof("hello") = 6` 都在用户态算完，一次系统调用都不发。
</details>

<details>
<summary>5. 我明明先 <code>printf("[A]")</code> 再 <code>write("[B]")</code>，为什么屏幕上 B 先出来？</summary>

因为 **stdio 在缓冲**。本节段 ④ 实测：

```text
  isatty(STDOUT_FILENO) = 0  (0 = stdout 接的是管道/文件 → 全缓冲)
  [B] 这行由 write 直接落到 fd 1
  [A] 这行由 printf 写入 stdio 缓冲，此刻还没进内核
```

源码顺序是 A → B → C → D，实测是 **B → A → C → D**。`isatty(1) == 0` 说明 stdout 不是终端，stdio 于是用**全缓冲**（默认 8192 字节，即 `BUFSIZ`）：`printf` 的字先躺在用户态缓冲里，而 `write()` 是系统调用、立刻落到 `fd 1`。

两条推论：**①** 想在热路径上让输出顺序确定，就别用 stdio——直接 `write()`；**②** 想把 `printf` 的内容立刻推出去，`fflush(stdout)`。反过来说，这个缓冲也正是性能手段：一次 1000 字节的 `printf` 只发 1 次 `write`，而 1000 次 1 字节的 `write` 要发 1000 次 syscall。
</details>

<details>
<summary>6. 为什么 HFT 热路径要「尽量少系统调用」？有哪些替代手段？</summary>

系统调用要模式切换 + 保存现场 + 权限校验，约数百 ns，对微秒级敏感路径不可忽略。替代：

1. `mmap` 把文件/设备映射进用户态，后续直接访存（[2.8](./2.8-memory-mappings.md)）；
2. 批量 I/O（一次 `read`/`write` 传大数据）；
3. `io_uring` 异步批量提交；
4. 高频计时用 vDSO（`clock_gettime` 不进内核，[2.16](./2.16-date-time.md)）。

核心原则：**把 N 次小 syscall 合并成 1 次大操作**。
</details>

<details>
<summary>7. <code>man 2</code> 和 <code>man 3</code> 的区别？系统调用和 glibc 是两个独立的库吗？</summary>

`man 2` 查**系统调用**（内核提供的接口，调它会陷入内核），`man 3` 查**库函数**（glibc 等用户态库提供的接口，可能进内核也可能不进）。同名冲突要带节号：`man 1 mkdir`（shell 命令）≠ `man 2 mkdir`（系统调用）。

系统调用和 glibc **不是两个独立的库**：系统调用根本不是库——它是内核（vmlinux）里的函数集合，跑特权态，没有 `.so` 可链接，只能经 `syscall`/`svc` 指令陷入；glibc 才是用户态共享库（`libc.so.6`），既提供系统调用的封装（`open`/`write`），也提供纯用户态函数（`strlen`/`strcpy`）。两者是**上下层**关系：glibc 靠系统调用落地，内核完全不依赖 glibc。

「绕开」还要再拆细一层：`syscall(SYS_write, ...)` 绕开的只是 glibc 对**各个**系统调用的单独包装（`write()` 那些），**它自己仍是 glibc 函数**，链接时照样要 glibc；想**完全脱离 glibc**，只能手写汇编直接发陷入指令——本节 `c2_1_nolibc` 实测：`-nostdlib -static` 编译，`ldd` 显示 *not a dynamic executable*，strace 全程只有 `write` + `exit` 两次系统调用（glibc 版 29 次），二进制 1296 字节（glibc 版 70496 字节）。
</details>
