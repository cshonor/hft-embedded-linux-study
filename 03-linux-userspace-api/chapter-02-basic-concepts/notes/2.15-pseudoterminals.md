## 本节讲什么

伪终端（PTY）是一对「互相连通」的设备，让程序**以为自己连着真终端**，实际另一端是另一个程序（`sshd`、`tmux`、终端模拟器）。本节回答三个问题：

1. PTY 的 master / slave 两端分别是什么？数据怎么流？
2. 为什么 `ssh`、`script`、`tmux`、`docker run -t` 都离不开 PTY？
3. PTY 和管道（pipe）的关键区别是什么？什么时候必须用 PTY？

完整 API 在 [Ch64](../../chapter-64-pseudoterminals/README.md)，这里建立「**PTY = 带终端语义的双向通道**」的核心心智。

本节要补的是一个**逆向的实测**：本容器**没有** `/dev/ptmx` 与 `/dev/pts`，所以 `posix_openpt()` 直接 `ENOENT`。这反而说明了一件重要的事——**PTY 不是内核里「一定有」的东西，它需要 devpts 文件系统挂载**。笔记把「跑通的部分」和「环境边界」分开记录，并用 `socketpair` 演练了骨架部分。

## 要点

### 一、PTY 的结构：master + slave 一对设备

```
程序 A（sshd / tmux / 终端模拟器）        程序 B（bash / vim / top）
   │                                              │
   ▼                                              ▼
PTY master ─────── 内核 PTY（含行规程）───────→ PTY slave
/dev/ptmx                                    /dev/pts/N
   │                                              │
   └─ 写 master 的数据 → slave 读到                └─ 以为自己连着真终端
      slave 写的数据 → master 读到                   （isatty() == 1）
```

| 端点 | 路径 | 谁持有 | 特性 |
|------|------|--------|------|
| **master（主端）** | `/dev/ptmx` | 「扮演终端」的程序 | 普通字符设备，无终端语义 |
| **slave（从端）** | `/dev/pts/N` | 「被控制」的程序 | **完整终端语义**：`isatty()==1`、termios、行规程、能收终端信号 |

数据流是**双向对称**的：

- master 写 → slave 读（等于「终端把内容显示给用户」）
- slave 写 → master 读（等于「用户敲键盘」）

### 二、中间那层「行规程（line discipline）」才是 PTY 的全部价值

PTY 的核心不是「双向字节流」（`socketpair` 就有），而是 slave 端挂的**行规程**——这一层由内核提供，普通 pipe/socket 一律没有：

| 行规程负责 | 效果 |
|-----------|------|
| **行缓冲**（`ICANON`） | 你打的字先攒着，按回车才交给程序 |
| **`Ctrl+C` → SIGINT** | 发给 slave 的**前台进程组**（就是 [2.13](./2.13-process-groups.md) 的广播） |
| `Ctrl+Z` → SIGTSTP；`Ctrl+\` → SIGQUIT | 同上 |
| **回显 / 退格处理**（`ECHO`） | 程序没写的字符也会显示出来 |
| **`ioctl(TIOCGWINSZ)`** | 让 `vim` / `top` 知道「窗口多少行多少列」 |
| **`ONLCR` 换行转换** | 程序写 `\n`，终端收到 `\r\n` |

所以「远程把 `bash` 接到一个管道上」是做不到的：`bash` 检查 `isatty(stdin)` 为假，就退化成**非交互模式**——不做补全、不打印提示符、不读 `.bashrc` 的交互分支。

### 三、打开 PTY 的固定套路（四步 + 一步到位的 BSD 版本）

```c
int master = posix_openpt(O_RDWR | O_NOCTTY);  /* ① 打开 master（需 /dev/ptmx） */
grantpt(master);                                /* ② 授权 slave 可被本用户打开 */
unlockpt(master);                               /* ③ 解锁 slave */
char *name = ptsname(master);                   /* ④ 得到 slave 路径 /dev/pts/N */
int slave  = open(name, O_RDWR);                /* ⑤ 打开 slave */

/* 之后：子进程 setsid + 把 slave 打开成 0/1/2 + exec shell */
```

| 调用 | 作用 |
|------|------|
| `posix_openpt()` | 拿 master fd（内核里对应打开 `/dev/ptmx`） |
| `grantpt()` | 改 slave 属主/权限（新内核由 devpts 自动处理） |
| `unlockpt()` | 解锁 slave，允许 `open` |
| `ptsname()` | 取 slave 路径（如 `/dev/pts/3`） |
| `openpty()` / `forkpty()` | **BSD 一步到位**：上面四步 + `fork`（`forkpty` 还把 slave 设为子进程的 0/1/2）；glibc 提供，在 `libutil` |

⚠️ `O_NOCTTY` 很重要：**防止 master 意外成为本进程的控制终端**。master 端不该带终端语义。

### 四、和控制终端的关系

PTY 的 slave 端**可以成为会话的控制终端**（见 [2.14](./2.14-sessions.md)）。内核里会话与终端的关联就存在 `signal_struct` 上：

```c
/* include/linux/sched/signal.h:174 */
struct tty_struct *tty;   /* NULL if no tty —— 会话的控制终端 */
```

`sshd` 给远程登录 shell 建会话的完整链路：

```
shell setsid() 成为会话首领
  → 打开 slave 作为 0/1/2
  → slave 成为该会话的控制终端（signal_struct->tty 指向它）
  → 之后 slave 行规程把 Ctrl+C 转成 SIGINT 发给前台进程组

ssh 断开：
  sshd 关闭 master → slave 检测到 hangup
  → tty 驱动向控制进程（shell）发 SIGHUP
  → shell 及其前台进程组受影响
```

这就是「ssh 一断，远程 shell 及其子进程收到 SIGHUP」的完整机制——[2.14](./2.14-sessions.md) 讲了「谁收 SIGHUP」，本节补上了「是谁产生的」。

### 五、谁在用 PTY

| 用途 | master 持有者 | slave 使用者 |
|------|--------------|--------------|
| **ssh / telnet 远程登录** | `sshd`（`forkpty`） | 远程交互 shell |
| **终端模拟器** | `xterm` / `gnome-terminal` | 里面的 shell |
| **script 录制会话** | `script` 程序（master 侧抄一份） | 被录制的 shell |
| **tmux / screen** | tmux 服务进程 | 每个窗格里的 shell |
| **自动化交互** | `expect` / `pexpect` | 被驱动的命令行程序 |
| **容器交互** | `docker run -t` / `kubectl exec -it` | 容器里的进程 |

> **记忆钩子**：见到 **`-t` / `-it`** 就想到 PTY——那个 `-t` 就是「**分配一个伪终端**」（`--tty`）。

**解读**

1. **段 ① 的 `ENOENT` 不是「PTY 不能用」，而是「这台机器没配 PTY」**——这个区分极其重要。`posix_openpt()` 的实现就是 `open("/dev/ptmx", O_RDWR|O_NOCTTY)`；`/dev/ptmx` 由 **devpts 文件系统**（或 `devtmpfs`）提供，容器默认**不挂**这两个（为了减少攻击面）。所以：

   | 环境 | `/dev/ptmx` | `posix_openpt()` |
   |------|-------------|------------------|
   | 普通 Linux / 有 `-t` 的容器 | 存在 | 成功，返回 master fd |
   | **本容器（无 devpts）** | **不存在** | **`ENOENT(2)`** |

   要在容器里拿到 PTY，需要 `docker run -t`（引擎会挂 devpts）或手动 `mount -t devpts`。**这属于「挂载配置」问题，不是 API 用法问题**——`ENOENT` 而不是 `EACCES` 就是证据。

2. **段 ③ 的输出里有换行的「错位」值得解释**（`"echo hello-from-master` 后面换行才出现 `"`）：因为写入的字符串**本身带 `\n`**，而这里**没有行规程做转换**——`socketpair` 是原始字节通道，`\n` 原样到达。这正是要点二表格里 **`ONLCR` 换行转换** 那一行的反面例证：

   | | 程序写 `\n` | 对端实际收到 |
   |---|---|---|
   | 真 PTY（有 `ONLCR`） | `\n` | **`\r\n`** |
   | `socketpair`（本节段 ③） | `\n` | `\n`（原样，故显示错位） |

   这也解释了为什么在真终端里跑 `printf("a\n")` 显示正常，而把输出重定向到文件再用 `cat` 看有时会「阶梯状」——那是**缺了 `\r`** 导致的，而终端会替你补。

3. **段 ③ 的两个 `isatty() = 0` 是「替代方案的天花板」**：`socketpair` 完美复现了「双向、能回话」的骨架，但**两端都不是终端**。所以：

   - 想让程序以为自己是终端 → **必须** PTY（或者用 `LD_PRELOAD` 伪造 `isatty`，那是黑客手段）；
   - 只做数据搬运 → `pipe`/`socketpair` **更轻**（无线程、无行规程加工）。

   **不要为了「看起来高级」而用 PTY**——它的行规程会改数据（换行转换、回显、`Ctrl+C` 被吃掉），对纯数据流是**破坏性的**。

4. **段 ⑤ 的「如实记录」是本节的方法论示范**：本 demo 的设计目标之一就是**展示一次真实的、因环境导致的失败**，并把「代码路径」和「可执行部分」分开。这比伪造一段「假想的 PTY 输出」诚实得多——而且 `ENOENT` 这个错误码本身就是有价值的结论（见解读 1）。

5. **`forkpty(&master, NULL, NULL, NULL)` 的四个参数值得记住**：`(int *amaster, char *name, struct termios *termp, struct winsize *winp)`。后三个都可以传 `NULL` 表示「用默认」；`winp` 是窗口大小（`TIOCGWINSZ` 的初值）——`tmux` 分屏时就是不断改这个值通知 slave 侧程序重画。**`forkpty` 返回的是 `pid`**（像 `fork` 一样），父进程拿到 master fd 走 `amaster` 出参，子进程拿到的是**已接好的 0/1/2**。

| **纯数据流不要用 PTY** | 段 ③ 结论：`socketpair` 更轻。PTY 的 `ONLCR`/回显/`Ctrl+C` 会**改数据**，对二进制或协议流是破坏性的 |

## 自测题

<details>
<summary>1. PTY 的 master 和 slave 分别是什么？数据怎么流？</summary>

| 端点 | 路径 | 谁持有 | 终端语义 |
|------|------|--------|----------|
| master | `/dev/ptmx` | 「扮演终端」的程序（`sshd`/`tmux`/模拟器） | ❌ 无 |
| slave | `/dev/pts/N` | 「被控制」的程序（`bash`/`vim`） | ✅ 完整（`isatty()==1`） |

数据**双向对称**：master 写 → slave 读（等于「终端显示给用户」）；slave 写 → master 读（等于「用户敲键盘」）。

本节段 ③ 用 `socketpair` 复现了这个骨架（能双向、能回话），但两端 `isatty()` 都是 `0`——**骨架能仿，终端语义仿不了**。
</details>

<details>
<summary>2. 为什么「用管道给 ssh 传密码」或「用管道跑 vim」会失败？</summary>

因为交互式程序会检查 **`isatty(stdin)`**——管道不是 tty，程序就进入**非交互模式**或直接拒绝：

- `ssh` 需要 tty 才读密码（或直接要求改用密钥/`SSH_ASKPASS`）；
- `vim` / `top` 需要 tty 才能画界面（还会 `ioctl(TIOCGWINSZ)` 问窗口大小）；
- `bash` 检测到非 tty 就不做补全、不打印提示符、不读 `.bashrc` 的交互分支。

根本原因不只是 `isatty` 为假，还因为管道**没有行规程**——没有 termios 属性、不产生终端信号、不做 `\n → \r\n` 转换（要点二的表）。

要跑交互式程序**必须**用 PTY 模拟真终端。这是 `ssh` / `tmux` / `script` / `expect` / `docker -t` 全用 PTY 的根本原因。
</details>

<details>
<summary>3. 打开 PTY 的标准四步 API 是什么？<code>O_NOCTTY</code> 为什么重要？</summary>

四步：

```c
int master = posix_openpt(O_RDWR | O_NOCTTY);  /* ① */
grantpt(master);                                /* ② 授权 slave */
unlockpt(master);                               /* ③ 解锁 slave */
char *name = ptsname(master);                   /* ④ 取路径 /dev/pts/N */
int slave = open(name, O_RDWR);
```

BSD 风格一步到位：`openpty()` / `forkpty()`（`<pty.h>`，需 `-lutil`）。

**`O_NOCTTY` 重要**是因为：如果 master 成为本进程的控制终端，本进程（比如 `sshd` 的主逻辑）就会开始接收终端信号（`Ctrl+C` → `SIGINT`）、并可能在某些操作后被 `SIGHUP` 干掉。**master 端应该是「干净的信道」，不带终端语义**——终端语义只应该出现在 slave 端。

本节段 ① 实测：本容器无 devpts，第一步就 `ENOENT(2)`。
</details>

<details>
<summary>4. PTY 和管道的关键区别是什么？什么时候必须用 PTY？</summary>

| 维度 | 管道（pipe/socketpair） | 伪终端（PTY） |
|------|------------------------|--------------|
| `isatty()` | ❌ false | ✅ **true** |
| termios 属性 | ❌ | ✅（波特率、行规程、`echo`） |
| `Ctrl+C` → SIGINT | ❌ | ✅（slave 行规程产生） |
| 作业控制 | ❌ | ✅ |
| 换行转换 | ❌（`\n` 原样） | ✅（`ONLCR`：`\n` → `\r\n`） |
| 开销 | 小 | 大（多一层行规程加工） |
| 用途 | 进程间传数据 | **跑交互式程序** |

**判断标准**：

- 对方**要检查 `isatty()`**（shell、`vim`、`ssh` 客户端、`expect` 驱动的程序）→ 必须 PTY；
- 只是**搬字节**（协议数据、二进制流、日志转发）→ **用 pipe/socketpair**，别用 PTY。

本节段 ③ 的换行「错位」就是反例：`socketpair` 不做 `ONLCR`，`\n` 原样到达；真 PTY 会自动补 `\r`。
</details>

<details>
<summary>5. 「ssh 一断，远程 shell 及其子进程收到 SIGHUP」的完整链路是什么？</summary>

```
① sshd 给远程 shell 建会话：
     shell setsid() 成为会话首领
     → 打开 PTY slave 作为 0/1/2
     → slave 成为该会话的控制终端（信号结构里 signal_struct->tty 指向它，
       include/linux/sched/signal.h:174）

② ssh 连接断开：
     sshd 关闭 master
     → slave 检测到 hangup（tty_hangup）
     → tty 驱动向会话的**控制进程**（shell）发 SIGHUP
     → shell 默认终止，其前台进程组（子进程）随之受影响
```

要防止被挂断：`setsid` 脱离终端，或 `tmux` / `nohup` 托管。

**关键分工**：[2.14](./2.14-sessions.md) 讲的是「**谁收** `SIGHUP`」（会话首领/控制进程），本节补上了「**是谁产生**的」（master 关闭 → slave hangup → tty 驱动）。
</details>

<details>
<summary>6. <code>docker run -t</code> 里的 <code>-t</code> 做了什么？不加会怎样？</summary>

`-t` = `--tty`，作用是让引擎**为容器挂载 devpts 文件系统**（提供 `/dev/ptmx` + `/dev/pts`），并给容器主进程分配一个 PTY slave 作为它的 stdin/stdout/stderr。

**不加 `-t`**：

- 容器里没有 `/dev/ptmx`、`/dev/pts`（**本节段 ① 实测的就是这个状态**）→ `posix_openpt()` 报 `ENOENT(2)`；
- 主进程的 `isatty(0/1)` 为 `0` → `bash` 进入非交互模式、`top` 拒绝运行、彩色输出自动关闭；
- `kubectl exec -it` 少了 `-t` 同理：**`kubectl exec -i` 只能喂管道，`-it` 才能开交互 shell**。

**记忆钩子**：见到 `-t` / `-it` 就想到 PTY——它就是「**分配一个伪终端**」。
</details>

<details>
<summary>7. 为什么这个 demo 要去测一个「注定失败」的调用？</summary>

因为**失败本身是结论**，而且比「假设成功」更有信息量：

1. **错误码能定位病因**：`ENOENT(2)` 而不是 `EACCES(13)` 或 `EPERM(1)`，说明问题是「**设备不存在**」（devpts 没挂），不是权限。排查方向立刻明确：查 `mount | grep devpts`，而不是查 `CAP_*` 或 `uid`。
2. **它把一个隐性前提变成了显性知识**：读完这段就知道「**PTY 需要挂载**」，而只读 API 文档是看不出来的——`posix_openpt(3)` 的文档不会告诉你「容器里可能没挂 devpts」。
3. **它示范了「笔记」的诚实底线**：段 ⑤ 明确写「本环境在第一步就 `ENOENT` 了，后面全部无法执行 —— 如实记录」。**把「跑通的部分」和「环境边界」分开标注**，比伪造一段看起来跑通的输出可信得多——这也是本仓库所有「CE 复核」章节的统一纪律。
</details>
