## 本节讲什么

伪终端（PTY）是一对「互相连通」的设备，让程序**以为自己连着真终端**，实际另一端是另一个程序。本节回答三个问题：

1. PTY 的 master/slave 两端分别是什么？数据怎么流？
2. 为什么 `ssh`、`script`、终端模拟器都离不开 PTY？
3. PTY 和管道（pipe）的关键区别是什么？什么时候必须用 PTY？

完整 API 在 Ch64，这里建立「PTY = 带终端语义的双向通道」的核心心智。

---

## 1. PTY 的结构：master + slave 一对

```
程序 A（如 sshd）          内核           程序 B（如 shell）
   │                                        │
   ▼                                        ▼
PTY master ──────────── 双向数据流 ──────→ PTY slave
/dev/ptmx                               /dev/pts/N
   │                                        │
   └─ 写 master 的数据 → slave 读到          └─ shell 以为连着真终端
      slave 写的数据 → master 读到
```

- **master（主端）**：`/dev/ptmx`，由「扮演终端」的程序持有（sshd、终端模拟器）
- **slave（从端）**：`/dev/pts/N`，给「被控制」的程序（交互式 shell），它看到的是一个**真终端**——`isatty()` 返回 true，有 termios 属性、有行规程（line discipline）、能收终端信号

数据流是**双向对称**的：master 写 → slave 读（等于「终端显示给用户」），slave 写 → master 读（等于「用户敲键盘」）。

## 2. 打开 PTY 的固定套路

```c
int master = posix_openpt(O_RDWR | O_NOCTTY);  /* ① 打开 master */
grantpt(master);                                /* ② 授权 slave 可被打开 */
unlockpt(master);                               /* ③ 解锁 slave */
char *name = ptsname(master);                   /* ④ 得到 slave 路径 /dev/pts/N */
int slave  = open(name, O_RDWR);                /* ⑤ 打开 slave */

/* 接下来：子进程 setsid + 打开 slave 作为 0/1/2 + exec shell */
```

四步 API（`posix_openpt` → `grantpt` → `unlockpt` → `ptsname`）是 POSIX 标准序列；BSD 风格有一步到位的 `openpty()`/`forkpty()`（`<pty.h>`，glibc 提供）。内核侧，master 是 `/dev/ptmx`（每 `open` 一次分配一个新的 slave），slave 由 **devpts** 文件系统动态挂载到 `/dev/pts/`。

## 3. 与「控制终端」的关系

PTY 的 slave 端**可以成为会话的控制终端**（见 2.14）。内核里会话与终端的关联存在 `signal_struct` 里：

```c
/* include/linux/sched/signal.h:174 */
struct tty_struct *tty;   /* NULL if no tty —— 会话的控制终端 */
```

当 `sshd` 给远程登录的 shell 建会话时：shell `setsid()` 成为会话首领 → 打开 slave 作为 stdin/stdout/stderr → 这个 slave 成为会话的控制终端。之后：slave 侧的行规程把 `Ctrl+C` 转成 SIGINT 发给前台进程组、终端断开时 master 关闭 → slave 检测到 hangup → 向控制进程发 SIGHUP（这就是「ssh 一断，远程 shell 及其子进程收到 SIGHUP」的完整链路）。

## 4. PTY 的典型用途

| 用途 | master 持有者 | slave 使用者 |
|------|--------------|--------------|
| **ssh 远程登录** | sshd | 远程交互 shell |
| **终端模拟器** | xterm/gnome-terminal | 里面的 shell |
| **script 录制会话** | `script` 程序 | 被录制的 shell |
| **tmux/screen** | tmux 服务进程 | 每个窗格里的 shell |
| **自动化交互** | expect/pexpect | 被驱动的命令行程序 |

## 5. PTY vs 管道：什么时候必须用 PTY

| 维度 | 管道（pipe） | 伪终端（PTY） |
|------|-------------|--------------|
| `isatty()` | false | **true** |
| termios 属性 | ❌ | ✅（波特率、行规程、`echo` 等） |
| 终端信号（Ctrl+C→SIGINT） | ❌ | ✅（slave 行规程产生） |
| 作业控制 | ❌ | ✅ |
| 换行转换 | ❌（原样） | ✅（`\n` → `\r\n`，`ONLCR`） |
| 用途 | 进程间传数据 | **跑交互式程序** |

**关键**：交互式程序（shell、vim、top、ssh 客户端）会检查 `isatty(stdin)`，如果不是 tty 就进入**非交互模式**或直接报错。所以「用管道给 ssh 传密码」「用管道跑 vim」都会失败——必须用 PTY 模拟出真终端。反之，纯数据管道用 pipe 就够，别用 PTY（有行规程加工、更重）。

## 6. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 远程运维交易机 | `ssh` 登录靠 PTY 建立交互 shell，ssh 断开触发 SIGHUP（见 2.14，须 `setsid`/`tmux` 托管） |
| 自动化交易 CLI 工具 | 用 `expect`/`pexpect` 驱动需要交互输入的命令行工具（走 PTY） |
| headless 交易机 | 无终端环境，stdout 非 tty，程序据此关闭彩色输出/进度条防 ANSI 污染日志 |
| 嵌入式串口登录 | getty 在串口上跑登录进程，本质也是「串口 → 控制终端」的关联，PTY 是软件版 |
| 日志采集 | `script` 录制操作审计（走 PTY），保留完整的输入输出时间线 |

## 7. 代码示例

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <pty.h>

/* forkpty：一步建 PTY + fork 子进程，子进程的标准 IO 接到 slave */
int main(void) {
    int master;
    pid_t pid = forkpty(&master, NULL, NULL, NULL);

    if (pid == -1) { perror("forkpty"); return 1; }

    if (pid == 0) {
        /* 子进程：stdin/stdout/stderr 已接到 slave，跑交互式 shell */
        execl("/bin/sh", "sh", NULL);
        perror("execl");
        _exit(127);
    }

    /* 父进程：通过 master 与子进程的 shell 交互 */
    char buf[4096];
    ssize_t n;
    write(master, "echo hello-from-pty\n", 20);       /* 给 shell 发命令 */
    while ((n = read(master, buf, sizeof(buf) - 1)) > 0) {
        buf[n] = '\0';
        printf("master got: %s", buf);                 /* 读 shell 的输出 */
    }
    return 0;
}
```

编译：`gcc -o pty pty.c -lutil`（`forkpty` 在 libutil）。运行后父进程通过 master 给子进程的 shell 发命令、读回输出——这就是 `ssh`/`script` 控制交互程序的核心机制。

<summary>代码自测（Q&A）</summary>

**Q1：PTY 的 master 和 slave 分别是什么？数据怎么流？**
A：master（`/dev/ptmx`）由「扮演终端」的程序持有，slave（`/dev/pts/N`）给「被控制」的程序。数据双向对称：master 写 → slave 读（等于「终端显示给用户」），slave 写 → master 读（等于「用户敲键盘」）。slave 端让程序以为自己连着真终端（`isatty` 为 true、有 termios）。

**Q2：为什么「用管道给 ssh 传密码」或「用管道跑 vim」会失败？**
A：因为交互式程序会检查 `isatty(stdin)`——管道不是 tty，程序就进入非交互模式或拒绝运行。此外管道没有 termios 属性、不产生终端信号、不做行规程加工。要跑交互式程序必须用 PTY 模拟出真终端（`isatty` 为 true）。这是 `ssh`/`tmux`/`script`/`expect` 都用 PTY 的根本原因。

**Q3：打开 PTY 的标准四步 API 是什么？**
A：`posix_openpt(O_RDWR|O_NOCTTY)` 打开 master → `grantpt(master)` 授权 slave 可被本用户打开 → `unlockpt(master)` 解锁 slave → `ptsname(master)` 得到 slave 路径 `/dev/pts/N`，再 `open` 它。BSD 风格可用一步到位的 `openpty()`/`forkpty()`。`O_NOCTTY` 防止 master 意外成为控制终端。

**Q4：PTY 和管道的关键区别是什么？**
A：管道是纯数据通道（`isatty` 为 false、无 termios、无信号），PTY 是「带终端语义」的双向通道（`isatty` 为 true、有 termios 属性、slave 行规程把 `Ctrl+C` 转成 SIGINT、做 `\n→\r\n` 换行转换、支持作业控制）。传数据用 pipe 就够（更轻），跑交互式程序才必须 PTY。

**Q5：「ssh 一断，远程 shell 及其子进程收到 SIGHUP」的完整链路是什么？**
A：sshd 给远程 shell 建会话：shell `setsid` 成为会话首领，打开 PTY slave 作为 0/1/2，slave 成为会话控制终端（内核存在 `signal_struct->tty`）。当 ssh 连接断开：sshd 关闭 master → slave 检测到 hangup → tty 驱动向会话的控制进程（shell）发 SIGHUP → shell 默认终止，其子进程（前台进程组）也随之受影响。要防止进程被挂断，须 `setsid` 脱离终端或 `tmux`/`nohup` 托管。
