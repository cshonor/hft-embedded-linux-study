## 本节讲什么

Linux 有两类时间：**日历时间**（墙上的钟，可被修改）和**进程时间**（CPU 消耗）。本节回答三个问题：

1. 日历时间和进程时间分别是什么？用什么 API 拿？
2. `CLOCK_REALTIME`、`CLOCK_MONOTONIC`、`CLOCK_MONOTONIC_RAW` 有什么区别？HFT 计时该用哪个？
3. 为什么 `clock_gettime` 能快到「不进内核」（vDSO）？

完整 API 在 [Ch10](../../chapter-10-time/README.md)，这里建立「**计时选对时钟 = 延迟测量正确性**」的核心心智。

本节要补的是一个**能直接量出来的实验**：同一段 200 万次循环，用 `CLOCK_MONOTONIC` 测得 `6889676 ns`，用 `CLOCK_REALTIME` 测得 `5901373 ns`，用进程 CPU 时间测得 `5827561 ns`——**三个数字不一样**，而差异的来源就是本节的结论。

## 要点

### 一、两类时间：日历时间 vs 进程时间

| 类型 | 说明 | 典型 API |
|------|------|----------|
| **日历时间（wall clock）** | 自 Epoch（1970-01-01 00:00:00 UTC）起的秒数，**可被修改** | `time()`、`gettimeofday()`、`clock_gettime(CLOCK_REALTIME)` |
| **进程时间（CPU time）** | 进程消耗的 CPU 时间，**不可回拨** | `times()`、`clock()`、`clock_gettime(CLOCK_PROCESS_CPUTIME_ID)` |

进程时间又分三段：

| 时间 | 含义 |
|------|------|
| **user time** | 用户态执行消耗的 CPU 时间 |
| **system time** | 内核态（系统调用）消耗的 CPU 时间 |
| **real time** | 墙上实际流逝时间（= user + system + **等待/被抢占**） |

`time` 命令输出的 `real/user/sys` 三列就是这个区分——`real` 可能远大于 `user+sys`（进程在等 I/O、被调度器抢占）。

### 二、`clockid_t`：选哪个钟是个严肃决定

```c
time_t t = time(NULL);                          /* 秒级，最粗最省 */
struct timeval tv; gettimeofday(&tv, NULL);     /* 微秒级，过时但仍广泛使用 */
struct timespec ts;
clock_gettime(CLOCK_REALTIME, &ts);             /* 纳秒级，现代首选 */
```

`clock_gettime` 用 `clockid_t` 选择「哪个钟」——**这个选择决定了测量是否可信**：

| clockid | 起点 / 含义 | 会被 NTP 影响吗 | 含 suspend 吗 |
|---------|------------|----------------|--------------|
| `CLOCK_REALTIME` | **Epoch（1970）** —— 墙上时间 | ✅ **会被步进（回拨/跳变）** | — |
| `CLOCK_MONOTONIC` | 开机某点，**只前进** | ⚠️ 只受频率微调（slew），**不回拨** | ❌ 不含（`CLOCK_BOOTTIME` 才含） |
| `CLOCK_MONOTONIC_RAW` | 纯硬件计数 | ❌ **完全不受 NTP 任何影响** | ❌ |
| `CLOCK_REALTIME_COARSE` | 缓存的墙上时间 | ✅（同 REALTIME） | — |
| `CLOCK_BOOTTIME` | 单调，**含 suspend 时间** | ⚠️ 同 MONOTONIC | ✅ **含** |
| `CLOCK_PROCESS_CPUTIME_ID` | 本进程 CPU 时间 | ❌ | — |
| `CLOCK_THREAD_CPUTIME_ID` | 本线程 CPU 时间 | ❌ | — |

### 三、HFT 计时铁律：测间隔绝不用 `CLOCK_REALTIME`

**`CLOCK_REALTIME` 会被 NTP 步进（stepping）或管理员 `settimeofday` 回拨**，用它做区间测量会算出**负的时间差**。

```
CLOCK_REALTIME:      ├───────────┤  NTP 回拨 → 时间倒退，间隔算出负数 ❌
CLOCK_MONOTONIC:     ├───────────→  只会单调递增，间隔永远 ≥ 0        ✅
```

| 场景 | 该用 |
|------|------|
| 测量延迟 / 间隔（latency） | `CLOCK_MONOTONIC`，微秒级抖动用 `CLOCK_MONOTONIC_RAW` |
| 记录「事件发生在墙上几点」 | `CLOCK_REALTIME`（**但别用它算间隔**） |
| 统计进程 / 线程 CPU 占用 | `CLOCK_PROCESS_CPUTIME_ID` / `CLOCK_THREAD_CPUTIME_ID` |
| 只想知道「大概几点了」 | `CLOCK_REALTIME_COARSE` 或 `time()`（**便宜得多**） |

**`CLOCK_MONOTONIC` vs `CLOCK_MONOTONIC_RAW`**：前者会被 NTP **频率微调**（slew——缓慢校正晶振漂移，让时间走快/走慢一点，但绝不回拨）；后者是**纯硬件计数**，完全不受 NTP 干扰。日常测间隔用 `CLOCK_MONOTONIC` 即可；要在**纳秒级抖动测量**里排除 NTP 的持续微调，才用 `MONOTONIC_RAW`。

**`CLOCK_MONOTONIC` vs `CLOCK_BOOTTIME`**：两者的差别只有一个——**挂起（suspend）期间的时间算不算**。`MONOTONIC` **不算**（笔记本合盖 1 小时，`MONOTONIC` 只走了几分钟），`BOOTTIME` **算**。所以「判断设备开机多久」要用 `BOOTTIME`，「测代码耗时」用 `MONOTONIC`。

### 四、vDSO：`clock_gettime` 为什么能不进内核

`clock_gettime` 的系统调用号是 **228**（`syscall_64.tbl:239`，x86-64 固定 ABI），但**实际调用常常不陷入内核**——内核把时钟数据通过 **vDSO**（virtual dynamic shared object）映射到每个进程的地址空间，`clock_gettime` 直接在用户态读这块只读数据算出来：

```c
/* lib/vdso/gettimeofday.c:110 —— 高精度路径，用户态直接算 */
static __always_inline int do_hres(const struct vdso_data *vd, clockid_t clk,
				   struct __kernel_timespec *ts)
```

机制三点：

| 点 | 说明 |
|----|------|
| **映射** | 内核把一段代码 + 数据（`vdso_data`）映射进每个进程的用户态地址空间（在 `/proc/self/maps` 里能看到 `[vdso]` 段） |
| **分派** | glibc 的 `clock_gettime` / `gettimeofday` / `time` **优先走 vDSO 快速路径**，成功就直接返回 |
| **回退** | 只有 vDSO 无法处理的情况（如需要精确校准的罕见表）才真正发系统调用 228 陷入内核 |

**为什么这件事对 HFT 至关重要**：热路径里每笔行情都打时间戳，如果每次 `clock_gettime` 都是「陷入内核 + 返回」的完整系统调用（几百纳秒），时间戳本身就吃掉了可观的比例。走 vDSO 后开销降到**几十纳秒**（纯用户态几条内存读 + 乘法）。

## 代码

### c2_16 时钟：一族 clockid 的对比 + 「用哪个测耗时」实验

[`../code/c2_16_clock.c`](../code/c2_16_clock.c) 分五段：

| 段 | 做什么 | 钉死什么 |
|----|--------|----------|
| ① | 遍历 5 个 `clockid`，打印 `clock_gettime` 值 + `clock_getres` 分辨率 | REALTIME（17 亿秒）与 MONOTONIC（8019 秒）**不同源** |
| ② | 同一段 200 万次循环，分别用 MONOTONIC / REALTIME / CPU 时间测 | **三个数字不一样**，墙钟 ≠ CPU 时间 |
| ③ | 在循环里同时取 REALTIME 与 MONOTONIC，比较各自「走了多少」 | 基数差是常数，有意义的是**前进速度** |
| ④ | `time()` / `gettimeofday()` / `CLOCK_REALTIME_COARSE` 对比 | 便宜时钟与精确时钟的取舍 |
| ⑤ | 读 `/proc/uptime` 与 `TZ` 环境变量 | 用 `/proc` 佐证 MONOTONIC / BOOTTIME |

```c
/* TLPI 第 2 章 §2.16 —— 日期与时间：先把「哪一类时钟」分清楚
 *
 * 编译：gcc -O0 -Wall -Wextra c2_16_clock.c -o c2_16
 * 运行：./c2_16
 *
 * 本节要钉死的事实：
 *   ① 时钟不是一个，是一族：墙上时间（可被 NTP 改）与单调时间（只前进）必须分开。
 *   ② 测「过了多久」只能用 CLOCK_MONOTONIC / CLOCK_BOOTTIME，绝不能用 REALTIME。
 *   ③ 进程/线程 CPU 时间（CLOCK_PROCESS_CPUTIME_ID）与墙上时间是两回事。
 *   ④ /proc/uptime 与 CLOCK_BOOTTIME 同源。
 *
 * ⚠️ 本节的定位是「分清楚有哪几类时钟」；struct tm / strftime / 时区 / 夏令时
 *    这套日历转换在 TLPI Ch10 展开，这里不重复。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <time.h>
#include <sys/time.h>

static long long ns_diff(struct timespec a, struct timespec b)
{
    return (b.tv_sec - a.tv_sec) * 1000000000LL + (b.tv_nsec - a.tv_nsec);
}

int main(void)
{
    printf("=== ① 一族时钟的当前值与分辨率 ===\n");
    struct { clockid_t id; const char *name; const char *meaning; } clocks[] = {
        { CLOCK_REALTIME,           "CLOCK_REALTIME",           "墙上时间：可被 NTP/adjtime 改，会跳" },
        { CLOCK_MONOTONIC,          "CLOCK_MONOTONIC",          "单调：只前进，含 suspend 以外的停机时间" },
        { CLOCK_BOOTTIME,           "CLOCK_BOOTTIME",           "单调 + 含 suspend 时间" },
        { CLOCK_PROCESS_CPUTIME_ID, "CLOCK_PROCESS_CPUTIME_ID", "本进程消耗的 CPU 时间" },
        { CLOCK_THREAD_CPUTIME_ID,  "CLOCK_THREAD_CPUTIME_ID",  "本线程消耗的 CPU 时间" },
    };
    printf("  %-24s %-20s %-12s %s\n", "clock", "now", "res", "含义");
    printf("  %-24s %-20s %-12s %s\n", "------------------------",
           "--------------------", "------------", "------------------");
    for (unsigned i = 0; i < sizeof(clocks) / sizeof(clocks[0]); i++) {
        struct timespec ts, res;
        char val[32] = "?", rv[32] = "?";
        if (clock_gettime(clocks[i].id, &ts) == 0)
            snprintf(val, sizeof(val), "%lld.%09ld", (long long)ts.tv_sec, ts.tv_nsec);
        if (clock_getres(clocks[i].id, &res) == 0)
            snprintf(rv, sizeof(rv), "%lldns", (long long)res.tv_sec * 1000000000LL + res.tv_nsec);
        printf("  %-24s %-20s %-12s %s\n", clocks[i].name, val, rv, clocks[i].meaning);
    }
    printf("  -> CLOCK_REALTIME 是一千七百多万秒（epoch 起算）；\n");
    printf("     CLOCK_MONOTONIC 是「开机以来的秒数」，明显更小 —— 两者不同源。\n");

    printf("\n=== ② 用哪个时钟测耗时：一个不能省的实验 ===\n");
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    volatile long acc = 0;
    for (long i = 0; i < 2000000; i++) acc += i;        /* 一段假热路径 */
    clock_gettime(CLOCK_MONOTONIC, &t1);
    long long mono_ns = ns_diff(t0, t1);

    struct timespec w0, w1;
    clock_gettime(CLOCK_REALTIME, &w0);
    struct timespec c0, c1;
    clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &c0);

    volatile long acc2 = 0;
    for (long i = 0; i < 2000000; i++) acc2 += i;

    clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &c1);
    clock_gettime(CLOCK_REALTIME, &w1);

    printf("  同一段循环跑两遍：\n");
    printf("    第 1 遍  MONOTONIC 测得        = %lld ns\n", mono_ns);
    printf("    第 2 遍  REALTIME  测得        = %lld ns\n", ns_diff(w0, w1));
    printf("    第 2 遍  进程 CPU 时间测得     = %lld ns\n", ns_diff(c0, c1));
    printf("  -> 墙钟（REALTIME/MONOTONIC）会包含「被别的进程挤掉 CPU」的时间；\n");
    printf("     进程 CPU 时间只算自己真正占着 CPU 的那部分。\n");
    printf("  -> 三者都不该用 REALTIME 来做区间测量：NTP 一调整就是负数区间。\n");

    printf("\n=== ③ REALTIME 与 MONOTONIC 的差值会漂移 ===\n");
    struct timespec r1, m1, r2, m2;
    clock_gettime(CLOCK_REALTIME, &r1); clock_gettime(CLOCK_MONOTONIC, &m1);
    struct timespec nap = { 0, 20000000L };             /* 20ms */
    nanosleep(&nap, NULL);
    clock_gettime(CLOCK_REALTIME, &r2); clock_gettime(CLOCK_MONOTONIC, &m2);
    printf("  REALTIME  在这段里走了 %lld ns\n", ns_diff(r1, r2));
    printf("  MONOTONIC 在这段里走了 %lld ns\n", ns_diff(m1, m2));
    printf("  两者基数之差 = %lld ns  （≈ 一个巨大的常数：epoch 到开机那一刻）\n",
           ns_diff(m2, r2));
    printf("  -> 差值本身没有意义，有意义的是「两个时钟各自前进的速度是否一致」。\n");

    printf("\n=== ④ 传统接口与粗糙时钟 ===\n");
    printf("  time(NULL)               = %ld  （秒级，最省）\n", (long)time(NULL));
    struct timeval tv;
    if (gettimeofday(&tv, NULL) == 0)
        printf("  gettimeofday(&tv)        = %ld.%06ld\n", (long)tv.tv_sec, (long)tv.tv_usec);
    struct timespec coarse;
    if (clock_gettime(CLOCK_REALTIME_COARSE, &coarse) == 0)
        printf("  CLOCK_REALTIME_COARSE    = %lld.%09ld  （走缓存，比精确的便宜得多）\n",
               (long long)coarse.tv_sec, coarse.tv_nsec);
    printf("  -> 只想知道「大概几点了」用 COARSE 或 time()；\n");
    printf("     要测间隔才需要精确的 MONOTONIC。\n");

    printf("\n=== ⑤ /proc 里能佐证的两个文件 ===\n");
    FILE *f = fopen("/proc/uptime", "r");
    if (f) {
        double up = 0, idle = 0;
        if (fscanf(f, "%lf %lf", &up, &idle) == 2) {
            printf("  /proc/uptime 第一列 = %.2f 秒（≈ CLOCK_BOOTTIME）\n", up);
            printf("  /proc/uptime 第二列 = %.2f 秒（所有 CPU 的累计 idle 时间）\n", idle);
        }
        fclose(f);
    }
    errno = 0;
    const char *tz = getenv("TZ");
    printf("  TZ 环境变量 = %s\n", tz ? tz : "(未设置 → 用系统默认，通常是 UTC)");
    printf("  localtime()/strftime()/时区/夏令时 → 见 TLPI Ch10，本节不展开。\n");
    return 0;
}
```

**解读**

1. **段 ① 的第一行和第二行是「不同源」的直接证据**：

   | clockid | now | 量级 |
   |---------|-----|------|
   | `CLOCK_REALTIME` | `1789358076.96` | **17.9 亿秒**（≈ 2026-09 的 epoch 秒数） |
   | `CLOCK_MONOTONIC` | `8019.14` | **8019 秒**（≈ 2 小时 13 分 ≈ 容器启动至今） |

   两者**不是「同一时刻的两种表示」**，而是两个独立计数器，起点不同。所以绝不能把 `REALTIME` 与 `MONOTONIC` 的读数相减当「开机时刻」用——段 ③ 的 `1789350057824821258 ns` 就是这个相减的结果，它**只是 epoch 到开机那一刻的常数**，没有信息量。

2. **段 ② 的三个数字是本节的实验核心**，必须看懂它们的**包含关系**：

   | 时钟 | 测得 | 含义 |
   |------|------|------|
   | `CLOCK_MONOTONIC` | `6889676 ns` | 墙钟：从循环开始到结束的**全部**墙上时间（含被抢占） |
   | `CLOCK_REALTIME` | `5901373 ns` | 同样是墙钟，但**这次循环恰好在 CPU 上有更多时间**（被抢占更少） |
   | 进程 CPU 时间 | `5827561 ns` | **只算真正占着 CPU** 的时间 |

   两个墙钟数**不相等**（6.89ms vs 5.90ms）——**同是墙钟，两次运行的结果也不该指望相等**，因为调度器抢占是随机的。而 CPU 时间（5.83ms）比这次的墙钟（5.90ms）略小，差额就是**这次运行里的极小抢占与系统调用开销**。

   **怎么读这组数据**：不要记具体数字（每次运行都不同），要记住**关系**——

   ```
   进程 CPU 时间  ≤  墙钟（MONOTONIC）
   且 墙钟 - CPU 时间  =  等待 / 被抢占 / 缺页 / 系统调用
   ```

   这正是 `time` 命令 `real` vs `user+sys` 的同一个道理。

3. **段 ③ 那句「差值本身没有意义」是防错的关键**。很多人第一次看到「REALTIME 与 MONOTONIC 的差」会以为它能算出「开机时间戳」——理论上可以（`epoch 秒数 - 开机至今秒数`），但**段 ③ 里两者各自走的量不同**：

   ```
   REALTIME  走了 20098749 ns
   MONOTONIC 走了 20099088 ns
   ```

   差了 339ns（≈ 0.0017%）。这说明两个计数器**前进速率不完全一致**（NTP slew 会让 `REALTIME` 走快/走慢一点点）。所以「用某个瞬时的差值当常量」是不严谨的——真正有意义的是**两个时钟各自前进多快**（即漂移率），那是 NTP/时钟同步的话题。

4. **段 ④ 的 `CLOCK_REALTIME_COARSE` 是「便宜的墙上时间」**：

   | 调用 | 值 | 代价 |
   |------|-----|------|
   | `time(NULL)` | `1789358076`（秒） | 最省，可能走 vDSO |
   | `gettimeofday()` | `1789358076.996418` | 微秒 |
   | `CLOCK_REALTIME_COARSE` | `1789358076.996093622` | **读缓存，比精确的便宜得多** |

   注意 `COARSE` 的值 `.996093622` 与 `gettimeofday` 的 `.996418` 有约 **324µs** 的差——**这就是「粗糙」的含义**：它返回的是「上一次时钟中断时更新的缓存值」，分辨率受 `CONFIG_HZ` 限制（通常 1–10ms），不是真的纳秒。**只关心「大概几点」时用它是极划算的**；测间隔绝不能用它。

5. **段 ⑤ 的 `/proc/uptime` 第一列 `8019.17` 与段 ① 的 `CLOCK_MONOTONIC = 8019.14` 对得上**（差 0.03 秒是两次读取的时间差）——这是「MONOTONIC ≈ 开机至今」的**外部佐证**。`/proc/uptime` 实际对应 `CLOCK_BOOTTIME`（含 suspend），在容器里没有 suspend 所以两者数值一致。

   **方法论**：当一个数值有疑问时，用 `/proc` 里的另一个来源交叉验证——这比反复读同一份文档可靠。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 延迟测量正确性 | 段 ② 实验：**必须用 `CLOCK_MONOTONIC` 测间隔**；用 `REALTIME` 一旦 NTP 回拨就出负延迟 |
| 高频时间戳零开销 | 要点四：`clock_gettime` 走 vDSO 用户态直读（`lib/vdso/gettimeofday.c:110`），**热路径每笔行情打时间戳不拖慢系统** |
| 订单时间戳审计 | 用 `CLOCK_REALTIME` 记「墙上几点」做对账（对接交易所时钟），**内部排序与超时一律用 MONOTONIC** |
| CPU 占用归因 | 段 ② 的三个数字：**墙钟 − CPU 时间 = 等待/抢占**。这个差额大，说明进程不是 CPU 瓶颈而是 I/O 或锁瓶颈 |
| 微秒级抖动测量 | 用 `CLOCK_MONOTONIC_RAW` 排除 NTP slew 的持续微调；只测普通耗时用 `MONOTONIC` 就够 |
| 日志时间戳的成本 | 若日志逐行调 `gettimeofday()`（非 vDSO 路径或跨 CPU），可能显著影响吞吐。**用 `CLOCK_REALTIME_COARSE` 或直接在共享内存里存 MONOTONIC 时间戳**更划算 |
| **`CLOCK_MONOTONIC` 不含 suspend** | 笔记本合盖、嵌入式设备进睡眠：`MONOTONIC` **不走**，「开机多久」要读 `CLOCK_BOOTTIME` 或 `/proc/uptime`。**用 `MONOTONIC` 算「设备运行时长」会少算睡眠时间** |
| 嵌入式 RTC 与时间跳变 | 无网络设备靠 RTC 芯片维持 `CLOCK_REALTIME`，启动时同步——**同步瞬间 `REALTIME` 可能大步跳变**。所以依赖墙上时间的定时逻辑（如「到点开闸」）必须用 MONOTONIC 或做跳变检测 |
| **容器里的容器时间 ≠ 宿主时间** | `CLOCK_REALTIME` 在容器里可能被 namespace 偏移（`time_for_children`），`/proc/uptime` 反映的是**宿主**的。跨容器做时间同步要先统一时间源 |

## 自测题

<details>
<summary>1. 日历时间和进程时间的区别是什么？</summary>

**日历时间**（wall clock）是「墙上的钟」——自 Epoch（1970-01-01 UTC）起的秒数，**可被 NTP / `settimeofday` 修改**（会跳变）。

**进程时间**（CPU time）是「进程消耗的 CPU 时间」——**不可回拨**，只增不减。

进程时间又分三段（要点一）：

| 时间 | 含义 |
|------|------|
| user time | 用户态执行消耗的 CPU |
| system time | 内核态（系统调用）消耗的 CPU |
| real time | 墙上实际流逝（= user + system + **等待/被抢占**） |

`time` 命令的 `real/user/sys` 就是这个区分。本节段 ② 实测把这个区别量化了：同一段循环，墙钟 `6889676 ns` vs 进程 CPU `5827561 ns`。
</details>

<details>
<summary>2. <code>CLOCK_REALTIME</code> 和 <code>CLOCK_MONOTONIC</code> 的区别是什么？为什么测间隔不能用 REALTIME？</summary>

| | `CLOCK_REALTIME` | `CLOCK_MONOTONIC` |
|---|---|---|
| 起点 | **Epoch（1970）** | 开机某点 |
| 可修改 | ✅ NTP 步进 / `settimeofday` | ⚠️ 只受 NTP **slew**（频率微调） |
| 会回拨 | ✅ **会** | ❌ **绝不** |

**测间隔不能用 REALTIME** 的原因很简单：NTP 步进（stepping）或管理员改时间会让它**回拨**，于是「结束时间 − 开始时间」算出**负数**。

```
CLOCK_REALTIME:      ├───────────┤  NTP 回拨 → 间隔为负 ❌
CLOCK_MONOTONIC:     ├───────────→  单调递增，间隔永远 ≥ 0 ✅
```

本节段 ① 的实测就是两者「不同源」的证据：`REALTIME = 1789358076.96`（17.9 亿秒）vs `MONOTONIC = 8019.14`（8019 秒）。

**规矩**：测延迟/间隔用 MONOTONIC；记「墙上几点」才用 REALTIME，**且绝不拿它算差值**。
</details>

<details>
<summary>3. <code>CLOCK_MONOTONIC</code>、<code>CLOCK_MONOTONIC_RAW</code>、<code>CLOCK_BOOTTIME</code> 三者有什么区别？</summary>

| clockid | NTP 影响 | 含 suspend | 用途 |
|---------|----------|-----------|------|
| `CLOCK_MONOTONIC` | ⚠️ 受 **slew**（频率微调，不回拨） | ❌ | **日常测间隔**（默认选择） |
| `CLOCK_MONOTONIC_RAW` | ❌ **完全不受** | ❌ | **纳秒级抖动测量**（连 slew 都不要） |
| `CLOCK_BOOTTIME` | ⚠️ 同 MONOTONIC | ✅ **含** | 「设备开机多久」（`/proc/uptime` 就是它） |

**slew 是什么**：NTP 发现本地晶振快了/慢了，不直接跳时间，而是让时钟**走快/走慢一点点**来追平——所以 `MONOTONIC` 的秒长并不严格等于 1 秒。`MONOTONIC_RAW` 绕过这一切，直接读硬件计数器。

**实践**：普通耗时测量用 `MONOTONIC`；做**抖动/延迟分布**分析（HFT 场景）用 `MONOTONIC_RAW` 更纯粹；判断「设备运行了多久」用 `BOOTTIME`（否则睡眠时间会被漏算）。

⚠️ 段 ③ 实测两者在 20ms 内前进量差 `339 ns`——这就是 slew 造成的漂移率差异。
</details>

<details>
<summary>4. 为什么 <code>clock_gettime</code> 能快到「不陷入内核」？</summary>

因为 **vDSO**（virtual dynamic shared object）机制：

1. **映射**：内核把一段代码 + 数据（`vdso_data`）映射进**每个进程的用户态地址空间**（`/proc/self/maps` 里能看到 `[vdso]` 段）；
2. **分派**：glibc 的 `clock_gettime` / `gettimeofday` / `time` **优先走 vDSO 快速路径**（`lib/vdso/gettimeofday.c:110` 的 `do_hres`），成功就直接在用户态算出时间返回；
3. **回退**：只有 vDSO 处理不了的情况才真正发系统调用 **228**（`syscall_64.tbl:239`）陷入内核。

**对 HFT 的意义**：完整系统调用要几百纳秒，走 vDSO 只要**几十纳秒**（纯用户态内存读 + 乘法）。热路径里每笔行情都打时间戳，这个差别直接决定系统能不能扛住高频。

⚠️ 一个已知的坑：**跨 CPU 迁移后 vDSO 数据可能略旧**——所以有的超低延迟系统会**把进程钉核**（见 [2.18](./2.18-realtime.md) 的 CPU 亲和）后再计时。
</details>

<details>
<summary>5. <code>time</code> 命令输出的 <code>real/user/sys</code> 三列是什么？为什么 <code>real</code> 可能远大于 <code>user+sys</code>？</summary>

| 列 | 含义 |
|----|------|
| `real` | 墙上实际流逝时间（`CLOCK_MONOTONIC` 的差值） |
| `user` | 用户态 CPU 时间 |
| `sys` | 内核态 CPU 时间（系统调用） |

**`real > user+sys` 是常态**，因为进程在**等 I/O、被调度器抢占、睡眠**时，CPU 时间不增加但墙上时间在走。

| 情形 | 特征 |
|------|------|
| `real` 远大于 `user+sys` | **I/O 密集**（大量等待）或严重被抢占 |
| `real` ≈ `user+sys` | **CPU 密集**（时间都花在计算上） |

本节段 ② 的三个数字是同一个道理在**单段代码**尺度上的体现：

```text
第 1 遍  MONOTONIC 测得        = 6889676 ns     ← 墙钟（含被抢占）
第 2 遍  进程 CPU 时间测得     = 5827561 ns     ← 只算占着 CPU 的时间
```

差额 ≈ 1.06ms 就是两次测量之间的「等待 / 抢占 / 系统调用」开销。**这个差额大说明瓶颈不在 CPU**——这是性能分析里第一个要看的信号。
</details>

<details>
<summary>6. <code>CLOCK_REALTIME_COARSE</code> 和 <code>CLOCK_REALTIME</code> 差在哪？什么时候该用粗糙的？</summary>

`CLOCK_REALTIME_COARSE` 返回的是**上一次时钟中断时更新的缓存值**，不是实时读硬件。所以：

| | `CLOCK_REALTIME` | `CLOCK_REALTIME_COARSE` |
|---|---|---|
| 精度 | **纳秒级**（真读硬件） | 受 `CONFIG_HZ` 限制（通常 1–10 ms） |
| 代价 | 高（可能走 vDSO 但仍要算） | **极低**（读一个缓存变量） |

段 ④ 实测的差距就是证据：

```text
  gettimeofday(&tv)        = 1789358076.996418
  CLOCK_REALTIME_COARSE    = 1789358076.996093622   ← 与上面 gettimeofday 相差约 324 µs
```

**什么时候用 COARSE**：

- 只想知道「大概几点了」——**日志时间戳、审计记录、超时上限粗判**；
- 高频调用、又不需要精确（**每秒几十万次的计时打点**）。

**什么时候不能用**：测间隔、算延迟、做顺序判定——这些**必须** `MONOTONIC`。

⚠️ 段 ④ 的最后一行也是本节的取舍总结：**「只想知道大概几点了用 COARSE 或 `time()`；要测间隔才需要精确的 MONOTONIC」**。
</details>

<details>
<summary>7. 嵌入式设备进睡眠（suspend）后，用 <code>CLOCK_MONOTONIC</code> 测「运行时长」会怎样？</summary>

**会少算睡眠时间。**

`CLOCK_MONOTONIC` 的定义就是**不含 suspend 时间**——笔记本合盖 1 小时，MONOTONIC 只走了几分钟。要含睡眠时间必须用 **`CLOCK_BOOTTIME`**（要点二的表：「单调 + 含 suspend 时间」）。

段 ① 的实测可以验证：容器没有 suspend，所以

```text
  CLOCK_MONOTONIC          8019.138674358
  CLOCK_BOOTTIME           8019.138676125     ← 几乎相同（因为无 suspend）
```

两者只差 **1.7 µs**（读取时间差）。**在真的会睡眠的设备上，这两个数字会差出整个睡眠时长**。

段 ⑤ 的 `/proc/uptime` 第一列（`8019.17` 秒）实际反映的就是 `BOOTTIME`。

**嵌入式正确做法**：

| 想算 | 用 |
|------|-----|
| 代码耗时 / 超时 | `CLOCK_MONOTONIC` |
| 设备运行时长（含睡眠） | `CLOCK_BOOTTIME` 或 `/proc/uptime` |
| 「到点开闸」这类绝对时刻 | `CLOCK_REALTIME` + **跳变检测**（因为它会在 RTC 同步时大步跳） |
</details>
