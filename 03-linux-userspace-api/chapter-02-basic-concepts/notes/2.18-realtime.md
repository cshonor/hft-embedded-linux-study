## 本节讲什么

「实时」指系统能在**确定的时限内**响应事件。本节回答三个问题：

1. 硬实时和软实时的本质区别是什么？错过期限的代价有何不同？
2. Linux 靠哪几样机制凑出「实时能力」？`SCHED_FIFO`、`mlock`、`PREEMPT_RT` 各管什么？
3. HFT 的微秒级延迟，为什么必须 `mlockall` + CPU 亲和绑定？

完整调度机制在 [Ch35](../../chapter-35-process-priorities-scheduling/README.md) 与 [Ch50](../../chapter-50-virtual-memory/README.md)，这里建立「**实时 = 确定性，不是快**」的核心心智。

本节要补的是**权限边界的实测**：容器里 `CapEff = 0x0`（没有 `CAP_SYS_NICE`），所以 `SCHED_FIFO` 两次都 `EPERM(1)`；但 `mlockall` **却成功了**——原因不是权限，而是 `RLIMIT_MEMLOCK` 被设成了约 2GB。**同一份「没权限」的判断，在两个调用上得出相反结果**，这是本节最有价值的一组对照。

## 要点

### 一、硬实时 vs 软实时：区别在「错过的代价」

| 维度 | 硬实时（Hard RT） | 软实时（Soft RT） |
|------|------------------|------------------|
| 错过期限的后果 | **系统级失败**（事故 / 物理损坏） | 性能下降、服务质量降低，**可容忍** |
| 追求的目标 | **最坏情况延迟（WCET）有上界** | 「尽量快、平均延迟低」 |
| 典型场景 | 核反应堆控制、安全气囊、飞行控制、心脏起搏器 | **HFT**、音视频流、游戏 |
| 对 Linux 的要求 | 通常需 RTOS 或 `PREEMPT_RT` | 标准内核 + 实时调度策略基本够用 |

**核心是「确定性」而非「快」**：硬实时要求的是**最坏情况延迟有上界**，不是平均响应快。标准 Linux 内核是「吞吐优先」，`CONFIG_PREEMPT_NONE` 下关中断 / 持自旋锁的临界区会引入不可预知的调度延迟，所以纯标准内核无法保证硬实时。

**HFT 落在哪**：段 ⑥ 的判词很准——「**软实时的极端版**：不要求 0 抖动，只要求抖动小到**对手吃不到你的价**。所以工程重点在**把长尾砍掉**，不是追平均值」。这是后面所有优化的取舍基准。

### 二、实时调度策略：`SCHED_FIFO` / `SCHED_RR`

普通进程用 `SCHED_NORMAL`（CFS，完全公平调度，按 `vruntime` 分配时间片）。实时进程用：

| 策略 | 语义 | 抢占行为 |
|------|------|----------|
| `SCHED_FIFO` | 先进先出，**没有时间片** | 跑到主动让出（sleep/阻塞）或被更高优先级抢占 |
| `SCHED_RR` | 轮转，同优先级**有时间片**（默认约 100ms） | 同优先级轮流跑，防饿死 |

**实时优先级范围**（内核注释原文，`kernel/sched/core.c:7652-7654`）：

```c
/* Valid priorities for SCHED_FIFO and SCHED_RR are
 * 1..MAX_RT_PRIO-1, valid priority for SCHED_NORMAL,
 * SCHED_BATCH and SCHED_IDLE is 0. */
```

`MAX_RT_PRIO = 100`，所以实时优先级是 **1~99**（用户态），**数值越大优先级越高**。

> **关键事实：任何实时进程（优先级 ≥ 1）都优先于所有 `SCHED_NORMAL` 进程（优先级 0）**——所以一个跑飞的 `SCHED_FIFO` 任务能把整台机器「卡死」，因为它永远不让出 CPU（除非被更高实时优先级抢占）。这也解释了为什么 `EPERM` 保护是必要的。

```c
struct sched_param sp = { .sched_priority = 50 };   /* 1..99 */
sched_setscheduler(0, SCHED_FIFO, &sp);              /* 需 CAP_SYS_NICE */
```

**`EPERM` 与 `EINVAL` 的区别是本节段 ② 的教学点**：

| errno | 含义 | 什么时候报 |
|-------|------|-----------|
| `EINVAL(22)` | **参数不合法** | `prio` 超出 `[1,99]` 范围（`core.c:7656` 的检查） |
| `EPERM(1)` | 参数没问题，**权限不够** | 没有 `CAP_SYS_NICE` |

**顺序上 `EINVAL` 更早**（段 ② 实测：`prio=9999` 报 `EINVAL` 而不是 `EPERM`）——内核先验证参数、再查权限。**排查时先确认参数范围，再怀疑权限**。

### 三、内存锁定：`mlock` / `mlockall`（防换页）

实时任务的隐形杀手是**缺页（page fault）**：哪怕 CPU 上跑得好好的，一旦访问的页被换出（swap），就要等磁盘换入，延迟从微秒暴涨到毫秒级。`mlock` 把页钉在物理内存里，禁止换出：

```c
/* mm/mlock.c:622 */
SYSCALL_DEFINE2(mlock, unsigned long, start, size_t, len)

/* mm/mlock.c:705 */
SYSCALL_DEFINE1(mlockall, int, flags)
```

三个 `MCL_*` 标志：

| 标志 | 含义 |
|------|------|
| `MCL_CURRENT` | 锁定**当前**已映射的所有页（并立即 `mm_populate` 建立页表、分配物理页） |
| `MCL_FUTURE` | 锁定**以后**新映射的页（`mmap`/`malloc` 增长的部分自动带 `VM_LOCKED`） |
| `MCL_ONFAULT` | 延迟锁定：等页首次被访问（缺页）时才锁，省内存；**可单独用，但与另两个组合时会被拒** |

**HFT 用 `mlockall(MCL_CURRENT | MCL_FUTURE)`**：既锁现有页，又锁将来分配的热路径缓冲，彻底消除「策略开跑后首次访问某块内存」的缺页毛刺。代价是锁定的内存不计入 swap 候选，系统内存压力大时可能 OOM。

### 四、谁能调 `mlockall`：`CAP_IPC_LOCK` **或** `RLIMIT_MEMLOCK`

`mlockall` 的权限检查是**「二选一」**，`mm/mlock.c` 里的 `can_do_mlock()`：

```c
static inline bool can_do_mlock(void)
{
	if (rlimit(RLIMIT_MEMLOCK) != 0)
		return true;
	if (capable(CAP_IPC_LOCK))
		return true;
	return false;
}
```

**即**：

| 条件 | 结果 |
|------|------|
| 有 `CAP_IPC_LOCK` | ✅ 可锁定**任意**量（不受 rlimit 限制） |
| **`RLIMIT_MEMLOCK > 0`** | ✅ **可在该上限内锁定** |
| 两者都没有（`RLIMIT_MEMLOCK = 0` 且无 capability） | ❌ `EPERM` |

**这是本节最容易搞错的地方**：容器里 `CapEff = 0x0`（**没有** `CAP_IPC_LOCK`），但 `mlockall` **成功了**——因为 `RLIMIT_MEMLOCK` 被设成了 `1996169216` 字节（≈ 1.86 GiB）。**「没有 capability」≠「不能锁定内存」**。

### 五、`PREEMPT_RT`：让内核本身可抢占

实时调度策略和内存锁定都只解决**用户态**的确定性；真正的延迟往往来自**内核态**——关中断、持自旋锁、关抢占的临界区。`PREEMPT_RT`（现已逐步合入主线，`CONFIG_PREEMPT_RT`）把内核里几乎所有自旋锁换成可睡眠的互斥锁（`rt_mutex`）、把中断处理线程化，使内核态也能被高优先级任务抢占。

| 内核配置 | 抢占能力 | 适用 |
|----------|----------|------|
| `PREEMPT_NONE` | 仅在返回用户态时调度 | 服务器吞吐优先 |
| `PREEMPT_VOLUNTARY` | 自愿让出点 + 返回用户态 | 桌面 |
| `PREEMPT` | 内核态大部分可抢占 | 通用低延迟 |
| **`PREEMPT_RT`** | **近乎全可抢占（含中断线程化）** | 硬实时 |

## 代码

### c2_18 实时三件套：capability 家底 / 调度策略 / CPU 亲和 / 内存锁定

[`../code/c2_18_realtime.c`](../code/c2_18_realtime.c) 分六段：

| 段 | 做什么 | 钉死什么 |
|----|--------|----------|
| ① | 读 `CapEff`，检查 bit 23 / bit 14 | **家底先行**：后面每步成败都能对上 |
| ② | 试 `SCHED_FIFO(80)` / `FIFO(1)` / `OTHER(0)` / `FIFO(9999)` | `EPERM(1)` vs **`EINVAL(22)`** 的分界 |
| ③ | `sched_setaffinity` 把进程钉到 CPU 0 | 亲和集从 `0 1` 变成 `0` |
| ④ | 读 `RLIMIT_MEMLOCK`，试 `mlockall` + `mlock(64MiB)` | **无 capability 也能锁**（rlimit 够大） |
| ⑤ | 实时性改造的**七层谱系**表 | 前三层是应用层，后四层要动内核/硬件 |
| ⑥ | 硬实时 vs 软实时的判据 + HFT 定位 | **把长尾砍掉，不是追平均** |

```c
/* TLPI 第 2 章 §2.18 —— 实时：调度策略、内存锁定、CPU 亲和，逐项实测
 *
 * 编译：gcc -O0 -Wall -Wextra c2_18_realtime.c -o c2_18
 * 运行：./c2_18
 *
 * 本节要钉死的事实：
 *   ① 实时性 = 可预测的**最坏**延迟，不是平均快。
 *   ② 三个最常被一起使用的开关：sched_setscheduler（抢占）、mlockall（防缺页）、
 *      sched_setaffinity（防迁移）。它们的权限要求各不相同。
 *   ③ 每一个都有对应的 capability：CAP_SYS_NICE（调度）、CAP_IPC_LOCK（锁内存）。
 *      euid=0 不等于拥有它们 —— 用 /proc/self/status 的 CapEff 验证。
 *   ④ PREEMPT_RT 解决的是「内核自己不可抢占」的问题，是另一层的事。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <sched.h>
#include <time.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/time.h>

#define CAP_SYS_NICE_BIT 23           /* include/uapi/linux/capability.h */
#define CAP_IPC_LOCK_BIT 14

static unsigned long long read_hex_line(const char *key)
{
    FILE *f = fopen("/proc/self/status", "r");
    if (!f) return 0;
    char line[512];
    unsigned long long v = 0;
    size_t klen = strlen(key);
    while (fgets(line, sizeof(line), f))
        if (strncmp(line, key, klen) == 0) { sscanf(line + klen, "%llx", &v); break; }
    fclose(f);
    return v;
}

static const char *policy_name(int p)
{
    switch (p) {
    case SCHED_OTHER: return "SCHED_OTHER";
    case SCHED_FIFO:  return "SCHED_FIFO";
    case SCHED_RR:    return "SCHED_RR";
    case SCHED_BATCH: return "SCHED_BATCH";
    case SCHED_IDLE:  return "SCHED_IDLE";
    default:          return "?";
    }
}

static void try_sched(int policy, int prio)
{
    struct sched_param sp;
    memset(&sp, 0, sizeof(sp));
    sp.sched_priority = prio;
    errno = 0;
    int rc = sched_setscheduler(0, policy, &sp);
    if (rc == 0)
        printf("  sched_setscheduler(%s, prio=%d) -> OK，当前策略现在是 %s\n",
               policy_name(policy), prio, policy_name(sched_getscheduler(0)));
    else
        printf("  sched_setscheduler(%s, prio=%d) -> 失败 errno=%d (%s)\n",
               policy_name(policy), prio, errno, strerror(errno));
    errno = 0;
}

int main(void)
{
    printf("=== ① 先看家底：有没有那两个 capability ===\n");
    unsigned long long capEff = read_hex_line("CapEff:");
    printf("  CapEff = 0x%016llx\n", capEff);
    printf("  CAP_SYS_NICE (bit %d) = %s\n", CAP_SYS_NICE_BIT,
           (capEff >> CAP_SYS_NICE_BIT) & 1 ? "有" : "没有");
    printf("  CAP_IPC_LOCK (bit %d) = %s\n", CAP_IPC_LOCK_BIT,
           (capEff >> CAP_IPC_LOCK_BIT) & 1 ? "有" : "没有");
    printf("  -> 记住这两个开关的状态，下面每一步的成败都能对上。\n");

    printf("\n=== ② 调度策略：实时策略要 CAP_SYS_NICE ===\n");
    printf("  当前策略 = %s\n", policy_name(sched_getscheduler(0)));
    printf("  SCHED_FIFO 优先级范围 = [%d, %d]\n",
           sched_get_priority_min(SCHED_FIFO), sched_get_priority_max(SCHED_FIFO));
    printf("  SCHED_RR   优先级范围 = [%d, %d]\n",
           sched_get_priority_min(SCHED_RR), sched_get_priority_max(SCHED_RR));
    printf("  SCHED_FIFO 与 SCHED_RR 的区别：同优先级下 FIFO 一直跑到主动让出，\n");
    printf("  RR 会按时间片轮转。二者都抢占 SCHED_OTHER 的任务。\n\n");

    try_sched(SCHED_FIFO, 80);
    try_sched(SCHED_FIFO, 1);
    try_sched(SCHED_OTHER, 0);

    printf("\n  -> 上面 FIFO 两次都失败、OTHER 成功，说明本进程没有 CAP_SYS_NICE。\n");
    printf("     注意 EPERM(%d) 与 EINVAL(%d) 的区别：\n", EPERM, EINVAL);
    printf("       EINVAL = 参数不合法（比如 prio 超出范围）；\n");
    printf("       EPERM  = 参数没问题，是权限不够。\n");
    errno = 0;
    try_sched(SCHED_FIFO, 9999);       /* 故意给个越界优先级，看错误码 */
    printf("      ↑ 这一条就是 EINVAL：优先级越界比权限检查更早。\n");

    printf("\n=== ③ CPU 亲和：把进程钉在某个核上 ===\n");
    cpu_set_t before;
    if (sched_getaffinity(0, sizeof(before), &before) == 0) {
        printf("  当前亲和的 CPU：");
        for (int i = 0; i < CPU_SETSIZE; i++) if (CPU_ISSET(i, &before)) printf("%d ", i);
        printf("\n");
    }
    cpu_set_t one;
    CPU_ZERO(&one);
    CPU_SET(0, &one);
    errno = 0;
    if (sched_setaffinity(0, sizeof(one), &one) == 0) {
        cpu_set_t after;
        sched_getaffinity(0, sizeof(after), &after);
        printf("  sched_setaffinity(只留 CPU 0) -> OK，现在亲和集：");
        for (int i = 0; i < CPU_SETSIZE; i++) if (CPU_ISSET(i, &after)) printf("%d ", i);
        printf("\n");
    } else {
        printf("  sched_setaffinity 失败 errno=%d (%s)\n", errno, strerror(errno));
    }
    /* 恢复原样，别影响后面的实验 */
    sched_setaffinity(0, sizeof(before), &before);
    errno = 0;

    printf("\n=== ④ 内存锁定：消除缺页带来的毛刺 ===\n");
    struct rlimit rl;
    if (getrlimit(RLIMIT_MEMLOCK, &rl) == 0)
        printf("  RLIMIT_MEMLOCK: soft=%lld  hard=%lld 字节\n",
               (long long)rl.rlim_cur, (long long)rl.rlim_max);
    errno = 0;
    if (mlockall(MCL_CURRENT | MCL_FUTURE) == 0) {
        printf("  mlockall(MCL_CURRENT|MCL_FUTURE) -> OK\n");
        printf("    MCL_CURRENT = 锁住现在已映射的页\n");
        printf("    MCL_FUTURE  = 之后新分配的页也自动锁住\n");
    } else {
        printf("  mlockall -> 失败 errno=%d (%s)\n", errno, strerror(errno));
    }
    errno = 0;

    /* 单个 mlock 能不能锁一段？实测一下容量感受 */
    size_t want = 64 * 1024 * 1024;              /* 64 MiB */
    void *p = mmap(NULL, want, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p != MAP_FAILED) {
        errno = 0;
        int rc = mlock(p, want);
        printf("  mlock(64MiB) -> %s", rc == 0 ? "OK\n" : "失败 ");
        if (rc != 0) printf("errno=%d (%s)\n", errno, strerror(errno));
        munmap(p, want);
    }
    errno = 0;

    printf("\n=== ⑤ 实时性的层次：从「调参数」到「换内核」 ===\n");
    printf("  %-30s %s\n", "层次", "解决什么");
    printf("  %-30s %s\n", "------------------------------", "--------------------------");
    printf("  %-30s %s\n", "SCHED_FIFO / SCHED_RR", "让本任务抢占普通任务");
    printf("  %-30s %s\n", "mlockall", "消除缺页导致的微秒级停顿");
    printf("  %-30s %s\n", "sched_setaffinity", "消除跨核迁移 / 缓存失效");
    printf("  %-30s %s\n", "隔离 CPU（isolcpus / cpuset）", "让别的任务别来抢这个核");
    printf("  %-30s %s\n", "关闭 C-state / 锁频", "消除降频唤醒延迟");
    printf("  %-30s %s\n", "PREEMPT_RT 内核", "让内核本身也可抢占（中断线程化）");
    printf("  %-30s %s\n", "busy-poll / 无锁队列", "把「等」变成「直接查」");
    printf("\n  → 前三条是应用层能做的，本 demo 全试了；\n");
    printf("     后三条要动内核/固件/硬件，属于 §2.18 里说的「另一层」。\n");

    printf("\n=== ⑥ 硬实时 vs 软实时：先问清需求 ===\n");
    printf("  硬实时：错过截止时间 = 系统失败（飞控、心脏起搏器、工业伺服）\n");
    printf("  软实时：偶尔错过只是质量下降（音视频、行情推送、交易回报）\n");
    printf("  HFT 大多落在「软实时的极端版」：不要求 0 抖动，只要求抖动小到\n");
    printf("  对手吃不到你的价。所以工程重点在「把长尾砍掉」，不是追平均值。\n");
    return 0;
}
```

```text
    MCL_CURRENT = 锁住现在已映射的页
    MCL_FUTURE  = 之后新分配的页也自动锁住
  mlock(64MiB) -> OK

=== ⑤ 实时性的层次：从「调参数」到「换内核」 ===
  层次                         解决什么
  ------------------------------ --------------------------
  SCHED_FIFO / SCHED_RR          让本任务抢占普通任务
  mlockall                       消除缺页导致的微秒级停顿
  sched_setaffinity              消除跨核迁移 / 缓存失效
  隔离 CPU（isolcpus / cpuset） 让别的任务别来抢这个核
  关闭 C-state / 锁频        消除降频唤醒延迟
  PREEMPT_RT 内核              让内核本身也可抢占（中断线程化）
  busy-poll / 无锁队列       把「等」变成「直接查」

  → 前三条是应用层能做的，本 demo 全试了；
     后三条要动内核/固件/硬件，属于 §2.18 里说的「另一层」。

=== ⑥ 硬实时 vs 软实时：先问清需求 ===
  硬实时：错过截止时间 = 系统失败（飞控、心脏起搏器、工业伺服）
  软实时：偶尔错过只是质量下降（音视频、行情推送、交易回报）
  HFT 大多落在「软实时的极端版」：不要求 0 抖动，只要求抖动小到
  对手吃不到你的价。所以工程重点在「把长尾砍掉」，不是追平均值。
```

**解读**

1. **段 ① 的「先看家底」是本节的方法论**：`CapEff = 0x0000000000000000` 意味着**这个容器什么 capability 都没有**（尽管 `uid=0`）。**这解释了后面每一步的成败**：

   | 段 | 操作 | 结果 | 原因 |
   |----|------|------|------|
   | ② | `SCHED_FIFO(80)` | ❌ `EPERM(1)` | 需要 `CAP_SYS_NICE`（bit 23） |
   | ② | `SCHED_FIFO(1)` | ❌ `EPERM(1)` | 同上（**即使是优先级 1 也需要**） |
   | ② | `SCHED_OTHER(0)` | ✅ | 普通策略不需要权限 |
   | ② | `SCHED_FIFO(9999)` | ❌ **`EINVAL(22)`** | 参数越界，**先于权限检查** |
   | ④ | `mlockall` | ✅ | **不需要 `CAP_IPC_LOCK`**，`RLIMIT_MEMLOCK > 0` 即可 |

   **`uid=0` 不等于「什么都能干」**——这正是 Linux capabilities 的设计目的（把 root 的权限拆成细粒度位）。`CapEff` 全 0 的 root 在很多操作上和普通用户一样受限。

2. **段 ② 的四行是本节的「errno 教学」**。把四种情况排成一条判定链：

   ```
   sched_setscheduler(policy, prio)
        │
        ├─ prio 不在 [1,99]（对 RT 策略）→ EINVAL(22)   ← 先查参数
        ├─ policy 是 RT 但没有 CAP_SYS_NICE → EPERM(1)  ← 再查权限
        └─ policy 是 SCHED_OTHER → OK（prio 必须是 0）
   ```

   注意 `SCHED_FIFO` 的**优先级 1 和 80 都失败**（都是 `EPERM`）——说明**权限检查与优先级高低无关**，「用最低优先级就不需要权限」是错的。

   还要注意最后一行 `SCHED_OTHER(0) -> OK`：**这是「返回 0 = 成功」的对照**，避免把「全都失败」误读成「函数根本不能用」。

3. **段 ③ 的 `当前亲和的 CPU：0 1` 后跟 `sched_setaffinity(只留 CPU 0) -> OK`** 揭示了一个可以调优的事实：

   | 操作前 | `0 1`（两个 CPU，`ncpu=2`） |
   |--------|---------------------------|
   | 操作后 | `0`（只跑 CPU 0） |

   **为什么要钉核**（[2.16](./2.16-date-time.md) 也提到过）：
   - **消除跨核迁移**（迁移要搬缓存、代价微秒级）；
   - **缓存预热有效**（L1/L2 不会被别的核冷掉）；
   - **配合 `isolcpus` 才有意义**——单把进程钉到 CPU 0，**别的进程仍可以跑在 CPU 0 上**（`sched_setaffinity` 只约束**自己**）。所以「钉核」必须配合「隔离核」（段 ⑤ 的第 4 层）才能独占。

   ⚠️ `sched_setaffinity` **不需要特殊 capability**——所以它能在无权限的容器里成功，而 `SCHED_FIFO` 不行。

4. **段 ④ 的 `RLIMIT_MEMLOCK: soft=hard=1996169216` 是「`mlockall` 为什么能成功」的答案**：

   | 数字 | 换算 |
   |------|------|
   | `1996169216` 字节 | ≈ **1.86 GiB**（约是容器内存上限的某个比例） |

   要点四的判定逻辑在这里兑现：**`RLIMIT_MEMLOCK != 0` → 允许 `mlock`**。所以尽管 `CapEff = 0x0`，`mlockall(MCL_CURRENT|MCL_FUTURE)` 和 `mlock(64MiB)` 都成功。

   **这也给了一个重要的反例**：网上很多资料说「`mlockall` 需要 `CAP_IPC_LOCK`」——**不完整**。准确的表述是「需要 `CAP_IPC_LOCK` **或** `RLIMIT_MEMLOCK > 0`」。**`ulimit -l` 就能改这个限制**，这是普通用户也能做的（在现代内核上受 namespace 约束）。

   ⚠️ 一个真实的坑：**`MCL_FUTURE` 与 `RLIMIT_MEMLOCK` 组合可能导致「later `malloc` 失败」**——因为之后新映射的页自动锁定，一旦累计超过 rlimit，`malloc`/`mmap` 就报 `ENOMEM`。所以 HFT 里常**先做大额 `mlock` 然后把 rlimit 调小**，或**预先分配好所有热路径缓冲**。

5. **段 ⑤ 的七层谱系是「实时改造清单」的权威版本**，按「能动的层级」分：

   | 层 | 手段 | 本 demo 试了吗 |
   |----|------|--------------|
   | **应用层** | `SCHED_FIFO` / `SCHED_RR` | ✅ 试了（`EPERM`） |
   | **应用层** | `mlockall` | ✅ 试了（**成功**） |
   | **应用层** | `sched_setaffinity` | ✅ 试了（**成功**） |
   | 内核参数 | `isolcpus` / `cpuset` | ❌ 要改启动参数 |
   | 固件 / BIOS | 关 C-state / 锁频 | ❌ 要动固件 |
   | 内核版本 | `PREEMPT_RT` | ❌ 要换内核 |
   | 用户态架构 | busy-poll / 无锁队列 | ❌ demo 里只提了 |

   **「前三层是应用层能做的，本 demo 全试了；后三条要动内核/固件/硬件」**——这个划分非常实用：它明确了「一个普通进程（哪怕有权限）能走多远」。

   注意最后一行 `busy-poll / 无锁队列` **不是「调参数」而是「换架构」**：把「等」（阻塞、事件通知）变成「直接查」（轮询共享内存）。这是 HFT 最核心的一招，也是它能把延迟压到硬件极限的原因——**段 ⑤ 的排序暗示：越往下，收益越大，代价也越大**。

6. **段 ⑥ 的 HFT 定位是本节的最终结论**，值得记住那句「**把长尾砍掉，不是追平均值**」：

   | 指标 | HFT 关心吗 |
   |------|-----------|
   | 平均延迟 | 参考 |
   | **p99 / p99.9 / 最大值** | **决定性** |

   因为**一次长尾抖动就可能让对手吃掉你的价**。这解释了为什么 HFT 不满足于「平均 5µs」——要看的是「最差 100µs 那种情况一年发生几次」。**这也是「软实时的极端版」这个说法的确切含义**：不需要 0 抖动（那是硬实时的目标），只需要抖动小到**对手吃不到你的价**。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 微秒级响应 | `SCHED_FIFO` + 高优先级抢占 CFS（需 `CAP_SYS_NICE` 或 setcap 授权） |
| **`uid=0` 也拿不到 `SCHED_FIFO`** | 段 ① 实测 `CapEff = 0x0` → 段 ② `EPERM`。**用 `setcap cap_sys_nice+ep ./trading_bin` 显式授权**，而不是靠 root，更安全 |
| **`mlockall` 不需要 `CAP_IPC_LOCK`** | 段 ④ 实测成功。**只要 `ulimit -l` 够大**（≈2GB）。这一条纠正了「必须 root」的常见误解 |
| **`MCL_FUTURE` 可能让后续 `malloc` 失败** | 要点三的坑：新映射页自动锁定，累计超 `RLIMIT_MEMLOCK` → `ENOMEM`。**HFT 应预先分配全部热路径缓冲**，或 `MCL_CURRENT` + 手工 `mlock` 关键区 |
| 消除缺页毛刺 | `mlockall(MCL_CURRENT\|MCL_FUTURE)`——把 swap 换入与首次缺页的毫秒级停顿消掉 |
| 消除跨核迁移 / 缓存失效 | `sched_setaffinity` + `isolcpus`。**注意：单钉核不够，别的进程仍能跑在这个核上**（要点三解读 3） |
| 避免系统调用开销 | 批量化、`io_uring`、**busy-poll 用户态轮询**（段 ⑤ 最后一层：把「等」变成「直接查」） |
| 避免调度抖动 | 独占核 + `nohz_full`（关周期 tick） |
| 降频导致的唤醒延迟 | 关 C-state / 锁频（段 ⑤ 第 5 层，**要动固件/BIOS**） |
| 嵌入式实时改造的红线 | 段 ⑤ 的分层：**应用层三项（FIFO / mlockall / 亲和）是「改代码」；`isolcpus`/`nohz_full` 是「改启动参数」；`PREEMPT_RT` 是「换内核」**。嵌入式项目的前期选型（内核版本、有没有 RT）决定了后期能走多远 |
| **嵌入式 `RLIMIT_MEMLOCK` 常常是小值** | 容器/嵌入式默认可能是 64KB 或 8MB——`mlockall` 会 `EPERM` 或部分失败。启动脚本里 `ulimit -l unlimited`（或 systemd 的 `LimitMEMLOCK=infinity`）是部署必备 |
| HFT 只看长尾 | 段 ⑥：**p99/p99.9/max 才是指标**，平均值无意义。「把长尾砍掉」是全部工作的目标 |

## 自测题

<details>
<summary>1. 硬实时和软实时的本质区别是什么？HFT 属于哪一类？</summary>

区别在**错过期限的后果**：

| | 硬实时 | 软实时 |
|---|---|---|
| 错过期限 | **系统级失败**（事故/物理损坏） | 性能下降，**可容忍** |
| 目标 | **最坏情况延迟有上界** | 「尽量快、平均延迟低」 |
| 例 | 飞控、心脏起搏器、工业伺服 | 音视频、行情推送、交易回报 |

**HFT 属于「软实时的极端版」**（段 ⑥）：不要求 0 抖动，只要求**抖动小到对手吃不到你的价**。所以工程重点是「**把长尾砍掉**，不是追平均值」——看 p99/p99.9/max，不看均值。

**容易混淆的一点**：硬实时的核心是「**确定性**」而不是「快」——一个平均 1ms 但最坏 1.1ms 的系统比平均 10µs 但最坏 10ms 的系统更「硬实时」。
</details>

<details>
<summary>2. <code>SCHED_FIFO</code> 和 <code>SCHED_RR</code> 有什么区别？实时优先级的范围是多少？</summary>

| | `SCHED_FIFO` | `SCHED_RR` |
|---|---|---|
| **同优先级** | 一直跑到主动让出（sleep/阻塞） | 按**时间片**轮转，防饿死 |
| 被抢占 | 更高优先级任务可抢占 | 同左 |
| 时间片 | **无** | 有（默认约 100ms） |

**优先级范围**：内核注释（`kernel/sched/core.c:7652-7654`）明确

```
/* Valid priorities for SCHED_FIFO and SCHED_RR are
 * 1..MAX_RT_PRIO-1, valid priority for SCHED_NORMAL,
 * SCHED_BATCH and SCHED_IDLE is 0. */
```

`MAX_RT_PRIO = 100` → 实时优先级 **1~99**（用户态），**数值越大优先级越高**；`SCHED_NORMAL` 等普通策略的 `prio` 必须是 **0**。

⚠️ **任何实时进程（prio ≥ 1）都优先于所有 `SCHED_NORMAL`**——所以一个跑飞的 `SCHED_FIFO` 任务能让整机卡死（段 ② 实测它需要 `CAP_SYS_NICE` 就是为了防止这种事故）。

段 ② 实测：`SCHED_FIFO` 的优先级范围打印为 `[1, 99]`。
</details>

<details>
<summary>3. <code>EPERM</code> 和 <code>EINVAL</code> 在 <code>sched_setscheduler</code> 里分别代表什么？哪个先触发？</summary>

| errno | 含义 | 触发条件 |
|-------|------|----------|
| **`EINVAL(22)`** | **参数不合法** | `prio` 超出 `[1,99]`（RT 策略），或 `SCHED_OTHER` 传了非 0 的 `prio` |
| **`EPERM(1)`** | **权限不够** | 参数合法，但没有 `CAP_SYS_NICE` |

**`EINVAL` 先触发**——内核先验证参数、再查权限。段 ② 实测：

| 调用 | 结果 | 说明 |
|------|------|------|
| `sched_setscheduler(SCHED_FIFO, prio=80)` | **`EPERM(1)`** | 参数合法，但无 `CAP_SYS_NICE` |
| `sched_setscheduler(SCHED_FIFO, prio=1)` | **`EPERM(1)`** | **优先级低也要权限**（不是「低优先级就免检」） |
| `sched_setscheduler(SCHED_OTHER, prio=0)` | `OK` | 对照：成功路径，证明函数本身可用 |
| `sched_setscheduler(SCHED_FIFO, prio=9999)` | **`EINVAL(22)`** | **越界比权限检查更早** |

**排查意义**：报 `EINVAL` 时**先确认参数范围**，别浪费时间查权限；报 `EPERM` 才是权限问题。

⚠️ 注意第三行 `SCHED_OTHER(0) -> OK`：**这是「函数能用」的对照**——避免把「全失败」误读成「系统不支持实时调度」。
</details>

<details>
<summary>4. <code>mlockall()</code> 到底需要什么权限？「必须 root」对吗？</summary>

**「必须 root」是不准确的。** 准确的判定（`mm/mlock.c` 的 `can_do_mlock()`）是**二选一**：

| 条件 | 结果 |
|------|------|
| 有 `CAP_IPC_LOCK` | ✅ 可锁定**任意**量（不受 rlimit 限制） |
| **`RLIMIT_MEMLOCK > 0`** | ✅ **可在该上限内锁定** |
| 都没有（`RLIMIT_MEMLOCK == 0` 且无 capability） | ❌ `EPERM` |

段 ④ 的实测是最佳反例：

```text
  CapEff = 0x0000000000000000                  ← 阶段 ① 测的：没有 CAP_IPC_LOCK
  RLIMIT_MEMLOCK: soft=1996169216  hard=1996169216 字节   ← ≈ 1.86 GiB
  mlockall(MCL_CURRENT|MCL_FUTURE) -> OK       ← 成功！
  mlock(64MiB) -> OK
```

**`uid=0` + `CapEff=0x0` 仍然成功**，因为 `RLIMIT_MEMLOCK` 不为 0。

**实践含义**：

- 普通用户可以通过 `ulimit -l` 提高 `RLIMIT_MEMLOCK`（受 namespace 约束），从而用 `mlockall`；
- 嵌入式/容器默认的 `RLIMIT_MEMLOCK` 可能很小（64KB~8MB），**部署时要显式设置**（systemd 的 `LimitMEMLOCK=infinity`）；
- 需要**超过 rlimit** 的锁定量，才必须 `CAP_IPC_LOCK`。

⚠️ `mlock(2)` 手册里提到 `RLIMIT_MEMLOCK` 有 **0 字节误差上限**（传统上意味着「不允许锁定」，除非有 `CAP_IPC_LOCK`）。
</details>

<details>
<summary>5. <code>MCL_CURRENT</code> 和 <code>MCL_FUTURE</code> 分别锁什么？<code>MCL_FUTURE</code> 有什么风险？</summary>

| 标志 | 锁定范围 |
|------|----------|
| **`MCL_CURRENT`** | **当前已映射**的所有页，并立即 `mm_populate(0, TASK_SIZE)` 建立页表、分配物理页 |
| **`MCL_FUTURE`** | **之后新映射**的页（`mmap` / 堆增长）自动带 `VM_LOCKED`，无需再次调用 |
| `MCL_ONFAULT` | 延迟锁定：等页首次被访问（缺页）时才锁，省内存 |

**HFT 两个都要**（`MCL_CURRENT | MCL_FUTURE`）：既锁已有缓冲，又锁开跑后热路径动态分配的内存。

⚠️ **`MCL_FUTURE` 的风险**（要点三的坑）：

**后续新映射的页自动锁定 → 累计锁定内存可能超过 `RLIMIT_MEMLOCK` → 之后 `malloc` / `mmap` 报 `ENOMEM`，而且报错位置离「罪魁祸首」很远，极难排查。**

两种规避方式：

1. **预先分配全部热路径缓冲**（启动时把该要的内存一次要够），之后再 `MCL_FUTURE`；
2. 只用 `MCL_CURRENT`，对关键区**手工 `mlock`**。

⚠️ 另注意 `mlockall` 对 `flags` 的校验：`flags` 不能为 0、不能含未知位、**`flags == MCL_ONFAULT` 单独一个会被拒**（`EINVAL`）——`mm/mlock.c` 里那行 `if (!flags || (flags & ~(MCL_CURRENT|MCL_FUTURE|MCL_ONFAULT)) || flags == MCL_ONFAULT)`。
</details>

<details>
<summary>6. 光靠 <code>SCHED_FIFO</code> + <code>mlockall</code> 为什么到不了「硬实时」？</summary>

因为**延迟大头在内核态**：关中断、持自旋锁、关抢占的临界区会让用户态高优先级任务**无法被及时调度**，而且这段延迟**不可预测**。

用户态的 `SCHED_FIFO` / `mlockall` / 亲和只能解决**用户态**的确定性：

| 层 | 手段 | 能消除什么 | 不能消除什么 |
|----|------|-----------|-------------|
| 应用层 | `SCHED_FIFO` | 被 CFS 排队 / 时间片抢占 | **内核临界区造成的延迟** |
| 应用层 | `mlockall` | 缺页 / swap 换入 | 内核自身的页面管理停顿 |
| 内核参数 | `isolcpus` / `nohz_full` | 别的任务抢占、周期 tick 中断 | — |
| **内核版本** | **`PREEMPT_RT`** | **内核态也能被抢占（中断线程化）** | 硬件中断本身的物理延迟 |

**要压缩内核态延迟必须换内核**（`PREEMPT_RT`：自旋锁换 `rt_mutex`、中断线程化），再配合固件（关 C-state / 锁频）与用户态架构（busy-poll / 无锁队列）。

段 ⑤ 的七层谱系就是这个完整清单。本 demo 只跑了**前三层**（应用层三项），并明确标注「后三条要动内核/固件/硬件」。

**结论**：「实时」是**用户态 + 内核态 + 固件**协同的系统工程，不是单靠一个系统调用。
</details>

<details>
<summary>7. 为什么这个 demo 第一段就要读 <code>CapEff</code>？</summary>

因为**它是后面每一步成败的「解释变量」**。段 ① 打印：

```text
  CapEff = 0x0000000000000000
  CAP_SYS_NICE (bit 23) = 没有
  CAP_IPC_LOCK (bit 14) = 没有
  -> 记住这两个开关的状态，下面每一步的成败都能对上。
```

有了这份「家底」，后面每一步的成败就**从「不知道为什么不成功」变成「可预测」**：

| 段 | 结果 | 能否用家底解释 |
|----|------|--------------|
| ② `SCHED_FIFO` → `EPERM` | ❌ 失败 | ✅ 因为无 `CAP_SYS_NICE` |
| ② `SCHED_FIFO(9999)` → `EINVAL` | ❌ 失败 | ✅ **不是权限**，是参数越界（对照项） |
| ③ `sched_setaffinity` → OK | ✅ 成功 | ✅ **这个调用不需要 capability** |
| ④ `mlockall` → OK | ✅ 成功 | ⚠️ 表面上「无 `CAP_IPC_LOCK` 却成功」——**解释了为什么**（`RLIMIT_MEMLOCK > 0`） |

**这是「实验设计」的示范**：

1. **先测环境基线**（而不是假设自己有权限）；
2. **让每个结论都有对照**（有成功路径 `SCHED_OTHER`，也有失败路径）；
3. **对「反直觉的成功」（段 ④）继续追问原因**，并给出正确判据（`can_do_mlock()`）。

如果没有段 ①，段 ④ 的成功会被误读成「文档错了」；有了段 ①，它变成「`mlockall` 的权限判据是**或**关系」这个正确知识。
</details>

<details>
<summary>8. 把进程钉到 CPU 0（<code>sched_setaffinity</code>）后，那个核就被独占了？</summary>

**不是。** `sched_setaffinity` **只约束自己**——它规定「我只能在哪些 CPU 上跑」，**不排除别人跑在这个 CPU 上**。

段 ③ 实测：

```text
  当前亲和的 CPU：0 1 
  sched_setaffinity(只留 CPU 0) -> OK，现在亲和集：0 
```

这只让**本进程**不再跑 CPU 1。CPU 0 上仍然可能有：内核线程、其他进程、中断处理。

**要「独占核」需要配合**（段 ⑤ 的第 4 层）：

| 手段 | 作用 |
|------|------|
| `isolcpus=0`（内核启动参数） | 把 CPU 0 从调度器的**通用负载均衡**里摘出来，普通任务不会被调度过去 |
| `cpuset`（cgroup） | 把一组进程限制到指定 CPU |
| `nohz_full=0` | 关掉该核的周期 tick（消除定时器中断抖动） |
| 中断亲和（`/proc/irq/*/smp_affinity`） | 把中断也挪到别的核，否则网卡中断会打断你 |

**注意 `sched_setaffinity` 的好处**：它**不需要任何 capability**（段 ③ 在 `CapEff=0x0` 下成功）——所以应用层能做的三项里，只有它是「无门槛」的。

⚠️ 实战提醒：`isolcpus` 之后，**那个核上的任务不再被负载均衡，跑飞的实时任务会让核彻底卡死**（连 `kill -9` 都要等它主动让出）。所以调试时要留 `ssh` 在别的核上，或设好看门狗。
</details>
