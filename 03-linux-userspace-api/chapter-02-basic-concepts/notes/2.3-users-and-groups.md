## 本节讲什么

Linux 的权限模型建立在「用户（UID）与组（GID）」之上。本节回答三个问题：

1. UID/GID 是什么？内核用什么类型存它们？root 为什么是 0？
2. 内核在「打开文件」那一刻，权限检查的完整流程是什么？
3. real/effective/saved UID 三种身份为什么要分开？

完整 API 在 Ch8/Ch9，这里建立「权限 = UID/GID 逐位比对」的核心心智。

---

## 1. 用户与组的基本概念

| 概念 | 说明 |
|------|------|
| **UID** | 用户 ID，`root` 的 UID = **0** |
| **GID** | 主组 ID，用户登录时的默认组 |
| **补充组（supplementary groups）** | 用户可同时属于多个组，额外权限来源 |
| `/etc/passwd` | 用户名 ↔ UID/GID 映射（密码字段已移走） |
| `/etc/shadow` | 密码哈希（只有 root 可读） |
| `/etc/group` | 组名 ↔ GID 映射 |

内核并不关心「用户名」字符串，只认**数字 UID/GID**。用户名 → UID 的解析是用户态库（glibc/NSS）通过读 `/etc/passwd` 完成的。内核侧类型是 32 位无符号整数：

```c
/* include/linux/types.h:37-38 */
typedef __kernel_uid32_t	uid_t;
typedef __kernel_gid32_t	gid_t;
```

## 2. 权限检查：进程凭证 vs 文件权限位

内核在「打开文件」这类操作时，拿**进程的凭证**和**文件的 owner/group/mode 位**做比对。核心在 `fs/namei.c` 的 `generic_permission`（`:400`）：

```
进程想 open("/etc/passwd", O_RDONLY)
      │
      ▼
内核拿 inode 的 mode 位（owner/group/other 三组 rwx）
      │
      ▼ 先查 ACL（acl_permission_check）
      ▼ 查普通权限：进程的 fsuid/fsgid 与 inode 的 uid/gid 逐级匹配
```

**三种匹配顺序**（每个文件有 owner/group/other 三组权限位）：

| 进程身份 | 用哪组权限位 | 说明 |
|----------|-------------|------|
| 进程 `fsuid == 文件 uid` | **owner** 位 | 文件属主 |
| 进程属于文件所在组 | **group** 位 | 主组或补充组匹配 |
| 其他情况 | **other** 位 | 兜底 |

> **顺序是「命中即停」**：owner 匹配了就不再往下看 group/other。所以文件属主自己可能比「other」权限还低（如 owner 只读、other 可写）——这是常见反直觉坑。

root（或带 `CAP_DAC_OVERRIDE` 能力）可以**绕过** DAC 权限位检查（`generic_permission` 里的 `capable_wrt_inode_uidgid(..., CAP_DAC_OVERRIDE)`），但**不是无限制**——仍受 SELinux/AppArmor（MAC）约束。

## 3. 三种 UID：real / effective / saved

权限检查用的不是单一的 UID，而是三份（完整在 Ch9）：

| 身份 | 全称 | 用途 |
|------|------|------|
| **real UID** | 真实 UID | 进程「真正是谁」（登录用户） |
| **effective UID** | 有效 UID | **权限检查用这个**（决定能访问什么） |
| **saved set-UID** | 保存的设置 UID | 用于「临时降权后恢复」 |

普通进程三者相同；`set-user-ID` 程序（`passwd`、`sudo`）的 effective UID 会被设为**文件属主**（通常是 root），从而获得临时特权。这引出一个关键安全原则：**特权程序要尽快把不需要的特权永久降掉**（`setuid` 丢弃 saved UID），用 `seteuid` 只做临时下放（可恢复）——详见 Ch9/Ch38。

## 4. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 交易进程最小权限 | 用独立 `trading` 用户 + 专属组运行，不跑 root，减少被攻破后的破坏面 |
| 端口 <1024 需要特权 | 绑 80/443 需 root 或 `CAP_NET_BIND_SERVICE`（见 Ch39），交易端口一般 >1024 免特权 |
| setuid 程序风险 | 交易系统的 setuid 程序要慎之又慎——effective UID 提权是注入攻击的常见目标 |
| 配置文件权限 | 策略文件/密钥文件用 `chmod 600` + 属主隔离，靠 owner 位保护 |
| 共享内存/锁文件权限 | 跨进程 IPC（shm/FIFO）的 mode 位决定哪些用户可读写，部署时须显式设置 |

## 5. 代码示例

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>

int main(void) {
    uid_t ruid, euid, suid;
    gid_t rgid, egid, sgid;

    /* 三种 UID 和 GID */
    getresuid(&ruid, &euid, &suid);
    getresgid(&rgid, &egid, &sgid);
    printf("uid: real=%d effective=%d saved=%d\n", ruid, euid, suid);
    printf("gid: real=%d effective=%d saved=%d\n", rgid, egid, sgid);

    /* 补充组 */
    int ngroups = getgroups(0, NULL);
    gid_t *groups = malloc(ngroups * sizeof(gid_t));
    getgroups(ngroups, groups);
    printf("supplementary groups: %d\n", ngroups);

    /* 权限检查：effective UID 决定能 open 什么 */
    int fd = open("/etc/shadow", O_RDONLY);   /* 非 root 会 EACCES */
    if (fd < 0)
        perror("open /etc/shadow");            /* Permission denied */

    free(groups);
    return 0;
}
```

运行：普通用户跑会看到 `Permission denied`（`/etc/shadow` 是 `root:shadow 640`），`sudo ./a.out` 则能打开——因为 sudo 把 effective UID 提成了 0。

<summary>代码自测（Q&A）</summary>

**Q1：root 的 UID 是多少？内核关心「用户名」吗？**
A：root 的 UID 是 **0**。内核**不关心用户名字符串**，只认数字 UID/GID。用户名 → UID 的解析是用户态库（读 `/etc/passwd`）完成的。所以「谁是 root」在内核眼里就是「谁的有效 UID == 0」。

**Q2：内核在 `open` 文件时，权限检查的匹配顺序是什么？**
A：拿进程的 `fsuid`/`fsgid` 与文件 inode 的 `uid`/`gid` 三级匹配：① 若 `fsuid == 文件 uid` 用 **owner** 位；② 否则若进程属于文件组（主组或补充组）用 **group** 位；③ 否则用 **other** 位。**命中即停**，不往下继续——所以可能出现「属主比 other 权限还低」的反直觉现象。root（或 `CAP_DAC_OVERRIDE`）可绕过这套 DAC 检查，但仍受 MAC（SELinux/AppArmor）约束。

**Q3：real、effective、saved UID 有什么区别？权限检查用哪个？**
A：**real UID** = 进程真实身份（登录用户）；**effective UID** = 权限检查实际使用的身份；**saved set-UID** = 用于「临时降权后恢复」。set-user-ID 程序（如 `passwd`）的 effective UID 被设为文件属主（root），从而获得临时特权。普通进程三者相同。

**Q4：为什么说「root 不受任何限制」是错的？**
A：root（UID=0）能绕过的是**传统 DAC 权限位**（owner/group/other rwx）。但它仍受 **MAC**（强制访问控制，如 SELinux/AppArmor）约束，以及 capability 模型约束——现代内核里 root 的特权已被拆成几十个细粒度 capability（`CAP_NET_ADMIN`、`CAP_SYS_ADMIN` 等），进程得有对应 capability 才能做相应特权操作（见 Ch39）。

**Q5：一个用户可以属于多少个组？补充组的作用是什么？**
A：一个用户有**一个主组**（`/etc/passwd` 里的 GID）+ **多个补充组**（supplementary groups，`/etc/group` 里把用户名列进去）。补充组让用户获得多个组的权限——权限检查时「进程属于文件组」会同时匹配主组和所有补充组。`getgroups()` 可查询，`setgroups()` 可设置（需特权）。

</details>
