## 本节讲什么

Linux 的权限模型建立在「用户（UID）与组（GID）」之上。本节回答三个问题：

1. UID/GID 是什么？内核用什么类型存它们？root 为什么是 0？
2. 内核在「打开文件」那一刻，权限检查的完整流程是什么？
3. real/effective/saved UID 三种身份为什么要分开？

完整 API 在 [Ch8](../../chapter-08-users-and-groups/README.md)/[Ch9](../../chapter-09-process-credentials/README.md)，这里建立「权限 = UID/GID 逐位比对」的核心心智。

本节还要拆掉一个流传很广的错误说法：**「root 想开什么就开什么」在现代内核里是错的**——本节实测会给出一份 `euid=0` 却拿到 `EACCES` 的记录。

## 要点

### 一、用户与组的基本概念

| 概念 | 说明 |
|------|------|
| **UID** | 用户 ID，`root` 的 UID = **0** |
| **GID** | 主组 ID，用户登录时的默认组 |
| **补充组（supplementary groups）** | 用户可同时属于多个组，额外权限来源 |
| `/etc/passwd` | 用户名 ↔ UID/GID 映射（密码字段已移走） |
| `/etc/shadow` | 密码哈希（只有 root 可读） |
| `/etc/group` | 组名 ↔ GID 映射 |

内核并不关心「用户名」字符串，只认**数字 UID/GID**。用户名 → UID 的解析是用户态库（glibc/NSS）通过读 `/etc/passwd` 完成的。

内核侧的类型分成两层，**这是 user namespace 引入后才有的区分**：

| 类型 | 定义位置 | 含义 |
|------|----------|------|
| `uid_t` / `gid_t` | `include/linux/types.h:37-38` | **用户态可见**的 32 位值（`__kernel_uid32_t`） |
| `kuid_t` / `kgid_t` | `include/linux/uidgid.h:21-28` | 内核内部的**包装类型**，带 user namespace 语境 |

```c
/* include/linux/uidgid.h:21-28 —— 内核内部类型 */
typedef struct {
	uid_t val;
} kuid_t;

typedef struct {
	gid_t val;
} kgid_t;
```

> 头文件里的注释说得很清楚：这两个类型的**唯一目的**是「让编译器能发现我们什么时候把用户态值和内核值搞混了」。因为有了 user namespace，同一个数字 `0` 在不同 namespace 里代表不同的用户，所以内核不允许你直接把 `uid_t` 当 `kuid_t` 用——必须走 `make_kuid(ns, uid)` / `from_kuid(ns, kuid)`。

### 二、权限检查：进程凭证 vs 文件权限位

内核在「打开文件」这类操作时，拿**进程的凭证**和**文件的 owner/group/mode 位**做比对。核心在 `fs/namei.c:400` 的 `generic_permission()`：

```
进程想 open("/etc/passwd", O_RDONLY)
      │
      ▼
内核拿 inode 的 mode 位（owner/group/other 三组 rwx）
      │
      ▼ 先查 ACL（acl_permission_check）
      ▼ 查普通权限：进程的 fsuid/fsgid 与 inode 的 uid/gid 逐级匹配
```

**三种匹配顺序**（每个文件有 owner/group/other 三组权限位）：

| 进程身份 | 用哪组权限位 | 说明 |
|----------|-------------|------|
| 进程 `fsuid == 文件 uid` | **owner** 位 | 文件属主 |
| 进程属于文件所在组 | **group** 位 | 主组或补充组匹配 |
| 其他情况 | **other** 位 | 兜底 |

> **顺序是「命中即停」**：owner 匹配了就不再往下看 group/other。所以文件属主自己可能比「other」权限还低（如 owner 只读、other 可写）——这是常见反直觉坑，本节 demo 的 case **[E]** 专门演示它。

### 三、root 到底能绕过什么

`generic_permission()` 里有一段 `capable_wrt_inode_uidgid(..., CAP_DAC_OVERRIDE)`。所以：

- root（或带 `CAP_DAC_OVERRIDE` 的进程）可以**绕过传统 DAC 权限位**检查；
- 但**不是无限制**——仍受 MAC（SELinux/AppArmor）、capability 模型、以及「文件系统本身只读」这类内建检查约束。

现代内核把 root 的特权拆成了 40+ 个细粒度 capability，`CAP_DAC_OVERRIDE` 只是**第 1 位**（值 `2`）。所以「euid==0」**不等于**「有所有 capability」——容器就是典型反例：`euid=0` 但 `CapEff=0x0`。本节 demo 段 ②④ 把这个链条实测了一遍。

### 四、三种 UID：real / effective / saved

权限检查用的不是单一的 UID，而是三份（完整在 [Ch9](../../chapter-09-process-credentials/README.md)）：

| 身份 | 全称 | 用途 |
|------|------|------|
| **real UID** | 真实 UID | 进程「真正是谁」（登录用户） |
| **effective UID** | 有效 UID | **权限检查用这个**（决定能访问什么） |
| **saved set-UID** | 保存的设置 UID | 用于「临时降权后恢复」 |

普通进程三者相同；`set-user-ID` 程序（`passwd`、`sudo`）的 effective UID 会被设为**文件属主**（通常是 root），从而获得临时特权。这引出一个关键安全原则：**特权程序要尽快把不需要的特权永久降掉**（`setuid` 丢弃 saved UID），用 `seteuid` 只做临时下放（可恢复）——详见 [Ch9](../../chapter-09-process-credentials/README.md)/[Ch38](../../chapter-38-secure-privileged/README.md)。

> ⚠️ 还有第四个 ID：**fsuid**（filesystem UID）。**文件权限检查实际用的是 fsuid，不是 euid**。内核保证「euid 变则 fsuid 跟随」，所以平时两者相等；`setfsuid()` 可以让它们分离（[Ch9 §9.5](../../chapter-09-process-credentials/README.md)）。

## 代码

### c2_3 三份身份 + 权限位三级匹配 + 「euid=0 却 EACCES」的实测

[`../code/c2_3_cred.c`](../code/c2_3_cred.c) 分五段：

1. **三份身份** —— `getresuid`/`getresgid` 拿 R/E/S，`getgroups` 拿补充组个数与列表。
2. **`/proc/self/status` 里的凭证行（内核视角）** —— 读 `Uid:`/`Gid:`/`Groups:`，并直接从 `CapEff`/`CapPrm`/`CapBnd` 三个十六进制位掩码里**判断有没有 `CAP_DAC_OVERRIDE`（第 1 位，值 2）**。
3. **权限位三级匹配的完整推演（纯逻辑）** —— 六个 case（A–F），每个都打印「进程 uid/gid → 文件 uid/gid/mode → 命中哪一级 → 有效位 → 能不能读」。case **[E]** 是反直觉的那个：**进程就是属主，但 owner 位是 0，即使 other 位写着 `r--` 也读不到**。
4. **真实文件实验** —— 先建 `m644.txt`/`m600.txt`/`m000.txt`/`m400.txt` 四个不同 mode 的文件，再逐个 `open`，把上面那套推演落到真实 errno 上。
5. **`root` 到底能绕过什么** —— 对照 `EROFS(30)`（盘只读）和 `EACCES(13)`（权限不够）。

```c
/* TLPI 第 2 章 §2.3 —— 用户与组：三份身份 + 权限位「命中即停」+ capability 实测
 *
 * 编译：gcc -O0 -Wall -Wextra c2_3_cred.c -o c2_3
 * 运行：./c2_3
 *
 * 本节要钉死的事实：
 *   ① 内核只认数字 UID/GID，看不见「用户名」。
 *   ② 权限检查拿 fsuid/fsgid 与 inode 的 uid/gid 做三级匹配（owner→group→other），
 *      命中即停 —— 所以文件属主可能比 other 权限还低（本 demo 用纯逻辑推演钉死）。
 *   ③ 「root 无所不能」是错的：真正的特权单位是 capability。
 *      本 demo 用 CapEff 位图 + 真实 EACCES 证明：euid=0 但 CapEff=0 时，
 *      DAC 权限位**照常生效**（因为没有 CAP_DAC_OVERRIDE）。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <sys/types.h>

#define CAP_DAC_OVERRIDE_BIT 1          /* include/uapi/linux/capability.h: CAP_DAC_OVERRIDE = 1 */

/* ============ 权限位匹配的纯逻辑推演（顺序与 fs/namei.c 一致） ============ */

static const char *which_class(uid_t puid, gid_t pgid, int in_supp,
                               uid_t fuid, gid_t fgid)
{
    if (puid == fuid)       return "owner";   /* ① 属主：命中即停，不再往下看 */
    if (pgid == fgid)       return "group";   /* ② 主组匹配 */
    if (in_supp)            return "group";   /* ② 补充组匹配 */
    return "other";                           /* ③ 兜底 */
}

static int bits_of(mode_t mode, const char *cls)
{
    if (strcmp(cls, "owner") == 0) return (mode >> 6) & 7;
    if (strcmp(cls, "group") == 0) return (mode >> 3) & 7;
    return mode & 7;
}

static void rwx(int bits, char out[4])
{
    out[0] = (bits & 4) ? 'r' : '-';
    out[1] = (bits & 2) ? 'w' : '-';
    out[2] = (bits & 1) ? 'x' : '-';
    out[3] = '\0';
}

static void matrix(void)
{
    struct { const char *tag, *who; uid_t puid; gid_t pgid; int sup;
             mode_t mode; uid_t fuid; gid_t fgid; } c[] = {
        { "A", "属主本人",          1000, 1000, 0, 0640, 1000, 1000 },
        { "B", "同主组",            2000, 1000, 0, 0640, 1000, 1000 },
        { "C", "同补充组",          2000, 2000, 1, 0640, 1000, 1000 },
        { "D", "都不沾边",          2000, 2000, 0, 0640, 1000, 1000 },
        { "E", "属主但 owner 位=0", 1000, 1000, 0, 0004, 1000, 1000 },
        { "F", "不沾边但 other=rwx", 3000, 3000, 0, 0007, 1000, 1000 },
    };

    for (unsigned i = 0; i < sizeof(c) / sizeof(c[0]); i++) {
        const char *cls = which_class(c[i].puid, c[i].pgid, c[i].sup,
                                      c[i].fuid, c[i].fgid);
        int b = bits_of(c[i].mode, cls);
        char s[4]; rwx(b, s);
        printf("  [%s] 进程 uid=%u gid=%u%s\n", c[i].tag, c[i].puid, c[i].pgid,
               c[i].sup ? "（属于文件的补充组）" : "");
        printf("      文件 uid=%u gid=%u mode=%04o  ← %s\n",
               c[i].fuid, c[i].fgid, c[i].mode, c[i].who);
        printf("      命中 %-5s → 有效位 %s → 可读 %s\n\n",
               cls, s, (b & 4) ? "YES" : "no");
    }

    printf("  E 行是本节最反直觉的一条：进程就是属主，但 owner 位是 0，\n");
    printf("  即使 other 位写着 r--，也读不到 —— 因为「命中即停」，\n");
    printf("  属主根本不会去看 other 位。\n\n");
}

/* ================ 真实权限实验 ================ */

static void try_open(const char *path, int flags, const char *what)
{
    errno = 0;
    int fd = open(path, flags);
    if (fd >= 0) { printf("    %-34s %-8s OK (fd=%d)\n", path, what, fd); close(fd); }
    else         printf("    %-34s %-8s EACCES? errno=%d (%s)\n",
                        path, what, errno, strerror(errno));
    errno = 0;
}

static void fs_experiment(void)
{
    const char *dir = "/tmp/c2_3";
    mkdir(dir, 0755);

    struct { const char *n; mode_t m; } f[] = {
        { "m644.txt", 0644 }, { "m600.txt", 0600 },
        { "m000.txt", 0000 }, { "m400.txt", 0400 },
    };
    char path[128];

    printf("  先建 4 个不同 mode 的文件：\n");
    for (unsigned i = 0; i < sizeof(f) / sizeof(f[0]); i++) {
        snprintf(path, sizeof(path), "%s/%s", dir, f[i].n);
        int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, f[i].m);
        if (fd < 0) { printf("    %s 建不出来：%s\n", f[i].n, strerror(errno)); continue; }
        if (write(fd, "x", 1) != 1) perror("write");
        close(fd);
        chmod(path, f[i].m);            /* umask 可能改过它，显式设回 */
        struct stat st;
        if (stat(path, &st) == 0)
            printf("    %-10s mode=%04o  st_uid=%d st_gid=%d\n",
                   f[i].n, st.st_mode & 07777, st.st_uid, st.st_gid);
    }

    printf("\n  再逐个尝试打开（本进程 euid=%d）：\n", geteuid());
    snprintf(path, sizeof(path), "%s/m000.txt", dir);
    try_open(path, O_RDONLY, "只读");
    snprintf(path, sizeof(path), "%s/m400.txt", dir);
    try_open(path, O_RDONLY, "只读");
    try_open(path, O_WRONLY, "只写");
    snprintf(path, sizeof(path), "%s/m644.txt", dir);
    try_open(path, O_WRONLY, "只写");

    printf("\n  可以解释的三个「非权限」错误码对照：\n");
    try_open("/proc/1/mem", O_RDONLY, "读别的进程内存");
    try_open("/t_root_only.txt", O_WRONLY | O_CREAT, "根目录建文件");
}

/* ================ 读 /proc/self/status 的凭证 + capability ================ */

static unsigned long long read_hex_line(const char *key)
{
    FILE *f = fopen("/proc/self/status", "r");
    if (!f) return 0;
    char line[512];
    unsigned long long v = 0;
    size_t klen = strlen(key);
    while (fgets(line, sizeof(line), f))
        if (strncmp(line, key, klen) == 0) { sscanf(line + klen, "%llx", &v); break; }
    fclose(f);
    return v;
}

static void status_creds(void)
{
    FILE *f = fopen("/proc/self/status", "r");
    if (!f) { perror("fopen /proc/self/status"); return; }
    char line[512];
    while (fgets(line, sizeof(line), f))
        if (strncmp(line, "Uid:", 4) == 0 || strncmp(line, "Gid:", 4) == 0 ||
            strncmp(line, "Groups:", 7) == 0)
            printf("  %s", line);
    fclose(f);
}

int main(void)
{
    printf("=== ① 三份身份 ===\n");
    uid_t r, e, s; gid_t gr, ge, gs;
    if (getresuid(&r, &e, &s) == 0)
        printf("  Uid:  real=%d  effective=%d  saved=%d\n", r, e, s);
    if (getresgid(&gr, &ge, &gs) == 0)
        printf("  Gid:  real=%d  effective=%d  saved=%d\n", gr, ge, gs);

    long n = getgroups(0, NULL);
    printf("  getgroups(0, NULL) = %ld   （补充组个数）\n", n);
    if (n > 0 && n < 64) {
        gid_t g[64];
        if (getgroups((int)n, g) >= 0) {
            printf("  补充组列表：");
            for (long i = 0; i < n; i++) printf("%d ", g[i]);
            printf("\n");
        }
    }
    printf("  → 权限检查用的是 effective UID（这里是 %d），不是 real UID\n", geteuid());

    printf("\n=== ② /proc/self/status 里的凭证行（内核视角）===\n");
    status_creds();

    unsigned long long capEff = read_hex_line("CapEff:");
    printf("  CapEff = 0x%016llx   CapPrm = 0x%016llx   CapBnd = 0x%016llx\n",
           capEff, read_hex_line("CapPrm:"), read_hex_line("CapBnd:"));
    printf("  CAP_DAC_OVERRIDE 是第 %d 位（值 %llu）\n",
           CAP_DAC_OVERRIDE_BIT, 1ULL << CAP_DAC_OVERRIDE_BIT);
    printf("  本进程有没有它？%s\n",
           (capEff & (1ULL << CAP_DAC_OVERRIDE_BIT)) ? "有 → 能绕过 DAC 位"
                                                     : "没有 → DAC 位照常生效");
    printf("  → 这一行是下面第 ④ 步结果的直接原因，也是「root ≠ 无限」的证据。\n");

    printf("\n=== ③ 权限位三级匹配的完整推演（纯逻辑，顺序与内核一致）===\n");
    matrix();

    printf("=== ④ 真实文件实验（用 mode 位检验上面的推演）===\n");
    fs_experiment();

    printf("\n  结论（按实测，不按传说）：\n");
    printf("    · m000.txt 打不开、m400.txt 只能读不能写 —— DAC 位在本环境**有效**。\n");
    printf("    · 原因不是「root 权限不够」，而是本进程 euid=0 却 CapEff=0x0，\n");
    printf("      缺少 CAP_DAC_OVERRIDE 这一位。\n");
    printf("    · 拥有该 capability 的进程（如宿主机上的真 root）能打开 mode 0000 的文件。\n");

    printf("\n=== ⑤ root 到底能绕过什么 ===\n");
    printf("  root 绕过的只是**传统 DAC 权限位**（而且要靠 CAP_DAC_OVERRIDE 这一位）；\n");
    printf("  它仍受：\n");
    printf("    · capability 模型的细粒度约束（40+ 个独立能力位）\n");
    printf("    · MAC（SELinux / AppArmor）的强制策略\n");
    printf("    · 内建检查：例如根文件系统只读（下面这条实测）\n");
    errno = 0;
    int fd = open("/t.bin", O_WRONLY | O_CREAT, 0644);
    printf("    open(\"/t.bin\", O_CREAT) -> %s", fd < 0 ? "失败 " : "成功 ");
    if (fd < 0) printf("errno=%d (%s)", errno, strerror(errno));
    else close(fd);
    printf("\n    注意 EROFS(%d) 与 EACCES(%d) 是两码事：一个说「盘只读」，\n", EROFS, EACCES);
    printf("    一个说「权限不够」—— 排障时别混。\n");
    return 0;
}
```

```text
=== ④ 真实文件实验（用 mode 位检验上面的推演）===
  先建 4 个不同 mode 的文件：
    m644.txt   mode=0644  st_uid=0 st_gid=0
    m600.txt   mode=0600  st_uid=0 st_gid=0
    m000.txt   mode=0000  st_uid=0 st_gid=0
    m400.txt   mode=0400  st_uid=0 st_gid=0

  再逐个尝试打开（本进程 euid=0）：
    /tmp/c2_3/m000.txt                 只读   EACCES? errno=13 (Permission denied)
    /tmp/c2_3/m400.txt                 只读   OK (fd=3)
    /tmp/c2_3/m400.txt                 只写   EACCES? errno=13 (Permission denied)
    /tmp/c2_3/m644.txt                 只写   OK (fd=3)

  可以解释的三个「非权限」错误码对照：
    /proc/1/mem                        读别的进程内存 EACCES? errno=13 (Permission denied)
    /t_root_only.txt                   根目录建文件 EACCES? errno=30 (Read-only file system)

  结论（按实测，不按传说）：
    · m000.txt 打不开、m400.txt 只能读不能写 —— DAC 位在本环境**有效**。
    · 原因不是「root 权限不够」，而是本进程 euid=0 却 CapEff=0x0，
      缺少 CAP_DAC_OVERRIDE 这一位。
    · 拥有该 capability 的进程（如宿主机上的真 root）能打开 mode 0000 的文件。

=== ⑤ root 到底能绕过什么 ===
  root 绕过的只是**传统 DAC 权限位**（而且要靠 CAP_DAC_OVERRIDE 这一位）；
  它仍受：
    · capability 模型的细粒度约束（40+ 个独立能力位）
    · MAC（SELinux / AppArmor）的强制策略
    · 内建检查：例如根文件系统只读（下面这条实测）
    open("/t.bin", O_CREAT) -> 失败 errno=30 (Read-only file system)
    注意 EROFS(30) 与 EACCES(13) 是两码事：一个说「盘只读」，
    一个说「权限不够」—— 排障时别混。
```

**解读**

1. **段 ② 是整篇的钥匙**。段 ① 说「本进程 euid=0」，很容易顺着推出「那它想开什么就开什么」。段 ② 立刻把这个推论掐掉：`CapEff = 0x0000000000000000`，**一个 capability 都没有**。而绕过 DAC 需要的是 `CAP_DAC_OVERRIDE`（第 1 位，值 `2`），本进程没有。
2. **段 ④ 是段 ② 的必然结果，不是意外**：`m000.txt`（mode `0000`）→ `EACCES(13)`；`m400.txt`（mode `0400`）→ 只读 `OK`、只写 `EACCES`。**`mode` 位在这里百分之百生效**，说明「euid=0」并没有带来 DAC 豁免。这就是「root ≠ 无限」的直接证据。
3. **段 ③ 的 case [E] 值得单独记一笔**：进程 uid 与文件 uid 相同（`1000 == 1000`），但文件的 owner 位是 `0`（`mode=0004`），于是**可读位为 `---` → `no`**。注意文件其实有 `other = r--`，可进程根本不会去看——因为**命中即是终点**。工程含义：给文件设 `chmod 004 root-owned` 时，**属主 root 自己反而读不了**（除非有 `CAP_DAC_OVERRIDE`）。
4. **`EROFS(30)` 和 `EACCES(13)` 必须分清**。段 ⑤ 的最后两条实测把两类错误并排了：`/t_root_only.txt` 在根目录下 `O_CREAT` 得到 **`EROFS(30)`**（根文件系统是只读挂载，跟权限**无关**），而 `/proc/1/mem` 读别的进程内存得到 **`EACCES(13)`**（这个才是权限问题）。**排障时把 30 当权限问题去查 `ls -l` 会白费半天。**
5. **一个可迁移的判断法**：以后看到「明明是 root 却 Permission denied」，按这个顺序查——**①** `CapEff` 有没有 `CAP_DAC_OVERRIDE`（`/proc/self/status`）；**②** 挂载选项是不是 `ro`/`nosuid`（`/proc/self/mountinfo`）；**③** 有没有 SELinux/AppArmor 拒绝记录（`dmesg`/`audit.log`）。本 demo 覆盖了前两条。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 交易进程最小权限 | 用独立 `trading` 用户 + 专属组运行，不跑 root，减少被攻破后的破坏面 |
| 端口 <1024 需要特权 | 绑 80/443 需 root 或 `CAP_NET_BIND_SERVICE`（见 [Ch39](../../chapter-39-capabilities/README.md)），交易端口一般 >1024 免特权 |
| setuid 程序风险 | 交易系统的 setuid 程序要慎之又慎——effective UID 提权是注入攻击的常见目标 |
| 配置文件权限 | 策略文件/密钥文件用 `chmod 600` + 属主隔离，靠 owner 位保护 |
| 共享内存/锁文件权限 | 跨进程 IPC（shm/FIFO）的 mode 位决定哪些用户可读写，部署时须显式设置 |
| **容器里 `euid=0` 不等于有权限** | 段 ②④ 实测：`CapEff=0x0` 时 `mode 0000` 的文件照样 `EACCES`。K8s `securityContext.capabilities.drop: ["ALL"]` 就是这个效果，**别用「跑在 root 下」当权限论证** |
| **`EROFS` 是嵌入式最常见的假权限错** | 只读 rootfs（squashfs/erofs/`ro` 挂载）下往 `/` 写必然 `EROFS(30)`。要写就得 `mount -o remount,rw` 或写 `/tmp`、`/var` 这类 tmpfs——**跟 DAC 位一点关系都没有** |
| **`chmod 004` 型配置会把自己的服务坑死** | case [E] 的教训：属主位为 0 时，**属主自己都读不到**（除非有 `CAP_DAC_OVERRIDE`）。部署脚本里 `chmod 400`/`600` 是安全的，但 `chmod 004` 要确认属主是不是运行用户 |

## 自测题

<details>
<summary>1. root 的 UID 是多少？内核关心「用户名」吗？</summary>

root 的 UID 是 **0**。内核**不关心用户名字符串**，只认数字 UID/GID。用户名 → UID 的解析是用户态库（读 `/etc/passwd`）完成的。所以「谁是 root」在内核眼里就是「谁的有效 UID == 0」。

内核侧甚至连「一个数字」都不是：用户态看到的是 `uid_t`（`include/linux/types.h:37`），内核内部用的是包装类型 `kuid_t`（`include/linux/uidgid.h:21-23`）——因为这个值要带 user namespace 语境。
</details>

<details>
<summary>2. 内核在 <code>open</code> 文件时，权限检查的匹配顺序是什么？</summary>

拿进程的 `fsuid`/`fsgid` 与文件 inode 的 `uid`/`gid` 三级匹配：

1. 若 `fsuid == 文件 uid` → 用 **owner** 位；
2. 否则若进程属于文件组（主组**或**任一补充组）→ 用 **group** 位；
3. 否则 → 用 **other** 位。

**命中即停**，不往下继续。所以会出现「属主比 other 权限还低」的反直觉现象——本节 demo 的 case **[E]** 就是这个：

```text
  [E] 进程 uid=1000 gid=1000
      文件 uid=1000 gid=1000 mode=0004  ← 属主但 owner 位=0
      命中 owner → 有效位 --- → 可读 no
```

文件明明有 `other = r--`，但进程是属主，**根本不会去看 other 位**。

root（或带 `CAP_DAC_OVERRIDE`）可绕过这套 DAC 检查，但仍受 MAC（SELinux/AppArmor）与挂载选项约束。
</details>

<details>
<summary>3. 我的进程 <code>euid=0</code>，为什么打开 <code>mode 0000</code> 的文件还是 <code>Permission denied</code>？</summary>

**因为绕过 DAC 需要的是 `CAP_DAC_OVERRIDE` 这个 capability，而不是「euid==0」这个身份。** 本节实测：

```text
  CapEff = 0x0000000000000000
  CAP_DAC_OVERRIDE 是第 1 位（值 2）
  本进程有没有它？没有 → DAC 位照常生效
  ...
    /tmp/c2_3/m000.txt                 只读   EACCES? errno=13 (Permission denied)
    /tmp/c2_3/m400.txt                 只读   OK (fd=3)
    /tmp/c2_3/m400.txt                 只写   EACCES? errno=13 (Permission denied)
```

`CapEff=0x0` 说明进程**一个 capability 都没有**（容器 `drop: ALL` 的效果），所以 `mode` 位百分之百生效。

排查顺序：**①** `grep CapEff /proc/self/status` 看有没有 bit 1；**②** `/proc/self/mountinfo` 看挂载是不是 `ro`；**③** 看 SELinux/AppArmor 有没有拒绝记录。
</details>

<details>
<summary>4. <code>EROFS(30)</code> 和 <code>EACCES(13)</code> 有什么区别？</summary>

**两个完全不同层面的失败，排障方向相反。**

| errno | 名字 | 含义 | 该查什么 |
|-------|------|------|----------|
| 13 | `EACCES` | 权限不够（DAC/MAC 拒绝） | `ls -l`、`CapEff`、SELinux |
| 30 | `EROFS` | **文件系统是只读挂载** | `mount` 输出、`/proc/self/mountinfo` |

本节实测两条并排：

```text
    /proc/1/mem                        读别的进程内存 EACCES? errno=13 (Permission denied)
    /t_root_only.txt                   根目录建文件 EACCES? errno=30 (Read-only file system)   ← errno 30 才是判据，demo 统一印 "EACCES?" 只是措辞
```

在只读 rootfs 的嵌入式设备上，往 `/` 写**永远**是 30——此时去调 `chmod`/`chown` 一点用都没有，得 `remount,rw` 或改写到 `/tmp`、`/var`（tmpfs）。
</details>

<details>
<summary>5. real、effective、saved UID 有什么区别？权限检查用哪个？</summary>

- **real UID** = 进程真实身份（登录用户）；
- **effective UID** = 权限检查实际使用的身份；
- **saved set-UID** = 用于「临时降权后恢复」。

set-user-ID 程序（如 `passwd`）的 effective UID 被设为文件属主（root），从而获得临时特权。普通进程三者相同。

⚠️ 但**文件权限检查真正用的是第四个 ID：fsuid**。内核保证「euid 变则 fsuid 跟随」，所以平时相等；`setfsuid()` 能让它们分离（[Ch9 §9.5](../../chapter-09-process-credentials/README.md) 有 `setfsuid` 静默失败的完整实测）。
</details>

<details>
<summary>6. 一个用户可以属于多少个组？补充组的作用是什么？</summary>

一个用户有**一个主组**（`/etc/passwd` 里的 GID）+ **多个补充组**（`/etc/group` 里把用户名列进去）。补充组让用户获得多个组的权限——权限检查时「进程属于文件组」会同时匹配主组和所有补充组。

本节 demo 段 ① 实测：`getgroups(0, NULL) = 1`，补充组列表 `0`。上限由 `_SC_NGROUPS_MAX` 给出（本环境 `65536`，见 [2.11](./2.11-signals.md) 同系列的 `sysconf` 读取）。

`getgroups()` 可查询，`setgroups()` 可设置（需特权，[Ch9 §9.6](../../chapter-09-process-credentials/README.md) 有两道闸门的实测）。
</details>
