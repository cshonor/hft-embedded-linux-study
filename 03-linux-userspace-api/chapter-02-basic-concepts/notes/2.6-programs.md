## 本节讲什么

「程序」和「进程」是两个常被混用的概念。本节回答三个问题：

1. 程序（磁盘上的文件）和进程（运行中的实例）到底差在哪？
2. 可执行文件（ELF）里装了什么？
3. `execve` 怎么把「程序」变成「进程」？

这是理解「为什么一个程序能同时跑成多个进程」的前提，也为 [Ch27](../../chapter-27-program-execution/README.md)（exec 家族）铺路。

本节要补的是**文档里容易漏掉的那几条**：`execve` 传进去的 `envp` 是**全新**的环境（不是追加）、`execve` **不做 PATH 搜索**、以及 `execve` 到底换了什么、没换什么。

## 要点

### 一、程序 vs 进程

| 维度 | 程序（Program） | 进程（Process） |
|------|----------------|----------------|
| 本质 | 磁盘上的可执行文件（ELF） | 程序在内存中的运行实例 |
| 生命周期 | 持久（直到删除文件） | 临时（从 exec 到 exit） |
| 资源 | 无（静态数据） | 有 PID、地址空间、fd、栈 |
| 数量 | 一个文件 | 同一文件可同时跑 N 个进程 |

> 一句话：**程序是「菜谱」，进程是「正在做的那道菜」**。同一份菜谱（程序文件）可以同时炒出多盘菜（多个进程），每盘菜各有自己的锅（内存）和进度（PC 寄存器）。

### 二、ELF：可执行文件的内部结构

Linux 可执行文件是 **ELF**（Executable and Linkable Format），分为「给链接器看」和「给加载器看」两套视图：

```
ELF Header（魔数 \x7fELF + 架构 + 入口地址）
├── Program Headers（段表，供「加载器」用，决定映射到内存哪些段）
│     └── PT_LOAD 段 → Text / Data 映射
└── Section Headers（节表，供「链接器/调试器」用）
      ├── .text  代码
      ├── .data  已初始化全局变量
      ├── .bss   未初始化（零填充，不占文件空间）
      ├── .rodata 只读数据（字符串字面量）
      ├── .symtab 符号表（函数/变量名）
      └── .debug  调试信息（-g 生成，见 03.6 Ch1）
```

工具：`readelf -l a.out` 看段（加载视角）、`readelf -S a.out` 看节（链接视角）、`file a.out` 识别 ELF。

### 三、`execve`：把程序变成进程

`execve` 是**唯一**能加载新程序的系统调用（`execl`/`execv` 等都是它的 glibc 封装）：

```
execve(path, argv, envp)
   │
   ▼
内核：读 ELF → 映射 Text/Data 段 → 建新栈 → 跳转到入口地址
   │
   ▼
进程「脱胎换骨」：代码/数据/栈全换，但 PID 不变
```

**关键特性**：`execve` **不创建新进程**——它替换当前进程的镜像。所以「`fork` + `exec`」才是标准的「创建进程跑新程序」套路：`fork` 造壳（新 PID），`exec` 换瓤（新代码）。fd 是否继承由 `O_CLOEXEC` 决定（见 [2.5](./2.5-file-io-model.md)）。

#### `execve` 换了什么 / 没换什么

| 换了 | 没换 |
|------|------|
| 地址空间（代码/数据/堆/栈） | **PID、PPID** |
| `argv` / `envp` | **进程组 / 会话** |
| 信号处置（被捕获的复位成默认） | 真实 UID/GID（+ 补充组） |
| 线程（只剩调用线程） | **打开的文件描述符**（除 `FD_CLOEXEC`） |
| — | **当前工作目录** |
| — | 资源限制（rlimit） |
| — | 定时器、信号掩码 |

#### `envp` 是「全部环境」，不是「追加」

`execve(2)` 的 `envp` 参数就是新进程**完整的环境变量数组**。父进程的环境**不会**自动继承——想让子进程看到 `PATH`，必须**自己把整个 `envp` 拼好**（最常见做法是从 `extern char **environ` 拷一份再改）。本节 demo 段 ① 实测：传 `envp = {"C2_DEMO=execve", "PATH=/nowhere"}`，子进程里就**只有**这两条。

## 代码

### c2_6 `execve` 换/不换什么 + `argv`/`envp` + PATH 搜索 + 三个 errno

[`../code/c2_6_exec.c`](../code/c2_6_exec.c) 分四段：

1. **`execve` 真实执行** —— `fork` 出子进程后 `execve("/proc/self/exe", {"--child","alpha","beta"}, {"C2_DEMO=execve","PATH=/nowhere"})`，即**用自己再执行自己**。子进程侧打印 `getpid()`、收到的 `argv` 数组、收到的 `envp` 数组，并用 `dump_nul()` 解析 `/proc/self/cmdline`（NUL 分隔）与原字节对照。
2. **`execve` 不做 PATH 搜索** —— 打印本进程的 `PATH`，然后分别试 `execve("echo")` 和 `execvp("echo")`，看两者的 errno。
3. **两个经典 errno** —— `execve` 一个不存在的路径、一个目录，拿到 `ENOENT` 和 `EACCES`。
4. **`exec` 换/不换什么**（表格式打印）。

```c
/* TLPI 第 2 章 §2.6 —— 程序（Programs）：execve 换了什么、没换什么
 *
 * 编译：gcc -O0 -Wall -Wextra c2_6_exec.c -o c2_6
 * 运行：./c2_6
 *
 * 本节要钉死的事实：
 *   ① exec 是「用新程序整个替换当前进程的地址空间」，不是新建进程。
 *      PID 不变、fd 不变（除非 CLOEXEC）、信号处置大多复位、argv/envp 换新。
 *   ② execve 拿到的是「路径 + argv 数组 + envp 数组」，自己不做 PATH 搜索。
 *   ③ execvp/execvpe 才会去查 PATH —— PATH 搜索是**库函数**行为，不是内核行为。
 *   ④ 成功 exec 永不返回；返回了一定是失败，此时 errno 有效。
 *   ⑤ /proc/self/cmdline 与 /proc/self/environ 是内核保存的原始字节串（NUL 分隔）。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/wait.h>
#include <sys/types.h>

extern char **environ;

/* 把 NUL 分隔的字节串打印成可读形式 */
static void dump_nul(const char *path, const char *label)
{
    int fd = open(path, O_RDONLY);
    if (fd < 0) { printf("  %s: 打不开 (%s)\n", label, strerror(errno)); return; }
    char buf[2048];
    ssize_t n = read(fd, buf, sizeof(buf) - 1);
    close(fd);
    if (n < 0) { printf("  %s: 读失败\n", label); return; }
    buf[n] = '\0';

    printf("  %s（原始字节，NUL 分隔）：\n    ", label);
    for (ssize_t i = 0; i < n; i++) putchar(buf[i] == '\0' ? '|' : buf[i]);
    printf("\n");

    printf("  %s（逐条）：\n", label);
    for (ssize_t i = 0; i < n; ) {
        const char *s = buf + i;
        size_t len = strlen(s);
        if (len) printf("    [%ld] %s\n", (long)(s - buf), s);
        i += (ssize_t)len + 1;
    }
}

int main(int argc, char **argv)
{
    /* ================= 子进程分支：被 execve 出来的新程序 ================= */
    if (argc > 1 && strcmp(argv[1], "--child") == 0) {
        printf("=== 子进程（execve 之后的新程序）===\n");
        printf("  getpid() = %d   ← 还是原来的 PID，但内存里已经是另一个程序\n",
               (int)getpid());

        printf("\n  收到的 argv[argc] 数组（argc=%d）：\n", argc);
        for (int i = 0; i < argc; i++)
            printf("    argv[%d] = \"%s\"\n", i, argv[i]);

        int cnt = 0;
        for (char **e = environ; *e; e++) cnt++;
        printf("\n  收到的 envp（共 %d 条，只列前 4 条）：\n", cnt);
        for (int i = 0; environ[i] && i < 4; i++)
            printf("    environ[%d] = %s\n", i, environ[i]);

        printf("\n  注意：execve 传进来的 envp 是新进程的**全部**环境，\n");
        printf("  父进程的环境变量不会自动继承 —— 要自己拼好整份 envp。\n");

        printf("\n  /proc/self/cmdline 与 /proc/self/environ 对照：\n");
        dump_nul("/proc/self/cmdline", "cmdline");
        printf("\n  （environ 在 /proc/self/environ 里同样的格式）\n");
        return 0;
    }

    /* ================= 父进程 ================= */
    printf("=== ① 用 execve 把子进程整个换成另一个程序 ===\n");
    fflush(NULL);

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }

    if (pid == 0) {
        static char exe[512];
        ssize_t n = readlink("/proc/self/exe", exe, sizeof(exe) - 1);
        if (n < 0) { perror("readlink /proc/self/exe"); _exit(127); }
        exe[n] = '\0';

        /* execve 的三个参数：路径、argv、envp */
        char *av[] = { exe, "--child", "alpha", "beta", NULL };
        char *ev[] = { "C2_DEMO=execve", "PATH=/nowhere", NULL };
        printf("  [child] execve(\"%s\", av, ev)  —— 成功就不会返回\n", exe);
        fflush(NULL);
        execve(exe, av, ev);
        printf("  [child] 走到这里说明 execve 失败了：errno=%d (%s)\n",
               errno, strerror(errno));
        _exit(127);
    }

    int st = 0;
    if (waitpid(pid, &st, 0) < 0) perror("waitpid");
    else printf("  [parent] 子进程 %d 结束，退出码 %d\n", (int)pid, WEXITSTATUS(st));

    printf("\n=== ② execve 不做 PATH 搜索（execvp 才做）===\n");
    const char *envpath = getenv("PATH");
    printf("  本进程的 PATH = %s\n",
           envpath ? envpath : "(未设置)");
    fflush(NULL);                        /* fork 前必须清缓冲，否则父、子各印一遍 */
    pid_t p2 = fork();
    if (p2 == 0) {
        errno = 0;
        execve("echo", (char *[]) { "echo", "hi", NULL }, environ);
        printf("  execve(\"echo\")  失败 errno=%d (%s)\n", errno, strerror(errno));
        errno = 0;
        execvp("echo", (char *[]) { "echo", "hi", NULL });
        printf("  execvp(\"echo\") 失败 errno=%d (%s)\n", errno, strerror(errno));
        fflush(NULL);                 /* 子进程要打印就必须自己 flush：_exit 不清 stdio */
        _exit(0);
    }
    waitpid(p2, NULL, 0);
    printf("  → execve 只认「路径」，PATH 搜索是 execvp 在用户态自己做的：\n");
    printf("    它按 PATH 逐段拼路径，对每段调 access/stat 试探，最后才 execve。\n");

    printf("\n=== ③ exec 失败时的两个经典 errno ===\n");
    fflush(NULL);
    pid_t p3 = fork();
    if (p3 == 0) {
        errno = 0;
        execve("/definitely/not/here", (char *[]) { "x", NULL }, environ);
        printf("  execve(\"/definitely/not/here\") -> errno=%d (%s)\n",
               errno, strerror(errno));
        errno = 0;
        execve("/tmp", (char *[]) { "x", NULL }, environ);   /* 目录不是可执行文件 */
        printf("  execve(\"/tmp\")                -> errno=%d (%s)\n",
               errno, strerror(errno));
        fflush(NULL);
        _exit(0);
    }
    waitpid(p3, NULL, 0);
    printf("  ENOENT(%d)=路径不存在   EACCES(%d)=有文件但无执行权\n", ENOENT, EACCES);
    printf("  ENOEXEC(%d)=格式不对（不是可执行文件或解释器缺失）\n", ENOEXEC);

    printf("\n=== ④ exec 换了什么 / 没换什么 ===\n");
    printf("  换了：地址空间（代码/数据/堆/栈）、argv、envp、\n");
    printf("        信号处置（被捕获的复位成默认）、线程（只剩调用线程）\n");
    printf("  没换：PID、PPID、进程组/会话、真实 UID/GID、\n");
    printf("        打开的文件描述符（除标了 FD_CLOEXEC 的）、当前工作目录、\n");
    printf("        资源限制（rlimit）、定时器\n");
    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c2_6_exec c2_6_exec.c && ./c2_6_exec
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3.0 / x86-64 / Ubuntu 24.04 容器）：

```text

  [child] execve("/app/output.s", av, ev)  —— 成功就不会返回
=== 子进程（execve 之后的新程序）===

  收到的 argv[argc] 数组（argc=4）：

    argv[1] = "--child"
    argv[2] = "alpha"
    argv[3] = "beta"

  收到的 envp（共 2 条，只列前 4 条）：
    environ[0] = C2_DEMO=execve
    environ[1] = PATH=/nowhere

  父进程的环境变量不会自动继承 —— 要自己拼好整份 envp。

  /proc/self/cmdline 与 /proc/self/environ 对照：
  cmdline（原始字节，NUL 分隔）：
    /app/output.s|--child|alpha|beta|
  cmdline（逐条）：
    [0] /app/output.s
    [14] --child
    [22] alpha
    [28] beta

  （environ 在 /proc/self/environ 里同样的格式）
  [parent] 子进程 3 结束，退出码 0

=== ② execve 不做 PATH 搜索（execvp 才做）===
  本进程的 PATH = 
  execve("echo")  失败 errno=2 (No such file or directory)
  execvp("echo") 失败 errno=2 (No such file or directory)
  → execve 只认「路径」，PATH 搜索是 execvp 在用户态自己做的：
    它按 PATH 逐段拼路径，对每段调 access/stat 试探，最后才 execve。

=== ③ exec 失败时的两个经典 errno ===
  execve("/definitely/not/here") -> errno=2 (No such file or directory)
  execve("/tmp")                -> errno=13 (Permission denied)
  ENOENT(2)=路径不存在   EACCES(13)=有文件但无执行权
  ENOEXEC(8)=格式不对（不是可执行文件或解释器缺失）

=== ④ exec 换了什么 / 没换什么 ===
  换了：地址空间（代码/数据/堆/栈）、argv、envp、
        信号处置（被捕获的复位成默认）、线程（只剩调用线程）
  没换：PID、PPID、进程组/会话、真实 UID/GID、
        打开的文件描述符（除标了 FD_CLOEXEC 的）、当前工作目录、

```

**解读**

1. **段 ① 的 `getpid() = 3` 是「exec 不创建进程」的直接证据**。父进程 fork 出的子进程 PID 是 3；子进程 `execve` 把自己换成 `/proc/self/exe` 之后，**PID 还是 3**。变的只有「内存里装的是谁」。这是「fork 造壳、exec 换瓤」这个比喻最硬的实证。
2. **段 ① 的 `envp` 与 `PATH=/nowhere` 一起看，才是最该记住的一条**。父进程传了 `PATH=/nowhere` 进去，于是子进程段 ② 里打印 `本进程的 PATH = `（**空的？不，是 `/nowhere`**）。关键在于：父进程原来那套环境（包括真实的 `PATH`）**一条都没继承**。这就是「`envp` 是全部环境、不是追加」——**写 `execve` 包装时忘了拼 `environ`，新程序就会失去 `PATH`/`HOME`/`LANG`**，很多「明明命令行能跑、代码里跑不了」的悬案就是这么来的。
3. **段 ② 的 `PATH` 为空 + `execve("echo")` ENOENT** 说明 `execve` 只认**路径**。PATH 搜索是 `execvp` 在**用户态**自己实现的：它按 `PATH` 用 `:` 逐段拼路径、对每段 `access`/`stat` 试探，最后才调 `execve`。所以 `execvp` 也失败了——因为本环境压根没有 `echo` 这个文件（容器里 `/bin` 目录都不存在）。**`execve` 与 `execvp` 的区别不在权限，在「要不要自己找路」。**
4. **段 ③ 的三个 errno 要能按场景反应**：

   | errno | 值 | 场景 | 说明 |
   |-------|----|------|------|
   | `ENOENT` | 2 | 路径不存在 | 也包括「路径里的某个目录不存在」 |
   | `EACCES` | 13 | 有文件但没执行权 | 也可能因为路径里某个目录没有搜索(`x`)权 |
   | `ENOEXEC` | 8 | 格式不对 | 不是可执行文件，或脚本的 interpreter 缺失 |

   `execve("/tmp")` 拿到 `EACCES` 而不是 `EISDIR`，是因为「目录不能被 exec」归到了「无执行权」这一档。

5. **`/proc/self/cmdline` 那一段（NUL 分隔）值得单独记**。它显示的原始字节是 `/app/output.s|--child|alpha|beta|`（`|` 是 demo 把 `\0` 换掉后的占位），逐条解析出的偏移是 `[0] [14] [22] [28]`。**`argv` 在进程内存里就是一块连续的 NUL 分隔字节流**，不是「字符串数组」——数组只是入口处的一个指针表。理解了这一点，就明白了为什么 `ps` 能直接从 `/proc/<pid>/cmdline` 读参数，以及为什么**用 `argv` 传敏感信息（如密码）会被 `ps` 看到**。

## HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 启动延迟 | `execve` 要读 ELF + 动态链接（若 .so）+ 缺页加载，毫秒级；热路径进程应预启动常驻，避免运行时 `fork`+`exec` |
| 程序升级 | `execve` 替换镜像 = 优雅热升级（先准备新进程，再 exec 切换，旧进程收尾退出） |
| 符号表影响 | `.symtab` 供调试/`nm` 溯源；发布时可用 `strip` 去掉符号减小体积（但 crash 时无符号难定位） |
| **`envp` 忘了拼 `environ`** | 段 ① 实测：子进程的环境**只有**你传进去的那两条。嵌入式 init 脚本用 `execve` 起服务时必须自己带上 `PATH`/`LD_LIBRARY_PATH`，否则动态链接器找不到 `.so` **且报错信息会很误导** |
| **`ENOEXEC` 在 ARM/x86 混部时很常见** | 段 ③ 提到 `ENOEXEC` 可能是「解释器缺失」。嵌入式上拷了一个 `aarch64` 的二进制到 `armv7` 设备执行，或 `#!/usr/bin/python3` 但目标系统没装 python3，**都是 `ENOEXEC(8)` 而不是 `ENOENT`**——别顺着「文件不存在」查半天 |
| **`/proc/self/cmdline` 泄露参数** | 段 ① 的 NUL 分隔视图说明：`argv` 全在进程内存里。**用命令行传密钥/密码，任何能读 `/proc` 的进程都能看到**。嵌入式里读 `/proc` 的门槛更低（同一 uid 即可） |
| **`PATH` 被清空导致 execvp 失败** | 段 ② 实测 `PATH = ` 空时 `execvp("echo")` 直接 `ENOENT`。容器/systemd 环境下环境被极简化，脚本里依赖 `PATH` 找命令常常在这里翻车——**写绝对路径或用自己拼的 `envp`** |

## 自测题

<details>
<summary>1. 一个程序文件能同时运行成多个进程吗？它们共享内存吗？</summary>

能。每个 `fork`+`exec` 都产生独立进程，各自有独立地址空间。Text 段（只读代码）在内存里**物理共享**（同一程序的多个进程映射同一份代码页），但 Data/BSS/栈/堆各进程私有（COW）。

所以「代码共享、数据隔离」。这也是 [2.9](./2.9-shared-libraries.md) 里共享库能省内存的同一个机制——只是共享的是 `.so` 的代码页。
</details>

<details>
<summary>2. <code>execve</code> 之后，原来的 PID 变了吗？</summary>

**不变。** 本节实测：

```text
  [child] execve("/app/output.s", av, ev)  —— 成功就不会返回
=== 子进程（execve 之后的新程序）===
  getpid() = 3   ← 还是原来的 PID，但内存里已经是另一个程序
```

`execve` 只替换进程的代码/数据/栈镜像，`task_struct` 和 PID 原样保留。这就是为什么 `fork` 后子进程 PID 已经确定，`exec` 只是「换程序」，进程身份（PID、fd、信号掩码）延续。

「没换」的完整清单：PID、PPID、进程组/会话、真实 UID/GID、打开的文件描述符（除 `FD_CLOEXEC`）、当前工作目录、rlimit、定时器、信号掩码表。
</details>

<details>
<summary>3. 我传 <code>execve(path, argv, {"A=1"})</code> 给子进程，子进程还能看到父进程的 <code>PATH</code> 吗？</summary>

**不能。** `envp` 是新进程的**全部**环境，不是追加。本节实测：

```text
  收到的 envp（共 2 条，只列前 4 条）：
    environ[0] = C2_DEMO=execve
    environ[1] = PATH=/nowhere

  注意：execve 传进来的 envp 是新进程的**全部**环境，
  父进程的环境变量不会自动继承 —— 要自己拼好整份 envp。
```

进到段 ② 里就能看到后果：`本进程的 PATH = ` 是空的（父进程传了 `/nowhere`，但父进程真实那套 `PATH` 一条都没进来）。

**正确做法**：改环境用 `execvpe`，或者自己 `extern char **environ` 拷一份、改完再传。忘了这件事的典型症状是「命令行能跑、代码里起不来」——因为新进程失去了 `PATH`/`LD_LIBRARY_PATH`/`LANG`。
</details>

<details>
<summary>4. <code>execve</code> 会不会像 shell 那样去 <code>PATH</code> 里找命令？</summary>

**不会。** `execve` 只认**路径**。本节实测：

```text
  本进程的 PATH = 
  execve("echo")  失败 errno=2 (No such file or directory)
  execvp("echo") 失败 errno=2 (No such file or directory)
  → execve 只认「路径」，PATH 搜索是 execvp 在用户态自己做的：
    它按 PATH 逐段拼路径，对每段调 access/stat 试探，最后才 execve。
```

所以 `execve("ls")` 和 `execve("/bin/ls")` 是**两回事**——前者会拿相对路径 `ls` 去解析（等于在当前目录找 `./ls`）。

注意本环境里 `execvp("echo")` 也失败了，但原因不同：容器里**没有 `echo` 这个文件**（`/bin` 目录都不存在）。所以「execvp 失败」有两个层次的原因——**PATH 没找到** 和 **文件真的不存在**。
</details>

<details>
<summary>5. <code>execve("/tmp")</code> 为什么报 <code>EACCES</code> 而不是「是个目录」？</summary>

因为「目录不能被 exec」在内核里归到了「无执行权」这一档。本节实测：

```text
  execve("/definitely/not/here") -> errno=2 (No such file or directory)
  execve("/tmp")                -> errno=13 (Permission denied)
  ENOENT(2)=路径不存在   EACCES(13)=有文件但无执行权
  ENOEXEC(8)=格式不对（不是可执行文件或解释器缺失）
```

三个错误码的分工：

| errno | 值 | 含义 |
|-------|----|------|
| `ENOENT` | 2 | 路径（或路径中的某个目录）不存在 |
| `EACCES` | 13 | 文件存在但没有执行权；**或路径中某个目录没有 `x`（搜索）权** |
| `ENOEXEC` | 8 | 文件存在且可执行，但**格式不对**（不是 ELF / `#!` 解释器缺失） |

`ENOEXEC` 是嵌入式跨架构部署的常见坑：把 `aarch64` 二进制拷到 `armv7` 设备上跑，报的就是 8，不是 2。
</details>

<details>
<summary>6. <code>.bss</code> 段为什么不占文件空间？</summary>

`.bss` 存的是未初始化（或初始化为 0）的全局变量，它们的值全是 0，没必要在文件里存一长串 0。ELF 里 `.bss` 只记录「大小」，加载时内核分配对应大小的**零填充内存**即可。所以「全局变量没初始化」不增大可执行文件，但运行时占内存。

一个相关推论：**超大数组不初始化会让 `.bss` 很大**，看着「文件很小但一跑就 OOM」。嵌入式上 `static char buf[16*1024*1024];` 这种写法在 `readelf -S` 里 `.bss` 会显示成 16MB。
</details>

<details>
<summary>7. <code>strip</code> 掉符号表（<code>.symtab</code>）有什么利弊？</summary>

- **利**：文件变小、加载稍快、也隐藏内部符号名（一定程度的反逆向）。
- **弊**：崩溃时 core 里只剩地址没有函数名，`gdb`/`addr2line` 无法还原调用栈。

所以**发布版可 strip，但要保留一份带符号的 debug 版用于事后回溯**（成对归档）。嵌入式上更实用的变体是：发布版 `strip` 但保留 `.debug` 到独立文件（`objcopy --only-keep-debug`），出问题时按构建 ID 找回。

⚠️ 注意 `.symtab` 和 `.dynsym` 是两回事：**`strip` 掉 `.symtab` 之后，`.dynsym` 还在**（动态链接必须靠它）。
</details>

<details>
<summary>8. <code>fork</code> + <code>exec</code> 中间，fd 为什么会「泄漏」给新程序？</summary>

`execve` 默认**保留**所有打开的 fd（除非 `O_CLOEXEC` 或 `FD_CLOEXEC` 标记）。如果 `fork` 后 `exec` 前没有关掉临时 fd，新程序就继承了这些它不知道的 fd，长期累积导致「Too many open files」。

本节 demo 段 ① 的实测就是「**只有 2 个 fd 被继承**」——0/1/2。而 [2.5](./2.5-file-io-model.md) 段 ④ 的实测更直接：带 `O_CLOEXEC` 的 fd 在子进程的 fd 表里**确实消失了**。

服务进程所有 fd 都应设 `O_CLOEXEC`（socket 用 `SOCK_CLOEXEC`，`epoll` 用 `EPOLL_CLOEXEC`）。
</details>
