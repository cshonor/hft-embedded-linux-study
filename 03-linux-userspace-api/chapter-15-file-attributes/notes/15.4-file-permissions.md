## 本节讲什么

全章最重的一节（官方分 7 个子节）：权限判定算法、`access()`、SUID/SGID/sticky、`umask()`、`chmod()`。本篇钉住五个实测事实：

1. 权限判定是 **switch 不是 if 连判**——选中的三元组说了算，不叠加；
2. 目录的 r/w/x 各管一件事，"能进不能看"的目录真实存在（实测）；
3. `umask` 只作用于**创建**，不作用于 `chmod`；
4. SUID 程序里 `access()`（real ID）与 `open()`（effective ID）的回答可以不同；
5. 大写 X 的 `a+rX` 语义怎么用程序实现（习题 15-6）。

## §15.4.1/15.4.2 权限位与目录三权

| 位 | 普通文件 | 目录 |
|----|---------|------|
| r | 读内容 | **列目录项**（需要 x 配合拿到属性） |
| w | 写内容 | **创建/删除/改名目录内对象**（无需读权） |
| x | 执行 | **穿越**（路径解析经过此目录 / open 目录内文件） |

## §15.4.3 判定算法：三选一，不叠加

```
euid == st_uid                  → 只看属主三元组
else egid ∈ {st_gid, 补充组}    → 只看属组三元组
else                            → 只看其他三元组
```

实测（[`code/c15_6_access.c`](../code/c15_6_access.c)，mode=0077，属主就是我们）：

```text
== ① mode=0077：属主位=---，属主自己也被拒（不叠加！）==
  文件属主 = 501（就是我们），mode=0077（0077；创建时被 umask 剪成 0055 的教训见 15.4.6）
  access(..., R_OK) = -1  Permission denied
  → 「其他」位明明有 r，但属主判定走属主三元组：---，拒。
     权限判定是 switch 不是 if 连判——这条是 15.4.3 的灵魂。
```

（这个 demo 本身还演示了 umask 的坑：`open(..., 0077)` 被进程 umask 0022 剪成 0055，所以代码里显式 `chmod 0077` 保证实验前提——一个 demo 踩两个坑，都是本节的正课。）

**特权规则**：euid=0（root） bypass 大部分检查，但**执行权限例外**——x 位一位都不置时 root 也不能执行。

## §15.4.4 `access()`：按 real ID 判定

```c
int access(const char *pathname, int mode);   /* mode: F_OK / R_OK|W_OK|X_OK */
```

为什么需要它：SUID 程序 euid=0，`open()` 按有效 ID 判——root 全通；但交互用户问的是"**我**有没有权限"，要按 real ID 判。`access()` 就是给 SUID 程序用的。

mode=0000 的四连测（实测）：

```text
== ② mode=0000 时 access() 四连测 ==
  access(..., F_OK) =  0  允许      ← F_OK 只问存在
  access(..., R_OK) = -1  Permission denied
  access(..., W_OK) = -1  Permission denied
  access(..., X_OK) = -1  Permission denied
```

⚠️ `access()` 的 **TOCTOU 缺陷**：检查与真正 `open` 之间权限可被对手换掉。原子替代：直接 `open` 看返回码（SUID 程序则临时 `seteuid(real uid)` 再 `open`）。

**faccessat(AT_EACCESS)**：显式选"按有效 ID"——把两种语义装进同一个接口。

## §15.4.5 SUID / SGID / Sticky

| 位 | 文件 | 目录 |
|----|------|------|
| SUID (04000) | 执行时 euid=文件属主 | 无意义 |
| SGID (02000) | 执行时 egid=文件属组 | 新文件**继承目录属组**（两派共同点） |
| Sticky (01000) | 历史遗留（伪换出） | **/tmp 模式**：目录内对象只有属主能删 |

实测（[`code/c15_5_chmod_umask.c`](../code/c15_5_chmod_umask.c)）：`chmod 4755` → `mode=4755`、`chmod 1777` 目录 → `mode=1777`，均无需特权。SUID 的安全性完整的讨论在 Ch38（特权程序）与 Ch9（凭证切换）。

## §15.4.6 `umask()`：创建掩码

```c
mode_t umask(mode_t mask);   /* 永远"设置并返回旧值"——没有只读形态 */
```

实测三连（`umask 022`）：

```text
  open(0666) 实得            mode=0644     ← 666 & ~022
  chmod(0666) 之后           mode=0666     ← chmod 不受 umask 管！
  mkdir(0777) 实得           mode=0755     ← 777 & ~022
```

三条规则：**掩码取反再与**；只作用于 `open/mkdir` 等**创建类**调用；**chmod 满额通过**。

原书 Listing 15-5 [`code/t_umask.c`](../code/t_umask.c) 实测输出（macOS）：

```text
Requested file perms: rw-rw----
Process umask:        ----wx-wx
Actual file perms:    rw-r-----
Requested dir. perms: rwxrwxrwx
Process umask:        ----wx-wx
Actual dir. perms:    rwxr--r--
```

"怎么只读 umask 不留副作用"是习题 15-5（umask(0)+恢复的竞态、fork 子进程探测、Linux 读 `/proc/self/status` 的 `Umask` 行）——实现见 [`code/ex15_5_umask_peek.c`](../code/ex15_5_umask_peek.c)。

## §15.4.7 `chmod()` / `fchmod()`

```c
int chmod(const char *pathname, mode_t mode);
int fchmod(int fd, mode_t mode);
```

- `chmod` 的 mode 是**绝对赋值**（区别于 `chmod(1)` 的符号模式 a+rX 等，习题 15-6 自行实现，[`code/ex15_6_chmod_arX.c`](../code/ex15_6_chmod_arX.c)）；
- **文件属主或特权者**才能 chmod——"能写文件"不能 chmod；
- chmod 更新 ctime，不动 atime/mtime（15.2 实测）；
- Linux 对**只读文件系统上的可执行文件**拒绝清 SUID/SGID（防 root 用户启动被篡改的 SUID 程序）。

## 目录三权的实测（本节最反直觉的一段）

```text
== ④ 目录的 r=「列名字」 x=「穿越/打开」 ==
  dir=r-- 时 open(dir/file):        Permission denied   ← 有 r 没 x，穿越不了
  dir=r-- 时 open(dir):             OK                  ← 列目录（读目录数据）可以
  dir=-wx 时 open(dir/file):        OK                  ← 有 x 没 r，知道名字就能开
  → 只有 x 没有 r：摸得到里面的文件，但 ls 列不出目录内容
```

习题 15-1 的程序化验证（[`code/ex15_1_perms.c`](../code/ex15_1_perms.c)）：属主 0 位被拒、无 x 不能穿越、有 w 没 r 能建文件不能列目录——三条论断全部实测为真。

## 常见坑

| 坑 | 正解 |
|----|------|
| "属主没有 r，但其他有 r，属主也能读" | 不能。三选一算法，属主只看属主位（实测 mode=0077 拒读） |
| SUID 程序用 `open()` 检查用户权限 | 按有效 ID 判，root 永远通过。用 `access()`/`faccessat(AT_EACCESS)` 区分语义 |
| `access()` 通过后再 `open()` | TOCTOU 窗口。直接 `open` 看错误码，或 seteuid 切换后 open |
| `umask()` 当"读"用后不恢复 | `umask(0)` 把掩码清成 0，窗口内创建的文件权限放大。用 ex15_5 的子进程/proc 方法 |
| `chmod(1)` 的 `a+rX` 直接映射到 `chmod(2)` | `chmod(2)` 是绝对赋值；X 逻辑要自己实现（见 ex15_6） |
| 目录给 w 却不给 x | 创建了文件也进不去/改不了属性；w 与 x 是两件事 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 服务目录最小权限 | 数据目录 `0750` 属主属组制；日志目录 `0730`（组可写不可列）——r/w/x 分工直接落地 |
| SUID 工具面收敛 | 列出系统 SUID 文件（`find / -perm -4000`），HFT 主机上应趋近于零 |
| umask 策略 | 守护进程启动显式 `umask(027)`：默认组可读、其他全盲——比事后 chmod 便宜且无窗口 |
| 秒级攻防 | 权限检查与 open 必须合并成一步（fstat 校验 `(dev,ino)`），杜绝 access-then-open |
| 嵌入式多租户 | sticky 目录做设备间交换区（/tmp 语义）；SGID 目录做产线数据共享 |

<summary>代码自测（Q&A）</summary>

**Q1：mode=0077 的文件，属主为什么读不了？**
A：判定算法先看 euid==属主 → 选属主三元组 `---` → 拒。其他位的 rwx 对属主**永远不生效**——switch 语义。

**Q2：`access(F_OK)` 在 mode=0000 时为什么还允许？**
A：F_OK 只问"路径可达 + 存在"，不涉及权限位。四连测实测 F_OK=0、R/W/X 全拒。

**Q3：`umask 022` 下 `chmod(0666)` 为什么结果是 0666？**
A：umask 只参与**创建**（open/mkdir 的 mode 参数），chmod 是事后绝对赋值，满额通过。实测两者差异清晰可见。

**Q4：SUID 程序里 `access(R_OK)` 和 `open(O_RDONLY)` 为什么可能给出相反答案？**
A：access 按 real ID（发起者），open 按有效 ID（SUID 后的 euid）。两者回答的是两个不同的问题——这正是 access 存在的理由。

**Q5：目录 sticky 位 1777 意味着什么？**
A：任何人可创建/删除**自己的**文件，但不能删别人的（/tmp 就是它）。sticky 对普通文件在现代系统只是历史语义。

**Q6：`chmod(2)` 为什么没有 `a+rX`？**
A：它只有绝对赋值。符号模式是 `chmod(1)` 在用户态解析的；X 语义（目录或有任一 x 才加 x）需要先 stat 再算，ex15_6 给出了完整实现。

**Q7：怎么安全地"看一眼"umask？**
A：单线程：`umask(0)` 后立即恢复；多线程：fork 子进程探测或读 `/proc/self/status` 的 Umask 行（Linux 4.7+）。umask(0)+恢复在多线程下有真实竞态窗口。

</details>
