## 18-1 为什么能「覆盖」正在执行的程序？

**题面（转述）**：§4.3.2 说过「文件正在被执行时不能写打开（`ETXTBSY`）」。但从 shell 里却可以：编译出 `longrunner`、后台跑起来、修改源码、再次 `cc -o longrunner longrunner.c`——最后这条成功。为什么？（提示：用 `ls -li` 看两次编译后的 inode。）

**答案（两部分，程序四段逐条钉住）**：

1. **两次编译产出的是两个不同 inode**。`cc` 从不写老文件：它把新二进制写到临时文件，再 `rename` 覆盖名字。老 inode 的 `nlink` 归零，但**运行中进程的 fd（准确说是 exec 时建立的文本映射引用）把它吊住**，直到进程退出才真正释放——正是 §18.3 的释放条件。
2. **直接写打开正在执行的文件才被拒**（Linux `ETXTBSY`），而 rename 换目录项不算「写文件」。

**实测输出**（macOS，子进程探活确认有效）：

```text
== ⓪ 陷阱预热：为什么长跑程序不能「拷」系统的 sleep ==
  cp /bin/sleep 的副本 被信号杀死：SIG 9（rc=137 = 128+9）
  → 平台签名二进制离开原位置即被 AMFI/taskgated 干掉。
     若用它当长跑程序，子进程秒退 → 后面所有结论都是假的。
  ✔ 正解：长跑程序拷**自己编译**的二进制（ad-hoc 签名可任意搬）。

== ① 待测对象 ==
  子进程 pid=7022 正在执行 /tmp/ex18_1_longrunner（inode=2278094）
  探活：仍在运行 ✔
== ② 直接以写方式打开「正在执行」的二进制 ==
  open(PROG, O_WRONLY) = 3 errno=0(未置位)
  → ⚠️ 本机 macOS(APFS) **不 enforce ETXTBSY**：正在执行的二进制
     竟可被写打开（危险！）。Linux 上是 ETXTBSY(16)。
== ③ cc 的「覆盖」：建新 inode + rename，老 inode 被 fd 吊住 ==
  rename(.new → 老名字) = 0 
  覆盖后 PROG 的 inode = 2278099  → 已换成新 inode ✔
  老 inode 2278094 呢？  再次探活：仍在运行 ✔
```

**两个额外钉住的点**：

- ⚠️ **macOS(APFS) 不 enforce ETXTBSY**：正在执行的二进制可以被 `O_WRONLY` 打开（实测确认子进程真的在跑）。Linux 上是 `ETXTBSY(16)`。**跨平台部署要单独验证这条**。
- ⚠️ **踩坑自证**：第一版 demo 用 `cp /bin/sleep /tmp/prog` 造长跑程序，结果子进程**瞬间 SIGKILL**（rc=137 = 128+9）——macOS 的代码签名强制拒绝「离开原位置的平台二进制」。那样测出的「open 成功」只证明「打开了一个没在运行的文件」，结论完全无效。**教训：做「正在运行的进程」类实验，必须先确认进程真的活着**（`waitpid(WNOHANG)` 探活），且长跑程序要用自编译二进制。

## 18-2 为什么 `chmod` 会失败？

**题面（转述）**：TLPI 给出一段代码：`mkdir("test")` → 在 `test/` 里建 `myfile` → `symlink("myfile", "../mylink")` → `chmod("../mylink", S_IRUSR)`。最后一步失败。为什么？

**官方解**：[`code/bad_symlink.c`](../code/bad_symlink.c)（TLPI dist 逐字镜像）。

**答案**：符号链接的目标 `"myfile"` 是**相对串**，解析时以**链接所在目录**（`../mylink` 所在的父目录）为基准——那里没有 `myfile`（它在 `test/` 里）。且 `symlink()` 本身返回 0（创建不检查目标），错误推迟到 `chmod` 才爆：

```text
（本机实测输出）
  chmod: No such file or directory
```

**关联**：[18.2 符号链接](18.2-symbolic-soft-links.md)（相对目标的解析基准）。

## 18-3 实现 realpath()

**题面（转述）**：实现 `realpath()`——把路径解析为无符号链接、无 `.`/`..`、无多余斜杠的绝对路径。

**实现**：[`code/ex18_3_realpath.c`](../code/ex18_3_realpath.c)（教学版：逐组件 `lstat` + `readlink` 展开 + 栈式 `..` 处理，链接计数上限 40 与内核对齐；诚实声明不含逐级权限检查）。

**对拍实测**（与系统库逐字节比）：

```text
输入: /etc/../etc/hosts
自实现: /private/etc/hosts
系统库: /private/etc/hosts
→ 一致 ✔
--
输入: /tmp/./tlpi_nonexist_zzz
自实现: /private/tmp/tlpi_nonexist_zzz
系统库: 失败（No such file or directory）——常见于末组件不存在的情况差异
--
输入: /usr/lib   /   → 均一致 ✔
```

**本题的教学含金量**：`/etc/../etc/hosts` 这个用例**只有**「逐级 lstat」才能答对——`/etc` 是符号链接，`..` 的物理父目录是 `/private` 不是 `/`。字符串消 `..` 的做法会给出 `/etc/hosts`（错）。另外「末组件不存在」的语义两平台不同（自实现按 POSIX 允许成功，macOS 库报 `ENOENT`）——跨平台别依赖这个分支。

详见 [18.13](18.13-resolving-a-pathname-realpath.md)。

## 18-4 用 readdir_r 改写 Listing 18-2

**题面（转述）**：把 Listing 18-2 改成可重入版本，用 `readdir_r` 替代 `readdir`。

**官方解**：[`code/list_files_readdir_r.c`](../code/list_files_readdir_r.c)（TLPI dist 逐字镜像，本机实测可编译运行）。

**但要注意时效**：`readdir_r` 在 POSIX.1-2008 之后**已废弃**（glibc 手册明说）。原因：① 缓冲大小要用 `offsetof(struct dirent, d_name) + pathconf(_PC_NAME_MAX) + 1` 反人类地算；② 返回值语义与 `errno` 混淆。**现代正解是每个线程独立 `opendir`**，或对共享 `DIR` 加锁。本题的价值在理解「为什么 `readdir` 不可重入」（静态内部缓冲），而不在于真的用 `readdir_r`。

详见 [18.8](18.8-reading-directories-opendir-and-readdir.md)。

## 18-9 「记住老目录」哪种方案高效？

**题面（转述）**：§18.10 给了两种回到老 cwd 的方法（`fchdir` vs `getcwd`+`chdir`）。反复操作时哪种更高效？为什么？写程序验证。

**答案与实测**：**fd 方案（`open(".")` + `fchdir`）**。三层理由 + 实测：

1. **省一次完整路径解析**：`chdir(buf)` 要从 `/` 逐级 namei；`fchdir(fd)` 只是从 fd 拿到 inode 引用，无解析。
2. **免疫路径变化**：老目录被改名/移动后，字符串方案 `chdir(老路径)` 失败，fd 方案照常回去（fd 绑定 inode 不绑定路径）——[18.10 实测](18.10-the-current-working-directory-of-a-proce.md)。
3. **无 `PATH_MAX` 截断风险**、无额外内存。

实测输出（[`code/c18_4_cwd.c`](../code/c18_4_cwd.c)）：

```text
== ③ fchdir + 目录 fd：零字符串开销地「记住老目录」==
  chdir(/) 后 cwd = /
  fchdir(old_fd) 回到 = /Users/a0000/WorkBuddy/.../chapter-18-directories-links（无需字符串、无路径重解析）
```

严格基准测试（微秒级差值）未做——本机 APFS 上差异会被符号链接解析与文件系统缓存噪声淹没；结论由「解析次数对比」这一结构性证据支撑，Pi5 复测清单可补一条 `clock_gettime` 计时版本。

<summary>代码自测（Q&A）</summary>

**Q1：18-1 里「cc 的覆盖」和「直接写打开」的本质区别是什么？**
A：前者是**目录表操作**（rename 换目录项指向新 inode），后者是**inode 写操作**（要真的改老 inode 的数据）。内核只对后者施加 ETXTBSY；目录表层面没有任何「这个文件在跑」的概念。所以 rename 永远能成功。

**Q2：为什么 macOS 的签名机制会 SIGKILL 拷贝的 /bin/sleep？**
A：`/bin/sleep` 带 Apple 平台签名（`Platform identifier=26`），系统强制它只能从受信位置运行；拷到 `/tmp` 后签名校验语境失效，AMFI 直接 SIGKILL。自己 clang 编译的是 ad-hoc 签名，无位置约束。**这是做系统实验时的 macOS 专属陷阱**，Linux 无此机制。

**Q3：18-3 的自实现与系统库最可能在哪类输入上分歧？**
A：① 末组件不存在（POSIX 允许成功、macOS 实测报 `ENOENT`）；② 路径中某级目录无 `x` 权限（教学版没做逐级权限检查）；③ 超长路径（教学版按 `PATH_MAX` 截断语义，实际 realpath 契约是报错）。教学版的边界都写在源码头注释里。

**Q4：18-7 的统计为什么必须 `FTW_PHYS`？不加会怎样？**
A：不加时指向目录的链接会被当作目录下钻，其子树的每个文件都会被**再数一次**（实测 inode 相同、条目重复）。`/etc` 这类含 `/etc/periodic -> ...` 链接的目录立刻就能看出重复计数。

**Q5：18-9 的两种方案，除了效率还有什么区别值得记？**
A：失败模式不同。字符串方案在「老目录被改名/删除」时**回不去**（`chdir` 失败）；fd 方案在同样情况下**照常回去**（fd 绑定 inode）。对一个长期运行、目录结构可能变化的服务，后者是唯一正确的选择——效率反而是次要的。

**Q6：这 9 道题里哪道最有工程价值？**
A：18-1。它把 §18.3（unlink 语义）、§18.4（rename 原子替换）和真实部署（灰度发布、热更新不掉数据）串成一条线，且顺带钉出了 macOS 签名与 ETXTBSY 两个跨平台坑。其次是 18-3（`..` 的物理语义是安全代码的地基）。
