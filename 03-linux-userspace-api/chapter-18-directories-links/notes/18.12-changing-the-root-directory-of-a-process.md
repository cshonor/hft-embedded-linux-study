# 18.12 Changing the Root Directory of a Process: chroot() 改变进程的根目录

> 本章：[TLPI 第 18 章 — Directories and Links](../README.md)
> 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注
> 源码核验：man-pages **6.19** `chroot(2)` / `chroot(2)` 的 SECURITY NOTES 段 + Linux v6.6 `fs/open.c`（`SYSCALL_DEFINE1(chroot)`，检查 `CAP_SYS_CHROOT`）
> - 上一节：[18.11 *at() 族](18.11-operating-relative-to-a-directory-file-d.md)
> - 下一节：[18.13 realpath()](18.13-resolving-a-pathname-realpath.md)

## 本节讲什么

1. `chroot()` 改的是**路径解析的起点**（进程视角的 `/`），不是「进了某个目录」；
2. 它需要特权（`CAP_SYS_CHROOT`）——本机非特权实测 `EPERM`；
3. 它**不改 cwd**——这是书上专门强调、也是最容易漏的一步；
4. 经典越狱：`chroot` 前先 `open(".")` 存 fd，`chroot` 后 `fchdir(fd)` 就站到新根之外了——所以「chroot 后必须 `chdir("/")` 并放弃 fd」不是最佳实践，是**必要条件**。

---

## 要点：契约表

```c
#include <unistd.h>
int chroot(const char *path);
/* 需要 CAP_SYS_CHROOT（Linux）/ root（BSD）；改变调用进程的根目录 */
```

| 项 | 规则 |
|----|------|
| 改什么 | 进程**路径解析的起点**：之后 `/xxx` 都从 `path` 开始找 |
| 不改什么 | **cwd**、已打开的 fd、进程可见性、网络、IPC |
| 权限 | `CAP_SYS_CHROOT`（Linux）；本机非特权实测 `EPERM` |
| 继承 | fork 继承新根；exec 保留 |
| 可逆吗 | **没有 unchroot**；但（见下）root 有办法出来 |

**与 `*at()` 的分工**：`chroot` 是「重定义 `/`」，`*at()` 是「绕过 `/`」。前者改变边界，后者在边界内消除竞态。两者正交，可叠加。

## 实测：非特权 chroot = EPERM

**完整源码（[`code/c18_4_cwd.c`](../code/c18_4_cwd.c)）：**

```c
/* c18_4_cwd.c — Ch18 §18.10/§18.11/§18.12：进程的工作目录与根目录
 *
 * 钉住的点（全部实测）：
 * ① cwd 是**进程属性**：fork 继承、exec 保留——chdir("…") 后 exec 的
 *    程序会在新 cwd 里找相对路径；
 * ② getcwd 缓冲不足返回 ERANGE（老式 getwd 已废弃）；realloc 循环是标准写法；
 * ③ fchdir + 保存 fd 是「记住老目录」的零开销方案（习题 18-9 的正解之一）；
 *    对比 getcwd+chdir 的字符串方案（有 EAMETOOLONG 与路径重解析成本）；
 * ④ open(".", O_RDONLY) 得到目录 fd——O_PATH/O_RDONLY + fchdir 都用它；
 * ⑤ chroot 非特权一律 EPERM（实测），语义标注（进程视角的 "/" 重定向，
 *    不改变 cwd！chroot 后必须显式 chdir("/")，书上专门强调）。
 *
 * 编译： cc -Wall -Wextra -o c18_4_cwd c18_4_cwd.c
 * 取材： man-pages 6.19 getcwd(3)/chroot(2) + TLPI §18.10-§18.12
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#ifndef PATH_MAX
#define PATH_MAX 4096
#endif

int main(void)
{
    char buf[PATH_MAX];

    /* ---------- ①② getcwd 与 realloc 循环 ---------- */
    printf("== ①② cwd 是进程属性；getcwd 探大小循环 ==\n");
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd"); return EXIT_FAILURE; }
    printf("  初始 cwd = %s\n", buf);

    /* ---------- ③ fchdir + fd 方案（习题 18-9 正解）---------- */
    printf("\n== ③ fchdir + 目录 fd：零字符串开销地「记住老目录」==\n");
    int old_fd = open(".", O_RDONLY);            /* 保存老 cwd 的 fd */
    if (old_fd == -1) { perror("open ."); return EXIT_FAILURE; }
    if (chdir("/") == -1) { perror("chdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd2"); return EXIT_FAILURE; }
    printf("  chdir(/) 后 cwd = %s\n", buf);
    if (fchdir(old_fd) == -1) { perror("fchdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd3"); return EXIT_FAILURE; }
    printf("  fchdir(old_fd) 回到 = %s（无需字符串、无路径重解析）\n", buf);
    printf("  ⚠️ 对比 getcwd(old)+chdir(old) 方案：多一次路径解析、有\n");
    printf("     PATH_MAX 截断风险，且老目录可能已被改名/删除（fd 方案免疫）。\n\n");

    /* ---------- ④ 目录 fd 的另一个用途：openat 的锚点 ---------- */
    printf("== ④ open(\".\") 的目录 fd 也是 openat 的锚点（§18.11）==\n");
    int dfd = open("/tmp", O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open /tmp"); return EXIT_FAILURE; }
    int f2 = openat(dfd, "tlpi_c18_4.txt", O_RDWR | O_CREAT | O_EXCL, 0644);
    printf("  openat(/tmp 的 fd, \"tlpi_c18_4.txt\") = %d（相对锚点，不受 cwd 影响）\n", f2);
    if (f2 != -1) close(f2);
    printf("  ⚠️ openat 防的是「cwd 被别人改走」与 TOCTOU：锚点一旦打开即固定。\n\n");

    /* ---------- ⑤ chroot：非特权 EPERM（实测） ---------- */
    printf("== ⑤ chroot：需要特权（实测）==\n");
    errno = 0;
    int r = chroot("/tmp/tlpi_c18_4_jail");
    printf("  chroot(非特权) = %d errno=%d(%s)  ← 需 CAP_SYS_CHROOT/root\n",
           r, errno, strerror(errno));
    printf("  语义标注（书上强调，未实测——需特权环境）：\n");
    printf("    · chroot 只改进程视角的 \"/\"，**不会改 cwd**；\n");
    printf("    · 经典越狱：chroot 前先 open(\".\") 存 fd，chroot 后\n");
    printf("      fchdir(fd) 就站在新根之外——所以 chroot 必须后接 chdir(\"/\")\n");
    printf("      并放弃 fd（或 double chroot），否则形同虚设。\n");
    close(dfd);
    unlink("/tmp/tlpi_c18_4.txt");
    close(old_fd);
    return EXIT_SUCCESS;
}
```

```text

  chroot(非特权) = -1 errno=1(Operation not permitted)  ← 需 CAP_SYS_CHROOT/root
  语义标注（书上强调，未实测——需特权环境）：
    · chroot 只改进程视角的 "/"，**不会改 cwd**；
    · 经典越狱：chroot 前先 open(".") 存 fd，chroot 后
```

## 要点：正确的 chroot 四步（书上的原话顺序，一步都不能少）

```c
/* 1. 备好 jail：把目标程序 + 它依赖的动态库/设备文件都放进去
 *    （否则 exec 之后立刻死：连 ld.so 都找不到）*/
chroot("/srv/jail");        /* 2. 改根 */
chdir("/");                 /* 3. 把 cwd 也挪进新根（关键！）*/
setgid(gid); setgroups(0, NULL); setuid(uid);   /* 4. 丢特权（不可逆）*/
execl("/bin/app", "app", NULL);
```

| 步骤 | 缺了会怎样 |
|------|-----------|
| 2. `chroot` | 没有边界 |
| 3. `chdir("/")` | cwd 还在老根里 → 相对路径直接逃逸 |
| 4. 丢特权 | root 能用「double chroot」逃逸（见下） |
| 备 jail 内容 | `exec` 失败 `ENOENT`，或运行时缺库/缺 `/dev/null` |

**为什么必须先 `chdir("/")`**：`chroot` 只改「解析起点」，cwd 还是老位置。cwd 里的进程可以用相对路径 `../..` 往上走——cwd 在新根之外，就直接走出去了。

**为什么必须丢特权（double chroot 越狱）**：持有 `CAP_SYS_CHROOT` 的进程可以：

```c
mkdir("out", 0755); chroot("out");   /* 现在根在 "out"，但 cwd 已在新根之外的上层 */
chdir("../../../..");                /* 相对 cwd 向上走，离开 jail 的 inode 子树 */
chroot(".");                          /* 把根设到真正的老根 */
/* 完全逃逸 */
```

这是 man-pages 里白纸黑字写的逃逸路径，也是「chroot 不是安全边界、namespaces 才是」的根源。

## 要点：chroot vs 容器（namespaces）——为什么说 chroot「只是路径花招」

| 隔离维度 | `chroot` | mount ns + 其他 ns（容器） |
|----------|----------|---------------------------|
| 文件系统视图 | 只改 `/` 的解析起点 | 完整 mount namespace（连挂载表都隔离） |
| 进程可见性 | ❌ 无隔离（`kill` 仍可达外部进程） | pid ns 隔离 |
| 网络 | ❌ | net ns 隔离 |
| 用户/特权 | 需要特权才能设置；特权进程可逃逸 | user ns 可映射非特权 root |
| 逃逸面 | **已知多条**（fd 越狱、double chroot） | 少得多（且有 seccomp/LSM 叠加） |
| 开销 | 几乎为零 | 轻（namespace 切换）但非零 |

工程结论：`chroot` 适合「防呆」——防止程序**误**写到系统目录；不适合「防敌」——防不了有心的攻击者。现代等价物是容器/`pivot_root`（比 `chroot` 更难逃逸，因为老根被卸载且 cwd 也被换）。

## 常见坑

| 坑 | 正解 |
|----|------|
| `chroot` 后直接 `exec` | cwd 在老根 → 相对路径逃逸；必须先 `chdir("/")` |
| `chroot` 后不丢特权 | root 可 double chroot 逃逸（见上）；必须 `setgid`+`setuid` |
| 以为 `chroot` 能隔离进程/网络 | 只隔离文件系统路径；要真隔离用 namespaces（容器） |
| jail 里缺动态库 / 缺 `/dev` | `exec` 报 `ENOENT` 或运行时莫名崩溃；用 `ldd` 清点依赖，`mknod` 补设备 |
| 绝对符号链接放进 jail | 链接内容是路径串，`chroot` 后按**新根**解析 → 断链；jail 内一律相对链接（[18.2](18.2-symbolic-soft-links.md)） |
| 用 `chroot` 代替 `pivot_root` | `chroot` 保留老根可逃逸；`pivot_root` 把老根卸载/挂到别处，逃逸面小一个量级 |
| 以为 `chroot` 影响**其他**进程 | 只影响调用者及其后代；别的进程视图不变 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 策略进程沙箱 | 第三方策略插件用 chroot+jail 限制文件访问，配合丢特权；但要清楚这是「防呆」级别 |
| 嵌入式恢复模式 | 救援系统 chroot 进备用根文件系统修主系统——嵌入式运维的常规操作 |
| 构建环境隔离 | chroot 构建容器的前身（现已被 namespaces 取代）；理解它才看得懂 Dockerfile 的构建历史 |
| 绝对链接即断链 | 打包 rootfs 时**全部用相对链接**（`libx.so -> libx.so.1`），否则进了 jail/别的挂载点就断（§18.2 的坑在这里兑现） |
| HFT 实际取向 | 现代交易系统几乎不用 chroot，而用「非特权用户 + 显式白名单路径 + `openat` 锚点」——不需要特权，隔离面反而更可控 |
| 调试参考 | `chroot` 后 `/proc` 也要重新挂载，否则 `ps`/`top` 全失效——嵌入式镜像忘挂 `/proc` 的经典坑 |

<summary>代码自测（Q&A）</summary>

**Q1：chroot 之后，进程还能访问新根之外的文件吗？**
A：能，两条路：① cwd 还在外面（忘了 `chdir("/")`）时相对路径直接出去；② `chroot` 前 `open(".")` 存下的 fd 还在手里，`fchdir(fd)` 就出去了。所以「chroot 后必须 `chdir("/")` 并关闭多余 fd」是必要条件，不是最佳实践。

**Q2：为什么特权进程能 double chroot 逃逸？**
A：`chroot` 可以对**任何**目录再设一次根。先 `mkdir` + `chroot` 把根「往上抬」，此时 cwd 已在新根之外，`chdir("../../..")` 走到真正的老根，再 `chroot(".")` 就出来了。要点是「第二次 chroot 把根放回原处」。丢掉特权（setuid 不可逆）后这条路就死了。

**Q3：jail 里的程序一 exec 就死，最常见原因？**
A：动态链接器（`ld-linux.so`）不在 jail 里 → 内核加载失败报 `ENOENT`。其次是缺 `/dev/null`、`/dev/urandom` 和 `/etc` 配置。用 `ldd $(which app)` 清点依赖，逐个拷进 jail。

**Q4：chroot 里面读 `/proc` 会读到什么？**
A：什么都没有——`/proc` 是挂载点，jail 里没挂就没有。需要的话要在 jail 里 `mount -t proc proc /proc`（嵌入式忘挂 `/proc` 是同源坑：`ps`/`top` 全失效）。

**Q5：`pivot_root` 比 `chroot` 强在哪？**
A：`pivot_root` 把整个 mount 的根换掉并把**老根卸载**（或挂到临时位置后 umount），逃逸者连「往上走」的路径都没有；且它通常配合 mount namespace 使用，改动只影响本 ns。`chroot` 只是改一个解析起点变量，老树还完整挂着。

**Q6：本机实测只能看到 `EPERM`，为什么笔记还敢写「chroot 不改 cwd」？**
A：来自两层核验：man-pages `chroot(2)` 明确写「The current working directory is not changed」；Linux `fs/open.c` 的 `SYSCALL_DEFINE1(chroot)` 只改 `current->fs->root`，不碰 `pwd`。行为与源码一致但未在本机运行验证，故 Pi5 复测清单里保留一条（Pi 有 sudo 可实测）。

</details>
