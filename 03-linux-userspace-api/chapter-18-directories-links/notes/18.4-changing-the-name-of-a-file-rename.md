# 18.4 Changing the Name of a File: rename() 改变文件的名字

## 本节讲什么

`rename()` 是全章**唯一**带「原子替换」语义的接口，也是「可靠写入」模式的根：

1. 对已存在的目标文件：**原子替换**，任何时刻路径都指向一个完整的老文件或完整的新文件；
2. 对目录有一套独立规则（目标必须空、不能移进自己的子树、不能改 `..`）；
3. 它**不换 inode**——换的是目录项，所以文件时间戳/数据都不动；
4. 同一文件系统内 O(1)（只改目录表）；跨 FS 直接 `EXDEV`，不存在「自动帮你复制」。

## 要点：契约表

```c
#include <stdio.h>          /* 注意：stdio.h，不是 unistd.h */
int rename(const char *oldpath, const char *newpath);
#include <fcntl.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, ..., unsigned int flags);  /* Linux 3.15+ 专有 */
```

| `oldpath` | `newpath` 不存在 | `newpath` 是文件 | `newpath` 是**空**目录 | `newpath` 是**非空**目录 |
|-----------|------------------|------------------|------------------------|--------------------------|
| 文件 | 改名 | **原子替换** | `EISDIR` | `EISDIR` |
| 目录 | 改名 | `ENOTDIR` | **整体搬过去** | `ENOTEMPTY` |

另两条独立规则：`newpath` 不能是 `oldpath` 的**子路径**（`EINVAL`，否则造出不可达的环）；`..` 不能被改名（`EINVAL`）。

## 实测：原子替换与全部目录规则（[`code/c18_2_rename.c`](../code/c18_2_rename.c)）

```text
== ① rename(file, 存在的 file)：原子替换 ==
  rename(a → 已存在的 b)           = 0 
  b 现在的内容: "NEW CONTENT"（b 的旧内容被整体替换，无中间态）
  ⚠️ inode=2277517 未变——rename 换的是目录项不是数据（§18.4）

== safe-write 惯用法 ==
  写配置 → 写到 temp → fsync → rename(temp, 配置) →
  读者永远看到完整旧版或完整新版；崩溃也不会留下半截文件。

== ② 目录规则 ==
  rename(文件 → 目录)              = -1 Is a directory
  rename(目录 → 文件)              = -1 Not a directory
  rename(空 dir1 → 非空 dir2)       = -1 Directory not empty
  rename(非空 dir2 → 空 dir1)       = 0 
  rename(dir1 → dir1/sub 自己的子树) = -1 Invalid argument
  rename(dir1 → dir1/..)               = -1 Invalid argument
```

三个值得停下来的点：

- **inode 未变**（2277517）：替换后 `b` 还是老 `a` 的 inode。也就是说 rename **不搬数据**，只改了两个目录表里的行。这与 §15.2 实测「rename 不动文件时间戳」互相印证。
- **目录四条全部与 Linux 一致**：本机实测的 `EISDIR` / `ENOTDIR` / `ENOTEMPTY` 与 man-pages `rename(2)` 逐条对上（这是本轮升级**专门核对过**的——早前笔记曾怀疑 macOS 与 Linux 在目录覆盖上有差异，实测证伪：**两边语义一致**）。
- **两条 `EINVAL`**：不能把目录移进自己的子树、不能改 `..`。第一条是防止「目录变成自己的后代」，否则 `nftw`、`find`、`..` 链全部失效。

## 要点：safe-write 惯用法（本节的工程价值所在）

```c
/* 1. 写到同目录的临时文件（同 FS 才能原子 rename）*/
int fd = open("/etc/app.conf.tmp", O_WRONLY|O_CREAT|O_TRUNC, 0644);
write(fd, new_conf, len);
fsync(fd);                /* 数据先落盘（掉电才有意义）*/
close(fd);
/* 2. 原子替换——读者要么看到完整旧版，要么看到完整新版 */
rename("/etc/app.conf.tmp", "/etc/app.conf");
```

四个**都必须**的细节，缺一个就可能翻车：

| 细节 | 缺了会怎样 |
|------|-----------|
| 临时文件与目标**同目录** | 跨 FS 时 `rename` 变 `EXDEV`，惯用法直接失效 |
| `fsync(fd)` 在 `rename` 之前 | 掉电后 rename 落盘了、数据没落，目标指向半截文件 |
| 目录也要 `fsync`（严格场景） | 极端掉电顺序下 rename 本身可能没落盘 |
| `chmod`/`chown` 临时文件 | `open(..., 0644)` 受 umask 削减，直接 rename 会把意外权限带入目标 |

## 实测：rename 换 inode 的另一个证据（[`code/ex18_1_txtbsy.c`](../code/ex18_1_txtbsy.c)，习题 18-1）

```text
== ③ cc 的「覆盖」：建新 inode + rename，老 inode 被 fd 吊住 ==
  老 inode 2278094 呢？  再次探活：仍在运行 ✔
  覆盖后 PROG 的 inode = 2278099  → 已换成新 inode ✔
```

完整解释见 [18.16 习题](18.16-exercises.md)：`cc` 之所以能「覆盖」正在运行的程序，正是因为 rename 换的是目录项——**老 inode 被运行中进程的 fd 吊着，数据根本没被碰**。

## 常见坑

| 坑 | 正解 |
|----|------|
| 以为 `rename` 能跨文件系统 | `EXDEV`；「跨 FS 移动」内核不提供原子接口，只能复制+删除（非原子） |
| safe-write 里忘了 `fsync` | 掉电后 rename 落了、数据没落，配置文件变半截——比不写还糟 |
| `rename(dir, dir/sub)` 期望移动 | `EINVAL`：不能把目录放进自己的子树（会造出不可达的环） |
| 用 `rename` 替换**目录**里的文件时忘了目录规则 | 目标目录必须**空**；非空目录不能被覆盖（`ENOTEMPTY`） |
| 以为 rename 会更新文件 mtime | 不会（[15.2 实测](../../chapter-15-file-attributes/notes/15.2-file-timestamps.md)：Linux 不动；macOS 会动 **ctime**——跨平台别当不变量） |
| 多线程下两个线程各 rename 到同一路径 | 结果是「最后一次赢」，但**每次都是原子的**——不会出现半截状态；要有序就加锁或用唯一临时名 |
| 拿 `rename` 当「加锁」原语 | `rename` 不报 `EEXIST`（直接覆盖）；互斥要么 `link()`（会 `EEXIST`）要么 `O_CREAT\|O_EXCL` |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 配置热更新 | 「写 tmp + fsync + rename」是唯一能保证**读者永远看到一致文件**的手法；配合 inotify（Ch19）做无损重载 |
| 行情文件落盘 | 逐 tick 直接写会暴露半截数据；按「整文件写完再 rename」提交，下游 `open` 永远拿到完整版本 |
| 掉电安全 | 嵌入式无 UPS，`fsync`+`rename` 的顺序就是掉电安全协议；顺序错了 journal 也救不回 |
| 日志轮转 | `mv app.log app.log.1` 后**老进程还往旧 inode 写**——轮转工具必须配合「重开 fd」或用 `O_APPEND`+信号，否则磁盘悄悄涨 |
| 原子互斥 | `link()` 的 `EEXIST` 语义可做跨进程锁（比 `rename` 正确，见坑表最后一行） |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：rename 是「原子的」到底指什么？**
A：指**可见性**——任何时刻，`newpath` 要么解析到完整的老文件、要么解析到完整的新文件，绝无「半新半旧」或「名字消失」的中间态。它**不**保证数据已落盘（那是 `fsync` 的事），也不保证并发 rename 的顺序。

**Q2：为什么 `rename(file, dir)` 是 `EISDIR` 而 `rename(dir, file)` 是 `ENOTDIR`？两个不是一回事吗？**
A：内核分两步检查：先看 `oldpath` 的类型能不能覆盖 `newpath` 的类型。文件→目录：目录不能被普通文件覆盖 → `EISDIR`（「newpath 是目录，而你给的是文件」）；目录→文件：目录不能被当文件写 → `ENOTDIR`。实测与 Linux 一致。

**Q3：`rename` 同目录和跨目录有性能差吗？**
A：同一 FS 内都是 O(1)（改几个目录项 + 移动 inode 的 parent 指针），跨目录只多一层目录的修改，量级不变。**真正的分水岭是跨文件系统**（`EXDEV`，必须复制）。

**Q4：safe-write 为什么要先 `fsync(fd)` 再 `rename`？顺序能反吗？**
A：不能反。`rename` 只是把目录项指向新 inode，这个操作自己会被 journal 记下；如果数据块还没落盘，掉电后 journal 回放可能得到「名字指向了新 inode，但新 inode 的数据块是垃圾」。先 `fsync` 保证数据先于名字可见。

**Q5：`renameat2` 的 `RENAME_EXCHANGE` 是什么？**
A：Linux 3.15+ 专有：**原子互换**两个路径（不是覆盖）。可以用来做「双缓冲目录」——但 macOS 没有，跨平台代码要留好降级路径。Pi5 复测清单可补一条实测。

**Q6：用 `rename` 做进程间锁为什么是错的？**
A：`rename` 的语义是「无条件覆盖」——两个进程同时 rename 同一目标，都会成功，锁形同虚设。正确的原子互斥用 `link()`（目标已存在则 `EEXIST`）或 `open(O_CREAT|O_EXCL)`；解锁用 `unlink`。

</details>
