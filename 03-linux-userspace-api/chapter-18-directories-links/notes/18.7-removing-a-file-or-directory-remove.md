## 本节讲什么

TLPI 这一节非常短，但有一个常被误解的点值得单独成节：

1. `remove()` **不是系统调用**——它头文件是 `<stdio.h>`（C 标准，不是 POSIX），实现在 libc 里；
2. 它是一个**分派器**：先判类型 → 目录走 `rmdir()`，其余走 `unlink()`；
3. 因为是先判类型再分派，它对**符号链接**的行为是「删链接本身」（用 `lstat` 判，不跟目标）；
4. 它的存在意义：**屏蔽类型判断**，让「删除这个路径」成为一句话。代价是失败码继承了两个接口的并集。

---

## 要点：三个删除接口对照

| 函数 | 来源 | 头文件 | 普通文件 | 符号链接 | 空目录 | 非空目录 |
|------|------|--------|---------|---------|--------|---------|
| `unlink()` | POSIX | `<unistd.h>` | ✅ | ✅（删链接本身） | ❌ `EISDIR`(Linux)/`EPERM`(macOS) | ❌ |
| `rmdir()` | POSIX | `<unistd.h>` | ❌ `ENOTDIR` | ❌ `ENOTDIR` | ✅ | ❌ `ENOTEMPTY` |
| `remove()` | **C 标准** | `<stdio.h>` | ✅ | ✅ | ✅ | ❌ `ENOTEMPTY` |

> 注意 `remove` 的移植性优势：C 标准保证它在**任何**符合 C 标准的平台（包括 Windows CRT）都存在；而 `unlink`/`rmdir` 是 POSIX 专属。写可移植代码时 `remove` 是唯一「零依赖」选项。

## 实测：分派行为的三个证据（[`code/c18_7_remove.c`](../code/c18_7_remove.c)）

```text
== ① remove() 自动分派 ==
  remove(普通文件)     → unlink 分支 = 0 
  再删一次（已不存在）           = -1 No such file or directory

== ② 空目录走 rmdir 分支 ==
  remove(空目录)       → rmdir 分支 = 0 
  remove(非空目录)     → 继承 ENOTEMPTY = -1 Directory not empty

== ③ 符号链接：remove 删的是链接本身（lstat 不跟目标）==
  remove(指向目录的符号链接)      = 0 
  目标 d 还在？ stat(d) = 0（目录安然无恙，只掉了链接）

== ④ unlink(目录)：Linux=EISDIR / macOS=EPERM（都拒绝，码不同）==
  unlink(目录) = -1 errno=1(Operation not permitted)
  → remove() 存在的意义：屏蔽这层类型判断，给你一个统一入口。
```

三个钉住的点：

- **③ 是最容易被误解的一条**：链接指向的是**目录**，`remove` 成功且返回 0——但目录完好。因为分派用的是 `lstat`（看链接本身，类型是 `S_IFLNK`），走的是 `unlink` 分支。**`remove` 永远不会替你删掉链接背后的目录**。
- **④ 展示了为什么需要统一入口**：`unlink` 拒绝目录这件事两平台都做，但**错误码不同**（Linux `EISDIR`，macOS `EPERM`）。「都拒绝」是共识，「码是什么」不是——可移植代码应该用 `remove`（或先 `lstat` 自己分派），别依赖具体 errno。
- **失败码是并集**：`remove` 可能返回 `ENOENT`（`unlink`/`rmdir` 都会）、`ENOTEMPTY`（只来自 `rmdir`）、`EACCES`（来自写权限）等。写错误处理时按「可能是三种之一」来对待。

## 要点：删除非空目录的正确姿势

`remove`（以及 `unlink`/`rmdir` 任何一个）都**不提供**递归删除。标准做法是 `nftw` + 后序遍历：

```c
#include <ftw.h>
static int rm_cb(const char *path, const struct stat *sb,
                 int typeflag, struct FTW *ftwbuf) {
    return remove(path);           /* FTW_DEPTH 保证到达时子项已删光 */
}
int rm_recursive(const char *dir) {
    return nftw(dir, rm_cb, 64, FTW_DEPTH | FTW_PHYS);
}
```

`FTW_DEPTH`（后序）是**必须**的：先序到达目录时子项还在，`remove` 会 `ENOTEMPTY`。`FTW_PHYS`（不跟随链接）同样是必须的：否则链接指向的**外部**文件会被误删。完整机制见 [18.9 nftw()](18.9-file-tree-walking-nftw.md)（含实测输出）。

## 常见坑

| 坑 | 正解 |
|----|------|
| 以为 `remove` 能删非空目录 | `ENOTEMPTY`；递归删除用 `nftw + FTW_DEPTH`（见上） |
| 以为 `remove(链接)` 会删到目标 | 删的是**链接本身**（分派用 `lstat`）；要删目标先 `realpath`/`readlink` 再处理 |
| `remove` 成功 = 数据立刻腾出磁盘 | 和 `unlink` 一样：`nlink==0` **且**无打开 fd 才释放（[18.3 实测](18.3-creating-and-removing-hard-links-link-an.md)） |
| 跨平台依赖 `unlink(dir)` 的 errno | Linux `EISDIR`、macOS `EPERM`；用 `remove` 或先 `lstat` 分派 |
| 拿 `remove` 删「可能不存在的路径」 | `ENOENT` 是正常返回不是异常；幂等清理要显式容忍它 |
| 在 Windows 上用 `unlink` | 没有；`remove` 是 C 标准、跨平台唯一通吃的删除接口 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 日志清理 | 按日期分片的日志目录，`nftw + FTW_DEPTH|FTW_PHYS` 后序删除；`remove` 做单点删除，失败码统一 |
| 临时文件回收 | UNIX domain socket 文件（如 `/tmp/app.sock`）在崩溃后残留，启动时 `remove()` 幂等清理（容忍 `ENOENT`） |
| 嵌入式 OTA | 旧固件包清理走 `remove`，且必须容忍 `ENOENT`（可能已被删）；掉电后残留半截目录树用后序 nftw 收尾 |
| 符号链接安全 | 清理脚本处理用户提供的路径前，先 `lstat` 判 `S_ISLNK`——`remove` 对链接「只删链接」的特性，既是安全特性也是意外来源 |
| 跨平台部署 | 交易系统的 Windows/Linux 双构建里，`remove` 是唯一两边语义一致的删除入口 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`remove()` 是系统调用吗？**
A：不是。头文件 `<stdio.h>` 表明它是 C 标准库函数（C99 7.21.4.1），libc 内部实现为「判类型 → `unlink` 或 `rmdir`」。所以它有 libc 层开销（一次 `lstat`），但不值得为此优化——目录操作本来就慢。

**Q2：为什么 `remove` 对符号链接的行为是「删链接」而不是「删目标」？**
A：分派依据是 `lstat` 的类型。链接的类型是 `S_IFLNK`，不是 `S_IFDIR`，所以走 `unlink` 分支——`unlink` 对链接本来就是删链接本身。这保证了 `remove` 不会「意外地」删掉链接背后的目录树。

**Q3：`remove` 与 `unlink` 的性能差多少？**
A：多一次 `lstat`。在目录操作（本身就是纳秒~微秒级 syscall）里可忽略；只有在**热路径批量删除几十万文件**时才值得直接用 `unlink` 省一次类型判定。

**Q4：怎么写一个「幂等」的删除？**
A：`if (remove(p) == -1 && errno != ENOENT) /* 真错误 */;`。把 `ENOENT` 当成功处理，重启/重试逻辑就无需「先检查存在」——检查本身有竞态，`remove` 的 `ENOENT` 才是权威答案。

**Q5：递归删除时为什么 `FTW_PHYS` 也是必须的？**
A：没有它，`nftw` 会跟随符号链接**离开这棵树**——回调会对链接指向的外部文件调用 `remove`，把不相关的数据删掉。`FTW_DEPTH|FTW_PHYS` 是递归删除的固定搭配，缺一不可。

**Q6：`remove` 能删一个「正在被写」的文件吗？**
A：能。它调 `unlink`，只摘名字；数据的释放仍受「无打开 fd」约束（§18.3）。正在写的进程继续写，写完 close，数据才消失——这正是临时文件惯用法的基础。

</details>
