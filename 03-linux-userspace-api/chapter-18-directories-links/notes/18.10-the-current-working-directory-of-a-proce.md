# 18.10 The Current Working Directory of a Process 进程的当前工作目录

## 本节讲什么

1. cwd 是**进程属性**：`fork` 继承、`exec` 保留——这是「shell `cd` 不影响子进程」等一切现象的根源；
2. 两种「记住老目录再回去」的方案：`open(".") + fchdir`（fd 方案）vs `getcwd + chdir`（字符串方案）——**fd 方案全面占优**（习题 18-9 的正解）；
3. `getcwd` 的缓冲不足返回 `ERANGE`，标准写法是「从合理大小起步、逐次翻倍重试」；
4. cwd 在内核里就是一个**挂靠的 path 引用**——所以目录被删了进程还活着，但 `getcwd` 就会失败。

---

## 要点：核心 API

```c
#include <unistd.h>
int chdir(const char *path);
int fchdir(int fd);                      /* fd 必须是目录且为 O_RDONLY 打开 */
char *getcwd(char *buf, size_t size);    /* 成功返回 buf；失败 NULL+errno */
```

| 项 | 规则 |
|----|------|
| cwd 归属 | 进程级（`task_struct` → `fs_struct` → `pwd`），**不是线程独立**（同一进程的线程共享 cwd） |
| 继承 | `fork` 复制引用（子进程独立改不影响父）、`exec` 保留 |
| `fchdir` 前提 | 目录 fd；`O_PATH` 打开的 fd 在 Linux 上也可用 |
| `getcwd` 缓冲不足 | `NULL` + `ERANGE`（**老式 `getwd` 已废弃**，别用） |
| cwd 被删后 | 进程还能跑，但 `getcwd` 失败（Linux 上读 `/proc/self/cwd` 得 `(deleted)`） |

## 实测：fchdir 方案 vs 字符串方案

**完整源码（[`code/c18_4_cwd.c`](../code/c18_4_cwd.c)）：**

```c
/* c18_4_cwd.c — Ch18 §18.10/§18.11/§18.12：进程的工作目录与根目录
 *
 * 钉住的点（全部实测）：
 * ① cwd 是**进程属性**：fork 继承、exec 保留——chdir("…") 后 exec 的
 *    程序会在新 cwd 里找相对路径；
 * ② getcwd 缓冲不足返回 ERANGE（老式 getwd 已废弃）；realloc 循环是标准写法；
 * ③ fchdir + 保存 fd 是「记住老目录」的零开销方案（习题 18-9 的正解之一）；
 *    对比 getcwd+chdir 的字符串方案（有 EAMETOOLONG 与路径重解析成本）；
 * ④ open(".", O_RDONLY) 得到目录 fd——O_PATH/O_RDONLY + fchdir 都用它；
 * ⑤ chroot 非特权一律 EPERM（实测），语义标注（进程视角的 "/" 重定向，
 *    不改变 cwd！chroot 后必须显式 chdir("/")，书上专门强调）。
 *
 * 编译： cc -Wall -Wextra -o c18_4_cwd c18_4_cwd.c
 * 取材： man-pages 6.19 getcwd(3)/chroot(2) + TLPI §18.10-§18.12
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#ifndef PATH_MAX
#define PATH_MAX 4096
#endif

int main(void)
{
    char buf[PATH_MAX];

    /* ---------- ①② getcwd 与 realloc 循环 ---------- */
    printf("== ①② cwd 是进程属性；getcwd 探大小循环 ==\n");
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd"); return EXIT_FAILURE; }
    printf("  初始 cwd = %s\n", buf);

    /* ---------- ③ fchdir + fd 方案（习题 18-9 正解）---------- */
    printf("\n== ③ fchdir + 目录 fd：零字符串开销地「记住老目录」==\n");
    int old_fd = open(".", O_RDONLY);            /* 保存老 cwd 的 fd */
    if (old_fd == -1) { perror("open ."); return EXIT_FAILURE; }
    if (chdir("/") == -1) { perror("chdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd2"); return EXIT_FAILURE; }
    printf("  chdir(/) 后 cwd = %s\n", buf);
    if (fchdir(old_fd) == -1) { perror("fchdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd3"); return EXIT_FAILURE; }
    printf("  fchdir(old_fd) 回到 = %s（无需字符串、无路径重解析）\n", buf);
    printf("  ⚠️ 对比 getcwd(old)+chdir(old) 方案：多一次路径解析、有\n");
    printf("     PATH_MAX 截断风险，且老目录可能已被改名/删除（fd 方案免疫）。\n\n");

    /* ---------- ④ 目录 fd 的另一个用途：openat 的锚点 ---------- */
    printf("== ④ open(\".\") 的目录 fd 也是 openat 的锚点（§18.11）==\n");
    int dfd = open("/tmp", O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open /tmp"); return EXIT_FAILURE; }
    int f2 = openat(dfd, "tlpi_c18_4.txt", O_RDWR | O_CREAT | O_EXCL, 0644);
    printf("  openat(/tmp 的 fd, \"tlpi_c18_4.txt\") = %d（相对锚点，不受 cwd 影响）\n", f2);
    if (f2 != -1) close(f2);
    printf("  ⚠️ openat 防的是「cwd 被别人改走」与 TOCTOU：锚点一旦打开即固定。\n\n");

    /* ---------- ⑤ chroot：非特权 EPERM（实测） ---------- */
    printf("== ⑤ chroot：需要特权（实测）==\n");
    errno = 0;
    int r = chroot("/tmp/tlpi_c18_4_jail");
    printf("  chroot(非特权) = %d errno=%d(%s)  ← 需 CAP_SYS_CHROOT/root\n",
           r, errno, strerror(errno));
    printf("  语义标注（书上强调，未实测——需特权环境）：\n");
    printf("    · chroot 只改进程视角的 \"/\"，**不会改 cwd**；\n");
    printf("    · 经典越狱：chroot 前先 open(\".\") 存 fd，chroot 后\n");
    printf("      fchdir(fd) 就站在新根之外——所以 chroot 必须后接 chdir(\"/\")\n");
    printf("      并放弃 fd（或 double chroot），否则形同虚设。\n");
    close(dfd);
    unlink("/tmp/tlpi_c18_4.txt");
    close(old_fd);
    return EXIT_SUCCESS;
}
```

实测输出：

```text
== ①② cwd 是进程属性；getcwd 探大小循环 ==
  初始 cwd = /Users/a0000/WorkBuddy/2026-09-04-17-26-07/hft-embedded-linux-study/03-linux-userspace-api/chapter-18-directories-links

== ③ fchdir + 目录 fd：零字符串开销地「记住老目录」==
  chdir(/) 后 cwd = /
  fchdir(old_fd) 回到 = /Users/a0000/WorkBuddy/2026-09-04-17-26-07/hft-embedded-linux-study/03-linux-userspace-api/chapter-18-directories-links（无需字符串、无路径重解析）
  ⚠️ 对比 getcwd(old)+chdir(old) 方案：多一次路径解析、有
     PATH_MAX 截断风险，且老目录可能已被改名/删除（fd 方案免疫）。
```

demo 里用 `chdir("/")` 让差异可见（macOS 上 `/tmp` 是指向 `/private/tmp` 的符号链接，`chdir("/tmp")` 后 `getcwd` 会显示解析后的 `/private/tmp`——跨平台输出会让人误会）。三种方案对照：

| 方案 | 成本 | 失败模式 | 评价 |
|------|------|---------|------|
| `int fd = open(".", O_RDONLY); ... fchdir(fd); close(fd);` | 3 次 syscall，**零字符串** | 老 fd 失效几乎不可能（除非 fd 泄漏被关） | **首选**（习题 18-9 正解） |
| `getcwd(buf); ... chdir(buf);` | 2 次 syscall + **一次完整路径解析** | `PATH_MAX` 截断、老目录被改名/删除、老目录权限变化 | 次选 |
| `get_current_dir_name()`（GNU） | malloc 分配 | 同上 + 需 free | 便利性选择 |

**为什么 fd 方案免疫**：它记住的是 **inode 引用**，不是「一条路径」。老目录被改名、被移到别处，inode 不变，`fchdir` 照样回去。字符串方案记住的是「一条路怎么走」，路改了就回不去。

## 实测：目录 fd 的另一个身份——openat 的锚点（同上 demo）

```text
== ④ open(".") 的目录 fd 也是 openat 的锚点（§18.11）==
  openat(/tmp 的 fd, "tlpi_c18_4.txt") = 5（相对锚点，不受 cwd 影响）
  ⚠️ openat 防的是「cwd 被别人改走」与 TOCTOU：锚点一旦打开即固定。
```

这正是下一节的主题：**同一个目录 fd，既能 `fchdir` 回去，也能 `openat` 进去**。两者都是「把位置从『一条路径』变成『一个引用』」。

## 要点：为什么多线程进程怕 `chdir`

cwd 是**进程级**的，所以：

1. 一个线程 `chdir`，**所有线程**的相对路径解析基准立刻全变；
2. 另一个线程正在 `open("data/tick.log")`——它解析的 `data/` 已经是别的目录了；
3. 这种 bug 的表现是「偶发读错文件」，几乎无法稳定复现。

正解（按优先级）：

| 方案 | 说明 |
|------|------|
| **进程内禁止 `chdir`** | 规约层面：一律绝对路径或相对「启动锚点 fd」的 `openat` |
| `openat` + 目录 fd（§18.11） | 把「基准」从进程级变成 fd 级，每线程/每模块自己的锚点 |
| 短暂 `chdir` + 立刻恢复 | 仅在确知单线程时可用；fd 方案恢复，别用字符串方案 |

## 常见坑

| 坑 | 正解 |
|----|------|
| 库函数里偷偷 `chdir` 改变全局状态 | 库代码**禁止** `chdir`；需要相对基准就用 `openat` 传目录 fd 进来 |
| `getcwd(buf, 64)` 期望自动扩展 | `ERANGE`；要么 `PATH_MAX` 栈缓冲，要么逐次翻倍重试 |
| 用 `getwd()` / `get_current_dir_name()` 不看移植性 | `getwd` 已废弃（无长度检查）；GNU 扩展在 BSD 不可用；标准解是 `getcwd` |
| 「恢复 cwd」用字符串方案 | 老目录被改名/删除后回不去；fd 方案免疫（本节实测 + 习题 18-9） |
| `chdir("/tmp")` 后 `getcwd` 显示 `/private/tmp` | macOS 上 `/tmp` 是符号链接，`getcwd` 给**解析后**的物理路径；跨平台别对字符串做比较 |
| 以为线程有独立 cwd | 同一进程所有线程共享 `fs_struct`；想隔离就开子进程 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 启动即锁锚点 | `main` 里第一件事 `int anchor = open("/", O_RDONLY|O_DIRECTORY)`（或业务根目录），之后一切相对操作走 `openat(anchor, ...)`——cwd 变成无关变量 |
| 配置加载 | 策略参数按「相对锚点」定位；运维 `cd` 到任何目录重启服务，行为一致（不会因为「从别的目录启动」读错配置） |
| 崩溃诊断 | `getcwd` 结果打进每条日志前缀（或 `/proc/PID/cwd`），排查「为什么读到了别的文件」的第一线索 |
| systemd 服务 | `WorkingDirectory=` 就是启动时替你 `chdir`；理解本节才明白为什么相对路径配置有时灵有时不灵 |
| 嵌入式看门狗 | 工作目录被删（如 tmpfs 清理）后，`getcwd` 失败可作为「环境异常」的早期信号触发自检 |
| fd 泄漏 | `open(".")` 存目录 fd 是常见模式，忘了 `close` 就是一个 fd 泄漏点；进程退出会回收，长跑进程要审计 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：为什么 shell 里 `cd` 之后子 shell 也跟着变，但父 shell 不受子进程 `cd` 影响？**
A：`fork` 时 cwd 引用被**复制**（不是共享）。子进程 `chdir` 只改自己 `fs_struct` 的 `pwd`，父进程的 `pwd` 没变。反过来，同一进程内的线程**共享** `fs_struct`，所以线程间会互相影响——方向别搞反。

**Q2：目录被 rmdir 之后，还在里面的进程会怎样？**
A：进程照常运行（内核里 cwd 还是一个有效的 inode 引用），但 `getcwd` 失败（`ENOENT`）。Linux 上读 `/proc/self/cwd` 会得到 `(deleted)` 后缀。应用若继续用相对路径 `open`，会在一个「幽灵目录」里工作。

**Q3：`fchdir` 需要什么权限？**
A：fd 必须是**目录**且以可搜索方式打开（`O_RDONLY|O_DIRECTORY` 最常见）。Linux 上 `O_PATH` 打开的目录 fd 也能 `fchdir`（这是 `O_PATH` 的少数实际用途之一）。macOS 上 `O_PATH` 不可用。

**Q4：`getcwd` 的「翻倍重试」写法具体怎么做？**
A：从 `PATH_MAX`（或 256）起步，`ERANGE` 时翻倍再试，直到成功或达到上限。另一种更省的是「先 `lstat(".")` 不可行，直接给 `PATH_MAX` 栈缓冲」——大多数系统 `PATH_MAX` 够用；真正会超的是深层递归遍历场景（那时通常已经有目录 fd 可用，不需要 getcwd）。

**Q5：`chdir` 与 `openat` 的性能差？**
A：`chdir` 是 1 次 syscall + 一次路径解析；`openat(dirfd, name)` 是 1 次 syscall + 少量解析（从锚点开始）。多文件操作时 `openat` 全面胜出：不用反复 chdir，也没有全局状态竞争。

**Q6：为什么 demo 里用 `chdir("/")` 而不是 `chdir("/tmp")`？**
A：macOS 上 `/tmp` 是指向 `/private/tmp` 的符号链接，`getcwd` 会返回解析后的物理路径，输出里看不出「真的换了目录」。`chdir("/")` 后 `getcwd` 明确显示 `/`，差异可见。这也是「cwd 显示的是解析后路径」的一个佐证。

</details>
