## 本节讲什么

1. `dirname()`/`basename()` 是**纯字符串操作**——不碰文件系统、不解析符号链接；
2. 它们**可能修改输入字符串**（插 NUL 截断）——所以同一个 `path` 不能喂两次；
3. 一组反直觉的边界规则（`/usr/` → `usr`、`..` → `.`、空串 → `.`）——本节用原书 Listing 18-5 把 TLPI 的整张表**逐行实测**；
4. 原书镜像 `t_dirbasename.c` 本身就示范了正确用法：**先 `strdup` 再喂**。

## 要点：接口与语义表

```c
#include <libgen.h>
char *dirname(char *path);
char *basename(char *path);
```

TLPI 的完整规则表，**本机逐行实测**（[`code/t_dirbasename.c`](../code/t_dirbasename.c)，Listing 18-5）：

```text
$ ./t_dirbasename /usr/lib/libc.so /usr/ usr / . .. "" "a/b/" "///" "/a//b"
/usr/lib/libc.so ==> /usr/lib + libc.so
/usr/             ==> / + usr
usr               ==> . + usr
/                 ==> / + /
.                 ==> . + .
..                ==> . + ..
                  ==> . + .
a/b/              ==> a + b
///               ==> / + /
/a//b             ==> /a + b
```

| 输入 | `dirname` | `basename` | 为什么 |
|------|-----------|------------|--------|
| `/usr/lib/libc.so` | `/usr/lib` | `libc.so` | 平凡切分 |
| `/usr/` | `/` | `usr` | **尾部斜杠忽略**，`/usr` 的目录部分是 `/` |
| `usr` | `.` | `usr` | 无目录部分 → `.`（不是空串！） |
| `/` | `/` | `/` | 唯一 `dirname`==`basename` 的输入 |
| `.` | `.` | `.` | 两者都是「当前」 |
| `..` | `.` | `..` | basename 保留 `..`，dirname 给 `.` |
| `""`（空串） | `.` | `.` | 空串等价 `.` |
| `a/b/` | `a` | `b` | 尾部斜杠忽略 |
| `///` | `/` | `/` | 多个斜杠当一个 |
| `/a//b` | `/a` | `b` | 同上 |

三个最反直觉的点：**尾部斜杠被吃掉**（`/usr/` → `usr`）、**`..` 的 dirname 是 `.`**、**空串两把都给 `.`**。写路径拼接代码时必须把这表刻进脑子——`dirname("usr")` 是 `.` 不是 `""`，拼出来是 `./usr`。

## 要点：两个重大陷阱

### ① 输入会被修改（甚至返回内部指针）

```c
/* ✗ 同一个变量喂两次 —— dirname 先把 '/' 换成 '\0'，basename 看到的已是残串 */
char *p = strdup("/usr/lib/libc.so");
char *d = dirname(p);          /* p 现在是 "/usr/lib"（p[9] 被改成 '\0'）*/
char *b = basename(p);         /* 拿到 "lib"，不是 "libc.so"！ */

/* ✓ 各自 strdup 一份（原书 Listing 18-5 正是这么写的）*/
char *t1 = strdup(argv[j]);
char *t2 = strdup(argv[j]);
printf("%s ==> %s + %s\n", argv[j], dirname(t1), basename(t2));
free(t1); free(t2);
```

实现细节决定陷阱形态：POSIX 版可能返回**静态缓冲**（下次调用覆盖）；GNU/glibc 版**修改输入**。两种都不可重入、不可多线程共享。**跨平台代码一律按「会毁输入 + 会覆盖返回值」假设**。

### ② 不检查文件系统

`dirname("/nonexistent/dir/file")` 照样返回 `/nonexistent/dir`——它们不 `stat`、不解析链接（`/link/file` 的 basename 是 `file`，不管 `/link` 指向哪）。这是**特性不是缺陷**：配置解析、日志命名这类纯文本场景要的就是这个。需要物理事实时用 `realpath`（§18.13）或 `lstat`。

## 要点：什么时候用它们，什么时候自己写

| 需求 | 用什么 |
|------|--------|
| 一次性解析、接受输入被毁 | `dirname`/`basename` + 各自 `strdup`（标准、边界规则齐全） |
| 多线程 / 不能毁输入 | 自己写（十几行，语义可控） |
| 需要与 shell 行为一致（`dirname(1)`/`basename(1)` 命令） | 就是这两个函数（命令是薄封装） |
| 只要「最后一个 `/` 后面那段」且输入是受控的 | `strrchr(path, '/')` 更轻 |

手写版（线程安全、不改输入）：

```c
const char *safe_basename(const char *path) {
    if (!path || !*path) return ".";
    const char *end = path + strlen(path);
    while (end > path && end[-1] == '/') end--;    /* 吃掉尾部斜杠 */
    if (end == path) return "/";                    /* 全是斜杠 */
    const char *start = end;
    while (start > path && start[-1] != '/') start--;
    return start;                                   /* 指向原串内部，无需复制 */
}
```

## 常见坑

| 坑 | 正解 |
|----|------|
| 同一个 `path` 先后喂 `dirname` 和 `basename` | 第一次调用就毁了输入；各自 `strdup` |
| 以为返回值生命周期到程序结束 | 可能是静态缓冲，**下次调用覆盖**；要用就立刻复制 |
| 多线程共用这两个函数 | 静态缓冲竞争；手写线程安全版（见上）或加锁 |
| 以为 `basename("/usr/")` 是 `""` | 尾部斜杠忽略 → `usr`；要「空 basename」语义得自己判 |
| 拿 `dirname`/`basename` 的结果去 `stat` 并以为「解析过链接」 | 纯字符串操作；要物理路径用 `realpath` |
| `dirname("usr")` 期望 `""` | 给 `.`；拼路径要意识到这点（`./usr` 而非 `usr`——两者语义不同但都合法） |
| 处理 Windows 风格路径 `C:\dir\file` | 这些函数只认 `/`；跨平台路径处理用专门的库或自己规范化 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 日志文件命名 | `basename(argv[0])` 生成默认日志名（`myapp.log`），不关心安装路径 |
| 配置解析 | 分离「目录 + 文件名」后目录可配置、文件名固定；注意 `dirname` 可能给 `.`，拼接时别产生 `//` |
| 归档/备份索引 | 用 `basename` 做 key、`dirname` 做分组——纯字符串，快且确定 |
| 多线程服务 | 进程内高并发路径处理**禁用**这两个函数（静态缓冲）；用 `strrchr`/手写版 |
| 嵌入式脚本兼容 | BusyBox 的 `dirname`/`basename` 命令行为与本函数一致（同一套 POSIX 表）；shell 脚本和 C 代码行为对齐 |
| 符号链接免疫 | 因为不解析链接，用于「清单/元数据」处理时结果可复现（`realpath` 的结果会随挂载变化） |

<summary>代码自测（Q&A）</summary>

**Q1：为什么 `dirname` 和 `basename` 不能用同一个输入？**
A：实现要找最后一个 `/` 并把它改成 `'\0'` 来就地切分。`dirname("/usr/lib/libc.so")` 返回 `/usr/lib` 的同时把第 9 个字符改成了 NUL——此时再用同一指针调 `basename`，看到的是 `/usr/lib` 这个残串，得到 `lib`。各自 `strdup` 是唯一正解。

**Q2：`basename("/usr/")` 为什么是 `usr` 而不是空串？**
A：POSIX 规定**尾部的多个斜杠都忽略**。`/usr/` 语义上就是 `/usr`，所以 basename 是 `usr`、dirname 是 `/`。这也是为什么 `///` 两把都给 `/`——斜杠全被吃掉后剩的是根。

**Q3：`basename("..")` 为什么保留 `..` 而 `dirname` 给 `.`？**
A：`..` 本身是一个**名字**（目录项就叫这两个字符），所以 basename 保留它；而它前面没有目录部分，dirname 按规则给 `.`。同理 `.` 的两把都是 `.`。

**Q4：返回的指针指向哪里？能用多久？**
A：三种可能：输入串内部（GNU）、静态缓冲（POSIX 某些实现）、或调用者缓冲。只有「下一次调用前」有效。要用久就 `strdup` 返回值。原书 Listing 18-5 在同一次 `printf` 里用完就 free，是标准姿势。

**Q5：需要线程安全的路径切分怎么办？**
A：三个选择：① 手写（`strrchr` + 边界处理，十几行，不改输入）；② 先 `strdup` 再调 POSIX 版（仍有静态缓冲风险，看实现）；③ 加互斥锁（性能差）。生产代码选 ①。

**Q6：这些函数和 `realpath` 的输出能混用吗？**
A：能，但要清楚它们回答不同的问题：`dirname/basename` 回答「这条**字符串**怎么读」，`realpath` 回答「这个路径**物理上**指向哪」。日志记录用前者（可复现），安全校验用后者（物理事实）。

</details>
