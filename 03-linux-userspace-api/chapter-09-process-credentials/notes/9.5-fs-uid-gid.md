## 本节讲什么

9.2 里那句被反复划线的话是这一节的主角：

> On most UNIX systems, these IDs also determine the permissions when accessing files. **However, Linux uses the filesystem IDs described below for this task.**

fsuid / fsgid 是 **Linux 专有**的一对 ID（`setfsuid(2)` STANDARDS 一节只写 "Linux"）。它有两个反直觉的性质：

1. **平时看不到它**——因为内核保证「euid 一变，fsuid 跟着变」，所以两者几乎永远相等，只有显式调 `setfsuid()` 才会分叉；
2. **它的接口是全 Linux 最糟糕的接口之一**：失败时**不设 errno、不返回错误码**，成功和失败的返回值**一模一样**。man 里专门有 BUGS 一节写这件事。

本节要把这两点都变成可观测的事实。

## 要点

### 一、fsuid 是什么，为什么存在

`setfsuid(2)` DESCRIPTION：

> On Linux, a process has both a filesystem user ID and an effective user ID. **The (Linux-specific) filesystem user ID is used for permissions checking when accessing filesystem objects, while the effective user ID is used for various other kinds of permissions checks** (see `credentials(7)`).
>
> Normally, the value of the process's filesystem user ID is the same as the value of its effective user ID. This is so, because **whenever a process's effective user ID is changed, the kernel also changes the filesystem user ID to be the same as the new value of the effective user ID**. A process can cause the value of its filesystem user ID to diverge from its effective user ID by using `setfsuid()` …

`credentials(7)` 把「分离」这件事说得更完整：

> These IDs, **in conjunction with the supplementary group IDs described below, are used to determine permissions for accessing files**; see `path_resolution(7)` for details. … The filesystem IDs can be made to differ from the effective IDs by calling `setfsuid(2)` and `setfsgid(2)`.

整理成一句话：**Linux 上文件权限检查的输入是三元组 `(fsuid, fsgid, 补充组)`，不是 `(euid, egid, 补充组)`。**

因此 9.6 里 `in_group_p()` 那一行才那么重要——它比的是 **fsgid**：

```c
int in_group_p(kgid_t grp)                              /* kernel/groups.c:229 */
{
    const struct cred *cred = current_cred();
    int retval = 1;

    if (!gid_eq(grp, cred->fsgid))                      /* :234  ← fsgid，不是 egid */
        retval = groups_search(cred->group_info, grp);
    return retval;
}
```

### 二、历史：为什么 Linux 1.2 要有这个东西，以及为什么现在不需要了

`setfsuid(2)` HISTORY 原文（这段写得像一篇小型考古）：

> Linux 1.2. At the time when this system call was introduced, **one process could send a signal to another process with the same effective user ID**. This meant that if a privileged process changed its effective user ID for the purpose of file permission checking, then it could become **vulnerable to receiving signals sent by another (unprivileged) process with the same user ID**. The filesystem user ID attribute was thus added to allow a process to change its user ID for the purposes of file permission checking **without at the same time becoming vulnerable to receiving unwanted signals**. **Since Linux 2.0, signal permission handling is different (see `kill(2)`)** … Thus, `setfsuid()` is **nowadays unneeded and should be avoided in new applications** (likewise for `setfsgid(2)`).

也就是说：

| 时代 | 场景 | 结论 |
|------|------|------|
| Linux 1.2 | NFS 服务器以 root 运行，但要**代表客户端用户**做文件权限检查。如果直接改 euid，就落进「同 euid 可互发信号」的规则里，会被普通用户骚扰 | 需要 fsuid：**只改文件检查用的身份，不动 euid** |
| Linux ≥ 2.0 | 信号权限改用 RUID/EUID + `kill(2)` 的新规则，改 euid 不再带来信号风险 | fsuid **不再必要** |
| 现在 | `setfsuid` 在 glibc 的 SYNOPSIS 里已经标成 **`[[deprecated]]`** | **新代码不要用** |

**glibc 头文件里它真的带了 deprecated 标记**：

```c
/* sys/fsuid.h */
[[deprecated]] int setfsuid(uid_t fsuid);
```

不过实测（gcc 13.3 + glibc 2.39，`-Wall -Wextra`）**没有**报 `-Wdeprecated-declarations`：`[[deprecated]]` 这条属性在 glibc 里是靠 `__attr_dealloc` 之外的一个可选宏开的，Ubuntu 的默认头文件组合下不触发。所以本节 demo 能干净地编译通过；但**别的发行版 / 别的 glibc 版本可能会报**，那时加 `-Wno-deprecated-declarations` 即可。

### 三、那个「看不出成败」的接口

`setfsuid(2)` RETURN VALUE 全文只有一句：

> **On both success and failure, this call returns the previous filesystem user ID of the caller.**

`setfsuid(2)` BUGS 全文：

> **No error indications of any kind are returned to the caller, and the fact that both successful and unsuccessful calls return the same value makes it impossible to directly determine whether the call succeeded or failed.** Instead, the caller must resort to looking at the return value from a further call such as **`setfsuid(-1)` (which will always fail)**, in order to determine if a preceding call to `setfsuid()` changed the filesystem user ID. **At the very least, EPERM should be returned when the call fails (because the caller lacks the `CAP_SETUID` capability).**

于是产生了那个著名的惯用法：

```c
uid_t now = (uid_t) setfsuid((uid_t) -1);   /* -1 永远不合法 -> 一定不改动任何东西 */
                                            /* 但它的返回值 = 当前的 fsuid       */
```

**为什么 `-1` 一定不合法**：内核的开头就是 `make_kuid(ns, -1)`；`(uid_t)-1` 是内核约定的「未映射」值，`uid_valid()` 必然为假。`user_namespaces(7)` 里专门为这个约定留了一段说明："Leaving `(uid_t) -1` unmapped and unusable guarantees that there will be no confusion when using these interfaces."

### 四、内核里的放行条件（四条 or 一条）

`kernel/sys.c:865` 的 `__sys_setfsuid()`（在 `#ifdef CONFIG_MULTIUSER` 内，`:373`–`:949`）：

```c
long __sys_setfsuid(uid_t uid)                                  /* :865 */
{
    ...
    if (uid_eq(kuid, old->uid)  || uid_eq(kuid, old->euid)  ||   /* :883 */
        uid_eq(kuid, old->suid) || uid_eq(kuid, old->fsuid) ||   /* :884 */
        ns_capable_setid(old->user_ns, CAP_SETUID)) {            /* :885 */
        if (!uid_eq(kuid, old->fsuid)) {
            new->fsuid = kuid;                                   /* :887 */
            if (security_task_fix_setuid(new, old, LSM_SETID_FS) == 0)
                goto change_okay;
        }
    }

    abort_creds(new);                                            /* :893 */
    return old_fsuid;                                            /* :894  ← 静默失败 */
...
```

| 放行条件 | 说明 |
|----------|------|
| `uid == old->uid`（RUID） | 集合内的值可以直接设 |
| `uid == old->euid`（EUID） | 同上 |
| `uid == old->suid`（SUID） | 同上 |
| `uid == old->fsuid`（当前 fsuid） | 同上（这条最容易漏——它允许「再设一次自己」） |
| 有 `CAP_SETUID` | 任意值 |

**四条全不满足时**：走 `abort_creds(new)` 丢弃准备中的凭证，然后 `return old_fsuid` —— **返回旧的 fsuid，不设 errno，不报错**。所以「`setfsuid(t)` 返回了值」这件事**不能推出任何结论**，必须**再读一次**。

注意放行集合和 `setuid()` 的**不一样**（[9.2](./9.2-effective-uid-gid.md) 的分支表对比）：`setfsuid` 的集合里**多了 `fsuid` 自己**，`setuid` 的检查里则要看 `new->suid`（因为 setuid 会先改 suid）。

### 五、`fsuid` 的第二个读法：`/proc/self/status` 的第 4 列

`proc_pid_status(5)`：

> **Uid**  Real, effective, saved set, and **filesystem** UIDs
> **Gid**  Real, effective, saved set, and **filesystem** GIDs

所以 `Uid:` 行的**第 4 列就是 fsuid**，和 `setfsuid(-1)` 的返回值**必然相等**。本节实测把这个等式做成了硬证据（下一节的输出第 ① 段）。

## 代码

### c9_2 fsuid 的两个读法 + 那个分辨不出成败的返回值

[`../code/c9_2_fsuid.c`](../code/c9_2_fsuid.c) 五段：

| 段 | 做什么 |
|----|--------|
| ① | **两种读法对照**：`setfsuid(-1)` 的返回值 vs `/proc/self/status` 的 `Uid:` 第 4 列 |
| ② | **失败却看起来像成功**：`setfsuid(10240)`（未映射）→ 对比返回值与「再读一次」的结果 |
| ③ | fsgid 同构 |
| ④ | 把那句 BUGS 原文打出来 |
| ⑤ | 把内核 `kernel/sys.c:883-885` 的四条放行条件打出来 |

```c
/* c9_2_fsuid.c —— filesystem ID 与那个「看不出成败」的接口
 *
 * 9.5 的主题：Linux 独有的 fsuid / fsgid。
 *
 * 本程序要坐实三件事：
 *   ① fsuid 有两个**独立**读法：setfsuid(-1) 与 /proc/self/status 的 Uid: 第 4 列。
 *   ② setfsuid() 失败时**不报错**：返回值是「旧值」，成功也是「旧值」——光看返回值
 *      无法分辨。必须再读一次才知道有没有生效。
 *   ③ 文件权限检查用的是 fsgid/fsuid + 补充组，不是 egid/euid（内核 groups.c:234
 *      in_group_p() 里第一句比的就是 cred->fsgid）。
 *
 * 权威依据：
 *   - setfsuid(2) RETURN VALUE："On both success and failure, this call returns the
 *     previous filesystem user ID of the caller."
 *   - setfsuid(2) BUGS："No error indications of any kind are returned to the caller,
 *     ... the caller must resort to looking at the return value from a further call
 *     such as setfsuid(-1) (which will always fail) ... At the very least, EPERM
 *     should be returned when the call fails (because the caller lacks the
 *     CAP_SETUID capability)."
 *   - proc_pid_status(5)：Uid / Gid = Real, effective, saved set, and filesystem UIDs。
 *   - kernel/sys.c:865 __sys_setfsuid()：不改动时 `return old_fsuid;`（静默）。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_2_fsuid c9_2_fsuid.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/fsuid.h>
#include <sys/types.h>
#include <unistd.h>

/* 取 /proc/self/status 里某一行（如 "Uid:"）的第 col 列（1-based） */
static unsigned status_col(const char *key, int col)
{
    FILE *fp = fopen("/proc/self/status", "r");
    if (fp == NULL)
        return 0;
    size_t klen = strlen(key);
    char buf[512];
    unsigned v[4] = { 0, 0, 0, 0 };
    unsigned ret = 0;
    while (fgets(buf, sizeof buf, fp) != NULL) {
        if (strncmp(buf, key, klen) == 0 && buf[klen] == ':') {
            /* key 已经是 "Uid:" 形式，sscanf 直接从冒号后取 4 个数 */
            if (sscanf(buf + klen, "%u %u %u %u", &v[0], &v[1], &v[2], &v[3]) >= col)
                ret = v[col - 1];
            break;
        }
    }
    fclose(fp);
    return ret;
}

int main(void)
{
    printf("=== ① fsuid 的两个读法 ===\n");
    uid_t via_api = (uid_t) setfsuid((uid_t) -1);
    unsigned via_proc = status_col("Uid:", 4);
    printf("  setfsuid(-1) 读回          : %u\n", (unsigned) via_api);
    printf("  /proc/self/status 第 4 列  : %u\n", via_proc);
    printf("  两者一致? %s\n", ((unsigned) via_api == via_proc) ? "是" : "否");

    printf("\n=== ② setfsuid() 的返回值分辨不出成败 ===\n");
    uid_t before = (uid_t) setfsuid((uid_t) -1);
    errno = 0;
    uid_t ret = (uid_t) setfsuid((uid_t) 10240);   /* 本容器里未映射的 uid */
    printf("  setfsuid(10240) 返回 %u   (errno=%d %s)\n",
           (unsigned) ret, errno, errno ? strerror(errno) : "未置位");
    uid_t after = (uid_t) setfsuid((uid_t) -1);
    printf("  再读一次 fsuid     = %u\n", (unsigned) after);
    printf("  判决: ");
    if (after == (uid_t) 10240)
        printf("生效了\n");
    else if (before == ret)
        printf("**没生效**，但它的返回值和「成功」完全一样 —— 看返回值看不出来\n");
    else
        printf("变化了 %u -> %u\n", (unsigned) before, (unsigned) after);

    printf("\n=== ③ fsgid 同理 ===\n");
    gid_t fa = (gid_t) setfsgid((gid_t) -1);
    printf("  setfsgid(-1)               = %u\n", (unsigned) fa);
    printf("  /proc/self/status 第 4 列  = %u\n", status_col("Gid:", 4));

    printf("\n=== ④ setfsuid(2) BUGS 原文 ===\n");
    printf("  \"No error indications of any kind are returned to the caller,\n");
    printf("   and the fact that both successful and unsuccessful calls return the\n");
    printf("   same value makes it impossible to directly determine whether the\n");
    printf("   call succeeded or failed.\"\n");

    printf("\n=== ⑤ 内核里 setfsuid() 的放行条件（kernel/sys.c:883-885）===\n");
    printf("  uid == ruid || uid == euid || uid == suid || uid == fsuid\n");
    printf("      || ns_capable_setid(user_ns, CAP_SETUID)\n");
    printf("  四条全不满足 -> 不动 cred，也**不设 errno**，直接 return old_fsuid\n");
    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c9_2_fsuid c9_2_fsuid.c && ./c9_2_fsuid
```

```text
=== ① fsuid 的两个读法 ===
  setfsuid(-1) 读回          : 0
  /proc/self/status 第 4 列  : 0
  两者一致? 是

=== ② setfsuid() 的返回值分辨不出成败 ===
  setfsuid(10240) 返回 0   (errno=0 未置位)
  再读一次 fsuid     = 0
  判决: **没生效**，但它的返回值和「成功」完全一样 —— 看返回值看不出来

=== ③ fsgid 同理 ===
  setfsgid(-1)               = 0
  /proc/self/status 第 4 列  = 0

=== ④ setfsuid(2) BUGS 原文 ===
  "No error indications of any kind are returned to the caller,
   and the fact that both successful and unsuccessful calls return the
   same value makes it impossible to directly determine whether the
   call succeeded or failed."

=== ⑤ 内核里 setfsuid() 的放行条件（kernel/sys.c:883-885）===
  uid == ruid || uid == euid || uid == suid || uid == fsuid
      || ns_capable_setid(user_ns, CAP_SETUID)
  四条全不满足 -> 不动 cred，也**不设 errno**，直接 return old_fsuid
```

**解读**

1. **第 ① 段的「两者一致? 是」是本节的第一个硬证据。** `setfsuid(-1)` 与 `/proc/self/status` 第 4 列读到的都是 `0`。这直接印证了 `proc_pid_status(5)` 那个 "Real, effective, saved set, and **filesystem** UIDs" 的列序——**`Uid:` 行是 4 列，第 4 列是 fsuid**，不是「3 列」也不是「第 3 列」。
2. **第 ② 段是本节的核心。** `setfsuid(10240)` 返回 `0`，`errno` 是 `0`（**未置位**），看上去完美成功。但紧接着「再读一次 fsuid」得到 `0` —— **和设之前一样，压根没生效**。程序打印的判断是"**没生效**，但它的返回值和「成功」完全一样 —— 看返回值看不出来"。
   - 为什么没生效？`10240` 不在 `{ruid, euid, suid, fsuid}` 这四个值里（它们是 `{0,0,0,0}`），而且本进程 `CapEff = 0` **没有 `CAP_SETUID`** → 四条放行条件全不满足 → 走 `abort_creds(new); return old_fsuid;`（`kernel/sys.c:893-894`）。
   - 为什么 `errno` 是 0？因为**那条 return 路径根本不碰 errno**。这是 BUGS 里点名的问题："At the very least, EPERM should be returned when the call fails."
3. **第 ③ 段 fsgid 同构**：`setfsgid(-1)` 也是 `0`，`Uid:`/`Gid:` 第 4 列都是 0。**`Gid:` 行同样是 4 列**，很多人只记得 `Uid:` 有 4 列却忘了 `Gid:` 也有。
4. **第 ⑤ 段是给「怎么判断成败」的答案**：既然返回值不可信、errno 也不可信，唯一可靠的办法就是**回读**——而且要用一个「一定不会成功」的调用来读。这就是 `setfsuid(-1)` 这个惯用法的逻辑依据：`(uid_t)-1` 是内核约定的未映射值（`user_namespaces(7)` 明文保证它 unusable），所以 `setfsuid(-1)` 永远不会改变状态，它的返回值**必然**是调用前的 fsuid。
5. **本节 demo 里的 `status_col("Uid:", 4)` 是个可复用的读法**：`sscanf(buf + strlen("Uid:"), "%u %u %u %u", ...)` 一次取全部 4 列，比 `strtok` 或手工找空格干净。注意 `key` 参数里带冒号（`"Uid:"`），所以冒号后面直接就是第一个数字。

## HFT / 嵌入式关联

- **新代码不要碰 `setfsuid`。** glibc 把它标成了 `[[deprecated]]`，man 说 "nowadays unneeded and should be avoided in new applications"。代码审查里见到它，第一反应应该是「这段代码是从哪个上世纪的 NFS 相关项目抄来的」。
- **但你必须知道它在哪生效，因为排查文件权限问题时绕不过它。** 「同一个 euid，为什么 `open()` 一个文件成功、`stat()` 另一个失败」这类问题，很可能就是某段老代码（或某个库的初始化）调过 `setfsuid`，把文件检查身份和 euid 分岔了。排查手段：
  ```bash
  cat /proc/self/status | grep -E '^(Uid|Gid):'   # 第 4 列 vs 第 2 列
  ```
  第 2 列（euid）与第 4 列（fsuid）不等，就是「有人在调 setfsuid」的铁证。
- **`setfsuid(-1)` 是唯一安全的读法。** 如果非要读 fsuid（比如做审计），用 `setfsuid(-1)` 而**不要**用「`setfsuid(geteuid())` 再看返回值」——后者可能真的改动状态。或者直接读 `/proc/self/status`（无副作用，更便宜）。
- **嵌入式裁剪内核时注意 `CONFIG_MULTIUSER`。** 如果 BSP 为了省空间把它关掉，`setuid`/`setgid`/`setfsuid`/`setfsgid`/`setgroups` 这一整族 syscall **全部消失**，链接时不会报错（glibc 有 stub），运行时返回 `ENOSYS`。这在极小的 RTOS-like 嵌入式配置里出现过。判断方法：`grep -c "setfsuid" /proc/kallsyms`。
- **`in_group_p()` 比 fsgid 而不是 egid**（`kernel/groups.c:234`）这一条，对理解「为什么我 `setegid` 之后文件权限没变」很关键——**`setegid` 会同步 fsgid**（`credentials(7)` 的总纲），所以正常情况看不到差别；但如果同时有人调了 `setfsgid`，就会出现「egid 已改、文件权限仍按旧 fsgid 判」的错位。
- **NFS 服务器身份映射在现代内核走的是 `nfsd`** 的专门接口，不再依赖 `setfsuid`；容器里的「用户映射」走的是 `uid_map`/`gid_map`（[9.1](./9.1-real-uid-gid.md)）。**这两者容易和 fsuid 混为一谈**，记住它们的层次不同：`uid_map` 决定「ns 里的编号对应宿主哪个 uid」，fsuid 决定「进程此刻用哪个编号做文件检查」。

## 自测题

<details>
<summary>1. 怎么读出一个进程当前的 fsuid？有几种办法？</summary>

**两种，都可靠，各有取舍。**

| 办法 | 写法 | 代价 |
|------|------|------|
| API | `uid_t f = (uid_t) setfsuid((uid_t) -1);` | 一次 syscall；`-1` 永远不合法所以**必然不改状态** |
| `/proc` | `/proc/self/status` 的 `Uid:` 行**第 4 列** | 要开文件 + 解析；**无副作用**，且能一次拿到 4 列 |

本节实测两者**必然相等**：

```text
  setfsuid(-1) 读回          : 0
  /proc/self/status 第 4 列  : 0
  两者一致? 是
```

依据：`proc_pid_status(5)` 的 "**Uid** Real, effective, saved set, and **filesystem** UIDs"。

**不要用**「`setfsuid(geteuid())` 再看返回值」这条——虽然多数情况下 `geteuid()` 落在放行集合里，但这个调用**有改动状态的可能**，只是碰巧没改就看不出来。读值就应该用不产生副作用的写法。
</details>

<details>
<summary>2. <code>setfsuid(10240)</code> 返回 0，是不是成功了？</summary>

**不是。它失败了，但接口不告诉你。**

`setfsuid(2)` RETURN VALUE："**On both success and failure, this call returns the previous filesystem user ID of the caller.**"

本节实测：

```text
  setfsuid(10240) 返回 0   (errno=0 未置位)
  再读一次 fsuid     = 0
  判决: **没生效**，但它的返回值和「成功」完全一样 —— 看返回值看不出来
```

三件事同时成立：

1. 返回值是 `0` —— 但那是**旧值**（进程原本 fsuid 就是 0），不是「成功码」；
2. `errno` 是 `0` —— 因为 `kernel/sys.c:893-894` 的失败路径 `abort_creds(new); return old_fsuid;` **根本不碰 errno**；
3. 实际没生效 —— `10240` 不在 `{ruid, euid, suid, fsuid} = {0,0,0,0}` 里，且本进程无 `CAP_SETUID`。

判断方法只有一个：**再读一次**（`setfsuid(-1)`）。

man 的 BUGS 一节对这件事的评价是："At the very least, EPERM should be returned when the call fails (because the caller lacks the `CAP_SETUID` capability)." —— 这是一个**公认的设计缺陷**，不是文档写得不清楚。
</details>

<details>
<summary>3. 为什么 Linux 上「文件权限看 EUID」是错的？</summary>

因为 Linux 引入了 **fsuid / fsgid** 这对专有 ID，文件权限检查用的是**它们**，不是 euid/egid。

`credentials(7)` 原文（Effective ID 一节）：

> These IDs are used by the kernel to determine the permissions that the process will have when accessing shared resources such as message queues, shared memory, and semaphores. **On most UNIX systems, these IDs also determine the permissions when accessing files. However, Linux uses the filesystem IDs described below for this task.**

完整的文件权限检查输入是**三元组**：

| 分量 | 来自 |
|------|------|
| fsuid | `cred->fsuid`（内核 `path_resolution(7)` 流程用） |
| fsgid | `cred->fsgid`（`kernel/groups.c:234` 的 `in_group_p()` 先比它） |
| 补充组 | `cred->group_info`（`groups_search()` 二分） |

**那为什么平时「看 EUID」也对？** 因为内核保证同步：`credentials(7)` 说 "Whenever a process's effective user (group) ID is changed, the kernel **also automatically changes** the filesystem user (group) ID to the same value."。所以只要没人显式调 `setfsuid`，两者恒等，「看 EUID」在实践中成立。

要打破这个等式，只有一条路：显式 `setfsuid()` / `setfsgid()`（本节 demo 的用法）。而这条路**已经被标为 deprecated**——所以「Linux 用 fsuid 做文件检查」这个事实，主要价值在于**排查疑难权限问题时能想到这一层**，而不是鼓励你去用它。
</details>

<details>
<summary>4. <code>setfsuid()</code> 非特权进程能设成哪些值？和 <code>setuid()</code> 的放行集合有什么不同？</summary>

**能设成 4 个值之一**（`kernel/sys.c:883-885`）：

```c
uid_eq(kuid, old->uid)  || uid_eq(kuid, old->euid)  ||
uid_eq(kuid, old->suid) || uid_eq(kuid, old->fsuid) ||
ns_capable_setid(old->user_ns, CAP_SETUID)
```

即 `{RUID, EUID, SUID, 当前 fsuid}` 之一，或拥有 `CAP_SETUID`。

**和 `setuid()` 的关键差别**：

| | 放行集合 |
|---|----------|
| `setuid(u)`（非特权分支，`kernel/sys.c:637`） | `u == old->uid`（RUID）**或** `u == new->suid` |
| `setfsuid(u)`（`kernel/sys.c:883-885`） | `u ∈ {RUID, EUID, SUID, fsuid}` —— **多了 EUID 和 fsuid 自己** |

两点值得注意：

1. **`setfsuid` 允许「再设一次当前的 fsuid」**，所以 `setfsuid(getfsuid())` 是一个永远会「成功」的 no-op（但你看不出它成功了——返回值一样）。
2. **`setuid` 检查的是 `new->suid`**（因为 `setuid` 在 `:631` 已经把 `new->suid` 赋成了目标值，所以那个比较实际上是「u 是不是旧 RUID」的镜像，见 [9.2](./9.2-effective-uid-gid.md) 的分支表）。**不要用记忆里的「两者差不多」去推**，写代码时真想确认就回读。

`setfsuid(2)` DESCRIPTION 的表述是："will succeed only if the caller is the superuser or if `fsuid` matches either the caller's **real user ID, effective user ID, saved set-user-ID, or current filesystem user ID**."
</details>

<details>
<summary>5. 内核配置关掉 <code>CONFIG_MULTIUSER</code> 会怎样？</summary>

**`setfsuid` / `setfsgid`（以及 `setuid` / `setgid` / `setgroups` 一族）会整个消失。**

Linux v6.6 `kernel/sys.c` 里这段代码被 `#ifdef CONFIG_MULTIUSER` 包住，范围是 **`:373` – `:949`**——`__sys_setreuid()` / `__sys_setuid()` / `__sys_setresuid()` / `__sys_setfsuid()` / `__sys_setfsgid()` 全在里面。

`CONFIG_MULTIUSER` 是给 **单用户嵌入式 / unikernel 式配置**用的（省内存 + 去掉一整类安全面）。后果：

| 层面 | 现象 |
|------|------|
| 编译 | 应用照常编译通过（glibc 有 syscall stub） |
| 运行 | 这些调用返回 `-1` 且 `errno = ENOSYS`（不是 EPERM！） |
| 排查 | `grep -c setfsuid /proc/kallsyms` 返回 0 |
| 影响面 | 「启动时降权」的功能**完全没有意义**，因为根本没有多用户概念 |

所以嵌入式项目里，**「这台设备有没有用户概念」要先确认**再去写降权逻辑。看到 `ENOSYS` 就说明内核根本不支持，改代码没用，得改内核配置。

顺带一提：`CONFIG_MULTIUSER=n` 不是 `CONFIG_USER_NS=n`。前者砍掉整族 syscall，后者只砍 namespace 支持——两者影响的排查方向完全不同。
</details>
