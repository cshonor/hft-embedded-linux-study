## 本章回顾

第 9 章讲的是**一个进程此刻「是谁」**——不是账户数据库（那是 Ch8），而是运行时持有的那一组 ID。

```
        ┌────────────────────────────────────────────────────────┐
        │  struct cred（内核里的一份凭证）                          │
        │  uid   gid      ← real：谁拥有这个进程                    │
        │  euid  egid     ← effective：共享资源（IPC 等）的权限检查  │
        │  suid  sgid     ← saved：exec 时的 euid 副本，用来来回切    │
        │  fsuid fsgid    ← filesystem：**文件**权限检查用的（Linux）│
        │  group_info     ← 补充组列表（最多 65536 个）              │
        └────────────────────────────────────────────────────────┘
                    ↑ 读：getresuid / getgroups / /proc/self/status
                    ↑ 写：setresuid / setgroups / setfsuid
                    ↑ 自动变：execve（set-user-ID 位）
```

**一句话主线**：Linux 把「文件权限看 EUID」改成了「文件权限看 **fsuid**」（[9.5](./9.5-fs-uid-gid.md)）→ fsuid 平时跟着 euid 走所以看不出差别 → 唯一能自动改 euid 的机制是 **set-user-ID 程序**（[9.3](./9.3-set-user-id.md)）→ 有了 **saved** 才能「降下去再升回来」（[9.4](./9.4-saved-id.md)）→ 降权时必须**先清补充组**（[9.6](./9.6-supplementary-groups.md)）→ 而这一切的前提是 **uid 在本 user namespace 里有映射**（[9.1](./9.1-real-uid-gid.md)）。

## 五类凭证一览

| 凭证 | 用途 | 读 | 写 | 谁会自动改它 |
|------|------|----|----|--------------|
| **Real** UID/GID | 拥有者；信号权限；资源记账（`RLIMIT_NPROC`） | `getuid()` / `getgid()` | `setuid` / `setresuid` | `fork`（继承） |
| **Effective** UID/GID | 共享资源（IPC）的权限检查；**「特权」的判据** | `geteuid()` / `getegid()` | `seteuid` / `setreuid` / `setresuid` / **`setuid`** | `execve`（set-user-ID 位） |
| **Saved set**-UID/GID | 保存 exec 时的 euid，供 `seteuid` 来回切 | `getresuid()` | `setreuid` / `setresuid` / **`setuid`（特权时）** | `execve`（无条件 ← 新 euid） |
| **Filesystem** UID/GID（Linux 专有） | **文件**权限检查 | `setfsuid(-1)` 或 `/proc/self/status` 第 4 列 | `setfsuid` / `setfsgid`（已废弃） | 任何 euid 变更 → 同步 |
| **Supplementary** groups | 文件/IPC 权限检查的额外集合 | `getgroups()` | `setgroups()` / `initgroups()` | `fork`（继承）；`execve` 不动 |

依据：`credentials(7)` 的 "User and group identifiers" 一节（5 个 bullet）。

## 权限检查到底看哪个 ID

| 检查对象 | 用哪个 | 依据 |
|----------|--------|------|
| **文件** | `fsuid` + `fsgid` + 补充组 | `credentials(7)`："**Linux uses the filesystem IDs described below for this task**"；`kernel/groups.c:234` |
| 消息队列 / 共享内存 / 信号量 | `euid` + `egid` + 补充组 | `credentials(7)` |
| 发信号（`kill(2)`） | RUID **或** EUID | `credentials(7)`："when determining the permissions for sending signals" |
| 改 nice / 调度策略 / CPU 亲和 | capability | `credentials(7)` 后续 bullet |
| **「是不是特权进程」** | `EUID == 0`（TLPI 判据）/ **capability**（内核判据） | `setuid(2)`："more precisely: … the `CAP_SETUID` capability" |

> ⚠️ 最后一行是本章最容易背错的地方。**现代内核的真正判据是 capability**，`euid == 0` 只是它的历史近似。本批实测的容器就是反例：`uid=euid=0` 而 `CapEff=0000000000000000`（[9.1](./9.1-real-uid-gid.md)）。

## `set*id` 语义总表

| 调用 | 改哪些 | 特权（有 `CAP_SETUID`） | 非特权 |
|------|--------|--------------------------|--------|
| `setuid(u)` | R+E+S **或** 只 E | `r=e=s=u`，**不可逆** | 只 `e=u`，要求 `u ∈ {r, s}` |
| `seteuid(e)` | 只 E | 任意合法 uid | `e ∈ {r, s}` |
| `setreuid(r, e)` | R 与/或 E，**可能顺带 S** | 一般可设 `{r, e, s}` | `e ∈ {r, e, s}`；`r ∈ {r, e}` |
| `setresuid(r, e, s)` | R/E/S 各自独立 | 任意组合 | 每项 ∈ 当前 `{r, e, s}` |
| `setfsuid(u)` | 只 F | 任意 | `u ∈ {r, e, s, f}`；否则**静默失败** |
| `setgroups(n, l)` | 补充组 | ✅ | ❌ `EPERM`（还受 ns 的 `setgroups` 管） |

GID 侧（`setgid` / `setegid` / `setregid` / `setresgid` / `setfsgid`）与 UID 侧完全对称。

**四条贯穿规则**：

1. `-1` = 不改这一项（`setreuid` / `setresuid` / `setregid` / `setresgid`）；
2. 任何 euid 变更都会**同步 fsuid**；
3. `setuid` 在特权进程下**连 saved 一起改** → 临时降权必须用 `seteuid`；
4. `EINVAL` 排在 `EPERM` **之前**：uid 无映射 → `EINVAL`；uid 合法但不许改 → `EPERM`。

## `fork` / `execve` 对凭证的影响

| 事件 | Real | Effective | Saved | fsuid | 补充组 |
|------|------|-----------|-------|-------|--------|
| `fork()` | 继承 | 继承 | 继承 | 继承 | 继承 |
| `execve()` 普通程序 | **不变** | **不变**（仍 = 旧 euid） | **← euid**（无条件） | ← euid | **不变** |
| `execve()` set-user-ID-root 程序 | **不变**（仍是启动者） | **0**（文件属主） | **← 新的 euid = 0** | ← euid = 0 | **不变** |

> ⚠️ **「exec 无 setuid 位时 saved 不更新」是错的。** `execve(2)` 原文："The effective user ID of the process is **copied to the saved set-user-ID** … **This copying takes place after any effective ID changes**" —— 没有任何前提条件。**saved 永远被设成新的 euid**，所以普通程序 exec 之后 `saved == euid == ruid`。
>
> ⚠️ 第二行还有个细节：`execve` **不动补充组**（"as well as its supplementary group IDs, are **unchanged**"）。所以 SUID 程序里补充组仍然是启动者的 —— 想让 egid/补充组也换，得靠 set-group-ID 位（`fs/exec.c:1642`，且**要求组执行位**）或 `setgroups()`。

## 降权：正确顺序与常见错误

```c
/* ① 先清补充组 —— 它需要 CAP_SETGID，丢了特权就再也调不动 */
if (setgroups(0, NULL) == -1) die("setgroups");

/* ② 再改 gid */
if (setgid(t) == -1) die("setgid");

/* ③ 最后 R/E/S 一起钉死（不可逆） */
if (setresuid(t, t, t) == -1) die("setresuid");

/* ④ 回读验证 —— 别信返回值（set*id 可能返回 0 却是 no-op） */
uid_t r, e, s;
getresuid(&r, &e, &s);
if (r != t || e != t || s != t) die("降权没有生效");
```

| 常见错误 | 后果 |
|----------|------|
| 顺序反了（先 `setresuid`） | `setgroups` → `EPERM`，**补充组里还留着特权组** |
| 用 `seteuid` 当「永久降权」 | `saved` 还在 → 任何代码执行都能 `seteuid(0)` 回到 root |
| 不检查 `setuid` 的返回值 | `setuid(2)` 原文："**it is a grave security error to omit checking for a failure return**" |
| 只检查返回值不验证 | 容器里 `set*id` 可能返回 0 却是 no-op（[9.2](./9.2-effective-uid-gid.md) 实测） |
| 以为 `euid == 0` 就等于有特权 | 容器 / `capsh --drop` / `NoNewPrivileges` 下不成立 |

## 自测题

<details>
<summary>1. 列出「一个进程此刻是谁」的全部 5 类 ID，并说明文件权限检查用哪几个。</summary>

**5 类**（`credentials(7)` 的 5 个 bullet）：

| 类 | 成员 |
|----|------|
| Real | `uid` / `gid` |
| Effective | `euid` / `egid` |
| Saved set | `suid` / `sgid` |
| Filesystem（Linux 专有） | `fsuid` / `fsgid` |
| Supplementary groups | 组列表 |

**文件权限检查用的三元组是 `(fsuid, fsgid, 补充组)`** —— 不是 `(euid, egid, …)`。

依据：`credentials(7)`："On most UNIX systems, these IDs also determine the permissions when accessing files. **However, Linux uses the filesystem IDs described below for this task.**"；`kernel/groups.c:234` 的 `in_group_p()` 先比 `cred->fsgid`。

**为什么平时感觉「看 EUID」也对**：内核保证同步——"Whenever a process's effective user (group) ID is changed, the kernel also automatically changes the filesystem user (group) ID to the same value."。所以只有显式 `setfsuid()` 才会让两者分岔。

**Effective 管的是别的东西**：消息队列、共享内存、信号量的权限检查（`credentials(7)` 原文列举的正是这三样）。
</details>

<details>
<summary>2. 一个 SUID-root 程序 exec 之后，R/E/S/F 各是多少？exec 一个普通程序呢？</summary>

**SUID-root 程序**（uid 1000 的用户执行属主为 root 的程序）：

| ID | 值 |
|----|----|
| RUID | 1000（**不变**） |
| EUID | 0（文件属主） |
| SUID | 0（← 新的 euid） |
| fsuid | 0（跟随 euid） |
| 补充组 | 与 exec 前相同 |

**普通程序**（`R=1000 E=1000 S=1000`）：

| ID | 值 |
|----|----|
| RUID | 1000 |
| EUID | 1000（**不变**） |
| SUID | 1000（← euid，**无条件**） |
| fsuid | 1000 |
| 补充组 | 不变 |

⚠️ **第二张表里最容易错的就是 SUID 那一格**。常见的错误说法是「无 setuid 位时 saved 不更新」——错。`execve(2)`："The effective user ID of the process is **copied to the saved set-user-ID** … This copying takes place after any effective ID changes that occur because of the set-user-ID and set-group-ID mode bits." 没有任何前提条件。

**推论**：普通程序 exec 之后 `saved == euid == ruid`，所以它能安全地 `seteuid(getuid())`；一个 `R=1000 E=0 S=0` 的 SUID 程序降权成 `R=1000 E=1000 S=0` 之后还能 `seteuid(0)` 升回去 —— **全部靠 saved**。
</details>

<details>
<summary>3. 降权为什么要按 <code>setgroups</code> → <code>setgid</code> → <code>setresuid</code> 的顺序？</summary>

因为 **`setgroups()` 需要 `CAP_SETGID`**，而 `setresuid()` 会把特权丢掉。

`kernel/groups.c:187`：

```c
bool may_setgroups(void)
{
    struct user_namespace *user_ns = current_user_ns();
    return ns_capable_setid(user_ns, CAP_SETGID) &&
           userns_may_setgroups(user_ns);
}
```

先 `setresuid(t,t,t)` 的后果：

| ID | 状态 |
|----|------|
| uid / gid | 已降 ✅ |
| **补充组** | **仍是原来那些（含特权组）** ❌ |

而权限检查的第 2 步就是「fsgid 或**补充组**匹配文件属主 gid」（[9.6](./9.6-supplementary-groups.md) 要点一），所以残留的特权组**照样能访问那些组的文件**。这就是「降权没降干净」。

**还要注意两道闸门**：`CAP_SETGID`（`may_setgroups()` 的左半边）之外还有 `userns_may_setgroups()`，容器里常见 `/proc/self/setgroups = deny`（[9.6](./9.6-supplementary-groups.md) 实测）。

另外 `credentials(7)` 提醒补充组是跟着进程走的："During an `execve(2)`, a process's real user and group ID and **supplementary group IDs are preserved**" —— 换个程序执行不会帮你清掉。
</details>

<details>
<summary>4. 为什么容器里 <code>setuid(10240)</code> 是 <code>EINVAL</code>，而真机上是 <code>EPERM</code>？</summary>

**因为内核先查「uid 有没有映射」，再查「你有没有权限」。**

`kernel/sys.c:620-622`：

```c
kuid = make_kuid(ns, uid);
if (!uid_valid(kuid))
    return -EINVAL;              /* ← 排在 capability 检查之前 */
```

`ns_capable_setid(..., CAP_SETUID)` 在 `:630`，**在后面**。

| 环境 | `make_kuid(10240)` | 结果 |
|------|--------------------|------|
| 容器（`uid_map` = `0 113 1`） | 拿不到合法 kuid | **`EINVAL(22)`** |
| 真机（UID 空间完整） | 合法 | 继续 → **`EPERM(1)`** |

`setuid(2)` ERRORS 两条的定义本来就不同：

- `EINVAL` — "The user ID specified in `uid` is not valid in **this user namespace**."
- `EPERM` — "The user is not privileged … and `uid` does not match the real UID or saved set-user-ID of the calling process."

本批实测在容器里看到的是 22（[9.2](./9.2-effective-uid-gid.md)、[9.7](./9.7-api.md) 的 `c9_4`、9.4 的 `c9_5` 三个程序都是）。**同一条代码在宿主上返回 1、在容器里返回 22** —— 排查跨环境问题时这个差别很值钱。
</details>
