# 9.3 Set-User-ID and Set-Group-ID Programs

> 权威依据：`execve(2)`（man-pages 6.19）· `capabilities(7)` · `credentials(7)` · `chmod(2)` · Linux v6.6 `fs/exec.c`
> 本节演示在 [Compiler Explorer](https://godbolt.org/) 上真实编译 + 运行（gcc 13.3.0 / x86-64 / Ubuntu 24.04 容器）
> 本章：[TLPI 第 09 章 — Process Credentials](../README.md)
> - 上一节：[9.2 Effective User ID and Effective Group ID](./9.2-effective-uid-gid.md)
> - 下一节：[9.4 Saved Set-User-ID and Saved Set-Group-ID](./9.4-saved-id.md)

## 本节讲什么

9.2 说「权限看 EUID」，但 EUID 平时等于 RUID。**唯一能让 EUID 自动 ≠ RUID 的机制，就是 set-user-ID / set-group-ID 程序**。

这一节最容易写成一句话就结束：「`execve` 之后 euid 变成文件属主」。本节要补的是**那句话说不到的地方**：

1. 内核里控制这件事的函数只有 20 行，但里面有 **4 条独立的「不生效」路径**，其中一条 man 里根本没写；
2. set-user-ID 位**会被写操作清掉**——这是真的能在这里做的实验；
3. 「镜像里唯一的 SUID 文件 `execve` 之后什么也没发生」——本条实测，值得解释清楚为什么。

---

## 要点

### 一、怎么造一个 set-user-ID 程序

```bash
chmod u+s program     # set-user-ID
chmod g+s program     # set-group-ID
ls -l program         # -rwsr-xr-x / -rwxr-sr-x
```

`ls -l` 的第 4 位从 `x` 变 `s`。注意八进制写法要**四位**：`chmod 4755`（set-user-ID）／`chmod 2755`（set-group-ID）／`chmod 6755`（两个都开）。写成三位 `chmod 755` 会把这两个位一起抹掉。

### 二、`execve` 改什么、不改什么

`execve(2)` 原文：

> If the set-user-ID bit is set on the program file referred to by `path`, then the **effective user ID** of the calling process is changed to that of the **owner of the program file**. Similarly, if the set-group-ID bit is set …, then the **effective group ID** … is set to the group of the program file.
>
> The effective user ID of the process is **copied to the saved set-user-ID**; similarly, the effective group ID is copied to the saved set-group-ID. **This copying takes place after any effective ID changes** that occur because of the set-user-ID and set-group-ID mode bits.
>
> The process's **real UID and real GID, as well as its supplementary group IDs, are unchanged** by a call to `execve()`.

整理成表（以「uid 1000 的用户执行属主为 root 的 SUID 程序」为例）：

| ID | exec 前 | exec 后 | 谁定的 |
|----|---------|---------|--------|
| RUID | 1000 | **1000**（不变） | `execve` 规定 real 侧不动 |
| EUID | 1000 | **0** | set-user-ID 位 → 文件属主 |
| SUID | 1000 | **0** | ← 新的 EUID，**无条件**拷贝 |
| 补充组 | 原样 | **原样** | `execve` 不动 |
| fsuid | 1000 | **0** | 内核保证「euid 变则 fsuid 跟随」 |

> ⚠️ **「不带 set-user-ID 位时 saved 不更新」是错的。** `execve(2)` 那句 "*This copying takes place after any effective ID changes*" 没有任何前提条件——**saved 永远被设成新的 euid**。所以普通程序 exec 之后 `saved == euid == ruid`，这也是为什么普通程序能安全地 `seteuid(getuid())`（[9.4](./9.4-saved-id.md)）。

### 三、四条「set-user-ID 位被无视」的路径

内核全部逻辑在 `fs/exec.c:1602` 的 `bprm_fill_uid()`，只有 20 行：

```c
static void bprm_fill_uid(struct linux_binprm *bprm, struct file *file)   /* :1602 */
{
    ...
    if (!mnt_may_suid(file->f_path.mnt))                     /* :1611 */
        return;                       /* ① 挂载带 nosuid */
    if (task_no_new_privs(current))                          /* :1614 */
        return;                       /* ② no_new_privs 置位 */
    mode = READ_ONCE(inode->i_mode);
    if (!(mode & (S_ISUID|S_ISGID)))                          /* :1618 */
        return;                       /* ③ 压根没这两位 */
    ...
    if (!vfsuid_has_mapping(bprm->cred->user_ns, vfsuid) ||   /* :1633 */
        !vfsgid_has_mapping(bprm->cred->user_ns, vfsgid))
        return;                       /* ④ 属主在本 ns 里没有映射 */
    ...
}
```

| # | 条件 | 源码 | man 里有吗 |
|---|------|------|-----------|
| ① | 文件所在挂载点带 `nosuid` | `fs/exec.c:1611` `mnt_may_suid()` | `execve(2)`：有（"the underlying filesystem is mounted nosuid"） |
| ② | 线程设了 `no_new_privs` | `fs/exec.c:1614` `task_no_new_privs()` | `execve(2)`：有（"the no_new_privs attribute is set for the calling thread"） |
| ③ | 文件本身没这两位 | `fs/exec.c:1618` | 不算条件，是常识 |
| ④ | **文件属主在本 user namespace 里没有映射** | `fs/exec.c:1633` `vfsuid_has_mapping()` | ❌ **`execve(2)` 里没有这条** |

`execve(2)` 列的是三条（nosuid / no_new_privs / **被 ptrace**）。第 3 条 ptrace 走的是**另一条路径**：`check_unsafe_exec()`（`fs/exec.c:1564-1600`）把 `LSM_UNSAFE_PTRACE`（`:1569-1570`，判据是 `p->ptrace`）和 `LSM_UNSAFE_NO_NEW_PRIVS`（`:1576-1577`）一起记在 `bprm->unsafe` 上，交给 LSM 钩子在真正设凭证之前拦下 —— 它**不在** `bprm_fill_uid()` 里。所以「man 与源码」的对照结论是：

> **`bprm_fill_uid()` 有四条 return，`execve(2)` 只写了其中两条半。第 ④ 条（属主无映射）是最容易在容器 / user namespace 环境里踩到、而文档里查不到的那一条。**

### 四、set-group-ID 多一个条件：必须同时有**组执行位**

`fs/exec.c:1642`：

```c
if ((mode & (S_ISGID | S_IXGRP)) == (S_ISGID | S_IXGRP)) {
    bprm->per_clear |= PER_CLEAR_ON_SETID;
    bprm->cred->egid = vfsgid_into_kgid(vfsgid);
}
```

对照 set-user-ID 那一支（`:1637` 只判 `mode & S_ISUID`）。也就是说：

| 模式 | 八进制 | set-user-ID 生效？ | set-group-ID 生效？ |
|------|--------|--------------------|---------------------|
| `-rwSr--r--` | `4644` | ✅ | — |
| `-rwxr-sr-x` | `2755` | — | ✅（**有** `x`） |
| `-rwxr-Sr-x` | `2745` | — | ❌（**没有** `x`） |

大写 `S` 就是「位开了但没有执行位」的显示形式，它**不会**提升 egid。这是 `ls -l` 输出的一个真实陷阱。

### 五、**写操作会清掉 SUID/SGID 位**

这一条不在 `execve(2)` 里，但在实践中最常撞上：**你以为设好了 SUID 位，一改文件内容就没了**。原理是内核的 `file_remove_privs()`——只要以**可写**方式打开并写入，就清掉 `S_ISUID|S_ISGID`。本节实测把这个过程做成了 7 步。

推论：

- **想改一个 SUID 程序的内容再保持 SUID，必须先改内容、再 `chmod u+s`**；
- 反过来，**「改一个既有 SUID 程序的正文来提权」这条路被内核堵死了**（普通用户本来就无权改属主为 root 的文件，这一条是给「有写权限但不是属主」的边界情况兜底）；
- **只读打开不动它**（实测第 [5] 步）。

### 六、`nosuid` 挂载与错误码

`execve(2)` ERRORS 里有一条：

> **EPERM** The filesystem is mounted `nosuid`, the user is not the superuser, and the file has the set-user-ID or set-group-ID bit set.

同一份 man 的 NOTES 里还提醒：

> The result of mounting a filesystem `nosuid` **varies across Linux kernel versions**: some will refuse execution of set-user-ID and set-group-ID executables when this would give the user powers she did not have already …, and (for a root user) some will **silently ignore** the set-user-ID and set-group-ID bits and `exec()` successfully.

**「静默忽略」和「报 EPERM」两种行为都合法**，所以别把「exec 没报错」当成「提权成功了」。

## 代码

### c9_6 set-user-ID 位：能做的实验 + 四条让它失效的路

[`../code/c9_6_suid_bit.c`](../code/c9_6_suid_bit.c) 做三件在这里**真能观测**的事：

1. **7 步观察「写文件会不会清掉 SUID/SGID 位」**——`chmod 04755` → 写 1 字节 → 看位；再 `chmod 04755` → **只读**打开 → 看位还在；`chmod 02755` → 再写一次。这一组对照能同时证明「写会清」和「读不会清」。
2. **扫出镜像里现存的 SUID 文件**（`/usr/bin`、`/usr/lib/openssh`、`/bin`、`/usr/sbin`、`/sbin` 五个目录）。
3. **把扫到的那个 SUID 文件 `execve` 一遍**，逐条打印「挂载点有没有 nosuid」「属主在不在 `uid_map` 里」「退出码是多少」。

```c
/* c9_6_suid_bit.c —— set-user-ID 位：能做的实验与四条「让它失效」的路
 *
 * 9.3 的主题：set-user-ID / set-group-ID 程序。
 *
 * 这一节最容易被写成「exec 之后 euid 变成文件属主」一句话就完了。其实内核里有
 * **四条独立的路径**会让这个位被无视（fs/exec.c:1602 bprm_fill_uid()）：
 *
 *   :1611  if (!mnt_may_suid(file->f_path.mnt)) return;          <- 挂载带 nosuid
 *   :1614  if (task_no_new_privs(current)) return;               <- no_new_privs=1
 *   :1618  if (!(mode & (S_ISUID|S_ISGID))) return;              <- 压根没这位
 *   :1633  if (!vfsuid_has_mapping(ns, vfsuid) || ...) return;   <- 属主在 ns 里没映射
 *
 * 对比 execve(2) 的 man：它只列了前三条里的 nosuid / no_new_privs / 正被 ptrace。
 * 「属主没映射」这条 man 里没写，只在源码里。
 *
 * 本程序做两件**在这里真能观测**的事：
 *   ① set-user-ID 位会被「写文件」清掉（只读打开不会）—— 这是内核
 *      file_remove_privs() 的行为，也解释了为什么不能靠改一个 setuid 程序来提权。
 *   ② 扫出镜像里现存的 SUID 文件，然后把它 execve 一遍，看看到底发生了什么。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_6_suid_bit c9_6_suid_bit.c
 */
#define _GNU_SOURCE
#include <dirent.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/prctl.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

static void show_mode(const char *path, const char *tag)
{
    struct stat st;
    if (stat(path, &st) == -1) {
        printf("    %-16s stat失败: %s\n", tag, strerror(errno));
        return;
    }
    printf("    %-16s mode=%04o  u+s=%s g+s=%s  uid=%u gid=%u\n",
           tag, (unsigned) (st.st_mode & 07777),
           (st.st_mode & S_ISUID) ? "ON " : "off",
           (st.st_mode & S_ISGID) ? "ON " : "off",
           (unsigned) st.st_uid, (unsigned) st.st_gid);
}

/* 实验 ①：写文件会不会清掉 set-user-ID / set-group-ID 位 */
static void experiment_write_clears_bit(void)
{
    const char *p = "/tmp/c9_suid_demo";
    printf("\n=== ① set-user-ID 位 vs 写文件 ===\n");
    unlink(p);
    int fd = open(p, O_CREAT | O_WRONLY | O_TRUNC, 0644);
    if (fd == -1) {
        printf("    建文件失败: %s\n", strerror(errno));
        return;
    }
    if (write(fd, "hello\n", 6) != 6)
        printf("    (写入长度不符)\n");
    close(fd);

    show_mode(p, "[1] 新建");
    if (chmod(p, 04755) == -1)
        printf("    chmod 04755 失败: %s\n", strerror(errno));
    show_mode(p, "[2] chmod 04755");
    fd = open(p, O_WRONLY | O_APPEND);
    if (fd == -1) {
        printf("    以写打开失败: %s\n", strerror(errno));
    } else {
        if (write(fd, "x", 1) != 1)
            printf("    (写入长度不符)\n");
        close(fd);
    }
    show_mode(p, "[3] 写了 1 字节");

    if (chmod(p, 04755) == -1)
        printf("    chmod 失败: %s\n", strerror(errno));
    show_mode(p, "[4] 再 chmod");
    fd = open(p, O_RDONLY);
    if (fd != -1) {
        char c;
        if (read(fd, &c, 1) < 0)
            printf("    (读失败)\n");
        close(fd);
    }
    show_mode(p, "[5] 只读打开");

    if (chmod(p, 02755) == -1)
        printf("    chmod 失败: %s\n", strerror(errno));
    show_mode(p, "[6] chmod 02755");
    fd = open(p, O_WRONLY | O_APPEND);
    if (fd != -1) {
        if (write(fd, "x", 1) != 1)
            printf("    (写入长度不符)\n");
        close(fd);
    }
    show_mode(p, "[7] 再写一次");
    unlink(p);
    printf("    结论: 一写就把 u+s / g+s 位清掉；只读不动。\n");
}

/* 实验 ②：扫出 SUID 文件 */
static int scan_suid(char found[][512], int max)
{
    const char *dirs[] = { "/usr/bin", "/usr/lib/openssh", "/bin", "/usr/sbin", "/sbin" };
    int n = 0;
    for (unsigned d = 0; d < sizeof dirs / sizeof dirs[0]; d++) {
        DIR *dp = opendir(dirs[d]);
        if (dp == NULL)
            continue;
        struct dirent *e;
        while ((e = readdir(dp)) != NULL && n < max) {
            if (e->d_name[0] == '.')
                continue;
            char full[512];
            snprintf(full, sizeof full, "%s/%s", dirs[d], e->d_name);
            struct stat st;
            if (stat(full, &st) == -1)
                continue;
            if (S_ISREG(st.st_mode) && (st.st_mode & S_ISUID)) {
                snprintf(found[n], 512, "%s", full);
                printf("    %04o uid=%u gid=%u  %s\n",
                       (unsigned) (st.st_mode & 07777), (unsigned) st.st_uid,
                       (unsigned) st.st_gid, full);
                n++;
            }
        }
        closedir(dp);
    }
    return n;
}

/* 实验 ③：这个文件所在的挂载点有没有 nosuid */
static void check_nosuid(const char *path)
{
    char dir[512];
    snprintf(dir, sizeof dir, "%s", path);
    char *slash = strrchr(dir, '/');
    if (slash != NULL)
        *slash = '\0';

    FILE *fp = fopen("/proc/self/mounts", "r");
    if (fp == NULL) {
        printf("    打不开 /proc/self/mounts\n");
        return;
    }
    char dev[256], mnt[512], fstype[64], opts[512];
    int printed = 0;
    while (fscanf(fp, "%255s %511s %63s %511s%*[^\n]\n", dev, mnt, fstype, opts) == 4) {
        size_t l = strlen(mnt);
        if (strncmp(dir, mnt, l) == 0 && (l == 1 || dir[l] == '/' || dir[l] == '\0')) {
            printf("    挂载点 %s (%s) 选项: %s\n", mnt, fstype, opts);
            printf("    -> 含 nosuid? %s\n", strstr(opts, "nosuid") ? "是（SUID 位被无视）" : "否");
            printed = 1;
            break;
        }
    }
    fclose(fp);
    if (!printed)
        printf("    没找到匹配的挂载点\n");
}

int main(void)
{
    printf("=== 决定「set-user-ID 位管不管用」的四个开关 ===\n");
    printf("  fs/exec.c:1611  mnt_may_suid()         挂载带 nosuid -> 无视\n");
    printf("  fs/exec.c:1614  task_no_new_privs()    no_new_privs=1 -> 无视\n");
    printf("  fs/exec.c:1618  mode & (S_ISUID|S_ISGID)  没这位 -> 无视\n");
    printf("  fs/exec.c:1633  vfsuid_has_mapping()   属主在 ns 里没映射 -> 无视\n");

    printf("\n=== 本进程相关状态 ===\n");
    {
        FILE *fp = fopen("/proc/self/status", "r");
        char buf[512];
        while (fp != NULL && fgets(buf, sizeof buf, fp) != NULL)
            if (strncmp(buf, "NoNewPrivs:", 11) == 0 || strncmp(buf, "CapEff:", 7) == 0)
                printf("  %s", buf);
        if (fp != NULL)
            fclose(fp);
    }
    errno = 0;
    printf("  prctl(PR_GET_NO_NEW_PRIVS) = %d  errno=%d\n",
           prctl(PR_GET_NO_NEW_PRIVS, 0, 0, 0, 0), errno);

    experiment_write_clears_bit();

    printf("\n=== ② 镜像里现存的 SUID 文件 ===\n");
    static char found[64][512];
    int n = scan_suid(found, 64);
    printf("    共 %d 个\n", n);

    if (n > 0) {
        const char *victim = found[0];
        printf("\n=== ③ 把 %s execve 一遍 ===\n", victim);
        check_nosuid(victim);
        show_mode(victim, "目标");
        printf("    它的属主 uid 在本 ns 的 uid_map 里吗？\n");
        {
            FILE *fp = fopen("/proc/self/uid_map", "r");
            char buf[256];
            printf("      uid_map: ");
            while (fp != NULL && fgets(buf, sizeof buf, fp) != NULL)
                printf("%s", buf);
            if (fp != NULL)
                fclose(fp);
            printf("      （只有一行 \"0 113 1\" -> uid 65534 不在里面）\n");
        }

        fflush(stdout);              /* ⚠️ fork 之前必须 flush，否则子进程会把缓冲吐两遍 */
        pid_t pid = fork();
        if (pid == 0) {
            char *args[] = { (char *) victim, NULL };
            char *envp[] = { NULL };
            execve(victim, args, envp);
            printf("    execve 失败: %s\n", strerror(errno));
            fflush(stdout);
            _exit(127);
        }
        int st = 0;
        if (waitpid(pid, &st, 0) == -1) {
            perror("waitpid");
        } else if (WIFEXITED(st)) {
            printf("    退出码 = %d\n", WEXITSTATUS(st));
        } else if (WIFSIGNALED(st)) {
            printf("    被信号杀掉 = %d\n", WTERMSIG(st));
        }
        printf("    注意: 本程序**没变** —— 它既没有 set-user-ID 提权，也没有崩。\n");
    }

    printf("\n=== 小结（四条路里，这台机器上是哪几条在起作用）===\n");
    printf("  - no_new_privs=1  -> 开着（见上）\n");
    printf("  - nosuid          -> 见 ③ 的挂载点输出\n");
    printf("  - 属主未映射      -> 见 ③ 的 uid_map 输出（65534 不在映射里）\n");
    printf("  三条都是**独立的**，任意一条成立，set-user-ID 位就不生效。\n");
    return 0;
}
```

```text
    -> 含 nosuid? 否
    目标           mode=4755  u+s=ON  g+s=off  uid=65534 gid=65534
    它的属主 uid 在本 ns 的 uid_map 里吗？
      uid_map:          0        113          1
      （只有一行 "0 113 1" -> uid 65534 不在里面）
    退出码 = 255
    注意: 本程序**没变** —— 它既没有 set-user-ID 提权，也没有崩。

=== 小结（四条路里，这台机器上是哪几条在起作用）===
  - no_new_privs=1  -> 开着（见上）
  - nosuid          -> 见 ③ 的挂载点输出
  - 属主未映射      -> 见 ③ 的 uid_map 输出（65534 不在映射里）
  三条都是**独立的**，任意一条成立，set-user-ID 位就不生效。
```

子进程 stderr 另有一行 `getpwuid failed`（那个 SUID 程序自己打的诊断，不是本程序的输出）。

**解读**

1. **第 [2]→[3] 步是本节的硬证据**：`mode=4755 u+s=ON` → 写 1 字节 → `mode=0755 u+s=off g+s=off`。**一次 `write()` 就把 set-user-ID 位清掉了。** 第 [6]→[7] 步对 set-group-ID 做同样的实验，结果一致（`2755` → 写入 → `0755`）。
2. **第 [4]→[5] 步是对照组**：`chmod 04755` 之后**只读**打开、只 `read()` 1 字节，`mode` 仍是 `4755`，位**没被清**。所以「清位」的触发条件是**打开方式为可写**，不是「碰了这个文件」。这就是内核 `file_remove_privs()` 的行为；也是为什么 `chmod u+s` 必须放在**改完内容之后**。
3. **第 ② 段只扫出 1 个 SUID 文件**，而且它的属主是 **uid 65534**（`overflowuid`，即 `nobody`）——不是 root。这本身就是个信号：评测镜像为了安全，把 SUID 面压到了最小。
4. **第 ③ 段的信息量最大**，三行证据各堵住一条路：
   - `挂载点 / (tmpfs) 选项: ro,relatime,uid=113,gid=113,inode64` → **不含 `nosuid`**，说明**不是** ① 号路在起作用；
   - `NoNewPrivs: 1`（第 ③ 段上方已打印）→ ② 号路**开着**；
   - `uid_map: 0 113 1`，而目标属主是 `65534` → **65534 不在映射里**，④ 号路**也开着**。
   所以这台机器上是**两条**独立的路同时把 SUID 位废掉了。程序末尾的小结说的就是这件事：「三条都是**独立的**，任意一条成立，set-user-ID 位就不生效。」
5. **`退出码 = 255` 与「本程序没变」**要一起读。`ssh-keysign` 因为拿不到自己的身份（`getpwuid(65534)` 失败）而主动退出 255——这是**这个程序自己的逻辑**，不是内核拒绝 exec。真正说明问题的是最后那句断言：**它既没有提权，也没有崩**。如果 ④ 号路不存在，`execve` 会让 euid 变成 65534（一个完全没映射的值），后续一切 uid 相关调用都会 EINVAL——那才是更糟的形态。
6. **给真机对照一个预期**：在普通 Linux 上执行一个 `4755 root:root` 的 SUID 程序，`euid` 会变成 0、`saved` 也变成 0、`ruid` 保持自己——这就是 [9.4](./9.4-saved-id.md) 要利用的那个初始状态。

## HFT / 嵌入式关联

- **SUID 是攻击面，嵌入式上尤其要数得清。** 本节实测的评测镜像整个文件系统**只有 1 个** SUID 文件——这是刻意的加固。自研嵌入式固件里常见十几二十个（`busybox`、`su`、`mount`、`passwd`、厂商工具），每一个都是本地提权入口。**定期 `find / -perm -4000 -type f` 是嵌入式安全基线的一条。**
- **`nosuid` 挂载是嵌入式最好用的一招。** 数据分区（`/data`、SD 卡、厂商可写区）用 `nosuid,nodev,noexec` 挂载，能一次性废掉「往可写分区放 SUID 二进制再执行」这类提权链。注意 `execve(2)` 的 NOTES 提醒：**内核对 nosuid 的处理在不同版本间不一致**，有的直接 EPERM、有的静默忽略——所以别把「exec 成功」当成「提权成功」。
- **`no_new_privs` 是单程票，谨慎用在长生命周期进程上。** 交易进程 / 行情网关启动早期设了 `prctl(PR_SET_NO_NEW_PRIVS, 1, ...)`（`kernel/sys.c:2570` 只接受 `arg2==1`，无法取消）之后，后面**任何**依赖 SUID helper 的动作都会静默失效。要设就在「所有需要提权的初始化都做完」之后设。
- **「属主无映射」这条隐形路径在容器编排里会咬人。** 打包 SUID 程序进镜像时，如果 `Dockerfile` 里 `chown` 的 uid 在运行时容器的 `uid_map` 里不存在，SUID 位**不会报错**，只是**不生效**——排查时看 `uid_map` 比看 `ls -l` 有用。本节实测的 `65534` 就是活样本。
- **`file_remove_privs()` 会毁掉你精心设的位。** 构建流程里若在 `chmod u+s` 之后还有任何写操作（写配置、`strip`、重新打包），位就没了。CI 里加一条 `[ "$(stat -c %a bin/tool)" = 4755 ]` 的断言，比事后排查省事得多。
- **大写 `S` 的陷阱在嵌入式脚本里常见**：`chmod 2745`（没有 `x`）在 `ls -l` 里看着像 set-group-ID，实际不生效（`fs/exec.c:1642` 要求两个位都在）。构建脚本里统一用 `2755`。

## 自测题

<details>
<summary>1. 一个 <code>-rwsr-xr-x root root</code> 的程序被 uid 1000 的用户执行，exec 之后 R/E/S 各是多少？</summary>

| ID | 值 | 为什么 |
|----|----|--------|
| RUID | **1000** | `execve(2)`："The process's real UID and real GID … are unchanged" |
| EUID | **0** | set-user-ID 位 → 文件属主 |
| SUID | **0** | `execve(2)`："The effective user ID is copied to the saved set-user-ID … after any effective ID changes" |
| fsuid | **0** | 内核保证「euid 变则 fsuid 跟随」 |

注意 **saved 变成 0 是无条件的**（只要 euid 变了），不是因为「有 SUID 位才更新」。这也正是 `passwd` 能在 `seteuid(1000)` 降权之后**再 `seteuid(0)` 升回去**的本钱（[9.4](./9.4-saved-id.md)）。

⚠️ 前提是**上面四条路都没关着**：挂载点不带 `nosuid`、进程没有 `no_new_privs`、文件属主在本 user namespace 里有映射。本节实测里最后一条就不成立（属主 65534 不在 `uid_map` 里），所以那个 SUID 文件 exec 之后**权限一点没变**。
</details>

<details>
<summary>2. <code>chmod 2755</code> 和 <code>chmod 2745</code> 有什么区别？哪个的 set-group-ID 会生效？</summary>

**`2755` 生效，`2745` 不生效。**

`fs/exec.c:1642`：

```c
if ((mode & (S_ISGID | S_IXGRP)) == (S_ISGID | S_IXGRP)) {   /* 两个位都要有 */
    bprm->per_clear |= PER_CLEAR_ON_SETID;
    bprm->cred->egid = vfsgid_into_kgid(vfsgid);
}
```

对比 set-user-ID 那一支（`:1637`）只判 `mode & S_ISUID`，**没有**「同时要有 user 执行位」这个要求。所以两个位的生效条件**不对称**：

| 模式 | 八进制 | `ls -l` | set-group-ID 生效？ |
|------|--------|---------|---------------------|
| `rwxr-sr-x` | `2755` | 小写 `s` | ✅ |
| `rwxr-Sr-x` | `2745` | **大写 `S`** | ❌（缺 `IXGRP`） |
| `rwSr--r--` | `4644` | 大写 `S` | set-uid 位：✅（不要求 `x`） |

所以 `ls -l` 里看到**大写 `S`** 就说明「位设了但不会生效」。构建脚本里老老实实写 `2755`。
</details>

<details>
<summary>3. 为什么我 <code>chmod u+s</code> 之后一改文件内容，<code>s</code> 就没了？</summary>

**因为内核在以可写方式打开并写入时，会主动清掉 `S_ISUID|S_ISGID`**（`file_remove_privs()`）。

本节 7 步实测：

```text
    [2] chmod 04755  mode=4755  u+s=ON  g+s=off   ← 位开
    [3] 写了 1 字节 mode=0755  u+s=off g+s=off   ← 写一次就清掉
    [4] 再 chmod    mode=4755  u+s=ON  g+s=off   ← 重新开
    [5] 只读打开 mode=4755  u+s=ON  g+s=off   ← 只读不动它
    [6] chmod 02755  mode=2755  u+s=off g+s=ON    ← setgid 位同理
    [7] 再写一次 mode=0755  u+s=off g+s=off   ← 也被清
```

第 [4]→[5] 步是**对照组**：只读打开**不会**清位。所以触发条件是「**可写**打开」，不是「碰了这个文件」。

两条推论：

- **顺序很重要**：先改内容，最后 `chmod u+s`。反了就要重设。
- **这条机制本身是一道防线**：「改一个既有 SUID 程序的正文来提权」被堵死了，因为写操作直接把 SUID 位拿掉，改完还得重新 `chmod`——而 `chmod` 需要属主权限。
</details>

<details>
<summary>4. 我 <code>chmod u+s</code> 了，<code>ls -l</code> 也显示 <code>-rwsr-xr-x</code>，为什么运行起来 EUID 还是我自己？</summary>

因为还有**四条独立的路**能让这个位被无视（`fs/exec.c:1602` 的 `bprm_fill_uid()`）：

| # | 检查 | 怎么查 |
|---|------|--------|
| ① | 挂载点带 `nosuid` | `grep " $(df -P /path \| tail -1 \| awk '{print $6}') " /proc/mounts` |
| ② | 进程有 `no_new_privs` | `grep NoNewPrivs /proc/self/status`，或 `prctl(PR_GET_NO_NEW_PRIVS)` |
| ③ | 文件没有这两位 | `stat -c %A file` |
| ④ | **文件属主在本 user namespace 里没有映射** | `cat /proc/self/uid_map`，看属主 uid 在不在映射范围内 |

第 ④ 条**man 里没写**（`execve(2)` 只列了 nosuid / no_new_privs / ptrace），只在 `fs/exec.c:1633` 的 `vfsuid_has_mapping()` 里。

本节实测里 ② 和 ④ **同时**成立：

```text
  NoNewPrivs:	1
    4755 uid=65534 gid=65534  /usr/lib/openssh/ssh-keysign
      uid_map:          0        113          1
```

属主 65534 不在 `0 113 1` 这一行映射里，所以那个 SUID 文件 `execve` 之后「既没有 set-user-ID 提权，也没有崩」——这是设计使然，不是 bug。
</details>

<details>
<summary>5. <code>execve</code> 会改补充组吗？会改 <code>fsuid</code> 吗？</summary>

**补充组：不改。** `execve(2)`："The process's real UID and real GID, as well as its **supplementary group IDs, are unchanged** by a call to `execve()`."

**fsuid：会跟着 euid 变。** 虽然 `execve(2)` 没提，但 `credentials(7)` 有总纲："Whenever a process's effective user (group) ID is changed, the kernel **also automatically changes the filesystem user (group) ID to the same value**."。所以 SUID 程序 exec 之后 fsuid 也是 0。

这两条合起来有一个实践后果：**SUID 程序里「用 EUID 提权」这个能力对文件访问是自动生效的**，不需要额外动作（fsuid 跟着 euid 走）；但**补充组是启动者的**，所以「提权到 root 之后能访问哪些组文件」在 exec 前后**完全一样**。想让 egid/补充组也换，得靠 set-group-ID 位（`fs/exec.c:1642`）或 `setgroups()`（[9.6](./9.6-supplementary-groups.md)）。
</details>
