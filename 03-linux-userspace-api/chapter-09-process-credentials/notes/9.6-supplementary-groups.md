> 权威依据：`getgroups(2)`（man-pages 6.19）· `setgroups(2)` · `initgroups(3)` · `getgrouplist(3)` · `credentials(7)` · `user_namespaces(7)` · Linux v6.6 `kernel/groups.c`

## 本节讲什么

前五节讲的都是 UID/GID 的**单个**值。这一节讲一个**列表**：进程除了 `gid`/`egid` 之外，还能同时属于最多 65536 个组。

它在权限模型里的地位和前几类不同：**补充组是「额外通行证」，只增不减**。一个进程能访问的文件，等于「主身份能访问的」∪「补充组能访问的」。所以安全代码里 `setgroups(0, NULL)`（清空）往往比 `setuid` 更早做——**降权时漏掉它，等于留了一堆后门没关**。

本节要钉死四件事：

1. 读补充组的**惯用法**，以及 `getgroups()` 的**两个** `EINVAL` 分支（不是 `ERANGE`）；
2. 写补充组要过**两道独立闸门**——这是 man 里分两条 `EPERM` 写的，内核里也是两个函数；
3. **内核会排序**，所以「顺序」不是契约；
4. `initgroups()` 只是 `setgroups()` 的封装，它的失败方式**不可能**和 `setgroups()` 不同。

## 要点

### 一、补充组是权限检查的第三个分量

`credentials(7)`：

> **Supplementary group IDs.** This is a set of additional group IDs that are used for permission checks when accessing files and other shared resources. Before Linux 2.6.4, a process can be a member of up to **32** supplementary groups; since Linux 2.6.4, a process can be a member of up to **65536** supplementary groups. The call `sysconf(_SC_NGROUPS_MAX)` can be used to determine the number of supplementary groups of which a process may be a member. A process can obtain its set of supplementary group IDs using `getgroups(2)`.

Linux 上文件权限检查的完整输入（`path_resolution(7)`）：

```
1. fsuid == 文件属主 uid ?          -> 用 owner 权限位
2. 否则 fsgid == 文件属主 gid         -> 用 group 权限位
   或 文件属主 gid ∈ 补充组列表       （kernel/groups.c:234 in_group_p）
3. 否则                              -> 用 other 权限位
```

**关键的一条：第 2 步里比的是 `fsgid`，不是 `egid`**（[9.5](./9.5-fs-uid-gid.md)）。正常情况下两者相等，所以「egid 或补充组」这个说法在实践中成立。

### 二、三个接口

| 函数 | 头文件 | 原型 | 要特权？ |
|------|--------|------|----------|
| `getgroups` | `<unistd.h>` | `int getgroups(int size, gid_t list[])` | 不要 |
| `setgroups` | `<grp.h>` | `int setgroups(size_t size, const gid_t *list)` | **要 `CAP_SETGID`** + ns 允许 |
| `initgroups` | `<grp.h>` | `int initgroups(const char *user, gid_t group)` | 要（底层是 `setgroups`） |
| `getgrouplist` | `<grp.h>` | `int getgrouplist(const char *user, gid_t group, gid_t *list, int *ngroups)` | 不要（**只读库，不装**） |

**`getgroups` ←→ `setgroups` 的对称性**要提醒一句：`getgroups` 的 size 是 **`int`**（可以传负值，内核要判），`setgroups` 的 size 是 **`size_t`**（无符号，传不了负值）。这是历史遗留，写代码时别混。

### 三、读补充组的惯用法：先问个数再分配

`getgroups(2)` DESCRIPTION：

> If `size` is zero, `list` is not modified, but the **total number of supplementary group IDs** for the process is returned. This allows the caller to determine the size of a dynamically allocated list to be used in a further call to `getgroups()`.

```c
int n = getgroups(0, NULL);              /* 只问个数，不动缓冲 */
if (n < 0) die("getgroups");
gid_t *g = malloc(sizeof(gid_t) * (size_t) n);
if (g == NULL) die("malloc");
int got = getgroups(n, g);               /* got 可能 <= n */
```

两个细节：

- **第二次调用的返回值不一定等于 `n`**（组列表理论上可能在两次调用之间变化，虽然只在多个线程同时改凭证时才会），所以要**用 `got` 而不是 `n`** 去遍历和 `free`。
- **`n == 0` 是合法结果**（进程没有任何补充组）。此时**不要** `malloc(0)`（返回值可能是 `NULL` 也可能是非 `NULL`，都不算错），直接跳过。

### 四、`getgroups()` 的**两个** `EINVAL` 分支——都不是 `ERANGE`

`getgroups(2)` ERRORS：

> **EINVAL** `size` is less than the number of supplementary group IDs, but is not zero.

内核 `kernel/groups.c:163` 的 `SYSCALL_DEFINE2(getgroups, ...)`:

```c
if (gidsetsize < 0)                                              /* :168 */
    return -EINVAL;                     /* 分支 ①  负 size */

i = cred->group_info->ngroups;
if (gidsetsize) {
    if (i > gidsetsize) {                                        /* :174 */
        i = -EINVAL;                    /* 分支 ②  缓冲不够 */
        goto out;
    }
    if (groups_to_user(grouplist, cred->group_info)) {
        i = -EFAULT;                    /* :179  用户指针不合法 */
        goto out;
    }
}
```

| 分支 | 条件 | 返回 |
|------|------|------|
| ① | `size < 0` | `-EINVAL` |
| ② | `size > 0` 且 `size < 组数` | `-EINVAL` |
| ③ | `list` 指向非法地址 | `-EFAULT` |

> ⚠️ **这里不是 `ERANGE`。** 把「缓冲不够」写成 `ERANGE` 是很自然的类比（`getpwnam_r` 就是 `ERANGE`，见 [Ch8 §8.4](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)），但 `getgroups` 用的是 `EINVAL`。**同一个错误语义在不同 syscall 上用不同的 errno，这是 Linux 的常态**，只能查 man。

**顺带一个编译期彩蛋**：如果直接写 `getgroups(-1, NULL)`，gcc 会在 `-Wall` 下报 `-Wstringop-overflow`：

```
warning: 'getgroups' specified size 4294967295 exceeds maximum object size ...
```

原因是 glibc 的 `unistd.h` 给 `getgroups` 标了

```c
__attribute__((access(write_only, 2, 1)))
```

——编译器知道「size 为负」必然越界，所以**这个笔误其实是能被静态抓出来的**。本节 demo 里为了让内核真的返回 `EINVAL`（而不是编译不过），用一个 `volatile` 变量转了一手：

```c
volatile int neg_size = -1;
int r = getgroups(neg_size, NULL);       /* 编译器不能在编译期知道具体值 -> 告警消失 */
```

**这不是绕过检查，而是把「编译器能抓 / 内核也会抓」两层防线都演示一遍。**

### 五、写补充组要过**两道**闸门

`getgroups(2)` ERRORS 里**有两条 `EPERM`**：

> **EPERM** The calling process has insufficient privilege (the caller does not have the `CAP_SETGID` capability in the user namespace in which it resides).
>
> **EPERM** (since Linux 3.19) The use of `setgroups()` is **denied in this user namespace**. See the description of `/proc/pid/setgroups` in `user_namespaces(7)`.

内核里这两条对应 `kernel/groups.c:187` 的 `may_setgroups()`，它是 `&&` 连接的两个条件：

```c
bool may_setgroups(void)                                       /* :187 */
{
    struct user_namespace *user_ns = current_user_ns();

    return ns_capable_setid(user_ns, CAP_SETGID) &&            /* :191 闸门 ① */
           userns_may_setgroups(user_ns);                      /* :192 闸门 ② */
}
```

| 闸门 | 条件 | 怎么查 | 怎么开 |
|------|------|--------|--------|
| ① | 有 `CAP_SETGID` | `/proc/self/status` 的 `CapEff` | 加 capability |
| ② | 本 ns 允许 `setgroups` | `cat /proc/self/setgroups`（`allow` / `deny`） | 写 `deny` 是**关**，不是开 |

**两道是独立的**：`CapEff` 够了但 ns 是 `deny` 也失败；ns 是 `allow` 但没 capability 也失败。而且**靠 errno 分辨不出是哪一道**——两条都返回 `EPERM(1)`。

`/proc/pid/setgroups` 的语义（`user_namespaces(7)`）：

> The `/proc/pid/setgroups` file displays the string "**allow**" if processes in the user namespace that contains the process `pid` are permitted to employ the `setgroups(2)` system call; it displays "**deny**" if `setgroups(2)` is **not** permitted in that user namespace. **Note that regardless of the value in the `/proc/pid/setgroups` file (and regardless of the process's capabilities), calls to `setgroups(2)` are also not permitted if `/proc/pid/gid_map` has not yet been set.**
>
> **Writing "deny" … will permanently disable `setgroups(2)`** in a user namespace and **allow writing to `/proc/pid/gid_map` without having the `CAP_SETGID` capability** in the parent user namespace.

所以 `deny` 是一个**交易**：放弃 `setgroups` 能力，换取「无特权也能写 `gid_map`」。这条规则的存在本身说明了 `setgroups` 有多敏感——**内核宁可让你放弃它，也不让你在映射了组之后还能改组成员的身份**。

> 📌 这里有一句容易被忽略的话：「**`gid_map` 没写之前，`setgroups` 也是不允许的**」。也就是说在一个刚 `unshare(CLONE_NEWUSER)` 出来的新 ns 里，`setgroups` **必然**失败——不管 `setgroups` 文件写着什么。[9.7](./9.7-api.md) 的实测里能看到这个组合。

### 六、内核会**排序**，所以「顺序」不是契约

`kernel/groups.c:200` 的 `setgroups()` 里有一句（`:219`）：

```c
groups_sort(group_info);                                   /* :219 */
retval = set_current_groups(group_info);
```

`groups_sort()`（`:88-90`）内部就是 `sort(group_info->gid, ..., gid_cmp, NULL)`。**排序的目的是让二分查找成立**——`groups_search()`（`:94`）是一个手写的 `bsearch`：

```c
/* a simple bsearch */
int groups_search(const struct group_info *group_info, kgid_t grp)   /* :94 */
{
    ...
    while (left < right) {
        unsigned int mid = (left+right)/2;
        if (gid_gt(grp, group_info->gid[mid])) left = mid + 1;
        else if (gid_lt(grp, group_info->gid[mid])) right = mid;
        else return 1;
    }
```

所以：

- **`getgroups()` 返回的顺序是内核排过序的**（升序），不是你 `setgroups()` 时传进去的顺序；
- **不要写「假设 `groups[0]` 是主组」这类代码**；
- 反过来，`setgroups()` 的内部排序**意味着你可以放心用 O(n) 的线性查找**在自己的代码里（组数通常个位数）。

### 七、`initgroups()` = 读库 + `setgroups()`，没有别的花样

`initgroups(3)` DESCRIPTION：

> The `initgroups()` function initializes the group access list by **reading the group database `/etc/group`** and using all groups of which `user` is a member. **The additional group `group` is also added to the list.**

`initgroups(3)` ERRORS **只有两条**：

> **ENOMEM** Insufficient memory to allocate group information structure.
> **EPERM** The calling process has insufficient privilege. **See the underlying system call `setgroups(2)`.**

**「EPERM 见 `setgroups(2)`」这句话是本节最有用的一句**：它意味着 `initgroups()` **不可能**有独立的失败模式——它失败在 `EPERM` 上时，`setgroups()` 也必然以同样的原因失败。本节实测把这件事做成了两行并排的输出。

对称地，`getgrouplist(3)` 做的是**同一套算法，但只读系统组库（NSS）、不装**。所以：

| 函数 | 读什么 | 装吗 |
|------|--------|------|
| `initgroups(user, gid)` | NSS 组库（通常是 `/etc/group`，但可被 `nsswitch.conf` 改成 LDAP/SSSD） | ✅ 调 `setgroups()` |
| `getgrouplist(user, gid, ...)` | NSS 组库 | ❌ 只把列表写进出参缓冲 |

**这两个函数读的是「系统组库」而不是「某个文件」**——本节实测里那个 `errno=2 (ENOENT)` 就是这条的副产品：容器里既没有 `/etc/group` 也没有 `nsswitch.conf`，NSS 走到底没找到任何后端。

> ⚠️ 注意 `initgroups(3)` 的 man 里写 "reading the group database `/etc/group`"，这是**简化说法**。glibc 的实现走 NSS，实际后端由 `/etc/nsswitch.conf` 决定。**在接了 LDAP / SSSD 的机器上，`initgroups()` 可能是一次网络往返**——启动路径里不要小看它。

### c9_3 补充组：怎么读、为什么写不了

[`../code/c9_3_groups.c`](../code/c9_3_groups.c) 六段，把上面的要点逐条做成实测：

| 段 | 做什么 |
|----|--------|
| ① | 读补充组的惯用法：`getgroups(0, NULL)` 问个数 → 分配 → 再取 |
| ② | `getgroups()` 的**负 size** 分支（`volatile` 转一手以拿到内核的 EINVAL，而不是编译告警） |
| ③ | 写补充组的**两道闸门**：`CapEff` 与 `/proc/self/setgroups`，加 `setgroups(0, NULL)` 的实测返回 |
| ④ | `initgroups()` 与 `setgroups()` **同因同果** |
| ⑤ | `getgrouplist()` 读的是 NSS 组库（本容器没有，所以只剩 `basegid`） |
| ⑥ | 内核排序 / 二分 / `in_group_p()` 比 fsgid 三条源码事实 |

```c
/* c9_3_groups.c —— 补充组：怎么读、为什么写不了
 *
 * 9.6 的主题：Supplementary Group IDs。
 *
 * 本程序要坐实四件事：
 *   ① 读补充组的**惯用法**：先 getgroups(0, NULL) 问个数，再分配、再取。
 *   ② getgroups() 的两个 EINVAL 分支（负 size / 缓冲不够）在源码里是两处不同判断。
 *   ③ 写补充组（setgroups）要过**两道独立闸门**：CAP_SETGID 与 ns 是否允许；
 *      本环境两道都关着，而且能分别看到证据。
 *   ④ initgroups() 只是 setgroups() 的封装，所以它失败的方式和 setgroups() 一样。
 *
 * 权威依据：
 *   - kernel/groups.c:163 getgroups()：`if (gidsetsize < 0) return -EINVAL;`
 *     以及 :174 `if (i > gidsetsize) { i = -EINVAL; }`（注意**不是 ERANGE**）。
 *   - kernel/groups.c:187 may_setgroups()：
 *       `return ns_capable_setid(user_ns, CAP_SETGID) && userns_may_setgroups(user_ns);`
 *   - kernel/groups.c:200 setgroups() 里（:219）`groups_sort(group_info);` —— 内核会排序。
 *   - kernel/groups.c:229 in_group_p()：先比 **fsgid**，再二分查补充组。
 *   - getgroups(2) ERRORS / EPERM（两个来源）；initgroups(3) ERRORS -> setgroups(2)。
 *   - /proc/pid/setgroups = "deny" 的含义见 user_namespaces(7)。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_3_groups c9_3_groups.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <grp.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static void show_setgroups_file(void)
{
    FILE *fp = fopen("/proc/self/setgroups", "r");
    printf("--- /proc/self/setgroups ---\n");
    if (fp == NULL) {
        printf("  (打不开)\n");
        return;
    }
    char buf[64];
    while (fgets(buf, sizeof buf, fp) != NULL)
        printf("  %s", buf);
    fclose(fp);
}

int main(void)
{
    printf("=== ① 读补充组的惯用法 ===\n");
    errno = 0;
    int n = getgroups(0, NULL);          /* size=0：不动缓冲，只回个数 */
    printf("  getgroups(0, NULL) = %d   errno=%d\n", n, errno);
    if (n < 0) {
        perror("getgroups");
        return 1;
    }
    if (n == 0) {
        printf("  （本进程没有任何补充组）\n");
    } else {
        gid_t *g = malloc(sizeof(gid_t) * (size_t) n);
        if (g == NULL) {
            perror("malloc");
            return 1;
        }
        errno = 0;
        int got = getgroups(n, g);
        printf("  getgroups(%d, buf) = %d   errno=%d\n", n, got, errno);
        printf("  列表:");
        for (int i = 0; i < got; i++)
            printf(" %u", (unsigned) g[i]);
        printf("\n");
        free(g);
    }

    printf("\n=== ② getgroups() 的两个 EINVAL 分支 ===\n");
    /* 这里的 -1 是**故意**的。有意思的是：如果直接写 getgroups(-1, NULL)，
     * gcc（-Wall）会报 -Wstringop-overflow，因为 unistd.h 里给 getgroups 标了
     * "__attribute__((access(write_only, 2, 1)))" —— 编译器知道「size 为负」
     * 必然越界，所以这个笔误是能被静态抓出来的。用一个 volatile 变量转一手，
     * 编译器就无法在编译期知道具体值，告警随之消失；内核那边照样返回 EINVAL。 */
    volatile int neg_size = -1;
    errno = 0;
    int r = getgroups(neg_size, NULL);   /* 负 size —— 源码里第一处判断 */
    printf("  getgroups(-1, NULL)  = %d  errno=%d (%s)\n", r, errno, strerror(errno));
    printf("  「缓冲不够」那一支（size 比组数少且非 0）在源码里是另一处判断，\n");
    printf("  本环境只有 %d 个补充组，构造不出（需要 >= 2 个组）。\n", n > 0 ? n : 0);

    printf("\n=== ③ 写补充组要过两道闸门 ===\n");
    show_setgroups_file();
    errno = 0;
    r = setgroups(0, NULL);
    printf("  setgroups(0, NULL)   = %d  errno=%d (%s)\n", r, errno, strerror(errno));
    printf("  闸门 1  CAP_SETGID  : 看主程序的 CapEff —— 本环境是 0（无任何 capability）\n");
    printf("  闸门 2  ns 是否允许 : /proc/self/setgroups = deny（见上）\n");
    printf("  两道独立，任何一道关着都返回 EPERM；靠 errno 分辨不出是哪一道。\n");

    printf("\n=== ④ initgroups() 是 setgroups() 的封装 ===\n");
    errno = 0;
    r = initgroups("ce", (gid_t) 10240);
    printf("  initgroups(\"ce\", 10240) = %d  errno=%d (%s)\n", r, errno, strerror(errno));
    printf("  man 里 initgroups(3) 的 EPERM 一条写的就是 \"See the underlying\n");
    printf("  system call setgroups(2)\" —— 所以它不可能有别的失败方式。\n");

    printf("\n=== ⑤ getgrouplist() 与 /etc/group 的关系 ===\n");
    {
        int ng = 8;
        gid_t gl[8];
        errno = 0;
        r = getgrouplist("ce", (gid_t) 10240, gl, &ng);
        printf("  getgrouplist(\"ce\", 10240, ...) = %d  ngroups=%d  errno=%d (%s)\n",
               r, ng, errno, strerror(errno));
        printf("  它只会写进 basegid + 从组数据库查到的组；本容器没有 /etc/group，\n");
        printf("  所以只剩 basegid 一个（errno 是查库时留下的 ENOENT，不是函数失败）。\n");
    }

    printf("\n=== ⑥ 内核会排序，所以别把「顺序」当契约 ===\n");
    printf("  kernel/groups.c:200 setgroups() 里（:219）调 groups_sort()；\n");
    printf("  :94 groups_search() 是 bsearch —— 排序是为了让二分查找成立；\n");
    printf("  :234 in_group_p() 先比 cred->fsgid，再二分查补充组（**不是 egid**）。\n");
    return 0;
}
```

```text
=== ⑤ getgrouplist() 与 /etc/group 的关系 ===
  getgrouplist("ce", 10240, ...) = 1  ngroups=1  errno=2 (No such file or directory)
  它只会写进 basegid + 从组数据库查到的组；本容器没有 /etc/group，
  所以只剩 basegid 一个（errno 是查库时留下的 ENOENT，不是函数失败）。

=== ⑥ 内核会排序，所以别把「顺序」当契约 ===
  kernel/groups.c:200 setgroups() 里（:219）调 groups_sort()；
  :94 groups_search() 是 bsearch —— 排序是为了让二分查找成立；
  :234 in_group_p() 先比 cred->fsgid，再二分查补充组（**不是 egid**）。
```

**解读**

1. **第 ① 段是标准套路**：`getgroups(0, NULL) = 1` 先问个数，再 `getgroups(1, buf) = 1` 取列表 → `列表: 0`。两次 `errno` 都是 0。注意**第二次返回的 `got` 才是权威**——程序里打印的是 `got` 而不是 `n`。
2. **第 ② 段只跑到一个分支**：`getgroups(-1, NULL)` → `-1 / errno=22`（内核 `:168` 的 `gidsetsize < 0`）。第二个分支（缓冲不够，`:174` 的 `i > gidsetsize`）在这里**构造不出来**——本进程只有 1 个补充组，要触发就得传 `size=0` 以外的更小值，做不到。程序如实说明了这一点，而不是编一个假的。
   - 这段代码本身还有个副产品：为了让**内核**返回 EINVAL 而不是让**编译器**拒绝编译，用 `volatile int neg_size = -1;` 转了一手。直接写 `getgroups(-1, NULL)` 在 gcc `-Wall` 下会报 `-Wstringop-overflow`（glibc 给 `getgroups` 标了 `__attribute__((access(write_only, 2, 1)))`）。**这个告警本身是个好事**：说明这个笔误能被静态抓到。
3. **第 ③ 段是本节最有价值的一段**，因为它把两道闸门**分别**取到了证据：
   - `--- /proc/self/setgroups ---` 下面是 `deny` → **闸门 ②** 关着；
   - `setgroups(0, NULL) = -1 errno=1` → 返回 `EPERM`；
   - 闸门 ① 的证据在 [9.1](./9.1-real-uid-gid.md)/[9.2](./9.2-effective-uid-gid.md) 已经实测过：`CapEff = 0000000000000000` → **闸门 ①** 也关着。
   两道同时关着，`EPERM(1)` 只有一个数字，**分辨不出是哪一道**——程序里那句「靠 errno 分辨不出是哪一道」就是在说这件事。要分辨只能分别去读 `CapEff` 和 `/proc/self/setgroups`。
4. **第 ④ 段两行一起读**：`initgroups("ce", 10240)` 也是 `-1 / errno=1`，和上面的 `setgroups` **完全一样**。这不是巧合——`initgroups(3)` 的 ERRORS 只有 `ENOMEM` 和 `EPERM`，而 `EPERM` 那条写的就是 "See the underlying system call `setgroups(2)`"。**它没有独立的失败模式**，所以必然同因同果。
5. **第 ⑤ 段那个 `errno=2` 特别值得注意**：`getgrouplist("ce", 10240, ...) = 1  ngroups=1  errno=2`。返回值是 `1`（表示 `basegid` 之外还找到 0 个组，`ngroups` 最终是 1），**函数本身没失败**；那个 `ENOENT` 是**查 NSS 库时留下的残留**。所以这里**不能**用「`errno != 0` 就是失败」去判断——`errno` 只有在**返回值表示失败**时才有意义。这和 [Ch8 §8.4](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md) 讲的 `errno` 范式是同一件事的两面：**先看返回值，再看 errno**。
6. **第 ⑥ 段的三个行号是这个模块里最该记住的一组源码事实**：
   - `kernel/groups.c:200` `setgroups()` 调 `groups_sort()`（`:219`） → **内核会排序**；
   - `kernel/groups.c:94` `groups_search()` 是手写 bsearch → **排序是为了二分**；
   - `kernel/groups.c:234` `in_group_p()` **先比 `cred->fsgid`，再二分查补充组**（不是 egid）。
   第三条把 [9.5](./9.5-fs-uid-gid.md) 的 fsuid/fsgid 和本节的补充组接上了——**Linux 文件权限检查的完整输入就是 `(fsuid, fsgid, 补充组)`**。

## HFT / 嵌入式关联

- **降权的正确顺序：`setgroups(0, NULL)` → `setgid(t)` → `setresuid(t,t,t)`。** 顺序不能乱的理由很硬：`setgroups` 需要 `CAP_SETGID`（`kernel/groups.c:191`），一旦 `setresuid` 把特权丢光，`setgroups` 就永远 `EPERM` 了——**主 GID 改了但补充组仍含特权组，等于没降权**。这是 setuid 程序最经典的一个漏洞形态。

  ```c
  /* 正确顺序 */
  if (setgroups(0, NULL) == -1) die("setgroups");   /* 先清空 */
  if (setgid(t) == -1)        die("setgid");        /* 再改 gid */
  if (setresuid(t, t, t) == -1) die("setresuid");   /* 最后动 uid（不可逆） */
  ```

- **「清空」比「换成目标用户的组」更保守。** `setgroups(0, NULL)` 之后进程没有任何补充组，权限面最小；想保留目标用户的组就用 `initgroups(user, gid)`。**HFT 场景下通常两者都可以，但别用 `initgroups(被攻击者能控制的用户名, ...)`** —— 那是一次 NSS 查询（可能走网络），而且用户组关系是外部数据。
- **容器里 `setgroups` 失败是常态，且原因有两种。** `docker run` 默认会在新 user namespace 里写 `setgroups=deny`（为的是能让 rootless 容器写 `gid_map`）。所以容器里「以 root 身份却调不了 `setgroups`」是**设计行为**。排查时读两个地方：`CapEff`（闸门 ①）和 `/proc/self/setgroups`（闸门 ②），**别只看 errno**。
- **`getgroups()` 的 `EINVAL` 不是 `ERANGE`。** 写过 `getpwnam_r`（`ERANGE` 重试）的人很容易把它也写成 `ERANGE` 重试，结果永远进不去那个分支。嵌入式上这种 bug 往往在只有少数用户组的设备上**测不出来**（组数少、缓冲够），一上生产（接了 LDAP）就爆。
- **不要假设 `getgroups()` 的顺序。** 内核 `groups_sort()`（`kernel/groups.c:219`）会排序。写「`groups[0]` 是主组」或「按传入顺序读回」这类代码一定出错。另外**先 `getegid()` 再自己并入列表**（`getgroups(2)` 明说 "It is unspecified whether the effective group ID … is included"）——不同 libc / 内核版本行为不一致。
- **启动路径上的 `initgroups()` 可能是一次网络往返。** 接了 SSSD/LDAP 的机器上，`su` / `sshd` / `systemd` 都会调它。HFT 的启动脚本如果要切换用户，**优先用 `setgroups()` 配一份固定列表**，别依赖 NSS。
- **`NGROUPS_MAX` 上限在内核配置里可能被改小。** `getgroups(2)` 说的是 32（2.6.4 前）/ 65536（2.6.4 后），但嵌入式 BSP 可能设了更小的值。**用 `sysconf(_SC_NGROUPS_MAX)` 问，别写死。**

## 自测题

<details>
<summary>1. 降权时为什么必须最先调用 <code>setgroups()</code>？</summary>

**因为 `setgroups()` 需要 `CAP_SETGID`，而 `setuid`/`setresuid` 会把它丢掉。**

正确顺序：

```c
setgroups(0, NULL);            /* ① 清空补充组 —— 需要 CAP_SETGID */
setgid(t);                     /* ② 改主 GID */
setresuid(t, t, t);            /* ③ 永久丢 UID 特权（不可逆） */
```

**如果顺序反了**（先 `setresuid`）：进程已经没有特权，`setgroups()` 返回 `EPERM`（`kernel/groups.c:191` 的 `ns_capable_setid(user_ns, CAP_SETGID)` 为假）。结果是：

| ID | 状态 |
|----|------|
| uid / gid | 已降到普通用户 ✅ |
| **补充组** | **还是原来那些（含特权组）** ❌ |

所有权检查的第 2 步是「fsgid 或 **补充组** 匹配文件属主 gid」（[9.6 要点一](#一补充组是权限检查的第三个分量)），所以残留的特权组**仍然能访问那些组的文件**。这就是「降权没降干净」的经典形态。

`credentials(7)` 也提示了 `execve` 不会帮你清理："During an `execve(2)`, a process's real user and group ID and **supplementary group IDs are preserved**" —— 补充组是**跟着进程走**的，只靠 exec 换程序不会重置它。

另外注意容器里还有第二道闸门（`/proc/self/setgroups = deny`），**两道都关着才叫「做不了」**；只关一道也可能失败。
</details>

<details>
<summary>2. <code>getgroups()</code> 的「缓冲不够」返回什么 errno？</summary>

**`EINVAL`，不是 `ERANGE`。**

`getgroups(2)` ERRORS：

> **EINVAL** `size` is less than the number of supplementary group IDs, but is not zero.

内核 `kernel/groups.c:174`：

```c
if (i > gidsetsize) {
    i = -EINVAL;
    goto out;
}
```

对比一下同类 API，这个差异很值得记：

| API | 「缓冲不够」的 errno |
|-----|---------------------|
| `getpwnam_r` / `getgrnam_r`（[Ch8 §8.4](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)） | **`ERANGE`**（34） |
| `getgroups` | **`EINVAL`**（22） |

**`getgroups()` 的 `EINVAL` 有两个分支**（`:168` 和 `:174`），一个负 size、一个缓冲不够。本节实测的是第一个（`getgroups(-1, NULL) = -1 errno=22`），第二个在只有 1 个补充组的容器里构造不出来。

正确写法就是 man 给的惯用法：**先 `getgroups(0, NULL)` 问个数**，就不会撞上第二个分支。
</details>

<details>
<summary>3. 内核会保留我传给 <code>setgroups()</code> 的顺序吗？</summary>

**不会。内核会排序。**

`kernel/groups.c:200` 的 `setgroups()`：

```c
groups_sort(group_info);                /* :219 */
retval = set_current_groups(group_info);
```

`groups_sort()` 内部是 `sort(group_info->gid, group_info->ngroups, sizeof(*group_info->gid), gid_cmp, NULL)`（`:88-90`）——**按 gid 升序排**。

排序的目的是让 `groups_search()`（`:94` 的 "a simple bsearch"）成立——那个函数是手写二分：

```c
while (left < right) {
    unsigned int mid = (left+right)/2;
    if (gid_gt(grp, group_info->gid[mid]))      left = mid + 1;
    else if (gid_lt(grp, group_info->gid[mid])) right = mid;
    else return 1;
}
```

三条实践结论：

1. **`getgroups()` 回来的顺序是内核排序后的升序**，不是你传进去的顺序。
2. **不要写「`groups[0]` 是主组」**——主组（egid）根本不保证出现在这个列表里（`getgroups(2)`："It is **unspecified** whether the effective group ID … is included"）。要主组就单独 `getegid()`。
3. 排序对调用方是好事：**你可以放心用线性查找**（组数通常个位数），或者学内核用二分。

作为对照，`setreuid` / `setresuid` 那边就有**明显**的顺序契约（[9.4](./9.4-saved-id.md)：`setgroups` 必须在 `setgid`/`setuid` 之前）——所以「顺序是不是契约」要逐个接口查，不能一概而论。
</details>

<details>
<summary>4. <code>initgroups()</code> 和 <code>getgrouplist()</code> 有什么区别？</summary>

**同一套算法，一个装、一个不装。**

| | `initgroups(user, gid)` | `getgrouplist(user, gid, list, &ngroups)` |
|---|------------------------|-------------------------------------------|
| 读什么 | NSS 组库（`/etc/group`，可被 `nsswitch.conf` 改成 LDAP/SSSD） | 同样的 NSS 组库 |
| 做什么 | 算出「用户所属的所有组 + `gid`」，然后**调 `setgroups()` 装上去** | 只把列表**写进出参缓冲**，不装 |
| 要特权 | ✅ 要（底层 `setgroups` 要 `CAP_SETGID`） | ❌ 不要 |
| 失败码 | `ENOMEM` / `EPERM`（**EPERM 就是 `setgroups` 传上来的**） | 见 man `getgrouplist(3)` |

本节实测的两行直接印证了「同因同果」：

```text
  setgroups(0, NULL)   = -1  errno=1 (Operation not permitted)
  initgroups("ce", 10240) = -1  errno=1 (Operation not permitted)
```

`initgroups(3)` 的 ERRORS 只有两条，`EPERM` 那条写的是 "**See the underlying system call `setgroups(2)`**" —— 所以 `initgroups()` **不可能**有独立的失败模式。

本节实测里 `getgrouplist("ce", 10240, ...) = 1  ngroups=1  errno=2` 那一行还揭示了一个坑：**`errno` 是 `ENOENT`（查 NSS 组库时的残留），但函数并没有失败**（返回值 1、`ngroups=1`，列表里只有 `basegid`）。所以判断成败**先看返回值，再看 `errno`**——`errno` 只在返回值表示失败时才有意义。
</details>

<details>
<summary>5. 一个进程能属于多少个补充组？当前有几个？分别怎么查？</summary>

**两个不同的问题，两个不同的调用。**

| 问题 | 调用 | 本节实测 |
|------|------|----------|
| **系统允许最多几个** | `sysconf(_SC_NGROUPS_MAX)` | `65536` |
| **本进程此刻有几个** | `getgroups(0, NULL)` | `1` |

`credentials(7)`："Before Linux 2.6.4, a process can be a member of up to **32** supplementary groups; since Linux 2.6.4, a process can be a member of up to **65536** supplementary groups. The call `sysconf(_SC_NGROUPS_MAX)` can be used to determine the number of supplementary groups of which a process may be a member."

另外 `getgroups(2)` ERRORS 里 `setgroups()` 有一条 `EINVAL`："`size` is greater than `NGROUPS_MAX` (32 before Linux 2.6.4; 65536 since Linux 2.6.4)" —— 也就是说 `NGROUPS_MAX` 同时也是 `setgroups()` 的**入参上限判据**。

写代码时：

```c
int n = getgroups(0, NULL);              /* ← 用这个拿「实际个数」 */
if (n < 0) die("getgroups");
gid_t *g = malloc(sizeof(gid_t) * (size_t) n);   /* ← 别按 65536 开数组 */
```

按 `_SC_NGROUPS_MAX` 开一个 65536 项的数组是 256 KB 的无谓分配——**每次调用这种函数都来一次，在嵌入式上就是灾难**。

⚠️ 还有一点：嵌入式 BSP 里的 `NGROUPS_MAX` 可能被内核配置改小，**所以永远用 `sysconf` 问，不要写死 65536 或 32**。
</details>
