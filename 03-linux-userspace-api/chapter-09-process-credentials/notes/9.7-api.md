## 9.7.1 读/写 R、E、S 的接口

### 读：三个 `get*`

| 函数 | 头文件 | 签名 | 备注 |
|------|--------|------|------|
| `getuid()` / `getgid()` | `<unistd.h>` | `uid_t getuid(void)` | 只拿 RUID / RGID |
| `geteuid()` / `getegid()` | `<unistd.h>` | `uid_t geteuid(void)` | 只拿 EUID / EGID |
| `getresuid()` / `getresgid()` | `<unistd.h>`（`_GNU_SOURCE`） | `int getresuid(uid_t *, uid_t *, uid_t *)` | **一次拿 R/E/S**；Linux 扩展 |

内核 `kernel/sys.c:749` 的 `getresuid()` 就三行有效代码——三次 `from_kuid_munged()`：

```c
ruid = from_kuid_munged(cred->user_ns, cred->uid);      /* :755 */
euid = from_kuid_munged(cred->user_ns, cred->euid);     /* :756 */
suid = from_kuid_munged(cred->user_ns, cred->suid);     /* :757 */
```

注意 `from_kuid_munged` 的 **`_munged`**：拿不到映射时它会**返回「溢出 uid」而不是报错**（[9.1](./9.1-real-uid-gid.md) 的 `65534` 就是这么来的）。所以 `getuid()` **永远不会失败**，它总是给你一个看起来正常的数字。

> 📌 **`getresuid()` 有一个隐藏好处**：它是原子的（内核拿的是 `current_cred()` 的快照）。`getuid()` + `geteuid()` 分两次调用在多线程下可能读到不一致的组合。降权后的验证代码应该用 `getresuid()`（[9.4](./9.4-saved-id.md) 的 `c9_5` 就是这么写的）。

### 写：四个 `set*uid`

| 函数 | 标准 | 改哪些 | 关键规则 |
|------|------|--------|----------|
| `setuid(uid)` | POSIX | **看身份**：特权时 R+E+S，非特权时只 E | SysV 语义；特权时**不可逆** |
| `seteuid(euid)` | POSIX | **只 E** | 非特权时 `euid` 必须 ∈ `{ruid, suid}` |
| `setreuid(ruid, euid)` | BSD（`_XOPEN_SOURCE >= 500`） | R 与/或 E，**可能顺带改 S** | `-1` = 不改该项 |
| `setresuid(ruid, euid, suid)` | **Linux 扩展** | R / E / S **各自独立** | `-1` = 不改该项 |

GID 侧完全对称：`setgid` / `setegid` / `setregid` / `setresgid`。

**`setresuid()` 的两个要点**（`setresuid(2)` DESCRIPTION）：

> **If one of the arguments equals -1, the corresponding value is not changed.**
>
> **Regardless of what changes are made to the real UID, effective UID, and saved set-user-ID, the filesystem UID is always set to the same value as the (possibly new) effective UID.**

第二条是**全局规则**：`setuid` / `seteuid` / `setreuid` / `setresuid` **任何一个**改动了 euid，内核都会把 fsuid 同步过去。所以正常路径下你**不需要**手动管 fsuid。

## 9.7.2 读/写 fsuid、fsgid 的接口

| 方向 | 接口 | 返回值 | 备注 |
|------|------|--------|------|
| 写 | `setfsuid(fsuid)` | **旧 fsuid**（成功失败都一样） | 无 errno；glibc 标 `[[deprecated]]` |
| 写 | `setfsgid(fsgid)` | 同上 | 同上 |
| 读（API） | `setfsuid((uid_t) -1)` | 当前 fsuid | `-1` 必然非法 → 一定不改状态 |
| 读（`/proc`） | `/proc/self/status` 的 `Uid:` **第 4 列** | 当前 fsuid | 无副作用，一次拿 4 列 |

**没有标准的 getter**——这是 fsuid 接口最别扭的地方：**读它必须借用一个「写」函数**。完整语义与实测见 [9.5](./9.5-fs-uid-gid.md)。

## 9.7.3 读/写补充组的接口

| 函数 | 签名 | 签名里的细节 |
|------|------|--------------|
| `getgroups(size, list)` | `int getgroups(int size, gid_t list[])` | size 是 **`int`**（可为负，内核要判） |
| `setgroups(size, list)` | `int setgroups(size_t size, const gid_t list[size])` | size 是 **`size_t`**（无符号） |
| `initgroups(user, group)` | `int initgroups(const char *user, gid_t group)` | 读 NSS 组库 + `setgroups()` |
| `getgrouplist(user, group, list, &ngroups)` | `int getgrouplist(const char *user, gid_t group, gid_t *list, int *ngroups)` | 只算不装 |

**`getgroups()` 的两个 `EINVAL` 分支**（`kernel/groups.c:168` 负 size、`:174` 缓冲不够）**都不是 `ERANGE`**；`setgroups()` 有两道**独立闸门**（`CAP_SETGID` 与 `userns_may_setgroups()`）。详见 [9.6](./9.6-supplementary-groups.md)。

**「先读再写」的完整套路**（`initgroups()` 干的事）：

```
① getpwnam(user)                -> 拿到主组 gid
② 遍历组数据库（fgetgrent）      -> 收集「user 是成员」的所有 gid
③ 把主组 gid 并进列表
④ setgroups(n, list)            -> 一次装上
```

[练习 9-3](./9.9-exercises.md) 的 `ex9_3_my_initgroups.c` 就是这四步的可运行实现。

## 9.7.4 Summary of Calls for Modifying Process Credentials

这张表是本章的**总账**。「改哪些 ID」一列是核心——安全代码里所有「有没有真正降权」的推理都建立在它上面。

| 调用 | 改哪些 | 特权进程（有 `CAP_SETUID`） | 非特权进程 |
|------|--------|------------------------------|------------|
| `setuid(u)` | R+E+S **或** 只 E | `r=e=s=u`（不可逆） | 只 `e=u`，要求 `u ∈ {r, s}`；否则 `EPERM` |
| `seteuid(e)` | 只 E | 任意合法 uid（受 ns 映射限制） | 要求 `e ∈ {r, s}` |
| `setreuid(r, e)` | R 与/或 E，**可能顺带 S** | 一般可设 `{r, e, s}` 内 | `e` 只能设成 `{r, e, s}` 之一；`r` 只能设成 `{r, e}` 之一 |
| `setresuid(r, e, s)` | R/E/S 各自独立 | 任意组合（`-1` 跳过） | 每一项只能设成「当前 R/E/S 之一」 |
| `setfsuid(u)` | 只 F | 任意 | `u ∈ {r, e, s, f}`；否则**静默失败** |
| `setfsgid(g)` | 只 F | 任意 | 同上 |
| `setgroups(n, l)` | 补充组 | ✅ | ❌ `EPERM`（且还受 ns 的 `setgroups` 文件管） |
| `setgid` / `setegid` / `setregid` / `setresgid` | 与 UID 侧**完全对称** | | |

**四条贯穿全表的规则**：

1. **`-1` = 不改这一项**（`setreuid` / `setresuid` / `setregid` / `setresgid`）；
2. **改 euid 就同步 fsuid**（内核保证）；
3. **`setuid` 在特权进程下连 `saved` 一起改** → 临时降权必须用 `seteuid`（[9.4](./9.4-saved-id.md)）；
4. **`EINVAL` 可能在 `EPERM` 之前**：uid 在本 user namespace 里没映射时，内核**连通配检查都不做**就返回 `EINVAL`（`kernel/sys.c:620-622`）。所以「合法 uid」是这一切的前提。

### c9_4 八个 `set*id` 接口的返回码实测

[`../code/c9_4_setid_probe.c`](../code/c9_4_setid_probe.c) 在 [9.2](./9.2-effective-uid-gid.md) 里已经登过场。放在本节是因为它同时覆盖 **9.7.1 的两族接口**（UID 侧 8 条 + GID 侧 7 条）——是这张总表的可执行对照。

```c
/* c9_4_setid_probe.c —— 把「按规则应该怎样」和「实测返回什么」并排放
 *
 * 9.2 / 9.3 / 9.4 / 9.7 的规则可以用文字背，但**返回码**必须实测。
 * 本程序对 8 个 set*id 接口各试三类参数：
 *   (a) 设成「自己」         -> 应当成功（ps: 这是特例，见下）
 *   (b) -1 形式（不改动）    -> 应当成功，且什么都不变
 *   (c) 未映射的 uid/gid     -> 应当 EINVAL（若内核版本/命名空间如此）
 *
 * 为什么 (a) 会成功：内核**不是**先看「有没有 CAP_SETUID」，而是先看目标值
 * 是否落在 {ruid, euid, suid, fsuid} 里（kernel/sys.c:883 等）。设成自己必然在集合内，
 * 所以不需要任何 capability。这解释了「uid=0 但 CapEff=0」的进程为什么还能调
 * setuid(0) 成功 —— 它其实什么都没做。
 *
 * 权威依据：
 *   - setuid(2) ERRORS EINVAL: "The user ID specified in uid is not valid in this
 *     user namespace."（描述），内核对应 kernel/sys.c:620 make_kuid + :621 uid_valid。
 *   - setresuid(2) DESCRIPTION：非特权进程只能在各 ID 之间互相设；
 *     "If one of the arguments equals -1, the corresponding value is not changed."
 *   - setreuid(2) DESCRIPTION：-1 表示不改；suid 的更新规则。
 *   - kernel/sys.c:612 __sys_setuid()、:669 __sys_setresuid()、:531 __sys_setreuid()。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_4_setid_probe c9_4_setid_probe.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>

#define UNMAPPED 10240u

#define TRY(expr, rule)                                                       \
    do {                                                                      \
        errno = 0;                                                            \
        int rc_ = (int) (expr);                                               \
        int e_ = errno;                                                       \
        printf("  %-32s | %-30s | %4d | %2d %-16s\n",                         \
               #expr, rule, rc_, e_, e_ ? strerror(e_) : "-");                \
    } while (0)

static int same_as_before(void)
{
    uid_t a, b, c;
    if (getresuid(&a, &b, &c) == -1)
        return -1;
    return (a == 0 && b == 0 && c == 0) ? 1 : 0;
}

int main(void)
{
    uid_t ru, eu, su;
    gid_t rg, eg, sg;
    getresuid(&ru, &eu, &su);
    getresgid(&rg, &eg, &sg);

    printf("环境: uid=%u/%u/%u  gid=%u/%u/%u\n",
           (unsigned) ru, (unsigned) eu, (unsigned) su,
           (unsigned) rg, (unsigned) eg, (unsigned) sg);

    printf("\n=== uid 家族 ===\n");
    printf("  %-32s | %-30s | %4s | %s\n", "调用", "按规则应当", "ret", "errno");
    printf("  ---------------------------------+--------------------------------+------+------------------\n");
    TRY(setuid(getuid()),            "自己在集合内 -> 0");
    TRY(setreuid((uid_t) -1, (uid_t) -1), "-1 = 不改 -> 0");
    TRY(setresuid((uid_t) -1, (uid_t) -1, (uid_t) -1), "-1 = 不改 -> 0");
    TRY(setresuid(getuid(), getuid(), getuid()), "自己在集合内 -> 0");
    TRY(setuid((uid_t) UNMAPPED),    "未映射 -> EINVAL(22)");
    TRY(seteuid((uid_t) UNMAPPED),   "未映射 -> EINVAL(22)");
    TRY(setreuid((uid_t) UNMAPPED, (uid_t) UNMAPPED), "未映射 -> EINVAL(22)");
    TRY(setresuid((uid_t) UNMAPPED, (uid_t) UNMAPPED, (uid_t) UNMAPPED),
        "未映射 -> EINVAL(22)");

    printf("\n=== gid 家族 ===\n");
    printf("  %-32s | %-30s | %4s | %s\n", "调用", "按规则应当", "ret", "errno");
    printf("  ---------------------------------+--------------------------------+------+------------------\n");
    TRY(setgid(getgid()),            "自己在集合内 -> 0");
    TRY(setregid((gid_t) -1, (gid_t) -1), "-1 = 不改 -> 0");
    TRY(setresgid((gid_t) -1, (gid_t) -1, (gid_t) -1), "-1 = 不改 -> 0");
    TRY(setgid((gid_t) UNMAPPED),    "未映射 -> EINVAL(22)");
    TRY(setegid((gid_t) UNMAPPED),   "未映射 -> EINVAL(22)");
    TRY(setregid((gid_t) UNMAPPED, (gid_t) UNMAPPED), "未映射 -> EINVAL(22)");
    TRY(setresgid((gid_t) UNMAPPED, (gid_t) UNMAPPED, (gid_t) UNMAPPED),
        "未映射 -> EINVAL(22)");

    printf("\n=== 试完一圈，身份变了没有？ ===\n");
    uid_t a, b, c;
    gid_t x, y, z;
    getresuid(&a, &b, &c);
    getresgid(&x, &y, &z);
    printf("  现在 uid=%u/%u/%u   gid=%u/%u/%u\n",
           (unsigned) a, (unsigned) b, (unsigned) c,
           (unsigned) x, (unsigned) y, (unsigned) z);
    printf("  与开始时相同? %s\n", same_as_before() == 1 ? "是（所有调用要么是 no-op，要么被 EINVAL 挡下）" : "否");

    printf("\n=== 为什么「未映射」是 EINVAL 而不是 EPERM ===\n");
    printf("  内核先做 make_kuid(ns, uid) -> 拿不到合法 kuid 时**连通配检查都不做**，\n");
    printf("  直接 -EINVAL（kernel/sys.c:620-622）。EPERM 才是「uid 合法但不许改」。\n");
    printf("  这条区分只在有 user namespace 的环境里才看得到：\n");
    printf("  普通系统上所有 uid 都有映射，setuid(10240) 得到的是 EPERM。\n");
    return 0;
}
```

**解读**（完整分析见 [9.2 的解读](./9.2-effective-uid-gid.md)，这里只挑与「接口对照表」直接相关的）

1. **15 条调用里 7 条返回 0，8 条返回 `-1/22`** —— 而且**返回 0 的全部是 no-op**（目标等于现状，或 `-1` 哨兵）。这条比例本身就是对总表的最好注脚：「返回 0」与「改动了什么」是两件事。
2. **两族的对称性完全成立**：UID 侧和 GID 侧的返回码逐条对应，`setgid(getgid())` 与 `setuid(getuid())`、`setregid(-1,-1)` 与 `setreuid(-1,-1)`……这是 `credentials(7)` 用 "Completely analogously" 一句话带过的地方，实测证实没有例外。
3. **`setresuid(getuid(), getuid(), getuid())` 也返回 0** —— 三个参数都等于当前 RUID，落在集合内，是 no-op。注意这一条**不在** `-1` 那类里：它显式给了三个值，只不过值恰好都是现状。**「no-op」的判据是「新值等于旧值」，不是「参数是不是 -1」。**

### Listing 9-1 `proccred/idshow.c`：把五类 ID 全打出来

原书 9.7.5 的唯一程序。完整复刻见 [`../code/idshow.c`](../code/idshow.c)。

它有两个值得学的写法：

1. **用 `getresuid()` / `getresgid()` 一次拿 R/E/S**，而不是 `getuid()` + `geteuid()` 两次调用；
2. **读 fsuid 用的是 `fsuid = setfsuid(0);`** —— 一个「借用写函数来读值」的怪接口。原书在这一行上方留了注释：

   ```c
   /* Attempts to change the file-system IDs are always ignored
      for unprivileged processes, but even so, the following
      calls return the current file-system IDs */
   fsuid = setfsuid(0);
   fsgid = setfsgid(0);
   ```

   注意它传的是 **`0` 而不是 `-1`**。这在特权进程下是合法 no-op（`0` 落在放行集合里），在非特权进程下会被静默拒绝但**照旧返回当前 fsuid**——两种情况下返回值都是「当前 fsuid」。这是把 9.5 那个缺陷接口**用对了**的范例；但它只对「euid 是 0，或者 fsuid 本来就是 0」的场合成立，所以更稳妥的现代写法是 `setfsuid((uid_t) -1)` 或读 `/proc/self/status`。

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *

/* idshow.c

   Display all user and group identifiers associated with a process.

   Note: This program uses Linux-specific calls and the Linux-specific
   file-system user and group IDs.
*/
/* ---------------------------------------------------------------------------
 * 本文件是 TLPI 官方源码 proccred/idshow.c 的逐行复刻（= 原书 Listing 9-1）。
 * 官方页面: https://man7.org/tlpi/code/online/dist/proccred/idshow.c
 *
 * 为了能在本仓库里单独编译，只做了两处**与逻辑无关**的调整：
 *   1. 去掉 "#include \"tlpi_hdr.h\""，改为直接包含它提供的那几个标准头，
 *      并内联一个最小的 errExit()（原来是 tlpi_hdr.h 里的宏）。
 *   2. 原样保留 "#include \"ugid_functions.h\""：那是 Listing 8-1 的助手函数，
 *      本仓库不复制它，直接用 Ch08 目录下那一份（编译命令见 code/README.md）。
 *
 * 原书的两个教学点在这份源码里看得最清楚：
 *   - 它用 **getresuid/getresgid** 一次拿 R/E/S，而不是 getuid/geteuid/getgid 三连；
 *   - 它读 fsuid/fsgid 用的是 `fsuid = setfsuid(0);` —— 这个「返回值其实是旧值」
 *     的怪接口，配套注释写的是 "Attempts to change the file-system IDs are always
 *     ignored for unprivileged processes, but even so, the following calls return
 *     the current file-system IDs"。
 * ------------------------------------------------------------------------- */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <errno.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/fsuid.h>
#include <sys/types.h>
#include <unistd.h>

#include "ugid_functions.h"   /* userNameFromId() & groupNameFromId() */

#define SG_SIZE (NGROUPS_MAX + 1)

/* 替代 tlpi_hdr.h 的 errExit()（原书里是宏） */
static void errExit(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

int
main(int argc, char *argv[])
{
    uid_t ruid, euid, suid, fsuid;
    gid_t rgid, egid, sgid, fsgid;
    gid_t suppGroups[SG_SIZE];
    int numGroups, j;
    char *p;

    (void) argc;
    (void) argv;

    if (getresuid(&ruid, &euid, &suid) == -1)
        errExit("getresuid");
    if (getresgid(&rgid, &egid, &sgid) == -1)
        errExit("getresgid");

    /* Attempts to change the file-system IDs are always ignored
       for unprivileged processes, but even so, the following
       calls return the current file-system IDs */

    fsuid = setfsuid(0);
    fsgid = setfsgid(0);

    printf("UID: ");
    p = userNameFromId(ruid);
    printf("real=%s (%ld); ", (p == NULL) ? "???" : p, (long) ruid);
    p = userNameFromId(euid);
    printf("eff=%s (%ld); ", (p == NULL) ? "???" : p, (long) euid);
    p = userNameFromId(suid);
    printf("saved=%s (%ld); ", (p == NULL) ? "???" : p, (long) suid);
    p = userNameFromId(fsuid);
    printf("fs=%s (%ld); ", (p == NULL) ? "???" : p, (long) fsuid);
    printf("\n");

    printf("GID: ");
    p = groupNameFromId(rgid);
    printf("real=%s (%ld); ", (p == NULL) ? "???" : p, (long) rgid);
    p = groupNameFromId(egid);
    printf("eff=%s (%ld); ", (p == NULL) ? "???" : p, (long) egid);
    p = groupNameFromId(sgid);
    printf("saved=%s (%ld); ", (p == NULL) ? "???" : p, (long) sgid);
    p = groupNameFromId(fsgid);
    printf("fs=%s (%ld); ", (p == NULL) ? "???" : p, (long) fsgid);
    printf("\n");

    numGroups = getgroups(SG_SIZE, suppGroups);
    if (numGroups == -1)
        errExit("getgroups");

    printf("Supplementary groups (%d): ", numGroups);
    for (j = 0; j < numGroups; j++) {
        p = groupNameFromId(suppGroups[j]);
        printf("%s (%ld) ", (p == NULL) ? "???" : p, (long) suppGroups[j]);
    }
    printf("\n");

    exit(EXIT_SUCCESS);
}
```

```bash

gcc -O0 -Wall -Wextra -o idshow idshow.c ../chapter-08-users-and-groups/code/ugid_functions.c
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
UID: real=??? (0); eff=??? (0); saved=??? (0); fs=??? (0); 
GID: real=??? (0); eff=??? (0); saved=??? (0); fs=??? (0); 
Supplementary groups (1): ??? (0) 
```

**解读**

1. **全部名字是 `???`，但数字都正确。** 这不是 bug：程序调的是 `userNameFromId()` / `groupNameFromId()`（Ch8 Listing 8-1 的助手），它们内部走 `getpwuid()` / `getgrgid()`；而本容器的 `/etc/passwd` 里**只有一条 `ce` 账号的记录**（[Ch8 §8.4 实测](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)），`getpwuid(0)` 返回 `NULL` → 程序打印 `"???"`。
2. **所有数字都是 `0`，且 `real / eff / saved / fs` 四个位置都对**——这一行同时印证了三件事：
   - `Uid:` 的列序是 `real, effective, saved, filesystem`（[9.1](./9.1-real-uid-gid.md)）；
   - `fs` 那一列（来自 `setfsuid(0)` 的返回值）**和 `UID` 行的其他三列一致**，说明本进程 fsuid == euid（[9.5](./9.5-fs-uid-gid.md) 的同步规则）；
   - `Supplementary groups (1)` 里那一项是 `??? (0)`——本进程有 1 个补充组，gid 0（[9.6](./9.6-supplementary-groups.md)）。
3. **这行输出是「环境决定的」，不是「程序决定的」。** 换一台有完整 `/etc/passwd` 的机器，同样的二进制会打出 `UID: real=alice (1000); eff=root (0); saved=root (0); fs=root (0);` 这种可读结果。**验证「程序逻辑对不对」和「环境能不能提供名字」是两件事**，`???` 只说明后者不满足。
4. **`SG_SIZE` 的定义值得注意**：

   ```c
   #define SG_SIZE (NGROUPS_MAX + 1)
   ```

   `NGROUPS_MAX` 是编译期常量（`<limits.h>` 里通常是 65536），`+ 1` 是原书的习惯——留一格冗余。所以这个程序在栈上开了 **65537 个 `gid_t`**（约 256 KB）。**在嵌入式上是够呛的**（默认线程栈可能只有 128 KB）。生产代码应该用 `getgroups(0, NULL)` + `malloc`（[9.6](./9.6-supplementary-groups.md) 的惯用法）。

## HFT / 嵌入式关联

- **这张接口总表就是「降权代码该怎么写」的答案表。** 生产代码里最常见的一条是：

  ```c
  setgroups(0, NULL);            /* 9.6：先清补充组 */
  setgid(t);                     /* 9.6：再改 gid  */
  setresuid(t, t, t);            /* 9.7：R/E/S 一次钉死，表达「永久」 */
  ```

  为什么用 `setresuid(t,t,t)` 而不是 `setuid(t)`：**`setuid` 的行为依赖调用者身份**（[9.7.4 总表](#974-summary-of-calls-for-modifying-process-credentials) 第一行），而 `setresuid` 的行为是显式的。安全代码里不要写「行为随环境变化」的调用。
- **读接口的选择也有讲究。** 降权验证必须用 `getresuid()`（原子 + 一次拿三个），不要用 `getuid()` + `geteuid()` 两次调用拼。HFT 进程常常是多线程的，两次调用之间凭证可能被另一线程改掉。
- **`fsuid` 在 HFT 里唯一的存在价值是「知道自己被什么人影响过」。** 若某段第三方库（NFS 客户端、某些归档工具）调过 `setfsuid`，你会看到「同一个 euid，`open` 一个文件成功、另一个失败」这种诡异现象。**排查方法就是拿 `/proc/self/status` 的 `Uid:` 第 2 列和第 4 列对比**：
  ```bash
  awk '/^Uid:/ { if ($2 != $5) print "euid != fsuid: 有人在调 setfsuid" }' /proc/self/status
  ```
- **`idshow` 这种「打印全部凭证」的工具应该进部署脚本的自检段。** 效果等价于现成的 `id` 命令，但**不依赖外部二进制**——嵌入式 rootfs 里 `id` 可能被裁掉了（`busybox` 有时不带它）。`SG_SIZE = NGROUPS_MAX + 1` 那个 256 KB 的栈数组在嵌入式上要改成 `malloc`。
- **`getresuid` 返回的 65534 是「没有映射」，不是「nobody」。** `from_kuid_munged()` 的 `_munged` 后缀就是「拿不到映射时给你溢出值」。所以 `getuid() == 65534` 在容器 / 嵌入式沙箱里应当先怀疑 `uid_map`（[9.1](./9.1-real-uid-gid.md) 有一个亲手 `unshare(CLONE_NEWUSER)` 的实测：写映射前 `uid=65534`），而不是「这个进程属于 nobody 用户」。

## 自测题

<details>
<summary>1. 读取一个进程的 R/E/S 三个 UID，最推荐哪个接口？为什么不用 <code>getuid()</code> + <code>geteuid()</code>？</summary>

**推荐 `getresuid(&r, &e, &s)`。**

| | `getuid()` + `geteuid()` | `getresuid(&r,&e,&s)` |
|---|--------------------------|------------------------|
| 调用次数 | 2 次（SUID 拿不到，还得再加） | **1 次** |
| 原子性 | ❌ 两次调用之间凭证可能被改 | ✅ 内核取的是 `current_cred()` 快照 |
| 覆盖范围 | R 和 E（S 要另找办法） | **R + E + S** |
| 代价 | POSIX | Linux 扩展（`_GNU_SOURCE`） |

内核实现 `kernel/sys.c:749`：

```c
ruid = from_kuid_munged(cred->user_ns, cred->uid);      /* :755 */
euid = from_kuid_munged(cred->user_ns, cred->euid);     /* :756 */
suid = from_kuid_munged(cred->user_ns, cred->suid);     /* :757 */
```

**多线程下这不是洁癖。** [9.4](./9.4-saved-id.md) 的降权验证代码如果写成 `getuid()` + `geteuid()`，在两个调用之间另一线程恰好改了凭证，就会读出「R 是旧的、E 是新的」这种不可能的组合，验证逻辑失效。`getresuid()` 一次拿到一致快照。

⚠️ 注意 `from_kuid_munged` 的 `_munged`：**拿不到映射时返回溢出值（65534）而不是报错**。所以 `getuid()` 永远不会失败，它总是给你一个看起来正常的数字——这正是 [9.5](./9.5-fs-uid-gid.md)/[9.1](./9.1-real-uid-gid.md) 里 65534 的来源。
</details>

<details>
<summary>2. 表格里 <code>setuid</code> 的「改哪些」为什么写成「R+E+S <b>或</b> 只 E」？</summary>

因为**它的行为取决于调用者的身份**（`setuid(2)` DESCRIPTION + `kernel/sys.c:612`）：

```c
if (ns_capable_setid(old->user_ns, CAP_SETUID)) {
    new->suid = new->uid = kuid;      /* :631  ← 特权：R 和 S 一起设 */
    ...
} else if (!uid_eq(kuid, old->uid) && !uid_eq(kuid, new->suid)) {
    goto error;                       /* :637  → EPERM */
}
new->fsuid = new->euid = kuid;        /* :641  ← 两条路都改 E（和 fsuid） */
```

| 调用者 | 结果 |
|--------|------|
| 有 `CAP_SETUID`（或 euid==0 且能力齐全） | `r = e = s = u`。**不可逆**（saved 被砸了） |
| 非特权，且 `u ∈ {ruid, suid}` | 只 `e = u`（等价于 `seteuid`） |
| 非特权，且 `u ∉ {ruid, suid}` 且 `u` 有映射 | `-EPERM` |
| 任意身份，`u` 无映射 | `-EINVAL` |

所以 `setuid` 是本章**唯一一个「同名同参、语义随环境变」**的接口。`setuid(2)` 的描述也承认这点："Under Linux, `setuid()` is implemented like the POSIX version with the `_POSIX_SAVED_IDS` feature."

**工程结论**：安全代码里不要用 `setuid()` 表达「永久降权」，用 `setresuid(t, t, t)`。它的语义不依赖身份，而且 `-1` 能精确控制改哪几项。
</details>

<details>
<summary>3. 读了 R/E/S 之后想读 fsuid，有标准接口吗？</summary>

**没有 getter。** 只能借用一个**写**函数：

| 办法 | 写法 | 备注 |
|------|------|------|
| API（推荐） | `uid_t f = (uid_t) setfsuid((uid_t) -1);` | `-1` 必然非法 → 一定不改状态 |
| `/proc`（也推荐） | `/proc/self/status` 的 `Uid:` **第 4 列** | 无副作用、一次拿 4 列、无需 syscall |
| 原书 Listing 9-1 的写法 | `fsuid = setfsuid(0);` | 只有在「euid==0 或 fsuid==0」时才可靠 |

`setfsuid(2)` RETURN VALUE："**On both success and failure, this call returns the previous filesystem user ID of the caller.**"——所以返回值**恰好**就是「调用前的 fsuid」，这就是能拿它当读接口的原因。

原书 `proccred/idshow.c` 用的是 `setfsuid(0)`，配套注释写得很明白：

```c
/* Attempts to change the file-system IDs are always ignored
   for unprivileged processes, but even so, the following
   calls return the current file-system IDs */
fsuid = setfsuid(0);
```

它传 `0` 而不是 `-1`：在特权进程下 `0` 是合法 no-op，在非特权进程下被静默拒绝——**两种情况下都返回当前 fsuid**。这个技巧成立的前提是「进程的 euid 是 0，或者 fsuid 本来就是 0」。**现代代码用 `-1` 更安全**（无条件保证不改状态）。
</details>

<details>
<summary>4. <code>setresuid(-1, 0, -1)</code> 在「R=1000 E=1000 S=1000」的进程里会失败吗？</summary>

**会，`EPERM`。**

因为它试图把 **EUID 设成 0**，而 `0 ∉ {ruid, euid, suid} = {1000, 1000, 1000}`，而且进程没有 `CAP_SETUID`。

`setresuid(2)` DESCRIPTION："An unprivileged process may change its real UID, effective UID, and saved set-user-ID, **each to one of: the current real UID, the current effective UID, or the current saved set-user-ID**."

内核 `kernel/sys.c:700-708`：先算出三个 `*_new` 布尔（「这个新值不在任何现有 ID 里」），任一为真且没有 `CAP_SETUID` 就 `-EPERM`。

把这一点和 set-user-ID 程序对照，就知道 `saved` 为什么重要了：

| 进程状态 | `setresuid(-1, 0, -1)` |
|----------|------------------------|
| `R=1000 E=1000 S=1000`（普通进程） | **EPERM** ❌ |
| `R=1000 E=0 S=0`（刚 exec 完 SUID-root 程序） | **成功**，`euid` 已经是 0；若 `E=1000 S=0` 则设成 0 也合法，因为 `0 ∈ {R,E,S} = {1000,1000,0}` ✅ |

**`saved` 里的那个 0，就是非特权进程能「升回 root」的全部依据。** 一旦 saved 被砸（`setuid` / `setresuid(t,t,t)`），`{r,e,s}` 里就再没有 0 了——这条命令会永远 EPERM。这就是 [9.4](./9.4-saved-id.md) 讲的「永久降权」的机制。
</details>

<details>
<summary>5. 原书 Listing 9-1 的输出全是 <code>???</code>，是程序有问题吗？</summary>

**不是。是环境没有账号数据。**

`idshow.c` 调 `userNameFromId()` / `groupNameFromId()`（Ch8 Listing 8-1 的助手），它们内部是 `getpwuid()` / `getgrgid()`。本容器的 `/etc/passwd` 里只有一条 `ce` 账号的记录（[Ch8 §8.4 实测](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)），所以：

```text
UID: real=??? (0); eff=??? (0); saved=??? (0); fs=??? (0); 
GID: real=??? (0); eff=??? (0); saved=??? (0); fs=??? (0); 
Supplementary groups (1): ??? (0) 
```

程序对 `NULL` 返回值的处理是打印 `"???"`——**这是正确的降级行为**（[Ch8 的 `ugid_functions` 契约](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)：`userNameFromId()` 查不到返回 `NULL`），不是错误。

**真正有价值的是数字那一半**：`real / eff / saved / fs` 四个位置都是 `0`，顺序与 `proc_pid_status(5)` 的 "Real, effective, saved set, and filesystem UIDs" 完全一致；补充组那行 `(1)` 说明有 1 个组、gid 是 0。换一台有完整 `/etc/passwd` 的机器，同样的二进制会打出可读的名字。

**这也说明一个测试方法论**：`???` 只说明**环境数据缺失**，不说明**程序逻辑错误**。验证程序逻辑要看数字部分和自己的身份是否吻合。
</details>
