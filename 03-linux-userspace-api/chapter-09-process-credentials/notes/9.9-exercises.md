## 练习 9-1：五个调用之后，四类 ID 各是什么

**题目原文**

> Assume in each of the following cases that the initial set of process user IDs is **real=1000 effective=0 saved=0 file-system=0**. What would be the state of the user IDs after the following calls?
>
> a) `setuid(2000);`
> b) `setreuid(–1, 2000);`
> c) `seteuid(2000);`
> d) `setfsuid(2000);`
> e) `setresuid(–1, 2000, 3000);`

### 答案表

| 调用 | Real | Effective | Saved | File-system |
|------|------|-----------|-------|-------------|
| **初始状态** | 1000 | 0 | 0 | 0 |
| a) `setuid(2000)` | **2000** | **2000** | **2000** | **2000** |
| b) `setreuid(-1, 2000)` | 1000 | **2000** | **2000** | **2000** |
| c) `seteuid(2000)` | 1000 | **2000** | **0** | **2000** |
| d) `setfsuid(2000)` | 1000 | **0** | **0** | **2000** |
| e) `setresuid(-1, 2000, 3000)` | 1000 | **2000** | **3000** | **2000** |

### 推导（每格都有源码依据）

**前提**：初始 `EUID = 0` 且该程序是 set-user-ID-root 程序 → **进程有 `CAP_SETUID`**（`setuid(2)` 的 privileged 判据）。所以 a / b / e 走的是**特权分支**。

| 小题 | 内核依据 |
|------|----------|
| **a** | `kernel/sys.c:630-631`：有 `CAP_SETUID` → `new->suid = new->uid = kuid`；`:641` `new->fsuid = new->euid = kuid`。**R/E/S/F 四个全变 2000。** `setuid(2)`："if it is the superuser, **all process-related user ID's are set to `uid`**" |
| **b** | `kernel/sys.c:575-577`：`ruid == -1` 但 `euid(2000) != old->uid(1000)` → 条件成立 → **`new->suid = new->euid = 2000`**；`:578` fsuid 同步 2000。RUID 保持 1000 |
| **c** | `seteuid` **只改 EUID**（`kernel/sys.c` 里 `seteuid` 走 `setresuid(-1, euid, -1)` 的等价路径）。saved **保持 0** —— 这是本节最该记住的一格；fsuid 照旧同步 2000 |
| **d** | `kernel/sys.c:883-885` 放行（`uid` ∈ {R, E, S, F} 或 `CAP_SETUID`）→ 内层 `:886-890` 只有值**确实不同**才 `new->fsuid = kuid`（`:887`），**R/E/S 一点都不动**。这是 `setfsuid` 与「所有 euid 变更都同步 fsuid」那条规则**唯一**的例外方向——它是**反过来**的（只改 fsuid，不改 euid） |
| **e** | `kernel/sys.c:714-726`：三项各自按「是不是 -1」独立设置 → `uid` 不动、`euid = 2000`、`suid = 3000`；`:726` `new->fsuid = new->euid = 2000` |

**两个记忆钩子**：

- **c 与 b 的差别在 saved**：同样是「把 euid 设成 2000」，`seteuid` 让 saved 保持 0，`setreuid` 让 saved 变成 2000。差别来自 `setreuid` 的那条附加规则（`:575-577`）。
- **d 是唯一「不碰 euid」的一格**：R/E/S 三个全是初始值，只有 fsuid 变。这说明 `fsuid` 是**独立可写**的（[9.5](./9.5-fs-uid-gid.md)）。

### 可执行验证器

一个进程的凭证改了就回不去，所以五个小题**必须各起一个新进程**。[`../code/ex9_1_id_state.c`](../code/ex9_1_id_state.c) 用 `argv[1]` 选 a..e，每题自检初始状态、执行、打印「实测 / 期望 / 依据 / 是否一致」四行。

```c
/* ex9_1_id_state.c —— 原书练习 9-1 的**可执行验证器**
 *
 * 原书练习 9-1（TLPI 9.9）：
 *   "假设进程的初始用户 ID 集合是 real=1000, effective=0, saved=0, file-system=0。
 *    在下列调用之后，这些 ID 分别是什么状态？
 *      (a) setuid(2000)
 *      (b) setreuid(-1, 2000)
 *      (c) seteuid(2000)
 *      (d) setfsuid(2000)
 *      (e) setresuid(-1, 2000, 3000)"
 *
 * 每一个小题都要**从同一个初始状态出发**，而一个进程的凭证改了就回不去，
 * 所以本程序一次只做一题（用 argv[1] 选 a..e），每题都要重启一个新进程。
 *
 * 怎么造出 R=1000 / E=0 / S=0 这个初始状态：
 *   正是「一个 set-user-ID-root 程序被 uid 1000 的用户执行」时的状态。
 *      gcc -O0 -Wall -Wextra -o ex9_1_id_state ex9_1_id_state.c
 *      sudo chown root ex9_1_id_state
 *      sudo chmod u+s ex9_1_id_state
 *      sudo -u '#1000' ./ex9_1_id_state a      # 依次 a..e
 *
 * 本程序会先**自检**初始状态；不符就明确说「这台机器上做不了这个实验」并给出上面的
 * 步骤，而不是把一个假的成功打印出来。
 *
 * 「期望值」一栏怎么来的（全部按 kernel/sys.c 的源码推，不是抄的）：
 *   特权分支 setuid()      : new->suid = new->uid = uid; 然后 new->fsuid = new->euid = uid
 *   特权分支 setreuid(r,e) : suid 在「r != -1 或 e != 旧 ruid」时被设为新 euid；
 *                            最后恒有 new->fsuid = new->euid
 *   setresuid(r,e,s)       : 三者各自独立改（-1 = 不改），最后 new->fsuid = new->euid
 *   setfsuid(u)            : 只改 fsuid，不动 R/E/S
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex9_1_id_state ex9_1_id_state.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/fsuid.h>
#include <sys/types.h>
#include <unistd.h>

struct quad {
    unsigned r, e, s, f;
};

static struct quad snap(void)
{
    struct quad q;
    uid_t r, e, s;
    if (getresuid(&r, &e, &s) == -1) {
        perror("getresuid");
        exit(1);
    }
    q.r = (unsigned) r;
    q.e = (unsigned) e;
    q.s = (unsigned) s;
    q.f = (unsigned) setfsuid((uid_t) -1);
    return q;
}

static void print_quad(const char *tag, struct quad q)
{
    printf("  %-10s real=%-6u effective=%-6u saved=%-6u fs=%-6u\n",
           tag, q.r, q.e, q.s, q.f);
}

int main(int argc, char *argv[])
{
    if (argc != 2 || strchr("abcde", argv[1][0]) == NULL || argv[1][1] != '\0') {
        fprintf(stderr, "用法: %s <a|b|c|d|e>\n", argv[0]);
        return 2;
    }
    char which = argv[1][0];

    printf("=== 初始状态自检 ===\n");
    struct quad q0 = snap();
    print_quad("实测", q0);
    printf("  期望  real=1000   effective=0      saved=0      fs=0\n");
    if (!(q0.r != 0 && q0.e == 0 && q0.s == 0)) {
        printf("\n  ✗ 初始状态不符 —— 本环境做不了这个实验。\n");
        printf("    它需要「一个 set-user-ID-root 程序被 uid 1000 的用户执行」。\n");
        printf("    在容器里做不到，因为容器只映射了 1 个 uid，chown 不出 root 属主：\n");
        printf("      cat /proc/self/uid_map      # 只有一行 \"0 <host> 1\"\n");
        printf("    真机上照上面注释里的四条命令做即可。\n");
        printf("    本题的答案（按 kernel/sys.c 推导）见 note 9.9 的答案表。\n");
        return 0;                    /* 不是程序出错，是环境不具备 */
    }

    printf("\n=== 执行 (%c) ===\n", which);
    errno = 0;
    int rc = 0;
    switch (which) {
    case 'a': rc = setuid((uid_t) 2000);                    break;
    case 'b': rc = setreuid((uid_t) -1, (uid_t) 2000);      break;
    case 'c': rc = seteuid((uid_t) 2000);                   break;
    case 'd': rc = setfsuid((uid_t) 2000);                  break;
    case 'e': rc = setresuid((uid_t) -1, (uid_t) 2000, (uid_t) 3000); break;
    }
    printf("  返回值 %d   errno=%d (%s)\n", rc, errno, errno ? strerror(errno) : "未置位");

    struct quad q1 = snap();
    print_quad("结果", q1);

    /* 期望值表（练习 9-1 的答案） */
    struct quad want;
    const char *why;
    switch (which) {
    case 'a':
        want = (struct quad) { 2000, 2000, 2000, 2000 };
        why = "有 CAP_SETUID -> suid 与 uid 一起设；fsuid 跟随 euid";
        break;
    case 'b':
        want = (struct quad) { 1000, 2000, 2000, 2000 };
        why = "ruid=-1 不动；euid 改了且 != 旧 ruid -> suid 也设成新 euid";
        break;
    case 'c':
        want = (struct quad) { 1000, 2000, 0, 2000 };
        why = "seteuid 只改 euid；suid 保持 0；fsuid 跟随 euid";
        break;
    case 'd':
        want = (struct quad) { 1000, 0, 0, 2000 };
        why = "setfsuid 只改 fsuid，R/E/S 一点不动";
        break;
    default:
        want = (struct quad) { 1000, 2000, 3000, 2000 };
        why = "三者各自生效；fsuid 跟随 euid";
        break;
    }
    print_quad("期望", want);
    printf("  依据: %s\n", why);
    printf("  一致? %s\n",
           (q1.r == want.r && q1.e == want.e && q1.s == want.s && q1.f == want.f)
               ? "是" : "**否** —— 若初值自检通过而这里不一致，说明内核行为与推导不符");
    return 0;
}
```

真机跑法（把初始状态造出来：**一个 set-user-ID-root 程序被 uid 1000 的用户执行**）：

```bash
gcc -O0 -Wall -Wextra -o ex9_1_id_state ex9_1_id_state.c
sudo chown root ex9_1_id_state
sudo chmod u+s ex9_1_id_state
sudo -u '#1000' ./ex9_1_id_state a      # 依次 a..e
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

不带参数（用法提示走 stderr，退出码 2）：

```text
用法: ./output.s <a|b|c|d|e>
```

`./ex9_1_id_state a`：

```text
=== 初始状态自检 ===
  实测     real=0      effective=0      saved=0      fs=0     
  期望  real=1000   effective=0      saved=0      fs=0

  ✗ 初始状态不符 —— 本环境做不了这个实验。
    它需要「一个 set-user-ID-root 程序被 uid 1000 的用户执行」。
    在容器里做不到，因为容器只映射了 1 个 uid，chown 不出 root 属主：
      cat /proc/self/uid_map      # 只有一行 "0 <host> 1"
    真机上照上面注释里的四条命令做即可。
    本题的答案（按 kernel/sys.c 推导）见 note 9.9 的答案表。
```

**解读**

1. **程序先做「初值自检」再动手**：它要求 `real != 0 && effective == 0 && saved == 0`。这三条正是「SUID-root 程序被普通用户执行」的特征。**不满足就明确说「这台机器上做不了这个实验」**，并给出真机的四条命令。
   - 本容器的实测值是 `real=0 effective=0 saved=0`：**real 是 0 而不是 1000**，因为容器只映射了 1 个 uid（[`uid_map` = `0 113 1`](./9.1-real-uid-gid.md)），`chown` 不出 root 属主，所以造不出「普通用户执行 root 程序」这个场景。
2. **`return 0` 而不是报错**（源码里 `return 0; /* 不是程序出错，是环境不具备 */`）。这是有意的：**「环境不满足前提」和「程序有 bug」是两类事**，退出码要区分开。
3. **为什么不做「一次跑完五题」的版本**：一题的凭证改了就回不去，第二题就不是从初始状态出发了（比如 (b) 之后 saved 已经变成 2000，(c) 的期望值就对不上）。**所以必须一题一进程**，这也是 `argv[1]` 存在的理由。
4. **`snap()` 用 `setfsuid((uid_t) -1)` 读 fsuid**（[9.5](./9.5-fs-uid-gid.md) 的惯用法），`print_quad()` 把 R/E/S/F 四个值并排——正好对应答案表的四列。
5. **真机上跑起来会看到什么**：每题打印「一致? 是」。`(c)` 那一题会最直观——`结果 real=1000 effective=2000 saved=0 fs=2000`，**saved 那一列在「euid 变了」的同时保持 0**，这就是 `seteuid` 与 `setreuid` 的分水岭。

## 练习 9-2：这样的进程算特权吗？

**题目原文**

> Is a process with the following user IDs privileged? Explain your answer.
>
> **real=0 effective=1000 saved=1000 file-system=1000**

### 答案

**不算特权进程**，但它可以**轻易地**变回特权。

| 判据 | 结论 |
|------|------|
| TLPI 的判据（`euid == 0`） | `euid = 1000` → **不是特权进程** |
| 内核的判据（capability） | `euid != 0` 时 effective capability 集合通常为空 → **不是特权进程**——两种判据在这里一致 |

**为什么「轻易变回特权」**：`real = 0` 落在非特权 `seteuid` / `setuid` 的放行集合里。

```c
seteuid(0);      /* 0 ∈ {ruid=0, suid=1000}  → 成功，euid 变 0 */
```

`seteuid(2)` DESCRIPTION："An unprivileged process can change an effective ID only to the same value as the corresponding **real or saved set ID**." —— `0` 恰好就是 RUID。

**这个状态长什么样、从哪来**：典型的场景是「一个本来以 root 启动的程序，用 `seteuid(1000)` 临时降了权但没砸掉 saved，而 real 还是 0」。也就是说它**处在一个「挂起特权」的中间态**，不是「已经降权」。

**教学价值**：这道题考的是「priviliged 的判据只看 effective，不看 real」这一条。本题里 `real=0` 完全不改变「不特权」这个结论，但它决定了**恢复特权的成本**——**从零成本到零成本**。所以真实的安全评估里，`real=0` 这个事实比 `euid` 更值得警惕。

> ⚠️ 注意本题与 [练习 9-1](#练习-9-1五个调用之后四类-id-各是什么) 的初始状态是**对偶**的：9-1 是 `real=1000 effective=0`（普通用户借 SUID 程序拿到了特权），9-2 是 `real=0 effective=1000`（root 主动挂起了特权）。

## 练习 9-3：用 `setgroups()` + §8.4 的库函数实现 `initgroups()`

**题目原文**

> Implement `initgroups()` using `setgroups()` and library functions for retrieving information from the password and group files (**Section 8.4**). Remember that a process must be privileged in order to be able to call `setgroups()`.

### 实现思路（四步）

```
① getpwnam(user)                 -> 拿到主组 gid（如果不信传进来的 basegid）
② 遍历组数据库（fgetgrent）       -> 收集「user 出现在 gr_mem 里」的所有 gid
③ 把 basegid（主组）并进列表
④ setgroups(n, list)             -> 一次装上
```

第 ② 步用 **`fgetgrent(FILE *)`** 而不是 `getgrent()`：`getpwnam()` / `getgrent()` 那一族读的路径是**编译期写死**的（[Ch8 §8.4](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)），`fgetgrent()` 是**唯一能指定任意组文件的正规入口**。

### 参考实现

[`../code/ex9_3_my_initgroups.c`](../code/ex9_3_my_initgroups.c) 除了实现 `my_initgroups()`，还做了两件比「照抄答案」更有用的事：

1. **在没有 `/etc/group` 的环境（本容器）里先造一个合成组文件**再扫——于是这份实现**在这里真的能跑出结果**，而不是卡在 `EPERM` 上；
2. **顺手调一遍 glibc 的 `getgrouplist()` 做对照**——那个函数做的是同一套算法，但**只认系统的 NSS 组库**，扫不到合成的文件。这个差异本身就说明「库函数读的是哪个数据库」是被 `nsswitch.conf` 决定、可以被替换/缺失的。

```c
/* ex9_3_my_initgroups.c —— 原书练习 9-3：自己实现 initgroups()
 *
 * 原书练习 9-3（TLPI 9.9）：
 *   "用 setgroups() 和第 8.4 节里那些读口令/组文件的库函数实现 initgroups()。
 *    记住：进程必须有特权才能调用 setgroups()。"
 *
 * 实现思路（就是 glibc initgroups() 做的事）：
 *   1. 遍历组数据库，凡是成员名单里出现该用户的组，把它的 gid 收进来；
 *   2. 再把 basegid（主组）也加进去；
 *   3. 调 setgroups() 一次装上。
 *
 * 本程序有两点比「照抄答案」更有用：
 *   ① 它用 **fgetgrent(FILE *)**（Ch8 §8.4）扫一个**可以自己指定**的组文件。
 *      因为评测容器里根本没有 /etc/group，程序会先造一个合成的组文件再扫 ——
 *      于是这份实现**在这里真的能跑出结果**，而不是卡在 EPERM 上。
 *   ② 它顺手把 glibc 的 getgrouplist() 也调一遍做对照：那个函数做的是同一件事，
 *      只是它只认系统的组数据库（NSS），扫不到我们合成的文件 —— 这个差异本身
 *      就说明「库函数读的是哪个文件」是可以被替换/缺失的。
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex9_3_my_initgroups ex9_3_my_initgroups.c
 * 用法: ./ex9_3_my_initgroups [用户名] [主组gid] [组文件]
 *       默认: alice 1000 /etc/group（不存在时自动改用 /tmp 合成文件）
 */
#define _GNU_SOURCE
#include <errno.h>
#include <grp.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#define MAXGROUPS 64

/* 造一个合成的组文件，字段格式与 /etc/group 完全一致（4 字段） */
static const char *make_synthetic_group_file(void)
{
    const char *p = "/tmp/ex9_3_group";
    FILE *fp = fopen(p, "w");
    if (fp == NULL)
        return NULL;
    /* 注意最后一行空成员的组：它**没有**任何成员，实现里必须不被选中 */
    fputs("wheel:x:10:alice,bob\n", fp);
    fputs("dev:x:2000:alice\n", fp);
    fputs("docker:x:999:bob,alice\n", fp);
    fputs("empty:x:3000:\n", fp);        /* gr_mem[0] == NULL 的组 */
    fclose(fp);
    return p;
}

/* 核心：扫组文件，收集「user 是成员」的所有 gid，最后补上 basgid */
static int my_initgroups(const char *user, gid_t basegid, const char *path,
                         gid_t *out, int max, int *count, const char **scanned)
{
    gid_t list[MAXGROUPS];
    int n = 0;
    int empty_seen = 0;

    FILE *fp = fopen(path, "r");
    if (fp == NULL)
        return -1;
    *scanned = path;

    struct group *gr;
    while ((gr = fgetgrent(fp)) != NULL) {
        if (gr->gr_mem == NULL)
            continue;
        if (gr->gr_mem[0] == NULL) {
            empty_seen++;                       /* 空组：明确记一笔 */
            continue;
        }
        for (char **m = gr->gr_mem; *m != NULL; m++) {
            if (strcmp(*m, user) == 0) {
                if (n < MAXGROUPS)
                    list[n++] = gr->gr_gid;
                break;                          /* 同一组只收一次 */
            }
        }
    }
    fclose(fp);

    printf("  扫 %s：命中 %d 个组，另有 %d 个「空成员」组被跳过\n",
           path, n, empty_seen);

    list[n++] = basegid;                        /* 主组也要在集合里 */
    if (n > max)
        return -2;
    memcpy(out, list, sizeof(gid_t) * (size_t) n);
    *count = n;
    return 0;
}

int main(int argc, char *argv[])
{
    const char *user = (argc > 1) ? argv[1] : "alice";
    gid_t basegid = (argc > 2) ? (gid_t) strtoul(argv[2], NULL, 10) : (gid_t) 1000;
    const char *path = (argc > 3) ? argv[3] : "/etc/group";

    printf("=== 目标: 为 %s 构造补充组列表（主组 gid=%u）===\n",
           user, (unsigned) basegid);

    if (access(path, R_OK) != 0) {
        printf("  %s 不可读（%s），改用合成组文件\n", path, strerror(errno));
        path = make_synthetic_group_file();
        if (path == NULL) {
            printf("  造合成文件失败: %s\n", strerror(errno));
            return 1;
        }
    }

    gid_t list[MAXGROUPS];
    int n = 0;
    const char *used = NULL;
    if (my_initgroups(user, basegid, path, list, MAXGROUPS, &n, &used) != 0) {
        printf("  my_initgroups 失败: %s\n", strerror(errno));
        return 1;
    }

    printf("\n=== 我算出来的列表（%d 个）===\n  ", n);
    for (int i = 0; i < n; i++)
        printf("%u ", (unsigned) list[i]);
    printf("\n");

    printf("\n=== 对照: glibc 的 getgrouplist()（同一算法，但只读系统组库）===\n");
    {
        int ng = MAXGROUPS;
        gid_t gl[MAXGROUPS];
        errno = 0;
        int rc = getgrouplist(user, basegid, gl, &ng);
        printf("  getgrouplist(\"%s\", %u, ...) = %d  ngroups=%d  errno=%d (%s)\n",
               user, (unsigned) basegid, rc, ng, errno, strerror(errno));
        printf("  列表: ");
        for (int i = 0; i < ng; i++)
            printf("%u ", (unsigned) gl[i]);
        printf("\n");
        printf("  差异原因: getgrouplist 走 NSS（本环境无 /etc/group，也没有\n");
        printf("            nsswitch.conf），扫不到合成文件，所以只剩 basegid。\n");
    }

    printf("\n=== 装上去: setgroups(%d, list) ===\n", n);
    errno = 0;
    int rc = setgroups((size_t) n, list);
    printf("  返回 %d  errno=%d (%s)\n", rc, errno, strerror(errno));
    if (rc == -1)
        printf("  预期之内: setgroups 要 CAP_SETGID，且 /proc/self/setgroups 是 deny，\n"
               "  两道闸门本环境都关着（见 c9_3_groups.c）。\n");
    else
        printf("  居然成功了 —— 那说明本进程确实有 CAP_SETGID。\n");

    printf("\n=== glibc 的 initgroups() 做的是同一件事 ===\n");
    errno = 0;
    rc = initgroups(user, basegid);
    printf("  initgroups(\"%s\", %u) = %d  errno=%d (%s)\n",
           user, (unsigned) basegid, rc, errno, strerror(errno));
    printf("  它的 EPERM 是 setgroups() 传上来的，所以和上面那条必然同因同果。\n");
    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o ex9_3_my_initgroups ex9_3_my_initgroups.c
./ex9_3_my_initgroups                # 默认 alice 1000
./ex9_3_my_initgroups alice 1000     # 显式指定（输出一致）
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
=== 目标: 为 alice 构造补充组列表（主组 gid=1000）===
  /etc/group 不可读（No such file or directory），改用合成组文件
  扫 /tmp/ex9_3_group：命中 3 个组，另有 1 个「空成员」组被跳过

=== 我算出来的列表（4 个）===
  10 2000 999 1000 

=== 对照: glibc 的 getgrouplist()（同一算法，但只读系统组库）===
  getgrouplist("alice", 1000, ...) = 1  ngroups=1  errno=2 (No such file or directory)
  列表: 1000 
  差异原因: getgrouplist 走 NSS（本环境无 /etc/group，也没有
            nsswitch.conf），扫不到合成文件，所以只剩 basegid。

=== 装上去: setgroups(4, list) ===
  返回 -1  errno=1 (Operation not permitted)
  预期之内: setgroups 要 CAP_SETGID，且 /proc/self/setgroups 是 deny，
  两道闸门本环境都关着（见 c9_3_groups.c）。

=== glibc 的 initgroups() 做的是同一件事 ===
  initgroups("alice", 1000) = -1  errno=1 (Operation not permitted)
  它的 EPERM 是 setgroups() 传上来的，所以和上面那条必然同因同果。
```

**解读**

1. **「命中 3 个组，另有 1 个空成员组被跳过」是本实现的核心考点。** 合成组文件是四行：

   ```text
   wheel:x:10:alice,bob
   dev:x:2000:alice
   docker:x:999:bob,alice
   empty:x:3000:
   ```

   `alice` 出现在前三个组的成员名单里（`10` / `2000` / `999`），第四个 `empty:x:3000:` **一个成员都没有**——`gr_mem[0] == NULL`。`fgetgrent()` 返回的 `struct group` 里 `gr_mem` 是**以 `NULL` 结尾的字符串数组**，**空组的 `gr_mem[0]` 就是 `NULL`**（[Ch8 §8.3 的空组陷阱](../../chapter-08-users-and-groups/notes/8.3-group-file.md)）。实现里的判断是：

   ```c
   if (gr->gr_mem == NULL)  continue;
   if (gr->gr_mem[0] == NULL) { empty_seen++; continue; }   /* 空组：明确记一笔 */
   ```

   **两层判断都要有**：`gr_mem == NULL` 是「这个结构体没填」（不同 libc 表现不一致），`gr_mem[0] == NULL` 是「这个组确实没有成员」。少判一层就会段错误或漏计数。

2. **列表 `10 2000 999 1000` 的最后一个 `1000` 是主组**——`list[n++] = basegid;` 那一步补进去的。顺序是「组文件里出现的顺序 + 主组」，**这是实现的顺序，不是契约**（内核 `setgroups()` 会 `groups_sort()` 重排，[9.6](./9.6-supplementary-groups.md)）。

3. **`getgrouplist()` 那一行是最有教学价值的一行**：`= 1  ngroups=1  errno=2`。
   - **返回值 `1` 不是错误**，函数正常返回；`ngroups` 最终是 1，列表里只有 `basegid`；
   - **`errno = 2 (ENOENT)` 是残留**——查 NSS 组库时 `open("/etc/group")` 失败留下的。**函数本身没失败。**
   - 所以 **「`errno != 0` 就是出错」是错的**，必须**先看返回值**。这和 [Ch8 §8.4 的 `errno` 范式](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md) 是同一件事的两面。

4. **`setgroups(4, list)` 和 `initgroups("alice", 1000)` 都返回 `-1 / EPERM(1)`**，而且**必然同因**——`initgroups(3)` 的 ERRORS 里 `EPERM` 一条写的就是 "**See the underlying system call `setgroups(2)`**"。这里两道闸门都关着：`CapEff = 0`（无 `CAP_SETGID`）+ `/proc/self/setgroups = deny`（[9.6](./9.6-supplementary-groups.md)）。

5. **题面提示「a process must be privileged」在真机上的做法**（[练习 9-3 的官方答案](https://github.com/wangshifuzecy/tlpi_solutions/tree/main/ch09) 那种写法）：

   ```bash
   gcc -O0 -Wall -Wextra -o ex9_3_my_initgroups ex9_3_my_initgroups.c
   sudo chown root ex9_3_my_initgroups
   sudo chmod u+s ex9_3_my_initgroups      # 用 SUID 拿到 CAP_SETGID
   ./ex9_3_my_initgroups alice 1000
   ```

   此时 `setgroups()` 那一段会返回 0，并且**它的副作用会真的生效**——之后再调 `getgroups()` 就能看到 4 个组。**这正是 `login` / `su` / `sshd` 在切换用户时做的事。**

## 练习 9-4：`X` → set-user-ID 程序（非 root）的四种接口

**题目原文**

> If a process whose user IDs all have the value **X** executes a set-user-ID program whose user ID, **Y**, is **nonzero**, then the process credentials are set as follows: **real=X effective=Y saved=Y**. (We ignore the file-system user ID, since it tracks the effective user ID.)
>
> Show the `setuid()`, `seteuid()`, `setreuid()`, and `setresuid()` calls, respectively, that would be used to perform the following operations:
>
> a) **Suspend and resume** the set-user-ID identity (i.e., switch the effective user ID to the value of the real user ID and then back to the saved set-user-ID).
> b) **Permanently drop** the set-user-ID identity (i.e., ensure that the effective user ID and the saved set-user-ID are set to the value of the real user ID).
>
> (This exercise also requires the use of `getuid()` and `geteuid()` to retrieve the process's real and effective user IDs.) **Note that for certain of the system calls listed above, some of these operations can't be performed.**

**初始状态**：`R=X, E=Y, S=Y`（`Y ≠ 0`）→ **`euid != 0`，所以是非特权进程**（[练习 9-2](#练习-9-2这样的进程算特权吗) 的判据）→ 所有调用走**非特权分支**。

### 答案表

| 接口 | 挂起（suspend） | 恢复（resume） | 永久丢弃（permanent drop） |
|------|------------------|----------------|----------------------------|
| `setuid()` | `setuid(getuid())` | `setuid(e)`（`e = geteuid()` 先存下来） | ❌ **做不到** |
| `seteuid()` | `seteuid(getuid())` | `seteuid(e)` | ❌ **做不到** |
| `setreuid()` | `setreuid(-1, getuid())` | `setreuid(-1, e)` | ✅ `setreuid(getuid(), getuid())` |
| `setresuid()` | `setresuid(-1, getuid(), -1)` | `setresuid(-1, e, -1)` | ✅ `setresuid(getuid(), getuid(), getuid())` |

（`e` 是进入本题前用 `geteuid()` 存下的初始 effective uid，也就是 Y。必须在第一次降权**之前**存——降权后就取不到 Y 了。）

### 为什么 `setuid` / `seteuid` 做不到「永久丢弃」

因为**非特权进程调用它们时都只改 EUID，不动 saved**：

- `setuid(u)` 非特权分支：`kernel/sys.c:637` 只要求 `u ∈ {ruid, suid}`，然后 `:641` `new->fsuid = new->euid = kuid` —— **`new->suid` 从头到尾没被赋值**，保持 `old->suid = Y`。
- `seteuid(e)`：语义就是「只改 EUID」（`setresuid(-1, e, -1)` 的等价物）。

所以 saved 永远是 Y，而**永久丢弃的定义就是 `saved ← X`**。**两个调用都办不到。**

### 为什么 `setreuid` / `setresuid` 办得到

- `setreuid(getuid(), getuid())`：`ruid != -1` → 命中 `kernel/sys.c:575-577` 的条件 → `new->suid = new->euid = X`。✅
- `setresuid(X, X, X)`：三个参数显式给出，`:724-725` 把 `new->suid = ksuid = X`。✅

### 一个细节：「恢复」为什么用 `e` 而不是 `Y`

`e` 就是初始的 `euid`，也就是 `Y`——两者数值相同，但**用 `geteuid()` 存下来的写法更稳**：它不假设「文件属主 uid 是多少」，而是「记住我降权前是谁」。这是 TLPI 题面明确要求用 `getuid()` / `geteuid()` 的原因。

### ⚠️ 网上答案集里的一处错误

搜索到的若干答案集把 `setreuid()` 的**挂起**写成：

```c
setreuid(-1, geteuid());      /* ✗ 错的 */
```

**这是错的。** 在第一次调用时 `geteuid()` 就是 `Y`，而 `setreuid(-1, Y)` 的结果是 `euid` 从 `Y` 变成 `Y` —— **一个 no-op，什么也没挂起**。

正确的挂起是 `setreuid(-1, getuid())`（把 euid 换成 RUID = X）。推导依据是同一个 `kernel/sys.c:575-577`：

```c
if (ruid != (uid_t) -1 ||
    (euid != (uid_t) -1 && !uid_eq(keuid, old->uid)))
    new->suid = new->euid;
```

用 `setreuid(-1, getuid())` 时，`keuid = X == old->uid` → 条件为假 → **suid 保持 Y**（这是好事：挂起不能砸掉 saved，否则就恢复不了了）。而用 `setreuid(-1, geteuid())`（= Y）时，`Y != old->uid(X)` → 条件为真 → `suid = Y`，**虽然结果数值一样，但这次「挂起」根本没发生**。

**结论**：网上流传的答案集不能照抄，**必须按 `kernel/sys.c` 逐条推**。这也是本仓库所有 Ch9 笔记都给出内核行号的原因。

## 练习 9-5：`X` → set-user-ID-**root** 程序的四种接口

**题目原文**

> Repeat the previous exercise for a process executing a set-user-ID-**root** program, which has the following initial set of process credentials: **real=X effective=0 saved=0**

**初始状态**：`R=X, E=0, S=0` → `euid == 0` → **特权进程**。

### 答案表

| 接口 | 挂起（suspend） | 恢复（resume） | 永久丢弃（permanent drop） |
|------|------------------|----------------|----------------------------|
| `setuid()` | ❌ **做不到** | ❌ **做不到** | ✅ `setuid(getuid())`（见下方备注） |
| `seteuid()` | `seteuid(getuid())` | `seteuid(0)` | ❌ 做不到 |
| `setreuid()` | `setreuid(-1, getuid())` | `setreuid(-1, 0)` | ✅ `setreuid(getuid(), getuid())` |
| `setresuid()` | `setresuid(-1, getuid(), -1)` | `setresuid(-1, 0, -1)` | ✅ `setresuid(getuid(), getuid(), getuid())` |

### 与 9-4 的对照：`setuid` 的能力正好互补

这是两题合起来最该记住的一张表：

| 初始状态 | `setuid()` 能做什么 | 不能做什么 |
|----------|---------------------|-----------|
| 9-4：`E = Y ≠ 0`（**非特权**） | ✅ **挂起 / 恢复**（只改 euid，saved 保 Y） | ❌ 永久丢弃（saved 动不了） |
| 9-5：`E = 0`（**特权**） | ✅ **永久丢弃**（`setuid(getuid())` → R=E=S=X） | ❌ 挂起 / 恢复（saved 被一起砸了） |

**`setuid()` 要么只能挂起/恢复，要么只能永久丢弃 —— 从来不能两者兼得。** 原因就是 `kernel/sys.c:630-641` 那个 `if/else`：

```c
if (ns_capable_setid(old->user_ns, CAP_SETUID)) {
    new->suid = new->uid = kuid;      /* :631  特权：R 和 S 一起设 → 不可逆 */
    ...
}
new->fsuid = new->euid = kuid;        /* :641  两条路都只把 E 设成 u */
```

**这就是「临时降权必须用 `seteuid`」这句话的全部来源**（[9.4](./9.4-saved-id.md)）。

### 备注：9-5 里 `setuid()` 那一格的两种情形

严格说，`setuid()` 在 9-5 里的行为**取决于 capability 还在不在**：

| 情形 | `setuid(getuid())` 的结果 | 是挂起还是永久丢弃 |
|------|---------------------------|--------------------|
| **capability 还在**（典型 SUID-root 程序 exec 之后的常态） | `R=X E=X S=X` | **永久丢弃**（挂起/恢复做不到） |
| capability 已被丢掉（例如先调了 `setresuid(X,X,X)`，或跑了 `PR_SET_NO_NEW_PRIVS` 的路径） | `R=X E=X S=0` | **变成了挂起**（saved 保住 0，还能 `seteuid(0)` 回去） |

**同一个调用、同一个程序，语义随 capability 状态而变。** 这正是 [9.7.4 总表](./9.7-api.md#974-summary-of-calls-for-modifying-process-credentials)把 `setuid` 的「改哪些」写成「R+E+S **或** 只 E」的原因，也是安全代码里**不该用 `setuid()` 表达降权意图**的理由——**用 `setresuid(t, t, t)`，它的语义不随环境变。**

### 两题共同的一句话总结

| 目标 | 该用什么 | 为什么 |
|------|----------|--------|
| **临时**降权（还要升回来） | `seteuid(t)` / `setresuid(-1, t, -1)` | 只碰 EUID，saved 完好 |
| **永久**降权 | `setresuid(t, t, t)` | 显式钉死三个，语义与身份无关 |
| 想把 saved 换成某个特定值 | `setreuid(t, t)` 或 `setresuid(t, t, t)` | saved 的更新只在 `setreuid` 的两个条件下、或 `setresuid` 显式给值时发生 |

> 真机上验证这两题，用 [练习 9-1 的验证器](../code/ex9_1_id_state.c) 那个骨架改一下即可：`sudo chmod u+s` 之后，把 `snap()` 打印出来的 R/E/S/F 与上面的表逐格对——**答案对不对，四行输出就能证伪。**

<details>
<summary>1. 练习 9-1 的 (c) 与 (b) 结果只差 saved 一格，为什么？</summary>

因为 `seteuid` 只改 EUID，`setreuid` 的规则**宽得多**。

| 调用 | E | S | 机制 |
|------|---|---|------|
| `seteuid(2000)` | 2000 | **0**（不动） | `seteuid` 的定义就是「只改 effective」 |
| `setreuid(-1, 2000)` | 2000 | **2000**（被改） | `kernel/sys.c:575-577`：**euid 被设成 ≠ 旧 ruid** → `new->suid = new->euid` |

`setreuid(2)` DESCRIPTION：

> If the real user ID is set (i.e., `ruid` is not -1) **or the effective user ID is set to a value not equal to the previous real user ID**, the saved set-user-ID will be set to the new effective user ID.

本题 `ruid = -1`（没设 real），但 `euid = 2000 ≠ 旧 ruid(1000)` → 条件成立 → `saved = 2000`。

**这一格是整张表最有价值的地方**：它说明「把 euid 设成某个值」这件事，不同接口的**副作用范围不同**。安全代码里如果只想动 euid，**必须用 `seteuid`**，否则可能顺手把 saved 也改了（进而**改变进程未来能不能升权**）。
</details>

<details>
<summary>2. 练习 9-1 的 (d) 为什么 R/E/S 全不变？</summary>

因为 `setfsuid()` **只写 `new->fsuid`，不碰任何别的 ID**。

`kernel/sys.c:865` 的 `__sys_setfsuid()`：

```c
/* ex9_1_id_state.c —— 原书练习 9-1 的**可执行验证器**
 *
 * 原书练习 9-1（TLPI 9.9）：
 *   "假设进程的初始用户 ID 集合是 real=1000, effective=0, saved=0, file-system=0。
 *    在下列调用之后，这些 ID 分别是什么状态？
 *      (a) setuid(2000)
 *      (b) setreuid(-1, 2000)
 *      (c) seteuid(2000)
 *      (d) setfsuid(2000)
 *      (e) setresuid(-1, 2000, 3000)"
 *
 * 每一个小题都要**从同一个初始状态出发**，而一个进程的凭证改了就回不去，
 * 所以本程序一次只做一题（用 argv[1] 选 a..e），每题都要重启一个新进程。
 *
 * 怎么造出 R=1000 / E=0 / S=0 这个初始状态：
 *   正是「一个 set-user-ID-root 程序被 uid 1000 的用户执行」时的状态。
 *      gcc -O0 -Wall -Wextra -o ex9_1_id_state ex9_1_id_state.c
 *      sudo chown root ex9_1_id_state
 *      sudo chmod u+s ex9_1_id_state
 *      sudo -u '#1000' ./ex9_1_id_state a      # 依次 a..e
 *
 * 本程序会先**自检**初始状态；不符就明确说「这台机器上做不了这个实验」并给出上面的
 * 步骤，而不是把一个假的成功打印出来。
 *
 * 「期望值」一栏怎么来的（全部按 kernel/sys.c 的源码推，不是抄的）：
 *   特权分支 setuid()      : new->suid = new->uid = uid; 然后 new->fsuid = new->euid = uid
 *   特权分支 setreuid(r,e) : suid 在「r != -1 或 e != 旧 ruid」时被设为新 euid；
 *                            最后恒有 new->fsuid = new->euid
 *   setresuid(r,e,s)       : 三者各自独立改（-1 = 不改），最后 new->fsuid = new->euid
 *   setfsuid(u)            : 只改 fsuid，不动 R/E/S
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex9_1_id_state ex9_1_id_state.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/fsuid.h>
#include <sys/types.h>
#include <unistd.h>

struct quad {
    unsigned r, e, s, f;
};

static struct quad snap(void)
{
    struct quad q;
    uid_t r, e, s;
    if (getresuid(&r, &e, &s) == -1) {
        perror("getresuid");
        exit(1);
    }
    q.r = (unsigned) r;
    q.e = (unsigned) e;
    q.s = (unsigned) s;
    q.f = (unsigned) setfsuid((uid_t) -1);
    return q;
}

static void print_quad(const char *tag, struct quad q)
{
    printf("  %-10s real=%-6u effective=%-6u saved=%-6u fs=%-6u\n",
           tag, q.r, q.e, q.s, q.f);
}

int main(int argc, char *argv[])
{
    if (argc != 2 || strchr("abcde", argv[1][0]) == NULL || argv[1][1] != '\0') {
        fprintf(stderr, "用法: %s <a|b|c|d|e>\n", argv[0]);
        return 2;
    }
    char which = argv[1][0];

    printf("=== 初始状态自检 ===\n");
    struct quad q0 = snap();
    print_quad("实测", q0);
    printf("  期望  real=1000   effective=0      saved=0      fs=0\n");
    if (!(q0.r != 0 && q0.e == 0 && q0.s == 0)) {
        printf("\n  ✗ 初始状态不符 —— 本环境做不了这个实验。\n");
        printf("    它需要「一个 set-user-ID-root 程序被 uid 1000 的用户执行」。\n");
        printf("    在容器里做不到，因为容器只映射了 1 个 uid，chown 不出 root 属主：\n");
        printf("      cat /proc/self/uid_map      # 只有一行 \"0 <host> 1\"\n");
        printf("    真机上照上面注释里的四条命令做即可。\n");
        printf("    本题的答案（按 kernel/sys.c 推导）见 note 9.9 的答案表。\n");
        return 0;                    /* 不是程序出错，是环境不具备 */
    }

    printf("\n=== 执行 (%c) ===\n", which);
    errno = 0;
    int rc = 0;
    switch (which) {
    case 'a': rc = setuid((uid_t) 2000);                    break;
    case 'b': rc = setreuid((uid_t) -1, (uid_t) 2000);      break;
    case 'c': rc = seteuid((uid_t) 2000);                   break;
    case 'd': rc = setfsuid((uid_t) 2000);                  break;
    case 'e': rc = setresuid((uid_t) -1, (uid_t) 2000, (uid_t) 3000); break;
    }
    printf("  返回值 %d   errno=%d (%s)\n", rc, errno, errno ? strerror(errno) : "未置位");

    struct quad q1 = snap();
    print_quad("结果", q1);

    /* 期望值表（练习 9-1 的答案） */
    struct quad want;
    const char *why;
    switch (which) {
    case 'a':
        want = (struct quad) { 2000, 2000, 2000, 2000 };
        why = "有 CAP_SETUID -> suid 与 uid 一起设；fsuid 跟随 euid";
        break;
    case 'b':
        want = (struct quad) { 1000, 2000, 2000, 2000 };
        why = "ruid=-1 不动；euid 改了且 != 旧 ruid -> suid 也设成新 euid";
        break;
    case 'c':
        want = (struct quad) { 1000, 2000, 0, 2000 };
        why = "seteuid 只改 euid；suid 保持 0；fsuid 跟随 euid";
        break;
    case 'd':
        want = (struct quad) { 1000, 0, 0, 2000 };
        why = "setfsuid 只改 fsuid，R/E/S 一点不动";
        break;
    default:
        want = (struct quad) { 1000, 2000, 3000, 2000 };
        why = "三者各自生效；fsuid 跟随 euid";
        break;
    }
    print_quad("期望", want);
    printf("  依据: %s\n", why);
    printf("  一致? %s\n",
           (q1.r == want.r && q1.e == want.e && q1.s == want.s && q1.f == want.f)
               ? "是" : "**否** —— 若初值自检通过而这里不一致，说明内核行为与推导不符");
    return 0;
}
```

对比 `setresuid()` 的最后一行 `:726` `new->fsuid = new->euid;` —— 那是**反向**的同步（euid 变了就带着 fsuid 走）。

所以关系是**单向的**：

| 调用 | 方向 |
|------|------|
| `setuid` / `seteuid` / `setreuid` / `setresuid` | euid 变 → **fsuid 跟着变** |
| `setfsuid` | **只 fsuid 变**，euid 不动 |

这也解释了为什么 (d) 是唯一「euid 保持 0」的一题——**它是唯一不经过 euid 这条同步链的调用**。

注意前提：`setfsuid(2000)` 能成功，是因为进程**有 `CAP_SETUID`**（初始 euid=0 的特权进程）。非特权进程想设成 2000，必须先让 `2000 ∈ {ruid, euid, suid, fsuid}`——本容器里这四个都是 0，所以会**静默失败**（[9.5](./9.5-fs-uid-gid.md) 实测）。
</details>

<details>
<summary>3. 练习 9-4 里为什么 <code>setuid</code> / <code>seteuid</code> 做不到「永久丢弃」？</summary>

因为它们**都不碰 saved**（在非特权进程上）。

| 调用 | `new->suid` 会变吗 |
|------|---------------------|
| `setuid(u)`（非特权，`kernel/sys.c:637-641`） | ❌ 代码里根本没有给 `new->suid` 赋值的语句 |
| `seteuid(e)` | ❌ 语义就是「只改 EUID」 |
| `setreuid(r, e)` | ✅ 当 `ruid != -1` 或 `euid != 旧 ruid` 时（`:575-577`） |
| `setresuid(r, e, s)` | ✅ 当 `suid != -1` 时（`:724-725`） |

而「永久丢弃」的定义是 **`saved ← X`**（题目原文："ensure that the effective user ID and the saved set-user-ID are set to the value of the real user ID"）。saved 动不了，这个目标就达不到。

**推论（本练习最重要的产物）**：

> **`setuid()` 和 `seteuid()` 只能用于「临时」降权场景，`setreuid()` / `setresuid()` 才是「永久」降权的工具。**

这条正好和 [9.4](./9.4-saved-id.md) 的安全建议对上：**永久降权写 `setresuid(t, t, t)`。**
</details>

<details>
<summary>4. 练习 9-5 里 <code>setuid(getuid())</code> 是挂起还是永久丢弃？</summary>

**默认是永久丢弃**，但如果 capability 已经丢了，它会退化成挂起。

| capability 状态 | `setuid(getuid())` 结果 | 性质 |
|-----------------|-------------------------|------|
| **有 `CAP_SETUID`**（SUID-root 程序 exec 后的常态） | `R=X E=X S=X` | **永久丢弃** |
| 无 capability | `R=X E=X S=0` | **挂起**（saved 保住 0） |

依据是 `kernel/sys.c:630-641` 的 `if/else`：

```c
if (ns_capable_setid(old->user_ns, CAP_SETUID)) {
    new->suid = new->uid = kuid;               /* 特权分支：R、S 一起设 */
    ...
}
new->fsuid = new->euid = kuid;                 /* 两条路都设 E */
```

**「同一个调用、语义随 capability 变」这件事本身就是结论**：安全代码里不要用 `setuid()` 表达降权意图。改用 `setresuid(t, t, t)` —— 它要么成功、要么报错，**不存在「成功但意思不一样」的中间态**。

⚠️ 顺带说明：网上若看到「9-5 的 `setuid` 连永久丢弃都做不到」，那是错的。特权进程下 `setuid(getuid())` **正是**那个「R=E=S=X」的动作。真正做不到的是**挂起/恢复**（因为 saved 被一起砸了，没有 0 可以回去）。
</details>

<details>
<summary>5. 练习 9-3 里为什么必须用 <code>fgetgrent()</code> 而不是 <code>getgrent()</code>？</summary>

因为 **`getgrent()` 读的路径是编译期写死的**，`fgetgrent()` 才允许你指定文件。

glibc 里 `getpwnam` / `getgrnam` / `getgrent` 这一族走 NSS，后端文件路径由 `nsswitch.conf` 决定（默认 `/etc/group`）；它们的**路径不可参数化**（[Ch8 §8.4](../../chapter-08-users-and-groups/notes/8.4-retrieving-info.md)：`#define DATAFILE "/etc/" DATABASE`）。`fgetgrent(FILE *)` 是**唯一能读任意组文件的正规入口**。

本题的实际需要：

| 场景 | 用哪个 |
|------|--------|
| 读系统的组库 | `getgrent()` 或 `initgroups()` |
| **读自己造的文件 / 测试数据** | **`fgetgrent()`** |

本节实测就是这条差别的活证据：`ex9_3` 用 `fgetgrent()` 扫合成的 `/tmp/ex9_3_group`，**命中 3 个组**；而同一时刻 glibc 的 `getgrouplist()` 扫系统 NSS 库，**只拿到 `basegid` 一个**（`errno=2 ENOENT`，因为容器里既没有 `/etc/group` 也没有 `nsswitch.conf`）。

**「同一套算法、不同的数据源、结果完全不同」** —— 这也是为什么测试代码读组库时不该依赖系统文件，而应该自己造一份再 `fgetgrent()`。

⚠️ 还有一条 `struct group` 的细节：`gr_mem` 是 **`NULL` 结尾的字符串数组**，**空组的 `gr_mem[0] == NULL`**。本节实现里那两层判断（`gr_mem == NULL` 与 `gr_mem[0] == NULL`）**都要有**，否则遇到空组会段错误或漏计数（[Ch8 §8.3](../../chapter-08-users-and-groups/notes/8.3-group-file.md)）。
</details>
