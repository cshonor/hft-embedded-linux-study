## 本节讲什么

EUID/EGID 是**权限检查**用的那一对 ID。本节要钉死三件事：

1. **「特权进程」的判据是 EUID 还是 RUID？** —— 是 EUID，且更严格地说 Linux 上是 capability。
2. **`setuid()` 在非特权进程上到底是「改 EUID」还是「失败」？** —— 要看 uid 落在哪个集合里，返回码有 EINVAL / EPERM / 0 三种。
3. **为什么 `setuid(10240)` 在容器里是 EINVAL 而不是 EPERM？** —— 内核的检查顺序决定的，这条顺序解释了一整类「看起来像越权，其实是没映射」的怪现象。

## 要点

### 一、EUID 是「工牌」：权限检查看它，不看 RUID

`credentials(7)` 对 Effective ID 的两句：

> These IDs are used by the kernel to determine the **permissions** that the process will have when accessing **shared resources such as message queues, shared memory, and semaphores**.
>
> **On most UNIX systems, these IDs also determine the permissions when accessing files. However, Linux uses the filesystem IDs described below for this task.**

所以准确的表述是：

| 检查对象 | 用哪个 ID |
|----------|-----------|
| 消息队列 / 共享内存 / 信号量（System V IPC） | **EUID / EGID**（+ 补充组） |
| 文件（Linux） | **fsuid / fsgid**（+ 补充组）——[9.5](./9.5-fs-uid-gid.md) |
| 发信号 | RUID **或** EUID（`kill(2)` 的规则） |
| 设置调度参数 / nice / CPU 亲和 | 看 capability |
| 「是不是特权进程」 | **EUID == 0**（TLPI 书里的判据）；**内核实际判的是 capability** |

> 📌 **TLPI 的「privileged process = EUID 为 0」是一个 2005 年的简化判据。** 现代内核把 root 的权限拆成了 capability，所以 `setuid(2)` 的 DESCRIPTION 自己是这么写的：
>
> > If the calling process is privileged (**more precisely: if the process has the CAP_SETUID capability in its user namespace**), the real UID and saved set-user-ID are also set.
>
> 这两句的差别在本节的实测里是**看得见**的：本进程 `euid=0`（按 TLPI 判据是特权的），但 `CapEff=0`（按内核判据不是特权的），于是一切「改自己」的调用都成功、「改别人」的调用全部失败——**两种判据给出的预测不同，实测站在内核那边**。

### 二、`setuid()` 的三个返回码分支

`setuid(2)` DESCRIPTION 原文（SysV + SAVED_IDS 语义）：

> `setuid()` sets the **effective** user ID of the calling process. If the calling process is privileged …, the **real UID and saved set-user-ID are also set**.
>
> Under Linux, `setuid()` is implemented like the POSIX version with the `_POSIX_SAVED_IDS` feature. …
>
> Thus, a set-user-ID-root program wishing to temporarily drop root privileges, assume the identity of an unprivileged user, and then regain root privileges afterward **cannot use `setuid()`**. You can accomplish this with `seteuid(2)`.

配合内核 `kernel/sys.c:612` 的 `__sys_setuid()`，一个 `setuid(u)` 实际会落进哪个分支，取决于 **`u` 落在哪个集合里**：

```c
kuid = make_kuid(ns, uid);            /* :620 */
if (!uid_valid(kuid))
    return -EINVAL;                   /* :621-622  ← 分支 A */
...
if (ns_capable_setid(old->user_ns, CAP_SETUID)) {
    new->suid = new->uid = kuid;      /* :631      ← 分支 B：真特权 */
    ...
} else if (!uid_eq(kuid, old->uid) && !uid_eq(kuid, new->suid)) {
    goto error;                       /* :637-638  → retval = -EPERM，分支 C */
}
new->fsuid = new->euid = kuid;        /* :641 */
```

| 分支 | 触发条件 | 结果 | 实测（本节） |
|------|----------|------|--------------|
| **A** | `make_kuid()` 拿不到合法 kuid：**uid 在本 user namespace 里没有映射** | `-EINVAL`(22) | `setuid(10240)` → `-1 / 22` |
| **B** | 有 `CAP_SETUID` | **R + E + S 全设为 u** | 本环境做不到（无 capability） |
| **C** | 无 capability，且 `u` **既不是 RUID 也不是 SUID** | `-EPERM`(1) | 本环境被 A 先拦住，看不到 |
| **成功** | 无 capability，但 `u` **等于 RUID 或 SUID**（含「就是现在的值」这种 no-op） | `0`，只改 EUID（和 fsuid） | `setuid(getuid())` → `0` |

**关键的一条：`uid_valid()` 的检查（A）排在 capability 检查（B）之前。** 这就是为什么容器里得到的是 EINVAL 而不是 EPERM——内核还没走到「你有没有权限」那一步，就已经判定「这个 uid 在本 ns 里根本不存在」。

### 三、为什么「`setuid(getuid())` 成功」不代表「我有特权」

本节实测里 `setuid(getuid())` 返回 `0`——而本进程 `CapEff=0`，一个 capability 都没有。这条最容易被误读成「我是特权进程」。

真实原因：把 uid 设成**它当前已经是**的值，是一个 **no-op**；内核根本不需要改动 `struct cred`，自然也不需要 capability。`kernel/sys.c:612` 的路径是：

| 判定点 | 取值 | 结果 |
|--------|------|------|
| `make_kuid(0)` | 合法（0 有映射） | 通过 |
| `ns_capable_setid(...)` | 假 | 走 `else if` 分支 |
| `!uid_eq(kuid, old->uid)` | 假（就是自己） | 整个条件为假，**不掉进 `error`** |
| `new->fsuid = new->euid = kuid;` | — | 执行了，但写回的是**同样的值** |

`setresuid()` 更是把这件事写成了**显式的短路**（`kernel/sys.c:693-698`）：

```c
/* check for no-op */
if ((ruid == (uid_t) -1 || uid_eq(kruid, old->uid)) &&
    (euid == (uid_t) -1 || (uid_eq(keuid, old->euid) &&
                            uid_eq(keuid, old->fsuid))) &&
    (suid == (uid_t) -1 || uid_eq(ksuid, old->suid)))
    return 0;
```

——三个参数全落在现有集合里，**直接 `return 0`**，连 `prepare_creds()` 都不调。

### 四、`-1` 是「不改这一项」的哨兵值

`setresuid(2)` / `setreuid(2)` DESCRIPTION：

> **If one of the arguments equals -1, the corresponding value is not changed.**

注意 `-1` 在 `uid_t`（无符号）里是 `0xFFFFFFFF`（64 位 `uid_t` 下打印成 `4294967295`），**不是**一个「无效 uid」。内核的写法是把这个比较**放在最前面**：

```c
if ((ruid != (uid_t) -1) && !uid_valid(kruid))   /* :682 */
    return -EINVAL;
```

所以 `setreuid(-1, -1)` / `setresuid(-1, -1, -1)` 都是彻底的 no-op，返回 `0`——本节实测两行都印证了这一点。

### 五、EUID 什么时候会 ≠ RUID？

| 场景 | RUID | EUID | 说明 |
|------|------|------|------|
| 普通程序 | `u` | `u` | 相等 |
| **set-user-ID 程序**（`chmod u+s`，属主 root） | 启动者 `u` | **0** | exec 时被改，[9.3](./9.3-set-user-id.md) |
| `seteuid(t)` 之后 | 不变 | `t` | **只有 EUID 变**，[9.4](./9.4-saved-id.md) |
| `setuid(t)` 由特权进程调用 | `t` | `t` | R+E+S 全设，**不可逆** |
| 登录 shell | 登录用户 | 登录用户 | 相等 |

所以 EUID ≠ RUID **本身就是「正在扮演别人」的信号**。`/usr/bin/passwd` 是教科书例子：

```bash
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 59976 ... /usr/bin/passwd
$ stat -c '%A %U' /usr/bin/passwd
-rwsr-xr-x root
```

`s` 就是 set-user-ID 位：普通用户执行时 `RUID=自己 / EUID=0`，于是能写 `/etc/shadow`（Ch8 的那个 0644 文件），而程序退出后身份就还回去了。

## 代码

### c9_4 `set*id` 家族返回码实测：把「按规则应当」和「实测」并排

规则可以背，但**返回码必须实测**。[`../code/c9_4_setid_probe.c`](../code/c9_4_setid_probe.c) 对 uid 与 gid 两个家族各试三类参数：

| 参数类 | 按规则应当 | 为什么 |
|--------|-----------|--------|
| 设成「自己」 | `0` | 落在 `{ruid, euid, suid, fsuid}` 集合内 → no-op，不需要 capability |
| `-1` 形式 | `0` | `-1` = 不改这一项 |
| 未映射的 uid/gid（`10240`） | `EINVAL(22)` | `make_kuid()` 失败，**连通配检查都不做** |

```c
/* c9_4_setid_probe.c —— 把「按规则应该怎样」和「实测返回什么」并排放
 *
 * 9.2 / 9.3 / 9.4 / 9.7 的规则可以用文字背，但**返回码**必须实测。
 * 本程序对 8 个 set*id 接口各试三类参数：
 *   (a) 设成「自己」         -> 应当成功（ps: 这是特例，见下）
 *   (b) -1 形式（不改动）    -> 应当成功，且什么都不变
 *   (c) 未映射的 uid/gid     -> 应当 EINVAL（若内核版本/命名空间如此）
 *
 * 为什么 (a) 会成功：内核**不是**先看「有没有 CAP_SETUID」，而是先看目标值
 * 是否落在 {ruid, euid, suid, fsuid} 里（kernel/sys.c:883 等）。设成自己必然在集合内，
 * 所以不需要任何 capability。这解释了「uid=0 但 CapEff=0」的进程为什么还能调
 * setuid(0) 成功 —— 它其实什么都没做。
 *
 * 权威依据：
 *   - setuid(2) ERRORS EINVAL: "The user ID specified in uid is not valid in this
 *     user namespace."（描述），内核对应 kernel/sys.c:620 make_kuid + :621 uid_valid。
 *   - setresuid(2) DESCRIPTION：非特权进程只能在各 ID 之间互相设；
 *     "If one of the arguments equals -1, the corresponding value is not changed."
 *   - setreuid(2) DESCRIPTION：-1 表示不改；suid 的更新规则。
 *   - kernel/sys.c:612 __sys_setuid()、:669 __sys_setresuid()、:531 __sys_setreuid()。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_4_setid_probe c9_4_setid_probe.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>

#define UNMAPPED 10240u

#define TRY(expr, rule)                                                       \
    do {                                                                      \
        errno = 0;                                                            \
        int rc_ = (int) (expr);                                               \
        int e_ = errno;                                                       \
        printf("  %-32s | %-30s | %4d | %2d %-16s\n",                         \
               #expr, rule, rc_, e_, e_ ? strerror(e_) : "-");                \
    } while (0)

static int same_as_before(void)
{
    uid_t a, b, c;
    if (getresuid(&a, &b, &c) == -1)
        return -1;
    return (a == 0 && b == 0 && c == 0) ? 1 : 0;
}

int main(void)
{
    uid_t ru, eu, su;
    gid_t rg, eg, sg;
    getresuid(&ru, &eu, &su);
    getresgid(&rg, &eg, &sg);

    printf("环境: uid=%u/%u/%u  gid=%u/%u/%u\n",
           (unsigned) ru, (unsigned) eu, (unsigned) su,
           (unsigned) rg, (unsigned) eg, (unsigned) sg);

    printf("\n=== uid 家族 ===\n");
    printf("  %-32s | %-30s | %4s | %s\n", "调用", "按规则应当", "ret", "errno");
    printf("  ---------------------------------+--------------------------------+------+------------------\n");
    TRY(setuid(getuid()),            "自己在集合内 -> 0");
    TRY(setreuid((uid_t) -1, (uid_t) -1), "-1 = 不改 -> 0");
    TRY(setresuid((uid_t) -1, (uid_t) -1, (uid_t) -1), "-1 = 不改 -> 0");
    TRY(setresuid(getuid(), getuid(), getuid()), "自己在集合内 -> 0");
    TRY(setuid((uid_t) UNMAPPED),    "未映射 -> EINVAL(22)");
    TRY(seteuid((uid_t) UNMAPPED),   "未映射 -> EINVAL(22)");
    TRY(setreuid((uid_t) UNMAPPED, (uid_t) UNMAPPED), "未映射 -> EINVAL(22)");
    TRY(setresuid((uid_t) UNMAPPED, (uid_t) UNMAPPED, (uid_t) UNMAPPED),
        "未映射 -> EINVAL(22)");

    printf("\n=== gid 家族 ===\n");
    printf("  %-32s | %-30s | %4s | %s\n", "调用", "按规则应当", "ret", "errno");
    printf("  ---------------------------------+--------------------------------+------+------------------\n");
    TRY(setgid(getgid()),            "自己在集合内 -> 0");
    TRY(setregid((gid_t) -1, (gid_t) -1), "-1 = 不改 -> 0");
    TRY(setresgid((gid_t) -1, (gid_t) -1, (gid_t) -1), "-1 = 不改 -> 0");
    TRY(setgid((gid_t) UNMAPPED),    "未映射 -> EINVAL(22)");
    TRY(setegid((gid_t) UNMAPPED),   "未映射 -> EINVAL(22)");
    TRY(setregid((gid_t) UNMAPPED, (gid_t) UNMAPPED), "未映射 -> EINVAL(22)");
    TRY(setresgid((gid_t) UNMAPPED, (gid_t) UNMAPPED, (gid_t) UNMAPPED),
        "未映射 -> EINVAL(22)");

    printf("\n=== 试完一圈，身份变了没有？ ===\n");
    uid_t a, b, c;
    gid_t x, y, z;
    getresuid(&a, &b, &c);
    getresgid(&x, &y, &z);
    printf("  现在 uid=%u/%u/%u   gid=%u/%u/%u\n",
           (unsigned) a, (unsigned) b, (unsigned) c,
           (unsigned) x, (unsigned) y, (unsigned) z);
    printf("  与开始时相同? %s\n", same_as_before() == 1 ? "是（所有调用要么是 no-op，要么被 EINVAL 挡下）" : "否");

    printf("\n=== 为什么「未映射」是 EINVAL 而不是 EPERM ===\n");
    printf("  内核先做 make_kuid(ns, uid) -> 拿不到合法 kuid 时**连通配检查都不做**，\n");
    printf("  直接 -EINVAL（kernel/sys.c:620-622）。EPERM 才是「uid 合法但不许改」。\n");
    printf("  这条区分只在有 user namespace 的环境里才看得到：\n");
    printf("  普通系统上所有 uid 都有映射，setuid(10240) 得到的是 EPERM。\n");
    return 0;
}
```

编译与运行：

```bash

```

**解读**

1. **`setuid(getuid())` 返回 0 —— 这条最容易被读成「我是特权进程」，其实不是。** 它只是 no-op：目标 uid 就是当前 uid，内核不需要改 `cred`。把这一行和紧接着的 `setuid(UNMAPPED) -> -1/22` 并排看，就能体会出内核的判定顺序是「**这个值合法吗**」→「**你有权限改吗**」，而不是反过来。
2. **`-1` 两行都返回 0**，证明 `-1` 是**哨兵值**（"the corresponding value is not changed"），不是「无效 uid」。注意 gid 家族的 `setegid` 那一行本程序没测，因为 `setegid(-1, -1)` 这种双参数形式不存在（那是 `setregid`）。
3. **`EINVAL(22)` 铺满整个「未映射」区**，8 条 UID 调用里 4 条、7 条 GID 调用里 4 条。原因是同一个：`make_kuid()` 拿不到合法 kuid，内核**在 capability 检查之前**就返回了。`setuid(2)` ERRORS 的 EINVAL 条写的就是这件事："The user ID specified in `uid` is not valid in this user namespace."
4. **「身份变了没有」这一栏是本程序最该记住的部分**：跑完 15 条调用，`uid=0/0/0` 与开始时**完全相同**。这印证了一句实践法则——**在容器里，`set*id` 的返回值并不代表它做了什么**。真要知道身份有没有变，必须**回读**（`getresuid()` 或 `/proc/self/status`），不能只信返回值。
5. **普通系统上这一栏会不一样。** 在真机上所有 uid 都有映射，`setuid(10240)` 会走 capability 检查，得到的是 `EPERM(1)`。所以**同一条代码在容器里报 22、在真机上报 1** —— 排查跨环境问题时这个差别很值钱。

| Linux `kernel/sys.c:612` | `__sys_setuid()`；`:620` `make_kuid`；`:621-622` `!uid_valid -> -EINVAL`；`:630` `ns_capable_setid(..., CAP_SETUID)`；`:637-638` `goto error`（→ `-EPERM`）；`:641` `new->fsuid = new->euid = kuid` |
| Linux `kernel/sys.c:669` | `__sys_setresuid()`；`:682-689` 三个 `uid_valid` → EINVAL；`:693-698` **no-op 短路 `return 0`**；`:706-708` 只有真引入新值才要 `CAP_SETUID`；`:726` `new->fsuid = new->euid` |
| Linux `kernel/sys.c:531` | `__sys_setreuid()`；`:542/544` EINVAL；`:553-568` ruid/euid 各自的放行集合；`:575-577` suid 更新规则；`:578` `new->fsuid = new->euid` |

## HFT / 嵌入式关联

- **「降权」不能只改 EUID，但「降全程」必须改 R+E+S。** 交易进程启动阶段要绑低端口 / `mlockall`，这些靠的是 capability；进主循环前要**永久**丢掉它们。用 `seteuid()` 只是换工牌，`CAP_SETUID` 还在手里，被攻破后照样能换回去——真正的做法是 `setresuid(t, t, t)` 或 `setuid(t)`（[9.4](./9.4-saved-id.md)）。
- **`return 0` 不等于「身份变了」。** `setuid(getuid())` 这种 no-op 会返回 0 却什么都不做。安全敏感的代码里，降权之后**必须回读验证**（`getresuid()` ＋ `CapEff`），否则会留下「以为降了其实没降」的窗口。本节实测的「身份变了没有 → 是（相同）」就是这个道理的反面教材。
- **容器 / 嵌入式沙箱里 EINVAL 比 EPERM 常见。** 见到 `setuid() -> EINVAL` 先去看 `/proc/self/uid_map`，不要一头扎进 capability 排查。跨容器 / 跨 ns 的部署脚本尤其要注意：**同一条 `setuid` 调用，宿主上返回 1、容器里返回 22**。
- **嵌入式上 `set*id` 的 libc 差异。** musl 的 `setuid()` 语义与 glibc 一致（都走 POSIX SysV + SAVED_IDS），但 `setresuid` 的 unprivileged 规则在极老的 uClibc 上有过不同实现。**跨 libc 的代码只依赖 man 写下的契约**（返回值 / errno / 是不是 no-op），不要依赖实测到的具体 errno 数值。
- **`CAP_SETUID` 与 `CAP_SETGID` 是两把独立的钥匙。** 只给了 `CAP_SETGID` 的交易进程可以换组但不能换用户；`setgroups()` 还需要额外过第二道闸门（`userns_may_setgroups()`，[9.6](./9.6-supplementary-groups.md)）。

## 自测题

<details>
<summary>1. 怎么判断一个进程是不是「特权进程」？TLPI 的判据和现代内核的判据一样吗？</summary>

**不一样。**

- **TLPI 的判据**：`effective user ID == 0`。
- **现代内核的判据**：`capabilities(7)` 里的具体 capability。`setuid(2)` 自己写的是 "if the process has the **`CAP_SETUID` capability** in its user namespace"。

两者在传统系统上等价（euid=0 → 全套 capability），但在容器 / 被 `capsh --drop` 过的进程 / 开了 `NoNewPrivileges` 的服务上**不等价**。

本节实测证据：进程 `uid=0 euid=0`（按 TLPI 判据是特权的），但 `CapEff=0000000000000000`（按内核判据不是）。实测结果是内核那一边说了算——所有「改自己」的调用成功（那是 no-op），所有「改别人」的调用失败。

所以工程上的正确写法是：**别用 `geteuid() == 0` 判断权限**，用 `capget()` 或直接试一次操作看 errno。
</details>

<details>
<summary>2. <code>setuid(getuid())</code> 返回 0，是不是说明这个进程有特权？</summary>

**不是。它是个 no-op。**

把 uid 设成它**已经是**的值，不需要改动 `struct cred`，因此内核根本不需要检查 capability。

`kernel/sys.c:612` 的 `__sys_setuid()` 路径：

```c
if (ns_capable_setid(old->user_ns, CAP_SETUID)) {
    new->suid = new->uid = kuid;        /* 有 capability 的路径 */
} else if (!uid_eq(kuid, old->uid) && !uid_eq(kuid, new->suid)) {
    goto error;                          /* → EPERM */
}
new->fsuid = new->euid = kuid;
```

当 `uid == 当前 uid` 时，`else if` 的第一个条件 `!uid_eq(...)` 就是**假**，于是整个条件为假，不掉进 `error`。

`setresuid()` 更直白，`kernel/sys.c:693-698` 有显式的 `/* check for no-op */`，三个参数都在现有集合里就 `return 0`。

本节实测：`setuid(getuid())` → `0`，而同一进程 `setuid(10240)` → `-1/22`。**同一个进程，一个成功一个失败，「有没有特权」这个解释解释不了**，只有「是不是 no-op」解释得了。
</details>

<details>
<summary>3. 为什么容器里 <code>setuid(10240)</code> 是 EINVAL，真机上却是 EPERM？</summary>

**因为内核的检查顺序：先 `uid_valid()`，再 capability。**

`kernel/sys.c:620-622`：

```c
kuid = make_kuid(ns, uid);
if (!uid_valid(kuid))
    return -EINVAL;          /* ← 先走这里 */
```

再看 capability（`:630`）。所以：

| 环境 | `make_kuid(10240)` | 结果 |
|------|--------------------|------|
| 容器（`uid_map` 只有 `0 113 1` 一行） | 拿不到合法 kuid | **EINVAL(22)** |
| 真机（10240 有映射，或无所谓因为 UID 空间完整） | 合法 | 继续走，最终 **EPERM(1)** |

`setuid(2)` ERRORS 对这两条的定义本来就不一样：

- `EINVAL` — "The user ID specified in `uid` is not valid in **this user namespace**."
- `EPERM` — "The user is not privileged … and `uid` does not match the real UID or saved set-user-ID of the calling process."

**实操建议**：写降权代码时同时处理 1 和 22，并且打印 `/proc/self/uid_map` 一起判断。见到 22 就说明「换环境」而不是「改代码」能解决。
</details>

<details>
<summary>4. <code>setreuid(-1, -1)</code> 做了什么？<code>-1</code> 为什么不是「无效 uid」？</summary>

**什么都没做，返回 0。**

`setreuid(2)` DESCRIPTION："Supplying a value of `-1` for either the real or effective user ID **forces the system to leave that ID unchanged**."

`-1` 在 `uid_t` 里就是全 1（`0xFFFFFFFF`），它是一个约定的**哨兵值**，表示「这一项别动」。内核把它写成**最前面的短路比较**：

```c
if ((ruid != (uid_t) -1) && !uid_valid(kruid))   /* kernel/sys.c:542 */
    return -EINVAL;
```

——因为 `ruid == (uid_t) -1`，整个条件直接为假，连 `make_kuid()` 的结果都不看。

本节实测两行：

```text
  setreuid((uid_t) -1, (uid_t) -1) | -1 = 不改 -> 0               |    0 |  0 -
  setresuid((uid_t) -1, (uid_t) -1, (uid_t) -1) | -1 = 不改 -> 0               |    0 |  0 -
```

注意 `printf("%u", (uid_t)-1)` 会打印 `4294967295`，别被这个数字吓到——它不代表一个真实用户。
</details>

<details>
<summary>5. <code>ls -l</code> 里 <code>-rwsr-xr-x</code> 的那个 <code>s</code> 意味着运行时 RUID 和 EUID 有什么关系？</summary>

`RUID = 执行者`，`EUID = 文件属主`。

`execve(2)`："If the set-user-ID bit is set on the program file … then the **effective user ID** of the calling process is changed to that of the **owner of the program file**."，同时 "The process's real UID … **unchanged** by a call to `execve()`."

所以 `/usr/bin/passwd`（`-rwsr-xr-x root root`）被普通用户执行时：

| ID | 值 |
|----|----|
| RUID | 执行者的 uid（比如 1000） |
| EUID | **0**（文件属主 root） |
| SUID | 0（exec 时从新 EUID 拷来，[9.4](./9.4-saved-id.md)） |

于是它能写 `/etc/shadow`（Ch8 实测是 `0644`，只有 root 能写），而程序内部靠 RUID 知道「是谁在改口令」。

⚠️ 这个 `s` 位**不是永远生效**：[9.3](./9.3-set-user-id.md) 会给出四条让它被无视的路径（nosuid 挂载 / `no_new_privs` / 没有这一位 / **属主在 ns 里没映射**）。本容器里 `NoNewPrivs=1`，所以镜像里唯一那个 SUID 文件 `execve` 之后**权限一点没提**——实测过。
</details>
