## 本节讲什么

9.3 说 exec 之后 `saved ← euid`。**那 saved 到底是为什么存在的？**

答案只有一句：**为了让 set-user-ID 程序能「降下去干活、再升回来」**。没有 saved，一个特权程序一旦降权就永远回不去，只能把整个特权阶段一口气做完——那既不安全也不实用。

本节要钉死三件事：

1. saved 的**唯一来源**是 exec 时的 euid 拷贝（以及特权 `setuid`/`setreuid`/`setresuid` 的显式赋值）；
2. 「**临时降权**」与「**永久降权**」的区别落在**哪些 ID 被改**上，而不是落在调用了哪个函数名上；
3. 为什么 `setuid()` 不能用来做临时降权——内核源码里有一段注释把话说得很直白。

## 要点

### 一、saved 是什么，以及它为什么存在

`credentials(7)` 原文：

> **Saved set-user-ID and saved set-group-ID.** These IDs are used in set-user-ID and set-group-ID programs **to save a copy of the corresponding effective IDs that were set when the program was executed** (see `execve(2)`). **A set-user-ID program can assume and drop privileges by switching its effective user ID back and forth between the values in its real user ID and saved set-user-ID.** This switching is done via calls to `seteuid(2)`, `setreuid(2)`, or `setresuid(2)`.

关键词是「**back and forth**」。saved 不是「另一个 real」，它是**一把备用钥匙**：只要 `euid` 能落在 `{ruid, suid}` 里，非特权进程就能在两者之间自由切换（`setresuid(2)` DESCRIPTION 明确非特权进程可以把 R/E/S **各**设成「当前的 R/E/S 之一」）。

`set-user-ID` → `seteuid` 的经典四拍：

| 阶段 | 调用 | RUID | EUID | SUID | 说明 |
|------|------|------|------|------|------|
| ① | `exec` 之后（SUID 程序刚起来） | 1000 | **0** | 0 | 全权限 |
| ② | `seteuid(getuid())` | 1000 | 1000 | 0 | 降权干活——**不可信输入必须在这一段处理** |
| ③ | `seteuid(0)` | 1000 | **0** | 0 | 靠 saved 升回去，做特权收尾 |
| ④ | `setuid(getuid())` | 1000 | 1000 | **1000** | 连 saved 一起砸，**回不去了** |

第 ④ 步之前的每一刻，进程都**还在能升回 root 的状态**。**安全上的分界线在第 ④ 步**，不在第 ② 步。

> 📌 这条对「SUID 程序该什么时候处理不可信输入」有直接指导：**必须在 ④ 之后处理**。在 ①②③ 阶段处理不可信输入，一旦触发漏洞就是 root 代码执行。

### 二、「临时降权」与「永久降权」的精确区别

不是看函数名，是看**改了哪些 ID**：

| 做法 | RUID | EUID | SUID | 能回切？ | 靠什么机制 |
|------|------|------|------|----------|-----------|
| `seteuid(t)` | 不变 | → `t` | **不变** | ✅ 能 | `t` 必须是 `{ruid, euid, suid}` 之一 |
| `setegid(t)` / `setregid` / `setresgid` | 同上（GID 版） | | | | |
| `setreuid(-1, t)` | 不变 | → `t` | **可能被改**（见下） | 取决于 suid | — |
| `setresuid(-1, t, -1)` | 不变 | → `t` | **不变** | ✅ 能 | `-1` = 该项不改 |
| `setuid(t)`（特权时） | → `t` | → `t` | → `t` | ❌ **不能** | `kernel/sys.c:631` |
| `setresuid(t, t, t)` | → `t` | → `t` | → `t` | ❌ **不能** | 三个都显式改 |

**`setreuid` 的 suid 规则比较绕**，`setreuid(2)` DESCRIPTION 原文：

> **If the real user ID is set (i.e., `ruid` is not -1) or the effective user ID is set to a value not equal to the previous real user ID, the saved set-user-ID will be set to the new effective user ID.**

内核里就是 `kernel/sys.c:575-577` 那三行：

```c
if (ruid != (uid_t) -1 ||
    (euid != (uid_t) -1 && !uid_eq(keuid, old->uid)))
    new->suid = new->euid;
```

所以「`setreuid(-1, t)` 会不会砸掉 saved」取决于 `t` 是不是等于**旧的 ruid**：等于则 saved 保住，不等于则 saved 变成 `t`。这是 [练习 9-1 (b)](./9.9-exercises.md) 那个答案（`saved` 从 0 变成 2000）的机制。

### 三、为什么 `setuid()` 做不了临时降权——内核注释原文

`setuid(2)` DESCRIPTION：

> Under Linux, `setuid()` is implemented like the POSIX version with the `_POSIX_SAVED_IDS` feature. This allows a set-user-ID (**other than root**) program to drop all of its user privileges, do some unprivileged work, and then reengage the original effective user ID in a secure manner.
>
> If the user is root or the program is set-user-ID-root, special care must be taken: `setuid()` checks the effective user ID of the caller and **if it is the superuser, all process-related user ID's are set to `uid`**. After this has occurred, **it is impossible for the program to regain root privileges**.
>
> Thus, a set-user-ID-root program wishing to temporarily drop root privileges … and then regain root privileges afterward **cannot use `setuid()`**. You can accomplish this with `seteuid(2)`.

内核文档把同一个意思写得更不客气，`kernel/sys.c:601-611` 的注释块（就在 `__sys_setuid()` 上面）：

```c
/*
 * setuid() is implemented like SysV with SAVED_IDS
 *
 * Note that SAVED_ID's is deficient in that a setuid root program
 * like sendmail, for example, cannot set its uid to be a normal
 * user and then switch back, because if you're root, setuid() sets
 * the saved uid too.  If you don't like this, blame the bright people
 * in the POSIX committee and/or USG.  Note that the BSD-style setreuid()
 * will allow a root program to temporarily drop privileges and be able to
 * regain them by swapping the real and effective uid.
 */
```

读法：**「setuid 只改 EUID」和「setuid 改 R+E+S」这两种语义不能同时要**。POSIX 选了「特权时全改」（这样「永久丢弃」才是一句话的事），代价是失去临时降权能力；BSD 的 `setreuid()` 走另一条路（交换 real/effective），能来回切。Linux 两个都提供。

### 四、`setuid()` 失败也要检查——哪怕你是 root

`setuid(2)` RETURN VALUE：

> Note: there are cases where **`setuid()` can fail even when the caller is UID 0**; **it is a grave security error to omit checking for a failure return from `setuid()`**.

（`setresuid(2)` / `setreuid(2)` 的 RETURN VALUE 里有同样的句子。）

后果是：如果调用了 `setuid()` 却没检查返回值，程序可能**以为自己已经降权，实际还是 root**——后面所有「降权后才处理不可信输入」的安全假设全部不成立。**降权后必须回读验证**，这不是洁癖，是 man 明确点名的高危缺陷。

### 五、`setresuid()` 是表达「永久降权」最清楚的形式

`setresuid(2)` DESCRIPTION：

> `setresuid()` sets the real user ID, the effective user ID, and the saved set-user-ID of the calling process.
>
> **If one of the arguments equals -1, the corresponding value is not changed.**
>
> **Regardless of what changes are made … the filesystem UID is always set to the same value as the (possibly new) effective UID.**

所以：

```c
setresuid(t, t, t);       /* 三个一起钉死 —— 「我要永久丢权」的最佳表达 */
setresuid(-1, t, -1);     /* 只改 EUID —— 等价于 seteuid(t)，但意图更显式 */
```

对照表的最后一行 `setresuid(t, t, t)` 比 `setuid(t)` 更好，因为**它不依赖「调用者是不是特权」这个前提**——`setuid(t)` 在非特权进程里只改 EUID（[9.2](./9.2-effective-uid-gid.md) 的分支表），而 `setresuid(t,t,t)` 在任何情况下都表达「三个都要是 t」，不满足就报 EPERM。**意图明确、失败可见**，这是安全代码里很重要的一点。

## 代码

### c9_5 临时降权 vs 永久降权（三种模式）

[`../code/c9_5_drop_privileges.c`](../code/c9_5_drop_privileges.c) 用 `show` / `temp` / `perm` 三种模式把上面那张表跑出来：

| 模式 | 干什么 | 期望 |
|------|--------|------|
| `show` | 只打印当前 R/E/S | — |
| `temp <uid>` | `seteuid(target)` 降权 → **再 `seteuid(getuid())` 回切** | 两次都成功，因为 saved 没被砸 |
| `perm <uid>` | `setuid(target)` 降权 → 再试 `setuid(0)` 回切 | 第二次**必须失败**，这就是「永久」 |

⚠️ **本程序在评测容器里跑不出降权效果**：目标 uid 没有映射，内核在 `make_kuid()` 阶段就以 EINVAL 挡掉了（[9.2](./9.2-effective-uid-gid.md)）。这不是程序写错，是环境物理上做不到。程序会**如实打印这个失败**，绝不编一个假的成功输出。

```c
/* c9_5_drop_privileges.c —— 临时降权 vs 永久降权
 *
 * 9.4 的主题：saved set-user-ID 的存在意义，就是让 set-user-ID 程序能
 * 「降下来干活、再升回去」。
 *
 *   临时降权：seteuid(t)          euid 变、ruid/suid 不变 -> 还能 seteuid(0) 回切
 *   永久降权：setuid(t)           ruid=euid=suid=t       -> 回不去了
 *             或 setresuid(t,t,t) 同上，而且更明确地表达「连 saved 也要砸掉」
 *
 * 为什么 setuid() 回不去：POSIX 的 setuid() 是 SysV 语义，**把 saved 也一起设**。
 * 在真正的 set-user-ID-root 程序里，一旦用 setuid() 降权，就再也拿不回 root。
 * 内核源码里那条注释把话说得很直白（kernel/sys.c:601-611）：
 *   "Note that SAVED_ID's is deficient in that a setuid root program like sendmail,
 *    for example, cannot set its uid to be a normal user and then switch back,
 *    because if you're root, setuid() sets the saved uid too."
 *
 * ⚠️ 本程序在评测容器里**跑不出降权效果** —— 容器只映射了 1 个 uid（见
 *    /proc/self/uid_map），内核在 make_kuid() 阶段就以 EINVAL 挡掉了。这不是程序
 *    写错，是环境物理上做不到。程序会如实打印这个失败，并把真机上的跑法印出来。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_5_drop_privileges c9_5_drop_privileges.c
 * 真机跑法（需要 root）:
 *   sudo useradd -m bob
 *   id bob                       # 拿到 bob 的 uid，假设是 1001
 *   sudo ./c9_5_drop_privileges temp 1001
 *   sudo ./c9_5_drop_privileges perm 1001
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>

static void print_ids(const char *tag)
{
    uid_t r, e, s;
    if (getresuid(&r, &e, &s) == -1) {
        perror("getresuid");
        return;
    }
    printf("    %-22s r=%u e=%u s=%u\n", tag, (unsigned) r, (unsigned) e, (unsigned) s);
}

static int do_temp(uid_t target)
{
    printf("\n--- 临时降权：seteuid(%u) ---\n", (unsigned) target);
    print_ids("降权前");
    errno = 0;
    if (seteuid(target) == -1) {
        printf("    seteuid(%u) 失败: errno=%d (%s)\n",
               (unsigned) target, errno, strerror(errno));
        return 1;
    }
    print_ids("降权后");
    printf("    → 用 ruid/suid 回切：seteuid(%u)\n", (unsigned) getuid());
    errno = 0;
    if (seteuid(getuid()) == -1) {
        printf("    seteuid 回切失败: errno=%d (%s)\n", errno, strerror(errno));
        return 1;
    }
    print_ids("回切后");
    printf("    可以回切，因为 saved(=suid) 没被砸掉。\n");
    return 0;
}

static int do_perm(uid_t target)
{
    printf("\n--- 永久降权：setuid(%u) ---\n", (unsigned) target);
    print_ids("降权前");
    errno = 0;
    if (setuid(target) == -1) {
        printf("    setuid(%u) 失败: errno=%d (%s)\n",
               (unsigned) target, errno, strerror(errno));
        return 1;
    }
    print_ids("降权后");
    printf("    → 试着用 setuid(0) 回切：\n");
    errno = 0;
    if (setuid(0) == -1)
        printf("    setuid(0) 失败: errno=%d (%s)  ← 回不去了，这就是「永久」\n",
               errno, strerror(errno));
    else {
        printf("    setuid(0) 成功了！\n");
        print_ids("回切后");
        printf("    ⚠️ 这里成功说明降权没有砸掉所有东西，不是安全写法。\n");
    }
    return 0;
}

int main(int argc, char *argv[])
{
    const char *mode = (argc > 1) ? argv[1] : "show";
    uid_t target = (argc > 2) ? (uid_t) strtoul(argv[2], NULL, 10) : (uid_t) 1000;

    print_ids("开始");

    if (strcmp(mode, "show") == 0) {
        printf("\n用法: %s <show|temp|perm> [目标uid]\n", argv[0]);
        printf("  show  只打印当前 R/E/S\n");
        printf("  temp  seteuid 降权再回切（需要 saved 还在）\n");
        printf("  perm  setuid  永久降权（连 saved 一起砸）\n");
        printf("\n本环境只能走 show：目标 uid 没有映射，set*id 会 EINVAL。\n");
        return 0;
    }
    if (strcmp(mode, "temp") == 0)
        return do_temp(target);
    if (strcmp(mode, "perm") == 0)
        return do_perm(target);

    printf("未知模式: %s\n", mode);
    return 2;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c9_5_drop_privileges c9_5_drop_privileges.c
./c9_5_drop_privileges show
./c9_5_drop_privileges temp 1000
./c9_5_drop_privileges perm 1000
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

`show`：

```text

用法: ./output.s <show|temp|perm> [目标uid]
  show  只打印当前 R/E/S
  temp  seteuid 降权再回切（需要 saved 还在）
  perm  setuid  永久降权（连 saved 一起砸）

本环境只能走 show：目标 uid 没有映射，set*id 会 EINVAL。
```

`temp 1000`：

```text
    开始                 r=0 e=0 s=0

--- 临时降权：seteuid(1000) ---
    降权前              r=0 e=0 s=0

```

`perm 1000`：

```text
    开始                 r=0 e=0 s=0

--- 永久降权：setuid(1000) ---
    降权前              r=0 e=0 s=0
    setuid(1000) 失败: errno=22 (Invalid argument)
```

（`temp` / `perm` 两次运行都以退出码 1 结束——`main` 把 `do_temp` / `do_perm` 的返回值直接传给了 `return`。）

**解读**

1. **`temp` 和 `perm` 都失败在第一步**，errno 都是 `22`（`EINVAL`），而不是「`perm` 失败了但 `temp` 成功」这种更有戏剧性的结果。原因已经清楚：目标 uid 1000 在本 ns 里没有映射，内核在 capability 检查之前就返回了。所以**这台机器上连「降权」这个前提动作都做不到**，两种模式的差别无从体现。
2. **`show` 模式的用法提示就是程序的诚实声明**：「本环境只能走 show：目标 uid 没有映射，set\*id 会 EINVAL。」——**做不成的实验就写清楚做不成**，不打印假的成功。这也是本仓库所有 demo 的统一约定（Ch8 的 `c8_2` 降权实验同样如此）。
3. **真机上的预期输出**（需要 root 执行）：

   ```text
   # temp 模式（临时降权，saved 保住）
   --- 临时降权：seteuid(1001) ---
       降权前              r=0 e=0 s=0
       降权后              r=0 e=1001 s=0      ← 只有 e 变
       回切后              r=0 e=0 s=0         ← 靠 saved(=0) 回得来
       可以回切，因为 saved(=suid) 没被砸掉。

   # perm 模式（永久降权，saved 一起砸）
   --- 永久降权：setuid(1001) ---
       降权前              r=0 e=0 s=0
       降权后              r=1001 e=1001 s=1001   ← 三个都变
       setuid(0) 失败: errno=1 (Operation not permitted)  ← 回不去了
   ```

   真机跑法（文件头注释里也写了）：

   ```bash
   sudo useradd -m bob
   id bob                                  # 拿到 bob 的 uid，假设是 1001
   sudo ./c9_5_drop_privileges temp 1001
   sudo ./c9_5_drop_privileges perm 1001
   ```

4. **`print_ids()` 打的是 `getresuid()` 的三个值**，不是 `getuid()` / `geteuid()` 分开调。这一点值得学：判断降权效果**一次 `getresuid()` 就够**，而且 `setresuid()` 是原子的快照语义，比三次分开调用更不容易读到不一致的中间态。

## HFT / 嵌入式关联

- **「降权」这个词在安全代码里必须拆成两步**：先**永久**降权（`setresuid(t,t,t)`），再处理不可信输入。中间态（`euid` 降了但 `suid` 还在）**不是安全状态**——只要进程还持有 `suid`，一次 `seteuid(suid)` 就回到 root，任何代码执行漏洞都会直接变成 root 漏洞。
- **降权后必须回读验证。** `setuid(2)` RETURN VALUE 明写「even when the caller is UID 0 也可能失败」+「grave security error to omit checking」。正确形态：

  ```c
  if (setresuid(t, t, t) == -1) die("setresuid");
  uid_t r, e, s;
  if (getresuid(&r, &e, &s) == -1) die("getresuid");
  if (r != t || e != t || s != t) die("降权没有生效");   /* 回读验证 */
  ```

  在容器里这一步尤其必要：`set*id` 可能返回 0 却是 no-op（[9.2](./9.2-effective-uid-gid.md) 实测），只有回读才靠得住。
- **HFT 网关的典型形态**：以 root 启动 → 绑 1024 以下端口 / `mlockall` / 设 `sched_setscheduler` → `setgroups(0, NULL)` → `setgid(t)` → `setresuid(t,t,t)` → **回读验证** → 进主循环。四步顺序不能乱（`setgroups` 排第一的理由见 [9.6](./9.6-supplementary-groups.md)）。
- **嵌入式上 `saved` 的唯一来源是 exec。** `su` / `login` / `sshd` 这类「切用户」程序全都依赖 set-user-ID + saved 这套组合。裁剪 libc（musl / uClibc）时注意：`seteuid()` 在 musl 里就是 `setresuid(-1, euid, -1)` 的包装，语义一致；但极老的 uClibc 有过「`seteuid()` 不检查返回值」的历史问题。**跨 libc 只依赖 POSIX/man 契约。**
- **「永久降权」在嵌入式上的另一个含义是 capability**。`setresuid(uid, uid, uid)` 会清掉 UID 相关的 capability（permitted/effective 集合被重算），但对**非 UID 类** capability（如 `CAP_NET_ADMIN`、`CAP_SYS_RAWIO`）不一定全清。真正的「全丢」要看 `capabilities(7)` 和 `PR_SET_KEEPCAPS`——[Ch39](../../chapter-39-capabilities/README.md)。

## 自测题

<details>
<summary>1. <code>seteuid(getuid())</code> 和 <code>setuid(getuid())</code> 有什么区别？</summary>

差在**改了几个 ID**，也就是「还能不能升回去」：

| 调用（特权进程中） | RUID | EUID | SUID | 能回 root？ |
|--------------------|------|------|------|-------------|
| `seteuid(getuid())` | 0 | t | **0** | ✅ 可以 `seteuid(0)` 回去 |
| `setuid(getuid())` | t | t | **t** | ❌ 回不去了 |

`setuid()` 在特权进程下的行为（`kernel/sys.c:631`）：

```c
new->suid = new->uid = kuid;      /* R 和 S 一起设 */
...
new->fsuid = new->euid = kuid;
```

`setuid(2)` DESCRIPTION："if it is the superuser, **all process-related user ID's are set to `uid`**. After this has occurred, **it is impossible for the program to regain root privileges**."

所以：

- **想「降下去干点活再升回来」** → `seteuid(t)`；
- **想「从此不再需要特权」** → `setuid(t)` 或更明确的 `setresuid(t, t, t)`。

安全上的分界线是「**saved 有没有被砸**」，不是「euid 是不是变了」。
</details>

<details>
<summary>2. <code>setreuid(-1, 2000)</code> 会动 saved 吗？（初值 R=1000 E=0 S=0）</summary>

**会。saved 变成 2000。**

`setreuid(2)` DESCRIPTION：

> If the real user ID is set (i.e., `ruid` is not -1) **or the effective user ID is set to a value not equal to the previous real user ID**, the saved set-user-ID will be set to the new effective user ID.

本题：`ruid == -1`（没设 real），但 `euid = 2000` **≠ 旧 ruid(1000)** → 条件成立 → `saved = 2000`。

内核 `kernel/sys.c:575-577` 就是这个条件：

```c
if (ruid != (uid_t) -1 ||
    (euid != (uid_t) -1 && !uid_eq(keuid, old->uid)))
    new->suid = new->euid;
```

结果：`R=1000 E=2000 S=2000`，而且最后 `new->fsuid = new->euid`（`:578`）所以 fsuid 也变 2000。

**这条是练习 9-1 (b) 与 (c) 的分水岭**：同样目标是 2000，

| 调用 | E | S |
|------|---|---|
| `setreuid(-1, 2000)` | 2000 | **2000**（被改了） |
| `seteuid(2000)` | 2000 | **0**（保持不动） |

`seteuid` 只碰 EUID，`setreuid` 的规则更宽。见 [练习 9-1 的答案表](./9.9-exercises.md)。

⚠️ 另外注意：`setreuid(-1, t)` 里如果 `t` **正好等于旧 ruid**，条件就不成立，saved **不会被改**。所以这条规则的完整形态是「设了 real，或 euid 被设成 ≠ 旧 real」。
</details>

<details>
<summary>3. 为什么说「`saved` 还在 = 还没真正降权」？</summary>

因为只要 `saved` 还是 0，**任何在这个进程里执行的代码都能一行升回 root**：

```c
seteuid(0);        /* saved == 0，所以这一行成功 */
```

`credentials(7)` 说 saved 的用途就是 "switching its effective user ID **back and forth**"；`setresuid(2)` 说非特权进程可以把 E/U 设成「当前的 R/E/S 之一」——`saved == 0` 意味着 0 一直在那个集合里。

所以安全模型上是**两段式**的：

| 阶段 | 处理什么 | 被攻破的后果 |
|------|----------|--------------|
| `saved != 0`（euid 可来回切） | **只处理可信输入**（配置文件、环境、命令行由管理员控制的） | 代码执行 → **root** |
| `saved == 0`（永久降权完成） | **才处理不可信输入**（网络报文、用户数据、行情流） | 代码执行 → 普通用户 |

本节 `c9_5` 的 `perm` 模式做的就是这个切换。真机上输出 `r=1001 e=1001 s=1001`，之后 `setuid(0)` 返回 `EPERM`。

工程上的正确形态：

```c
/* 1. 特权阶段：做完所有需要 root 的事 */
bind(80); mlockall(MCL_CURRENT | MCL_FUTURE);
/* 2. 永久丢权（先组后用户，见 9.6） */
setgroups(0, NULL); setgid(t); setresuid(t, t, t);
/* 3. 回读验证 —— 别信返回值（9.2 的 no-op 陷阱） */
if (geteuid() != t || getuid() != t) die("降权失败");
/* 4. 从这里开始才碰不可信输入 */
serve_requests();
```
</details>

<details>
<summary>4. 我是 root，<code>setuid()</code> 一定成功吗？</summary>

**不一定。**

`setuid(2)` RETURN VALUE：

> Note: there are cases where **`setuid()` can fail even when the caller is UID 0**; **it is a grave security error to omit checking for a failure return from `setuid()`**.

（`setresuid(2)` / `setreuid(2)` 有同样的句子。）可能的失败原因至少有三类：

| errno | 触发 |
|-------|------|
| `EINVAL` | 目标 uid 在本 user namespace 里没有映射（[9.2](./9.2-effective-uid-gid.md) 实测：容器里 `setuid(1000) → 22`，**即使 euid 是 0**） |
| `EAGAIN` | 会改 RUID 但内核 `alloc_uid()` 失败（`kernel/sys.c:484`） |
| `EAGAIN` | 目标 uid 名下进程数会超 `RLIMIT_NPROC`（`setuid(2)` ERRORS 第二条；"Since Linux 3.1, this error case no longer occurs"） |
| `EPERM` | 目标 uid 合法但不在允许集合里（[9.2](./9.2-effective-uid-gid.md) 的分支 C） |

本节 `c9_5` 的 `perm 1000` 就是活样本：**进程 `euid=0`，`setuid(1000)` 仍然返回 `-1 / errno=22`**。

所以「降权」这段代码的写法必须是 `if (setuid(t) == -1) die(...)` **加上**回读验证——**两样都要**。只检查返回值会漏掉「返回 0 但其实是 no-op」，只回读不检查会漏掉「失败原因诊断」。
</details>

<details>
<summary>5. 为什么 <code>setresuid(t, t, t)</code> 比 <code>setuid(t)</code> 更值得推荐？</summary>

三点：

1. **意图明确**。`setresuid(t,t,t)` 字面意思就是「三个都设成 t」，不依赖于「调用者是不是特权」。`setuid(t)` 的行为**取决于调用者身份**（[9.2](./9.2-effective-uid-gid.md) 的分支表：特权时改 3 个，非特权时只改 1 个，还可能直接 EINVAL/EPERM）。安全代码里**行为随环境变化的调用**是隐患来源。
2. **失败可见**。`setresuid(t,t,t)` 在任何情况下不满足就报错；`setuid(t)` 在非特权进程里会**降级成 seteuid**——它"成功"了，但 saved 还在，你以为永久降权了其实没有。这个「成功但语义不同」是最危险的形态。
3. **有 `-1` 这个精确开关**。`setresuid(-1, t, -1)` 只改 EUID 且字面可读（等价于 `seteuid(t)`），`setresuid(-1, t, t)` 只改 E/U 保 R 等等——组合是显式的。

`setresuid(2)` DESCRIPTION 也明确："If one of the arguments equals -1, the corresponding value is not changed."，同时保证 "the filesystem UID is **always** set to the same value as the (possibly new) effective UID"。

唯一代价：`setresuid` 是 **Linux 扩展**（"STANDARDS: Linux"），不像 `setuid`/`seteuid` 那样 POSIX 化。跨平台代码要先探 `#ifdef __linux__`。
</details>
