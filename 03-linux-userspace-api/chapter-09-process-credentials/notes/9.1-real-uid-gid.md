# 9.1 Real User ID and Real Group ID

> 权威依据：`credentials(7)`（man-pages 6.19）· `proc_pid_status(5)` · `user_namespaces(7)` · `setuid(2)` · `execve(2)` · Linux v6.6 `kernel/sys.c`

> 本章：[TLPI 第 09 章 — Process Credentials](../README.md)

> - 下一节：[9.2 Effective User ID and Effective Group ID](./9.2-effective-uid-gid.md)

## 本节讲什么

「进程凭证」这个词很容易被当成一个整体。实际上它是一组**可枚举的 5 类 ID**，每一类的**读法、写法和在权限检查中的地位都不同**。第 9 章的六节（9.1–9.6）就是逐类拆开讲。

9.1 只讲**第 1 类**——real user ID / real group ID——但先把 5 类总表立起来，因为后面每节只讲一条，没有总表会散。

同时这一节要破掉一个必须先破的误解：**`uid=0` 不等于「特权进程」**。本批实测的容器里 `uid = euid = gid = egid = 0`，可是 `CapEff = 0000000000000000`——一个 capability 都没有。原因在 `/proc/self/uid_map`：容器里的 `0` 只是**某个 user namespace 里的编号**，映射到宿主的普通 uid。

---

## 要点

### 一、五类 ID 总表

`credentials(7)` 的 "User and group identifiers" 一节把 Linux 的凭证**逐条列成 5 类**（原文 bullets，中文为对照）：

| # | 类 | 成员 | 干什么用 | 哪一节 |
|---|----|------|----------|--------|
| 1 | **Real** user/group ID | `uid` / `gid` | "determine **who owns** the process" | **9.1** |
| 2 | **Effective** user/group ID | `euid` / `egid` | "used by the kernel to determine the **permissions** … when accessing shared resources such as message queues, shared memory, and semaphores" | [9.2](./9.2-effective-uid-gid.md) |
| 3 | **Saved set**-user-ID / set-group-ID | `suid` / `sgid` | set-user-ID 程序里保存 exec 那一刻的 euid，用来**来回切换** | [9.4](./9.4-saved-id.md) |
| 4 | **Filesystem** user/group ID（Linux 专有） | `fsuid` / `fsgid` | "in conjunction with the supplementary group IDs … determine permissions for accessing **files**" | [9.5](./9.5-fs-uid-gid.md) |
| 5 | **Supplementary** group IDs | 组列表 | "additional group IDs that are used for permission checks when accessing files and other shared resources" | [9.6](./9.6-supplementary-groups.md) |

> ⚠️ 表里第 2 类和第 4 类那段是**最容易读漏的一句**。`credentials(7)` 在 Effective 一节写：
>
> > These IDs are used by the kernel to determine the permissions that the process will have when accessing shared resources such as message queues, shared memory, and semaphores. **On most UNIX systems, these IDs also determine the permissions when accessing files. However, Linux uses the filesystem IDs described below for this task.**
>
> 也就是说：**「文件权限看 EUID」是大多数 UNIX 的说法，Linux 不是。** Linux 上文件权限看 **fsuid**（+ 补充组）。只是内核保证「只要 euid 变，fsuid 就跟着变」，所以两者**平时相等**，才让「看 EUID」这句话在实践中不算错。这个分岔是 [9.5](./9.5-fs-uid-gid.md) 的主题。

### 二、Real UID / Real GID：「谁拥有这个进程」

| 项 | 结论 | 依据 |
|----|------|------|
| 含义 | "determine who **owns** the process" | `credentials(7)` |
| 获取 | `getuid()` / `getgid()`；或 `getresuid()` 一次拿 R/E/S | — |
| `fork` 之后 | 子进程**继承** | `credentials(7)`："A child process created by fork(2) inherits copies of its parent's user and groups IDs." |
| `execve` 之后 | **不变** | `execve(2)`："The process's real UID and real GID, as well as its supplementary group IDs, are **unchanged** by a call to execve()." |
| 权限检查 | **不参与文件权限检查** | 见上表 ⚠️ |
| 参与什么 | 发信号的权限（`kill(2)`）、`/proc/<pid>` 目录属主、按 uid 记账的资源限制（如 `RLIMIT_NPROC`） | `credentials(7)`："when determining the permissions for sending signals" |

一句话记忆：**RUID 是「身份证」，EUID 是「工牌」。** 门禁（文件权限）不看身份证，看工牌；但出了事追责（信号来源、资源记账）看身份证。

### 三、uid 是「命名空间里的编号」——所以 uid=0 可以毫无特权

本节实测的容器：

```text
--- /proc/self/uid_map ---
             0        113          1
```

`uid_map` 的 3 列含义是 `ns 内的 ID ｜ 父 ns 里的 ID ｜ 长度`。这一行读作：**本 namespace 的 uid 0，对应父 namespace 的 uid 113，长度 1**（宿主上的 rootless 容器，本 ns 的 0 号其实是个普通用户）。所以「我是 uid 0」只说明「在我所在的这个 namespace 里我是 0 号」；真正决定能干什么的，是 capability 集合（`CapEff`）——本容器是 `0000000000000000`，一个都没有。

这个区别在返回码上是能看见的，`setuid(2)` ERRORS：

> **EINVAL** The user ID specified in `uid` is not valid in this user namespace.

而「uid 合法但你不许改」才是 `EPERM`。所以容器里 `setuid(10240)` 得到的是 **EINVAL(22)** 而不是 EPERM——详见 [9.2](./9.2-effective-uid-gid.md) 的实测表格。

### 四、`/proc/self/status` 的 `Uid:` 是 **4 列**，不是 3 列

`proc_pid_status(5)` 原文：

> **Uid**  Real, effective, saved set, and **filesystem** UIDs
> **Gid**  Real, effective, saved set, and **filesystem** GIDs
> **Groups**  Supplementary group list.

本节实测这一行是：

```text
  Uid:	0	0	0	0
```

四个 0。**第 4 列就是 fsuid**——它和 `setfsuid(-1)` 的返回值必然相等（[9.5](./9.5-fs-uid-gid.md) 实测了这一致性）。只想拿 R/E/S 的话，用 `getresuid()` 更明确；`/proc` 这一路的优势是「内核自己吐的，不受 libc 包装影响」，适合做交叉验证。

### 五、两个上限：`_SC_NGROUPS_MAX` 与 `_SC_LOGIN_NAME_MAX`

`credentials(7)`：

> Before Linux 2.6.4, a process can be a member of up to **32** supplementary groups; since Linux 2.6.4, a process can be a member of up to **65536** supplementary groups. The call `sysconf(_SC_NGROUPS_MAX)` can be used to determine the number of supplementary groups of which a process may be a member.

本节实测 `_SC_NGROUPS_MAX = 65536`（即 2.6.4 之后的值），`_SC_LOGIN_NAME_MAX = 256`。

## 代码

### c9_1 五类凭证：两条独立读法 + 为什么 uid=0 不是特权

[`../code/c9_1_all_creds.c`](../code/c9_1_all_creds.c) 做一件事：把 5 类 ID 从**两条互相独立的路径**读出来并对照。

- 路径 ①：API（`getresuid` / `getresgid` / `setfsuid(-1)` / `getgroups`）
- 路径 ②：内核自己吐的 `/proc/self/status`（`Uid:` / `Gid:` / `Groups:` 行）

两条路看到同一组数字，才算把 9.1 坐实。程序末尾另外 dump `uid_map` / `gid_map` 和两个 `sysconf` 上限。

```c
/* c9_1_all_creds.c —— 一个进程到底持有几类凭证？
 *
 * 9.1 只解决一件事：把「凭证（credentials）」这个笼统的词拆成**可枚举的 5 类 ID**，
 * 并给出两个**互相独立**的读法：一组 API，以及内核自己吐的 /proc 文件。
 * 两者都看到同一组数字，才算把这一节坐实。
 *
 * 权威依据：
 *   - credentials(7), User and group identifiers 一节：5 类逐条（real / effective /
 *     saved set / filesystem / supplementary）。
 *   - proc_pid_status(5)：Uid / Gid 行是 **四列** —— "Real, effective, saved set,
 *     and filesystem UIDs (GIDs)."；Groups 行是 "Supplementary group list."
 *   - kernel/sys.c:749 getresuid() 实现：三次 from_kuid_munged(cred->user_ns, ...)。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_1_all_creds c9_1_all_creds.c
 */
#define _GNU_SOURCE
#include <grp.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/fsuid.h>
#include <sys/types.h>
#include <unistd.h>

/* 从 /proc/self/status 里取一行（只用静态缓冲，避免自己引入堆分配） */
static void show_status_line(const char *key)
{
    FILE *fp = fopen("/proc/self/status", "r");
    if (fp == NULL) {
        printf("  (打不开 /proc/self/status)\n");
        return;
    }
    char buf[512];
    size_t klen = 0;
    while (key[klen] != '\0')
        klen++;
    while (fgets(buf, sizeof buf, fp) != NULL) {
        if (strncmp(buf, key, klen) == 0 && buf[klen] == ':') {
            printf("  %s", buf);      /* 整行原样抄，不加工 */
            break;
        }
    }
    fclose(fp);
}

static void show_whole_file(const char *path)
{
    FILE *fp = fopen(path, "r");
    printf("--- %s ---\n", path);
    if (fp == NULL) {
        printf("  (打不开)\n");
        return;
    }
    char buf[256];
    int any = 0;
    while (fgets(buf, sizeof buf, fp) != NULL) {
        printf("    %s", buf);
        any = 1;
    }
    if (!any)
        printf("    (空文件)\n");
    fclose(fp);
}

int main(void)
{
    /* ---------- 1 类 + 2 类 + 3 类：一次全拿 ---------- */
    uid_t ruid, euid, suid;
    gid_t rgid, egid, sgid;
    if (getresuid(&ruid, &euid, &suid) == -1) {
        perror("getresuid");
        return 1;
    }
    if (getresgid(&rgid, &egid, &sgid) == -1) {
        perror("getresgid");
        return 1;
    }

    /* ---------- 4 类：filesystem ID ----------
     * setfsuid() 的返回值是**旧** fsuid，而且成功失败都返回它（setfsuid(2) BUGS）。
     * 所以惯用法是再调一次 setfsuid(-1)：-1 永远不合法，这一调用一定不改任何东西，
     * 但它的返回值就是「当前的 fsuid」。 */
    uid_t fsuid = (uid_t) setfsuid((uid_t) -1);
    gid_t fsgid = (gid_t) setfsgid((gid_t) -1);

    /* ---------- 5 类：supplementary groups ---------- */
    int ng = getgroups(0, NULL);        /* 先问几个，不传缓冲 */
    gid_t *groups = NULL;
    if (ng > 0) {
        groups = malloc(sizeof(gid_t) * (size_t) ng);
        if (groups == NULL) {
            perror("malloc");
            return 1;
        }
        int got = getgroups(ng, groups);
        if (got == -1) {
            perror("getgroups");
            return 1;
        }
        ng = got;
    }

    printf("=== 来源 ①：API ===\n");
    printf("UID  real=%u  effective=%u  saved=%u  filesystem=%u\n",
           (unsigned) ruid, (unsigned) euid, (unsigned) suid, (unsigned) fsuid);
    printf("GID  real=%u  effective=%u  saved=%u  filesystem=%u\n",
           (unsigned) rgid, (unsigned) egid, (unsigned) sgid, (unsigned) fsgid);
    printf("补充组 %d 个:", ng);
    for (int i = 0; i < ng; i++)
        printf(" %u", (unsigned) groups[i]);
    printf("\n");
    free(groups);

    printf("\n=== 来源 ②：内核自己的 /proc/self/status ===\n");
    show_status_line("Uid");
    show_status_line("Gid");
    show_status_line("Groups");
    show_status_line("CapEff");
    show_status_line("NoNewPrivs");

    printf("\n=== 为什么 uid=0 却不是「特权进程」===\n");
    show_whole_file("/proc/self/uid_map");
    show_whole_file("/proc/self/gid_map");

    printf("\n=== sysconf 给出的上限 ===\n");
    printf("  _SC_NGROUPS_MAX    = %ld\n", sysconf(_SC_NGROUPS_MAX));
    printf("  _SC_LOGIN_NAME_MAX = %ld\n", sysconf(_SC_LOGIN_NAME_MAX));
    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c9_1_all_creds c9_1_all_creds.c && ./c9_1_all_creds
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
=== 来源 ①：API ===
UID  real=0  effective=0  saved=0  filesystem=0
GID  real=0  effective=0  saved=0  filesystem=0
补充组 1 个: 0

=== 来源 ②：内核自己的 /proc/self/status ===
  Uid:	0	0	0	0
  Gid:	0	0	0	0
  Groups:	0 
  CapEff:	0000000000000000
  NoNewPrivs:	1

=== 为什么 uid=0 却不是「特权进程」===
--- /proc/self/uid_map ---
             0        113          1
--- /proc/self/gid_map ---
             0        113          1

=== sysconf 给出的上限 ===
  _SC_NGROUPS_MAX    = 65536
  _SC_LOGIN_NAME_MAX = 256
```

**解读**

1. **两条路径完全对上**：`real=0 effective=0 saved=0 filesystem=0`（API）与 `Uid: 0 0 0 0`（内核）逐列相同。这印证了 `proc_pid_status(5)` 那句 "Real, effective, saved set, and filesystem UIDs" 的列序，也说明 `setfsuid(-1)` 这个怪接口读到的就是第 4 列。
2. **`CapEff: 0000000000000000` 是本节最重要的一行**。`uid=0` 在这台机器上**换不来任何特权**。要验证这一点不需要别的工具——紧接着的 `uid_map` 两行就解释了：本 ns 的 0 号映射到父 ns 的 113 号，它只是一个「代号叫 0 的普通用户」。
3. **`NoNewPrivs: 1`**：这个进程被设了 `no_new_privs`。它的后果是**所有 set-user-ID 位一律失效**（[9.3](./9.3-set-user-id.md) 的四个开关之一），并且 `kernel/sys.c:2570` 的 `PR_SET_NO_NEW_PRIVS` 只接受 `arg2 == 1`——**一旦置位无法取消**。
4. **`Groups: 0`**：本进程有 1 个补充组，gid 是 0。注意 `Groups` 行**不包含** egid（`getgroups(2)` 原文："It is unspecified whether the effective group ID of the calling process is included in the returned list."）——[9.6](./9.6-supplementary-groups.md)。
5. **`_SC_NGROUPS_MAX = 65536`**：这是**上限**，不是当前组数（当前组数是 1）。嵌入式上真实取值可能被内核配置改小，所以**永远用 `sysconf` 问，不要写死 32**。

### c9_7 亲手造一个 user namespace，看 uid 怎么被重新解释

上面 §三 讲的 `uid_map` 是**只读观察**。[`../code/c9_7_user_ns.c`](../code/c9_7_user_ns.c) 更进一步：**自己 `unshare(CLONE_NEWUSER)` 造一个新 namespace**，把「uid 只是编号」这件事变成可以看的现象。

程序分父 / 子两段，子进程走 10 步：`fork` → `unshare(CLONE_NEWUSER)` → dump 三个 proc 文件 → 写 `setgroups=deny` → 写 `gid_map` → 写 `uid_map` → 调 `setuid(10240)`。

```c
/* c9_7_user_ns.c —— 亲手造一个 user namespace，看凭证怎么被重新解释
 *
 * 这是 9.1 的一个极端例子，也是理解「uid 是个命名空间里的编号」最直观的方法。
 *
 * 现象（本程序跑出来会看到）：
 *   ① unshare(CLONE_NEWUSER) 之后、写映射之前，getuid() 变成 **65534** ——
 *      不是「没有人」，而是溢出值 overflowuid：新 ns 里还没有任何映射，
 *      内核打印自己的 uid 时取不到对应值，就给你 65534。
 *   ② 写 gid_map 成功，写 uid_map 却 EPERM —— 两条规则完全不同（见下）。
 *   ③ uid_map 写失败后，这个 ns 里**一个 uid 都没映射**，于是 setuid 任何值都 EINVAL。
 *
 * 为什么 uid_map 会 EPERM：user_namespaces(7) 第 370-381 行 ——
 *   "If updating /proc/pid/uid_map to create a mapping that maps **UID 0 in the
 *    parent namespace**, then one of the following must be true: ... it must have
 *    the CAP_SETFCAP capability in that user namespace"（Linux 5.12 起）。
 *   我们 CapEff=0，没有 CAP_SETFCAP -> 写 uid_map 被拒。
 *   而 gid_map 的规则里没有这一条，所以同一个进程写得进 gid_map。
 *
 * 还有一条规则也值得记住（:412）：非特权进程只能写「**一行**，且把写入者自己的
 * euid 映射进去」的映射。所以不存在「随便挑个 uid 映射」这回事。
 *
 * 编译: gcc -O0 -Wall -Wextra -o c9_7_user_ns c9_7_user_ns.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

static void dump(const char *path)
{
    FILE *fp = fopen(path, "r");
    printf("    %s: ", path);
    if (fp == NULL) {
        printf("(打不开 %s)\n", strerror(errno));
        return;
    }
    char buf[256];
    int any = 0;
    while (fgets(buf, sizeof buf, fp) != NULL) {
        printf("%s", buf);
        any = 1;
    }
    if (!any)
        printf("(空 —— 一行映射都没有)\n");
    fclose(fp);
}

static void write_one(const char *path, const char *what)
{
    errno = 0;
    FILE *fp = fopen(path, "w");
    if (fp == NULL) {
        printf("    [%s] 打不开: errno=%d (%s)\n", what, errno, strerror(errno));
        return;
    }
    int r = fputs(what, fp);
    int c = fclose(fp);                 /* ⚠️ 必须 fclose 才知道写有没有失败 */
    printf("    [%s] 写 \"%s\": fputs=%d fclose=%d errno=%d (%s)\n",
           what, what, r, c, errno, errno ? strerror(errno) : "未置位");
}

int main(void)
{
    printf("=== 父进程 ===\n");
    printf("  uid=%u euid=%u gid=%u\n",
           (unsigned) getuid(), (unsigned) geteuid(), (unsigned) getgid());
    dump("/proc/self/uid_map");

    printf("\n=== 子进程：unshare(CLONE_NEWUSER) ===\n");
    fflush(stdout);                     /* ⚠️ fork 前 flush，否则父进程缓冲被复制后吐两遍 */
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return 1;
    }
    if (pid == 0) {
        printf("  [1] fork 之后          uid=%u gid=%u\n",
               (unsigned) getuid(), (unsigned) getgid());

        errno = 0;
        int rc = unshare(CLONE_NEWUSER);
        printf("  [2] unshare(CLONE_NEWUSER) = %d  errno=%d (%s)\n",
               rc, errno, errno ? strerror(errno) : "未置位");
        if (rc == -1) {
            fflush(stdout);
            _exit(1);
        }
        printf("  [3] 写映射之前          uid=%u gid=%u   <- 65534 = overflowuid\n",
               (unsigned) getuid(), (unsigned) getgid());
        dump("/proc/self/uid_map");
        dump("/proc/self/gid_map");
        dump("/proc/self/setgroups");
        {
            FILE *fp = fopen("/proc/sys/kernel/overflowuid", "r");
            char buf[64];
            if (fp != NULL) {
                if (fgets(buf, sizeof buf, fp) != NULL)
                    printf("    /proc/sys/kernel/overflowuid = %s", buf);
                fclose(fp);
            }
        }

        printf("\n  [4] 写 setgroups=deny（写 gid_map 的前置条件）\n");
        write_one("/proc/self/setgroups", "deny");

        printf("\n  [5] 写 gid_map = \"0 0 1\"（子ns uid 0 <- 父ns gid 0）\n");
        write_one("/proc/self/gid_map", "0 0 1");
        printf("  [6] 写完之后            uid=%u gid=%u\n",
               (unsigned) getuid(), (unsigned) getgid());
        dump("/proc/self/gid_map");

        printf("\n  [7] 写 uid_map = \"0 0 1\"（同样的形态，只换了文件）\n");
        write_one("/proc/self/uid_map", "0 0 1");
        printf("  [8] 写完之后            uid=%u gid=%u   <- uid 没变\n",
               (unsigned) getuid(), (unsigned) getgid());
        dump("/proc/self/uid_map");

        printf("\n  [9] 在这种状态下调 setuid(10240)\n");
        errno = 0;
        int r2 = setuid((uid_t) 10240);
        printf("      setuid(10240) = %d  errno=%d (%s)\n",
               r2, errno, strerror(errno));

        printf("\n  [10] 结论\n");
        printf("      uid_map 里一行都没有 -> 这个 ns 里任何 uid 都「不合法」->\n");
        printf("      连 setuid 自己都做不了。这不是 bug，是映射没建起来。\n");
        fflush(stdout);
        _exit(0);
    }

    int st = 0;
    if (waitpid(pid, &st, 0) == -1)
        perror("waitpid");
    else
        printf("\n=== 父进程后续 ===\n  子进程结束: exited=%d status=%d\n",
               WIFEXITED(st), WIFEXITED(st) ? WEXITSTATUS(st) : -1);
    return 0;
}
```

```text
=== 父进程 ===
  uid=0 euid=0 gid=0
    /proc/self/uid_map:          0        113          1

=== 子进程：unshare(CLONE_NEWUSER) ===
  [1] fork 之后          uid=0 gid=0
  [2] unshare(CLONE_NEWUSER) = 0  errno=0 (未置位)
  [3] 写映射之前          uid=65534 gid=65534   <- 65534 = overflowuid
    /proc/self/uid_map: (空 —— 一行映射都没有)
    /proc/self/gid_map: (空 —— 一行映射都没有)
    /proc/self/setgroups: deny
    /proc/sys/kernel/overflowuid = 65534

  [4] 写 setgroups=deny（写 gid_map 的前置条件）
    [deny] 写 "deny": fputs=1 fclose=0 errno=0 (未置位)

  [5] 写 gid_map = "0 0 1"（子ns uid 0 <- 父ns gid 0）
    [0 0 1] 写 "0 0 1": fputs=1 fclose=0 errno=0 (未置位)
  [6] 写完之后            uid=65534 gid=0
    /proc/self/gid_map:          0          0          1

  [7] 写 uid_map = "0 0 1"（同样的形态，只换了文件）
    [0 0 1] 写 "0 0 1": fputs=1 fclose=-1 errno=1 (Operation not permitted)
  [8] 写完之后            uid=65534 gid=0   <- uid 没变
    /proc/self/uid_map: (空 —— 一行映射都没有)

  [9] 在这种状态下调 setuid(10240)
      setuid(10240) = -1  errno=22 (Invalid argument)

  [10] 结论
      uid_map 里一行都没有 -> 这个 ns 里任何 uid 都「不合法」->
      连 setuid 自己都做不了。这不是 bug，是映射没建起来。

=== 父进程后续 ===
  子进程结束: exited=1 status=0
```

**解读**

1. **第 [3] 步是本节最反直觉的一行**：`unshare(CLONE_NEWUSER)` **成功**（返回 0），紧接着 `uid` 变成了 **65534**。这不是「变成了某个用户」，而是**溢出值 `overflowuid`**——程序顺手把 `/proc/sys/kernel/overflowuid` 也打了出来，确认就是 `65534`。原因：新 ns 里**还没有任何映射**，内核要把内部 `kuid` 打印成 ns 内的编号时取不到值，就给你溢出值。
2. **两个 map 都是空的**：`(空 —— 一行映射都没有)`。所以「我是谁」这件事在新 ns 里**根本没有定义**。
3. **`/proc/self/setgroups: deny`** 在第 [3] 步就已经是 `deny` 了 —— 新 user namespace **默认就是拒绝 `setgroups`**（[9.6](./9.6-supplementary-groups.md) 的两道闸门之一）。第 [4] 步「写 deny」实际上是**写一遍同样的值**（幂等），属于流程上的显式确认。
4. **第 [5]→[6] 步：`gid_map` 写成功。** `fputs=1 fclose=0 errno=0`，之后 `gid` 从 65534 变成 **0**，`/proc/self/gid_map` 里出现了 `0 0 1`。注意这里 `fclose` 是 **0**（成功）。
5. **第 [7]→[8] 步：`uid_map` 写失败，而且失败是被 `fclose` 暴露的。** 三行输出里 `fputs=1`（写缓冲成功）但 **`fclose=-1 errno=1 (Operation not permitted)`**。

   > ⚠️ **这是本程序最重要的一个工程细节**：`/proc` 里的这些文件**写操作在 `fclose()` 时才真正提交并检查**。如果程序只检查 `fputs()` 或 `fprintf()` 的返回值，会**误判成功**。程序里那句注释（`/* ⚠️ 必须 fclose 才知道写有没有失败 */`）就是为这件事写的。`write(2)` 直接写同样会立刻返回错误——问题只出在**用了 stdio 缓冲**的场合。

6. **为什么 `gid_map` 写得进、`uid_map` 写不进？** 因为 `user_namespaces(7)` 对 **uid_map** 多了一条规则（`:370-381`）：

   > If updating `/proc/pid/uid_map` to create a mapping that maps **UID 0 in the parent namespace**, then one of the following must be true: … it must have the **`CAP_SETFCAP`** capability in that user namespace. **This rule has been in place since Linux 5.12.**

   本进程 `CapEff = 0`，没有 `CAP_SETFCAP` → 写 uid_map 被拒。而 `gid_map` 的规则里**没有这一条**，所以同样形态的写入成功了。**这就是「同一个进程、同样写法、一个成功一个失败」的全部原因。**

7. **第 [9] 步把 §三 的结论闭环了**：`uid_map` 一行都没有 → 这个 ns 里**任何 uid 都不合法** → `setuid(10240)` 返回 `EINVAL(22)`。这和 [9.2](./9.2-effective-uid-gid.md) 的分支 A、[9.7](./9.7-api.md) 的 `c9_4` 是同一个机制：**`make_kuid()` 拿不到合法 kuid 时，内核连通配检查都不做。**
8. **第 [10] 步那句「这不是 bug，是映射没建起来」值得记住**。在容器里做 `user namespace` 实验时，`EINVAL` 铺满地是**预期**，不是环境坏了。想让它能干点事，得先用**特权**（父 ns 的 `CAP_SETFCAP`）把映射建起来。

## HFT / 嵌入式关联

- **「uid=0 却不等于什么都能干」在容器和嵌入式里都是常态。** 很多 BSP 的 systemd 服务跑在 `ProtectSystem` / `NoNewPrivileges=yes` 下：`uid=0` 但 capability 被剥空、SUID 位全废。**排查「为什么 root 也写不了这个文件」时，第一件事是看 `CapEff` 和 `no_new_privs`，不是怀疑权限位。**
- **RUID 才是记账口径。** `RLIMIT_NPROC` 按 **RUID** 统计进程数（`kernel/sys.c:484` 的 `set_user()` 就是为这件事服务的）。HFT 里用 setuid 程序启动一份交易进程后，如果 `setuid()` 只改了 EUID 而 RUID 仍是启动者，那么**所有由它 fork 出来的进程都算在启动者名下**，一不留神就撞上 `RLIMIT_NPROC`。
- **user namespace 一样影响 uid。** 容器/嵌入式沙箱里 `uid_map` 通常只有一行，于是 `setuid(10240)` 直接 EINVAL 而不是 EPERM。做「启动时降权」的功能时，**不要把 EPERM 当成唯一失败形式**——见到 EINVAL 要想到「这个 uid 在本 ns 里没映射」。
- **`/proc/self/uid_map` 是最便宜的身份自检。** 嵌入式设备上排查「服务是不是真的降权了 / 是不是还在 init ns 里」，`cat /proc/self/uid_map` 一行就够，比装 `capsh` 省事。

## 自测题

<details>
<summary>1. 一个进程 <code>uid=0 euid=0</code>，它能写任意文件吗？</summary>

**不能保证。** `uid=0` 只是「在它所在的那个 user namespace 里编号是 0」。

本节实测反例：`Uid: 0 0 0 0` 而 `CapEff: 0000000000000000`，同时 `uid_map` 只有 `0 113 1` 一行——这个「0」在父 namespace 里其实是普通用户。

判断能不能写某个文件，至少要看三样：

| 看什么 | 在哪看 | 本节实测值 |
|--------|--------|-----------|
| 文件权限检查用的 fsuid | `/proc/self/status` 的 `Uid:` **第 4 列** | `0` |
| 补充组 | `Groups:` 行 | `0` |
| capability | `CapEff:` 行 | `0000000000000000`（空） |

`credentials(7)` 明写 Linux 上**文件**权限用的是 filesystem ID（+ 补充组），不是 EUID；而 root「绕过权限位」的能力实际来自 `CAP_DAC_OVERRIDE` 这个 capability——本进程一个 capability 都没有，所以 `uid=0` 换不来任何额外权限。
</details>

<details>
<summary>2. <code>/proc/self/status</code> 的 <code>Uid:</code> 有几个字段？第 4 个是什么？</summary>

**4 个**，第 4 个是 **filesystem UID（fsuid）**。

`proc_pid_status(5)` 原文：

> **Uid**  Real, effective, saved set, and **filesystem** UIDs
> **Gid**  Real, effective, saved set, and **filesystem** GIDs

列序 = `real  effective  saved  filesystem`。本节实测 `Uid: 0 0 0 0`。

这个第 4 列与 `setfsuid(-1)` 的返回值**必然相等**（[9.5](./9.5-fs-uid-gid.md) 把这条一致性做成了实测的一行「两者一致? 是」）。`ps` / `pidstat` 之类只看前 3 列，要 fsuid 得自己读 `/proc` 或调 `setfsuid(-1)`。
</details>

<details>
<summary>3. <code>fork</code> 和 <code>execve</code> 之后，RUID 各是什么？</summary>

| 事件 | RUID | RGID | 补充组 | 依据 |
|------|------|------|--------|------|
| `fork()` | 继承父进程 | 继承父进程 | 继承 | `credentials(7)`："inherits **copies** of its parent's user and groups IDs" |
| `execve()`（无论有没有 set-user-ID 位） | **不变** | **不变** | **不变** | `execve(2)`："The process's real UID and real GID, as well as its supplementary group IDs, are **unchanged** by a call to `execve()`." |

`execve` 会动的是 **euid 和 saved set ID**（而且 saved 是**无条件** ← 新的 euid），real 那一侧**永远不动**。所以「启动者是谁」这个事实从登录到程序退出都保持——这也正是 set-user-ID 程序能靠 RUID 认回原始用户的原因（[9.4](./9.4-saved-id.md)）。

注意 `fork` 之后父子进程是**独立的副本**：之后再各自 `setuid` 互不影响。
</details>

<details>
<summary>4. 为什么 <code>sysconf(_SC_NGROUPS_MAX)</code> 比 <code>getgroups(0, NULL)</code> 大那么多？</summary>

**因为它们回答两个不同的问题。**

| 调用 | 问题 | 本节实测 |
|------|------|----------|
| `sysconf(_SC_NGROUPS_MAX)` | **系统允许**一个进程最多属于几个补充组 | `65536` |
| `getgroups(0, NULL)` | **本进程此刻实际**属于几个 | `1` |

`credentials(7)`：Linux 2.6.4 起上限是 65536；`getgroups(2)` 描述里 size=0 的调用 "list is not modified, but the total number of supplementary group IDs for the process is returned"。

写代码时的正确姿势是：用 `getgroups(0, NULL)` 拿**实际个数**再 `malloc`（[9.6](./9.6-supplementary-groups.md) 的惯用法），而不是按 `_SC_NGROUPS_MAX` 开一个 65536 项的数组——那是 256 KB 的无谓分配。反过来，`setgroups()` 的 **EINVAL** 判据用的才是 `NGROUPS_MAX`（`getgroups(2)` ERRORS："**EINVAL** `size` is greater than `NGROUPS_MAX`"）。
</details>

<details>
<summary>5. 本节程序里的 <code>NoNewPrivs: 1</code> 说明什么？能取消吗？</summary>

说明这个进程（及其将来的子进程）**不能通过 set-user-ID / set-group-ID / file capability 获得新特权**。这是 `proc_pid_status(5)` 里 `NoNewPrivs` 行的含义，也是 [9.3](./9.3-set-user-id.md) 里「set-user-ID 位被无视」的四条路之一（`fs/exec.c:1614` `task_no_new_privs(current)` 直接 `return`）。

**不能取消。** `kernel/sys.c:2570`：

```c
case PR_SET_NO_NEW_PRIVS:
    if (arg2 != 1 || arg3 || arg4 || arg5)
        return -EINVAL;
    task_set_no_new_privs(current);
    break;
```

只接受 `arg2 == 1`，没有任何「清位」分支——这是个**单向开关**，设计上就是「降下去就升不回来」。同一段代码里 `case PR_GET_NO_NEW_PRIVS`（`:2576`）只负责读回。

工程含义：**在自己程序里调 `prctl(PR_SET_NO_NEW_PRIVS, 1, ...)` 是不可逆的安全增强**（沙箱、CI runner 都用它），但它同时会让后面所有依赖 SUID 的调用（比如去 `execve` 一个 SUID helper）静默失效。
</details>
