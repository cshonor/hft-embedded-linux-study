## 本节讲什么

「让进程睡一会儿」看起来是最简单的需求，但它有三个**互相纠缠**的坑：

1. **被信号打断了怎么办？** 睡一半被打断，剩下那半怎么补？
2. **补的方式会不会引入漂移？** 反复「打断 → 补 → 再打断」时，每次补都会向上取整到 jiffy ⇒ 可能永远睡不完。
3. **它跟 `alarm()` 会不会打架？** 老实现里 `sleep()` 就是用 `alarm()` 做的 ⇒ 混用必然互相踩。

本节按原书的两个小节走：先看低精度的 `sleep()`，再看高精度的 `nanosleep()`，并把（3）的答案——「Linux 上 `sleep()` 就是 `nanosleep()`，所以**不**打架，但 POSIX 没规定」——钉死。

---

## 23.4.1 低精度睡眠：`sleep()`

```c
#include <unistd.h>

unsigned int sleep(unsigned int seconds);
```

原书 §23.4.1 逐字：

> The `sleep()` function suspends execution of the calling process for the number of seconds specified in the `seconds` argument **or until a signal is caught** (thus interrupting the call).
>
> If the sleep completes, `sleep()` returns **0**. If the sleep is interrupted by a signal, `sleep()` returns the number of **remaining (unslept) seconds**.

所以返回值只有两种含义，必须分清：

| 返回值 | 含义 | 后果 |
|--------|------|------|
| `0` | 睡满了 | 正常 |
| `> 0` | 被信号打断，还剩这么多秒 | **需要自己决定要不要再睡一次** |

### ⭐ 最容易踩的一条：`sleep()` 与 `alarm()` 的关系

原书接着给了很关键的一段：

> SUSv3 leaves possible interactions of `sleep()` with `alarm()` and `setitimer()` **unspecified**. On Linux, `sleep()` is implemented as a call to `nanosleep()` (Section 23.4.2), with the consequence that there is **no interaction** between `sleep()` and the timer functions. However, on **many implementations, especially older ones**, `sleep()` is implemented using `alarm()` and a handler for the `SIGALRM` signal. **For portability, we should avoid mixing the use of `sleep()` with `alarm()` and `setitimer()`.**

拆开看：

| 实现 | `sleep()` 的底层 | 与 `alarm()` 混用 |
|------|-----------------|------------------|
| **Linux（glibc 现代实现）** | `nanosleep()` | **不冲突** —— 两者用不同的机制 |
| 老式 UNIX / 某些嵌入式 libc | `alarm()` + `SIGALRM` 处理器 | **互相覆盖**：`sleep()` 会毁掉你的 `alarm()`，你的 `alarm()` 也会提前叫醒 `sleep()` |

> ⚠️ 结论就是书里那句：**可移植的代码不要混用 `sleep()` 与 `alarm()`/`setitimer()`**。虽然 Linux 上没事，但「在 Linux 上没事」不等于「在目标板上没事」—— 这一点对嵌入式尤其重要（很多板子跑的是精简 libc）。

## 23.4.2 高精度睡眠：`nanosleep()`

```c
#define _POSIX_C_SOURCE 199309
#include <time.h>

int nanosleep(const struct timespec *request, struct timespec *remain);

struct timespec {
    time_t tv_sec;         /* Seconds */
    long   tv_nsec;        /* Nanoseconds，必须落在 0..999999999 */
};
```

相对 `sleep()` 的三个优势：

1. **精度可到纳秒**（实际精度另说，见 §23.2）；
2. **SUSv3 明确规定它不得用信号实现** ⇒ 原书原文：

   > A further advantage of `nanosleep()` is that SUSv3 explicitly specifies that it should not be implemented using signals. This means that, unlike the situation with `sleep()`, we can **portably** mix calls to `nanosleep()` with calls to `alarm()` or `setitimer()`.

3. **被打断时能把「还剩多久」还给你**：

   > ...`nanosleep()` **may still be interrupted by a signal handler**. In this case, `nanosleep()` returns `-1`, with `errno` set to the usual `EINTR` and, if the argument `remain` is not `NULL`, the buffer it points to returns the remaining unslept time.

### ⭐ 但「用 `remain` 续睡」有个致命缺陷

原书在 Listing 23-3 之后点出了这个问题：

> This rounding behavior means that if signals are received at a **high rate**, then there is a problem with the approach employed in the program in Listing 23-3. The problem is that **each restart of `nanosleep()` will be subject to rounding errors**, since the returned `remain` time is unlikely to be an exact multiple of the granularity of the software clock. Consequently, each restarted `nanosleep()` will sleep **longer** than the value returned in `remain` by the previous call. In the case of an extremely high rate of signal delivery (i.e., as or more frequent than the software clock granularity), **the process may never be able to complete its sleep**.

推演一遍（假设 jiffy = 4 ms，要睡 1 秒）：

| 轮次 | `nanosleep` 请求 | 实际睡了 | 返回的 `remain` | 下一轮请求 |
|------|-----------------|---------|----------------|-----------|
| 1 | 1000.000 ms | 被打断于 1000 ms | 8.1466 ms | **8.1466 ms** |
| 2 | 8.1466 ms | 向上取整到 **12 ms** | 0 ms（睡满） | —— |

注意第 2 轮：请求 8.1466 ms，但 jiffy 是 4 ms ⇒ 内核**向上**桶取整到 12 ms。「多睡」的那部分就被**扔掉**了。信号来得越密，被打断越频繁，每轮都要多睡一截；信号密集到「间隔 ≤ jiffy」时，**每一轮都睡不完**，程序就卡死了。

**原书给的解药**：`clock_nanosleep()` + `TIMER_ABSTIME`（Linux 2.6 起）—— 见 [23.5 POSIX Clocks](23.5-posix-clocks.md) §23.5.4。

> 📌 还有一个只影响老内核的历史坑，原书也写明了：**Linux 2.4 及更早**，`nanosleep()` 进程被 `SIGSTOP` 停住再 `SIGCONT` 恢复后，**停在 stopped 状态的那段时间不计入睡眠**（于是睡得比预期久）；**Linux 2.6 起**改为「自动恢复且把 stopped 时间计入」。

## 完整源码（Listing 23-3）

**实现**：`code/t_nanosleep.c`，逐行取自 man7 官方 `timers/t_nanosleep.c`（Listing 23-3，原书 page 490–491）。

[`code/t_nanosleep.c`](../code/t_nanosleep.c)

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* t_nanosleep.c

   Demonstrate the use of nanosleep() to sleep for an interval
   specified in nanoseconds.

   See also t_clock_nanosleep.c.
*/
#define _POSIX_C_SOURCE 199309
#include <sys/time.h>
#include <time.h>
#include <signal.h>
#include "tlpi_hdr.h"

static void
sigintHandler(int sig)
{
    return;                     /* Just interrupt nanosleep() */
}

int
main(int argc, char *argv[])
{
    struct timeval start, finish;
    struct timespec request, remain;
    struct sigaction sa;
    int s;

    if (argc != 3 || strcmp(argv[1], "--help") == 0)
        usageErr("%s secs nanosecs\n", argv[0]);

    request.tv_sec = getLong(argv[1], 0, "secs");
    request.tv_nsec = getLong(argv[2], 0, "nanosecs");

    /* Allow SIGINT handler to interrupt nanosleep() */

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sa.sa_handler = sigintHandler;
    if (sigaction(SIGINT, &sa, NULL) == -1)
        errExit("sigaction");

    if (gettimeofday(&start, NULL) == -1)
        errExit("gettimeofday");

    for (;;) {
        s = nanosleep(&request, &remain);
        if (s == -1 && errno != EINTR)
            errExit("nanosleep");

        if (gettimeofday(&finish, NULL) == -1)
            errExit("gettimeofday");
        printf("Slept for: %9.6f secs\n", finish.tv_sec - start.tv_sec +
                        (finish.tv_usec - start.tv_usec) / 1000000.0);

        if (s == 0)
            break;                      /* nanosleep() completed */

        printf("Remaining: %2ld.%09ld\n", (long) remain.tv_sec, remain.tv_nsec);
        request = remain;               /* Next sleep is with remaining time */
    }

    printf("Sleep complete\n");
    exit(EXIT_SUCCESS);
}
```

编译（`code/` 目录下）：

```bash
gcc -O0 -Wall -Wextra -o t_nanosleep t_nanosleep.c get_num.c
```

> ⚠️ 依赖 `lib/tlpi_hdr.h` 与 `lib/get_num.c`；本仓库用 `code/tlpi_hdr.h` 替身（差异见 [`code/README.md`](../code/README.md)），故命令行要带上 `get_num.c`。

程序结构就三段：

1. 装一个**只 `return`** 的 `SIGINT` 处理器 —— 目的仅仅是「让 `nanosleep()` 能被 `Ctrl-C` 打断」；
2. `for (;;)` 循环：睡 → 打印累计睡了多少 → 若 `s == 0` 就 `break`，否则打印 `remain` 并**用剩余时间续睡**（`request = remain;`）；
3. 循环结束后打印 `Sleep complete`。

```text
Slept for:  1.000071 secs
Sleep complete
```

## CE 实测：睡 1.5 秒

```text
Slept for:  1.500096 secs
Sleep complete
```

两行一起读：

| 请求 | 实测 | 超出 | 说明 |
|------|------|------|------|
| `1 0`（1 秒） | `1.000071 secs` | **+71 µs** | 一次睡满，没被打断（`s == 0` 直接 `break`） |
| `1 500000000`（1.5 秒） | `1.500096 secs` | **+96 µs** | 同上 |

三点：

- **`Sleep complete` 出现 = 循环正常退出**，说明这一轮 `nanosleep()` 返回了 `0`（睡满，没被 `EINTR` 打断）。CE 的执行器不会给进程发 `SIGINT`，所以本页看不到 `Remaining:` 那一行走进现实中。
- **超出量是几十微秒**，不是 jiffy（1 ms）量级 ⇒ 这台机器的 HRT 在起作用（见 §23.2 实测 `clock_getres` = 1 ns）。
- 打印格式是 `%9.6f`，所以是 ` 1.000071`（前面补空格到 9 位宽）；**这个宽度会在 §23.5 的 `t_clock_nanosleep`（`%.6f`）里变成不带补空格**，两处对比着看很直观。

> ⚠️ **诚实标注**：CE 环境下无法向进程发 `SIGINT`，所以本页**没有** `Remaining: <n>.<nnnnnnnnn>` 那两行的实测。书里给的示例（`$ ./t_nanosleep 10 0` 然后连按三次 `Ctrl-C`）需要**真终端**。要看「剩余时间续睡」的实际输出，本仓库的做法是用 §23.5 的 `TIMER_ABSTIME` 版本做对照 —— 那一版**不需要** `remain` 续睡，正好把「有没有 `remain` 这条路」的差别摆出来。

## `sleep()` vs `nanosleep()` vs `clock_nanosleep()` 速查

| 维度 | `sleep()` | `nanosleep()` | `clock_nanosleep()` |
|------|-----------|---------------|---------------------|
| 头文件 / 原型 | `<unistd.h>` | `<time.h>` | `<time.h>` |
| 参数单位 | 秒 | `timespec`（ns） | `timespec`（ns） |
| 返回风格 | **`unsigned int`**（剩余秒） | `0` / `-1` + `errno` | **`0` 或正数错误码**（不用 `errno`） |
| 被打断时 | 返回剩余**秒**（粒度粗） | 返回 `-1`/`EINTR`，`remain` 给**剩余时间** | 返回 `EINTR`（**注意：不是 -1**） |
| 能否混合 `alarm()` | SUSv3 未规定；**老实现会打架** | ✅ 明确规定不用信号实现 | ✅ |
| 绝对时刻睡眠 | ❌ | ❌ | ✅ `TIMER_ABSTIME` |
| 选哪个时钟 | 不可选 | 不可选（隐含 `CLOCK_REALTIME`？—— 实现对 `remain` 的语义是「相对」） | ✅ `clockid` 可选 |
| 标准 | SUSv3 | SUSv3（`_POSIX_C_SOURCE 199309`） | `_XOPEN_SOURCE 600`（Linux 专有实现，2.6 起） |
| 本页实测 | —— | `1.000071` / `1.500096` | 见 [23.5](23.5-posix-clocks.md)：`1.000071` / `1.000051` |

> ⭐ 最后一行那个**返回值风格差异**是真正的坑：`nanosleep()` 失败返回 `-1` 并把错误码放 `errno`；`clock_nanosleep()` **直接返回错误码**（正数），像 `pthread_*` 一样。所以 `if (clock_nanosleep(...) == -1)` 是**错的**，要写 `if (s != 0)`。`t_clock_nanosleep.c` 里那句 `if (s != 0 && s != EINTR) errExitEN(s, "clock_nanosleep");` 就是在正确处理这一点。

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 以为 `sleep()` 的返回值是「实际睡了多少秒」 | 是「**还剩**多少秒」；睡满才是 0 |
| 2 | 在高精度需求下用 `sleep()` | 它只有秒级参数，且老实现粒度是整秒 |
| 3 | 用 `nanosleep()` 的 `remain` 循环续睡，却忘了每轮会被向上取整 | 信号一密集就**永远睡不完**（原书原文点名的问题）；改用 `clock_nanosleep(TIMER_ABSTIME)` |
| 4 | `request.tv_nsec` 写 ≥ 1000000000 | `nanosleep()` 直接返回 `EINVAL`。要自己进位到 `tv_sec`（`t_clock_nanosleep.c` 里就有这段进位代码） |
| 5 | 把 `tv_nsec` 当 `long` 无所谓 | 是 `long`；但某些平台的 `time_t` 宽度不同，跨平台别假设 |
| 6 | 以为 `nanosleep()` 不可被打断 | 会被信号打断，返回 `-1`/`EINTR`；不处理就会提前结束睡眠 |
| 7 | 混用 `sleep()` 与 `alarm()` | Linux 上没事，**移植到老 libc 就出事**；可移植代码不要混 |
| 8 | 靠 `sleep()` 做精确定时循环 | 见 §23.2：`sleep` 循环会**累积漂移**；用周期定时器或 `TIMER_ABSTIME` |
| 9 | 以为「睡 1 秒」就是 1.000000 秒 | 实测 +71~96 µs；「至少这么久」是保证，「不会更久」不是 |
| 10 | 在多线程程序里用 `sleep()` 做同步 | `sleep()` 睡的是**整个进程**吗？不 —— `nanosleep()` 睡的是**调用线程**。要线程级等待用条件变量/`futex`，别用睡眠当同步 |

## HFT / 嵌入式关联

| 路线 | 结论怎么用 |
|------|-----------|
| **HFT** | ① **绝对不要用睡眠做同步** —— 「睡一会儿再看」是竞态之源。要在某个**绝对时刻**动手就用 `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`（§23.5.4）：它按绝对时刻睡，中途被打断后**重算剩余**而不是拿老 `remain` 续睡，天然免疫「向上取整导致永远睡不完」。② 不要 `sleep()` 轮询行情 —— 用 `epoll_wait` 的超时参数，一次调用同时等数据与等超时。③ 节流（rate limit）用 `CLOCK_MONOTONIC` 而非 `CLOCK_REALTIME`，避免 NTP 阶跃把节流窗口错位。 |
| **嵌入式** | ① **目标板上的 `sleep()` 实现要查清楚**：如果是 `alarm()` 版，那么「看门狗喂狗 `sleep()` + 业务 `alarm()`」这种组合必然互踩。② `nanosleep()` 的 `tv_nsec` 精度在**无 HRT** 的内核上就是 jiffy（HZ=100 时 10 ms）—— 用 10 µs 去 `nanosleep` 会实际睡 10 ms，低功耗任务的实际占空比会比你算的大得多。③ 低功耗等待优先用**中断唤醒 + 定时器兜底**，而不是纯 `sleep`；纯 sleep 期间 CPU 不省电（只是不干活），要把 tickless/`NO_HZ_IDLE` 打开才真省。④ `sleep()` 会返回剩余秒数是**迁就老实现**的接口设计，写驱动时别依赖「打断后剩余时间的精度」。 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`sleep()` 返回 3，是什么意思？**

A：进程原计划睡 n 秒，但被某个信号处理器打断了，**还剩 3 秒没睡**。要不要再睡一次由你决定 —— 直接重试 `sleep(3)` 会引入漂移（见 §23.2），正确做法是算出目标绝对时刻再睡到那时。

**Q2：为什么说 `nanosleep()` 比 `sleep()` 更适合和 `alarm()` 混用？**

A：因为 SUSv3 **明确规定 `nanosleep()` 不得用信号实现**，所以它和 `alarm()`/`setitimer()` 用的 `ITIMER_REAL` 是两套独立机制，可以可移植地共存。而 `sleep()` 在老实现里**就是** `alarm()` + `SIGALRM` 处理器，混用会互相覆盖 —— SUSv3 对这一点「未规定」（unspecified），等于不做任何保证。

**Q3：`nanosleep()` 用 `remain` 续睡为什么会「永远睡不完」？**

A：因为每次重启都要**向上取整到软件时钟粒度**（jiffy）。假设 jiffy = 4 ms，`remain` 每次返回一个不是 4 ms 整数倍的值（比如 8.1466 ms），内核会向上取整到 12 ms 才触发。如果信号来得比 jiffy 还密（每次都在新的一轮里打断你），那么「剩余时间」永远不会归零，循环永不退出。解药是 `clock_nanosleep(TIMER_ABSTIME)`：请求的是**绝对时刻**，每次重启只是「睡到那个时刻」，不存在累积的取整误差。

**Q4：书里说「`tv_nsec` must be a number in the range 0 to 999,999,999」。如果我不小心传了 1500000000 会怎样？**

A：`nanosleep()` 会失败，返回 `-1` 且 `errno = EINVAL`。内核**不会**帮你把 1.5 秒拆成 `tv_sec=1, tv_nsec=500000000`。要自己进位 —— `t_clock_nanosleep.c` 里就有一段标准的进位写法：

```c
request.tv_sec  += getLong(argv[1], 0, "secs");
request.tv_nsec += getLong(argv[2], 0, "nanosecs");
if (request.tv_nsec >= 1000000000) {
    request.tv_sec += request.tv_nsec / 1000000000;
    request.tv_nsec %= 1000000000;
}
```

**Q5：本页 CE 实测里为什么看不到 `Remaining:` 那一行？**

A：因为那一行只在 `nanosleep()` **被信号打断**（`s == -1 && errno == EINTR`）时才打印。CE 的执行器不会向被测进程发 `SIGINT`，所以 `nanosleep()` 每次都睡满、返回 `0`，循环直接 `break`。要复现书里的输出需要一个**真终端**，手动连按 `Ctrl-C`。

**Q6：`nanosleep()` 睡的是「进程」还是「线程」？**

A：**调用线程**。这是它和 `sleep()` 的一个重要差别 —— `sleep()` 在 POSIX 里早期语义是整个进程，而 `nanosleep()` 明确是线程级的。多线程程序里用睡眠做同步本身就是设计错误，但至少要知道睡的是哪一个，否则调试时会被「为什么其他线程没停」搞晕。
