## 原书 §23.8 全文要点

> A process can use `setitimer()` or `alarm()` to set a timer, so that it receives a signal after the passage of a specified amount of real or process time. One use of timers is to **set an upper limit on the time for which a system call can block**.
>
> Applications that need to **suspend execution for a specified interval of real time** can use a variety of sleep functions for this purpose.
>
> Linux 2.6 implements the POSIX.1b extensions that define an API for **high-precision clocks and timers**. POSIX.1b timers provide a number of advantages over traditional (`setitimer()`) UNIX timers. We can: **create multiple timers**; **choose the signal** that is delivered on timer expiration; **retrieve the timer overrun count** in order to determine if a timer has expired multiple times since the last expiration notification; and **choose to receive timer notifications via execution of a thread function** instead of delivery of a signal.
>
> The Linux-specific `timerfd` API provides a set of interfaces for creating timers that is similar to the POSIX timers API, but allows timer notifications to be **read via a file descriptor**. This file descriptor can be monitored using `select()`, `poll()`, and `epoll`.

一句话提炼：**本章是一条「从最弱到最强」的演进线**，每一步都是被前一步的缺陷逼出来的：

```
alarm()/setitimer()  ──4 个硬伤──▶  POSIX 定时器（多实例 / 换信号 / overrun / 纳秒）
                                        │
                            信号通知的异步上下文问题
                            overrun 要「收到后立刻读」的时序问题
                                        ▼
                                    timerfd（fd 可读 / read 直接拿计数）
```

## 2. ⭐ 「取整方向」总表（本章最容易记错的一组事实）

| 场景 | 取整方向 | 为什么 |
|------|---------|--------|
| `clock_settime()` 传入非分辨率整数倍 | **向下** | 「设置时间」要尽量接近你要的值，不能凭空往未来推 |
| `setitimer()` / `timer_settime()` / `timerfd_settime()` 传非分辨率整数倍 | **向上** | 「定时器」承诺「**至少**等这么久」，提前触发会破坏语义 |
| `alarm()` 的**返回值**（剩余时间） | **向上**（≥ 0.5 s 时进位） | 内核注释原话：*we'd better return too much than too little* |
| 「裸 `setitimer()` 读 `old.it_value.tv_sec`」 | 截断 | 只是取字段，没有额外逻辑 |
| `nanosleep()` 用 `remain` 续睡的每一轮 | **向上** | ⇒ 这就是「信号密集时永远睡不完」的根因 |

## 7. ⭐ 本章给工程决策的三条结论

1. **不要用信号做定时。** 信号处理器只能调 async-signal-safe 函数，而定时器天然高频 —— 这两件事冲突。要「同步处理定时事件」就用 `sigwaitinfo()`（§23.9 习题 23-4）或 `signalfd`。
2. **要「等 I/O + 等定时」一起等，就用 `timerfd`。** 把定时器变成 fd 是 Linux 给事件循环最好的礼物 —— 主循环只有一个 `epoll_wait`，没有异步上下文，没有 `overrun` 时序陷阱。代价是 **Linux 专有（≥ 2.6.25）**。
3. **时间基准一律选对。** 量「过了多久」用 `CLOCK_MONOTONIC`；要「绝对时刻对齐」用 `CLOCK_REALTIME`（跨机）/`CLOCK_TAI`（避闰秒）；要「完全不受 NTP 影响」用 `CLOCK_MONOTONIC_RAW`；**只有 `CLOCK_REALTIME` 可以被设置**。选错时钟是本章最隐蔽的一类 bug —— 代码能跑，只在 NTP 阶跃/闰秒/suspend 的那一刻出错。

<details>
<summary>代码自测（Q&A）</summary>

**Q1：一句话说清「本章四个 API 该选哪个」。**

A：按需求选：
- **只想给一个阻塞调用加超时，且不能改那段代码** ⇒ `alarm()` + `SIGALRM`（§23.3），注意竞态与 `SA_RESTART`。
- **只想睡一会儿** ⇒ `nanosleep()`；**要睡到某个绝对时刻、且不怕信号干扰** ⇒ `clock_nanosleep(TIMER_ABSTIME)`。
- **要多个定时器、要精确控制通知方式** ⇒ POSIX 定时器（§23.6）；**但高频/多路复用场景不要用它**。
- **程序有事件循环（`epoll`/`poll`），或要同时等 I/O 与定时** ⇒ **`timerfd`**（§23.7）。**这是最优先的选项。**

**Q2：本章哪一条最容易在真实项目里造成难以复现的 bug？**

A：三选一，都很难查：
1. **选错时钟** —— `CLOCK_REALTIME` 做周期任务，只在 NTP 阶跃/闰秒/suspend 那一刻出错；
2. **忘记 `alarm(0)`** —— 残留定时器在之后某段无关代码里打断别的系统调用（§23.3）；
3. **忽略 `overrun`** —— 定时器实际到期 1000 次，代码以为是 1 次（§23.6.6）。这类 bug 只在「信号被阻塞」或「处理器很慢」时浮现。

**Q3：为什么说「`timerfd` 是 HFT 的默认选择」？**

A：因为它把定时器**归一成 fd 事件**，从而同时消除了三个问题：(a) 异步信号上下文不能随便调函数的限制；(b) `overrun` 必须「收到信号后立刻读」的时序约束（`read()` 直接给计数，读走即清零）；(c) 「等 I/O」与「等定时」被迫分成两个等待点的结构问题。代价是 `fork` 语义（父子共享同一定时器）和 Linux 专有性。

**Q4：`alarm(5)` 之后 4.699919 秒调 `alarm(0)` 返回 5 —— 那 `sleep(5)` 被信号打断时返回什么？**

A：返回**剩余的整秒数**（`sleep()` 的接口就是整秒粒度）。按内核 `alarm_setitimer()` 的逻辑，剩余 4.699919 秒会返回 **5**（向上取整）。这解释了为什么 `sleep()` 的返回值不能当「精确剩余时间」用 —— 它只有秒的粒度，而且是**向上**取整的（§23.9 习题 23-1 有完整实测）。（⚠️ 这是「把同一族的取整规则外推」得到的结论，本仓库没有单独实测 `sleep()` 的返回值；要看精确剩余应该用 `nanosleep()` 的 `remain` 或 `getitimer()`。）

**Q5：为什么本仓库要在笔记里标注「本条是采集到的、不是程序产生的」？**

A：因为 CE 的执行环境有**硬上限**（20 秒 SIGKILL、约 32 KB 输出采集上限、8 KB 全缓冲）。这些上限会让「行数」「通知次数」这类计数**小于**程序真实产生的量。不标注的话，读者会拿笔记里的数字去核程序行为，得出错误结论。**诚实标注实测环境的边界，本身就是笔记质量的一部分。**
