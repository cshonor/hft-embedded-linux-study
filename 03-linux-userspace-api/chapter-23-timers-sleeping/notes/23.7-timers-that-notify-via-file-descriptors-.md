## 本节讲什么

前面讲的三种定时器通知方式（信号、`sigwaitinfo`、线程）都有一个共同的结构性问题：**它们都不是「文件描述符」**。所以在一个已经用 `epoll` 管着一堆 fd 的程序里，定时器是个**异构的**东西 —— 你得额外开一个线程去 `sigwaitinfo()`，或者被迫在信号处理器里干活。

`timerfd` 的价值就一句话：**把「定时器到期」变成一个 fd 的「可读」事件。**

原书原文：

> Starting with kernel **2.6.25**, Linux provides another API for creating timers. The Linux-specific `timerfd` API creates a timer whose expiration notifications can be **read from a file descriptor**. This is useful because the file descriptor can be **monitored along with other descriptors using `select()`, `poll()`, and `epoll`**. (With the other timer APIs discussed in this chapter, it requires some effort to be able to simultaneously monitor one or more timers along with a set of file descriptors.)

本节钉五件事：

1. 三个系统调用与 POSIX 定时器的**一一对应**关系；
2. `read()` 读到的不是「数据」，而是**到期次数**（`uint64_t`）—— 这天然解决了 §23.6.6 的 overrun 问题；
3. 可选时钟只有两个：`CLOCK_REALTIME` / `CLOCK_MONOTONIC`；
4. `fork`/`exec` 的语义与 POSIX 定时器**不同**（fd 是继承并保留的）；
5. ⭐ **实测**：怎么用一个「1 微秒间隔」的定时器把 overrun 逼出来（`expirations read: 47`）。

## 1. 三个系统调用

| `timerfd` | 对应 POSIX 定时器 | 作用 |
|-----------|------------------|------|
| `timerfd_create()` | `timer_create()` | 创建定时器，返回 **fd** |
| `timerfd_settime()` | `timer_settime()` | 武装 / 解除武装 |
| `timerfd_gettime()` | `timer_gettime()` | 查询当前设置 |
| （`close()`） | `timer_delete()` | ⭐ **删除定时器就是关 fd** —— 不需要单独的 delete 调用 |

```c
#include <sys/timerfd.h>

int timerfd_create(int clockid, int flags);
int timerfd_settime(int fd, int flags,
                    const struct itimerspec *new_value,
                    struct itimerspec *old_value);
int timerfd_gettime(int fd, struct itimerspec *curr_value);
```

### `timerfd_create()` 的 `clockid` 与 `flags`

原书原文：

> The value of `clockid` can be either **`CLOCK_REALTIME`** or **`CLOCK_MONOTONIC`** (see Table 23-1).

⚠️ 注意范围比 POSIX 定时器**窄得多**：不能填 `CLOCK_PROCESS_CPUTIME_ID` 之类的 CPU 时钟，也不能填从那两个 `*_getcpuclockid()` 拿到的 ID。

`flags` 在最初的实现里必须为 0，**Linux 2.6.27 起**支持两个：

| flag | 作用 | 为什么有用 |
|------|------|-----------|
| `TFD_CLOEXEC` | 给新 fd 设 `FD_CLOEXEC` | 与 `open(O_CLOEXEC)` 同理：防 `exec` 后泄漏到子程序 |
| `TFD_NONBLOCK` | 给底层 open file description 设 `O_NONBLOCK` | 省掉一次 `fcntl()`；非阻塞读在没有到期时返回 `EAGAIN` |

### `timerfd_settime()` 的 `flags`

原书原文：

> It may either be 0, meaning that `new_value.it_value` is interpreted **relative** to the time of the call to `timerfd_settime()`, or it can be **`TFD_TIMER_ABSTIME`**, meaning that `new_value.it_value` is interpreted as an **absolute time** (i.e., measured from the clock's zero point).

和 `timer_settime()` 的 `TIMER_ABSTIME` 是同一个概念，**只是宏名不同**（`TFD_TIMER_ABSTIME`）。这一点很容易写错。

### `timerfd_gettime()` 与「武装状态」的判定

原书原文：

> The `curr_value.it_value` field returns the time until the next timer expiration, **even if this timer was established as an absolute timer using `TFD_TIMER_ABSTIME`**. If both fields of the returned `curr_value.it_value` structure are 0, then the timer is currently **disarmed**. If both fields of the returned `curr_value.it_interval` structure are 0, then the timer expires **just once**, at the time given in `curr_value.it_value`.

这和 `timer_gettime()` 的读法完全一样（包括「绝对武装也返回相对剩余」这个容易被忘掉的性质）。

## 2. ⭐ `read()` 读到的是「到期次数」

这是 `timerfd` 最漂亮的设计。原书原文：

> Once we have armed a timer with `timerfd_settime()`, we can use `read()` to read information about timer expirations from the associated file descriptor. For this purpose, the buffer given to `read()` must be large enough to hold an **unsigned 8-byte integer (`uint64_t`)**.
>
> If one or more expirations have occurred since the timer settings were last modified using `timerfd_settime()` **or the last `read()` was performed**, then `read()` returns **immediately**, and the returned buffer contains **the number of expirations that have occurred**. If **no** timer expirations have occurred, then `read()` **blocks until the next expiration occurs**. It is also possible to use the `fcntl()` `F_SETFL` operation... to set the `O_NONBLOCK` flag..., so that reads are nonblocking, and will fail with the error **`EAGAIN`** if no timer expirations have occurred.

用一张表把语义钉死：

| 情形 | `read()` 的行为 | 返回值 |
|------|----------------|--------|
| 上次 `read()`（或 `timerfd_settime()`）之后有 N 次到期 | **立即返回** | `uint64_t` 里是 **N** |
| 无到期且阻塞模式 | **阻塞到下次到期** | 之后返回到期次数 |
| 无到期且 `O_NONBLOCK` | 立即失败 | `-1` / `errno = EAGAIN` |
| **读完之后**再读（无新到期） | 阻塞 / `EAGAIN` | —— |

> ⭐ **「读到计数」为什么比 §23.6.6 的 overrun 机制更干净？**
>
> - `SIGEV_SIGNAL`：内核只保留**一个** pending 信号 ⇒ 1000 次到期你只能知道 `overrun = 999`，而且**必须在收到信号后立刻读**，否则被重置。
> - `timerfd`：`read()` 直接把**计数**交给你，**读走即清零**，不需要 overrun 字段，也不会因为「只送一个信号」而丢信息。多路复用场景下还能 `epoll` 一次性拿到。
>
> 本页实测里 `timerfd_overrun` 读出了 `expirations read: 47` 这样的数字 —— 这是 `SIGEV_SIGNAL` 那条路**结构上给不出**的粒度。

## 3. `fork` / `exec` 的语义（与 POSIX 定时器相反！）

原书原文：

> **During a `fork()`, a child process inherits copies of file descriptors created by `timerfd_create()`. These file descriptors refer to the same timer objects as the corresponding descriptors in the parent, and timer expirations can be read in either process.**
>
> File descriptors created by `timerfd_create()` are **preserved across an `exec()`** (unless the descriptors are marked close-on-exec...), and **armed timers will continue to generate timer expirations after the `exec()`**.

和 §23.6 的 POSIX 定时器对照：

| 事件 | POSIX 定时器（§23.6） | `timerfd`（本节） |
|------|---------------------|------------------|
| `fork()` | **不继承**（子进程一个都没有） | ✅ **fd 被继承**，父子**指向同一个定时器对象**，任一方都能读到期 |
| `exec()` | **被解除武装并删除** | ✅ **保留**（除 `TFD_CLOEXEC`），武装状态延续 |
| 删除 | `timer_delete()` | `close()` |

> ⚠️ 「`exec` 后仍然保留」这一条是把双刃剑：它让「`exec` 重启自己」的程序**不会丢掉定时器**（这正是 `TFD_CLOEXEC` 存在的意义 —— 不想要就显式关掉），但也意味着**新程序会继承一个自己不知道的定时器**。写 `exec` 链式启动（shell、supervisor、`systemd` 风格）时必须显式处理。

> ⭐ 另外，`fork` 之后**父子都能读同一个定时器**，这就带来一个竞态：谁读到谁就把计数清零了。原书没有展开，但实践上应当**明确只有一个读者**（比如父进程读，子进程只管自己的事）。

```c
/* demo_timerfd.c

   Demonstrate the use of the timerfd API, which creates timers whose
   expirations can be read via a file descriptor.

   This program is Linux-specific. The timerfd API is supported since kernel
   2.6.25. Library support is provided since glibc 2.8.
*/
#include <sys/timerfd.h>
#include <time.h>
#include <stdint.h>                     /* Definition of uint64_t */
#include "itimerspec_from_str.h"        /* Declares itimerspecFromStr() */
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    struct itimerspec ts;
    struct timespec start, now;
    int fd, secs, nanosecs;
    uint64_t numExp, totalExp, maxExp;
    ssize_t s;

    if (argc < 2 || strcmp(argv[1], "--help") == 0)
        usageErr("%s secs[/nsecs][:int-secs[/int-nsecs]] [max-exp]\n", argv[0]);

    itimerspecFromStr(argv[1], &ts);
    maxExp = (argc > 2) ? getInt(argv[2], GN_GT_0, "max-exp") : 1;

    fd = timerfd_create(CLOCK_REALTIME, 0);
    if (fd == -1)
        errExit("timerfd_create");

    if (timerfd_settime(fd, 0, &ts, NULL) == -1)
        errExit("timerfd_settime");

    if (clock_gettime(CLOCK_MONOTONIC, &start) == -1)
        errExit("clock_gettime");

    for (totalExp = 0; totalExp < maxExp;) {

        /* Read number of expirations on the timer, and then display
           time elapsed since timer was started, followed by number
           of expirations read and total expirations so far. */

        s = read(fd, &numExp, sizeof(uint64_t));
        if (s != sizeof(uint64_t))
            errExit("read");

        totalExp += numExp;

        if (clock_gettime(CLOCK_MONOTONIC, &now) == -1)
            errExit("clock_gettime");

        secs = now.tv_sec - start.tv_sec;
        nanosecs = now.tv_nsec - start.tv_nsec;
        if (nanosecs < 0) {
            secs--;
            nanosecs += 1000000000;
        }

        printf("%d.%03d: expirations read: %llu; total=%llu\n",
                secs, (nanosecs + 500000) / 1000000,
                (unsigned long long) numExp, (unsigned long long) totalExp);
    }

    exit(EXIT_SUCCESS);
}
```

编译（`code/` 目录下）：

```bash
gcc -O0 -Wall -Wextra -o demo_timerfd demo_timerfd.c itimerspec_from_str.c get_num.c
```

用法：`demo_timerfd secs[/nsecs][:int-secs[/int-nsecs]] [max-exp]`（第 2 个参数默认 1）。

程序结构：

| 片段 | 作用 |
|------|------|
| `fd = timerfd_create(CLOCK_REALTIME, 0);` | 只用 `CLOCK_REALTIME`，`flags = 0` |
| `timerfd_settime(fd, 0, &ts, NULL);` | `flags = 0` ⇒ **相对**武装 |
| `clock_gettime(CLOCK_MONOTONIC, &start);` | 基准时刻用 **`CLOCK_MONOTONIC`** |
| `s = read(fd, &numExp, sizeof(uint64_t));` | ⭐ **读 8 字节** —— 读到的不是字符串，是**到期次数** |
| `totalExp += numExp;` | 累加到期总数，`totalExp >= maxExp` 才退出 |
| `printf("%d.%03d: expirations read: %llu; total=%llu\n", ...)` | 打印「自启动以来的 `秒.毫秒`」+ 本次读到的次数 + 累计次数 |

> 📌 **注意一个「混用两种时钟」的细节**：**定时器**用 `CLOCK_REALTIME`（因为它是书里演示顺手的写法），**耗时测量**却用 `CLOCK_MONOTONIC`（`start` / `now`）。这是**正确**的做法 —— 用 `CLOCK_MONOTONIC` 量「过了多久」才不会被 NTP 阶跃污染（§23.5）。但也就意味着打印出来的 `秒.毫秒` 是**单调时钟口径**，不是墙钟。

> 📌 **与书里印刷版的一处差异（源码核验）**：书上 Listing 23-8 的局部变量声明是
> `int maxExp, fd, secs, nanosecs;`
> 而 man7 当前分发版是
> `int fd, secs, nanosecs; uint64_t numExp, totalExp, maxExp;`
> 也就是**把 `maxExp` 提到了 `uint64_t`**。这处改动是必要的：`printf` 里 `numExp`/`totalExp` 用的是 `%llu`，而 `maxExp` 参与 `totalExp < maxExp` 的比较 —— 用 `int` 会在超大 `max-exp` 或累加溢出时出错。**当前版更正确。**

## CE 实测 ①：正常周期（`0/500000000:0/500000000 4`）

500 ms 后首次，之后每 500 ms，收满 4 次到期就退出。

```text
0.500: expirations read: 1; total=1
1.000: expirations read: 1; total=2
1.500: expirations read: 1; total=3
2.000: expirations read: 1; total=4
```

读法：

| 行 | 含义 |
|----|------|
| `0.500: expirations read: 1; total=1` | 睡了 500 ms 后第一次到期 ⇒ 读到 **1 次**（这一轮只有 1 次到期） |
| `1.000: expirations read: 1; total=2` | 再过 500 ms，又只有 1 次 ⇒ `total` 累加到 2 |
| `1.500 / 2.000` | 同上，最后 `total=4 == maxExp` ⇒ `exit(EXIT_SUCCESS)` |

**关键点：`expirations read` 全是 `1`。** 因为「read + clock_gettime + printf」这一轮的开销（微秒级）远小于 500 ms 的周期 ⇒ 每次 `read()` 时**恰好只累积了一次到期**。程序能**正常退出**（本章少数几个能自己结束的程序之一）。

## CE 实测 ②：用 1 微秒间隔把 overrun 逼出来（`1/0:0/1000 100`）

1 秒后首次，之后**每 1 微秒**一次 —— 这个间隔远小于「read + `clock_gettime` + `printf`」的轮转耗时。

```text
1.000: expirations read: 16; total=16
1.000: expirations read: 47; total=63
1.000: expirations read: 7; total=70
1.000: expirations read: 7; total=77
1.000: expirations read: 7; total=84
1.000: expirations read: 7; total=91
1.000: expirations read: 6; total=97
1.000: expirations read: 7; total=104
```

**这就是「log 里读到的数字 > 1」的实测证据：**

| 行 | `expirations read` | 读法 |
|----|-------------------|------|
| `1.000: expirations read: 16; total=16` | **16** | 首次到期在 1 秒；从「武装」到「第一次 `read` 返回」之间已经积累了 16 次到期 |
| `1.000: expirations read: 47; total=63` | **47** | 同一毫秒内第二次读 —— 我这次 `read()` 返回前又积了 47 次（1 µs 周期 ⇒ 50 µs 的轮转就是 50 次） |
| `...: expirations read: 7; total=70` | 7 | 之后稳定在 6~7 —— 说明每轮 `read → clock_gettime → printf` 大约耗时 **6~7 微秒** |
| `1.000: expirations read: 6; total=97` | 6 | 同上 |

三点收获：

1. **`timerfd` 不丢到期** —— 到期累计在 fd 的计数里，`read()` 一次性取走。多次到期被**合并成一个数字**，而不是像 `SIGEV_SIGNAL` 那样只留一个信号（§23.6.6）。
2. **`total=104` 说明 100 次到期的上限被越过** —— 因为 `maxExp` 是「累计到期数」的判据，而单次 `read()` 可能一次就带回 47 次 ⇒ 循环条件 `totalExp < maxExp` 会在超过后退出（这是原书程序本身的性质，不是 bug，但要知道它**不是**「精确读 100 次」）。
3. **`printf` 的 `%d.%03d` 全打在 `1.000`** —— 因为整个 100 次到期全发生在 1 秒那一瞬间完成的；后续的 `秒.毫秒` 保持 `1.000` 说明这 8 次 `read()` 都在同一毫秒内完成。

> ⭐ 这一条实测顺带给出了「**`timerfd` 也不解决调度延迟**」的证据：定时器每 1 µs 到期，但你的进程每 6~7 µs 才能轮一次 `read`。**定时器能表达的精度 ≠ 你的代码能响应的精度**（§23.2 的结论在这里再次出现）。

## 5. 三种定时器 API 横向对比

| 维度 | `setitimer`（§23.1） | POSIX 定时器（§23.6） | `timerfd`（本节） |
|------|---------------------|---------------------|------------------|
| 实例数 | **每种 `which` 一个** | 多个（受 realtime 信号上限约束） | **多个（受 fd 数量约束）** |
| 通知方式 | 只能信号（且不可换） | `NONE`/`SIGNAL`/`THREAD`/`THREAD_ID` | **fd 可读**（可 `select`/`poll`/`epoll`） |
| 能进 `epoll` | ❌ | ❌ | ✅ **这是它的全部价值** |
| 多次到期的表达 | 丢掉，无法知道 | `overrun` 计数（收到信号后必须立刻读） | **`read()` 直接返回计数** |
| 可选时钟 | 只有 `ITIMER_REAL` 走墙钟 | 任意 POSIX 时钟 | **只有 `CLOCK_REALTIME` / `CLOCK_MONOTONIC`** |
| 绝对时刻武装 | ❌ | ✅ `TIMER_ABSTIME` | ✅ `TFD_TIMER_ABSTIME` |
| 精度上限 | 微秒表示，受 jiffy/HRT | 纳秒表示，受 jiffy/HRT | 纳秒表示，受 jiffy/HRT |
| `fork` 继承 | ❌ | ❌ | ✅ **fd 继承，指向同一对象** |
| `exec` 后 | 保留 | 被清除 | **保留**（除 `TFD_CLOEXEC`） |
| 信号安全 | 处理器限制多 | 处理器限制多 | ✅ **无异步上下文**，代码随便写 |
| 跨平台 | ✅ POSIX | ✅ POSIX | ❌ **Linux 专有（≥ 2.6.25）** |
| glibc 支持 | —— | —— | ≥ 2.8 |

> ⭐ 最后两行是选型的关键：`timerfd` 是 **Linux 专有**的。要跨平台（含 macOS/BSD）就必须留一条 `SIGEV_SIGNAL`/`kqueue` 的退路 —— 这也是原书虽然把 `timerfd` 放在最后讲、却在总结里给它很高评价的原因。

## 常见坑

| # | 坑 | 正解 |
|---|----|------|
| 1 | 只 `close(fd)` 就以为「定时器停了」 | `close()` 确实会释放定时器（kref 归零时），但**如果 fd 被 `fork`/`dup` 多处共享**，只有**所有**引用都关闭后才真正释放 |
| 2 | 读缓冲给小了（比如 `int`） | 必须是 **`uint64_t`（8 字节）**；`read` 返回的不是 8 会报错（`demo_timerfd.c` 里 `if (s != sizeof(uint64_t)) errExit("read")` 就是在防这个） |
| 3 | 以为 `read()` 返回的是「距下次到期的时间」 | 返回的是**上次读之后的到期次数** |
| 4 | 用 `TIMER_ABSTIME` 而不是 `TFD_TIMER_ABSTIME` | **宏名不同**：`timerfd_settime()` 用 `TFD_TIMER_ABSTIME` |
| 5 | `clockid` 填 `CLOCK_PROCESS_CPUTIME_ID` | 不支持，只有 `CLOCK_REALTIME` / `CLOCK_MONOTONIC` |
| 6 | 忽略 `read()` 可能一次带回多次到期 | 计数要**累加**（`totalExp += numExp`），不能假设每次都是 1 |
| 7 | 用 `fd` 当「一次性事件」 | 它是**水平触发**的语义：计数没读走就一直可读；读完清零。`epoll` 里用水平触发（LT）最自然 |
| 8 | `fork` 后父子都去 `read()` | 谁读谁清零 ⇒ **明确只有一个读者** |
| 9 | `exec` 后忘了新程序会继承定时器 | 不想要就加 `TFD_CLOEXEC` |
| 10 | 用 `CLOCK_REALTIME` 做周期心跳 | NTP 阶跃会让周期错位 ⇒ 周期任务用 `CLOCK_MONOTONIC`（书里示例用 `CLOCK_REALTIME` 是为了和另外两个程序对照）；跨机对齐的时间戳才用 `CLOCK_REALTIME` |
| 11 | 以为「定时器 1 µs 一次」响应就是 1 µs | 实测每轮 `read → clock_gettime → printf` 要 6~7 µs ⇒ **响应精度受你自己代码的轮转速度限制** |
| 12 | 在非阻塞模式下 `read` 失败就报错退出 | `EAGAIN` 是**正常**的（暂时没到期），要区分于真错误 |
| 13 | 期望 `timerfd` 跨平台 | Linux 专有（≥ 2.6.25） |

## HFT / 嵌入式关联

| 路线 | 结论怎么用 |
|------|-----------|
| **HFT** | ① ⭐ **这是 HFT 里最该用的定时器形态**：`timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK \| TFD_CLOEXEC)` + `epoll` —— 行情 socket、控制 socket、定时器**全部是 fd**，主循环只有一个 `epoll_wait`，既没有异步信号上下文的限制，也没有多线程。② 需要「**在绝对时刻动手**」（开盘、集合竞价结束、收盘前 N 秒）就用 `TFD_TIMER_ABSTIME`，语义与 `clock_nanosleep(TIMER_ABSTIME)` 一致，免疫抖动累积（§23.5.4）。③ 用 `read()` 返回的**计数**做「欠了多少次心跳」的自检：计数 > 1 说明主循环被某段逻辑卡住了，这是**免费的延迟告警**。④ 定时器基准时钟用 `CLOCK_MONOTONIC`，绝不用 `CLOCK_REALTIME`（NTP 阶跃 / 闰秒）。⑤ 每个策略/每个连接一个 `timerfd` 会让 fd 数暴涨 ⇒ 需要评估 `RLIMIT_NOFILE`；也可以共用一个高精度 tick 定时器做统一调度。 |
| **嵌入式** | ① **单线程事件循环的固件首选 `timerfd`**：一个 `poll()` 同时等 UART/GPIO/网络/定时器，不需要为定时器开线程或进信号处理器（后者在 RTOS 风格的固件里尤其难受）。② 内核要求 **≥ 2.6.25**，工具链/内核版本受限的项目要确认；旧内核上退回 `SIGEV_SIGNAL`（注意 overrun）。③ `TFD_CLOEXEC` 在「主程序 `exec` 起子程序」的固件里几乎总是该加 —— 否则子程序会继承一堆它不认识的定时器。④ `timerfd` 的 fd 是**内核对象**，`fork` 后父子共享定时器 —— 某些「父子各自计时」的设计会因此错乱，要么 `fork` 后重新 `timerfd_create`，要么约定只有一个读者。 |

<summary>代码自测（Q&A）</summary>

**Q1：`timerfd` 相比 `SIGEV_SIGNAL` 到底「好」在哪里？两点。**

A：① **它是个 fd** —— 可以和 socket、管道一起进 `select`/`poll`/`epoll`，这样「等 I/O」和「等定时」合成一次调用，一个线程一个主循环就能管住全部事件。`SIGEV_SIGNAL` 做不到这一点，必须另开线程去 `sigwaitinfo()`，或者在信号处理器里干活。② **它不会丢到期信息** —— `read()` 直接返回「到期了多少次」，而不是「只送一个信号 + 让你猜 `overrun`」。

**Q2：`timerfd_overrun` 实测里为什么 `expirations read` 会变成 47？**

A：因为定时器周期是 **1 微秒**，而程序每轮要做 `read()` + `clock_gettime()` + `printf()` 三件事。第二轮读之前，程序花了大约 50 微秒（第一次读之后到第二次读之间），这期间定时器到期了 **47 次** —— 这些到期全部累计在 fd 的计数里，一次 `read()` 就全取回来了。后面的 `6~7` 就是程序每轮的**实际轮转耗时（微秒）**。

**Q3：`timerfd` 和 POSIX 定时器在 `fork`/`exec` 上为什么相反？**

A：因为 `timerfd` 的本质是**文件描述符**，而 fd 的继承规则是内核统一的：`fork` 继承、`exec` 保留（除 `CLOEXEC`）。POSIX 定时器没有 fd 这个载体，内核就把它的生命周期**绑在进程上**：不跨 `fork`、`exec` 时清除。**一个是「fd 对象」，一个是「进程资源」** —— 记住这个区别就不会记反。

**Q4：`close(timerfd)` 和 `timer_delete()` 等价吗？**

A：功能上都是「释放定时器」，但语义不同。`timerfd` 的 fd 是**引用计数**的：`fork`/`dup` 之后可能有多个 fd 指向同一个 open file description，**所有**引用都关闭后定时器才真正释放。而 `timer_delete()` 是按句柄直接删。所以「只关掉自己的那份 fd」不等于「定时器没了」。

**Q5：为什么 `demo_timerfd.c` 里定时器用 `CLOCK_REALTIME` 而耗时测量用 `CLOCK_MONOTONIC`？**

A：因为定时器用哪个时钟是**书里示例的选择**（和另外两个程序保持对照），而「过了多久」必须用 `CLOCK_MONOTONIC` 量才不会被 NTP 阶跃污染（§23.5）。所以打印出来的 `秒.毫秒` 是**单调时钟口径**，不是墙上钟。**生产代码里定时器本身也应该用 `CLOCK_MONOTONIC`。**

**Q6：`total=104` 而不是 `total=100`，是 bug 吗？**

A：不是 bug，是**原书程序的设计性质**。循环条件是 `totalExp < maxExp`，而 `totalExp += numExp` 里的 `numExp` 可能一次就是 **47**（1 µs 周期导致）。所以累计值会**越过** `maxExp` 才退出 —— 这是「最多等 maxExp 次到期」而不是「精确读 maxExp 次」。要知道这个差别：如果你需要「精确 N 次」，必须自己切分计数值。

**Q7：定时器 1 µs 一次，我的代码响应也是 1 µs 吗？**

A：不是。实测每轮 `read → clock_gettime → printf` 要 **6~7 微秒**。定时器能表达的**周期**精度和你的**响应**精度是两件事 —— 这正呼应 §23.2 的结论：到期只负责「把事件标记出来」，真正干活要等你的代码轮转。**要提高响应精度只能简化轮转路径（去掉 `printf`、去掉多余的 `clock_gettime`）。**
