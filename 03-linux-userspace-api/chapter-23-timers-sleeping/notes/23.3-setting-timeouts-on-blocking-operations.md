## 本节讲什么

`ITIMER_REAL` 最经典的一个用途，不是「周期性干活」，而是**给一个可能永远阻塞的系统调用加一个上限** —— 读终端、读管道、收网络包，都可能一直等下去。

原理只有一句话：**不装 `SA_RESTART` 的信号处理器 + 一个到点会打断系统调用的定时器**。处理器本身什么都不用干，它存在的唯一意义是让内核把阻塞中的系统调用**提前结束并返回 `-1` / `errno = EINTR`**。

本节钉四件事：

1. 书里给的**五步法**，以及每一步为什么必要。
2. `errno` 必须在 `alarm(0)` **之前**存下来 —— 这是个很容易写错的地方。
3. **`SA_RESTART` 会让这套办法失效**：系统调用被自动重启，超时形同不存在。
4. ⭐ **实测发现**：在非交互环境（stdin 是已关闭的管道/重定向文件）下，`read()` 会**立刻返回 EOF 0**，根本走不到超时分支 —— 本书配套的 CE 实测因此看不到 `Read timed out`。本节用另一个**延伸 demo** 把它真的跑出来。

## 1. 书中给出的五步法

原书 §23.3 逐字列出：

> 1. Call `sigaction()` to establish a handler for `SIGALRM`, **omitting the `SA_RESTART` flag**, so that system calls are not restarted (refer to Section 21.5).
> 2. Call `alarm()` or `setitimer()` to establish a timer specifying the upper limit of time for which we wish the system call to block.
> 3. Make the blocking system call.
> 4. After the system call returns, call `alarm()` or `setitimer()` once more to **disable the timer** (in case the system call completed before the timer expired).
> 5. Check to see whether the blocking system call failed with `errno` set to `EINTR` (interrupted system call).

逐步说清：

| 步 | 做什么 | 漏了会怎样 |
|----|--------|-----------|
| 1 | 装 `SIGALRM` 处理器，**不带** `SA_RESTART` | 不装处理器 ⇒ 信号默认处置是**终止进程**；带了 `SA_RESTART` ⇒ 系统调用被自动重启，超时永不生效 |
| 2 | `alarm(n)` 设上限 | 没上限 ⇒ 可能永远阻塞 |
| 3 | 做阻塞调用 | —— |
| 4 | 系统调用返回后 `alarm(0)` **撤销** | 残留的定时器会在**后面某段无关代码**里打断某个系统调用 —— 这是最阴的一种 bug |
| 5 | 判 `errno == EINTR` | 分不清「超时被打断」与「真的读到了 EOF / 出错」 |

> ⭐ 第 4 步是**必须**的。定时器是「一次性的」，但它仍会在 n 秒后触发；如果系统调用早就成功返回了而你忘了撤销，那颗定时器就会在之后任意一个时刻把 `SIGALRM` 送到进程里。

```c
/* timed_read.c

   Demonstrate the use of a timer to place a timeout on a blocking system call
   (read(2) in this case).
*/
#include <signal.h>
#include "tlpi_hdr.h"

#define BUF_SIZE 200

static void     /* SIGALRM handler: interrupts blocked system call */
handler(int sig)
{
    printf("Caught signal\n");          /* UNSAFE (see Section 21.1.2) */
}

int
main(int argc, char *argv[])
{
    struct sigaction sa;
    char buf[BUF_SIZE];
    ssize_t numRead;
    int savedErrno;

    if (argc > 1 && strcmp(argv[1], "--help") == 0)
        usageErr("%s [num-secs [restart-flag]]\n", argv[0]);

    /* Set up handler for SIGALRM. Allow system calls to be interrupted,
       unless second command-line argument was supplied. */

    sa.sa_flags = (argc > 2) ? SA_RESTART : 0;
    sigemptyset(&sa.sa_mask);
    sa.sa_handler = handler;
    if (sigaction(SIGALRM, &sa, NULL) == -1)
        errExit("sigaction");

    alarm((argc > 1) ? getInt(argv[1], GN_NONNEG, "num-secs") : 10);

    numRead = read(STDIN_FILENO, buf, BUF_SIZE);

    savedErrno = errno;                 /* In case alarm() changes it */
    alarm(0);                           /* Ensure timer is turned off */
    errno = savedErrno;

    /* Determine result of read() */

    if (numRead == -1) {
        if (errno == EINTR)
            printf("Read timed out\n");
        else
            errMsg("read");
    } else {
        printf("Successful read (%ld bytes): %.*s",
                (long) numRead, (int) numRead, buf);
    }

    exit(EXIT_SUCCESS);
}
```

```bash
gcc -O0 -Wall -Wextra -o timed_read timed_read.c get_num.c
```

> 📌 **与书里印刷版的一处差异（源码核验）**：书上 Listing 23-2 的读是
> `numRead = read(STDIN_FILENO, buf, BUF_SIZE - 1);`
> 而 man7 当前分发版是
> `numRead = read(STDIN_FILENO, buf, BUF_SIZE);`
>
> 差别在「要不要给 `buf` 留一个 `'\0'`」。当前版把 `- 1` 去掉了 —— 因为打印用的是 `printf("%.*s", (int) numRead, buf)`，**精度已经限定了最多读 `numRead` 个字符**，不依赖结尾的 `'\0'`。功能等价，但用**旧**写法更保险：一旦有人把打印改成 `%s`，`- 1` 就是唯一的防线。

## CE 实测：三个作业

命令行是 `[num-secs [restart-flag]]`。

### ① 给了 stdin 数据：`timed_read 2` + `hello from stdin`

```text
Successful read (17 bytes): hello from stdin
```

读法：`read()` 在数据到达时**立刻**成功返回，压根没等到 2 秒；随后 `alarm(0)` 撤销定时器（所以后面不会再冒出 `SIGALRM`）。`17` = `"hello from stdin\n"` 的字节数（15 + `\n` + 结尾？—— 逐字数是 `hello from stdin` 16 字符 + `\n` = **17**）。

### ② 不给 stdin 数据：`timed_read 2`（stdin 是空管道）

```text
Successful read (0 bytes): 
```

### ③ 第 2 个参数存在 ⇒ 装 `SA_RESTART`：`timed_read 2 y`

```text
Successful read (0 bytes): 
```

> ⚠️⚠️ **诚实标注 —— ②③ 都没有走到「超时」这条路上。**
>
> 本书配套的 CE 实测环境里，`stdin` 是一个**已经关闭写端的管道**（语义上等价于把 `/dev/null` 接进 stdin：fd 可读、但立刻 EOF）。对这种 fd 调 `read()` 会**立刻**返回 `0`（EOF），不会阻塞 —— 所以 `alarm(2)` 那两秒**根本没等**（两个作业的 `execTime` 分别只有 21 ms / 30 ms，而不是 2000 ms），也谈不上被 `SIGALRM` 打断。
>
> 于是三件事在 CE 上**无法观察**：
>
> | 想看的东西 | CE 上为什么看不到 |
> |-----------|------------------|
> | `Read timed out` 分支 | `read()` 立刻 EOF，不进阻塞态 ⇒ 没有 `EINTR` |
> | `sa_flags = SA_RESTART` 的差异 | 同上 —— 系统调用根本没被信号打断，重启与否无从体现 |
> | `handler()` 打印的 `Caught signal` | 定时器被 `alarm(0)` 在第 4 步就撤掉了，`SIGALRM` 从未送达 |
>
> **要观察到这些，必须让 `read()` 真的阻塞住。** 见下一节 —— 本仓库为此写了一个延伸 demo。

## 延伸 demo：把「Read timed out」真的跑出来

⚠️ **原书没有这个程序。** 造一个「一定会阻塞的 fd」最简单：`pipe()` 之后**故意不关写端**。管道无数据 + 至少一个写端存在 ⇒ `read()` 一直阻塞。

**实现**：`code/c23_alarm_pipe_timeout.c`（本仓库自写，非原书内容）。

[`code/c23_alarm_pipe_timeout.c`](../code/c23_alarm_pipe_timeout.c)

```c
/* c23_alarm_pipe_timeout.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。
      §23.3 的 Listing 23-2 是 `timed_read.c`，它演示「用定时器给阻塞系统调用
      加超时」。但它的 `Read timed out` 分支在**非交互环境**下极难复现：只要
      stdin 是「已关闭的管道/重定向的普通文件」，read() 会立刻返回 0（EOF），
      根本走不到超时那一步 —— 本仓库在 CE 上实测正是如此。

   本程序把「会真的阻塞下去的 fd」造出来：用一个**写端保持打开**的匿名管道，
   读端必然阻塞。于是同一条 5 步法能观察到两种截然不同的结果：

     对照 A（sa_flags = 0）          ⇒ SIGALRM 打断 read()，返回 -1 / errno = EINTR
     对照 B（sa_flags = SA_RESTART） ⇒ read() 被内核自动重启，永远不返回

   这样 §23.3 讲的「装上 SA_RESTART 与否」就不再是纸面差别。

   ⚠️ stdout 设为无缓冲（setvbuf _IONBF）：对照 B 会一直阻塞到被执行器杀掉。
      CE 的 stdout 是 **socket** ⇒ glibc 用 8KB 全缓冲 ⇒ 有缓冲的话前面已经
      打印的内容会跟着进程一起消失。这是本仓库实测环境的事实，不是程序行为。

   编译：gcc -O0 -Wall -Wextra -o c23_alarm_pipe c23_alarm_pipe_timeout.c
   ⚠️ 只依赖 libc，不需要 tlpi_hdr.h / get_num.c。

   ⚠️ 本文件**刻意不定义 `_POSIX_C_SOURCE`**，与 Listing 23-2（timed_read.c）
      的写法保持一致。原因实测踩过：一旦显式定义 `_POSIX_C_SOURCE 199309`，
      glibc 就**不再隐式打开 `_DEFAULT_SOURCE`**，`SA_RESTART` 随之变成
      `error: 'SA_RESTART' undeclared`。
      （原书 Makefile 之所以能编过 `ptmr_*.c` 那批带 `_POSIX_C_SOURCE` 的文件，
        是因为 IMPL_CFLAGS 里还有 `-D_DEFAULT_SOURCE`。）
*/
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t handlerCalls = 0;

static void
handler(int sig)
{
    (void) sig;                 /* 处理器什么都不做，只负责打断 read() */
    handlerCalls++;
}

int
main(void)
{
    int fds[2];
    char buf[64];
    ssize_t nr;
    int savedErrno;

    setvbuf(stdout, NULL, _IONBF, 0);   /* 见文件头：对照 B 会被杀，不能留缓冲 */

    if (pipe(fds) == -1) {
        perror("pipe");
        exit(EXIT_FAILURE);
    }

    printf("pipe() 造出读端 fd=%d、写端 fd=%d —— 写端**故意不关**\n", fds[0], fds[1]);
    printf("所以 read(fd=%d, ...) 一定会阻塞。\n\n", fds[0]);

    /* ---------------- 对照 A：不加 SA_RESTART（Listing 23-2 的做法） -------- */

    printf("[对照 A] sa_flags = 0，alarm(1)\n");
    {
        struct sigaction sa;

        sa.sa_flags = 0;
        sigemptyset(&sa.sa_mask);
        sa.sa_handler = handler;
        if (sigaction(SIGALRM, &sa, NULL) == -1) {
            perror("sigaction");
            exit(EXIT_FAILURE);
        }
    }

    handlerCalls = 0;
    alarm(1);                           /* 第 2 步：设超时上限 */
    nr = read(fds[0], buf, sizeof(buf)); /* 第 3 步：做阻塞系统调用 */
    savedErrno = errno;                 /* alarm() 会动 errno，先存 */
    alarm(0);                           /* 第 4 步：撤销定时器 */
    errno = savedErrno;

    printf("  read() 返回 %ld\n", (long) nr);
    if (nr == -1) {
        printf("  errno = %d (%s)\n", savedErrno,
               savedErrno == EINTR ? "EINTR" : "其它");
        printf("  => Listing 23-2 会走 \"Read timed out\" 分支\n");
    }
    printf("  handler 共被调用 %d 次\n\n", (int) handlerCalls);

    /* ---------------- 对照 B：加 SA_RESTART -------------------------------- */

    printf("[对照 B] sa_flags = SA_RESTART，alarm(1)\n");
    printf("  预期：read() 被自动重启，永远不返回 => 本行之后不会再有输出\n");
    {
        struct sigaction sa;

        sa.sa_flags = SA_RESTART;
        sigemptyset(&sa.sa_mask);
        sa.sa_handler = handler;
        if (sigaction(SIGALRM, &sa, NULL) == -1) {
            perror("sigaction");
            exit(EXIT_FAILURE);
        }
    }

    handlerCalls = 0;
    alarm(1);
    nr = read(fds[0], buf, sizeof(buf));
    savedErrno = errno;
    alarm(0);
    errno = savedErrno;

    printf("  read() 返回 %ld，errno = %d"
           "  <= 能打印出这一行说明本机行为与预期不同\n",
           (long) nr, savedErrno);
    printf("  handler 共被调用 %d 次\n", (int) handlerCalls);

    return 0;
}
```

编译（`code/` 目录下）：

```bash
gcc -O0 -Wall -Wextra -o c23_alarm_pipe c23_alarm_pipe_timeout.c
```

### CE 实测

```text
pipe() 造出读端 fd=3、写端 fd=4 —— 写端**故意不关**
所以 read(fd=3, ...) 一定会阻塞。

[对照 A] sa_flags = 0，alarm(1)
  read() 返回 -1
  errno = 4 (EINTR)
  => Listing 23-2 会走 "Read timed out" 分支
  handler 共被调用 1 次

[对照 B] sa_flags = SA_RESTART，alarm(1)
  预期：read() 被自动重启，永远不返回 => 本行之后不会再有输出
```

同一段 5 步法，两种 `sa_flags` 的结果天差地别：

| 对照 | `sa_flags` | `read()` 的结果 | 说明 |
|------|-----------|----------------|------|
| **A** | `0` | 返回 **-1**，`errno = 4 (EINTR)` | 这就是 Listing 23-2 的 `Read timed out` 分支 —— 超时**生效**了 |
| **B** | `SA_RESTART` | **永远不返回** | 内核在信号处理器返回后**自动重启** `read()`，超时**完全失效** |

对照 B 的作业在 CE 上跑到 **20.234 秒**被执行器 `SIGKILL`（`Killed - processing time exceeded`，`exit code = 143`）—— 这**正是**预期结果：程序卡在重启后的 `read()` 里，永远等不到数据。

> 📌 这个程序里 `setvbuf(stdout, NULL, _IONBF, 0)` 不是装饰：对照 B 会被强杀，而 CE 的 stdout 是 **socket** ⇒ glibc 用 **8KB 全缓冲** ⇒ 有缓冲的话前面 A 部分的输出会跟着进程一起消失。**这是本仓库实测环境的事实，不是程序行为**（§23.1 也踩过同一个坑）。
>
> 📌 另一处实测踩坑写在文件头：本文件**不能**定义 `_POSIX_C_SOURCE`。一旦显式定义它，glibc 就不再隐式打开 `_DEFAULT_SOURCE`，`SA_RESTART` 直接变成 `error: 'SA_RESTART' undeclared`。原书 Makefile 能编过 `ptmr_*.c`（它们定义了 `_POSIX_C_SOURCE 199309` 且用到了 `SIGRTMAX` 等），靠的是 `IMPL_CFLAGS` 里还带了 `-D_DEFAULT_SOURCE`。

## 2. 理论竞态：书上自己指出的缺陷

原书 §23.3 在 Listing 23-2 之后紧接着说：

> Note that there is a **theoretical race condition** in the program in Listing 23-2. If the timer expires **after** the call to `alarm()`, but **before** the `read()` call is started, then the `read()` call **won't** be interrupted by the signal handler. Since the timeout value used in scenarios like this is normally relatively large (at least several seconds) this is highly unlikely to occur, so that, in practice, this is a viable technique.

把时间线画出来就清楚了：

| 时刻 | 事件 | 后果 |
|------|------|------|
| T1 | `alarm(n)` 返回，定时器已挂上 | —— |
| T2 | ⚠️ 定时器到期，`SIGALRM` 送达并**跑完处理器** | 系统调用**还没开始**，没东西可打断 |
| T3 | 才走到 `read()` | 此时信号已消费，`read()` **正常阻塞** ⇒ **超时彻底失效** |

也就是说：**这套机制的保证是「不定向」的** —— 它只能打断**已经开始**的系统调用。T2 与 T3 之间的窗口就是它的漏洞。

书里给出两条替代路线：

> [Stevens & Rago, 2005] proposes an alternative technique using `longjmp()`. A further alternative when dealing with I/O system calls is to use the **timeout feature of the `select()` or `poll()` system calls** (Chapter 63), which also have the advantage of allowing us to **simultaneously wait for I/O on multiple descriptors**.

## 3. 该用哪种「超时」？

| 方案 | 机制 | 优点 | 缺点 / 适用边界 |
|------|------|------|----------------|
| **`SIGALRM` + 阻塞调用**（本节） | 定时器打断系统调用 | 改动最小；任何系统调用都能套 | ① 有 T2/T3 竞态；② `ITIMER_REAL` 每进程只有一个 ⇒ 与 `sleep()`/`alarm()` 冲突；③ 打不进「同时等多个 fd」的场景 |
| **`select()` / `poll()` / `epoll_wait()` 的超时参数** | 把「等 I/O」与「等超时」合并成一次调用 | 无竞态；**天生支持多 fd**；超时精度由内核给 | 只能用于 fd 类 I/O；每次要重算剩余时间 |
| **`timerfd`**（§23.7） | 定时器**变成一个 fd** | 可以和其他 fd 一起进 `epoll`；读到的还是「超时次数」；`CLOCK_MONOTONIC` 可选 | Linux 专有（≥ 2.6.25） |
| **`SO_RCVTIMEO` / `SO_SNDTIMEO`** | 套接字自带的超时 | 一行 `setsockopt` | 只能用于 socket；超时后返回 `EAGAIN`，且**定时器状态会被静默修改**（坑） |
| **`ppoll()` / `pselect()`** | 原子地「换信号掩码 + 等 I/O + 等超时」 | 一步解决竞态 | 同样是 fd 类 I/O |
| **`signalfd` + `epoll`** | 信号变成 fd | 信号处理回到主循环里同步做 | 需要 `SIG_BLOCK` 先屏蔽 |

> ⭐ **HFT 场景的标准答案**：`timerfd`（`CLOCK_MONOTONIC`）+ `epoll`。所有「定时」与「I/O」都归一成 fd 事件，主循环里同步处理，既没有异步信号处理的限制，也没有竞态。

| # | 坑 | 正解 |
|---|----|------|
| 1 | 装了 `SA_RESTART` 还指望超时生效 | `SA_RESTART` 会**自动重启**系统调用，超时形同不存在（本页延伸 demo 的对照 B 实测：永远不返回） |
| 2 | 忘记第 4 步 `alarm(0)` | 残留定时器会在之后**某段无关代码**里打断别的系统调用 —— 最难查的一类 bug |
| 3 | 用 `errno` 之前先调了 `alarm(0)` | `alarm()` 自己可能改 `errno`。必须先 `savedErrno = errno;` 再 `alarm(0);` 再 `errno = savedErrno;`（Listing 23-2 就是这么写的，别「简化」掉） |
| 4 | 把「`read` 返回 0」当成「超时」 | 返回 0 是 **EOF**（对端关了）；超时是返回 **-1 + `EINTR`**。两者是完全不同的事件 |
| 5 | 假设这套机制一定生效 | 有 T2/T3 竞态：定时器在 `alarm()` 之后、系统调用之前到期，则超时失效 |
| 6 | 用 `ITIMER_VIRTUAL` / `ITIMER_PROF` 做超时 | 它们走 CPU 时间，进程阻塞时**不增长** ⇒ 永远等不到（§23.1） |
| 7 | 在一个进程里同时用 `alarm()` / `sleep()` / `setitimer(ITIMER_REAL)` | 三者共享**同一个**定时器，互相覆盖 |
| 8 | 想「同时」给多个 fd 加超时 | 每进程只有一个 `ITIMER_REAL` ⇒ 改用 `poll`/`epoll` + 统一超时，或 `timerfd` |
| 9 | 在信号处理器里做业务（打印、加锁、分配内存） | 处理器里只能用 **async-signal-safe** 函数（原书 §21.1.2）。本节处理器里的 `printf()` 是**故意**示范「UNSAFE」的写法 |
| 10 | 在非交互环境（重定向/CI/CE）里期望看到 `Read timed out` | stdin 若是已关闭的管道 ⇒ `read` 立刻 EOF。要复现必须用**真终端**或**写端未关的管道**（本页延伸 demo 的做法） |
| 11 | `SO_RCVTIMEO` 超时后以为「没副作用」 | 超时返回 `EAGAIN`，而且内核会**静默地**把超时量改掉（`man 7 socket` 有说明） |
| 12 | 用「超时」来实现「轮询」 | 反复「超时 → 再试」会累积成为忙等；该用 `poll()` 的 timeout 参数一次解决 |

## HFT / 嵌入式关联

| 路线 | 结论怎么用 |
|------|-----------|
| **HFT** | ① **别用信号做超时**：HFT 主循环要么是忙轮询，要么是 `epoll` 等待。信号超时会把处理逻辑推进异步上下文，而那里连 `printf` 都不能安全调，更别说下单/撤单这种要审计的操作。② 标准形态 = **`timerfd(CLOCK_MONOTONIC)` + `epoll_wait`**：一个 `epoll_wait` 同时拿到「行情到了」和「心跳该发了」，没有竞态。③ 网关/会话超时用 `SO_RCVTIMEO` 要小心它**静默改超时量**的行为，宁可自己用 `poll` 管。④ 「已发送未确认」这类重传超时用 `CLOCK_MONOTONIC` 做基准，避免 NTP 阶跃把重传节奏打乱。 |
| **嵌入式** | ① 串口/ADC/单总线这类「等应答」的读，用本节机制加超时是**最小改动**方案 —— 几乎所有老驱动都这么写（`wait_event_interruptible_timeout` 是内核里的对应物）。② 但注意：**内核态**里没有 `SIGALRM`，对应工具是 `completion` + `wait_event_timeout` / `msleep_interruptible`。③ 看门狗 + I/O 超时要留「调度延迟不可控」的余量（§23.2），别把喂狗周期和 I/O 超时设成同一个值。④ 单核 + 低 `CONFIG_HZ` 的板子上，`alarm(1)` 实际可能是 1~1 jiffy+ε 秒，验收用例别写等号。 |

<summary>代码自测（Q&A）</summary>

**Q1：为什么必须把 `errno` 在 `alarm(0)` 之前存下来？**

A：因为 `alarm()` 是个系统调用，**它自己可能改写 `errno`**。Listing 23-2 里的
```c
savedErrno = errno;   /* In case alarm() changes it */
alarm(0);
errno = savedErrno;
```
就是为了这个。如果写成 `alarm(0); if (errno == EINTR) ...`，一旦 `alarm()` 内部把 `errno` 改成别的值，你就再也认不出 `EINTR` 了。

**Q2：`read()` 返回 0 和返回 -1/`EINTR`，在本节的语境下分别意味着什么？**

A：返回 `0` = **文件结束（EOF）**，说明对端把写端关了（或读到文件末尾）—— 这是**正常**结果，不是超时。返回 `-1` 且 `errno == EINTR` = **被信号打断**，也就是超时到了。本页 CE 实测的 ②③ 两个作业拿到的都是 `0`（因为 CE 的 stdin 是已关闭的管道），所以**不是**超时。

**Q3：为什么这节的处理器里只 `printf("Caught signal\n")`，什么都不做？**

A：它的唯一职责就是**让系统调用被打断**。「处理器是否执行了业务」不重要 —— 重要的是信号**送达**这个事实：内核在把信号交给用户态之前，会先把阻塞中的系统调用提前中止（除非装 `SA_RESTART`）。书里还特意标注这句 `printf()` 是 `UNSAFE`，因为 `printf` 不是 async-signal-safe 函数（原书 §21.1.2）。

**Q4：`SA_RESTART` 到底重启了哪些系统调用？**

A：不是全部。`man 7 signal` 有一张专门的表，把「被中断后行为」分成三类：(a) 装了 `SA_RESTART` 就自动重启（`read`/`write`/`wait`/`nanosleep`… 的**可重启**情形）；(b) 无论有没有 `SA_RESTART` 都**绝不**重启（如 `select`、`poll`、`epoll_wait`、`msgrcv` 等）；(c) 有些调用在「已经传输了部分数据」时不会被重启（如 `read` 已经读到一部分）。所以「装了 `SA_RESTART` ⇒ 所有系统调用都不会被信号打断」是**错的**。

**Q5：本节这套办法在什么场景下仍然是最好的选择？**

A：**你无法控制那个阻塞点**的时候。比如你在调一个第三方库，它内部做了一个会阻塞的 `read()`，而你不想、也不能改它 —— 那么「装个 `SIGALRM` 处理器」就成了唯一能从外部给它加超时的手段。反过来，只要你能控制代码，`poll`/`epoll`/`timerfd` 永远更优（无竞态、多路复用、没有异步上下文限制）。

**Q6：延伸 demo 里对照 B 挂了 20 秒被 SIGKILL，这算「测试失败」吗？**

A：不算，**它就是结论本身**。`SA_RESTART` 的语义正是「系统调用被自动重启」—— 所以 `read()` 永远不返回，`alarm(0)`/后续 `printf` 也永远执行不到。程序一直阻塞到被执行器强杀，就是这条语义最直接的证据。

</details>
