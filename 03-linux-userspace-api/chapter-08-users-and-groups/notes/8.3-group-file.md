## 本节讲什么

组比用户多一层麻烦：**同一个「用户属于哪些组」的信息，被拆在两个文件里**。这一节回答：

1. `/etc/group` 的 4 个字段分别是什么？
2. 主组（primary）和附属组（supplementary）分别写在哪？为什么必须这么拆？
3. 「没有 `/etc/group` 条目」会发生什么？
4. `gr_mem` 对**空组**返回 NULL 吗？
5. `errno` 范式在这里的一个真实失效点。

---

## 要点

### 一、四个字段

`group(5)` DESCRIPTION 原文：

> The `/etc/group` file is a text file that defines the groups on the system. There is one entry per line, with the following format:
>
> ```
> group_name:password:GID:user_list
> ```

| # | 字段 | `group(5)` 原文 |
|---|------|-----------------|
| 1 | `group_name` | "the name of the group." |
| 2 | `password` | "the (encrypted) group password. **If this field is empty, no password is needed.**"（实际几乎总是 `x` 或 `*`） |
| 3 | `GID` | "the numeric group ID." |
| 4 | `user_list` | "a list of the usernames that are members of this group, **separated by commas**." |

`group(5)` 自己带一段 BUGS，值得抄下来：

> As the 4.2BSD `initgroups(3)` man page says: **no one seems to keep `/etc/group` up-to-date.**

这不是玩笑。第 4 字段是**手工/脚本维护的冗余信息**，它和「用户实际的附属组集合」只在 `initgroups()` 跑过之后才一致 —— 这也是下面第四节要说清「附属组其实是**进程凭证**，不是文件内容」的原因。

### 二、主组 vs 附属组：一个用户的组身份拆在两处

| | 存在哪 | 每个用户能有几个 | 权威原文 |
|---|--------|------------------|----------|
| **主组**（primary GID） | `/etc/passwd` 的 **第 4 字段** | **恰好一个**（字段只有一个） | `passwd(5)`："This is the numeric **primary** group ID for this user." |
| **附属组**（supplementary） | `/etc/group` 的 **`user_list`** | 多个，且**一个用户可出现在多行** | `passwd(5)`："(Additional groups for the user are defined in the system group file; see `group(5)`)." |

两者在权限判定时**一起参与**：内核检查文件权限时，看的是「有效 GID == 文件 GID」**或**「文件 GID ∈ 附属组集合」。完整机制（`getgroups` / `setgroups` / `initgroups`、以及主组与附属组的互斥关系）属于 [Ch9 §9.6 附属组 ID](../../chapter-09-process-credentials/README.md)，本节只把**文件侧**说清楚。

> ⚠️ 所以「这个用户属于哪些组」这个问题，**没有单一权威来源**：一半在 `/etc/passwd`，一半在 `/etc/group`。想看进程**当前真正持有**的组，只能问内核（`getgroups()`）。

### 三、「没有条目」= 「没有这个组」

`passwd(5)` NOTES 原文：

> If you want to create user groups, **there must be an entry in `/etc/group`, or no group will exist.**

这是一句很强的表述：`/etc/passwd` 里写了 `gid=10240` **不代表** 10240 这个组存在。组存在与否**只看 `/etc/group`**。

本容器正好是这个状态（下面实测第一行）：`fopen(/etc/group)` 返回 NULL，`getgrent()` 遍历到 **0 个组**，而 `ce` 的 `pw_gid` 明明写着 10240。于是 `getgrgid(10240) -> NULL` —— 用户有主组号，但那个组**不存在**。

### 四、`struct group` 与空组的 `gr_mem`

`getgrnam(3)` 给出的 `<grp.h>` 定义：

```c
struct group {
    char   *gr_name;   /* group name */
    char   *gr_passwd; /* group password */
    gid_t   gr_gid;    /* group ID */
    char  **gr_mem;    /* NULL-terminated array of pointers
                          to names of group members */
};
```

`gr_mem` 是「**以 NULL 结尾的指针数组**」。这里有个真实的坑：

**空组的 `gr_mem` 不是 `NULL`，而是「首元素为 `NULL` 的数组」。** 本节实测的 `emptygrp` 行给出了铁证：

```text
(gr_mem==NULL? no ; gr_mem[0]==NULL? yes)
```

所以下面这种「教科书式」写法是错的：

```c
/* ✗ 错：空组时 gr_mem 非 NULL，这段会打印一行空内容而不是跳过 */
if (gr->gr_mem != NULL) {
    for (char **m = gr->gr_mem; *m != NULL; m++)
        printf("%s ", *m);
}
```

正确写法是**直接遍历 NULL 结尾数组**，或者两级都判：

```c
/* ✓ 直接遍历：空组自然一次都不进循环 */
for (char **m = gr->gr_mem; m != NULL && *m != NULL; m++)
    printf("%s ", *m);
```

### 五、一个真实的 `errno` 陷阱（本容器实测）

很多资料会告诉你这个范式：

```c
errno = 0;
gr = getgrgid(gid);
if (gr == NULL) {
    if (errno == 0)  /* 没有这个组 */;
    else             /* 系统错误 */;
}
```

**它在 `/etc/group` 不存在时会给出错误结论。** 本节实测里 `getgrgid(10240)` 返回 NULL 且 **`errno = 2 (ENOENT)`**，按上面的写法会被判成「系统错误」，而真相是「确实没有这个组」。

原因在标准里写得很清楚。`getgrnam(3)` ERRORS 第一条居然是：

> **0 or ENOENT or ESRCH or EBADF or EPERM or ...**
> The given name or gid was not found.

`getpwnam(3)` NOTES 讲得更透：

> One might argue that according to POSIX errno should be left unchanged if an entry is not found. **Experiments on various UNIX-like systems show that lots of different values occur in this situation: 0, ENOENT, EBADF, ESRCH, EWOULDBLOCK, EPERM, and probably others.**

机制层面（glibc 2.39 `nss/files-XXX.c`）：

| 路径 | 代码 | errno 行为 |
|------|------|-----------|
| **文件打不开** | `internal_setent()` `:69-85`：`*stream == NULL` → `status = errno == EAGAIN ? TRYAGAIN : UNAVAIL` | **完全不碰 errno** → `open()` 留下的 `ENOENT` 一路透传给你 |
| **文件打开、扫完没匹配** | `internal_getent()` `:130`：`__set_errno (saved_errno);`（`saved_errno` 在 `:112` 采集） | **把你调用前设的 0 还回来** → errno 不变 |
| **缓冲太小** | `internal_getent()` `:114-119`：`*errnop = ERANGE` | `ERANGE` |

所以准确的结论表是：

| 情况 | 返回值 | `errno` | 能否与「出错」区分 |
|------|--------|---------|-------------------|
| 文件在，没有该 GID | `NULL` | 不变（0） | ✅ 能 |
| **文件不在 / 打不开** | `NULL` | `ENOENT` / `EACCES` … | ❌ **不能** |
| 内存不足 | `NULL` | `ENOMEM` | ✅ 能 |

**「errno 范式」只能区分「文件在、没这条」和「出问题了」。它区分不了「文件不在」和「出问题了」** —— 因为「文件不在」本身就是通过 errno 报上来的。

要稳妥，就得多做一步显式检查：

```c
/* 想区分「没有这个组」和「组数据库不可用」，得自己看文件在不在 */
if (gr == NULL) {
    if (errno == 0)
        puts("没有这个组");
    else if (access("/etc/group", R_OK) != 0)
        puts("组数据库不可用（/etc/group 不存在或不可读）");
    else
        perror("getgrgid");     /* 真正的系统错误 */
}
```

或者接受更简单的工程取舍：**`NULL` 一律按「没有这个组」处理，并把 `errno` 写进日志**。

## 代码

### c8_3 真实环境的组查询 + 合成 group 文件的字段解析

完整程序见 [`../code/c8_3_group_file.c`](../code/c8_3_group_file.c)：前半段如实报告真实环境的 API 行为（`getgrent` 计数、`getgrgid` 返回 NULL）；后半段用 `fgetgrent()` 解析一份合成 group，把 `gr_mem` 的空组语义跑出来。

```c
/* c8_3_group_file.c —— 8.3：/etc/group 与「主组 / 附属组」
 *
 * 本容器里 /etc/group 根本不存在（第一条输出就是证据），所以这里做两件事：
 *   1. 如实报告真实 API 的行为（getgrent 计数、getgrgid 返回 NULL）
 *   2. 用 fgetgrent() 解析一份合成 group 文件，看 4 字段格式与 gr_mem 语义
 *
 * 编译：cc -Wall -Wextra -o c8_3_group_file c8_3_group_file.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <grp.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    /* ---- 1. 真实环境 ---- */
    errno = 0;                          /* errno 必须在调用前清零！ */
    FILE *f = fopen("/etc/group", "r");
    printf("fopen(/etc/group) -> %s  errno=%d(%s)\n",
           f ? "ok" : "NULL", errno, strerror(errno));
    if (f != NULL)
        fclose(f);

    int n = 0;
    struct group *gr;
    setgrent();
    while ((gr = getgrent()) != NULL)
        n++;
    endgrent();
    printf("getgrent() 遍历到 %d 个组\n", n);

    errno = 0;
    gr = getgrgid(10240);
    printf("getgrgid(10240) -> %s（errno=%d）—— passwd 里写了 gid 10240，\n"
           "                  但 group 文件不存在，所以查不到\n",
           gr ? gr->gr_name : "NULL", errno);

    struct passwd *pw = getpwnam("ce");
    if (pw != NULL) {
        const char *gname = NULL;
        struct group *g2 = getgrgid(pw->pw_gid);
        if (g2 != NULL)
            gname = g2->gr_name;
        printf("用户 ce 的主组 gid=%ld -> 组名 %s\n", (long) pw->pw_gid,
               gname ? gname : "(查不到)");
    }

    /* ---- 2. 合成 group 文件：看格式与 gr_mem ---- */
    const char *gf = "/tmp/c8_group_demo";
    FILE *w = fopen(gf, "w");
    if (w == NULL) {
        perror("fopen for write");
        return 1;
    }
    fputs("rocket:x:500:alice,bob\n"
          "toolchain:x:501:carol\n"
          "emptygrp:x:502:\n", w);      /* 空组：冒号后面什么都没有 */
    fclose(w);

    puts("\n-- fgetgrent() 解析合成 group（格式 name:x:gid:member,member） --");
    f = fopen(gf, "r");
    while (f != NULL && (gr = fgetgrent(f)) != NULL) {
        printf("组名=%-12s 组密文=%-3s gid=%-5ld 成员数=",
               gr->gr_name, gr->gr_passwd, (long) gr->gr_gid);

        if (gr->gr_mem == NULL) {
            printf("gr_mem==NULL");
        } else {
            int cnt = 0;
            for (char **m = gr->gr_mem; *m != NULL; m++)
                cnt++;
            printf("%d", cnt);
        }
        printf("  成员=");
        if (gr->gr_mem != NULL) {
            for (char **m = gr->gr_mem; *m != NULL; m++)
                printf("[%s]", *m);
        }
        /* 空组的 gr_mem 不是 NULL，而是「首元素为 NULL 的数组」 */
        printf("   (gr_mem==NULL? %s ; gr_mem[0]==NULL? %s)\n",
               gr->gr_mem == NULL ? "yes" : "no",
               (gr->gr_mem == NULL || gr->gr_mem[0] == NULL) ? "yes" : "no");
    }
    if (f != NULL)
        fclose(f);

    puts("\n主组：写在 /etc/passwd 的 gid 字段（每个用户恰好一个）");
    puts("附属组：写在 /etc/group 的成员列表里（一个用户可以出现在多行）");
    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c8_3_group_file c8_3_group_file.c && ./c8_3_group_file
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
fopen(/etc/group) -> NULL  errno=2(No such file or directory)
getgrent() 遍历到 0 个组
getgrgid(10240) -> NULL（errno=2）—— passwd 里写了 gid 10240，
                  但 group 文件不存在，所以查不到
用户 ce 的主组 gid=10240 -> 组名 (查不到)

-- fgetgrent() 解析合成 group（格式 name:x:gid:member,member） --
组名=rocket       组密文=x   gid=500   成员数=2  成员=[alice][bob]   (gr_mem==NULL? no ; gr_mem[0]==NULL? no)
组名=toolchain    组密文=x   gid=501   成员数=1  成员=[carol]   (gr_mem==NULL? no ; gr_mem[0]==NULL? no)
组名=emptygrp     组密文=x   gid=502   成员数=0  成员=   (gr_mem==NULL? no ; gr_mem[0]==NULL? yes)

主组：写在 /etc/passwd 的 gid 字段（每个用户恰好一个）
附属组：写在 /etc/group 的成员列表里（一个用户可以出现在多行）
```

**解读**

1. **前三行是「文件为空」的真实后果**：`/etc/group` 不存在 → `getgrent()` 遍历到 **0 个组** → `getgrgid(10240)` 返回 `NULL`。而 `ce` 明明有 `pw_gid=10240`。这就是 `passwd(5)` 那句 "there must be an entry in `/etc/group`, or no group will exist" 的实证。
2. **`errno=2` 是本节的陷阱样本**。按教科书写法它会被判成「系统错误」，真相是「没有这个组」。详见要点第五节：`internal_setent()` 在 `fopen` 失败时**不碰 errno**，而成功扫完没匹配时反而会把 errno 还回 0。
3. `fgetgrent()` 解析合成文件得到三组：`rocket`（2 人）、`toolchain`（1 人）、`emptygrp`（0 人）。**格式 `name:x:gid:m1,m2` 被逐字段还原**，和 8.1 的 `passwd` 一样：「组数据库 API」就是对这一行的封装。
4. **`emptygrp` 那一行是本节的第二个坑**：`gr_mem==NULL? no` 但 `gr_mem[0]==NULL? yes`。空组的 `gr_mem` 是一个**首元素为 NULL 的数组**，不是 NULL 指针。任何写 `if (gr->gr_mem != NULL)` 就认为「有成员」的代码都会在这里走错分支。
5. 最后两行是在提醒：**「用户属于哪些组」没有单一权威来源**。`/etc/passwd` 只给一个主组号，`/etc/group` 给的是**名单**（从组视角看）；两者都不等于「这个进程此刻持有哪些组」（那要问内核，见 Ch9 §9.6）。

## HFT / 嵌入式关联

- **不要在热路径上做「组名 ↔ gid」翻译**。`getgrgid()` 和 `getpwuid()` 一样要 `fopen` + 线性扫描；接了 LDAP/SSSD 的机器上还会变成网络往返。日志、审计、权限报错信息里优先写**数字 gid**。
- **权限排查要问内核，不要读文件**。用户抱怨「明明在组里却没权限」时，正确的检查顺序是：① `id`（看进程/登录会话**实际持有**的组）；② `getgroups()` 的输出；③ 才去看 `/etc/group`。`group(5)` 的 BUGS 段说明文件内容经常是过期的。
- **`getgrent()` 遍历是 O(n) 且每次重开文件**，`/etc/group` 在大量用户/组的机器上可以很大。要枚举全系统组，读一次 `fgetgrent()` 或直接缓存。
- **嵌入式**：BusyBox 系统里 `/etc/group` 常常只有 `root:x:0:` 一行，甚至根本不存在。**依赖「gid → 组名」做展示或策略判断的代码在嵌入式上必须能接受 NULL**，否则会打印一堆 `(null)` 或直接崩在 `gr_name` 解引用上。
- **`gr_mem` 的空组语义是真会咬人的**：写「打印组成员」这类工具时，用 `for (m = gr->gr_mem; m && *m; m++)` 而不是 `if (gr->gr_mem) { ... }`，可以省掉一个只在空组上出现的 bug。
- **`+` / `-` 开头的组行是 NIS 语法**，`files` 后端会主动跳过（`nss/files-grp.c` 的 `break_if_match` 里带 `name[0] != '-' && name[0] != '+'`）。交叉编译的老发行版镜像里见到这类行不要当损坏数据删掉。

## 自测题

<details>
<summary>1. 一个用户的 <code>/etc/passwd</code> 里写着 <code>gid=10240</code>，是否说明 10240 这个组存在？</summary>

**不说明。**

`passwd(5)` NOTES 原文："If you want to create user groups, **there must be an entry in `/etc/group`, or no group will exist**." 组的存在性**只看 `/etc/group`**；`/etc/passwd` 的 GID 字段只是一个数字。

本容器就是活样本：`ce` 的 `pw_gid = 10240`，而 `/etc/group` 根本不存在 → `getgrent()` 遍历到 **0 个组**，`getgrgid(10240) -> NULL`。

工程影响：**任何"先把 gid 翻成组名再展示/判断"的代码都必须能接受 NULL**。这个状态在精简容器镜像里非常常见（`FROM scratch` 或只 COPY 应用程序的那种镜像里根本没有 `/etc/group`）。
</details>

<details>
<summary>2. 空组的 <code>gr_mem</code> 是 <code>NULL</code> 吗？</summary>

**通常不是。** glibc 的 `files` 后端给出的空组 `gr_mem` 是「**首元素为 NULL 的数组**」—— 指针本身非 NULL，但 `gr_mem[0] == NULL`。

本节实测（`emptygrp` 行）：`(gr_mem==NULL? no ; gr_mem[0]==NULL? yes)`。

所以：

```c
/* ✗ 会走错分支 */
if (gr->gr_mem != NULL) { /* 这里会以为"有成员" */ }

/* ✓ 两种都覆盖 */
for (char **m = gr->gr_mem; m != NULL && *m != NULL; m++)
    printf("[%s]", *m);
```

注意 `gr_mem` 的契约本来就是 "**NULL-terminated array**"（`getgrnam(3)`）——「以 NULL 结尾」意味着**空数组只含一个 NULL**，而不是「没有数组」。按这个契约写，空组自然一次循环都不进。
</details>

<details>
<summary>3. <code>errno = 0; getgrgid(gid);</code> 之后 <code>errno == ENOENT</code>，是「没有这个组」还是「出错了」？</summary>

**在这个场景下分不清 —— 而 `ENOENT` 恰恰是「没有这个组」的常见取值之一。**

`getgrnam(3)` ERRORS 第一条把这个可能性直接列出来了：

> **0 or ENOENT or ESRCH or EBADF or EPERM or ...**
> The given name or gid was not found.

`getpwnam(3)` NOTES 也承认这一点："**Experiments on various UNIX-like systems show that lots of different values occur in this situation: 0, ENOENT, EBADF, ESRCH, EWOULDBLOCK, EPERM, and probably others.**"

机制（glibc 2.39 `nss/files-XXX.c`）：文件**打不开**时 `internal_setent()` 只设 `NSS_STATUS_UNAVAIL`，**不碰 errno**，于是 `open()` 留下的 `ENOENT` 透传给你；反过来「文件打开、扫完没匹配」的路径会在 `:130` 用 `__set_errno(saved_errno)` 把你设的 0 **还回来**。

也就是说，**除了 `ENOENT` 这种"后端不可用"的取值外，`errno` 范式是成立的**。要稳妥就加一步 `access("/etc/group", R_OK)` 做存在性检查，或者接受「NULL 一律按没有这个组处理」并把 errno 记进日志。
