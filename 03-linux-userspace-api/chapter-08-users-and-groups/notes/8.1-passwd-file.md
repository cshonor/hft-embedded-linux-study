# 8.1 The Password File：`/etc/passwd`

> 权威依据：`passwd(5)`（Linux man-pages 6.19）· `getpwnam(3)`（man-pages 6.19）· glibc 2.39 NSS `files` 后端（`nss/files-pwd.c`、`nss/files-XXX.c`、`nss/files-parse.c`、`nss/getXXbyYY.c`）

## 本节讲什么

Linux 把「系统里有哪些用户」这件事放在一个**纯文本文件**里。这一节只要回答四个问题：

1. 一行 `/etc/passwd` 有哪七段？每个字段的**权威定义**在哪？
2. 它为什么**必须全局可读**？（这个「必须」直接决定了 8.2 的存在）
3. C 程序拿到的 `struct passwd` 和文本行是什么关系？
4. 读它的 API 为什么是 O(n) 的，返回值为什么不能留住？

---

## 要点

### 一、七个字段：以 man 原文为准

`passwd(5)` DESCRIPTION 原文：

> Each line of the file describes a single user, and contains **seven colon-separated fields**:
>
> ```
> name:password:UID:GID:GECOS:directory:shell
> ```

| # | 字段 | `passwd(5)` 原文 | 要点 |
|---|------|------------------|------|
| 1 | `name` | "This is the user's login name. It should not contain capital letters." | 登录名 |
| 2 | `password` | "This is either the encrypted user password, an asterisk (`*`), or the letter 'x'." | 有 shadow 时是 `x` |
| 3 | `UID` | "The privileged root login account (superuser) has the user ID **0**." | **0 = root** |
| 4 | `GID` | "This is the numeric **primary** group ID for this user. (Additional groups for the user are defined in the system group file; see `group(5)`)." | 主组；附属组在 `/etc/group` |
| 5 | `GECOS` | "This field (sometimes called the "comment field") is optional and used only for informational purposes." | 纯注释，**不参与认证** |
| 6 | `directory` | "the initial directory where the user is placed after logging in. The value in this field is used to set the **HOME** environment variable." | 只是初始化 `HOME` |
| 7 | `shell` | "This is the program to run at login (if empty, use `/bin/sh`)." | 初始化 `SHELL` |

第 2 字段有四个特殊值，全部出自 `passwd(5)`，含义差别很大：

| 值 | 含义 | 原文 |
|----|------|------|
| `x` | 真密文搬到 `/etc/shadow` 了 | "the letter 'x'" |
| `*` | 这一账号不能用口令登录 | "many system administrators use an asterisk (`*`) in the encrypted password field to make sure that this user can not authenticate themself using a password" |
| `*NP*` | 影子记录应从 NIS+ 取 | "If the encrypted password in `/etc/passwd` is `*NP*` (without the quotes), the shadow record should be obtained from an NIS+ server." |
| **空串** | **不口令直接放行** | "If the encrypted password, whether in `/etc/passwd` or in `/etc/shadow`, **is an empty string, login is allowed without even asking for a password**." |

> ⚠️ 最后一行是**真的安全口子**，不是笔误。它也是各种「登录绕过」漏洞的常见形态：一个手滑留下来的空密码字段 = 一个无需口令的账号。

### 二、「必须全局可读」是被需求逼出来的

`passwd(5)` 第一段原文：

> The `/etc/passwd` file is a text file that describes user login accounts for the system. **It should have read permission allowed for all users (many utilities, like `ls(1)` use it to map user IDs to usernames), but write access only for the superuser.**

这句话把 8.2 的动机说尽了：**`ls -l` 必须能把 `uid=10240` 显示成 `ce`** —— 这个「数字 ↔ 名字」的映射表就得人人可读。而一旦人人可读，第 2 字段里就**不能放密文**。

所以「`/etc/passwd` 是 644、`/etc/shadow` 是 600/640」不是风格习惯，是这两条约束的必然结果。

### 三、`struct passwd`：文本行 → 内存结构

`getpwnam(3)` DESCRIPTION 给出的定义（`<pwd.h>`）：

```c
struct passwd {
    char  *pw_name;    /* username */
    char  *pw_passwd;  /* user password */
    uid_t  pw_uid;     /* user ID */
    gid_t  pw_gid;     /* group ID */
    char  *pw_gecos;   /* user information */
    char  *pw_dir;     /* home directory */
    char  *pw_shell;   /* shell program */
};
```

字段顺序和文件**一一对应**，区别只是：行 → 结构体，`:` → 各自独立的指针，十进制文本 → `uid_t` / `gid_t` 整数。`getpwnam()` 没有任何魔法，它就是 NSS 后端里的一次 `fopen` + 按 `:` 切分。

> ⚠️ `getpwnam(3)` VERSIONS 段明确说：`pw_gecos` "is **not specified in POSIX**, but is present on most implementations." 用它要接受可移植性折扣。

### 四、三个不显眼但会咬人的文件层事实（本容器实测）

| 事实 | 证据（见下文实测输出） |
|------|------------------------|
| **末行可能没有换行符** | `== 记录 1：字段数 7（文件末行没有换行符）` —— 本容器 `/etc/passwd` 只有 1 条记录，**末尾没有 `\n`** |
| **有 UID 0 的进程 ≠ 有 UID 0 的记录** | 进程 `uid=0`，但 `getpwuid(0) -> NULL（errno=0）` |
| **没有 `/etc/group` 条目就等于没有这个组** | `passwd(5)` NOTES："If you want to create user groups, **there must be an entry in `/etc/group`, or no group will exist**."（8.3 实测 `getgrgid(10240)` 返回 NULL） |

第一条的杀伤力最直接：自己写解析器时若假设「每行都以 `\n` 结尾」再无条件 `line[len-1] = '\0'`，就会把最后一个字符吃掉 —— 本例里会把 `10240` 削成 `1024`。

### 五、谁真的在读它：glibc NSS `files` 后端

**路径是编译期写死的**（glibc 2.39 `nss/files-XXX.c:42`）：

```c
#define DATAFILE	"/etc/" DATABASE
```

所以 `getpwnam()` / `getpwuid()` / `getpwent()` 永远读 `/etc/passwd`，**没有任何环境变量或参数能改**。想读自己造的测试文件，唯一的正规入口是 `fgetpwent(FILE *)`。

**查询是 O(n) 线性扫描**。所有 `getXXbyYY` 由一个宏生成（`nss/files-XXX.c:198-222`，此处节选主体）：

```c
/* DB_LOOKUP 宏生成的函数体（删去宏拼接细节） */
{
  enum nss_status status;
  FILE *stream = NULL;

  /* Open file.  */
  status = internal_setent (&stream);

  if (status == NSS_STATUS_SUCCESS)
    {
      while ((status = internal_getent (stream, result, buffer, buflen, errnop)) 
	     == NSS_STATUS_SUCCESS)
	{ break_if_match }          /* ← 读到匹配就 break */

      fclose (stream);
    }

  return status;
}
```

三件事一次说清：

1. **每次调用都要 `fopen` + 逐行读 + `fclose`** —— 没有索引、没有缓存（除非跑 `nscd`）。
2. **匹配就是 `strcmp`**，记录数 n 就是最坏 O(n) 次 `readline`。
3. **比较里带 NIS 兼容判断**（`nss/files-pwd.c:33-38`）：

```c
DB_LOOKUP (pwnam, '.', 0, ("%s", name),
	   {
	     if (name[0] != '+' && name[0] != '-'
		 && ! strcmp (name, result->pw_name))
	       break;
	   }, const char *name)
```

`+` / `-` 开头的行是 NIS 的 include/exclude 语法，`files` 后端**主动跳过**它们。这是「NSS 把多个数据源拼在一起」留下的化石 —— 账号库从来不止一个文件。

## 代码

### c8_1 手工切一遍 `/etc/passwd`，再和 `getpwnam()` 对照

完整程序见 [`../code/c8_1_passwd_parse.c`](../code/c8_1_passwd_parse.c)：自己按 `:` 切 7 段、自己剥 `\n`，再把同一行交给 `getpwnam()`，两侧逐字段对照。

```c
/* c8_1_passwd_parse.c —— 8.1：/etc/passwd 的 7 字段格式
 *
 * 手工按 ':' 切分每一行，再和 getpwnam() 的结果逐字段对照：
 * 「账户库 API」说到底就是对这几个文本文件的封装。
 *
 * 编译：cc -Wall -Wextra -o c8_1_passwd_parse c8_1_passwd_parse.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define NFIELD 7

static const char *fieldname[NFIELD] = {
    "登录名", "密文占位", "UID", "主 GID", "注释(GECOS)", "家目录", "登录 shell"
};

/* 就地把 line 按 ':' 切成最多 NFIELD 段，把 ':' 改成 '\0'；返回实际段数 */
static int split_fields(char *line, char **f)
{
    int n = 0;
    char *p = line;

    if (n < NFIELD)
        f[n++] = p;
    for (; *p != '\0' && n < NFIELD; p++) {
        if (*p == ':') {
            *p = '\0';
            f[n++] = p + 1;
        }
    }
    return n;
}

int main(void)
{
    FILE *fp = fopen("/etc/passwd", "r");
    if (fp == NULL) {
        perror("fopen /etc/passwd");
        return 1;
    }

    char line[512];
    int rec = 0;
    while (fgets(line, sizeof line, fp) != NULL) {
        size_t len = strlen(line);
        int had_nl = (len > 0 && line[len - 1] == '\n');

        if (had_nl)
            line[len - 1] = '\0';       /* 自己剥掉换行，别让 strtol 撞上 */

        rec++;
        char *f[NFIELD];
        int n = split_fields(line, f);
        printf("== 记录 %d：字段数 %d%s\n", rec, n,
               had_nl ? "" : "（文件末行没有换行符）");
        for (int i = 0; i < n; i++)
            printf("   %d %-12s = %s\n", i + 1, fieldname[i], f[i]);

        if (n >= 3) {
            char *end;
            long uid = strtol(f[2], &end, 10);
            printf("   -> strtol(f[2]) = %ld（UID 在文件里只是十进制文本）\n", uid);
        }
    }
    fclose(fp);
    printf("共读到 %d 条记录\n", rec);

    /* ---- 同一份数据，走 API ---- */
    struct passwd *pw = getpwnam("ce");
    if (pw != NULL) {
        printf("\ngetpwnam(\"ce\") -> pw_name=%s pw_passwd=%s pw_uid=%ld pw_gid=%ld\n",
               pw->pw_name, pw->pw_passwd, (long) pw->pw_uid, (long) pw->pw_gid);
        printf("                    pw_gecos=%s pw_dir=%s pw_shell=%s\n",
               pw->pw_gecos, pw->pw_dir, pw->pw_shell);
        printf("pw_passwd 是占位符还是真密文：%s\n",
               strcmp(pw->pw_passwd, "x") == 0 ? "占位符 \"x\"" : "真密文");
    } else {
        printf("\ngetpwnam(\"ce\") -> NULL\n");
    }

    /* ---- 「UID 0」不等于「passwd 里有 0 号记录」 ---- */
    errno = 0;
    pw = getpwuid(0);
    printf("getpwuid(0) -> %s（errno=%d）\n", pw ? pw->pw_name : "NULL", errno);

    return 0;
}
```

编译与运行：

```bash
gcc -O0 -Wall -Wextra -o c8_1_passwd_parse c8_1_passwd_parse.c && ./c8_1_passwd_parse
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
== 记录 1：字段数 7（文件末行没有换行符）
   1 登录名    = ce
   2 密文占位 = x
   3 UID          = 10240
   4 主 GID      = 10240
   5 注释(GECOS) = Not a real account
   6 家目录    = /app
   7 登录 shell = /bin/bash
   -> strtol(f[2]) = 10240（UID 在文件里只是十进制文本）
共读到 1 条记录

getpwnam("ce") -> pw_name=ce pw_passwd=x pw_uid=10240 pw_gid=10240
                    pw_gecos=Not a real account pw_dir=/app pw_shell=/bin/bash
pw_passwd 是占位符还是真密文：占位符 "x"
getpwuid(0) -> NULL（errno=0）
```

**解读**

1. 第一行括号里的「文件末行没有换行符」不是装饰：这份 `/etc/passwd` 的**最后一行确实没有 `\n`**。程序里 `had_nl` 就是靠 `strlen(line)` 之后看最后一个字符得出的，剥换行前先判断 —— 无条件剥就会吃掉一个真实字符。
2. 手工切出的 7 段与 `getpwnam("ce")` 的 7 个字段**一一对应**（`pw_uid=10240`、`pw_gid=10240`、`pw_gecos=Not a real account`、`pw_dir=/app`、`pw_shell=/bin/bash`）。这就是"账户库 API = 对几个文本文件的封装"的实证。
3. `pw_passwd` 是占位符 `"x"`，不是密文。所以**拿 `pw_passwd` 直接 `crypt()` 必然失败**（会得到 libxcrypt 的失败哨兵 `*0`，见 8.5）—— 正确的做法是先 `getspnam()` 覆盖它，这正是原书 Listing 8-2 第 67 行干的事。
4. 最后一行 `getpwuid(0) -> NULL（errno=0）` 是本节第二个坑：**进程 `uid=0`，库里却没有 0 号记录**。「我是 root」是进程属性，「库里有 root 这条记录」是数据库内容，两者互不推导。评测容器恰好把这两件事拆开了，是个难得的教学样本。
5. 「UID 在文件里只是十进制文本」：文件里存的是字符串 `10240`，`struct passwd` 里是 `uid_t`。转换发生在 libc 内部（`nss/files-parse.c:96` 的 `parse_line`），所以任何**手工**解析都得自己 `strtol` 并检查溢出 —— 这正是程序里那行 `strtol(f[2])` 想点出的。

## HFT / 嵌入式关联

- **绝不在热路径上查账户库**。`getpwuid()` 在本容器里要走一趟 `fopen("/etc/passwd")` + 线性扫描；在接了 LDAP/SSSD 的机器上它是一次**网络往返**。日志线程里顺手 `getpwuid` 就是把行情线程拖进 DNS/网络超时。
- **审计的正确姿势**：记录**数字 uid**，展示时才翻译（并且翻译结果要缓存 —— 账户表在进程生命周期里几乎不变）。反过来「先把 uid 翻成名字再写日志」会把 I/O 带进热路径。
- **嵌入式**：BusyBox 系统常省掉 `/etc/shadow`，甚至把账号编译进二进制（`CONFIG_USE_BB_PWD_GRP` 直接内置 passwd/group 解析）。这类系统的 `getpwnam()` 不碰文件系统 —— 所以**「getpwnam 会读文件」不是可以依赖的语义**，只是 glibc + `nsswitch.conf: files` 下的实现。
- **`nsswitch.conf` 决定一切**：改成 `passwd: ldap files`，路径写死的就不是 `/etc/passwd` 了。排障时 `getent passwd <name>` 是比 `cat /etc/passwd` 更接近程序视角的检查手段。
- **`*NP*` / `+`/`-` 这类 NIS 遗留语法**在现代发行版里已经没有任何东西会去解析，但 `files` 后端仍在跳过它们。读交叉编译出来的老系统镜像时见到 `+::::::` 这类行，不要当成损坏数据。

## 自测题

<details>
<summary>1. 为什么 <code>/etc/passwd</code> 必须对所有用户可读，而密文必须搬去 <code>/etc/shadow</code>？</summary>

两句 `man` 原文拼起来就是答案：

- `passwd(5)`："/etc/passwd ... **It should have read permission allowed for all users** (many utilities, like `ls(1)` use it to map user IDs to usernames), but write access only for the superuser."
- `shadow(5)`："This file **must not be readable by regular users** if password security is to be maintained."

`ls -l` 要把 `uid` 显示成名字，映射表就得人人可读；映射表人人可读，密文就不能放里面。**这两个约束是因果关系，不是两条独立约定。**

顺带解释了一个常见误解：`/etc/passwd` 是 644 不是「配置不严」，而是设计使然；**反过来说，`/etc/shadow` 若是 644 就是确凿的配置错误**（见 [8.2](./8.2-shadow-file.md) 的实测）。
</details>

<details>
<summary>2. 进程 <code>getuid()</code> 返回 0，是不是就说明 <code>getpwuid(0)</code> 一定能拿到记录？</summary>

**不是。** 这是两个不同的数据库视角：

- `getuid()` 读的是**内核里的进程凭证**（`task_struct` 的 uid 字段）；
- `getpwuid(0)` 查的是**用户空间的账户库**（`/etc/passwd`、NIS、LDAP…）。

本容器实测就把它拆开了：进程 `uid=0`，而 `getpwuid(0) -> NULL（errno=0）` —— `/etc/passwd` 里只有一条 `ce(10240)`，压根没有 0 号记录。

写代码时的实际影响：**不要用 `getpwuid(getuid())->pw_name` 来做日志前缀而不判 NULL**。容器（尤其是精简基础镜像）里这条链断掉是常态。安全写法见本节 `c8_1` 与 [8.4](./8.4-retrieving-info.md)。
</details>

<details>
<summary>3. 为什么 <code>getpwnam()</code> 读不到我临时造的那份 passwd 文件？</summary>

因为 glibc `files` 后端的路径是**编译期常量**（`nss/files-XXX.c:42`）：

```c
#define DATAFILE	"/etc/" DATABASE
```

`getpwnam()` 走到 `_nss_files_getpwnam_r()`，里面的 `internal_setent()` 固定 `fopen("/etc/passwd")`。既没有环境变量能重定向，也没有参数能传路径。

要读自己造的文件，用 **`fgetpwent(FILE *)`**（8.4 有实测）。另一条路是改 `nsswitch.conf` 走向别的后端 —— 那已经不属于"读一个文件"了。
</details>
