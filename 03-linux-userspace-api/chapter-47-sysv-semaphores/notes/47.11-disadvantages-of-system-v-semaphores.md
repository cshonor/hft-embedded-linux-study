# 47.11 Disadvantages of System V Semaphores

> 本章：[TLPI 第 47 章](./README.md)

## 本节讲什么

System V 信号量的固有缺陷和设计问题，以及为什么现代应用推荐使用 POSIX 信号量或 pthread 互斥锁替代。

## 要点

### 主要缺点

| 缺点 | 说明 | 影响 |
|------|------|------|
| 信号量集而非单个 | API 操作的是信号量集合 | 使用复杂 |
| 创建和初始化非原子 | semget + semctl 两步 | 竞争窗口 |
| semop 不自动重启 | 信号中断返回 EINTR | 需手动重试 |
| 内核限制多 | SEMMNI/SEMMNS/SEMMSL | 可扩展性差 |
| 无超时（标准） | 需 semtimedop 扩展 | 不便控制 |
| 引用计数语义 | 创建者崩溃导致残留 | 资源泄漏 |
| 不支持进程内线程同步 | 设计目标为进程间 | 性能差 |

### 创建-初始化竞争

```c
/* 问题：两步操作 */
int semid = semget(key, 1, IPC_CREAT | 0666);  /* step 1: 创建 */
semctl(semid, 0, SETVAL, 1);                    /* step 2: 初始化 */
/* 如果 step 1 后进程崩溃，信号量值为 0（未初始化） */
/* 另一个进程 semget 获得未初始化的信号量 */
```

解决方案（但仍不便）：
1. 使用 `sem_otime` 检查是否已初始化
2. 只允许创建者初始化（`IPC_CREAT | IPC_EXCL`）

### IPC 资源持久性

SysV IPC 对象在进程退出后**仍存在**，直到：
- 显式 `IPC_RMID` 删除
- 系统重启

这导致：
- 崩溃的程序留下残留信号量
- 累积的 IPC 对象耗尽系统限制
- 需要手动 `ipcrm` 清理

### SysV vs POSIX 信号量对比

| 特性 | SysV | POSIX (named) | POSIX (unnamed) |
|------|------|---------------|-----------------|
| 类型 | 内核持久 | 文件系统持久 | 进程/共享内存内 |
| API 复杂度 | 高 | 低 | 低 |
| 初始化 | 两步 | 原子 | 原子 |
| 操作 | 信号量集 | 单个 | 单个 |
| 超时 | 扩展 API | `sem_timedwait` | `sem_timedwait` |
| 移植性 | Linux/Unix | POSIX.1-2001 | POSIX.1-2001 |
| 性能 | 中 | 高 | 高 |

### 替代方案推荐

| 场景 | 推荐 |
|------|------|
| 进程间互斥 | POSIX 信号量 / fcntl 文件锁 |
| 线程间同步 | pthread 互斥锁 / 条件变量 |
| 进程间通知 | eventfd / 管道 |
| 带超时等待 | POSIX `sem_timedwait` |

## HFT / 嵌入式关联

- HFT 进程间同步优先使用 POSIX 信号量或共享内存 + pthread 互斥锁
- 避免 SysV 信号量的 EINTR 重试开销
- 嵌入式系统内存有限，避免 SysV IPC 资源泄漏
- 遗留系统维护：用 `ipcs`/`ipcrm` 清理

## 代码示例

```c
/* SysV 信号量竞争安全初始化 */
#include <sys/sem.h>
#include <errno.h>

union semun { int val; struct semid_ds *buf; unsigned short *array; };

int init_semaphore(key_t key, int initial_val) {
    int semid, created = 0;

    /* 尝试创建 */
    semid = semget(key, 1, IPC_CREAT | IPC_EXCL | 0666);
    if (semid != -1) {
        created = 1;  /* 我们是创建者 */
    } else if (errno == EEXIST) {
        /* 已存在，打开 */
        semid = semget(key, 1, 0666);
        if (semid == -1) return -1;
    } else {
        return -1;
    }

    if (created) {
        /* 创建者负责初始化 */
        union semun arg;
        arg.val = initial_val;
        semctl(semid, 0, SETVAL, arg);
    }

    /* 等待初始化完成（非创建者） */
    struct semid_ds ds;
    union semun arg;
    arg.buf = &ds;
    int retry = 0;
    while (!created && retry++ < 100) {
        semctl(semid, 0, IPC_STAT, arg);
        if (ds.sem_otime != 0) break;  /* 已初始化 */
        usleep(10000);
    }

    return semid;
}
```

## 代码自测

<details>
<summary>为什么说 SysV 信号量的创建和初始化存在竞争窗口？</summary>

`semget()` 创建信号量集时，所有信号量初始值为 0。必须用 `semctl(SETVAL)` 单独设置初始值。在 `semget` 和 `semctl` 之间，如果另一个进程也调用 `semget`（不带 `IPC_EXCL`），它会获得一个值仍为 0 的信号量，而非期望的初始值。解决方案是检查 `sem_otime`（非 0 表示创建者已完成初始化并执行了 semop），但这需要忙等或轮询。

</details>
