## 19-1 记录目录树下所有文件的创建、删除与改名

**题面（转述）**：写程序记录命令行给定目录下所有文件的创建、删除与改名。必须监控**该目录下所有子目录**（用 `nftw()` 枚举，§18.9）；当树里新建或删除子目录时，监控集合要**相应更新**。

**实现**：[`code/ex19_1_log_events.c`](../code/ex19_1_log_events.c)

**四个设计要点（与题面逐条对应）**：

| 题面要求 | 实现机制 |
|---------|---------|
| 监控所有子目录 | `nftw(FTW_PHYS)` 枚举，回调里只对 `FTW_D`/`FTW_DP` `add_watch`（`FTW_PHYS` 防止链接指向的树外目录被误监控，Ch18 §18.9 实测过不加它的后果） |
| 新建子目录 → 更新监控集 | `IN_CREATE|IN_ISDIR`（以及 `IN_MOVED_TO|IN_ISDIR`，改名进来的目录同样要监控）→ `add_watch` 新目录，并**立即 rescan**该目录补 add 之前的漏 |
| 删除子目录 → 更新监控集 | `IN_DELETE_SELF`/`IN_MOVE_SELF`（目录自己没了）→ 槽位作废；`IN_IGNORED` 到达后彻底清映射 |
| 记录创建/删除/改名 | mask 全订阅 `IN_CREATE|IN_DELETE|IN_MOVED_FROM|IN_MOVED_TO`，打印时带 `wd → 路径` 前缀 |

**实现里三个值得单独记的点**：

1. **`wd → 路径` 映射**：用 `dirmap[wd]` 数组直接索引（wd 是实例内小整数且递增）。目录删除时槽位 `free` + 置 NULL，防「孤儿 wd」解引用；
2. **补漏的必要性**：`mkdir sub` 与「add_watch(sub)」之间存在窗口——窗口内 sub 里发生的变更没有事件。add 完成后立刻 rescan 一次 sub，把漏掉的现状补进状态（这正是 `inotify_dtree` 参考实现的核心套路）；
3. **`IN_Q_OVERFLOW` 分支**：打印告警并提示应全量重建——本题的实现注释里明确说「丢事件 = 状态失同步」，生产版本这里要接 `nftw` 重建。

**Pi5 实测步骤**（清单项）：

```bash
cc -Wall -Wextra -o ex19_1_log_events ex19_1_log_events.c
./ex19_1_log_events /tmp/tree &
# 在另一终端：
mkdir /tmp/tree/newdir          # → CREATE  /tmp/tree/newdir/  （且 watch 集合+1）
touch /tmp/tree/newdir/f1       # → CREATE  /tmp/tree/newdir/f1
mv /tmp/tree/newdir/f1 /tmp/tree/f2   # → MOVED_FROM + MOVED_TO（cookie 配对）
mv /tmp/tree/newdir /tmp/tree/nd      # → MOVED_TO/nd/（watch 跟随到新路径）
rmdir /tmp/tree/nd              # → DELETE_SELF + IN_IGNORED（watch 集合-1）
```

预期输出形如（`mask_name` 的输出）：

```text
CREATE         /tmp/tree/newdir/
CREATE         /tmp/tree/newdir/f1
MOVED_FROM     /tmp/tree/newdir/f1
MOVED_TO       /tmp/tree/f2
MOVED_TO       /tmp/tree/nd/
DELETE_SELF(目录) /tmp/tree/nd
```

> ⚠️ 上述输出是**按 man-pages 语义推演的预期值**，不是实测——本机无法运行。Pi5 上以实际输出为准修正本笔记（这正是复测清单的意义）。

**与官方参考实现的差异**：`inotify_dtree.c`（官方补充程序）是本题的「满血版」——它维护完整的目录树缓存、处理所有一致性边界（并发变更、溢出重建），并把交互接口暴露出来供 `rand_dtree` 随机压测。本题实现是它的最小骨架，覆盖题面要求但不处理全部边界。

## 常见坑（习题维度）

| 坑 | 正解 |
|----|------|
| 只 `nftw` 初始化、不处理 `IN_CREATE|IN_ISDIR` | 新建子目录完全失明（题面明确要求动态更新） |
| 补 watch 时不 rescan 新目录 | add 前窗口内创建的文件永久失明 |
| 监控集合用路径字符串匹配清理 | wd 才是身份；`IN_IGNORED`/`IN_DELETE_SELF` 按 wd 清理 |
| `nftw` 忘了 `FTW_PHYS` | 链接指向树外的目录也被 watch（监控范围失控，Ch18 实测过重复遍历） |
| 处理 `IN_MOVED_FROM|IN_ISDIR` | 目录被改名**移出**监控树 → 该目录的 watch 成孤儿；靠 `IN_IGNORED` 兜底清理 |
| 对 `IN_Q_OVERFLOW` 只打印不重建 | 监控状态从此不可信；生产版必须接重建逻辑 |

<summary>代码自测（Q&A）</summary>

**Q1：为什么「add_watch 后立即 rescan」能保证不漏？**
A：add_watch 是时间点 T2，mkdir 发生在 T1 < T2，窗口内 (T1,T2) 的变更没有事件。rescan 在 T3 > T2 执行，它看到的目录状态是 T3 时的全集——包含窗口内创建的一切。只要「扫描成本」可接受，这个「事件 + 一次性快照」的组合就是完备的。

**Q2：如果 rescan 与事件处理并发（多线程），会怎样？**
A：可能乱序（扫描结果晚于事件到达）。`inotify_dtree` 的做法是单线程事件循环 + 扫描也在同一循环内排队——顺序性是状态一致性的前提，宁可慢不可乱。

**Q3：`IN_MOVED_TO|IN_ISDIR` 的新目录也要 rescan 吗？**
A：要。rename 进来的目录可能内部已有内容（甚至刚在别处建好整棵子树），add_watch 只看顶层。更严谨的做法是对新目录再跑一次 `nftw` 把整棵子树都挂上 watch。

**Q4：本题为什么订阅 `IN_DELETE_SELF`/`IN_MOVE_SELF` 却说靠 `IN_IGNORED` 兜底？**
A：这两个事件告诉你「为什么」失效（语义），`IN_IGNORED` 告诉你「现在可以清了」（生命周期）。清理动作放在 `IN_IGNORED` 分支最安全——它保证是最后一条该 wd 的事件，清理后不会再有孤儿。

**Q5：这题与 `find`/`inotifywait`（inotify-tools）功能重叠吗？**
A：重叠，但本题练的是「动态 watch 集合维护」这个通用模式——它同样适用于 kqueue（macOS）、fanotify、甚至自己封装的变更通知服务。工具是结果，模式是可迁移的能力。

**Q6：生产版还要补什么？**
A：① 溢出重建（nftw 全量）；② 日志结构化（JSON：mask/cookie/路径/时间戳）；③ 平滑退出（信号处理里 `inotify_rm_watch` + 释放映射）；④ 与上层状态机对接（去重：CREATE 后紧跟 MOVED_FROM 同名是编辑器原子保存模式）。

</details>
