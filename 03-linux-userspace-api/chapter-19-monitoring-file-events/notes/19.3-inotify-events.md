## 本节讲什么

1. `struct inotify_event` 的五个字段——尤其是**变长的 `name`** 与它的对齐规则；
2. 事件 mask 全表：哪些事件报告**子项**（带 `name`）、哪些报告**被监控对象本身**（不带 `name`）；
3. `cookie` 的配对语义（`MOVED_FROM`/`MOVED_TO`）；
4. 三个「系统级」事件：`IN_IGNORED`/`IN_Q_OVERFLOW`/`IN_UNMOUNT`。

---

## 要点：结构体与变长 name

```c
struct inotify_event {
    int      wd;        /* 产生事件的 watch descriptor */
    uint32_t mask;      /* 事件位（可能含 IN_ISDIR 等修饰位） */
    uint32_t cookie;    /* 关联标识（改名配对用；其余为 0） */
    uint32_t len;       /* name 的长度（含尾部对齐填充的 NUL） */
    char     name[];    /* 变长：子项名；len==0 时这个字段不存在 */
};
```

| 字段 | 关键点 |
|------|--------|
| `wd` | 实例内唯一；应用自己维护 `wd → 路径` 映射 |
| `mask` | 事件位 + 修饰位（`IN_ISDIR`、`IN_IGNORED`、`IN_Q_OVERFLOW`、`IN_UNMOUNT`） |
| `cookie` | **只有** `IN_MOVED_FROM`/`IN_MOVED_TO` 一对共享同一个非零值；其余事件恒为 0 |
| `len` | 是**含填充**的长度（内核把名字补齐到 4 字节边界）；遍历步进用 `sizeof(*ev) + ev->len`，**不要用 `strlen(ev->name)`** |
| `name` | 只在事件针对**被监控目录的子项**时存在；事件针对被监控对象本身（如 `IN_DELETE_SELF`）时 `len == 0` |

**步进规则**（§19.4 的 read 循环全靠它）：

```c
for (char *p = buf; p < buf + n; ) {
    struct inotify_event *ev = (struct inotify_event *) p;
    /* ev->len > 0 时可读 ev->name（打印前自己补 NUL 或用 %.*s）*/
    p += sizeof(struct inotify_event) + ev->len;
}
```

## 要点：事件 mask 全表（按「报告对象」分组）

### A. 报告**子项**（带 `name`，watch 目录才有）

| 事件 | 触发 | 与哪个 syscall 对应 |
|------|------|---------------------|
| `IN_CREATE` | 子项被创建 | `open(O_CREAT)`、`mkdir`、`link`、`symlink` |
| `IN_DELETE` | 子项被删除 | `unlink`、`rmdir` |
| `IN_MOVED_FROM` | 子项被**移出**（改名到别处） | `rename` 的 oldpath 一侧 |
| `IN_MOVED_TO` | 子项被**移入** | `rename` 的 newpath 一侧 |
| `IN_OPEN` / `IN_ACCESS` / `IN_MODIFY` / `IN_ATTRIB` | 子项被打开/读/写/元数据变更 | `open` / `read` / `write` / `chmod` 等 |
| `IN_CLOSE_WRITE` / `IN_CLOSE_NOWRITE` | 以**写/非写**方式打开的 fd 被 close | `close` |

### B. 报告**被监控对象本身**（`len==0`，无 `name`）

| 事件 | 触发 | 配套 |
|------|------|------|
| `IN_DELETE_SELF` | 监控对象被删除 | 之后紧跟 `IN_IGNORED` |
| `IN_MOVE_SELF` | 监控对象被改名/移动 | watch 依然有效（挂 inode） |
| `IN_UNMOUNT` | 所在文件系统被卸载 | 之后 `IN_IGNORED`；此间事件不可靠 |

### C. 系统级事件（修饰位形式出现在 `mask` 里）

| 事件 | 含义 | 应用必须做什么 |
|------|------|----------------|
| `IN_IGNORED` | watch 已失效（删除/卸载/`rm_watch`/`IN_ONESHOT` 触发后） | **清理 wd 映射**；别再期待这个 wd 的事件 |
| `IN_Q_OVERFLOW` | 内核事件队列溢出——**有事件丢了** | `wd == -1`；要**全量重建**（rescan + 重挂 watch） |
| `IN_ISDIR` | 修饰位：事件对象是目录（建子树监控的判据） | `ev->mask & IN_ISDIR` |

## 要点：cookie 配对（改名语义的关键）

一次 `rename("/dir/a", "/dir/b")`（同目录内改名）会**同时**产生两条事件：

```
IN_MOVED_FROM  cookie=12345  name="a"
IN_MOVED_TO    cookie=12345  name="b"
```

| 场景 | 事件形态 |
|------|---------|
| 同目录改名 | `MOVED_FROM` + `MOVED_TO`，**cookie 相同** |
| 跨目录改名（同 FS） | 两目录各出一条，**cookie 相同** |
| 移到**另一文件系统**（`mv /tmp/x /mnt/y` 实际是复制+删除） | `MOVED_FROM`（或 `DELETE`）+ 另一侧 `CREATE`——**cookie 配不上** |
| 只监听了单侧目录 | 只收到一条 `MOVED_FROM`（cookie 用不上） |

**工程含义**：把改名处理成「删+建」是安全的降级（多一次 rescan，语义不丢）；把「删+建」硬凑成「改名」则是危险的升级（cookie 对不上时凑出来的改名是错的）。**降级永远安全**。

## 常见坑

| 坑 | 正解 |
|----|------|
| 步进用 `ev->len` 当「名字长度」 | `len` **含对齐填充**；步进用 `sizeof(*ev) + ev->len`，名字打印用 `%.*s` 或按返回的 `len` 截断 |
| 用 `strlen(ev->name)` 当长度 | name 以 NUL 结尾（内核保证最后一个字节是 NUL），但用 `strlen` 而不看 `len==0` 的分支会读越界（无 name 的事件里 `name` 字段根本不存在） |
| 忽略 `IN_IGNORED` | wd 永久失效且**不会再有事件**；映射不清则后续事件按「孤儿 wd」处理 |
| 忽略 `IN_Q_OVERFLOW` | 丢了多少事件不知道；唯一正解是全量 rescan 重建 |
| 对 `IN_CLOSE_WRITE` 与 `IN_MODIFY` 混用 | 流式读取（日志跟随）用 `IN_MODIFY`；「文件写完了可以拿走」用 `IN_CLOSE_WRITE`——safe-write 的产物总是伴随 `IN_MOVED_TO` + `IN_CLOSE_WRITE` 不出现（rename 不 close） |
| 只等 `IN_DELETE` 而忘了 `MOVED_FROM` | `mv` 出去的文件不触发 `DELETE`；「删除检测」要用 `IN_DELETE|IN_MOVED_FROM` |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 行情文件就绪检测 | `IN_MOVED_TO|IN_CLOSE_WRITE`（而非 `IN_CREATE`）：rename 进来的文件是**完整**的，create 的可能还在写 |
| 配置热重载 | `IN_MOVED_TO` + `IN_CLOSE_WRITE` + `IN_ATTRIB` 全订阅，按 cookie/顺序去重 |
| 嵌入式掉电 | `IN_UNMOUNT`/`IN_IGNORED` 是掉电/卸载的哨兵；收到后必须停止依赖 watch 而走 rescan 慢路径 |
| 审计日志 | `IN_ATTRIB` 对应权限/属主变更（安全审计）；`IN_ACCESS` 在 `relatime` 下不可靠（Ch15 实测）——别用 atime 事件做合规判据 |
| 带宽控制 | `IN_MODIFY` 对大文件写入是**高频事件**（每次 write 都触发）；按「写完」跟踪要用 `IN_CLOSE_WRITE`，否则队列爆（§19.5） |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：为什么 `name` 要对齐填充到 4 字节？**
A：内核按 `struct inotify_event` 序列化事件流，下一条事件的起始必须是 4 字节对齐（结构体成员对齐要求）。`len` 反映的是「这一段变长区域的总长」而非「名字的 C 串长」，所以遍历步进必须用 `sizeof + len`。

**Q2：`IN_Q_OVERFLOW` 的 wd 为什么是 -1？**
A：溢出是**实例级**事件，不属于任何 watch。内核无法把它挂到某个 wd 上，约定 `wd == -1`。这也是「收到它就全量重建」的原因：丢的事件可能涉及任意 watch。

**Q3：`IN_DELETE_SELF` 和 `IN_IGNORED` 的先后关系？**
A：对象被删除 → 队列里先是 `IN_DELETE_SELF`（描述发生了什么），随后内核把 watch 移除并补一条 `IN_IGNORED`（宣告 wd 失效）。应用按这个顺序清理：先处理语义事件，再在 `IN_IGNORED` 里删映射。

**Q4：同目录内 `rename("a","b")`，cookie 相同的两条事件顺序有保证吗？**
A：有——`MOVED_FROM` 先于 `MOVED_TO`（内核在 vfs_rename 内按序入队）。但**跨目录**时两条事件挂在不同 watch 上，若两个 watch 在同一实例里，顺序仍保证；跨实例则无保证。

**Q5：能否用 inotify 统计「文件内容改了多少字节」？**
A：不能。`IN_MODIFY` 只说「内容变了」，不带偏移与长度。要精确 diff 只能自己记快照（mtime+size 触发重扫）或用 `fanotify`/`eBPF`（kprobes on vfs_write）这类更底层机制。

**Q6：`IN_OPEN`/`IN_ACCESS` 这些「读侧」事件在生产上常用吗？**
A：很少。粒度太细、频率太高（读一个目录条目都可能触发），通常只用于调试或安全审计的特定 inode。监控「就绪/变更」用写侧事件（CREATE/CLOSE_WRITE/MOVED_TO）。

</details>
