## 本节讲什么

dnotify 不是「inotify 的前身那么简单」——它是理解「为什么事件接口必须 fd 化」的**反面教材**：

1. `fcntl(fd, F_NOTIFY, mask)`：对**已打开的目录 fd** 订阅事件，通知以**信号**送达；
2. 三大硬伤：信号通知、不带文件名、fd 钉住目录；
3. 官方镜像 `dnotify.c` 演示全部要点（含 `F_SETSIG` 用 realtime 信号的增强写法）。

---

## 要点：接口与事件

```c
#include <fcntl.h>
int fcntl(int dirfd, F_NOTIFY, int bitmask);   /* dirfd 必须是 O_RDONLY 打开的目录 */
/* 位：DN_ACCESS DN_MODIFY DN_CREATE DN_DELETE DN_RENAME DN_ATTRIB
 * 修饰：DN_MULTISHOT（默认一次性！要持续通知必须加）| DN_DELETE 是 DN_* 之一 */
```

| 项 | 语义 |
|----|------|
| 通知方式 | 默认发 `SIGIO`；配合 `F_SETSIG` 可换成指定信号（realtime 信号可排队，见下） |
| `DN_MULTISHOT` | **默认是一次性**——首个事件后自动清掉订阅；持续监控必须置位 |
| 作用范围 | **只目录**：报告该目录的直接子项变更（不递归，与 inotify 同） |
| 继承 | 经 fork 继承；**经 exec 保留**（除非目录 fd 被 CLOEXEC 处理） |
| 取消 | `fcntl(fd, F_NOTIFY, 0)` 或关闭 fd |

## 要点：三大硬伤（inotify 逐条修复的对象）

| 硬伤 | 后果 | inotify 的回答 |
|------|------|----------------|
| ① **信号通知** | 处理器是异步的；标准信号**会合并**（两次修改只收到一次）；处理器里能做的事受限（async-signal-safe） | 事件进 fd 队列：可 `read`、可 `poll`/`epoll`、不丢不乱 |
| ② **不带文件名** | 只知道「这目录有变动」，想知道谁变了必须 **rescan 整个目录** 再 diff | `inotify_event.name` 直接给名字 |
| ③ **每目录一个 fd 且钉住目录** | fd 泄漏即目录泄漏；被监控目录**无法卸载**（umount 报 EBUSY）；大量目录监控 fd 耗尽 | 实例 + 轻量 watch 记录，无此问题 |

**① 的半解**：`F_SETSIG` 换成 `SIGRTMIN` 系 realtime 信号 + `SA_SIGINFO`——realtime 信号**可排队**（不合并），且 `siginfo_t.si_fd` 带来事件的目录 fd。这就是官方 `dnotify.c` 用的写法。但它仍然是信号：处理器里只能把信息转投队列（self-pipe / signalfd），复杂度全转移到应用。

**② 的代价量化**：目录里有 10 万文件时，「谁变了」的 rescan 是 O(目录大小)——每事件 10 万次 `readdir`/`lstat`，监控变成了 DoS 自己。

## 要点：官方演示程序 dnotify.c 的骨架

**完整源码（[`code/dnotify.c`](../code/dnotify.c)）：**

```c
/*************************************************************************\

\*************************************************************************/

/* Supplementary program for Chapter 19 */

/* dnotify.c

   Demonstrate the use of the (obsolete) dnotify feature to obtain directory
   change notifications. (Modern programs should use inotify instead of
   dnotify. The inotify API is available in Linux 2.6.13 and later.)

   Usage is as shown in usageError() below. An example is the following:

        dnotify dir1:a xyz/dir2:acdM

   See also demo_inotify.c.

   This program is Linux-specific.
*/
#define _GNU_SOURCE             /* To get DN_* constants from <fcntl.h> */
#include <fcntl.h>
#include <signal.h>
#include "tlpi_hdr.h"

static void             /* Print (optional) message and usage info, then exit */
usageError(const char *progName, const char *msg)
{
    if (msg != NULL)
        fprintf(stderr, "%s", msg);

    fprintf(stderr, "Usage: %s directory:[events]...\n", progName);
    fprintf(stderr, "    Events are:\n"
        "        a - access; A - attrib; c - create; d - delete\n"
        "        m - modify; r - rename; M - multishot\n"
        "        (default is all events)\n");
    exit(EXIT_FAILURE);
}

static void
handler(int sig, siginfo_t *si, void *ucontext)
{
    printf("Got event on descriptor %d\n", si->si_fd);
                        /* UNSAFE (see Section 21.1.2) */
}

int
main(int argc, char *argv[])
{
    if (argc < 2 || strcmp(argv[1], "--help") == 0)
        usageError(argv[0], NULL);

    /* Establish handler for notification signal */

    const int NOTIFY_SIG = SIGRTMIN;

    struct sigaction sa;
    sa.sa_sigaction = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO;           /* So handler gets siginfo_t arg. */
    if (sigaction(NOTIFY_SIG, &sa, NULL) == -1)
        errExit("sigaction");

    for (int fnum = 1; fnum < argc; fnum++) {
        int events;
        char *p = strchr(argv[fnum], ':');      /* Look for optional ':' */

        if (p == NULL) {                /* Default is all events + multishot */
            events = DN_ACCESS | DN_ATTRIB | DN_CREATE | DN_DELETE |
                     DN_MODIFY | DN_RENAME | DN_MULTISHOT;
        } else {                        /* ':' present, parse event chars */
            *p = '\0';                  /* Terminates directory component */
            events = 0;
            for (p++; *p != '\0'; p++) {
                switch (*p) {
                case 'a': events |= DN_ACCESS;          break;
                case 'A': events |= DN_ATTRIB;          break;
                case 'c': events |= DN_CREATE;          break;
                case 'd': events |= DN_DELETE;          break;
                case 'm': events |= DN_MODIFY;          break;
                case 'r': events |= DN_RENAME;          break;
                case 'M': events |= DN_MULTISHOT;       break;
                default:  usageError(argv[0], "Bad event character\n");
                }
            }
        }

        /* Obtain a file descriptor for the directory to be monitored */

        int fd = open(argv[fnum], O_RDONLY);
        if (fd == -1)
            errExit("open");
        printf("opened '%s' as file descriptor %d\n", argv[fnum], fd);

        /* Use alternate signal instead of SIGIO for dnotify events */

        if (fcntl(fd, F_SETSIG, NOTIFY_SIG) == -1)
            errExit("fcntl - F_SETSIG");

        /* Enable directory change notifications */

        if (fcntl(fd, F_NOTIFY, events) == -1)
            errExit("fcntl-F_NOTIFY");
        printf("events: %o\n", (unsigned int) events);
    }

    for (;;)
        pause();                        /* Wait for events */
}
```

关键骨架摘录：

```c
#define _GNU_SOURCE          /* DN_* 常量在 <fcntl.h>，需 _GNU_SOURCE */
#include <fcntl.h>

/* 用法（源码头注释）： dnotify dir1:a xyz/dir2:acdM
 *   目录:标志串 —— a=DN_ATTRIB c=DN_CREATE d=DN_DELETE M=DN_MULTISHOT … */
for (每个 "dir:flags" 参数) {
    int fd = open(dir, O_RDONLY);
    fcntl(fd, F_SETSIG, SIGRTMIN);          /* 换 realtime 信号（增强）*/
    fcntl(fd, F_NOTIFY, flags | DN_MULTISHOT);  /* 订阅 + 持续模式 */
}
/* 然后 sigwaitinfo / 信号处理器里读 siginfo->si_fd 找出是哪个目录 */
```

它同时是「realtime 信号 + F_SETSIG + si_fd」三件套的教学样本——这套机制在 inotify 出现前是 Linux 异步 I/O 的通用底座。

## 要点：读旧代码时的对照表

| dnotify 时代 | inotify 时代 |
|--------------|-------------|
| `open(dir,O_RDONLY)` + `fcntl(F_NOTIFY)` | `inotify_add_watch(ifd, dir, mask)` |
| `DN_CREATE` | `IN_CREATE` |
| `DN_DELETE` | `IN_DELETE`（+ 目录自身 `IN_DELETE_SELF`） |
| `DN_RENAME` | `IN_MOVED_FROM`/`IN_MOVED_TO`（+ cookie 配对） |
| `DN_ATTRIB` | `IN_ATTRIB` |
| `DN_ACCESS`/`DN_MODIFY` | `IN_ACCESS`/`IN_MODIFY` |
| `DN_MULTISHOT` | 默认持续（`IN_ONESHOT` 才是一次性——**语义反转**） |
| `F_SETSIG` + realtime 信号 | 普通 fd + `read`/`epoll` |

**语义反转陷阱**：dnotify 默认一次性（要 `DN_MULTISHOT` 才持续）；inotify 默认持续（要 `IN_ONESHOT` 才一次性）。从 dnotify 迁移的代码若按旧直觉「忘了加持续位」，行为反而**更持久**——这类迁移 bug 是静默的。

## 常见坑

| 坑 | 正解 |
|----|------|
| 新项目还在用 dnotify | 一律 inotify；dnotify 只用于读旧代码 |
| 忘了 `DN_MULTISHOT` | 收到一条事件后订阅被清——行为像 `IN_ONESHOT` |
| 忘了 `#define _GNU_SOURCE` | `DN_*` 常量声明不可见（编译错或隐式声明） |
| 在信号处理器里 rescan 目录 | 处理器只能 async-signal-safe 操作；把 si_fd 转投队列，rescan 放主循环 |
| 以为能监控单个文件 | F_NOTIFY **只对目录**；监控文件 inotify 之前没有干净方案（这也解释了它为何被淘汰） |
| 期望「目录能卸载」 | 被 watch 的目录 fd 打开着 → umount `EBUSY`；这是结构性缺陷非配置问题 |

<summary>代码自测（Q&A）</summary>

**Q1：dnotify 为什么把通知绑在「目录 fd」上而不是路径？**
A：实现简单：内核在 inode 的写操作点检查「有没有人 F_NOTIFY 过这个目录」，fd 就是订阅句柄。但这决定了它的三个结构性缺陷（信号通知、无文件名、fd 钉目录）——改进它等于重新设计接口，所以直接诞生了 inotify。

**Q2：realtime 信号真的「不丢」吗？**
A：在排队范围内不合并也不丢，但队列本身有限（`RLIMIT_SIGPENDING`），超限后仍丢。dnotify 时代它比标准信号好得多，但「丢事件」的根本问题要等事件进 fd 队列（inotify）才解决。

**Q3：为什么说 dnotify 的「无文件名」在理论上可以弥补？**
A：`si_fd` 能定位到目录，配合 rescan 可以知道目录现状；缺的是「变更集」。理论上有应用靠「每次 rescan + 与上次快照 diff」运行——功能等价但成本 O(目录)，等于退回轮询，只是轮询的触发点由事件提供。

**Q4：dnotify 能监控「目录树」吗？**
A：和 inotify 一样不递归，但给每个子目录挂 watch 的成本更高（每目录一个 fd，还会钉住所有目录无法卸载）。大规模树监控在 dnotify 时代基本不可行。

**Q5：`F_NOTIFY` 的订阅会被 exec 清掉吗？**
A：订阅随目录 fd 走；exec 不清（fd 属性继承），但如果 fd 带 `FD_CLOEXEC` 则 exec 后 fd 关闭、订阅随之消失。旧代码常忘记这一点，导致 exec 子进程后的监控行为差异。

**Q6：现在还有理由用 dnotify 吗？**
A：只有一种：维护必须在极老内核（无 inotify）上运行的代码。即便如此，新代码也应编译期探测 inotify 可用性并优先使用。教学价值（理解信号驱动接口的缺陷）大于工程价值。

</details>
