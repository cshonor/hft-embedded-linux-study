# 19.2 The inotify API

> 本章：[TLPI 第 19 章 — Monitoring File Events](../README.md)

## 本节讲什么

介绍 Linux inotify 机制：监控文件/目录的创建、修改、删除等事件。涵盖 `inotify_init1()`、`inotify_add_watch()`、`read()` 事件流的完整编程模型。

## 要点

### inotify 核心 API

| 函数 | 原型 | 说明 |
|------|------|------|
| `inotify_init1(flags)` | `int inotify_init1(int flags)` | 创建 inotify 实例 fd |
| `inotify_add_watch(fd, path, mask)` | `int inotify_add_watch(int fd, const char *path, uint32_t mask)` | 添加监控，返回 watch fd |
| `inotify_rm_watch(fd, wd)` | `int inotify_rm_watch(int fd, int wd)` | 移除监控 |
| `read(fd, buf, n)` | 标准 read | 读取事件数据 |

### inotify_init1 flags

| flag | 说明 |
|------|------|
| `IN_NONBLOCK` | 设置 fd 为非阻塞 |
| `IN_CLOEXEC` | exec 时自动关闭 |

### 事件类型（mask）

| 事件 | 含义 |
|------|------|
| `IN_ACCESS` | 文件被读取 |
| `IN_MODIFY` | 文件被修改 |
| `IN_ATTRIB` | 属性改变（mode/uid/size） |
| `IN_CLOSE_WRITE` | 可写文件被关闭 |
| `IN_CLOSE_NOWRITE` | 只读文件被关闭 |
| `IN_OPEN` | 文件被打开 |
| `IN_MOVED_FROM` | 文件被移走 |
| `IN_MOVED_TO` | 文件被移入 |
| `IN_CREATE` | 创建文件/目录 |
| `IN_DELETE` | 删除文件/目录 |
| `IN_DELETE_SELF` | 监控对象本身被删除 |
| `IN_MOVE_SELF` | 监控对象本身被移走 |
| `IN_ALL_EVENTS` | 所有事件 |
| `IN_MOVE` | MOVED_FROM \| MOVED_TO |
| `IN_CLOSE` | CLOSE_WRITE \| CLOSE_NOWRITE |
| `IN_DONT_FOLLOW` | 不跟随符号链接 |
| `IN_MASK_ADD` | 追加到已有 mask |
| `IN_ONESHOT` | 只报告一次事件 |
| `IN_ONLYDIR` | 只监控目录（非目录返回错误） |

### inotify_event 结构

```c
struct inotify_event {
    int      wd;       /* watch descriptor */
    uint32_t mask;     /* 触发的事件 mask */
    uint32_t cookie;   | 重命名关联 cookie（同一操作的 FROM/TO cookie 相同） */
    uint32_t len;      /* name 字段长度 */
    char     name[];   /* 可选：子文件名（监控目录时） */
};
```

### 事件读取模式

```
fd = inotify_init1(IN_NONBLOCK | IN_CLOEXEC);
wd = inotify_add_watch(fd, "/data/orders", IN_CREATE | IN_MODIFY | IN_DELETE);

char buf[4096] __attribute__((aligned(8)));
ssize_t n = read(fd, buf, sizeof(buf));

/* buf 中包含多个 struct inotify_event，需遍历 */
char *p = buf;
while (p < buf + n) {
    struct inotify_event *ev = (struct inotify_event *)p;
    /* 处理 ev... */
    p += sizeof(struct inotify_event) + ev->len;
}
```

### 事件合并与溢出

| 情况 | 行为 |
|------|------|
| 多个相同事件 | 内核可能合并（丢弃中间事件） |
| 队列满 | `IN_Q_OVERFLOW` 事件，wd=-1 |
| 读取太慢 | 事件被丢弃 |

## HFT / 嵌入式关联

- **配置热加载**：监控配置文件 `IN_MODIFY`，自动重新加载策略参数
- **订单文件监控**：监控订单目录 `IN_CREATE`，新订单文件到达时自动处理
- **日志轮转**：监控日志文件 `IN_MOVE_SELF`，触发重打开日志 fd
- **嵌入式**：inotify 需要内核 `CONFIG_INOTIFY_USER=y`，精简系统可能未启用
- **与 epoll 集成**：inotify fd 可以加入 epoll 事件循环，与网络 I/O 统一管理

## 代码示例

```c
#include <sys/inotify.h>
#include <unistd.h>
#include <stdio.h>
#include <string.h>

static void handle_event(struct inotify_event *ev) {
    printf("wd=%2d mask=0x%08x ", ev->wd, ev->mask);
    if (ev->mask & IN_CREATE)  printf("[CREATE] ");
    if (ev->mask & IN_MODIFY)  printf("[MODIFY] ");
    if (ev->mask & IN_DELETE)  printf("[DELETE] ");
    if (ev->mask & IN_MOVED_FROM) printf("[MOVED_FROM] ");
    if (ev->mask & IN_MOVED_TO)   printf("[MOVED_TO] ");
    if (ev->len > 0) printf("name=%s", ev->name);
    printf("\n");
}

int watch_dir(const char *path) {
    int ifd = inotify_init1(IN_CLOEXEC);
    if (ifd == -1) { perror("inotify_init1"); return -1; }

    uint32_t mask = IN_CREATE | IN_MODIFY | IN_DELETE
                  | IN_MOVED_FROM | IN_MOVED_TO;
    int wd = inotify_add_watch(ifd, path, mask);
    if (wd == -1) { perror("inotify_add_watch"); return -1; }

    char buf[4096] __attribute__((aligned(8)));
    while (1) {
        ssize_t n = read(ifd, buf, sizeof(buf));
        if (n <= 0) break;
        char *p = buf;
        while (p < buf + n) {
            struct inotify_event *ev = (struct inotify_event *)p;
            handle_event(ev);
            p += sizeof(struct inotify_event) + ev->len;
        }
    }
    close(ifd);
    return 0;
}
```

## 代码自测

<details>
<summary>1. 监控目录时，IN_MODIFY 事件中 name 字段的含义？</summary>

当监控的是目录，目录中某个文件被修改时，`name` 字段包含被修改文件的文件名。当监控的是文件本身，事件中 `name` 为空（`len=0`），因为被修改的就是被监控的文件本身。
</details>

<details>
<summary>2. IN_MOVED_FROM 和 IN_MOVED_TO 的 cookie 有什么作用？</summary>

重命名操作产生两个事件：`IN_MOVED_FROM`（旧路径）和 `IN_MOVED_TO`（新路径）。两个事件可能有不同的 watch wd（如果源和目标在不同监控目录）。`cookie` 在同一重命名操作的两个事件中相同，用于关联它们，重建完整的重命名操作。
</details>

<details>
<summary>3. inotify 事件队列满了怎么办？</summary>

队列满时，内核丢弃溢出的事件并发送一个 `IN_Q_OVERFLOW` 事件（wd=-1, mask=0x2000）。处理溢出：(1) 记录警告日志；(2) 重新扫描所有监控目录，比对当前状态与上次记录的差异；(3) 如果无法恢复完整状态，可能需要重启监控。
</details>
