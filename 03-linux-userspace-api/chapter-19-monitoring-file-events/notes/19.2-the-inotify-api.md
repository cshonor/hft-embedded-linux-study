## 本节讲什么

三个 syscall 的完整契约，以及四个**必须钉住**的语义：

1. `inotify_init1()` 创建实例 fd（`IN_NONBLOCK`/`IN_CLOEXEC`）；
2. `inotify_add_watch()` 返回 `wd`——**同一 inode 重复 add 是「修改 mask」并返回同一个 wd**；
3. `inotify_rm_watch()` 会触发一条 `IN_IGNORED` 事件（不是静默消失）；
4. watch 挂 inode 不挂路径 → 改名不丢监控、删除自动失效。

---

## 要点：三个 syscall

```c
#include <sys/inotify.h>
int inotify_init1(int flags);        /* IN_NONBLOCK | IN_CLOEXEC；返回实例 fd */
int inotify_add_watch(int fd, const char *pathname, uint32_t mask);
                                     /* 返回 watch descriptor（wd） */
int inotify_rm_watch(int fd, int wd);
```

| 调用 | 成功返回 | 典型失败 |
|------|---------|---------|
| `inotify_init1` | 实例 fd | `EMFILE`（实例数超 `/proc/sys/fs/inotify/max_user_instances`）、`ENOMEM` |
| `inotify_add_watch` | wd（非负） | `ENOSPC`（watch 数超 `max_user_watches`）、`EACCES`、`EINVAL`（`IN_ONLYDIR` 但不是目录） |
| `inotify_rm_watch` | 0 | `EINVAL`（wd 无效） |

## 要点：mask 的两个身份

同一套 `IN_*` 位在两个地方出现，身份不同：

| 身份 | 出现位置 | 例子 |
|------|---------|------|
| **事件位**（发生了什么） | `read` 出来的 `ev->mask` | `IN_CREATE`、`IN_MODIFY`、`IN_ISDIR` |
| **订阅位**（想看什么） | `inotify_add_watch` 的 mask 参数 | 同名位 + 控制位 `IN_ONLYDIR` 等 |

订阅位多出来的**控制位**（不表示事件）：

| 控制位 | 作用 |
|--------|------|
| `IN_ONLYDIR` | 只监控目录；路径不是目录则报 **`ENOTDIR`**（内核 v6.6 `fs/notify/inotify/inotify_user.c:756` 用 `LOOKUP_DIRECTORY` 让路径解析层直接拒绝，`fs/namei.c:2822` 附近返回 `-ENOTDIR`） |
| `IN_DONT_FOLLOW` | 不跟随符号链接：监控**链接本身** |
| `IN_EXCL_UNLINK` | 已 unlink 的子项不再报告（防临时文件噪音） |
| `IN_MASK_ADD` | **追加**而不是替换已有 mask（重复 add 同一 inode 时） |
| `IN_ONESHOT` | 一次性：首个事件后自动移除 watch |

> ⚠️ 注意 `IN_ONLYDIR` 与老接口的差异：它让「是目录吗」的检查**原子化**（否则「stat 判目录 + add_watch」之间可被换）——与 Ch18 §18.6 的 `mkdir` 原子检查同一设计哲学。

## 要点：重复 add_watch 的语义（最容易写错的一条）

```c
int wd1 = inotify_add_watch(fd, "/var/data", IN_CREATE);
int wd2 = inotify_add_watch(fd, "/var/data", IN_MODIFY);
/* wd1 == wd2 —— 同一 inode！且此时 mask 是 **IN_MODIFY**（替换语义），
   原来的 IN_CREATE 丢了；要叠加必须 IN_MASK_ADD：
   inotify_add_watch(fd, "/var/data", IN_MODIFY | IN_MASK_ADD); */
```

**推论**：通过**不同路径**（如硬链接、或 `..` 拼接的不同写法）add 同一 inode，得到的也是**同一个 wd**。应用维护 `wd → 路径` 映射时，路径只是「第一次 add 时的名字」，不是稳定身份。

## 要点：watch 的生命周期

| 事件 | watch 会怎样 | 应用要做什么 |
|------|-------------|-------------|
| 监控的**目录**里文件被删/移出 | watch 不受影响（watch 的是目录） | — |
| 监控的**文件本身**被删除 | watch 失效，队列里出现 `IN_IGNORED`（带 `IN_DELETE_SELF` 前后伴随） | 清理 wd 映射 |
| 监控的文件/目录被**改名** | watch 依然有效（挂 inode） | 路径名变了，展示层要自己跟进 |
| 所在文件系统被**卸载** | 失效 + `IN_UNMOUNT` + `IN_IGNORED` | 全量清理 |
| `inotify_rm_watch` | 队列里出现 `IN_IGNORED` | 事件循环里清映射，别只清本地变量 |
| `IN_ONESHOT` | 首个事件后自动移除 | 想续就重新 add |

## 要点：标准程序骨架（本仓库两个 demo 的两种形态）

```c
/* 形态 A：阻塞 read（inotify_dir.c）*/
int ifd = inotify_init1(IN_CLOEXEC);
inotify_add_watch(ifd, dir, mask);
for (;;) {
    char buf[BUF_LEN];
    ssize_t n = read(ifd, buf, sizeof buf);      /* 阻塞直到有事件 */
    for (char *p = buf; p < buf + n; ) {         /* 变长记录遍历 */
        struct inotify_event *ev = (void *) p;
        /* ... 处理 ev ... */
        p += sizeof(*ev) + ev->len;
    }
}

/* 形态 B：非阻塞 + epoll（inotify_epoll.c，Ch63 的预演）*/
int ifd = inotify_init1(IN_NONBLOCK | IN_CLOEXEC);
int epd = epoll_create1(0);
epoll_ctl(epd, EPOLL_CTL_ADD, ifd, &(struct epoll_event){ .events = EPOLLIN });
for (;;) { epoll_wait(...); read(ifd, ...); /* EAGAIN 结束本轮 */ }
```

## 常见坑

| 坑 | 正解 |
|----|------|
| 重复 `add_watch` 期望「再加一路事件」 | **替换**语义；要叠加用 `IN_MASK_ADD`，否则老 mask 静默丢失 |
| 只清 `wd` 映射、不等 `IN_IGNORED` | 事件循环里还会来一条带该 wd 的事件；按 `IN_IGNORED` 清理才完整 |
| `inotify_init()` 老接口 + 手动 `fcntl(FD_CLOEXEC)` | 用 `inotify_init1(IN_CLOEXEC)`，一次原子完成（否则 exec 泄漏 fd 有竞态） |
| 以为 watch 数量可以无限 | `max_user_watches`（默认常被调大）；`ENOSPC` 要有降级路径 |
| 对**文件**的 watch 期望「文件被覆盖后还在」 | 覆盖若经 rename（safe-write），watch 的是**老 inode**——新文件不再被监控！配置热重载要 watch **目录**而不是文件 |
| mask 里忘了 `IN_ISDIR` 判断 | `IN_CREATE` 对文件和目录都触发；建子树监控要 `ev->mask & IN_ISDIR` |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 配置热重载 | watch **目录** + `IN_MOVED_TO|IN_CLOSE_WRITE`——safe-write 的 rename 正好触发；watch 文件会被 rename 换 inode 的行为坑掉（上表） |
| 行情落盘感知 | 目录 `IN_CREATE|IN_CLOSE_WRITE|IN_MOVED_TO`；`IN_CLOSE_WRITE` 才是「写完了」的信号，`IN_CREATE` 只是「名字出现了」 |
| 守护进程 | `IN_CLOEXEC` 必加：exec 子进程不该继承 inotify fd（否则子进程不关就锁住监控） |
| 多实例服务 | 实例数受 `max_user_instances` 限制；每 worker 一个实例即可，别每请求一个 |
| Pi5 复测清单 | ① 重复 add_watch 的替换/`IN_MASK_ADD` 行为；② rename 被监控文件后 wd 是否存活；③ `IN_IGNORED` 的到达时机 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`inotify_add_watch` 返回的 wd 与文件描述符是什么关系？**
A：wd 是**实例内**的编号（跨实例不唯一），fd 是实例本身。同一 inode 在同一实例内重复 add 永远得到同一个 wd（并按替换/`IN_MASK_ADD` 语义改 mask）。跨实例监控同一 inode 则得到两个独立 wd、两份事件。

**Q2：为什么官方推荐 `inotify_init1` 而不是老的 `inotify_init`？**
A：老的没有 flags 参数，`IN_NONBLOCK`/`IN_CLOEXEC` 都得事后 `fcntl` 补——「创建后再设置」在多线程下有窗口（另一线程可能恰好 exec）。`init1` 一步原子完成，与 `open(O_CLOEXEC)` 的教训同源。

**Q3：监控一个被 safe-write 反复替换的配置文件，会发生什么？**
A：watch 挂在**第一次 add 时的 inode** 上。每次 rename 替换都产生新 inode，老 inode（连同 watch）随老文件消失——你会收到 `IN_DELETE_SELF`/`IN_IGNORED`，之后**静默失明**。正解是监控**所在目录**。

**Q4：`IN_MASK_ADD` 与 `IN_ONESHOT` 能组合吗？**
A：`IN_MASK_ADD` 是 mask 维护语义、`IN_ONESHOT` 是生命周期语义，可组合；但 `IN_ONESHOT` + 反复 add 的组合要小心——首个事件后 watch 消失并带 `IN_IGNORED`，此前叠加的 mask 一并清零。

**Q5：`inotify_rm_watch` 之后，事件循环里应该期待什么？**
A：一条 `IN_IGNORED` 事件（wd 对应的事件）。它是 wd 的「讣告」——收到后才能安全地删除 `wd → 路径` 映射。跳过这一步的事件循环会在后续读到「孤儿 wd」。

**Q6：为什么说「wd → 路径」映射里的路径只是快照？**
A：watch 挂 inode：目录被改名后事件继续到达，但 `name` 字段只给**子项**名，目录本身的新路径不在事件里。应用要么在 `MOVED_TO` 等事件里自己维护目录改名，要么接受路径过期（用于日志展示时通常无妨）。

</details>
