## 本章一条主线

**「文件系统是被动数据源，事件接口把它变成主动通知流」**。三代技术的演进就是通知的三个属性逐步工程化：

| 属性 | 轮询 | dnotify | inotify |
|------|------|---------|---------|
| 通知**到达方式** | 自己去问 | 信号（异步、会合并） | **fd 队列**（可 read/可 poll） |
| 通知**内容** | 无（全量扫） | 只有「目录变了」 | 谁（name）+ 什么（mask）+ 改名配对（cookie） |
| 通知**可靠性** | 永不丢但永不及时 | 队列满会丢（溢出也是事件） | 队列满会丢（但 `IN_Q_OVERFLOW` 明说） |

## API 全景

### 生命周期（§19.2）

| 接口 | 一句话 | 关键语义 |
|------|--------|---------|
| `inotify_init1(flags)` | 建实例 | `IN_NONBLOCK`/`IN_CLOEXEC` 一步原子 |
| `inotify_add_watch(fd,path,mask)` | 挂 watch | 返回 wd；同 inode 重复 add = **替换 mask**（`IN_MASK_ADD` 才叠加）；`IN_ONLYDIR` 非目录 → `ENOTDIR` |
| `inotify_rm_watch(fd,wd)` | 摘 watch | 队列里会到一条 `IN_IGNORED` |

### 事件（§19.3）

| 分组 | 事件 | 要点 |
|------|------|------|
| 子项事件（带 `name`） | `IN_CREATE`/`IN_DELETE`/`IN_MOVED_FROM`/`IN_MOVED_TO`/`IN_OPEN`/`IN_ACCESS`/`IN_MODIFY`/`IN_ATTRIB`/`IN_CLOSE_WRITE`/`IN_CLOSE_NOWRITE` | `cookie` 只在 MOVED_FROM/TO 配对 |
| 对象自身（`len==0`） | `IN_DELETE_SELF`/`IN_MOVE_SELF`/`IN_UNMOUNT` | watch 挂 inode：改名不失效、删除即失效 |
| 系统级 | `IN_IGNORED`/`IN_Q_OVERFLOW`（wd=-1）+ 修饰位 `IN_ISDIR` | 前两者是清理与重建的触发器 |
| 读取（§19.4） | `read` 变长记录流 | 步进 `sizeof + len`；缓冲保底 `sizeof + NAME_MAX + 1`；批量 read 摊销 syscall |
| 容量（§19.5） | `max_queued_events`/`max_user_instances`/`max_user_watches` | 溢出静默丢；实例/watch 超限报 `EMFILE`/`ENOSPC` |

## 必须钉住的六条纪律

1. **watch 不递归**：`IN_CREATE|IN_ISDIR`（和 `IN_MOVED_TO|IN_ISDIR`）时补 watch，并立即 rescan 该目录补漏；
2. **watch 挂 inode**：监控「会被 safe-write 替换的文件」必失效——监控**目录**；
3. **读循环先判系统级事件**（`IN_Q_OVERFLOW`→全量重建；`IN_IGNORED`→清映射），再进业务；
4. **重活异步**：事件循环只分派，否则队列溢出只是时间问题（§19.5）；
5. **改名降级安全**：把 MOVED_FROM/TO 处理成「删+建」永远正确，把「删+建」凑成改名是危险升级；
6. **跨平台红线**：macOS 无 inotify；抽象层按 kqueue/FSEvents 的最小公倍数设计，cookie 配对与溢出语义不可假设对齐。

<summary>代码自测（Q&A）</summary>

**Q1：inotify 编程「真正难」的地方在哪？**
A：不在 API（三个 syscall 一页纸），在**一致性**：事件流是异步的、有延迟的、可能丢的，而应用维护的状态必须与文件系统一致。`inotify_dtree.c` 给出的答案是「事件驱动 + 定期校准 + 溢出全量重建」的混合模式——这是所有事件驱动缓存（不止文件系统）的通用架构。

**Q2：为什么说「批量 read + 重活异步」是同一枚硬币的两面？**
A：批量 read 降低的是「消费一条事件」的固定成本；重活异步降低的是「消费一条事件」的可变成本。队列长度（§19.5）限制的是平均消费速度——两者任何一头不到位，队列都会满。

**Q3：迁移自 dnotify 的代码最容易犯什么错？**
A：语义反转（一次性 vs 持续）与「文件名缺失」——旧代码习惯 rescan，新代码看到 name 反而忘了处理 `MOVED_FROM/TO` 配对，把改名当成删除+创建处理时又没做降级（丢 cookie 检查）。

**Q4：监控「目录树」的正确架构是什么？**
A：三层：① `nftw` 初始挂 watch（每目录一个）；② 事件循环里 `IN_CREATE|IN_ISDIR`/`IN_MOVED_TO|IN_ISDIR` 补 watch（add 后立即 rescan 该目录补漏）；③ `IN_DELETE_SELF`/`IN_IGNORED` 清理。习题 19-1 与 `inotify_dtree` 都是这个结构。

**Q5：为什么 inotify 没有被 fanotify 取代？**
A：两者定位不同：inotify 是**进程级**的细粒度通知（面向应用）；fanotify 是**系统级**的文件访问控制/通知（面向安全软件，需要特权，能拦截而非仅观察）。后续还有 eBPF（kprobe vfs 读写）做更深的观测。工具箱是加法不是替换。

**Q6：如果 macOS 版本也要做配置热重载，怎么对齐语义？**
A：kqueue `EVFILT_VNODE`（NOTE_WRITE/NOTE_RENAME/NOTE_DELETE）无 name、无 cookie、无溢出事件——只能监控**具体文件**或靠 rescan。工程做法：抽象层只承诺「有变更」+ 自己 diff；改名配对、溢出重建这些 inotify 独有能力在 macOS 侧降级为全量校验。
