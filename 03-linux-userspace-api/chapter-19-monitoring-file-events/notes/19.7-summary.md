# 19.7 Summary

> 本章：[TLPI 第 19 章 — Monitoring File Events](./README.md)

## 本章回顾

### inotify API 速查

| API | 功能 |
|-----|------|
| `inotify_init1(flags)` | 创建 inotify 实例 |
| `inotify_add_watch(fd, path, mask)` | 添加监控 |
| `inotify_rm_watch(fd, wd)` | 移除监控 |
| `read(fd, buf, n)` | 读取事件 |
| `select()`/`poll()`/`epoll` | 等待事件 |

### 事件类型一览

| 类别 | 事件 |
|------|------|
| 文件内容 | `IN_ACCESS` `IN_MODIFY` `IN_CLOSE_WRITE` `IN_CLOSE_NOWRITE` |
| 属性 | `IN_ATTRIB` |
| 创建/删除 | `IN_CREATE` `IN_DELETE` `IN_DELETE_SELF` |
| 移动 | `IN_MOVED_FROM` `IN_MOVED_TO` `IN_MOVE_SELF` |
| 组合 | `IN_MOVE` `IN_CLOSE` `IN_ALL_EVENTS` |
| 特殊 | `IN_Q_OVERFLOW` `IN_IGNORED` |

### 与旧机制对比

| 特性 | inotify | dnotify (旧) | 轮询 readdir |
|------|---------|-------------|-------------|
| 方式 | 事件驱动 | 信号通知 | 定时扫描 |
| 实时性 | 实时 | 实时 | 延迟 |
| 精度 | 文件级 | 目录级 | 目录级 |
| 开销 | 低 | 中（信号开销） | 高（轮询） |
| 可扩展性 | 好（fd+epoll） | 差（信号） | 差 |
| POSIX | 否（Linux 特有） | 否 | 是 |

### 限制

| 限制 | 查看 | 调整 |
|------|------|------|
| `/proc/sys/fs/inotify/max_user_watches` | 每用户最大监控数 | `sysctl` |
| `/proc/sys/fs/inotify/max_user_instances` | 每用户最大实例数 | `sysctl` |
| `/proc/sys/fs/inotify/max_queued_events` | 队列最大事件数 | `sysctl` |

## HFT / 嵌入式关联

- **配置热加载**：策略参数文件修改触发 `IN_MODIFY`
- **订单文件**：订单目录新文件触发 `IN_CREATE`
- **与 epoll 集成**：inotify fd 加入 epoll，统一事件循环
- **嵌入式限制**：`max_user_watches` 可能不足，监控大量文件时需调整

## 代码自测

<details>
<summary>1. inotify 和 dnotify 的核心区别？</summary>

- **dnotify**（旧机制）：通过信号（SIGIO）通知目录变化，目录级粒度，信号处理复杂，无法知道具体哪个文件变化
- **inotify**（现代）：通过文件描述符读取事件流，文件级粒度，每个事件包含 watch fd、mask、文件名，可与 epoll 集成
- inotify 完全替代了 dnotify，dnotify 已废弃
</details>

<details>
<summary>2. 监控大量文件时，inotify 可能遇到什么问题？</summary>

1. **watch 数量限制**：`max_user_watches` 默认可能较小（8192），监控大量目录/文件时需调高
2. **事件风暴**：大量文件同时修改（如 tar 解压），队列溢出丢事件
3. **内存开销**：每个 watch 占用内核内存（约 1KB）
4. **递归监控**：inotify 不支持递归，监控子树需手动添加每个子目录的 watch
</details>
