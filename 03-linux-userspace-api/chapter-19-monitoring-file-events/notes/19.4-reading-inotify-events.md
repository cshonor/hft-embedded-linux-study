## 本节讲什么

1. `read()` 在 inotify fd 上返回的是**变长记录流**——一次 read 可含多条、半条都不存在；
2. 缓冲要多大、步进怎么算、为什么「一次读一批」在性能上重要；
3. 阻塞 / 非阻塞 / `poll`-`epoll` 三种读法（对应本仓库两个 demo）；
4. `NAME_MAX + 1` 这个「保底缓冲」公式为什么成立。

---

## 要点：read 的语义

```c
char buf[BUF_LEN];
ssize_t n = read(ifd, buf, sizeof buf);
/* n = 本次读到的总字节数（≥ 一条完整事件；== 0 不会出现——队列空且阻塞时 sleep）*/
/* n = -1 且 errno == EAGAIN：非阻塞模式下队列空 */
```

| 模式 | 队列空时 | 队列有事件时 |
|------|---------|-------------|
| 阻塞（默认） | `read` 睡眠直到有事件 | 返回**一到多条**事件（内核把队列里当时所有能放进缓冲的都给你） |
| 非阻塞（`IN_NONBLOCK`） | `-1` + `EAGAIN`/`EWOULDBLOCK` | 同上 |
| `poll`/`epoll` 等就绪再读 | `read` 立即返回（就绪才进来） | 同上 |

**一次 read 最多放得下的事件数** = `min(队列里的事件, 缓冲能装下的条数)`——内核**不会**给半条事件；如果缓冲连一条都装不下，`read` 报 `EINVAL`。

## 要点：缓冲大小公式

```c
/* TLPI 给出的「最坏情况」保底公式 */
#define BUF_LEN (16 * (sizeof(struct inotify_event) + NAME_MAX + 1))
```

| 项 | 含义 |
|----|------|
| `sizeof(struct inotify_event)` | 定长头 16 字节（int + 3×uint32，按 LP64 恰 16） |
| `NAME_MAX + 1` | 最长文件名（通常 255）+ 结尾 NUL；`len` 会补齐对齐，取 +1 是保守估计 |
| ×16 | TLPI 的经验值：一次 read 期望装下 16 条 |

**三条实际规则**：

1. **绝对最小值**是 `sizeof(struct inotify_event) + NAME_MAX + 1`——小于它，`read` 连一条都可能装不下（`EINVAL`）；
2. **批量读更高效**：一次 syscall 处理 N 条事件，比每条一次 read 省 N−1 次陷入；高频场景（`IN_MODIFY` 风暴）差距是数量级；
3. **事件之间无对齐空洞可依赖**——缓冲里的记录边界只由 `sizeof + len` 决定，不能按固定步长切。

## 要点：标准读循环（全章的模板）

```c
for (;;) {
    ssize_t n = read(ifd, buf, sizeof buf);
    if (n == -1) {
        if (errno == EAGAIN) { /* 非阻塞：无事件，去做别的 */ continue; }
        perror("read"); break;
    }
    for (char *p = buf; p < buf + n; ) {
        struct inotify_event *ev = (struct inotify_event *) p;

        if (ev->mask & IN_Q_OVERFLOW)      { rebuild_all(); }        /* 队列溢出 */
        else if (ev->mask & IN_IGNORED)    { drop_watch(ev->wd); }   /* wd 失效 */
        else                               { handle(ev); }           /* 业务 */

        p += sizeof(struct inotify_event) + ev->len;   /* 唯一正确的步进 */
    }
}
```

**`IN_Q_OVERFLOW`/`IN_IGNORED` 的检查要在业务分支之前**——这两条不是普通事件，落在它们上面继续按业务处理会读到无效 wd。

## 要点：三种读法的选择（对应两个 demo + epoll）

| 方案 | 代码形态 | 适用 | 代价 |
|------|---------|------|------|
| 阻塞 read（[`inotify_dir.c`](../code/inotify_dir.c)） | `init1(IN_CLOEXEC)` + 循环 `read` | 专职监控进程、单线程 demo | 无法同时等别的 fd |
| 非阻塞轮询 | `init1(IN_NONBLOCK)` + 空转 `read` | ❌ 几乎不该用 | 空转烧 CPU |
| 非阻塞 + poll/epoll（[`inotify_epoll.c`](../code/inotify_epoll.c)） | `init1(IN_NONBLOCK\|IN_CLOEXEC)` + fd 入 `epoll` | **生产标准**：文件系统事件与网络/定时器同循环 | 多一个 epoll 实例 |

```c
/* epoll 形态骨架（Ch63 的预演）*/
int epd = epoll_create1(0);
struct epoll_event ee = { .events = EPOLLIN };
epoll_ctl(epd, EPOLL_CTL_ADD, ifd, &ee);
for (;;) {
    epoll_wait(epd, events, MAX, -1);
    /* 就绪后循环 read 到 EAGAIN（边缘触发语义下必须读干；水平触发可读一批）*/
}
```

## 要点：读侧的几个细节

| 细节 | 说明 |
|------|------|
| `read` 返回 0 吗 | 正常不会（inotify fd 是「队列」语义）；返回 0 视为异常 |
| 一次 read 里事件**跨 watch** 混排 | 是的，同一实例的所有 watch 的事件按发生序混在一起；按 `ev->wd` 分派 |
| 处理一条事件时又产生新事件 | 新事件入队列，下一轮 read 读到——**事件循环里做重活会导致队列积压**（见 §19.5） |
| `name` 打印 | `printf("%.*s", (int) ev->len, ev->name)`，或先按 `len` 拷出再补 NUL（`len` 含填充） |
| 缓冲复用 | 栈缓冲即可；`read` 是拷贝语义，不持有用户指针 |

## 常见坑

| 坑 | 正解 |
|----|------|
| `read` 后只处理「一条」事件 | 一次 read 可能有多条；必须 `for (p = buf; p < buf+n; p += sizeof+len)` |
| 缓冲按 `sizeof(inotify_event)` 分配 | 装不下带 `name` 的事件 → `EINVAL` 或截断；用保底公式 |
| 事件循环里做重 I/O | 队列积压 → 溢出（`IN_Q_OVERFLOW`）→ 全量重建；重活丢线程池 |
| 忽略 `EAGAIN` 分支（非阻塞模式） | 把「暂无事件」当错误退出 |
| 在 `epoll` 边缘触发下只 read 一次 | ET 必须**读到 EAGAIN**；水平触发则无此要求（Ch63 详述） |
| 处理顺序不管 `IN_IGNORED`/`IN_Q_OVERFLOW` | 先判系统级事件再进业务，见上面模板 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 低延迟落盘感知 | 大缓冲批量 read：一 syscall 拿一簇事件，把「事件到达 → 业务反应」的 syscall 摊销压到最低 |
| 与网络事件同循环 | inotify fd + socket fd 进同一个 `epoll`：行情落盘感知与行情接收零线程切换 |
| 嵌入式低内存 | `16 × (16 + 256)` ≈ 4.3 KB 栈缓冲即可；不必堆大缓冲 |
| 热路径纪律 | 事件循环只做「分派 + 入队」，重活（重载配置、扫描目录）一律异步——否则 §19.5 的队列上限就是你的延迟上界 |
| 调试 | `read` 返回值 / 每条事件的 `(wd, mask, cookie, name)` 打成结构化日志，定位「为什么没收到事件」第一现场 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：为什么一次 read 可以返回多条事件？这违反「read 读一串字节」吗？**
A：不违反——事件流本来就是字节流，只是字节流里有**内部结构**。内核的 `inotify_read` 把队列里的事件逐条拷进用户缓冲直到放不下为止，和管道返回「攒下的多段数据」同构。

**Q2：read 报 EINVAL 最常见的原因？**
A：缓冲连一条完整事件都装不下（内核拒绝给出半条）。按「`sizeof(struct inotify_event) + NAME_MAX + 1` 保底」公式分配即可避免。

**Q3：处理事件时能直接持有 `ev->name` 指针到下一轮循环吗？**
A：不能跨轮。缓冲内容只在「这一次 read 的处理期间」有效，下一轮 read 会覆盖。要保留就拷贝（`strndup(ev->name, ev->len)`）。

**Q4：`IN_NONBLOCK` 下 `read` 返回 n>0 之后还有事件，此时该再 read 吗？**
A：水平触发（poll/epoll 默认）下会再次就绪通知你；但**当轮**一次 read 只拿了缓冲装得下的部分，队列里可能还有。生产做法：无论哪种触发模式，读到 `EAGAIN` 为止，逻辑最简单且对 ET 正确。

**Q5：为什么 demo 里 read 用 4.3 KB 缓冲而不是 1 MB？**
A：批量收益在「前几条」最大，16 条已能摊销绝大多数 syscall 开销；超大缓冲的边际收益趋零，而每轮的内存清零/缓存成本恒定。嵌入式场景 4 KB 也正好是一页的整数倍邻域，对栈友好。

**Q6：事件循环里可以直接调 `inotify_add_watch`（如子树监控）吗？**
A：可以——add 作用于内核数据结构，不影响正在读的缓冲。但**注意顺序**：先 add 后可能漏掉 add 之前发生的创建事件；标准解法是「add 完成后立刻 rescan 该目录一次」，习题 19-1 正是这么处理。

</details>
