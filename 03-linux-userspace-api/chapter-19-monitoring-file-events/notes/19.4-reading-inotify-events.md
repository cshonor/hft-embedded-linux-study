## 本节讲什么

1. `read()` 在 inotify fd 上返回的是**变长记录流**——一次 read 可含多条、半条都不存在；
2. 缓冲要多大、步进怎么算、为什么「一次读一批」在性能上重要；
3. 阻塞 / 非阻塞 / `poll`-`epoll` 三种读法（对应本仓库两个 demo）；
4. `NAME_MAX + 1` 这个「保底缓冲」公式为什么成立。

---

## 要点：read 的语义

```c
char buf[BUF_LEN];
ssize_t n = read(ifd, buf, sizeof buf);
/* n = 本次读到的总字节数（≥ 一条完整事件；== 0 不会出现——队列空且阻塞时 sleep）*/
/* n = -1 且 errno == EAGAIN：非阻塞模式下队列空 */
```

| 模式 | 队列空时 | 队列有事件时 |
|------|---------|-------------|
| 阻塞（默认） | `read` 睡眠直到有事件 | 返回**一到多条**事件（内核把队列里当时所有能放进缓冲的都给你） |
| 非阻塞（`IN_NONBLOCK`） | `-1` + `EAGAIN`/`EWOULDBLOCK` | 同上 |
| `poll`/`epoll` 等就绪再读 | `read` 立即返回（就绪才进来） | 同上 |

**一次 read 最多放得下的事件数** = `min(队列里的事件, 缓冲能装下的条数)`——内核**不会**给半条事件；如果缓冲连一条都装不下，`read` 报 `EINVAL`。

## 要点：缓冲大小公式

```c
/* TLPI 给出的「最坏情况」保底公式 */
#define BUF_LEN (16 * (sizeof(struct inotify_event) + NAME_MAX + 1))
```

| 项 | 含义 |
|----|------|
| `sizeof(struct inotify_event)` | 定长头 16 字节（int + 3×uint32，按 LP64 恰 16） |
| `NAME_MAX + 1` | 最长文件名（通常 255）+ 结尾 NUL；`len` 会补齐对齐，取 +1 是保守估计 |
| ×16 | TLPI 的经验值：一次 read 期望装下 16 条 |

**三条实际规则**：

1. **绝对最小值**是 `sizeof(struct inotify_event) + NAME_MAX + 1`——小于它，`read` 连一条都可能装不下（`EINVAL`）；
2. **批量读更高效**：一次 syscall 处理 N 条事件，比每条一次 read 省 N−1 次陷入；高频场景（`IN_MODIFY` 风暴）差距是数量级；
3. **事件之间无对齐空洞可依赖**——缓冲里的记录边界只由 `sizeof + len` 决定，不能按固定步长切。

## 要点：标准读循环（全章的模板）

```c
for (;;) {
    ssize_t n = read(ifd, buf, sizeof buf);
    if (n == -1) {
        if (errno == EAGAIN) { /* 非阻塞：无事件，去做别的 */ continue; }
        perror("read"); break;
    }
    for (char *p = buf; p < buf + n; ) {
        struct inotify_event *ev = (struct inotify_event *) p;

        if (ev->mask & IN_Q_OVERFLOW)      { rebuild_all(); }        /* 队列溢出 */
        else if (ev->mask & IN_IGNORED)    { drop_watch(ev->wd); }   /* wd 失效 */
        else                               { handle(ev); }           /* 业务 */

        p += sizeof(struct inotify_event) + ev->len;   /* 唯一正确的步进 */
    }
}
```

**`IN_Q_OVERFLOW`/`IN_IGNORED` 的检查要在业务分支之前**——这两条不是普通事件，落在它们上面继续按业务处理会读到无效 wd。

## 要点：三种读法的选择（对应两个 demo + epoll）

| 方案 | 代码形态 | 适用 | 代价 |
|------|---------|------|------|
| 阻塞 read（`code/inotify_dir.c`） | `init1(IN_CLOEXEC)` + 循环 `read` | 专职监控进程、单线程 demo | 无法同时等别的 fd |
| 非阻塞轮询 | `init1(IN_NONBLOCK)` + 空转 `read` | ❌ 几乎不该用 | 空转烧 CPU |
| 非阻塞 + poll/epoll（`code/inotify_epoll.c`） | `init1(IN_NONBLOCK\|IN_CLOEXEC)` + fd 入 `epoll` | **生产标准**：文件系统事件与网络/定时器同循环 | 多一个 epoll 实例 |

```c
/* epoll 形态骨架（Ch63 的预演）*/
int epd = epoll_create1(0);
struct epoll_event ee = { .events = EPOLLIN };
epoll_ctl(epd, EPOLL_CTL_ADD, ifd, &ee);
for (;;) {
    epoll_wait(epd, events, MAX, -1);
    /* 就绪后循环 read 到 EAGAIN（边缘触发语义下必须读干；水平触发可读一批）*/
}
```

## 要点：读侧的几个细节

| 细节 | 说明 |
|------|------|
| `read` 返回 0 吗 | 正常不会（inotify fd 是「队列」语义）；返回 0 视为异常 |
| 一次 read 里事件**跨 watch** 混排 | 是的，同一实例的所有 watch 的事件按发生序混在一起；按 `ev->wd` 分派 |
| 处理一条事件时又产生新事件 | 新事件入队列，下一轮 read 读到——**事件循环里做重活会导致队列积压**（见 §19.5） |
| `name` 打印 | `printf("%.*s", (int) ev->len, ev->name)`，或先按 `len` 拷出再补 NUL（`len` 含填充） |
| 缓冲复用 | 栈缓冲即可；`read` 是拷贝语义，不持有用户指针 |

## 常见坑

| 坑 | 正解 |
|----|------|
| `read` 后只处理「一条」事件 | 一次 read 可能有多条；必须 `for (p = buf; p < buf+n; p += sizeof+len)` |
| 缓冲按 `sizeof(inotify_event)` 分配 | 装不下带 `name` 的事件 → `EINVAL` 或截断；用保底公式 |
| 事件循环里做重 I/O | 队列积压 → 溢出（`IN_Q_OVERFLOW`）→ 全量重建；重活丢线程池 |
| 忽略 `EAGAIN` 分支（非阻塞模式） | 把「暂无事件」当错误退出 |
| 在 `epoll` 边缘触发下只 read 一次 | ET 必须**读到 EAGAIN**；水平触发则无此要求（Ch63 详述） |
| 处理顺序不管 `IN_IGNORED`/`IN_Q_OVERFLOW` | 先判系统级事件再进业务，见上面模板 |

## 代码示例

本节配两个可以独立运行的完整监控器，就是上面「三种读法的选择」表里点名的**形态 A** 与**形态 B**。想抄哪一份取决于你的主循环是「专职等 fs 事件」还是「fs 事件只是若干 fd 之一」。

### 一、`inotify_dir.c`（自编，形态 A：阻塞 `read`）

最小可用的目录监控器：`inotify_init()` → `inotify_add_watch(IN_CREATE|IN_DELETE|IN_MODIFY|IN_ATTRIB|IN_MOVED_FROM|IN_MOVED_TO|IN_CLOSE_WRITE)` → 死循环 `read` → 按变长记录步进 → 逐条打印 `wd`/`cookie`/`mask`/`name`。

完整源码（[`code/inotify_dir.c`](../code/inotify_dir.c)）：

```c
/* Blocking inotify on a directory.
 * cc -Wall -Wextra -o inotify_dir inotify_dir.c
 * ./inotify_dir DIR
 */
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/inotify.h>
#include <unistd.h>

#define BUF_LEN (16 * (sizeof(struct inotify_event) + NAME_MAX + 1))

static void print_mask(uint32_t mask)
{
    if (mask & IN_ACCESS)        printf(" ACCESS");
    if (mask & IN_MODIFY)        printf(" MODIFY");
    if (mask & IN_ATTRIB)        printf(" ATTRIB");
    if (mask & IN_CLOSE_WRITE)   printf(" CLOSE_WRITE");
    if (mask & IN_CLOSE_NOWRITE) printf(" CLOSE_NOWRITE");
    if (mask & IN_OPEN)          printf(" OPEN");
    if (mask & IN_CREATE)        printf(" CREATE");
    if (mask & IN_DELETE)        printf(" DELETE");
    if (mask & IN_DELETE_SELF)   printf(" DELETE_SELF");
    if (mask & IN_MOVE_SELF)     printf(" MOVE_SELF");
    if (mask & IN_MOVED_FROM)    printf(" MOVED_FROM");
    if (mask & IN_MOVED_TO)      printf(" MOVED_TO");
    if (mask & IN_IGNORED)       printf(" IGNORED");
    if (mask & IN_Q_OVERFLOW)    printf(" Q_OVERFLOW");
    if (mask & IN_UNMOUNT)       printf(" UNMOUNT");
    if (mask & IN_ISDIR)         printf(" [DIR]");
}

int main(int argc, char *argv[])
{
    const char *dir;
    int fd, wd;
    char buf[BUF_LEN] __attribute__((aligned(__alignof__(struct inotify_event))));

    if (argc != 2) {
        fprintf(stderr, "usage: %s DIR\n", argv[0]);
        return EXIT_FAILURE;
    }
    dir = argv[1];

    fd = inotify_init();
    if (fd == -1) {
        perror("inotify_init");
        return EXIT_FAILURE;
    }

    wd = inotify_add_watch(fd, dir,
                           IN_CREATE | IN_DELETE | IN_MODIFY | IN_ATTRIB |
                           IN_MOVED_FROM | IN_MOVED_TO | IN_CLOSE_WRITE);
    if (wd == -1) {
        perror("inotify_add_watch");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("watching %s (wd=%d); Ctrl-C to stop\n", dir, wd);

    for (;;) {
        ssize_t n = read(fd, buf, sizeof(buf));
        char *p;

        if (n <= 0) {
            perror("read");
            break;
        }
        for (p = buf; p < buf + n; ) {
            struct inotify_event *ev = (struct inotify_event *)p;
            printf("wd=%d cookie=%u", ev->wd, ev->cookie);
            print_mask(ev->mask);
            if (ev->len > 0)
                printf(" name=\"%s\"", ev->name);
            printf("\n");
            if (ev->mask & IN_Q_OVERFLOW)
                fprintf(stderr, "WARNING: event queue overflow — state may be stale\n");
            p += sizeof(struct inotify_event) + ev->len;
        }
    }

    close(fd);
    return 0;
}
```

### 二、`inotify_epoll.c`（自编，形态 B：非阻塞 + `epoll`，生产标准）

同一件事的**生产写法**：fd 用 `inotify_init1(IN_NONBLOCK | IN_CLOEXEC)` 一次把两个 flag 打进去（避免 `inotify_init()` + `fcntl(FD_CLOEXEC)` 之间 exec 泄漏 fd 的竞态），再把这个 fd 注册进 `epoll`，就绪后**循环读到 `EAGAIN` 为止**。

完整源码（[`code/inotify_epoll.c`](../code/inotify_epoll.c)）：

```c
/* Nonblocking inotify + epoll loop.
 * cc -Wall -Wextra -o inotify_epoll inotify_epoll.c
 * ./inotify_epoll DIR
 */
#include <errno.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/epoll.h>
#include <sys/inotify.h>
#include <unistd.h>

#define BUF_LEN (16 * (sizeof(struct inotify_event) + NAME_MAX + 1))

static void handle_events(int ifd)
{
    char buf[BUF_LEN] __attribute__((aligned(__alignof__(struct inotify_event))));
    char *p;

    for (;;) {
        ssize_t n = read(ifd, buf, sizeof(buf));
        if (n == -1) {
            if (errno == EAGAIN)
                return;
            perror("read");
            return;
        }
        if (n == 0)
            return;

        for (p = buf; p < buf + n; ) {
            struct inotify_event *ev = (struct inotify_event *)p;
            printf("event mask=0x%x", ev->mask);
            if (ev->len)
                printf(" name=%s", ev->name);
            if (ev->mask & (IN_MOVED_FROM | IN_MOVED_TO))
                printf(" cookie=%u", ev->cookie);
            if (ev->mask & IN_Q_OVERFLOW)
                printf(" <<OVERFLOW>>");
            printf("\n");
            p += sizeof(struct inotify_event) + ev->len;
        }
    }
}

int main(int argc, char *argv[])
{
    const char *dir;
    int ifd, efd, wd;
    struct epoll_event ev, events[1];

    if (argc != 2) {
        fprintf(stderr, "usage: %s DIR\n", argv[0]);
        return EXIT_FAILURE;
    }
    dir = argv[1];

    ifd = inotify_init1(IN_NONBLOCK | IN_CLOEXEC);
    if (ifd == -1) {
        perror("inotify_init1");
        return EXIT_FAILURE;
    }

    wd = inotify_add_watch(ifd, dir,
                           IN_CREATE | IN_DELETE | IN_MODIFY |
                           IN_MOVED_FROM | IN_MOVED_TO | IN_CLOSE_WRITE);
    if (wd == -1) {
        perror("inotify_add_watch");
        close(ifd);
        return EXIT_FAILURE;
    }

    efd = epoll_create1(EPOLL_CLOEXEC);
    if (efd == -1) {
        perror("epoll_create1");
        close(ifd);
        return EXIT_FAILURE;
    }

    ev.events = EPOLLIN;
    ev.data.fd = ifd;
    if (epoll_ctl(efd, EPOLL_CTL_ADD, ifd, &ev) == -1) {
        perror("epoll_ctl");
        close(efd);
        close(ifd);
        return EXIT_FAILURE;
    }

    printf("epoll+inotify on %s; Ctrl-C to stop\n", dir);
    for (;;) {
        int n = epoll_wait(efd, events, 1, -1);
        if (n == -1) {
            if (errno == EINTR)
                continue;
            perror("epoll_wait");
            break;
        }
        if (events[0].data.fd == ifd)
            handle_events(ifd);
    }

    close(efd);
    close(ifd);
    return 0;
}
```

编译与运行（**Linux / Pi5 专有**——本机 macOS 无 `sys/inotify.h`）：

```bash
cc -Wall -Wextra -o inotify_dir    inotify_dir.c
cc -Wall -Wextra -o inotify_epoll  inotify_epoll.c

mkdir -p /tmp/tlpi_inotify
./inotify_dir /tmp/tlpi_inotify
# 另一终端制造事件：
#   touch /tmp/tlpi_inotify/a; echo x >> /tmp/tlpi_inotify/a; rm /tmp/tlpi_inotify/a
#   mv /tmp/tlpi_inotify/x /tmp/tlpi_inotify/y   ← 观察 IN_MOVED_FROM/TO 的 cookie 配对
```

**预期事件序列**（按 `inotify(7)` 语义推演，非实测）：

| 操作 | `inotify_dir` 预期输出（形态 A） | `inotify_epoll` 预期输出（形态 B） |
|------|--------------------------------|----------------------------------|
| 启动 | `watching /tmp/tlpi_inotify (wd=1); Ctrl-C to stop` | `epoll+inotify on /tmp/tlpi_inotify; Ctrl-C to stop` |
| `touch a` | `wd=1 cookie=0 CREATE name="a"` | `event mask=0x100 name=a` |
| `echo x >> a` | `wd=1 cookie=0 MODIFY name="a"` 后接 `CLOSE_WRITE` | `event mask=0x2 name=a` 后接 `event mask=0x8 name=a` |
| `rm a` | `wd=1 cookie=0 DELETE name="a"` | `event mask=0x400 name=a` |
| `mv x y` | `wd=1 cookie=NN MOVED_FROM name="x"` + `wd=1 cookie=NN MOVED_TO name="y"` | `event mask=0x40 name=x cookie=NN` + `event mask=0x80 name=y cookie=NN` |
| `mkdir d` | 多一个 ` [DIR]` 后缀（`CREATE name="d" [DIR]`） | 无 `IN_ISDIR` 分支——形态 B 没打印它，需自行补 |

**逐条解读**：

- **两个程序对 `IN_ISDIR` 的处理不同**：形态 A 的 `print_mask()` 打印 `[DIR]`，形态 B 没打印。这不是 bug，是刻意展示「mask 里哪些位值得看由你决定」——`IN_ISDIR` 只是 `IN_CREATE`/`IN_DELETE`/`IN_MOVED_*` 的**修饰位**，不单独构成事件。
- **形态 B 的 `for(;;)` 内层循环不能省**：`epoll` 只告诉你「有数据可读」，一条就绪通知背后可能有**一批**事件。读到 `EAGAIN` 才返回，才能在边缘触发（`EPOLLET`）语义下不漏事件；水平触发下读一批也行，但读干是更稳的写法。
- **`epoll_wait` 的 `EINTR` 必须 `continue`**：注册了信号处理器（或 `SA_RESTART` 未生效）时，`epoll_wait` 会被打断返回 `-1/EINTR`。这不是错误，直接重试即可——把它当错误 `break` 会让监控器被一个无关信号莫名杀死。
- **`events[0].data.fd == ifd` 这层判断在生产代码里是必须的**：真实程序会把 inotify fd、监听 socket、timerfd、signalfd 全塞进同一个 `epoll`，就绪的是哪个 fd 必须分流。这里只有一个 fd 显得多余，但骨架照抄到多 fd 场景就能直接用（Ch63 会展开）。
- **`IN_Q_OVERFLOW` 的处理位置不同**：形态 A 在打印完之后才 `fprintf(stderr, ...)` 警告；形态 B 直接在 `printf` 里打 `<<OVERFLOW>>`。两种都行，关键是**必须判**——溢出意味着有事件被静默丢弃，本地缓存的状态已经不可信（见 [19.5](19.5-queue-limits-and-proc-files.md)）。
- **`read()` 返回 `0` 的语义**：形态 A 把它归到 `n <= 0` 一起 `break`；形态 B 单独判 `n == 0` 直接 `return`。inotify fd 上返回 0 在语义上不该发生，两处都按「异常但退出」处理，与 Listing 19-1 的 `fatal()` 是同一判断。

**源码坐标**：本节两个程序为**自编**（原书无此节对应的完整程序；原书 Listing 19-1 `demo_inotify.c` 见 [19.2](19.2-the-inotify-api.md)）。相关接口：`inotify_init1(2)`、`read(2)`、`epoll(7)`、`epoll_create1(2)`、`epoll_ctl(2)`、`epoll_wait(2)`；内核 `fs/notify/inotify/inotify_user.c`（read 侧拷贝语义）、`fs/eventpoll.c`（就绪通知）。

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 低延迟落盘感知 | 大缓冲批量 read：一 syscall 拿一簇事件，把「事件到达 → 业务反应」的 syscall 摊销压到最低 |
| 与网络事件同循环 | inotify fd + socket fd 进同一个 `epoll`：行情落盘感知与行情接收零线程切换 |
| 嵌入式低内存 | `16 × (16 + 256)` ≈ 4.3 KB 栈缓冲即可；不必堆大缓冲 |
| 热路径纪律 | 事件循环只做「分派 + 入队」，重活（重载配置、扫描目录）一律异步——否则 §19.5 的队列上限就是你的延迟上界 |
| 调试 | `read` 返回值 / 每条事件的 `(wd, mask, cookie, name)` 打成结构化日志，定位「为什么没收到事件」第一现场 |

<summary>代码自测（Q&A）</summary>

**Q1：为什么一次 read 可以返回多条事件？这违反「read 读一串字节」吗？**
A：不违反——事件流本来就是字节流，只是字节流里有**内部结构**。内核的 `inotify_read` 把队列里的事件逐条拷进用户缓冲直到放不下为止，和管道返回「攒下的多段数据」同构。

**Q2：read 报 EINVAL 最常见的原因？**
A：缓冲连一条完整事件都装不下（内核拒绝给出半条）。按「`sizeof(struct inotify_event) + NAME_MAX + 1` 保底」公式分配即可避免。

**Q3：处理事件时能直接持有 `ev->name` 指针到下一轮循环吗？**
A：不能跨轮。缓冲内容只在「这一次 read 的处理期间」有效，下一轮 read 会覆盖。要保留就拷贝（`strndup(ev->name, ev->len)`）。

**Q4：`IN_NONBLOCK` 下 `read` 返回 n>0 之后还有事件，此时该再 read 吗？**
A：水平触发（poll/epoll 默认）下会再次就绪通知你；但**当轮**一次 read 只拿了缓冲装得下的部分，队列里可能还有。生产做法：无论哪种触发模式，读到 `EAGAIN` 为止，逻辑最简单且对 ET 正确。

**Q5：为什么 demo 里 read 用 4.3 KB 缓冲而不是 1 MB？**
A：批量收益在「前几条」最大，16 条已能摊销绝大多数 syscall 开销；超大缓冲的边际收益趋零，而每轮的内存清零/缓存成本恒定。嵌入式场景 4 KB 也正好是一页的整数倍邻域，对栈友好。

**Q6：事件循环里可以直接调 `inotify_add_watch`（如子树监控）吗？**
A：可以——add 作用于内核数据结构，不影响正在读的缓冲。但**注意顺序**：先 add 后可能漏掉 add 之前发生的创建事件；标准解法是「add 完成后立刻 rescan 该目录一次」，习题 19-1 正是这么处理。
