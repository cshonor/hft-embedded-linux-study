## 本节讲什么

文件系统事件监控的**三代技术**，以及为什么 dnotify 被淘汰：

1. 轮询（`readdir`/`stat` 周期扫描）——正确但昂贵；
2. dnotify——信号驱动，每目录一个 fd，事件粒度粗且**不带文件名**；
3. inotify——fd 化的事件队列，粒度细、可多路复用，是现代 Linux 的标准答案。

---

## 要点：三代技术对照

| | 轮询 | dnotify（1999） | inotify（2.6.13, 2005） |
|--|------|-----------------|-------------------------|
| 模型 | 主动周期扫描 | **信号**驱动（SIGIO） | **fd 事件队列** |
| 粒度 | 无（全量扫） | 目录级，事件种类少（`DN_ACCESS`/`DN_MODIFY`/`DN_CREATE`/`DN_DELETE`/`DN_RENAME`/`DN_ATTRIB`） | 文件级 + 目录级，十余种事件 |
| 通知里带文件名吗 | — | ❌（**必须自己 rescan 目录**找出变了谁） | ✅（`name` 字段） |
| 资源占用 | 高（持续 I/O + syscall） | 每目录占一个 fd（fd 挂着目录 → **目录无法卸载**） | 一个 inotify 实例 + 每 watch 一条内核记录 |
| 与 I/O 多路复用 | — | 信号（难整合，realtime 信号可缓解） | ✅ `poll`/`select`/`epoll` 天然可等 |
| 现状 | 特定场景仍用 | **已淘汰**（TLPI 只留一节） | Linux 标准 |

## 要点：inotify 的核心心智模型

```
inotify 实例（fd）
 ├── watch 1: /var/data  (mask=IN_CREATE|IN_DELETE|…)  → wd=1
 ├── watch 2: /var/log   (mask=…)                       → wd=2
 └── …
 事件队列（内核排队，read() 读出 struct inotify_event 序列）
```

- **fd 是实例**，`wd` 是实例内的 watch 编号——`read()` 出来的事件带着 `wd`，应用自己维护 `wd → 路径` 映射；
- **watch 挂在 inode 上**，不是路径上：监控中的文件被改名/移动，watch 依然有效（这是与直觉相反、也最常被误解的一点）；
- **不递归**：watch 一个目录只看它的**直接子项**；子树要逐目录建 watch（习题 19-1 正是练这个）。

## 为什么「监控文件变化」比看起来难

| 难点 | 轮询 | dnotify | inotify 的回答 |
|------|------|---------|----------------|
| 谁动了哪个文件 | 全量 diff | 不知道（要 rescan） | `name` 字段直接给 |
| 改名是「删+建」还是「改名」 | 看不出来 | 看不出来 | `MOVED_FROM/TO` + **cookie 配对** |
| 大目录高频变更 | 扫不过来 | 信号风暴 | 队列 + 限流（§19.5） |
| 与主事件循环整合 | 定时器 | 信号处理器的异步地狱 | 就是一个普通 fd |

## 常见坑（全章预告，详见各节）

| 坑 | 正解 | 节 |
|----|------|----|
| 以为 watch 是递归的 | 只看直接子项；`IN_CREATE|IN_ISDIR` 时补 watch | 19.2 |
| `read` 缓冲按 `sizeof(inotify_event)` 算 | 变长记录：至少 `sizeof + NAME_MAX + 1`，按 `len` 步进 | 19.4 |
| 以为 `MOVED_FROM/TO` 是两个独立事件 | 用 `cookie` 配对；配不上（如跨挂载点移出）会只有一个 | 19.3 |
| 忽略 `IN_Q_OVERFLOW` | 事件**丢了**，必须全量重建 | 19.5 |
| 忽略 `IN_IGNORED` | watch 已失效（删/卸载/`rm_watch`），映射表要清 | 19.3 |
| 继续用 dnotify | 只有读旧代码时才需要；新代码一律 inotify | 19.6 |

## HFT / 嵌入式关联

| 场景 | 本章机制怎么兑现 |
|------|----------------|
| 配置热重载 | watch 配置目录 `IN_CLOSE_WRITE|IN_MOVED_TO`（safe-write 落盘正好触发 `IN_MOVED_TO`，见 Ch18 §18.4）→ 重载策略 |
| 行情文件落盘感知 | 数据目录 `IN_CREATE|IN_CLOSE_WRITE` → 新文件立即可读（比轮询省一个数量级延迟） |
| 嵌入式只读根 | flash 上 watch 开销极小，但 `IN_UNMOUNT`/`IN_IGNORED` 处理是固件鲁棒性的一部分 |
| macOS/跨平台 | 等价物是 kqueue（`EVFILT_VNODE`）或 FSEvents——**语义不对齐**（尤其 cookie 配对与队列溢出语义），跨平台抽象层要按最小公倍数设计 |
| 与 Ch63 的关系 | inotify fd 可以直接进 `epoll`——「文件系统事件」与「网络事件」在同一个事件循环里 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：为什么 dnotify 需要「每目录一个 fd」会成为致命缺点？**
A：① fd 是有限资源，大规模目录监控直接耗尽；② 打开的目录 fd 使目录处于「使用中」，**无法卸载**所在文件系统（挂载管理噩梦）；③ 事件通过信号送达，信号没有队列语义（标准信号会合并），只能配合 realtime 信号 + `SA_SIGINFO` 缓解。

**Q2：inotify 的 watch 为什么「挂 inode 不挂路径」？**
A：内核实现（`fs/notify/inotify/`）是 inode 上的钩子（`fsnotify` 连接器）。好处：改名/移动不丢监控；代价：目录被删除时 watch 自动失效（`IN_IGNORED`），应用必须清理映射。两种行为都要显式处理。

**Q3：inotify 能监控 NFS/网络文件系统吗？**
A：一般不能——事件由本地内核在 vnode 操作点产生，网络 FS 的远端变更不会触发（部分实现支持本地缓存行为）。生产上跨机同步不能依赖 inotify，要做协议层通知。

**Q4：macOS 上做等价功能的正确姿势？**
A：单目录细粒度用 kqueue `EVFILT_VNODE`（NOTE_WRITE/NOTE_DELETE/...，同样不带名字）；整树监控用 FSEvents（带路径但粒度粗、延迟更高）。与 inotify 的**语义差异**（尤其改名配对）要在抽象层抹平，不能假设一一对应。

</details>
