# 19.5 Queue Limits and /proc Files 队列限制与 /proc 文件

> 本章：[TLPI 第 19 章 — Monitoring File Events](../README.md)

## 本节讲什么

1. 三个 sysctl knob 分别限制什么（队列长度 / 实例数 / watch 数）；
2. 队列溢出的确切语义：丢事件 + `IN_Q_OVERFLOW`——**不可恢复，必须重建**；
3. 为什么「事件循环做重活」是这个节失败的第一原因；
4. 生产上的容量规划方法。

---

## 要点：三个 sysctl

| `/proc/sys/fs/inotify/…` | 限制什么 | 常见默认 | 超限错误 |
|--------------------------|---------|---------|---------|
| `max_queued_events` | 单实例**事件队列**长度（内核排队上限） | 16384 | 不报错——**静默丢事件**，队列里补一条 `IN_Q_OVERFLOW` |
| `max_user_instances` | **每真实用户**可建的 inotify 实例数 | 128 | `inotify_init1` → `EMFILE` |
| `max_user_watches` | **每真实用户**挂的 watch 总数 | 8192（发行版常调到几十万） | `inotify_add_watch` → `ENOSPC` |

读写方式与所有 sysctl 相同（`open`+`write`，Ch12 的坑同样适用——**写完回读验证**）：

```bash
cat /proc/sys/fs/inotify/max_user_watches
sudo sysctl fs.inotify.max_user_watches=524288     # 或直接 echo > /proc/...
```

> ⚠️ 默认值**不是 API 契约**：不同内核/发行版差异很大（尤其 `max_user_watches`，桌面发行版常已调大）。容量规划读 `/proc`，别写死数字。

## 要点：溢出的确切语义（本节最重要的一段）

```
事件产生速率 > 应用消费速率
        ↓
内核队列填满 max_queued_events 条
        ↓
再来的事件【被丢弃】，同时往队列尾追加一条 IN_Q_OVERFLOW（wd == -1）
        ↓
应用读到 IN_Q_OVERFLOW → 唯一正确反应：全量 rescan + 重建 watch 集合
```

三个必须钉住的点：

1. **静默丢**：溢出不返回错误、不 `EMFILE`——应用不处理 `IN_Q_OVERFLOW` 就是「丢事件而不自知」，监控状态从此与文件系统失同步；
2. **丢多少不知道**：溢出事件只告诉你「发生过溢出」，不告诉你丢了哪些；增量修补不可能，只能重建；
3. **重建的正确姿势**：先 `rm` 全部 watch（或干脆废弃实例重建一个），再 `nftw` 全量扫一遍树重建 watch 集合（习题 19-1 的结构）——重建期间的变更由扫描本身兜住。

## 要点：为什么队列会满（三个根因）

| 根因 | 机理 | 缓解 |
|------|------|------|
| **事件循环做重活** | 处理一条事件花 50 ms，产生速率 100/s → 队列 5 s 塞满 | 重活丢线程池；循环只分派 |
| 订阅了高频事件 | `IN_MODIFY` 对大文件流式写是**每次 write 一条** | 只订阅必要的写侧事件（`IN_CLOSE_WRITE`） |
| watch 太多、目录太热 | `IN_ATTRIB` 在 `atime`/ctime 变更时也触发（含读！） | 按需订阅；`IN_EXCL_UNLINK` 去临时文件噪音 |

## 要点：容量规划速查

```c
/* 事件量级估算（设计期做，不是运行期猜）：
 *   行情落盘目录：每秒 N 个文件 × 每 3 事件（CREATE/MOVED_TO/CLOSE_WRITE）
 *   = 3N 事件/秒。N=1000 → 3000/s。
 *   若消费循环最坏停顿 T 秒，队列需 ≥ 3000×T。
 *   T 由「重活最大时长」决定——这再次说明重活必须异步。*/
```

| 参数 | 经验值 |
|------|--------|
| 单实例队列 | 默认 16384，多数场景够；批处理停顿 > 5 s 就要调大**或**改设计 |
| watch 数 | 目录树规模 × 1.2 余量；`max_user_watches` 不足时 `ENOSPC` 是**清晰**错误，可捕获后降级为轮询 |
| 实例数 | 每进程 1~2 个；容器里注意 `max_user_instances` 是**每用户**全局的（同 uid 的所有容器共享） |

## 常见坑

| 坑 | 正解 |
|----|------|
| 不处理 `IN_Q_OVERFLOW` | 丢事件不自知；收到就全量重建（没有中间态） |
| 用 `EMFILE`/`ENOSPC` 之外的方式判断溢出 | 溢出**不报错**；唯一信号就是那条 overflow 事件 |
| 调大 `max_queued_events` 当作解决方案 | 治标：只是把「必现」变「偶现」；根因是消费太慢或订阅太宽 |
| 忽略 `max_user_instances` 的**每用户**语义 | 同 uid 的所有进程（含容器、systemd 服务）共享额度；128 个实例很容易被泄漏的实例吃光 |
| `echo` 写 sysctl 后不回读验证 | Ch12 的坑：偏移/权限问题可能导致静默失败；`cat` 确认 |
| 认为 watch 数超限是实例错误 | `ENOSPC` 来自 `add_watch`，单条失败——按「第 N 个目录失败」处理，别整个实例放弃 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 行情落盘监控 | 事件量级按「文件数/秒 × 3」预估；消费循环只分派，重活（解析行情）异步 |
| 配置热重载 | 事件率极低（人改配置的频率），默认队列绰绰有余；但要防「编辑器保存风暴」——`IN_ATTRIB`（备份/编辑器 swap）会放大事件量 |
| 嵌入式 watchdog | 收到 `IN_Q_OVERFLOW` 视为「监控子系统降级」，触发自检/告警而不是继续假装正常 |
| 容器化部署 | `max_user_instances`/`max_user_watches` 是**用户级**共享额度；同一节点多容器要预算分配（或 runtime 里统一调大 sysctl） |
| 降级路径 | watch 建不起来（`ENOSPC`）→ 降级为周期 `nftw` 扫描（慢但正确）；降级开关要有日志与指标 |
| 容量告警 | 监控脚本定期读 `/proc/sys/fs/inotify/*` 与实际用量（`/proc/PID/fd` 侧不直接可见，靠自统计），逼近上限前告警 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：溢出后为什么不选择「丢弃一半旧事件、保留新的」这类增量策略？**
A：因为丢了什么不可知——可能是「目录被删」这样改变结构的事件，增量修补的假设已失效。全量重建（rescan + 重挂 watch）是唯一能证明「状态与文件系统一致」的操作，且实现简单、无死角。

**Q2：`max_user_watches` 超限的 `ENOSPC` 和磁盘满的 `ENOSPC` 怎么区分？**
A：来源不同——`inotify_add_watch` 返回的 `ENOSPC` 是 watch 配额；`write` 返回的是磁盘。errno 无处标注来源，靠调用点区分。应用日志里应写明「add_watch 的 ENOSPC（watch 配额）」。

**Q3：事件队列是每个 inotify 实例一个，还是每个 watch 一个？**
A：每**实例**一个。实例内所有 watch 的事件混排在同一队列里（§19.4 的一次 read 混排多 watch 事件就是这个原因）。

**Q4：`IN_Q_OVERFLOW` 占不占队列长度？**
A：占。溢出时内核先丢新事件，再把 overflow 事件排进队尾——如果队列当时满到连 overflow 都放不下，会先腾出位置。所以 overflow 保证**可达**（这正是它的设计目的），但不保证及时。

**Q5：`max_user_instances` 按「真实用户」统计是什么意思？**
A：按 `real UID` 计（`fsnotify` 的成本计费对象）。同一 uid 下 root 运行的所有服务、所有容器共享 128 的额度；互相挤兑时后建的 `inotify_init1` 直接 `EMFILE`。多服务同机部署要预算或调大。

**Q6：怎么在不改 sysctl 的前提下降低队列压力？**
A：三招：① 收窄 mask（去掉 `IN_ACCESS`/`IN_OPEN` 这类高频读侧事件）；② `IN_EXCL_UNLINK` 去临时文件噪音；③ 消费提速——批量 read + 重活异步。三者都是应用层改动，比调内核参数可控得多。

</details>
