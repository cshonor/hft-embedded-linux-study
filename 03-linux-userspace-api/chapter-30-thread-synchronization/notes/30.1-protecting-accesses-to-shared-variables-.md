## 本节讲什么

1. **竞态到底怎么发生的**——`x++` 在 CPU 层面是三条指令，两条线程交错执行就会丢更新；本节用实测数据（跨核丢失 52%）和一段 objdump 反汇编证明两件事：竞态是真的，而且**编译器还可能把你的整个循环合并成一条加法指令，让竞态"看起来消失"**。
2. **`pthread_mutex_*` 全家 API**——静态/动态初始化、`lock/trylock/timedlock/unlock`、错误码约定（返回值而非 `errno`）、四种锁类型（NORMAL/ERRORCHECK/RECURSIVE/ADAPTIVE_NP）。
3. **mutex 的内核底座：futex**——无竞争时 mutex 完全在用户态（一条 CAS，实测 7.1 ns）；有竞争才陷入内核，睡在 `struct futex_hash_bucket` 的优先级链表上。本节把 `FUTEX_WAIT` / `FUTEX_WAKE` 的内核路径逐步拆开，包括那段著名的「先锁哈希桶再读用户内存」的加锁顺序注释。

## 一、竞态：丢更新到底怎么发生的

### 1.1 `x++` 不是一条指令

C 语句 `shared++` 编译到 x86-64 至少是三条指令：

```asm
        mov    shared(%rip), %rax    ; ① 读
        add    $1, %rax              ; ② 改（寄存器里）
        mov    %rax, shared(%rip)    ; ③ 写
```

两条线程同时执行这个序列，交错就会**丢失更新**（lost update）：

```
时间 →         shared 初值 = 100

线程 A                          线程 B
mov shared,%rax   ; A 读到 100
                                 mov shared,%rax   ; B 也读到 100
add $1,%rax       ; A: 101
                                 add $1,%rax       ; B: 101
mov %rax,shared   ; 写回 101
                                 mov %rax,shared   ; 写回 101  ← 覆盖了 A 的结果

两个 ++，只 +1。丢了一次。
```

### 1.2 实测：跨核 4 线程丢失 52%

本节配套基准（WSL2 / 12 核 / gcc -O2，`pthread_barrier` 强制 4 线程同时开跑）：

```c
static volatile long shared;          /* ⭐ volatile：gcc 无法合并，每次都真读真写 */
static void *worker(void *a){
    pthread_barrier_wait(&bar);       /* 4 线程同时起跑 */
    for (int i = 0; i < 500000; i++) shared++;
    return NULL;
}
```

实测结果（4 线程 × 500,000 次）：

| 场景 | 耗时 | 得到 / 期望 | 丢失 |
|------|------|------------|------|
| 无保护 `volatile ++`（跨核） | 1.8 ns/次 | 959,293 / 2,000,000 | **52.04%** |
| 无保护 `volatile ++`（4 线程全钉 CPU0） | 3.4 ns/次 | 2,000,000 / 2,000,000 | 0.00% |
| 无保护 读→延迟→写（放大窗口） | 97.3 ns/次 | 30,454 / 80,000 | **61.93%** |
| mutex 保护（跨核） | 69.3 ns/次 | 2,000,000 / 2,000,000 | 0.00% |
| mutex 保护（全钉 CPU0） | 26.7 ns/次 | 2,000,000 / 2,000,000 | 0.00% |

三个结论：

1. **竞态是真实且严重的**：跨核场景下超过一半的自增凭空消失，而且程序**不崩溃、不报错**——这正是竞态的可怕之处，它静悄悄地破坏数据。
2. **「放大窗口」丢得更多**（61.93%）：把 读→算→写 的窗口人为拉宽（模拟临界区里夹着真实计算），碰撞概率随之上升。竞态丢失率 ≈ 窗口宽度 × 竞争强度。
3. **全钉单核丢失 0.00% ≠ 安全**：单核上线程靠时间片切换交错，只有恰好在 ① 和 ③ 之间被抢占才会丢。窗口 ~3 ns，时间片 ~ms 级，概率约 10⁻⁶ 量级——2,000,000 次实验碰上 0 次很正常。**换个核数、换个负载、换个编译器，它就可能丢**。把这段代码放进一个只跑单核的嵌入式盒子？中断和实时任务照样在 ①③ 之间打断你。

### 1.3 ⭐ 反直觉：编译器能把 50 万次 `++` 合并成 1 次加法

第一次做这个实验时，无保护版本**丢失 0.00%、耗时 0.3 ns/次**——明显不可信。排查后用 objdump 抓到了铁证。对下面这段代码：

```c
static long shared;                              /* 注意：非 volatile */
void f(void){ for (int i = 0; i < 500000; i++) shared++; }
```

`gcc -O2 -c` 后反汇编：

```asm
0000000000000000 <f>:
   0:   f3 0f 1e fa             endbr64
   4:   48 81 05 xx xx xx xx    addq   $0x7a120, 0x0(%rip)   ; shared += 500000
   b:   20 a1 07 00
   f:   c3                      ret
```

`0x7a120` = 500000。**整个循环被合并成一条 `shared += 500000`**。这是合法优化：单线程语义下（as-if 规则）`500000 次自增` ≡ `加 500000`；`shared` 没有 `volatile`/`_Atomic` 修饰，编译器没有义务假设别的线程会碰它。于是 4 个线程各自只在循环结束时做**一次**读改写——次数少了三个数量级，时间上又恰好错开，丢失率归零。

这一坑有两层教训：

| 教训 | 含义 |
|------|------|
| **测竞态必须 `volatile`（或 `_Atomic`）** | 否则你测的是编译器，不是调度器 |
| **无同步的共享访问连"看起来对"都保证不了** | 编译器可以重排、合并、缓存；C 内存模型下这就是 UB。竞态不只是"调度时机问题"，**编译器也在跟你的共享变量捣乱** |

> 这也解释了一个经典悖论：「我加了 printf 调试，bug 消失了」——printf 是函数调用，编译器不能跨调用合并读写，副作用变多了，竞态窗口被 printf 的微秒级耗时稀释到测不到。

## 二、`pthread_mutex_*` API

### 2.1 初始化与销毁

```c
/* 静态初始化：文件作用域全局/静态变量，零运行时开销 */
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

/* 动态初始化：栈上/堆上变量，或需要设置属性时 */
pthread_mutex_t mtx;
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
/* ... 设置类型/robust/协议 ... */
pthread_mutex_init(&mtx, &attr);
pthread_mutexattr_destroy(&attr);

pthread_mutex_destroy(&mtx);   /* 销毁：必须处于未锁定状态，否则 UB */
```

- `PTHREAD_MUTEX_INITIALIZER` 等价于全零初始化：glibc 的 `__kind` 字段为 0 = `PTHREAD_MUTEX_TIMED_NP`（普通锁）。
- **禁止拷贝 mutex**：`pthread_mutex_t a = b;` 行为未定义。mutex 的身份（等待队列挂在它上面）不可复制。

### 2.2 加锁与解锁

```c
int pthread_mutex_lock    (pthread_mutex_t *mutex);            /* 阻塞 */
int pthread_mutex_trylock (pthread_mutex_t *mutex);            /* 非阻塞：拿不到返回 EBUSY */
int pthread_mutex_timedlock(pthread_mutex_t *mutex,
                            const struct timespec *abstime);   /* 绝对时间超时 */
int pthread_mutex_unlock  (pthread_mutex_t *mutex);
```

三条约定：

1. **错误码从返回值拿，不走 `errno`**——这是 Pthreads 的风格（区别于大多数系统调用）。检查方式是 `if (pthread_mutex_lock(&m) != 0)`。
2. `timedlock` 的 `abstime` 是**绝对时间**（`CLOCK_REALTIME` 基准），不是时长。到点拿不到锁返回 `ETIMEDOUT`。绝对时间的意义：即使 `timedlock` 被信号打断重启，超时时刻不变。
3. `lock` 是取消点（cancellation point，Ch32 主题），`timedlock` 同样。

### 2.3 四种锁类型

```c
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_NORMAL);        /* 0：默认 */
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);    /* 1 */
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_RECURSIVE);     /* 2 */
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ADAPTIVE_NP);   /* 3，GNU 扩展 */
```

| 类型 | 同线程二次 lock | 非持有者 unlock | 解锁次数 | 开销 | 适用 |
|------|----------------|----------------|----------|------|------|
| `NORMAL`（默认） | **死锁**（通常） | UB | 1:1 | 最低 | 生产代码（你知道自己在干什么） |
| `ERRORCHECK` | 立即返回 `EDEADLK` | 返回 `EPERM` | 1:1 | 每次 lock/unlock 都做完整检查 | 调试期 |
| `RECURSIVE` | 计数 +1 | — | 必须与 lock 次数相等 | 维护 `__count` | 递归函数/回调链（**能用别用**，见下） |
| `ADAPTIVE_NP`（glibc） | 同 NORMAL | 同 NORMAL | 1:1 | 先自旋 ~100 次再 futex 睡 | 短临界区、竞争短暂 |

关于 `RECURSIVE` 的忠告：可重入锁掩盖设计问题——它允许你在不知道调用链上游是否已持锁的情况下"安全"地再次加锁，等于**放弃了"这段代码对锁的可见性"这一设计约束**。通常更好的做法是把"需要持锁的内部函数"和"对外接口"分层（内部函数要求已持锁，接口函数负责加锁）。

`ERRORCHECK` 的价值实测见本章代码示例演示 3：同线程二次 `lock` 返回 `EDEADLK`、解锁后再 `unlock` 返回 `EPERM`——`NORMAL` 锁在同样场景下分别是死锁和 UB。

> TLPI 还提到 `PTHREAD_MUTEX_STALLED` vs `PTHREAD_MUTEX_ROBUST`（robust mutex：持锁线程意外终止后，下一个拿锁者得到 `EOWNERDEAD` 而不是永久死等）。robust 属于 Ch32 之后的高级话题，这里先记住入口：`pthread_mutexattr_setrobust()`。

## 三、深入内核：mutex 的底座是 futex

### 3.1 glibc 视角：一条 CAS 的快路径

glibc（NPTL）的 `pthread_mutex_t` 核心字段（`sysdeps/nptl/bits/thread-shared-types.h`）：

```c
struct __pthread_mutex_s {
    int __lock;          /* ⭐ futex 词：0=空闲 1=锁定无等待者 2=锁定有等待者 */
    unsigned int __count; /* RECURSIVE 的计数 */
    int __owner;         /* 持有者 TID（0=无人持有）*/
    unsigned int __nusers;
    int __kind;          /* 类型：NORMAL/ERRORCHECK/RECURSIVE/ADAPTIVE/ROBUST... */
    short __spins; short __elision;   /* ADAPTIVE 自旋计数 */
    __pthread_list_t __list;          /* robust 链表 */
};
```

`lock` 的逻辑（简化伪码）：

```c
pthread_mutex_lock(m):
    if (CAS(&m->__lock, 0 → 1))        /* 快路径：一条 lock cmpxchg */
        m->__owner = mytid;            /* 无竞争，全程用户态，~7 ns */
    else
        慢路径: 自旋若干次（ADAPTIVE）→ syscall(futex, &m->__lock,
                 FUTEX_WAIT_PRIVATE, 2, ...)  /* 睡眠，让出 CPU */
```

`unlock` 的逻辑：

```c
pthread_mutex_unlock(m):
    old = atomic_exchange(&m->__lock, 0);   /* 归零并取旧值 */
    if (old == 2)                            /* 有等待者 */
        syscall(futex, &m->__lock, FUTEX_WAKE_PRIVATE, 1, ...)
```

三个数字（实测，见 §5）串起来就是这套设计的意义：

| 操作 | 实测耗时 | 本质 |
|------|---------|------|
| 无竞争 lock+unlock | 7.1 ns | 两次原子指令（用户态 CAS），**零系统调用** |
| 空 futex 系统调用（FUTEX_WAKE 无等待者） | 203.4 ns | 系统调用本身的底价 |
| 有竞争的 lock+unlock（跨核） | 69.3 ns | 缓存行在核间乒乓 + 偶发 futex |

**futex 的核心设计哲学**（Rusty Russell 2002 年引入，名字 = *fast userspace mutex*）：**无竞争时同步根本不需要内核**——内核只负责"有人睡着时叫醒他"这一件事。等待队列在内核，锁的状态字在用户内存。

### 3.2 futex 全景图

内核侧（v6.6）的静态结构：

```
用户地址空间                        内核地址空间
┌──────────────┐                  ┌──────────────────────────────────┐
│ pthread_mutex│                  │  struct futex_hash_bucket[]       │
│  __lock: int │────hash──────▶   │  （全局数组 futex_queues，         │
└──────────────┘   jhash2(key)    │   ____cacheline_aligned_in_smp）  │
                                  │                                   │
   key 的三要素：                  │   ┌─────────────────────────┐    │
   · private: (mm, uaddr, offset)│   │ atomic_t  waiters        │    │
   · shared : (inode, pgoff)     │   │ spinlock_t lock          │    │
     （跨进程锁用同一把时          │   │ plist_head chain   ◀────┼──┐  │
       key 必须落在同一个          │   └─────────────────────────┘  │  │
       inode 上）                 │       ... 按 hash 分布 ...       │  │
                                  │                                 │  │
                                  │   struct futex_q（每个睡着的    │  │
                                  │   任务一个，挂进 chain）：       │  │
                                  │   ┌─────────────────────────┐  │  │
                                  │   │ plist_node list ────────┼──┼──┘
                                  │   │ task_struct *task       │  │
                                  │   │ spinlock_t *lock_ptr    │  │
                                  │   │ union futex_key key     │  │
                                  │   │ futex_pi_state *pi_state│  │ ← PI 锁才用
                                  │   │ u32 bitset              │  │
                                  │   └─────────────────────────┘  │
                                  └──────────────────────────────────┘
```

要点（`kernel/futex/futex.h:45` / `:96`）：

- **哈希桶按地址哈希**：`futex_hash():115`（`kernel/futex/core.c`）对 `union futex_key` 做 `jhash2`，`& futex_queues[hash & (futex_hashsize-1)]`。**不同地址可能落进同一个桶**（哈希碰撞），所以桶内还要用 `futex_match()` 逐个比对 key 才能唤醒——`futex_wake()` 里的 `plist_for_each_entry_safe` 循环就是干这个的。
- **`plist`（优先级链表）**：等待队列不是 FIFO，是按优先级排序的。`FUTEX_WAKE` 唤醒 nr 个**优先级最高**的等待者——实时线程优先醒来。这也是优先级继承（PI futex）的基础设施。
- **`____cacheline_aligned_in_smp`**：哈希桶按缓存行对齐，避免相邻桶的锁在 SMP 上假共享。

### 3.3 `FUTEX_WAIT` 内核路径：先锁桶、再读用户内存

`syscall(SYS_futex, &m->__lock, FUTEX_WAIT_PRIVATE, expected, ...)` 进入内核后（`syscalls.c:164` → `do_futex():85` 分发 → `waitwake.c:632 futex_wait`）：

```c
/* kernel/futex/waitwake.c:577 —— 关键路径全部展开 */
int futex_wait_setup(u32 __user *uaddr, u32 val, ..., struct futex_q *q,
                     struct futex_hash_bucket **hb)
{
    /*
     * Access the page AFTER the hash-bucket is locked.   ⭐ :584
     * Order is important:
     *   Userspace waiter: val = var; if (cond(val)) futex_wait(&var, val);
     *   Userspace waker:  if (cond(var)) { var = new; futex_wake(&var); }
     *
     * The basic logical guarantee of a futex is that it blocks ONLY
     * if cond(var) is known to be true at the time of blocking... :590
     */
retry:
    get_futex_key(uaddr, ..., &q->key, ...);       /* 算 key（:220，core.c）*/
    *hb = futex_q_lock(q);                          /* ① 先锁哈希桶 */
    ret = futex_get_value_locked(&uval, uaddr);     /* ② 桶锁保护下读用户内存 */
    ...
    if (uval != val) {                              /* ③ 值已变 → 不睡 */
        futex_q_unlock(*hb);
        ret = -EWOULDBLOCK;                         /*    返回让用户态重试 */
    }
    return ret;
}
```

为什么要**先锁桶、再读值**？注释（`:584-598`）给出了教科书级的解释，值得逐句消化：

- futex 的基本逻辑保证：**任务只会因为"入睡那一刻 `*uaddr` 仍然等于 expected"而睡着**。
- 如果顺序反过来（先读值、再锁桶入队），窗口期内唤醒方可能：改值 → 锁桶 → 发现无人 → 解锁 → 唤醒 0 个；然后睡眠方才锁桶入队，读到的却是**旧值检查已经通过**的状态，于是永远睡下去——**丢失唤醒**。
- `expected` 参数（用户态传进来的 `val`）就是防线：如果读到的当前值 ≠ expected，说明"检查谓词"和"入睡"之间值已经变了，内核返回 `-EWOULDBLOCK`（用户态看到的就是 `EAGAIN`），**用户态重读重试**。这套「读值-比较-入睡」原子性正是 30.2 条件变量 `while` 谓词能成立的内核保证。

成功通过检查后（`futex_wait():632` 后半）：

```c
futex_wait_queue(hb, &q, to);   /* 入队（plist 按优先级插好）→ set_current_state
                                   (TASK_INTERRUPTIBLE) → spin_unlock(hb) →
                                   schedule()：让出 CPU，直到被 wake/信号/超时 */
```

### 3.4 `FUTEX_WAKE` 内核路径：延迟到锁外唤醒

```c
/* kernel/futex/waitwake.c:143 —— 逐行标注 */
int futex_wake(u32 __user *uaddr, unsigned int flags, int nr_wake, u32 bitset)
{
    ...
    get_futex_key(uaddr, ..., &key, ...);          /* 同一把 key */
    hb = futex_hash(&key);                          /* 同一个桶 */

    if (!futex_hb_waiters_pending(hb))              /* ⭐ :161 无等待者早退 */
        return ret;                                 /*    连 spinlock 都不拿！*/

    spin_lock(&hb->lock);
    plist_for_each_entry_safe(this, next, &hb->chain, list) {
        if (futex_match(&this->key, &key)) {        /* key 相同（桶内有碰撞）*/
            ...
            futex_wake_mark(&wake_q, this);         /* 摘队 + 入 wake_q */
            if (++ret >= nr_wake) break;            /* 唤醒够了 nr 个 */
        }
    }
    spin_unlock(&hb->lock);
    wake_up_q(&wake_q);                             /* ⭐ 锁外才真正唤醒 */
    return ret;
}
```

两个精妙设计：

1. **`futex_hb_waiters_pending()` 早退**（`:161`）：桶上有个 `atomic_t waiters` 计数，睡眠方入队时递增。唤醒方先无锁读这个计数，为 0 直接返回——这就是 `pthread_mutex_unlock` 无等待者时的路径，也是实测「空 FUTEX_WAKE 203 ns」里进一步省掉桶锁的优化。mutex 无竞争解锁甚至**连这个系统调用都不发**（`__lock` 从 1 归 0 即可，只有旧值为 2——"有等待者"——才唤醒）。
2. **`wake_up_q()` 延迟到锁外**（`futex_wake_mark():115`）：先把要唤醒的任务摘出链表、挂到栈上的 `wake_q`，**释放 `hb->lock` 之后**才逐个 `try_to_wake_up()`。原因：唤醒是慢操作（要拿目标任务的 `pi_lock`、改状态、可能触发负载均衡），拿着哈希桶自旋锁做这些会让其他 CPU 上的 futex 操作全部空转。

## 四、死锁

### 4.1 两大成因与四个必要条件

成因一：**同线程对普通锁二次 lock**（自锁）。`NORMAL` 锁通常永久死锁——第二次 `lock` 的 futex 睡在自己持有的锁上，永远无人唤醒。

成因二：**多锁加锁顺序不一致**（ABBA）：

```
线程 1                          线程 2
lock(A)  ✓
                                lock(B)  ✓
lock(B)  …等 B（B 在线程 2 手里）
                                lock(A)  …等 A（A 在线程 1 手里）
                                ↯ 互相等待，永久僵死
```

经典理论框架——死锁的四个必要条件（同时满足才死锁）：

| # | 条件 | 破坏法 |
|---|------|--------|
| 1 | 互斥 | 有的资源没法共享（锁天然满足）|
| 2 | 持有并等待 | 一次性申请全部锁（先拿"总锁"再拿细分锁）|
| 3 | 不可剥夺 | `trylock` + 失败放弃已持有的锁 |
| 4 | 循环等待 | **全局统一加锁顺序**（最常用）|

### 4.2 防御清单

```c
/* 防御 1：全局锁序（按地址/ID 排序，谁小先锁谁） */
void transfer(account_t *from, account_t *to, long amt) {
    account_t *first  = (from < to) ? from : to;    /* 指针序也是全序 */
    account_t *second = (from < to) ? to   : from;
    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);
    ...
}

/* 防御 2：trylock + 退避（拿不到就全部放掉重来） */
for (;;) {
    pthread_mutex_lock(&a);
    if (pthread_mutex_trylock(&b) == 0) break;     /* 两把都到手 */
    pthread_mutex_unlock(&a);                       /* 放掉 a，退避 */
    usleep(1000 + rand() % 1000);                   /* 加随机抖动防活锁 */
}

/* 防御 3：timedlock 探测（嵌入式看门狗思路，本章代码示例演示 4） */
struct timespec ts; clock_gettime(CLOCK_REALTIME, &ts);
ts.tv_nsec += 200 * 1000000;  /* 200ms 后必须拿到 */
if (pthread_mutex_timedlock(&b, &ts) == ETIMEDOUT)
    /* 超时 = 高度怀疑死锁：打日志、放锁、退出重试 */
```

调试利器：`ERRORCHECK` 锁能抓住自锁（返回 `EDEADLK`）；更重的武器是 `pthread_mutex_timedlock` 全局看门狗与 ThreadSanitizer（TSan，见 [03.6 用户态调试](../../../03.6-userspace-debugging/README.md)）。

## 五、实测开销解剖（WSL2 / 12 核 / gcc -O2）

### 5.1 全量数据

```
[A] 单线程基线（各 2,000,000 次）
  volatile ++  无保护（下限）   :   3.1 ns/次
  atomic fetch_add relaxed      :  13.8 ns/次
  mutex  lock+unlock 无竞争     :   7.1 ns/次
  spin   lock+unlock 无竞争     :  15.1 ns/次
  futex(FUTEX_WAKE) 空唤醒      : 203.4 ns/次（系统调用下限）

[D] 4 线程竞争，同一临界区 500,000 次 ++
  atomic fetch_add              :  25.5 ns/次   0% 丢失
  mutex  保护（跨核）           :  69.3 ns/次   0% 丢失
  mutex  保护（全钉 CPU0）      :  26.7 ns/次   0% 丢失
  spinlock 保护（跨核）         :  81.0 ns/次   0% 丢失

[E] futex WAIT+WAKE 乒乓往返    :  67.8 µs/次（WSL2 虚拟化放大，native 约 1~5 µs）
```

### 5.2 每个数字背后的机制

| 数字 | 解释 |
|------|------|
| 无竞争 mutex 7.1 ns < atomic 13.8 ns | mutex 快路径 = 一次 `lock cmpxchg`（`__lock: 0→1`）；`atomic_fetch_add` 是 `lock xadd`（读写都走总线仲裁），还多一次返回值依赖。**无竞争时 mutex 是最便宜的原语之一** |
| spinlock 无竞争 15.1 ns | `pthread_spin_lock` 的 `pthread_spin` 有 QSBR/测试版本差异，glibc 实现含 `atomic_exchange` + 编译器屏障，比单 CAS 贵 |
| 钉 CPU0 的 mutex（26.7 ns）vs 跨核（69.3 ns） | 跨核时锁的缓存行在 4 个核的 L1 之间乒乓（MESI 的 Invalid→Exclusive 迁移），每次 CAS 都是一次跨核缓存一致性事务；钉单核时缓存行不动，只有时间片切换的额外开销 |
| spinlock 跨核 81.0 ns > mutex 69.3 ns | 反直觉但合理：4 个核同时自旋，**自旋本身就在持续锤那个缓存行**，让持有者更难推进（持锁核每次解锁也要抢缓存行）。多核 + 临界区不极短时，自适应 mutex（先短自旋再睡）完胜纯自旋 |
| 空系统调用 203 ns | 进出内核的固定底价（含 KPTI 页表切换）。一切"要不要陷入内核"的优化都要先跟这个数比 |
| ⚠ WSL2 唤醒 67.8 µs | 虚拟化环境的调度延迟被显著放大，**绝对值不可信，只看量级和相对关系**。native Linux 上 futex 乒乓典型值 1~5 µs（见 [05-linux-kernel](../../../05-linux-kernel/README.md) 调度部分） |

### 5.3 一句话结论

**mutex 的价格结构是"阶梯"**：无竞争一条 CAS（7 ns）；跨核竞争缓存行乒乓（70 ns）；真的睡过去再被叫醒（微秒级，含两次系统调用 + 调度器）。选型时真正要想清楚的是：你的临界区会不会经常走到第三档。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT · 热路径 | 一核一线程架构下锁几乎无竞争——此时 mutex 就是一条 7 ns 的 CAS，**够快，不必上无锁结构**。真正的敌人是偶发的"睡过去"：一次 futex 睡眠 + 唤醒 = 微秒级尾延迟。热路径锁必须保证快路径永远命中（临界区纳秒级、无 IO、无长循环） |
| HFT · 优先级反转 | 低优先级行情线程持锁，高优先级订单线程等锁；中间优先级的 GC/日志线程再抢占低优先级 → 高优先级被"间接"拖住毫秒级。解药：`PTHREAD_PRIO_INHERIT`（内核路径：`futex_lock_pi` → `rt_mutex`，见 §衔接）或干脆热路径无锁 |
| HFT · 锁序纪律 | 多锁必循全局锁序；code review 时锁序是必查项。死锁在压测里不一定现形，生产高峰才爆 |
| 嵌入式 · 单核 | 单核≠无竞态（时间片 + 中断同样交错窗口）。但单核上**自旋锁是活锁**（持有者等不到 CPU），临界区内禁用抢占的自旋变体是内核态做法；用户态单核直接用 mutex（睡 = 让出 CPU 给持有者） |
| 嵌入式 · RTOS | 优先级反转的经典案例是 Mars Pathfinder（1997，VxWorks 优先级继承救场）。POSIX mutex 的 `PTHREAD_PRIO_INHERIT` / `PTHREAD_PRIO_PROTECT` 是同名机制的 pthread 接口 |

## 代码示例

`mutex_demo.c`（配套实测，gcc -O2 -Wall -Wextra 零告警编译通过）：

```c
/* mutex_demo.c — Ch30.1：竞态复现、mutex 修复、ERRORCHECK、timedlock 死锁探测
 * 编译：gcc -O2 -Wall -Wextra -o mutex_demo mutex_demo.c -pthread
 */
#include <stdio.h>
#include <string.h>
#include <pthread.h>
#include <time.h>

static double now_ns(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
    return t.tv_sec*1e9+t.tv_nsec;}

#define NT 4
#define M  200000
static pthread_barrier_t bar;

/* ---------- 演示 1：volatile++ 的真竞态（gcc 无法合并 volatile RMW） ---------- */
static volatile long vshared;
static void *vworker(void *a){(void)a;
    pthread_barrier_wait(&bar);                    /* 4 线程同时起跑 */
    for (int i = 0; i < M; i++) vshared++;
    return NULL;}

static void demo_volatile_race(void){
    pthread_t t[NT];
    vshared = 0;
    pthread_barrier_init(&bar, NULL, NT);
    for (int i = 0; i < NT; i++) pthread_create(&t[i], NULL, vworker, NULL);
    for (int i = 0; i < NT; i++) pthread_join(t[i], NULL);
    pthread_barrier_destroy(&bar);
    printf("[demo1] volatile++ 无保护 : 得到 %ld / 期望 %ld（丢失 %.1f%%）\n",
           vshared, (long)NT*M, 100.0*((long)NT*M - vshared)/(NT*(double)M));
}

/* ---------- 演示 2：同一份代码，mutex 修复 ---------- */
static long mshared;
static pthread_mutex_t mx = PTHREAD_MUTEX_INITIALIZER;
static void *mworker(void *a){(void)a;
    pthread_barrier_wait(&bar);
    for (int i = 0; i < M; i++) {
        pthread_mutex_lock(&mx);
        mshared++;
        pthread_mutex_unlock(&mx);
    }
    return NULL;}

static void demo_mutex_fix(void){
    pthread_t t[NT];
    mshared = 0;
    pthread_barrier_init(&bar, NULL, NT);
    double t0 = now_ns();
    for (int i = 0; i < NT; i++) pthread_create(&t[i], NULL, mworker, NULL);
    for (int i = 0; i < NT; i++) pthread_join(t[i], NULL);
    double dt = now_ns() - t0;
    pthread_barrier_destroy(&bar);
    printf("[demo2] mutex  保护        : 得到 %ld / 期望 %ld（丢失 %.1f%%，"
           "%.1f ns/次）\n",
           mshared, (long)NT*M,
           100.0*((long)NT*M - mshared)/(NT*(double)M),
           dt / (NT*(double)M));
}

/* ---------- 演示 3：ERRORCHECK 抓非法操作 ---------- */
static void demo_errorcheck(void){
    pthread_mutex_t m;
    pthread_mutexattr_t a;
    pthread_mutexattr_init(&a);
    pthread_mutexattr_settype(&a, PTHREAD_MUTEX_ERRORCHECK);
    pthread_mutex_init(&m, &a);

    pthread_mutex_lock(&m);
    int r2 = pthread_mutex_lock(&m);          /* 同线程二次 lock */
    pthread_mutex_unlock(&m);
    int r4 = pthread_mutex_unlock(&m);        /* 已解锁再 unlock */
    printf("[demo3] ERRORCHECK: 二次lock=%s 解锁后再unlock=%s\n",
           r2 ? strerror(r2) : "0", r4 ? strerror(r4) : "0");
    /* NORMAL 锁在这两处的下场分别是：死锁 和 未定义行为 */
    pthread_mutex_destroy(&m);
    pthread_mutexattr_destroy(&a);
}

/* ---------- 演示 4：ABBA 死锁 + timedlock 探测 ---------- */
static pthread_mutex_t dlA = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t dlB = PTHREAD_MUTEX_INITIALIZER;

static void *dl_one(void *x){(void)x;
    pthread_mutex_lock(&dlA);
    pthread_barrier_wait(&bar);               /* 确保 AB 各持一把 */
    struct timespec ts; clock_gettime(CLOCK_REALTIME, &ts);
    ts.tv_nsec += 200*1000000; if (ts.tv_nsec >= 1000000000L)
        { ts.tv_sec++; ts.tv_nsec -= 1000000000L; }
    int r = pthread_mutex_timedlock(&dlB, &ts);
    printf("[demo4] 线程1(持A)拿B: %s\n", r ? strerror(r) : "成功");
    if (r == 0) pthread_mutex_unlock(&dlB);
    pthread_mutex_unlock(&dlA);
    return NULL;}
static void *dl_two(void *x){(void)x;
    pthread_mutex_lock(&dlB);
    pthread_barrier_wait(&bar);
    struct timespec ts; clock_gettime(CLOCK_REALTIME, &ts);
    ts.tv_nsec += 200*1000000; if (ts.tv_nsec >= 1000000000L)
        { ts.tv_sec++; ts.tv_nsec -= 1000000000L; }
    int r = pthread_mutex_timedlock(&dlA, &ts);
    printf("[demo4] 线程2(持B)拿A: %s\n", r ? strerror(r) : "成功");
    if (r == 0) pthread_mutex_unlock(&dlA);
    pthread_mutex_unlock(&dlB);
    return NULL;}

static void demo_deadlock(void){
    pthread_t t1, t2;
    pthread_barrier_init(&bar, NULL, 2);
    pthread_create(&t1, NULL, dl_one, NULL);
    pthread_create(&t2, NULL, dl_two, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    pthread_barrier_destroy(&bar);
}

int main(void){
    demo_volatile_race();
    demo_mutex_fix();
    demo_errorcheck();
    demo_deadlock();
    return 0;
}
```

实测输出（WSL2 / 12 核；demo1 的丢失率随机器/负载浮动）：

```text
[demo1] volatile++ 无保护 : 得到 297768 / 期望 800000（丢失 62.8%）
[demo2] mutex  保护        : 得到 800000 / 期望 800000（丢失 0.0%，71.2 ns/次）
[demo3] ERRORCHECK: 二次lock=Resource deadlock avoided 解锁后再unlock=Operation not permitted
[demo4] 线程2(持B)拿A: Connection timed out
[demo4] 线程1(持A)拿B: 成功
```

三点解读：

1. `Connection timed out` 就是 `ETIMEDOUT` 的 `strerror` 文案。
2. demo4 有两种结局，都算"成功脱身"：**双超时**（两线程都在 200 ms 点放弃），或如本次——**一超时放锁救活另一个**：线程 2 超时放弃并解锁 B 的瞬间，还睡在 B 上的线程 1 被 futex 唤醒、成功拿锁。这正是 timedlock 的价值：**把永久死锁降级为可重试失败**。
3. 生产代码里这个模式可以升级成"超时 → 记录锁序违规日志 → 指数退避重试"。

## 自测题

**题目 1（实测分析）**：无锁 4 线程各 `++` 500,000 次的测试里，共享变量声明为普通 `long` 时丢失 0.00%，改为 `volatile long` 后丢失 52%。为什么普通版本"不丢"？这说明什么？

<details>
<summary>参考答案</summary>

普通 `long` 无任何同步语义，gcc 依 as-if 规则把整个循环合并成一条 `shared += 500000`（objdump 可证：`addq $0x7a120, shared(%rip)`），每个线程只在结束时做一次读改写，碰撞概率骤降且时间上错开，所以"看起来不丢"。这说明：① 无同步的共享访问在 C 内存模型下是 UB，编译器可以任意重排/合并，你测到的"无竞态"可能只是编译器的副作用；② 测竞态必须用 `volatile`（挡合并）或 `_Atomic`（真同步），否则测的是编译器不是调度器。

</details>

**题目 2（概念）**：单核 CPU 上（或 4 线程全钉一个核），无保护 `++` 实测丢失 0.00%。这能证明单核没有竞态吗？

<details>
<summary>参考答案</summary>

不能。单核上线程靠时间片切换交错，只有恰好在 load 和 store 之间被抢占才丢更新。窗口 ~3 ns，时间片 ~ms 级，单次概率 ~10⁻⁶，200 万次实验可能一次都碰不上。竞态**存在**但**概率极低**——这正是竞态 bug 的典型形态：换负载、换核数、加中断压力它就现形。另外单核上中断处理程序若也碰同一变量，窗口同样存在。

</details>

**题目 3（API 细节）**：`pthread_mutex_lock` 失败时错误码从哪里取？`trylock` 拿不到锁返回什么？

<details>
<summary>参考答案</summary>

Pthreads 系列函数的错误码**从返回值取**，不设置 `errno`（区别于传统系统调用）。写法是 `int err = pthread_mutex_lock(&m); if (err) ...`。`trylock` 在锁被占时立即返回 `EBUSY`，不阻塞。

</details>

**题目 4（内核路径）**：`futex_wait_setup()` 为什么必须**先锁哈希桶、再读用户内存的值**？如果反过来会发生什么？

<details>
<summary>参考答案</summary>

先锁桶再读值保证了"读值 → 入队"在桶锁保护下原子完成。如果反过来（先读值、后锁桶入队），存在窗口：睡眠方读到旧值 → 唤醒方改值、锁桶、发现无人、唤醒 0 个、解锁 → 睡眠方才锁桶入队、基于早已过期的旧值检查通过而睡下 → 永远无人唤醒（丢失唤醒）。futex 的基本保证是"任务只会因为入睡那一刻 *uaddr 仍等于 expected 而睡着"，先锁桶是实现这一保证的前提（`kernel/futex/waitwake.c:584` 注释原文）。

</details>

**题目 5（选型）**：多核机器上、临界区约 100 ns 的计数器更新，4 线程高并发。`pthread_spinlock` 一定比 `pthread_mutex` 快吗？

<details>
<summary>参考答案</summary>

不一定，实测往往更慢。本机数据：跨核 4 线程下 spinlock 81 ns/次 vs mutex 69 ns/次。原因：4 个核同时自旋会持续锤锁所在的缓存行（MESI 乒乓），持锁核每次访问锁和临界区数据都要跟 4 个自旋核抢缓存一致性事务，反而被拖慢。glibc 自适应 mutex（默认类型在竞争时）先短自旋再 futex 睡眠，兼顾两头。纯自旋锁只在"临界区极短 + 持锁者确定在别的核上跑着不会被换走 + 上下文切换成本 >> 自旋成本"时占优。

</details>
