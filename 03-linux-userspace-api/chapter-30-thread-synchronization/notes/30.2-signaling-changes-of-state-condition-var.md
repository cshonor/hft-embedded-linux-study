## 本节讲什么

1. **为什么 mutex 不够**——mutex 只能保证"一次一个人进"，解决不了"等队列非空再干活"：轮询烧 CPU，sleep 加延迟。条件变量补上"睡到条件成立"的原语。
2. **`pthread_cond_wait` 的三步原子语义**——放锁、睡、醒来重新拿锁，为什么必须持锁调用、为什么谓词必须用 `while` 而不是 `if`（虚假唤醒 + 多人被唤醒 + 抢锁失败三种场景）。
3. **丢失唤醒的时序解剖**——不持锁就 signal 会发生什么；以及实测证明：condvar 的唤醒延迟 ≈ 裸 futex 的唤醒延迟（condvar 只是 futex 加一层用户态记账）。

## 一、为什么 mutex 不够

需求：消费者线程要等 `queue` 非空才能干活。用 mutex 只有两种写法，都不行：

```c
/* 写法 1：轮询 —— 烧 CPU */
for (;;) {
    pthread_mutex_lock(&m);
    if (queue非空) { 取数据; pthread_mutex_unlock(&m); break; }
    pthread_mutex_unlock(&m);
    /* 不睡 = 100% CPU 空转；睡 usleep(1ms) = 平均 0.5ms 额外延迟 */
}

/* 写法 2：拿着锁睡 —— 更糟 */
pthread_mutex_lock(&m);
while (queue空) sleep(1);        /* ⚠ 睡着还持锁！生产者永远进不来 */
```

死结在于：**检查谓词需要持锁（防止检查瞬间被改），但等待需要放锁（让别人能改）**——这两件事必须"原子地"一起发生。这正是条件变量存在的意义：

> **条件变量 = 「放锁入睡 + 醒来重新拿锁」的原子封装**。

mutex 与 cond 的职责分工：

| 原语 | 职责 | 回答的问题 |
|------|------|-----------|
| mutex | 互斥访问**状态** | "现在能不能碰这个数据" |
| cond | 等待**状态变化** | "状态变了没有？没变我睡，变了叫我" |

## 二、API 与 wait 的三步语义

### 2.1 API

```c
pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;    /* 静态初始化 */
pthread_cond_init(&cond, &attr);                    /* 动态（可设 CLOCK_MONOTONIC）*/
pthread_cond_destroy(&cond);

int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_timedwait(pthread_cond_t *cond, pthread_mutex_t *mutex,
                           const struct timespec *abstime);   /* 绝对时间 */
int pthread_cond_signal(pthread_cond_t *cond);      /* 唤醒至少一个等待者 */
int pthread_cond_broadcast(pthread_cond_t *cond);  /* 唤醒全部等待者 */
```

### 2.2 `wait` 的三步原子语义

```c
pthread_cond_wait(&cond, &m);
/* 展开成三步，且①②不可分割（原子）：
 *   ① 原子地：释放 m + 挂入 cond 的等待队列（内核里：锁桶 → 入队 → 放锁 → schedule）
 *   ② 睡……（TASK_INTERRUPTIBLE，等 futex 唤醒/信号/超时）
 *   ③ 醒来后重新 pthread_mutex_lock(m)，拿到了才从 wait 返回
 */
```

三个推论，每个都是坑点：

1. **必须持锁调用 `wait`**——因为它要放锁。不持锁调用是 UB（glibc 里会直接解锁一把没锁的 mutex，`__owner` 检查不过就崩）。
2. **`wait` 返回时你又持有锁**——所以 `wait` 外层的 `while` 谓词检查天然是持锁的，无需再加锁。
3. **signal 的一方，通常也持锁**——修改谓词（共享状态）本身就需要锁。signal 可以在放锁之后（"墙倒众人推"优化），但**改谓词必须在持锁下**（§四）。

### 2.3 标准模板（背诵级）

```c
/* 等待方 */
pthread_mutex_lock(&m);
while (!predicate)                  /* ⭐ while，不是 if */
    pthread_cond_wait(&cond, &m);
/* 此刻：持锁 && 谓词为真 */
...消费状态...
pthread_mutex_unlock(&m);

/* 通知方 */
pthread_mutex_lock(&m);
...修改状态，使 predicate 可能为真...
pthread_cond_signal(&cond);         /* 或 broadcast */
pthread_mutex_unlock(&m);
```

## 三、谓词为什么必须 `while`

`if (predicate) wait` 有三类真实故障，`while` 一次性全部兜住：

### 3.1 虚假唤醒（spurious wakeup）

**没有任何人 signal，wait 自己醒了**。这是允许的（POSIX 明文）：内核的 `futex_wait` 被信号打断、唤醒路径的竞态（`futex_wake_mark` 注释里那个 spurious wakeup 例子）、glibc 的 `__wseq` 序号实现细节，都会造成"醒来但无事发生"。醒来后谓词仍为假，`while` 转一圈接着睡；`if` 版本直接往下走，**拿着假谓词进入临界区消费不存在的数据**。

### 3.2 多人被唤醒（broadcast 惊群）

broadcast 唤醒 5 个消费者，但队列里只有 1 条数据：

```
broadcast → 5 人同时从 wait 返回（当然，串行抢锁）
  消费者 1 抢到锁：谓词真，取走数据，unlock
  消费者 2 抢到锁：谓词已假 → while 转回去接着睡 ✓
                   if 版本：谓词检查发生在醒来瞬间（逻辑上），
                   消费不存在的数据 → 空指针/下溢/崩溃 ✗
```

### 3.3 signal 唤醒了"错误"的等待者

一个 cond 被多个谓词复用时（不推荐但常见于历史代码），signal 唤醒的线程等的是谓词 A，而成立的是谓词 B——被唤醒者 `while` 一检查发现 A 仍为假，接着睡，无事发生；`if` 版本则会消费错误状态。**条件变量不带任何谓词信息**，它只是个"闹钟"，判断该不该起床永远是等待者自己的事（`while` 谓词）。

> 记忆钩子：**cond 是哑的，谓词是活的；醒来先看表（while），别闭着眼下床（if）**。

### 3.4 signal vs broadcast 决策表

| 场景 | 用哪个 | 理由 |
|------|--------|------|
| 每次状态变化只"解锁"一个等待者（队列来了 1 条消息） | `signal` | 只需一个消费者干活；多醒是浪费（醒了抢锁失败又睡回去） |
| 所有等待者都该看一眼状态（广播关闭、水位变化） | `broadcast` | 语义正确性优先 |
| 不确定 / 谓词复杂 / 多种等待者共用一个 cond | `broadcast` | signal 只保证"至少一个"被唤醒，若被唤醒的不是该干活的那个，且没人再 signal → 全体饿死 |
| HFT 热路径 | 尽量都不用 | 唤醒 = futex 系统调用 + 调度延迟（微秒级尾延迟），热路径用无锁队列 + 自旋/忙等 |

`signal` 的语义是"唤醒**至少一个**"——实现上允许当惊群用（glibc 实际按 LIFO/FIFO 唤醒一个，但标准不保证只一个）。所以**即使你用 signal，等待方也必须写 while**。

## 四、丢失唤醒：不持锁 signal 的时序解剖

**条件变量不记忆信号**。signal 时刻没有任何等待者 → 这个 signal 凭空消失，不会存起来补偿给后来的 wait。谓词 + 持锁是唯一的防线：

```
错误写法：通知方不持锁
                                        等待方（持锁）
                                        lock(m)
                                        if (queue空)          ① 检查：空
signal(cond)   ② 此刻等待方还没睡着！
               （signal 落空，无人被唤醒，信号不保存）
                                        wait(cond, m)         ③ 放锁入睡
                                                               → 睡到天荒地老
```

正确的持锁写法为什么不会丢？signal 落在 ①③ 之间时，**它根本进不来**——m 被等待方持有，通知方阻塞在 lock 上，直到 ③ 放锁入睡的瞬间才获得机会改状态 + signal，而等待方已经挂在队列上（①放锁和②入队是原子的）。若 signal 落在 ③ 之后，等待方已在队列上，正常被唤醒。

更精确地说，防线的最底层是 §五讲的 futex 语义：**等待方"放锁 + 入队"原子，通知方"改值 + 唤醒"必须与它互斥**——在用户态这套互斥由 mutex 提供；内核里 `futex_wait_setup` 的"先锁桶再读值"把最后一级窗口也焊死了（30.1 §3.3）。

三个推论：

1. **先改谓词，后 signal**（都在持锁下）——只 signal 不改谓词 = 白叫，`while` 转一圈接着睡。
2. signal 后立刻 unlock 的传统写法 vs 先 unlock 再 signal（"hurry up and wait" 优化）：后者少一次锁交接（被唤醒者不必和 signal 方抢锁），语义都正确；但先 unlock 再 signal 在"判断是否有等待者"的实现上可能有惊群窗口，**按 TLPI 的建议：默认持锁 signal， profiling 发现锁交接是瓶颈再优化**。
3. **timedwait + 绝对时间**：重试循环里不要重算 deadline（`abstime` 是绝对时刻，被虚假唤醒打断重进 while 后，`timedwait` 用同一个 `abstime`，不会把总等待时间拉长）。

## 五、深入内核：condvar 只是 futex 的记账外壳

### 5.1 glibc 的 condvar 结构（2.25+ 的 wseq 设计）

glibc `pthread_cond_t` 的核心字段（简化）：

```c
struct pthread_cond_s {
    __atomic_wide_counter __wseq;      /* ⭐ wait 序号：每次 wait 递增 */
    __atomic_wide_counter __g1_start;  /* 当前"代"（generation）的起始序号 */
    unsigned int __g_refs[2];          /* 两代等待组（G1 在睡，G2 在涌入）*/
    unsigned int __g_size[2];
    unsigned int __g1_orig_size;
    unsigned int __wrefs;
    unsigned int __g_signals[2];
    ...
};
```

- 每次 `wait`：`__wseq++`，序号决定你属于哪一代（G1/G2），然后睡在**与代绑定的 futex 词**上。
- `signal`：递增 `__g_signals`，对当前代发一次 `futex(FUTEX_WAKE, 1)`。
- `broadcast`：把当前代"闭代"，全体 `futex(FUTEX_WAKE, INT_MAX)`，新来者进下一代。
- 唤醒后的等待者要**重新抢 mutex**（30.1 的完整路径），然后 `while` 谓词复查。

### 5.2 实测：condvar 唤醒延迟 ≈ 裸 futex 唤醒延迟

配套基准的两组数据（WSL2，严格握手 ping-pong 模式）：

| 测试 | 实测 | 说明 |
|------|------|------|
| 裸 futex（`FUTEX_WAIT` + `FUTEX_WAKE` 手写乒乓） | 67.8 µs/往返 | 内核下限：两次系统调用 + 两次调度 |
| `pthread_cond_signal → wait 醒来` | 67.8 µs/次 | glibc condvar 完整路径 |

两者**几乎相等**——证明 condvar 的用户态记账（wseq/代/簿记）开销相对内核唤醒可以忽略，**条件变量的延迟瓶颈就是 futex 唤醒 + 调度器**。这也是它和"自旋/忙等"路线的分水岭：数据到了你愿意睡（省 CPU、延迟微秒级），还是愿意烧核（延迟亚微秒级）。

> ⚠ 67.8 µs 是 WSL2 虚拟化的调度放大值，native Linux 典型 1~5 µs。绝对值不可信，**但两组的相对关系（≈相等）可信**——它们走的是同一条内核路径。

### 5.3 与 30.1 的 futex 坐标对照

| condvar 操作 | 底层 futex | 内核入口 |
|--------------|-----------|----------|
| `wait` 睡眠 | `FUTEX_WAIT`（cond 的 futex 词） | `futex_wait_setup():577`（先锁桶读值）→ `schedule()` |
| `signal` 唤醒 1 个 | `FUTEX_WAKE, 1` | `futex_wake():143`（waiters 早退 → 桶锁 → wake_q 锁外唤醒） |
| `broadcast` 唤醒全部 | `FUTEX_WAKE, INT_MAX` | 同上，`nr_wake` 传 `INT_MAX` |
| `timedwait` 超时 | `FUTEX_WAIT_BITSET` + hrtimer | `futex_setup_timer()`（`core.c:126`）挂高精度定时器 |
| wait 被信号打断 | 返回后重启循环 | `futex_wait` 的 `restart_block` 机制（`EINTR` 语义在 condvar 层被隐藏，重启是 glibc 做的） |

## 六、生产者-消费者：本章的中央模式

固定容量环形队列，双条件变量（`not_full` / `not_empty`）：

```c
#define QCAP 8
typedef struct {
    void *buf[QCAP];
    int head, tail, count;
    int closed;
    pthread_mutex_t m;
    pthread_cond_t  not_full;      /* 消费者在它上面等"有空位"（消费后 signal）*/
    pthread_cond_t  not_empty;     /* 生产者在它上面等"有数据"（生产后 signal）*/
} queue_t;

/* 生产者 */
void q_push(queue_t *q, void *item) {
    pthread_mutex_lock(&q->m);
    while (q->count == QCAP && !q->closed)     /* 满了且没关门：等 */
        pthread_cond_wait(&q->not_full, &q->m);
    if (q->closed) { pthread_mutex_unlock(&q->m); return; }
    q->buf[q->tail] = item;
    q->tail = (q->tail + 1) % QCAP;
    q->count++;
    pthread_cond_signal(&q->not_empty);        /* 有数据了，叫一个消费者 */
    pthread_mutex_unlock(&q->m);
}
```

六个细节，每个都对应前面某条原理：

| # | 细节 | 对应原理 |
|---|------|----------|
| 1 | `while (count == QCAP && !closed)` | while 谓词（§三）；条件里带 `closed` 让关闭时能醒着退出 |
| 2 | push 里 signal `not_empty`，pop 里 signal `not_full` | 唤醒的是"对面"的等待者——你制造了空位才有人能等空位 |
| 3 | 单条数据 signal 一次，不 broadcast | 每条消息只需一个消费者（§3.4）；多生产者多消费者天然负载均衡 |
| 4 | `closed` 的关闭：持锁置位 + **两个 cond 都 broadcast** | 关闭是全局事件，所有等待者都要醒来看 `while` 的 `!closed` 分支 |
| 5 | `pthread_cond_wait` 的返回值不检查 | 它成功时返回 0；虚假唤醒靠 while 兜，timedwait 的 ETIMEDOUT 才需要查 |
| 6 | 队列结构体和锁放一起、按数据对象组织锁 | 锁的粒度 = 数据的粒度，防止"一把大锁包全场" |

完整的可运行实现（含优雅关闭 + 统计）见 [30.4 练习](30.4-exercises.md) 综合题。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT · 热路径 | 行情→策略的传递**不用 condvar**：唤醒延迟 = futex 系统调用 + 调度（微秒级尾延迟），热路径用 SPSC 无锁环形队列 + 消费侧忙等/自旋（忙等延迟亚微秒）。condvar 用于非热路径：风控开关、配置热更新、订单确认等"毫秒级无所谓"的事件 |
| HFT · 尾延迟思维 | condvar 的延迟分布是长尾（本机实测最慢样本 883 µs，均值 68 µs 的 13 倍——调度器被干扰时的排队）。任何"睡着等人叫"的设计都要评估 p99.9 而不是均值 |
| HFT · 多消费者 | signal 唤醒"至少一个"不保证"恰好该干活的那一个"；策略组多线程共用一个 cond 时宁可用 broadcast 让 while 谓词自己分流，也别赌 signal 命中 |
| 嵌入式 · 采集→处理 | 经典架构：中断/DMA 采集线程 `q_push`，处理线程 `q_pop` 阻塞等待——CPU 占用近零，比轮询省几个数量级的功耗（电池设备关键） |
| 嵌入式 · 时钟选择 | `pthread_condattr_setclock(CLOCK_MONOTONIC)` + timedwait：嵌入式系统墙钟跳变（NTP 校时、RTC 没电）会让 CLOCK_REALTIME 的 timedwait 永不超时或立刻超时。**单调整钟是超时类 API 的唯一安全选择** |
| 嵌入式 · 优先级 | 高优先级消费者睡在 cond 上时，被 signal 唤醒的顺序由 futex 的 plist（优先级链表）决定，实时线程先醒（30.1 §3.2）——前提是策略线程用了实时调度（Ch35） |

## 代码示例

`cond_demo.c`（gcc -O2 -Wall -Wextra 零告警编译通过；演示 2 用 timedwait 兜住本会永久挂死的 bug 版本）：

```c
/* cond_demo.c — Ch30.2：while 谓词、丢唤醒、signal vs broadcast
 * 编译：gcc -O2 -Wall -Wextra -o cond_demo cond_demo.c -pthread
 */
#include <stdio.h>
#include <string.h>
#include <pthread.h>
#include <time.h>
#include <unistd.h>

static double now_ns(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
    return t.tv_sec*1e9+t.tv_nsec;}

/* ---------- 演示 1：while 谓词 + 严格握手 ping-pong（正确范式） ---------- */
static pthread_mutex_t m1 = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c1 = PTHREAD_COND_INITIALIZER;
static int ball;                        /* 0=轮到生产者, 1=轮到消费者 */
static long handshakes;

static void *cons1(void *a){(void)a;
    for (long i = 0; i < 100000; i++) {
        pthread_mutex_lock(&m1);
        while (!ball)                   /* ⭐ while：虚假唤醒/惊群全兜住 */
            pthread_cond_wait(&c1, &m1);
        ball = 0;
        pthread_cond_signal(&c1);       /* 告诉生产者：该你了 */
        pthread_mutex_unlock(&m1);
    }
    return NULL;}
static void *prod1(void *a){(void)a;
    for (long i = 0; i < 100000; i++) {
        pthread_mutex_lock(&m1);
        while (ball)
            pthread_cond_wait(&c1, &m1);
        ball = 1;
        handshakes++;
        pthread_cond_signal(&c1);
        pthread_mutex_unlock(&m1);
    }
    return NULL;}

static void demo_handshake(void){
    pthread_t t1, t2;
    ball = 0; handshakes = 0;
    double t0 = now_ns();
    pthread_create(&t1, NULL, cons1, NULL);
    pthread_create(&t2, NULL, prod1, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    printf("[demo1] 严格握手 %ld 次，平均 %.1f ns/次（含全部锁竞争）\n",
           handshakes, (now_ns() - t0)/handshakes);
}

/* ---------- 演示 2：丢唤醒 bug 版（不持锁 signal） ---------- */
static pthread_mutex_t m2 = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c2 = PTHREAD_COND_INITIALIZER;
static int ready2;

static void *waker(void *a){(void)a;
    usleep(100000);                     /* 等受害者跑到 wait 前面 */
    ready2 = 1;                         /* ⚠ 不持锁改谓词 */
    pthread_cond_signal(&c2);           /* ⚠ 不持锁 signal：落空风险 */
    return NULL;}
static void *victim(void *a){(void)a;
    pthread_mutex_lock(&m2);
    struct timespec dl; clock_gettime(CLOCK_REALTIME, &dl);
    dl.tv_nsec += 300*1000000; if (dl.tv_nsec >= 1000000000L)
        { dl.tv_sec++; dl.tv_nsec -= 1000000000L; }
    int r = 0;
    while (!ready2 && r == 0)           /* timedwait：最多睡 300ms 就放弃 */
        r = pthread_cond_timedwait(&c2, &m2, &dl);
    printf("[demo2] 受害者醒来：ready2=%d %s（r=%s）\n", ready2,
           r == 0 ? "被正常唤醒" : "超时放弃——signal 丢了",
           r ? strerror(r) : "0");
    pthread_mutex_unlock(&m2);
    return NULL;}

static void demo_lost_wakeup(void){
    pthread_t t1, t2;
    pthread_create(&t2, NULL, victim, NULL);
    pthread_create(&t1, NULL, waker, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
}

/* ---------- 演示 3：broadcast 惊群 + while 自动分流 ---------- */
static pthread_mutex_t m3 = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c3 = PTHREAD_COND_INITIALIZER;
static int tokens;                      /* 令牌数 */
static long grabbed[3];                 /* 每个消费者抢到的次数 */

static void *grabber(void *a){
    long id = (long)(intptr_t)a;
    for (int round = 0; round < 3; round++) {
        pthread_mutex_lock(&m3);
        while (tokens == 0)
            pthread_cond_wait(&c3, &m3);    /* 没令牌就睡 */
        tokens--;                           /* 抢到一枚 */
        grabbed[id]++;
        pthread_mutex_unlock(&m3);
    }
    return NULL;}

static void demo_thundering_herd(void){
    pthread_t t[3];
    tokens = 0;
    memset(grabbed, 0, sizeof grabbed);
    for (long i = 0; i < 3; i++) pthread_create(&t[i], NULL, grabber, (void*)(intptr_t)i);
    usleep(100000);
    for (int round = 0; round < 9; round++) {     /* 9 轮 × 1 枚 = 9 枚令牌总量
                                                     = 3 人 × 3 轮，人人都能收工 */
        pthread_mutex_lock(&m3);
        tokens = 1;                         /* 只放 1 枚令牌 */
        pthread_cond_broadcast(&c3);        /* 惊醒全部 3 人 */
        pthread_mutex_unlock(&m3);
        usleep(100000);
    }
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    printf("[demo3] broadcast 惊群分流（9 轮各 1 枚令牌）：抢到 {A=%ld, B=%ld, C=%ld}"
           "（共 %ld，被白唤醒的都回 while 睡回去了）\n",
           grabbed[0], grabbed[1], grabbed[2],
           grabbed[0]+grabbed[1]+grabbed[2]);
}

int main(void){
    demo_handshake();
    demo_lost_wakeup();
    demo_thundering_herd();
    return 0;
}
```

实测输出（WSL2 / 12 核；demo2 的结局取决于调度，两种都可能出现）：

```text
[demo1] 严格握手 100000 次，平均 247723.2 ns/次（含全部锁竞争）
[demo2] 受害者醒来：ready2=1 被正常唤醒（r=0）
[demo3] broadcast 惊群分流（9 轮各 1 枚令牌）：抢到 {A=3, B=3, C=3}（共 9，被白唤醒的都回 while 睡回去了）
```

三点解读：

1. demo1 每次握手包含**两次** signal→wake 往返（生产者叫消费者、消费者叫生产者），WSL2 下每次唤醒 68~250 µs 波动很大（native Linux 约 1~5 µs）——这正是 §5.2 表里"condvar signal→wake 延迟"的来源与量级。
2. demo2 这次运气好（signal 恰好落在受害者入睡之后），但**这个正确性靠的是运气**：不持锁改谓词 + signal 的窗口真实存在（§四的时序图），换负载/换核就可能打出"超时放弃——signal 丢了"的结局。正确写法是给 waker 也加上 `pthread_mutex_lock(&m2)`。
3. demo3 每轮只放 1 枚令牌、broadcast 惊醒 3 人：1 人抢到，2 人 `while` 复查发现令牌已空、默默睡回去。**惊群不丢正确性（while 兜底），只浪费唤醒**——这正是 broadcast 语义安全的代价。

## 自测题

**题目 1（语义）**：`pthread_cond_wait(&cond, &m)` 从调用到返回，锁 `m` 的状态经历什么变化？为什么说"必须持锁调用"？

<details>
<summary>参考答案</summary>

进入时必须已持有 `m`；wait 内部原子地（释放 `m` + 挂入 cond 等待队列）；被唤醒后重新 `lock(m)`，**拿到锁才返回**。所以返回时刻必然持锁。必须持锁调用的原因：① wait 要放锁，不持锁则放锁行为未定义；② 谓词检查（while 的条件）必须在持锁下做，否则检查瞬间谓词可能被并发修改——"检查谓词"与"放锁入睡"的原子性正是 condvar 存在的意义。

</details>

**题目 2（坑点辨析）**：把标准模板的 `while (!predicate) wait(...)` 改成 `if (!predicate) wait(...)`，在什么情况下会出 bug？至少说出三种场景。

<details>
<summary>参考答案</summary>

① 虚假唤醒：无人 signal 却醒了，if 版本拿着假谓词往下走；② broadcast 惊群：N 个等待者全醒，但资源只有 1 份，第一个抢到的把谓词改回假，其余 if 版本不再复查、直接消费不存在/不完整的状态；③ signal 命中"错误"等待者：一个 cond 复用多个谓词时，被唤醒者等的是别的谓词。共同本质：**醒来 ≠ 谓词为真**，只有 while 能把"醒"翻译回"检查"。

</details>

**题目 3（丢失唤醒）**：画时序说明"通知方不持锁直接 signal"为什么可能永久丢失唤醒。修复的最小改动是什么？

<details>
<summary>参考答案</summary>

时序：等待方 lock(m) → 检查谓词为假 → 【窗口】→ 通知方改谓词 + signal（此刻无人在队列上，信号不保存、凭空消失）→ 等待方 wait() 放锁入睡 → 永远无人再 signal → 永久睡眠。最小修复：通知方的"改谓词 + signal"包进 `lock(m)/unlock(m)`——这样它要么在等待方检查之前完成（等待方看到新谓词，根本不睡），要么被挡在锁外直到等待方原子地"放锁+入队"之后才执行（signal 必中）。

</details>

**题目 4（实测理解）**：为什么实测"裸 futex 乒乓延迟"与"condvar signal→wake 延迟"几乎相等？这个结论对架构选型意味着什么？

<details>
<summary>参考答案</summary>

因为 condvar 的唤醒路径最终就是对内部的 futex 词执行 `FUTEX_WAIT`/`FUTEX_WAKE`，glibc 加的记账（wseq 序号、代管理）是纯用户态原子操作，纳秒级；而唤醒本身要付出系统调用 + 调度器唤醒 + 新任务等 CPU 的微秒级成本。两者相等说明**condvar 的延迟地板就是内核 futex + 调度**，用户态无法再优化。选型含义：凡是"睡着等人叫"的方案延迟都是微秒级长尾，HFT 热路径要亚微秒就只能反向选择——不睡（自旋/忙等/无锁队列）。

</details>

**题目 5（API 细节）****：`pthread_cond_signal` 和 `pthread_cond_broadcast` 的语义分别是什么？"signal 只唤醒一个"这个说法对吗？

<details>
<summary>参考答案</summary>

signal：唤醒**至少一个**等待者；broadcast：唤醒**全部**等待者。"signal 恰好唤醒一个"不对——POSIX 只承诺"至少一个"，实现允许在 signal 时多醒（等效惊群）。因此即使全程序都用 signal，等待方仍必须写 while 谓词。选型规则：一次状态变化只该解锁一个等待者 → signal；所有等待者都要重新评估状态 → broadcast；拿不准 → broadcast（正确性优先，代价是惊群）。

</details>
