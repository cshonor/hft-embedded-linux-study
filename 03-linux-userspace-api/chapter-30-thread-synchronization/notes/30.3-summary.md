## 一、全章速览

| 节 | 主题 | 核心结论 | 关键内核坐标（v6.6） |
|----|------|----------|---------------------|
| 30.1 | 互斥量 | mutex = futex 的用户态封装：无竞争一条 CAS（7 ns），有竞争睡进内核哈希桶 | `futex_hash():115` · `futex_wait_setup():577`（先锁桶再读值）· `futex_wake():143`（wake_q 锁外唤醒）· `struct futex_q:96` |
| 30.2 | 条件变量 | cond = 「放锁入睡 + 醒来重拿锁」的原子封装；谓词必须 while；不记忆信号 | `FUTEX_WAIT:11` / `FUTEX_WAKE:12`（`include/uapi/linux/futex.h`）· plist 优先级排队 |

**职责一句话**：mutex 管「现在能不能碰数据」，cond 管「状态变了叫我」。所有等待都用同一套内核基础设施——同一个地址哈希进同一个桶，plist 按优先级排队。

## 二、五个反直觉真相

| # | 真相 | 证据 |
|---|------|------|
| 1 | **竞态"测不出来"不代表不存在**——编译器能把 50 万次 `++` 合并成一条加法，让丢失率归零 | objdump：`addq $0x7a120, shared(%rip)`（§30.1.3）；`volatile` 版实测丢失 52% |
| 2 | **单核 0% 丢失 ≠ 安全**——只是窗口（~3 ns）撞上时间片切换（~ms）的概率约 10⁻⁶ | 4 线程全钉 CPU0 实测 0.00%，跨核 52%（§30.1.2） |
| 3 | **无竞争 mutex 是最便宜的原语之一**——比 `atomic_fetch_add` 还便宜（1 次 CAS vs `lock xadd`） | 实测 7.1 ns vs 13.8 ns（§30.1.5.1） |
| 4 | **condvar 的延迟地板就是内核 futex**——glibc 记账开销可忽略，两者实测几乎相等 | 裸 futex 乒乓 67.8 µs ≈ condvar signal→wake 67.8 µs（§30.2.5.2） |
| 5 | **signal 不保存信号**——无人等待时 signal 凭空消失；signal 只保证"至少一个"，不保证"恰好一个/该醒的那个" | 丢唤醒时序图（§30.2.四）；因此等待方永远写 while |

## 三、十条铁律

1. **共享可变数据必须同步**——C 内存模型下无同步共享 = UB，编译器和调度器都在跟你捣乱。
2. **测竞态用 `volatile` 或 `_Atomic`**——否则你测的是编译器的优化，不是调度器的竞态。
3. **错误码从 Pthreads 函数返回值取**，不查 `errno`。
4. **禁止拷贝 mutex / cond**——身份不可复制。
5. **所有路径都 unlock**——早退分支、错误分支，用 `goto cleanup` 统一收尾。
6. **多锁全局统一顺序**；拿不准就 trylock + 退避；怀疑死锁用 timedlock 探测。
7. **cond 必须配 mutex**：检查谓词持锁、改谓词持锁、wait 的放锁入睡醒来拿锁是原子的。
8. **谓词永远 `while`，永远 `while`，永远 `while`**——`if` 在虚假唤醒/惊群/错醒三种场景下全灭。
9. **一个 cond 对应一个谓词**——复用 cond 等多种状态是丢唤醒与错醒的温床。
10. **唤醒语义按"至少一个"设计**——signal 落空正常、惊群正常，正确性由谓词保证，效率由 signal/broadcast 选择与队列结构优化。

## 四、同步原语成本账本（实测汇总）

WSL2 / 12 核 / gcc -O2（⚠ 虚拟化放大了微秒级数字，ns 级数字基本可信；跨机只看量级）：

| 操作 | 实测成本 | 组成 |
|------|---------|------|
| `volatile ++`（下限参照） | 3.1 ns | 一次访存 RMW |
| mutex 无竞争 lock+unlock | 7.1 ns | 2 条用户态 CAS，**零系统调用** |
| `atomic_fetch_add` | 13.8 ns | `lock xadd` 总线级原子 |
| spinlock 无竞争 | 15.1 ns | 原子交换 + 屏障 |
| mutex 4 线程竞争（钉 1 核） | 26.7 ns/次 | 时间片切换 + 锁开销 |
| `atomic_fetch_add` 4 线程竞争 | 25.5 ns/次 | 缓存行乒乓 |
| mutex 4 线程竞争（跨核） | 69.3 ns/次 | 缓存行跨核乒乓 |
| spinlock 4 线程竞争（跨核） | 81.0 ns/次 | 自旋风暴反而拖慢持锁者 |
| 空系统调用（FUTEX_WAKE 无人等） | 203 ns | 进出内核底价 |
| futex 睡→醒一次 | ~34 µs（WSL2 放大值） | 2 次系统调用 + 2 次调度（native 约 1~5 µs） |
| condvar signal→wake | ≈ futex 睡醒 | 同一条内核路径 |

**HFT 决策速查**：

| 需求 | 选择 | 依据 |
|------|------|------|
| 单生产者单消费者传数据（热路径） | SPSC 无锁环形队列 + 忙等/事件混合 | 避开微秒级唤醒延迟 |
| 多线程偶发共享（非热路径） | mutex | 无竞争时 7 ns，简单正确 |
| 计数器/序号 | `_Atomic` | 25 ns 且无锁 |
| 等开关/配置/关闭事件 | condvar + while | 睡着零 CPU，延迟无所谓 |
| 短临界区强争抢（多核） | 自适应 mutex（默认就是） | 纯自旋在多核竞争下反而更慢 |
| 优先级敏感（RT 线程拿锁） | `PTHREAD_PRIO_INHERIT` | 防 Mars Pathfinder 式优先级反转 |

## 五、易错清单（全章合并版）

1. 用普通变量测竞态 → 测了个寂寞（编译器合并循环）。
2. `if` 谓词 → 虚假唤醒/惊群直接穿透。
3. 不持锁 signal / 不持锁改谓词 → 丢唤醒，偶发且必现于高负载。
4. 忘了 broadcast 里带"关闭"谓词 → 关闭时等待者睡死不退。
5. 同线程二次 lock 普通锁 → 自锁死锁；误以为 unlock 可以别人代调 → UB。
6. 多锁顺序不一致 → ABBA 死锁，压测不现形生产才爆。
7. `pthread_mutex_lock` 返回值不查 + 走 `errno` → 永远查不到错。
8. 临界区内做 IO / 长循环 / 再拿别的锁 → 争抢升级 + 死锁面扩大。
9. 拿锁调用可能睡的函数（`malloc`、`read`、`printf`）→ 峰值延迟失控。
10. 以为 signal "存住了" → 队列空着 signal 完就退出，后来者永久等待。

## 自测题

**题目 1（综合）**：一句话说清 mutex 和 cond 各自的职责，以及为什么"轮询 + usleep"两个都替代不了。

<details>
<summary>参考答案</summary>

mutex：互斥访问共享状态（"现在能不能碰"）；cond：等待状态变化（"变了叫我"）。轮询烧 CPU 且延迟随轮询间隔线性增加；usleep 睡着时拿不到"状态恰好变化"的事件。condvar 用一次内核 futex 睡眠换"零 CPU + 变化即醒"，是两者的合取；代价是被唤醒的微秒级延迟（系统调用 + 调度）。

</details>

**题目 2（排错）**：多消费者程序偶发挂死，日志显示消费者全停在 `pthread_cond_wait`，队列里还有数据。给出三个最可能的 bug 和对应检查点。

<details>
<summary>参考答案</summary>

① 谓词写成了 `if`：惊群/虚假唤醒穿透后消费了不存在的数据，后续状态错乱使 count 永不为正——检查谓词是否 while；② signal 落空：生产者不持锁（或改了谓词但 signal 了错误的 cond）——检查"持锁改谓词 → signal 同一个 cond"；③ 用 signal 但多个谓词复用一个 cond：被唤醒者 while 复查后睡回去，该醒的没人叫——检查 cond 与谓词是否一一对应。另有一个隐藏嫌疑：`while (count==0)` 忘了带关闭条件，关闭后没人 broadcast。

</details>

**题目 3（成本）**：为什么说"无竞争的 mutex 比原子加法还便宜"？什么时候这个结论反转？

<details>
<summary>参考答案</summary>

无竞争 lock = 一次 `lock cmpxchg`（0→1）+ unlock 一次原子写，共 7 ns；`atomic_fetch_add` 是 `lock xadd`，13.8 ns。反转点：① 有竞争时 mutex 走慢路径（自旋/futex 睡眠），成本跳到几十 ns 甚至微秒，而原子加法只涨到缓存行乒乓的 ~25 ns；② 如果临界区本来就是一条原子指令能表达的（计数器、序号），直接用 `_Atomic` 更便宜也更简单——mutex 保护的应该是"多条语句的复合不变量"。

</details>

**题目 4（设计）**：给一个采集（1 线程）→ 处理（1 线程）的嵌入式流水线选同步方案：数据速率 1 kHz，处理耗时 ~200 µs。

<details>
<summary>参考答案</summary>

1 kHz → 每 1 ms 一条数据，处理 200 µs 只占 20% CPU。方案：有界阻塞队列 + mutex + 两个 cond（not_full/not_empty），处理线程 `while(空) wait` 睡眠——CPU 占用近零（电池友好），延迟上限 1 个唤醒周期（µs 级）完全够用。不需要无锁结构（数据率低，锁无竞争或低竞争）。注意三点：队列容量按背压策略定（≥2×突发深度）；关闭要 broadcast + 谓词带 closed；嵌入式时钟跳变环境用 `pthread_condattr_setclock(CLOCK_MONOTONIC)` + timedwait 做看门狗。

</details>
