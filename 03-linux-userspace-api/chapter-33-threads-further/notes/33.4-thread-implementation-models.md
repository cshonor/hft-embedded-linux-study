## 本节讲什么

1. 用户线程 / 内核线程 / 映射关系——M:1、1:1、M:N 三种模型到底差在哪？
2. 每种模型的「阻塞一次系统调用」会发生什么（这是模型选择的试金石）？
3. 为什么 Linux 选了 1:1，而学界推崇的 M:N 在 Linux 上失败了？

---

## 要点

### 三种模型

```text
M:1（用户级线程）              1:1（内核级，Linux/NPTL）       M:N（混合）
┌──────────────┐              ┌──────────────┐               ┌──────────────┐
│ M 用户线程    │              │ 用户线程 1     │               │ M 用户线程    │
│  ↑↓ 用户态    │              │  │  一一对应   │               │  ↑↓ 用户态    │
│ 调度器(库)    │              │ 内核线程 1     │               │ M':N 调度器   │
│  │            │              │  │            │               │  (库+内核协同) │
│ 1 内核线程    │              │ 内核线程 2     │               │ N 内核线程    │
└──────────────┘              │  ↑ 对应       │               └──────────────┘
 内核只见 1 个任务              │ 用户线程 2     │                内核见 N 个任务
                              └──────────────┘
```

| 维度 | M:1 | **1:1** | M:N |
|------|-----|---------|-----|
| 代表 | 早期 GNU Portable Threads / 协程（同思想） | **Linux NPTL**、Windows | Solaris（旧）、IRIX；Linux 尝试 NGPT 失败 |
| 创建成本 | 极低（库函数 + 栈切换） | clone 系统调用（v6.6 实测 ~1-4μs 级，29.9 数据） | 中（两层登记） |
| 阻塞系统调用 | **全体拖死**（内核只认那 1 个任务） | 只睡这一个内核线程 | 库须拦截重写为非阻塞（"缝合层"） |
| 多核并行 | ❌（1 个内核任务只能上 1 核） | ✅（每线程可绑不同核） | ✅（N 个内核任务上 N 核） |
| 抢占 | 仅在库调度点（协作式为主） | 内核随意抢占（时间片/优先级） | 两层抢占，复杂 |
| 信号/定时器粒度 | 进程级（内核不知道有 M 个） | **线程级**（`task->pending` 独立） | 混乱（历史痛点） |

### 试金石：一个线程 read() 阻塞了

- **M:1**：`read` 阻塞的是唯一的内核任务 → 整个进程（含其他"线程"）卡死。库要自救必须把所有阻塞调用改写成非阻塞 + 就绪调度（等于重写半个内核接口）；
- **1:1**：只睡调用线程的内核任务，调度器换下一个；其他线程照常跑在不同核；
- **M:N**：库拦截 `read`，登记到调度器，切到同核其他用户线程；完成后再切回——正确但每次都多一层库内切换，且任何没被拦截的"漏网"阻塞调用退化成 M:1 行为。

### 为什么 Linux 选择了 1:1

1. **内核已经会调度**：CFS 本来就是任务级调度器，1:1 直接复用，不需要库内再造一个调度器；
2. **SMP 免费拿**：内核任务天然分布多核；
3. **语义干净**：阻塞、信号、抢占、`ps`/`top`/perf 全部按任务粒度工作，无观测盲区；
4. **M:N 的缝合成本证明过高**：Linux 的 NGPT（IBM 推的 M:N 实现）在 NPTL 出现后被放弃——双层调度的复杂度（锁协作、阻塞拦截、亲和性传递）吃掉了理论收益。业界后验：连 Solaris 也在 Solaris 9/10 淘汰了 M:N，回 1:1。

### 「用户级轻量」思想的现代转世

M:1 并没有死，它换了个名字活在**协程**（goroutine 的 G-M 模型、C++20 coroutine、rust async）里：

- 面对的还是同一对矛盾：切换成本 vs 阻塞语义；
- 解法也还是老一套：运行时把阻塞调用改写成非阻塞 + 就绪队列（Go runtime 的 netpoller）；
- 区别于 pthread：协程是**协作式、绑定在线程上**的二级调度——本质是"用户线程 2.0"，与 1:1 内核线程不冲突（goroutine 最终也跑在 OS 线程上）。

| | pthread（1:1） | 协程（M:1 思想） |
|--|---------------|-----------------|
| 切换成本 | 1-6μs（进内核，29.9 实测 5.92μs WSL 放大值） | ~10-100ns（用户态寄存器交换） |
| 阻塞容忍 | 任意阻塞 | 必须 await/非阻塞，漏一个就拖死整核 |
| 抢占 | 内核强制 | 协作（Go 1.14+ 异步抢占仅限安全点） |
| 适用 | CPU 并行、隔离故障域 | 海量并发 IO（百万连接） |

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | 1:1 = 线程可绑核 + `SCHED_FIFO` + `perf` 精确到线程——热路径观测性是 1:1 给的；协程适用于 IO 密集闸机（行情网关），策略计算仍用线程 |
| 嵌入式 | RTOS 的 task ≈ 1:1 内核任务思想；无 MMU 小系统跑 M:1（协作式调度器）省栈省内存——模型选择=资源预算 |
| 通用 | 选型口诀：CPU 并行用线程，海量并发 IO 用协程，两者混合是常态（reactor 线程池 + 每核协程环） |

## 自测题

**题目 1（推演）：** M:1 模型下，用户线程 A 阻塞在 `read()`，用户线程 B 还能跑吗？为什么？

<details>
<summary>参考答案</summary>

不能。内核视角只有 1 个任务，`read` 把它置为睡眠 → CPU 让给别人（别的进程），进程内所有用户线程一起冻结——内核根本不知道 B 存在。这正是 M:1 的死刑判决：任何未改写成非阻塞的阻塞调用都拖死全体。

</details>

**题目 2（辨析）：** 1:1 模型「每个 pthread 对应一个内核任务」——这个"对应"是什么机制建立的？

<details>
<summary>参考答案</summary>

glibc 的 `pthread_create` 调 `clone(CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SYSVSEM|SETTLS...)`——每线程就是一次 clone 产生的**内核 task_struct**（有自己的 PID/TID，`gettid()` 可见），CLONE_THREAD 使其加入同线程组（共享 TGID）。不是"对应"，而是**本来就是同一个东西的两个视角**：pthread_t 是 glibc 侧句柄，task_struct 是内核侧实体。

</details>

**题目 3（判断）：** 协程比线程"快"，所以高性能服务器应该全部用协程替代线程？

<details>
<summary>参考答案</summary>

错在场景混用。协程切换便宜（用户态 ~10-100ns vs 线程 1-6μs）是因为**不进内核、不换地址空间语义**——代价是协作式：一个协程跑死循环，同核其他协程全饿（除非异步抢占安全点）。CPU 密集并行仍要线程/进程铺满核；协程赢在**海量并发 IO**（百万连接的事件循环）。两者是分层关系（goroutine 跑在 OS 线程上）而非替代。

</details>
