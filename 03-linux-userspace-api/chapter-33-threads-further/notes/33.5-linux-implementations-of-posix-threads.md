## 要点

### LinuxThreads：没有 CLONE_THREAD 的年代

内核 2.0-2.4 只有 `CLONE_VM|CLONE_FILES|CLONE_SIGHAND`，没有线程组概念——每线程是一个**独立 PID**（内核任务），LinuxThreads 在此之上模拟 POSIX：

| POSIX 要求 | LinuxThreads 实际行为 | 后果 |
|-----------|----------------------|------|
| 同进程同 PID | 每线程独立 PID，只有 leader 是"进程 PID" | `kill(pid)` 只发给 leader——其他线程要靠管理线程转发 |
| 信号发给"进程" | **管理线程**（额外克隆的第一个线程）拦截 `SIGUSR1` 等并转投 | 信号延迟一跳；标准信号合并语义怪异 |
| `getpid()` 全线程一致 | 每线程返回自己的 PID | 直接违反 POSIX |
| fork 后 kill 语义 | 依赖 leader 是否存在 | 杂乱 |
| 进程内线程数 | 管理线程 + 每线程一个系统任务 | `ps` 里一片假进程 |

管理线程（manager thread）是 LinuxThreads 最标志性设计：它持有个信号转投和线程清理职责——也是最大的语义污染源。

### NPTL 的三大内核地基（2.5.x / 2.6 引入）

| 内核机制 | 干什么 | 带来的 POSIX 达标 |
|---------|--------|------------------|
| **`CLONE_THREAD` / 线程组** | clone 位把新任务挂进 `signal->thread_head`，共享 TGID | `getpid()` 全组一致；`kill()` 按 TGID 投递进程级信号；`/proc` 只显示组长（`/proc/tid` 才见每线程） |
| **`CLONE_CHILD_CLEARTID` + futex 唤醒** | 线程退出时内核 `mm_release():1634` 写 0 + `futex(FUTEX_WAKE,1)`（`kernel/fork.c:1634-1635`，29.7 核验过） | `pthread_join` 不再轮询——睡在 futex 上 |
| **`tgkill()` / `do_send_specific():3935`** | 按 (tgid, tid) 精确投递 | `pthread_kill` 语义正确，不撞 PID 复用（Ch32） |
| 配套：TLS 支持（`CLONE_SETTLS` → `set_new_tls():130`） | 每线程 fs base | `errno` 每线程独立（31.4 反汇编实测） |

结果：NPTL 通过了 POSIX compliance suite（含信号用例），性能上 10 万线程创建+join 也撑住了（当年 Ulrich Drepper 的著名基准）。

### 现代（glibc 2.34+）：LinuxThreads 彻底谢幕

- glibc 2.34 起 `libpthread` **并入 libc**——链接 `-pthread` 只是开启宏定义，不再有独立库；
- 线程栈默认 8MB（= `RLIMIT_STACK`，unlimited 时退 2MB）；
- 栈缓存：退出线程的栈进 per-CPU 缓存复用（`kernel/fork.c:303-306` 注释）。

### 身份换算表（必须刻进肌肉记忆）

| 想要什么 | API | 说明 |
|---------|-----|------|
| glibc 线程句柄 | `pthread_self()` → `pthread_t` | **指针**（`struct pthread *`），非整数、不可比较大小、会被复用 |
| 内核线程 ID | `gettid()` / `syscall(SYS_gettid)` | 全局唯一整数；`/proc/<pid>/task/<tid>`；**`pthread_t` 无法换算成它**（除非创建时线程自己上报） |
| 进程 ID | `getpid()` | = TGID = 组长 TID |
| 给线程发信号 | `pthread_kill(pthread_t)`（进程内）或 `tgkill()`（裸） | 见 33.2 |

⚠ `pthread_t` 和 TID **没有任何换算公式**：一个在 glibc 堆/栈结构里，一个在内核。跨系统观测（top -H、perf）认 TID；代码内认 pthread_t。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | 观测要线程粒度时用 TID：`perf -t <tid>`、`taskset -p <mask> <tid>`、`/proc/<pid>/task/<tid>/stat`（自旋/切换计数）——pthread_t 对工具链不可见 |
| 嵌入式 | 老产品若还有 uClibc + LinuxThreads 残留（2.4 内核时代）：信号语义不达标是工程事故源，升级路径 glibc/musl + NPTL |
| 通用 | musl 也是 1:1 + futex，语义同 NPTL（静态链接体积小——嵌入式友好） |

## 自测题

**题目 1（历史+内核）：** NPTL 靠哪三个内核机制让 `pthread_join` 从"轮询/信号 hack"变成干净语义？

<details>
<summary>参考答案</summary>

① `CLONE_THREAD` 线程组（TGID 共享，进程身份统一）；② `CLONE_CHILD_CLEARTID`：线程退出内核写清 tid 字段并 `futex(FUTEX_WAKE,1)`（`mm_release()`，kernel/fork.c:1634-1635）——joiner 睡在这个 futex 上被精确唤醒；③ `tgkill()` 定向信号支撑 `pthread_kill`。LinuxThreads 时代只能靠管理线程 `waitpid` 轮询收尸。

</details>

**题目 2（辨析）：** `pthread_t` 是什么类型？能 `printf("%d", tid)` 吗？

<details>
<summary>参考答案</summary>

glibc 里是无符号长整（实为 `struct pthread *` 指针——栈底地址）。**不是**内核 TID：无换算公式、退出后可能被复用（栈缓存复用）、大小比较无意义。要看内核身份用 `gettid()`（glibc 2.30+）或 `syscall(SYS_gettid)`；跨工具（top -H/perf/sched）一律认 TID。

</details>

**题目 3（判断）：** glibc 2.34+ 之后程序不再需要链接 `-lpthread`，说明线程已经变成"纯用户库"了？

<details>
<summary>参考答案</summary>

错。`libpthread` 合并进 libc 只是**库的组织形式**变化——线程实体依然是 `clone(CLONE_THREAD...)` 出来的内核 task_struct，同步原语依然落在 futex 系统调用上（无竞争时用户态快路径，见 30.1）。1:1 模型一点没变，变的只是符号藏在哪个 .so 里。

</details>
