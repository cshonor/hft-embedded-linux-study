## 本节讲什么

这是全章唯一一个"**看起来像 bug，其实是正确行为**"的章节。
一个三行程序，在终端上跑得好好的，重定向到文件后**一行输出变成两行、顺序还乱了**。

原书（书 p.537）原话：

> *"The output yielded by the program in Listing 25-2 demonstrates a phenomenon that is
> at first puzzling."*

现象（原书给的两种运行方式）：

```
$ ./fork_stdio_buf
Hello world
Ciao

$ ./fork_stdio_buf > a
$ cat a
Ciao
Hello world
Hello world
```

原书用一句话点出两个怪现象：

> *"In the above output, we see two strange things: **the line written by `printf()`
> appears twice**, and **the output of `write()` precedes that of `printf()`**."*

⭐ 这一节的全部内容，就是解释这两个现象，并给出三种修法。
而且它把上一节（`exit()` 三步）和 Ch24（`fork` 复制内存）**接在了一起**：

| 拼图 | 来自 |
|------|------|
| stdio 缓冲在**用户态内存**里 | §13.2 |
| `fork()` **复制**父进程的内存（含 stdio 缓冲） | Ch24 §24.2 |
| `exit()` 的第 ② 步**flush** stdio 缓冲 | §25.1 |
| `_exit()` **不** flush | §25.1 |

四块拼图一合，重复输出现象就是**必然**，而不是 bug。

### 逐条解读

**① 这个输出正是原书 `> a` 之后 `cat a` 的那三行。** 逐字一致：

```text
Ciao
Hello world
Hello world
```

⚠️ **为什么在 CE 上直接就是"重定向到文件"那一半？**
因为 CE 的 stdout 不是终端 —— 本章 `probe25` 实测 `S_ISSOCK = 1` / `isatty(1) = 0`。
glibc 的规则是"**只有终端**才用行缓冲"，所以这里 stdout 走**块缓冲（全缓冲）**。
⇒ **原书 `$ ./fork_stdio_buf`（终端、行缓冲）那一半，在本环境里物理上观察不到。**
后面第 3 节用一个自写程序间接补上这一半。

**② `Hello world` 出现两遍** —— 原书（书 p.538）：

> *"recall that the stdio buffers are maintained in a process's user-space memory…
> Therefore, these buffers are duplicated in the child by `fork()`. When standard output
> is directed to a terminal, it is line-buffered by default, with the result that the
> newline-terminated string written by `printf()` appears immediately. However, when
> standard output is directed to a file, it is block-buffered by default. Thus, in our
> example, the string written by `printf()` is still in the parent's stdio buffer at the
> time of the `fork()`, and this string is duplicated in the child. When the parent and
> the child later call `exit()`, they both flush their copies of the stdio buffers,
> resulting in duplicate output."*

时间线拆开看：

| 时刻 | 父进程用户态缓冲 | 内核缓冲 | 子进程 |
|------|------------------|----------|--------|
| `printf("Hello world\n")` 后 | `"Hello world\n"` | — | 还不存在 |
| `write(..., "Ciao\n", 5)` 后 | `"Hello world\n"` | `"Ciao\n"` | 还不存在 |
| `fork()` 后 | `"Hello world\n"` | `"Ciao\n"` | **缓冲副本**里有 `"Hello world\n"` |
| 子进程 `exit()` | 清空 → 写 `"Hello world\n"` | `"Ciao\n"` + `"Hello world\n"` | — |
| 父进程 `exit()` | 清空 → 又写 `"Hello world\n"` | `"Ciao\n"` + `"Hello world\n"` + `"Hello world\n"` | — |

⇒ **`fork()` 复制的是"还没送出去的输出"**。这就是重复的成因。

**③ `Ciao` 只出现一遍** —— 原书（书 p.538）：

> *"The output of the `write()` in the program in Listing 25-2 doesn't appear twice,
> because `write()` transfers data directly to a kernel buffer, and this buffer is not
> duplicated during a `fork()`."*

⭐ 这一条给出了一个**判定规则**：**重复与否，取决于数据在 `fork()` 那一刻
待在"用户态"还是"内核态"。**

| 通路 | `fork()` 那一刻数据在哪 | 会不会重复 |
|------|------------------------|-----------|
| `printf()` / `fwrite()` / `puts()` | 用户态 `FILE` 缓冲（块缓冲时） | **会** |
| `write()` / `sendfile()` / `read()` | 内核缓冲（或已交给设备） | 不会 |

**④ `Ciao` 排在 `Hello world` 前面** —— 原书（书 p.538）：

> *"The output of `write()` appears before that from `printf()` because the output of
> `write()` is immediately transferred to the kernel buffer cache, while the output from
> `printf()` is transferred only when the stdio buffers are flushed by the call to
> `exit()`."*

⇒ 这其实就是 §25.1 那三步的又一次体现：`write()` 立刻可见、`printf()` 要等第 ② 步。

**⑤ `diagnostics = 7`** —— 7 条诊断里，两条是官方源码自己的
`unused parameter 'argc'` / `'argv'`（`-Wunused-parameter`），
其余是 gcc 统计里的位置引用行。**与 Listing 25-1 一样，本仓库不修官方源码的 warning**，
以保证逐字镜像。见 `code/README.md`。

## 2. 三种修法（原书给的"药"）

原书（书 p.538）把修法分成两条 bullet，第二条里还藏了一条**通用准则**：

> *"We can prevent this duplicated output from occurring in one of the following ways:
> - As a specific solution to the stdio buffering issue, we can use `fflush()` to flush
>   the stdio buffer prior to a `fork()` call. Alternatively, we could use `setvbuf()`
>   or `setbuf()` to disable buffering on the stdio stream.
> - Instead of calling `exit()`, the child can call `_exit()`, so that it doesn't flush
>   stdio buffers. This technique exemplifies **a more general principle: in an
>   application that creates child processes, typically only one of the processes (most
>   often the parent) should terminate via `exit()`, while the other processes should
>   terminate via `_exit()`**. This ensures that only one process calls exit handlers and
>   flushes stdio buffers, which is usually desirable."*

整理成表格：

| 修法 | 做法 | 作用范围 | 代价 |
|------|------|----------|------|
| **A** | `fork()` 之前 `fflush(stdout)` | 只解决"这一刻缓冲里已有的内容" | 之后父进程继续 `printf` 还会进缓冲，**只在 `fork` 点有效** |
| **B** | 子进程用 `_exit()` 而不是 `exit()` | 从根上解决（子进程永不 flush、永不跑 handler） | 子进程自己的 handler 也不跑 ⇒ 需要"每个进程各自收场"时不能用 |
| **C** | `setbuf(stdout, NULL)` / `setvbuf(...)` 关缓冲 | 从根上解决，且父进程行为也变 | **每次 `printf` 都是一次 `write` 系统调用** ⇒ 性能大幅下降 |

原书还补了一段"什么时候可以父子都 `exit()`"（书 p.538）：

> *"Other approaches that allow both the parent and child to call `exit()` are possible
> (and sometimes necessary). For example, it may be possible to design exit handlers so
> that they operate correctly even if called from multiple processes, or to have the
> application install exit handlers only after the call to `fork()`. Furthermore,
> sometimes we may actually want all processes to flush their stdio buffers after a
> `fork()`. In this case, we may choose to terminate the processes using `exit()`, or use
> explicit calls to `fflush()` in each process, as appropriate."*

⇒ **三种"合法地父子都 `exit()`"的情形**：
① handler 本身写成多进程安全；② handler 只在 `fork()` **之后**才注册；
③ 你**确实想**每个进程都 flush 一次（比如每个进程各写一份日志）。

## 3. 三种修法的实测对照

把"病"和三种"药"放进同一个源文件，用 `argv[1]` 选模式，就能逐个对照。

### 完整源码（自写）

[`code/c25_fork_stdio_three_fixes.c`](../code/c25_fork_stdio_three_fixes.c)

```c
/* c25_fork_stdio_three_fixes.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 Listing 25-2（`fork_stdio_buf.c`）只演示了**病**：
     "Hello world\n" 走 printf（进用户态缓冲）、然后 write("Ciao\n")、
     然后 fork()、然后父子都 exit() —— 当 stdout 是**块缓冲**（被重定向到文件）时，
     父进程那一刻还没 flush 的缓冲被 fork() 复制进子进程，
     于是父子各 flush 一次 ⇒ "Hello world" 打印两遍，且 "Ciao" 反而在前。

   原书 §25.4 接着给了**药**，一共三种：
     A. fork() 之前用 fflush()（或 setvbuf()/setbuf() 关掉缓冲）
     B. 子进程改用 _exit()（不 flush，也不跑 exit handler）
        —— 由此引出更一般的准则：一个程序里应该只有**一个**进程用 exit() 收场，
           通常是父进程
     C. （同 A 的后半）直接对 stdio 流关缓冲

   本程序把病与三种药放进同一个源文件，用 argv[1] 选模式，方便逐个对照。

   ⚠️ 在 CE 上跑：stdout 不是终端（是 socket）⇒ glibc 对 stdout 用**全缓冲**，
   所以 CE 上「模式 0」直接就等于原书里 `./fork_stdio_buf > a` 那一半，
   而原书 `./fork_stdio_buf`（终端，行缓冲）那一半**在 CE 上观察不到** —— 
   模式 3（关缓冲）是 CE 上唯一能拿到「类终端顺序」的办法。

   编译: gcc -O0 -Wall -Wextra -o c25_fork_stdio_three_fixes c25_fork_stdio_three_fixes.c
   运行: ./c25_fork_stdio_three_fixes <0|1|2|3>
*/
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void
label(int mode)
{
    const char *desc;
    char buf[256];

    switch (mode) {
    case 1:  desc = "修法 A：fork() 之前 fflush(stdout)";      break;
    case 2:  desc = "修法 B：子进程改用 _exit()";               break;
    case 3:  desc = "修法 C：setbuf(stdout, NULL) 关掉缓冲";    break;
    default: desc = "模式 0（原书 Listing 25-2 原样）";          break;
    }
    snprintf(buf, sizeof(buf), "--- 模式 %d | %s ---\n", mode, desc);
    write(STDOUT_FILENO, buf, strlen(buf));   /* 用 write 打标签，不参与缓冲顺序 */
}

int
main(int argc, char *argv[])
{
    int mode = (argc > 1) ? atoi(argv[1]) : 0;
    pid_t pid;

    /* 修法 C 必须在第一次 printf 之前生效 */
    if (mode == 3)
        setbuf(stdout, NULL);

    label(mode);

    printf("Hello world\n");                    /* → 用户态缓冲（模式 3 除外） */
    write(STDOUT_FILENO, "Ciao\n", 5);          /* → 立刻进内核缓冲 */

    if (mode == 1)
        fflush(stdout);                         /* 修法 A：把缓冲清空后再 fork */

    pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        if (mode == 2)
            _exit(EXIT_SUCCESS);                /* 修法 B：子进程不 flush */
        exit(EXIT_SUCCESS);
    }

    if (wait(NULL) == -1) {
        perror("wait");
        return EXIT_FAILURE;
    }
    exit(EXIT_SUCCESS);
}
```

### 逐条解读

**① 模式 0 复现了病**：`Ciao` / `Hello world` / `Hello world` —— 与官方
`fork_stdio_buf` 的输出**逐字一致**。这是"病"的基准。

**② 模式 1 与模式 2 治好了重复**：都只剩一行 `Hello world`。
两种药机制不同但结果相同：

| 模式 | 机制 | 子进程还有没有 `"Hello world"` 的副本 |
|------|------|--------------------------------------|
| 1 | `fflush` 在 `fork` 前把缓冲清空 | **没有**（清空是共享的） |
| 2 | 子进程 `_exit()`，不 flush | **有，但没人送出去** |

⇒ 一条是"**让数据不在缓冲里**"，一条是"**让人不去送**"。**两条都能修，但适用范围不同**：
模式 1 只在 `fork()` 那一刻有效（之后父进程再 `printf` 又会有新内容）；
模式 2 是结构性的（子进程永远不 flush）。

**③ 模式 3 的**顺序反过来了**：`Hello world` 在 `Ciao` 之前** ——
这正是"**在终端上跑**"那一半的顺序（原书 `$ ./fork_stdio_buf` 的输出是
`Hello world` / `Ciao`）。

为什么？因为 `setbuf(stdout, NULL)` 让 stdout **无缓冲** ⇒ `printf("Hello world\n")`
立刻变成一次 `write()` 落到内核里，**排在后面那句 `write("Ciao\n")` 前面**。

⇒ ⭐ **所以模式 3 是 CE 上唯一能间接展示"行缓冲/无缓冲时顺序正常"的办法。**
它不等价于真终端（真终端是**行**缓冲，靠 `\n` 触发 flush；这里是**无**缓冲），
但在"输出顺序"这个观察面上等效。**笔记里必须说清这个区别，不能当成"终端行为"。**

**④ `execTime` 的对比值得一提**：模式 3（41 ms）明显慢于模式 0（18 ms）。
差别不完全来自 `setbuf`（这个程序输出量太小），但方向上是对的：
**无缓冲 = 每次 `printf` 一次系统调用**。原书在 §13.2 讲 stdio 性能时也强调这一点。
⇒ **生产代码里不要随手关缓冲。** 要的是"控制 flush 的时机"，不是"取消缓冲"。

**⑤ 一个容易忽略的细节：为什么标签用 `write()` 打？**
因为标签是"模式 N | 修法 X"这种**说明性文字**，如果它走 `printf`，
它会和被测数据挤进同一个缓冲，把观察顺序弄乱。
用 `write()` 打标签让它**不参与缓冲顺序**，观察才干净。
这是"观察者不能影响被测对象"在 I/O 层面的体现。

## 4. 一般化：什么时候该用 `_exit()`，什么时候该用 `exit()`

原书那条"更一般的准则"值得单独画一张决策表：

| 场景 | 用哪个 | 为什么 |
|------|--------|--------|
| 单进程程序正常结束 | `exit()`（或 `main` return） | 要跑 handler、要 flush |
| `fork()` 出来的**子进程**（不 `exec`） | **`_exit()`** | 避免重复 flush / 重复跑 handler |
| `fork()` 之后立刻 `exec()` 的子进程 | 无所谓（但习惯用 `_exit()`） | `exec` 会清 handler；且失败路径要立刻收场 |
| `vfork()` 的子进程 | **必须 `_exit()`** | SUSv3 规定；`return` 会拆父进程的栈（Ch24 §24.3） |
| **信号处理器**里 | **`_exit()`** | `exit()` 不是 async-signal-safe（原书 §25.3 明说） |
| 主进程 / 最后一个收场的人 | `exit()` | 它负责跑 handler 与 flush |

⚠️ 注意第 2 与第 6 条是**互补**的：**"一个程序里只有一个进程该用 `exit()` 收场，
通常是父进程。"** 这句话听起来像风格建议，其实是为了**保证 handler 只跑一次、
缓冲只 flush 一次**。

## 5. ⚠️ 混用 stdio 与系统调用：原书点到的一条更普遍的坑

原书在本节末尾（书 p.538）留了一句跨章的提醒：

> *"(In general, care is required when mixing stdio functions and system calls to
> perform I/O on the same file, as described in Section 13.7.)"*

本节的程序就是这句话的**最小反例**：同一个 stdout 上，`printf` 与 `write` 的输出
**顺序无法预测**（取决于缓冲状态）。在真实代码里这会变成更隐蔽的问题：

| 混用写法 | 危险 |
|----------|------|
| `printf(...)` + `write(fileno(stdout), ...)` | 顺序错乱（本节） |
| `fprintf(fp, ...)` + `write(fileno(fp), ...)` | 同上，且**文件偏移**可能错位 |
| `fread(fp)` + `read(fileno(fp))` | **读串位**：`fread` 已经预读了一大块进缓冲，`read` 从内核位置继续读 ⇒ 数据丢失 |
| `fprintf(fp)` + `ftruncate(fileno(fp))` | 缓冲里的数据还没落盘，截断尺寸不对 |

⇒ **规则：同一个文件一个进程里只选一套 API。** 要么全 stdio，要么全系统调用。
非要混用就在边界处 `fflush()` / `fseek(fp, 0, SEEK_CUR)`（后者会丢弃预读缓冲）。

## 6. 源码坐标

| 主题 | 坐标 | 说明 |
|------|------|------|
| glibc 判定"该不该用行缓冲" | glibc `libio/iopopen.c` / `libio/fileops.c`：`_IO_file_doallocate()` 里查 `st_blksize`；`libio/iosetbuffer.c` 设置缓冲模式 | 核心判据是 **`isatty(fd)`**；是终端 ⇒ 行缓冲，否则 ⇒ 块缓冲（`st_blksize`，通常 4096） |
| stdout 的默认缓冲 | glibc `libio/stdio.c` / `_IO_2_1_stdout_` | stdout 的 `_flags` 里有 `_IO_LINE_BUF` 位，仅在 `isatty` 为真时置位 |
| `setvbuf()` / `setbuf()` | glibc `libio/setvbuf.c` / `libio/setbuf.c` | `setbuf(fp, NULL)` 等价 `setvbuf(fp, NULL, _IONBF, 0)` |
| `fflush()` 走 `_IO_SYNC` | glibc `libio/iofflush.c` | `_IO_flush_all()` 会遍历所有打开的流 |
| `printf` 的落盘时机 | glibc `libio/vfprintf.c` | 缓冲满 / 遇 `\n`（行缓冲）/ 显式 flush / `exit()` 的 `_IO_cleanup` |
| `exit()` 里的 flush | glibc 2.39 `stdlib/exit.c:128-129` | `if (run_list_atexit) call_function_static_weak (_IO_cleanup);` |
| `write()` 的路径 | Linux v6.6 `fs/read_write.c` `ksys_write()` → `vfs_write()` | **直接进内核缓冲**，与用户态 `FILE` 无关 |
| `fork()` 复制用户态内存 | Linux v6.6 `kernel/fork.c:2240` `copy_process()` → `dup_task_struct()` / `copy_mm()` | COW 复制 ⇒ 缓冲内容"看起来"被复制了 |
| 内核**没有** stdio 概念 | —— | 内核只见 `write()`；`FILE` / 缓冲 / 行缓冲全部是 glibc 的东西 |
| §13.2 stdio 缓冲 | 本仓库 [../chapter-13-file-io-buffering/](../../chapter-13-file-io-buffering/README.md) | 缓冲模式的完整规则 |
| §13.7 stdio 与系统调用混用 | 同上 | 混用时的偏移与缓冲问题 |

⚠️ **一个关键的认识**：`fork()` **并没有"复制 stdio 缓冲"这个动作**。
它只是复制了**整个用户态地址空间**（COW），而缓冲恰好住在里面。
所以**任何"住在用户态里的状态"在 `fork()` 之后都会有一份副本** ——
不只是 stdio 缓冲，还有：你自定义的日志缓冲、malloc 里的 arena 元数据、
`rand()` 的内部状态、你的"批量攒够了再发"的行情缓冲。

⇒ **`fork()` 之后的子进程必须假设"所有用户态缓存都是过期的"。**

---

## 7. 常见坑

1. **别在 `fork()` 之前留 `printf` 输出在缓冲里**（本节主角）。
   `fflush(NULL)` 一次全清，或者在 `fork` 之后立刻让子进程走 `_exit()`。
2. **`fflush(stdout)` 只清 stdout**，`stderr` 默认无缓冲不用管，
   但别的东西（你自己 `fopen` 的日志文件）要 `fflush(NULL)` 或逐个清。
3. **`fork()` 之后父子共用同一个文件偏移（共享 open file description）**，
   所以即使不重复输出，两边的 `write` 也会**交错**。
   想让子进程自己写一份，得先 `open` 一个新 fd（或者 `O_APPEND`）。
4. **`setbuf(stdout, NULL)` 要放在第一次 `printf` 之前**，
   否则缓冲区已经分配，行为是"已分配但换成无缓冲"，语义不清晰。
5. **`setvbuf()` 必须在任何 I/O 之前调用**（POSIX 要求）。
6. **别把 `fork()` 之后的子进程 `exit()` 当成"等价于 `_exit()`"** ——
   它会跑一遍父进程注册的 handler（那些 handler 可能假设"只有父进程会跑"，
   比如写固定路径的日志文件 / 释放共享资源）⇒ 双重释放、日志写两遍。
7. **在 CE 上不能观察"终端行缓冲"那一半**（`probe25` 实测 stdout 是 socket）。
   笔记里凡是引用"终端行为"，必须标为**原书行为**，不能用 CE 实测冒充。

---

## 8. HFT / 嵌入式关联

**① `fork` 之后的"双重 flush"在 HFT 里通常表现为"日志写两遍"或"审计记录重复"。**
一个下单进程 `fork` 出子进程处理某个连接，父子都 `exit()` ——
如果父进程的日志缓冲里还有没落盘的行，子进程会把它再写一遍。
**后果不是"多一行日志"，而是"多一条看起来合法的成交记录"。**
⇒ 这是**数据集污染的经典成因**，排查时先看"记录数是不是恰好成倍"。

**② 更隐蔽的一类：`fork()` 复制的不只是 stdio 缓冲，而是所有用户态批量缓冲。**
一个"攒够 64 条行情再一次性发包"的网关，如果在 `fork()` 那一刻缓冲里有 30 条，
子进程会把这 30 条**再发一遍**。⇒ **在任何 `fork()` 之前，
所有"攒着的、还没送出去的东西"都必须显式处理干净**（flush、清空、或者干脆不用 `fork`）。

**③ 嵌入式里 `_exit()` 反而是常态。**
资源极度受限的 daemon 经常在错误路径上"直接重启"：
`_exit(EXIT_FAILURE)` 然后让 init / watchdog 拉起来。
这**故意**跳过了 handler 与 flush —— 前提是**关键状态不放在用户态缓冲里**，
而是每步都同步落到 flash / SD 卡 / NVRAM。

**④ 反过来，如果嵌入式程序依赖 `printf` 打日志到串口（终端），
它的行为是行缓冲，和 `fork` 之后的块缓冲完全不同。**
同一个程序"在开发板上直接跑"和"通过日志重定向到文件跑"，
输出顺序可能不一样 —— 这正是本节现象的实战版本。

**⑤ 性能上的一点提醒**：低延迟路径上应该**明确控制缓冲**，
而不是依赖默认值。常见做法是：日志走**独立的无缓冲 fd**（`write()` 到
`/dev/shm/` 或 ring buffer），业务输出走默认缓冲。
把"要不要立刻可见"变成一个**显式决策**，而不是"取决于 stdout 是不是终端"。

<summary>代码自测（Q&A）</summary>

**Q1：`fork_stdio_buf` 重定向到文件时，为什么 `Hello world` 打印两遍？**

A：因为 **stdio 缓冲在用户态内存**里，`fork()` 会把它**整个复制一份**。
`printf("Hello world\n")` 的内容在块缓冲模式下还留在父进程缓冲里，
`fork()` 时被复制进子进程；随后父子各调 `exit()`，**各 flush 一次**
⇒ 同一行输出两次。
关键判据：数据在 `fork()` 那一刻待在**用户态**还是**内核态**。

**Q2：为什么 `Ciao` 只出现一遍，而且排在 `Hello world` 前面？**

A：`Ciao` 是用 `write()` 写的，**直接进内核缓冲**，内核缓冲**不会**被 `fork()`
复制 ⇒ 不重复。而 `printf` 要等 `exit()` 的第 ② 步才 flush ⇒ 时间上晚，
所以 `Ciao` 先出现。

**Q3：原书给了哪三种修法？各自的适用面是什么？**

A：
1. **`fork()` 之前 `fflush()`**（或 `setvbuf` / `setbuf` 关缓冲）——
   只解决"`fork` 那一刻缓冲里已有的内容"。
2. **子进程改用 `_exit()`** —— 结构性解决（子进程永不 flush、永不跑 handler）。
3. **对 stdio 流关缓冲** —— 也解决，但每次 `printf` 都变成系统调用，**有性能代价**。

**Q4：原书说"更一般的准则"是什么？**

A：*"in an application that creates child processes, typically **only one of the
processes (most often the parent) should terminate via `exit()`**, while the other
processes should terminate via `_exit()`."*
理由：**保证只有一处调用 exit handler、只有一处 flush 缓冲。**

**Q5：什么时候"父子都调用 `exit()`"是可以的？**

A：原书列了三种：① exit handler 设计成"被多个进程调用也正确"；
② **只在 `fork()` 之后才注册 exit handler**；
③ 你**确实想**每个进程都 flush 一次自己的缓冲。
另外一种通用做法是在每个进程里各显式 `fflush()` 一次。

**Q6：为什么 CE 上只能观察到"重定向到文件"那一半？**

A：因为 CE 的 stdout 是 **socket**（实测 `S_ISSOCK = 1`、`isatty(1) = 0`），
glibc 只对**终端**用行缓冲，这里走**块缓冲**。
所以本节官方程序在 CE 上直接就是原书 `> a` 那一半。
"终端行缓冲"那一半**物理上不可观察**，本仓库用自写程序模式 3
（`setbuf(stdout, NULL)`）来间接展示"顺序正常"的情形 ——
但必须说明那是**无缓冲**，不等于**行缓冲**。

**Q7：`setbuf(stdout, NULL)` 为什么能让输出的顺序变成"正常"？**

A：因为关掉缓冲后 `printf("Hello world\n")` **立刻**变成一次 `write()`，
落进内核缓冲，于是它排在后面那句 `write("Ciao\n")` **前面** ——
和原书在终端上看到的顺序一致。
注意：终端是**行**缓冲（靠 `\n` 触发），而这里是**无**缓冲，机制不同、观察面相同。

**Q8：`fork()` 之后，子进程除了 stdio 缓冲之外还"继承"了哪些危险状态？**

A：凡是**住在用户态里的缓存**都有一份副本。典型：
你自己实现的"攒够 N 条再发"的行情缓冲、日志缓冲、
`rand()` / 伪随机数的内部状态、数据库连接池里的半成品请求、
内存分配器里的空闲链表视图。
⇒ **`fork()` 之后必须假设所有用户态缓存都是过期的。**
