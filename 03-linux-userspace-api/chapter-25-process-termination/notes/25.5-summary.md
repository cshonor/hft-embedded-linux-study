## 小结原文（书 p.538–539）

原书这一节只有三段，但把全章讲完了：

> *"A process can terminate either abnormally or normally. Abnormal termination occurs on
> delivery of certain signals, some of which also cause the process to produce a core
> dump file."*
>
> *"Normal termination is accomplished by calling `_exit()` or, more usually, `exit()`,
> which is layered on top of `_exit()`. Both `_exit()` and `exit()` take an integer
> argument whose least significant 8 bits define the termination status of the process.
> By convention, a status of 0 is used to indicate successful termination, and a nonzero
> status indicates unsuccessful termination."*
>
> *"As part of **both** normal and abnormal process termination, the kernel performs
> various cleanup steps. Terminating a process normally by calling `exit()` additionally
> causes exit handlers registered using `atexit()` and `on_exit()` to be called (in
> reverse order of registration), and causes stdio buffers to be flushed."*

拆成三句人话：

| 原书句子 | 要点 |
|----------|------|
| "abnormally … on delivery of certain signals" | 异常终止 = 信号；**部分信号还会产生 core dump**（本仓库 Ch24 实测：沙箱 `RLIMIT_CORE = 0`，core 拿不到） |
| "`exit()` … **layered on top of** `_exit()`" | `exit()` 不是另一条路，它就是 `_exit()` **加了两层**：逆序 handler + flush |
| "As part of **both** normal and abnormal … the kernel performs various cleanup steps" | **⚠️ 这句是全章最容易读漏的一句。** 内核那十条（§25.2）**不管你怎么死都执行**；被 `SIGKILL` 也一样 |

⭐ 全章的逻辑链其实是**一条直线**：

```text
exit() 的定义（§25.1：三步）
      │
      ├─ 第 ① 步「逆序跑 exit handler」 ─────────► §25.3 Exit Handlers
      │                                            （LIFO / 插队首 / 不返回 / 上限 / fork 继承 / exec 清除）
      │
      ├─ 第 ② 步「flush stdio 缓冲」 ─────────────► §25.4 fork + 缓冲 + _exit()
      │                                            （缓冲在用户态 ⇒ fork 复制 ⇒ 重复输出）
      │
      └─ 第 ③ 步「调 _exit(status)」 ─────────────► §25.6 习题 25-1
                                                   （低 8 位怎么变成 WEXITSTATUS）

另有不在 exit() 里的一条支线：
      §25.2 内核 + C 库的十条清理（正常/异常都执行）
```

## 本章值得记住的 8 条

1. **`exit()` = `_exit()` + ① 逆序 exit handler + ② flush stdio 缓冲**，
   顺序**不能换**。glibc 的实现就是 `stdlib/exit.c:135-140` 那一行调用，
   而 `_IO_cleanup()`（第 ② 步）写在 `while` 循环**之后**、`_exit()` **之前**。
2. **`_exit()` 之后，没 flush 的输出就是垃圾。** 实测（`c25_exit_handler_no_return`
   情形 A）：两行 `printf` 的输出**彻底消失**。
   ⇒ 可能走 `_exit()` / `abort()` 的代码路径上，**用 `write(2)` 或
   `fprintf(stderr, ...)` 记录现场**。
3. **exit handler 完全是 glibc 用户态机制，内核一无所知**（`kernel/exit.c` 里
   没有任何相关代码）。这直接解释了为什么"被信号杀死时 handler 不跑"。
4. **⭐ 原书一处数字勘误：** `sysconf(_SC_ATEXIT_MAX)` 原书写 **2,147,482,647**，
   实测是 **2,147,483,647**（`0x7fffffff` = `INT_MAX`）。
   原书自己那句括号里的解释（"the maximum signed 32-bit integer"）才是对的。
5. **handler 里再注册 handler ⇒ 插到剩余待调列表的队首（下一个就跑）。**
   实测顺序 `C → B → D → A`。机制在 `cxa_atexit.c:104-131` + `exit.c:113-116`
   的 `goto restart`。
6. **`fork()` 复制的是"整个用户态地址空间"，而 stdio 缓冲恰好住在里面。**
   ⇒ 重复输出不是 bug。真正的规则是：**任何"住在用户态里的缓存"在 `fork()`
   之后都有一份副本** —— 不只 stdio，还有你自己攒的行情缓冲、日志缓冲。
7. **一条通用准则：一个程序里只该有一个进程用 `exit()` 收场（通常是父进程），
   其余用 `_exit()`。** 这保证 handler 只跑一次、缓冲只 flush 一次。
8. **`_BSD_SOURCE` 在 glibc 2.39 已弃用**（实测编译报警，
   `include/features.h:196`），但**仍然有效** —— 报警后会自动定义成 `_DEFAULT_SOURCE`。
   新代码直接用 `_DEFAULT_SOURCE`。

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`exit()` 和 `_exit()` 的差别，一句话说清？**

A：**`exit()` = `_exit()` + ① 逆序跑 exit handler + ② flush stdio 缓冲。**
`_exit()` 只做第 ③ 步。所以：handler 不跑、缓冲不 flush 的路径，
一定是走了 `_exit()`（或者被信号杀死）。

**Q2：§25.2 那十条清理动作，被 `SIGKILL` 杀掉时会执行吗？**

A：**会。** 原书写的是 *"During **both normal and abnormal** termination of a process,
the following actions occur"* —— 这十条是 `do_exit()` 里的内核动作。
被信号杀掉**不执行**的只有用户态那三件事（handler / flush / `_exit()` 的返回值语义）。

**Q3：`atexit()` 注册的 handler，怎么"注销"？**

A：**注销不了**。原书给的标准做法是**全局 flag**：
handler 里先检查 flag，要禁用就清 flag 并直接 `return`。

**Q4：handler 里调 `exit()` 会怎样？**

A：**Linux 上剩下的 handler 照常跑、flush 照常发生**（实测情形 B，父进程拿到 9）。
但 **SUSv3 说这是 UB**，原书明确警告某些系统会**无限递归到栈溢出**
（*"Portably applications should avoid calling `exit()` inside an exit handler."*）。

**Q5：原书说"更一般的原则"是什么？**

A：*"in an application that creates child processes, typically **only one of the
processes (most often the parent) should terminate via `exit()`**, while the other
processes should terminate via `_exit()`."*
目的是**只让一处跑 handler、只让一处 flush**。

**Q6：`fork_stdio_buf` 重定向到文件时输出三行，为什么？**

A：`printf` 的 `"Hello world\n"` 在块缓冲下还留在用户态缓冲里，`fork()` 连缓冲一起复制，
父子各 `exit()` 各 flush 一次 ⇒ 出现两遍；
`write` 的 `"Ciao\n"` 直接进内核缓冲、不被 `fork` 复制 ⇒ 只出现一遍，
而且因为它立刻可见、`printf` 要等 `exit()` 才可见 ⇒ 它排在前面。

**Q7：本章最大的"意外收获"是什么？**

A：**原书一处数字勘误。** 原书 p.535 说 `sysconf(_SC_ATEXIT_MAX)` 返回
**2,147,482,647**，实测是 **2,147,483,647**（`0x7fffffff` = `INT_MAX`）。
原书同一句里"i.e., the maximum signed 32-bit integer"的解释才是对的。
⇒ **凡是原书里出现的"具体数字"，都应该实测一遍。**

**Q8：为什么说"exit handler 是纯用户态机制"这件事很重要？**

A：因为它一次性解释了三条现象：
① 被信号杀死时 handler 不跑（内核直接进 `do_exit()`，glibc 没机会介入）；
② `exec()` 会清掉注册（handler 是**代码**，代码被换掉了）；
③ `fork()` 会得到一份副本（注册表是**用户态数据**，被 COW 复制）。
三条现象是同一个事实的三个面。

**Q9：本章最该带走的"工程准则"是哪一条？**

A：**"一个程序里只该有一个进程用 `exit()` 收场"** ——
以及它的直接推论：**凡是可能走 `_exit()` / `abort()` / 被信号杀死的代码路径，
不要用 `printf` 记录现场**（实测：那两行输出会彻底消失）。
