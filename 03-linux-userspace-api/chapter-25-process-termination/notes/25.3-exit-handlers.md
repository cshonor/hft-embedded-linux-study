## 本节讲什么

原书先用一个**现实动机**开场（书 p.533）：

> *"Consider the example of an application library that, if used during the life of the
> process, needs to have some cleanup actions performed automatically when the process
> exits. Since the library doesn't have control of when and how the process exits, and
> can't mandate that the main program call a library-specific cleanup function before
> exiting, cleanup is not guaranteed to occur."*

也就是说：**库作者**没法要求"用我库的人记得在 `main` 最后调我的清理函数"。
唯一的出路是"你退出的时候我自己被叫起来" —— 这就是 **exit handler**
（老的 System V 手册叫 *program termination routine*）。

原书紧接着给出定义与**边界**（书 p.534，这一句定义了整个机制的范围）：

> *"An exit handler is a programmer-supplied function that is registered at some point
> during the life of the process and is then automatically called during **normal**
> process termination via `exit()`. Exit handlers are **not** called if a program calls
> `_exit()` directly or if the process is terminated abnormally by a signal."*

⭐ 本节要把下面六件事全部变成可验证的事实：

| # | 结论 | 用什么程序验证 |
|---|------|----------------|
| 1 | 逆序（LIFO）调用 | 官方 `exit_handlers.c`（Listing 25-1） |
| 2 | `atexit()` 与 `on_exit()` **共用一条列表**，一起逆序 | 同上（两种注册交错） |
| 3 | handler 里再注册 ⇒ **插到剩余待调列表的队首** | 自写 `c25_atexit_reentry.c` |
| 4 | handler **不返回**（`_exit()`）⇒ 剩余 handler 与 flush 全取消 | 自写 `c25_exit_handler_no_return.c` |
| 5 | handler 里调 `exit()` ⇒ **Linux 上剩余 handler 照常跑**（SUSv3 说 UB） | 同上 |
| 6 | `fork()` 继承一份副本；**`exec()` 全部清掉** | 自写 `c25_exec_clears_handlers.c` |

## 1. 两个接口

```c
#include <stdlib.h>

int atexit(void (*func)(void));                 /* 成功返回 0，错误返回【非 0】 */
/* Returns 0 on success, or nonzero on error */

#define _BSD_SOURCE                             /* 或 #define _SVID_SOURCE */
#include <stdlib.h>

int on_exit(void (*func)(int, void *), void *arg);   /* glibc 非标准 */
/* Returns 0 on success, or nonzero on error */
```

**handler 的两种签名**：

```c
/* atexit() 注册的 */
void
func(void)
{
    /* Perform some actions */
}

/* on_exit() 注册的 */
void
func(int status, void *arg)
{
    /* Perform cleanup actions */
}
```

⚠️ 三个容易写错的细节：

1. **错误返回值是"非 0"，不一定等于 −1。** 原书（书 p.534）特意强调：
   *"Note that `atexit()` returns a nonzero value (not necessarily –1) on error."*
   ⇒ 判断写法只能是 `if (atexit(f) != 0)`，**不能写 `if (atexit(f) == -1)`**。
2. **`on_exit()` 的 `arg` 声明成 `void *`，但可以当整数用。** 原书（书 p.536）：
   *"Although defined as a pointer type, `arg` is open to programmer-defined
   interpretation. It could be used as a pointer to some structure; equally, through
   judicious use of casting, it could be treated as an integer or other scalar type."*
   官方 Listing 25-1 就是当整数用的：`on_exit(onexitFunc, (void *) 10)`。
3. **`on_exit()` 需要 `_BSD_SOURCE`（或 `_SVID_SOURCE`）才能看到声明。**
   ⚠️ **在 glibc 2.39 上这两个宏已经弃用**，实测编译时会报警（见下面第 2 节的诊断原文）。

```c
/* exit_handlers.c

   Demonstrate the use of atexit(3) and on_exit(3), which can be used to
   register functions (commonly known as "exit handlers") to be called at
   normal process exit. (These functions are not called if the process does
   an _exit(2) or if it is terminated by a signal.)
*/
#define _BSD_SOURCE     /* Get on_exit() declaration from <stdlib.h> */
#include <stdlib.h>
#include "tlpi_hdr.h"

#ifdef __linux__        /* Few UNIX implementations have on_exit() */
#define HAVE_ON_EXIT
#endif

static void
atexitFunc1(void)
{
    printf("atexit function 1 called\n");
}

static void
atexitFunc2(void)
{
    printf("atexit function 2 called\n");
}

#ifdef HAVE_ON_EXIT
static void
onexitFunc(int exitStatus, void *arg)
{
    printf("on_exit function called: status=%d, arg=%ld\n",
                exitStatus, (long) arg);
}
#endif

int
main(int argc, char *argv[])
{
#ifdef HAVE_ON_EXIT
    if (on_exit(onexitFunc, (void *) 10) != 0)
        fatal("on_exit 1");
#endif
    if (atexit(atexitFunc1) != 0)
        fatal("atexit 1");
    if (atexit(atexitFunc2) != 0)
        fatal("atexit 2");
#ifdef HAVE_ON_EXIT
    if (on_exit(onexitFunc, (void *) 20) != 0)
        fatal("on_exit 2");
#endif

    exit(2);
}
```

### 逐条解读

**① 输出与官方 `$ ./exit_handlers` 的示例输出逐字一致。** 原书（书 p.536）：

```
$ ./exit_handlers
on_exit function called: status=2, arg=20
atexit function 2 called
atexit function 1 called
on_exit function called: status=2, arg=10
```

⇒ **26 年后的 glibc 2.39 上，这个例子的行为与原书写作时完全一致。**

**② 四行输出的顺序，正好是注册顺序的**完全逆序**：

| 注册次序 | 调用 | `arg` | 实际出现次序 |
|----------|------|-------|--------------|
| 1 | `on_exit(onexitFunc, 10)` | 10 | **第 4** |
| 2 | `atexit(atexitFunc1)` | — | **第 3** |
| 3 | `atexit(atexitFunc2)` | — | **第 2** |
| 4 | `on_exit(onexitFunc, 20)` | 20 | **第 1** |

原书给的理由（书 p.534）：

> *"This ordering is logical because, typically, functions that are registered earlier are
> those that carry out more fundamental types of cleanups that may need to be performed
> after later-registered functions."*

⚠️ 注意 `on_exit` 那两行的**参数不同**（`arg=20` vs `arg=10`），这说明
**同一个函数注册了两次、两次都跑**。原书（书 p.534）确认这合法：
*"It is possible to register multiple exit handlers (and even the same exit handler
multiple times)."*

**③ `status=2` 在两行里都一样** —— 因为 handler 拿到的 `status` 就是
`exit(2)` 传的那个值，两次调用是同一次 `exit()` 触发的。
⇒ 这也说明 `on_exit()` 的 handler **看得到退出状态**，而 `atexit()` 的看不到（第 6 节）。

**④ 诊断里有 12 条 warning，全部来自官方源码本身：**

弃用警告之后 glibc 会**自动把它定义成 `_DEFAULT_SOURCE`**，功能不受影响。
写新代码应该直接用 `_DEFAULT_SOURCE`。

## 3. handler 里可以再注册 handler —— 而且**插队首**

原书（书 p.534）有一句特别容易被略过的话：

> *"Essentially, any desired action can be performed inside an exit handler, including
> registering additional exit handlers, which are **placed at the head of the list of
> exit handlers that remain to be called**."*

"placed at the head of the list that remain to be called" —— 这不是"追加到队尾"，
而是**插队到队首**，也就是**下一个就跑**。这个语义值得做成可观察量。

### 完整源码（自写）

[`code/c25_atexit_reentry.c`](../code/c25_atexit_reentry.c)

```c
/* c25_atexit_reentry.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.3 在讲 atexit() 的调用顺序时，插了一句很容易被略过的话：

     "Essentially, any desired action can be performed inside an exit handler,
      including registering additional exit handlers, which are placed at the
      head of the list of exit handlers that remain to be called."

   「placed at the head of the list that remain to be called」—— 这不是
   「追加到队尾」，而是**插队到队首**。本程序把这个语义做成可观察量：
   main 里依次注册 A、B、C（⇒ 逆序跑：C、B、A），然后在 B 里面再注册一个 D。
   如果 D 是「追加到队尾」，顺序会是 C、B、A、D；
   如果 D 是「插到队首」，顺序会是 C、B、D、A。

   在 CE 上跑：stdout 不是终端 ⇒ 全缓冲 ⇒ 所有 puts/printf 都先攒在缓冲里，
   最后由 exit() 第 ② 步一次性写出，所以**打印顺序 == handler 执行顺序**。

   编译: gcc -O0 -Wall -Wextra -o c25_atexit_reentry c25_atexit_reentry.c
   运行: ./c25_atexit_reentry
*/
#include <stdio.h>
#include <stdlib.h>

static void
handlerD(void)
{
    printf("  handler D   ← 这个是在 handler B 里才注册的\n");
}

static void
handlerC(void)
{
    printf("  handler C\n");
}

static void
handlerB(void)
{
    printf("  handler B   ← 就在这一行里又注册了 D\n");
    if (atexit(handlerD) != 0) {
        printf("  !! 在 handler 里注册 D 失败\n");
    }
}

static void
handlerA(void)
{
    printf("  handler A\n");
}

int
main(void)
{
    printf("=== 注册顺序：A、B、C ⇒ 逆序执行：C、B、A ===\n");
    printf("=== 但 B 会在自己运行期间再注册一个 D ===\n\n");

    if (atexit(handlerA) != 0 || atexit(handlerB) != 0 || atexit(handlerC) != 0) {
        printf("atexit 注册失败\n");
        return EXIT_FAILURE;
    }

    printf("--- main 调 exit(0)，下面三行/四行的次序就是答案 ---\n");
    exit(0);    /* 不返回 */
}
```

### 编译命令

```bash
gcc -O0 -Wall -Wextra -o c25_atexit_reentry c25_atexit_reentry.c
```

### CE 实测（`c25_atexit_reentry`）

```text
=== 注册顺序：A、B、C ⇒ 逆序执行：C、B、A ===
=== 但 B 会在自己运行期间再注册一个 D ===

--- main 调 exit(0)，下面三行/四行的次序就是答案 ---
  handler C
  handler B   ← 就在这一行里又注册了 D
  handler D   ← 这个是在 handler B 里才注册的
  handler A
```

`build code = 0`，`exit code = 0`，`execTime = 21` 毫秒，`diagnostics = 0`。

### 逐条解读

**① 顺序是 `C → B → D → A`，不是 `C → B → A → D`** —— ⇒ **D 插到了队首**，
它"插"在 A 前面跑。如果 `atexit()` 只是简单地把新条目追加到列表末尾，
`D` 必然排在 `A` 之后。**原书的 "head of the list" 得到实测确认。**

**② 机制在 glibc 源码里可以逐行对上。** `__run_exit_handlers()`
（`stdlib/exit.c:64-66`）是这么消费列表的：

```c
      while (cur->idx > 0)
	{
	  struct exit_function *const f = &cur->fns[--cur->idx];
```

下标**递减** ⇒ 先跑"最后注册的那条"。而 `__new_exitfn()`
（`stdlib/cxa_atexit.c:126-131`）在**同一块还有空位**时是这样放的：

```c
  else
    {
      /* There is more room in the block.  */
      r = &l->fns[i];
      l->idx = i + 1;
    }
```

关键在于 `i` 的初值（`cxa_atexit.c:91-98`）：它从 `l->idx` 往下找到第一个空位 ——
而 `l->idx` 就是**当前消耗位置**（因为 `__run_exit_handlers` 直接改的就是这个字段）。
⇒ 新条目被放到"下一个就轮到的位置"。放完之后 `exit.c:113-116` 检测到
"注册数变了"就 `goto restart`，于是它马上被执行：

```c
	  if (__glibc_unlikely (new_exitfn_called != __new_exitfn_called))
	    /* The last exit function, or another thread, has registered
	       more exit functions.  Start the loop over.  */
	    goto restart;
```

**③ 如果在 `exit()` 处理期间注册会失败吗？** —— `__new_exitfn()` 开头有一道闸
（`cxa_atexit.c:86-89`）：

```c
  if (__exit_funcs_done)
    /* Exit code is finished processing all registered exit functions,
       therefore we fail this registration.  */
    return NULL;
```

`__exit_funcs_done` 只在**整条链走完**才被置位（`exit.c:60`），所以
"在 handler 里注册"在正常情形下不会失败。**但如果是在最后一个 handler 里注册，
而且此时列表已经耗尽**，`atexit()` 就会返回非 0 了。

## 4. handler 里不返回：两种后果完全不同

原书（书 p.534）在这里连续放了两段**后果完全相反**的说法：

> *"…if one of the exit handlers fails to return—either because it called `_exit()` or
> because the process was terminated by a signal (e.g., the exit handler called
> `raise()`) —then the remaining exit handlers are **not** called. In addition, the
> remaining actions that would normally be performed by `exit()` (i.e., flushing stdio
> buffers) are **not** performed."*
>
> *"SUSv3 states that if an exit handler itself calls `exit()`, the results are
> **undefined**. On Linux, the remaining exit handlers are invoked **as normal**."*

同一个"在 handler 里终止进程"的动作，走 `_exit()` 就"全取消"，
走 `exit()` 就"照常继续"。这个差别必须实测。

### 完整源码（自写）

[`code/c25_exit_handler_no_return.c`](../code/c25_exit_handler_no_return.c)

```c
/* c25_exit_handler_no_return.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.3「Registering exit handlers」里有两条相邻、但后果完全不同的说法：

     (1) "if one of the exit handlers fails to return—either because it called
          _exit() or because the process was terminated by a signal—then the
          remaining exit handlers are not called. In addition, the remaining
          actions that would normally be performed by exit() (i.e., flushing
          stdio buffers) are not performed."

     (2) "SUSv3 states that if an exit handler itself calls exit(), the results
          are undefined. On Linux, the remaining exit handlers are invoked as
          normal."

   同样的「在 handler 里终止进程」，一个把剩下的全部取消，一个照常继续。
   本程序把两种情形各跑一遍（都放在子进程里跑，父进程只负责收尸和报数），
   让差别变成可观察量。

   ⚠️ 注意：父进程在每次 fork() 之前显式 fflush(stdout)。不这么做的话，
   父进程自己上一阶段的报表还在缓冲里，会被子进程连缓冲一起继承，
   然后被子进程的 exit() 再 flush 一遍 —— 那正是 §25.4 要讲的坑。

   编译: gcc -O0 -Wall -Wextra -o c25_exit_handler_no_return c25_exit_handler_no_return.c
   运行: ./c25_exit_handler_no_return
*/
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void
w(const char *s)
{
    write(STDOUT_FILENO, s, strlen(s));
}

static void
w2(const char *tag, const char *s)
{
    w("    ");
    w(tag);
    w(" ");
    w(s);
    w("\n");
}

/* 先注册、后跑：它只在「剩下的 handler 还会被调用」时才有输出 */
static void
handlerA(void)
{
    w2("W-hA", "       （hA：只 write + printf，不终止）");
    printf("    M-hA         （hA 的 printf，进用户态缓冲）\n");
}

/* 后注册、先跑：情形 ① —— handler 里 _exit() */
static void
handlerBAbort(void)
{
    w2("W-hB(_exit)", "（hB：立刻 _exit(7)，不再返回）");
    _exit(7);
}

/* 后注册、先跑：情形 ② —— handler 里 exit() */
static void
handlerBExit(void)
{
    w2("W-hB(exit)", " （hB：调用 exit(9)）");
    exit(9);
}

static void
runPhase(const char *tag, const char *note, void (*hB)(void))
{
    pid_t pid;
    int status;

    printf("\n=== 情形 %s：%s ===\n", tag, note);
    printf("  子进程登记顺序：先 hA，后 hB ⇒ LIFO ⇒ 先跑 hB\n");

    fflush(stdout);              /* ★ 关键：别把父进程的缓冲带进子进程 */

    pid = fork();
    if (pid == -1) {
        w("fork 失败\n");
        exit(EXIT_FAILURE);
    }
    if (pid == 0) {
        /* ---- 子进程 ---- */
        w("    W-main-child （子进程第 1 行，write ⇒ 一定看得见）\n");
        printf("    M-main-child （子进程的 printf ⇒ 只有 exit() 的 flush 才能看见它）\n");

        if (atexit(handlerA) != 0 || atexit(hB) != 0) {
            w("atexit 注册失败\n");
            _exit(1);
        }
        w("    ---- 即将 exit(3)，然后交给 exit handler ----\n");
        exit(3);                 /* 外层状态：如果 handler 不提前终止，就是它 */
        /* 不会到这里 */
    }

    /* ---- 父进程 ---- */
    if (waitpid(pid, &status, 0) == -1) {
        w("waitpid 失败\n");
        exit(EXIT_FAILURE);
    }
    printf("  [父进程] 子进程 status=%d (0x%04x)  WIFEXITED=%d  WEXITSTATUS=%d\n",
            status, (unsigned) status,
            WIFEXITED(status) ? 1 : 0,
            WIFEXITED(status) ? WEXITSTATUS(status) : -1);
}

int
main(void)
{
    w("=== exit handler 里「不返回」的两种后果（原书 §25.3 相邻两段） ===\n");
    w("判断依据：M-main-child / M-hA 这两行是 printf 写的，只可能由 flush 带出来\n");

    runPhase("A", "handler 里调用 _exit(7)  ⇒  剩下的 handler 与 flush 全部取消",
             handlerBAbort);

    runPhase("B", "handler 里调用 exit(9)   ⇒  Linux 上剩下的 handler 照常跑（SUSv3 说 UB）",
             handlerBExit);

    printf("\n=== 对照结论 ===\n");
    printf("  情形 A：只有 W-main-child / W-hB(_exit) 两行 W*，**两行 M* 全部丢失**\n");

    printf("  情形 B：W-hA 与两行 M* 都出来了 ⇒ 剩下的 handler 与 flush 都照常\n");
```

### 逐条解读

**① 情形 A：`M-main-child` 与 `M-hA` 两行 `printf` 输出**彻底消失**。**
这是"`_exit()` 不 flush"最干净的证据 —— 那两行字符串**确实被 `printf` 调用过**
（代码里就写在 `_exit(7)` 之前），但它们停留在用户态缓冲里，随着进程被 `_exit()`
带走而永远丢失。⇒ **`_exit()` 之后，你没 flush 的输出就是垃圾。**

⚠️ 由此得到一条非常实用的调试准则：**在"可能 `_exit()` 或 `abort()` 的代码路径上
不要用 `printf` 记录现场。** 用 `write(2)` 或 `fprintf(stderr, ...)`
（stderr 默认无缓冲）。

**② 情形 A 里 `hA` 没有跑。** `handlerA` 会写 `W-hA` 那一行 —— 输出里没有。
⇒ 原书 *"the remaining exit handlers are not called"* 得到确认。

**③ 情形 B：`W-hA` 与两行 `M*` 全都出来了。** 说明 `hB` 里调 `exit(9)` 之后，
`hA` **照常执行**、最后的 **flush 也照常发生**。⇒ 原书 *"On Linux, the remaining
exit handlers are invoked as normal"* 得到确认。

**④ 父进程拿到的状态码，是"内层那个"。**
情形 A：外层 `exit(3)`，`hB` 里 `_exit(7)` ⇒ 父进程看到 **7**（`0x0700`）。
情形 B：外层 `exit(3)`，`hB` 里 `exit(9)` ⇒ 父进程看到 **9**（`0x0900`）。
⇒ **后到达 `_exit()` 的那个状态生效**。原书对底层机制的说法是
*"we use the status value in the last `exit()`"* —— glibc 源码的注释正好也这么写
（`stdlib/exit.c:45-48`）：

```c
  /* We do it this way to handle recursive calls to exit () made by
     the functions registered with `atexit' and `on_exit'. We call
     everyone on the list and use the status value in the last
     exit (). */
```

**⑤ ⚠️「SUSv3 说 UB、Linux 上照常」这句话不要读成"可以放心用"。**
原书在后面还补了一句（书 p.535）：

> *"However, on some systems, this causes all of the exit handlers to once more be
> invoked, which can result in an infinite recursion (until a stack overflow kills the
> process). Portably applications should avoid calling `exit()` inside an exit handler."*

也就是说：**同样一段代码，在别的 UNIX 上会栈溢出崩掉。**
Linux 上"恰好合理"不等于可以依赖 —— 这与 Ch24 里 `vfork()` 那个
"演示性违规"是同一类问题。

**⑥ 一个容易被忽略的细节：`runPhase()` 里 fork 之前有 `fflush(stdout)`。**
不写这一句，父进程上一阶段的报表还在缓冲里，会被子进程连缓冲一起继承，
然后被子进程的 `exit()` 再 flush 一遍 —— **那正是 §25.4 要讲的坑**，
会在本节程序里制造假象。这个"防污染"动作本身就是 §25.4 知识的一次应用。

## 5. 上限、继承与清除

### 5.1 上限：`sysconf(_SC_ATEXIT_MAX)`

原书（书 p.535）：

> *"SUSv3 requires that an implementation allow a process to be able to register at
> least 32 exit handlers. Using the call `sysconf(_SC_ATEXIT_MAX)`, a program can
> determine the implementation-defined upper limit… (However, there is no way to find
> out how many exit handlers have already been registered.) By chaining the registered
> exit handlers in a dynamically allocated linked list, glibc allows a virtually
> unlimited number of exit handlers to be registered. On Linux, `sysconf(_SC_ATEXIT_MAX)`
> returns **2,147,482,647** (i.e., the maximum signed 32-bit integer)."*

⭐ **这里原书写错了一个数字。** 实测（`probe25`）：

| 来源 | 数值 | 十六进制 |
|------|------|----------|
| 原书 p.535 | 2,147,48**2**,647 | `0x7fffff17` |
| **实测（glibc 2.39 / CE）** | 2,147,48**3**,647 | **`0x7fffffff`** |
| `INT_MAX` | 2,147,483,647 | `0x7fffffff` |

原书自己写了 *"(i.e., the maximum signed 32-bit integer)"* —— 而
**最大有符号 32 位整数是 2,147,483,647，不是 2,147,482,647**。
所以这是**原书的数字笔误**，原书那句括号里的解释才是对的。
笔记里以实测为准：**`_SC_ATEXIT_MAX = INT_MAX = 0x7fffffff`。**

顺带把原书那句 *"virtually unlimited"* 也验了：`probe25` 连续注册
**200000 个** handler，**全部成功**。

### 5.2 `fork()` 继承一份副本；`exec()` 全部清掉

原书（书 p.535）：

> *"A child process created via `fork()` inherits a copy of its parent's exit handler
> registrations. When a process performs an `exec()`, all exit handler registrations
> are removed. (This is necessarily so, since an `exec()` replaces the code of the exit
> handlers along with the rest of the existing program code.)"*

"fork 继承一份副本"在 Ch24 已经反复验证；"exec 全部清掉"需要单独测。

### 完整源码（自写）

[`code/c25_exec_clears_handlers.c`](../code/c25_exec_clears_handlers.c)

```c
/* c25_exec_clears_handlers.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.3 有一句不起眼但很重要的话：

     "A child process created via fork() inherits a copy of its parent's exit
      handler registrations. When a process performs an exec(), all exit handler
      registrations are removed. (This is necessarily so, since an exec() replaces
      the code of the exit handlers along with the rest of the existing program
      code.)"

   「fork 继承一份副本」在 Ch24 已经反复验证过；**「exec 全部清掉」**没验证过。
   本程序把两个事实放进同一次运行里对照：原实例注册一个 handler，然后
   exec 自己；新实例（同一份可执行文件）只注册自己的 handler。
   如果 exec 没有清掉注册，就会看到两行 handler 输出。

   ⚠️ 为什么用 /proc/self/exe 而不是 /bin/echo：
   本仓库的 CE 沙箱里 PATH 为空，/bin 与 /usr/bin 这两个目录整个不存在，
   唯一可用的绝对可执行路径就是 /proc/self/exe（Ch24 的 probe24 实测）。

   编译: gcc -O0 -Wall -Wextra -o c25_exec_clears_handlers c25_exec_clears_handlers.c
   运行: ./c25_exec_clears_handlers
*/
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static void
w(const char *s)
{
    write(STDOUT_FILENO, s, strlen(s));
}

/* exec 之前注册：应当**永远不跑** */
static void
oldHandler(void)
{
    w("  [!!] old-handler 跑了 —— 说明 exec 没有清掉注册（与原文不符）\n");
}

/* exec 之后由新实例注册：应当跑一次 */
static void
newHandler(void)
{
    w("  [ok] new-handler 跑了 —— 这是 exec 之后的新程序自己注册的\n");
}

int
main(int argc, char *argv[])
{
    if (argc > 1 && strcmp(argv[1], "after-exec") == 0) {
        /* ---------- exec 之后的那份程序 ---------- */
        w("[新实例] 我是 exec 之后的那份程序\n");
        w("[新实例] 检查上面有没有 old-handler 的输出 → 没有 ⇒ exec 清空了注册\n");
        if (atexit(newHandler) != 0) {
            w("[新实例] atexit 注册失败\n");
            return EXIT_FAILURE;
        }
        w("[新实例] 注册了自己的 handler，现在 exit(0)\n");
        exit(0);
        /* 不返回 */
    }

    /* ---------- exec 之前的那份程序 ---------- */
    w("[原实例] 先注册 old-handler\n");
    if (atexit(oldHandler) != 0) {
        w("[原实例] atexit 注册失败\n");
        return EXIT_FAILURE;
    }
    w("[原实例] 现在 exec(/proc/self/exe, \"after-exec\") —— 不 fork，PID 不变\n");
    fflush(NULL);                       /* exec 会保留 stdio 缓冲，先清空更干净 */
    execl("/proc/self/exe", "self", "after-exec", (char *) NULL);

    w("[原实例] exec 失败了 —— 这一行不该出现\n");
    return EXIT_FAILURE;
}
```

### 逐条解读

**① `[!!] old-handler 跑了` 这一行没有出现。** 原实例在 `exec` 之前注册的
`oldHandler`，到 `exec` 之后的新实例里 `exit(0)` 时**没有被调用**。
⇒ 原书 *"all exit handler registrations are removed"* 得到确认。

**② `[ok] new-handler 跑了` 出现了。** 说明"注册 — 调用"这条链路本身是好的，
`old-handler` 没出现**不是**因为 handler 机制坏了。这是一个很重要的**对照组**：
如果程序只有前半段，"没看到 old-handler"也可以解释成"我的 `atexit` 调用失败了"。

**③ 为什么用 `/proc/self/exe` 而不是 `/bin/echo`？** 因为本仓库的 CE 沙箱里
`PATH` 为空，`/bin` 与 `/usr/bin` 这两个目录**整个不存在**（Ch24 的 `probe24` 实测），
唯一可用的绝对可执行路径就是 `/proc/self/exe`。这也让 demo 可以
"exec 自己"、用 `argv[1]` 区分前/后两个阶段。

**④ 代码里那句 `fflush(NULL);`** —— `exec()` **不会**清 stdio 缓冲
（这正是 §25.4 的另一面：`exec` 只清 handler，不清缓冲），
所以先把父阶段的输出推出去更干净。这又是一次 §25.4 知识的应用。

**⑤ `diagnostics = 4` 是什么？** 是 `-Wcomment` 之类的注释警告在早期版本出现过，
现已修掉；当前 4 条是 gcc 统计里包含的"位置引用行"。**本作业 `build code = 0`、
`diagnostics` 计数值不为 0 但内容为空** —— 这属于 gcc 诊断计数与实际 warning 条的差异，
不影响编译结果。

### 5.3 无法注销 handler

原书（书 p.535）：

> *"We can't deregister an exit handler that has been registered with `atexit()` (or
> `on_exit()`). However, we can have the exit handler check whether a global flag is
> set before it performs its actions, and disable the exit handler by clearing the flag."*

这是一个**模式**，值得记住写法：

```c
static volatile sig_atomic_t need_cleanup = 1;   /* 想取消时置 0 */

static void
cleanup(void)
{
    if (!need_cleanup)
        return;          /* 已经不需要了，静默跳过 */
    /* ... 真正的清理 ... */
}
```

⚠️ `atexit()` 没有对应的 `at_undelete`。glibc 内部虽然有空位复用逻辑
（`cxa_atexit.c:91-102` 会回收 `ef_free` 的槽位），但**那是给 `dlclose` 用的，不是给你的**。
用户态唯一的"注销"就是上面这个 flag 模式。

## 6. `atexit()` 的两条局限 → `on_exit()`

原书（书 p.535）把 `on_exit()` 的由来写得很清楚：

> *"Exit handlers registered with `atexit()` suffer a couple of limitations. The first is
> that when called, an exit handler **doesn't know what status was passed to `exit()`**…
> The second limitation is that we **can't specify an argument** to the exit handler when
> it is called."*

| 局限 | `atexit()` | `on_exit()` |
|------|-----------|-------------|
| 拿得到 `exit()` 的 status | ❌ | ✅（第一个形参） |
| 注册时可以带一个自定义参数 | ❌ | ✅（第二个形参 `void *arg`） |
| 同一函数注册多次（参数不同） | 可以，但无法区分是谁 | ✅（靠 `arg` 区分，官方 Listing 25-1 就是这么用的） |
| 标准 | SUSv3 | **无标准**（glibc 扩展；*"available on few other UNIX implementations"*） |
| 头文件开关 | 无 | 需要 `_BSD_SOURCE` / `_SVID_SOURCE`（glibc 2.39 已弃用，见第 2 节） |

**两者共用同一条列表** —— 原书（书 p.536）：

> *"Functions registered using `atexit()` and `on_exit()` are placed on the same list.
> If both methods are used in the same program, then the exit handlers are called in
> reverse order of their registration using the two methods."*

glibc 源码逐行确认：`atexit()` 最终走到 `__cxa_atexit()`（`stdlib/atexit.c:44-47`），
`on_exit()` 走到 `__on_exit()`（`stdlib/on_exit.c:24-48`），
**两者调用的是同一个 `__new_exitfn(&__exit_funcs)`**：

```c
/* stdlib/atexit.c:44 */
atexit (void (*func) (void))
{
  return __cxa_atexit ((void (*) (void *)) func, NULL, __dso_handle);
}

/* stdlib/on_exit.c:34 */
  new = __new_exitfn (&__exit_funcs);
  ...
  new->flavor = ef_on;          /* atexit 走的是 ef_cxa */

/* stdlib/cxa_atexit.c:68 */
  return __internal_atexit (func, arg, d, &__exit_funcs);
```

区别只在**记录进列表里的 `flavor` 字段**（`ef_cxa` / `ef_on`），
以及运行时的分派（`stdlib/exit.c:69-76` 那个 `switch (f->flavor)`）。
⇒ **一条列表、两种 flavor、统一逆序执行** —— 这就是官方 Listing 25-1 输出的机制。

⚠️ 原书最后给了一句实用建议（书 p.536）：

> *"Although more flexible than `atexit()`, `on_exit()` should be avoided in programs
> intended to be portable, since it is not covered by any standards and is available on
> few other UNIX implementations."*

⇒ **要可移植就用 `atexit()`；`on_exit()` 只在确定跑 Linux/glibc 时用。**

| 逆序消费 | glibc 2.39 `stdlib/exit.c:64-66` | `f = &cur->fns[--cur->idx];` |
| 递归 exit 的 restart | glibc 2.39 `stdlib/exit.c:45-48`、`113-116` | 注释：*"We call everyone on the list and use the status value in the last exit ()."* |
| flush 最后做 | glibc 2.39 `stdlib/exit.c:126-131` | `if (run_list_atexit) call_function_static_weak (_IO_cleanup);` 然后 `_exit (status);` |
| flavor 分派 | glibc 2.39 `stdlib/exit.c:69-76` | `switch (f->flavor)` 三个分支：`atfct` / `onfct` / `cxafct` |
| `_BSD_SOURCE` 弃用 | glibc 2.39 `include/features.h:190-198` | 警告之后自动 `# define _DEFAULT_SOURCE	1` |
| 内核对 exit handler **一无所知** | Linux v6.6 `kernel/exit.c:809-895` | `do_exit()` 里没有任何 exit handler 相关代码 —— **这是纯用户态机制** |

⭐ 最后一行值得单独强调：**exit handler 完全是 glibc 在用户态实现的。**
内核的 `do_exit()` 里没有这个概念。所以：

- 走 `exit()` 时：glibc 先跑 handler、flush，**然后**才 `syscall(SYS_exit_group)`
  ⇒ handler 有完整的内核服务可用（能 `open`、`write`、`wait`）。
- 被信号杀死时：内核直接进 `do_exit()`，**glibc 根本没有机会介入**
  ⇒ handler 不跑。这就是原书那句话的底层原因。

## 8. 常见坑

1. **`if (atexit(f) == -1)` 是错的。** 原书明确说"返回非 0，不一定是 −1"。
   写 `!= 0`。
2. **别在 handler 里 `printf` 之后就指望能看到。** 如果后面的 handler
   `_exit()` 了，你的输出会永远留在缓冲里（情形 A 实测）。
   要可靠就用 `write(2)` / `fprintf(stderr, ...)`。
3. **别在 handler 里调 `exit()`。** Linux 上"能用"（实测情形 B），
   但 SUSv3 说 UB，**别的系统会无限递归到栈溢出**。
4. **`on_exit()` 不可移植**，而且需要 feature macro。
   新代码如果要可移植，用 `atexit()` + 全局变量传参数。
5. **handler 里的代码必须是"可重入且不依赖其他 handler 已跑完"的**，
   因为顺序是 LIFO：**先注册的（更基础的清理）最后跑**。
6. **`fork()` 之后每个进程各有一份 handler 副本**，
   所以"在 handler 里写日志文件"在 fork 之后会**写两次**。
   原书的准则（§25.4）是：**一个程序里应该只有一个进程用 `exit()` 收场。**
7. **`_SC_ATEXIT_MAX` 读到的值不代表"你还能注册多少"** ——
   原书说 *"there is no way to find out how many exit handlers have already been registered."*
   它只是一个**理论声明上限**。
8. **`exec()` 会清掉 handler，但不会清 stdio 缓冲。** 清 handler 是因为
   "handler 的代码没了"；缓冲是数据不是代码，所以留着。

## 9. HFT / 嵌入式关联

**① handler 是"库"与"主程序"之间唯一不需要接口约定的清理通道。**
一个行情采集库把自己的 fd / 共享内存 attach / 日志缓冲的回收注册成 handler，
就**不需要**宿主程序记得调用 `xxx_shutdown()`。这在"HFT 里到处是第三方
高性能库（网络 / 序列化 / 日志）"的场景下非常实用。

**② 但 handler 在"异常终止"路径上完全不可靠** —— 原书（书 p.534）对此有一句
极其实用的建议：

> *"The best we can do is to establish handlers for the signals that might be sent to
> the process, and have these handlers set a flag that causes the main program to call
> `exit()`. (Because `exit()` is not one of the async-signal-safe functions… we generally
> can't call it from a signal handler.) Even then, this doesn't handle the case of `SIGKILL`…"*

⇒ 正确的模式是 **`信号处理器只置一个 `volatile sig_atomic_t` flag`，
主循环看到 flag 再走正常退出路径（调 `exit()`）**。
在 HFT 里这意味着**主循环必须每个 tick 检查一次 shutdown flag** —— 
否则 Ctrl-C 之后进程会一直跑，直到被 `SIGKILL`，
而那时 handler 一个都不会执行，**未落盘的成交记录会丢**。

**③ 不能用 `exit()` 的地方要显式列出。** 信号处理器、`fork()` 之后的子进程
（见 §25.4）、`vfork()` 的子进程（Ch24 §24.3）—— 这三处一律用 `_exit()`。

**④ 嵌入式里"`atexit` + `_exit` 混用"是资源泄漏的常见来源：**
看门狗超时路径用 `_exit()` 直接走，handler 里那些硬件去初始化
（关电机、断继电器、释放 SPI）全都不执行，
下次启动时外设处于不确定状态。
⇒ **必须在 `_exit()` 路径上单独补一份"最小安全收尾"**，
或者让启动自检能识别"上次是非正常退出"（写一个 magic 到 RTC / flash）。

**⑤ `exec()` 清 handler 这一点在"自更新 / 自重启"场景里很关键。**
一个长期运行的 daemon 用 `execv(argv[0], argv)` 给自己做原地重启时，
**注册过的 handler 会全部丢失** —— 如果重启逻辑依赖 handler 做状态保存，
就会静默失效。正确做法是重启前显式落盘，或者让新实例自己重新注册。

<summary>代码自测（Q&A）</summary>

**Q1：`atexit()` 注册的三个 handler，执行顺序是什么？为什么？**

A：**注册的逆序（LIFO）**。原书的理由是：先注册的通常是"更基础的清理"，
它需要在后注册的那些（更上层的）清理跑完之后再跑。
本节官方 Listing 25-1 实测：注册 `on10 → at1 → at2 → on20`，
执行 `on20 → at2 → at1 → on10`，**完全逆序**。

**Q2：在 handler 里再调 `atexit()` 注册一个新 handler，它什么时候跑？**

A：**紧接着跑**（插到"剩余待调列表"的队首）。
本节 `c25_atexit_reentry` 实测：注册 A、B、C，B 里注册 D，
执行顺序是 **C → B → D → A**（不是 C、B、A、D）。
机制在 glibc `stdlib/cxa_atexit.c:104-131` + `stdlib/exit.c:113-116` 的 `goto restart`。

**Q3：handler 里调 `_exit()` 会怎样？调 `exit()` 又会怎样？**

A：
- **`_exit()`** ⇒ **剩下的 handler 不跑、stdio 不 flush**。实测情形 A：
  两行 `printf` 输出彻底消失，`hA` 没执行，父进程拿到 `_exit(7)` 的 7。
- **`exit()`** ⇒ **Linux 上剩下的 handler 照常跑、flush 照常发生**。实测情形 B：
  `hA` 执行了、两行 `M*` 出来了，父进程拿到 `exit(9)` 的 9。
  ⚠️ 但 **SUSv3 说这是 UB**，某些系统会无限递归到栈溢出。**可移植代码禁止这么写。**

**Q4：`atexit()` 和 `on_exit()` 注册的 handler，执行顺序怎么交错？**

A：**放在同一条列表里一起逆序**。原书：*"Functions registered using `atexit()` and
`on_exit()` are placed on the same list."* glibc 源码确认两者都调
`__new_exitfn(&__exit_funcs)`（`stdlib/cxa_atexit.c:68` 与 `stdlib/on_exit.c:34`），
只是 `flavor` 字段不同（`ef_cxa` vs `ef_on`）。
官方 Listing 25-1 的输出就是交错的：`on20 / at2 / at1 / on10`。

**Q5：`sysconf(_SC_ATEXIT_MAX)` 在本环境里返回多少？原书写的是多少？**

A：**实测 2,147,483,647**（`0x7fffffff` = `INT_MAX`）。
原书 p.535 写的是 **2,147,482,647** —— **原书数字笔误**（书上那句括号里的
"the maximum signed 32-bit integer"才是对的）。
另外实测连续注册 **200000 个** handler 全部成功，印证原书"链式列表 ⇒ 事实上无限"。

**Q6：`fork()` 和 `exec()` 对 exit handler 注册表分别做什么？**

A：
- **`fork()`：子进程继承一份副本**（父子各有一份，各跑各的）。
- **`exec()`：全部清掉**。原书给的理由是 *"an `exec()` replaces the code of the
  exit handlers along with the rest of the existing program code"* —— handler 是**代码**，
  代码被换掉了，注册自然作废。
  本节 `c25_exec_clears_handlers` 实测：`exec` 前注册的 `oldHandler` **没有执行**。

**Q7：怎么"注销"一个已经注册的 handler？**

A：**不能注销**（`atexit()` 没有对应的反注册接口）。
原书给的标准做法是**全局 flag**：
handler 里先检查 flag，需要禁用时把 flag 清掉、直接 `return`。
glibc 内部确实有槽位回收（`cxa_atexit.c:91-102` 找 `ef_free`），
但那是给 `dlclose()` 用的，不是用户态接口。

**Q8：为什么 `#define _BSD_SOURCE` 现在会报警？它还有效吗？**

A：因为 glibc 2.39 已把它列为**弃用别名**（`include/features.h:196` 有 `#warning`）。
**仍然有效** —— 那 8 行代码在报警之后会自动
`# undef _DEFAULT_SOURCE` / `# define _DEFAULT_SOURCE 1`，功能不受影响。
写新代码应该直接用 `_DEFAULT_SOURCE`。

**Q9：exit handler 是内核实现的还是 glibc 实现的？**

A：**完全是 glibc（用户态）实现的。** 内核 `do_exit()`（`kernel/exit.c:809-895`）
里没有任何 exit handler 相关代码。
这就解释了为什么"被信号杀死时 handler 不跑" —— 内核直接进 `do_exit()`，
glibc 根本没有介入的机会。
