## 本节讲什么

§25.1 讲的是「进程怎么结束」，§25.2 讲的是「结束的瞬间，内核和库**替你做了什么**」。

这一节在原书里只有 **533 页的一页半**，全是清单，没有任何代码、没有任何 Listing、
也没有一句「为什么」。但它是**整章最容易吃亏的一节**——因为清单上的每一行，
都对应一个「不写清理代码也不会泄漏」的保证，而**这些保证是有边界的**：

- 有些资源是**内核**替你放的（关 fd、解 map、detach shm）；
- 有些是**库**替你放的（`exit()` 里的 stdio flush）；
- 还有些**只有你自己做**才行（比如把数据落盘）。

⚠️ **原书 §25.2 没有 Listing，也没有配套程序。**
本节用 CE 沙箱的探针实测 + Linux v6.6 `kernel/exit.c` 的逐行坐标，
把这份清单**逐条对到内核代码上**——这样你就知道哪些是「保证」，哪些只是「约定」。

## 1. 原书清单（10 条）与它们在代码里的位置

原书把进程终止时被清理的东西列成 10 条。下表把每一条对到**内核 v6.6 的具体调用**：

| # | 原书说的资源 | 内核/库里的现场 | 备注 |
|---|-------------|---------------|------|
| 1 | 关闭所有文件描述符、目录流、消息目录描述符、转换描述符 | `exit_files(tsk)`（`kernel/exit.c:869`） | 每个 fd 的引用计数减一；**引用计数归零才真的关** |
| 2 | 释放该进程持有的**文件锁** | 同上（随 `struct file` 释放） | ⚠️ 见下面的「经典陷阱」 |
| 3 | detach System V 共享内存段（`shm_nattch` 减一） | `exit_shm(tsk)`（`kernel/exit.c:868`） | 段本身**不删**，只 detach |
| 4 | 把 `semadj` 加回 System V 信号量 | `exit_sem(tsk)`（`kernel/exit.c:867`） | 这就是 `SEM_UNDO` 的实现点 |
| 5 | 若是控制终端的 controlling process ⇒ 向前台进程组发 `SIGHUP` + 解除会话关联 | `disassociate_ctty(1)`（`kernel/exit.c:871`，仅 `group_dead` 时） | ⚠️ 只对**会话首进程**生效 |
| 6 | 关闭 POSIX 命名信号量（`sem_close()` 那类） | 随 fd 关闭（`/dev/shm/sem.*` 就是 fd） | 名字还在，`sem_unlink()` 才删 |
| 7 | 关闭 POSIX 消息队列（`mq_close()` 那类） | 同上（`mqueue` 也是 fd） | 同上，`mq_unlink()` 才删 |
| 8 | 若进程组因此变孤儿、且组内有**停止的**进程 ⇒ 发 `SIGHUP` 再发 `SIGCONT` | `kill_orphaned_pgrp()`（`kernel/exit.c:737`） | 这是 job control 的兜底 |
| 9 | 移除 `mlock()` / `mlockall()` 加的内存锁 | `exit_mm()` 里随 mm 释放 | 锁是进程私有的 |
| 10 | unmap `mmap()` 建立的映射 | `exit_mm()`（`kernel/exit.c:862`） | 私有映射直接丢；共享映射只减引用 |

⭐ 把这 10 条按「谁负责」重新分组，比按原书顺序背更有用：

| 负责方 | 条目 | 可靠性 |
|-------|------|-------|
| **内核无条件做** | 1–5、8–10 | ✅ 不写代码也保证 |
| **库在 `exit()` 里做** | stdio flush（§25.1 第②步） | ⚠️ 走 `_exit()` 或被杀就**不做** |
| **必须你自己做** | 数据落盘、`shmctl(IPC_RMID)`、`sem_unlink()`、`mq_unlink()`、优雅通知对端 | ❌ 内核不管 |

⚠️ **第 3/6/7 条最容易被误读**：内核只做「detach / close」，**不做「删除」**。
System V 共享内存段、POSIX 信号量名、POSIX 消息队列名都是**持久化对象**，
进程死了它们还在（直到 reboot 或有人 `*_RMID`/`*_unlink`）。§25.2 的清单说的是
「解除本进程的关联」，不是「清理掉这个对象」。

## 2. 一个经典的「清单陷阱」：文件锁

`fcntl()` 的**记录锁**（`F_SETLK` 那套）的语义是：

> 锁由**进程**持有；进程一终止，内核**立刻**释放它。

这和「关闭 fd 会释放锁」是两个**独立**的触发条件（POSIX 的记录锁规则）。
所以原书第 2 条说的是「进程终止 ⇒ 锁没了」。

⚠️ 由此有一个很常见的 HFT / 嵌入式事故模式：

| 场景 | 后果 |
|------|------|
| A 进程对文件加记录锁，然后 fork 出 B（B 不开这个文件） | B 里**看不到**这把锁（锁属于 A） |
| A 进程一 `exit()`/被杀 | 锁**立刻**释放，哪怕 B 还在写这个文件 |
| 运维以为「锁能保护到我修完数据」 | ❌ 锁在 A 死的瞬间就没了 |

**正解**：跨进程互斥用 `flock()`（也由 fd 持有）+ 明确的 `open`/`close` 生命周期管理，
或者干脆用 `fcntl` 的 `F_OFD_SETLK`（Linux 3.15+，**open file description 锁**，
生命周期绑在 fd 上而不是进程上）。

## 3. 内核里的完整清理序列（v6.6 `kernel/exit.c` `do_exit()`）

把 `do_exit()` 后半段的清理动作按顺序抄下来（这是 §25.2 清单的**原始现场**）：

```c
/* kernel/exit.c:866-875（节选，逐字） */
	exit_sem(tsk);
	exit_shm(tsk);
	exit_files(tsk);
	exit_fs(tsk);
	if (group_dead)
		disassociate_ctty(1);
	exit_task_namespaces(tsk);
	exit_task_work(tsk);
	exit_thread(tsk);
```

| 行 | 调用 | 对应原书第几条 |
|----|------|--------------|
| 867 | `exit_sem(tsk)` | 第 4 条（`semadj` 加回） |
| 868 | `exit_shm(tsk)` | 第 3 条（detach shm，`shm_nattch` 减一） |
| 869 | `exit_files(tsk)` | 第 1、2、6、7 条（fd 类全部） |
| 870 | `exit_fs(tsk)` | 第 1 条里的**目录流**（`fs_struct`） |
| 871 | `disassociate_ctty(1)` | 第 5 条（控制终端 + `SIGHUP`） |

⭐ 注意 `if (group_dead)` 这个条件：**只有线程组里最后一个线程退出时**
才做「解除控制终端」这种影响整个会话的动作。`group_dead` 来自
`atomic_dec_and_test(&tsk->signal->live)`（`kernel/exit.c:843`）。

然后是**僵尸的诞生与消亡**：

```c
/* kernel/exit.c:727-755（节选，逐字） */
static void exit_notify(struct task_struct *tsk, int group_dead)
{
	...
	forget_original_parent(tsk, &dead);

	if (group_dead)
		kill_orphaned_pgrp(tsk->group_leader, NULL);

	tsk->exit_state = EXIT_ZOMBIE;
	if (unlikely(tsk->ptrace)) {
		...
		autoreap = do_notify_parent(tsk, sig);
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&
			do_notify_parent(tsk, tsk->exit_signal);
	} else {
		autoreap = true;
	}

	if (autoreap) {
		tsk->exit_state = EXIT_DEAD;
		list_add(&tsk->ptrace_entry, &dead);
	}
	...
}
```

| 坐标 | 内容 | 教学含义 |
|------|------|---------|
| `kernel/exit.c:737` | `kill_orphaned_pgrp(tsk->group_leader, NULL);` | 原书第 8 条（孤儿进程组 + 停止进程 ⇒ `SIGHUP` + `SIGCONT`） |
| `kernel/exit.c:739` | `tsk->exit_state = EXIT_ZOMBIE;` | ⭐ **僵尸态的诞生点**——进程已经不跑了，但 `task_struct` 还留着，等父进程 `wait()` |
| `kernel/exit.c:748` | `do_notify_parent(tsk, tsk->exit_signal);` | 给父进程发 `SIGCHLD` |
| `kernel/exit.c:754` | `tsk->exit_state = EXIT_DEAD;` | `autoreap` 时直接进「可回收」 |
| `kernel/exit.c:239` | `void release_task(struct task_struct *p)` | 真正把 `task_struct` 还回去（父进程 `wait()` 之后走这里） |

⚠️ 这就是 §25.1 和 Ch26 之间的接缝：**`exit_notify()` 把进程变成僵尸，
但把它彻底回收的是父进程的 `wait()`**。本章只负责「变成僵尸」这一半。

## 4. 沙箱实测：探针能问出来的那部分

原书清单里的多数条目要靠 System V IPC 或会话/终端才能观察，
而 CE 沙箱里**没有终端**、也未必允许 IPC。所以本节用一个探针把**能问的都问一遍**，
剩下的老实留给内核源码坐标。

[`code/probe25.c`](../code/probe25.c)

```c
/* probe25.c

   ⚠️ 本仓库自写 —— 探针，**不属于原书内容**。

   每开一章先建它：把笔记里要引用的「CE 沙箱事实」一次性问清楚，
   免得在笔记里写「本机观察到 …」的时候其实是凭空想象。

   本章（Ch25 Process Termination）要问的：

     ① sysconf(_SC_ATEXIT_MAX) —— 原书 25.3 明确点名了这个数字，
        并断言 glibc 用链表实现 ⇒ 上限是「有符号 32 位整数最大值」。
     ② 真的连续注册 20 万个 exit handler 会不会失败（验证 ① 的说法）。
     ③ stdout 到底是不是 socket —— Ch13 已经确认过，本章 §25.4 全靠它：
        只有「stdout 不是终端」时，Listing 25-2 那个重复输出的现象才出得来。
     ④ glibc 版本、EXIT_SUCCESS / EXIT_FAILURE 的实际取值。
     ⑤ 本章要引用的几个 rlimit 与 PID namespace 事实（与 Ch24 同源，复核一次）。

   编译: gcc -O0 -Wall -Wextra -o probe25 probe25.c
   运行: ./probe25
*/
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/stat.h>
#include <unistd.h>

#include <gnu/libc-version.h>    /* gnu_get_libc_version() */

#define N_HANDLERS 200000

static void nothing(void)
{
    /* 空的 exit handler：本节只想撞出「注册上限」，不想刷屏 */
}

int
main(int argc, char *argv[])
{
    struct stat st;
    struct rlimit rl;
    long v;

    /* 用 setvbuf 关缓冲：后面每行 println 都要能被单独看到，
       否则全缓冲下报错信息会和别的输出挤在一起看不清。 */
    setvbuf(stdout, NULL, _IONBF, 0);

    printf("[进程] getpid()  = %ld   getppid() = %ld\n",
            (long) getpid(), (long) getppid());

    printf("[libc] gnu_get_libc_version() = %s\n", gnu_get_libc_version());
    printf("[libc] __GLIBC__ = %d, __GLIBC_MINOR__ = %d\n",
            __GLIBC__, __GLIBC_MINOR__);

    printf("\n[①] sysconf(_SC_ATEXIT_MAX) —— 原书 25.3 点名的那个数字\n");
    v = sysconf(_SC_ATEXIT_MAX);
    if (v == -1)
        printf("  _SC_ATEXIT_MAX  = -1（不确定 / 无限）\n");
    else
        printf("  _SC_ATEXIT_MAX  = %ld  (0x%lx)\n", v, (unsigned long) v);
    printf("  对照：INT_MAX   = 2147483647 (0x7fffffff)\n");

    printf("\n[②] 真的连续注册 %d 个 exit handler（用空函数，不刷屏）\n",
            N_HANDLERS);
    {
        long i;
        int failed = -1;
        for (i = 0; i < N_HANDLERS; i++) {
            if (atexit(nothing) != 0) {   /* 原书：成功返回 0，失败返回非 0 */
                failed = (int) i;
                break;
            }
        }
        if (failed < 0)
            printf("  注册 %d 个：全部成功\n", N_HANDLERS);
        else
            printf("  注册到第 %d 个失败（errno=%d %s）\n",
                    failed, errno, strerror(errno));
        printf("  ⇒ 原书「glibc 用链式列表 ⇒ 实际上撞不到上限」得到印证\n");
        /* 用 _exit() 收场：跳过后面的 handler 与 stdio flush，省时间 */
    }

    printf("\n[③] stdout 是什么（本章 §25.4 的前提）\n");
    if (fstat(STDOUT_FILENO, &st) == -1) {
        printf("  fstat(1) 失败: %s\n", strerror(errno));
    } else {
        printf("  S_ISREG  = %d   S_ISCHR = %d   S_ISFIFO = %d   S_ISSOCK = %d\n",
                S_ISREG(st.st_mode) ? 1 : 0,
                S_ISCHR(st.st_mode) ? 1 : 0,
                S_ISFIFO(st.st_mode) ? 1 : 0,
                S_ISSOCK(st.st_mode) ? 1 : 0);
        printf("  isatty(1) = %d\n", isatty(STDOUT_FILENO));
        printf("  ⇒ 不是终端 ⇒ glibc 对 stdout 用【全缓冲】(BUFSIZ=%d)\n",
                BUFSIZ);
        printf("  ⇒ 原书 Listing 25-2 在 CE 上直接表现为「重定向到文件」那一半\n");
    }

    printf("\n[④] EXIT_SUCCESS / EXIT_FAILURE\n");
    printf("  EXIT_SUCCESS = %d\n", EXIT_SUCCESS);
    printf("  EXIT_FAILURE = %d\n", EXIT_FAILURE);

    printf("\n[⑤] 几个 rlimit（与 Ch24 同源，复核一次）\n");
    if (getrlimit(RLIMIT_CORE, &rl) == 0)
        printf("  RLIMIT_CORE   soft=%llu hard=%llu\n",
                (unsigned long long) rl.rlim_cur,
                (unsigned long long) rl.rlim_max);
    if (getrlimit(RLIMIT_NOFILE, &rl) == 0)
        printf("  RLIMIT_NOFILE soft=%llu hard=%llu\n",
                (unsigned long long) rl.rlim_cur,
                (unsigned long long) rl.rlim_max);
    printf("  _SC_OPEN_MAX  = %ld\n", sysconf(_SC_OPEN_MAX));
    printf("  _SC_CHILD_MAX = %ld\n", sysconf(_SC_CHILD_MAX));
    printf("  _SC_NPROCESSORS_ONLN = %ld\n", sysconf(_SC_NPROCESSORS_ONLN));

    printf("\n[⑥] 本进程读到的 PATH 与 argv[0]\n");
    printf("  getenv(\"PATH\") = %s\n",
            getenv("PATH") ? getenv("PATH") : "(NULL)");
    if (argc > 0)
        printf("  argv[0]        = %s\n", argv[0]);

    _exit(0);   /* 跳过后台那 20 万个空 handler */
}
```

### 逐条解读（只挑与本节有关的几段）

| 段 | 实测 | 与 §25.2 的关系 |
|----|------|---------------|
| `[③]` | `S_ISREG=0` `S_ISCHR=0` `S_ISFIFO=0` **`S_ISSOCK=1`**，`isatty(1)=0` | 沙箱的 stdout 是 **socket**。这决定了 §25.4 那个「重复输出」现象在 CE 上**必然**出现（全缓冲）——不是配置问题，是环境事实 |
| `[⑤]` | `RLIMIT_NOFILE soft=100 hard=100`、`_SC_OPEN_MAX=100` | 沙箱最多 100 个 fd ⇒ §25.2 第 1 条「关闭所有 fd」在 CE 上最多涉及 100 个 |
| `[⑤]` | `_SC_CHILD_MAX = 27191` | ⚠️ **这个数字会漂**：同一章 Ch24 那次跑出来是 **54956**（CE 会换宿主机）。引用时必须带「沙箱」二字 |
| `[⑥]` | `getenv("PATH") =`（空） | 沙箱没有 `PATH` ⇒ 任何依赖 `execlp` / `system()` 的清理动作在 CE 上都会 `ENOENT` |
| `[⑥]` | `argv[0] = ./output.s` | CE 把源码编译产物固定命名为 `output.s` |

⚠️ `[②]` 那一段（连续注册 20 万个 exit handler）是给 §25.3 用的，本节不解释。

⭐ 为什么探针最后用 `_exit(0)` 收场（`probe25.c:122`）？
因为 `[②]` 已经注册了 **20 万个**空 handler——如果走 `exit()`，
glibc 要把这 20 万个函数跑一遍，白白浪费时间。这本身就是对 §25.1「三步」的一个实用注解：
**`_exit()` 的用途之一就是「我不想跑那些 handler」**。

## 5. 常见坑

| # | 坑 | 后果 | 正解 |
|---|----|------|------|
| 1 | 以为进程死了 System V 共享内存段就没了 | 段还在，`ipcs -m` 里看得见 | 显式 `shmctl(shmid, IPC_RMID, NULL)` |
| 2 | 以为进程死了 POSIX 信号量/消息队列就没了 | 名字还在（持久化对象） | 显式 `sem_unlink()` / `mq_unlink()` |
| 3 | 靠 `fcntl` 记录锁做跨进程互斥，对端进程一死就以为锁还在 | 锁随进程消失 | 用 `F_OFD_SETLK`（绑 fd）或 `flock()` |
| 4 | 把「数据落盘」交给 `atexit` 兜底 | `SIGKILL` / OOM 时一条都不跑 | 持续落盘 + 启动时对账 |
| 5 | 在非会话首进程里指望 `disassociate_ctty` 生效 | 不会触发 | 只有 `group_dead` 时（最后一个线程）才走 |
| 6 | 缓存 `sysconf(_SC_CHILD_MAX)` 的值 | 换宿主机就变 | 运行时读，别写死 |

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **HFT** | 内核那 10 条是「保证」，但**落盘不是**。撮合/风控进程被 OOM killer 干掉时 `atexit` 不执行 ⇒ 状态机快照必须**周期性强刷**，退出时只做「补刷最后一次」。 |
| **HFT** | 热重启（fast restart）依赖「旧进程一死 fd/锁/共享内存立刻释放」这条保证。**但要注意**：`shm` 段不会自动删，重启脚本里必须显式 `IPC_RMID`，否则 `nattch` 残留会让新进程误判。 |
| **嵌入式** | `exit_files()` 关掉的不只是普通 fd，还包括 `epoll` / `eventfd` / `timerfd` / `signalfd` ⇒ 靠这些做事件循环的 daemon，退出时**不需要**手写 `close()` 循环。 |
| **嵌入式** | 第 5 条（控制终端 + `SIGHUP`）是「终端一关，daemon 跟着死」的机制来源。daemon 化（`setsid()` + 切到 `/`）就是为了**脱离**这个行为——原书 §37 会展开。 |
| **嵌入式** | 第 9 条（`mlock` 解除）意味着 `mlockall(MCL_CURRENT|MCL_FUTURE)` 的实时进程**退出后**内存锁自动没了，不需要显式 `munlock`。 |

## 代码自测

<details>
<summary>代码自测（Q&A）</summary>

**Q1：进程 `exit()` 之后，它创建的 System V 共享内存段会消失吗？**

**不会。** 内核做的是 `exit_shm(tsk)`（`kernel/exit.c:868`），即把该进程**detach**，
`shm_nattch` 减一。段本身是**持久化对象**，要等 `shmctl(shmid, IPC_RMID, NULL)`
或系统重启才消失。

同理，POSIX 命名信号量（`/dev/shm/sem.*`）与消息队列（`/dev/mqueue/*`）
只会被 `close`，名字要等 `sem_unlink()` / `mq_unlink()` 才没。


**Q2：为什么说「靠 `fcntl()` 记录锁做互斥，对端进程一死锁就没了」？**

POSIX 记录锁（`F_SETLK`）的持有者是**进程**。内核在进程终止时释放它——
这与「关闭 fd 会释放锁」是两个**独立**的触发条件。所以任何 `exit()`、`_exit()`，
甚至一个 `SIGSEGV`，都会**立刻**放锁，持有者根本没机会「先把数据写完」。

要绕开这一点，用 `F_OFD_SETLK`（Linux 3.15+）：锁绑在 **open file description** 上，
生命周期跟 fd 走，可以跨进程传递，也不会因为某个进程退出而神秘消失。


**Q3：`disassociate_ctty(1)` 为什么包在 `if (group_dead)` 里？**

因为它做的是**会话级**动作（解除控制终端、给前台进程组发 `SIGHUP`），
只能由「线程组的最后一个线程」来做。

`group_dead` 来自 `atomic_dec_and_test(&tsk->signal->live)`（`kernel/exit.c:843`）——
只有 `live` 减到 0 才为真。如果每个线程退出都去解除控制终端，多线程程序会被反复踢出会话。


**Q4：本节探针里 `_SC_CHILD_MAX` 是 27191，为什么不能在别处直接引用这个数？**

因为它是**沙箱宿主机的属性**，不是内核常量。CE 会换宿主机，
同一章在 Ch24 那轮跑出来是 **54956**，本轮是 **27191**。

这一类数字（`_SC_CHILD_MAX`、`uptime`、`loads`、`procs`、`totalram`）都是「会漂」的，
引用时必须写明「某次实测的沙箱值」，不能当成常量写进结论。
「N 百万次平均」这类统计量才相对稳定。


**Q5：为什么 `probe25.c` 最后用 `_exit(0)` 而不是 `exit(0)`？**

因为它在 `[②]` 里连续注册了 **200000** 个空 exit handler。如果走 `exit(0)`，
glibc 会把这两万个注册项**逐个调用**（`__run_exit_handlers` 的 `while` 循环），
白白消耗时间。

这正好是 `_exit()` 的典型使用场景之一：**「我不想跑 handler，我要立刻消失」**。
同一个道理也适用于「fork 出来的子进程」——见 §25.4。

</details>
