## 题目原文（书 p.539）

原书 §25.6 的**全部内容**就是这一题：

> ***"25-1.** If a child process makes the call `exit(–1)`, what exit status (as returned
> by `WEXITSTATUS()`) will be seen by the parent?"*

⚠️ 两个值得注意的细节：

2. **原书没有给答案。** TLPI 的习题解答是单独一本（*The Linux Programming Interface:
   Exercise Solutions*），本节用的 `ex25_1_exit_minus_one.c` 是**本仓库自写**的。

## 答案

> ### **255**

不是 −1，不是 65535，也不是 256。

**为什么：** 原书 §25.1（书 p.532）已经给了规则 ——
*"only the lowest 8 bits of the status are made available to the parent process."*
`−1` 的二进制是全 1，取低 8 位得 `0xFF = 255`。

但**光知道"低 8 位"还不够**，因为你会立刻遇到第二个疑问：
**父进程 `wait()` 拿到的那个数，为什么是 65280 而不是 255？**
这就必须把 `wait status` 的**编码**搞清楚 —— 见下面第 3 节。

## 1. 一次把 16 个边界值全测掉

题目只问 `−1`，但"低 8 位"这条规则的边界分布在
`0 / 127 / 128 / 255 / 256 / 257 / 300 / 511` 这些点上，
而且**负数和被信号杀死**这两类容易被混为一谈。
所以本程序把一整排值都跑一遍。

### 完整源码（自写）

[`code/ex25_1_exit_minus_one.c`](../code/ex25_1_exit_minus_one.c)

```c
/* ex25_1_exit_minus_one.c

   ⚠️ 本仓库自写 —— 习题 25-1 的解，**原书没有给这一题的答案**。

   题目原文（书 p.539 §25.6 Exercise）：
     "25-1. If a child process makes the call exit(-1), what exit status
      (as returned by WEXITSTATUS()) will be seen by the parent?"

   答案：**255**。

   为什么不是 -1 也不是 65535：
     · exit(status) 的形参是 int，但原书 §25.1 明说
       "only the bottom 8 bits of status are actually made available to
        the parent"；
     · 截断发生在**系统调用入口**，不在父进程取状态的时候 ——
       Linux v6.6 kernel/exit.c:989-992（exit）与 1033-1035（exit_group）
       都是 `do_exit((error_code & 0xff) << 8)`：先取低 8 位，再左移 8 位
       换成「wait status」编码（低字节留给信号号 / core 位）。
       glibc 的 _exit() 走的就是 exit_group。
     · 于是 -1 ⇒ (0xFFFFFFFF & 0xff) << 8 = 0xFF00 = 65280，
       而 WEXITSTATUS(65280) = 0xFF = 255。

   本程序不只回答 -1，而是把一整排值都跑一遍，让「低 8 位」这条规则的
   边界（127/128/255/256/257/300/511、负数、以及被信号杀死）都能被看见。

   编译: gcc -O0 -Wall -Wextra -o ex25_1_exit_minus_one ex25_1_exit_minus_one.c
   运行: ./ex25_1_exit_minus_one
*/
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

/* 故意跨过 0/127/128/255/256/257 这些边界，两侧都取值 */
static const int STATUSES[] = {
    -1, -2, -256, -1000,
    0, 1, 2, 127, 128, 255, 256, 257, 300, 511, 1000, 65535,
};
#define N_STATUS (sizeof(STATUSES) / sizeof(STATUSES[0]))

static void
showStatus(int st, int status)
{
    printf("  exit(%-6d)  内核记的 status = %-6d (0x%04x)   "
           "WIFEXITED=%d  WEXITSTATUS=%-3d   (st & 0xff) = %d\n",
            st, status, (unsigned) status,
            WIFEXITED(status) ? 1 : 0,
            WIFEXITED(status) ? WEXITSTATUS(status) : -1,
            st & 0xff);
}

int
main(void)
{
    int i;

    /* 关掉 stdio 缓冲：本程序要 fork，但父进程从 printf 自己的报表都在
       fork 之后，关缓冲可以彻底排除「父子各持一份缓冲」这个干扰 */
    setvbuf(stdout, NULL, _IONBF, 0);

    printf("=== 习题 25-1：exit(status) 的 status 只有低 8 位会到父进程手里 ===\n\n");
    printf("每行格式：子进程调的 exit() 值 → 父进程 wait() 看到的 status（十六进制）\n"
           "           → WIFEXITED / WEXITSTATUS → 与 st & 0xff 对照\n\n");

    for (i = 0; i < (int) N_STATUS; i++) {
        int st = STATUSES[i];
        pid_t pid;
        int status;

        pid = fork();
        if (pid == -1) {
            printf("  fork 失败（第 %d 个）\n", i);
            return EXIT_FAILURE;
        }
        if (pid == 0) {
            exit(st);            /* 题目里的写法：exit()，不是 _exit() */
            /* 不会到这里 */
        }
        if (waitpid(pid, &status, 0) == -1) {
            printf("  waitpid 失败\n");
            return EXIT_FAILURE;
        }
        showStatus(st, status);
    }

    printf("\n=== 对照：子进程被信号杀死时，低 8 位不是退出码 ===\n");
    {
        pid_t pid = fork();
        int status;

        if (pid == 0) {
            raise(SIGSEGV);      /* 默认动作：终止 + core */
            _exit(0);
        }
        if (waitpid(pid, &status, 0) == -1) {
            printf("  waitpid 失败\n");
            return EXIT_FAILURE;
        }
        printf("  raise(SIGSEGV)  status = %d (0x%04x)   "
               "WIFSIGNALED=%d  WTERMSIG=%d  WCOREDUMP=%d\n",
                status, (unsigned) status,
                WIFSIGNALED(status) ? 1 : 0,
                WIFSIGNALED(status) ? WTERMSIG(status) : -1,
                WCOREDUMP(status) ? 1 : 0);
        printf("  WIFEXITED=%d   WEXITSTATUS(原样) = %d —— 无意义，别读它\n",
                WIFEXITED(status) ? 1 : 0,
                WEXITSTATUS(status));
        printf("  ⇒ status 低 7 位是信号号 11（SIGSEGV）；最高位 0x80 是 core 标志\n"
               "     ⇒ 139 = 128 + 11，这就是 shell 里 $? 的由来\n");
        printf("  ⇒ 也正因如此，exit(128+n) 与「被信号 n 杀死」在 shell 里无法区分\n");
    }

    printf("\n⭐ 习题 25-1 的答案：exit(-1) ⇒ 父进程 WEXITSTATUS() = 255\n");
    return EXIT_SUCCESS;
}
```

## 2. 把这 16 行读成一张规则表

把实测输出重排成"输入 → 内核存的数 → `WEXITSTATUS`"：

| 子进程 `exit(n)` | `n & 0xff` | `status`（十进制） | `status`（十六进制） | `WEXITSTATUS(status)` |
|------------------|-----------|--------------------|----------------------|-----------------------|
| `-1` | `0xff` = **255** | 65280 | `0xff00` | **255** |
| `-2` | `0xfe` = **254** | 65024 | `0xfe00` | **254** |
| `-256` | `0x00` = 0 | 0 | `0x0000` | 0 |
| `-1000` | `0x18` = 24 | 6144 | `0x1800` | 24 |
| `0` | 0 | 0 | `0x0000` | 0 |
| `1` | 1 | 256 | `0x0100` | 1 |
| `2` | 2 | 512 | `0x0200` | 2 |
| `127` | 127 | 32512 | `0x7f00` | 127 |
| `128` | 128 | 32768 | `0x8000` | 128 |
| `255` | 255 | 65280 | `0xff00` | 255 |
| `256` | 0 | 0 | `0x0000` | 0 |
| `257` | 1 | 256 | `0x0100` | 1 |
| `300` | 44 | 11264 | `0x2c00` | 44 |
| `511` | 255 | 65280 | `0xff00` | 255 |
| `1000` | 232 | 59392 | `0xe800` | 232 |
| `65535` | 255 | 65280 | `0xff00` | 255 |

### 逐条解读

**① 右侧两列永远相等** —— `WEXITSTATUS(status)` 恒等于 `n & 0xff`。
这正是"父进程取状态那一刻做截断"这个印象的来源，
但真正的截断点还要更早（第 3 节）。

**② 好几个不同的输入吃到同一个输出**：

| 输入 | `WEXITSTATUS` | 说明 |
|------|--------------|------|
| `-1` / `255` / `511` / `65535` | **255** | 低 8 位都是 `0xff` |
| `0` / `-256` / `256` | **0** | 低 8 位都是 `0x00` |
| `-2` | 254 | 与 `254` 等价 |
| `-1000` | 24 | `-1000 & 0xff = 0x18` |
| `257` / `1` | 1 | |

⚠️ **这是"退出码不够用"的直接证据**：`exit(-1)`、`exit(255)`、`exit(511)`、
`exit(65535)` 在父进程看来**完全无法区分**。
⇒ **不要用退出码传递超出 8 位的信息**（比如"错误码 + 模块号 + 行号"）。

**③ `exit(-1000)` ⇒ 24 这一行最反直觉。** `-1000` 的两补码是 `0xFFFFFC18`，
低 8 位是 `0x18 = 24`；然后左移 8 位得 `0x1800 = 6144`。
⇒ **负数和正数走的是同一条"取低位"规则**，没有什么"负数特殊处理"。

**④ `exit(300)` ⇒ 44** —— `300 = 0x12C`，低 8 位 `0x2C = 44`。
⇒ 超过 255 的数**不是**"截成 255"，而是**按位取低 8 位**。

## 3. ⭐ 为什么 `status` 是 65280 而不是 255 —— 编码揭秘

这是本题**真正的考点**。父进程 `wait()` 拿到的那个 `int status` **不是退出码本身**，
而是一个把三样东西打包在一起的 **wait status**：

| 位 | 含义 |
|----|------|
| 第 **0–6** 位 | **信号号**（被信号杀死时有效；正常退出时是 0） |
| 第 **7** 位（`0x80`） | **core dump 标志**（本轮实测有 core 时置 1） |
| 第 **8–15** 位 | **退出码**（正常退出时有效） |

所以对一个**正常退出**的进程，`status = exit_code << 8`：

```
exit(-1)  ⇒  低 8 位 = 0xff  ⇒  status = 0xff << 8 = 0xff00 = 65280
WEXITSTATUS(65280) = (65280 >> 8) & 0xff = 0xff = 255   ✓
```

**"取低 8 位 + 左移 8 位"这两步都在系统调用入口完成**，
在内核源码里可以逐行对上（Linux v6.6 `kernel/exit.c`）：

```c
/* kernel/exit.c:989-992 —— 单线程退出 */
SYSCALL_DEFINE1(exit, int, error_code)
{
	do_exit((error_code&0xff)<<8);
}
```

```c
/* kernel/exit.c:1033-1037 —— 整个线程组退出（glibc 的 _exit() 走这条） */
SYSCALL_DEFINE1(exit_group, int, error_code)
{
	do_group_exit((error_code & 0xff) << 8);
	/* NOTREACHED */
	return 0;
}
```

然后这个已经编码好的值被存进 `task_struct`：

```c
/* kernel/exit.c:858 */
	tsk->exit_code = code;
```

父进程取的时候**直接搬走、不再做任何变换**：

```c
/* kernel/exit.c:1193-1195，wait_task_zombie() */
	status = (p->signal->flags & SIGNAL_GROUP_EXIT)
		? p->signal->group_exit_code : p->exit_code;
	wo->wo_stat = status;
```

⇒ ⭐ **一个常见误解**："低 8 位截断发生在 `WEXITSTATUS()` 里"。
**不对。** `WEXITSTATUS` 只是"从第 8–15 位取出来"，
真正的 `& 0xff` 发生在**子进程调 `exit()` 的那一刻**（系统调用入口）。
如果截断发生在读取端，那么 `exit(256)` 应该和 `exit(0)` 在内核里存**不同的值** ——
但实测两者都是 `status = 0`，说明内核里存的就已经是 `0` 了。

## 4. 对照：被信号杀死时，低 8 位不是退出码

程序最后跑了一次 `raise(SIGSEGV)` 作对照：

```text
  raise(SIGSEGV)  status = 139 (0x008b)   WIFSIGNALED=1  WTERMSIG=11  WCOREDUMP=1
  WIFEXITED=0   WEXITSTATUS(原样) = 0 —— 无意义，别读它
```

拆开 `139 = 0x008b`：

| 位段 | 值 | 含义 |
|------|-----|------|
| 第 0–6 位 | `0x0b` = **11** | 信号号 = `SIGSEGV` |
| 第 7 位 | `0x80` = 1 | **core dump 标志置位** |
| 第 8–15 位 | `0x00` | 没有退出码（不是正常退出） |

⭐ 三条要点：

1. **必须先判 `WIFEXITED` / `WIFSIGNALED`，再决定用哪个宏取数。**
   对一个被信号杀死的进程调 `WEXITSTATUS()` 拿到的是**垃圾**（实测返回 0）。
   ⇒ 正确写法：`if (WIFEXITED(status)) code = WEXITSTATUS(status);`
2. **`139 = 128 + 11` 就是 shell 里 `$?` 的由来。** shell 用
   "正常退出 ⇒ `$?` = 退出码"、"被信号杀死 ⇒ `$?` = 128 + 信号号"的统一规则。
3. ⚠️ **由此产生一个无法消除的歧义**：`exit(128 + n)` 与"被信号 `n` 杀死"
   在 shell 层面**完全一样**。原书 §25.1（书 p.532）原话：

   > *"…this is one reason why a value greater than 128 should not be used as
   > an exit status, since it can be confused with a process being killed by a signal."*

   ⇒ **约定：正常的退出码取 0–127。** 128 及以上留给"被信号杀死"。

**关于 `WCOREDUMP = 1` 的一个提醒**（与 Ch24 的发现呼应）：
本环境 `RLIMIT_CORE` 是 `soft=0 hard=0`（`probe25` 实测），
**磁盘上并没有 core 文件**。`WCOREDUMP` 置位只表示"内核走完了 coredump 流程"，
不等于"有 core 文件"。详见 Ch24 §24.7 的 `ex24_3_core_dump`。

| 停止进程的编码（对照） | Linux v6.6 `kernel/exit.c:1313` | `wo->wo_stat = (exit_code << 8) \| 0x7f;` —— 低字节 `0x7f` 表示"已停止" |
| 继续运行的编码（对照） | Linux v6.6 `kernel/exit.c:1364` | `wo->wo_stat = 0xffff;`（`SIGCONT` 通知） |
| `WEXITSTATUS` 等宏 | glibc 2.39 `bits/waitstatus.h` / `stdlib/stdlib.h` | `WEXITSTATUS(status) = (((status) & 0xff00) >> 8)`；`WCOREDUMP(status) = ((status) & 0x80)` |
| `exit()` 的 8 位规则（原书） | 原书 §25.1 书 p.532 | *"only the lowest 8 bits of the status are made available to the parent process"* |
| 别用 >128 的退出码（原书） | 原书 §25.1 书 p.532 | 与被信号杀死混淆 |

⚠️ `WCOREDUMP()` 在 glibc 里是 `((status) & 0x80)`，**位掩码，不是布尔值**
（只能取 `0` 或 `128`）。这是 Ch24 那章的发现，本章实测再次确认（`WCOREDUMP=1` 是我程序里
`? 1 : 0` 归一化过的结果，原始值就是 `0x80`）。

## 6. 常见坑

1. **`exit()` 的状态码只走 0–255。** 传 `-1` 会得到 255；传 `65535` 也是 255。
   想让父进程区分 4 种以上状态，就把它们映射到 0–127 的几个值上。
2. **不要用 128 以上的退出码**（原书明确建议）。`exit(139)` 与
   `SIGSEGV` 致死在 shell 层面无法区分。
3. **`WEXITSTATUS()` / `WTERMSIG()` 不能盲用**，先判 `WIFEXITED` / `WIFSIGNALED`。
4. **`status` 是 `int`，但只有低 16 位有意义。** 别把它当成"退出码"直接比较，
   要比较退出码就 `WEXITSTATUS(status) == 3`。
5. **`exit(-1)` 的正确读法**：`-1` 在 C 里是 `int`，两补码 `0xFFFFFFFF`，
   低 8 位 `0xFF` ⇒ 255。**不是"负数变 255"，而是"按位取低 8 位"。**
6. **`status` 的高 16 位可能是垃圾**（内核只填低 16 位），
   所以 `status == 0x12340000` 这种比较没有意义。
7. **glibc 的 `exit()` 走 `exit_group`，不是 `exit`。** 这也是为什么
   "一个线程调 `exit()`"会**终止整个进程**（而不是只结束那个线程）——
   单线程退出要用 `pthread_exit()`（Ch33）。

## 7. HFT / 嵌入式关联

**① 8 位的退出码是一份非常廉价的"故障分类字典"。**
在低延迟系统里，重启是常规操作，**"为什么重启"比"重启了"重要得多**。
把常见故障映射到 0–127 的固定值上（比如 0 = 正常、10 = 配置错、20 = 对端断连、
30 = 内部断言、40 = 风控拒单、50 = 依赖超时），
supervisor 侧只需要读 8 位就能分类告警。

⚠️ 但要注意 **`exit(255)` 与 `exit(-1)` 无法区分**，所以：
- **别用 255 做"未分类错误"**（会和 `-1` 撞车）；
- **别用 128–255 这一整段**（会和"被信号杀死"撞车，原书建议）。

**② "被信号杀死"是 HFT 进程最常见的死法之一**（OOM killer / watchdog / `kill -9`），
所以退出码分析必须**同时**看 `WIFEXITED` 与 `WIFSIGNALED`：

| 判据 | 含义 | 该怎么办 |
|------|------|----------|
| `WIFEXITED && WEXITSTATUS == 0` | 正常退出 | 正常 |
| `WIFEXITED && WEXITSTATUS != 0` | 自己报的错 | 查字典 |
| `WIFSIGNALED && WTERMSIG == 9` | 被 `SIGKILL` | 看 dmesg 有无 OOM；看是不是 watchdog |
| `WIFSIGNALED && WTERMSIG == 6` | `SIGABRT`（`abort()`） | 内部断言失败，**要看 core / `backtrace`** |
| `WIFSIGNALED && WTERMSIG == 11` | `SIGSEGV` | 内存错误，**要看 core** |

⇒ **只记 `$?` 的 shell 脚本会漏掉第 3–5 行**（因为 `$?` 把它们混成 137 / 134 / 139）。

**③ 嵌入式里"退出码"常被用来做"启动级别"的信号。**
一个 init 脚本根据前一次退出的码决定"要不要进安全模式"。
由于只有 8 位，**一定要写死一张映射表并注释在源码里**，
否则半年后没人知道 `exit(42)` 是什么意思。

**④ 调试上的直接收益：知道"低 8 位在系统调用入口就被截"这件事，
就能立刻回答"为什么我用 `exit(-1)` 记录的错误码在日志里变成 255"。**
这个坑在嵌入式里很常见（错误码用负数表示的代码风格 + `exit()` 路径）。

<summary>代码自测（Q&A）</summary>

**Q1：习题 25-1 的答案是多少？**

A：**255。** `exit(-1)` 的 `-1` 低 8 位是 `0xFF = 255`，
父进程 `WEXITSTATUS()` 拿到 255。

**Q2：父进程 `wait()` 拿到的 `status` 为什么是 65280（`0xff00`）而不是 255？**

A：因为 `status` **不是退出码本身**，而是一个打包结构：
低 7 位是信号号、第 7 位是 core 标志、**第 8–15 位才是退出码**。
所以正常退出时 `status = 退出码 << 8`。`0xff << 8 = 0xff00 = 65280`。

**Q3：`& 0xff` 这一步到底在哪里发生？**

A：在**系统调用入口**。Linux v6.6 `kernel/exit.c:989-992`（`exit`）和
`1033-1037`（`exit_group`，glibc `_exit()` 走的这条）都是
`do_exit((error_code & 0xff) << 8)` —— **先取低 8 位、再左移 8 位**。
父进程取状态时（`kernel/exit.c:1193-1195`）**不再做任何变换，直接搬走**。
⇒ "截断发生在读取端"是常见误解。证据：`exit(256)` 与 `exit(0)`
在内核里存的都是 `0`。

**Q4：`exit(255)`、`exit(-1)`、`exit(511)`、`exit(65535)` 能被区分吗？**

A：**不能。** 四者的低 8 位都是 `0xff`，父进程看到的 `status` 都是 65280。
实测表格里它们在同一行水平上完全一致。

**Q5：子进程被 `SIGSEGV` 杀死，`status` 是多少？怎么读？**

A：实测 **139**（`0x008b`）。拆开：低 7 位 `0x0b = 11` 是 `SIGSEGV`、
第 7 位 `0x80` 是 core 标志、第 8–15 位是 0（没有退出码）。
⇒ 必须先 `WIFSIGNALED(status)` 为真，再用 `WTERMSIG(status)` 取 11。
**对这样的 `status` 调 `WEXITSTATUS()` 拿到的是垃圾**（实测返回 0）。

**Q6：为什么原书建议不要用大于 128 的退出码？**

A：因为 shell 里 `$?` 的统一规则是"被信号 `n` 杀死 ⇒ `$?` = 128 + `n`"。
所以 `exit(139)` 和"被 `SIGSEGV`（11）杀死"在 shell 层面**完全无法区分**。
⇒ 正常退出码约定用 **0–127**。

**Q7：`WCOREDUMP(status)` 返回 1 就说明磁盘上有 core 文件吗？**

A：**不一定。** `WCOREDUMP()` 是位掩码 `status & 0x80`（只能取 0 或 128），
它只表示"内核走完了 coredump 流程"。
本环境 `RLIMIT_CORE` 是 `soft=0 hard=0`（`probe25` 实测），
**磁盘上没有 core 文件**。详见 Ch24 的 `ex24_3_core_dump`。

**Q8：glibc 的 `exit()` 走的是 `exit` 还是 `exit_group`？为什么重要？**

A：走 **`exit_group`**。这解释了一个常见困惑：**在任何一个线程里调 `exit()`，
整个进程都会结束**（不是只结束那个线程）——
因为 `exit_group` 的语义就是"干掉整个线程组"
（`kernel/exit.c:1028-1031` 的注释：*"this kills every thread in the thread group"*）。
要多线程里只结束一个线程，得用 `pthread_exit()`（Ch33）。
