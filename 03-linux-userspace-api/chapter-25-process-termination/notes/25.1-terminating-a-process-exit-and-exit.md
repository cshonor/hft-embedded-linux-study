## 本节讲什么

原书 §25.1 只做一件事：把「一个进程怎么结束」拆成**两条入口、三种写法、一条 8 位通道**。

| 要讲清的问题 | 答案在哪 |
|-------------|---------|
| 进程有几种死法？ | 正常（主动调 `_exit`）· 异常（被信号杀） |
| `exit()` 和 `_exit()` 差别在哪？ | `exit()` 多做两件事：跑 exit handler、flush stdio |
| 退出码为什么只有 8 位？ | 内核只把 `status & 0xff` 左移 8 位存进 `exit_code` |
| `return n` 和 `exit(n)` 等价吗？ | 几乎等价（crt0 拿 main 的返回值去调 `exit`），但有例外 |
| 掉出 `main` 末尾呢？ | C89 未定义；**C99 起等价于 `exit(0)`** |

⚠️ **原书 §25.1 没有任何 Listing**（本章仅有的两个 Listing 分别在 §25.3 和 §25.4）。
本仓库为此自写了两个程序（`c25_exit_three_steps.c`、`c25_fall_off_main.c`），
把「三步顺序」与「掉出末尾」变成**可运行的真实输出**。

## 1. 两种终止方式

| 方式 | 触发者 | 会跑 exit handler？ | 会 flush stdio？ | 内核里留下的东西 |
|------|--------|--------------------|-----------------|-----------------|
| **正常终止** | 进程自己调 `_exit()` / `_Exit()` / `exit()`，或 `main` 返回 | 只有走 `exit()` 才跑 | 只有走 `exit()` 才刷 | 8 位退出码 |
| **异常终止** | 收到**致命信号**（默认动作是终止的那些） | ❌ 一律不跑 | ❌ 一律不刷 | 信号号 + 是否 core |

⭐ 记住这一条就够用了：**`exit handler` 和 `stdio flush` 都是 `exit()` 这个库函数提供的，
不是「进程终止」这件事自带的**。走 `_exit()` 或被杀，这两件事都不会发生。

由此推出一条原书反复强调的实践准则：
**`SIGKILL` 永远无法被拦截**——它连 `exit()` 都不走，所以任何「用 `atexit` 做清理来兜底」的设计，
在 `SIGKILL` 面前都是空的。这也是「尽量先发 `SIGTERM`」的又一个理由
（`SIGTERM` 可以被处理函数接住，在函数里从容地 `exit()`）。

## 2. `_exit(status)`：只有低 8 位到得了父进程手里

原书原文（§25.1）：

> Although declared as an `int`, **only the bottom 8 bits of `status` are actually made available to the parent**.

也就是说，`_exit()` 的形参是 `int`（32 位），但**通道只有 8 位宽**。

- `_exit(0)` 或 `EXIT_SUCCESS` ⇒ 成功。实测沙箱里 `EXIT_SUCCESS = 0`、`EXIT_FAILURE = 1`。
- 为什么是 8 位而不是 32 位？见本文第 6 节的源码坐标——**截断发生在内核的 syscall 入口**，
  一行 `do_exit((error_code&0xff)<<8)` 就把这件事钉死了。

⚠️ 原书在 §25.1 里给了一个**很实际的警告**：如果程序用一个大于 128 的值当退出码，
shell 脚本会读不懂。因为按惯例 `$?` 在被信号杀死时等于 `128 + 信号号`：

| 看起来的写法 | shell 里 `$?` | 能不能和「被信号杀」区分 |
|-------------|--------------|----------------------|
| `_exit(1)` | 1 | ✅ 能 |
| `_exit(127)` | 127 | ✅ 能 |
| `_exit(130)` | 130 | ❌ 和 `SIGINT`(2) 杀死 **完全一样** |
| `_exit(139)` | 139 | ❌ 和 `SIGSEGV`(11) 杀死 **完全一样** |

**约定：退出码就用 0–127**，把 128–255 留给内核报信号。

## 3. `exit()`：三步，顺序不能变

原书 §25.1 用三个 bullet 写清了 `exit()` 做的事（**顺序即语义**）：

| 步 | 动作 | 谁实现 |
|---|------|-------|
| ① | 按**注册的逆序**（LIFO）调用所有 exit handler | 用户态（`atexit` / `on_exit` 注册的那些） |
| ② | flush 所有 stdio 流的缓冲 | 用户态（glibc 的 `_IO_cleanup`） |
| ③ | 调用 `_exit(status)` | 进内核 |

⭐ 「①在②之前」这条顺序很关键：它意味着**在 exit handler 里 `printf` 出去的字符串，
还能被第②步的 flush 送出去**；反过来，如果 handler 里调了 `_exit`，那第②步就被跳过，
handler 里 printf 的东西会**一起丢掉**（第 4 节的实测会把这半句也钉死）。

---

## 4. 把「三步顺序」变成可观察量（本仓库自写）

读文档只能知道「①在②之前」，没法建立直觉。做法是把两条通路混着用：

| 通路 | 数据先到哪 | 什么时候能在 stdout 看到 |
|------|-----------|----------------------|
| `write(2)` | **直接进内核** | **立刻** |
| `printf(3)` | 先进用户态 `FILE` 缓冲 | 等 flush（正常退出时就是第②步） |

于是「谁先出现」就等于「内核缓冲 vs 用户态缓冲」，而 flush 的那一刻会被精确定位到某个 `write` 之后。

[`code/c25_exit_three_steps.c`](../code/c25_exit_three_steps.c)

```c
/* c25_exit_three_steps.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.1 用三行 bullet 说清了 exit() 依次做三件事：
     ① 按注册的【逆序】调用 exit handler（atexit / on_exit 注册的）
     ② flush stdio 流缓冲
     ③ 调用 _exit(status)

   但「① 在 ② 之前」这句话没法靠读文档建立直觉，得让顺序变成**可观察量**。
   做法是把两条通路混着用：
     · write(2)  → 直接进内核缓冲，**立刻**出现在 stdout
     · printf(3) → 先进用户态 FILE 缓冲，要等 flush 才出现
   于是「谁先出现」就等价于「内核缓冲 vs 用户态缓冲」，而 flush 的时刻
   会被精确定位到某个 write 之后。

   在 CE 上跑：stdout 不是终端（是 socket）⇒ glibc 对 stdout 用**全缓冲**，
   所以下面这个顺序是**确定**的。如果在真终端上跑，stdout 是行缓冲，
   printf 会被换行符逐个推出去，顺序就完全不同 —— 这本身就是 §25.4 的内容。

   编译: gcc -O0 -Wall -Wextra -o c25_exit_three_steps c25_exit_three_steps.c
   运行: ./c25_exit_three_steps
*/
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

/* write() 的包装：只写固定字符串 */
static void
w(const char *s)
{
    write(STDOUT_FILENO, s, strlen(s));
}

/* 先跑的 handler（后注册）：只 write + printf，不 flush */
static void
handlerB(void)
{
    w("W2  来自 hB 的 write()      —— 立刻出来\n");
    printf("M2  来自 hB 的 printf()    —— 先进用户态缓冲\n");
}

/* 后跑的 handler（先注册）：中间插一次 fflush，把「此刻缓冲里有什么」钉死 */
static void
handlerA(void)
{
    w("W3  来自 hA 的 write()      —— 立刻出来\n");
    fflush(stdout);          /* ← 关键：把 M1、M2 推出去，证明它们一直躺在缓冲里 */
    printf("M3  来自 hA 的 printf()    —— 直到 exit() 第 ② 步才出来\n");
    w("W4  来自 hA 的 write()      —— 在它自己的 printf 之后！\n");
}

int
main(void)
{
    w("=== 图例：W* 走 write(2)（立刻可见）；M* 走 printf(3)（先进用户态缓冲）===\n");
    w("=== 观察点：M1/M2 什么时候出现，就等于 hA 那次 fflush 的位置 ===\n\n");

    printf("M1  来自 main 的 printf()  —— 先进用户态缓冲\n");
    w("W1  来自 main 的 write()    —— 立刻出来\n");

    if (atexit(handlerA) != 0 || atexit(handlerB) != 0) {
        w("atexit 注册失败\n");
        return EXIT_FAILURE;
    }
    w("\n--- 下面调用 exit(0)：handler 先跑（LIFO：hB 再 hA），最后才 flush ---\n");

    exit(0);   /* 不返回 */
}
```

编译命令（与官方 `Makefile.inc` 同名参数）：

```bash
gcc -O0 -Wall -Wextra -o c25_exit_three_steps c25_exit_three_steps.c
./c25_exit_three_steps
```

CE 实测（`c25_exit_three_steps`，逐字取自冻结日志）：

```text
=== 图例：W* 走 write(2)（立刻可见）；M* 走 printf(3)（先进用户态缓冲）===
=== 观察点：M1/M2 什么时候出现，就等于 hA 那次 fflush 的位置 ===

W1  来自 main 的 write()    —— 立刻出来

--- 下面调用 exit(0)：handler 先跑（LIFO：hB 再 hA），最后才 flush ---
W2  来自 hB 的 write()      —— 立刻出来
W3  来自 hA 的 write()      —— 立刻出来
M1  来自 main 的 printf()  —— 先进用户态缓冲
M2  来自 hB 的 printf()    —— 先进用户态缓冲
W4  来自 hA 的 write()      —— 在它自己的 printf 之后！
M3  来自 hA 的 printf()    —— 直到 exit() 第 ② 步才出来
```

### 逐条解读

| 行 | 观察 | 说明 |
|----|------|------|
| `W1` | main 的 `write()` 先出来 | `write` 不等任何人 |
| `W2` `W3` | 两个 handler 的 `write()` 紧接着 | handler 确实**在 flush 之前**跑 |
| `M1` `M2` | 两个 `printf` 挤在 `W3` **之后** | 它们一直躺在用户态缓冲里，直到 `hA` 里那行 `fflush(stdout)` |
| `W4` | `hA` 在**自己的 printf 之后**又 `write` 了一行 | 证明 `M3` 此刻还**没**出去 |
| `M3` | 最后一行 | 它是被 `exit()` 第②步（`_IO_cleanup`）推出去的，**不是**被 `hA` 那行 `fflush` |
| 顺序 | `hB` 先跑、`hA` 后跑 | 注册顺序是 `hA`、`hB`，逆序 ⇒ `hB` 先 ⇒ **LIFO 实证** |

⭐ 这一节同时钉死两件事：**handler 在 flush 之前**、**handler 之间是 LIFO**。
第③步（`_exit`）在这份输出里看不出来——它只是让进程真的消失，没有任何输出。

⚠️ **CE 沙箱的前提**：stdout 是 **socket**（`S_ISSOCK=1`，`isatty(1)=0`），
所以 glibc 对 stdout 用**全缓冲**，上面这个顺序是**确定**的。
如果在真终端上跑，stdout 变行缓冲，`printf` 会被换行符逐个推出去，顺序完全不同——
那正是 §25.4 要讲的内容。

## 5. `return n` 与「掉出 main 末尾」

原书 §25.1 末尾这一段经常被略过，但它解释了一个真实的诡异现象。

`return n;` 在 `main` 里**几乎等于** `exit(n)`：crt0 里的 `__libc_start_main` 拿到 `main` 的返回值后，
就是拿它去调用 `exit()`。所以 `return` 也会走 exit handler、也会 flush。

⚠️ 但「几乎」二字后面有一个**真实例外**：如果程序在 `exit` 的过程中还要访问 `main` 的**局部变量**，
那 `return` 就是未定义行为。原书举的例子是 `setvbuf()` 的参数指向了 `main` 里的局部数组——
因为 `main` 返回后那些局部变量的生命周期就结束了。

### 掉出末尾：C89 与 C99 的分水岭

| 标准 | 从 `main` 掉出末尾（既不 `return` 也不 `exit`） |
|------|---------------------------------------------|
| **C89** | **未定义行为**——原书点名 gcc 默认就是这种情形：退出状态取自「栈或某个 CPU 寄存器里的某个随机值」 |
| **C99 起** | **等价于 `exit(0)`** |

本仓库用一个程序把这两半都跑出来：

[`code/c25_fall_off_main.c`](../code/c25_fall_off_main.c)

```c
/* c25_fall_off_main.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.1 末尾提到一件容易忽略的事：从 main() **掉出末尾**（既没 return
   也没调 exit()）时，调用 main() 的那段运行时（crt0 里的 __libc_start_main）
   会接着调 exit()，但**用什么参数**取决于 C 标准和编译选项：

     · C89：行为**未定义**，程序可能带任意状态值终止。原书点名 gcc 默认就是
       这种情形 —— 退出状态取自「栈上或某个 CPU 寄存器里的某个随机值」。
     · C99：掉出 main 末尾**等价于 exit(0)**。原书说用 `gcc -std=c99` 就能拿到
       这个行为。

   本程序故意写成一个没有 return 的 main，然后**用同一个源文件、只改 -std**
   编两遍，把两次的退出码并列出来。

   为了让「那个随机值」可指认，main 的最后一句是 `marker()`（返回 42 的函数）
   —— 它的返回值没人接，很可能就留在返回寄存器里，被 crt0 当成 main 的返回值。
   ⚠️ 这只是**实现细节**，不是标准保证的东西；C89 下真正的语义就是「未定义」。

   编译（两个作业）:
     gcc -O0 -Wall -Wextra -std=c89 -o c25_fall_off_c89 c25_fall_off_main.c
     gcc -O0 -Wall -Wextra -std=c99 -o c25_fall_off_c99 c25_fall_off_main.c
   运行: ./c25_fall_off_c89 ; echo $?     （看退出码）
*/
#include <string.h>
#include <unistd.h>

static const char MSG[] =
    "main() 走完了最后一条语句：没有 return，也没有调 exit()\n"
    "本程序的退出码，就是 crt0 拿到的那个「main 的返回值」\n";

static int
marker(void)
{
    return 42;      /* 故意留一个可指认的数字 */
}

int
main(void)
{
    write(STDOUT_FILENO, MSG, strlen(MSG));
    marker();       /* 最后一句：返回值无人接收 */
}
```

编译命令（同一个源文件，只改 `-std`）：

```bash
gcc -O0 -Wall -Wextra -std=c89 -o c25_fall_off_c89 c25_fall_off_main.c
gcc -O0 -Wall -Wextra -std=c99 -o c25_fall_off_c99 c25_fall_off_main.c
```

CE 实测（`c25_fall_off_c89`，`exit code = 42`）：

```text
main() 走完了最后一条语句：没有 return，也没有调 exit()
本程序的退出码，就是 crt0 拿到的那个「main 的返回值」
```

CE 实测（`c25_fall_off_c99`，`exit code = 0`）：

```text
main() 走完了最后一条语句：没有 return，也没有调 exit()
本程序的退出码，就是 crt0 拿到的那个「main 的返回值」
```

### 逐条解读

| 作业 | `-std` | 进程退出码 | 与预测是否一致 |
|------|--------|-----------|--------------|
| `c25_fall_off_c89` | `c89` | **42** | ✅ 与「寄存器里那个残留值」的猜测一致 |
| `c25_fall_off_c99` | `c99` | **0** | ✅ 标准规定就是 `exit(0)` |

⭐ `42` 的来源：`main` 的最后一句是 `marker()`（一个返回 42 的函数），它的返回值没人接收，
很可能就留在**返回寄存器**里，被 crt0 当成 `main` 的返回值用了。
这也解释了 gcc 为什么会给出警告：

```text
warning: control reaches end of non-void function [-Wreturn-type]
```

⚠️ **`42` 是实现细节，不是标准保证的东西**。C89 下真正的语义就是「未定义」——
换个编译器、换个优化级别，这个数字就会变。**能确定的只有 C99 那一半：0。**

📌 工程结论：**`main` 永远写显式 `return`**。不要依赖 C99 的隐式 `return 0`
（老代码可能用 C89 编译），更不要依赖一个「恰好是 42」的巧合。

| 项目 | 实测值 | 说明 |
|------|-------|------|

⭐ `139 = 128 + 11`——这就是 shell 里 `$?` 的由来，也正是第 2 节那条

## 7. 源码坐标

### 内核侧（Linux v6.6 `kernel/exit.c`）

| 坐标 | 内容 | 为什么重要 |
|------|------|-----------|
| `kernel/exit.c:989-992` | `SYSCALL_DEFINE1(exit, int, error_code) { do_exit((error_code&0xff)<<8); }` | ⭐ **「只有低 8 位」的现场**：`&0xff` 在 syscall 入口就把高位切掉了 |
| `kernel/exit.c:809` | `void __noreturn do_exit(long code)` | 所有终止路径的汇合点 |
| `kernel/exit.c:858` | `tsk->exit_code = code;` | 退出码存进 `task_struct` |
| `kernel/exit.c:999` | `do_group_exit(int exit_code)` | 致命信号走的另一条入口 |
| `kernel/exit.c:1024` | `do_exit(exit_code);` | `do_group_exit` 的收口 |

⭐ 注意 `(error_code&0xff)<<8` 这个写法：内核**先**把用户给的值截成 8 位，**再**左移 8 位存起来。
所以 `exit(-1)` 在 `task_struct` 里躺的是 `0xff00`，而不是 `0xffffffff`——
这正是实测表里 `status = 65280 (0xff00)` 的来源。

### glibc 侧（2.39）

| 坐标 | 内容 |
|------|------|
| `stdlib/stdlib.h:734` | `extern int atexit (void (*__func) (void)) __THROW` |
| `stdlib/stdlib.h:749` | `extern int on_exit (...)` —— 注意它在 `#ifdef __USE_MISC` 里面 |
| `stdlib/stdlib.h:753-756` | 注释原文：*Call all functions registered with `atexit` and `on_exit`, in the reverse of the order in which they were registered, perform stdio cleanup, and terminate program execution with STATUS* ← **原书三步说的库内出处** |
| `stdlib/exit.c:136-138` | `void exit (int status) { __run_exit_handlers (status, &__exit_funcs, true, true); }` |
| `stdlib/exit.c:128-131` | `if (run_list_atexit) call_function_static_weak (_IO_cleanup); _exit (status);` ← ⭐ **②flush 和 ③`_exit` 就在这里** |
| `stdlib/exit.c:36-37` | `__run_exit_handlers (int status, struct exit_function_list **listp, bool run_list_atexit, bool run_dtors)` |

⚠️ 从 `exit.c:36` 的形参能看出一个原书**没提**的细节：glibc 的 `exit()` 实际上做了**四件事**——
在①之前还有一个 `if (run_dtors) call_function_static_weak (__call_tls_dtors);`（`exit.c:40-41`），
即先跑 **TLS 析构函数**（C++ 的 `thread_local` 析构走这条路）。C 程序基本碰不到它，
但读源码时要意识到「三步」是**原书的简化说法**。

## 8. 常见坑

| # | 坑 | 症状 | 正解 |
|---|----|------|------|
| 1 | fork 出来的子进程用 `exit()` | 父进程的 stdio 缓冲被复制、父子各 flush 一遍 ⇒ 输出重复 | 子进程用 `_exit()`（见 §25.4） |
| 2 | 退出码写 `130` 想表示「中断」 | shell 里和 `SIGINT` 杀死无法区分 | 用 0–127 |
| 3 | 用 `exit()` 当「快速退出」 | 会跑完所有 handler，不可控 | 需要立刻消失就用 `_exit()` |
| 4 | `main` 不写 `return` | C89 下退出码是垃圾值 | 永远写显式 `return` |
| 5 | 以为 `SIGKILL` 能被 handler 兜住 | `atexit` 里的清理一条都不跑 | 用 `SIGTERM`；`SIGKILL` 只能靠外部兜底 |
| 6 | 在 exit handler 里访问 `main` 的局部变量 | `return` 路径下 UB | 把需要的数据放全局/静态 |

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **HFT** | 热路径上的「快速退出」必须走 `_exit()`：`exit()` 会**遍历 exit handler 列表 + flush 全部 stdio**，在延迟敏感场景里是不可接受的不确定性。反过来，行情网关的**优雅下线**要走 `exit()`，靠 `atexit` 把 socket 关掉、把日志刷盘。 |
| **HFT** | 进程被 `SIGKILL`（OOM killer 或运维强杀）时，`atexit` 里的对账/落盘**一条都不会执行** ⇒ 关键状态不能只放在内存里等退出时写，必须**持续落盘**（write-ahead）。 |
| **嵌入式** | 退出码只有 8 位 ⇒ 用「状态码 + 错误码」两位编码（如 `(模块 << 4) | 原因`）比塞一个大整数有效。`systemd` 的 `Restart=`/`SuccessExitStatus=` 也都是按 8 位判的。 |
| **嵌入式** | daemon 化之后 `main` 返回的语义会被 supervisor 看见；用 `_exit()` 收场可以**跳过** atexit 链——这在「watchdog 已经要重启我了，别做无谓清理」的场景下是优点。 |

## 代码自测

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`_exit(-1)` 之后，父进程 `waitpid()` 拿到的 status 是 255 吗？**

不是。**status 本身是 65280（`0xff00`），`WEXITSTATUS(status)` 才是 255。**

原因：内核在 syscall 入口做 `do_exit((error_code&0xff)<<8)`（`kernel/exit.c:991`），
低 8 位被搬到 status 的**高字节**。父进程再用 `WEXITSTATUS` 宏把它搬回来。
所以「255」这个数字是 `WEXITSTATUS` 的解释结果，不是 status 的原始值。


**Q2：为什么在 exit handler 里 `printf` 的内容还能打出来，但 handler 里调 `_exit` 后同样一行就没了？**

因为 `printf` 只是把字符串放进**用户态 FILE 缓冲**，真正的输出要等 `exit()` 的第②步
（`_IO_cleanup`，见 `stdlib/exit.c:128-129`）。

- handler 正常返回 ⇒ 第②步照跑 ⇒ 内容出去。
- handler 调 `_exit()` ⇒ 直接进内核（`exit.c:131` 那行 `_exit(status)` **都没机会执行**）⇒ 缓冲一起丢。

§25.3 的 `c25_exit_handler_no_return.c` 把这两种情形并排跑了一次，差别肉眼可见。


**Q3：`return 0;` 和 `exit(0);` 在 `main` 里有什么区别？**

正常路径上**几乎没区别**：crt0（`__libc_start_main`）拿到 `main` 的返回值后就是用它调 `exit()`，
所以 handler、flush 都会发生。

区别出现在**生命周期**上：`return` 会先结束 `main` 的作用域，之后如果在 flush/handler 阶段
还去访问 `main` 的局部变量（例如 `setvbuf()` 的参数指向 `main` 里的局部数组），就是 **UB**。
`exit()` 从 `main` 内部调用，`main` 的栈帧还没退，没有这个问题。


**Q4：`c25_fall_off_c89` 退出码为什么是 42？这是可移植的行为吗？**

不是。42 只是「`main` 最后一句调用的 `marker()` 的返回值恰好留在返回寄存器里」这个
**实现细节**的副产品。C89 对「掉出 `main` 末尾」的定义就是**未定义行为**——
换编译器、换优化级别，这个数字就会变。

能指望的只有 C99 那一半：`c25_fall_off_c99` 的退出码稳定是 **0**。


**Q5：看到 `$?` 是 139，能确定程序是自己 `exit(139)` 还是被 `SIGSEGV` 杀的吗？**

**不能。** 这正是原书 §25.1 的警告。

- 被 `SIGSEGV`(11) 杀 ⇒ status 低 7 位是 11，shell 报 `128 + 11 = 139`。
- 自己 `_exit(139)` ⇒ 内核存 `139 << 8`，`WEXITSTATUS` 也是 139，shell 同样报 139。

要在程序内部区分，必须看 `WIFEXITED` / `WIFSIGNALED`（shell 里做不到）。
本仓库的 `ex25_1_exit_minus_one.c` 实测里 `WIFSIGNALED=1 / WTERMSIG=11` 那一行就是判据。

</details>
