## 本节讲什么

`alloca` 走的是和 `malloc` 完全相反的路线：**不动堆，只挪栈指针**。

一句话语义（glibc 头文件里的注释原文）：

```c
/* Allocate a block that will be freed when the calling function exits.  */
extern void *alloca (size_t __size) __THROW;

#ifdef	__GNUC__
# define alloca(size)	__builtin_alloca (size)
#endif /* GCC.  */
```

记住这句注释里的两个词：**freed when the calling function exits** —— 回收的粒度是**函数返回**，不是作用域结束，更不是 `free`。这一节的所有反直觉现象都从这句话长出来。

⚠️ 首先明确：**`alloca` 不是标准 C，也不是 POSIX**。它是编译器扩展 —— glibc 只是提供了一个头文件把它接到 GCC 的 `__builtin_alloca`（`stdlib/alloca.h:35`）。换编译器（MSVC 没有，一些嵌入式工具链也没有）就不存在，**跨平台代码里不要用**。

## 要点

### 一、它比 `malloc` 快在哪

| 维度 | `alloca` | `malloc` |
|------|----------|----------|
| 分配动作 | **调整 `rsp`**（一条 `sub`，通常无函数调用） | 查 bin / top chunk，必要时 `sbrk` / `mmap` |
| 分配位置 | 当前函数的**栈帧** | 堆（或新的 mmap 段） |
| 释放动作 | **函数返回时自动**（`leave` 一条指令弹回） | 手动 `free`，进空闲链表 |
| 释放粒度 | **整个函数**（不是作用域！） | 任意时刻、任意顺序 |
| 能否泄漏 | 不可能 | 可能 |
| 上限 | `RLIMIT_STACK`（默认 8 MB） | 虚拟地址空间 + 物理内存 + swap |
| 失败表现 | **没有失败** —— 直接 `SIGSEGV` | 返回 `NULL` + `errno` |
| 标准性 | ❌ 非标准扩展 | ✅ C 标准 |

**为什么快**：`malloc` 最坏情况要沿着 bin 链找块，再可能要一次系统调用；`alloca` 只是把栈指针往下挪 `size` 字节（还要按 16 对齐处理一下）。

### 二、和 C99 VLA 的关系

C99 的**变长数组**（VLA）和 `alloca` 是同一种机制的两张皮 —— 都在栈上、都靠挪 `rsp`：

```c
int n = 10;
int arr[n];             /* VLA：一次分配 n*sizeof(int)，随作用域结束失效 */
void *p = alloca(n * sizeof(int));   /* 等价，但指针活到函数返回 */
```

| | VLA | `alloca` |
|---|---|---|
| 标准 | C99 起是标准（C11 起可选） | 非标准 |
| 存活期 | **作用域**（C99 说声明所在块的末尾） | **函数返回** |
| 位置 | 栈 | 栈 |
| 能否返回指针给调用者 | 不能 | 不能 |

⚠️ 别被「VLA 随作用域结束」误导成「栈内存被回收了」—— 它只是**名字不可见**了，`rsp` 并没有动。两者在物理上都没回收。

### 三、三条硬限制（每一条都有实测）

**1. 没有任何错误检查**

`malloc` 失败会返回 `NULL`，你可以处理。`alloca` **没有返回值可以判**：栈不够就直接撞进 guard page → `SIGSEGV`。

实测（c7_7 的 C 段，8 MB 栈上要 16 MB）：

```text
C. alloca(16MB)，栈只有 8MB ...
C. 子进程被信号 11 (SIGSEGV) 杀死 → 栈溢出没有「优雅失败」的途径
```

**2. 不能跨函数**

```c
void *bad(void) {
    return alloca(100);      /* ❌ 返回的指针指向已经消失的栈帧 */
}
```

`alloca` 申请的内存在**当前函数**返回时就被弹掉了。把指针传出去（返回、存进全局、塞进链表），调用者一用就踩别人的栈帧 —— 而且这种 bug 常常「看起来能跑」，直到调用栈变了才崩。

**3. 循环里不回收，会累积**

回收粒度是函数返回，所以循环里每次 `alloca` 都**真的往下走一段**，一路不回头：

实测（c7_7 的 B 段，循环 5 次 `alloca(4096)`）：

```text
B. 循环里 alloca(4096) 五次：
   i=0  p=0x7ffd2a1c8d60  与前次相差 +0
   i=1  p=0x7ffd2a1c7d50  与前次相差 -4112
   i=2  p=0x7ffd2a1c6d40  与前次相差 -4112
   i=3  p=0x7ffd2a1c5d30  与前次相差 -4112
   i=4  p=0x7ffd2a1c4d20  与前次相差 -4112
```

每次固定下移 **4112** 字节（4096 + 16 对齐开销），**5 次就是 20 KB，全部留在栈上**。所以「循环里用 `alloca`」等于「手写一个会爆栈的循环」—— 循环次数不可控时这是致命的。

### 四、工程里怎么管住它

**（a）用 `-Walloca` 把调用点全找出来**

GCC 有这个开关，能把源码里**每一处** `alloca` 都报出来。实测对 c7_7 编译：

```bash
gcc -O2 -Wall -Wextra -Walloca -o c7_7_alloca c7_7_alloca.c
```

实测输出（节选）：

```text
<source>: In function 'where_is_alloca':
<source>:20:15: warning: use of 'alloca' [-Walloca]
   20 |     char *s = alloca(16);
      |               ^~~~~~
<source>: In function 'alloca_in_loop':
<source>:36:19: warning: use of 'alloca' [-Walloca]
   36 |         char *p = alloca(4096);
      |                   ^~~~~~
<source>: In function 'alloca_huge':
<source>:56:15: warning: use of 'alloca' [-Walloca]
   56 |     char *p = alloca(bytes);
      |               ^~~~~~
<source>: In function 'vla_demo':
<source>:72:15: warning: use of 'alloca' [-Walloca]
   72 |     char *a = alloca(sizeof vla);
      |               ^~~~~~
```

四个调用点一个不漏（`diagnostics = 32` 是把内联产生的 `vla_demo.constprop` 变体也算了一遍）。**把它加进 CI 的告警白名单里，就能保证新代码不会再引入不受控的栈分配。**

**（b）连 glibc 自己都不敢对大块用 `alloca`**

glibc 内部（`printf` 这类函数要临时缓冲时会用到）有一套门槛判断：

```c
extern int __libc_use_alloca (size_t size) __attribute__ ((const));
extern int __libc_alloca_cutoff (size_t size) __attribute__ ((const));

#define __MAX_ALLOCA_CUTOFF	65536
```

（`include/alloca.h:18` / `:22`）

也就是说：**glibc 自己在 64 KB 以上就改用 `malloc` 了**。这是很有说服力的旁证 —— `alloca` 的舒适区是**小块、临时、同一函数内**。

## 代码

完整程序见 [`../code/c7_7_alloca.c`](../code/c7_7_alloca.c)：四个实验 —— 地址落在哪个区、循环里会不会回收、VLA 对比、超大分配的后果。

```c
/* Ch7 §7.2 — alloca：栈上分配，函数返回才回收
 * 编译: gcc -O2 -Wall -Wextra -o c7_7_alloca c7_7_alloca.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <signal.h>
#include <alloca.h>
#include <sys/resource.h>
#include <sys/wait.h>

static volatile char g_sink;

/* ── A. alloca 的地址落在哪个区 ── */
static void where_is_alloca(void)
{
    char local[16];
    char *h = malloc(16);
    char *s = alloca(16);

    printf("A. 栈上局部变量 local = %p\n", (void *) local);
    printf("   alloca(16)        = %p   ← 与 local 同区，即栈\n", (void *) s);
    printf("   堆上 malloc(16)   = %p   (与 local 相距 %ld 字节)\n",
           (void *) h, (long) ((char *) h - (char *) local));
    printf("   alloca 与 local 相距 %ld 字节\n\n", (long) (s - local));
    free(h);
}

/* ── B. 循环里 alloca：不会在每次迭代结束回收 ── */
static void alloca_in_loop(void)
{
    printf("B. 循环里 alloca(4096) 五次：\n");
    char *prev = NULL;
    for (int i = 0; i < 5; i++) {
        char *p = alloca(4096);
        memset(p, i, 4096);             /* 防优化：真去碰这块内存 */
        printf("   i=%d  p=%p  与前次相差 %+ld\n", i, (void *) p,
               prev ? (long) (p - prev) : 0L);
        prev = p;
    }
    printf("   → 差值是个固定量：上一轮的块没有被回收。\n");
    printf("     alloca 只挪 sp，回收要等整个函数返回时一次性弹回。\n");
    printf("     （栈向低地址增长，所以差值是负的；多出的部分是对齐开销。）\n\n");
}

/* ── C. alloca 超大 → 直接 SIGSEGV，没有任何返回值可检查 ── */
static void alloca_huge(void)
{
    size_t mb = 16;                     /* 默认栈只有 8MB */

    printf("C. alloca(%zuMB)，栈只有 8MB ...\n", mb);
    fflush(stdout);

    size_t bytes = mb * 1024 * 1024;
    char *p = alloca(bytes);

    /* 逐页用 volatile 写：否则编译器会把「只写不读」的这段当死代码删掉，
     * 一页都不会真碰到，栈也就永远溢不出去。 */
    volatile char *vp = p;
    for (size_t i = 0; i < bytes; i += 4096)
        vp[i] = 'x';
    g_sink = vp[0];
    printf("   竟然没崩\n");
}

/* ── D. VLA 与 alloca 都在栈上，方向相反 ── */
static void vla_demo(int n)
{
    char vla[n];                        /* C99 VLA，同样在栈上 */
    memset(vla, 'v', sizeof vla);
    char *a = alloca(sizeof vla);
    printf("D. VLA[%d] = %p, alloca 同尺寸 = %p, 相差 %ld\n",
           n, (void *) vla, (void *) a, (long) (a - vla));
    printf("   （都落在栈上；栈向低地址增长，所以后分配的在更低处）\n\n");
}

int main(void)
{
    struct rlimit rl;
    if (getrlimit(RLIMIT_STACK, &rl) == 0) {
        if (rl.rlim_cur == RLIM_INFINITY)
            printf("本进程 RLIMIT_STACK = 不限制\n\n");
        else
            printf("本进程 RLIMIT_STACK = %lu MB\n\n",
                   (unsigned long) (rl.rlim_cur / 1024 / 1024));
    }

    where_is_alloca();
    alloca_in_loop();
    vla_demo(256);

    /* C 段放子进程里跑，父进程负责报告死因 */
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) { alloca_huge(); return 0; }

    int st = 0;
    waitpid(pid, &st, 0);
    if (WIFSIGNALED(st))
        printf("C. 子进程被信号 %d (%s) 杀死 → 栈溢出没有「优雅失败」的途径\n",
               WTERMSIG(st), WTERMSIG(st) == SIGSEGV ? "SIGSEGV" : "?");
    else
        printf("C. 子进程 exit = %d\n", WEXITSTATUS(st));
    return 0;
}
```

编译与运行：

```bash
gcc -O2 -Wall -Wextra -o c7_7_alloca c7_7_alloca.c && ./c7_7_alloca
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
本进程 RLIMIT_STACK = 8 MB

A. 栈上局部变量 local = 0x7ffd2a1c9d60
   alloca(16)        = 0x7ffd2a1c9d40   ← 与 local 同区，即栈
   堆上 malloc(16)   = 0x21a372b0   (与 local 相距 -140724745611952 字节)
   alloca 与 local 相距 -32 字节

B. 循环里 alloca(4096) 五次：
   i=0  p=0x7ffd2a1c8d60  与前次相差 +0
   i=1  p=0x7ffd2a1c7d50  与前次相差 -4112
   i=2  p=0x7ffd2a1c6d40  与前次相差 -4112
   i=3  p=0x7ffd2a1c5d30  与前次相差 -4112
   i=4  p=0x7ffd2a1c4d20  与前次相差 -4112
   → 差值是个固定量：上一轮的块没有被回收。
     alloca 只挪 sp，回收要等整个函数返回时一次性弹回。
     （栈向低地址增长，所以差值是负的；多出的部分是对齐开销。）

D. VLA[256] = 0x7ffd2a1c9c90, alloca 同尺寸 = 0x7ffd2a1c9b80, 相差 -272
   （都落在栈上；栈向低地址增长，所以后分配的在更低处）

C. alloca(16MB)，栈只有 8MB ...
C. 子进程被信号 11 (SIGSEGV) 杀死 → 栈溢出没有「优雅失败」的途径
```

**解读**

1. **A 段一眼看出「在栈上」**：`alloca(16)` 拿到 `0x7ffd2a1c9d40`，和局部变量 `local`（`0x7ffd2a1c9d60`）**同一个 `0x7ffd...` 区间**，只差 32 字节；而 `malloc(16)` 在 `0x21a372b0` —— 两地相差约 **1.4 × 10¹⁴** 字节。这就是「堆在低地址、栈在高地址」的字面形态（见 [6.3](../../chapter-06-processes/notes/6.3-address-space-process.md)）。
   - `alloca` 与 `local` 相差 **−32**：负数说明**向低地址**（x86-64 栈向下长），32 是 `alloca` 的对齐调整量。
2. **B 段的 −4112 是本节最值得记的数字**：4096 是请求量，多出的 16 是对齐开销。五次迭代**一次都没回收** —— 这就是「回收粒度是函数返回」的实测形态。若把 5 换成 100000，在 8 MB 栈上就会中途崩掉。
3. **D 段证明 VLA 与 `alloca` 同为栈分配**：`VLA[256]` 与 `alloca(256)` 相差 **−272**，两者都在 `0x7ffd...` 区间。272 = 256 + 16 的对齐与临时变量开销。
4. **C 段是「没有错误检查」的实证**：16 MB > `RLIMIT_STACK`（8 MB），子进程被 **信号 11** 杀死。对比 `malloc(16MB)` —— 那个会**成功返回**（虚拟地址而已，物理页欠着，实测见 [6.4](../../chapter-06-processes/notes/6.4-virtual-memory.md)：`malloc(128MB)` 后 RSS 只涨 0.1 MB），根本不会崩。这是两种分配方式最根本的分野。
5. 为什么 C 段要放进子进程：栈溢出会杀掉整个进程，父进程负责 `wait` 并报告 `WTERMSIG`，这样「死因」还能被打印出来（同样的手法见 [6.5 的爆栈实验](../../chapter-06-processes/notes/6.5-stack-frames.md)）。
6. 为什么 C 段要**逐页用 `volatile` 写**：`alloca` 只挪 `rsp`，若不真去碰内存，GCC 会把这个「只分配不使用」的调用当成死代码删掉 —— 一页都不碰，栈自然也溢不出去。这一点调试时很容易被误导。

## HFT / 嵌入式关联

- **`alloca` 是「确定性分配」**：一条 `sub rsp` 指令，没有锁、没有 bin 搜索、没有系统调用 —— 延迟是可预测的常量。这是它对 HFT 唯一的吸引力。
- **但它把风险从「运行期失败」换成了「崩溃」**：`malloc` 失败你能降级（拒绝这笔报单），`alloca` 失败直接 `SIGSEGV` 丢掉整个进程。在交易系统里后者通常更不可接受，所以**热路径的常见做法是预分配固定池**，而不是 `alloca`。
- **栈大小是被线程限定的**：主线程用 `RLIMIT_STACK`（默认 8 MB），**每个新线程的栈默认只有 8 MB 甚至更小**（`pthread_attr_setstacksize` 可调）。在多线程里用 `alloca` 要按**那个线程的栈**算，别按主线程的算。
- **嵌入式**：很多小型工具链**根本没有 `alloca`**（非 GCC 系）。而且任务是长期运行的，一次栈溢出的后果比一次 `malloc` 失败严重得多 —— 所以嵌入式代码里 `alloca` 更是罕见。
- **例外**：`alloca` 在**信号处理器**里是危险动作（信号可能在任何栈深度上到达），TLPI 在讲信号时专门提过。若信号处理器需要缓冲，用静态缓冲区或 `sigaltstack`。

## 自测题

<details>
<summary>1. `alloca(4096)` 在循环里跑 1000 次，会怎样？</summary>

**栈上会累积 1000 × 4112 ≈ 4 MB，一路不回收** —— 因为 `alloca` 的回收粒度是**函数返回**，不是循环体结束、也不是作用域结束。

实测（5 次迭代）：每次固定下移 4112 字节（4096 请求 + 16 对齐开销）。

在 8 MB 栈上跑 1000 次就会中途撞进 guard page → **`SIGSEGV`**。而且**没有任何办法提前知道**（没有返回值、没有 `errno`）。

正确做法：把 `alloca` 挪到循环外（分配一次，复用它），或者改用 `malloc` / 固定大小的栈上数组。
</details>

<details>
<summary>2. 为什么 `alloca` 失败时不返回 `NULL`？</summary>

因为它**根本不是函数调用**。glibc 把它映射成 GCC 的 `__builtin_alloca`（`stdlib/alloca.h:35`），编译器直接生成「调整 `rsp`」的指令序列 —— 没有函数体、没有返回值路径，自然也没有检查失败的机会。

后果：栈不够时，新的 `rsp` 会落在内核为栈预留的 **guard page** 上。硬件在真正访问时发现页不可读写 → 触发页错误 → 内核送 **SIGSEGV**。

对比 `malloc`：堆的上限可以检查（`sbrk` 返回 `-1`），所以 `malloc` 有失败路径。**这就是「栈分配快但不安全」的本质**。
</details>

<details>
<summary>3. glibc 自己在 64 KB 以上就不敢用 `alloca` 了，这说明什么？</summary>

看 `include/alloca.h:18/:22`：

```c
extern int __libc_use_alloca (size_t size) __attribute__ ((const));
#define __MAX_ALLOCA_CUTOFF	65536
```

`printf` 这类需要临时缓冲的 glibc 函数，会先用 `__libc_use_alloca(size)` 判断：**size 超过 64 KB 就走 `malloc`**。

这说明两点：

1. **`alloca` 的甜区是「小块 + 临时 + 同一函数内」** —— 大到一定程度，栈溢出的风险就压过了「快」的收益，连 libc 作者都选择退回到 `malloc`。
2. 它给了一个**保守的工程阈值参考**：你自己写代码时，若某个 `alloca` 的尺寸可能超过几 KB 且来源不可控，就该考虑换方案。
