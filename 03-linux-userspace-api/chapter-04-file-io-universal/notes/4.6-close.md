## 本节讲什么

`close()` 释放 fd。本节回答三个问题：

1. `close()` 在内核里到底做了什么？为什么「不可重启」？
2. 引用计数（`f_count`）在其中起什么作用？
3. 什么时候**必须**检查 `close()` 的返回值？

---

## 1. 原型与内核链路

```c
#include <unistd.h>
int close(int fd);
/* 成功返回 0；失败返回 -1 并设 errno */
```

```
用户态 close(fd)
      ▼
SYSCALL_DEFINE1(close)            fs/open.c:1557
      ├─→ close_fd_get_file(fd)  ← 从 fd 表取出并清空该槽位
      │     （fd 无效 → 返回 -EBADF）
      ├─→ filp_flush(file, ...)  ← 刷内核缓冲、处理延迟错误
      └─→ __fput_sync(file)      ← 引用计数减一，归零则释放 struct file
```

关键源码（`fs/open.c:1557-1577`）：

```c
SYSCALL_DEFINE1(close, unsigned int, fd)
{
	int retval;
	struct file *file;

	file = close_fd_get_file(fd);
	if (!file)
		return -EBADF;

	retval = filp_flush(file, current->files);
	__fput_sync(file);

	/* 不能重启 close：fd 表项已经清掉了 */
	if (unlikely(retval == -ERESTARTSYS || retval == -ERESTARTNOINTR ||
		     retval == -ERESTARTNOHAND || retval == -ERESTART_RESTARTBLOCK))
		retval = -EINTR;

	return retval;
}
```

## 2. 为什么 close 不可重启

普通 `read`/`write` 被信号打断会返回 `ERESTARTSYS`，内核在返回用户态时**自动重启**该系统调用。但 `close` 不能这么做：

> `close_fd_get_file()` 在第一步就把 fd 表项**清空**了。如果信号打断了 `filp_flush` 再重启，第二次进来时 fd 已经不存在，会得到 `-EBADF`——语义就错了。所以内核把 `ERESTARTSYS` 等一律转成 `-EINTR`，明确告诉用户「这次关闭**没有完成**，但 fd 已经释放，别再重试了」。

这也是 `close` 一个隐蔽陷阱：**收到 `EINTR` 时 fd 状态是不确定的**（Linux 上通常已关闭），不能简单地「重试 close」，否则可能误关一个已被复用给其他文件的同号 fd。

## 3. 引用计数：close ≠ 真正释放

`close` 只是把 fd 表项清空 + `f_count` 减一。`struct file` 真正的释放在引用计数归零时才发生：

| 操作 | 对 `f_count` 的影响 |
|------|-------------------|
| `open()` | 新建 `struct file`，`f_count = 1` |
| `dup()`/`dup2()` | 复制 fd，`f_count++`（共享同一 `struct file`） |
| `fork()` | 子进程继承 fd 表，`f_count++` |
| `close()` | `f_count--`；归零 → 调用 `f_op->release` 释放 |

所以「close 一个 fd」不等于「文件被关闭」——只要还有其他 fd（或子进程）引用着同一个 `struct file`，文件就还开着，偏移也还共享。这就是 Ch5 三层结构的核心。

## 4. 什么时候必须检查 close 的返回值

| 场景 | 是否检查 |
|------|---------|
| 普通本地文件 | 通常可不检查（但最佳实践是检查） |
| **网络文件系统（NFS）** | **必须检查**——写失败可能延迟到 close 才报 |
| 带缓冲的 stdio | `fclose` 前先 `fflush`/`fsync`，`fclose` 失败要处理 |

NFS 上 `write` 可能先成功（进客户端缓存），真正的网络写错误延迟到 `close` 时才返回，所以「`write` 没报错」不代表「数据安全落地」。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| fd 泄漏 | 长驻进程不 `close`，fd 一直占着直到 `ulimit -n` 耗尽 → 无法开新文件/socket |
| 误关复用 fd | 多线程里一个线程 `close` 后，另一个线程 `open` 可能复用同号 fd，再被误关——经典竞态 |
| `O_CLOEXEC` 防泄漏 | `exec` 时自动关 fd，避免子程序继承不该有的句柄 |
| 崩溃一致性 | `close` 不保证落盘；关键数据先 `fsync` 再 `close` |

## 6. 代码示例

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/demo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }

    write(fd, "data", 4);

    /* 关键数据：先 fsync 再 close，保证落盘 */
    if (fsync(fd) < 0) perror("fsync");
    if (close(fd) < 0) perror("close");   /* 检查 close 返回值 */
    return 0;
}
```

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`close()` 的作用是什么？进程退出时未关闭的 fd 会怎样？**
A：`close` 清空 fd 表项并让引用计数减一，归零才真正释放 `struct file`。进程退出时 `exit_files()` 会逐个 `fput` 所有 fd，所以正常退出不会永久泄漏；但长驻进程不 `close` 会一直占着句柄，直到进程结束。

**Q2：为什么 `close` 收到 `EINTR` 后不能简单重试？**
A：因为 `close_fd_get_file` 已经先把 fd 表项清空了。若重试，该 fd 号可能已被其他线程的 `open` 复用，重试 `close(fd)` 会误关别人的文件。收到 `EINTR` 时应把 fd 视为「已释放」，不再重试。

**Q3：为什么 NFS 场景必须检查 `close()` 的返回值？**
A：NFS 的写错误可能延迟到 `close` 时才返回（`filp_flush` 触发真正的网络 flush）。`write` 成功只是写进客户端缓存，`close` 才可能报出 `EIO`/`ENOSPC`。漏查会让「数据没写进去」被误判成成功。

**Q4：`close(fd)` 后，同一个 `struct file` 一定被释放了吗？**
A：不一定。`close` 只让 `f_count` 减一；只有引用计数归零才释放。如果之前 `dup` 过、或 `fork` 出的子进程还持有同一 `struct file`，那它仍然活着，偏移也仍被共享。

**Q5：`close` 能保证数据写到磁盘吗？**
A：不能。`close` 只负责释放 fd 和刷内核缓冲，不保证物理落盘。要持久化必须 `fsync`/`fdatasync`（且顺序是「先 fsync 再 close」）。忘记这点会导致「以为 close 了数据就安全了」的断电丢数据事故。

</details>
