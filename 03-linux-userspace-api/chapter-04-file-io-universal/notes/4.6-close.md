## 本节讲什么

`close()` 释放 fd。本节回答三个问题：

1. `close()` 在内核里到底做了什么？为什么「不可重启」？
2. 引用计数（`f_count`）在其中起什么作用？
3. 什么时候**必须**检查 `close()` 的返回值？

本节有条实测结论很重要：**`close` 之后 fd 号会被立刻回收**——这意味着「继续用旧 fd」不会报错，只会静默操作到**别人**的文件上。这是多线程程序里的经典事故。

---

## 1. 原型与内核链路

```c
#include <unistd.h>
int close(int fd);
/* 成功返回 0；失败返回 -1 并设 errno */
```

`close` 的**逐字全文**（`fs/open.c:1557-1584`，v6.6）：

```c
SYSCALL_DEFINE1(close, unsigned int, fd)
{
	int retval;
	struct file *file;

	file = close_fd_get_file(fd);
	if (!file)
		return -EBADF;

	retval = filp_flush(file, current->files);

	/*
	 * We're returning to user space. Don't bother
	 * with any delayed fput() cases.
	 */
	__fput_sync(file);

	/* can't restart close syscall because file table entry was cleared */
	if (unlikely(retval == -ERESTARTSYS ||
		     retval == -ERESTARTNOINTR ||
		     retval == -ERESTARTNOHAND ||
		     retval == -ERESTART_RESTARTBLOCK))
		retval = -EINTR;

	return retval;
}
```

三步：

| 步骤 | 做什么 |
|------|--------|
| `close_fd_get_file(fd)` | 从 fd 表**取出并清空**该槽位；fd 无效 → `-EBADF` |
| `filp_flush(file, ...)` | 刷内核缓冲、处理延迟错误（NFS 的写错误可能这时才报） |
| `__fput_sync(file)` | 引用计数减一，归零则释放 `struct file` |

## 2. 为什么 close 不可重启

普通 `read`/`write` 被信号打断会返回 `ERESTARTSYS`，内核在返回用户态时**自动重启**该系统调用。但 `close` 不能这么做，内核注释写得很直白：

```c
	/* can't restart close syscall because file table entry was cleared */
```

`close_fd_get_file()` 在第一步就把 fd 表项**清空**了。如果信号打断了 `filp_flush` 再重启，第二次进来时 fd 已经不存在，会得到 `-EBADF`——语义就错了。所以内核把 `ERESTARTSYS` 等一律转成 `-EINTR`，明确告诉用户「这次关闭**没有完成**，但 fd 已经释放，别再重试了」。

这也是 `close` 一个隐蔽陷阱：**收到 `EINTR` 时 fd 状态是不确定的**（Linux 上通常已关闭），不能简单地「重试 close」，否则可能误关一个已被复用给其他文件的同号 fd。

## 3. 引用计数：close ≠ 真正释放

`close` 只是把 fd 表项清空 + `f_count`（`include/linux/fs.h:1005`）减一。`struct file` 真正的释放在引用计数归零时才发生：

| 操作 | 对 `f_count` 的影响 |
|------|-------------------|
| `open()` | 新建 `struct file`，`f_count = 1` |
| `dup()`/`dup2()` | 复制 fd，`f_count++`（共享同一 `struct file`） |
| `fork()` | 子进程继承 fd 表，`f_count++` |
| `close()` | `f_count--`；归零 → 调用 `f_op->release` 释放 |

所以「close 一个 fd」不等于「文件被关闭」——只要还有其他 fd（或子进程）引用着同一个 `struct file`，文件就还开着，偏移也还共享。这就是 Ch5 三层结构的核心。

## 4. 代码：四组实测

完整源码 [`code/c4_6_close.c`](../code/c4_6_close.c)：

```c
/* c4_6_close.c — close() 的三个真相：回收 fd 号、减引用计数、不保证落盘
 *
 * 演示四件事：
 *   1) close 之后那个 fd 号立刻可被复用（所以「用旧 fd」是致命错误）
 *   2) 重复 close / close 非法 fd -> EBADF
 *   3) dup 出来的两个 fd 共用一个「打开文件描述」，close 一个不影响另一个
 *   4) fork 之后父子共享同一个打开描述（引用计数 +1）
 *
 * 编译: gcc -O0 -Wall -o c4_6_close c4_6_close.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/wait.h>

int main(void)
{
    char c;
    const char *path = "/tmp/c4_close.txt";

    printf("== 1. close 后 fd 号立即被回收 ==\n");
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
    write(fd, "ABCDEFGHIJ", 10);
    printf("  打开 -> fd=%d\n", fd);
    close(fd);
    printf("  close(%d) 完成\n", fd);

    int other = open(path, O_RDONLY);
    printf("  再打开同一个文件 -> fd=%d  （%s）\n", other,
           other == fd ? "复用了刚释放的号" : "没复用");
    printf("  ⚠️ 此刻若还用旧的 fd=%d 去读写，操作的是「other」这个文件\n", fd);
    printf("     （内核不会报错——号还是合法的，只是指向变了）。\n");

    printf("\n== 2. close 非法 fd / 重复 close ==\n");
    errno = 0;
    int rc = close(999);
    printf("  close(999) -> %d  errno=%d (%s)\n", rc, errno, strerror(errno));
    errno = 0;
    rc = close(other);
    printf("  close(%d) 第一次 -> %d  errno=%d (%s)\n", other, rc, errno, strerror(errno));
    errno = 0;
    rc = close(other);
    printf("  close(%d) 第二次 -> %d  errno=%d (%s)  ← 重复关闭\n",
           other, rc, errno, strerror(errno));

    printf("\n== 3. dup 共享打开文件描述：close 一个，另一个照用 ==\n");
    int a = open(path, O_RDONLY);
    int b = dup(a);
    printf("  a=%d, dup 得 b=%d（同一个 struct file，引用计数 = 2）\n", a, b);
    lseek(a, 3, SEEK_SET);
    read(a, &c, 1);
    printf("  用 a 读到偏移 3 的 '%c'，此时 a 的偏移 = %ld\n",
           c, (long) lseek(a, 0, SEEK_CUR));
    printf("  用 b 查偏移           = %ld  ← 共享！同一个 f_pos\n",
           (long) lseek(b, 0, SEEK_CUR));
    close(a);
    printf("  close(a) 之后：\n");
    ssize_t rn = read(b, &c, 1);            /* 单独一行：别把有副作用的调用塞进 printf 参数 */
    printf("    用 b 还能读吗？read(b) -> %zd 字节，读到 '%c'\n", rn, c);
    printf("  → close 只是让引用计数减一，没减到 0 就不释放 struct file。\n");
    close(b);

    printf("\n== 4. fork 之后父子的偏移也共享 ==\n");
    int f = open(path, O_RDONLY);
    lseek(f, 0, SEEK_SET);
    pid_t pid = fork();
    if (pid == 0) {
        /* 子进程：继承 f，读 4 字节 */
        char cb[5];
        ssize_t n = read(f, cb, 4);
        cb[n > 0 ? n : 0] = '\0';
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("  子进程读了 4 字节后，父进程里 f 的偏移 = %ld\n",
           (long) lseek(f, 0, SEEK_CUR));
    printf("  → 4，不是 0。fork 复制的是 fd 表，表项指向同一个 struct file。\n");
    printf("    父子共享偏移 = 多进程写同一日志会交错，这才是 O_APPEND 存在的理由。\n");
    close(f);
    unlink(path);
    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c4_6_close c4_6_close.c && ./c4_6_close
```

CE（gcc 13.3.0 / x86-64 / Ubuntu 24.04）实测：

```text
== 1. close 后 fd 号立即被回收 ==
  打开 -> fd=3
  close(3) 完成
  再打开同一个文件 -> fd=3  （复用了刚释放的号）
  ⚠️ 此刻若还用旧的 fd=3 去读写，操作的是「other」这个文件
     （内核不会报错——号还是合法的，只是指向变了）。

== 2. close 非法 fd / 重复 close ==
  close(999) -> -1  errno=9 (Bad file descriptor)
  close(3) 第一次 -> 0  errno=0 (Success)
  close(3) 第二次 -> -1  errno=9 (Bad file descriptor)  ← 重复关闭

== 3. dup 共享打开文件描述：close 一个，另一个照用 ==
  a=3, dup 得 b=4（同一个 struct file，引用计数 = 2）
  用 a 读到偏移 3 的 'D'，此时 a 的偏移 = 4
  用 b 查偏移           = 4  ← 共享！同一个 f_pos
  close(a) 之后：
    用 b 还能读吗？read(b) -> 1 字节，读到 'E'
  → close 只是让引用计数减一，没减到 0 就不释放 struct file。

== 4. fork 之后父子的偏移也共享 ==
  子进程读了 4 字节后，父进程里 f 的偏移 = 4
  → 4，不是 0。fork 复制的是 fd 表，表项指向同一个 struct file。
    父子共享偏移 = 多进程写同一日志会交错，这才是 O_APPEND 存在的理由。
```

逐条看：

| 观察 | 说明 |
|------|------|
| `close(3)` 后新 `open` 又得 `3` | fd 号**立即**回收到位图。所以「旧的 fd 值」在 close 之后随时可能指向**另一个**打开文件 |
| `close(999)` → `EBADF` | 没打开过的号报错。`close` 只看「这个槽位现在有没有东西」 |
| `close(3)` 第一次 → `0`，第二次 → `EBADF` | 重复关闭同一个 fd 会在第二次失败——**`close` 不是幂等的**。所以「`close` 失败就重试」是错误写法 |
| `dup` 后 `b` 查到偏移 4 | **`dup` 共享 `f_pos`**。用 `a` 读了一个字节，`b` 看到的偏移也前进——因为它们指向**同一个 `struct file`** |
| `close(a)` 后 `b` 仍能读 | `f_count` 从 2 减到 1，`struct file` 没被释放。`b` 继续从偏移 4 读到 `'E'` |
| fork 后父进程偏移 = 4 | 子进程读了 4 字节，父进程看到偏移也是 4。**fork 复制 fd 表，但表项指针原样复制** |

> **「关错文件」的风险是推演，不是本 demo 的直接观测**——但第 1 节的实测已经给出了它成立的前提（fd 号被立即回收）。完整时间线是：`close(old)` → 同进程另一处 `open()` 拿到同一个号 → 你因为没把变量置 `-1`，又 `close(old)` → **这次会成功返回 0，但关掉的是别人的打开文件**。本 demo 没构造多线程场景，所以只把前提摆出来；结论是「关闭后立刻把 fd 变量置 `-1`」这条纪律为什么必要。

## 5. 什么时候必须检查 close 的返回值

| 场景 | 是否检查 |
|------|---------|
| 普通本地文件 | 通常可不检查（但最佳实践是检查） |
| **网络文件系统（NFS）** | **必须检查**——写失败可能延迟到 close 才报 |
| 带缓冲的 stdio | `fclose` 前先 `fflush`/`fsync`，`fclose` 失败要处理 |

NFS 上 `write` 可能先成功（进客户端缓存），真正的网络写错误延迟到 `close` 时才返回，所以「`write` 没报错」不代表「数据安全落地」。

## 6. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| fd 泄漏 | 长驻进程不 `close`，fd 一直占着直到 `ulimit -n` 耗尽 → 无法开新文件/socket |
| 误关复用 fd | 多线程里一个线程 `close` 后，另一个线程 `open` 可能复用同号 fd，再被误关——**实测证明复用是立即发生的**，这不是理论风险 |
| `O_CLOEXEC` 防泄漏 | `exec` 时自动关 fd，避免子程序继承不该有的句柄 |
| 崩溃一致性 | `close` 不保证落盘；关键数据先 `fsync` 再 `close` |
| 引用计数决定生命周期 | 父子进程/多 fd 共享时，要算清 `f_count` 才能知道资源何时真正释放 |

<summary>代码自测（Q&A）</summary>

**Q1：`close()` 的作用是什么？进程退出时未关闭的 fd 会怎样？**
A：`close` 清空 fd 表项并让引用计数减一，归零才真正释放 `struct file`。进程退出时 `exit_files()` 会逐个 `fput` 所有 fd，所以正常退出不会永久泄漏；但长驻进程不 `close` 会一直占着句柄，直到进程结束。

**Q2：为什么 `close` 收到 `EINTR` 后不能简单重试？**
A：因为 `close_fd_get_file` 已经先把 fd 表项清空了（内核注释：`can't restart close syscall because file table entry was cleared`）。若重试，该 fd 号可能已被其他线程的 `open` 复用，重试 `close(fd)` 会误关别人的文件。收到 `EINTR` 时应把 fd 视为「已释放」，不再重试。

**Q3：为什么 NFS 场景必须检查 `close()` 的返回值？**
A：NFS 的写错误可能延迟到 `close` 时才返回（`filp_flush` 触发真正的网络 flush）。`write` 成功只是写进客户端缓存，`close` 才可能报出 `EIO`/`ENOSPC`。漏查会让「数据没写进去」被误判成成功。

**Q4：`close(fd)` 后，同一个 `struct file` 一定被释放了吗？**
A：不一定。`close` 只让 `f_count` 减一；只有引用计数归零才释放。如果之前 `dup` 过、或 `fork` 出的子进程还持有同一 `struct file`，那它仍然活着，偏移也仍被共享（实测：`close(a)` 之后 `b` 照常读）。

**Q5：`close` 能保证数据写到磁盘吗？**
A：不能。`close` 只负责释放 fd 和刷内核缓冲，不保证物理落盘。要持久化必须 `fsync`/`fdatasync`（且顺序是「先 fsync 再 close」）。忘记这点会导致「以为 close 了数据就安全了」的断电丢数据事故。

**Q6：为什么「close 一个已经 close 过的 fd」特别危险？**
A：因为那个号可能已经被别人（同进程的另一个线程，或你自己后续的 `open`）复用。此时 `close` 会**成功返回 0**，但它关掉的是**别人的**打开文件——没有任何错误提示。实测第 1 节展示的「close(3) 后新 open 又拿到 3」正是这个危险的机制来源。防御办法：关闭后立刻把变量置为 `-1`，或用 `O_CLOEXEC` + 明确的所有权约定。

</details>
