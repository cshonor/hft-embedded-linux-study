## 本节讲什么

`ioctl()` 是通用 I/O 模型的「兜底出口」。本节回答三个问题：

1. 为什么 `read/write/lseek` 之外还需要 `ioctl`？
2. 那个神秘的 `request` 参数是怎么编码「方向 + 大小 + 编号」的？
3. 一个 `ioctl` 从用户态到设备驱动走的是哪条路？

---

## 1. 原型与定位

```c
#include <sys/ioctl.h>
int ioctl(int fd, int request, ...);   /* 可变参数：驱动自定义的结构体指针 */
/* 成功返回 0（或自定义值）；失败 -1 并设 errno */
```

`ioctl` 处理的是「**字节流之外的控制**」：设置终端窗口、查询磁盘几何、配置网卡混杂模式——这些没有对应的 `read/write` 语义，只能靠一个「命令字 + 数据指针」的万能接口。

```
用户态 ioctl(fd, request, &arg)
      ▼
SYSCALL_DEFINE3(ioctl)                （fs/ioctl.c）
      ▼
do_vfs_ioctl(filp, fd, cmd, arg)      （通用命令在此统一处理）
      ├─→ 若是通用命令（FIOCLEX/FIONBIO/FIONREAD…）直接处理
      └─→ 否则分派：file->f_op->unlocked_ioctl(filp, cmd, arg)
              │
              ▼
          驱动 switch(cmd) { case MY_CMD: ... }   ← 设备专属逻辑
```

与 `read/write` 一样，差异被 `f_op->unlocked_ioctl` 吸收——但这次连「命令语义」都是设备自定义的，VFS 层完全不理解 `request` 的含义，只负责透传。

## 2. `request` 的编码：`_IO/_IOR/_IOW/_IOWR`

`request` 是一个 32 位整数，四个字段按位打包（`include/uapi/asm-generic/ioctl.h`）：

```
 31                 16 15         8  7        0
┌────────────────────┬─────────────┬──────────┐
│      size          │   type/magic │   nr     │
│  (arg 数据字节数)   │  (设备类别号) │ (命令号)  │
└────────────────────┴─────────────┴──────────┘
 + 2 位 direction（读写方向）
```

生成命令字用这几个宏（由驱动头文件定义好）：

| 宏 | 方向 | 含义 |
|----|------|------|
| `_IO(type, nr)` | 无数据 | 纯命令，无参数 |
| `_IOR(type, nr, datatype)` | 内核 → 用户（读） | 内核写数据给用户 |
| `_IOW(type, nr, datatype)` | 用户 → 内核（写） | 用户传数据给内核 |
| `_IOWR(type, nr, datatype)` | 双向 | 读写都有 |

`type` 是 8 位「魔法数」标识设备类别（如 `'T'` 代表 tty），`nr` 是命令序号，`datatype` 告诉内核参数的大小（用于 `copy_from_user`/`copy_to_user` 时校验边界）。

## 3. 示例：查终端窗口大小（`TIOCGWINSZ`）

窗口行列数是「字节流」表达不了的，只能 `ioctl`：

```c
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <termios.h>    /* struct winsize */
#include <stdio.h>

int main(void) {
    struct winsize ws;
    if (ioctl(STDIN_FILENO, TIOCGWINSZ, &ws) == 0) {
        printf("终端: %d 行 x %d 列\n", ws.ws_row, ws.ws_col);
    } else {
        perror("ioctl TIOCGWINSZ");
        printf("（非终端环境，如管道/重定向）\n");
    }
    return 0;
}
```

`TIOCGWINSZ` 是 `_IOR('T', 104, struct winsize)`——「tty 设备、读方向、参数是 `struct winsize`」。

## 4. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 设备专属控制 | 嵌入式点灯、读传感器、配寄存器：驱动实现 `unlocked_ioctl`，用户态用 `ioctl` 下发命令 |
| 网卡 offload / 硬件时间戳 | `ioctl`（或 `setsockopt`）开启网卡硬件时间戳，`read/write` 做不到 |
| 通用命令 | `FIONREAD` 查可读字节数、`FIONBIO` 切非阻塞——这些是 `ioctl` 里少数「通用」命令 |
| 类型安全靠约定 | `request` 编码靠「魔法数 + 大小」防错，但仍是约定式，传错结构体会静默出错 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：为什么有了 `read/write/lseek` 还要 `ioctl`？**
A：因为「字节流」语义覆盖不了「控制/查询」类操作。设置终端窗口大小、查询磁盘扇区数、配置网卡——这些不是「搬一段字节」，没有对应的 `read/write` 动词。`ioctl` 用「命令字 + 数据指针」提供了一个万能兜底，让设备能暴露任意自定义操作。

**Q2：`request` 参数里为什么要编码 `size`（数据大小）？**
A：为了安全。`ioctl` 的可变参数是用户态指针，内核在 `unlocked_ioctl` 里要 `copy_from_user`/`copy_to_user`。`request` 里的 `size` 字段让内核知道要拷贝多少字节，避免越界；`_IOR`/`_IOW` 宏用 `sizeof(datatype)` 自动填入这个大小。

**Q3：`ioctl` 和普通文件（非设备）搭配会怎样？**
A：普通文件通常没实现对应命令，多数返回 `-ENOTTY`（「not a typewriter」，历史遗留错误名，意为「该对象不支持此 ioctl」）。`isatty()` 就是靠探测 `TCGETS` 这类命令来判断 fd 是不是终端的。

**Q4：`_IOR` 和 `_IOW` 的「方向」有什么实际作用？**
A：它告诉内核数据流向，内核据此决定 `copy_from_user`（用户→内核）还是 `copy_to_user`（内核→用户），并在部分架构上做校验。方向写错会导致数据没按预期拷贝——这是驱动 bug 的常见来源。

**Q5：`ioctl` 的返回值一定是 0/1 吗？**
A：不。`ioctl` 失败返回 `-1` 并设 `errno`，但成功时的返回值由驱动自定义（多数返回 0，也可能返回有意义的值）。所以不能用「返回值 == 某个正数」当成功判据，标准写法是 `if (ioctl(...) == -1) 出错`。

</details>
