## 本节讲什么

`ioctl()` 是通用 I/O 模型的「兜底出口」。本节回答四个问题：

1. 为什么 `read/write/lseek` 之外还需要 `ioctl`？它在内核里走哪条路？
2. `request` 那个 32 位整数是怎么编码「方向 + 大小 + 类型 + 编号」的？
3. `ENOTTY` 到底是什么错误？内核里它有几个来源？
4. `isatty()`、`FIONREAD`、`FIONBIO` 这些「通用能力」在源码里长什么样？

本节还有一个**实测纠正**：`TIOCGWINSZ` 这个最常见的 ioctl 例子，**并不符合 `_IOR/_IOW` 的编码规范**——`dir` 和 `size` 两位都是 0。网上流传的 `_IOR('T', 104, struct winsize)` 是错的（算出来是 `0x80085468`，真值是 `0x5413`）。

---

## 1. 原型与内核链路

```c
#include <sys/ioctl.h>
int ioctl(int fd, int request, ...);   /* 可变参数：驱动自定义的结构体指针 */
/* 成功返回 0（或驱动自定义值）；失败 -1 并设 errno */
```

`ioctl` 处理的是「**字节流之外的控制**」：查终端窗口大小、配网卡混杂模式、读取设备寄存器——这些没有 `read/write` 语义，只能靠一个「命令字 + 数据指针」的万能接口。

```
用户态 ioctl(fd, cmd, arg)
      ▼
SYSCALL_DEFINE3(ioctl)                    fs/ioctl.c:857
      ├─→ fdget(fd)                       无效 fd → -EBADF
      ├─→ security_file_ioctl()           LSM 钩子
      ▼
do_vfs_ioctl(filp, fd, cmd, arg)          fs/ioctl.c:773  ← 通用命令在此统一处理
      ├─→ 命中通用命令：FIOCLEX / FIONCLEX / FIONBIO / FIONREAD / FIOQSIZE …
      ├─→ default: 普通文件 → file_ioctl() fs/ioctl.c:324
      └─→ break → 返回 -ENOIOCTLCMD
      ▼（返回值是 -ENOIOCTLCMD 时）
vfs_ioctl(filp, cmd, arg)                 fs/ioctl.c:44
      ├─→ 没有 f_op->unlocked_ioctl → 直接 -ENOTTY
      └─→ f_op->unlocked_ioctl(filp, cmd, arg)   ← 驱动 switch(cmd)
              └─→ 驱动返回 -ENOIOCTLCMD → 翻译成 -ENOTTY
```

`SYSCALL_DEFINE3(ioctl, …)` 逐字（`fs/ioctl.c:857-876`，v6.6）：

```c
SYSCALL_DEFINE3(ioctl, unsigned int, fd, unsigned int, cmd, unsigned long, arg)
{
	struct fd f = fdget(fd);
	int error;

	if (!f.file)
		return -EBADF;

	error = security_file_ioctl(f.file, cmd, arg);
	if (error)
		goto out;

	error = do_vfs_ioctl(f.file, fd, cmd, arg);
	if (error == -ENOIOCTLCMD)
		error = vfs_ioctl(f.file, cmd, arg);

out:
	fdput(f);
	return error;
}
```

三层结构说清了一件事：**VFS 只负责「通用命令」和「转发」两件事，它完全不懂你的 `request` 是什么意思**。和 `read/write` 一样，差异被 `f_op->unlocked_ioctl` 吸收——只不过这次连「命令语义」都是设备自定义的。

## 2. `request` 的编码：`_IO / _IOR / _IOW / _IOWR`

`request` 是 32 位整数，四段按位打包（`include/uapi/asm-generic/ioctl.h:5-13` 原文注释）：

```c
/* ioctl command encoding: 32 bits total, command in lower 16 bits,
 * size of the parameter structure in the lower 14 bits of the
 * upper 16 bits.
 * ...
 * The highest 2 bits are reserved for indicating the ``access mode''.
 * NOTE: This limits the max parameter size to 16kB -1 !
 */
```

```
 31   30 29                16 15            8 7             0
┌───────┬───────────────────┬───────────────┬───────────────┐
│ dir   │      size         │  type (magic) │      nr       │
│ 2 bit │     14 bit        │     8 bit     │    8 bit      │
└───────┴───────────────────┴───────────────┴───────────────┘
  读/写     arg 结构体字节数      设备类别号        命令序号
```

位移常量（`include/uapi/asm-generic/ioctl.h:44-47`）：

```c
#define _IOC_NRSHIFT	0
#define _IOC_TYPESHIFT	(_IOC_NRSHIFT+_IOC_NRBITS)      /* 0+8   = 8  */
#define _IOC_SIZESHIFT	(_IOC_TYPESHIFT+_IOC_TYPEBITS)  /* 8+8   = 16 */
#define _IOC_DIRSHIFT	(_IOC_SIZESHIFT+_IOC_SIZEBITS)  /* 16+14 = 30 */
```

宏本体（`include/uapi/asm-generic/ioctl.h:69-73`）：`_IOC(dir,type,nr,size)` 就是四个字段左移后按位或。四个生成宏（`include/uapi/asm-generic/ioctl.h:85-88`）：

| 宏 | 方向位 | 含义 |
|----|--------|------|
| `_IO(type,nr)` | `_IOC_NONE` (0) | 纯命令，无参数 |
| `_IOR(type,nr,size)` | `_IOC_READ` (2) | 用户态**读**：内核 → 用户 |
| `_IOW(type,nr,size)` | `_IOC_WRITE` (1) | 用户态**写**：用户 → 内核 |
| `_IOWR(type,nr,size)` | `READ\|WRITE` (3) | 双向 |

> 注意方向命名的视角坑（`include/uapi/asm-generic/ioctl.h:82-83` 原文注释）：
> `NOTE: _IOW means userland is writing and kernel is reading. _IOR means userland is reading and kernel is writing.`
> ——**站在用户态视角命名**，和「内核读/写」正好相反。

解码宏（`:94-97`）是逆运算，驱动里常用：`_IOC_DIR(nr)` / `_IOC_TYPE(nr)` / `_IOC_NR(nr)` / `_IOC_SIZE(nr)`。

## 3. 实测：`TIOCGWINSZ` 并不符合编码规范

查终端窗口大小是最经典的 ioctl 例子：

```c
struct winsize ws;
ioctl(STDIN_FILENO, TIOCGWINSZ, &ws);   /* 成功则 ws.ws_row / ws.ws_col 有效 */
```

按规范，它「应该」是 `_IOR('T', <nr>, struct winsize)`。但实测把 `0x5413` 按位拆开：

| 字段 | 位 | 实测值 |
|------|----|--------|
| `dir` | 30-31 | **0** ← 既不是 `_IOC_READ`(2) 也不是 `_IOC_WRITE`(1) |
| `size` | 16-29 | **0** ← 不是 `sizeof(struct winsize)` = 8 |
| `type` | 8-15 | 84 = `'T'` ✓ |
| `nr` | 0-7 | 19 = `0x13` |

原因在 `ioctl.h` 隔壁那个文件：**它是硬编码的老式命令字**（`include/uapi/asm-generic/ioctls.h:38`）：

```c
#define TIOCGWINSZ	0x5413
```

`0x5413` 恰好等于 `_IO('T', 0x13)`（无参数写法）——`type='T'` 占 8 位 → `0x54`，`nr=0x13` → `0x13`，`dir`/`size` 都是 0。数值对得上，**但语义是"无参数"**，这就埋了个坑：内核靠的是 `type`/`nr` 路由，`size` 只用于部分架构的边界校验，所以它能工作。

而网上流传的 `_IOR('T', 104, struct winsize)` 算出来是：

```
_IOC(2, 'T', 104, 8) = (2<<30) | ('T'<<8) | (104<<0) | (8<<16)
                     = 0x80000000 | 0x00005400 | 0x68 | 0x00080000
                     = 0x80085468        ← 跟真值 0x5413 完全对不上
```

**那条说法是错的**（`nr` 和 `dir`/`size` 三处都不对）。tty 有一大批命令字沿用 `0x54xx` 这段历史编号（`TCGETS 0x5401`、`TIOCGWINSZ 0x5413`、`FIONREAD 0x541B`、`FIONBIO 0x5421`、`FIOCLEX 0x5451`…），别指望它们都合规。

> 反例：同一文件里的 `TCGETS2` 就是**合规**的——`ioctls.h:61` 写的是 `#define TCGETS2 _IOR('T', 0x2A, struct termios2)`。新命令字才按规范来。

## 4. 实测：`ENOTTY` 的两个来源

`ENOTTY` 的字面意思是 "not a typewriter"（历史遗留），现代含义是「**这个对象不认识这个命令**」。它在内核里有**两条**产生路径，都在 `vfs_ioctl` 里（`fs/ioctl.c:44-56` 逐字）：

```c
long vfs_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
	int error = -ENOTTY;

	if (!filp->f_op->unlocked_ioctl)
		goto out;

	error = filp->f_op->unlocked_ioctl(filp, cmd, arg);
	if (error == -ENOIOCTLCMD)
		error = -ENOTTY;
 out:
	return error;
}
```

| 来源 | 行号 | 条件 |
|------|------|------|
| ① 对象**没有** `unlocked_ioctl` 方法 | `:46` + `:48-49` | 初值 `error = -ENOTTY`，直接 `goto out` |
| ② 对象**有**方法，但驱动说「命令不认识」 | `:52-53` | 驱动返回 `-ENOIOCTLCMD` → 统一翻译成 `-ENOTTY` |

`-ENOIOCTLCMD` 是个**纯内核内部**的哨兵值（`include/linux/errno.h` 里定义为 `-ENOIOCTLCMD 515` 附近的内部错误码），设计目的就是「让驱动表达'这条命令我没实现'，由 VFS 决定对外报什么」。**用户态永远看不到 `ENOIOCTLCMD`**——它是被 `vfs_ioctl` 吃掉、翻译成 `ENOTTY` 的。

实测三种对象：

| 对象 | 请求 | 结果 |
|------|------|------|
| stdout（被 CE 重定向到管道/文件） | `TIOCGWINSZ` | `-1 errno=25 (ENOTTY)` |
| 普通文件（`/tmp/c4_ioctl.txt`） | `TIOCGWINSZ` | `-1 errno=25 (ENOTTY)` |
| 管道（写端关掉后读） | `FIONREAD` | **成功**，返回可读字节数 |

对普通文件，`do_vfs_ioctl` 的 `default:` 分支会先转给 `file_ioctl`（`fs/ioctl.c:324-340`），而它只管 `FIBMAP` / 预分配（`FS_IOC_RESVSP`）/ `FS_IOC_ZERO_RANGE` 这几条，其余返回 `-ENOIOCTLCMD`——于是 `TIOCGWINSZ` 走完 ② 路径变成 `ENOTTY`。

## 5. `isatty()` 的真相：标准库在用 ioctl

`isatty()` 看着像个「系统提供的布尔变量」，实际就是**试一个 tty 专属 ioctl**。glibc 2.39 的完整链路：

```c
/* sysdeps/posix/isatty.c:21-28 —— 逐字 */
/* Return 1 if FD is a terminal, 0 if not.  */
int
__isatty (int fd)
{
  struct termios term;

  return __tcgetattr (fd, &term) == 0;
}

weak_alias (__isatty, isatty)
```

而 `__tcgetattr` 最终落到 `ioctl`（`sysdeps/unix/sysv/linux/tcgetattr.c:33-38` 逐字）：

```c
int
__tcgetattr (int fd, struct termios *termios_p)
{
  struct __kernel_termios k_termios;
  int retval;

  retval = INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios);
```

所以 `isatty(fd) == (ioctl(fd, TCGETS, &k_termios) == 0)`——**成功了就是终端，`ENOTTY` 就不是**。`TCGETS = 0x5401`（`ioctls.h:20`）。

实测（CE 沙箱里 stdin/stdout 都被接管）：

```text
  isatty(STDIN_FILENO)  = 0
  isatty(STDOUT_FILENO) = 0
  isatty(open("/tmp")) = 0
```

三个都是 0 —— 沙箱里没有任何 fd 是终端。

## 6. 通用命令：`FIONREAD` 与 `FIONBIO`

### `FIONREAD`：现在有多少字节可读

它藏在 `do_vfs_ioctl` 的 switch 里（`fs/ioctl.c:829-834` 逐字）：

```c
	case FIONREAD:
		if (!S_ISREG(inode->i_mode))
			return vfs_ioctl(filp, cmd, arg);

		return put_user(i_size_read(inode) - filp->f_pos,
				(int __user *)argp);
```

逻辑分叉很漂亮：

- **普通文件** → 直接算 `i_size - f_pos`，即「文件里还剩多少字节没读」，不用任何设备配合
- **非普通文件**（管道/socket/字符设备）→ `vfs_ioctl` 转发给对象自己的 `unlocked_ioctl`

管道那边就是 `pipe_ioctl`（`fs/pipe.c:608-626` 逐字节选）：

```c
static long pipe_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
	struct pipe_inode_info *pipe = filp->private_data;
	unsigned int count, head, tail, mask;

	switch (cmd) {
	case FIONREAD:
		__pipe_lock(pipe);
		count = 0;
		head = pipe->head;
		tail = pipe->tail;
		mask = pipe->ring_size - 1;

		while (tail != head) {
			count += pipe->bufs[tail & mask].len;
			tail++;
		}
		__pipe_unlock(pipe);

		return put_user(count, (int __user *)arg);
```

它遍历环形缓冲区把各段长度加起来——这是为什么它要加锁。注册点（`fs/pipe.c:1228`）：`.unlocked_ioctl = pipe_ioctl`。

实测：写 9 字节 → `avail=9`；读走 4 字节 → `avail=5`。

### `FIONBIO`：用 ioctl 切非阻塞

`do_vfs_ioctl` 里直接转给 `ioctl_fionbio`（`fs/ioctl.c:342-362` 逐字节选）：

```c
static int ioctl_fionbio(struct file *filp, int __user *argp)
{
	unsigned int flag;
	int on, error;

	error = get_user(on, argp);
	if (error)
		return error;
	flag = O_NONBLOCK;
	...
	spin_lock(&filp->f_lock);
	if (on)
		filp->f_flags |= flag;
	else
		filp->f_flags &= ~flag;
	spin_unlock(&filp->f_lock);
	return error;
}
```

**它就是在 `filp->f_flags` 上置/清 `O_NONBLOCK` 位**——和 `fcntl(fd, F_SETFL, O_NONBLOCK)` 改的是同一个字段、同一个位。所以：

```c
ioctl(fd, FIONBIO, &on);              /* 老式写法，POSIX 之前的风格 */
fcntl(fd, F_SETFL, O_NONBLOCK);       /* 现代写法，语义等价 */
```

区别只在于 `fcntl` 会**重建整份 `f_flags`**（你给什么就是什么），而 `FIONBIO` 只动 `O_NONBLOCK` 一位。实测设为非阻塞后读空管道 → `-1 errno=11 (EAGAIN)`，立刻返回不阻塞。

## 7. 代码：六组实测

完整源码 [`code/c4_8_ioctl.c`](../code/c4_8_ioctl.c)：

```c
/* c4_8_ioctl.c — ioctl()：通用模型之外的「控制通道」
 *
 * 演示五件事：
 *   1) 把 request 整数拆开看：方向 / size / type / nr 四个字段
 *   2) TIOCGWINSZ 查终端窗口大小——stdout 是管道时 ENOTTY
 *   3) isatty() 是怎么实现的（本质就是试一个 tty 专属 ioctl）
 *   4) FIONREAD 查「现在有多少字节可读」（通用命令，管道也能用）
 *   5) FIONBIO 用 ioctl 切非阻塞（与 fcntl 殊途同归，Ch5 详述）
 *
 * 编译: gcc -O0 -Wall -o c4_8_ioctl c4_8_ioctl.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>
#include <sys/ioctl.h>
#include <termios.h>
#include <sys/uio.h>

struct my_winsize { unsigned short ws_row, ws_col, ws_xpixel, ws_ypixel; };

int main(void)
{
    printf("== 1. request 整数里装了什么 ==\n");
    printf("  TIOCGWINSZ = 0x%08lx = %lu\n",
           (unsigned long) TIOCGWINSZ, (unsigned long) TIOCGWINSZ);
    printf("    按 asm-generic/ioctl.h 的位域拆：\n");
    printf("      dir  (2 bit, 位 30-31) = %lu\n",
           ((unsigned long) TIOCGWINSZ >> 30) & 0x3);
    printf("      size (14 bit, 位 16-29) = %lu   ← arg 结构体字节数\n",
           ((unsigned long) TIOCGWINSZ >> 16) & 0x3fff);
    printf("      type (8 bit, 位 8-15)  = %lu = '%c'   ← 设备类别「魔法数」\n",
           ((unsigned long) TIOCGWINSZ >> 8) & 0xff,
           (int) (((unsigned long) TIOCGWINSZ >> 8) & 0xff));
    printf("      nr   (8 bit, 位 0-7)   = %lu (0x%lx)   ← 命令序号\n",
           (unsigned long) TIOCGWINSZ & 0xff, (unsigned long) TIOCGWINSZ & 0xff);

    printf("\n  ⚠️ 注意 dir 和 size 都是 0 —— 它**没有**按 _IOR/_IOW 的规矩编码！\n");
    printf("     TIOCGWINSZ 是 tty 的**老式**命令字，内核里硬编码：\n");
    printf("       include/uapi/asm-generic/ioctls.h:  #define TIOCGWINSZ  0x5413\n");
    printf("     它恰好等于「无参数」写法 _IO('T', 0x13)：\n");
    printf("       _IO('T', 0x13) = 0x%08lx\n", (unsigned long) _IO('T', 0x13));
    printf("     若按网上流传的 `_IOR('T', 104, struct winsize)` 算，得到的是\n");
    printf("       0x%08lx —— 跟真实值对不上。那条说法是错的。\n",
           (unsigned long) _IOR('T', 104, struct my_winsize));
    printf("     tty 的一大批命令字都沿用 0x54xx 这段历史编号，别指望它们都合规。\n");

    printf("\n== 2. TIOCGWINSZ 查窗口大小 ==\n");
    struct winsize ws;
    errno = 0;
    int rc = ioctl(STDOUT_FILENO, TIOCGWINSZ, &ws);
    if (rc == 0 && ws.ws_row != 0)
        printf("  stdout 是终端：%u 行 x %u 列（像素 %u x %u）\n",
               ws.ws_row, ws.ws_col, ws.ws_xpixel, ws.ws_ypixel);
    else
        printf("  ioctl(stdout, TIOCGWINSZ) -> %d  errno=%d (%s)\n"
               "  → stdout 被重定向/接管了，不是终端，所以这个 tty 专属命令不认。\n",
               rc, errno, strerror(errno));

    printf("\n== 3. isatty() 的真相 ==\n");
    printf("  isatty(STDIN_FILENO)  = %d\n", isatty(STDIN_FILENO));
    printf("  isatty(STDOUT_FILENO) = %d\n", isatty(STDOUT_FILENO));
    printf("  isatty(open(\"/tmp\")) = %d\n", isatty(open("/tmp/c4_ioctl.txt", O_CREAT | O_WRONLY, 0644)));
    printf("  → glibc 的 isatty() 内部就是 ioctl(fd, TCGETS, &t)：能成功就是终端，\n");
    printf("    失败(ENOTTY)就不是。标准库把 ioctl 用在了最基础的判断上。\n");

    printf("\n== 4. FIONREAD：现在有多少字节可读 ==\n");
    int p[2];
    pipe(p);
    write(p[1], "123456789", 9);
    int avail = 0;
    rc = ioctl(p[0], FIONREAD, &avail);
    printf("  写 9 字节后 FIONREAD: 返回值=%d, avail=%d\n", rc, avail);
    char tmp[16];
    read(p[0], tmp, 4);
    ioctl(p[0], FIONREAD, &avail);
    printf("  读走 4 字节后再查:     avail=%d  ← 读走多少就少多少\n", avail);
    close(p[0]);
    close(p[1]);

    printf("\n== 5. FIONBIO：用 ioctl 切非阻塞 ==\n");
    int q[2];
    pipe(q);
    int on = 1;
    ioctl(q[0], FIONBIO, &on);                 /* 同 fcntl(q[0], F_SETFL, O_NONBLOCK) */
    errno = 0;
    ssize_t n = read(q[0], tmp, 4);            /* 管道是空的 */
    printf("  设为非阻塞后读空管道 -> %zd  errno=%d (%s)  ← 不阻塞，直接报「稍后再试」\n",
           n, errno, strerror(errno));
    close(q[0]);
    close(q[1]);

    printf("\n== 6. 普通文件上的 ioctl：ENOTTY ==\n");
    int f = open("/tmp/c4_ioctl.txt", O_RDONLY);
    errno = 0;
    rc = ioctl(f, TIOCGWINSZ, &ws);
    printf("  ioctl(普通文件, TIOCGWINSZ) -> %d  errno=%d (%s)\n",
           rc, errno, strerror(errno));
    printf("  → ENOTTY 的字面是 \"not a typewriter\"，历史遗留；\n");
    printf("    现代含义是「这个对象不认识这个命令」。\n");
    close(f);
    unlink("/tmp/c4_ioctl.txt");
    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c4_8_ioctl c4_8_ioctl.c && ./c4_8_ioctl
```

CE（gcc 13.3.0 / x86-64 / Ubuntu 24.04）实测：

```text
== 1. request 整数里装了什么 ==
  TIOCGWINSZ = 0x00005413 = 21523
    按 asm-generic/ioctl.h 的位域拆：
      dir  (2 bit, 位 30-31) = 0
      size (14 bit, 位 16-29) = 0   ← arg 结构体字节数
      type (8 bit, 位 8-15)  = 84 = 'T'   ← 设备类别「魔法数」
      nr   (8 bit, 位 0-7)   = 19 (0x13)   ← 命令序号

  ⚠️ 注意 dir 和 size 都是 0 —— 它**没有**按 _IOR/_IOW 的规矩编码！
     TIOCGWINSZ 是 tty 的**老式**命令字，内核里硬编码：
       include/uapi/asm-generic/ioctls.h:  #define TIOCGWINSZ  0x5413
     它恰好等于「无参数」写法 _IO('T', 0x13)：
       _IO('T', 0x13) = 0x00005413
     若按网上流传的 `_IOR('T', 104, struct winsize)` 算，得到的是
       0x80085468 —— 跟真实值对不上。那条说法是错的。
     tty 的一大批命令字都沿用 0x54xx 这段历史编号，别指望它们都合规。

== 2. TIOCGWINSZ 查窗口大小 ==
  ioctl(stdout, TIOCGWINSZ) -> -1  errno=25 (Inappropriate ioctl for device)
  → stdout 被重定向/接管了，不是终端，所以这个 tty 专属命令不认。

== 3. isatty() 的真相 ==
  isatty(STDIN_FILENO)  = 0
  isatty(STDOUT_FILENO) = 0
  isatty(open("/tmp")) = 0
  → glibc 的 isatty() 内部就是 ioctl(fd, TCGETS, &t)：能成功就是终端，
    失败(ENOTTY)就不是。标准库把 ioctl 用在了最基础的判断上。

== 4. FIONREAD：现在有多少字节可读 ==
  写 9 字节后 FIONREAD: 返回值=0, avail=9
  读走 4 字节后再查:     avail=5  ← 读走多少就少多少

== 5. FIONBIO：用 ioctl 切非阻塞 ==
  设为非阻塞后读空管道 -> -1  errno=11 (Resource temporarily unavailable)  ← 不阻塞，直接报「稍后再试」

== 6. 普通文件上的 ioctl：ENOTTY ==
  ioctl(普通文件, TIOCGWINSZ) -> -1  errno=25 (Inappropriate ioctl for device)
  → ENOTTY 的字面是 "not a typewriter"，历史遗留；
    现代含义是「这个对象不认识这个命令」。
```

逐条看：

| 观察 | 说明 |
|------|------|
| `dir = 0`、`size = 0` | `TIOCGWINSZ` **不合编码规范**。`type='T'` 和 `nr=0x13` 对上，说明路由靠这两个字段 |
| `_IO('T', 0x13) = 0x00005413` | 数值与 `TIOCGWINSZ` 完全相同——它是「老式无参数命令字」，不是「读 `struct winsize`」 |
| `_IOR('T',104,…)` = `0x80085468` ≠ `0x5413` | 网上流传的写法是错的。三处都不对：`dir`、`size`、`nr` |
| `ioctl(stdout, TIOCGWINSZ)` → `ENOTTY` | CE 里 stdout 被重定向成管道/文件，不是 tty——**同一份代码在本地终端会成功** |
| 三个 `isatty()` 全是 `0` | glibc 内部试 `TCGETS`；没有 tty 就全失败。终端程序里 `isatty(fd)` 是最常用的「是交互式吗」判断 |
| `FIONREAD` 返回值 = 0，`avail` = 9 | `ioctl` 的**返回值**和它写回的**数据**是两件事。返回值 0 表示命令成功，9 在 `avail` 里 |
| 读走 4 → `avail=5` | 管道自己维护环形缓冲区的各段长度，`FIONREAD` 现场遍历求和 |
| `FIONBIO` 后读空管道 → `EAGAIN` | 不阻塞，立刻告诉「现在没数据，稍后再来」。这是事件循环/非阻塞 IO 的基石 |
| 普通文件 `TIOCGWINSZ` → `ENOTTY` | 走 ② 路径：`file_ioctl` 不认识这条命令 → `-ENOIOCTLCMD` → 翻译成 `-ENOTTY` |

## 8. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 设备专属控制 | 嵌入式点灯、读传感器、配寄存器：驱动实现 `unlocked_ioctl`，用户态用 `ioctl` 下发命令字。「读寄存器」不是字节流语义，只能走 ioctl |
| 网卡 offload / 硬件时间戳 | `SIOCSHWTSTAMP` 之类的 ioctl 开启网卡硬件时间戳——`read/write` 做不到 |
| `FIONREAD` 做「有没有数据」预检 | 事件循环里想「不阻塞地看一眼有没有数据」，`ioctl(fd, FIONREAD, &n)` 比先 `read` 再回退更干净（流对象根本不能回退） |
| `FIONBIO` 与 `fcntl` 同源 | 两者都改 `filp->f_flags` 的 `O_NONBLOCK` 位。混用不会冲突，但别指望它们是两套独立状态 |
| `_IOR/_IOW` 的方向是**用户态视角** | 驱动里写 `copy_from_user` / `copy_to_user` 时方向搞反是经典 bug 源。看到 `_IOW` 要读成「用户写给内核」 |
| 命令字必须全局唯一 | `type`（魔法数）冲突会让两条命令互相打架。Linux 内核 `Documentation/userspace-api/ioctl/ioctl-number.rst` 维护着已分配的魔法数表 |

<summary>代码自测（Q&A）</summary>

**Q1：为什么有了 `read/write/lseek` 还要 `ioctl`？**
A：因为「字节流」语义覆盖不了「控制/查询」类操作。设置终端窗口大小、查询设备寄存器、配网卡混杂模式——这些不是「搬一段字节」，没有对应的 `read/write` 动词。`ioctl` 用「命令字 + 数据指针」提供万能兜底。内核里 `vfs_ioctl` 的两条路（`:46` 无方法 → `ENOTTY`，`:52-53` 有方法但返回 `-ENOIOCTLCMD` → `ENOTTY`）就是它「透传 + 兜底」的体现。

**Q2：`request` 里为什么编码 `size`？**
A：为了安全。`ioctl` 的可变参数是用户态指针，驱动要 `copy_from_user`/`copy_to_user`。`request` 的 `size` 字段（`include/uapi/asm-generic/ioctl.h:5-13` 注释原话：「useful for catching programs compiled with old versions and to avoid overwriting user space outside the user buffer area」）让内核知道要拷多少字节。`_IOR/_IOW` 用 `sizeof(datatype)` 自动填入，并把上限卡在 16 kB−1。

**Q3：为什么 `TIOCGWINSZ` 的 `dir`/`size` 都是 0？**
A：因为它是**硬编码的老式命令字**（`ioctls.h:38` 直接写 `0x5413`），不是用宏拼出来的。`0x5413` 恰好等于 `_IO('T', 0x13)`——「无参数」的编码。tty 的 `0x54xx` 段都这德行。所以别用「按位拆 `dir`」来推断它读还是写；要看内核源码里这个 `case` 实际怎么用 `arg`。

**Q4：`ENOTTY` 有几种来源？**
A：两种，都在 `vfs_ioctl`（`fs/ioctl.c:44-56`）：①对象没有 `unlocked_ioctl` → 初值 `-ENOTTY` 直接返回；②有方法但驱动返回 `-ENOIOCTLCMD` → 翻译成 `-ENOTTY`。用户态**永远看不到 `ENOIOCTLCMD`**，它是内核内部哨兵值。字面 "not a typewriter" 是历史遗留，现代含义就是「对象不认识这条命令」。

**Q5：`isatty()` 内部做了什么？**
A：glibc 2.39 里 `__isatty`（`sysdeps/posix/isatty.c:23-28`）只做一件事：`return __tcgetattr(fd, &term) == 0;`。而 `__tcgetattr`（`sysdeps/unix/sysv/linux/tcgetattr.c:38`）里是 `INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios)`。所以 `isatty` 就是「试一下 tty 专属 ioctl，成功就是终端」——清清爽爽的 ioctl 应用。

**Q6：`FIONBIO` 和 `fcntl(F_SETFL, O_NONBLOCK)` 有什么区别？**
A：改的是**同一个东西**——`filp->f_flags` 的 `O_NONBLOCK` 位（`ioctl_fionbio` 里 `filp->f_flags |= O_NONBLOCK`）。区别：`FIONBIO` 只动这一位，`fcntl(F_SETFL)` 是「整份标志替换」（你给什么剩什么）。`fcntl` 是 POSIX 正路，`FIONBIO` 是老式写法。混用不会打架，但要知道它们共享同一份状态。

**Q7：管道上的 `FIONREAD` 是谁实现的？**
A：不是 VFS 的通用代码，而是管道的 `pipe_ioctl`（`fs/pipe.c:608`，注册在 `:1228` 的 `.unlocked_ioctl = pipe_ioctl`）。`do_vfs_ioctl` 的 `FIONREAD` 分支（`:829-834`）发现「不是普通文件」后 `return vfs_ioctl(...)` 转发过去，`pipe_ioctl` 加锁遍历环形缓冲区把各段 `len` 加起来。**同一个命令字，普通文件和管道走两套完全不同的实现**。

**Q8：`ioctl` 的返回值可靠吗？**
A：只能可靠地判断「成功/失败」。失败是 `-1` + `errno`；成功时的返回值由驱动自定义（`FIONREAD` 返回 0，但数据写在 `arg` 里）。所以标准写法是 `if (ioctl(...) == -1)`，**不要**用「返回值 == 某个正数」当成功判据。
