## 本章回顾：一条主线，五个动词

4.1 – 4.8 讲的其实是**同一件事的五种操作**：

| 动词 | 问题 | 内核入口 | 关键结论 |
|------|------|----------|----------|
| `open()` | 怎么拿到一个句柄 | `fs/open.c:1441` | 拿到的是**进程 fd 表的一个槽位**，不是一个「文件」 |
| `read()` | 怎么从对象取字节 | `fs/read_write.c:621` | 短读是合法结果；`count` 超 buffer 不报错 |
| `write()` | 怎么往对象送字节 | `fs/read_write.c:646` | 部分写是合法结果；`count=0` 返回 0 |
| `close()` | 怎么还掉句柄 | `fs/open.c:1557` | 号立即回收；**不幂等**，重复 close 报 `EBADF` |
| `lseek()` | 怎么移动游标 | `fs/read_write.c:311` | 只改 `f_pos`；流对象 `ESPIPE` |

以及一个**兜底出口**：

| 兜底 | 什么时候用 | 内核入口 |
|------|-----------|----------|
| `ioctl()` | 「控制/查询」类操作，字节流语义表达不了 | `fs/ioctl.c:857` → `do_vfs_ioctl` → `f_op->unlocked_ioctl` |

一条贯穿全章的主线是：

> **「文件」不是一个东西，是一个三层结构。**
> 用户态看到的是个整数（fd），中间是一张进程私有的**槽位表**，最后才落到内核的**打开文件描述**（`struct file`）和 **inode**。

```
进程 A                     进程 B
┌──────────────┐          ┌──────────────┐
│ fd 表         │          │ fd 表         │
│  0 ──┐        │          │  0 ──┐        │
│  3 ──┼──┐     │          │  5 ──┼──┐     │
└──────┼──┼─────┘          └──────┼──┼─────┘
       │  │                       │  │
       │  └───────┬───────────────┘  │
       ▼          ▼                  ▼
   ┌────────┐  ┌──────────────────┐  ┌────────┐
   │struct  │  │ struct file      │  │struct  │
   │file    │  │  f_mode/f_pos/   │  │file    │
   │(stdin) │  │  f_flags/f_count │  │(独立)  │
   └───┬────┘  └────────┬─────────┘  └───┬────┘
       │                │                │
       └────────────────┼────────────────┘
                        ▼
                  ┌───────────┐
                  │  inode    │  ← i_size / i_mode / 数据块映射
                  └───────────┘
```

**读法**：同一行（`fork`/`dup`）→ 共享 `struct file`（**共享偏移**）；不同行（各自 `open`）→ 各自的 `struct file`（**各自偏移**），但可能指向同一个 inode。Ch5 会把这张图讲透。

## 「反直觉」清单：本章最值钱的八条

这八条都是**跑出来才知道**的，靠读书容易想反：

| # | 反直觉点 | 真实行为 | 证据 |
|---|---------|---------|------|
| 1 | `close` 之后那个号是不是「用完就废」 | 号**立即回收**，下一次 `open` 就拿到它 | `close(3)` → `open c=3` |
| 2 | `write(fd, buf, 0)` 算不算错误 | **合法**，返回 0。`count=0` 时内核连数据都不碰 | `write(...,0)` → `0`，`errno=0` |
| 3 | `read(fd, buf[64], 1GiB)` 会不会失败 | **成功**。内核只验证地址范围属于用户空间，**不管 buffer 实际多大** | 返回 36（栈上真实数据） |
| 4 | `O_CLOEXEC` 能不能用 `F_GETFL` 查出来 | **不能**。它在**另一层**（`F_GETFD` 的 `FD_CLOEXEC` 位） | `F_GETFL`→`0x8000` 无该位 |
| 5 | `F_GETFL` 返回的是不是你 `open` 时传的 | **不是**。内核会补 `O_LARGEFILE`（`fs/open.c:1443-1444`） | 传 0 得到 `0x8000` |
| 6 | 所有 ioctl 都按 `_IOR/_IOW` 编码 | **不是**。`TIOCGWINSZ` 等一批老命令字是硬编码的 | `dir=0`、`size=0` |
| 7 | `SEEK_HOLE` 会给出精确的洞位置 | 通用兜底实现假设「洞 = 文件末尾」，真实检测靠 FS | 实测 `4096` ≠ `i_size` |
| 8 | `close` 失败就重试 | **不能重试**。重复 close 报 `EBADF`，重试会关掉别人的 fd | `close(3)` 第二次 → `EBADF` |

## 三层结构与生命周期

| 层 | 生命周期由谁决定 | 关掉会怎样 |
|----|----------------|-----------|
| **进程 fd 表槽位** | `files_struct`（`include/linux/fdtable.h:49`） | 槽位立即空出，可被下次 `open`/`dup` 复用 |
| **打开文件描述 `struct file`** | `f_count` 引用计数（`include/linux/fs.h:1005`） | `f_count--`；**归零才释放**（`dup`/`fork` 会让多个 fd 共享一个） |
| **inode** | inode 缓存 + 硬链接数 | 用 `unlink` 减链接数；链接数为 0 且无引用才真删数据 |

**这解释了三件事**：

1. 为什么 `close(3)` 之后号能立刻复用 —— 它只释放了**第一层**
2. 为什么 `dup`/`fork` 后 `close` 一个不影响另一个 —— `f_count` 还没归零
3. 为什么删掉打开中的文件后还能继续读写 —— `unlink` 只减**第三层**的链接数

## HFT / 嵌入式关联

| 要点 | 兑现 |
|------|------|
| 短读/部分写必须循环 | HFT 行情落盘、固件 OTA 烧写，不处理就**静默丢数据**。实测：往 4 KiB 管道裸 `write(8192)` 只写 4096 |
| `write` 成功 ≠ 落盘 | `write` 只保证数据进了**页缓存**。要落盘得 `fsync`/`fdatasync`（实测都返回 0） |
| 热路径少 syscall | 每个 `read`/`write` 都是内核转换。批量落盘用 `writev`（Ch5），文件映射用 `mmap`（Ch49） |
| 流对象不可 seek | 行情流只能顺序消费，天然「只前进」；要回放就落盘成可 seek 的文件 |
| `/dev` 也走同一套 | 嵌入式点灯/读传感器仍是 `open` + `ioctl`（+ `read`/`write`），只是命令字设备自定义 |
| `O_CLOEXEC` 防泄漏 | 长跑的交易进程 `fork+exec` 时，不设它会把行情 fd 泄露给子进程 |

<summary>代码自测（Q&A）</summary>

**Q1：为什么 `read/write` 可能返回小于请求的字节数？**
A：`read` 侧：到了 EOF、管道/socket 缓冲区只有部分数据、被信号中断（`EINTR`）、终端读到行尾。`write` 侧：磁盘空间不足（`ENOSPC`）、管道缓冲只剩一部分、被信号中断。**这是合法结果不是错误**，正确做法是循环调用直到传完。实测两个极端：文件只剩 6 字节时 `read(8)` 返回 6；往 4 KiB 容量管道裸 `write(8192)` 返回 4096。

**Q2：`fork()` 后父子进程共享文件偏移吗？**
A：共享。`fork` 复制的是**第一层**（fd 表），表项指向的还是**同一个 `struct file`**（第二层），`f_pos` 在 `struct file` 里（`include/linux/fs.h:1007`），所以父子看到同一个游标。实测子进程读走 4 字节后，父进程查到的偏移就是 4。要各自独立就各自 `open`。

**Q3：`O_APPEND` 为什么能保证多进程写入不交错？**
A：内核把「定位到末尾 + 写」在 `vfs_write` 内部**原子**完成——不是用户态的两步。所以多个进程的追加严格串行。没有 `O_APPEND` 时 `lseek(SEEK_END)` + `write()` 是两步，之间有 TOCTOU 竞争窗口，会互相覆盖。这是本章唯一**无法用用户态代码复刻同等原子性**的机制。

**Q4：为什么 `close()` 不能重试？**
A：`close` 失败返回 `EBADF` 时，说明这个 fd **本来就不是有效的**——但内核仍可能已经把槽位释放掉了（Linux 的 `close` 在 `fput` 之后才报错）。此时重试 `close(3)`，如果这期间别的线程 `open` 拿到了 3 号，你关的就是**别人的文件**。实测第二次 `close(3)` 返回 `EBADF`。正确姿势：`close` 失败**不要重试**，最多打个日志。

**Q5：`F_GETFL` 返回的标志和 `open` 时传的一样吗？**
A：不一定。内核会在 `do_sys_openat2` 里补一些位——最典型的是 `if (force_o_largefile()) flags |= O_LARGEFILE;`（`fs/open.c:1443-1444`），在 32 位系统上强制加 `O_LARGEFILE`。实测传 0 得到 `F_GETFL = 0x8000`，正是这个位。另外 `O_CLOEXEC` **不在** `F_GETFL` 里——它是 fd 标志，要用 `F_GETFD` 查 `FD_CLOEXEC`。

**Q6：`isatty()` 是怎么实现的？**
A：glibc 2.39 里 `__isatty`（`sysdeps/posix/isatty.c:23-28`）就是 `return __tcgetattr(fd, &term) == 0;`，而 `__tcgetattr`（`sysdeps/unix/sysv/linux/tcgetattr.c:38`）是 `INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios)`。**所以 `isatty` 本质就是「试一个 tty 专属 ioctl」**——成功是终端，`ENOTTY` 就不是。标准库把 ioctl 用在了最基础的判断上。

**Q7：`read(fd, buf, count)` 的 `count` 能随便给吗？为什么会「成功」？**
A：`count` 只受两层限制：① `MAX_RW_COUNT`（`include/linux/fs.h:2399`，`INT_MAX & PAGE_MASK`）——超过会被截断；② `access_ok` 只验证**地址范围落在用户空间**，它**不知道你的 buffer 到底分配了多大**。实测拿一个 64 字节的栈数组、`count` 给 1 GiB，内核照样读到文件末尾返回 36——**它把超出 buffer 的部分写进了你的栈**。这是静默内存破坏，比报错危险得多。

**Q8：为什么 `write` 返回成功不代表数据安全了？**
A：因为 `write` 只保证数据进了**页缓存**（page cache），磁盘上还没有。此时断电，数据就没了。要落盘必须显式调 `fsync(fd)`（连元数据一起）或 `fdatasync(fd)`（只保证数据），或者用 `O_SYNC`/`O_DSYNC` 打开。实测两者在本章 demo 里都返回 0。HFT 场景下「成交回报必须落盘」就得走这条路。
