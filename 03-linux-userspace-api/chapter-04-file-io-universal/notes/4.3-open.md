## 要点

```c
#include <fcntl.h>
int open(const char *pathname, int flags, /* mode_t mode */);
```

| | |
|--|--|
| 成功 | 返回 fd |
| 失败 | `-1` |

**flags（位掩码；访问模式三选一）**

| 标志 | 含义 |
|------|------|
| `O_RDONLY` / `O_WRONLY` / `O_RDWR` | 只读 / 只写 / 读写 |
| `O_CREAT` | 不存在则创建；须给 **mode** |
| `O_TRUNC` | 存在则截断为 0 |
| `O_APPEND` | 追加（原子性详 Ch5） |
| `O_NONBLOCK` | 非阻塞打开 |
| `O_NOFOLLOW` | 不跟随符号链接 |

**mode：** 新建权限，受 **umask** 屏蔽：最终权限 ≈ `mode & ~umask`。  
默认 `open` **跟随** 符号链接。

## 与 C 语言学习的关系

`open()` 是 **POSIX 系统调用**（内核接口），直接向 Linux 内核发起服务，**不是** C 语言标准库函数。

```c
int open(const char *pathname, int flags, mode_t mode);  // POSIX 系统调用
FILE *fopen(const char *path, const char *mode);          // C 标准库（libc 封装）
```

`fopen()` 是 C 标准库函数，内部底层会调用 `open()` 系统调用，并额外带上**用户态缓冲区**。K&R 第 8 章讲解的正是这套文件系统接口。

**fopen 模式 → open flags 映射：**

| fopen 模式 | open 对应 flags | 说明 |
|---|---|---|
| `"r"` | `O_RDONLY` | 只读 |
| `"w"` | `O_WRONLY \| O_CREAT \| O_TRUNC` | 只写、创建、截断清空旧文件 |
| `"a"` | `O_WRONLY \| O_CREAT \| O_APPEND` | 追加写 |

**关键区别：** `fopen` 在用户态带缓冲区（`FILE` 结构体内部 buffer）；`open` 没有用户态缓冲，读写直接进入内核。

---

## HFT / 嵌入式关联

UNIX 文件 I/O 分**两层**：用户态 libc 库层 ↔ 内核系统调用层。

| 路线 | 要点 |
|------|------|
| **嵌入式 Linux** | 可选 libc 封装（`fopen`，自带缓冲，简单）；也可直接调用 `open` 系统调用做裸文件操作，适合资源受限场景。`/dev` 设备也走同一套 open/read/write；专属控制靠 `ioctl` |
| **HFT 低延迟** | `fopen`/`fread`/`fwrite`：libc 自带用户层缓冲区，多一层拷贝，带来微小额外延迟。直接 `open`/`read`/`write`：绕开 libc 用户缓冲，但系统调用本身陷入内核也有开销。工程上要权衡：什么时候用库缓冲、什么时候直接系统调用，`mmap` 也经常登场 |
| **通用** | 短读/部分写；热路径少 syscall；落盘语义与缓冲要清楚 |

## 补充区分重点（面试 / 考试高频）

| | `fopen` / `fread` / `fwrite` | `open` / `read` / `write` |
|---|---|---|
| **返回值** | `FILE *` 指针 | `int fd`（内核整数句柄） |
| **层级** | C 标准库（libc） | POSIX 系统调用（内核接口） |
| **缓冲** | 用户态带缓冲区 | 无用户态缓冲 |
| **关闭** | `fclose()` → 内部调用 `close()` | `close(fd)` |
| **可移植** | C 标准，跨平台 | POSIX，Unix/Linux 限定 |

## 常见陷阱

1. **O_CREAT 忘传 mode**

```c
/* mode 参数丢失，权限不确定 */
fd = open("f.txt", O_WRONLY | O_CREAT);
/* 必须给 mode */
fd = open("f.txt", O_WRONLY | O_CREAT, 0644);
```

O_CREAT 时第三个参数 mode 是新文件权限，受 umask 影响。漏传会导致权限不确定（取决于栈上残留值）。

2. **返回值未检查**

```c
int fd = open(path, O_RDONLY);
read(fd, buf, n);  /* fd=-1 → EBADF */
```

open 失败返回 -1。不检查直接用 fd 会导致后续操作全部失败。必须 `if ((fd = open(...)) < 0) { perror; exit; }`。

3. **O_TRUNC 意外截断**

```c
/* 想追加写，却加了 O_TRUNC */
fd = open("log.txt", O_WRONLY | O_TRUNC);  /* 清空了! */
fd = open("log.txt", O_WRONLY | O_APPEND);  /* 正确 */
```

O_TRUNC 在文件存在时截断为 0。追加写场景误加 O_TRUNC 会丢失数据。

## 自测题

**题目 1（选择）：** `open("f.txt", O_CREAT)` 缺少什么参数？
A. flags 不对
B. mode 参数
C. pathname
D. 返回值

<details>
<summary>参考答案</summary>

B。O_CREAT 时必须提供 mode（如 0644），受 umask 影响。漏传会使用栈上不确定的值。

</details>

**题目 2（判断）：** `open` 失败时返回 0。

<details>
<summary>参考答案</summary>

错误。open 失败返回 -1 并设置 errno。fd=0 是 stdin，open 正常时可能返回 0（如果 stdin 被关闭）。

</details>

**题目 3（踩坑）：** 以下代码有什么问题？
```c
int fd = open("/etc/passwd", O_WRONLY|O_CREAT|O_TRUNC, 0644);
```

<details>
<summary>参考答案</summary>

对 /etc/passwd 用 O_WRONLY|O_TRUNC 会截断系统密码文件！想读文件应用 O_RDONLY。这是非常危险的操作。

</details>

**题目 4（应用）：** 写代码：以读写方式打开文件，不存在则创建（权限 0644），存在则追加。

<details>
<summary>参考答案</summary>

```c
int fd = open("data.txt", O_RDWR|O_CREAT|O_APPEND, 0644);
if (fd < 0) { perror("open"); exit(1); }
```

</details>

## 代码示例

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
/* open(): flags = O_RDONLY / O_WRONLY / O_RDWR + O_CREAT/O_TRUNC/O_APPEND */
int main(void) {
    int fd = open("/tmp/ch4_open.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    write(fd, "test", 4);
    close(fd);

    fd = open("/tmp/ch4_open.txt", O_RDONLY);
    char buf[8];
    read(fd, buf, 4);
    buf[4] = '\0';
    printf("read: %s\n", buf);
    close(fd);
    return 0;
}
```

## 思考题

**HFT 热路径写日志，用 `fprintf`（fopen），还是 `open` + `write`？各自优缺点是什么？**

<details>
<summary>参考思路</summary>

- `fprintf`（fopen）：libc 缓冲减少 syscall 次数（批量 flush），但多一次用户态拷贝；格式化方便；缓冲区 flush 时机不可控
- `open` + `write`：无 libc 缓冲层，延迟更低更可控；但每次 write 都陷入内核，频繁写时 syscall 开销大
- HFT 实践：热路径日志常用自定义 ring buffer + 批量 write，或 mmap + 定期刷盘，兼顾低延迟和少 syscall

</details>
