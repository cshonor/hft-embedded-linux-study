## 本节讲什么

`open()` 把「路径名」变成「fd」，是万能 I/O 模型的第一步。本节回答三个问题：

1. `open()` 在内核里走的是怎样一条链路（从路径字符串到 fd 槽位）？
2. `flags` 和 `mode` 两个参数各自控制什么？`umask` 怎么参与？
3. `open()`（系统调用）和 `fopen()`（C 库函数）差在哪？

---

## 1. 原型与内核链路

```c
#include <fcntl.h>
int open(const char *pathname, int flags, /* mode_t mode */);
/* 成功返回 fd；失败返回 -1 并设 errno */
```

`open` 是**变参**函数——只有 `flags` 含 `O_CREAT`（或 `O_TMPFILE`）时才需要第三个参数 `mode`。内核侧完整链路（v6.6）：

```
用户态 open(path, flags, mode)
      │
      ▼
SYSCALL_DEFINE3(open)                    fs/open.c:1441
      │  force_o_largefile() → 自动补 O_LARGEFILE（32 位平台）
      ▼
do_sys_open(AT_FDCWD, ...)               fs/open.c:1434
      ▼
do_sys_openat2()                         fs/open.c:1406
      ├─→ build_open_flags()  解析 flags/mode 成 struct open_flags
      ├─→ getname()           从用户态拷贝路径字符串（copy_from_user）
      ├─→ get_unused_fd_flags()  ← 分配「最小可用」fd
      ├─→ do_filp_open()      真正打开：路径解析 + 调用 f_op->open
      │                        （这里才做权限检查、创建文件、挂 inode）
      └─→ fd_install(fd, f)   把 struct file 装进 fd 表的 fd 槽位
```

> 关键：fd 的分配（`get_unused_fd_flags`）发生在**真正打开之前**——先占坑，`do_filp_open` 失败再 `put_unused_fd` 还回去。`open` 默认相对 `AT_FDCWD`（当前工作目录）；`openat`/`openat2` 可指定 `dfd` 做相对路径（用于防 TOCTOU，见 Ch18）。

## 2. flags：位掩码，访问模式三选一

| 标志 | 含义 |
|------|------|
| `O_RDONLY` / `O_WRONLY` / `O_RDWR` | 只读 / 只写 / 读写（**三者必选其一**） |
| `O_CREAT` | 不存在则创建；此时**必须给 mode** |
| `O_EXCL` | 与 `O_CREAT` 配合：文件已存在则失败（原子「排他创建」） |
| `O_TRUNC` | 存在则截断为 0（需写权限） |
| `O_APPEND` | 每次写前原子地把偏移设到末尾（详 Ch5） |
| `O_NONBLOCK` | 非阻塞打开（对管道/FIFO/设备有意义） |
| `O_CLOEXEC` | `exec` 时自动关闭，防 fd 泄漏给子程序 |
| `O_NOFOLLOW` | 不跟随符号链接 |
| `O_SYNC` / `O_DSYNC` | 写以同步方式完成（每次 write 落盘，Ch13） |

## 3. mode 与 umask

`mode` 只在新文件被 `O_CREAT` 创建时生效，指定的是**请求的权限**；最终权限还要被进程的 `umask` 屏蔽：

```
最终权限 = mode & ~umask
例如 mode=0666, umask=022 → 0644 (rw-r--r--)
     mode=0666, umask=002 → 0664 (rw-rw-r--)
```

`umask` 是进程级属性（`umask()` 系统调用可改），默认 `022`。它只**屏蔽**（清除）权限位，不能「新增」`mode` 里没有的位。

## 4. `open()` vs `fopen()`：系统调用 vs C 库

```c
int   open(const char *pathname, int flags, mode_t mode);  // POSIX 系统调用
FILE *fopen(const char *path, const char *mode);           // C 标准库封装
```

| | `open` / `read` / `write` | `fopen` / `fread` / `fwrite` |
|---|---|---|
| 返回值 | `int fd`（内核整数句柄） | `FILE *` 指针 |
| 层级 | POSIX 系统调用（直接进内核） | C 标准库（libc，内部调 `open`） |
| 缓冲 | **无**用户态缓冲 | **有**用户态缓冲（`FILE` 内部 buffer） |
| 关闭 | `close(fd)` | `fclose()` → 内部 `close()` |
| 可移植 | Unix/Linux 限定 | C 标准，跨平台 |

`fopen` 的「r/w/a」模式到 `open` flags 的映射：

| fopen 模式 | open 对应 flags |
|---|---|
| `"r"` | `O_RDONLY` |
| `"w"` | `O_WRONLY \| O_CREAT \| O_TRUNC` |
| `"a"` | `O_WRONLY \| O_CREAT \| O_APPEND` |

## 5. HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **嵌入式 Linux** | 资源受限场景可直接 `open` 裸文件操作（免 libc 缓冲层）；`/dev` 设备走同一套 `open`；专属控制靠 `ioctl` |
| **HFT 低延迟** | `fopen` 多一层用户态拷贝；直接 `open/write` 少一层但每次 syscall 都陷内核。热路径常权衡：批量写 or `mmap` or `io_uring` |
| **多进程日志** | `O_APPEND` 保证多进程追加不交错（原子设偏移+写）；`O_CLOEXEC` 防 `exec` 后 fd 泄漏 |

## 6. 常见陷阱

1. **`O_CREAT` 忘传 `mode`** — 漏传时 `mode` 取栈上残留值，权限不可预测：
```c
fd = open("f.txt", O_WRONLY | O_CREAT);          /* 错！权限不确定 */
fd = open("f.txt", O_WRONLY | O_CREAT, 0644);    /* 对 */
```

2. **返回值未检查** — `open` 失败返回 `-1`，直接用 `-1` 当 fd 会让后续 `read/write` 全部 `EBADF`：
```c
int fd = open(path, O_RDONLY);
if (fd == -1) { perror("open"); exit(1); }
read(fd, buf, n);
```

3. **`O_TRUNC` 意外截断** — 想追加写却误加 `O_TRUNC`，清空旧数据：
```c
fd = open("log.txt", O_WRONLY | O_TRUNC);   /* 清空了！ */
fd = open("log.txt", O_WRONLY | O_APPEND);  /* 追加，正确 */
```

## 7. 代码示例

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/ch4_open.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    write(fd, "test", 4);
    close(fd);

    fd = open("/tmp/ch4_open.txt", O_RDONLY);
    if (fd < 0) { perror("open read"); return 1; }
    char buf[8];
    ssize_t n = read(fd, buf, 4);
    buf[n] = '\0';
    printf("read: %s\n", buf);
    close(fd);
    return 0;
}
```

<details>
<summary>代码自测（Q&A）</summary>

**Q1：`open("f.txt", O_CREAT)` 少了什么参数？为什么危险？**
A：少了 `mode`。`open` 是变参函数，只有 `flags` 含 `O_CREAT` 时才读第三个参数；漏传时内核会读栈上的残留值当 `mode`，导致新文件权限随机。正确写法 `open("f.txt", O_CREAT, 0644)`（再受 `umask` 屏蔽）。

**Q2：`open` 失败时返回 0 吗？**
A：不。失败返回 `-1` 并设 `errno`。`0` 是合法 fd（stdin），只有 `0` 号槽位空闲时才可能返回 0——这本身不是错误。判断成功与否只能用 `fd == -1`。

**Q3：`O_EXCL | O_CREAT` 组合有什么用途？**
A：原子地「仅当文件不存在时创建」。两个进程同时用这个组合创建同名文件，内核保证只有一个成功、另一个得到 `-EEXIST`——这是「用文件当锁」或「原子生成临时文件」的经典手段，避免 `open` 后再 `stat` 的 TOCTOU 竞争窗口。

**Q4：为什么 `umask` 只能「屏蔽」权限，不能「添加」权限？**
A：内核里的计算是 `mode & ~umask`——`umask` 只把某些位清零。`mode` 里本就没有的位，`umask` 造不出来。所以想让新文件「其他人可写」（`0666`），必须 `mode` 里先有 `022` 之外还要 `022`，而 `umask` 不能帮你补。

**Q5：`fopen("a")` 和 `open(..., O_APPEND)` 在「追加」语义上等价吗？**
A：等价，且底层是同一个机制。`fopen("a")` 内部就是 `open(path, O_WRONLY|O_CREAT|O_APPEND, ...)`，`O_APPEND` 让内核在每次 `write` 前原子地把偏移设到文件末尾，多进程追加不会交错。区别只在 `fopen` 多了用户态缓冲，`fclose` 时才真正 flush + `close`。

</details>
