## 本节讲什么

这是本章的「思想核心」，回答四个问题：

1. 为什么拷贝磁盘文件、写终端、读 `/proc` 能用**同一段代码**？
2. 文件类型之间的差异，内核在哪里把它们「吸收」掉了？
3. 当这套万能模型不够用时，靠什么兜底？
4. 原书第一个完整程序 `copy.c`（Listing 4-1）是怎么把这套模型用出来的？（见 §5）

本节把「一切皆文件」从口号落到 VFS 的 `f_op` 函数指针表上，讲清「通用」与「特化」的边界——并且**真的用同一套代码去打四种对象**，再把原书 `copy.c` 的三种调用姿势跑一遍。

---

## 1. 同一套 API，通吃所有文件类型

```c
/* 下面是同一套 open/read/write/close，目标是三种截然不同的对象 */
int fd   = open("/tmp/demo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644); /* 普通文件 */
int dev  = open("/dev/null",     O_WRONLY);                        /* 设备文件 */
int proc = open("/proc/version", O_RDONLY);                        /* 内核伪文件 */
```

三段代码除了路径和 flags，**没有任何区别**。应用层完全不关心目标是 ext4 文件、块设备还是 proc 伪文件系统——这是「通用 I/O 模型」的全部意义。

## 2. 差异被 VFS 的 `f_op` 函数指针吸收

差异并没有消失，而是被**下沉**到了内核的虚拟文件系统层（VFS）：

```
用户态   read(fd, buf, n)
              │  （一条 syscall，对所有文件类型都一样）
              ▼
内核     vfs_read(file, buf, n, pos)          fs/read_write.c:450
              │  只做通用校验（f_mode、access_ok、rw_verify_area）
              ▼
        file->f_op->read / read_iter          ← 差异在这里！
              │
     ┌────────┼────────────┬──────────────┐
     ▼        ▼            ▼              ▼
 ext4 读    proc 读      tty 读        /dev/null 读
（走页缓存）（现场生成文本）（行规程）   （直接返回 0）
```

`struct file` 里的 `f_op` 是指向 `struct file_operations`（`include/linux/fs.h:1852`）的指针，这个结构体是一张**函数指针表**：`read`、`write`、`llseek`、`unlocked_ioctl`、`mmap`、`open`、`release`…… 每个文件系统/驱动在 `open` 时把属于自己的那张表挂到 `file->f_op` 上。此后所有 `read`/`write` 都通过同一个指针分派，VFS 上层代码一行都不用改。

> 这本质是内核里的**多态**——`f_op` 就是 vtable，`vfs_read` 调 `file->f_op->read` 就是虚函数调用。对照 LKD 见 [`05/Ch13.2 VFS 的面向对象设计`](../../../05-linux-kernel/chapter-13-vfs/notes/section-13.2-VFS-的面向对象设计.md)。

## 3. 通用模型之外：`ioctl()` 是逃生舱

「万能模型」只覆盖 `open/read/write/close`（+ `lseek`）这几种「流式字节」语义。一旦要做的不是「读字节/写字节」——比如设置终端窗口大小、查询磁盘扇区数、配置网卡混杂模式——这套模型就没有对应动词了。

于是内核留了一个「万能兜底」：

```c
int ioctl(int fd, int request, ...);   /* 任意设备专属命令 */
```

`request` 是一个编码了「方向 + 数据大小 + 编号」的整数，内核据此把后面的可变参数解释成设备要的结构体。设备驱动在 `file_operations->unlocked_ioctl` 里用 `switch(request)` 分派。详见 4.8。

| 机制 | 覆盖范围 | 例子 |
|------|---------|------|
| `read`/`write` | 流式字节 I/O | 读文件内容、写终端 |
| `lseek` | 随机定位（可 seek 对象） | 跳到文件第 N 字节 |
| `ioctl` | 一切「字节流之外」的控制 | `TIOCGWINSZ` 查窗口大小 |

## 4. 代码：同一段代码打四种对象

「通吃」这句话，用一个程序同时操作「真文件 / 字符设备 / 内核伪文件 / 管道」最能说明问题。

完整源码 [`code/c4_2_universal.c`](../code/c4_2_universal.c)：

```c
/* c4_2_universal.c — 「通用 I/O 模型」：同一套 open/read/write/close 通吃四种对象
 *
 * 四个目标：
 *   1) 普通文件        /tmp/c4_univ.txt
 *   2) 设备文件        /dev/null（写进去就消失）与 /dev/zero（读出来全是 0）
 *   3) 内核伪文件      /proc/version（内容由内核现场生成，没有磁盘块）
 *   4) 管道            pipe(2) 造出来的匿名管道
 *
 * 看点：调用形式完全一样，返回值/语义却不同——差异全被 VFS 的
 *       file->f_op 函数指针吸收了，用户态一行都不用改。
 *
 * 编译: gcc -O0 -Wall -o c4_2_universal c4_2_universal.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

int main(void)
{
    char buf[128];
    ssize_t n;

    printf("== 1. 普通文件：写入后能读回来 ==\n");
    int fd = open("/tmp/c4_univ.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open file"); return 1; }
    printf("  写入 \"hello universal\" -> write 返回 %zd\n",
           write(fd, "hello universal", 15));
    lseek(fd, 0, SEEK_SET);                 /* 回到开头才能读到自己写的 */
    n = read(fd, buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = '\0';
    printf("  读回 %zd 字节: \"%s\"\n", n, buf);
    close(fd);

    printf("\n== 2. 设备文件 /dev/null：写进去就消失，读出来立刻 EOF ==\n");
    int dn = open("/dev/null", O_RDWR);
    if (dn < 0) { perror("open /dev/null"); return 1; }
    n = write(dn, "这段数据会被内核丢掉", 30);
    printf("  write 30 字节 -> %zd  （报告成功，但没有落点）\n", n);
    n = read(dn, buf, sizeof buf);
    printf("  read      -> %zd  （0 = EOF：永远读不到东西）\n", n);
    close(dn);

    printf("\n== 3. 内核伪文件 /proc/version：内容现场生成 ==\n");
    int pv = open("/proc/version", O_RDONLY);
    if (pv < 0) { perror("open /proc/version"); return 1; }
    n = read(pv, buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = '\0';
    printf("  read %zd 字节，开头是: %.60s...\n", n, buf);
    n = read(pv, buf, sizeof buf - 1);      /* 再读一次 */
    printf("  再 read -> %zd  （还不是 0：/proc/version 比这个 buffer 大）\n", n);
    n = read(pv, buf, sizeof buf - 1);      /* 第三次 */
    printf("  第三次 read -> %zd  （0 = 终于到 EOF）\n", n);
    printf("  → 连 proc 伪文件都必须「循环读到 0」，别假设一次就能读完。\n");
    close(pv);

    printf("\n== 4. 管道：两个 fd，一个读端一个写端，同一个 pipe(2) 造的 ==\n");
    int p[2];
    if (pipe(p) < 0) { perror("pipe"); return 1; }
    printf("  pipe() 给出读端 p[0]=%d 写端 p[1]=%d\n", p[0], p[1]);
    write(p[1], "via pipe", 8);
    n = read(p[0], buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = '\0';
    printf("  从 p[0] 读到 %zd 字节: \"%s\"\n", n, buf);

    printf("\n== 5. 差异在哪：同一个 read，四种对象走四个实现 ==\n");
    printf("  普通文件 read -> ext4/overlayfs 的 read_iter（走页缓存）\n");
    printf("  /dev/null  read -> 内核直接返回 0，没有任何存储\n");
    printf("  /proc/version -> procfs 的 read，现场格式化成字符串\n");
    printf("  管道        read -> 从内核环形缓冲区搬字节，读完即销毁\n");
    close(p[0]);
    close(p[1]);
    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c4_2_universal c4_2_universal.c && ./c4_2_universal
```

CE（gcc 13.3.0 / x86-64 / Ubuntu 24.04，沙箱内核 Linux 7.0.0-1012-aws）实测：

```text
== 1. 普通文件：写入后能读回来 ==
  写入 "hello universal" -> write 返回 15
  读回 15 字节: "hello universal"

== 2. 设备文件 /dev/null：写进去就消失，读出来立刻 EOF ==
  write 30 字节 -> 30  （报告成功，但没有落点）
  read      -> 0  （0 = EOF：永远读不到东西）

== 3. 内核伪文件 /proc/version：内容现场生成 ==
  read 127 字节，开头是: Linux version 7.0.0-1012-aws (buildd@lcy02-amd64-024) (x86_6...
  再 read -> 92  （还不是 0：/proc/version 比这个 buffer 大）
  第三次 read -> 0  （0 = 终于到 EOF）
  → 连 proc 伪文件都必须「循环读到 0」，别假设一次就能读完。

== 4. 管道：两个 fd，一个读端一个写端，同一个 pipe(2) 造的 ==
  pipe() 给出读端 p[0]=3 写端 p[1]=4
  从 p[0] 读到 8 字节: "via pipe"

== 5. 差异在哪：同一个 read，四种对象走四个实现 ==
  普通文件 read -> ext4/overlayfs 的 read_iter（走页缓存）
  /dev/null  read -> 内核直接返回 0，没有任何存储
  /proc/version -> procfs 的 read，现场格式化成字符串
  管道        read -> 从内核环形缓冲区搬字节，读完即销毁
```

逐条看：

| 观察 | 说明 |
|------|------|
| `/dev/null` 的 `write(30)` **返回 30** | 报告"成功"，但数据没有任何落点。**"写成功"从来不意味着"被保存"——`/dev/null` 是这句话最纯粹的证明** |
| `/dev/null` 的 `read` 立刻返回 0 | 0 是 EOF 而不是错误。一个永远读不到东西的对象，在通用模型里表现为"空文件" |
| `/proc/version` 三次才读完 | 文件是 219 字节（127+92），我的 buffer 是 127。**连伪文件都必须循环读到 0**——它也是"文件" |
| `pipe()` 给出 `p[0]=3, p[1]=4` | 管道是**两个 fd**（读端 + 写端），而不是一个。它们和普通文件一样进 fd 表 |
| 同一个 `read()` 四种实现 | 这就是「通用」的代价与价值：用户态零差异，差异全在 `f_op` 后面 |

> 第 3 条是最容易被忽略的：很多人以为 `/proc` 下的"小文件"一次就能读完。实测 219 字节遇上 127 字节的 buffer 就需要三轮。**读文件的代码只有一种正确写法：循环，直到返回 0 或出错。**

## 5. 原书 Listing 4-1：`copy.c` 三种调用姿势实测

原书 [`code/copy.c`](../code/copy.c) 是本章第一个完整程序（**Listing 4-1, p.71**），也是「通用模型」最直白的证明——它的 `main` 里只有 `open` / 循环 `read`+`write` / `close`，**没有任何「这是文件还是终端」的判断**：

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* copy.c  —— TLPI Listing 4-1（逐字镜像，未改动）

   Copy the file named argv[1] to a new file named in argv[2].
*/
#include <sys/stat.h>
#include <fcntl.h>
#include "tlpi_hdr.h"

#ifndef BUF_SIZE        /* Allow "cc -D" to override definition */
#define BUF_SIZE 1024
#endif

int
main(int argc, char *argv[])
{
    int inputFd, outputFd, openFlags;
    mode_t filePerms;
    ssize_t numRead;
    char buf[BUF_SIZE];

    if (argc != 3 || strcmp(argv[1], "--help") == 0)
        usageErr("%s old-file new-file\n", argv[0]);

    /* Open input and output files */

    inputFd = open(argv[1], O_RDONLY);
    if (inputFd == -1)
        errExit("opening file %s", argv[1]);

    openFlags = O_CREAT | O_WRONLY | O_TRUNC;
    filePerms = S_IRUSR | S_IWUSR | S_IRGRP | S_IWGRP |
                S_IROTH | S_IWOTH;      /* rw-rw-rw- */
    outputFd = open(argv[2], openFlags, filePerms);
    if (outputFd == -1)
        errExit("opening file %s", argv[2]);

    /* Transfer data until we encounter end of input or an error */

    while ((numRead = read(inputFd, buf, BUF_SIZE)) > 0)
        if (write(outputFd, buf, numRead) != numRead)
            fatal("write() returned error or partial write occurred");
    if (numRead == -1)
        errExit("read");

    if (close(inputFd) == -1)
        errExit("close input");
    if (close(outputFd) == -1)
        errExit("close output");

    exit(EXIT_SUCCESS);
}
```

三种调用姿势（CE 实测，同一份二进制、同一个可执行文件 `output.s`）：

| 命令 | 期望行为 | 实际结果 |
|------|---------|---------|
| `./output.s /proc/version /tmp/copy_out.txt` | 文件 → 文件 | 退出码 **0**，**零输出**（stdout 和 stderr 都是空） |
| `./output.s /nonexistent-file-xyz /tmp/copy_out.txt` | 源文件打不开 | 退出码 **1**，stderr 见下 |
| `./output.s --help` | 参数个数不对 | 退出码 **1**，打出用法 |

两条错误路径的 stderr 原文：

```text
  opening file /nonexistent-file-xyz: No such file or directory
  Usage: ./output.s old-file new-file
```

逐条看：

| 观察 | 说明 | 源码坐标 |
|------|------|---------|
| 成功时**一个字都不打** | 没有「拷贝完成」「写了 N 字节」之类的汇报。这是 UNIX 工具的惯例：**成功就闭嘴，失败才说话**——因为成功可以用退出码表达，而安静使得它可以在管道里安全组合 | `copy.c:60` `exit(EXIT_SUCCESS)` |
| `opening file %s` 后面自动跟了 `: No such file or directory` | `errExit` 是**变参**助手：它先打你给的 `fmt`，再补 `": " + strerror(errno)`，然后 `exit(EXIT_FAILURE)`。所以调用点是 `errExit("opening file %s", argv[1])`，**错误码不用自己传** | `copy.c:37-38` |
| `Usage: ./output.s` 里的 `./output.s` | 用的是 `argv[0]`。CE 把可执行文件命名为 `output.s`，所以打出这个怪名字——**本地编译会显示你自己的程序名** | `copy.c:32` `usageErr("%s old-file new-file\n", argv[0])` |
| `--help` 走的是**参数校验**，不是专门的 help 分支 | `copy.c:31` 把 `argc != 3` 和 `strcmp(argv[1], "--help") == 0` 合并成同一个 `if`，两种情况的处置都是打用法 | `copy.c:31-32` |
| 写不满就 `fatal` | `copy.c:50-51`：`if (write(outputFd, buf, numRead) != numRead) fatal(...)`。这在「只写普通文件」时是安全的；**一旦目标换成管道/socket 就会误杀**（原因见 [4.10 练习 4-3](4.10-exercises.md)） | `copy.c:50-51` |

> **为什么源文件用 `/proc/version`**：CE 沙箱里 `/etc/os-release` 不存在、`/dev/stdout` 是只读挂载，`/proc/version` 是唯一既存在又足够短小的常规文件。
>
> 而 `copy.c` 自己什么都不打印，连「拷了多少字节」都没有——这本身就是个观测点：**成功是无声的**。

## 6. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 设备驱动即文件 | 嵌入式里点灯、读传感器：写个字符设备驱动，挂到 `f_op->read/write/unlocked_ioctl`，用户态用 `open/read/write/ioctl` 直接操作 |
| 换存储介质零改代码 | 应用只面对 fd，底层从 eMMC 换到 NVMe、从 ext4 换到 XFS，用户态代码不变——差异全在 `f_op` 后面 |
| 性能边界 | 「通用」是有代价的：每层函数指针分派 + 通用校验。HFT 热路径追求极致时会绕过通用模型（`mmap`、`sendfile`、`io_uring`），但通用模型是理解这些优化的起点 |
| ioctl 是唯一出路 | 网卡 offload、硬件时间戳、DMA 配置这类「非字节流」操作，只能走 `ioctl`，没有 `read/write` 等价物 |
| "写成功"不可信 | `/dev/null` 把这点演到极致。所以落盘确认必须靠 `fsync` 的返回值（见 4.5），不能靠 `write` 的返回值 |

<summary>代码自测（Q&A）</summary>

**Q1：「一切皆文件」到底是真的「都是文件」，还是只是一种抽象？**
A：是抽象，不是字面事实。`/dev/null` 不是磁盘上的文件，`/proc/version` 的内容也不是存在哪里的字节——它们只是在 VFS 层**表现得像**文件：都有 `struct file`、都填了 `f_op` 函数指针。所谓「皆文件」=「皆可用 open/read/write/close 这套接口访问」。

**Q2：`vfs_read()` 里哪一行体现了「差异被吸收」？**
A：`ret = file->f_op->read(file, buf, count, pos)`（`fs/read_write.c:467`）。`vfs_read` 前面的校验（`FMODE_READ`→`-EBADF`、`access_ok`→`-EFAULT`）对所有文件类型都一样，真正干活的是通过 `f_op->read` 分派到具体实现——ext4 有 ext4 的实现，proc 有 proc 的实现，VFS 层不关心。

**Q3：为什么 `read`/`write` 管不了「设置终端窗口大小」这种事？**
A：因为窗口大小不是「一段字节流」。`read`/`write` 的语义是「从当前偏移搬运 N 字节」，而窗口行列数是一个「控制查询」，没有字节流可以表达。这类「字节流之外」的操作必须走 `ioctl(fd, TIOCGWINSZ, &ws)`，由驱动在 `unlocked_ioctl` 里识别命令字 `TIOCGWINSZ`。

**Q4：如果我想让一个自定义硬件设备能被 `read`/`write` 访问，内核侧最少要做什么？**
A：实现一个字符设备驱动，填一个 `struct file_operations`（至少 `open`、`read`、`write`、`release`），用 `register_chrdev` 注册，然后在 `/dev` 下建设备节点。之后用户态就能 `open("/dev/mydev")` + `read/write`，走的正是本节讲的通用模型。

**Q5：「通用模型」在性能上有什么代价？HFT 为什么有时要绕过它？**
A：代价来自三处：① 每次 `read/write` 都要 syscall 陷入内核；② `vfs_read/vfs_write` 的通用校验（f_mode、access_ok、rw_verify_area）有固定开销；③ `f_op` 函数指针间接跳转。HFT 极致低延迟场景会用 `mmap` 直接把文件映射进地址空间、用 `sendfile` 做内核内零拷贝、用 `io_uring` 批量提交 I/O，绕开「一次一 syscall + 通用校验」的路径。

**Q6：`/dev/null` 的 `write()` 为什么返回成功？这不是骗人吗？**
A：不算骗。`write` 的契约是「把这 N 个字节交给这个打开文件所代表的接收方」，`/dev/null` 的接收方语义就是「丢弃」——它诚实地完成了自己的语义。教训是：**`write` 的返回值只说明"内核收下了"，不说明"数据到了哪里"**。要确认落盘只能靠 `fsync`/`fdatasync`（见 4.5）。
