## 本节讲什么

`read()` 从 fd 读字节。本节回答三个问题：

1. `read()` 在内核里经过哪些校验，最后才真正碰数据？
2. 「短读（short read）」为什么是**正常现象**，必须怎么处理？
3. `EOF`、`EINTR`、`EFAULT`、`EBADF` 这几个返回值/错误怎么区分？

本节还会回答一个更隐蔽的问题：**如果我把 `count` 传得比 buffer 实际大小大得多，内核会拦住我吗？**（答案你可能会意外。）

---

## 1. 原型与内核链路

```c
#include <unistd.h>
ssize_t read(int fd, void *buffer, size_t count);
/* >0 读到的字节数（可能 < count）；0 = EOF；-1 = 出错 */
```

```
用户态 read(fd, buf, count)
      ▼
SYSCALL_DEFINE3(read)          fs/read_write.c:621
      ▼
ksys_read()                    fs/read_write.c:602
      ├─→ fdget_pos(fd)       ← 由 fd 取 struct file（校验 fd 有效）
      ├─→ file_ppos()         ← 取偏移指针（不可 seek 对象返回 NULL）
      ├─→ vfs_read()          ← 通用校验 + 分派（见下）
      └─→ 成功则回写 f_pos，fdput_pos(f)
```

`vfs_read()` 的**逐字全文**（`fs/read_write.c:450-478`，v6.6）：

```c
ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
{
	ssize_t ret;

	if (!(file->f_mode & FMODE_READ))
		return -EBADF;
	if (!(file->f_mode & FMODE_CAN_READ))
		return -EINVAL;
	if (unlikely(!access_ok(buf, count)))
		return -EFAULT;

	ret = rw_verify_area(READ, file, pos, count);
	if (ret)
		return ret;
	if (count > MAX_RW_COUNT)
		count =  MAX_RW_COUNT;

	if (file->f_op->read)
		ret = file->f_op->read(file, buf, count, pos);
	else if (file->f_op->read_iter)
		ret = new_sync_read(file, buf, count, pos);
	else
		ret = -EINVAL;
	if (ret > 0) {
		fsnotify_access(file);
		add_rchar(current, ret);
	}
	inc_syscr(current);
	return ret;
}
```

注意校验顺序：先 `EBADF`（fd 没读权限）→ `EINVAL`（对象不可读）→ `EFAULT`（用户地址非法）→ `rw_verify_area`（范围/锁）。`EBADF` 和 `EFAULT` 是最常见的两个坑（见第 3、4 节实测）。

其中 `FMODE_READ`（`0x1`）与 `FMODE_CAN_READ`（`0x20000`）分别在 `include/linux/fs.h:111` 和 `:149`；`MAX_RW_COUNT` 在 `:2399`，定义是 `(INT_MAX & PAGE_MASK)` —— 约 2 GiB 减一页。

## 2. 返回值语义

| 返回 | 含义 | 处理 |
|------|------|------|
| **`> 0`** | 读到的字节数，**可能小于 `count`（短读）** | 循环继续读剩余 |
| **`0`** | EOF（文件末尾） | 结束读取 |
| **`-1` / `errno=EINTR`** | 被信号中断（**不是错误**） | 重试，或 `SA_RESTART` |
| **`-1` / 其他 errno** | 真错误（`EBADF`/`EFAULT`/`EIO`…） | 报错处理 |

## 3. 短读（short read）：正常现象，必须循环

`read` 返回的字节数**没有义务**等于 `count`。短读在以下对象上尤其常见：

| 对象 | 短读原因 |
|------|---------|
| 管道/FIFO | 缓冲区里当前只有这么多数据 |
| socket | 收到一个 TCP 段就返回，不等填满 |
| 终端 | 通常读到换行就返回（行规程） |
| 普通文件 | 接近 EOF 时最后一次不足 `count` |

因此网络/管道编程必须写「循环读到 EOF 或读满」的封装。最常用的 `readall`：

```c
ssize_t readall(int fd, void *buf, size_t n)
{
    size_t total = 0;

    while (total < n) {
        ssize_t r = read(fd, (char *) buf + total, n - total);
        if (r < 0 && errno == EINTR)
            continue;                       /* 信号中断：重试 */
        if (r < 0)
            return -1;                      /* 真错误 */
        if (r == 0)
            break;                          /* EOF：提前收工 */
        total += (size_t) r;
    }
    return (ssize_t) total;                 /* 可能 < n（遇到 EOF） */
}
```

## 4. 代码：六组实测把语义钉死

完整源码 [`code/c4_4_read.c`](../code/c4_4_read.c)：

```c
/* c4_4_read.c — read() 的三种返回值：正数（可能短读）/ 0（EOF）/ -1（错误）
 *
 * 演示五件事：
 *   1) 循环读到 EOF 的正确写法
 *   2) 短读是正常现象：小 buffer 读大文件，一次读不满
 *   3) EBADF：fd 无效，或没以读方式打开
 *   4) EFAULT：buf 指针非法（用户态内存 bug 的暴露点）
 *   5) 读管道时的短读：有多少读多少，绝不等待
 *
 * 编译: gcc -O0 -Wall -o c4_4_read c4_4_read.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/stat.h>

int main(void)
{
    char buf[64];
    ssize_t n;

    printf("== 1. 循环读到 EOF ==\n");
    const char *path = "/tmp/c4_read.txt";
    int w = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    const char *text = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ";   /* 36 字节 */
    write(w, text, 36);
    close(w);

    int fd = open(path, O_RDONLY);
    int rounds = 0, total = 0;
    while ((n = read(fd, buf, sizeof buf)) > 0) {     /* 只在 >0 时继续 */
        rounds++;
        total += (int) n;
        printf("  第 %d 次 read(64) -> %2zd 字节\n", rounds, n);
    }
    printf("  退出循环时 read 返回 %zd（0 = EOF，不是错误）\n", n);
    printf("  合计 %d 字节，%d 轮\n", total, rounds);

    printf("\n== 2. 短读：请求 8 字节，可文件只剩 6 字节 ==\n");
    off_t end = lseek(fd, 0, SEEK_END);
    lseek(fd, end - 6, SEEK_SET);            /* 挪到最后 6 个字节 */
    char small[8];
    n = read(fd, small, sizeof small);       /* 请求 8，实际只有 6 可读 */
    printf("  在「剩余 6 字节」处 read(8) -> %zd 字节  ← 短读！请求 8，只给 6\n", n);
    n = read(fd, small, sizeof small);
    printf("  再 read(8) -> %zd  ← 0 = EOF\n", n);
    printf("  → 短读不是错误，它是 read 的**正常**返回值之一。\n");
    printf("    管道/终端/socket 上「返回 < 请求」更是家常便饭。\n");
    close(fd);

    printf("\n== 3. EBADF：fd 侧的问题 ==\n");
    int wfd = open(path, O_WRONLY);        /* 以「只写」打开 */
    errno = 0;
    n = read(wfd, buf, 10);
    printf("  用只写 fd 去 read -> %zd  errno=%d (%s)\n", n, errno, strerror(errno));
    close(wfd);

    errno = 0;
    n = read(999, buf, 10);                /* 一个没打开过的号 */
    printf("  用 fd=999 去 read -> %zd  errno=%d (%s)\n", n, errno, strerror(errno));

    printf("\n== 4. EFAULT：buf 侧的问题（地址非法）==\n");
    fd = open(path, O_RDONLY);
    volatile long bad_addr = 0x1;            /* volatile：让 gcc 别静态推断出「目标在地址 0」 */
    errno = 0;
    n = read(fd, (void *) bad_addr, 10);     /* 这个地址落在内核区，access_ok 挡下 */
    printf("  read(fd, (void*)0x1, 10) -> %zd  errno=%d (%s)\n",
           n, errno, strerror(errno));
    printf("  → EBADF 查「句柄」，EFAULT 查「内存」。两个不同的坑。\n");
    close(fd);

    printf("\n== 5. 从管道读：有多少读多少 ==\n");
    int p[2];
    pipe(p);
    write(p[1], "abc", 3);                 /* 只放 3 字节 */
    n = read(p[0], buf, sizeof buf);        /* 却要 64 字节 */
    printf("  管道里只有 3 字节，read(64) -> %zd 字节\n", n);
    printf("  → 管道上 read 不会「等到凑满 64 字节」再返回。\n");
    write(p[1], "de", 2);
    n = read(p[0], buf, sizeof buf);
    printf("  再放 2 字节，read(64) -> %zd 字节\n", n);
    close(p[0]);
    close(p[1]);

    printf("\n== 6. count 远超 buffer 实际大小，会怎样 ==\n");
    fd = open(path, O_RDONLY);
    volatile size_t huge = (size_t) 1 << 30;   /* 1 GiB；volatile 防编译器静态告警 */
    errno = 0;
    n = read(fd, buf, huge);                   /* buf 实际只有 64 字节！ */
    printf("  read(fd, buf[64], 1GiB) -> %zd  errno=%d (%s)\n",
           n, errno, strerror(errno));
    printf("  → 居然成功。因为内核只知道「从 buf 起、长 1GiB」这个范围落在用户空间里，\n");
    printf("    它无从知道 buf 真正分配了多少字节。文件只有 36 字节，所以只拷了 36 字节。\n");
    printf("  ⚠️ 若这个文件真有 1GiB，这行就会往 64 字节的栈缓冲里灌 1GiB —— 静默栈溢出。\n");
    printf("  → count 必须由「缓冲区实际大小」决定，内核不替你把关。\n");
    close(fd);
    unlink(path);
    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c4_4_read c4_4_read.c && ./c4_4_read
```

CE（gcc 13.3.0 / x86-64 / Ubuntu 24.04）实测：

```text
== 1. 循环读到 EOF ==
  第 1 次 read(64) -> 36 字节
  退出循环时 read 返回 0（0 = EOF，不是错误）
  合计 36 字节，1 轮

== 2. 短读：请求 8 字节，可文件只剩 6 字节 ==
  在「剩余 6 字节」处 read(8) -> 6 字节  ← 短读！请求 8，只给 6
  再 read(8) -> 0  ← 0 = EOF
  → 短读不是错误，它是 read 的**正常**返回值之一。
    管道/终端/socket 上「返回 < 请求」更是家常便饭。

== 3. EBADF：fd 侧的问题 ==
  用只写 fd 去 read -> -1  errno=9 (Bad file descriptor)
  用 fd=999 去 read -> -1  errno=9 (Bad file descriptor)

== 4. EFAULT：buf 侧的问题（地址非法）==
  read(fd, (void*)0x1, 10) -> -1  errno=14 (Bad address)
  → EBADF 查「句柄」，EFAULT 查「内存」。两个不同的坑。

== 5. 从管道读：有多少读多少 ==
  管道里只有 3 字节，read(64) -> 3 字节
  → 管道上 read 不会「等到凑满 64 字节」再返回。
  再放 2 字节，read(64) -> 2 字节

== 6. count 远超 buffer 实际大小，会怎样 ==
  read(fd, buf[64], 1GiB) -> 36  errno=0 (Success)
  → 居然成功。因为内核只知道「从 buf 起、长 1GiB」这个范围落在用户空间里，
    它无从知道 buf 真正分配了多少字节。文件只有 36 字节，所以只拷了 36 字节。
  ⚠️ 若这个文件真有 1GiB，这行就会往 64 字节的栈缓冲里灌 1GiB —— 静默栈溢出。
  → count 必须由「缓冲区实际大小」决定，内核不替你把关。
```

逐条看：

| 观察 | 说明 |
|------|------|
| `read(64)` 一次拿到 36 字节，然后再读得 `0` | EOF 用 **0** 表达（不是 -1）。`0` 和 `-1` 是两种截然不同的结束方式 |
| 请求 8 字节、只剩 6 字节 → 返回 **6** | 这就是短读。**不要写 `if (read(...) != count) 出错`** |
| 只写打开的 fd 去 `read` → `EBADF` | 同一个 `EBADF`，两种成因：**fd 无效**（`999`）或**没以读方式打开**（`vfs_read` 里 `FMODE_READ` 检查失败） |
| `(void *)0x1` → `EFAULT` | 地址 `0x1` 落在内核地址空间，`access_ok()` 直接挡下。**注意是 `-1` + `EFAULT`，不是段错误**——内核替你拦住了 |
| 管道里有 3 字节，`read(64)` 返回 3 | 流式对象**不承诺读满**。这跟普通文件的行为一样，但成因不同：管道里"暂时只有这么多" |
| **`read(fd, buf[64], 1GiB)` 返回 36、`errno=0`** | **最反直觉的一条**。内核不检查"你的 buffer 到底多大"——它只能验证 `[buf, buf+1GiB)` 这个地址范围在用户空间内。文件只有 36 字节，所以实际只拷了 36 字节；如果文件真有 1GiB，这行就是一次**静默的栈溢出** |

> 第 6 条值得单独记一笔。`access_ok()` 的语义是「这个地址范围**属于用户空间**吗」，不是「用户真的分配了这么多吗」——后者内核无法知道（`malloc` 的账本在 libc 里，不在内核里）。所以 `count` 是**你的责任**。这也解释了为什么「传一个巨大的 `count` 去读」不是防御手段，而是 bug。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 行情流短读 | 从 socket 读行情，一次 `read` 可能只回一个帧的碎片，必须按协议边界循环拼包 |
| `EFAULT` 定位野指针 | 传入未初始化/已释放的 `buf` 会触发 `access_ok` → `EFAULT`，是用户态内存 bug 的常见暴露点 |
| `EINTR` 被信号打断 | 交易进程收到信号（如定时器、`SIGALRM`）会打断阻塞读，循环重试或 `SA_RESTART` 是必备处理 |
| 少 syscall | 每次 `read` 陷入内核（`vfs_read` 末尾 `inc_syscr(current)` 就在数这个）；批量读大缓冲比多次小 `read` 更省 |
| `count` 必须等于 buffer 大小 | 用 `sizeof buf` 而不是魔数。第 6 节的实测说明：传错了内核不会报错，只会静默越界 |

<summary>代码自测（Q&A）</summary>

**Q1：`read()` 返回 `-1` 且 `errno=EBADF` 和 `errno=EFAULT` 分别是什么问题？**
A：`EBADF` 是 **fd 侧**的问题——`fd` 无效（没打开/已关闭，实测 `fd=999` 得 `errno=9`），或没以读方式打开（`vfs_read` 里 `!(f_mode & FMODE_READ)`）。`EFAULT` 是 **buf 侧**的问题——`buf` 指向的地址非法（野指针、已释放内存），`access_ok` 检查失败（实测 `(void*)0x1` 得 `errno=14`）。两者一个是句柄错、一个是内存错。

**Q2：`read` 一定会读满请求的字节数吗？**
A：不。`read` 可能返回少于 `count` 的字节（短读），尤其在管道、socket、终端上。实测「请求 8 字节、文件只剩 6 字节」就直接返回 6。只有「读满或遇 EOF」这个目标要靠**循环**保证，单次 `read` 不作任何承诺。

**Q3：返回 `0`（EOF）和返回 `-1`（错误）怎么区分？**
A：`0` 表示**正常**到达文件末尾，不是错误；`-1` 才表示出错（具体看 `errno`）。用 `feof()` 预判 EOF 是反模式（它只在读越过末尾后才为真），正确做法是检查 `read` 返回值本身。

**Q4：`read` 被信号打断返回 `EINTR`，为什么「不是错误」？**
A：信号处理函数返回后，系统调用可能被打断（无 `SA_RESTART` 时），此时数据没读、也没出错，只是「还没读完」。语义上应重试同一调用。`readall` 里的 `if (r < 0 && errno == EINTR) continue;` 就是标准处理。

**Q5：`read(fd, buf, 1<<30)` 这种超大请求，内核会怎么处理？**
A：分两步看。① `vfs_read` 里 `if (count > MAX_RW_COUNT) count = MAX_RW_COUNT;`（`fs.h:2399`，约 2 GiB 减一页）会把请求**截断**到上限。② 但截断**之后**的 `count` 仍然可能远大于你 buffer 的实际大小——`access_ok` 只验证地址范围在用户空间内，管不了你的分配大小。**实测：`char buf[64]` 传 `1GiB`，`read` 返回 36、`errno=0`，一切"正常"。** 如果文件真有那么大，就是静默越界。

**Q6：为什么从管道 `read(64)` 只返回 3 字节，而不是阻塞到凑满 64 字节？**
A：因为 `read` 的语义是「**有多少给多少**」，不是「读满才返回」。管道是流式对象，内核认为「先交付已有的数据」比「等到攒够」更有用（否则交互式程序会卡死）。想"凑满"必须自己循环——这就是 `readall` 存在的理由。

</details>
