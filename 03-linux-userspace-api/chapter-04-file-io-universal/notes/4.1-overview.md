## 本节讲什么

这是「文件 I/O」的开篇，回答三个问题：

1. Linux 操作一切资源（普通文件、设备、管道、socket）的**统一入口**是什么？
2. 文件描述符（fd）到底是什么？它在内核里长什么样？
3. 一套「万能 I/O 模型」由哪几个系统调用拼成，各自干什么？

原书这里只做概念铺垫；本节补上内核侧的 `struct file` / `struct fdtable` 坐标，再把「fd 只是一个整数」这句话**跑给你看**——fd 怎么分配、怎么回收、0 号为什么不是特权。

## 1. 万物皆文件：统一的 I/O 入口

Linux 用**同一套系统调用**操作所有 I/O 资源。无论目标是磁盘上的普通文件、`/dev` 下的设备文件、管道、套接字，还是 `/proc` 里的伪文件，都走同一条路：先 `open()` 拿到 fd，再用 `read()`/`write()` 读写，最后 `close()`。

| 操作 | 系统调用 | 原型 | 内核入口（v6.6） |
|------|---------|------|------------------|
| 打开 | `open()` | `int open(const char *pathname, int flags, ...);` | `SYSCALL_DEFINE3(open)` @ `fs/open.c:1441` |
| 读 | `read()` | `ssize_t read(int fd, void *buf, size_t count);` | `SYSCALL_DEFINE3(read)` @ `fs/read_write.c:621` |
| 写 | `write()` | `ssize_t write(int fd, const void *buf, size_t count);` | `SYSCALL_DEFINE3(write)` @ `fs/read_write.c:646` |
| 关闭 | `close()` | `int close(int fd);` | `SYSCALL_DEFINE1(close)` @ `fs/open.c:1557` |
| 定位 | `lseek()` | `off_t lseek(int fd, off_t offset, int whence);` | `SYSCALL_DEFINE3(lseek)` @ `fs/read_write.c:311` |

`ioctl()`（`SYSCALL_DEFINE3(ioctl)`）则是「通用模型之外」的兜底，处理设备专属控制（见 4.8）。

> 这四行行号是**实测**（对 v6.6 源码 `grep -n` 得到），不是从别处抄的——第 5 章、第 10 章都用同一套核对方式。

## 2. 文件描述符（fd）：一个整数背后的三层结构

fd 是**进程内**用来引用「已打开文件」的非负整数。用户态看到的就是个 `int`，但内核里它只是一张表的下标：

```
进程 task_struct
   └── files_struct  (struct files_struct @ include/linux/fdtable.h:49)
         ├── fdt  → struct fdtable @ :27
         │          ├── max_fds          容量上限
         │          └── fd[]   struct file * 数组  ← fd 就是这个数组的下标
         └── fdtab（内嵌的小 fdtable，前 64 个 fd 的快速路径）
```

三层关系（这是 Ch5 要深挖的核心，这里先立骨架）：

| 层 | 数据结构 | 位置 | 关键字段 |
|----|---------|------|----------|
| **fd 表** | `struct fdtable` | `include/linux/fdtable.h:27` | `fd[]`（`struct file *` 数组）、`max_fds` |
| **打开文件描述** | `struct file` | `include/linux/fs.h:992` | `f_mode`（`:1004`）、`f_count`（`:1005`）、`f_pos`（`:1007`）、`f_flags`（`:1008`）、`f_op` |
| **inode 对象** | `struct inode` | `include/linux/fs.h` | 文件真实属性、数据块位置 |

几个必须记住的事实：

| 事实 | 说明 |
|------|------|
| **默认三个 fd** | `0`=`STDIN_FILENO`、`1`=`STDOUT_FILENO`、`2`=`STDERR_FILENO`（`<unistd.h>`） |
| **最小可用分配** | 新 `open()` 返回**当前最小的未用 fd**；`close(fd)` 后该号可被复用 |
| **进程私有** | 两进程里相同数字的 fd，通常指向**不同**的打开实例 |
| **偏移在 struct file** | 读写位置 `f_pos` 存在打开文件描述里，**不在** fd 表里（所以 `dup`/`fork` 共享偏移，见 Ch5） |

> `f_pos` 在 `fs.h:1007` 这个坐标值得记牢——Ch5 讲「为什么 `dup` 共享偏移而两次 `open` 不共享」时，它就是答案本身。

## 3. 万能 I/O 模型全景

```
用户态
  open(path, flags, mode) ──→ 返回 fd（最小可用）
        │
        ▼
  read(fd, buf, n)  /  write(fd, buf, n)
        │                 │
        ▼                 ▼
     vfs_read()        vfs_write()     ← 校验 + 分派到 f_op->read/write
        │                 │
        └────────┬────────┘
                 ▼
        close(fd)  ──→ 释放 fd 槽位 + 引用计数减一
   （lseek 改 f_pos；ioctl 走设备专属命令，视对象而定）
```

这条链路是「一切皆文件」的实现基础：`read`/`write` 不关心目标是 ext4 文件还是 tty 设备，差异被 VFS 层的 `f_op` 函数指针吸收（见 4.2）。

## 4. 代码：fd 的分配规则，跑一遍看

「fd 是最小可用号」「close 后号会被复用」这两句话，背下来容易，验证一遍才真信。

完整源码 [`code/c4_1_fd_basics.c`](../code/c4_1_fd_basics.c)：

```c
/* c4_1_fd_basics.c — fd 到底是什么：进程内「打开文件表」的下标
 *
 * 演示四件事：
 *   1) 三个标准 fd（0/1/2）的常量值
 *   2) 新 fd 从「当前最小可用」数字分配
 *   3) close 掉的号立刻被回收复用
 *   4) fd 表在内核里的样子（/proc/self/fd/ 这个目录本身就是一个 fd）
 *
 * 编译: gcc -O0 -Wall -o c4_1_fd_basics c4_1_fd_basics.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
#include <dirent.h>

static void list_open_fds(const char *tag)
{
    DIR *d = opendir("/proc/self/fd");      /* 注意：opendir 自己也会占一个 fd */
    struct dirent *e;

    printf("  [%s] /proc/self/fd 里有: ", tag);
    while ((e = readdir(d)) != NULL) {
        if (e->d_name[0] == '.')            /* 跳过 . 和 .. */
            continue;
        printf("%s ", e->d_name);
    }
    printf("\n");
    closedir(d);
}

int main(void)
{
    printf("== 1. 三个标准 fd 的常量 ==\n");
    printf("  STDIN_FILENO  = %d\n", STDIN_FILENO);
    printf("  STDOUT_FILENO = %d\n", STDOUT_FILENO);
    printf("  STDERR_FILENO = %d\n", STDERR_FILENO);

    printf("\n== 2. 新 fd 从「最小可用」开始分配 ==\n");
    int a = open("/tmp/c4_a.txt", O_CREAT | O_RDWR, 0644);
    int b = open("/tmp/c4_b.txt", O_CREAT | O_RDWR, 0644);
    printf("  open a -> %d\n", a);
    printf("  open b -> %d\n", b);

    printf("\n== 3. close 之后那个号立刻被回收 ==\n");
    close(a);
    int c = open("/tmp/c4_c.txt", O_CREAT | O_RDWR, 0644);
    printf("  close(%d) 后 open c -> %d   （%s）\n", a, c,
           c == a ? "复用了刚释放的号" : "没有复用，说明另有空闲号");

    printf("\n== 4. fd 表长什么样：/proc/self/fd ==\n");
    list_open_fds("a b c 都开着时");
    printf("  当前我持有的: a=%d b=%d c=%d\n", a, b, c);

    printf("\n== 5. 经典技巧：关掉 0 号，新 fd 就会拿到 0 ==\n");
    int saved0 = dup(STDIN_FILENO);         /* 先把 0 号备份到别的号 */
    close(STDIN_FILENO);
    int d = open("/tmp/c4_d.txt", O_CREAT | O_RDWR, 0644);
    printf("  close(0) 后 open d -> %d   （%s）\n", d,
           d == 0 ? "拿到 0 号：0 不是特权，只是默认值" : "没拿到 0");

    dup2(saved0, STDIN_FILENO);             /* 恢复 0 号 */
    close(saved0);
    close(b);
    close(c);
    close(d);
    list_open_fds("收尾");
    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c4_1_fd_basics c4_1_fd_basics.c && ./c4_1_fd_basics
```

在 Compiler Explorer（gcc 13.3.0 / x86-64 / Ubuntu 24.04，沙箱内核 Linux 7.0.0-1012-aws）上实测：

```text
== 1. 三个标准 fd 的常量 ==
  STDIN_FILENO  = 0
  STDOUT_FILENO = 1
  STDERR_FILENO = 2

== 2. 新 fd 从「最小可用」开始分配 ==
  open a -> 3
  open b -> 4

== 3. close 之后那个号立刻被回收 ==
  close(3) 后 open c -> 3   （复用了刚释放的号）

== 4. fd 表长什么样：/proc/self/fd ==
  [a b c 都开着时] /proc/self/fd 里有: 0 1 2 3 4 5 
  当前我持有的: a=3 b=4 c=3

== 5. 经典技巧：关掉 0 号，新 fd 就会拿到 0 ==
  close(0) 后 open d -> 0   （拿到 0 号：0 不是特权，只是默认值）
  [收尾] /proc/self/fd 里有: 0 1 2 
```

逐条看：

| 观察 | 说明 |
|------|------|
| `a=3, b=4` | 0/1/2 被占着，所以第一个可用号是 3、然后 4。**「最小可用」不是「排到最后」** |
| `close(3)` 后新 `open` 又拿到 3 | 号被立刻回收，说明内核维护的是一张**位图**（`fdtable::open_fds`），不是在末尾追加 |
| 第 4 节列出 `0 1 2 3 4 5` 共 6 个 | 前 5 个是进程自己的（0/1/2 + a/b/c 里的 3、4），**多出来的 5 是 `opendir()` 自己占的**——列 fd 表这个动作本身也消耗 fd |
| `close(0)` 后 `open` 拿到 0 | **0 号没有任何特权**，它只是「进程启动时恰好被 stdin 占用」的普通槽位。这就是「关闭标准输入再打开文件，新 fd 变成 0」那个老技巧的根据 |

> 第 4 节那行输出里藏着一个小陷阱：你看到的 `5` 其实来自 `opendir`。所以**别拿 `/proc/self/fd` 去数「我自己开了几个 fd」**——至少要多减 1（如果实现里还用 `readdir` 之外的缓冲，可能要减更多）。生产代码判断泄漏应该看 `/proc/<pid>/fdinfo` 配合 `rlimit`，或者用 `ls /proc/self/fd | wc -l` 前后对比。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| fd 泄漏耗尽句柄 | 每个 `open` 占一个 fd 槽位，不 `close` 会一直涨到 `ulimit -n` 上限 → 无法再开新文件/socket |
| 热路径少 syscall | 每次 `read`/`write` 都陷入内核（`inc_syscr` 计数），高频率行情读写要批量化或走 `mmap` |
| 设备统一访问 | 嵌入式里 `/dev/mem`、自定义字符设备都走同一套 `open/read/write`，专属控制交给 `ioctl` |
| 偏移是共享状态 | `f_pos` 在 `struct file` 里，`fork`/`dup` 后父子/多 fd 共享同一偏移，并发写要 `O_APPEND` 或文件锁（Ch5） |
| 守护进程重绑 0/1/2 | 服务常 `close(0); open("/dev/null", O_RDONLY)` 把标准 fd 指向安全对象，防止程序误读已断开的终端 |

<details>
<summary>代码自测（Q&A）</summary>

**Q1：fd 为什么「进程私有」？两个进程里 fd=3 一定指向不同文件吗？**
A：fd 只是本进程 `files_struct->fdtab.fd[]` 数组的下标。每个进程有自己的 `files_struct`，下标 3 对应的是各自数组里存的 `struct file *`，完全可以指向不同文件。唯一的例外是 `fork` 后子进程继承了父进程的 fd 表（`copy_files`），此时父子 fd=3 指向**同一个** `struct file`（共享偏移）。

**Q2：`open()` 返回的 fd 为什么总是「最小可用」？**
A：内核在 `get_unused_fd_flags()` 里用位图（`open_fds`）找第一个为 0 的位。刚关掉的 fd 号立即回收到位图里，所以下次 `open` 会优先复用。实测里 `close(3)` 之后新 `open` 又拿到 3，就是这个机制的直观证据。这也是「关闭 0 号 fd 再打开文件，新 fd 变成 0」这类技巧的根据。

**Q3：读写偏移 `f_pos` 为什么放在 `struct file`（`fs.h:1007`）而不放在 fd 表里？**
A：因为 `dup`/`dup2`/`fork` 会复制 fd 表，但希望**共享**同一个读写位置——两个 fd 指向同一打开文件时，一个读了 100 字节，另一个看到的偏移也前进 100。若偏移存在 fd 表里就做不到共享。代价是并发读写同一文件时偏移是竞争点，需 `O_APPEND` 或锁（Ch5）。

**Q4：本章 5 个系统调用里，哪两个「不是所有文件类型都支持」？**
A：`lseek` 和 `ioctl` 视对象而定。管道/socket/终端不设 `FMODE_LSEEK`（`fs.h:115` 定义该位），`lseek` 返回 `-ESPIPE`（见 4.7，实测 `errno=29`）；`ioctl` 只有实现了对应命令的设备才有意义，普通文件上多数 `ioctl` 返回 `-ENOTTY`（见 4.8，实测 `errno=25`）。`open/read/write/close` 则是真正的「万能四件套」。

**Q5：为什么说「每个 fd 占内核资源」，进程退出时会自动回收吗？**
A：fd 表项、`struct file`（引用计数）都是内核对象。进程退出时 `exit_files()` 会逐个 `fput`，把引用计数减到 0 并释放 `struct file`，所以正常退出不会永久泄漏 fd。但**长驻进程**里不 `close` 的 fd 会一直占着，直到进程结束——这正是服务进程 fd 泄漏的根源。

**Q6：`/proc/self/fd` 列出来的条目数，等于我打开的文件数吗？**
A：不等于。实测里我持有 5 个 fd（0/1/2 + a/b/c 中的 3、4），但目录列出 6 个——多出来的那个是 `opendir()` 自己占的。任何「通过某个 fd 去读 fd 表」的操作都会把自己算进去，数数时记得扣掉。

</details>
