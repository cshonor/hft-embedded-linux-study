## 一、慢系统调用与 `EINTR`

**慢系统调用（slow system call）** = 可能**无限期阻塞**的系统调用。

| 典型慢调用 | 例子 |
|-----------|------|
| 终端 / 管道 / socket 的 `read` | 等对端写数据 |
| 管道的 `write` | 等缓冲区有空间 |
| `open` 某些设备（FIFO、终端） | 等对端打开 |
| `wait` / `waitpid` | 等子进程退出 |
| `pause` / `sleep` / `nanosleep` | 等时间 |
| `select` / `poll` / `epoll_wait` | 等 I/O 事件 |
| `accept` / `connect` / `recv` / `send` | 等网络事件 |
| `flock` / `fcntl(F_SETLKW)` | 等文件锁 |

**`EINTR` 的产生**：

```
   进程阻塞在 read() 中（内核态，TASK_INTERRUPTIBLE）
        │
        ↓ 信号递送
   内核唤醒进程 → 执行 handler
        │
        ↓ handler 返回
   内核决定：这个 read() 怎么办？
        ├─ 不重启 → 返回 -EINTR 给用户态
        └─ 重启   → 重新执行 read()
```

不设 `SA_RESTART` 时，被中断的调用返回 `-1`，`errno = EINTR`。内核里对应的就是不重启分支：

```c
// kernel/signal.c:3040
long do_no_restart_syscall(struct restart_block *param)
{
	return -EINTR;
}
```

---

## 二、`SA_RESTART`：内核如何自动重启

设了 `SA_RESTART` 后，被中断的慢调用会**被内核自动重新执行**，用户态看不到 `EINTR`。

内核机制是 `task_struct.restart_block`——把被中断的 syscall 状态存下来，需要重启时调用其 `fn` 函数指针：

```c
// kernel/signal.c:3034
/**
 *  sys_restart_syscall - restart a system call
 */
SYSCALL_DEFINE0(restart_syscall)
{
	struct restart_block *restart = &current->restart_block;
	return restart->fn(restart);
}
```

```
   read(fd, buf, n) 阻塞中
        │
        ↓ 信号中断
   内核把 read 的参数/进度存入 current->restart_block
   并让 restart_block.fn = 对应的重启函数
        │
        ↓ handler 返回后，内核检查 SA_RESTART
   ┌────┴────┐
   设了 → 调 restart_block.fn()  重新执行（restart_syscall 通路）
   没设 → do_no_restart_syscall() 返回 -EINTR
```

> **注意**：重启是**内核态**行为，用户态完全无感知——`read()` 的返回地址不变，C 代码里就是一次普通的 `read()` 调用。这与「用户态手写 `while (EINTR)` 重试循环」有本质区别：内核重启不产生额外的系统调用开销。

## 三、哪些能重启，哪些不能（关键表）

**这是本节最重要的实践知识**：即便设了 `SA_RESTART`，以下情况**仍然返回 `EINTR`**。

| 类别 | 具体调用 | 设 `SA_RESTART` 后 |
|------|----------|-------------------|
| **普通慢调用** | `read`/`write`（终端、管道、socket）、`wait`/`waitpid`、`open`（FIFO/终端）、`flock`、`fcntl(F_SETLKW)` | ✅ **自动重启** |
| **带超时的等待** | `select`、`poll`、`epoll_wait`、`epoll_pwait`、`semop` 的 timeout、`sigtimedwait` | ❌ 返回 `EINTR` |
| **`connect`** | `connect()` | ❌ 返回 `EINTR` |
| **`send`/`sendto`/`sendmsg`** | 部分平台（尤其带 `SO_SNDTIMEO`） | ❌ 可能返回 `EINTR` |
| **`recv` 带 `MSG_WAITALL`** | 已收到部分数据时 | ❌ 返回已收字节数（非错误） |
| **`nanosleep`/`clock_nanosleep`** | 被中断 | ❌ 返回 `EINTR`，`rem` 中保存剩余时间 |
| **`ioctl`** | 部分设备 | ⚠️ 视驱动而定 |
| **`close`** | Linux 上 | ❌ 返回 `EINTR`，但 fd **已关闭**（详见陷阱） |

**为什么带超时的不能重启**：重启会重置超时计时，语义就变了（原本 3 秒超时可能变成 6 秒）。所以内核选择让调用者自己决定怎么处理。

**为什么 `connect` 不能重启**：`connect` 是非幂等的——重启会重新发起连接，可能掩盖错误。

## 四、防御性写法

**规则：即便设了 `SA_RESTART`，涉及 I/O 多路复用和网络的调用也应显式处理 `EINTR`。**

```c
/* read 的防御性包装 */
ssize_t read_retry(int fd, void *buf, size_t n)
{
    ssize_t ret;
    do {
        ret = read(fd, buf, n);
    } while (ret == -1 && errno == EINTR);
    return ret;
}

/* write 同理（注意部分写的处理） */
ssize_t write_retry(int fd, const void *buf, size_t n)
{
    ssize_t ret;
    do {
        ret = write(fd, buf, n);
    } while (ret == -1 && errno == EINTR);
    return ret;
}
```

### `nanosleep` 的剩余时间处理

`nanosleep` 被中断时，会在第二个参数里保存**剩余未睡完的时间**：

```c
/* 精确的睡眠：被信号中断后继续睡剩余时间 */
int sleep_full(const struct timespec *req)
{
    struct timespec rem = *req;
    while (nanosleep(&rem, &rem) == -1 && errno == EINTR)
        ;                       /* rem 已被更新为剩余时间 */
    return 0;
}
```

> **注意**：`sleep()` 被中断时返回**剩余秒数**（不是 -1），语义与 `nanosleep` 不同。而 `usleep()` 已被废弃。

## 五、陷阱：`close()` 返回 `EINTR` 时 fd 已关闭

这是 Linux 特有的一个坑：

```c
/* Linux 上：即使 close 返回 EINTR，fd 也已经被关闭了 */
if (close(fd) == -1 && errno == EINTR) {
    close(fd);        /* ❌ 危险！可能关掉了别人刚打开的 fd */
}
```

Linux 的 `close()` 即使在被信号中断的情况下也会完成关闭动作。此时若重试 `close(fd)`，而该 fd 号已被其他线程/代码分配给新文件，就会**误关别人的 fd**。

**正确做法**：在 Linux 上，`close()` 返回 `EINTR` 时**不要重试**。

> 对比：POSIX 原本规定 `close()` 返回 `EINTR` 时状态未定义（fd 可能关了也可能没关），所以可移植代码需要区分平台。Linux 的行为是"已关闭"，HP-UX 等是"未关闭"。

## 六、`EINTR` vs `EAGAIN`

两者都表示「没成功，但不一定是错误」，容易混淆：

| | `EINTR` | `EAGAIN` |
|--|---------|----------|
| 含义 | 被**信号**中断 | 资源暂时不可用（非阻塞 I/O 无数据） |
| 触发 | 慢调用 + 信号递送 | 非阻塞 fd 上 `read` 无数据 / `accept` 无连接 |
| 处理 | 通常**重试** | 通常**等下次事件通知**（epoll） |
| 是否错误 | ❌ 不是 | ❌ 不是 |

```c
ssize_t n = read(fd, buf, sizeof buf);
if (n == -1) {
    if (errno == EINTR)       /* 被信号打断 → 重试 */
        goto retry;
    else if (errno == EAGAIN) /* 无数据 → 返回事件循环 */
        return 0;
    else
        return -1;            /* 真错误 */
}
```

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 慢设备 I/O（串口/网络）极易被信号打断，嵌入式代码对 `read`/`write` **必须**处理 `EINTR` 重试，否则偶发中断会静默丢数据——这类 bug 往往几周才复现一次，现场极难定位。设 `SA_RESTART` 能从源头减少 `EINTR`，但 `select`/`poll` 仍要显式处理 |
| HFT | `EINTR` 是延迟抖动来源之一：阻塞中的 `recv`/`epoll_wait` 被打断后返回，若未重试会**漏掉一个事件周期**；若盲目重试又可能引入额外延迟。HFT 的正确做法是：统一 `while (ret < 0 && errno == EINTR)` 重试保证不丢事件，同时**把无关信号全部屏蔽**，从源头消除中断——让 `EINTR` 路径成为永不触发的冷路径 |

## 代码示例：观察 `SA_RESTART` 的效果

```c
/* eintrdemo.c —— 对比设/不设 SA_RESTART 时 read 的行为
 * 编译: gcc -o eintrdemo eintrdemo.c
 * 运行: 另开终端 kill -USR1 <pid> 触发信号 */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <stdlib.h>

static volatile sig_atomic_t caught = 0;
static void handler(int sig) { caught = 1; }

/* 用 alarm 自动发信号，避免手工操作 */
static void trial(const char *tag, int use_restart)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = use_restart ? SA_RESTART : 0;
    sigaction(SIGALRM, &sa, NULL);

    char buf[64];
    caught = 0;
    alarm(2);                              /* 2 秒后发 SIGALRM */
    ssize_t n = read(STDIN_FILENO, buf, sizeof buf);   /* 阻塞等输入 */

    if (n == -1 && errno == EINTR)
        printf("%-20s read 返回 -1, errno=EINTR（被中断，未重启）\n", tag);
    else
        printf("%-20s read 返回 %zd（已重启/读到数据）\n", tag, n);

    alarm(0);
}

/* nanosleep 的剩余时间处理演示 */
static void nanosleep_demo(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                        /* 不设 SA_RESTART */
    sigaction(SIGALRM, &sa, NULL);

    struct timespec req = { .tv_sec = 3, .tv_nsec = 0 };
    struct timespec rem = {0};

    alarm(1);                               /* 1 秒后打断 3 秒的睡眠 */
    while (nanosleep(&req, &rem) == -1 && errno == EINTR) {
        printf("nanosleep 被中断，剩余 %ld.%03lds，继续睡\n",
               (long)rem.tv_sec, rem.tv_nsec / 1000000);
        req = rem;                          /* 睡剩余时间 */
        alarm(0);
    }
    printf("nanosleep 完成\n");
}

int main(void)
{
    printf("=== SA_RESTART 对比（请在 2 秒内不要输入，等 SIGALRM 触发）===\n");
    trial("无 SA_RESTART:", 0);
    trial("有 SA_RESTART:", 1);             /* 这一路会一直阻塞到真输入 */

    printf("\n=== nanosleep 剩余时间处理 ===\n");
    nanosleep_demo();
    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b>什么是慢系统调用？被信号中断后会发生什么？</summary>

**慢系统调用** = 可能**无限期阻塞**的系统调用。

典型例子：终端/管道/socket 的 `read`、`write` 管道、`open` FIFO、`wait`、`pause`、`sleep`、`select`/`poll`/`epoll_wait`、`accept`/`connect`/`recv`、`flock`。

**被信号中断后**：

- **未设 `SA_RESTART`** → 调用返回 `-1`，`errno = EINTR`
- **设了 `SA_RESTART`** → 内核**自动重新执行**该调用，用户态无感知

内核里对应的两个分支：

```c
// 重启：从 restart_block 恢复并重新执行
SYSCALL_DEFINE0(restart_syscall)              // kernel/signal.c:3034
{
	struct restart_block *restart = &current->restart_block;
	return restart->fn(restart);
}

// 不重启：直接返回 EINTR
long do_no_restart_syscall(struct restart_block *param)   // :3040
{
	return -EINTR;
}
```

</details>

<details>
<summary><b>问 2：</b>设了 <code>SA_RESTART</code> 就万事大吉了吗？哪些调用仍会返回 <code>EINTR</code>？</summary>

**不可以高枕无忧**。以下调用即便设了 `SA_RESTART` **仍然返回 `EINTR`**：

| 类别 | 例子 | 原因 |
|------|------|------|
| **带超时** | `select`、`poll`、`epoll_wait`、`sigtimedwait`、`semop`(timeout) | 重启会重置超时，语义被破坏 |
| **`connect`** | `connect()` | 非幂等，重启会重新发起连接 |
| **`nanosleep`** | `nanosleep()` | 返回 `EINTR`，剩余时间存在 `rem` 参数里 |
| **`close`** | Linux `close()` | 返回 `EINTR`，但**fd 已关闭**（见陷阱） |
| 部分网络发送 | 带 `SO_SNDTIMEO` 的 `send` | 平台相关 |

**实践规则**：

1. `read`/`write`/`wait`/`open`(FIFO) 等普通慢调用 → `SA_RESTART` 能覆盖，但仍建议防御性重试
2. `select`/`poll`/`epoll_wait`/`connect`/`nanosleep` → **必须显式处理 `EINTR`**
3. `close` → Linux 上**不要**因 `EINTR` 重试

**一句话**：`SA_RESTART` 是减少 `EINTR` 的便利手段，不是免除 `EINTR` 处理的理由。

</details>

<details>
<summary><b>问 3：</b><code>close()</code> 返回 <code>EINTR</code> 时应该重试吗？</summary>

**在 Linux 上绝对不要重试。**

Linux 的 `close()` 实现即使在被信号中断的情况下也**已经完成了关闭动作**。此时 fd 号已经释放，可能被其他线程或后续 `open()` 分配给新文件。如果重试 `close(fd)`，就会**误关别人刚打开的文件**——这是极难排查的隐蔽 bug。

```c
/* ❌ 危险 */
if (close(fd) == -1 && errno == EINTR)
    close(fd);        /* 可能关掉别人刚分配的 fd！ */

/* ✅ 正确：不重试 */
close(fd);            /* 忽略 EINTR，fd 在 Linux 上已关闭 */
```

**为什么会有这种差异**：

POSIX 原本规定 `close()` 返回 `EINTR` 时 fd 状态**未定义**（可能关了也可能没关），所以可移植代码需要区分平台：

| 平台 | `close` 返回 `EINTR` 时 fd 状态 |
|------|-------------------------------|
| **Linux** | **已关闭**（不要重试） |
| HP-UX 等传统 UNIX | 未关闭（可重试） |

Linux 后来明确了这个行为，并成为事实标准。**写 Linux 专用代码时，`close()` 一律不重试 `EINTR`。**

</details>

<details>
<summary><b>问 4：</b><code>nanosleep</code> 被信号打断后怎么保证睡够指定时长？</summary>

`nanosleep` 被中断时返回 `-1`，`errno = EINTR`，并在**第二个参数（`rem`）**里写入**剩余未睡完的时间**。循环时用 `rem` 更新请求即可：

```c
int sleep_full(const struct timespec *req)
{
    struct timespec rem = *req;
    while (nanosleep(&rem, &rem) == -1 && errno == EINTR)
        ;                        /* 循环体为空：rem 已被内核更新为剩余时间 */
    return 0;
}
```

**关键点**：第二个参数既是输出又是下一次的输入。上例中 `rem` 在每次失败后被更新，直接复用即可。

**对比其他睡眠接口**：

| 接口 | 被信号中断时 | 如何恢复 |
|------|-------------|----------|
| `nanosleep(&req, &rem)` | 返回 `-1`，`errno=EINTR`，`rem` 存剩余时间 | 用 `rem` 继续 |
| `clock_nanosleep(..., &rem)`（不设 `TIMER_ABSTIME`） | 同上 | 同上 |
| `clock_nanosleep(..., TIMER_ABSTIME)` | 返回 `EINTR`，**不写 `rem`** | 用**绝对时间**重新调用（天然正确） |
| `sleep(sec)` | 返回**剩余秒数**（不是 -1） | 用返回值继续 |
| `usleep()` | 返回 `-1`，`errno=EINTR` | 已废弃，勿用 |

**推荐**：需要精确时长时用 `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`——绝对时间语义下，重试天然不会累积误差，也不受 `SA_RESTART` 影响。

</details>

<details>
<summary><b>问 5：</b><code>EINTR</code> 和 <code>EAGAIN</code> 有什么区别？分别该怎么处理？</summary>

| | `EINTR` | `EAGAIN` |
|--|---------|----------|
| 含义 | 被**信号**中断 | 资源暂时不可用 |
| 触发场景 | 慢调用阻塞中信号递送 | 非阻塞 fd 上 `read` 无数据 / `accept` 无待处理连接 / `fork` 达上限 |
| 本质 | 被外部事件打断 | 条件不满足 |
| 处理 | **重试** | **等下次事件通知**（回到 epoll 循环） |

**典型处理框架**：

```c
ssize_t n = read(fd, buf, sizeof buf);
if (n >= 0) {
    /* 成功，处理数据 */
} else if (errno == EINTR) {
    goto retry;                 /* 被信号打断 → 立即重试 */
} else if (errno == EAGAIN || errno == EWOULDBLOCK) {
    return 0;                   /* 无数据 → 回事件循环，不要忙等重试！ */
} else {
    return -1;                  /* 真错误 */
}
```

**关键区别在处理动作**：

- **`EINTR` → 立即重试**：信号已经处理完，重试大概率能继续
- **`EAGAIN` → 不要重试**：立刻重试只会空转烧 CPU。正确做法是回到 `epoll_wait` 等待下次事件通知

**HFT 特别注意**：把 `EAGAIN` 当成 `EINTR` 去重试，会在无数据时产生**忙等**，直接烧毁一个 CPU 核心——这是低延迟系统里常见的性能事故。

</details>
