## 一、为什么 handler 难写

回顾 [Ch20.4](../../chapter-20-signals-fundamentals/notes/20.4-introduction-to-signal-handlers.md) 的核心事实：

> **handler 不是新线程**——它在被打断线程**自己的栈**上执行，与被中断的代码**共享全部状态**。

这带来三个根本困难：

| 困难 | 说明 |
|------|------|
| **随时插入** | 主流程可能在**任意指令边界**被打断，包括"操作做到一半"的时刻 |
| **共享状态** | handler 与主流程读写同一批全局变量、堆、栈，天然是数据竞争 |
| **锁不可靠** | handler 与被中断代码在**同一线程**，加锁会导致**自我死锁**（锁不会被让出） |

```
   主流程                          handler
   ───────                         ───────
   malloc()
   ├─ 获取堆锁
   ├─ 正在修改空闲链表
   │                      ← 信号递送
   │                         malloc()
   │                         └─ 尝试获取堆锁 → 同一线程重入 → ❌ 死锁
```

**结论**：handler 里能做的事**非常有限**。这不是编码风格建议，而是信号机制的本质约束。

## 二、两条黄金法则

### 法则 1：handler 只做最小动作——通常是「设置一个标志」

```c
static volatile sig_atomic_t got_sigint = 0;

static void handler(int sig)
{
    got_sigint = 1;          /* 就这一行，最安全 */
}

/* 主循环里检查标志并做真正的处理 */
for (;;) {
    if (got_sigint) {
        got_sigint = 0;
        do_shutdown();       /* 这里可以随意调用 printf/malloc/... */
    }
    do_work();
}
```

这是**最推荐**的模式：把复杂逻辑移回主流程，handler 只留下一个原子的"通知"。

### 法则 2：handler 里只调用异步信号安全函数

**异步信号安全（async-signal-safe）函数** = 可以安全地在 handler 里调用的函数。判据：

- 不持有锁（或持有的锁不会与主流程冲突）
- 不使用静态/全局缓冲区（或使用时不会被重入破坏）
- 不依赖被中断代码的中间状态

| ✅ 安全（可直接用） | ❌ 不安全（禁止） |
|---------------------|-------------------|
| `write()`、`read()` | `printf()`、`fprintf()`、`sprintf()`（stdio 锁） |
| `_exit()`、`_Exit()` | `exit()`（flush stdio + atexit） |
| `kill()`、`raise()`、`sigaction()`、`sigprocmask()` | `malloc()`、`free()`、`calloc()`、`realloc()`（堆锁） |
| 给 `volatile sig_atomic_t` 赋值 | `strtok()`、`gmtime()`、`localtime()`（静态缓冲） |
| `strlen()`、`memcpy()`、`memset()` | 任何 `pthread_*` 函数 |
| `snprintf()`（实践中常用，但非 POSIX 保证） | `syslog()`、`fopen()`、`fclose()` |

> **权威清单**：`man 7 signal-safety` 给出完整的异步信号安全函数列表（POSIX + Linux 扩展）。写代码前应当查阅。
>
> **判断原则**：如果一个函数**可能加锁或分配内存**，就假定它不安全。

## 三、`volatile sig_atomic_t`：两个限定符各解决一个问题

handler 与主流程共享变量的标准写法：

```c
static volatile sig_atomic_t flag = 0;
```

**为什么两个限定符缺一不可？**

### `volatile` —— 防止编译器优化

```c
static sig_atomic_t flag = 0;      /* ❌ 少了 volatile */

while (!flag) {                     /* 编译器认为 flag 在本循环里没被改过 */
    do_work();                      /* → 优化成：读一次到寄存器，然后死循环 */
}
```

编译器**看不见** handler（它是被内核调用的，不在控制流里），因此会认为 `flag` 在主循环中不会改变，把它**缓存到寄存器**——主流程永远看不到 handler 写入的新值。

`volatile` 告诉编译器：**这个变量可能被你不知道的方式修改，每次都必须从内存重新读取**。

### `sig_atomic_t` —— 保证读写原子性

```c
static volatile long long counter = 0;    /* ❌ 8 字节，非原子 */

void handler(int sig) { counter++; }      /* 读-改-写，可能被信号打断 */
```

如果变量的操作不是原子的（如 64 位 `long long` 在 32 位系统上，或 `counter++` 这种读-改-写），信号可能在**操作中间**插入，导致半写状态：

```
   counter = 0x00000000FFFFFFFF
   handler 写入高 32 位 → 0x00000001FFFFFFFF
                          ↑ 此时主流程读取 → 得到"半新半旧"的垃圾值
   再写入低 32 位
```

`sig_atomic_t` 是 POSIX 保证**读写具有原子性**的整数类型（Linux 上通常是 `int`），单次读写不会被信号打断。

### 组合效果

| 限定符 | 解决的问题 | 不用的后果 |
|--------|-----------|-----------|
| `volatile` | 编译器优化（值被缓存到寄存器） | 主流程**永远看不到** handler 的修改 |
| `sig_atomic_t` | 非原子操作（半写状态） | 主流程读到**半新半旧**的垃圾值 |

> **注意**：`volatile sig_atomic_t` **只保证单次读写的原子性**，不保证 `flag++` 这类读-改-写的原子性。需要计数时，应让 handler 只做 `flag = 1`（单次写），或用其他 IPC 机制。

## 四、与主流程交换数据的正确模式

handler 里只能设标志，那需要传递更多信息怎么办？

| 模式 | 做法 | 适用 |
|------|------|------|
| **标志变量** | `volatile sig_atomic_t` | 只需"有没有发生" |
| **无锁环形队列** | handler 写，主流程读（SPSC） | 需传递多条记录，且要求零锁 |
| **eventfd** | handler 里 `write(efd, &one, 8)`，主流程 epoll 监听 | 需计数、需接入事件循环 |
| **self-pipe** | handler 写管道一字节，主流程 `read` | 经典技巧，可移植 |
| **signalfd** | 不用 handler，直接 `read()` 信号 | **最干净**，见 [Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md) |
| **sigwaitinfo** | 不用 handler，同步取 | 多线程专用线程模型，见 [Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md) |

### self-pipe 技巧（经典可移植方案）

```c
static int pipe_fd[2];

static void handler(int sig)
{
    char c = (char)sig;
    write(pipe_fd[1], &c, 1);       /* write 是 async-signal-safe */
}

/* 主循环用 select/poll/epoll 监听 pipe_fd[0] */
```

把信号变成一个**字节流事件**，天然接入 I/O 多路复用。HFT 与网络服务广泛使用。

### 更现代：signalfd

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, NULL);      /* ① 必须阻塞，否则走 handler */

int sfd = signalfd(-1, &mask, SFD_NONBLOCK);   /* ② 信号变 fd */
/* ③ 加入 epoll，与业务 socket 一起等待 */
```

**优势**：完全没有 handler → 没有异步信号安全问题 → 处理代码里可随意 `printf`/`malloc`。这是 Linux 上**最推荐**的方案，详见 [Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md)。

## 五、其他设计要点

| 要点 | 说明 |
|------|------|
| **保护 `errno`** | handler 若调用了可能修改 `errno` 的函数，进入时保存、返回时恢复 |
| **不要做浮点运算** | 浮点寄存器状态在信号递送时的保存/恢复是架构相关的，handler 里用浮点可能破坏主流程的 FPU 状态 |
| **不要 `longjmp` 出去** | `sigsetjmp`/`siglongjmp` 是特化版本，普通 `longjmp` 会**不恢复信号掩码**，造成掩码泄漏 |
| **注意重入** | 默认情况下内核已自动阻塞同号信号（[Ch20.4](../../chapter-20-signals-fundamentals/notes/20.4-introduction-to-signal-handlers.md)），但**不同**信号仍可嵌套——用 `sa_mask` 屏蔽相关信号 |

```c
/* 保护 errno 的标准写法 */
void handler(int sig)
{
    int saved_errno = errno;        /* 保存 */
    /* ... 处理（可能调用修改 errno 的函数）... */
    errno = saved_errno;            /* 恢复 */
}
```

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | handler 必须极简——嵌入式线程栈小（8KB~64KB），复杂 handler 易溢出；且嵌入式常无调试器，handler 里的 bug 极难定位。对 `SIGSEGV` 务必配 `SA_ONSTACK` 备用栈（[21.3](21.3-handling-a-signal-on-an-alternate-stack-.md)）。诊断信息用 `write()` 直写 fd，绝不用 `printf` |
| HFT | handler 会**异步抢占关键路径**，是延迟毛刺的经典来源。HFT 的正确策略是**消灭 handler**：关键路径全程屏蔽无关信号，控制信号走 signalfd 进事件循环，让"信号处理"变成同步的 `read()`。若必须保留 handler，则严格遵循「只设 `volatile sig_atomic_t` 标志」这一条 |

## 代码示例

### 一、`flag_handler.c`（自编 · 21.1）

演示「handler 只置 `volatile sig_atomic_t` 旗、主循环消费」这一最推荐范式；顺带演示 `sa_mask`：`sigemptyset` 后 `sigaddset(&sa.sa_mask, SIGTERM)`，表示**仅在该 handler 执行期间**额外屏蔽 SIGTERM（不是永久屏蔽）。

完整源码（[`code/flag_handler.c`](../code/flag_handler.c)）：

```c
/* Canonical pattern: handler only sets volatile sig_atomic_t.
 * Also blocks SIGTERM while handling SIGINT (sa_mask demo).
 *
 * cc -Wall -Wextra -o flag_handler flag_handler.c && ./flag_handler
 */
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t got_sigint = 0;

static void on_int(int sig)
{
    (void)sig;
    got_sigint = 1;
}

int main(void)
{
    struct sigaction sa;
    int count = 0;

    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = on_int;
    sigemptyset(&sa.sa_mask);
    sigaddset(&sa.sa_mask, SIGTERM); /* extra block only during handler */
    sa.sa_flags = 0;

    if (sigaction(SIGINT, &sa, NULL) == -1) {
        perror("sigaction");
        return EXIT_FAILURE;
    }

    printf("pid=%ld  press Ctrl+C (exits after 3 deliveries)\n", (long)getpid());
    while (count < 3) {
        if (got_sigint) {
            got_sigint = 0;
            count++;
            printf("main: saw SIGINT #%d\n", count);
        }
        pause(); /* wake on signal; ok here for demo */
    }
    return 0;
}
```

编译（macOS 26.6.2 / arm64 · clang 23.1.0）：

```bash
CC=clang   # cdev 环境的 clang 23.1.0
$CC -Wall -Wextra -o flag_handler   flag_handler.c
```

实测输出：

```text
pid=10686  press Ctrl+C (exits after 3 deliveries)
main: saw SIGINT #1
main: saw SIGINT #2
main: saw SIGINT #3                        ← handler 只置旗，main 循环消费，exit=0
```

**逐条解读**：

- **第 1 行 `pid=10686  press Ctrl+C (exits after 3 deliveries)`**：`getpid()` 的真实值；格式串用 `%ld` 并强转 `(long)`——macOS 上 `pid_t` 是 `int`，不转会触发 `-Wall -Wextra` 的格式告警。`printf` 带 `\n`，终端行缓冲，立刻可见。
- **第 2–4 行 `main: saw SIGINT #1..#3`**：每次 Ctrl+C → 内核递送 SIGINT → `on_int()` 只执行 `got_sigint = 1` 这一条赋值就返回 → 被打断的 `pause()` 返回 `-1/EINTR`（本程序没检查返回值，直接进入下一轮 `while`）→ 主循环发现旗、清零、`count++` 并打印。**handler 里一次函数调用都没有**，`printf` 全在主循环——这就是「法则 1：把复杂逻辑移回主流程」的实测形态。
- **`got_sigint` 的 `volatile` 也实测生效**：`while (count < 3)` 里没有任何对 `got_sigint` 的写，若编译器把它缓存进寄存器，主循环将永远看不到 handler 的写（见本节正文「三、`volatile sig_atomic_t`」）。`volatile` 迫使每轮从内存重读。`sig_atomic_t` 保证这次单字节/单字读写原子——只用赋值、不做 `got_sigint++`，所以不需要锁。
- **退出码**：三次后 `count == 3` 跳出循环，`return 0`。README 标注 `exit=0`——对照 21.2：handler 内**没有**终止进程，终止决策仍在主流程。
- **`sa_mask` 是「叠加」不是「替换」**：`on_int` 执行期间，掩码里除内核自动加入的 SIGINT 外，还多一个 SIGTERM；handler 返回后由 `sigreturn` 自动恢复原掩码。本程序输出看不出这一点（没在 handler 里查掩码），要看实证得配合 `sigprocmask`/`printSigMask`——见 [`sigmask_longjmp.c`](21.2-other-methods-of-terminating-a-signal-ha.md)。

**源码坐标**：TLPI 21.1「设计信号处理器」；`sigaction(2)`（`sa_mask` / `SA_NODEFER` / 处理器期间自动阻塞本信号）、`signal(7)`、`signal-safety(7)`、`pause(2)`；`sig_atomic_t` 见 `sigaction(2)` 的 NOTES 与本节正文「三、`volatile sig_atomic_t`」。

### 二、`sigchld_reap.c`（自编 · 21.1）

演示黄金法则在 **`SIGCHLD` 回收僵尸**场景的工程后果：**标准信号不排队**，所以 handler 里必须用 `while (waitpid(-1, &st, WNOHANG)) > 0` 把已退出的子进程一次性收干净，写成 `if` 就漏僵尸。

完整源码（[`code/sigchld_reap.c`](../code/sigchld_reap.c)）：

```c
/* Reap all exited children in SIGCHLD handler via waitpid(WNOHANG) loop.
 * cc -Wall -Wextra -o sigchld_reap sigchld_reap.c && ./sigchld_reap
 */
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static volatile sig_atomic_t kids_left = 0;

static void on_chld(int sig)
{
    int status;
    pid_t pid;

    (void)sig;
    /* Loop: standard SIGCHLD does not queue — one delivery may cover many */
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        if (kids_left > 0)
            kids_left--;
    }
}

int main(void)
{
    struct sigaction sa;
    int i;

    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = on_chld;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;

    if (sigaction(SIGCHLD, &sa, NULL) == -1) {
        perror("sigaction");
        return EXIT_FAILURE;
    }

    for (i = 0; i < 3; i++) {
        pid_t pid = fork();
        if (pid == -1) {
            perror("fork");
            return EXIT_FAILURE;
        }
        if (pid == 0) {
            _exit(10 + i);
        }
        kids_left++;
    }

    printf("spawned 3 children; waiting for reaps...\n");
    while (kids_left > 0)
        pause();

    printf("all children reaped (no zombies)\n");
    return 0;
}
```

编译（macOS 26.6.2 / arm64 · clang 23.1.0）：

```bash
$CC -Wall -Wextra -o sigchld_reap   sigchld_reap.c
```

实测输出：

```text
spawned 3 children; waiting for reaps...
all children reaped (no zombies)           ← while(waitpid(-1,...,WNOHANG))>0 是唯一正确写法
```

**逐条解读**：

- **第 1 行 `spawned 3 children; waiting for reaps...`**：`fork()` 三次，每个子进程立刻 `_exit(10+i)`；父进程 `kids_left` 累加到 3。
- **为什么一次投递要收多个**：3 个子进程几乎同时退出，但 SIGCHLD 是**标准信号**——内核只保证「有一个 SIGCHLD 处于 pending」，**不会**为每个死掉的子进程各排一个。因此 handler 可能只被调用一次，却要负责 3 个已死子进程；也可能被调用多次。无论哪种，**只有 `while` 循环能保证收干净**。
- **写成 `if` 的后果**：只 `waitpid` 一次 → 剩下 2 个僵尸永久滞留（`kids_left` 永远 > 0）→ 父进程卡死在 `wait()`/`pause()`。这是生产事故级的 bug，且只在「多子同亡」的时序下出现，复现概率低。
- **`WNOHANG` 的含义**：无已退出子进程时立即返回 `0`，循环自然终止——保证 handler 内**绝不阻塞**（handler 阻塞会拖住整个进程）。
- **`waitpid` 是 async-signal-safe 的**：它在 `signal-safety(7)` 的安全清单里，所以可以在 handler 内直接调用；换成 `wait3()`/`wait4()` 也可，但 `system()` 之类不行。
- **第 2 行 `all children reaped (no zombies)`**：`kids_left` 归零，父进程正常退出（退出码 0）。事后 `ps` 应看不到 `<defunct>`。
- **`sa_flags = SA_RESTART` 在本程序里没有实际作用**：`pause()` 属于「永远返回 `EINTR`」的特例，不会被自动重启；写这句只是常见习惯。真正保证正确性的是 `while (kids_left > 0) pause()`。

**源码坐标**：TLPI 21.1 及 26.x 僵尸回收；`waitpid(2)`（`WNOHANG`、`ECHILD`）、`signal(7)`（标准信号合并/不排队 vs 实时信号排队）、`signal-safety(7)`；参见 [Ch26 监控子进程](../../chapter-26-monitoring-child-processes/README.md)。

### 三、`nonatomic_uint64.c`（官方补充 · 21.1.3）

官方 dist 的补充程序：证明 **`volatile uint64_t` 不够用**——在 32 位平台上 64 位读写会「撕裂」（memory tearing），主流程可能读到半新半旧的混合值。它是 `sig_atomic_t` 那条规定存在的直接理由。

完整源码（[`code/nonatomic_uint64.c`](../code/nonatomic_uint64.c)）：

```c
/*************************************************************************\

*                                                                         *

* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* Supplementary program for Chapter 21 */

/* nonatomic_uint64.c

   On x86-32, stores and fetches of a 64-bit integer are not atomic. This
   can result in "memory tearing" on fetches and stores, where the memory
   access requires two bus transactions. Consequently, a fetch of an integer
   that is being modified on another CPU might receive half of the old value
   and half of the new value. Thus, for example, a 64-bit integer can not be
   safely used as the flag variable set by a signal handler and checked by
   the main program.

   This program demonstrates the behavior. The signal handler inverts a
   64-bit integer whose initial value is zero, so that the value constantly
   switches between all bits zero and all bits one. The main program
   repeatedly fetches a copy of that integer and prints out a message
   whenever the fetched value is not all zeros or all ones.

   Compile this program with -m32, and run it:

        $ cc -o nonatomic_uint64 -m32 nonatomic_uint64.c
        $ ./nonatomic_uint64
        Unexpected: ffffffff00000000 (loop 48533)
        Unexpected: ffffffff00000000 (loop 171488)
        Unexpected: 00000000ffffffff (loop 272321)
        Unexpected: 00000000ffffffff (loop 297708)

   On Ubuntu and Debian, you may need to install the package 'gcc-multilib'
   in order to build this program as described above.
*/
#include <inttypes.h>
#include <stdlib.h>
#include <stdio.h>
#include <unistd.h>
#include <signal.h>

#define errExit(msg)    do { perror(msg); exit(EXIT_FAILURE); } while (0)

#define SIG SIGUSR1

static volatile uint64_t ip = 0;  /* 'volatile' included here just to show
                                      that it really doesn't help. */

/* Signal handler inverts bits in '*ip'; this may not be atomic. */

static void
handler(int sig)
{
    ip = ~ip;
}

int
main(int argc, char *argv[])
{
    /* Set up signal handler. */

    struct sigaction sa;

    sa.sa_handler = handler;
    sa.sa_flags = 0;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIG, &sa, NULL) == -1)
        errExit("sigaction");

    /* Create child that will blast signals at parent. */

    pid_t childPid = fork();
    if (childPid == -1)
        errExit("fork");

    if (childPid == 0) {
        while (1) {
            if (kill(getppid(), SIG) == -1)
                errExit("kill() failed in child");
        }
    }

    /* Parent falls through */

    /* Loop, fetching the value of '*ip' (the fetch may not be atomic)
       and checking whether the result is all bits zero or all bits one.
       If it is not, print the fetched value and the loop counter. */

    for (int long long j = 0; ; j++) {
        uint64_t loc = ip;
        if (loc != 0 && loc != ~0)
            printf("Unexpected: %016" PRIx64 " (loop %lld)\n", loc, j);
    }

    exit(EXIT_SUCCESS);
}
```

源码头部注释给出的参考输出（**x86-32 环境，非本机实测**）：

```text
Unexpected: ffffffff00000000 (loop 48533)
Unexpected: ffffffff00000000 (loop 171488)
Unexpected: 00000000ffffffff (loop 272321)
Unexpected: 00000000ffffffff (loop 297708)
```

**逐条解读**：

- **为什么必须是 `-m32` / x86-32**：64 位整数在 32 位平台上要靠**两次 32 位访存**完成，中间给了信号插入的窗口。这与 `sig_atomic_t` 的定义（保证原子读写的整数类型，Linux 上通常是 `int`）互为对照：能被 `sig_atomic_t` 覆盖的宽度才有原子保证。
- **`Unexpected: ffffffff00000000` 是什么**：`ip` 在「全 0」与「全 1（`~0`）」之间翻转；混合值 `ffffffff00000000` 表示主流程读到「高 32 位是新值、低 32 位是旧值」，`00000000ffffffff` 则相反。这两种值**既非 0 也非 `~0`**，所以被判为异常打印。
- **`volatile` 为什么救不了**：`volatile` 只禁止编译器把变量缓存到寄存器、强制每次访存；它**不提供任何原子性或内存序保证**。源注释特意加了 `volatile` 就是要点破这个常见误解。
- **`~ip` 是读-改-写**：即便宽度够，`ip = ~ip` 也不是单次原子操作——信号可能在「读」与「写」之间插入。所以旗变量不但要有原子类型，**还必须只做单次写**（如 `flag = 1`），不能在 handler 里做 `flag++`/`~flag`。
- **工程结论**：跨 handler / 主流程共享 64 位数据，不能靠 `sig_atomic_t`（它只有 `int` 宽）。要么改设计（handler 只置一个 `sig_atomic_t`），要么换 IPC（eventfd / self-pipe / 无锁 SPSC 队列 / signalfd），见 21.1 正文「四、与主流程交换数据的正确模式」。

**源码坐标**：TLPI 21.1.3（`sig_atomic_t` 的宽度局限）；`signal(7)`、`sigaction(2)`、`sig_atomic_t` 定义见 `siginfo_t` 同级的 `sigaction(2)` NOTES 与 POSIX `<signal.h>`；`signal-safety(7)`。

```c
/* handlerdesign.c —— 对比危险写法与安全写法
 * 编译: gcc -D_GNU_SOURCE -o handlerdesign handlerdesign.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

/* ────── 写法 A（❌ 危险）：handler 里做复杂工作 ────── */
static void bad_handler(int sig)
{
    printf("caught %d\n", sig);         /* ❌ printf 非 async-signal-safe */
    char *buf = malloc(64);             /* ❌ malloc 有堆锁 */
    if (buf) { snprintf(buf, 64, "sig=%d", sig); free(buf); }
    /* 可能死锁、破坏堆、死循环 */
}

/* ────── 写法 B（✅ 正确）：只设标志 + 保护 errno ────── */
static volatile sig_atomic_t got_signal = 0;
static volatile sig_atomic_t last_signo = 0;

static void good_handler(int sig)
{
    int saved_errno = errno;            /* ① 保护 errno */
    got_signal = 1;                     /* ② 只做原子赋值 */
    last_signo = sig;
    errno = saved_errno;                /* ③ 恢复 */
}

/* ────── 写法 C（✅ 更好）：self-pipe，可接入事件循环 ────── */
static int sp[2];                       /* self-pipe */
static void pipe_handler(int sig)
{
    int saved_errno = errno;
    unsigned char c = (unsigned char)sig;
    write(sp[1], &c, 1);                /* write 是 async-signal-safe */
    errno = saved_errno;
}

int main(int argc, char **argv)
{
    int mode = (argc > 1) ? atoi(argv[1]) : 2;   /* 默认用写法 B */

    if (mode == 3) {
        if (pipe(sp) == -1) { perror("pipe"); return 1; }
    }

    struct sigaction sa = {0};
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = (mode == 1) ? bad_handler
                  : (mode == 2) ? good_handler
                                : pipe_handler;
    sigaction(SIGUSR1, &sa, NULL);

    printf("模式 %d: %s\n", mode,
           mode == 1 ? "危险（printf+malloc）"
         : mode == 2 ? "安全（标志变量）"
                     : "更安全（self-pipe）");
    printf("PID=%d，请执行: kill -USR1 %d\n", getpid(), getpid());

    if (mode == 3) {
        /* 用 read 阻塞等待 pipe —— 等价于等待信号 */
        unsigned char c;
        ssize_t n = read(sp[0], &c, 1);
        if (n == 1) printf("通过 pipe 收到信号 %d\n", c);
    } else {
        /* 主循环轮询标志（真实场景应用 sigsuspend/ppoll 而非忙等） */
        while (!got_signal) {
            usleep(100000);             /* 演示用；生产代码用 sigsuspend */
        }
        printf("收到信号 %d\n", (int)last_signo);
    }
    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b>为什么 <code>volatile</code> 和 <code>sig_atomic_t</code> 两个限定符缺一不可？</summary>

两者解决**完全不同**的问题：

**`volatile` —— 防止编译器优化掉内存读取**

```c
static sig_atomic_t flag = 0;       /* 少了 volatile */
while (!flag) { do_work(); }        /* 编译器：flag 在本循环没被改 → 缓存到寄存器 → 死循环 */
```

编译器**看不见** handler（它由内核调用，不在程序控制流里），因此认为 `flag` 不会变，把它优化进寄存器。主流程**永远看不到** handler 写的新值。

**`sig_atomic_t` —— 保证读写是原子的**

```c
static volatile long long counter = 0;    /* 8 字节，非原子 */
void handler(int sig) { counter++; }      /* 读-改-写，会被打断 */
```

若变量的读写不是原子操作（如 32 位系统上的 64 位整数），信号可能在**操作中间**插入：

```
counter = 0x00000000FFFFFFFF
handler 写高 32 位 → 0x00000001FFFFFFFF
                      ↑ 主流程此时读取 → 半新半旧的垃圾值
再写低 32 位
```

| 限定符 | 解决 | 缺少的后果 |
|--------|------|-----------|
| `volatile` | 编译器缓存优化 | 永远看不到修改 |
| `sig_atomic_t` | 非原子读写 | 读到半新半旧的垃圾值 |

**注意**：`volatile sig_atomic_t` 只保证**单次读写**原子，不保证 `flag++`（读-改-写）原子。需要计数请换机制（eventfd / signalfd / 无锁队列）。

</details>

<details>
<summary><b>问 2：</b>handler 里为什么加锁解决不了数据竞争？</summary>

因为 **handler 不是新线程**——它在**被打断的同一个线程**上执行。

同一线程重入同一把**非递归**互斥锁，结果是**死锁**（不是等待）：

```
主流程                             handler
───────                            ───────
pthread_mutex_lock(&m)  ✅ 获得
├─ 正在修改共享数据
│                          ← 信号递送
│                             pthread_mutex_lock(&m)
│                             └─ 锁的 owner 就是当前线程
│                                └─ 非递归锁 → ❌ 死锁
│                                   （不会"让出"，因为根本没别的线程持有它）
```

**即使用递归锁（recursive mutex）也不对**：递归锁允许重入，于是 handler 会看到**被修改到一半的共享数据**——数据结构处于不一致状态，读写都会出错。

**所以正确的思路不是"加锁"，而是"不共享复杂状态"**：

1. handler 只写一个 `volatile sig_atomic_t`（单次原子写，无需锁）
2. 复杂数据的处理全部移回主流程
3. 或者用专门设计的**无锁 SPSC 队列**（handler 只做生产者，主流程只做消费者）
4. 最彻底：用 signalfd / `sigwaitinfo`，**完全不用 handler**

</details>

<details>
<summary><b>问 3：</b>handler 里调用 <code>printf</code> 一定会出问题吗？</summary>

**不保证出错，但也不保证安全**——这是最危险的一类 bug：**大部分时候能跑，偶尔死锁或输出乱码**。

**出错条件**：主流程**恰好**在 `printf` 执行中（持有 stdio 锁）时信号递送，handler 再次 `printf` → 同一线程重入 stdio 锁 → 死锁。

由于窗口很窄，这类 bug 可能：

- 开发环境跑几千次都不复现
- 生产环境负载高、信号频繁时偶发挂起
- 崩溃现场是"进程卡在 `printf`"，看不出与信号有关

**为什么是"同一线程重入"**：handler 在被打断线程上执行，`flockfile(stdout)` 已被该线程持有；再次 `flockfile` 不会检测"是自己持有的"，而是直接死锁（stdio 锁默认非递归）。

**正确做法**：

```c
/* 方案 1：用 write（async-signal-safe） */
static void handler(int sig) {
    const char m[] = "caught\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
}

/* 方案 2：handler 只设标志，主流程输出 */
static volatile sig_atomic_t got = 0;
static void handler(int sig) { got = 1; }
/* 主流程 */
if (got) { printf("caught signal\n"); got = 0; }

/* 方案 3：完全不用 handler —— signalfd / sigwaitinfo */
```

**判断原则**：只要一个函数**可能加锁或分配内存**，就假定它在 handler 里不安全。

</details>

<details>
<summary><b>问 4：</b>handler 与主流程需要交换较多数据时有哪些正确模式？</summary>

| 模式 | 机制 | 特点 |
|------|------|------|
| **标志变量** | `volatile sig_atomic_t` | 只能传"发生了没有"，最简单 |
| **self-pipe** | handler `write()` 一字节到管道，主流程 `read` | 可传信号编号，天然接入 `select`/`epoll`，高度可移植 |
| **eventfd** | handler `write(efd, &one, 8)` | 内核计数器，**可累计次数**，可被 epoll 监听，Linux 首选 |
| **无锁 SPSC 环形队列** | handler 写、主流程读 | 可传完整记录，**零系统调用**，最低延迟 |
| **signalfd** | 不用 handler，直接 `read()` | **最干净**，无异步信号安全问题 |
| **`sigwaitinfo`** | 不用 handler，同步取 | 多线程专用线程模型 |

**推荐优先级（Linux）**：

1. **signalfd** —— 彻底消灭 handler，最安全、最易维护
2. **eventfd / self-pipe** —— 需要保留 handler 时，把信号转成可监听事件
3. **无锁环形队列** —— HFT 热路径，要求零 syscall
4. **标志变量** —— 只需最简单的"是否发生"

**HFT 特别说明**：热路径避免任何 syscall，所以用**无锁环形队列**；控制路径（停机、配置重载）用 signalfd 更清晰。

</details>

<details>
<summary><b>问 5：</b>为什么 handler 里要保护 <code>errno</code>？</summary>

因为 handler 可能在主流程**任意位置**打断执行——包括主流程刚设置完 `errno`、正准备检查它的时刻。

**出错场景**：

```c
/* 主流程 */
errno = 0;
int fd = open(path, O_RDONLY);
if (fd == -1) {
    /* ← 信号在此递送，handler 调用了某个函数，把 errno 改成了别的 */
    if (errno == ENOENT) {          /* ❌ 读到的已不是 open 设置的 errno */
        ...
    }
}
```

**后果**：错误判断完全错误——明明是 `ENOENT` 被判成 `EINTR`，或反过来。这类 bug **偶发且无法复现**，极难排查。

**标准写法**：

```c
void handler(int sig)
{
    int saved_errno = errno;       /* ① 进入时保存 */
    /* ... 处理（可能调用修改 errno 的函数）... */
    errno = saved_errno;           /* ② 返回前恢复 */
}
```

**这不是可选项**：即便 handler 里只调用了"看起来无害"的函数（如 `write()`），失败时也会设置 `errno`。所以**任何**调用了库函数的 handler 都应当保护 `errno`。

**同理适用于浮点状态**：handler 里做浮点运算可能破坏主流程的 FPU/SIMD 寄存器状态（保存与恢复是架构相关的），所以 handler 里也应避免浮点运算。

</details>
