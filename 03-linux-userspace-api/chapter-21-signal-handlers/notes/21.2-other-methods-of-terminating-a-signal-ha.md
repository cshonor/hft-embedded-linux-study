## 本节讲什么

1. 为什么**不能在 handler 里调用 `exit()`**——它做的事情比你想的多
2. 从 handler 终止进程有**哪几种正确方式**，各自适用什么场景
3. 经典技巧「**恢复默认处置后重新发信号**」——为什么它能产生正确的退出状态与 core dump

---

## 一、陷阱：`exit()` 不是异步信号安全的

```c
void handler(int sig)
{
    printf("fatal: %d\n", sig);
    exit(1);            /* ❌ 危险！ */
}
```

`exit()` 在返回内核前会做一串工作：

1. 调用所有通过 `atexit()` / `on_exit()` 注册的**清理函数**
2. **flush 并关闭所有 stdio 流**（`fcloseall` 语义）
3. 删除 `tmpfile()` 创建的临时文件
4. 最后才调用 `_exit()` 进入内核

**每一步都涉及全局数据结构和锁**，而 handler 可能在主流程正执行其中任意一步时插进来——结果就是**死锁或数据损坏**。

**经典死锁场景**：

```
   主流程                                    handler
   ────────                                  ───────
   exit(1)
   ├─ 获取 stdio 锁
   ├─ 正在 flush 缓冲区
   │                              ← 信号递送
   │                                 exit(1)
   │                                 ├─ 尝试获取 stdio 锁  ← 已被主流程持有
   │                                 └─ ❌ 死锁（同一线程重入同一把锁）
```

> **关键**：handler **不是新线程**（[Ch20.4](../../chapter-20-signals-fundamentals/notes/20.4-introduction-to-signal-handlers.md)），它在**同一线程**上执行。所以主流程持有的锁，handler 再次获取时**不会让出**，直接死锁。

---

## 二、四种正确方式

| 方式 | 行为 | 适用场景 |
|------|------|----------|
| **`_exit(status)`** | 立即进入内核终止，**不** flush stdio、**不**跑 atexit | 最常用；handler 中标准终止手段 |
| **`_Exit(status)`** | 同 `_exit()`（C99 标准名） | 同上，可移植性更好 |
| **`abort()`** | 触发 `SIGABRT` → 默认产生 **core dump** | 需要留下 core 供事后分析 |
| **恢复 `SIG_DFL` 后重新 raise** | 让信号的**默认动作**执行 | 需要正确的退出状态 / core（见下） |

### 1. `_exit()` / `_Exit()` —— 标准做法

```c
void handler(int sig)
{
    const char msg[] = "fatal signal\n";
    write(STDERR_FILENO, msg, sizeof msg - 1);   /* write 是 async-signal-safe */
    _exit(1);                                     /* ✅ 正确 */
}
```

`_exit()` 直接发起 `exit_group` 系统调用进入内核，跳过所有用户态清理，因此**是异步信号安全的**。

### 2. `abort()` —— 留下 core dump

```c
void handler(int sig)
{
    write(STDERR_FILENO, "aborting\n", 9);
    abort();            /* 触发 SIGABRT → core dump */
}
```

`abort()` 的特殊之处：**它会先解除对 `SIGABRT` 的阻塞**，确保即使调用者阻塞了 `SIGABRT`，`abort()` 也一定能终止进程。

流程是：`raise(SIGABRT)` → 若 handler 返回，则把 `SIGABRT` 处置恢复为 `SIG_DFL` → **再次** `raise(SIGABRT)` → 默认动作执行（`do_coredump` + 终止）。

> 注意 `abort()` **不是**严格的异步信号安全函数（POSIX 未列入清单），但 glibc 实现保证了它在 handler 中可用——因为它只调用 `raise` 和 `sigaction`，且刻意不触碰 stdio/堆。

### 3. 恢复默认处置后重新发信号（经典技巧）

**问题**：自定义 handler 处理后调用 `_exit(1)`，进程的退出状态是 `1`（正常退出），而**丢失了"被信号杀死"这一信息**——父进程 `wait()` 得到的 `WIFSIGNALED` 为假，看起来像是程序自己正常退出的。

**解法**：在 handler 里把处置恢复为 `SIG_DFL`，然后**重新给自己发同一个信号**。这次递送会走默认动作，产生正确的终止语义：

```c
void handler(int sig)
{
    /* 1. 做最小限度的诊断输出（用 write，不用 printf） */
    const char m[] = "caught fatal signal, re-raising\n";
    write(STDERR_FILENO, m, sizeof m - 1);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底：若上面未生效（如信号被阻塞），强制退出 */
    _exit(128 + sig);
}
```

**效果对比**：

| 写法 | 父进程 `wait()` 看到 | core dump |
|------|---------------------|-----------|
| `_exit(1)` | `WIFEXITED`，status=1 —— **看不出是被信号杀的** | ❌ |
| 恢复 `SIG_DFL` + `raise(sig)` | `WIFSIGNALED`，`WTERMSIG`=sig ✅ | ✅（若该信号默认动作是 core） |

> **这是 shell 里 `kill -9` 与程序自己 `exit(137)` 的区别**：前者 `WIFSIGNALED` 为真，后者 `WIFEXITED` 为真。监控系统、supervisor、CI 都依赖这个区分。

## 三、内核默认终止动作分派

恢复 `SIG_DFL` 后信号再次递送时，内核在 `get_signal()` 里走这条路径（`kernel/signal.c:2861-2892`）：

```c
		/*
		 * Anything else is fatal, maybe with a core dump.
		 */
		current->flags |= PF_SIGNALED;

		if (sig_kernel_coredump(signr)) {          /* ① 是否产 core */
			if (print_fatal_signals)
				print_fatal_signal(ksig->info.si_signo);
			proc_coredump_connector(current);
			/*
			 * If it was able to dump core, this kills all
			 * other threads in the group and synchronizes with
			 * their demise.  ...
			 */
			do_coredump(&ksig->info);              /* :2878 */
		}

		if (current->flags & PF_USER_WORKER)
			goto out;

		/*
		 * Death signals, no core dump.
		 */
		do_group_exit(ksig->info.si_signo);         /* :2892 */
		/* NOTREACHED */
```

| 步骤 | 行号 | 判据 / 动作 |
|------|------|-------------|
| ① | `:2866` | `sig_kernel_coredump(signr)` —— 该信号是否产 core |
| ② | `:2878` | 是 → `do_coredump()` 先写 core 文件 |
| ③ | `:2892` | `do_group_exit(signr)` —— 终止**整个线程组** |

**判据 `sig_kernel_coredump`**（`include/linux/signal.h:445`）：

```c
#define sig_kernel_coredump(sig)   siginmask(sig, SIG_KERNEL_COREDUMP_MASK)
```

`SIG_KERNEL_COREDUMP_MASK`（`include/linux/signal.h:425`）覆盖 `SIGQUIT`/`SIGILL`/`SIGTRAP`/`SIGABRT`/`SIGFPE`/`SIGSEGV`/`SIGBUS`/`SIGSYS`/`SIGXCPU`/`SIGXFSZ`/`SIGEMT`。

> **重要**：`do_group_exit` 终止的是**整个线程组**，不只是当前线程。所以多线程进程里任一线程触发致命信号，全进程一起退出。

## 四、完整对照表

| 方式 | async-signal-safe | flush stdio | 跑 atexit | core dump | `WIFSIGNALED` |
|------|-------------------|-------------|-----------|-----------|---------------|
| **`exit()`** | ❌ **危险** | ✅ | ✅ | ❌ | ❌ |
| **`_exit()` / `_Exit()`** | ✅ | ❌ | ❌ | ❌ | ❌ |
| **`abort()`** | ⚠️ 实践可用 | ❌ | ❌ | ✅ | ✅（`SIGABRT`） |
| **恢复 `SIG_DFL` + `raise()`** | ✅ | ❌ | ❌ | ✅（视信号） | ✅ |

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 嵌入式服务常在 handler 里做「紧急落盘 + 终止」，但 `exit()` 会死锁——必须 `_exit()`。若需要保留现场，用 `abort()` 或「恢复 `SIG_DFL` 后 re-raise」产生 core。注意嵌入式存储有限，需先配好 `core_pattern` 与 `RLIMIT_CORE`，否则 core 写不出来 |
| HFT | 交易进程的终止路径必须**可预测且快速**：`_exit()` 是唯一安全的选择（无锁、无 I/O、无清理）。诊断信息应通过**无锁环形队列 + 独立日志线程**在平时就落盘，而不是崩溃时才写——崩溃时刻的任何 I/O 都可能因锁状态未知而死锁。终止状态用 `WIFSIGNALED` 语义（re-raise 技巧），让监控能区分「被杀」与「自退」 |

## 代码示例

### 一、`sigmask_longjmp.c`（原书 Listing 21-2 · 21.2.1）

handler 里用 `[sig]longjmp` 跳出，观察**跳转后信号掩码的残留状态**。它同时是「handler 里不要随便 `longjmp`」这条建议的实测证据。默认走 `setjmp`/`longjmp`；编译时加 `-DUSE_SIGSETJMP` 走 `sigsetjmp(env, 1)`/`siglongjmp` 版本。

完整源码（[`code/sigmask_longjmp.c`](../code/sigmask_longjmp.c)）：

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* Listing 21-2 */

/* sigmask_longjmp.c

   Demonstrate the different effects of longjmp() and siglongjmp()
   on the process signal mask.

   By default, this program uses setjmp() + longjmp(). Compile with
   -DUSE_SIGSETJMP to use sigsetjmp() + siglongjmp().
*/
#define _GNU_SOURCE     /* Get strsignal() declaration from <string.h> */
#include <string.h>
#include <setjmp.h>
#include <signal.h>
#include "signal_functions.h"           /* Declaration of printSigMask() */
#include "tlpi_hdr.h"

static volatile sig_atomic_t canJump = 0;
                        /* Set to 1 once "env" buffer has been
                           initialized by [sig]setjmp() */
#ifdef USE_SIGSETJMP
static sigjmp_buf senv;
#else
static jmp_buf env;
#endif

static void
handler(int sig)
{
    /* UNSAFE: This handler uses non-async-signal-safe functions
       (printf(), strsignal(), printSigMask(); see Section 21.1.2) */

    printf("Received signal %d (%s), signal mask is:\n", sig,
            strsignal(sig));
    printSigMask(stdout, NULL);

    if (!canJump) {
        printf("'env' buffer not yet set, doing a simple return\n");
        return;
    }

#ifdef USE_SIGSETJMP
    siglongjmp(senv, 1);
#else
    longjmp(env, 1);
#endif
}

int
main(int argc, char *argv[])
{
    struct sigaction sa;

    printSigMask(stdout, "Signal mask at startup:\n");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sa.sa_handler = handler;
    if (sigaction(SIGINT, &sa, NULL) == -1)
        errExit("sigaction");

#ifdef USE_SIGSETJMP
    printf("Calling sigsetjmp()\n");
    if (sigsetjmp(senv, 1) == 0)
#else
    printf("Calling setjmp()\n");
    if (setjmp(env) == 0)
#endif
        canJump = 1;                    /* Executed after [sig]setjmp() */

    else                                /* Executed after [sig]longjmp() */
        printSigMask(stdout, "After jump from handler, signal mask is:\n" );

    for (;;)                            /* Wait for signals until killed */
        pause();
}
```

编译（macOS 26.6.2 / arm64 · clang 23.1.0）：

```bash
CC=clang   # cdev 环境的 clang 23.1.0
D='-D_DARWIN_C_SOURCE -I.'
$CC $D -Wall -Wextra -o sigmask_longjmp  sigmask_longjmp.c  get_num.c signal_functions.c
```

实测输出：

```text
Signal mask at startup:
        <empty signal set>
Calling setjmp()
Received signal 2 (Interrupt: 2), signal mask is:
        2 (Interrupt: 2)          ← handler 执行期 SIGINT 自动入掩码
After jump from handler, signal mask is:
        <empty signal set>        ← 本平台 longjmp 后掩码恢复为空（macOS 行为；
                                     POSIX 说此值在 setjmp 版未定义，Linux 上常保持阻塞！）
```

**逐条解读**：

- **`Signal mask at startup:` / `<empty signal set>`**：`printSigMask()` 来自 Listing 20-4（本目录镜像了 `signal_functions.c/h`）。进程刚启动时掩码为空。
- **`Calling setjmp()`**：`setjmp(env)` 首次返回 `0` → `canJump = 1` → 进入 `for (;;) pause()` 等信号。`canJump` 用 `volatile sig_atomic_t`，防止 handler 里读到被编译器缓存的旧值。
- **`Received signal 2 (Interrupt: 2)`**：收到 Ctrl+C 的 SIGINT，`strsignal(2)` 返回 `"Interrupt: 2"`（macOS 的文案带信号号）。
- **掩码里为什么出现 `2 (Interrupt: 2)`**：内核在**进入 handler 时自动把该信号加入掩码**（除非设了 `SA_NODEFER`），避免同号信号递归打断自己；handler 返回时由 `sigreturn` 自动撤除。这里因为 handler 还没返回（`longjmp` 跳走了），所以打印时它是阻塞的。
- **`After jump from handler, signal mask is:` / `<empty signal set>`**：`longjmp(env, 1)` 让 `setjmp` 点「再次返回」，这次返回 1 → 走 `else` 分支打印跳转后的掩码。macOS 上结果是**空集**，即掩码被恢复成了 setjmp 时的状态。
- **这里是本节的核心考点，不是平台八卦**：POSIX 对 **`setjmp`/`longjmp` 版跳转后的掩码**明确说「未定义」——同一份代码在 Linux 上常表现为 SIGINT **仍保持阻塞**。若程序此后再收不到 Ctrl+C，就是这个原因。要掩码可移植，必须 `-DUSE_SIGSETJMP`，用 `sigsetjmp(env, 1)` 保存并在 `siglongjmp` 时恢复掩码（第二个参数非 0 = 保存掩码）。
- **handler 里的 `printf`/`strsignal`/`printSigMask` 全是 UNSAFE**：源文件注释已自曝（`see Section 21.1.2`）。本程序只为演示掩码语义；生产 handler 只能用 `write(2)`。

**源码坐标**：TLPI **Listing 21-2**（21.2.1）；`setjmp(3)`、`sigsetjmp(3)`、`longjmp(3)`、`siglongjmp(3)`、`sigaction(2)`（`SA_NODEFER`）、`sigprocmask(2)`、`signal-safety(7)`；掩码打印依赖 Listing 20-4 的 `printSigMask()`（`signal_functions.c`）。

### 二、`ex21_1_abort.c`（习题 21-1 · 21.2.2）

自实现 `abort()`（`my_abort()`），用三个场景验证 SUSv3 对 `abort()` 的三条要求：① 无视 `SIGABRT` 被阻塞/忽略，必须终止进程；② 若装了 handler，先让 handler 跑，handler 返回后把处置复位为 `SIG_DFL` 再 `raise` 一次 → 必死；③ 终止前 flush 并关闭 stdio 流。

完整源码（[`code/ex21_1_abort.c`](../code/ex21_1_abort.c)）：

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* ex21_1_abort.c — 习题 21-1：实现 abort()

   SUSv3 要求的 abort() 语义（TLPI 21.2.2 / P433）：
   1. 无论 SIGABRT 被阻塞还是忽略，abort() 都必须终止进程（override 阻塞/忽略）
   2. 若进程用 handler 捕获 SIGABRT，先让 handler 跑；
      handler 若返回，则 abort() 把处置复位为 SIG_DFL 再 raise 一次 → 必死
   3. 终止前 flush 并关闭 stdio 流

   本程序实现 my_abort()，并用三个场景验证：
     ⓪ 默认处置：直接终止
     ① SIGABRT 被阻塞：解除阻塞语义 → 仍终止
     ② handler 捕获并返回：复位 SIG_DFL → 第二次 raise 终止
   实测环境：macOS 26.6.2 (arm64)，clang 23.1.0
*/
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>

/* —— 习题 21-1 的核心：my_abort() —— */
static void
my_abort(void)
{
    sigset_t mask;
    struct sigaction sa;

    /* SUSv3：abort() 必须无视阻塞 —— 先解除 SIGABRT 的阻塞 */
    sigemptyset(&mask);
    sigaddset(&mask, SIGABRT);
    if (sigprocmask(SIG_UNBLOCK, &mask, NULL) == -1) {
        perror("sigprocmask");
        _exit(EXIT_FAILURE);
    }

    /* 查当前处置：若装了 handler，让它跑（handler 可能 longjmp 不回来） */
    if (sigaction(SIGABRT, NULL, &sa) == -1) {
        perror("sigaction");
        _exit(EXIT_FAILURE);
    }
    if (sa.sa_handler != SIG_DFL && sa.sa_handler != SIG_IGN)
        raise(SIGABRT);                 /* handler 返回 = 没终止进程 */

    /* 走到这里说明 handler 返回（或原处置是 SIG_IGN）：
       复位 SIG_DFL，flush stdio，再 raise 一次 —— 这次必死 */
    sa.sa_handler = SIG_DFL;
    sa.sa_flags = 0;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGABRT, &sa, NULL) == -1) {
        perror("sigaction reset");
        _exit(EXIT_FAILURE);
    }
    fflush(stdout);
    raise(SIGABRT);

    /* 若信号仍被忽略（理论上不可能，SIG_DFL 已复位）：兜底 */
    _exit(EXIT_FAILURE);
}

/* —— 场景 ② 的 handler：捕获后直接返回 —— */
static void
handler(int sig)
{
    printf("    handler: 捕获 SIGABRT(%d) 后返回 → my_abort 应回位 SIG_DFL 再来一次\n", sig);
}

int
main(int argc, char *argv[])
{
    printf("PID=%ld  用法：无参=⓪默认；b=①阻塞；h=②handler 返回\n",
            (long) getpid());

    if (argc > 1 && argv[1][0] == 'b') {
        /* ① 阻塞 SIGABRT 再 abort —— SUSv3：必须仍终止 */
        sigset_t mask;
        sigemptyset(&mask);
        sigaddset(&mask, SIGABRT);
        sigprocmask(SIG_BLOCK, &mask, NULL);
        printf("[①] SIGABRT 已阻塞，调 my_abort() —— 应仍然终止\n");
        printf("[①] 这行**能**打出来：abort() 终止前必须 flush stdio（SUSv3 要求）\n");
        my_abort();

    } else if (argc > 1 && argv[1][0] == 'h') {
        /* ② handler 捕获并返回 —— 复位 SIG_DFL 后第二次 raise 终止 */
        struct sigaction sa;
        sa.sa_handler = handler;
        sa.sa_flags = 0;
        sigemptyset(&sa.sa_mask);
        sigaction(SIGABRT, &sa, NULL);
        printf("[②] 装 handler，调 my_abort()\n");
        my_abort();

    } else {
        /* ⓪ 默认处置直接终止 */
        printf("[⓪] 默认处置，调 my_abort() —— 直接 SIGABRT 终止\n");
        my_abort();
    }

    printf("不应到达这里\n");
    exit(EXIT_SUCCESS);
}
```

```text
$ ex21_1_abort b      → [exit=134]  ① 阻塞也拦不住（SUSv3 override），且终止前 flush 了 stdio
$ ex21_1_abort h      → [exit=134]  ② handler 捕获返回 → 复位 SIG_DFL → 第二次 raise 必死
```

**逐条解读**：

- **三个场景退出码都是 `134`**：`134 = 128 + 6`，6 是 SIGABRT 的编号。shell 用 `128+signo` 表示「进程被信号 N 杀死」，说明三次都走了 **SIGABRT 默认动作**——这正是 `abort()` 语义正确的标志（对照：若在 handler 里 `_exit(1)`，退出码会是 1，父进程 `wait()` 看到的是 `WIFEXITED` 而非 `WIFSIGNALED`，见 21.2 正文「二、四种正确方式」）。
- **⓪ 默认处置**：`sigaction(SIGABRT, NULL, &sa)` 查出 `sa_handler == SIG_DFL` → 跳过第一次 `raise` → 直接复位 `SIG_DFL`、`fflush`、`raise(SIGABRT)` → 默认动作终止。
- **① 阻塞也拦不住**：`main` 先 `sigprocmask(SIG_BLOCK, {SIGABRT})`，但 `my_abort()` 开头立即 `sigprocmask(SIG_UNBLOCK, {SIGABRT})`——这就是 SUSv3 要求的 **override 阻塞**。随后 `raise` 直接生效。两行 `[①] ...` 能打出来，证明 `my_abort()` 在最终 `raise` 前执行了 `fflush(stdout)`（SUSv3 第 3 条：终止前 flush stdio）。
- **② handler 无法拦停 abort**：处置不是 `SIG_DFL`/`SIG_IGN` → 先 `raise(SIGABRT)` 让 `handler()` 跑；`handler()` 打印后**正常返回**（没终止进程）→ `my_abort()` 继续走到「复位 `SIG_DFL` + `fflush` + 第二次 `raise`」→ 这次没有任何 handler 可拦，默认动作必死。这就是 `abort()` 与普通「发个 SIGABRT」的本质区别。
- **为什么第二次 `raise` 之前要 `fflush(stdout)`**：默认动作（`do_coredump` + `do_group_exit`）不会 flush 用户态 stdio 缓冲。若 stdout 重定向到文件/管道，`handler` 里那句 `printf` 的内容会随缓冲一起丢失；显式 `fflush` 保证诊断信息落盘。
- **core 文件**：README 差异表记录 macOS 默认不落盘 core（`/cores` + sysctl 限制），所以这里只验证了**退出状态**；Linux 上要拿到 core 需 `ulimit -c unlimited`，见 Pi5 复测清单「`ex21_1_abort ⓪` + 查 `/proc/sys/kernel/core_pattern`」。
- **`abort()` 不在严格的 async-signal-safe 清单里**，但本实现只调 `sigprocmask`/`sigaction`/`raise`/`fflush`/`_exit`，刻意不碰堆与 stdio 流以外的资源；glibc 的 `abort()` 也是同样思路（见 21.2 正文的说明）。

**源码坐标**：TLPI **习题 21-1**（正文 21.2.2 / P433）；`abort(3)`（SUSv3 语义）、`raise(3)`、`sigaction(2)`、`sigprocmask(2)`、`signal-safety(7)`；内核默认动作分派 `do_coredump:2878` / `do_group_exit:2892`（见本节正文「三、内核默认终止动作分派」）。

```c
/* termdemo.c —— 对比 exit() 与 _exit()，以及 re-raise 技巧
 * 编译: gcc -o termdemo termdemo.c
 * 用法: ./termdemo _exit | exit | reraise */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

/* ❌ 错误示范：handler 里用 exit() */
static void bad_handler(int sig)
{
    const char m[] = "  [bad] handler: 调用 exit()\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
    exit(1);                        /* ❌ 不是 async-signal-safe */
}

/* ✅ 正确：_exit() */
static void good_handler(int sig)
{
    const char m[] = "  [good] handler: 调用 _exit()\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
    _exit(1);                       /* ✅ 安全 */
}

/* ✅ 正确：恢复 SIG_DFL 后重新发信号（保留 WIFSIGNALED 语义） */
static void reraise_handler(int sig)
{
    const char m[] = "  [reraise] 恢复默认处置并重新发信号\n";
    write(STDOUT_FILENO, m, sizeof m - 1);

    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    raise(sig);                     /* 走默认动作：core + 终止 */

    _exit(128 + sig);               /* 兜底 */
}

static void run(const char *mode)
{
    pid_t p = fork();
    if (p == 0) {
        struct sigaction sa = {0};
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = SA_RESTART;

        if (!strcmp(mode, "exit"))        sa.sa_handler = bad_handler;
        else if (!strcmp(mode, "_exit"))  sa.sa_handler = good_handler;
        else                              sa.sa_handler = reraise_handler;

        sigaction(SIGSEGV, &sa, NULL);
        printf("子进程 %d (%s 模式) 触发 SIGSEGV...\n", getpid(), mode);
        fflush(stdout);
        raise(SIGSEGV);                   /* 触发 */
        _exit(0);
    }

    int st;
    waitpid(p, &st, 0);
    printf("  父进程观察: ");
    if (WIFSIGNALED(st))
        printf("WIFSIGNALED=true, 终止信号=%d (WTERMSIG)\n", WTERMSIG(st));
    else if (WIFEXITED(st))
        printf("WIFEXITED=true, 退出码=%d （看不出是被信号杀的）\n", WEXITSTATUS(st));
}

int main(int argc, char **argv)
{
    const char *modes[] = { "_exit", "exit", "reraise" };
    if (argc > 1) {
        run(argv[1]);
    } else {
        for (size_t i = 0; i < 3; i++) {
            printf("\n=== 模式: %s ===\n", modes[i]);
            run(modes[i]);
        }
    }
    return 0;
}
```

预期输出（关键差异在第 3 种）：

```
=== 模式: _exit ===
  父进程观察: WIFEXITED=true, 退出码=1 （看不出是被信号杀的）

=== 模式: exit ===
  父进程观察: WIFEXITED=true, 退出码=1 （且可能死锁，视时序）

=== 模式: reraise ===
  父进程观察: WIFSIGNALED=true, 终止信号=11 (WTERMSIG)   ← 正确保留了"被杀死"语义
```

## 自测题

<details>
<summary><b>问 1：</b>为什么不能在信号处理函数里调用 <code>exit()</code>？</summary>

`exit()` **不是异步信号安全函数**——它在进入内核前会执行一串用户态清理：

1. 调用 `atexit()` / `on_exit()` 注册的所有清理函数
2. **flush 并关闭所有 stdio 流**
3. 删除 `tmpfile()` 创建的临时文件
4. 最后才调用 `_exit()`

每一步都操作**全局数据结构并加锁**。

**经典死锁场景**：

```
主流程 exit(1)
  ├─ 获取 stdio 锁
  ├─ 正在 flush 缓冲区
  │                    ← 信号递送
  │                       handler: exit(1)
  │                         └─ 尝试获取 stdio 锁 → 已被持有 → 死锁
```

**关键在于**：handler **不是新线程**，它在**同一线程**上执行。主流程持有的锁不会被 handler"等待让出"——同一线程重入同一把非递归锁，直接死锁。

**正确做法**：用 `_exit()` / `_Exit()`，它们直接发起 `exit_group` 系统调用，跳过所有用户态清理，是异步信号安全的。

</details>

<details>
<summary><b>问 2：</b>什么是「恢复默认处置后重新发信号」技巧？解决什么问题？</summary>

**解决的问题**：保留「进程是被信号杀死的」这一语义信息。

如果 handler 里直接 `_exit(1)`，父进程 `wait()` 看到的是 `WIFEXITED=true, status=1`——**看起来像程序自己正常退出**，无法区分「被 OOM killer 杀」与「业务主动退出」。

**技巧步骤**：

```c
void handler(int sig)
{
    /* 1. 最小诊断（用 write） */
    write(STDERR_FILENO, "fatal\n", 6);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底 */
    _exit(128 + sig);
}
```

**效果**：

| 写法 | 父进程看到 | core |
|------|-----------|------|
| `_exit(1)` | `WIFEXITED=true, status=1` | ❌ |
| re-raise | **`WIFSIGNALED=true, WTERMSIG=sig`** | ✅（若默认动作是 core） |

**为什么有效**：`raise(sig)` 时 disposition 已是 `SIG_DFL`，内核在 `get_signal()` 里走致命分支——`do_coredump()`（若该信号产 core）+ `do_group_exit(signo)`（`kernel/signal.c:2878`/`:2892`）。

**第 4 步兜底必要**：若该信号在 handler 执行期间被阻塞（如 `sa_mask` 里有它），`raise` 只会让它 pending 而不会立即递送。此时 `_exit(128+sig)` 保证进程一定退出（`128+sig` 是 shell 表示"被信号 N 杀死"的惯例）。

</details>

<details>
<summary><b>问 3：</b><code>abort()</code> 有什么特殊之处？它一定会终止进程吗？</summary>

`abort()` **一定会终止进程**——这是它的契约保证。

**特殊机制**：`abort()` 会**先解除对 `SIGABRT` 的阻塞**，确保即使调用者用 `sigprocmask` 阻塞了 `SIGABRT`，`abort()` 也一定能生效。

**执行流程**：

```
abort()
  ├─ 解除对 SIGABRT 的阻塞
  ├─ raise(SIGABRT)
  │     ├─ 若有自定义 handler → 执行它
  │     └─ handler 返回 → 继续
  ├─ 把 SIGABRT 的处置恢复为 SIG_DFL
  ├─ 再次 raise(SIGABRT)      ← 这次一定走默认动作
  └─ 默认动作：do_coredump() + do_group_exit()  → 进程终止 + core dump
```

**关键设计**：即使用户注册了 `SIGABRT` handler 并且 handler 正常返回，`abort()` 也会**再次**发信号并强制走默认动作——所以 `abort()` **不可能被 handler"拦截"**。

**用途**：

- 断言失败（`assert()` 内部就是 `abort()`）
- 需要留下 core 供事后 gdb 分析
- 「不可恢复错误」的最终手段

**与 `_exit()` 的对比**：

| | `abort()` | `_exit()` |
|--|-----------|-----------|
| core dump | ✅ | ❌ |
| `WIFSIGNALED` | ✅（`SIGABRT`） | ❌ |
| 可被 handler 拦截 | ❌（会 re-raise） | 不适用 |
| 严格 async-signal-safe | ⚠️ POSIX 未列入，但 glibc 保证可用 | ✅ |

</details>

<details>
<summary><b>问 4：</b>内核执行「默认终止动作」时具体做了什么？</summary>

在 `get_signal()` 中（`kernel/signal.c:2861-2892`）：

```c
		/*
		 * Anything else is fatal, maybe with a core dump.
		 */
		current->flags |= PF_SIGNALED;

		if (sig_kernel_coredump(signr)) {          /* ① 判据 */
			if (print_fatal_signals)
				print_fatal_signal(ksig->info.si_signo);
			proc_coredump_connector(current);
			do_coredump(&ksig->info);              /* ② 写 core（:2878） */
		}

		if (current->flags & PF_USER_WORKER)
			goto out;

		/*
		 * Death signals, no core dump.
		 */
		do_group_exit(ksig->info.si_signo);         /* ③ 终止（:2892） */
		/* NOTREACHED */
```

| 步骤 | 行号 | 内容 |
|------|------|------|
| ① | `:2866` | `sig_kernel_coredump(signr)` 判断是否产 core |
| ② | `:2878` | 是 → `do_coredump()` 写 core 文件 |
| ③ | `:2892` | `do_group_exit(signo)` 终止**整个线程组** |

**判据**（`include/linux/signal.h:445`）：

```c
#define sig_kernel_coredump(sig)  siginmask(sig, SIG_KERNEL_COREDUMP_MASK)
```

`SIG_KERNEL_COREDUMP_MASK`（`include/linux/signal.h:425`）覆盖：`SIGQUIT`、`SIGILL`、`SIGTRAP`、`SIGABRT`、`SIGFPE`、`SIGSEGV`、`SIGBUS`、`SIGSYS`、`SIGXCPU`、`SIGXFSZ`、`SIGEMT`。

**两个要点**：

1. **产 core 的信号有限**——`SIGTERM`/`SIGINT`/`SIGKILL` 等**不产** core，只有上表 11 个会。
2. **`do_group_exit` 终止整个线程组**——多线程进程里任一线程触发致命信号，全进程一起退出，不只是那个线程。内核注释也强调了这点："this kills all other threads in the group and synchronizes with their demise"。

</details>

<details>
<summary><b>问 5：</b><code>exit()</code>、<code>_exit()</code>、<code>abort()</code>、re-raise 四者该怎么选？</summary>

| 方式 | async-signal-safe | flush stdio | atexit | core | `WIFSIGNALED` | 何时用 |
|------|-------------------|-------------|--------|------|---------------|--------|
| `exit()` | ❌ **危险** | ✅ | ✅ | ❌ | ❌ | handler 里**绝不用** |
| `_exit()`/`_Exit()` | ✅ | ❌ | ❌ | ❌ | ❌ | handler 中**默认选择**：快速、安全 |
| `abort()` | ⚠️ 实践可用 | ❌ | ❌ | ✅ | ✅ | 断言失败 / 需要 **core dump** |
| re-raise | ✅ | ❌ | ❌ | ✅（视信号） | ✅ | 需要**保留"被信号杀死"语义** |

**决策流程**：

```
handler 中要终止进程？
  ├─ 需要 core dump 供 gdb 分析？
  │    ├─ 是，用 abort()（固定 SIGABRT + core）
  │    └─ 是，且要保留原信号类型 → re-raise 技巧
  └─ 不需要，只想快速退出
       └─ _exit(status)  ← 默认选择
```

**HFT 特别建议**：

- 崩溃路径用 **re-raise**（保留 `WIFSIGNALED`，让监控能区分「被杀」与「自退」）
- 正常停机路径用 `_exit()`（快速、无锁）
- **诊断信息平时就落盘**（无锁环形队列 + 独立日志线程），不要等崩溃时才写——崩溃时刻的锁状态未知，任何 I/O 都可能死锁

</details>
