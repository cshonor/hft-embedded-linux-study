## 本节讲什么

1. 为什么**不能在 handler 里调用 `exit()`**——它做的事情比你想的多
2. 从 handler 终止进程有**哪几种正确方式**，各自适用什么场景
3. 经典技巧「**恢复默认处置后重新发信号**」——为什么它能产生正确的退出状态与 core dump

---

## 一、陷阱：`exit()` 不是异步信号安全的

```c
void handler(int sig)
{
    printf("fatal: %d\n", sig);
    exit(1);            /* ❌ 危险！ */
}
```

`exit()` 在返回内核前会做一串工作：

1. 调用所有通过 `atexit()` / `on_exit()` 注册的**清理函数**
2. **flush 并关闭所有 stdio 流**（`fcloseall` 语义）
3. 删除 `tmpfile()` 创建的临时文件
4. 最后才调用 `_exit()` 进入内核

**每一步都涉及全局数据结构和锁**，而 handler 可能在主流程正执行其中任意一步时插进来——结果就是**死锁或数据损坏**。

**经典死锁场景**：

```
   主流程                                    handler
   ────────                                  ───────
   exit(1)
   ├─ 获取 stdio 锁
   ├─ 正在 flush 缓冲区
   │                              ← 信号递送
   │                                 exit(1)
   │                                 ├─ 尝试获取 stdio 锁  ← 已被主流程持有
   │                                 └─ ❌ 死锁（同一线程重入同一把锁）
```

> **关键**：handler **不是新线程**（[Ch20.4](../../chapter-20-signals-fundamentals/notes/20.4-introduction-to-signal-handlers.md)），它在**同一线程**上执行。所以主流程持有的锁，handler 再次获取时**不会让出**，直接死锁。

---

## 二、四种正确方式

| 方式 | 行为 | 适用场景 |
|------|------|----------|
| **`_exit(status)`** | 立即进入内核终止，**不** flush stdio、**不**跑 atexit | 最常用；handler 中标准终止手段 |
| **`_Exit(status)`** | 同 `_exit()`（C99 标准名） | 同上，可移植性更好 |
| **`abort()`** | 触发 `SIGABRT` → 默认产生 **core dump** | 需要留下 core 供事后分析 |
| **恢复 `SIG_DFL` 后重新 raise** | 让信号的**默认动作**执行 | 需要正确的退出状态 / core（见下） |

### 1. `_exit()` / `_Exit()` —— 标准做法

```c
void handler(int sig)
{
    const char msg[] = "fatal signal\n";
    write(STDERR_FILENO, msg, sizeof msg - 1);   /* write 是 async-signal-safe */
    _exit(1);                                     /* ✅ 正确 */
}
```

`_exit()` 直接发起 `exit_group` 系统调用进入内核，跳过所有用户态清理，因此**是异步信号安全的**。

### 2. `abort()` —— 留下 core dump

```c
void handler(int sig)
{
    write(STDERR_FILENO, "aborting\n", 9);
    abort();            /* 触发 SIGABRT → core dump */
}
```

`abort()` 的特殊之处：**它会先解除对 `SIGABRT` 的阻塞**，确保即使调用者阻塞了 `SIGABRT`，`abort()` 也一定能终止进程。

流程是：`raise(SIGABRT)` → 若 handler 返回，则把 `SIGABRT` 处置恢复为 `SIG_DFL` → **再次** `raise(SIGABRT)` → 默认动作执行（`do_coredump` + 终止）。

> 注意 `abort()` **不是**严格的异步信号安全函数（POSIX 未列入清单），但 glibc 实现保证了它在 handler 中可用——因为它只调用 `raise` 和 `sigaction`，且刻意不触碰 stdio/堆。

### 3. 恢复默认处置后重新发信号（经典技巧）

**问题**：自定义 handler 处理后调用 `_exit(1)`，进程的退出状态是 `1`（正常退出），而**丢失了"被信号杀死"这一信息**——父进程 `wait()` 得到的 `WIFSIGNALED` 为假，看起来像是程序自己正常退出的。

**解法**：在 handler 里把处置恢复为 `SIG_DFL`，然后**重新给自己发同一个信号**。这次递送会走默认动作，产生正确的终止语义：

```c
void handler(int sig)
{
    /* 1. 做最小限度的诊断输出（用 write，不用 printf） */
    const char m[] = "caught fatal signal, re-raising\n";
    write(STDERR_FILENO, m, sizeof m - 1);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底：若上面未生效（如信号被阻塞），强制退出 */
    _exit(128 + sig);
}
```

**效果对比**：

| 写法 | 父进程 `wait()` 看到 | core dump |
|------|---------------------|-----------|
| `_exit(1)` | `WIFEXITED`，status=1 —— **看不出是被信号杀的** | ❌ |
| 恢复 `SIG_DFL` + `raise(sig)` | `WIFSIGNALED`，`WTERMSIG`=sig ✅ | ✅（若该信号默认动作是 core） |

> **这是 shell 里 `kill -9` 与程序自己 `exit(137)` 的区别**：前者 `WIFSIGNALED` 为真，后者 `WIFEXITED` 为真。监控系统、supervisor、CI 都依赖这个区分。

## 三、内核默认终止动作分派

恢复 `SIG_DFL` 后信号再次递送时，内核在 `get_signal()` 里走这条路径（`kernel/signal.c:2861-2892`）：

```c
		/*
		 * Anything else is fatal, maybe with a core dump.
		 */
		current->flags |= PF_SIGNALED;

		if (sig_kernel_coredump(signr)) {          /* ① 是否产 core */
			if (print_fatal_signals)
				print_fatal_signal(ksig->info.si_signo);
			proc_coredump_connector(current);
			/*
			 * If it was able to dump core, this kills all
			 * other threads in the group and synchronizes with
			 * their demise.  ...
			 */
			do_coredump(&ksig->info);              /* :2878 */
		}

		if (current->flags & PF_USER_WORKER)
			goto out;

		/*
		 * Death signals, no core dump.
		 */
		do_group_exit(ksig->info.si_signo);         /* :2892 */
		/* NOTREACHED */
```

| 步骤 | 行号 | 判据 / 动作 |
|------|------|-------------|
| ① | `:2866` | `sig_kernel_coredump(signr)` —— 该信号是否产 core |
| ② | `:2878` | 是 → `do_coredump()` 先写 core 文件 |
| ③ | `:2892` | `do_group_exit(signr)` —— 终止**整个线程组** |

**判据 `sig_kernel_coredump`**（`include/linux/signal.h:445`）：

```c
#define sig_kernel_coredump(sig)   siginmask(sig, SIG_KERNEL_COREDUMP_MASK)
```

`SIG_KERNEL_COREDUMP_MASK`（`include/linux/signal.h:425`）覆盖 `SIGQUIT`/`SIGILL`/`SIGTRAP`/`SIGABRT`/`SIGFPE`/`SIGSEGV`/`SIGBUS`/`SIGSYS`/`SIGXCPU`/`SIGXFSZ`/`SIGEMT`。

> **重要**：`do_group_exit` 终止的是**整个线程组**，不只是当前线程。所以多线程进程里任一线程触发致命信号，全进程一起退出。

## 四、完整对照表

| 方式 | async-signal-safe | flush stdio | 跑 atexit | core dump | `WIFSIGNALED` |
|------|-------------------|-------------|-----------|-----------|---------------|
| **`exit()`** | ❌ **危险** | ✅ | ✅ | ❌ | ❌ |
| **`_exit()` / `_Exit()`** | ✅ | ❌ | ❌ | ❌ | ❌ |
| **`abort()`** | ⚠️ 实践可用 | ❌ | ❌ | ✅ | ✅（`SIGABRT`） |
| **恢复 `SIG_DFL` + `raise()`** | ✅ | ❌ | ❌ | ✅（视信号） | ✅ |

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 嵌入式服务常在 handler 里做「紧急落盘 + 终止」，但 `exit()` 会死锁——必须 `_exit()`。若需要保留现场，用 `abort()` 或「恢复 `SIG_DFL` 后 re-raise」产生 core。注意嵌入式存储有限，需先配好 `core_pattern` 与 `RLIMIT_CORE`，否则 core 写不出来 |
| HFT | 交易进程的终止路径必须**可预测且快速**：`_exit()` 是唯一安全的选择（无锁、无 I/O、无清理）。诊断信息应通过**无锁环形队列 + 独立日志线程**在平时就落盘，而不是崩溃时才写——崩溃时刻的任何 I/O 都可能因锁状态未知而死锁。终止状态用 `WIFSIGNALED` 语义（re-raise 技巧），让监控能区分「被杀」与「自退」 |

## 代码示例：正确的终止方式

```c
/* termdemo.c —— 对比 exit() 与 _exit()，以及 re-raise 技巧
 * 编译: gcc -o termdemo termdemo.c
 * 用法: ./termdemo _exit | exit | reraise */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

/* ❌ 错误示范：handler 里用 exit() */
static void bad_handler(int sig)
{
    const char m[] = "  [bad] handler: 调用 exit()\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
    exit(1);                        /* ❌ 不是 async-signal-safe */
}

/* ✅ 正确：_exit() */
static void good_handler(int sig)
{
    const char m[] = "  [good] handler: 调用 _exit()\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
    _exit(1);                       /* ✅ 安全 */
}

/* ✅ 正确：恢复 SIG_DFL 后重新发信号（保留 WIFSIGNALED 语义） */
static void reraise_handler(int sig)
{
    const char m[] = "  [reraise] 恢复默认处置并重新发信号\n";
    write(STDOUT_FILENO, m, sizeof m - 1);

    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    raise(sig);                     /* 走默认动作：core + 终止 */

    _exit(128 + sig);               /* 兜底 */
}

static void run(const char *mode)
{
    pid_t p = fork();
    if (p == 0) {
        struct sigaction sa = {0};
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = SA_RESTART;

        if (!strcmp(mode, "exit"))        sa.sa_handler = bad_handler;
        else if (!strcmp(mode, "_exit"))  sa.sa_handler = good_handler;
        else                              sa.sa_handler = reraise_handler;

        sigaction(SIGSEGV, &sa, NULL);
        printf("子进程 %d (%s 模式) 触发 SIGSEGV...\n", getpid(), mode);
        fflush(stdout);
        raise(SIGSEGV);                   /* 触发 */
        _exit(0);
    }

    int st;
    waitpid(p, &st, 0);
    printf("  父进程观察: ");
    if (WIFSIGNALED(st))
        printf("WIFSIGNALED=true, 终止信号=%d (WTERMSIG)\n", WTERMSIG(st));
    else if (WIFEXITED(st))
        printf("WIFEXITED=true, 退出码=%d （看不出是被信号杀的）\n", WEXITSTATUS(st));
}

int main(int argc, char **argv)
{
    const char *modes[] = { "_exit", "exit", "reraise" };
    if (argc > 1) {
        run(argv[1]);
    } else {
        for (size_t i = 0; i < 3; i++) {
            printf("\n=== 模式: %s ===\n", modes[i]);
            run(modes[i]);
        }
    }
    return 0;
}
```

预期输出（关键差异在第 3 种）：

```
=== 模式: _exit ===
  父进程观察: WIFEXITED=true, 退出码=1 （看不出是被信号杀的）

=== 模式: exit ===
  父进程观察: WIFEXITED=true, 退出码=1 （且可能死锁，视时序）

=== 模式: reraise ===
  父进程观察: WIFSIGNALED=true, 终止信号=11 (WTERMSIG)   ← 正确保留了"被杀死"语义
```

## 自测题

<details>
<summary><b>问 1：</b>为什么不能在信号处理函数里调用 <code>exit()</code>？</summary>

`exit()` **不是异步信号安全函数**——它在进入内核前会执行一串用户态清理：

1. 调用 `atexit()` / `on_exit()` 注册的所有清理函数
2. **flush 并关闭所有 stdio 流**
3. 删除 `tmpfile()` 创建的临时文件
4. 最后才调用 `_exit()`

每一步都操作**全局数据结构并加锁**。

**经典死锁场景**：

```
主流程 exit(1)
  ├─ 获取 stdio 锁
  ├─ 正在 flush 缓冲区
  │                    ← 信号递送
  │                       handler: exit(1)
  │                         └─ 尝试获取 stdio 锁 → 已被持有 → 死锁
```

**关键在于**：handler **不是新线程**，它在**同一线程**上执行。主流程持有的锁不会被 handler"等待让出"——同一线程重入同一把非递归锁，直接死锁。

**正确做法**：用 `_exit()` / `_Exit()`，它们直接发起 `exit_group` 系统调用，跳过所有用户态清理，是异步信号安全的。

</details>

<details>
<summary><b>问 2：</b>什么是「恢复默认处置后重新发信号」技巧？解决什么问题？</summary>

**解决的问题**：保留「进程是被信号杀死的」这一语义信息。

如果 handler 里直接 `_exit(1)`，父进程 `wait()` 看到的是 `WIFEXITED=true, status=1`——**看起来像程序自己正常退出**，无法区分「被 OOM killer 杀」与「业务主动退出」。

**技巧步骤**：

```c
void handler(int sig)
{
    /* 1. 最小诊断（用 write） */
    write(STDERR_FILENO, "fatal\n", 6);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底 */
    _exit(128 + sig);
}
```

**效果**：

| 写法 | 父进程看到 | core |
|------|-----------|------|
| `_exit(1)` | `WIFEXITED=true, status=1` | ❌ |
| re-raise | **`WIFSIGNALED=true, WTERMSIG=sig`** | ✅（若默认动作是 core） |

**为什么有效**：`raise(sig)` 时 disposition 已是 `SIG_DFL`，内核在 `get_signal()` 里走致命分支——`do_coredump()`（若该信号产 core）+ `do_group_exit(signo)`（`kernel/signal.c:2878`/`:2892`）。

**第 4 步兜底必要**：若该信号在 handler 执行期间被阻塞（如 `sa_mask` 里有它），`raise` 只会让它 pending 而不会立即递送。此时 `_exit(128+sig)` 保证进程一定退出（`128+sig` 是 shell 表示"被信号 N 杀死"的惯例）。

</details>

<details>
<summary><b>问 3：</b><code>abort()</code> 有什么特殊之处？它一定会终止进程吗？</summary>

`abort()` **一定会终止进程**——这是它的契约保证。

**特殊机制**：`abort()` 会**先解除对 `SIGABRT` 的阻塞**，确保即使调用者用 `sigprocmask` 阻塞了 `SIGABRT`，`abort()` 也一定能生效。

**执行流程**：

```
abort()
  ├─ 解除对 SIGABRT 的阻塞
  ├─ raise(SIGABRT)
  │     ├─ 若有自定义 handler → 执行它
  │     └─ handler 返回 → 继续
  ├─ 把 SIGABRT 的处置恢复为 SIG_DFL
  ├─ 再次 raise(SIGABRT)      ← 这次一定走默认动作
  └─ 默认动作：do_coredump() + do_group_exit()  → 进程终止 + core dump
```

**关键设计**：即使用户注册了 `SIGABRT` handler 并且 handler 正常返回，`abort()` 也会**再次**发信号并强制走默认动作——所以 `abort()` **不可能被 handler"拦截"**。

**用途**：

- 断言失败（`assert()` 内部就是 `abort()`）
- 需要留下 core 供事后 gdb 分析
- 「不可恢复错误」的最终手段

**与 `_exit()` 的对比**：

| | `abort()` | `_exit()` |
|--|-----------|-----------|
| core dump | ✅ | ❌ |
| `WIFSIGNALED` | ✅（`SIGABRT`） | ❌ |
| 可被 handler 拦截 | ❌（会 re-raise） | 不适用 |
| 严格 async-signal-safe | ⚠️ POSIX 未列入，但 glibc 保证可用 | ✅ |

</details>

<details>
<summary><b>问 4：</b>内核执行「默认终止动作」时具体做了什么？</summary>

在 `get_signal()` 中（`kernel/signal.c:2861-2892`）：

```c
		/*
		 * Anything else is fatal, maybe with a core dump.
		 */
		current->flags |= PF_SIGNALED;

		if (sig_kernel_coredump(signr)) {          /* ① 判据 */
			if (print_fatal_signals)
				print_fatal_signal(ksig->info.si_signo);
			proc_coredump_connector(current);
			do_coredump(&ksig->info);              /* ② 写 core（:2878） */
		}

		if (current->flags & PF_USER_WORKER)
			goto out;

		/*
		 * Death signals, no core dump.
		 */
		do_group_exit(ksig->info.si_signo);         /* ③ 终止（:2892） */
		/* NOTREACHED */
```

| 步骤 | 行号 | 内容 |
|------|------|------|
| ① | `:2866` | `sig_kernel_coredump(signr)` 判断是否产 core |
| ② | `:2878` | 是 → `do_coredump()` 写 core 文件 |
| ③ | `:2892` | `do_group_exit(signo)` 终止**整个线程组** |

**判据**（`include/linux/signal.h:445`）：

```c
#define sig_kernel_coredump(sig)  siginmask(sig, SIG_KERNEL_COREDUMP_MASK)
```

`SIG_KERNEL_COREDUMP_MASK`（`include/linux/signal.h:425`）覆盖：`SIGQUIT`、`SIGILL`、`SIGTRAP`、`SIGABRT`、`SIGFPE`、`SIGSEGV`、`SIGBUS`、`SIGSYS`、`SIGXCPU`、`SIGXFSZ`、`SIGEMT`。

**两个要点**：

1. **产 core 的信号有限**——`SIGTERM`/`SIGINT`/`SIGKILL` 等**不产** core，只有上表 11 个会。
2. **`do_group_exit` 终止整个线程组**——多线程进程里任一线程触发致命信号，全进程一起退出，不只是那个线程。内核注释也强调了这点："this kills all other threads in the group and synchronizes with their demise"。

</details>

<details>
<summary><b>问 5：</b><code>exit()</code>、<code>_exit()</code>、<code>abort()</code>、re-raise 四者该怎么选？</summary>

| 方式 | async-signal-safe | flush stdio | atexit | core | `WIFSIGNALED` | 何时用 |
|------|-------------------|-------------|--------|------|---------------|--------|
| `exit()` | ❌ **危险** | ✅ | ✅ | ❌ | ❌ | handler 里**绝不用** |
| `_exit()`/`_Exit()` | ✅ | ❌ | ❌ | ❌ | ❌ | handler 中**默认选择**：快速、安全 |
| `abort()` | ⚠️ 实践可用 | ❌ | ❌ | ✅ | ✅ | 断言失败 / 需要 **core dump** |
| re-raise | ✅ | ❌ | ❌ | ✅（视信号） | ✅ | 需要**保留"被信号杀死"语义** |

**决策流程**：

```
handler 中要终止进程？
  ├─ 需要 core dump 供 gdb 分析？
  │    ├─ 是，用 abort()（固定 SIGABRT + core）
  │    └─ 是，且要保留原信号类型 → re-raise 技巧
  └─ 不需要，只想快速退出
       └─ _exit(status)  ← 默认选择
```

**HFT 特别建议**：

- 崩溃路径用 **re-raise**（保留 `WIFSIGNALED`，让监控能区分「被杀」与「自退」）
- 正常停机路径用 `_exit()`（快速、无锁）
- **诊断信息平时就落盘**（无锁环形队列 + 独立日志线程），不要等崩溃时才写——崩溃时刻的锁状态未知，任何 I/O 都可能死锁
