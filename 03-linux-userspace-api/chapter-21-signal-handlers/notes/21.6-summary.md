## 一、handler 设计的两条黄金法则

| # | 法则 | 原因 |
|---|------|------|
| 1 | **handler 只做最小动作**（通常只是设一个 `volatile sig_atomic_t` 标志） | handler 在被打断线程上执行，共享全部状态，加锁会自我死锁 |
| 2 | **只调用异步信号安全函数** | 非安全函数（`printf`/`malloc`/`exit`）持锁或用静态缓冲，重入会死锁或破坏数据 |

**根本原因**：handler **不是新线程**（[Ch20.4](../../chapter-20-signals-fundamentals/notes/20.4-introduction-to-signal-handlers.md)），它在同一线程的栈上执行。所以：

- 主流程持有的锁，handler 再来获取 → **死锁**（不是等待）
- 主流程操作到一半的数据结构，handler 看到的是**不一致状态**

## 二、异步信号安全速查

| ✅ 安全 | ❌ 不安全 |
|---------|-----------|
| `write()` / `read()` | `printf()` / `fprintf()` / `sprintf()` |
| `_exit()` / `_Exit()` | `exit()` |
| `kill()` / `raise()` / `sigaction()` / `sigprocmask()` | `malloc()` / `free()` / `calloc()` / `realloc()` |
| 给 `volatile sig_atomic_t` 赋值 | `strtok()` / `gmtime()` / `localtime()` |
| `strlen()` / `memcpy()` / `memset()` | 任何 `pthread_*` 函数 |
| — | `syslog()` / `fopen()` / `fclose()` |

> 完整清单见 `man 7 signal-safety`。判断原则：**可能加锁或分配内存的函数，一律假定不安全**。

## 三、从 handler 终止进程的四种方式

| 方式 | async-signal-safe | core dump | `WIFSIGNALED` | 何时用 |
|------|-------------------|-----------|---------------|--------|
| `exit()` | ❌ **危险** | ❌ | ❌ | **绝不用** |
| `_exit()` / `_Exit()` | ✅ | ❌ | ❌ | 默认选择，快速退出 |
| `abort()` | ⚠️ 实践可用 | ✅ | ✅ | 断言失败 / 需要 core |
| **恢复 `SIG_DFL` + `raise()`** | ✅ | ✅（视信号） | ✅ | 保留"被信号杀死"语义 |

## 四、备用栈要点

| 要点 | 说明 |
|------|------|
| **为什么需要** | 栈溢出时原栈无空间，handler 无法执行 → `force_sigsegv` 直接杀进程 |
| **两个步骤** | ① `sigaltstack()` 登记 ② `sigaction` 设 **`SA_ONSTACK`**（缺一不可） |
| **作用域** | **线程属性**，每个线程需各自设置，且需独立内存 |
| **大小** | 建议 **≥ 32KB**；太小会被 `force_sigsegv` 杀死 |
| **约束** | 不能在备用栈上运行期间修改它 → `-EPERM`（`do_sigaltstack:4226`） |
| **`SS_AUTODISARM`** | handler 返回后自动禁用，可安全 `free()`（`kernel/signal.c:2929`） |

---

## 五、`EINTR` 与 `SA_RESTART`

| 调用类别 | 设 `SA_RESTART` 后 |
|----------|-------------------|
| 普通慢调用（`read`/`write`/`wait`/`open`(FIFO)） | ✅ 自动重启 |
| **带超时**（`select`/`poll`/`epoll_wait`/`sigtimedwait`） | ❌ 仍返回 `EINTR` |
| **`connect`** | ❌ 返回 `EINTR` |
| **`nanosleep`** | ❌ 返回 `EINTR`，剩余时间写入 `rem` |
| **`close`**（Linux） | ❌ 返回 `EINTR`，但 **fd 已关闭——不要重试** |

**实践规则**：`SA_RESTART` 是**减少** `EINTR` 的便利手段，不是**免除** `EINTR` 处理的理由。I/O 多路复用与网络调用始终显式处理 `EINTR`。

---

## 六、`SA_SIGINFO` 与 `siginfo_t`

**`siginfo_t` 是 union**——同一块内存按信号类型有不同解读，**只有匹配当前信号的字段才有意义**（读错字段得到垃圾值且不报错）。

| 信号 | 有效字段 |
|------|----------|
| `kill` / `sigqueue` 来的 | `si_pid`、`si_uid`、`si_value` |
| `SIGSEGV`/`SIGBUS`/`SIGILL`/`SIGFPE` | **`si_addr`** |
| `SIGCHLD` | `si_pid`、`si_status`、`si_utime`/`si_stime` |
| `SIGPOLL`/`SIGIO` | `si_fd`、`si_band` |
| `SIGSYS`（seccomp） | `si_syscall`、`si_arch` |

**来源判据**（`siginfo.h:190-191`）：

```c
#define SI_FROMUSER(siptr)	((siptr)->si_code <= 0)    /* 用户进程 */
#define SI_FROMKERNEL(siptr)	((siptr)->si_code > 0)     /* 内核 */
```

## 七、更根本的方案：消灭 handler

本章讲的全是"如何安全地写 handler"。但更好的思路是**根本不写 handler**：

| 方案 | 机制 | 优势 |
|------|------|------|
| **signalfd** | 信号变 fd，`read()` 出来 | 无 handler → 无异步信号安全问题；可进 epoll |
| **`sigwaitinfo`** | 同步取信号 | 多线程专用线程模型，行为可预测 |
| **eventfd / self-pipe** | handler 只 `write` 一字节 | 需保留 handler 时的轻量桥接 |

> **HFT 视角**：handler 会异步抢占关键路径、产生不可控延迟毛刺。让信号走 signalfd 进事件循环，把"异步抢占"变成"同步事件"——这才是低延迟系统的正确架构。

## 代码示例

小结篇内联全章最核心的 Listing 21-1——**非可重入函数在 handler 里被重入的后果**，它是「法则 2：只调用异步信号安全函数」的直接反例。

### 一、`nonreentrant.c`（原书 Listing 21-1 · 21.1.2）

`crypt(3)` 返回指向**静态缓冲区**的指针，因此不可重入。程序先把 `crypt(argv[1])` 的结果 `strdup` 到自己的缓冲 `cr1`，再在主循环里反复 `strcmp(crypt(argv[1]), cr1)`；同时 handler 里也调 `crypt(str2)`。一旦信号在主循环的 `crypt` 返回后、`strcmp` 前插入，静态缓冲会被 handler 覆盖，`strcmp` 立刻报 `Mismatch`。

完整源码（[`code/nonreentrant.c`](../code/nonreentrant.c)）：

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* Listing 21-1 */

/* nonreentrant.c

   Demonstrate the nonreentrant nature of some library functions, in this
   example, crypt(3).
*/
#if ! defined(_XOPEN_SOURCE) || _XOPEN_SOURCE < 600
#define _XOPEN_SOURCE 600
#endif
#include <unistd.h>
#include <signal.h>
#include <string.h>
#include <crypt.h>
#include "tlpi_hdr.h"

static char *str2;                  /* Set from argv[2] */
static volatile int handled = 0;    /* Counts number of calls to handler */

static void
handler(int sig)
{
    crypt(str2, "xx");
    handled++;
}

int
main(int argc, char *argv[])
{
    char *cr1;
    int callNum, mismatch;
    struct sigaction sa;

    if (argc != 3)
        usageErr("%s str1 str2\n", argv[0]);

    str2 = argv[2];                      /* Make argv[2] available to handler */
    cr1 = strdup(crypt(argv[1], "xx"));  /* Copy statically allocated string
                                            to another buffer */
    if (cr1 == NULL)
        errExit("strdup");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sa.sa_handler = handler;
    if (sigaction(SIGINT, &sa, NULL) == -1)
        errExit("sigaction");

    /* Repeatedly call crypt() using argv[1]. If interrupted by a
       signal handler, then the static storage returned by crypt()
       will be overwritten by the results of encrypting argv[2], and
       strcmp() will detect a mismatch with the value in 'cr1'. */

    for (callNum = 1, mismatch = 0; ; callNum++) {
        if (strcmp(crypt(argv[1], "xx"), cr1) != 0) {
            mismatch++;
            printf("Mismatch on call %d (mismatch=%d handled=%d)\n",
                    callNum, mismatch, handled);
        }
    }
}
```

编译（macOS 26.6.2 / arm64 · clang 23.1.0）：

```bash
# nonreentrant.c：macOS 无 <crypt.h>，Linux 专有，Pi5 上编译
#   cc -D_GNU_SOURCE -I. -o nonreentrant nonreentrant.c get_num.c signal_functions.c -lcrypt
```

实测输出：**本机未取得**——macOS 无 `<crypt.h>`，编译不过，只能在 Linux / Pi5 上跑。`code/README.md`「macOS ↔ Linux 差异与未实测项」原文：

> `nonreentrant`（21-1） | macOS 无 `<crypt.h>` 编译不过；**Linux 专有**，Pi5 复测（预期：第二次进 handler 时 crypt 的静态缓冲已被上次调用覆盖）

**逐条解读**：

- **`cr1 = strdup(crypt(argv[1], "xx"))` 是整个演示的支点**：`strdup` 先把密文**拷贝到程序自己的缓冲**——否则 `cr1` 也指向同一个静态缓冲，比较永远相等，bug 就暴露不出来。
- **为什么要 `mismatch` 和 `handled` 两个计数**：`handled` 是 handler 被调用的次数，`mismatch` 是主流程抓到错配的次数。Linux 上的预期输出形如 `Mismatch on call N (mismatch=M handled=H)`——只要 `M > 0`，就实测复现了「静态缓冲被 handler 覆盖」。
- **`crypt()` 为什么不可重入**：它把结果写在自己的**静态缓冲区**并返回指针（`crypt(3)` 的 `RETURN VALUE` 明确写了这点）。`crypt_r()` 才是可重入版本（调用者提供缓冲）。所以 `crypt` 不在 `signal-safety(7)` 的安全清单里。
- **这是「法则 2」的杀伤力展示**：handler 里只调了一个「看起来无害」的库函数，没有 `printf`、没有 `malloc`，照样破坏主流程数据——因为它改的是主流程**下一次要读的全局状态**。这比死锁更隐蔽：程序不挂，只是偶尔算错。
- **修复方向**：handler 里**不要**调 `crypt`；改由 handler 只置旗，密文比较/重算全部留主流程；或者换 `crypt_r()` 并给 handler 一块独立缓冲。更彻底的做法是让信号走 signalfd，根本不进 handler（见本章「七、更根本的方案：消灭 handler」）。
- **对齐本章小结的判据**：`handled` 是 `volatile int`（不是 `sig_atomic_t`）——官方镜像保留原样，只为演示非可重入性，并非推荐写法；生产旗变量应写成 `volatile sig_atomic_t`。

**源码坐标**：TLPI **Listing 21-1**（21.1.2「异步信号安全」章节的原始示例）；`crypt(3)`（静态缓冲）、`crypt_r(3)`、`strdup(3)`、`sigaction(2)`、`signal-safety(7)`。

<details>
<summary><b>问 1：</b>写出一个"教科书式"的安全信号处理器，并说明每一行为什么这么写。</summary>

```c
static volatile sig_atomic_t got_signal = 0;      /* ① */

static void handler(int sig)                       /* ② */
{
    int saved_errno = errno;                       /* ③ */
    got_signal = 1;                                /* ④ */
    errno = saved_errno;                           /* ⑤ */
}

/* 主流程 */
for (;;) {
    if (got_signal) {                              /* ⑥ */
        got_signal = 0;
        handle_shutdown();     /* 这里可随意 printf/malloc */
    }
    do_work();
}
```

| # | 为什么 |
|---|--------|
| ① | `volatile` 防编译器缓存优化；`sig_atomic_t` 保证读写原子 |
| ② | 只有 `int sig` 一个参数（未设 `SA_SIGINFO`） |
| ③ | 保护 `errno`——handler 可能在主流程刚设完 `errno` 时插入 |
| ④ | **只做单次原子赋值**，不做读-改-写，无需锁 |
| ⑤ | 恢复 `errno`，避免破坏主流程的错误判断 |
| ⑥ | 复杂逻辑移回主流程，可自由使用任何库函数 |

**这个模式的关键**：handler 里**没有任何**函数调用（除了保存/恢复 errno，那是纯寄存器操作），因此 100% 安全。所有实质工作都在主流程完成。

</details>

<details>
<summary><b>问 2：</b>如果必须在 handler 里输出诊断信息，怎么做才安全？</summary>

**用 `write(2)`，不用 `printf`**：

```c
static void handler(int sig)
{
    /* 方案 1：固定字符串 */
    const char m[] = "caught signal\n";
    write(STDERR_FILENO, m, sizeof m - 1);      /* write 是 async-signal-safe */

    /* 方案 2：需要格式化时，预先格式化好或用极简转换 */
    char buf[32];
    char *p = buf + sizeof buf - 1;
    *p-- = '\n';
    int n = sig;
    do { *p-- = '0' + (n % 10); n /= 10; } while (n);
    p++;
    write(STDERR_FILENO, "sig=", 4);
    write(STDERR_FILENO, p, (buf + sizeof buf) - p);
}
```

**为什么不用 `printf`**：

- `printf` 内部**持有 stdio 锁**
- 主流程正 `printf` 持锁时信号递送 → handler 再 `printf` → **同一线程重入同一把锁 → 死锁**
- 即便不死锁，也可能破坏 stdio 缓冲区链表

**注意 `snprintf`**：很多代码在 handler 里用 `snprintf` 格式化，它**不在** POSIX 异步信号安全清单里（glibc 实现中可能分配内存）。实践中通常可用，但严格来说不安全。

**更稳妥的方案**：

1. handler 只把 `sig` 存进 `volatile sig_atomic_t`，主流程再格式化输出
2. 用 self-pipe / eventfd 把信号转到主流程
3. 用 signalfd，完全没有 handler

</details>

<details>
<summary><b>问 3：</b>备用栈设置好了但没设 <code>SA_ONSTACK</code>，会怎样？</summary>

**备用栈不会被使用**——handler 仍在原栈上执行，栈溢出时照样无法工作。

两个步骤语义不同：

| 调用 | 作用 |
|------|------|
| `sigaltstack(&ss, NULL)` | 向内核**登记**"有一块备用栈可用" |
| `sa_flags = SA_ONSTACK` | 告诉内核"**处理这个信号时**请切换到备用栈" |

**粒度**：`SA_ONSTACK` 是**每个信号独立**的。可以只让 `SIGSEGV` 用备用栈，其他信号仍在原栈执行——这正是常见做法（只有崩溃诊断需要备用栈）。

```c
stack_t ss = { .ss_sp = buf, .ss_size = SIGSTKSZ * 4, .ss_flags = 0 };
sigaltstack(&ss, NULL);                    /* ① 登记 */

struct sigaction sa = {0};
sa.sa_sigaction = segv_handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;     /* ② SA_ONSTACK 不可少 */
sigaction(SIGSEGV, &sa, NULL);
```

**验证方法**：查询备用栈状态，或在 handler 里查询：

```c
stack_t oss;
sigaltstack(NULL, &oss);
if (oss.ss_flags & SS_ONSTACK)
    /* 确实运行在备用栈上 */
```

</details>

<details>
<summary><b>问 4：</b>本章讲了四种终止方式，怎么选？</summary>

**决策流程**：

```
handler 中要终止进程？
  ├─ 需要 core dump 供 gdb 分析？
  │    ├─ 是 → abort()（固定 SIGABRT + core，且无法被 handler 拦截）
  │    └─ 是，且要保留原信号类型 → 恢复 SIG_DFL + raise(sig)
  └─ 不需要 core，只想快速安全退出
       └─ _exit(status)
```

| 方式 | 特点 |
|------|------|
| **`_exit()`** | 默认选择。异步信号安全、无锁、无 I/O、立即退出 |
| **`abort()`** | 需要 core dump。会先解除 `SIGABRT` 阻塞，保证一定生效 |
| **re-raise** | 需要让父进程 `wait()` 看到 `WIFSIGNALED`（区分"被杀"与"自退"） |
| **`exit()`** | ❌ **绝不用**——非异步信号安全，可能死锁 |

**HFT 建议**：

- 崩溃路径用 **re-raise**（`WIFSIGNALED` 语义让监控能区分事故类型）
- 正常停机用 `_exit()`
- **诊断信息平时就落盘**（无锁环形队列 + 独立日志线程），崩溃时刻的任何 I/O 都可能因锁状态未知而死锁

</details>

<details>
<summary><b>问 5：</b>从更高层面看，本章的技巧都是在"绕开"handler 的限制。有没有根本性的解法？</summary>

**有——根本不用 handler。** 本章讲的所有技巧（只设标志、只用安全函数、保护 errno）都是在**规避** handler 的固有缺陷。更好的架构是让信号根本不进入 handler：

| 方案 | 机制 | 消灭了什么问题 |
|------|------|---------------|
| **signalfd** | 阻塞信号 + `signalfd()` 拿 fd + `epoll` 监听 | 完全无 handler → 无异步信号安全、无抢占、无延迟毛刺 |
| **`sigwaitinfo`** | 阻塞信号 + 专用线程同步取 | 无 handler，且由固定线程处理，行为可预测 |
| **eventfd / self-pipe** | handler 只 `write` 一字节，主流程监听 | handler 极简化到只剩一次 `write` |

**对比**：

| | 传统 handler | signalfd |
|--|-------------|----------|
| 异步抢占关键路径 | ✅ 会 | ❌ 不会 |
| 异步信号安全限制 | ✅ 有 | ❌ 无 |
| 可调用 `printf`/`malloc` | ❌ | ✅ |
| 能接入 epoll 事件循环 | ❌（需 self-pipe） | ✅ 原生 |
| 信号丢失 | 标准信号会合并 | ❌ 不丢（内核队列） |
| 延迟可预测性 | ❌ | ✅ |

**HFT 结论**：交易系统的关键路径应**全程屏蔽**无关信号，控制信号（停机、配置重载）走 signalfd 进事件循环。handler 只作为 `SIGSEGV` 崩溃诊断的兜底设施，并配 `SA_ONSTACK` 备用栈。

详见 [Ch22.11 signalfd](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md)。

</details>
