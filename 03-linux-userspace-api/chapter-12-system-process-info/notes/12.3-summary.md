## 本章回顾：一批数据的三个入口

本章从头到尾在回答同一个问题：**「系统现在是什么样」这件事，该去哪儿问？** 三个入口的**能力边界**互不重叠：

| 入口 | 形态 | 给什么 | **不给什么** | 可移植性 |
|------|------|--------|-------------|---------|
| `uname()` | 一次系统调用，390 字节定长结构 | 系统**标识**：OS 名、主机名、内核版本、架构、NIS 域名 | CPU 数、内存量、负载、进程列表 | **POSIX**（`domainname` 是 GNU 扩展） |
| `gethostname()` | 一次调用，抄 `uname().nodename` | 主机名 | 同上 | **POSIX** |
| `/proc` | 一堆**文件**，`open`/`read`/`write` | 几乎所有东西：每进程一份 + 全局一份 | 无（这就是它的强大之处） | **Linux 专有** |
| `sysinfo()` | 一次系统调用，112 字节结构 | 内存/负载/uptime/procs 的**概览** | 细粒度（`Cached`/`Slab`/`MemAvailable` 都没有） | Linux + GNU |

一句话：**`uname()` 只回答「这台机器*是*什么」，`/proc` 回答「这台机器*正在发生*什么」。** 前者编译期常量居多、几乎不变；后者每次读都在变。

## 决策表：想查什么 → 用哪个入口

| 想查的东西 | 入口 | 稳定性 | 备注 |
|-----------|------|-------|------|
| OS 名 / 内核发布号 / 架构 | `uname()` | 编译期常量 | `release` **不要**用来判特性可用性 |
| 主机名 | `gethostname()`（POSIX）或 `/proc/sys/kernel/hostname`（Linux） | 运行时可改 | 缓冲给 **64** 字节，**必须查返回值** |
| NIS 域名 | `uts.domainname`（需 `_GNU_SOURCE`）或 `getdomainname()` | 运行时可改 | 默认字面量 `"(none)"` |
| 内存总量/可用量 | `/proc/meminfo`（细）或 `sysinfo()`（粗） | `MemTotal` 稳定、`MemFree` 漂移 | 别忘了 `× mem_unit` |
| 平均负载 | `/proc/loadavg`（两位小数）或 `sysinfo().loads[]`（定点） | 漂移 | `loads[i] / 65536.0` |
| 开机时长 | `/proc/uptime` 第一段（浮点） | 漂移 | `sysinfo().uptime` 是**向上取整**的整数 |
| CPU 个数 | `get_nprocs()` / `sysconf(_SC_NPROCESSORS_ONLN)` | 半稳定 | 容器里**不读 cgroup 配额** |
| 进程列表 | 遍历 `/proc/[0-9]*` | 完全动态 | 必须容忍进程随时消失 |
| 某进程的命令行 | `/proc/PID/cmdline`（完整 argv）或 `/proc/PID/comm`（≤15 字符） | 动态 | `cmdline` 用 `\0` 分隔 |
| 某进程打开的 fd | `/proc/PID/fd/*`（符号链接） | 动态 | target 前缀才是类型判据 |
| 内核可调参数 | `/proc/sys/**` 的 `open`+`read`/`write` | 运行时可改 | `sysctl(2)` 已删除 |

### `/proc` 全局文件 vs `sysinfo()`

| 项 | `/proc` 侧 | `sysinfo()` 侧 | 是否一致 |
|----|-----------|---------------|---------|
| 内存总量 | `MemTotal = 16079120 kB` → ×1024 = **16465018880** 字节 | `totalram × mem_unit = 16465018880` 字节 | ✅ **严格相等**（同源：都出自 `si_meminfo()`） |
| 空闲内存 | `MemFree = 346692 kB` | `freeram × mem_unit = 355012608` 字节 | 口径不同，**两次读之间就在变** |
| 负载 | `0.71 0.42 0.32` | `loads[] = 46464 27616 21056` → `/65536 = 0.71 0.42 0.32` | **一致** |
| 开机时长 | `uptime` 两个数（秒 + 各核空闲秒和） | `uptime = 48472` 秒 | `sysinfo` **向上取整**，最多差 1 秒 |
| 进程/线程数 | `/proc` 数字目录 **2** 个 | `procs = 236` | **差两个数量级** |

> **`procs` 那一行是本章最反直觉的数字**：man page 写 "Number of current processes"，而 `kernel/sys.c:2761` 赋的是 `info->procs = nr_threads;`——**线程数**。本容器 `procs=236` 而 `/proc` 下只有 2 个进程目录，原因**不是**命名空间隔离（`sysinfo()` 压根不做隔离，它报的是**宿主级**计数器），而是「宿主 236 个线程 vs 本 PID 命名空间 2 个进程目录」。
>
> `/proc/meminfo` 与 `sysinfo()` 的字节数**严格相等**（同源），这恰好**证明**二者都不是 cgroup 口径——容器里要配额必须读 cgroup。

## 「反直觉」清单

1. **`sizeof(struct utsname)` 是 390，不是 5 × 65** —— 有**六个**字段，第六个 `domainname` 是 GNU 扩展。
2. **`uname()` 在 Linux 上就是裸的 `uname(2)`** —— glibc 用 `sysdeps/unix/syscalls.list` 自动生成包装；`posix/uname.c` 里那份「libc 自己拼」的实现**不是 Linux 用的**。
3. **`gethostname(name, 2)` 返回 -1 而不是截断** —— 且失败时**缓冲里没有 NUL 终止符**。POSIX 允许两种行为，glibc 选了报错那一侧。
4. **`domainname = "(none)"` 是正常值** —— 内核的字面量初值（`UTS_DOMAINNAME`），不是「读取失败」。
5. **`/proc` 文件没有大小** —— `st_size = 0`（`/proc/version` 能读出 219 字节），`statfs().f_blocks = 0`。**不能按 st_size 分配缓冲**。
6. **`/proc` 的内容在 `read` 时现算** —— 同一个文件连读两次值不同；`/proc/self` 是内核现场拼的符号链接。
7. **`/proc/PID/status` 第 2 行不是 `Pid`，是 `Umask`** —— 字段顺序随内核版本增删，只能按 `key:` 查。
8. **`/proc/PID/stat` 的 `comm` 要用「第一个 `(` 配最后一个 `)`」定界** —— 朴素写法在进程名含 `)` 时会把后面 50 个字段全部读错位。要进程名就直接读 `/proc/PID/comm`。
9. **`cmdline` / `environ` 用 `\0` 分隔，不是空格也不是换行** —— `fgets` 只能拿到第一条。
10. **对 `O_RDONLY` 的 `/proc/sys` fd 调 `write` 是 `EBADF` 而不是 `EACCES`** —— 而「用 `O_RDONLY` 打开一个可写 knob」**会成功**。两次判据不一致。
11. **偏移不为 0 时写 `/proc/sys` 被内核静默忽略，`write` 却返回成功** —— 这就是 Listing 12-1 里那句 `lseek(fd, 0, SEEK_SET)` 的存在理由。
12. **`sysinfo().procs` 是线程数，不是进程数** —— man page 与实现不符（`info->procs = nr_threads;`）。
13. **`sysinfo()` 不做命名空间/cgroup 隔离** —— 容器里它报宿主机的线程数与内存量；`/proc/meminfo` 同样不是 cgroup 口径。
14. **`sysinfo().uptime` 是向上取整** —— 内核写 `tp.tv_sec + (tp.tv_nsec ? 1 : 0)`，所以它 ≥ `/proc/uptime` 的整数部分。
15. **`loads[]` 是定标 65536 的定点数** —— 忘了除会把负载 0.73 读成 47872，很容易被当成「负载爆表」写进告警阈值。
16. **`/proc/uptime` 第二个数不是 idle 比例** —— 它是「所有 CPU 空闲时间**之和**」，2 核机器上约等于 2× 开机秒。
17. **`get_nprocs()` 调用成功但 `errno = ENOENT`** —— 脏 errno 来自它内部第一条尝试（读 `/sys/devices/system/cpu/online` 失败）。`errno` 只在出错时有意义，成功时**不保证被清**。
18. **「有几个 CPU」不读 cgroup 配额** —— `docker run --cpus=2` 的容器里 `get_nprocs()` 完全可能报宿主的核数。要真实并行度用 `sched_getaffinity()` 或读 cgroup。
19. **`sysctl(2)` 自 Linux 5.5 起已删除** —— 只能走 `open`/`write` `/proc/sys/**`；glibc 里的 `sysctl` 只剩兼容符号，调用成功也不填数据。
20. **遍历 `/proc/PID` 时「进程消失」是常态不是异常** —— 原书在 `procfs_user_exe.c` 里对 `fopen` 失败只写了一句注释就 `continue`。

| 事实 | 值 | 影响 |
|------|----|------|
| `geteuid` / `getuid` | **0 / 0**（root） | `/proc/sys` 真的可写，Listing 12-1 的 `write` 分支能走通 |
| 进程数 | **2**（`dumb-init`=1、`output.s`=2） | `/proc/PID` 样本极少；进程树只有两层 |

## HFT / 嵌入式关联

| 场景 | 本章结论怎么用 |
|------|--------------|
| 启动自检 | `uname()` 的 `sysname/release/machine` + `sysinfo()` 的 `totalram` + `get_nprocs()` 一行落日志；**但它们全都不可作为特性判据**（发行版回填补丁、容器伪装版本） |
| 进程/线程数监控 | 要**进程数**就数 `/proc` 的数字目录或读 `/proc/loadavg` 第 4 段；要**线程数**读 `/proc/loadavg` 第 4 段的分母或 `/proc/PID/status` 的 `Threads:`。**不要**用 `sysinfo().procs`——它是宿主级线程数，容器里会给你一个完全无关的数量级 |
| 内存监控 | 细粒度必须 `/proc/meminfo`（`MemAvailable` 才是「还能分配多少」的近似）；`sysinfo().freeram` 只给「大概」。**任何 sysinfo 内存字段都要 `× mem_unit`** |
| 并行度决策 | 绑核/分 worker 用 `sched_getaffinity()` 的 `CPU_COUNT`（进程视角、受 cpuset 限制），**不要**用 `get_nprocs()`（机器视角、不看 cgroup） |
| 内核调参 | 一律 `open` + `write` `/proc/sys/**`，**写完必须回读验证**：`write` 返回成功不代表生效（偏移陷阱 + 内核 min/max 校验） |
| 容器/命名空间 | `uname()` / `/proc/PID/ns/*` 反映的是**当前命名空间**的视图；`sysinfo()` / `/proc/meminfo` **不做隔离**。要「本容器的配额」只有 cgroup |
| 嵌入式裁剪 | 裁剪 rootfs 若忘记 `mount -t proc proc /proc`，一切进程信息工具全失效。BusyBox 的 `ps`/`top` 就是读 `/proc`；`uname` 是 BusyBox 内建，但 `/bin/sh` 之外的 `popen` 路径要确认存在 |
| 高帧率禁用 | `/proc` 每个文件都是「读过才生成」（`seq_file` 序列化 + 内核态），有开销。监控线程 100 ms 采一次没问题，放进交易主循环就是灾难 |

<summary>本章自测（Q&A）</summary>

**Q1：一句话概括本章的核心技能。**
A：**分清「问谁」**。`uname()` 问系统的**身份**（可移植、几乎不变），`/proc` 问系统的**状态**（Linux 专有、每次读都在变），`sysinfo()` 是 `/proc` 的一层「一次系统调用换一屏概览」的快捷方式。搞错入口的代价是：拿到一个看着合理、但口径完全不对的数字（`sysinfo().procs` 是最好的例子）。

**Q2：`/proc` 文件为什么不能用 `st_size` 分配缓冲？**
A：因为它们**没有后备存储**。`stat("/proc/version")` 的 `st_size` / `st_blocks` 都是 **0**，但实际能读出 **219** 字节；`statfs("/proc")` 的 `f_blocks` / `f_files` 也是 **0**。内容由内核在 `read` 时现算（`seq_file`），所以只能「读到 EOF」。

**Q3：`/proc/PID/stat` 解析时最容易错在哪？**
A：`comm` 字段的定界。它被一对括号包住，而 `comm` 本身**可以含空格与括号**，所以分隔符不是空格。规则是**第一个 `(` 配最后一个 `)`**。实测把名字改成 `a)b`：正确切法长度 **3**（`a)b`），朴素切法长度 **1**（`a`）——后面约 50 个字段全部错位。省事的办法是直接读 `/proc/PID/comm`。

**Q4：写出 `/proc/sys` knob 的正确写法。**
A：
① 用 `O_WRONLY`（或 `O_RDWR`）打开，不要用 `O_RDONLY`（否则 `write` 得到 `EBADF(9)`）；
② `write` 之前 `lseek(fd, 0, SEEK_SET)`——否则内核**静默忽略**却返回成功；
③ 检查 `write` 的返回值与 `errno`（越界值会给 `EINVAL(22)`）；
④ **回读验证**（`lseek(0)` 后 `read`，或重新 `open`）——这是唯一能证明「真的改成了」的办法。

**Q5：`sysinfo().procs` 报 236，而 `/proc` 下只有 2 个进程目录，是不是容器被限制了？**
A：**不是**。两个独立原因叠加：① `procs` 在内核里赋的是 `nr_threads`——**线程数**，man page 的 "Number of current processes" 与实现不符；② `sysinfo()` **不做命名空间隔离**，它读的是宿主级计数器。而 `/proc` 的**进程目录列表**是 PID 命名空间隔离的。所以「236 vs 2」= 宿主的线程数 vs 本命名空间的进程数。

**Q6：`uname()` 和 `gethostname()` 会给出不同的主机名吗？**
A：**不会**。glibc 的 `gethostname()` 先调 `__uname(&buf)`，再把 `buf.nodename` `memcpy` 出来（`sysdeps/posix/gethostname.c:26-46`）。两者读同一个内核字段。差别只在可移植性与错误处理：`gethostname` 是 POSIX，且缓冲不足时返回 `-1/ENAMETOOLONG`。

**Q7：本章哪些实测数字是「一次运行有效」，哪些是「环境常量」？**
A：稳定：`sizeof(struct utsname)=390`、`sizeof(struct sysinfo)=112`、`_SC_HOST_NAME_MAX=64`、`statfs("/proc")` 的 `f_type=0x9fa0`/`f_blocks=0`、`stat("/proc/version").st_size=0`、`statm` 的字段个数（7）、`ns` 的 inode 语义、各错误码（`EFAULT`/`ENAMETOOLONG`/`EBADF`/`EINVAL`/`EACCES`）。会漂移：`uptime`、`loads[]`、`freeram`、`procs`、`get_avphys_pages()`、`/proc/self/fd` 条目数、`/proc` 顶层计数、`environ` 字节数。引用后者必须注明是哪一次运行。

**Q8：为什么本章要专门写一节的「沙箱环境限制表」？**
A：因为本章的很多结论**依赖环境**。CE 容器是 root（所以 `write /proc/sys` 能成功）、只有 2 个进程（所以进程树只有两层）、没有 `/bin/sh`（所以 Listing 12-1 最后的 `system()` 必然失败）、没有 `/sys`（所以 `get_nprocs()` 必然走 `/proc/stat` 退路并留下脏 `errno`）、`/etc/passwd` 只有 1 条（所以 `procfs_user_exe.c` 只能用数字串 UID）。这些前提不写清，读者会以为「`get_nprocs()` 总是留下 `ENOENT`」或「`procs` 总是比进程数大很多」。
