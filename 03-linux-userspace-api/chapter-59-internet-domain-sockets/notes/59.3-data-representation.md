## 本节讲什么

跨平台网络数据传输的表示问题：不同架构的整数大小、对齐、浮点格式差异。

---

## 要点

### 问题来源

| 差异 | 例子 |
|------|------|
| 整数大小 | `int` 在 ILP32 是 32 位，LP64 是 64 位 |
| 字节序 | x86 小端，SPARC 大端 |
| 结构体对齐 | `#pragma pack` 不同 |
| 浮点 | 几乎都是 IEEE 754，但非保证 |

### 解决方案

| 方案 | 适用场景 |
|------|----------|
| 文本协议 (HTTP, SMTP) | 通用、可调试，但解析慢 |
| 固定宽度整数 (`uint32_t`) | 二进制协议标准做法 |
| 序列化框架 (protobuf) | 复杂结构 |
| TLV (Type-Length-Value) | 灵活可扩展 |

### 二进制协议最佳实践

```c
/* 用固定宽度类型, 明确字节序 */
struct msg {
    uint32_t magic;      /* 固定 magic number */
    uint16_t version;    /* 协议版本 */
    uint16_t type;       /* 消息类型 */
    uint32_t length;     /* payload 长度 */
    /* payload follows */
};
/* 所有字段用 htonl/htons 转换后发送 */
```

### 常见陷阱

- 不要直接 `send(struct, sizeof(struct))` — 对齐和字节序不可控
- 不要用 `int`/`long` — 用 `uint32_t`/`uint64_t`
- 浮点数用文本传输或自定义编码

### 陈硕网络编程课开篇：新手常见坑逐条实证

陈硕《Linux C++ 网络编程实践》第 0 讲的 Common pitfalls of novices 清单，与本节（#4）及 TLPI 全书多处呼应。逐条给出本机实证：

| # | 坑 | 实证落点 |
|---|-----|---------|
| 1 | 业务逻辑与网络 IO 混在一起，无法单测 | 架构问题（muduo 的 Reactor + 回调分层就是答案），见 ch60 |
| 2 | 一次 recv 没拿全对端发的数据 | ✅ 实测② |
| 3 | 误判 TCP 消息边界 | ✅ 实测③ |
| 4 | 直接 send C 结构体 | ✅ 实测①（本节主题） |
| 5 | TCP 自连接 localhost:54321 <-> localhost:54321 | ✅ 实测④（Linux 独有） |
| 6 | 非阻塞编程的更多坑 | ch63 替代 IO 模型展开 |

**实测①：改全局对齐设置 → 第三方库读到垃圾（clang 23，arm64）**

课件原话"Modify the global align setting causes core dump in 3rd party library"。复现手法：公共头文件 `pkt.h` 定义 `struct Pkt { uint8_t type; uint32_t seq; };`，第三方库 `lib.c` 正常编译，`main.c` 用 `-fpack-struct` 全局改对齐（等价于 `#pragma pack(1)` 泄漏到整个 TU）：

```
正常（两边都不 pack）：
  [main] sizeof(Pkt)=8 offsetof(seq)=4 seq=0xAABBCCDD
  [lib]  sizeof(Pkt)=8 offsetof(seq)=4 seq=2864434397   ← 0xAABBCCDD，一致
main 加了全局 -fpack-struct：
  [main] sizeof(Pkt)=5 offsetof(seq)=1 seq=0xAABBCCDD
  [lib]  sizeof(Pkt)=8 offsetof(seq)=4 seq=6062250      ← 垃圾！
```

同一块内存，main 按偏移 1 写 `seq`，lib 按偏移 4 读——**两边对同一类型的"布局认知"不一致**。本例只是读到垃圾值；真实项目里结构体若含指针/函数指针，读错位 = 野指针 = core dump。教训三条：

- `#pragma pack` / `-fpack-struct` 是**编译单元级**的， ABI 契约却是**链接级**的——头文件里改对齐必须 `push`/`pop` 配对，绝不能泄漏
- 协议结构体**永远不要**靠改全局对齐来"凑"线格式；正确做法是固定宽度类型 + 显式逐字段序列化（上文 msg_hdr 模式），或 `_Static_assert(sizeof(struct Pkt)==5)` + `packed` 属性只作用于协议结构体本身
- 这也是为什么 `send(&struct, sizeof(struct))` 不可移植：线格式里混入了**填充字节**（本例自然布局下 3 字节填充，内容未定义）

**实测②③：一次 recv 拿不全 + TCP 没有消息边界（macOS 26 回环）**

同一程序内起服务端线程 + 客户端：

```
[client] 已发送 200000 字节
[server] 客户端 send() 了 200000 字节，一次 recv() 只拿到 65328 字节   ← 拿不全！
[client] 服务端发了两次("abc"+"def")，一次 recv 拿到 6 字节: "abcdef"  ← 边界消失！
```

两个数字合起来就是 TCP 字节流语义的全部要点：**recv 返回的是"当前缓冲区里有多少"，与 send 的次数、大小毫无对应关系**。正确姿势：按协议头里的 length 字段循环 recv 直到收满（TLPI 61.13 的 readLine / muduo 的 Buffer + length-header codec 都是这个模式）。

**实测④：TCP 自连接（Linux 6.18.39 Pi 5 实测，macOS 26 对照）**

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
bind(fd, {127.0.0.1, 54321});      /* 绑定后不 listen */
connect(fd, {127.0.0.1, 54321});   /* 直接连自己 */
```

| 平台 | 结果 |
|------|------|
| Linux 6.18（Pi 5, gcc 14.2） | **connect 成功**！`local=54321 peer=54321`，且 `send("hi")` 后自己能 `recv` 到 "hi"——一个 socket 首尾相接 |
| macOS 26（clang 23） | `connect 失败: Invalid argument`（EINVAL，BSD 系内核拒绝） |

成因：Linux 的 TCP 在 connect 目标恰为自身地址+端口时走了**同时打开（simultaneous open）**路径，SYN 与 SYN+ACK 交叉后四次握手合流，连接成立且两端是同一个 socket。陈硕把它列为新手坑的场景：程序 bind 了一个端口后又误连自己，得到一个"连接成功"但行为诡异的 socket。跨平台代码不能依赖这个行为——BSD/macOS 直接拒绝。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ARM + x86 混合通信必须统一二进制格式 |
| HFT | 二进制协议 + 固定宽度类型 + 零拷贝解析，延迟最低 |

## 代码示例

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <arpa/inet.h>
/* 二进制数据表示: 固定宽度 + 网络字节序 */
struct msg_hdr {
    uint32_t magic;
    uint16_t version;
    uint16_t type;
    uint32_t length;
};

int main(void) {
    /* 构造消息头 */
    struct msg_hdr hdr = {
        .magic = 0x4D474348,  /* "MGCH" */
        .version = 1,
        .type = 2,
        .length = 100
    };

    /* 序列化: 转为网络字节序 */
    uint32_t net_magic = htonl(hdr.magic);
    uint16_t net_ver = htons(hdr.version);
    uint16_t net_type = htons(hdr.type);
    uint32_t net_len = htonl(hdr.length);

    /* 发送时直接 send(&net_xxx, sizeof) */
    printf("serialized: magic=0x%08x ver=%d type=%d len=%d\n",
           net_magic, net_ver, net_type, net_len);

    /* 接收端反序列化 */
    hdr.magic = ntohl(net_magic);
    hdr.version = ntohs(net_ver);
    hdr.type = ntohs(net_type);
    hdr.length = ntohl(net_len);
    printf("deserialized: magic=0x%08x ver=%d type=%d len=%d\n",
           hdr.magic, hdr.version, hdr.type, hdr.length);
    return 0;
}
```
