# 6.5 栈与栈帧：272 字节一帧，30840 层就没了

> 源码核验：Linux v6.6 · `RLIMIT_STACK` 的落地在 `mm/mmap.c`（`expand_downwards` / guard gap）；本节数据由 [CE 复核](https://godbolt.org/)实测
> 本章：[TLPI 第 06 章 — Processes](../README.md)
> - 上一节：[6.4 虚拟内存管理](./6.4-virtual-memory.md)
> - 下一节：[6.6 命令行参数 `argv`](./6.6-command-line-args.md)

## 本节讲什么

每次函数调用在栈上压一个**栈帧**（stack frame），装着返回地址、旧帧指针、局部变量、保存的寄存器。这一节把三个数字钉死（都来自实测）：

1. **方向**：x86-64 上栈向**低地址**增长；
2. **每帧多大**：这台的实测值是 **272 字节/帧**（取决于 padding 与编译器）；
3. **多少层会死**：8 MB ÷ 272 B ≈ **30840 层**，超了就是 **SIGSEGV**，没有"优雅报错"。

---

## 要点

### 栈帧长什么样

```text
高地址  │ 调用者的栈帧        │
        ├────────────────────┤
        │ 参数（第 7 个起）    │
        ├────────────────────┤
        │ 返回地址            │ ← call 指令压入
        ├────────────────────┤
        │ 保存的 rbp          │ ← 帧指针（-O0 下 rbp 指向这里）
        ├────────────────────┤
        │ 保存的被调用者寄存器 │  rbx / r12-r15
        ├────────────────────┤
        │ 局部变量            │  ← 含数组、padding
低地址  │ ...                │ ← rsp 指向栈顶
```

⚠️ 别把"栈帧 = 局部变量"当全部：**返回地址和保存的寄存器也在里面**，这解释了为什么"递归太深"和"局部大数组"是同一类炸栈原因。

### 栈 vs 堆

| 特性 | 栈 | 堆 |
|------|----|----|
| 分配方式 | 移动 `rsp`（一条指令） | `malloc` 搜索空闲块 / 系统调用 |
| 释放 | 函数返回自动回收 | 手动 `free` |
| 大小 | **受 `RLIMIT_STACK` 限制（默认 8 MB）** | 受虚拟地址空间 + 物理内存 + swap 限制 |
| 增长方向 | 向**低**地址 | 向**高**地址（`brk`） |
| 碎片 | 无 | 有 |
| 多线程 | **每线程一个栈**，大小可用 `pthread_attr_setstacksize` 设 | 进程内共享 |

### 栈溢出（stack overflow）的三条事实

1. 内核给栈留了一段**不可访问的 guard page**；`rsp` 撞进去 → 硬件报页错误 → 内核送 **SIGSEGV**。
2. **不是"分配失败"那种可检查的错误**：没有返回值、没有 errno，直接是信号。
3. gcc **能静态检出部分无限递归**（`-Winfinite-recursion`），但**检测不到"递归有限但太深"**——那个只能靠跑。

## 代码

完整程序见 [`../code/c6_5_stack_frame.c`](../code/c6_5_stack_frame.c)：先量方向与帧大小，再把"无上限递归"放进子进程看它怎么死。

```c
/* c6_5_stack_frame.c — 6.5 栈与栈帧：方向、每帧字节数、栈上限、爆栈后果
 * 编译: gcc -O2 -Wall -Wextra -o c6_5_stack_frame c6_5_stack_frame.c
 * 说明: 递归函数里留 256B padding 并真实写它，防止被优化成尾调用/循环。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
#include <sys/resource.h>

#define PAD         256
#define SAFE_DEPTH  8000        /* 8000 × 272B ≈ 2.1MB，稳在 8MB 栈以内 */

static volatile long depth = 0;
static volatile long top1 = 0, top2 = 0;

/* 有深度上限：用来量每帧占用 */
static void recurse_safe(void)
{
    volatile char pad[PAD];
    pad[0] = (char)depth;                        /* 真实使用，防优化掉 */
    if (!top1) top1 = (long)&pad[0];
    else if (!top2) top2 = (long)&pad[0];

    depth++;
    if (depth < SAFE_DEPTH) recurse_safe();
    pad[PAD - 1] = 1;                            /* 递归调用后仍有代码 -> 不是尾调用 */
}

/* 无深度上限：制造爆栈 */
static void recurse_bomb(void)
{
    volatile char pad[PAD];
    pad[0] = (char)depth;
    depth++;
    recurse_bomb();
    pad[PAD - 1] = 1;
}

int main(void)
{
    /* ---- A. 栈增长方向 ---- */
    char a = 0, b = 0;
    char *hi = &a, *lo = &b;
    if (hi < lo) { char *t = hi; hi = lo; lo = t; }
    printf("A. 先声明的 %p > 后声明的 %p  ->  x86-64 栈向【低地址】增长\n",
           (void *)hi, (void *)lo);

    /* ---- B. 每帧字节数 ---- */
    top1 = top2 = 0; depth = 0;
    recurse_safe();
    long frame = top1 - top2;
    printf("B. 递归深度 %ld，相邻两层 pad[0] 相距 %ld B -> 每帧约 %ld B\n",
           depth, frame, frame);
    printf("   （8MB 栈 ÷ %ld B/帧 ≈ %ld 层就会耗尽）\n",
           frame, (8L * 1024 * 1024) / frame);

    /* ---- C. 栈上限 ---- */
    struct rlimit rl;
    getrlimit(RLIMIT_STACK, &rl);
    printf("C. RLIMIT_STACK = %lu MB（ulimit -s 改的就是它）\n",
           (unsigned long)(rl.rlim_cur / 1024 / 1024));

    /* ---- D. 爆栈后果：放进子进程，避免把自己搞死 ---- */
    pid_t c = fork();
    if (c == 0) { depth = 0; recurse_bomb(); _exit(0); }
    int st = 0;
    wait(&st);
    if (WIFSIGNALED(st))
        printf("D. 无上限递归的子进程：被信号 %d 杀死（%s）—— 栈溢出不是「优雅报错」，是直接 SIGSEGV\n",
               WTERMSIG(st), WTERMSIG(st) == SIGSEGV ? "SIGSEGV" : "其他");
    return 0;
}
```

编译与运行：

```bash
gcc -O2 -Wall -Wextra -o c6_5_stack_frame c6_5_stack_frame.c && ./c6_5_stack_frame
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
A. 先声明的 0x7ffe688827fb > 后声明的 0x7ffe688827fa  ->  x86-64 栈向【低地址】增长
B. 递归深度 8000，相邻两层 pad[0] 相距 272 B -> 每帧约 272 B
   （8MB 栈 ÷ 272 B/帧 ≈ 30840 层就会耗尽）
C. RLIMIT_STACK = 8 MB（ulimit -s 改的就是它）
D. 无上限递归的子进程：被信号 11 杀死（SIGSEGV）—— 栈溢出不是「优雅报错」，是直接 SIGSEGV
```

编译时 gcc 还顺带报了两条（**这是有价值的信息，不是噪音**）：

```text
<source>:33:19: warning: variable 'pad' set but not used [-Wunused-but-set-variable]
<source>:31:13: warning: infinite recursion detected [-Winfinite-recursion]
<source>:36:5: note: recursive call
```

**解读**：

1. **`272 B/帧` 是本程序的实测值**，不是通用常数。它 = 256 B 的 `pad` 数组 + 保存的 rbp + 对齐填充。换编译器、换 `-O` 级别、改变量数量都会变——所以**判断"会不会爆栈"必须量，不能猜**。
2. **`30840 层`是算出来的**（8 MB ÷ 272 B），但它是**上限估计**：每层还要算上一次函数调用的开销、以及 main 自己的栈帧。实际能到 3 万上下；这个数量级对"用递归处理大数组"是致命的。
3. **`SIGSEGV(11)` 就是栈溢出的形态**：子进程不是"返回错误"，而是被信号打死。父进程用 `WIFSIGNALED` + `WTERMSIG` 才看得出死因（如果用 `WEXITSTATUS` 会读出 0 这种假象）。
4. **`-Winfinite-recursion` 只在"编译器能证明必无限"时才报**。把 `if (depth < SAFE_DEPTH)` 加上就不会报——但那个版本仍可能因为深度太大而爆栈。**编译器管不了"太深"，只管"无限"**。
5. **`volatile char pad[PAD]` 里的 `volatile` 与"递归调用后再写 pad"都是为了防优化**：不加的话 gcc 会把它变成尾调用或循环，栈根本不涨，测出来的帧大小毫无意义（这是写栈相关微基准最容易翻车的地方）。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 线程/任务栈大小必须显式指定（`pthread_attr_setstacksize`、RTOS 的 task stack size）。FreeRTOS 这类系统通常只有几十 KB 栈，**272 B/帧意味着 100 层就炸**，所以嵌入式规范常禁止递归 |
| HFT | 热路径上的深递归是延迟不确定性的来源之一；更隐蔽的是**大局部数组**——`char buf[1<<20]` 一进函数就吃掉 1 MB 栈，几次嵌套就撞 guard page |
| HFT | 多线程 HFT 程序里，**每个线程栈**默认 8 MB（`pthread_attr` 里可调）。开 64 个线程 = 理论上 512 MB 地址空间（物理页仍按需才分），但 guard page 撞上就是整个进程挂 |
| HFT | 想抓栈溢出用 `-fstack-usage` 看每函数静态栈用量，或用 `ulimit -s unlimited` 配合 `-fstack-clash-protection` 排查；线上别关 guard page |

## 自测题

**题目 1：** 为什么"爆栈"不会返回错误码而是直接 SIGSEGV？

<details>
<summary>参考答案</summary>

因为栈的边界靠**硬件页保护**实现：内核在栈底留了一个 guard page（不可访问）。当 `rsp` 推进到 guard page 上并读写时，MMU 报页错误，内核的缺页处理发现"这是栈越界"（地址在 VMA 的 guard 区），无法合法扩展，于是送 SIGSEGV。整个过程没有"返回失败"的通道——它是异常，不是函数返回值。

</details>

**题目 2：** 上面程序为什么要把 `recurse_bomb()` 放进 `fork()` 出来的子进程里跑？

<details>
<summary>参考答案</summary>

因为栈溢出会**杀死整个进程**。如果直接在 main 里跑，程序在打印 D 段结果之前就死了，父进程那份"报告死因"的逻辑也没机会执行。放进子进程后，父进程 `wait(&st)` 拿到状态，用 `WIFSIGNALED/WTERMSIG` 读出"被 SIGSEGV 杀死"，还能正常收尾。这也是测试任何"会崩溃的路径"的标准手法——**把崩溃隔离在子进程**。

</details>

**题目 3：** 如果把 `volatile char pad[PAD]` 的 `volatile` 去掉、也删掉 `pad[PAD-1] = 1;`，会测出什么？

<details>
<summary>参考答案</summary>

gcc 会把 `recurse_safe()` 优化成尾调用或循环，`rsp` 几乎不动，`top1 - top2` 会得到 0 或一个荒谬的大数。帧大小、爆栈深度全部失真。这就是写栈相关微基准必须防优化的原因：**编译器看不见效果就会把它消掉**。同样的原因，测量递归深度时那个数组必须真实使用、且递归调用之后必须还有代码（阻止尾调用优化）。

</details>
