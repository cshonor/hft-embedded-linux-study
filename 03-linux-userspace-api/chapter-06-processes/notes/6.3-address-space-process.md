# 6.3 进程虚拟地址空间：段落在哪，内核怎么记

> 源码核验：Linux v6.6 · `include/linux/mm_types.h:673`（`struct mm_struct`）· `:807`（`arg_lock`）· `:809-811`（各段界与 argv/env 指针）

> - 上一节：[6.2 PID 与 PPID](./6.2-pid-ppid.md)
> - 下一节：[6.4 虚拟内存管理](./6.4-virtual-memory.md)

## 本节讲什么

每个进程有一套**自己的虚拟地址空间**，从低到高大致分五段：代码（text）、已初始化数据（data）、未初始化数据（bss）、堆（heap）、栈（stack）。这一节要钉死两件事：

1. **每类变量落在哪一段**——不是背结论，而是能用一个程序打印地址、再用 `/proc/self/maps` 交叉验证。
2. **内核对这件事有精确记账**：`mm_struct` 里成对存着 `start_code/end_code`、`start_data/end_data`、`start_brk/brk`、`start_stack`，argv 和 environ 也各有一对 `arg_start/arg_end`、`env_start/env_end`。

---

## 要点

### 经典布局（低 → 高）

```text
高地址  ┌──────────────────────┐
        │  内核空间（用户不可访） │
        ├──────────────────────┤
        │  栈 stack ↓           │  局部变量、参数、返回地址；受 RLIMIT_STACK 限制
        ├──────────────────────┤
        │  mmap 区 / 共享库      │  libc、mmap 出来的大块内存
        ├──────────────────────┤
        │  堆 heap ↑            │  malloc；上界 = program break（Ch7）
        ├──────────────────────┤
        │  bss（未初始化数据）    │  加载时清零；磁盘映像里几乎不占空间
        ├──────────────────────┤
        │  data（已初始化数据）   │  显式初始化的全局/静态
        ├──────────────────────┤
低地址  │  text（代码段，只读）   │  指令；同程序多进程可共享同一份物理页
        └──────────────────────┘
```

### 内核的记账（`mm_struct` 里的字段）

```c
/* include/linux/mm_types.h (v6.6) */
struct mm_struct {                                        /* :673 */
	struct {
		...
		spinlock_t arg_lock; /* protect the below fields */   /* :807 */
		unsigned long start_code, end_code, start_data, end_data;   /* :809 */
		unsigned long start_brk, brk, start_stack;                  /* :810 */
		unsigned long arg_start, arg_end, env_start, env_end;       /* :811 */
		...
	};
	...
};
```

| 字段 | 对应哪一段 | 用户态怎么看到 |
|------|-----------|---------------|
| `start_code` / `end_code` | text | `/proc/[pid]/maps` 的 `r-xp` 行 |
| `start_data` / `end_data` | data | `rw-p` 行（与 bss 合并在同一个段里） |
| `start_brk` / `brk` | 堆的起止 | 堆顶 = `sbrk(0)` 的返回值 |
| `start_stack` | 栈底（高地址端） | `/proc/[pid]/stat` 第 28 字段 |
| `arg_start/env_start` | argv / environ 字符串 | `/proc/[pid]/cmdline`、`/proc/[pid]/environ` |

⚠️ 两个容易混的点：

- **bss 没有独立的 start/end 字段**。它和 data 在同一个可读写段里，靠"文件映射大小 vs 内存大小"的差体现（`/proc/[pid]/maps` 里同一行的 offset 与设备号不同）。
- **`arg_lock` 保护的是后面那三行**（注释原文 `protect the below fields`）——因为 `arg_start/arg_end/env_start/env_end` 会在 `execve` 装载新程序时被改写，而 `/proc/[pid]/cmdline` 的读取是另一个上下文，要加锁。

### 变量落在哪一段（一张会用一辈子的表）

| 声明 | 落在 |
|------|------|
| 函数体 `int x;` | 栈 |
| `malloc()` / `new` 返回的内存 | 堆（大块走 mmap） |
| `int g = 7;` 全局/静态 | data |
| `static int g = 7;`（文件内） | data |
| `int g;` / `static int g = 0;` | **bss**（显式 = 0 也算未初始化） |
| `static const char *s = "hi";` | 指针 `s` 在 data；`"hi"` 在 `.rodata` |
| `"hi"` 字面量本体 | `.rodata`（只读，改写 → SIGSEGV） |
| 函数名 `main` | `.text` |

## 代码

完整程序见 [`../code/c6_3_addr_space.c`](../code/c6_3_addr_space.c)，打印各类变量的地址，再读 `/proc/self/maps` 对照。

```c
/* c6_3_addr_space.c — 6.3 进程虚拟地址空间：各段落点 + /proc/self/maps 交叉验证
 * 编译: gcc -O2 -Wall -Wextra -o c6_3_addr_space c6_3_addr_space.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>

/* 落在只读数据段（.rodata）的字面量 */
const char *ro_lit = "hello";

/* .data：显式初始化 */
int g_init = 7;
static int s_init = 100;

/* .bss：未初始化（或显式 0），加载时清零，磁盘上几乎不占空间 */
int g_zero;
static int s_zero;
static int s_expl_zero = 0;      /* 显式 = 0 也进 BSS */

int main(void)
{
    int stack_var = 42;                          /* 栈 */
    int *heap_var = malloc(sizeof *heap_var);    /* 堆 */
    *heap_var = 99;

    printf("=== 变量地址（低 -> 高）===\n");
    printf("  main 函数体    %p   <.text 代码段>\n", (void *)main);
    printf("  字面量 \"hello\" %p   <.rodata 只读>\n", (void *)ro_lit);
    printf("  g_init         %p   <.data 已初始化>\n", (void *)&g_init);
    printf("  s_init         %p   <.data>\n", (void *)&s_init);
    printf("  g_zero         %p   <.bss 未初始化, 值=%d>\n", (void *)&g_zero, g_zero);
    printf("  s_zero         %p   <.bss, 值=%d>\n", (void *)&s_zero, s_zero);
    printf("  s_expl_zero    %p   <.bss 显式=0 也进 BSS>\n", (void *)&s_expl_zero);
    printf("  heap(malloc)   %p   <堆, 值=%d>\n", (void *)heap_var, *heap_var);
    printf("  stack_var      %p   <栈>\n", (void *)&stack_var);

    printf("\n=== /proc/self/maps 前 8 行（内核眼中的真相）===\n");
    FILE *f = fopen("/proc/self/maps", "r");
    if (f) {
        char line[512];
        for (int i = 0; i < 8 && fgets(line, sizeof line, f); i++)
            printf("  %s", line);
        fclose(f);
    }
    free(heap_var);
    return 0;
}
```

编译与运行：

```bash
gcc -O2 -Wall -Wextra -o c6_3_addr_space c6_3_addr_space.c && ./c6_3_addr_space
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
=== 变量地址（低 -> 高）===
  main 函数体    0x4010a0   <.text 代码段>
  字面量 "hello" 0x402211   <.rodata 只读>
  g_init         0x40404c   <.data 已初始化>
  s_init         0x404048   <.data>
  g_zero         0x40405c   <.bss 未初始化, 值=0>
  s_zero         0x404064   <.bss, 值=0>
  s_expl_zero    0x404060   <.bss 显式=0 也进 BSS>
  heap(malloc)   0x24ed42a0   <堆, 值=99>
  stack_var      0x7ffeb3cff24c   <栈>

=== /proc/self/maps 前 8 行（内核眼中的真相）===
  00400000-00401000 r--p 00000000 ca:01 359002              /app/output.s
  00401000-00402000 r-xp 00001000 ca:01 359002              /app/output.s
  00402000-00403000 r--p 00002000 ca:01 359002              /app/output.s
  00403000-00404000 r--p 00002000 ca:01 359002              /app/output.s
  00404000-00405000 rw-p 00003000 ca:01 359002              /app/output.s
  24ed4000-24ef5000 rw-p 00000000 00:00 0                   [heap]
  739ee9c00000-739ee9c28000 r--p 00000000 ca:01 6456        /lib/x86_64-linux-gnu/libc.so.6
  739ee9c28000-739ee9db0000 r-xp 00028000 ca:01 6456        /lib/x86_64-linux-gnu/libc.so.6
```

**解读**：

1. **地址排序和教科书一致**：text `0x4010a0` < rodata `0x402211` < data `0x404048` < bss `0x40405c` < heap `0x24ed42a0` < stack `0x7ffe...`。三对变量（`g_init/s_init`、`g_zero/s_zero`）地址挨着，因为同段。
2. **`.rodata` 确实单独成段**：maps 前 5 行是**同一个可执行文件的 5 个映射**——`r--p`（ELF 头）、`r-xp`（text）、`r--p`（rodata）、`r--p`（eh_frame 之类）、`rw-p`（data+bss）。**注意第 3、4 行是两块独立的只读段**，这就是 `.rodata` 的实体。
3. **bss 与 data 共用同一个 `rw-p` 段**（`00404000-00405000`）：它们在文件里的 offset 相同、但内存里被撑开——`g_zero` 这类变量在磁盘上不占字节，加载时才清零分配。
4. **`s_expl_zero`（显式 `= 0`）地址在 bss 区**，证实"显式初始化为 0 也归 bss"。
5. **栈地址 `0x7ffe...` 在整个空间的最高处**，且向下增长——6.5 会实测方向。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 链接脚本（linker script）决定段布局，和这里 Linux 的默认布局不同源但同构。裸机移植时 `.data` 的"从 Flash 拷到 RAM"那步对应这里内核做的段映射 |
| HFT | `text` 段多进程共享同一份物理页：跑 N 个行情解析进程，代码段的内存只付一次 |
| HFT | 只读大表（行情符号表、参数表）放 `.rodata` 而非 data，既省 RAM（可共享）又天然防改写。但注意**跨进程共享 `.rodata` 是只读共享**，想改就别放这 |
| HFT | 对延迟敏感的进程常把关键数据结构从堆挪到**静态数组（data/bss）**——省掉 `malloc` 的不确定性，代价是启动时就占住地址空间（物理页仍按需才分，见 6.4） |

## 自测题

**题目 1：** `static int x = 0;` 落在 data 还是 bss？为什么？

<details>
<summary>参考答案</summary>

bss。C 标准要求静态存储期对象零初始化，编译器发现初值就是 0（或没写初值）时，就把它归到 bss——这样磁盘上的 ELF 不需要存这一串 0，内核在加载时统一清零即可。上面实测里 `s_expl_zero` 的地址与 `g_zero/s_zero` 同区，就是证据。

</details>

**题目 2：** 上面 maps 输出前 5 行都是同一个可执行文件的映射，为什么 text 那行是 `r-xp` 而 `r--p` 出现三次？

<details>
<summary>参考答案</summary>

同一条 ELF 被按"不同权限"拆成多个映射。第 1 行 `r--p` 是 ELF 头/程序头表；第 2 行 `r-xp` 是可执行的代码段（text）；第 3、4 行两块 `r--p` 是只读数据（`.rodata`、`.eh_frame` 等）；第 5 行 `rw-p` 是可读写数据（data + bss）。权限不同就必须分开映射——这也是"为什么改写字符串字面量会 SIGSEGV"的直接原因：那页是 `r--`。

</details>

**题目 3：** 既然 `malloc` 的内存"在堆上"，为什么实测里 `heap = 0x24ed42a0` 和 `start_brk` 附近不连续、反而离 libc 更近？

<details>
<summary>参考答案</summary>

因为 glibc 对大块分配（默认阈值 128 KB）不用 `brk` 抬堆顶，而是直接 `mmap` 一块匿名内存。`0x24ed42a0` 落在 `[heap]` 区间内说明这次是小块分配（走 brk），但它离 libc 的映射区比较近是因为这块堆本身是 mmap 分配的（现代内核在 `CONFIG_...` 下把 brk 也放在 mmap 区下方）。判据是看 maps：地址落在 `[heap]` 行内 = brk 堆；落在匿名 `rw-p` 无名字行 = mmap 出来的。Ch7 会实测这个阈值切换。

</details>
