# 6.8 非局部跳转：`setjmp` / `longjmp` 与 `volatile` 陷阱

> 源码核验：glibc 2.39 · `setjmp/setjmp.h:32`（`typedef struct __jmp_buf_tag jmp_buf[1]`）· `:41`（`__sigsetjmp`）· `setjmp/longjmp.c:29-41`（`val ?: 1`）· `sysdeps/x86_64/setjmp.S:31-33`（保存寄存器）
> 本章：[TLPI 第 06 章 — Processes](../README.md)
> - 上一节：[6.7 环境列表](./6.7-environment-list.md)
> - 下一节：[Ch7 内存分配](../../chapter-07-memory-allocation/notes)

## 本节讲什么

`goto` 只能在函数内跳；`setjmp` / `longjmp` 能**跨函数跳回来**。它常被当成"简易异常机制"用。这一节钉三件事：

1. **返回值的规矩**：`setjmp` 直接调用返回 0，`longjmp` 跳回来时返回你给的 `val`，但 **`val == 0` 会被强制改成 1**。
2. **`volatile` 陷阱**（本节的硬核）：`setjmp` 与 `longjmp` 之间被修改的**非 volatile 局部变量**，值可能被"回滚"——**实测确认**。
3. **它到底是什么**：`jmp_buf` 里存的是**一堆寄存器快照**，`longjmp` 是把它们恢复回去。

---

## 要点

### API

```c
#include <setjmp.h>
int  setjmp(jmp_buf env);            /* 直接调用返回 0；保存执行环境 */
void longjmp(jmp_buf env, int val);  /* 跳回 setjmp；表现为返回 val（0 -> 1） */
```

### 返回值的规矩

| 情况 | `setjmp` 的返回值 |
|------|------------------|
| 直接调用（第一次执行到） | **0** |
| `longjmp(env, 42)` 之后 | **42** |
| `longjmp(env, 0)` 之后 | **1**（0 被刻意避开，好让 0 专表"正常"） |

### `jmp_buf` 里存了什么

```c
/* glibc setjmp/setjmp.h —— 注意是个长度 1 的数组类型，所以传参时"自动退化成指针" */
typedef struct __jmp_buf_tag jmp_buf[1];                    /* :32 */

/* 内部实现只有一个函数，setjmp 与 sigsetjmp 都用它，靠 savemask 区分 */
extern int __sigsetjmp (struct __jmp_buf_tag __env[1], int __savemask);   /* :41 */
```

x86-64 上它保存的寄存器（`sysdeps/x86_64/setjmp.S:31` 起）：

```asm
ENTRY (__sigsetjmp)
	/* Save registers.  */
	movq %rbx, (JB_RBX*8)(%rdi)      # :33  rbx
	...                               #      rbp / r12-r15 / rsp / rip 依次保存
	jmp __sigjmp_save                 # :85  尾调用：按 savemask 决定存不存信号掩码
```

实测 `sizeof(jmp_buf) = 200` 字节 = **8 个 long（64 B，存放上面那批寄存器）+ `int __mask_was_saved`（4 B）+ 对齐 4 B + `__sigset_t __saved_mask`（128 B）**。

### ⭐ `longjmp` 与 `siglongjmp` 是同一个函数

```c
/* glibc setjmp/longjmp.c (2.39) */
void
__libc_siglongjmp (sigjmp_buf env, int val)                      /* :29 */
{
  _longjmp_unwind (env, val);                                    /* :32 */

  if (env[0].__mask_was_saved)                                   /* :34 */
    (void) __sigprocmask (SIG_SETMASK,
			  (sigset_t *) &env[0].__saved_mask,
			  (sigset_t *) NULL);            /* :36 只有 setjmp 时存过掩码才恢复 */

  __longjmp (env[0].__jmpbuf, val ?: 1);                         /* :41 ⭐ val==0 -> 1 */
}

weak_alias (__libc_siglongjmp, _longjmp)                         /* :50 */
weak_alias (__libc_siglongjmp, longjmp)                          /* :51 */
weak_alias (__libc_siglongjmp, siglongjmp)                       /* :52 */
```

两个结论直接来自源码：

- **`val == 0` 变成 1 就发生在 `:41` 的 `val ?: 1`**（GNU 扩展写法，等价 `val ? val : 1`）。
- **`longjmp` / `_longjmp` / `siglongjmp` 是同一个函数的三个别名**；是否恢复信号掩码**不由调用的名字决定**，而由**当初 `setjmp` 时 `savemask` 传的是不是 0**（`:34` 的 `__mask_was_saved`）决定。

### `volatile` 陷阱（本节最该记住的）

C 标准说：`setjmp` 与 `longjmp` 之间被修改的局部变量，**若它不是 `volatile`、且没有在别处取过地址，`longjmp` 之后的值是未定义的**。

原因很直白：这类变量常常**只活在寄存器里**，而 `longjmp` 是"把寄存器恢复到 `setjmp` 那一刻"——寄存器值被覆盖，变量自然"回滚"。

| 变量 | `-O2` 实测 | 结论 |
|------|-----------|------|
| `volatile int vol_var` | 200（正确） | volatile 强制走内存 |
| `int auto_var` | **100（回滚！）** | 只在寄存器里 → 被恢复覆盖 |
| `static int sta_var` | 200（正确） | 在 .data 段，不在寄存器 |

## 代码

完整程序见 [`../code/c6_8_setjmp.c`](../code/c6_8_setjmp.c)，三层调用链里出错、跳回 main，同时对比三种变量的命运。

```c
/* c6_8_setjmp.c — 6.8 setjmp/longjmp：跨函数跳转 + 非 volatile 局部变量被回滚
 * 编译对比: gcc -O0 与 gcc -O2 各跑一次，看 auto_var 的差异
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <setjmp.h>
#include <stdlib.h>

static jmp_buf env;

/* 深层调用：出错就跳回 main 的 setjmp 点 */
static void level3(int fail)
{
    if (fail) {
        printf("    [level3] 出错，longjmp(env, 42)\n");
        longjmp(env, 42);
    }
    printf("    [level3] 正常返回\n");
}
static void level2(int fail) { level3(fail); }
static void level1(int fail) { level2(fail); }

int main(void)
{
    /* jmp_buf 里到底存了什么：x86-64 glibc = 8 个 long(保存 rbx/rbp/r12-r15/rsp/rip)
     * + int __mask_was_saved + 128B __sigset_t __saved_mask */
    printf("sizeof(jmp_buf) = %zu B，sizeof(sigjmp_buf) = %zu B\n",
           sizeof(jmp_buf), sizeof(sigjmp_buf));

    /* 在 setjmp 与 longjmp 之间改动的局部变量：
     * auto_var   没有 volatile -> 可能只活在寄存器里 -> longjmp 后被「回滚」
     * vol_var    有 volatile   -> 强制走内存 -> 值一定是最新的
     */
    volatile int vol_var = 100;
    int auto_var = 100;
    static int sta_var = 100;              /* static 在 .data，不受影响 */

    int r = setjmp(env);
    if (r == 0) {
        printf("--- 第一次返回 0：正常路径 ---\n");
        level1(0);                          /* 正常 */
        printf("  改三个变量：100 -> 200\n");
        vol_var = auto_var = sta_var = 200;
        level1(1);                          /* 触发 longjmp */
        printf("  这行永远不执行\n");
    } else {
        printf("--- longjmp 回来，r = %d ---\n", r);
        printf("  volatile int vol_var = %d   (200 正确)\n", vol_var);
        printf("  int          auto_var= %d   (%s)\n", auto_var,
               auto_var == 200 ? "200 正确" : "被回滚成 100 ！");
        printf("  static int   sta_var = %d   (200 正确)\n", sta_var);
    }
    printf("集齐 setjmp：返回 0 表示直接调用，val==0 会被强制改成 1\n");

    /* 补一个 val==0 的演示 */
    if (setjmp(env) == 0) longjmp(env, 0);
    else printf("  longjmp(env, 0) 实际返回 1（0 被刻意避开）\n");
    return 0;
}
```

编译与运行（**两个优化级别都要跑**，对照才有意义）：

```bash
gcc -O2 -Wall -Wextra -o c6_8_setjmp_O2 c6_8_setjmp.c && ./c6_8_setjmp_O2
gcc -O0 -Wall -Wextra -o c6_8_setjmp_O0 c6_8_setjmp.c && ./c6_8_setjmp_O0
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
===== -O2 =====
sizeof(jmp_buf) = 200 B，sizeof(sigjmp_buf) = 200 B
--- 第一次返回 0：正常路径 ---
    [level3] 正常返回
  改三个变量：100 -> 200
    [level3] 出错，longjmp(env, 42)
--- longjmp 回来，r = 42 ---
  volatile int vol_var = 200   (200 正确)
  int          auto_var= 100   (被回滚成 100 ！)      ← ⭐ 陷阱现身
  static int   sta_var = 200   (200 正确)
  longjmp(env, 0) 实际返回 1（0 被刻意避开）

===== -O0 =====
sizeof(jmp_buf) = 200 B，sizeof(sigjmp_buf) = 200 B
--- 第一次返回 0：正常路径 ---
    [level3] 正常返回
  改三个变量：100 -> 200
    [level3] 出错，longjmp(env, 42)
--- longjmp 回来，r = 42 ---
  volatile int vol_var = 200   (200 正确)
  int          auto_var= 200   (200 正确)             ← -O0 下没回滚
  static int   sta_var = 200   (200 正确)
  longjmp(env, 0) 实际返回 1（0 被刻意避开）
```

**解读**：

1. **`-O2` 与 `-O0` 的差异是本节的核**：同一份源码，`-O2` 下 `auto_var` 回滚成 100，`-O0` 下是 200。差别就是**寄存器分配**——`-O0` 把每个局部变量都放栈上（天然"安全"），`-O2` 把它放进寄存器，`longjmp` 恢复寄存器时把它盖回旧值。
2. **`volatile` 和 `static` 都安全，但原因不同**：`volatile` 是**强制走内存**（编译器不许缓存到寄存器）；`static` 是**本来就住在 .data**，而 `longjmp` 只恢复寄存器、不动内存。别把两者当同一回事。
3. **`-O0` 下"没出问题"是假象**，不是"我的代码没问题"。这类 bug 只在开启优化后出现——**调 release 版才炸的典型**。
4. **`sizeof(jmp_buf) = 200`** 印证了源码结构：64 B 寄存器区 + 4 B `__mask_was_saved` + 4 B 对齐 + 128 B `__saved_mask` = 200。
5. **`longjmp(env, 0)` 返回 1**，与 `longjmp.c:41` 的 `val ?: 1` 对上——**源码级证据**，不是"书上这么说"。

⚠️ 本节只讲 `setjmp`/`longjmp`。**信号处理器里该用 `sigsetjmp`/`siglongjmp`**（要保存/恢复信号掩码），那属于 [Ch21 信号处理器](../../chapter-21-signal-handlers/notes) 的范围，限制比这里多得多。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 资源紧张的系统里 `setjmp/longjmp` 常被当"轻量异常"用（省掉 C++ 异常的开销）。但如上所述，**凡是跨 `setjmp` 改过的变量必须 `volatile`**，否则优化一开就出错——嵌入式常用 `-Os`，同样中招 |
| HFT | 热路径上**不要用** `setjmp/longjmp`：`jmp_buf` 有 200 B，保存/恢复 8 个寄存器 + 可能的 `sigprocmask` 系统调用（`mask_was_saved` 时），延迟比普通返回高一个量级 |
| HFT | 它真正的用武之地是**冷路径的错误跳出**：解析配置、初始化阶段用 `setjmp` 设一个"统一失败出口"，省掉层层返回错误码 |
| HFT | ⚠️ `longjmp` **不执行栈展开清理**：跳过的中间帧里的 `malloc` 不会被释放、持有的锁不会被释放、`atexit` 也不跑。在 C++ 里跨 `longjmp` 更是直接 UB（析构不执行） |

## 自测题

**题目 1：** `longjmp(env, 0)` 之后，`setjmp` 那行返回什么？

<details>
<summary>参考答案</summary>

返回 **1**。glibc 的实现是 `setjmp/longjmp.c:41` 的 `__longjmp(env[0].__jmpbuf, val ?: 1)`——`val` 为 0 时取 1。这是刻意设计：0 保留给"直接调用"这一情形，这样 `if (setjmp(env) == 0) { 正常 } else { 异常 }` 的惯用法才能工作。

</details>

**题目 2：** 为什么 `setjmp` 和 `longjmp` 之间改过的局部变量会被"回滚"？为什么加了 `volatile` 就好了？

<details>
<summary>参考答案</summary>

因为 `longjmp` 的本质是**恢复寄存器快照**（`sysdeps/x86_64/setjmp.S` 保存 rbx/rbp/r12-r15/rsp/rip）。如果某个局部变量在 `-O2` 下一直被放在寄存器里（没有被其他代码逼到栈上），恢复旧寄存器值就等于把它"改回"了 `setjmp` 那一刻的值。加 `volatile` 后编译器必须让它每次读写都真的落到内存，而 `longjmp` 不碰内存，所以值得以保留。实测对比：`-O2` 下 `auto_var` 变回 100，`-O0` 下是 200。

</details>

**题目 3：** `longjmp` 直接跳到别处，被跳过的那些栈帧里如果有 `malloc` 的内存和加过的锁，会怎样？

<details>
<summary>参考答案</summary>

不会被释放/解开。`longjmp` 只恢复寄存器（包括栈指针），不做任何"栈展开清理"——没有析构函数、没有 `atexit`、没有 RAII、没有自动解锁。所以被跳过的中间帧里 `malloc` 的内存泄漏、持有的 `pthread_mutex` 永久锁死。这也是为什么信号处理程序里用 `longjmp`（尤其 `_longjmp`）要极其小心，标准做法是只在里面做 `siglongjmp` 到安全点，且退出前不加锁、不分配。

</details>
