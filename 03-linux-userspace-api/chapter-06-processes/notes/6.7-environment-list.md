# 6.7 环境列表：`environ` 的读写与 `putenv` 的两个陷阱

> 源码核验：Linux v6.6 · `include/linux/mm_types.h:811`（`env_start/env_end`，与 `arg_start` 共用 `arg_lock:807`）· glibc 侧 `environ` 是 libc 维护的全局变量
> 本章：[TLPI 第 06 章 — Processes](../README.md)

## 本节讲什么

环境列表就是一组 `NAME=VALUE` 字符串，进程启动时由 `execve` 的第三个参数传进来，之后可以读写。这一节钉两件事：

1. **四件套 API 的语义差异**：`getenv` / `setenv` / `unsetenv` / `putenv`。
2. **`putenv` 的两个真实陷阱**——都实测出来了：传局部数组会留下**悬垂指针**；传自己的缓冲则**改缓冲环境跟着变**。

---

## 要点

### 三种访问方式

```c
extern char **environ;                    /* NAME=VALUE 数组，NULL 结尾 */
char *getenv(const char *name);           /* 查：返回指针，勿 free */

#include <stdlib.h>
int setenv(const char *name, const char *value, int overwrite);  /* 推荐 */
int unsetenv(const char *name);
int putenv(char *string);                 /* ⚠️ 见下面两个陷阱 */
int clearenv(void);                       /* 非 POSIX，慎用 */
```

| API | 是否复制字符串 | overwrite 语义 | 风险 |
|-----|--------------|---------------|------|
| `setenv` | **复制**（内部另分配） | `overwrite=0` 时**不覆盖**已有值 | 无 |
| `putenv` | **不复制，直接用你给的缓冲** | 总是替换（等价 overwrite=1） | ⚠️ 传局部/临时缓冲 → 悬垂 |
| `getenv` | — | — | 返回的指针**不要 `free`**；下次 `setenv` 后可能失效 |
| `unsetenv` | — | — | 无 |

### 继承与作用域

- 子进程**默认继承**父进程的环境（`fork` 复制 + `execve` 传递）。
- 进程内改环境**只影响自己和之后创建的子进程**，**改不到父进程 / shell 的环境**——这是进程隔离的必然结果，不是限制。
- `main` 的第三参 `envp` 是非标准扩展，**用 `environ`**。

### 内核对 environ 的记账

和 argv 完全对称：`mm_struct` 里 `env_start/env_end`（`mm_types.h:811`）记着 environ 字符串区的范围，与 `arg_start/arg_end` 共用 `arg_lock`（`:807`）。所以：

- `/proc/[pid]/environ` 读这段（需要 `ptrace` 权限，读别的进程时通常只有 root/同用户）；
- 修改环境**可能触发重新分配**那一段内存（glibc 视情况决定原地改还是搬家）。

## 代码

完整程序见 [`../code/c6_7_environ.c`](../code/c6_7_environ.c)，五段：查询、`setenv` 的 overwrite 语义、`putenv` 两个陷阱、遍历 environ。

```c
/* c6_7_environ.c — 6.7 环境变量：getenv/setenv/unsetenv/environ + putenv 两个陷阱
 * 编译: gcc -O2 -Wall -Wextra -o c6_7_environ c6_7_environ.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

extern char **environ;

static void show(const char *name)
{
    char *v = getenv(name);
    printf("  getenv(\"%s\") = %s\n", name, v ? v : "(NULL)");
}

int main(void)
{
    printf("=== A. 只读查询 ===\n");
    show("PATH");
    show("NO_SUCH_VAR");

    printf("=== B. setenv / unsetenv（推荐路径）===\n");
    setenv("MY_VAR", "hello", 0);
    show("MY_VAR");
    setenv("MY_VAR", "world", 0);      /* overwrite=0 -> 不覆盖 */
    show("MY_VAR");
    setenv("MY_VAR", "world", 1);      /* overwrite=1 -> 覆盖 */
    show("MY_VAR");
    unsetenv("MY_VAR");
    show("MY_VAR");

    printf("=== C. putenv 陷阱一：传入的是局部数组（栈上）===\n");
    {
        char localbuf[32];
        strcpy(localbuf, "PITFALL=local-stack-buffer");
        putenv(localbuf);              /* 内核环境区现在指向这个栈数组 */
        printf("  函数返回前: %s\n", getenv("PITFALL"));
    }
    /* localbuf 已随作用域失效 —— 这里读它是 UB（演示只打印指针是否还在） */
    printf("  块已退出，getenv(\"PITFALL\") 仍能命中(悬垂): %s\n",
           getenv("PITFALL") ? "是（危险！）" : "否");

    printf("=== D. putenv 陷阱二：改的是调用者自己的缓冲 ===\n");
    static char same[] = "MUTABLE=aaa";
    putenv(same);
    show("MUTABLE");
    strcpy(same, "MUTABLE=bbb");       /* 直接改那块内存 -> 环境跟着变 */
    show("MUTABLE");

    printf("=== E. 遍历 environ ===\n");
    int n = 0;
    for (char **e = environ; *e; e++) n++;
    printf("  环境变量共 %d 条，前 3 条:\n", n);
    for (int i = 0; i < 3 && environ[i]; i++)
        printf("    %s\n", environ[i]);
    return 0;
}
```

编译与运行：

```bash
gcc -O2 -Wall -Wextra -o c6_7_environ c6_7_environ.c && ./c6_7_environ
```

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

```text
=== A. 只读查询 ===
  getenv("PATH") =
  getenv("NO_SUCH_VAR") = (NULL)
=== B. setenv / unsetenv（推荐路径）===
  getenv("MY_VAR") = hello
  getenv("MY_VAR") = hello          ← overwrite=0，没被覆盖成 world
  getenv("MY_VAR") = world          ← overwrite=1，覆盖了
  getenv("MY_VAR") = (NULL)         ← unsetenv 生效
=== C. putenv 陷阱一：传入的是局部数组（栈上）===
  函数返回前: local-stack-buffer
  块已退出，getenv("PITFALL") 仍能命中(悬垂): 是（危险！）
=== D. putenv 陷阱二：改的是调用者自己的缓冲 ===
  getenv("MUTABLE") = aaa
  getenv("MUTABLE") = bbb           ← 只是改了 same[] 的内容，环境跟着变
=== E. 遍历 environ ===
  环境变量共 9 条，前 3 条:
    LD_LIBRARY_PATH=/opt/compiler-explorer/gcc-13.3.0/lib:/opt/compiler-explorer/gcc-13.3.0/lib32:/opt/compiler-explorer/gcc-13.3.0/lib64
    ASAN_OPTIONS=color=always
    UBSAN_OPTIONS=color=always
```

**解读**：

1. **B 段是 `overwrite` 语义的标准演示**：`setenv(..., 0)` 两次后值仍是 `hello`，改成 `1` 才变 `world`。注意"第一次设置"不需要覆盖，所以先 `0` 能设进去——**常见错答是"overwrite=0 就什么都不做"，错的**。
2. **C 段是 `putenv` 最危险的地方**：`localbuf` 是**栈上数组**，块退出后它的内存随时会被后续调用覆盖。但 `getenv("PITFALL")` **仍然能命中**——环境区里存的是一个**悬垂指针**。这次侥幸读到的还是旧内容，换台机器/换个编译选项就可能读到垃圾。所以 **`putenv` 的参数必须是静态/全局/堆上且永不释放的内存**，否则用 `setenv`。
3. **D 段是 `putenv` 的另一面**：`same[]` 是 `static`（在 data 段），生命周期没问题；但它**就是环境区里那个字符串本体**——所以 `strcpy(same, "MUTABLE=bbb")` 直接改了环境变量的值，完全绕过任何 API。这是 `putenv` 的设计（不复制）的必然结果。
4. **`getenv("PATH")` 返回的是空字符串，不是 `NULL`** —— 说明 CE 环境里 `PATH=` 这条**存在但值为空**。同一段里 `NO_SUCH_VAR` 返回 `(NULL)`，两者对比正好说明「存在但为空」与「不存在」是**两种状态**。这本身是个好例子：**环境变量是进程启动时注入的，不是一个全局常量**；写代码时别把 `""` 和 `NULL` 混为一谈。
5. **末尾 `environ` 里那 9 条**是 CE 沙箱注入的（`LD_LIBRARY_PATH` 指向 gcc 13.3 的库目录，`ASAN_OPTIONS`/`UBSAN_OPTIONS` 是 sanitizer 配置）——再次印证环境由调用者决定。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | BusyBox/init 脚本用环境变量传配置很常见，但**大多数嵌入式 init 的环境极其简陋**（可能连 `PATH` 都没有）。依赖某个变量前先判空，别假设有 |
| HFT | `LD_PRELOAD` 是环境变量，能劫持任意函数——**线上进程必须校验/清空环境**（或至少不要在热路径进程里依赖它）。同理，`LD_LIBRARY_PATH` 被污染会导致加载错版本的库 |
| HFT | **别用 `putenv` 传临时缓冲**（上面 C 段实测）；配置传递用 `setenv` 更安全。热路径上更不要反复 `setenv/unsetenv`——那会触发内存重分配 |
| HFT | 密钥/凭据不要放环境变量整体传给子进程：`/proc/[pid]/environ` 与 `/proc/[pid]/cmdline` 一样可被同机进程读（受权限控制但不绝对） |

## 自测题

**题目 1：** `setenv("X", "1", 0)` 在一个已经设了 `X=0` 的进程里做了什么？

<details>
<summary>参考答案</summary>

什么都不做——`overwrite=0` 表示"已存在就不要覆盖"，此时 `X` 仍为 `0`。注意如果 `X` **不存在**，`overwrite=0` 也会正常设进去（"不覆盖"针对的是已存在的情形）。上面实测 B 段第一次 `setenv(..., 0)` 成功设入 `hello`、第二次同类调用仍是 `hello`，就是这个语义。

</details>

**题目 2：** 为什么 `putenv(localbuf)`（局部数组）是危险的？实测里它"看起来正常"说明了什么？

<details>
<summary>参考答案</summary>

`putenv` **不复制字符串**，只把指针塞进环境数组。`localbuf` 是栈上数组，函数/块退出后那片内存失效，环境区就留下一个悬垂指针，后续任何栈使用都可能覆盖它。实测里 `getenv("PITFALL")` 仍能读到旧值，只是**运气**——那片内存暂时没被复用。这类 bug 的可怕之处正是"常常看起来正常"，在别的编译选项或调用序列下才炸。

</details>

**题目 3：** 在进程里 `setenv("PATH", "/tmp")`，会影响到启动它的那个 shell 吗？

<details>
<summary>参考答案</summary>

不会。环境变量是**进程私有**的：`fork` 时复制、`execve` 时传递，改动只沿"父 → 子"单向流动，无法反向影响父进程或外层 shell。想让 shell 看到，必须在 shell 自己的上下文里改（或由子进程把值打印出来让 shell `eval`）。

</details>
