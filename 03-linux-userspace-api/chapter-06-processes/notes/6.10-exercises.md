### 练习 1：打印进程信息

写一个程序，打印自己的 **PID、PPID、命令行参数、环境变量条数**。

<details>
<summary>参考答案（完整可编译）</summary>

```c
/* ex6_1.c — 打印 PID/PPID/argv/environ
 * 编译: gcc -O2 -Wall -Wextra -o ex6_1 ex6_1.c */
#include <stdio.h>
#include <unistd.h>

extern char **environ;

int main(int argc, char *argv[])
{
    printf("PID=%d PPID=%d\n", (int)getpid(), (int)getppid());

    printf("argc=%d\n", argc);
    for (int i = 0; i <= argc; i++)                 /* <= 顺便看到 NULL 哨兵 */
        printf("  argv[%d] = %s\n", i, i == argc ? "(NULL)" : argv[i]);

    int n = 0;
    for (char **p = environ; *p; p++) n++;
    printf("environ: %d 条\n", n);
    return 0;
}
```

实测输出（CE 复核，gcc 13.3）：

```text
PID=2 PPID=1
argc=1
  argv[0] = ./output.s
  argv[1] = (NULL)
environ: 7 条
```

（`environ` 条数每次跑都可能不同 —— 由调用者的环境决定；这里记的是本次 CE 沙箱里的值。）

**三个要注意的点**：

1. TLPI 书上的版本用了 `tlpi_hdr.h`（书配套头文件），**本机/沙箱可能没有**，所以这里换成标准头 —— 练习代码要能独立编译，别依赖书里的私有头。
2. 循环写成 `i <= argc` 就能顺带打印出 `argv[argc]` 这个 NULL 哨兵，比只循环到 `argc-1` 更有教学价值。
3. `argc` 和 `environ` 条数都**取决于调用者**：直接跑是 `argc=1`，带参数跑就变；`environ` 条数随环境变化。同一份二进制在不同环境输出不同。

</details>

### 练习 2：用 `setjmp`/`longjmp` 做错误恢复

主函数设置跳转点；调用链中任意层出错就 `longjmp` 跳回，并带出错误码。

<details>
<summary>参考答案（完整可编译）</summary>

```c
/* ex6_2.c — setjmp/longjmp 错误恢复
 * 编译: gcc -O2 -Wall -Wextra -o ex6_2 ex6_2.c */
#include <stdio.h>
#include <setjmp.h>

static jmp_buf err_env;
static int err_code;

void level3(int fail)
{
    if (fail) {
        err_code = 42;
        longjmp(err_env, err_code);        /* 直接从第 3 层跳回 main */
    }
    printf("level3: success\n");
}
void level2(int fail) { level3(fail); }
void level1(int fail) { level2(fail); }

int main(void)
{
    int r = setjmp(err_env);
    if (r == 0) {
        printf("第一次调用（正常路径）\n");
        level1(0);                         /* 不出错 */
        level1(1);                         /* 出错 -> longjmp */
        printf("这行不会执行\n");
    } else {
        printf("错误恢复：err_code=%d\n", r);
    }
    return 0;
}
```

实测输出（CE 复核，gcc 13.3）：

```text
第一次调用（正常路径）
level3: success
错误恢复：err_code=42
```

⚠️ 注意 `err_code` 必须声明为 **`static`（或 `volatile`）**：它在 `longjmp` 之后要被读，而它是**非局部**的普通变量时值可能不确定（见 6.8 的 `volatile` 陷阱）。这里用 `static` 让它住在 `.data`，天然安全。

</details>

### 练习 3：信号处理器里的 `longjmp`

解释为什么在信号处理器中调用 `longjmp` 是危险的，如何安全替代？

<details>
<summary>参考答案</summary>

**危险性**（三条，与 6.8 结尾的"不清理"是同一根源）：

1. **信号掩码不恢复**：普通的 `setjmp`/`longjmp` 不保存/恢复信号掩码（glibc 里靠 `__mask_was_saved` 决定，而 `setjmp` 设的是 0）。处理器执行期间内核自动屏蔽了当前信号，`longjmp` 跳出来不会解除，导致该信号永久收不到。
2. **跳过中间状态的收尾**：若信号打断的是 `malloc` / `printf` 这类非 async-signal-safe 函数，`longjmp` 会跳过它们的收尾，造成堆结构损坏或流缓冲乱套。
3. **目标栈帧可能已失效**：如果 `setjmp` 所在函数在信号到来前已经返回，那块栈已被复用，跳回去就是往垃圾里执行。

**安全替代**：

```c
#include <signal.h>
#include <setjmp.h>

static sigjmp_buf sig_env;

static void handler(int sig)
{
    (void)sig;
    siglongjmp(sig_env, 1);        /* 保存/恢复信号掩码 */
}

int main(void)
{
    if (sigsetjmp(sig_env, 1) == 0) {   /* 第二个参数 1 = 保存掩码 */
        signal(SIGINT, handler);
        /* 危险操作… */
    } else {
        /* 恢复点 */
    }
    return 0;
}
```

要点：`sigsetjmp(buf, 1)` 的第二个参数为 1 才保存信号掩码（glibc 源码里就是传给 `__sigsetjmp` 的 `savemask`，见 `setjmp/setjmp.h:41`），`siglongjmp` 会据此恢复。**即便如此**，处理器里仍然只应做 async-signal-safe 的操作。完整限制见 [Ch21 信号处理器](../../chapter-21-signal-handlers/notes)。

</details>

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 嵌入式异常恢复常借 `setjmp` 跳过故障模块，但**必须记得 `volatile`**（嵌入式常开 `-Os`，一样会回滚） |
| HFT | 进程信息（PID/PPID/环境）是监控面板的基础数据；但**热路径别查**——`/proc` 读取是系统调用 + 格式化开销 |
| HFT | `setjmp` 统一失败出口只用于**初始化/配置阶段**；交易循环里禁用（不可预测的跳转会破坏状态机，且跳过锁与内存释放） |
