## 环境变量 API 速查

| 函数 | 功能 | 是否复制字符串 | 注意 |
|------|------|--------------|------|
| `getenv(name)` | 获取 | — | 返回指针，**不要 `free`**；值为空串 ≠ 不存在 |
| `setenv(name, val, overwrite)` | 设置 | ✅ 复制 | `overwrite=0` 且已存在时不覆盖 |
| `putenv("NAME=VALUE")` | 设置/修改 | ❌ **不复制** | 参数必须长期有效，否则悬垂 |
| `unsetenv(name)` | 删除 | — | — |
| `clearenv()` | 清空 | — | 非 POSIX 扩展 |

## setjmp / longjmp 语义速查

```c
jmp_buf env;
int r = setjmp(env);     /* 直接调用返回 0；longjmp 后返回 val（0 强制变 1） */
if (r == 0) {
    /* 正常路径；出错时调 longjmp(env, code) */
} else {
    /* 错误恢复路径，r 就是那个 code */
}
```

| 注意点 | 说明 |
|--------|------|
| **寄存器变量** | 跨 `setjmp`/`longjmp` 改过的局部变量必须 `volatile`，否则 `-O2` 下可能回滚 |
| **不清理** | `longjmp` 不释放内存、不解锁、不跑析构 |
| **信号场景** | 处理器里要用 `sigsetjmp(buf, 1)` / `siglongjmp`。注意：`longjmp` / `_longjmp` / `siglongjmp` **是同一个函数的三个别名**（`longjmp.c:50-52`），**是否恢复信号掩码不由名字决定**，而由 `sigsetjmp` 的第二个参数是否非 0 决定（`:34` 看 `__mask_was_saved`）。详见 [6.8](./6.8-setjmp-longjmp.md) |

## HFT / 嵌入式关联

- **进程隔离**：HFT 常把行情 / 策略 / 风控拆成**独立进程**——一方越界或崩溃不拖累另一方，代价是只能走共享内存或 socket 通信。
- **地址空间**：`text` 段只读共享（多进程只付一份内存）；只读大表放 `.rodata` 省 RAM 又防改写。
- **懒分配**：`malloc` 不付物理页、首写才付（6.4 实测）。热路径要 `mlockall` + 预热，把缺页毛刺挤到开盘前。
- **栈**：272 B/帧（6.5 实测）意味着"递归处理大数组"在 8 MB 栈上撑不了几万层；嵌入式栈更小（几十 KB），所以嵌入式规范普遍禁递归。
- **环境变量**：HFT 用 `LD_PRELOAD` 做注入调试，但线上必须防污染；密钥别放 `argv` / `environ`（`/proc` 可读）。
- **`setjmp`**：只适合冷路径的"统一失败出口"；热路径别用（200 B 的 `jmp_buf` + 寄存器保存开销）。

## 自测题

**题目 1：** `setjmp` 返回值什么时候是 0？什么时候不是？

<details>
<summary>参考答案</summary>

直接调用 `setjmp(env)` 时返回 0（第一次执行到这一行）。后续任意时刻调用 `longjmp(env, val)`，执行流跳回 `setjmp` 的位置，此时它返回 `val`——但如果 `val` 是 0，会被强制改成 **1**（glibc 源码 `setjmp/longjmp.c:41` 的 `val ?: 1`）。所以 0 永远只表示"直接调用"。

</details>

**题目 2：** 为什么在信号处理器中用 `longjmp` 是危险的？

<details>
<summary>参考答案</summary>

三点：① **信号掩码不恢复**——`longjmp`（对应 `setjmp`，`savemask=0`）不会恢复掩码，处理器执行期间被自动屏蔽的信号会一直保持屏蔽；② **可能跳进/跳出不安全的中间状态**——如果信号打断了 `malloc`，`longjmp` 跳过它的收尾会造成堆损坏；③ **栈帧可能已失效**——目标 `setjmp` 所在函数若已返回，那块栈已被复用。正确做法是用 `sigsetjmp`/`siglongjmp`（它们保存/恢复信号掩码），并严格限制处理器里只调用 async-signal-safe 函数。

</details>

**题目 3：** `getenv` 返回的指针可以直接改吗？

<details>
<summary>参考答案</summary>

技术上是本进程的内存，改了就相当于改了该环境变量；但**不应该**这么做——它是环境区里的字符串本体，长度一变就破坏结构，正确做法用 `setenv` / `putenv`。另外两点：返回的指针**不要 `free`**（不属于你），且**下次 `setenv`/`putenv` 之后可能失效**（内部可能重新分配整个环境数组）。

</details>
