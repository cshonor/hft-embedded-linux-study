章节目标

掌握 handler 设计的两条黄金法则（只设标志 + 只调异步信号安全函数）；理解 volatile sig_atomic_t 两个限定符的各自作用；能用 sigaltstack + SA_ONSTACK 处理栈溢出崩溃；理解 SA_SIGINFO 与 siginfo_t 的 union 语义；正确处理 EINTR 与 SA_RESTART 的边界。

易错清单

  1. sa_mask 叠加，不替换；退出即撤（由 sigreturn 自动恢复）
  2. SA_NODEFER → 允许自我重入，易递归
  3. EINTR 合法，别当致命；SA_RESTART 非万能（带超时调用仍返回 EINTR）
  4. 标志用 volatile sig_atomic_t——两个限定符缺一不可
  5. handler 禁 printf/malloc/exit
  6. 实时信号 + sigqueue 需 SA_SIGINFO 才拿得到 si_value
  7. 多线程：信号交给未阻塞该信号的某线程执行，不可预测
  8. siginfo_t 是 union——只读当前信号匹配的有效字段
  9. close() 返回 EINTR 时 fd 已关闭，不要重试
  10. handler 里要保护并恢复 errno

练习

  1. sigaction + sa_mask
  2. 开关 SA_RESTART 看 read/EINTR
  3. SA_SIGINFO 打印发送者 pid
  4. sig_atomic_t 主循环范式
  5. SIGCHLD 循环 waitpid

背诵卡

# 要点
1 用 sigaction，不用 signal
2 handler 期间：自动阻本信号 + sa_mask
3 只设 volatile sig_atomic_t；禁非 async-safe
4 处理 EINTR；SA_RESTART 非万能
5 SIGCHLD：循环 WNOHANG 或 SA_NOCLDWAIT
6 SA_SIGINFO 才拿得到 siginfo_t / 队列数据

代码示例

#include <stdio.h>
#include <signal.h>
#include <string.h>
#include <unistd.h>

/* Ch21 信号处理器 — sigaction（替代可移植性差的 signal）。
 * 演示 sigaction 注册 + 信号信息获取。
 * 编译: gcc -o ch21_demo ch21_demo.c */

static volatile sig_atomic_t count = 0;

void handler(int sig, siginfo_t *info, void *ctx) {
    count++;
    /* 注意: printf 不是异步信号安全函数，这里仅做演示 */
    const char *msg = "caught SIGINT\n";
    write(STDOUT_FILENO, msg, strlen(msg));
}

int main(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = handler;
    sa.sa_flags = SA_SIGINFO;
    sigemptyset(&sa.sa_mask);

    /* sigaction 比 signal 更可移植、更强大 */
    if (sigaction(SIGINT, &sa, NULL) < 0) {
        perror("sigaction");
        return 1;
    }

    printf("Press Ctrl+C to test (will catch 3 times then exit)\n");
    printf("Or run: kill -INT %d\n", (int)getpid());

    while (count < 3) {
        pause();  /* 等待信号 */
    }
    printf("Caught %d signals, exiting.\n", count);
    return 0;
}

21.1

设计信号处理器

源码核验：Linux v6.6 · kernel/signal.c（get_signal:2660 · signal_delivered:2915）· include/linux/signal.h 本章：TLPI 第 21 章 — Signals: Signal Handlers - 上一节：Ch20.13 sigaction() - 下一节：21.2 从信号处理器终止进程

本节讲什么

  1. 信号处理器设计的两条黄金法则——为什么「越简单越好」不是建议而是必需
  2. volatile sig_atomic_t 为什么必须两个限定符同时用——各自解决什么问题
  3. 什么是异步信号安全函数，以及 handler 与主流程交换数据的正确模式

一、为什么 handler 难写

回顾 Ch20.4 的核心事实：

handler 不是新线程——它在被打断线程自己的栈上执行，与被中断的代码共享全部状态。

这带来三个根本困难：

困难 说明
随时插入 主流程可能在任意指令边界被打断，包括"操作做到一半"的时刻
共享状态 handler 与主流程读写同一批全局变量、堆、栈，天然是数据竞争
锁不可靠 handler 与被中断代码在同一线程，加锁会导致自我死锁（锁不会被让出） 
   主流程                          handler
   ───────                         ───────
   malloc()
   ├─ 获取堆锁
   ├─ 正在修改空闲链表
   │                      ← 信号递送
   │                         malloc()
   │                         └─ 尝试获取堆锁 → 同一线程重入 → ❌ 死锁

结论：handler 里能做的事非常有限。这不是编码风格建议，而是信号机制的本质约束。

二、两条黄金法则

法则 1：handler 只做最小动作——通常是「设置一个标志」

static volatile sig_atomic_t got_sigint = 0;

static void handler(int sig)
{
    got_sigint = 1;          /* 就这一行，最安全 */
}

/* 主循环里检查标志并做真正的处理 */
for (;;) {
    if (got_sigint) {
        got_sigint = 0;
        do_shutdown();       /* 这里可以随意调用 printf/malloc/... */
    }
    do_work();
}

这是最推荐的模式：把复杂逻辑移回主流程，handler 只留下一个原子的"通知"。

法则 2：handler 里只调用异步信号安全函数

异步信号安全（async-signal-safe）函数 = 可以安全地在 handler 里调用的函数。判据：

  • 不持有锁（或持有的锁不会与主流程冲突）
  • 不使用静态/全局缓冲区（或使用时不会被重入破坏）
  • 不依赖被中断代码的中间状态
✅ 安全（可直接用） ❌ 不安全（禁止）
write()、read() printf()、fprintf()、sprintf()（stdio 锁）
_exit()、_Exit() exit()（flush stdio + atexit）
kill()、raise()、sigaction()、sigprocmask() malloc()、free()、calloc()、realloc()（堆锁）
给 volatile sig_atomic_t 赋值 strtok()、gmtime()、localtime()（静态缓冲）
strlen()、memcpy()、memset() 任何 pthread_* 函数
snprintf()（实践中常用，但非 POSIX 保证） syslog()、fopen()、fclose()

权威清单：man 7 signal-safety 给出完整的异步信号安全函数列表（POSIX + Linux 扩展）。写代码前应当查阅。

判断原则：如果一个函数可能加锁或分配内存，就假定它不安全。

三、volatile sig_atomic_t：两个限定符各解决一个问题

handler 与主流程共享变量的标准写法：

static volatile sig_atomic_t flag = 0;

为什么两个限定符缺一不可？

volatile —— 防止编译器优化

static sig_atomic_t flag = 0;      /* ❌ 少了 volatile */

while (!flag) {                     /* 编译器认为 flag 在本循环里没被改过 */
    do_work();                      /* → 优化成：读一次到寄存器，然后死循环 */
}

编译器看不见 handler（它是被内核调用的，不在控制流里），因此会认为 flag 在主循环中不会改变，把它缓存到寄存器——主流程永远看不到 handler 写入的新值。

volatile 告诉编译器：这个变量可能被你不知道的方式修改，每次都必须从内存重新读取。

sig_atomic_t —— 保证读写原子性

static volatile long long counter = 0;    /* ❌ 8 字节，非原子 */

void handler(int sig) { counter++; }      /* 读-改-写，可能被信号打断 */

如果变量的操作不是原子的（如 64 位 long long 在 32 位系统上，或 counter++ 这种读-改-写），信号可能在操作中间插入，导致半写状态：

   counter = 0x00000000FFFFFFFF
   handler 写入高 32 位 → 0x00000001FFFFFFFF
                          ↑ 此时主流程读取 → 得到"半新半旧"的垃圾值
   再写入低 32 位

sig_atomic_t 是 POSIX 保证读写具有原子性的整数类型（Linux 上通常是 int），单次读写不会被信号打断。

组合效果

限定符 解决的问题 不用的后果
volatile 编译器优化（值被缓存到寄存器） 主流程永远看不到 handler 的修改
sig_atomic_t 非原子操作（半写状态） 主流程读到半新半旧的垃圾值

注意：volatile sig_atomic_t 只保证单次读写的原子性，不保证 flag++ 这类读-改-写的原子性。需要计数时，应让 handler 只做 flag = 1（单次写），或用其他 IPC 机制。

四、与主流程交换数据的正确模式

handler 里只能设标志，那需要传递更多信息怎么办？

模式 做法 适用
标志变量 volatile sig_atomic_t 只需"有没有发生"
无锁环形队列 handler 写，主流程读（SPSC） 需传递多条记录，且要求零锁
eventfd handler 里 write(efd, &one, 8)，主流程 epoll 监听 需计数、需接入事件循环
self-pipe handler 写管道一字节，主流程 read 经典技巧，可移植
signalfd 不用 handler，直接 read() 信号 最干净，见 Ch22.11
sigwaitinfo 不用 handler，同步取 多线程专用线程模型，见 Ch22.10

self-pipe 技巧（经典可移植方案）

static int pipe_fd[2];

static void handler(int sig)
{
    char c = (char)sig;
    write(pipe_fd[1], &c, 1);       /* write 是 async-signal-safe */
}

/* 主循环用 select/poll/epoll 监听 pipe_fd[0] */

把信号变成一个字节流事件，天然接入 I/O 多路复用。HFT 与网络服务广泛使用。

更现代：signalfd

sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, NULL);      /* ① 必须阻塞，否则走 handler */

int sfd = signalfd(-1, &mask, SFD_NONBLOCK);   /* ② 信号变 fd */
/* ③ 加入 epoll，与业务 socket 一起等待 */

优势：完全没有 handler → 没有异步信号安全问题 → 处理代码里可随意 printf/malloc。这是 Linux 上最推荐的方案，详见 Ch22.11。

五、其他设计要点

要点 说明
保护 errno handler 若调用了可能修改 errno 的函数，进入时保存、返回时恢复
不要做浮点运算 浮点寄存器状态在信号递送时的保存/恢复是架构相关的，handler 里用浮点可能破坏主流程的 FPU 状态
不要 longjmp 出去 sigsetjmp/siglongjmp 是特化版本，普通 longjmp 会不恢复信号掩码，造成掩码泄漏
注意重入 默认情况下内核已自动阻塞同号信号（Ch20.4），但不同信号仍可嵌套——用 sa_mask 屏蔽相关信号 
/* 保护 errno 的标准写法 */
void handler(int sig)
{
    int saved_errno = errno;        /* 保存 */
    /* ... 处理（可能调用修改 errno 的函数）... */
    errno = saved_errno;            /* 恢复 */
}

HFT / 嵌入式关联

路线 要点
嵌入式 handler 必须极简——嵌入式线程栈小（8KB~64KB），复杂 handler 易溢出；且嵌入式常无调试器，handler 里的 bug 极难定位。对 SIGSEGV 务必配 SA_ONSTACK 备用栈（21.3）。诊断信息用 write() 直写 fd，绝不用 printf
HFT handler 会异步抢占关键路径，是延迟毛刺的经典来源。HFT 的正确策略是消灭 handler：关键路径全程屏蔽无关信号，控制信号走 signalfd 进事件循环，让"信号处理"变成同步的 read()。若必须保留 handler，则严格遵循「只设 volatile sig_atomic_t 标志」这一条

代码示例：从危险到安全的三种写法

/* handlerdesign.c —— 对比危险写法与安全写法
 * 编译: gcc -D_GNU_SOURCE -o handlerdesign handlerdesign.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

/* ────── 写法 A（❌ 危险）：handler 里做复杂工作 ────── */
static void bad_handler(int sig)
{
    printf("caught %d\n", sig);         /* ❌ printf 非 async-signal-safe */
    char *buf = malloc(64);             /* ❌ malloc 有堆锁 */
    if (buf) { snprintf(buf, 64, "sig=%d", sig); free(buf); }
    /* 可能死锁、破坏堆、死循环 */
}

/* ────── 写法 B（✅ 正确）：只设标志 + 保护 errno ────── */
static volatile sig_atomic_t got_signal = 0;
static volatile sig_atomic_t last_signo = 0;

static void good_handler(int sig)
{
    int saved_errno = errno;            /* ① 保护 errno */
    got_signal = 1;                     /* ② 只做原子赋值 */
    last_signo = sig;
    errno = saved_errno;                /* ③ 恢复 */
}

/* ────── 写法 C（✅ 更好）：self-pipe，可接入事件循环 ────── */
static int sp[2];                       /* self-pipe */
static void pipe_handler(int sig)
{
    int saved_errno = errno;
    unsigned char c = (unsigned char)sig;
    write(sp[1], &c, 1);                /* write 是 async-signal-safe */
    errno = saved_errno;
}

int main(int argc, char **argv)
{
    int mode = (argc > 1) ? atoi(argv[1]) : 2;   /* 默认用写法 B */

    if (mode == 3) {
        if (pipe(sp) == -1) { perror("pipe"); return 1; }
    }

    struct sigaction sa = {0};
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = (mode == 1) ? bad_handler
                  : (mode == 2) ? good_handler
                                : pipe_handler;
    sigaction(SIGUSR1, &sa, NULL);

    printf("模式 %d: %s\n", mode,
           mode == 1 ? "危险（printf+malloc）"
         : mode == 2 ? "安全（标志变量）"
                     : "更安全（self-pipe）");
    printf("PID=%d，请执行: kill -USR1 %d\n", getpid(), getpid());

    if (mode == 3) {
        /* 用 read 阻塞等待 pipe —— 等价于等待信号 */
        unsigned char c;
        ssize_t n = read(sp[0], &c, 1);
        if (n == 1) printf("通过 pipe 收到信号 %d\n", c);
    } else {
        /* 主循环轮询标志（真实场景应用 sigsuspend/ppoll 而非忙等） */
        while (!got_signal) {
            usleep(100000);             /* 演示用；生产代码用 sigsuspend */
        }
        printf("收到信号 %d\n", (int)last_signo);
    }
    return 0;
}

自测题

问 1：为什么 volatile 和 sig_atomic_t 两个限定符缺一不可？

两者解决完全不同的问题：

volatile —— 防止编译器优化掉内存读取

static sig_atomic_t flag = 0;       /* 少了 volatile */
while (!flag) { do_work(); }        /* 编译器：flag 在本循环没被改 → 缓存到寄存器 → 死循环 */

编译器看不见 handler（它由内核调用，不在程序控制流里），因此认为 flag 不会变，把它优化进寄存器。主流程永远看不到 handler 写的新值。

sig_atomic_t —— 保证读写是原子的

static volatile long long counter = 0;    /* 8 字节，非原子 */
void handler(int sig) { counter++; }      /* 读-改-写，会被打断 */

若变量的读写不是原子操作（如 32 位系统上的 64 位整数），信号可能在操作中间插入：

counter = 0x00000000FFFFFFFF
handler 写高 32 位 → 0x00000001FFFFFFFF
                      ↑ 主流程此时读取 → 半新半旧的垃圾值
再写低 32 位
限定符 解决 缺少的后果
volatile 编译器缓存优化 永远看不到修改
sig_atomic_t 非原子读写 读到半新半旧的垃圾值

注意：volatile sig_atomic_t 只保证单次读写原子，不保证 flag++（读-改-写）原子。需要计数请换机制（eventfd / signalfd / 无锁队列）。

问 2：handler 里为什么加锁解决不了数据竞争？

因为 handler 不是新线程——它在被打断的同一个线程上执行。

同一线程重入同一把非递归互斥锁，结果是死锁（不是等待）：

主流程                             handler
───────                            ───────
pthread_mutex_lock(&m)  ✅ 获得
├─ 正在修改共享数据
│                          ← 信号递送
│                             pthread_mutex_lock(&m)
│                             └─ 锁的 owner 就是当前线程
│                                └─ 非递归锁 → ❌ 死锁
│                                   （不会"让出"，因为根本没别的线程持有它）

即使用递归锁（recursive mutex）也不对：递归锁允许重入，于是 handler 会看到被修改到一半的共享数据——数据结构处于不一致状态，读写都会出错。

所以正确的思路不是"加锁"，而是"不共享复杂状态"：

  1. handler 只写一个 volatile sig_atomic_t（单次原子写，无需锁）
  2. 复杂数据的处理全部移回主流程
  3. 或者用专门设计的无锁 SPSC 队列（handler 只做生产者，主流程只做消费者）
  4. 最彻底：用 signalfd / sigwaitinfo，完全不用 handler
问 3：handler 里调用 printf 一定会出问题吗？

不保证出错，但也不保证安全——这是最危险的一类 bug：大部分时候能跑，偶尔死锁或输出乱码。

出错条件：主流程恰好在 printf 执行中（持有 stdio 锁）时信号递送，handler 再次 printf → 同一线程重入 stdio 锁 → 死锁。

由于窗口很窄，这类 bug 可能：

  • 开发环境跑几千次都不复现
  • 生产环境负载高、信号频繁时偶发挂起
  • 崩溃现场是"进程卡在 printf"，看不出与信号有关

为什么是"同一线程重入"：handler 在被打断线程上执行，flockfile(stdout) 已被该线程持有；再次 flockfile 不会检测"是自己持有的"，而是直接死锁（stdio 锁默认非递归）。

正确做法：

/* 方案 1：用 write（async-signal-safe） */
static void handler(int sig) {
    const char m[] = "caught\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
}

/* 方案 2：handler 只设标志，主流程输出 */
static volatile sig_atomic_t got = 0;
static void handler(int sig) { got = 1; }
/* 主流程 */
if (got) { printf("caught signal\n"); got = 0; }

/* 方案 3：完全不用 handler —— signalfd / sigwaitinfo */

判断原则：只要一个函数可能加锁或分配内存，就假定它在 handler 里不安全。

问 4：handler 与主流程需要交换较多数据时有哪些正确模式？
模式 机制 特点
标志变量 volatile sig_atomic_t 只能传"发生了没有"，最简单
self-pipe handler write() 一字节到管道，主流程 read 可传信号编号，天然接入 select/epoll，高度可移植
eventfd handler write(efd, &one, 8) 内核计数器，可累计次数，可被 epoll 监听，Linux 首选
无锁 SPSC 环形队列 handler 写、主流程读 可传完整记录，零系统调用，最低延迟
signalfd 不用 handler，直接 read() 最干净，无异步信号安全问题
sigwaitinfo 不用 handler，同步取 多线程专用线程模型

推荐优先级（Linux）：

  1. signalfd —— 彻底消灭 handler，最安全、最易维护
  2. eventfd / self-pipe —— 需要保留 handler 时，把信号转成可监听事件
  3. 无锁环形队列 —— HFT 热路径，要求零 syscall
  4. 标志变量 —— 只需最简单的"是否发生"

HFT 特别说明：热路径避免任何 syscall，所以用无锁环形队列；控制路径（停机、配置重载）用 signalfd 更清晰。

问 5：为什么 handler 里要保护 errno？

因为 handler 可能在主流程任意位置打断执行——包括主流程刚设置完 errno、正准备检查它的时刻。

出错场景：

/* 主流程 */
errno = 0;
int fd = open(path, O_RDONLY);
if (fd == -1) {
    /* ← 信号在此递送，handler 调用了某个函数，把 errno 改成了别的 */
    if (errno == ENOENT) {          /* ❌ 读到的已不是 open 设置的 errno */
        ...
    }
}

后果：错误判断完全错误——明明是 ENOENT 被判成 EINTR，或反过来。这类 bug 偶发且无法复现，极难排查。

标准写法：

void handler(int sig)
{
    int saved_errno = errno;       /* ① 进入时保存 */
    /* ... 处理（可能调用修改 errno 的函数）... */
    errno = saved_errno;           /* ② 返回前恢复 */
}

这不是可选项：即便 handler 里只调用了"看起来无害"的函数（如 write()），失败时也会设置 errno。所以任何调用了库函数的 handler 都应当保护 errno。

同理适用于浮点状态：handler 里做浮点运算可能破坏主流程的 FPU/SIMD 寄存器状态（保存与恢复是架构相关的），所以 handler 里也应避免浮点运算。

从信号处理器终止进程

源码核验：Linux v6.6 · kernel/signal.c（默认动作分派 do_coredump:2878 · do_group_exit:2892 · sig_kernel_coredump @include/linux/signal.h:445） 本章：TLPI 第 21 章 — Signals: Signal Handlers - 上一节：21.1 设计信号处理器 - 下一节：21.3 在备用栈上处理信号

本节讲什么

  1. 为什么不能在 handler 里调用 exit()——它做的事情比你想的多
  2. 从 handler 终止进程有哪几种正确方式，各自适用什么场景
  3. 经典技巧「恢复默认处置后重新发信号」——为什么它能产生正确的退出状态与 core dump

一、陷阱：exit() 不是异步信号安全的

void handler(int sig)
{
    printf("fatal: %d\n", sig);
    exit(1);            /* ❌ 危险！ */
}

exit() 在返回内核前会做一串工作：

  1. 调用所有通过 atexit() / on_exit() 注册的清理函数
  2. flush 并关闭所有 stdio 流（fcloseall 语义）
  3. 删除 tmpfile() 创建的临时文件
  4. 最后才调用 _exit() 进入内核

每一步都涉及全局数据结构和锁，而 handler 可能在主流程正执行其中任意一步时插进来——结果就是死锁或数据损坏。

经典死锁场景：

   主流程                                    handler
   ────────                                  ───────
   exit(1)
   ├─ 获取 stdio 锁
   ├─ 正在 flush 缓冲区
   │                              ← 信号递送
   │                                 exit(1)
   │                                 ├─ 尝试获取 stdio 锁  ← 已被主流程持有
   │                                 └─ ❌ 死锁（同一线程重入同一把锁）

关键：handler 不是新线程（Ch20.4），它在同一线程上执行。所以主流程持有的锁，handler 再次获取时不会让出，直接死锁。

二、四种正确方式

方式 行为 适用场景
_exit(status) 立即进入内核终止，不 flush stdio、不跑 atexit 最常用；handler 中标准终止手段
_Exit(status) 同 _exit()（C99 标准名） 同上，可移植性更好
abort() 触发 SIGABRT → 默认产生 core dump 需要留下 core 供事后分析
恢复 SIG_DFL 后重新 raise 让信号的默认动作执行 需要正确的退出状态 / core（见下）

1. _exit() / _Exit() —— 标准做法

void handler(int sig)
{
    const char msg[] = "fatal signal\n";
    write(STDERR_FILENO, msg, sizeof msg - 1);   /* write 是 async-signal-safe */
    _exit(1);                                     /* ✅ 正确 */
}

_exit() 直接发起 exit_group 系统调用进入内核，跳过所有用户态清理，因此是异步信号安全的。

2. abort() —— 留下 core dump

void handler(int sig)
{
    write(STDERR_FILENO, "aborting\n", 9);
    abort();            /* 触发 SIGABRT → core dump */
}

abort() 的特殊之处：它会先解除对 SIGABRT 的阻塞，确保即使调用者阻塞了 SIGABRT，abort() 也一定能终止进程。

流程是：raise(SIGABRT) → 若 handler 返回，则把 SIGABRT 处置恢复为 SIG_DFL → 再次 raise(SIGABRT) → 默认动作执行（do_coredump + 终止）。

注意 abort() 不是严格的异步信号安全函数（POSIX 未列入清单），但 glibc 实现保证了它在 handler 中可用——因为它只调用 raise 和 sigaction，且刻意不触碰 stdio/堆。

3. 恢复默认处置后重新发信号（经典技巧）

问题：自定义 handler 处理后调用 _exit(1)，进程的退出状态是 1（正常退出），而丢失了"被信号杀死"这一信息——父进程 wait() 得到的 WIFSIGNALED 为假，看起来像是程序自己正常退出的。

解法：在 handler 里把处置恢复为 SIG_DFL，然后重新给自己发同一个信号。这次递送会走默认动作，产生正确的终止语义：

void handler(int sig)
{
    /* 1. 做最小限度的诊断输出（用 write，不用 printf） */
    const char m[] = "caught fatal signal, re-raising\n";
    write(STDERR_FILENO, m, sizeof m - 1);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底：若上面未生效（如信号被阻塞），强制退出 */
    _exit(128 + sig);
}

效果对比：

写法 父进程 wait() 看到 core dump
_exit(1) WIFEXITED，status=1 —— 看不出是被信号杀的 ❌
恢复 SIG_DFL + raise(sig) WIFSIGNALED，WTERMSIG=sig ✅ ✅（若该信号默认动作是 core）

这是 shell 里 kill -9 与程序自己 exit(137) 的区别：前者 WIFSIGNALED 为真，后者 WIFEXITED 为真。监控系统、supervisor、CI 都依赖这个区分。

 * 编译: gcc -o termdemo termdemo.c
 * 用法: ./termdemo _exit | exit | reraise */

#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

static void bad_handler(int sig)
{
    const char m[] = "  [bad] handler: 调用 exit()\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
    exit(1);                        /* ❌ 不是 async-signal-safe */
}

/* ✅ 正确：_exit() */
static void good_handler(int sig)
{
    const char m[] = "  [good] handler: 调用 _exit()\n";
    write(STDOUT_FILENO, m, sizeof m - 1);
    _exit(1);                       /* ✅ 安全 */
}

/* ✅ 正确：恢复 SIG_DFL 后重新发信号（保留 WIFSIGNALED 语义） */
static void reraise_handler(int sig)
{
    const char m[] = "  [reraise] 恢复默认处置并重新发信号\n";
    write(STDOUT_FILENO, m, sizeof m - 1);

    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    raise(sig);                     /* 走默认动作：core + 终止 */

    _exit(128 + sig);               /* 兜底 */
}

static void run(const char *mode)
{
    pid_t p = fork();
    if (p == 0) {
        struct sigaction sa = {0};
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = SA_RESTART;

        if (!strcmp(mode, "exit"))        sa.sa_handler = bad_handler;
        else if (!strcmp(mode, "_exit"))  sa.sa_handler = good_handler;
        else                              sa.sa_handler = reraise_handler;

        sigaction(SIGSEGV, &sa, NULL);
        printf("子进程 %d (%s 模式) 触发 SIGSEGV...\n", getpid(), mode);
        fflush(stdout);
        raise(SIGSEGV);                   /* 触发 */
        _exit(0);
    }

    int st;
    waitpid(p, &st, 0);
    printf("  父进程观察: ");
    if (WIFSIGNALED(st))
        printf("WIFSIGNALED=true, 终止信号=%d (WTERMSIG)\n", WTERMSIG(st));
    else if (WIFEXITED(st))
        printf("WIFEXITED=true, 退出码=%d （看不出是被信号杀的）\n", WEXITSTATUS(st));
}

int main(int argc, char **argv)
{
    const char *modes[] = { "_exit", "exit", "reraise" };
    if (argc > 1) {
        run(argv[1]);
    } else {
        for (size_t i = 0; i < 3; i++) {
            printf("\n=== 模式: %s ===\n", modes[i]);
            run(modes[i]);
        }
    }
    return 0;
}

自测题

问 1：为什么不能在信号处理函数里调用 exit()？

exit() 不是异步信号安全函数——它在进入内核前会执行一串用户态清理：

  1. 调用 atexit() / on_exit() 注册的所有清理函数
  2. flush 并关闭所有 stdio 流
  3. 删除 tmpfile() 创建的临时文件
  4. 最后才调用 _exit()

每一步都操作全局数据结构并加锁。

经典死锁场景：

主流程 exit(1)
  ├─ 获取 stdio 锁
  ├─ 正在 flush 缓冲区
  │                    ← 信号递送
  │                       handler: exit(1)
  │                         └─ 尝试获取 stdio 锁 → 已被持有 → 死锁

关键在于：handler 不是新线程，它在同一线程上执行。主流程持有的锁不会被 handler"等待让出"——同一线程重入同一把非递归锁，直接死锁。

正确做法：用 _exit() / _Exit()，它们直接发起 exit_group 系统调用，跳过所有用户态清理，是异步信号安全的。

问 2：什么是「恢复默认处置后重新发信号」技巧？解决什么问题？

解决的问题：保留「进程是被信号杀死的」这一语义信息。

如果 handler 里直接 _exit(1)，父进程 wait() 看到的是 WIFEXITED=true, status=1——看起来像程序自己正常退出，无法区分「被 OOM killer 杀」与「业务主动退出」。

技巧步骤：

void handler(int sig)
{
    /* 1. 最小诊断（用 write） */
    write(STDERR_FILENO, "fatal\n", 6);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底 */
    _exit(128 + sig);
}

效果：

写法 父进程看到 core
_exit(1) WIFEXITED=true, status=1 ❌
re-raise WIFSIGNALED=true, WTERMSIG=sig ✅（若默认动作是 core）

为什么有效：raise(sig) 时 disposition 已是 SIG_DFL，内核在 get_signal() 里走致命分支——do_coredump()（若该信号产 core）+ do_group_exit(signo)（kernel/signal.c:2878/:2892）。

第 4 步兜底必要：若该信号在 handler 执行期间被阻塞（如 sa_mask 里有它），raise 只会让它 pending 而不会立即递送。此时 _exit(128+sig) 保证进程一定退出（128+sig 是 shell 表示"被信号 N 杀死"的惯例）。

问 3：abort() 有什么特殊之处？它一定会终止进程吗？

abort() 一定会终止进程——这是它的契约保证。

特殊机制：abort() 会先解除对 SIGABRT 的阻塞，确保即使调用者用 sigprocmask 阻塞了 SIGABRT，abort() 也一定能生效。

执行流程：

abort()
  ├─ 解除对 SIGABRT 的阻塞
  ├─ raise(SIGABRT)
  │     ├─ 若有自定义 handler → 执行它
  │     └─ handler 返回 → 继续
  ├─ 把 SIGABRT 的处置恢复为 SIG_DFL
  ├─ 再次 raise(SIGABRT)      ← 这次一定走默认动作
  └─ 默认动作：do_coredump() + do_group_exit()  → 进程终止 + core dump

关键设计：即使用户注册了 SIGABRT handler 并且 handler 正常返回，abort() 也会再次发信号并强制走默认动作——所以 abort() 不可能被 handler"拦截"。

用途：

  • 断言失败（assert() 内部就是 abort()）
  • 需要留下 core 供事后 gdb 分析
  • 「不可恢复错误」的最终手段

与 _exit() 的对比：

abort() _exit()
core dump ✅ ❌
WIFSIGNALED ✅（SIGABRT） ❌
可被 handler 拦截 ❌（会 re-raise） 不适用
严格 async-signal-safe ⚠️ POSIX 未列入，但 glibc 保证可用 ✅

两个要点：

  1. 产 core 的信号有限——SIGTERM/SIGINT/SIGKILL 等不产 core，只有上表 11 个会。
  2. do_group_exit 终止整个线程组——多线程进程里任一线程触发致命信号，全进程一起退出，不只是那个线程。内核注释也强调了这点："this kills all other threads in the group and synchronizes with their demise"。

21.3

在备用栈上处理信号

源码核验：Linux v6.6 · kernel/signal.c（do_sigaltstack:4205 · SYSCALL_DEFINE2(sigaltstack):4263 · signal_delivered:2929-2930 · signal_setup_done:2935） 本章：TLPI 第 21 章 — Signals: Signal Handlers - 上一节：21.2 从信号处理器终止进程 - 下一节：21.4 SA_SIGINFO 标志

本节讲什么

  1. 为什么需要备用栈——栈溢出时 handler 无处可跑的死局
  2. sigaltstack() 怎么用，三个标志（SS_ONSTACK / SS_DISABLE / SS_AUTODISARM）各自含义
  3. 内核做哪些校验，以及栈设得太小会怎样（不是简单的"失败"）

一、为什么需要备用栈

回顾 Ch20.4：handler 在被打断线程自己的用户栈上执行，不是新线程。

于是有个死局：

   线程栈（8MB）
   ┌────────────────────┐
   │                    │
   │   已用              │
   │   ...              │
   ├────────────────────┤ ← 栈指针 SP 越过了栈底
   │  ✗ 已溢出，无空间   │
   └────────────────────┘
        ↓
   无限递归 / 超大栈帧 → SIGSEGV
        ↓
   内核想在栈上搭 sigframe 执行 handler
        ↓
   ❌ 没有栈空间了 → 搭不起来 → force_sigsegv() → 进程直接死

结果：段错误诊断 handler 根本没机会运行，进程裸奔崩溃，拿不到任何现场信息。

解法：预先分配一块独立的栈空间，告诉内核「处理信号时请用这块栈」——这就是 备用栈（alternate signal stack）。

   线程栈（已溢出）          备用栈（预分配，如 64KB）
   ┌────────────┐           ┌──────────────────┐
   │   ✗ 溢出    │           │ sigframe         │
   │            │   ──────▶ │ handler()        │  ← 在这里正常执行
   │            │           │ （可打印诊断信息） │
   └────────────┘           └──────────────────┘

二、API

#include <signal.h>

typedef struct {
    void  *ss_sp;       /* 备用栈的基地址 */
    int    ss_flags;    /* SS_ONSTACK / SS_DISABLE / SS_AUTODISARM / 0 */
    size_t ss_size;     /* 备用栈大小（字节） */
} stack_t;

int sigaltstack(const stack_t *ss, stack_t *old_ss);
/* 返回：成功 0，失败 -1 */

三个标志

标志 含义
0 设置（或替换）备用栈，使其可用
SS_ONSTACK 查询用：表示进程当前正运行在备用栈上（作为 ss 传入时无意义）
SS_DISABLE 禁用备用栈（ss_sp/ss_size 被忽略）
SS_AUTODISARM handler 返回后自动禁用并复位（Linux 4.7+，配合 SA_ONSTACK 可安全释放栈内存）

标准用法

#include <signal.h>
#include <stdlib.h>
#include <stdio.h>

static void setup_altstack(void)
{
    stack_t ss;

    /* ① 分配备用栈空间 */
    ss.ss_sp = malloc(SIGSTKSZ);
    if (ss.ss_sp == NULL) { perror("malloc"); exit(1); }
    ss.ss_size = SIGSTKSZ;
    ss.ss_flags = 0;                       /* 0 = 启用 */
    if (sigaltstack(&ss, NULL) == -1) { perror("sigaltstack"); exit(1); }

    /* ② 让 handler 使用备用栈 —— 关键是 SA_ONSTACK */
    struct sigaction sa = {0};
    sa.sa_sigaction = segv_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;  /* ← SA_ONSTACK 不可少 */
    sigaction(SIGSEGV, &sa, NULL);
}

两个步骤缺一不可：sigaltstack() 只是登记备用栈；必须再在 sigaction 里设 SA_ONSTACK，内核才会在处理该信号时切换过去。

三、内核校验链

do_sigaltstack()（kernel/signal.c:4205）：

static int
do_sigaltstack (const stack_t *ss, stack_t *oss, unsigned long sp,
        size_t min_ss_size)
{
    struct task_struct *t = current;
    int ret = 0;

    if (oss) {                                        /* ① 读旧值 */
        memset(oss, 0, sizeof(stack_t));
        oss->ss_sp = (void __user *) t->sas_ss_sp;
        oss->ss_size = t->sas_ss_size;
        oss->ss_flags = sas_ss_flags(sp) |
            (current->sas_ss_flags & SS_FLAG_BITS);
    }

    if (ss) {
        void __user *ss_sp = ss->ss_sp;
        size_t ss_size = ss->ss_size;
        unsigned ss_flags = ss->ss_flags;
        int ss_mode;

        if (unlikely(on_sig_stack(sp)))          /* ② 不能在备用栈上改备用栈 */
            return -EPERM;

        ss_mode = ss_flags & ~SS_FLAG_BITS;
        if (unlikely(ss_mode != SS_DISABLE && ss_mode != SS_ONSTACK &&
                ss_mode != 0))                  /* ③ 标志合法性 */
            return -EINVAL;

        /* ④ 无变化则提前返回 */
        if (t->sas_ss_sp == (unsigned long)ss_sp &&
            t->sas_ss_size == ss_size &&
            t->sas_ss_flags == ss_flags)
            return 0;

        sigaltstack_lock();
        if (ss_mode == SS_DISABLE) {             /* ⑤ 禁用 */
            ss_size = 0;
            ss_sp = NULL;
        } else {
            if (unlikely(ss_size < min_ss_size))         /* ⑥ 太小 */
                ret = -ENOMEM;
            if (!sigaltstack_size_valid(ss_size))        /* ⑦ 大小非法 */
                ret = -ENOMEM;
        }
        if (!ret) {                              /* ⑧ 写入 task_struct */
            t->sas_ss_sp = (unsigned long) ss_sp;
            t->sas_ss_size = ss_size;
            t->sas_ss_flags = ss_flags;
        }
        sigaltstack_unlock();
    }
    return ret;
}
# 行号 检查 违反后果
① :4212 读旧值（含 SS_ONSTACK 实时状态） —
② :4226 当前不在备用栈上 -EPERM
③ :4230 标志只能是 SS_DISABLE/SS_ONSTACK/0 -EINVAL
④ :4238 无变化则提前返回（快速路径） 返回 0
⑤ :4244 SS_DISABLE → size=0, sp=NULL —
⑥ :4248 不小于最小尺寸 -ENOMEM
⑦ :4250 大小合法 -ENOMEM
⑧ :4253 写入 task_struct.sas_ss_* —

第 ② 条值得留意：不能在备用栈运行期间修改备用栈——典型的「鸡生蛋」约束。如果你正在备用栈上跑 handler，此时再调 sigaltstack() 会返回 -EPERM。

SS_AUTODISARM 的自动复位

signal_delivered() 末尾（kernel/signal.c:2929-2930）：

    if (current->sas_ss_flags & SS_AUTODISARM)
        sas_ss_reset(current);

设了 SS_AUTODISARM 后，handler 一返回，内核立即自动禁用并复位备用栈。这让「临时分配备用栈 → 用完释放」变得安全——否则栈正在使用时被 free() 会造成内存破坏。

四、栈设得太小会怎样

答案不是"调用失败"，而是进程收到 SIGSEGV——因为 do_sigaltstack 的第 ⑥⑦ 步会拦下过小的栈，但刚好通过检查却仍不足以搭建 sigframe 的情况仍然存在：

// kernel/signal.c:2935
void signal_setup_done(int failed, struct ksignal *ksig, int stepping)
{
    if (failed)
        force_sigsegv(ksig->sig);      /* 栈帧搭不起来 → 强制 SIGSEGV */
    else
        signal_delivered(ksig, stepping);
}

实践：备用栈必须足够大。建议 ≥ 32KB，不要只用 MINSIGSTKSZ。

  • MINSIGSTKSZ：内核要求的最小值，仅够搭最简 sigframe
  • SIGSTKSZ：glibc 推荐的默认大小（通常 8KB~32KB，随架构变化）

注意 glibc 2.34 起 MINSIGSTKSZ/SIGSTKSZ 变成了运行时动态值（不再是编译期常量），所以不能用于静态数组声明或 switch case，只可用于 malloc()。

/* ✅ 正确：动态分配 */
ss.ss_sp = malloc(SIGSTKSZ);
ss.ss_size = SIGSTKSZ;

/* ❌ 错误：glibc 2.34+ 下 SIGSTKSZ 不是常量 */
static char stack[SIGSTKSZ];

五、判断当前是否在备用栈上

stack_t oss;
sigaltstack(NULL, &oss);                  /* 只查询 */
if (oss.ss_flags & SS_ONSTACK)
    printf("正在备用栈上运行\n");
else if (oss.ss_flags & SS_DISABLE)
    printf("备用栈已禁用\n");
else
    printf("备用栈已启用，当前不在其上\n");

第一个参数传 NULL 表示只查询不修改。

HFT / 嵌入式关联

路线 要点
嵌入式 备用栈是嵌入式崩溃诊断的必备设施——无调试器的现场，靠 SIGSEGV handler + SA_ONSTACK + si_addr（21.4）打印故障地址。嵌入式线程栈通常很小（8KB~64KB），递归或大栈帧极易溢出，备用栈要每个线程都设（它是线程属性）。栈大小建议 ≥ 32KB，用 MINSIGSTKSZ 容易因 sigframe 搭不起来被 force_sigsegv 打死
HFT 交易进程应全程启用备用栈处理 SIGSEGV/SIGBUS，保证崩溃时能抓到现场而非裸死。但注意：备用栈上的 handler 仍会抢占关键路径并带来延迟毛刺；HFT 的正确策略是屏蔽无关信号 + 关键路径零信号，备用栈只作为兜底的诊断设施，而非依赖路径

代码示例：栈溢出后仍能诊断

/* altstack.c —— 栈溢出后用备用栈 handler 打印现场
 * 编译: gcc -D_GNU_SOURCE -o altstack altstack.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static void segv_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)sig; (void)ctx;
    /* 注意：handler 运行在备用栈上，此处栈是干净的 */
    char buf[256];
    const char *reason =
        (info->si_code == SEGV_MAPERR) ? "地址未映射" :
        (info->si_code == SEGV_ACCERR) ? "权限不足"  : "其他";

    int n = snprintf(buf, sizeof buf,
        "\n=== SIGSEGV 捕获成功（handler 运行在备用栈上）===\n"
        "  故障地址 si_addr = %p\n"
        "  原因            = %s (si_code=%d)\n"
        "  进程可以继续输出诊断信息，而不是裸死\n",
        info->si_addr, reason, info->si_code);
    write(STDOUT_FILENO, buf, n);
    _exit(1);                       /* 用 _exit 而非 exit（见 21.2） */
}

/* 无限递归 —— 必然栈溢出 */
static void recurse(int depth)
{
    volatile char padding[4096];    /* 每层消耗 4KB，加速溢出 */
    padding[0] = (char)depth;
    if (depth > 0) recurse(depth + 1);
    (void)padding[0];
}

int main(void)
{
    /* ① 分配并登记备用栈 */
    stack_t ss;
    ss.ss_sp = malloc(SIGSTKSZ * 4);        /* 用 4 倍，更保险 */
    ss.ss_size = SIGSTKSZ * 4;
    ss.ss_flags = 0;
    if (sigaltstack(&ss, NULL) == -1) { perror("sigaltstack"); return 1; }
    printf("备用栈已启用: sp=%p size=%zu\n", ss.ss_sp, ss.ss_size);

    /* ② 注册 handler，关键是 SA_ONSTACK */
    struct sigaction sa = {0};
    sa.sa_sigaction = segv_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;   /* ← SA_ONSTACK */
    sigaction(SIGSEGV, &sa, NULL);

    /* ③ 查询状态 */
    stack_t oss;
    sigaltstack(NULL, &oss);
    printf("当前在备用栈上? %s\n",
           (oss.ss_flags & SS_ONSTACK) ? "是" : "否");

    printf("\n--- 开始无限递归，即将栈溢出 ---\n");
    recurse(0);                              /* 触发栈溢出 */

    printf("不会执行到这里\n");
    return 0;
}

对照实验：把 SA_ONSTACK 去掉，栈溢出时 handler 无法在已耗尽的栈上执行，内核会 force_sigsegv()，进程直接被杀，看不到任何诊断输出。

备用栈已启用: sp=0x... size=32768
当前在备用栈上? 否

自测题

问 1：为什么需要备用栈？不用会怎样？

因为 handler 在被打断线程自己的用户栈上执行（Ch20.4），不是新线程。

栈溢出场景的死局：

  1. 无限递归 / 超大栈帧导致线程栈耗尽，触发 SIGSEGV
  2. 内核想在栈上搭建 sigframe 执行 handler
  3. 但栈已经没有空间了
  4. signal_setup_done()（kernel/signal.c:2935）检测到 failed，调用 force_sigsegv()
  5. 进程直接被杀，handler 从未执行，拿不到任何现场信息

用了备用栈：handler 在预先分配的独立栈上执行，即使原栈已毁也能正常运行，可以打印故障地址、保存诊断信息。

实践意义：这是无调试器环境（嵌入式现场、生产服务器）崩溃诊断的核心设施。

问 2：sigaltstack() 之后还需要做什么？

还需要在 sigaction() 里设 SA_ONSTACK。

/* ① 登记备用栈 */
stack_t ss = { .ss_sp = buf, .ss_size = size, .ss_flags = 0 };
sigaltstack(&ss, NULL);

/* ② 让 handler 使用它 —— 缺了这步，备用栈形同虚设 */
struct sigaction sa = {0};
sa.sa_sigaction = handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;      /* ← SA_ONSTACK 不可少 */
sigaction(SIGSEGV, &sa, NULL);

语义区分：

调用 作用
sigaltstack(&ss, NULL) 向内核登记「有一块备用栈可用」
sa_flags = SA_ONSTACK 告诉内核「处理这个信号时请切换到备用栈」

两者是「有资源」与「用资源」的关系。登记了但没设 SA_ONSTACK，handler 仍在原栈上跑；设了 SA_ONSTACK 但没登记，sigaltstack 没调用过，内核无栈可切（会按无备用栈处理）。

粒度：SA_ONSTACK 是每个信号独立的——可以只让 SIGSEGV 用备用栈，其他信号仍在原栈执行。

问 3：备用栈设得太小会发生什么？

进程收到 SIGSEGV，而不是"设置失败"。

分两种情况：

情况 A：小到通不过内核检查 → do_sigaltstack() 返回 -ENOMEM：

// kernel/signal.c:4248-4251
        if (unlikely(ss_size < min_ss_size))
            ret = -ENOMEM;
        if (!sigaltstack_size_valid(ss_size))
            ret = -ENOMEM;

这时 sigaltstack() 返回 -1，errno = ENOMEM，调用方能感知。

情况 B：恰好通过检查，但搭不起 sigframe → 进程被 force_sigsegv：

内核搭建 sigframe 需要保存寄存器、原信号掩码、sigreturn 蹦床地址等，实际所需空间可能超过 min_ss_size。此时：

// kernel/signal.c:2935
void signal_setup_done(int failed, struct ksignal *ksig, int stepping)
{
    if (failed)
        force_sigsegv(ksig->sig);      /* ← 强制 SIGSEGV */
    else
        signal_delivered(ksig, stepping);
}

讽刺的结果：本想"优雅处理栈溢出"，反而被自己的保护机制杀死，且比不用备用栈更隐蔽（因为它发生在信号递送时刻，而非设置时刻）。

实践建议：

  • 用 ≥ 32KB，不要只用 MINSIGSTKSZ
  • MINSIGSTKSZ 只是内核的理论最小值，仅够最简 sigframe
  • 复杂 handler（有 snprintf、局部数组）需要更多空间
问 4：能在备用栈运行期间调用 free() 释放它吗？SS_AUTODISARM 解决什么？

不能直接释放——handler 正在这块内存上执行，free() 会造成内存破坏（该内存可能被 malloc 元数据或新分配占用，而 handler 还在往里写栈帧）。

SS_AUTODISARM 解决这个问题（Linux 4.7+）：

// kernel/signal.c:2929-2930
    if (current->sas_ss_flags & SS_AUTODISARM)
        sas_ss_reset(current);

设了这个标志后，handler 一返回，内核立即自动禁用并复位备用栈。这样：

/* 临时分配 → 使用 → 安全释放的完整流程 */
void *buf = malloc(SIGSTKSZ * 4);
stack_t ss = { .ss_sp = buf, .ss_size = SIGSTKSZ * 4,
               .ss_flags = SS_AUTODISARM };
sigaltstack(&ss, NULL);

/* ... handler 执行 ... */

/* handler 返回后，内核已自动禁用备用栈，可以安全 free */
free(buf);

没有 SS_AUTODISARM 时：handler 返回后备用栈仍是启用状态。如果此时 free(buf)，下次信号递送时内核会切换到已释放的内存上——未定义行为。

注意：SS_AUTODISARM 是一次性的。若希望后续信号仍用备用栈，需要在每次使用后重新设置——这适合「临时诊断」场景，不适合长期启用的生产配置。

问 5：多线程程序里，备用栈需要每个线程都设置吗？

是的。备用栈是线程属性（存在 task_struct 的 sas_ss_sp/sas_ss_size/sas_ss_flags），不是进程共享的。

// kernel/signal.c:4253-4257
        if (!ret) {
            t->sas_ss_sp = (unsigned long) ss_sp;
            t->sas_ss_size = ss_size;
            t->sas_ss_flags = ss_flags;
        }

注意是 t（= current，即当前线程），不是 t->signal。

对比其他信号属性的作用域（高频考点）：

属性 存放位置 作用域
掩码 task_struct.blocked 线程私有
备用栈 task_struct.sas_ss_* 线程私有
处置 sighand->action[] 进程共享

实践要点：

  1. 每个线程都要各自调用 sigaltstack()——主线程设置不影响其他线程
  2. 每个线程需要独立的栈内存（不能多个线程共用一块！否则 handler 并发执行时栈帧互相覆盖）
  3. 新线程不会继承父线程的备用栈
  4. 典型做法：在线程入口函数开头设置，用线程局部存储或 pthread_key 管理栈内存
void *worker(void *arg)
{
    /* 每个线程独立设置自己的备用栈 */
    stack_t ss = { .ss_sp = malloc(SIGSTKSZ * 4),
                   .ss_size = SIGSTKSZ * 4, .ss_flags = 0 };
    sigaltstack(&ss, NULL);
    ...
}

嵌入式特别注意：嵌入式线程栈本身就小（8KB~64KB），更容易溢出，备用栈对每个线程都更有必要——但也意味着内存开销 × 线程数，需要权衡。

21.4

`SA_SIGINFO` 标志

源码核验：Linux v6.6 · include/uapi/asm-generic/siginfo.h:139-191（siginfo_t union 定义）· kernel/signal.c（copy_siginfo_from_user:3401 · do_rt_sigqueueinfo @SYSCALL_DEFINE3(rt_sigqueueinfo):4032） 本章：TLPI 第 21 章 — Signals: Signal Handlers - 上一节：21.3 在备用栈上处理信号 - 下一节：21.5 系统调用的中断与重启

本节讲什么

  1. SA_SIGINFO 开启了什么——从 void(int) 升级到 void(int, siginfo_t*, void*) 能拿到哪些信息
  2. siginfo_t 的 union 语义——同一块内存按信号类型有不同解读，用错字段就是垃圾值
  3. si_code 怎么区分信号来源（用户 / 内核 / 具体原因），以及各信号对应哪些有效字段

一、开启 SA_SIGINFO

在 sigaction 的 sa_flags 里加上 SA_SIGINFO，并把处理器装进 sa_sigaction：

void handler(int sig, siginfo_t *info, void *ucontext);

struct sigaction sa = {0};
sa.sa_sigaction = handler;             /* ← 注意用 sa_sigaction */
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO;              /* ← 必须设这个标志 */
sigaction(SIGUSR1, &sa, NULL);
参数 类型 内容
sig int 信号编号
info siginfo_t * 信号的详细信息（发送者 PID/UID、故障地址、附加数据…）
ucontext void * 指向 ucontext_t，保存被中断时刻的完整 CPU 上下文（寄存器、栈指针、PC）

⚠️ 陷阱：sa_handler 与 sa_sigaction 在 Linux/glibc 上是 union 的同一块内存（详见 Ch20.13）。设了 SA_SIGINFO 就必须用 sa_sigaction，反之亦然，绝不能同时赋值。

ucontext 的用途：可以读取甚至修改被中断时刻的寄存器状态。这是实现「修复故障继续执行」（如模拟 FPU 指令、处理 SIGSEGV 后跳转）的基础。但这是高度架构相关的非可移植操作，通常用 (ucontext_t *)ucontext 访问 uc_mcontext。

二、siginfo_t 是 union，不是 struct

这是本节最关键的认知。siginfo_t 的第三个成员是一个 union：

// include/uapi/asm-generic/siginfo.h:139
typedef struct siginfo {
    int si_signo;         /* 信号编号，总是有效 */
    int si_errno;         /* 通常不用（Linux 未填充） */
    int si_code;          /* 信号来源/原因码，总是有效 */

    union {
        int _si_pad[SI_MAX_SIZE/sizeof(int)];
        /* kill()/sigqueue()/终端 */
        struct { pid_t _pid; uid_t _uid; } _kill;
        /* POSIX.1b timers */
        struct { ... } _timer;
        /* SIGCHLD */
        struct { pid_t _pid; uid_t _uid; int _status; clock_t _utime, _stime; } _sigchld;
        /* SIGILL/SIGFPE/SIGSEGV/SIGBUS */
        struct { void *_addr; short _addr_lsb; ... } _sigfault;
        /* SIGPOLL/SIGIO */
        struct { long _band; int _fd; } _sigpoll;
        /* SIGSYS（seccomp） */
        struct { void *_call_addr; int _syscall; unsigned int _arch; } _sigsys;
        /* 实时信号 */
        struct { pid_t _pid; uid_t _uid; union sigval _sigval; } _rt;
    } _sifields;
} siginfo_t;

所有具体字段都是宏，映射到 union 的某个成员：

宏 行号 映射到 有效于
si_pid :149 _sifields._kill._pid kill / sigqueue / SIGCHLD
si_uid :150 _sifields._kill._uid 同上
si_value :157 _sifields._rt._sigval sigqueue / 实时信号
si_int :158 _sifields._rt._sigval.sival_int 同上（int 形态）
si_ptr :159 _sifields._rt._sigval.sival_ptr 同上（void* 形态）
si_addr :160 _sifields._sigfault._addr SIGSEGV/SIGBUS/SIGILL/SIGFPE
si_status :154 _sifields._sigchld._status SIGCHLD（子进程退出状态）
si_utime/si_stime :155/:156 _sifields._sigchld.* SIGCHLD（子进程 CPU 时间）
si_fd :170 _sifields._sigpoll._fd SIGPOLL/SIGIO（就绪 fd）
si_band :169 _sifields._sigpoll._band SIGPOLL（事件类型位掩码）
si_syscall :172 _sifields._sigsys._syscall SIGSYS（seccomp 拦截的系统调用号）

核心规则：只有与当前信号类型匹配的字段才有意义。在 SIGSEGV 的 handler 里读 si_pid 得到的是 _sigfault._addr 的低位——完全无意义的垃圾。

各信号的有效字段

信号 有效字段
kill() / raise() 发送的任何信号 si_pid（发送者 PID）、si_uid（发送者 real UID）
sigqueue() 发送的实时信号 si_pid、si_uid、si_value（si_int / si_ptr）
SIGCHLD si_pid（子进程 PID）、si_status（退出状态/停止信号）、si_utime、si_stime
SIGSEGV / SIGBUS / SIGILL / SIGFPE si_addr（触发故障的内存地址）
SIGPOLL / SIGIO si_fd（就绪的 fd）、si_band（POLLIN/POLLOUT/POLLERR 等）
SIGSYS（seccomp） si_syscall（被拦截的系统调用号）、si_arch、si_call_addr

三、si_code：信号从哪来

si_code 描述信号的来源与具体原因。两个判据宏：

// include/uapi/asm-generic/siginfo.h:190-191
#define SI_FROMUSER(siptr)  ((siptr)->si_code <= 0)
#define SI_FROMKERNEL(siptr)    ((siptr)->si_code > 0)
判据 含义
SI_FROMUSER(info) 信号来自用户进程（kill/sigqueue/raise）
SI_FROMKERNEL(info) 信号来自内核（硬件异常、终端、定时器、子进程通知…）

常见 si_code 值

si_code 值 含义
SI_USER 0 kill() 发送
SI_KERNEL 0x80 内核内部产生
SI_QUEUE -1 sigqueue() 发送
SI_TIMER -2 POSIX 定时器到期
SI_MESGQ -3 POSIX 消息队列状态变化
SI_ASYNCIO -4 异步 I/O 完成
SI_SIGIO -5 信号驱动 I/O（SIGIO）
SI_TKILL -6 tgkill() 发送
SEGV_MAPERR 1 SIGSEGV：地址未映射
SEGV_ACCERR 2 SIGSEGV：权限不足（如写只读页）
CLD_EXITED 1 SIGCHLD：子进程正常退出
CLD_KILLED 2 SIGCHLD：子进程被信号杀死
CLD_STOPPED 4 SIGCHLD：子进程被停止
CLD_CONTINUED 6 SIGCHLD：子进程被继续

注意 si_code 的正负约定：用户来源 ≤ 0，内核来源 > 0。所以 SI_USER 是 0 而 SI_QUEUE 是 -1，而 SEGV_MAPERR 是 1（内核）。

四、典型用途

用途 做法
审计谁发的信号 读 si_pid / si_uid（如确认 SIGTERM 是否来自合法运维进程）
诊断段错误 读 si_addr 获取故障地址，配合 si_code（SEGV_MAPERR vs SEGV_ACCERR）区分"野指针"与"写只读页"
SIGCHLD 精确处理 读 si_status + si_code 区分正常退出 / 被信号杀死 / 停止
实时信号传数据 sigqueue() 的 si_value 携带 int 或指针（见 Ch22.8）
信号驱动 I/O SIGIO 的 si_fd / si_band 知道哪个 fd 就绪（见 Ch63.3）
seccomp 沙箱 SIGSYS 的 si_syscall 得知被拦截的调用号

HFT / 嵌入式关联

路线 要点
嵌入式 SIGSEGV handler 里读 si_addr 可在无调试器的现场打印故障地址，是嵌入式崩溃诊断的核心手段。配合 SA_ONSTACK 备用栈（21.3）即使栈溢出也能工作。注意 si_addr 只在 SIGSEGV/SIGBUS/SIGILL/SIGFPE 下有效，其他信号读它是垃圾值
HFT si_pid/si_uid 可审计停机信号来源——区分「运维正常停机」与「误杀/恶意信号」，是交易系统风控的一环。但注意：handler 里不能调用 printf/syslog（非异步信号安全），正确做法是把 si_pid/si_signo 存进 volatile sig_atomic_t 或无锁队列，回主流程再落日志

代码示例：三种典型场景

/* siginfodemo.c —— SA_SIGINFO 的三种典型用法
 * 编译: gcc -o siginfodemo siginfodemo.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>

/* 场景 1：审计信号来源（谁发的） */
static void audit_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)ctx;
    char buf[256];
    int n = snprintf(buf, sizeof buf,
        "[audit] signo=%d si_code=%d 来自 %s: si_pid=%d si_uid=%d\n",
        sig, info->si_code,
        SI_FROMKERNEL(info) ? "内核" : "用户进程",
        info->si_pid, info->si_uid);
    write(STDOUT_FILENO, buf, n);
}

/* 场景 2：诊断段错误 */
static void segv_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)ctx;
    char buf[256];
    const char *reason = "未知";
    if (sig == SIGSEGV) {
        if (info->si_code == SEGV_MAPERR) reason = "地址未映射（野指针/已释放）";
        else if (info->si_code == SEGV_ACCERR) reason = "权限不足（写只读页？）";
    }
    int n = snprintf(buf, sizeof buf,
        "[segv] 故障地址 si_addr=%p  原因: %s\n", info->si_addr, reason);
    write(STDOUT_FILENO, buf, n);
    _exit(1);                       /* 用 _exit 而非 exit（见 21.2） */
}

/* 场景 3：SIGCHLD 精确处理 */
static void chld_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)ctx; (void)sig;
    char buf[256];
    const char *how = "?";
    switch (info->si_code) {
    case CLD_EXITED:    how = "正常退出"; break;
    case CLD_KILLED:    how = "被信号杀死"; break;
    case CLD_DUMPED:    how = "被信号杀死并 core"; break;
    case CLD_STOPPED:   how = "被停止"; break;
    case CLD_CONTINUED: how = "被继续"; break;
    }
    int n = snprintf(buf, sizeof buf,
        "[chld] 子进程 %d %s, si_status=%d\n",
        info->si_pid, how, info->si_status);
    write(STDOUT_FILENO, buf, n);
}

static void install(int sig, void (*h)(int, siginfo_t *, void *))
{
    struct sigaction sa = {0};
    sa.sa_sigaction = h;              /* ← 用 sa_sigaction */
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO;         /* ← 必须 */
    sigaction(sig, &sa, NULL);
}

int main(void)
{
    install(SIGUSR1, audit_handler);
    install(SIGSEGV, segv_handler);
    install(SIGCHLD, chld_handler);

    raise(SIGUSR1);                   /* 来自自己 → 用户来源 */

    pid_t p = fork();
    if (p == 0) _exit(42);
    sleep(1);                         /* 等 SIGCHLD */

    /* 触发段错误（最后一击） */
    printf("\n--- 即将触发段错误 ---\n");
    volatile int *bad = (int *)0xDEAD;
    *bad = 1;
    return 0;
}

自测题

问 1：siginfo_t 为什么是 union？读错字段会怎样？

siginfo_t 的大小是固定的（SI_MAX_SIZE），但不同信号需要携带的信息各不相同（发送者 PID、故障地址、子进程状态、fd…）。内核用 union 让同一块内存按信号类型有不同解读，从而复用同一个结构体。

typedef struct siginfo {
    int si_signo;      /* 总是有效 */
    int si_errno;
    int si_code;       /* 总是有效 */
    union {
        int _si_pad[...];
        struct { pid_t _pid; uid_t _uid; } _kill;
        struct { void *_addr; ... } _sigfault;
        struct { pid_t _pid; int _status; ... } _sigchld;
        struct { long _band; int _fd; } _sigpoll;
        ...
    } _sifields;
} siginfo_t;

读错字段的后果：得到垃圾值，且不会报错。

例如在 SIGSEGV 的 handler 里读 si_pid：

#define si_pid   _sifields._kill._pid        /* union 的 _kill 分支 */
#define si_addr  _sifields._sigfault._addr   /* union 的 _sigfault 分支 */

两者是同一块内存的不同解读。SIGSEGV 时内核填的是 _sigfault._addr，此时读 _kill._pid 得到的就是 _addr 的低 32 位——一个"看起来像 PID"的随机数。

规则：只读写当前信号类型对应的字段。

信号 有效字段
kill/sigqueue 来的 si_pid、si_uid、si_value
SIGSEGV/SIGBUS/SIGILL/SIGFPE si_addr
SIGCHLD si_pid、si_status、si_utime/si_stime
SIGPOLL/SIGIO si_fd、si_band
问 2：怎么判断一个信号是用户进程发的还是内核产生的？

用 si_code 的符号，内核提供了两个判据宏：

// include/uapi/asm-generic/siginfo.h:190-191
#define SI_FROMUSER(siptr)  ((siptr)->si_code <= 0)
#define SI_FROMKERNEL(siptr)    ((siptr)->si_code > 0)
判据 含义
SI_FROMUSER(info)（si_code <= 0） 来自用户进程（kill/sigqueue/raise/tgkill）
SI_FROMKERNEL(info)（si_code > 0） 来自内核（硬件异常、终端、定时器、子进程通知…） 
void handler(int sig, siginfo_t *info, void *ctx)
{
    if (SI_FROMUSER(info))
        /* 来自用户进程：info->si_pid / si_uid 有效 */
    else
        /* 来自内核：如 SEGV_MAPERR、CLD_EXITED 等 */
}

注意正负约定：

  • SI_USER = 0（kill() 发送）→ 判为用户来源
  • SI_QUEUE = -1（sigqueue()）→ 判为用户来源
  • SEGV_MAPERR = 1（内核的段错误）→ 判为内核来源

所以"用户来源"包含 0 与负数，"内核来源"是正数。

典型用途：交易系统审计 SIGTERM 是运维正常停机（SI_USER + 预期 PID）还是异常来源。

问 3：怎么用 SA_SIGINFO 诊断段错误？

在 SIGSEGV handler 里读 si_addr（故障地址）和 si_code（故障类型）：

static void segv_handler(int sig, siginfo_t *info, void *ctx)
{
    const char *reason = "未知";
    if (info->si_code == SEGV_MAPERR)       reason = "地址未映射（野指针/已释放）";
    else if (info->si_code == SEGV_ACCERR)  reason = "权限不足（写只读页？）";
    fprintf(stderr, "SIGSEGV @ %p : %s\n", info->si_addr, reason);
    _exit(1);
}
si_code 含义 典型原因
SEGV_MAPERR（1） 地址未映射 野指针、use-after-free、数组越界到未映射区
SEGV_ACCERR（2） 地址已映射但权限不足 写只读页（如写 .text 段、写 mmap 的 PROT_READ 区）

两者的诊断价值：

  • SEGV_MAPERR → 指针值本身是错的（未初始化、已 free、算错）
  • SEGV_ACCERR → 指针值"对"但用法错（写只读、执行不可执行页）

必须配合 SA_ONSTACK：如果段错误是栈溢出引起的，此时栈已不可用，handler 无法在原地执行。必须用 sigaltstack() 提供备用栈（见 21.3）。

注意：handler 里不能调用 printf/malloc（非异步信号安全）。上例用 fprintf 是为可读性，生产代码应用 write(2)，或先保存信息再 _exit。

问 4：ucontext 参数有什么用？

ucontext 指向一个 ucontext_t，保存被中断时刻的完整 CPU 上下文（通用寄存器、栈指针、PC、浮点/SIMD 状态）。

两个用途：

  1. 诊断：读取被中断时的寄存器，尤其是 PC（程序计数器）——能精确定位是哪条指令触发了故障。si_addr 告诉"访问了哪个地址"，ucontext 的 PC 告诉"哪行代码访问的"。
#include <ucontext.h>
void segv_handler(int sig, siginfo_t *info, void *ctx)
{
    ucontext_t *uc = (ucontext_t *)ctx;
    /* x86-64: 触发故障的指令地址 */
    void *pc = (void *)uc->uc_mcontext.gregs[REG_RIP];
    /* ARM64: uc->uc_mcontext.pc */
}
  1. 修改执行流：因为 ucontext 是内核恢复上下文的依据，修改它就能改变返回后的行为。这用于：
  • 模拟未实现的指令（如某些 FPU 陷阱）
  • SIGSEGV 修复后跳过故障指令继续执行
  • 用户态协程/纤程（fiber）实现
  • 某些 JIT 编译器的边界检查优化

严重警告：

  • 这是高度架构相关的操作（uc_mcontext.gregs[REG_RIP] 是 x86-64 专用，ARM64 是 uc_mcontext.pc）
  • 修改上下文极易导致进程状态不一致
  • 属于专家级技巧，一般业务代码不要碰
问 5：设了 SA_SIGINFO 但用了 sa_handler 会怎样？

未定义行为——大概率崩溃。

sa_handler 与 sa_sigaction 在 Linux/glibc 上是 union 的同一块内存：

struct sigaction {
    union {
        void (*sa_handler)(int);
        void (*sa_sigaction)(int, siginfo_t *, void *);
    } __sigaction_handler;
    ...
};

设了 SA_SIGINFO 后，内核会用三参数的调用约定去调用你注册的函数指针：

handler(sig, info, ucontext);      /* 传三个参数 */

但如果该函数实际是 void handler(int)，它只会读取第一个参数、忽略另外两个——在多数 ABI 下这不会立即崩溃（多余的参数被忽略），代码"看似能跑"，但：

  • 你拿不到 siginfo_t
  • 依赖调用约定的优化（如寄存器分配）可能产生微妙错误
  • 换个架构（ARM64 vs x86-64）、换个编译器就可能崩

反向错误更危险：用 sa_sigaction 装了三参数函数，但没设 SA_SIGINFO：

handler(sig);                       /* 内核只传一个参数 */

此时第二个、第三个参数是寄存器里的垃圾值。函数会把垃圾当 siginfo_t * 去解引用 → 段错误。

规则：

sa_flags 用哪个成员
含 SA_SIGINFO sa.sa_sigaction
不含 SA_SIGINFO sa.sa_handler

永远不要同时给两者赋值（后者覆盖前者）。

系统调用的中断与重启

本节讲什么

  1. 阻塞在慢系统调用里的进程收到信号会怎样——EINTR 是怎么产生的

  3. 为什么并非所有调用都能重启，以及业务代码为什么仍应统一处理 EINTR

一、慢系统调用与 EINTR

慢系统调用（slow system call） = 可能无限期阻塞的系统调用。

典型慢调用 例子
终端 / 管道 / socket 的 read 等对端写数据
管道的 write 等缓冲区有空间
open 某些设备（FIFO、终端） 等对端打开
wait / waitpid 等子进程退出
pause / sleep / nanosleep 等时间
select / poll / epoll_wait 等 I/O 事件
accept / connect / recv / send 等网络事件
flock / fcntl(F_SETLKW) 等文件锁

EINTR 的产生：

   进程阻塞在 read() 中（内核态，TASK_INTERRUPTIBLE）
        │
        ↓ 信号递送
   内核唤醒进程 → 执行 handler
        │
        ↓ handler 返回
   内核决定：这个 read() 怎么办？
        ├─ 不重启 → 返回 -EINTR 给用户态
        └─ 重启   → 重新执行 read()

不设 SA_RESTART 时，被中断的调用返回 -1，errno = EINTR。内核里对应的就是不重启分支：

// kernel/signal.c:3040
long do_no_restart_syscall(struct restart_block *param)
{
    return -EINTR;
}

二、SA_RESTART：内核如何自动重启

设了 SA_RESTART 后，被中断的慢调用会被内核自动重新执行，用户态看不到 EINTR。

内核机制是 task_struct.restart_block——把被中断的 syscall 状态存下来，需要重启时调用其 fn 函数指针：

// kernel/signal.c:3034
/**
 *  sys_restart_syscall - restart a system call
 */
SYSCALL_DEFINE0(restart_syscall)
{
    struct restart_block *restart = &current->restart_block;
    return restart->fn(restart);
}

   read(fd, buf, n) 阻塞中
        │
        ↓ 信号中断
   内核把 read 的参数/进度存入 current->restart_block
   并让 restart_block.fn = 对应的重启函数
        │
        ↓ handler 返回后，内核检查 SA_RESTART
   ┌────┴────┐
   设了 → 调 restart_block.fn()  重新执行（restart_syscall 通路）
   没设 → do_no_restart_syscall() 返回 -EINTR

注意：重启是内核态行为，用户态完全无感知——read() 的返回地址不变，C 代码里就是一次普通的 read() 调用。这与「用户态手写 while (EINTR) 重试循环」有本质区别：内核重启不产生额外的系统调用开销。

三、哪些能重启，哪些不能（关键表）

这是本节最重要的实践知识：即便设了 SA_RESTART，以下情况仍然返回 EINTR。

类别 具体调用 设 SA_RESTART 后
普通慢调用 read/write（终端、管道、socket）、wait/waitpid、open（FIFO/终端）、flock、fcntl(F_SETLKW) ✅ 自动重启
带超时的等待 select、poll、epoll_wait、epoll_pwait、semop 的 timeout、sigtimedwait ❌ 返回 EINTR
connect connect() ❌ 返回 EINTR
send/sendto/sendmsg 部分平台（尤其带 SO_SNDTIMEO） ❌ 可能返回 EINTR
recv 带 MSG_WAITALL 已收到部分数据时 ❌ 返回已收字节数（非错误）
nanosleep/clock_nanosleep 被中断 ❌ 返回 EINTR，rem 中保存剩余时间
ioctl 部分设备 ⚠️ 视驱动而定
close Linux 上 ❌ 返回 EINTR，但 fd 已关闭（详见陷阱）

为什么带超时的不能重启：重启会重置超时计时，语义就变了（原本 3 秒超时可能变成 6 秒）。所以内核选择让调用者自己决定怎么处理。

为什么 connect 不能重启：connect 是非幂等的——重启会重新发起连接，可能掩盖错误。

四、防御性写法

规则：即便设了 SA_RESTART，涉及 I/O 多路复用和网络的调用也应显式处理 EINTR。

/* read 的防御性包装 */
ssize_t read_retry(int fd, void *buf, size_t n)
{
    ssize_t ret;
    do {
        ret = read(fd, buf, n);
    } while (ret == -1 && errno == EINTR);
    return ret;
}

/* write 同理（注意部分写的处理） */
ssize_t write_retry(int fd, const void *buf, size_t n)
{
    ssize_t ret;
    do {
        ret = write(fd, buf, n);
    } while (ret == -1 && errno == EINTR);
    return ret;
}

nanosleep 的剩余时间处理

nanosleep 被中断时，会在第二个参数里保存剩余未睡完的时间：

/* 精确的睡眠：被信号中断后继续睡剩余时间 */
int sleep_full(const struct timespec *req)
{
    struct timespec rem = *req;
    while (nanosleep(&rem, &rem) == -1 && errno == EINTR)
        ;                       /* rem 已被更新为剩余时间 */
    return 0;
}

注意：sleep() 被中断时返回剩余秒数（不是 -1），语义与 nanosleep 不同。而 usleep() 已被废弃。

五、陷阱：close() 返回 EINTR 时 fd 已关闭

这是 Linux 特有的一个坑：

/* Linux 上：即使 close 返回 EINTR，fd 也已经被关闭了 */
if (close(fd) == -1 && errno == EINTR) {
    close(fd);        /* ❌ 危险！可能关掉了别人刚打开的 fd */
}

Linux 的 close() 即使在被信号中断的情况下也会完成关闭动作。此时若重试 close(fd)，而该 fd 号已被其他线程/代码分配给新文件，就会误关别人的 fd。

正确做法：在 Linux 上，close() 返回 EINTR 时不要重试。

对比：POSIX 原本规定 close() 返回 EINTR 时状态未定义（fd 可能关了也可能没关），所以可移植代码需要区分平台。Linux 的行为是"已关闭"，HP-UX 等是"未关闭"。

六、EINTR vs EAGAIN

两者都表示「没成功，但不一定是错误」，容易混淆：

EINTR EAGAIN
含义 被信号中断 资源暂时不可用（非阻塞 I/O 无数据）
触发 慢调用 + 信号递送 非阻塞 fd 上 read 无数据 / accept 无连接
处理 通常重试 通常等下次事件通知（epoll）
是否错误 ❌ 不是 ❌ 不是 
ssize_t n = read(fd, buf, sizeof buf);
if (n == -1) {
    if (errno == EINTR)       /* 被信号打断 → 重试 */
        goto retry;
    else if (errno == EAGAIN) /* 无数据 → 返回事件循环 */
        return 0;
    else
        return -1;            /* 真错误 */
}

HFT / 嵌入式关联

路线 要点
嵌入式 慢设备 I/O（串口/网络）极易被信号打断，嵌入式代码对 read/write 必须处理 EINTR 重试，否则偶发中断会静默丢数据——这类 bug 往往几周才复现一次，现场极难定位。设 SA_RESTART 能从源头减少 EINTR，但 select/poll 仍要显式处理
HFT EINTR 是延迟抖动来源之一：阻塞中的 recv/epoll_wait 被打断后返回，若未重试会漏掉一个事件周期；若盲目重试又可能引入额外延迟。HFT 的正确做法是：统一 while (ret < 0 && errno == EINTR) 重试保证不丢事件，同时把无关信号全部屏蔽，从源头消除中断——让 EINTR 路径成为永不触发的冷路径

代码示例：观察 SA_RESTART 的效果

/* eintrdemo.c —— 对比设/不设 SA_RESTART 时 read 的行为
 * 编译: gcc -o eintrdemo eintrdemo.c
 * 运行: 另开终端 kill -USR1 <pid> 触发信号 */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <stdlib.h>

static volatile sig_atomic_t caught = 0;
static void handler(int sig) { caught = 1; }

/* 用 alarm 自动发信号，避免手工操作 */
static void trial(const char *tag, int use_restart)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = use_restart ? SA_RESTART : 0;
    sigaction(SIGALRM, &sa, NULL);

    char buf[64];
    caught = 0;
    alarm(2);                              /* 2 秒后发 SIGALRM */
    ssize_t n = read(STDIN_FILENO, buf, sizeof buf);   /* 阻塞等输入 */

    if (n == -1 && errno == EINTR)
        printf("%-20s read 返回 -1, errno=EINTR（被中断，未重启）\n", tag);
    else
        printf("%-20s read 返回 %zd（已重启/读到数据）\n", tag, n);

    alarm(0);
}

/* nanosleep 的剩余时间处理演示 */
static void nanosleep_demo(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                        /* 不设 SA_RESTART */
    sigaction(SIGALRM, &sa, NULL);

    struct timespec req = { .tv_sec = 3, .tv_nsec = 0 };
    struct timespec rem = {0};

    alarm(1);                               /* 1 秒后打断 3 秒的睡眠 */
    while (nanosleep(&req, &rem) == -1 && errno == EINTR) {
        printf("nanosleep 被中断，剩余 %ld.%03lds，继续睡\n",
               (long)rem.tv_sec, rem.tv_nsec / 1000000);
        req = rem;                          /* 睡剩余时间 */
        alarm(0);
    }
    printf("nanosleep 完成\n");
}

int main(void)
{
    printf("=== SA_RESTART 对比（请在 2 秒内不要输入，等 SIGALRM 触发）===\n");
    trial("无 SA_RESTART:", 0);
    trial("有 SA_RESTART:", 1);             /* 这一路会一直阻塞到真输入 */

    printf("\n=== nanosleep 剩余时间处理 ===\n");
    nanosleep_demo();
    return 0;
}

自测题

问 1：什么是慢系统调用？被信号中断后会发生什么？

慢系统调用 = 可能无限期阻塞的系统调用。

典型例子：终端/管道/socket 的 read、write 管道、open FIFO、wait、pause、sleep、select/poll/epoll_wait、accept/connect/recv、flock。

被信号中断后：

  • 未设 SA_RESTART → 调用返回 -1，errno = EINTR
  • 设了 SA_RESTART → 内核自动重新执行该调用，用户态无感知

内核里对应的两个分支：

// 重启：从 restart_block 恢复并重新执行
SYSCALL_DEFINE0(restart_syscall)              // kernel/signal.c:3034
{
    struct restart_block *restart = &current->restart_block;
    return restart->fn(restart);
}

// 不重启：直接返回 EINTR
long do_no_restart_syscall(struct restart_block *param)   // :3040
{
    return -EINTR;
}
问 2：设了 SA_RESTART 就万事大吉了吗？哪些调用仍会返回 EINTR？

不可以高枕无忧。以下调用即便设了 SA_RESTART 仍然返回 EINTR：

类别 例子 原因
带超时 select、poll、epoll_wait、sigtimedwait、semop(timeout) 重启会重置超时，语义被破坏
connect connect() 非幂等，重启会重新发起连接
nanosleep nanosleep() 返回 EINTR，剩余时间存在 rem 参数里
close Linux close() 返回 EINTR，但fd 已关闭（见陷阱）
部分网络发送 带 SO_SNDTIMEO 的 send 平台相关

实践规则：

  1. read/write/wait/open(FIFO) 等普通慢调用 → SA_RESTART 能覆盖，但仍建议防御性重试
  2. select/poll/epoll_wait/connect/nanosleep → 必须显式处理 EINTR
  3. close → Linux 上不要因 EINTR 重试

一句话：SA_RESTART 是减少 EINTR 的便利手段，不是免除 EINTR 处理的理由。

问 3：close() 返回 EINTR 时应该重试吗？

在 Linux 上绝对不要重试。

Linux 的 close() 实现即使在被信号中断的情况下也已经完成了关闭动作。此时 fd 号已经释放，可能被其他线程或后续 open() 分配给新文件。如果重试 close(fd)，就会误关别人刚打开的文件——这是极难排查的隐蔽 bug。

/* ❌ 危险 */
if (close(fd) == -1 && errno == EINTR)
    close(fd);        /* 可能关掉别人刚分配的 fd！ */

/* ✅ 正确：不重试 */
close(fd);            /* 忽略 EINTR，fd 在 Linux 上已关闭 */

为什么会有这种差异：

POSIX 原本规定 close() 返回 EINTR 时 fd 状态未定义（可能关了也可能没关），所以可移植代码需要区分平台：

平台 close 返回 EINTR 时 fd 状态
Linux 已关闭（不要重试）
HP-UX 等传统 UNIX 未关闭（可重试）

Linux 后来明确了这个行为，并成为事实标准。写 Linux 专用代码时，close() 一律不重试 EINTR。

问 4：nanosleep 被信号打断后怎么保证睡够指定时长？

nanosleep 被中断时返回 -1，errno = EINTR，并在第二个参数（rem）里写入剩余未睡完的时间。循环时用 rem 更新请求即可：

int sleep_full(const struct timespec *req)
{
    struct timespec rem = *req;
    while (nanosleep(&rem, &rem) == -1 && errno == EINTR)
        ;                        /* 循环体为空：rem 已被内核更新为剩余时间 */
    return 0;
}

关键点：第二个参数既是输出又是下一次的输入。上例中 rem 在每次失败后被更新，直接复用即可。

对比其他睡眠接口：

接口 被信号中断时 如何恢复
nanosleep(&req, &rem) 返回 -1，errno=EINTR，rem 存剩余时间 用 rem 继续
clock_nanosleep(..., &rem)（不设 TIMER_ABSTIME） 同上 同上
clock_nanosleep(..., TIMER_ABSTIME) 返回 EINTR，不写 rem 用绝对时间重新调用（天然正确）
sleep(sec) 返回剩余秒数（不是 -1） 用返回值继续
usleep() 返回 -1，errno=EINTR 已废弃，勿用

推荐：需要精确时长时用 clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)——绝对时间语义下，重试天然不会累积误差，也不受 SA_RESTART 影响。

问 5：EINTR 和 EAGAIN 有什么区别？分别该怎么处理？
EINTR EAGAIN
含义 被信号中断 资源暂时不可用
触发场景 慢调用阻塞中信号递送 非阻塞 fd 上 read 无数据 / accept 无待处理连接 / fork 达上限
本质 被外部事件打断 条件不满足
处理 重试 等下次事件通知（回到 epoll 循环）

典型处理框架：

ssize_t n = read(fd, buf, sizeof buf);
if (n >= 0) {
    /* 成功，处理数据 */
} else if (errno == EINTR) {
    goto retry;                 /* 被信号打断 → 立即重试 */
} else if (errno == EAGAIN || errno == EWOULDBLOCK) {
    return 0;                   /* 无数据 → 回事件循环，不要忙等重试！ */
} else {
    return -1;                  /* 真错误 */
}

关键区别在处理动作：

  • EINTR → 立即重试：信号已经处理完，重试大概率能继续
  • EAGAIN → 不要重试：立刻重试只会空转烧 CPU。正确做法是回到 epoll_wait 等待下次事件通知

HFT 特别注意：把 EAGAIN 当成 EINTR 去重试，会在无数据时产生忙等，直接烧毁一个 CPU 核心——这是低延迟系统里常见的性能事故。

    errno = saved_errno;                           /* ⑤ */
}

/* 主流程 */
for (;;) {
    if (got_signal) {                              /* ⑥ */
        got_signal = 0;
        handle_shutdown();     /* 这里可随意 printf/malloc */
    }
    do_work();
}
# 为什么
① volatile 防编译器缓存优化；sig_atomic_t 保证读写原子
② 只有 int sig 一个参数（未设 SA_SIGINFO）
③ 保护 errno——handler 可能在主流程刚设完 errno 时插入
④ 只做单次原子赋值，不做读-改-写，无需锁
⑤ 恢复 errno，避免破坏主流程的错误判断
⑥ 复杂逻辑移回主流程，可自由使用任何库函数

这个模式的关键：handler 里没有任何函数调用（除了保存/恢复 errno，那是纯寄存器操作），因此 100% 安全。所有实质工作都在主流程完成。

问 2：如果必须在 handler 里输出诊断信息，怎么做才安全？

用 write(2)，不用 printf：

static void handler(int sig)
{
    /* 方案 1：固定字符串 */
    const char m[] = "caught signal\n";
    write(STDERR_FILENO, m, sizeof m - 1);      /* write 是 async-signal-safe */

    /* 方案 2：需要格式化时，预先格式化好或用极简转换 */
    char buf[32];
    char *p = buf + sizeof buf - 1;
    *p-- = '\n';
    int n = sig;
    do { *p-- = '0' + (n % 10); n /= 10; } while (n);
    p++;
    write(STDERR_FILENO, "sig=", 4);
    write(STDERR_FILENO, p, (buf + sizeof buf) - p);
}

为什么不用 printf：

  • printf 内部持有 stdio 锁
  • 主流程正 printf 持锁时信号递送 → handler 再 printf → 同一线程重入同一把锁 → 死锁
  • 即便不死锁，也可能破坏 stdio 缓冲区链表

注意 snprintf：很多代码在 handler 里用 snprintf 格式化，它不在 POSIX 异步信号安全清单里（glibc 实现中可能分配内存）。实践中通常可用，但严格来说不安全。

更稳妥的方案：

  1. handler 只把 sig 存进 volatile sig_atomic_t，主流程再格式化输出
  2. 用 self-pipe / eventfd 把信号转到主流程
  3. 用 signalfd，完全没有 handler
问 3：备用栈设置好了但没设 SA_ONSTACK，会怎样？

备用栈不会被使用——handler 仍在原栈上执行，栈溢出时照样无法工作。

两个步骤语义不同：

调用 作用
sigaltstack(&ss, NULL) 向内核登记"有一块备用栈可用"
sa_flags = SA_ONSTACK 告诉内核"处理这个信号时请切换到备用栈"

粒度：SA_ONSTACK 是每个信号独立的。可以只让 SIGSEGV 用备用栈，其他信号仍在原栈执行——这正是常见做法（只有崩溃诊断需要备用栈）。

stack_t ss = { .ss_sp = buf, .ss_size = SIGSTKSZ * 4, .ss_flags = 0 };
sigaltstack(&ss, NULL);                    /* ① 登记 */

struct sigaction sa = {0};
sa.sa_sigaction = segv_handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;     /* ② SA_ONSTACK 不可少 */
sigaction(SIGSEGV, &sa, NULL);

验证方法：查询备用栈状态，或在 handler 里查询：

stack_t oss;
sigaltstack(NULL, &oss);
if (oss.ss_flags & SS_ONSTACK)
    /* 确实运行在备用栈上 */
问 4：本章讲了四种终止方式，怎么选？

决策流程：

handler 中要终止进程？
  ├─ 需要 core dump 供 gdb 分析？
  │    ├─ 是 → abort()（固定 SIGABRT + core，且无法被 handler 拦截）
  │    └─ 是，且要保留原信号类型 → 恢复 SIG_DFL + raise(sig)
  └─ 不需要 core，只想快速安全退出
       └─ _exit(status)
方式 特点
_exit() 默认选择。异步信号安全、无锁、无 I/O、立即退出
abort() 需要 core dump。会先解除 SIGABRT 阻塞，保证一定生效
re-raise 需要让父进程 wait() 看到 WIFSIGNALED（区分"被杀"与"自退"）
exit() ❌ 绝不用——非异步信号安全，可能死锁

HFT 建议：

  • 崩溃路径用 re-raise（WIFSIGNALED 语义让监控能区分事故类型）
  • 正常停机用 _exit()
  • 诊断信息平时就落盘（无锁环形队列 + 独立日志线程），崩溃时刻的任何 I/O 都可能因锁状态未知而死锁
问 5：从更高层面看，本章的技巧都是在"绕开"handler 的限制。有没有根本性的解法？

有——根本不用 handler。 本章讲的所有技巧（只设标志、只用安全函数、保护 errno）都是在规避 handler 的固有缺陷。更好的架构是让信号根本不进入 handler：

方案 机制 消灭了什么问题
signalfd 阻塞信号 + signalfd() 拿 fd + epoll 监听 完全无 handler → 无异步信号安全、无抢占、无延迟毛刺
sigwaitinfo 阻塞信号 + 专用线程同步取 无 handler，且由固定线程处理，行为可预测
eventfd / self-pipe handler 只 write 一字节，主流程监听 handler 极简化到只剩一次 write

对比：

传统 handler signalfd
异步抢占关键路径 ✅ 会 ❌ 不会
异步信号安全限制 ✅ 有 ❌ 无
可调用 printf/malloc ❌ ✅
能接入 epoll 事件循环 ❌（需 self-pipe） ✅ 原生
信号丢失 标准信号会合并 ❌ 不丢（内核队列）
延迟可预测性 ❌ ✅

HFT 结论：交易系统的关键路径应全程屏蔽无关信号，控制信号（停机、配置重载）走 signalfd 进事件循环。handler 只作为 SIGSEGV 崩溃诊断的兜底设施，并配 SA_ONSTACK 备用栈。

练习 1：signal() vs sigaction() —— 为什么必须弃用前者

题目：下面两段代码看起来效果相同，为什么生产代码必须用后者？

/* A */
signal(SIGINT, handler);

/* B */
struct sigaction sa = {0};
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;
sigaction(SIGINT, &sa, NULL);
参考答案

signal() 的行为随实现而变，不可移植：

语义 是否自动复位为 SIG_DFL handler 期间是否阻塞同号信号
System V ✅ 复位 ❌ 不阻塞
BSD 4.3+ ❌ 不复位 ✅ 阻塞

两派截然相反。

Linux 内核的 sys_signal 固定采用 SVr4 风格（kernel/signal.c:4628 硬编码 SA_ONESHOT | SA_NOMASK），而 glibc 的 signal() 包装却走 rt_sigaction + SA_RESTART 模拟 BSD——同一台 Linux 上，用不用 libc 包装结果都不一样。

sigaction() 额外提供的能力：

能力 signal() sigaction()
SA_RESTART（自动重启被中断的 syscall） ❌ ✅
sa_mask（handler 期间额外屏蔽） ❌ ✅
SA_SIGINFO（获取 siginfo_t） ❌ ✅
SA_ONSTACK（备用栈） ❌ ✅
SA_RESETHAND（一次性，显式） ❌ ✅

结论：signal() 只适合 demo 或一键 SIG_IGN；生产代码一律 sigaction()。

练习 2：找出这段代码里的所有问题

题目：下面的信号处理器有几处错误？逐一指出并修正。

int counter = 0;
char logbuf[256];

void handler(int sig) {
    printf("received signal %d\n", sig);
    sprintf(logbuf, "sig=%d", sig);
    int fd = open("/tmp/sig.log", O_APPEND | O_WRONLY);
    write(fd, logbuf, strlen(logbuf));
    close(fd);
    counter++;
    exit(0);
}
参考答案

六处问题：

# 问题 原因 修正
1 printf() 非 async-signal-safe，持有 stdio 锁 → 同一线程重入死锁 用 write(2) 或移到主流程
2 sprintf() 同 printf，stdio 锁 不用，或手工极简转换
3 open() / close() 不在安全清单；open 可能分配内存 移到主流程，或预先打开 fd
4 counter++ ① 缺 volatile → 主流程看不到修改
② 缺 sig_atomic_t → 非原子
③ ++ 是读-改-写，即便原子类型也不安全		 volatile sig_atomic_t flag = 1;（只做赋值）
5 exit() 非 async-signal-safe，会 flush stdio + 跑 atexit → 死锁 _exit() / _Exit()
6 logbuf 全局数组 handler 与主流程共享，无保护 改为局部变量或不用

修正版：

static volatile sig_atomic_t got_signal = 0;
static volatile sig_atomic_t last_signo = 0;

static void handler(int sig)
{
    int saved_errno = errno;        /* 保护 errno */
    got_signal = 1;                 /* 只做原子赋值 */
    last_signo = sig;
    errno = saved_errno;
}

/* 主流程：所有复杂操作都在这里，可随意 printf/open/exit */
int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sigaction(SIGINT, &sa, NULL);

    for (;;) {
        if (got_signal) {
            printf("received signal %d\n", (int)last_signo);   /* 安全 */
            got_signal = 0;
            /* open/write/close 都可以在这里做 */
        }
        do_work();
    }
}

练习 3：让进程"被信号杀死"而非"自己退出"

题目：程序捕获 SIGTERM 后想退出，但希望父进程 wait() 时看到的是 WIFSIGNALED（被信号杀死）而不是 WIFEXITED。怎么做？

参考答案

用「恢复默认处置后重新发信号」技巧：

static void handler(int sig)
{
    /* 1. 最小诊断（用 async-signal-safe 的 write） */
    const char m[] = "caught SIGTERM, re-raising\n";
    write(STDERR_FILENO, m, sizeof m - 1);

    /* 2. 恢复默认处置 */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);

    /* 3. 重新发同一个信号 → 走默认动作 */
    raise(sig);

    /* 4. 兜底：若信号被阻塞未能立即递送，强制退出 */
    _exit(128 + sig);
}

效果对比：

写法 父进程 wait() 看到
_exit(1) WIFEXITED=true, status=1 —— 看不出是被信号杀的
re-raise WIFSIGNALED=true, WTERMSIG=SIGTERM ✅

原理：raise(sig) 时 disposition 已恢复为 SIG_DFL，内核在 get_signal() 中走致命分支——do_coredump()（若该信号产 core）+ do_group_exit(signo)（kernel/signal.c:2878/:2892）。

第 4 步为什么必要：若该信号在 handler 执行期间被阻塞（例如 sa_mask 里有它，或自身信号自动阻塞尚未解除），raise 只会让它 pending 而不立即递送。此时 _exit(128+sig) 保证进程一定退出——128+sig 是 shell 表示"被信号 N 杀死"的惯例值。

练习 4：EINTR 的正确处理

题目：下面两段 read 调用，在注册了信号处理器后各有什么问题？

/* A：什么都不处理 */
ssize_t n = read(fd, buf, sizeof buf);
if (n < 0) { perror("read"); return -1; }

/* B：盲目重试 */
ssize_t n;
do {
    n = read(fd, buf, sizeof buf);
} while (n < 0);
参考答案

A 的问题：read 被信号中断时返回 -1 且 errno == EINTR，这不是真正的错误。直接 perror 并退出会导致偶发的、不可复现的失败——慢设备 I/O（终端、管道、socket）上尤其常见。

B 的问题：把所有错误都当"可重试"，包括：

  • EAGAIN（非阻塞无数据）→ 忙等烧 CPU
  • EBADF（fd 无效）、EIO（硬件错误）→ 无限死循环

正确写法：只重试 EINTR，其他错误区分处理：

ssize_t n;
do {
    n = read(fd, buf, sizeof buf);
} while (n == -1 && errno == EINTR);        /* 只重试 EINTR */

if (n == -1) {
    if (errno == EAGAIN || errno == EWOULDBLOCK)
        return 0;                            /* 无数据 → 回事件循环，不重试 */
    return -1;                               /* 真错误 */
}
/* 处理数据 */

设了 SA_RESTART 还需要这样写吗？

需要。以下调用即便设了 SA_RESTART 仍然返回 EINTR：

类别 例子
带超时 select、poll、epoll_wait、sigtimedwait
网络连接 connect
定时 nanosleep（剩余时间写入 rem）
Linux 特有 close（fd 已关闭，不要重试）

nanosleep 的完整处理：

struct timespec rem = req;
while (nanosleep(&rem, &rem) == -1 && errno == EINTR)
    ;                       /* rem 已被更新为剩余时间，继续睡 */

练习 5：栈溢出的崩溃诊断

题目：程序有无限递归的风险。希望能在崩溃时打印故障地址，而不是进程直接消失。怎么做？

参考答案

核心是三件事：备用栈 + SA_SIGINFO + si_addr。

#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

static void segv_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)sig; (void)ctx;
    /* 运行在备用栈上，原栈已毁但这里干净 */
    char buf[256];
    const char *reason =
        (info->si_code == SEGV_MAPERR) ? "地址未映射（野指针/已释放）" :
        (info->si_code == SEGV_ACCERR) ? "权限不足（写只读页）" : "其他";
    int n = snprintf(buf, sizeof buf,
        "SIGSEGV @ %p : %s (si_code=%d)\n", info->si_addr, reason, info->si_code);
    write(STDERR_FILENO, buf, n);
    _exit(1);
}

int main(void)
{
    /* ① 登记备用栈 */
    stack_t ss;
    ss.ss_sp = malloc(SIGSTKSZ * 4);          /* ≥32KB，别用 MINSIGSTKSZ */
    ss.ss_size = SIGSTKSZ * 4;
    ss.ss_flags = 0;
    sigaltstack(&ss, NULL);

    /* ② 关键：SA_ONSTACK + SA_SIGINFO */
    struct sigaction sa = {0};
    sa.sa_sigaction = segv_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigaction(SIGSEGV, &sa, NULL);

    /* ③ 触发栈溢出 */
    recurse_forever();
}

三个要点：

要点 原因
sigaltstack() + SA_ONSTACK 栈溢出时原栈无空间，handler 无法执行 → 内核 force_sigsegv() 直接杀进程（kernel/signal.c:2935）
栈要够大（≥32KB） 太小会通不过内核检查（-ENOMEM）或搭不起 sigframe（→ force_sigsegv）
_exit() 而非 exit() exit() 非 async-signal-safe，可能死锁

为什么 snprintf 可以用：严格说它不在安全清单，但运行在干净的备用栈上且不涉及 stdio 流的锁（只格式化到局部 buf），实践上可接受。更严格的做法是手工转换或直接用 write 输出固定串。

对照实验：去掉 SA_ONSTACK，栈溢出时 handler 无法执行，进程裸死，看不到任何诊断输出。

/* sigmod.c —— 生产级信号处理骨架
 * 要点：signalfd 消灭 handler + SIGSEGV 兜底诊断 + 屏蔽无关信号
 * 编译: gcc -D_GNU_SOURCE -o sigmod sigmod.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/signalfd.h>
#include <sys/epoll.h>

/* ── SIGSEGV 兜底：运行在备用栈上 ── */
static void segv_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)sig; (void)ctx;
    char buf[128];
    int n = snprintf(buf, sizeof buf,
                     "FATAL SIGSEGV @ %p (si_code=%d)\n",
                     info->si_addr, info->si_code);
    write(STDERR_FILENO, buf, n);
    _exit(128 + SIGSEGV);          /* 兜底退出 */
}

static void setup_crash_handler(void)
{
    stack_t ss;
    ss.ss_sp = malloc(SIGSTKSZ * 4);
    ss.ss_size = SIGSTKSZ * 4;
    ss.ss_flags = 0;
    sigaltstack(&ss, NULL);

    struct sigaction sa = {0};
    sa.sa_sigaction = segv_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGBUS,  &sa, NULL);
}

int main(void)
{
    setup_crash_handler();                    /* ① 崩溃诊断兜底 */

    /* ② 阻塞所有控制信号 —— 它们将走 signalfd，不进 handler */
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);
    sigaddset(&mask, SIGTERM);
    sigaddset(&mask, SIGHUP);
    sigprocmask(SIG_BLOCK, &mask, NULL);

    /* ③ 信号变 fd */
    int sfd = signalfd(-1, &mask, SFD_NONBLOCK);

    /* ④ 加入 epoll，与业务 I/O 一起等待 */
    int epfd = epoll_create1(0);
    struct epoll_event ev = { .events = EPOLLIN, .data.fd = sfd };
    epoll_ctl(epfd, EPOLL_CTL_ADD, sfd, &ev);

    printf("PID=%d — 试 kill -TERM %d 或 kill -INT %d\n",
           getpid(), getpid(), getpid());

    int running = 1;
    while (running) {
        struct epoll_event events[8];
        int n = epoll_wait(epfd, events, 8, -1);

        for (int i = 0; i < n; i++) {
            if (events[i].data.fd == sfd) {
                struct signalfd_siginfo si;
                while (read(sfd, &si, sizeof si) == sizeof si) {
                    /* 这里是普通上下文 —— 可随意 printf/malloc/写日志 */
                    printf("收到信号 %d (来自 pid=%d)\n",
                           si.ssi_signo, si.ssi_pid);
                    if (si.ssi_signo == SIGTERM || si.ssi_signo == SIGINT)
                        running = 0;
                }
            }
        }
    }

    printf("优雅退出\n");
    close(sfd);
    close(epfd);
    return 0;
}
