章节目标

  • 分清「名字」与「本体」两个层次：目录项/路径串是名字，inode 是本体。link/unlink/rename 全是目录表操作——unlink 只摘名字（实测：名字全没了 fd 还能读回数据，close 才释放）、rename 原子换名（实测：inode 不变）
  • 三种「覆盖/替换」语义：unlink+open（有竞态窗口）、rename（原子替换，safe-write 的根）、cc 覆盖运行中的程序（= rename 换 inode，老 inode 被 fd 吊住——习题 18-1 完整实测）
  • 目录是一等公民但有独立规则：r/w/x 三位含义完全不同于文件（实测：st_nlink = 2 + 子目录数）；rmdir 只吃「只剩 ./..」的目录；指向目录的符号链接要用 unlink 删（rmdir 报 ENOTDIR）
  • 遍历的正确姿势：readdir 返回 NULL 要查 errno（否则 I/O 错误被当「读完」→ 备份工具丢数据）；nftw 递归删除必须 FTW_DEPTH|FTW_PHYS（实测：不加 FTW_PHYS 指向目录的链接会让子树被遍历两次）
  • 消除 cwd 全局状态：*at() 族把基准从进程属性变成一个 fd——锚点打开即固定，TOCTOU 与多线程竞争一起消掉；「记住老目录」用 open(".") + fchdir（fd 方案免疫改名/删除，习题 18-9 正解）
  • 诚实：本轮实测纠正了两处旧结论——① macOS 与 Linux 的 rename 目录规则一致（此前笔记怀疑有差异，实测证伪）；② 「macOS 不 enforce ETXTBSY」必须用自编译长跑程序验证（拷贝的系统二进制会被代码签名 SIGKILL，rc=137，此前测试无效）

18.1

Directories and (Hard) Links 目录与（硬）链接

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 stat(2) / link(2) / unlink(2) + TLPI dist dirs_links/ + 官方目录 toc-detailed.html（18.1–18.16 逐条对齐） - 上一节：本章首页 - 下一节：18.2 Symbolic (Soft) Links 符号链接

本节讲什么

TLPI 第 18 章的「地基节」。本节回答四个问题：

  1. 目录到底是不是文件？它的「内容」是什么？
  2. 硬链接的本质是什么？（一句话：同一 inode 的第二个名字）
  3. 目录的 r / w / x 三位为什么含义完全不同于普通文件？
  4. st_nlink 从 2 开始数的是谁？（不是「被链接的次数」）

要点：目录是「名字 → inode」的映射表

普通文件 目录
数据块存内容 数据块存目录项（directory entry）：(文件名, inode 编号)
st_size = 内容字节数 st_size 的含义由文件系统决定（见下）
st_nlink = 被硬链接次数 st_nlink = 2 + 子目录数（自己 + . + 各子目录的 ..）

两个方向都可以反过来说：

  • 一个 inode 可以有多个名字（硬链接），但一个目录项只指向一个 inode；
  • . 和 .. 不是「特殊语法」，它们就是目录里实实在在的两条目录项——所以 .. 能用 .. 访问，根目录的 .. 指向自己（防止向上走到表外）。

实测：st_nlink 的真实算法

完整源码（code/c18_6_mkdir_rmdir.c）：

/* c18_6_mkdir_rmdir.c — Ch18 §18.6：mkdir() / rmdir() 的真实语义
 *
 * 钉住的点（全部实测）：
 *   ① mkdir() 的 mode **受 umask 削减**（与 open 同一套规则），
 *      且目录必定带上 x 位才有用（没有 x 连 cd 都进不去）；
 *   ② 目录的 st_nlink 不是「被链接次数」而是 **2 + 子目录数**：
 *      自己一条、"." 一条，每个子目录的 ".." 再各算一条；
 *   ③ rmdir() 只吃**空目录**：非空 ENOTEMPTY、指向文件的 ENOTDIR、
 *      指向目录的**符号链接**也是 ENOTDIR（要用 unlink 删链接本身）；
 *   ④ rmdir(".") / rmdir("..") → EINVAL/EBUSY，内核不许把树上节点摘断；
 *   ⑤ unlinkat(dirfd, name, AT_REMOVEDIR) 是 rmdir 的 *at 版本（§18.11）。
 *
 * 编译： cc -Wall -Wextra -o c18_6_mkdir_rmdir c18_6_mkdir_rmdir.c
 * 取材： man-pages 6.19 mkdir(2)/rmdir(2) + TLPI §18.6
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>

static void try_mkdir(const char *p, mode_t mode, const char *tag)
{
    errno = 0;
    int r = mkdir(p, mode);
    printf("  %-42s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

static void try_rmdir(const char *p, const char *tag)
{
    errno = 0;
    int r = rmdir(p);
    printf("  %-42s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

int main(void)
{
    const char *base = "/tmp/tlpi_c18_6";
    char d[128], sub[160], f[160], lnk[160];
    snprintf(d,   sizeof d,   "%s/d",     base);
    snprintf(sub, sizeof sub, "%s/d/sub", base);
    snprintf(f,   sizeof f,   "%s/d/f",   base);
    snprintf(lnk, sizeof lnk, "%s/d_lnk", base);
    system("rm -rf /tmp/tlpi_c18_6 && mkdir /tmp/tlpi_c18_6");

    /* ---------- ① mode & umask ---------- */
    printf("== ① mkdir 的 mode 受 umask 削减 ==\n");
    mode_t old = umask(0);                       /* 先读出当前 umask */
    umask(old);
    printf("  当前 umask = %04o\n", (unsigned) old);
    try_mkdir(d, 0777, "mkdir(d, 0777)");
    struct stat sb;
    stat(d, &sb);
    printf("  实得 mode = %04o（= 0777 & ~%04o）\n",
           (unsigned) (sb.st_mode & 07777), (unsigned) old);

    /* ---------- ② st_nlink 的算法 ---------- */
    printf("\n== ② 目录的 st_nlink = 2 + 子目录数 ==\n");
    stat(d, &sb);
    printf("  空目录 d          st_nlink = %ld   ← 自己\n",
           (long) sb.st_nlink);
    mkdir(sub, 0755);
    stat(d, &sb);
    printf("  建 d/sub 之后 d   st_nlink = %ld   ← +子目录的 \"..\"\n",
           (long) sb.st_nlink);
    printf("  ⚠️ d/sub 自己的 st_nlink = ");
    stat(sub, &sb);
    printf("%ld（新建空目录恒为 2）\n", (long) sb.st_nlink);

    /* ---------- ③ rmdir 的失败面 ---------- */
    printf("\n== ③ rmdir 只吃空目录 ==\n");
    int fd = open(f, O_WRONLY | O_CREAT | O_EXCL, 0644);
    if (fd == -1) { perror("open"); return EXIT_FAILURE; }
    close(fd);
    try_rmdir(d, "rmdir(非空 d)");
    try_rmdir(f, "rmdir(普通文件)");
    symlink(d, lnk);
    try_rmdir(lnk, "rmdir(指向目录的符号链接)");
    printf("  → 删链接本身请用 unlink；rmdir 只跟到底层对象的类型\n");

    try_rmdir(".", "rmdir(\".\")");
    try_rmdir("..", "rmdir(\"..\")");

    /* ---------- ④ *at 版本 ---------- */
    printf("\n== ④ unlinkat(AT_REMOVEDIR) == rmdir ==\n");
    int dfd = open(d, O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open dir"); return EXIT_FAILURE; }
    char *slash = strrchr(f, '/');
    errno = 0;
    int r = unlinkat(dfd, slash + 1, 0);              /* 0 = 删文件 */
    printf("  unlinkat(dfd, \"%s\", 0)             = %d %s\n",
           slash + 1, r, r == 0 ? "" : strerror(errno));
    errno = 0;
    r = unlinkat(dfd, "sub", AT_REMOVEDIR);           /* 删空目录 */
    printf("  unlinkat(dfd, \"sub\", AT_REMOVEDIR)   = %d %s\n",
           r, r == 0 ? "" : strerror(errno));
    close(dfd);

    /* ---------- ⑤ mkdir 的存在/父目录检查 ---------- */
    printf("\n== ⑤ mkdir 的前置检查（都是内建原子性，不是先 stat 再建）==\n");
    try_mkdir(d, 0755, "mkdir(已存在的 d)");
    try_mkdir("/tmp/tlpi_c18_6/no/such/parent", 0755, "mkdir(父目录不存在)");

    /* 清理 */
    unlink(lnk);
    try_rmdir(d, "rmdir(空 d)  ← 现在可以了");
    rmdir(base);
    return EXIT_SUCCESS;
}

实测输出：

== ② 目录的 st_nlink = 2 + 子目录数 ==
  空目录 d          st_nlink = 2   ← 自己
  建 d/sub 之后 d   st_nlink = 3   ← +子目录的 ".."
  ⚠️ d/sub 自己的 st_nlink = 2（新建空目录恒为 2）

交叉验证：本机 stat("/tmp") 实测 st_nlink=61（/tmp 里有 59 个子目录）——目录的 nlink 永远能被「子目录个数」解释，跟这个目录里有多少普通文件无关。

要点：目录的 r / w / x 是三件完全不同的事

位 普通文件 目录
r 读内容 列出目录项（见得到名字）
x 执行 穿过 / 解析路径（访问内部文件必备）
w 写内容 增删改名目录项（mkdir / unlink / rename 都要它）

最反直觉的组合是「只有 r 没有 x」：能 ls 看到所有名字，却打不开其中任何一个（路径解析停在中间那一级）。反过来「只有 x 没有 r」：名字看不到，但如果你已经知道确切路径，照样能 open ——这正是 chmod 711 $HOME 的原理（别人进得来、列不出来）。

跨平台要点：Linux 的 ext4 / tmpfs 上目录 st_size 总是块大小的整数倍（新建空目录 4096），而 APFS 实测是 1952 / 960 这类非块对齐的真实字节数。结论：任何拿目录 st_size 做「目录内容大小」估算的代码都是错的——跨平台更错。要真算大小只能 nftw() 累加（见 §18.9）。

代码自测（Q&A）

Q1：目录和普通文件在内核层面差在哪？ A：都是 inode + 数据块。差别在数据块的解释方式：目录块被内核解析成 (文件名, inode#) 的定长/变长记录表（ext4 用 ext4_dir_entry_2），而普通文件块是裸字节。S_ISDIR(st_mode) 只是给了你一个「该怎么解释」的提示。

Q2：为什么目录的 st_nlink 最小是 2？ A：目录自己被父目录引用一次，再被自己的 . 引用一次。每新增一个子目录，那个子目录的 .. 又引用它一次，所以 +1。实测：空目录 2 → 建一个子目录变 3。

Q3：只有 r 没有 x 的目录，到底能干什么？ A：能 readdir 列出名字，不能解析路径进到里面的文件（open 报 EACCES）。所以「能看到名字」和「能访问内容」是两个独立权限。

Q4：APFS 上目录 st_size=1952，Linux 上为什么总是 4096 的倍数？ A：ext4 的目录按块组织，i_size 随块分配增长；APFS 的目录是 B-tree 记录，st_size 反映的是记录流的实际字节数。结论别依赖：目录大小从来不是 API 承诺过的量。

Q5：ls 和 ls -l 对目录权限的要求一样吗？ A：不一样。ls 只需 r（列名字）；ls -l 要 r + x（还要对每个条目 stat，得能穿过目录）。实测上「只有 r」的目录 ls 正常、ls -l 报权限错。

18.2

Symbolic (Soft) Links 符号链接

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 symlink(2) / readlink(2) / path_resolution(7) + Linux v6.6 fs/namei.c（max_links / ELOOP）+ TLPI dist dirs_links/view_symlink.c（Listing 18-4）、bad_symlink.c（习题 18-2 官方解） - 上一节：18.1 Directories and (Hard) Links - 下一节：18.3 Creating and Removing (Hard) Links

本节讲什么

符号链接是另一种东西，不是「另一种硬链接」：

  1. 它是一个独立 inode，数据块里存的是一段路径字符串；
  2. 创建时完全不检查目标——所以「悬空链接」是合法状态，不是错误；
  3. 相对目标的解析基准是链接所在目录，不是进程 cwd（习题 18-2 官方解钉的就是这个）；
  4. 内核在路径解析层用 ELOOP 防环——本机实测这个上限是40 层。

要点：硬链接 vs 符号链接（一张表定终身）

硬链接 符号链接
本质 同一 inode 的第二、三个名字 独立 inode，内容是路径串
跨文件系统 ❌ EXDEV ✅（存的是字符串，无所谓）
指向目录 ❌（用户态禁止，防环） ✅
目标被删后 数据仍在（还有别的名字） 悬空（dangling）
stat() 目标 跟随到目标（悬空则 ENOENT）
lstat() 目标 链接本身：S_ISLNK，st_size=路径串长度
创建 / 读取 link() / 无需 symlink() / readlink()

实测：悬空链接合法、lstat/stat/open 三种态度

完整源码（code/c18_3_symlink_readlink.c）：

/* c18_3_symlink_readlink.c — Ch18 §18.2/§18.5：符号链接的行为清单
 *
 * 钉住的点（全部实测）：
 *   ① symlink() 可以指向**不存在的路径**（悬空链接）——创建时不检查目标；
 *   ② 链接自身有 inode（lstat 见 15.1），st_size = 目标路径串长度；
 *   ③ readlink() 返回的是裸路径串（不带 NUL，size 是你给的缓冲上限）；
 *   ④ ELOOP：内核路径解析层限制链接层级（macOS 实测 40 层）；
 *   ⑤ 链接属主/权限有微妙的平台差异（macOS 实测 0777 + 属组继承目录）。
 *
 * 编译： cc -Wall -Wextra -o c18_3_symlink_readlink c18_3_symlink_readlink.c
 * 取材： man-pages 6.19 symlink(2)/readlink(2) + TLPI §18.2/§18.5（Listing 18-4 view_symlink.c）
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void)
{
    const char *dangling = "/tmp/tlpi_c18_3_dangling.lnk";
    const char *target = "/tmp/tlpi_c18_3_target.txt";
    unlink(dangling); unlink(target);

    /* ---------- ① 悬空链接 ---------- */
    printf("== ① symlink() 创建时不检查目标：悬空链接合法 ==\n");
    if (symlink("/no/such/path/ever.txt", dangling) == -1) {
        perror("symlink"); return EXIT_FAILURE;
    }
    struct stat sb;
    if (lstat(dangling, &sb) == -1) { perror("lstat"); return EXIT_FAILURE; }
    printf("  lstat(悬空链接): 类型=%s st_size=%ld（=目标路径串长度）\n",
           S_ISLNK(sb.st_mode) ? "symlink" : "?", (long) sb.st_size);
    errno = 0;
    int fd = open(dangling, O_RDONLY);
    printf("  open(悬空链接) = %d errno=%d(%s)——用的时候才爆\n",
           fd, errno, strerror(errno));
    errno = 0;
    int sr = stat(dangling, &sb);
    printf("  stat(悬空链接) = %d errno=%d(%s)\n", sr, errno, strerror(errno));

    /* ---------- ③ readlink 的裸字节串语义 ---------- */
    printf("\n== ③ readlink(): 裸路径串，不补 NUL ==\n");
    if (symlink(target, "/tmp/tlpi_c18_3_ok.lnk") == -1) { perror("symlink2"); return EXIT_FAILURE; }
    char buf[256];
    ssize_t n = readlink("/tmp/tlpi_c18_3_ok.lnk", buf, sizeof buf - 1);
    if (n == -1) { perror("readlink"); return EXIT_FAILURE; }
    buf[n] = '\0';                       /* 必须自己补 NUL */
    printf("  readlink = \"%s\" (%zd 字节，字符串长 %zu)\n", buf, n, strlen(buf));
    printf("  ⚠️ readlink 返回值是**写入的字节数**，不是字符串长——\n");
    printf("     超过缓冲会静默截断且无 NUL，必须按返回值处理。\n\n");

    /* ---------- ④ ELOOP ---------- */
    printf("== ④ 链接链：内核 ELOOP 保护 ==\n");
    char a[64], b2[64];
    snprintf(a, sizeof a, "/tmp/c18_3_loop_a");
    snprintf(b2, sizeof b2, "/tmp/c18_3_loop_b");
    unlink(a); unlink(b2);
    symlink(b2, a);
    symlink(a, b2);                      /* 互指成环 */
    errno = 0;
    fd = open(a, O_RDONLY);
    printf("  open(互指环) = %d errno=%d(%s)\n", fd, errno, strerror(errno));
    if (fd != -1) close(fd);
    /* 数一数最多能串几层 */
    int depth = 0;
    char cur[64], next[64];
    snprintf(cur, sizeof cur, "/tmp/c18_3_chain_0");
    unlink(cur);
    symlink("/tmp/c18_3_chain_base", cur);
    for (depth = 1; depth < 200; depth++) {
        snprintf(next, sizeof next, "/tmp/c18_3_chain_%d", depth);
        unlink(next);
        if (symlink(cur, next) == -1) break;
        snprintf(cur, sizeof cur, "%s", next);
    }
    errno = 0;
    fd = open(next, O_RDONLY);
    int ok = (fd != -1);
    if (ok) close(fd);
    printf("  串 %d 层链接 open = %s（errno=%d %s）\n",
           depth, ok ? "OK" : "失败", errno, strerror(errno));
    printf("  → 解析上限是内核常量（macOS=40，Linux=40 SYMLOOP/8 MAXSYMLINKS 语义见 man）；\n");
    /* 清理链条 */
    for (int i = 0; i <= depth; i++) {
        snprintf(next, sizeof next, "/tmp/c18_3_chain_%d", i);
        unlink(next);
    }
    unlink(a); unlink(b2);

    /* ---------- ⑤ 属主/权限的平台差异 ---------- */
    printf("\n== ⑤ 链接自身的属主与权限（平台差异实测）==\n");
    if (lstat("/tmp/tlpi_c18_3_ok.lnk", &sb) == -1) { perror("lstat2"); return EXIT_FAILURE; }
    printf("  macOS 实测: uid=%ld gid=%ld mode=%lo（链接有自己的 mode=0777&~umask；\n"
           "     跟随打开时的权限判定用目标文件——链接 mode 本身无访问语义）\n",
           (long) sb.st_uid, (long) sb.st_gid, (unsigned long) (sb.st_mode & 07777));
    printf("  ⚠️ 书上/Linux：链接权限被忽略、属主影响删除权（sticky 目录）；\n");
    printf("     macOS(BSD) 给链接自己的 uid/gid/mode——别跨平台假设。\n");
    unlink("/tmp/tlpi_c18_3_ok.lnk");
    unlink(dangling);
    return EXIT_SUCCESS;
}

代码自测（Q&A）

Q1：符号链接的数据块里存的是什么？有没有可能是空的？ A：一段路径字符串（目标），NUL 结尾与否是文件系统私有细节，读的时候用 readlink 的返回值。st_size 就是这段串的长度。空串目标无法通过 symlink() 创建（symlink("", x) 返回 ENOENT）。

Q2：为什么说「悬空链接是合法状态」？系统不觉得矛盾吗？ A：链接 inode 的内容只是一段字符串，内核在 open 时才去解析它。解析失败给 ENOENT，但链接本身完好。这和 C 里「指针可以悬空」是同一个设计取向：把解析推迟到使用时。

Q3：硬链接指向目录为什么被禁？ A：防环。目录树若允许任意成环，.. 向上走、nftw 遍历、路径解析都可能不终止。内核内部有 ./.. 这两个特例，但用户态 link() 一律 EPERM。

Q4：ELOOP 的 40 是 POSIX 规定的吗？ A：不是。POSIX 只定义 ELOOP 这个错误，上限是实现的（Linux MAXSYMLINKS=40，macOS 实测也是 40）。写代码只能当作「有上限」，不能假设具体值。

Q5：lstat 看到的符号链接 st_uid 有什么用？ A：Linux 上几乎没有用（权限从不看它），只有 sticky 目录里「谁能删这个链接」会用到；macOS 上链接有自己的属主三元组。跨平台代码不要依赖。

Q6：怎么判断「一个链接是否悬空」？ A：lstat 成功 + stat 失败（ENOENT）。两步都做，缺一不可：只 stat 失败区分不了「链接本身不存在」和「链接在但目标没了」。

18.3

Creating and Removing (Hard) Links: link() and unlink() 创建与删除（硬）链接

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 link(2) / unlink(2) / unlinkat(2) + Linux v6.6 fs/namei.c（vfs_link/vfs_unlink）+ TLPI dist dirs_links/t_unlink.c（Listing 18-1） - 上一节：18.2 Symbolic (Soft) Links - 下一节：18.4 Changing the Name of a File: rename()

本节讲什么

本节把 §18.1 的概念落成两个 syscall，并把「删除」的真相讲清：

  1. link() 只是在目录表里加一行——所以「复制」「移动」「拷贝内容」这些词全都用错了；
  2. unlink() 删的也是目录表里的一行——所以「删除文件」这个词在 inode 还被 fd 吊住时是假的；
  3. nlink == 0 && 没有打开的 fd 才是真删除，这两个条件缺一不可；
  4. 「先 open 再 unlink」是全 Unix 最优雅的临时文件惯用法——竞态面为零。

要点：两个 syscall 的契约

#include <unistd.h>
int link(const char *oldpath, const char *newpath);
int linkat(int olddirfd, const char *oldpath,
           int newdirfd, const char *newpath, int flags);
int unlink(const char *pathname);
int unlinkat(int dirfd, const char *pathname, int flags);
规则 证据 / 错误码
oldpath 必须已存在 实测 ENOENT（见下）
newpath 不得存在（不存在「覆盖」语义，那要 rename） EEXIST
两者必须在同一文件系统 EXDEV（硬链接 = 同一 inode 的第二条目录项，inode 换了 FS 就无从谈起）
不能 link 目录 EPERM

{

    printf("  %-22s st_nlink=%ld\n", tag, (long) sb.st_nlink);
}

要点：「先 open 再 unlink」为什么竞态面为零

int fd = open(path, O_RDWR | O_CREAT | O_EXCL, 0600);
unlink(path);            /* 名字从这一刻起不存在于任何目录表 */
/* ... 用 fd 读写 ... */
close(fd);               /* 数据真正释放 */

对比传统「/tmp/myname.pid」式临时文件：其他进程可以在你 open 与 unlink 之间猜到那个名字并打开/篡改（TOCTOU）。而 open 后立刻 unlink，名字存在的窗口只有两条 syscall 之间，且之后从未有过——攻击面为零。glibc 的 tmpfile(3) 内部就是这么做的；mkstemp + unlink 是它的手动版。

代码自测（Q&A）

Q1：unlink 之后还能从 fd 读到数据吗？ A：能，而且能继续写。实测：unlink 后写入 15 字节，随后从同一 fd 读回 21 字节（含 unlink 前写的 6 字节）。inode 与 fd 的绑定在打开时就定了，unlink 只摘目录表里的名字。

Q2：st_nlink 变成 0 的瞬间数据就被释放了吗？ A：不是。还要没有任何打开的 fd。内核对 inode 的引用计数（i_count）与链接计数（i_nlink）是两个独立的东西；两者都归零，inode 才被回收到空闲表。

Q3：link() 为什么不能跨文件系统？ A：硬链接的本质是「同一 inode 的第二条目录项」。inode 编号只在单个文件系统内部有意义——你不可能在另一个 FS 里「引用」这个 FS 的 inode。所以内核在 vfs_link() 里直接 EXDEV。

Q4：O_EXCL 在这个惯用法里是必须的吗？ A：强烈建议。没有它，如果另一个进程恰好已经 open 了同一路径，你的 open 会拿到同一个 inode 的另一个 fd，随后 unlink + 写入就把对方的数据搅了。O_EXCL 保证「这个 inode 是我刚建的、还没人见过」。

Q5：怎么在 Linux 上抢救「刚被删但还有进程开着」的文件？ A：/proc/PID/fd/N 是那个 fd 的符号链接，指向「inode 还活着」的对象——可以 cp 出来。macOS 没有等价接口（lsof 只能告诉你谁开着）。这也是「救援要趁早」的原因：进程一退，fd 关闭，inode 才真正释放。

Q6：linkat(AT_FDCWD, ..., AT_EMPTY_PATH) 能对 fd 建链接吗？ A：Linux 特有（需要 CAP_DAC_READ_SEARCH 或配合 O_PATH + /proc/self/fd/N），macOS 无此能力。它把「先 open 再 unlink」的惯用法推进到「先 open 再 link 回来」，用于实现可恢复的临时文件。Pi5 复测清单里可以补一条。

Changing the Name of a File: rename() 改变文件的名字

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 rename(2) / renameat(2) / renameat2(2) + Linux v6.6 fs/namei.c（vfs_rename）+ TLPI dist dirs_links/ - 上一节：18.3 link() and unlink() - 下一节：18.5 symlink() and readlink()

本节讲什么

rename() 是全章唯一带「原子替换」语义的接口，也是「可靠写入」模式的根：

  1. 对已存在的目标文件：原子替换，任何时刻路径都指向一个完整的老文件或完整的新文件；
  2. 对目录有一套独立规则（目标必须空、不能移进自己的子树、不能改 ..）；
  3. 它不换 inode——换的是目录项，所以文件时间戳/数据都不动；
  4. 同一文件系统内 O(1)（只改目录表）；跨 FS 直接 EXDEV，不存在「自动帮你复制」。

要点：契约表

#include <stdio.h>          /* 注意：stdio.h，不是 unistd.h */

#include <fcntl.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, ..., unsigned int flags);  /* Linux 3.15+ 专有 */
oldpath newpath 不存在 newpath 是文件 newpath 是空目录 newpath 是非空目录
文件 改名 原子替换 EISDIR EISDIR
目录 改名 ENOTDIR 整体搬过去 ENOTEMPTY

另两条独立规则：newpath 不能是 oldpath 的子路径（EINVAL，否则造出不可达的环）；.. 不能被改名（EINVAL）。

 *   ② rename 对目录：目标必须是空目录；目录到文件（或反之）→ EISDIR/ENOTDIR；
 *   ③ 目录的 ".." 不可改、不能把目录移到自己子树里（EINVAL/EBUSY）；
 *   ④ rename 不换 inode（15.2 实测过：Linux 不动文件时间戳）；
 *   ⑤ 同文件系统内 O(1)（改目录项），跨 FS 会 EXDEV（内核搬数据，不原子）。
 *

static int try_rename(const char *oldp, const char *newp, const char *tag)

    errno = 0;

int main(void)
{
    const char *dir = "/tmp/tlpi_c18_2";
    char a[128], b[128], d1[128], d2[128];
    snprintf(a, sizeof a, "%s/a.txt", dir);
    snprintf(b, sizeof b, "%s/b.txt", dir);
    snprintf(d1, sizeof d1, "%s/dir1", dir);
    snprintf(d2, sizeof d2, "%s/dir2", dir);
    system("rm -rf /tmp/tlpi_c18_2 && mkdir /tmp/tlpi_c18_2");

    /* ---------- ① 原子替换 ---------- */
    printf("== ① rename(file, 存在的 file)：原子替换 ==\n");
    int fd = open(a, O_RDWR | O_CREAT | O_EXCL, 0644);
    if (fd == -1) { perror("open"); return EXIT_FAILURE; }
    write(fd, "NEW CONTENT\n", 12);
    close(fd);
    fd = open(b, O_RDWR | O_CREAT | O_EXCL, 0644);
    if (fd == -1) { perror("open2"); return EXIT_FAILURE; }
    write(fd, "OLD\n", 4);
    close(fd);
    try_rename(a, b, "rename(a → 已存在的 b)");

    int rfd = open(b, O_RDONLY);
    ssize_t n = read(rfd, buf, sizeof buf);
    printf("  b 现在的内容: \"%.*s\"（b 的旧内容被整体替换，无中间态）\n",
           (int) n, buf);

           (unsigned long) s1.st_ino);

    printf("== safe-write 惯用法 ==\n");
    printf("  写配置 → 写到 temp → fsync → rename(temp, 配置) →\n");
    printf("  读者永远看到完整旧版或完整新版；崩溃也不会留下半截文件。\n\n");

    try_rename(inner, d2, "rename(文件 → 目录)");
    try_rename(d2, inner, "rename(目录 → 文件)");
    try_rename(d1, d2, "rename(空 dir1 → 非空 dir2)");
    try_rename(d2, d1, "rename(非空 dir2 → 空 dir1)");   /* 此时 d2 已消失 */

    /* 目录进自己的子树：必须 EINVAL（否则会造出不可达的环） */
    char sub[160];
    snprintf(sub, sizeof sub, "%s/sub", d1);
    try_rename(d1, sub, "rename(dir1 → dir1/sub 自己的子树)");
    /* ".." 不能被 rename 改写 */
    char dotdot[160];
    snprintf(dotdot, sizeof dotdot, "%s/..", d1);
    try_rename(d1, dotdot, "rename(dir1 → dir1/..)");

    /* 清理 */
    unlink(inner); rmdir(d1); rmdir(d2);
    unlink(b);
    rmdir(dir);
    return EXIT_SUCCESS;
}

三个值得停下来的点：

  • inode 未变（2277517）：替换后 b 还是老 a 的 inode。也就是说 rename 不搬数据，只改了两个目录表里的行。这与 §15.2 实测「rename 不动文件时间戳」互相印证。
  • 目录四条全部与 Linux 一致：本机实测的 EISDIR / ENOTDIR / ENOTEMPTY 与 man-pages rename(2) 逐条对上（这是本轮升级专门核对过的——早前笔记曾怀疑 macOS 与 Linux 在目录覆盖上有差异，实测证伪：两边语义一致）。
  • 两条 EINVAL：不能把目录移进自己的子树、不能改 ..。第一条是防止「目录变成自己的后代」，否则 nftw、find、.. 链全部失效。

/* 2. 原子替换——读者要么看到完整旧版，要么看到完整新版 */

实测：rename 换 inode 的另一个证据（习题 18-1）

完整源码（code/ex18_1_txtbsy.c）：

/* ex18_1_txtbsy.c — 习题 18-1：正在执行的程序为什么还能被「覆盖」？
 *
 * 题面（原书 §18 习题 18-1，按转述）：§4.3.2 说「文件正在被执行时不能以写方式
 * 打开（open 返回 -1，errno=ETXTBSY）」。但从 shell 里却可以：
 *     cc -o longrunner longrunner.c
 *     ./longrunner &                 # 后台留着跑
 *     vi longrunner.c                # 改源码
 *     cc -o longrunner longrunner.c  # 这条居然成功！
 * 为什么？（提示：两次编译后用 ls -li 看可执行文件的 i-node。）
 *
 * 答案（②③④三部分钉住）：
 *   ③ 直接以 O_WRONLY 打开**正在执行**的二进制 → Linux 拒（ETXTBSY）；
 *   ④ cc 的「覆盖」根本没写老文件，而是**建新 inode + rename 换目录项**：
 *      rename 成功、inode 号变了，而老 inode 被运行中进程的 fd 吊住
 *      （回到 §18.3：nlink 归零且无 fd 才真删）。所以「覆盖」安全，
 *      正在跑的程序用的仍是老那份数据。
 *
 * ⚠️ ⓪ 是本程序特意保留的「踩坑自证」环节，别删：
 *   最初长跑程序是 `cp /bin/sleep /tmp/prog` 造的，结果子进程**瞬间就退**——
 *   macOS 代码签名（AMFI/taskgated）会 SIGKILL 掉「离开原位置的平台二进制」
 *   （实测 rc=137 = 128+SIGKILL）。那样测出的「open 成功」只证明「打开了一个
 *   没在运行的文件」，结论完全无效。所以长跑程序改为**拷自己编译的二进制**。
 *
 * 编译： cc -Wall -Wextra -o ex18_1_txtbsy ex18_1_txtbsy.c
 * 取材： TLPI §4.3.2 / §18.1 / §18.3 / 习题 18-1；man-pages 6.19 open(2)(ETXTBSY)、rename(2)
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <signal.h>
#include <sys/wait.h>
#include <unistd.h>

#define PROG     "/tmp/ex18_1_longrunner"       /* 会被"覆盖"的可执行文件 */
#define PROG_NEW "/tmp/ex18_1_longrunner.new"   /* "重新编译"的产物 */
#define SYSCOPY  "/tmp/ex18_1_syscopy"          /* ⓪ 用的系统二进制副本 */

static ino_t ino_of(const char *p)
{
    struct stat sb;
    return stat(p, &sb) == 0 ? sb.st_ino : 0;
}

/* 三态探活：真的在跑 / 已退出 / 查询出错 */
static const char *probe(pid_t c)
{
    int st;
    errno = 0;
    pid_t w = waitpid(c, &st, WNOHANG);
    if (w == 0) return "仍在运行 ✔";
    if (w == c) return "已退出 ✘（子进程没跑住 → 本项测试无效）";
    return "waitpid 出错（ECHILD 等）";
}

/* 跑一小段以观察它是「正常退出」还是「被信号杀死」 */
static void exec_and_report(const char *prog, const char *tag)
{
    pid_t c = fork();
    if (c < 0) { perror("fork"); return; }
    if (c == 0) { execl(prog, prog, (char *) NULL); _exit(127); }
    int st;
    waitpid(c, &st, 0);
    if (WIFSIGNALED(st))
        printf("  %-22s 被信号杀死：SIG %d（rc=%d = 128+%d）\n",
               tag, WTERMSIG(st), 128 + WTERMSIG(st), WTERMSIG(st));
    else
        printf("  %-22s 正常退出 rc=%d\n", tag, WEXITSTATUS(st));
}

/* 子模式：被 exec 起来的长跑进程本体（也方便本程序自证「能跑住」）*/
static int child_mode(void)
{
    fprintf(stderr, "[longrunner] pid=%d 正在运行，sleep(20)\n", (int) getpid());
    sleep(20);
    return 0;
}

int main(int argc, char *argv[])
{
    if (argc > 1 && strcmp(argv[1], "--child") == 0)
        return child_mode();

    /* ---------- ⓪ 先演示那个坑：拷系统二进制 = 跑不起来 ---------- */
    printf("== ⓪ 陷阱预热：为什么长跑程序不能「拷」系统的 sleep ==\n");
    char cp[256];
    snprintf(cp, sizeof cp, "cp /bin/sleep %s 2>/dev/null && chmod 755 %s",
             SYSCOPY, SYSCOPY);
    if (system(cp) == 0) {
        exec_and_report(SYSCOPY, "cp /bin/sleep 的副本");
        printf("  → 平台签名二进制离开原位置即被 AMFI/taskgated 干掉。\n");
        printf("     若用它当长跑程序，子进程秒退 → 后面所有结论都是假的。\n");
        unlink(SYSCOPY);
    } else {
        printf("  （本机无 /bin/sleep，跳过此项）\n");
    }
    printf("  ✔ 正解：长跑程序拷**自己编译**的二进制（ad-hoc 签名可任意搬）。\n\n");

    /* ---------- 准备长跑程序：拷贝本程序自身 ---------- */
    unlink(PROG);
    snprintf(cp, sizeof cp, "cp %s %s", argv[0], PROG);
    if (system(cp) != 0) { perror("copy self"); return EXIT_FAILURE; }
    ino_t ino_before = ino_of(PROG);

    pid_t child = fork();
    if (child == -1) { perror("fork"); return EXIT_FAILURE; }
    if (child == 0) {
        execl(PROG, PROG, "--child", (char *) NULL);
        _exit(127);
    }
    sleep(1);                                  /* 等孩子进入 exec */

    printf("== ① 待测对象 ==\n");
    printf("  子进程 pid=%d 正在执行 %s（inode=%lu）\n",
           (int) child, PROG, (unsigned long) ino_before);
    printf("  探活：%s（若显示已退出，说明长跑程序没准备好，后面结论无效）\n",
           probe(child));

    printf("\n== ② 直接以写方式打开「正在执行」的二进制 ==\n");
    errno = 0;
    int fd = open(PROG, O_WRONLY);
    printf("  open(PROG, O_WRONLY) = %d errno=%d(%s)\n",
           fd, errno, fd == -1 ? strerror(errno) : "未置位");
    if (fd == -1)
        printf("  → 被拒。Linux 上此即 ETXTBSY(16)「Text file busy」。\n");
    else {
        printf("  → ⚠️ 本机 macOS(APFS) **不 enforce ETXTBSY**：正在执行的二进制\n");
        printf("     竟可被写打开（危险！）。Linux 上是 ETXTBSY(16)。跨平台务必单独验证。\n");
        close(fd);
    }

    printf("\n== ③ cc 的「覆盖」：建新 inode + rename，老 inode 被 fd 吊住 ==\n");
    snprintf(cp, sizeof cp, "cp %s %s", argv[0], PROG_NEW);   /* 冒充"重新编译的产物" */
    if (system(cp) != 0) { perror("copy new"); return EXIT_FAILURE; }
    printf("  「重新编译」产出 %s（inode=%lu）\n",
           PROG_NEW, (unsigned long) ino_of(PROG_NEW));
    errno = 0;
    int r = rename(PROG_NEW, PROG);            /* 就是 cc 落盘那一下 */
    printf("  rename(.new → 老名字) = %d %s\n", r, r == 0 ? "" : strerror(errno));
    printf("  覆盖后 PROG 的 inode = %lu  %s\n",
           (unsigned long) ino_of(PROG),
           ino_of(PROG) == ino_before ? "→ 没变（意外）"
                                      : "→ 已换成新 inode ✔（ls -li 可验证）");
    printf("  老 inode %lu 呢？", (unsigned long) ino_before);
    printf("  再次探活：%s\n", probe(child));
    printf("  ⇒ 所谓「覆盖正在执行的程序」= §18.4 的 rename 原子替换；\n");
    printf("     老 inode 因 nlink 归零但仍有 fd 而存活，直到进程退出（§18.3）。\n");

    printf("\n== ④ 子进程退出后再写打开 ==\n");
    int st;
    kill(child, SIGTERM);                      /* 不等 20 秒 */
    waitpid(child, &st, 0);
    errno = 0;
    fd = open(PROG, O_WRONLY);
    printf("  open(O_WRONLY) = %d errno=%d(%s)\n",
           fd, errno, fd == -1 ? strerror(errno) : "未置位");
    if (fd != -1) {
        printf("  → 成功。与 ② 对比：若 ② 为 ETXTBSY，这就是「忙 / 闲」的判据。\n");
        close(fd);
    }

    unlink(PROG); unlink(PROG_NEW);
    return EXIT_SUCCESS;
}

坑 正解
以为 rename 能跨文件系统 EXDEV；「跨 FS 移动」内核不提供原子接口，只能复制+删除（非原子）
safe-write 里忘了 fsync 掉电后 rename 落了、数据没落，配置文件变半截——比不写还糟

以为 rename 会更新文件 mtime 不会（15.2 实测：Linux 不动；macOS 会动 ctime——跨平台别当不变量）
多线程下两个线程各 rename 到同一路径 结果是「最后一次赢」，但每次都是原子的——不会出现半截状态；要有序就加锁或用唯一临时名
拿 rename 当「加锁」原语 rename 不报 EEXIST（直接覆盖）；互斥要么 link()（会 EEXIST）要么 O_CREAT\|O_EXCL

代码自测（Q&A）

Q1：rename 是「原子的」到底指什么？ A：指可见性——任何时刻，newpath 要么解析到完整的老文件、要么解析到完整的新文件，绝无「半新半旧」或「名字消失」的中间态。它不保证数据已落盘（那是 fsync 的事），也不保证并发 rename 的顺序。

Q2：为什么 rename(file, dir) 是 EISDIR 而 rename(dir, file) 是 ENOTDIR？两个不是一回事吗？ A：内核分两步检查：先看 oldpath 的类型能不能覆盖 newpath 的类型。文件→目录：目录不能被普通文件覆盖 → EISDIR（「newpath 是目录，而你给的是文件」）；目录→文件：目录不能被当文件写 → ENOTDIR。实测与 Linux 一致。

Q3：rename 同目录和跨目录有性能差吗？ A：同一 FS 内都是 O(1)（改几个目录项 + 移动 inode 的 parent 指针），跨目录只多一层目录的修改，量级不变。真正的分水岭是跨文件系统（EXDEV，必须复制）。

Q4：safe-write 为什么要先 fsync(fd) 再 rename？顺序能反吗？ A：不能反。rename 只是把目录项指向新 inode，这个操作自己会被 journal 记下；如果数据块还没落盘，掉电后 journal 回放可能得到「名字指向了新 inode，但新 inode 的数据块是垃圾」。先 fsync 保证数据先于名字可见。

Q5：renameat2 的 RENAME_EXCHANGE 是什么？ A：Linux 3.15+ 专有：原子互换两个路径（不是覆盖）。可以用来做「双缓冲目录」——但 macOS 没有，跨平台代码要留好降级路径。Pi5 复测清单可补一条实测。

Q6：用 rename 做进程间锁为什么是错的？ A：rename 的语义是「无条件覆盖」——两个进程同时 rename 同一目标，都会成功，锁形同虚设。正确的原子互斥用 link()（目标已存在则 EEXIST）或 open(O_CREAT|O_EXCL)；解锁用 unlink。

18.5

Working with Symbolic Links: symlink() and readlink() 操作符号链接

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 symlink(2) / readlink(2) / readlinkat(2) + TLPI dist dirs_links/view_symlink.c（Listing 18-4） - 上一节：18.4 rename() - 下一节：18.6 mkdir() and rmdir()

本节讲什么

§18.2 讲了符号链接是什么，本节讲怎么用——两个接口、四个必须钉住的细节：

  1. symlink() 创建时不检查目标（§18.2 已实测），但检查链接名本身（EEXIST）；
  2. readlink() 返回裸字节串：不补 NUL、不解析、返回值是「写入的字节数」；
  3. readlink 的语义陷阱：静默截断且无 NUL——最常见的崩溃源头；
  4. 原书 Listing 18-4 (view_symlink.c) 把 readlink 与 realpath 并排，一眼看出「裸串」和「解析结果」的差别。

要点：两个接口的契约

#include <unistd.h>
int symlink(const char *linkpath_target, const char *linkpath);
ssize_t readlink(const char *pathname, char *buf, size_t bufsiz);
ssize_t readlinkat(int dirfd, const char *pathname,
                   char *buf, size_t bufsiz);      /* POSIX.1-2008 */
项 规则 错误码（实测）
symlink 目标 不检查存在性，任何字符串都行（悬空合法） —
symlink 链接名 不得已存在 EEXIST
readlink 缓冲 按 bufsiz 上限写，不补 NUL 缓冲太小 → 静默截断，返回 bufsiz
readlink 返回值 写入的字节数（= lstat().st_size，若缓冲够大） 失败 -1
readlink 非链接 报错（它不跟随） EINVAL

readlink 的正确姿势（三行，缺一不可）：

char buf[PATH_MAX];
ssize_t n = readlink(path, buf, sizeof(buf) - 1);  /* 留 1 字节给 NUL */
if (n == -1) { /* 真出错：EINVAL=不是链接, ENOENT... */ }
buf[n] = '\0';                                     /* 自己补 NUL，n 是字节数不是长度 */

⚠️ 若 n == sizeof(buf)-1 说明可能被截断（目标串长度 ≥ 缓冲）。严谨实现应 lstat 拿 st_size 后分配 st_size+1 再读一次。

实测：readlink 的裸串语义

完整源码（code/c18_3_symlink_readlink.c）：

/* c18_3_symlink_readlink.c — Ch18 §18.2/§18.5：符号链接的行为清单
 *
 * 钉住的点（全部实测）：
 *   ① symlink() 可以指向**不存在的路径**（悬空链接）——创建时不检查目标；
 *   ② 链接自身有 inode（lstat 见 15.1），st_size = 目标路径串长度；
 *   ③ readlink() 返回的是裸路径串（不带 NUL，size 是你给的缓冲上限）；
 *   ④ ELOOP：内核路径解析层限制链接层级（macOS 实测 40 层）；
 *   ⑤ 链接属主/权限有微妙的平台差异（macOS 实测 0777 + 属组继承目录）。
 *
 * 编译： cc -Wall -Wextra -o c18_3_symlink_readlink c18_3_symlink_readlink.c
 * 取材： man-pages 6.19 symlink(2)/readlink(2) + TLPI §18.2/§18.5（Listing 18-4 view_symlink.c）
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void)
{
    const char *dangling = "/tmp/tlpi_c18_3_dangling.lnk";
    const char *target = "/tmp/tlpi_c18_3_target.txt";

   Demonstrate the use of readlink() and realpath() to read and display
   the contents of a symbolic link.

#include <sys/stat.h>
#include <limits.h>             /* For definition of PATH_MAX */
#include "tlpi_hdr.h"

#define BUF_SIZE PATH_MAX

int
main(int argc, char *argv[])
{
    struct stat statbuf;
    char buf[BUF_SIZE];
    ssize_t numBytes;

    if (argc != 2 || strcmp(argv[1], "--help") == 0)
        usageErr("%s pathname\n", argv[0]);

    /* User lstat() to check whether the supplied pathname is
       a symbolic link. Alternatively, we could have checked to
       whether readlink() failed with EINVAL. */

    if (lstat(argv[1], &statbuf) == -1)
        errExit("lstat");

    if (!S_ISLNK(statbuf.st_mode))
        fatal("%s is not a symbolic link", argv[1]);

    numBytes = readlink(argv[1], buf, BUF_SIZE - 1);
    if (numBytes == -1)
        errExit("readlink");
    buf[numBytes] = '\0';                       /* Add terminating null byte */
    printf("readlink: %s --> %s\n", argv[1], buf);

    if (realpath(argv[1], buf) == NULL)
        errExit("realpath");
    printf("realpath: %s --> %s\n", argv[1], buf);

    exit(EXIT_SUCCESS);
}

要点：什么时候用 readlink，什么时候用 realpath

需求 用谁 原因
「链接里到底写了什么」（存储/备份） readlink 只要原文，不要解析（解析会丢「相对性」）
「这个路径最终指向哪个真实文件」（安全检查） realpath 全展开 + 消除 ./..，可用于目录穿越校验
判断两个路径是否同一文件 realpath 后比串，或直接比 st_dev+st_ino 字符串比对面有 ./x vs x 这种平凡差异
把相对链接改写成绝对链接 readlink（拿原文）+ 手动拼 realpath 会连目标一起解析，丢失链接本身的信息

常见坑

坑 正解
readlink 后直接 printf("%s", buf) 不补 NUL → 未定义行为；必须 buf[n] = '\0'
char buf[64] 而 readlink(path, buf, sizeof(buf)) 截断且无 NUL；给 sizeof(buf)-1 并检查 n == sizeof(buf)-1
以为 readlink 能读普通文件 EINVAL（它不跟随）；读任意路径的解析结果用 realpath
symlink 返回 0 就认为「链接可用」 只说明链接建好了；目标可能不存在（悬空），要 open/stat 才知道
用 symlink 实现「原子替换」 symlink 遇已存在名字报 EEXIST；先 unlink+symlink 有窗口，原子换向要用「临时名 + rename」或 Linux 的 renameat2(RENAME_EXCHANGE)
把 readlink 的返回值当 strlen 返回值是写入字节数；只有「没截断」时二者才相等

HFT / 嵌入式关联

场景 本节机制怎么兑现
版本目录的原子换向 symlink(new_tmp) → rename(new_tmp, current)：两步都原子，读者要么旧要么新；readlink 用于回滚时拿到上一版
配置/数据集指针 服务读 data.current 前先 readlink 记录「当前用的是哪个版本」，审计日志可直接落这个串
安全校验 realpath 后确认前缀在白名单目录内，再 open——防目录穿越（../../etc/passwd）
嵌入式打包 固件里 .so -> .so.1 链接必须存相对串；备份/烧录工具只 readlink 拿原文重建，用 realpath 会把相对性烧死成绝对路径
st_size 即缓冲大小 读链接前 lstat 拿 st_size+1 分配缓冲，杜绝截断——是 readlink 唯一「自描述」的地方

代码自测（Q&A）

Q1：readlink 为什么不像 read 那样自动补 NUL？ A：因为链接内容本质是字节串而不是 C 字符串——某些场景（如存进元数据、做哈希）就是要原文长度。补 NUL 是调用者的责任，这也使得「被截断」变成可检测的状态（n == bufsiz）。

Q2：怎么确定 readlink 没截断？ A：两种办法：① 先 lstat 拿 st_size（= 链接串长度），按它分配缓冲，读完比对 n == st_size；② 用足够大缓冲，若 n == sizeof(buf)-1 就再放大重读。方法 ① 更省一次系统调用且天然免疫截断。

Q3：symlink("a", "b") 时 b 已存在会怎样？和 ln -s 命令行为一致吗？ A：EEXIST。ln -sf 的 -f 是命令自己先 unlink 再 symlink（所以那中间有窗口，不是原子的）。要原子换向必须走「临时名 + rename」。

Q4：readlinkat 相比 readlink 的价值？ A：① 锚定目录 fd，消除路径竞态（§18.11）；② 配合 O_PATH 打开的目录做受限遍历；③ readlinkat(fd, "", buf, n) 可以读已打开文件本身的链接（如 /proc/PID/fd/N），这是无 dirfd 版做不到的。

Q5：链接串里能放 NUL 字节吗？ A：不能。symlink 的目标以 NUL 结尾，串里不可能含 NUL。这也是为什么 readlink 的返回值通常是「长度+1」争议的根源——不存在「串里带了 NUL」这种可能。

Q6：view_symlink.c 输出里 /etc/hosts → /private/etc/hosts，readlink 为什么只显示一层？ A：readlink 只读这一个链接的内容（/etc/hosts），不解析。/etc → /private/etc 是文件系统层的另一个链接，只有 realpath 这种逐级解析的接口才会把它展开。

18.6

Creating and Removing Directories: mkdir() and rmdir() 创建与删除目录

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 mkdir(2) / rmdir(2) / unlinkat(2) + Linux v6.6 fs/namei.c（vfs_mkdir/vfs_rmdir） - 上一节：18.5 symlink() and readlink() - 下一节：18.7 remove()

本节讲什么

  1. mkdir() 的 mode 参数受 umask 削减（和 open 同一套规则），且目录必须有 x 才有用；
  2. rmdir() 只吃空目录——「空」的判定是「只有 . 和 ..」；
  3. 目录的 st_nlink 在这里形成闭环：新建目录的瞬间，父目录 +1、自己 = 2；
  4. mkdir 的存在性检查是内核原子完成的，不是「先 stat 再 mkdir」。

要点：契约表

#include <sys/stat.h>
int mkdir(const char *pathname, mode_t mode);   /* mode 受 umask 削减 */
int mkdirat(int dirfd, const char *pathname, mode_t mode);
#include <unistd.h>
int rmdir(const char *pathname);
调用 结果 实测错误码
mkdir(已存在) 失败 EEXIST（File exists）
mkdir(父目录不存在) 失败 ENOENT（不自动建多级；要 mkdir -p 得自己循环）
rmdir(非空目录) 失败 ENOTEMPTY（Directory not empty）
rmdir(普通文件) 失败 ENOTDIR（Not a directory）
rmdir(指向目录的符号链接) 失败 ENOTDIR —— 删链接本身要用 unlink
rmdir(".") / rmdir("..") 失败 EINVAL（macOS 实测两者同码；Linux man-pages 只把「末组件为 . → EINVAL」写进契约，.. 的具体码待 Pi5 复测）

「空」的精确定义：目录里只剩 . 和 .. 两条目录项。哪怕里面有一个符号链接或一个空子目录，都算非空——递归删除必须自后序遍历（见 §18.9 的 FTW_DEPTH）。

实测：umask 削减与 st_nlink 闭环

完整源码（code/c18_6_mkdir_rmdir.c）：

/* c18_6_mkdir_rmdir.c — Ch18 §18.6：mkdir() / rmdir() 的真实语义
 *
 * 钉住的点（全部实测）：
 *   ① mkdir() 的 mode **受 umask 削减**（与 open 同一套规则），
 *      且目录必定带上 x 位才有用（没有 x 连 cd 都进不去）；
 *   ② 目录的 st_nlink 不是「被链接次数」而是 **2 + 子目录数**：
 *      自己一条、"." 一条，每个子目录的 ".." 再各算一条；
 *   ③ rmdir() 只吃**空目录**：非空 ENOTEMPTY、指向文件的 ENOTDIR、
 *      指向目录的**符号链接**也是 ENOTDIR（要用 unlink 删链接本身）；
 *   ④ rmdir(".") / rmdir("..") → EINVAL/EBUSY，内核不许把树上节点摘断；
 *   ⑤ unlinkat(dirfd, name, AT_REMOVEDIR) 是 rmdir 的 *at 版本（§18.11）。
 *
 * 编译： cc -Wall -Wextra -o c18_6_mkdir_rmdir c18_6_mkdir_rmdir.c
 * 取材： man-pages 6.19 mkdir(2)/rmdir(2) + TLPI §18.6
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>

static void try_mkdir(const char *p, mode_t mode, const char *tag)
{
    errno = 0;
    int r = mkdir(p, mode);
    printf("  %-42s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

static void try_rmdir(const char *p, const char *tag)
{
    errno = 0;
    int r = rmdir(p);
    printf("  %-42s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

int main(void)
{
    const char *base = "/tmp/tlpi_c18_6";
    char d[128], sub[160], f[160], lnk[160];
    snprintf(d,   sizeof d,   "%s/d",     base);
    snprintf(sub, sizeof sub, "%s/d/sub", base);
    snprintf(f,   sizeof f,   "%s/d/f",   base);
    snprintf(lnk, sizeof lnk, "%s/d_lnk", base);
    system("rm -rf /tmp/tlpi_c18_6 && mkdir /tmp/tlpi_c18_6");

    /* ---------- ① mode & umask ---------- */
    printf("== ① mkdir 的 mode 受 umask 削减 ==\n");
    mode_t old = umask(0);                       /* 先读出当前 umask */
    umask(old);
    printf("  当前 umask = %04o\n", (unsigned) old);
    try_mkdir(d, 0777, "mkdir(d, 0777)");
    struct stat sb;
    stat(d, &sb);
    printf("  实得 mode = %04o（= 0777 & ~%04o）\n",
           (unsigned) (sb.st_mode & 07777), (unsigned) old);

    /* ---------- ② st_nlink 的算法 ---------- */
    printf("\n== ② 目录的 st_nlink = 2 + 子目录数 ==\n");
    stat(d, &sb);
    printf("  空目录 d          st_nlink = %ld   ← 自己\n",
           (long) sb.st_nlink);
    mkdir(sub, 0755);
    stat(d, &sb);
    printf("  建 d/sub 之后 d   st_nlink = %ld   ← +子目录的 \"..\"\n",
           (long) sb.st_nlink);
    printf("  ⚠️ d/sub 自己的 st_nlink = ");
    stat(sub, &sb);
    printf("%ld（新建空目录恒为 2）\n", (long) sb.st_nlink);

    /* ---------- ③ rmdir 的失败面 ---------- */
    printf("\n== ③ rmdir 只吃空目录 ==\n");
    int fd = open(f, O_WRONLY | O_CREAT | O_EXCL, 0644);
    if (fd == -1) { perror("open"); return EXIT_FAILURE; }
    close(fd);
    try_rmdir(d, "rmdir(非空 d)");
    try_rmdir(f, "rmdir(普通文件)");
    symlink(d, lnk);
    try_rmdir(lnk, "rmdir(指向目录的符号链接)");
    printf("  → 删链接本身请用 unlink；rmdir 只跟到底层对象的类型\n");

    try_rmdir(".", "rmdir(\".\")");
    try_rmdir("..", "rmdir(\"..\")");

    /* ---------- ④ *at 版本 ---------- */
    printf("\n== ④ unlinkat(AT_REMOVEDIR) == rmdir ==\n");
    int dfd = open(d, O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open dir"); return EXIT_FAILURE; }
    char *slash = strrchr(f, '/');
    errno = 0;
    int r = unlinkat(dfd, slash + 1, 0);              /* 0 = 删文件 */
    printf("  unlinkat(dfd, \"%s\", 0)             = %d %s\n",
           slash + 1, r, r == 0 ? "" : strerror(errno));
    errno = 0;
    r = unlinkat(dfd, "sub", AT_REMOVEDIR);           /* 删空目录 */
    printf("  unlinkat(dfd, \"sub\", AT_REMOVEDIR)   = %d %s\n",
           r, r == 0 ? "" : strerror(errno));
    close(dfd);

    /* ---------- ⑤ mkdir 的存在/父目录检查 ---------- */
    printf("\n== ⑤ mkdir 的前置检查（都是内建原子性，不是先 stat 再建）==\n");
    try_mkdir(d, 0755, "mkdir(已存在的 d)");
    try_mkdir("/tmp/tlpi_c18_6/no/such/parent", 0755, "mkdir(父目录不存在)");

    /* 清理 */
    unlink(lnk);
    try_rmdir(d, "rmdir(空 d)  ← 现在可以了");
    rmdir(base);
    return EXIT_SUCCESS;
}

  rmdir(空 d)  ← 现在可以了          = 0

三个要点：

  • umask 削减：0777 & ~0022 = 0755。若要「确保」某权限位，mkdir 后得再 chmod（或先临时清 umask）。另注意：即使 umask 是 0，mkdir 也会自动置上执行位（内核保证目录至少 x）——因为没 x 的目录连 cd 都进不去。
  • st_nlink 闭环：mkdir(sub) 同时做了两件事——给父目录 nlink+1，给新目录 nlink=2。所以「目录的 nlink 永远能被子目录数解释」（18.1 实测）。
  • rmdir 对符号链接报 ENOTDIR 是最常被误判的一条：很多人以为它会顺着链接去删目录，实际它先 lstat 判类型——链接不是目录，所以拒绝。删链接用 unlink。

要点：mkdir 的原子性（与 TOCTOU 的关系）

mkdir(已存在) → EEXIST 意味着「检查 + 创建」在内核里是一步完成的。因此：

/* ✗ 有竞态：stat 和 mkdir 之间目录可能被别人建出来 */
if (stat(dir, &sb) == -1) mkdir(dir, 0755);

/* ✓ 无竞态：EEXIST 就当作"已经在了" */
if (mkdir(dir, 0755) == -1 && errno != EEXIST) { /* 真错误 */ }

这个模式和 §18.3 的「先 open 再 unlink」、§18.4 的「link 做锁」是同一族：把检查交给 syscall 的错误码，别自己排 stat。

代码自测（Q&A）

Q1：mkdir(path, 0777) 在 umask=0 时会得到 0777 吗？ A：会得到 0777（或内核补充的必要位）。但 umask=0 的进程很少见；实测默认 0022 → 0755。要精确权限只能 mkdir 后 chmod，或临时 umask(0) 再恢复（多线程下危险）。

Q2：为什么目录即使 umask 全掩也至少有 x？ A：内核在 vfs_mkdir 里会 |=S_IXUGO 的必要部分——没有 x 的目录连 cd 都进不去，是个无意义的对象。这是「目录权限的最小可用集」的实现层保证。

Q3：rmdir 对「指向目录的符号链接」报什么？为什么？ A：ENOTDIR。内核先对路径做类型判定（等价 lstat），链接不是目录 → 拒绝。这与 open（会跟随链接）形成对比：删除类接口对链接都是「删链接本身」。

Q4：mkdir 的 EEXIST 能当「目录已存在」的可信信号吗？ A：能，而且这正是它的推荐用法。mkdir 在内核里原子完成「检查+创建」，EEXIST 表示「现在确实已经存在（不管是谁建的、什么时候建的）」。比「先 stat 再 mkdir」严格更优。

Q5：rmdir(".") 为什么不允许？ A：删掉「当前正在里面」的目录会让 cwd 悬空，且「.」是目录自身对自身的引用，摘掉它等于摘断树。内核直接 EINVAL。macOS 对 .. 也给 EINVAL；Linux 的具体码未在本机核验，见 Pi5 复测清单。

Q6：递归删除一个目录树，为什么必须后序（FTW_DEPTH）？ A：rmdir 只删空目录。先序遍历会在子项还在时尝试删父目录 → ENOTEMPTY。后序保证到达一个目录时它的所有子项已被删光，rmdir 必然成功。

18.7

Removing a File or Directory: remove() 统一删除入口

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 remove(3) / unlink(2) / rmdir(2) + C99/C23 7.21.4.1 - 上一节：18.6 mkdir() and rmdir() - 下一节：18.8 opendir() and readdir()

本节讲什么

TLPI 这一节非常短，但有一个常被误解的点值得单独成节：

  1. remove() 不是系统调用——它头文件是 <stdio.h>（C 标准，不是 POSIX），实现在 libc 里；
  2. 它是一个分派器：先判类型 → 目录走 rmdir()，其余走 unlink()；
  3. 因为是先判类型再分派，它对符号链接的行为是「删链接本身」（用 lstat 判，不跟目标）；
  4. 它的存在意义：屏蔽类型判断，让「删除这个路径」成为一句话。代价是失败码继承了两个接口的并集。

要点：三个删除接口对照

函数 来源 头文件 普通文件 符号链接 空目录 非空目录
unlink() POSIX <unistd.h> ✅ ✅（删链接本身） ❌ EISDIR(Linux)/EPERM(macOS) ❌
rmdir() POSIX <unistd.h> ❌ ENOTDIR ❌ ENOTDIR ✅ ❌ ENOTEMPTY
remove() C 标准 <stdio.h> ✅ ✅ ✅ ❌ ENOTEMPTY

注意 remove 的移植性优势：C 标准保证它在任何符合 C 标准的平台（包括 Windows CRT）都存在；而 unlink/rmdir 是 POSIX 专属。写可移植代码时 remove 是唯一「零依赖」选项。

实测：分派行为的三个证据

完整源码（code/c18_7_remove.c）：

/* c18_7_remove.c — Ch18 §18.7：remove() 是「分派器」，不是新 syscall
 *
 * 钉住的点（全部实测）：
 *   ① remove() **不是系统调用**，是 C 标准库（stdio.h）里的分派器：
 *      实现上先用 lstat（）判类型 → 目录走 rmdir()，其余走 unlink()；
 *   ② 因此它删**符号链接**时删的是链接本身（lstat 不跟目标）——
 *      哪怕链接指向一个目录也不会去 rmdir 那个目录；
 *   ③ 它继承了两边的全部失败面：非空目录 ENOTEMPTY、不存在 ENOENT；
 *   ④ 对比 unlink(目录)：Linux 给 EISDIR，macOS 给 EPERM——
 *      「都拒绝」是共识，「码是什么」不是。
 *
 * 编译： cc -Wall -Wextra -o c18_7_remove c18_7_remove.c
 * 取材： man-pages 6.19 remove(3)/unlink(2) + TLPI §18.7
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void try_remove(const char *p, const char *tag)
{
    errno = 0;
    int r = remove(p);
    printf("  %-40s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

int main(void)
{
    const char *base = "/tmp/tlpi_c18_7";
    char d[128], f[160], lnk[160], keep[160];
    snprintf(d,    sizeof d,    "%s/d",     base);
    snprintf(f,    sizeof f,    "%s/d/f",   base);
    snprintf(keep, sizeof keep, "%s/d/keep", base);
    snprintf(lnk,  sizeof lnk,  "%s/d_lnk", base);
    system("rm -rf /tmp/tlpi_c18_7 && mkdir -p /tmp/tlpi_c18_7/d");
    int fd = open(f, O_WRONLY | O_CREAT, 0644);
    if (fd == -1) { perror("open"); return EXIT_FAILURE; }
    close(fd);

    /* ---------- ① 分派：文件走 unlink ---------- */
    printf("== ① remove() 自动分派 ==\n");
    try_remove(f, "remove(普通文件)     → unlink 分支");
    try_remove(f, "再删一次（已不存在）");

    /* ---------- ② 分派：空目录走 rmdir ---------- */
    printf("\n== ② 空目录走 rmdir 分支 ==\n");
    try_remove(d, "remove(空目录)       → rmdir 分支");
    mkdir(d, 0755);
    fd = open(keep, O_WRONLY | O_CREAT, 0644);
    if (fd == -1) { perror("open2"); return EXIT_FAILURE; }
    close(fd);
    try_remove(d, "remove(非空目录)     → 继承 ENOTEMPTY");

    /* ---------- ③ 符号链接：删链接，不动目标 ---------- */
    printf("\n== ③ 符号链接：remove 删的是链接本身（lstat 不跟目标）==\n");
    symlink("d", lnk);                       /* 链接指向**目录** d */
    try_remove(lnk, "remove(指向目录的符号链接)");
    struct stat sb;
    printf("  目标 d 还在？ stat(d) = %d（目录安然无恙，只掉了链接）\n",
           stat(d, &sb));

    /* ---------- ④ 对比 unlink(目录) ---------- */
    printf("\n== ④ unlink(目录)：Linux=EISDIR / macOS=EPERM（都拒绝，码不同）==\n");
    errno = 0;
    int r = unlink(d);
    printf("  unlink(目录) = %d errno=%d(%s)\n", r, errno, strerror(errno));
    printf("  → remove() 存在的意义：屏蔽这层类型判断，给你一个统一入口。\n");

    /* 清理 */
    unlink(keep);
    rmdir(d);
    rmdir(base);
    return EXIT_SUCCESS;
}

三个钉住的点：

  • ③ 是最容易被误解的一条：链接指向的是目录，remove 成功且返回 0——但目录完好。因为分派用的是 lstat（看链接本身，类型是 S_IFLNK），走的是 unlink 分支。remove 永远不会替你删掉链接背后的目录。
  • ④ 展示了为什么需要统一入口：unlink 拒绝目录这件事两平台都做，但错误码不同（Linux EISDIR，macOS EPERM）。「都拒绝」是共识，「码是什么」不是——可移植代码应该用 remove（或先 lstat 自己分派），别依赖具体 errno。
  • 失败码是并集：remove 可能返回 ENOENT（unlink/rmdir 都会）、ENOTEMPTY（只来自 rmdir）、EACCES（来自写权限）等。写错误处理时按「可能是三种之一」来对待。

要点：删除非空目录的正确姿势

remove（以及 unlink/rmdir 任何一个）都不提供递归删除。标准做法是 nftw + 后序遍历：

#include <ftw.h>
static int rm_cb(const char *path, const struct stat *sb,
                 int typeflag, struct FTW *ftwbuf) {
    return remove(path);           /* FTW_DEPTH 保证到达时子项已删光 */
}
int rm_recursive(const char *dir) {
    return nftw(dir, rm_cb, 64, FTW_DEPTH | FTW_PHYS);
}

FTW_DEPTH（后序）是必须的：先序到达目录时子项还在，remove 会 ENOTEMPTY。FTW_PHYS（不跟随链接）同样是必须的：否则链接指向的外部文件会被误删。完整机制见 18.9 nftw()（含实测输出）。

代码自测（Q&A）

Q1：remove() 是系统调用吗？ A：不是。头文件 <stdio.h> 表明它是 C 标准库函数（C99 7.21.4.1），libc 内部实现为「判类型 → unlink 或 rmdir」。所以它有 libc 层开销（一次 lstat），但不值得为此优化——目录操作本来就慢。

Q2：为什么 remove 对符号链接的行为是「删链接」而不是「删目标」？ A：分派依据是 lstat 的类型。链接的类型是 S_IFLNK，不是 S_IFDIR，所以走 unlink 分支——unlink 对链接本来就是删链接本身。这保证了 remove 不会「意外地」删掉链接背后的目录树。

Q3：remove 与 unlink 的性能差多少？ A：多一次 lstat。在目录操作（本身就是纳秒~微秒级 syscall）里可忽略；只有在热路径批量删除几十万文件时才值得直接用 unlink 省一次类型判定。

Q4：怎么写一个「幂等」的删除？ A：if (remove(p) == -1 && errno != ENOENT) /* 真错误 */;。把 ENOENT 当成功处理，重启/重试逻辑就无需「先检查存在」——检查本身有竞态，remove 的 ENOENT 才是权威答案。

Q5：递归删除时为什么 FTW_PHYS 也是必须的？ A：没有它，nftw 会跟随符号链接离开这棵树——回调会对链接指向的外部文件调用 remove，把不相关的数据删掉。FTW_DEPTH|FTW_PHYS 是递归删除的固定搭配，缺一不可。

Q6：remove 能删一个「正在被写」的文件吗？ A：能。它调 unlink，只摘名字；数据的释放仍受「无打开 fd」约束（§18.3）。正在写的进程继续写，写完 close，数据才消失——这正是临时文件惯用法的基础。

18.8

Reading Directories: opendir() and readdir() 读目录

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 readdir(3) / fdopendir(3) / seekdir(3) + Linux v6.6 fs/readdir.c（getdents64）+ TLPI dist dirs_links/list_files.c（Listing 18-2）、list_files_readdir_r.c（习题 18-4 官方解） - 上一节：18.7 remove() - 下一节：18.9 nftw()

本节讲什么

  1. readdir() 返回 NULL 有两种含义（读完 / 出错）——不查 errno 的遍历会把 I/O 错误当「读完」，静默少列文件；
  2. telldir() 返回的是不透明书签，且本机实测它不是字节偏移（macOS 给的是计数，Linux 给的是偏移）；
  3. 本机实测发现一个硬差异：APFS 上 seekdir() 恒等于 rewinddir——任何 cookie 都回到第一项；
  4. fdopendir() 之后 fd 的所有权归 DIR：再自己 close(fd) 是双重关闭；
  5. d_type 只是「省一次 lstat」的优化，不是权威（可能 DT_UNKNOWN）。

要点：核心 API 与 struct dirent

完整源码（code/c18_8_readdir.c）：

/* c18_8_readdir.c — Ch18 §18.8：readdir 的四个必知细节
 *
 * 钉住的点（全部实测）：
 *   ① 「读到末尾」与「读出错」都返回 NULL —— 必须用 errno 协议区分：
 *      进循环前 errno = 0，返回 NULL 后看 errno，非 0 才是错；
 *   ② telldir/seekdir 是**不透明的书签**（不能当字节偏移做算术），
 *      rewinddir 才是回到开头；
 *   ③ fdopendir 之后 **fd 归 DIR 所有**：再自己 close(fd) 或 read(fd)

① errno 协议

== ① readdir 返回 NULL：末页 or 出错？靠 errno 协议区分 ==
  遍历完 5 项，返回 NULL 时 errno = 0(未置位) → 正常结束
  ⚠️ 不去查 errno 的写法在 NFS / 坏盘上会把 I/O 错误当「读完了」，
     静默少列文件——这是备份工具最经典的丢数据 bug。

正确姿势：进循环前 errno = 0；循环退出后 errno != 0 才是真错误。

② telldir 的 cookie 不是字节偏移

== ② telldir 返回的是「不透明书签」，别当字节偏移 ==
  TLPI 的警告：不同系统里这个值的含义不一样。本机实测：
    读 .    -> telldir() = 0
    读 ..   -> telldir() = 1
    读 ll   -> telldir() = 2
    读 dd   -> telldir() = 3
    读 aa   -> telldir() = 4
  → macOS(APFS) 给的是「已读项计数」式的 0,1,2,…；
     Linux(ext4) 给的是目录内部偏移（d_off，字节数，4 的倍数）。
     跨平台做算术（mark+N）必炸——这是原书专门点的坑。

③ seekdir 在本机恒等于 rewinddir（本轮实测的核心发现）

== ③ seekdir：POSIX 契约 vs 本机实测 ==
  契约：读完 X 后 telldir 取 t，seekdir(t) 的下一次 readdir 必须再给 X 的后继。
    seekdir(0) -> 下一项 = .
    seekdir(1) -> 下一项 = .
    seekdir(2) -> 下一项 = .
    seekdir(3) -> 下一项 = .
    seekdir(4) -> 下一项 = .
  ⚠️ 本机 macOS 26.6.2 / APFS 实测：**seekdir 恒等于 rewinddir**——
     换任何 cookie 都从第一项重新开始，完全没定位效果。
     Linux/ext4 上同样代码能正确复现位置。
  ⇒ 结论：目录扫描要「打点续扫」，别用 telldir/seekdir 做断点；
     用 rewinddir 重来，或干脆把要处理的路径收集起来再遍历。
     （rewinddir 本机实测正常，是可靠的。）

验证方法（demo 里就是这么写的，可复现）：rewinddir 后逐项读到 dd 取 cookie，再 rewinddir + 故意读 2 项错位，然后 seekdir(cookie) ——下一项不是 dd 的后继，而是第一项。对 5 个不同 cookie 全部如此。这是 POSIX 契约的违反，不是我的序列问题（demo 输出里契约与实测并排）。Linux 上同样代码能正确定位——典型「书上的话在本机不成立」。

④ fdopendir 的所有权移交

== ④ fdopendir 之后 fd 归 DIR 管 ==
  open 得到 fd = 4
  fdopendir(fd) = 0x128004150
  ⚠️ 此后 raw 的所有权移交 DIR：只能 closedir(d2)，
     再 close(raw) 会 double close；read(raw) 会与 readdir 抢偏移。

⑤ d_type vs lstat

== ⑤ d_type 只是优化；lstat 才是权威 ==
  name   d_type           lstat      一致?
  ll     LNK              LNK        是
  dd     DIR              DIR        是
  aa     REG              REG        是
  ⚠️ 注意 ll 是**符号链接**：readdir 报 LNK，而 stat（跟随）会报 REG。
     「列举后的下一步」默认该用 lstat，否则统计目录时会重复计数。

本机 APFS 上 d_type 是可用的（DT_REG=8 / DT_DIR=4 / DT_LNK=10，与 Linux 同值）。但可移植代码必须处理 DT_UNKNOWN（此时只能 lstat 补齐）。

#include <sys/types.h>

#include <stddef.h>
#include "tlpi_hdr.h"

static void             /* List all files in directory 'dirpath' */
listFiles(const char *dirpath)
{
    DIR *dirp;
    Boolean isCurrent;          /* True if 'dirpath' is "." */
    struct dirent *result, *entryp;
    int nameMax;

    isCurrent = strcmp(dirpath, ".") == 0;

    /* On Linux, NAME_MAX is defined in <limits.h>. However, this limit
       may vary across file systems, so we really should use pathconf()
       to find the true limit for this file system. */

    nameMax = pathconf(dirpath, _PC_NAME_MAX);
    if (nameMax == -1)          /* Indeterminate or error */
        nameMax = 255;          /* So take a guess */

    entryp = malloc(offsetof(struct dirent, d_name) + nameMax + 1);
    if (entryp == NULL)
        errExit("malloc");

    /* Open the directory - on failure print an error and return */

    dirp = opendir(dirpath);
    if (dirp == NULL) {
        errMsg("opendir failed on '%s'", dirpath);
        free(entryp);
        return;
    }

    /* Look at each of the entries in this directory */

    for (;;) {
        errno = readdir_r(dirp, entryp, &result);
        if (errno != 0)
            errExit("readdir_r");

        if (result == NULL)     /* End of stream */
            break;

        /* Skip . and .. */

        if (strcmp(entryp->d_name, ".") == 0 ||
                strcmp(entryp->d_name, "..") == 0)
            continue;

        /* Print directory + filename */

        if (!isCurrent) printf("%s/", dirpath);
        printf("%s\n", entryp->d_name);
    }

    if (closedir(dirp) == -1)
        errMsg("closedir");
}

main(int argc, char *argv[])
{
    if (argc == 1)              /* No arguments - use current directory */
        listFiles(".");
    else
        for (argv++; *argv; argv++)
            listFiles(*argv);
    exit(EXIT_SUCCESS);
}

代码自测（Q&A）

Q1：readdir 返回 NULL 后 errno 仍是 0，能确定「读完了」吗？ A：能确定「这次遍历没有报错」，但不能确定「目录里所有条目都看到了」——目录可能在遍历中被并发修改。readdir 的契约只保证「返回过的条目曾存在」。要严格一致快照得靠文件系统层支持（快照/AT_FDCWD 冻结做不到）。

Q2：为什么 d_name 是唯一可移植的字段？ A：POSIX 只把 d_ino/d_name 列为必需，且对 d_ino 的取值还有「可能不填」的豁免；d_type、d_reclen、d_off 都是扩展。所以跨平台代码里，类型判断永远要走 lstat，不能赌 d_type。

Q3：fdopendir 有什么实际用途？为什么不让它复制 fd？ A：用途：已有 fd（如 openat 的结果、O_PATH 打开的目录、dirfd）想复用 readdir 的便利。不复制是设计选择：复制会引入「fd 与 DIR 各自偏移」的双状态问题，所有权移交最简单。代价是你不能再碰那个 fd。

Q4：APFS 的 seekdir 为什么失效？ A：本机实测 cookie 是 0,1,2,…（计数式），而 seekdir 的 BSD 实现把 cookie 当「缓冲内偏移 + 块基址」处理；小目录整目录进一个缓冲，cookie 与内部偏移量纲不匹配，落点全部错回开头。这是实现 bug 级差异——跨平台代码必须假设 seekdir 不可靠。

Q5：遍历大目录时 opendir 会把整个目录读进内存吗？ A：不会。readdir 按块流式读（Linux 走 getdents64，一次一个缓冲区），内存占用 O(缓冲)。但这意味着「遍历中途目录被修改」是常态而非异常——用 openat 锚定 + 接受快照非严格，是工程正解。

Q6：scandir 和手写 opendir+readdir 差在哪？ A：scandir 自动：收集成数组 + 按过滤函数筛选 + 按 alphasort 排序 + malloc 管理。代价是全量内存 + 需要释放数组。要顺序、要过滤、目录不太大时用它最省事；超大目录或内存敏感时手写流式遍历。

18.9

File Tree Walking: nftw() 文件树遍历

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 nftw(3) / ftw(3) + Linux v6.6 fs/namei.c（kern_path 深度）+ TLPI dist dirs_links/nftw_dir_tree.c（Listing 18-3）、file_type_stats.c（习题 18-7 官方解） - 上一节：18.8 opendir() and readdir() - 下一节：18.10 The Current Working Directory of a Process

本节讲什么

  1. nftw() = 递归遍历目录树的标准接口：递归逻辑、深度限制、先序/后序、链接策略全部由内核/libc 代理；
  2. 四个 flag 里 FTW_DEPTH（后序）与 FTW_PHYS（不跟随链接）是工程上最常用的一对——递归删除的固定搭配；
  3. 本机实测展示了「不跟随」与「跟随」的本质区别：默认模式下，指向目录的符号链接会让同一棵子树被遍历两次；
  4. nopenfd（同时打开的目录数上限）是资源护栏，不是「越大越好」。

要点：接口契约

代码自测（Q&A）

Q1：为什么默认模式会把「指向目录的链接」当目录遍历？ A：nftw 内部对每个条目先 stat（跟随），得到的类型是目录 → 递归进去。这个行为是 POSIX 规定的，不是 bug。FTW_PHYS 让它改用 lstat，链接就报 FTW_SL 并停止下钻。实测 inode 相同（2278245）证明「两个名字、同一 inode」。

Q2：FTW_SLN 和 FTW_SL 的区别？ A：都是链接。FTW_SL = 不跟随模式（FTW_PHYS）下的链接本身；FTW_SLN = 跟随模式下 stat 失败的链接（一般是悬空）。实测：同一棵树里 dangling 在默认模式下是 SLN，加 -p 后变 SL。

Q3：nopenfd 给 1 会怎样？ A：功能正确，但每进入一层目录就要关掉上一层的 DIR（保存位置、重开、seek 回去），性能急剧下降。它是「同时打开目录数」的护栏；给 20~64 通常既能防 fd 耗尽又不触发频繁重开。

Q4：回调返回 3 会发生什么？nftw 返回什么？ A：立即停止遍历（剩余子树不访问），nftw 把 3 原样返回给调用者。注意与 -1（nftw 自身出错）区分。所以「用户自定义错误码」要选非 0、非 -1 的值，或者用全局变量传递。

Q5：遍历时目录被并发删除会怎样？ A：nftw 用 lstat/opendir 逐级访问，被删的子树可能报 FTW_NS/FTW_DNR，也可能正常跳过——没有一致性保证。要强一致快照得靠文件系统快照，应用层只能「容忍竞态 + 按错误码分派处理」。

Q6：nftw 能并行化吗？ A：接口本身串行（一个回调、一个遍历游标）。要并行得手写递归 + 线程池（每个 worker 用 openat 锚定自己的子树）。这也是「需要并行就别用 nftw」的根本原因。

18.10

The Current Working Directory of a Process 进程的当前工作目录

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 getcwd(3) / chdir(2) / fchdir(2) + Linux v6.6 fs/open.c（SYSCALL_DEFINE2(chdir) 等）、fs/d_path.c + TLPI dist dirs_links/ - 上一节：18.9 nftw() - 下一节：18.11 Operating Relative to a Directory File Descriptor

本节讲什么

  1. cwd 是进程属性：fork 继承、exec 保留——这是「shell cd 不影响子进程」等一切现象的根源；
  2. 两种「记住老目录再回去」的方案：open(".") + fchdir（fd 方案）vs getcwd + chdir（字符串方案）——fd 方案全面占优（习题 18-9 的正解）；
  3. getcwd 的缓冲不足返回 ERANGE，标准写法是「从合理大小起步、逐次翻倍重试」；
  4. cwd 在内核里就是一个挂靠的 path 引用——所以目录被删了进程还活着，但 getcwd 就会失败。

要点：核心 API

#include <unistd.h>
int chdir(const char *path);
int fchdir(int fd);                      /* fd 必须是目录且为 O_RDONLY 打开 */
char *getcwd(char *buf, size_t size);    /* 成功返回 buf；失败 NULL+errno */
项 规则
cwd 归属 进程级（task_struct → fs_struct → pwd），不是线程独立（同一进程的线程共享 cwd）

要点：为什么多线程进程怕 chdir

cwd 是进程级的，所以：

  1. 一个线程 chdir，所有线程的相对路径解析基准立刻全变；
  2. 另一个线程正在 open("data/tick.log")——它解析的 data/ 已经是别的目录了；
  3. 这种 bug 的表现是「偶发读错文件」，几乎无法稳定复现。

代码自测（Q&A）

Q1：为什么 shell 里 cd 之后子 shell 也跟着变，但父 shell 不受子进程 cd 影响？ A：fork 时 cwd 引用被复制（不是共享）。子进程 chdir 只改自己 fs_struct 的 pwd，父进程的 pwd 没变。反过来，同一进程内的线程共享 fs_struct，所以线程间会互相影响——方向别搞反。

Q2：目录被 rmdir 之后，还在里面的进程会怎样？ A：进程照常运行（内核里 cwd 还是一个有效的 inode 引用），但 getcwd 失败（ENOENT）。Linux 上读 /proc/self/cwd 会得到 (deleted) 后缀。应用若继续用相对路径 open，会在一个「幽灵目录」里工作。

Q3：fchdir 需要什么权限？ A：fd 必须是目录且以可搜索方式打开（O_RDONLY|O_DIRECTORY 最常见）。Linux 上 O_PATH 打开的目录 fd 也能 fchdir（这是 O_PATH 的少数实际用途之一）。macOS 上 O_PATH 不可用。

Q4：getcwd 的「翻倍重试」写法具体怎么做？ A：从 PATH_MAX（或 256）起步，ERANGE 时翻倍再试，直到成功或达到上限。另一种更省的是「先 lstat(".") 不可行，直接给 PATH_MAX 栈缓冲」——大多数系统 PATH_MAX 够用；真正会超的是深层递归遍历场景（那时通常已经有目录 fd 可用，不需要 getcwd）。

Q5：chdir 与 openat 的性能差？ A：chdir 是 1 次 syscall + 一次路径解析；openat(dirfd, name) 是 1 次 syscall + 少量解析（从锚点开始）。多文件操作时 openat 全面胜出：不用反复 chdir，也没有全局状态竞争。

Q6：为什么 demo 里用 chdir("/") 而不是 chdir("/tmp")？ A：macOS 上 /tmp 是指向 /private/tmp 的符号链接，getcwd 会返回解析后的物理路径，输出里看不出「真的换了目录」。chdir("/") 后 getcwd 明确显示 /，差异可见。这也是「cwd 显示的是解析后路径」的一个佐证。

本节讲什么

*at() 族是 Linux 2.6.16 引入、POSIX.1-2008 收编的一整族接口。它解决两个老接口的结构性缺陷：

  1. TOCTOU：chdir(dir) 与 open("file") 之间，目录可以被换掉；
  2. 进程级全局状态：cwd 是进程属性，多线程共享，谁都能搅局。

*at() 把「基准」从进程属性（cwd）变成一个 fd——锚点打开即固定，之后所有操作都相对它。本节还实测 openat 与 cwd 的解耦。

要点：*at() 族对照表

unlinkat unlink/rmdir AT_REMOVEDIR（= rmdir）
renameat / renameat2 rename renameat2：RENAME_EXCHANGE/RENAME_NOREPLACE（Linux 专有）

 *   ② 目录的 st_nlink 不是「被链接次数」而是 **2 + 子目录数**：
 *      自己一条、"." 一条，每个子目录的 ".." 再各算一条；
 *   ③ rmdir() 只吃**空目录**：非空 ENOTEMPTY、指向文件的 ENOTDIR、
 *      指向目录的**符号链接**也是 ENOTDIR（要用 unlink 删链接本身）；
 *   ④ rmdir(".") / rmdir("..") → EINVAL/EBUSY，内核不许把树上节点摘断；
 *   ⑤ unlinkat(dirfd, name, AT_REMOVEDIR) 是 rmdir 的 *at 版本（§18.11）。
 *
 * 编译： cc -Wall -Wextra -o c18_6_mkdir_rmdir c18_6_mkdir_rmdir.c
 * 取材： man-pages 6.19 mkdir(2)/rmdir(2) + TLPI §18.6
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>

static void try_mkdir(const char *p, mode_t mode, const char *tag)
{
    errno = 0;
    int r = mkdir(p, mode);
    printf("  %-42s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

static void try_rmdir(const char *p, const char *tag)
{
    errno = 0;
    int r = rmdir(p);
    printf("  %-42s = %d %s\n", tag, r, r == 0 ? "" : strerror(errno));
}

int main(void)
{
    const char *base = "/tmp/tlpi_c18_6";
    char d[128], sub[160], f[160], lnk[160];
    snprintf(d,   sizeof d,   "%s/d",     base);
    snprintf(sub, sizeof sub, "%s/d/sub", base);
    snprintf(f,   sizeof f,   "%s/d/f",   base);
    snprintf(lnk, sizeof lnk, "%s/d_lnk", base);
    system("rm -rf /tmp/tlpi_c18_6 && mkdir /tmp/tlpi_c18_6");

    /* ---------- ① mode & umask ---------- */
    printf("== ① mkdir 的 mode 受 umask 削减 ==\n");
    mode_t old = umask(0);                       /* 先读出当前 umask */
    umask(old);
    printf("  当前 umask = %04o\n", (unsigned) old);
    try_mkdir(d, 0777, "mkdir(d, 0777)");
    struct stat sb;
    stat(d, &sb);
    printf("  实得 mode = %04o（= 0777 & ~%04o）\n",
           (unsigned) (sb.st_mode & 07777), (unsigned) old);

    /* ---------- ② st_nlink 的算法 ---------- */
    printf("\n== ② 目录的 st_nlink = 2 + 子目录数 ==\n");
    stat(d, &sb);
    printf("  空目录 d          st_nlink = %ld   ← 自己\n",
           (long) sb.st_nlink);
    mkdir(sub, 0755);
    stat(d, &sb);
    printf("  建 d/sub 之后 d   st_nlink = %ld   ← +子目录的 \"..\"\n",
           (long) sb.st_nlink);
    printf("  ⚠️ d/sub 自己的 st_nlink = ");
    stat(sub, &sb);
    printf("%ld（新建空目录恒为 2）\n", (long) sb.st_nlink);

    /* ---------- ③ rmdir 的失败面 ---------- */
    printf("\n== ③ rmdir 只吃空目录 ==\n");
    int fd = open(f, O_WRONLY | O_CREAT | O_EXCL, 0644);
    if (fd == -1) { perror("open"); return EXIT_FAILURE; }
    close(fd);
    try_rmdir(d, "rmdir(非空 d)");
    try_rmdir(f, "rmdir(普通文件)");
    symlink(d, lnk);
    try_rmdir(lnk, "rmdir(指向目录的符号链接)");
    printf("  → 删链接本身请用 unlink；rmdir 只跟到底层对象的类型\n");

    try_rmdir(".", "rmdir(\".\")");
    try_rmdir("..", "rmdir(\"..\")");

    /* ---------- ④ *at 版本 ---------- */
    printf("\n== ④ unlinkat(AT_REMOVEDIR) == rmdir ==\n");
    int dfd = open(d, O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open dir"); return EXIT_FAILURE; }
    char *slash = strrchr(f, '/');
    errno = 0;
    int r = unlinkat(dfd, slash + 1, 0);              /* 0 = 删文件 */
    printf("  unlinkat(dfd, \"%s\", 0)             = %d %s\n",
           slash + 1, r, r == 0 ? "" : strerror(errno));
    errno = 0;
    r = unlinkat(dfd, "sub", AT_REMOVEDIR);           /* 删空目录 */
    printf("  unlinkat(dfd, \"sub\", AT_REMOVEDIR)   = %d %s\n",
           r, r == 0 ? "" : strerror(errno));
    close(dfd);

    /* ---------- ⑤ mkdir 的存在/父目录检查 ---------- */
    printf("\n== ⑤ mkdir 的前置检查（都是内建原子性，不是先 stat 再建）==\n");
    try_mkdir(d, 0755, "mkdir(已存在的 d)");
    try_mkdir("/tmp/tlpi_c18_6/no/such/parent", 0755, "mkdir(父目录不存在)");

    /* 清理 */
    unlink(lnk);
    try_rmdir(d, "rmdir(空 d)  ← 现在可以了");
    rmdir(base);
    return EXIT_SUCCESS;
}

要点：TOCTOU 的三段式与 *at() 的破法

老写法的竞态窗口：

/* ✗ 三步之间，dir 可以被改名/换成符号链接 */
struct stat sb;
stat("/srv/data/config", &sb);      /* 1. 检查 */
chdir("/srv/data");                 /* 2. 进入 —— 这里 dir 可能已被换 */
int fd = open("config", O_RDONLY);  /* 3. 使用 —— 打开的可能已是别的东西 */

*at() 的破法：把「进入」变成「持有一个引用」。

/* ✓ 锚点打开后不可替换（fd 指向 inode，不指向路径） */
int dirfd = open("/srv/data", O_RDONLY | O_DIRECTORY);   /* 唯一的路径检查点 */
struct stat sb;
fstatat(dirfd, "config", &sb, 0);
int fd = openat(dirfd, "config", O_RDONLY);

配合 O_NOFOLLOW（open 时拒绝链接）与 fstatat(AT_SYMLINK_NOFOLLOW)，可以把「用户可控路径」的攻击面压到只剩一次 open。

更彻底的口诀（TLPI 反复强调）：先 open（拿到 fd = 拿到 inode），再对 fd 做一切操作（fstat/fchmod/fchown/futimens）。路径解析只发生一次，后面全是 inode 级操作，无竞态可言。

要点：openat 的性能红利

场景 老接口 *at() 接口
深层目录批量操作 每个文件都要全路径解析（逐级查目录） 锚点 fd 已在深处，只解析最后一段
遍历 + 打开 拼串 + 全路径 open dirfd 从 readdir 的目录直接 openat(e->d_name)
多线程 cwd 全局竞争 每线程/每模块自己的锚点 fd，零竞争

对海量小文件（行情落盘、日志分片）的场景，*at() 不是「安全选配」而是吞吐量来源——路径解析是 namei 层的锁与 dcache 查找，省一次全路径就是省一串操作。

代码自测（Q&A）

Q1：openat(AT_FDCWD, "x", O_RDONLY) 和 open("x", O_RDONLY) 有区别吗？ A：没有。AT_FDCWD 就是「用 cwd」，两条完全等价（内核走同一条路径）。所以「为了用 at 而用 AT_FDCWD」是自我安慰——防 TOCTOU 的前提是传入真实的目录 fd*。

Q2：锚点 fd 为什么「不可替换」？ A：fd 在打开时就绑定到了具体 inode（open 完成解析后引用计数 +1）。之后把那个路径改名、删除、甚至换成符号链接，fd 指向的 inode 不变。这正是 §18.3「unlink 后 fd 仍可读」的同一机制。

Q3：fstatat(AT_SYMLINK_NOFOLLOW) 和 lstat 完全等价吗？ A：语义等价（都不跟随），但 fstatat 多了锚定能力：可以「相对某目录 fd 判断类型」，lstat 只能全路径。在遍历中配合 readdir 使用时，fstatat(dirfd, name, AT_SYMLINK_NOFOLLOW) 比「拼串 + lstat」既快又无竞态。

Q4：openat 打开目录 fd 时需要什么 flags？ A：O_RDONLY|O_DIRECTORY 是可移植写法（macOS 无 O_PATH）。Linux 上 O_PATH|O_DIRECTORY 更强（不做权限检查、不能 read 但能当锚点和 fchdir）。跨平台代码用前者。

Q5：为什么说 *at() 族「把 cwd 从代码里删掉了」？ A：因为所有路径操作都可以改写成 *at(anchor, ...) 形式，cwd 从此与逻辑无关——运维从哪个目录启动、哪个线程 chdir 了，都不影响行为。这是一种消除全局状态的重构，价值不亚于安全性本身。

Q6：AT_EMPTY_PATH 是什么？macOS 有吗？ A：Linux 扩展：pathname 传空串时操作fd 本身指向的对象（如 fstatat(fd, "", &sb, AT_EMPTY_PATH) = fstat(fd, &sb)）。macOS 没有。对 fd 的操作在 macOS 上要用对应的 f 版接口（fstat/fchmod/...）。

18.12

Changing the Root Directory of a Process: chroot() 改变进程的根目录

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 chroot(2) / chroot(2) 的 SECURITY NOTES 段 + Linux v6.6 fs/open.c（SYSCALL_DEFINE1(chroot)，检查 CAP_SYS_CHROOT） - 上一节：18.11 *at() 族 - 下一节：18.13 realpath()

本节讲什么

  1. chroot() 改的是路径解析的起点（进程视角的 /），不是「进了某个目录」；
  2. 它需要特权（CAP_SYS_CHROOT）——本机非特权实测 EPERM；
  3. 它不改 cwd——这是书上专门强调、也是最容易漏的一步；
  4. 经典越狱：chroot 前先 open(".") 存 fd，chroot 后 fchdir(fd) 就站到新根之外了——所以「chroot 后必须 chdir("/") 并放弃 fd」不是最佳实践，是必要条件。

要点：契约表

#include <unistd.h>
int chroot(const char *path);
/* 需要 CAP_SYS_CHROOT（Linux）/ root（BSD）；改变调用进程的根目录 */
项 规则
改什么 进程路径解析的起点：之后 /xxx 都从 path 开始找
不改什么 cwd、已打开的 fd、进程可见性、网络、IPC
权限 CAP_SYS_CHROOT（Linux）；本机非特权实测 EPERM
继承 fork 继承新根；exec 保留
可逆吗 没有 unchroot；但（见下）root 有办法出来

与 *at() 的分工：chroot 是「重定义 /」，*at() 是「绕过 /」。前者改变边界，后者在边界内消除竞态。两者正交，可叠加。

实测：非特权 chroot = EPERM

完整源码（code/c18_4_cwd.c）：

/* c18_4_cwd.c — Ch18 §18.10/§18.11/§18.12：进程的工作目录与根目录
 *
 * 钉住的点（全部实测）：
 * ① cwd 是**进程属性**：fork 继承、exec 保留——chdir("…") 后 exec 的
 *    程序会在新 cwd 里找相对路径；
 * ② getcwd 缓冲不足返回 ERANGE（老式 getwd 已废弃）；realloc 循环是标准写法；
 * ③ fchdir + 保存 fd 是「记住老目录」的零开销方案（习题 18-9 的正解之一）；
 *    对比 getcwd+chdir 的字符串方案（有 EAMETOOLONG 与路径重解析成本）；
 * ④ open(".", O_RDONLY) 得到目录 fd——O_PATH/O_RDONLY + fchdir 都用它；
 * ⑤ chroot 非特权一律 EPERM（实测），语义标注（进程视角的 "/" 重定向，
 *    不改变 cwd！chroot 后必须显式 chdir("/")，书上专门强调）。
 *
 * 编译： cc -Wall -Wextra -o c18_4_cwd c18_4_cwd.c
 * 取材： man-pages 6.19 getcwd(3)/chroot(2) + TLPI §18.10-§18.12
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#ifndef PATH_MAX
#define PATH_MAX 4096
#endif

int main(void)
{
    char buf[PATH_MAX];

    /* ---------- ①② getcwd 与 realloc 循环 ---------- */
    printf("== ①② cwd 是进程属性；getcwd 探大小循环 ==\n");
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd"); return EXIT_FAILURE; }
    printf("  初始 cwd = %s\n", buf);

    /* ---------- ③ fchdir + fd 方案（习题 18-9 正解）---------- */
    printf("\n== ③ fchdir + 目录 fd：零字符串开销地「记住老目录」==\n");
    int old_fd = open(".", O_RDONLY);            /* 保存老 cwd 的 fd */
    if (old_fd == -1) { perror("open ."); return EXIT_FAILURE; }
    if (chdir("/") == -1) { perror("chdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd2"); return EXIT_FAILURE; }
    printf("  chdir(/) 后 cwd = %s\n", buf);
    if (fchdir(old_fd) == -1) { perror("fchdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd3"); return EXIT_FAILURE; }
    printf("  fchdir(old_fd) 回到 = %s（无需字符串、无路径重解析）\n", buf);
    printf("  ⚠️ 对比 getcwd(old)+chdir(old) 方案：多一次路径解析、有\n");
    printf("     PATH_MAX 截断风险，且老目录可能已被改名/删除（fd 方案免疫）。\n\n");

    /* ---------- ④ 目录 fd 的另一个用途：openat 的锚点 ---------- */
    printf("== ④ open(\".\") 的目录 fd 也是 openat 的锚点（§18.11）==\n");
    int dfd = open("/tmp", O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open /tmp"); return EXIT_FAILURE; }
    int f2 = openat(dfd, "tlpi_c18_4.txt", O_RDWR | O_CREAT | O_EXCL, 0644);
    printf("  openat(/tmp 的 fd, \"tlpi_c18_4.txt\") = %d（相对锚点，不受 cwd 影响）\n", f2);
    if (f2 != -1) close(f2);
    printf("  ⚠️ openat 防的是「cwd 被别人改走」与 TOCTOU：锚点一旦打开即固定。\n\n");

    /* ---------- ⑤ chroot：非特权 EPERM（实测） ---------- */
    printf("== ⑤ chroot：需要特权（实测）==\n");
    errno = 0;
    int r = chroot("/tmp/tlpi_c18_4_jail");
    printf("  chroot(非特权) = %d errno=%d(%s)  ← 需 CAP_SYS_CHROOT/root\n",
           r, errno, strerror(errno));
    printf("  语义标注（书上强调，未实测——需特权环境）：\n");
    printf("    · chroot 只改进程视角的 \"/\"，**不会改 cwd**；\n");
    printf("    · 经典越狱：chroot 前先 open(\".\") 存 fd，chroot 后\n");
    printf("      fchdir(fd) 就站在新根之外——所以 chroot 必须后接 chdir(\"/\")\n");
    printf("      并放弃 fd（或 double chroot），否则形同虚设。\n");
    close(dfd);
    unlink("/tmp/tlpi_c18_4.txt");
    close(old_fd);
    return EXIT_SUCCESS;
}

诚实标注：本机（macOS 普通用户）只能实测到 EPERM 这一层；chroot 生效后的行为（解析起点改变、越狱路径）来自 man-pages chroot(2) 的 SECURITY NOTES 与 Linux fs/open.c 源码核验，未实测——列入 Pi5 复测清单（Pi 上有 NOPASSWD sudo，可以补齐）。

要点：正确的 chroot 四步（书上的原话顺序，一步都不能少）

/* 1. 备好 jail：把目标程序 + 它依赖的动态库/设备文件都放进去
 *    （否则 exec 之后立刻死：连 ld.so 都找不到）*/
chroot("/srv/jail");        /* 2. 改根 */
chdir("/");                 /* 3. 把 cwd 也挪进新根（关键！）*/
setgid(gid); setgroups(0, NULL); setuid(uid);   /* 4. 丢特权（不可逆）*/
execl("/bin/app", "app", NULL);
步骤 缺了会怎样
2. chroot 没有边界
3. chdir("/") cwd 还在老根里 → 相对路径直接逃逸
4. 丢特权 root 能用「double chroot」逃逸（见下）
备 jail 内容 exec 失败 ENOENT，或运行时缺库/缺 /dev/null

为什么必须先 chdir("/")：chroot 只改「解析起点」，cwd 还是老位置。cwd 里的进程可以用相对路径 ../.. 往上走——cwd 在新根之外，就直接走出去了。

为什么必须丢特权（double chroot 越狱）：持有 CAP_SYS_CHROOT 的进程可以：

mkdir("out", 0755); chroot("out");   /* 现在根在 "out"，但 cwd 已在新根之外的上层 */
chdir("../../../..");                /* 相对 cwd 向上走，离开 jail 的 inode 子树 */
chroot(".");                          /* 把根设到真正的老根 */
/* 完全逃逸 */

这是 man-pages 里白纸黑字写的逃逸路径，也是「chroot 不是安全边界、namespaces 才是」的根源。

要点：chroot vs 容器（namespaces）——为什么说 chroot「只是路径花招」

隔离维度 chroot mount ns + 其他 ns（容器）
文件系统视图 只改 / 的解析起点 完整 mount namespace（连挂载表都隔离）
进程可见性 ❌ 无隔离（kill 仍可达外部进程） pid ns 隔离
网络 ❌ net ns 隔离
用户/特权 需要特权才能设置；特权进程可逃逸 user ns 可映射非特权 root
逃逸面 已知多条（fd 越狱、double chroot） 少得多（且有 seccomp/LSM 叠加）
开销 几乎为零 轻（namespace 切换）但非零

工程结论：chroot 适合「防呆」——防止程序误写到系统目录；不适合「防敌」——防不了有心的攻击者。现代等价物是容器/pivot_root（比 chroot 更难逃逸，因为老根被卸载且 cwd 也被换）。

chroot 后不丢特权 root 可 double chroot 逃逸（见上）；必须 setgid+setuid

代码自测（Q&A）

Q1：chroot 之后，进程还能访问新根之外的文件吗？ A：能，两条路：① cwd 还在外面（忘了 chdir("/")）时相对路径直接出去；② chroot 前 open(".") 存下的 fd 还在手里，fchdir(fd) 就出去了。所以「chroot 后必须 chdir("/") 并关闭多余 fd」是必要条件，不是最佳实践。

Q2：为什么特权进程能 double chroot 逃逸？ A：chroot 可以对任何目录再设一次根。先 mkdir + chroot 把根「往上抬」，此时 cwd 已在新根之外，chdir("../../..") 走到真正的老根，再 chroot(".") 就出来了。要点是「第二次 chroot 把根放回原处」。丢掉特权（setuid 不可逆）后这条路就死了。

Q3：jail 里的程序一 exec 就死，最常见原因？ A：动态链接器（ld-linux.so）不在 jail 里 → 内核加载失败报 ENOENT。其次是缺 /dev/null、/dev/urandom 和 /etc 配置。用 ldd $(which app) 清点依赖，逐个拷进 jail。

Q4：chroot 里面读 /proc 会读到什么？ A：什么都没有——/proc 是挂载点，jail 里没挂就没有。需要的话要在 jail 里 mount -t proc proc /proc（嵌入式忘挂 /proc 是同源坑：ps/top 全失效）。

Q5：pivot_root 比 chroot 强在哪？ A：pivot_root 把整个 mount 的根换掉并把老根卸载（或挂到临时位置后 umount），逃逸者连「往上走」的路径都没有；且它通常配合 mount namespace 使用，改动只影响本 ns。chroot 只是改一个解析起点变量，老树还完整挂着。

Q6：本机实测只能看到 EPERM，为什么笔记还敢写「chroot 不改 cwd」？ A：来自两层核验：man-pages chroot(2) 明确写「The current working directory is not changed」；Linux fs/open.c 的 SYSCALL_DEFINE1(chroot) 只改 current->fs->root，不碰 pwd。行为与源码一致但未在本机运行验证，故 Pi5 复测清单里保留一条（Pi 有 sudo 可实测）。

Resolving a Pathname: realpath() 解析路径名

本章：TLPI 第 18 章 — Directories and Links 实测环境：macOS 26.6.2 (arm64) · clang 23.1.0（micromamba cdev）· APFS；Linux 专有行为按 man-pages 6.19 / 内核 v6.6 源码标注 源码核验：man-pages 6.19 realpath(3) + POSIX.1-2008 + 习题 18-3 自实现与系统库对拍实测 - 上一节：18.12 chroot() - 下一节：18.14 dirname() and basename()

本节讲什么

  1. realpath() 把任意路径解析成「无符号链接、无 ./..、无多余 /」的绝对路径；
  2. 它的语义有个豁口：最后的组件允许不存在——这正是它在「打开前校验」场景里的价值；
  3. 本节最有分量的内容是习题 18-3：自实现一个 realpath 并与系统库逐字节对拍（完整源码见下）；
  4. macOS 的一个「意外教学点」：/etc 本身是符号链接，所以 /etc/../etc/hosts 解析成 /private/etc/hosts——系统库与自实现给出一致的结果。

要点：接口契约

#include <stdlib.h>
char *realpath(const char *path, char *resolved_path);
/* 成功返回 resolved_path（或 malloc 的缓冲）；失败 NULL + errno */
resolved_path 行为 注意
NULL 内部 malloc，调用者负责 free POSIX.1-2008 已标准化，推荐
非 NULL 写入调用者缓冲 缓冲必须 ≥ PATH_MAX，否则可能溢出（实现相关）
errno 含义
ENOENT 路径中（除最后一段外的）某段不存在
EACCES 某级目录缺 x（搜索权）
ELOOP 链接展开超上限（本机实测 40，18.2）
ENAMETOOLONG 路径或某段超长

关键语义：「末组件可以不存在」——realpath("/tmp/不存在.txt") 通常成功（返回 /tmp/不存在.txt，前提是 /tmp 能解析）。这让它在「open 之前先校验用户给的路径」场景里不可替代：既验证了目录部分，又不要求目标已存在。

实测：自实现 vs 系统库对拍（习题 18-3）

完整源码（code/ex18_3_realpath.c）：

/* ex18_3_realpath.c — 习题 18-3：实现 realpath()
 *
 * 题面：实现 realpath()——把任意路径解析为「无符号链接、无 . / ..、
 * 无多余斜杠」的绝对路径。
 *
 * 思路（分层消化）：
 *   1. 相对路径前拼 cwd；
 *   2. 以 '/' 切分组件，逐个处理：
 *        "" / "."  → 跳过
 *        ".."      → 弹栈（模拟目录树回退）
 *        其他      → 压栈（对每个组件做 lstat：是符号链接就 readlink 展开，
 *                    把展开结果按"相对当前栈"拼接后**重新走解析**——递归深度有限，
 *                    超过上限即 ELOOP）
 *   3. 末组件允许不存在（realpath 的 resolved 语义：最后的组件可以不存在）。
 *
 * 简化声明（诚实）：本实现是**教学版**——不含路径级权限检查（realpath 契约里
 * 每级目录要可搜索 x），ELOOP 上限取 40（macOS 实测值；Linux SYMLOOP 上限 40）。
 * 逐组件用 lstat+readlink 与内核路径解析同构，核心逻辑与原书答案一致。
 *
 * 编译： cc -Wall -Wextra -o ex18_3_realpath ex18_3_realpath.c
 * 取材： TLPI §18.13 习题 18-3；man-pages realpath(3)
 */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

#ifndef PATH_MAX
#define PATH_MAX 4096
#endif
#define MAX_LINKS 40

/* 把组件栈渲染成绝对路径 */
static void join(char *out, size_t n, char **comp, int depth)
{
    if (depth == 0) { snprintf(out, n, "/"); return; }
    size_t used = 0;
    for (int i = 0; i < depth; i++)
        used += (size_t) snprintf(out + used, n - used, "/%s", comp[i]);
}

/* 逐组件解析；返回 0 成功（结果在 out），-1 出错 */
static int resolve(const char *in, char *out, size_t n, int *links_used)
{
    char work[PATH_MAX * 2];
    char *comp[256];
    int depth = 0;

    /* 相对路径 → 拼 cwd */
    if (in[0] != '/') {
        char cwd[PATH_MAX];
        if (getcwd(cwd, sizeof cwd) == NULL)
            return -1;
        snprintf(work, sizeof work, "%s/%s", cwd, in);
    } else {
        snprintf(work, sizeof work, "%s", in);
    }

    char *save = NULL;
    for (char *tok = strtok_r(work, "/", &save); tok;
         tok = strtok_r(NULL, "/", &save)) {
        if (strcmp(tok, ".") == 0)
            continue;
        if (strcmp(tok, "..") == 0) {
            if (depth > 0) depth--;         /* 根之上再 .. 停在根 */
            continue;
        }
        comp[depth++] = tok;

        /* 检查这一级是否是符号链接 */
        char cur[PATH_MAX];
        join(cur, sizeof cur, comp, depth);
        struct stat sb;
        if (lstat(cur, &sb) == -1) {
            /* 只允许最后一个组件不存在（realpath 语义） */
            if (errno == ENOENT && strtok_r(NULL, "/", &save) == NULL)
                break;
            return -1;
        }
        if (S_ISLNK(sb.st_mode)) {
            if (++(*links_used) > MAX_LINKS) { errno = ELOOP; return -1; }
            char target[PATH_MAX];
            ssize_t tl = readlink(cur, target, sizeof target - 1);
            if (tl == -1) return -1;
            target[tl] = '\0';
            /* 链接目标 + 未处理的剩余部分 → 重新解析 */
            depth--;
            char rest[PATH_MAX];
            char *rem = strtok_r(NULL, "", &save);   /* 剩余原文 */
            snprintf(rest, sizeof rest, "%s%s%s",
                     target, rem ? "/" : "", rem ? rem : "");
            /* 拼上已解析前缀，继续循环 */
            char prefix[PATH_MAX];
            join(prefix, sizeof prefix, comp, depth);
            char combined[PATH_MAX * 2];
            if (rest[0] == '/')
                snprintf(combined, sizeof combined, "%s", rest);
            else
                snprintf(combined, sizeof combined, "%s%s/%s",
                         depth > 0 ? prefix : "", depth > 0 ? "" : "/", rest);
            char in2[PATH_MAX * 2];
            snprintf(in2, sizeof in2, "%s", combined);
            char out2[PATH_MAX];
            if (resolve(in2, out2, sizeof out2, links_used) == -1)
                return -1;
            snprintf(out, n, "%s", out2);
            return 0;
        }
    }
    join(out, n, comp, depth);
    return 0;
}

int main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "Usage: %s path\n", argv[0]);
        return EXIT_FAILURE;
    }
    int links = 0;
    char out[PATH_MAX];
    if (resolve(argv[1], out, sizeof out, &links) == -1) {
        fprintf(stderr, "realpath(%s): %s\n", argv[1], strerror(errno));
        return EXIT_FAILURE;
    }
    printf("输入: %s\n自实现: %s\n", argv[1], out);

    /* 与系统 realpath 对拍 */
    char *sys = realpath(argv[1], NULL);
    if (sys) {
        printf("系统库: %s\n%s\n", sys,
               strcmp(sys, out) == 0 ? "→ 一致 ✔" : "→ 不一致 ✘");
        free(sys);
    } else {
        printf("系统库: 失败（%s）——常见于末组件不存在的情况差异\n", strerror(errno));
    }
    return 0;
}

代码自测（Q&A）

Q1：为什么 /etc/../etc/hosts 不能字符串消成 /etc/hosts？ A：因为 /etc 是符号链接（macOS 指向 /private/etc）。.. 的语义是「物理父目录」，即 inode 层面的 parent——/etc/.. 解析到 /private，不是 /。所以正确答案是 /private/etc/hosts。实测自实现（逐级 lstat）与系统库一致，字符串消法会给出错误结果。

Q2：自实现和系统库在「末组件不存在」时为什么不一致？ A：POSIX 允许（甚至期望）realpath 对「末组件不存在」返回成功（只要目录部分能解析）；macOS 的 libc 实现按严格语义报 ENOENT。两者都符合标准字面（标准在这里留了实现自由）。跨平台代码不要依赖这个分支的行为。

Q3：realpath 的解析为什么要「重新走」而不是原地替换？ A：链接目标本身可能是相对路径、又含 ..、又指向另一个链接。把「目标 + 剩余部分」拼成一个新输入重新解析，才能正确处理所有嵌套情况；原地替换无法处理「目标是相对路径」的情况。

Q4：realpath 能防止符号链接攻击吗？ A：能防「路径长什么样」的攻击（穿越、环），不能防 TOCTOU——解析完成后、open 之前，攻击者仍可替换路径中的某一级。完整方案是 realpath 校验 + openat/O_NOFOLLOW 原子打开（§18.11）。

Q5：realpath(path, NULL) 与固定缓冲各适合什么场合？ A：NULL（malloc）：路径长度未知、或想避免 PATH_MAX 硬编码，代价是要 free；固定缓冲：栈上即可、无分配失败分支，但要保证 ≥ PATH_MAX 且接受「超长路径直接失败」。

Q6：自实现里为什么链接计数用 40？ A：本机实测的解析上限（18.2 实测：串 200 层链接，40 层是临界点）；Linux 的 MAXSYMLINKS 同为 40。教学版取 40 与内核对齐；生产实现应该用 ELOOP 的实际发生来判断而不是硬编码计数。

② 不检查文件系统

要点：什么时候用它们，什么时候自己写

需求 用什么

手写版（线程安全、不改输入）：

const char *safe_basename(const char *path) {
    if (!path || !*path) return ".";
    const char *end = path + strlen(path);
    while (end > path && end[-1] == '/') end--;    /* 吃掉尾部斜杠 */
    if (end == path) return "/";                    /* 全是斜杠 */
    const char *start = end;
    while (start > path && start[-1] != '/') start--;
    return start;                                   /* 指向原串内部，无需复制 */
}

代码自测（Q&A）

Q1：为什么 dirname 和 basename 不能用同一个输入？ A：实现要找最后一个 / 并把它改成 '\0' 来就地切分。dirname("/usr/lib/libc.so") 返回 /usr/lib 的同时把第 9 个字符改成了 NUL——此时再用同一指针调 basename，看到的是 /usr/lib 这个残串，得到 lib。各自 strdup 是唯一正解。

Q2：basename("/usr/") 为什么是 usr 而不是空串？ A：POSIX 规定尾部的多个斜杠都忽略。/usr/ 语义上就是 /usr，所以 basename 是 usr、dirname 是 /。这也是为什么 /// 两把都给 /——斜杠全被吃掉后剩的是根。

Q3：basename("..") 为什么保留 .. 而 dirname 给 .？ A：.. 本身是一个名字（目录项就叫这两个字符），所以 basename 保留它；而它前面没有目录部分，dirname 按规则给 .。同理 . 的两把都是 .。

Q4：返回的指针指向哪里？能用多久？ A：三种可能：输入串内部（GNU）、静态缓冲（POSIX 某些实现）、或调用者缓冲。只有「下一次调用前」有效。要用久就 strdup 返回值。原书 Listing 18-5 在同一次 printf 里用完就 free，是标准姿势。

Q5：需要线程安全的路径切分怎么办？ A：三个选择：① 手写（strrchr + 边界处理，十几行，不改输入）；② 先 strdup 再调 POSIX 版（仍有静态缓冲风险，看实现）；③ 加互斥锁（性能差）。生产代码选 ①。

Q6：这些函数和 realpath 的输出能混用吗？ A：能，但要清楚它们回答不同的问题：dirname/basename 回答「这条字符串怎么读」，realpath 回答「这个路径物理上指向哪」。日志记录用前者（可复现），安全校验用后者（物理事实）。

Q1：本章哪几条实测结论与「书上的话」不一致，写代码时要当心？ A：① macOS seekdir 恒等于 rewinddir（书按 POSIX 契约描述）；② macOS 不 enforce ETXTBSY（书按 Linux 描述）；③ macOS/APFS 目录 st_size 非块对齐（书按「块整数倍」描述）；④ macOS 链接有自己的 uid/gid/mode（书说权限被忽略）；⑤ realpath 对「末组件不存在」的实现差异。全部已在本章各节实测钉住。

Q2：「把名字换成引用」具体指什么？为什么它消除竞态？ A：指尽早 open（得到绑定 inode 的 fd），之后不再做路径操作（用 fstat/fchmod/fchdir/readlinkat 等 fd 级接口）。路径解析（TOCTOU 所在）只发生一次；fd 一旦建立，后续操作的对象固定，不存在「检查与使用之间被换掉」。

Q3：本章哪几个接口能做「原子」互斥？为什么 rename 不行？ A：link()（目标存在则 EEXIST）、open(O_CREAT|O_EXCL)、mkdir()（存在则 EEXIST）——三者都是「检查+创建」在内核一步完成。rename 是无条件覆盖，两个进程同时 rename 都成功，锁形同虚设。

Q4：目录操作里最容易被忽略的性能点？ A：路径解析。每条全路径 open 都要从 / 逐级走（namei + dcache 锁）；深目录 + 海量文件时 openat 锚点（只解析最后一段）是数量级差距。其次是大目录的 readdir 顺序（无序 → 排序成本）。

Q5：如果要给本章画一张「安全性等级」图，怎么排？ A：从弱到强：字符串拼路径 → 全路径 stat+open（TOCTOU）→ O_NOFOLLOW → realpath 校验 → *at() 锚点 → 全 fd 化（open 后只用 f 系接口）→ chroot/容器（边界隔离，但 chroot 本身可逃逸）。工程正解通常是「*at() 锚点 + O_NOFOLLOW」这一档——不需要特权，覆盖面够。

Q6：本章与 Ch19（inotify）怎么衔接？ A：本章所有目录操作都是「拉」模型（主动查）；Ch19 的 inotify 是「推」模型（内核主动通知目录变化）。配置热更新 = 本章的 safe-write + Ch19 的事件监听；目录监控 = Ch19 的 IN_CREATE/IN_DELETE/IN_MOVED_FROM。两者合起来才是完整的文件系统编程图景。

18-1 为什么能「覆盖」正在执行的程序？

题面（转述）：§4.3.2 说过「文件正在被执行时不能写打开（ETXTBSY）」。但从 shell 里却可以：编译出 longrunner、后台跑起来、修改源码、再次 cc -o longrunner longrunner.c——最后这条成功。为什么？（提示：用 ls -li 看两次编译后的 inode。）

答案（两部分，程序四段逐条钉住）：

  1. 两次编译产出的是两个不同 inode。cc 从不写老文件：它把新二进制写到临时文件，再 rename 覆盖名字。老 inode 的 nlink 归零，但运行中进程的 fd（准确说是 exec 时建立的文本映射引用）把它吊住，直到进程退出才真正释放——正是 §18.3 的释放条件。
  2. 直接写打开正在执行的文件才被拒（Linux ETXTBSY），而 rename 换目录项不算「写文件」。

实测输出（macOS，子进程探活确认有效）：

  → 平台签名二进制离开原位置即被 AMFI/taskgated 干掉。
     若用它当长跑程序，子进程秒退 → 后面所有结论都是假的。

18-3 实现 realpath()

题面（转述）：实现 realpath()——把路径解析为无符号链接、无 ./..、无多余斜杠的绝对路径。

实现（教学版：逐组件 lstat + readlink 展开 + 栈式 .. 处理，链接计数上限 40 与内核对齐；诚实声明不含逐级权限检查）。

完整源码（code/ex18_3_realpath.c）：

/* ex18_3_realpath.c — 习题 18-3：实现 realpath()
 *
 * 题面：实现 realpath()——把任意路径解析为「无符号链接、无 . / ..、
 * 无多余斜杠」的绝对路径。
 *
 * 思路（分层消化）：
 *   1. 相对路径前拼 cwd；
 *   2. 以 '/' 切分组件，逐个处理：
 *        "" / "."  → 跳过
 *        ".."      → 弹栈（模拟目录树回退）
 *        其他      → 压栈（对每个组件做 lstat：是符号链接就 readlink 展开，
 *                    把展开结果按"相对当前栈"拼接后**重新走解析**——递归深度有限，
 *                    超过上限即 ELOOP）
 *   3. 末组件允许不存在（realpath 的 resolved 语义：最后的组件可以不存在）。
 *
 * 简化声明（诚实）：本实现是**教学版**——不含路径级权限检查（realpath 契约里
 * 每级目录要可搜索 x），ELOOP 上限取 40（macOS 实测值；Linux SYMLOOP 上限 40）。
 * 逐组件用 lstat+readlink 与内核路径解析同构，核心逻辑与原书答案一致。
 *
 * 编译： cc -Wall -Wextra -o ex18_3_realpath ex18_3_realpath.c
 * 取材： TLPI §18.13 习题 18-3；man-pages realpath(3)
 */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

#ifndef PATH_MAX
#define PATH_MAX 4096
#endif
#define MAX_LINKS 40

/* 把组件栈渲染成绝对路径 */
static void join(char *out, size_t n, char **comp, int depth)
{
    if (depth == 0) { snprintf(out, n, "/"); return; }
    size_t used = 0;
    for (int i = 0; i < depth; i++)
        used += (size_t) snprintf(out + used, n - used, "/%s", comp[i]);
}

/* 逐组件解析；返回 0 成功（结果在 out），-1 出错 */
static int resolve(const char *in, char *out, size_t n, int *links_used)
{
    char work[PATH_MAX * 2];
    char *comp[256];
    int depth = 0;

    /* 相对路径 → 拼 cwd */
    if (in[0] != '/') {
        char cwd[PATH_MAX];
        if (getcwd(cwd, sizeof cwd) == NULL)
            return -1;
        snprintf(work, sizeof work, "%s/%s", cwd, in);
    } else {
        snprintf(work, sizeof work, "%s", in);
    }

    char *save = NULL;
    for (char *tok = strtok_r(work, "/", &save); tok;
         tok = strtok_r(NULL, "/", &save)) {
        if (strcmp(tok, ".") == 0)
            continue;
        if (strcmp(tok, "..") == 0) {
            if (depth > 0) depth--;         /* 根之上再 .. 停在根 */
            continue;
        }
        comp[depth++] = tok;

        /* 检查这一级是否是符号链接 */
        char cur[PATH_MAX];
        join(cur, sizeof cur, comp, depth);
        struct stat sb;
        if (lstat(cur, &sb) == -1) {
            /* 只允许最后一个组件不存在（realpath 语义） */
            if (errno == ENOENT && strtok_r(NULL, "/", &save) == NULL)
                break;
            return -1;
        }
        if (S_ISLNK(sb.st_mode)) {
            if (++(*links_used) > MAX_LINKS) { errno = ELOOP; return -1; }
            char target[PATH_MAX];
            ssize_t tl = readlink(cur, target, sizeof target - 1);
            if (tl == -1) return -1;
            target[tl] = '\0';
            /* 链接目标 + 未处理的剩余部分 → 重新解析 */
            depth--;
            char rest[PATH_MAX];
            char *rem = strtok_r(NULL, "", &save);   /* 剩余原文 */
            snprintf(rest, sizeof rest, "%s%s%s",
                     target, rem ? "/" : "", rem ? rem : "");
            /* 拼上已解析前缀，继续循环 */
            char prefix[PATH_MAX];
            join(prefix, sizeof prefix, comp, depth);
            char combined[PATH_MAX * 2];
            if (rest[0] == '/')
                snprintf(combined, sizeof combined, "%s", rest);
            else
                snprintf(combined, sizeof combined, "%s%s/%s",
                         depth > 0 ? prefix : "", depth > 0 ? "" : "/", rest);
            char in2[PATH_MAX * 2];
            snprintf(in2, sizeof in2, "%s", combined);
            char out2[PATH_MAX];
            if (resolve(in2, out2, sizeof out2, links_used) == -1)
                return -1;
            snprintf(out, n, "%s", out2);
            return 0;
        }
    }
    join(out, n, comp, depth);
    return 0;
}

int main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "Usage: %s path\n", argv[0]);
        return EXIT_FAILURE;
    }
    int links = 0;
    char out[PATH_MAX];
    if (resolve(argv[1], out, sizeof out, &links) == -1) {
        fprintf(stderr, "realpath(%s): %s\n", argv[1], strerror(errno));
        return EXIT_FAILURE;
    }
    printf("输入: %s\n自实现: %s\n", argv[1], out);

    /* 与系统 realpath 对拍 */
    char *sys = realpath(argv[1], NULL);
    if (sys) {
        printf("系统库: %s\n%s\n", sys,
               strcmp(sys, out) == 0 ? "→ 一致 ✔" : "→ 不一致 ✘");
        free(sys);
    } else {
        printf("系统库: 失败（%s）——常见于末组件不存在的情况差异\n", strerror(errno));
    }
    return 0;
}

/* list_files_readdir_r.c

   Demonstrate the use of opendir() and readdir_r() to list files
   in a directory.

   Usage: list_files_readdir_r [dir...]

   Walks through each directory named on the command line (current directory
   if none are specified) to display a list of the files it contains.

   See also list_files_readdir.c.
*/
#if defined(__APPLE__)
        /* Darwin requires this header before including <dirent.h> */
#include <sys/types.h>
#endif
#include <limits.h>
#include <dirent.h>
#include <stddef.h>
#include "tlpi_hdr.h"

static void             /* List all files in directory 'dirpath' */
listFiles(const char *dirpath)
{
    DIR *dirp;
    Boolean isCurrent;          /* True if 'dirpath' is "." */
    struct dirent *result, *entryp;
    int nameMax;

    isCurrent = strcmp(dirpath, ".") == 0;

    /* On Linux, NAME_MAX is defined in <limits.h>. However, this limit
       may vary across file systems, so we really should use pathconf()
       to find the true limit for this file system. */

    nameMax = pathconf(dirpath, _PC_NAME_MAX);
    if (nameMax == -1)          /* Indeterminate or error */
        nameMax = 255;          /* So take a guess */

    entryp = malloc(offsetof(struct dirent, d_name) + nameMax + 1);
    if (entryp == NULL)
        errExit("malloc");

    /* Open the directory - on failure print an error and return */

    dirp = opendir(dirpath);
    if (dirp == NULL) {
        errMsg("opendir failed on '%s'", dirpath);
        free(entryp);
        return;
    }

    /* Look at each of the entries in this directory */

    for (;;) {
        errno = readdir_r(dirp, entryp, &result);
        if (errno != 0)
            errExit("readdir_r");

        if (result == NULL)     /* End of stream */
            break;

        /* Skip . and .. */

        if (strcmp(entryp->d_name, ".") == 0 ||
                strcmp(entryp->d_name, "..") == 0)
            continue;

        /* Print directory + filename */

        if (!isCurrent) printf("%s/", dirpath);
        printf("%s\n", entryp->d_name);
    }

    if (closedir(dirp) == -1)
        errMsg("closedir");
}

int
main(int argc, char *argv[])
{
    if (argc == 1)              /* No arguments - use current directory */
        listFiles(".");
    else
        for (argv++; *argv; argv++)
            listFiles(*argv);
    exit(EXIT_SUCCESS);
}

但要注意时效：readdir_r 在 POSIX.1-2008 之后已废弃（glibc 手册明说）。原因：① 缓冲大小要用 offsetof(struct dirent, d_name) + pathconf(_PC_NAME_MAX) + 1 反人类地算；② 返回值语义与 errno 混淆。现代正解是每个线程独立 opendir，或对共享 DIR 加锁。本题的价值在理解「为什么 readdir 不可重入」（静态内部缓冲），而不在于真的用 readdir_r。

/* file_type_stats.c

   An example of the use of nftw(): traverse the directory tree named in the
   command line, and print out statistics about the types of file in the tree.
*/
#if defined(__sun)
#define _XOPEN_SOURCE 500   /* Solaris 8 needs it this way */
#else
#if ! defined(_XOPEN_SOURCE) || _XOPEN_SOURCE < 600
#define _XOPEN_SOURCE 600   /* Get nftw() and S_IFSOCK declarations */
#endif
#endif
#include <ftw.h>
#include "tlpi_hdr.h"

static int numReg = 0, numDir = 0, numSymLk = 0, numSocket = 0,
           numFifo = 0, numChar = 0, numBlock = 0,
           numNonstatable = 0;

static int
countFile(const char *path, const struct stat *sb, int flag, struct FTW *ftwb)

{
    if (flag == FTW_NS) {
        numNonstatable++;
        return 0;
    }

    switch (sb->st_mode & S_IFMT) {
    case S_IFREG:  numReg++;    break;
    case S_IFDIR:  numDir++;    break;
    case S_IFCHR:  numChar++;   break;
    case S_IFBLK:  numBlock++;  break;
    case S_IFLNK:  numSymLk++;  break;
    case S_IFIFO:  numFifo++;   break;
    case S_IFSOCK: numSocket++; break;
    }
    return 0;           /* Always tell nftw() to continue */
}

static void
printStats(const char *msg, int num, int numFiles)
{
    printf("%-15s   %6d %6.1f%%\n", msg, num, num * 100.0 / numFiles);
}

int
main(int argc, char *argv[])
{
    if (argc != 2 || strcmp(argv[1], "--help") == 0)
        usageErr("%s dir-path\n", argv[0]);

    /* Traverse directory tree counting files; don't follow symbolic links */

    if (nftw(argv[1], &countFile, 20, FTW_PHYS) == -1)
        errExit("nftw");

    int numFiles = numReg + numDir + numSymLk + numSocket +
                numFifo + numChar + numBlock + numNonstatable;

    if (numFiles == 0) {
        printf("No files found\n");
    } else {
        printf("Total files:      %6d\n", numFiles);
        printStats("Regular:", numReg, numFiles);
        printStats("Directory:", numDir, numFiles);
        printStats("Char device:", numChar, numFiles);
        printStats("Block device:", numBlock, numFiles);
        printStats("Symbolic link:", numSymLk, numFiles);
        printStats("FIFO:", numFifo, numFiles);
        printStats("Socket:", numSocket, numFiles);
        printStats("Non-statable:", numNonstatable, numFiles);
    }
    exit(EXIT_SUCCESS);
}

18-9 「记住老目录」哪种方案高效？

题面（转述）：§18.10 给了两种回到老 cwd 的方法（fchdir vs getcwd+chdir）。反复操作时哪种更高效？为什么？写程序验证。

答案与实测：fd 方案（open(".") + fchdir）。三层理由 + 实测：

  1. 省一次完整路径解析：chdir(buf) 要从 / 逐级 namei；fchdir(fd) 只是从 fd 拿到 inode 引用，无解析。
  2. 免疫路径变化：老目录被改名/移动后，字符串方案 chdir(老路径) 失败，fd 方案照常回去（fd 绑定 inode 不绑定路径）——18.10 实测。
  3. 无 PATH_MAX 截断风险、无额外内存。

完整源码（code/c18_4_cwd.c）：

/* c18_4_cwd.c — Ch18 §18.10/§18.11/§18.12：进程的工作目录与根目录
 *
 * 钉住的点（全部实测）：
 * ① cwd 是**进程属性**：fork 继承、exec 保留——chdir("…") 后 exec 的
 *    程序会在新 cwd 里找相对路径；
 * ② getcwd 缓冲不足返回 ERANGE（老式 getwd 已废弃）；realloc 循环是标准写法；
 * ③ fchdir + 保存 fd 是「记住老目录」的零开销方案（习题 18-9 的正解之一）；
 *    对比 getcwd+chdir 的字符串方案（有 EAMETOOLONG 与路径重解析成本）；
 * ④ open(".", O_RDONLY) 得到目录 fd——O_PATH/O_RDONLY + fchdir 都用它；
 * ⑤ chroot 非特权一律 EPERM（实测），语义标注（进程视角的 "/" 重定向，
 *    不改变 cwd！chroot 后必须显式 chdir("/")，书上专门强调）。
 *
 * 编译： cc -Wall -Wextra -o c18_4_cwd c18_4_cwd.c
 * 取材： man-pages 6.19 getcwd(3)/chroot(2) + TLPI §18.10-§18.12
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#ifndef PATH_MAX
#define PATH_MAX 4096
#endif

int main(void)
{
    char buf[PATH_MAX];

    /* ---------- ①② getcwd 与 realloc 循环 ---------- */
    printf("== ①② cwd 是进程属性；getcwd 探大小循环 ==\n");
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd"); return EXIT_FAILURE; }
    printf("  初始 cwd = %s\n", buf);

    /* ---------- ③ fchdir + fd 方案（习题 18-9 正解）---------- */
    printf("\n== ③ fchdir + 目录 fd：零字符串开销地「记住老目录」==\n");
    int old_fd = open(".", O_RDONLY);            /* 保存老 cwd 的 fd */
    if (old_fd == -1) { perror("open ."); return EXIT_FAILURE; }
    if (chdir("/") == -1) { perror("chdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd2"); return EXIT_FAILURE; }
    printf("  chdir(/) 后 cwd = %s\n", buf);
    if (fchdir(old_fd) == -1) { perror("fchdir"); return EXIT_FAILURE; }
    if (getcwd(buf, sizeof buf) == NULL) { perror("getcwd3"); return EXIT_FAILURE; }
    printf("  fchdir(old_fd) 回到 = %s（无需字符串、无路径重解析）\n", buf);
    printf("  ⚠️ 对比 getcwd(old)+chdir(old) 方案：多一次路径解析、有\n");
    printf("     PATH_MAX 截断风险，且老目录可能已被改名/删除（fd 方案免疫）。\n\n");

    /* ---------- ④ 目录 fd 的另一个用途：openat 的锚点 ---------- */
    printf("== ④ open(\".\") 的目录 fd 也是 openat 的锚点（§18.11）==\n");
    int dfd = open("/tmp", O_RDONLY | O_DIRECTORY);
    if (dfd == -1) { perror("open /tmp"); return EXIT_FAILURE; }
    int f2 = openat(dfd, "tlpi_c18_4.txt", O_RDWR | O_CREAT | O_EXCL, 0644);
    printf("  openat(/tmp 的 fd, \"tlpi_c18_4.txt\") = %d（相对锚点，不受 cwd 影响）\n", f2);
    if (f2 != -1) close(f2);
    printf("  ⚠️ openat 防的是「cwd 被别人改走」与 TOCTOU：锚点一旦打开即固定。\n\n");

    /* ---------- ⑤ chroot：非特权 EPERM（实测） ---------- */
    printf("== ⑤ chroot：需要特权（实测）==\n");
    errno = 0;
    int r = chroot("/tmp/tlpi_c18_4_jail");
    printf("  chroot(非特权) = %d errno=%d(%s)  ← 需 CAP_SYS_CHROOT/root\n",
           r, errno, strerror(errno));
    printf("  语义标注（书上强调，未实测——需特权环境）：\n");
    printf("    · chroot 只改进程视角的 \"/\"，**不会改 cwd**；\n");
    printf("    · 经典越狱：chroot 前先 open(\".\") 存 fd，chroot 后\n");
    printf("      fchdir(fd) 就站在新根之外——所以 chroot 必须后接 chdir(\"/\")\n");
    printf("      并放弃 fd（或 double chroot），否则形同虚设。\n");
    close(dfd);
    unlink("/tmp/tlpi_c18_4.txt");
    close(old_fd);
    return EXIT_SUCCESS;
}

代码自测（Q&A）

Q1：18-1 里「cc 的覆盖」和「直接写打开」的本质区别是什么？ A：前者是目录表操作（rename 换目录项指向新 inode），后者是inode 写操作（要真的改老 inode 的数据）。内核只对后者施加 ETXTBSY；目录表层面没有任何「这个文件在跑」的概念。所以 rename 永远能成功。

Q2：为什么 macOS 的签名机制会 SIGKILL 拷贝的 /bin/sleep？ A：/bin/sleep 带 Apple 平台签名（Platform identifier=26），系统强制它只能从受信位置运行；拷到 /tmp 后签名校验语境失效，AMFI 直接 SIGKILL。自己 clang 编译的是 ad-hoc 签名，无位置约束。这是做系统实验时的 macOS 专属陷阱，Linux 无此机制。

Q3：18-3 的自实现与系统库最可能在哪类输入上分歧？ A：① 末组件不存在（POSIX 允许成功、macOS 实测报 ENOENT）；② 路径中某级目录无 x 权限（教学版没做逐级权限检查）；③ 超长路径（教学版按 PATH_MAX 截断语义，实际 realpath 契约是报错）。教学版的边界都写在源码头注释里。

Q4：18-7 的统计为什么必须 FTW_PHYS？不加会怎样？ A：不加时指向目录的链接会被当作目录下钻，其子树的每个文件都会被再数一次（实测 inode 相同、条目重复）。/etc 这类含 /etc/periodic -> ... 链接的目录立刻就能看出重复计数。

Q5：18-9 的两种方案，除了效率还有什么区别值得记？ A：失败模式不同。字符串方案在「老目录被改名/删除」时回不去（chdir 失败）；fd 方案在同样情况下照常回去（fd 绑定 inode）。对一个长期运行、目录结构可能变化的服务，后者是唯一正确的选择——效率反而是次要的。

Q6：这 9 道题里哪道最有工程价值？ A：18-1。它把 §18.3（unlink 语义）、§18.4（rename 原子替换）和真实部署（灰度发布、热更新不掉数据）串成一条线，且顺带钉出了 macOS 签名与 ETXTBSY 两个跨平台坑。其次是 18-3（.. 的物理语义是安全代码的地基）。
