#include <stdio.h>
#include <unistd.h>
#include <string.h>

/* Ch1 历史/标准章 — 用最小程序演示"POSIX C 接口"长什么样。
 * write() 是 POSIX 标准系统调用（经 libc 包装）；
 * printf() 是 C 标准库（ISO C），底层最终也调 write()。
 * 编译: gcc -o ch1_demo ch1_demo.c */

int main(void) {
    /* POSIX 系统调用：直接经 libc 陷入内核 */
    if (write(STDOUT_FILENO, "hello via write()\n", 18) < 0)
        perror("write");

    /* ISO C 标准库：用户态缓冲，flush 时才调 write() */
    printf("hello via printf()\n");
    fflush(stdout);

    /* 检查 POSIX 标准是否定义了某些宏 */
#ifdef _POSIX_VERSION
    printf("_POSIX_VERSION = %ldL\n", (long)_POSIX_VERSION);
#else
    printf("POSIX not defined\n");
#endif
    return 0;
}

要点

  1. 1969 Ken Thompson，Bell 实验室，PDP-7 汇编初代 UNIX
  2. 1973 Ritchie 发明 C；UNIX 内核用 C 重写 → 可移植革命
  3. 1979 UNIX V7 后分裂两大分支：
    - BSD（伯克利）：TCP/IP 套接字、信号、csh；FreeBSD、macOS XNU 源自此
    - System V：IPC（消息队列、信号量、共享内存）
  4. 分支接口分歧 → 移植成本高 → 催生 POSIX 标准化

HFT / 嵌入式关联

路线 要点
嵌入式 BSD 分支带来 TCP/IP 套接字，是嵌入式联网设备网络栈源头；System V 带来 IPC（消息队列/信号量/共享内存），嵌入式进程间通信常用
HFT 套接字（BSD）是行情/下单网络通道基础，共享内存（SysV/POSIX）是跨进程零拷贝低延迟共享行情的核心手段；两大分支接口分歧正是 POSIX 标准化的动因

01.3

Linux = 内核 + GNU 工具链（必分清）

本章：TLPI 第 01 章 — History and Standards - 上一节：01.2 UNIX & C 极简时间线 - 下一节：01.4 标准化：POSIX / SUS / LSB

本节讲什么

GNU（GNU's Not Unix）是 Stallman 发起的自由软件项目：目标是提供一套完全自由、兼容 UNIX 风格的操作系统，重点在用户态组件（编译器、编辑器、C 库、shell、常用命令等）。 Linus 写的是 Linux 内核（1991）：管进程、内存、驱动、系统调用等底层；不含 shell/ls/gcc 这类用户态程序。 GNU 自己的内核（Hurd）未成主流；和 Linux 内核一结合，才形成日常说的「Linux 系统」。

要点

GNU（GNU's Not Unix）是 Stallman 发起的自由软件项目：目标是提供一套完全自由、兼容 UNIX 风格的操作系统，重点在用户态组件（编译器、编辑器、C 库、shell、常用命令等）。
Linus 写的是 Linux 内核（1991）：管进程、内存、驱动、系统调用等底层；不含 shell/ls/gcc 这类用户态程序。
GNU 自己的内核（Hurd）未成主流；和 Linux 内核一结合，才形成日常说的「Linux 系统」。

部件 谁 内容
Linux 内核 Linus 等 地基：硬件与资源管理、syscall
GNU 用户态 Stallman 项目等 房子：glibc、bash、gcc、make、coreutils（ls/cp…）

完整发行版 ≈ Linux 内核 + GNU 用户态工具链（再加包管理、桌面等；其中也有非 GNU 组件，如 systemd）

类比：内核 = 地基，GNU = 盖在上面的房子；只有内核几乎没法日常用。

❌ 勿混：Linux ≠ GNU。内核与用户态是两套独立项目；Linus 没写 GNU，Stallman 也没写 Linux 内核。
glibc 封装 syscall — 对照 04 LKD Ch5 libc≠syscall

HFT / 嵌入式关联

路线 要点
嵌入式 嵌入式系统 = Linux 内核 + 裁剪的 GNU 用户态（busybox 替代 coreutils、musl 替代 glibc）；分清内核与用户态才知道哪些在改内核、哪些在改应用
HFT 交易进程跑在用户态（glibc 封装 syscall），性能优化主战场在用户态代码与内核调度；理解 glibc≠内核，避免把库调用误当系统调用开销

代码示例

#include <unistd.h>
/* Linux = 内核; GNU = 工具链; 发行版 = 内核 + GNU */
int main(void) {
    /* GNU C 扩展示例: typeof */
    int x = 42;
    typeof(x) y = x + 1;
    printf("typeof demo: x=%d y=%d\n", x, y);
    return 0;
}

1.3

Standardization

本章：TLPI 第 01 章 — History and Standards

一句话（双线共用）：主力标准 POSIX；SUS 当拓展参考；LSB 工程里忘掉。 - UNIX（商标）：须通过 SUS 等认证。 - Linux：遵循 POSIX 接口语义，但没有官方 UNIX 认证 → 习惯称「类 UNIX」。

要点

一句话（双线共用）：主力标准 POSIX；SUS 当拓展参考；LSB 工程里忘掉。

标准 层级 作用 对本仓库
POSIX（IEEE 1003.1） 源码级可移植 定义 syscall/文件 I/O/进程/信号/pthread/实时接口、clock_gettime、mmap… 主力；Linux 尽可能兼容（未花钱官方认证，日常按这套语义写）
SUS（Single UNIX Specification） POSIX + 额外扩展 通过认证才能合法用 「UNIX」商标 了解即可；发行版几乎不花钱认证；写代码很少刻意追 SUS
LSB（Linux Standard Base） 曾求跨发行版二进制兼容 一份编译产物多发行版跑 已废：末版约 2015，停维护；Yocto/主流发行版已撤；嵌入式/HFT 不考虑。Primer 为何仍写：见 08-lsb-vs-posix

易混考点：Linux ≠ UNIX（商标）

  • UNIX（商标）：须通过 SUS 等认证。
  • Linux：遵循 POSIX 接口语义，但没有官方 UNIX 认证 → 习惯称「类 UNIX」。

HFT / 嵌入式关联

路线 要点
嵌入式 嵌入式应用层以 POSIX 为基准，代码易在 x86 PC 与 ARM 板子间移植；LSB 已废（2015 停维护），Yocto 裁剪根文件系统下二进制兼容无价值，直接忽略
HFT 交易代码基础逻辑尽量 POSIX（可移植），热路径优化才用 Linux 专属接口；SUS/LSB 对固化机房（固定发行版+内核）无意义，不必为其牺牲性能

代码示例

#include <stdio.h>
#include <unistd.h>
/* POSIX/SUS/LSB 标准化 */
int main(void) {
#ifdef _POSIX_VERSION
    printf("POSIX version: %ldL\n", (long)_POSIX_VERSION);
#endif
    printf("uname, fork, read 等 POSIX 标准接口\n");
    return 0;
}

POSIX vs Linux 扩展

  1. 应用层以 POSIX 为基准（open/read/write、fork、pthread、信号、定时器、SHM…）→ 易在 x86 PC / ARM 板子间移植。 2. 驱动 / 内核模块不受 POSIX 约束——POSIX 只管用户态 API；内核是 Linux 独有（走 LKD）。 3. SUS：几乎不关心（除非要迁 Solaris/AIX 等真 UNIX）。

要点

类型 例子 可移植性
POSIX 标准 API fork、pipe、socket、pthread、clock_gettime、mlock、SCHED_FIFO（实时扩展） Linux / macOS / BSD 等通用（程度因实现而异）
Linux 特有扩展 epoll、signalfd、timerfd、io_uring、sched_setaffinity、大页、SO_BUSY_POLL / TPACKET… 仅 Linux

嵌入式 Linux（用户态应用）

  1. 应用层以 POSIX 为基准（open/read/write、fork、pthread、信号、定时器、SHM…）→ 易在 x86 PC / ARM 板子间移植。
  2. 驱动 / 内核模块不受 POSIX 约束——POSIX 只管用户态 API；内核是 Linux 独有（走 LKD）。
  3. SUS：几乎不关心（除非要迁 Solaris/AIX 等真 UNIX）。
  4. LSB：静态链接、裁剪根文件系统场景下跨发行版二进制兼容无价值 → 忽略。

HFT（低延迟用户态）

  1. 基础仍靠 POSIX：单调时钟、pthread、实时信号、mlock、实时调度等。
  2. 极致延迟会用大量 Linux 私有扩展（io_uring、亲和性、大页、忙轮询 socket…）。
  3. 规则：基础逻辑尽量 POSIX；热路径优化主动用 Linux 专属，放弃可移植。
  4. SUS / LSB 对固化机房（固定发行版+内核）无意义。

极简工程守则

  1. 学习 / 面试：弄清三者关系，核心吃透 POSIX。
  2. 业务：可移植 → 只用 POSIX；HFT/嵌入式底层优化 → 允许 Linux 扩展（文档标清「非标准」）。
  3. SUS：概念即可，不当硬约束。
  4. LSB：历史产物，现代开发不考虑。

HFT / 嵌入式关联

路线 要点
嵌入式 应用层 POSIX 基准 + 驱动/内核不受 POSIX 约束（走 LKD）；Linux 专属扩展（epoll、signalfd、timerfd）在嵌入式实时场景广泛使用
HFT 极致延迟主动用 Linux 私有扩展（io_uring、大页、亲和性、SO_BUSY_POLL），放弃可移植性；规则 = 基础逻辑 POSIX、热路径 Linux 专属

代码示例

#include <stdio.h>
#include <unistd.h>
/* POSIX 标准接口 vs Linux 独有扩展 */
int main(void) {
    /* POSIX: write 跨平台 */
    write(STDOUT_FILENO, "POSIX write\n", 12);
    /* Linux only: /proc 文件系统 */
    printf("Linux-only: /proc/self/status\n");
    return 0;
}

1.x

Unix 系统调用对外接口就是 C（libc 包装 ≠ 内核）

FAQ · 锚定 TLPI Ch1 标准脉络 · 对照 notes §4 POSIX
类比：POSIX/C99 = 接口契约；内核源码 = 实现原理（同「标准 vs 实现」）

结论

对：Unix/类 Unix 对用户程序暴露的系统调用接口，以 C 语言形式呈现。
你写的 open / read / fork / socket 是 用户态 libc 的 C 封装；真正干活在内核里。

拆两层（防混淆）

libc 不包含「系统调用本身」。
系统调用是内核提供的服务；libc 是用户态库，但其中一部分函数会发起系统调用。

在哪 干什么
系统调用 内核态 服务编号（如 __NR_open）+ 内核里真正打开/读写… 的实现
libc::open 仍在用户态 备参 → 执行 syscall（x86-64）/ svc（ARM64）→ 陷入内核 → 拿返回值再 return 给你 
你的程序（用户态）
     ↓ 调用
libc::open（依旧用户态！不拥有内核代码）
     ↓ syscall / svc   ← 这里发生态切换
Linux 内核（内核态，真正干活）

用户程序无权直接跑内核代码；必须靠这条陷阱指令切态。

libc 里还有「完全不碰 syscall」的部分

纯用户态逻辑，和「桥」无关，例如：

  • strcpy / strlen
  • malloc / free（多数在用户态堆上转；缺内存时才可能 brk/mmap）
  • printf 缓冲逻辑（真正吐出时才可能 write）

三层拆开

层 是什么 语言/形态
1. 内核本体 进程、VFS、驱动、真正的 syscall 实现 汇编 + C；跑在内核态，不是普通用户态 C 程序
2. libc 包装 open()、read()… 用户态 C 函数；内部用 syscall / 昔日 int 0x80 / ARM svc 等 陷入内核
3. POSIX 规定这些 C 函数的签名、返回值、语义 接口标准；不规定 Linux/FreeBSD 内核内部怎么写 
你的 C 程序
  → libc: open("a.txt", O_RDONLY)     ← C 接口（用户态）
  → 陷入内核（系统调用入口）
  → Linux 内核：真正打开文件         ← 实现（可改算法）

只要 对外 C/POSIX 行为不变，内核随便改内部实现，上层 C 程序一行都不用动。

和 C99 / 标准的同一套逻辑

标准 管什么 不管什么
C99 语言接口与语义 某编译器/某 OS 内部怎么实现
POSIX Unix C 用户态 API 长什么样、什么行为 Linux 内核源码怎么实现 sys_open

联系 TLPI

《The Linux Programming Interface》讲的是：

POSIX / Linux 的 C 语言用户态接口（怎么正确调用、错误怎么处理）

不是内核内部原理。内核内部 → LKD / ULK / 07；驱动 → 12。

glibc 封装与「libc ≠ 裸 syscall」对照：见 Ch1 notes 里链到的 LKD Ch5 笔记。

一句话

  1. 系统调用： 内核提供的服务，内核态执行。
  2. libc： 用户态库。一部分函数用汇编触发 syscall；一部分纯用户态计算。
  3. libc ≠ 内核；libc 只是通往内核的用户态桥梁。

对外接口语言是 C（经 libc）；POSIX 管契约；内核源码管实现。

写应用读 TLPI；改内核/驱动另开书。

延伸： 觉得 libc「像个超级 crate」——表层像、本质是桥 → 「libc ≠ crate」专篇（待补）。

代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

/* 演示：libc write() 是 syscall 的薄包装。
 * syscall(SYS_write, ...) 直接陷入内核；
 * libc write() 做了错误码转 errno 后再调 syscall。
 * 编译: gcc -o syscall_demo syscall_demo.c */

int main(void) {
    const char *msg = "via libc write()\n";
    const char *msg2 = "via raw syscall()\n";

    /* 方式1: libc 包装 — errno 自动设置 */
    if (write(STDOUT_FILENO, msg, 16) < 0)
        perror("libc write");

    /* 方式2: 原始 syscall — 返回值即内核返回值 */
    long ret = syscall(SYS_write, STDOUT_FILENO, msg2, 18);
    if (ret < 0)
        perror("raw syscall");

    printf("Both call the same kernel function sys_write\n");
    return 0;
}
