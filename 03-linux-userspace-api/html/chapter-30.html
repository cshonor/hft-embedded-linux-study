章节目标

竞态到底怎么发生（含编译器合并循环的铁证）；pthread_mutex_* 全家 + 四种锁类型；futex 内核路径（哈希桶 / plist / 先锁桶再读值 / wake_q 锁外唤醒）；死锁四条件与防御；条件变量三步原子语义、while 谓词三种故障、丢唤醒时序；生产者-消费者有界队列与优雅关闭。

一句话内核视角：pthread 的 mutex 和 condvar 是同一套 futex 设施的两个用户态前端——锁的状态字就在用户内存（__lock/__wseq），无竞争时零系统调用（7 ns 一条 CAS），有竞争才进内核睡哈希桶；唤醒按优先级（plist）出队。

速查：mutex vs cond 职责

原语 职责 无竞争成本 有竞争成本
mutex 互斥访问状态 7 ns（用户态 CAS） 缓存行乒乓 ~70 ns；futex 睡眠 µs 级
cond 等待状态变化 —（配 mutex 用） signal→wake ≈ 一次 futex 唤醒（WSL2 实测 ≈ 裸 futex）

五个反直觉真相

# 真相
1 编译器能把 50 万次 ++ 合并成一条 addq $0x7a120——普通变量测竞态测了个寂寞（实测 volatile 版丢失 52%）
2 单核 0% 丢失 ≠ 安全，只是窗口 ~3ns 撞上时间片切换的概率 ≈ 10⁻⁶
3 无竞争 mutex（7.1 ns）比 atomic_fetch_add（13.8 ns）还便宜
4 condvar 唤醒延迟 ≈ 裸 futex 唤醒延迟（实测两者几乎相等）——延迟地板在内核，用户态优化不动
5 signal 不保存信号、只保证"至少一个"——正确性永远靠 while 谓词，不靠唤醒语义

易错清单

  1. 普通变量测竞态 → 编译器合并，丢失率假 0%
  2. if 谓词 → 虚假唤醒 / 惊群 / 错醒三种死法
  3. 不持锁改谓词或 signal → 丢唤醒（高负载偶发，最难查）
  4. while 谓词忘了带关闭条件 → close 后等待者睡死
  5. 同线程二次 lock 普通锁 → 自锁死锁
  6. 非持有者 unlock → UB（ERRORCHECK 下才报 EPERM）
  7. 多锁顺序不一致 → ABBA 死锁
  8. Pthreads 错误码查 errno → 永远查不到（从返回值取）
  9. 拷贝 mutex / cond → UB
  10. 忘 destroy / 忘 unlock 早退分支
  11. 临界区里做 IO、malloc、printf → 峰值延迟失控
  12. RECURSIVE 锁当万能药 → 掩盖设计问题
  13. 以为 signal 存信号 / signal 唤醒"恰好一个" → 都不是
  14. 多核竞争下无脑用 spinlock → 自旋风暴反而更慢（实测 81 vs 69 ns）
  15. timedlock/timedwait 误用相对时长或 REALTIME 基准 → 用绝对时间；时钟跳变环境配 MONOTONIC

背诵卡

# 要点
1 共享可变数据必须同步；无同步 = UB（编译器也参与捣乱）
2 测竞态必须 volatile/_Atomic
3 错误码从 Pthreads 返回值取
4 mutex 快路径 = 一条 CAS（7 ns，零系统调用）
5 futex 无竞争不出内核；等待队列在内核、状态字在用户内存
6 futex_wait_setup：先锁哈希桶、再读值（防丢唤醒的最后防线）
7 futex_wake：无等待者早退；wake_q 延迟到锁外唤醒
8 cond 必须永远配 mutex
9 谓词永远 while (!pred) wait
10 wait = 原子放锁入睡 + 醒来重拿锁
11 signal 至少一个 / broadcast 全部；都不保存信号
12 一个 cond 对应一个谓词
13 关闭队列：持锁置 closed + 双 broadcast
14 多锁全局统一顺序；timedlock 当死锁探测器
15 唤醒延迟地板 = futex + 调度（µs 级）；热路径要么不睡要么无锁

互斥量：保护共享变量

本章：TLPI 第 30 章 — Threads: Thread Synchronization - 上一节：本章首页 - 下一节：30.2 条件变量 pthread_cond_t

源码核验：Linux v6.6 · kernel/futex/core.c（futex_hash():115）· kernel/futex/waitwake.c（futex_wake():143 / futex_wait_setup():577 / futex_wait():632 / futex_wake_mark():115）· kernel/futex/futex.h（struct futex_hash_bucket:45 / struct futex_q:96）· kernel/futex/syscalls.c（do_futex():85 / SYSCALL_DEFINE6(futex):164）· include/uapi/linux/futex.h（FUTEX_WAIT:11 / FUTEX_WAKE:12 / FUTEX_PRIVATE_FLAG:26）

本节讲什么

  1. 竞态到底怎么发生的——x++ 在 CPU 层面是三条指令，两条线程交错执行就会丢更新；本节用实测数据（跨核丢失 52%）和一段 objdump 反汇编证明两件事：竞态是真的，而且编译器还可能把你的整个循环合并成一条加法指令，让竞态"看起来消失"。
  2. pthread_mutex_* 全家 API——静态/动态初始化、lock/trylock/timedlock/unlock、错误码约定（返回值而非 errno）、四种锁类型（NORMAL/ERRORCHECK/RECURSIVE/ADAPTIVE_NP）。
  3. mutex 的内核底座：futex——无竞争时 mutex 完全在用户态（一条 CAS，实测 7.1 ns）；有竞争才陷入内核，睡在 struct futex_hash_bucket 的优先级链表上。本节把 FUTEX_WAIT / FUTEX_WAKE 的内核路径逐步拆开，包括那段著名的「先锁哈希桶再读用户内存」的加锁顺序注释。

一、竞态：丢更新到底怎么发生的

1.1 x++ 不是一条指令

C 语句 shared++ 编译到 x86-64 至少是三条指令：

        mov    shared(%rip), %rax    ; ① 读
        add    $1, %rax              ; ② 改（寄存器里）
        mov    %rax, shared(%rip)    ; ③ 写

两条线程同时执行这个序列，交错就会丢失更新（lost update）：

时间 →         shared 初值 = 100

线程 A                          线程 B
mov shared,%rax   ; A 读到 100
                                 mov shared,%rax   ; B 也读到 100
add $1,%rax       ; A: 101
                                 add $1,%rax       ; B: 101
mov %rax,shared   ; 写回 101
                                 mov %rax,shared   ; 写回 101  ← 覆盖了 A 的结果

两个 ++，只 +1。丢了一次。

1.2 实测：跨核 4 线程丢失 52%

本节配套基准（WSL2 / 12 核 / gcc -O2，pthread_barrier 强制 4 线程同时开跑）：

static volatile long shared;          /* ⭐ volatile：gcc 无法合并，每次都真读真写 */
static void *worker(void *a){
    pthread_barrier_wait(&bar);       /* 4 线程同时起跑 */
    for (int i = 0; i < 500000; i++) shared++;
    return NULL;
}

实测结果（4 线程 × 500,000 次）：

场景 耗时 得到 / 期望 丢失
无保护 volatile ++（跨核） 1.8 ns/次 959,293 / 2,000,000 52.04%
无保护 volatile ++（4 线程全钉 CPU0） 3.4 ns/次 2,000,000 / 2,000,000 0.00%
无保护 读→延迟→写（放大窗口） 97.3 ns/次 30,454 / 80,000 61.93%
mutex 保护（跨核） 69.3 ns/次 2,000,000 / 2,000,000 0.00%
mutex 保护（全钉 CPU0） 26.7 ns/次 2,000,000 / 2,000,000 0.00%

三个结论：

  1. 竞态是真实且严重的：跨核场景下超过一半的自增凭空消失，而且程序不崩溃、不报错——这正是竞态的可怕之处，它静悄悄地破坏数据。
  2. 「放大窗口」丢得更多（61.93%）：把 读→算→写 的窗口人为拉宽（模拟临界区里夹着真实计算），碰撞概率随之上升。竞态丢失率 ≈ 窗口宽度 × 竞争强度。
  3. 全钉单核丢失 0.00% ≠ 安全：单核上线程靠时间片切换交错，只有恰好在 ① 和 ③ 之间被抢占才会丢。窗口 ~3 ns，时间片 ~ms 级，概率约 10⁻⁶ 量级——2,000,000 次实验碰上 0 次很正常。换个核数、换个负载、换个编译器，它就可能丢。把这段代码放进一个只跑单核的嵌入式盒子？中断和实时任务照样在 ①③ 之间打断你。

1.3 ⭐ 反直觉：编译器能把 50 万次 ++ 合并成 1 次加法

第一次做这个实验时，无保护版本丢失 0.00%、耗时 0.3 ns/次——明显不可信。排查后用 objdump 抓到了铁证。对下面这段代码：

static long shared;                              /* 注意：非 volatile */
void f(void){ for (int i = 0; i < 500000; i++) shared++; }

gcc -O2 -c 后反汇编：

0000000000000000 <f>:
   0:   f3 0f 1e fa             endbr64
   4:   48 81 05 xx xx xx xx    addq   $0x7a120, 0x0(%rip)   ; shared += 500000
   b:   20 a1 07 00
   f:   c3                      ret

0x7a120 = 500000。整个循环被合并成一条 shared += 500000。这是合法优化：单线程语义下（as-if 规则）500000 次自增 ≡ 加 500000；shared 没有 volatile/_Atomic 修饰，编译器没有义务假设别的线程会碰它。于是 4 个线程各自只在循环结束时做一次读改写——次数少了三个数量级，时间上又恰好错开，丢失率归零。

这一坑有两层教训：

教训 含义
测竞态必须 volatile（或 _Atomic） 否则你测的是编译器，不是调度器
无同步的共享访问连"看起来对"都保证不了 编译器可以重排、合并、缓存；C 内存模型下这就是 UB。竞态不只是"调度时机问题"，编译器也在跟你的共享变量捣乱

这也解释了一个经典悖论：「我加了 printf 调试，bug 消失了」——printf 是函数调用，编译器不能跨调用合并读写，副作用变多了，竞态窗口被 printf 的微秒级耗时稀释到测不到。

二、pthread_mutex_* API

2.1 初始化与销毁

/* 静态初始化：文件作用域全局/静态变量，零运行时开销 */
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

/* 动态初始化：栈上/堆上变量，或需要设置属性时 */
pthread_mutex_t mtx;
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
/* ... 设置类型/robust/协议 ... */
pthread_mutex_init(&mtx, &attr);
pthread_mutexattr_destroy(&attr);

pthread_mutex_destroy(&mtx);   /* 销毁：必须处于未锁定状态，否则 UB */
  • PTHREAD_MUTEX_INITIALIZER 等价于全零初始化：glibc 的 __kind 字段为 0 = PTHREAD_MUTEX_TIMED_NP（普通锁）。
  • 禁止拷贝 mutex：pthread_mutex_t a = b; 行为未定义。mutex 的身份（等待队列挂在它上面）不可复制。

2.2 加锁与解锁

int pthread_mutex_lock    (pthread_mutex_t *mutex);            /* 阻塞 */
int pthread_mutex_trylock (pthread_mutex_t *mutex);            /* 非阻塞：拿不到返回 EBUSY */
int pthread_mutex_timedlock(pthread_mutex_t *mutex,
                            const struct timespec *abstime);   /* 绝对时间超时 */
int pthread_mutex_unlock  (pthread_mutex_t *mutex);

三条约定：

  1. 错误码从返回值拿，不走 errno——这是 Pthreads 的风格（区别于大多数系统调用）。检查方式是 if (pthread_mutex_lock(&m) != 0)。
  2. timedlock 的 abstime 是绝对时间（CLOCK_REALTIME 基准），不是时长。到点拿不到锁返回 ETIMEDOUT。绝对时间的意义：即使 timedlock 被信号打断重启，超时时刻不变。
  3. lock 是取消点（cancellation point，Ch32 主题），timedlock 同样。

2.3 四种锁类型

pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_NORMAL);        /* 0：默认 */
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);    /* 1 */
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_RECURSIVE);     /* 2 */
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ADAPTIVE_NP);   /* 3，GNU 扩展 */
类型 同线程二次 lock 非持有者 unlock 解锁次数 开销 适用
NORMAL（默认） 死锁（通常） UB 1:1 最低 生产代码（你知道自己在干什么）
ERRORCHECK 立即返回 EDEADLK 返回 EPERM 1:1 每次 lock/unlock 都做完整检查 调试期
RECURSIVE 计数 +1 — 必须与 lock 次数相等 维护 __count 递归函数/回调链（能用别用，见下）
ADAPTIVE_NP（glibc） 同 NORMAL 同 NORMAL 1:1 先自旋 ~100 次再 futex 睡 短临界区、竞争短暂

关于 RECURSIVE 的忠告：可重入锁掩盖设计问题——它允许你在不知道调用链上游是否已持锁的情况下"安全"地再次加锁，等于放弃了"这段代码对锁的可见性"这一设计约束。通常更好的做法是把"需要持锁的内部函数"和"对外接口"分层（内部函数要求已持锁，接口函数负责加锁）。

ERRORCHECK 的价值实测见本章代码示例演示 3：同线程二次 lock 返回 EDEADLK、解锁后再 unlock 返回 EPERM——NORMAL 锁在同样场景下分别是死锁和 UB。

TLPI 还提到 PTHREAD_MUTEX_STALLED vs PTHREAD_MUTEX_ROBUST（robust mutex：持锁线程意外终止后，下一个拿锁者得到 EOWNERDEAD 而不是永久死等）。robust 属于 Ch32 之后的高级话题，这里先记住入口：pthread_mutexattr_setrobust()。

三、深入内核：mutex 的底座是 futex

3.1 glibc 视角：一条 CAS 的快路径

glibc（NPTL）的 pthread_mutex_t 核心字段（sysdeps/nptl/bits/thread-shared-types.h）：

struct __pthread_mutex_s {
    int __lock;          /* ⭐ futex 词：0=空闲 1=锁定无等待者 2=锁定有等待者 */
    unsigned int __count; /* RECURSIVE 的计数 */
    int __owner;         /* 持有者 TID（0=无人持有）*/
    unsigned int __nusers;
    int __kind;          /* 类型：NORMAL/ERRORCHECK/RECURSIVE/ADAPTIVE/ROBUST... */
    short __spins; short __elision;   /* ADAPTIVE 自旋计数 */
    __pthread_list_t __list;          /* robust 链表 */
};

lock 的逻辑（简化伪码）：

pthread_mutex_lock(m):
    if (CAS(&m->__lock, 0 → 1))        /* 快路径：一条 lock cmpxchg */
        m->__owner = mytid;            /* 无竞争，全程用户态，~7 ns */
    else
        慢路径: 自旋若干次（ADAPTIVE）→ syscall(futex, &m->__lock,
                 FUTEX_WAIT_PRIVATE, 2, ...)  /* 睡眠，让出 CPU */

unlock 的逻辑：

pthread_mutex_unlock(m):
    old = atomic_exchange(&m->__lock, 0);   /* 归零并取旧值 */
    if (old == 2)                            /* 有等待者 */
        syscall(futex, &m->__lock, FUTEX_WAKE_PRIVATE, 1, ...)

三个数字（实测，见 §5）串起来就是这套设计的意义：

操作 实测耗时 本质
无竞争 lock+unlock 7.1 ns 两次原子指令（用户态 CAS），零系统调用
空 futex 系统调用（FUTEX_WAKE 无等待者） 203.4 ns 系统调用本身的底价
有竞争的 lock+unlock（跨核） 69.3 ns 缓存行在核间乒乓 + 偶发 futex

futex 的核心设计哲学（Rusty Russell 2002 年引入，名字 = fast userspace mutex）：无竞争时同步根本不需要内核——内核只负责"有人睡着时叫醒他"这一件事。等待队列在内核，锁的状态字在用户内存。

3.3 FUTEX_WAIT 内核路径：先锁桶、再读用户内存

syscall(SYS_futex, &m->__lock, FUTEX_WAIT_PRIVATE, expected, ...) 进入内核后（syscalls.c:164 → do_futex():85 分发 → waitwake.c:632 futex_wait）：

                     struct futex_hash_bucket **hb)
{
    /*
     * Access the page AFTER the hash-bucket is locked.   ⭐ :584
     * Order is important:
     *   Userspace waiter: val = var; if (cond(val)) futex_wait(&var, val);
     *   Userspace waker:  if (cond(var)) { var = new; futex_wake(&var); }
     *
     * The basic logical guarantee of a futex is that it blocks ONLY
     * if cond(var) is known to be true at the time of blocking... :590

retry:
    get_futex_key(uaddr, ..., &q->key, ...);       /* 算 key（:220，core.c）*/
    *hb = futex_q_lock(q);                          /* ① 先锁哈希桶 */
    ret = futex_get_value_locked(&uval, uaddr);     /* ② 桶锁保护下读用户内存 */
    ...
    if (uval != val) {                              /* ③ 值已变 → 不睡 */
        futex_q_unlock(*hb);

为什么要先锁桶、再读值？注释（:584-598）给出了教科书级的解释，值得逐句消化：

  • futex 的基本逻辑保证：任务只会因为"入睡那一刻 *uaddr 仍然等于 expected"而睡着。
  • 如果顺序反过来（先读值、再锁桶入队），窗口期内唤醒方可能：改值 → 锁桶 → 发现无人 → 解锁 → 唤醒 0 个；然后睡眠方才锁桶入队，读到的却是旧值检查已经通过的状态，于是永远睡下去——丢失唤醒。
  • expected 参数（用户态传进来的 val）就是防线：如果读到的当前值 ≠ expected，说明"检查谓词"和"入睡"之间值已经变了，内核返回 -EWOULDBLOCK（用户态看到的就是 EAGAIN），用户态重读重试。这套「读值-比较-入睡」原子性正是 30.2 条件变量 while 谓词能成立的内核保证。

3.4 FUTEX_WAKE 内核路径：延迟到锁外唤醒

/* kernel/futex/waitwake.c:143 —— 逐行标注 */
int futex_wake(u32 __user *uaddr, unsigned int flags, int nr_wake, u32 bitset)
{
    ...
    get_futex_key(uaddr, ..., &key, ...);          /* 同一把 key */
    hb = futex_hash(&key);                          /* 同一个桶 */

    if (!futex_hb_waiters_pending(hb))              /* ⭐ :161 无等待者早退 */
        return ret;                                 /*    连 spinlock 都不拿！*/

    spin_lock(&hb->lock);
    plist_for_each_entry_safe(this, next, &hb->chain, list) {
        if (futex_match(&this->key, &key)) {        /* key 相同（桶内有碰撞）*/
            ...
            futex_wake_mark(&wake_q, this);         /* 摘队 + 入 wake_q */
            if (++ret >= nr_wake) break;            /* 唤醒够了 nr 个 */
        }
    }
    spin_unlock(&hb->lock);
    wake_up_q(&wake_q);                             /* ⭐ 锁外才真正唤醒 */
    return ret;
}

两个精妙设计：

  1. futex_hb_waiters_pending() 早退（:161）：桶上有个 atomic_t waiters 计数，睡眠方入队时递增。唤醒方先无锁读这个计数，为 0 直接返回——这就是 pthread_mutex_unlock 无等待者时的路径，也是实测「空 FUTEX_WAKE 203 ns」里进一步省掉桶锁的优化。mutex 无竞争解锁甚至连这个系统调用都不发（__lock 从 1 归 0 即可，只有旧值为 2——"有等待者"——才唤醒）。
  2. wake_up_q() 延迟到锁外（futex_wake_mark():115）：先把要唤醒的任务摘出链表、挂到栈上的 wake_q，释放 hb->lock 之后才逐个 try_to_wake_up()。原因：唤醒是慢操作（要拿目标任务的 pi_lock、改状态、可能触发负载均衡），拿着哈希桶自旋锁做这些会让其他 CPU 上的 futex 操作全部空转。

四、死锁

4.1 两大成因与四个必要条件

成因一：同线程对普通锁二次 lock（自锁）。NORMAL 锁通常永久死锁——第二次 lock 的 futex 睡在自己持有的锁上，永远无人唤醒。

成因二：多锁加锁顺序不一致（ABBA）：

线程 1                          线程 2
lock(A)  ✓
                                lock(B)  ✓
lock(B)  …等 B（B 在线程 2 手里）
                                lock(A)  …等 A（A 在线程 1 手里）
                                ↯ 互相等待，永久僵死

经典理论框架——死锁的四个必要条件（同时满足才死锁）：

# 条件 破坏法
1 互斥 有的资源没法共享（锁天然满足）
2 持有并等待 一次性申请全部锁（先拿"总锁"再拿细分锁）
3 不可剥夺 trylock + 失败放弃已持有的锁
4 循环等待 全局统一加锁顺序（最常用）

5.2 每个数字背后的机制

数字 解释
无竞争 mutex 7.1 ns < atomic 13.8 ns mutex 快路径 = 一次 lock cmpxchg（__lock: 0→1）；atomic_fetch_add 是 lock xadd（读写都走总线仲裁），还多一次返回值依赖。无竞争时 mutex 是最便宜的原语之一
spinlock 无竞争 15.1 ns pthread_spin_lock 的 pthread_spin 有 QSBR/测试版本差异，glibc 实现含 atomic_exchange + 编译器屏障，比单 CAS 贵
钉 CPU0 的 mutex（26.7 ns）vs 跨核（69.3 ns） 跨核时锁的缓存行在 4 个核的 L1 之间乒乓（MESI 的 Invalid→Exclusive 迁移），每次 CAS 都是一次跨核缓存一致性事务；钉单核时缓存行不动，只有时间片切换的额外开销
spinlock 跨核 81.0 ns > mutex 69.3 ns 反直觉但合理：4 个核同时自旋，自旋本身就在持续锤那个缓存行，让持有者更难推进（持锁核每次解锁也要抢缓存行）。多核 + 临界区不极短时，自适应 mutex（先短自旋再睡）完胜纯自旋
空系统调用 203 ns 进出内核的固定底价（含 KPTI 页表切换）。一切"要不要陷入内核"的优化都要先跟这个数比
⚠ WSL2 唤醒 67.8 µs 虚拟化环境的调度延迟被显著放大，绝对值不可信，只看量级和相对关系。native Linux 上 futex 乒乓典型值 1~5 µs（见 05-linux-kernel 调度部分）

5.3 一句话结论

mutex 的价格结构是"阶梯"：无竞争一条 CAS（7 ns）；跨核竞争缓存行乒乓（70 ns）；真的睡过去再被叫醒（微秒级，含两次系统调用 + 调度器）。选型时真正要想清楚的是：你的临界区会不会经常走到第三档。

HFT / 嵌入式关联

路线 要点
HFT · 热路径 一核一线程架构下锁几乎无竞争——此时 mutex 就是一条 7 ns 的 CAS，够快，不必上无锁结构。真正的敌人是偶发的"睡过去"：一次 futex 睡眠 + 唤醒 = 微秒级尾延迟。热路径锁必须保证快路径永远命中（临界区纳秒级、无 IO、无长循环）
HFT · 优先级反转 低优先级行情线程持锁，高优先级订单线程等锁；中间优先级的 GC/日志线程再抢占低优先级 → 高优先级被"间接"拖住毫秒级。解药：PTHREAD_PRIO_INHERIT（内核路径：futex_lock_pi → rt_mutex，见 §衔接）或干脆热路径无锁
HFT · 锁序纪律 多锁必循全局锁序；code review 时锁序是必查项。死锁在压测里不一定现形，生产高峰才爆
嵌入式 · 单核 单核≠无竞态（时间片 + 中断同样交错窗口）。但单核上自旋锁是活锁（持有者等不到 CPU），临界区内禁用抢占的自旋变体是内核态做法；用户态单核直接用 mutex（睡 = 让出 CPU 给持有者）
嵌入式 · RTOS 优先级反转的经典案例是 Mars Pathfinder（1997，VxWorks 优先级继承救场）。POSIX mutex 的 PTHREAD_PRIO_INHERIT / PTHREAD_PRIO_PROTECT 是同名机制的 pthread 接口

  1. Connection timed out 就是 ETIMEDOUT 的 strerror 文案。
  2. demo4 有两种结局，都算"成功脱身"：双超时（两线程都在 200 ms 点放弃），或如本次——一超时放锁救活另一个：线程 2 超时放弃并解锁 B 的瞬间，还睡在 B 上的线程 1 被 futex 唤醒、成功拿锁。这正是 timedlock 的价值：把永久死锁降级为可重试失败。
  3. 生产代码里这个模式可以升级成"超时 → 记录锁序违规日志 → 指数退避重试"。

自测题

题目 1（实测分析）：无锁 4 线程各 ++ 500,000 次的测试里，共享变量声明为普通 long 时丢失 0.00%，改为 volatile long 后丢失 52%。为什么普通版本"不丢"？这说明什么？

参考答案

普通 long 无任何同步语义，gcc 依 as-if 规则把整个循环合并成一条 shared += 500000（objdump 可证：addq $0x7a120, shared(%rip)），每个线程只在结束时做一次读改写，碰撞概率骤降且时间上错开，所以"看起来不丢"。这说明：① 无同步的共享访问在 C 内存模型下是 UB，编译器可以任意重排/合并，你测到的"无竞态"可能只是编译器的副作用；② 测竞态必须用 volatile（挡合并）或 _Atomic（真同步），否则测的是编译器不是调度器。

题目 2（概念）：单核 CPU 上（或 4 线程全钉一个核），无保护 ++ 实测丢失 0.00%。这能证明单核没有竞态吗？

参考答案

不能。单核上线程靠时间片切换交错，只有恰好在 load 和 store 之间被抢占才丢更新。窗口 ~3 ns，时间片 ~ms 级，单次概率 ~10⁻⁶，200 万次实验可能一次都碰不上。竞态存在但概率极低——这正是竞态 bug 的典型形态：换负载、换核数、加中断压力它就现形。另外单核上中断处理程序若也碰同一变量，窗口同样存在。

题目 3（API 细节）：pthread_mutex_lock 失败时错误码从哪里取？trylock 拿不到锁返回什么？

参考答案

Pthreads 系列函数的错误码从返回值取，不设置 errno（区别于传统系统调用）。写法是 int err = pthread_mutex_lock(&m); if (err) ...。trylock 在锁被占时立即返回 EBUSY，不阻塞。

题目 4（内核路径）：futex_wait_setup() 为什么必须先锁哈希桶、再读用户内存的值？如果反过来会发生什么？

参考答案

先锁桶再读值保证了"读值 → 入队"在桶锁保护下原子完成。如果反过来（先读值、后锁桶入队），存在窗口：睡眠方读到旧值 → 唤醒方改值、锁桶、发现无人、唤醒 0 个、解锁 → 睡眠方才锁桶入队、基于早已过期的旧值检查通过而睡下 → 永远无人唤醒（丢失唤醒）。futex 的基本保证是"任务只会因为入睡那一刻 *uaddr 仍等于 expected 而睡着"，先锁桶是实现这一保证的前提（kernel/futex/waitwake.c:584 注释原文）。

题目 5（选型）：多核机器上、临界区约 100 ns 的计数器更新，4 线程高并发。pthread_spinlock 一定比 pthread_mutex 快吗？

参考答案

不一定，实测往往更慢。本机数据：跨核 4 线程下 spinlock 81 ns/次 vs mutex 69 ns/次。原因：4 个核同时自旋会持续锤锁所在的缓存行（MESI 乒乓），持锁核每次访问锁和临界区数据都要跟 4 个自旋核抢缓存一致性事务，反而被拖慢。glibc 自适应 mutex（默认类型在竞争时）先短自旋再 futex 睡眠，兼顾两头。纯自旋锁只在"临界区极短 + 持锁者确定在别的核上跑着不会被换走 + 上下文切换成本 >> 自旋成本"时占优。

30.2

条件变量：通知状态变化

本章：TLPI 第 30 章 — Threads: Thread Synchronization - 上一节：30.1 互斥量：保护共享变量 - 下一节：30.3 总结：职责与铁律

源码核验：Linux v6.6 · kernel/futex/waitwake.c（futex_wake():143 / futex_wait_setup():577）· kernel/futex/futex.h（struct futex_q:96）· include/uapi/linux/futex.h（FUTEX_WAIT:11 / FUTEX_WAKE:12）

本节讲什么

  1. 为什么 mutex 不够——mutex 只能保证"一次一个人进"，解决不了"等队列非空再干活"：轮询烧 CPU，sleep 加延迟。条件变量补上"睡到条件成立"的原语。
  2. pthread_cond_wait 的三步原子语义——放锁、睡、醒来重新拿锁，为什么必须持锁调用、为什么谓词必须用 while 而不是 if（虚假唤醒 + 多人被唤醒 + 抢锁失败三种场景）。
  3. 丢失唤醒的时序解剖——不持锁就 signal 会发生什么；以及实测证明：condvar 的唤醒延迟 ≈ 裸 futex 的唤醒延迟（condvar 只是 futex 加一层用户态记账）。

一、为什么 mutex 不够

需求：消费者线程要等 queue 非空才能干活。用 mutex 只有两种写法，都不行：

/* 写法 1：轮询 —— 烧 CPU */
for (;;) {
    pthread_mutex_lock(&m);
    if (queue非空) { 取数据; pthread_mutex_unlock(&m); break; }
    pthread_mutex_unlock(&m);
    /* 不睡 = 100% CPU 空转；睡 usleep(1ms) = 平均 0.5ms 额外延迟 */
}

/* 写法 2：拿着锁睡 —— 更糟 */
pthread_mutex_lock(&m);
while (queue空) sleep(1);        /* ⚠ 睡着还持锁！生产者永远进不来 */

死结在于：检查谓词需要持锁（防止检查瞬间被改），但等待需要放锁（让别人能改）——这两件事必须"原子地"一起发生。这正是条件变量存在的意义：

条件变量 = 「放锁入睡 + 醒来重新拿锁」的原子封装。

mutex 与 cond 的职责分工：

原语 职责 回答的问题
mutex 互斥访问状态 "现在能不能碰这个数据"
cond 等待状态变化 "状态变了没有？没变我睡，变了叫我"

二、API 与 wait 的三步语义

2.1 API

pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;    /* 静态初始化 */
pthread_cond_init(&cond, &attr);                    /* 动态（可设 CLOCK_MONOTONIC）*/
pthread_cond_destroy(&cond);

int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_timedwait(pthread_cond_t *cond, pthread_mutex_t *mutex,
                           const struct timespec *abstime);   /* 绝对时间 */
int pthread_cond_signal(pthread_cond_t *cond);      /* 唤醒至少一个等待者 */
int pthread_cond_broadcast(pthread_cond_t *cond);  /* 唤醒全部等待者 */

2.2 wait 的三步原子语义

pthread_cond_wait(&cond, &m);
/* 展开成三步，且①②不可分割（原子）：
 *   ① 原子地：释放 m + 挂入 cond 的等待队列（内核里：锁桶 → 入队 → 放锁 → schedule）
 *   ② 睡……（TASK_INTERRUPTIBLE，等 futex 唤醒/信号/超时）
 *   ③ 醒来后重新 pthread_mutex_lock(m)，拿到了才从 wait 返回
 */

三个推论，每个都是坑点：

  1. 必须持锁调用 wait——因为它要放锁。不持锁调用是 UB（glibc 里会直接解锁一把没锁的 mutex，__owner 检查不过就崩）。
  2. wait 返回时你又持有锁——所以 wait 外层的 while 谓词检查天然是持锁的，无需再加锁。
  3. signal 的一方，通常也持锁——修改谓词（共享状态）本身就需要锁。signal 可以在放锁之后（"墙倒众人推"优化），但改谓词必须在持锁下（§四）。

2.3 标准模板（背诵级）

/* 等待方 */
pthread_mutex_lock(&m);
while (!predicate)                  /* ⭐ while，不是 if */
    pthread_cond_wait(&cond, &m);
/* 此刻：持锁 && 谓词为真 */
...消费状态...
pthread_mutex_unlock(&m);

/* 通知方 */
pthread_mutex_lock(&m);
...修改状态，使 predicate 可能为真...
pthread_cond_signal(&cond);         /* 或 broadcast */
pthread_mutex_unlock(&m);

三、谓词为什么必须 while

if (predicate) wait 有三类真实故障，while 一次性全部兜住：

3.1 虚假唤醒（spurious wakeup）

没有任何人 signal，wait 自己醒了。这是允许的（POSIX 明文）：内核的 futex_wait 被信号打断、唤醒路径的竞态（futex_wake_mark 注释里那个 spurious wakeup 例子）、glibc 的 __wseq 序号实现细节，都会造成"醒来但无事发生"。醒来后谓词仍为假，while 转一圈接着睡；if 版本直接往下走，拿着假谓词进入临界区消费不存在的数据。

3.2 多人被唤醒（broadcast 惊群）

broadcast 唤醒 5 个消费者，但队列里只有 1 条数据：

broadcast → 5 人同时从 wait 返回（当然，串行抢锁）
  消费者 1 抢到锁：谓词真，取走数据，unlock
  消费者 2 抢到锁：谓词已假 → while 转回去接着睡 ✓
                   if 版本：谓词检查发生在醒来瞬间（逻辑上），
                   消费不存在的数据 → 空指针/下溢/崩溃 ✗

3.3 signal 唤醒了"错误"的等待者

一个 cond 被多个谓词复用时（不推荐但常见于历史代码），signal 唤醒的线程等的是谓词 A，而成立的是谓词 B——被唤醒者 while 一检查发现 A 仍为假，接着睡，无事发生；if 版本则会消费错误状态。条件变量不带任何谓词信息，它只是个"闹钟"，判断该不该起床永远是等待者自己的事（while 谓词）。

记忆钩子：cond 是哑的，谓词是活的；醒来先看表（while），别闭着眼下床（if）。

3.4 signal vs broadcast 决策表

场景 用哪个 理由
每次状态变化只"解锁"一个等待者（队列来了 1 条消息） signal 只需一个消费者干活；多醒是浪费（醒了抢锁失败又睡回去）
所有等待者都该看一眼状态（广播关闭、水位变化） broadcast 语义正确性优先
不确定 / 谓词复杂 / 多种等待者共用一个 cond broadcast signal 只保证"至少一个"被唤醒，若被唤醒的不是该干活的那个，且没人再 signal → 全体饿死
HFT 热路径 尽量都不用 唤醒 = futex 系统调用 + 调度延迟（微秒级尾延迟），热路径用无锁队列 + 自旋/忙等

signal 的语义是"唤醒至少一个"——实现上允许当惊群用（glibc 实际按 LIFO/FIFO 唤醒一个，但标准不保证只一个）。所以即使你用 signal，等待方也必须写 while。

四、丢失唤醒：不持锁 signal 的时序解剖

条件变量不记忆信号。signal 时刻没有任何等待者 → 这个 signal 凭空消失，不会存起来补偿给后来的 wait。谓词 + 持锁是唯一的防线：

错误写法：通知方不持锁
                                        等待方（持锁）
                                        lock(m)
                                        if (queue空)          ① 检查：空
signal(cond)   ② 此刻等待方还没睡着！
               （signal 落空，无人被唤醒，信号不保存）
                                        wait(cond, m)         ③ 放锁入睡
                                                               → 睡到天荒地老

正确的持锁写法为什么不会丢？signal 落在 ①③ 之间时，它根本进不来——m 被等待方持有，通知方阻塞在 lock 上，直到 ③ 放锁入睡的瞬间才获得机会改状态 + signal，而等待方已经挂在队列上（①放锁和②入队是原子的）。若 signal 落在 ③ 之后，等待方已在队列上，正常被唤醒。

更精确地说，防线的最底层是 §五讲的 futex 语义：等待方"放锁 + 入队"原子，通知方"改值 + 唤醒"必须与它互斥——在用户态这套互斥由 mutex 提供；内核里 futex_wait_setup 的"先锁桶再读值"把最后一级窗口也焊死了（30.1 §3.3）。

三个推论：

  1. 先改谓词，后 signal（都在持锁下）——只 signal 不改谓词 = 白叫，while 转一圈接着睡。
  2. signal 后立刻 unlock 的传统写法 vs 先 unlock 再 signal（"hurry up and wait" 优化）：后者少一次锁交接（被唤醒者不必和 signal 方抢锁），语义都正确；但先 unlock 再 signal 在"判断是否有等待者"的实现上可能有惊群窗口，按 TLPI 的建议：默认持锁 signal， profiling 发现锁交接是瓶颈再优化。
  3. timedwait + 绝对时间：重试循环里不要重算 deadline（abstime 是绝对时刻，被虚假唤醒打断重进 while 后，timedwait 用同一个 abstime，不会把总等待时间拉长）。

五、深入内核：condvar 只是 futex 的记账外壳

5.1 glibc 的 condvar 结构（2.25+ 的 wseq 设计）

glibc pthread_cond_t 的核心字段（简化）：

struct pthread_cond_s {
    __atomic_wide_counter __wseq;      /* ⭐ wait 序号：每次 wait 递增 */
    __atomic_wide_counter __g1_start;  /* 当前"代"（generation）的起始序号 */
    unsigned int __g_refs[2];          /* 两代等待组（G1 在睡，G2 在涌入）*/
    unsigned int __g_size[2];
    unsigned int __g1_orig_size;
    unsigned int __wrefs;
    unsigned int __g_signals[2];
    ...
};
  • 每次 wait：__wseq++，序号决定你属于哪一代（G1/G2），然后睡在与代绑定的 futex 词上。
  • signal：递增 __g_signals，对当前代发一次 futex(FUTEX_WAKE, 1)。
  • broadcast：把当前代"闭代"，全体 futex(FUTEX_WAKE, INT_MAX)，新来者进下一代。
  • 唤醒后的等待者要重新抢 mutex（30.1 的完整路径），然后 while 谓词复查。

5.2 实测：condvar 唤醒延迟 ≈ 裸 futex 唤醒延迟

配套基准的两组数据（WSL2，严格握手 ping-pong 模式）：

测试 实测 说明
裸 futex（FUTEX_WAIT + FUTEX_WAKE 手写乒乓） 67.8 µs/往返 内核下限：两次系统调用 + 两次调度
pthread_cond_signal → wait 醒来 67.8 µs/次 glibc condvar 完整路径

两者几乎相等——证明 condvar 的用户态记账（wseq/代/簿记）开销相对内核唤醒可以忽略，条件变量的延迟瓶颈就是 futex 唤醒 + 调度器。这也是它和"自旋/忙等"路线的分水岭：数据到了你愿意睡（省 CPU、延迟微秒级），还是愿意烧核（延迟亚微秒级）。

⚠ 67.8 µs 是 WSL2 虚拟化的调度放大值，native Linux 典型 1~5 µs。绝对值不可信，但两组的相对关系（≈相等）可信——它们走的是同一条内核路径。

六、生产者-消费者：本章的中央模式

固定容量环形队列，双条件变量（not_full / not_empty）：

#define QCAP 8
typedef struct {
    void *buf[QCAP];
    int head, tail, count;
    int closed;
    pthread_mutex_t m;
    pthread_cond_t  not_full;      /* 消费者在它上面等"有空位"（消费后 signal）*/
    pthread_cond_t  not_empty;     /* 生产者在它上面等"有数据"（生产后 signal）*/
} queue_t;

/* 生产者 */
void q_push(queue_t *q, void *item) {
    pthread_mutex_lock(&q->m);
    while (q->count == QCAP && !q->closed)     /* 满了且没关门：等 */
        pthread_cond_wait(&q->not_full, &q->m);
    if (q->closed) { pthread_mutex_unlock(&q->m); return; }
    q->buf[q->tail] = item;
    q->tail = (q->tail + 1) % QCAP;
    q->count++;
    pthread_cond_signal(&q->not_empty);        /* 有数据了，叫一个消费者 */
    pthread_mutex_unlock(&q->m);
}

六个细节，每个都对应前面某条原理：

# 细节 对应原理
1 while (count == QCAP && !closed) while 谓词（§三）；条件里带 closed 让关闭时能醒着退出
2 push 里 signal not_empty，pop 里 signal not_full 唤醒的是"对面"的等待者——你制造了空位才有人能等空位
3 单条数据 signal 一次，不 broadcast 每条消息只需一个消费者（§3.4）；多生产者多消费者天然负载均衡
4 closed 的关闭：持锁置位 + 两个 cond 都 broadcast 关闭是全局事件，所有等待者都要醒来看 while 的 !closed 分支
5 pthread_cond_wait 的返回值不检查 它成功时返回 0；虚假唤醒靠 while 兜，timedwait 的 ETIMEDOUT 才需要查
6 队列结构体和锁放一起、按数据对象组织锁 锁的粒度 = 数据的粒度，防止"一把大锁包全场"

完整的可运行实现（含优雅关闭 + 统计）见 30.4 练习 综合题。

路线 要点
HFT · 热路径 行情→策略的传递不用 condvar：唤醒延迟 = futex 系统调用 + 调度（微秒级尾延迟），热路径用 SPSC 无锁环形队列 + 消费侧忙等/自旋（忙等延迟亚微秒）。condvar 用于非热路径：风控开关、配置热更新、订单确认等"毫秒级无所谓"的事件
HFT · 尾延迟思维 condvar 的延迟分布是长尾（本机实测最慢样本 883 µs，均值 68 µs 的 13 倍——调度器被干扰时的排队）。任何"睡着等人叫"的设计都要评估 p99.9 而不是均值
HFT · 多消费者 signal 唤醒"至少一个"不保证"恰好该干活的那一个"；策略组多线程共用一个 cond 时宁可用 broadcast 让 while 谓词自己分流，也别赌 signal 命中
嵌入式 · 采集→处理 经典架构：中断/DMA 采集线程 q_push，处理线程 q_pop 阻塞等待——CPU 占用近零，比轮询省几个数量级的功耗（电池设备关键）
嵌入式 · 时钟选择 pthread_condattr_setclock(CLOCK_MONOTONIC) + timedwait：嵌入式系统墙钟跳变（NTP 校时、RTC 没电）会让 CLOCK_REALTIME 的 timedwait 永不超时或立刻超时。单调整钟是超时类 API 的唯一安全选择
嵌入式 · 优先级 高优先级消费者睡在 cond 上时，被 signal 唤醒的顺序由 futex 的 plist（优先级链表）决定，实时线程先醒（30.1 §3.2）——前提是策略线程用了实时调度（Ch35）

cond_demo.c（gcc -O2 -Wall -Wextra 零告警编译通过；演示 2 用 timedwait 兜住本会永久挂死的 bug 版本）：

/* cond_demo.c — Ch30.2：while 谓词、丢唤醒、signal vs broadcast
 * 编译：gcc -O2 -Wall -Wextra -o cond_demo cond_demo.c -pthread
 */
#include <stdio.h>
#include <string.h>
#include <pthread.h>
#include <time.h>
#include <unistd.h>

static double now_ns(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
    return t.tv_sec*1e9+t.tv_nsec;}

/* ---------- 演示 1：while 谓词 + 严格握手 ping-pong（正确范式） ---------- */
static pthread_mutex_t m1 = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c1 = PTHREAD_COND_INITIALIZER;
static int ball;                        /* 0=轮到生产者, 1=轮到消费者 */
static long handshakes;

static void *cons1(void *a){(void)a;
    for (long i = 0; i < 100000; i++) {
        pthread_mutex_lock(&m1);
        while (!ball)                   /* ⭐ while：虚假唤醒/惊群全兜住 */
            pthread_cond_wait(&c1, &m1);
        ball = 0;
        pthread_cond_signal(&c1);       /* 告诉生产者：该你了 */
        pthread_mutex_unlock(&m1);
    }
    return NULL;}
static void *prod1(void *a){(void)a;
    for (long i = 0; i < 100000; i++) {
        pthread_mutex_lock(&m1);
        while (ball)
            pthread_cond_wait(&c1, &m1);
        ball = 1;
        handshakes++;
        pthread_cond_signal(&c1);
        pthread_mutex_unlock(&m1);
    }
    return NULL;}

static void demo_handshake(void){
    pthread_t t1, t2;
    ball = 0; handshakes = 0;
    double t0 = now_ns();
    pthread_create(&t1, NULL, cons1, NULL);
    pthread_create(&t2, NULL, prod1, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    printf("[demo1] 严格握手 %ld 次，平均 %.1f ns/次（含全部锁竞争）\n",
           handshakes, (now_ns() - t0)/handshakes);
}

/* ---------- 演示 2：丢唤醒 bug 版（不持锁 signal） ---------- */
static pthread_mutex_t m2 = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c2 = PTHREAD_COND_INITIALIZER;
static int ready2;

static void *waker(void *a){(void)a;
    usleep(100000);                     /* 等受害者跑到 wait 前面 */
    ready2 = 1;                         /* ⚠ 不持锁改谓词 */
    pthread_cond_signal(&c2);           /* ⚠ 不持锁 signal：落空风险 */
    return NULL;}
static void *victim(void *a){(void)a;
    pthread_mutex_lock(&m2);
    struct timespec dl; clock_gettime(CLOCK_REALTIME, &dl);
    dl.tv_nsec += 300*1000000; if (dl.tv_nsec >= 1000000000L)
        { dl.tv_sec++; dl.tv_nsec -= 1000000000L; }
    int r = 0;
    while (!ready2 && r == 0)           /* timedwait：最多睡 300ms 就放弃 */
        r = pthread_cond_timedwait(&c2, &m2, &dl);
    printf("[demo2] 受害者醒来：ready2=%d %s（r=%s）\n", ready2,
           r == 0 ? "被正常唤醒" : "超时放弃——signal 丢了",
           r ? strerror(r) : "0");
    pthread_mutex_unlock(&m2);
    return NULL;}

static void demo_lost_wakeup(void){
    pthread_t t1, t2;
    pthread_create(&t2, NULL, victim, NULL);
    pthread_create(&t1, NULL, waker, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
}

/* ---------- 演示 3：broadcast 惊群 + while 自动分流 ---------- */
static pthread_mutex_t m3 = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c3 = PTHREAD_COND_INITIALIZER;
static int tokens;                      /* 令牌数 */
static long grabbed[3];                 /* 每个消费者抢到的次数 */

static void *grabber(void *a){
    long id = (long)(intptr_t)a;
    for (int round = 0; round < 3; round++) {
        pthread_mutex_lock(&m3);
        while (tokens == 0)
            pthread_cond_wait(&c3, &m3);    /* 没令牌就睡 */
        tokens--;                           /* 抢到一枚 */
        grabbed[id]++;
        pthread_mutex_unlock(&m3);
    }
    return NULL;}

static void demo_thundering_herd(void){
    pthread_t t[3];
    tokens = 0;
    memset(grabbed, 0, sizeof grabbed);
    for (long i = 0; i < 3; i++) pthread_create(&t[i], NULL, grabber, (void*)(intptr_t)i);
    usleep(100000);
    for (int round = 0; round < 9; round++) {     /* 9 轮 × 1 枚 = 9 枚令牌总量
                                                     = 3 人 × 3 轮，人人都能收工 */
        pthread_mutex_lock(&m3);
        tokens = 1;                         /* 只放 1 枚令牌 */
        pthread_cond_broadcast(&c3);        /* 惊醒全部 3 人 */
        pthread_mutex_unlock(&m3);
        usleep(100000);
    }
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    printf("[demo3] broadcast 惊群分流（9 轮各 1 枚令牌）：抢到 {A=%ld, B=%ld, C=%ld}"
           "（共 %ld，被白唤醒的都回 while 睡回去了）\n",
           grabbed[0], grabbed[1], grabbed[2],
           grabbed[0]+grabbed[1]+grabbed[2]);
}

int main(void){
    demo_handshake();
    demo_lost_wakeup();
    demo_thundering_herd();
    return 0;
}

[demo2] 受害者醒来：ready2=1 被正常唤醒（r=0）
[demo3] broadcast 惊群分流（9 轮各 1 枚令牌）：抢到 {A=3, B=3, C=3}（共 9，被白唤醒的都回 while 睡回去了）

三点解读：

  1. demo1 每次握手包含两次 signal→wake 往返（生产者叫消费者、消费者叫生产者），WSL2 下每次唤醒 68~250 µs 波动很大（native Linux 约 1~5 µs）——这正是 §5.2 表里"condvar signal→wake 延迟"的来源与量级。
  2. demo2 这次运气好（signal 恰好落在受害者入睡之后），但这个正确性靠的是运气：不持锁改谓词 + signal 的窗口真实存在（§四的时序图），换负载/换核就可能打出"超时放弃——signal 丢了"的结局。正确写法是给 waker 也加上 pthread_mutex_lock(&m2)。
  3. demo3 每轮只放 1 枚令牌、broadcast 惊醒 3 人：1 人抢到，2 人 while 复查发现令牌已空、默默睡回去。惊群不丢正确性（while 兜底），只浪费唤醒——这正是 broadcast 语义安全的代价。

自测题

题目 1（语义）：pthread_cond_wait(&cond, &m) 从调用到返回，锁 m 的状态经历什么变化？为什么说"必须持锁调用"？

参考答案

进入时必须已持有 m；wait 内部原子地（释放 m + 挂入 cond 等待队列）；被唤醒后重新 lock(m)，拿到锁才返回。所以返回时刻必然持锁。必须持锁调用的原因：① wait 要放锁，不持锁则放锁行为未定义；② 谓词检查（while 的条件）必须在持锁下做，否则检查瞬间谓词可能被并发修改——"检查谓词"与"放锁入睡"的原子性正是 condvar 存在的意义。

题目 2（坑点辨析）：把标准模板的 while (!predicate) wait(...) 改成 if (!predicate) wait(...)，在什么情况下会出 bug？至少说出三种场景。

参考答案

① 虚假唤醒：无人 signal 却醒了，if 版本拿着假谓词往下走；② broadcast 惊群：N 个等待者全醒，但资源只有 1 份，第一个抢到的把谓词改回假，其余 if 版本不再复查、直接消费不存在/不完整的状态；③ signal 命中"错误"等待者：一个 cond 复用多个谓词时，被唤醒者等的是别的谓词。共同本质：醒来 ≠ 谓词为真，只有 while 能把"醒"翻译回"检查"。

题目 3（丢失唤醒）：画时序说明"通知方不持锁直接 signal"为什么可能永久丢失唤醒。修复的最小改动是什么？

参考答案

时序：等待方 lock(m) → 检查谓词为假 → 【窗口】→ 通知方改谓词 + signal（此刻无人在队列上，信号不保存、凭空消失）→ 等待方 wait() 放锁入睡 → 永远无人再 signal → 永久睡眠。最小修复：通知方的"改谓词 + signal"包进 lock(m)/unlock(m)——这样它要么在等待方检查之前完成（等待方看到新谓词，根本不睡），要么被挡在锁外直到等待方原子地"放锁+入队"之后才执行（signal 必中）。

题目 4（实测理解）：为什么实测"裸 futex 乒乓延迟"与"condvar signal→wake 延迟"几乎相等？这个结论对架构选型意味着什么？

参考答案

因为 condvar 的唤醒路径最终就是对内部的 futex 词执行 FUTEX_WAIT/FUTEX_WAKE，glibc 加的记账（wseq 序号、代管理）是纯用户态原子操作，纳秒级；而唤醒本身要付出系统调用 + 调度器唤醒 + 新任务等 CPU 的微秒级成本。两者相等说明condvar 的延迟地板就是内核 futex + 调度，用户态无法再优化。选型含义：凡是"睡着等人叫"的方案延迟都是微秒级长尾，HFT 热路径要亚微秒就只能反向选择——不睡（自旋/忙等/无锁队列）。

题目 5（API 细节）**：pthread_cond_signal 和 pthread_cond_broadcast 的语义分别是什么？"signal 只唤醒一个"这个说法对吗？

参考答案

signal：唤醒至少一个等待者；broadcast：唤醒全部等待者。"signal 恰好唤醒一个"不对——POSIX 只承诺"至少一个"，实现允许在 signal 时多醒（等效惊群）。因此即使全程序都用 signal，等待方仍必须写 while 谓词。选型规则：一次状态变化只该解锁一个等待者 → signal；所有等待者都要重新评估状态 → broadcast；拿不准 → broadcast（正确性优先，代价是惊群）。

三、十条铁律

  1. 共享可变数据必须同步——C 内存模型下无同步共享 = UB，编译器和调度器都在跟你捣乱。
  2. 测竞态用 volatile 或 _Atomic——否则你测的是编译器的优化，不是调度器的竞态。
  3. 错误码从 Pthreads 函数返回值取，不查 errno。
  4. 禁止拷贝 mutex / cond——身份不可复制。
  5. 所有路径都 unlock——早退分支、错误分支，用 goto cleanup 统一收尾。
  6. 多锁全局统一顺序；拿不准就 trylock + 退避；怀疑死锁用 timedlock 探测。
  7. cond 必须配 mutex：检查谓词持锁、改谓词持锁、wait 的放锁入睡醒来拿锁是原子的。
  8. 谓词永远 while，永远 while，永远 while——if 在虚假唤醒/惊群/错醒三种场景下全灭。
  9. 一个 cond 对应一个谓词——复用 cond 等多种状态是丢唤醒与错醒的温床。
  10. 唤醒语义按"至少一个"设计——signal 落空正常、惊群正常，正确性由谓词保证，效率由 signal/broadcast 选择与队列结构优化。

自测题

题目 1（综合）：一句话说清 mutex 和 cond 各自的职责，以及为什么"轮询 + usleep"两个都替代不了。

参考答案

mutex：互斥访问共享状态（"现在能不能碰"）；cond：等待状态变化（"变了叫我"）。轮询烧 CPU 且延迟随轮询间隔线性增加；usleep 睡着时拿不到"状态恰好变化"的事件。condvar 用一次内核 futex 睡眠换"零 CPU + 变化即醒"，是两者的合取；代价是被唤醒的微秒级延迟（系统调用 + 调度）。

题目 2（排错）：多消费者程序偶发挂死，日志显示消费者全停在 pthread_cond_wait，队列里还有数据。给出三个最可能的 bug 和对应检查点。

参考答案

① 谓词写成了 if：惊群/虚假唤醒穿透后消费了不存在的数据，后续状态错乱使 count 永不为正——检查谓词是否 while；② signal 落空：生产者不持锁（或改了谓词但 signal 了错误的 cond）——检查"持锁改谓词 → signal 同一个 cond"；③ 用 signal 但多个谓词复用一个 cond：被唤醒者 while 复查后睡回去，该醒的没人叫——检查 cond 与谓词是否一一对应。另有一个隐藏嫌疑：while (count==0) 忘了带关闭条件，关闭后没人 broadcast。

题目 3（成本）：为什么说"无竞争的 mutex 比原子加法还便宜"？什么时候这个结论反转？

参考答案

无竞争 lock = 一次 lock cmpxchg（0→1）+ unlock 一次原子写，共 7 ns；atomic_fetch_add 是 lock xadd，13.8 ns。反转点：① 有竞争时 mutex 走慢路径（自旋/futex 睡眠），成本跳到几十 ns 甚至微秒，而原子加法只涨到缓存行乒乓的 ~25 ns；② 如果临界区本来就是一条原子指令能表达的（计数器、序号），直接用 _Atomic 更便宜也更简单——mutex 保护的应该是"多条语句的复合不变量"。

题目 4（设计）：给一个采集（1 线程）→ 处理（1 线程）的嵌入式流水线选同步方案：数据速率 1 kHz，处理耗时 ~200 µs。

参考答案

1 kHz → 每 1 ms 一条数据，处理 200 µs 只占 20% CPU。方案：有界阻塞队列 + mutex + 两个 cond（not_full/not_empty），处理线程 while(空) wait 睡眠——CPU 占用近零（电池友好），延迟上限 1 个唤醒周期（µs 级）完全够用。不需要无锁结构（数据率低，锁无竞争或低竞争）。注意三点：队列容量按背压策略定（≥2×突发深度）；关闭要 broadcast + 谓词带 closed；嵌入式时钟跳变环境用 pthread_condattr_setclock(CLOCK_MONOTONIC) + timedwait 做看门狗。

综合题：多生产者-多消费者流水线（完整可运行）

要求：N_PROD 个生产者各产生 N_ITEMS 条消息 → 有界队列 → N_CONS 个消费者消费；统计每个生产者/消费者的处理量与总耗时；close() 后消费者优雅退出。参考实现（gcc -O2 -Wall -Wextra 零告警，-pthread）：

/* pipe_bench.c — Ch30.4 综合题：多生产多消费 + 优雅关闭 + 统计
 * 编译：gcc -O2 -Wall -Wextra -o pipe_bench pipe_bench.c -pthread
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>             /* intptr_t */
#include <pthread.h>
#include <time.h>

#define QCAP     64          /* 队列容量 */
#define N_PROD   3
#define N_CONS   2
#define N_ITEMS  20000       /* 每个生产者的条数 */

static double now_ns(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
    return t.tv_sec*1e9+t.tv_nsec;}

typedef struct {
    long buf[QCAP];
    int head, tail, count;
    int closed;
    pthread_mutex_t m;
    pthread_cond_t  not_full;    /* 生产者等空位 */
    pthread_cond_t  not_empty;   /* 消费者等数据 */
} bqueue_t;

static void bq_init(bqueue_t *q){
    q->head = q->tail = q->count = 0;
    q->closed = 0;
    pthread_mutex_init(&q->m, NULL);
    pthread_cond_init(&q->not_full, NULL);
    pthread_cond_init(&q->not_empty, NULL);
}

/* 返回 0 成功；-1 队列已关闭 */
static int bq_push(bqueue_t *q, long v){
    pthread_mutex_lock(&q->m);
    while (q->count == QCAP && !q->closed)      /* 满：等空位（关闭可打断）*/
        pthread_cond_wait(&q->not_full, &q->m);
    if (q->closed) { pthread_mutex_unlock(&q->m); return -1; }
    q->buf[q->tail] = v;
    q->tail = (q->tail + 1) % QCAP;
    q->count++;
    pthread_cond_signal(&q->not_empty);         /* 有了数据：叫一个消费者 */
    pthread_mutex_unlock(&q->m);
    return 0;
}

/* 返回 0 取到数据；-1 队列空且已关闭（EOF） */
static int bq_pop(bqueue_t *q, long *out){
    pthread_mutex_lock(&q->m);
    while (q->count == 0 && !q->closed)         /* 空：等数据（关闭可打断）*/
        pthread_cond_wait(&q->not_empty, &q->m);
    if (q->count == 0) {                        /* 空且关闭：收工 */
        pthread_mutex_unlock(&q->m);
        return -1;
    }
    *out = q->buf[q->head];
    q->head = (q->head + 1) % QCAP;
    q->count--;
    pthread_cond_signal(&q->not_full);          /* 腾出空位：叫一个生产者 */
    pthread_mutex_unlock(&q->m);
    return 0;
}

static void bq_close(bqueue_t *q){
    pthread_mutex_lock(&q->m);
    q->closed = 1;
    pthread_cond_broadcast(&q->not_empty);      /* 关闭是全局事件：全叫醒 */
    pthread_cond_broadcast(&q->not_full);
    pthread_mutex_unlock(&q->m);
}

static bqueue_t q;
static long prod_cnt[N_PROD], cons_cnt[N_CONS];
static long checksum_in, checksum_out;          /* 简单校验：所有消息求和 */

static void *producer(void *a){
    long id = (long)(intptr_t)a;
    for (long i = 0; i < N_ITEMS; i++) {
        if (bq_push(&q, id * N_ITEMS + i) != 0) break;   /* 被关闭 */
        prod_cnt[id]++;
        __atomic_fetch_add(&checksum_in, id * N_ITEMS + i,
                           __ATOMIC_RELAXED);
    }
    return NULL;}

static void *consumer(void *a){
    long id = (long)(intptr_t)a;
    long v;
    while (bq_pop(&q, &v) == 0) {
        cons_cnt[id]++;
        __atomic_fetch_add(&checksum_out, v, __ATOMIC_RELAXED);
    }
    return NULL;}

int main(void){
    pthread_t tp[N_PROD], tc[N_CONS];
    bq_init(&q);

    double t0 = now_ns();
    for (long i = 0; i < N_PROD; i++)
        pthread_create(&tp[i], NULL, producer, (void*)(intptr_t)i);
    for (long i = 0; i < N_CONS; i++)
        pthread_create(&tc[i], NULL, consumer, (void*)(intptr_t)i);

    for (int i = 0; i < N_PROD; i++) pthread_join(tp[i], NULL);
    bq_close(&q);                               /* 生产者全部收工 → 关队列 */
    for (int i = 0; i < N_CONS; i++) pthread_join(tc[i], NULL);
    double dt = now_ns() - t0;

    long total_in = 0, total_out = 0;
    for (int i = 0; i < N_PROD; i++) total_in  += prod_cnt[i];
    for (int i = 0; i < N_CONS; i++) total_out += cons_cnt[i];
    printf("生产 %ld 条（期望 %d），消费 %ld 条（期望 %d）\n",
           total_in, N_PROD * N_ITEMS, total_out, N_PROD * N_ITEMS);
    printf("校验和 in=%ld out=%ld %s\n", checksum_in, checksum_out,
           checksum_in == checksum_out ? "一致" : "✗ 不一致！");
    printf("各生产者: ");
    for (int i = 0; i < N_PROD; i++) printf("%ld ", prod_cnt[i]);
    printf("\n各消费者: ");
    for (int i = 0; i < N_CONS; i++) printf("%ld ", cons_cnt[i]);
    printf("\n总耗时 %.1f ms（%.1f ns/条，含队列阻塞与调度）\n",
           dt / 1e6, dt / total_out);
    return 0;
}

校验和 in=1799970000 out=1799970000 一致

各消费者: 32541 27459

逐条核对：

  1. 总账平：60000/60000，校验和一致——while 谓词 + 持锁 signal 的正确性证据。
  2. 消费者负载不均（39531 vs 20469）：signal 唤醒"至少一个"，谁抢到锁归谁——公平性不是 condvar 的承诺（需要公平就走门 semaphore/队列锁路线）。
  3. 9.6 µs/条远高于锁成本：队列空/满频繁切换睡眠，每条消息平均摊到一次唤醒往返（WSL2 放大值）；生产消费速率接近时这个数字会显著下降。
