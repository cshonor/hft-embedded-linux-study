章节目标

  • fork() 是「一调两返」 —— 父进程里返回子进程 PID、子进程里返回 0、失败返回 −1。这是全网唯一的分叉判据。实测 c24_lifecycle：父 fork() 返回 3、子 fork() 返回 0（沙箱里 pid 从 2 开始，见下）
  • 内存是「复制」的，fd 是「共享」的 —— 实测 t_fork：子 idata=333 istack=666、父 idata=111 istack=222（各有一份）而 fork_file_sharing 显示 offset 与 O_APPEND 都共享（同一个 open file description）
  • 信号三件事的继承规则不同 —— 实测 c24_sigmask_inherit：掩码继承、pending 清零、handler 表继承。机制在 kernel/fork.c:1091 *dst = *src;（整个 task_struct 拷一份）与 kernel/fork.c:2391 init_sigpending(&p->pending);（pending 显式清）
  • vfork() 不复制地址空间，父进程被挂起 —— 实测 t_vfork：子进程 sleep(3) 之后仍然先打印，父进程读到的 istack 是子进程改过的 666（初值 222）；execTime = 3027 就是那 3 秒挂起
  • fork() 之后谁先跑不确定，而且会「成簇」 —— 实测 whos_first_1000：1000 次里 parent 先 91.6%、child 先 8.4%；但 j ∈ [800, 860] 那 61 次里 56 次（92%） 是 child 先，而紧邻的 j ∈ [861, 999] 共 139 次一次都没有。这不是随机，是外部负载
  • 原书那个「调节旋钮」已经失效 —— /proc/sys/kernel/sched_child_runs_first 实测 ENOENT；probe24_sched 还拿到 nice = 19（最低优先级）、SCHED_OTHER、2 个 CPU —— 这说明「本机实测 xx%」必须连同调度环境一起说
  • 同步信号必须在 fork() 之前屏蔽 —— 原书 p.528 明说；反过来写会让父进程 sigsuspend() 永久挂起（子进程跑得快时信号被空 handler 消费掉）。实测 fork_sig_sync 的后两行顺序被保证，前两行自由（书上是 child 先，我们是 parent 先，都对）
  • WCOREDUMP 不是布尔值 —— glibc 里它是 status & 0x80，只能取 0 或 128。实测 ex24_3_core_dump：status=134、WTERMSIG=6、WCOREDUMP=128，但磁盘上没有 core 文件（./core 与 /core 都 ENOENT）
  • 容器里拿不到 core 是常态 —— 实测沙箱 RLIMIT_CORE = 0/0 且 hard limit 提不动（setrlimit 报 EPERM），而 core_pattern 是管道（|/usr/share/apport/apport ...）⇒ 管道模式下内核不看 RLIMIT_CORE（fs/coredump.c:613 直接设成 RLIM_INFINITY），所以流程走完、位置上了，但文件不落地
  • 诚实：本章所有实测都跑在 CE 公开 API（gcc 13.3.0 / x86-64 / Ubuntu 24.04，沙箱内核 7.0.0-1012-aws），不是本机。笔记明确标注了 CE 环境的硬边界：20 秒 SIGKILL、约 32 KB 输出采集上限、stdout 是 socket ⇒ 8 KB 全缓冲、PATH 为空、/bin/* 全部不存在（所以 c24_lifecycle 用 /proc/self/exe 做 exec 演示）、argv[0] 恒为 ./output.s

一条主线：本章只有「一个分叉」和它每一步的代价

阶段 调用 它给了什么 它带来的问题
一 fork() 一个几乎完全相同的副本（内存 COW、fd 共享） 谁先跑不确定 ⇒ 竞态

易错清单

  1. 把 fork() 理解成「重新运行程序」 —— 子进程从 fork() 返回处继续，不清空变量、不重跑 main
  2. 以为 fork() 之后内存是共享的 —— 是复制（COW）；共享的是 fd 背后的 open file description
  3. 以为文件偏移不共享 —— offset 与 O_APPEND 状态都在 open file description 里，父子共享（实测 fork_file_sharing：offset 0 → 1000）
  4. 忘了 fork() 之后 fd 是「加引用计数」而不是「复制对象」 —— 关掉一个不影响另一个；dup/fork 出来的 fd 指向同一个对象
  5. 以为 fork() 之后父进程/子进程一定谁先跑 —— 两个方向都是错的；实测 91.6% / 8.4%（§24.4）
  6. 用「本机多次运行都一样」当「行为确定」 —— 实测 j ∈ [800,860] 92% child 先、j ∈ [861,999] 0% —— 机器一忙，结论就翻
  7. 照抄书上的 sched_child_runs_first 调参 —— 实测内核上该文件 ENOENT；v6.7 起 upstream 已删除
  8. 在多核上讨论「谁先」 —— 书 p.525 明说多处理器上两者可能同时拿到 CPU
  9. printf 到 stdout 却不 setbuf(stdout, NULL) —— 父子各持一份全缓冲副本，顺序被缓冲吃掉；严重时同一行打印两次
  10. 在 fork() 之后才屏蔽同步信号 —— 原书 p.528 点名的错误；子进程跑得快时信号被空 handler 消费掉 ⇒ 父进程永久挂起
  11. 在 fork() 之后才 sigaction() —— 若信号在装 handler 之前递送，SIGUSR1 的默认动作是终止进程
  12. 用 pause() 代替 sigsuspend() —— 不是原子的，信号可能在两步之间丢失（经典竞态）
  13. sigsuspend() 的 -1 当错误处理 —— 正常被信号唤醒时也返回 −1 + EINTR；要写成 if (rc == -1 && errno != EINTR)
  14. 以为 fork 之后子进程的信号掩码是干净的 —— 掩码继承（实测），子进程也屏蔽着同一个信号
  15. 以为 pending 信号会跟着走 —— pending 清零（实测 c24_sigmask_inherit：父 1 / 子 0）
  16. 在 vfork() 子进程里改数据 —— 直接改到父进程的内存上（实测 istack=666）
  17. 在 vfork() 子进程里 return / exit() / 调库函数 —— SUSv3 三条 UB；return 通常直接 SIGSEGV
  18. 在 vfork() 子进程里用 printf —— stdio 缓冲在共享的用户地址空间里；原书为此用裸 write()
  19. 以为 vfork 之后 fd 表也共享 —— fd 表在内核里，vfork 仍然 copy_files()（实测 vfork_fd_test：父进程第一次 close(1) 成功）
  20. 以为 vfork 比 fork 快所以该用 —— COW 之后差距很小；原书结论是避免使用
  21. 在 NOMMU 平台上用 fork —— 内核直接 -EINVAL（kernel/fork.c 的 #ifndef CONFIG_MMU 分支）
  22. WCOREDUMP(status) 当布尔值 —— 它是 status & 0x80，取值 0 或 128（实测 128）
  23. 以为 WCOREDUMP 非 0 就是「磁盘上有 core 文件」 —— 实测 WCOREDUMP=128 而 ./core 不存在
  24. 以为把 RLIMIT_CORE 设大就能拿到 core —— hard limit 是 0 时非 root 提不动（实测 EPERM）；且 core_pattern 是管道时内核根本不看 RLIMIT_CORE
  25. 以为 fork();fork();fork(); 是 3 个新进程 —— 是 2³ − 1 =7 个（实测 ex24_1_fork_count）
  26. 忘了父进程必须 wait() —— 子进程变僵尸；父进程先死则子进程变孤儿被 init 收养（实测出现 ppid=1）

双线提示

线 本章拿什么去用
HFT ① 启动路径上的「父先做 A、子再做 B」是实盘事故高发点 —— 测试机永远是对的原因见 §24.4（机器闲 ⇒ 成簇偏向一侧）；正确做法是 pipe / eventfd / 信号握手，不是靠调度顺序；② fork() 的代价与父进程地址空间大小成正比（要复制页表）⇒ 想让 fork+exec 快，就该把父进程地址空间做小（别在父进程里 mmap 大块行情缓冲）；③ 实时调度（SCHED_FIFO/SCHED_RR）下不要把 fork 放在热路径 —— 通行做法是启动时一次性 fork/exec 好，之后只做进程间通信；④ 热路径里量出来的任何「调度顺序」结论都要连同 nice / CPU 数 / 宿主负载一起记录（本章实测环境就是 nice=19、2 核、共享宿主）
嵌入式 ① NOMMU 平台（uClinux 等）fork() 直接不可用（内核返回 -EINVAL）⇒ 只能 vfork()+exec()；这也是 BusyBox 在 NOMMU 下编译出不同代码的原因；② 单核上「谁先跑」只有两种可能，成簇效应更明显 ⇒ 更容易被误解成「确定行为」，写代码时更危险；③ 多线程进程 + fork 只保留调用线程（Ch33）⇒ 其它线程持有的锁可能永久锁死，嵌入式固件里要 fork 就立刻 exec；④ daemon 化的经典流程（双 fork + 父等子发信号）机制上就是 §24.5 那一套；⑤ 交叉工具链上 _BSD_SOURCE 这类 feature-test 宏要留意（vfork() 的声明依赖它）
两条线共同的坑 顺序是「观测到的」而不是「保证的」 —— 本章所有百分比（99.97% / 99.98% / 91.6%）都是特定内核 + 特定负载下的测量值；CE 的 PATH 为空、/bin/* 不存在、argv[0] 恒为 ./output.s、20 秒 SIGKILL、32 KB 输出上限都会影响演示形式

Overview of fork(), exit(), wait(), and execve() 四个调用的分工

本章：TLPI 第 24 章 — Process Creation 源码核验：man7 官方 Ch24 分发文件 7 个（procexec/）· 原书 §24 正文（书页 513–530）· 官方 Makefile.inc 编译参数 · Linux v6.6（kernel/fork.c / fs/file.c / mm/memory.c）· glibc 2.39 · CE 实测（gcc 13.3.0 / x86-64 / Ubuntu 24.04，沙箱内核 7.0.0-1012-aws） 本章所有实测数字来自冻结日志 tlpi-ch24-final*.txt - 上一节：本章首页 - 下一节：24.2 Creating a New Process: fork()

本节讲什么

原书 §24.1 只有 一张图（Figure 24-1）。它把「进程从哪来、怎么走」压缩成四个调用：

fork() ──► 复制出一个新进程
exit() ──► 结束自己，留下一个 8 位状态码
wait() ──► 父进程取回子进程的终止状态
execve() ► 用另一个程序**替换**当前进程的映像

后面三章就是在把这四个调用逐个展开：Ch25（进程终止）、Ch26（监控子进程）、Ch27（程序执行）。本节只做两件事：把职责边界画清，把四个调用的最小闭环跑通。

⚠️ 原书这一节没有任何 Listing、也没有配套程序，只有图。本仓库为此写了一个程序 （c24_lifecycle.c，见下），把 Figure 24-1 变成一串可运行的真实输出—— 这样后面三章每深入一个调用时，都有一个共同的地基可以对照。

1. 四个调用各自的职责与「展开在哪一章」

调用 一句话职责 谁创建/销毁了什么 原书展开
fork() 复制出一个几乎一模一样的新进程 内核克隆 task_struct + 复制页表（COW） 本章 §24.2；细节在 Ch28
exit() / _exit() 主动结束自己 释放内存/fd，状态码留在一个 8 位字段里 Ch25
wait() / waitpid() 父进程取回终止状态 回收僵尸（zombie） Ch26
execve() 用另一个程序替换当前映像 保留 PID、fd 表、PID/会话；换掉代码段 Ch27

⭐ 一句话记住四者的关系：fork 负责「多一个」，exec 负责「变一个」，exit 负责「少一个」，wait 负责「知道少的那一个怎么走的」。

2. Figure 24-1 的文字版

原书那张图的核心信息量，用表格重画一遍（这是后面三章的坐标系）：

时刻 调用者 动作 谁还在跑
① 父进程 走到 fork() 父进程阻塞在 fork() 里
② 内核 克隆出子进程；两个进程都从 fork() 返回 父、子都就绪
③ 子进程 走到 exit()/_exit() 只剩父进程
④ 父进程 fork() 返回子进程 PID，继续跑；需要时调 wait() 取状态 父进程
⑤ 子进程 （另一条路）走到 execve()——不创建新进程，只是换映像 同一个 PID 在跑新程序

⚠️ ② 那一步有个容易说错的点：fork() 是一次调用、两次返回。父进程拿到的返回值是子进程的 PID，子进程拿到的是 0；失败时只有父进程拿到 -1。所以 if (pid == 0) 是「我是子进程」的判据，不是「fork 成功了」。

3. 先给三条结论（后面几节会一一钉死）

  1. fork 的复制是「写时才复制」（COW）。所以「父子的全局变量互不影响」不是靠一开始就拷贝，而是靠写触发缺页。§24.2 的 Listing 24-1、24-3 演示这件事。
  2. fd 表被复制，但 struct file 是共享的。父子写同一个 fd，文件偏移是同一个。§24.2.1 的 Listing 24-2 演示这件事。
  3. fork 之后谁先跑是不确定的。要靠 wait()/信号来定序，不能靠 sleep()。§24.4、§24.5 演示这件事。

/* c24_lifecycle.c

   ⚠️ 本仓库自写 —— 原书 §24.1 **只有一张 Figure 24-1**（"Overview of the use of
      fork(), exit(), wait(), and execve()"），既没有 Listing，也没有配套程序。

   本程序把 Figure 24-1 从"一张图"变成"一串可运行的真实输出"：

     ① 单进程：报自己的 pid / ppid
     ② fork()  —— 一次调用，两个返回值（父得子 pid，子得 0）
     ③ _exit(7) —— 子进程带一个状态码退出
     ④ wait(&status) —— 父进程取回状态，并把它**解码**（很多人只会用 WEXITSTATUS
        却不知道 status 里还有什么）
     ⑤ fork() + execve() —— 再起一个子进程，用 exec 把它的**程序映像**换掉；
        对照 ③：这次子进程不是"_exit"，而是"变成了另一个程序"

   ⚠️ ⑤ 为什么 exec 的是「自己」（/proc/self/exe）而不是 /bin/echo：
      CE 的 executor 沙箱里 **PATH 是空的、/bin 和 /usr/bin 下什么都没有**
      （实测见 code/probe24.c：`access("/bin/echo", X_OK) == -1`）。
      而 exec 自己恰好是最干净的演示 —— 同一个可执行文件，换一副 argv 就是
      「另一个程序」；并且能顺便看到 **exec 不换 PID**（对比 fork 会换）。

   ⚠️ 没写 exit() vs _exit() 的区别：那是 §25.1 的主题（exit() 会刷 stdio 缓冲、
      会跑 atexit 处理器，_exit() 不会）。这里两个都用 `_exit()`。

   编译（自包含）：
     gcc -O0 -Wall -Wextra -o c24_lifecycle c24_lifecycle.c
*/

#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

int main(int argc, char *argv[])
{
    pid_t childPid;
    int status;

    setvbuf(stdout, NULL, _IONBF, 0);   /* 关缓冲，父子输出不互相夹杂 */

    /* ---- 被 ⑤ 里的 exec 拉起来时走这条分支：说明"我已经是另一个映像了" ---- */
    if (argc > 1 && strcmp(argv[1], "--after-exec") == 0) {
        printf("⑤★ exec 之后  pid 还是 %ld —— execve 换映像但**不换 PID**\n",
                (long) getpid());
        printf("     （能走到这一行，本身就证明 execve 成功了：\n");
        printf("      同一个可执行文件，靠 argv[1]=\"%s\" 走了不同分支）\n", argv[1]);
        return 0;
    }

    /* ---------------- ① ---------------- */
    printf("① 单进程      pid=%ld ppid=%ld\n", (long) getpid(), (long) getppid());

    /* ---------------- ② ③ ④ ------------- */
    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:                                  /* ③ 子进程 */
        printf("② 子进程      pid=%ld  fork() 返回 0（这是子进程的判据）\n",
                (long) getpid());
        printf("③ 子进程      _exit(7) —— 带 7 退出\n");
        _exit(7);                            /* 注意：不是 exit() */

    default:                                 /* ② 父进程 */
        printf("② 父进程      pid=%ld  fork() 返回 %ld（= 子进程 pid）\n",
                (long) getpid(), (long) childPid);

        if (wait(&status) == -1)             /* ④ */
            die("wait");

        /* status 不是"退出码"，是内核打包的一整块信息 */
        printf("④ 父进程      wait() 拿到 status=%d\n", status);
        printf("   WIFEXITED   = %d\n", WIFEXITED(status));
        printf("   WEXITSTATUS = %d   （子进程 _exit 的那个 7）\n",
                WEXITSTATUS(status));
        printf("   WIFSIGNALED = %d   （0 = 不是被信号杀死的）\n",
                WIFSIGNALED(status));
        printf("   —— 7 << 8 = %d，所以直接看 status 会看到 %d 而不是 7\n",
                7 << 8, 7 << 8);
        break;
    }

    /* ---------------- ⑤ execve 把子进程换成另一个程序 ------------- */
    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:
        printf("⑤ 子进程      pid=%ld 即将 exec —— 下面两行的输出来自新映像\n",
                (long) getpid());
        execl("/proc/self/exe", "c24_lifecycle", "--after-exec", (char *) NULL);
        die("execl(/proc/self/exe)");        /* exec 成功则永远到不了这里 */

    default:
        if (wait(NULL) == -1)
            die("wait");
        printf("⑤ 父进程      第二个子进程（pid=%ld）也收完了\n", (long) childPid);
        break;
    }

    printf("── 结束：Figure 24-1 的四个调用都跑过一遍了 ──\n");
    return 0;
}

逐条解读

① pid=2 ppid=1 —— 不是笔误，是容器 PID namespace 的直接证据。这个程序是 新 PID namespace 里的第 2 个进程（1 号是 namespace 的 init），它的父进程是 namespace 外的进程，映射进来就是 1。所以本章后面所有日志里的 PID 都是 2、3、4…… 这种一位数。⚠️ 这不代表「PID 不会超过几」 —— probe24 实测 _SC_CHILD_MAX = 54956、RLIMIT_NPROC = 54956，能开的进程多得很。

② 一次调用、两次返回 —— 父进程拿到 3（子进程的 PID），子进程拿到 0。 注意输出顺序：父进程那行先出现。这不是保证，只是这次调度如此（§24.4 会把这件事 量化）。原书 Listing 24-1 里用 sleep(3) 在父进程侧来"保证"子进程先打印，原书自己 也承认这不是可靠办法（书 p.517 原话："Using sleep() in this manner is not a foolproof method of guaranteeing this result"）。

③ _exit(7) —— 用的是 _exit() 而不是 exit()。本文刻意如此：exit() 会 刷 stdio 缓冲，而 stdout 在 CE 上是 socket（8KB 全缓冲），两者的差别会立刻 体现出来。这条差异是 Ch25 §25.1 的主题，本节只留个钩子。

④ status=1792 而有用的退出码是 7 —— 这是最容易踩的坑：wait(&status) 给回来的 status 不是退出码，而是内核打包的一整块终止信息。退出码只占 8 位，放在 status 的高 8 位里（7 << 8 == 1792），低 7 位留给信号编号等。 所以必须用 WEXITSTATUS(status) 取，不能直接 printf("%d", status)。

⚠️ 为什么是 8 位？因为内核里这个字段本身只有 8 位：进程的 exit_code 是 int，但 wait() 只把低 8 位（0xFF）当作退出状态交给父进程（见「源码坐标」）。 所以 _exit(256) 和 _exit(0) 在父进程看来是同一个值 0。

⑤ exec 把映像换掉、但 PID 不变 —— 这一行 ⑤★ exec 之后 pid 还是 4 是本节 最有价值的一条对照： * fork() 出来的是新 PID（②里 2 → 3）； * execve() 不创建进程，所以 PID 不变（⑤里 4 → 4）。

⚠️ 为什么 exec 的是自己（/proc/self/exe）而不是 /bin/echo：CE 的 executor 沙箱里 PATH 是空的，/bin、/usr/bin 下的常规程序一个都不存在。这不是 猜测，是 code/probe24.c 的实测（见下）。而「exec 自己 + 用一个 argv 走另一条分支」 反而把 execve 的语义演示得更纯：同一个可执行文件，换一副 argv 就是另一个程序。

  • WEXITSTATUS 只有 8 位 = 子进程的"错误码"只能塞 0–255：HFT 里常用它把子进程 （比如行情录制进程）的失败原因带回来。超过 255 就要走别的通道（pipe / 共享内存 / 退出日志），本仓库 §24.7 的习题 24-1、24-5 都会碰到这个约束。

  • PID namespace（本节 ① 的 pid=2） 是容器隔离的基础；HFT 里用它把策略进程 的 PID 空间与宿主机上的运维工具隔开，副作用是 /proc 里的 PID 与宿主机不同 —— 排查问题时要记得看 NSpid 而不是 Pid。

代码自测（Q&A）

Q1：fork() 返回 -1 时，子进程存在吗？

A：不存在。失败时只有调用者一侧会从 fork() 返回，返回 -1 并把 errno 设好 （常见是 EAGAIN/ENOMEM）。所以「一次调用两次返回」只在成功时成立。

Q2：为什么本节 ② 里父进程那行先打印？这是保证吗？

A：不是。这是调度器的临时决定。原书 p.517 用 sleep(3) 在父进程侧来"保证" 子进程先跑完，并且自己说明这不是 foolproof（因为 sleep 到期后调度谁、以及 子进程是否已经跑完，都不受你控制）。§24.4 用 1000 次 fork 把这个不确定性量化了。

Q3：_exit(7) 之后父进程拿到 status=1792，为什么不是 7？

A：因为 wait(&status) 交回的是内核打包的一整块终止信息，退出码只占高 8 位。 7 << 8 == 1792。要用 WEXITSTATUS(status) 取。反过来说，只有 0–255 能被带出去： _exit(256) 父进程会看到 0。

Q4：⑤ 里 exec 之后 PID 没变，那「exec 也算创建了个进程」这种说法错在哪？

A：错在「进程」的判定标准。execve() 不调用 copy_process()，它只在当前进程里 换掉 mm_struct 指向的代码/数据映像（PID、task_struct、fd 表、PID/会话都留着）。 所以进程个数不变 —— 这正是 Figure 24-1 把 fork 和 execve 画成两个不同分支的原因。

Q5：本节为什么不用 /bin/echo 做 exec 演示，而要 exec 自己？

A：因为 CE 的 executor 沙箱里 PATH 是空的、/bin 和 /usr/bin 下什么都没有 （probe24.c 实测：access("/bin/echo", X_OK) == -1）。所以 execlp() 一定失败 （ENOENT），而 execl() 只能给绝对路径。/proc/self/exe 是探测中唯一可执行的 绝对路径 —— 而且拿它做演示更干净：同一个文件、不同 argv = 不同程序，还顺带 把「exec 不换 PID」显示出来了。

Q6：pid=2 ppid=1 说明这台机器上只有几个进程吗？

A：完全不是。这是容器 PID namespace 造成的：这个程序是它所在 namespace 里 第 2 个进程，1 号是 namespace 的 1 号进程。probe24 实测 _SC_CHILD_MAX = 54956、RLIMIT_NPROC = 54956 —— 能开的进程一点都不少。 把 namespace 的 PID 当成"机器上的序号"是排查容器问题时的经典翻车点。

/* t_fork.c

   Demonstrate the use of fork(), showing that parent and child
   get separate copies of stack and data segments.
*/
#include "tlpi_hdr.h"

static int idata = 111;             /* Allocated in data segment */

int
main(int argc, char *argv[])
{
    int istack = 222;               /* Allocated in stack segment */
    pid_t childPid;

    switch (childPid = fork()) {
    case -1:
        errExit("fork");

    case 0:
        idata *= 3;
        istack *= 3;
        break;

    default:
        sleep(3);                   /* Give child a chance to execute */
        break;
    }

    /* Both parent and child come here */

    printf("PID=%ld %s idata=%d istack=%d\n", (long) getpid(),
            (childPid == 0) ? "(child) " : "(parent)", idata, istack);

    exit(EXIT_SUCCESS);
}

2. §24.2.1 文件语义：fd 表复制，但 struct file 共享

这是最容易想错的一处。fork 之后：

  • fd 表（fd → struct file * 的映射）是复制的 —— 你 close(3) 不影响对方；
  • 但 struct file（打开文件描述，里面装着文件偏移和 open file status flags） 是同一个对象 —— 所以父子 write 同一个 fd 会接着对方的偏移往下写。

原书 Listing 24-2（fork_file_sharing.c，书 p.519）用两条可观察量把这个语义扒出来： 文件偏移 和 O_APPEND 标志。

/* fork_file_sharing.c

   Show that the file descriptors of a forked child refer to the
   same open file objects as the parent.
*/
#include <sys/stat.h>
#include <fcntl.h>
#include <sys/wait.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int fd, flags;
    char template[] = "/tmp/testXXXXXX";

    setbuf(stdout, NULL);                   /* Disable buffering of stdout */

    /* Open a temporary file, set its file offset to some arbitrary value,
       and change the setting of one of the open file status flags. */

    fd = mkstemp(template);
    if (fd == -1)
        errExit("mkstemp");

    printf("File offset before fork(): %lld\n",
            (long long) lseek(fd, 0, SEEK_CUR));

    flags = fcntl(fd, F_GETFL);
    if (flags == -1)
        errExit("fcntl - F_GETFL");
    printf("O_APPEND flag before fork() is: %s\n",
            (flags & O_APPEND) ? "on" : "off");

    switch (fork()) {
    case -1:
        errExit("fork");

    case 0:     /* Child: change file offset and status flags */
        if (lseek(fd, 1000, SEEK_SET) == -1)
            errExit("lseek");

        flags = fcntl(fd, F_GETFL);         /* Fetch current flags */
        if (flags == -1)
            errExit("fcntl - F_GETFL");
        flags |= O_APPEND;                  /* Turn O_APPEND on */
        if (fcntl(fd, F_SETFL, flags) == -1)
            errExit("fcntl - F_SETFL");
        _exit(EXIT_SUCCESS);

    default:    /* Parent: can see file changes made by child */
        if (wait(NULL) == -1)
            errExit("wait");                /* Wait for child exit */
        printf("Child has exited\n");

        printf("File offset in parent: %lld\n",
                (long long) lseek(fd, 0, SEEK_CUR));

        flags = fcntl(fd, F_GETFL);
        if (flags == -1)
            errExit("fcntl - F_GETFL");
        printf("O_APPEND flag in parent is: %s\n",
                (flags & O_APPEND) ? "on" : "off");
        exit(EXIT_SUCCESS);
    }
}

  • ⚠️ 两个「不共享」的对照（别搞混）：
  • fd 表不共享 —— 子进程 close(fd) 之后父进程那个 fd 还在（习题 24-2 就是用 vfork 演示同一件事，见 §24.7）；

3. §24.2.2 内存语义再进一步：COW 可以主动利用

原书 §24.2.2（书 p.522）说清了一件事：fork 时的"复制"是 COW（copy-on-write）—— 一开始父子指向同一批物理页，只有谁写了才真正复制那一页。所以：

  • fork 本身很便宜（不拷内存）；
  • 但一旦父子都大量写，内存就会翻倍 —— 这时 COW 反而没有帮你省。

Listing 24-3（footprint.c，书 p.522）把 COW 反着用：想让"用完就还"的内存不留在 自己身上，就把它放到子进程里去花。子进程一退出，它占的那些物理页全部还回系统， 父进程的"内存足迹"一点没变。

/* footprint.c

   Using fork() + wait() to control the memory footprint of an application.

   This program contains a function that (artificially) consumes a large
   amount of memory. To avoid changing the process's memory footprint, the
   program creates a child process that calls the function. When the child
   terminates, all of its memory is freed, and the memory consumption of
   the parent is left unaffected.
*/
#define _BSD_SOURCE     /* To get sbrk() declaration from <unistd.h> in case
                           _XOPEN_SOURCE >= 600; defining _SVID_SOURCE or
                           _GNU_SOURCE also suffices */
#include <sys/wait.h>
#include "tlpi_hdr.h"

static int
func(int arg)
{
    int j;

    for (j = 0; j < 0x100; j++)
        if (malloc(0x8000) == NULL)
            errExit("malloc");
    printf("Program break in child:  %10p\n", sbrk(0));

    return arg;
}

int
main(int argc, char *argv[])
{
    int arg = (argc > 1) ? getInt(argv[1], 0, "arg") : 0;
    pid_t childPid;
    int status;

    setbuf(stdout, NULL);           /* Disable buffering of stdout */

    printf("Program break in parent: %10p\n", sbrk(0));

    childPid = fork();
    if (childPid == -1)
        errExit("fork");

    if (childPid == 0)              /* Child calls func() and */
        exit(func(arg));            /* uses return value as exit status */

    /* Parent waits for child to terminate. It can determine the
       result of func() by inspecting 'status' */

    if (wait(&status) == -1)
        errExit("wait");

    printf("Program break in parent: %10p\n", sbrk(0));

    printf("Status = %d %d\n", status, WEXITSTATUS(status));

    exit(EXIT_SUCCESS);
}

  • ⚠️ 地址每次运行都不一样，而且 CE 可能换宿主机 —— 本节的四个地址是同一次冻结 日志里的原样，只用来做相对比较（父 vs 子、前 vs 后），不能当"某个固定值"引用。
  • 父进程前后两次 sbrk(0) 完全相同 —— 这就是 COW 的可见证据：子进程那 8 MB 与 父进程的堆顶无关，子进程退出后彻底还给系统，父进程自己的堆顶一米没动。
  • Status = 0 0 vs Status = 1792 7：第二个数是 WEXITSTATUS(status)，即 func(arg) 的返回值。传 7 就带回 7（第一次 status 是 1792 = 7 << 8， 原理见 §24.1 的 ④）。默认无参数时 arg=0，所以两个都是 0。
  • ⭐ 这个模式（fork 出去干重活、干完 exit 把内存还掉、用 8 位退出码把结果带回来） 是 HFT/后端里非常真实的手法，见「HFT / 嵌入式关联」。

     ① 信号掩码（signal mask）**继承**

        父进程先屏蔽 SIGUSR1，再 raise(SIGUSR1) ⇒ 这个信号变成「已产生但未递送」

#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

int main(void)
{
    sigset_t blockSet, curSet, pendingSet;
    pid_t childPid;

    /* 关掉 stdout 缓冲：父子两段输出不会互相污染（CE 的 stdout 是 socket，
       glibc 会按 8KB 全缓冲 —— 不关的话父子各持一份副本缓冲，容易看不出真相）*/
    setvbuf(stdout, NULL, _IONBF, 0);

    /* ---------- 父进程：屏蔽 SIGUSR1，并让它变成 pending ---------- */
    sigemptyset(&blockSet);
    sigaddset(&blockSet, SIGUSR1);
    if (sigprocmask(SIG_BLOCK, &blockSet, NULL) == -1)
        die("sigprocmask(SIG_BLOCK)");

    if (raise(SIGUSR1) != 0)          /* 自己给自己发；因为被屏蔽 ⇒ 停在 pending */
        die("raise(SIGUSR1)");

    if (sigprocmask(SIG_BLOCK, NULL, &curSet) == -1)   /* 查询当前掩码 */
        die("sigprocmask(查询掩码)");
    if (sigpending(&pendingSet) == -1)
        die("sigpending");

    printf("父进程 pid=%ld ppid=%ld\n", (long) getpid(), (long) getppid());
    printf("  掩码 中 SIGUSR1 = %d   （1 = 屏蔽）\n", sigismember(&curSet, SIGUSR1));
    printf("  pending 中 SIGUSR1 = %d   （1 = 有未递送信号）\n",
            sigismember(&pendingSet, SIGUSR1));

    /* ---------- fork：掩码与 pending 的继承差异就在这一刻分开 ---------- */
    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:   /* 子进程：什么都不改，只把继承到的东西读出来 */
        if (sigprocmask(SIG_BLOCK, NULL, &curSet) == -1)
            die("child sigprocmask(查询掩码)");
        if (sigpending(&pendingSet) == -1)
            die("child sigpending");

        printf("子进程 pid=%ld ppid=%ld\n", (long) getpid(), (long) getppid());
        printf("  掩码 中 SIGUSR1 = %d   （继承来的）\n", sigismember(&curSet, SIGUSR1));
        printf("  pending 中 SIGUSR1 = %d   （不继承）\n",
                sigismember(&pendingSet, SIGUSR1));
        _exit(EXIT_SUCCESS);

    default:
        if (waitpid(childPid, NULL, 0) == -1)
            die("waitpid");

        /* 父进程自己再看一眼：raise(SIGUSR1) 那个信号仍然挂在自己身上 */
        if (sigpending(&pendingSet) == -1)
            die("sigpending");
        printf("父进程 fork 之后：pending 中 SIGUSR1 = %d（自己的还留着）\n",
                sigismember(&pendingSet, SIGUSR1));
        _exit(EXIT_SUCCESS);
    }
}

HFT / 嵌入式关联

  • Listing 24-3 的 footprint 模式是真实手法：想跑一次"吃 8 MB 的解析"又不让 常驻进程的 RSS 涨上去，就 fork 出去做、用退出码（8 位）把结果带回来。 HFT 里的场景：盘前一次性把历史数据反序列化成索引、或者跑一遍"预热/自检"。 代价是结果只有 0–255，超了得走 pipe / 共享内存。
  • fd 共享偏移是 HFT 日志的暗坑：行情录制进程 fork 出子进程后，父子都往同一个 O_APPEND 日志 fd 写 —— 因为共享偏移，不会互相覆盖（这正是 O_APPEND 在 struct file 里的意义）。但如果没有 O_APPEND，两条流会交错着互相破坏。
  • COW 与 HFT 的"快照语义"：策略进程 fork 出风控进程后，风控看到的是fork 那一刻 的一致内存快照（COW），不需要加锁。这是"用 fork 代替读写锁"的经典招式；代价是 指针/句柄在父子间的语义必须自查（fd 是共享的，见上）。
  • 嵌入式 / NOMMU：fork() 需要 MMU 才能做 COW。uClinux 这类无 MMU 平台上 只有 vfork() 可用（§24.3 会讲它为什么可行）；这也是很多 RTOS 移植里 "为什么没有 fork" 的答案。
  • RLIMIT_NOFILE = 100（probe24 实测）：嵌入式默认 fd 上限往往很小， fork 继承的 fd 表就这么大；写守护进程时 close 掉不需要的 fd 不只是卫生问题， 是真会撞上限。

代码自测（Q&A）

Q1：Listing 24-1 里子进程改了 idata，为什么父进程看不到？

A：因为是 COW 出来的副本。idata 在数据段，父子的页表都指向同一批物理页， 子进程执行 idata *= 3 触发写保护缺页，内核这时才复制那一页并让子进程的页表 指过去。父进程的页表没动，所以仍读到 111。

Q2：那为什么 Listing 24-2 里子进程改的偏移和 O_APPEND，父进程看得到？

A：因为这俩不在内存副本里，而在内核的 struct file 里。dup_fd() 只复制 fd 表的指针数组并对每个 struct file 加引用计数（fs/file.c:385 的 get_file(f)）， 父子指向同一个 struct file。所以对它的修改双方都看得见。

Q3：Status = 1792 7 里那个 1792 是什么？

A：7 << 8。wait(&status) 的 status 是内核打包的终止信息，退出码占高 8 位。 第二个数才是 WEXITSTATUS(status) 的结果。这就是为什么退出码只能是 0–255。

Q4：footprint 里父进程两次 sbrk(0) 一样，能不能推出"父进程内存完全没变"？

A：不能。sbrk(0) 只是堆顶地址。子进程那 8 MB 与父进程堆顶无关，这一点是确定的； 但"父进程内存完全没变"需要看 RSS。原书用 sbrk(0) 是因为它足以说明「子进程分配的内存 没有算到父进程的堆上」——结论方向对，但证据强度要按"堆顶"这个口径来读。

Q5：为什么本节反复强调 setbuf(stdout, NULL) / _exit()？

A：因为 CE 的 stdout 是 socket（不是终端），glibc 会按 8KB 全缓冲。 于是「父子共享一份被复制过的缓冲区」这个经典坑真的会发生：不关缓冲、又用 exit()，同一行就会打印两遍。原书把这个坑正式放在 Ch25 的 Listing 25-2 （fork_stdio_buf.c）。

Q6：延伸 demo 里为什么父进程的 pending 是 1，子进程是 0？

A：copy_process() 里有一行 init_sigpending(&p->pending); （kernel/fork.c:2391）—— 新进程的 pending 集被显式清空。这是 POSIX 的要求 （"shall be initialized to the empty set"），不是 Linux 的实现意外。 而信号掩码是 copy_sighand()/copy_signal() 复制过来的，所以继承。

Q7：如果子进程在 fork 之后立刻 close(0)，父进程的 0 号 fd 会怎样？

A：不受影响。fd 表是复制的（dup_fd 造了新表），关闭只改自己那张表。 原书习题 24-2 就是考这个，而且是用 vfork 来演示（见 §24.7 的 vfork_fd_test.c）—— vfork 连地址空间都不复制，却仍然复制 fd 表，对照更强烈。

本节讲什么

vfork() 也创建子进程，但它和 fork() 有两条根本差异：

差异 fork() vfork()
地址空间 复制（COW） 不复制 —— 子进程跑在父进程的地址空间里
谁先跑 不确定（调度器定） 子进程保证先跑；父进程被挂起，直到子进程 exec() 或 _exit()

结论先给：原书的态度是「能不用就别用」。原因不是性能（COW 之后 vfork 的性能优势 基本没了），而是它的语义让"写错"变成"直接把父进程搞崩"。

⭐ 本节的核心证明只需要两行输出对比：子进程 sleep(3) 之后仍然先打印 （说明父进程真的被挂起了），以及父进程读到的 istack 是子进程改过的值 （说明内存真的共享）。

位置 写法 为什么这么写
子进程 write(STDOUT_FILENO, "Child executing\n", 16) 用裸 write 而不是 printf —— 因为 stdio 的缓冲区在共享的地址空间里，父子用同一个 FILE 状态会互相破坏
父进程 write(...) 之后才 printf("istack=%d\n") 父进程这边已经等到子进程走了，用 printf 安全
子进程 _exit(EXIT_SUCCESS) 必须 _exit，不能 return，也不能 exit()（见第 4 节）

④ ⚠️ 关于那个 sleep(3)：它其实"违规"了。

原书在注释里写 "Even if we sleep for a while, parent still is not scheduled" —— 这个 sleep(3) 是故意放的：它让"父进程被挂起"从"一瞬间的事"变成"肉眼可见的 3 秒"。

但严格按 SUSv3 说，sleep() 属于"calls any other function before successfully calling _exit() or performing an exec()"，也就是行为未定义的那一类。 在 glibc/Linux 上它恰好能工作（因为 sleep 只是个系统调用，不碰栈上的复杂状态）， 但这是"能跑"，不是"保证能跑"。读原书代码时要能分辨这种"演示性违规"。

3. 为什么 vfork 里能安全做的事只有"操作 fd"

原书（书 p.525）明确列了边界：

"There are a few things that the child process can do between vfork() and exec() without affecting the parent. Among these are operations on open file descriptors (but not stdio file streams). Since the file descriptor table for each process is maintained in kernel space (Section 5.4) and is duplicated during vfork(), the child process can perform file descriptor operations without affecting the parent."

拆开看就三句：

  1. fd 表在内核里（struct files_struct 挂在 task_struct 上，不在用户地址空间）；
  2. vfork 仍然复制 fd 表（和 fork 一样走 copy_files()）；
  3. 所以子进程 close(0) 只改自己那张表，父进程不受影响。

⚠️ 但 stdio 流（FILE *）不行 —— stdin/stdout 这些 FILE 结构和它们的缓冲区 就在共享的用户地址空间里。子进程往里写，父进程醒来后看到的是被改过的状态。 这就是原书 Listing 24-4 里子进程用 write() 而不用 printf() 的原因。

这一条正是习题 24-2 的题面，官方给了参考解 vfork_fd_test.c（见 §24.7）。

4. SUSv3 规定的「未定义行为」三条

原书（书 p.525）原样引了这三条：

"SUSv3 says that the behavior of a program is undefined if it: a) modifies any data other than a variable of type pid_t used to store the return value of vfork(); b) returns from the function in which vfork() was called; or c) calls any other function before successfully calling _exit() or performing an exec()."

为什么是这三条？逐条对上内核机制：

违规 后果 机制
a) 改别的数据 直接改到父进程的内存 共享 mm_struct（CLONE_VM）
b) 从函数返回 栈被搞坏，典型 SIGSEGV 父子共用同一段栈；子进程返回时把父进程的栈帧弹掉了
c) 调别的函数 同上（大多是栈操作）；还可能破坏 libc 状态 库函数的局部变量/缓冲区都在共享栈上

原书为此举了个类比（书 p.525）："This is similar to the example described in Section 6.8 of trying to longjmp() into a function from which a return has already been performed." —— 对应本仓库 C 语言模块的 §6.8 那节讲的"跳回已返回的函数"。

5. 为什么现在不该用它

年代 情况
早期 UNIX / 无 COW 的 fork fork 要真的拷整个地址空间，vfork+exec 省掉这一大笔开销，是刚需
有 COW 之后 fork 只复制页表、不拷内存 ⇒ 省下的那点开销不再重要
今天 vfork 语义危险（上面三条 UB）、且可移植性差（POSIX 曾一度把它移除又加回）。原书建议：除非有明确理由，否则用 fork()

⭐ 现在唯一还"必须有"的场景是 NOMMU 平台（uClinux 之类）：没有 MMU 就没有 COW， fork() 根本实现不了，只能 vfork()+exec。

常见坑

HFT / 嵌入式关联

  • vfork 是 posix_spawn 类实现的底层手法之一：glibc 的 posix_spawn 在没有 clone3(CLONE_VM|CLONE_VFORK) 快路径时，就走"vfork 一个子进程 → 子进程里只做 fd 操作 → exec"。理解"子进程在 exec 之前只能碰 fd"，就知道为什么 posix_spawn 的 file_actions 能精确表达"重定向 fd"却表达不了太复杂的东西。
  • HFT 冷启动延迟：策略进程 fork+exec 的启动路径上，fork 的页表复制成本与 父进程地址空间大小成正比。实测手法是把"父进程地址空间做小"（别在父进程里 mmap 大块行情缓冲），而不是换 vfork —— 因为 COW 下 dup_mm 仍要复制页表。
  • 嵌入式 / NOMMU（uClinux、部分 Cortex-M + Linux 变体）：fork() 直接不可用 （内核返回 -EINVAL），vfork()+exec() 是唯一路径。这也是 BusyBox 在 NOMMU 下 会编译出不同代码的原因。
  • vfork 与"共享栈"的坑在裸机/RTOS 移植里换个名字出现：本质是"两个执行流用 同一段栈" —— 任何中断服务例程在共享栈上做函数调用都会踩到同一类问题。 理解了 vfork 为什么禁止 return，就理解了中断上下文的栈纪律。

代码自测（Q&A）

Q1：t_vfork 里子进程 sleep(3)，为什么 Parent executing 还是排在它后面？

A：因为 vfork 的语义是父进程挂起，直到子进程 exec() 或 _exit()。 这 3 秒里父进程根本没被调度。execTime = 3027 毫秒就是这段挂起时间； fork 版本（Listing 24-1）里那 3 秒是父进程自己 sleep 的，性质完全不同。

Q2：istack=666 说明了什么？

A：说明子进程没有自己的 istack。它写的是父进程栈上的那一个变量 （222 * 3 = 666）。这是"共享地址空间"（CLONE_VM）的直接观察。

Q3：为什么子进程用 write() 而父进程能用 printf()？

A：stdio 的 FILE 对象和缓冲区在用户地址空间，而 vfork 子进程和父进程共用这段 空间。子进程动 stdio 就等于动父进程的 stdio 状态。用裸 write() 绕过 stdio 才安全。 父进程那侧已经等子进程结束了（wait 语义由 vfork 自动保证），所以 printf 没问题。

Q4：vfork 子进程里 close(0) 会不会把父进程的 0 号 fd 也关掉？

A：不会。fd 表在内核里（struct files_struct），vfork 仍然通过 copy_files()→dup_fd() 复制它。这正是习题 24-2 的答案，官方解 vfork_fd_test.c 里父进程连关两次 stdout：第一次成功、第二次失败（EBADF）， 说明子进程那次 close 没影响到父进程。

Q5：既然 COW 让 fork 很便宜，vfork 还剩什么价值？

A：两个：① NOMMU 平台（没有 MMU 就没法 COW，fork 直接不可用）； ② 极端的 fork+exec 快路径（posix_spawn/clone3 的实现里省掉复制页表那一步）。 除此之外，原书的态度是避免使用。

Q6：为什么 vfork 子进程里调 sleep() 是"违规"的？

A：SUSv3 允许的只有「操作 fd」和「执行 _exit/exec」，其他函数调用一律 UB （条款 c）。原书放 sleep(3) 是为了让"父进程被挂起"这件事看得见 —— 是一个刻意为之的演示性违规。生产代码里不要在 vfork 子进程里调任何库函数。

Q7：vfork 之后父进程是"睡在"哪里？

A：睡在内核里的一个 completion 上：kernel/fork.c:2946 的 wait_for_vfork_done(p, &vfork)。子进程在 exec() 或退出时释放自己的 mm， mm_release()（kernel/fork.c:1645）发现 tsk->vfork_done 非空就 complete_vfork_done() 把父进程唤醒。

/* fork_whos_on_first.c

   Parent repeatedly creates a child, and then processes both race to be the
   first to print a message. (Each child terminates after printing its message.)
   The results of running this program give us an idea of which of the two
   processes--parent or child--is usually scheduled first after a fork().

   Whether the child or the parent is scheduled first after fork() has
   changed a number of times across different kernel versions.
*/
#include <sys/wait.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int numChildren, j;
    pid_t childPid;

    if (argc > 1 && strcmp(argv[1], "--help") == 0)
        usageErr("%s [num-children]\n", argv[0]);

    numChildren = (argc > 1) ? getInt(argv[1], GN_GT_0, "num-children") : 1;

    setbuf(stdout, NULL);               /* Make stdout unbuffered */

    for (j = 0; j < numChildren; j++) {
        switch (childPid = fork()) {
        case -1:
            errExit("fork");

        case 0:
            printf("%d child\n", j);
            _exit(EXIT_SUCCESS);

        default:
            printf("%d parent\n", j);
            wait(NULL);                 /* Wait for child to terminate */
            break;
        }
    }

    exit(EXIT_SUCCESS);
}

2. 逐条解读

① 输出为什么总是成对出现，而且是 0 0 1 1 2 2 …

这不是巧合，是父进程那个 wait(NULL) 造出来的结构。

j=0: 父 fork ──┬─> 父打印 "0 parent"  ──> 父 wait(NULL) ←──┐
               └─> 子打印 "0 child"  ──> _exit() ──────────┘
j=1: 父 fork（此时 j 已经 ++ 到 1）……

父进程必须等这一轮的子进程退出，才会进 for 的下一轮去 fork 下一个。 所以：

  • 每一对 j parent / j child 一定属于同一个 j；
  • 第 j+1 轮一定在第 j 轮父子都打完之后才开始。

这个设计是刻意的 —— 它把 1000 次实验变成串行的，每次实验互不干扰， 统计出来的百分比才有意义。否则 1000 个进程同时抢一个 stdout，输出会乱成一团。

② 那 8.4% 不是「均匀随机」，是成簇的

把 84 次 child 先的 j 按区间摊开：

j 区间 child 先的次数 区间长度 占比
0 – 599 25 600 4.2%
600 – 699 3 100 3.0%
700 – 799 0 100 0%
800 – 860 56 61 92%
861 – 999 0 139 0%

最刺眼的是 j ∈ [800, 860] 那 61 次里，有 56 次是子进程先打印； 而紧跟着的 j ∈ [861, 999] 共 139 次，一次都没有。

再看 j ∈ [800, 860] 里没有发生反转的 5 个位置，它们也是散的： 818、822、832、840、857。

这说明什么？

「父/子谁先跑」在这台机器上不是掷骰子。它在一段时间内会稳定地偏向一边， 而偏哪一边取决于那一刻宿主机在忙什么。

这正是原书那句话的实测版：

"Such bugs can be hard to find, as their occurrence depends on scheduling decisions that the kernel makes according to system load."（书 p.525）

⭐ 对写程序的人来说，这个"成簇"比"随机"更危险。 随机会让你在本地测试时立刻 发现问题；成簇意味着：你测试的那 10 分钟机器刚好不忙 → 全绿；上线后遇到一段忙的 时间窗 → 连续翻车。而且忙闲状态一过去，问题又消失了，根本抓不到现场。

③ setbuf(stdout, NULL) 不是可选项

把这一行删掉会怎样？——printf 的输出去全缓冲，父子两个进程各持一份缓冲区副本， 输出顺序会被缓冲彻底搅乱，而且 fork() 之后子进程缓冲区里可能残留父进程还没刷的 内容，导致同一行被打印两次（这个现象在 Ch25 的 Listing 25-2 里有专门演示）。

想测「谁先跑」，就必须让 printf 当场变成 write(2)。setbuf(stdout, NULL) 就是干 这个的。

④ 实测环境画像：nice = 19、2 个 CPU

probe24 / probe24_sched 两个探针给出的环境事实：

项 实测值
_SC_NPROCESSORS_ONLN 2
sched_getscheduler(0) 0（SCHED_OTHER）

nice = 19 是 nice 取值范围的最低一端（-20 到 19）。这解释了两件事：

  • 为什么 91.6% 而不是接近 100%：执行进程优先级被压到最低，父进程打完那行 printf 之前被宿主上其它进程抢走的概率显著上升；
  • 为什么会出现 800–860 那样的连续反转：那一段宿主机负载变了。

「每 3000 次错一次」和「父进程要做的事越多、错得越多」——把「依赖顺序」的代价算得 明明白白。

3.2 两派各自的论据

为什么要 child first（2.6 采纳它的理由） —— 书 p.527：

"...consider what happens with copy-on-write semantics when the child of a fork() performs an immediate exec(). In this case, as the parent carries on after the fork() to modify data and stack pages, the kernel duplicates the to-be-modified pages for the child. Since the child performs an exec() as soon as it is scheduled to run, this duplication is wasted. According to this argument, it is better to schedule the child first, so that by the time the parent is next scheduled, no page copying is required."

一句话：父进程 fork 之后继续跑会触发 COW 复制；而子进程反正马上 exec（把整个地址 空间扔掉）⇒ 这些复制白做了。让子进程先跑，父进程再动页面时子进程已经不管这块内存了。

为什么 2.6.32 又改回 parent first —— 书 p.527：

"The argument for switching back to "parent first after fork()" in Linux 2.6.32 was based on the observation that, after a fork(), the parent's state is already active in the CPU and its memory-management information is already cached in the hardware memory management unit's translation look-aside buffer (TLB). Therefore, running the parent first should result in better performance. This was informally verified by measuring the time required for kernel builds under the two behaviors."

一句话：父进程"热" —— 它在 CPU 上、页表项还在 TLB 里。子进程是"冷"的，切过去 等于 TLB/缓存全部重来。

原书最后自己给了个台阶（书 p.527）：

"In conclusion, it is worth noting that the performance differences between the two behaviors are rather small, and won't affect most applications."

所以别把「谁先跑」当成性能优化点。它是个语义陷阱，不是性能旋钮。

HFT / 嵌入式关联

  • 启动路径上的顺序依赖是实盘事故的高发点：策略进程 fork 出子进程去做 「预热 / 建连 / mmap 行情缓冲」，父进程紧接着用自己的 fd 或共享内存 —— 如果父进程 假设「子进程已经初始化好了」，这段代码在测试机上永远是对的（机器闲、parent 先、 子进程那点活还没开始）。唯一正确做法是握手：pipe / eventfd / 信号，见 §24.5。
  • nice = 19 的启示：本仓库的实测数字是在一个 nice = 19、2 核、共享宿主的沙箱里 采到的。任何「调度顺序」类的百分比都必须连同调度环境一起记录，否则换台机器就 无法复现，也无法解释。做延迟敏感系统时，这条同样适用于「本机 benchmark 数字」。
  • 实时调度（SCHED_FIFO / SCHED_RR）下不要用 fork 做热路径：新任务继承父进程的 调度策略与优先级，fork 本身就带页表复制。HFT 的通行做法是启动时一次性 fork/exec 好、之后只做进程间通信，或者干脆单进程多线程 + CPU 亲和。
  • 嵌入式 / 单核 ARM：单核上「谁先跑」只有两种可能，分布比多核更容易观察，但更容易 被误解成"确定行为"（因为单核上成簇效应更明显、更容易复现）。加进 BSP 的 sched_child_runs_first 在 v6.7 之后已经无效，老 BSP 打补丁时要核对内核版本。
  • 内核版本是运维风险：一个假设 「child first」（2.6 时代）或 「parent first」 （2.2 时代）的老程序，升级内核就可能静默改变行为。真实系统里这类 bug 的表现形式 往往是"某次内核升级后偶发失败"，而没人会想到是 24 年前的内核行为差异。
  • 这条经验可迁移到任何「不确定顺序」的场合：多核内存序、malloc 之后的地址、 select/epoll 返回的事件顺序 —— 共同点是依赖它 = 埋雷，正确做法都是显式同步。

代码自测（Q&A）

Q1：whos_first_1 里 0 parent 排在 0 child 前面，是不是说明父进程一定先跑？

A：不是。原书自己用的措辞是 "we might see"。这一次确实是父进程先打印， 但那是当时调度器的决定。同一份代码在 2.6.30 内核上有 99.98% 的概率反过来。

Q2：为什么输出总是成对、而且是 0 0 1 1 2 2 …？

A：父进程在 default 分支里有个 wait(NULL) ——它必须等这一轮的子进程退出， 才进入 for 的下一轮。所以 1000 次实验是串行的，j 相同的两行必然相邻。

Q3：那 8.4% 的 child 先为什么集中在 j ∈ [800, 860]？

A：因为「谁先跑」不是掷骰子，而是由外部负载和调度器的虚拟 deadline 决定的。 那 61 次里 56 次反转（92%），而它前后两段分别是 3% 和 0% —— 说明中间那段时间 宿主机状态变了。这正是原书说的 "depends on scheduling decisions that the kernel makes according to system load"。

Q4：把 setbuf(stdout, NULL) 删掉会怎样？

A：stdout 变全缓冲，父子各有一份缓冲区副本，输出顺序被缓冲搅乱，甚至出现同一行 打印两次（子进程继承了父进程缓冲区里未刷出的内容）。要观察「谁先跑」就必须让 printf 立刻落成 write(2)。

Q5：原书说改 /proc/sys/kernel/sched_child_runs_first 就能改行为，现在还行吗？

A：不行。实测沙箱（内核 7.0.0-1012-aws）上该文件 ENOENT；源码对照显示 v6.6 里它已经没有消费点（只剩定义 + 一个打印），v6.7 起 upstream 连定义都删了。 这句话只对 2.6.32 ~ 6.5 的内核有效。

Q6：v6.6 的 task_fork_fair() 只剩一行 place_entity(...)，那「谁先跑」到底谁定？

A：两步。① task_fork_fair()（fair.c:12410）给新任务算 vruntime / deadline， ENQUEUE_INITIAL 让它只拿半个时间片；② wake_up_new_task()（core.c:4848） 里 check_preempt_curr(rq, p, WF_FORK)（core.c:4874）→ check_preempt_wakeup() （fair.c:8055）按虚拟 deadline 决定要不要当场切过去。

Q7：为什么 whos_first_help 打印的是 ./output.s 而不是程序真名？

A：因为 CE 沙箱里执行产物的名字就是 output.s，argv[0] 跟着它走。 usageErr() 用的是 argv[0]，所以报文里出现的是 ./output.s。 这也顺便说明 usageErr() 的退出码是 1（exit(EXIT_FAILURE)）—— 实测 exit code = 1，与之一致。

Q8：代码里子进程用 _exit() 而不是 exit()，为什么？

A：exit() 会刷 stdio 缓冲区。由于 fork 让子进程持有一份父进程缓冲区的副本， 子进程 exit() 会把这份副本刷一遍 —— 结果是本该只打印一次的内容出现两次。 _exit() 直接走 exit_group 系统调用，不碰 stdio。

Avoiding Race Conditions by Synchronizing with Signals

本节讲什么

§24.4 的结论是「fork() 之后谁先跑靠不住」。那要保证顺序该怎么办？原书给的第一种 答案是信号（书 p.527）：

"If we need to guarantee a particular order, we must use some kind of synchronization technique. We describe several synchronization techniques in later chapters, including semaphores, file locks, and sending messages between processes using pipes. One other method, which we describe next, is to use signals."

信号同步的骨架只有三步：

① 在 fork() 之前，先把同步信号**屏蔽**掉
② fork()
③ 子进程做完事 → kill(父进程, 同步信号)
   父进程 → sigsuspend() 睡下等这个信号

⭐ 整个方案的正确性，全部压在「第 ① 步必须在 fork 之前」这一点上。这一节的重点 就是把这个「为什么」讲透。

/* fork_sig_sync.c

   Demonstrate how signals can be used to synchronize the actions
   of a parent and child process.
*/
#include <signal.h>
#include "curr_time.h"                  /* Declaration of currTime() */
#include "tlpi_hdr.h"

#define SYNC_SIG SIGUSR1                /* Synchronization signal */

static void             /* Signal handler - does nothing but return */
handler(int sig)
{
}

int
main(int argc, char *argv[])
{
    pid_t childPid;
    sigset_t blockMask, origMask, emptyMask;
    struct sigaction sa;

    setbuf(stdout, NULL);               /* Disable buffering of stdout */

    sigemptyset(&blockMask);
    sigaddset(&blockMask, SYNC_SIG);    /* Block signal */
    if (sigprocmask(SIG_BLOCK, &blockMask, &origMask) == -1)
        errExit("sigprocmask");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = handler;
    if (sigaction(SYNC_SIG, &sa, NULL) == -1)
        errExit("sigaction");

    switch (childPid = fork()) {
    case -1:
        errExit("fork");

    case 0: /* Child */

        /* Child does some required action here... */

        printf("[%s %ld] Child started - doing some work\n",
                currTime("%T"), (long) getpid());
        sleep(2);               /* Simulate time spent doing some work */

        /* And then signals parent that it's done */

        printf("[%s %ld] Child about to signal parent\n",
                currTime("%T"), (long) getpid());
        if (kill(getppid(), SYNC_SIG) == -1)
            errExit("kill");

        /* Now child can do other things... */

        _exit(EXIT_SUCCESS);

    default: /* Parent */

        /* Parent may do some work here, and then waits for child to
           complete the required action */

        printf("[%s %ld] Parent about to wait for signal\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        if (sigsuspend(&emptyMask) == -1 && errno != EINTR)
            errExit("sigsuspend");
        printf("[%s %ld] Parent got signal\n", currTime("%T"), (long) getpid());

        /* If required, return signal mask to its original state */

        if (sigprocmask(SIG_SETMASK, &origMask, NULL) == -1)
            errExit("sigprocmask");

        /* Parent carries on to do other things... */

        exit(EXIT_SUCCESS);
    }
}

注意代码顺序：sigprocmask(SIG_BLOCK) 和 sigaction() 都在 fork() 之前。 这不是风格问题，是必需（见第 3 节）。

逐条解读

① 后两行是被保证的，前两行是自由的。

行 谁先谁后有保证吗 依据
Parent about to wait for signal vs Child started - doing some work 没有 这两行都在 fork() 刚返回的位置；§24.4 已证顺序不定
Child about to signal parent vs Parent got signal 有 父进程 sigsuspend() 必须等到 kill() 的那一发才醒；子进程必须先 sleep(2) 再发

所以程序对与不对，只取决于后两行的顺序有没有成立 —— 而它成立。 这就是「同步」的含义：不消除不确定性，而是把不确定性赶出关键区。

⭐ 和原书的示例对照（书 p.528，书上的 shell session 日志）：

$ ./fork_sig_sync

[17:59:02 5172] Parent about to wait for signal
[17:59:04 5173] Child about to signal parent
[17:59:04 5172] Parent got signal

书上是 child 先，我们是 parent 先 —— 前两行反了。但两次都对。 而且这次「parent 先」正好与 §24.4 测到的 91.6% 一致。

② 时间戳给的证据：05:40:18 → 05:40:20，整整 2 秒，就是子进程那句 sleep(2)。 execTime = 2047 毫秒与之一致。父进程在这一段时间里什么都没干（睡在 sigsuspend 里）。

③ 两行的 pid：父 2、子 3 —— 和 Ch24 其它作业一样（容器 PID namespace，见 §24.1）。 getppid() 在子进程里拿到的是 2，就是父进程。

④ sigsuspend(&emptyMask) 这一句有三个动作，是原子的：

步骤 说明
1. 把信号掩码设为 emptyMask（空集 = 不屏蔽任何信号） 于是 SIGUSR1 从「屏蔽」变成「可递送」
2. 挂起进程，直到有信号被递送 睡在这里等
3. 信号处理完后，把掩码恢复成调用前的值 所以调用者不用自己恢复

⚠️ 这里传的是空集，意思是「任何信号都能唤醒我」。原书这么做是因为这个程序里没别的 信号；更严谨的写法是只解屏蔽 SYNC_SIG（把 origMask 拷一份、sigdelset(SYNC_SIG)）， 这样其它信号仍被屏蔽。真实程序里应该这么写。

⑤ SA_RESTART 在这段代码里其实用不上（sigsuspend 无论如何都返回 EINTR）， 它真正的价值是在后面被信号打断的 read()/write() 之类的调用上。原书把 sa_flags 设成 SA_RESTART 是通用习惯。

2. 为什么「在 fork 之前屏蔽」是唯一正确的写法

原书只用一句话点出来（书 p.528）：

"Note that we block the synchronization signal (SIGUSR1) before the fork() call in Listing 24-6. If the parent tried blocking the signal after the fork(), it would remain vulnerable to the very race condition we are trying to avoid."

把「如果反过来写」的时序摊开看，就知道它为什么是致命的：

❌ 错误写法：fork 之后才 sigprocmask(SIG_BLOCK)

  父进程                              子进程
  ─────────                           ─────────
  fork() ──────────────────────────>  fork() 返回
   │                                   │
   │ ←── 危险窗口 ──→                   sleep(2)……（这里还看不出问题）
   │                                   │
  sigprocmask(SIG_BLOCK)               │
   │                                   │
  sigsuspend()  ← 已经睡下，等信号      │
                                       │
                                      kill(父, SIGUSR1) ──> ✔ 正常唤醒

上面这段推演看起来还行 —— 因为子进程 sleep(2) 拖长了时间，父进程有充足的时间 完成 sigprocmask。问题出在「子进程不 sleep 就发信号」的情形：

❌ 错误写法（子进程不做耗时工作）

  父进程                              子进程
  ─────────                           ─────────
  fork() ──────────────────────────>  fork() 返回
   │                                   │
   │                                 kill(父, SIGUSR1)
   │                                   │
   │  ← 此刻父进程还【没有】屏蔽 SIGUSR1
   │  ← 信号立刻递送 → handler 空转一下 → 信号【用掉了】
   │                                   _exit(0)
   │
  sigprocmask(SIG_BLOCK)   ← 现在才屏蔽（已经晚了，信号已经消费掉）
   │
  sigsuspend()  ← ★ 永远等不到信号，【永久挂起】

⭐ 这个 bug 比「顺序错了」更恶劣 —— 它是死锁。 而且它只在子进程跑得足够快时 才出现，也就是说：

  • 平时（子进程稍慢）跑一百次都对；
  • 机器一空闲、子进程抢得先（§24.4 里那 8.4%）→ 父进程挂死；
  • 而且这个 bug 在 §24.4 那种「本机负载随时变」的环境里看起来像随机现象。

正确写法的时序（fork 之前就已经屏蔽）：

✔ 正确写法

  父进程                              子进程
  ─────────                           ─────────
  sigprocmask(SIG_BLOCK, SIGUSR1)
  sigaction(SIGUSR1, handler)
  fork() ──────────────────────────>  fork() 返回（掩码继承：SIGUSR1 也是屏蔽的）
   │                                   │
   │                                 kill(父, SIGUSR1)
   │                                   │
   │  ← 信号到达，但父进程【屏蔽着它】⇒ 停在 pending，不丢
   │                                   _exit(0)
   │
  sigsuspend(&emptyMask)  ← 原子地解屏蔽 → pending 里的 SIGUSR1 立刻递送 → 唤醒
   │
  ✔ 无论子进程多快都不会丢

关键差别：信号在到达时就已经被拦住（pending 起来），而不是靠运气赶在它到达之前 把门关上。

⭐ 用 §24.2 的实测支撑这条推理

「掩码会被子进程继承」这件事不是猜的。§24.2 的延伸 demo c24_sigmask_inherit 实测过：

父进程 pid=2 ppid=1
  掩码 中 SIGUSR1 = 1   （1 = 屏蔽）
  pending 中 SIGUSR1 = 1   （1 = 有未递送信号）
子进程 pid=3 ppid=2
  掩码 中 SIGUSR1 = 1   （继承来的）
  pending 中 SIGUSR1 = 0   （不继承）
父进程 fork 之后：pending 中 SIGUSR1 = 1（自己的还留着）

三行结论：

项 fork 之后 机制
信号掩码 继承 kernel/fork.c:1091 *dst = *src;（arch_dup_task_struct() 把整个 task_struct 拷一份，blocked 跟着走）
pending 信号集 不继承（清零） kernel/fork.c:2391 init_sigpending(&p->pending);
信号处置（handler 表） 继承 kernel/fork.c:2495 copy_sighand(clone_flags, p)

因为掩码继承，子进程天然也是屏蔽着 SIGUSR1 的。这对本程序没有影响（子进程不给自己 发信号），但如果你打算在子进程里用同一个信号做别的事，记得先 sigsuspend/sigprocmask 把它解开 —— 这正是原书那句括号里的话（书 p.528）：

"(In this program, we assume that the state of the signal mask in the child is irrelevant; if necessary, we can unblock SIGUSR1 in the child after the fork().)"

3. 反过来用：让子进程等父进程 / 双向握手

原书（书 p.528）说这个模式是对称的：

"In this program, we assume that it is the parent that must wait on the child to carry out some action. The signal-related calls in the parent and child can be swapped if the child must wait on the parent. It is even possible for both parent and child to signal each other multiple times in order to coordinate their actions, although, in practice, such coordination is more likely to be done using semaphores, file locks, or message passing."

这就是习题 24-5 的题面。本仓库自写了一份双向握手的解（原书没有这一节的代码）：

code/ex24_5_fork_sig_sync2.c

/* ex24_5_fork_sig_sync2.c

   ⚠️ 本仓库自写 —— 原书习题 24-5 **没有官方解答文件**
      （官方只给了习题 24-2 的解：procexec/vfork_fd_test.c）。

   习题 24-5：如果**子进程也要等父进程**完成某个动作，Listing 24-6
              （fork_sig_sync.c）需要怎么改？

   答：一个信号不够了，要**两个**信号做双向握手：
         子 → 父 用 SIGUSR1（"我干完了"）
         父 → 子 用 SIGUSR2（"我干完了"）
       并且**两个信号都要在 fork() 之前屏蔽**。原因是 Listing 24-6 里
       已经写明的那条：如果先 fork 再屏蔽，那么"信号已经发出"与"我开始屏蔽"
       之间存在窗口，对方那一枪可能在你 sigsuspend 之前就打完了 ——
       这正是要避免的那个竞态。

   本程序的输出**顺序是确定的**（靠信号保证），这跟 Listing 24-5 的
   fork_whos_on_first 形成对照：那里没有同步，先后完全看调度器。

   编译（需要 curr_time.c 提供 currTime()，见 code/README.md）：
     gcc -O0 -Wall -Wextra -o ex24_5_fork_sig_sync2 \
         ex24_5_fork_sig_sync2.c curr_time.c
*/

#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#include "curr_time.h"          /* currTime() */

#define CHILD_READY SIGUSR1     /* 子 → 父 */
#define PARENT_DONE SIGUSR2     /* 父 → 子 */

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

static void handler(int sig)    /* 什么都不做，只为让 sigsuspend 醒过来 */
{
    (void) sig;
}

static void waitFor(sigset_t *emptyMask)
{
    if (sigsuspend(emptyMask) == -1 && errno != EINTR)
        die("sigsuspend");
}

int main(void)
{
    pid_t childPid;
    sigset_t blockMask, emptyMask;
    struct sigaction sa;

    setvbuf(stdout, NULL, _IONBF, 0);

    /* ---------- 屏蔽**两个**信号：必须在 fork() 之前 ---------- */
    sigemptyset(&blockMask);
    sigaddset(&blockMask, CHILD_READY);
    sigaddset(&blockMask, PARENT_DONE);
    if (sigprocmask(SIG_BLOCK, &blockMask, NULL) == -1)
        die("sigprocmask(SIG_BLOCK)");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = handler;
    if (sigaction(CHILD_READY, &sa, NULL) == -1)
        die("sigaction(SIGUSR1)");
    if (sigaction(PARENT_DONE, &sa, NULL) == -1)
        die("sigaction(SIGUSR2)");

    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:   /* ---------- 子进程 ---------- */
        printf("[%s %ld] Child  started - working\n",
                currTime("%T"), (long) getpid());
        sleep(2);                                   /* 模拟干活 */

        printf("[%s %ld] Child  -> SIGUSR1 to parent\n",
                currTime("%T"), (long) getpid());
        if (kill(getppid(), CHILD_READY) == -1)
            die("kill(SIGUSR1)");

        /* 反过来等父进程（习题 24-5 新增的部分）*/
        printf("[%s %ld] Child  waiting for parent\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);

        printf("[%s %ld] Child  got SIGUSR2 -> done\n",
                currTime("%T"), (long) getpid());
        _exit(EXIT_SUCCESS);

    default:  /* ---------- 父进程 ---------- */
        printf("[%s %ld] Parent waiting for child\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);                        /* 等 SIGUSR1 */

        printf("[%s %ld] Parent got SIGUSR1 - working\n",
                currTime("%T"), (long) getpid());
        sleep(1);                                   /* 模拟干活 */

        printf("[%s %ld] Parent -> SIGUSR2 to child\n",
                currTime("%T"), (long) getpid());
        if (kill(childPid, PARENT_DONE) == -1)
            die("kill(SIGUSR2)");

        if (wait(NULL) == -1)
            die("wait");
        printf("[%s %ld] Parent done\n", currTime("%T"), (long) getpid());
        exit(EXIT_SUCCESS);
    }
}

双向握手要多想一步：两个方向各需要一个信号，而且必须在 fork() 之前把两个都屏蔽。 本仓库的实现用：

信号 方向 用于
SIGUSR1 子 → 父 「我干完了，该你了」
SIGUSR2 父 → 子 「我干完了，收工」

用两个不同的信号而不是一个信号互相发，是因为一个信号无法表达「这是你发给我的还是 我发给你的」；用一个信号做双向握手会分不清方向，很容易写出自己唤醒自己的逻辑。

4. 信号同步的局限（为什么后面还要学管道/信号量）

原书在 p.528 那句带了前半句很重要：

"Although, in practice, such coordination is more likely to be done using semaphores, file locks, or message passing."

信号能同步，但代价不小：

局限 说明
一次只能传「一个 bit」 信号不带数据。要说「我算出来 42」还得另找地方放
标准信号会合并 连续两次 SIGUSR1 到达而还没被处理，只会 pending 一次 —— 计数会丢
需要处理信号语义 掩码、EINTR、SA_RESTART、异步信号安全（handler 里只能调 write() 之类的少数函数）
与多线程交互复杂 信号可以投递到进程里的任意一个线程（Ch33 详述）
不适合高频通信 每次 kill() 都是一次系统调用 + 一次调度器唤醒

⭐ 原书还提到一种工程习惯（书 p.528，引 Stevens）：

"[Stevens & Rago, 2005] suggests encapsulating such synchronization steps (block signal, send signal, catch signal) into a standard set of functions for process synchronization. The advantage of such encapsulation is that we then later replace the use of signals by another IPC mechanism, if desired."

「封装成 sync 函数对」这个建议很实用：把「屏蔽 + 发 + 等」包成 syncInit() / syncSignal() / syncWait()，之后就只是换个实现，调用点一个字不用改。

常见坑

# 坑 说明
1 在 fork() 之后屏蔽同步信号 原书 p.528 明确点名的错误。子进程跑得快时信号会被 handler 空转掉，父进程永久挂起
2 fork() 之后才 sigaction() 装 handler 若信号在装 handler 之前就解屏蔽递送，SIGUSR1 的默认动作是终止进程 → 父进程直接被杀
3 用 pause() 代替 sigsuspend() pause() 不是原子的：信号可能在 sigprocmask/pause 之间到达并丢失。这是经典竞态，必须用 sigsuspend
4 忘了检查 errno != EINTR sigsuspend 正常被信号唤醒时也返回 -1 并设 errno = EINTR。直接 if (sigsuspend(...) == -1) errExit() 会把正常路径当错误
5 在子进程里忘了掩码是继承来的 子进程同样屏蔽着 SYNC_SIG；要在子进程里用这个信号，得先解屏蔽
6 用标准信号做「计数」 标准信号会合并：发两次只 pending 一次。要计数得用 实时信号（SIGRTMIN 系列，Ch22 有详述）
7 handler 里调 printf handler 必须异步信号安全。printf 会用锁，不安全；write() 才行
8 双向握手共用一个信号 分不清方向，容易自己唤醒自己。一个方向一个信号（实测解用 SIGUSR1 + SIGUSR2）
9 把信号同步当高性能方案 每次握手 = kill() 系统调用 + 唤醒调度，比管道/eventfd/futex 都重

HFT / 嵌入式关联

  • 「同步点必须在 fork 之前建立」是通用的启动纪律：任何「父进程先准备好、子进程再 接手」的启动序列（HFT 里的预热 / 建连 / mmap 共享行情缓冲 / 绑核），都必须 在 fork 前把同步原语建好（pipe / eventfd / 信号掩码）。反过来写就是 §24.5 那个「父进程永久挂起」的 bug —— 而它在低负载测试机上永远不出现。
  • 信号 vs eventfd/pipe 的取舍：信号的优势是不占 fd、开销小；劣势是不带 数据、会合并、与线程交互复杂。HFT 里更常用 eventfd 或 futex（Ch30 的 futex() + Ch53 的 POSIX 信号量），信号多用于「进程被杀 / 配置重载」这类低频事件。
  • SIGUSR1/SIGUSR2 的工程约定：很多低延迟系统用 SIGUSR1 做「停止交易」、 SIGUSR2 做「强制平仓」，配合 signalfd（Ch22）把信号变成 fd 事件塞进 epoll —— 这样就统一到一套事件循环里，不会打乱 epoll 的等待。signalfd 是「信号」与 「fd 事件」的桥，值得记住。
  • 嵌入式 / 守护进程：daemon 化的经典流程里，父进程 fork 之后必须等子进程 发信号再退出（BSD 的「双 fork + 父等子」），否则调用者拿不到「服务已就绪」的 保证。那套 setsid() + kill(getppid(), SIGUSR1) 的写法，机制就是本节这一套。
  • 单核 MCU / RTOS 里的对应物：信号 ≈ RTOS 的「事件标志 / 任务通知」。同样有 「一次只传一个 bit、会合并」的问题，同样要求在创建任务之前把同步对象建好 （否则中断可能在对象初始化完成前就发通知）。这是同一类竞态在不同抽象层的复现。
  • 信号是「异步事件」，永远要按异步来处理：handler 里只做「记个标志 / 写个 eventfd」，真正的工作放到主循环 —— 这就是 signalfd / self-pipe trick 的来由，也是 Ch63（alternative I/O）要讲的东西。

Q1：为什么后两行（Child about to signal parent / Parent got signal）的顺序一定有保证， 前两行没有？

A：后两行的顺序是 sigsuspend() 造出来的 —— 父进程必须等到子进程 kill() 那一发才醒。 前两行都在 fork() 刚返回的位置，谁先跑取决于调度器（§24.4 实测：parent 先 91.6%）。 同步的作用是把不确定性赶出关键区，不是消灭它。

Q2：如果在 fork() 之后才 sigprocmask(SIG_BLOCK)，最坏会怎样？

A：子进程若在父进程完成屏蔽之前就 kill()，信号会立刻递送并被空的 handler 消费掉； 父进程随后才屏蔽、再 sigsuspend() —— 此时信号已经用掉了，父进程永久挂起。 这个 bug 只在子进程抢得够快时出现，所以看起来像随机故障。

Q3：sigsuspend() 为什么不能用 pause() 代替？

A：pause() 和「解屏蔽」是两步，中间有窗口：信号可能在这两步之间到达并丢失。 sigsuspend() 把「改掩码 + 挂起」做成一个原子操作，堵住了这个窗口。 原书 Ch22 专门讲这个经典竞态。

Q4：sigsuspend() 正常被唤醒时返回什么？

A：返回 -1，errno = EINTR。所以代码里必须写成 if (sigsuspend(&emptyMask) == -1 && errno != EINTR) errExit(...) —— 直接判 == -1 就报错会把正常路径当成错误。

Q5：为什么 sigaction() 也要放在 fork() 之前？

A：因为信号可能在任何时刻到达。若 handler 还没装好而信号已经被解屏蔽递送， SIGUSR1 的默认动作是终止进程 → 父进程直接被杀。 放在 fork 之前，子进程也顺带继承了 handler（虽然它用不到）。

Q6：子进程需要自己去解屏蔽 SIGUSR1 吗？

A：本程序不需要（子进程不用这个信号）。但掩码是继承来的，子进程同样屏蔽着 SIGUSR1， 这一点必须知道。原书 p.528 括号里就提了：需要的话，在 fork() 之后在子进程里解屏蔽。

Q7：双向握手为什么用两个信号？

A：一个信号无法区分方向。用 SIGUSR1（子→父）+ SIGUSR2（父→子）各管一个方向， 逻辑才不会自己唤醒自己。实现时两个信号都必须在 fork() 之前屏蔽。

Q8：这个方案能不能用来传数据？

A：不能。信号只传「发生了」这一个 bit，而且标准信号会合并（连发两次只 pending 一次）。 要传数据用管道 / 共享内存 / eventfd，信号只当「通知」。这也正是原书说「实践中更常用 信号量、文件锁、消息传递」的原因。

本章值得记住的 8 条

  1. fork() 复制的是「进程」，不是「程序」。子进程从 fork() 返回处继续执行，fork() 在父进程里返回子进程 PID、在子进程里返回 0 —— 这是全网唯一的分叉判据。
  2. fork() 之后内存是「复制」的，fd 是「共享」的。内存走 COW（写才复制），fd 走 get_file() 加引用计数（同一个 open file description，偏移量也共享）。
  3. 信号掩码继承、pending 清零、handler 继承。这三条在写同步代码时决定成败。
  4. vfork() 不复制地址空间，父进程被挂起，直到子进程 exec() 或 _exit()。 SUSv3 明令：在 vfork 子进程里改数据 / return / 调别的函数都是未定义行为。
  5. fork() 之后谁先跑不确定，而且不是均匀随机 —— 实测 j ∈ [800, 860] 有 92% 是 child 先，紧邻的 j ∈ [861, 999] 是 0%。依赖顺序 = 竞态 = 偶发故障。
  6. 原书点的 sched_child_runs_first 开关今天已经没了：v6.6 里已成空壳（零消费点）， v6.7 起连定义都删除，实测沙箱里 /proc/sys/kernel/sched_child_runs_first 是 ENOENT。 ⇒ /proc 路径是最容易腐烂的一类知识，见到先 ls。
  7. 同步信号必须在 fork() 之前屏蔽。反过来写，子进程跑得快时会把信号消费在 handler 里，父进程 sigsuspend() 永久挂起。而且这个 bug 只在低负载机器上不出现。
  8. WCOREDUMP 不是布尔值。glibc 里它是 status & 0x80（只能取 0 或 128）。 实测 WCOREDUMP = 128 只说明「内核走完了 coredump 流程」，不等于磁盘上有 core 文件 —— 实测 ./core 和 /core 都不存在。

本章复习自测（Q&A）

Q1：fork() 之后父子进程共享的三样东西是什么？

A：① 文件描述符表（更准确说是同一批 open file description，get_file() 加引用计数 ⇒ 共享文件偏移和状态标志）；② 父进程已有的信号处置（handler）；③ 信号掩码。 不共享的是：PID、pending 信号集、以及（写时复制的）内存。

Q2：t_fork 里子进程打印 idata=333 istack=666，父进程打印 111 / 222，说明什么？

A：说明 fork() 之后父子各有自己的一份 glob / loc / 动态分配的 dyn / 栈上的 istack。子进程改自己的不影响父进程 —— 这是 COW 的正常表现。 与 §24.3 的 t_vfork（istack=666 出现在父进程）正好对照。

Q3：为什么说「vfork() 用错会把父进程搞崩」？

A：因为子进程跑在父进程的地址空间和栈上。① 从函数里 return 会把父进程的栈拆掉 （典型 SIGSEGV）；② 调库函数会破坏共享的 libc 状态；③ exit() 会刷 stdio（父子同一份缓冲区）。 SUSv3 明确把这三条列为未定义行为。

Q4：fork() 之后父/子谁先跑，能不能靠内核参数控制？

A：今天不能。 原书 p.526 说的 /proc/sys/kernel/sched_child_runs_first 实测已经 ENOENT；源码对照显示 v6.6 里它已是空壳、v6.7 起 upstream 删除了定义。 现在由 wake_up_new_task() → check_preempt_curr(..., WF_FORK) 按 EEVDF 的虚拟 deadline 决定。

Q5：为什么同步信号非要在 fork() 之前屏蔽？

A：因为要在信号可能到达之前就把门关上。若 fork 之后才屏蔽，子进程可能在这个窗口里 把信号发过来 —— 信号立刻被空的 handler 消费掉，父进程随后 sigsuspend() 就永远等不到。 而且因为掩码是继承的，在 fork 前屏蔽还顺便让子进程也处于一致的屏蔽状态。

Q6：WCOREDUMP(status) 返回 128 是正常的吗？

A：正常。glibc 里它是位掩码 status & 0x80（bits/waitstatus.h），所以只能取 0 或 128。 status = 134 = 0x80 | 6 表示「子进程被 6 号信号（SIGABRT）杀死，且内核走完了 coredump 流程」。但它不代表磁盘上有 core 文件 —— 实测沙箱里 ./core 和 /core 都不存在。

Q7：本章 7 个官方文件里，哪一个属于别的章？

A：procexec/fork_stdio_buf.c。它在官方源里，但归 Ch25 的 Listing 25-2 （讲 fork 之后 stdio 缓冲区的复制问题），不属于 Ch24。本章的 7 个文件是 t_fork / fork_file_sharing / footprint / t_vfork / fork_whos_on_first / fork_sig_sync / vfork_fd_test（最后一个是习题 24-2 的解）。

24-1：fork(); fork(); fork(); 之后有几个新进程？

答案

新产生 7 个进程，加上原来那个一共 8 个。

为什么是 2³ 而不是 3？因为每一次 fork() 都被「当时已经存在的所有进程」各执行一遍：

第几次 fork() 执行它的进程数 之后总进程数
开始 1 1
第 1 次 1 2
第 2 次 2 4
第 3 次 4 8

新产生的进程数 = 8 − 1 = 7。

⭐ 这就是「fork 炸弹」的数学形式：fork() 的次数是线性增长，进程数却是指数增长。

实测（ex24_1_fork_count，本仓库自写解）

程序用一根在任何 fork() 之前就建好的管道把 7 个新进程的 pid/ppid 收集回来 （管道要在 fork 之前建，否则后 fork 出来的进程看不到它 —— 见 code/ex24_1_fork_count.c 里的注释）：

原始进程 pid=2
--- 开始 fork(); fork(); fork(); ---
新进程 pid=4      ppid=2
新进程 pid=3      ppid=2
新进程 pid=5      ppid=2
新进程 pid=6      ppid=4
新进程 pid=7      ppid=1
新进程 pid=9      ppid=7
新进程 pid=8      ppid=1
--- 新进程行数 = 7 ---
--- 进程总数   = 8 ---
（2^3 = 8 个进程并存；新产生 8 - 1 = 7 个。行的顺序不定，
  因为 fork 之后父子谁先跑由调度器决定 —— 见 §24.4）

execTime = 31 毫秒，exit code = 0，diagnostics = 7。

逐条解读

① 「新进程行数 = 7」与推导一致。 三个 fork() 之后 8 个进程，其中 7 个是新的。

② pid 的出现顺序是乱的：4, 3, 5, 6, 7, 9, 8。这就是 §24.4 讲的 「fork 之后谁先跑不确定」的又一个现场 —— 连往管道里写一行这么小的动作，顺序都不保证。

③ ppid=1 出现了两次（pid=7 和 pid=8）。这不是 bug，而是孤儿进程被收养：

  • 这两个进程在打印时，它们的父进程已经退出了；
  • 内核在父进程退出时把子进程的父指针改指向 init（PID 1）—— 实测沙箱里 init 在 容器 PID namespace 里的编号就是 1；
  • 于是它们读到 getppid() == 1。

这正好是 Ch26（Monitoring Child Processes） 的引子：父进程必须 wait() 子进程， 否则子进程会变僵尸；而如果父进程自己先死，子进程就变孤儿，由 init 兜底。

④ ppid 链本身也能看出 fork 的树形结构：pid=4 的 ppid 是 2（原始进程）， pid=6 的 ppid 是 4（它是 pid=4 那个进程 fork 出来的）。 8 个进程构成一棵三层的二叉树（每个进程最多 fork 出 2 个孩子）。

24-3：怎么在某一刻拿到 core dump，同时让进程继续跑？

思路

fork() 一个子进程，让子进程去死。

  • 子进程的地址空间是父进程那一刻的副本（COW）⇒ 子进程崩溃产生的 core 里， 就是父进程当时的完整内存映像；
  • 父进程 wait() 收尸之后继续执行 —— 这正是题目要求的 "while letting the process continue execution"。

不能用「直接给自己发 SIGSEGV」也不行的原因：那样进程就死了，谈不上「继续执行」。 所以「复制一份来死」是唯一干净的做法。

位 值 含义

③ WCOREDUMP 不是布尔值，是位掩码。 glibc 里它长这样 （glibc 2.39，bits/waitstatus.h）：

#define __WCOREDUMP(status) ((status) & __WCOREFLAG)   /* 第 53 行 */

所以它的取值只能是 0 或 128。实测拿到 128 是正常的 —— 别以为哪里出错了。

原因有两个，都在实测输出里：

原因 实测证据

core_pattern 是管道（以 \| 开头） 第 ① 段：\|/usr/share/apport/apport -p%p -s%s ...

⑤ 为什么 WCOREDUMP 位还是被置上了？ 因为 core_pattern 是管道模式， 而管道模式下内核根本不看 RLIMIT_CORE（fs/coredump.c:613）：

    if (ispipe) {
        ...
        if (cprm.limit == 1) {
            /* See umh_pipe_setup() which sets RLIMIT_CORE = 1. ...
             * Normally core limits are irrelevant to pipes, since
             * we're not writing to the file system, but we use
             * cprm.limit of 1 here as a special value, this is a
             * consistent way to catch recursive crashes.
             */
            ...
            goto fail_unlock;
        }
        cprm.limit = RLIM_INFINITY;

—— cprm.limit = RLIM_INFINITY 这一行（fs/coredump.c:613）把 RLIMIT_CORE = 0 抹掉了。 于是内核认为 coredump 流程走完了，在收尾时置位（fs/coredump.c:438）：

    if (core_dumped && !__fatal_signal_pending(current))
        current->signal->group_exit_code |= 0x80;

这就是那个 0x80 位的来源。 至于数据实际写去了哪儿（apport 在容器里能不能跑、 写不写得进 /var/crash），内核不管 —— 所以「置位」和「磁盘上有文件」是两件事。

        if (cprm.limit < binfmt->min_coredump)
            goto fail_unlock;

⑦ 工程结论：要在容器里真的拿到 core 文件，得同时满足 （a）RLIMIT_CORE > 0（且 hard limit 允许）（b）core_pattern 指向一个容器内可写、 可执行的落盘路径（而不是宿主上的 apport）。这两条在多数容器默认配置下都不满足 —— 所以「core dump 拿不到」在容器里是常态，不是程序写错了。

⭐ 顺带一个实用替代方案：不追求 core 文件，而是用 gdb -p <pid> 的 gcore 命令 在另一个进程里抓快照 —— 那才是生产环境里更常用的手法（进程完全不受影响）。

#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#include "curr_time.h"          /* currTime() */

#define CHILD_READY SIGUSR1     /* 子 → 父 */
#define PARENT_DONE SIGUSR2     /* 父 → 子 */

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

static void handler(int sig)    /* 什么都不做，只为让 sigsuspend 醒过来 */
{
    (void) sig;
}

static void waitFor(sigset_t *emptyMask)
{
    if (sigsuspend(emptyMask) == -1 && errno != EINTR)
        die("sigsuspend");
}

int main(void)
{
    pid_t childPid;
    sigset_t blockMask, emptyMask;
    struct sigaction sa;

    setvbuf(stdout, NULL, _IONBF, 0);

    /* ---------- 屏蔽**两个**信号：必须在 fork() 之前 ---------- */
    sigemptyset(&blockMask);
    sigaddset(&blockMask, CHILD_READY);
    sigaddset(&blockMask, PARENT_DONE);
    if (sigprocmask(SIG_BLOCK, &blockMask, NULL) == -1)
        die("sigprocmask(SIG_BLOCK)");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = handler;
    if (sigaction(CHILD_READY, &sa, NULL) == -1)
        die("sigaction(SIGUSR1)");
    if (sigaction(PARENT_DONE, &sa, NULL) == -1)
        die("sigaction(SIGUSR2)");

    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:   /* ---------- 子进程 ---------- */
        printf("[%s %ld] Child  started - working\n",
                currTime("%T"), (long) getpid());

        printf("[%s %ld] Child  -> SIGUSR1 to parent\n",
                currTime("%T"), (long) getpid());
        if (kill(getppid(), CHILD_READY) == -1)
            die("kill(SIGUSR1)");

        /* 反过来等父进程（习题 24-5 新增的部分）*/
        printf("[%s %ld] Child  waiting for parent\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);

        printf("[%s %ld] Child  got SIGUSR2 -> done\n",
                currTime("%T"), (long) getpid());
        _exit(EXIT_SUCCESS);

    default:  /* ---------- 父进程 ---------- */
        printf("[%s %ld] Parent waiting for child\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);                        /* 等 SIGUSR1 */

        printf("[%s %ld] Parent got SIGUSR1 - working\n",
                currTime("%T"), (long) getpid());
        sleep(1);                                   /* 模拟干活 */

        printf("[%s %ld] Parent -> SIGUSR2 to child\n",
                currTime("%T"), (long) getpid());
        if (kill(childPid, PARENT_DONE) == -1)
            die("kill(SIGUSR2)");

        if (wait(NULL) == -1)
            die("wait");
        printf("[%s %ld] Parent done\n", currTime("%T"), (long) getpid());
        exit(EXIT_SUCCESS);
    }
}

核心改动三处：

# 改动 为什么
1 用两个信号：SIGUSR1（子→父）、SIGUSR2（父→子） 一个信号分不清方向，容易自己唤醒自己
2 两个信号都要在 fork() 之前屏蔽 与 §24.5 同一个理由：必须赶在信号可能到达之前把门关上
3 父子的 sigsuspend() / kill() 各写两遍 握手是两轮：子做完 → 通知父 → 父做完 → 通知子

逐条解读

① 8 行输出，顺序是确定的（从第 3 行开始）：

子做完 → SIGUSR1 → 父开始
父做完 → SIGUSR2 → 子结束

每一个「箭头」都由一次 kill() + 一次 sigsuspend() 完成 —— 谁都不可能越过对方先走。

② 前两行的顺序仍然自由（Parent waiting for child 在 Child started - working 前面， 但这一次恰好父进程先跑）—— 和 §24.5 一样：同步消除的是关键区里的不确定性， 不是全部不确定性。

③ 时间戳显示两段等待：31 → 33（子进程干活 2 秒），33 → 34（父进程干活 1 秒）。 execTime = 3018 毫秒 ≈ 3 秒，与两段等待之和一致。

④ 为什么不用「一个信号来回发」？ 因为接收方无法区分「这个信号是我在等的那一发， 还是我刚发出去绕回来的」。用两个信号，语义就一对一了： SIGUSR1 永远只表示「子进程就绪」，SIGUSR2 永远只表示「父进程就绪」。

⭐ 原书在 p.528 提过这类封装的工程价值（引 Stevens）：

"[Stevens & Rago, 2005] suggests encapsulating such synchronization steps (block signal, send signal, catch signal) into a standard set of functions for process synchronization. The advantage of such encapsulation is that we then later replace the use of signals by another IPC mechanism, if desired."

本仓库这个自写解就是照这个思路写的：把「屏蔽 + 发 + 等」包成宏/函数， 将来换成 eventfd 或管道，调用点不用改。

代码自测（Q&A）

Q1：fork(); fork(); fork(); 为什么是 8 个进程而不是 4 个？

A：因为每次 fork() 都会被当时所有已存在的进程执行一遍：1 → 2 → 4 → 8。 新产生的进程数是 8 − 1 = 7。

Q2：ex24_1_fork_count 的输出里 ppid=1 是怎么来的？

A：那两个进程在打印时父进程已经退出了。父进程退出时内核把子进程的父指针改指向 init（容器 PID namespace 里的 PID 1）—— 这叫孤儿进程被收养。 另外 pid=6 的 ppid=4 说明 8 个进程构成一棵三层的 fork 树。

Q3：vfork_fd_test 只输出了一行错误，怎么就能证明 fd 表是独立的？

A：程序里父进程连关两次 stdout：第一次期望成功、第二次期望失败。 如果 fd 表共享，子进程那次 close 会让父进程的第一次 close 也失败 → 会多打一行。 实测只有一行 ⇒ 父进程第一次 close 成功了 ⇒ 子进程的 close 没影响父进程。

Q4：WCOREDUMP(status) 返回 128，是 bug 吗？

A：不是。glibc 里它是 status & 0x80（bits/waitstatus.h），只能取 0 或 128。 它由内核在 fs/coredump.c:438 用 group_exit_code |= 0x80 置上。

Q5：既然 WCOREDUMP 被置位了，为什么磁盘上没有 core 文件？

A：两个原因叠加：① RLIMIT_CORE = 0/0（且 hard limit 是 0，非 root 提不动， 实测 setrlimit 报 EPERM）；② core_pattern 是管道（|/usr/share/apport/apport ...）， 管道模式下内核不看 RLIMIT_CORE（fs/coredump.c:613 直接 cprm.limit = RLIM_INFINITY）， 所以流程走完、位置上了，但数据交给 apport 之后落到哪里、有没有落地，内核不管。

Q6：为什么双向握手非要用两个信号？

A：一个信号分不清方向 —— 接收方无法区分「我等的信号」和「我刚发出去又绕回来」。 用 SIGUSR1（子→父）+ SIGUSR2（父→子），每个信号只有一个含义。 两个信号都必须在 fork() 之前屏蔽，否则会重演 §24.5 那个「父进程永久挂起」的坑。

Q7：24-4 要求换别的 UNIX，本仓库为什么改成对照内核版本？

A：CE 沙箱只提供 Linux，跑不了别的 UNIX。而原书那句话本身（「2.6.32 起又改回 parent 先」） 本身就跨越了内核版本 —— 用 upstream 源码做跨版本对照是能验证它的唯一途径， 而且比「在别人的机器上跑一次」更可复核（每一行都能给出文件和行号）。
