代码示例

#include <stdio.h>
#include <dlfcn.h>
#include <stdlib.h>
#include <string.h>

/* Ch41 共享库 — dlopen/dlsym/dlclose 动态加载。
 * 演示运行时加载 libm 并调用 sqrt。
 * 编译: gcc -o ch41_demo ch41_demo.c -ldl */

int main(void) {
    /* 动态加载数学库 */
    void *handle = dlopen("libm.so.6", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "dlopen failed: %s\n", dlerror());
        return 1;
    }

    /* 查找 sqrt 函数符号 */
    dlerror();  /* 清除错误 */
    double (*sqrt_fn)(double) = dlsym(handle, "sqrt");
    const char *err = dlerror();
    if (err) {
        fprintf(stderr, "dlsym failed: %s\n", err);
        dlclose(handle);
        return 1;
    }

    /* 调用动态加载的函数 */
    double val = 144.0;
    double result = sqrt_fn(val);
    printf("sqrt(%.0f) = %.4f\n", val, result);

    /* 查找 pow 函数 */
    double (*pow_fn)(double, double) = dlsym(handle, "pow");
    if (pow_fn) {
        printf("pow(2.0, 10.0) = %.4f\n", pow_fn(2.0, 10.0));
    }

    /* 列出链接的共享库 (通过 /proc/self/maps) */
    printf("\nLinked libraries (see /proc/self/maps):\n");
    FILE *fp = fopen("/proc/self/maps", "r");
    if (fp) {
        char line[512];
        while (fgets(line, sizeof(line), fp)) {
            if (strstr(line, ".so") && !strstr(line, "["))
                printf("  %s", line);
        }
        fclose(fp);
    }

    dlclose(handle);
    return 0;
}

41.2

Static Libraries

本章：TLPI 第 41 章

本节讲什么

静态库是目标文件（.o）的归档集合（.a）。链接时，链接器从库中提取所需目标文件，将其代码直接复制到可执行文件中。运行时不依赖库文件。

要点

创建静态库流程

源文件 → 编译 → 目标文件 → 归档 → 静态库
.c          .o              ar      .a

# 1. 编译为目标文件
gcc -c foo.c bar.c baz.c    # 生成 foo.o bar.o baz.o

# 2. 归档为静态库
ar rcs libmylib.a foo.o bar.o baz.o
#    r = 替换已有成员
#    c = 创建库
#    s = 写入索引（等同于 ranlib）

ar 命令

选项 功能
r 插入/替换成员
c 静默创建
s 创建索引
t 列出成员
x 提取成员
d 删除成员

静态库符号表

libmylib.a
├── 符号索引（symdef）  ← ar s 创建，加速链接
├── foo.o              ← 目标文件
├── bar.o
└── baz.o

链接器通过索引快速查找符号所在的目标文件，只提取引用到的 .o。

链接静态库

# 方式1：直接在命令行指定
gcc -o app app.o libmylib.a

# 方式2：使用 -l（需 -L 指定路径）
gcc -o app app.o -L. -lmylib

静态库 vs 共享库

特性 静态库 (.a) 共享库 (.so)
代码复制 是，每个程序各一份 否，内存中一份
可执行文件大小 大 小
运行时依赖 无 有
升级 需重新链接 替换 .so 即可
内存占用 每进程一份代码 多进程共享
启动速度 快 稍慢（需动态链接）

HFT / 嵌入式关联

  • HFT 核心策略库可静态链接，消除运行时依赖和启动延迟
  • 嵌入式交叉编译常使用静态库减少目标系统依赖
  • 安全敏感代码静态链接避免库替换攻击

代码示例

#!/bin/bash
# 完整静态库创建和使用示例

# 1. 源文件
cat > greet.c << 'EOF'
#include <stdio.h>
void greet(const char *name) {
    printf("Hello, %s!\n", name);
}
EOF

cat > farewell.c << 'EOF'
#include <stdio.h>
void farewell(const char *name) {
    printf("Goodbye, %s!\n", name);
}
EOF

# 2. 编译 + 归档
gcc -c greet.c farewell.c
ar rcs libgreet.a greet.o farewell.o

# 3. 查看内容
ar t libgreet.a

# 4. 链接使用
cat > main.c << 'EOF'
void greet(const char *);
void farewell(const char *);
int main() {
    greet("HFT");
    farewell("HFT");
    return 0;
}
EOF
gcc -o app main.c libgreet.a
./app

代码自测

ar 命令的 s 选项为什么重要？

s 选项创建符号索引表（archive symbol table），让链接器快速查找符号所在的目标文件，避免线性扫描所有 .o。没有索引时链接器需要逐个扫描目标文件，大型库链接速度显著变慢。现代 ar 默认创建索引，但显式 s 确保兼容性。ranlib 命令也可单独创建索引。

41.3

Overview of Shared Libraries

本章：TLPI 第 41 章

本节讲什么

共享库（.so）在运行时动态加载，多个进程共享同一份代码。本节介绍共享库的工作原理：地址无关代码（PIC）、动态链接器、符号解析和共享库的优势。

要点

共享库 vs 静态库

特性 共享库 (.so) 静态库 (.a)
链接时机 运行时 编译时
代码共享 多进程共享一份 每程序各一份
内存占用 低 高
磁盘占用 低（一份） 高（每程序含副本）
升级 替换 .so 即生效 需重新链接
启动开销 需动态链接 无
版本管理 需 SONAME 不涉及

地址无关代码（PIC）

PIC 让共享库代码段可在任意虚拟地址加载，无需重定位：

代码段 数据段 技术
可共享（只读） 每进程独立副本 GOT/PLL
通过 GOT 间接访问全局变量 GOT 记录实际地址 延迟绑定

动态链接过程

1. 加载可执行文件 → 发现 PT_INTERP (ld-linux.so)
2. ld-linux.so 加载 → 读取 DT_NEEDED 递归加载依赖库
3. 符号解析 → GOT/PLT 绑定（可延迟到首次调用）
4. 运行 → 程序入口 _start → main()

创建共享库

# -fPIC: 生成地址无关代码
gcc -fPIC -c foo.c bar.c

# -shared: 创建共享库
gcc -shared -o libmylib.so foo.o bar.o

# -Wl,-soname: 设置 SONAME
gcc -shared -Wl,-soname,libmylib.so.1 -o libmylib.so.1.0.0 foo.o bar.o

共享库命名约定

文件名 用途 示例
libfoo.so 链接器搜索名（开发用） -lfoo
libfoo.so.1 SONAME（运行时加载名） 记录在 ELF DT_SONAME
libfoo.so.1.0.0 real name（实际文件） 包含完整版本号

HFT / 嵌入式关联

  • 策略引擎作为 .so 动态加载，支持热更新无需重启交易进程
  • 多个交易进程共享同一份行情解析库代码段，节省内存
  • 嵌入式设备 OTA 升级只需替换 .so 文件

代码示例

#!/bin/bash
# 完整共享库创建和使用

# 1. 创建源文件
cat > greet.c << 'EOF'
#include <stdio.h>
void greet(const char *name) {
    printf("Hello from .so, %s!\n", name);
}
EOF

# 2. 编译为 PIC 目标文件
gcc -fPIC -c greet.c

# 3. 创建共享库（带 SONAME）
gcc -shared -Wl,-soname,libgreet.so.1 -o libgreet.so.1.0 greet.o

# 4. 创建符号链接
ln -sf libgreet.so.1.0 libgreet.so.1
ln -sf libgreet.so.1   libgreet.so

# 5. 链接使用
cat > main.c << 'EOF'
void greet(const char *);
int main() {
    greet("HFT");
    return 0;
}
EOF
gcc -o app main.c -L. -lgreet
export LD_LIBRARY_PATH=.
./app

# 6. 查看依赖
ldd app

代码自测

为什么共享库需要 -fPIC（地址无关代码）？

共享库代码段被多个进程映射到不同的虚拟地址。如果代码段中包含绝对地址引用，每个进程都需要不同的重定位，导致代码段无法共享（每个进程各一份 COW 副本）。PIC 通过 GOT（全局偏移表）间接引用，使代码段完全只读可共享，只有数据段（GOT 本身）需要每进程独立。这大幅减少了共享库的内存占用。

41.7

Installing Shared Libraries

本章：TLPI 第 41 章

本节讲什么

共享库的安装涉及文件放置、符号链接创建、soname 记录和动态链接器缓存更新。

要点

安装步骤

1. 复制 real name → /lib 或 /usr/lib
2. 创建 SONAME 符号链接 → libfoo.so.1 → libfoo.so.1.0.0
3. 创建链接器名符号链接 → libfoo.so → libfoo.so.1
4. 运行 ldconfig 更新缓存

三种名称的关系

libfoo.so        → 开发时链接器搜索（-lfoo）
  └── libfoo.so.1 → 运行时加载名（ELF DT_NEEDED 中记录）

代码自测

ldconfig 的作用是什么？不执行会怎样？

ldconfig 扫描标准库目录，创建 SONAME 到 real name 的符号链接，并生成 /etc/ld.so.cache 缓存文件。缓存加速运行时动态链接器查找库的速度。如果不执行 ldconfig，新安装的库可能无法被找到（除非用 LD_LIBRARY_PATH），因为旧缓存中没有新库的记录。ldconfig 还会自动创建/修复 SONAME 符号链接。

41.8

Compatible versus Incompatible Libraries

本章：TLPI 第 41 章

本节讲什么

共享库的兼容性规则：何时需要递增版本号，何时可以安全替换。区分 ABI 兼容与不兼容的变更类型。

要点

兼容性分级

级别 定义 处理
源码兼容 重新编译即可工作 更新次版本号
ABI 兼容 二进制不需重编译 可直接替换 .so
不兼容 二进制接口改变 递增主版本号

ABI 不兼容的变更

变更类型 示例 兼容性
删除导出符号 删除 foo() 不兼容
添加必需参数 foo(int) → foo(int, int) 不兼容
改变字段大小 struct 增加/移除字段 不兼容
改变字段偏移 调整 struct 字段顺序 不兼容
改变枚举值 enum {A=0, B=1} → {A=0, B=2} 不兼容
改变函数返回类型 int foo() → long foo() 不兼容
改变 ABI 调用约定 cdecl → stdcall 不兼容

兼容的变更

变更类型 条件
添加新导出符号 不影响现有使用者
增加函数参数（带默认值） C 无默认值，不适用
修改函数内部实现 不改签名
增加 struct 末尾字段 使用者不直接分配该 struct

版本号规则

libfoo.so.MAJOR.MINOR.PATCH
        │      │      │
        │      │      └─ 补丁：bug 修复，完全兼容
        │      └──── 次版本：新增功能，向后兼容
        └───────── 主版本：ABI 破坏性变更
变更类型 主版本 SONAME 旧程序
bug 修复 不变 不变 正常工作
新增接口 不变 不变 正常工作
ABI 破坏 +1 libfoo.so.N+1 需重新编译

符号版本控制（GNU 扩展）

libfoo.so.1
├── VERSION_1.0 {  ← 初始版本
│     foo;
│     bar;
│ }
├── VERSION_1.1 {  ← 新增接口
│     baz;
│ } VERSION_1.0;   ← 依赖 1.0
└── VERSION_2.0 {  ← 不兼容版本
│     foo;  ← 签名改变
│ }

HFT / 嵌入式关联

  • 行情解析库 ABI 变更需通知所有策略程序重新编译
  • 使用符号版本控制同时支持新旧接口，平滑迁移
  • 嵌入式设备固件升级需验证库版本兼容性

代码自测

struct 末尾增加字段是否 ABI 兼容？

不一定。如果调用者直接在栈上或堆上分配该 struct，增加字段会导致分配大小不足，写入新字段时越界。但如果 struct 只由库内部分配（如 struct foo *foo_create()），则使用者不关心大小，是兼容的。应配合 opaque pointer 模式或 *_sizeof() 函数来安全扩展。

41.9

Upgrading Shared Libraries

本章：TLPI 第 41 章

本节讲什么

共享库升级的两种方式：兼容升级（替换 .so 文件）和不兼容升级（共存多个版本）。如何安全地在生产环境中升级。

要点

兼容升级流程

旧: libfoo.so.1.0.0 ← libfoo.so.1
新: libfoo.so.1.1.0 ← libfoo.so.1 (更新符号链接)
  1. 安装新 real name 文件
  2. 更新 SONAME 符号链接指向新文件
  3. 运行 ldconfig
  4. 正在运行的进程不受影响（旧 inode 仍存活）
  5. 新进程启动自动使用新版本

不兼容升级流程

旧: libfoo.so.1.0.0 ← libfoo.so.1   (保留)
新: libfoo.so.2.0.0 ← libfoo.so.2   (新增)
  1. 安装新主版本文件
  2. 创建新 SONAME 符号链接
  3. 旧 SONAME 保留（兼容旧程序）
  4. 链接器名 libfoo.so 指向新版本
  5. 新程序编译时用新版本，旧程序运行时用旧版本

升级安全性

场景 处理
文件正在被使用 Linux 下可直接替换（旧 inode 存活）
正在执行 新进程用新版，旧进程不变
即时生效 需重启进程
回滚 保留旧版本文件，更新符号链接

热升级模式

# 1. 安装新版本（不删除旧版本）
install -m 755 libfoo.so.1.1.0 /usr/local/lib/
ldconfig  # SONAME 指向新版本

# 2. 重启使用该库的服务
systemctl restart hft-engine

# 3. 确认无误后清理旧版本（可选）
rm /usr/local/lib/libfoo.so.1.0.0

进程级热加载（dlopen）

/* 运行时加载新版本，不重启进程 */
void *handle = dlopen("libfoo.so.1.1", RTLD_NOW);
void (*new_func)(void) = dlsym(handle, "new_api");

HFT / 嵌入式关联

  • 交易系统零停机升级：dlopen 加载新策略库，切换后卸载旧库
  • 行情解析库兼容升级：安装新 .so，重启子进程
  • 嵌入式 OTA：新固件验证通过后替换库，失败回滚

代码示例

#!/bin/bash
# 兼容升级示例

OLD_VER=1.0.0
NEW_VER=1.1.0
SONAME=libhft.so.1

echo "=== 升级前 ==="
ls -la /usr/local/lib/libhft.so*

# 安装新版本
install -m 755 libhft.so.${NEW_VER} /usr/local/lib/
ldconfig

echo "=== 升级后 ==="
ls -la /usr/local/lib/libhft.so*

# 验证符号链接指向新版本
readlink /usr/local/lib/${SONAME}

# 检查正在使用旧版本的进程
echo "=== 使用旧版本的进程 ==="
lsof | grep libhft.so.${OLD_VER}

代码自测

升级共享库时正在运行的进程会受影响吗？

不会。Linux 允许替换正在使用的文件：旧 inode 保持存活直到所有引用关闭，新进程打开文件时看到新版本。运行中的进程代码段仍映射在旧 inode 上，不受影响。但新启动的进程会使用新版本。要让运行中的进程使用新版本，需要重启进程或用 dlopen 动态加载。

41.11

Finding Shared Libraries at Run Time

本章：TLPI 第 41 章

本节讲什么

动态链接器在运行时如何查找共享库：搜索路径顺序、LD_LIBRARY_PATH、ld.so.conf 配置、DT_RPATH/DT_RUNPATH、以及 LD_PRELOAD 预加载机制。

要点

搜索路径顺序

1. DT_RPATH (deprecated, 链接时 -Wl,-rpath)
2. LD_LIBRARY_PATH (环境变量)
3. DT_RUNPATH (现代, -Wl,--enable-new-dtags,-rpath)
4. ld.so.cache (/etc/ld.so.cache, 来自 ld.so.conf)
5. 默认路径 (/lib, /usr/lib, /lib64, /usr/lib64)
来源 设置时机 作用域 优先级
DT_RPATH 编译链接 编译时固定 1 (最高)
LD_LIBRARY_PATH 运行时 当前进程 2
DT_RUNPATH 编译链接 编译时固定 3
ld.so.cache ldconfig 系统级 4
默认路径 内置 系统级 5 (最低)

LD_LIBRARY_PATH

# 临时指定库路径
LD_LIBRARY_PATH=/opt/mylib ./app

# 多路径
LD_LIBRARY_PATH=/opt/lib1:/opt/lib2 ./app
  • 仅影响动态链接器搜索，不影响 ld 链接器
  • 安全限制：setuid 程序忽略此环境变量
  • 生产环境不推荐使用（用 RPATH 或 ld.so.conf 替代）

RPATH / RUNPATH

# 编译时嵌入搜索路径
gcc -o app app.o -L. -lfoo -Wl,-rpath,/opt/mylib

# 使用 RUNPATH (推荐)
gcc -o app app.o -L. -lfoo -Wl,--enable-new-dtags,-rpath,/opt/mylib

# 相对 RPATH ($ORIGIN 表示可执行文件所在目录)
gcc -o app app.o -L. -lfoo -Wl,-rpath,'$ORIGIN/../lib'
标签 优先级 覆盖 LD_LIBRARY_PATH 推荐
DT_RPATH 高于 LD_LIBRARY_PATH 是 否（已废弃）
DT_RUNPATH 低于 LD_LIBRARY_PATH 否 是

LD_PRELOAD

# 预加载库，覆盖标准库函数
LD_PRELOAD=./mymalloc.so ./app
  • 在所有其他库之前加载
  • 可用于函数插桩（interpose）
  • setuid 程序忽略（安全限制）

查看和调试

# 查看依赖库
ldd ./app

# 查看 RPATH/RUNPATH
readelf -d ./app | grep -E 'RPATH|RUNPATH'

# 调试动态链接器
LD_DEBUG=libs ./app 2>&1 | head -50
LD_DEBUG=files ./app
LD_DEBUG=bindings ./app | grep foo

HFT / 嵌入式关联

  • 使用 $ORIGIN RPATH 实现可移植部署（不依赖系统路径）
  • LD_PRELOAD 注入自定义 malloc 实现低延迟内存分配
  • LD_DEBUG 调试交易系统库加载问题

代码示例

代码自测

RPATH 和 RUNPATH 有什么区别？为什么要引入 RUNPATH？

RPATH 的优先级高于 LD_LIBRARY_PATH，意味着编译时嵌入的路径会覆盖用户通过环境变量设置的路径，带来安全风险（用户无法覆盖库路径）。RUNPATH 优先级低于 LD_LIBRARY_PATH，允许用户覆盖。因此现代链接器推荐使用 RUNPATH（--enable-new-dtags）。另一个区别：RPATH 是递归的（库的 RPATH 也用于查找其依赖），RUNPATH 是非递归的（只影响直接依赖的查找）。

41.13

Using a Static Library Instead of a Shared Library

本章：TLPI 第 41 章

本节讲什么

何时选择静态库而非共享库，以及静态链接的特殊场景：全静态链接（-static）、部分静态链接（-Bstatic）、glibc 的静态链接警告。

要点

全静态 vs 动态链接

特性 全静态 (-static) 动态链接
可执行文件大小 大（含所有库代码） 小
运行时依赖 无 需要共享库存在
启动速度 快（无需动态链接） 稍慢
库升级 需重新编译 替换 .so 即可
NSS 服务 不工作 正常
内存占用 每进程各一份 共享
兼容性 好（不依赖系统库版本） 需匹配库版本

部分静态链接

# 仅 libfoo 静态链接，其余动态
gcc -o app app.o -L. -Wl,-Bstatic -lfoo -Wl,-Bdynamic -lm

# 或指定直接使用 .a 文件
gcc -o app app.o /path/to/libfoo.a -lm

glibc 静态链接警告

warning: Using 'dlopen' in statically linked applications ...
warning: Using 'getaddrinfo' in statically linked applications ...
warning: Using 'getpwuid' in statically linked applications ...

glibc 的 NSS（Name Service Switch）机制依赖 dlopen 动态加载 /lib/libnss_*.so。全静态链接时这些功能不可用，getpwuid/gethostbyname 等函数会失败或退化。

选择指南

场景 推荐 原因
容器/嵌入式 全静态 无依赖，自包含
系统工具 全静态 救援模式下可用
库代码需更新 共享 替换 .so 即可
HFT 核心路径 静态 减少动态链接开销
HFT 辅助工具 共享 便于升级
多程序共享大库 共享 节省内存

静态链接的安全优势

  • 无 LD_PRELOAD 注入风险
  • 无 LD_LIBRARY_PATH 劫持
  • 无库路径篡改
  • 无动态链接器漏洞

HFT / 嵌入式关联

  • HFT 核心交易引擎全静态链接，消除启动延迟和库依赖
  • 交易策略插件保持动态链接（需热更新）
  • 嵌入式设备固件全静态，减少 OTA 包大小
  • 安全敏感组件静态链接，防止库替换攻击

代码示例

#!/bin/bash
# 静态链接示例

# 1. 全静态链接
gcc -static -o app_static app.c -lm
# 验证无动态依赖
ldd app_static  # "not a dynamic executable"

# 2. 检查文件类型
file app_static
# app_static: ELF 64-bit LSB executable, x86-64, statically linked

# 3. 部分静态链接
gcc -o app_mixed app.c \
    -L./lib -Wl,-Bstatic -lstrategy -Wl,-Bdynamic -lm -lpthread

# 4. 体积对比
echo "Static:  $(stat -c%s app_static) bytes"
echo "Dynamic: $(stat -c%s app_dynamic) bytes"

代码自测

全静态链接 glibc 程序中 getpwuid() 为什么可能失败？

getpwuid() 通过 NSS（Name Service Switch）机制查找用户信息。glibc 的 NSS 实现使用 dlopen 动态加载 /lib/libnss_files.so（或 libnss_ldap.so 等）。全静态链接的程序无法调用 dlopen（没有动态链接器），因此 NSS 功能不工作，getpwuid 无法获取 /etc/passwd 中的信息，只能返回硬编码的默认值。

代码自测

共享库的 SONAME 有什么作用？

SONAME 记录在 ELF 文件的 DT_SONAME 字段中。当链接器链接共享库时，会将 SONAME（而非文件名）记录在可执行文件的 DT_NEEDED 字段中。运行时，动态链接器根据 DT_NEEDED 中的 SONAME 查找库文件，而非原始文件名。这使得 libfoo.so.1.0.0 和 libfoo.so.1.1.0 都可以被 SONAME 为 libfoo.so.1 的程序使用，实现兼容升级。

练习 1：创建共享库

题目：从以下源文件创建共享库 libstr.so.1.0.0，设置正确的 SONAME，并安装到系统目录。

// str_reverse.c
void str_reverse(char *s, int len) { /* ... */ }
// str_upper.c
void str_upper(char *s, int len) { /* ... */ }
参考答案 
# 1. 编译为 PIC 目标文件
gcc -fPIC -c str_reverse.c str_upper.c

# 2. 创建共享库（设置 SONAME）
gcc -shared -Wl,-soname,libstr.so.1 -o libstr.so.1.0.0 \
    str_reverse.o str_upper.o

# 3. 安装到系统目录
sudo install -m 755 libstr.so.1.0.0 /usr/local/lib/

# 4. 创建符号链接
sudo ln -sf libstr.so.1.0.0 /usr/local/lib/libstr.so.1
sudo ln -sf libstr.so.1     /usr/local/lib/libstr.so

# 5. 更新缓存
sudo ldconfig

# 6. 验证
ldconfig -p | grep libstr

练习 2：版本兼容性

题目：以下对共享库的变更哪些是 ABI 兼容的？

(a) 增加 void new_func(void) 导出函数 (b) 将 int foo(int) 改为 int foo(int, int) (c) 在 struct 末尾增加字段 (d) 修复函数内部 bug (e) 删除导出函数 bar()

参考答案
  • (a) 兼容 — 新增导出符号不影响已有接口
  • (b) 不兼容 — 改变函数参数数量，调用方传参方式改变
  • (c) 可能不兼容 — 如果调用者直接分配该 struct，大小不足
  • (d) 兼容 — 内部实现改变不影响 ABI
  • (e) 不兼容 — 删除导出符号，使用该函数的程序无法链接

练习 3：运行时查找

题目：一个可执行文件使用 -Wl,-rpath,/opt/app/lib 编译，但运行时 libfoo.so 在 /opt/app/lib 中不存在。解释动态链接器的搜索顺序。

参考答案

如果使用 --enable-new-dtags（生成 RUNPATH 而非 RPATH）： 1. LD_LIBRARY_PATH（如果设置） 2. DT_RUNPATH (/opt/app/lib) — 此处找不到 3. ld.so.cache — 搜索 /etc/ld.so.conf 配置的路径 4. 默认路径 /lib, /usr/lib

如果使用旧 RPATH： 1. DT_RPATH (/opt/app/lib) — 此处找不到 2. LD_LIBRARY_PATH 3. ld.so.cache 4. 默认路径

最终结果取决于哪个路径中存在 libfoo.so。
