易错清单

# 易错点 正确认识
1 以为 exit() 的 status 是 32 位的 只有低 8 位走到父进程；内核在 syscall 入口就 (code & 0xff) << 8（kernel/exit.c:991）
2 以为 WEXITSTATUS() 里做了截断 截断在子进程调 exit() 那一刻；WEXITSTATUS 只是把高字节取回来
3 用 exit(130) / exit(139) 表示「被中断/越界」 与「被信号 2 / 11 杀死」在 shell 里无法区分；退出码用 0–127
4 以为 atexit 能兜住 SIGKILL SIGKILL 连 exit() 都不走，一条 handler 都不会跑
5 在 exit handler 里调 _exit() 想「提前收场」 剩下的 handler 和 stdio flush 一起取消，连前面 printf 的都丢
6 在 exit handler 里调 exit() SUSv3 判 UB；Linux 上「照常跑」，换个系统可能无限递归到栈溢出
7 以为 handler 里注册的新 handler 会排到队尾 会插到剩余列表的队首（实测顺序 C / B / D / A）
8 抄书上的 _SC_ATEXIT_MAX 书上印的是 2,147,482,647，实测是 2,147,483,647（= INT_MAX），原书勘误
9 fork 出来的子进程用 exit() 父进程的 stdio 缓冲被复制 ⇒ 输出重复、handler 跑两遍；子进程用 _exit()
10 在 CE 上想复现「终端 vs 重定向」两种输出 沙箱 stdout 是 socket（S_ISSOCK=1）⇒ 只能看到全缓冲那一半
11 以为进程死了 System V 共享内存段 / 信号量名就没了 内核只 detach / close，对象是持久化的，要显式 IPC_RMID / *_unlink
12 靠 fcntl() 记录锁做跨进程互斥 锁随进程消失（不是随 fd）；用 F_OFD_SETLK 或 flock()
13 main 不写 return C89 下是 UB（实测退出码 42，来自返回寄存器残留值）；C99 起等价 exit(0)
14 #define _BSD_SOURCE 直接用 glibc 2.39 报弃用警告（include/features.h:196）；新代码用 _DEFAULT_SOURCE
15 以为 atexit 能「注销」 没有 API；用全局 flag 让 handler 自己跳过

背诵卡

# 要点
1 exit() = ①exit handler（逆序）+ ②flush stdio + ③_exit()
2 _exit() / 被信号杀：①②都不做；内核清理照做
3 退出码只有低 8 位；status = (code & 0xff) << 8，截断在 syscall 入口
4 exit(-1) ⇒ status = 65280、WEXITSTATUS = 255
5 退出码用 0–127；128–255 留给「被信号 n 杀死」（$? = 128 + n）
6 SIGKILL 一定绕过全部用户态清理（这是「先发 SIGTERM」的根本理由）
7 handler LIFO；handler 里再注册 ⇒ 插到剩余列表队首
8 handler 不返回 ⇒ 剩余 handler 与 flush 一起取消
9 fork() 复制 handler 注册副本；exec() 清空全部注册
10 _SC_ATEXIT_MAX = INT_MAX（书上印错了 1000）
11 fork() 复制用户态缓冲 ⇒ printf 重复；write 直进内核 ⇒ 不重复
12 一个程序里只让一个进程（通常是父进程）用 exit() 收场
13 内核只 detach / close（shm、信号量名、消息队列名都是持久对象）
14 内核保证清理资源，但不保证落盘

25.1

Terminating a Process: `_exit()` and `exit()` 终止的两条路

本章：TLPI 第 25 章 — Process Termination 源码核验：man7 官方 Ch25 分发文件 2 个（procexec/ 下 exit_handlers.c / fork_stdio_buf.c）· 原书 §25 正文（书页 531–539，全 64 章里最短的一章）· 官方 Makefile.inc 编译参数 · Linux v6.6（kernel/exit.c）· glibc 2.39（stdlib/exit.c / stdlib/stdlib.h）· CE 实测（gcc 13.3.0 / x86-64 / Ubuntu 24.04，沙箱内核 7.0.0-1012-aws） 本章所有实测数字来自冻结日志 tlpi-ch25-final.txt - 上一节：本章首页 - 下一节：25.2 Details of Process Termination

本节讲什么

原书 §25.1 只做一件事：把「一个进程怎么结束」拆成两条入口、三种写法、一条 8 位通道。

要讲清的问题 答案在哪
进程有几种死法？ 正常（主动调 _exit）· 异常（被信号杀）
exit() 和 _exit() 差别在哪？ exit() 多做两件事：跑 exit handler、flush stdio
退出码为什么只有 8 位？ 内核只把 status & 0xff 左移 8 位存进 exit_code
return n 和 exit(n) 等价吗？ 几乎等价（crt0 拿 main 的返回值去调 exit），但有例外
掉出 main 末尾呢？ C89 未定义；C99 起等价于 exit(0)

⚠️ 原书 §25.1 没有任何 Listing（本章仅有的两个 Listing 分别在 §25.3 和 §25.4）。 本仓库为此自写了两个程序（c25_exit_three_steps.c、c25_fall_off_main.c）， 把「三步顺序」与「掉出末尾」变成可运行的真实输出。

1. 两种终止方式

方式 触发者 会跑 exit handler？ 会 flush stdio？ 内核里留下的东西
正常终止 进程自己调 _exit() / _Exit() / exit()，或 main 返回 只有走 exit() 才跑 只有走 exit() 才刷 8 位退出码
异常终止 收到致命信号（默认动作是终止的那些） ❌ 一律不跑 ❌ 一律不刷 信号号 + 是否 core

⭐ 记住这一条就够用了：exit handler 和 stdio flush 都是 exit() 这个库函数提供的， 不是「进程终止」这件事自带的。走 _exit() 或被杀，这两件事都不会发生。

由此推出一条原书反复强调的实践准则： SIGKILL 永远无法被拦截——它连 exit() 都不走，所以任何「用 atexit 做清理来兜底」的设计， 在 SIGKILL 面前都是空的。这也是「尽量先发 SIGTERM」的又一个理由 （SIGTERM 可以被处理函数接住，在函数里从容地 exit()）。

2. _exit(status)：只有低 8 位到得了父进程手里

原书原文（§25.1）：

Although declared as an int, only the bottom 8 bits of status are actually made available to the parent.

也就是说，_exit() 的形参是 int（32 位），但通道只有 8 位宽。

  • _exit(0) 或 EXIT_SUCCESS ⇒ 成功。实测沙箱里 EXIT_SUCCESS = 0、EXIT_FAILURE = 1。
  • 为什么是 8 位而不是 32 位？见本文第 6 节的源码坐标——截断发生在内核的 syscall 入口， 一行 do_exit((error_code&0xff)<<8) 就把这件事钉死了。

⚠️ 原书在 §25.1 里给了一个很实际的警告：如果程序用一个大于 128 的值当退出码， shell 脚本会读不懂。因为按惯例 $? 在被信号杀死时等于 128 + 信号号：

看起来的写法 shell 里 $? 能不能和「被信号杀」区分
_exit(1) 1 ✅ 能
_exit(127) 127 ✅ 能
_exit(130) 130 ❌ 和 SIGINT(2) 杀死 完全一样
_exit(139) 139 ❌ 和 SIGSEGV(11) 杀死 完全一样

约定：退出码就用 0–127，把 128–255 留给内核报信号。

3. exit()：三步，顺序不能变

原书 §25.1 用三个 bullet 写清了 exit() 做的事（顺序即语义）：

步 动作 谁实现
① 按注册的逆序（LIFO）调用所有 exit handler 用户态（atexit / on_exit 注册的那些）
② flush 所有 stdio 流的缓冲 用户态（glibc 的 _IO_cleanup）
③ 调用 _exit(status) 进内核

⭐ 「①在②之前」这条顺序很关键：它意味着在 exit handler 里 printf 出去的字符串， 还能被第②步的 flush 送出去；反过来，如果 handler 里调了 _exit，那第②步就被跳过， handler 里 printf 的东西会一起丢掉（第 4 节的实测会把这半句也钉死）。

4. 把「三步顺序」变成可观察量（本仓库自写）

读文档只能知道「①在②之前」，没法建立直觉。做法是把两条通路混着用：

通路 数据先到哪 什么时候能在 stdout 看到
write(2) 直接进内核 立刻
printf(3) 先进用户态 FILE 缓冲 等 flush（正常退出时就是第②步）

于是「谁先出现」就等于「内核缓冲 vs 用户态缓冲」，而 flush 的那一刻会被精确定位到某个 write 之后。

code/c25_exit_three_steps.c

/* c25_exit_three_steps.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.1 用三行 bullet 说清了 exit() 依次做三件事：
     ① 按注册的【逆序】调用 exit handler（atexit / on_exit 注册的）
     ② flush stdio 流缓冲
     ③ 调用 _exit(status)

   但「① 在 ② 之前」这句话没法靠读文档建立直觉，得让顺序变成**可观察量**。
   做法是把两条通路混着用：
     · write(2)  → 直接进内核缓冲，**立刻**出现在 stdout
     · printf(3) → 先进用户态 FILE 缓冲，要等 flush 才出现
   于是「谁先出现」就等价于「内核缓冲 vs 用户态缓冲」，而 flush 的时刻
   会被精确定位到某个 write 之后。

   在 CE 上跑：stdout 不是终端（是 socket）⇒ glibc 对 stdout 用**全缓冲**，
   所以下面这个顺序是**确定**的。如果在真终端上跑，stdout 是行缓冲，
   printf 会被换行符逐个推出去，顺序就完全不同 —— 这本身就是 §25.4 的内容。

   编译: gcc -O0 -Wall -Wextra -o c25_exit_three_steps c25_exit_three_steps.c
   运行: ./c25_exit_three_steps
*/
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

/* write() 的包装：只写固定字符串 */
static void
w(const char *s)
{
    write(STDOUT_FILENO, s, strlen(s));
}

/* 先跑的 handler（后注册）：只 write + printf，不 flush */
static void
handlerB(void)
{
    w("W2  来自 hB 的 write()      —— 立刻出来\n");
    printf("M2  来自 hB 的 printf()    —— 先进用户态缓冲\n");
}

/* 后跑的 handler（先注册）：中间插一次 fflush，把「此刻缓冲里有什么」钉死 */
static void
handlerA(void)
{
    w("W3  来自 hA 的 write()      —— 立刻出来\n");
    fflush(stdout);          /* ← 关键：把 M1、M2 推出去，证明它们一直躺在缓冲里 */
    printf("M3  来自 hA 的 printf()    —— 直到 exit() 第 ② 步才出来\n");
    w("W4  来自 hA 的 write()      —— 在它自己的 printf 之后！\n");
}

int
main(void)
{
    w("=== 图例：W* 走 write(2)（立刻可见）；M* 走 printf(3)（先进用户态缓冲）===\n");
    w("=== 观察点：M1/M2 什么时候出现，就等于 hA 那次 fflush 的位置 ===\n\n");

    printf("M1  来自 main 的 printf()  —— 先进用户态缓冲\n");
    w("W1  来自 main 的 write()    —— 立刻出来\n");

    if (atexit(handlerA) != 0 || atexit(handlerB) != 0) {
        w("atexit 注册失败\n");
        return EXIT_FAILURE;
    }
    w("\n--- 下面调用 exit(0)：handler 先跑（LIFO：hB 再 hA），最后才 flush ---\n");

    exit(0);   /* 不返回 */
}

逐条解读

⭐ 这一节同时钉死两件事：handler 在 flush 之前、handler 之间是 LIFO。 第③步（_exit）在这份输出里看不出来——它只是让进程真的消失，没有任何输出。

⚠️ CE 沙箱的前提：stdout 是 socket（S_ISSOCK=1，isatty(1)=0）， 所以 glibc 对 stdout 用全缓冲，上面这个顺序是确定的。 如果在真终端上跑，stdout 变行缓冲，printf 会被换行符逐个推出去，顺序完全不同—— 那正是 §25.4 要讲的内容。

5. return n 与「掉出 main 末尾」

原书 §25.1 末尾这一段经常被略过，但它解释了一个真实的诡异现象。

return n; 在 main 里几乎等于 exit(n)：crt0 里的 __libc_start_main 拿到 main 的返回值后， 就是拿它去调用 exit()。所以 return 也会走 exit handler、也会 flush。

⚠️ 但「几乎」二字后面有一个真实例外：如果程序在 exit 的过程中还要访问 main 的局部变量， 那 return 就是未定义行为。原书举的例子是 setvbuf() 的参数指向了 main 里的局部数组—— 因为 main 返回后那些局部变量的生命周期就结束了。

掉出末尾：C89 与 C99 的分水岭

标准 从 main 掉出末尾（既不 return 也不 exit）
C89 未定义行为——原书点名 gcc 默认就是这种情形：退出状态取自「栈或某个 CPU 寄存器里的某个随机值」
C99 起 等价于 exit(0)

本仓库用一个程序把这两半都跑出来：

code/c25_fall_off_main.c

/* c25_fall_off_main.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.1 末尾提到一件容易忽略的事：从 main() **掉出末尾**（既没 return
   也没调 exit()）时，调用 main() 的那段运行时（crt0 里的 __libc_start_main）
   会接着调 exit()，但**用什么参数**取决于 C 标准和编译选项：

     · C89：行为**未定义**，程序可能带任意状态值终止。原书点名 gcc 默认就是
       这种情形 —— 退出状态取自「栈上或某个 CPU 寄存器里的某个随机值」。
     · C99：掉出 main 末尾**等价于 exit(0)**。原书说用 `gcc -std=c99` 就能拿到
       这个行为。

   本程序故意写成一个没有 return 的 main，然后**用同一个源文件、只改 -std**
   编两遍，把两次的退出码并列出来。

   为了让「那个随机值」可指认，main 的最后一句是 `marker()`（返回 42 的函数）
   —— 它的返回值没人接，很可能就留在返回寄存器里，被 crt0 当成 main 的返回值。
   ⚠️ 这只是**实现细节**，不是标准保证的东西；C89 下真正的语义就是「未定义」。

   编译（两个作业）:
     gcc -O0 -Wall -Wextra -std=c89 -o c25_fall_off_c89 c25_fall_off_main.c
     gcc -O0 -Wall -Wextra -std=c99 -o c25_fall_off_c99 c25_fall_off_main.c
   运行: ./c25_fall_off_c89 ; echo $?     （看退出码）
*/
#include <string.h>
#include <unistd.h>

static const char MSG[] =
    "main() 走完了最后一条语句：没有 return，也没有调 exit()\n"
    "本程序的退出码，就是 crt0 拿到的那个「main 的返回值」\n";

static int
marker(void)
{
    return 42;      /* 故意留一个可指认的数字 */
}

int
main(void)
{
    write(STDOUT_FILENO, MSG, strlen(MSG));
    marker();       /* 最后一句：返回值无人接收 */
}

CE 实测（c25_fall_off_c89，exit code = 42）：

main() 走完了最后一条语句：没有 return，也没有调 exit()

逐条解读

作业 -std 进程退出码 与预测是否一致
c25_fall_off_c89 c89 42 ✅ 与「寄存器里那个残留值」的猜测一致
c25_fall_off_c99 c99 0 ✅ 标准规定就是 exit(0)

⭐ 42 的来源：main 的最后一句是 marker()（一个返回 42 的函数），它的返回值没人接收， 很可能就留在返回寄存器里，被 crt0 当成 main 的返回值用了。 这也解释了 gcc 为什么会给出警告：

⚠️ 42 是实现细节，不是标准保证的东西。C89 下真正的语义就是「未定义」—— 换个编译器、换个优化级别，这个数字就会变。能确定的只有 C99 那一半：0。

📌 工程结论：main 永远写显式 return。不要依赖 C99 的隐式 return 0 （老代码可能用 C89 编译），更不要依赖一个「恰好是 42」的巧合。

# 坑 症状 正解

HFT / 嵌入式关联

路线 要点
HFT 热路径上的「快速退出」必须走 _exit()：exit() 会遍历 exit handler 列表 + flush 全部 stdio，在延迟敏感场景里是不可接受的不确定性。反过来，行情网关的优雅下线要走 exit()，靠 atexit 把 socket 关掉、把日志刷盘。
HFT 进程被 SIGKILL（OOM killer 或运维强杀）时，atexit 里的对账/落盘一条都不会执行 ⇒ 关键状态不能只放在内存里等退出时写，必须持续落盘（write-ahead）。
嵌入式 退出码只有 8 位 ⇒ 用「状态码 + 错误码」两位编码（如 (模块 << 4) | 原因）比塞一个大整数有效。systemd 的 Restart=/SuccessExitStatus= 也都是按 8 位判的。
嵌入式 daemon 化之后 main 返回的语义会被 supervisor 看见；用 _exit() 收场可以跳过 atexit 链——这在「watchdog 已经要重启我了，别做无谓清理」的场景下是优点。

代码自测（Q&A）

Q1：_exit(-1) 之后，父进程 waitpid() 拿到的 status 是 255 吗？

不是。status 本身是 65280（0xff00），WEXITSTATUS(status) 才是 255。

原因：内核在 syscall 入口做 do_exit((error_code&0xff)<<8)（kernel/exit.c:991）， 低 8 位被搬到 status 的高字节。父进程再用 WEXITSTATUS 宏把它搬回来。 所以「255」这个数字是 WEXITSTATUS 的解释结果，不是 status 的原始值。

Q2：为什么在 exit handler 里 printf 的内容还能打出来，但 handler 里调 _exit 后同样一行就没了？

因为 printf 只是把字符串放进用户态 FILE 缓冲，真正的输出要等 exit() 的第②步 （_IO_cleanup，见 stdlib/exit.c:128-129）。

  • handler 正常返回 ⇒ 第②步照跑 ⇒ 内容出去。
  • handler 调 _exit() ⇒ 直接进内核（exit.c:131 那行 _exit(status) 都没机会执行）⇒ 缓冲一起丢。

§25.3 的 c25_exit_handler_no_return.c 把这两种情形并排跑了一次，差别肉眼可见。

Q3：return 0; 和 exit(0); 在 main 里有什么区别？

正常路径上几乎没区别：crt0（__libc_start_main）拿到 main 的返回值后就是用它调 exit()， 所以 handler、flush 都会发生。

区别出现在生命周期上：return 会先结束 main 的作用域，之后如果在 flush/handler 阶段 还去访问 main 的局部变量（例如 setvbuf() 的参数指向 main 里的局部数组），就是 UB。 exit() 从 main 内部调用，main 的栈帧还没退，没有这个问题。

Q4：c25_fall_off_c89 退出码为什么是 42？这是可移植的行为吗？

不是。42 只是「main 最后一句调用的 marker() 的返回值恰好留在返回寄存器里」这个 实现细节的副产品。C89 对「掉出 main 末尾」的定义就是未定义行为—— 换编译器、换优化级别，这个数字就会变。

能指望的只有 C99 那一半：c25_fall_off_c99 的退出码稳定是 0。

Q5：看到 $? 是 139，能确定程序是自己 exit(139) 还是被 SIGSEGV 杀的吗？

不能。 这正是原书 §25.1 的警告。

  • 被 SIGSEGV(11) 杀 ⇒ status 低 7 位是 11，shell 报 128 + 11 = 139。
  • 自己 _exit(139) ⇒ 内核存 139 << 8，WEXITSTATUS 也是 139，shell 同样报 139。

要在程序内部区分，必须看 WIFEXITED / WIFSIGNALED（shell 里做不到）。 本仓库的 ex25_1_exit_minus_one.c 实测里 WIFSIGNALED=1 / WTERMSIG=11 那一行就是判据。

25.2

Details of Process Termination 内核与库到底回收了什么

本章：TLPI 第 25 章 — Process Termination 源码核验：man7 官方 Ch25 分发文件 2 个（procexec/）· 原书 §25.2 正文（书页 533，只有一页半）· Linux v6.6（kernel/exit.c 逐行实读）· glibc 2.39 · CE 实测（gcc 13.3.0 / x86-64 / Ubuntu 24.04，沙箱内核 7.0.0-1012-aws） 本章所有实测数字来自冻结日志 tlpi-ch25-final.txt - 上一节：25.1 Terminating a Process: _exit() and exit() - 下一节：25.3 Exit Handlers

本节讲什么

§25.1 讲的是「进程怎么结束」，§25.2 讲的是「结束的瞬间，内核和库替你做了什么」。

这一节在原书里只有 533 页的一页半，全是清单，没有任何代码、没有任何 Listing、 也没有一句「为什么」。但它是整章最容易吃亏的一节——因为清单上的每一行， 都对应一个「不写清理代码也不会泄漏」的保证，而这些保证是有边界的：

  • 有些资源是内核替你放的（关 fd、解 map、detach shm）；
  • 有些是库替你放的（exit() 里的 stdio flush）；
  • 还有些只有你自己做才行（比如把数据落盘）。

⚠️ 原书 §25.2 没有 Listing，也没有配套程序。 本节用 CE 沙箱的探针实测 + Linux v6.6 kernel/exit.c 的逐行坐标， 把这份清单逐条对到内核代码上——这样你就知道哪些是「保证」，哪些只是「约定」。

1. 原书清单（10 条）与它们在代码里的位置

原书把进程终止时被清理的东西列成 10 条。下表把每一条对到内核 v6.6 的具体调用：

# 原书说的资源 内核/库里的现场 备注

2. 一个经典的「清单陷阱」：文件锁

fcntl() 的记录锁（F_SETLK 那套）的语义是：

锁由进程持有；进程一终止，内核立刻释放它。

这和「关闭 fd 会释放锁」是两个独立的触发条件（POSIX 的记录锁规则）。 所以原书第 2 条说的是「进程终止 ⇒ 锁没了」。

⚠️ 由此有一个很常见的 HFT / 嵌入式事故模式：

场景 后果
A 进程对文件加记录锁，然后 fork 出 B（B 不开这个文件） B 里看不到这把锁（锁属于 A）
A 进程一 exit()/被杀 锁立刻释放，哪怕 B 还在写这个文件
运维以为「锁能保护到我修完数据」 ❌ 锁在 A 死的瞬间就没了

正解：跨进程互斥用 flock()（也由 fd 持有）+ 明确的 open/close 生命周期管理， 或者干脆用 fcntl 的 F_OFD_SETLK（Linux 3.15+，open file description 锁， 生命周期绑在 fd 上而不是进程上）。

HFT / 嵌入式关联

路线 要点
HFT 内核那 10 条是「保证」，但落盘不是。撮合/风控进程被 OOM killer 干掉时 atexit 不执行 ⇒ 状态机快照必须周期性强刷，退出时只做「补刷最后一次」。
HFT 热重启（fast restart）依赖「旧进程一死 fd/锁/共享内存立刻释放」这条保证。但要注意：shm 段不会自动删，重启脚本里必须显式 IPC_RMID，否则 nattch 残留会让新进程误判。
嵌入式 exit_files() 关掉的不只是普通 fd，还包括 epoll / eventfd / timerfd / signalfd ⇒ 靠这些做事件循环的 daemon，退出时不需要手写 close() 循环。
嵌入式 第 5 条（控制终端 + SIGHUP）是「终端一关，daemon 跟着死」的机制来源。daemon 化（setsid() + 切到 /）就是为了脱离这个行为——原书 §37 会展开。
嵌入式 第 9 条（mlock 解除）意味着 mlockall(MCL_CURRENT|MCL_FUTURE) 的实时进程退出后内存锁自动没了，不需要显式 munlock。

代码自测

代码自测（Q&A）

Q1：进程 exit() 之后，它创建的 System V 共享内存段会消失吗？

不会。 内核做的是 exit_shm(tsk)（kernel/exit.c:868），即把该进程detach， shm_nattch 减一。段本身是持久化对象，要等 shmctl(shmid, IPC_RMID, NULL) 或系统重启才消失。

同理，POSIX 命名信号量（/dev/shm/sem.*）与消息队列（/dev/mqueue/*） 只会被 close，名字要等 sem_unlink() / mq_unlink() 才没。

Q2：为什么说「靠 fcntl() 记录锁做互斥，对端进程一死锁就没了」？

POSIX 记录锁（F_SETLK）的持有者是进程。内核在进程终止时释放它—— 这与「关闭 fd 会释放锁」是两个独立的触发条件。所以任何 exit()、_exit()， 甚至一个 SIGSEGV，都会立刻放锁，持有者根本没机会「先把数据写完」。

要绕开这一点，用 F_OFD_SETLK（Linux 3.15+）：锁绑在 open file description 上， 生命周期跟 fd 走，可以跨进程传递，也不会因为某个进程退出而神秘消失。

Q3：disassociate_ctty(1) 为什么包在 if (group_dead) 里？

因为它做的是会话级动作（解除控制终端、给前台进程组发 SIGHUP）， 只能由「线程组的最后一个线程」来做。

group_dead 来自 atomic_dec_and_test(&tsk->signal->live)（kernel/exit.c:843）—— 只有 live 减到 0 才为真。如果每个线程退出都去解除控制终端，多线程程序会被反复踢出会话。

Q4：本节探针里 _SC_CHILD_MAX 是 27191，为什么不能在别处直接引用这个数？

因为它是沙箱宿主机的属性，不是内核常量。CE 会换宿主机， 同一章在 Ch24 那轮跑出来是 54956，本轮是 27191。

这一类数字（_SC_CHILD_MAX、uptime、loads、procs、totalram）都是「会漂」的， 引用时必须写明「某次实测的沙箱值」，不能当成常量写进结论。 「N 百万次平均」这类统计量才相对稳定。

Q5：为什么 probe25.c 最后用 _exit(0) 而不是 exit(0)？

因为它在 [②] 里连续注册了 200000 个空 exit handler。如果走 exit(0)， glibc 会把这两万个注册项逐个调用（__run_exit_handlers 的 while 循环）， 白白消耗时间。

这正好是 _exit() 的典型使用场景之一：「我不想跑 handler，我要立刻消失」。 同一个道理也适用于「fork 出来的子进程」——见 §25.4。

3. handler 里可以再注册 handler —— 而且插队首

原书（书 p.534）有一句特别容易被略过的话：

"Essentially, any desired action can be performed inside an exit handler, including registering additional exit handlers, which are placed at the head of the list of exit handlers that remain to be called."

"placed at the head of the list that remain to be called" —— 这不是"追加到队尾"， 而是插队到队首，也就是下一个就跑。这个语义值得做成可观察量。

/* c25_atexit_reentry.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.3 在讲 atexit() 的调用顺序时，插了一句很容易被略过的话：

     "Essentially, any desired action can be performed inside an exit handler,
      including registering additional exit handlers, which are placed at the
      head of the list of exit handlers that remain to be called."

   「placed at the head of the list that remain to be called」—— 这不是
   「追加到队尾」，而是**插队到队首**。本程序把这个语义做成可观察量：
   main 里依次注册 A、B、C（⇒ 逆序跑：C、B、A），然后在 B 里面再注册一个 D。
   如果 D 是「追加到队尾」，顺序会是 C、B、A、D；
   如果 D 是「插到队首」，顺序会是 C、B、D、A。

   在 CE 上跑：stdout 不是终端 ⇒ 全缓冲 ⇒ 所有 puts/printf 都先攒在缓冲里，
   最后由 exit() 第 ② 步一次性写出，所以**打印顺序 == handler 执行顺序**。

   编译: gcc -O0 -Wall -Wextra -o c25_atexit_reentry c25_atexit_reentry.c
   运行: ./c25_atexit_reentry
*/
#include <stdio.h>
#include <stdlib.h>

static void
handlerD(void)
{
    printf("  handler D   ← 这个是在 handler B 里才注册的\n");
}

static void
handlerC(void)
{
    printf("  handler C\n");
}

static void
handlerB(void)
{
    printf("  handler B   ← 就在这一行里又注册了 D\n");
    if (atexit(handlerD) != 0) {
        printf("  !! 在 handler 里注册 D 失败\n");
    }
}

static void
handlerA(void)
{
    printf("  handler A\n");
}

int
main(void)
{
    printf("=== 注册顺序：A、B、C ⇒ 逆序执行：C、B、A ===\n");
    printf("=== 但 B 会在自己运行期间再注册一个 D ===\n\n");

    if (atexit(handlerA) != 0 || atexit(handlerB) != 0 || atexit(handlerC) != 0) {
        printf("atexit 注册失败\n");
        return EXIT_FAILURE;
    }

    printf("--- main 调 exit(0)，下面三行/四行的次序就是答案 ---\n");
    exit(0);    /* 不返回 */
}

① 顺序是 C → B → D → A，不是 C → B → A → D —— ⇒ D 插到了队首， 它"插"在 A 前面跑。如果 atexit() 只是简单地把新条目追加到列表末尾， D 必然排在 A 之后。原书的 "head of the list" 得到实测确认。

② 机制在 glibc 源码里可以逐行对上。 __run_exit_handlers() （stdlib/exit.c:64-66）是这么消费列表的：

      while (cur->idx > 0)
    {
      struct exit_function *const f = &cur->fns[--cur->idx];

下标递减 ⇒ 先跑"最后注册的那条"。而 __new_exitfn() （stdlib/cxa_atexit.c:126-131）在同一块还有空位时是这样放的：

  else
    {
      /* There is more room in the block.  */
      r = &l->fns[i];
      l->idx = i + 1;
    }

关键在于 i 的初值（cxa_atexit.c:91-98）：它从 l->idx 往下找到第一个空位 —— 而 l->idx 就是当前消耗位置（因为 __run_exit_handlers 直接改的就是这个字段）。 ⇒ 新条目被放到"下一个就轮到的位置"。放完之后 exit.c:113-116 检测到 "注册数变了"就 goto restart，于是它马上被执行：

      if (__glibc_unlikely (new_exitfn_called != __new_exitfn_called))
        /* The last exit function, or another thread, has registered
           more exit functions.  Start the loop over.  */
        goto restart;

③ 如果在 exit() 处理期间注册会失败吗？ —— __new_exitfn() 开头有一道闸 （cxa_atexit.c:86-89）：

  if (__exit_funcs_done)
    /* Exit code is finished processing all registered exit functions,
       therefore we fail this registration.  */
    return NULL;

__exit_funcs_done 只在整条链走完才被置位（exit.c:60），所以 "在 handler 里注册"在正常情形下不会失败。但如果是在最后一个 handler 里注册， 而且此时列表已经耗尽，atexit() 就会返回非 0 了。

4. handler 里不返回：两种后果完全不同

原书（书 p.534）在这里连续放了两段后果完全相反的说法：

"…if one of the exit handlers fails to return—either because it called _exit() or because the process was terminated by a signal (e.g., the exit handler called raise()) —then the remaining exit handlers are not called. In addition, the remaining actions that would normally be performed by exit() (i.e., flushing stdio buffers) are not performed."

"SUSv3 states that if an exit handler itself calls exit(), the results are undefined. On Linux, the remaining exit handlers are invoked as normal."

同一个"在 handler 里终止进程"的动作，走 _exit() 就"全取消"， 走 exit() 就"照常继续"。这个差别必须实测。

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 §25.3「Registering exit handlers」里有两条相邻、但后果完全不同的说法：

     (1) "if one of the exit handlers fails to return—either because it called
          _exit() or because the process was terminated by a signal—then the
          remaining exit handlers are not called. In addition, the remaining
          actions that would normally be performed by exit() (i.e., flushing
          stdio buffers) are not performed."

     (2) "SUSv3 states that if an exit handler itself calls exit(), the results
          are undefined. On Linux, the remaining exit handlers are invoked as
          normal."

   让差别变成可观察量。

   ⚠️ 注意：父进程在每次 fork() 之前显式 fflush(stdout)。不这么做的话，
   父进程自己上一阶段的报表还在缓冲里，会被子进程连缓冲一起继承，

#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void
w(const char *s)
{
    write(STDOUT_FILENO, s, strlen(s));
}

static void
w2(const char *tag, const char *s)
{
    w("    ");
    w(tag);
    w(" ");
    w(s);
    w("\n");
}

{
    w2("W-hA", "       （hA：只 write + printf，不终止）");
    printf("    M-hA         （hA 的 printf，进用户态缓冲）\n");
}

handlerBAbort(void)

static void
runPhase(const char *tag, const char *note, void (*hB)(void))
{
    pid_t pid;
    int status;

    printf("\n=== 情形 %s：%s ===\n", tag, note);
    printf("  子进程登记顺序：先 hA，后 hB ⇒ LIFO ⇒ 先跑 hB\n");

    fflush(stdout);              /* ★ 关键：别把父进程的缓冲带进子进程 */

    pid = fork();
    if (pid == -1) {
        w("fork 失败\n");
        exit(EXIT_FAILURE);
    }
    if (pid == 0) {
        /* ---- 子进程 ---- */
        w("    W-main-child （子进程第 1 行，write ⇒ 一定看得见）\n");
        printf("    M-main-child （子进程的 printf ⇒ 只有 exit() 的 flush 才能看见它）\n");

        if (atexit(handlerA) != 0 || atexit(hB) != 0) {
            w("atexit 注册失败\n");
            _exit(1);
        }
        w("    ---- 即将 exit(3)，然后交给 exit handler ----\n");
        exit(3);                 /* 外层状态：如果 handler 不提前终止，就是它 */
        /* 不会到这里 */
    }

    /* ---- 父进程 ---- */
    if (waitpid(pid, &status, 0) == -1) {
        w("waitpid 失败\n");
        exit(EXIT_FAILURE);
    }
    printf("  [父进程] 子进程 status=%d (0x%04x)  WIFEXITED=%d  WEXITSTATUS=%d\n",
            status, (unsigned) status,
            WIFEXITED(status) ? 1 : 0,
            WIFEXITED(status) ? WEXITSTATUS(status) : -1);
}

{

逐条解读

① 情形 A：M-main-child 与 M-hA 两行 printf 输出彻底消失。 这是"_exit() 不 flush"最干净的证据 —— 那两行字符串确实被 printf 调用过 （代码里就写在 _exit(7) 之前），但它们停留在用户态缓冲里，随着进程被 _exit() 带走而永远丢失。⇒ _exit() 之后，你没 flush 的输出就是垃圾。

⚠️ 由此得到一条非常实用的调试准则：在"可能 _exit() 或 abort() 的代码路径上 不要用 printf 记录现场。 用 write(2) 或 fprintf(stderr, ...) （stderr 默认无缓冲）。

② 情形 A 里 hA 没有跑。 handlerA 会写 W-hA 那一行 —— 输出里没有。 ⇒ 原书 "the remaining exit handlers are not called" 得到确认。

③ 情形 B：W-hA 与两行 M* 全都出来了。 说明 hB 里调 exit(9) 之后， hA 照常执行、最后的 flush 也照常发生。⇒ 原书 "On Linux, the remaining exit handlers are invoked as normal" 得到确认。

④ 父进程拿到的状态码，是"内层那个"。 情形 A：外层 exit(3)，hB 里 _exit(7) ⇒ 父进程看到 7（0x0700）。 情形 B：外层 exit(3)，hB 里 exit(9) ⇒ 父进程看到 9（0x0900）。 ⇒ 后到达 _exit() 的那个状态生效。原书对底层机制的说法是 "we use the status value in the last exit()" —— glibc 源码的注释正好也这么写 （stdlib/exit.c:45-48）：

  /* We do it this way to handle recursive calls to exit () made by
     the functions registered with `atexit' and `on_exit'. We call
     everyone on the list and use the status value in the last
     exit (). */

⑤ ⚠️「SUSv3 说 UB、Linux 上照常」这句话不要读成"可以放心用"。 原书在后面还补了一句（书 p.535）：

"However, on some systems, this causes all of the exit handlers to once more be invoked, which can result in an infinite recursion (until a stack overflow kills the process). Portably applications should avoid calling exit() inside an exit handler."

也就是说：同样一段代码，在别的 UNIX 上会栈溢出崩掉。 Linux 上"恰好合理"不等于可以依赖 —— 这与 Ch24 里 vfork() 那个 "演示性违规"是同一类问题。

⑥ 一个容易被忽略的细节：runPhase() 里 fork 之前有 fflush(stdout)。 不写这一句，父进程上一阶段的报表还在缓冲里，会被子进程连缓冲一起继承， 然后被子进程的 exit() 再 flush 一遍 —— 那正是 §25.4 要讲的坑， 会在本节程序里制造假象。这个"防污染"动作本身就是 §25.4 知识的一次应用。

5. 上限、继承与清除

5.1 上限：sysconf(_SC_ATEXIT_MAX)

原书（书 p.535）：

"SUSv3 requires that an implementation allow a process to be able to register at least 32 exit handlers. Using the call sysconf(_SC_ATEXIT_MAX), a program can determine the implementation-defined upper limit… (However, there is no way to find out how many exit handlers have already been registered.) By chaining the registered exit handlers in a dynamically allocated linked list, glibc allows a virtually unlimited number of exit handlers to be registered. 5.2 fork() 继承一份副本；exec() 全部清掉

原书（书 p.535）：

"A child process created via fork() inherits a copy of its parent's exit handler registrations. When a process performs an exec(), all exit handler registrations are removed. (This is necessarily so, since an exec() replaces the code of the exit handlers along with the rest of the existing program code.)"

"fork 继承一份副本"在 Ch24 已经反复验证；"exec 全部清掉"需要单独测。

5.3 无法注销 handler

原书（书 p.535）：

"We can't deregister an exit handler that has been registered with atexit() (or on_exit()). However, we can have the exit handler check whether a global flag is set before it performs its actions, and disable the exit handler by clearing the flag."

这是一个模式，值得记住写法：

static volatile sig_atomic_t need_cleanup = 1;   /* 想取消时置 0 */

static void
cleanup(void)
{
    if (!need_cleanup)
        return;          /* 已经不需要了，静默跳过 */
    /* ... 真正的清理 ... */
}

⚠️ atexit() 没有对应的 at_undelete。glibc 内部虽然有空位复用逻辑 （cxa_atexit.c:91-102 会回收 ef_free 的槽位），但那是给 dlclose 用的，不是给你的。 用户态唯一的"注销"就是上面这个 flag 模式。

6. atexit() 的两条局限 → on_exit()

原书（书 p.535）把 on_exit() 的由来写得很清楚：

"Exit handlers registered with atexit() suffer a couple of limitations. The first is that when called, an exit handler doesn't know what status was passed to exit()… The second limitation is that we can't specify an argument to the exit handler when it is called."

局限 atexit() on_exit()
拿得到 exit() 的 status ❌ ✅（第一个形参）
注册时可以带一个自定义参数 ❌ ✅（第二个形参 void *arg）
同一函数注册多次（参数不同） 可以，但无法区分是谁 ✅（靠 arg 区分，官方 Listing 25-1 就是这么用的）
标准 SUSv3 无标准（glibc 扩展；"available on few other UNIX implementations"）
头文件开关 无 需要 _BSD_SOURCE / _SVID_SOURCE（glibc 2.39 已弃用，见第 2 节）

两者共用同一条列表 —— 原书（书 p.536）：

"Functions registered using atexit() and on_exit() are placed on the same list. If both methods are used in the same program, then the exit handlers are called in reverse order of their registration using the two methods."

glibc 源码逐行确认：atexit() 最终走到 __cxa_atexit()（stdlib/atexit.c:44-47）， on_exit() 走到 __on_exit()（stdlib/on_exit.c:24-48）， 两者调用的是同一个 __new_exitfn(&__exit_funcs)：

/* stdlib/atexit.c:44 */
atexit (void (*func) (void))
{
  return __cxa_atexit ((void (*) (void *)) func, NULL, __dso_handle);
}

/* stdlib/on_exit.c:34 */
  new = __new_exitfn (&__exit_funcs);
  ...
  new->flavor = ef_on;          /* atexit 走的是 ef_cxa */

/* stdlib/cxa_atexit.c:68 */
  return __internal_atexit (func, arg, d, &__exit_funcs);

区别只在记录进列表里的 flavor 字段（ef_cxa / ef_on）， 以及运行时的分派（stdlib/exit.c:69-76 那个 switch (f->flavor)）。 ⇒ 一条列表、两种 flavor、统一逆序执行 —— 这就是官方 Listing 25-1 输出的机制。

⚠️ 原书最后给了一句实用建议（书 p.536）：

"Although more flexible than atexit(), on_exit() should be avoided in programs intended to be portable, since it is not covered by any standards and is available on few other UNIX implementations."

⇒ 要可移植就用 atexit()；on_exit() 只在确定跑 Linux/glibc 时用。

8. 常见坑

  1. if (atexit(f) == -1) 是错的。 原书明确说"返回非 0，不一定是 −1"。 写 != 0。
  2. 别在 handler 里 printf 之后就指望能看到。 如果后面的 handler _exit() 了，你的输出会永远留在缓冲里（情形 A 实测）。 要可靠就用 write(2) / fprintf(stderr, ...)。
  3. 别在 handler 里调 exit()。 Linux 上"能用"（实测情形 B）， 但 SUSv3 说 UB，别的系统会无限递归到栈溢出。
  4. on_exit() 不可移植，而且需要 feature macro。 新代码如果要可移植，用 atexit() + 全局变量传参数。
  5. handler 里的代码必须是"可重入且不依赖其他 handler 已跑完"的， 因为顺序是 LIFO：先注册的（更基础的清理）最后跑。
  6. fork() 之后每个进程各有一份 handler 副本， 所以"在 handler 里写日志文件"在 fork 之后会写两次。 原书的准则（§25.4）是：一个程序里应该只有一个进程用 exit() 收场。
  7. _SC_ATEXIT_MAX 读到的值不代表"你还能注册多少" —— 原书说 "there is no way to find out how many exit handlers have already been registered." 它只是一个理论声明上限。
  8. exec() 会清掉 handler，但不会清 stdio 缓冲。 清 handler 是因为 "handler 的代码没了"；缓冲是数据不是代码，所以留着。

9. HFT / 嵌入式关联

① handler 是"库"与"主程序"之间唯一不需要接口约定的清理通道。 一个行情采集库把自己的 fd / 共享内存 attach / 日志缓冲的回收注册成 handler， 就不需要宿主程序记得调用 xxx_shutdown()。这在"HFT 里到处是第三方 高性能库（网络 / 序列化 / 日志）"的场景下非常实用。

② 但 handler 在"异常终止"路径上完全不可靠 —— 原书（书 p.534）对此有一句 极其实用的建议：

"The best we can do is to establish handlers for the signals that might be sent to the process, and have these handlers set a flag that causes the main program to call exit(). (Because exit() is not one of the async-signal-safe functions… we generally can't call it from a signal handler.) Even then, this doesn't handle the case of SIGKILL…"

⇒ 正确的模式是 信号处理器只置一个volatile sig_atomic_tflag， 主循环看到 flag 再走正常退出路径（调 exit()）。 在 HFT 里这意味着主循环必须每个 tick 检查一次 shutdown flag —— 否则 Ctrl-C 之后进程会一直跑，直到被 SIGKILL， 而那时 handler 一个都不会执行，未落盘的成交记录会丢。

③ 不能用 exit() 的地方要显式列出。 信号处理器、fork() 之后的子进程 （见 §25.4）、vfork() 的子进程（Ch24 §24.3）—— 这三处一律用 _exit()。

④ 嵌入式里"atexit + _exit 混用"是资源泄漏的常见来源： 看门狗超时路径用 _exit() 直接走，handler 里那些硬件去初始化 （关电机、断继电器、释放 SPI）全都不执行， 下次启动时外设处于不确定状态。 ⇒ 必须在 _exit() 路径上单独补一份"最小安全收尾"， 或者让启动自检能识别"上次是非正常退出"（写一个 magic 到 RTC / flash）。

⑤ exec() 清 handler 这一点在"自更新 / 自重启"场景里很关键。 一个长期运行的 daemon 用 execv(argv[0], argv) 给自己做原地重启时， 注册过的 handler 会全部丢失 —— 如果重启逻辑依赖 handler 做状态保存， 就会静默失效。正确做法是重启前显式落盘，或者让新实例自己重新注册。

代码自测（Q&A）

Q1：atexit() 注册的三个 handler，执行顺序是什么？为什么？

A：注册的逆序（LIFO）。原书的理由是：先注册的通常是"更基础的清理"， 它需要在后注册的那些（更上层的）清理跑完之后再跑。 本节官方 Listing 25-1 实测：注册 on10 → at1 → at2 → on20， 执行 on20 → at2 → at1 → on10，完全逆序。

Q2：在 handler 里再调 atexit() 注册一个新 handler，它什么时候跑？

A：紧接着跑（插到"剩余待调列表"的队首）。 本节 c25_atexit_reentry 实测：注册 A、B、C，B 里注册 D， 执行顺序是 C → B → D → A（不是 C、B、A、D）。 机制在 glibc stdlib/cxa_atexit.c:104-131 + stdlib/exit.c:113-116 的 goto restart。

Q3：handler 里调 _exit() 会怎样？调 exit() 又会怎样？

A： - _exit() ⇒ 剩下的 handler 不跑、stdio 不 flush。实测情形 A： 两行 printf 输出彻底消失，hA 没执行，父进程拿到 _exit(7) 的 7。 - exit() ⇒ Linux 上剩下的 handler 照常跑、flush 照常发生。实测情形 B： hA 执行了、两行 M* 出来了，父进程拿到 exit(9) 的 9。 ⚠️ 但 SUSv3 说这是 UB，某些系统会无限递归到栈溢出。可移植代码禁止这么写。

Q4：atexit() 和 on_exit() 注册的 handler，执行顺序怎么交错？

A：放在同一条列表里一起逆序。原书："Functions registered using atexit() and on_exit() are placed on the same list." glibc 源码确认两者都调 __new_exitfn(&__exit_funcs)（stdlib/cxa_atexit.c:68 与 stdlib/on_exit.c:34）， 只是 flavor 字段不同（ef_cxa vs ef_on）。 官方 Listing 25-1 的输出就是交错的：on20 / at2 / at1 / on10。

Q5：sysconf(_SC_ATEXIT_MAX) 在本环境里返回多少？原书写的是多少？

A：实测 2,147,483,647（0x7fffffff = INT_MAX）。 原书 p.535 写的是 2,147,482,647 —— 原书数字笔误（书上那句括号里的 "the maximum signed 32-bit integer"才是对的）。 另外实测连续注册 200000 个 handler 全部成功，印证原书"链式列表 ⇒ 事实上无限"。

Q6：fork() 和 exec() 对 exit handler 注册表分别做什么？

A： - fork()：子进程继承一份副本（父子各有一份，各跑各的）。 - exec()：全部清掉。原书给的理由是 "an exec() replaces the code of the exit handlers along with the rest of the existing program code" —— handler 是代码， 代码被换掉了，注册自然作废。 本节 c25_exec_clears_handlers 实测：exec 前注册的 oldHandler 没有执行。

Q7：怎么"注销"一个已经注册的 handler？

A：不能注销（atexit() 没有对应的反注册接口）。 原书给的标准做法是全局 flag： handler 里先检查 flag，需要禁用时把 flag 清掉、直接 return。 glibc 内部确实有槽位回收（cxa_atexit.c:91-102 找 ef_free）， 但那是给 dlclose() 用的，不是用户态接口。

Q8：为什么 #define _BSD_SOURCE 现在会报警？它还有效吗？

A：因为 glibc 2.39 已把它列为弃用别名（include/features.h:196 有 #warning）。 仍然有效 —— 那 8 行代码在报警之后会自动 # undef _DEFAULT_SOURCE / # define _DEFAULT_SOURCE 1，功能不受影响。 写新代码应该直接用 _DEFAULT_SOURCE。

Q9：exit handler 是内核实现的还是 glibc 实现的？

A：完全是 glibc（用户态）实现的。 内核 do_exit()（kernel/exit.c:809-895） 里没有任何 exit handler 相关代码。 这就解释了为什么"被信号杀死时 handler 不跑" —— 内核直接进 do_exit()， glibc 根本没有介入的机会。

① 这个输出正是原书 > a 之后 cat a 的那三行。 逐字一致：

⚠️ 为什么在 CE 上直接就是"重定向到文件"那一半？ 因为 CE 的 stdout 不是终端 —— 本章 probe25 实测 S_ISSOCK = 1 / isatty(1) = 0。 glibc 的规则是"只有终端才用行缓冲"，所以这里 stdout 走块缓冲（全缓冲）。 ⇒ 原书 $ ./fork_stdio_buf（终端、行缓冲）那一半，在本环境里物理上观察不到。 后面第 3 节用一个自写程序间接补上这一半。

② Hello world 出现两遍 —— 原书（书 p.538）：

"recall that the stdio buffers are maintained in a process's user-space memory… Therefore, these buffers are duplicated in the child by fork(). When standard output is directed to a terminal, it is line-buffered by default, with the result that the newline-terminated string written by printf() appears immediately. However, when standard output is directed to a file, it is block-buffered by default. Thus, in our example, the string written by printf() is still in the parent's stdio buffer at the time of the fork(), and this string is duplicated in the child. When the parent and the child later call exit(), they both flush their copies of the stdio buffers, resulting in duplicate output."

时间线拆开看：

时刻 父进程用户态缓冲 内核缓冲 子进程
printf("Hello world\n") 后 "Hello world\n" — 还不存在
write(..., "Ciao\n", 5) 后 "Hello world\n" "Ciao\n" 还不存在
fork() 后 "Hello world\n" "Ciao\n" 缓冲副本里有 "Hello world\n"
子进程 exit() 清空 → 写 "Hello world\n" "Ciao\n" + "Hello world\n" —
父进程 exit() 清空 → 又写 "Hello world\n" "Ciao\n" + "Hello world\n" + "Hello world\n" —

⇒ fork() 复制的是"还没送出去的输出"。这就是重复的成因。

③ Ciao 只出现一遍 —— 原书（书 p.538）：

"The output of the write() in the program in Listing 25-2 doesn't appear twice, because write() transfers data directly to a kernel buffer, and this buffer is not duplicated during a fork()."

⭐ 这一条给出了一个判定规则：重复与否，取决于数据在 fork() 那一刻 待在"用户态"还是"内核态"。

通路 fork() 那一刻数据在哪 会不会重复
printf() / fwrite() / puts() 用户态 FILE 缓冲（块缓冲时） 会
write() / sendfile() / read() 内核缓冲（或已交给设备） 不会

④ Ciao 排在 Hello world 前面 —— 原书（书 p.538）：

"The output of write() appears before that from printf() because the output of write() is immediately transferred to the kernel buffer cache, while the output from printf() is transferred only when the stdio buffers are flushed by the call to exit()."

⇒ 这其实就是 §25.1 那三步的又一次体现：write() 立刻可见、printf() 要等第 ② 步。

2. 三种修法（原书给的"药"）

原书（书 p.538）把修法分成两条 bullet，第二条里还藏了一条通用准则：

"We can prevent this duplicated output from occurring in one of the following ways: - As a specific solution to the stdio buffering issue, we can use fflush() to flush the stdio buffer prior to a fork() call. Alternatively, we could use setvbuf() or setbuf() to disable buffering on the stdio stream. - Instead of calling exit(), the child can call _exit(), so that it doesn't flush stdio buffers. This technique exemplifies a more general principle: in an application that creates child processes, typically only one of the processes (most often the parent) should terminate via exit(), while the other processes should terminate via _exit(). This ensures that only one process calls exit handlers and flushes stdio buffers, which is usually desirable."

整理成表格：

修法 做法 作用范围 代价
A fork() 之前 fflush(stdout) 只解决"这一刻缓冲里已有的内容" 之后父进程继续 printf 还会进缓冲，只在 fork 点有效
B 子进程用 _exit() 而不是 exit() 从根上解决（子进程永不 flush、永不跑 handler） 子进程自己的 handler 也不跑 ⇒ 需要"每个进程各自收场"时不能用
C setbuf(stdout, NULL) / setvbuf(...) 关缓冲 从根上解决，且父进程行为也变 每次 printf 都是一次 write 系统调用 ⇒ 性能大幅下降

原书还补了一段"什么时候可以父子都 exit()"（书 p.538）：

"Other approaches that allow both the parent and child to call exit() are possible (and sometimes necessary). For example, it may be possible to design exit handlers so that they operate correctly even if called from multiple processes, or to have the application install exit handlers only after the call to fork(). Furthermore, sometimes we may actually want all processes to flush their stdio buffers after a fork(). In this case, we may choose to terminate the processes using exit(), or use explicit calls to fflush() in each process, as appropriate."

⇒ 三种"合法地父子都 exit()"的情形： ① handler 本身写成多进程安全；② handler 只在 fork() 之后才注册； ③ 你确实想每个进程都 flush 一次（比如每个进程各写一份日志）。

/* c25_fork_stdio_three_fixes.c

   ⚠️ 延伸 demo —— **原书没有这个程序**。

   原书 Listing 25-2（`fork_stdio_buf.c`）只演示了**病**：
     "Hello world\n" 走 printf（进用户态缓冲）、然后 write("Ciao\n")、
     然后 fork()、然后父子都 exit() —— 当 stdout 是**块缓冲**（被重定向到文件）时，
     父进程那一刻还没 flush 的缓冲被 fork() 复制进子进程，
     于是父子各 flush 一次 ⇒ "Hello world" 打印两遍，且 "Ciao" 反而在前。

   原书 §25.4 接着给了**药**，一共三种：
     A. fork() 之前用 fflush()（或 setvbuf()/setbuf() 关掉缓冲）
     B. 子进程改用 _exit()（不 flush，也不跑 exit handler）
        —— 由此引出更一般的准则：一个程序里应该只有**一个**进程用 exit() 收场，
           通常是父进程
     C. （同 A 的后半）直接对 stdio 流关缓冲

   本程序把病与三种药放进同一个源文件，用 argv[1] 选模式，方便逐个对照。

   ⚠️ 在 CE 上跑：stdout 不是终端（是 socket）⇒ glibc 对 stdout 用**全缓冲**，
   所以 CE 上「模式 0」直接就等于原书里 `./fork_stdio_buf > a` 那一半，
   而原书 `./fork_stdio_buf`（终端，行缓冲）那一半**在 CE 上观察不到** —— 
   模式 3（关缓冲）是 CE 上唯一能拿到「类终端顺序」的办法。

   编译: gcc -O0 -Wall -Wextra -o c25_fork_stdio_three_fixes c25_fork_stdio_three_fixes.c
   运行: ./c25_fork_stdio_three_fixes <0|1|2|3>
*/
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void
label(int mode)
{
    const char *desc;
    char buf[256];

    switch (mode) {
    case 1:  desc = "修法 A：fork() 之前 fflush(stdout)";      break;
    case 2:  desc = "修法 B：子进程改用 _exit()";               break;
    case 3:  desc = "修法 C：setbuf(stdout, NULL) 关掉缓冲";    break;
    default: desc = "模式 0（原书 Listing 25-2 原样）";          break;
    }
    snprintf(buf, sizeof(buf), "--- 模式 %d | %s ---\n", mode, desc);
    write(STDOUT_FILENO, buf, strlen(buf));   /* 用 write 打标签，不参与缓冲顺序 */
}

int
main(int argc, char *argv[])
{
    int mode = (argc > 1) ? atoi(argv[1]) : 0;
    pid_t pid;

    /* 修法 C 必须在第一次 printf 之前生效 */
    if (mode == 3)
        setbuf(stdout, NULL);

    label(mode);

    printf("Hello world\n");                    /* → 用户态缓冲（模式 3 除外） */
    write(STDOUT_FILENO, "Ciao\n", 5);          /* → 立刻进内核缓冲 */

    if (mode == 1)
        fflush(stdout);                         /* 修法 A：把缓冲清空后再 fork */

    pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        if (mode == 2)
            _exit(EXIT_SUCCESS);                /* 修法 B：子进程不 flush */
        exit(EXIT_SUCCESS);
    }

    if (wait(NULL) == -1) {
        perror("wait");
        return EXIT_FAILURE;
    }
    exit(EXIT_SUCCESS);
}

② 模式 1 与模式 2 治好了重复：都只剩一行 Hello world。 两种药机制不同但结果相同：

模式 机制 子进程还有没有 "Hello world" 的副本
1 fflush 在 fork 前把缓冲清空 没有（清空是共享的）

⇒ 一条是"让数据不在缓冲里"，一条是"让人不去送"。两条都能修，但适用范围不同： 模式 1 只在 fork() 那一刻有效（之后父进程再 printf 又会有新内容）； 模式 2 是结构性的（子进程永远不 flush）。

为什么？因为 setbuf(stdout, NULL) 让 stdout 无缓冲 ⇒ printf("Hello world\n") 立刻变成一次 write() 落到内核里，排在后面那句 write("Ciao\n") 前面。

⇒ ⭐ 所以模式 3 是 CE 上唯一能间接展示"行缓冲/无缓冲时顺序正常"的办法。 它不等价于真终端（真终端是行缓冲，靠 \n 触发 flush；这里是无缓冲）， 但在"输出顺序"这个观察面上等效。笔记里必须说清这个区别，不能当成"终端行为"。

④ execTime 的对比值得一提：模式 3（41 ms）明显慢于模式 0（18 ms）。 差别不完全来自 setbuf（这个程序输出量太小），但方向上是对的： 无缓冲 = 每次 printf 一次系统调用。原书在 §13.2 讲 stdio 性能时也强调这一点。 ⇒ 生产代码里不要随手关缓冲。 要的是"控制 flush 的时机"，不是"取消缓冲"。

⑤ 一个容易忽略的细节：为什么标签用 write() 打？ 因为标签是"模式 N | 修法 X"这种说明性文字，如果它走 printf， 它会和被测数据挤进同一个缓冲，把观察顺序弄乱。 用 write() 打标签让它不参与缓冲顺序，观察才干净。 这是"观察者不能影响被测对象"在 I/O 层面的体现。

4. 一般化：什么时候该用 _exit()，什么时候该用 exit()

原书那条"更一般的准则"值得单独画一张决策表：

场景 用哪个 为什么
单进程程序正常结束 exit()（或 main return） 要跑 handler、要 flush
fork() 出来的子进程（不 exec） _exit() 避免重复 flush / 重复跑 handler
fork() 之后立刻 exec() 的子进程 无所谓（但习惯用 _exit()） exec 会清 handler；且失败路径要立刻收场

5. ⚠️ 混用 stdio 与系统调用：原书点到的一条更普遍的坑

原书在本节末尾（书 p.538）留了一句跨章的提醒：

"(In general, care is required when mixing stdio functions and system calls to perform I/O on the same file, as described in Section 13.7.)"

本节的程序就是这句话的最小反例：同一个 stdout 上，printf 与 write 的输出 顺序无法预测（取决于缓冲状态）。在真实代码里这会变成更隐蔽的问题：

混用写法 危险
printf(...) + write(fileno(stdout), ...) 顺序错乱（本节）
fprintf(fp, ...) + write(fileno(fp), ...) 同上，且文件偏移可能错位
fread(fp) + read(fileno(fp)) 读串位：fread 已经预读了一大块进缓冲，read 从内核位置继续读 ⇒ 数据丢失
fprintf(fp) + ftruncate(fileno(fp)) 缓冲里的数据还没落盘，截断尺寸不对

⇒ 规则：同一个文件一个进程里只选一套 API。 要么全 stdio，要么全系统调用。 非要混用就在边界处 fflush() / fseek(fp, 0, SEEK_CUR)（后者会丢弃预读缓冲）。

⚠️ 一个关键的认识：fork() 并没有"复制 stdio 缓冲"这个动作。 它只是复制了整个用户态地址空间（COW），而缓冲恰好住在里面。 所以任何"住在用户态里的状态"在 fork() 之后都会有一份副本 —— 不只是 stdio 缓冲，还有：你自定义的日志缓冲、malloc 里的 arena 元数据、 rand() 的内部状态、你的"批量攒够了再发"的行情缓冲。

⇒ fork() 之后的子进程必须假设"所有用户态缓存都是过期的"。

7. 常见坑

  1. 别在 fork() 之前留 printf 输出在缓冲里（本节主角）。 fflush(NULL) 一次全清，或者在 fork 之后立刻让子进程走 _exit()。
  2. fflush(stdout) 只清 stdout，stderr 默认无缓冲不用管， 但别的东西（你自己 fopen 的日志文件）要 fflush(NULL) 或逐个清。
  3. fork() 之后父子共用同一个文件偏移（共享 open file description）， 所以即使不重复输出，两边的 write 也会交错。 想让子进程自己写一份，得先 open 一个新 fd（或者 O_APPEND）。
  4. setbuf(stdout, NULL) 要放在第一次 printf 之前， 否则缓冲区已经分配，行为是"已分配但换成无缓冲"，语义不清晰。
  5. setvbuf() 必须在任何 I/O 之前调用（POSIX 要求）。
  6. 别把 fork() 之后的子进程 exit() 当成"等价于 _exit()" —— 它会跑一遍父进程注册的 handler（那些 handler 可能假设"只有父进程会跑"， 比如写固定路径的日志文件 / 释放共享资源）⇒ 双重释放、日志写两遍。
  7. 在 CE 上不能观察"终端行缓冲"那一半（probe25 实测 stdout 是 socket）。 笔记里凡是引用"终端行为"，必须标为原书行为，不能用 CE 实测冒充。

8. HFT / 嵌入式关联

① fork 之后的"双重 flush"在 HFT 里通常表现为"日志写两遍"或"审计记录重复"。 一个下单进程 fork 出子进程处理某个连接，父子都 exit() —— 如果父进程的日志缓冲里还有没落盘的行，子进程会把它再写一遍。 后果不是"多一行日志"，而是"多一条看起来合法的成交记录"。 ⇒ 这是数据集污染的经典成因，排查时先看"记录数是不是恰好成倍"。

② 更隐蔽的一类：fork() 复制的不只是 stdio 缓冲，而是所有用户态批量缓冲。 一个"攒够 64 条行情再一次性发包"的网关，如果在 fork() 那一刻缓冲里有 30 条， 子进程会把这 30 条再发一遍。⇒ 在任何 fork() 之前， 所有"攒着的、还没送出去的东西"都必须显式处理干净（flush、清空、或者干脆不用 fork）。

③ 嵌入式里 _exit() 反而是常态。 资源极度受限的 daemon 经常在错误路径上"直接重启"： _exit(EXIT_FAILURE) 然后让 init / watchdog 拉起来。 这故意跳过了 handler 与 flush —— 前提是关键状态不放在用户态缓冲里， 而是每步都同步落到 flash / SD 卡 / NVRAM。

④ 反过来，如果嵌入式程序依赖 printf 打日志到串口（终端）， 它的行为是行缓冲，和 fork 之后的块缓冲完全不同。 同一个程序"在开发板上直接跑"和"通过日志重定向到文件跑"， 输出顺序可能不一样 —— 这正是本节现象的实战版本。

⑤ 性能上的一点提醒：低延迟路径上应该明确控制缓冲， 而不是依赖默认值。常见做法是：日志走独立的无缓冲 fd（write() 到 /dev/shm/ 或 ring buffer），业务输出走默认缓冲。 把"要不要立刻可见"变成一个显式决策，而不是"取决于 stdout 是不是终端"。

代码自测（Q&A）

Q1：fork_stdio_buf 重定向到文件时，为什么 Hello world 打印两遍？

A：因为 stdio 缓冲在用户态内存里，fork() 会把它整个复制一份。 printf("Hello world\n") 的内容在块缓冲模式下还留在父进程缓冲里， fork() 时被复制进子进程；随后父子各调 exit()，各 flush 一次 ⇒ 同一行输出两次。 关键判据：数据在 fork() 那一刻待在用户态还是内核态。

Q2：为什么 Ciao 只出现一遍，而且排在 Hello world 前面？

A：Ciao 是用 write() 写的，直接进内核缓冲，内核缓冲不会被 fork() 复制 ⇒ 不重复。而 printf 要等 exit() 的第 ② 步才 flush ⇒ 时间上晚， 所以 Ciao 先出现。

Q3：原书给了哪三种修法？各自的适用面是什么？

A： 1. fork() 之前 fflush()（或 setvbuf / setbuf 关缓冲）—— 只解决"fork 那一刻缓冲里已有的内容"。 2. 子进程改用 _exit() —— 结构性解决（子进程永不 flush、永不跑 handler）。 3. 对 stdio 流关缓冲 —— 也解决，但每次 printf 都变成系统调用，有性能代价。

Q4：原书说"更一般的准则"是什么？

A："in an application that creates child processes, typically only one of the processes (most often the parent) should terminate via exit(), while the other processes should terminate via _exit()." 理由：保证只有一处调用 exit handler、只有一处 flush 缓冲。

Q5：什么时候"父子都调用 exit()"是可以的？

A：原书列了三种：① exit handler 设计成"被多个进程调用也正确"； ② 只在 fork() 之后才注册 exit handler； ③ 你确实想每个进程都 flush 一次自己的缓冲。 另外一种通用做法是在每个进程里各显式 fflush() 一次。

Q6：为什么 CE 上只能观察到"重定向到文件"那一半？

A：因为 CE 的 stdout 是 socket（实测 S_ISSOCK = 1、isatty(1) = 0）， glibc 只对终端用行缓冲，这里走块缓冲。 所以本节官方程序在 CE 上直接就是原书 > a 那一半。 "终端行缓冲"那一半物理上不可观察，本仓库用自写程序模式 3 （setbuf(stdout, NULL)）来间接展示"顺序正常"的情形 —— 但必须说明那是无缓冲，不等于行缓冲。

Q7：setbuf(stdout, NULL) 为什么能让输出的顺序变成"正常"？

A：因为关掉缓冲后 printf("Hello world\n") 立刻变成一次 write()， 落进内核缓冲，于是它排在后面那句 write("Ciao\n") 前面 —— 和原书在终端上看到的顺序一致。 注意：终端是行缓冲（靠 \n 触发），而这里是无缓冲，机制不同、观察面相同。

Q8：fork() 之后，子进程除了 stdio 缓冲之外还"继承"了哪些危险状态？

A：凡是住在用户态里的缓存都有一份副本。典型： 你自己实现的"攒够 N 条再发"的行情缓冲、日志缓冲、 rand() / 伪随机数的内部状态、数据库连接池里的半成品请求、 内存分配器里的空闲链表视图。 ⇒ fork() 之后必须假设所有用户态缓存都是过期的。

  2. _exit() 之后，没 flush 的输出就是垃圾。 实测（c25_exit_handler_no_return 情形 A）：两行 printf 的输出彻底消失。 ⇒ 可能走 _exit() / abort() 的代码路径上，用 write(2) 或 fprintf(stderr, ...) 记录现场。
  3. exit handler 完全是 glibc 用户态机制，内核一无所知（kernel/exit.c 里 没有任何相关代码）。这直接解释了为什么"被信号杀死时 handler 不跑"。
  4. ⭐ 原书一处数字勘误： sysconf(_SC_ATEXIT_MAX) 原书写 2,147,482,647， 实测是 2,147,483,647（0x7fffffff = INT_MAX）。 原书自己那句括号里的解释（"the maximum signed 32-bit integer"）才是对的。
  5. handler 里再注册 handler ⇒ 插到剩余待调列表的队首（下一个就跑）。 实测顺序 C → B → D → A。机制在 cxa_atexit.c:104-131 + exit.c:113-116 的 goto restart。
  6. fork() 复制的是"整个用户态地址空间"，而 stdio 缓冲恰好住在里面。 ⇒ 重复输出不是 bug。真正的规则是：任何"住在用户态里的缓存"在 fork() 之后都有一份副本 —— 不只 stdio，还有你自己攒的行情缓冲、日志缓冲。
  7. 一条通用准则：一个程序里只该有一个进程用 exit() 收场（通常是父进程）， 其余用 _exit()。 这保证 handler 只跑一次、缓冲只 flush 一次。
  8. _BSD_SOURCE 在 glibc 2.39 已弃用（实测编译报警， include/features.h:196），但仍然有效 —— 报警后会自动定义成 _DEFAULT_SOURCE。 新代码直接用 _DEFAULT_SOURCE。

代码自测（Q&A）

Q1：exit() 和 _exit() 的差别，一句话说清？

A：exit() = _exit() + ① 逆序跑 exit handler + ② flush stdio 缓冲。 _exit() 只做第 ③ 步。所以：handler 不跑、缓冲不 flush 的路径， 一定是走了 _exit()（或者被信号杀死）。

Q2：§25.2 那十条清理动作，被 SIGKILL 杀掉时会执行吗？

A：会。 原书写的是 "During both normal and abnormal termination of a process, the following actions occur" —— 这十条是 do_exit() 里的内核动作。 被信号杀掉不执行的只有用户态那三件事（handler / flush / _exit() 的返回值语义）。

Q3：atexit() 注册的 handler，怎么"注销"？

A：注销不了。原书给的标准做法是全局 flag： handler 里先检查 flag，要禁用就清 flag 并直接 return。

Q4：handler 里调 exit() 会怎样？

A：Linux 上剩下的 handler 照常跑、flush 照常发生（实测情形 B，父进程拿到 9）。 但 SUSv3 说这是 UB，原书明确警告某些系统会无限递归到栈溢出 （"Portably applications should avoid calling exit() inside an exit handler."）。

Q5：原书说"更一般的原则"是什么？

A："in an application that creates child processes, typically only one of the processes (most often the parent) should terminate via exit(), while the other processes should terminate via _exit()." 目的是只让一处跑 handler、只让一处 flush。

Q6：fork_stdio_buf 重定向到文件时输出三行，为什么？

A：printf 的 "Hello world\n" 在块缓冲下还留在用户态缓冲里，fork() 连缓冲一起复制， 父子各 exit() 各 flush 一次 ⇒ 出现两遍； write 的 "Ciao\n" 直接进内核缓冲、不被 fork 复制 ⇒ 只出现一遍， 而且因为它立刻可见、printf 要等 exit() 才可见 ⇒ 它排在前面。

Q7：本章最大的"意外收获"是什么？

A：原书一处数字勘误。 原书 p.535 说 sysconf(_SC_ATEXIT_MAX) 返回 2,147,482,647，实测是 2,147,483,647（0x7fffffff = INT_MAX）。 原书同一句里"i.e., the maximum signed 32-bit integer"的解释才是对的。 ⇒ 凡是原书里出现的"具体数字"，都应该实测一遍。

Q8：为什么说"exit handler 是纯用户态机制"这件事很重要？

A：因为它一次性解释了三条现象： ① 被信号杀死时 handler 不跑（内核直接进 do_exit()，glibc 没机会介入）； ② exec() 会清掉注册（handler 是代码，代码被换掉了）； ③ fork() 会得到一份副本（注册表是用户态数据，被 COW 复制）。 三条现象是同一个事实的三个面。

Q9：本章最该带走的"工程准则"是哪一条？

A："一个程序里只该有一个进程用 exit() 收场" —— 以及它的直接推论：凡是可能走 _exit() / abort() / 被信号杀死的代码路径， 不要用 printf 记录现场（实测：那两行输出会彻底消失）。

题目原文（书 p.539）

原书 §25.6 的全部内容就是这一题：

"25-1. If a child process makes the call exit(–1), what exit status (as returned by WEXITSTATUS()) will be seen by the parent?"

⚠️ 两个值得注意的细节：

  1. 这是本章唯一的习题，而 TLPI 其他章的习题动辄 5–8 题。这与本章"最短一章"的定位一致。
  2. 原书没有给答案。 TLPI 的习题解答是单独一本（The Linux Programming Interface: Exercise Solutions），本节用的 ex25_1_exit_minus_one.c 是本仓库自写的。

答案

255

不是 −1，不是 65535，也不是 256。

为什么： 原书 §25.1（书 p.532）已经给了规则 —— "only the lowest 8 bits of the status are made available to the parent process." −1 的二进制是全 1，取低 8 位得 0xFF = 255。

但光知道"低 8 位"还不够，因为你会立刻遇到第二个疑问： 父进程 wait() 拿到的那个数，为什么是 65280 而不是 255？ 这就必须把 wait status 的编码搞清楚 —— 见下面第 3 节。

1. 一次把 16 个边界值全测掉

题目只问 −1，但"低 8 位"这条规则的边界分布在 0 / 127 / 128 / 255 / 256 / 257 / 300 / 511 这些点上， 而且负数和被信号杀死这两类容易被混为一谈。 所以本程序把一整排值都跑一遍。

     "25-1. If a child process makes the call exit(-1), what exit status
      (as returned by WEXITSTATUS()) will be seen by the parent?"

   答案：**255**。

   为什么不是 -1 也不是 65535：

#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

/* 故意跨过 0/127/128/255/256/257 这些边界，两侧都取值 */
static const int STATUSES[] = {
    -1, -2, -256, -1000,
    0, 1, 2, 127, 128, 255, 256, 257, 300, 511, 1000, 65535,
};
#define N_STATUS (sizeof(STATUSES) / sizeof(STATUSES[0]))

static void
showStatus(int st, int status)
{
    printf("  exit(%-6d)  内核记的 status = %-6d (0x%04x)   "
           "WIFEXITED=%d  WEXITSTATUS=%-3d   (st & 0xff) = %d\n",
            st, status, (unsigned) status,
            WIFEXITED(status) ? 1 : 0,
            WIFEXITED(status) ? WEXITSTATUS(status) : -1,
            st & 0xff);
}

{

    /* 关掉 stdio 缓冲：本程序要 fork，但父进程从 printf 自己的报表都在
       fork 之后，关缓冲可以彻底排除「父子各持一份缓冲」这个干扰 */
    setvbuf(stdout, NULL, _IONBF, 0);

    for (i = 0; i < (int) N_STATUS; i++) {
        int st = STATUSES[i];
        pid_t pid;
        int status;

        pid = fork();

            printf("  fork 失败（第 %d 个）\n", i);
            return EXIT_FAILURE;

        if (pid == 0) {
            exit(st);            /* 题目里的写法：exit()，不是 _exit() */
            /* 不会到这里 */
        }
        if (waitpid(pid, &status, 0) == -1) {
            printf("  waitpid 失败\n");
            return EXIT_FAILURE;
        }
        showStatus(st, status);
    }

    printf("\n=== 对照：子进程被信号杀死时，低 8 位不是退出码 ===\n");
    {
        pid_t pid = fork();
        int status;

        if (pid == 0) {
            raise(SIGSEGV);      /* 默认动作：终止 + core */
            _exit(0);
        }
        if (waitpid(pid, &status, 0) == -1) {
            printf("  waitpid 失败\n");
            return EXIT_FAILURE;
        }
        printf("  raise(SIGSEGV)  status = %d (0x%04x)   "
               "WIFSIGNALED=%d  WTERMSIG=%d  WCOREDUMP=%d\n",
                status, (unsigned) status,
                WIFSIGNALED(status) ? 1 : 0,
                WIFSIGNALED(status) ? WTERMSIG(status) : -1,
                WCOREDUMP(status) ? 1 : 0);
        printf("  WIFEXITED=%d   WEXITSTATUS(原样) = %d —— 无意义，别读它\n",
                WIFEXITED(status) ? 1 : 0,
                WEXITSTATUS(status));

    }

    printf("\n⭐ 习题 25-1 的答案：exit(-1) ⇒ 父进程 WEXITSTATUS() = 255\n");

}

300 44 11264 0x2c00 44
511 255 65280 0xff00 255
1000 232 59392 0xe800 232
65535 255 65280 0xff00 255

逐条解读

① 右侧两列永远相等 —— WEXITSTATUS(status) 恒等于 n & 0xff。 这正是"父进程取状态那一刻做截断"这个印象的来源， 但真正的截断点还要更早（第 3 节）。

② 好几个不同的输入吃到同一个输出：

输入 WEXITSTATUS 说明
-1 / 255 / 511 / 65535 255 低 8 位都是 0xff
0 / -256 / 256 0 低 8 位都是 0x00
-2 254 与 254 等价
-1000 24 -1000 & 0xff = 0x18
257 / 1 1

⚠️ 这是"退出码不够用"的直接证据：exit(-1)、exit(255)、exit(511)、 exit(65535) 在父进程看来完全无法区分。 ⇒ 不要用退出码传递超出 8 位的信息（比如"错误码 + 模块号 + 行号"）。

③ exit(-1000) ⇒ 24 这一行最反直觉。 -1000 的两补码是 0xFFFFFC18， 低 8 位是 0x18 = 24；然后左移 8 位得 0x1800 = 6144。 ⇒ 负数和正数走的是同一条"取低位"规则，没有什么"负数特殊处理"。

④ exit(300) ⇒ 44 —— 300 = 0x12C，低 8 位 0x2C = 44。 ⇒ 超过 255 的数不是"截成 255"，而是按位取低 8 位。

3. ⭐ 为什么 status 是 65280 而不是 255 —— 编码揭秘

这是本题真正的考点。父进程 wait() 拿到的那个 int status 不是退出码本身， 而是一个把三样东西打包在一起的 wait status：

位 含义
第 0–6 位 信号号（被信号杀死时有效；正常退出时是 0）
第 7 位（0x80） core dump 标志（本轮实测有 core 时置 1）
第 8–15 位 退出码（正常退出时有效）

所以对一个正常退出的进程，status = exit_code << 8：

exit(-1)  ⇒  低 8 位 = 0xff  ⇒  status = 0xff << 8 = 0xff00 = 65280
WEXITSTATUS(65280) = (65280 >> 8) & 0xff = 0xff = 255   ✓

"取低 8 位 + 左移 8 位"这两步都在系统调用入口完成， 在内核源码里可以逐行对上（Linux v6.6 kernel/exit.c）：

/* kernel/exit.c:989-992 —— 单线程退出 */
SYSCALL_DEFINE1(exit, int, error_code)
{
    do_exit((error_code&0xff)<<8);
}

/* kernel/exit.c:1033-1037 —— 整个线程组退出（glibc 的 _exit() 走这条） */
SYSCALL_DEFINE1(exit_group, int, error_code)
{
    do_group_exit((error_code & 0xff) << 8);
    /* NOTREACHED */
    return 0;
}

然后这个已经编码好的值被存进 task_struct：

/* kernel/exit.c:858 */
    tsk->exit_code = code;

父进程取的时候直接搬走、不再做任何变换：

/* kernel/exit.c:1193-1195，wait_task_zombie() */
    status = (p->signal->flags & SIGNAL_GROUP_EXIT)
        ? p->signal->group_exit_code : p->exit_code;
    wo->wo_stat = status;

⇒ ⭐ 一个常见误解："低 8 位截断发生在 WEXITSTATUS() 里"。 不对。 WEXITSTATUS 只是"从第 8–15 位取出来"， 真正的 & 0xff 发生在子进程调 exit() 的那一刻（系统调用入口）。 如果截断发生在读取端，那么 exit(256) 应该和 exit(0) 在内核里存不同的值 —— 但实测两者都是 status = 0，说明内核里存的就已经是 0 了。

4. 对照：被信号杀死时，低 8 位不是退出码

程序最后跑了一次 raise(SIGSEGV) 作对照：

  raise(SIGSEGV)  status = 139 (0x008b)   WIFSIGNALED=1  WTERMSIG=11  WCOREDUMP=1
  WIFEXITED=0   WEXITSTATUS(原样) = 0 —— 无意义，别读它

拆开 139 = 0x008b：

位段 值 含义
第 0–6 位 0x0b = 11 信号号 = SIGSEGV
第 7 位 0x80 = 1 core dump 标志置位
第 8–15 位 0x00 没有退出码（不是正常退出）

⭐ 三条要点：

  1. 必须先判 WIFEXITED / WIFSIGNALED，再决定用哪个宏取数。 对一个被信号杀死的进程调 WEXITSTATUS() 拿到的是垃圾（实测返回 0）。 ⇒ 正确写法：if (WIFEXITED(status)) code = WEXITSTATUS(status);
  2. 139 = 128 + 11 就是 shell 里 $? 的由来。 shell 用 "正常退出 ⇒ $? = 退出码"、"被信号杀死 ⇒ $? = 128 + 信号号"的统一规则。
  3. ⚠️ 由此产生一个无法消除的歧义：exit(128 + n) 与"被信号 n 杀死" 在 shell 层面完全一样。原书 §25.1（书 p.532）原话：

"…this is one reason why a value greater than 128 should not be used as an exit status, since it can be confused with a process being killed by a signal."

⇒ 约定：正常的退出码取 0–127。 128 及以上留给"被信号杀死"。

关于 WCOREDUMP = 1 的一个提醒（与 Ch24 的发现呼应）： 本环境 RLIMIT_CORE 是 soft=0 hard=0（probe25 实测）， 磁盘上并没有 core 文件。WCOREDUMP 置位只表示"内核走完了 coredump 流程"， 不等于"有 core 文件"。详见 Ch24 §24.7 的 ex24_3_core_dump。

6. 常见坑

  1. exit() 的状态码只走 0–255。 传 -1 会得到 255；传 65535 也是 255。 想让父进程区分 4 种以上状态，就把它们映射到 0–127 的几个值上。
  2. 不要用 128 以上的退出码（原书明确建议）。exit(139) 与 SIGSEGV 致死在 shell 层面无法区分。
  3. WEXITSTATUS() / WTERMSIG() 不能盲用，先判 WIFEXITED / WIFSIGNALED。
  4. status 是 int，但只有低 16 位有意义。 别把它当成"退出码"直接比较， 要比较退出码就 WEXITSTATUS(status) == 3。
  5. exit(-1) 的正确读法：-1 在 C 里是 int，两补码 0xFFFFFFFF， 低 8 位 0xFF ⇒ 255。不是"负数变 255"，而是"按位取低 8 位"。
  6. status 的高 16 位可能是垃圾（内核只填低 16 位）， 所以 status == 0x12340000 这种比较没有意义。
  7. glibc 的 exit() 走 exit_group，不是 exit。 这也是为什么 "一个线程调 exit()"会终止整个进程（而不是只结束那个线程）—— 单线程退出要用 pthread_exit()（Ch33）。

7. HFT / 嵌入式关联

① 8 位的退出码是一份非常廉价的"故障分类字典"。 在低延迟系统里，重启是常规操作，"为什么重启"比"重启了"重要得多。 把常见故障映射到 0–127 的固定值上（比如 0 = 正常、10 = 配置错、20 = 对端断连、 30 = 内部断言、40 = 风控拒单、50 = 依赖超时）， supervisor 侧只需要读 8 位就能分类告警。

⚠️ 但要注意 exit(255) 与 exit(-1) 无法区分，所以： - 别用 255 做"未分类错误"（会和 -1 撞车）； - 别用 128–255 这一整段（会和"被信号杀死"撞车，原书建议）。

② "被信号杀死"是 HFT 进程最常见的死法之一（OOM killer / watchdog / kill -9）， 所以退出码分析必须同时看 WIFEXITED 与 WIFSIGNALED：

判据 含义 该怎么办
WIFEXITED && WEXITSTATUS == 0 正常退出 正常
WIFEXITED && WEXITSTATUS != 0 自己报的错 查字典
WIFSIGNALED && WTERMSIG == 9 被 SIGKILL 看 dmesg 有无 OOM；看是不是 watchdog
WIFSIGNALED && WTERMSIG == 6 SIGABRT（abort()） 内部断言失败，要看 core / backtrace
WIFSIGNALED && WTERMSIG == 11 SIGSEGV 内存错误，要看 core

⇒ 只记 $? 的 shell 脚本会漏掉第 3–5 行（因为 $? 把它们混成 137 / 134 / 139）。

③ 嵌入式里"退出码"常被用来做"启动级别"的信号。 一个 init 脚本根据前一次退出的码决定"要不要进安全模式"。 由于只有 8 位，一定要写死一张映射表并注释在源码里， 否则半年后没人知道 exit(42) 是什么意思。

④ 调试上的直接收益：知道"低 8 位在系统调用入口就被截"这件事， 就能立刻回答"为什么我用 exit(-1) 记录的错误码在日志里变成 255"。 这个坑在嵌入式里很常见（错误码用负数表示的代码风格 + exit() 路径）。

代码自测（Q&A）

Q1：习题 25-1 的答案是多少？

A：255。 exit(-1) 的 -1 低 8 位是 0xFF = 255， 父进程 WEXITSTATUS() 拿到 255。

Q2：父进程 wait() 拿到的 status 为什么是 65280（0xff00）而不是 255？

A：因为 status 不是退出码本身，而是一个打包结构： 低 7 位是信号号、第 7 位是 core 标志、第 8–15 位才是退出码。 所以正常退出时 status = 退出码 << 8。0xff << 8 = 0xff00 = 65280。

Q3：& 0xff 这一步到底在哪里发生？

A：在系统调用入口。Linux v6.6 kernel/exit.c:989-992（exit）和 1033-1037（exit_group，glibc _exit() 走的这条）都是 do_exit((error_code & 0xff) << 8) —— 先取低 8 位、再左移 8 位。 父进程取状态时（kernel/exit.c:1193-1195）不再做任何变换，直接搬走。 ⇒ "截断发生在读取端"是常见误解。证据：exit(256) 与 exit(0) 在内核里存的都是 0。

Q4：exit(255)、exit(-1)、exit(511)、exit(65535) 能被区分吗？

A：不能。 四者的低 8 位都是 0xff，父进程看到的 status 都是 65280。 实测表格里它们在同一行水平上完全一致。

Q5：子进程被 SIGSEGV 杀死，status 是多少？怎么读？

A：实测 139（0x008b）。拆开：低 7 位 0x0b = 11 是 SIGSEGV、 第 7 位 0x80 是 core 标志、第 8–15 位是 0（没有退出码）。 ⇒ 必须先 WIFSIGNALED(status) 为真，再用 WTERMSIG(status) 取 11。 对这样的 status 调 WEXITSTATUS() 拿到的是垃圾（实测返回 0）。

Q6：为什么原书建议不要用大于 128 的退出码？

A：因为 shell 里 $? 的统一规则是"被信号 n 杀死 ⇒ $? = 128 + n"。 所以 exit(139) 和"被 SIGSEGV（11）杀死"在 shell 层面完全无法区分。 ⇒ 正常退出码约定用 0–127。

Q7：WCOREDUMP(status) 返回 1 就说明磁盘上有 core 文件吗？

A：不一定。 WCOREDUMP() 是位掩码 status & 0x80（只能取 0 或 128）， 它只表示"内核走完了 coredump 流程"。 本环境 RLIMIT_CORE 是 soft=0 hard=0（probe25 实测）， 磁盘上没有 core 文件。详见 Ch24 的 ex24_3_core_dump。

Q8：glibc 的 exit() 走的是 exit 还是 exit_group？为什么重要？

A：走 exit_group。这解释了一个常见困惑：在任何一个线程里调 exit()， 整个进程都会结束（不是只结束那个线程）—— 因为 exit_group 的语义就是"干掉整个线程组" （kernel/exit.c:1028-1031 的注释："this kills every thread in the thread group"）。 要多线程里只结束一个线程，得用 pthread_exit()（Ch33）。
