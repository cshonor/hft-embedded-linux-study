章节目标

本章只回答一个问题：内核把什么东西打包成了一个「进程」。拆成四层看：

  1. 身份：PID / PPID / PGID / SID，以及为什么 getpid() 和 gettid() 在多线程下返回不同的值。（6.1 / 6.2）
  2. 地盘：虚拟地址空间怎么切（text / rodata / data / bss / heap / stack），每一段的边界在内核里由哪个字段记。（6.3 / 6.4 / 6.5）
  3. 初始数据：argv 和 environ 这两块数据从哪来、谁复制、谁能改、改完影响谁。（6.6 / 6.7）
  4. 控制流：setjmp / longjmp 跨越栈帧跳转，以及为什么它跟 volatile 绑在一起。（6.8）

⚠️ 本章不含 fork() / execve() 正文。进程的分裂与替换在 Ch24–28。本章讲的是「被 fork 出来的那个东西长什么样」。

易错清单

  1. argv[argc] 一定是 NULL，不是「可能」——它是标准保证的循环终止条件。
  2. 显式写 = 0 的全局变量进 BSS，不是 DATA。判据是「初值是否为零常量」，不是「有没有写 =」。
  3. BSS 在磁盘上的可执行文件里几乎不占空间（只占一个大小字段），加载后分配并清零。
  4. getenv() 返回的指针不要 free()，也不要写——它直接指向 environ 里的字符串。
  5. putenv() 不复制字符串。传局部栈数组 → 函数返回后 environ 里就是悬垂指针；悬垂之后 getenv 往往还能命中，这才是最危险的地方。
  6. setenv(..., overwrite=0) 不覆盖已有值，putenv 则无条件覆盖。两者语义不同。
  7. getenv() 返回空串 ≠ 返回 NULL：PATH= 是「存在但值为空」，NULL 才是「不存在」。
  8. setjmp 之后的非 volatile 局部变量，longjmp 回来可能被回滚（-O2 下实测会）。要跨跳转存活的局部变量必须 volatile。
  9. longjmp(env, 0) 实际返回 1——val == 0 被强制成 1（setjmp/longjmp.c:41 的 val ?: 1）。
  10. longjmp 不恢复自动变量的值，也不回滚堆；它只恢复寄存器 + 栈指针。
  11. 栈溢出不是「可检查的返回错误」，是 SIGSEGV——保护页挡住在前一页，进程直接死。
  12. 用 environ，别依赖 main 的第三个参数 envp——POSIX 没规定，用 environ 才可移植。
  13. 本章没有 fork / exec；别和 Ch24–27 混章。demos 里出现的 fork 只是为了造场景（造孤儿、改 argv[0]），不是本章的教学目标。

6.1

进程基本概念：程序、进程与内核的两块账本

源码核验：Linux v6.6 · include/linux/sched.h:743（struct task_struct，CONFIG_THREAD_INFO_IN_TASK 下 thread_info 内嵌为首成员） 本章：TLPI 第 06 章 — Processes - 上一节：本章首页 - 下一节：6.2 PID 与 PPID

本节讲什么

程序（program）是磁盘上的静态可执行文件；进程（process）是它被加载进内存、正在执行的动态实例。同一个程序可以有好几个进程，彼此互不影响。

内核眼里的一个进程 = 两块账本：

  1. 用户空间内存：代码、已初始化数据、未初始化数据、堆、栈（下一节 6.3 逐段拆）；
  2. 内核态描述符 PCB：Linux 里就是 struct task_struct——PID、父指针、fd 表、信号掩码、资源限制、调度信息全在里面。

进程不是"程序在跑"这么模糊的说法，而是内核用 task_struct 记账、用一块独立地址空间当沙盒的一个对象。

要点

程序 进程
存在形态 磁盘上的 ELF 文件（静态） 内存中的执行实例（动态）
数量关系 一份 可同时有多份（各自独立）
内核里的对应物 无 struct task_struct
生命周期 直到被删除 fork 诞生 → 退出回收

内核为进程记的账（挑几个字段对应成你能验证的东西）

task_struct / mm 里的东西 用户态怎么看到
pid / tgid getpid()、/proc/[pid]
real_parent getppid()
files_struct（fd 表） 0/1/2、/proc/[pid]/fd/
signal_struct（信号处置/掩码） /proc/[pid]/status 的 Sig* 行
mm_struct（地址空间） /proc/[pid]/maps
signal->rlim[]（资源限制） getrlimit()、ulimit -a

一句话：你在用户态敲的每个 getpid() / getrlimit()，本质都是从 task_struct 里读一个字段。

代码

完整程序见 ../code/c6_1_process_ctx.c，它把上面那张表逐行打出来：

/* c6_1_process_ctx.c — 6.1 进程 = 内核管理的执行上下文（资源容器视角）
 * 编译: gcc -O2 -Wall -Wextra -o c6_1_process_ctx c6_1_process_ctx.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/resource.h>

int main(void)
{
    /* 身份：内核 task_struct 里的第一组字段 */
    printf("PID  = %d\n", (int)getpid());
    printf("PPID = %d\n", (int)getppid());
    printf("PGID = %d   (进程组)\n", (int)getpgrp());
    printf("SID  = %d   (会话)\n", (int)getsid(0));
    printf("UID=%d EUID=%d  GID=%d EGID=%d\n",
           (int)getuid(), (int)geteuid(), (int)getgid(), (int)getegid());

    /* 资源二：fd 表（内核替你维护的打开文件表） */
    printf("fd 表: stdin=%d stdout=%d stderr=%d\n",
           STDIN_FILENO, STDOUT_FILENO, STDERR_FILENO);

    /* 资源三：资源限制（rlimit，进程属性） */
    struct rlimit rl;
    if (getrlimit(RLIMIT_NOFILE, &rl) == 0)
        printf("RLIMIT_NOFILE: cur=%lu  max=%lu\n",
               (unsigned long)rl.rlim_cur, (unsigned long)rl.rlim_max);
    if (getrlimit(RLIMIT_STACK, &rl) == 0)
        printf("RLIMIT_STACK : cur=%lu MB\n",
               (unsigned long)(rl.rlim_cur / 1024 / 1024));
    return 0;
}

解读：

  • stdin/stdout/stderr = 0/1/2 不是规定死的，而是约定——进程一诞生，内核就替它打开这三个 fd。这也是为什么 6.1 说"fd 表是进程的私有资源"：换一个进程，012 背后可能是完全不同的文件。
  • RLIMIT_NOFILE = 100 是容器给的值，你本机跑大概率是 1024 或 1048576。这正是"限制不能硬编码"的现场证据（Ch11 会专门讲怎么查）。
  • RLIMIT_STACK = 8 MB 与 6.5 爆栈深度直接挂钩（8 MB ÷ 每帧字节数）。
  • 沙箱里 PID=2 / PPID=1 是容器 PID 命名空间造成的，不要把它当成"PID 从 2 开始"的规律；本机跑通常是几百到几万。

HFT / 嵌入式关联

路线 要点
嵌入式 没有 MMU 的 RTOS 里"进程"这个抽象很薄，往往只有一个地址空间；Linux 上则是靠 mm_struct 硬隔离。移植代码时，凡是依赖"每个进程独立 fd 表"的假设都要先确认目标平台

HFT RLIMIT_NOFILE 决定你能同时开多少行情连接；上线前必须显式 setrlimit + 留够余量，别用默认值

自测题

题目 1： getpid() 返回的到底是什么？多线程程序里它和安全意义上的"线程 ID"是一回事吗？

参考答案

不是。glibc 的 getpid() 走内核 SYSCALL_DEFINE0(getpid)（kernel/sys.c:958），返回 task_tgid_vnr(current) —— TGID，即线程组 ID。同一进程的所有线程 getpid() 返回同一个值（因为 tgid 相同）。要拿内核内部意义上的线程号，得用 gettid()（:964，返回 task_pid_vnr(current)，即 task_struct.pid）。6.2 会展开这张"两个 PID"的对照表。

题目 2： 为什么说"程序是静态的，进程是动态的"？磁盘上的 ELF 里有 task_struct 吗？

参考答案

ELF 里只有代码、数据、符号表等内容，没有任何运行时状态；task_struct 是内核在 fork 时分配、在运行过程中不断变化的运行时数据结构。同一个 ELF 被加载两次就是两个互不相干的进程，各自有独立的 PID、fd 表、地址空间。

题目 3： 上面实测里 RLIMIT_NOFILE = 100，如果程序要开 200 个行情连接，会发生什么？怎么提前发现？

参考答案

第 101 个 socket() / open() 会返回 -1 并置 errno = EMFILE（进程级 fd 用尽；若是系统级则 ENFILE）。提前发现的办法就是在启动时 getrlimit(RLIMIT_NOFILE, ...) 读一次并与需求比对，或直接 setrlimit 抬高上限（上限不超过 rlim_max）。Ch11 专门讲这套查询 API，Ch36 讲 rlimit 的修改。

PID 与 PPID：两个 PID，和孤儿是怎么被收养的

源码核验：Linux v6.6 · kernel/sys.c:958（SYSCALL_DEFINE0(getpid)）· :964（gettid）· :975（SYSCALL_DEFINE0(getppid)）· include/linux/sched.h:1584（task_pid_vnr）· :1636（task_tgid_vnr） 本章：TLPI 第 06 章 — Processes - 上一节：6.1 进程基本概念 - 下一节：6.3 进程虚拟地址空间

本节讲什么

进程的第一个身份标识是 PID，第二个是 PPID（父进程 PID）。这一节要钉死三件事：

  1. 内核里其实有两个"PID"：task_struct.pid（线程号）和 task_struct.tgid（进程号）。getpid() 返回的是 tgid，不是 pid。
  2. getpid / getppid 永不失败——源码里连 -1 都没有，不需要判错。
  3. 父进程先退出，子进程的 PPID 会被内核改写（"孤儿收养"），这是可观测的。

要点

API 与返回值

#include <unistd.h>
pid_t getpid(void);    /* 返回 TGID（线程组 ID）；绝不失败 */
pid_t getppid(void);   /* 返回父进程的 TGID；绝不失败 */
pid_t gettid(void);    /* Linux 专有：返回内核内部线程号（task_struct.pid） */

内核源码：两个 PID 到底差在哪

/* kernel/sys.c (v6.6) —— 注释原文："SMP safe as current->tgid does not change" */
SYSCALL_DEFINE0(getpid)                        /* :958 */
{
    return task_tgid_vnr(current);         /* :960  -> 返回 TGID */
}

/* Thread ID - the internal kernel "pid" */
SYSCALL_DEFINE0(gettid)                        /* :964 */
{
    return task_pid_vnr(current);          /* :966  -> 返回 task_struct.pid */
}

SYSCALL_DEFINE0(getppid)                       /* :975 */
{
    int pid;

    rcu_read_lock();                       /* :979 */
    pid = task_tgid_vnr(rcu_dereference(current->real_parent));   /* :980 */
    rcu_read_unlock();                     /* :981 */

    return pid;
}
名字 取的字段 相同进程内多线程时
getpid() / task_tgid_vnr() task_struct.tgid 所有线程相同
gettid() / task_pid_vnr() task_struct.pid 每个线程不同
getppid() real_parent 的 tgid 所有线程相同

⚠️ getppid 这里有个容易忽略的点：源码注释（:969-973）明确写着 ->real_parent 的读取不是 SMP 安全的，必须用 rcu_read_lock() 包着、且只能接受"可能过期"的值。这解释了为什么 6.2 结尾的现象是"父进程刚退出时 getppid() 可能还返回旧值一瞬"——不是 bug，是内核刻意的取舍。

PPID 的四种取值

场景 getppid() 得到什么
常规 创建它的那个进程的 TGID
父进程已退出（孤儿） 1（被 init/systemd 收养），现代发行版也可能是某个 subreaper
调用者是 init/systemd（PID 1） 0（它没有父）
容器里 还是容器 PID 命名空间内的号，不是宿主机的号

进程组的两个配套函数

getpgrp() / getsid(0) 分别返回进程组 ID 和会话 ID——它们不是新概念，而是内核把"若干进程"分组管理用的 ID，详见 Ch34 进程组、会话与控制终端。

/* c6_2_pid_orphan.c — 6.2 PID/PPID、子进程回收、孤儿进程（PPID 被改写）
 * 编译: gcc -O2 -Wall -Wextra -o c6_2_pid_orphan c6_2_pid_orphan.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

static void say(const char *tag)
{
    printf("  [%-10s] pid=%-6d ppid=%-4d\n", tag, (int)getpid(), (int)getppid());
    fflush(stdout);   /* ⚠️ 子进程随后 _exit()，不 flush 的话这段输出会丢 */
}

int main(void)
{
    say("main");

    /* ---- A. 正常父子：子进程打印时父还活着 ---- */
    printf("--- A. fork 后父子各自的身份 ---\n");
    pid_t c = fork();
    if (c < 0) { perror("fork"); return 1; }
    if (c == 0) { say("child"); _exit(0); }

    int st = 0;
    pid_t w = wait(&st);
    printf("  wait 返回 %d（就是子进程 PID）；WIFEXITED=%d WEXITSTATUS=%d\n",
           (int)w, WIFEXITED(st), WEXITSTATUS(st));

    /* ---- B. 孤儿：让「中间父」先退，孙子的 PPID 被内核改写 ---- */
    printf("--- B. 中间父退出 -> 孙子变孤儿，PPID 被改写 ---\n");
    c = fork();
    if (c < 0) { perror("fork"); return 1; }
    if (c == 0) {
        pid_t g = fork();
        if (g < 0) _exit(1);
        if (g == 0) {                     /* 孙子 */
            sleep(1);                     /* 等中间父退出 */
            say("grandchild");
            printf("             ↑ 中间父已退出，PPID 不再是它，而是被 1 号进程收养\n");
            fflush(stdout);
            _exit(0);
        }
        _exit(0);                          /* 中间父立刻退出 -> 孙子成孤儿 */
    }
    wait(NULL);                            /* 只收得到中间父 */

    /* main 自己多活一会儿，等孙子把话说完（CE 沙箱里 main 一退就收走全部子进程） */
    sleep(2);
    printf("  [main      ] 收工（pid=%d）\n", (int)getpid());
    return 0;
}

解读（三个都值得记）：

  1. 孤儿收养的证据链：child 打印时 ppid=2（父活着，指 main）；grandchild 打印时 ppid=1——它的直接父（pid=4，那个"中间父"）已经退出，内核把它改挂到 1 号进程名下。这就是 getppid 源码里 rcu_dereference(current->real_parent) 读到的字段被改写的结果。
  2. wait() 只等得到直接子进程：wait 返回 3（A 段那个子进程），而对孙子完全无能为力——孙子不是 main 的孩子。这也是为什么"孤儿"在实现上没问题：它本来就不归你管了。
  3. ⚠️ 输出里 --- A. --- 出现了两次，不是打印错了：printf 的 stdout 在管道里是全缓冲的，fork() 会把尚未 flush 的缓冲区一并复制给子进程。子进程 fflush 时把自己那份（含父进程留下的 --- A. ---）刷了出来，父进程最后退出时又刷了一遍。这是 fork + stdio 最经典的坑，规避办法是 fork 前 fflush(NULL)，或子进程统一用 _exit + 显式 write(2)。

自测题

题目 1： 一个进程里三个线程各自调用 getpid()，返回值一样吗？gettid() 呢？

参考答案

getpid() 三个都一样——它是 task_tgid_vnr(current)（kernel/sys.c:960），读的是 tgid，同一线程组共享。gettid() 三个都不同——它是 task_pid_vnr(current)（:966），读的是 task_struct.pid，每个任务唯一。注意"线程"在 Linux 内核眼里就是一个 task_struct，所以有独立的 pid。

题目 2： 为什么 getpid() 永远不用检查返回值是不是 -1？

参考答案

因为它只是从 current（当前 task_struct）里读一个字段再换个命名空间，没有任何可能失败的操作——源码 kernel/sys.c:958-961 就是一行 return task_tgid_vnr(current);，没有错误分支。凡是没有失败路径的 syscall，包一层判 -1 是纯浪费。

题目 3： fork 之后子进程 printf 的内容有时会「重复打印两遍」，为什么？怎么避免？

参考答案

子进程 _exit() 不会 flush stdio 缓冲，而 fork() 会把父进程尚未 flush 的缓冲区内容复制一份给子进程。于是子进程刷一次、父进程退出时又刷一次，同一段文字出现两遍。避免办法：fork() 之前调用 fflush(NULL) 清空所有流；或者子进程里只用 write(2)（无缓冲）输出；或者子进程正常 exit()（会 flush，但可能把父进程的内容也带出来——所以首选 fflush(NULL)）。上面实测输出里 --- A. --- 出现两次就是这个现象。

6.3

进程虚拟地址空间：段落在哪，内核怎么记

源码核验：Linux v6.6 · include/linux/mm_types.h:673（struct mm_struct）· :807（arg_lock）· :809-811（各段界与 argv/env 指针） 本章：TLPI 第 06 章 — Processes - 上一节：6.2 PID 与 PPID - 下一节：6.4 虚拟内存管理

本节讲什么

每个进程有一套自己的虚拟地址空间，从低到高大致分五段：代码（text）、已初始化数据（data）、未初始化数据（bss）、堆（heap）、栈（stack）。这一节要钉死两件事：

  1. 每类变量落在哪一段——不是背结论，而是能用一个程序打印地址、再用 /proc/self/maps 交叉验证。
  2. 内核对这件事有精确记账：mm_struct 里成对存着 start_code/end_code、start_data/end_data、start_brk/brk、start_stack，argv 和 environ 也各有一对 arg_start/arg_end、env_start/env_end。

要点

经典布局（低 → 高）

高地址  ┌──────────────────────┐
        │  内核空间（用户不可访） │
        ├──────────────────────┤
        │  栈 stack ↓           │  局部变量、参数、返回地址；受 RLIMIT_STACK 限制
        ├──────────────────────┤
        │  mmap 区 / 共享库      │  libc、mmap 出来的大块内存
        ├──────────────────────┤
        │  堆 heap ↑            │  malloc；上界 = program break（Ch7）
        ├──────────────────────┤
        │  bss（未初始化数据）    │  加载时清零；磁盘映像里几乎不占空间
        ├──────────────────────┤
        │  data（已初始化数据）   │  显式初始化的全局/静态
        ├──────────────────────┤
低地址  │  text（代码段，只读）   │  指令；同程序多进程可共享同一份物理页
        └──────────────────────┘

内核的记账（mm_struct 里的字段）

/* include/linux/mm_types.h (v6.6) */
struct mm_struct {                                        /* :673 */
    struct {
        ...
        spinlock_t arg_lock; /* protect the below fields */   /* :807 */
        unsigned long start_code, end_code, start_data, end_data;   /* :809 */
        unsigned long start_brk, brk, start_stack;                  /* :810 */
        unsigned long arg_start, arg_end, env_start, env_end;       /* :811 */
        ...
    };

字段 对应哪一段 用户态怎么看到
start_code / end_code text /proc/[pid]/maps 的 r-xp 行
start_data / end_data data rw-p 行（与 bss 合并在同一个段里）
start_brk / brk 堆的起止 堆顶 = sbrk(0) 的返回值
start_stack 栈底（高地址端） /proc/[pid]/stat 第 28 字段
arg_start/env_start argv / environ 字符串 /proc/[pid]/cmdline、/proc/[pid]/environ

⚠️ 两个容易混的点：

  • bss 没有独立的 start/end 字段。它和 data 在同一个可读写段里，靠"文件映射大小 vs 内存大小"的差体现（/proc/[pid]/maps 里同一行的 offset 与设备号不同）。
  • arg_lock 保护的是后面那三行（注释原文 protect the below fields）——因为 arg_start/arg_end/env_start/env_end 会在 execve 装载新程序时被改写，而 /proc/[pid]/cmdline 的读取是另一个上下文，要加锁。

声明 落在

/* 落在只读数据段（.rodata）的字面量 */
const char *ro_lit = "hello";

/* .data：显式初始化 */

自测题

题目 1： static int x = 0; 落在 data 还是 bss？为什么？

参考答案

bss。C 标准要求静态存储期对象零初始化，编译器发现初值就是 0（或没写初值）时，就把它归到 bss——这样磁盘上的 ELF 不需要存这一串 0，内核在加载时统一清零即可。上面实测里 s_expl_zero 的地址与 g_zero/s_zero 同区，就是证据。

题目 2： 上面 maps 输出前 5 行都是同一个可执行文件的映射，为什么 text 那行是 r-xp 而 r--p 出现三次？

参考答案

同一条 ELF 被按"不同权限"拆成多个映射。第 1 行 r--p 是 ELF 头/程序头表；第 2 行 r-xp 是可执行的代码段（text）；第 3、4 行两块 r--p 是只读数据（.rodata、.eh_frame 等）；第 5 行 rw-p 是可读写数据（data + bss）。权限不同就必须分开映射——这也是"为什么改写字符串字面量会 SIGSEGV"的直接原因：那页是 r--。

题目 3： 既然 malloc 的内存"在堆上"，为什么实测里 heap = 0x24ed42a0 和 start_brk 附近不连续、反而离 libc 更近？

参考答案

因为 glibc 对大块分配（默认阈值 128 KB）不用 brk 抬堆顶，而是直接 mmap 一块匿名内存。0x24ed42a0 落在 [heap] 区间内说明这次是小块分配（走 brk），但它离 libc 的映射区比较近是因为这块堆本身是 mmap 分配的（现代内核在 CONFIG_... 下把 brk 也放在 mmap 区下方）。判据是看 maps：地址落在 [heap] 行内 = brk 堆；落在匿名 rw-p 无名字行 = mmap 出来的。Ch7 会实测这个阈值切换。

6.4

虚拟内存管理：地址是假的，物理页是欠着的

源码核验：Linux v6.6 · mm/memory.c:4067（do_anonymous_page）· :164（zero_pfn）· 详见 06-linux-mm 与 Ch49.7 匿名映射 本章：TLPI 第 06 章 — Processes - 上一节：6.3 进程虚拟地址空间 - 下一节：6.5 栈与栈帧

本节讲什么

6.3 说的是"地址排布"，这一节说的是这套地址是假的：你拿到的每一条虚拟地址都要经过页表翻译才落到物理页，而物理页是等到你第一次碰它才分配的（按需分页 / demand paging）。

这一节只钉一件事，但它是后续全部性能讨论的地基：

malloc 返回成功 ≠ 拿到物理内存。 地址空间是"记账"，物理页是"欠着"，首次访问才真的付。

要点

三件套：页表、MMU、缺页

概念 一句话
虚拟地址 进程看到并使用的地址，每个进程独立
页表 内核为每个进程维护的"虚拟页 → 物理页帧"映射表
MMU CPU 里的硬件，负责查页表做翻译
缺页异常（page fault） 访问的页还没装进页表时触发，内核介入补上再重试指令
按需分页 页的物理分配推迟到首次访问，不是 mmap/malloc 时
全局零页 内核里一个共享的只读全零物理页；读没写过的匿名页时大家指同一页，不占各自 RSS
swap 内存紧张时把页换到磁盘；被换出的页访问时再换入

关键区分：地址空间 ≠ 物理内存

动作 做了什么 RSS 变吗
malloc(128MB) glibc 用 mmap 登记一段 VMA（只记地址范围） 不变
读这段内存 每次读缺页都挂到全局零页 基本不变
写这段内存 首写才分配清零物理页 按写入量涨
mlock() 强制把页装进来并锁定 立刻涨

代码

完整程序见 ../code/c6_4_vm_demand.c：申请 128MB，然后在"未触碰 / 全量读 / 写一半"三个阶段分别查 /proc/self/statm 的常驻集。

/* c6_4_vm_demand.c — 6.4 虚拟内存：按需分页 / 零页 / RSS 只统计真碰过的页
 * 编译: gcc -O2 -Wall -Wextra -o c6_4_vm_demand c6_4_vm_demand.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>

#define MB (1024UL * 1024)

/* 用 /proc/self/statm 第 2 列拿常驻集（单位：页） */
static long rss_pages(void)
{
    int fd = open("/proc/self/statm", O_RDONLY);
    if (fd < 0) return -1;
    char b[128];
    ssize_t n = read(fd, b, sizeof b - 1);
    close(fd);
    if (n <= 0) return -1;
    b[n] = 0;
    long size = 0, resident = 0;
    sscanf(b, "%ld %ld", &size, &resident);
    return resident;
}

static void report(const char *tag, long base, long ps)
{
    long r = rss_pages();
    printf("  %-26s RSS = %6.1f MB  (%+.1f MB)\n",
           tag, (double)r * ps / MB, (double)(r - base) * ps / MB);
}

int main(void)
{
    long ps = sysconf(_SC_PAGESIZE);
    printf("页大小 = %ld B\n", ps);

    /* 1. malloc 128MB：只是登记 VMA，一个物理页都没给 */
    size_t sz = 128 * MB;
    char *p = malloc(sz);
    if (!p) { perror("malloc"); return 1; }
    long base = rss_pages();
    report("malloc(128MB) 后", base, ps);

    /* 2. 只读一遍：读缺页挂全局零页，RSS 纹丝不动 */
    long sum = 0;
    for (size_t i = 0; i < sz; i += (size_t)ps)
        sum += p[i];
    report("全量读一遍后", base, ps);

    /* 3. 写一半：首写才分配清零实页 */
    memset(p, 0x5A, sz / 2);
    report("写前一半后", base, ps);

    printf("  (读到的字节和 = %ld，证明页确实被访问过)\n", sum);
    free(p);
    return 0;
}

编译与运行：

gcc -O2 -Wall -Wextra -o c6_4_vm_demand c6_4_vm_demand.c && ./c6_4_vm_demand

实测输出（另在 Compiler Explorer 复核，gcc 13.3，4KB 页）：

页大小 = 4096 B
  malloc(128MB) 后          RSS =    1.6 MB  (+0.1 MB)
  全量读一遍后         RSS =    1.6 MB  (+0.2 MB)
  写前一半后            RSS =   65.6 MB  (+64.2 MB)
  (读到的字节和 = 0，证明页确实被访问过)

解读：

  • +0.1 MB：malloc 128 MB 后 RSS 几乎没动。内核只登记了一段 VMA，物理账上一页未付。
  • +0.2 MB：把 128 MB 逐页读了一遍（32768 次缺页！），RSS 仍然没涨。因为读缺页由内核用 do_anonymous_page()（mm/memory.c:4067）的零页分支满足——只装 PTE，指向那个全局只读零页（zero_pfn，:164）。零页不属于任何进程，连 RSS 都不计。
  • +64.2 MB：写前一半（64 MB）→ 恰好涨 64 MB。这才是真正分配：每个首写页分到一个清零的新物理页。
  • 读到的字节和 = 0 不是 bug：这 128 MB 从没写过，读出来当然全 0——正好反证"读的是零页"。

⚠️ 一个比"COW 复制零页"更精确的说法：首写匿名私有页时内核调的是 vma_alloc_zeroed_movable_folio() 直接分配清零页，并没有发生"从零页 memcpy"（目标本来就是全 0，清零更便宜）。"复制零页"只出现在 fork 之后的 wp_page_copy() 特判里。完整辨析见 Ch49.7。

HFT / 嵌入式关联

路线 要点
嵌入式 没有 swap、没有 overcommit 的裸机/RTOS 上，"申请即分配"是常态。从 Linux 移植过去时，凡依赖"按需分配"的内存估算都要重算
HFT 懒分配是确定性延迟的敌人：热路径上的首次访问会触发缺页 + 清零（还可能触发内存回收），延迟从 ns 级跳到 μs 级。标准做法是启动时 mlockall(MCL_CURRENT\|MCL_FUTURE) + 把热区全量触碰一遍（预热），把毛刺挤到开盘前
HFT 反过来，"申请 1TB 成功"和"物理耗尽 OOM"可以相隔任意久——overcommit 让 malloc 的返回值不能用作"内存够不够"的判据。要做容量规划必须看 /proc/meminfo 的 Committed_AS 与 MemAvailable
HFT 大页（huge pages）减少 TLB miss，但大页不享受零页优化（必须立刻分配），预热成本更高

自测题

题目 1： mmap 返回成功、也读到了全 0，物理内存分配了吗？

参考答案

对"被读过的那批页"来说没有。读路径的缺页由 do_anonymous_page():4086 用零页满足：只装 PTE，不分配物理页。零页是内核全局共享的只读页，连 RSS 都不计入（实测 A2 阶段 +0.2 MB 就是证据）。真正的物理分配推迟到首写。

题目 2： 上面实测中「全量读一遍 128MB」触发了 32768 次缺页，为什么 RSS 只涨了 0.2 MB？

参考答案

因为读缺页只需要装一条 PTE 指向全局零页，不需要分配物理页。涨的 0.2 MB 是零散的页表页（页表本身也要内存）和少量噪声，不是 128 MB 的数据页。这也是「缺页次数多 ≠ 内存占用高」的最好例证。

题目 3： 为什么说 malloc 成功不能作为"内存够用"的判据？

参考答案

因为默认的 overcommit 策略（heuristic）允许已登记的 VMA 总量超过 RAM + swap，分配只记账不付物理页。所以"申请 1TB 返回成功"和之后"写满时 OOM 被 kill"可以相隔任意久。要判断真实余量得看 /proc/meminfo 的 Committed_AS（已承诺量）与 MemAvailable（可用量），而不是看 malloc 的返回值。

6.5

栈与栈帧：272 字节一帧，30840 层就没了

源码核验：Linux v6.6 · RLIMIT_STACK 的落地在 mm/mmap.c（expand_downwards / guard gap）；本节数据由 CE 复核实测 本章：TLPI 第 06 章 — Processes - 上一节：6.4 虚拟内存管理 - 下一节：6.6 命令行参数 argv

本节讲什么

每次函数调用在栈上压一个栈帧（stack frame），装着返回地址、旧帧指针、局部变量、保存的寄存器。这一节把三个数字钉死（都来自实测）：

  1. 方向：x86-64 上栈向低地址增长；
  2. 每帧多大：这台的实测值是 272 字节/帧（取决于 padding 与编译器）；
  3. 多少层会死：8 MB ÷ 272 B ≈ 30840 层，超了就是 SIGSEGV，没有"优雅报错"。

要点

栈帧长什么样

高地址  │ 调用者的栈帧        │
        ├────────────────────┤
        │ 参数（第 7 个起）    │
        ├────────────────────┤
        │ 返回地址            │ ← call 指令压入
        ├────────────────────┤
        │ 保存的 rbp          │ ← 帧指针（-O0 下 rbp 指向这里）
        ├────────────────────┤
        │ 保存的被调用者寄存器 │  rbx / r12-r15
        ├────────────────────┤
        │ 局部变量            │  ← 含数组、padding
低地址  │ ...                │ ← rsp 指向栈顶

⚠️ 别把"栈帧 = 局部变量"当全部：返回地址和保存的寄存器也在里面，这解释了为什么"递归太深"和"局部大数组"是同一类炸栈原因。

栈 vs 堆

特性 栈 堆
分配方式 移动 rsp（一条指令） malloc 搜索空闲块 / 系统调用
释放 函数返回自动回收 手动 free
大小 受 RLIMIT_STACK 限制（默认 8 MB） 受虚拟地址空间 + 物理内存 + swap 限制
增长方向 向低地址 向高地址（brk）
碎片 无 有
多线程 每线程一个栈，大小可用 pthread_attr_setstacksize 设 进程内共享

栈溢出（stack overflow）的三条事实

  1. 内核给栈留了一段不可访问的 guard page；rsp 撞进去 → 硬件报页错误 → 内核送 SIGSEGV。
  2. 不是"分配失败"那种可检查的错误：没有返回值、没有 errno，直接是信号。
  3. gcc 能静态检出部分无限递归（-Winfinite-recursion），但检测不到"递归有限但太深"——那个只能靠跑。

代码

完整程序见 ../code/c6_5_stack_frame.c：先量方向与帧大小，再把"无上限递归"放进子进程看它怎么死。

/* c6_5_stack_frame.c — 6.5 栈与栈帧：方向、每帧字节数、栈上限、爆栈后果
 * 编译: gcc -O2 -Wall -Wextra -o c6_5_stack_frame c6_5_stack_frame.c
 * 说明: 递归函数里留 256B padding 并真实写它，防止被优化成尾调用/循环。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
#include <sys/resource.h>

#define PAD         256
#define SAFE_DEPTH  8000        /* 8000 × 272B ≈ 2.1MB，稳在 8MB 栈以内 */

static volatile long depth = 0;
static volatile long top1 = 0, top2 = 0;

/* 有深度上限：用来量每帧占用 */
static void recurse_safe(void)
{
    volatile char pad[PAD];
    pad[0] = (char)depth;                        /* 真实使用，防优化掉 */
    if (!top1) top1 = (long)&pad[0];
    else if (!top2) top2 = (long)&pad[0];

    depth++;
    if (depth < SAFE_DEPTH) recurse_safe();
    pad[PAD - 1] = 1;                            /* 递归调用后仍有代码 -> 不是尾调用 */
}

/* 无深度上限：制造爆栈 */
static void recurse_bomb(void)
{
    volatile char pad[PAD];
    pad[0] = (char)depth;
    depth++;
    recurse_bomb();
    pad[PAD - 1] = 1;
}

int main(void)
{
    /* ---- A. 栈增长方向 ---- */
    char a = 0, b = 0;
    char *hi = &a, *lo = &b;
    if (hi < lo) { char *t = hi; hi = lo; lo = t; }
    printf("A. 先声明的 %p > 后声明的 %p  ->  x86-64 栈向【低地址】增长\n",
           (void *)hi, (void *)lo);

    /* ---- B. 每帧字节数 ---- */
    top1 = top2 = 0; depth = 0;
    recurse_safe();
    long frame = top1 - top2;
    printf("B. 递归深度 %ld，相邻两层 pad[0] 相距 %ld B -> 每帧约 %ld B\n",
           depth, frame, frame);
    printf("   （8MB 栈 ÷ %ld B/帧 ≈ %ld 层就会耗尽）\n",
           frame, (8L * 1024 * 1024) / frame);

    /* ---- C. 栈上限 ---- */
    struct rlimit rl;
    getrlimit(RLIMIT_STACK, &rl);
    printf("C. RLIMIT_STACK = %lu MB（ulimit -s 改的就是它）\n",
           (unsigned long)(rl.rlim_cur / 1024 / 1024));

    /* ---- D. 爆栈后果：放进子进程，避免把自己搞死 ---- */
    pid_t c = fork();
    if (c == 0) { depth = 0; recurse_bomb(); _exit(0); }
    int st = 0;
    wait(&st);
    if (WIFSIGNALED(st))
        printf("D. 无上限递归的子进程：被信号 %d 杀死（%s）—— 栈溢出不是「优雅报错」，是直接 SIGSEGV\n",
               WTERMSIG(st), WTERMSIG(st) == SIGSEGV ? "SIGSEGV" : "其他");
    return 0;
}

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

B. 递归深度 8000，相邻两层 pad[0] 相距 272 B -> 每帧约 272 B
   （8MB 栈 ÷ 272 B/帧 ≈ 30840 层就会耗尽）
C. RLIMIT_STACK = 8 MB（ulimit -s 改的就是它）
D. 无上限递归的子进程：被信号 11 杀死（SIGSEGV）—— 栈溢出不是「优雅报错」，是直接 SIGSEGV

编译时 gcc 还顺带报了两条（这是有价值的信息，不是噪音）：

<source>:33:19: warning: variable 'pad' set but not used [-Wunused-but-set-variable]
<source>:31:13: warning: infinite recursion detected [-Winfinite-recursion]
<source>:36:5: note: recursive call

解读：

  1. 272 B/帧 是本程序的实测值，不是通用常数。它 = 256 B 的 pad 数组 + 保存的 rbp + 对齐填充。换编译器、换 -O 级别、改变量数量都会变——所以判断"会不会爆栈"必须量，不能猜。
  2. 30840 层是算出来的（8 MB ÷ 272 B），但它是上限估计：每层还要算上一次函数调用的开销、以及 main 自己的栈帧。实际能到 3 万上下；这个数量级对"用递归处理大数组"是致命的。
  3. SIGSEGV(11) 就是栈溢出的形态：子进程不是"返回错误"，而是被信号打死。父进程用 WIFSIGNALED + WTERMSIG 才看得出死因（如果用 WEXITSTATUS 会读出 0 这种假象）。
  4. -Winfinite-recursion 只在"编译器能证明必无限"时才报。把 if (depth < SAFE_DEPTH) 加上就不会报——但那个版本仍可能因为深度太大而爆栈。编译器管不了"太深"，只管"无限"。
  5. volatile char pad[PAD] 里的 volatile 与"递归调用后再写 pad"都是为了防优化：不加的话 gcc 会把它变成尾调用或循环，栈根本不涨，测出来的帧大小毫无意义（这是写栈相关微基准最容易翻车的地方）。

HFT / 嵌入式关联

路线 要点
嵌入式 线程/任务栈大小必须显式指定（pthread_attr_setstacksize、RTOS 的 task stack size）。FreeRTOS 这类系统通常只有几十 KB 栈，272 B/帧意味着 100 层就炸，所以嵌入式规范常禁止递归
HFT 热路径上的深递归是延迟不确定性的来源之一；更隐蔽的是大局部数组——char buf[1<<20] 一进函数就吃掉 1 MB 栈，几次嵌套就撞 guard page
HFT 多线程 HFT 程序里，每个线程栈默认 8 MB（pthread_attr 里可调）。开 64 个线程 = 理论上 512 MB 地址空间（物理页仍按需才分），但 guard page 撞上就是整个进程挂
HFT 想抓栈溢出用 -fstack-usage 看每函数静态栈用量，或用 ulimit -s unlimited 配合 -fstack-clash-protection 排查；线上别关 guard page

自测题

题目 1： 为什么"爆栈"不会返回错误码而是直接 SIGSEGV？

参考答案

因为栈的边界靠硬件页保护实现：内核在栈底留了一个 guard page（不可访问）。当 rsp 推进到 guard page 上并读写时，MMU 报页错误，内核的缺页处理发现"这是栈越界"（地址在 VMA 的 guard 区），无法合法扩展，于是送 SIGSEGV。整个过程没有"返回失败"的通道——它是异常，不是函数返回值。

题目 2： 上面程序为什么要把 recurse_bomb() 放进 fork() 出来的子进程里跑？

参考答案

因为栈溢出会杀死整个进程。如果直接在 main 里跑，程序在打印 D 段结果之前就死了，父进程那份"报告死因"的逻辑也没机会执行。放进子进程后，父进程 wait(&st) 拿到状态，用 WIFSIGNALED/WTERMSIG 读出"被 SIGSEGV 杀死"，还能正常收尾。这也是测试任何"会崩溃的路径"的标准手法——把崩溃隔离在子进程。

题目 3： 如果把 volatile char pad[PAD] 的 volatile 去掉、也删掉 pad[PAD-1] = 1;，会测出什么？

参考答案

gcc 会把 recurse_safe() 优化成尾调用或循环，rsp 几乎不动，top1 - top2 会得到 0 或一个荒谬的大数。帧大小、爆栈深度全部失真。这就是写栈相关微基准必须防优化的原因：编译器看不见效果就会把它消掉。同样的原因，测量递归深度时那个数组必须真实使用、且递归调用之后必须还有代码（阻止尾调用优化）。

6.6

命令行参数 `argv`：`argv[0]` 可以是任何字符串

源码核验：Linux v6.6 · include/linux/mm_types.h:807（arg_lock）· :811（arg_start/arg_end）· fs/proc/base.c:358（proc_pid_cmdline_read）· :369（get_task_cmdline） 本章：TLPI 第 06 章 — Processes - 上一节：6.5 栈与栈帧 - 下一节：6.7 环境列表

本节讲什么

int main(int argc, char *argv[]) 人人都写过，但有三点常被忽略：

  1. argv[0] 可以不是程序名——它是调用者随便指定的字符串，甚至可以是 "改名了"。
  2. argv[argc] 一定是 NULL，这是 C 标准保证的哨兵，不需要传长度。
  3. argv 的来源是 execve，内核把字符串存在进程地址空间的栈顶区，mm_struct 里用 arg_start/arg_end 记住范围，/proc/[pid]/cmdline 读的就是这段。

要点

布局（都在栈顶区，紧挨着）

高地址  ┌──────────────────┐
        │  environ 字符串…  │ ← env_start / env_end
        ├──────────────────┤
        │ argv 字符串…      │ ← arg_start / arg_end
        ├──────────────────┤
        │ NULL             │ ← argv[argc]
        ├──────────────────┤
        │ &argv[argc-1]    │
        │ …                │   argv[] 指针数组本身
        │ &argv[0]         │
        ├──────────────────┤
        │ argc             │
        └──────────────────┘  start_stack 附近

内核对 argv 的记账

/* include/linux/mm_types.h (v6.6) */
spinlock_t arg_lock; /* protect the below fields */            /* :807 */
unsigned long arg_start, arg_end, env_start, env_end;          /* :811 */

arg_lock 为什么必须存在？因为 execve() 换程序时会改写这四个指针（旧程序的 argv 被丢弃、新程序的接上），而 /proc/[pid]/cmdline 的读取是另一个上下文——不加锁就会读到"半个旧 argv + 半个新 argv"。

/* fs/proc/base.c (v6.6) —— /proc/[pid]/cmdline 的 read 实现 */
static ssize_t proc_pid_cmdline_read(struct file *file, char __user *buf,   /* :358 */
                     size_t count, loff_t *pos)
{
    struct task_struct *tsk;
    ssize_t ret;

    BUG_ON(*pos < 0);

    tsk = get_proc_task(file_inode(file));
    if (!tsk)
        return -ESRCH;
    ret = get_task_cmdline(tsk, buf, count, pos);      /* :369 读 arg_start..arg_end */
    put_task_struct(tsk);
    if (ret > 0)
        *pos += ret;
    return ret;
}

三条容易错的语义

说法 真相
argv[0] 是程序名 不是。它只是调用者传的第一个字符串。execve(path, argv, envp) 里 argv[0] 与 path 完全独立
可以用 argv[argc] 之前不知道长度 对——argv[argc] ≡ NULL，所以 while (*argv) 也能遍历
改 argv[i] 的内容 可以，那块内存属于本进程。但别改 argv 指针数组本身的结构（某些实现依赖它连续、以 NULL 结尾）
/proc/[pid]/cmdline 分隔符 不是空格，是 NUL（\0）；所以 cat 出来看着是连在一起的

代码

完整程序见 ../code/c6_6_argv.c：打印自己的 argv，再用 fork + execv 给另一个进程指定一个假的 argv[0]。

/* c6_6_argv.c — 6.6 命令行参数：argc/argv 布局 + argv[argc]==NULL + 来源(fork+execv)
 * 编译: gcc -O2 -Wall -Wextra -o c6_6_argv c6_6_argv.c
 * 用法: ./c6_6_argv -a hello --flag
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

static void dump_argv(int argc, char **argv)
{
    printf("  argc = %d\n", argc);
    for (int i = 0; i <= argc; i++) {
        if (i == argc)
            printf("  argv[%d] = %-12s  <- C 标准保证的 NULL 哨兵\n",
                   i, argv[i] ? "(非NULL!)" : "NULL");
        else
            printf("  argv[%d] = %-12s (@%p)\n", i, argv[i], (void *)argv[i]);
    }
}

int main(int argc, char **argv)
{
    printf("=== A. 本进程的 argv ===\n");
    dump_argv(argc, argv);

    printf("=== B. /proc/self/cmdline（内核存的原始副本，NUL 分隔）===\n");
    FILE *f = fopen("/proc/self/cmdline", "rb");
    if (f) {
        char buf[512];
        size_t n = fread(buf, 1, sizeof buf, f);
        for (size_t i = 0; i < n; i++)
            putchar(buf[i] == '\0' ? '|' : buf[i]);
        putchar('\n');
        fclose(f);
    }

    /* 防无限递归：execv 起来的那个进程 argv[1] 是 「first」，直接收工 */
    if (argc > 1 && strcmp(argv[1], "first") == 0) {
        printf("=== C. 我是被 execv 起来的，argv 由父进程指定，不再自我重启 ===\n");
        return 0;
    }

    printf("=== C. 用 fork + execv 给另一个进程指定 argv ===\n");
    char self[512];
    ssize_t k = readlink("/proc/self/exe", self, sizeof self - 1);
    if (k <= 0) { printf("  readlink(/proc/self/exe) 失败\n"); return 0; }
    self[k] = 0;
    printf("  可执行文件真实路径 = %s\n", self);

    pid_t pid = fork();
    if (pid == 0) {
        /* argv[0] 可以是任意字符串，与真实程序名无关 —— 观察 A 段会打印 「改名了」 */
        char *newargv[] = { (char *)"改名了", (char *)"first", (char *)"-x", NULL };
        execv(self, newargv);
        perror("execv");
        _exit(127);                 /* 只有 execv 失败才会到这 */
    }
    wait(NULL);
    return 0;
}

路线 要点

题目 1： 一个程序打印 argv[0]，结果不是它自己的文件名，可能吗？为什么？

参考答案

完全可能，而且这就是标准行为。argv[0] 由调用者在 execve(path, argv, envp) 里指定，与 path（真正的可执行文件）是两个独立参数。上面实测里可执行文件是 /app/output.s，但 argv[0] 是父进程写的 "改名了"。所以任何"靠 argv[0] 判断我是谁/是否被合法调用"的安全逻辑都是错的。

题目 2： 为什么 argv[argc] 一定是 NULL，这个保证有什么实用价值？

参考答案

C 标准（C99 §5.1.2.2.1）要求 argv[argc] 是空指针，这样接收方即使不知道 argc 也能遍历：for (char **p = argv; *p; p++)。很多库的 API（如 execv 自己）就依赖这个哨兵来知道数组到哪结束。

题目 3： /proc/[pid]/cmdline 里参数之间是什么分隔符？读的时候要注意什么？

参考答案

是 NUL（\0），不是空格。所以直接 cat 会看到参数连成一片。程序里要用 \0 切分（上面 demo 是把它换成 | 才好读）。另外注意末尾也有一个 \0，且这个文件由内核从 mm->arg_start..arg_end 复制出来（fs/proc/base.c:358 的 proc_pid_cmdline_read → get_task_cmdline），受 arg_lock 保护。

6.7

环境列表：`environ` 的读写与 `putenv` 的两个陷阱

源码核验：Linux v6.6 · include/linux/mm_types.h:811（env_start/env_end，与 arg_start 共用 arg_lock:807）· glibc 侧 environ 是 libc 维护的全局变量 本章：TLPI 第 06 章 — Processes - 上一节：6.6 命令行参数 argv - 下一节：6.8 非局部跳转 setjmp / longjmp

本节讲什么

环境列表就是一组 NAME=VALUE 字符串，进程启动时由 execve 的第三个参数传进来，之后可以读写。这一节钉两件事：

  1. 四件套 API 的语义差异：getenv / setenv / unsetenv / putenv。
  2. putenv 的两个真实陷阱——都实测出来了：传局部数组会留下悬垂指针；传自己的缓冲则改缓冲环境跟着变。

要点

三种访问方式

extern char **environ;                    /* NAME=VALUE 数组，NULL 结尾 */
char *getenv(const char *name);           /* 查：返回指针，勿 free */

#include <stdlib.h>
int setenv(const char *name, const char *value, int overwrite);  /* 推荐 */
int unsetenv(const char *name);
int putenv(char *string);                 /* ⚠️ 见下面两个陷阱 */
int clearenv(void);                       /* 非 POSIX，慎用 */
API 是否复制字符串 overwrite 语义 风险
setenv 复制（内部另分配） overwrite=0 时不覆盖已有值 无
putenv 不复制，直接用你给的缓冲 总是替换（等价 overwrite=1） ⚠️ 传局部/临时缓冲 → 悬垂
getenv — — 返回的指针不要 free；下次 setenv 后可能失效
unsetenv — — 无

继承与作用域

  • 子进程默认继承父进程的环境（fork 复制 + execve 传递）。
  • 进程内改环境只影响自己和之后创建的子进程，改不到父进程 / shell 的环境——这是进程隔离的必然结果，不是限制。
  • main 的第三参 envp 是非标准扩展，用 environ。

内核对 environ 的记账

和 argv 完全对称：mm_struct 里 env_start/env_end（mm_types.h:811）记着 environ 字符串区的范围，与 arg_start/arg_end 共用 arg_lock（:807）。所以：

  • /proc/[pid]/environ 读这段（需要 ptrace 权限，读别的进程时通常只有 root/同用户）；
  • 修改环境可能触发重新分配那一段内存（glibc 视情况决定原地改还是搬家）。

代码

完整程序见 ../code/c6_7_environ.c，五段：查询、setenv 的 overwrite 语义、putenv 两个陷阱、遍历 environ。

/* c6_7_environ.c — 6.7 环境变量：getenv/setenv/unsetenv/environ + putenv 两个陷阱
 * 编译: gcc -O2 -Wall -Wextra -o c6_7_environ c6_7_environ.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

extern char **environ;

static void show(const char *name)
{
    char *v = getenv(name);
    printf("  getenv(\"%s\") = %s\n", name, v ? v : "(NULL)");
}

int main(void)
{
    printf("=== A. 只读查询 ===\n");
    show("PATH");
    show("NO_SUCH_VAR");

    printf("=== B. setenv / unsetenv（推荐路径）===\n");
    setenv("MY_VAR", "hello", 0);
    show("MY_VAR");
    setenv("MY_VAR", "world", 0);      /* overwrite=0 -> 不覆盖 */
    show("MY_VAR");
    setenv("MY_VAR", "world", 1);      /* overwrite=1 -> 覆盖 */
    show("MY_VAR");
    unsetenv("MY_VAR");
    show("MY_VAR");

    printf("=== C. putenv 陷阱一：传入的是局部数组（栈上）===\n");
    {
        char localbuf[32];
        strcpy(localbuf, "PITFALL=local-stack-buffer");
        putenv(localbuf);              /* 内核环境区现在指向这个栈数组 */
        printf("  函数返回前: %s\n", getenv("PITFALL"));
    }
    /* localbuf 已随作用域失效 —— 这里读它是 UB（演示只打印指针是否还在） */
    printf("  块已退出，getenv(\"PITFALL\") 仍能命中(悬垂): %s\n",
           getenv("PITFALL") ? "是（危险！）" : "否");

    printf("=== D. putenv 陷阱二：改的是调用者自己的缓冲 ===\n");
    static char same[] = "MUTABLE=aaa";
    putenv(same);
    show("MUTABLE");
    strcpy(same, "MUTABLE=bbb");       /* 直接改那块内存 -> 环境跟着变 */
    show("MUTABLE");

    printf("=== E. 遍历 environ ===\n");
    int n = 0;
    for (char **e = environ; *e; e++) n++;
    printf("  环境变量共 %d 条，前 3 条:\n", n);
    for (int i = 0; i < 3 && environ[i]; i++)
        printf("    %s\n", environ[i]);
    return 0;
}

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

  getenv("MY_VAR") = world          ← overwrite=1，覆盖了

=== C. putenv 陷阱一：传入的是局部数组（栈上）===
  函数返回前: local-stack-buffer
  块已退出，getenv("PITFALL") 仍能命中(悬垂): 是（危险！）
=== D. putenv 陷阱二：改的是调用者自己的缓冲 ===
  getenv("MUTABLE") = aaa
  getenv("MUTABLE") = bbb           ← 只是改了 same[] 的内容，环境跟着变
=== E. 遍历 environ ===
  环境变量共 9 条，前 3 条:
    LD_LIBRARY_PATH=/opt/compiler-explorer/gcc-13.3.0/lib:/opt/compiler-explorer/gcc-13.3.0/lib32:/opt/compiler-explorer/gcc-13.3.0/lib64
    ASAN_OPTIONS=color=always
    UBSAN_OPTIONS=color=always

解读：

  1. B 段是 overwrite 语义的标准演示：setenv(..., 0) 两次后值仍是 hello，改成 1 才变 world。注意"第一次设置"不需要覆盖，所以先 0 能设进去——常见错答是"overwrite=0 就什么都不做"，错的。
  2. C 段是 putenv 最危险的地方：localbuf 是栈上数组，块退出后它的内存随时会被后续调用覆盖。但 getenv("PITFALL") 仍然能命中——环境区里存的是一个悬垂指针。这次侥幸读到的还是旧内容，换台机器/换个编译选项就可能读到垃圾。所以 putenv 的参数必须是静态/全局/堆上且永不释放的内存，否则用 setenv。
  3. D 段是 putenv 的另一面：same[] 是 static（在 data 段），生命周期没问题；但它就是环境区里那个字符串本体——所以 strcpy(same, "MUTABLE=bbb") 直接改了环境变量的值，完全绕过任何 API。这是 putenv 的设计（不复制）的必然结果。
  4. getenv("PATH") 返回的是空字符串，不是 NULL —— 说明 CE 环境里 PATH= 这条存在但值为空。同一段里 NO_SUCH_VAR 返回 (NULL)，两者对比正好说明「存在但为空」与「不存在」是两种状态。这本身是个好例子：环境变量是进程启动时注入的，不是一个全局常量；写代码时别把 "" 和 NULL 混为一谈。
  5. 末尾 environ 里那 9 条是 CE 沙箱注入的（LD_LIBRARY_PATH 指向 gcc 13.3 的库目录，ASAN_OPTIONS/UBSAN_OPTIONS 是 sanitizer 配置）——再次印证环境由调用者决定。

路线 要点

题目 1： setenv("X", "1", 0) 在一个已经设了 X=0 的进程里做了什么？

参考答案

什么都不做——overwrite=0 表示"已存在就不要覆盖"，此时 X 仍为 0。注意如果 X 不存在，overwrite=0 也会正常设进去（"不覆盖"针对的是已存在的情形）。上面实测 B 段第一次 setenv(..., 0) 成功设入 hello、第二次同类调用仍是 hello，就是这个语义。

题目 2： 为什么 putenv(localbuf)（局部数组）是危险的？实测里它"看起来正常"说明了什么？

参考答案

putenv 不复制字符串，只把指针塞进环境数组。localbuf 是栈上数组，函数/块退出后那片内存失效，环境区就留下一个悬垂指针，后续任何栈使用都可能覆盖它。实测里 getenv("PITFALL") 仍能读到旧值，只是运气——那片内存暂时没被复用。这类 bug 的可怕之处正是"常常看起来正常"，在别的编译选项或调用序列下才炸。

题目 3： 在进程里 setenv("PATH", "/tmp")，会影响到启动它的那个 shell 吗？

参考答案

不会。环境变量是进程私有的：fork 时复制、execve 时传递，改动只沿"父 → 子"单向流动，无法反向影响父进程或外层 shell。想让 shell 看到，必须在 shell 自己的上下文里改（或由子进程把值打印出来让 shell eval）。

6.8

非局部跳转：`setjmp` / `longjmp` 与 `volatile` 陷阱

源码核验：glibc 2.39 · setjmp/setjmp.h:32（typedef struct __jmp_buf_tag jmp_buf[1]）· :41（__sigsetjmp）· setjmp/longjmp.c:29-41（val ?: 1）· sysdeps/x86_64/setjmp.S:31-33（保存寄存器） 本章：TLPI 第 06 章 — Processes - 上一节：6.7 环境列表 - 下一节：Ch7 内存分配

本节讲什么

goto 只能在函数内跳；setjmp / longjmp 能跨函数跳回来。它常被当成"简易异常机制"用。这一节钉三件事：

  1. 返回值的规矩：setjmp 直接调用返回 0，longjmp 跳回来时返回你给的 val，但 val == 0 会被强制改成 1。
  2. volatile 陷阱（本节的硬核）：setjmp 与 longjmp 之间被修改的非 volatile 局部变量，值可能被"回滚"——实测确认。
  3. 它到底是什么：jmp_buf 里存的是一堆寄存器快照，longjmp 是把它们恢复回去。

要点

API

#include <setjmp.h>
int  setjmp(jmp_buf env);            /* 直接调用返回 0；保存执行环境 */
void longjmp(jmp_buf env, int val);  /* 跳回 setjmp；表现为返回 val（0 -> 1） */

返回值的规矩

情况 setjmp 的返回值
直接调用（第一次执行到） 0
longjmp(env, 42) 之后 42
longjmp(env, 0) 之后 1（0 被刻意避开，好让 0 专表"正常"）

jmp_buf 里存了什么

/* glibc setjmp/setjmp.h —— 注意是个长度 1 的数组类型，所以传参时"自动退化成指针" */
typedef struct __jmp_buf_tag jmp_buf[1];                    /* :32 */

/* 内部实现只有一个函数，setjmp 与 sigsetjmp 都用它，靠 savemask 区分 */
extern int __sigsetjmp (struct __jmp_buf_tag __env[1], int __savemask);   /* :41 */

x86-64 上它保存的寄存器（sysdeps/x86_64/setjmp.S:31 起）：

ENTRY (__sigsetjmp)
    /* Save registers.  */
    movq %rbx, (JB_RBX*8)(%rdi)      # :33  rbx
    ...                               #      rbp / r12-r15 / rsp / rip 依次保存
    jmp __sigjmp_save                 # :85  尾调用：按 savemask 决定存不存信号掩码

实测 sizeof(jmp_buf) = 200 字节 = 8 个 long（64 B，存放上面那批寄存器）+ int __mask_was_saved（4 B）+ 对齐 4 B + __sigset_t __saved_mask（128 B）。

⭐ longjmp 与 siglongjmp 是同一个函数

/* glibc setjmp/longjmp.c (2.39) */
void
__libc_siglongjmp (sigjmp_buf env, int val)                      /* :29 */
{
  _longjmp_unwind (env, val);                                    /* :32 */

  if (env[0].__mask_was_saved)                                   /* :34 */
    (void) __sigprocmask (SIG_SETMASK,
              (sigset_t *) &env[0].__saved_mask,
              (sigset_t *) NULL);            /* :36 只有 setjmp 时存过掩码才恢复 */

  __longjmp (env[0].__jmpbuf, val ?: 1);                         /* :41 ⭐ val==0 -> 1 */
}

weak_alias (__libc_siglongjmp, _longjmp)                         /* :50 */
weak_alias (__libc_siglongjmp, longjmp)                          /* :51 */
weak_alias (__libc_siglongjmp, siglongjmp)                       /* :52 */

两个结论直接来自源码：

  • val == 0 变成 1 就发生在 :41 的 val ?: 1（GNU 扩展写法，等价 val ? val : 1）。
  • longjmp / _longjmp / siglongjmp 是同一个函数的三个别名；是否恢复信号掩码不由调用的名字决定，而由当初 setjmp 时 savemask 传的是不是 0（:34 的 __mask_was_saved）决定。

volatile 陷阱（本节最该记住的）

C 标准说：setjmp 与 longjmp 之间被修改的局部变量，若它不是 volatile、且没有在别处取过地址，longjmp 之后的值是未定义的。

原因很直白：这类变量常常只活在寄存器里，而 longjmp 是"把寄存器恢复到 setjmp 那一刻"——寄存器值被覆盖，变量自然"回滚"。

变量 -O2 实测 结论
volatile int vol_var 200（正确） volatile 强制走内存
int auto_var 100（回滚！） 只在寄存器里 → 被恢复覆盖
static int sta_var 200（正确） 在 .data 段，不在寄存器

代码

完整程序见 ../code/c6_8_setjmp.c，三层调用链里出错、跳回 main，同时对比三种变量的命运。

/* c6_8_setjmp.c — 6.8 setjmp/longjmp：跨函数跳转 + 非 volatile 局部变量被回滚
 * 编译对比: gcc -O0 与 gcc -O2 各跑一次，看 auto_var 的差异
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <setjmp.h>
#include <stdlib.h>

static jmp_buf env;

/* 深层调用：出错就跳回 main 的 setjmp 点 */
static void level3(int fail)
{
    if (fail) {
        printf("    [level3] 出错，longjmp(env, 42)\n");
        longjmp(env, 42);
    }
    printf("    [level3] 正常返回\n");
}
static void level2(int fail) { level3(fail); }
static void level1(int fail) { level2(fail); }

int main(void)
{
    /* jmp_buf 里到底存了什么：x86-64 glibc = 8 个 long(保存 rbx/rbp/r12-r15/rsp/rip)
     * + int __mask_was_saved + 128B __sigset_t __saved_mask */
    printf("sizeof(jmp_buf) = %zu B，sizeof(sigjmp_buf) = %zu B\n",
           sizeof(jmp_buf), sizeof(sigjmp_buf));

    /* 在 setjmp 与 longjmp 之间改动的局部变量：
     * auto_var   没有 volatile -> 可能只活在寄存器里 -> longjmp 后被「回滚」
     * vol_var    有 volatile   -> 强制走内存 -> 值一定是最新的
     */
    volatile int vol_var = 100;
    int auto_var = 100;
    static int sta_var = 100;              /* static 在 .data，不受影响 */

    int r = setjmp(env);
    if (r == 0) {
        printf("--- 第一次返回 0：正常路径 ---\n");
        level1(0);                          /* 正常 */
        printf("  改三个变量：100 -> 200\n");
        vol_var = auto_var = sta_var = 200;
        level1(1);                          /* 触发 longjmp */
        printf("  这行永远不执行\n");
    } else {
        printf("--- longjmp 回来，r = %d ---\n", r);
        printf("  volatile int vol_var = %d   (200 正确)\n", vol_var);
        printf("  int          auto_var= %d   (%s)\n", auto_var,
               auto_var == 200 ? "200 正确" : "被回滚成 100 ！");
        printf("  static int   sta_var = %d   (200 正确)\n", sta_var);
    }
    printf("集齐 setjmp：返回 0 表示直接调用，val==0 会被强制改成 1\n");

    /* 补一个 val==0 的演示 */
    if (setjmp(env) == 0) longjmp(env, 0);
    else printf("  longjmp(env, 0) 实际返回 1（0 被刻意避开）\n");
    return 0;
}

gcc -O2 -Wall -Wextra -o c6_8_setjmp_O2 c6_8_setjmp.c && ./c6_8_setjmp_O2
gcc -O0 -Wall -Wextra -o c6_8_setjmp_O0 c6_8_setjmp.c && ./c6_8_setjmp_O0

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

    [level3] 出错，longjmp(env, 42)

  int          auto_var= 100   (被回滚成 100 ！)      ← ⭐ 陷阱现身
  static int   sta_var = 200   (200 正确)

===== -O0 =====

解读：

  1. -O2 与 -O0 的差异是本节的核：同一份源码，-O2 下 auto_var 回滚成 100，-O0 下是 200。差别就是寄存器分配——-O0 把每个局部变量都放栈上（天然"安全"），-O2 把它放进寄存器，longjmp 恢复寄存器时把它盖回旧值。
  2. volatile 和 static 都安全，但原因不同：volatile 是强制走内存（编译器不许缓存到寄存器）；static 是本来就住在 .data，而 longjmp 只恢复寄存器、不动内存。别把两者当同一回事。
  3. -O0 下"没出问题"是假象，不是"我的代码没问题"。这类 bug 只在开启优化后出现——调 release 版才炸的典型。
  4. sizeof(jmp_buf) = 200 印证了源码结构：64 B 寄存器区 + 4 B __mask_was_saved + 4 B 对齐 + 128 B __saved_mask = 200。
  5. longjmp(env, 0) 返回 1，与 longjmp.c:41 的 val ?: 1 对上——源码级证据，不是"书上这么说"。

⚠️ 本节只讲 setjmp/longjmp。信号处理器里该用 sigsetjmp/siglongjmp（要保存/恢复信号掩码），那属于 Ch21 信号处理器 的范围，限制比这里多得多。

HFT / 嵌入式关联

路线 要点
嵌入式 资源紧张的系统里 setjmp/longjmp 常被当"轻量异常"用（省掉 C++ 异常的开销）。但如上所述，凡是跨 setjmp 改过的变量必须 volatile，否则优化一开就出错——嵌入式常用 -Os，同样中招
HFT 热路径上不要用 setjmp/longjmp：jmp_buf 有 200 B，保存/恢复 8 个寄存器 + 可能的 sigprocmask 系统调用（mask_was_saved 时），延迟比普通返回高一个量级
HFT 它真正的用武之地是冷路径的错误跳出：解析配置、初始化阶段用 setjmp 设一个"统一失败出口"，省掉层层返回错误码
HFT ⚠️ longjmp 不执行栈展开清理：跳过的中间帧里的 malloc 不会被释放、持有的锁不会被释放、atexit 也不跑。在 C++ 里跨 longjmp 更是直接 UB（析构不执行）

自测题

题目 1： longjmp(env, 0) 之后，setjmp 那行返回什么？

参考答案

返回 1。glibc 的实现是 setjmp/longjmp.c:41 的 __longjmp(env[0].__jmpbuf, val ?: 1)——val 为 0 时取 1。这是刻意设计：0 保留给"直接调用"这一情形，这样 if (setjmp(env) == 0) { 正常 } else { 异常 } 的惯用法才能工作。

题目 2： 为什么 setjmp 和 longjmp 之间改过的局部变量会被"回滚"？为什么加了 volatile 就好了？

参考答案

因为 longjmp 的本质是恢复寄存器快照（sysdeps/x86_64/setjmp.S 保存 rbx/rbp/r12-r15/rsp/rip）。如果某个局部变量在 -O2 下一直被放在寄存器里（没有被其他代码逼到栈上），恢复旧寄存器值就等于把它"改回"了 setjmp 那一刻的值。加 volatile 后编译器必须让它每次读写都真的落到内存，而 longjmp 不碰内存，所以值得以保留。实测对比：-O2 下 auto_var 变回 100，-O0 下是 200。

题目 3： longjmp 直接跳到别处，被跳过的那些栈帧里如果有 malloc 的内存和加过的锁，会怎样？

参考答案

不会被释放/解开。longjmp 只恢复寄存器（包括栈指针），不做任何"栈展开清理"——没有析构函数、没有 atexit、没有 RAII、没有自动解锁。所以被跳过的中间帧里 malloc 的内存泄漏、持有的 pthread_mutex 永久锁死。这也是为什么信号处理程序里用 longjmp（尤其 _longjmp）要极其小心，标准做法是只在里面做 siglongjmp 到安全点，且退出前不加锁、不分配。

自测题

题目 1： setjmp 返回值什么时候是 0？什么时候不是？

参考答案

直接调用 setjmp(env) 时返回 0（第一次执行到这一行）。后续任意时刻调用 longjmp(env, val)，执行流跳回 setjmp 的位置，此时它返回 val——但如果 val 是 0，会被强制改成 1（glibc 源码 setjmp/longjmp.c:41 的 val ?: 1）。所以 0 永远只表示"直接调用"。

题目 2： 为什么在信号处理器中用 longjmp 是危险的？

参考答案

三点：① 信号掩码不恢复——longjmp（对应 setjmp，savemask=0）不会恢复掩码，处理器执行期间被自动屏蔽的信号会一直保持屏蔽；② 可能跳进/跳出不安全的中间状态——如果信号打断了 malloc，longjmp 跳过它的收尾会造成堆损坏；③ 栈帧可能已失效——目标 setjmp 所在函数若已返回，那块栈已被复用。正确做法是用 sigsetjmp/siglongjmp（它们保存/恢复信号掩码），并严格限制处理器里只调用 async-signal-safe 函数。

题目 3： getenv 返回的指针可以直接改吗？

参考答案

技术上是本进程的内存，改了就相当于改了该环境变量；但不应该这么做——它是环境区里的字符串本体，长度一变就破坏结构，正确做法用 setenv / putenv。另外两点：返回的指针不要 free（不属于你），且下次 setenv/putenv 之后可能失效（内部可能重新分配整个环境数组）。

练习 1：打印进程信息

写一个程序，打印自己的 PID、PPID、命令行参数、环境变量条数。

参考答案（完整可编译） 
/* ex6_1.c — 打印 PID/PPID/argv/environ
 * 编译: gcc -O2 -Wall -Wextra -o ex6_1 ex6_1.c */
#include <stdio.h>
#include <unistd.h>

extern char **environ;

int main(int argc, char *argv[])
{
    printf("PID=%d PPID=%d\n", (int)getpid(), (int)getppid());

    printf("argc=%d\n", argc);
    for (int i = 0; i <= argc; i++)                 /* <= 顺便看到 NULL 哨兵 */
        printf("  argv[%d] = %s\n", i, i == argc ? "(NULL)" : argv[i]);

    int n = 0;
    for (char **p = environ; *p; p++) n++;
    printf("environ: %d 条\n", n);
    return 0;
}

实测输出（CE 复核，gcc 13.3）：

PID=2 PPID=1
argc=1
  argv[0] = ./output.s
  argv[1] = (NULL)
environ: 7 条

（environ 条数每次跑都可能不同 —— 由调用者的环境决定；这里记的是本次 CE 沙箱里的值。）

三个要注意的点：

  1. TLPI 书上的版本用了 tlpi_hdr.h（书配套头文件），本机/沙箱可能没有，所以这里换成标准头 —— 练习代码要能独立编译，别依赖书里的私有头。
  2. 循环写成 i <= argc 就能顺带打印出 argv[argc] 这个 NULL 哨兵，比只循环到 argc-1 更有教学价值。
  3. argc 和 environ 条数都取决于调用者：直接跑是 argc=1，带参数跑就变；environ 条数随环境变化。同一份二进制在不同环境输出不同。

练习 2：用 setjmp/longjmp 做错误恢复

主函数设置跳转点；调用链中任意层出错就 longjmp 跳回，并带出错误码。

参考答案（完整可编译） 
/* ex6_2.c — setjmp/longjmp 错误恢复
 * 编译: gcc -O2 -Wall -Wextra -o ex6_2 ex6_2.c */
#include <stdio.h>
#include <setjmp.h>

static jmp_buf err_env;
static int err_code;

void level3(int fail)
{
    if (fail) {
        err_code = 42;
        longjmp(err_env, err_code);        /* 直接从第 3 层跳回 main */
    }
    printf("level3: success\n");
}
void level2(int fail) { level3(fail); }
void level1(int fail) { level2(fail); }

int main(void)
{
    int r = setjmp(err_env);
    if (r == 0) {
        printf("第一次调用（正常路径）\n");
        level1(0);                         /* 不出错 */
        level1(1);                         /* 出错 -> longjmp */
        printf("这行不会执行\n");
    } else {
        printf("错误恢复：err_code=%d\n", r);
    }
    return 0;
}

实测输出（CE 复核，gcc 13.3）：

第一次调用（正常路径）
level3: success
错误恢复：err_code=42

⚠️ 注意 err_code 必须声明为 static（或 volatile）：它在 longjmp 之后要被读，而它是非局部的普通变量时值可能不确定（见 6.8 的 volatile 陷阱）。这里用 static 让它住在 .data，天然安全。

练习 3：信号处理器里的 longjmp

解释为什么在信号处理器中调用 longjmp 是危险的，如何安全替代？

参考答案

危险性（三条，与 6.8 结尾的"不清理"是同一根源）：

  1. 信号掩码不恢复：普通的 setjmp/longjmp 不保存/恢复信号掩码（glibc 里靠 __mask_was_saved 决定，而 setjmp 设的是 0）。处理器执行期间内核自动屏蔽了当前信号，longjmp 跳出来不会解除，导致该信号永久收不到。
  2. 跳过中间状态的收尾：若信号打断的是 malloc / printf 这类非 async-signal-safe 函数，longjmp 会跳过它们的收尾，造成堆结构损坏或流缓冲乱套。
  3. 目标栈帧可能已失效：如果 setjmp 所在函数在信号到来前已经返回，那块栈已被复用，跳回去就是往垃圾里执行。

安全替代：

#include <signal.h>
#include <setjmp.h>

static sigjmp_buf sig_env;

static void handler(int sig)
{
    (void)sig;
    siglongjmp(sig_env, 1);        /* 保存/恢复信号掩码 */
}

int main(void)
{
    if (sigsetjmp(sig_env, 1) == 0) {   /* 第二个参数 1 = 保存掩码 */
        signal(SIGINT, handler);
        /* 危险操作… */
    } else {
        /* 恢复点 */
    }
    return 0;
}

要点：sigsetjmp(buf, 1) 的第二个参数为 1 才保存信号掩码（glibc 源码里就是传给 __sigsetjmp 的 savemask，见 setjmp/setjmp.h:41），siglongjmp 会据此恢复。即便如此，处理器里仍然只应做 async-signal-safe 的操作。完整限制见 Ch21 信号处理器。
