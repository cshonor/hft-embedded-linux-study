代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

/* Ch38 安全与特权编程 — 降权 + 最小权限原则。
 * 演示 setuid 程序如何临时/永久放弃特权。
 * 编译: gcc -o ch38_demo ch38_demo.c */

int main(void) {
    uid_t ruid = getuid();    /* 实际 uid */
    uid_t euid = geteuid();   /* 有效 uid */

    printf("Before: real=%u, effective=%u\n", ruid, euid);

    if (euid == 0) {
        printf("Running as root (or setuid-root)\n");

        /* 永久降权: 先设 effective，再设 saved-set */
        /* 假设要降为 uid 1000 */
        uid_t target = 1000;
        gid_t target_gid = 1000;

        /* 步骤1: 临时降 effective uid */
        seteuid(target);
        printf("After seteuid(%u): euid=%u\n", target, (unsigned)geteuid());

        /* 步骤2: 需要特权时临时恢复 */
        seteuid(0);
        printf("Restored: euid=%u\n", (unsigned)geteuid());

        /* 步骤3: 永久放弃 root (三连设) */
        setgid(target_gid);
        setuid(target);
        printf("After permanent drop: real=%u, eff=%u\n",
               (unsigned)getuid(), (unsigned)geteuid());
        printf("Cannot regain root now\n");
    } else {
        printf("Running as normal user (uid=%u)\n", euid);
        printf("Secure programming: validate all input, minimize privileges\n");
    }
    return 0;
}

38.1

两类特权程序

本章：TLPI 第 38 章 — Writing Secure Privileged Programs - 上一节：本章首页 - 下一节：38.2 丢弃与恢复（核心）

本节讲什么

凭证细节见 Ch9：RUID / EUID / Saved-UID / FSUID。Saved-UID 支撑临时降权后再提权。 ---

要点

类型
root 启动的 daemon 启动 EUID=0，可再降权
SUID/SGID 文件 exec 后 EUID=文件属主（如 passwd）

凭证细节见 Ch9：RUID / EUID / Saved-UID / FSUID。Saved-UID 支撑临时降权后再提权。

HFT / 嵌入式关联

路线 要点
嵌入式 root 启动 daemon（启动 EUID=0 再降权）与 SUID/SGID 文件（exec 后 EUID=文件属主）；Saved-UID 支撑临时降权再提权
HFT 交易服务以 root 启动绑定特权资源后立即降权，最小化被攻破面；避免 SUID 二进制

代码示例

#include <unistd.h>
#include <stdio.h>
/* 编写 setuid 程序的安全原则:
 * 1. 最小权限: 用完特权立即丢弃
 * 2. 净化环境: 清除 LD_PRELOAD 等危险变量
 * 3. 检查所有返回值
 * 4. 不用 system(), 用 execve
 */
int main(void) {
    printf("EUID=%d\n", geteuid());
    if (geteuid() == 0) {
        printf("特权程序! 需格外小心\n");
        /* 永久丢弃特权 */
        setuid(getuid());
        printf("特权已丢弃: EUID=%d\n", geteuid());
    }
    return 0;
}

38.2

丢弃与恢复（核心）

本章：TLPI 第 38 章 — Writing Secure Privileged Programs - 上一节：38.1 两类特权程序 - 下一节：38.3 安全准则（精要）

本节讲什么

int setuid(uid_t uid); int seteuid(uid_t euid); seteuid(getuid()); / 无特权业务 /

要点

int setuid(uid_t uid);
int seteuid(uid_t euid);
调用方 setuid(uid) seteuid(euid)
EUID==0 常把 R+E+S 全改 → 永久丢 root 只改 EUID → 可再 seteuid(0)（若 Saved 仍为 0）
EUID≠0（典型 SUID） 多等价于只改 EUID 在 RUID↔Saved 间切 EUID

临时下放（推荐）

seteuid(getuid());   /* 无特权业务 */
/* ... */
seteuid(0);          /* 必要特权操作 */

永久丢弃

setuid(getuid());    /* 确认不再需要特权 */

Demo（需 setuid-root 二进制）：
Ch9 seteuid_drop_restore.c ·
Ch9 setuid_permanent_drop.c

HFT / 嵌入式关联

路线 要点
嵌入式 seteuid 只改 EUID 可再提权（临时下放），setuid 全改 R+E+S 永久丢 root；选对三件套
HFT 热路径业务 seteuid(getuid()) 降权跑，仅特权操作（绑端口/改调度）临时 seteuid(0)，最小特权窗口

38.3

安全准则（精要）

本章：TLPI 第 38 章 — Writing Secure Privileged Programs - 上一节：38.2 丢弃与恢复（核心） - 下一节：下一章+1:02d}-*/notes.md)

本节讲什么

  1. 尽量别写 SUID；改权限 / 专用 daemon / Capability 2. 最小特权：特权代码短；默认无特权跑业务 3. 不再需要 → 永久 setuid(getuid())

要点

  1. 尽量别写 SUID；改权限 / 专用 daemon / Capability
  2. 最小特权：特权代码短；默认无特权跑业务
  3. 不再需要 → 永久 setuid(getuid())
  4. 环境：勿信 PATH/LD_*；清空后只注可信变量；用绝对路径 exec*，禁 execlp/execvp/system/popen
  5. 禁 shell：system/popen → 注入
  6. TOCTOU：勿 stat 再 open；open（可加 O_NOFOLLOW）+ fstat(fd)
  7. 符号链接：可写目录慎放敏感文件
  8. 校验一切输入；防 ../
  9. 创建文件：umask + 显式 mode + O_EXCL；少用世界可写 /tmp 存秘密
  10. RLIMIT_CORE=0 防敏感 core；信号里不做特权重活
  11. O_CLOEXEC / 关多余 fd
  12. 勿信 stdin/stdout/stderr

Demo：code/open_fstat_safe.c · code/no_system_exec.c（注释对照）

HFT / 嵌入式关联

路线 要点
嵌入式 勿写 SUID；清环境变量（PATH/LD_*）；禁 system/popen；TOCTOU 用 open+fstat；O_CLOEXEC；RLIMIT_CORE=0
HFT 服务进程用绝对路径 exec 禁 shell 注入，open(O_NOFOLLOW)+fstat 防符号链接劫持，全面校验输入

代码示例

#include <unistd.h>
#include <stdio.h>
int main(void) {
    /* SUID 程序常见攻击:
     * 1. LD_PRELOAD 注入 (Linux 自动忽略 SUID 程序的 LD_*)
     * 2. 硬链接攻击 (SUID 程序被替换)
     * 3. TOCTOU 竞态
     * 4. 缓冲区溢出
     * 5. PATH 劫持
     */
    printf("SUID 安全: 清环境 → 丢特权 → 防溢出 → 检链接\n");
    /* 清除危险环境变量 */
    unsetenv("LD_PRELOAD");
    unsetenv("LD_LIBRARY_PATH");
    unsetenv("IFS");
    printf("已清除 LD_PRELOAD/LD_LIBRARY_PATH/IFS\n");
    return 0;
}

38.4

Avoid Exposing Sensitive Information

本章：TLPI 第 38 章

本节讲什么

特权程序必须避免向非特权用户泄露敏感信息。泄露途径包括：环境变量传递、命令行参数可见性、核心转储、临时文件残留、错误信息过度暴露等。

要点

常见泄露途径与对策

泄露途径 风险 对策
命令行参数 ps/top 可见 用文件/管道传密码，不直接传 argv
环境变量 子进程继承 敏感数据不存 env，或用后 unsetenv
临时文件 /tmp 可读 O_CREAT\|O_EXCL + 0600 权限
核心转储 含内存数据 setrlimit(RLIMIT_CORE, 0)
错误信息 泄露路径/结构 只向日志写细节，用户看通用消息
argv[0] 伪装 ps 中暴露 prctl(PR_SET_NAME) 改进程名

关键原则

  • 最小暴露面：只输出用户需要知道的信息
  • 日志分级：详细错误写 syslog，用户看到的是通用提示
  • 内存清理：用完敏感数据后 memset/explicit_bzero 清零
  • 避免核心转储：特权程序应禁用 core dump

HFT / 嵌入式关联

  • 嵌入式设备中，固件更新程序常以 root 运行，需避免在日志中暴露密钥
  • HFT 交易系统的 API key/证书路径不应出现在命令行参数中
  • 量化回测框架的数据库连接串应从受保护配置文件读取，而非环境变量

代码示例

#include <sys/resource.h>
#include <string.h>
#include <errno.h>

void secure_init(void)
{
    /* 禁用 core dump，防止内存中的敏感数据被提取 */
    struct rlimit rl = { 0, 0 };
    setrlimit(RLIMIT_CORE, &rl);

    /* 清除可能继承的敏感环境变量 */
    unsetenv("DB_PASSWORD");
    unsetenv("API_SECRET_KEY");
}

/* 安全地清除内存中的敏感数据（防止编译器优化掉 memset） */
void secure_bzero(void *ptr, size_t len)
{
    /* explicit_bzero 是 POSIX.1-2008 标准，不会被优化掉 */
    explicit_bzero(ptr, len);
}

/* 安全的错误报告：用户看通用消息，细节写 syslog */
void report_error(const char *user_msg, const char *detail)
{
    /* syslog 写详细信息 */
    syslog(LOG_ERR, "Error: %s (errno=%d: %s)", detail, errno, strerror(errno));
    /* 用户只看到通用提示 */
    fprintf(stderr, "%s\n", user_msg);
}

代码自测

为什么 memset(ptr, 0, len) 可能不安全？

编译器在优化时，如果看到 memset 之后该内存不再被使用，可能会将 memset 调用完全删除（死代码消除）。这会导致敏感数据残留在内存中。应使用 explicit_bzero() 或 memset_s()（C11 Annex K），它们保证不被优化掉。

特权程序为什么要禁用 core dump？

Core dump 包含进程内存的完整映像，可能包含密码、密钥、令牌等敏感数据。如果特权程序崩溃，任何能读取 core 文件的用户都能提取这些信息。通过 setrlimit(RLIMIT_CORE, 0) 禁用 core dump 是防御措施之一。

38.5

Confine the Process

本章：TLPI 第 38 章

本节讲什么

限制特权进程的运行环境，减少被利用后的影响范围。核心思路：在完成特权操作后立即丢弃权限、使用 chroot 改变文件系统根目录、使用最小权限原则。

要点

权限丢弃策略

策略 API 说明
永久丢弃 UID setuid(getuid()) 切换回调用者 UID，不可恢复
永久丢弃 GID setgid(getgid()) 同上，针对组
临时切换 seteuid()/setegid() 可恢复，但需谨慎
清除补充组 setgroups(0, NULL) 必须在 setgid 之前调用

chroot 限制

chroot("/safe/chroot");   /* 改变文件系统根 */
chdir("/");               /* 必须立即 chdir，否则旧根仍可访问 */
  • chroot 不是安全沙箱：root 用户可以逃逸（如通过 chroot(".") 再次改变根）
  • 必须先 chroot，再丢弃 root 权限
  • chroot 环境需要包含必要的库文件和设备节点

最小权限操作顺序

1. 打开特权资源（绑定端口 < 1024 等）
2. chroot 到受限目录（如果使用）
3. setgroups(0, NULL)  清除补充组
4. setgid()            设置真实 GID
5. setuid()            设置真实 UID（最后一步，不可逆）
6. 继续非特权操作

HFT / 嵌入式关联

  • 交易网关：绑定 443 端口后立即 setuid 到专用交易用户
  • 嵌入式 Web 服务器：初始化后丢弃 root，仅保留 CAP_NET_BIND_SERVICE
  • 策略引擎沙箱：用 chroot 将策略进程限制在数据目录中

代码示例

#include <unistd.h>
#include <sys/types.h>
#include <grp.h>
#include <stdio.h>

/* 权限丢弃的典型模式 */
int drop_privileges(const char *chroot_dir)
{
    uid_t ruid = getuid();  /* 真实用户 ID */
    gid_t rgid = getgid();  /* 真实组 ID */

    /* 1. 如果需要 chroot，在丢权限前做 */
    if (chroot_dir != NULL) {
        if (chroot(chroot_dir) == -1) {
            perror("chroot");
            return -1;
        }
        if (chdir("/") == -1) {  /* 必须立即 chdir */
            perror("chdir");
            return -1;
        }
    }

    /* 2. 清除补充组（必须在 setgid 前） */
    if (setgroups(0, NULL) == -1) {
        perror("setgroups");
        return -1;
    }

    /* 3. 设置 GID */
    if (setgid(rgid) == -1) {
        perror("setgid");
        return -1;
    }

    /* 4. 设置 UID（最后一步，不可逆） */
    if (setuid(ruid) == -1) {
        perror("setuid");
        return -1;
    }

    /* 验证权限已丢弃 */
    if (setuid(0) != -1) {
        fprintf(stderr, "Failed to drop root privileges!\n");
        return -1;
    }
    return 0;
}

代码自测

为什么 setgroups(0, NULL) 必须在 setgid() 之前调用？

setgroups() 需要 root 权限才能修改补充组列表。如果先执行 setgid() 丢弃了 root 权限，后续的 setgroups() 调用会失败，导致旧的补充组（可能包含 root 组）仍然保留，造成权限泄露。

为什么 chroot 不能作为安全沙箱？

chroot 仅改变文件系统根目录，但不改变进程的 root 权限。拥有 root 权限的进程可以通过多种方式逃逸 chroot：使用 chroot(".") 创建新的 chroot、通过文件描述符访问旧根、利用 mknod 创建设备文件等。正确做法是先 chroot，再丢弃 root 权限。

38.6

Beware of Signals and Race Conditions

本章：TLPI 第 38 章

本节讲什么

特权程序中信号处理与系统调用之间存在竞态条件。攻击者可在特权操作的窗口期发送信号，干扰程序执行流。关键是理解信号何时可中断系统调用、何时产生竞争窗口。

要点

竞态场景

场目 竞态窗口 后果
setuid + open 检查 UID → 打开文件 TOCTOU：文件被替换
信号中断 open open 返回 EINTR 特权未丢弃时继续执行
access + open access 检查 → open 打开 符号链接替换攻击
信号处理中调用非异步信号安全函数 handler 执行期间 死锁/内存损坏

防御措施

  1. 屏蔽信号：在特权操作期间屏蔽所有信号 c sigset_t mask, oldmask; sigfillset(&mask); sigprocmask(SIG_BLOCK, &mask, &oldmask); /* 特权操作 */ sigprocmask(SIG_SETMASK, &oldmask, NULL);

  2. 避免 TOCTOU：不用 access() + open()，改用 open() + fstat()

  3. 信号处理只设标志：handler 中只设置 volatile sig_atomic_t 标志，主循环检查

  4. SA_RESTART：让被中断的系统调用自动重启

HFT / 嵌入式关联

  • 交易系统中，订单提交路径必须屏蔽信号，防止关键操作被中断
  • 嵌入式设备升级程序在写固件时需屏蔽信号，防止半完成状态
  • 行情处理进程的信号 handler 只设标志，主 epoll 循环统一处理

代码示例

#include <signal.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/stat.h>

/* 安全打开文件：屏蔽信号 + 避免 TOCTOU */
int safe_open(const char *path, int flags, mode_t mode)
{
    sigset_t mask, oldmask;
    int fd;
    struct stat st;

    /* 屏蔽所有信号 */
    sigfillset(&mask);
    sigprocmask(SIG_BLOCK, &mask, &oldmask);

    /* 打开文件（不依赖之前的 access 检查） */
    fd = open(path, flags | O_NOFOLLOW, mode);  /* O_NOFOLLOW 防符号链接 */
    if (fd == -1) {
        sigprocmask(SIG_SETMASK, &oldmask, NULL);
        return -1;
    }

    /* 用 fstat 而非 stat 检查文件属性（避免 TOCTOU） */
    if (fstat(fd, &st) == -1) {
        close(fd);
        sigprocmask(SIG_SETMASK, &oldmask, NULL);
        return -1;
    }

    /* 验证文件不是符号链接、属主正确 */
    if (!S_ISREG(st.st_mode) || (st.st_mode & S_IWOTH)) {
        close(fd);
        sigprocmask(SIG_SETMASK, &oldmask, NULL);
        return -1;
    }

    /* 恢复信号 */
    sigprocmask(SIG_SETMASK, &oldmask, NULL);
    return fd;
}

代码自测

为什么 access() + open() 模式不安全？

access() 检查的是真实 UID/GID 的权限，而 open() 使用有效 UID/GID。在特权程序中（setuid），两者不同。更重要的是，在 access() 和 open() 之间，攻击者可以替换文件（如用符号链接指向另一个文件），这就是 TOCTOU（Time-of-Check to Time-of-Use）攻击。正确做法是直接 open() 后用 fstat() 检查。

信号处理函数中为什么不能调用 printf？

printf 不是异步信号安全函数。它内部使用 malloc/stdio 缓冲区等非可重入资源。如果在信号处理期间主程序正在使用这些资源，会导致缓冲区损坏或死锁。信号处理函数只应调用异步信号安全函数（如 write），或仅设置 volatile sig_atomic_t 标志。

38.7

Pitfalls When Performing File Operations

本章：TLPI 第 38 章

本节讲什么

特权程序执行文件操作时的常见陷阱：符号链接攻击、硬链接攻击、文件描述符泄漏、竞争条件、权限检查不当等。

要点

文件操作陷阱表

陷阱 说明 防御
符号链接攻击 攻击者创建符号链接指向敏感文件 O_NOFOLLOW 打开失败
硬链接攻击 攻击者创建硬链接到特权文件 fstat 检查链接数 st_nlink
路径竞争 stat → open 间文件被替换 直接 open + fstat
FD 泄漏 特权 FD 被子进程继承 fcntl(fd, F_SETFD, FD_CLOEXEC)
目录遍历 ../ 跳出预期目录 realpath + 路径白名单
临时文件竞争 猜测文件名抢占创建 mkstemp 或 O_EXCL

关键标志

标志 作用
O_NOFOLLOW 最后一个组件不能是符号链接
O_CREAT\|O_EXCL 文件不存在才创建（防竞争）
O_CLOEXEC exec 时自动关闭 fd
O_NOFOLLOW + O_DIRECTORY 确保打开的是目录

权限检查原则

  • 用 fstat 不用 stat：先打开再检查，避免 TOCTOU
  • 检查真实 UID：st.st_uid 是否为预期用户
  • 检查文件类型：S_ISREG 确保是普通文件
  • 检查权限位：不应有 S_IWOTH（其他用户可写）

HFT / 嵌入式关联

  • 配置文件读取：交易系统加载策略配置时需防止符号链接注入
  • 日志文件写入：日志目录权限应严格控制，防止硬链接攻击
  • 量化系统回测数据加载：确保数据文件未被替换

代码示例

#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>
#include <stdio.h>

/* 安全打开特权文件：防符号链接 + 防 TOCTOU + 验证属性 */
int secure_file_open(const char *path)
{
    int fd;
    struct stat st;

    /* O_NOFOLLOW: 最后组件不能是符号链接 */
    fd = open(path, O_RDONLY | O_NOFOLLOW | O_CLOEXEC);
    if (fd == -1) return -1;

    /* fstat 而非 stat：检查已打开的文件 */
    if (fstat(fd, &st) == -1) { close(fd); return -1; }

    /* 验证：普通文件、属主 root、其他用户不可写 */
    if (!S_ISREG(st.st_mode) ||
        st.st_uid != 0 ||
        (st.st_mode & S_IWOTH)) {
        close(fd);
        return -1;
    }

    /* 检查硬链接数：防止硬链接攻击 */
    if (st.st_nlink > 1) {
        close(fd);
        return -1;
    }

    return fd;
}

/* 安全创建临时文件 */
int secure_temp_file(char *tmpl, size_t len)
{
    /* mkstemp 原子创建，权限 0600 */
    int fd = mkstemp(tmpl);
    if (fd == -1) return -1;

    /* 创建后立即 unlink，文件在 fd 关闭后自动删除 */
    if (unlink(tmpl) == -1) {
        close(fd);
        return -1;
    }

    /* FD_CLOEXEC：exec 时不泄漏 */
    fcntl(fd, F_SETFD, FD_CLOEXEC);
    return fd;
}

代码自测

为什么检查硬链接数 st_nlink > 1 可以防御硬链接攻击？

攻击者可以对特权文件创建硬链接（如果他们在同一文件系统且有读权限）。当程序以 root 身份打开该硬链接时，可能修改了攻击者本无权限修改的文件。如果 st_nlink == 1，说明文件没有被额外的硬链接引用，更安全。但这种检查也有局限——攻击者可能在检查后创建硬链接，所以对关键文件应结合 O_EXCL 和专用目录使用。

为什么 mkstemp 比 mktemp + open 更安全？

mktemp 只生成文件名但不创建文件，存在 TOCTOU 竞争：在 mktemp 返回和 open 调用之间，攻击者可以创建同名文件。mkstemp 原子地生成文件名并创建文件（使用 O_CREAT|O_EXCL），消除了竞争窗口。

38.8

Don't Trust Inputs or the Environment

本章：TLPI 第 38 章

本节讲什么

特权程序不能信任任何来自用户的输入：命令行参数、环境变量、配置文件、网络数据。所有输入都需验证和净化。环境变量尤其危险，因为它们影响库函数行为（如 LD_PRELOAD、IFS、PATH）。

不受信任的输入源

输入源 风险 处理方式

environ LD_PRELOAD 劫持 清空环境或白名单

环境变量清理

/* 最安全：完全清空环境，只保留必要的 */
extern char **environ;

/* 或者：只保留白名单变量 */
clearenv();
setenv("PATH", "/usr/bin:/bin", 1);  /* 使用安全 PATH */

输入验证原则

  1. 长度限制：所有输入缓冲区使用带长度限制的函数（strncpy/snprintf）
  2. 类型检查：数字范围、字符集白名单
  3. 路径净化：拒绝 ..、绝对路径、空字节
  4. 最小暴露：错误消息不回显原始输入

HFT / 嵌入式关联

  • 交易系统接收的市场数据必须校验长度和格式，防止畸形包导致解析崩溃
  • 策略加载器不能信任策略文件内容，需沙箱化执行
  • 嵌入式设备的网络配置接口需验证所有输入字段

代码示例

#include <stdlib.h>
#include <string.h>
#include <stdio.h>
#include <limits.h>

/* 净化环境：清空后只设安全值 */
void sanitize_environment(void)
{
    clearenv();
    setenv("PATH", "/usr/bin:/bin", 1);
    setenv("IFS", " \t\n", 1);
    setenv("TZ", "UTC", 1);  /* 固定时区，避免时区注入 */
}

/* 安全路径验证：拒绝 .. 和绝对路径 */
int validate_path(const char *input, char *out, size_t outlen)
{
    if (input == NULL || *input == '\0') return -1;

    /* 拒绝绝对路径和相对回溯 */
    if (input[0] == '/' || strstr(input, "..") != NULL)
        return -1;

    /* 拒绝空字节注入 */
    if (strlen(input) != strnlen(input, outlen))
        return -1;

    /* 长度检查 */
    if (strlen(input) >= outlen) return -1;

    strncpy(out, input, outlen - 1);
    out[outlen - 1] = '\0';
    return 0;
}

/* 安全整数解析：带范围检查 */
int safe_strtoi(const char *s, int min, int max, int *result)
{
    char *endp;
    long val;

    errno = 0;
    val = strtol(s, &endp, 10);
    if (errno != 0 || *endp != '\0' || endp == s)
        return -1;  /* 解析失败 */
    if (val < min || val > max)
        return -1;  /* 超出范围 */

    *result = (int)val;
    return 0;
}

代码自测

LD_PRELOAD 环境变量为什么对特权程序特别危险？

LD_PRELOAD 指定的共享库会在程序启动时优先加载，可以覆盖（interpose）标准库函数。在 setuid 程序中，如果攻击者能设置 LD_PRELOAD，就可以替换 setuid()、open() 等函数，完全控制程序行为。现代 Linux 会忽略 setuid 程序的 LD_PRELOAD，但自定义的动态链接程序可能不受保护。最安全的做法是在特权程序启动时清空所有环境变量。

为什么路径验证中要检查空字节（null byte）？

C 字符串以空字节结尾，但某些系统调用（如 open）接受的是带长度的路径。攻击者可以在输入中嵌入空字节（如 safe.txt\0/etc/passwd），C 字符串函数只看到 safe.txt，但底层系统调用可能看到完整路径。strlen 返回第一个空字节前的长度，而 strnlen 受 outlen 限制，两者不一致即可检测到空字节注入。

38.9

Beware of Buffer Overruns

本章：TLPI 第 38 章

本节讲什么

缓冲区溢出是特权程序中最严重的安全漏洞之一。攻击者通过精心构造的输入覆盖内存，可能执行任意代码。本节介绍溢出原理和防御措施。

要点

危险函数与安全替代

危险函数 风险 安全替代
gets 无长度限制 fgets
strcpy 无边界检查 strncpy/strlcpy
strcat 无边界检查 strncat/strlcat
sprintf 无边界检查 snprintf
vsprintf 无边界检查 vsnprintf
scanf("%s") 无长度限制 scanf("%99s") 或 fgets

防御层次

层次 技术 效果
编译期 -D_FORTIFY_SOURCE=2 编译器插入边界检查
编译期 -fstack-protector-strong 栈 canary 保护
链接期 -Wl,-z,relro,-z,now GOT 只读
运行期 ASLR（内核默认开启） 地址随机化
运行期 NX bit（-z noexecstack） 栈不可执行
编码 snprintf 替代 sprintf 源头防御

常见溢出模式

  1. 栈溢出：局部数组写入超长数据 → 覆盖返回地址
  2. 堆溢出：堆缓冲区越界 → 破坏堆元数据
  3. 整数溢出：size_t len = a + b 溢出 → 分配小缓冲区 → 后续写入溢出
  4. off-by-one：循环条件 < 写成 <= → 写入一个额外字节

HFT / 嵌入式关联

  • 行情解析：二进制协议解析必须校验长度字段，防止恶意包导致溢出
  • 嵌入式设备资源受限，可能缺少 ASLR/stack-protector，编码安全更重要
  • 交易协议解码器应使用 memcpy_s 或显式长度检查

代码示例

#include <stdio.h>
#include <string.h>
#include <stdlib.h>

/* 错误示例：整数溢出导致小分配 */
void dangerous_alloc(size_t count, const char *data)
{
    /* 如果 count 很大，count * sizeof(char) 可能溢出为小值 */
    char *buf = malloc(count);  /* 可能分配很小的缓冲区 */
    if (buf) {
        memcpy(buf, data, count);  /* 写入溢出！ */
        free(buf);
    }
}

/* 正确示例：溢出检查 */
int safe_alloc_copy(size_t count, const char *data, size_t data_len)
{
    /* 检查乘法溢出（虽然 char 大小为 1，但养成习惯） */
    if (count > SIZE_MAX) return -1;

    /* 确保不超过源数据长度 */
    if (count > data_len) count = data_len;

    char *buf = malloc(count + 1);  /* +1 给终止符 */
    if (!buf) return -1;

    memcpy(buf, data, count);
    buf[count] = '\0';
    free(buf);
    return 0;
}

/* 安全的字符串拼接 */
int safe_concat(char *dst, size_t dstsize, const char *src)
{
    size_t dlen = strnlen(dst, dstsize);
    if (dlen >= dstsize) return -1;  /* dst 未终止 */

    /* snprintf 返回需要的长度，截断后安全终止 */
    int n = snprintf(dst + dlen, dstsize - dlen, "%s", src);
    if (n < 0 || (size_t)n >= dstsize - dlen) return -1;  /* 截断 */
    return 0;
}

代码自测

什么是 off-by-one 错误？举例说明。

Off-by-one 是指循环或索引多访问了一个元素。例如：char buf[8]; for (i = 0; i <= 8; i++) buf[i] = ...; —— 循环条件应该是 i < 8。这个多余的一个字节可能覆盖栈上相邻的关键数据（如保存的帧指针低位），在某些架构上可被利用。

-D_FORTIFY_SOURCE=2 如何工作？

编译器在编译期分析缓冲区大小（对已知大小的栈/静态数组），在运行时插入边界检查。例如 strcpy(dst, src) 被替换为 __strcpy_chk(dst, src, __bos(dst))，如果 src 长度超过 dst 大小，调用 __chk_fail() 终止程序。级别 2 比级别 1 多检查了 snprintf 返回值等更多场景。

Beware of Denial-of-Service Attacks

本节讲什么

特权程序可能成为拒绝服务攻击的目标。攻击者通过耗尽资源（CPU、内存、文件描述符、磁盘空间）或触发无限循环来使程序不可用。

  • 行情网关必须设置 FD 和内存限制，防止恶意连接耗尽资源
  • 交易系统用 alarm() 为每个订单操作设置超时，防止阻塞
  • 嵌入式设备内存有限，需严格控制每个连接的缓冲区大小

#include <sys/resource.h>
#include <signal.h>
#include <unistd.h>
#include <stdio.h>

/* 为特权程序设置资源限制 */
void set_resource_limits(void)
{
    struct rlimit rl;

    /* 限制 CPU 时间 30 秒 */
    rl.rlim_cur = 30; rl.rlim_max = 30;
    setrlimit(RLIMIT_CPU, &rl);

    /* 限制虚拟内存 256 MB */
    rl.rlim_cur = 256L * 1024 * 1024;
    rl.rlim_max = rl.rlim_cur;
    setrlimit(RLIMIT_AS, &rl);

    /* 限制文件描述符数 64 */
    rl.rlim_cur = 64; rl.rlim_max = 64;
    setrlimit(RLIMIT_NOFILE, &rl);

    /* 限制文件大小 1 MB（防止日志写满磁盘） */
    rl.rlim_cur = 1024 * 1024; rl.rlim_max = rl.rlim_cur;
    setrlimit(RLIMIT_FSIZE, &rl);

    /* 限制 fork 进程数 0（不需要子进程） */
    rl.rlim_cur = 0; rl.rlim_max = 0;
    setrlimit(RLIMIT_NPROC, &rl);
}

/* 操作超时模式 */
void timed_operation(void)
{
    /* 设置 10 秒 alarm */
    alarm(10);
    /* 执行可能阻塞的操作... */
    do_blocking_work();
    /* 取消 alarm */
    alarm(0);
}

/* SIGALRM 处理：操作超时 */
static volatile sig_atomic_t timed_out = 0;
void alarm_handler(int sig) { timed_out = 1; }

代码自测

为什么 RLIMIT_NPROC 设为 0 可以防止 fork 炸弹？

RLIMIT_NPROC 限制用户可创建的进程数。设为 0 意味着该用户不能创建任何新进程（fork() 返回 EAGAIN）。如果特权程序不需要创建子进程，将其设为 0 可以彻底防止 fork 炸弹攻击。注意此限制针对用户 ID，不是单个进程。

网络服务中为什么需要同时设置连接超时和请求大小限制？

连接超时（如 30 秒）防止慢速攻击（slowloris），攻击者发送极慢的数据保持连接不释放。请求大小限制防止攻击者发送超大请求体耗尽内存。两者互补：超时解决"慢"的问题，大小限制解决"大"的问题。缺少任何一个都可能被利用。

38.11

Check Return Statuses and Fail Safely

本章：TLPI 第 38 章

本节讲什么

特权程序必须检查每个系统调用的返回值，并在失败时安全退出。忽略返回值可能导致程序在非预期状态下继续运行，造成安全漏洞。"Fail safely"意味着失败时进入最安全的默认状态。

要点

返回值检查清单

系统调用 失败返回 常见错误 必须检查
open -1 ENOENT/EACCES 是
read/write -1 或短读 EINTR/短写 是
malloc NULL ENOMEM 是
setuid -1 EPERM 是（验证权限丢弃）
chroot -1 EACCES/EPERM 是
snprintf -1 或 >= size 截断 是
fork -1 EAGAIN/ENOMEM 是
exec* -1（成功不返回） ENOENT/EACCES 是

Fail-Safe 原则

原则 说明
默认拒绝 权限检查失败时拒绝访问
失败关闭 打开失败时不继续操作
立即退出 关键操作失败时终止程序
不可恢复 安全状态不可降级
日志记录 失败原因写日志

常见错误模式

/* 错误：忽略返回值 */
close(fd);  /* fd 未关闭怎么办？ */
write(sock, buf, len);  /* 短写？管道断裂？ */

/* 错误：失败后继续 */
if (setuid(0) == -1) {
    /* 什么也不做，继续以 root 运行！ */
}
do_privileged_work();  /* 危险！ */

/* 正确：失败即退出 */
if (setuid(getuid()) == -1) {
    syslog(LOG_ERR, "Failed to drop privileges: %m");
    _exit(EXIT_FAILURE);  /* 立即退出，不用 atexit */
}

HFT / 嵌入式关联

  • 交易系统：订单提交路径任何步骤失败必须回滚并报警，不可继续
  • 嵌入式设备：固件写入失败必须进入恢复模式，不能继续启动
  • 量化系统：数据源连接断开时策略应进入安全状态（停止交易）

代码示例

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <syslog.h>
#include <errno.h>
#include <string.h>

/* 安全退出：不调用 atexit 处理器 */
void safe_exit(int code)
{
    /* _exit 不执行 atexit/on_exit，避免不可预测的行为 */
    _exit(code);
}

/* 检查并处理 write 的短写 */
int safe_write(int fd, const void *buf, size_t len)
{
    const char *p = buf;
    size_t remaining = len;
    ssize_t n;

    while (remaining > 0) {
        n = write(fd, p, remaining);
        if (n == -1) {
            if (errno == EINTR) continue;  /* 被信号中断，重试 */
            return -1;  /* 真正的错误 */
        }
        if (n == 0) return -1;  /* 不应该发生 */
        p += n;
        remaining -= n;
    }
    return len;
}

/* 权限丢弃：必须验证成功 */
int verify_drop_privileges(void)
{
    uid_t target_uid = getuid();  /* 真实 UID */

    if (setgid(getgid()) == -1) {
        syslog(LOG_ERR, "setgid failed: %s", strerror(errno));
        return -1;
    }

    if (setuid(target_uid) == -1) {
        syslog(LOG_ERR, "setuid failed: %s", strerror(errno));
        return -1;
    }

    /* 验证：尝试恢复 root 应该失败 */
    if (setuid(0) != -1) {
        syslog(LOG_CRIT, "Privilege drop verified FAILED!");
        return -1;
    }

    syslog(LOG_INFO, "Privileges dropped successfully");
    return 0;
}

/* malloc 失败处理 */
void *safe_malloc(size_t size)
{
    void *ptr = malloc(size);
    if (ptr == NULL) {
        syslog(LOG_ERR, "malloc(%zu) failed: %s", size, strerror(errno));
        safe_exit(EXIT_FAILURE);
    }
    return ptr;
}

代码自测

为什么安全退出应该用 _exit() 而不是 exit()？

exit() 会调用 atexit() 注册的处理函数和 stdio 的 flush 操作。在特权程序出错时，这些操作可能访问已损坏的数据结构或执行不可预测的操作。_exit() 直接进入内核，跳过所有用户空间清理，确保程序立即停止。对于安全敏感的退出路径，_exit() 更安全。

什么是 "短写"（short write）？为什么需要循环处理？

write() 不保证一次写入所有请求的字节。对于管道、套接字等非普通文件，write 可能返回小于请求长度的值（短写）。如果只调用一次 write 而不检查返回值，部分数据可能未被写入。正确做法是用循环检查返回值并继续写入剩余数据，如 safe_write 函数所示。

代码自测

特权程序初始化时，为什么要按"chroot → setgroups → setgid → setuid"的顺序？
  1. chroot 在 setuid 之前：chroot 需要 root 权限。丢弃权限后无法再 chroot。
  2. setgroups 在 setgid 之前：setgroups 需要 root 权限。如果先 setgid 丢弃 root，setgroups 会失败，旧的补充组（可能包含 root 组）不会清除。
  3. setgid 在 setuid 之前：setuid 后程序不再是 root，setgid 可能失败（虽然有些实现允许 setgid 到自己的组）。
  4. setuid 最后：这是不可逆的权限丢弃，之后所有操作以非特权身份执行。
-fstack-protector-strong 和 -fstack-protector 有什么区别？

-fstack-protector 只在有 char 数组的函数中插入 canary 保护。-fstack-protector-strong 扩大了保护范围，对所有有局部数组（任何类型）的函数、取地址局部变量的函数都插入 canary。-fstack-protector-all 对所有函数都插入（性能开销大）。推荐使用 -fstack-protector-strong，在安全性和性能之间取得平衡。

练习 1：安全权限丢弃

题目：编写一个函数，在绑定 80 端口后丢弃 root 权限。需要考虑哪些安全因素？

参考答案 
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <grp.h>
#include <syslog.h>

int bind_and_drop(int port)
{
    int sockfd;
    struct sockaddr_in addr = {0};

    /* 1. 以 root 身份创建 socket 并绑定特权端口 */
    sockfd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
    if (sockfd < 0) return -1;

    int opt = 1;
    setsockopt(sockfd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = INADDR_ANY;
    addr.sin_port = htons(port);

    if (bind(sockfd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        close(sockfd);
        return -1;
    }

    /* 2. 清除补充组（必须在 setgid 前） */
    if (setgroups(0, NULL) < 0) {
        syslog(LOG_ERR, "setgroups: %m");
        close(sockfd);
        return -1;
    }

    /* 3. 设置 GID */
    gid_t gid = getgid();
    if (setgid(gid) < 0) {
        syslog(LOG_ERR, "setgid: %m");
        close(sockfd);
        return -1;
    }

    /* 4. 设置 UID（不可逆） */
    uid_t uid = getuid();
    if (setuid(uid) < 0) {
        syslog(LOG_ERR, "setuid: %m");
        close(sockfd);
        return -1;
    }

    /* 5. 验证权限已丢弃 */
    if (setuid(0) != -1) {
        syslog(LOG_CRIT, "Failed to drop root!");
        _exit(1);
    }

    return sockfd;
}

安全因素： - 先绑定再丢权限（顺序不可反） - setgroups 必须在 setgid 前 - setuid 是最后一步且不可逆 - 必须验证 setuid(0) 失败 - FD 设置 CLOEXEC 防止泄漏 - 错误时安全退出

练习 2：临时文件安全

题目：为什么以下代码不安全？如何修正？

/* 不安全版本 */
char tmpl[] = "/tmp/myappXXXXXX";
mktemp(tmpl);           /* 只生成文件名 */
int fd = open(tmpl, O_RDWR | O_CREAT, 0644);  /* 竞争窗口！ */
参考答案

mktemp 只生成文件名但不创建文件，在 mktemp 返回和 open 创建之间存在 TOCTOU 竞争窗口。攻击者可以预测文件名或抢先创建同名文件/符号链接。

修正方案：

char tmpl[] = "/tmp/myappXXXXXX";
int fd = mkstemp(tmpl);   /* 原子创建，权限 0600 */
if (fd < 0) return -1;

/* 创建后立即 unlink，fd 关闭后文件自动删除 */
unlink(tmpl);

/* 设置 CLOEXEC */
fcntl(fd, F_SETFD, FD_CLOEXEC);

mkstemp 使用 O_CREAT | O_EXCL 原子创建，消除竞争窗口。默认权限 0600（仅属主可读写）。

练习 3：整数溢出

题目：以下代码有什么安全漏洞？

char *read_data(int count, int size) {
    char *buf = malloc(count * size);  /* 整数溢出！ */
    /* ... 读取数据 ... */
    return buf;
}
参考答案

count * size 可能整数溢出。例如 count = 0x10000, size = 0x10000，乘积为 0x100000000，在 32 位系统上溢出为 0。malloc(0) 返回 NULL 或小缓冲区，后续写入造成堆溢出。

修正：

char *read_data(size_t count, size_t size) {
    /* 检查乘法溢出 */
    if (count != 0 && count > SIZE_MAX / size) {
        errno = ENOMEM;
        return NULL;
    }
    char *buf = malloc(count * size);
    if (buf == NULL) return NULL;
    /* ... 读取数据 ... */
    return buf;
}

使用 size_t 避免负数，显式检查乘法溢出。
