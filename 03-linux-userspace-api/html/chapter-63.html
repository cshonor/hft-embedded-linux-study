63.3

信号驱动 I/O

本章：TLPI 第 63 章 — 备用 I/O 模型（指向模块 README；本章目录尚未建章节级 README） - 上一节：63.2 I/O 多路复用 select/poll（本模块尚未建笔记） - 下一节：63.4 epoll API

源码核验：Linux v6.6 —— fs/fcntl.c（1035 行）、net/socket.c、net/core/sock.c、 include/linux/fs.h、include/linux/net.h、include/uapi/asm-generic/{fcntl,siginfo}.h、 include/linux/signal.h、include/linux/poll.h。 下文所有常量、结构体字段、行号均来自缓存的 v6.6 源码，可逐条复查。

本节讲什么

信号驱动 I/O 的核心思想是：进程不主动问内核"fd 好了没"，而是让内核在 fd 就绪时 主动给它发一个信号。本节回答四层问题：

  1. 接口层：要建立这套通知，用户态需要几步 fcntl()？每步在内核里改了什么字段？
  2. 机制层：内核用什么数据结构记住"该给谁发、发哪个信号"？
  3. ⭐ 语义层（本节核心）：内核真的每来一个包就发一次 SIGIO 吗？—— 答案是否， 有两道被几乎所有中文资料忽略的去重闸门
  4. 工程层：为什么它最终被 epoll 取代？在 HFT / 嵌入式里还有没有残余价值？

🔗 本篇只讲信号驱动 I/O 的 API 与内核实现； epoll 主场在 63.4 epoll API； io_uring 作为现代替代方案主场在 12.5 现代网络 （该模块 io_uring 命中 121 处）。

要点

1. 五步建立流程 —— 以及每一步在内核里改了什么

教科书给的建立步骤是 5 步，但通常不解释每步的内核副作用。补齐这一层：

步骤 用户态调用 内核落点（v6.6） 改了什么
① 设属主 fcntl(fd, F_SETOWN, getpid()) f_setown() fcntl.c:115 → __f_setown :107 → f_modown :88 file->f_owner.pid / .pid_type / .uid / .euid
② 设非阻塞 fcntl(fd, F_SETFL, O_NONBLOCK) setfl() fcntl.c:37 file->f_flags |= O_NONBLOCK
③ 开异步通知 fcntl(fd, F_SETFL, O_ASYNC) setfl() fcntl.c:37 → filp->f_op->fasync() :74 不是直接置位，见下节
④ 装 handler sigaction(SIGIO, ...) 进程 sighand 注册信号处理函数
⑤ （可选）换信号 fcntl(fd, F_SETSIG, signum) do_fcntl fcntl.c:393 file->f_owner.signum

步骤 ② 不是可选项，而是让通知机制正常工作的前提 —— 原因在第 6 节「两道闸门」里解释， 那是本节最反直觉的一块。

⚠️ 顺序有讲究：必须先 F_SETOWN 再开 O_ASYNC。 因为 O_ASYNC 一开，设备/协议栈立刻就可能发信号；若此时 f_owner.pid 还是 NULL， send_sigio() 会在 fcntl.c:783 的 if (!pid) goto out_unlock_fown; 直接静默返回 —— 通知被丢掉，且没有任何错误提示。

2. ⭐ O_ASYNC 在内核头文件里根本不存在

这是本节第一个"凭记忆必错"的点。去内核 uapi 里找 O_ASYNC，是找不到的：

/* include/uapi/asm-generic/fcntl.h:44-45 */
#ifndef FASYNC
#define FASYNC      00020000    /* fcntl, for BSD compatibility */
#endif

v6.6 的 include/uapi/asm-generic/fcntl.h 里 只有 FASYNC，没有 O_ASYNC。 x86 也没有自己的覆盖版本（arch/x86/include/uapi/asm/fcntl.h 在该版本不存在）。

那我们代码里写的 O_ASYNC 从哪来？glibc 自己定义的（bits/fcntl-linux.h）：

名字 来源 值（八进制） 值（十进制/十六进制）
FASYNC 内核 uapi fcntl.h:45 00020000 8192 / 0x2000
O_ASYNC glibc bits/fcntl-linux.h 020000 8192 / 0x2000

两者数值完全相同（八进制前导零不影响数值），所以它们是同义的： O_ASYNC 是 POSIX 叫法，FASYNC 是 BSD 遗留叫法，内核只认后者。

📌 实践含义：不要指望内核头文件给你 O_ASYNC。 写内核代码（或做 F_SETFL 的位运算推理）时用 FASYNC；写用户态程序用 O_ASYNC 没问题， 但要明白它是 libc 的礼物。

setfl() 里 FASYNC 的诡异处理

更值得注意的是 setfl() 怎么处理这个位。看 fs/fcntl.c:35 的掩码：

/* fs/fcntl.c:35 */
#define SETFL_MASK (O_APPEND | O_NONBLOCK | O_NDELAY | O_DIRECT | O_NOATIME)

FASYNC 不在 SETFL_MASK 里。所以 :81 那行赋值根本不会把 FASYNC 写进 f_flags：

/* fs/fcntl.c:71-81 */
    /*
     * ->fasync() is responsible for setting the FASYNC bit.
     */
    if (((arg ^ filp->f_flags) & FASYNC) && filp->f_op->fasync) {
        error = filp->f_op->fasync(fd, filp, (arg & FASYNC) != 0);
        if (error < 0)
            goto out;
        if (error > 0)
            error = 0;
    }
    spin_lock(&filp->f_lock);
    filp->f_flags = (arg & SETFL_MASK) | (filp->f_flags & ~SETFL_MASK);
    filp->f_iocb_flags = iocb_flags(filp);
    spin_unlock(&filp->f_lock);

FASYNC 位是由驱动/协议栈的 ->fasync() 回调设置的，最终落到 fasync_insert_entry() 的这一行：

/* fs/fcntl.c:934 —— fasync_insert_entry() 末尾 */
    filp->f_flags |= FASYNC;

为什么要这么绕？ 因为「开启异步通知」不是改一个标志位就完事 —— 它要分配一个 struct fasync_struct 并挂进队列。这个操作可能失败（-ENOMEM）， 如果先置位再分配，失败后标志位就撒谎了。所以内核让回调来负责置位， 保证 FASYNC 位与"这个 filp 确实在 fasync 队列里"严格等价。

源码里那句注释就是铁律（fs/fcntl.c:908-910）：

/*
 * NOTE! It is very important that the FASYNC flag always
 * match the state "is the filp on a fasync list".
 */

🔍 由此得出一个可观测的结论： 若 f_op->fasync 为 NULL（该设备不支持异步通知）， setfl() 里 filp->f_op->fasync 的判空会让整个 if 跳过 —— fcntl(fd, F_SETFL, O_ASYNC) 返回 0（成功），但什么都没发生。 这是信号驱动 I/O 最隐蔽的失败模式：开了但没真开，且无报错。

3. F_SETOWN / F_SETOWN_EX / F_SETSIG 三个命令

3.1 F_SETOWN（cmd = 8）

/* fs/fcntl.c:115 */
int f_setown(struct file *filp, int who, int force)
{
    enum pid_type type;
    struct pid *pid = NULL;
    int ret = 0;

    type = PIDTYPE_TGID;
    if (who < 0) {
        /* avoid overflow below */
        if (who == INT_MIN)
            return -EINVAL;

        type = PIDTYPE_PGID;
        who = -who;
    }

    rcu_read_lock();
    if (who) {
        pid = find_vpid(who);
        if (!pid)
            ret = -ESRCH;
    }

    if (!ret)
        __f_setown(filp, pid, type, force);
    rcu_read_unlock();

    return ret;
}

三个要点：

  1. who > 0 → 发给单个线程组（TGID）；who < 0 → 发给进程组 PGID（取绝对值）
  2. who == 0 → 撤销属主（pid = NULL，此后 send_sigio 静默返回）
  3. 🔒 信号量语义是"覆盖"不是"追加" —— 一个 fd 只有一个属主。 与 epoll 不同（一个 epoll fd 可以监听 N 个 fd），信号驱动 I/O 天然是 1:1 的

3.2 F_SETOWN_EX（cmd = 15）—— 补上线程粒度

F_SETOWN 只能发到「线程组」或「进程组」，发不到单个线程。 F_SETOWN_EX 传一个结构体解决：

/* include/uapi/asm-generic/fcntl.h:151-158 */
#define F_OWNER_TID 0
#define F_OWNER_PID 1
#define F_OWNER_PGRP    2

struct f_owner_ex {
    int type;
    __kernel_pid_t  pid;
};

内核侧的分派（fs/fcntl.c:181-193）：

owner.type 内核 enum pid_type 含义
F_OWNER_TID = 0 PIDTYPE_PID 单个线程（F_SETOWN 做不到）
F_OWNER_PID = 1 PIDTYPE_TGID 线程组（等价于 F_SETOWN 正值）
F_OWNER_PGRP = 2 PIDTYPE_PGID 进程组（等价于 F_SETOWN 负值）

⚠️ 注意 F_OWNER_TID 与 F_OWNER_PID 的编号容易记反： 直觉上 "PID" 更像单线程，但 F_OWNER_PID 是线程组（1）， 单个线程是 F_OWNER_TID（0）。

3.3 F_SETSIG（cmd = 10）—— 把 SIGIO 换成排队信号

/* fs/fcntl.c:390-397 —— do_fcntl() 内 */
    case F_GETSIG:
        err = filp->f_owner.signum;
        break;
    case F_SETSIG:
        /* arg == 0 restores default behaviour. */
        if (!valid_signal(argi)) {
            break;
        }
        err = 0;
        filp->f_owner.signum = argi;
        break;
  • F_SETSIG 0 = 恢复默认（发 SIGIO）
  • 传实时信号（SIGRTMIN ~ SIGRTMAX）才有意义：实时信号会排队

关于错误处理的一个细节：do_fcntl() 的 err 初值是 -EINVAL（fs/fcntl.c:352）：

static long do_fcntl(int fd, unsigned int cmd, unsigned long arg,
        struct file *filp)
{
    ...
    long err = -EINVAL;

所以 F_SETSIG 传非法信号时那个 break 并不是"静默成功"—— 它跳出 switch 后 return err，拿到的正是初值 -EINVAL。 （这一点很容易看错：如果默认以为 err 初值是 0，就会得出"无效信号被静默忽略"的错误结论。）

4. 内核怎么记住"发给谁、发什么" —— 两个结构体

   struct file                         struct socket
   ┌──────────────────────┐            ┌──────────────────────┐
   │ f_owner: fown_struct │            │ wq: struct socket_wq │
   │  ├─ lock   (rwlock)  │            │  ├─ wait (wq_head)   │
   │  ├─ pid    ──────────┼──► struct pid
   │  ├─ pid_type         │            │  ├─ fasync_list ─────┼──┐
   │  ├─ uid / euid       │            │  ├─ flags  ★闸门位    │  │
   │  └─ signum  (F_SETSIG)│           │  └─ rcu              │  │
   │                      │            └──────────────────────┘  │
   │ f_flags: FASYNC 位   │                                      │
   │ f_op->fasync()       │            struct fasync_struct  ◄───┘
   └──────────────────────┘             ├─ fa_lock  (rwlock)
                                        ├─ magic  (FASYNC_MAGIC)
                                        ├─ fa_fd   ★ si_fd 的来源
                                        ├─ fa_next ──► 下一个（单链表）
                                        ├─ fa_file ──► 回指 struct file
                                        └─ fa_rcu  (RCU 延迟释放)

struct fown_struct —— 记录"发给谁、发什么信号"

/* include/linux/fs.h（v6.6） */
struct fown_struct {
    rwlock_t lock;          /* protects pid, uid, euid fields */
    struct pid *pid;    /* pid or -pgrp where SIGIO should be sent */
    enum pid_type pid_type; /* Kind of process group SIGIO should be sent to */
    kuid_t uid, euid;   /* uid/euid of process setting the owner */
    int signum;     /* posix.1b rt signal to be delivered on IO */
};

⭐ struct fown_struct 里没有 fd 字段。 直觉上"设了属主就该记住是哪个 fd"，但内核不在这里存 fd —— fd 记在 fasync_struct.fa_fd 里（见下）。 实测 v4.19 / v5.10 / v5.15 / v5.16 / v5.17 / v6.6 六个版本的 struct fown_struct 全部不含 fd 字段，这不是某个版本的变化，是一直如此。

struct fasync_struct —— 记录"这个 fd 在通知队列里"

/* include/linux/fs.h（v6.6） */
struct fasync_struct {
    rwlock_t        fa_lock;
    int         magic;
    int         fa_fd;
    struct fasync_struct    *fa_next; /* singly linked list */
    struct file     *fa_file;
    struct rcu_head     fa_rcu;
};

注意 fa_next 是单链表而不是 epoll 的红黑树 —— 每个设备/套接字维护自己的 fasync 队列，查找是 O(n) 线性扫描。这是信号驱动 I/O 扩展性差的结构性原因之一 （对比 epoll 的 rb_root_cached 是 O(log n)）。

magic 字段用于校验（FASYNC_MAGIC），kill_fasync_rcu() 里会检查：

/* fs/fcntl.c:993-997 */
        if (fa->magic != FASYNC_MAGIC) {
            printk(KERN_ERR "kill_fasync: bad magic number in "
                   "fasync_struct!\n");
            return;
        }

struct socket_wq —— socket 侧的通知总控

/* include/linux/net.h（v6.6） */
struct socket_wq {
    /* Note: wait MUST be first field of socket_wq */
    wait_queue_head_t   wait;
    struct fasync_struct    *fasync_list;
    unsigned long       flags; /* %SOCKWQ_ASYNC_NOSPACE, etc */
    struct rcu_head     rcu;
} ____cacheline_aligned_in_smp;

flags 就是第 6 节那两道闸门的位置。它历史上不在 socket_wq 里， 源码注释交代了迁移动机（include/linux/net.h:35-37）：

/* Historically, SOCKWQ_ASYNC_NOSPACE & SOCKWQ_ASYNC_WAITDATA were located
 * in sock->flags, but moved into sk->sk_wq->flags to be RCU protected.
 * Eventually all flags will be in sk->sk_wq->flags.
 */

📌 迁移到 sk_wq->flags 的目的是让它能被 RCU 保护（sk_wq 本身是 RCU 指针 rcu_dereference(sk->sk_wq)），这样读侧不用持 sk 锁就能安全读闸门位。

5. 注册链路：从 fcntl(O_ASYNC) 到挂进队列

socket 的 ->fasync() 回调是 sock_fasync()：

/* net/socket.c */
static int sock_fasync(int fd, struct file *filp, int on)
{
    struct socket *sock = filp->private_data;
    struct sock *sk = sock->sk;
    struct socket_wq *wq = &sock->wq;

    if (sk == NULL)
        return -EINVAL;

    lock_sock(sk);
    fasync_helper(fd, filp, on, &wq->fasync_list);

    if (!wq->fasync_list)
        sock_reset_flag(sk, SOCK_FASYNC);
    else
        sock_set_flag(sk, SOCK_FASYNC);

    release_sock(sk);
    return 0;
}

整条链路：

用户态 fcntl(fd, F_SETFL, O_ASYNC)
   │
   ▼
SYSCALL fcntl  ─►  do_fcntl()  ─►  F_SETFL 分支  ─►  setfl()      [fs/fcntl.c:37]
   │
   ▼  setfl() 发现 FASYNC 位翻转 → 调 filp->f_op->fasync()
sock_fasync()                                                     [net/socket.c]
   │
   ├─► fasync_helper(fd, filp, on, &wq->fasync_list)               [fs/fcntl.c:975]
   │        │
   │        ├─ on = 0 → fasync_remove_entry()                      [fs/fcntl.c:864]
   │        └─ on = 1 → fasync_add_entry() → fasync_insert_entry() [fs/fcntl.c:912]
   │                        ├─ 已存在（同 filp）→ 只更新 fa_fd，返回旧条目
   │                        └─ 不存在 → 新分配、挂链表头、filp->f_flags |= FASYNC
   │
   └─► 根据 wq->fasync_list 是否为空，设/清 SOCK_FASYNC 标志

fasync_insert_entry() 的完整实现：

/* fs/fcntl.c:912 */
struct fasync_struct *fasync_insert_entry(int fd, struct file *filp, struct fasync_struct **fapp, struct fasync_struct *new)
{
        struct fasync_struct *fa, **fp;

    spin_lock(&filp->f_lock);
    spin_lock(&fasync_lock);
    for (fp = fapp; (fa = *fp) != NULL; fp = &fa->fa_next) {
        if (fa->fa_file != filp)
            continue;

        write_lock_irq(&fa->fa_lock);
        fa->fa_fd = fd;
        write_unlock_irq(&fa->fa_lock);
        goto out;
    }

    rwlock_init(&new->fa_lock);
    new->magic = FASYNC_MAGIC;
    new->fa_file = filp;
    new->fa_fd = fd;
    new->fa_next = *fapp;
    rcu_assign_pointer(*fapp, new);
    filp->f_flags |= FASYNC;

out:
    spin_unlock(&fasync_lock);
    spin_unlock(&filp->f_lock);
    return fa;
}

三个可观察的性质：

  1. 按 fa_file 去重：同一个 struct file 只占一个队列条目，重复调用只更新 fa_fd
  2. 插入是头插（new->fa_next = *fapp），无排序
  3. RCU 发布（rcu_assign_pointer），因为发送侧 kill_fasync_rcu() 只持 RCU 读锁

fasync_helper() 的返回值语义（常被忽略）：

返回 含义
< 0 出错（如 -ENOMEM）
0 什么都没改，只是更新了已有条目（fasync_add_entry 的注释："did no changes"）
> 0 真的新增/删除了条目

注意 setfl() 里 if (error > 0) error = 0; —— 把正数返回值统一收敛成 0， 因为 fcntl() 对用户态只该返回 0 或负 errno。

6. ⭐⭐ 两道去重闸门 —— 内核并不是每来一个包就发信号

这是本节最重要、也最容易被跳过的一块。

普遍的说法是「信号驱动 I/O 里，TCP 每个事件都会触发 SIGIO，所以信号太频繁」。 按 v6.6 源码，这个说法不准确 —— 内核在 socket 层放了两道闸门， 会主动抑制大部分重复通知。

看 sock_wake_async()（net/socket.c）：

/* net/socket.c */
int sock_wake_async(struct socket_wq *wq, int how, int band)
{
    if (!wq || !wq->fasync_list)
        return -1;

    switch (how) {
    case SOCK_WAKE_WAITD:
        if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
            break;
        goto call_kill;
    case SOCK_WAKE_SPACE:
        if (!test_and_clear_bit(SOCKWQ_ASYNC_NOSPACE, &wq->flags))
            break;
        fallthrough;
    case SOCK_WAKE_IO:

        kill_fasync(&wq->fasync_list, SIGIO, band);
        break;
    case SOCK_WAKE_URG:
        kill_fasync(&wq->fasync_list, SIGURG, band);
    }

    return 0;
}

⭐ 语义 = 边沿触发（edge-triggered）： 只有发生「可写 → 不可写 → 可写」的跃变，才会发一次 SIGIO/POLL_OUT。 缓冲区一直可写时，一个信号都不会发。

这与 epoll 的 EPOLLET 是同一类设计哲学： 只在状态跃变时通知一次，避免"水平条件一直成立 → 疯狂通知"。

这个位的置位点极其反直觉 —— 它只在阻塞等待路径里被置位：

/* net/core/sock.c:3019 —— sk_wait_data() */

{

    int rc;

    sk_clear_bit(SOCKWQ_ASYNC_WAITDATA, sk);
    remove_wait_queue(sk_sleep(sk), &wait);
    return rc;
}

⭐⭐ 语义解读：SOCKWQ_ASYNC_WAITDATA 的真名应该叫「有人正在阻塞等数据」。

  • 位已置 → 说明某线程正卡在 sk_wait_data() 里 → 它自己会被唤醒，不需要额外发信号
  • 位未置 → 没人在阻塞等 → 才发 SIGIO 通知用户态

由此推出本节最有实践价值的一条规律：

socket 模式 SOCKWQ_ASYNC_WAITDATA 状态 SIGIO 行为
阻塞（无 O_NONBLOCK），线程卡在读 置位 ❌ 几乎收不到 SIGIO（被闸门 B 挡住）
阻塞，但线程没在读（在干别的） 未置 ✅ 每个报文一次 SIGIO
非阻塞（O_NONBLOCK）+ 事件循环 永远未置 ✅✅ 每个报文一次 SIGIO —— 这才是"过于频繁"的真正来源

🔑 这就解释了建立流程里第 ② 步（设 O_NONBLOCK）的真实作用： 它不是"为了避免 read 阻塞"这种泛泛的理由，而是 让闸门 B 永远处于"开启"状态，从而保证通知不会被抑制。 反过来说：阻塞 socket 配 O_ASYNC 是一个自相矛盾的组合 —— 你一边阻塞等、一边又要异步通知，内核的闸门 B 会让通知几乎不出现。

两道闸门的意义：与 epoll 的设计对照

信号驱动 I/O epoll
去重的责任方 内核（sk_wq->flags 两位） 内核（rdllist + ovflist）
可读语义 每个报文一次（非阻塞时） LT：不读就一直报；ET：跃变才报
可写语义 只有跃变才报（闸门 A，EPOLLET 式） 取决于 LT/ET 注册
漏通知的代价 信号可能被合并/丢弃（见 §8.3） 事件在 rdllist 里不会丢

⚠️ 一个值得注意的不对称： 可写方向是边沿触发式的（闸门 A），可读方向默认却不是（闸门 B 只在阻塞时挡）。 于是在非阻塞场景下，可读通知可能远多于可写通知 —— 这与 epoll 的默认行为（两个方向都是 LT）正好相反。

kill_fasync() 的两个工程细节：

/* fs/fcntl.c:1012 */
void kill_fasync(struct fasync_struct **fp, int sig, int band)
{
    /* First a quick test without locking: usually
     * the list is empty.
     */
    if (*fp) {
        rcu_read_lock();
        kill_fasync_rcu(rcu_dereference(*fp), sig, band);
        rcu_read_unlock();
    }
}
EXPORT_SYMBOL(kill_fasync);
  1. 无锁快查：先裸读 *fp，为空就直接返回。这是给「绝大多数 fd 没开 O_ASYNC」 的常见情况做优化 —— 否则每个包的接收路径都要白拿一次 RCU 读锁
  2. EXPORT_SYMBOL：kill_fasync 是驱动可见的公开 API， 字符设备驱动在自己的中断处理里直接调它（这也是它必须快的原因）

SIGURG 的特判

/* fs/fcntl.c:1000-1006 */
        if (fa->fa_file) {
            fown = &fa->fa_file->f_owner;
            /* Don't send SIGURG to processes which have not set a
               queued signum: SIGURG has its own default signalling
               mechanism. */

即：如果用户没用 F_SETSIG 指定信号，就不要送 SIGURG。 因为 SIGURG 有自己默认的处理机制（sk_send_sigurg() 会先试 send_sigurg() 直接走 f_owner），重复送会造成语义混乱。

注意 sk_send_sigurg() 的写法：

{

8. ⭐ 信号里到底携带什么 —— siginfo 的三个关键字段

这是原笔记里需要修正的一处。原笔记说「标准 SIGIO 不携带 fd 信息」， 这个说法对一半：

  • ❌ 错的一半：用 F_SETSIG + SA_SIGINFO 时，信号明确携带 fd 和事件类型
  • ✅ 对的一半：默认情况（signum == 0，走普通 SIGIO）确实不携带 —— 见 §8.3

8.1 构造 siginfo 的代码

/* fs/fcntl.c:717-773 —— send_sigio_to_task()  */
static void send_sigio_to_task(struct task_struct *p,
                   struct fown_struct *fown,
                   int fd, int reason, enum pid_type type)
{
    /*
     * F_SETSIG can change ->signum lockless in parallel, make
     * sure we read it once and use the same value throughout.
     */
    int signum = READ_ONCE(fown->signum);

    if (!sigio_perm(p, fown, signum))
        return;

    switch (signum) {
        default: {
            kernel_siginfo_t si;

            clear_siginfo(&si);
            si.si_signo = signum;
            si.si_errno = 0;
                si.si_code  = reason;
            /*
             * Posix definies POLL_IN and friends to be signal
             * specific si_codes for SIG_POLL.  Linux extended
             * these si_codes to other signals in a way that is
             * ambiguous if other signals also have signal
             * specific si_codes.  In that case use SI_SIGIO instead
             * to remove the ambiguity.
             */
            if ((signum != SIGPOLL) && sig_specific_sicodes(signum))
                si.si_code = SI_SIGIO;

            /* Make sure we are called with one of the POLL_*
               reasons, otherwise we could leak kernel stack into
               userspace.  */
            BUG_ON((reason < POLL_IN) || ((reason - POLL_IN) >= NSIGPOLL));
            if (reason - POLL_IN >= NSIGPOLL)
                si.si_band  = ~0L;
            else
                si.si_band = mangle_poll(band_table[reason - POLL_IN]);
            si.si_fd    = fd;
            if (!do_send_sig_info(signum, &si, p, type))
                break;
        }
            fallthrough;    /* fall back on the old plain SIGIO signal */
        case 0:
            do_send_sig_info(SIGIO, SEND_SIG_PRIV, p, type);
    }
}

三个字段：

字段 内容 来源
si_signo 你用 F_SETSIG 设的信号号 READ_ONCE(fown->signum)
si_code 事件原因：POLL_IN/POLL_OUT/POLL_ERR/… 或 SI_SIGIO reason 参数
si_band poll 位掩码（POLLIN/POLLOUT/… 的位组合） mangle_poll(band_table[...])
si_fd 就绪的文件描述符 fasync_struct.fa_fd

8.2 si_band 是怎么算出来的 —— 两级映射

事件原因（reason）是紧凑的 POLL_IN..POLL_HUP 编号：

/* include/uapi/asm-generic/siginfo.h:295-301 */
#define POLL_IN     1   /* data input available */
#define POLL_OUT    2   /* output buffers available */
#define POLL_MSG    3   /* input message available */
#define POLL_ERR    4   /* i/o error */
#define POLL_PRI    5   /* high priority input available */
#define POLL_HUP    6   /* device disconnected */
#define NSIGPOLL    6

第一级：band_table[] 把编号翻译成内核内部的 EPOLL* 位掩码：

/* fs/fcntl.c:692 */
static const __poll_t band_table[NSIGPOLL] = {
    EPOLLIN | EPOLLRDNORM,          /* POLL_IN */
    EPOLLOUT | EPOLLWRNORM | EPOLLWRBAND,   /* POLL_OUT */
    EPOLLIN | EPOLLRDNORM | EPOLLMSG,       /* POLL_MSG */
    EPOLLERR,               /* POLL_ERR */
    EPOLLPRI | EPOLLRDBAND,         /* POLL_PRI */
    EPOLLHUP | EPOLLERR         /* POLL_HUP */
};

第二级：mangle_poll() 把 EPOLL* 位翻成用户态看到的 POLL* 位（__u16）：

/* include/linux/poll.h */
static inline __u16 mangle_poll(__poll_t val)
{
    __u16 v = (__force __u16)val;
#define M(X) __MAP(v, (__force __u16)EPOLL##X, POLL##X)
    return M(IN) | M(OUT) | M(PRI) | M(ERR) | M(NVAL) |
        M(RDNORM) | M(RDBAND) | M(WRNORM) | M(WRBAND) |
        M(HUP) | M(RDHUP) | M(MSG);
#undef M
}

所以 POLL_IN 最终给到用户态的 si_band 是 POLLIN | POLLRDNORM。

📌 注意 POLL_HUP 映射成 EPOLLHUP | EPOLLERR —— 挂断同时带错误位。 处理 si_band 时不能只判 POLLHUP。

8.3 ⭐ 什么时候 si_code 会退化成 SI_SIGIO

    if ((signum != SIGPOLL) && sig_specific_sicodes(signum))
        si.si_code = SI_SIGIO;

sig_specific_sicodes() 查的是这个掩码（include/linux/signal.h:437-448）：

#define SIG_SPECIFIC_SICODES_MASK (\
    rt_sigmask(SIGILL)    |  rt_sigmask(SIGFPE)    | \
    rt_sigmask(SIGSEGV)   |  rt_sigmask(SIGBUS)    | \
    rt_sigmask(SIGTRAP)   |  rt_sigmask(SIGCHLD)   | \
    rt_sigmask(SIGPOLL)   |  rt_sigmask(SIGSYS)    | \
    SIGEMT_MASK                                    )

#define sig_specific_sicodes(sig)   siginmask(sig, SIG_SPECIFIC_SICODES_MASK)

这些信号已经有自己专属的 si_code 取值空间（比如 SIGSEGV 的 SEGV_MAPERR）， POLL_IN（=1）这种值会与之冲突。所以内核把 si_code 改成 SI_SIGIO（= -5）， 代价是丢失了事件类型信息 —— 用户态只能去看 si_band。

⚠️ 实践结论：F_SETSIG 应该选普通实时信号（SIGRTMIN+n）， 不要选 SIGILL/SIGFPE/SIGSEGV/SIGBUS/SIGTRAP/SIGCHLD/SIGPOLL/SIGSYS。 选了后者，si_code 会退化成 SI_SIGIO。

8.4 ⭐⭐ 默认 SIGIO 不排队 —— fallthrough 降级

            if (!do_send_sig_info(signum, &si, p, type))
                break;
        }
            fallthrough;    /* fall back on the old plain SIGIO signal */
        case 0:
            do_send_sig_info(SIGIO, SEND_SIG_PRIV, p, type);

两条路径的差别巨大：

默认（signum == 0） F_SETSIG 指定实时信号
走哪条 case 0 分支 default 分支
携带 siginfo ❌ SEND_SIG_PRIV（无 siginfo） ✅ 完整 si_fd/si_band/si_code
是否排队 ❌ 不排队（标准信号，多个合并成一个） ✅ 排队（实时信号，逐个保留）
溢出行为 合并 → 丢事件 队列满 → fallthrough 降级为普通 SIGIO

⭐ 这就是原笔记"不携带 fd 信息"说法成立的唯一场景： 默认 SIGIO（signum=0）走 SEND_SIG_PRIV，根本没有 siginfo， 所以 handler 里拿不到 si_fd。

也正因为不排队：连续到达 10 个报文，进程可能只收到 1 个 SIGIO。 用 F_SETSIG 换成实时信号后，10 个报文会排 10 个信号 —— 但队列满了仍会降级。

🔑 这是信号驱动 I/O 与 epoll 最本质的差距： epoll 的事件存在内核的 rdllist 里，不会因为"用户还没取"就丢； 而信号（尤其默认的 SIGIO）会被合并，通知数量与事件数量不再一一对应。 对 HFT 这类要求"每个事件都可追溯"的场景，这是致命的。

8.5 权限检查 —— sigio_perm()

/* fs/fcntl.c:702 */
static inline int sigio_perm(struct task_struct *p,
                             struct fown_struct *fown, int sig)
{
    const struct cred *cred;
    int ret;

    rcu_read_lock();
    cred = __task_cred(p);
    ret = ((uid_eq(fown->euid, GLOBAL_ROOT_UID) ||
        uid_eq(fown->euid, cred->suid) || uid_eq(fown->euid, cred->uid) ||
        uid_eq(fown->uid,  cred->suid) || uid_eq(fown->uid,  cred->uid)) &&
           !security_file_send_sigiotask(p, fown, sig));
    rcu_read_unlock();
    return ret;
}

规则：设置属主时记录的 uid/euid，必须与被通知进程的 uid 或 suid 之一匹配 （或是 root），并且还要过 LSM 钩子 security_file_send_sigiotask()（SELinux/AppArmor 的接入点）。

📌 这防止的是：A 进程给 B 进程的 fd 设属主，让内核替自己骚扰 B。 不过注意判据是 uid 匹配而不是"同一进程"—— 同一 uid 下的跨进程通知是允许的。

最后一行的注释解释了为什么用 READ_ONCE 而不是加锁：

F_SETSIG 是在 do_fcntl 里无锁直写 filp->f_owner.signum 的（:396）， 而发送侧可能同时在读。内核的做法是：写侧不管，读侧用 READ_ONCE 保证 读到的是一个完整的、前后一致的值（不会读到撕裂的半写值，且整段逻辑复用同一个值）。

全部不含 fd。 所以"F_SETOWN 记录了 fd"是错的 —— fd 存在于 fasync_struct.fa_fd，而 fasync_struct 是开 O_ASYNC 时才创建的。

这也解释了一个行为差异：只 F_SETOWN 而不开 O_ASYNC，什么都不会发生， 因为压根没有 fasync_struct，send_sigio() 永远不会被调用到。

10. 优缺点（修正版）

原笔记的优缺点表基本成立，但需要补上机制层的根据：

优势 机制依据
无需轮询 事件由中断/协议栈直接触发 sk->sk_data_ready → kill_fasync()
不阻塞 进程继续执行，信号 handler 异步跑
内核侧有去重 ⭐ 两道闸门（§6）—— 可写方向是跃变触发，可读方向在阻塞时被抑制
注册成本低 一个 fd 一个 fasync_struct（对比 epoll 的 epitem + 红黑树节点）
劣势 机制依据

队列满会降级 rt signal 排队失败 → fallthrough 到普通 SIGIO（§8.4）
每个信号一次上下文切换 信号投递走 do_send_sig_info → 设置 TIF_SIGPENDING → 返回用户态前进入 handler
查找是 O(n) fasync_struct 是单链表（fa_next），kill_fasync_rcu 线性遍历
1:1 限制 fown_struct 只有一个 pid（+pid_type），一个 fd 只能通知一个目标（§3.1）

🔑 第 1、2 条（丢事件）是它不适合严肃场景的决定性原因， 而不是常说的"信号开销大"。开销大的问题可以靠批量处理缓解， 丢事件无法缓解。

11. 与 epoll 的对比（修正原笔记的三处错误）

原笔记的对比表里有三处需要按 v6.6 源码修正：

维度 信号驱动 I/O epoll 原笔记的说法 修正

fd 信息 默认无，F_SETSIG+SA_SIGINFO 时有 si_fd epoll_data_t（8 字节自由携带） 「不携带」 ⚠️ 不准确：配好了能携带

📌 关于"epoll 用共享内存"这个常见误解： epoll 的接口是 epoll_wait(epfd, events, maxevents, timeout)， 内核把就绪事件拷贝到用户提供的 events 数组里。 全程没有 mmap，没有共享内存页。真正用共享内存做 I/O 的是 io_uring （SQ/CQ 环形缓冲区 mmap 到用户态）—— 那属于 12.5 现代网络 的范畴。

12. 现代内核里还有哪些残余用途

原笔记说「被 epoll 完全取代」，方向上对，但有几个它仍在被使用的场景值得知道：

场景 说明
终端设备 / 串口 tty 层是最经典的 fasync 用户：键盘输入、modem 状态变化。SIGIO 在 POSIX 终端语义里有规范地位
SIGURG 带外数据通知只有信号这一条路（sk_send_sigurg()），epoll 的 EPOLLPRI 是另一套机制，不能互相替代
文件租约（file lease） F_SETLEASE / F_NOTIFY 这套机制复用 fasync 基础设施（fasync_helper 的注释里明确写了 "and for regular files by the file lease code"）
字符设备驱动 自定义硬件（FPGA、ADC、GPIO 中断）在驱动里调 kill_fasync() 通知用户态，是最省事的方案
signalfd() ⭐ 把信号转成 fd，配合 epoll 使用 —— 这反而是"信号机制在现代程序里的最佳归宿"（见 63.5）

🔑 最有价值的一条：signalfd() + epoll 的组合让信号重新变得可用 —— 信号变成可读的 fd，塞进同一个 epoll 事件循环， 既保留了信号的语义，又摆脱了"handler 里能干什么"的限制。 这是 63.5 的主题。

HFT / 嵌入式关联

路线 要点
HFT · 结论 不用信号驱动 I/O 做行情/订单主路径。三条硬伤见下
HFT · 硬伤 1：丢事件 默认 SIGIO 不排队（§8.4），多个报文合并成一个信号。行情链路要求每个 tick 可追溯，信号语义天然不满足
HFT · 硬伤 2：抖动 信号投递要设置 TIF_SIGPENDING 并在返回用户态前进入 handler；若进程正在跑热路径（或持有锁），handler 的插入点是不可预测的。抖动量级是微秒到几十微秒，且无上界
HFT · 硬伤 3：handler 限制 handler 里只能调 async-signal-safe 函数。不能分配内存、不能加锁（会死锁）、不能调大多数库函数 —— 这对复杂业务逻辑是致命约束
HFT · 唯一可用场景 用它做低频旁路通知（如"风控阈值被触发"、"运维信号"），主路径仍走 epoll / busy-poll
HFT · 该用什么 行情：epoll + SO_BUSY_POLL / AF_XDP；订单：io_uring。见 63.4 与 12.5 现代网络
嵌入式 · 串口/传感器 ⭐ 这里信号驱动 I/O 是合理选择：数据量低（KB/s 级）、事件稀疏、CPU 弱（不能跑轮询浪费 cycles）、丢事件的后果可控。比起开一个线程阻塞 read()，SIGIO 省一个栈
嵌入式 · 自定义驱动 在字符设备驱动里 kill_fasync() 通知用户态，是 Linux 驱动教材的标准范式，代码量远小于实现 poll/epoll 回调
嵌入式 · 实时性 ⚠️ 注意：SIGIO 的投递不保证优先级。若需要硬实时，应配合 sched_setscheduler(SCHED_FIFO) + 信号优先级（实时信号号越小优先级越高：SIGRTMIN 最高）
通用 · 迁移建议 旧代码里见到 O_ASYNC，优先改 epoll；若必须保留信号语义，改 signalfd() 再并入 epoll

📌 一个容易忽略的点：实时信号的投递优先级由信号号决定，号越小越优先。 所以 F_SETSIG(SIGRTMIN) 不只是"能排队"，还意味着最高投递优先级。 这在 RT 场景下是有意义的调优手段。

代码示例

示例 1：最小可用骨架 —— 带 SA_SIGINFO 拿到 si_fd / si_band

/* sigio_min.c —— 信号驱动 I/O 最小骨架（UDP）
 * 编译: gcc -O2 -Wall -o sigio_min sigio_min.c
 * 要点: 用 SA_SIGINFO + F_SETSIG 才能拿到 si_fd / si_band
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <netinet/in.h>
#include <sys/socket.h>

static volatile sig_atomic_t got = 0;

static void sigio_handler(int sig, siginfo_t *si, void *uc)
{
    (void)sig; (void)uc;
    /* si->si_code 是 POLL_IN/POLL_OUT/POLL_ERR...（若被退化则为 SI_SIGIO）
     * si->si_band 是 POLL* 位掩码（POLLIN|POLLRDNORM 等）
     * si->si_fd   是就绪的 fd —— 这正是原笔记说"不携带"的那个信息 */
    printf("SIGIO: fd=%d code=%d band=0x%x (POLLIN=%d)\n",
           si->si_fd, si->si_code, si->si_band,
           !!(si->si_band & POLLIN));
    got = 1;
}

int main(void)
{
    int fd = socket(AF_INET, SOCK_DGRAM, 0);
    if (fd < 0) { perror("socket"); return 1; }

    struct sockaddr_in a = {0};
    a.sin_family = AF_INET;
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    a.sin_port = htons(9999);
    if (bind(fd, (struct sockaddr *)&a, sizeof a) < 0) {
        perror("bind"); return 1;
    }

    /* ① 装 handler —— 必须 SA_SIGINFO，否则拿不到 siginfo */
    struct sigaction sa = {0};
    sa.sa_sigaction = sigio_handler;
    sa.sa_flags = SA_SIGINFO | SA_RESTART;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGIO, &sa, NULL) < 0) { perror("sigaction"); return 1; }

    /* ② 设属主 —— 必须早于 O_ASYNC，否则首批通知会被静默丢弃 */
    if (fcntl(fd, F_SETOWN, getpid()) < 0) { perror("F_SETOWN"); return 1; }

    /* ③ 换成一个实时信号：既排队、又带 siginfo
     *    注意别用 SIGSEGV/SIGILL/SIGCHLD/SIGPOLL 等有专用 si_code 的信号，
     *    否则 si_code 会被内核改成 SI_SIGIO，丢失事件类型 */
    int rt = SIGRTMIN;                      /* 实时信号中优先级最高 */
    if (fcntl(fd, F_SETSIG, rt) < 0) { perror("F_SETSIG"); return 1; }

    /* ④ 非阻塞 + 异步通知
     *    O_NONBLOCK 不是可选项：它保证闸门 B(SOCKWQ_ASYNC_WAITDATA) 永远开启，
     *    否则数据到达时通知会被抑制 */
    int fl = fcntl(fd, F_GETFL);
    if (fcntl(fd, F_SETFL, fl | O_NONBLOCK | O_ASYNC) < 0) {
        perror("F_SETFL"); return 1;
    }

    printf("waiting on UDP 127.0.0.1:9999  (rt signal = %d)\n", rt);
    printf("try:  echo hello | nc -u 127.0.0.1 9999\n");

    /* 生产环境不会这么写（pause 无法与业务逻辑组合），
     * 这里只为演示。真实用法见示例 3 的 signalfd 方案 */
    while (!got)
        pause();

    char buf[1500];
    ssize_t n = recv(fd, buf, sizeof buf, 0);       /* 不会阻塞：有数据 */
    printf("recv %zd bytes\n", n);

    close(fd);
    return 0;
}

示例 2：观测两道闸门 —— 计数而非猜

下面这个程序用 poll() 把"可写跃变"和"实际收到 SIGIO"的次数对照起来， 直观展示闸门 A 的边沿语义。

/* sigio_gate.c —— 验证闸门 A(SOCKWQ_ASYNC_NOSPACE) 的边沿语义
 * 做法：不断向一个 UDP socket 发送数据直到发送缓冲满（置位 NOSPACE），
 *       再读掉，观察 POLL_OUT 类型的 SIGIO 只出现一次，而不是每次腾空都来一次。
 * 编译: gcc -O2 -Wall -o sigio_gate sigio_gate.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <netinet/in.h>
#include <sys/socket.h>

static volatile sig_atomic_t n_pollin = 0, n_pollout = 0;

static void h(int sig, siginfo_t *si, void *uc)
{
    (void)sig; (void)uc;
    /* 注意：内核给的是 POLL* 位（mangle_poll 之后），不是 EPOLL* */
    if (si->si_band & (POLLOUT | POLLWRNORM)) n_pollout++;
    if (si->si_band & (POLLIN  | POLLRDNORM)) n_pollin++;
}

static int setup_async(int fd, int signum)
{
    struct sigaction sa = {0};
    sa.sa_sigaction = h;
    sa.sa_flags = SA_SIGINFO;
    sigemptyset(&sa.sa_mask);
    if (sigaction(signum, &sa, NULL) < 0) return -1;
    if (fcntl(fd, F_SETOWN, getpid()) < 0) return -1;
    if (fcntl(fd, F_SETSIG, signum) < 0) return -1;
    int fl = fcntl(fd, F_GETFL);
    return fcntl(fd, F_SETFL, fl | O_NONBLOCK | O_ASYNC);
}

int main(void)
{
    /* 用 socketpair 造一对 UDP 式的对端，简化实验 */
    int sv[2];
    if (socketpair(AF_UNIX, SOCK_DGRAM, 0, sv) < 0) { perror("socketpair"); return 1; }

    int sig = SIGRTMIN;
    if (setup_async(sv[0], sig) < 0) { perror("setup_async"); return 1; }

    char buf[64 * 1024];
    memset(buf, 'x', sizeof buf);

    /* ① 不停写，直到 EAGAIN —— 此刻内核置位 SOCKWQ_ASYNC_NOSPACE（欠账） */
    long wrote = 0, bytes = 0;
    for (;;) {
        ssize_t n = send(sv[0], buf, sizeof buf, MSG_DONTWAIT);
        if (n < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break;
            if (errno == ENOBUFS) break;
            perror("send"); return 1;
        }
        bytes += n;
        if (++wrote > 100000) { fprintf(stderr, "sendbuf never filled?\n"); break; }
    }
    printf("filled send buffer: %ld bytes, %ld sends  -> NOSPACE 位已置\n",
           bytes, wrote);

    /* ② 从对端把数据读掉，让发送侧腾出空间 —— 触发 sock_def_write_space()
     *    → sk_wake_async(SOCK_WAKE_SPACE, POLL_OUT)
     *    → test_and_clear_bit(NOSPACE)：欠账则发一次 SIGIO 并清账 */
    size_t drained = 0;
    for (;;) {
        ssize_t n = recv(sv[1], buf, sizeof buf, MSG_DONTWAIT);
        if (n <= 0) break;
        drained += (size_t)n;
    }
    printf("drained %zu bytes from peer\n", drained);

    /* ③ 让信号有机会投递 */
    usleep(200 * 1000);

    printf("SIGIO 计数: POLLIN=%d  POLLOUT=%d\n", n_pollin, n_pollout);
    printf("\n预期解读:\n");
    printf("  - POLLOUT 是 '跃变' 语义：缓冲区由满变空才通知一次，\n");
    printf("    而不是每腾出一块就通知一次（闸门 A: test_and_clear_bit）\n");
    printf("  - 若你在同一 socket 上 O_NONBLOCK 且持续收数据，\n");
    printf("    POLLIN 会远多于 POLLOUT（闸门 B 在非阻塞时不抑制）\n");

    close(sv[0]); close(sv[1]);
    return 0;
}

⚠️ 两个例子里的 printf() 不是 async-signal-safe 的， 仅用于演示。生产代码里 handler 只应做 write() 到一个 O_NONBLOCK 的自管道，或干脆用示例 3 的 signalfd 方案。

示例 3：现代写法 —— signalfd() 把信号并进 epoll

/* sigio_signalfd.c —— 推荐的现代形态：信号 → fd → epoll
 * 好处: ① 不再受 async-signal-safe 限制
 *       ② 信号与 socket 在同一个 epoll 循环里，无竞态
 *       ③ 可用 epoll_pwait2 做纳秒级超时
 * 编译: gcc -O2 -Wall -o sigio_signalfd sigio_signalfd.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <sys/signalfd.h>
#include <sys/epoll.h>
#include <netinet/in.h>
#include <sys/socket.h>

int main(void)
{
    int udp = socket(AF_INET, SOCK_DGRAM, 0);
    if (udp < 0) { perror("socket"); return 1; }

    struct sockaddr_in a = {0};
    a.sin_family = AF_INET;
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    a.sin_port = htons(9998);
    if (bind(udp, (struct sockaddr *)&a, sizeof a) < 0) { perror("bind"); return 1; }

    /* ① 先把 SIGIO 屏蔽掉 —— signalfd 只接管"被阻塞"的信号 */
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGIO);
    if (sigprocmask(SIG_BLOCK, &mask, NULL) < 0) { perror("sigprocmask"); return 1; }

    /* ② 信号变 fd */
    int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
    if (sfd < 0) { perror("signalfd"); return 1; }

    /* ③ socket 侧照旧设属主 + O_ASYNC（信号不再进 handler，而是排队等 signalfd 读） */
    if (fcntl(udp, F_SETOWN, getpid()) < 0) { perror("F_SETOWN"); return 1; }
    int fl = fcntl(udp, F_GETFL);
    if (fcntl(udp, F_SETFL, fl | O_NONBLOCK | O_ASYNC) < 0) { perror("F_SETFL"); return 1; }

    /* ④ 两个 fd 进同一个 epoll */
    int ep = epoll_create1(EPOLL_CLOEXEC);
    if (ep < 0) { perror("epoll_create1"); return 1; }

    struct epoll_event ev = {0};
    ev.events = EPOLLIN;
    ev.data.fd = sfd;   epoll_ctl(ep, EPOLL_CTL_ADD, sfd, &ev);
    ev.data.fd = udp;   epoll_ctl(ep, EPOLL_CTL_ADD, udp, &ev);

    printf("epoll + signalfd ready on UDP 127.0.0.1:9998\n");

    struct epoll_event out[16];
    for (int i = 0; i < 20; ) {
        int n = epoll_wait(ep, out, 16, 5000);
        if (n < 0) { if (errno == EINTR) continue; perror("epoll_wait"); break; }
        if (n == 0) { printf("(timeout)\n"); break; }

        for (int k = 0; k < n; k++) {
            if (out[k].data.fd == sfd) {
                /* 读一个 signalfd_siginfo —— 这里能拿到完整的 si_fd / si_band */
                struct signalfd_siginfo si;
                while (read(sfd, &si, sizeof si) == sizeof si) {
                    printf("[signal] signo=%u code=%d band=0x%x fd=%d\n",
                           si.ssi_signo, si.ssi_code, si.ssi_band, si.ssi_fd);
                }
                i++;
            } else if (out[k].data.fd == udp) {
                char buf[1500];
                ssize_t r;
                while ((r = recv(udp, buf, sizeof buf, 0)) > 0)
                    printf("[udp] %zd bytes\n", r);
                i++;
            }
        }
    }

    close(ep); close(sfd); close(udp);
    return 0;
}

🔑 示例 3 才是信号驱动 I/O 在 2026 年该有的样子： 底层的 fasync / kill_fasync / 两道闸门机制一点没变， 但消费信号的方式从"异步 handler"变成了"同步读 fd"。 这样既保留了 O_ASYNC 的语义，又拿到了 epoll 的可控性。 这是 63.5「同时等待信号和 fd」要展开的主题。

自测题（点击展开）

Q1. 内核头文件里有 O_ASYNC 吗？O_ASYNC 和 FASYNC 是什么关系？

答案

内核 uapi 里没有 O_ASYNC，只有 FASYNC：

/* include/uapi/asm-generic/fcntl.h:44-45 */
#ifndef FASYNC
#define FASYNC      00020000    /* fcntl, for BSD compatibility */
#endif

O_ASYNC 由 glibc 定义（bits/fcntl-linux.h）为 020000。 两者数值完全相同（都是 8192 / 0x2000，八进制前导零不影响数值）， 只是叫法不同：O_ASYNC 是 POSIX 叫法，FASYNC 是 BSD 遗留。

实践含义：写内核代码或做 F_SETFL 位运算推理时用 FASYNC； 写用户态程序用 O_ASYNC 没问题，但要知道它是 libc 提供的。

📌 顺带一提：v6.6 的 arch/x86/include/uapi/asm/fcntl.h 不存在， x86 直接用 asm-generic 版本，所以这个结论在 x86 上没有例外。

Q2. 建立信号驱动 I/O 时，F_SETOWN 和 F_SETFL(O_ASYNC) 的先后顺序有影响吗？为什么？

答案

有，必须先 F_SETOWN 再开 O_ASYNC。

原因是 send_sigio() 开头就检查 pid：

/* fs/fcntl.c:773-783 */
void send_sigio(struct fown_struct *fown, int fd, int band)
{
    ...
    read_lock_irqsave(&fown->lock, flags);

    type = fown->pid_type;
    pid = fown->pid;
    if (!pid)
        goto out_unlock_fown;      /* ← 属主未设：静默返回，什么都不做 */

O_ASYNC 一开启，设备/协议栈立刻就可能触发通知。 若此时 f_owner.pid 还是 NULL，通知会被静默丢弃 —— fcntl() 返回 0，没有任何 errno，也没有任何日志。

⚠️ 这类"返回成功但没生效"的问题最难排查，因为所有系统调用都成功了。 排查手法：F_GETOWN 回读确认属主真的设上了。

Q3. fcntl(fd, F_SETFL, O_ASYNC) 内部是怎么设置 FASYNC 标志位的？如果设备不支持异步通知会怎样？

答案

setfl() 自己不设 FASYNC 位。 看掩码：

/* fs/fcntl.c:35 */
#define SETFL_MASK (O_APPEND | O_NONBLOCK | O_NDELAY | O_DIRECT | O_NOATIME)

FASYNC 不在 SETFL_MASK 里，所以 :81 的赋值不会碰它。 真正的置位在驱动的 ->fasync() 回调尽头：

/* fs/fcntl.c:934 —— fasync_insert_entry() */
    filp->f_flags |= FASYNC;

为什么要绕这一圈？ 因为开启异步通知要分配 fasync_struct 并挂进队列， 可能失败（-ENOMEM）。若先置位再分配，失败后标志位就与事实不符了。 源码把这写成铁律（:908-910）：

/*
 * NOTE! It is very important that the FASYNC flag always
 * match the state "is the filp on a fasync list".
 */

如果 f_op->fasync 为 NULL（设备不支持）：

    if (((arg ^ filp->f_flags) & FASYNC) && filp->f_op->fasync) {

判空让整个 if 跳过 → fcntl() 返回 0（成功），但什么都没发生。 这是最隐蔽的失败模式：开了但没真开，且无报错。

Q4. struct fown_struct 里有没有记录 fd？si_fd 是从哪来的？

Q5. ⭐ 内核真的每来一个包就发一次 SIGIO 吗？描述 sock_wake_async() 里的两道闸门。

答案

不是。 sock_wake_async()（net/socket.c）里有两道闸门主动抑制重复通知：

int sock_wake_async(struct socket_wq *wq, int how, int band)
{
    if (!wq || !wq->fasync_list)
        return -1;

    switch (how) {
    case SOCK_WAKE_WAITD:
        if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
            break;                    /* 闸门 B：位已置 → 不发 */
        goto call_kill;
    case SOCK_WAKE_SPACE:
        if (!test_and_clear_bit(SOCKWQ_ASYNC_NOSPACE, &wq->flags))
            break;                    /* 闸门 A：不欠账 → 不发 */
        fallthrough;
    case SOCK_WAKE_IO:
call_kill:
        kill_fasync(&wq->fasync_list, SIGIO, band);
        break;
    case SOCK_WAKE_URG:
        kill_fasync(&wq->fasync_list, SIGURG, band);
    }

    return 0;
}

闸门 A（可写方向）SOCKWQ_ASYNC_NOSPACE —— 记账式 / 边沿触发

  • 置位（欠账）：sock_alloc_send_pskb() net/core/sock.c:2786、 tcp_poll() net/ipv4/tcp.c:569（注释 /* send SIGIO later */）
  • 消费：test_and_clear_bit() —— 只有真欠账才发，发完清账
  • → 语义是「可写 → 不可写 → 可写」跃变才通知一次，缓冲区一直可写一个都不发

闸门 B（可读方向）SOCKWQ_ASYNC_WAITDATA —— 在场者抑制

  • 置位点只在阻塞等待路径：sk_wait_data() net/core/sock.c:3019-3029 （sk_set_bit 进 / sk_clear_bit 出）
  • → 这个位的真名该叫「有人正在阻塞等数据」
  • 位已置 → 某人卡在读里、自己会被唤醒 → 不发信号
按 v6.6 修订/补充

原笔记（扩写前）的说法是「主要用于 UDP socket（TCP 的信号过于频繁）」。 按 v6.6 源码，这个说法不精确 —— 频繁与否不取决于 TCP/UDP， 而取决于是否 O_NONBLOCK：

socket 模式 闸门 B 状态 SIGIO 行为
阻塞 + 线程卡在读 置位 ❌ 几乎收不到
阻塞 + 线程没在读 未置 ✅ 每个报文一次
非阻塞 + 事件循环 永远未置 ✅✅ 每个报文一次 ← "过于频繁"的真正来源

所以建立流程里「设 O_NONBLOCK」这一步的真实作用是 让闸门 B 永远处于开启状态，保证通知不被抑制， 而不只是"避免 read 阻塞"这种泛泛理由。

Q6. ⭐ 一个阻塞 socket 配 O_ASYNC 会怎样？这是合理的组合吗？

答案

不合理，几乎收不到通知。

SOCKWQ_ASYNC_WAITDATA 只在 sk_wait_data() 里被置位， 而 sk_wait_data() 是阻塞等待路径：

/* net/core/sock.c:3019 */
int sk_wait_data(struct sock *sk, long *timeo, const struct sk_buff *skb)
{
    DEFINE_WAIT_FUNC(wait, woken_wake_function);
    int rc;

    add_wait_queue(sk_sleep(sk), &wait);
    sk_set_bit(SOCKWQ_ASYNC_WAITDATA, sk);        /* ← 进阻塞前置位 */
    rc = sk_wait_event(sk, timeo, skb_peek_tail(&sk->sk_receive_queue) != skb, &wait);
    sk_clear_bit(SOCKWQ_ASYNC_WAITDATA, sk);      /* ← 出阻塞后清零 */
    remove_wait_queue(sk_sleep(sk), &wait);
    return rc;
}

而发送侧：

    case SOCK_WAKE_WAITD:
        if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
            break;      /* 有人在阻塞等 → 不发，他自己会被唤醒 */

逻辑是自洽的：线程既然已经卡在 read() 里等数据， 内核会直接 wake_up_interruptible_sync_poll() 唤醒它（见 sock_def_readable() :3323）， 再额外发一个 SIGIO 就是纯粹的浪费。

🔑 所以「阻塞 socket + O_ASYNC」是自相矛盾的组合： 一边阻塞等、一边要异步通知，闸门 B 会让通知几乎不出现。 这也解释了为什么所有信号驱动 I/O 的示例代码都同时设 O_NONBLOCK。

Q8. 用 F_SETSIG 选信号时，选哪些会导致 si_code 退化？为什么？

答案

选 有专属 si_code 取值空间的信号会导致退化：

            if ((signum != SIGPOLL) && sig_specific_sicodes(signum))
                si.si_code = SI_SIGIO;

sig_specific_sicodes() 查的掩码（include/linux/signal.h:437-442）：

#define SIG_SPECIFIC_SICODES_MASK (\
    rt_sigmask(SIGILL)    |  rt_sigmask(SIGFPE)    | \
    rt_sigmask(SIGSEGV)   |  rt_sigmask(SIGBUS)    | \
    rt_sigmask(SIGTRAP)   |  rt_sigmask(SIGCHLD)   | \
    rt_sigmask(SIGPOLL)   |  rt_sigmask(SIGSYS)    | \
    SIGEMT_MASK                                    )

黑名单：SIGILL / SIGFPE / SIGSEGV / SIGBUS / SIGTRAP / SIGCHLD / SIGSYS / SIGEMT（以及非 SIGPOLL 时的 SIGPOLL）。

原因：这些信号已有自己的 si_code 语义（如 SIGSEGV 的 SEGV_MAPERR）， POLL_IN（= 1）这种值会与之冲突。内核把 si_code 改成 SI_SIGIO（= -5）来消除歧义。

代价：丢失事件类型信息，用户态只能去看 si_band。

✅ 实践结论：F_SETSIG 选普通实时信号（SIGRTMIN + n）。 顺带：实时信号号越小投递优先级越高，所以 SIGRTMIN 既排队又优先级最高。

Q9. si_band 的值是怎么算出来的？为什么内核要存一张 band_table？

答案

两级映射。

第一级：band_table[] 把紧凑的事件编号翻译成内核内部的 EPOLL* 位掩码：

/* fs/fcntl.c:692 */
static const __poll_t band_table[NSIGPOLL] = {
    EPOLLIN | EPOLLRDNORM,          /* POLL_IN  = 1 */
    EPOLLOUT | EPOLLWRNORM | EPOLLWRBAND,   /* POLL_OUT = 2 */
    EPOLLIN | EPOLLRDNORM | EPOLLMSG,       /* POLL_MSG = 3 */
    EPOLLERR,               /* POLL_ERR = 4 */
    EPOLLPRI | EPOLLRDBAND,         /* POLL_PRI = 5 */
    EPOLLHUP | EPOLLERR         /* POLL_HUP = 6 */
};

（NSIGPOLL == 6，include/uapi/asm-generic/siginfo.h:301）

第二级：mangle_poll() 把 EPOLL* 位翻成用户态的 POLL* 位（__u16）：

/* include/linux/poll.h */
static inline __u16 mangle_poll(__poll_t val)
{
    __u16 v = (__force __u16)val;
#define M(X) __MAP(v, (__force __u16)EPOLL##X, POLL##X)
    return M(IN) | M(OUT) | M(PRI) | M(ERR) | M(NVAL) |
        M(RDNORM) | M(RDBAND) | M(WRNORM) | M(WRBAND) |
        M(HUP) | M(RDHUP) | M(MSG);
#undef M
}

为什么要这么绕？ 因为内核内部统一用 EPOLL* 位（__poll_t，poll 回调的返回类型）， 而 POSIX 的 SIGIO 约定 si_band 用 POLL* 位。两套编码位值不同，必须转换。 反向转换是 demangle_poll()。

⚠️ 两个易错点：

  1. POLL_HUP 映射成 EPOLLHUP | EPOLLERR —— 挂断同时带错误位， 处理 si_band 时不能只判 POLLHUP
  2. 转换后是 __u16，只覆盖 12 个位（IN/OUT/PRI/ERR/NVAL/RDNORM/RDBAND/WRNORM/WRBAND/HUP/RDHUP/MSG）， EPOLL* 里超出这个范围的位会被丢掉

63.4

epoll API

本章：TLPI 第 63 章 — 备用 I/O 模型 - 上一节：63.3 信号驱动 I/O - 下一节：63.5 同时等待信号和 fd

源码核验：Linux v6.6（fs/eventpoll.c 2479 行、include/uapi/linux/eventpoll.h、include/linux/eventpoll.h） 下文所有常量、结构体字段、行号均来自缓存的 v6.6 源码，可逐条复查。

本节讲什么

epoll 是 Linux 的高性能 I/O 多路复用机制。本节回答四层问题：

  1. 接口层：6 个 syscall 各自是什么关系（不止"三件套"）
  2. 机制层：内核里到底用什么数据结构撑起它 —— 红黑树、就绪链表、以及一个常被忽略的 ovflist
  3. 语义层：水平触发 / 边沿触发 / oneshot 三种模式在代码上差在哪一行
  4. 工程层：HFT 低延迟场景下的精度、惊群、选型陷阱

🔗 本篇只讲 epoll API 与实现；io_uring 作为现代替代方案主场在 12.5 现代网络（该模块 io_uring 命中 121 处）。

要点

1. 不是"三件套"，是 6 个 syscall

教科书常说 epoll 有 3 个函数，实际 v6.6 的 fs/eventpoll.c 里注册了 6 个：

syscall 定义位置 签名要点 用途
epoll_create1 :2073 SYSCALL_DEFINE1 (int flags) 推荐。flags 仅接受 EPOLL_CLOEXEC
epoll_create :2078 SYSCALL_DEFINE1 (int size) 历史遗留，size 参数已被忽略
epoll_ctl :2267 SYSCALL_DEFINE4 (epfd, op, fd, event*) 增 / 删 / 改监听
epoll_wait :2325 SYSCALL_DEFINE4 (epfd, events, maxevents, timeout) 等待事件，timeout 单位毫秒
epoll_pwait :2359 SYSCALL_DEFINE6 多 sigmask, sigsetsize 原子地替换信号掩码再等待
epoll_pwait2 :2370 SYSCALL_DEFINE6 timeout 是 struct __kernel_timespec * 纳秒精度超时（v5.11+） 
/* fs/eventpoll.c:2370 */
SYSCALL_DEFINE6(epoll_pwait2, int, epfd, struct epoll_event __user *, events,
        int, maxevents, const struct __kernel_timespec __user *, timeout,
        const sigset_t __user *, sigmask, size_t, sigsetsize)
{
    struct timespec64 ts, *to = NULL;
    if (timeout) {
        if (get_timespec64(&ts, timeout))
            return -EFAULT;
        to = &ts;
        if (poll_select_set_timeout(to, ts.tv_sec, ts.tv_nsec))
            return -EINVAL;
    }
    return do_epoll_pwait(epfd, events, maxevents, to, sigmask, sigsetsize);
}

为什么要有 pwait？ 因为「设置信号掩码 → 调用 epoll_wait」这两步之间， 信号可能在掩码生效之前到达并被丢弃（经典竞态）。pwait 把两步合成一个原子 syscall。 pwait2 再进一步把毫秒改成 timespec。

⚠️ epoll_pwait 名字里的 p 是 "pselect-style signal mask"，不是 "poll"。

2. epoll_create1 的 flags 只有一种合法值

/* fs/eventpoll.c:2030-2039 */
static int do_epoll_create(int flags)
{
    /* Check the EPOLL_* constant for consistency.  */
    BUILD_BUG_ON(EPOLL_CLOEXEC != O_CLOEXEC);

    if (flags & ~EPOLL_CLOEXEC)
        return -EINVAL;
    ...
  • BUILD_BUG_ON(EPOLL_CLOEXEC != O_CLOEXEC) —— 编译期断言：EPOLL_CLOEXEC 的值 必须等于 O_CLOEXEC。头文件里确实如此：uapi:23 #define EPOLL_CLOEXEC O_CLOEXEC
  • flags & ~EPOLL_CLOEXEC → 传任何其他 flag 直接 -EINVAL
  • 传 0 合法（不设 CLOEXEC）

3. epoll_ctl 的 op：只有 3 个，没有第 4 个

/* include/uapi/linux/eventpoll.h:25-28 */
/* Valid opcodes to issue to sys_epoll_ctl() */
#define EPOLL_CTL_ADD 1
#define EPOLL_CTL_DEL 2
#define EPOLL_CTL_MOD 3
op 值 作用
EPOLL_CTL_ADD 1 添加 fd 到监听集合
EPOLL_CTL_DEL 2 移除
EPOLL_CTL_MOD 3 修改监听事件掩码

⚠️ 没有 EPOLL_CTL_DISABLE —— v6.6 的 fs/eventpoll.c 与 uapi 头文件里 EPOLL_CTL_DISABLE 均 0 处命中。网上一些旧资料提到的这个 op 在当前内核已不存在。 想临时禁用某个 fd，正确做法是用 EPOLLONESHOT 或 EPOLL_CTL_MOD 改掩码。

epoll_ctl 的实现（:2267）只对「需要 event 参数的 op」做 copy_from_user：

if (ep_op_has_event(op) &&
    copy_from_user(&epds, event, sizeof(struct epoll_event)))
    return -EFAULT;

4. 事件位全表（含两个"高位"新/内部标志）

/* include/uapi/linux/eventpoll.h:31-42 */
#define EPOLLIN     (__force __poll_t)0x00000001
#define EPOLLPRI    (__force __poll_t)0x00000002

5. struct epoll_event 只有 12 字节 —— 因为 x86-64 上被 packed

packed（x86-64 实际） 4B 8B（紧跟，无 padding） 12

为什么要 packed？ 32 位程序里 __u64 只有 4 字节对齐，结构体就是 12 字节； 64 位程序里按默认规则会变成 16 字节。两个 ABI 不一致会让 32 位兼容层（compat）很难受。 于是 x86-64 上强制 packed，让两者都是 12 字节。

8. 回调：ep_poll_callback（:1167）—— 五步判定

当被监听的 fd 状态变化，内核通过 file->f_op->poll() 注册的等待队列回调到这里：

static int ep_poll_callback(wait_queue_entry_t *wait, unsigned mode, int sync, void *key)
{
    struct epitem *epi = ep_item_from_wait(wait);
    struct eventpoll *ep = epi->ep;
    __poll_t pollflags = key_to_poll(key);

    read_lock_irqsave(&ep->lock, flags);          /* ① 读锁 + 关中断 */

    /* ② EPOLLONESHOT 禁用判定 */
    if (!(epi->event.events & ~EP_PRIVATE_BITS))
        goto out_unlock;

    /* ③ 事件过滤（key 可能为 NULL，此时不过滤） */
    if (pollflags && !(pollflags & epi->event.events))
        goto out_unlock;

    /* ④⑤ 决定挂到 rdllist 还是 ovflist */
    if (READ_ONCE(ep->ovflist) != EP_UNACTIVE_PTR) {
        if (chain_epi_lockless(epi))             /* ⑤a 扫描中 → 无锁挂 ovflist */
            ep_pm_stay_awake_rcu(epi);
    } else if (!ep_is_linked(epi)) {
        if (list_add_tail_lockless(&epi->rdllink, &ep->rdllist))  /* ⑤b 常态 */
            ep_pm_stay_awake_rcu(epi);
    }
    ...

几个要点：

  • ① read_lock_irqsave：用的是 rwlock_t 的读侧，因为回调可能并发发生（多个 fd 同时就绪）， 读侧可以并行；只有 ep_send_events 的扫描路径才需要写侧。
  • ② ~EP_PRIVATE_BITS：把私有位（ONESHOT/ET/EXCLUSIVE/WAKEUP 等）去掉后， 如果剩下的事件掩码为 0，说明这个 epitem 被 EPOLLONESHOT 清空过 → 直接忽略。
  • ③ pollflags && ... 的短路：注释（:1189-1193）明确说「并非所有设备都在 key 里上报事件」，所以 key == NULL 时跳过过滤，全部当作就绪。
  • ④⑤ 无锁：chain_epi_lockless / list_add_tail_lockless 都是 lockless 版本， 这正是 epoll 可扩展的关键。

9. ovflist 三态：为什么传输事件时不用持锁

ep->ovflist 有三个状态：

值 含义 回调行为
EP_UNACTIVE_PTR（(void *) -1L，:96） 常态 直接入 rdllist
NULL 正在扫描（ep_start_scan 设置） 无锁挂到 ovflist 单链表
链表头指针 有溢出事件待回收 同上，继续挂 
/* fs/eventpoll.c:616 */
static void ep_start_scan(struct eventpoll *ep, struct list_head *txlist)
{
    write_lock_irq(&ep->lock);
    list_splice_init(&ep->rdllist, txlist);   /* "偷走"就绪链表，原链表置空 */
    WRITE_ONCE(ep->ovflist, NULL);            /* 进入扫描态 */
    write_unlock_irq(&ep->lock);
}

/* fs/eventpoll.c:633 */
static void ep_done_scan(struct eventpoll *ep, struct list_head *txlist)
{
    write_lock_irq(&ep->lock);
    /*
     * ovflist 是 LIFO（头插），这里用 list_add 头插回 rdllist 实现反转 → 保持 FIFO
     */
    for (nepi = READ_ONCE(ep->ovflist); (epi = nepi) != NULL;
         nepi = epi->next, epi->next = EP_UNACTIVE_PTR) {
        if (!ep_is_linked(epi)) {
            list_add(&epi->rdllink, &ep->rdllist);
            ep_pm_stay_awake(epi);
        }
    }
    WRITE_ONCE(ep->ovflist, EP_UNACTIVE_PTR);  /* 恢复常态 */
    list_splice(txlist, &ep->rdllist);         /* 未处理完的重新注入 */
    __pm_relax(ep->ws);
    write_unlock_irq(&ep->lock);
}

为什么要这么绕？ 因为 ep_send_events 在遍历就绪链表时要做两件 不能持锁的事：

  1. 调用 ep_item_poll(epi, &pt, 1) —— 可能触发驱动代码，耗时不可控
  2. epoll_put_uevent() 拷贝数据到用户空间 —— 可能缺页、可能被信号打断

如果全程持有 ep->lock，一个慢速 fd 会阻塞所有其他 CPU 上的回调。 ovflist 让回调在无锁情况下照样能入队，扫描结束后一次性回收。

📌 LIFO → FIFO 反转是个容易忽略的细节：ovflist 用头插（LIFO）， 回收时也用 list_add 头插回 rdllist，两次反转抵消，最终保持 FIFO 顺序。

10. ⭐ LT / ET / ONESHOT 的唯一分叉点（ep_send_events，:1745-1755）

这是整篇最重要的一段代码 —— 三种触发模式的差异全在这里：

/* fs/eventpoll.c:1676 ep_send_events() 循环体内 */
res++;
if (epi->event.events & EPOLLONESHOT)
    epi->event.events &= EP_PRIVATE_BITS;        /* ① ONESHOT：清空事件掩码 */
else if (!(epi->event.events & EPOLLET)) {
    /*
     * ② LT：重新插回就绪链表，下次 epoll_wait 会再检查一次
     */
    list_add_tail(&epi->rdllink, &ep->rdllist);
    ep_pm_stay_awake(epi);
}
/* ③ ET：什么都不做 —— 已经从 rdllist 摘掉了，不回来 */
模式 这行代码做什么 后果
ET 无操作 已 list_del_init 从 rdllist 摘除，不回来。下次只靠 ep_poll_callback 重新入队
LT list_add_tail 回 rdllist 下次 epoll_wait 再检查一次
ONESHOT events &= EP_PRIVATE_BITS 事件掩码清零 → ep_poll_callback 第②步直接 return，直到 EPOLL_CTL_MOD 重新武装

🔑 ONESHOT 的"禁用"不是移除监听，只是把事件掩码清空。 epitem 还留在红黑树里，直到 EPOLL_CTL_MOD 重新设置掩码。

同一个循环里还有两个关键行为：

list_del_init(&epi->rdllink);                /* 先摘下来 */
revents = ep_item_poll(epi, &pt, 1);         /* 重新 poll 一次，确认真的就绪 */
if (!revents)
    continue;                                /* 已不就绪 → 不报告，也不重新入队 */

⚠️ 即使是 LT 模式、fd 已经在就绪链表上，内核还是会重新 poll() 一次。 如果这次 poll 返回 0（比如数据已被别的线程读走），就 continue —— 既不报告用户， 也不会因为 LT 重新入队。这解释了"为什么 LT 下 fd 状态变了就不再重复报"。

以及开头的短路：

12. 复杂度真相：epoll 并不是"O(1)"

⚠️ 按 v6.6 源码修订：常见的"epoll 是 O(1)"说法过于笼统，需要按操作拆开看。

操作 复杂度 依据
epoll_ctl(ADD/DEL/MOD) O(log n) rbr 是红黑树（rb_root_cached）
epoll_wait 取回 k 个就绪事件 O(k) + 常数 遍历 rdllist 前 k 个
epoll_wait 判断是否无事件 O(1) 只需看 rdllist 是否为空
每个 epitem 的就绪判定 O(1) 回调直接挂链表

epoll 相对 select/poll 的真正优势不是"O(1)"，而是：

  1. 无需每次重复传递 fd 集合 —— select/poll 每次调用都要把整个 fd 数组从用户态拷到内核态， epoll 的监听集合由内核长期持有（rbr）
  2. 返回的都是就绪的 —— select/poll 返回后用户还得 O(n) 遍历一遍找出谁就绪； epoll 只把就绪的拷回来
  3. 就绪通知是事件驱动的 —— 靠回调挂链表，不是每次调用时轮询所有 fd

select/poll 的开销是 O(总 fd 数)，epoll 是 O(就绪 fd 数)。 当总 fd 很多而每轮就绪很少时（典型的高并发空闲连接场景），差距才体现出来。

HFT / 嵌入式关联

关注点 epoll 的现实 HFT 含义
超时精度 epoll_wait 是 int 毫秒；epoll_pwait2 才是 timespec 纳秒 需要精确超时控制时用 epoll_pwait2（v5.11+），否则毫秒粒度对 HFT 太粗
syscall 开销 每次 epoll_wait 都是一次真正的系统调用 极致延迟场景会被 io_uring（提交/完成环形队列、可轮询无 syscall）取代
惊群 多线程 epoll_wait 同一 epfd 时，一个事件可能唤醒所有线程 用 EPOLLEXCLUSIVE（v4.5+）只唤醒一个；或每线程独立 epfd + SO_REUSEPORT
busy poll eventpoll 有 napi_id 字段（CONFIG_NET_RX_BUSY_POLL，:231-233） 与 SO_BUSY_POLL 配合可在软中断前就直接收包，降延迟但吃 CPU
ET + 非阻塞 ET 必须循环读到 EAGAIN HFT 标准做法：一次事件尽量把数据读完，减少 epoll_wait 往返次数
ONESHOT 多线程 触发一次后自动禁用 保证同一个 fd 不会被两个线程同时处理，避免加锁
嵌套 epoll 上限 4 层 分层 event loop 设计时别超
嵌入式 无 EPOLLWAKEUP 需求时不要设（需要 CAP_BLOCK_SUSPEND） 嵌入式省电场景反而可能要用 EPOLLWAKEUP 防止处理中挂起

⚠️ HFT 选型提醒：epoll 是事件通知机制，不是零拷贝机制。 数据仍要通过 read()/recv() 从内核拷到用户态。若追求极致， 现代替代是 io_uring（12.5 模块）或内核旁路（13 DPDK 模块）。

/* ET 模式：必须循环读到 EAGAIN，否则剩余数据要等下一次事件 */
void handle_et_read(int fd) {
    char buf[4096];
    for (;;) {
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n > 0) {
            /* 处理 n 字节 */
            continue;
        }
        if (n == 0) {
            /* EOF：对端关闭 */
            close(fd);
            return;
        }
        /* n < 0 */
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            return;              /* 本次事件数据已读完 —— ET 下必须到这里 */
        if (errno == EINTR)
            continue;            /* 被信号打断，重试 */
        perror("read");
        close(fd);
        return;
    }
}

⚠️ ET 下 fd 必须是非阻塞的。阻塞 fd + ET = 最后一次 read() 会永久阻塞 （因为数据已读完但 ET 不会再通知）。

Q1. epoll 常被说成"O(1) 复杂度"。按 v6.6 源码，这个说法准确吗？三个主要操作各自的复杂度是什么？

答案

不准确，需要按操作拆开：

操作 复杂度 依据
epoll_ctl(ADD/DEL/MOD) O(log n) 监听集合是红黑树 rb_root_cached（:200）
epoll_wait 取 k 个事件 O(k) 遍历 rdllist 前 k 个
判断"有无事件" O(1) 只看 rdllist 空否

epoll 真正的优势不是 O(1)，而是： 1. 监听集合常驻内核，不必每次调用重传 2. 只返回就绪的 fd，用户侧不用 O(n) 扫描 3. 就绪判定是回调驱动（事件到达时挂链表），不是调用时轮询

select/poll 是 O(总 fd 数)，epoll 是 O(就绪 fd 数)。

Q2. 一个 epitem 已经在就绪链表 rdllist 上了，ep_send_events 会直接把它报告给用户吗？

答案

不会直接报告 —— 会先摘下来再重新 poll 一次：

fs/eventpoll.c:1729-1735。所以"在 rdllist 上"只是候选，不代表最终会报告。

自测题 3（点击展开）

Q3. ep->ovflist 有哪三种状态？为什么需要它？

答案

三态（EP_UNACTIVE_PTR 定义在 :96，值为 (void *) -1L）：

值 状态 回调行为
EP_UNACTIVE_PTR 常态 直接 list_add_tail_lockless 入 rdllist
NULL 扫描中（ep_start_scan 设置，:616） 无锁 chain_epi_lockless 挂到 ovflist
链表头 有溢出待回收 继续挂

为什么需要：ep_send_events 在遍历就绪链表时要做两件不能持锁的事： 1. ep_item_poll() 可能触发驱动代码，耗时不可控 2. epoll_put_uevent() 拷贝到用户空间，可能缺页

如果全程持有 ep->lock，一个慢 fd 会阻塞其他 CPU 上的回调。 ovflist 让回调在无锁情况下照样入队，扫描结束后由 ep_done_scan（:633）一次性回收。

额外细节：ovflist 是 LIFO（头插），回收时用 list_add 头插回 rdllist，两次反转抵消保持 FIFO。

Q4. 水平触发（LT）和边沿触发（ET）在内核代码上的差异具体在哪几行？

答案

差异集中在 ep_send_events() 的 fs/eventpoll.c:1745-1755：

res++;
if (epi->event.events & EPOLLONESHOT)
    epi->event.events &= EP_PRIVATE_BITS;
else if (!(epi->event.events & EPOLLET)) {
    list_add_tail(&epi->rdllink, &ep->rdllist);   /* ← 只有 LT 会执行这行 */

  • ET：两个分支都不进，epi 已被 list_del_init 摘除且不回来 → 只靠下次回调重新入队

自测题 5（点击展开）

Q5. EPOLLONESHOT 是怎么实现"触发一次后自动禁用"的？epitem 被移出红黑树了吗？

答案

没有移出红黑树，只是清空了事件掩码：

if (epi->event.events & EPOLLONESHOT)
    epi->event.events &= EP_PRIVATE_BITS;      /* 只保留私有位，I/O 事件位清零 */

（:1746-1747）

配合 ep_poll_callback 的第②步判定（:1186）：

if (!(epi->event.events & ~EP_PRIVATE_BITS))
    goto out_unlock;        /* 掩码去掉私有位后为空 → 视为已禁用，直接忽略 */

于是后续事件到达时回调直接返回，epitem 不再入就绪链表。

重新武装必须用 EPOLL_CTL_MOD（v6.6 没有 EPOLL_CTL_DISABLE）， 它会走 ep_modify() 重新设置掩码并立即 poll 一次。

自测题 7（点击展开）

Q7. sizeof(struct epoll_event) 是多少？为什么 x86-64 上要用 packed？

答案

12 字节（x86-64 上）。

struct epoll_event {
    __poll_t events;   /* 4 字节 */
    __u64 data;        /* 8 字节 */
} EPOLL_PACKED;        /* x86-64 上 = __attribute__((packed)) */

不 packed 的话，64 位下 __u64 data 会按 8 字节对齐 → events 后补 4 字节 padding → 16 字节。

为什么 packed（uapi 头文件 :71-75 注释）：

On x86-64 make the 64bit structure have the same alignment as the 32bit structure. This makes 32bit emulation easier.

32 位程序里 __u64 只有 4 字节对齐，结构体天然是 12 字节。为了让 32/64 位 ABI 一致（简化 compat 兼容层），x86-64 上强制 packed。

连带影响：EP_MAX_EVENTS = INT_MAX / sizeof(struct epoll_event)（:95） = 2147483647 / 12 = 178,956,970（若按 16 字节算则是 134,217,727）。

自测题 9（点击展开）

Q9. 多个线程 epoll_wait 同一个 epfd 时会发生什么？怎么解决？

答案

会发生惊群（thundering herd）：一个 fd 就绪时，挂在 ep->wq 等待队列上的 所有线程都可能被唤醒，但最终只有一个能拿到事件，其余白白被调度。

解决方式有三种：

  1. EPOLLEXCLUSIVE（v4.5+，1U << 28）—— 注册时加上， 唤醒时只唤醒一个等待者，而不是全部
  2. SO_REUSEPORT —— 每线程/进程独立 epfd，由内核做负载均衡
  3. EPOLLONESHOT —— 保证同一 fd 在重新武装前只被一个线程处理

📌 EPOLLEXCLUSIVE 实测：v4.4 的 fs/eventpoll.c 中 0 处命中，v4.5 中 10 处 → v4.5 引入。

注意：EPOLLEXCLUSIVE 只对 EPOLL_CTL_ADD 生效，对 MOD 无效； 且它不改变"谁拿到事件"，只减少无谓唤醒。

答案

计算方式（fs/eventpoll.c:2455-2456）：

max_user_watches = (((si.totalram - si.totalhigh) / 25) << PAGE_SHIFT) /

其中 EP_ITEM_COST（:99）= sizeof(struct epitem) + sizeof(struct eppoll_entry)。

即：可用内存（totalram - totalhigh）的 1/25，除以每个监听项的内存成本。

自测题 11（点击展开）

Q11. ep_modify() 里为什么先设置新的事件掩码、后调用 f_op->poll()？中间那句 smp_mb() 有什么用？

答案

顺序原因（fs/eventpoll.c:1612-1615 注释）：

Set the new event interest mask before calling f_op->poll(); otherwise we might miss an event that happens between the f_op->poll() call and the new event set registering.

如果先 poll 后改掩码，那么 poll 返回后、掩码生效前这段时间里到达的事件会丢失。

smp_mb() 的两个作用（:1622-1638 注释）：

  1. 把 epi 的改动刷到其他 CPU —— 改 epi->event.events 时没有持 ep->lock， 而 ep_poll_callback 是持 ep->lock 的。屏障保证回调能看到新掩码，否则可能漏事件
  2. 确保不漏"过去"的事件 —— 这个屏障与 wq_has_sleeper() 里的屏障配对

📌 这是内核里典型的"防丢事件"范式，与 Ch4.4 休眠与唤醒 里「先把自己加入等待队列、再检查条件」是同一个问题的两种表现。

63.5

同时等待信号和文件描述符

本章：TLPI 第 63 章 — 备用 I/O 模型（指向模块 README；本章目录尚未建章节级 README） - 上一节：63.4 epoll API - 下一节：63.6 总结

源码核验：Linux v6.6 —— fs/select.c（1449 行）、fs/signalfd.c（353 行）、 include/uapi/linux/signalfd.h、kernel/signal.c（127915 字节）、 include/linux/sched/signal.h（22161 字节）、fs/eventpoll.c。 手册核验：man7 select(2) / signalfd(2)。 下文所有常量、结构体字段、行号均来自缓存的 v6.6 源码或官方手册原文，可逐条复查。

本节讲什么

一个进程既要等 fd（网络包、管道、终端），又要等信号（SIGTERM 停机、SIGCHLD 收尸、 SIGIO 通知），而这两件事原本属于两套完全不同的等待机制。把它们拼在一起， 就撞上了一道经典竞态。本节按四层展开：

  1. 问题层：竞态的精确形态是什么？为什么"先检查标志再等 fd"必然有洞？
  2. 方案层：pselect() / ppoll() / epoll_pwait() 如何把"解除阻塞 + 等待"压进一次系统调用？
  3. 内核层：set_user_sigmask() / restore_saved_sigmask_unless() / poll_select_finish() 三个函数怎么配合？—— 这里藏着本节最有实践价值的一个坑（timeout 被悄悄改写）
  4. 终局层：signalfd() 换了个思路 —— 干脆把信号变成字节流，让竞态根本不存在

🔗 分工：pselect/ppoll 的可移植语义主场在 TLPI Ch20 信号：基本概念； epoll 的机制主场在 63.4 epoll API； 信号驱动 I/O（SIGIO）主场在 63.3 信号驱动 I/O； io_uring 作为终极替代主场在 12.5 现代网络。

要点

1. 竞态的精确形态 —— 不是一个窗口，是"检查"与"等待"之间的整段

教科书常把这段竞态画成"信号恰好落在两个系统调用中间"，听起来概率极低、不值得防。 这个印象是错的。 真正的洞不在两个系统调用之间，而在用户态的"检查标志"动作 与内核的"进入等待"动作之间 —— 这一段的长度是一个完整的用户态指令序列， 而且只要信号在你检查之后到达，你就永远看不到它了。

精确的时间线（错误写法）：

用户态                                       内核 / 信号
─────────────────────────────────────────────────────────
if (!got_sig) {          ← ① 读到 0
                                             ② 信号到达，pending
  sigprocmask(SIG_SETMASK, &unblocked);
                                             ③ 返回用户态 → handler 跑 → got_sig = 1
  select(nfds, ..., NULL);        ← ④ 但 got_sig 已经读过了！
                                             ⑤ select 睡死
}

关键在于 ③ 发生在 ④ 之前：sigprocmask() 一解除阻塞，pending 的信号会在 该系统调用返回用户态之前立刻投递、handler 立刻跑完。等你执行到 ④ 的 select()， got_sig 已经是 1 了，可你早就用 ① 的旧值做了分支判断。

这跟"概率"无关 —— 只要信号在 ① 之后到达，100% 丢。 示例 1 给出了一个 100% 可复现的构造。

📌 这也是为什么 SA_RESTART 帮不上忙：SA_RESTART 管的是"等待中被信号打断后要不要重启"， 而这里的信号根本没有打断任何等待 —— 它是在等待开始之前到达的。

2. ⭐ pselect() 的 timeout 陷阱 —— 手册说的和内核做的不是一回事

这是本节最值得记住的一条。

几乎所有资料（包括 TLPI）都写："pselect() 不修改它的 timeout 参数，这一点与 select() 不同"。这句话只对你通过 glibc 调用 pselect() 时成立。 man7 select(2) 的 NOTES 节把这事说得很清楚：

The pselect() interface described in this page is implemented by glibc. The underlying Linux system call is named pselect6(). This system call has somewhat different behavior from the glibc wrapper function.

The Linux pselect6() system call modifies its timeout argument. However, the glibc wrapper function hides this behavior by using a local variable for the timeout argument that is passed to the system call. Thus, the glibc pselect() function does not modify its timeout argument; this is the behavior required by POSIX.1-2001.

也就是说：

你调用的是 timeout 会不会被改 谁在替你兜底
glibc pselect() 不会 glibc 把 timeout 拷到局部变量再传给 syscall，你传入的对象原封不动
内核 pselect6()（裸 syscall()、汇编、io_uring 等路径） 会 没人兜底
glibc ppoll() 不会（同一套手法） glibc
内核 ppoll（裸 syscall()） 会 没人兜底
select() 会（glibc 不隐藏） POSIX 允许两种行为之一

而且还有更狠的一条，在 BUGS 节：

On Linux, select() also modifies timeout if the call is interrupted by a signal handler (i.e., the EINTR error return). This is not permitted by POSIX.1.

被信号打断时也改 —— 而 POSIX 明确规定 EINTR 返回时 timeout 不该动。 这正是 示例 2 要实测的东西。

内核里的作案现场

fs/select.c 的 poll_select_finish() 是唯一的收尾出口，pselect6 和 ppoll 都从这里返回：

                  void __user *p,

{

    restore_saved_sigmask_unless(ret == -ERESTARTNOHAND);

    if (!p)
        return ret;                          /* timeout 为 NULL → 不写回 */

    if (current->personality & STICKY_TIMEOUTS)

        return ret;                          /* 传进来的 timeout 是 0 → 不写回 */

    ktime_get_ts64(&rts);
    rts = timespec64_sub(*end_time, rts);         /* 剩余时间 = 到期时刻 - 现在 */
    if (rts.tv_sec < 0)
        rts.tv_sec = rts.tv_nsec = 0;

    switch (pt_type) {
    ...
    case PT_TIMESPEC:
        if (!put_timespec64(&rts, p))            /* ← 写回用户态 */
            return ret;
        break;

注意 restore_saved_sigmask_unless() 在第一行，写回 timeout 在后面 —— 无论返回原因是超时、有 fd 就绪、还是被信号打断，只要 p 非空且原 timeout 非零， 写回都会发生。这就是"EINTR 时也改 timeout"的源码依据。

三个不写回的例外，值得单独记住：

情形 后果
timeout == NULL 不写回（无对象可写）—— pselect 的"死等"模式完全免疫此坑
原 timeout 为 {0, 0} 不写回（源码显式跳过）—— 纯轮询模式也免疫
personality & STICKY_TIMEOUTS 跳到 sticky:，不写回（兼容老 Unix 行为）

为什么 glibc 的做法算是"正确的"

POSIX.1-2001 要求 pselect() 的 timeout 是 const struct timespec *：

int pselect(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds,
            const struct timespec *timeout,   /* ← const */
            const sigset_t *sigmask);         /* ← const */

const 就意味着"我不改你"。对照 select()：

int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds,
           struct timeval *timeout);          /* ← 非 const */

签名上的这个 const 差异，就是 glibc 必须拷一份局部变量的原因 —— 内核 syscall 的 ABI 里没有 const 这个概念，它只有一个可写的用户态指针。

🔑 元教训（第 3 次应验）：man page 描述的是 glibc 封装的契约，不是内核 syscall 的行为。 前两次是 epoll_create(size) 的 size 被忽略（见 63.4）， 这次是 pselect6() 改 timeout。凡是手册里出现 "The X interface described in this page is implemented by glibc / The underlying Linux system call has somewhat different behavior" 这类字眼， 内核行为就要单独查源码。

3. 内核实现（上）：set_user_sigmask() 的三连

pselect / ppoll / epoll_pwait 三家共用同一个入口函数：

/* kernel/signal.c:3122-3147 */
/*
 * The api helps set app-provided sigmasks.
 *
 * This is useful for syscalls such as ppoll, pselect, io_pgetevents and
 * epoll_pwait where a new sigmask is passed from userland for the syscalls.
 *
 * Note that it does set_restore_sigmask() in advance, so it must be always
 * paired with restore_saved_sigmask_unless() before return from syscall.
 */
int set_user_sigmask(const sigset_t __user *umask, size_t sigsetsize)
{
    sigset_t kmask;

    if (!umask)
        return 0;                                        /* ① 快路径 */
    if (sigsetsize != sizeof(sigset_t))
        return -EINVAL;
    if (copy_from_user(&kmask, umask, sizeof(sigset_t)))
        return -EFAULT;

    set_restore_sigmask();                               /* ② 打标记 */
    current->saved_sigmask = current->blocked;           /* ③ 存旧值 */
    set_current_blocked(&kmask);                         /* ④ 换新值 */

    return 0;
}

四个要点，逐个都有实际后果：

① sigmask == NULL 时直接返回 0，什么都不做。 所以 pselect(..., NULL) 严格等价于 select(...)，ppoll(..., NULL) 严格等价于 poll(...)。 手册也印证："If sigmask is NULL, the signal mask is not modified during the pselect() call."

② set_restore_sigmask() 只是设一个 thread flag：

/* include/linux/sched/signal.h:488-491 */
static inline void set_restore_sigmask(void)
{
    set_thread_flag(TIF_RESTORE_SIGMASK);
}

它不改任何掩码，只在 task 上插一面旗子，告诉"即将返回用户态的那段 arch 代码"： 记得先把掩码还原。注释里解释了为什么还要顺带设 TIF_SIGPENDING：

We set TIF_SIGPENDING here to ensure that the arch signal code always gets run when TIF_RESTORE_SIGMASK is set.

③ saved_sigmask 存的是"调用前的 blocked"，也就是要还原回去的值。

④ set_current_blocked() 会强行剔除 SIGKILL / SIGSTOP：

/* kernel/signal.c:3064-3068 */
void set_current_blocked(sigset_t *newset)
{
    sigdelsetmask(newset, sigmask(SIGKILL) | sigmask(SIGSTOP));
    __set_current_blocked(newset);
}

所以你就算在 sigmask 里"解除阻塞 SIGKILL"，内核也不理 —— 这跟 63.3 里 do_signalfd4() 的 sigdelsetmask() 是同一套保险。

⚠️ 对比一下 __set_current_blocked()：它不做这个剔除。注释写得很直白：

NOTE! Unlike the user-mode sys_sigprocmask(), the kernel interface happily blocks "unblockable" signals like SIGKILL and friends.

内核内部 API 和 syscall 包装的语义不一样 —— 又一处"同名不同义"。

4. ⭐ 内核实现（下）：restore_saved_sigmask_unless() —— 两家的判定条件不一样

这是本节一个容易看漏的细节。同一个 helper，在 select.c 和 eventpoll.c 里 传进去的条件表达式不同：

调用点 源码 判定条件
pselect6 / ppoll fs/select.c:304 restore_saved_sigmask_unless(ret == -ERESTARTNOHAND)
epoll_pwait / epoll_pwait2 fs/eventpoll.c:2354 restore_saved_sigmask_unless(error == -EINTR)

helper 本身只有三行：

/* include/linux/sched/signal.h:555-561 */
static inline void restore_saved_sigmask_unless(bool interrupted)
{
    if (interrupted)
        WARN_ON(!signal_pending(current));
    else
        restore_saved_sigmask();
}

/* :547-551 */
static inline void restore_saved_sigmask(void)
{
    if (test_and_clear_restore_sigmask())
        __set_current_blocked(&current->saved_sigmask);
}

语义：interrupted == true 时不在这里还原掩码，只断言"确实有信号 pending"； 留给返回用户态前的 arch 信号代码（它看到 TIF_RESTORE_SIGMASK 就会还原）。 interrupted == false 时立刻就地还原。

为什么非要分叉？

因为"被信号打断"这件事，在两条路径上的表示方式不同：

fs/select.c:686      ret = -ERESTARTNOHAND;      ← do_select() 的中断返回码
fs/select.c:939      count = -ERESTARTNOHAND;    ← do_poll() 的中断返回码
fs/eventpoll.c:1877  return -EINTR;              ← ep_poll() 的中断返回码

do_select() / do_poll() 返回的是内部错误码 -ERESTARTNOHAND （含义：有 handler 就不重启、直接给 userspace -EINTR）， 它在 poll_select_finish() 里还没被翻译成 -EINTR（只有在 sticky 分支才翻译）。 而 ep_poll() 直接返回 -EINTR。

所以：两处条件看似不一致，实则都在判断同一件事 —— "这次返回是被信号打断的吗"， 只是要在各自的代码点上用当时那个返回值的表示形式去比。

被打断时的完整时序

pselect(..., &empty_mask)                      信号在等待期间到达
  │
  ├─ set_user_sigmask()     blocked := empty（解除阻塞），TIF_RESTORE_SIGMASK := 1
  │
  ├─ core_sys_select()      ← 阻塞中
  │      ↑ 信号到达，进程被唤醒
  │
  ├─ do_select() 返回 -ERESTARTNOHAND
  │
  ├─ poll_select_finish()
  │     ├─ restore_saved_sigmask_unless(true)   → 只 WARN_ON，**不还原**
  │     └─ put_timespec64() 写回剩余 timeout
  │
  └─ 返回用户态前（arch 代码）：
        ├─ handler 用【解除阻塞后的掩码】跑           ← 关键
        └─ restore_saved_sigmask()  blocked := saved（原掩码） ← 然后才还原
        → 用户看到 errno == EINTR

"handler 跑完之后才还原掩码" 这一点很重要：如果你的 handler 里又触发了新的等待， 那次等待看到的还是临时掩码，不是原掩码。这也是 set_user_sigmask() 注释强调 "must be always paired with restore_saved_sigmask_unless() before return from syscall" 的原因 —— 两行代码必须成对，漏了就会把掩码永久改掉。

5. poll_select_finish()：谁写回 timeout —— 一张表终结混乱

把 fs/select.c 和 fs/eventpoll.c 并排看，会得出一个很干净的结论：

接口 timeout 类型 内核是否写回 依据
select() struct timeval *（非 const） ✅ 写回 select.c:723 → poll_select_finish(..., PT_TIMEVAL, ret)
pselect6()（内核） struct __kernel_timespec * ✅ 写回 select.c:764 → poll_select_finish(..., type, ret)
ppoll（内核） struct __kernel_timespec * ✅ 写回 select.c:1122 → poll_select_finish(..., PT_TIMESPEC, ret)
glibc pselect() / ppoll() const struct timespec * ❌ 不改 glibc 拷局部变量后传给内核
epoll_pwait() int timeout（按值） ❌ 无从写起 eventpoll.c:2359-2368
epoll_pwait2() const struct __kernel_timespec * ❌ 不写回 eventpoll.c:2370-2386，走完即止

epoll_pwait2 的源码很直白 —— 它甚至没有 poll_select_finish 的对应物：

/* fs/eventpoll.c:2370-2386 */
SYSCALL_DEFINE6(epoll_pwait2, int, epfd, struct epoll_event __user *, events,
        int, maxevents, const struct __kernel_timespec __user *, timeout,
        const sigset_t __user *, sigmask, size_t, sigsetsize)
{
    struct timespec64 ts, *to = NULL;

    if (timeout) {
        if (get_timespec64(&ts, timeout))
            return -EFAULT;
        to = &ts;
        if (poll_select_set_timeout(to, ts.tv_sec, ts.tv_nsec))
            return -EINVAL;
    }

    return do_epoll_pwait(epfd, events, maxevents, to, sigmask, sigsetsize);
}

to = &ts 指向的是栈上的局部变量，do_epoll_wait 用完之后就丢了， 从来没有人 copy_to_user 回 timeout。所以 epoll_pwait2() 是这堆接口里 唯一既支持纳秒精度、又不改 timeout 的一个 —— 如果你在写自己的事件循环， 这是个被低估的选择。

epoll_pwait 的 int timeout 是按值传的，更是天然不可能被改。

📌 顺带一个常规做法：ppoll(NULL, 0, &ts, &sigmask) 是一个被广泛使用的 "带信号掩码的 nanosleep"。do_sys_poll() 里 nfds == 0 时循环立刻退出 （len = min_t(unsigned int, 0, N_STACK_PPS) = 0 → break）， do_poll() 直接落到 if (!count) { count = wait->error; if (signal_pending) count = -ERESTARTNOHAND; }， 于是它就是一个纯睡眠 + 原子换掩码。同理 ppoll 里传 pollfd.fd = -1 也只会被 do_pollfd() 忽略（mask 保持 0，不会置 POLLNVAL）。

6. pselect6 为什么是 6 个参数 —— struct sigset_argpack

pselect() 逻辑上有 7 个参数：nfds, readfds, writefds, exceptfds, timeout, sigmask, sigsetsize。 但内核头里它是 SYSCALL_DEFINE6。多出来的那个去哪了？

/* fs/select.c:767-805 */
/*
 * Most architectures can't handle 7-argument syscalls. So we provide a
 * 6-argument version where the sixth argument is a pointer to a structure
 * which has a pointer to the sigset_t itself followed by a size_t containing
 * the sigset size.
 */
struct sigset_argpack {
    sigset_t __user *p;
    size_t size;
};

static inline int get_sigset_argpack(struct sigset_argpack *to,
                     struct sigset_argpack __user *from)
{
    // the path is hot enough for overhead of copy_from_user() to matter
    if (from) {
        if (!user_read_access_begin(from, sizeof(*from)))
            return -EFAULT;
        unsafe_get_user(to->p, &from->p, Efault);
        unsafe_get_user(to->size, &from->size, Efault);
        user_read_access_end();
    }
    return 0;
Efault:
    user_access_end();
    return -EFAULT;
}

SYSCALL_DEFINE6(pselect6, int, n, fd_set __user *, inp, fd_set __user *, outp,
        fd_set __user *, exp, struct __kernel_timespec __user *, tsp,
        void __user *, sig)
{
    struct sigset_argpack x = {NULL, 0};

    if (get_sigset_argpack(&x, sig))
        return -EFAULT;

    return do_pselect(n, inp, outp, exp, tsp, x.p, x.size, PT_TIMESPEC);
}

两个细节：

  1. "多数架构处理不了 7 参数 syscall" —— 这是 ABI 硬约束。syscall 参数通过寄存器传， 通用寄存器就那么几个。源码注释和 man7 是同一句话： "most architectures support a maximum of 6 arguments to a system call."
  2. get_sigset_argpack() 没用 copy_from_user()，而是用了 user_read_access_begin() + unsafe_get_user()。注释点明原因： "the path is hot enough for overhead of copy_from_user() to matter" —— pselect 在高频事件循环里会被疯狂调用，连 copy_from_user 的开销都要省。 （copy_from_user() 有 might_fault() / 各种检查，unsafe_get_user 在 user_access_begin/end 保护下省掉这些。）

man7 给的结构体名字不同（ss / ss_len），但布局一致：

struct {
    const kernel_sigset_t *ss;   /* Pointer to signal set */
    size_t ss_len;               /* Size (in bytes) of object pointed to by 'ss' */
};

⚠️ 手册里这个 kernel_sigset_t 是内核的 sigset_t（8 字节 / 64 位）， 不是 glibc 的 sigset_t（128 字节 / 1024 位）。这正是必须把 size 一起传进来的原因 —— 内核要检查 sigsetsize != sizeof(sigset_t) 再决定接受还是 -EINVAL。

顺带把 enum poll_time_type 也列一下，它决定了 timeout 的编解码方式：

/* fs/select.c:291-296 */
enum poll_time_type {
    PT_TIMEVAL = 0,        /* struct __kernel_old_timeval   —— select()        */
    PT_OLD_TIMEVAL = 1,    /* struct old_timeval32          —— compat select() */
    PT_TIMESPEC = 2,       /* struct __kernel_timespec      —— pselect6/ppoll  */
    PT_OLD_TIMESPEC = 3,   /* struct old_timespec32         —— 32 位 time_t    */
};

do_pselect() 只接受 PT_TIMESPEC / PT_OLD_TIMESPEC，其他值直接 BUG() （select.c:750-751）—— 这是内核内部的"不可能发生"断言。

7. signalfd —— 换个思路：把信号变成字节流

前三节的方案都在"怎么让信号和 fd 安全地一起等"。signalfd() 的思路完全不同：

不要让信号去打断等待 —— 让信号本身变成一个可读的 fd。

一旦信号变成 fd，它就和 socket / pipe / timerfd 完全同构了， 可以进 epoll 监听，竞态从根上消失（信号全程阻塞，永远不会"打断"任何东西）。

7.1 struct signalfd_ctx —— 只有一个字段，而且存的是反码

/* fs/signalfd.c:41-43 */
struct signalfd_ctx {
    sigset_t sigmask;
};

就这么一个字段。但它的语义是反的 —— 存的是"不要通过 signalfd 递送的信号集合"， 而不是"要递送的集合"。原因在 do_signalfd4()：

/* fs/signalfd.c:253-272 */
static int do_signalfd4(int ufd, sigset_t *mask, int flags)
{
    struct signalfd_ctx *ctx;

    /* Check the SFD_* constants for consistency.  */
    BUILD_BUG_ON(SFD_CLOEXEC != O_CLOEXEC);
    BUILD_BUG_ON(SFD_NONBLOCK != O_NONBLOCK);

    if (flags & ~(SFD_CLOEXEC | SFD_NONBLOCK))
        return -EINVAL;

    sigdelsetmask(mask, sigmask(SIGKILL) | sigmask(SIGSTOP));   /* ① 剔除不可拦信号 */
    signotset(mask);                                            /* ② 取反 */

    if (ufd == -1) {
        ctx = kmalloc(sizeof(*ctx), GFP_KERNEL);
        if (!ctx)
            return -ENOMEM;

        ctx->sigmask = *mask;                                   /* ③ 存反码 */
        ...
        ufd = anon_inode_getfd("[signalfd]", &signalfd_fops, ctx,
                       O_RDWR | (flags & (O_CLOEXEC | O_NONBLOCK)));

三步：

  • ① sigdelsetmask(mask, SIGKILL|SIGSTOP) —— 先把这两个不可拦的信号从 "用户想接收的集合"里剔除。man7 印证：

    "It is not possible to receive SIGKILL or SIGSTOP signals via a signalfd file descriptor; these signals are silently ignored if specified in mask." ⚠️ 静默忽略 —— 不报错、不返回 -EINVAL，你只是永远读不到它们。 这已经是本批笔记里第 4 次遇到"静默"行为了 （前三次见 63.3 的元教训）。

  • ② signotset(mask) —— 取反。
  • ③ 存进 ctx。

为什么要反？因为下游用的是 dequeue_signal(current, &ctx->sigmask, info, &type)， 而 dequeue_signal() 的第二个参数是"要跳过的信号集合"。 所以存反码正好可以直接喂给它。

📌 /proc/pid/fdinfo 里看到的 sigmask: 是再取反一次之后的（即用户原始语义）： c /* fs/signalfd.c:232-240 */ sigmask = ctx->sigmask; signotset(&sigmask); render_sigset_t(m, "sigmask:\t", &sigmask);

7.2 signalfd_read() —— 批量读，但只有第一次可能阻塞

/* fs/signalfd.c:202-229 */
static ssize_t signalfd_read(struct file *file, char __user *buf, size_t count,
                 loff_t *ppos)
{
    struct signalfd_ctx *ctx = file->private_data;
    struct signalfd_siginfo __user *siginfo;
    int nonblock = file->f_flags & O_NONBLOCK;
    ssize_t ret, total = 0;
    kernel_siginfo_t info;

    count /= sizeof(struct signalfd_siginfo);          /* ① 向下取整到"能装几个" */
    if (!count)
        return -EINVAL;                                /* ② 缓冲区 < 128 字节 */

    siginfo = (struct signalfd_siginfo __user *) buf;
    do {
        ret = signalfd_dequeue(ctx, &info, nonblock);
        if (unlikely(ret <= 0))
            break;
        ret = signalfd_copyinfo(siginfo, &info);
        if (ret < 0)
            break;
        siginfo++;
        total += ret;
        nonblock = 1;                                  /* ③ 之后一律非阻塞 */
    } while (--count);

    return total ? total: ret;
}

三个要点：

① count /= sizeof(...) —— 你传的字节数被换算成"能装几个 siginfo"。 多出来的零头直接扔掉，read(sfd, buf, 200) 和 read(sfd, buf, 128) 效果一样（都只装 1 个）。

② ⚠️ 缓冲区小于 128 字节 → -EINVAL。 man7 只在正文写了一句 "The buffer must be at least sizeof(struct signalfd_siginfo) bytes."， 但 ERRORS 小节里根本没有这一条 —— 那里只列了两条 EINVAL（fd 不是 signalfd / flags 非法）。 也就是说，这个错误码只能靠读源码知道。实测见 示例 3。

③ nonblock = 1 —— 第一次成功取到信号之后，循环里的后续取信号一律非阻塞。 语义是："要么立刻给我一个，要么就去等（但只等第一次）"。 这样一次 read() 能批量取走多个 pending 信号，又不会在最后卡住。

7.3 signalfd_dequeue() —— 真的是"摘走"，不是"窥视"

/* fs/signalfd.c:155-195 */
static ssize_t signalfd_dequeue(struct signalfd_ctx *ctx, kernel_siginfo_t *info,
                int nonblock)
{
    enum pid_type type;
    ssize_t ret;
    DECLARE_WAITQUEUE(wait, current);

    spin_lock_irq(&current->sighand->siglock);
    ret = dequeue_signal(current, &ctx->sigmask, info, &type);   /* ← 真摘 */
    switch (ret) {
    case 0:
        if (!nonblock)
            break;
        ret = -EAGAIN;
        fallthrough;
    default:
        spin_unlock_irq(&current->sighand->siglock);
        return ret;
    }

    add_wait_queue(&current->sighand->signalfd_wqh, &wait);      /* ← 挂在 sighand 上 */
    for (;;) {
        set_current_state(TASK_INTERRUPTIBLE);
        ret = dequeue_signal(current, &ctx->sigmask, info, &type);
        if (ret != 0)
            break;
        if (signal_pending(current)) {
            ret = -ERESTARTSYS;                                  /* ← 注意这个码 */
            break;
        }
        spin_unlock_irq(&current->sighand->siglock);
        schedule();
        spin_lock_irq(&current->sighand->siglock);
    }
    spin_unlock_irq(&current->sighand->siglock);

    remove_wait_queue(&current->sighand->signalfd_wqh, &wait);
    __set_current_state(TASK_RUNNING);

    return ret;
}
  • dequeue_signal() 是真的把信号从 pending 队列里摘下来。man7：

    "As a consequence of the read(2), the signals are consumed, so that they are no longer pending for the process (i.e., will not be caught by signal handlers, and cannot be accepted using sigwaitinfo(2))."

  • 等待队列是 current->sighand->signalfd_wqh —— 挂在 sighand 上， 信号到达时由 signalfd_notify() 一类的路径 wake_up。
  • 阻塞时若被非 signalfd 集合内的信号打断，返回 -ERESTARTSYS （注意：跟前面 select/poll 的 -ERESTARTNOHAND 不是一个码 —— -ERESTARTSYS 意味着装了 SA_RESTART 的 handler 会自动重启这次 read）。

7.4 signalfd_poll() —— 查两个队列

/* fs/signalfd.c:51-66 */
static __poll_t signalfd_poll(struct file *file, poll_table *wait)
{
    struct signalfd_ctx *ctx = file->private_data;
    __poll_t events = 0;

    poll_wait(file, &current->sighand->signalfd_wqh, wait);

    spin_lock_irq(&current->sighand->siglock);
    if (next_signal(&current->pending, &ctx->sigmask) ||
        next_signal(&current->signal->shared_pending,
            &ctx->sigmask))
        events |= EPOLLIN;
    spin_unlock_irq(&current->sighand->siglock);

    return events;
}

查的是两个队列：

队列 含义 谁来填
current->pending 线程私有 pending pthread_kill() / tgkill() / 同步故障（SIGSEGV 等）
current->signal->shared_pending 进程（线程组）共享 pending kill() / sigqueue() / 终端信号 / SIGCHLD

注意这里用的是 current —— 不是创建 signalfd 的那个 task，而是正在 poll/read 的那个线程。 这直接引出下一节那个最容易踩的坑。

8. ⭐⭐ signalfd 的线程语义 —— 它读的是"当前线程"的信号

这是 signalfd 在多线程程序里最容易踩的坑，而且内核源码和 man7 的说法完全一致， 可以放心当作硬事实。

先把源码依据摆出来（重复一次 7.4 的关键行）：

    if (next_signal(&current->pending, &ctx->sigmask) ||        /* 当前线程的私有队列 */
        next_signal(&current->signal->shared_pending,           /* 进程级共享队列    */
            &ctx->sigmask))
        events |= EPOLLIN;

man7 signalfd(2) 的 Thread semantics 小节：

"when a thread reads from a signalfd file descriptor, it will read the signals that are directed to the thread itself and the signals that are directed to the process (i.e., the entire thread group). (A thread will not be able to read signals that are directed to other threads in the process.)"

翻译成一张表：

信号来源 落在哪个队列 线程 A 的 signalfd 能读到吗？
kill(pid, sig)（发给进程） shared_pending ✅ 任何线程都能读
sigqueue(pid, sig, ...) shared_pending ✅ 任何线程都能读
终端 Ctrl+C → SIGINT shared_pending ✅
子进程退出 → SIGCHLD shared_pending ✅
pthread_kill(A, sig)（定向到 A） A.pending ✅ 只有 A 自己能读
tgkill(pid, tid_A, sig) A.pending ✅ 只有 A 自己能读
线程 A 访问非法地址 → SIGSEGV A.pending ⚠️ 见下（同步信号本来就不能用 signalfd）

实践结论：

在多线程程序里，不要让"事件循环线程"替其他线程读 signalfd。 如果工作线程用 pthread_kill() 给自己发了个信号，主循环线程的 signalfd 永远读不到它 —— 不会报错，就是永远不就绪。

对 HFT 的直接影响：常见的"一个 pin 住的低延迟线程跑事件循环 + 若干工作线程"布局下， 如果你的停机/重配置信号是用 pthread_kill() 定向到工作线程的， 那 signalfd 方案就废了 —— 必须改成 kill(getpid(), sig)（进程级）， 或者让每个线程自己建一个 signalfd。

📌 fork 的语义（man7）： "After a fork(2), the child inherits a copy of the signalfd file descriptor. A read(2) from the file descriptor in the child will return information about signals queued to the child." ⚠️ 还有一个更阴的：如果父进程把 signalfd 加进了 epoll 实例，fork 后子进程 epoll_wait() 不会把这个继承来的 fd 报成就绪。变通办法是子进程关掉继承的 fd、 重建 signalfd、再重新加进 epoll。

9. signalfd 的三个硬限制

限制一：收不到同步生成的信号

man7 Limitations：

"The signalfd mechanism can't be used to receive signals that are synchronously generated, such as the SIGSEGV signal that results from accessing an invalid memory address or the SIGFPE signal that results from an arithmetic error. Such signals can be caught only via signal handler."

原因不复杂：同步信号是在故障指令的上下文里直接投递的（force_sig_fault() 一类路径）， 它们根本不进"等待被摘取"的 pending 队列模型 —— 内核必须在返回用户态前处理掉， 否则就会回到同一条出错指令上死循环。

对 HFT 的含义：栈溢出 / 非法访问的兜底 handler 不能用 signalfd 实现， 只能是传统 handler（而且还得配 sigaltstack()）。

限制二：SIGKILL / SIGSTOP 被静默忽略

已在 7.1 讲过 —— sigdelsetmask() 在 do_signalfd4() 里直接剔除，不报错。

限制三：非实时信号不排队

/* kernel/signal.c:1079-1082 */
static inline bool legacy_queue(struct sigpending *signals, int sig)
{
    return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
}

/* :1104-1106 */
    if (legacy_queue(pending, sig))
        goto ret;      /* 已有同号 pending → 不再排队 */

标准信号（SIGINT / SIGTERM / SIGHUP / SIGCHLD …）在 pending 时只记一个位， 不排队。所以：三个 SIGTERM 连发，你 read() 只能拿到一个。

对"停机"语义无所谓（一个就够了），但如果你的 signalfd 承担了 "统计信号次数"的职责，就必须改用 SIGRTMIN..SIGRTMAX（实时信号，真排队）。

信号类型 排队？ 典型用途
标准信号（SIGTERM / SIGINT / SIGCHLD） ❌ 合并为 1 停机、重载、收尸
实时信号（SIGRTMIN+，配合 sigqueue()） ✅ 真排队 需要计数/携带数据的场景

man7 还有一条相关的：

"If a signal appears in the mask of more than one of the file descriptors, then occurrences of that signal can be read (once) from any one of the file descriptors."

即：一个进程可以有多个 signalfd，同一信号出现在多个 fd 的 mask 里时， 它只会被读走一次，不是每个 fd 各读一份。

（附）一个容易忽略的顺序要求

"Normally, the set of signals to be received via the file descriptor should be blocked using sigprocmask(2), to prevent the signals being handled according to their default dispositions."

必须先 sigprocmask(SIG_BLOCK, ...) 再 signalfd()。 顺序反了的话， 在 signalfd 建好之前到达的信号会走默认动作（比如 SIGTERM 直接杀进程）， signalfd 根本来不及接。

还有 execve 的连带问题：

"If spawning a child process to execute a helper program (that does not need the signalfd file descriptor), then, after the call to fork(2), you will normally want to unblock those signals before calling execve(2) … Be aware, however, that this won't be possible in the case of a helper program spawned behind the scenes by any library function that the program may call. In such cases, one must fall back to using a traditional signal handler that writes to a file descriptor monitored by select(2), poll(2), or epoll(7)."

"信号被阻塞"这个状态会跨 execve 继承下去 —— 所以你 fork 出去的 helper 程序 会莫名其妙收不到它期待的信号。这条在写守护进程时经常坑人。

示例 1：确定性复现竞态（race_demo.c）

原笔记里那段"信号在 sigprocmask 和 select 之间到达"的伪码没法稳定复现。 下面这个版本是 100% 确定性的 —— 用"先阻塞再 raise()"造出一个已 pending 的信号， 然后走一遍错误写法。

/* race_demo.c —— 确定性复现「检查标志 → 等待」竞态
 * 构建: gcc -O0 -o race_demo race_demo.c
 * 用法: ./race_demo            (错误写法，会挂住，请用 timeout 5 ./race_demo)
 *       ./race_demo pselect    (正确写法，立刻返回)
 */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/select.h>

static volatile sig_atomic_t got;

static void handler(int s) { (void)s; got = 1; }

int main(int argc, char **argv)
{
    int use_pselect = (argc > 1 && !strcmp(argv[1], "pselect"));

    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);

    sigset_t blocked, empty;
    sigemptyset(&blocked); sigaddset(&blocked, SIGUSR1);
    sigemptyset(&empty);

    /* 全程阻塞 SIGUSR1，然后造一个「已经 pending、handler 还没跑」的信号 */
    sigprocmask(SIG_BLOCK, &blocked, NULL);
    raise(SIGUSR1);
    printf("[%s] SIGUSR1 已 pending, got=%d\n",
           use_pselect ? "pselect" : "select ", (int)got);

    if (!got) {                                  /* ← ① 读到 0 */
        if (use_pselect) {
            /* 正确：解除阻塞 + 等待 压进【一个】系统调用。
               pending 的信号在等待期间投递 → pselect 立刻返回 -1/EINTR */
            struct timespec ts = { .tv_sec = 2, .tv_nsec = 0 };
            errno = 0;
            int r = pselect(0, NULL, NULL, NULL, &ts, &empty);
            printf("  pselect -> %d (errno=%s), got=%d\n",
                   r, strerror(errno), (int)got);
        } else {
            /* 错误：两步走。
               sigprocmask 一返回用户态，pending 信号立刻投递、handler 立刻跑完，
               但 got 已经在 ① 被读成 0 了 —— select 睡死。 */
            sigprocmask(SIG_SETMASK, &empty, NULL);
            printf("  解除阻塞后 got=%d，即将 select(NULL timeout) …\n", (int)got);
            select(0, NULL, NULL, NULL, NULL);
            printf("  select 返回了（正常情况看不到这行）\n");
        }
    }
    return 0;
}

预期输出：

$ timeout 5 ./race_demo pselect
[pselect] SIGUSR1 已 pending, got=0
  pselect -> -1 (errno=Interrupted system call), got=1

$ timeout 5 ./race_demo
[select ] SIGUSR1 已 pending, got=0
  解除阻塞后 got=1，即将 select(NULL timeout) …
$ echo $?
124          ← timeout(1) 的退出码：进程被杀，说明 select 真的睡死了

got=1 那行是关键证据：handler 确实跑了，只是跑在 ① 之后， 分支判断用的是旧值。

#define _GNU_SOURCE

    sa.sa_handler = on_alarm;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                        /* 故意不加 SA_RESTART */
    sigaction(SIGALRM, &sa, NULL);

    /* pollfd.fd = -1 → do_pollfd() 直接忽略（mask 保持 0，不置 POLLNVAL），
       于是 ppoll 退化成「可换掩码的 nanosleep」 */
    struct pollfd pfd = { .fd = -1, .events = 0 };

    /* ---- A: 裸 syscall，绕过 glibc 的局部变量拷贝 ---- */
    struct timespec a = { .tv_sec = 5, .tv_nsec = 0 };
    printf("A) 裸 syscall(SYS_ppoll)，timeout=5s，1 秒后 SIGALRM 打断\n");
    show("调用前", &a);
    alarm(1);
    errno = 0;
    long ra = syscall(SYS_ppoll, &pfd, 1, &a, (void *)0, (size_t)8);
    printf("   ret=%ld errno=%d(%s) alarms=%d\n", ra, errno, strerror(errno), (int)alarms);
    show("调用后", &a);                     /* ← 被改成了剩余时间 ≈ 4s */

    /* ---- B: glibc ppoll()，glibc 帮你拷了局部变量 ---- */
    struct timespec b = { .tv_sec = 5, .tv_nsec = 0 };
    printf("\nB) glibc ppoll()，timeout=5s，1 秒后 SIGALRM 打断\n");
    show("调用前", &b);
    alarm(1);
    errno = 0;
    long rb = ppoll(&pfd, 1, &b, NULL);
    printf("   ret=%ld errno=%d(%s) alarms=%d\n", rb, errno, strerror(errno), (int)alarms);
    show("调用后", &b);                     /* ← 原封不动 {5, 0} */

    /* ---- C: 超时到期（非 EINTR）路径，裸 syscall 同样会改 ---- */
    struct timespec c = { .tv_sec = 1, .tv_nsec = 0 };
    printf("\nC) 裸 syscall(SYS_ppoll)，timeout=1s，让它正常超时到期\n");
    show("调用前", &c);
    errno = 0;
    long rc = syscall(SYS_ppoll, &pfd, 1, &c, (void *)0, (size_t)8);
    printf("   ret=%ld errno=%d(%s)\n", rc, errno, strerror(errno));
    show("调用后", &c);                     /* ← 归零 {0, 0} */

    return 0;
}

/* sfd_read_semantics.c —— 实测 signalfd 的 read 语义
 * 构建: gcc -O0 -o sfd_read_semantics sfd_read_semantics.c
 */

#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/signalfd.h>
#include <unistd.h>

int main(void)
{
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGRTMIN);
    sigprocmask(SIG_BLOCK, &mask, NULL);        /* ① 必须先阻塞，顺序不能反 */

    int sfd = signalfd(-1, &mask, SFD_NONBLOCK);
    if (sfd < 0) { perror("signalfd"); return 1; }

    /* 灌 3 个排队信号（实时信号才排队） */
    union sigval sv;
    for (int i = 0; i < 3; i++) {
        sv.sival_int = 100 + i;
        sigqueue(getpid(), SIGRTMIN, sv);
    }
    printf("已 sigqueue 3 个 SIGRTMIN\n");

    /* (a) 缓冲区 64 字节 < 128 → -EINVAL，而且不消耗任何信号 */
    char small[64];
    errno = 0;
    ssize_t r1 = read(sfd, small, sizeof small);
    printf("(a) read(64)      -> %zd  errno=%d(%s)\n",
           r1, errno, strerror(errno));

    /* (b) 缓冲区够大 → 一次 read 批量取走 3 个（nonblock=1 让循环不卡住） */
    struct signalfd_siginfo buf[8];
    errno = 0;
    ssize_t r2 = read(sfd, buf, sizeof buf);
    int n = (int)(r2 / (ssize_t)sizeof(buf[0]));
    printf("(b) read(%zu)   -> %zd  (= %d 个 siginfo)\n", sizeof buf, r2, n);
    for (int i = 0; i < n; i++)
        printf("      [%d] signo=%u si_code=%d si_int=%d\n",
               i, buf[i].ssi_signo, buf[i].ssi_code, buf[i].ssi_int);

    /* (c) 再读一次 → 队列已空，SFD_NONBLOCK → EAGAIN */
    errno = 0;
    ssize_t r3 = read(sfd, buf, sizeof buf);
    printf("(c) read again    -> %zd  errno=%d(%s)\n",
           r3, errno, strerror(errno));

    /* (d) 换成标准信号，验证「不排队」 */
    sigset_t m2; sigemptyset(&m2); sigaddset(&m2, SIGUSR1);
    sigprocmask(SIG_BLOCK, &m2, NULL);
    int sfd2 = signalfd(-1, &m2, SFD_NONBLOCK);
    for (int i = 0; i < 3; i++) raise(SIGUSR1);
    errno = 0;
    ssize_t r4 = read(sfd2, buf, sizeof buf);
    printf("(d) 3 个 SIGUSR1，read -> %zd (= %d 个，标准信号被合并)\n",
           r4, (int)(r4 > 0 ? r4 / (ssize_t)sizeof(buf[0]) : 0));

    close(sfd); close(sfd2);
    return 0;
}

示例 4：生产骨架 —— signalfd 并进 epoll（sfd_epoll_loop.c）

这是本节的推荐形态。注意它用的是普通 epoll_wait()，不是 epoll_pwait() —— 因为信号全程阻塞，竞态不存在。

/* sfd_epoll_loop.c —— signalfd + epoll 统一事件循环
 * 构建: gcc -O2 -Wall -o sfd_epoll_loop sfd_epoll_loop.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/epoll.h>
#include <sys/signalfd.h>
#include <unistd.h>

#define MAXEV 64

int main(void)
{
    /* ① 先阻塞，再建 signalfd —— 顺序反了会漏信号 */
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);
    sigaddset(&mask, SIGTERM);
    sigaddset(&mask, SIGHUP);
    sigaddset(&mask, SIGCHLD);
    sigprocmask(SIG_BLOCK, &mask, NULL);

    /* ② 建 signalfd。SFD_NONBLOCK 必带：EPOLLET 下阻塞 fd 会卡死 */
    int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
    if (sfd < 0) { perror("signalfd"); return 1; }

    /* ③ 建 epoll，把 signalfd 当普通 fd 加进去 */
    int ep = epoll_create1(EPOLL_CLOEXEC);
    if (ep < 0) { perror("epoll_create1"); return 1; }

    struct epoll_event ev = { .events = EPOLLIN, .data.fd = sfd };
    if (epoll_ctl(ep, EPOLL_CTL_ADD, sfd, &ev) < 0) {
        perror("epoll_ctl(sfd)"); return 1;
    }
    /* 业务 fd 照常加：epoll_ctl(ep, EPOLL_CTL_ADD, sock, ...); */

    printf("pid=%ld 运行中。Ctrl+C / kill -TERM / kill -HUP %ld\n",
           (long)getpid(), (long)getpid());

    struct epoll_event evs[MAXEV];
    struct signalfd_siginfo si;
    int quit = 0;

    while (!quit) {
        /* ④ 用普通 epoll_wait —— 不需要 epoll_pwait。
           信号已全程阻塞，不可能在「检查→等待」之间溜进来。 */
        int n = epoll_wait(ep, evs, MAXEV, -1);
        if (n < 0) {
            /* mask 之外的信号（比如 SIGSEGV）仍可能打断，理论上要处理 */
            if (errno == EINTR) continue;
            perror("epoll_wait");
            break;
        }

        for (int i = 0; i < n; i++) {
            if (evs[i].data.fd != sfd) {
                /* 业务 fd 就绪 —— 正常处理 */
                continue;
            }

            /* ⑤ signalfd 就绪：循环读到 EAGAIN 为止，尽量批量取走 */
            for (;;) {
                ssize_t r = read(sfd, &si, sizeof si);
                if (r != (ssize_t)sizeof si)
                    break;                      /* EAGAIN 或出错 → 下一轮 epoll */

                switch (si.ssi_signo) {
                case SIGINT:
                    printf("SIGINT  (from pid %u) → 退出\n", si.ssi_pid);
                    quit = 1;
                    break;
                case SIGTERM:
                    printf("SIGTERM (from pid %u) → 退出\n", si.ssi_pid);
                    quit = 1;
                    break;
                case SIGHUP:
                    printf("SIGHUP  → 重载配置\n");
                    break;
                case SIGCHLD:
                    printf("SIGCHLD pid=%u status=%d\n",
                           si.ssi_pid, si.ssi_status);
                    break;
                }
                if (quit) break;
            }
            if (quit) break;
        }
    }

    close(ep);
    close(sfd);
    return 0;
}

为什么这么写：

决定 理由
sigprocmask 在 signalfd 之前 man7 明确要求；反了会漏掉建立期间到达的信号
SFD_NONBLOCK 必带 若将来改成 EPOLLET，阻塞 fd 会漏事件并卡死；带了就两种触发模式都安全
SFD_CLOEXEC 建议带 BUILD_BUG_ON(SFD_CLOEXEC != O_CLOEXEC)，与 O_CLOEXEC 同值
用 epoll_wait 而非 epoll_pwait signalfd 让竞态不存在，epoll_pwait 是多余开销
read 循环到 EAGAIN signalfd_read 的 nonblock = 1 语义：一次 epoll_wait 可能对应多个信号
if (errno == EINTR) continue 仍保留 mask 之外的信号（如 SIGSEGV）照样能打断 epoll_wait

⚠️ 如果是多线程程序：把 signalfd 的创建和 read 都放在同一个线程里， 并确保你要收的信号是进程级的（kill(getpid(), ...) / 终端 / SIGCHLD）。 见第 8 节。

Q1. pselect() 到底会不会修改它的 timeout 参数？

答案

取决于你调的是 glibc 封装还是内核 syscall。

  • glibc pselect()：不会。glibc 把 timeout 拷到一个局部变量再传给内核， 你传入的对象原封不动。
  • 内核 pselect6()：会。

man7 select(2) NOTES 原文：

The Linux pselect6() system call modifies its timeout argument. However, the glibc wrapper function hides this behavior by using a local variable for the timeout argument that is passed to the system call. Thus, the glibc pselect() function does not modify its timeout argument; this is the behavior required by POSIX.1-2001.

为什么 glibc 非要多拷一次？ 因为 POSIX.1-2001 把 pselect() 的 timeout 声明成 const struct timespec *：

int pselect(..., const struct timespec *timeout, const sigset_t *sigmask);
                 ^^^^^

对比 select() 的 struct timeval *timeout 没有 const。 内核 syscall 的 ABI 里没有 const 的概念——它拿到的就是一个可写的用户态指针， poll_select_finish() 会用 put_timespec64() 把剩余时间写回去（fs/select.c:346）。 glibc 的局部变量拷贝是为了让用户可见的行为符合那个 const。

实践影响：只要你走 syscall(SYS_ppoll, ...)、手写汇编、 或者任何绕过 glibc 封装的路径，timeout 就会被改。 在循环里复用同一个 struct timespec 时会静默出错。

Q2. select() 在被信号打断（EINTR）返回时，会不会修改 timeout？POSIX 怎么说？

答案

会改，而 POSIX 不允许。

man7 select(2) BUGS 节原文：

On Linux, select() also modifies timeout if the call is interrupted by a signal handler (i.e., the EINTR error return). This is not permitted by POSIX.1.

源码层面：poll_select_finish() 里 restore_saved_sigmask_unless() 是第一行 （fs/select.c:304），写回 timeout 在它后面 —— 两者之间没有按返回原因分叉。 只要满足三个条件就写回：

条件 说明
p != NULL 用户传了非 NULL 的 timeout
!(personality & STICKY_TIMEOUTS) 没设 sticky timeout personality
end_time 非全零 传入的 timeout 不是 {0, 0}

跟"是不是 EINTR 返回"完全无关。

顺带说清楚 select() 的超时返回也改 timeout，这个是 POSIX 允许的：

On Linux, select() modifies timeout to reflect the amount of time not slept; most other implementations do not do this. (POSIX.1 permits either behavior.)

所以 Linux 上 select() 的 timeout 无论怎么返回都该当成未定义：

"Consider timeout to be undefined after select() returns."

Q3. pselect(sigmask == NULL) 和 select() 有区别吗？ppoll(NULL, 0, &ts, NULL) 呢？

答案

pselect(..., NULL) 与 select(...) 严格等价（只差 timeout 的类型/精度）。

源码依据 —— set_user_sigmask() 的第一行就是这个快路径：

/* kernel/signal.c:3131-3137 */
int set_user_sigmask(const sigset_t __user *umask, size_t sigsetsize)
{
    sigset_t kmask;

    if (!umask)
        return 0;                            /* ← 直接返回，什么都不做 */
    if (sigsetsize != sizeof(sigset_t))
        return -EINVAL;
    ...

注意两点： 1. sigmask == NULL 时连 sigsetsize 都不检查（所以 syscall(SYS_ppoll, fds, n, &ts, NULL, 8) 里那个 8 传什么都行）。 2. TIF_RESTORE_SIGMASK 也不会被设置 → 返回路径上 restore_saved_sigmask() 是 no-op。

man7 一致："If sigmask is NULL, the signal mask is not modified during the pselect() call."

ppoll(NULL, 0, &ts, &sigmask) 是一个有用的惯用法：相当于"带信号掩码的 nanosleep"。

do_sys_poll() 在 nfds == 0 时：

/* fs/select.c:990-995 */
    len = min_t(unsigned int, nfds, N_STACK_PPS);
    for (;;) {
        walk->next = NULL;
        walk->len = len;
        if (!len)
            break;                              /* len = 0 → 立刻退出 */
        ...

于是 do_poll() 走进循环时 count 为 0，直接落到：

/* fs/select.c:936-939 */
        if (!count) {
            count = wait->error;
            if (signal_pending(current))
                count = -ERESTARTNOHAND;
        }

纯睡眠 + 原子换掩码。同理，传 pollfd.fd = -1 也可以 —— do_pollfd() 对 fd < 0 直接返回 0（不置 POLLNVAL）。

Q4. 为什么 pselect/ppoll 里是 restore_saved_sigmask_unless(ret == -ERESTARTNOHAND)， 而 epoll_pwait 里是 restore_saved_sigmask_unless(error == -EINTR)？哪个写错了？

答案

都没写错。两处判断的是同一件事，只是"被信号打断"在两个子系统里的表示方式不同。

/* fs/select.c:304 */
    restore_saved_sigmask_unless(ret == -ERESTARTNOHAND);

/* fs/eventpoll.c:2354 */
    restore_saved_sigmask_unless(error == -EINTR);

看各自的中断返回码：

等待函数 源码行 中断返回码
do_select() select.c:686 ret = -ERESTARTNOHAND;
do_poll() select.c:939 count = -ERESTARTNOHAND;
ep_poll() eventpoll.c:1877 return -EINTR;

select/poll 这一支返回的是内核内部错误码 -ERESTARTNOHAND （含义："如果装了 handler 就不重启，直接给用户态 -EINTR"； 在 poll_select_finish() 里它还没被翻译 —— 只有走到 sticky: 标签才会 if (ret == -ERESTARTNOHAND) ret = -EINTR;）。

epoll 这一支直接返回 -EINTR。

所以两处条件都必须匹配自己那个子系统当时用的表示形式。

helper 本身的语义：

/* include/linux/sched/signal.h:555-561 */
static inline void restore_saved_sigmask_unless(bool interrupted)
{
    if (interrupted)
        WARN_ON(!signal_pending(current));
    else
        restore_saved_sigmask();
}

interrupted == true → 不在这里还原，只断言"确实有信号 pending"， 把还原工作留给返回用户态前的 arch 信号代码（它看到 TIF_RESTORE_SIGMASK 就会处理）。

为什么要留到那时候？ 因为顺序很重要：

handler 用【临时的、已解除阻塞的】掩码跑
    ↓
handler 返回后，arch 代码看到 TIF_RESTORE_SIGMASK
    ↓
restore_saved_sigmask() → blocked := saved_sigmask
    ↓
用户看到 errno == EINTR，且掩码已还原

如果在这里就地还原，handler 就会在原掩码（信号全阻塞）下运行， 那 pselect 传进来的 sigmask 就白传了。

kernel/signal.c:3128 的注释把这条约束写成了硬性要求：

"Note that it does set_restore_sigmask() in advance, so it must be always paired with restore_saved_sigmask_unless() before return from syscall."

Q5. epoll_pwait2() 会像 ppoll() 那样把剩余时间写回 timeout 吗？

答案

不会。 它是这一堆接口里唯一"纳秒精度 + 不改 timeout"的。

/* fs/eventpoll.c:2370-2386 */
SYSCALL_DEFINE6(epoll_pwait2, int, epfd, struct epoll_event __user *, events,
        int, maxevents, const struct __kernel_timespec __user *, timeout,
        const sigset_t __user *, sigmask, size_t, sigsetsize)
{
    struct timespec64 ts, *to = NULL;

    if (timeout) {
        if (get_timespec64(&ts, timeout))
            return -EFAULT;
        to = &ts;                            /* ← 指向【栈上局部变量】 */
        if (poll_select_set_timeout(to, ts.tv_sec, ts.tv_nsec))
            return -EINVAL;
    }

    return do_epoll_pwait(epfd, events, maxevents, to, sigmask, sigsetsize);
}

to = &ts 指向栈变量，do_epoll_wait() 用完之后就随栈帧一起消失 —— 从来没有任何 copy_to_user 把它写回 timeout。 （对比 ppoll 有 poll_select_finish(&end_time, tsp, PT_TIMESPEC, ret)， 里面就是 put_timespec64(&rts, p)。）

完整对照表：

接口 timeout 形参 内核写回?
select() struct __kernel_old_timeval * ✅
pselect6() struct __kernel_timespec * ✅
ppoll struct __kernel_timespec * ✅
epoll_pwait() int timeout（按值） ❌ 无从写起
epoll_pwait2() const struct __kernel_timespec * ❌

📌 epoll_pwait() 的 int timeout 是按值传的（毫秒精度）， 物理上不可能被写回。这既是它的缺点（只有 ms 精度），也是它的优点（天然免疫此坑）。

Q6. struct signalfd_ctx 里存的 sigmask 是"我想接收的信号集"吗？SIGKILL 放进 mask 会怎样？

答案

不是。存的是取反后的（"要跳过"的）集合。

/* fs/signalfd.c:41-43 —— 只有一个字段 */
struct signalfd_ctx {
    sigset_t sigmask;
};

/* fs/signalfd.c:263-272 */
    if (flags & ~(SFD_CLOEXEC | SFD_NONBLOCK))
        return -EINVAL;

    sigdelsetmask(mask, sigmask(SIGKILL) | sigmask(SIGSTOP));   /* ① */
    signotset(mask);                                            /* ② 取反 */

    if (ufd == -1) {
        ctx = kmalloc(sizeof(*ctx), GFP_KERNEL);
        if (!ctx)
            return -ENOMEM;

        ctx->sigmask = *mask;                                   /* ③ 存反码 */

为什么要存反码？ 因为下游直接用它调 dequeue_signal()， 而 dequeue_signal() 的第二个参数语义是"要跳过的信号集合"：

/* fs/signalfd.c:163 */
    ret = dequeue_signal(current, &ctx->sigmask, info, &type);

存反码正好可以直接喂进去，省掉每次取反。

SIGKILL / SIGSTOP 放进 mask 会怎样？—— 静默忽略。

① 那行在取反之前就把它们从"用户想接收的集合"里删掉了， 所以取反之后它们落在"要跳过"的那一侧 —— 你永远读不到。

man7 印证（两次强调）：

"It is not possible to receive SIGKILL or SIGSTOP signals via a signalfd file descriptor; these signals are silently ignored if specified in mask."

"Attempts to include SIGKILL and SIGSTOP in mask are silently ignored."

⚠️ 注意"silently"：不返回 -EINVAL，不打日志，man7 也只是陈述事实。 这已经是本批笔记里第 4 次遇到内核的"静默"行为了 （前三次见 63.3：f_op->fasync == NULL 时 fcntl(O_ASYNC) 返回 0、F_SETOWN 未设时静默丢通知、epoll_create(size) 忽略 size）。

📌 顺带：/proc/pid/fdinfo 里看到的 sigmask: 是再取反一次的结果， 也就是用户的原始语义，方便人读： c /* fs/signalfd.c:237-239 */ sigmask = ctx->sigmask; signotset(&sigmask); render_sigset_t(m, "sigmask:\t", &sigmask);

Q7. read(sfd, buf, 64)（缓冲区小于 128 字节）会发生什么？

答案

返回 -1，errno == EINVAL。一个字节都不读，也不消耗任何信号。

/* fs/signalfd.c:211-213 */
    count /= sizeof(struct signalfd_siginfo);      /* 64 / 128 = 0 */
    if (!count)
        return -EINVAL;                            /* ← 直接返回 */

⚠️ 这里是文档缺口：man7 signalfd(2) 只在正文里写了一句

"The buffer must be at least sizeof(struct signalfd_siginfo) bytes."

但 ERRORS 小节里列的两条 EINVAL 都不包含这条：

EINVAL fd is not a valid signalfd file descriptor.
EINVAL flags is invalid; or, in Linux 2.6.26 or earlier, flags is nonzero.

也就是说，这个错误码只能靠读源码（或亲自踩）才知道。 这跟第 71 条是同一族的问题：手册记录的是"应该怎么用"，不是"用错了会发生什么"。

另外两个相关语义：

  1. 零头被丢弃：count /= sizeof(...) 是整数除法。 read(sfd, buf, 200) 和 read(sfd, buf, 128) 等效（都只装 1 个）。

  2. 批量读取，但只有第一次可能阻塞： c /* fs/signalfd.c:216-226 */ do { ret = signalfd_dequeue(ctx, &info, nonblock); if (unlikely(ret <= 0)) break; ret = signalfd_copyinfo(siginfo, &info); if (ret < 0) break; siginfo++; total += ret; nonblock = 1; /* ← 第一次成功后一律非阻塞 */ } while (--count); nonblock = 1 保证：一次 read 能把当前 pending 的信号批量取走， 但绝不会在取完最后一个之后卡住等新信号。

自测题 8（点击展开）

Q8. 多线程程序里，主线程建了 signalfd 并 epoll_wait，工作线程用 pthread_kill(worker_tid, SIGUSR1) 给自己发信号。主线程的 signalfd 能读到吗？

答案

读不到。永远读不到，而且不会有任何错误提示。

源码依据 —— signalfd_poll() 查的是两个队列：

/* fs/signalfd.c:58-62 */
    spin_lock_irq(&current->sighand->siglock);
    if (next_signal(&current->pending, &ctx->sigmask) ||          /* ① 当前线程私有 */
        next_signal(&current->signal->shared_pending,             /* ② 进程级共享 */
            &ctx->sigmask))
        events |= EPOLLIN;
    spin_unlock_irq(&current->sighand->siglock);

关键在于 current —— 是"正在 poll/read 的那个线程"， 不是"创建 signalfd 的那个线程"。

pthread_kill(worker_tid, ...) 产生的信号进的是 worker 的私有 pending 队列， 主线程（= current）的 current->pending 里没有它。

man7 说得更直白：

"when a thread reads from a signalfd file descriptor, it will read the signals that are directed to the thread itself and the signals that are directed to the process (i.e., the entire thread group). (A thread will not be able to read signals that are directed to other threads in the process.)"

对照表：

来源 落在哪个队列 主线程 signalfd
kill(getpid(), sig) shared_pending ✅ 读得到
sigqueue(getpid(), sig, ...) shared_pending ✅ 读得到
终端 Ctrl+C → SIGINT shared_pending ✅ 读得到
子进程退出 → SIGCHLD shared_pending ✅ 读得到
pthread_kill(worker_tid, sig) worker.pending ❌ 读不到
tgkill(pid, worker_tid, sig) worker.pending ❌ 读不到
worker 自己的 SIGSEGV worker.pending ❌（且同步信号本来就不能用 signalfd）

怎么办（三选一）：

  1. 改成进程级发送：kill(getpid(), sig) / sigqueue(getpid(), ...)。
  2. 让每个线程自己建一个 signalfd，各自 read。
  3. 由需要收信号的那个线程自己去 read 这个 signalfd（signalfd fd 是共享的， 谁 read 就查谁的队列）。

对 HFT 的直接影响：常见的"一个 pin 核线程跑事件循环 + 若干工作线程"布局下， 如果停机/重配置信号是工作线程用 pthread_kill() 自发自收的， 那"主线程统一 signalfd"的方案从设计上就不成立。这是必须在架构阶段就想清楚的。

📌 相关的 fork 语义（man7）： "After a fork(2), the child inherits a copy of the signalfd file descriptor. A read(2) from the file descriptor in the child will return information about signals queued to the child." ⚠️ 更阴的一点：如果父进程把 signalfd 加进了 epoll 实例， fork 后子进程的 epoll_wait() 不会把这个继承来的 fd 报成就绪。 变通办法：子进程关掉继承的 fd，重建 signalfd，重新加进 epoll。

Q9. 连发 3 个 SIGTERM（进程已用 sigprocmask 阻塞），然后 read() signalfd，能读到几个？

答案

1 个。 标准信号不排队，pending 状态只记一个位。

/* kernel/signal.c:1079-1082 */
static inline bool legacy_queue(struct sigpending *signals, int sig)
{
    return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
}

/* :1104-1106 —— 在 __send_signal_locked() 里 */
    if (legacy_queue(pending, sig))
        goto ret;                    /* 已有同号 pending → 不再排队 */

legacy_queue() 返回 true 的条件是"sig < SIGRTMIN 且已经在 pending 集合里" —— 两个条件都满足就跳过排队，直接返回。

信号类型 排队? 3 连发能读到
标准信号（SIGTERM/SIGINT/SIGHUP/SIGCHLD，1–31） ❌ 合并为 1 1 个
实时信号（SIGRTMIN+，配合 sigqueue()） ✅ 真排队 3 个

实践判断：

  • 停机/重载语义下无所谓 —— 一个就够了，多余的是噪音。
  • 需要计数或携带不同数据时必须用 SIGRTMIN..SIGRTMAX + sigqueue()。 实时信号的 pending 用的是链表（不是位图），所以真的会排队。

man7 还补充了一条多 fd 的情形：

"If a signal appears in the mask of more than one of the file descriptors, then occurrences of that signal can be read (once) from any one of the file descriptors."

即：一个进程建了多个 signalfd、同一个信号在多个 fd 的 mask 里时， 它只会被读走一次，不是每个 fd 各一份。

自测题 10（点击展开）

Q10. 判断下列说法对错，并给出依据：

① 用了 signalfd 之后，还需要 epoll_pwait() 来保证不丢信号。 ② signalfd 可以替代所有 signal handler，包括 SIGSEGV 的兜底。 ③ epoll_pwait() 的 timeout 参数和 ppoll() 一样，返回时会被改成剩余时间。 ④ pselect6 的第 6 个参数是 sigset_t *。 ⑤ set_current_blocked() 会按你给的掩码原样设置。

答案

全部为错。

# 判定 依据
① 还需 epoll_pwait ❌ 恰恰相反 —— 不需要了。 signalfd 方案里信号全程被 sigprocmask 阻塞，永远不会"打断"任何等待；竞态的前提（"信号在等待开始前到达"）根本不成立。用普通 epoll_wait() 就够。见 sfd_epoll_loop.c
② 能替代所有 handler ❌ 同步生成的信号收不到。 man7 Limitations 原文："The signalfd mechanism can't be used to receive signals that are synchronously generated, such as the SIGSEGV signal that results from accessing an invalid memory address or the SIGFPE signal that results from an arithmetic error. Such signals can be caught only via signal handler." 栈溢出兜底仍需传统 handler + sigaltstack()
③ epoll_pwait 改 timeout ❌ epoll_pwait() 的 timeout 是 int（按值传、毫秒精度），物理上无从写起。 即便是纳秒精度的 epoll_pwait2()，也不写回 —— to = &ts 指向栈变量，用后即弃（eventpoll.c:2374-2386）。改 timeout 的是 ppoll/pselect6/select
④ 第 6 参是 sigset_t * ❌ 是 struct sigset_argpack { sigset_t __user *p; size_t size; }（select.c:773-776）。原因写在注释里："Most architectures can't handle 7-argument syscalls. So we provide a 6-argument version where the sixth argument is a pointer to a structure which has a pointer to the sigset_t itself followed by a size_t containing the sigset size."
⑤ 原样设置 ❌ 会强行剔除 SIGKILL/SIGSTOP：
void set_current_blocked(sigset_t *newset) { sigdelsetmask(newset, sigmask(SIGKILL) \| sigmask(SIGSTOP)); __set_current_blocked(newset); }（signal.c:3064-3068）。
而 __set_current_blocked()（多两个下划线）不剔除 —— 注释："NOTE! Unlike the user-mode sys_sigprocmask(), the kernel interface happily blocks 'unblockable' signals like SIGKILL and friends."

最容易凭直觉答对的是 ③ 和 ⑤ —— 尤其是 ⑤， set_current_blocked() 和 __set_current_blocked() 只差两个下划线， 语义却差了一道保险。内核里这种"同名近似 API 语义不同"的情况要格外小心 （参见 63.4 里 epoll_create / epoll_create1 的对比）。

📌 关于 ①，补一句常见误解：signalfd 消灭的是 EINTR 重试循环和竞态窗口， 不是"信号处理的延迟"。信号仍要完整走一遍 sighand->siglock 加锁 → pending 入队 → 唤醒 signalfd_wqh → epoll_wait 返回 → read() 系统调用。 它的价值是代码结构简单、行为可预测，不是延迟更低。 真要压延迟，方向是 12.5 现代网络 的 io_uring。

代码自测

1. epoll 的 ET 模式为什么必须用非阻塞 fd？

ET 模式只在状态变化时通知一次。如果用阻塞 fd，read/recv 在缓冲区数据读完后会阻塞，导致无法返回事件循环处理其他 fd。非阻塞 fd 读到 EAGAIN 表示数据读完，可以安全返回等待下一个事件。

2. select 和 epoll 的核心区别？

select 每次调用需要拷贝 fd_set 到内核，返回后全量遍历检查每个 fd，复杂度 O(n)，且 fd 数量受 FD_SETSIZE (1024) 限制。epoll 在内核维护红黑树，只返回就绪的 fd，复杂度 O(1)，无数量限制。

1. 用 epoll 实现一个 echo 服务端，支持多客户端并发 
int epfd = epoll_create1(0);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = listen_fd };
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);

struct epoll_event events[64];
while (1) {
    int n = epoll_wait(epfd, events, 64, -1);
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == listen_fd) {
            int cfd = accept(listen_fd, NULL, NULL);
            fcntl(cfd, F_SETFL, O_NONBLOCK);
            ev.events = EPOLLIN | EPOLLET;
            ev.data.fd = cfd;
            epoll_ctl(epfd, EPOLL_CTL_ADD, cfd, &ev);
        } else {
            /* echo: 读到 EAGAIN 为止, 原样写回 */
            char buf[4096];
            while (1) {
                ssize_t r = read(events[i].data.fd, buf, sizeof(buf));
                if (r <= 0) break;
                write(events[i].data.fd, buf, r);
            }
        }
    }
}
2. 为什么 pselect 需要额外的 sigmask 参数？

pselect 原子地"用 sigmask 替换信号掩码 + 等待 fd"，返回后恢复原掩码。这消除了"解除信号阻塞"和"进入等待"之间的竞态窗口，确保不会错过信号。如果分两步做（sigprocmask + select），信号可能在两步之间到达，select 会永远阻塞。

3. signalfd + epoll 相比 pselect 有什么优势？

signalfd 将信号变成普通 fd 事件，融入 epoll 事件循环。优势：(1) 统一处理 fd 和信号，无需 handler；(2) 没有 handler 的异步中断，代码全同步；(3) 可与大量 fd 一起高效管理；(4) 线程安全，可指定接收信号的线程。
