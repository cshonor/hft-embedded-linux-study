导读

优先级：🔴 必读（UNIX/Linux 一切 I/O 的地基，后面 60 章都在复用这套模型） 前置：Ch2 基本概念（fd / 进程与内核的分工）· Ch3 系统编程概念（syscall 与 errno 范式） 后置：Ch5 文件 I/O 深入（fcntl / dup / pread / readv）→ Ch13 文件 I/O 缓冲

章节目标

  • 模型：UNIX 的「一切皆文件」不是修辞，而是同一个 struct file_operations 接口被普通文件、设备、管道、socket 各自实现
  • 动词：open / read / write / close 四个动词 + lseek 定位 + ioctl 兜底——全部 I/O 都由这六个组成
  • 层次：用户态拿到的是整数 fd，中间是进程私有的槽位表，底下才是内核的 struct file（偏移、标志、引用计数）与 inode
  • 诚实：短读、部分写、write 成功≠落盘、close 不幂等——这些「反直觉」才是本章真正要带走的东西
  • 溯源：本章 13 处「书上的说法 / 网上的说法」被 v6.6 源码 + CE 实测修正（详见 4.9 §反直觉清单）

一条主线

层 是什么 谁拥有 关键字段
① 进程 fd 表 int 号 → 槽位 进程（files_struct） 槽位号 = fd
② 打开文件描述 struct file 可以多进程/多 fd 共享 f_mode / f_pos / f_flags / f_count
③ inode 文件本体 全局（inode 缓存） i_size / i_mode / 块映射

读法：同一行（dup / fork）→ 共享 ②（共享偏移）；不同行（各自 open）→ 各自的 ②（各自偏移），但可能指向同一个 ③。

易错清单

  1. close 之后那个 fd 号立刻能复用 —— 不是「用完就废」。实测 close(3) 后下一次 open 拿到的就是 3。
  2. close 不幂等 —— 重复 close(3) 返回 EBADF。所以「close 失败就重试」是危险写法（重试可能关掉别的线程刚拿到的同一个号）。
  3. close(0) 之后新 open 会拿到 0 号 —— 0/1/2 只是「约定」不是「保留」。守护进程重绑标准输入输出正是靠这个。
  4. write(fd, buf, 0) 返回 0 是合法的 —— count = 0 时内核连数据都不碰，errno 保持干净。
  5. read(fd, buf, count) 里 count 超过 buffer 实际大小不会报错 —— 内核的 access_ok 只验证地址范围属于用户空间，不知道你分配了多少。实测 read(fd, buf[64], 1GiB) 成功返回 36，多出来的字节写进了相邻内存。静默内存破坏。
  6. count 有硬上限 MAX_RW_COUNT —— INT_MAX & PAGE_MASK（include/linux/fs.h:2399），超过会被截断而不是报错。
  7. O_CLOEXEC 不在 F_GETFL 里 —— 它是fd 标志，要用 F_GETFD 查 FD_CLOEXEC 位。实测 F_GETFL 拿到 0x8000 里没有 O_CLOEXEC。
  8. F_GETFL 返回的不等于你 open 时传的 —— 内核会在 do_sys_openat2 里补位：if (force_o_largefile()) flags |= O_LARGEFILE;（fs/open.c:1443-1444）。这就是那个多出来的 0x8000 的来源。
  9. O_LARGEFILE 在 x86-64 的 glibc 头文件里根本没有 —— 因为 __libc_open 整块包在 #ifndef __OFF_T_MATCHES_OFF64_T 里（glibc 2.39 sysdeps/unix/sysv/linux/open.c:33），64 位平台上完全不参与编译。别去 glibc 里找答案，答案在内核侧。
  10. umask 是「减权限」不是「设权限」 —— 最终权限 = mode & ~umask。实测 umask 0022 + 请求 0666 → 实际 0644；umask 0027 → 0640。
  11. write 成功 ≠ 数据安全 —— 只保证进了页缓存，掉电即丢。要落盘得 fsync/fdatasync（实测都返回 0）。
  12. 短读不是错误 —— read 返回小于 count 的正数是正常结果（EOF、管道剩余量、信号、终端行缓冲都会造成）。必须循环。
  13. 部分写不是错误 —— 实测：容量 4 KiB 的管道上裸 write(8192) 返回 4096，errno 干净。原书 Listing 4-1 里那句 fatal("...partial write occurred") 只在「只写普通文件」时安全。
  14. SIGPIPE 默认杀进程 —— 往读端已关的管道写，子进程直接死于 signal 13。忽略它才会拿到 -1 errno=32 (EPIPE)。
  15. /dev/null 写 30 字节返回 30 —— 「写成功」和「数据被保存」是两件事，这是最纯粹的证明。
  16. TIOCGWINSZ 不符合 _IOR 编码规范 —— 它是硬编码的 0x5413（ioctls.h:38），按位拆出来 dir = 0、size = 0。网上流传的 _IOR('T', 104, struct winsize) 算出来是 0x80085468，对不上。
  17. _IOR / _IOW 的方向是「用户态视角」 —— ioctl.h:82-83 原话：_IOW means userland is writing and kernel is reading。和「内核读/写」正好相反。
  18. ENOTTY 有两个来源 —— ① 对象没有 unlocked_ioctl（fs/ioctl.c:46-49）；② 对象有、但驱动返回内部哨兵 -ENOIOCTLCMD（:52-53）。用户态永远看不到 ENOIOCTLCMD。
  19. isatty() 内部就是 ioctl —— glibc 走 __isatty → __tcgetattr → INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios)。
  20. FIONBIO 与 fcntl(F_SETFL, O_NONBLOCK) 改的是同一个位 —— 都是 filp->f_flags 的 O_NONBLOCK（fs/ioctl.c:342 ioctl_fionbio）。不是两套独立状态。
  21. 同一个 FIONREAD 有两套实现 —— 普通文件在 do_vfs_ioctl 里直接算 i_size - f_pos（fs/ioctl.c:829-834）；管道则转发给 pipe_ioctl（fs/pipe.c:608）加锁遍历环形缓冲区。
  22. lseek 是 0-based 的 —— lseek(fd, 4, SEEK_SET) 之后的第一个字节是第 5 个字符。原书 seek_io 实测：wABCDEFGHIJ 后 s4 r3 得到 EFG。
  23. lseek(fd, 0, SEEK_CUR) 是「查偏移而不移动」 —— default_llseek 里有专门的快捷分支（fs/read_write.c:78-81），直接返回 file->f_pos。
  24. lseek 不改数据、不触发磁盘 I/O —— 只改内存里的 f_pos。同一位置重复读结果不变。
  25. SEEK_HOLE 的边界按文件系统块对齐，但会被 i_size 截断 —— 实测同一份代码两种表现：数据段顶到文件末尾时报 i_size（2097157，看着像字节级精确）；后面还有洞时报块边界（2101248）。
  26. SEEK_HOLE / SEEK_DATA 的可移植性取决于底层文件系统 —— 内核通用兜底 default_llseek 假设「文件末尾是唯一的洞」（fs/read_write.c:95-106 注释原话）。在不支持的 FS 上，稀疏拷贝优化会静默失效。
  27. 朴素 read/write 拷贝会把空洞灌实 —— 读空洞得到的是真实的 0 字节，写过去就真分配块了。实测一个 3 MiB 逻辑 / 12 KiB 物理的稀疏文件，物理占用差 256 倍。
  28. fork 前必须 fflush(stdout) —— stdout 被重定向时是全缓冲的，子进程会继承缓冲再刷一遍，输出重复两遍。（本章 c4_5_write.c 真踩过这个坑。）
  29. 流对象不可 seek —— 管道/socket/终端没有 FMODE_LSEEK（fs.h:115，值 0x4），vfs_llseek 第一行就 -ESPIPE（实测 errno=29）。
  30. dup / fork 共享偏移，各自 open 才是独立的 —— 因为 f_pos 在 struct file 里（include/linux/fs.h:1007），不在 fd 表里。
  31. read / write 失败不会留下「半个偏移」 —— ksys_read 先把偏移拷到局部 pos，只有 ret >= 0 才回写进 f_pos（fs/read_write.c:602-618）。
  32. O_APPEND 的原子性无法用用户态代码复刻 —— lseek(SEEK_END) + write() 是两步，中间有 TOCTOU 竞争窗口；O_APPEND 把「定位到末尾」下沉到内核的 write 里完成。

双线提示

路线
HFT 短读/部分写必须循环，否则静默丢数据；write 成功只到页缓存，成交回报要 fsync；热路径减少 syscall → writev（Ch5）/mmap（Ch49）；多进程行情日志统一 O_APPEND，绝不用 lseek+write；长跑进程 open 一律带 O_CLOEXEC 防 fd 泄漏给子进程；read(fd, buf, n) 的 n 必须是真实的 buffer 大小——内核不替你检查
嵌入式 /dev 下设备节点用同一套 open/read/write/close；专属控制（点灯、读寄存器、配波特率）走 ioctl，命令字由驱动定义、魔法数要全局唯一；串口/管道是流对象，不可 seek；umask 决定设备节点权限（mknod 之后要给对）；裸 flash/无 fsync 语义的介质上，「写成功」与「落盘」的差距更大

/* c4_1_fd_basics.c — fd 到底是什么：进程内「打开文件表」的下标
 *
 * 演示四件事：
 *   1) 三个标准 fd（0/1/2）的常量值
 *   2) 新 fd 从「当前最小可用」数字分配
 *   3) close 掉的号立刻被回收复用
 *   4) fd 表在内核里的样子（/proc/self/fd/ 这个目录本身就是一个 fd）
 *
 * 编译: gcc -O0 -Wall -o c4_1_fd_basics c4_1_fd_basics.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
#include <dirent.h>

static void list_open_fds(const char *tag)
{
    DIR *d = opendir("/proc/self/fd");      /* 注意：opendir 自己也会占一个 fd */
    struct dirent *e;

    printf("  [%s] /proc/self/fd 里有: ", tag);
    while ((e = readdir(d)) != NULL) {
        if (e->d_name[0] == '.')            /* 跳过 . 和 .. */
            continue;
        printf("%s ", e->d_name);
    }
    printf("\n");
    closedir(d);
}

int main(void)
{
    printf("== 1. 三个标准 fd 的常量 ==\n");
    printf("  STDIN_FILENO  = %d\n", STDIN_FILENO);
    printf("  STDOUT_FILENO = %d\n", STDOUT_FILENO);
    printf("  STDERR_FILENO = %d\n", STDERR_FILENO);

    printf("\n== 2. 新 fd 从「最小可用」开始分配 ==\n");
    int a = open("/tmp/c4_a.txt", O_CREAT | O_RDWR, 0644);
    int b = open("/tmp/c4_b.txt", O_CREAT | O_RDWR, 0644);
    printf("  open a -> %d\n", a);
    printf("  open b -> %d\n", b);

    printf("\n== 3. close 之后那个号立刻被回收 ==\n");
    close(a);
    int c = open("/tmp/c4_c.txt", O_CREAT | O_RDWR, 0644);
    printf("  close(%d) 后 open c -> %d   （%s）\n", a, c,
           c == a ? "复用了刚释放的号" : "没有复用，说明另有空闲号");

    printf("\n== 4. fd 表长什么样：/proc/self/fd ==\n");
    list_open_fds("a b c 都开着时");
    printf("  当前我持有的: a=%d b=%d c=%d\n", a, b, c);

    printf("\n== 5. 经典技巧：关掉 0 号，新 fd 就会拿到 0 ==\n");
    int saved0 = dup(STDIN_FILENO);         /* 先把 0 号备份到别的号 */
    close(STDIN_FILENO);
    int d = open("/tmp/c4_d.txt", O_CREAT | O_RDWR, 0644);
    printf("  close(0) 后 open d -> %d   （%s）\n", d,
           d == 0 ? "拿到 0 号：0 不是特权，只是默认值" : "没拿到 0");

    dup2(saved0, STDIN_FILENO);             /* 恢复 0 号 */
    close(saved0);
    close(b);
    close(c);
    close(d);
    list_open_fds("收尾");
    return 0;
}

代码自测（Q&A）

Q1：fd 为什么「进程私有」？两个进程里 fd=3 一定指向不同文件吗？ A：fd 只是本进程 files_struct->fdtab.fd[] 数组的下标。每个进程有自己的 files_struct，下标 3 对应的是各自数组里存的 struct file *，完全可以指向不同文件。唯一的例外是 fork 后子进程继承了父进程的 fd 表（copy_files），此时父子 fd=3 指向同一个 struct file（共享偏移）。

Q2：open() 返回的 fd 为什么总是「最小可用」？ A：内核在 get_unused_fd_flags() 里用位图（open_fds）找第一个为 0 的位。刚关掉的 fd 号立即回收到位图里，所以下次 open 会优先复用。实测里 close(3) 之后新 open 又拿到 3，就是这个机制的直观证据。这也是「关闭 0 号 fd 再打开文件，新 fd 变成 0」这类技巧的根据。

Q3：读写偏移 f_pos 为什么放在 struct file（fs.h:1007）而不放在 fd 表里？ A：因为 dup/dup2/fork 会复制 fd 表，但希望共享同一个读写位置——两个 fd 指向同一打开文件时，一个读了 100 字节，另一个看到的偏移也前进 100。若偏移存在 fd 表里就做不到共享。代价是并发读写同一文件时偏移是竞争点，需 O_APPEND 或锁（Ch5）。

Q4：本章 5 个系统调用里，哪两个「不是所有文件类型都支持」？ A：lseek 和 ioctl 视对象而定。管道/socket/终端不设 FMODE_LSEEK（fs.h:115 定义该位），lseek 返回 -ESPIPE（见 4.7，实测 errno=29）；ioctl 只有实现了对应命令的设备才有意义，普通文件上多数 ioctl 返回 -ENOTTY（见 4.8，实测 errno=25）。open/read/write/close 则是真正的「万能四件套」。

Q5：为什么说「每个 fd 占内核资源」，进程退出时会自动回收吗？ A：fd 表项、struct file（引用计数）都是内核对象。进程退出时 exit_files() 会逐个 fput，把引用计数减到 0 并释放 struct file，所以正常退出不会永久泄漏 fd。但长驻进程里不 close 的 fd 会一直占着，直到进程结束——这正是服务进程 fd 泄漏的根源。

Q6：/proc/self/fd 列出来的条目数，等于我打开的文件数吗？ A：不等于。实测里我持有 5 个 fd（0/1/2 + a/b/c 中的 3、4），但目录列出 6 个——多出来的那个是 opendir() 自己占的。任何「通过某个 fd 去读 fd 表」的操作都会把自己算进去，数数时记得扣掉。

本节把「一切皆文件」从口号落到 VFS 的 f_op 函数指针表上，讲清「通用」与「特化」的边界——并且真的用同一套代码去打四种对象，再把原书 copy.c 的三种调用姿势跑一遍。

1. 同一套 API，通吃所有文件类型

/* 下面是同一套 open/read/write/close，目标是三种截然不同的对象 */
int fd   = open("/tmp/demo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644); /* 普通文件 */
int dev  = open("/dev/null",     O_WRONLY);                        /* 设备文件 */
int proc = open("/proc/version", O_RDONLY);                        /* 内核伪文件 */

三段代码除了路径和 flags，没有任何区别。应用层完全不关心目标是 ext4 文件、块设备还是 proc 伪文件系统——这是「通用 I/O 模型」的全部意义。

2. 差异被 VFS 的 f_op 函数指针吸收

差异并没有消失，而是被下沉到了内核的虚拟文件系统层（VFS）：

用户态   read(fd, buf, n)
              │  （一条 syscall，对所有文件类型都一样）
              ▼
内核     vfs_read(file, buf, n, pos)          fs/read_write.c:450
              │  只做通用校验（f_mode、access_ok、rw_verify_area）
              ▼
        file->f_op->read / read_iter          ← 差异在这里！
              │
     ┌────────┼────────────┬──────────────┐
     ▼        ▼            ▼              ▼
 ext4 读    proc 读      tty 读        /dev/null 读
（走页缓存）（现场生成文本）（行规程）   （直接返回 0）

struct file 里的 f_op 是指向 struct file_operations（include/linux/fs.h:1852）的指针，这个结构体是一张函数指针表：read、write、llseek、unlocked_ioctl、mmap、open、release…… 每个文件系统/驱动在 open 时把属于自己的那张表挂到 file->f_op 上。此后所有 read/write 都通过同一个指针分派，VFS 上层代码一行都不用改。

这本质是内核里的多态——f_op 就是 vtable，vfs_read 调 file->f_op->read 就是虚函数调用。对照 LKD 见 05/Ch13.2 VFS 的面向对象设计。

3. 通用模型之外：ioctl() 是逃生舱

「万能模型」只覆盖 open/read/write/close（+ lseek）这几种「流式字节」语义。一旦要做的不是「读字节/写字节」——比如设置终端窗口大小、查询磁盘扇区数、配置网卡混杂模式——这套模型就没有对应动词了。

于是内核留了一个「万能兜底」：

int ioctl(int fd, int request, ...);   /* 任意设备专属命令 */

request 是一个编码了「方向 + 数据大小 + 编号」的整数，内核据此把后面的可变参数解释成设备要的结构体。设备驱动在 file_operations->unlocked_ioctl 里用 switch(request) 分派。详见 4.8。

机制 覆盖范围 例子
read/write 流式字节 I/O 读文件内容、写终端
lseek 随机定位（可 seek 对象） 跳到文件第 N 字节
ioctl 一切「字节流之外」的控制 TIOCGWINSZ 查窗口大小

完整源码 code/c4_2_universal.c：

/* c4_2_universal.c — 「通用 I/O 模型」：同一套 open/read/write/close 通吃四种对象
 *
 * 四个目标：
 *   1) 普通文件        /tmp/c4_univ.txt
 *   2) 设备文件        /dev/null（写进去就消失）与 /dev/zero（读出来全是 0）
 *   3) 内核伪文件      /proc/version（内容由内核现场生成，没有磁盘块）
 *   4) 管道            pipe(2) 造出来的匿名管道
 *
 * 看点：调用形式完全一样，返回值/语义却不同——差异全被 VFS 的
 *       file->f_op 函数指针吸收了，用户态一行都不用改。
 *
 * 编译: gcc -O0 -Wall -o c4_2_universal c4_2_universal.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

int main(void)
{
    char buf[128];
    ssize_t n;

    printf("== 1. 普通文件：写入后能读回来 ==\n");
    int fd = open("/tmp/c4_univ.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open file"); return 1; }
    printf("  写入 \"hello universal\" -> write 返回 %zd\n",
           write(fd, "hello universal", 15));
    lseek(fd, 0, SEEK_SET);                 /* 回到开头才能读到自己写的 */
    n = read(fd, buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = '\0';
    printf("  读回 %zd 字节: \"%s\"\n", n, buf);
    close(fd);

    printf("\n== 2. 设备文件 /dev/null：写进去就消失，读出来立刻 EOF ==\n");
    int dn = open("/dev/null", O_RDWR);
    if (dn < 0) { perror("open /dev/null"); return 1; }
    n = write(dn, "这段数据会被内核丢掉", 30);
    printf("  write 30 字节 -> %zd  （报告成功，但没有落点）\n", n);
    n = read(dn, buf, sizeof buf);
    printf("  read      -> %zd  （0 = EOF：永远读不到东西）\n", n);
    close(dn);

    printf("\n== 3. 内核伪文件 /proc/version：内容现场生成 ==\n");
    int pv = open("/proc/version", O_RDONLY);
    if (pv < 0) { perror("open /proc/version"); return 1; }
    n = read(pv, buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = '\0';
    printf("  read %zd 字节，开头是: %.60s...\n", n, buf);
    n = read(pv, buf, sizeof buf - 1);      /* 再读一次 */
    printf("  再 read -> %zd  （还不是 0：/proc/version 比这个 buffer 大）\n", n);
    n = read(pv, buf, sizeof buf - 1);      /* 第三次 */
    printf("  第三次 read -> %zd  （0 = 终于到 EOF）\n", n);
    printf("  → 连 proc 伪文件都必须「循环读到 0」，别假设一次就能读完。\n");
    close(pv);

    printf("\n== 4. 管道：两个 fd，一个读端一个写端，同一个 pipe(2) 造的 ==\n");
    int p[2];
    if (pipe(p) < 0) { perror("pipe"); return 1; }
    printf("  pipe() 给出读端 p[0]=%d 写端 p[1]=%d\n", p[0], p[1]);
    write(p[1], "via pipe", 8);
    n = read(p[0], buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = '\0';
    printf("  从 p[0] 读到 %zd 字节: \"%s\"\n", n, buf);

    printf("\n== 5. 差异在哪：同一个 read，四种对象走四个实现 ==\n");
    printf("  普通文件 read -> ext4/overlayfs 的 read_iter（走页缓存）\n");
    printf("  /dev/null  read -> 内核直接返回 0，没有任何存储\n");
    printf("  /proc/version -> procfs 的 read，现场格式化成字符串\n");
    printf("  管道        read -> 从内核环形缓冲区搬字节，读完即销毁\n");
    close(p[0]);
    close(p[1]);
    return 0;
}

                S_IROTH | S_IWOTH;      /* rw-rw-rw- */

            fatal("write() returned error or partial write occurred");

代码自测（Q&A）

Q1：「一切皆文件」到底是真的「都是文件」，还是只是一种抽象？ A：是抽象，不是字面事实。/dev/null 不是磁盘上的文件，/proc/version 的内容也不是存在哪里的字节——它们只是在 VFS 层表现得像文件：都有 struct file、都填了 f_op 函数指针。所谓「皆文件」=「皆可用 open/read/write/close 这套接口访问」。

Q2：vfs_read() 里哪一行体现了「差异被吸收」？ A：ret = file->f_op->read(file, buf, count, pos)（fs/read_write.c:467）。vfs_read 前面的校验（FMODE_READ→-EBADF、access_ok→-EFAULT）对所有文件类型都一样，真正干活的是通过 f_op->read 分派到具体实现——ext4 有 ext4 的实现，proc 有 proc 的实现，VFS 层不关心。

Q3：为什么 read/write 管不了「设置终端窗口大小」这种事？ A：因为窗口大小不是「一段字节流」。read/write 的语义是「从当前偏移搬运 N 字节」，而窗口行列数是一个「控制查询」，没有字节流可以表达。这类「字节流之外」的操作必须走 ioctl(fd, TIOCGWINSZ, &ws)，由驱动在 unlocked_ioctl 里识别命令字 TIOCGWINSZ。

Q4：如果我想让一个自定义硬件设备能被 read/write 访问，内核侧最少要做什么？ A：实现一个字符设备驱动，填一个 struct file_operations（至少 open、read、write、release），用 register_chrdev 注册，然后在 /dev 下建设备节点。之后用户态就能 open("/dev/mydev") + read/write，走的正是本节讲的通用模型。

Q5：「通用模型」在性能上有什么代价？HFT 为什么有时要绕过它？ A：代价来自三处：① 每次 read/write 都要 syscall 陷入内核；② vfs_read/vfs_write 的通用校验（f_mode、access_ok、rw_verify_area）有固定开销；③ f_op 函数指针间接跳转。HFT 极致低延迟场景会用 mmap 直接把文件映射进地址空间、用 sendfile 做内核内零拷贝、用 io_uring 批量提交 I/O，绕开「一次一 syscall + 通用校验」的路径。

Q6：/dev/null 的 write() 为什么返回成功？这不是骗人吗？ A：不算骗。write 的契约是「把这 N 个字节交给这个打开文件所代表的接收方」，/dev/null 的接收方语义就是「丢弃」——它诚实地完成了自己的语义。教训是：write 的返回值只说明"内核收下了"，不说明"数据到了哪里"。要确认落盘只能靠 fsync/fdatasync（见 4.5）。

本节讲什么

open() 把「路径名」变成「fd」，是万能 I/O 模型的第一步。本节回答三个问题：

  1. open() 在内核里走的是怎样一条链路（从路径字符串到 fd 槽位）？
  2. flags 和 mode 两个参数各自控制什么？umask 怎么参与？
  3. open()（系统调用）和 fopen()（C 库函数）差在哪？

本节把「权限是算出来的」和「fd 标志 vs 文件状态标志分属两层」这两件事跑到屏幕上——尤其是第二件，它直接决定 Ch5 讲 dup 时哪些东西会被共享。

1. 原型与内核链路

#include <fcntl.h>
int open(const char *pathname, int flags, /* mode_t mode */);
/* 成功返回 fd；失败返回 -1 并设 errno */

open 是变参函数——只有 flags 含 O_CREAT（或 O_TMPFILE）时才需要第三个参数 mode。内核侧完整链路（v6.6）：

用户态 open(path, flags, mode)
      │
      ▼
SYSCALL_DEFINE3(open)                    fs/open.c:1441
      │  if (force_o_largefile()) flags |= O_LARGEFILE;   ← fs/open.c:1443-1444
      ▼
do_sys_open(AT_FDCWD, ...)               fs/open.c:1434
      ▼

      ├─→ build_open_flags()  解析 flags/mode 成 struct open_flags

关键：fd 的分配（get_unused_fd_flags）发生在真正打开之前——先占坑，do_filp_open 失败再 put_unused_fd 还回去。open 默认相对 AT_FDCWD（当前工作目录）；openat/openat2 可指定 dfd 做相对路径（用于防 TOCTOU，见 Ch18）。

2. flags：位掩码，访问模式三选一

标志 含义
O_RDONLY / O_WRONLY / O_RDWR 只读 / 只写 / 读写（三者必选其一，占 O_ACCMODE 掩码 0x3）
O_CREAT 不存在则创建；此时必须给 mode
O_EXCL 与 O_CREAT 配合：文件已存在则失败（原子「排他创建」）
O_TRUNC 存在则截断为 0（需写权限）
O_APPEND 每次写前原子地把偏移设到末尾（详 Ch5）
O_NONBLOCK 非阻塞打开（对管道/FIFO/设备有意义）
O_CLOEXEC exec 时自动关闭，防 fd 泄漏给子程序
O_NOFOLLOW 不跟随符号链接
O_SYNC / O_DSYNC 写以同步方式完成（每次 write 落盘，Ch13）

3. mode 与 umask

mode 只在新文件被 O_CREAT 创建时生效，指定的是请求的权限；最终权限还要被进程的 umask 屏蔽：

最终权限 = mode & ~umask
例如 mode=0666, umask=022 → 0644 (rw-r--r--)
     mode=0666, umask=002 → 0664 (rw-rw-r--)

umask 是进程级属性（umask() 系统调用可改），默认 022。它只屏蔽（清除）权限位，不能「新增」mode 里没有的位。

4. 代码：四组实测验证 flags 与 mode

完整源码 code/c4_3_open.c：

/* c4_3_open.c — open() 的 flags 与 mode：权限到底怎么算出来的
 *
 * 演示四件事：
 *   1) 最终权限 = mode & ~umask，用三组 umask 实测
 *   2) O_EXCL + O_CREAT = 原子排他创建（第二次必失败 EEXIST）
 *   3) O_TRUNC 清空 / O_APPEND 追加，同一个文件两种命运
 *   4) O_CLOEXEC 落在「fd 标志位」里，不在文件状态标志里
 *
 * 编译: gcc -O0 -Wall -o c4_3_open c4_3_open.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/stat.h>

static void show(const char *tag, const char *path)
{
    struct stat st;
    if (stat(path, &st) < 0) { printf("  %s: stat 失败\n", tag); return; }
    printf("  %-28s 权限 = %04o (%s%s%s%s%s%s%s%s%s)  大小 = %lld\n",
           tag, st.st_mode & 07777,
           (st.st_mode & S_IRUSR) ? "r" : "-", (st.st_mode & S_IWUSR) ? "w" : "-",
           (st.st_mode & S_IXUSR) ? "x" : "-", (st.st_mode & S_IRGRP) ? "r" : "-",
           (st.st_mode & S_IWGRP) ? "w" : "-", (st.st_mode & S_IXGRP) ? "x" : "-",
           (st.st_mode & S_IROTH) ? "r" : "-", (st.st_mode & S_IWOTH) ? "w" : "-",
           (st.st_mode & S_IXOTH) ? "x" : "-",
           (long long) st.st_size);
}

int main(void)
{
    const mode_t MODE = 0666;               /* 请求的权限：rw-rw-rw- */
    const char *path = "/tmp/c4_open.txt";

    printf("== 1. 最终权限 = mode & ~umask  （本节核心）==\n");
    printf("  请求 mode = %04o (rw-rw-rw-)\n\n", MODE);

    mode_t masks[] = { 0000, 0022, 0077, 0027 };
    for (unsigned i = 0; i < sizeof masks / sizeof masks[0]; i++) {
        unlink(path);                        /* 先删掉，确保每次都是新建 */
        mode_t old = umask(masks[i]);
        int fd = open(path, O_WRONLY | O_CREAT, MODE);
        umask(old);                          /* 恢复，别影响后面 */
        close(fd);
        printf("  umask = %04o  ->  mode & ~umask = %04o & %04o = %04o\n",
               masks[i], (unsigned) MODE, (unsigned) (~masks[i] & 07777),
               (unsigned) (MODE & ~masks[i]));
        show("          实测", path);
    }
    printf("\n  结论：umask 只能「减」不能「加」。mode 里没有的位，umask 造不出来。\n");

    printf("\n== 2. O_EXCL + O_CREAT：原子的「不存在才创建」==\n");
    unlink(path);
    int fd = open(path, O_WRONLY | O_CREAT | O_EXCL, 0644);
    printf("  第一次 open(O_CREAT|O_EXCL) -> %d  （成功）\n", fd);
    close(fd);

    errno = 0;

代码自测（Q&A）

Q1：open("f.txt", O_CREAT) 少了什么参数？为什么危险？ A：少了 mode。open 是变参函数，只有 flags 含 O_CREAT 时才读第三个参数；漏传时内核会读栈上的残留值当 mode，导致新文件权限随机。正确写法 open("f.txt", O_CREAT, 0644)（再受 umask 屏蔽）。

Q2：open 失败时返回 0 吗？ A：不。失败返回 -1 并设 errno。0 是合法 fd（stdin），只有 0 号槽位空闲时才可能返回 0——这本身不是错误。判断成功与否只能用 fd == -1。实测里 close(0) 之后 open 就拿到了 0（见 4.1）。

Q3：O_EXCL | O_CREAT 组合有什么用途？ A：原子地「仅当文件不存在时创建」。两个进程同时用这个组合创建同名文件，内核保证只有一个成功、另一个得到 -EEXIST（实测 errno=17）——这是「用文件当锁」或「原子生成临时文件」的经典手段，避免 open 后再 stat 的 TOCTOU 竞争窗口。

Q4：为什么 umask 只能「屏蔽」权限，不能「添加」权限？ A：内核里的计算是 mode & ~umask——umask 只把某些位清零。mode 里本就没有的位，umask 造不出来。实测四组对照（0000/0022/0077/0027）都严格符合这个式子。

Q5：fopen("a") 和 open(..., O_APPEND) 在「追加」语义上等价吗？ A：等价，且底层是同一个机制。fopen("a") 内部就是 open(path, O_WRONLY|O_CREAT|O_APPEND, ...)，O_APPEND 让内核在每次 write 前原子地把偏移设到文件末尾，多进程追加不会交错。区别只在 fopen 多了用户态缓冲，fclose 时才真正 flush + close。

Q6：FD_CLOEXEC 和 O_CLOEXEC 有什么区别？ A：O_CLOEXEC 是传给 open 的入参，FD_CLOEXEC 是读出来的 fd 标志位（fcntl(fd, F_GETFD)）。实测：open(path, O_RDONLY|O_CLOEXEC) 之后 F_GETFD = 0x1，即 FD_CLOEXEC 已设。已打开的 fd 也可以用 fcntl(fd, F_SETFD, FD_CLOEXEC) 补设——这正是 O_CLOEXEC 出现之前的老做法。

Q7：为什么说「F_GETFL 的返回值不等于你传的 flags」？ A：实测 open("/dev/null", O_RDONLY|O_CLOEXEC) 之后 F_GETFL = 0x8000，而 O_RDONLY 是 0——多出来的 0x8000 是内核在 open 入口按平台条件补的 O_LARGEFILE（fs/open.c:1443-1444）。所以判断访问模式必须用 O_ACCMODE 掩码取低 2 位，不能拿整数直接比。

vfs_read() 的逐字全文（fs/read_write.c:450-478，v6.6）：

ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
{
    ssize_t ret;

    if (!(file->f_mode & FMODE_READ))
        return -EBADF;
    if (!(file->f_mode & FMODE_CAN_READ))
        return -EINVAL;
    if (unlikely(!access_ok(buf, count)))
        return -EFAULT;

    ret = rw_verify_area(READ, file, pos, count);
    if (ret)
        return ret;
    if (count > MAX_RW_COUNT)
        count =  MAX_RW_COUNT;

    if (file->f_op->read)
        ret = file->f_op->read(file, buf, count, pos);
    else if (file->f_op->read_iter)
        ret = new_sync_read(file, buf, count, pos);
    else
        ret = -EINVAL;
    if (ret > 0) {
        fsnotify_access(file);
        add_rchar(current, ret);
    }
    inc_syscr(current);
    return ret;
}

注意校验顺序：先 EBADF（fd 没读权限）→ EINVAL（对象不可读）→ EFAULT（用户地址非法）→ rw_verify_area（范围/锁）。EBADF 和 EFAULT 是最常见的两个坑（见第 3、4 节实测）。

其中 FMODE_READ（0x1）与 FMODE_CAN_READ（0x20000）分别在 include/linux/fs.h:111 和 :149；MAX_RW_COUNT 在 :2399，定义是 (INT_MAX & PAGE_MASK) —— 约 2 GiB 减一页。

2. 返回值语义

> 0 读到的字节数，可能小于 count（短读） 循环继续读剩余
0 EOF（文件末尾） 结束读取

3. 短读（short read）：正常现象，必须循环

read 返回的字节数没有义务等于 count。短读在以下对象上尤其常见：

对象 短读原因
管道/FIFO 缓冲区里当前只有这么多数据
socket 收到一个 TCP 段就返回，不等填满
终端 通常读到换行就返回（行规程）
普通文件 接近 EOF 时最后一次不足 count

因此网络/管道编程必须写「循环读到 EOF 或读满」的封装。最常用的 readall：

ssize_t readall(int fd, void *buf, size_t n)
{
    size_t total = 0;

    while (total < n) {
        ssize_t r = read(fd, (char *) buf + total, n - total);
        if (r < 0 && errno == EINTR)
            continue;                       /* 信号中断：重试 */
        if (r < 0)
            return -1;                      /* 真错误 */
        if (r == 0)
            break;                          /* EOF：提前收工 */
        total += (size_t) r;
    }
    return (ssize_t) total;                 /* 可能 < n（遇到 EOF） */
}

完整源码 code/c4_4_read.c：

/* c4_4_read.c — read() 的三种返回值：正数（可能短读）/ 0（EOF）/ -1（错误）
 *
 * 演示五件事：
 *   1) 循环读到 EOF 的正确写法
 *   2) 短读是正常现象：小 buffer 读大文件，一次读不满
 *   3) EBADF：fd 无效，或没以读方式打开
 *   4) EFAULT：buf 指针非法（用户态内存 bug 的暴露点）
 *   5) 读管道时的短读：有多少读多少，绝不等待
 *
 * 编译: gcc -O0 -Wall -o c4_4_read c4_4_read.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/stat.h>

int main(void)
{
    char buf[64];
    ssize_t n;

    printf("== 1. 循环读到 EOF ==\n");
    const char *path = "/tmp/c4_read.txt";
    int w = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    const char *text = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ";   /* 36 字节 */
    write(w, text, 36);
    close(w);

    int fd = open(path, O_RDONLY);
    int rounds = 0, total = 0;
    while ((n = read(fd, buf, sizeof buf)) > 0) {     /* 只在 >0 时继续 */
        rounds++;
        total += (int) n;
        printf("  第 %d 次 read(64) -> %2zd 字节\n", rounds, n);
    }
    printf("  退出循环时 read 返回 %zd（0 = EOF，不是错误）\n", n);
    printf("  合计 %d 字节，%d 轮\n", total, rounds);

    printf("\n== 2. 短读：请求 8 字节，可文件只剩 6 字节 ==\n");
    off_t end = lseek(fd, 0, SEEK_END);
    lseek(fd, end - 6, SEEK_SET);            /* 挪到最后 6 个字节 */
    char small[8];
    n = read(fd, small, sizeof small);       /* 请求 8，实际只有 6 可读 */
    printf("  在「剩余 6 字节」处 read(8) -> %zd 字节  ← 短读！请求 8，只给 6\n", n);
    n = read(fd, small, sizeof small);
    printf("  再 read(8) -> %zd  ← 0 = EOF\n", n);
    printf("  → 短读不是错误，它是 read 的**正常**返回值之一。\n");
    printf("    管道/终端/socket 上「返回 < 请求」更是家常便饭。\n");
    close(fd);

    printf("\n== 3. EBADF：fd 侧的问题 ==\n");
    int wfd = open(path, O_WRONLY);        /* 以「只写」打开 */
    errno = 0;
    n = read(wfd, buf, 10);
    printf("  用只写 fd 去 read -> %zd  errno=%d (%s)\n", n, errno, strerror(errno));
    close(wfd);

    errno = 0;
    n = read(999, buf, 10);                /* 一个没打开过的号 */
    printf("  用 fd=999 去 read -> %zd  errno=%d (%s)\n", n, errno, strerror(errno));

    printf("\n== 4. EFAULT：buf 侧的问题（地址非法）==\n");
    fd = open(path, O_RDONLY);
    volatile long bad_addr = 0x1;            /* volatile：让 gcc 别静态推断出「目标在地址 0」 */
    errno = 0;
    n = read(fd, (void *) bad_addr, 10);     /* 这个地址落在内核区，access_ok 挡下 */
    printf("  read(fd, (void*)0x1, 10) -> %zd  errno=%d (%s)\n",
           n, errno, strerror(errno));
    printf("  → EBADF 查「句柄」，EFAULT 查「内存」。两个不同的坑。\n");
    close(fd);

    printf("\n== 5. 从管道读：有多少读多少 ==\n");
    int p[2];
    pipe(p);
    write(p[1], "abc", 3);                 /* 只放 3 字节 */
    n = read(p[0], buf, sizeof buf);        /* 却要 64 字节 */
    printf("  管道里只有 3 字节，read(64) -> %zd 字节\n", n);
    printf("  → 管道上 read 不会「等到凑满 64 字节」再返回。\n");
    write(p[1], "de", 2);
    n = read(p[0], buf, sizeof buf);
    printf("  再放 2 字节，read(64) -> %zd 字节\n", n);
    close(p[0]);
    close(p[1]);

    printf("\n== 6. count 远超 buffer 实际大小，会怎样 ==\n");
    fd = open(path, O_RDONLY);
    volatile size_t huge = (size_t) 1 << 30;   /* 1 GiB；volatile 防编译器静态告警 */
    errno = 0;
    n = read(fd, buf, huge);                   /* buf 实际只有 64 字节！ */

代码自测（Q&A）

Q1：read() 返回 -1 且 errno=EBADF 和 errno=EFAULT 分别是什么问题？ A：EBADF 是 fd 侧的问题——fd 无效（没打开/已关闭，实测 fd=999 得 errno=9），或没以读方式打开（vfs_read 里 !(f_mode & FMODE_READ)）。EFAULT 是 buf 侧的问题——buf 指向的地址非法（野指针、已释放内存），access_ok 检查失败（实测 (void*)0x1 得 errno=14）。两者一个是句柄错、一个是内存错。

Q2：read 一定会读满请求的字节数吗？ A：不。read 可能返回少于 count 的字节（短读），尤其在管道、socket、终端上。实测「请求 8 字节、文件只剩 6 字节」就直接返回 6。只有「读满或遇 EOF」这个目标要靠循环保证，单次 read 不作任何承诺。

Q3：返回 0（EOF）和返回 -1（错误）怎么区分？ A：0 表示正常到达文件末尾，不是错误；-1 才表示出错（具体看 errno）。用 feof() 预判 EOF 是反模式（它只在读越过末尾后才为真），正确做法是检查 read 返回值本身。

Q4：read 被信号打断返回 EINTR，为什么「不是错误」？ A：信号处理函数返回后，系统调用可能被打断（无 SA_RESTART 时），此时数据没读、也没出错，只是「还没读完」。语义上应重试同一调用。readall 里的 if (r < 0 && errno == EINTR) continue; 就是标准处理。

Q5：read(fd, buf, 1<<30) 这种超大请求，内核会怎么处理？ A：分两步看。① vfs_read 里 if (count > MAX_RW_COUNT) count = MAX_RW_COUNT;（fs.h:2399，约 2 GiB 减一页）会把请求截断到上限。② 但截断之后的 count 仍然可能远大于你 buffer 的实际大小——access_ok 只验证地址范围在用户空间内，管不了你的分配大小。实测：char buf[64] 传 1GiB，read 返回 36、errno=0，一切"正常"。 如果文件真有那么大，就是静默越界。

Q6：为什么从管道 read(64) 只返回 3 字节，而不是阻塞到凑满 64 字节？ A：因为 read 的语义是「有多少给多少」，不是「读满才返回」。管道是流式对象，内核认为「先交付已有的数据」比「等到攒够」更有用（否则交互式程序会卡死）。想"凑满"必须自己循环——这就是 readall 存在的理由。

ssize_t vfs_write(struct file *file, const char __user *buf, size_t count, loff_t *pos)
{
    ssize_t ret;

    if (!(file->f_mode & FMODE_WRITE))
        return -EBADF;
    if (!(file->f_mode & FMODE_CAN_WRITE))
        return -EINVAL;
    if (unlikely(!access_ok(buf, count)))
        return -EFAULT;

    ret = rw_verify_area(WRITE, file, pos, count);
    if (ret)
        return ret;
    if (count > MAX_RW_COUNT)
        count =  MAX_RW_COUNT;
    file_start_write(file);
    if (file->f_op->write)
        ret = file->f_op->write(file, buf, count, pos);
    else if (file->f_op->write_iter)
        ret = new_sync_write(file, buf, count, pos);
    else
        ret = -EINVAL;
    if (ret > 0) {
        fsnotify_modify(file);
        add_wchar(current, ret);
    }
    inc_syscw(current);
    file_end_write(file);

2. 偏移是从哪回写的？—— 看 ksys_read

vfs_read/vfs_write 里那个 loff_t *pos 参数到底指向谁？ksys_read（:602-618）给出了答案，逐字：

ssize_t ksys_read(unsigned int fd, char __user *buf, size_t count)
{
    struct fd f = fdget_pos(fd);
    ssize_t ret = -EBADF;

    if (f.file) {
        loff_t pos, *ppos = file_ppos(f.file);
        if (ppos) {
            pos = *ppos;
            ppos = &pos;
        }
        ret = vfs_read(f.file, buf, count, ppos);
        if (ret >= 0 && ppos)
            f.file->f_pos = pos;
        fdput_pos(f);
    }
    return ret;
}

而 file_ppos（:597-600）：

/* file_ppos returns &file->f_pos or NULL if file is stream */
static inline loff_t *file_ppos(struct file *file)
{
    return file->f_mode & FMODE_STREAM ? NULL : &file->f_pos;
}

三件事一次说清：

  1. 普通文件：ppos 指向 struct file::f_pos，vfs_read 直接改它；
  2. 但代码还是先拷到局部 pos 再传出去，读完才 f.file->f_pos = pos 回写——这样「读失败」时偏移不会被改动一半；
  3. 流式对象（socket/pipe 设了 FMODE_STREAM）ppos == NULL，vfs_read 收到 NULL 也不回写——这就是它们没有"当前位置"、lseek 返回 ESPIPE 的同一根源。

3. 部分写（partial write）：必须循环

和 read 的短读一样，write 可以只写一部分就返回：

部分写原因 场景
管道/FIFO 缓冲不足 PIPE_BUF 限制，只写满缓冲区就返回
磁盘空间不足 ENOSPC，只写入剩余空间能容纳的部分
socket 发送缓冲部分满 TCP 发送缓冲区只有这么多空闲
信号中断 EINTR，部分数据已写出

标准封装 writeall：

ssize_t writeall(int fd, const void *buf, size_t n)
{
    size_t total = 0;

    while (total < n) {
        ssize_t w = write(fd, (char *) buf + total, n - total);
        if (w < 0 && errno == EINTR)
            continue;                       /* 信号中断：重试 */
        if (w < 0)
            return -1;
        total += (size_t) w;
    }
    return (ssize_t) total;
}

原书 Listing 4-1（copy.c）用的是 if (write(...) != numRead) fatal(...)——它敢这么写，因为只拷普通文件。一旦换成管道/socket，"部分写"就是常态，!= 直接报错等于把「可恢复的慢」当成「不可恢复的错」。手工制造一次部分写见 练习 4-3。

4. 代码：六组实测，包括三次"以为会怎样、实际不是"

完整源码 code/c4_5_write.c：

/* c4_5_write.c — write() 的返回值、部分写、以及「成功 ≠ 落盘」
 *
 * 演示六件事：
 *   1) write 返回实际写入字节数；写入普通文件通常一次写满
 *   2) count == 0 时 write 返回 0（合法，不是错误）
 *   3) /dev/full：写永远报 ENOSPC（磁盘满是什么样）
 *   4) SIGPIPE：写「读端已关闭」的管道——不忽略会被信号杀掉
 *   5) 忽略 SIGPIPE 后，同样的操作变成 -1 + EPIPE
 *   6) write 成功只到页缓存；fsync 才是落盘
 *
 * 编译: gcc -O0 -Wall -o c4_5_write c4_5_write.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <signal.h>
#include <errno.h>
#include <sys/wait.h>

/* 往「读端已关闭」的管道写，在 SIGPIPE 默认动作下的下场 */
static void default_sigpipe_child(void)
{
    int p[2];
    pipe(p);
    close(p[0]);                        /* 读端关掉：已经没人听了 */
    printf("  [子进程] 读端已关闭，现在 write(p[1], ...) ...\n");
    fflush(stdout);
    ssize_t n = write(p[1], "x", 1);    /* 这一步会触发 SIGPIPE */
    printf("  [子进程] write 返回 %zd （走不到这里）\n", n);
    _exit(0);                           /* 不用 exit()，它会刷 stdio */
}

int main(void)
{
    char big[4096];
    memset(big, 'A', sizeof big);
    ssize_t n;

    printf("== 1. 正常写：普通文件一次写满 ==\n");
    const char *path = "/tmp/c4_write.txt";
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    n = write(fd, big, sizeof big);
    printf("  write(4096) -> %zd  （普通文件通常一次写完）\n", n);

    printf("\n== 2. count = 0：合法返回 0 ==\n");
    errno = 0;
    n = write(fd, big, 0);
    printf("  write(fd, buf, 0) -> %zd  errno=%d  （0 不是错误，是「写了 0 个字节」）\n", n, errno);
    close(fd);

    printf("\n== 3. /dev/full：永远 ENOSPC，模拟磁盘满 ==\n");
    int full = open("/dev/full", O_WRONLY);
    if (full >= 0) {
        errno = 0;
        n = write(full, big, sizeof big);
        printf("  write(/dev/full, 4096) -> %zd  errno=%d (%s)\n",
               n, errno, strerror(errno));
        close(full);
    } else {
        printf("  （本环境没有 /dev/full）\n");
    }

    printf("\n== 4. SIGPIPE 的默认动作：直接杀进程 ==\n");
    /* ⚠️ fork 之前必须 flush：stdout 被重定向时是全缓冲，缓冲区内容会被
       子进程一起继承，父子各刷一遍 → 前面的输出重复两遍。 */
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) {
        default_sigpipe_child();
        _exit(0);
    }
    int status;
    waitpid(pid, &status, 0);
    if (WIFSIGNALED(status)) {
        printf("  [父进程] 子进程被信号杀死：signal = %d", WTERMSIG(status));
        if (WTERMSIG(status) == SIGPIPE) printf(" = SIGPIPE");
        printf("\n  → 服务器写 socket 前不忽略它，一个断连就能带走整个进程。\n");
    } else {
        printf("  [父进程] 子进程正常退出 status=%d\n", WEXITSTATUS(status));
    }

    printf("\n== 5. 忽略 SIGPIPE：变成可处理的 EPIPE ==\n");
    signal(SIGPIPE, SIG_IGN);
    int p[2];
    pipe(p);
    close(p[0]);
    errno = 0;
    n = write(p[1], "x", 1);
    printf("  signal(SIGPIPE, SIG_IGN) 后 write -> %zd  errno=%d (%s)\n",
           n, errno, strerror(errno));
    printf("  → 进程活着，错误变成可判断、可恢复的返回值。这是网络服务的标准做法。\n");
    close(p[1]);

    printf("\n== 6. write 成功 ≠ 落盘 ==\n");
    fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    n = write(fd, "durable?", 8);
    printf("  write 返回 %zd —— 数据此刻在页缓存（脏页）里，还没进磁盘\n", n);
    int rc = fsync(fd);
    printf("  fsync 返回 %d —— 到这里才算真正刷到存储设备\n", rc);
#ifdef __linux__
    rc = fdatasync(fd);
    printf("  fdatasync 返回 %d —— 只保证数据部分，不保证元数据\n", rc);
#endif
    printf("  → 断电测试：write 之后立刻拔电，数据可能丢；fsync 之后拔电才安全。\n");
    close(fd);
    unlink(path);
    return 0;
}

忽略后变成 -1 errno=32 EPIPE signal(SIGPIPE, SIG_IGN) 之后，同一个操作变成可判断、可恢复的错误码。网络服务的标准做法
fsync 返回 0 才算落盘 write 返回 8 时数据在页缓存（脏页）里。断电就丢。fsync（数据+元数据）/ fdatasync（只数据）才是持久化边界，详见 Ch13

第 4 条的实测里有个细节：子进程是在 printf 一句之后、write 那一刻被杀的，所以父进程 waitpid 拿到的是 WIFSIGNALED 而非退出码。血统纯正的 SIGPIPE 事故就长这样——程序没有任何错误日志，直接消失。

5. SIGPIPE：写已关闭的管道会杀进程

向「读端已关闭」的管道/socket 写数据时，内核会向写进程发送 SIGPIPE 信号；该信号默认动作是终止进程：

write(pipe_fd, buf, n);   /* 对端已 close → 进程被 SIGPIPE 杀死 */
signal(SIGPIPE, SIG_IGN); /* 忽略后，write 返回 -1，errno=EPIPE */

服务器写 socket 时对端可能随时断开，因此必须先忽略 SIGPIPE，否则一个断连就能让整个服务崩溃。忽略后 write 返回 -1 + EPIPE（实测 errno=32），程序自己处理。

6. 成功 ≠ 落盘：数据先入页缓存

write 返回成功，只表示数据拷进了内核页缓存（page cache），尚未写进物理磁盘：

write(fd, data, size)
   │  copy_from_user → 页缓存（脏页）
   │  返回成功！但数据还在内存里
   ▼
fsync(fd) / fdatasync(fd)   ← 强制把脏页刷到磁盘

断电、内核崩溃时，页缓存里尚未刷盘的脏页会丢失。要保证持久化必须显式 fsync/fdatasync（Ch13）。嵌入式/HFT 落盘场景尤其要分清「写进内核」和「写进磁盘」的边界。

代码自测（Q&A）

Q1：write() 返回值小于请求字节数时该怎么办？ A：这是「部分写」，正常现象，不能当错误。应循环写剩余部分直到全部写完（见 writeall）。不处理会导致数据静默丢失——尤其管道、socket、磁盘快满时。

Q2：write 成功返回后，数据一定在磁盘上了吗？ A：不一定。write 成功只表示数据进了内核页缓存（脏页），断电/崩溃会丢。要保证持久化必须 fsync（连元数据一起刷）或 fdatasync（只刷数据）。这正是「成功 ≠ 落盘」的含义。

Q3：向对端已关闭的管道写数据，进程为什么可能「莫名退出」？ A：内核会向写进程发 SIGPIPE（实测信号号 13），默认动作是终止进程——所以程序没有任何错误日志就直接消失。服务器写 socket 时对端随时可能断开，所以要先 signal(SIGPIPE, SIG_IGN) 忽略它，这样 write 会返回 -1 + EPIPE（实测 errno=32），由程序自己处理断连。

Q4：write 的 -EBADF 和 -EFAULT 分别查什么？ A：EBADF 查 fd——无效或没以写方式打开（vfs_write 里 !(f_mode & FMODE_WRITE)）。EFAULT 查 buf——用户态缓冲区地址非法（access_ok 失败），buf 可能是野指针或 count 越界。

Q5：流式对象（socket/pipe）为什么没有「文件偏移」？ A：看 file_ppos()（fs/read_write.c:597-600）：file->f_mode & FMODE_STREAM ? NULL : &file->f_pos。socket/pipe 是流，数据读走即消失、没有「当前位置」概念，所以 f_pos 为 NULL，ksys_write 也就不回写偏移（if (ret >= 0 && ppos) 里 ppos 为空）。这也是它们不支持 lseek（ESPIPE）的同一根源。

Q6：write(fd, buf, 0) 返回 0，这是错误吗？ A：不是。实测 errno=0（成功）。写入 0 个字节是一次合法的"空操作"。但要小心：这意味着 while ((w = write(...)) > 0) 这种循环写法在 w == 0 时会退出——如果你的 count 因为某种原因算成了 0，循环会静默结束且什么都没写。writeall 用的是 total < n 作条件，不会踩这个坑。

Q7：为什么 ksys_read 要多一次 pos 的拷贝，而不让 vfs_read 直接改 f_pos？ A：为了失败时不留半个偏移。看 ksys_read：pos 是局部变量，vfs_read 改的是 &pos；只有 ret >= 0 才写回 f.file->f_pos = pos。如果直接传 &f->f_pos，一次失败的部分读也可能把偏移推走，后续重试就对不上了。

4.6

`close()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/open.c:1557-1584 SYSCALL_DEFINE1(close)） - 上一节：4.5 write() - 下一节：4.7 lseek()

本节讲什么

close() 释放 fd。本节回答三个问题：

  1. close() 在内核里到底做了什么？为什么「不可重启」？
  2. 引用计数（f_count）在其中起什么作用？
  3. 什么时候必须检查 close() 的返回值？

本节有条实测结论很重要：close 之后 fd 号会被立刻回收——这意味着「继续用旧 fd」不会报错，只会静默操作到别人的文件上。这是多线程程序里的经典事故。

1. 原型与内核链路

#include <unistd.h>
int close(int fd);
/* 成功返回 0；失败返回 -1 并设 errno */

close 的逐字全文（fs/open.c:1557-1584，v6.6）：

SYSCALL_DEFINE1(close, unsigned int, fd)
{
    int retval;
    struct file *file;

    file = close_fd_get_file(fd);
    if (!file)
        return -EBADF;

    retval = filp_flush(file, current->files);

    /*
     * We're returning to user space. Don't bother
     * with any delayed fput() cases.
     */
    __fput_sync(file);

    /* can't restart close syscall because file table entry was cleared */
    if (unlikely(retval == -ERESTARTSYS ||
             retval == -ERESTARTNOINTR ||
             retval == -ERESTARTNOHAND ||
             retval == -ERESTART_RESTARTBLOCK))
        retval = -EINTR;

    return retval;
}

三步：

步骤 做什么
close_fd_get_file(fd) 从 fd 表取出并清空该槽位；fd 无效 → -EBADF
filp_flush(file, ...) 刷内核缓冲、处理延迟错误（NFS 的写错误可能这时才报）
__fput_sync(file) 引用计数减一，归零则释放 struct file

2. 为什么 close 不可重启

普通 read/write 被信号打断会返回 ERESTARTSYS，内核在返回用户态时自动重启该系统调用。但 close 不能这么做，内核注释写得很直白：

    /* can't restart close syscall because file table entry was cleared */

close_fd_get_file() 在第一步就把 fd 表项清空了。如果信号打断了 filp_flush 再重启，第二次进来时 fd 已经不存在，会得到 -EBADF——语义就错了。所以内核把 ERESTARTSYS 等一律转成 -EINTR，明确告诉用户「这次关闭没有完成，但 fd 已经释放，别再重试了」。

这也是 close 一个隐蔽陷阱：收到 EINTR 时 fd 状态是不确定的（Linux 上通常已关闭），不能简单地「重试 close」，否则可能误关一个已被复用给其他文件的同号 fd。

3. 引用计数：close ≠ 真正释放

close 只是把 fd 表项清空 + f_count（include/linux/fs.h:1005）减一。struct file 真正的释放在引用计数归零时才发生：

操作 对 f_count 的影响
open() 新建 struct file，f_count = 1
dup()/dup2() 复制 fd，f_count++（共享同一 struct file）
fork() 子进程继承 fd 表，f_count++
close() f_count--；归零 → 调用 f_op->release 释放

所以「close 一个 fd」不等于「文件被关闭」——只要还有其他 fd（或子进程）引用着同一个 struct file，文件就还开着，偏移也还共享。这就是 Ch5 三层结构的核心。

4. 代码：四组实测

完整源码 code/c4_6_close.c：

/* c4_6_close.c — close() 的三个真相：回收 fd 号、减引用计数、不保证落盘
 *
 * 演示四件事：
 *   1) close 之后那个 fd 号立刻可被复用（所以「用旧 fd」是致命错误）
 *   2) 重复 close / close 非法 fd -> EBADF
 *   3) dup 出来的两个 fd 共用一个「打开文件描述」，close 一个不影响另一个
 *   4) fork 之后父子共享同一个打开描述（引用计数 +1）
 *
 * 编译: gcc -O0 -Wall -o c4_6_close c4_6_close.c
 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/wait.h>

int main(void)
{
    char c;
    const char *path = "/tmp/c4_close.txt";

    printf("== 1. close 后 fd 号立即被回收 ==\n");
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
    write(fd, "ABCDEFGHIJ", 10);
    printf("  打开 -> fd=%d\n", fd);
    close(fd);
    printf("  close(%d) 完成\n", fd);

    int other = open(path, O_RDONLY);
    printf("  再打开同一个文件 -> fd=%d  （%s）\n", other,
           other == fd ? "复用了刚释放的号" : "没复用");
    printf("  ⚠️ 此刻若还用旧的 fd=%d 去读写，操作的是「other」这个文件\n", fd);
    printf("     （内核不会报错——号还是合法的，只是指向变了）。\n");

    printf("\n== 2. close 非法 fd / 重复 close ==\n");
    errno = 0;
    int rc = close(999);
    printf("  close(999) -> %d  errno=%d (%s)\n", rc, errno, strerror(errno));
    errno = 0;
    rc = close(other);
    printf("  close(%d) 第一次 -> %d  errno=%d (%s)\n", other, rc, errno, strerror(errno));
    errno = 0;
    rc = close(other);
    printf("  close(%d) 第二次 -> %d  errno=%d (%s)  ← 重复关闭\n",
           other, rc, errno, strerror(errno));

    printf("\n== 3. dup 共享打开文件描述：close 一个，另一个照用 ==\n");
    int a = open(path, O_RDONLY);
    int b = dup(a);
    printf("  a=%d, dup 得 b=%d（同一个 struct file，引用计数 = 2）\n", a, b);
    lseek(a, 3, SEEK_SET);
    read(a, &c, 1);
    printf("  用 a 读到偏移 3 的 '%c'，此时 a 的偏移 = %ld\n",
           c, (long) lseek(a, 0, SEEK_CUR));
    printf("  用 b 查偏移           = %ld  ← 共享！同一个 f_pos\n",
           (long) lseek(b, 0, SEEK_CUR));
    close(a);
    printf("  close(a) 之后：\n");
    ssize_t rn = read(b, &c, 1);            /* 单独一行：别把有副作用的调用塞进 printf 参数 */
    printf("    用 b 还能读吗？read(b) -> %zd 字节，读到 '%c'\n", rn, c);
    printf("  → close 只是让引用计数减一，没减到 0 就不释放 struct file。\n");
    close(b);

    printf("\n== 4. fork 之后父子的偏移也共享 ==\n");
    int f = open(path, O_RDONLY);
    lseek(f, 0, SEEK_SET);
    pid_t pid = fork();
    if (pid == 0) {
        /* 子进程：继承 f，读 4 字节 */
        char cb[5];
        ssize_t n = read(f, cb, 4);
        cb[n > 0 ? n : 0] = '\0';
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("  子进程读了 4 字节后，父进程里 f 的偏移 = %ld\n",
           (long) lseek(f, 0, SEEK_CUR));
    printf("  → 4，不是 0。fork 复制的是 fd 表，表项指向同一个 struct file。\n");
    printf("    父子共享偏移 = 多进程写同一日志会交错，这才是 O_APPEND 存在的理由。\n");
    close(f);
    unlink(path);
    return 0;
}

代码自测（Q&A）

Q1：close() 的作用是什么？进程退出时未关闭的 fd 会怎样？ A：close 清空 fd 表项并让引用计数减一，归零才真正释放 struct file。进程退出时 exit_files() 会逐个 fput 所有 fd，所以正常退出不会永久泄漏；但长驻进程不 close 会一直占着句柄，直到进程结束。

Q2：为什么 close 收到 EINTR 后不能简单重试？ A：因为 close_fd_get_file 已经先把 fd 表项清空了（内核注释：can't restart close syscall because file table entry was cleared）。若重试，该 fd 号可能已被其他线程的 open 复用，重试 close(fd) 会误关别人的文件。收到 EINTR 时应把 fd 视为「已释放」，不再重试。

Q3：为什么 NFS 场景必须检查 close() 的返回值？ A：NFS 的写错误可能延迟到 close 时才返回（filp_flush 触发真正的网络 flush）。write 成功只是写进客户端缓存，close 才可能报出 EIO/ENOSPC。漏查会让「数据没写进去」被误判成成功。

Q4：close(fd) 后，同一个 struct file 一定被释放了吗？ A：不一定。close 只让 f_count 减一；只有引用计数归零才释放。如果之前 dup 过、或 fork 出的子进程还持有同一 struct file，那它仍然活着，偏移也仍被共享（实测：close(a) 之后 b 照常读）。

Q5：close 能保证数据写到磁盘吗？ A：不能。close 只负责释放 fd 和刷内核缓冲，不保证物理落盘。要持久化必须 fsync/fdatasync（且顺序是「先 fsync 再 close」）。忘记这点会导致「以为 close 了数据就安全了」的断电丢数据事故。

Q6：为什么「close 一个已经 close 过的 fd」特别危险？ A：因为那个号可能已经被别人（同进程的另一个线程，或你自己后续的 open）复用。此时 close 会成功返回 0，但它关掉的是别人的打开文件——没有任何错误提示。实测第 1 节展示的「close(3) 后新 open 又拿到 3」正是这个危险的机制来源。防御办法：关闭后立刻把变量置为 -1，或用 O_CLOEXEC + 明确的所有权约定。

`lseek()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/read_write.c:230-278 default_llseek、:285 vfs_llseek、:293 ksys_lseek、:311 SYSCALL_DEFINE3(lseek)；include/linux/fs.h:1007 f_pos）+ 原书 Listing 4-3 seek_io.c - 上一节：4.6 close() - 下一节：4.8 ioctl()

本节讲什么

lseek() 调整文件偏移。本节回答四个问题：

  2. 为什么管道/socket 上 lseek 返回 ESPIPE？

本节还有一个源码层面的发现：SEEK_HOLE/SEEK_DATA 在内核里有两套实现——通用兜底的那套假设文件没有洞，真正的洞检测是具体文件系统提供的。实测输出（4096 而不是 i_size）证明跑的是后者。

1. 原型与内核链路

#include <unistd.h>
off_t lseek(int fd, off_t offset, int whence);
/* 成功返回新偏移；失败 -1（ESPIPE / EBADF / EINVAL） */
whence 基准 语义
SEEK_SET 文件起始 偏移 = offset
SEEK_CUR 当前偏移 偏移 = f_pos + offset（且 offset==0 时只查不改）
SEEK_END 文件末尾 偏移 = i_size + offset
SEEK_DATA / SEEK_HOLE — 定位到下一个数据/空洞区（需文件系统支持） 
用户态 lseek(fd, offset, whence)
      ▼
SYSCALL_DEFINE3(lseek)         fs/read_write.c:311
      ▼
ksys_lseek()                   fs/read_write.c:293
      ├─→ fdget_pos(fd)       ← 取 struct file，fd 无效 → -EBADF
      ├─→ vfs_llseek()        ← 见下
      └─→ fdput_pos(f)

vfs_llseek() 先做「可 seek 性」检查（fs/read_write.c:285-291，逐字）：

loff_t vfs_llseek(struct file *file, loff_t offset, int whence)
{
    if (!(file->f_mode & FMODE_LSEEK))
        return -ESPIPE;
    return file->f_op->llseek(file, offset, whence);
}
EXPORT_SYMBOL(vfs_llseek);

FMODE_LSEEK 值是 0x4（include/linux/fs.h:115）——管道/socket/终端不设这位，所以直接被挡在 -ESPIPE。

2. default_llseek：通用兜底实现

普通文件通常不自己实现 llseek，走内核的默认实现。逐字全文（fs/read_write.c:230-278，v6.6）：

loff_t default_llseek(struct file *file, loff_t offset, int whence)
{
    struct inode *inode = file_inode(file);
    loff_t retval;

    inode_lock(inode);
    switch (whence) {
        case SEEK_END:
            offset += i_size_read(inode);
            break;
        case SEEK_CUR:
            if (offset == 0) {
                retval = file->f_pos;
                goto out;
            }
            offset += file->f_pos;
            break;
        case SEEK_DATA:
            /*
             * In the generic case the entire file is data, so as
             * long as offset isn't at the end of the file then the
             * offset is data.
             */
            if (offset >= inode->i_size) {
                retval = -ENXIO;
                goto out;
            }
            break;
        case SEEK_HOLE:
            /*
             * There is a virtual hole at the end of the file, so
             * as long as offset isn't i_size or larger, return
             * i_size.
             */
            if (offset >= inode->i_size) {
                retval = -ENXIO;
                goto out;
            }
            offset = inode->i_size;
            break;
    }
    retval = -EINVAL;
    if (offset >= 0 || unsigned_offsets(file)) {
        if (offset != file->f_pos) {
            file->f_pos = offset;
            file->f_version = 0;
        }
        retval = offset;
    }
out:
    inode_unlock(inode);
    return retval;
}

三个必须看清的点：

点 说明
SEEK_CUR + offset == 0 → retval = file->f_pos; goto out; 这是「查当前位置」的专用快捷路径：lseek(fd, 0, SEEK_CUR) 不改任何东西，只把当前偏移返回给你
SEEK_END 的「末尾」= i_size_read(inode) 文件大小的权威来源是 inode 的 i_size，不是「实际扫到 EOF」。所以它不需要读一个字节就能算出末尾
if (offset != file->f_pos) 才写回，并清 f_version 偏移没变就不碰 f_pos；一旦改动还会清 f_version（供 NFS/缓存一致性用）

一个源码层面的发现：default_llseek 假设「文件没有洞」

看 SEEK_HOLE 分支的注释和代码：

        case SEEK_HOLE:
            /*
             * There is a virtual hole at the end of the file, so
             * as long as offset isn't i_size or larger, return
             * i_size.
             */
            ...
            offset = inode->i_size;

它的语义是「文件末尾是唯一的洞」——不管 offset 在哪，只要没超出文件末尾，就告诉你「下一个洞在 i_size 处」。

但实测 lseek(4, SEEK_HOLE) 返回的是 4096，不是 i_size（1048580）。 说明真正管事的不是这个通用兜底，而是文件系统自己实现的 llseek（ext4 / overlayfs 会真实遍历 extent 树报告洞的位置）。

这解释了一个容易踩的坑：同样的代码在不同文件系统上行为不同。在不支持洞检测的 FS 上，SEEK_HOLE 会退化成「洞 = 文件末尾」，你的稀疏文件优化逻辑就静默失效了。

3. 文件空洞（sparse file）

lseek(fd, 1024*1024, SEEK_SET);   /* 跳到 1MB 处 */
write(fd, "x", 1);                /* 中间 1MB 是空洞 */

产生一个「逻辑大小 1MB+1，物理只占几 KB」的稀疏文件：

  • 空洞区不分配磁盘块（ls -lh 显示逻辑大小，du -h 显示真实占用）
  • 读空洞区返回 0（内核在页缓存里「现场造零」）
  • 拷贝稀疏文件若用普通 read/write 循环，会把空洞「读成真的 0 字节」写满目标——cp 默认能识别稀疏（cp --sparse=auto），自己写拷贝工具要注意（正确做法见 练习 4-2）

4. 代码：六组实测

/* c4_7_lseek.c — lseek()：只改偏移、不碰磁盘；越尾写就造出空洞
 *
 * 演示六件事：
 *   1) SEEK_SET / SEEK_CUR / SEEK_END 三种基准
 *   2) lseek(fd, 0, SEEK_CUR) 是「查当前偏移」的惯用法
 *   3) lseek 不改数据：同一偏移重复读，内容一样
 *   4) 越尾写造空洞：st_size 大、st_blocks 小（逻辑大小 ≠ 物理占用）
 *   5) 空洞区读出来是 0
 *   6) 管道上 lseek -> ESPIPE
 *
 * 编译: gcc -O0 -Wall -o c4_7_lseek c4_7_lseek.c
 */
#define _GNU_SOURCE     /* 必须在所有 include 之前：SEEK_HOLE / SEEK_DATA 靠它才可见 */
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/stat.h>

static void report_size(const char *tag, const char *path)
{
    struct stat st;
    if (stat(path, &st) < 0) return;
    printf("  %-22s st_size = %8lld 字节   st_blocks = %6lld 块  →  物理占用 ≈ %lld 字节\n",
           tag, (long long) st.st_size, (long long) st.st_blocks,
           (long long) st.st_blocks * 512);
}

int main(void)
{
    char c;
    const char *path = "/tmp/c4_lseek.txt";

    printf("== 1. 三种基准 ==\n");
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
    write(fd, "ABCDEFGHIJ", 10);             /* 10 字节 */
    printf("  文件内容 \"ABCDEFGHIJ\"（10 字节），写完偏移 = %ld\n",
           (long) lseek(fd, 0, SEEK_CUR));

    lseek(fd, 3, SEEK_SET);
    read(fd, &c, 1);
    printf("  SEEK_SET 到 3 再读 1 字节 -> '%c'   新偏移 = %ld\n",
           c, (long) lseek(fd, 0, SEEK_CUR));

    lseek(fd, -2, SEEK_CUR);
    read(fd, &c, 1);
    printf("  SEEK_CUR 回退 2 再读 1 字节 -> '%c'  新偏移 = %ld\n",
           c, (long) lseek(fd, 0, SEEK_CUR));

    lseek(fd, -1, SEEK_END);
    read(fd, &c, 1);
    printf("  SEEK_END 回退 1 再读 1 字节 -> '%c'  新偏移 = %ld\n",
           c, (long) lseek(fd, 0, SEEK_CUR));

    printf("\n== 2. lseek 只改偏移，不改数据 ==\n");
    lseek(fd, 0, SEEK_SET);
    read(fd, &c, 1);
    printf("  偏移 0 读到 '%c'\n", c);
    lseek(fd, 0, SEEK_SET);
    read(fd, &c, 1);
    printf("  再回偏移 0 读到 '%c'  ← 数据没被动过，动的只是游标\n", c);

    printf("\n== 3. 越尾写 = 文件空洞（sparse file）==\n");
    close(fd);
    unlink(path);
    fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
    write(fd, "HEAD", 4);                     /* 真实数据 4 字节 */
    report_size("只写 4 字节", path);

    off_t at = lseek(fd, 1024 * 1024, SEEK_SET);   /* 跳到 1 MiB 处 */
    printf("  lseek 到 1 MiB -> %ld\n", (long) at);
    write(fd, "TAIL", 4);
    report_size("越尾写 4 字节后", path);
    printf("  → 逻辑大小 ≈ 1 MiB + 4，物理占用只有几 KB。中间是空洞。\n");

    printf("\n== 4. 空洞区读出来是 0 ==\n");
    lseek(fd, 4096, SEEK_SET);                /* 跳进空洞中间 */
    char zbuf[8];
    ssize_t n = read(fd, zbuf, sizeof zbuf);
    printf("  从空洞里读 %zd 字节，全部是零？%s\n", n,
           (n == 8 && zbuf[0] == 0 && zbuf[7] == 0) ? "是" : "否");
    printf("  → 没有磁盘块存在，内核在页缓存里「现场造零」。\n");

    printf("\n== 5. SEEK_HOLE / SEEK_DATA：问文件系统「哪里有洞」==\n");
#ifdef SEEK_HOLE
    lseek(fd, 0, SEEK_SET);
    off_t d = lseek(fd, 0, SEEK_DATA);
    printf("  lseek(0, SEEK_DATA) -> %lld   （0：开头就是数据）\n", (long long) d);
    off_t h = lseek(fd, 4, SEEK_HOLE);
    printf("  lseek(4, SEEK_HOLE) -> %lld   ← 不是 4！文件系统按**块**报边界\n",
           (long long) h);
    if (h > 0) {
        d = lseek(fd, h, SEEK_DATA);
        printf("  lseek(%lld, SEEK_DATA) -> %lld   （下一个数据段的起点）\n",
               (long long) h, (long long) d);
    }
    printf("  → 粒度是文件系统块（这里 4096 字节），不是字节。所以洞的范围会被\n");
    printf("    向上取整到块边界；别拿它做逐字节的精确判断。\n");
#else
    printf("  （本平台没定义 SEEK_HOLE；需要 _GNU_SOURCE + 支持该特性的文件系统）\n");
#endif
    close(fd);

    printf("\n== 6. 管道上 lseek：ESPIPE ==\n");
    int p[2];
    pipe(p);
    errno = 0;
    off_t r = lseek(p[0], 0, SEEK_CUR);
    printf("  lseek(pipe, 0, SEEK_CUR) -> %ld  errno=%d (%s)\n",
           (long) r, errno, strerror(errno));
    printf("  → 管道是流，数据读走即消失，根本没有「当前位置」这个概念。\n");
    close(p[0]);
    close(p[1]);
    unlink(path);
    return 0;
}

/* seek_io.c

   Demonstrate the use of lseek() and file I/O system calls.

   Usage: seek_io file {r<length>|R<length>|w<string>|s<offset>}...

   This program opens the file named on its command line, and then performs
   the file I/O operations specified by its remaining command-line arguments:

           r<length>    Read 'length' bytes from the file at current
                        file offset, displaying them as text.

           R<length>    Read 'length' bytes from the file at current
                        file offset, displaying them in hex.

           w<string>    Write 'string' at current file offset.

           s<offset>    Set the file offset to 'offset'.

   Example:

        seek_io myfile wxyz s1 r2
*/
#include <sys/stat.h>
#include <fcntl.h>
#include <ctype.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    size_t len;
    off_t offset;
    int fd, ap, j;
    unsigned char *buf;
    ssize_t numRead, numWritten;

    if (argc < 3 || strcmp(argv[1], "--help") == 0)
        usageErr("%s file {r<length>|R<length>|w<string>|s<offset>}...\n",
                 argv[0]);

    fd = open(argv[1], O_RDWR | O_CREAT,
                S_IRUSR | S_IWUSR | S_IRGRP | S_IWGRP |
                S_IROTH | S_IWOTH);                     /* rw-rw-rw- */
    if (fd == -1)
        errExit("open");

    for (ap = 2; ap < argc; ap++) {
        switch (argv[ap][0]) {
        case 'r':   /* Display bytes at current offset, as text */
        case 'R':   /* Display bytes at current offset, in hex */
            len = getLong(&argv[ap][1], GN_ANY_BASE, argv[ap]);

            buf = malloc(len);
            if (buf == NULL)
                errExit("malloc");

            numRead = read(fd, buf, len);
            if (numRead == -1)
                errExit("read");

            if (numRead == 0) {
                printf("%s: end-of-file\n", argv[ap]);
            } else {
                printf("%s: ", argv[ap]);
                for (j = 0; j < numRead; j++) {
                    if (argv[ap][0] == 'r')
                        printf("%c", isprint(buf[j]) ?  buf[j] : '?');
                    else
                        printf("%02x ", buf[j]);
                }
                printf("\n");
            }

            free(buf);
            break;

        case 'w':   /* Write string at current offset */
            numWritten = write(fd, &argv[ap][1], strlen(&argv[ap][1]));
            if (numWritten == -1)
                errExit("write");
            printf("%s: wrote %ld bytes\n", argv[ap], (long) numWritten);
            break;

        case 's':   /* Change file offset */
            offset = getLong(&argv[ap][1], GN_ANY_BASE, argv[ap]);
            if (lseek(fd, offset, SEEK_SET) == -1)
                errExit("lseek");
            printf("%s: seek succeeded\n", argv[ap]);
            break;

        default:
            cmdLineErr("Argument must start with [rRws]: %s\n", argv[ap]);
        }
    }

    if (close(fd) == -1)
        errExit("close");

    exit(EXIT_SUCCESS);
}

两个使用注意

  1. open 用的是 O_RDWR | O_CREAT，没有 O_TRUNC（seek_io.c:54-56）。所以对同一个文件重复运行，新写的字符会盖在旧内容上，读出来的东西和上一次有关。CE 每次是干净沙箱所以看不出来；本地反复跑请换文件名或先删。
  2. r 模式把不可打印字符打成 ?（seek_io.c:80：isprint(buf[j]) ? buf[j] : '?'）。所以想看清二进制内容要用 R（hex）。想看「洞里的 0」用 R 才能看到 00。

6. HFT / 嵌入式关联

现象 本节机制的兑现
日志文件大小 lseek(fd, 0, SEEK_END) 是「不用 stat 拿文件大小」的快捷方式（但要恢复原偏移）；更稳的是 fstat
稀疏文件省盘 预分配大文件（如行情回放文件）用 lseek + 写尾，逻辑大小大、物理占用小。实测 1 MiB 逻辑只占 8 KiB
洞检测要挑文件系统 SEEK_HOLE 在支持它的 FS 上给精确边界，在不支持的 FS 上退化成 default_llseek 的「洞=文件末尾」——同一份代码两种行为
管道不可 seek 从管道/socket 读流时不能回退/跳转，只能顺序消费——行情流天然是「只前进」的
偏移是共享状态 f_pos 在 struct file 里，dup/fork 共享；多进程随机读写要各自独立 open

代码自测（Q&A）

Q1：lseek(fd, 0, SEEK_CUR) 的作用是什么？ A：从当前位置偏移 0 字节，即「查询当前偏移而不移动」。default_llseek 里有专门的快捷分支：case SEEK_CUR: if (offset == 0) { retval = file->f_pos; goto out; }——直接返回，连锁里的 switch 都不走完。

Q2：所有文件类型都支持 lseek 吗？ A：不。管道、socket、终端没有 FMODE_LSEEK（fs.h:115，值 0x4）标志，vfs_llseek 第一行就 return -ESPIPE。实测管道上 errno=29。它们是流式对象，数据读走即消失，没有「位置」概念。

Q3：lseek 越尾再写会怎样？为什么「中间不占磁盘」？ A：产生文件空洞。lseek 只改 f_pos 不写数据，中间的偏移区间没有对应磁盘块；只有后来 write 的尾部字节真正分配块。读空洞区时内核返回 0（页缓存现场造零）。实测：逻辑 1048580 字节、物理 8192 字节。

Q4：用「lseek(SEEK_END) 拿文件大小」有什么要注意的？ A：SEEK_END 会移动 f_pos 到末尾。若之后还要在原位置读写，必须先 SEEK_CUR 记住原偏移、查完再 SEEK_SET 恢复。更稳妥的是用 fstat/stat 直接读 st_size，不碰偏移。

Q5：lseek 会不会触发磁盘 I/O？ A：不会。它只改内存里的 struct file::f_pos（include/linux/fs.h:1007），不读数据、不分配块（除非后续 write 到空洞区才分配）。这也是「lseek 极快」的原因。

Q6：SEEK_HOLE 在所有文件系统上都返回真实洞位置吗？ A：不一定。default_llseek 的 SEEK_HOLE 分支写死了「文件末尾是唯一的洞」（注释：There is a virtual hole at the end of the file），会直接返回 i_size。只有文件系统自己实现了 llseek 才会报告真实洞位置。实测在 overlayfs 上 lseek(4, SEEK_HOLE) 返回 4096（真实边界），说明走的是文件系统实现——所以这段代码的可移植性取决于底层 FS。

Q7：为什么 SEEK_HOLE 报的洞起点是 4096 而不是 5？ A：因为洞检测的粒度是文件系统块（这里 4 KiB），不是字节。前 5 字节 HEAD- 落在第 0 号块里，整个块就被视为「有数据」，所以下一个洞从块边界 4096 开始。做稀疏拷贝优化时要按块处理，不要假设字节级精度。

本节讲什么

ioctl() 是通用 I/O 模型的「兜底出口」。本节回答四个问题：

  1. 为什么 read/write/lseek 之外还需要 ioctl？它在内核里走哪条路？
  2. request 那个 32 位整数是怎么编码「方向 + 大小 + 类型 + 编号」的？
  3. ENOTTY 到底是什么错误？内核里它有几个来源？
  4. isatty()、FIONREAD、FIONBIO 这些「通用能力」在源码里长什么样？

本节还有一个实测纠正：TIOCGWINSZ 这个最常见的 ioctl 例子，并不符合 _IOR/_IOW 的编码规范——dir 和 size 两位都是 0。网上流传的 _IOR('T', 104, struct winsize) 是错的（算出来是 0x80085468，真值是 0x5413）。

1. 原型与内核链路

#include <sys/ioctl.h>
int ioctl(int fd, int request, ...);   /* 可变参数：驱动自定义的结构体指针 */
/* 成功返回 0（或驱动自定义值）；失败 -1 并设 errno */

ioctl 处理的是「字节流之外的控制」：查终端窗口大小、配网卡混杂模式、读取设备寄存器——这些没有 read/write 语义，只能靠一个「命令字 + 数据指针」的万能接口。

用户态 ioctl(fd, cmd, arg)
      ▼
SYSCALL_DEFINE3(ioctl)                    fs/ioctl.c:857
      ├─→ fdget(fd)                       无效 fd → -EBADF
      ├─→ security_file_ioctl()           LSM 钩子
      ▼
do_vfs_ioctl(filp, fd, cmd, arg)          fs/ioctl.c:773  ← 通用命令在此统一处理
      ├─→ 命中通用命令：FIOCLEX / FIONCLEX / FIONBIO / FIONREAD / FIOQSIZE …
      ├─→ default: 普通文件 → file_ioctl() fs/ioctl.c:324
      └─→ break → 返回 -ENOIOCTLCMD
      ▼（返回值是 -ENOIOCTLCMD 时）
vfs_ioctl(filp, cmd, arg)                 fs/ioctl.c:44
      ├─→ 没有 f_op->unlocked_ioctl → 直接 -ENOTTY
      └─→ f_op->unlocked_ioctl(filp, cmd, arg)   ← 驱动 switch(cmd)
              └─→ 驱动返回 -ENOIOCTLCMD → 翻译成 -ENOTTY

SYSCALL_DEFINE3(ioctl, …) 逐字（fs/ioctl.c:857-876，v6.6）：

SYSCALL_DEFINE3(ioctl, unsigned int, fd, unsigned int, cmd, unsigned long, arg)
{
    struct fd f = fdget(fd);
    int error;

    if (!f.file)
        return -EBADF;

    error = security_file_ioctl(f.file, cmd, arg);
    if (error)
        goto out;

    error = do_vfs_ioctl(f.file, fd, cmd, arg);
    if (error == -ENOIOCTLCMD)
        error = vfs_ioctl(f.file, cmd, arg);

out:
    fdput(f);
    return error;
}

三层结构说清了一件事：VFS 只负责「通用命令」和「转发」两件事，它完全不懂你的 request 是什么意思。和 read/write 一样，差异被 f_op->unlocked_ioctl 吸收——只不过这次连「命令语义」都是设备自定义的。

2. request 的编码：_IO / _IOR / _IOW / _IOWR

request 是 32 位整数，四段按位打包（include/uapi/asm-generic/ioctl.h:5-13 原文注释）：

/* ioctl command encoding: 32 bits total, command in lower 16 bits,
 * size of the parameter structure in the lower 14 bits of the
 * upper 16 bits.
 * ...
 * The highest 2 bits are reserved for indicating the ``access mode''.
 * NOTE: This limits the max parameter size to 16kB -1 !
 */

 31   30 29                16 15            8 7             0
┌───────┬───────────────────┬───────────────┬───────────────┐
│ dir   │      size         │  type (magic) │      nr       │
│ 2 bit │     14 bit        │     8 bit     │    8 bit      │
└───────┴───────────────────┴───────────────┴───────────────┘
  读/写     arg 结构体字节数      设备类别号        命令序号

位移常量（include/uapi/asm-generic/ioctl.h:44-47）：

#define _IOC_NRSHIFT    0
#define _IOC_TYPESHIFT  (_IOC_NRSHIFT+_IOC_NRBITS)      /* 0+8   = 8  */
#define _IOC_SIZESHIFT  (_IOC_TYPESHIFT+_IOC_TYPEBITS)  /* 8+8   = 16 */
#define _IOC_DIRSHIFT   (_IOC_SIZESHIFT+_IOC_SIZEBITS)  /* 16+14 = 30 */

宏本体（include/uapi/asm-generic/ioctl.h:69-73）：_IOC(dir,type,nr,size) 就是四个字段左移后按位或。四个生成宏（include/uapi/asm-generic/ioctl.h:85-88）：

宏 方向位 含义
_IO(type,nr) _IOC_NONE (0) 纯命令，无参数
_IOR(type,nr,size) _IOC_READ (2) 用户态读：内核 → 用户
_IOW(type,nr,size) _IOC_WRITE (1) 用户态写：用户 → 内核
_IOWR(type,nr,size) READ\|WRITE (3) 双向

注意方向命名的视角坑（include/uapi/asm-generic/ioctl.h:82-83 原文注释）： NOTE: _IOW means userland is writing and kernel is reading. _IOR means userland is reading and kernel is writing. ——站在用户态视角命名，和「内核读/写」正好相反。

解码宏（:94-97）是逆运算，驱动里常用：_IOC_DIR(nr) / _IOC_TYPE(nr) / _IOC_NR(nr) / _IOC_SIZE(nr)。

3. 实测：TIOCGWINSZ 并不符合编码规范

查终端窗口大小是最经典的 ioctl 例子：

struct winsize ws;
ioctl(STDIN_FILENO, TIOCGWINSZ, &ws);   /* 成功则 ws.ws_row / ws.ws_col 有效 */

按规范，它「应该」是 _IOR('T', <nr>, struct winsize)。但实测把 0x5413 按位拆开：

字段 位 实测值
dir 30-31 0 ← 既不是 _IOC_READ(2) 也不是 _IOC_WRITE(1)
size 16-29 0 ← 不是 sizeof(struct winsize) = 8
type 8-15 84 = 'T' ✓
nr 0-7 19 = 0x13

原因在 ioctl.h 隔壁那个文件：它是硬编码的老式命令字（include/uapi/asm-generic/ioctls.h:38）：

#define TIOCGWINSZ  0x5413

0x5413 恰好等于 _IO('T', 0x13)（无参数写法）——type='T' 占 8 位 → 0x54，nr=0x13 → 0x13，dir/size 都是 0。数值对得上，但语义是"无参数"，这就埋了个坑：内核靠的是 type/nr 路由，size 只用于部分架构的边界校验，所以它能工作。

而网上流传的 _IOR('T', 104, struct winsize) 算出来是：

_IOC(2, 'T', 104, 8) = (2<<30) | ('T'<<8) | (104<<0) | (8<<16)
                     = 0x80000000 | 0x00005400 | 0x68 | 0x00080000
                     = 0x80085468        ← 跟真值 0x5413 完全对不上

那条说法是错的（nr 和 dir/size 三处都不对）。tty 有一大批命令字沿用 0x54xx 这段历史编号（TCGETS 0x5401、TIOCGWINSZ 0x5413、FIONREAD 0x541B、FIONBIO 0x5421、FIOCLEX 0x5451…），别指望它们都合规。

反例：同一文件里的 TCGETS2 就是合规的——ioctls.h:61 写的是 #define TCGETS2 _IOR('T', 0x2A, struct termios2)。新命令字才按规范来。

4. 实测：ENOTTY 的两个来源

ENOTTY 的字面意思是 "not a typewriter"（历史遗留），现代含义是「这个对象不认识这个命令」。它在内核里有两条产生路径，都在 vfs_ioctl 里（fs/ioctl.c:44-56 逐字）：

long vfs_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
    int error = -ENOTTY;

    if (!filp->f_op->unlocked_ioctl)
        goto out;

    error = filp->f_op->unlocked_ioctl(filp, cmd, arg);
    if (error == -ENOIOCTLCMD)
        error = -ENOTTY;
 out:
    return error;
}
来源 行号 条件
① 对象没有 unlocked_ioctl 方法 :46 + :48-49 初值 error = -ENOTTY，直接 goto out
② 对象有方法，但驱动说「命令不认识」 :52-53 驱动返回 -ENOIOCTLCMD → 统一翻译成 -ENOTTY

-ENOIOCTLCMD 是个纯内核内部的哨兵值（include/linux/errno.h 里定义为 -ENOIOCTLCMD 515 附近的内部错误码），设计目的就是「让驱动表达'这条命令我没实现'，由 VFS 决定对外报什么」。用户态永远看不到 ENOIOCTLCMD——它是被 vfs_ioctl 吃掉、翻译成 ENOTTY 的。

实测三种对象：

对象 请求 结果
stdout（被 CE 重定向到管道/文件） TIOCGWINSZ -1 errno=25 (ENOTTY)
普通文件（/tmp/c4_ioctl.txt） TIOCGWINSZ -1 errno=25 (ENOTTY)
管道（写端关掉后读） FIONREAD 成功，返回可读字节数

对普通文件，do_vfs_ioctl 的 default: 分支会先转给 file_ioctl（fs/ioctl.c:324-340），而它只管 FIBMAP / 预分配（FS_IOC_RESVSP）/ FS_IOC_ZERO_RANGE 这几条，其余返回 -ENOIOCTLCMD——于是 TIOCGWINSZ 走完 ② 路径变成 ENOTTY。

5. isatty() 的真相：标准库在用 ioctl

isatty() 看着像个「系统提供的布尔变量」，实际就是试一个 tty 专属 ioctl。glibc 2.39 的完整链路：

/* sysdeps/posix/isatty.c:21-28 —— 逐字 */
/* Return 1 if FD is a terminal, 0 if not.  */
int
__isatty (int fd)
{
  struct termios term;

  return __tcgetattr (fd, &term) == 0;
}

weak_alias (__isatty, isatty)

而 __tcgetattr 最终落到 ioctl（sysdeps/unix/sysv/linux/tcgetattr.c:33-38 逐字）：

int
__tcgetattr (int fd, struct termios *termios_p)
{
  struct __kernel_termios k_termios;
  int retval;

  retval = INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios);

所以 isatty(fd) == (ioctl(fd, TCGETS, &k_termios) == 0)——成功了就是终端，ENOTTY 就不是。TCGETS = 0x5401（ioctls.h:20）。

实测（CE 沙箱里 stdin/stdout 都被接管）：

  isatty(STDIN_FILENO)  = 0
  isatty(STDOUT_FILENO) = 0
  isatty(open("/tmp")) = 0

三个都是 0 —— 沙箱里没有任何 fd 是终端。

6. 通用命令：FIONREAD 与 FIONBIO

FIONREAD：现在有多少字节可读

它藏在 do_vfs_ioctl 的 switch 里（fs/ioctl.c:829-834 逐字）：

    case FIONREAD:
        if (!S_ISREG(inode->i_mode))
            return vfs_ioctl(filp, cmd, arg);

        return put_user(i_size_read(inode) - filp->f_pos,
                (int __user *)argp);

逻辑分叉很漂亮：

  • 普通文件 → 直接算 i_size - f_pos，即「文件里还剩多少字节没读」，不用任何设备配合
  • 非普通文件（管道/socket/字符设备）→ vfs_ioctl 转发给对象自己的 unlocked_ioctl

管道那边就是 pipe_ioctl（fs/pipe.c:608-626 逐字节选）：

static long pipe_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
    struct pipe_inode_info *pipe = filp->private_data;
    unsigned int count, head, tail, mask;

    switch (cmd) {
    case FIONREAD:
        __pipe_lock(pipe);
        count = 0;
        head = pipe->head;
        tail = pipe->tail;
        mask = pipe->ring_size - 1;

        while (tail != head) {
            count += pipe->bufs[tail & mask].len;
            tail++;
        }
        __pipe_unlock(pipe);

        return put_user(count, (int __user *)arg);

它遍历环形缓冲区把各段长度加起来——这是为什么它要加锁。注册点（fs/pipe.c:1228）：.unlocked_ioctl = pipe_ioctl。

实测：写 9 字节 → avail=9；读走 4 字节 → avail=5。

FIONBIO：用 ioctl 切非阻塞

do_vfs_ioctl 里直接转给 ioctl_fionbio（fs/ioctl.c:342-362 逐字节选）：

static int ioctl_fionbio(struct file *filp, int __user *argp)
{
    unsigned int flag;
    int on, error;

    error = get_user(on, argp);
    if (error)
        return error;
    flag = O_NONBLOCK;
    ...
    spin_lock(&filp->f_lock);
    if (on)
        filp->f_flags |= flag;
    else
        filp->f_flags &= ~flag;
    spin_unlock(&filp->f_lock);
    return error;
}

它就是在 filp->f_flags 上置/清 O_NONBLOCK 位——和 fcntl(fd, F_SETFL, O_NONBLOCK) 改的是同一个字段、同一个位。所以：

ioctl(fd, FIONBIO, &on);              /* 老式写法，POSIX 之前的风格 */
fcntl(fd, F_SETFL, O_NONBLOCK);       /* 现代写法，语义等价 */

区别只在于 fcntl 会重建整份 f_flags（你给什么就是什么），而 FIONBIO 只动 O_NONBLOCK 一位。实测设为非阻塞后读空管道 → -1 errno=11 (EAGAIN)，立刻返回不阻塞。

    close(p[1]);

    pipe(q);
    int on = 1;
    ioctl(q[0], FIONBIO, &on);                 /* 同 fcntl(q[0], F_SETFL, O_NONBLOCK) */
    errno = 0;
    ssize_t n = read(q[0], tmp, 4);            /* 管道是空的 */

           n, errno, strerror(errno));
    close(q[0]);
    close(q[1]);

    printf("\n== 6. 普通文件上的 ioctl：ENOTTY ==\n");
    int f = open("/tmp/c4_ioctl.txt", O_RDONLY);
    errno = 0;
    rc = ioctl(f, TIOCGWINSZ, &ws);
    printf("  ioctl(普通文件, TIOCGWINSZ) -> %d  errno=%d (%s)\n",
           rc, errno, strerror(errno));
    printf("  → ENOTTY 的字面是 \"not a typewriter\"，历史遗留；\n");
    printf("    现代含义是「这个对象不认识这个命令」。\n");

    unlink("/tmp/c4_ioctl.txt");

代码自测（Q&A）

Q1：为什么有了 read/write/lseek 还要 ioctl？ A：因为「字节流」语义覆盖不了「控制/查询」类操作。设置终端窗口大小、查询设备寄存器、配网卡混杂模式——这些不是「搬一段字节」，没有对应的 read/write 动词。ioctl 用「命令字 + 数据指针」提供万能兜底。内核里 vfs_ioctl 的两条路（:46 无方法 → ENOTTY，:52-53 有方法但返回 -ENOIOCTLCMD → ENOTTY）就是它「透传 + 兜底」的体现。

Q2：request 里为什么编码 size？ A：为了安全。ioctl 的可变参数是用户态指针，驱动要 copy_from_user/copy_to_user。request 的 size 字段（include/uapi/asm-generic/ioctl.h:5-13 注释原话：「useful for catching programs compiled with old versions and to avoid overwriting user space outside the user buffer area」）让内核知道要拷多少字节。_IOR/_IOW 用 sizeof(datatype) 自动填入，并把上限卡在 16 kB−1。

Q3：为什么 TIOCGWINSZ 的 dir/size 都是 0？ A：因为它是硬编码的老式命令字（ioctls.h:38 直接写 0x5413），不是用宏拼出来的。0x5413 恰好等于 _IO('T', 0x13)——「无参数」的编码。tty 的 0x54xx 段都这德行。所以别用「按位拆 dir」来推断它读还是写；要看内核源码里这个 case 实际怎么用 arg。

Q4：ENOTTY 有几种来源？ A：两种，都在 vfs_ioctl（fs/ioctl.c:44-56）：①对象没有 unlocked_ioctl → 初值 -ENOTTY 直接返回；②有方法但驱动返回 -ENOIOCTLCMD → 翻译成 -ENOTTY。用户态永远看不到 ENOIOCTLCMD，它是内核内部哨兵值。字面 "not a typewriter" 是历史遗留，现代含义就是「对象不认识这条命令」。

Q5：isatty() 内部做了什么？ A：glibc 2.39 里 __isatty（sysdeps/posix/isatty.c:23-28）只做一件事：return __tcgetattr(fd, &term) == 0;。而 __tcgetattr（sysdeps/unix/sysv/linux/tcgetattr.c:38）里是 INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios)。所以 isatty 就是「试一下 tty 专属 ioctl，成功就是终端」——清清爽爽的 ioctl 应用。

Q6：FIONBIO 和 fcntl(F_SETFL, O_NONBLOCK) 有什么区别？ A：改的是同一个东西——filp->f_flags 的 O_NONBLOCK 位（ioctl_fionbio 里 filp->f_flags |= O_NONBLOCK）。区别：FIONBIO 只动这一位，fcntl(F_SETFL) 是「整份标志替换」（你给什么剩什么）。fcntl 是 POSIX 正路，FIONBIO 是老式写法。混用不会打架，但要知道它们共享同一份状态。

Q7：管道上的 FIONREAD 是谁实现的？ A：不是 VFS 的通用代码，而是管道的 pipe_ioctl（fs/pipe.c:608，注册在 :1228 的 .unlocked_ioctl = pipe_ioctl）。do_vfs_ioctl 的 FIONREAD 分支（:829-834）发现「不是普通文件」后 return vfs_ioctl(...) 转发过去，pipe_ioctl 加锁遍历环形缓冲区把各段 len 加起来。同一个命令字，普通文件和管道走两套完全不同的实现。

Q8：ioctl 的返回值可靠吗？ A：只能可靠地判断「成功/失败」。失败是 -1 + errno；成功时的返回值由驱动自定义（FIONREAD 返回 0，但数据写在 arg 里）。所以标准写法是 if (ioctl(...) == -1)，不要用「返回值 == 某个正数」当成功判据。

Q1：为什么 read/write 可能返回小于请求的字节数？ A：read 侧：到了 EOF、管道/socket 缓冲区只有部分数据、被信号中断（EINTR）、终端读到行尾。write 侧：磁盘空间不足（ENOSPC）、管道缓冲只剩一部分、被信号中断。这是合法结果不是错误，正确做法是循环调用直到传完。实测两个极端：文件只剩 6 字节时 read(8) 返回 6；往 4 KiB 容量管道裸 write(8192) 返回 4096。

Q2：fork() 后父子进程共享文件偏移吗？ A：共享。fork 复制的是第一层（fd 表），表项指向的还是同一个 struct file（第二层），f_pos 在 struct file 里（include/linux/fs.h:1007），所以父子看到同一个游标。实测子进程读走 4 字节后，父进程查到的偏移就是 4。要各自独立就各自 open。

Q3：O_APPEND 为什么能保证多进程写入不交错？ A：内核把「定位到末尾 + 写」在 vfs_write 内部原子完成——不是用户态的两步。所以多个进程的追加严格串行。没有 O_APPEND 时 lseek(SEEK_END) + write() 是两步，之间有 TOCTOU 竞争窗口，会互相覆盖。这是本章唯一无法用用户态代码复刻同等原子性的机制。

Q4：为什么 close() 不能重试？ A：close 失败返回 EBADF 时，说明这个 fd 本来就不是有效的——但内核仍可能已经把槽位释放掉了（Linux 的 close 在 fput 之后才报错）。此时重试 close(3)，如果这期间别的线程 open 拿到了 3 号，你关的就是别人的文件。实测第二次 close(3) 返回 EBADF。正确姿势：close 失败不要重试，最多打个日志。

Q5：F_GETFL 返回的标志和 open 时传的一样吗？ A：不一定。内核会在 do_sys_openat2 里补一些位——最典型的是 if (force_o_largefile()) flags |= O_LARGEFILE;（fs/open.c:1443-1444），在 32 位系统上强制加 O_LARGEFILE。实测传 0 得到 F_GETFL = 0x8000，正是这个位。另外 O_CLOEXEC 不在 F_GETFL 里——它是 fd 标志，要用 F_GETFD 查 FD_CLOEXEC。

Q6：isatty() 是怎么实现的？ A：glibc 2.39 里 __isatty（sysdeps/posix/isatty.c:23-28）就是 return __tcgetattr(fd, &term) == 0;，而 __tcgetattr（sysdeps/unix/sysv/linux/tcgetattr.c:38）是 INLINE_SYSCALL (ioctl, 3, fd, TCGETS, &k_termios)。所以 isatty 本质就是「试一个 tty 专属 ioctl」——成功是终端，ENOTTY 就不是。标准库把 ioctl 用在了最基础的判断上。

Q7：read(fd, buf, count) 的 count 能随便给吗？为什么会「成功」？ A：count 只受两层限制：① MAX_RW_COUNT（include/linux/fs.h:2399，INT_MAX & PAGE_MASK）——超过会被截断；② access_ok 只验证地址范围落在用户空间，它不知道你的 buffer 到底分配了多大。实测拿一个 64 字节的栈数组、count 给 1 GiB，内核照样读到文件末尾返回 36——它把超出 buffer 的部分写进了你的栈。这是静默内存破坏，比报错危险得多。

Q8：为什么 write 返回成功不代表数据安全了？ A：因为 write 只保证数据进了页缓存（page cache），磁盘上还没有。此时断电，数据就没了。要落盘必须显式调 fsync(fd)（连元数据一起）或 fdatasync(fd)（只保证数据），或者用 O_SYNC/O_DSYNC 打开。实测两者在本章 demo 里都返回 0。HFT 场景下「成交回报必须落盘」就得走这条路。

实现

完整源码 code/ex4_1_tee.c：

/* ex4_1_tee.c — TLPI 练习 4-1：用 I/O 系统调用实现 tee
 *
 * 【题干（原书 Exercise 4-1，逐字）】
 *   The tee command reads its standard input until end-of-file, writing a
 *   copy of the input to standard output and to the file named in its
 *   command-line argument.  Implement tee using I/O system calls.  By
 *   default, tee overwites any existing file with the given name.
 *   Implement the -a command-line option (tee -a file), which casuses tee
 *   to append text to the end of a file if it already exists.
 *
 * 【实现要点】
 *   - 一份输入，两处输出：stdout 一份、文件一份
 *   - 循环 read 到 0（EOF）；每轮把读到的 n 字节写两处
 *   - -a：打开文件时加 O_APPEND（而不是 O_TRUNC）
 *   - getopt(3) 解析选项；用完记得检查 optind == argc - 1（恰好一个文件参数）
 *
 * 【踩坑提示】写 stdout 也可能发生部分写（stdout 可能是管道且缓冲区满），
 *   所以两处都要用 writeAll 循环，不能只 `write(...)` 一下就走。
 *
 * 编译: gcc -O0 -Wall -o ex4_1_tee ex4_1_tee.c
 * 用法: echo hello | ./ex4_1_tee out.txt
 *       echo world | ./ex4_1_tee -a out.txt
 */
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

#define BUF_SIZE 1024

/* 把 buf 里 len 字节完整写到 fd：处理部分写和 EINTR */
static ssize_t writeAll(int fd, const char *buf, size_t len)
{
    size_t written = 0;

    while (written < len) {
        ssize_t n = write(fd, buf + written, len - written);
        if (n < 0) {
            if (errno == EINTR)
                continue;               /* 被信号打断：数据没写、不是错误，重试 */
            return -1;                  /* 真错误 */
        }
        written += (size_t) n;
    }
    return (ssize_t) written;
}

int main(int argc, char *argv[])
{
    int append = 0;
    int opt;

    while ((opt = getopt(argc, argv, "a")) != -1) {
        switch (opt) {
        case 'a': append = 1;  break;
        default:
            fprintf(stderr, "Usage: %s [-a] file\n", argv[0]);
            return 1;
        }
    }

    if (optind != argc - 1) {
        fprintf(stderr, "Usage: %s [-a] file\n", argv[0]);
        return 1;
    }
    const char *path = argv[optind];

    int flags = O_WRONLY | O_CREAT | (append ? O_APPEND : O_TRUNC);
    int fd = open(path, flags, 0644);
    if (fd < 0) {
        fprintf(stderr, "open %s: %s\n", path, strerror(errno));
        return 1;
    }

    char buf[BUF_SIZE];
    ssize_t n;
    int rounds = 0;

    while ((n = read(STDIN_FILENO, buf, sizeof buf)) > 0) {
        rounds++;
        if (writeAll(fd, buf, (size_t) n) < 0) {   /* 去处一：文件 */
            fprintf(stderr, "write %s: %s\n", path, strerror(errno));
            return 1;
        }
        if (writeAll(STDOUT_FILENO, buf, (size_t) n) < 0) {  /* 去处二：屏幕 */
            fprintf(stderr, "write stdout: %s\n", strerror(errno));
            return 1;
        }
    }
    if (n < 0) {
        fprintf(stderr, "read: %s\n", strerror(errno));
        return 1;
    }

    fprintf(stderr, "[ex4_1_tee] 读了 %d 轮，模式 = %s\n",
            rounds, append ? "append (-a)" : "overwrite (默认 O_TRUNC)");
    close(fd);
    return 0;
}

两处细节值得单独点出来：

  1. 写 stdout 也必须循环。stdout 被重定向到管道时，缓冲区满会部分写——和写文件一样要用 writeAll。只对文件循环、对 stdout 直接 write() 一下，是这道题最常见的半对答案。
  2. getopt 之后要检查 optind == argc - 1。否则 ./tee a b（两个文件参数）会被当成合法输入，静默忽略 b。optind 是「第一个非选项参数的下标」。

练习 4-2：写一个保留空洞的 cp

题干（原书 Exercise 4-2，逐字）

Write a program like cp that, when used to copy a regular file that contains holes (sequences of null bytes), also creates corresponding holes in the target file.

朴素做法错在哪

教科书式的拷贝循环：

while ((n = read(in, buf, sizeof buf)) > 0)
    write(out, buf, n);

读空洞区时，内核交给你的是真实的 0 字节（4.7 实测：空洞读出来全是 0）。这些 0 被老老实实写进目标文件，目标文件就真的分配了磁盘块——空洞被「灌实」了。

一个 1 MB 逻辑大小、实际只占 12 KB 的稀疏文件，拷完变成实打实 1 MB。逻辑内容一样，物理占用暴涨 80 倍。

正确做法

用 SEEK_DATA / SEEK_HOLE 问文件系统「这段是数据还是洞」，只把数据段搬过去；洞段在目标文件里用 lseek 跳过去（不写）。目标文件的洞是「跳出来的」，不是「写零写出来的」。

源文件:  [数据 4K][    洞 500K    ][数据 4K][      洞 1.5M      ][数据 5B]
            ↓ 读+写    ↓ lseek 跳过    ↓ 读+写    ↓ lseek 跳过     ↓ 读+写
目标文件:[数据 4K][    洞 500K    ][数据 4K][      洞 1.5M      ][数据 5B]
                                            ↑ 最后由 ftruncate 补齐逻辑长度

完整源码 code/ex4_2_cpholes.c：

/* ex4_2_cpholes.c — TLPI 练习 4-2：像 cp 一样拷贝，但保留源文件的「空洞」
 *
 * 【题干（原书 Exercise 4-2，逐字）】
 *   Write a program like cp that, when used to copy a regular file that
 *   contains holes (sequences of null bytes), also creates correspdonding
 *   holes in the target file.
 *
 * 【朴素做法错在哪】
 *   普通 copy 用 `while (read(...) > 0) write(...)`，读到空洞区会拿到一堆
 *   真实的 0 字节，然后老老实实写进目标文件 —— 空洞被「灌实」了，
 *   目标文件物理占用暴涨。源文件 4 KB、目标文件 1 MB 的荒唐结果从此而来。
 *
 * 【正确做法】
 *   用 lseek(fd, off, SEEK_DATA) / SEEK_HOLE 问文件系统「哪里有数据、
 *   哪里有洞」，把有数据的段读出来写过去，洞则在目标文件里用 lseek
 *   跳过去（不写）。目标文件的洞是「跳出来」的，不是「写零写出来」的。
 *
 * 【注意】SEEK_HOLE/SEEK_DATA 需要文件系统支持（ext4/xfs/btrfs 都支持，
 *   某些陈旧 FS 或 overlayfs 可能不支持，会返回 EINVAL）。
 *
 * 编译: gcc -O0 -Wall -o ex4_2_cpholes ex4_2_cpholes.c
 * 用法: ./ex4_2_cpholes src dst
 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/stat.h>

#define BUF_SIZE 4096

static ssize_t writeAll(int fd, const char *buf, size_t len)
{
    size_t written = 0;
    while (written < len) {
        ssize_t n = write(fd, buf + written, len - written);
        if (n < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        written += (size_t) n;
    }
    return (ssize_t) written;
}

static void report(const char *tag, const char *path)
{
    struct stat st;
    if (stat(path, &st) < 0) return;
    printf("  %-14s st_size = %8lld B   st_blocks*512 = %8lld B   块数 = %lld\n",
           tag, (long long) st.st_size, (long long) st.st_blocks * 512,
           (long long) st.st_blocks);
}

int main(int argc, char *argv[])
{
    const char *src, *dst;

    if (argc == 3) {
        src = argv[1];
        dst = argv[2];
    } else if (argc == 1) {
        /* 无参数模式：自己造一个带洞的源文件再拷它 —— 便于在无预置数据的
           环境（如 Compiler Explorer 沙箱）里自测。 */
        src = "/tmp/c4_holes_src.bin";
        dst = "/tmp/c4_holes_dst.bin";
        printf("== 0. 先造一个带洞的源文件 ==\n");
        int f = open(src, O_RDWR | O_CREAT | O_TRUNC, 0644);
        if (f < 0) { perror("open src"); return 1; }
        write(f, "HEAD-", 5);                        /* 数据段 1 */
        lseek(f, 512 * 1024, SEEK_SET);              /* 洞 1：跳 500 KB */
        write(f, "MIDDLE", 6);                       /* 数据段 2 */
        lseek(f, 2 * 1024 * 1024, SEEK_SET);         /* 洞 2：再跳 1.5 MB */
        write(f, "TAIL!", 5);                        /* 数据段 3 */
        /* 洞 3（**尾部洞**）：只把长度撑到 3 MiB，不写任何数据。
           这一段专门用来把「尾部是洞」这个场景造出来 —— 它同时逼出
           拷贝循环里的 ENXIO 分支和收尾的 ftruncate()。 */
        ftruncate(f, 3 * 1024 * 1024);
        close(f);
        report("造好的源文件", src);
        printf("\n== 开始拷贝 ==\n");
    } else {
        fprintf(stderr, "Usage: %s [src dst]\n", argv[0]);
        return 1;
    }

    int in = open(src, O_RDONLY);
    if (in < 0) { fprintf(stderr, "open %s: %s\n", src, strerror(errno)); return 1; }

    int out = open(dst, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (out < 0) { fprintf(stderr, "open %s: %s\n", dst, strerror(errno)); return 1; }

    struct stat st;
    fstat(in, &st);
    off_t size = st.st_size;
    printf("  源文件 %s: st_size = %lld B, st_blocks*512 = %lld B\n",
           src, (long long) st.st_size, (long long) st.st_blocks * 512);

    off_t pos = 0;
    int holes = 0, data_segs = 0;
    char buf[BUF_SIZE];

    while (pos < size) {
        /* 从 pos 找下一段数据；没有数据就是纯洞，直接收尾 */
        off_t data = lseek(in, pos, SEEK_DATA);
        if (data < 0) {
            if (errno == ENXIO) {            /* 后面全是洞 */
                printf("  从偏移 %lld 起到文件末尾：全是洞，目标文件直接 lseek 跳过\n",
                       (long long) pos);
                holes++;
                break;
            }
            fprintf(stderr, "SEEK_DATA(%lld): %s\n", (long long) pos, strerror(errno));
            return 1;
        }

        if (data > pos) {                    /* [pos, data) 是一段洞 */
            printf("  洞   : 偏移 %8lld .. %8lld  （%lld 字节）\n",
                   (long long) pos, (long long) data, (long long) (data - pos));
            holes++;
            if (lseek(out, data, SEEK_SET) < 0) {   /* 目标文件也跳过这段 */
                fprintf(stderr, "lseek out: %s\n", strerror(errno));
                return 1;
            }
        }

        /* 从 data 找下一个洞 → [data, hole) 是有数据的段 */
        off_t hole = lseek(in, data, SEEK_HOLE);
        if (hole < 0) hole = size;           /* 文件系统不报洞就一路拷到底 */
        printf("  数据 : 偏移 %8lld .. %8lld  （%lld 字节）\n",
               (long long) data, (long long) hole, (long long) (hole - data));
        data_segs++;

        if (lseek(in, data, SEEK_SET) < 0) return 1;
        if (lseek(out, data, SEEK_SET) < 0) return 1;
        off_t remaining = hole - data;
        while (remaining > 0) {
            size_t want = remaining < (off_t) sizeof buf ? (size_t) remaining
                                                         : sizeof buf;
            ssize_t n = read(in, buf, want);
            if (n < 0) { if (errno == EINTR) continue;
                         fprintf(stderr, "read: %s\n", strerror(errno)); return 1; }
            if (n == 0) break;
            if (writeAll(out, buf, (size_t) n) < 0) {
                fprintf(stderr, "write: %s\n", strerror(errno)); return 1;
            }
            remaining -= n;
        }
        pos = hole;
    }

    /* 关键一步：把目标文件「撑」到和源文件一样的逻辑大小。
       本轮源文件以一段尾部洞收尾（循环是靠 ENXIO 退出的），所以最后那个
       数据段之后什么都没有写 —— 不执行这一句，目标文件就比源文件短。
       ftruncate 扩出来的区域不分配磁盘块，所以洞依然保留。 */
    if (ftruncate(out, size) < 0)
        fprintf(stderr, "ftruncate: %s\n", strerror(errno));

    printf("  共 %d 段数据、%d 处洞\n", data_segs, holes);
    close(in);
    close(out);

    printf("\n== 结果对比 ==\n");
    report(src, src);
    report(dst, dst);
    printf("  → 两者 st_size 一样（逻辑内容相同），st_blocks 也接近（洞被保留）。\n");
    printf("    若用朴素 read/write 拷贝，目标 st_blocks 会被灌到跟 st_size 一个量级。\n");
    return 0;
}

三个关键点：

点 代码 为什么
找下一段数据 lseek(in, pos, SEEK_DATA) 返回 pos 之后第一个数据字节的偏移；没有数据则 errno == ENXIO
找下一个洞 lseek(in, data, SEEK_HOLE) 返回 data 之后第一个洞；失败就退化成「一路拷到底」（hole = size）
补齐尾部洞 ftruncate(out, size) 漏了这句，跳过尾部洞的文件会比源文件短

ftruncate 这一步最容易忘：循环结束时 out 的偏移停在最后一个数据段的末尾，后面那一大段尾部洞没有「写」过，所以文件逻辑长度不够。ftruncate 把它撑到 size，而这个扩展出来的区域天然就是洞（不分配块）。

解读：

观察 说明
源 st_size = 3145728（3 MiB），st_blocks*512 = 12288（12 KiB） 逻辑 3 MiB、物理 12 KiB，差了 256 倍——这就是稀疏文件
扫出 3 段数据 + 3 处洞 交错分布。最后那段洞是尾部洞：循环是靠 SEEK_DATA 返回 ENXIO 退出的，不是靠 pos < size 走完
第三段报 4096 字节，可源文件里只写了 5 字节 段边界按文件系统块报，不是按写入字节数报（这 4096 字节里有 4091 个「块内补零」）
洞的边界 4096 / 524288 / 528384 / 2097152 / 2101248 全是 4 KiB 的整数倍——粒度是块，不是字节
目标 st_size 完全相同 逻辑内容一致。这一轮靠的正是末尾那句 ftruncate(out, size)：最后一个数据段之后什么都没写，out 本来只有 2101248 字节，是 ftruncate 把它撑到 3145728
目标 st_blocks 也完全相同（12288 B / 24 块） 洞被真正保留了——连 ftruncate 撑出来的尾部洞也是洞（扩展区不分配块）。这就是本题的全部意义

一个副产品：段边界「块对齐，但被 i_size 截断」

注意第三段数据报的是 4096 字节，而源文件里明明只写了 5 字节。这不是 bug——把这个 demo 的前一版（源文件以数据段结尾，i_size = 2097157）的输出放在一起看，规律就出来了：

版本 最后一段数据写了几字节 i_size FS 报的段尾
前一版（无尾部洞） 5 2097157 2097157（正好是 i_size）
本版（有尾部洞） 5 3145728 2101248（2097152 + 4096，块对齐）

两版唯一的差别是 i_size：段边界按块算，但会被 i_size 截断。所以：

  • 数据段恰好顶到文件末尾时，报的是 i_size（看起来像「字节级精确」）
  • 数据段后面还有洞时，报的就是块边界（露出 4091 个零填充字节）

这和 4.7 里 lseek(4, SEEK_HOLE) → 4096 是同一个机制。结论：拿 SEEK_DATA/SEEK_HOLE 做逻辑时，一律按块对齐去理解，别假设字节级精度。

对比一下：把 SEEK_DATA/SEEK_HOLE 换成朴素循环，目标 st_blocks*512 会从 12288 涨到约 3145728（3 MiB）——逻辑大小一样，物理占用 256 倍。

一个可移植性坑

SEEK_DATA/SEEK_HOLE 不是所有文件系统都支持。ext4/xfs/btrfs 支持，某些文件系统会返回 EINVAL。而且前面 4.7 已经挖出过：内核通用兜底 default_llseek 对这两个 whence 的实现是「文件末尾是唯一的洞」——在不支持洞检测的 FS 上，这份代码会退化成「一路拷到底」，洞静默失效。所以程序里那句 if (hole < 0) hole = size; 既是容错，也藏着「优化可能悄悄不生效」的风险。

练习 4-3（自编）：制造一次真实的部分写

4.5 write() 里说「部分写是合法结果」。但用普通文件很难制造出来——你也看到了，原书 Listing 4-1 干脆写了 fatal("write() returned error or partial write occurred")，因为「往普通文件写一小段」这个受控场景下部分写确实不该出现。

想亲眼看一次，得找一个有容量上限的对象。管道正好：它有一个固定容量的环形缓冲区。

完整源码 code/ex4_3_partial_write.c：

/* ex4_3_partial_write.c — 亲手制造一次「部分写」，看 writeAll 怎么救回来
 *
 * 【为什么需要这个 demo】
 *   原书 Listing 4-1（copy.c）写的是：
 *        if (write(outputFd, buf, numRead) != numRead)
 *            fatal("write() returned error or partial write occurred");
 *   它敢这么写，是因为它只拷普通文件——普通文件上部分写几乎不出现。
 *   但只要换成管道/socket/磁盘快满，部分写就是**常态**，`!=` 直接报错
 *   就等于把「可恢复的慢」当成「不可恢复的错」。
 *
 *   这个 demo 用 pipe + 缩小管道缓冲 + 非阻塞，强制内核只写一部分，
 *   让「部分写」从书本概念变成屏幕上看得见的数字。
 *
 * 编译: gcc -O0 -Wall -o ex4_3_partial_write ex4_3_partial_write.c
 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>

/* 通用写法：循环直到写完（处理部分写 + EINTR） */
static ssize_t writeAll(int fd, const char *buf, size_t len)
{
    size_t written = 0;
    while (written < len) {
        ssize_t n = write(fd, buf + written, len - written);
        if (n < 0) {
            if (errno == EINTR)    continue;   /* 被打断：重试 */
            if (errno == EAGAIN)   break;      /* 非阻塞且缓冲满：先收工，稍后再来 */
            return -1;
        }
        written += (size_t) n;
    }
    return (ssize_t) written;
}

int main(void)
{
    char buf[8192];
    memset(buf, 'Z', sizeof buf);

    printf("== 1. 造一个「容量很小」的管道 ==\n");
    int p[2];
    if (pipe(p) < 0) { perror("pipe"); return 1; }

    int defsz = fcntl(p[1], F_GETPIPE_SZ);
    printf("  默认管道容量 F_GETPIPE_SZ = %d 字节\n", defsz);

    /* 调小到一页，便于观察「写不下」 */
    int want = 4096;
    if (fcntl(p[1], F_SETPIPE_SZ, want) < 0)
        printf("  F_SETPIPE_SZ(%d) 失败: %s（继续用默认容量）\n", want, strerror(errno));
    int nowsz = fcntl(p[1], F_GETPIPE_SZ);
    printf("  现在容量 F_GETPIPE_SZ = %d 字节\n", nowsz);

    printf("\n== 2. 非阻塞写「远超容量」的数据 → 必然部分写 ==\n");
    int fl = fcntl(p[1], F_GETFL);
    fcntl(p[1], F_SETFL, fl | O_NONBLOCK);       /* 不阻塞，写不下就立刻返回 */

    size_t want_write = sizeof buf;              /* 8192 字节 */
    errno = 0;
    ssize_t n = write(p[1], buf, want_write);    /* 先来一次「裸 write」 */
    printf("  裸 write(p[1], buf, %zu) -> %zd 字节", want_write, n);
    if (n < (ssize_t) want_write)
        printf("   ← 部分写！请求 %zu，只写了 %zd\n", want_write, n);
    else
        printf("\n");

    printf("\n== 3. 同一件事：writeAll 循环版，把剩余的都补上 ==\n");
    /* 先把管道清空，重新来过。
       注意：读端也要设非阻塞，否则「读空管道」会一直阻塞下去
       （这就是本 demo 第一版在 CE 上跑满 20 秒被 kill 的原因）。 */
    fcntl(p[0], F_SETFL, fcntl(p[0], F_GETFL) | O_NONBLOCK);
    { char drain[8192]; while (read(p[0], drain, sizeof drain) > 0) ; }

    size_t total = 0;
    for (int spins = 0; spins < 100 && total < want_write; spins++) {
        ssize_t w = writeAll(p[1], buf + total, want_write - total);
        if (w < 0) { perror("writeAll"); break; }
        total += (size_t) w;
        printf("  writeAll 一轮写出 %zd 字节，累计 %zu / %zu\n", w, total, want_write);
        if (total < want_write) {
            char drain[8192];                      /* 缓冲满了：真实程序此时该等「可写事件」 */
            ssize_t got = read(p[0], drain, sizeof drain);
            printf("    管道满，读端消费 %zd 字节后继续\n", got);
            if (got <= 0) break;                   /* 真读不到就收手，别空转 */
        }
    }
    printf("  writeAll 最终写出 %zu 字节（请求 %zu）\n", total, want_write);

    printf("\n== 4. 结论 ==\n");
    printf("  同一份数据、同一次请求，内核可以只写一部分就返回。\n");
    printf("  所以：write 的返回值必须用，且要用循环；`!= count 就报错` 只适用于\n");
    printf("  「只写普通文件」这种受控场景（原书 Listing 4-1 正是这个场景）。\n");
    close(p[0]);
    close(p[1]);
    return 0;
}

思路： 1. fcntl(p[1], F_SETPIPE_SZ, 4096) 把管道容量压到 4096 字节 2. 读端也设 O_NONBLOCK（否则写满后 drain 会死锁） 3. 非阻塞 write(p[1], buf, 8192) → 内核装不下 8192，只写 4096 就返回 4. 再用 writeAll 循环版：写一轮、读端消费一轮、再写一轮，最终写满 8192

观察 说明

这也解释了为什么 4.5 的 demo 里 write(4096) 一次就返回 4096：目标是普通文件，没有容量天花板。对象决定行为——这就是通用 I/O 模型的另一面：接口统一，但底下的容量特性千差万别。

补充练习（自编，巩固机制）

原书只有上面两道，下面两道不要写代码，但值得想清楚：

补充 1：short write 的至少 3 种成因

  1. 管道/FIFO 缓冲区只剩一部分空间：内核能装多少装多少（本页练习 4-3 实测）。
  2. 被信号中断（EINTR）：部分数据已写入后被打断。正确处理是重试而不是报错。
  3. 磁盘/配额空间不足（ENOSPC / EDQUOT）：只写入剩余空间能容纳的部分。
  4. socket 发送缓冲区部分填满：TCP 只拷了能放下的字节。

对应内核机制：vfs_write 不做「保证写满」的承诺（fs/read_write.c:564），实际写入量由 f_op->write / f_op->write_iter 决定。vfs_read 同理（:450）。

补充 2：O_APPEND 的原子性

有 O_APPEND：不交错。内核在 vfs_write 内部把「定位到末尾 + 写」做成一个不可分割的动作——注意它是内核代码里的原子性，不是用户态两次 syscall 的巧合。

无 O_APPEND：会交错。lseek(SEEK_END) + write() 是两步，进程 A 的两步之间可能插入进程 B，两者都从同一个「旧末尾」开始写，导致互相覆盖。

这是经典的 TOCTOU 竞争窗口。用户态代码无法复刻 O_APPEND 的同等原子性——这是本章唯一一个「必须有内核配合才能做对」的机制。

代码自测（Q&A）

Q1：tee 为什么必须对 stdout 也用循环写？ A：因为 stdout 可能是管道（| grep、| tee）。管道有容量上限，写超过剩余空间就会部分写——和写文件一样。只对文件循环、对 stdout 单次 write()，在本地终端下测不出问题（tty 慢且通常能收下），一旦被管道接管就会丢数据。这正是练习 4-3 实测的那个现象。

Q2：tee -a 和默认行为在内核里差什么？ A：只差一个标志位：默认 O_TRUNC（打开时把文件截断为 0），-a 用 O_APPEND（每次写前原子地定位到末尾）。O_TRUNC 发生在 open 时，O_APPEND 发生在每次 write 时——所以 -a 在多进程并发下也是安全的，O_TRUNC 语义上就是「清空重来」。

Q3：为什么朴素 read/write 拷贝会把空洞灌实？ A：因为内核对空洞区的读返回真实的 0 字节（4.7 实测：8 字节全是 0），而 read 不告诉你「这段原本是洞」。用户态只看到「一堆 0」，就会把它们写进目标文件，目标文件于是真的分配块、真的存了 0。要区分「洞」和「真数据里的 0」，只能反过来问文件系统——这就是 SEEK_DATA/SEEK_HOLE 存在的理由。

Q4：练习 4-2 里 ftruncate(out, size) 那句能不能省？ A：不能省。循环只写到最后一个数据段的末尾。本 demo 的源文件是以尾部洞收尾的（循环靠 SEEK_DATA 返回 ENXIO 退出），最后一个数据段只到 2101248，而 i_size 是 3145728——不 ftruncate，目标文件就比源文件短 1 MB。实测两份 st_size 完全相同，这一句正是原因。 有意思的是，这个 demo 的前一版源文件以数据段结尾（i_size = 2097157，最后一段写到 2097157），那时 ftruncate 恰好是空操作——看不出来它有没有用。这正是它危险的地方：一行看起来可有可无的代码，只在特定输入下才暴露必要性。 ftruncate 扩展出来的区域不分配磁盘块（实测尾部洞撑到 3 MiB 后 st_blocks 仍是 24 块），所以补长度的同时洞依然保留。

Q5：SEEK_DATA/SEEK_HOLE 在所有文件系统上都能用吗？ A：不能。内核通用兜底 default_llseek（fs/read_write.c:230-278）对这两个 whence 的实现是「文件末尾是唯一的洞」——在不支持真实洞检测的 FS 上，SEEK_DATA 直接返回 offset（当成全是数据）、SEEK_HOLE 返回 i_size。所以这份代码在不支持的 FS 上会静默地退化成朴素拷贝：结果正确，优化失效。程序里 if (hole < 0) hole = size; 是容错，但要意识到它也有「悄悄不优化」的一面。

Q6：练习 4-3 里为什么读端也要设 O_NONBLOCK？ A：因为要边写边读：管道写满 → 必须让读端消费 → 才能继续写。如果读端是阻塞的，主循环里那一步 drain 会在「管道里暂时没数据」时永久阻塞，程序卡死。实测：最初版本就是阻塞读的 drain 循环，在 CE 里跑满 20 秒被 kill（exit code = 143）；改成两端都非阻塞、用有界循环配 EAGAIN 才修好。

Q7：为什么 write 部分写的时候 errno 还是干净的？ A：因为部分写不是错误。write 返回一个小于 count 的正数，语义是「我只写了这么多」。errno 只在返回 -1 时才有意义。所以正确写法是：

ssize_t n = write(fd, buf, len);
if (n < 0) {
    if (errno == EINTR) continue;   /* 被打断，重试 */
    /* 真错误 */
} else {
    /* n 可能是 1..len 之间的任何值，扣掉 n 继续 */
}

把 n < len 当成错误（原书 Listing 4-1 的 fatal(...)）只在「只写普通文件」这种受控场景成立。
