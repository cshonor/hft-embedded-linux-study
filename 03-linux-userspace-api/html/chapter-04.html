章节定位

UNIX「一切皆文件」的操作根基：同一套 4 个系统调用 操作普通文件、终端、管道、socket、设备文件。

open() → read() / write() → close()

易错清单

代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

/* Ch4 通用 I/O 模型 — open/read/write/close 四件套。
 * 所有文件类型（普通文件/设备/proc）统一用这套接口。
 * 编译: gcc -o ch4_demo ch4_demo.c */

int main(void) {
    int fd = open("/tmp/ch4_test.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }

    const char *msg = "Hello, Universal I/O!\n";
    write(fd, msg, strlen(msg));
    close(fd);

    /* 重新打开读取 */
    fd = open("/tmp/ch4_test.txt", O_RDONLY);
    if (fd < 0) { perror("open read"); return 1; }

    char buf[256];
    ssize_t n = read(fd, buf, sizeof(buf) - 1);
    if (n > 0) {
        buf[n] = '\0';
        printf("read back: %s", buf);
    }
    close(fd);
    return 0;
}

4.1

Overview 概览

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/open.c、fs/read_write.c、include/linux/fs.h、include/linux/fdtable.h） - 上一节：本章首页 - 下一节：4.2 通用 I/O 模型

本节讲什么

这是「文件 I/O」的开篇，回答三个问题：

  1. Linux 操作一切资源（普通文件、设备、管道、socket）的统一入口是什么？
  2. 文件描述符（fd）到底是什么？它在内核里长什么样？
  3. 一套「万能 I/O 模型」由哪几个系统调用拼成，各自干什么？

原书这里只做概念铺垫；本节补上内核侧的 struct file / struct fdtable 坐标，把「fd 只是一个整数」这个抽象落到实处，为后面 4.3–4.8 逐个系统调用打底。

1. 万物皆文件：统一的 I/O 入口

Linux 用同一套系统调用操作所有 I/O 资源。无论目标是磁盘上的普通文件、/dev 下的设备文件、管道、套接字，还是 /proc 里的伪文件，都走同一条路：先 open() 拿到 fd，再用 read()/write() 读写，最后 close()。

操作 系统调用 原型 内核入口（v6.6）
打开 open() int open(const char *pathname, int flags, ...); SYSCALL_DEFINE3(open) @ fs/open.c:1441
读 read() ssize_t read(int fd, void *buf, size_t count); SYSCALL_DEFINE3(read) @ fs/read_write.c:621
写 write() ssize_t write(int fd, const void *buf, size_t count); SYSCALL_DEFINE3(write) @ fs/read_write.c:646
关闭 close() int close(int fd); SYSCALL_DEFINE1(close) @ fs/open.c:1557
定位 lseek() off_t lseek(int fd, off_t offset, int whence); SYSCALL_DEFINE3(lseek) @ fs/read_write.c:311

ioctl()（SYSCALL_DEFINE3(ioctl)）则是「通用模型之外」的兜底，处理设备专属控制（见 4.8）。

2. 文件描述符（fd）：一个整数背后的三层结构

fd 是进程内用来引用「已打开文件」的非负整数。用户态看到的就是个 int，但内核里它只是一张表的下标：

进程 task_struct
   └── files_struct  (struct files_struct @ include/linux/fdtable.h:49)
         ├── fdt  → struct fdtable @ :27
         │          ├── max_fds          容量上限
         │          └── fd[]   struct file * 数组  ← fd 就是这个数组的下标
         └── fdtab（内嵌的小 fdtable，前 64 个 fd 的快速路径）

三层关系（这是 Ch5 要深挖的核心，这里先立骨架）：

层 数据结构 位置 关键字段
fd 表 struct fdtable include/linux/fdtable.h:27 fd[]（struct file * 数组）、max_fds
打开文件描述 struct file include/linux/fs.h:992 f_mode、f_count、f_pos（:1007）、f_op
inode 对象 struct inode include/linux/fs.h 文件真实属性、数据块位置

几个必须记住的事实：

事实 说明
默认三个 fd 0=STDIN_FILENO、1=STDOUT_FILENO、2=STDERR_FILENO（<unistd.h>）
最小可用分配 新 open() 返回当前最小的未用 fd；close(fd) 后该号可被复用
进程私有 两进程里相同数字的 fd，通常指向不同的打开实例
偏移在 struct file 读写位置 f_pos 存在打开文件描述里，不在 fd 表里（所以 dup/fork 共享偏移，见 Ch5）

3. 万能 I/O 模型全景

用户态
  open(path, flags, mode) ──→ 返回 fd（最小可用）
        │
        ▼
  read(fd, buf, n)  /  write(fd, buf, n)
        │                 │
        ▼                 ▼
     vfs_read()        vfs_write()     ← 校验 + 分派到 f_op->read/write
        │                 │
        └────────┬────────┘
                 ▼
        close(fd)  ──→ 释放 fd 槽位 + 引用计数减一
   （lseek 改 f_pos；ioctl 走设备专属命令，视对象而定）

这条链路是「一切皆文件」的实现基础：read/write 不关心目标是 ext4 文件还是 tty 设备，差异被 VFS 层的 f_op 函数指针吸收（见 4.2）。

4. HFT / 嵌入式关联

现象 本节机制的兑现
fd 泄漏耗尽句柄 每个 open 占一个 fd 槽位，不 close 会一直涨到 ulimit -n 上限 → 无法再开新文件/socket
热路径少 syscall 每次 read/write 都陷入内核（inc_syscr 计数），高频率行情读写要批量化或走 mmap
设备统一访问 嵌入式里 /dev/mem、自定义字符设备都走同一套 open/read/write，专属控制交给 ioctl
偏移是共享状态 f_pos 在 struct file 里，fork/dup 后父子/多 fd 共享同一偏移，并发写要 O_APPEND 或文件锁（Ch5）

5. 代码示例

#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

/* fd 本质：进程内打开文件表的下标；新 fd 从最小可用数字分配 */
int main(void) {
    printf("STDIN=%d STDOUT=%d STDERR=%d\n",
           STDIN_FILENO, STDOUT_FILENO, STDERR_FILENO);   /* 0 1 2 */

    int a = open("/tmp/a.txt", O_CREAT | O_RDWR, 0644);   /* 期望 3 */
    int b = open("/tmp/b.txt", O_CREAT | O_RDWR, 0644);   /* 期望 4 */
    printf("a=%d b=%d\n", a, b);

    close(a);                                             /* 3 被回收 */
    int c = open("/tmp/c.txt", O_CREAT | O_RDWR, 0644);   /* 复用 3 */
    printf("c=%d (复用最小可用)\n", c);

    close(b); close(c);
    return 0;
}

代码自测（Q&A）

Q1：fd 为什么「进程私有」？两个进程里 fd=3 一定指向不同文件吗？ A：fd 只是本进程 files_struct->fdtab.fd[] 数组的下标。每个进程有自己的 files_struct，下标 3 对应的是各自数组里存的 struct file *，完全可以指向不同文件。唯一的例外是 fork 后子进程继承了父进程的 fd 表（copy_files），此时父子 fd=3 指向同一个 struct file（共享偏移）。

Q2：open() 返回的 fd 为什么总是「最小可用」？ A：内核在 get_unused_fd_flags() 里用位图（open_fds）找第一个为 0 的位。刚关掉的 fd 号立即回收到位图里，所以下次 open 会优先复用。这也是「关闭 0 号 fd 再打开文件，新 fd 变成 0」这类经典技巧的根据。

Q3：读写偏移 f_pos 为什么放在 struct file 而不放在 fd 表里？ A：因为 dup/dup2/fork 会复制 fd 表，但希望共享同一个读写位置——两个 fd 指向同一打开文件时，一个读了 100 字节，另一个看到的偏移也前进 100。若偏移存在 fd 表里就做不到共享。代价是并发读写同一文件时偏移是竞争点，需 O_APPEND 或锁（Ch5）。

Q4：本章 5 个系统调用里，哪两个「不是所有文件类型都支持」？ A：lseek 和 ioctl 视对象而定。管道/socket/终端不设 FMODE_LSEEK，lseek 返回 -ESPIPE（见 4.7）；ioctl 只有实现了对应命令的设备才有意义，普通文件上多数 ioctl 返回 -ENOTTY（见 4.8）。open/read/write/close 则是真正的「万能四件套」。

Q5：为什么说「每个 fd 占内核资源」，进程退出时会自动回收吗？ A：fd 表项、struct file（引用计数）都是内核对象。进程退出时 exit_files() 会逐个 fput，把引用计数减到 0 并释放 struct file，所以正常退出不会永久泄漏 fd。但长驻进程里不 close 的 fd 会一直占着，直到进程结束——这正是服务进程 fd 泄漏的根源。

4.2

通用 I/O 模型（核心思想）

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（include/linux/fs.h struct file_operations、fs/read_write.c vfs_read/vfs_write） - 上一节：4.1 Overview 概览 - 下一节：4.3 open()

本节讲什么

这是本章的「思想核心」，回答三个问题：

  1. 为什么拷贝磁盘文件、写终端、读 /proc 能用同一段代码？
  2. 文件类型之间的差异，内核在哪里把它们「吸收」掉了？
  3. 当这套万能模型不够用时，靠什么兜底？

本节把「一切皆文件」从口号落到 VFS 的 f_op 函数指针表上，讲清「通用」与「特化」的边界。

1. 同一套 API，通吃所有文件类型

/* 下面是同一套 open/read/write/close，目标是三种截然不同的对象 */
int fd  = open("/tmp/demo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644); /* 普通文件 */
int dev = open("/dev/null",      O_WRONLY);                        /* 设备文件 */
int proc = open("/proc/version", O_RDONLY);                        /* 内核伪文件 */

三段代码除了路径和 flags，没有任何区别。应用层完全不关心目标是 ext4 文件、块设备还是 proc 伪文件系统——这是「通用 I/O 模型」的全部意义。

2. 差异被 VFS 的 f_op 函数指针吸收

差异并没有消失，而是被下沉到了内核的虚拟文件系统层（VFS）：

用户态   read(fd, buf, n)
              │  （一条 syscall，对所有文件类型都一样）
              ▼
内核     vfs_read(file, buf, n, pos)          fs/read_write.c:450
              │  只做通用校验（f_mode、access_ok、rw_verify_area）
              ▼
        file->f_op->read / read_iter          ← 差异在这里！
              │
     ┌────────┼────────────┬──────────────┐
     ▼        ▼            ▼              ▼
 ext4 读    proc 读      tty 读        /dev/null 读
（走页缓存）（现场生成文本）（行规程）   （直接返回 0）

struct file 里的 f_op 是指向 struct file_operations 的指针，这个结构体是一张函数指针表：read、write、llseek、unlocked_ioctl、mmap、open、release…… 每个文件系统/驱动在 open 时把属于自己的那张表挂到 file->f_op 上。此后所有 read/write 都通过同一个指针分派，VFS 上层代码一行都不用改。

这本质是内核里的多态——f_op 就是 vtable，vfs_read 调 file->f_op->read 就是虚函数调用。对照 LKD 见 05/Ch13.2 VFS 的面向对象设计。

3. 通用模型之外：ioctl() 是逃生舱

「万能模型」只覆盖 open/read/write/close（+ lseek）这几种「流式字节」语义。一旦要做的不是「读字节/写字节」——比如设置终端窗口大小、查询磁盘扇区数、配置网卡混杂模式——这套模型就没有对应动词了。

于是内核留了一个「万能兜底」：

int ioctl(int fd, int request, ...);   /* 任意设备专属命令 */

request 是一个编码了「方向 + 数据大小 + 编号」的整数，内核据此把后面的可变参数解释成设备要的结构体。设备驱动在 file_operations->unlocked_ioctl 里用 switch(request) 分派。详见 4.8。

机制 覆盖范围 例子
read/write 流式字节 I/O 读文件内容、写终端
lseek 随机定位（可 seek 对象） 跳到文件第 N 字节
ioctl 一切「字节流之外」的控制 TIOCGWINSZ 查窗口大小

4. HFT / 嵌入式关联

现象 本节机制的兑现
设备驱动即文件 嵌入式里点灯、读传感器：写个字符设备驱动，挂到 f_op->read/write/unlocked_ioctl，用户态用 open/read/write/ioctl 直接操作
换存储介质零改代码 应用只面对 fd，底层从 eMMC 换到 NVMe、从 ext4 换到 XFS，用户态代码不变——差异全在 f_op 后面
性能边界 「通用」是有代价的：每层函数指针分派 + 通用校验。HFT 热路径追求极致时会绕过通用模型（mmap、sendfile、io_uring），但通用模型是理解这些优化的起点
ioctl 是唯一出路 网卡 offload、硬件时间戳、DMA 配置这类「非字节流」操作，只能走 ioctl，没有 read/write 等价物

5. 代码示例

#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

/* 同一套 open/read/write/close 适用于所有文件类型 */
int main(void) {
    /* 1) 普通文件 */
    int fd = open("/tmp/demo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644);
    write(fd, "hello\n", 6);
    close(fd);

    /* 2) 设备文件 /dev/null — 数据被丢弃但调用成功 */
    int dev = open("/dev/null", O_WRONLY);
    write(dev, "anything", 8);
    close(dev);

    /* 3) 内核伪文件 /proc/version — 内容由内核现场生成 */
    int proc = open("/proc/version", O_RDONLY);
    char buf[256];
    ssize_t n = read(proc, buf, sizeof(buf) - 1);
    if (n > 0) { buf[n] = '\0'; printf("%s", buf); }
    close(proc);
    return 0;
}

三段代码路径不同，但 open/read/write/close 的用法完全一样——这就是「通用 I/O 模型」。

代码自测（Q&A）

Q1：「一切皆文件」到底是真的「都是文件」，还是只是一种抽象？ A：是抽象，不是字面事实。/dev/null 不是磁盘上的文件，/proc/version 的内容也不是存在哪里的字节——它们只是在 VFS 层表现得像文件：都有 struct file、都填了 f_op 函数指针。所谓「皆文件」=「皆可用 open/read/write/close 这套接口访问」。

Q2：vfs_read() 里哪一行体现了「差异被吸收」？ A：ret = file->f_op->read(file, buf, count, pos)（fs/read_write.c:467 附近）。vfs_read 前面的校验（FMODE_READ→-EBADF、access_ok→-EFAULT）对所有文件类型都一样，真正干活的是通过 f_op->read 分派到具体实现——ext4 有 ext4 的实现，proc 有 proc 的实现，VFS 层不关心。

Q3：为什么 read/write 管不了「设置终端窗口大小」这种事？ A：因为窗口大小不是「一段字节流」。read/write 的语义是「从当前偏移搬运 N 字节」，而窗口行列数是一个「控制查询」，没有字节流可以表达。这类「字节流之外」的操作必须走 ioctl(fd, TIOCGWINSZ, &ws)，由驱动在 unlocked_ioctl 里识别命令字 TIOCGWINSZ。

Q4：如果我想让一个自定义硬件设备能被 read/write 访问，内核侧最少要做什么？ A：实现一个字符设备驱动，填一个 struct file_operations（至少 open、read、write、release），用 register_chrdev 注册，然后在 /dev 下建设备节点。之后用户态就能 open("/dev/mydev") + read/write，走的正是本节讲的通用模型。

Q5：「通用模型」在性能上有什么代价？HFT 为什么有时要绕过它？ A：代价来自三处：① 每次 read/write 都要 syscall 陷入内核；② vfs_read/vfs_write 的通用校验（f_mode、access_ok、rw_verify_area）有固定开销；③ f_op 函数指针间接跳转。HFT 极致低延迟场景会用 mmap 直接把文件映射进地址空间、用 sendfile 做内核内零拷贝、用 io_uring 批量提交 I/O，绕开「一次一 syscall + 通用校验」的路径。

4.3

`open()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/open.c:1406-1478） - 上一节：4.2 通用 I/O 模型 - 下一节：4.4 read()

本节讲什么

open() 把「路径名」变成「fd」，是万能 I/O 模型的第一步。本节回答三个问题：

  1. open() 在内核里走的是怎样一条链路（从路径字符串到 fd 槽位）？
  2. flags 和 mode 两个参数各自控制什么？umask 怎么参与？
  3. open()（系统调用）和 fopen()（C 库函数）差在哪？

1. 原型与内核链路

#include <fcntl.h>
int open(const char *pathname, int flags, /* mode_t mode */);
/* 成功返回 fd；失败返回 -1 并设 errno */

open 是变参函数——只有 flags 含 O_CREAT（或 O_TMPFILE）时才需要第三个参数 mode。内核侧完整链路（v6.6）：

用户态 open(path, flags, mode)
      │
      ▼
SYSCALL_DEFINE3(open)                    fs/open.c:1441
      │  force_o_largefile() → 自动补 O_LARGEFILE（32 位平台）
      ▼
do_sys_open(AT_FDCWD, ...)               fs/open.c:1434
      ▼
do_sys_openat2()                         fs/open.c:1406
      ├─→ build_open_flags()  解析 flags/mode 成 struct open_flags
      ├─→ getname()           从用户态拷贝路径字符串（copy_from_user）
      ├─→ get_unused_fd_flags()  ← 分配「最小可用」fd
      ├─→ do_filp_open()      真正打开：路径解析 + 调用 f_op->open
      │                        （这里才做权限检查、创建文件、挂 inode）
      └─→ fd_install(fd, f)   把 struct file 装进 fd 表的 fd 槽位

关键：fd 的分配（get_unused_fd_flags）发生在真正打开之前——先占坑，do_filp_open 失败再 put_unused_fd 还回去。open 默认相对 AT_FDCWD（当前工作目录）；openat/openat2 可指定 dfd 做相对路径（用于防 TOCTOU，见 Ch18）。

2. flags：位掩码，访问模式三选一

标志 含义
O_RDONLY / O_WRONLY / O_RDWR 只读 / 只写 / 读写（三者必选其一）
O_CREAT 不存在则创建；此时必须给 mode
O_EXCL 与 O_CREAT 配合：文件已存在则失败（原子「排他创建」）
O_TRUNC 存在则截断为 0（需写权限）
O_APPEND 每次写前原子地把偏移设到末尾（详 Ch5）
O_NONBLOCK 非阻塞打开（对管道/FIFO/设备有意义）
O_CLOEXEC exec 时自动关闭，防 fd 泄漏给子程序
O_NOFOLLOW 不跟随符号链接
O_SYNC / O_DSYNC 写以同步方式完成（每次 write 落盘，Ch13）

3. mode 与 umask

mode 只在新文件被 O_CREAT 创建时生效，指定的是请求的权限；最终权限还要被进程的 umask 屏蔽：

最终权限 = mode & ~umask
例如 mode=0666, umask=022 → 0644 (rw-r--r--)
     mode=0666, umask=002 → 0664 (rw-rw-r--)

umask 是进程级属性（umask() 系统调用可改），默认 022。它只屏蔽（清除）权限位，不能「新增」mode 里没有的位。

4. open() vs fopen()：系统调用 vs C 库

int   open(const char *pathname, int flags, mode_t mode);  // POSIX 系统调用
FILE *fopen(const char *path, const char *mode);           // C 标准库封装
open / read / write fopen / fread / fwrite
返回值 int fd（内核整数句柄） FILE * 指针
层级 POSIX 系统调用（直接进内核） C 标准库（libc，内部调 open）
缓冲 无用户态缓冲 有用户态缓冲（FILE 内部 buffer）
关闭 close(fd) fclose() → 内部 close()
可移植 Unix/Linux 限定 C 标准，跨平台

fopen 的「r/w/a」模式到 open flags 的映射：

fopen 模式 open 对应 flags
"r" O_RDONLY
"w" O_WRONLY \| O_CREAT \| O_TRUNC
"a" O_WRONLY \| O_CREAT \| O_APPEND

5. HFT / 嵌入式关联

路线 要点
嵌入式 Linux 资源受限场景可直接 open 裸文件操作（免 libc 缓冲层）；/dev 设备走同一套 open；专属控制靠 ioctl
HFT 低延迟 fopen 多一层用户态拷贝；直接 open/write 少一层但每次 syscall 都陷内核。热路径常权衡：批量写 or mmap or io_uring
多进程日志 O_APPEND 保证多进程追加不交错（原子设偏移+写）；O_CLOEXEC 防 exec 后 fd 泄漏

6. 常见陷阱

  1. O_CREAT 忘传 mode — 漏传时 mode 取栈上残留值，权限不可预测：
fd = open("f.txt", O_WRONLY | O_CREAT);          /* 错！权限不确定 */
fd = open("f.txt", O_WRONLY | O_CREAT, 0644);    /* 对 */
  1. 返回值未检查 — open 失败返回 -1，直接用 -1 当 fd 会让后续 read/write 全部 EBADF：
int fd = open(path, O_RDONLY);
if (fd == -1) { perror("open"); exit(1); }
read(fd, buf, n);
  1. O_TRUNC 意外截断 — 想追加写却误加 O_TRUNC，清空旧数据：
fd = open("log.txt", O_WRONLY | O_TRUNC);   /* 清空了！ */
fd = open("log.txt", O_WRONLY | O_APPEND);  /* 追加，正确 */

7. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/ch4_open.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    write(fd, "test", 4);
    close(fd);

    fd = open("/tmp/ch4_open.txt", O_RDONLY);
    if (fd < 0) { perror("open read"); return 1; }
    char buf[8];
    ssize_t n = read(fd, buf, 4);
    buf[n] = '\0';
    printf("read: %s\n", buf);
    close(fd);
    return 0;
}

代码自测（Q&A）

Q1：open("f.txt", O_CREAT) 少了什么参数？为什么危险？ A：少了 mode。open 是变参函数，只有 flags 含 O_CREAT 时才读第三个参数；漏传时内核会读栈上的残留值当 mode，导致新文件权限随机。正确写法 open("f.txt", O_CREAT, 0644)（再受 umask 屏蔽）。

Q2：open 失败时返回 0 吗？ A：不。失败返回 -1 并设 errno。0 是合法 fd（stdin），只有 0 号槽位空闲时才可能返回 0——这本身不是错误。判断成功与否只能用 fd == -1。

Q3：O_EXCL | O_CREAT 组合有什么用途？ A：原子地「仅当文件不存在时创建」。两个进程同时用这个组合创建同名文件，内核保证只有一个成功、另一个得到 -EEXIST——这是「用文件当锁」或「原子生成临时文件」的经典手段，避免 open 后再 stat 的 TOCTOU 竞争窗口。

Q4：为什么 umask 只能「屏蔽」权限，不能「添加」权限？ A：内核里的计算是 mode & ~umask——umask 只把某些位清零。mode 里本就没有的位，umask 造不出来。所以想让新文件「其他人可写」（0666），必须 mode 里先有 022 之外还要 022，而 umask 不能帮你补。

Q5：fopen("a") 和 open(..., O_APPEND) 在「追加」语义上等价吗？ A：等价，且底层是同一个机制。fopen("a") 内部就是 open(path, O_WRONLY|O_CREAT|O_APPEND, ...)，O_APPEND 让内核在每次 write 前原子地把偏移设到文件末尾，多进程追加不会交错。区别只在 fopen 多了用户态缓冲，fclose 时才真正 flush + close。

4.4

`read()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/read_write.c:450-480 vfs_read、:602 ksys_read、:621 SYSCALL_DEFINE3(read)） - 上一节：4.3 open() - 下一节：4.5 write()

本节讲什么

read() 从 fd 读字节。本节回答三个问题：

  1. read() 在内核里经过哪些校验，最后才真正碰数据？
  2. 「短读（short read）」为什么是正常现象，必须怎么处理？
  3. EOF、EINTR、EFAULT、EBADF 这几个返回值/错误怎么区分？

1. 原型与内核链路

#include <unistd.h>
ssize_t read(int fd, void *buffer, size_t count);
/* >0 读到的字节数（可能 < count）；0 = EOF；-1 = 出错 */

用户态 read(fd, buf, count)
      ▼
SYSCALL_DEFINE3(read)          fs/read_write.c:621
      ▼
ksys_read()                    fs/read_write.c:602
      ├─→ fdget_pos(fd)       ← 由 fd 取 struct file（校验 fd 有效）
      ├─→ file_ppos()         ← 取偏移指针（不可 seek 对象返回 NULL）
      ├─→ vfs_read()          ← 通用校验 + 分派（见下）
      └─→ 成功则回写 f_pos，fdput_pos(f)

vfs_read() 的校验链（fs/read_write.c:450-468）是本节重点：

ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
{
    if (!(file->f_mode & FMODE_READ))        return -EBADF;   /* 没以读方式打开 */
    if (!(file->f_mode & FMODE_CAN_READ))    return -EINVAL;  /* 对象不支持读 */
    if (unlikely(!access_ok(buf, count)))    return -EFAULT;  /* 用户缓冲非法 */
    ret = rw_verify_area(READ, file, pos, count);             /* 锁/范围校验 */
    if (count > MAX_RW_COUNT)  count = MAX_RW_COUNT;          /* 截断超大请求 */

    if (file->f_op->read)         ret = file->f_op->read(file, buf, count, pos);
    else if (file->f_op->read_iter) ret = new_sync_read(file, buf, count, pos);
    else                          ret = -EINVAL;              /* 无读实现 */
    ...
}

注意校验顺序：先 EBADF（fd 没读权限）→ EINVAL（对象不可读）→ EFAULT（用户地址非法）。EBADF 和 EFAULT 是最常见的两个坑（见自测 Q1/Q2）。

2. 返回值语义

返回 含义 处理
> 0 读到的字节数，可能小于 count（短读） 循环继续读剩余
0 EOF（文件末尾） 结束读取
-1 / errno=EINTR 被信号中断（不是错误） 重试，或 SA_RESTART
-1 / 其他 errno 真错误（EBADF/EFAULT/EIO…） 报错处理

3. 短读（short read）：正常现象，必须循环

read 返回的字节数没有义务等于 count。短读在以下对象上尤其常见：

对象 短读原因
管道/FIFO 缓冲区里当前只有这么多数据
socket 收到一个 TCP 段就返回，不等填满
终端 通常读到换行就返回（行规程）
普通文件 接近 EOF 时最后一次不足 count

因此网络/管道编程必须写「循环读到 EOF 或读满」的封装。最常用的 readall：

ssize_t readall(int fd, void *buf, size_t n) {
    size_t total = 0;
    while (total < n) {
        ssize_t r = read(fd, (char*)buf + total, n - total);
        if (r < 0 && errno == EINTR) continue;   /* 信号中断，重试 */
        if (r < 0) return -1;                    /* 真错误 */
        if (r == 0) break;                       /* EOF */
        total += r;
    }
    return total;                                 /* 可能 < n（EOF 提前） */
}

4. HFT / 嵌入式关联

现象 本节机制的兑现
行情流短读 从 socket 读行情，一次 read 可能只回一个帧的碎片，必须按协议边界循环拼包
EFAULT 定位野指针 传入未初始化/已释放的 buf 会触发 access_ok → EFAULT，是用户态内存 bug 的常见暴露点
EINTR 被信号打断 交易进程收到信号（如定时器、SIGALRM）会打断阻塞读，循环重试或 SA_RESTART 是必备处理
少 syscall 每次 read 陷入内核；批量读大缓冲比多次小 read 更省（但一次超大请求会被 MAX_RW_COUNT 截断）

5. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

/* read(): 返回读取字节数, 0=EOF, -1=错误 */
int main(void) {
    int fd = open("/etc/hostname", O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }
    char buf[256];
    ssize_t n;
    while ((n = read(fd, buf, sizeof(buf))) > 0)
        write(STDOUT_FILENO, buf, n);       /* 循环读，直到 EOF */
    if (n < 0) perror("read");
    close(fd);
    return 0;
}

代码自测（Q&A）

Q1：read() 返回 -1 且 errno=EBADF 和 errno=EFAULT 分别是什么问题？ A：EBADF 是 fd 侧的问题——fd 无效（没打开/已关闭），或没以读方式打开（vfs_read 里 !(f_mode & FMODE_READ)）。EFAULT 是 buf 侧的问题——buf 指向的地址非法（野指针、已释放内存、count 越界），access_ok 检查失败。两者一个是句柄错、一个是内存错。

Q2：read 一定会读满请求的字节数吗？ A：不。read 可能返回少于 count 的字节（短读），尤其在管道、socket、终端上。只有「读满或遇 EOF」这个目标要靠循环保证，单次 read 不作任何承诺。

Q3：返回 0（EOF）和返回 -1（错误）怎么区分？ A：0 表示正常到达文件末尾，不是错误；-1 才表示出错（具体看 errno）。用 feof() 预判 EOF 是反模式（它只在读越过末尾后才为真），正确做法是检查 read 返回值本身。

Q4：read 被信号打断返回 EINTR，为什么「不是错误」？ A：信号处理函数返回后，系统调用可能被打断（无 SA_RESTART 时），此时数据没读、也没出错，只是「还没读完」。语义上应重试同一调用。readall 里的 if (r < 0 && errno == EINTR) continue; 就是标准处理。

Q5：为什么一次 read(fd, buf, 1<<30) 超大请求，内核不会真的读 1GB？ A：vfs_read 里 if (count > MAX_RW_COUNT) count = MAX_RW_COUNT; 会把请求截断到上限（通常约 2GB 减一页）。这既保护内核栈/内存，也避免单个 syscall 垄断太久。所以「一次读超大块」有天花板，HFT 场景反而更关注「单次读多大最划算」。

`write()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/read_write.c:564-594 vfs_write、:626 ksys_write、:646 SYSCALL_DEFINE3(write)） - 上一节：4.4 read() - 下一节：4.6 close()

本节讲什么

write() 把字节写进 fd。本节回答三个问题：

  1. write() 在内核里怎么校验、怎么落到页缓存？
  2. 「部分写（partial write）」为什么是正常现象，怎么处理？
  3. 为什么「write 成功 ≠ 数据已落盘」？SIGPIPE 又是什么？

1. 原型与内核链路

#include <unistd.h>

/* >0 实际写入字节（可能 < count）；-1 = 出错 */

      ▼

      ▼
ksys_write()                  fs/read_write.c:626

      ├─→ vfs_write()        ← 通用校验 + 分派（见下）

vfs_write() 校验链与 vfs_read 完全对称（fs/read_write.c:564-583）：

ssize_t vfs_write(struct file *file, const char __user *buf, size_t count, loff_t *pos)
{
    if (!(file->f_mode & FMODE_WRITE))       return -EBADF;
    if (!(file->f_mode & FMODE_CAN_WRITE))   return -EINVAL;
    if (unlikely(!access_ok(buf, count)))    return -EFAULT;

    file_start_write(file);

2. 部分写（partial write）：必须循环

和 read 的短读一样，write 可以只写一部分就返回：

部分写原因 场景
管道/FIFO 缓冲不足 PIPE_BUF 限制，只写满缓冲区就返回
磁盘空间不足 ENOSPC，只写入剩余空间能容纳的部分
socket 发送缓冲部分满 TCP 发送缓冲区只有这么多空闲
信号中断 EINTR，部分数据已写出

标准封装 writeall：

ssize_t writeall(int fd, const void *buf, size_t n) {
    size_t total = 0;
    while (total < n) {
        ssize_t w = write(fd, (char*)buf + total, n - total);
        if (w < 0 && errno == EINTR) continue;   /* 信号中断，重试 */
        if (w < 0) return -1;
        total += w;
    }
    return total;
}

3. 成功 ≠ 落盘：数据先入页缓存

write 返回成功，只表示数据拷进了内核页缓存（page cache），尚未写进物理磁盘：

write(fd, data, size)
   │  copy_from_user → 页缓存（脏页）
   │  返回成功！但数据还在内存里
   ▼
fsync(fd) / fdatasync(fd)   ← 强制把脏页刷到磁盘

断电、内核崩溃时，页缓存里尚未刷盘的脏页会丢失。要保证持久化必须显式 fsync/fdatasync（Ch13）。嵌入式/HFT 落盘场景尤其要分清「写进内核」和「写进磁盘」的边界。

4. SIGPIPE：写已关闭的管道会杀进程

向「读端已关闭」的管道/socket 写数据时，内核会向写进程发送 SIGPIPE 信号；该信号默认动作是终止进程：

write(pipe_fd, buf, n);   /* 对端已 close → 进程被 SIGPIPE 杀死 */
signal(SIGPIPE, SIG_IGN); /* 忽略后，write 返回 -1，errno=EPIPE */

服务器写 socket 时对端可能随时断开，因此必须先忽略 SIGPIPE，否则一个断连就能让整个服务崩溃。忽略后 write 返回 -1 + EPIPE，程序自己处理。

5. HFT / 嵌入式关联

现象 本节机制的兑现
行情日志落盘 write 成功不代表安全，崩溃可能丢最近几秒日志；关键数据要 fdatasync，但 fdatasync 会阻塞，需权衡
多进程追加 O_APPEND 让每次 write 原子地追加到末尾，避免部分写交错（Ch5）
服务器防崩 写 socket 前忽略 SIGPIPE，否则对端断连直接杀进程
少 syscall 批量 write（大缓冲）比多次小 write 省 syscall，但大缓冲也意味着延迟数据攒满才写

6. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

/* write(): 可能部分写入, 需循环保证写完 */
int main(void) {
    int fd = open("/tmp/ch4_write.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    const char *msg = "hello write\n";
    size_t total = strlen(msg), written = 0;
    while (written < total) {
        ssize_t n = write(fd, msg + written, total - written);
        if (n < 0) { perror("write"); break; }
        written += n;
    }
    printf("wrote %zu bytes\n", written);
    close(fd);
    return 0;
}

Q5：流式对象（socket/pipe）为什么没有「文件偏移」？ A：看 file_ppos()（fs/read_write.c:597）：file->f_mode & FMODE_STREAM ? NULL : &file->f_pos。socket/pipe 是流，数据读走即消失、没有「当前位置」概念，所以 f_pos 为 NULL，ksys_write 也就不回写偏移。这也是它们不支持 lseek（ESPIPE）的同一根源。

`close()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/open.c:1557-1589 SYSCALL_DEFINE1(close)） - 上一节：4.5 write() - 下一节：4.7 lseek()

本节讲什么

close() 释放 fd。本节回答三个问题：

  1. close() 在内核里到底做了什么？为什么「不可重启」？
  2. 引用计数（f_count）在其中起什么作用？
  3. 什么时候必须检查 close() 的返回值？

1. 原型与内核链路

#include <unistd.h>
int close(int fd);
/* 成功返回 0；失败返回 -1 并设 errno */

用户态 close(fd)
      ▼
SYSCALL_DEFINE1(close)            fs/open.c:1557
      ├─→ close_fd_get_file(fd)  ← 从 fd 表取出并清空该槽位
      │     （fd 无效 → 返回 -EBADF）
      ├─→ filp_flush(file, ...)  ← 刷内核缓冲、处理延迟错误
      └─→ __fput_sync(file)      ← 引用计数减一，归零则释放 struct file

关键源码（fs/open.c:1557-1577）：

SYSCALL_DEFINE1(close, unsigned int, fd)
{
    int retval;
    struct file *file;

    file = close_fd_get_file(fd);
    if (!file)
        return -EBADF;

    retval = filp_flush(file, current->files);
    __fput_sync(file);

    /* 不能重启 close：fd 表项已经清掉了 */
    if (unlikely(retval == -ERESTARTSYS || retval == -ERESTARTNOINTR ||
             retval == -ERESTARTNOHAND || retval == -ERESTART_RESTARTBLOCK))
        retval = -EINTR;

    return retval;
}

2. 为什么 close 不可重启

普通 read/write 被信号打断会返回 ERESTARTSYS，内核在返回用户态时自动重启该系统调用。但 close 不能这么做：

close_fd_get_file() 在第一步就把 fd 表项清空了。如果信号打断了 filp_flush 再重启，第二次进来时 fd 已经不存在，会得到 -EBADF——语义就错了。所以内核把 ERESTARTSYS 等一律转成 -EINTR，明确告诉用户「这次关闭没有完成，但 fd 已经释放，别再重试了」。

这也是 close 一个隐蔽陷阱：收到 EINTR 时 fd 状态是不确定的（Linux 上通常已关闭），不能简单地「重试 close」，否则可能误关一个已被复用给其他文件的同号 fd。

3. 引用计数：close ≠ 真正释放

close 只是把 fd 表项清空 + f_count 减一。struct file 真正的释放在引用计数归零时才发生：

操作 对 f_count 的影响
open() 新建 struct file，f_count = 1
dup()/dup2() 复制 fd，f_count++（共享同一 struct file）
fork() 子进程继承 fd 表，f_count++
close() f_count--；归零 → 调用 f_op->release 释放

所以「close 一个 fd」不等于「文件被关闭」——只要还有其他 fd（或子进程）引用着同一个 struct file，文件就还开着，偏移也还共享。这就是 Ch5 三层结构的核心。

4. 什么时候必须检查 close 的返回值

场景 是否检查
普通本地文件 通常可不检查（但最佳实践是检查）
网络文件系统（NFS） 必须检查——写失败可能延迟到 close 才报
带缓冲的 stdio fclose 前先 fflush/fsync，fclose 失败要处理

NFS 上 write 可能先成功（进客户端缓存），真正的网络写错误延迟到 close 时才返回，所以「write 没报错」不代表「数据安全落地」。

5. HFT / 嵌入式关联

现象 本节机制的兑现
fd 泄漏 长驻进程不 close，fd 一直占着直到 ulimit -n 耗尽 → 无法开新文件/socket
误关复用 fd 多线程里一个线程 close 后，另一个线程 open 可能复用同号 fd，再被误关——经典竞态
O_CLOEXEC 防泄漏 exec 时自动关 fd，避免子程序继承不该有的句柄
崩溃一致性 close 不保证落盘；关键数据先 fsync 再 close

6. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/demo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }

    write(fd, "data", 4);

    /* 关键数据：先 fsync 再 close，保证落盘 */
    if (fsync(fd) < 0) perror("fsync");
    if (close(fd) < 0) perror("close");   /* 检查 close 返回值 */
    return 0;
}

代码自测（Q&A）

Q1：close() 的作用是什么？进程退出时未关闭的 fd 会怎样？ A：close 清空 fd 表项并让引用计数减一，归零才真正释放 struct file。进程退出时 exit_files() 会逐个 fput 所有 fd，所以正常退出不会永久泄漏；但长驻进程不 close 会一直占着句柄，直到进程结束。

Q2：为什么 close 收到 EINTR 后不能简单重试？ A：因为 close_fd_get_file 已经先把 fd 表项清空了。若重试，该 fd 号可能已被其他线程的 open 复用，重试 close(fd) 会误关别人的文件。收到 EINTR 时应把 fd 视为「已释放」，不再重试。

Q3：为什么 NFS 场景必须检查 close() 的返回值？ A：NFS 的写错误可能延迟到 close 时才返回（filp_flush 触发真正的网络 flush）。write 成功只是写进客户端缓存，close 才可能报出 EIO/ENOSPC。漏查会让「数据没写进去」被误判成成功。

Q4：close(fd) 后，同一个 struct file 一定被释放了吗？ A：不一定。close 只让 f_count 减一；只有引用计数归零才释放。如果之前 dup 过、或 fork 出的子进程还持有同一 struct file，那它仍然活着，偏移也仍被共享。

Q5：close 能保证数据写到磁盘吗？ A：不能。close 只负责释放 fd 和刷内核缓冲，不保证物理落盘。要持久化必须 fsync/fdatasync（且顺序是「先 fsync 再 close」）。忘记这点会导致「以为 close 了数据就安全了」的断电丢数据事故。

`lseek()`

本章：TLPI 第 04 章 — File I/O: The Universal I/O Model 源码核验：Linux v6.6（fs/read_write.c:230 default_llseek、:285 vfs_llseek、:293 ksys_lseek、:311 SYSCALL_DEFINE3(lseek)） - 上一节：4.6 close() - 下一节：4.8 ioctl()

本节讲什么

lseek() 调整文件偏移。本节回答三个问题：

  1. lseek 在内核里怎么改 f_pos？SEEK_END 的「末尾」从哪来？
  2. 为什么管道/socket 上 lseek 返回 ESPIPE？
  3. 「文件空洞」是怎么来的？读空洞区得到什么？

1. 原型与内核链路

#include <unistd.h>
off_t lseek(int fd, off_t offset, int whence);
/* 成功返回新偏移；失败 -1（ESPIPE / EBADF / EINVAL） */
whence 基准 语义
SEEK_SET 文件起始 偏移 = offset
SEEK_CUR 当前偏移 偏移 = f_pos + offset
SEEK_END 文件末尾 偏移 = i_size + offset
SEEK_DATA / SEEK_HOLE — 定位到下一个数据/空洞区（部分文件系统支持） 
用户态 lseek(fd, offset, whence)
      ▼
SYSCALL_DEFINE3(lseek)         fs/read_write.c:311
      ▼
ksys_lseek()                   fs/read_write.c:293
      ├─→ fdget_pos(fd)       ← 取 struct file，fd 无效 → -EBADF
      ├─→ vfs_llseek()        ← 见下
      └─→ fdput_pos(f)

vfs_llseek() 先做「可 seek 性」检查（fs/read_write.c:285）：

loff_t vfs_llseek(struct file *file, loff_t offset, int whence)
{
    if (!(file->f_mode & FMODE_LSEEK))
        return -ESPIPE;              /* 管道/socket/终端 → 不支持 seek */
    return file->f_op->llseek(file, offset, whence);
}

普通文件走默认实现 default_llseek()（fs/read_write.c:230）：

loff_t default_llseek(struct file *file, loff_t offset, int whence)
{
    struct inode *inode = file_inode(file);
    switch (whence) {
    case SEEK_END:
        offset += i_size_read(inode);   /* 末尾 = inode 记录的大小 */
        break;
    case SEEK_CUR:
        if (offset == 0) { retval = file->f_pos; goto out; }  /* 只查不改 */
        offset += file->f_pos;
        break;
    case SEEK_DATA: ...   case SEEK_HOLE: ...
    }
    if (offset >= 0) { file->f_pos = offset; retval = offset; }
    ...
}

2. 关键语义

特性 说明
只改偏移，不产生 I/O lseek 改的是 struct file::f_pos（:1007），不碰磁盘，也不移动数据
SEEK_END 的末尾来自 inode i_size_read(inode)——文件大小的权威来源是 inode 的 i_size，不是「实际扫到 EOF」
SEEK_CUR + offset=0 返回当前 f_pos 而不移动，是「查当前偏移」的惯用法
越尾再写 = 空洞 lseek 跳过尾部再 write，中间字节不占磁盘块（读得 0）
不可 seek 对象 管道/socket/终端没设 FMODE_LSEEK → -1 + errno=ESPIPE

3. 文件空洞（sparse file）

lseek(fd, 1024*1024, SEEK_SET);   /* 跳到 1MB 处 */
write(fd, "x", 1);                /* 中间 1MB 是空洞 */

产生一个「逻辑大小 1MB+1，物理只占几 KB」的稀疏文件：

  • 空洞区不分配磁盘块（ls -lh 显示逻辑大小，du -h 显示真实占用）
  • 读空洞区返回 0（内核在页缓存里「现场造零」）
  • 拷贝稀疏文件若用普通 read/write 循环，会把空洞「读成真的 0 字节」写满目标——cp 默认能识别稀疏（cp --sparse=auto），自己写拷贝工具要注意

4. HFT / 嵌入式关联

现象 本节机制的兑现
日志文件大小 lseek(fd, 0, SEEK_END) 是「不用 stat 拿文件大小」的快捷方式（但要恢复原偏移）
稀疏文件省盘 预分配大文件（如行情回放文件）用 lseek + 写尾，逻辑大小大、物理占用小
管道不可 seek 从管道/socket 读流时不能回退/跳转，只能顺序消费——行情流天然是「只前进」的
偏移是共享状态 f_pos 在 struct file 里，dup/fork 共享；多进程随机读写要各自独立 open

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/ch4_lseek.txt", O_RDWR|O_CREAT|O_TRUNC, 0644);
    write(fd, "ABCDEFGHIJ", 10);

    lseek(fd, 3, SEEK_SET);              /* 移到偏移 3 */
    char c; read(fd, &c, 1);
    printf("byte at offset 3: %c\n", c); /* 'D' */

    printf("current offset: %ld\n", (long)pos);

    lseek(fd, -1, SEEK_END);             /* 末尾回退 1 */
    read(fd, &c, 1);
    printf("last byte: %c\n", c);        /* 'J' */

}

Q1：lseek(fd, 0, SEEK_CUR) 的作用是什么？ A：从当前位置偏移 0 字节，即「查询当前偏移而不移动」——这是不用 stat 拿当前位置的惯用法。default_llseek 里 SEEK_CUR 且 offset==0 直接返回 f_pos。

Q2：所有文件类型都支持 lseek 吗？ A：不。管道、socket、终端没有 FMODE_LSEEK 标志，vfs_llseek 返回 -ESPIPE。它们是流式对象，数据读走即消失，没有「位置」概念。

Q3：lseek 越尾再写会怎样？为什么「中间不占磁盘」？ A：产生文件空洞。lseek 只改 f_pos 不写数据，中间的偏移区间没有对应磁盘块；只有后来 write 的尾部字节真正分配块。读空洞区时内核返回 0（页缓存现场造零）。所以逻辑大小可能远大于物理占用。

Q4：用「lseek(SEEK_END) 拿文件大小」有什么要注意的？ A：SEEK_END 会移动 f_pos 到末尾。若之后还要在原位置读写，必须先 SEEK_CUR 记住原偏移、查完再 SEEK_SET 恢复。更稳妥的是用 fstat/stat 直接读 st_size，不碰偏移。

Q5：lseek 会不会触发磁盘 I/O？ A：不会。它只改内存里的 struct file::f_pos（include/linux/fs.h:1007），不读数据、不分配块（除非后续 write 到空洞区才分配）。这也是「lseek 极快」的原因。

`ioctl()`

本节讲什么

1. 原型与定位

#include <sys/ioctl.h>

ioctl 处理的是「字节流之外的控制」：设置终端窗口、查询磁盘几何、配置网卡混杂模式——这些没有对应的 read/write 语义，只能靠一个「命令字 + 数据指针」的万能接口。

宏 方向 含义
_IO(type, nr) 无数据 纯命令，无参数
_IOR(type, nr, datatype) 内核 → 用户（读） 内核写数据给用户
_IOW(type, nr, datatype) 用户 → 内核（写） 用户传数据给内核
_IOWR(type, nr, datatype) 双向 读写都有

type 是 8 位「魔法数」标识设备类别（如 'T' 代表 tty），nr 是命令序号，datatype 告诉内核参数的大小（用于 copy_from_user/copy_to_user 时校验边界）。

3. 示例：查终端窗口大小（TIOCGWINSZ）

窗口行列数是「字节流」表达不了的，只能 ioctl：

#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <termios.h>    /* struct winsize */
#include <stdio.h>

int main(void) {
    struct winsize ws;
    if (ioctl(STDIN_FILENO, TIOCGWINSZ, &ws) == 0) {
        printf("终端: %d 行 x %d 列\n", ws.ws_row, ws.ws_col);
    } else {
        perror("ioctl TIOCGWINSZ");
        printf("（非终端环境，如管道/重定向）\n");
    }
    return 0;
}

TIOCGWINSZ 是 _IOR('T', 104, struct winsize)——「tty 设备、读方向、参数是 struct winsize」。

代码自测（Q&A）

Q1：为什么有了 read/write/lseek 还要 ioctl？ A：因为「字节流」语义覆盖不了「控制/查询」类操作。设置终端窗口大小、查询磁盘扇区数、配置网卡——这些不是「搬一段字节」，没有对应的 read/write 动词。ioctl 用「命令字 + 数据指针」提供了一个万能兜底，让设备能暴露任意自定义操作。

Q2：request 参数里为什么要编码 size（数据大小）？ A：为了安全。ioctl 的可变参数是用户态指针，内核在 unlocked_ioctl 里要 copy_from_user/copy_to_user。request 里的 size 字段让内核知道要拷贝多少字节，避免越界；_IOR/_IOW 宏用 sizeof(datatype) 自动填入这个大小。

Q3：ioctl 和普通文件（非设备）搭配会怎样？ A：普通文件通常没实现对应命令，多数返回 -ENOTTY（「not a typewriter」，历史遗留错误名，意为「该对象不支持此 ioctl」）。isatty() 就是靠探测 TCGETS 这类命令来判断 fd 是不是终端的。

Q4：_IOR 和 _IOW 的「方向」有什么实际作用？ A：它告诉内核数据流向，内核据此决定 copy_from_user（用户→内核）还是 copy_to_user（内核→用户），并在部分架构上做校验。方向写错会导致数据没按预期拷贝——这是驱动 bug 的常见来源。

Q5：ioctl 的返回值一定是 0/1 吗？ A：不。ioctl 失败返回 -1 并设 errno，但成功时的返回值由驱动自定义（多数返回 0，也可能返回有意义的值）。所以不能用「返回值 == 某个正数」当成功判据，标准写法是 if (ioctl(...) == -1) 出错。

代码自测

1. 为什么 read/write 可能返回小于请求的字节数？
  • read：到达 EOF、管道/套接字缓冲区只有部分数据、被信号中断、从终端读取遇到换行符
  • write：磁盘空间不足、写入管道且缓冲区部分满、被信号中断
  • 正确做法：循环调用直到完成全部数据传输（参见练习 1）
2. fork() 后父子进程共享文件偏移量吗？

是。fork() 复制 fd 表，但指向相同的内核打开文件表项。父子进程共享偏移量和状态标志。这是一个重要的并发问题——多进程操作同一文件需用 O_APPEND 或文件锁。

3. O_APPEND 为什么能保证多进程写入不交错？

内核在执行 write() 时，先原子地将偏移量设为文件末尾，再执行写入。这个"设偏移量+写"操作是不可分割的原子步骤。没有 O_APPEND 时，lseek(SEEK_END) + write() 是两步，存在 TOCTOU 竞争窗口。

练习 1：实现简化版 cp（短读 + 部分写）

用 open/read/write/close 实现文件拷贝，要求处理短读和部分写。

参考答案 
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main(int argc, char *argv[]) {
    if (argc != 3) { fprintf(stderr, "usage: %s src dst\n", argv[0]); return 1; }

    int src = open(argv[1], O_RDONLY);
    if (src < 0) { perror("open src"); return 1; }

    int dst = open(argv[2], O_WRONLY|O_CREAT|O_TRUNC, 0644);
    if (dst < 0) { perror("open dst"); return 1; }

    char buf[8192];
    ssize_t n;
    while ((n = read(src, buf, sizeof(buf))) > 0) {     /* 循环读（短读） */
        ssize_t written = 0;
        while (written < n) {                            /* 循环写（部分写） */
            ssize_t w = write(dst, buf + written, n - written);
            if (w < 0) { perror("write"); return 1; }
            written += w;
        }
    }
    if (n < 0) perror("read");

    if (close(src) < 0) perror("close src");
    if (close(dst) < 0) perror("close dst");
    return 0;
}

练习 2：文件内容倒序输出（lseek 随机定位）

用 lseek 从末尾向前逐字节读，倒序输出。

参考答案 
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main(int argc, char *argv[]) {
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }

    off_t size = lseek(fd, 0, SEEK_END);   /* 拿文件大小（顺带移到末尾） */
    for (off_t pos = size - 1; pos >= 0; pos--) {
        lseek(fd, pos, SEEK_SET);
        char c;
        if (read(fd, &c, 1) == 1)
            write(STDOUT_FILENO, &c, 1);
    }
    close(fd);
    return 0;
}

练习 3：解释 short write 的至少 3 种成因

参考答案
  1. 管道/FIFO 缓冲不足：写入超过 PIPE_BUF 或缓冲区剩余空间，只写满就返回。
  2. 信号中断：EINTR，部分数据已写入后被打断。
  3. 磁盘空间不足：ENOSPC，只写入剩余空间能容纳的部分。
  4. 网络 socket：TCP 发送缓冲区部分填满，只拷贝了能放下的字节。

对应内核机制：vfs_write 不做「保证写满」的承诺，实际写入量由 f_op->write 决定（fs/read_write.c:564）。

练习 4：O_APPEND 的原子性

多进程同时写同一文件，O_APPEND 会交错吗？不用 O_APPEND 呢？

参考答案
  • 有 O_APPEND：不会交错。内核在每次 write 前原子地把偏移设到文件末尾，然后写。「设偏移 + 写」是一个不可分割的整体，多个进程的追加严格串行。
  • 无 O_APPEND：会交错。lseek(SEEK_END) + write() 是两步操作，进程 A 的 lseek 和 write 之间可能被进程 B 插入，两者都从同一个「旧末尾」写，导致覆盖或交错。

这是经典的 TOCTOU（check-to-use）竞争窗口。O_APPEND 把「定位到末尾」这个动作下沉到内核的 write 里原子完成，用户态无法用 lseek+write 复刻同等的原子性。
