章节目标

  • 分清三代技术：轮询（正确但贵）→ dnotify（信号通知、不带文件名、fd 钉目录——已淘汰）→ inotify（fd 化事件队列：可 read、可 poll/epoll、带文件名与改名配对）
  • API 只有三个 syscall，难在一致性：watch 挂 inode 不挂路径（改名不丢监控、safe-write 替换的文件必失效——所以要监控目录）；watch 不递归（IN_CREATE|IN_ISDIR/IN_MOVED_TO|IN_ISDIR 时补 watch 并立即 rescan）
  • 事件流的三个工程事实：变长记录（步进 sizeof + len，缓冲保底 sizeof + NAME_MAX + 1）；cookie 只在 MOVED_FROM/TO 配对（跨 FS 移动配不上——把改名降级成「删+建」永远安全）；IN_Q_OVERFLOW = 丢事件 = 必须全量重建
  • 容量面：max_queued_events（溢出静默丢）/ max_user_instances（每真实用户）/ max_user_watches（ENOSPC）；队列满的第一根因是「事件循环做重活」——重活必须异步
  • 诚实：本章含一处错误码级源码核验——IN_ONLYDIR 对非目录报 ENOTDIR（内核 fs/notify/inotify/inotify_user.c:756 经 LOOKUP_DIRECTORY 让路径解析层拒绝），man-pages 未明写；其余预期输出按语义推演并明确标注「非实测」

六条纪律（全章的工程兑现）

  1. watch 不递归 → IN_CREATE|IN_ISDIR 与 IN_MOVED_TO|IN_ISDIR 时补 watch，add 后立即 rescan 补漏
  2. watch 挂 inode → 监控「会被 safe-write 替换的文件」必失效；监控目录 + IN_MOVED_TO|IN_CLOSE_WRITE
  3. 读循环先判系统级事件 → IN_Q_OVERFLOW（全量重建）与 IN_IGNORED（清映射）在业务分支之前
  4. 重活异步 → 事件循环只分派；消费速率跟不上 = 队列溢出只是时间问题
  5. 改名降级安全 → MOVED_FROM/TO 处理成「删+建」永远正确；把「删+建」凑成改名是危险升级
  6. 跨平台红线 → macOS/Windows 语义不对齐（无 name、无 cookie、无溢出事件）；抽象层按最小公倍数设计

19.1

Overview 概述

本章：TLPI 第 19 章 — Monitoring File Events ⚠️ inotify 是 Linux 专有接口（2.6.13+；dnotify 更早）。macOS 没有等价机制（BSD 用 kqueue/FSEvents），本章全部程序未在本机编译运行——源码按 man-pages 6.19 inotify(7) / inotify_init(2) / inotify_add_watch(2) / fcntl(2)(F_NOTIFY) + Linux v6.6 fs/notify/inotify/ 核验，实测项全部入 Pi5 复测清单 官方节号核验：toc-detailed.html 19.1–19.8 与本仓库文件名一一对应 - 上一节：本章首页 - 下一节：19.2 The inotify API

本节讲什么

文件系统事件监控的三代技术，以及为什么 dnotify 被淘汰：

  1. 轮询（readdir/stat 周期扫描）——正确但昂贵；
  2. dnotify——信号驱动，每目录一个 fd，事件粒度粗且不带文件名；
  3. inotify——fd 化的事件队列，粒度细、可多路复用，是现代 Linux 的标准答案。

要点：三代技术对照

轮询 dnotify（1999） inotify（2.6.13, 2005）
模型 主动周期扫描 信号驱动（SIGIO） fd 事件队列
粒度 无（全量扫） 目录级，事件种类少（DN_ACCESS/DN_MODIFY/DN_CREATE/DN_DELETE/DN_RENAME/DN_ATTRIB） 文件级 + 目录级，十余种事件
通知里带文件名吗 — ❌（必须自己 rescan 目录找出变了谁） ✅（name 字段）
资源占用 高（持续 I/O + syscall） 每目录占一个 fd（fd 挂着目录 → 目录无法卸载） 一个 inotify 实例 + 每 watch 一条内核记录
与 I/O 多路复用 — 信号（难整合，realtime 信号可缓解） ✅ poll/select/epoll 天然可等
现状 特定场景仍用 已淘汰（TLPI 只留一节） Linux 标准

要点：inotify 的核心心智模型

inotify 实例（fd）
 ├── watch 1: /var/data  (mask=IN_CREATE|IN_DELETE|…)  → wd=1
 ├── watch 2: /var/log   (mask=…)                       → wd=2
 └── …
 事件队列（内核排队，read() 读出 struct inotify_event 序列）
  • fd 是实例，wd 是实例内的 watch 编号——read() 出来的事件带着 wd，应用自己维护 wd → 路径 映射；
  • watch 挂在 inode 上，不是路径上：监控中的文件被改名/移动，watch 依然有效（这是与直觉相反、也最常被误解的一点）；
  • 不递归：watch 一个目录只看它的直接子项；子树要逐目录建 watch（习题 19-1 正是练这个）。

为什么「监控文件变化」比看起来难

难点 轮询 dnotify inotify 的回答
谁动了哪个文件 全量 diff 不知道（要 rescan） name 字段直接给
改名是「删+建」还是「改名」 看不出来 看不出来 MOVED_FROM/TO + cookie 配对
大目录高频变更 扫不过来 信号风暴 队列 + 限流（§19.5）
与主事件循环整合 定时器 信号处理器的异步地狱 就是一个普通 fd

代码自测（Q&A）

Q1：为什么 dnotify 需要「每目录一个 fd」会成为致命缺点？ A：① fd 是有限资源，大规模目录监控直接耗尽；② 打开的目录 fd 使目录处于「使用中」，无法卸载所在文件系统（挂载管理噩梦）；③ 事件通过信号送达，信号没有队列语义（标准信号会合并），只能配合 realtime 信号 + SA_SIGINFO 缓解。

Q2：inotify 的 watch 为什么「挂 inode 不挂路径」？ A：内核实现（fs/notify/inotify/）是 inode 上的钩子（fsnotify 连接器）。好处：改名/移动不丢监控；代价：目录被删除时 watch 自动失效（IN_IGNORED），应用必须清理映射。两种行为都要显式处理。

Q3：inotify 能监控 NFS/网络文件系统吗？ A：一般不能——事件由本地内核在 vnode 操作点产生，网络 FS 的远端变更不会触发（部分实现支持本地缓存行为）。生产上跨机同步不能依赖 inotify，要做协议层通知。

Q4：macOS 上做等价功能的正确姿势？ A：单目录细粒度用 kqueue EVFILT_VNODE（NOTE_WRITE/NOTE_DELETE/...，同样不带名字）；整树监控用 FSEvents（带路径但粒度粗、延迟更高）。与 inotify 的语义差异（尤其改名配对）要在抽象层抹平，不能假设一一对应。

19.2

The inotify API inotify 应用编程接口

本章：TLPI 第 19 章 — Monitoring File Events ⚠️ Linux 专有（2.6.13+）；macOS 无此接口。本章程序未在本机编译运行——源码按 man-pages 6.19 inotify(7) / inotify_init(2) / inotify_add_watch(2) / inotify_rm_watch(2) + Linux v6.6 fs/notify/inotify/inotify_user.c 核验，Pi5 复测清单见章 README - 上一节：19.1 Overview - 下一节：19.3 inotify Events

本节讲什么

三个 syscall 的完整契约，以及四个必须钉住的语义：

  1. inotify_init1() 创建实例 fd（IN_NONBLOCK/IN_CLOEXEC）；
  2. inotify_add_watch() 返回 wd——同一 inode 重复 add 是「修改 mask」并返回同一个 wd；
  3. inotify_rm_watch() 会触发一条 IN_IGNORED 事件（不是静默消失）；
  4. watch 挂 inode 不挂路径 → 改名不丢监控、删除自动失效。

要点：三个 syscall

#include <sys/inotify.h>
int inotify_init1(int flags);        /* IN_NONBLOCK | IN_CLOEXEC；返回实例 fd */
int inotify_add_watch(int fd, const char *pathname, uint32_t mask);
                                     /* 返回 watch descriptor（wd） */
int inotify_rm_watch(int fd, int wd);
调用 成功返回 典型失败
inotify_init1 实例 fd EMFILE（实例数超 /proc/sys/fs/inotify/max_user_instances）、ENOMEM
inotify_add_watch wd（非负） ENOSPC（watch 数超 max_user_watches）、EACCES、EINVAL（IN_ONLYDIR 但不是目录）
inotify_rm_watch 0 EINVAL（wd 无效）

要点：mask 的两个身份

同一套 IN_* 位在两个地方出现，身份不同：

身份 出现位置 例子
事件位（发生了什么） read 出来的 ev->mask IN_CREATE、IN_MODIFY、IN_ISDIR
订阅位（想看什么） inotify_add_watch 的 mask 参数 同名位 + 控制位 IN_ONLYDIR 等

订阅位多出来的控制位（不表示事件）：

控制位 作用
IN_ONLYDIR 只监控目录；路径不是目录则报 ENOTDIR（内核 v6.6 fs/notify/inotify/inotify_user.c:756 用 LOOKUP_DIRECTORY 让路径解析层直接拒绝，fs/namei.c:2822 附近返回 -ENOTDIR）
IN_DONT_FOLLOW 不跟随符号链接：监控链接本身
IN_EXCL_UNLINK 已 unlink 的子项不再报告（防临时文件噪音）
IN_MASK_ADD 追加而不是替换已有 mask（重复 add 同一 inode 时）
IN_ONESHOT 一次性：首个事件后自动移除 watch

⚠️ 注意 IN_ONLYDIR 与老接口的差异：它让「是目录吗」的检查原子化（否则「stat 判目录 + add_watch」之间可被换）——与 Ch18 §18.6 的 mkdir 原子检查同一设计哲学。

要点：重复 add_watch 的语义（最容易写错的一条）

int wd1 = inotify_add_watch(fd, "/var/data", IN_CREATE);
int wd2 = inotify_add_watch(fd, "/var/data", IN_MODIFY);
/* wd1 == wd2 —— 同一 inode！且此时 mask 是 **IN_MODIFY**（替换语义），
   原来的 IN_CREATE 丢了；要叠加必须 IN_MASK_ADD：
   inotify_add_watch(fd, "/var/data", IN_MODIFY | IN_MASK_ADD); */

推论：通过不同路径（如硬链接、或 .. 拼接的不同写法）add 同一 inode，得到的也是同一个 wd。应用维护 wd → 路径 映射时，路径只是「第一次 add 时的名字」，不是稳定身份。

要点：watch 的生命周期

事件 watch 会怎样 应用要做什么
监控的目录里文件被删/移出 watch 不受影响（watch 的是目录） —
监控的文件本身被删除 watch 失效，队列里出现 IN_IGNORED（带 IN_DELETE_SELF 前后伴随） 清理 wd 映射
监控的文件/目录被改名 watch 依然有效（挂 inode） 路径名变了，展示层要自己跟进
所在文件系统被卸载 失效 + IN_UNMOUNT + IN_IGNORED 全量清理
inotify_rm_watch 队列里出现 IN_IGNORED 事件循环里清映射，别只清本地变量
IN_ONESHOT 首个事件后自动移除 想续就重新 add

要点：标准程序骨架（本仓库两个 demo 的两种形态）

/* 形态 A：阻塞 read（inotify_dir.c）*/

for (;;) {
    char buf[BUF_LEN];

        /* ... 处理 ev ... */
        p += sizeof(*ev) + ev->len;
    }
}

/* 形态 B：非阻塞 + epoll（inotify_epoll.c，Ch63 的预演）*/

epoll_ctl(epd, EPOLL_CTL_ADD, ifd, &(struct epoll_event){ .events = EPOLLIN });
for (;;) { epoll_wait(...); read(ifd, ...); /* EAGAIN 结束本轮 */ }

代码自测（Q&A）

Q1：inotify_add_watch 返回的 wd 与文件描述符是什么关系？ A：wd 是实例内的编号（跨实例不唯一），fd 是实例本身。同一 inode 在同一实例内重复 add 永远得到同一个 wd（并按替换/IN_MASK_ADD 语义改 mask）。跨实例监控同一 inode 则得到两个独立 wd、两份事件。

Q2：为什么官方推荐 inotify_init1 而不是老的 inotify_init？ A：老的没有 flags 参数，IN_NONBLOCK/IN_CLOEXEC 都得事后 fcntl 补——「创建后再设置」在多线程下有窗口（另一线程可能恰好 exec）。init1 一步原子完成，与 open(O_CLOEXEC) 的教训同源。

Q3：监控一个被 safe-write 反复替换的配置文件，会发生什么？ A：watch 挂在第一次 add 时的 inode 上。每次 rename 替换都产生新 inode，老 inode（连同 watch）随老文件消失——你会收到 IN_DELETE_SELF/IN_IGNORED，之后静默失明。正解是监控所在目录。

Q4：IN_MASK_ADD 与 IN_ONESHOT 能组合吗？ A：IN_MASK_ADD 是 mask 维护语义、IN_ONESHOT 是生命周期语义，可组合；但 IN_ONESHOT + 反复 add 的组合要小心——首个事件后 watch 消失并带 IN_IGNORED，此前叠加的 mask 一并清零。

Q5：inotify_rm_watch 之后，事件循环里应该期待什么？ A：一条 IN_IGNORED 事件（wd 对应的事件）。它是 wd 的「讣告」——收到后才能安全地删除 wd → 路径 映射。跳过这一步的事件循环会在后续读到「孤儿 wd」。

Q6：为什么说「wd → 路径」映射里的路径只是快照？ A：watch 挂 inode：目录被改名后事件继续到达，但 name 字段只给子项名，目录本身的新路径不在事件里。应用要么在 MOVED_TO 等事件里自己维护目录改名，要么接受路径过期（用于日志展示时通常无妨）。

19.3

inotify Events inotify 事件

本章：TLPI 第 19 章 — Monitoring File Events ⚠️ Linux 专有；macOS 无此接口。本章程序未在本机编译运行——源码按 man-pages 6.19 inotify(7)（struct inotify_event 与 mask 全表）+ Linux v6.6 include/uapi/linux/inotify.h 核验，Pi5 复测清单见章 README - 上一节：19.2 The inotify API - 下一节：19.4 Reading inotify Events

本节讲什么

  1. struct inotify_event 的五个字段——尤其是变长的 name 与它的对齐规则；
  2. 事件 mask 全表：哪些事件报告子项（带 name）、哪些报告被监控对象本身（不带 name）；
  3. cookie 的配对语义（MOVED_FROM/MOVED_TO）；
  4. 三个「系统级」事件：IN_IGNORED/IN_Q_OVERFLOW/IN_UNMOUNT。

要点：结构体与变长 name

struct inotify_event {
    int      wd;        /* 产生事件的 watch descriptor */
    uint32_t mask;      /* 事件位（可能含 IN_ISDIR 等修饰位） */
    uint32_t cookie;    /* 关联标识（改名配对用；其余为 0） */
    uint32_t len;       /* name 的长度（含尾部对齐填充的 NUL） */
    char     name[];    /* 变长：子项名；len==0 时这个字段不存在 */
};
字段 关键点
wd 实例内唯一；应用自己维护 wd → 路径 映射
mask 事件位 + 修饰位（IN_ISDIR、IN_IGNORED、IN_Q_OVERFLOW、IN_UNMOUNT）
cookie 只有 IN_MOVED_FROM/IN_MOVED_TO 一对共享同一个非零值；其余事件恒为 0
len 是含填充的长度（内核把名字补齐到 4 字节边界）；遍历步进用 sizeof(*ev) + ev->len，不要用 strlen(ev->name)
name 只在事件针对被监控目录的子项时存在；事件针对被监控对象本身（如 IN_DELETE_SELF）时 len == 0

步进规则（§19.4 的 read 循环全靠它）：

for (char *p = buf; p < buf + n; ) {
    struct inotify_event *ev = (struct inotify_event *) p;
    /* ev->len > 0 时可读 ev->name（打印前自己补 NUL 或用 %.*s）*/
    p += sizeof(struct inotify_event) + ev->len;
}

要点：事件 mask 全表（按「报告对象」分组）

A. 报告子项（带 name，watch 目录才有）

事件 触发 与哪个 syscall 对应
IN_CREATE 子项被创建 open(O_CREAT)、mkdir、link、symlink
IN_DELETE 子项被删除 unlink、rmdir
IN_MOVED_FROM 子项被移出（改名到别处） rename 的 oldpath 一侧
IN_MOVED_TO 子项被移入 rename 的 newpath 一侧
IN_OPEN / IN_ACCESS / IN_MODIFY / IN_ATTRIB 子项被打开/读/写/元数据变更 open / read / write / chmod 等
IN_CLOSE_WRITE / IN_CLOSE_NOWRITE 以写/非写方式打开的 fd 被 close close

B. 报告被监控对象本身（len==0，无 name）

事件 触发 配套
IN_DELETE_SELF 监控对象被删除 之后紧跟 IN_IGNORED
IN_MOVE_SELF 监控对象被改名/移动 watch 依然有效（挂 inode）
IN_UNMOUNT 所在文件系统被卸载 之后 IN_IGNORED；此间事件不可靠

C. 系统级事件（修饰位形式出现在 mask 里）

事件 含义 应用必须做什么
IN_IGNORED watch 已失效（删除/卸载/rm_watch/IN_ONESHOT 触发后） 清理 wd 映射；别再期待这个 wd 的事件
IN_Q_OVERFLOW 内核事件队列溢出——有事件丢了 wd == -1；要全量重建（rescan + 重挂 watch）
IN_ISDIR 修饰位：事件对象是目录（建子树监控的判据） ev->mask & IN_ISDIR

要点：cookie 配对（改名语义的关键）

一次 rename("/dir/a", "/dir/b")（同目录内改名）会同时产生两条事件：

IN_MOVED_FROM  cookie=12345  name="a"
IN_MOVED_TO    cookie=12345  name="b"
场景 事件形态
同目录改名 MOVED_FROM + MOVED_TO，cookie 相同
跨目录改名（同 FS） 两目录各出一条，cookie 相同
移到另一文件系统（mv /tmp/x /mnt/y 实际是复制+删除） MOVED_FROM（或 DELETE）+ 另一侧 CREATE——cookie 配不上
只监听了单侧目录 只收到一条 MOVED_FROM（cookie 用不上）

工程含义：把改名处理成「删+建」是安全的降级（多一次 rescan，语义不丢）；把「删+建」硬凑成「改名」则是危险的升级（cookie 对不上时凑出来的改名是错的）。降级永远安全。

常见坑

坑 正解
步进用 ev->len 当「名字长度」 len 含对齐填充；步进用 sizeof(*ev) + ev->len，名字打印用 %.*s 或按返回的 len 截断
用 strlen(ev->name) 当长度 name 以 NUL 结尾（内核保证最后一个字节是 NUL），但用 strlen 而不看 len==0 的分支会读越界（无 name 的事件里 name 字段根本不存在）
忽略 IN_IGNORED wd 永久失效且不会再有事件；映射不清则后续事件按「孤儿 wd」处理
忽略 IN_Q_OVERFLOW 丢了多少事件不知道；唯一正解是全量 rescan 重建
对 IN_CLOSE_WRITE 与 IN_MODIFY 混用 流式读取（日志跟随）用 IN_MODIFY；「文件写完了可以拿走」用 IN_CLOSE_WRITE——safe-write 的产物总是伴随 IN_MOVED_TO + IN_CLOSE_WRITE 不出现（rename 不 close）
只等 IN_DELETE 而忘了 MOVED_FROM mv 出去的文件不触发 DELETE；「删除检测」要用 IN_DELETE|IN_MOVED_FROM

HFT / 嵌入式关联

场景 本节机制怎么兑现
行情文件就绪检测 IN_MOVED_TO|IN_CLOSE_WRITE（而非 IN_CREATE）：rename 进来的文件是完整的，create 的可能还在写
配置热重载 IN_MOVED_TO + IN_CLOSE_WRITE + IN_ATTRIB 全订阅，按 cookie/顺序去重
嵌入式掉电 IN_UNMOUNT/IN_IGNORED 是掉电/卸载的哨兵；收到后必须停止依赖 watch 而走 rescan 慢路径
审计日志 IN_ATTRIB 对应权限/属主变更（安全审计）；IN_ACCESS 在 relatime 下不可靠（Ch15 实测）——别用 atime 事件做合规判据
带宽控制 IN_MODIFY 对大文件写入是高频事件（每次 write 都触发）；按「写完」跟踪要用 IN_CLOSE_WRITE，否则队列爆（§19.5）

代码自测（Q&A）

Q1：为什么 name 要对齐填充到 4 字节？ A：内核按 struct inotify_event 序列化事件流，下一条事件的起始必须是 4 字节对齐（结构体成员对齐要求）。len 反映的是「这一段变长区域的总长」而非「名字的 C 串长」，所以遍历步进必须用 sizeof + len。

Q2：IN_Q_OVERFLOW 的 wd 为什么是 -1？ A：溢出是实例级事件，不属于任何 watch。内核无法把它挂到某个 wd 上，约定 wd == -1。这也是「收到它就全量重建」的原因：丢的事件可能涉及任意 watch。

Q3：IN_DELETE_SELF 和 IN_IGNORED 的先后关系？ A：对象被删除 → 队列里先是 IN_DELETE_SELF（描述发生了什么），随后内核把 watch 移除并补一条 IN_IGNORED（宣告 wd 失效）。应用按这个顺序清理：先处理语义事件，再在 IN_IGNORED 里删映射。

Q4：同目录内 rename("a","b")，cookie 相同的两条事件顺序有保证吗？ A：有——MOVED_FROM 先于 MOVED_TO（内核在 vfs_rename 内按序入队）。但跨目录时两条事件挂在不同 watch 上，若两个 watch 在同一实例里，顺序仍保证；跨实例则无保证。

Q5：能否用 inotify 统计「文件内容改了多少字节」？ A：不能。IN_MODIFY 只说「内容变了」，不带偏移与长度。要精确 diff 只能自己记快照（mtime+size 触发重扫）或用 fanotify/eBPF（kprobes on vfs_write）这类更底层机制。

Q6：IN_OPEN/IN_ACCESS 这些「读侧」事件在生产上常用吗？ A：很少。粒度太细、频率太高（读一个目录条目都可能触发），通常只用于调试或安全审计的特定 inode。监控「就绪/变更」用写侧事件（CREATE/CLOSE_WRITE/MOVED_TO）。

19.4

Reading inotify Events 读取 inotify 事件

本章：TLPI 第 19 章 — Monitoring File Events ⚠️ Linux 专有；macOS 无此接口。本章程序未在本机编译运行——源码按 man-pages 6.19 inotify(7)（READ EVENTS 段）+ Linux v6.6 fs/notify/inotify/inotify_user.c（inotify_read，逐条拷贝进用户缓冲）核验，Pi5 复测清单见章 README - 上一节：19.3 inotify Events - 下一节：19.5 Queue Limits and /proc Files

本节讲什么

  1. read() 在 inotify fd 上返回的是变长记录流——一次 read 可含多条、半条都不存在；
  2. 缓冲要多大、步进怎么算、为什么「一次读一批」在性能上重要；
  3. 阻塞 / 非阻塞 / poll-epoll 三种读法（对应本仓库两个 demo）；
  4. NAME_MAX + 1 这个「保底缓冲」公式为什么成立。

要点：read 的语义

char buf[BUF_LEN];
ssize_t n = read(ifd, buf, sizeof buf);
/* n = 本次读到的总字节数（≥ 一条完整事件；== 0 不会出现——队列空且阻塞时 sleep）*/
/* n = -1 且 errno == EAGAIN：非阻塞模式下队列空 */
模式 队列空时 队列有事件时
阻塞（默认） read 睡眠直到有事件 返回一到多条事件（内核把队列里当时所有能放进缓冲的都给你）
非阻塞（IN_NONBLOCK） -1 + EAGAIN/EWOULDBLOCK 同上
poll/epoll 等就绪再读 read 立即返回（就绪才进来） 同上

一次 read 最多放得下的事件数 = min(队列里的事件, 缓冲能装下的条数)——内核不会给半条事件；如果缓冲连一条都装不下，read 报 EINVAL。

要点：缓冲大小公式

/* TLPI 给出的「最坏情况」保底公式 */
#define BUF_LEN (16 * (sizeof(struct inotify_event) + NAME_MAX + 1))
项 含义
sizeof(struct inotify_event) 定长头 16 字节（int + 3×uint32，按 LP64 恰 16）
NAME_MAX + 1 最长文件名（通常 255）+ 结尾 NUL；len 会补齐对齐，取 +1 是保守估计
×16 TLPI 的经验值：一次 read 期望装下 16 条

三条实际规则：

  1. 绝对最小值是 sizeof(struct inotify_event) + NAME_MAX + 1——小于它，read 连一条都可能装不下（EINVAL）；
  2. 批量读更高效：一次 syscall 处理 N 条事件，比每条一次 read 省 N−1 次陷入；高频场景（IN_MODIFY 风暴）差距是数量级；
  3. 事件之间无对齐空洞可依赖——缓冲里的记录边界只由 sizeof + len 决定，不能按固定步长切。

要点：标准读循环（全章的模板）

for (;;) {
    ssize_t n = read(ifd, buf, sizeof buf);
    if (n == -1) {
        if (errno == EAGAIN) { /* 非阻塞：无事件，去做别的 */ continue; }
        perror("read"); break;
    }
    for (char *p = buf; p < buf + n; ) {
        struct inotify_event *ev = (struct inotify_event *) p;

        if (ev->mask & IN_Q_OVERFLOW)      { rebuild_all(); }        /* 队列溢出 */
        else if (ev->mask & IN_IGNORED)    { drop_watch(ev->wd); }   /* wd 失效 */
        else                               { handle(ev); }           /* 业务 */

        p += sizeof(struct inotify_event) + ev->len;   /* 唯一正确的步进 */
    }
}

IN_Q_OVERFLOW/IN_IGNORED 的检查要在业务分支之前——这两条不是普通事件，落在它们上面继续按业务处理会读到无效 wd。

要点：三种读法的选择（对应两个 demo + epoll）

方案 代码形态 适用 代价
阻塞 read（inotify_dir.c） init1(IN_CLOEXEC) + 循环 read 专职监控进程、单线程 demo 无法同时等别的 fd
非阻塞轮询 init1(IN_NONBLOCK) + 空转 read ❌ 几乎不该用 空转烧 CPU
非阻塞 + poll/epoll（inotify_epoll.c） init1(IN_NONBLOCK\|IN_CLOEXEC) + fd 入 epoll 生产标准：文件系统事件与网络/定时器同循环 多一个 epoll 实例 
/* epoll 形态骨架（Ch63 的预演）*/
int epd = epoll_create1(0);
struct epoll_event ee = { .events = EPOLLIN };
epoll_ctl(epd, EPOLL_CTL_ADD, ifd, &ee);
for (;;) {
    epoll_wait(epd, events, MAX, -1);
    /* 就绪后循环 read 到 EAGAIN（边缘触发语义下必须读干；水平触发可读一批）*/
}

要点：读侧的几个细节

细节 说明
read 返回 0 吗 正常不会（inotify fd 是「队列」语义）；返回 0 视为异常
一次 read 里事件跨 watch 混排 是的，同一实例的所有 watch 的事件按发生序混在一起；按 ev->wd 分派
处理一条事件时又产生新事件 新事件入队列，下一轮 read 读到——事件循环里做重活会导致队列积压（见 §19.5）
name 打印 printf("%.*s", (int) ev->len, ev->name)，或先按 len 拷出再补 NUL（len 含填充）
缓冲复用 栈缓冲即可；read 是拷贝语义，不持有用户指针

常见坑

坑 正解
read 后只处理「一条」事件 一次 read 可能有多条；必须 for (p = buf; p < buf+n; p += sizeof+len)
缓冲按 sizeof(inotify_event) 分配 装不下带 name 的事件 → EINVAL 或截断；用保底公式
事件循环里做重 I/O 队列积压 → 溢出（IN_Q_OVERFLOW）→ 全量重建；重活丢线程池

代码自测（Q&A）

Q1：为什么一次 read 可以返回多条事件？这违反「read 读一串字节」吗？ A：不违反——事件流本来就是字节流，只是字节流里有内部结构。内核的 inotify_read 把队列里的事件逐条拷进用户缓冲直到放不下为止，和管道返回「攒下的多段数据」同构。

Q2：read 报 EINVAL 最常见的原因？ A：缓冲连一条完整事件都装不下（内核拒绝给出半条）。按「sizeof(struct inotify_event) + NAME_MAX + 1 保底」公式分配即可避免。

Q3：处理事件时能直接持有 ev->name 指针到下一轮循环吗？ A：不能跨轮。缓冲内容只在「这一次 read 的处理期间」有效，下一轮 read 会覆盖。要保留就拷贝（strndup(ev->name, ev->len)）。

Q4：IN_NONBLOCK 下 read 返回 n>0 之后还有事件，此时该再 read 吗？ A：水平触发（poll/epoll 默认）下会再次就绪通知你；但当轮一次 read 只拿了缓冲装得下的部分，队列里可能还有。生产做法：无论哪种触发模式，读到 EAGAIN 为止，逻辑最简单且对 ET 正确。

Q5：为什么 demo 里 read 用 4.3 KB 缓冲而不是 1 MB？ A：批量收益在「前几条」最大，16 条已能摊销绝大多数 syscall 开销；超大缓冲的边际收益趋零，而每轮的内存清零/缓存成本恒定。嵌入式场景 4 KB 也正好是一页的整数倍邻域，对栈友好。

Q6：事件循环里可以直接调 inotify_add_watch（如子树监控）吗？ A：可以——add 作用于内核数据结构，不影响正在读的缓冲。但注意顺序：先 add 后可能漏掉 add 之前发生的创建事件；标准解法是「add 完成后立刻 rescan 该目录一次」，习题 19-1 正是这么处理。

19.5

Queue Limits and /proc Files 队列限制与 /proc 文件

本章：TLPI 第 19 章 — Monitoring File Events ⚠️ Linux 专有；macOS 无此接口与这些 sysctl。源码按 man-pages 6.19 inotify(7)（Queue Limits 段）+ Linux v6.6 fs/notify/inotify/inotify_user.c（溢出逻辑）+ Documentation/sysctl/fs.rst 核验；三个 knob 的实际默认值随内核/发行版而异，以目标机 /proc 实测为准（Pi5 复测清单） - 上一节：19.4 Reading inotify Events - 下一节：19.6 dnotify

本节讲什么

  1. 三个 sysctl knob 分别限制什么（队列长度 / 实例数 / watch 数）；
  2. 队列溢出的确切语义：丢事件 + IN_Q_OVERFLOW——不可恢复，必须重建；
  3. 为什么「事件循环做重活」是这个节失败的第一原因；
  4. 生产上的容量规划方法。

要点：三个 sysctl

/proc/sys/fs/inotify/… 限制什么 常见默认 超限错误
max_queued_events 单实例事件队列长度（内核排队上限） 16384 不报错——静默丢事件，队列里补一条 IN_Q_OVERFLOW
max_user_instances 每真实用户可建的 inotify 实例数 128 inotify_init1 → EMFILE
max_user_watches 每真实用户挂的 watch 总数 8192（发行版常调到几十万） inotify_add_watch → ENOSPC

读写方式与所有 sysctl 相同（open+write，Ch12 的坑同样适用——写完回读验证）：

cat /proc/sys/fs/inotify/max_user_watches
sudo sysctl fs.inotify.max_user_watches=524288     # 或直接 echo > /proc/...

⚠️ 默认值不是 API 契约：不同内核/发行版差异很大（尤其 max_user_watches，桌面发行版常已调大）。容量规划读 /proc，别写死数字。

要点：溢出的确切语义（本节最重要的一段）

事件产生速率 > 应用消费速率
        ↓
内核队列填满 max_queued_events 条
        ↓
再来的事件【被丢弃】，同时往队列尾追加一条 IN_Q_OVERFLOW（wd == -1）
        ↓
应用读到 IN_Q_OVERFLOW → 唯一正确反应：全量 rescan + 重建 watch 集合

三个必须钉住的点：

  1. 静默丢：溢出不返回错误、不 EMFILE——应用不处理 IN_Q_OVERFLOW 就是「丢事件而不自知」，监控状态从此与文件系统失同步；
  2. 丢多少不知道：溢出事件只告诉你「发生过溢出」，不告诉你丢了哪些；增量修补不可能，只能重建；
  3. 重建的正确姿势：先 rm 全部 watch（或干脆废弃实例重建一个），再 nftw 全量扫一遍树重建 watch 集合（习题 19-1 的结构）——重建期间的变更由扫描本身兜住。

要点：为什么队列会满（三个根因）

根因 机理 缓解
事件循环做重活 处理一条事件花 50 ms，产生速率 100/s → 队列 5 s 塞满 重活丢线程池；循环只分派
订阅了高频事件 IN_MODIFY 对大文件流式写是每次 write 一条 只订阅必要的写侧事件（IN_CLOSE_WRITE）
watch 太多、目录太热 IN_ATTRIB 在 atime/ctime 变更时也触发（含读！） 按需订阅；IN_EXCL_UNLINK 去临时文件噪音

要点：容量规划速查

/* 事件量级估算（设计期做，不是运行期猜）：
 *   行情落盘目录：每秒 N 个文件 × 每 3 事件（CREATE/MOVED_TO/CLOSE_WRITE）
 *   = 3N 事件/秒。N=1000 → 3000/s。
 *   若消费循环最坏停顿 T 秒，队列需 ≥ 3000×T。
 *   T 由「重活最大时长」决定——这再次说明重活必须异步。*/
参数 经验值
单实例队列 默认 16384，多数场景够；批处理停顿 > 5 s 就要调大或改设计
watch 数 目录树规模 × 1.2 余量；max_user_watches 不足时 ENOSPC 是清晰错误，可捕获后降级为轮询
实例数 每进程 1~2 个；容器里注意 max_user_instances 是每用户全局的（同 uid 的所有容器共享）

常见坑

坑 正解
不处理 IN_Q_OVERFLOW 丢事件不自知；收到就全量重建（没有中间态）
用 EMFILE/ENOSPC 之外的方式判断溢出 溢出不报错；唯一信号就是那条 overflow 事件

代码自测（Q&A）

Q1：溢出后为什么不选择「丢弃一半旧事件、保留新的」这类增量策略？ A：因为丢了什么不可知——可能是「目录被删」这样改变结构的事件，增量修补的假设已失效。全量重建（rescan + 重挂 watch）是唯一能证明「状态与文件系统一致」的操作，且实现简单、无死角。

Q2：max_user_watches 超限的 ENOSPC 和磁盘满的 ENOSPC 怎么区分？ A：来源不同——inotify_add_watch 返回的 ENOSPC 是 watch 配额；write 返回的是磁盘。errno 无处标注来源，靠调用点区分。应用日志里应写明「add_watch 的 ENOSPC（watch 配额）」。

Q3：事件队列是每个 inotify 实例一个，还是每个 watch 一个？ A：每实例一个。实例内所有 watch 的事件混排在同一队列里（§19.4 的一次 read 混排多 watch 事件就是这个原因）。

Q4：IN_Q_OVERFLOW 占不占队列长度？ A：占。溢出时内核先丢新事件，再把 overflow 事件排进队尾——如果队列当时满到连 overflow 都放不下，会先腾出位置。所以 overflow 保证可达（这正是它的设计目的），但不保证及时。

Q5：max_user_instances 按「真实用户」统计是什么意思？ A：按 real UID 计（fsnotify 的成本计费对象）。同一 uid 下 root 运行的所有服务、所有容器共享 128 的额度；互相挤兑时后建的 inotify_init1 直接 EMFILE。多服务同机部署要预算或调大。

Q6：怎么在不改 sysctl 的前提下降低队列压力？ A：三招：① 收窄 mask（去掉 IN_ACCESS/IN_OPEN 这类高频读侧事件）；② IN_EXCL_UNLINK 去临时文件噪音；③ 消费提速——批量 read + 重活异步。三者都是应用层改动，比调内核参数可控得多。

19.6

An Older System for Monitoring File Events: dnotify 旧一代监控（dnotify）

本章：TLPI 第 19 章 — Monitoring File Events ⚠️ Linux 专有且已淘汰（F_NOTIFY 自 2.4 起、被 inotify 取代）。源码按 man-pages 6.19 fcntl(2)（F_NOTIFY/DN_* 段）+ TLPI dist inotify/dnotify.c（官方演示程序，逐字镜像于本目录 code/dnotify.c）核验；本机无此接口未实测，Pi5 复测清单见章 README - 上一节：19.5 Queue Limits and /proc Files - 下一节：19.7 Summary

本节讲什么

dnotify 不是「inotify 的前身那么简单」——它是理解「为什么事件接口必须 fd 化」的反面教材：

  1. fcntl(fd, F_NOTIFY, mask)：对已打开的目录 fd 订阅事件，通知以信号送达；
  2. 三大硬伤：信号通知、不带文件名、fd 钉住目录；
  3. 官方镜像 dnotify.c 演示全部要点（含 F_SETSIG 用 realtime 信号的增强写法）。

要点：接口与事件

#include <fcntl.h>
int fcntl(int dirfd, F_NOTIFY, int bitmask);   /* dirfd 必须是 O_RDONLY 打开的目录 */
/* 位：DN_ACCESS DN_MODIFY DN_CREATE DN_DELETE DN_RENAME DN_ATTRIB
 * 修饰：DN_MULTISHOT（默认一次性！要持续通知必须加）| DN_DELETE 是 DN_* 之一 */
项 语义
通知方式 默认发 SIGIO；配合 F_SETSIG 可换成指定信号（realtime 信号可排队，见下）
DN_MULTISHOT 默认是一次性——首个事件后自动清掉订阅；持续监控必须置位
作用范围 只目录：报告该目录的直接子项变更（不递归，与 inotify 同）
继承 经 fork 继承；经 exec 保留（除非目录 fd 被 CLOEXEC 处理）
取消 fcntl(fd, F_NOTIFY, 0) 或关闭 fd

要点：三大硬伤（inotify 逐条修复的对象）

硬伤 后果 inotify 的回答
① 信号通知 处理器是异步的；标准信号会合并（两次修改只收到一次）；处理器里能做的事受限（async-signal-safe） 事件进 fd 队列：可 read、可 poll/epoll、不丢不乱
② 不带文件名 只知道「这目录有变动」，想知道谁变了必须 rescan 整个目录 再 diff inotify_event.name 直接给名字
③ 每目录一个 fd 且钉住目录 fd 泄漏即目录泄漏；被监控目录无法卸载（umount 报 EBUSY）；大量目录监控 fd 耗尽 实例 + 轻量 watch 记录，无此问题

① 的半解：F_SETSIG 换成 SIGRTMIN 系 realtime 信号 + SA_SIGINFO——realtime 信号可排队（不合并），且 siginfo_t.si_fd 带来事件的目录 fd。这就是官方 dnotify.c 用的写法。但它仍然是信号：处理器里只能把信息转投队列（self-pipe / signalfd），复杂度全转移到应用。

② 的代价量化：目录里有 10 万文件时，「谁变了」的 rescan 是 O(目录大小)——每事件 10 万次 readdir/lstat，监控变成了 DoS 自己。

要点：官方演示程序 code/dnotify.c 的骨架

#define _GNU_SOURCE          /* DN_* 常量在 <fcntl.h>，需 _GNU_SOURCE */
#include <fcntl.h>

/* 用法（源码头注释）： dnotify dir1:a xyz/dir2:acdM
 *   目录:标志串 —— a=DN_ATTRIB c=DN_CREATE d=DN_DELETE M=DN_MULTISHOT … */
for (每个 "dir:flags" 参数) {
    int fd = open(dir, O_RDONLY);
    fcntl(fd, F_SETSIG, SIGRTMIN);          /* 换 realtime 信号（增强）*/
    fcntl(fd, F_NOTIFY, flags | DN_MULTISHOT);  /* 订阅 + 持续模式 */
}
/* 然后 sigwaitinfo / 信号处理器里读 siginfo->si_fd 找出是哪个目录 */

它同时是「realtime 信号 + F_SETSIG + si_fd」三件套的教学样本——这套机制在 inotify 出现前是 Linux 异步 I/O 的通用底座。

要点：读旧代码时的对照表

dnotify 时代 inotify 时代
open(dir,O_RDONLY) + fcntl(F_NOTIFY) inotify_add_watch(ifd, dir, mask)
DN_CREATE IN_CREATE
DN_DELETE IN_DELETE（+ 目录自身 IN_DELETE_SELF）
DN_RENAME IN_MOVED_FROM/IN_MOVED_TO（+ cookie 配对）
DN_ATTRIB IN_ATTRIB
DN_ACCESS/DN_MODIFY IN_ACCESS/IN_MODIFY
DN_MULTISHOT 默认持续（IN_ONESHOT 才是一次性——语义反转）
F_SETSIG + realtime 信号 普通 fd + read/epoll

语义反转陷阱：dnotify 默认一次性（要 DN_MULTISHOT 才持续）；inotify 默认持续（要 IN_ONESHOT 才一次性）。从 dnotify 迁移的代码若按旧直觉「忘了加持续位」，行为反而更持久——这类迁移 bug 是静默的。

常见坑

坑 正解

代码自测（Q&A）

Q1：dnotify 为什么把通知绑在「目录 fd」上而不是路径？ A：实现简单：内核在 inode 的写操作点检查「有没有人 F_NOTIFY 过这个目录」，fd 就是订阅句柄。但这决定了它的三个结构性缺陷（信号通知、无文件名、fd 钉目录）——改进它等于重新设计接口，所以直接诞生了 inotify。

Q2：realtime 信号真的「不丢」吗？ A：在排队范围内不合并也不丢，但队列本身有限（RLIMIT_SIGPENDING），超限后仍丢。dnotify 时代它比标准信号好得多，但「丢事件」的根本问题要等事件进 fd 队列（inotify）才解决。

Q3：为什么说 dnotify 的「无文件名」在理论上可以弥补？ A：si_fd 能定位到目录，配合 rescan 可以知道目录现状；缺的是「变更集」。理论上有应用靠「每次 rescan + 与上次快照 diff」运行——功能等价但成本 O(目录)，等于退回轮询，只是轮询的触发点由事件提供。

Q4：dnotify 能监控「目录树」吗？ A：和 inotify 一样不递归，但给每个子目录挂 watch 的成本更高（每目录一个 fd，还会钉住所有目录无法卸载）。大规模树监控在 dnotify 时代基本不可行。

Q5：F_NOTIFY 的订阅会被 exec 清掉吗？ A：订阅随目录 fd 走；exec 不清（fd 属性继承），但如果 fd 带 FD_CLOEXEC 则 exec 后 fd 关闭、订阅随之消失。旧代码常忘记这一点，导致 exec 子进程后的监控行为差异。

Q6：现在还有理由用 dnotify 吗？ A：只有一种：维护必须在极老内核（无 inotify）上运行的代码。即便如此，新代码也应编译期探测 inotify 可用性并优先使用。教学价值（理解信号驱动接口的缺陷）大于工程价值。

必须钉住的六条纪律

  1. watch 不递归：IN_CREATE|IN_ISDIR（和 IN_MOVED_TO|IN_ISDIR）时补 watch，并立即 rescan 该目录补漏；
  2. watch 挂 inode：监控「会被 safe-write 替换的文件」必失效——监控目录；
  3. 读循环先判系统级事件（IN_Q_OVERFLOW→全量重建；IN_IGNORED→清映射），再进业务；
  4. 重活异步：事件循环只分派，否则队列溢出只是时间问题（§19.5）；
  5. 改名降级安全：把 MOVED_FROM/TO 处理成「删+建」永远正确，把「删+建」凑成改名是危险升级；
  6. 跨平台红线：macOS 无 inotify；抽象层按 kqueue/FSEvents 的最小公倍数设计，cookie 配对与溢出语义不可假设对齐。

代码自测（Q&A）

Q1：inotify 编程「真正难」的地方在哪？ A：不在 API（三个 syscall 一页纸），在一致性：事件流是异步的、有延迟的、可能丢的，而应用维护的状态必须与文件系统一致。inotify_dtree.c 给出的答案是「事件驱动 + 定期校准 + 溢出全量重建」的混合模式——这是所有事件驱动缓存（不止文件系统）的通用架构。

Q2：为什么说「批量 read + 重活异步」是同一枚硬币的两面？ A：批量 read 降低的是「消费一条事件」的固定成本；重活异步降低的是「消费一条事件」的可变成本。队列长度（§19.5）限制的是平均消费速度——两者任何一头不到位，队列都会满。

Q3：迁移自 dnotify 的代码最容易犯什么错？ A：语义反转（一次性 vs 持续）与「文件名缺失」——旧代码习惯 rescan，新代码看到 name 反而忘了处理 MOVED_FROM/TO 配对，把改名当成删除+创建处理时又没做降级（丢 cookie 检查）。

Q4：监控「目录树」的正确架构是什么？ A：三层：① nftw 初始挂 watch（每目录一个）；② 事件循环里 IN_CREATE|IN_ISDIR/IN_MOVED_TO|IN_ISDIR 补 watch（add 后立即 rescan 该目录补漏）；③ IN_DELETE_SELF/IN_IGNORED 清理。习题 19-1 与 inotify_dtree 都是这个结构。

Q5：为什么 inotify 没有被 fanotify 取代？ A：两者定位不同：inotify 是进程级的细粒度通知（面向应用）；fanotify 是系统级的文件访问控制/通知（面向安全软件，需要特权，能拦截而非仅观察）。后续还有 eBPF（kprobe vfs 读写）做更深的观测。工具箱是加法不是替换。

Q6：如果 macOS 版本也要做配置热重载，怎么对齐语义？ A：kqueue EVFILT_VNODE（NOTE_WRITE/NOTE_RENAME/NOTE_DELETE）无 name、无 cookie、无溢出事件——只能监控具体文件或靠 rescan。工程做法：抽象层只承诺「有变更」+ 自己 diff；改名配对、溢出重建这些 inotify 独有能力在 macOS 侧降级为全量校验。

题面（转述）：写程序记录命令行给定目录下所有文件的创建、删除与改名。必须监控该目录下所有子目录（用 nftw() 枚举，§18.9）；当树里新建或删除子目录时，监控集合要相应更新。

四个设计要点（与题面逐条对应）：

题面要求 实现机制
监控所有子目录 nftw(FTW_PHYS) 枚举，回调里只对 FTW_D/FTW_DP add_watch（FTW_PHYS 防止链接指向的树外目录被误监控，Ch18 §18.9 实测过不加它的后果）

实现里三个值得单独记的点：

代码自测（Q&A）

Q1：为什么「add_watch 后立即 rescan」能保证不漏？ A：add_watch 是时间点 T2，mkdir 发生在 T1 < T2，窗口内 (T1,T2) 的变更没有事件。rescan 在 T3 > T2 执行，它看到的目录状态是 T3 时的全集——包含窗口内创建的一切。只要「扫描成本」可接受，这个「事件 + 一次性快照」的组合就是完备的。

Q2：如果 rescan 与事件处理并发（多线程），会怎样？ A：可能乱序（扫描结果晚于事件到达）。inotify_dtree 的做法是单线程事件循环 + 扫描也在同一循环内排队——顺序性是状态一致性的前提，宁可慢不可乱。

Q3：IN_MOVED_TO|IN_ISDIR 的新目录也要 rescan 吗？ A：要。rename 进来的目录可能内部已有内容（甚至刚在别处建好整棵子树），add_watch 只看顶层。更严谨的做法是对新目录再跑一次 nftw 把整棵子树都挂上 watch。

Q4：本题为什么订阅 IN_DELETE_SELF/IN_MOVE_SELF 却说靠 IN_IGNORED 兜底？ A：这两个事件告诉你「为什么」失效（语义），IN_IGNORED 告诉你「现在可以清了」（生命周期）。清理动作放在 IN_IGNORED 分支最安全——它保证是最后一条该 wd 的事件，清理后不会再有孤儿。

Q5：这题与 find/inotifywait（inotify-tools）功能重叠吗？ A：重叠，但本题练的是「动态 watch 集合维护」这个通用模式——它同样适用于 kqueue（macOS）、fanotify、甚至自己封装的变更通知服务。工具是结果，模式是可迁移的能力。

Q6：生产版还要补什么？ A：① 溢出重建（nftw 全量）；② 日志结构化（JSON：mask/cookie/路径/时间戳）；③ 平滑退出（信号处理里 inotify_rm_watch + 释放映射）；④ 与上层状态机对接（去重：CREATE 后紧跟 MOVED_FROM 同名是编辑器原子保存模式）。
