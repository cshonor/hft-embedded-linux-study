2.1

内核（Kernel）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（arch/x86/entry/syscall_64.c、include/linux/types.h、fs/namei.c） - 上一节：本章首页 - 下一节：2.2 Shell

本节讲什么

内核是操作系统中始终驻留内存、掌握全部硬件的核心部分。本节回答三个问题：

  1. 内核是什么？宏内核和微内核差在哪，Linux 为什么选宏内核？
  2. 「用户态 / 内核态」到底是什么？程序凭什么只能通过系统调用进入内核？
  3. glibc 库函数和系统调用是什么关系？为什么 man 2 和 man 3 要分开？

原书把「内核」和「用户态/内核态/系统调用」连在一起讲，本节合并为一篇，把「内核边界」这个抽象落到 sys_call_table 上，为后面所有系统调用学习打底。

1. 内核是什么

职责 说明 HFT/嵌入式视角
CPU 调度 决定哪个任务占用 CPU、上下文切换 实时调度策略 SCHED_FIFO（见 2.18）
内存管理 虚拟地址空间、页表、换页、mmap mlockall 防换页毛刺（见 2.18）
文件系统 VFS 抽象层，对接 ext4/proc 等 /proc 虚拟文件系统（见 2.19）
设备驱动 磁盘、网卡、串口…… 网卡驱动零拷贝是延迟关键
网络协议栈 TCP/IP、socket 层 行情/下单的网络通路
安全 权限检查、capabilities、namespace 最小权限部署

内核代码编译成 vmlinux（可启动镜像），驱动可以编进内核，也可以动态加载为 .ko 模块（insmod/modprobe）。

2. 宏内核 vs 微内核

架构 内核态放什么 特点 代表
宏内核（monolithic） 调度、驱动、FS、网络全在内核态 性能高，但一处崩溃拖垮全系统 Linux、Unix
微内核（microkernel） 只留 IPC + 调度，驱动跑用户态 更安全/隔离好，但 IPC 开销大、慢 QNX、MINIX
混合内核 折中 兼顾 Windows NT、macOS XNU

Linux 选宏内核是为性能：系统调用直接陷入内核处理，没有微内核那种「用户态服务进程 ↔ 内核」的额外 IPC 消息往返。代价是内核态代码量大、驱动 bug 可能 panic 整个系统——所以嵌入式才需要「内核裁剪」（make menuconfig 只保留用得到的子系统）。

3. 用户态 vs 内核态

┌─────────────────────────────────────────┐
│ 用户态 (User Space)    ring 3 (x86) / EL0 (ARM) │
│  应用程序 + glibc，权限受限，不能直接碰硬件   │
│        │  syscall 指令（主动陷入）          │
│        ▼  （中断/异常也会切换）             │
│ 内核态 (Kernel Space)  ring 0 (x86) / EL1 (ARM) │
│  内核代码 + 驱动，特权模式，可访问任何内存    │
└─────────────────────────────────────────┘
  • 用户态：CPU 处于低特权级（ring 3 / EL0），不能执行特权指令、不能直接访问硬件端口、不能读写内核内存。
  • 内核态：CPU 处于最高特权级（ring 0 / EL1），任何指令、任何内存都可访问。
  • 切换：用户程序通过 syscall（x86-64）或 svc（AArch64）指令主动陷入内核；硬件中断、缺页异常也会强制切换。

关键认知：用户态和内核态共享同一个虚拟地址空间（Linux 设计），内核占据高地址段（0xffff...），用户态占据低地址段，两者被页表权限隔离。所以系统调用不需要切换页表（省了 TLB 刷新），只是 CPU 特权级变化——这也是 Linux 系统调用快的原因之一。

4. 系统调用：进入内核的「唯一正规入口」

用户程序想干活（读文件、fork、mmap），只能通过系统调用。x86-64 的完整链路：

C 代码 write(1, "hi", 2)
      │  glibc 封装：把参数塞寄存器，rax = syscall 号
      ▼
syscall 指令（用户态 → 内核态，CPU 特权级切换）
      │  内核入口读 rax 得到系统调用号（如 write=1）
      ▼
sys_call_table[nr] 查表分发        arch/x86/entry/syscall_64.c:16
      ▼
__x64_sys_write(...)              内核态真正干活
      ▼
返回用户态，继续执行

系统调用号是固定的 ABI，写在 arch/x86/entry/syscalls/syscall_64.tbl：

系统调用号 名字 内核实现
0 read sys_read
1 write sys_write
2 open sys_open
9 mmap sys_mmap
57 fork sys_fork
228 clock_gettime sys_clock_gettime
257 openat sys_openat

内核用这张表把「用户态传来的号码」映射到「内核函数」：

/* arch/x86/entry/syscall_64.c:16 —— 系统调用分发表 */
asmlinkage const sys_call_ptr_t sys_call_table[] = {
#include <asm/syscalls_64.h>   /* 展开成 [0]=__x64_sys_read, [1]=__x64_sys_write, ... */
};

5. glibc 的角色：库函数 ≠ 系统调用

glibc 是用户态和系统调用之间的「翻译层」：

类型 例子 是否进内核
薄封装（一次 syscall） open/read/write/fork ✅ 直接陷入
多层封装（缓冲 + syscall） fopen/fread/printf ✅ 内部调 open/read/write
纯用户态（不进内核） strcpy/atoi/strlen/memcpy ❌ 零系统调用

区分方法：man 2 = 系统调用，man 3 = 库函数。有些函数是「薄封装」只做一次 syscall，有些是「纯用户态」根本不进内核，还有些是「多层」会做多次 syscall（如 printf 触发 write）。这是排查「热路径为什么有这么多 syscall」的基本功。

6. HFT / 嵌入式关联

现象 本节机制的兑现
每次系统调用都有陷入开销 模式切换 + 保存现场 + 权限校验，约数百 ns；热路径要少 syscall
逐字节 read 是灾难 n 字节 = n 次上下文切换；批量 read(fd, buf, n) 只 1 次
mmap 免系统调用 把文件/设备映射进用户态地址空间，后续读写直接访存（见 2.8）
io_uring 异步批量提交 减少 syscall 往返，高性能 I/O 首选
嵌入式内核裁剪 make menuconfig 只留必要驱动/子系统，减小内核体积与攻击面
vDSO 免陷入 clock_gettime/gettimeofday 走 vDSO，用户态直接读内核映射的只读数据，不切换特权级

7. 代码示例

#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <string.h>

int main(void) {
    /* 直接写：glibc 封装 write() → syscall 指令 */
    write(STDOUT_FILENO, "hello via write()\n", 18);

    /* 绕过 glibc，用 syscall() 直接发系统调用（通常不需要这么做） */
    const char *msg = "hello via syscall()\n";
    syscall(SYS_write, STDOUT_FILENO, msg, strlen(msg));

    /* 纯用户态：strlen 不进内核 */
    size_t n = strlen(msg);
    printf("strlen (纯用户态) = %zu\n", n);
    return 0;
}

编译运行后用 strace -c ./a.out 统计系统调用次数——你会看到 write 出现多次，而 strlen/printf 的内部 write 也能被 strace 看到（printf 有缓冲，最后才 write）。这是「库函数 vs 系统调用」最直观的验证。

代码自测（Q&A）

Q1：宏内核和微内核的本质区别是什么？Linux 为什么选宏内核？ A：区别在「驱动/文件系统/网络跑在哪」：宏内核全部塞进内核态，微内核只留 IPC+调度、其余跑用户态。Linux 选宏内核是为性能——系统调用直接陷入内核处理，没有微内核「用户态服务进程↔内核」的额外 IPC 往返。代价是内核代码量大、驱动 bug 可能 panic 全系统，所以嵌入式要靠 make menuconfig 裁剪内核。

Q2：用户态和内核态运行在同一个地址空间吗？系统调用要切换页表吗？ A：是同一个地址空间（Linux 虚拟内存模型）：内核占高地址段、用户态占低地址段，靠页表权限隔离。所以系统调用不需要切换页表（不用刷新 TLB），只是 CPU 特权级从 ring 3/EL0 升到 ring 0/EL1。这是 Linux 系统调用快于部分其他 OS 设计的原因之一。

Q3：系统调用号（如 write=1）是怎么变成内核函数的？ A：内核维护一张 sys_call_table[]（arch/x86/entry/syscall_64.c:16），下标就是系统调用号。用户态 syscall 指令陷入后，内核入口从 rax 读号码，然后 sys_call_table[nr] 查到对应的 __x64_sys_write 等实现。号码是固定 ABI（写死在 syscall_64.tbl），不能乱改，否则破坏用户态兼容。

Q4：fopen、write、strlen 三者谁是系统调用？ A：只有 write 是系统调用（man 2，glibc 薄封装、直接陷入）。fopen 是库函数（man 3，内部调用 open 系统调用 + 建立缓冲），strlen 是纯用户态函数（不进内核）。区分靠 man 2（syscall）vs man 3（库函数）。

Q5：为什么 HFT 热路径要「尽量少系统调用」？有哪些替代手段？ A：系统调用要模式切换 + 保存现场 + 权限校验，约数百 ns，对微秒级敏感路径不可忽略。替代：① mmap 把文件/设备映射进用户态，后续直接访存；② 批量 I/O（一次 read/write 传大数据）；③ io_uring 异步批量提交；④ 高频计时用 vDSO（clock_gettime 不进内核）。核心原则：把 N 次小 syscall 合并成 1 次大操作。

Shell

本章：TLPI 第 02 章 — Fundamental Concepts - 上一节：2.1 内核（Kernel） - 下一节：2.3 用户与组（Users and Groups）

本节讲什么

Shell 是「用户与内核之间的命令行解释器」。本节回答三个问题：

  1. Shell 是内核的一部分吗？它的核心循环是什么？
  2. 内置命令（builtin）和外部命令有什么区别？system() 为什么危险？
  3. Shell 的「作业控制」和前面讲的进程组/会话有什么关系？

1. Shell 的本质：一个普通用户态进程

Shell 不是内核的一部分，它只是一个跑在用户态的程序（/bin/bash、/bin/dash 等），做的事就是循环：

/* shell 核心循环（极度简化） */
while (1) {
    printf("$ ");                        /* 打印提示符 */
    if (fgets(cmd, sizeof(cmd), stdin) == NULL) break;  /* 读一行命令 */

    pid_t pid = fork();                  /* ① fork 出子进程 */
    if (pid == 0) {
        execvp(argv[0], argv);           /* ② 子进程 exec 成目标程序 */
        perror("execvp"); _exit(127);    /* exec 失败才走到这 */
    }
    waitpid(pid, &status, 0);            /* ③ 父进程等待子进程结束 */
}

「读命令 → fork → exec → wait」就是 shell 的全部秘密。每敲一条外部命令，就 fork 一个新进程 + exec 掉它——这也是「为什么 shell 里循环启动进程有开销」的根源。

2. 常见 Shell 与「内置 vs 外部」

Shell 路径 特点
bash /bin/bash GNU 默认，功能最全
dash /bin/dash Debian/Ubuntu 轻量，/bin/sh 常软链到它
zsh /usr/bin/zsh 交互补全强
fish /usr/bin/fish 现代，非 POSIX 兼容（脚本会跑挂）

内置命令 vs 外部命令是关键区分：

类型 例子 是否 fork
内置命令（builtin） cd、export、echo(bash)、ulimit ❌ 不 fork，直接改 shell 自身状态
外部命令 ls、grep、cat ✅ fork + exec 子进程

cd 必须是内置命令——因为它要改的是 shell 进程自己的工作目录；若 fork 子进程去 chdir，改的是子进程、父 shell 的工作目录根本不变。同理 ulimit 改的是 shell 的 rlimit。

3. system()：隐式的 /bin/sh -c

C 程序里执行 shell 命令用 system()，但它是隐式 fork 三层：

system("ls -l");
/* 等价于： fork → execl("/bin/sh", "sh", "-c", "ls -l", NULL) → waitpid */
隐患 说明
阻塞 system() 会 wait，调用线程卡住直到命令结束
信号干扰 期间 SIGINT/SIGQUIT 被屏蔽，SIGCHLD 被忽略，容易漏处理
命令注入 拼接字符串传给 sh -c，用户输入含 ;/$() 即被解析执行
依赖 /bin/sh 不同系统 /bin/sh 指向不同（bash/dash），行为可能不同

所以：生产代码里能用 fork+exec+wait 就别用 system()，尤其别把不可信输入拼进 system() 字符串。

4. Shell 的作业控制

Shell 之所以能实现 Ctrl+C 杀整条管道、Ctrl+Z 挂起、fg/bg 切换，靠的是它作为「会话首领 + 前台进程组管理者」的身份：

  • shell 启动时是会话首领，拥有控制终端（见 2.14）
  • 每条管道命令放进一个进程组（见 2.13）
  • Ctrl+C → 终端驱动给前台进程组发 SIGINT
  • Ctrl+Z → 发 SIGTSTP，shell 把该组移到后台，打印 [1]+ Stopped
  • fg/bg → shell 调 tcsetpgrp() 切换前台进程组 + 发 SIGCONT

所以「作业控制」本质是 shell 对进程组 + 会话这两套内核机制的编排，不是 shell 自创的魔法。

5. HFT / 嵌入式关联

现象 本节机制的兑现
启动编排 shell 脚本负责拉起/重启交易进程、设置环境变量、ulimit（RLIMIT_MEMLOCK、NOFILE）

6. 代码示例

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

/* 手动实现 system() 的安全替代：fork + exec + wait */
int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s <cmd> [args...]\n", argv[0]); return 1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }

    if (pid == 0) {
        execvp(argv[1], &argv[1]);   /* 子进程 exec 成目标程序 */
        perror("execvp");
        _exit(127);
    }

    int status;
    waitpid(pid, &status, 0);        /* 父进程等待 */
    if (WIFEXITED(status))
        printf("exit=%d\n", WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("killed by signal %d\n", WTERMSIG(status));
    return 0;
}

编译运行：gcc -o run run.c && ./run ls -l。对比 system("ls -l") 的差异——这里你可以精确控制「要不要等」「怎么处理信号」「传参不用拼字符串」，避免注入。

代码自测（Q&A）

Q1：Shell 是内核的一部分吗？它的核心循环是什么？ A：不是。Shell 是普通用户态进程（/bin/bash 等），核心循环是「读命令 → fork → exec → wait」四步。每执行一条外部命令就 fork 一个新进程、exec 成目标程序，父 shell 等待其结束。

Q2：为什么 cd 必须是内置命令，不能是外部命令？ A：因为 cd 要改的是 shell 进程自己的当前工作目录（chdir）。若做成外部命令，fork 出的子进程执行 chdir 只改子进程的工作目录，父 shell 的目录不变——命令返回后「什么都没发生」。同理 export（改环境）、ulimit（改 rlimit）都必须是内置命令。

Q3：system("ls -l") 背后发生了什么？为什么说它危险？ A：它隐式执行 fork → execl("/bin/sh", "sh", "-c", "ls -l", NULL) → waitpid 三步。危险在于：① 阻塞当前线程直到命令结束；② 若命令字符串由用户输入拼接，会被 sh 解析执行（命令注入，如 "; rm -rf /"）；③ 期间信号处理被扰动。生产代码应改用 fork+exec+wait。

Q4：Ctrl+C 能杀掉一条管道里的所有命令，是 shell 的魔法吗？ A：不是魔法，是「进程组」机制。shell 把 ls | grep | wc 这条管道里的进程放进同一个进程组（前台进程组），Ctrl+C 时终端驱动向该组广播 SIGINT，整组全收（见 2.13）。shell 只是编排者，机制来自内核的进程组/会话。

Q5：脚本里 for 循环调几百次外部命令，为什么慢？怎么优化？ A：每次外部命令都要 fork + exec 一个新进程（创建进程 + 加载程序 + 复制页表），几百次循环就是几百次进程创建开销。优化：① 用 shell 内置命令/参数展开替代循环外部命令；② 用 xargs 批量；③ 把循环逻辑写进单个 awk/sed/python 进程一次处理；④ 对性能敏感的编排改用编译型程序。

用户与组（Users and Groups）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（include/linux/types.h、fs/namei.c） - 上一节：2.2 Shell - 下一节：2.4 单根目录树（Directory Hierarchy）

本节讲什么

Linux 的权限模型建立在「用户（UID）与组（GID）」之上。本节回答三个问题：

  1. UID/GID 是什么？内核用什么类型存它们？root 为什么是 0？
  2. 内核在「打开文件」那一刻，权限检查的完整流程是什么？
  3. real/effective/saved UID 三种身份为什么要分开？

完整 API 在 Ch8/Ch9，这里建立「权限 = UID/GID 逐位比对」的核心心智。

1. 用户与组的基本概念

概念 说明
UID 用户 ID，root 的 UID = 0
GID 主组 ID，用户登录时的默认组
补充组（supplementary groups） 用户可同时属于多个组，额外权限来源
/etc/passwd 用户名 ↔ UID/GID 映射（密码字段已移走）
/etc/shadow 密码哈希（只有 root 可读）
/etc/group 组名 ↔ GID 映射

内核并不关心「用户名」字符串，只认数字 UID/GID。用户名 → UID 的解析是用户态库（glibc/NSS）通过读 /etc/passwd 完成的。内核侧类型是 32 位无符号整数：

/* include/linux/types.h:37-38 */
typedef __kernel_uid32_t    uid_t;
typedef __kernel_gid32_t    gid_t;

2. 权限检查：进程凭证 vs 文件权限位

内核在「打开文件」这类操作时，拿进程的凭证和文件的 owner/group/mode 位做比对。核心在 fs/namei.c 的 generic_permission（:400）：

进程想 open("/etc/passwd", O_RDONLY)
      │
      ▼
内核拿 inode 的 mode 位（owner/group/other 三组 rwx）
      │
      ▼ 先查 ACL（acl_permission_check）
      ▼ 查普通权限：进程的 fsuid/fsgid 与 inode 的 uid/gid 逐级匹配

三种匹配顺序（每个文件有 owner/group/other 三组权限位）：

进程身份 用哪组权限位 说明
进程 fsuid == 文件 uid owner 位 文件属主
进程属于文件所在组 group 位 主组或补充组匹配
其他情况 other 位 兜底

顺序是「命中即停」：owner 匹配了就不再往下看 group/other。所以文件属主自己可能比「other」权限还低（如 owner 只读、other 可写）——这是常见反直觉坑。

root（或带 CAP_DAC_OVERRIDE 能力）可以绕过 DAC 权限位检查（generic_permission 里的 capable_wrt_inode_uidgid(..., CAP_DAC_OVERRIDE)），但不是无限制——仍受 SELinux/AppArmor（MAC）约束。

3. 三种 UID：real / effective / saved

权限检查用的不是单一的 UID，而是三份（完整在 Ch9）：

身份 全称 用途
real UID 真实 UID 进程「真正是谁」（登录用户）
effective UID 有效 UID 权限检查用这个（决定能访问什么）
saved set-UID 保存的设置 UID 用于「临时降权后恢复」

普通进程三者相同；set-user-ID 程序（passwd、sudo）的 effective UID 会被设为文件属主（通常是 root），从而获得临时特权。这引出一个关键安全原则：特权程序要尽快把不需要的特权永久降掉（setuid 丢弃 saved UID），用 seteuid 只做临时下放（可恢复）——详见 Ch9/Ch38。

4. HFT / 嵌入式关联

现象 本节机制的兑现
交易进程最小权限 用独立 trading 用户 + 专属组运行，不跑 root，减少被攻破后的破坏面
端口 <1024 需要特权 绑 80/443 需 root 或 CAP_NET_BIND_SERVICE（见 Ch39），交易端口一般 >1024 免特权
setuid 程序风险 交易系统的 setuid 程序要慎之又慎——effective UID 提权是注入攻击的常见目标
配置文件权限 策略文件/密钥文件用 chmod 600 + 属主隔离，靠 owner 位保护
共享内存/锁文件权限 跨进程 IPC（shm/FIFO）的 mode 位决定哪些用户可读写，部署时须显式设置

5. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>

int main(void) {
    uid_t ruid, euid, suid;
    gid_t rgid, egid, sgid;

    /* 三种 UID 和 GID */
    getresuid(&ruid, &euid, &suid);
    getresgid(&rgid, &egid, &sgid);
    printf("uid: real=%d effective=%d saved=%d\n", ruid, euid, suid);
    printf("gid: real=%d effective=%d saved=%d\n", rgid, egid, sgid);

    /* 补充组 */
    int ngroups = getgroups(0, NULL);
    gid_t *groups = malloc(ngroups * sizeof(gid_t));
    getgroups(ngroups, groups);
    printf("supplementary groups: %d\n", ngroups);

    /* 权限检查：effective UID 决定能 open 什么 */
    int fd = open("/etc/shadow", O_RDONLY);   /* 非 root 会 EACCES */
    if (fd < 0)
        perror("open /etc/shadow");            /* Permission denied */

    free(groups);
    return 0;
}

运行：普通用户跑会看到 Permission denied（/etc/shadow 是 root:shadow 640），sudo ./a.out 则能打开——因为 sudo 把 effective UID 提成了 0。

代码自测（Q&A）

Q1：root 的 UID 是多少？内核关心「用户名」吗？ A：root 的 UID 是 0。内核不关心用户名字符串，只认数字 UID/GID。用户名 → UID 的解析是用户态库（读 /etc/passwd）完成的。所以「谁是 root」在内核眼里就是「谁的有效 UID == 0」。

Q2：内核在 open 文件时，权限检查的匹配顺序是什么？ A：拿进程的 fsuid/fsgid 与文件 inode 的 uid/gid 三级匹配：① 若 fsuid == 文件 uid 用 owner 位；② 否则若进程属于文件组（主组或补充组）用 group 位；③ 否则用 other 位。命中即停，不往下继续——所以可能出现「属主比 other 权限还低」的反直觉现象。root（或 CAP_DAC_OVERRIDE）可绕过这套 DAC 检查，但仍受 MAC（SELinux/AppArmor）约束。

Q3：real、effective、saved UID 有什么区别？权限检查用哪个？ A：real UID = 进程真实身份（登录用户）；effective UID = 权限检查实际使用的身份；saved set-UID = 用于「临时降权后恢复」。set-user-ID 程序（如 passwd）的 effective UID 被设为文件属主（root），从而获得临时特权。普通进程三者相同。

Q4：为什么说「root 不受任何限制」是错的？ A：root（UID=0）能绕过的是传统 DAC 权限位（owner/group/other rwx）。但它仍受 MAC（强制访问控制，如 SELinux/AppArmor）约束，以及 capability 模型约束——现代内核里 root 的特权已被拆成几十个细粒度 capability（CAP_NET_ADMIN、CAP_SYS_ADMIN 等），进程得有对应 capability 才能做相应特权操作（见 Ch39）。

Q5：一个用户可以属于多少个组？补充组的作用是什么？ A：一个用户有一个主组（/etc/passwd 里的 GID）+ 多个补充组（supplementary groups，/etc/group 里把用户名列进去）。补充组让用户获得多个组的权限——权限检查时「进程属于文件组」会同时匹配主组和所有补充组。getgroups() 可查询，setgroups() 可设置（需特权）。

单根目录树、目录与链接（Directory Hierarchy）

本节讲什么

Linux 只有一棵目录树，所有文件和文件系统都挂在这棵树的某个节点下。本节回答三个问题：

  1. 「单根目录树」是什么意思？不同的磁盘分区怎么变成 / 下的目录？
  2. 硬链接和软链接的本质区别是什么？分别调哪个系统调用？
  3. Linux 的 7 种文件类型分别是什么？

完整 API 在 Ch18，这里建立「目录树 + inode + 链接」的核心心智。

1. 单根目录树与挂载

Linux 只有一个根目录 /，所有文件系统（磁盘分区、U 盘、网络盘）都「挂载（mount）」到 / 树的某个节点上，形成一棵统一的大树：

/                          ← 根文件系统（rootfs）
├── /bin                    ← 用户命令（常软链到 /usr/bin）
├── /dev                    ← devtmpfs：设备文件
├── /proc                   ← procfs：内核信息（见 2.19）
├── /sys                    ← sysfs：设备/驱动信息
├── /mnt/data               ← 挂载点：另一块磁盘分区挂在这
└── /home                   ← 用户家目录（可能是独立分区）

这和 Windows 的「每个盘符一棵树」（C:\、D:\）完全不同。Linux 里你感觉不到「换了块盘」——挂载点对上层完全透明，/mnt/data/foo 就是普通路径。

2. 目录、路径与 inode

概念 说明
绝对路径 从 / 开始：/home/user/file
相对路径 相对当前工作目录：../etc/passwd
. / .. 当前目录 / 父目录（目录里的两个硬链接）
inode 文件的「身份证」，存权限/大小/数据块指针，不含文件名

关键认知：文件名不在 inode 里，而是存在目录的数据块里——目录本质是一张「文件名 → inode 号」的映射表。所以「删除文件」其实是删除目录里的映射项（unlink），当 inode 的链接计数（i_nlink）降到 0 才真正释放数据块。

3. 硬链接 vs 软链接

特性 硬链接（hard link） 软链接（symlink）
本质 同一 inode 的另一个名字 存路径字符串的特殊文件
跨文件系统 ❌（inode 号只在单个 FS 内唯一） ✅（只存路径文本）
指向目录 ❌（避免环，通常禁止） ✅
删原文件 不影响（inode 引用计数 >0 仍可访问） 悬空（dangling，指向不存在的路径）
创建系统调用 link() symlink()
内核实现 目录项 +1 到同一 inode 新建 inode，内容 = 路径串 
硬链接：  /a/hard  ──┐
                   ├──→ inode 123（数据块）   链接计数 = 2
          /b/orig ──┘

软链接：  /a/sym ──→ 存 "/b/orig" 字符串 ──→ 解析后找到 /b/orig 的 inode

SYSCALL_DEFINE2(symlink, ...)   /* fs/namei.c:4526  建软链接 */
SYSCALL_DEFINE1(unlink, ...)    /* fs/namei.c:4445  删名字（计数-1） */

6. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/stat.h>
#include <sys/types.h>

int main(void) {
    /* 硬链接：同一 inode 两个名字 */
    if (link("orig.txt", "hard.txt") == -1) perror("link");

    /* 软链接：存路径字符串 */
    if (symlink("orig.txt", "sym.txt") == -1) perror("symlink");

    struct stat st1, st2;
    stat("orig.txt", &st1);
    stat("hard.txt", &st2);
    printf("orig  inode=%ld  nlink=%ld\n", (long)st1.st_ino, (long)st1.st_nlink);
    printf("hard  inode=%ld  nlink=%ld\n", (long)st2.st_ino, (long)st2.st_nlink);

    /* 硬链接：inode 相同、nlink=2；软链接则是不同 inode */
    struct stat st3;
    lstat("sym.txt", &st3);        /* lstat 不追符号链接本身 */
    printf("sym   inode=%ld (type=%s)\n", (long)st3.st_ino,
           S_ISLNK(st3.st_mode) ? "symlink" : "other");

    unlink("hard.txt"); unlink("sym.txt");
    return 0;
}

运行：orig.txt 和 hard.txt 的 inode 号相同、nlink=2（两个名字指向同一 inode）；sym.txt 是独立 inode、类型是 symlink。

代码自测（Q&A）

Q1：硬链接和软链接的本质区别是什么？ A：硬链接是同一 inode 的另一个名字——目录里多个名字映射到同一个 inode，链接计数（nlink）增加；软链接是存路径字符串的特殊文件，本身有独立 inode，内容是目标路径。所以硬链接删原文件不影响（inode 还在），软链接删原文件就悬空（dangling）。

Q2：为什么硬链接不能跨文件系统？ A：因为硬链接的本质是「多个目录项指向同一 inode 号」，而 inode 号只在单个文件系统内唯一（/dev/sda1 和 /dev/sdb1 都可能有自己的 inode #123）。跨文件系统无法用 inode 号唯一定位目标，所以 link() 跨 FS 会返回 EXDEV。软链接只存路径字符串，天然可跨 FS。

Q3：Linux 的 7 种文件类型是什么？怎么在代码里判断？ A：普通文件 -、目录 d、符号链接 l、字符设备 c、块设备 b、FIFO p、套接字 s。代码里用 stat/lstat 取 st_mode，配合 S_ISREG/S_ISDIR/S_ISLNK/S_ISCHR/S_ISBLK/S_ISFIFO/S_ISSOCK 宏判断。注意 stat 会跟随符号链接（返回目标类型），lstat 不跟随（返回符号链接本身）。

Q4：文件名存在哪里？为什么「删除文件」不是删数据？ A：文件名不在 inode 里，而是存在目录的数据块（目录 = 「文件名 → inode 号」映射表）。unlink 只删除目录里的这个映射项，inode 的链接计数（i_nlink）减 1；当计数降到 0（没有任何名字指向它）且没有进程打开它，内核才真正释放数据块。所以「文件被删但进程还开着」时数据仍在（打开的文件持有引用），进程关闭后才会真正释放。

Q5：rename() 为什么能实现「崩溃安全的文件替换」？ A：rename 在同一文件系统内是原子的（fs/namei.c:5057 的 SYSCALL_DEFINE2(rename)）：要么新名字完全生效，要么完全不变，不会出现中间态。所以「写临时文件 → fsync → rename 覆盖目标」是配置文件/数据文件安全替换的标准套路——即使中途崩溃，要么是旧文件、要么是新文件，不会出现写了一半的损坏文件。

文件 I/O 模型（File I/O Model）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（fs/open.c、fs/read_write.c、include/linux/fdtable.h） - 上一节：2.4 目录层次 - 下一节：2.6 程序（Programs）

本节讲什么

Linux 的「一切皆文件」模型。本节回答三个问题：

  1. fd（文件描述符）到底是什么？它和内核里的「打开文件」怎么对应？
  2. open/read/write 在内核里各走哪条链路？
  3. 为什么 fork 后父子能共享 fd？O_CLOEXEC 为什么重要？

这是全书 I/O 的「纲」——后面 Ch4/Ch5 的每个 open/read/write 细节，都建立在本节的 fd 三层结构之上。

1. fd 的三层结构（内核视角）

用户态手里的 fd 只是一个小整数，真正的打开文件状态在内核里分三层：

用户态             内核态
 fd (int) ──────► files_struct（每进程一份，task_struct->files）
                     │  fdtable（fd 数组，fd 即下标）
                     ▼
                  struct file（打开文件对象：inode + 偏移量 + f_op）
                     │
                     ▼
                  struct inode（磁盘文件本体，VFS 层）
层 结构 作用 源码
进程级 struct files_struct 每进程的文件表，含 next_fd（下一个可分配 fd） fdtable.h:49-63
表级 struct fdtable fd → struct file* 的数组，max_fds 限制上限 fdtable.h:27-28
文件级 struct file 打开文件的运行时状态（当前偏移、访问模式、f_op） include/linux/fs.h

关键认知：fd 是「进程私有」的——两个进程的 fd 3 可以指向完全不同的文件。但 fork 后，父子进程的 fdtable 指向同一批 struct file（各自持引用计数），所以共享同一个文件偏移量（详见 Ch24）。

2. open / read / write 的系统调用链路

SYSCALL_DEFINE3(open, const char __user *, filename, int, flags, umode_t, mode)   /* fs/open.c:1441 */
SYSCALL_DEFINE3(read, unsigned int, fd, char __user *, buf, size_t, count)        /* fs/read_write.c:621 */
SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf, size_t, count) /* fs/read_write.c:646 */

open(filename, flags)  → do_sys_open → 分配最小可用 fd → 填 fdtable[fd] = file
read(fd, buf, n)       → fdget_pos(fd) 拿 file → vfs_read  → file->f_op->read
write(fd, buf, n)      → fdget_pos(fd) 拿 file → vfs_write → file->f_op->write
close(fd)              → 从 fdtable 摘除 → 引用计数减一 → 归零才释放 file

read/write 只认 fd 这个整数，不认文件名——文件名只在 open 那一刻被解析成 inode。所以「重命名/删除一个正在被写的文件」不影响已经打开的 fd（inode 还在），这也是「写临时文件 + rename 原子替换」能工作的原因（见 Ch18）。

3. 「一切皆文件」与默认三个 fd

Linux 用同一套 API（open/read/write/close）操作所有 I/O 资源：

资源 打开方式 说明
普通文件 open("/path", ...) 磁盘文件
设备 open("/dev/sda", ...) 字符/块设备文件
管道 pipe() 无文件名，直接返回两个 fd
套接字 socket() 网络 I/O
目录 open("/dir", O_RDONLY) 读目录项

每个进程启动时默认打开三个 fd（由父进程/登录 shell 传入）：

fd 名称 用途
0 stdin 标准输入
1 stdout 标准输出
2 stderr 标准错误（不缓冲，错误立即可见）

4. HFT / 嵌入式关联

现象 本节机制的兑现
fd 泄漏导致「Too many open files」 fdtable->max_fds 达上限；长期运行进程必须 close 成对，或用 O_CLOEXEC 防 exec 后泄漏
fork+exec 竞态泄漏 fd 父进程 open 后未关、子进程 exec 继承 → 用 O_CLOEXEC 让 exec 时原子关闭
日志热路径延迟 write 走 file->f_op->write 有内核态拷贝；高频日志用 write 批量或异步落盘
文件偏移共享 fork 后父子共享 struct file 偏移 → 并发写同一文件会交错，需 O_APPEND 原子追加

5. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
/* fd 是进程私有小整数；O_CLOEXEC 防 exec 泄漏 */
int main(void) {
    int fd = open("/tmp/note.txt", O_WRONLY | O_CREAT | O_CLOEXEC, 0644);
    if (fd < 0) { perror("open"); return 1; }

    const char *msg = "hello fd\n";
    write(fd, msg, strlen(msg));   /* fd 是 open 返回的整数 */
    close(fd);                     /* 释放 fd，引用计数减一 */
    return 0;
}

代码自测（Q&A）

Q1：两个进程都有 fd 3，它们指向同一个文件吗？ A：不一定。fd 是进程私有的下标，指向各自 files_struct->fdtable[3]。只有「继承」（fork 共享 struct file）或「显式传 fd」（sendmsg 的 SCM_RIGHTS）时，两个进程的 fd 才指向同一 struct file。

Q2：open 返回的 fd 一定是最小可用整数吗？为什么？ A：是。files_struct->next_fd 记录下一个候选，do_sys_open 从最小空闲位分配。这是刻意设计——close(1) 后下次 open 往往拿到 fd 1，正好接替 stdout，实现「重定向」惯用法。

Q3：read(fd, ...) 为什么不需要文件名参数？ A：因为 open 时已经把路径解析成 inode 并存入 struct file。之后 read/write/lseek 只操作这个已打开的文件对象，与文件名解耦。所以文件被删除/重命名后，已打开的 fd 仍可正常读写。

Q4：O_CLOEXEC 解决什么问题？不用它有什么后果？ A：多线程程序里，线程 A 在 open 和「设 FD_CLOEXEC 标志」之间，线程 B 可能 fork+exec，导致子进程继承了一个本应关闭的 fd（竞态泄漏）。O_CLOEXEC 让 open 和「exec 时关闭」原子绑定，无竞态窗口。长期服务进程所有 fd 都应带 O_CLOEXEC。

Q5：close(fd) 之后文件真的立刻关闭了吗？ A：不一定。close 只是把 fdtable[fd] 摘除、struct file 引用计数减一。只有引用计数归零（所有指向它的 fd 都关了、fork 的子进程也关了），内核才真正释放 struct file。这就是「同一文件被 open 两次，关一个 fd 另一个还能用」的原因。

2.6

程序（Programs）

本章：TLPI 第 02 章 — Fundamental Concepts - 上一节：2.5 文件 I/O 模型 - 下一节：2.7 进程（Process）

本节讲什么

「程序」和「进程」是两个常被混用的概念。本节回答三个问题：

  1. 程序（磁盘上的文件）和进程（运行中的实例）到底差在哪？
  2. 可执行文件（ELF）里装了什么？
  3. execve 怎么把「程序」变成「进程」？

这是理解「为什么一个程序能同时跑成多个进程」的前提，也为 Ch27（exec 家族）铺路。

1. 程序 vs 进程

维度 程序（Program） 进程（Process）
本质 磁盘上的可执行文件（ELF） 程序在内存中的运行实例
生命周期 持久（直到删除文件） 临时（从 exec 到 exit）
资源 无（静态数据） 有 PID、地址空间、fd、栈
数量 一个文件 同一文件可同时跑 N 个进程

一句话：程序是「菜谱」，进程是「正在做的那道菜」。同一份菜谱（程序文件）可以同时炒出多盘菜（多个进程），每盘菜各有自己的锅（内存）和进度（PC 寄存器）。

2. ELF：可执行文件的内部结构

Linux 可执行文件是 ELF（Executable and Linkable Format），分为「给链接器看」和「给加载器看」两套视图：

ELF Header（魔数 \x7fELF + 架构 + 入口地址）
├── Program Headers（段表，供「加载器」用，决定映射到内存哪些段）
│     └── PT_LOAD 段 → Text / Data 映射
└── Section Headers（节表，供「链接器/调试器」用）
      ├── .text  代码
      ├── .data  已初始化全局变量
      ├── .bss   未初始化（零填充，不占文件空间）
      ├── .rodata 只读数据（字符串字面量）
      ├── .symtab 符号表（函数/变量名）
      └── .debug  调试信息（-g 生成，见 03.6 Ch1）

工具：readelf -l a.out 看段（加载视角）、readelf -S a.out 看节（链接视角）、file a.out 识别 ELF。

3. execve：把程序变成进程

execve 是唯一能加载新程序的系统调用（execl/execv 等都是它的 glibc 封装）：

execve(path, argv, envp)
   │
   ▼
内核：读 ELF → 映射 Text/Data 段 → 建新栈 → 跳转到入口地址
   │
   ▼
进程「脱胎换骨」：代码/数据/栈全换，但 PID 不变

关键特性：execve 不创建新进程——它替换当前进程的镜像。所以「fork + exec」才是标准的「创建进程跑新程序」套路：fork 造壳（新 PID），exec 换瓤（新代码）。fd 是否继承由 O_CLOEXEC 决定（见 2.5）。

4. HFT / 嵌入式关联

现象 本节机制的兑现
启动延迟 execve 要读 ELF + 动态链接（若 .so）+ 缺页加载，毫秒级；热路径进程应预启动常驻，避免运行时 fork+exec
程序升级 execve 替换镜像 = 优雅热升级（先准备新进程，再 exec 切换，旧进程收尾退出）
符号表影响 .symtab 供调试/nm 溯源；发布时可用 strip 去掉符号减小体积（但 crash 时无符号难定位）

5. 代码示例

#include <stdio.h>
#include <unistd.h>
/* fork + exec：创建新进程并替换成新程序 */
int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        /* 子进程：用 execve 把自身替换成 /bin/ls */
        char *argv[] = { "ls", "-l", NULL };
        char *envp[] = { NULL };
        execve("/bin/ls", argv, envp);
        perror("execve");        /* execve 成功就不会走到这 */
        return 1;
    }
    /* 父进程：等待子进程 */
    wait(NULL);
    printf("parent done\n");
    return 0;
}

代码自测（Q&A）

Q1：一个程序文件能同时运行成多个进程吗？它们共享内存吗？ A：能。每个 fork+exec 都产生独立进程，各自有独立地址空间。Text 段（只读代码）在内存里物理共享（同一程序的多个进程映射同一份代码页），但 Data/BSS/栈/堆各进程私有（COW）。所以「代码共享、数据隔离」。

Q2：execve 之后，原来的 PID 变了吗？ A：不变。execve 只替换进程的代码/数据/栈镜像，task_struct 和 PID 原样保留。这就是为什么 fork 后子进程 PID 已经确定，exec 只是「换程序」，进程身份（PID、fd、信号掩码）延续。

Q3：.bss 段为什么不占文件空间？ A：.bss 存的是未初始化（或初始化为 0）的全局变量，它们的值全是 0，没必要在文件里存一长串 0。ELF 里 .bss 只记录「大小」，加载时内核分配对应大小的零填充内存即可。所以「全局变量没初始化」不增大可执行文件，但运行时占内存。

Q4：strip 掉符号表（.symtab）有什么利弊？ A：利：文件变小、加载稍快、也隐藏内部符号名（一定程度的反逆向）。弊：崩溃时 core 里只剩地址没有函数名，gdb/addr2line 无法还原调用栈。所以发布版可 strip，但要保留一份带符号的 debug 版用于事后回溯（成对归档，见 03.6 Ch3）。

Q5：fork + exec 中间，fd 为什么会「泄漏」给新程序？ A：execve 默认保留所有打开的 fd（除非 O_CLOEXEC 或 FD_CLOEXEC 标记）。如果 fork 后 exec 前没有关掉临时 fd，新程序就继承了这些它不知道的 fd，长期累积导致「Too many open files」。服务进程所有 fd 都应设 O_CLOEXEC。

进程（Process）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（kernel/fork.c、include/linux/sched.h） - 上一节：2.6 程序（Programs） - 下一节：2.8 内存映射（Memory Mappings）

本节讲什么

进程是「程序运行的实例」。本节回答三个问题：

  1. 进程的基本身份是什么？PID/PPID 从哪来？
  2. 进程怎么被创建？fork() 在内核里走的是怎样一条链路？
  3. 进程有哪些状态（内核视角的 TASK_*），内存布局长什么样？

原书以「概念」为主；本节补上内核侧的实现坐标，把「进程」这个抽象落到 task_struct 上，为后面 Ch24（fork 深入）、Ch6（进程详解）打底。

1. 进程的基本属性

属性 含义 内核来源
PID 进程唯一标识 kernel_clone() 里 pid_vnr(pid) 取回（kernel/fork.c:2921-2922）
PPID 父进程 ID 复制自父进程 task_struct 的 real_parent
TGID 线程组 ID（主线程 PID） 同一进程的所有线程共享 TGID
状态 TASK_RUNNING / TASK_INTERRUPTIBLE 等 task_struct->__state（sched.h:86-131）

每个进程（init/systemd 的 PID=1 除外）都由父进程通过 fork() 创建。PID 1 是系统启动后第一个用户态进程；PID 0 是内核的 idle 进程（swapper），不参与用户态调度（见 05 内核 Ch3.10）。

2. 进程创建：fork() 的完整链路

fork() 不是「凭空造一个进程」，而是复制当前进程。内核侧的真实链路是：

用户态 fork()                    (glibc 封装)
      │
      ▼
SYSCALL_DEFINE0(fork)            kernel/fork.c:2991
      │  args.exit_signal = SIGCHLD   (:2995)
      ▼
kernel_clone(args)               kernel/fork.c:2868
      │  copy_process(NULL, trace, NUMA_NO_NODE, args)   (:2909)
      ▼
copy_process()                   kernel/fork.c:2240
      │  复制 task_struct / 信号 / 文件表 / 内存描述符(mm)
      ├─→ dup_task_struct      复制 task_struct + 内核栈
      ├─→ copy_mm              COW 复制页表（不复制物理页）
      ├─→ copy_files           fd 表（fork 默认共享表项、各持引用计数）
      └─→ copy_sighand        信号处理表
      ▼
返回 pid：父进程拿「子进程 PID」，子进程拿 0

关键源码（kernel/fork.c:2991）：

SYSCALL_DEFINE0(fork)
{
#ifdef CONFIG_MMU
    struct kernel_clone_args args = {
        .exit_signal = SIGCHLD,   /* 子进程退出时给父进程发 SIGCHLD */
    };
    return kernel_clone(&args);
#else
    /* can not support in nommu mode */
    return -EINVAL;
#endif
}

fork 本质是 clone 的特例——fork 只设了 exit_signal=SIGCHLD，共享粒度（内存/文件表）由内核默认；clone(SIGCHLD, 0, ...) 等价于 fork。pthread_create 则走 clone 传 CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND 实现线程（共享内存/文件表，见 Ch29）。

3. 进程状态机（内核视角）

内核用 task_struct->__state 的一个位掩码表示状态（include/linux/sched.h:86-131），ps/top 看到的单字母是它的投影：

内核宏 值 ps 标志 含义 HFT 场景
TASK_RUNNING 0x00000000 R 正在运行或就绪排队 交易主循环占满 CPU
TASK_INTERRUPTIBLE 0x00000001 S 可中断睡眠，等事件 recv 等行情（可被信号打断）
TASK_UNINTERRUPTIBLE 0x00000002 D 不可中断睡眠（通常等 I/O） 等磁盘/网络驱动返回，信号无法打断
__TASK_STOPPED 0x00000004 T 被 SIGSTOP/SIGTSTP 停止 Ctrl+Z 挂起调试
__TASK_TRACED 0x00000008 t 被 ptrace 跟踪（gdb） 调试器单步
EXIT_ZOMBIE 0x00000020 Z 已终止、父进程未 wait 收尸 僵尸堆积耗尽 PID
EXIT_DEAD 0x00000010 — 已 wait、资源释放前最后态 —

两个组合态（源码里是位运算拼出来的）：

#define TASK_KILLABLE  (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)   /* :116 可被致命信号杀死 */
#define TASK_STOPPED   (TASK_WAKEKILL | __TASK_STOPPED)          /* :117 */

D 状态是 HFT 排查重点：进程卡在 D（TASK_UNINTERRUPTIBLE）时，连 kill -9 都打不断——它在等一个内核侧的 I/O 完成。交易机若发现 worker 卡 D 且 ps 的 WCHAN 指向磁盘/网络驱动，通常是存储或网卡驱动卡死，而非业务逻辑死锁。

4. 进程内存布局

一个进程的虚拟地址空间，从低到高：

高地址 ┌──────────────────────┐
       │      Stack（栈）      │  局部变量、函数帧，向下增长
       │        ...           │  （运行时动态）
       ├──────────────────────┤
       │        ↕             │  ← 中间留空，可 mmap
       ├──────────────────────┤
       │      Heap（堆）       │  malloc 分配，向上增长（brk/mmap）
       ├──────────────────────┤
       │   BSS（未初始化全局）  │  零填充，不占磁盘
       ├──────────────────────┤
       │   Data（已初始化全局） │  占磁盘、加载时拷贝进内存
       ├──────────────────────┤
       │   Text（代码，只读）   │  可共享、只读
低地址 └──────────────────────┘
段 内容 来源 共享性
Text 机器指令 可执行文件 .text 同一程序多进程共享（只读）
Data 已初始化全局/静态变量 .data 每进程私有
BSS 未初始化全局/静态变量 .bss（零填充） 每进程私有
Heap malloc 分配 brk/mmap 动态 每进程私有
Stack 局部变量、函数帧 内核启动时分配 每进程私有（线程各自独立栈）

fork 后父子进程的 Text/Data/BSS 页暂时共享（COW），直到某一方写入才真正复制——所以「fork 复制整个内存」是误区，实际只复制页表。

5. HFT / 嵌入式关联

现象 本节机制的兑现
进程创建是启动延迟预算 fork 要 dup_task_struct+copy_mm 复制页表，毫秒级；热路径应线程池预创建、避免运行时 fork
COW 首写触发缺页毛刺 fork 后第一次写共享页触发 page fault + 物理页复制，是「父子都活」场景的隐藏延迟
僵尸进程耗尽 PID 长期运行进程不 wait 收尸 → 僵尸堆积 → pid_max 耗尽 → 无法新建进程
卡 D 状态 worker 卡 TASK_UNINTERRUPTIBLE 等 I/O，kill -9 无效，须查 WCHAN 定位驱动
多线程 = 共享地址空间 clone(CLONE_VM) 让线程共享页表，省内存但引入数据竞争（见 Ch29-30）

6. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>
/* fork: 父进程拿到子进程 PID，子进程拿到 0 */
int main(void) {
    pid_t pid = fork();

    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        /* 子进程：pid == 0 */
        printf("child : my pid=%d, my ppid=%d\n", getpid(), getppid());
        return 42;                        /* 退出码 42 */
    } else {
        /* 父进程：pid == 子进程 PID */
        int status;
        printf("parent: child pid=%d\n", pid);
        wait(&status);                    /* 收尸，否则子进程变僵尸 */
        if (WIFEXITED(status))
            printf("parent: child exited with %d\n", WEXITSTATUS(status));
    }
    return 0;
}

编译运行：gcc -o demo fork.c && ./demo。注意 wait() 必不可少——不 wait 的子进程退出后停在 EXIT_ZOMBIE，直到父进程退出或显式回收。

代码自测（Q&A）

Q1：fork() 之后，父子进程谁先执行？为什么不能假设顺序？ A：两者先后由调度器决定，不可预测。内核在 kernel_clone() 里 wake_up_new_task() 唤醒子进程后，父子都可能先被调度。依赖「父先执行」是经典竞态 bug——需要同步时用 wait/管道/信号显式约定。

Q2：fork() 返回两次，父进程拿到 PID、子进程拿到 0，这个「0」是怎么来的？ A：copy_process() 复制出的子进程，其返回路径（ret_from_fork）会强制让 fork 在子进程里返回 0。这是内核故意设计的「同一段代码、两个返回值」——父进程走 kernel_clone 的 return nr（子 PID），子进程首次被调度时从 ret_from_fork 起步、rax 清 0。

Q3：为什么说「fork 复制整个内存」是错的？ A：copy_mm 只复制页表（dup_mm→dup_mmap），父子共享物理页，页表项标只读。任一进程写入时触发写保护缺页，内核才分配新物理页 + 复制内容（COW）。所以 fork 成本与「内存大小」无关，只与「页表项数量」相关。

Q4：进程和线程在内核里到底有什么区别？ A：几乎只有「共享粒度」的区别——fork 默认共享最少，pthread_create 用 clone(CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD) 让新 task 与父共享地址空间/文件表/信号表，此时它没有独立 PID（共享 TGID），就是一个线程。内核里两者都是 task_struct，没有独立的「线程」结构体。

Q5：一个进程卡在 ps 的 D 状态，kill -9 也杀不掉，为什么？ A：D = TASK_UNINTERRUPTIBLE，进程在等内核态 I/O 完成（磁盘/网络驱动），信号投递被延迟到 I/O 返回之后。kill -9 只是置一个 pending 信号，进程从 D 转回 R 之前不会处理。排查：ps -o pid,stat,wchan 看 WCHAN 指向哪个驱动，通常是存储或网卡问题，而非进程本身。

2.8

内存映射（Memory Mappings）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（mm/mmap.c、include/linux/mm_types.h） - 上一节：2.7 进程（Process） - 下一节：2.9 共享库（Shared Libraries）

本节讲什么

内存映射（mmap）：把文件或设备「映射」进进程地址空间，之后用内存访问代替 read/write。本节回答三个问题：

  1. mmap 在内核里留下什么数据结构？（vm_area_struct）
  2. 文件映射 vs 匿名映射有什么区别？
  3. mmap 什么时候比 read/write 快？代价是什么？

这是 HFT 里「零拷贝」「共享内存」两大性能手段的共同地基（Ch49 完整展开）。

1. 内核表示：vm_area_struct（VMA）

mmap() 的实质，是在进程的地址空间里登记一块区域（VMA），记录「这段虚拟地址对应什么」：

SYSCALL_DEFINE6(mmap_pgoff, unsigned long, addr, unsigned long, len, ...)  /* mm/mmap.c:1427 */

struct vm_area_struct {              /* include/linux/mm_types.h:565 */
    unsigned long vm_start;          /* :522 区域起始地址（含） */
    unsigned long vm_end;            /* :523 区域结束地址（不含，[start,end)） */
    struct file  *vm_file;           /* :526 映射的文件，匿名映射为 NULL */
    unsigned long vm_pgoff;          /* :525 文件内偏移（页为单位） */
    pgprot_t      vm_page_prot;      /* :580 访问权限（读/写/执行） */
    vm_flags_t    vm_flags;          /* :521 标志：MAP_SHARED/PRIVATE/ANON... */
};

进程地址空间 = 一串 VMA 链表（task_struct->mm->mmap）
┌──────┬──────────────┬──────────┬────────┬──────┐
│ Text │ Data/Heap    │  mmap 区  │ libc.so │ Stack│   ← 每段一个 VMA
└──────┴──────────────┴──────────┴────────┴──────┘

cat /proc/pid/maps 就是遍历这个 VMA 链表打印出来的——每一行是一个 vm_area_struct。

2. 两种映射类型

类型 关键标志 后端 用途
文件映射 MAP_SHARED/MAP_PRIVATE + 文件 fd 磁盘文件的页缓存 零拷贝读文件、多进程共享文件内容
匿名映射 MAP_ANONYMOUS，无 fd 物理页（零填充） malloc 大块内存、父子进程共享内存 
文件映射： 虚拟地址 ──缺页──► 页缓存(page cache) ──► 磁盘文件
匿名映射： 虚拟地址 ──缺页──► 分配零填充物理页（无文件后端）

访问机制：mmap 后访问映射区，第一次触发缺页中断（page fault），内核才把文件页读进页缓存、建页表映射。之后就是纯内存访问，不再有系统调用——这就是它比 read/write 快的本质。

3. mmap vs read/write

维度 read/write mmap
数据路径 内核页缓存 → 用户缓冲区（一次拷贝） 页缓存直接映射进用户地址（零拷贝）
系统调用 每次读写都 syscall 仅 mmap/munmap 两次
页错误 无 首次访问每页一次缺页
适用 顺序读一次、小文件 随机访问、大文件、共享

不是永远快：小文件或顺序读一次，mmap 的缺页 + TLB 开销可能反超 read。mmap 的优势在「随机访问大文件」「反复访问」「跨进程共享」场景。

4. HFT / 嵌入式关联

现象 本节机制的兑现
零拷贝行情分发 文件映射让数据从页缓存直达用户态，省一次内核拷贝
跨进程共享内存 MAP_SHARED + 同一文件（或 MAP_ANONYMOUS + fork）实现进程间共享，无 IPC 序列化开销
缺页毛刺 mmap 后首次 touch 每页都触发 page fault，热路径要 madvise(MADV_WILLNEED) 或 MAP_POPULATE 预取
观测映射布局 /proc/pid/maps = VMA 链表 dump，排查「地址被映射到哪」的第一工具

5. 代码示例

#include <stdio.h>
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/stat.h>
/* 文件映射：读文件零拷贝 */
int main(void) {
    int fd = open("/tmp/data.bin", O_RDONLY);
    struct stat st;
    fstat(fd, &st);                       /* 拿文件大小 */

    char *p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    /* 之后直接读内存，无需 read() 系统调用 */
    for (off_t i = 0; i < st.st_size; i++)
        putchar(p[i]);

    munmap(p, st.st_size);                /* 解除映射 */
    close(fd);
    return 0;
}

代码自测（Q&A）

Q1：mmap 之后马上能读到文件内容吗？为什么？ A：能读到，但不是「立刻全量读入」。首次访问某页时触发缺页，内核才把那一页从磁盘读进页缓存并映射。所以 mmap 是惰性的——只有 touch 到的页才真正 I/O。这解释了「映射大文件很快，但遍历它才慢」的现象。

Q2：MAP_PRIVATE 和 MAP_SHARED 的区别？ A：MAP_SHARED 的修改写回文件、其他映射同一文件的进程可见；MAP_PRIVATE 的修改不写回文件，写时触发 COW 复制一份私有页（类似 fork 的 COW）。调试器常用 MAP_PRIVATE 读文件，避免意外改文件。

Q3：vm_start 和 vm_end 是左闭右开区间 [start, end)，这有什么好处？ A：相邻 VMA 能无缝拼接——一个的 vm_end 就是下一个的 vm_start，遍历时无重叠、无空洞歧义。这也是 mmap 返回地址按页对齐的原因：vm_end - vm_start 恒为页大小整数倍。

Q4：匿名映射的「匿名」是什么意思？它映射到哪里？ A：「匿名」= 没有文件后端（vm_file == NULL）。缺页时内核直接分配零填充物理页，不涉及磁盘。malloc 分配大块（超过 MMAP_THRESHOLD，默认 128KB）走的就是匿名 mmap；fork 后的共享内存也常基于匿名映射。

Q5：为什么说 mmap 是「零拷贝」而 read 不是？ A：read 的数据路径是「磁盘 → 页缓存 → 用户缓冲区」两次拷贝（页缓存→用户态那次是 CPU 拷贝）。mmap 让用户地址直接映射到页缓存那一页，读取时 CPU 直接访问页缓存，省掉「页缓存→用户缓冲区」那次拷贝。注意「零拷贝」指省 CPU 拷贝，磁盘 I/O 本身省不掉。

2.9

静态库与共享库（Static & Shared Libraries）

本章：TLPI 第 02 章 — Fundamental Concepts - 上一节：2.8 内存映射（Memory Mappings） - 下一节：2.10 IPC

本节讲什么

程序除了自己的代码，还依赖库（glibc、数学库、第三方 SDK）。本节回答三个问题：

  1. 静态库（.a）和共享库（.so）有什么区别？
  2. 程序启动时，动态链接器（ld-linux.so）做了什么？
  3. 为什么共享库能「多进程共享一份物理内存」？

完整机制在 Ch41-42，这里建立「静态 = 编译时拷入 vs 共享 = 运行时映射」的核心区分。

1. 静态库 vs 共享库

维度 静态库（.a） 共享库（.so）
链接时机 编译链接时拷入 运行时由动态链接器映射
代码位置 每个可执行文件里各有一份 磁盘/内存共享一份
文件体积 大（每个程序都嵌入） 小（只存引用）
更新 重编译所有程序 替换 .so 即可（ABI 兼容前提下）
启动速度 快（无运行时解析） 稍慢（要加载 + 符号重定位）
依赖 无（自包含） 需 .so 在运行时能找到

编译对照：

gcc -static  main.c -o main_static    # 静态：把所有库拷进 main_static
gcc          main.c -o main_dynamic   # 动态：只记录「依赖 libc.so.6」

2. 动态链接器（ld-linux.so）

动态链接程序的可执行文件里，ELF 的 DT_NEEDED 项记录了「依赖哪些 .so」。启动时：

execve(dynamic_program)
   │
   ▼
内核读 ELF → 发现 PT_INTERP（解释器段）→ 加载 /lib64/ld-linux-x86-64.so.2
   │
   ▼
ld-linux.so 按 DT_NEEDED 逐个加载 .so → 用 mmap 映射进进程地址空间
   │
   ▼
符号重定位（PLT/GOT 填充）→ 跳转程序入口 main()

共享库靠 mmap 加载（回接 2.8）：多个进程映射同一个 .so 文件的同一物理页，所以「N 个进程共享一份 libc 的物理内存」——这就是共享库省内存的本质。每个进程的 Data/BSS 段仍各自 COW 私有。

3. 三级命名与工具

名称 形式 用途
real name libfoo.so.1.2.3 真实文件，含完整版本
soname libfoo.so.1 主版本（ABI 不变则稳定）
linker name libfoo.so 编译时 -lfoo 找的链接名（软链）

工具：ldd 看依赖、nm -D 看导出符号、readelf -d 看 DT_NEEDED、ldconfig 维护 soname 软链缓存。

4. HFT / 嵌入式关联

现象 本节机制的兑现
启动延迟 动态链接要加载 N 个 .so + 重定位，冷启动慢；可 LD_BIND_NOW 或静态链接减少运行期解析抖动
符号重定位毛刺 默认延迟绑定（首次调用才解析 PLT），热路径首次调库函数会有一次解析开销
插桩观测 LD_PRELOAD 注入自定义 .so 拦截库调用（ltrace/性能打点原理，见 03.6 Ch5）
部署一致性 目标机 .so 版本与编译机不一致 → ABI 不兼容崩溃，需 soname 管版本

代码自测（Q&A）

Q1：静态链接的程序能在目标机上独立运行吗？共享库呢？ A：静态链接能——所有库代码已拷进可执行文件，目标机不需要任何 .so；共享库不能——目标机必须有对应的 .so（且版本兼容），否则启动时 ld-linux.so 报「error while loading shared libraries」。

Q2：为什么共享库能「多进程共享一份物理内存」？ A：因为 .so 的 Text 段（代码）是只读的，内核用 mmap 把多个进程的虚拟地址映射到同一个物理页（文件的页缓存）。所以 100 个进程跑起来，libc 代码在物理内存里只有一份。各进程的全局变量（Data/BSS）则 COW 各自私有。

Q3：-static 和动态链接，启动速度哪个快？为什么？ A：静态快。动态链接启动时要：加载 ld-linux.so → 逐个打开 DT_NEEDED 的 .so → 符号重定位（PLT/GOT）→ 才进 main。静态链接跳过了这些，但代价是文件大、无法享受 .so 的安全更新、也不能 LD_PRELOAD 插桩。

Q4：什么是「延迟绑定」（lazy binding）？它带来什么副作用？ A：默认情况下，共享库函数在首次被调用时才通过 PLT/GOT 解析真实地址（ld-linux.so 的 _dl_runtime_resolve）。好处是启动快；副作用是首次调用有额外解析开销。HFT 热路径若不能接受这个抖动，用 -Wl,-z,now（LD_BIND_NOW）在启动时一次性绑定。

Q5：LD_PRELOAD 是什么原理？ A：LD_PRELOAD=/path/my.so ./prog 让动态链接器优先加载 my.so，它导出的同名符号（如 malloc、open）会「覆盖」后续 .so 的同名符号（符号介入）。所以能拦截库调用做打点/追踪——ltrace 的 PLT 拦截、性能分析工具都基于类似机制。静态链接程序无 PLT，故 LD_PRELOAD 无效。

2.10

进程间通信与同步（IPC）

本章：TLPI 第 02 章 — Fundamental Concepts - 上一节：2.9 共享库（Shared Libraries） - 下一节：2.11 信号（Signals）

本节讲什么

进程间内存隔离，所以「通信」和「同步」必须借助内核提供的专门机制。本节回答三个问题：

  1. IPC 要解决哪三类问题？
  2. Linux 有哪些 IPC 机制？各自适合什么场景？
  3. 一个 HFT 场景（如行情分发、订单撮合）该怎么选型？

这是全书 IPC 部分的「地图」——Ch43 概览、Ch44-55 逐机制详解，都从这张图出发。

1. IPC 的三大用途

用途 要解决什么 典型机制
传数据 把字节/消息从一个进程搬到另一个 管道、消息队列、共享内存、socket
同步 协调「谁先谁后」，防止竞争 信号量、文件锁、互斥量、条件变量
通知 只发「发生了某事件」的信号，不带数据 信号、eventfd、inotify

「共享内存 + 同步机制」是性能最高、也最易错的组合：共享内存负责「零拷贝传数据」，但不提供任何同步——必须配信号量/锁。很多并发 bug 就出在「以为共享内存自带同步」。

2. 机制全景

机制 类别 传数据 同步 通知 内核形态 章节
管道 / FIFO 字节流 ✅ ❌ ❌ 内核缓冲区 Ch44
SysV 消息队列 消息 ✅ ❌ ❌ id + 内核对象 Ch46
POSIX 消息队列 消息 ✅ ❌ ✅ mqd_t（≈fd） Ch52
SysV 共享内存 共享 ✅ ❌ ❌ id + 内核段 Ch48
POSIX 共享内存 共享 ✅ ❌ ❌ fd（/dev/shm） Ch54

两条关键分界线：

  1. fd 型 vs id 型：POSIX IPC / socket / eventfd 用 fd，能塞进 epoll 统一多路复用；SysV IPC 用 id（整数），不能 epoll。工程上「要统一事件循环」就选 fd 型。
  2. 是否内核持久：SysV 和 POSIX 命名 IPC 对象在所有进程关闭后仍残留内核，须显式 IPC_RMID / unlink 清理，否则累积泄漏。

      │是
      ▼

4. HFT / 嵌入式关联

现象 本节机制的兑现
行情进程 → 策略进程零拷贝分发 共享内存 + 无锁环形队列（配内存屏障），避免 socket 拷贝
撮合引擎多进程协作 共享内存存订单簿，信号量/锁保护临界区

5. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
/* 管道：最简 IPC，父子进程传字节流 */
int main(void) {
    int fd[2];
    pipe(fd);                       /* fd[0] 读端，fd[1] 写端 */

    if (fork() == 0) {              /* 子进程写 */
        close(fd[0]);
        write(fd[1], "hello", 5);
        close(fd[1]);
        return 0;
    } else {                        /* 父进程读 */
        char buf[16];
        close(fd[1]);
        int n = read(fd[0], buf, sizeof(buf));
        close(fd[0]);
        wait(NULL);
        printf("parent got: %.*s\n", n, buf);
    }
    return 0;
}

代码自测（Q&A）

Q1：管道和消息队列的核心区别？ A：管道是无边界字节流——写入的字节流到读端是连续的，读 5 字节不知道它们是「一条消息」；消息队列是有边界消息——每条消息独立，读端一次读一条，还能按 mtype 选优先级（POSIX mq 数值大先出）。要「消息边界/优先级」选消息队列，要「简单字节流」选管道。

Q2：为什么共享内存是最快的 IPC？它有什么代价？ A：数据直接在内存共享，没有内核拷贝（管道/socket 都要经过内核缓冲区搬一次）。代价是没有同步——两个进程同时读写同一块内存会竞态，必须额外配信号量/锁/原子操作，而这恰恰是最容易出错的地方。

Q3：SysV 消息队列和 POSIX 消息队列，工程上优先哪个？为什么？ A：POSIX。因为 POSIX mq 是 fd 型（mqd_t 可塞进 epoll），能和其他 fd 统一多路复用；SysV mq 是 id 型，无法 epoll，只能阻塞读或轮询。且 POSIX mq 有 mq_notify 异步通知。SysV 的唯一优势是「多锁原子性」（SEM_UNDO）和更老的兼容性。

Q4：「IPC 对象内核持久」意味着什么？会有什么坑？ A：SysV 信号量/共享内存、POSIX 命名 mq/sem，创建后即使所有进程都退出，对象仍留在内核（ipcs 能看到），直到显式 IPC_RMID/unlink。崩溃的程序会留下孤儿对象，累积耗尽内核限额。所以「创建者要负责清理」，或在启动时先清理同名对象。

Q5：一个进程要同时等「网络 socket」和「子进程管道」有数据，该怎么设计？ A：用 fd 型 IPC + epoll——把 socket fd 和管道读端 fd 一起加入 epoll，统一阻塞在 epoll_wait。这就是「事件循环」模型。若混用了 SysV 消息队列（id 型），它进不了 epoll，只能另开线程轮询，复杂度陡增。

2.11

信号（Signals）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（kernel/signal.c、include/linux/sched/signal.h） - 上一节：2.10 IPC - 下一节：2.12 线程（Threads）

本节讲什么

信号是内核向进程投递的异步通知（软件中断）。本节回答三个问题：

  1. 信号在内核里怎么表示？（sighand_struct）
  2. kill 和 tgkill 有什么区别？（进程级 vs 线程级）
  3. 为什么 HFT 热路径要小心信号？

完整展开在 Ch20-22，这里先建立「信号 = 异步抢占」的核心心智。

1. 信号的本质与内核表示

信号不是「数据通道」，而是一个编号 + 一个待处理标志。标准信号（1-31）不排队——同一信号连发多次，进程可能只看到一次（实时信号 34-64 才排队，见 Ch22）。

内核侧，每个进程的 task_struct 挂一个 sighand_struct：

struct sighand_struct {              /* include/linux/sched/signal.h:20 */
    ...
    struct k_sigaction action[_NSIG];  /* :24 每个信号一个处理动作 */
};

action[SIGINT] 存的就是「SIGINT 该怎么处理」：默认动作 / 忽略 / 自定义处理器（sigaction 注册的那个）。

2. 发送信号的三个系统调用

SYSCALL_DEFINE2(kill,  pid_t, pid, int, sig)                       /* kernel/signal.c:3807 */
SYSCALL_DEFINE3(tgkill, pid_t, tgid, pid_t, pid, int, sig)         /* :3988 线程级 */
SYSCALL_DEFINE2(tkill, pid_t, pid, int, sig)                       /* :4004 线程级(旧) */
调用 目标 说明
kill(pid, sig) 整个进程组 pid>0 发该进程；pid==0 发同进程组；pid==-1 发所有（有权限的）
tgkill(tgid, pid, sig) 指定线程 tgid 是进程（线程组），pid 是具体线程（tid）
tkill(pid, sig) 指定线程 老接口，等价 tgkill 但少了线程组校验，已不推荐

多线程进程里，kill 投递的信号由任意一个未屏蔽该信号的线程处理（内核挑一个）；tgkill 才能精确投给某个 tid。这正是「要定向通知某个工作线程」时必须用 tgkill 的原因。

3. 信号生命周期

发送方: kill(pid, sig) ──► 内核: 置目标 pending 标志
                                    │ 目标阻塞该信号？ ──是──► 挂起，等解除阻塞
                                    │否
                                    ▼
                         目标进程: 从内核态返回用户态时，检查 pending
                                    │ 有自定义 handler
                                    ▼
                         切换到用户态 handler 执行 → 返回中断点继续

关键：信号的处理时机是「目标进程下一次从内核态返回用户态」——不是发送那一刻立即执行。所以： - 一个正在「纯用户态死循环」的进程，能收到信号（因为时钟中断会周期性把它拉进内核再返回） - 一个卡在 D 状态（不可中断睡眠）的进程，kill -9 也打不断（信号投递被推迟到 I/O 返回）

4. 常见信号速览

信号 编号 默认动作 来源 可否捕获/阻塞
SIGINT 2 终止 Ctrl+C ✅
SIGSEGV 11 终止 + core 非法内存访问 ✅
SIGTERM 15 终止 kill 默认 ✅
SIGKILL 9 终止 kill -9 ❌ 不可捕获/阻塞
SIGSTOP 19 停止 作业控制 ❌ 不可捕获/阻塞

5. HFT / 嵌入式关联

现象 本节机制的兑现
信号造成延迟毛刺 信号是异步抢占——handler 执行时打断主循环，热路径应 pthread_sigmask 屏蔽，让信号只在专用线程处理
优雅停机 SIGTERM handler 置「停止」标志，主循环看到后刷缓冲、释放资源再退出（比 kill -9 安全）
段错误溯源 SIGSEGV 默认 dump core，配合 03.6 模块的 coredump 分析定位崩溃点
处理信号首选 HFT 用 sigwaitinfo（同步等信号，无 handler 抢占）而非异步 handler（见 Ch22）

6. 代码示例

#include <stdio.h>
#include <signal.h>
#include <unistd.h>
/* sigaction: 可移植的信号注册（替代 signal） */
static void handler(int sig) {
    /* 异步上下文：只做信号安全操作，写系统调用 */
    const char msg[] = "got signal\n";
    write(STDOUT_FILENO, msg, sizeof(msg) - 1);
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;         /* 自动重启被中断的慢系统调用 */
    sigaction(SIGINT, &sa, NULL);

    for (;;) pause();                 /* 挂起等信号 */
    return 0;
}

代码自测（Q&A）

Q1：信号是同步还是异步的？ A：异步。发送方 kill 立即返回，信号由内核「稍后」投递——具体是目标进程下一次从内核态返回用户态时。发送方和目标进程的执行时间线是解耦的（这区别于「同步」的函数调用或 sigwaitinfo 这种同步等信号）。

Q2：kill 和 tgkill 有什么区别？什么时候必须用 tgkill？ A：kill 以「进程（线程组）」为粒度，信号由内核挑一个未屏蔽该信号的线程处理；tgkill 以「具体线程（tid）」为粒度，精确投递。多线程程序要通知特定工作线程时，kill 做不到定向，必须 tgkill(tgid, tid, sig)。

Q3：为什么 SIGKILL 和 SIGSTOP 不能被捕获或阻塞？ A：这是内核的「保底」设计——必须保证「任何进程都能被无条件杀死/停止」，否则一个故意屏蔽/捕获所有信号的进程会变成无法杀死的僵尸。sigaction 对这两个信号注册 handler 会直接返回错误。

Q4：标准信号「不排队」是什么意思？会造成什么问题？ A：连发 3 次 SIGINT，进程可能只处理 1 次（内核只记一个 pending 位，不记次数）。所以标准信号不能用来计数。要可靠计数用实时信号（SIGRTMIN+，排队投递，sigqueue 还能携带 si_value）或改用 eventfd/管道。

Q5：进程卡在 D 状态时 kill -9 为什么无效？ A：D = TASK_UNINTERRUPTIBLE，进程在内核态等 I/O 完成。信号只是置 pending 标志，真正处理要等进程从内核态返回用户态。D 状态的进程不返回用户态（一直睡在内核里等 I/O），所以信号永远没机会处理。只有 I/O 完成（或驱动超时）进程醒来，信号才生效。

线程（Threads）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（kernel/fork.c、include/linux/sched.h） - 上一节：2.11 信号（Signals） - 下一节：2.13 进程组（Process Groups）

本节讲什么

线程是进程内的执行单元。本节回答三个问题：

  1. 线程和进程在内核里到底有什么区别？
  2. pthread_create 底层走的是哪个系统调用、传了什么标志？
  3. 为什么 getpid() 在线程里返回的都是同一个值？

这是后面 Ch29-33 线程系列（创建/同步/线程安全/取消）的入口。

1. 内核真相：线程 = 共享更多资源的 task

Linux 内核里没有独立的「线程」结构体——线程和进程都是 task_struct，区别只在共享粒度：

struct task_struct {                 /* include/linux/sched.h */
    pid_t pid;                       /* :967 线程 ID（tid，内核唯一） */
    pid_t tgid;                      /* :968 线程组 ID（= 主线程的 pid） */
};

进程（单线程）:  task_struct A（pid=100, tgid=100）
线程组:          task_struct A（pid=100, tgid=100）   ← 主线程
                 task_struct B（pid=101, tgid=100）   ← 同组线程
                 task_struct C（pid=102, tgid=100）
                        ↑ tgid 相同 = 同一进程
  • 用户态 getpid() 返回的是 tgid（线程组 ID）→ 同一进程所有线程返回相同值
  • gettid() 返回的是 pid（内核唯一 tid）→ 每个线程不同
  • ps -L / top -H 看到的每个「线程」就是 task_struct->pid

2. pthread_create 底层：clone 传共享标志

pthread_create(&tid, NULL, start, arg)
        │
        ▼
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, 新栈顶)
        │        │         │             │                └─ 加入同一线程组(共享 tgid)
        │        │         │             └─ 共享信号处理表(sighand_struct)
        │        │         └─ 共享 fd 表(files_struct)
        │        └─ 共享根目录/工作目录
        └─ 共享地址空间(页表，mm_struct)

源码里这些标志的判定（kernel/fork.c）：

标志 语义 行号
CLONE_VM 共享地址空间（不复制页表） :1731
CLONE_FILES 共享 fd 表 :1784
CLONE_SIGHAND 共享信号处理表 :1803
CLONE_THREAD 加入同一线程组（共享 tgid） :1852

对照：fork 只设 exit_signal=SIGCHLD，这些标志全不传 → 页表/文件表/信号表各自复制。所以「进程」和「线程」是同一机制（clone）的两个参数组合，不是两套代码。

3. 线程共享 vs 私有

共享（全线程可见） 私有（每线程独立）
地址空间（Text/Data/Heap） 栈（stack）
fd 表 寄存器（含 PC/SP）
信号处理表（sighand） 线程 ID（tid）
工作目录、根目录 errno
全局变量 信号掩码（pthread_sigmask 可设线程级）

errno 是线程私有的——每个线程有独立 errno，所以多线程里「检查 errno」不会互相串。但共享全局变量正是数据竞争的温床，必须加锁或用原子操作（见 Ch30、03.6 模块 Ch4）。

4. HFT / 嵌入式关联

现象 本节机制的兑现
线程比进程省创建开销 clone(CLONE_VM) 不复制页表，创建仅「分配栈 + task_struct」，微秒级；进程要复制页表，毫秒级
共享内存通信零开销 线程共享地址空间，直接用共享变量通信，无需 IPC
数据竞争风险 共享变量无锁写是竞态，需锁/原子/TSan 检测（见 03.6 Ch4）
线程崩溃拖垮全进程 共享地址空间，一个线程段错误 → 整个进程崩溃（进程隔离则只挂一个）

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>
/* 线程：共享全局变量，各有独立栈 */
static int shared = 0;

static void *worker(void *arg) {
    printf("thread: pid=%d tid=%ld\n", getpid(), (long)gettid());

    pthread_t tid;
    pthread_create(&tid, NULL, worker, NULL);
    pthread_join(tid, NULL);
    printf("main:   pid=%d, shared=%d\n", getpid(), shared);
    return 0;
}

代码自测（Q&A）

Q1：为什么说「Linux 没有真正的线程，只有 task_struct」？ A：因为内核只有一种调度实体 task_struct。线程和进程都用它表示，区别只是 clone 时传的共享标志——传 CLONE_VM|CLONE_FILES|... 就是线程（共享资源），不传就是进程（各自复制）。内核调度器一视同仁，按 task_struct 调度。

Q2：getpid() 和 gettid() 分别返回 task_struct 的哪个字段？多线程里它们相等吗？ A：getpid() 返回 tgid（线程组 ID，task_tgid_nr() 直接返回 tsk->tgid），同一进程所有线程相同；gettid() 返回 pid（内核唯一 tid），每个线程不同。多线程里 getpid() 恒等、gettid() 各不相同。

Q3：一个线程 close(fd) 会影响同进程其他线程吗？ A：会。因为 CLONE_FILES 让线程共享同一份 files_struct（fd 表），fd 是进程级资源。线程 A close(3) 后，线程 B 的 read(3) 立刻失败。这是「fd 表共享」的直接后果，也是线程编程的常见坑。

Q4：线程有自己的栈吗？栈放哪里？ A：有，每个线程独立栈。pthread_create 时 glibc 用 mmap 分配一块区域（默认 8MB 虚拟空间，按需提交）作为线程栈，clone 时把新栈顶指针传进去。主线程用进程的初始栈，其余线程各有一块独立栈。栈溢出时可能破坏相邻线程栈的「保护页」（guard page），触发段错误。

Q5：线程和进程的「崩溃隔离」差异，对 HFT 意味着什么？ A：进程隔离——一个进程崩溃不影响其他进程，但通信要 IPC、创建开销大；线程共享——一个线程段错误整个进程都挂，但共享内存通信零开销。HFT 常见折中：关键模块用多进程隔离（行情/策略/下单分开，一个崩了能重启），进程内部用多线程共享数据。这是「进程为界、线程为内」的架构原则。

进程组与作业控制（Process Groups）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（include/linux/sched.h） - 上一节：2.12 线程（Threads） - 下一节：2.14 会话（Sessions）

本节讲什么

进程组是「一组相关进程」的集合，shell 用它实现作业控制（Ctrl+C/Ctrl+Z/fg/bg）。本节回答三个问题：

  1. 进程组是什么？PGID 怎么定？
  2. 为什么 Ctrl+C 能一次杀掉一整个「管道命令」？
  3. 内核里进程组存在哪？

完整机制在 Ch34，这里建立「组 = 信号广播单位」的核心心智。

1. 进程组的基本概念

概念 说明
PGID 进程组 ID，= 组长（第一个进程）的 PID
组长 创建进程组的进程，PGID == 组长 PID
归属 每个进程都属于一个进程组，可 setpgid() 迁移 
pid_t getpgrp(void);                     /* 取本进程组 ID */
int   setpgid(pid_t pid, pid_t pgid);    /* 设置进程组 */

内核侧，进程组 ID 通过 task_struct 关联的 pid 结构获取：

static inline pid_t task_pgrp_nr(struct task_struct *tsk)   /* linux/sched.h:1659 */
{ return task_pgrp_nr_ns(tsk, &init_pid_ns); }

2. 作业控制：信号按「组」广播

shell 跑 ls | grep foo | wc 是一条管道，三个进程组成一个进程组（PGID = ls 的 PID）。终端信号按组发送：

操作 信号 发给谁
Ctrl+C SIGINT 整个前台进程组（三个进程全收）
Ctrl+Z SIGTSTP 整个前台进程组（暂停）
fg / bg SIGCONT 恢复指定作业

关键：终端驱动（或 shell）把 Ctrl+C 变成 SIGINT 后，发给的是前台进程组，不是单个进程。这就是「kill -INT -pgid」能一次停掉整条交易管线的原因——负号表示「进程组」。

3. 进程组、会话、终端的关系

会话 (session)
 ├── 前台进程组  ←─ 接收终端输入（Ctrl+C 等信号）
 ├── 后台进程组 1
 └── 后台进程组 2
  • 前台进程组：唯一能读终端输入、接收终端信号的组
  • 后台进程组：读终端会触发 SIGTTIN，写触发 SIGTTOU（默认暂停）

4. HFT / 嵌入式关联

现象 本节机制的兑现
一次停掉整条交易管线 kill(-pgid, SIGTERM) 按组广播，feed → 策略 → 下单全链路优雅退出
交易进程 daemon 化 setsid() 脱离控制终端（见 2.14），避免误按 Ctrl+Z 挂起主循环
后台读终端被暂停 后台进程读 stdin 触发 SIGTTIN 默认挂起——headless 交易机 stdout 非 tty 无此问题

5. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <signal.h>
#include <sys/wait.h>
/* kill(-pgid, sig)：给整个进程组发信号 */
int main(void) {
    pid_t pgid = getpgrp();
    printf("my pgid = %d\n", pgid);

    if (fork() == 0) {
        setpgid(0, 0);               /* 子进程自成一组（组长） */
        for (;;) pause();            /* 挂起等信号 */
    }
    /* 父进程给「负 pgid」发信号 = 广播到整组 */
    kill(-pgid, SIGTERM);
    wait(NULL);
    return 0;
}

代码自测（Q&A）

Q1：PGID 和组长的关系是什么？ A：进程组 ID（PGID）等于组长进程的 PID。组长是第一个创建该组的进程。组长退出后进程组仍可存在（组内其他进程还在），此时 PGID 不再对应任何存活进程，但组 ID 仍有效。

Q2：kill(pid, sig) 里的 pid 传负数是什么意思？ A：传 -pgid 表示「给整个进程组 pgid 发信号」。kill 的 pid 参数语义：>0 发该进程、==0 发同进程组、==-1 发所有有权限的进程、<-1 发进程组 -pid。所以 kill(-123, SIGTERM) 是「停掉整个进程组 123」。

Q3：为什么 Ctrl+C 能一次杀掉 ls | grep | wc 整条管道？ A：shell 把管道里的进程放进同一个进程组，终端驱动收到 Ctrl+C 后产生 SIGINT 发给前台进程组（整组）。所以三个进程同时收到 SIGINT。这依赖「组」作为信号广播单位——若各自独立进程组，就得逐个 kill。

Q4：后台进程读终端会发生什么？ A：后台进程组读终端（stdin）时，终端驱动发 SIGTTIN，默认动作是暂停（stop）该进程，直到被 fg 调到前台并继续。写终端同理触发 SIGTTOU。这是作业控制保证「只有前台进程能跟终端交互」的机制。

Q5：交易进程为什么要 setsid() 脱离控制终端？ A：控制终端是「会话」的属性，挂着一个会话会收到终端的 SIGHUP（终端关闭时）和 SIGINT/SIGTSTP（按键时）。交易服务要长期后台运行，必须脱离控制终端，否则运维人员误按 Ctrl+C/Ctrl+Z 会直接打断交易主循环。setsid 新建会话、脱离旧终端（见 2.14、Ch37）。

2.14

会话、控制终端与控制进程（Sessions）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（include/linux/sched.h、include/linux/sched/signal.h） - 上一节：2.13 进程组（Process Groups） - 下一节：2.15 伪终端（Pseudoterminals）

本节讲什么

会话（session）是「进程组之上的容器」，把一组进程组与一个控制终端绑定。本节回答三个问题：

  1. 会话（SID）和进程组（PGID）是什么关系？setsid() 做了什么？
  2. 「控制终端」为什么会发出 Ctrl+C/SIGHUP，信号到底发给谁？
  3. 守护进程为什么要 fork() + setsid() 两步脱离终端？

完整机制在 Ch34，这里建立「会话 = 终端关联单位」的核心心智。

1. 会话的基本结构

会话 (SID = 会话首领 PID)
 ├── 前台进程组  ←─ 唯一能读终端输入、接收 Ctrl+C 的组
 ├── 后台进程组 1
 ├── 后台进程组 2
 └── ...
概念 说明
SID 会话 ID，= 会话首领进程的 PID
会话首领 调用 setsid() 创建会话的进程
控制终端 会话可（可选）关联一个终端设备，/dev/tty 指向它
控制进程 会话首领（若它有控制终端，也叫控制进程） 
pid_t setsid(void);    /* 新建会话，调用者成为会话首领 */
pid_t getsid(pid_t pid);

2. 内核里的 session：task->signal->pids[PIDTYPE_SID]

会话 ID 和进程组 ID 一样，存在进程的 signal 结构里，按 PIDTYPE_* 索引取：

/* include/linux/sched/signal.h:697 */
static inline struct pid *task_session(struct task_struct *task)
{ return task->signal->pids[PIDTYPE_SID]; }

/* include/linux/sched/signal.h:692 */
static inline struct pid *task_pgrp(struct task_struct *task)
{ return task->signal->pids[PIDTYPE_PGID]; }

取数值 ID 走 task_session_vnr（include/linux/sched.h:1626，内部 __task_pid_nr_ns(tsk, PIDTYPE_SID, NULL)）。要点：pids[] 是个数组，PIDTYPE_PID/PIDTYPE_TGID/PIDTYPE_PGID/PIDTYPE_SID 各自存一份 struct pid 引用，所以一个进程同时「属于」进程组和会话——不是树形嵌套，是两套独立的归属标签。

3. 控制终端：信号的源头

控制终端不是「进程的属性」，而是会话的属性。终端驱动（tty）收到按键后，把字符转成信号发给会话的前台进程组：

按键/事件 产生的信号 发给谁
Ctrl+C（intr） SIGINT 前台进程组
Ctrl+Z（susp） SIGTSTP 前台进程组
Ctrl+\（quit） SIGQUIT 前台进程组
终端断开（挂机/hangup） SIGHUP 会话首领（控制进程）

SIGHUP 是关键：终端关闭（ssh 断开、串口拔出、pty 关闭）时，内核向会话的控制进程发 SIGHUP。默认动作是终止进程，这就是「ssh 一断，前台任务全挂」的根因——除非用 nohup/setsid/tmux 把进程挪出这个会话。

4. 守护进程为什么要 setsid()（两步脱离）

守护进程要在后台长期运行、不依赖任何终端，所以必须「脱离控制终端」。标准套路是两次 fork + setsid：

/* 第一次 fork：子进程不再是「组长」，才有资格 setsid */
if (fork() > 0) _exit(0);      /* 父进程退出 */

setsid();                       /* 新会话，子进程成为会话首领（但尚无控制终端） */

/* 第二次 fork：会话首领退出，孙进程彻底不是首领、永远拿不到控制终端 */
if (fork() > 0) _exit(0);

/* 可选：chdir("/") + umask(0) + 关闭 0/1/2 + 打开 /dev/null */

为什么 setsid 前要先 fork？ 内核规定：进程组组长不能调用 setsid（会返回 EPERM）。因为组长若成为新会话首领，会造成「组 ID 和会话 ID 冲突」的歧义。第一次 fork 让子进程变成非组长，才有资格 setsid。

为什么还要第二次 fork？ setsid 后子进程成为会话首领，而会话首领可以再获取控制终端（打开一个 tty 就自动成为它的控制终端）。第二次 fork 产生孙进程（非首领），它永远无法再获取控制终端，从而彻底摆脱终端。

5. HFT / 嵌入式关联

现象 本节机制的兑现
交易服务 daemon 化 fork+setsid 脱离控制终端，避免运维误按 Ctrl+C 打断策略主循环
ssh 断开导致策略进程被杀 终端关闭触发 SIGHUP → 控制进程默认终止；生产环境必须 setsid 或 tmux 托管

嵌入式 init 进程 PID 1（init/systemd）自成一会话、无控制终端，负责收养孤儿进程

6. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

/* 演示：setsid 后进程脱离控制终端，SID == 自己的 PID */
int main(void) {
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid > 0) _exit(0);          /* 父进程退出，子进程成为孤儿 */

    if (setsid() == -1) {           /* 成为新会话首领 */
        perror("setsid"); return 1;
    }

    printf("sid=%d (should == pid=%d)\n", getsid(0), getpid());
    printf("tty=%s (null = 已脱离终端)\n",
           ttyname(0) ? ttyname(0) : "none");

    /* 后台常驻，不再响应终端 Ctrl+C */
    for (;;) pause();
    return 0;
}

编译运行后 ps -o pid,sid,pgid,tty,cmd 查看：SID 等于进程自己的 PID，TTY 列为空——标志它已脱离控制终端。

代码自测（Q&A）

Q1：会话和进程组是什么关系？ A：会话是「进程组的容器」，一个会话里有多个进程组，其中至多一个是前台进程组。进程组归属用 pids[PIDTYPE_PGID] 标记，会话归属用 pids[PIDTYPE_SID] 标记，两者是独立的两套标签，不是树形嵌套。会话 ID（SID）等于会话首领的 PID。

Q2：setsid() 到底做了什么？为什么组长不能调用？ A：setsid 做三件事：① 让调用进程成为新会话的首领；② 让调用进程成为新进程组的组长（新组里只有它自己）；③ 与旧控制终端断开。组长不能调用是因为：若允许组长成为新会话首领，就会出现「它的 PGID 同时是一个组的 ID 又是新会话的 ID」的歧义，内核干脆禁止（返回 EPERM）。

Q3：控制终端什么时候会发 SIGHUP？发之前发生了什么？ A：终端设备断开（ssh 掉线、串口拔出、pty 主端关闭）时，tty 驱动检测到挂机（hangup），向该会话的控制进程（会话首领）发送 SIGHUP。SIGHUP 默认动作是终止进程，所以「ssh 一断前台全挂」。之后会话若继续存在，其成员读/写已断的终端会得到 EIO。

Q4：为什么守护进程要两次 fork？一次不行吗？ A：一次 fork + setsid 后，进程已经是会话首领，而会话首领仍可能再获取控制终端（只要打开一个 tty 就自动绑定）。第二次 fork 产生孙进程（非首领、非组长），它结构上就永远无法再获取控制终端，从而彻底杜绝「被终端信号打断」的风险。所以两次 fork 是「double fork」守护进程标准写法。

Q5：nohup 和 setsid 防挂断的原理一样吗？ A：不完全一样。nohup 只是让进程忽略 SIGHUP（信号来了不终止），进程仍在原会话、仍挂控制终端，其他终端信号（SIGINT/SIGTSTP）照收。setsid 是彻底脱离：新建会话、无控制终端，从根源上就不会收到终端驱动产生的任何信号。要真正「后台常驻」应优先用 setsid（或 tmux/screen 这类会话管理器）。

2.15

伪终端（Pseudoterminals）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（include/linux/sched/signal.h 控制终端关联字段；PTY 实现在 drivers/tty/pty.c + devpts） - 上一节：2.14 会话（Sessions） - 下一节：2.16 日期与时间（Date and Time）

本节讲什么

伪终端（PTY）是一对「互相连通」的设备，让程序以为自己连着真终端，实际另一端是另一个程序。本节回答三个问题：

  1. PTY 的 master/slave 两端分别是什么？数据怎么流？
  2. 为什么 ssh、script、终端模拟器都离不开 PTY？
  3. PTY 和管道（pipe）的关键区别是什么？什么时候必须用 PTY？

完整 API 在 Ch64，这里建立「PTY = 带终端语义的双向通道」的核心心智。

1. PTY 的结构：master + slave 一对

程序 A（如 sshd）          内核           程序 B（如 shell）
   │                                        │
   ▼                                        ▼
PTY master ──────────── 双向数据流 ──────→ PTY slave
/dev/ptmx                               /dev/pts/N
   │                                        │
   └─ 写 master 的数据 → slave 读到          └─ shell 以为连着真终端
      slave 写的数据 → master 读到
  • master（主端）：/dev/ptmx，由「扮演终端」的程序持有（sshd、终端模拟器）
  • slave（从端）：/dev/pts/N，给「被控制」的程序（交互式 shell），它看到的是一个真终端——isatty() 返回 true，有 termios 属性、有行规程（line discipline）、能收终端信号

数据流是双向对称的：master 写 → slave 读（等于「终端显示给用户」），slave 写 → master 读（等于「用户敲键盘」）。

2. 打开 PTY 的固定套路

int master = posix_openpt(O_RDWR | O_NOCTTY);  /* ① 打开 master */
grantpt(master);                                /* ② 授权 slave 可被打开 */
unlockpt(master);                               /* ③ 解锁 slave */
char *name = ptsname(master);                   /* ④ 得到 slave 路径 /dev/pts/N */
int slave  = open(name, O_RDWR);                /* ⑤ 打开 slave */

/* 接下来：子进程 setsid + 打开 slave 作为 0/1/2 + exec shell */

四步 API（posix_openpt → grantpt → unlockpt → ptsname）是 POSIX 标准序列；BSD 风格有一步到位的 openpty()/forkpty()（<pty.h>，glibc 提供）。内核侧，master 是 /dev/ptmx（每 open 一次分配一个新的 slave），slave 由 devpts 文件系统动态挂载到 /dev/pts/。

3. 与「控制终端」的关系

PTY 的 slave 端可以成为会话的控制终端（见 2.14）。内核里会话与终端的关联存在 signal_struct 里：

/* include/linux/sched/signal.h:174 */
struct tty_struct *tty;   /* NULL if no tty —— 会话的控制终端 */

当 sshd 给远程登录的 shell 建会话时：shell setsid() 成为会话首领 → 打开 slave 作为 stdin/stdout/stderr → 这个 slave 成为会话的控制终端。之后：slave 侧的行规程把 Ctrl+C 转成 SIGINT 发给前台进程组、终端断开时 master 关闭 → slave 检测到 hangup → 向控制进程发 SIGHUP（这就是「ssh 一断，远程 shell 及其子进程收到 SIGHUP」的完整链路）。

4. PTY 的典型用途

用途 master 持有者 slave 使用者
ssh 远程登录 sshd 远程交互 shell
终端模拟器 xterm/gnome-terminal 里面的 shell
script 录制会话 script 程序 被录制的 shell
tmux/screen tmux 服务进程 每个窗格里的 shell
自动化交互 expect/pexpect 被驱动的命令行程序

5. PTY vs 管道：什么时候必须用 PTY

维度 管道（pipe） 伪终端（PTY）
isatty() false true
termios 属性 ❌ ✅（波特率、行规程、echo 等）
终端信号（Ctrl+C→SIGINT） ❌ ✅（slave 行规程产生）
作业控制 ❌ ✅
换行转换 ❌（原样） ✅（\n → \r\n，ONLCR）
用途 进程间传数据 跑交互式程序

关键：交互式程序（shell、vim、top、ssh 客户端）会检查 isatty(stdin)，如果不是 tty 就进入非交互模式或直接报错。所以「用管道给 ssh 传密码」「用管道跑 vim」都会失败——必须用 PTY 模拟出真终端。反之，纯数据管道用 pipe 就够，别用 PTY（有行规程加工、更重）。

7. 代码示例

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <pty.h>

/* forkpty：一步建 PTY + fork 子进程，子进程的标准 IO 接到 slave */
int main(void) {
    int master;
    pid_t pid = forkpty(&master, NULL, NULL, NULL);

    if (pid == -1) { perror("forkpty"); return 1; }

    if (pid == 0) {
        /* 子进程：stdin/stdout/stderr 已接到 slave，跑交互式 shell */
        execl("/bin/sh", "sh", NULL);
        perror("execl");
        _exit(127);
    }

    /* 父进程：通过 master 与子进程的 shell 交互 */
    char buf[4096];
    ssize_t n;
    write(master, "echo hello-from-pty\n", 20);       /* 给 shell 发命令 */
    while ((n = read(master, buf, sizeof(buf) - 1)) > 0) {
        buf[n] = '\0';
        printf("master got: %s", buf);                 /* 读 shell 的输出 */
    }
    return 0;
}

编译：gcc -o pty pty.c -lutil（forkpty 在 libutil）。运行后父进程通过 master 给子进程的 shell 发命令、读回输出——这就是 ssh/script 控制交互程序的核心机制。

代码自测（Q&A）

Q1：PTY 的 master 和 slave 分别是什么？数据怎么流？ A：master（/dev/ptmx）由「扮演终端」的程序持有，slave（/dev/pts/N）给「被控制」的程序。数据双向对称：master 写 → slave 读（等于「终端显示给用户」），slave 写 → master 读（等于「用户敲键盘」）。slave 端让程序以为自己连着真终端（isatty 为 true、有 termios）。

Q2：为什么「用管道给 ssh 传密码」或「用管道跑 vim」会失败？ A：因为交互式程序会检查 isatty(stdin)——管道不是 tty，程序就进入非交互模式或拒绝运行。此外管道没有 termios 属性、不产生终端信号、不做行规程加工。要跑交互式程序必须用 PTY 模拟出真终端（isatty 为 true）。这是 ssh/tmux/script/expect 都用 PTY 的根本原因。

Q3：打开 PTY 的标准四步 API 是什么？ A：posix_openpt(O_RDWR|O_NOCTTY) 打开 master → grantpt(master) 授权 slave 可被本用户打开 → unlockpt(master) 解锁 slave → ptsname(master) 得到 slave 路径 /dev/pts/N，再 open 它。BSD 风格可用一步到位的 openpty()/forkpty()。O_NOCTTY 防止 master 意外成为控制终端。

Q4：PTY 和管道的关键区别是什么？ A：管道是纯数据通道（isatty 为 false、无 termios、无信号），PTY 是「带终端语义」的双向通道（isatty 为 true、有 termios 属性、slave 行规程把 Ctrl+C 转成 SIGINT、做 \n→\r\n 换行转换、支持作业控制）。传数据用 pipe 就够（更轻），跑交互式程序才必须 PTY。

Q5：「ssh 一断，远程 shell 及其子进程收到 SIGHUP」的完整链路是什么？ A：sshd 给远程 shell 建会话：shell setsid 成为会话首领，打开 PTY slave 作为 0/1/2，slave 成为会话控制终端（内核存在 signal_struct->tty）。当 ssh 连接断开：sshd 关闭 master → slave 检测到 hangup → tty 驱动向会话的控制进程（shell）发 SIGHUP → shell 默认终止，其子进程（前台进程组）也随之受影响。要防止进程被挂断，须 setsid 脱离终端或 tmux/nohup 托管。

日期与时间（Date and Time）

本章：TLPI 第 02 章 — Fundamental Concepts 源码核验：Linux v6.6（arch/x86/entry/syscalls/syscall_64.tbl、lib/vdso/gettimeofday.c） - 上一节：2.15 伪终端（Pseudoterminals） - 下一节：2.17 客户端/服务器（Client-Server）

本节讲什么

Linux 有两类时间：日历时间（墙上的钟，可被修改）和进程时间（CPU 消耗）。本节回答三个问题：

  1. 日历时间和进程时间分别是什么？用什么 API 拿？
  2. CLOCK_REALTIME、CLOCK_MONOTONIC、CLOCK_MONOTONIC_RAW 有什么区别？HFT 计时该用哪个？
  3. 为什么 clock_gettime 能快到「不进内核」（vDSO）？

完整 API 在 Ch10，这里建立「计时选对时钟 = 延迟测量正确性」的核心心智。

1. 两类时间

类型 说明 典型 API
日历时间（wall clock） 自 Epoch（1970-01-01 00:00:00 UTC）起的秒数，可被修改 time()、gettimeofday()、clock_gettime()
进程时间（CPU time） 进程消耗的 CPU 时间 times()、clock()、clock_gettime(CLOCK_PROCESS_CPUTIME_ID)

进程时间又分三段：

时间 含义
user time 用户态执行消耗的 CPU 时间
system time 内核态（系统调用）消耗的 CPU 时间
real time 实际墙上流逝时间（= user + system + 等待/被抢占）

time 命令的 real/user/sys 三列就是这个区分——real 可能远大于 user+sys（进程在等 I/O、被调度器抢占）。

2. 三种时钟 API 与精度

time_t t = time(NULL);                          /* 秒级，最粗 */
struct timeval tv; gettimeofday(&tv, NULL);     /* 微秒级 */
struct timespec ts;
clock_gettime(CLOCK_REALTIME, &ts);             /* 纳秒级，现代首选 */

clock_gettime 是 POSIX 标准推荐接口，用 clockid_t 选择「哪个钟」：

clockid 含义 会跳变吗
CLOCK_REALTIME 墙上时间（Epoch 起） ✅ 被 NTP 步进、settimeofday 修改
CLOCK_MONOTONIC 单调递增（从某点起） ❌ 只受 NTP 频率微调（slew），不回拨
CLOCK_MONOTONIC_RAW 纯硬件计数（不受 NTP 任何调整） ❌ 完全不受 NTP 影响
CLOCK_PROCESS_CPUTIME_ID 本进程 CPU 时间 ❌
CLOCK_THREAD_CPUTIME_ID 本线程 CPU 时间 ❌

3. HFT 计时铁律：用 CLOCK_MONOTONIC

测「时间间隔」绝不能用 CLOCK_REALTIME——它会被 NTP 步进（stepping）或管理员改时间回拨，导致测出负的时间差。正确做法：

场景 该用
测量延迟/间隔（latency） CLOCK_MONOTONIC 或 CLOCK_MONOTONIC_RAW
记录「事件发生在墙上几点」 CLOCK_REALTIME（但别用它算间隔）
统计进程 CPU 占用 CLOCK_PROCESS_CPUTIME_ID 
CLOCK_REALTIME:      ├───────────┤  NTP 回拨 → 时间倒退，间隔算出负数 ❌
CLOCK_MONOTONIC:     ├───────────→  只会单调递增，间隔永远 ≥ 0        ✅

CLOCK_MONOTONIC vs CLOCK_MONOTONIC_RAW：前者会被 NTP 频率微调（slew，缓慢校正晶振漂移，不回拨），后者是纯硬件计数、完全不受 NTP 干扰。HFT 测微秒级抖动用 CLOCK_MONOTONIC_RAW 更纯粹（不受 NTP 的 slew 影响），但日常测间隔用 CLOCK_MONOTONIC 即可。

4. vDSO：clock_gettime 为什么能不进内核

clock_gettime 的系统调用号是 228（syscall_64.tbl），但实际调用常常不陷入内核——因为内核把时钟数据通过 vDSO（virtual dynamic shared object）映射到用户态，clock_gettime 直接在用户态读这块只读数据：

/* lib/vdso/gettimeofday.c:110 —— 高精度时钟，用户态直接算 */
static __always_inline int do_hres(const struct vdso_data *vd, clockid_t clk,
                   struct __kernel_timespec *ts)

vDSO 是内核映射进每个进程地址空间的一段代码 + 数据（vdso_data），glibc 的 clock_gettime/gettimeofday/time 会优先走 vDSO 快速路径，只有需要「精确到纳秒 + 实时校准」的罕见情况才真正陷入内核。这是「高频计时零开销」的关键——HFT 热路径里大量 clock_gettime 调用不会拖慢系统。

5. HFT / 嵌入式关联

现象 本节机制的兑现
延迟测量正确性 用 CLOCK_MONOTONIC 测间隔，避免 NTP 回拨导致负延迟
高频时间戳零开销 clock_gettime 走 vDSO 用户态直接读，不陷入内核
订单时间戳审计 用 CLOCK_REALTIME 记「墙上时间」做对账，但内部排序用 MONOTONIC
CPU 占用归因 CLOCK_PROCESS_CPUTIME_ID 区分「跑在用户态 vs 内核态」的时间
嵌入式 RTC 嵌入式设备无网络时靠 RTC 芯片维持 CLOCK_REALTIME，启动时同步

6. 代码示例

#define _GNU_SOURCE
#include <stdio.h>
#include <time.h>

/* 测一段代码的耗时：必须用 CLOCK_MONOTONIC，不能 REALTIME */
static long long ns_diff(struct timespec a, struct timespec b) {
    return (b.tv_sec - a.tv_sec) * 1000000000LL
         + (b.tv_nsec - a.tv_nsec);
}

int main(void) {
    struct timespec t0, t1;

    clock_gettime(CLOCK_MONOTONIC, &t0);
    /* 模拟一段热路径（如解析行情包） */
    volatile long x = 0;
    for (long i = 0; i < 1000000; i++) x += i;
    clock_gettime(CLOCK_MONOTONIC, &t1);

    printf("elapsed = %lld ns\n", ns_diff(t0, t1));

    /* 墙上时间（用于审计，别用来算间隔） */
    struct timespec wall;
    clock_gettime(CLOCK_REALTIME, &wall);
    printf("wall clock = %lld.%09ld\n",
           (long long)wall.tv_sec, wall.tv_nsec);

    /* 进程 CPU 时间 */
    clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &wall);
    printf("cpu time   = %lld.%09ld\n",
           (long long)wall.tv_sec, wall.tv_nsec);
    return 0;
}

编译：gcc -o t t.c（clock_gettime 在 glibc 2.17+ 不需要 -lrt）。elapsed 是单调时钟测的间隔，NTP 调整也不会变成负数。

代码自测（Q&A）

Q1：日历时间和进程时间的区别是什么？ A：日历时间是「墙上的钟」（自 Epoch 起的秒数，可被修改），进程时间是「进程消耗的 CPU 时间」（不可回拨）。进程时间又分 user time（用户态）、system time（内核态）、real time（实际流逝 = user + system + 等待/被抢占）。

Q2：CLOCK_REALTIME 和 CLOCK_MONOTONIC 的区别是什么？为什么测间隔不能用 REALTIME？ A：CLOCK_REALTIME 是墙上时间，会被 NTP 步进或管理员改时间回拨，用它测间隔可能算出负数；CLOCK_MONOTONIC 从某点单调递增、只受 NTP 频率微调（slew）不回拨，间隔永远 ≥ 0。所以「测延迟/间隔」用 MONOTONIC，「记墙上几点」才用 REALTIME。

Q3：CLOCK_MONOTONIC 和 CLOCK_MONOTONIC_RAW 有什么区别？ A：CLOCK_MONOTONIC 受 NTP 频率微调（slew——缓慢校正晶振漂移，让时间走快/走慢一点，但绝不回拨）；CLOCK_MONOTONIC_RAW 是纯硬件计数，完全不受 NTP 任何调整。HFT 测微秒级抖动用 RAW 更纯粹（连 slew 都不想要），日常测间隔用 MONOTONIC 即可。

Q4：为什么 clock_gettime 能快到「不陷入内核」？ A：因为 vDSO 机制——内核把时钟数据（vdso_data）和一段代码映射进每个进程的地址空间，glibc 的 clock_gettime/gettimeofday/time 优先走 vDSO 快速路径，直接在用户态读只读数据算出时间（lib/vdso/gettimeofday.c 的 do_hres/do_coarse），只有需要纳秒级实时校准的罕见情况才真正发系统调用（号 228）陷入内核。所以高频计时几乎零开销。

Q5：time 命令输出的 real/user/sys 三列分别是什么？为什么 real 可能远大于 user+sys？ A：real = 墙上实际流逝时间；user = 用户态 CPU 时间；sys = 内核态 CPU 时间（系统调用）。real > user+sys 是常态，因为进程在等 I/O、被调度器抢占、睡眠时，CPU 时间不增加但墙上时间在走。real 远大于 user+sys 说明进程大量时间在等待（I/O 密集），接近则说明是 CPU 密集。

客户端/服务器（Client-Server）

本章：TLPI 第 02 章 — Fundamental Concepts - 上一节：2.16 日期与时间（Date and Time） - 下一节：2.18 实时（Realtime）

本节讲什么

客户端-服务器（C/S）是分布式系统最基础的架构模式。本节回答三个问题：

  1. C/S 模型的本质是什么？请求-响应循环长什么样？
  2. 同机和跨机的 C/S 分别用什么 IPC 机制？
  3. 迭代服务器和并发服务器有什么区别？HFT 为什么偏爱事件驱动？

1. C/S 模型的本质

客户端               服务器
   │  ① 发送请求         │
   ├──────────────────→ │
   │                     │  ② 处理请求
   │  ③ 返回响应         │
   │ ←──────────────────┤
   │                     │  ④ 继续监听下一个请求
  • 服务器：长期运行的进程，监听某个通信端点（socket、FIFO、共享内存），收到请求后处理并返回响应。
  • 客户端：主动发起连接/请求，拿到响应后可能继续或退出。

「服务器」不是某种特殊进程，只是角色——一个进程在 A 交互里是服务器，在 B 交互里可能是客户端。核心特征是「被动等待请求 → 处理 → 响应 → 再等待」这个循环。

2. IPC 选择：同机 vs 跨机

场景 首选 IPC 原因
同机 Unix domain socket / 管道 / 共享内存 零网络栈开销、零校验和、零路由
跨机 TCP/UDP socket 唯一能跨主机的方式

同机通信的排序（性能从高到低，详见 Ch43/44）：

机制 性能 特点
共享内存 最快 零拷贝，但需自己同步（信号量/锁）
Unix domain socket（AF_UNIX） 快 有 fd 语义、可 epoll、可靠流
FIFO/管道 快 字节流，仅亲缘/命名
TCP loopback 慢 走完整 TCP/IP 栈，同机也耗

HFT 同机通信优先 AF_UNIX 或共享内存——AF_UNIX 跳过网络栈（无 IP 头、无校验和、无路由），比 TCP loopback 快得多；共享内存最快但要自己管同步。

3. 服务器类型：迭代 vs 并发 vs 事件驱动

类型 处理方式 优点 缺点
迭代服务器 逐个处理，处理完一个才接下一个 简单，无并发问题 一个慢请求阻塞所有后续请求
并发服务器（fork/线程） 每个请求 fork 子进程/线程 隔离性好，能并行 进程/线程创建开销大，连接多时撑不住
事件驱动 单线程 + I/O 多路复用（epoll） 高并发、低开销 编程复杂度高（状态机） 
迭代：  req1 → 处理 → req2 → 处理 → req3 ...
并发：  req1 → fork 子进程处理（并行）
         req2 → fork 子进程处理（并行）
事件：  单线程 epoll 监听 N 个连接，谁有数据就处理谁（非阻塞）

HFT 选型：热路径（行情/下单）用事件驱动（epoll，见 Ch63），因为单线程 + 非阻塞能扛住成千上万连接、零进程切换开销；隔离性要求高、处理逻辑重的（风控引擎）用多进程/线程池。

4. HFT 中的 C/S 架构

交易所（服务器）          本地交易系统
      │                       │
      │  行情流（组播/UDP）     │
      ├──────────────────────→│ 行情网关（客户端）
      │                       │     │
      │                       │     │  订单簿更新（共享内存/AF_UNIX）
      │                       │     ▼
      │                       │  策略引擎
      │                       │     │
      │  下单请求（TCP）        │     │  信号（AF_UNIX）
      │ ←──────────────────────┤     ▼
      │                       │  风控/执行网关

典型的多级 C/S：

组件 角色 通信
行情网关 交易所的客户端 接收行情（组播/UDP）
行情网关 → 策略 服务器/客户端 共享内存或 AF_UNIX 广播订单簿
策略引擎 风控的客户端 AF_UNIX 发交易信号
风控/执行网关 策略的服务器 AF_UNIX 收信号，再作为客户端连交易所

5. 连接 vs 无连接

维度 面向连接（TCP/SOCK_STREAM） 无连接（UDP/SOCK_DGRAM）
可靠性 有序、可靠、不丢 尽力而为，可能丢/乱序
延迟 有握手、确认开销 低，无连接建立
场景 下单（必须可靠） 行情（丢一帧无所谓，快更重要）

HFT 的经典取舍：行情用 UDP/组播（快、丢帧可容忍，下一帧马上来），下单用 TCP（必须可靠、有序）。这也解释了为什么行情链路和交易链路常常分开设计。

6. 代码示例

/* 迭代服务器骨架：单连接逐个处理（教学用，生产用 epoll 事件驱动） */
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <sys/un.h>

int main(void) {
    int sfd = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr = { .sun_family = AF_UNIX };
    strcpy(addr.sun_path, "/tmp/cs_demo.sock");
    unlink(addr.sun_path);

    bind(sfd, (struct sockaddr *)&addr, sizeof(addr));
    listen(sfd, 8);
    printf("server listening on /tmp/cs_demo.sock\n");

    for (;;) {
        int cfd = accept(sfd, NULL, NULL);   /* 等一个客户端 */
        char buf[256];
        ssize_t n = read(cfd, buf, sizeof(buf) - 1);  /* 读请求 */
        buf[n] = '\0';
        printf("got request: %s", buf);
        write(cfd, "pong\n", 5);             /* 回响应 */
        close(cfd);
    }
}

这是最简单的迭代服务器（AF_UNIX 域，同机通信），一次只服务一个客户端。它清晰展示了 C/S 的「监听 → 收请求 → 处理 → 回响应 → 再监听」循环；生产环境要并发处理，就把 accept 后的处理交给子进程/线程池或改用 epoll。

代码自测（Q&A）

Q1：客户端-服务器模型的基本流程是什么？ A：服务器长期运行、监听通信端点，收到客户端请求后处理并返回响应，然后继续等待下一个请求；客户端主动发起请求、接收响应。核心是「被动等待 → 处理 → 响应 → 再等待」的循环。「服务器」只是角色，不是特殊进程——一个进程可在不同交互里既当服务器又当客户端。

Q2：迭代服务器和并发服务器的区别是什么？ A：迭代服务器逐个处理请求，处理完一个才 accept 下一个——简单无并发问题，但一个慢请求会阻塞所有后续请求。并发服务器为每个请求 fork 子进程或起线程并行处理——隔离好、能并行，但进程/线程创建开销大、连接多时撑不住。两者之上还有「事件驱动」（单线程 + epoll 多路复用），HFT 热路径的首选。

Q3：同机和跨机通信分别用什么 IPC？为什么？ A：同机优先 Unix domain socket / 管道 / 共享内存——AF_UNIX 跳过网络栈（无 IP 头、无校验和、无路由），比 TCP loopback 快得多；共享内存最快但需自己同步。跨机只能 TCP/UDP socket（唯一能跨主机的方式）。所以「同机用 TCP loopback」是常见浪费，应改 AF_UNIX。

Q4：HFT 里为什么行情用 UDP、下单用 TCP？ A：因为两者可靠性需求不同：行情是高频、可容忍丢帧的数据流（丢一帧下一帧马上来），用 UDP/组播换更低延迟、无连接建立开销；下单是必须可靠有序的关键指令（丢一单可能造成损失），用 TCP 保证不丢、有序。所以行情链路和交易链路常分开设计。

Q5：HFT 交易系统里「共享内存」和「Unix domain socket」分别用在什么场景？ A：共享内存用于「零拷贝高频数据共享」——如行情网关把订单簿写进共享内存，多个策略进程 mmap 同一块物理页直接读（见 2.8），最快但需信号量/锁同步；AF_UNIX 用于「需要 fd 语义 + 可 epoll 的消息通信」——如策略给风控发交易信号，有连接管理、可多路复用、可靠流。一句话：极致性能的裸数据用共享内存，要可靠消息/多路复用用 AF_UNIX。

本节讲什么

「实时」指系统能在确定的时限内响应事件。本节回答三个问题：

  1. 硬实时和软实时的本质区别是什么？错过期限的代价有何不同？
  2. Linux 靠哪几样机制凑出「实时能力」？SCHED_FIFO、mlock、PREEMPT_RT 各管什么？
  3. HFT 的微秒级延迟，为什么必须 mlockall + CPU 亲和绑定？

完整调度机制在 Ch35（实时调度）与 Ch50（内存锁定），这里建立「实时 = 确定性」的核心心智。

1. 硬实时 vs 软实时

维度 硬实时（Hard RT） 软实时（Soft RT）
错过期限的后果 系统级失败（可能造成事故/损坏） 性能下降、服务质量降低，可容忍
典型场景 核反应堆控制、安全气囊、飞行控制 HFT、音视频流、游戏
对 Linux 的要求 通常需 RTOS 或 PREEMPT_RT 补丁 标准内核 + 实时调度策略基本够用

核心是「确定性」而非「快」：硬实时要求的是最坏情况延迟（worst-case latency）有上界，不是平均响应快。标准 Linux 内核是「吞吐优先」，CONFIG_PREEMPT_NONE 下关中断/持自旋锁的临界区会引入不可预知的调度延迟，所以纯标准内核无法保证硬实时。

2. 实时调度策略：SCHED_FIFO / SCHED_RR

普通进程用 SCHED_NORMAL（CFS，完全公平调度，按 vruntime 分配时间片）。实时进程用：

策略 语义 抢占行为
SCHED_FIFO 先进先出，没有时间片，跑到主动让出/被更高优先级抢占 高优先级可抢占低优先级
SCHED_RR 轮转，同优先级有时间片（sched_rr_timeslice_ms） 同优先级轮流跑

实时优先级范围（内核注释，kernel/sched/core.c:7652-7654）：

/* Valid priorities for SCHED_FIFO and SCHED_RR are
 * 1..MAX_RT_PRIO-1, valid priority for SCHED_NORMAL,
 * SCHED_BATCH and SCHED_IDLE is 0. */

MAX_RT_PRIO = 100，所以实时优先级是 1~99（用户态），数值越大优先级越高。关键事实：任何实时进程（优先级 ≥1）都优先于所有 SCHED_NORMAL 进程（优先级 0）——所以一个跑飞的 SCHED_FIFO 任务能把整台机器「卡死」，因为它永远不让出 CPU。

struct sched_param sp = { .sched_priority = 50 };   /* 1..99 */
sched_setscheduler(0, SCHED_FIFO, &sp);              /* 需 CAP_SYS_NICE 权限 */

3. 内存锁定：mlock / mlockall（防换页）

实时任务的隐形杀手是缺页（page fault）：哪怕 CPU 上跑得好好的，一旦访问的页被换出（swap），就要等磁盘换入，延迟从微秒暴涨到毫秒级。mlock 把页钉在物理内存里，禁止换出：

/* mm/mlock.c:622 */
SYSCALL_DEFINE2(mlock, unsigned long, start, size_t, len)

/* mm/mlock.c:705 */
SYSCALL_DEFINE1(mlockall, int, flags)
{
    ...
    if (!flags || (flags & ~(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)) ||
        flags == MCL_ONFAULT)
        return -EINVAL;

    if (!can_do_mlock())
        return -EPERM;

    lock_limit = rlimit(RLIMIT_MEMLOCK);   /* 受 RLIMIT_MEMLOCK 限制 */
    lock_limit >>= PAGE_SHIFT;
    ...
    ret = apply_mlockall_flags(flags);    /* 给 VMA 打 VM_LOCKED 标记 */
    ...
    if (!ret && (flags & MCL_CURRENT))
        mm_populate(0, TASK_SIZE);        /* 立即建立页表 + 分配物理页 */
    return ret;
}

三个 MCL_* 标志：

标志 含义
MCL_CURRENT 锁定当前已映射的所有页
MCL_FUTURE 锁定以后新映射的页（mmap/malloc 增长的部分）
MCL_ONFAULT 延迟锁定：等页首次被访问（缺页）时才锁，省内存

HFT 用 mlockall(MCL_CURRENT | MCL_FUTURE)：既锁现有页，又锁将来分配的热路径缓冲，彻底消除「策略开跑后首次访问某块内存」的缺页毛刺。代价是锁定的内存不计入 swap 候选，系统内存压力大时可能 OOM。

4. PREEMPT_RT 补丁：让内核本身可抢占

实时调度策略和内存锁定都只解决用户态的确定性；真正的延迟往往来自内核态——关中断、持自旋锁、关抢占的临界区。PREEMPT_RT（现已逐步合入主线，CONFIG_PREEMPT_RT）把内核里几乎所有自旋锁换成可睡眠的互斥锁（rt_mutex）、把中断处理线程化，使内核态也能被高优先级任务抢占，从而压低最坏情况调度延迟。

内核配置 抢占能力 适用
PREEMPT_NONE 仅在返回用户态时调度 服务器吞吐优先
PREEMPT_VOLUNTARY 自愿让出点 + 返回用户态 桌面
PREEMPT（抢占式内核） 内核态大部分可抢占 通用低延迟
PREEMPT_RT 近乎全可抢占（含中断线程化） 硬实时

5. HFT 的实时需求兑现

HFT 是典型的软实时 + 极致低延迟场景，一条完整的「低延迟改造清单」都对应本节机制：

需求 手段 消除的延迟源
微秒级响应 SCHED_FIFO + 高优先级 被 CFS 排队 / 时间片抢占
稳定的延迟上界 CPU 亲和（sched_setaffinity）+ isolcpus 隔离核 跨 CPU 迁移 / 缓存失效
消除缺页毛刺 mlockall(MCL_CURRENT\|MCL_FUTURE) swap 换入 / 首次缺页
避免系统调用开销 批量化、io_uring、用户态轮询（busy-wait） 上下文切换 / 系统调用进出
避免调度抖动 SCHED_FIFO 独占核、关掉 tick（nohz_full） 周期定时器中断打断

诚实评估：单靠应用层（SCHED_FIFO + mlockall + CPU 亲和）能压掉 80% 的软实时延迟；但要逼近硬件极限（个位数微秒、抖动 <1µs），还需要 isolcpus/nohz_full 内核参数 + PREEMPT_RT 内核 + 网卡驱动零拷贝（AF_XDP/DPDK）配合，这已经是「内核 + 用户态」协同的系统工程。

6. 代码示例

#define _GNU_SOURCE
#include <stdio.h>
#include <sched.h>
#include <sys/mman.h>
#include <unistd.h>

/* 把进程钉在 CPU 2，锁内存，升实时优先级 */
int main(void) {
    /* 1. CPU 亲和：只跑在 CPU 2 */
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(2, &set);
    if (sched_setaffinity(0, sizeof(set), &set) == -1)
        perror("sched_setaffinity");

    /* 2. 锁内存：当前 + 将来，消除缺页毛刺 */
    if (mlockall(MCL_CURRENT | MCL_FUTURE) == -1)
        perror("mlockall");        /* 需 CAP_IPC_LOCK 或足够 RLIMIT_MEMLOCK */

    /* 3. 实时调度：SCHED_FIFO 优先级 80 */
    struct sched_param sp = { .sched_priority = 80 };
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == -1)
        perror("sched_setscheduler");  /* 需 CAP_SYS_NICE */

    printf("pinned to CPU 2, FIFO prio 80, memory locked\n");
    for (;;) ;  /* 热循环占核（busy-wait 轮询行情） */
    return 0;
}

编译运行（sudo 获取权限后）：gcc -o rt rt.c && sudo ./rt。用 top -H 看 PR 列显示 -80 或 rt，确认已进实时调度；ps -o pid,psr,ni,rtprio,cmd 确认 PSR=2（钉在 CPU 2）。

代码自测（Q&A）

Q1：硬实时和软实时的本质区别是什么？ A：区别在错过期限的后果：硬实时错过期限 = 系统失败（可能造成物理损坏/事故），所以要求最坏情况延迟有严格上界；软实时错过期限只是性能/体验下降，追求的是「尽量快、延迟尽量低」。HFT 是软实时——偶尔一次延迟毛刺是亏损，不是「系统失败」，所以标准内核 + 实时策略通常够用，不必上 RTOS。

Q2：SCHED_FIFO 和 SCHED_RR 有什么区别？ A：都是实时策略（优先级 1~99，高于所有普通进程）。SCHED_FIFO 没有时间片，任务一直跑到主动让出（sleep/阻塞）或被更高优先级抢占；SCHED_RR 给同优先级的任务分配时间片轮转，避免一个 FIFO 任务把同优先级伙伴饿死。两者都被更高优先级任务抢占。

Q3：HFT 为什么必须 mlockall()？ A：因为缺页是低延迟的头号杀手——访问被换出（swap）的页要等磁盘换入，延迟从微秒涨到毫秒级，且发生时机不可预测。mlockall(MCL_CURRENT|MCL_FUTURE) 把当前及未来映射的页全部钉在物理内存、禁止换出，消除「策略开跑后首次访问某块内存」的缺页毛刺。代价是占用物理内存、系统内存紧张时可能 OOM。

Q4：MCL_CURRENT 和 MCL_FUTURE 分别锁什么？ A：MCL_CURRENT 锁定调用时已经映射的所有页（并触发 mm_populate 立即分配物理页）；MCL_FUTURE 锁定之后新映射的页（后续 mmap/堆增长自动带 VM_LOCKED）。HFT 两个都要：既锁已有缓冲，又锁开跑后热路径动态分配的内存。

Q5：为什么光靠 SCHED_FIFO + mlockall 还到不了「硬实时」？ A：因为延迟大头在内核态：关中断、持自旋锁、关抢占的临界区会让用户态高优先级任务无法被及时调度，且这段延迟不可预测。要压缩它需要内核级配合——PREEMPT_RT 补丁（自旋锁换 rt_mutex、中断线程化，让内核态也可抢占）+ isolcpus/nohz_full（隔离核、关周期 tick）。所以「实时」是用户态 + 内核态协同的系统工程，不是单靠一个系统调用。

本节讲什么

/proc 是内核暴露给用户态的一个虚拟文件系统（procfs），是「读文件 = 查内核、写文件 = 改内核」的统一接口。本节回答三个问题：

  1. /proc 为什么「不占磁盘」，读它的瞬间发生了什么？
  2. 内核里 /proc/[pid]/status 这种文件是怎么「凭空」长出来的？
  3. HFT 排查为什么离不开 /proc/[pid]/maps、/proc/interrupts、/proc/softirqs？

完整机制在 Ch12，这里建立「procfs = 内核信息的文件视图」的核心心智。

1. /proc 是什么

/proc 挂载的是 procfs，一个伪文件系统——它的 inode 和内容都在内存里，由内核在读取时动态生成，不落磁盘：

特性 说明
零磁盘占用 文件内容实时生成，ls -l 看到的大小多为 0 或虚值
读 = 查询 read() 触发内核的 show 函数，现场拼字符串返回
写 = 配置 写 /proc/sys/... 即调内核参数（sysctl）
目录 = 数据视图 /proc/[pid] 每个目录对应一个进程 
$ ls -l /proc/$$/status /proc/meminfo
-r--r--r-- 1 root root 0 ... /proc/$$/status    # 大小显示 0，但 cat 有内容
-r--r--r-- 1 root root 0 ... /proc/meminfo

2. 内核实现：ONE 宏 + tgid_base_stuff[] 表

/proc/[pid]/ 下的每个文件，都是内核用宏注册一个 show 函数生成的：

/* fs/proc/base.c:145 —— 注册「单个 show 函数」的文件 */
#define ONE(NAME, MODE, show)               \
    NOD(NAME, (S_IFREG|(MODE)),         \
        NULL, &proc_single_file_operations, \
        { .proc_show = show } )

进程目录的文件清单来自 tgid_base_stuff[] 表（fs/proc/base.c:3241）：

static const struct pid_entry tgid_base_stuff[] = {
    ONE("status",     S_IRUGO, proc_pid_status),       /* :3252 */
    ONE("limits",     S_IRUGO, proc_pid_limits),       /* :3254 */
    ONE("stat",       S_IRUGO, proc_tgid_stat),        /* :3269 */
    ONE("wchan",      S_IRUGO, proc_pid_wchan),        /* :3292 */
    ONE("schedstat",  S_IRUGO, proc_pid_schedstat),    /* :3298 */
    ONE("oom_score",  S_IRUGO, proc_oom_score),        /* :3312 */
    ...
};

ONE("status", S_IRUGO, proc_pid_status) 的含义是：当用户 cat /proc/123/status 时，内核调 proc_pid_status() 现场生成该进程的状态文本。系统级文件同理，例如 /proc/meminfo：

    ...
}

代码自测（Q&A）

Q1：/proc 为什么 ls -l 显示文件大小是 0，cat 却有内容？ A：因为 procfs 是伪文件系统，内容不落磁盘、由内核在 read() 时现场生成。常规文件的 st_size 是「已存储的字节数」，procfs 文件没有「已存储」，所以 size 报 0（或一个虚值）。真正的内容是 show 函数（如 proc_pid_status）临时拼出的字符串。

Q2：内核是怎么「凭空」造出 /proc/[pid]/status 这种文件的？ A：不是逐个真实创建，而是注册表驱动。tgid_base_stuff[] 表里每项是 {名字, 权限, show 函数}，进程目录初始化时遍历这张表，把每项挂成一个 procfs 目录项。cat 时 procfs 的 read 回调转发到对应的 proc_pid_status()，由它现场生成文本。ONE 宏（fs/proc/base.c:145）就是这种「一个 show 函数」文件的注册糖。

Q3：如何通过 /proc 查看一个进程打开了哪些文件？ A：ls -l /proc/[pid]/fd/——每个文件描述符是一个符号链接，指向它打开的实际文件（管道、socket、普通文件、设备等）。fd 号就是链接名，readlink 可得真实路径。查 fd 泄漏时用它 ls /proc/[pid]/fd | wc -l 数个数，再对比 cat /proc/[pid]/limits 里的 Max open files。

Q4：/proc/[pid]/maps 和 /proc/[pid]/status 分别看什么？ A：maps 是虚拟内存映射列表（VMA 的投影），每行一个地址区间 + 权限 + 映射文件，看进程的代码段/堆/栈/共享库/匿名映射布局；status 是进程状态汇总（人类可读），看 State、线程数、VmRSS（常驻物理内存）、Cpus_allowed_list（CPU 亲和）、上下文切换计数等。一个偏「地址空间」，一个偏「运行状态」。

Q5：/proc/sys/ 和普通 /proc 文件有什么区别？ A：/proc/sys/ 是 sysctl 接口，专用于可写的内核参数（读 = 查参数，写 = 改参数，如 net/ipv4/ip_forward）。普通 /proc 文件大多是只读信息（cpuinfo、meminfo、[pid]/status），部分 /proc/[pid]/ 文件也可写（如 oom_score_adj）。/proc/sys/ 的写操作会触发内核的参数校验和热更新，是「运行时调内核」的标准通道。

章节自测（Q&A）

Q1：Ch2 讲了 19 个概念，它们可以归成哪几条主线？ A：① 内核与边界（内核/系统调用/Shell）；② 权限与文件（用户组/目录树/文件 I/O/proc）；③ 程序与进程（程序/进程/进程组/会话）；④ 内存与库（内存映射/共享库）；⑤ 并发与通信（IPC/信号/线程/C-S）；⑥ 时间与实时（时间/实时）；⑦ 终端（伪终端）。七块构成后续全部章节的地基。

Q2：Ch2 里哪些概念最贴近 HFT？为什么？ A：文件 I/O（fd 模型）、内存映射（零拷贝）、信号（异步抢占）、线程（并发）、IPC（跨进程通信）、实时（SCHED_FIFO+mlockall 低延迟）、时间（CLOCK_MONOTONIC 测延迟）、/proc（排查）。它们直接对应 HFT 的「低延迟 + 高并发 + 可靠通信」三大诉求，所以是 OUTLINE「HFT 最短路径」的起点。

Q3：为什么说「进程 = task_struct，线程 = clone 传共享标志」是 Ch2 最重要的心智之一？ A：因为它统一了「进程/线程」这对看似不同的概念——内核里两者都是 task_struct，区别只是 clone 传的共享标志（CLONE_VM/CLONE_FILES 等）。fork 是 clone 只设 exit_signal=SIGCHLD 的特例，pthread_create 是传共享标志实现线程。这个认知贯穿 Ch24-26（进程）、Ch28-33（线程）全部内容。

Q4：Ch2 的「权限」「内存」「信号」分别对应内核里的什么结构体？ A：权限 → 进程凭证（uid_t/gid_t + effective UID，权限检查在 generic_permission）；内存 → vm_area_struct（VMA，mmap 的实质）；信号 → signal_struct/sighand_struct（信号表 + 处理函数）。这些结构体是 05-linux-kernel / 06-linux-mm 模块追源码的核心对象。

Q5：学完 Ch2，下一步按什么顺序推进最高效？ A：按 HFT 最短路径：Ch3（系统编程概念）→ Ch4-5（文件 I/O）→ Ch20-22（信号）→ Ch29-30（线程）→ Ch35（实时调度）→ Ch49-50（mmap/mlock）→ Ch56-61（socket）→ Ch63（epoll）。这条路径优先覆盖 HFT 最需要的系统调用能力，其余章节（文件系统、终端、安全）按需再补。

章节自测

  1. 为何进程不能直接访问对方内存？靠什么隔离？
    各有独立 虚拟地址空间；由 内核 + MMU/页表 隔离保护。

  2. 系统调用为何有性能开销？
    特权级切换、保存/恢复上下文、进内核执行路径 — 上下文切换 成本。

  3. stdin/stdout/stderr 编号？
    0 / 1 / 2。

  4. 硬链接 vs 软链接？
    硬链接：多名字 → 同一 inode；软链接：存 路径字符串（可指不存在目标）。

  5. 测代码耗时用哪种时钟？
    用 单调/CPU 相关计时（如 CLOCK_MONOTONIC 一类）；不要用会跳变的墙上日历时间当唯一依据。书中「CPU 时间」适合看占核；测墙钟耗时用 单调时钟 更稳妥。
