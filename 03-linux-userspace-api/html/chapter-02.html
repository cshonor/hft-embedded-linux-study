代码示例

#include <stdio.h>
#include <errno.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>

/* Ch2 基本概念 — 演示 errno 错误处理 + 用户态/内核态切换。
 * open() 失败时 errno 被设置；strerror 将 errno 转为可读字符串。
 * 编译: gcc -o ch2_demo ch2_demo.c */

int main(void) {
    /* 故意打开不存在的文件，触发 errno */
    int fd = open("/nonexistent/file", O_RDONLY);
    if (fd < 0) {
        printf("open failed: errno=%d (%s)\n", errno, strerror(errno));
        perror("perror also works");
    }

    /* 演示: 同一系统调用成功时 errno 不被清零 */
    fd = open("/etc/hostname", O_RDONLY);
    if (fd >= 0) {
        char buf[256];
        ssize_t n = read(fd, buf, sizeof(buf) - 1);
        if (n > 0) {
            buf[n] = '\0';
            printf("hostname: %s", buf);
        }
        close(fd);
    }
    return 0;
}

2.1

内核（Kernel）

本章：TLPI 第 02 章 — Fundamental Concepts - 上一节：本章首页 - 下一节：2.2 用户态 / 内核态 / 系统调用

本节讲什么

操作系统的核心——内核。Linux 采用宏内核架构，所有驱动、调度器、内存管理都运行在同一个特权地址空间里。理解内核的存在和边界，是后续所有系统调用学习的前提。

要点

内核是什么

内核是操作系统中始终驻留内存的核心部分，负责管理全部硬件资源：

职责 说明
CPU 调度 决定哪个进程/线程占用 CPU，上下文切换
内存管理 虚拟地址空间、页表、换页、mmap
文件系统 VFS 抽象层，对接 ext4/btrfs/proc 等
设备驱动 磁盘、网卡、USB、串口……
网络 协议栈（TCP/IP），socket 层
安全 权限检查、capabilities、namespace

宏内核 vs 微内核

架构 特点 代表
宏内核 驱动、调度、FS 都在内核态；性能高 Linux
微内核 内核只留 IPC/调度；驱动在用户态；更安全但慢 QNX、MINIX
混合内核 折中 Windows NT、macOS XNU

Linux 选择宏内核是为了性能——系统调用直接陷入内核处理，没有额外的进程间通信开销。驱动可以编译进内核（vmlinux），也可以动态加载（.ko 模块）。

内核态 vs 用户态

用户态 (User Space)     ← 应用程序、glibc
    |  系统调用 (syscall)
内核态 (Kernel Space)   ← 内核代码、驱动
  • 用户态：权限受限，不能直接访问硬件、不能随意读写内存
  • 内核态：CPU 处于特权模式，可以执行任何指令、访问任何内存
  • 切换：用户程序通过系统调用（syscall 指令）主动进入内核态；中断/异常也会切换

和 C 语言的关系

C 语言本身没有"内核"概念——K&R 的 C 只关心用户态的 printf/fopen。但在 Linux 上：

  • 你写的 C 程序运行在用户态
  • 调用 open()/read() 等函数时，glibc 封装会触发系统调用，CPU 切到内核态执行内核代码
  • 内核处理完返回用户态，你的 C 程序继续执行
/* 这行 C 代码背后：glibc → syscall 指令 → 内核态 sys_write → 返回 */
write(1, "hello\n", 6);

HFT / 嵌入式关联

  • 嵌入式：内核可裁剪（make menuconfig），只保留需要的驱动和子系统；/dev 下的设备文件是用户态操作硬件的唯一入口
  • HFT：每次系统调用都有陷入开销（~1μs），热路径要尽量减少 syscall 数量；理解内核态/用户态边界是性能优化的基础

代码示例

#include <stdio.h>
#include <unistd.h>
/* 内核态 vs 用户态 */
int main(void) {
    /* printf 在用户态执行 */
    printf("User space: printf\n");
    /* write 触发系统调用, 切到内核态 */
    write(STDOUT_FILENO, "Kernel space: write syscall\n", 28);
    return 0;
}

用户态 / 内核态 / 系统调用

系统调用：用户程序进入内核的 唯一正规入口。 例：open / read / write / mmap / fork 用户程序 → glibc 封装 → CPU 陷入（syscall 等）

要点

空间 谁 权限
用户空间 User Space 普通应用 受限；不能直接碰硬件
内核空间 Kernel Space 内核代码 全权

系统调用：用户程序进入内核的 唯一正规入口。
例：open / read / write / mmap / fork

用户程序 → glibc 封装 → CPU 陷入（syscall 等）
         → 内核态执行服务 → 返回用户态

面试 / HFT 高频： 系统调用有 上下文切换开销；低延迟路径要 尽量少 syscall。

glibc 角色
作用 封装原始 syscall，提供友好接口
注意 有的函数内部会 多次 syscall；少数纯用户态（不进内核）

→ LKD §5.1 libc ≠ syscall

与 C 语言学习的关系

本节区分用户态和内核态——这是 C 程序员从 K&R 跨入系统编程的第一个概念转变。

K&R 教你的 C 程序运行在用户态（受限权限），而 open/read/write/fork/mmap 这些系统调用是唯一正规入口，让用户态程序请求内核干活。C 标准库函数（fopen/printf）内部也是通过系统调用进入内核的。

关键认知：用户态代码不能直接访问硬件、内核内存或其他进程的内存。一切特权操作必须通过系统调用。对照 K&R 第 8 章，那章讲的文件描述符、read/write 就是系统调用的入门实例。

常见陷阱

  1. 误以为用户态可以直接访问硬件
/* ❌ 用户态不能直接读写硬件端口或内核内存 */
/* ✅ 必须通过系统调用（open/read/write/ioctl）请求内核代劳 */
/* /dev 设备文件是内核暴露给用户态的接口，不是直接硬件访问 */

用户态程序运行在 ring 3（x86）或 EL0（ARM），权限受限。任何硬件操作都要通过系统调用进入内核（ring 0 / EL1）完成。

  1. 低估系统调用开销
/* HFT 热路径：逐字节 read，每次都上下文切换 */
for (int i = 0; i < n; i++)
    read(fd, &buf[i], 1);  /* n 次用户态→内核态切换！ */

/* 优化：批量读 */
read(fd, buf, n);  /* 1 次系统调用 */

系统调用涉及模式切换、保存现场、权限校验，开销远贵于普通函数调用（数百 ns 级）。HFT 热路径要尽量少 syscall，或用 mmap / 批量 I/O。

  1. 混淆 glibc 库函数与系统调用
/* strcpy / atoi / strlen → 纯用户态，不进内核 */
/* open / read / write  → glibc 薄封装，陷入内核 */
/* fopen / fread        → glibc 多层封装（缓冲 + 调用 open/read） */

区分方法：man 2 = 系统调用，man 3 = 库函数。有的库函数是薄封装（一次 syscall），有的是纯用户态（不进内核），有的是多层（缓冲 + syscall）。

自测题

题目 1（选择）： 用户态程序想要读取硬盘上的文件，必须通过什么方式？

A. 直接访问硬盘内存地址 B. 通过系统调用请求内核代劳 C. 通过 C 语言 fopen 函数（不涉及内核） D. 通过 DMA 直接传输

参考答案

B。用户态程序不能直接访问硬件，必须通过系统调用（open/read）请求内核代劳。C 选项错误：fopen 内部也会调用 open 系统调用进入内核。

题目 2（判断）： 用户态和内核态运行在同一个地址空间，只是权限不同。

参考答案

正确（Linux 的虚拟内存模型）。用户态和内核态共享同一个虚拟地址空间，但用户态代码只能访问用户空间部分（低地址），内核空间（高地址）受硬件保护。系统调用时不需要切换页表，只是 CPU 特权级变化（ring 3 → ring 0）。

题目 3（踩坑）： 以下代码有什么性能问题？

char buf[4096];
for (int i = 0; i < 4096; i++)
    read(fd, &buf[i], 1);
参考答案

每次 read(fd, &buf[i], 1) 触发一次系统调用（用户态→内核态上下文切换），4096 次循环 = 4096 次上下文切换，开销巨大。应一次读完：read(fd, buf, 4096)，只有 1 次系统调用。系统调用开销远贵于普通函数调用，批量操作是基本优化手段。

题目 4（应用）： 解释为什么 HFT 低延迟系统要尽量减少系统调用，并列出两种替代方案。

参考答案

系统调用需要用户态→内核态切换（保存寄存器、切换栈、权限检查），开销在数百 ns 级别，对 HFT 微秒级延迟敏感的场景影响显著。

替代方案： 1. mmap：把文件/设备内存映射到用户态地址空间，后续读写不需要 syscall，直接访问内存 2. 批量 I/O：一次 read/write 传输大量数据，减少 syscall 次数；或用 io_uring 异步批量提交

代码示例

#include <unistd.h>
#include <errno.h>
#include <string.h>

int main(void) {
    int fd = open("/nonexistent", 0);
    if (fd < 0)
        printf("errno=%d: %s\n", errno, strerror(errno));
    return 0;
}

2.2

The Shell

本章：TLPI 第 02 章 — Fundamental Concepts

本节讲什么

Shell 是用户与内核交互的命令行解释器。本节介绍 shell 的角色、常见实现（bash/dash/zsh）以及它与系统调用的关系。

要点

Shell 的本质

Shell 是一个普通用户态进程，它循环执行：读取命令 → 解析 → fork+exec 子进程 → 等待完成。

/* shell 的核心循环（简化） */
while (1) {
    printf("$ ");
    if (fgets(cmd, sizeof(cmd), stdin) == NULL) break;
    pid_t pid = fork();
    if (pid == 0) {
        execvp(cmd, args);  /* 子进程执行命令 */
        perror("execvp");
        _exit(1);
    }
    waitpid(pid, &status, 0);  /* 父进程等待 */
}

常见 Shell

Shell 路径 特点
bash /bin/bash GNU 默认，功能最全
dash /bin/dash Debian 轻量，/bin/sh 常指向它
zsh /usr/bin/zsh 交互体验好，补全强
fish /usr/bin/fish 现代，非 POSIX 兼容

Shell 脚本 vs C 程序

  • Shell 脚本：快速编排命令，适合系统管理
  • C 程序：需要性能/底层访问时使用
  • HFT 系统中 shell 用于启动/监控脚本，核心逻辑用 C/C++

常见误区

误区 纠正
shell 是内核的一部分 shell 是普通用户态进程
system() 直接执行命令 system() 内部调用 /bin/sh -c

  • shell 的本质是什么？它是内核的一部分吗？
  • system() 和 fork()+exec() 的区别？

Users and Groups

本章：TLPI 第 02 章 — Fundamental Concepts

本节讲什么

Linux 的用户和组模型：UID/GID、超级用户 root、权限检查基础。

要点

用户和组

  • 每个用户有唯一的 UID（user ID），root 的 UID = 0
  • 每个组有唯一的 GID（group ID）
  • 用户可属于多个组（supplementary groups）
  • /etc/passwd 存用户信息，/etc/group 存组信息

权限检查

内核对每个系统调用做权限检查，比较进程的 UID/GID 与文件的 owner/group/other 权限位。

相关概念（后续章节详述）

概念 章节

set-user-ID 程序 ch09
supplementary groups ch08/ch09
capabilities（细粒度权限） ch39

常见误区

误区 纠正
root 不受任何限制 root 仍受 MAC（SELinux/AppArmor）约束
UID=0 就是 root 是的，内核只检查 UID==0

自测要点

  • UID 和 GID 分别标识什么？root 的 UID 是多少？
  • 一个用户可以属于多少个组？

Linux 的单根目录树（/）、目录、硬链接和软链接的基本概念。

要点

单根目录树

Linux 只有一个目录树，根目录是 /。所有文件系统挂载到这棵树的某个节点。

目录和路径

  • . 当前目录，.. 父目录

File I/O Model

本章：TLPI 第 02 章 — Fundamental Concepts

本节讲什么

Linux 的"一切皆文件"模型：打开文件得到 fd，通过 fd 读写，最后关闭。

要点

万物皆文件

Linux 用统一的 I/O 模型操作所有资源：普通文件、设备、管道、套接字都用同一套 API。

文件描述符（FD）

  • 非负整数，进程级别的句柄
  • 每个进程默认有 3 个：0(stdin)、1(stdout)、2(stderr)
  • open() 返回新 fd，close() 释放
  • fd 是进程私有的小整数，指向内核的打开文件表

核心 I/O 系统调用

操作 系统调用 说明
打开 open() 返回 fd
读 read() 从 fd 读数据
写 write() 向 fd 写数据
关闭 close() 释放 fd

本节讲什么

内存映射（mmap）的概念：将文件或设备映射到进程地址空间，通过内存访问代替 read/write。

要点

mmap 的基本思想

进程地址空间                    磁盘文件
┌──────────┐
│ ...      │
│ 映射区域  │ ←──→  文件内容
│ ...      │
└──────────┘
  • mmap() 创建映射，munmap() 解除
  • 映射区域可以是文件（file mapping）或匿名（anonymous mapping）
  • 访问映射内存 = 访问文件内容，由内核管理页缓存

两种映射类型

类型 用途

mmap 的优势

  1. 减少系统调用（一次映射，多次内存访问）
  2. 内核自动管理页缓存
  3. 多进程可映射同一文件实现共享内存

常见误区

误区 纠正
mmap 一定比 read/write 快 小文件或顺序访问不一定，mmap 有 TLB 开销
mmap 的修改立即写回磁盘 需要 msync() 或 munmap() 时才刷写

Signals

本章：TLPI 第 02 章 — Fundamental Concepts

本节讲什么

信号（signal）是进程间通知机制：内核或进程可以向目标进程发送信号，目标进程收到后执行默认动作或自定义处理器。

要点

信号的本质

  • 信号是软件中断——内核向进程发送的异步通知
  • 每个信号有一个编号（1-31 标准，34-64 实时）和一个名称（SIGINT/SIGTERM/SIGKILL...）
  • 进程可以：接受默认动作、忽略、或自定义处理器（signal()/sigaction()）

常见信号

信号 编号 默认动作 来源
SIGINT 2 终止 Ctrl+C
SIGKILL 9 终止（不可捕获） kill -9
SIGSEGV 11 终止+core 非法内存访问
SIGTERM 15 终止 kill 默认
SIGCHLD 17 忽略 子进程状态变化

信号生命周期

发送方: kill(pid, sig) / raise(sig)
  ↓
内核: 检查目标进程是否阻塞该信号
  ↓ 未阻塞
目标进程: 下次从内核态返回用户态时执行处理器
  ↓
处理器执行完毕, 返回中断点

常见误区

误区 纠正
SIGKILL 可以被捕获 不可以，SIGKILL 和 SIGSTOP 不可捕获/阻塞
信号可以传大量数据 标准信号只传编号，实时信号可携带少量数据

章节自测

  1. 为何进程不能直接访问对方内存？靠什么隔离？
    各有独立 虚拟地址空间；由 内核 + MMU/页表 隔离保护。

  2. 系统调用为何有性能开销？
    特权级切换、保存/恢复上下文、进内核执行路径 — 上下文切换 成本。

  3. stdin/stdout/stderr 编号？
    0 / 1 / 2。

  4. 硬链接 vs 软链接？
    硬链接：多名字 → 同一 inode；软链接：存 路径字符串（可指不存在目标）。

  5. 测代码耗时用哪种时钟？
    用 单调/CPU 相关计时（如 CLOCK_MONOTONIC 一类）；不要用会跳变的墙上日历时间当唯一依据。书中「CPU 时间」适合看占核；测墙钟耗时用 单调时钟 更稳妥。
