易错清单

  1. 多线程改掩码用 pthread_sigmask，勿靠 sigprocmask（MT 语义已废除）
  2. 「掩码进程级共享」是错觉——处置共享，掩码每线程独立
  3. 主线程 return/exit 杀光线程；要留 worker 用 pthread_exit
  4. 多线程 fork → 子进程只准 async-signal-safe → 立刻 exec
  5. sigwait 优于满地异步 handler；前置 = 调用线程已阻塞目标信号
  6. pthread_kill 不能跨进程（pthread_t 本进程才有意义）
  7. 子线程栈不增长（无 VM_GROWSDOWN）；主线程栈可以
  8. 每线程 16KB 内核栈是立即占用的物理内存，且不计入进程 RSS
  9. NPTL = 1:1；pthread_t ≠ 内核 TID，观测工具只认 TID
  10. exec 杀线程没有任何清理回调（对比 cancel 的 cleanup 栈）——exec 前自己 quiesce
  11. rwlock 默认读者优先——写延迟敏感场景会写饥饿
  12. PROCESS_SHARED 忘设 → 跨进程假同步（futex key 各自哈希）
  13. robust 锁是 fork 幽灵锁唯一能"检测存活"的方案（EOWNERDEAD + consistent）
  14. pthread_atfork 的 child 回调里重新初始化锁，不是解锁无主锁
  15. barrier 的 SERIAL_THREAD 每轮可能落在不同线程——不能假设固定收尾者

线程栈

源码核验：Linux v6.6 · arch/x86/include/asm/page_64_types.h（THREAD_SIZE:16 = 16KB 内核栈）· kernel/fork.c（alloc_thread_stack_node():272，栈缓存复用注释 :303-306） 本章：TLPI 第 33 章 — Threads: Further Details - 上一节：本章首页（33.1 为首节） - 下一节：33.2 线程与信号（重难点）

本节讲什么

  1. 每个线程的栈在地址空间里长什么样——主线程栈和子线程栈是两种不同的东西？
  2. 栈大小从哪来：RLIMIT_STACK、pthread_attr_setstacksize、PTHREAD_STACK_MIN 的关系？
  3. 栈用完了会怎样——溢出的三种结局？

要点

主线程栈 vs 子线程栈：三个本质差异

这是本节最容易被忽略的认知——「线程栈」这个词掩盖了两套完全不同的机制：

维度 主线程栈 子线程栈
位置 进程栈区（高地址，0x7ffc... 附近，紧邻环境变量） mmap 区（0x7f... 中段，与库/共享内存同区）
分配者 内核 execve 时静态划定 glibc 调 mmap(MAP_STACK) 动态分配
可增长 ✅ expand_downwards() 按需向下扩展（VMA 可变） ❌ 固定大小，溢出即玩完
默认大小 RLIMIT_STACK（通常 8MB） glibc 取 RLIMIT_STACK（unlimited 时退回 2MB）
guard 页 无（溢出撞到的是别的 VMA 或空洞 → SIGSEGV） 有（默认 1 页 4KB 只读 guard）

为什么主线程栈可以增长？它的 VMA 带 VM_GROWSDOWN 标志，缺页时内核检查是否向下越界、在限额内就扩。子线程栈是普通匿名映射，没有这个标志——新线程栈不增长。

栈大小的 API 层

pthread_attr_setstacksize(attr, size)      /* 设大小，必须 ≥ PTHREAD_STACK_MIN */
pthread_attr_getstacksize(attr, &size)
pthread_attr_setstack(attr, addr, size)    /* 自备内存当栈（少用：需 4KB 对齐） */
pthread_attr_setguardsize(attr, size)      /* 0 = 关 guard */
sysconf(_SC_THREAD_STACK_MIN)              /* = PTHREAD_STACK_MIN，通常 16KB */

规则速记：

  • 设小于 PTHREAD_STACK_MIN（16KB）→ pthread_attr_setstacksize 返回 EINVAL；
  • guard 计入 mmap 总量但不计入 stacksize（后者是可用区）；
  • setstack 与 setstacksize/guardsize 互斥（一次设置覆盖另一侧）。

每线程的隐藏成本（HFT 算账用）

成本 大小 归属
用户态栈（虚拟） 默认 8MB/线程 mmap 地址空间
用户态栈（物理） 按需，只算触碰过的页 RSS
内核栈 16KB/线程（THREAD_SIZE = PAGE_SIZE << 2） 物理内存立即占用，不可分页
guard 页 4KB 8MB 里划出（虚拟）

1000 线程 = 16MB 内核栈物理内存 + 8GB 虚拟地址。内核栈用 __vmalloc_node_range() 分配（kernel/fork.c:309）且带缓存复用（:303-306 注释：线程退出后栈保留在 per-CPU 缓存，下一个新线程直接复用——省去 16KB 的分配/清零）。

栈溢出的三种结局

  1. 越过后撞 guard 页（小步溢出，如深递归）→ guard 页不可写 → SIGSEGV，崩溃点就在栈附近（好排查）；
  2. 一步跨过 guard 页（大缓冲区写入，如 char buf[8192] 溢出）→ guard 只有 4KB，直接踩进相邻 VMA → 可能不立即崩，数据悄悄坏（最难排查）；
  3. 主线程栈溢出（无 guard）→ 撞到任意映射 → SIGSEGV 或静默写坏别的数据。

HFT / 嵌入式关联

路线 要点
嵌入式 线程数 × 栈 = 硬内存预算：内核栈 16KB/线程是立即占用的物理内存，512MB 板子开 5000 线程光内核栈就烧 80MB
HFT 一核一线程 + 小栈（1~2MB）：既控制地址空间总量，又让所有线程常驻不同核的 cache；栈顶地址对齐到 2MB/4MB 边界可降低 TLB 压力
HFT 热路径禁深递归：每层 ~32B（实测 x86-64），1MB 栈 ≈ 3 万层余量，但递归本身是不确定延迟源

/* stack_probe.c — Ch33.1：主线程栈 vs 子线程栈的地址空间布局实测
 * 观测：三线程地址分区 / 默认栈大小 / PTHREAD_STACK_MIN / RLIMIT
 * 编译：gcc -O2 -Wall -Wextra -o stack_probe stack_probe.c -pthread
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <pthread.h>
#include <unistd.h>
#include <sys/resource.h>

static void print_frame(const char *who, int depth)
{
    char pad[32];
    memset(pad, ' ', depth * 2);
    pad[depth * 2] = '\0';
    char probe[16];
    printf("%s%-10s 帧地址 %p\n", pad, who, (void *)probe);
    if (depth > 0)
        print_frame(who, depth - 1);      /* 递归 5 层，观测 SP 下移 */
}

static void *worker(void *arg)
{
    long id = (long)arg;
    char name[16];
    snprintf(name, sizeof name, "worker%ld", id);
    print_frame(name, 5);
    return NULL;
}

int main(void)
{
    printf("== 栈属性 ==\n");
    printf("PTHREAD_STACK_MIN      = %d B (%d KB)\n",
           (int)sysconf(_SC_THREAD_STACK_MIN),
           (int)(sysconf(_SC_THREAD_STACK_MIN) / 1024));

    struct rlimit rl;
    getrlimit(RLIMIT_STACK, &rl);
    printf("RLIMIT_STACK           = ");
    if (rl.rlim_cur == RLIM_INFINITY) printf("unlimited（glibc 子线程退回 2MB）\n");
    else                                printf("%llu MB\n", (unsigned long long)(rl.rlim_cur >> 20));

    pthread_attr_t attr;
    pthread_attr_init(&attr);
    size_t ss = 0, gs = 0;
    pthread_attr_getstacksize(&attr, &ss);
    pthread_attr_getguardsize(&attr, &gs);
    printf("子线程默认 stacksize   = %zu B（%zu MB）\n", ss, ss >> 20);
    printf("子线程默认 guardsize   = %zu B\n", gs);
    pthread_attr_destroy(&attr);

    printf("\n== 地址空间分区（主线程高地址 / 子线程 mmap 区）==\n");
    print_frame("main", 5);

    pthread_t t[3];
    for (long i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, worker, (void *)i);
    for (int i = 0; i < 3; i++)
        pthread_join(t[i], NULL);
    return 0;
}

自测题

题目 1（判断）： 子线程栈默认 8MB 用完后会自动增长吗？

参考答案

不会。只有主线程栈的 VMA 带 VM_GROWSDOWN 标志（expand_downwards 按需扩展）；子线程栈是 glibc 用 mmap 映的普通匿名区，固定大小——新线程栈不增长，写越界要么撞 guard 页 SIGSEGV，要么跨过 guard 踩坏相邻 VMA。

题目 2（计算）： 512MB 内存的嵌入式板子，最多开多少个线程才安全（只算内核栈）？

参考答案

每线程内核栈 THREAD_SIZE = 16KB（PAGE_SIZE << 2，v6.6 x86-64 page_64_types.h:16）物理内存、立即占用、不可分页。512MB 全给线程栈（不现实，仅算上限）= 32768 个；实际还要留用户态物理页 + 内核其他结构，工程上按内存 5~10% 预算 → 1600~3200 线程量级。

题目 3（概念）： guard 页为什么只能挡「小步溢出」？

参考答案

guard 默认 1 页（4KB）且位于栈底之下（低地址）。递归类小步溢出每帧只向下挪几十字节，会先踩进 guard → SIGSEGV（好排查）。但单个大写入（如 char buf[8192] 的 memset）一步跨过 4KB guard 直接命中相邻 VMA——可能不崩，数据悄悄坏。

题目 4（观察）： 怎么用 pmap 或 /proc/pid/maps 区分主线程栈和子线程栈？

参考答案

主线程栈是 [stack] 标记的 VMA（高地址）；子线程栈无专门标记，表现为 mmap 区的匿名 VMA（[ anon ]，4KB/8MB 大小、前后常伴一个 ---p（无权限）小段即 guard）。demo 里 worker 帧地址 0x7f4f... 与 main 的 0x7ffc... 分区即直接证据。

  2. kill 发的信号到底哪个线程收到？内核怎么选（不是随机）？

要点

信号模型：共享与私有的精确分界

属性 作用域 说明
信号处置（handler/DFL/IGN） 进程级共享 所有线程共用一张 sigaction 表（sighand 结构，CLONE_SIGHAND 才共享）
信号掩码 每线程独立 每个 task_struct 自带 blocked 位图——不存在"进程掩码"
进程级 pending（shared_pending） 进程级 kill()/终端发给进程的信号先进这里

handler 的执行 跑在收到信号的那条线程上 用该线程的栈，异步于该线程的控制流

⚠ 速记口诀：处置共享，掩码私有；来源决定队列（进程级/线程级），投递选定线程。

                return;                        /* 单线程且它不想要 → 挂着 */
        else {
                t = signal->curr_target;       /* ② 从上次投递目标开始轮转 */
                while (!wants_signal(sig, t)) {
                        t = next_thread(t);
                        if (t == signal->curr_target)
                                return;        /* 全组都不想要 → 挂在共享队列 */
                }
                signal->curr_target = t;       /* 更新轮转游标 */
        }
        ...
        signal_wake_up(t, sig == SIGKILL);     /* 唤醒被选中的线程 */
}

wants_signal():987 的判定（不想要的四种情况）：

if (sigismember(&p->blocked, sig))      return false;  /* 阻塞了 */
if (p->flags & PF_EXITING)              return false;  /* 快死了 */
if (task_is_stopped_or_traced(p))       return false;  /* 停止/被追踪 */
return task_curr(p) || !task_sigpending(p);            /* 正在跑或没有积压 */

四个推论：

  1. 不是随机：从 curr_target 轮转，连续发同信号会依次落到不同线程（但若某线程独占解除阻塞，wants_signal 只有它满足，全部进它）；
  2. 全组都阻塞 → 挂在共享 pending 队列，谁先解除阻塞谁在返回用户态时优先取走；
  3. 定向信号（pthread_kill/tgkill，PIDTYPE_PID）跳过轮转直接指名——这就是"仅同进程内"的 pthread_kill 内核路径（do_send_specific():3935，Ch32 已核验）；
  4. 致命信号广播：complete_signal 下半段发现 sig_fatal 且非 core 场景，直接给全组每个线程塞 SIGKILL 并 SIGNAL_GROUP_EXIT——一个线程杀全组。

三件套 API

int pthread_sigmask(int how, const sigset_t *set, sigset_t *oldset);
int pthread_kill(pthread_t thread, int sig);   /* 仅同进程；跨进程用 tgkill(2) */
int sigwait(const sigset_t *set, int *sig);    /* 同步取走：不装 handler */
API 内核真身 要点
pthread_sigmask rt_sigprocmask():3177 系统调用（glibc 薄包装） 与 sigprocmask 同一 syscall；多线程程序里禁止用 sigprocmask（SUSv3 已废除其 MT 语义）
pthread_kill tgkill(tgid, tid, sig) → do_send_specific():3935 线程级 pending 队列；目标线程已退出 → ESRCH
sigwait 原子「取消阻塞 + 等待」循环（glibc 用户态实现） 前提：调用线程已阻塞这些信号；取走后不执行 handler

sigwait 的原子性：它先检查共享+线程 pending 队列，没有就睡（sigtimedwait syscall）——没有「先解除阻塞再等」的窗口，信号不会在这中间漏给别的线程或触发 handler。

推荐架构：sigwait 专用线程

main 启动（最先做的事）
  │ pthread_sigmask(SIG_BLOCK, {SIGINT,SIGTERM,SIGHUP,...})   ← 此后创建的线程全部继承阻塞
  │
  ├── 信号线程：sigwait(&set, &sig) → 翻译成内部事件（管道/事件fd/原子标志）
  ├── 业务线程 A/B/C：不装 handler，永不接收信号（全阻塞）
  └── 主线程：join / 事件循环

收益（相对 async handler）：

  1. handler 里什么都不能调（async-signal-safe 限制）→ sigwait 线程是普通线程，随便用 printf/malloc/lock；
  2. 异步信号在任意业务线程的任意指令间打断 → 确定性灾难（HFT 热路径毛刺）→ sigwait 线程集中处理，业务线程零干扰；
  3. 信号语义从「异步中断」变成「同步消息」——可以排队、可以日志、可以优雅退出。

HFT / 嵌入式关联

路线 要点
HFT 信号线程 + 全员阻塞是部署标准：热路径线程绝不允许被 SIGALRM/自定义信号异步打断；优雅退出统一走 sigwait → 广播 shutdown 事件
嵌入式 kill(pid, sig) 的进程级投递 + curr_target 轮转意味着「信号可能落在任何线程」——信号驱动的单线程假设在 MT 化后直接破坏；sigwait 模式让信号处理可预测
通用 pthread_kill 定向投递是给单线程「发中断」的合法手段（如打断阻塞中的 IO 线程），但要配 handler 或 sigwait 消费

代码示例

/* sig_model.c — Ch33.2：信号投递模型三组实测
 * demo1: 3 线程全阻塞，只有 worker1 解除阻塞 SIGUSR1 → kill() 进程级信号必落 worker1
 * demo2: pthread_kill 定向 → 只有目标线程的 handler 跑
 * demo3: sigwait 线程取走 SIGTERM（不触发 handler）
 * 编译：gcc -O2 -Wall -Wextra -o sig_model sig_model.c -pthread
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <pthread.h>
#include <signal.h>
#include <unistd.h>
#include <errno.h>
#include <sys/syscall.h>

static volatile sig_atomic_t got_in[4];
static volatile sig_atomic_t handler_ran;
static int unblock_all;                       /* demo2 置 1：全员解除阻塞 */

static void handler(int sig)
{
    handler_ran = 1;
    int tid = (int)syscall(SYS_gettid);
    for (int i = 0; i < 4; i++)
        if (got_in[i] == -tid) { got_in[i] = sig; return; }
}

static void *worker(void *arg)
{
    long id = (long)arg;
    got_in[id] = -(int)syscall(SYS_gettid);    /* 登记内核 TID（负数=待命） */

    if (id == 1 || unblock_all) {
        sigset_t set;
        sigemptyset(&set);
        sigaddset(&set, SIGUSR1);
        pthread_sigmask(SIG_UNBLOCK, &set, NULL);
    }
    sleep(3);                                  /* 等信号窗口 */
    return NULL;
}

static void *sigwaiter(void *arg)
{
    (void)arg;
    int sig;
    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, SIGTERM);
    for (;;) {
        if (sigwait(&set, &sig) != 0) break;
        printf("  [sigwait 线程] 取到信号 %d（handler_ran=%d，handler 没跑）\n",
               sig, (int)handler_ran);
        if (sig == SIGTERM) return NULL;
    }
    return NULL;
}

int main(void)
{
    /* 1. 创建任何线程前阻塞全部实验信号 → 所有线程继承 */
    sigset_t all;
    sigemptyset(&all);
    sigaddset(&all, SIGUSR1);
    sigaddset(&all, SIGTERM);
    pthread_sigmask(SIG_BLOCK, &all, NULL);

    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigaction(SIGUSR1, &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);

    printf("== demo1: 进程级投递只落解除阻塞的线程 ==\n");
    pthread_t t[3];
    for (long i = 0; i < 3; i++) pthread_create(&t[i], NULL, worker, (void *)i);
    usleep(200 * 1000);                        /* 等线程登记 */
    kill(getpid(), SIGUSR1);                   /* 进程级发送 */
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    for (int i = 0; i < 3; i++)
        printf("  worker%d %s\n", i, got_in[i] > 0 ? "收到 SIGUSR1" : "（阻塞，未收）");

    printf("== demo2: pthread_kill 定向（全员未阻塞，看谁收到）==\n");
    handler_ran = 0;
    unblock_all = 1;                           /* 全员解除阻塞：投递才有三选一 */
    memset((void *)got_in, 0, sizeof got_in);
    pthread_t t2[3];
    for (long i = 0; i < 3; i++) pthread_create(&t2[i], NULL, worker, (void *)i);
    usleep(200 * 1000);
    pthread_kill(t2[2], SIGUSR1);              /* 定向第三个 */
    for (int i = 0; i < 3; i++) pthread_join(t2[i], NULL);
    printf("  worker0/1/2 收到 = %d/%d/%d（定向只进 worker2）\n",
           got_in[0] > 0, got_in[1] > 0, got_in[2] > 0);

    printf("== demo3: sigwait 同步取信号 ==\n");
    handler_ran = 0;
    pthread_t sw;
    pthread_create(&sw, NULL, sigwaiter, NULL);
    usleep(100 * 1000);
    kill(getpid(), SIGTERM);                   /* 进程级 SIGTERM */
    pthread_join(sw, NULL);
    printf("  handler_ran=%d（sigwait 模式下 handler 完全不跑）\n", (int)handler_ran);
    return 0;
}

实测输出（WSL2 / 12 核，gcc -O2 零告警）：

== demo1: 进程级投递只落解除阻塞的线程 ==
  worker0 （阻塞，未收）
  worker1 收到 SIGUSR1
  worker2 （阻塞，未收）
== demo2: pthread_kill 定向（全员未阻塞，看谁收到）==
  worker0/1/2 收到 = 0/0/1（定向只进 worker2）
== demo3: sigwait 同步取信号 ==
  [sigwait 线程] 取到信号 15（handler_ran=0，handler 没跑）
  handler_ran=0（sigwait 模式下 handler 完全不跑）

三点解读：

  1. demo1 是 complete_signal 算法的活体演示：wants_signal() 对 worker0/2 因 blocked 判 false，轮转游标最终停在 worker1——全组唯一解除阻塞的线程。10 次运行 10 次落 worker1（确定性，不是概率）。
  2. demo2 验证定向队列：全员解除阻塞（排除掩码因素）后 pthread_kill → tgkill → 线程级 pending，仍只有 worker2 的 handler 跑——定向与「挑哪个未阻塞线程」的进程级选择互不相干。 （推论：若目标线程阻塞着该信号，定向信号进它的线程 pending 挂起——handler 要等它解除阻塞才跑，期间不丢。）
  3. demo3 的 handler_ran=0：SIGTERM 明明装了 handler，但被 sigwait 线程同步取走——signal 的「异步中断」语义被改写成「消息」。这就是推荐架构的根基。

自测题

题目 1（辨析）： 「多线程进程的信号掩码是进程级共享的」——对吗？

参考答案

错。掩码每线程独立（每个 task_struct 自带 blocked）。共享的是：信号处置表（sighand，CLONE_SIGHAND 复制并共享）、进程级 pending 队列（shared_pending）。pthread_sigmask 改的只是本线程的掩码——这正是「创建线程前主线程先阻塞 → 全体继承」模式成立的原因（新线程继承创建者的掩码副本）。

题目 2（内核）： kill(pid, SIGUSR1) 发给 4 线程进程，其中 3 个阻塞了 SIGUSR1、1 个没阻塞。信号一定被谁接收？如果 4 个全阻塞呢？

参考答案

未阻塞的那 1 个。complete_signal():1004 的轮转循环里 wants_signal():987 因 blocked/PF_EXITING/stopped 对另外 3 个返回 false，游标停在唯一合格者。全阻塞时：循环回到 curr_target 起点仍未找到 → 函数返回，信号留在共享 pending 队列；之后任何一个线程解除阻塞并在返回用户态时检查到它，就取走。

题目 3（设计）： 多线程热路径服务要处理 SIGTERM 优雅退出，为什么不能在 handler 里直接置 flag + printf 日志？

参考答案

① handler 是 async-signal-unsafe 重灾区：printf 动 stdio 锁（可能恰好被中断线程持有 → 死锁）；② 信号可能落在任意业务线程任意指令间——complete_signal 轮转不保证目标，热路径被随机打断本身就是延迟毛刺；③ 队列不保证（标准信号合并），快速连发只记一次。正确姿势：全员阻塞 + sigwait 专用线程取信号 → 写管道/事件 fd → 主循环统一处理（demo3 模式）。

题目 4（API 细节）： sigwait 的前置条件是什么？违反了会怎样？

参考答案

调用线程必须已阻塞待等信号（pthread_sigmask(SIG_BLOCK, ...)）。sigwait 是"原子地检查 pending 并取走，否则睡在 sigtimedwait 上"——若信号未阻塞且装了 handler，信号可能在进入 sigwait 之前就被递送、handler 抢跑；未阻塞且无 handler 则默认动作直接生效（SIGTERM 杀进程）。实践中先在创建线程前阻塞、再起 sigwait 线程，继承保证前置成立。

题目 5（陷阱）： pthread_kill(tid, sig) 可以给另一个进程的线程发信号吗？给已退出的线程发呢？

参考答案

不能跨进程：pthread_t 是本进程 glibc 的 struct pthread *，跨进程无意义；内核路径 tgkill(tgid, tid, sig)（do_send_specific():3935）本身就限定同 tgid。给已 join/退出的线程发：pthread_t 可能已被复用（栈缓存复用，29.5 警告），信号可能打到新线程——这是必须 join 之后再丢弃 pthread_t 的原因之一；内核侧若 TID 已死则 ESRCH。

33.3

进程控制

源码核验：Linux v6.6 · fs/exec.c（de_thread():1044 · group_exec_task 窃 PID 机制 :1093）· kernel/signal.c（zap_other_threads():1378）· kernel/exit.c（do_group_exit():999） 本章：TLPI 第 33 章 — Threads: Further Details - 上一节：33.2 线程与信号（重难点） - 下一节：33.4 实现模型

本节讲什么

  1. fork / exec / exit 三个老朋友在多线程环境下各变成什么语义？
  2. 「多线程 fork 后锁状态错乱」的内核层解释——为什么死锁是必然而非概率？
  3. pthread_atfork 能救多少？它的执行顺序和用途边界？

要点

三大调用 × 多线程语义总表

调用 子进程/结果 其他线程 内核路径
fork() 只复制调用线程（变单线程进程） 父进程全部继续 copy_process() 不带 CLONE_THREAD → 新线程组
exec() 成功后调用线程独活（地址空间全换） 全被杀光 de_thread():1044 → zap_other_threads():1378
exit() / main return — 整组全灭 do_group_exit():999 → 每线程塞 SIGKILL
主线程 pthread_exit() — 继续活（与 return 相反！） 只是本线程 do_exit()，无 group exit
任一线程被致命信号 — 整组全灭 complete_signal() 下半段全组广播（33.2）

fork：单线程子进程 + 锁的「幽灵状态」

fork 只复制调用线程（copy_process 不带 CLONE_THREAD 位，子进程是全新单线程组）。但地址空间是 COW 全量复制——包括所有锁的内存状态。

死锁机理（必然性论证）：

父进程（2 线程）                     fork 时刻的内存快照
├── 线程 A：持有 mutex M（M.locked=1）
└── 线程 B：调用 fork()              ──COW──▶  子进程（只有 B）
                                                ├─ M.locked=1  ← 锁状态原样继承
                                                └─ 持有者 A？不存在（没被复制）
子进程 lock(M)：
  glibc 看 M.locked=1 → 走 futex_wait 等待解锁
  但唯一能解锁的 A 在父进程里（另一个地址空间实例）
  → 子进程睡死。这不是概率，是结构性死锁。

三类高危锁：malloc 内部 arena 锁（子进程任何 malloc/printf 都可能踩）、stdio 流锁（printf 直接进锁）、用户全局 mutex。POSIX 结论：fork 后子进程在 exec 前只准调用 async-signal-safe 函数——因为 async-signal-safe 的约束（不可持锁）恰好覆盖这个场景。

exec：de_thread 的「窃取 PID」绝活

exec 杀光其他线程由 fs/exec.c:1264 的 de_thread(me) 完成（v6.6 核验）：

static int de_thread(struct task_struct *tsk)          // fs/exec.c:1044
{
        ...
        sig->group_exec_task = tsk;                     // 标记：exec 进行中
        sig->notify_count = zap_other_threads(tsk);     // :1067 杀光其他线程
        while (sig->notify_count) {                     // 等它们真正退出
                __set_current_state(TASK_KILLABLE);
                schedule();
        }
        ...
        if (!thread_group_leader(tsk)) {                // :1093 调用者不是 leader？
                struct task_struct *leader = tsk->group_leader;
                ...                                     // 等 leader 变 inactive
                /* 并 swap PID：非 leader 线程 exec 后"顶替"leader 的 PID */
        }
}

两个要点：

  1. 谁 exec 谁独活——不管是不是主线程。非 leader 线程 exec 时，内核让它接管 leader 的 PID（TID/TGID 换位）——因为 POSIX 语义要求 exec 后进程身份不变（getpid() 不能变）。这是 exec 实现里最精巧的一步；
  2. zap_other_threads()（kernel/signal.c:1378）给组内每个其他线程塞 SIGKILL 并等 notify_count 归零——exec 前其他线程持有的锁、正在写的数据全部戛然而止，没有清理机会（对比 Ch32 取消：至少还能跑 cleanup handler）。所以 exec 慎用于「其他线程有未落盘状态」的时刻。

exit 的不对称：return vs pthread_exit

主线程 其他线程 结果
return 任意 全灭（return 触发 exit() → exit_group 系统调用 → 每线程 SIGKILL）
exit() 任意 全灭（同上，do_group_exit():999）
pthread_exit() 任意 继续活（主线程只是普通线程退出；等价于 main 里 pthread_exit(NULL) 后进程"由剩下线程维持"）
_exit() 任意 全灭（直通 exit_group，绕过 atexit/flush）

主线程 return n 与 exit(n) 同效；想「主线程走人但 worker 跑完」必须用 pthread_exit。反过来 worker 里误调 exit() 会把整个进程（含主线程）带走——这是 MT 程序常见事故。

pthread_atfork：执行顺序与边界

pthread_atfork(prepare, parent, child);   /* 可注册多个，构成栈 */
阶段 执行者 顺序 典型用途
prepare 父进程（fork 前） 注册序（先注册先跑） 锁住全部共享锁
parent 父进程（fork 后） 注册逆序 解锁
child 子进程（fork 后） 注册逆序 重新初始化（而不是解锁）锁

边界（为什么"仅缓解"）：

  1. 只能锁你知道的锁——glibc 内部锁（malloc/stdio）轮不到你；
  2. prepare 持锁窗口里其他线程照常运行，fork 的 COW 快照仍可能切到不一致中间态；
  3. 多个库各自注册 atfork，顺序耦合脆弱；
  4. 子进程 child 里只能用 async-signal-safe 手段（此刻可能还持有一堆别人的锁）。

工程结论：多线程 + fork 的正解是 fork 后立即 exec（锁的幽灵状态被全新映像清空）；需要 fork-worker 模式时用 posix_spawn。

HFT / 嵌入式关联

路线 要点
HFT 多线程交易进程禁止 fork-worker（锁幽灵 + 抖动）；拉起外部工具一律 posix_spawn；exec 只在启动/重载配置用，且 exec 前自己确保无未落盘状态
HFT 主线程退出选 pthread_exit（让 logger/风控线程收尾）还是 exit（快速全灭）是关闭语义设计，不是细节
嵌入式 exec 的 de_thread 全杀意味着「热升级」方案里其他线程必须先自行 quiesce（进入无未提交状态点），否则状态丢失

代码示例

/* proc_ctrl.c — Ch33.3：fork/exec/exit 三语义实测
 * demo1: fork 锁幽灵 —— 子进程 trylock 得 EBUSY（持有者已不存在）
 * demo2: pthread_atfork 的 child 重初始化救场
 * demo3: exec 杀光其他线程 —— worker 心跳在 execl 后戛然而止
 * 编译：gcc -O2 -Wall -Wextra -o proc_ctrl proc_ctrl.c -pthread
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <pthread.h>
#include <unistd.h>
#include <errno.h>
#include <sys/wait.h>

static pthread_mutex_t m1 = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t m2 = PTHREAD_MUTEX_INITIALIZER;
static volatile sig_atomic_t heartbeat;

static void *locker(void *arg)
{
    (void)arg;
    pthread_mutex_lock(&m1);          /* 持有直到进程结束（不还） */
    return NULL;
}

static void *heart(void *arg)
{
    (void)arg;
    for (int i = 0; ; i++) {
        heartbeat = i;
        printf("  [worker] 心跳 %d（内核 TID 活着）\n", i);
        sleep(1);
    }
    return NULL;                      /* 不可达 */
}

static void atfork_prepare(void) { pthread_mutex_lock(&m2); }
static void atfork_parent (void) { pthread_mutex_unlock(&m2); }
static void atfork_child  (void)
{
    /* 子进程里：m2 处于锁定状态但持有者在父进程 → 重新初始化 */
    pthread_mutex_init(&m2, NULL);
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);          /* execl 前缓冲必须已落盘 */

    printf("== demo1: fork 锁幽灵（trylock 证据）==\n");
    pthread_t t;
    pthread_create(&t, NULL, locker, NULL);
    usleep(50 * 1000);                /* 等 locker 拿到 m1 */

    pid_t pid = fork();
    if (pid == 0) {
        int r = pthread_mutex_trylock(&m1);
        printf("  [子进程] trylock(m1) = %d (%s)\n", r,
               r == EBUSY ? "EBUSY：锁被'幽灵'持有，持有者不存在" : "拿到");
        _exit(0);
    }
    waitpid(pid, NULL, 0);

    printf("== demo2: pthread_atfork child 重初始化 ==\n");
    pthread_atfork(atfork_prepare, atfork_parent, atfork_child);
    pid = fork();                     /* prepare 锁 m2 → child 重初始化 → parent 解锁 */
    if (pid == 0) {
        int r = pthread_mutex_trylock(&m2);
        printf("  [子进程] trylock(m2) = %d（%s）\n", r,
               r == 0 ? "成功：atfork child 重初始化救场" : "EBUSY：仍被幽灵持有");
        _exit(0);
    }
    waitpid(pid, NULL, 0);

    printf("== demo3: exec 杀光其他线程 ==\n");
    pthread_t hw;
    pthread_create(&hw, NULL, heart, NULL);
    sleep(3);                         /* 看三秒心跳 */
    printf("  [main] execl(/bin/echo) —— de_thread() 即将杀光其他线程\n");
    fflush(stdout);
    execl("/bin/echo", "echo", "  [新映像] exec 完成：只剩 exec 调用线程", (char *)NULL);
    perror("execl");                  /* 只有失败才到这 */
    return 1;
}

实测输出（WSL2 / 12 核，gcc -O2 零告警）：

== demo1: fork 锁幽灵（trylock 证据）==
  [子进程] trylock(m1) = 16 (EBUSY：锁被'幽灵'持有，持有者不存在)
== demo2: pthread_atfork child 重初始化 ==
  [子进程] trylock(m2) = 0（成功：atfork child 重初始化救场）
== demo3: exec 杀光其他线程 ==
  [worker] 心跳 0（内核 TID 活着）
  [worker] 心跳 1（内核 TID 活着）
  [worker] 心跳 2（内核 TID 活着）
  [main] execl(/bin/echo) —— de_thread() 即将杀光其他线程
  [worker] 心跳 3（内核 TID 活着）
  [新映像] exec 完成：只剩 exec 调用线程

三点解读：

  1. demo1 用 trylock 代替 lock 拿到「死锁的活性证据」：EBUSY（16）说明锁确实处于锁定态——持有者线程没有被复制，lock() 会永远睡在 futex 上。换 lock() 就是必然死锁现场。
  2. demo2 是 atfork 的标准用法：prepare 在 fork 前锁住 m2（快照里它是锁定态）→ child 回调里 pthread_mutex_init 重新初始化（不是解锁——解锁一个"无主"锁语义上没定义）→ trylock 成功。注意 prepare 必须是唯一加锁者：主线程若已手动持锁再 fork，prepare 再锁就是同线程二次加锁 = 死锁（本 demo 初版实测翻车点）。atfork 的价值与边界：只救你自己管理的锁。
  3. demo3：worker 心跳到 3（main 打印与 execl 之间它又跳了一拍——exec 杀线程需要走 de_thread 的等待循环，不是零耗时）后戛然而止、echo 的输出出现——de_thread() 杀线程没有任何清理回调（对比 pthread_cancel 至少有 cleanup 栈），exec 是「全场清零」。

自测题

题目 1（推演）： 4 线程进程，线程 3（非 leader）调用 execve() 成功。exec 后 getpid() 返回什么？为什么内核要这么设计？

参考答案

返回原 leader 的 PID（进程身份不变）。de_thread():1044 里若调用者非 leader：等 leader 进入 inactive 后接管（窃取）其 PID（:1093 起的换位逻辑）——把调用线程的 TID/TGID 与已退出的 leader 互换。原因：POSIX 语义要求 exec 不改变进程身份（父 shell 按 PID 追踪子进程、waitpid 才能工作）。

题目 2（对比）： 主线程 return 0、exit(0)、pthread_exit(NULL) 三者对其他线程的影响？哪个最常被误用？

参考答案

前两个等价——全组退出（return 触发 exit() → exit_group → 每线程 SIGKILL）；pthread_exit(NULL) 只退主线程，其他线程继续活，进程直到最后一个线程结束才退出。误用冠军是 return：写了 main 以为「函数结束」结果把后台 worker 全杀了；以及 worker 线程里调 exit()（本想退出自己，实际全灭）。

题目 3（设计）： pthread_atfork 的 child 回调里应该「解锁」还是「重新初始化」锁？为什么？

参考答案

重新初始化（pthread_mutex_init）。子进程里锁的"锁定"状态是从父进程 COW 快照继承的内存位，但持有者线程不存在——对一个无主锁 unlock 没有定义（glibc 的 ERRORCHECK 锁会返回 EPERM）。init 把锁结构清回出厂态，语义干净。但注意：这只对你自己的锁有效，glibc malloc/stdio 内部锁无解——所以 atfork 只是缓解，正解仍是 fork 后立即 exec。

题目 4（边界）： exec 杀其他线程时，那些线程正在持有的用户态锁会释放吗？正在写一半的缓冲区呢？

参考答案

都不会。de_thread() → zap_other_threads() 直接塞 SIGKILL 等 notify_count 归零——没有 cleanup handler、没有 TLS 析构、没有 atexit，锁的内存位留着但无意义（地址空间马上被新映像替换，届时全部清零）。所以「其他线程有未落盘数据」时 exec = 数据丢失。要热替换先让 worker quiesce（确认空闲点）再 exec。

题目 5（综合）： 多线程日志服务要支持「定时重开日志文件（SIGHUP）」和「优雅退出（SIGTERM）」，把 33.2 + 33.3 的机制串起来设计。

参考答案

① 启动最先 pthread_sigmask(SIG_BLOCK, {SIGHUP,SIGTERM})；② sigwait 线程同步取信号（handler 全不装）；③ SIGHUP → 写内部事件管道 → 日志线程在安全的 flush 点切换 fd（绝不在写入中途）；④ SIGTERM → 广播 shutdown 事件 → 各 worker 走各自 cleanup → 主线程 pthread_exit（或最后一个线程自然退出）。fork 不参与；若必须拉起压缩子进程用 posix_spawn。

33.4

实现模型

本章：TLPI 第 33 章 — Threads: Further Details - 上一节：33.3 进程控制 - 下一节：33.5 LinuxThreads vs NPTL

本节讲什么

  1. 用户线程 / 内核线程 / 映射关系——M:1、1:1、M:N 三种模型到底差在哪？
  2. 每种模型的「阻塞一次系统调用」会发生什么（这是模型选择的试金石）？
  3. 为什么 Linux 选了 1:1，而学界推崇的 M:N 在 Linux 上失败了？

要点

三种模型

M:1（用户级线程）              1:1（内核级，Linux/NPTL）       M:N（混合）
┌──────────────┐              ┌──────────────┐               ┌──────────────┐
│ M 用户线程    │              │ 用户线程 1     │               │ M 用户线程    │
│  ↑↓ 用户态    │              │  │  一一对应   │               │  ↑↓ 用户态    │
│ 调度器(库)    │              │ 内核线程 1     │               │ M':N 调度器   │
│  │            │              │  │            │               │  (库+内核协同) │
│ 1 内核线程    │              │ 内核线程 2     │               │ N 内核线程    │
└──────────────┘              │  ↑ 对应       │               └──────────────┘
 内核只见 1 个任务              │ 用户线程 2     │                内核见 N 个任务
                              └──────────────┘
维度 M:1 1:1 M:N
代表 早期 GNU Portable Threads / 协程（同思想） Linux NPTL、Windows Solaris（旧）、IRIX；Linux 尝试 NGPT 失败
创建成本 极低（库函数 + 栈切换） clone 系统调用（v6.6 实测 ~1-4μs 级，29.9 数据） 中（两层登记）
阻塞系统调用 全体拖死（内核只认那 1 个任务） 只睡这一个内核线程 库须拦截重写为非阻塞（"缝合层"）
多核并行 ❌（1 个内核任务只能上 1 核） ✅（每线程可绑不同核） ✅（N 个内核任务上 N 核）
抢占 仅在库调度点（协作式为主） 内核随意抢占（时间片/优先级） 两层抢占，复杂
信号/定时器粒度 进程级（内核不知道有 M 个） 线程级（task->pending 独立） 混乱（历史痛点）

试金石：一个线程 read() 阻塞了

  • M:1：read 阻塞的是唯一的内核任务 → 整个进程（含其他"线程"）卡死。库要自救必须把所有阻塞调用改写成非阻塞 + 就绪调度（等于重写半个内核接口）；
  • 1:1：只睡调用线程的内核任务，调度器换下一个；其他线程照常跑在不同核；
  • M:N：库拦截 read，登记到调度器，切到同核其他用户线程；完成后再切回——正确但每次都多一层库内切换，且任何没被拦截的"漏网"阻塞调用退化成 M:1 行为。

为什么 Linux 选择了 1:1

  1. 内核已经会调度：CFS 本来就是任务级调度器，1:1 直接复用，不需要库内再造一个调度器；
  2. SMP 免费拿：内核任务天然分布多核；
  3. 语义干净：阻塞、信号、抢占、ps/top/perf 全部按任务粒度工作，无观测盲区；
  4. M:N 的缝合成本证明过高：Linux 的 NGPT（IBM 推的 M:N 实现）在 NPTL 出现后被放弃——双层调度的复杂度（锁协作、阻塞拦截、亲和性传递）吃掉了理论收益。业界后验：连 Solaris 也在 Solaris 9/10 淘汰了 M:N，回 1:1。

「用户级轻量」思想的现代转世

M:1 并没有死，它换了个名字活在协程（goroutine 的 G-M 模型、C++20 coroutine、rust async）里：

  • 面对的还是同一对矛盾：切换成本 vs 阻塞语义；
  • 解法也还是老一套：运行时把阻塞调用改写成非阻塞 + 就绪队列（Go runtime 的 netpoller）；
  • 区别于 pthread：协程是协作式、绑定在线程上的二级调度——本质是"用户线程 2.0"，与 1:1 内核线程不冲突（goroutine 最终也跑在 OS 线程上）。
pthread（1:1） 协程（M:1 思想）
切换成本 1-6μs（进内核，29.9 实测 5.92μs WSL 放大值） ~10-100ns（用户态寄存器交换）
阻塞容忍 任意阻塞 必须 await/非阻塞，漏一个就拖死整核
抢占 内核强制 协作（Go 1.14+ 异步抢占仅限安全点）
适用 CPU 并行、隔离故障域 海量并发 IO（百万连接）

HFT / 嵌入式关联

路线 要点
HFT 1:1 = 线程可绑核 + SCHED_FIFO + perf 精确到线程——热路径观测性是 1:1 给的；协程适用于 IO 密集闸机（行情网关），策略计算仍用线程
嵌入式 RTOS 的 task ≈ 1:1 内核任务思想；无 MMU 小系统跑 M:1（协作式调度器）省栈省内存——模型选择=资源预算
通用 选型口诀：CPU 并行用线程，海量并发 IO 用协程，两者混合是常态（reactor 线程池 + 每核协程环）

自测题

题目 1（推演）： M:1 模型下，用户线程 A 阻塞在 read()，用户线程 B 还能跑吗？为什么？

参考答案

不能。内核视角只有 1 个任务，read 把它置为睡眠 → CPU 让给别人（别的进程），进程内所有用户线程一起冻结——内核根本不知道 B 存在。这正是 M:1 的死刑判决：任何未改写成非阻塞的阻塞调用都拖死全体。

题目 2（辨析）： 1:1 模型「每个 pthread 对应一个内核任务」——这个"对应"是什么机制建立的？

参考答案

glibc 的 pthread_create 调 clone(CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SYSVSEM|SETTLS...)——每线程就是一次 clone 产生的内核 task_struct（有自己的 PID/TID，gettid() 可见），CLONE_THREAD 使其加入同线程组（共享 TGID）。不是"对应"，而是本来就是同一个东西的两个视角：pthread_t 是 glibc 侧句柄，task_struct 是内核侧实体。

题目 3（判断）： 协程比线程"快"，所以高性能服务器应该全部用协程替代线程？

参考答案

错在场景混用。协程切换便宜（用户态 ~10-100ns vs 线程 1-6μs）是因为不进内核、不换地址空间语义——代价是协作式：一个协程跑死循环，同核其他协程全饿（除非异步抢占安全点）。CPU 密集并行仍要线程/进程铺满核；协程赢在海量并发 IO（百万连接的事件循环）。两者是分层关系（goroutine 跑在 OS 线程上）而非替代。

33.5

LinuxThreads vs NPTL

本章：TLPI 第 33 章 — Threads: Further Details - 上一节：33.4 实现模型 - 下一节：33.6 高级同步（简介）

本节讲什么

  1. LinuxThreads（1996）当年怎么"用进程模拟线程"，POSIX 语义哪些根本做不到？
  2. NPTL（2002-2003）靠哪三个内核新增机制达标？
  3. pthread_t ≠ 内核 TID 的身份认知——用什么查、怎么换算？

要点

LinuxThreads：没有 CLONE_THREAD 的年代

内核 2.0-2.4 只有 CLONE_VM|CLONE_FILES|CLONE_SIGHAND，没有线程组概念——每线程是一个独立 PID（内核任务），LinuxThreads 在此之上模拟 POSIX：

POSIX 要求 LinuxThreads 实际行为 后果
同进程同 PID 每线程独立 PID，只有 leader 是"进程 PID" kill(pid) 只发给 leader——其他线程要靠管理线程转发
信号发给"进程" 管理线程（额外克隆的第一个线程）拦截 SIGUSR1 等并转投 信号延迟一跳；标准信号合并语义怪异
getpid() 全线程一致 每线程返回自己的 PID 直接违反 POSIX
fork 后 kill 语义 依赖 leader 是否存在 杂乱
进程内线程数 管理线程 + 每线程一个系统任务 ps 里一片假进程

管理线程（manager thread）是 LinuxThreads 最标志性设计：它持有个信号转投和线程清理职责——也是最大的语义污染源。

NPTL 的三大内核地基（2.5.x / 2.6 引入）

内核机制 干什么 带来的 POSIX 达标
CLONE_THREAD / 线程组 clone 位把新任务挂进 signal->thread_head，共享 TGID getpid() 全组一致；kill() 按 TGID 投递进程级信号；/proc 只显示组长（/proc/tid 才见每线程）
CLONE_CHILD_CLEARTID + futex 唤醒 线程退出时内核 mm_release():1634 写 0 + futex(FUTEX_WAKE,1)（kernel/fork.c:1634-1635，29.7 核验过） pthread_join 不再轮询——睡在 futex 上
tgkill() / do_send_specific():3935 按 (tgid, tid) 精确投递 pthread_kill 语义正确，不撞 PID 复用（Ch32）
配套：TLS 支持（CLONE_SETTLS → set_new_tls():130） 每线程 fs base errno 每线程独立（31.4 反汇编实测）

结果：NPTL 通过了 POSIX compliance suite（含信号用例），性能上 10 万线程创建+join 也撑住了（当年 Ulrich Drepper 的著名基准）。

现代（glibc 2.34+）：LinuxThreads 彻底谢幕

  • glibc 2.34 起 libpthread 并入 libc——链接 -pthread 只是开启宏定义，不再有独立库；
  • 线程栈默认 8MB（= RLIMIT_STACK，unlimited 时退 2MB）；
  • 栈缓存：退出线程的栈进 per-CPU 缓存复用（kernel/fork.c:303-306 注释）。

身份换算表（必须刻进肌肉记忆）

想要什么 API 说明
glibc 线程句柄 pthread_self() → pthread_t 指针（struct pthread *），非整数、不可比较大小、会被复用
内核线程 ID gettid() / syscall(SYS_gettid) 全局唯一整数；/proc/<pid>/task/<tid>；pthread_t 无法换算成它（除非创建时线程自己上报）
进程 ID getpid() = TGID = 组长 TID
给线程发信号 pthread_kill(pthread_t)（进程内）或 tgkill()（裸） 见 33.2

⚠ pthread_t 和 TID 没有任何换算公式：一个在 glibc 堆/栈结构里，一个在内核。跨系统观测（top -H、perf）认 TID；代码内认 pthread_t。

HFT / 嵌入式关联

路线 要点
HFT 观测要线程粒度时用 TID：perf -t <tid>、taskset -p <mask> <tid>、/proc/<pid>/task/<tid>/stat（自旋/切换计数）——pthread_t 对工具链不可见

通用 musl 也是 1:1 + futex，语义同 NPTL（静态链接体积小——嵌入式友好）

自测题

题目 1（历史+内核）： NPTL 靠哪三个内核机制让 pthread_join 从"轮询/信号 hack"变成干净语义？

参考答案

① CLONE_THREAD 线程组（TGID 共享，进程身份统一）；② CLONE_CHILD_CLEARTID：线程退出内核写清 tid 字段并 futex(FUTEX_WAKE,1)（mm_release()，kernel/fork.c:1634-1635）——joiner 睡在这个 futex 上被精确唤醒；③ tgkill() 定向信号支撑 pthread_kill。LinuxThreads 时代只能靠管理线程 waitpid 轮询收尸。

题目 2（辨析）： pthread_t 是什么类型？能 printf("%d", tid) 吗？

参考答案

glibc 里是无符号长整（实为 struct pthread * 指针——栈底地址）。不是内核 TID：无换算公式、退出后可能被复用（栈缓存复用）、大小比较无意义。要看内核身份用 gettid()（glibc 2.30+）或 syscall(SYS_gettid)；跨工具（top -H/perf/sched）一律认 TID。

题目 3（判断）： glibc 2.34+ 之后程序不再需要链接 -lpthread，说明线程已经变成"纯用户库"了？

参考答案

错。libpthread 合并进 libc 只是库的组织形式变化——线程实体依然是 clone(CLONE_THREAD...) 出来的内核 task_struct，同步原语依然落在 futex 系统调用上（无竞争时用户态快路径，见 30.1）。1:1 模型一点没变，变的只是符号藏在哪个 .so 里。

高级同步（简介）

源码核验：Linux v6.6 · kernel/locking/rwsem.c（glibc rwlock 语义参照）· kernel/locking/spinlock.c · futex 坐标见 30.1 本章：TLPI 第 33 章 — Threads: Further Details - 上一节：33.5 LinuxThreads vs NPTL - 下一节：33.7 总结

本节讲什么

  1. mutex/condvar 之外的同步原语速览：rwlock / barrier / spinlock 各自的适用判据（不只是"是什么"）；
  2. PTHREAD_PROCESS_SHARED——同步对象怎么放进共享内存跨进程用；
  3. 每种原语的「误用之最」。

要点

四原语对照表

原语 语义 典型场景 误用之最
pthread_rwlock_t 读共享、写独占 读多写少（配置表：99% 查 1% 更新） 读锁内调写者也要读的共享缓存（递归死锁）；写饥饿（glibc 默认读者优先变体，写者可能饿死——有 _NP 变体可调）
pthread_barrier_t 集合点：全员到齐才一起过 分阶段并行（全员到齐再进下一 phase）；数据接力（A 们写完 B 们才能读） 期望它带数据传递——barrier 只同步不传值；忘了 PTHREAD_BARRIER_SERIAL_THREAD 只有一个线程拿到返回值这个事实
pthread_spinlock_t 忙等锁 核内短临界区（<几十 ns：改几个变量）且不可阻塞 临界区里出现任何系统调用/内存缺页/长循环——自旋烧掉整个时间片还拖慢持锁者（30.1 实测跨核 spin 81ns/次比 mutex 69ns 还慢）
PTHREAD_PROCESS_SHARED 属性（非新原语） mutex/condvar/rwlock/barrier 放共享内存跨进程 忘设 shared 属性 → 跨进程锁假成功（各自锁了各自的缓存行）；锁所在的共享内存被双方以不同地址映射时仍 OK（futex key 按物理页），但对象内不能存指针

读写锁：读者优先的代价

glibc 默认实现读者优先：只要有读者鱼贯而来，写者就一直排队——写饥饿是真实风险：

变体 行为 获取
默认 读者优先（读者可以"插队"到等待写者前面） PTHREAD_RWLOCK_INITIALIZER
_NP 变体 写者优先 pthread_rwlockattr_setkind_np(&attr, PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP)

判据：写延迟敏感（如行情快照刷新）必须上 writer-prefer 或干脆 mutex；rwlock 的收益窗口其实很窄——读临界区必须足够短、写频率足够低，否则 mutex（无竞争 7ns）反而更快（30.1 数据）。

barrier：一到两次的"GO"

pthread_barrier_init(&b, NULL, nthreads);      /* 计数 = nthreads */
int rc = pthread_barrier_wait(&b);
/* rc == PTHREAD_BARRIER_SERIAL_THREAD（只在一个线程）→ 该线程做 phase 间串行收尾 */
pthread_barrier_destroy(&b);
  • rc 的设计：n 个线程同时返回，但其中恰好 1 个拿到 SERIAL_THREAD、其余拿 0——天然选出一个"收尾者"（改 phase 计数、重置共享变量），省一次额外同步；
  • barrier 可循环使用：同一批线程一遍遍过同一集合点（count 每轮自动重置）。

PROCESS_SHARED：同步对象进共享内存

pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_setpshared(&ma, PTHREAD_PROCESS_SHARED);   /* ⭐ 默认是 _PRIVATE */
pthread_mutex_init(m_in_shm, &ma);

两个坑：

  1. 默认 PRIVATE：放共享内存却忘了设 shared → 各进程在自己地址空间各锁各的（futex key 按 PRIVATE 哈希不含物理页身份）——假同步，数据竞争照跑，而且很难复现；
  2. 对象必须放在共享映射（shm_open+mmap 或 MAP_SHARED 匿名）里，普通全局变量在 fork 之前就在则另说（fork 复制的是 COW，锁状态分裂成两份，见 33.3）。

PRIVATE 为什么快：futex key 跳过 get_futex_key() 的 inode/page 反查（30.1 核验的 FUT_OFF_MMSHARED 路径），单进程内一律走 mm 偏移——省几十 ns 与一次 cache line 弹跳。

HFT / 嵌入式关联

路线 要点
HFT 订单簿/配置快照：seqlock 或 RCU 思想（读不加锁）优先于 rwlock；跨进程共享行情段 + PROCESS_SHARED mutex 只用于低频控制面（高频面走 lock-free）
HFT barrier 用于启动对齐：全员 mlockall+预热完成 → barrier → 同时开跑（消除起跑毛刺）
嵌入式 单核 MCU 上 spinlock 无意义（自旋=不让出 CPU=持锁者也跑不了）——等于关中断/信号量；SMP SoC 上才谈 spin
通用 选型顺序：先问能不能不加锁（每线程副本/原子变量/消息传递），再 mutex，rwlock/spin 是特化答案不是默认答案

代码示例

/* sync_prim.c — Ch33.6：rwlock/barrier/spin 三原语实测
 * demo1: rwlock 并发读计数（8 读 + 1 写）
 * demo2: barrier 三线程两轮集合点 + SERIAL_THREAD 收尾
 * demo3: spinlock 计数（对照 mutex 留给 30.1 数据）
 * 编译：gcc -O2 -Wall -Wextra -o sync_prim sync_prim.c -pthread
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

#define NRD 8

static pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;
static long shared_val;
static long read_sums[NRD];
static volatile long spin_val;
static pthread_spinlock_t sp;

static void *reader(void *arg)
{
    long id = (long)arg;
    long acc = 0;
    for (int i = 0; i < 100000; i++) {
        pthread_rwlock_rdlock(&rw);
        acc += shared_val;                    /* 读临界区：一行 */
        pthread_rwlock_unlock(&rw);
    }
    read_sums[id] = acc;
    return NULL;
}

static void *writer(void *arg)
{
    (void)arg;
    for (int i = 0; i < 1000; i++) {
        pthread_rwlock_wrlock(&rw);
        shared_val += 1;
        pthread_rwlock_unlock(&rw);
        usleep(100);                          /* 模拟低频写 */
    }
    return NULL;
}

static pthread_barrier_t bar;
static long phase_count[3];

static void *phaser(void *arg)
{
    long id = (long)arg;
    for (int round = 0; round < 2; round++) {
        phase_count[id]++;                    /* 本线程的 phase 进度 */
        int rc = pthread_barrier_wait(&bar);  /* 集合点 */
        if (rc == PTHREAD_BARRIER_SERIAL_THREAD)
            printf("  [round %d] 线程 %ld 是 SERIAL_THREAD：全队到齐（各自 phase=%ld/%ld/%ld）\n",
                   round, id, phase_count[0], phase_count[1], phase_count[2]);
    }
    return NULL;
}

static void *spinner(void *arg)
{
    (void)arg;
    for (int i = 0; i < 1000000; i++) {
        pthread_spin_lock(&sp);
        spin_val++;
        pthread_spin_unlock(&sp);
    }
    return NULL;
}

int main(void)
{
    printf("== demo1: rwlock 8 读 1 写 ==\n");
    pthread_t r[NRD], w;
    for (long i = 0; i < NRD; i++) pthread_create(&r[i], NULL, reader, (void *)i);
    pthread_create(&w, NULL, writer, NULL);
    for (int i = 0; i < NRD; i++) pthread_join(r[i], NULL);
    pthread_join(w, NULL);
    long expect = read_sums[0];               /* 各读者看到不同时刻，但都在 [0,1000] 区间 */
    printf("  writer 共写 %ld 次；读者 acc 样例 %ld（写者结束时其他读者可见终值 1000）\n",
           shared_val, expect);
    printf("  shared_val 终值 = %ld\n", shared_val);

    printf("== demo2: barrier 两轮集合 ==\n");
    pthread_barrier_init(&bar, NULL, 3);
    pthread_t p[3];
    for (long i = 0; i < 3; i++) pthread_create(&p[i], NULL, phaser, (void *)i);
    for (int i = 0; i < 3; i++) pthread_join(p[i], NULL);
    pthread_barrier_destroy(&bar);

    printf("== demo3: spinlock 1M 次自增 ==\n");
    pthread_spin_init(&sp, 0);
    pthread_t s1, s2;
    pthread_create(&s1, NULL, spinner, NULL);
    pthread_create(&s2, NULL, spinner, NULL);
    pthread_join(s1, NULL); pthread_join(s2, NULL);
    pthread_spin_destroy(&sp);
    printf("  spin_val = %ld（期望 2000000）\n", spin_val);
    return 0;
}

实测输出（WSL2 / 12 核，gcc -O2 零告警）：

== demo1: rwlock 8 读 1 写 ==
  writer 共写 1000 次；读者 acc 样例 729630（写者结束时其他读者可见终值 1000）
  shared_val 终值 = 1000
== demo2: barrier 两轮集合 ==
  [round 0] 线程 2 是 SERIAL_THREAD：全队到齐（各自 phase=1/1/1）
  [round 1] 线程 0 是 SERIAL_THREAD：全队到齐（各自 phase=2/2/2）
== demo3: spinlock 1M 次自增 ==
  spin_val = 2000000（期望 2000000）

三点解读：

  1. demo1：写 1000 次期间 8 个读者各读 10 万次没有互相阻塞（读共享）。acc 样例 729630 = 10 万次读到的 shared_val 累加和（全程读到 0→1000 间递增值，均值 ~7.3——写者 usleep(100µs)×1000 次 ≈ 0.1s 内写完，前 1 万次读看到大部分写入）；终值 1000 由写锁独占保证。
  2. demo2：两轮集合点，SERIAL_THREAD 每轮可能落在不同线程（round0 是 2、round1 是 0）——它是"恰好一个拿到"，不是"固定 leader"。phase=1/1/1、2/2/2 证明真到齐才放行。
  3. demo3：spinlock 正确性无虞（200 万精确），但 30.1 的基准数据（spin 跨核 81ns vs mutex 69ns）提醒：短临界区也得真量过再选，自旋不是免费的快。

自测题

题目 1（判据）： 什么条件下 spinlock 比 mutex 快？什么条件下反而慢？

参考答案

快：临界区短于两次上下文切换成本（μs 级）且运行在不同核上——等 50ns 比睡 3μs 划算。慢：①同核（自旋=烧自己的时间片，持锁者根本没机会跑——必须等调度）；②临界区含系统调用/缺页/长循环（自旋时间超过睡眠成本）；③竞争者多（每个自旋者都在烧 CPU 拖慢持锁者抢总线）。30.1 实测跨核 4 线程：spin 81ns 反而比 mutex 69ns 慢——自旋风暴干扰了持锁者的 cache。

题目 2（语义）： pthread_barrier_wait 的返回值设计解决了什么问题？

参考答案

n 个线程同时被放行，但恰好一个拿到 PTHREAD_BARRIER_SERIAL_THREAD——自动选出一个"收尾者"执行 phase 间串行工作（重置计数器、swap 缓冲、打印汇总），其余线程拿 0 直接进下一轮。没有它就得再补一次"谁负责收尾"的选举同步。demo2 还证明收尾者每轮可能不同——程序不能假设它固定。

题目 3（陷阱）： 把 PTHREAD_MUTEX_INITIALIZER 的 mutex 放进 shm_open 的共享内存，两个进程各自锁定/解锁都成功——数据却在竞争。哪里错了？

参考答案

忘了 pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED)。默认 PRIVATE 的 futex key 按"进程私有地址"哈希——两个进程各自锁的是逻辑上同一个对象、内核视角两个独立锁（key 不同桶）。必须 init 时设 shared 属性，futex key 才走物理页身份（FUT_OFF_INODE/MMSHARED 路径）锁定真身。

题目 4（选型）： 配置表 99% 读 1% 写、写延迟不敏感，rwlock 一定比 mutex 好吗？

参考答案

不一定。读临界区只有几 ns 时 rwlock 的原子计数开销（读者登记/退出）可能吃掉全部收益——无竞争 mutex 7ns（30.1 实测）很难输。rwlock 赢面在读临界区够长（μs 级：要遍历哈希表）且写低频（此时读侧重叠度才值回开销）。写延迟敏感场景 glibc 默认读者优先会写饥饿——上 writer-prefer 变体或换设计（双缓冲 + 原子指针切换）。

三个反直觉真相

  1. 「线程栈」是两种东西：主线程栈（VM_GROWSDOWN 可增长、进程栈区）与子线程栈（mmap 区固定、有 guard）——名字同，机制完全不同。
  2. 信号没有"进程掩码"：掩码每线程独立，complete_signal 只是从上次目标轮转找第一个未阻塞的——全员阻塞时信号安静地挂在共享队列，谁先解除谁领走（不是丢失）。
  3. exec 的 PID 窃取：非 leader 线程 exec 后，内核让它顶替已死 leader 的 PID——getpid() 语义靠一个换位 hack 保住。

代码自测

1. 为什么「全员阻塞 SIGUSR1 后 kill() 发 SIGUSR1」不会丢信号？

信号留在进程的共享 pending 队列（shared_pending）。complete_signal():1004 轮转一圈没有线程 wants_signal()（全 blocked）就返回——信号挂着，不丢弃。之后任何一个线程 pthread_sigmask(SIG_UNBLOCK, ...) 并返回用户态时，信号递送或被 sigwait 取走。阻塞 ≠ 丢弃，只有标准信号在队列里合并（多次投递记一次）。

2. fork 出的子进程里 printf 为什么可能死锁？和 exec 前的限制是什么关系？

stdio 流锁随地址空间 COW 继承。若父进程某线程恰好在 printf 内（持流锁）时另一线程 fork，子进程继承"锁定"的锁位，但持有者线程没被复制——子进程 printf 走到该锁即死锁。async-signal-safe 函数清单恰好就是"不持锁"的函数清单——信号处理器和 fork 子进程面对的是同一个世界（「别的执行流可能消失在持锁中途」），所以共享同一份白名单。exec 替换映像后锁状态清零，一切安全。

3. 四线程进程，线程 2（非 leader）执行 execve 成功。之后 getpid() 返回什么？/proc 里 task 目录少了几个？

getpid() 返回原 leader 的 PID——de_thread():1044 杀光其他 3 线程后，非 leader 调用者与已退出的 leader 换位（接管其 PID/TGID）。/proc/pid/task/ 从 4 项变 1 项。这就是「exec 后进程身份不变」的实现：物理上执行映像的线程换了，逻辑身份被内核手术缝合。

4. 子线程默认栈 8MB、内核栈 16KB、guard 4KB——一台 64GB 机器的理论线程数上限和实际工程预算差多少？

理论：64GB / 16KB = 4M 线程（只算内核栈物理内存；用户栈 8MB 是虚拟、按触碰收费，但 mmap 地址空间 128TB 也够）。实际工程：每线程还有 glibc struct pthread（TCB 等 ~数 KB 物理）、页表项、调度器开销（runqueue 负载）——实践中万级线程已是重负载（调度抖动、组唤醒风暴），千级是常见健康上限。预算按"内核栈 16KB × N 立即物理 + 触碰到的用户页"算。

5. 把 33.2/33.3 串起来：SIGHUP 重载配置 + SIGTERM 优雅退出 + 禁止 fork 的多线程服务，画出完整生命周期。 
main ─ pthread_sigmask(BLOCK {SIGHUP,SIGTERM})      ← 一切之前
    ├─ sigwait 线程：取信号 → 翻译成内部事件（管道/eventfd）
    ├─ 业务线程 × N：全员继承阻塞，永不收信号
    │     SIGHUP → 配置线程在读检查点原子换表（无锁读：双缓冲+原子指针）
    │     SIGTERM → shutdown 事件 → 各线程跑到 quiesce 点 → 退出
    └─ 主线程 pthread_exit（或 join 最后的 logger）
外部工具一律 posix_spawn；绝不 fork-worker。

3 个线程两轮循环：phase1 各自累加本地计数 → barrier → phase2 把本地值原子加进全局 → barrier → 下一轮。要求：全局汇总恰好由 SERIAL_THREAD 每轮清零。陷阱：你会在哪一步发现"SERIAL_THREAD 每轮可能不同"？

练习 6（综合）：多线程守护进程骨架

练习 1 答案

  1. handler 跑在 T0 和 T3（未阻塞者）上。次数：最多 10 次、可能少于——标准信号不排队，10 次 kill 若在 handler/递送完成前密集到达会合并；complete_signal 从 curr_target 轮转，T0/T3 交替是常态。
  2. 全员阻塞 → 10 次 kill 全挂共享 pending 队列（合并后 pending 位图只有 1 位）→ 没有任何 handler 跑，但没丢。验证：任一线程解除阻塞 → handler 跑 1 次；或 sigpending() 查看队列位图。

练习 2 答案

/* fork_ghost.c — 三种锁的 fork 后行为对照（全部 trylock，避免真死锁） */
#define _GNU_SOURCE
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>
#include <sys/wait.h>

static pthread_mutex_t m_normal  = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t m_errchk;
static pthread_mutex_t m_robust;
static pthread_mutexattr_t attr_e, attr_r;

static void *locker(void *arg)
{
    (void)arg;
    pthread_mutex_lock(&m_normal);           /* 持到进程结束 */
    return NULL;
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);
    pthread_mutexattr_init(&attr_e);
    pthread_mutexattr_settype(&attr_e, PTHREAD_MUTEX_ERRORCHECK);
    pthread_mutex_init(&m_errchk, &attr_e);
    pthread_mutexattr_init(&attr_r);
    pthread_mutexattr_setrobust(&attr_r, PTHREAD_MUTEX_ROBUST);
    pthread_mutex_init(&m_robust, &attr_r);

    pthread_t t;
    pthread_create(&t, NULL, locker, NULL);
    usleep(50 * 1000);
    pthread_mutex_lock(&m_errchk);           /* 主线程持 errorcheck */
    pthread_mutex_lock(&m_robust);           /* 主线程持 robust */

    pid_t pid = fork();
    if (pid == 0) {
        int r1 = pthread_mutex_trylock(&m_normal);
        int r2 = pthread_mutex_trylock(&m_errchk);
        int r3 = pthread_mutex_trylock(&m_robust);
        printf("  [子] normal trylock = %d (%s)\n", r1, strerror(r1));
        printf("  [子] errchk  trylock = %d (%s)\n", r2, strerror(r2));
        printf("  [子] robust  trylock = %d (%s)\n", r3, strerror(r3));
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    return 0;
}

实测（WSL2，零告警）：

  [子] normal trylock = 16 (Device or resource busy)
  [子] errchk  trylock = 16 (Device or resource busy)
  [子] robust  trylock = 16 (Device or resource busy)

robust 也救不了 fork——这是比 EOWNERDEAD 更重要的结论：

  • robust 的「持有者死亡检测」是内核在持有者线程真正走 do_exit() 时由 exit_robust_list()（kernel/futex/core.c:773）把链表上所有锁标记 EOWNERDEAD——它挂在退出路径上；
  • fork 里"消失"的线程从未运行过 do_exit（它只是没被复制），子进程的 robust 链表是空的、锁内存位原样照抄 → trylock EBUSY、lock() 永久睡在 futex 上（实测挂死，等同普通锁）；
  • 也就是说：robust 只覆盖「线程死了」一种死法，救不了「线程从未存在」的 fork 场景。工程上"可存活的 fork-worker"若真要用 robust+pthread_mutex_consistent()，防的是 worker 线程崩溃（走退出路径），不是 fork 幽灵。

练习 3 答案

  1. 没有截断：de_thread 杀线程发生在系统调用边界/可中断点——正在 write(2) 里的线程要么完成这次调用、要么被杀在调用前后，不会写半截 fd 状态（内核 write 路径里 SIGKILL 不打断已持锁的临界区，只是让它不再返回用户态）。exec 后 . 消失：没有线程了。
  2. printf 版：worker 的 stdio 缓冲在用户态——被杀时缓冲没 flush 的内容直接蒸发；反之若 worker 恰好 printf 完整但主线程 exec，缓冲不 flush 也蒸发。这正是「exec 杀线程无清理」的直接证据，也是为什么 multi-threaded 代码 exec 前 fflush(NULL) 只救主线程自己的缓冲。

练习 4 答案

/* barrier_phase.c */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdatomic.h>
#include <pthread.h>

enum { NTH = 3, ROUNDS = 3 };
static pthread_barrier_t bar;
static atomic_long global;
static long local_[NTH];

static void *work(void *arg)
{
    long id = (long)arg;
    for (int r = 0; r < ROUNDS; r++) {
        local_[id]++;                        /* phase 1：本地累加 */
        pthread_barrier_wait(&bar);
        if (r < ROUNDS - 1)
            atomic_fetch_add(&global, local_[id]);   /* phase 2：汇总 */
        pthread_barrier_wait(&bar);
        /* ⭐ 若在这里读 global 做判断——SERIAL_THREAD 的清零时机决定结果 */
    }
    return NULL;
}

int main(void)
{
    pthread_barrier_init(&bar, NULL, NTH);
    pthread_t t[NTH];
    for (long i = 0; i < NTH; i++) pthread_create(&t[i], NULL, work, (void *)i);
    for (int i = 0; i < NTH; i++) pthread_join(t[i], NULL);
    printf("全局 = %ld（ROUNDS=3：前两轮各线程 local 累进 1、2，总和 (1+2+3)×2=12？实测对账）\n",
           atomic_load(&global));
    pthread_barrier_destroy(&bar);
    return 0;
}

陷阱揭示：想「每轮由 SERIAL_THREAD 清零 global」时，清零必须发生在所有汇总完成之后——即第二个 barrier 之后的 SERIAL_THREAD。若在第一个 barrier 后清零，会读到上一轮的旧值；且 SERIAL_THREAD 每轮可能是不同线程（33.6 demo2 实测），谁清零不能写成固定线程。正确结构：累加 → bar → 汇总 → bar → SERIAL 清零（清零在第二个 bar 之后、下一轮开始前）。实测全局 = 9（round0 加 1×3、round1 加 2×3，末轮不汇）——与上述推演完全对账。

练习 5 答案

观察要点：VmSize 涨约 1000 × 8MB ≈ 8GB（虚拟、含 guard 对齐），RSS 只涨几 MB（线程栈没人触碰，全靠 mmap 未触碰页 = 零物理；涨的部分是 glibc TCB/内核结构的已触碰页 + 内核栈不在进程 RSS 里！）。对账陷阱：16KB 内核栈不计入进程 RSS——它是内核内存（slab/vmalloc），在 /proc/meminfo 的 Slab/KMalloc 曲线上，进程视角看不到。这题教的是：进程 RSS 严重低估多线程的真实物理成本。

/* mt_daemon.c — 多线程守护进程骨架：sigwait 线程 + 优雅退出，零异步 handler */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdatomic.h>
#include <pthread.h>
#include <signal.h>
#include <unistd.h>
#include <string.h>
#include <time.h>

static atomic_int  shutdown_req;      /* 0 跑 / 1 关 */
static atomic_long tick[2];

static void *worker(void *arg)
{
    long id = (long)arg;
    while (!atomic_load(&shutdown_req)) {
        atomic_fetch_add(&tick[id], 1);
        struct timespec ts = {0, 50 * 1000 * 1000};
        nanosleep(&ts, NULL);         /* 模拟工作（也是退出检查点） */
    }
    printf("worker%ld done（tick=%ld）\n", id, atomic_load(&tick[id]));
    fflush(stdout);
    return NULL;
}

static void *sig_thread(void *arg)
{
    (void)arg;
    int sig;
    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, SIGINT);
    sigaddset(&set, SIGTERM);
    sigaddset(&set, SIGHUP);
    for (;;) {
        if (sigwait(&set, &sig) != 0) break;
        if (sig == SIGHUP) { printf("[sig] SIGHUP：配置重载（此处省略）\n"); continue; }
        printf("[sig] 收到 %s → 广播退出\n", strsignal(sig));
        fflush(stdout);
        atomic_store(&shutdown_req, 1);
        return NULL;
    }
    return NULL;
}

int main(int argc, char **argv)
{
    setvbuf(stdout, NULL, _IOLBF, 0);

    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, SIGINT);
    sigaddset(&set, SIGTERM);
    sigaddset(&set, SIGHUP);
    pthread_sigmask(SIG_BLOCK, &set, NULL);     /* ⭐ 一切之前 */

    pthread_t w0, w1, st;
    pthread_create(&w0, NULL, worker, (void *)0L);
    pthread_create(&w1, NULL, worker, (void *)1L);
    pthread_create(&st, NULL, sig_thread, NULL);

    if (argc > 1 && strcmp(argv[1], "selftest") == 0) {
        /* 自测模式：2 秒后自己给自己发 SIGTERM（走完整信号路径） */
        sleep(2);
        kill(getpid(), SIGTERM);
    }
    pthread_join(st, NULL);                     /* 等信号线程发令 */
    pthread_join(w0, NULL);
    pthread_join(w1, NULL);
    printf("bye\n");
    return 0;
}

实测（./mt_daemon selftest——自测模式 2 秒后自己发 SIGTERM 走完整信号路径）：

[sig] 收到 Terminated → 广播退出
worker0 done（tick=40）
worker1 done（tick=40）
bye

验收全过：信号→广播→两个 worker 各自 done→bye，顺序稳定；全程没有任何 async handler（sigaction 一次都没调）。
