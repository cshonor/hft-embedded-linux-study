3.1

System Calls 系统调用

本章：TLPI 第 03 章 — System Programming Concepts - 上一节：本章首页 - 下一节：3.2 Library Functions（glibc）

本节讲什么

定义： 用户进程进入内核的 受控入口；请求内核做受保护操作（读写、建进程、IPC…）。 1. 应用调 glibc 包装（如 open()） 2. 包装把 调用号 + 参数 放入寄存器

要点

定义： 用户进程进入内核的 受控入口；请求内核做受保护操作（读写、建进程、IPC…）。

特性
模式切换 用户态 → 内核态
编号 每个 syscall 唯一号；内核用 sys_call_table 索引
谁触发陷阱 应用通常 不 手写 syscall；调 glibc 包装函数

标准流程（x86 概念）

  1. 应用调 glibc 包装（如 open()）
  2. 包装把 调用号 + 参数 放入寄存器
  3. 陷阱指令（int 0x80 / syscall）进内核
  4. 内核入口：保存现场 → 校验 → 执行服务例程
  5. 回用户态；返回值给包装
  6. 包装判断错误码，失败则设 errno

开销： 远贵于普通函数调用（切换、保存、校验）。HFT / 热路径要 少 syscall。

与 C 语言学习的关系

系统调用是操作系统的接口，不是 C 语言的一部分。C 语言标准（K&R / ISO-C）不定义任何系统调用——open、read、fork 这些函数全部来自 POSIX 规范，由 glibc 提供包装。

理解系统调用的关键是：glibc 的 open() 函数只是一层薄外壳，真正的工作发生在内核里（编号 + 寄存器 + syscall 指令）。K&R 第 8 章展示了这套接口的原始形态——文件描述符、read/write/open，它们是 Unix 系统编程的根基。

对照学习：K&R 8.1（文件描述符）→ 8.2（read/write）→ 8.3（open/creat/close）→ 8.4（用系统调用实现 fopen/fread/fclose），这条线完美展示了"系统调用 → C 标准库"的封装关系。

常见陷阱

  1. 不检查返回值和 errno
int fd = open(path, O_RDONLY);
read(fd, buf, n);  /* fd=-1 → EBADF，后续全废 */

系统调用失败返回 -1 并设置 errno。不检查直接用会导致连锁失败。必须 if ((fd = open(...)) < 0) { perror("open"); exit(1); }。

  1. 混淆系统调用与库函数
/* ❌ 误以为 strcpy / atoi 是系统调用 */
/* ✅ strcpy / atoi 是纯用户态库函数，不进内核 */
/* ❌ 误以为 open 是 C 标准函数 */
/* ✅ open 是 POSIX 系统调用包装，C 标准里没有 */

区分方法：man 2 查到的是系统调用，man 3 查到的是库函数。纯用户态库函数（strcpy/atoi/strlen）不会陷入内核。

  1. 热路径频繁 syscall
/* HFT 热路径：逐字节 read，每次都陷入内核 */
for (int i = 0; i < n; i++)
    read(fd, &buf[i], 1);  /* n 次上下文切换！ */

/* 优化：一次读完 */
read(fd, buf, n);  /* 1 次系统调用 */

系统调用开销远贵于普通函数调用（用户态→内核态切换、保存现场、校验）。HFT 热路径要尽量少 syscall，或用 mmap / 批量 I/O 替代。

自测题

题目 1（选择）： 系统调用与普通函数调用的最大区别是什么？

A. 系统调用更快 B. 系统调用会从用户态切换到内核态 C. 系统调用不需要参数 D. 系统调用只能用汇编写

参考答案

B。系统调用需要从用户态切换到内核态（模式切换），涉及保存现场、权限检查、寄存器传参等开销，远贵于普通函数调用。普通函数调用在同一个特权级内完成。

题目 2（判断）： strcpy 和 strlen 是系统调用。

参考答案

错误。strcpy 和 strlen 是纯用户态 C 标准库函数，不会陷入内核。它们在 man 3 里。系统调用在 man 2 里（如 open/read/write）。

题目 3（踩坑）： 以下代码有什么性能问题？如何优化？

char buf[1024];
for (int i = 0; i < 1024; i++)
    read(fd, &buf[i], 1);
参考答案

每次 read(fd, &buf[i], 1) 都触发一次系统调用（用户态→内核态切换），1024 次循环 = 1024 次上下文切换，开销巨大。优化：一次读完全部 read(fd, buf, 1024)，只有 1 次系统调用。或用 fread（libc 缓冲自动批量 read）。

题目 4（应用）： 描述 Linux x86-64 上 open() 系统调用的完整执行流程（从 C 代码到内核返回）。

参考答案
  1. 应用代码调用 open(path, flags, mode)（glibc 包装函数）
  2. glibc 把系统调用号（SYS_open=2）放入 rax，参数放入 rdi/rsi/rdx
  3. 执行 syscall 指令 → CPU 从用户态切换到内核态
  4. 内核入口：保存用户态寄存器，查找 sys_call_table[2] → sys_open
  5. sys_open 检查权限、创建/打开文件、分配 fd
  6. 内核恢复用户态寄存器，返回值放入 rax
  7. glibc 检查返回值：若为负数则设 errno 并返回 -1；否则返回 fd

#include <unistd.h>
#include <sys/syscall.h>
/* 系统调用: 用户态 -> 内核态 */
int main(void) {
    long ret = syscall(SYS_write, STDOUT_FILENO, "raw syscall\n", 12);
    printf("syscall returned %ld\n", ret);
    return 0;
}

3.2

Library Functions（glibc）

本章：TLPI 第 03 章 — System Programming Concepts - 上一节：3.1 System Calls 系统调用 - 下一节：3.3 错误处理（本章重中之重）

本节讲什么

C 标准库函数（fopen/printf/malloc）与 POSIX 系统调用（open/read/write）的根本区别：谁调用谁、glibc 在中间扮演什么角色、为什么同一个 fopen 在 Linux 和 Windows 底层走的路完全不同。

要点

三个角色（千万不要混在一起）

角色 层面 代表函数 谁定义
ISO-C 标准库 语言层面 fopen() / printf() / malloc() C 语言标准（ISO/IEC 9899）
POSIX 系统调用 操作系统内核层面 open / read / write POSIX 规范（操作系统接口）
glibc / musl 用户态中间层（桥梁） 实现上面两者的 C 代码 各 C 库项目

核心一句话： C 语言本身不操作操作系统硬件、文件。C 语言没有"打开文件"的内置语法，没有 openfile 关键字。全部靠库函数，库再请求操作系统内核干活。

调用链条（Linux 环境）

你写的应用 C 代码（正式 C）
        ↓ 调用
【glibc 库函数】
    ├─ 情况 A：你调用标准 C → fopen()
    │      ↓ glibc 内部代码执行，做缓冲区逻辑
    │      ↓ glibc 再去调用系统调用 open
    │
    └─ 情况 B：你直接调用 POSIX 接口 → open()
           ↓ glibc 薄薄一层封装，触发系统调用
                ↓ 陷入内核（svc / syscall 指令）
Linux 内核真正干活：打开文件
        ↓ 返回结果

方向：应用 C 代码 → glibc 库 → 系统调用 → 内核

❗ 千万不要理解成"系统调用调用 C 语言"。反过来！C 语言的库去调用系统调用。

库函数的三种类型

类型 例子 是否进内核
薄封装 read / write 通常一次 syscall
纯用户态 strcpy / atoi / strlen 否（不进内核）
多层 fopen 内部 open + 用户态缓冲管理等

fopen vs open：彻底分清

fopen() open()
归属 ISO-C 标准库函数 POSIX 系统调用包装
谁定义 C 语言标准 POSIX 操作系统规范
谁实现 glibc（Linux）/ msvcrt（Windows） glibc（薄外壳）
返回值 FILE * 指针（带缓冲区） int fd（内核整数句柄）
缓冲 用户态带缓冲区 无用户态缓冲
可移植 C 标准，跨平台 POSIX，Unix/Linux 限定
Windows 有没有 ✅ 有（msvcrt 实现） ❌ 没有（Windows 不遵守 POSIX）

⚠️ open() 这个 C 函数是 glibc 包装出来的外壳；真正的系统调用是内核那套汇编入口（编号 + 寄存器 + svc/syscall 指令）。POSIX 规定了 open() 的参数行为，要求 Linux/macOS 都提供这个外壳函数。Windows 不遵守 POSIX，所以没有 open。

同一个 fopen，不同操作系统内部完全不同

ISO-C 标准：规定了 FILE* fopen(const char *name, const char *mode);
            标准只写：功能是打开文件。不管底层怎么实现。

Linux 上：glibc 实现 fopen → 内部调用内核 open 系统调用
Windows 上：msvcrt 实现 fopen → 内部调用 Windows 内核 API CreateFileA

✅ 同一个 C 标准函数，不同操作系统，内部调用完全不一样的内核接口。C 标准只定义"外表"，不定义内核细节。

通俗类比

角色 类比
ISO-C 标准 规定"饮水机要有一个按钮，按一下出水"（只规定按钮外观行为）
系统调用 饮水机内部真正的阀门、水泵（内核，真正干活）
glibc 按钮和水泵中间的连接杆（用户态库）

你（C 代码）按按钮（fopen 标准 C 函数）；连接杆（glibc）收到动作，去扳开内部水泵阀门（系统调用），水泵（内核）出水。不同牌子饮水机（操作系统）按钮长得一样（C 标准 fopen 接口不变），但内部水泵阀门完全不一样（系统调用不一样）。

与 C 语言学习的关系

对照点 K&R（C 标准） TLPI（POSIX）
文件打开 fopen() 返回 FILE * open() 返回 int fd
文件读写 fread() / fwrite() read() / write()
文件关闭 fclose() close(fd)
缓冲 用户态带缓冲 无用户态缓冲
可移植 跨平台 POSIX 限定

K&R 第 8 章（UNIX 系统接口）讲解的正是这套底层接口。K&R 8.1 节讲文件描述符，8.2 节讲 read/write，8.3 节讲 open/creat/close，8.4 节用它们实现 fopen/fread/fclose——完美展示了"C 标准库函数封装系统调用"的过程。

fopen 模式 → open flags 映射：

fopen 模式 open 对应 flags 说明
"r" O_RDONLY 只读
"w" O_WRONLY \| O_CREAT \| O_TRUNC 只写、创建、截断清空
"a" O_WRONLY \| O_CREAT \| O_APPEND 追加写

理解这个映射关系，就理解了"C 标准库函数内部如何调用系统调用"。

HFT / 嵌入式关联

路线 要点
嵌入式 Linux 资源受限场景可选择直接调用 open/read/write 绕开 libc 缓冲，做裸文件操作；也可用 libc 封装（简单但多一层缓冲）。严格返回值 + errno 检查是基本要求
HFT 低延迟 fopen/fread/fwrite：libc 缓冲减少 syscall 次数但多一层拷贝；open/read/write：绕开 libc 缓冲但每次都陷入内核。热路径要权衡：何时用库缓冲、何时直接 syscall、何时上 mmap。测延迟时要区分 glibc 包装成本与真正陷入内核的开销
通用 库函数便于移植；系统调用更底层更可控。功能测试宏（_POSIX_C_SOURCE 等）保证 API 可见性

常见陷阱

  1. 误以为 open() 是 C 语言自带函数
/* ❌ 错误认知：open() 是 C 标准函数 */
/* ✅ 正确：open() 是 POSIX 系统调用包装，C 标准里根本没有 open */
/* 证明：不链接 glibc，open 符号不存在 → undefined reference to 'open' */

open() 属于 POSIX 规范，不是 C 语言标准。Linux 靠 glibc 提供这个函数。Windows 没有 open（只有 _open 非标准扩展）。

  1. 误以为 C 语言可以直接操作文件
/* ❌ 错误认知：C 语言有文件操作能力 */
/* ✅ 正确：C 语言没有文件操作能力，全部依赖库，库再请求操作系统内核 */
/* fopen 在 Linux 上一定会调用 open 系统调用 */
/* fopen 在 Windows 上调用的是 CreateFileA，完全不同的内核接口 */
  1. 不链接 glibc 的裸程序能用 fopen / open 吗？
/* 不链接 glibc，纯裸程序：
 * - fopen() 不能用：没有 C 标准库实现，链接器报 undefined reference
 * - open() 不能用：没有 glibc 包装函数，同样 undefined reference
 * - 但你仍然能和内核交互：直接用内嵌汇编发 syscall 指令
 */

/* 不链接 glibc，纯裸 x86-64，直接 syscall 打开文件 */
long my_open(const char *path, int flags, int mode) {
    long ret;
    asm volatile (
        "syscall"
        : "=a"(ret)
        : "a"(2),           /* SYS_open = 2 */
          "D"(path),         /* rdi = pathname */
          "S"(flags),        /* rsi = flags */
          "d"(mode)          /* rdx = mode */
        : "rcx", "r11", "memory"
    );
    return ret;
}

这印证了核心论点：系统调用是内核的编号 + 寄存器 + 指令，glibc 的 open() 只是包装外壳。剥掉外壳，内核门还在。这就是 freestanding 环境（裸机 / 固件 / 内核模块）的做法。

题目 2（判断）： fopen() 在 Linux 和 Windows 上内部调用的是同一个系统调用。

参考答案

错误。fopen 是 C 标准函数，接口统一，但底层实现取决于操作系统。Linux 上 glibc 实现的 fopen 内部调用 open 系统调用；Windows 上 msvcrt 实现的 fopen 内部调用 CreateFileA。同一个标准接口，不同操作系统走完全不同的内核路径。

题目 3（踩坑）： 以下代码在什么情况下会编译失败？为什么？

#include <fcntl.h>
int fd = open("test.txt", O_RDONLY);
参考答案

不链接 glibc（或任何提供 POSIX 接口的 C 库）时会链接失败：undefined reference to 'open'。open 不是 C 语言内置函数，是 glibc 提供的 POSIX 系统调用包装。在 freestanding 环境（如裸机固件、内核模块开发）中没有 glibc，open 符号不存在。解决方法：要么链接 C 库，要么用内嵌汇编直接发 syscall 指令。

题目 4（应用）： 画出以下代码的完整调用链（从你的代码到内核）：

FILE *fp = fopen("log.txt", "w");
fprintf(fp, "hello\n");
fclose(fp);
参考答案 
fopen("log.txt", "w")
  → glibc 内部：分配 FILE 结构体，设置缓冲区
  → glibc 调用 open("log.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666)
    → glibc 的 open 封装：设寄存器（rax=2, rdi=path, rsi=flags, rdx=mode）
      → syscall 指令陷入内核
        → 内核 sys_open：检查权限、创建/截断文件、分配 fd
          → 返回 fd 给 glibc

fprintf(fp, "hello\n")
  → glibc 内部：格式化字符串，写入 FILE 的用户态缓冲区
  → 缓冲区满或 fflush 时：glibc 调用 write(fd, buf, n)
    → syscall 陷入内核 → 内核写入文件 → 返回

fclose(fp)
  → glibc 内部：flush 剩余缓冲区（调用 write）
  → glibc 调用 close(fd)
    → syscall 陷入内核 → 内核释放 fd → 返回
  → glibc 释放 FILE 结构体

关键：fopen → open（C 标准库调用系统调用），fclose → close，fread → read。C 标准库函数内部调用系统调用，不是反过来。

#include <string.h>
/* 库函数: glibc 用户态实现, 可能内部调 syscall */
int main(void) {
    size_t len = strlen("hello");  /* 纯用户态 */
    printf("strlen=%zu (no syscall)\n", len);
    printf("printf flushes buffer via write() syscall\n");
    return 0;
}

The Standard C Library; The GNU C Library (glibc)

本章：TLPI 第 03 章 — System Programming Concepts 源码核验：Linux v6.6（include/linux/err.h — 内核错误返回约定） - 上一节：3.2 Library Functions（glibc） - 下一节：3.3 错误处理（本章重中之重）

本节讲什么

glibc 是 Linux 上事实标准的 C 库——既实现 ISO-C 标准库，又封装 POSIX 系统调用。本节回答三个问题：

  1. glibc 到底提供了什么？它和「C 标准库」「POSIX」是什么关系？
  2. glibc 封装系统调用时，怎么把内核的「负错误码」翻译成 errno + -1？
  3. glibc 和 musl 有什么区别？__GLIBC_PREREQ 是干嘛的？

1. glibc 的角色：一个库，三种身份

身份 提供什么 例子
ISO-C 标准库实现 C 语言标准要求的函数 printf/malloc/strcpy/qsort
POSIX 封装层 系统调用的薄外壳 open/read/write/fork/mmap
glibc 扩展 Linux 专属的非标准函数 epoll 系列、strerror_r 的 GNU 语义

所以「glibc」不是「C 标准库」的同义词——它包含 C 标准库，还多出 POSIX 封装和一堆 Linux 扩展。换个 C 库（如 musl），C 标准库函数还在（printf/malloc 都有），但扩展函数和某些行为细节会变。

2. glibc 怎么封装系统调用：MAX_ERRNO 错误转换

glibc 的 open() 不是把内核返回值原样传回，而是做一次错误翻译。关键在内核的错误返回约定：

/* include/linux/err.h:17 —— 内核错误码的取值范围 */
#define MAX_ERRNO   4095

完整的往返流程：

用户态调 open(path, flags)
      │  glibc 包装：rax=2(syscall号), rdi=path, rsi=flags, rdx=mode
      ▼
syscall 指令陷入内核
      │  内核 sys_open 干活，返回值放进 rax
      ▼
内核返回：成功 → rax = 新 fd（≥0）
          失败 → rax = -errno（如 -2 = -ENOENT，落在 [-4095, -1]）
      ▼
glibc 包装判断：rax 是否在 [-4095, -1]？
      ├─ 是 → errno = -rax（如 2），返回 -1
      └─ 否 → 返回 rax（合法 fd）

这就是「为什么系统调用失败返回 -1，具体原因看 errno」的底层机制——内核返回的是 -errno（负错误码），glibc 拆成「返回 -1 + 设 errno」两件事。所以直接 syscall() 拿到的返回值是负错误码（不是 -1），这就是绕过 glibc 时要自己判断的原因。

long ret = syscall(SYS_open, "/nonexistent", O_RDONLY);
/* ret == -2（-ENOENT），而不是 -1！因为跳过了 glibc 的翻译层 */

3. glibc 版本与特性检查

ldd --version          # 查看 glibc 版本
getconf GNU_LIBC_VERSION

编译时检查 glibc 特性用 __GLIBC_PREREQ：

#include <features.h>
#if __GLIBC_PREREQ(2, 17)
    /* glibc >= 2.17：clock_gettime 不再需要 -lrt */
#endif

glibc 版本 ≠ 内核版本：glibc 封装系统调用，但不是 1:1 映射——一个新内核特性（如 io_uring、close_range）要等 glibc 出新版本提供对应封装才能直接用；等不及时可以自己 syscall() 绕过（见 3.1）。老 glibc 跑在新内核上通常没问题（ABI 向后兼容），但用不到新 syscall 的现成封装。

4. glibc vs musl

维度 glibc musl
定位 功能最全、性能最优 极致精简、静态链接友好
体积 大（约 2MB+） 小（约 500KB）
扩展 最多（GNU 扩展） 严格 POSIX，少扩展
适用 桌面/服务器/通用 嵌入式、容器（Alpine 默认）、静态可移植二进制
许可 LGPL MIT

嵌入式/HFT 若要做静态链接、跨发行版可移植的单文件二进制，常选 musl；通用场景用 glibc。注意：musl 下 strerror_r 是 POSIX 语义（返回 int），glibc 默认是 GNU 语义（返回 char*）——这是两者可移植性差异的典型例子。

5. HFT / 嵌入式关联

现象 本节机制的兑现
直接 syscall() 拿负错误码 绕过 glibc 时返回值是 -errno，须自己判断 [-4095,-1]，不能当 -1 处理

6. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <fcntl.h>
#include <errno.h>

int main(void) {
    /* 正常路径：glibc 的 open() 返回 -1 + 设 errno */
    int fd = open("/nonexistent", O_RDONLY);
    if (fd == -1)
        printf("glibc open(): errno=%d (%s)\n", errno, strerror(errno));

    /* 绕过 glibc：syscall() 返回的是负错误码 */
    long ret = syscall(SYS_open, "/nonexistent", O_RDONLY);
    printf("raw syscall: ret=%ld (就是 -ENOENT)\n", ret);

    /* 手动还原成 errno 语义 */
    if (ret < 0 && ret >= -4095) {
        int e = -(int)ret;
        printf("manual: errno=%d (%s)\n", e, strerror(e));
    }
    return 0;
}

运行：gcc -o g g.c && ./g。你会看到 glibc 的 open 返回 -1 + errno=2，而 syscall(SYS_open, ...) 直接返回 -2——印证了「glibc 做了错误翻译」这一层。

Q1：glibc 是「C 标准库」吗？它到底提供了什么？ A：不完全是。glibc 包含 C 标准库（ISO-C 要求的 printf/malloc 等），但还多出 POSIX 系统调用封装（open/read/fork）和大量 Linux/GNU 扩展（epoll、GNU 版 strerror_r）。换 musl 时 C 标准库函数还在，但扩展和部分行为会变。所以「glibc」是「C 库的一种具体实现」，比「C 标准库」范围大。

Q2：为什么系统调用失败「返回 -1 + 设 errno」，而不是直接返回错误码？ A：这是 glibc 的错误翻译约定。内核实际返回的是 -errno（如 -2 = -ENOENT，落在 [-4095, -1]，见 include/linux/err.h 的 MAX_ERRNO=4095）。glibc 包装检查返回值是否在这个范围：是则设 errno = -返回值 并返回 -1，否则当作合法值返回。所以直接 syscall() 拿到的返回值是负错误码（-2），不是 -1。

Q3：__GLIBC_PREREQ 是干嘛的？glibc 版本和内核版本是什么关系？ A：__GLIBC_PREREQ(major, minor) 是编译期检查 glibc 版本的宏，用于条件编译（如 clock_gettime 在 glibc 2.17 起不用 -lrt）。glibc 版本 ≠ 内核版本：glibc 封装系统调用但非 1:1——新内核特性（io_uring、close_range）要等 glibc 提供封装才能直接用，否则自己 syscall() 绕过。老 glibc 跑新内核通常兼容（ABI 向后兼容），但用不到新 syscall 的现成封装。

Q4：glibc 和 musl 有什么区别？什么场景选 musl？ A：glibc 功能最全、性能最优、扩展最多（LGPL）；musl 极致精简（约 500KB）、严格 POSIX 少扩展、静态链接友好（MIT）。做静态链接、跨发行版可移植的单文件二进制（嵌入式、容器如 Alpine）常选 musl；通用场景用 glibc。注意两者 strerror_r 语义不同（musl 是 POSIX 返回 int，glibc 默认 GNU 返回 char*），是典型可移植性差异。

Q5：部署机报 GLIBC_x.yy not found 是什么原因？怎么解决？ A：编译机的 glibc 比部署机新，二进制链接了对旧 glibc 不存在的符号版本。解决：① 在部署机同版本环境编译；② 静态链接（-static，或用 musl 静态编译）；③ 用容器（Docker）锁定编译/运行环境一致；④ 降低用到的 glibc 特性（避免新符号）。核心是「编译环境 glibc ≤ 运行环境 glibc」。

3.3

错误处理（本章重中之重）

本章：TLPI 第 03 章 — System Programming Concepts 源码核验：Linux v6.6（include/linux/err.h — MAX_ERRNO 错误返回约定） - 上一节：3.3 The Standard C Library; The GNU C Library (glibc) - 下一节：3.5 参数传递（概念）

本节讲什么

系统调用和库函数失败时返回 -1 并设置 errno，正确读写 errno 是所有系统编程的底线。本节回答三个问题：

  1. errno 是什么？为什么「成功不会清零它」？
  2. 内核的「负错误码」怎么变成 glibc 的「-1 + errno」？
  3. perror/strerror/strerror_r 该怎么选？HFT 的错误处理有什么讲究？

1. errno 机制：成功不清零、失败才赋值

规则 说明
成功 不会把 errno 清零（保留上一次的值）
失败 才被赋为有意义的值
线程局部 现代 glibc 里 errno 是线程局部变量（每线程独立，见 2.12）
类型 int（<errno.h>），值是 E* 宏（如 ENOENT=2）

关键坑：不能「先调函数、再看 errno」，必须「先看返回值、失败才读 errno」：

/* ❌ 错误：成功路径也可能留下旧 errno */
open(path, O_RDONLY);
if (errno != 0) { ... }      /* errno 可能是上一次失败留下的脏值！ */

/* ✅ 正确：先看返回值，失败再读 errno */
int fd = open(path, O_RDONLY);
if (fd == -1) {
    /* 此时 errno 才有意义 */
    perror("open");
}

因为成功时内核/glibc 不碰 errno，它保留的是上一次失败的值。用 if (errno) 判断成功与否是经典 bug。

2. 底层机制：MAX_ERRNO 与负错误码

「返回 -1 + 设 errno」是 glibc 的翻译结果，内核实际返回的是 -errno：

内核返回：成功 → 返回值（fd ≥ 0 / 指针）
          失败 → rax = -errno（落在 [-4095, -1]）
                  ↑ MAX_ERRNO = 4095（include/linux/err.h:17）
      │
glibc 判断 rax ∈ [-4095, -1] ?
      ├─ 是 → errno = -rax，返回 -1
      └─ 否 → 返回 rax（合法值）

所以直接 syscall(SYS_open, ...) 拿到的返回值是 -2（-ENOENT），不是 -1——因为你绕过了 glibc 的翻译层（见 3.3）。这也是「错误码都是小负数」的由来：-1 ~ -4095 被内核保留给错误码，0 以上的才是合法返回值（fd、指针、字节数）。

3. 常见错误码速查（HFT 高频）

errno 值 含义 典型场景
EPERM 1 权限不足（无 capability） 绑低端口、改系统参数
ENOENT 2 文件/目录不存在 配置文件路径写错
EINTR 4 被信号打断 read/epoll_wait 被信号中断
EAGAIN/EWOULDBLOCK 11 非阻塞操作暂无数据 非阻塞 fd 读空
ENOMEM 12 内存不足 分配失败
EACCES 13 权限拒绝 打开无权限文件
EFAULT 14 传给内核的指针非法 野指针传给 syscall
EBUSY 16 资源忙 文件锁冲突、设备占用
EINVAL 22 参数无效 flags 传错
EMFILE 24 进程 fd 数达上限 fd 泄漏
ENOSPC 28 磁盘满 写盘失败
EPIPE 32 读端已关闭的管道 写已关闭的 socket

EINTR 是系统编程最常被忽略的错误码：系统调用被信号打断时返回 -1 + EINTR，这是正常情况不是错误，应重试而不是报错退出（见 Ch21 信号、Ch63 epoll）。

4. 打印 / 退出工具

strerror(errnum) 错误码 → 字符串 非线程安全（静态缓冲区）
strerror_r(errnum, buf, len) 线程安全版 GNU 语义返回 char*，POSIX 语义返回 int（musl 差异点）

5. HFT / 嵌入式关联

现象 本节机制的兑现
EINTR 打断热路径 recv/epoll_wait 被信号打断返回 EINTR，必须重试，否则漏掉行情/事件

6. 代码示例

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    /* 1. 标准错误处理：先返回值，失败读 errno */
    int fd = open("/no/such/file", O_RDONLY);
    if (fd == -1) {
        perror("open failed");                       /* "open failed: No such file..." */
        fprintf(stderr, "errno=%d (%s)\n", errno, strerror(errno));
    }

    /* 2. 线程安全版 strerror_r（GNU 语义返回 char*） */
    char buf[128];
    fprintf(stderr, "thread-safe: %s\n",
            strerror_r(ENOENT, buf, sizeof(buf)));

    /* 3. EINTR 重试模式 */
    char rbuf[16];
    ssize_t n;
    do {
        n = read(STDIN_FILENO, rbuf, sizeof(rbuf));
    } while (n == -1 && errno == EINTR);   /* 被信号打断，重试 */
    if (n == -1) perror("read");

    return 0;
}

代码自测（Q&A）

Q1：为什么「成功不会清零 errno」？这会导致什么 bug？ A：因为成功时内核/glibc 不去碰 errno（省一次写），它保留的是上一次失败留下的旧值。这导致 if (errno != 0) 判断成败是错的——可能上一次失败的脏值还在。正确做法是先看返回值（如 fd == -1），失败后才读 errno。

Q2：系统调用失败，为什么「返回 -1」而具体原因在 errno？底层机制是什么？ A：内核实际返回的是负错误码（-errno，如 -ENOENT=-2，落在 [-4095,-1]，MAX_ERRNO=4095）。glibc 包装判断返回值是否在这个范围：是则 errno = -返回值、返回 -1，否则当作合法返回值。所以「-1 + errno」是 glibc 翻译的结果——直接 syscall() 拿到的是 -2 不是 -1。

Q3：EINTR 是什么？为什么它不是真正的「错误」？ A：EINTR（=4）表示系统调用被信号打断了——某个信号处理函数执行完，被阻塞的系统调用（read/epoll_wait 等）返回 -1 + EINTR。这是正常情况，不是 I/O 失败，应该重试（while (n==-1 && errno==EINTR)），而不是当作错误退出。忽略它会导致热路径偶发漏读事件。

Q4：perror、strerror、strerror_r 有什么区别？多线程该用哪个？ A：perror(msg) 打印 msg: 错误文本 到 stderr（用当前 errno，最简单）；strerror(errnum) 把错误码转成字符串，但用静态缓冲区，非线程安全；strerror_r 是线程安全版（写入调用者提供的 buf）。多线程程序（HFT 交易系统）必须用 strerror_r，避免多个线程同时调 strerror 互相覆盖缓冲区。

Q5：EAGAIN 和 EACCES 分别是什么？如何区分处理？ A：EAGAIN（=11，非阻塞模式下 =EWOULDBLOCK）表示「资源暂时不可用、稍后重试」——如非阻塞 fd 读空、socket 发送缓冲满，是可恢复的暂时状态，应重试或进 epoll 等待；EACCES（=13）表示「权限不足」，是永久性失败，重试也没用，应报错或换权限。两者本质不同：一个「等一会再来」，一个「根本没权限」。

3.5

参数传递（概念）

本章：TLPI 第 03 章 — System Programming Concepts 源码核验：Linux v6.6（include/linux/uaccess.h、arch/x86/entry/syscalls/syscall_64.tbl） - 上一节：3.3 错误处理（本章重中之重） - 下一节：3.4 可移植编程（SUSv3 / POSIX）

本节讲什么

系统调用的参数从用户态传到内核态，不是「直接共享内存」那么简单。本节回答三个问题：

  1. x86-64 上系统调用的参数怎么传？（寄存器约定）
  2. 为什么内核不能直接解引用用户态传来的指针？copy_from_user 在防什么？
  3. 一个用户指针如果传错了，会发生什么（EFAULT）？

完整机制在 05 Ch5.4，这里建立「用户态/内核态数据传递要拷贝 + 校验」的核心心智。

1. 系统调用的参数传递：寄存器约定

系统调用号 + 参数都通过寄存器传（不是栈）。x86-64 约定：

寄存器 内容
rax 系统调用号（如 write=1）
rdi 第 1 个参数
rsi 第 2 个参数
rdx 第 3 个参数
r10 第 4 个参数
r8 第 5 个参数
r9 第 6 个参数 
/* write(fd, buf, count) 的底层：rax=1, rdi=fd, rsi=buf, rdx=count */
long my_write(int fd, const void *buf, size_t count) {
    long ret;
    asm volatile (
        "syscall"
        : "=a"(ret)
        : "a"(1), "D"(fd), "S"(buf), "d"(count)   /* 1=SYS_write */
        : "rcx", "r11", "memory"
    );
    return ret;
}

注意：系统调用最多 6 个参数（寄存器就这么多）。超过 6 个参数的系统调用很少见，必要时内核会定义结构体指针一次性传入（如 clone、io_uring_setup）。

系统调用号表（syscall_64.tbl）决定了「号码 → 内核函数」的映射：

0   read            sys_read
1   write           sys_write
2   open            sys_open
9   mmap            sys_mmap
57  fork            sys_fork
228 clock_gettime   sys_clock_gettime
257 openat          sys_openat

2. 为什么内核不能直接解引用用户指针

内核拿到用户态传来的指针（如 write 的 buf），不能直接 *buf 解引用。因为：

风险 说明
指向内核内存 恶意程序传一个内核地址，直接解引用 = 内核被读/写攻击
指向其他进程 用户指针可能指向别的进程的地址空间（内核态下无此隔离）
未映射/已换出 指针指向的页可能根本不存在，解引用触发内核态缺页异常 → panic

所以内核必须先校验范围 + 拷贝，用 copy_from_user/copy_to_user：

/* include/linux/uaccess.h —— 用户态↔内核态数据拷贝（内部先 access_ok 校验） */
static __always_inline __must_check unsigned long
__copy_from_user(void *to, const void __user *from, unsigned long n);   /* :93 */
static __always_inline __must_check unsigned long
__copy_to_user(void __user *to, const void *from, unsigned long n);     /* :120 */

完整流程：

用户态 write(fd, buf, count)
      │  glibc：buf 是用户态指针，塞进 rsi
      ▼
内核 sys_write
      │  拿到 buf（用户态指针），先 access_ok() 校验 buf 指向用户态合法范围
      ▼
copy_from_user(kernel_buf, buf, count)    ← 把数据从用户态拷贝到内核态缓冲区
      │  （若拷贝失败/越界，返回剩余未拷贝字节数，syscall 报 EFAULT）
      ▼
内核用 kernel_buf 干活（写文件/发网络）

为什么必须拷贝：内核不能信任用户指针，拷贝到内核缓冲区后，数据就在内核自己的内存里了，用户态再怎么改原指针也不影响。这就是「用户态↔内核态边界」的核心安全模型。

3. EFAULT：用户指针传错的信号

当用户态传了一个非法指针（野指针、未映射地址、指向内核的地址）给系统调用，copy_from_user/access_ok 校验失败，系统调用返回 -1 + EFAULT（=14）。

char *bad = (char *)0x1;            /* 非法地址 */
ssize_t n = write(1, bad, 10);      /* → 返回 -1，errno = EFAULT */
perror("write");                    /* "write: Bad address" */

关键区分：EFAULT 是「你传的指针有问题」（内存 bug），不是「I/O 出错了」。排查时先看是不是野指针/悬空指针/缓冲区越界，别去查磁盘或网络。

4. 系统调用的参数类型：标准 typedef

系统调用的参数和返回值大量用标准 typedef（而非裸 int/long），保证跨平台可移植：

类型 用途 例子
size_t 无符号长度 write 的 count
ssize_t 有符号长度（可返回 -1） read/write 返回值
off_t 文件偏移 lseek
pid_t 进程 ID fork/getpid
uid_t/gid_t 用户/组 ID chown

别写死 int/long 当 ID/偏移——off_t 在 32 位平台需 _FILE_OFFSET_BITS=64 才是 64 位，裸 long 会在大文件（>2GB）上溢出。这是可移植编程的基础（见 3.6）。

5. HFT / 嵌入式关联

现象 本节机制的兑现
野指针传内核 EFAULT 说明传了非法地址给 syscall，是内存 bug，先查指针生命周期
大数据拷贝开销 write 大缓冲时 copy_from_user 有拷贝成本，超大块考虑 mmap 零拷贝（见 2.8）
6 参数上限 系统调用最多 6 个参数，复杂调用用结构体指针（如 clone、io_uring_setup）
内核态安全 内核不信任用户指针，是「用户态崩溃不能拖垮内核」的隔离基石

6. 代码示例

#include <stdio.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

int main(void) {
    /* 正常：buf 指向合法用户态内存 */
    char buf[] = "hello kernel\n";
    write(STDOUT_FILENO, buf, strlen(buf));

    /* 非法指针：触发 EFAULT */
    char *bad = (char *)0x1;          /* 未映射地址 */
    ssize_t n = write(STDOUT_FILENO, bad, 10);
    if (n == -1)
        printf("write(bad_ptr) → errno=%d (%s)\n", errno, strerror(errno));

    /* 空指针：同样 EFAULT */
    n = write(STDOUT_FILENO, NULL, 10);
    if (n == -1)
        printf("write(NULL)    → errno=%d (%s)\n", errno, strerror(errno));

    return 0;
}

运行：gcc -o p p.c && ./p。两个非法指针调用都返回 errno=14（EFAULT）——内核的 access_ok 校验拦下了它们，而不是让内核去解引用非法地址。

代码自测（Q&A）

Q1：x86-64 系统调用的参数怎么传？最多几个参数？ A：通过寄存器传（不是栈）：rax=系统调用号，rdi/rsi/rdx/r10/r8/r9 = 第 1~6 个参数。所以最多 6 个参数。超过 6 个参数的系统调用（如 clone、io_uring_setup）会改用结构体指针，一次传入所有参数。

Q2：为什么内核不能直接解引用用户态传来的指针？ A：三个风险：① 恶意程序传内核地址，直接解引用 = 内核被读/写攻击；② 用户指针可能指向其他进程地址空间（内核态下无此隔离）；③ 指针指向的页可能未映射/已换出，解引用触发内核态缺页异常导致 panic。所以内核必须 access_ok 校验 + copy_from_user 拷贝到内核缓冲区。

Q3：copy_from_user 和 copy_to_user 分别干什么？为什么必须拷贝？ A：copy_from_user 把数据从用户态拷贝到内核态（如 write 的 buf），copy_to_user 反之（如 read 把数据拷回用户缓冲）。必须拷贝是因为内核不信任用户指针——拷到内核缓冲区后数据就在内核自己的内存里，用户态再改原指针也不影响内核操作，这是「用户态崩溃不能拖垮内核」的隔离基石。

Q4：EFAULT 是什么？它说明什么问题？ A：EFAULT（=14）表示传给内核的指针非法——access_ok/copy_from_user 校验失败（野指针、未映射地址、指向内核的地址）。它说明是用户态的内存 bug（指针生命周期/越界问题），不是 I/O 错误。排查时先查是不是野指针/悬空指针/缓冲区越界，别去查磁盘网络。

Q5：为什么 off_t 不要写死成 long？ A：因为 off_t 的宽度依赖平台和编译选项——32 位平台需定义 _FILE_OFFSET_BITS=64 才让 off_t 是 64 位，否则裸 long 在文件 >2GB 时会溢出，导致 lseek 偏移错误。用标准 typedef（off_t/pid_t/ssize_t）而不是裸 int/long，是跨平台可移植的基础（见 3.6）。

本节讲什么

同一份 C 代码，为什么在 Linux 能编译、换到别的 Unix 就报「未声明函数」？为什么手册里总让你在开头定义 _GNU_SOURCE？为什么文件偏移不能写死 long？本节回答三个问题：

  1. 功能测试宏（_POSIX_C_SOURCE / _XOPEN_SOURCE / _GNU_SOURCE）是什么？为什么必须放在所有 #include 之前？
  2. 标准 typedef（off_t / pid_t / size_t）为什么比裸 int / long 可移植？_FILE_OFFSET_BITS=64 解决什么？
  3. SUSv3 / POSIX 这套标准到底规定了什么？glibc 怎么用 features.h 落实「方言切换」？

1. 可移植性到底难在哪

「可移植」不是「写一次到处跑」，真正的障碍是这三件事：

障碍 例子 后果
API 存在性 epoll 只有 Linux；kqueue 只有 BSD 直接调用 → 别的平台编译不过
类型宽度 long 在 32 位平台是 4 字节、64 位平台是 8 字节 文件偏移 / ID 溢出，ABI 不匹配
语义细节 strerror_r 返回值：glibc 是 char*、musl 是 int 同一函数不同 C 库行为不同

Linux 世界解决这三件事的标准武器，就是功能测试宏（管「暴露哪些 API」）+ 标准 typedef（管「类型宽度跨平台一致」）。

2. 功能测试宏（Feature Test Macros）

glibc 里藏着一大堆非标准 / 各标准版本的函数。默认情况下 glibc 只暴露最保守的一批（ISO-C + 基础 POSIX）。要解锁更多 API，得先「声明自己要用哪个标准」——这就是功能测试宏。

宏 取值示例 解锁什么 谁定义
_POSIX_C_SOURCE 200809L POSIX.1-2008 标准接口 POSIX
_XOPEN_SOURCE 700 SUSv4（X/Open 扩展，POSIX 超集） SUS
_GNU_SOURCE （有定义即可） 全部 + Linux/GNU 扩展（epoll、GNU 版 strerror_r） glibc
_DEFAULT_SOURCE （有定义即可） 恢复 glibc 默认暴露的杂项 BSD/Linux 函数 glibc

两条铁律：

  1. 必须放在所有 #include 之前——功能测试宏在 <features.h> 里被读一次就「定型」，先 #include 了别的头再定义宏 = 无效。
/* ❌ 错误：宏定义太晚，前两个 include 已经按默认方言展开过了 */
#include <stdio.h>
#include <unistd.h>
#define _GNU_SOURCE        // 到这里才定义，前面的头已经定死

/* ✅ 正确：宏必须在最前面，或在编译命令里 -D_GNU_SOURCE */
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
  1. _GNU_SOURCE 最省心但最不「可移植」——它解锁了所有 Linux 专属函数，代价是写出来的代码一旦用了 epoll / GNU 版 strerror_r，换到非 glibc 环境就可能编译不过。追求「只在 Linux 上跑」就用 _GNU_SOURCE；追求「严格 POSIX 可移植」就只用 _POSIX_C_SOURCE=200809L。

编译期等价写法：

gcc -D_GNU_SOURCE -o prog prog.c          # 等价于源码里 #define _GNU_SOURCE
gcc -D_POSIX_C_SOURCE=200809L -o prog prog.c   # 严格 POSIX，锁掉 GNU 扩展

3. 标准 typedef：别写死 int / long

系统调用的参数和返回值大量用标准 typedef，而不是裸 int/long，就是为了让类型宽度在跨平台时由头文件统一决定：

类型 用途 定义处（glibc）
pid_t 进程 ID <bits/types.h> → __pid_t
off_t 文件偏移 <bits/types.h> → __off_t
size_t / ssize_t 无符号 / 有符号长度 <stddef.h> / <sys/types.h>
uid_t / gid_t 用户 / 组 ID <bits/types.h>
mode_t 文件权限位 <bits/types.h>
dev_t / ino_t 设备号 / inode 号 <bits/types.h>

最经典的坑是 off_t 与大文件：32 位平台上 off_t 默认是 32 位，lseek 无法处理 >2GB 的偏移。解决办法是定义 _FILE_OFFSET_BITS=64，让 off_t 变成 64 位：

#define _FILE_OFFSET_BITS 64   /* 32 位平台也要能操作 >2GB 大文件 */
#include <sys/types.h>
#include <unistd.h>

off_t pos = lseek(fd, 0, SEEK_END);   /* 现在 off_t 是 64 位，不会溢出 */

为什么别写死 long：long 的宽度跟平台走（LP64 下 8 字节，ILP32 下 4 字节），而 off_t 的宽度由 _FILE_OFFSET_BITS 决定，两者可能不一致。写死 long 当偏移，在 32 位平台 + 大文件场景下必然溢出或错位。用标准 typedef，让头文件替你管宽度。

4. SUSv3 / POSIX 标准演进

年份 标准 说明
1988 POSIX.1-1988 第一版，系统接口 + shell
1990 POSIX.1-1990 (ISO 9945-1) 成为 ISO 标准
1996 POSIX.1-1996 实时扩展（信号量、时钟、调度）
2001 POSIX.1-2001 = SUSv3 合并 X/Open，TLPI 全书基线
2008 POSIX.1-2008 = SUSv4 当前主流，_POSIX_C_SOURCE=200809L

TLPI 全书以 SUSv3 为基线，并标注「这是 Linux 扩展」的地方。读 TLPI 时遇到「SUSv3 规定……」意味着：这是 POSIX 保证的接口，任何合规 Unix 都有；而「Linux 特有」意味着：换平台要自己找替代（如 epoll ↔ kqueue）。

5. glibc 怎么落实方言切换：features.h

功能测试宏的真正机制在 <features.h>——所有 glibc 标准头文件开头都 #include <features.h>，它读一遍功能测试宏，据此 #define 或 #undef 一堆 __USE_* 内部开关，后续头文件再按这些开关决定「这个函数声明要不要露出来」。

#include <unistd.h>
      │  开头 #include <features.h>
      ▼
features.h 读 _GNU_SOURCE / _POSIX_C_SOURCE / _XOPEN_SOURCE ...
      │  换算成 __USE_GNU / __USE_POSIX / __USE_XOPEN ... 内部开关
      ▼
后续头文件按 __USE_* 决定暴露哪些声明（如 epoll_create 只在 __USE_GNU 时声明）

这就是「功能测试宏必须在最前面」的底层原因：<features.h> 只会被有效处理一次，先 include 别的头就会用「默认方言」把开关定死。

6. HFT / 嵌入式关联

现象 本节机制的兑现
静态可移植二进制 用 musl + 严格 POSIX（_POSIX_C_SOURCE）编译，摆脱 glibc 方言依赖（见 glibc 节）
大文件 / 大偏移 行情回放、日志文件 >2GB 时必须 _FILE_OFFSET_BITS=64，否则 lseek 溢出
锁死 GNU 扩展 用 epoll/io_uring 时需 _GNU_SOURCE；这是「只在 Linux 跑」的显式声明
交叉编译 功能测试宏 + 标准 typedef 保证目标平台 ABI 正确，不依赖宿主机类型宽度
类型宽度敏感 HFT 里用 int64_t 存时间戳/序号，别用可能 32 位的 long

    /* 3. 标准 typedef：pid_t 不写死 int */

}

代码自测（Q&A）

Q1：功能测试宏为什么必须放在所有 #include 之前？ A：因为 glibc 的所有标准头文件开头都会 #include <features.h>，它读取功能测试宏并一次性换算成 __USE_* 内部开关。如果你先 #include 了别的头，features.h 已经在「默认方言」下把开关定死了，之后再 #define _GNU_SOURCE 也不生效。所以宏必须在最前面，或编译期用 -D 传入。

Q2：_GNU_SOURCE、_POSIX_C_SOURCE、_XOPEN_SOURCE 分别解锁什么？ A：_POSIX_C_SOURCE（如 200809L）解锁 POSIX.1-2008 标准接口；_XOPEN_SOURCE（如 700）解锁 SUSv4（POSIX 超集，X/Open 扩展）；_GNU_SOURCE 解锁全部 + Linux/GNU 扩展（epoll、GNU 版 strerror_r）。_GNU_SOURCE 最省心但最不「可移植」——用了 GNU 扩展的代码换到非 glibc 环境可能编译不过。

Q3：off_t 为什么不能写死成 long？_FILE_OFFSET_BITS=64 干嘛的？ A：long 的宽度跟平台走（32 位 4 字节、64 位 8 字节），而 off_t 的宽度由 _FILE_OFFSET_BITS 决定。32 位平台上 off_t 默认 32 位，无法处理 >2GB 的文件偏移；定义 _FILE_OFFSET_BITS=64 后 off_t 变 64 位。写死 long 当偏移，在 32 位 + 大文件场景必然溢出或错位。用标准 typedef，让头文件替你管宽度。

Q4：标准 typedef（pid_t/off_t/mode_t 等）本质是什么？在哪定义的？ A：本质是「类型宽度的跨平台抽象」——用 pid_t 而不是 int，让头文件根据平台决定实际宽度。glibc 里它们在 <bits/types.h> 定义为 __pid_t/__off_t 等底层类型，再由 <sys/types.h> 等标准头 typedef 成公开名字。开发者只认公开的 pid_t/off_t，不关心底层是 int 还是 long。

Q5：SUSv3 和 POSIX 是什么关系？TLPI 为什么以 SUSv3 为基线？ A：SUSv3（Single UNIX Specification v3）= POSIX.1-2001，是 POSIX 与 X/Open 标准合并后的统一标准；SUSv4 = POSIX.1-2008 是当前主流。TLPI 以 SUSv3 为基线，遇到「SUSv3 规定……」意味着这是 POSIX 保证的接口（任何合规 Unix 都有），而「Linux 特有」意味着换平台要自己找替代（如 epoll ↔ kqueue）。

五个必须记住的坑

  1. 成功不清 errno → 判断成败只能看返回值，不能 if (errno)。
  2. EINTR 不是错误 → 被信号打断，while (n==-1 && errno==EINTR) 重试。
  3. EFAULT 是内存 bug → 传了非法指针给内核，查野指针/越界，别查 I/O。
  4. EAGAIN 是暂时状态 → 非阻塞「暂无数据」，重试或进 epoll，别当失败。

代码自测（Q&A）

Q1：用一句话串起本章五个概念。 A：系统调用是「用户态进内核的受控入口」（编号+寄存器+陷阱指令），库函数是 glibc 在其上的高层封装（纯用户态函数不进内核）；系统调用失败返回 -1 并设 errno（成功不清零、EINTR 重试）；参数通过寄存器传递且内核必须 copy_from_user 拷贝校验；跨平台靠功能测试宏 + 标准 typedef 保证 API 可见性与类型宽度一致。

Q2：为什么「判断成功失败要看返回值，不能看 errno」？ A：因为成功时内核/glibc 不会清零 errno，它保留的是上一次失败留下的旧值。用 if (errno != 0) 判断成败会误判。正确姿势：fd = open(...); if (fd == -1) { /* 这时才读 errno */ }。

Q3：系统调用失败，用户看到「-1 + errno」，内核实际返回了什么？ A：内核实际返回 -errno（负错误码，如 -ENOENT=-2，落在 [-4095,-1]，MAX_ERRNO=4095）。glibc 包装检测返回值在此范围，则设 errno = -返回值 并返回 -1。所以「-1 + errno」是 glibc 翻译的结果——直接 syscall() 拿到的是 -2 不是 -1。

Q4：EINTR、EAGAIN、EFAULT 三个错误码怎么区分处理？ A：EINTR（=4）被信号打断 → 重试（while(n==-1 && errno==EINTR)）；EAGAIN（=11）非阻塞暂时无数据 → 稍后重试或进 epoll；EFAULT（=14）传给内核的指针非法 → 查内存 bug（野指针/越界），不是 I/O 错误。前两个是「可恢复的暂时状态」，最后一个是「程序 bug」。

Q5：fopen 和 open 的本质区别是什么？ A：fopen 是 ISO-C 标准库函数，返回带用户态缓冲的 FILE*，跨平台（Windows 用 msvcrt 实现）；open 是 POSIX 系统调用包装，返回内核整数 fd，无用户态缓冲，Unix/Linux 限定。fopen 内部最终会调用 open 系统调用（Linux 上），但多了一层用户态缓冲管理。

题 1：文件复制（基础）

编写程序 ./copy source dest，用 open/read/write/close 复制文件，要求：

  1. 检查所有系统调用返回值
  2. 用 perror 报告错误
  3. 用标准 typedef（ssize_t/mode_t），不写死 int/long
参考答案 
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>

int main(int argc, char *argv[]) {
    if (argc != 3) {
        fprintf(stderr, "Usage: %s source dest\n", argv[0]);
        exit(EXIT_FAILURE);
    }

    int src = open(argv[1], O_RDONLY);
    if (src == -1) { perror("open source"); exit(EXIT_FAILURE); }

    int dst = open(argv[2], O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (dst == -1) { perror("open dest"); exit(EXIT_FAILURE); }

    char buf[4096];
    ssize_t n;
    while ((n = read(src, buf, sizeof(buf))) > 0) {
        if (write(dst, buf, n) != n) {   /* 短写处理：要求写满 n 字节 */
            perror("write"); exit(EXIT_FAILURE);
        }
    }
    if (n == -1) { perror("read"); exit(EXIT_FAILURE); }

    if (close(src) == -1) perror("close src");
    if (close(dst) == -1) perror("close dst");
    return 0;
}

题 2：EINTR 重试（错误处理）

上面的 read 没有处理 EINTR。改写循环，让 read 被信号打断时自动重试，而不是当作错误退出。

参考答案 
#include <errno.h>   /* errno, EINTR */

ssize_t n;
do {
    n = read(src, buf, sizeof(buf));
} while (n == -1 && errno == EINTR);   /* 被信号打断 → 重试 */

if (n == -1) { perror("read"); exit(EXIT_FAILURE); }
/* n == 0 表示读到 EOF，正常退出循环 */

要点：EINTR 是「被信号打断」的正常现象（见错误处理节），不是 I/O 失败。忽略它会导致热路径偶发漏读。

题 3：直接 syscall（绕过 glibc）

不调用 write()，用 syscall(SYS_write, ...) 直接写 "raw\n" 到标准输出，并解释为什么失败时返回值是负错误码而不是 -1。

参考答案 
#include <stdio.h>
#include <unistd.h>
#include <string.h>
#include <sys/syscall.h>

int main(void) {
    long ret = syscall(SYS_write, STDOUT_FILENO, "raw\n", 4);
    if (ret < 0 && ret >= -4095) {   /* 负错误码，需自己还原 errno */
        int e = -(int)ret;
        fprintf(stderr, "errno=%d (%s)\n", e, strerror(e));
    }
    return 0;
}

要点：syscall() 绕过 glibc 的 MAX_ERRNO 错误翻译层（见 glibc 节 / 错误处理节），失败时返回的是 -errno（如 -2=-ENOENT），不是 -1。要自己判断 [-4095,-1] 并还原 errno。

题 4：可移植性（功能测试宏）

下面代码用到了 GNU 扩展 strerror_r 返回 char* 的语义。说明如何用功能测试宏声明这一方言，以及换 musl 后为什么行为会变。

参考答案 
#define _GNU_SOURCE          /* 声明用 GNU 方言：strerror_r 返回 char* */
#include <string.h>
#include <stdio.h>

int main(void) {
    char buf[128];
    char *p = strerror_r(ENOENT, buf, sizeof(buf));  /* GNU：返回 char* */
    printf("%s\n", p);
    return 0;
}

要点：strerror_r 在 glibc 下默认是 GNU 语义（返回 char*），在 musl 下是 POSIX 语义（返回 int）。换 musl 后 char *p = strerror_r(...) 会类型不匹配——这就是「可移植性」的典型坑：同一个函数，不同 C 库语义不同（见 glibc 节 / 可移植节）。严格 POSIX 下应写成 int r = strerror_r(...); if (r == 0) ...。
