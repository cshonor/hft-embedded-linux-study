易错清单

  1. errno 成功时不清零 —— 判成败只能看返回值，不能 if (errno != 0)。
  2. errno 是 TLS —— 每线程一份，不能拿它做线程间通信。
  3. 库函数失败不一定设 errno —— getenv 找不到返回 NULL 且 errno = 0（先读 man NOTES）。
  4. strerror 返回全局静态缓冲 —— 存指针等于存「最后一次」的结果；多线程下是数据竞争。
  5. EINTR 不是错误 —— 被信号打断要重试，不是报错退出。
  6. EFAULT 是内存 bug —— 传了非法指针给内核，查野指针/越界，别去查磁盘或网络。
  7. 直接 syscall() 拿的是 -errno —— syscall(2) 库函数自带翻译层；只有手写 syscall 指令才是裸负值。
  8. fopen 与 open 不是一一对应 —— fopen("w") 隐含 O_CREAT，open(O_WRONLY) 没有。
  9. 「用 syscall() 更快」是错的直觉 —— 它比 glibc 包装还慢（多一层壳），只在 glibc 没包装时才用。
  10. 加编译旗标不一定只增不减 —— -std=c99 → __STRICT_ANSI__ → glibc 不再自动补 _DEFAULT_SOURCE/_POSIX_C_SOURCE → strdup/clock_gettime/strsignal 全部消失。
  11. memmem 守的是 __USE_MISC，不是 __USE_GNU —— 所以严格 POSIX 反而锁掉它。
  12. __USE_POSIX2008 这个宏不存在 —— POSIX.1-2008 在 glibc 里的真名是 __USE_XOPEN2K8。
  13. -std=c99 想拿回 POSIX 声明必须显式加 FTM —— -D_POSIX_C_SOURCE=200809L 或 -D_GNU_SOURCE。
  14. strerror_r 有两套签名 —— glibc 默认 POSIX 版（返回 int），只有 _GNU_SOURCE 才切 GNU 版（返回 char *）。
  15. char 的符号是实现定义 —— x86/aarch64 Linux 上 (char)0xFF 是 -1；getchar() 的返回值必须装进 int。
  16. struct{char;int;char} 是 12 字节 —— 不是 6 字节；跨平台传结构体必须显式定序 + 对齐。
  17. reboot() 没有 glibc 包装 —— 必须 syscall(SYS_reboot, ...)，且需要 CAP_SYS_BOOT。

3.1

System Calls 系统调用

本章：TLPI 第 03 章 — System Programming Concepts 源码核验：Linux v6.6 — arch/x86/entry/entry_64.S:87、arch/x86/entry/common.c:40,73、arch/x86/entry/syscall_64.c:16、include/linux/err.h:17 - 上一节：本章首页 - 下一节：3.2 Library Functions 库函数

本节讲什么

系统调用 = 用户进程请求内核做受保护操作的唯一受控入口。

一次 write(1, "x", 1) 表面上是调了个函数，实际上要走完「用户态寄存器准备 → 特权级切换 → 内核查表 → 服务例程 → 返回」这条路。本节把这条路拆成能实测的四件事：

  1. 同一次写操作的三条路径（glibc 包装 / syscall(2) / 手写 syscall 指令）——它们的差别不是「快慢」，而是谁替你翻译错误码。
  2. 失败时到底谁在说话：内核用 [-4095, -1] 表示错误，glibc 把它翻成 -1 + errno，手写指令拿到的是裸的 -errno。
  3. 系统调用号从哪来（syscall_64.tbl → sys_call_table[]）。
  4. 一种「不是错误码的失败」：SIGPIPE——写一个读端已关闭的管道，默认不是给你 EPIPE，而是把整个进程杀掉。

本节只讲「怎么进去、怎么出来、参数怎么过界」。内核入口的汇编细节见 05/Ch5 系统调用。

1. 三条调用路径

路径 写法 谁翻译错误码 什么时候用
glibc 包装 write(1, buf, n) glibc：-1 + 设 errno 99% 的场合，唯一推荐
syscall(2) syscall(SYS_write, 1, buf, n) syscall(2) 自己也翻译：-1 + 设 errno glibc 没提供包装的调用（如 SYS_gettid、早期的 io_uring）
手写指令 内联汇编 syscall 没人翻译：拿到裸的 -errno freestanding（裸机 / 固件 / 内核模块）、没有 libc 的场合

第一条最反直觉的是：syscall(2) 并不是「裸接口」。它自己就套了一层壳（存参、查表、把 -errno 翻成 -1 + errno）。真正裸的是第三条。

2. 错误返回约定：为什么是 [-4095, -1]

内核不能「返回 -1 同时设一个全局变量」——内核态没有 errno 这个概念。它的约定是：返回值直接就是 -errno，并且用 MAX_ERRNO 保证这个区间永远不和合法返回值冲突。

层 成功 失败
内核（裸 syscall 指令） rax = 结果（fd / 字节数 / 指针，≥ 0） rax = -errno，落在 [-4095, -1]
glibc 包装 原样返回 errno = -rax，返回 -1 
/* include/linux/err.h:17 */
#define MAX_ERRNO   4095

为什么是 4095：这个上界要同时满足两件事——① 比任何平台的 errno 最大值都大；② 小到让「合法返回值」永远不会落进来。内核里所有合法指针都在内核地址空间的低半区之上，0 以上、-4095 以下的整数不受影响，所以 [-4095,-1] 可以安全地当错误码专用区间。这也是为什么内核里到处能看到 if (IS_ERR(ptr)) 这种写法（IS_ERR 就是在判这个区间）。

3. 代码示例：三条路径 + 失败分支 + SIGPIPE

源码：../code/c3_1_syscall_path.c

/* TLPI 第 03 章 §3.1 —— 同一次写操作的「三条路径」+ 失败分支 + SIGPIPE
 *
 *   ① glibc 包装函数      write(1, ...)            唯一推荐用法
 *   ② syscall(2) 通用入口  syscall(SYS_write, ...)  给「glibc 没给包装」的调用兜底
 *   ③ 手写 syscall 指令    寄存器约定：rax=调用号，rdi/rsi/rdx/r10/r8/r9=参数，
 *                          返回值也在 rax；内核的失败约定是 rax 落在 [-4095, -1]
 *
 * 本节最反直觉的两条：
 *   1. syscall(2) 这个「通用入口」本身就做了一层翻译 —— 它把内核的 -errno 变成
 *      -1 并把 errno 设上；手写指令拿到的是裸返回码 -9，errno 根本没人碰。
 *   2. 往「没有读端的管道」里写，默认不是收到一个错误码，而是**整个进程被
 *      SIGPIPE(13) 杀掉**。这是网络服务必须第一行就忽略它的原因。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_1 c3_1_syscall_path.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>

/* 内核把 [-4095, -1] 这一段保留给错误码。范围上界来自
 * include/linux/err.h 的 MAX_ERRNO = 4095 —— 拿到裸返回码时，
 * 落在这个区间里就意味着失败，-ret 就是 errno 的值。 */
#define KERNEL_ERR_MAX (-4095)

/* 把三种调用方式的返回值放在一起读：同一个错误，三种「报法」 */
static void report(const char *tag, long ret, int err)
{
    if (ret >= 0) {
        printf("  %-34s ret=%-6ld (成功)\n", tag, ret);
    } else if (ret == -1) {
        printf("  %-34s ret=-1      errno=%d (%s)   ← glibc 约定：-1 + errno\n",
               tag, err, strerror(err));
    } else if (ret >= KERNEL_ERR_MAX) {
        printf("  %-34s ret=%-6ld  ← 裸返回码：-ret = %d 才是 errno 该有的值，而 errno 仍是 %d\n",
               tag, ret, (int) -ret, err);
    } else {
        printf("  %-34s ret=%-6ld  ← 超出内核错误码区间 [-4095,-1]\n", tag, ret);
    }
}

/* ③ 手写 syscall 指令：只传 3 个参数，足够覆盖 write 这组实验。
 *    clobber 里必须写 rcx / r11 —— syscall 指令会把返回地址放 rcx、
 *    把 rflags 放 r11，编译器不知道，所以要显式告诉它。 */
static long raw_syscall3(long nr, long a1, long a2, long a3)
{
    long ret;
    __asm__ volatile ("syscall"
                      : "=a"(ret)
                      : "a"(nr), "D"(a1), "S"(a2), "d"(a3)
                      : "rcx", "r11", "memory");
    return ret;
}

/* ⑧ 往「读端已关闭的管道」写一次，看 SIGPIPE 的两种处置 */
static void sigpipe_child(sighandler_t how, const char *label)
{
    int p[2];
    if (pipe(p) != 0) {
        printf("  %-16s → pipe 创建失败\n", label);
        return;
    }
    fflush(NULL);
    pid_t pid = fork();
    if (pid == 0) {                       /* ---- 子进程 ---- */
        signal(SIGPIPE, how);
        close(p[0]);                      /* 本进程里把读端关掉 → 管道再无读者 */
        errno = 0;
        ssize_t w = write(p[1], "x", 1);
        printf("  %-16s → 子进程没被杀死：write 返回 %zd，errno=%d (%s)  EPIPE=%d\n",
               label, w, errno, strerror(errno), EPIPE);
        _exit(0);
    }
    close(p[0]);
    close(p[1]);
    int status = 0;
    waitpid(pid, &status, 0);
    if (WIFSIGNALED(status)) {
        printf("  %-16s → 子进程被信号 %d 终止   （shell 里 $? = 128+%d = %d）\n",
               label, WTERMSIG(status), WTERMSIG(status), 128 + WTERMSIG(status));
    } else if (WIFEXITED(status)) {
        printf("  %-16s → 子进程 exit(%d)\n", label, WEXITSTATUS(status));
    }
}

int main(void)
{
    /* 容器里 stdout 是 socket → 默认全缓冲。混用 printf 与直接 write(1,...) 会乱序，
     * 这里显式关掉缓冲，让每一行的先后顺序真实可读。 */

    int err;

    err = errno;
    report("write(1, msg, n)", ret, err);

    printf("=== ② syscall(2) 通用入口 ===\n");

4. 参数怎么进内核：寄存器约定

系统调用的号与参数走寄存器，不走栈。x86-64 的约定：

寄存器 内容
rax 系统调用号（如 write=1）
rdi rsi rdx r10 r8 r9 第 1 ~ 6 个参数
rcx r11 被 syscall 指令破坏（分别存返回地址与 rflags），所以内联汇编里必须写进 clobber 列表

两个容易踩的点：

  • 最多 6 个参数。参数更多的调用（clone、io_uring_setup）改为「结构体指针 + 一次传进去」，本质还是 6 个以内的寄存器。
  • r10 而不是 rcx 当第 4 个参数。见下：syscall 指令会把 rcx 拿去存返回地址，「第 4 个参数用 rcx」是 int 0x80 时代的老约定。

内核入口的坐标（v6.6）

位置 作用
arch/x86/entry/entry_64.S:87 SYM_CODE_START(entry_SYSCALL_64) 内核侧入口：换栈（:97）、建立 pt_regs（:106）、sysretq 回程（:198）
arch/x86/entry/common.c:40 do_syscall_x64() :48 判 unr < NR_syscalls；:50 regs->ax = sys_call_table[unr](regs); —— 就是这一步执行了服务例程
arch/x86/entry/common.c:73 do_syscall_64() :76 从用户态进入（syscall_enter_from_user_mode）；:82 无效号回 __x64_sys_ni_syscall → ENOSYS
arch/x86/entry/syscall_64.c:16 const sys_call_ptr_t sys_call_table[] 号 → 内核函数的函数指针数组

所以「系统调用号」的本质就是这张表的数组下标。syscall_64.tbl 只是生成这张表的输入文件。

5. 拆开包装看真相：write() / syscall() / syscall 指令（Pi 实测）

先把两个撞名的东西分开——这一对名字是本章最高频的混淆点：

名字 是什么 在哪一层
syscall(2) glibc 提供的 C 函数（通用入口，号由你传） 用户态
syscall x86_64 的 CPU 指令（aarch64 上对应 svc #0），触发用户态→内核态切换 用户态/内核态边界

于是所有调用路径都可以归入一个三层封装阶梯：

层 是什么 系统调用号 陷入指令
write(fd, buf, len) glibc 专用封装 编译期写死（__NR_write） 间接执行
syscall(__NR_write, ...) glibc 通用封装 你的第一个参数 间接执行
手写汇编（不链 libc） 无封装 自己填 rax（aarch64 为 x8） 直接执行

实测一：glibc 的 write 到底有多薄（树莓派 5 · aarch64 · glibc 2.41）

对 Pi 5（Debian trixie）上的 /lib/aarch64-linux-gnu/libc.so.6 反汇编，write 符号总共 0x1c = 28 字节：

00000000000e4620 <__write@@GLIBC_2.17>:     ; ← 你调的 write() 就这 28 字节
   e4624: sxtw x0, w0                       ; fd 符号扩展到 64 位
   e4628: mov  x6, #0x40                    ; ★ 调用号 64（__NR_write）写死在这
   e462c: mov  x5, #0x0                     ; 补齐后续参数位（write 只有 3 参）
   e4634: mov  x3, #0x0
   e4638: b    8264c                        ; 尾跳公共路径

顺着尾跳追两层，就到了所有 syscall 共用的底部：

   825c8: mov  x8, x6                       ; 调用号进 x8（aarch64 约定：号在 x8）
      …                                     ; 参数整队到 x0–x5
   8ef68: svc  #0x0                         ; ★★ 真正的陷入指令，全 libc 就这几条
; ——返回之后，errno 翻译层——
   8265c: cmn  x0, #0x1, lsl #12            ; x0+4096 产生进位？→ 返回值落在 [-4095,-1]（2 节约定）
   8267c: neg  w3, w0                       ; errno = -返回值
   82680: mov  x0, #-1                      ; 返回值改写成 -1
   8268c: str  w3, [x2, x1]                 ; 写进线程局部 errno

这张反汇编一次性验证了本节的三个论断：

  1. write() 不直接进内核——它是 28 字节的薄封装，全部工作就是「把写死的调用号放好、参数整队、跳到公共路径」；
  2. 真正触发内核的是 svc #0x0（x86_64 上是 syscall 指令）——这才是「直接调用内核」那一步，同一个 libc 里所有系统调用共用它；
  3. -1 + errno 是封装翻译出来的——cmn x0, #4096 → 写 TLS → 返回 -1 那几条指令就是 2 节错误返回约定 + glibc 翻译层的实体（对应 3.3 的机制描述，这里给了机器码证据）。

x86_64 上是同一个故事：调用号进 rax、参数进 rdi/rsi/rdx/r10/r8/r9、陷入指令 syscall。区别只在寄存器名和指令名——架构决定了「号放哪、参数放哪、哪条指令陷入」，不变的是三层封装结构。

实测二：把封装剥干净——无 libc 纯汇编（code/c3_14_raw_asm.S）

    adr  x1, msg           /* buf */
    mov  x2, #21           /* len */
    mov  x8, #64           /* __NR_write —— 没有封装替你写死，自己填 */
    svc  #0x0              /* 和 glibc 包装底部同一条指令 */
    mov  x0, #42
    mov  x8, #93           /* __NR_exit —— exit 也得自己发 */
    svc  #0x0

6. 数据怎么过边界：access_ok + copy_from_user

内核拿到用户态传来的指针（如 write 的 buf），不能直接解引用：

风险 后果
指向内核地址 恶意程序借内核之手读/写内核内存
指向别的进程 内核态没有「当前进程的地址空间」之外的隔离幻想
指向未映射页 内核态缺页 → 直接 panic，而不是给个错误码

所以每个带指针参数的系统调用都要：access_ok() 校验范围 → copy_from_user() 把数据拷进内核缓冲。校验失败就是 EFAULT(14)（不是 SIGSEGV）。这一段的完整实测见 3.4 错误处理 的 c3_13_efault.c；内核侧细节见 05/Ch5.4 实现与参数验证。

7. HFT / 嵌入式关联

现象 本节机制的兑现
热路径少 syscall 每次调用都要跨特权级；c3_12_syscall_speed.c 实测「陷入内核」比同特权级的 call 贵一到两个数量级
绕过 glibc 拿裸返回码 syscall(2) 仍是翻译过的；只有手写指令才是裸的 —— 无 libc 环境判断错误必须自己看 [-4095,-1]
网络服务必须先忽略 SIGPIPE 对端断开后自己再 write，默认行为是进程被 13 号信号杀掉，而不是拿到一个错误码
新增 syscall 用不上包装 新内核特性（io_uring、close_range）在 glibc 提供包装前，只能自己 syscall(SYS_xxx, ...)
参数上限 6 个 自己设计 syscall 或写 ioctl 时，参数超 6 个就要改成结构体指针

常见陷阱

  1. 不检查返回值就往下用
int fd = open(path, O_RDONLY);
read(fd, buf, n);          /* ❌ fd == -1 时这里只会拿到 EBADF，真实原因已丢 */

正确写法：if ((fd = open(...)) == -1) { perror("open"); exit(1); }。失败原因只在 errno 里，而 errno 会被下一次调用覆盖（见 3.4）。

  1. 把 syscall() 当裸接口，以为它也返回负错误码

syscall(2) 是 glibc 提供的包装器的包装器。想拿裸返回码只能手写 syscall 指令——但那样也就没有 errno 了。

  1. 混淆系统调用与库函数

man 2 查到的是系统调用，man 3 查到的是库函数。strcpy/atoi/strlen 是纯用户态库函数，一次内核都不进（3.2 有实测）。

  1. 忘了处理「被信号打断」

EINTR（=4）是正常情况不是错误：read/epoll_wait 被信号打断就返回它，应该重试。

  1. 把 SIGPIPE 当普通错误码

它不是一个返回值，是一个信号。不忽略就默认杀进程——这正是本 demo 第一版挂掉的原因。

代码自测（Q&A）

Q1：glibc 的 write()、syscall(SYS_write, ...)、手写 syscall 指令，三者的本质区别是什么？ A：前两者都是包装：都会把内核的 -errno 翻译成「返回 -1 + 设 errno」。syscall(2) 不是裸接口，它自己就套了一层。只有手写 syscall 指令拿到的是裸返回码 -9，此时 errno 根本没被碰过——本 demo ④ 段实测三行并排，raw 那行 errno=0 就是证据。

Q2：内核为什么要保留 [-4095, -1] 作为错误码区间？4095 是怎么定的？ A：内核态没有 errno 全局变量，所以约定「返回值本身就是 -errno」。为了不和合法返回值冲突，用 MAX_ERRNO=4095（include/linux/err.h:17）圈出一个专用区间：上界比任何平台的 errno 最大值都大，下界又小到不会和合法值（fd、字节数、指针）撞上。IS_ERR() 判的就是这个区间。

Q3：sys_call_table 是什么？系统调用号从哪来？ A：sys_call_table[] 是 arch/x86/entry/syscall_64.c:16 定义的函数指针数组，「系统调用号 = 数组下标」。它由 arch/x86/entry/syscalls/syscall_64.tbl 生成。内核执行路径是 common.c:40 do_syscall_x64() → :48 判 unr < NR_syscalls → :50 regs->ax = sys_call_table[unr](regs)；号越界就落到 __x64_sys_ni_syscall() 返回 ENOSYS（本 demo ⑤ 段实测）。

Q4：write() 失败返回 -1 并把 errno 设成 EFAULT，为什么不是段错误？ A：因为内核从不直接解引用用户指针。它先 access_ok() 校验地址范围，再 copy_from_user() 拷贝；校验失败就直接返回 -EFAULT。所以用户态传坏指针不会把内核搞崩，只会拿到一个错误码——这也是「用户态崩溃拖不垮内核」的隔离基石。

Q5：往一个读端已关闭的管道里 write，会发生什么？网络服务为什么要忽略 SIGPIPE？ A：默认（SIG_DFL）是进程被 SIGPIPE(13) 终止，shell 视角 $? = 141；只有把 SIGPIPE 设成 SIG_IGN 之后，write 才会像普通失败那样返回 -1 + errno=EPIPE(32)。网络服务对端断开后再写就是同一情形——不忽略它，服务会被自己的日志/回包写死。见本 demo ⑧ 段。

3.2

Library Functions 库函数

本章：TLPI 第 03 章 — System Programming Concepts 实测核验：Compiler Explorer gcc 13.3.0 / glibc 2.39（/proc/self/io 计数器） - 上一节：3.1 System Calls 系统调用 - 下一节：3.3 The Standard C Library; The GNU C Library (glibc)

本节讲什么

「库函数不是系统调用」这句话人人会说，但多数人只是记住了结论。本节把它量出来：用 /proc/self/io 的 syscr/syscw 计数器（进程累计发起的 read/write 系统调用次数）直接看每一次调用有没有进内核。

三个要点：

  1. 库函数与系统调用的方向：C 代码 → glibc 库 → 系统调用 → 内核。
  2. 「不进内核」在计数器上长什么样——以及这个测量方法本身的两个陷阱（底噪、看不见的 brk/mmap）。
  3. 一个活教材：库函数的封装会附加你没写出来的 flag，所以同一文件 open() 能开、fopen() 不能开。

1. 三个角色，不要混在一起

角色 层面 代表函数 谁定义
ISO-C 标准库 语言层面 fopen() / printf() / malloc() C 语言标准（ISO/IEC 9899）
POSIX 系统调用 操作系统接口层面 open / read / write POSIX 规范
glibc / musl 用户态中间层（桥梁） 上面两者的具体实现 各 C 库项目

核心一句话：C 语言本身没有任何操作文件、进程、网络的内置语法——没有 openfile 关键字，没有 fork 运算符。全部靠库函数，库再去请求内核。

调用链条（Linux）：

你写的应用 C 代码
        │  调用
        ▼
【glibc】
   ├─ 情况 A：调标准 C 函数 fopen()
   │      → glibc 做用户态缓冲管理 → 内部再调 open() 系统调用
   └─ 情况 B：直接调 POSIX 接口 open()
          → glibc 薄薄一层封装 → 发 syscall 指令
                │
                ▼
        内核真正干活（打开文件）
                │
                ▼
        结果返回 glibc → 返回你的代码

方向千万别搞反：是 C 库去调用系统调用，不是系统调用调用 C 语言。

2. 库函数的三种类型

类型 例子 是否进内核
纯用户态 strcpy / strlen / atoi / snprintf 否（一次都不进）
薄封装 read / write / open 一次 syscall
多层 fopen / fprintf / fclose 内部 open + 用户态缓冲管理，flush 时才产生 write
走外部数据的 getpwnam / gethostbyname 每次都要读文件/网络（走 NSS），见下面的实测

3. 代码示例：把「不进内核」量出来

源码：../code/c3_2_lib_vs_syscall.c

/* TLPI 第 03 章 §3.2 —— 「库函数 ≠ 系统调用」的可测量版
 *
 * 口头说「atoi 不进内核、getpwuid 会读文件」很容易，本 demo 用 /proc/self/io
 * 的计数器把它**量出来**：
 *   rchar / wchar = 进程累计读/写的字节数
 *   syscr / syscw = 进程累计发起的 read / write 系统调用**次数**
 *
 * 方法论（很重要，否则读数会骗你）：
 *   读 /proc/self/io 这个动作自身就要 open + read + close，所以每测一次都自带
 *   一份「底噪」。本 demo 第一件事就是把这个底噪量出来，之后所有数字都与它对比，
 *   而不是假装底噪是 0。
 *   另外 /proc/self/io 只统计 read/write 这一类 I/O 系统调用 —— brk / mmap /
 *   ioctl 它看不见。所以它证明的是「没做 I/O」，不是「没进内核」。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_2 c3_2_lib_vs_syscall.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

struct io_counters {
    unsigned long long rchar, wchar, syscr, syscw;
};

static struct io_counters before, after;
static unsigned long long sink;
static char userbuf[64] = "ce";
static struct passwd *pw;
static FILE *out;

static int read_io(struct io_counters *io)
{
    FILE *f = fopen("/proc/self/io", "r");
    if (!f) {
        return -1;
    }
    char line[128];
    io->rchar = io->wchar = io->syscr = io->syscw = 0;
    while (fgets(line, sizeof line, f)) {
        sscanf(line, "rchar: %llu", &io->rchar);
        sscanf(line, "wchar: %llu", &io->wchar);
        sscanf(line, "syscr: %llu", &io->syscr);
        sscanf(line, "syscw: %llu", &io->syscw);
    }
    fclose(f);
    return 0;
}

/* 先把两次快照都取完，再打印 —— 打印本身也会产生 write 系统调用，
 * 若边打边测，就把自己的输出算进被测对象里了。 */
static void measure(const char *tag, void (*work)(void))
{
    if (read_io(&before) < 0) {
        printf("  %-34s /proc/self/io 不可读（errno=%d）\n", tag, errno);
        return;
    }
    work();
    if (read_io(&after) < 0) {
        return;
    }
    printf("  %-34s Δsyscr=%-3lld Δsyscw=%-3lld Δrchar=%-9lld Δwchar=%lld\n", tag,
           (long long) (after.syscr - before.syscr),
           (long long) (after.syscw - before.syscw),
           (long long) (after.rchar - before.rchar),
           (long long) (after.wchar - before.wchar));
}

/* ---------- 被测的五种「工作负载」 ---------- */

static void w_nothing(void)                 /* 空负载 → 量出底噪 */
{
}

static void w_userlib(void)                 /* 纯用户态：解析、拷贝、求长度 */
{
    char buf[256];
    for (int i = 0; i < 100000; i++) {
        strcpy(buf, "abcdef");
        sink += strlen(buf) + (unsigned long long) atoi("12345");
    }
}

static void w_snprintf(void)                /* 同样是「格式化」，但不落到任何 fd */
{
    char buf[64];
    for (int i = 0; i < 1000; i++) {
        snprintf(buf, sizeof buf, "%d-%s", i, "x");
        sink += (unsigned long long) buf[0];
    }
}

static void w_getpwnam(void)                /* 走 NSS 的查找：真的去读文件 */
{
    pw = getpwnam(userbuf);
}

static void w_malloc(void)                  /* 堆操作：brk/mmap 不在 /proc/self/io 视野里 */
{
    for (int i = 0; i < 1000; i++) {
        void *p = malloc(64);
        sink += (unsigned long long) (p != NULL);
        free(p);
    }
}

static void w_fprintf_buffered(void)        /* 100 次 fprintf，故意不 fflush */
{
    for (int i = 0; i < 100; i++) {
        fprintf(out, "x");
    }
}

static void w_fflush(void)                  /* 把用户态缓冲真正交出去 */
{
    fflush(out);
}

int main(void)
{
    setvbuf(stdout, NULL, _IONBF, 0);

    /* 先从 /etc/passwd 里自己读一个**真实存在**的用户名。
     * 不能写死 getuid()：本容器里 uid 0 并不在 /etc/passwd 中，
     * getpwuid(0) 会返回 NULL（那是「查无此人」，不是出错）。 */
    FILE *pwf = fopen("/etc/passwd", "r");
    if (pwf) {
        char line[256];
        if (fgets(line, sizeof line, pwf)) {
            char *colon = strchr(line, ':');
            if (colon) {
                *colon = '\0';
                size_t n = strlen(line);
                if (n > sizeof userbuf - 1) {      /* 手工截断，避免 -Wformat-truncation */
                    n = sizeof userbuf - 1;
                }
                memcpy(userbuf, line, n);
                userbuf[n] = '\0';
            }
        }
        fclose(pwf);
    }
    printf("=== 0. 本环境参数 ===\n");
    printf("  euid=%d uid=%d，/etc/passwd 第一条记录的用户名 = \"%s\"\n\n",
           (int) geteuid(), (int) getuid(), userbuf);

    /* ④ 要用的可写 FILE*：/dev/null 是最好的靶子（写进去的字节数照样计入 wchar）。
     * 这里必须用 open() + fdopen()：fopen("/dev/null","w") 在本容器里会被拒
     * （它隐式带 O_CREAT|O_TRUNC），而 open(O_WRONLY) 是允许的。 */
    int dn = open("/dev/null", O_WRONLY);
    errno = 0;
    FILE *probe = fopen("/dev/null", "w");
    printf("=== 0b. 先记一个 §3.2 的活教材：库函数封装给你加了什么 ===\n");
    printf("  open(\"/dev/null\", O_WRONLY)   → %s\n", dn >= 0 ? "成功" : "失败");
    printf("  fopen(\"/dev/null\", \"w\")       → %s（errno=%d %s）\n",
           probe ? "成功" : "失败", errno, strerror(errno));
    if (probe) {
        fclose(probe);
    }
    printf("    ↑ fopen 的 \"w\" 隐含 O_WRONLY|O_CREAT|O_TRUNC，比上面多了两位 flag；\n"
           "      本环境恰好只拒绝带 O_CREAT 的打开（/dev 是受限挂载）→ 同一个文件，\n"
           "      open() 能开、fopen() 不能开。所以下面改用 fdopen 绕开这一层。\n\n");
    out = dn >= 0 ? fdopen(dn, "w") : tmpfile();
    if (!out) {
        printf("  可写 FILE* 拿不到，后面的缓冲实验跳过\n");
    }

    printf("=== 1. 底噪：读一次 /proc/self/io 自身要花几个系统调用 ===\n");
    measure("空负载（这就是底噪）", w_nothing);
    printf("\n");

    printf("=== 2. 纯用户态库函数：strcpy / strlen / atoi ×100000 ===\n");
    measure("×100000 轮", w_userlib);
    printf("    ↑ 与上一行的底噪完全相同 → 放大十万倍也没多出一次 I/O。\n"
           "      这就是「库函数不进内核」的可测量形式。\n\n");

    printf("=== 3. snprintf：同样是「格式化」，所以它当然也不进内核 ===\n");
    measure("snprintf ×1000 次到内存", w_snprintf);
    printf("    ↑ 和 fprintf 的区别不在「格式化」，只在**写给了谁**\n\n");

    printf("=== 4. getpwnam()：走 NSS 的名称解析，真的会去读 /etc/passwd ===\n");
    measure("getpwnam() 第 1 次", w_getpwnam);
    measure("getpwnam() 第 2 次", w_getpwnam);
    measure("getpwnam() 第 3 次", w_getpwnam);
    printf("  → 查到用户 = %s，uid = %d，errno = %d\n", pw ? pw->pw_name : "NULL",
           pw ? (int) pw->pw_uid : -1, errno);
    printf("    ↑ 三次的增量都一样、且都明显大于底噪 → 每次调用都重新 open+read 了\n"
           "      /etc/passwd。本环境（glibc 无 nscd/systemd-userdbd）**没有跨调用的\n"
           "      缓存**；反过来说，在 HFT 的日志热路径里调 getpwuid/getpwnam，\n"
           "      每一行日志都要多付几次 read 系统调用。\n"
           "    另注：查无此人时返回 NULL 且**不设 errno** —— 本容器 getpwuid(0) 就是\n"
           "      这种情形，别把它当成 ENOENT 那种错误。\n\n");

    printf("=== 5. stdio 的缓冲：fprintf 不立即产生 write 系统调用 ===\n");
    if (out) {
        measure("fprintf ×100 次（未 fflush）", w_fprintf_buffered);
        measure("fflush() 一次", w_fflush);
        printf("    ↑ 100 次 fprintf 的 Δsyscw 是 0，字节只进了用户态缓冲；\n"
               "      fflush 一次才把它变成 1 次 write —— 这就是「printf 慢」的真正位置。\n"
               "      注意 Δwchar：缓冲里的字节数只有真正 write 出去才计入。\n\n");
    }

    printf("=== 6. malloc/free：/proc/self/io 看不见的「内核活动」 ===\n");
    measure("malloc(64)+free ×1000", w_malloc);
    printf("    ↑ 增量与底噪相同，但这**不能**推出「malloc 没进内核」：\n"
           "      brk / mmap 不是 read/write，压根不在 /proc/self/io 的统计范围内。\n"
           "      用本文件当可移植的「库函数 vs 系统调用」证据时，只对 I/O 类调用有效。\n\n");

    printf("=== 读表要点 ===\n");
    printf("  · Δsyscr / Δsyscw 是「次数」，Δrchar / Δwchar 是「字节数」\n");
    printf("  · 每测一次自带一份底噪（读 /proc/self/io 自身），所以只能比相对差\n");
    printf("  · 同一个「格式化」动作：snprintf→内存 0 次 I/O，fprintf→FILE* 由缓冲决定\n");
    printf("  · NSS 查找一次 = 数次 read；这是 getpwuid 出现在日志热路径里的代价\n");
    if (out) {
        fclose(out);
    }
    return 0;
}

4 副产物 查到 ce（uid 10240），getpwuid(0) → NULL 且 errno=0 「查无此人」与「出错」是两回事；NULL 不代表 errno 有意义
5 fprintf ×100 → Δsyscw=0；fflush() → Δsyscw=1、Δwchar=100 100 次 fprintf 一次内核都没进；fflush 才把它变成 1 次 write。「printf 慢」的位置在缓冲策略和字节量，不在格式化
6 malloc 等于底噪 但不能推出「malloc 没进内核」：brk/mmap 不是 read/write，不在 /proc/self/io 统计范围内

测量方法本身的两个陷阱（这是本 demo 最该带走的东西）： ① /proc/self/io 只统计 read/write 这一类 I/O 系统调用，brk/mmap/ioctl 它看不见 → 它证明的是「没做 I/O」，不是「没进内核」； ② 读计数器本身要花 2 次 read → 只能比相对差，不能指望绝对值为 0。

4. fopen 模式 → open flags 的映射

fopen 模式 open 对应的 flags 说明
"r" O_RDONLY 只读，文件必须存在
"w" O_WRONLY \| O_CREAT \| O_TRUNC 只写、不存在则创建、存在则截断清空
"a" O_WRONLY \| O_CREAT \| O_APPEND 追加写，O_APPEND 保证每次写在末尾
"r+" O_RDWR 读写，文件必须存在
"w+" O_RDWR \| O_CREAT \| O_TRUNC 读写 + 创建 + 截断
"a+" O_RDWR \| O_CREAT \| O_APPEND 读写 + 追加

对照本 demo 的 0b 段：fopen(path,"w") 一定会带上 O_CREAT|O_TRUNC。所以在「不允许创建/截断」的挂载点（只读文件系统、受限容器、某些设备节点）上，fopen("w") 会失败，而 open(path, O_WRONLY) 可以成功。

谁提供 fopen、谁提供 open

fopen() open()
归属 ISO-C 标准库 POSIX 系统调用包装
返回值 FILE *（带用户态缓冲 + 文件位置 + 锁） int fd（内核整数句柄）
缓冲 有（_IOFBF/_IOLBF/_IONBF 三档） 无，每次 read/write 就是一次调用
可移植 C 标准，跨平台 POSIX；Windows 只有非标准的 _open

同一个 fopen，不同操作系统内部不同：Linux 上 glibc 的 fopen 内部调 open 系统调用；Windows 上 msvcrt 的 fopen 内部调 CreateFileA。C 标准只规定「外表」，不规定内核细节。

5. HFT / 嵌入式关联

路线 要点

代码自测（Q&A）

Q1：怎么证明「strcpy/atoi 不进内核」，而不是只背下这句话？ A：用 /proc/self/io 的 syscr/syscw（进程累计的 read/write 系统调用次数）。先量一次空负载得到底噪（读计数器自身要 2 次 read），再跑 100000 轮 strcpy/strlen/atoi——读数与底噪完全相同。放大十万倍都没有多出一次 I/O，这就叫可测量。

Q2：/proc/self/io 能不能证明「某个库函数没进内核」？ A：不能。它只统计 read/write 这一类 I/O 系统调用，brk/mmap/ioctl/futex 都看不见。本 demo 里 malloc(64)+free ×1000 的增量等于底噪，但那是「没做 I/O」，不是「没进内核」——malloc 该 brk/mmap 的时候照样会进。要说「没进内核」得看 strace/perf。

Q3：fopen(path,"w") 和 open(path, O_WRONLY) 是同一件事吗？ A：不是。fopen 的 "w" 隐含 O_WRONLY|O_CREAT|O_TRUNC，比 open(O_WRONLY) 多了创建和截断两位。本 demo 0b 段实测：同一台机器的同一个 /dev/null，open("/dev/null", O_WRONLY) 成功、fopen("/dev/null","w") 失败 errno=13。这就是「库函数是薄封装」这句话的真实含义——薄，但不等于没有附加行为。

Q4：fprintf 100 次为什么一次 write 都没有？ A：因为字节进了用户态缓冲。stdout/stderr/FILE 的缓冲模式决定「什么时候真正发 write」：全缓冲（_IOFBF）要等缓冲满或 fflush；行缓冲（_IOLBF）遇到 \n 就发；无缓冲（_IONBF）每次立即发。本 demo 实测 fprintf ×100 → Δsyscw=0，紧随其后一次 fflush() → Δsyscw=1、Δwchar=100。

Q5：为什么说 getpwnam() 在 HFT 日志热路径里是「隐性成本」？ A：因为它走 NSS，每次调用都会去读 /etc/passwd（本 demo 实测每次 Δsyscr=4，三次都一样 → 本环境无缓存）。每写一行日志就多几次 read 系统调用，在高频路径上叠加起来很可观。要么把用户信息缓存下来，要么日志里不带这些字段。

The Standard C Library; The GNU C Library (glibc)

本节讲什么

TLPI 第 3.3 节标题里其实藏着三层身份，很多人读到这里会把它们混成一句话：

层 是什么 由什么标出
C 语言标准 ISO C / C99 / C11 / C17 —— 语言层面的库函数规格 __STDC_VERSION__
POSIX / SUS 操作系统接口规范（open/read/fork…） _POSIX_VERSION（来自 <unistd.h>）
具体实现 glibc / musl / uClibc / bionic —— 上面两者的落地 glibc 用 __GLIBC__ + gnu_get_libc_version() 标出自己

本节回答三个问题：

  1. glibc 到底提供了什么？它和「C 标准库」「POSIX」是什么关系？
  2. glibc 封装系统调用时，怎么把内核的负错误码翻译成 errno + -1？
  3. 怎么在代码里认出当前是哪个实现？为什么这件事在交叉编译时很值钱？

1. glibc 的角色：一个库，三种身份

身份 提供什么 例子
ISO-C 标准库实现 C 语言标准要求的函数 printf / malloc / strcpy / qsort
POSIX 封装层 系统调用的薄外壳 open / read / write / fork / mmap
glibc 扩展 Linux 专属的非标准函数与语义 epoll 系列、GNU 版 strerror_r、%m 格式符

所以「glibc」不是「C 标准库」的同义词——它包含 C 标准库，还多出 POSIX 封装和一堆 Linux 扩展。换个 C 库（musl），C 标准库函数还在，但扩展函数和某些行为细节会变。

2. glibc 怎么封装系统调用：MAX_ERRNO 错误翻译

glibc 的 open() 不是把内核返回值原样传回，而是做一次错误翻译。关键在内核的错误返回约定：

/* include/linux/err.h:17 —— 内核错误码的取值范围 */
#define MAX_ERRNO   4095

完整往返流程：

用户态调 open(path, flags)
      │  glibc 包装：rax=2(调用号), rdi=path, rsi=flags, rdx=mode
      ▼
syscall 指令陷入内核（arch/x86/entry/entry_64.S:87）
      │  arch/x86/entry/common.c:50  regs->ax = sys_call_table[nr](regs)
      ▼
内核返回：成功 → rax = 新 fd（≥ 0）
          失败 → rax = -errno（如 -2 = -ENOENT，落在 [-4095, -1]）
      ▼
glibc 包装判断：rax 是否落在 [-4095, -1]？
      ├─ 是 → errno = -rax（如 2），返回 -1
      └─ 否 → 返回 rax（合法 fd）

这就是「系统调用失败返回 -1、具体原因看 errno」的底层机制。 顺带解释了 3.1 里那条反直觉的实测：绕过 glibc 之后拿到的返回值是负错误码（-9/-38），不是 -1——因为翻译那一步没了。

glibc 版本 vs 内核版本

两者没有 1:1 对应关系：

  • glibc 封装系统调用，但滞后于内核。新内核特性（io_uring、close_range、pidfd_*）要等 glibc 出新版本提供封装才能直接用；等不及时就自己 syscall(SYS_xxx, ...)（见 3.1 ③⑥ 段）。
  • 老 glibc 跑在新内核上通常没问题（内核 ABI 向后兼容），但用不到新 syscall 的现成封装。
  • 反过来：新 glibc 编出的二进制跑在老 glibc 上会报 GLIBC_2.xx not found——它链接了对旧版本不存在的符号版本。

3. 代码示例：认出你用的是哪个实现

源码：../code/c3_3_glibc.c

/* TLPI 第 03 章 §3.3 —— 标准 C 库 vs GNU C 库：怎么认出你用的是哪一个
 *
 * 三层身份要分开：
 *   ① C 语言标准（ISO C / C99 / C11…）—— 由 __STDC_VERSION__ 标出
 *   ② POSIX / SUS 规范            —— 由 _POSIX_VERSION 标出（来自 unistd.h）
 *   ③ 具体实现（glibc / musl / uClibc / bionic）—— glibc 会定义 __GLIBC__ 并给出
 *      gnu_get_libc_version()、confstr(_CS_GNU_LIBC_VERSION)
 *
 * 嵌入式/HFT 的用处：交叉编译时「板上跑的是 glibc 还是 musl」决定了一堆行为差异
 * （NSS、locale、malloc 实现、dlopen 语义），所以部署脚本里认一下版本很值。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_3 c3_3_glibc.c
 */
#define _GNU_SOURCE
#include <features.h>
#include <gnu/libc-version.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    printf("=== ① 实现身份：这是 glibc 吗？ ===\n");
#ifdef __GLIBC__
    printf("  __GLIBC__       = %d\n", __GLIBC__);
    printf("  __GLIBC_MINOR__ = %d\n", __GLIBC_MINOR__);
#else
    printf("  未定义 __GLIBC__ → 不是 glibc（可能是 musl / uClibc / bionic）\n");
#endif

#ifdef __GLIBC_PREREQ
    printf("  __GLIBC_PREREQ(2, 34) = %d  (运行期/编译期都可用于条件编译)\n",
           __GLIBC_PREREQ(2, 34) ? 1 : 0);
#else
    printf("  未定义 __GLIBC_PREREQ\n");
#endif

    printf("\n=== ② 运行期问库自己（比宏更可信：宏只反映头文件版本） ===\n");
#ifdef __GLIBC__
    printf("  gnu_get_libc_version()          = %s\n", gnu_get_libc_version());
    printf("  gnu_get_libc_release()          = %s\n", gnu_get_libc_release());
#endif
    char cbuf[64] = {0};
    if (confstr(_CS_GNU_LIBC_VERSION, cbuf, sizeof cbuf) > 0) {
        printf("  confstr(_CS_GNU_LIBC_VERSION)   = %s\n", cbuf);
    } else {
        printf("  confstr(_CS_GNU_LIBC_VERSION)   不可用\n");
    }

    printf("\n=== ③ C 语言标准版本 ===\n");
#ifdef __STDC_VERSION__
    printf("  __STDC_VERSION__ = %ldL  (199901L=C99, 201112L=C11, 201710L=C17)\n",
           (long) __STDC_VERSION__);
#else
    printf("  __STDC_VERSION__ 未定义 → 编译器在 C89/C90 模式\n");
#endif
#ifdef __STDC__
    printf("  __STDC__         = %d\n", __STDC__);
#endif

    printf("\n=== ④ POSIX 规范版本（来自 unistd.h） ===\n");
#ifdef _POSIX_VERSION
    printf("  _POSIX_VERSION   = %ldL  (200809L = POSIX.1-2008)\n", (long) _POSIX_VERSION);
#else
    printf("  _POSIX_VERSION 未定义\n");
#endif

    printf("\n=== ⑤ 编译器身份 ===\n");
#ifdef __GNUC__
    printf("  __GNUC__         = %d  (gcc 主版本)\n", __GNUC__);
    printf("  __GNUC_MINOR__   = %d\n", __GNUC_MINOR__);
#endif
#ifdef __clang__
    printf("  __clang__        = %d.%d\n", __clang_major__, __clang_minor__);
#endif

    printf("\n=== ⑥ 同一个动作在两个实现下的差异（只列判据，不下结论）===\n");
    printf("  getpwnam() 走 NSS      → glibc 有；musl 只有简化实现、不支持 nsswitch\n");
    printf("  dlopen() 语义          → glibc 支持 RTLD_DEEPBIND 等 GNU 扩展；musl 不支持\n");
    printf("  %%m 格式符            → glibc 私有（printf 里输出 strerror(errno)），"
           "其它实现没有\n");
    printf("  __GLIBC__ / gnu_get_libc_version → glibc 独有，跨实现代码里要 #ifdef 包起来\n");
    return 0;
}

4. glibc vs musl

维度 glibc musl
定位 功能最全、性能最优 极致精简、静态链接友好
体积 大（约 2MB+） 小（约 500KB）
扩展 最多（GNU 扩展、NSS、%m） 严格 POSIX，少扩展
适用 桌面 / 服务器 / 通用 嵌入式、容器（Alpine 默认）、静态可移植二进制
许可 LGPL MIT

嵌入式 / HFT 若要做静态链接、跨发行版可移植的单文件二进制，常选 musl；通用场景用 glibc。

典型可移植性差异是 strerror_r：glibc 有两套签名——默认（不定义任何 FTM）给的是 POSIX 版（返回 int，把描述写进你给的缓冲），只有 _GNU_SOURCE 才切到 GNU 版（返回 char *）；musl 只有 POSIX 版。也就是说，同一个 glibc 换一个 FTM 就可能换一套 ABI（完整实测见 3.6.1 的五组旗标矩阵：只有 -D_GNU_SOURCE 那组走 string.h:448 的 GNU 版，其余四组都走 string.h:428 的 POSIX 版）。

代码自测（Q&A）

Q1：glibc 是「C 标准库」吗？ A：不完全是。glibc 包含 C 标准库（ISO-C 要求的 printf/malloc 等），但还多出 POSIX 系统调用封装（open/read/fork）和大量 Linux/GNU 扩展（epoll、GNU 版 strerror_r、%m）。换 musl 时 C 标准库函数还在，但扩展和部分行为会变。「glibc」是「C 库的一种具体实现」，范围比「C 标准库」大。

Q2：为什么系统调用失败是「返回 -1 + 设 errno」，而不是直接返回错误码？ A：这是 glibc 的错误翻译约定。内核实际返回 -errno（落在 [-4095,-1]，见 include/linux/err.h:17 的 MAX_ERRNO=4095）。glibc 包装检查返回值是否在这个范围：是则 errno = -返回值 并返回 -1，否则当合法值返回。所以直接发 syscall 指令拿到的是 -2 而不是 -1（3.1 ④ 段实测）。

Q3：__GLIBC__ 和 gnu_get_libc_version() 有什么区别？该用哪个？ A：__GLIBC__/__GLIBC_MINOR__ 是编译期宏，反映的是编译时头文件的版本；gnu_get_libc_version() / confstr(_CS_GNU_LIBC_VERSION) 是运行期查询，反映实际加载的 .so 版本。静态链接时两者一致；动态链接时可能不一致（编译用新头文件、运行加载老库），所以「部署环境检查」要用运行期那个。

Q4：__GLIBC_PREREQ 是干嘛的？glibc 版本和内核版本是什么关系？ A：__GLIBC_PREREQ(major, minor) 是编译期检查 glibc 版本的宏，用于条件编译（如 clock_gettime 在 glibc 2.17 起不用 -lrt）。glibc 版本 ≠ 内核版本：glibc 封装系统调用但滞后——新内核特性要等 glibc 提供封装才能直接用，否则自己 syscall() 绕过；它也不会因为内核升级就变版本。

Q5：部署机报 GLIBC_2.38 not found 是什么原因？怎么解决？ A：编译机的 glibc 比部署机新，二进制链接了对旧 glibc 不存在的符号版本。解决：① 在部署机同版本环境编译；② 静态链接（-static，或 musl 静态编译）；③ 用容器锁定编译/运行环境一致；④ 降低用到的 glibc 特性（避免新符号）。核心原则是「编译环境 glibc ≤ 运行环境 glibc」。

1. errno 的六条硬规则

出处：man errno(3) + man intro(2)（TLPI 3.4 节把这些散落的规则集中讲了一遍）。

# 规则 违反后果
1 先看返回值，失败才读 errno 成功路径上读到的是脏值
2 成功的调用不会把 errno 清零 用 if (errno != 0) 判成败 → 必误报
3 errno 是一个可赋值的左值宏（#define errno (*__errno_location())） 可以手动 errno = 0 来「清场」
4 errno 是线程私有的（TLS） 用它做线程间通信 → 拿不到别的线程的值
5 判断失败必须紧邻读取：中间插一条可能失败的调用就会冲掉 读到的是中间那次调用的错误
6 库函数失败不一定设 errno（看各自 man 的 NOTES） NULL/-1 不等于「errno 有意义」

规则 2 是本节的核心：errno 是「上一次失败的原因」，不是「当前状态」。所以它天然不能被用来判断「刚才那步成没成功」。

2. 代码示例 A：六条规则逐条实测

源码：../code/c3_4_errno.c

/* TLPI 第 03 章 §3.4 —— errno 范式的六条硬规则 + 一次实测
 *
 * 六条规则（man errno(3) / intro(2)）：
 *   1. 先看返回值，再读 errno —— errno 只在「失败」时有意义
 *   2. **成功的调用不会把 errno 清零**  ← 本节最常被写错的一条
 *   3. errno 是「左值宏」：#define errno (*__errno_location())，所以能赋值
 *   4. errno 是线程私有（TLS）的：每个线程一份自己的 errno
 *   5. 判断「某个调用有没有失败」必须紧邻读取：中间插一条可能失败的调用就会冲掉
 *   6. 库函数失败**不一定**设 errno（看各自 man 的 NOTES）
 *
 * 编译：gcc -O0 -Wall -Wextra -pthread -o c3_4 c3_4_errno.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static int *g_main_errno_addr;
static int *g_thread_errno_addr;

static void *worker(void *arg)
{
    (void) arg;
    /* 先把本线程的 errno 弄成非零，证明它跟主线程互相独立 */
    errno = 12345;
    g_thread_errno_addr = &errno;
    printf("  线程：   &errno = %p   errno = %d\n", (void *) &errno, errno);
    return NULL;
}

int main(void)
{
    setvbuf(stdout, NULL, _IONBF, 0);
    int save;

    printf("=== 规则 2 实测：成功的调用不会清零 errno ===\n");
    errno = 0;
    int fd = open("/dev/null", O_RDONLY);          /* 必然成功 */
    printf("  errno=0 时 open(\"/dev/null\") 成功 → fd=%d，errno=%d\n", fd, errno);

    /* 先人为制造一个非零 errno，再跑一个成功的调用 */
    open("/definitely/not/here", O_RDONLY);        /* 必然失败，errno 被设上 */
    save = errno;
    printf("  制造失败后                     errno=%d (%s)\n", save, strerror(save));

    close(fd);
    close(-1);                                     /* 这个会失败 */
    printf("  紧接着再做一次成功的 close      → close(fd) 的返回值被忽略，errno 仍是 %d\n",
           errno);
    printf("  ↑ 结论：**errno 不会被成功调用清掉**，所以「errno != 0 就说明上一步失败」是错的\n\n");

    printf("=== 规则 3 实测：errno 是可赋值的左值宏 ===\n");
    errno = 0;
    printf("  errno = 0 之后读回 = %d\n", errno);
    errno = EDOM;
    printf("  errno = EDOM(%d) 之后读回 = %d (%s)\n", EDOM, errno, strerror(errno));
    printf("  errno 的地址（即 __errno_location()）= %p\n\n", (void *) &errno);
    errno = 0;

    printf("=== 规则 4 实测：errno 是线程私有的 ===\n");
    g_main_errno_addr = &errno;
    errno = 999;
    printf("  主线程：&errno = %p   errno = %d\n", (void *) g_main_errno_addr, errno);
    pthread_t tid;
    if (pthread_create(&tid, NULL, worker, NULL) == 0) {
        pthread_join(tid, NULL);
        printf("  两个地址%s → errno 是 TLS，多线程下各自失败互不干扰\n",
               g_main_errno_addr == g_thread_errno_addr ? "相同（意外！）" : "不同");
    } else {
        printf("  pthread_create 失败\n");
    }
    printf("  主线程的 errno 仍是 %d（没被线程里那次赋值影响）\n\n", errno);

    printf("=== 规则 5 实测：中间插一条调用会冲掉 errno ===\n");
    errno = 0;
    int bad = open("/definitely/not/here", O_RDONLY);
    int saved = errno;                    /* ✅ 紧邻读取 */
    printf("  失败 open → bad=%d，立刻读 errno=%d (%s)\n", bad, saved, strerror(saved));

    errno = 0;
    bad = open("/definitely/not/here", O_RDONLY);
    printf("  失败 open → bad=%d，但中间先 printf 了一次（它自己可能碰 errno）\n", bad);
    printf("  之后才读 errno=%d\n", errno);
    printf("  ↑ 顺序上「printf 之后再读」在本次碰巧还对，但这是运气；范式要求紧邻读\n\n");

    printf("=== 规则 6 实测：库函数失败不一定设 errno ===\n");
    errno = 0;
    double d = strtod("0.0", NULL);       /* 成功，不该碰 errno */
    printf("  strtod(\"0.0\") = %g，errno = %d\n", d, errno);
    errno = 0;
    d = strtod("1e9999", NULL);           /* 溢出 → 规范要求设 ERANGE */
    printf("  strtod(\"1e9999\") = %g，errno = %d (%s)\n", d, errno, strerror(errno));

    errno = 0;
    char *e = getenv("___definitely_not_set___");
    printf("  getenv(不存在) = %p，errno = %d  ← NULL 不代表出错，读 man NOTES\n",
           (void *) e, errno);
    return 0;
}

段 读数 说明
规则 2 失败留下 errno=2，随后 close(fd) 成功 但 errno 仍是 9 实验设计很讲究：先制造 ENOENT(2)，再故意 close(-1) 把 errno 改成 EBADF(9)——于是能同时证明「成功调用不动 errno」和「errno 会被覆盖」
规则 3 errno = EDOM(33) 后读回 33 能赋值 ⇒ 它必然是宏（展开成 *(__errno_location())），不是普通变量。所以「取 errno 的地址」其实取的是 TLS 里那个 int 的地址
规则 4 主线程 0x7eae35ea86c8 vs 线程 0x7eae35bff648 地址不同 ⇒ 实实在在的两份。线程里 errno = 12345 不影响主线程的 999
规则 5 「printf 之后再读」这次碰巧还是 2 这是运气：glibc 的 printf 在成功路径上通常不碰 errno。范式要求「紧邻读」，不能靠运气
规则 6 strtod("1e9999") → inf + errno=34（ERANGE） 溢出时设 ERANGE 是 POSIX 要求；但 strtod 成功后不保证清零
规则 6 getenv(不存在) → NULL，errno = 0 NULL 不代表出错。getenv 的 man NOTES 明确说「找不到」不是错误。不查文档就报 errno 会冤枉库函数

/* TLPI 第 03 章 §3.4 —— errno 六种典型误用，逐个实测打脸
 *
 * 每条误用都给出「错在哪 → 实测现象 → 正确写法」。
 * 编译：gcc -O0 -Wall -Wextra -pthread -o c3_5 c3_5_errno_traps.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static char *g_saved_strerror1;
static char *g_saved_strerror2;

static void *worker(void *arg)
{
    (void) arg;
    /* 误用 ⑤：多线程里共享 strerror 的静态缓冲 */
    g_saved_strerror2 = strerror(EACCES);
    return NULL;
}

int main(void)
{
    setvbuf(stdout, NULL, _IONBF, 0);

    printf("=== 误用 1：用「errno != 0」判上一步是否失败 ===\n");
    errno = 0;
    int fd = open("/dev/null", O_RDONLY);
    printf("  成功 open 后 errno = %d（干净场景下确实是 0）\n", errno);
    close(fd);
    errno = 0;
    open("/definitely/not/here", O_RDONLY);   /* 失败，留下 ENOENT */
    fd = open("/dev/null", O_RDONLY);         /* 又成功，但 errno 不会归零 */
    printf("  失败一次再成功一次，errno = %d (%s)  → 用 errno!=0 判成功/失败必然误报\n",
           errno, strerror(errno));
    close(fd);
    printf("  正确：判返回值。open 失败才返回 -1，此时 errno 才有意义\n\n");

    printf("=== 误用 2：不查返回值，直接读 errno ===\n");
    errno = 0;
    char *p = getenv("___not_set___");
    printf("  getenv(不存在) 返回 %p，errno = %d\n", (void *) p, errno);
    printf("  → 返回 NULL 是「没找到」，不是「出错」；不查文档就报错会冤枉库函数\n\n");

    printf("=== 误用 3：把 errno 当普通全局变量跨线程传 ===\n");
    errno = 7;
    pthread_t tid;
    if (pthread_create(&tid, NULL, worker, NULL) == 0) {
        pthread_join(tid, NULL);
    }
    printf("  主线程 errno = %d（线程里设的 EACCES=%d 完全没影响主线程）\n", errno, EACCES);
    printf("  → errno 是 __thread 变量，每线程一份；不能用它做线程间通信\n\n");

    printf("=== 误用 4：长期保存 strerror 返回的指针 ===\n");
    g_saved_strerror1 = strerror(ENOENT);
    printf("  第一次 strerror(ENOENT) → %p  \"%s\"\n", (void *) g_saved_strerror1,
           g_saved_strerror1);
    g_saved_strerror1 = strerror(EACCES);      /* 下一次调用覆写同一块静态缓冲 */
    printf("  再调 strerror(EACCES)  → %p  \"%s\"\n", (void *) g_saved_strerror1,
           g_saved_strerror1);
    char *again = strerror(ENOENT);
    printf("  第三次 strerror(ENOENT)→ %p  \"%s\"\n", (void *) again, again);
    printf("  → 地址恒定为同一块静态缓冲，**保存指针等于保存「最后一次」的结果**\n");
    printf("    正确：立刻 strcpy/strdup 到自己缓冲；或改用 strerror_r\n\n");

    printf("=== 误用 5：多线程共享 strerror 的静态缓冲 ===\n");
    if (pthread_create(&tid, NULL, worker, NULL) == 0) {
        pthread_join(tid, NULL);
    }
    printf("  线程里算出的指针 %p，主线程拿它的结果 = \"%s\"\n", (void *) g_saved_strerror2,
           g_saved_strerror2);
    printf("  → 两个线程写同一块缓冲，谁后写谁赢 → 数据竞争\n");
    printf("    正确：用 strerror_r / strerror_l，各自传入自己的缓冲\n\n");

    printf("=== 误用 6：把 perror 当万能报错，丢掉上下文 ===\n");
    errno = ENOENT;
    printf("  perror 输出（到 stderr）：");
    fflush(stdout);
    perror("c3_5");
    printf("  perror(msg) 等价于 fprintf(stderr, \"%%s: %%s\\n\", msg, strerror(errno))\n");
    printf("  它只给「哪一步 + 什么错」，给不了「哪个路径、哪个 fd」——业务上下文要自己带\n\n");

    printf("=== 附：glibc 的 %%m 扩展（等价于 strerror(errno)，但不用另起参数）===\n");
    errno = EACCES;
    printf("  printf 里的 %%m 直接展开：errno=%d 就是 \"%m\"\n", errno);
    printf("  ↑ 这是 glibc 私有扩展，可移植代码里别用\n");
    errno = 0;
    return 0;
}

4 同一地址 0x7ac7f39cb77a 第三次出现 strerror 返回静态缓冲，保存指针等于保存最后一次；要留就 strcpy/strdup，或用 strerror_r
5 线程算的指针被主线程读出来是 "Permission denied" 多线程必须 strerror_r(errnum, buf, len)，各自传自己的缓冲
6 perror 输出到 stderr：c3_5: No such file or directory perror 只给「哪一步 + 什么错」。哪个路径、哪个 fd、哪次重试——业务上下文要自己带

误用 4 和 5 是同一个坑的两种表现：strerror 用一块全局静态缓冲（因此非线程安全），第一次和第三次返回的是完全相同的地址——这不是巧合，是同一块内存被反复覆写。HFT 里做高频日志时，把 strerror(errno) 的结果直接存进日志结构体，等同于存了「最后一次错误」。

 *
 * 内核**不能信任**用户指针：它可能指向内核地址、指向别的进程、或根本没映射。
 * 所以每个带指针参数的系统调用都要先 access_ok() 校验、再 copy_from_user() 拷贝。
 * 校验失败时系统调用返回 -1 + EFAULT(14)（裸 syscall 拿到的是 -14）。
 *
 * 本 demo 逐种「坏指针」实测，并把 errno 与裸 syscall 的返回值并排打印，
 * 顺带把 EFAULT 与其它「看着像但完全不同」的错误码分开（EFAULT vs EBADF vs EINVAL）。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_13 c3_13_efault.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <unistd.h>

/* printf 的 %-34s 是按**字节**补齐的，而一个汉字 3 字节、显示只占 2 列 →
 * 直接用会参差不齐。这里自己数显示宽度：ASCII 记 1 列，非 ASCII 记 2 列。 */
static int disp_width(const char *s)
{
    int w = 0;
    for (; *s; s++) {
        unsigned char c = (unsigned char) *s;
        if (c < 0x80) {
            w += 1;
        } else if ((c & 0xC0) != 0x80) {   /* UTF-8 续字节不重复计数 */
            w += 2;
        }
    }
    return w;
}

static void pad(const char *s, int width)
{
    fputs(s, stdout);
    for (int i = disp_width(s); i < width; i++) {
        putchar(' ');
    }
}

static void probe(const char *tag, const void *p, size_t n)
{
    /* ① glibc 包装：-1 + errno */
    errno = 0;
    ssize_t r = write(STDOUT_FILENO, p, n);
    int e1 = errno;

    /* ② 裸 syscall 指令：直接拿内核的 -errno（不经过 glibc 翻译） */
    errno = 0;
    long r2;
    __asm__ volatile ("syscall"
                      : "=a"(r2)
                      : "a"((long) SYS_write), "D"((long) STDOUT_FILENO),
                        "S"((long) p), "d"((long) n)
                      : "rcx", "r11", "memory");
    int e2 = errno;

    printf("  ");
    pad(tag, 30);
    printf("write()=%2zd errno=%-3d %-14s | raw=%4ld errno=%d\n",
           r, e1, e1 ? strerror(e1) : "(成功)", r2, e2);
}

{

    char ok[] = "[3.13] 合法缓冲区，正常写出\n";
    char *unmapped = (char *) 0x1;                     /* 极低地址，必然未映射 */
    char *kernel_ish = (char *) 0xffffffff81000000ULL;  /* 看着像内核地址 */

    /* 只读映射页：先写内容，再把写权限去掉。write(2) 只需要对用户缓冲有**读**权限 */
    void *map = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

代码自测（Q&A）

Q1：为什么「成功不会清零 errno」？会导致什么 bug？ A：因为成功时内核/glibc 不去碰 errno（省一次写）。它保留的是上一次失败留下的旧值。所以 if (errno != 0) 判断成败是错的：本 demo 实测「失败一次（errno=2）再成功一次」之后 errno 仍是 2。正确做法是先看返回值（fd == -1），失败后才读 errno。

Q2：系统调用失败为什么「返回 -1」，而具体原因在 errno？ A：内核实际返回 -errno（如 -2 = -ENOENT，落在 [-4095,-1]，MAX_ERRNO=4095）。glibc 包装判断返回值是否在这个范围：是则 errno = -返回值、返回 -1，否则当合法值返回。所以直接发 syscall 指令拿到的是 -2 而不是 -1。

Q3：errno 是线程安全的吗？能不能跨线程用它传值？ A：它是每线程一份的 TLS 变量（本 demo 实测主线程与子线程的 &errno 地址不同：0x7eae35ea86c8 vs 0x7eae35bff648），所以线程内读写是安全的，但不能用它做线程间通信——别的线程永远看不到你写的值。

Q4：为什么不建议长期保存 strerror() 返回的指针？ A：strerror 返回的是同一块全局静态缓冲的地址。本 demo 实测：strerror(ENOENT) → 0x7ac7f39cb77a，strerror(EACCES) → 0x7ac7f39cb850，第三次 strerror(ENOENT) → 又是 0x7ac7f39cb77a。所以保存指针 = 保存「最后一次」的结果，且多线程下是数据竞争。要留就立刻 strcpy/strdup，或改用 strerror_r。

Q5：perror("open") 打印的是 fd 的错还是 errno 的错？ A：是 errno 的错。perror(msg) 等价于 fprintf(stderr, "%s: %s\n", msg, strerror(errno))，用当前 errno。所以它必须在「失败分支里、紧接着失败调用」使用；中间插了别的调用就可能打出别人的错。

Q6：EFAULT 和 EBADF、EINVAL 分别指向哪类 bug？ A：EFAULT(14) = 指针/地址不合法 → 内存 bug（野指针、悬空指针、越界），先查指针生命周期；EBADF(9) = fd 无效 → fd 管理 bug（未打开、已关闭、写只读 fd）；EINVAL(22) = 参数取值不在允许范围 → 调用方逻辑 bug（flags 组合非法、count 超限）。三者混起来查会走很多弯路。

3. §3.5.1 命令行接口的统一约定

原书所有示例用同一种用法串描述自己的接口，形如：

./prog [-a] [-b value] file...

三条约定：

约定 说明
选项 = - + 单个字符 -a 是开关，-b value 带一个值。这是 POSIX getopt(3) 的语法
[...] 表示可选，裸词表示必需 [-a] 可省，file... 至少给一个
用法错就 usageErr() 并退出 打到 stderr、退出码 EXIT_FAILURE，让 shell 脚本能用 $? 判断

为什么统一用 getopt(3) 而不是自己解析 argv：它把「选项与操作数混排」「-ab 合并写」「-- 结束选项」这些边角都处理好了，且是 POSIX 标准（任何合规 Unix 都有）。

代码示例 A：argc / argv 的真实形状 + getopt 的三种结局

源码：../code/c3_6_cli_args.c

/* TLPI 第 03 章 §3.5.1 —— 命令行选项与参数：argc/argv 的形状 + getopt(3)
 *
 * 原书在 §3.5.1 说明「本书示例程序统一用什么方式解析命令行」，用到的就是
 * getopt(3)。本 demo 把解析逻辑做成函数，然后**喂人工构造的 argv** ——
 * 这样实验可控（CE 上真实 argv 只有 ./output.s），也顺带演示了
 * 「argc/argv 只是一个数组，没有魔法」。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_6 c3_6_cli_args.c
 */
#define _GNU_SOURCE
#include <getopt.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* ---------- ① argv 的形状：最后一个元素必然是 NULL ---------- */

static void show_argv(int argc, char **argv, const char *tag)
{
    printf("  [%s] argc = %d\n", tag, argc);
    for (int i = 0; i < argc; i++) {
        printf("      argv[%d] = \"%s\"\n", i, argv[i]);
    }
    printf("      argv[%d] = %s   ← 标准保证最后一个元素是 NULL\n", argc,
           argv[argc] == NULL ? "NULL" : "(非 NULL，不合法！)");
}

/* ---------- ② getopt(3)：`-a` / `-b val` / `-c` / 非法选项 ---------- */

static void parse(int argc, char **argv, const char *tag)
{
    printf("  [%s] 解析 \"%s\"（getopt 选项串 \"ab:c\"）\n", tag, argc > 1 ? argv[1] : "");
    optind = 1;          /* getopt 的状态是全局的，重入前必须复位 */
    opterr = 0;          /* 关掉 getopt 自己打的错误信息，改由我们统一报 */
    optarg = NULL;

    int ch;
    while ((ch = getopt(argc, argv, "ab:c")) != -1) {
        switch (ch) {
        case 'a':
            printf("      -a 开关，无参数\n");
            break;
        case 'b':
            printf("      -b 带参数，optarg = \"%s\"\n", optarg);
            break;
        case 'c':
            printf("      -c 开关，无参数\n");
            break;
        case '?':
            if (optopt) {
                printf("      非法选项 '-%c'（未知选项）→ 本该 usageErr 并退出\n", optopt);
            } else {
                printf("      '-%s' 缺少必需参数 → 本该 usageErr 并退出\n",
                       argv[optind - 1] ? argv[optind - 1] : "?");
            }
            break;
        default:
            printf("      getopt 返回了意外字符 '%c'\n", ch);
            break;
        }
    }
    printf("      解析结束 optind = %d\n", optind);
    for (int i = optind; i < argc; i++) {
        printf("      非选项参数（操作数）: \"%s\"\n", argv[i]);
    }
    printf("\n");
}

int main(int argc, char **argv)
{
    setvbuf(stdout, NULL, _IONBF, 0);

    printf("=== ① 本次真正的 argv（CE 上只给了程序名）===\n");
    show_argv(argc, argv, "真实 argv");
    printf("\n");

    printf("=== ② 人工构造的 argv：演示 getopt 的三种结局 ===\n");
    char *t1[] = {"prog", "-a", "-b", "42", "-c", "file1", "file2", NULL};
    char *t2[] = {"prog", "-x", NULL};
    char *t3[] = {"prog", "-b", NULL};
    char *t4[] = {"prog", "standalone.txt", NULL};
/* 用 sizeof 算 argc，别手数 —— 手数一次就会错 */
#define ARGC(a) ((int) (sizeof(a) / sizeof((a)[0]) - 1))
    parse(ARGC(t1), t1, "全部正常");
    parse(ARGC(t2), t2, "未知选项 -x");
    parse(ARGC(t3), t3, "缺参数 -b");
    parse(ARGC(t4), t4, "只有操作数");

    printf("=== ③ 为什么 GLIBC 的 getopt 支持 \"--long\"：getopt_long ===\n");
    printf("  POSIX 的 getopt 只认单字符选项；GNU 扩展 getopt_long/getopt_long_only\n");
    printf("  才认 \"--verbose\" 这种长选项（需要 <getopt.h>）\n\n");

    printf("  - 参数错 → usageErr(\"%%s [-a] [-b value] file...\", prog) 打到 stderr 并退出\n");
    printf("  - usageErr 的实现见 c3_8_error_functions.c\n");

段 读数 说明
① argc = 1，argv[0] = "./output.s"，argv[1] = NULL argv 就是一个以 NULL 结尾的字符串数组，没有魔法。CE 只传了程序名，所以只有一个元素。argv[argc] == NULL 是标准保证的哨兵，所以遍历可以写 for (char **p = argv; *p; p++)
② 全部正常 optind = 5，两个操作数 file1 / file2 getopt 每消费一个选项就推进 optind。选项解析完后，argv[optind] 起的全是操作数。注意 GNU 版会把选项重排到前面，所以两端的 file1 file2 被挪到了尾部
② 未知选项 -x 走 '?' 分支，optopt = 'x' getopt 返回 '?' 表示「这一步失败了」，具体是哪种失败看 optopt 或 optarg
② 缺参数 -b 打印的却是「未知选项 '-b'」 ⚠️ 这是 demo 判据不够细的地方，正好当教学点：optstring 写成 "ab:c" 时，「未知选项」和「-b 缺参数」都返回 '?'（只是 optopt 不同）。本 demo 的 if (optopt) 分支把两者混成了一个说法
② 只有操作数 optind = 1，没有 '?' 一个选项都没有时 getopt 立刻返回 -1，optind 停在 1，第一个参数就是操作数
③ getopt_long 才支持 --verbose POSIX 的 getopt 只认单字符选项；长选项是 GNU 扩展，需要 #include <getopt.h>

把「未知选项」和「缺参数」分开的正确做法：optstring 开头加一个冒号 → ":ab:c"。这时「缺参数」返回 ':'（而不是 '?'），「未知选项」仍返回 '?'，两类错误就分开了。这是 getopt(3) man page 里明确写的（man 3 getopt 的「Return value」段）。

另外注意 demo 里那句 optind = 1;——getopt 的解析状态是全局的（optind/optarg/optopt 都是全局变量），所以同一个进程里第二次解析前必须复位，否则会接着上一次的位置继续。

4. §3.5.2 工具 A：get_num —— 把「0」和「出错」分开

原书 get_num.c（Listing 3-6）暴露两个函数，被大量示例用来解析「从命令行拿到的数字」：

int getInt(const char *arg, int flags, const char *name);
long getLong(const char *arg, int flags, const char *name);

flags 是一组位标志，用来加约束：

flag 含义
GN_NONNEG 值必须 ≥ 0
GN_GT_0 值必须 > 0
GN_ANY_BASE / GN_BASE_8 / GN_BASE_16 允许任意基数 / 八进制 / 十六进制
GN_NOFLAG 不加约束

它存在的理由只有一个：atoi(3) 无法把「数字 0」和「解析失败」分开——两者都返回 0，且溢出时静默给一个截断值。原书 man atoi(3) 的一句原文是「The atoi() function ... has undefined behavior if the value cannot be represented」。所以示例程序必须自己造一个三态版本：成功 / 非法 / 溢出。

代码示例 B：复刻 get_num 的判据

/* TLPI 第 03 章 §3.5.2 —— 原书 get_num.c 要解决的问题：把「字符串读数字」
 * 里「0」和「出错」这两件完全不同的事分开。
 *
 * atoi(3) 的致命缺陷（man 原文）："The atoi() function ... has undefined behavior
 * if the value cannot be represented" —— 而且它**完全没有错误返回通道**：
 *   atoi("abc") == 0   也  atoi("0") == 0
 * 你还可能是 ERANGE 溢出，它照样给你一个截断后的值。
 *
 * 原书 lib/get_num.c（Listing 3-6）的做法 = strtol + errno + endptr 三态判定。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_7 c3_7_get_num.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* ---------- 反面教材：atoi 说不清到底发生了什么 ---------- */
static void show_atoi(const char *s)
{
    errno = 0;
    int v = atoi(s);
    printf("  atoi(%-28s) = %-12d errno = %d\n", s, v, errno);
}

/* ---------- 正面写法：原书 get_num.c 的三态判定 ---------- */
enum parse_status { OK, BAD_TOKEN, OVERFLOW, EMPTY };

static enum parse_status get_int(const char *str, int *out)
{
    if (str == NULL || *str == '\0') {
        return EMPTY;
    }
    errno = 0;
    char *endptr = NULL;
    long v = strtol(str, &endptr, 10);

    if (errno != 0) {              /* ① 溢出：strtol 设 ERANGE */
        return OVERFLOW;
    }
    if (endptr == str || *endptr != '\0') {   /* ② 一个数字字符都没吃 / 后面还有垃圾 */
        return BAD_TOKEN;
    }
    if (v < INT_MIN || v > INT_MAX) {         /* ③ long 装得下但 int 装不下 */
        return OVERFLOW;
    }
    *out = (int) v;
    return OK;
}

static const char *status_name(enum parse_status s)
{
    switch (s) {
    case OK:        return "OK";
    case BAD_TOKEN: return "BAD_TOKEN";
    case OVERFLOW:  return "OVERFLOW";
    case EMPTY:     return "EMPTY";
    }
    return "?";
}

int main(void)
{
    printf("=== ① atoi 的问题：0 与出错无法区分 ===\n");
    show_atoi("0");
    show_atoi("abc");
    show_atoi("");
    show_atoi("123abc");                       /* 只吃前缀，后半段被静默丢掉 */
    show_atoi("99999999999999999999");         /* 远超 int 范围 */
    show_atoi("-99999999999999999999");
    printf("  → 前两行的返回值一模一样，都是 0；最后两行的溢出也不报错\n\n");

    printf("=== ② 同一个输入用 strtol + errno + endptr 判 ===\n");
    const char *cases[] = {"0", "abc", "", "123abc", "99999999999999999999",
                           "-99999999999999999999", " 42", "42 ", "+7", "0x1f", "+0", NULL};
    for (int i = 0; cases[i] != NULL; i++) {
        int v = 0;
        enum parse_status st = get_int(cases[i], &v);
        printf("  get_int(%-24s) → %-10s", cases[i], status_name(st));
        if (st == OK) {
            printf(" out = %d", v);
        }
        printf("\n");
    }
    printf("\n");

    printf("=== ③ 朴素解法绕不过去的角落 ===\n");
    printf("  \" 42\"  → strtol 跳过前导空白后成功（返回 42）—— 与 atoi 行为一致\n");
    printf("  \"42 \"  → strtol 会在空格处停，endptr 指向空格 → 判 BAD_TOKEN\n");
    printf("            想接受尾随空白，得自己跳过 endptr 处的 isspace()\n");
    printf("  \"0x1f\" → 基数为 10 时只吃 \"0\"，endptr 指向 'x' → BAD_TOKEN\n");
    printf("            真正的十六进制要用基数 0（自动判别前缀）或 16\n");
    printf("  \"+7\"、\"-0\"、\"007\" 都是合法的，strtol 照收\n\n");

    printf("=== ④ 原书 get_num.c 的返回值语义（复刻其判据）===\n");
    printf("  它返回 int 而不是状态枚举，用「返回 -1 表示出错」的风格，\n");
    printf("  并在函数里直接 errExit(\"strtol\")，所以调用者只需处理「拿到数字」这一种情况。\n");
    printf("  两种风格都行，关键是：**必须有三态**（成功 / 非法 / 溢出），不能只有两态\n");
    return 0;
}

5. §3.5.2 工具 B：error_functions 与 ename.c.inc

原书 error_functions.[hc]（Listing 3-2 / 3-3）提供六个函数，全部往 stderr 打印并结束进程：

函数 打印什么 退出方式
errExit(msg) prog: msg: strerror(errno) exit(EXIT_FAILURE)
err_exit(msg) 同上 _exit()（不 flush stdio、不跑 atexit）
errExitEN(errnum, msg) 用显式给的 errnum 而非当前 errno exit
fatal(msg) prog: msg（不带 errno 描述） exit

cmdLineErr(fmt, ...) Command-line usage error: ... exit

配套的 ename.c.inc（Listing 3-4）是一张 errno → 名字 的静态数组，理由是：某些平台的 strerror() 只覆盖极少数 errno，其余返回 "Unknown error N"；原书要让示例在任何 Unix 上都打印出像样的名字，于是自带一张表。

代码示例 C：把「会自杀的函数」抓回来

难点很直白——这些函数都会把进程结束掉，没法「依次调用看输出」。本 demo 用 fork + 管道把子进程的 stdout/stderr 一起捞回来：

源码：../code/c3_8_error_functions.c

/* TLPI 第 03 章 §3.5.2 —— 原书 lib/error_functions.[hc]（Listing 3-2 / 3-3）
 * 的六个函数各自解决什么，以及它为什么要自带一张 errno 名字表（ename.c.inc）
 *
 * 六个函数的语义差别（照原书）：
 *   errExit(msg)            打印 "prog: msg: strerror(errno)" 到 stderr，exit(EXIT_FAILURE)
 *   err_exit(msg)           同上，但用 _exit()（不 flush stdio、不跑 atexit）
 *   errExitEN(errnum, msg)  用**显式**给定的 errno 号，而不是当前 errno
 *   fatal(msg)              打印 "prog: msg"（**不带** errno），exit
 *   usageErr(fmt, ...)      打印 "Usage: ..." 到 stderr，exit(EXIT_FAILURE)
 *   cmdLineErr(fmt, ...)    打印 "Command-line usage error: ..." 到 stderr，exit
 *
 * 难点：这些函数**都会把进程结束掉**，所以不能「依次调用看输出」。
 * 本 demo 用 fork + 管道把子进程的 stdout/stderr 都抓回来，于是每个函数的真实
 * 输出和真实退出码都能并排打印。
 *
 * 这里还顺带踩了两个真实的坑（都做成了独立段落）：
 *   坑 1  父进程从管道里「只 read 一次就 close」→ 子进程后续的 write 收到
 *         SIGPIPE(13) 直接被杀死，抓回来的输出全是残句。正确姿势是读到 EOF。
 *         demo 的第一版就是这么挂的：七个函数里六个变成「被信号 13 终止」，
 *         只有 fatal 侥幸活下来，整张表失去意义。
 *   坑 2  err_exit 用 _exit()，不 flush stdio → 崩溃路径上写进 stdout 缓冲的
 *         日志会**直接蒸发**。
 *

static void fatal(const char *fmt, ...)
{
    va_list ap;
    fflush(stdout);
    fprintf(stderr, "%s: ", progname);
    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
    fprintf(stderr, "\n");
    exit(EXIT_FAILURE);
}

static void errExit(const char *fmt, ...)
{
    va_list ap;
    int err = errno;                 /* 先存下来：后面 fprintf 自己可能改 errno */
    fflush(stdout);
    fprintf(stderr, "%s: ", progname);
    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
    fprintf(stderr, ": %s\n", strerror(err));
    exit(EXIT_FAILURE);
}

static void errExitEN(int errnum, const char *fmt, ...)
{

    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
    fprintf(stderr, ": %s\n", strerror(errnum));
    exit(EXIT_FAILURE);
}

static void err_exit(const char *fmt, ...)
{

typedef void (*errfn)(void);

static void c_msg_enoent(void) { errno = ENOENT; errExit("open"); }
static void c_msg_eacces(void) { errno = EACCES; errExit("open %s", "/etc/shadow"); }
static void c_en(void)         { errExitEN(ENOSYS, "pthread_style_call"); }
static void c_fatal(void)      { fatal("unexpected state: counter went negative"); }
static void c_usage(void)      { usageErr("%s [-a] [-b value] file...", progname); }
static void c_cmdline(void)    { cmdLineErr("option '-b' requires an argument"); }
static void c_err_exit(void)   { errno = ENOSPC; err_exit("write"); }

/* 这两个用来对比 exit() 与 _exit() 对 stdio 缓冲的不同态度：
 * 都先往 stdout 写一段标记，但子进程的 stdout 已被重定向到**管道** → 全缓冲，
 * 不 flush 就看不到。
 * 注意这里**不能**用 setvbuf 去改缓冲模式：流已经被用过，此时再 setvbuf 是 UB，
 * glibc 直接当没听见。本 demo 的正确做法是反过来 —— 全局**不**给 stdout 设
 * _IONBF（见 main 顶部注释），让它在「非 tty」的默认判定下就是全缓冲。 */
static void c_flush_via_errExit(void)
{
    fputs("MARKER-from-stdout-buffer\n", stdout);
    errno = ENOENT;
    errExit("flush-demo");           /* 里面那句 fflush(stdout) 会把它冲出来 */
}

static void c_flush_via_err_exit(void)
{
    fputs("MARKER-from-stdout-buffer\n", stdout);
    errno = ENOENT;
    err_exit("flush-demo");          /* 没有 fflush，_exit 直接丢缓冲 */
}

/* 子进程里跑 fn（它不会返回），父进程把它的 stdout+stderr 一起捞回来。
 * ⚠️ 关键：必须一直 read 到返回 0（EOF）才能 close —— EOF 意味着子进程
 *    那一端的 fd 已全部关闭。中途 close 会让还在写的子进程收到 SIGPIPE。 */
static void capture(const char *tag, void (*fn)(void))
{
    int fds[2];
    if (pipe(fds) != 0) {
        printf("  [%s] pipe 失败\n", tag);
        return;
    }
    fflush(NULL);                    /* fork 前清缓冲，否则子进程会重复输出一遍 */

    pid_t pid = fork();
    if (pid == 0) {                  /* ---- 子进程 ---- */
        close(fds[0]);
        dup2(fds[1], STDOUT_FILENO);
        dup2(fds[1], STDERR_FILENO);
        close(fds[1]);
        fn();                        /* 这里不会返回 */
        _exit(127);
    }
    /* ---- 父进程 ---- */
    close(fds[1]);
    char buf[512];
    size_t got = 0;
    for (;;) {
        char chunk[256];
        ssize_t n = read(fds[0], chunk, sizeof chunk);
        if (n <= 0) {                /* n == 0 就是 EOF：可以安全关闭了 */
            break;
        }
        size_t room = sizeof buf - 1 - got;
        size_t take = (size_t) n < room ? (size_t) n : room;
        memcpy(buf + got, chunk, take);
        got += take;
    }
    close(fds[0]);
    buf[got] = '\0';
    for (size_t i = 0; i < got; i++) {   /* 多行也排成一条记录，方便并排看 */
        if (buf[i] == '\n') {
            buf[i] = ' ';
        }
    }

    int status = 0;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status)) {
        printf("  %-12s exit(%d)  输出: %s\n", tag, WEXITSTATUS(status), buf);
    } else if (WIFSIGNALED(status)) {
        printf("  %-12s 被信号 %d 终止  输出: %s\n", tag, WTERMSIG(status), buf);
    }
}

/* ---------- 附：读端到底什么时候能关 ---------- */

static void pipe_close_order(void)
{
    printf("=== 附：抓子进程输出时，「管道读端什么时候能关」===\n");
    /* 子进程故意写 25×8192 = 204800 字节，远超管道容量（64 KiB）→ 必然写到阻塞，
     * 于是「提前 close」这一方的错误必定暴露，不依赖时序运气。 */
    for (int mode = 0; mode < 2; mode++) {
        int fds[2];
        if (pipe(fds) != 0) {
            return;
        }
        fflush(NULL);
        pid_t pid = fork();
        if (pid == 0) {
            close(fds[0]);
            dup2(fds[1], STDERR_FILENO);
            close(fds[1]);
            char blk[8192];
            memset(blk, 'x', sizeof blk);
            for (int i = 0; i < 25; i++) {
                if (write(STDERR_FILENO, blk, sizeof blk) < 0) {
                    break;           /* 只有在 SIGPIPE 被忽略时才会走到这里 */
                }
            }
            _exit(1);
        }
        close(fds[1]);
        char blk[8192];
        size_t got = 0;
        if (mode == 0) {
            for (;;) {                       /* 正确：读到 EOF */
                ssize_t n = read(fds[0], blk, sizeof blk);
                if (n <= 0) {
                    break;
                }
                got += (size_t) n;
            }
        } else {
            ssize_t n = read(fds[0], blk, sizeof blk);   /* 错误：只读一次就关 */
            got = n > 0 ? (size_t) n : 0;
        }
        close(fds[0]);
        int status = 0;
        waitpid(pid, &status, 0);
        const char *name = mode == 0 ? "读到 EOF 再关" : "读一次就关";
        if (WIFEXITED(status)) {
            printf("  %-14s → 子进程 exit(%d)，抓到 %zu 字节\n", name, WEXITSTATUS(status), got);
        } else if (WIFSIGNALED(status)) {
            printf("  %-14s → 子进程被信号 %d 终止，只抓到 %zu 字节\n", name,
                   WTERMSIG(status), got);
        }
    }
    printf("    教训：只要读端一关，还在写的子进程立刻收到 SIGPIPE(13)，默认处置是\n"
           "          终止进程 —— 于是你抓回来的是半句话，而且看不出任何报错。\n"
           "          正确姿势：read() 返回 0（EOF）才说明子进程那一端已经关干净，\n"
           "          此时再 close 是安全的。\n"
           "          同一个道理在服务端更致命：对端断开后自己再 write → SIGPIPE\n"
           "          把服务进程写死，所以启动时该 signal(SIGPIPE, SIG_IGN)。\n\n");
}

/* ---------- ename.c.inc 的意义：strerror 覆盖不到时怎么办 ---------- */

static void strerror_coverage(void)
{
    int unknown = 0, total = 0;
    printf("=== 扫 errno 1..200，看 strerror 的覆盖率 ===\n");
    for (int e = 1; e <= 200; e++) {
        const char *s = strerror(e);
        total++;
        if (strncmp(s, "Unknown error", 13) == 0) {
            unknown++;
        } else if (e <= 12 || e == 38 || e == 95 || e == 110 || e == 111) {
            printf("  errno %3d → %s\n", e, s);
        }
    }
    printf("  ...（1..200 中认得 = %d/%d，返回 \"Unknown error\" 的 = %d）\n\n",
           total - unknown, total, unknown);
    printf("  原书为什么要自带 ename.c.inc：\n");
    printf("    1. 有些平台的 strerror() 只覆盖极少数 errno，其余返回 \"Unknown error N\"，\n"
           "       而原书要让示例在任何 UN*X 上都打印出像样的名字，所以自带一张表；\n"
           "    2. 那张表是按 errno 值直接建索引的静态数组，取名字比 strerror 更快\n"
           "       （没有 locale 查询、没有函数调用）—— HFT 的错误日志路径里这点很实际；\n"
           "    3. 它用 #ifdef 把本平台不存在的 errno 整块剪掉，所以同一份表能跨平台编译。\n\n");
}

int main(void)
{
    /* 这里**故意不**调用 setvbuf(stdout, NULL, _IONBF, 0)。
     * 原因有两层：
     *   1. 本容器里 stdout 是 socket，不是 tty → 默认全缓冲，正好用来演示
     *      「缓冲没冲刷就 _exit() 会丢日志」；
     *   2. 每次 fork 之前都会 fflush(NULL)，所以缓冲里不会有残留被复制成两份。
     * 在别处写 demo 时若为了行序好看而设 _IONBF，这个「丢日志」现象就消失了。 */
    strerror_coverage();

    printf("=== 六个函数的真实输出与退出码（各关在一个子进程里）===\n");
    capture("errExit", c_msg_enoent);
    capture("errExit+fmt", c_msg_eacces);
    capture("errExitEN", c_en);
    capture("fatal", c_fatal);
    capture("usageErr", c_usage);
    capture("cmdLineErr", c_cmdline);
    capture("err_exit", c_err_exit);

    printf("\n=== err_exit 的 _exit() 到底少做了什么（同一个标记，两种结局）===\n");
    capture("errExit", c_flush_via_errExit);
    capture("err_exit", c_flush_via_err_exit);
    printf("    ↑ 两行都把 \"MARKER-from-stdout-buffer\" 写进了 stdout 缓冲；\n"
           "      errExit 里有 fflush(stdout) → 标记出现；\n"
           "      err_exit 走 _exit() → 缓冲里的字节随进程一起消失。\n"
           "      实战含义：崩溃路径上想留下最后一句话，就别用 _exit()，\n"
           "      或者自己先 fflush(NULL)。\n\n");

    pipe_close_order();

    printf("=== 读表要点 ===\n");
    printf("  · errExit / err_exit 多打一段 \": 错误描述\"，fatal / usageErr / cmdLineErr 不打\n");
    printf("  · 全部用 EXIT_FAILURE(=1) 退出，不是 0 —— 脚本才能用 $? 判失败\n");
    printf("  · 全部写 **stderr** 而不是 stdout，所以重定向 stdout 也不会丢错误\n");
    printf("  · err_exit 的 _exit() 跳过 atexit 与 stdio flush —— 想「立刻死、别做收尾」时用它，\n"
           "    但代价是缓冲里的日志一起蒸发\n");
    printf("  · errExitEN 的存在理由：pthread_* 这类 API 的失败码是**返回值**，errno 根本没动，\n"
           "    拿 errExit 只会报出一个无关的错误原因\n");
    return 0;
}

逐条解读

读数 说明
errExit / errExit+fmt 打的是 prog: msg: 描述 三个部分用 : 拼：程序名、调用点描述、strerror(errno)。errExit+fmt 那行带上了业务上下文（/etc/shadow 是哪个路径），这正是 perror 给不了的（见 3.4 误用 6）
errExitEN 报的是 Function not implemented 用的是显式传入的 ENOSYS，而不是当前 errno。用途：pthread_* 这类 API 把失败码当返回值返回、根本不碰 errno，拿 errExit 只会报出一个无关的原因
fatal / usageErr / cmdLineErr 都不带 strerror 段 它们描述的不是「系统调用失败」而是「程序自己发现的问题」，errno 没有意义
六个函数（含 err_exit）全部 exit(1) exit(EXIT_FAILURE) = 1，不是 0——否则 shell 脚本的 $? 判不出失败
全部写 stderr 所以 ./prog > out.txt 不会把错误信息也重定向走
MARKER 对照实验 两行都先 fputs("MARKER-from-stdout-buffer\n", stdout)。errExit 里有 fflush(stdout) → 标记出现；err_exit 走 _exit() → 标记消失，缓冲里的字节随进程一起蒸发
读到 EOF 再关 → 抓到 204800 字节 子进程写 25×8192 字节，超过 64 KiB 管道容量，必然写到阻塞
读一次就关 → 子进程被信号 13 终止，只抓到 8192 字节 读端一关，还在写的子进程立刻收到 SIGPIPE(13)，默认处置是终止进程。于是你抓回来的是半句话，而且看不出任何报错

这两个坑都是真实踩出来的（脚本注释里有记录）：demo 第一版「只 read 一次就 close」，结果七个函数里六个变成「被信号 13 终止」，只有 fatal 侥幸活下来，整张表失去意义。正确姿势是一直 read 到返回 0（EOF）——EOF 意味着子进程那一端的 fd 已经全部关干净，此时 close 才安全。

同一个道理在服务端更致命：对端断开后自己再 write → SIGPIPE 把服务进程写死。所以网络服务启动时该 signal(SIGPIPE, SIG_IGN)（详见 3.1 ⑧ 段）。

现象 本节内容的兑现
崩溃路径留不下日志 err_exit 用 _exit() 不 flush stdio——本 demo 的 MARKER 实验直接证明了缓冲里的字节会消失。要保证「最后一句一定写出去」，用 exit() 或自己 fflush(NULL)

代码自测（Q&A）

Q1：原书第 3 章的 6 个 Listing 分别是什么？ A：3-1 = lib/tlpi_hdr.h（公共头文件）；3-2 = lib/error_functions.h；3-3 = lib/error_functions.c；3-4 = lib/ename.c.inc（errno→名字静态表）；3-5 = lib/get_num.h；3-6 = lib/get_num.c。另外 lib/alt_functions.[hc] 与 progconc/syscall_speed.c 没有 Listing 编号。最容易记错的是：3-1 是 tlpi_hdr.h 而不是 error_functions.h，get_num.h 才是 3-5。

Q2：argc / argv 的形状是什么？遍历为什么可以不看 argc？ A：argv 是一个以 NULL 结尾的字符串数组，argv[0] 是程序名，argv[1..argc-1] 是参数，argv[argc] 被标准保证为 NULL。本 demo 实测 argc = 1 时 argv[1] = NULL。因为有这个哨兵，遍历可以写 for (char **p = argv; *p; p++) 而不需要 argc。

Q3：getopt 怎么区分「未知选项」和「选项缺参数」？ A：默认（optstring 不以 : 开头）下它不区分——两者都返回 '?'。本 demo 的实测就暴露了这一点：-b 缺参数时打印的是「非法选项 '-b'（未知选项）」，因为 demo 的 if (optopt) 分支把两者混成了一个说法。正确做法是 optstring 开头加冒号（":ab:c"）：缺参数返回 ':'，未知选项返回 '?'。另外 getopt 的解析状态（optind/optarg/optopt）是全局的，同一进程里第二次解析前必须 optind = 1 复位。

Q4：为什么原书要自己写 get_num.c，不用 atoi？ A：因为 atoi(3) 没有错误返回通道：atoi("0") 和 atoi("abc") 都返回 0，溢出时也只给一个截断值（本 demo 实测 atoi("99999999999999999999") = -1，errno=34，但这个 errno 是它内部转发的 strtol 留下的，atoi 的返回值本身毫无意义）。原书要的三态（成功 / 非法 / 溢出）只有 strtol + errno + endptr 组合才能给。

Q5：strtol 处理 " 42"、"42 "、"0x1f" 分别是什么结果？ A：" 42" → 成功（strtol 跳过前导空白，POSIX 规定）；"42 " → BAD_TOKEN（在空格处停，endptr 指向空格；想接受尾随空白要自己 isspace() 跳过）；"0x1f" → BAD_TOKEN（基数为 10 时只吃 "0"，endptr 指向 'x'；要认十六进制得传基数 0 或 16）。三者都是本 demo 实测。

Q6：err_exit 和 errExit 的区别是什么？ A：唯一的区别是退出方式——errExit 用 exit()，err_exit 用 _exit()。exit() 会 flush stdio 缓冲并跑 atexit 处理器；_exit() 直接让进程消失，缓冲里的日志一起丢掉。本 demo 的 MARKER 实验给出了直接证据：同样先往 stdout 写一段标记，errExit 那行标记出现，err_exit 那行标记消失。崩溃路径上想留下最后一句话，就别用 _exit()。

Q7：为什么 demo 里「抓子进程输出」必须先 read 到 EOF 再 close？ A：因为读端一关，还在写的子进程立刻收到 SIGPIPE(13)，默认处置是终止进程——于是抓回来的是半句话，而且看不出任何报错。本 demo 的附段用「子进程写 204800 字节（超过 64 KiB 管道容量，必然阻塞）」把错误逼出来：读到 EOF 再关能抓满 204800 字节，读一次就关只抓到 8192 字节且子进程被信号 13 杀掉。

1. §3.6.1 功能测试宏：glibc 的「方言开关」

背景事实：glibc 的同一个头文件里同时放着 ISO-C 的、POSIX 的、X/Open 的、GNU 私有的函数声明。默认只暴露最保守的一批。要解锁更多，得在 #include 之前声明「我要用哪个标准」——这就是功能测试宏（Feature Test Macro, FTM）。

宏 取值示例 解锁什么
_POSIX_C_SOURCE 200809L POSIX.1-2008 标准接口
_XOPEN_SOURCE 700 SUSv4（X/Open，POSIX 超集）
_GNU_SOURCE （有定义即可） 全部 + Linux/GNU 扩展（epoll、GNU 版 strerror_r）
_DEFAULT_SOURCE （有定义即可） glibc 默认暴露的杂项 BSD/Linux 函数（memmem 等）
_FILE_OFFSET_BITS 64 把 off_t 换成 64 位（见 §3.6.2）

机制：features.h 把 FTM 翻译成 __USE_*

#include <unistd.h>          （任何 glibc 标准头）
      │  开头 #include <features.h>
      ▼
features.h 读 _GNU_SOURCE / _POSIX_C_SOURCE / _XOPEN_SOURCE / _DEFAULT_SOURCE ...
      │  换算成 __USE_GNU / __USE_POSIX / __USE_XOPEN2K8 / __USE_MISC ... 内部开关
      ▼
各头文件按 __USE_* 决定「这条声明露不露」
   例：string.h:385  #ifdef __USE_MISC → memmem() 才声明

这就是「FTM 必须在所有 #include 之前」的底层原因：<features.h> 只被有效处理一次，先 include 了别的头，开关就已经在「默认方言」下定死了。

现象 说明
default 组：一个 FTM 都没定义，但 _POSIX_C_SOURCE = 200809L、_DEFAULT_SOURCE = 1 glibc 自动补的。features.h:231-239：没有 FTM 且不是 __STRICT_ANSI__ → 自动给 _DEFAULT_SOURCE=1；features.h:285-293：_DEFAULT_SOURCE 下若没指定 _POSIX_C_SOURCE 就补 200809L。所以「什么都不写」不等于「最保守」
xopen700 组：只定义了 _XOPEN_SOURCE=700，却出现了 _POSIX_C_SOURCE = 200809L features.h:295-309 的推断链：_XOPEN_SOURCE >= 700 → 推出 _POSIX_C_SOURCE=200809L。给了 SUS 就自动带上对应的 POSIX
gnu 组：_GNU_SOURCE = 1 换来 _XOPEN_SOURCE = 700 + _DEFAULT_SOURCE = 1 features.h:202-222：_GNU_SOURCE 会改写（不是追加）成 _POSIX_C_SOURCE=200809L、_XOPEN_SOURCE=700、_DEFAULT_SOURCE=1。所以 _GNU_SOURCE 是「上面全部 + __USE_GNU」
memmem 在 posix2008 / xopen700 下不可见，在 default / gnu 下可见 memmem 守的是 __USE_MISC（string.h:385），不是 __USE_GNU。它属于 glibc 默认暴露的 BSD 杂项，所以严格 POSIX 反而把它锁掉了——这是最容易记错的守护条件
strerror_r 在 gnu 下变成 GNU 版签名 同一个函数名，两种 FTM 下签名不同：string.h:428 是 POSIX 版（int strerror_r(int, char*, size_t)），string.h:448 是 GNU 版（char *strerror_r(int, char*, size_t)）。换旗标不只是「能不能用」，还可能改变 ABI
stdc99 组所有 POSIX 声明全部消失 ⚠️ 本节最重要的一条：加旗标不一定只增不减。-std=c99 → __STRICT_ANSI__=1 → glibc 不再自动补 _DEFAULT_SOURCE/_POSIX_C_SOURCE → 连 strdup、clock_gettime、strsignal 这些常用件都跟着消失。这是「-std=c99 编不过」类报错的真正原因
__USE_ISOC11 在 stdc99 下 OFF 它由 __STDC_VERSION__ >= 201112L 触发；-std=c99 下 __STDC_VERSION__ = 199901L，所以 OFF
__USE_FILE_OFFSET64 五组全 OFF 它只受 _FILE_OFFSET_BITS=64 控制（见 §3.6.2），跟上面这些 FTM 无关

__USE_POSIX2008 这个宏不存在——demo 的第一版曾打印它，是凭印象写的虚构名字。实测办法：让编译器自己吐宏表（gcc -dM -E -include features.h - < /dev/null），筛出 __USE_ 前缀，只有 25 个（__USE_ISOC11/ISOC99/ISOC95、__USE_POSIX_IMPLICITLY、__USE_POSIX/POSIX2/POSIX199309/POSIX199506、__USE_XOPEN/XOPEN_EXTENDED/UNIX98/XOPEN2K/XOPEN2K8/XOPEN2K8XSI、__USE_LARGEFILE/LARGEFILE64/FILE_OFFSET64、__USE_MISC/ATFILE/DYNAMIC_STACK_SIZE/GNU/FORTIFY_LEVEL/EXTERN_INLINES）。「POSIX.1-2008」在 glibc 里的真名是 __USE_XOPEN2K8。

2. §3.6.2 系统数据类型：别猜宽度

TLPI 的要点：int/long 的宽度随平台变，但系统调用的接口类型（pid_t/uid_t/off_t/size_t/ssize_t…）是实现定义好的类型。用它们而不是裸 int/long，宽度问题就交给头文件。

类型 用途 定义处（glibc）
pid_t 进程 ID <bits/types.h> → __pid_t
off_t 文件偏移 <bits/types.h> → __off_t
size_t / ssize_t 无符号 / 有符号长度 <stddef.h> / <sys/types.h>
uid_t / gid_t 用户 / 组 ID <bits/types.h>
mode_t 文件权限位 <bits/types.h>
dev_t / ino_t 设备号 / inode 号 <bits/types.h>

最经典的坑是 off_t 与大文件：32 位平台上 off_t 默认 32 位，lseek 处理不了 >2GB 的偏移。解法是定义 _FILE_OFFSET_BITS=64，让 off_t 变 64 位——代价是所有相关函数的 ABI 换一套（glibc 里是 open64/lseek64 一族）。

代码示例 B：两种 _FILE_OFFSET_BITS 设定

源码：../code/c3_10_types.c

/* TLPI 第 03 章 §3.6.2 —— 标准系统数据类型：别猜宽度，用 sizeof 问出来
 *
 * TLPI 专门强调：`int` / `long` 的宽度随平台变，但**系统调用的接口类型**
 * （pid_t、uid_t、off_t、size_t、ssize_t…）是由实现定义好的类型。
 * 想写出可移植的 printf，就必须用 <inttypes.h> 的 PRI* 宏。
 *
 * 本 demo 用两种 OFF_T 设定各编一次，看 off_t 是否变化：
 *   gcc -O0 -Wall -Wextra -o c3_10 c3_10_types.c
 *   gcc -O0 -Wall -Wextra -D_FILE_OFFSET_BITS=64 -o c3_10 c3_10_types.c
 */
#define _GNU_SOURCE
#include <inttypes.h>
#include <stddef.h>
#include <stdio.h>
#include <stdint.h>
#include <sys/types.h>
#include <unistd.h>

/* 用泛型「打印类型宽度」的宏，避免一行行重复 */
#define W(t) printf("  %-22s sizeof = %2zu 字节   %s\n", #t, sizeof(t), kind(sizeof(t)))

static const char *kind(size_t n)
{
    switch (n) {
    case 1: return "1B";
    case 2: return "2B";
    case 4: return "4B";
    case 8: return "8B";
    case 16: return "16B";
    default: return "?";
    }
}

int main(void)
{
    printf("=== ① 基础 C 类型：这就是「数据模型」===\n");
    W(char); W(short); W(int); W(long); W(long long);
    W(float); W(double); W(long double);
    W(void *); W(size_t); W(ptrdiff_t);
    printf("  → 指针 %zu 字节 + long %zu 字节 ⇒ 数据模型 %s\n",
           sizeof(void *), sizeof(long),
           (sizeof(void *) == 8 && sizeof(int) == 4) ? "LP64（x86-64 / aarch64 用户态）" : "其它");

    printf("\n=== ② 系统调用接口类型（POSIX 只规定「够用」，不规定具体宽度）===\n");
    W(pid_t); W(uid_t); W(gid_t); W(mode_t); W(dev_t);
    W(off_t); W(ssize_t); W(time_t);
#ifdef __USE_MISC
    W(socklen_t); W(useconds_t);
#endif

    printf("\n=== ③ _FILE_OFFSET_BITS=64 的作用 ===\n");
#ifdef _FILE_OFFSET_BITS
    printf("  _FILE_OFFSET_BITS = %d\n", _FILE_OFFSET_BITS);
#else
    printf("  _FILE_OFFSET_BITS 未定义\n");
#endif
    printf("  sizeof(off_t) = %zu\n", sizeof(off_t));
    printf("  在 x86-64/aarch64 上 off_t 本来就是 64 位，这个宏**没有影响**；\n");
    printf("  它真正的用武之地是 32 位平台：把 off_t 从 32 位换成 64 位，从而能操作 >2GB 文件。\n");
    printf("  代价是所有相关函数的 ABI 都换一套（glibc 里叫 open64/lseek64）。\n");

    printf("\n=== ④ 为什么必须有 PRI* 宏：同一份代码在不同平台的可移植打印 ===\n");
    int32_t  i32 = -123456;
    uint32_t u32 = 4000000000u;
    int64_t  i64 = -1234567890123456789LL;
    uint64_t u64 = 18446744073709551615ULL;
    size_t   sz  = sizeof(int64_t);
    ssize_t  ssz = -1;
    pid_t    pid = getpid();
    off_t    off = 1 << 20;

    printf("  int32_t  : %" PRId32 "\n", i32);
    printf("  uint32_t : %" PRIu32 "\n", u32);
    printf("  int64_t  : %" PRId64 "\n", i64);
    printf("  uint64_t : %" PRIu64 "\n", u64);
    printf("  size_t   : %zu\n", sz);            /* 用 %zu 而不是 %lu */
    printf("  ssize_t  : %zd\n", ssz);           /* 用 %zd 而不是 %ld */
    printf("  pid_t    : %d（按 %zu 字节的类型打印，编译期由 glibc 保证匹配）\n",
           (int) pid, sizeof(pid_t));
    printf("  off_t    : %jd（转型到 intmax_t 最保险）\n", (intmax_t) off);

    printf("\n=== ⑤ 踩坑清单 ===\n");
    printf("  ✗ printf(\"%%d\", sizeof(x))        → size_t 是 64 位，%%d 只读 32 位，栈错位\n");
    printf("  ✗ printf(\"%%ld\", ssize_t 值)      → 在 Windows/32 位下不对，用 %%zd\n");
    printf("  ✗ 把 pid_t 当 int 传给变参函数     → 用 (int) 显式转，或 %%jd\n");
    printf("  ✗ 假设 long 是 32 位               → LP64 下是 64 位，ILP32 下才是 32 位\n");
    printf("  ✓ 需要「恰好 N 位」时用 <stdint.h> 的 intN_t/uintN_t，别用 int/long\n");
    return 0;
}

段 读数 说明

② pid_t/uid_t/gid_t/mode_t/socklen_t/useconds_t = 4，dev_t/off_t/ssize_t/time_t = 8 POSIX 只规定「够用」，不规定具体宽度——这组数字是 glibc 在 x86-64 上的选择，不是标准保证

④ size_t 用 %zu、ssize_t 用 %zd、定长类型用 PRI*、intmax_t 用 %jd 可移植的打印方式：不要用 %d/%ld 硬套

3. §3.6.3 杂项可移植性

这一节列的坑都有一个共同特征：在 x86 上跑得好好的，交叉编到 ARM 就换了一套结果——静默 bug。

代码示例 C：六类「实现定义」行为一次测完

源码：../code/c3_11_portability.c

/* TLPI 第 03 章 §3.6.3 —— 杂项可移植性：编译器/平台宏、字节序、有符号性、右移
 *
 * 这些「不定行为」是嵌入式/HFT 里最常见的静默 bug 来源：在 x86 上跑得好好的，
 * 交叉编到 ARM 就换了一套结果。全部用编译期宏 + 实测把它钉死。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_11 c3_11_portability.c
 */
#define _GNU_SOURCE
#include <stddef.h>
#include <stdio.h>
#include <stdint.h>
#include <string.h>

/* 一个有「洞」的结构体，用来量对齐填充 */
struct padded {
    char a;
    int  b;
    char c;
};

{
    printf("  %-22s %-4s %s\n", name, on ? "YES" : "NO", note);
}

int main(void)
{
    printf("=== ① 平台/编译器宏（条件编译的判据）===\n");
#if defined(__linux__)
    flag("__linux__", 1, "= Linux 内核 ABI（不是「有 /proc」之类的功能判断）");
#else
    flag("__linux__", 0, "");
#endif
#if defined(__unix__) || defined(__unix)
    flag("__unix__", 1, "= 类 UNIX 系统");
#else
    flag("__unix__", 0, "");
#endif
#if defined(__x86_64__)
    flag("__x86_64__", 1, "64 位 x86");
#else
    flag("__x86_64__", 0, "");
#endif
#if defined(__aarch64__)
    flag("__aarch64__", 1, "64 位 ARM（嵌入式目标常见）");
#else
    flag("__aarch64__", 0, "");
#endif

    flag("__ARM_EABI__", 1, "32 位 ARM EABI");
#else
    flag("__ARM_EABI__", 0, "");
#endif
#if defined(__GNUC__) && !defined(__clang__)
    flag("__GNUC__", 1, "真 GCC（clang 也会定义 __GNUC__！要额外排除 __clang__）");
#else
    flag("__GNUC__", 1, "clang 伪装成的 GCC");
#endif
#if defined(__SIZEOF_POINTER__)
    printf("  __SIZEOF_POINTER__     %zu 字节\n", (size_t) __SIZEOF_POINTER__);
#endif
#if defined(__SIZEOF_LONG__)
    printf("  __SIZEOF_LONG__        %zu 字节\n", (size_t) __SIZEOF_LONG__);
#endif
#if defined(__BYTE_ORDER__)
    printf("  __BYTE_ORDER__         %s\n",
           __BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__ ? "LITTLE_ENDIAN（小端）" :
           __BYTE_ORDER__ == __ORDER_BIG_ENDIAN__ ? "BIG_ENDIAN（大端）" : "PDP/未知");

    printf("  __ORDER_LITTLE_ENDIAN__= %d\n", __ORDER_LITTLE_ENDIAN__);
#endif
#if defined(__FLOAT_WORD_ORDER__)
    printf("  __FLOAT_WORD_ORDER__   %s（浮点的字节序可与整数不同！）\n",
           __FLOAT_WORD_ORDER__ == __ORDER_LITTLE_ENDIAN__ ? "LITTLE_ENDIAN" : "BIG_ENDIAN");
#endif

    printf("\n=== ② 运行期验证字节序（宏之外还得看真实内存布局）===\n");

    unsigned char b[4];

    printf("  uint32_t v = 0x01020304，逐字节 = %02x %02x %02x %02x → %s端\n",

    int neg = -9;

    printf("  -9 >> 1 = %d   （有符号右移是实现定义：算术移位给 -5，逻辑移位给一个正数）\n",

    printf("  a 偏移 %zu, b 偏移 %zu, c 偏移 %zu\n",
           offsetof(struct padded, a), offsetof(struct padded, b),
           offsetof(struct padded, c));
    printf("  ↑ 跨平台传结构体（网络包、共享内存、驱动 ioctl）必须显式定序 + 对齐：\n");
    printf("    用 uint8_t/uint32_t、按大到小排成员、必要时 __attribute__((packed))\n");

段 读数 说明
① __x86_64__ YES / __aarch64__ NO 条件编译的判据是平台宏，不是「有没有某个头」。嵌入式的常见分支就是 #if defined(__aarch64__) \|\| defined(__ARM_EABI__)
① __GNUC__ YES 但 demo 里额外排除了 __clang__ clang 也会定义 __GNUC__（伪装成 GCC 以兼容大量代码）。想精确判断编译器必须同时看 __clang__
① __ORDER_BIG_ENDIAN__ = 4321 / __ORDER_LITTLE_ENDIAN__ = 1234 这两个数是 GCC 约定的「字节序编号」（写成 0x1234/0x4321 好记），不是地址
① __FLOAT_WORD_ORDER__ 单独存在 浮点的字节序可以与整数不同（历史上有混合端平台），所以 GNU 单独给了一个宏
② 0x01020304 逐字节 04 03 02 01 宏之外还要看真实内存布局。网络字节序固定是「大端」，所以小端机上 htonl()/ntohl() 真的会翻字节
③ (char)0xFF → -1 char 的符号性是实现定义的：x86/aarch64 Linux 上默认有符号（-fsigned-char），ARM 某些工具链默认无符号。危害：char c = getchar(); if (c == 0xFF) 在无符号平台永不成立；if (c == EOF) 在有符号平台可能把合法的 0xFF 字节当成 EOF
③ 正确做法 getchar() 的返回值必须装进 int（这样才能区分 EOF）；只当字节用时用 uint8_t / unsigned char
④ -9 / 2 = -4 C99 起规定向零截断，所以是 -4 不是 -5（C89 是实现定义，曾有平台给 -5）
④ -9 % 2 = -1 余数符号跟随被除数
④ -9 >> 1 = -5 有符号右移是实现定义：算术移位给 -5，逻辑移位给一个正数。x86/ARM 都是算术移位，但别依赖它
⑤ struct{char;int;char} sizeof = 12 不是 6：int 要 4 字节对齐 → 中间补 3 字节、尾部补 3 字节。偏移是 0 / 4 / 8（不是 0/1/5）
⑤ 正确做法 跨平台传结构体（网络包、共享内存、驱动 ioctl）必须显式定序 + 对齐：用 uint8_t/uint32_t、成员按「大到小」排可减少填充、必要时 __attribute__((packed))

结构体那条与第 4 本书的 4.13 packed 实践 是同一个知识点，那边有完整的 ioctl/协议头案例，此处不重复展开。

代码自测（Q&A）

Q1：功能测试宏为什么必须放在所有 #include 之前？ A：因为 glibc 的所有标准头文件开头都会 #include <features.h>，它读取 FTM 并一次性换算成 __USE_* 内部开关。如果你先 #include 了别的头，features.h 已经在「默认方言」下把开关定死了，之后再 #define _GNU_SOURCE 也不生效。所以宏必须在最前面，或编译期用 -D 传入。

Q2：_GNU_SOURCE、_POSIX_C_SOURCE、_XOPEN_SOURCE 分别解锁什么？ A：_POSIX_C_SOURCE（如 200809L）解锁 POSIX.1-2008 标准接口；_XOPEN_SOURCE（如 700）解锁 SUSv4（POSIX 超集，含 X/Open 扩展）；_GNU_SOURCE 解锁全部 + Linux/GNU 扩展。实测 _GNU_SOURCE=1 时 glibc 会改写成 _POSIX_C_SOURCE=200809L + _XOPEN_SOURCE=700 + _DEFAULT_SOURCE=1（features.h:202-222），所以它是「上面全部 + __USE_GNU」。代价是用了 GNU 扩展的代码换到非 glibc 环境可能编译不过。

Q3：为什么「一个 FTM 都不定义」不等于「最保守」？ A：因为 glibc 会自动补全。实测 default 组（只给 -O0 -Wall -Wextra）里 _POSIX_C_SOURCE = 200809L、_DEFAULT_SOURCE = 1 都是 glibc 自己给的：features.h:231-239（没有 FTM 且非 __STRICT_ANSI__ → 给 _DEFAULT_SOURCE）、features.h:285-293（_DEFAULT_SOURCE 下补 _POSIX_C_SOURCE=200809L）。同理只给 _XOPEN_SOURCE=700 时，features.h:295-309 的推断链会补上 _POSIX_C_SOURCE=200809L。

Q4：memmem() 的守护开关是 __USE_GNU 吗？ A：不是，是 __USE_MISC（glibc string.h:385）。这导致一个反直觉的实测结果：default 和 gnu 下 memmem 可见，而严格 POSIX 的 -D_POSIX_C_SOURCE=200809L 和 -D_XOPEN_SOURCE=700 反而让它不可见（因为这两组下 __USE_MISC 是 OFF）。查「函数为什么没声明」时必须查它的守护条件是哪个开关。

Q5：为什么 -std=c99 会让一堆 POSIX 函数消失？ A：因为 -std=c99（以及 -std=c11 等）会置上 __STRICT_ANSI__=1，glibc 此时不再自动补 _DEFAULT_SOURCE / _POSIX_C_SOURCE（features.h:231-239 的条件不满足）。结果是所有 __USE_POSIX*/__USE_XOPEN*/__USE_MISC/__USE_ATFILE 全部 OFF，连 strdup、clock_gettime、struct timespec、strsignal 都不可见（本节实测）。加旗标不一定只增不减——这是「-std=c99 编不过」类报错的真正原因。

Q6：off_t 为什么不能写死成 long？_FILE_OFFSET_BITS=64 干嘛的？ A：long 的宽度跟平台走（LP64 是 8 字节、ILP32 是 4 字节），而 off_t 的宽度由 _FILE_OFFSET_BITS 决定。32 位平台上 off_t 默认 32 位，无法处理 >2GB 的文件偏移；定义 _FILE_OFFSET_BITS=64 后变 64 位（代价是 ABI 换成 open64/lseek64 一族）。本 demo 实测：在 x86-64 上这个宏没有影响，sizeof(off_t) 两种设定都是 8——它是给 32 位平台用的。

Q7：__USE_POSIX2008 这个宏存在吗？ A：不存在。demo 的第一版凭印象打印了这个名字，核对 glibc 2.39 的 features.h（以及让编译器用 -dM -E 吐宏表）后确认：features.h 里真实存在 25 个 __USE_*，没有 __USE_POSIX2008。POSIX.1-2008 在 glibc 里的体现是 __USE_XOPEN2K8。教训：写「某个宏/某个行号」之前必须核源码，不能凭印象。

Q8：char 有没有符号？为什么它是「最阴的坑」？ A：char 的符号性是实现定义的：x86/aarch64 Linux 默认有符号（实测 (char)0xFF 转 int = -1），ARM 某些工具链默认无符号。危害有两个方向——char c = getchar(); if (c == 0xFF) 在无符号平台永不成立；而 if (c == EOF) 在有符号平台可能把合法的 0xFF 字节当成 EOF。正确做法：getchar() 的返回值必须装进 int；只当字节用时用 uint8_t / unsigned char。

Q9：struct{char;int;char} 在 x86-64 上是几字节？成员偏移是多少？ A：12 字节，偏移 0 / 4 / 8（不是 6 字节、偏移 0/1/5）。因为 int 需要 4 字节对齐，成员 b 前面要补 3 字节，整个结构体又要按最宽成员对齐，尾部再补 3 字节。跨平台传结构体（网络包、共享内存、驱动 ioctl）必须显式定序 + 对齐。

3. 代码示例：系统调用到底贵多少

原书这个程序（progconc/syscall_speed.c，无 Listing 编号）用 getppid() 与 syscall(SYS_getppid) 各跑 N 次比较耗时。本 demo 在原书基础上加了两条对照——普通函数调用（零点）与纯用户态库函数——把「贵在哪」分离出来。

源码：../code/c3_12_syscall_speed.c

/* TLPI 第 03 章 §3.7（成本全景）—— 系统调用到底贵多少：复刻原书 progconc/syscall_speed.c
 *
 * 本 demo 给 §3.7 小结做量化收束：把「系统调用 / glibc 包装 / 普通函数 / 纯用户态库函数」
 * 四种调用的单次耗时并排量出来，说明「贵的是跨特权级，不是库函数」。
 *
 * 原书这个程序（无 Listing 编号，属「supplementary file」）的做法：
 *   用 getppid() 与 syscall(SYS_getppid) 各跑 N 次，比较耗时，证明
 *   「glibc 包装 + 真正陷入内核」比普通函数调用贵一到两个数量级。
 *
 * 本 demo 在原书基础上加了两条对照：
 *   ③ 普通函数调用（同一进程内，无特权级切换）—— 作为「零点」
 *   ④ 纯用户态库函数调用（strlen 这种也被编译成函数调用）—— 验证「库函数也是零成本」
 *
 * 计时用 CLOCK_MONOTONIC：它只受 NTP 频率微调（adjtime）影响，不会被墙上时钟回拨搞乱。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_12 c3_12_syscall_speed.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

#define ITERS 2000000L

static volatile long sink;    /* 防止优化把整个循环删掉 */

static long nop_call(long x)  /* 普通函数调用：不陷入内核 */
{
    return x + 1;
}

static double now_sec(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double) ts.tv_sec + (double) ts.tv_nsec / 1e9;
}

static void bench(const char *tag, long (*fn)(long), long arg)
{
    double t0 = now_sec();
    long acc = 0;
    for (long i = 0; i < ITERS; i++) {
        acc += fn(arg);
    }
    double dt = now_sec() - t0;
    sink = acc;
    printf("  %-30s %7.1f ms  →  %6.1f ns/次\n", tag, dt * 1e3, dt / (double) ITERS * 1e9);
}

/* ---- 四种被测目标，签名统一成 long(long) 便于复用同一个 bench() ---- */

static long f_nop(long x)                 /* ③ 普通函数调用 */
{
    return nop_call(x);
}

static long f_userlib(long x)             /* ④ 纯用户态库函数（无内联，-O0 下是真调用） */
{
    char buf[16];
    snprintf(buf, sizeof buf, "%ld", x & 1);
    return buf[0];
}

static long f_glibc_wrapper(long x)       /* ① glibc 包装的 getppid() */
{
    (void) x;
    return (long) getppid();
}

static long f_syscall2(long x)            /* ② syscall(2) 通用入口 */
{
    (void) x;
    return (long) syscall(SYS_getppid);
}

int main(void)
{
    setvbuf(stdout, NULL, _IONBF, 0);

    printf("=== 系统调用开销实测（%ld 次，CE 容器 / gcc 13.3 / x86-64）===\n", ITERS);
    printf("  %-30s %7s     %8s\n", "被测对象", "总耗时", "单次");

    bench("① glibc 包装 getppid()", f_glibc_wrapper, 1);
    bench("② syscall(SYS_getppid)", f_syscall2, 1);
    bench("③ 普通函数调用 nop_call()", f_nop, 1);
    bench("④ 纯用户态库函数 snprintf()", f_userlib, 1);

    printf("\n=== 怎么读这张表 ===\n");
    printf("  · ①和②都在「真正陷入内核」那一档；两者的差距 = syscall(2) 自己套的那层壳\n");
    printf("    （存参、查表、把 -errno 翻成 -1+errno），不涉及特权级切换\n");
    printf("  · ③是零点：同一特权级内的 call/ret\n");
    printf("  · ④说明「库函数」本身不贵，贵的是**跨特权级**；atoi/strlen/snprintf 都是用户态\n");
    printf("  · 单次纳秒数是**这台机器**的绝对值，不能当你的机器/你的板的数值；\n");
    printf("    可迁移的结论只有**比值**：系统调用约比普通调用贵一到两个数量级\n");

    printf("\n=== 对 HFT / 嵌入式的直接推论 ===\n");
    printf("  1. 热路径别逐字节 read/write：一次批量调用替代 N 次小调用\n");
    printf("  2. 能用 vDSO 的调用（clock_gettime/gettimeofday/time/getcpu）不陷入内核\n");
    printf("  3. 同机通信优先 AF_UNIX/共享内存，省掉整个网络栈的系统调用序列\n");
    printf("  4. 别用 gettimeofday 之外的「看起来免费」的库函数做高频日志：printf 的代价在\n");
    printf("     格式化（用户态）而不是 write，但它会写很多字节 → 仍要批量化\n");
    return 0;
}

  2. 能用 vDSO 的调用（clock_gettime/gettimeofday/time/getcpu）不陷入内核
  3. 同机通信优先 AF_UNIX/共享内存，省掉整个网络栈的系统调用序列
  4. 别用 gettimeofday 之外的「看起来免费」的库函数做高频日志：printf 的代价在
     格式化（用户态）而不是 write，但它会写很多字节 → 仍要批量化

逐条解读

被测对象 单次耗时 相对于零点(③) 说明
① glibc 包装 getppid() 812.9 ns ≈ 116× 跨特权级：真正陷入内核
② syscall(SYS_getppid) 1275.3 ns ≈ 182× ①的 1.57 倍——差值就是 syscall(2) 自己那层壳（存参、查表、把 -errno 翻成 -1+errno），不涉及特权级切换
③ 普通函数调用 nop_call() 7.0 ns 1×（零点） 同一特权级内的 call/ret
④ 纯用户态库函数 snprintf() 75.2 ns ≈ 11× 比 nop_call 贵一个数量级，但仍然没有一次系统调用——「库函数贵」是格式化本身的开销，不是特权级切换

三个可迁移的结论（绝对值不可迁移，比值可以）：

  1. 系统调用比普通函数调用贵一到两个数量级。①/③ ≈ 116 倍。
  2. syscall(2) 比 glibc 包装还慢——它是「通用入口」，要遍历参数、查表、做错误翻译。所以「用 syscall() 绕开 glibc 更快」是错的直觉；它只在你需要 glibc 没包装的调用时才有价值（见 3.1 ⑥ 段）。
  3. 库函数本身不贵。贵的是跨特权级。④ 组用 snprintf 证明了这一点：同样是「格式化」，fprintf 到文件才会触发 write（见 3.2 实测第 5 段）。

⚠️ 这张表的数字不能当基准用：单次纳秒数是 CE 容器上的绝对值，换机器、换编译器优化级别（本 demo 是 -O0）、换负载都会变。能带走的是比值和机制。要测你自己的机器/板子，得在目标环境重跑。

代码自测（Q&A）

Q1：用一句话串起本章五个概念。 A：系统调用是「用户态进内核的受控入口」（编号 + 寄存器 + 陷阱指令，比普通函数调用贵一到两个数量级），库函数是 glibc 在其上的高层封装（纯用户态函数不进内核）；系统调用失败返回 -1 并设 errno（成功不清零、EINTR 重试）；参数通过寄存器传递且内核必须 copy_from_user 拷贝校验；跨平台靠功能测试宏 + 标准 typedef 保证 API 可见性与类型宽度一致。

Q2：为什么「判断成功失败要看返回值，不能看 errno」？ A：因为成功时内核/glibc 不会清零 errno，它保留的是上一次失败留下的旧值。用 if (errno != 0) 判断成败会误判。正确姿势：fd = open(...); if (fd == -1) { /* 这时才读 errno */ }。

Q3：系统调用失败，用户看到「-1 + errno」，内核实际返回了什么？ A：内核实际返回 -errno（负错误码，如 -ENOENT = -2，落在 [-4095,-1]，MAX_ERRNO=4095）。glibc 包装检测返回值是否在此范围，是则 errno = -返回值 并返回 -1。所以「-1 + errno」是 glibc 翻译的结果——直接 syscall() 拿到的是 -2 而不是 -1。

Q4：EINTR、EAGAIN、EFAULT 三个错误码怎么区分处理？ A：EINTR(=4) 被信号打断 → 重试（while (n == -1 && errno == EINTR)）；EAGAIN(=11) 非阻塞暂时无数据 → 稍后重试或进 epoll；EFAULT(=14) 传给内核的指针非法 → 查内存 bug（野指针/越界），不是 I/O 错误。前两个是「可恢复的暂时状态」，最后一个是「程序 bug」。

Q5：fopen 和 open 的本质区别是什么？ A：fopen 是 ISO-C 标准库函数，返回带用户态缓冲的 FILE*，跨平台（Windows 用 msvcrt 实现）；open 是 POSIX 系统调用包装，返回内核整数 fd，无用户态缓冲，Unix/Linux 限定。fopen 内部最终会调用 open（Linux 上），但多了一层用户态缓冲管理。注意两者不是一一对应：本仓库 3.2 的 0b 段实测了同一个 /dev/null 上 open(O_WRONLY) 成功而 fopen("w") 失败（fopen 隐含 O_CREAT）。

Q6：本节的实测说「系统调用贵 116 倍」，这个数字能直接拿去用吗？ A：不能。它是 CE 容器上 -O0 编译的绝对值（① getppid() 812.9 ns / ③ nop_call() 7.0 ns）。换机器、换优化级别（-O2 下 nop_call 可能被内联成 0 成本）、换负载都会变。可迁移的只有比值与机制：系统调用比普通函数调用贵一到两个数量级；syscall(2) 比 glibc 包装还慢（多一层壳，约 1.57 倍）；库函数本身不贵，贵的是跨特权级。要测自己的板子就在目标环境重跑。

Q7：为什么「用 syscall() 绕开 glibc 更快」是错的直觉？ A：因为 syscall(2) 是一个通用入口：它要存参、查表、把内核返回的 -errno 翻成 -1+errno，这一层壳本身有成本。 本节实测 ② 比 ① 慢约 462 ns/次（1275.3 vs 812.9）。它的真正价值是「glibc 没给你包装的调用也能发」（如 SYS_gettid），不是性能。

原书习题 3-1

Exercise 3-1. When using the Linux-specific reboot() system call to reboot the system, the second argument, magic2, must be specified as one of a set of magic numbers (e.g., LINUX_REBOOT_MAGIC2). What is the significance of these numbers? (Converting them to hexadecimal provides a clue).

题面中文：用 Linux 特有的 reboot() 系统调用重启系统时，第二个参数 magic2 必须取一组魔数之一（如 LINUX_REBOOT_MAGIC2）。这些数字有什么意义？（把它们转成十六进制就有线索了。）

参考解答

reboot() 是没有 glibc 包装的系统调用之一（man 2 reboot 的 NOTES 里明确说了「glibc does not provide a wrapper for this system call」），只能用 syscall(2) 直发。它要求四个参数：

#include <linux/reboot.h>

syscall(SYS_reboot, LINUX_REBOOT_MAGIC1, LINUX_REBOOT_MAGIC2, LINUX_REBOOT_CMD_RESTART, NULL);
/*        ↑ 4 个参数怎么塞进寄存器见 §3.1 */

魔数值来自内核头文件 include/uapi/linux/reboot.h（v6.6）：

#define LINUX_REBOOT_MAGIC1 0xfee1dead
#define LINUX_REBOOT_MAGIC2 672274793
#define LINUX_REBOOT_MAGIC2A    85072278
#define LINUX_REBOOT_MAGIC2B    369367448
#define LINUX_REBOOT_MAGIC2C    537993216

把这四个十进制的 magic2 值转成十六进制（实测）：

常量 十进制 十六进制 含义（ddmmyyyy）
LINUX_REBOOT_MAGIC2 672274793 0x28121969 28/12/1969 — Linus Torvalds 的生日
LINUX_REBOOT_MAGIC2A 85072278 0x05121996 05/12/1996 — 长女 Patricia Miranda
LINUX_REBOOT_MAGIC2B 369367448 0x16041998 16/04/1998 — 次女 Daniela Yolanda
LINUX_REBOOT_MAGIC2C 537993216 0x20112000 20/11/2000 — 三女 Celeste Amanda

LINUX_REBOOT_MAGIC1 则是 0xfee1dead —— leetspeak 的 "feel dead"。

为什么要有魔数：reboot() 是一个能瞬间关掉整台机器、且无法撤销的调用。加两个「必须同时猜对」的魔数（第一个是英文短语、第二个是生日），是为了让「误调用」几乎不可能发生——比如程序把随机内存当作参数传进来，恰好凑齐两组魔数的概率极低。

这道题的真正考点不是背生日，而是两件事： 1. reboot() 没有 glibc 包装，必须用 syscall(2) 直发——这正是 syscall() 存在的理由（3.1 ⑥ 段）。 2. man 2 reboot 已经写了答案（原文："The hexadecimal values of these constants are meaningful."，并列出了四个 hex 值）。系统编程的基本功是「先读 man；man 说不清就去读内核源码」，而不是猜。

顺带一个实用事实：reboot() 需要 CAP_SYS_BOOT。在容器里跑它只会拿到 EPERM——所以这道题是可以安全练习的，不会真把机器关掉。

自编练习 1：错误处理范式（errno + 短写 + EINTR）

写一个 ./copy source dest，用 open/read/write/close 复制文件。要求：

  1. 每一个系统调用都检查返回值，失败用 perror 报告（不要用 if (errno) 判成败）
  2. 处理 EINTR：被信号打断要重试，不是报错退出
  3. 处理 短写：write 可能只写出去一部分，必须循环到写满
  4. 用标准 typedef（ssize_t / mode_t），不写死 int / long
参考答案 
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <sys/types.h>

/* 循环直到写满 n 字节；中间遇到 EINTR 重试 */
static int write_all(int fd, const char *buf, size_t n)
{
    size_t done = 0;
    while (done < n) {
        ssize_t w = write(fd, buf + done, n - done);
        if (w == -1) {
            if (errno == EINTR) continue;   /* 被信号打断 → 重试，不是错误 */
            return -1;
        }
        done += (size_t) w;                 /* w 可能 < 剩余量（短写） */
    }
    return 0;
}

int main(int argc, char *argv[])
{
    if (argc != 3) {
        fprintf(stderr, "Usage: %s source dest\n", argv[0]);
        exit(EXIT_FAILURE);
    }

    int src = open(argv[1], O_RDONLY);
    if (src == -1) { perror("open source"); exit(EXIT_FAILURE); }

    int dst = open(argv[2], O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (dst == -1) { perror("open dest"); exit(EXIT_FAILURE); }

    char buf[4096];
    for (;;) {
        ssize_t n = read(src, buf, sizeof buf);
        if (n == 0) break;                       /* EOF */
        if (n == -1) {
            if (errno == EINTR) continue;
            perror("read");
            exit(EXIT_FAILURE);
        }
        if (write_all(dst, buf, (size_t) n) == -1) { perror("write"); exit(EXIT_FAILURE); }
    }

    if (close(src) == -1) perror("close src");
    if (close(dst) == -1) perror("close dst");
    return 0;
}

要点： - read 返回 0 才是 EOF；返回 -1 必须再看 errno 是不是 EINTR（见 3.4 六条规则）。 - 短写不是错误：write 的契约是「成功时返回已写字节数，可以小于请求」，所以必须循环。POSIX 只保证「对普通文件、且 n 不超过管道/文件系统的实现上限时，要么写满要么失败」——不要依赖这条。 - close 也可能失败（尤其是网络 fd 会把延迟错误暴露在这里），所以它也要检查。

自编练习 2：直接 syscall() 的负错误码

不调用 write()，用 syscall(SYS_write, ...) 写 "raw\n"，并故意传一个无效 fd，观察返回值：

  1. 说明为什么失败时返回值是负错误码而不是 -1
  2. 写一段代码把这个负值还原成 errno
参考答案 
#include <stdio.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <sys/syscall.h>

int main(void)
{
    /* 正常路径 */
    long r = syscall(SYS_write, STDOUT_FILENO, "raw\n", 4);
    printf("syscall 正常返回 = %ld\n", r);

    /* 失败路径：fd = -1 必然 EBADF */
    r = syscall(SYS_write, -1, "x", 1);
    printf("syscall 失败返回 = %ld\n", r);

    /* 自己还原 errno：内核约定 [-4095, -1] 表示错误 */
    if (r < 0 && r >= -4095) {
        int e = (int) -r;
        printf("还原出的 errno = %d (%s)\n", e, strerror(e));
    }
    return 0;
}

要点： - 内核用 -errno 表示失败，区间是 [-4095, -1]（include/linux/err.h:17 的 MAX_ERRNO = 4095）。 - glibc 的包装函数会做错误翻译：落在这个区间就把 errno = -返回值 并返回 -1；否则原样返回。而 syscall(2) 也做了这层翻译（它本身就在 glibc 里），所以你也拿到 -1+errno。 - 想拿到裸负值只有一条路：手写 syscall 指令，绕过 glibc 这一层（3.1 ③ 段实测拿到 ret=-9）。syscall(2) 这个库函数自己带翻译层，调它拿到的仍是 -1+errno。 - 所以上面「自己还原」那段主要是教学用：理解 [-4095,-1] 这个区间与 MAX_ERRNO 的约定，比记住某个 API 的返回值形态更重要。 - 判断成功失败必须先看返回值：r 也可能是 -4095..-1 之外的合法负值（有些调用合法范围就含负值，以各自 man 为准）。

自编练习 3：getopt 的两种失败

原书示例的 c3_6_cli_args.c 有一个判据不够细的地方：optstring = "ab:c" 时，「未知选项 -x」和「-b 缺参数」都返回 '?'，所以 demo 把两者都打成了「未知选项」。

  1. 改 optstring，让两者能被区分
  2. 说明 optind 为什么要复位
参考答案 
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>      /* optind / optarg / optopt */

int main(int argc, char **argv)
{
    optind = 1;          /* getopt 状态是全局的，重入前必须复位 */
    opterr = 0;          /* 关掉 getopt 自己的报错，改由我们统一报 */

    int ch;
    /* ★ 关键：optstring 开头的 ':' —— 缺参数时返回 ':' 而不是 '?' */
    while ((ch = getopt(argc, argv, ":ab:c")) != -1) {
        switch (ch) {
        case 'a': printf("-a\n"); break;
        case 'b': printf("-b %s\n", optarg); break;
        case 'c': printf("-c\n"); break;
        case ':':
            /* 走到这里 = 选项本身合法，但缺必需参数 */
            fprintf(stderr, "选项 -%c 缺少参数\n", optopt);
            return 1;
        case '?':
            /* 走到这里 = 选项本身不认识 */
            fprintf(stderr, "未知选项 -%c\n", optopt);
            return 1;
        }
    }
    for (int i = optind; i < argc; i++)
        printf("操作数: %s\n", argv[i]);
    return 0;
}

要点： - optstring 以 : 开头是 POSIX 定的区分手段：缺参数 → ':'，未知选项 → '?'。两种情况下 optopt 都是那个选项字符。 - getopt 的解析状态（optind / optarg / optopt）是全局变量，解析完停在 optind。同一个进程里第二次解析前必须 optind = 1，否则会接着上次的位置继续跑（本仓库 c3_6_cli_args.c 连解析四次，每次开头都复位）。 - 解析结束后，argv[optind..argc-1] 全是操作数。GNU 版 getopt 会把选项重排到前面（实测 t1 的 optind = 5，两个操作数被挪到尾部）。

自编练习 4：strerror_r 的两种签名取决于哪个宏

下面代码能在 glibc 上编过：

char buf[128];
char *p = strerror_r(ENOENT, buf, sizeof buf);   /* 按 GNU 语义用 */
  1. 说明为什么它能编过——是「glibc 默认就是 GNU 语义」吗？
  2. 严格 POSIX 下应该怎么写？
参考答案

1. 不是默认。 恰恰相反：glibc 默认给的是 POSIX 版（返回 int），只有定义了 _GNU_SOURCE（→ __USE_GNU）才切到 GNU 版（返回 char *）。

所以在上面那段代码前后必须能找到 #define _GNU_SOURCE（放在所有 #include 之前）或编译命令里的 -D_GNU_SOURCE。两道源码坐标：

版本 glibc 头文件位置 原型
POSIX 版 string/string.h:428 int strerror_r(int errnum, char *buf, size_t buflen)
GNU 版 string/string.h:448 char *strerror_r(int errnum, char *buf, size_t buflen)

本仓库 3.6.1 的五组旗标实测正是这个结论：只有 -D_GNU_SOURCE 那一组是 GNU 版，其余四组（含完全不定义 FTM 的默认组）都是 POSIX 版。

2. 严格 POSIX 写法（不定义 _GNU_SOURCE）：

#include <string.h>
#include <errno.h>
#include <stdio.h>

int main(void)
{
    char buf[128];
    int r = strerror_r(ENOENT, buf, sizeof buf);
    if (r != 0) {                   /* 返回 0 表示成功；非 0 时 buf 内容未定义 */
        fprintf(stderr, "strerror_r 本身失败: %d\n", r);
        return 1;
    }
    printf("%s\n", buf);
    return 0;
}

要点： - 「同一个函数名，两种 FTM 下签名不同」不是笔误，是 glibc 的既定设计（XSI 版 vs GNU 版共存）。换旗标不只是「能不能用」，还可能改变 ABI。 - 这也是「可移植性」最典型的坑：代码在 glibc + _GNU_SOURCE 下编得好好的，换到 musl（只有 POSIX 语义）就类型不匹配。要跨 C 库，就按 POSIX 版写。 - strerror 本身还有另一个坑：它返回全局静态缓冲，非线程安全、且每次调用覆写同一块内存（3.4 误用 4/5 实测了同一地址反复出现）。要留错误信息就用 strerror_r 或立刻 strdup。

自编练习 5：-std=c99 为什么让声明消失

某工程把编译命令从 gcc -O2 改成 gcc -O2 -std=c99 之后，strdup()、clock_gettime()、strsignal() 全部报「隐式声明」。

  1. 解释原因（要提到具体宏）
  2. 给出两种修法
参考答案

1. 原因：-std=c99 会置上 __STRICT_ANSI__，此时 glibc 的 <features.h> 不再自动补 _DEFAULT_SOURCE / _POSIX_C_SOURCE（条件在 features.h:231-239）。于是所有 __USE_POSIX* / __USE_XOPEN* / __USE_MISC / __USE_ATFILE 全部 OFF，那些 POSIX/BSD 声明就都不露出来了。

本仓库 3.6.1 的 stdc99 组实测把整条链记下来了：

阶段 值
① 定义了什么 四个 FTM 全未定义；__STRICT_ANSI__ = 1；__STDC_VERSION__ = 199901L
② 内部开关 除 __USE_ISOC99 外全部 OFF（含 __USE_POSIX / __USE_XOPEN2K8 / __USE_MISC）
③ 声明可见性 strdup()、struct timespec/clock_gettime/nanosleep、memmem()、strsignal() 全部不可见

关键认知：加旗标不一定只增不减。 -std=c99 的目的是「更严格的标准符合性」，代价就是关掉方言扩展。

2. 两种修法：

# 修法 A：显式把方言要回来（推荐，可移植性可控）
gcc -O2 -std=c99 -D_POSIX_C_SOURCE=200809L -o prog prog.c

# 修法 B：要 GNU 扩展（Linux 专属跑的话最省心）
gcc -O2 -std=c99 -D_GNU_SOURCE -o prog prog.c

或者写在源码里（必须在所有 #include 之前）：

#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <string.h>
#include <unistd.h>

另外注意：memmem() 守的是 __USE_MISC（string.h:385），不是 __USE_GNU——所以修法 A 仍然编译不过 memmem，用 memmem 就得走修法 B（_GNU_SOURCE）或单独加 -D_DEFAULT_SOURCE。这是 3.6.1 那张可见性表里最容易踩的一格。
