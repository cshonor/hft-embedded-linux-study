章节目标

动机；进程 5 集 + 文件能力；exec 转换；Bounding/Ambient；UID 切换影响；libcap / setcap；capability-aware vs dumb。

易错清单

  1. 能力是线程粒度
  2. 从 Permitted 删掉难自愈
  3. Ambient 不服务 root exec 传递
  4. 需 FS xattr 支持文件能力
  5. Bounding 只减
  6. 新项目：文件能力 > SUID-root

实验清单

  1. setcap/getcap 对比 SUID
  2. libcap 临时 Effective
  3. exec 后 /proc/.../status
  4. （选）Bounding / Ambient

背诵卡

# 要点
1 Effective 才真正授权
2 Permitted = 上限；Bounding = exec 天花板
3 文件能力存在 xattr
4 File Effective 是 1 bit
5 替 SUID-root 用文件能力
6 按需抬 Eff，用完清掉

代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <linux/capability.h>
#include <string.h>

/* Ch39 Linux 能力 (Capabilities) — 细粒度权限替代全 root。
 * 演示 capget/capset 获取和设置能力。
 * 编译: gcc -o ch39_demo ch39_demo.c -lcap
 * 需要安装: apt install libcap-dev */

int main(void) {
    /* 获取当前进程的能力 */
    struct __user_cap_header_struct hdr = {
        .version = _LINUX_CAPABILITY_VERSION_3,
        .pid = 0  /* 0 = 当前进程 */
    };
    struct __user_cap_data_struct data[2];

    if (capget(&hdr, data) < 0) {
        perror("capget (need libcap)");
        return 1;
    }

    /* 打印有效能力集 */
    printf("Effective capabilities: 0x%x 0x%x\n", data[0].effective, data[1].effective);
    printf("Permitted capabilities: 0x%x 0x%x\n", data[0].permitted, data[1].permitted);
    printf("Inheritable capabilities: 0x%x 0x%x\n", data[0].inheritable, data[1].inheritable);

    /* 检查特定能力 */
    if (data[0].effective & (1 << CAP_NET_BIND_SERVICE))
        printf("Has CAP_NET_BIND_SERVICE (can bind < 1024)\n");
    else
        printf("No CAP_NET_BIND_SERVICE\n");

    if (data[0].effective & (1 << CAP_SYS_ADMIN))
        printf("Has CAP_SYS_ADMIN (very powerful)\n");
    else
        printf("No CAP_SYS_ADMIN\n");

    /* 文件能力: getcap/setcap 命令行工具 */
    printf("\nUse 'getcap <binary>' to check file capabilities\n");
    printf("Use 'setcap cap_net_bind_service=ep <binary>' to grant\n");
    return 0;
}

39.2

The Linux Capabilities

本章：TLPI 第 39 章

本节讲什么

Linux capabilities 将传统的 root 全能权限拆分为细粒度的能力单元。程序只需获得所需的特定 capability，而非完整的 root 权限，实现最小权限原则。

要点

传统 root 权限的问题

问题 说明
全能权限 root 可做任何事，无法限制部分能力
二元模型 要么 root（全部权限）要么普通用户（无特权）
安全风险 一个漏洞 = 全系统沦陷
setuid 问题 setuid root 程序拥有全部 root 权限

常用 capabilities

Capability 权限 典型用途
CAP_NET_BIND_SERVICE 绑定 <1024 端口 Web 服务器
CAP_NET_RAW 原始套接字 ping, tcpdump
CAP_SYS_ADMIN 系统管理（最强） mount, hostname
CAP_SYS_TIME 修改系统时间 NTP 守护进程
CAP_SYS_PTRACE 跟踪进程 strace, gdb
CAP_KILL 发送信号 终止其他用户进程
CAP_SETUID 切换 UID su, login
CAP_DAC_OVERRIDE 跳过文件权限 读写任意文件
CAP_CHOWN 修改文件属主 chown
CAP_FOWNER 跳过文件属主限制 忽略文件锁

三组 capability 集合

集合 名称 说明
Effective cap_effective 当前生效的权限，内核检查此集合
Inheritable cap_inheritable exec 时可继承的权限
Permitted cap_permitted 可提升为 effective 的权限上限
Bounding cap_bounding exec 时 inheritable 的上限
Ambient cap_ambient Linux 4.3+，exec 时自动继承

集合交互（exec 时）

execve() 后新 capabilities:
  P' = (P_inheritable & F_inheritable) | (F_permitted & P_bounding) | P_ambient
  E' = (F_effective ? P' : 0) | P_ambient
  • F_* 来自文件的 capabilities（setcap 设置）
  • P_* 来自进程的 capabilities

HFT / 嵌入式关联

  • 交易进程只需 CAP_NET_BIND_SERVICE 绑定特权端口，无需 root
  • 策略进程只需 CAP_IPC_LOCK 锁定内存，不获取其他权限
  • 嵌入式设备用 capabilities 替代 setuid root 程序

代码示例

#include <sys/capability.h>
#include <stdio.h>

int main() {
    cap_t caps = cap_get_proc();
    char *str = cap_to_text(caps, NULL);
    printf("Current caps: %s\n", str);
    cap_free(str);
    cap_free(caps);
    return 0;
}

设置文件 capabilities

# 允许绑定特权端口（无需 root）
sudo setcap cap_net_bind_service=ep ./webserver

# 允许原始套接字
sudo setcap cap_net_raw=ep ./ping

# 允许锁定内存
sudo setcap cap_ipc_lock=ep ./hft_engine

# 查看文件 capabilities
getcap ./webserver

代码自测

capabilities 的三个主要集合（Effective/Inheritable/Permitted）有何关系？
  • Permitted 是权限池：定义进程可能拥有的最大权限范围
  • Effective 是当前生效权限：内核实际检查的集合，是 Permitted 的子集
  • Inheritable 是跨 exec 继承权限：定义 exec 后可保留的权限

程序可通过 cap_set_flag() 在 Permitted 范围内添加/移除 Effective 权限。这是能力提升/放弃的机制。Inheritable 决定 exec 后子进程能保留哪些权限（还需文件配合）。

39.3

进程能力集（**每线程**一份）

本章：TLPI 第 39 章 — Capabilities - 上一节：39.1 动机 - 下一节：39.5 exec 转换（简化）

本节讲什么

setcap 'cap_net_raw+ep' ./ping · getcap · /proc/$$/status 的 Cap*。 ---

要点

集合 作用
Permitted 可拥有的上限；可从中抬到 Effective；删掉难自恢复（除非再 exec 文件能力）
Effective 内核检查用；按需开关
Inheritable fork 继承；参与 exec 算新 Permitted
Bounding exec 能拿到的全局上界；只删不增；容器常用
Ambient（4.3+） 非 root 跨 exec 传能力；root exec 时清空

文件能力（xattr）

项
File Permitted 并入新进程 Permitted（∩ Bounding）
File Inheritable 与进程 Inheritable 与后并入
File Effective 1 bit：1 → 新 Effective=新 Permitted；0 → Effective 空（或 Ambient）

setcap 'cap_net_raw+ep' ./ping · getcap · /proc/$$/status 的 Cap*。

39.4

The Modern Capabilities Implementation

本章：TLPI 第 39 章

本节讲什么

Linux 2.6.24+ 引入了现代 capabilities 实现：VFS 扩展（文件 capabilities）、libcap 库 API、进程和文件 capability 的交互规则。

要点

进程 capability API

#include <sys/capability.h>

/* 获取进程 capabilities */
cap_t cap_get_proc(void);

/* 设置进程 capabilities */
int cap_set_proc(cap_t cap_p);

/* 获取文件 capabilities */
cap_t cap_get_file(const char *fname);

/* 设置文件 capabilities */
int cap_set_file(const char *fname, cap_t cap_p);

/* 文本 ↔ 内部格式转换 */
char *cap_to_text(cap_t caps, ssize_t *length);
cap_t cap_from_text(const char *str);

/* 释放 */
int cap_free(void *ptr);

libcap 操作流程

/* 1. 获取当前 caps */
cap_t caps = cap_get_proc();

/* 2. 修改 flag */
cap_value_t cap_list[] = { CAP_NET_BIND_SERVICE };
cap_set_flag(caps, CAP_EFFECTIVE, 1, cap_list, CAP_SET);
cap_set_flag(caps, CAP_PERMITTED, 1, cap_list, CAP_SET);

/* 3. 应用到进程 */
cap_set_proc(caps);

/* 4. 释放 */
cap_free(caps);

文件 capabilities 格式

# setcap 语法: capability=flags
# flags: e=effective, i=inheritable, p=permitted
setcap cap_net_bind_service=ep ./server
setcap cap_net_raw,cap_net_admin=ep ./tcpdump

securebits 控制

bit 名称 效果
1 SECBIT_NOROOT root 也需 capabilities
2 SECBIT_NOROOT_LOCKED 锁定 NOROOT
4 SECBIT_NO_SETUID_FIXUP setuid 不改变 caps
8 SECBIT_NO_SETUID_FIXUP_LOCKED 锁定

exec 后 capability 规则

文件有 capabilities (setcap):
  P' = (F_inheritable & P_inheritable) | (F_permitted & B)
  E' = F_effective ? P' : ambient_caps
  I' = P_inheritable  (不变)

文件无 capabilities (普通文件):
  若 setuid root:
    P' = B (bounding set)
    E' = P'
    I' = P'
  若普通文件:
    P' = (P_inheritable & ambient) | ambient
    E' = ambient

HFT / 嵌入式关联

  • HFT 引擎用 CAP_NET_BIND_SERVICE 绑定 80/443 端口，非 root 运行
  • 策略沙箱用 CAP_SYS_NICE 设置调度策略，不需要其他权限
  • 嵌入式设备启动脚本用 CAP_SYS_TIME 校准时钟

代码示例

#include <sys/capability.h>
#include <stdio.h>
#include <unistd.h>

/* 丢弃所有不必要的能力 */
int drop_capabilities_except(const cap_value_t *keep, int nkeep) {
    cap_t caps = cap_get_proc();
    if (!caps) return -1;

    /* 清除所有 effective 和 permitted */
    cap_clear_flag(caps, CAP_EFFECTIVE);
    cap_clear_flag(caps, CAP_PERMITTED);

    /* 只保留需要的 */
    if (nkeep > 0) {
        cap_set_flag(caps, CAP_EFFECTIVE, nkeep, keep, CAP_SET);
        cap_set_flag(caps, CAP_PERMITTED, nkeep, keep, CAP_SET);
    }

    int ret = cap_set_proc(caps);
    cap_free(caps);
    return ret;
}

int main() {
    cap_t caps = cap_get_proc();
    char *str = cap_to_text(caps, NULL);
    printf("Before: %s\n", str);
    cap_free(str);
    cap_free(caps);

    /* 只保留 NET_BIND_SERVICE */
    cap_value_t keep[] = { CAP_NET_BIND_SERVICE };
    drop_capabilities_except(keep, 1);

    caps = cap_get_proc();
    str = cap_to_text(caps, NULL);
    printf("After:  %s\n", str);
    cap_free(str);
    cap_free(caps);

    return 0;
}

代码自测

为什么建议在程序启动早期就丢弃不必要的 capabilities？
  1. 减少攻击面：丢弃后即使有漏洞也无法执行需要该能力的操作（如加载内核模块）
  2. 防止 fork/exec 泄漏：子进程继承 capabilities，尽早丢弃防止扩散
  3. 最小权限原则：只保留必要权限，降低漏洞影响范围
  4. 不可逆性：通过 Bounding set 限制后，丢弃的能力无法再获取

int main(void) {
    struct __user_cap_header_struct hdr;
    struct __user_cap_data_struct data[2];

    hdr.version = _LINUX_CAPABILITY_VERSION_3;
    hdr.pid = 0;  /* 0 = current process */

    /* capget: 获取当前能力 */
    if (capget(&hdr, data) < 0) {
        perror("capget");
        return 1;
    }

    printf("Effective: 0x%08x 0x%08x\n", data[0].effective, data[1].effective);
    printf("Permitted: 0x%08x 0x%08x\n", data[0].permitted, data[1].permitted);
    printf("Inheritable: 0x%08x 0x%08x\n", data[0].inheritable, data[1].inheritable);

    /* 检查特定能力 */
    int caps[] = {CAP_NET_BIND_SERVICE, CAP_SYS_ADMIN, CAP_KILL, CAP_SYS_RAWIO};
    const char *names[] = {"NET_BIND_SERVICE", "SYS_ADMIN", "KILL", "SYS_RAWIO"};
    for (int i = 0; i < 4; i++) {
        int idx = caps[i] / 32;
        int bit = caps[i] % 32;
        printf("CAP_%s: %s\n", names[i],
               (data[idx].effective & (1 << bit)) ? "yes" : "no");
    }

    /* 文件能力: 用 setcap 命令行设置 */
    printf("\nFile caps: use 'setcap cap_net_bind_service=ep ./binary'\n");
    return 0;
}

Creating Capabilities-Only Environments

SECBIT_NOROOT

LOCKED 位 防止撤销 NOROOT 模式

  • 嵌入式 systemd 服务配置精确的 capability bounding set
  • 容器化 HFT 组件用 capability 替代 root 权限

代码示例

#include <sys/capability.h>
#include <sys/prctl.h>
#include <unistd.h>
#include <stdio.h>

/* 初始化纯 capability 环境 */
int setup_cap_environment(void) {
    /* 1. 设置 Bounding Set（限制子进程可获取的 caps） */
    cap_value_t allowed[] = {
        CAP_NET_BIND_SERVICE, CAP_IPC_LOCK, CAP_SYS_NICE
    };
    for (int i = 0; i < sizeof(allowed)/sizeof(allowed[0]); i++)
        prctl(PR_CAPBSET_DROP, allowed[i], 0, 0, 0);

    /* 2. 设置允许的 caps 为 effective+permitted */
    cap_t caps = cap_get_proc();
    cap_clear(caps);
    cap_set_flag(caps, CAP_PERMITTED, 3, allowed, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 3, allowed, CAP_SET);
    cap_set_proc(caps);
    cap_free(caps);

    /* 3. 设置 ambient caps（Linux 4.3+） */
    for (int i = 0; i < 3; i++)
        prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_RAISE, allowed[i], 0, 0);

    /* 4. 开启 NOROOT（root 也需 caps） */
    prctl(PR_SET_SECUREBITS, 0x1 | 0x2); /* NOROOT | LOCKED */

    /* 5. 切换到非 root 用户 */
    setgid(1000);
    setuid(1000);

    return 0;
}

Ambient capabilities 和 Inheritable capabilities 有何区别？
  • Inheritable 需要文件 capabilities 配合：exec 时 F_inheritable & P_inheritable 才能继承，必须用 setcap 在目标文件上设置 inheritable flag
  • Ambient 是自动继承的：exec 时直接进入子进程的 Permitted 和 Effective 集合，不需要文件 capabilities 设置，也不需要 setcap

Ambient capabilities 简化了非 root 程序传递特权的流程，尤其适合容器和 systemd 服务。

39.10

Older Kernels and Systems Without File Capabilities

本章：TLPI 第 39 章

本节讲什么

在文件 capabilities 不可用的旧系统上的回退方案：纯进程 capabilities API、prctl(PR_SET_KEEPCAPS)、以及如何在旧内核上安全地使用 setuid 替代。

要点

文件 capabilities 不可用的场景

场景 原因
Linux < 2.6.24 文件 caps 尚未引入
文件系统不支持 xattr 如某些嵌入式文件系统
编译时未启用 内核配置 CONFIG_FILE_CAPS=n
SELinux 限制 策略禁止文件 caps

进程 capabilities API（无需文件 caps）

#include <sys/prctl.h>

/* 保留 caps 跨 exec（旧内核） */
prctl(PR_SET_KEEPCAPS, 1);  /* exec 后保持 permitted caps */
execve("/path/to/app", argv, envp);
/* 子进程中 caps 在 permitted 但不在 effective */

/* 重新提升 effective */
cap_t caps = cap_get_proc();
cap_set_flag(caps, CAP_EFFECTIVE, ...);
cap_set_proc(caps);

PR_SET_KEEPCAPS 模式

1. root 进程设置 KEEPCAPS
2. setuid(non_root) → 丢弃 effective, permitted 变为 0
3. 但 KEEPCAPS 使 permitted 保留
4. exec → 新程序有 permitted caps 但 effective 为空
5. 新程序用 cap_set_proc 提升到 effective

旧内核回退方案对比

方案 内核要求 安全性 用法
文件 caps ≥ 2.6.24 高 setcap cap_x=ep ./app
PR_SET_KEEPCAPS ≥ 2.2.20 中 程序内调用
setuid root 任何 低 chmod u+s ./app
ambient caps ≥ 4.3 高 prctl(PR_CAP_AMBIENT)

旧内核 setuid + KEEPCAPS 模式

/* 以 root 启动的服务，需要切换到非 root 但保留某些 caps */
void drop_root_keep_caps(void) {
    /* 1. 设置 KEEPCAPS */
    prctl(PR_SET_KEEPCAPS, 1);

    /* 2. 切换到非 root UID */
    setgid(1000);
    setuid(1000);

    /* 3. 此时 effective caps 丢失，但 permitted 保留 */
    /* 清除不需要的 caps */
    cap_t caps = cap_get_proc();
    cap_clear_flag(caps, CAP_PERMITTED);  /* 清空 */
    /* 只加回需要的 */
    cap_value_t keep[] = { CAP_NET_BIND_SERVICE };
    cap_set_flag(caps, CAP_PERMITTED, 1, keep, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 1, keep, CAP_SET);
    cap_set_proc(caps);
    cap_free(caps);
}

检测文件 caps 支持

# 检查内核是否支持文件 caps
# /proc/sys/kernel/cap_last_cap 存在则支持
cat /proc/sys/kernel/cap_last_cap

# 检查文件系统是否支持 xattr
# 尝试 setcap，如果失败则不支持
setcap cap_net_bind_service=ep /tmp/test 2>&1
# "Failed to set capabilities on file" = 不支持

HFT / 嵌入式关联

  • 旧版嵌入式内核不支持文件 caps，用 KEEPCAPS 回退
  • 兼容多版本内核：运行时检测 cap_last_cap 决定使用哪种方案
  • 安全审计：优先使用文件 caps，旧内核才考虑 setuid

代码示例

#include <sys/capability.h>
#include <sys/prctl.h>
#include <unistd.h>
#include <stdio.h>
#include <errno.h>

/* 检测并使用文件 caps，否则回退到 KEEPCAPS */
int setup_privileges(void) {
    /* 检测文件 caps 支持 */
    if (prctl(PR_CAPBSET_READ, CAP_NET_BIND_SERVICE) >= 0) {
        /* 现代内核：文件 caps 可用 */
        /* 应通过 setcap 在编译/部署阶段设置 */
        return 0;
    }

    /* 旧内核回退：KEEPCAPS */
    if (getuid() == 0) {
        /* root 启动 */
        prctl(PR_SET_KEEPCAPS, 1);
        setgid(1000);
        setuid(1000);

        /* 恢复需要的 caps */
        cap_t caps = cap_get_proc();
        cap_value_t cap = CAP_NET_BIND_SERVICE;
        cap_set_flag(caps, CAP_EFFECTIVE, 1, &cap, CAP_SET);
        cap_set_flag(caps, CAP_PERMITTED, 1, &cap, CAP_SET);
        if (cap_set_proc(caps) < 0) {
            perror("cap_set_proc");
            return -1;
        }
        cap_free(caps);
    }
    return 0;
}

代码自测

PR_SET_KEEPCAPS 的作用是什么？在什么场景下需要使用？

PR_SET_KEEPCAPS(1) 设置后，当 root 进程调用 setuid() 切换到非 root 用户时，permitted caps 不会被完全清除，而是保留在 permitted set 中（但 effective set 仍被清空）。这允许程序在 setuid 后通过 cap_set_proc() 重新提升某些 capabilities。主要在文件 caps 不可用的旧内核上使用，作为 setuid root 程序保留必要特权的替代方案。现代内核应优先使用文件 capabilities。

什么是 Bounding Set？它的作用是什么？

Bounding Set（边界集）限制了进程（及其后代）能拥有的 capabilities 上限。exec 时新进程的 permitted caps 会被 Bounding Set 过滤。通过 prctl(PR_CAPBSET_DROP, cap) 可以缩小 bounding set，且操作不可逆——一旦丢弃，该 cap 永远无法恢复。这是实现最小权限的重要工具：在程序启动初期丢弃所有不需要的 caps，防止后续代码（即使被攻击者控制）也无法获取这些权限。

练习 2：丢弃不必要的 capabilities

题目：编写 C 代码，在程序启动后丢弃所有 capabilities，只保留 CAP_NET_BIND_SERVICE。同时缩小 Bounding Set。

参考答案 
#include <sys/capability.h>
#include <sys/prctl.h>
#include <linux/capability.h>
#include <stdio.h>

int main() {
    /* 1. 缩小 Bounding Set：丢弃除 NET_BIND_SERVICE 外的所有 caps */
    int last_cap;
    if (prctl(PR_CAPBSET_READ, -1) >= 0)
        last_cap = prctl(PR_CAPBSET_READ, -1);
    else
        last_cap = 40;  /* 默认值 */

    for (int cap = 0; cap <= last_cap; cap++) {
        if (cap != CAP_NET_BIND_SERVICE) {
            if (prctl(PR_CAPBSET_DROP, cap) < 0 && errno != EINVAL) {
                perror("prctl DROP");
            }
        }
    }

    /* 2. 清除进程 caps，只保留 NET_BIND_SERVICE */
    cap_t caps = cap_get_proc();
    cap_clear_flag(caps, CAP_EFFECTIVE);
    cap_clear_flag(caps, CAP_PERMITTED);
    cap_clear_flag(caps, CAP_INHERITABLE);

    cap_value_t keep = CAP_NET_BIND_SERVICE;
    cap_set_flag(caps, CAP_PERMITTED, 1, &keep, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 1, &keep, CAP_SET);

    if (cap_set_proc(caps) < 0) {
        perror("cap_set_proc");
        return 1;
    }
    cap_free(caps);

    /* 3. 验证 */
    caps = cap_get_proc();
    char *str = cap_to_text(caps, NULL);
    printf("Capabilities: %s\n", str);
    cap_free(str);
    cap_free(caps);

    return 0;
}
