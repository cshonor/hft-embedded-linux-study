章节目标

读完本章应能回答：nice 到底改了内核什么（sched_prio_to_weight 查表）；为什么 RT 优先级 1 碾压 nice -20（统一 prio 空间反向映射）；sched_setscheduler 每一步校验与权限判据（user_check_sched_setscheduler）；FIFO/RR 的精确行为差异（task_tick_rt）；满负荷 FIFO 为什么每秒被冻结 50ms（RT throttling 950ms/1s）；绑核与独占核差在哪几层（isolcpus/nohz_full/IRQ）。

易错清单

  1. 把 nice 当优先级——它是 CFS 权重（core.c:11542），无任何抢占承诺；
  2. getpriority() 不清 errno 就判断错误——内核返回 rlimit 风格 1..40，glibc 转换后 -1 是合法值（sys.c:282-287）；
  3. setpriority 传越界值不报错——内核静默钳制（sys.c:232-235），必须读回验证；
  4. 同核放两个同级 FIFO——第二个饿死是设计行为（task_tick_rt:2652）；
  5. 以为 sched_yield() 能给低优先级任务让路——RT 的 yield 只排队尾（rt.c:1590）；
  6. 满负荷压测出现 50ms 周期性延迟尖峰——先查 dmesg | grep "RT throttling"；
  7. 绑核后以为独占——负载均衡照样派活，要 isolcpus + nohz_full + IRQ 绕行；
  8. RT 服务 fork/exec 脚本不带 SCHED_RESET_ON_FORK——脚本继承 FIFO 90 是整机级炸弹（负 nice 同样被重置，core.c:4753-4754）；
  9. nice 降权以为跨终端生效——autogroup（v2.6.38+ 默认开）让 nice 只在会话组内有意义；
  10. sched_getaffinity 读回比设置的小就怀疑 bug——可能是 CPU 热插拔（core.c:8482 交集 active）；
  11. sched_setscheduler(pid, …) 以为改的是"进程"——pid 是 TID 粒度，多线程要逐线程设（setpriority(PRIO_PROCESS,…) 同样是 TID 粒度，sys.c:219）；
  12. 想用 nice 给 SCHED_FIFO 任务"再提一档"——对 RT 无效，内核只写 static_prio 不动调度（core.c:7209-7212）；
  13. 普通用户把进程切 SCHED_IDLE 当"礼貌让路"——单向门：切回按 nice 20 提权审查，RLIMIT_NICE=0 必 EPERM（core.c:7598）；
  14. throttling 实验单次读数就下结论——任务起点与 period 相位的对齐让同程序两次跑差出 10%/14%，看数量级不看个位数。

35.1

进程优先级与 nice 值

源码核验：Linux v6.6 · include/linux/sched/prio.h（MAX_RT_PRIO:16、nice_to_rlimit:32）· kernel/sys.c（set_one_prio:194、getpriority:288）· kernel/sched/core.c（set_user_nice:7187、sched_prio_to_weight:11542）· kernel/sched/autogroup.c（sysctl_sched_autogroup_enabled:7）

本章：TLPI 第 35 章 — 进程优先级与调度 - 上一节：本章首页 - 下一节：35.2 实时调度概述

本节讲什么

  1. nice 值到底改了内核里的什么？——它不是"优先级"，是 CFS 权重表的查表下标；
  2. 为什么非特权进程只能调大 nice（降权）？——内核在哪一行、用哪个 rlimit 做判定；
  3. getpriority() 为什么必须先 errno = 0？——内核侧有一条专门为此写的注释，读完就忘不掉。

一、nice 值的真实身份：CFS 权重，不是优先级

用户视角：nice ∈ [-20, +19]，默认 0，越小越优先。 内核视角：nice 从头到尾不直接参与"谁先跑"的比较——它被换算三次，最后变成 task_struct.se.load.weight（一个正整数权重），CFS 用它分配 CPU 时间比例：

nice 值 (-20 … +19)
   │  NICE_TO_PRIO(nice) = nice + DEFAULT_PRIO(120)      prio.h:26
   ▼
static_prio (100 … 139)      ← 内核统一优先级空间的 CFS 段
   │  USER_PRIO(prio) = prio - MAX_RT_PRIO(100)
   ▼
权重表下标 (0 … 39)
   │  set_load_weight() → sched_prio_to_weight[prio]     core.c:1326
   ▼
se.load.weight (88761 … 15)   ← CFS 真正拿来分蛋糕的数

权重表 sched_prio_to_weight[40]（core.c:11542，摘录）：

nice -20 -10 -5 0 +5 +10 +15 +19
weight 88761 9548 3121 1024 335 110 36 15

core.c:11531-11540 的注释写明了设计意图：每差 1 级 nice，CPU 份额约 -10%；一方 -10%、另一方 +10%，相对差距就是 25%（即权重比 1.25）。所以"nice 差 5"的两任务，CPU 时间比约为 1.25⁵ ≈ 3.05 : 1，而不是线性的 5 : 1。

实测验证（nice_race，WSL2 核 11 单核对撞，两线程各自 setpriority(PRIO_PROCESS, 0, n) 后自旋 4s）： 预写: nice0/nice5 CPU 比 ≈ 1024/335 = 3.057 实测: nice0 = 3.06s, nice5 = 1.01s, 比值 = 3.03 : 1 (偏差 -0.8%) 权重表不是纸面理论——3% 以内的误差说明 CFS 的 vruntime 分蛋糕确实严格按 se.load.weight 比例执行（完整实验见 35.6 实验 4）。同表还有一对倒影 sched_prio_to_wmult[40]（core.c:11560）——预计算的 2³²/x 逆权重，把除法变乘法：权重不变时 CFS 用它加速 vruntime += delta * NICE_0_LOAD / weight 的换算。

⚠️ 关键推论：nice 是比例调节，不是抢占保证。nice -20 的任务与 nice 19 的任务公平分享 CPU（88761 : 15 ≈ 5918 : 1，但仍是"分享"）。任何就绪的实时任务都能瞬间抢占所有 CFS 任务，与 nice 无关——见 35.2。

二、三个 API 与 which 三粒度

#include <sys/resource.h>
int getpriority(int which, id_t who);            /* 读：返回 nice 值 */
int setpriority(int which, id_t who, int prio);  /* 写：prio 就是目标 nice 值 */
#include <unistd.h>
int nice(int inc);                               /* 当前进程：nice += inc */
which 作用对象 who = 0 时
PRIO_PROCESS 单个进程 当前进程
PRIO_PGRP 进程组内所有进程 调用者所在进程组
PRIO_USER 某真实 UID 的所有进程 调用者的 RUID

三个语义细节（全部有内核出处）：

  1. 批量设置：setpriority(PRIO_PGRP/PRIO_USER, …) 对组/用户内每个任务逐一执行（sys.c:253 do_each_pid_thread / :268 for_each_process_thread）——一次调用改一群。
  2. 静默钳制：传入 prio = 50 不报错，内核直接 clamp 到 19（sys.c:232-235 if (niceval > MAX_NICE) niceval = MAX_NICE;）；nice(inc) 同样先 clamp 增量再 clamp 结果（core.c:7285-7288）。返回 0 ≠ 你设的值生效了，读回验证才是可靠做法。
  3. nice() 是相对调整：nice(0) 是查询当前值的惯用法；nice(5) 是在当前值上加 5。

第四个细节（TLPI 未展开，多线程程序必知）：

  1. PRIO_PROCESS 的 pid 参数是 TID 粒度：sys.c:219 对 who == 0 执行 who = task_pid_vnr(current)——取的是调用线程自己的 pid 字段（即 TID），而 find_task_by_vpid(who) 找到的也是单个 task（线程），不是整个线程组。所以多线程进程里 setpriority(PRIO_PROCESS, 0, 10) 只降权当前线程；想给"另一个线程"降权必须传它的 TID，想全进程降权要逐线程设（或干脆在创建前设置让 fork 继承）。这与 sched_setscheduler 的 pid 参数语义一致（35.3）。实测证据：nice_race 实验里两个 worker 各自 setpriority(PRIO_PROCESS, 0, n)，读回各自独立生效（worker0=nice 0、worker1=nice 5 互不干扰）。

三、getpriority() 的三重陷阱（TLPI 经典）

陷阱 1：内核 syscall 返回的根本不是 nice 值

sys.c:282-287 有一条堪称"教科书注释"的原话：

Ugh. To avoid negative return values, "getpriority()" will not return the normal nice-value, but a negated value that has been offset by 20 (ie it returns 40..1 instead of -20..19) to stay compatible.

即：内核 syscall 返回 rlimit 风格值 1..40（= 20 - nice，prio.h:32 nice_to_rlimit），glibc 包装层再转回 nice 值。所以"syscall 返回值"和"库函数返回值"是两个东西——追溯 strace 输出时会看到差 20 的偏移。

陷阱 2：-1 是合法返回值 → errno 惯用法

nice = -1 时 getpriority() 返回 -1，与错误返回值撞车。标准写法：

errno = 0;
int n = getpriority(PRIO_PROCESS, 0);
if (n == -1 && errno != 0)
    perror("getpriority");   /* 真·出错 */

陷阱 3：多目标时返回最高优先级的那个

PRIO_PGRP/PRIO_USER 命中多个任务时，内核取 nice_to_rlimit 最大的那个（sys.c:309 if (niceval > retval) retval = niceval;）——rlimit 值大 = nice 值小 = 优先级最高的任务的 nice。

四、权限：谁能改谁的 nice

判定链（setpriority 路径）：

setpriority(which, who, prio)
   │ sys.c:218
   ▼
set_one_prio()  sys.c:194
   │
   ├─ set_one_prio_perm()  sys.c:178
   │    ├─ 我的 euid == 目标 uid 或 euid？ → 通过
   │    └─ ns_capable(CAP_SYS_NICE)？      → 通过
   │    都不是 ──────────────► -EPERM   （"不是你的进程"）
   │
   └─ niceval < task_nice(p) && !can_nice(p, niceval)？
        can_nice()  core.c:7262 = is_nice_reduction() || capable(CAP_SYS_NICE)
        is_nice_reduction()  core.c:7249：
            nice_to_rlimit(nice) <= task_rlimit(p, RLIMIT_NICE)
        都不满足 ────────────► -EACCES （"是你的进程，但提权被拒"）

EPERM 与 EACCES 的分界（TLPI 强调，内核一一对应）：

errno 含义 触发条件
EPERM 动不了别人的进程 set_one_prio_perm() 失败（非 owner 且无 CAP_SYS_NICE）
EACCES 是自己的进程，但想降低 nice 数值（提权）被拒 can_nice() 失败

RLIMIT_NICE 的换算（prio.h:32）：它的单位不是 nice 值，是 rlimit 风格 1..40。默认 0 → is_nice_reduction() 恒为假 → 非特权进程只能调大 nice。要让普通用户能设到 nice -10，需 RLIMIT_NICE = 20 - (-10) = 30。

五、nice 对实时任务无效 + autogroup 修正

对 FIFO/RR 任务：只写不生效

set_user_nice()（core.c:7187）对 RT/DL 任务的处理是原代码 + 原注释的铁证（core.c:7204-7208）：

The RT priorities are set via sched_setscheduler(), but we still allow the 'normal' nice value to be set - but as expected it won't have any effect on scheduling until the task is SCHED_DEADLINE, SCHED_FIFO or SCHED_RR:

即：给 SCHED_FIFO 任务 setpriority 只是改了 static_prio（:7210）就返回——调度决策完全不看它。

继承与 exec

fork 复制父进程的 static_prio（→ nice 继承）；exec 不改。所以"shell 里 nice -n 10 ./app"是把 shell 的 nice+10 传给 fork 出的子进程。

TLPI 之后的 autogroup（2011, v2.6.38+）

TLPI 出版（2010）时描述的语义是：同一终端里 nice 0 的 A 和 nice 0 的 B 平分 CPU；A nice 10 则按权重 1.25¹⁰ 分。v6.6 默认行为已被 autogroup 修改（autogroup.c:7 sysctl_sched_autogroup_enabled = 1）：

  • 每个会话（setsid，通常 = 每个终端/SSH 登录）自动建一个 task_group；
  • CFS 先在组间公平分配，再在组内按 nice 分——你把 A nice 10，只影响你所在会话组内部，对其它终端里的任务毫无影响；
  • 组级调整入口：写 /proc/<pid>/autogroup（autogroup.c:231 proc_sched_autogroup_set_nice），用的正是同一张权重表（:255-256）；
  • 关闭：启动参数 noautogroup（:227）或 echo 0 > /proc/sys/kernel/sched_autogroup_enabled。

HFT 视角的讽刺：厂商在建议你 nice 降权"后台任务"时，autogroup 可能让这招在跨会话场景下完全失效——这正是要读源码而不是背 man 的理由。

路线 要点
嵌入式 日志/监控等杂务进程调高 nice 降权，保护控制任务。但记住：nice 只是 CFS 内部的比例调节，控制任务真正要确定性仍须 SCHED_FIFO（35.3）
HFT ① nice 给落盘、统计、日志线程降权可用（同进程/同会话内有效）；② 关键路径绝不能靠 nice -20 求"高优先"——它是权重不是抢占；③ 交易机上多终端（多 autogroup）并存时，nice 跨会话不生效，用 cgroup 做资源隔离更可靠

代码示例

/* nice_probe.c — nice 三 API + getpriority 陷阱 + 权限边界实测
 * 普通用户运行演示 EACCES；root 运行演示全通（对照）。
 * 编译: gcc -O2 -Wall -Wextra -o nice_probe nice_probe.c
 */
#include <errno.h>
#include <stdio.h>
#include <sys/resource.h>
#include <unistd.h>

static int get_nice_safe(void)
{
    errno = 0;
    int n = getpriority(PRIO_PROCESS, 0);
    return (n == -1 && errno != 0) ? -999 : n;   /* -999 = 真·出错 */
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);  /* stderr 无缓冲, 行缓冲防输出乱序 */
    /* [1] 两种读法 + errno 惯用法演示 */
    errno = 0;
    int raw = getpriority(PRIO_PROCESS, 0);
    printf("[1] nice(0)=%d  getpriority(raw)=%d errno=%d\n",
           nice(0), raw, errno);

    /* [2] 非特权降权（调大 nice）: 应当成功 */
    if (setpriority(PRIO_PROCESS, 0, 10) == -1)
        perror("[2] setpriority(10)");
    printf("[2] after setpriority(10): nice=%d\n", get_nice_safe());

    /* [3] 回到 5 = 降低 nice 数值 = 提权: 普通用户应 EACCES, root 成功 */
    errno = 0;
    if (setpriority(PRIO_PROCESS, 0, 5) == -1)
        perror("[3] setpriority(5)");
    printf("[3] after setpriority(5): nice=%d\n", get_nice_safe());

    /* [4] 越界值: 内核静默钳制到 19, 不报错 */
    if (setpriority(PRIO_PROCESS, 0, 99) == -1)
        perror("[4] setpriority(99)");
    printf("[4] after setpriority(99): nice=%d (clamped, no error)\n",
           get_nice_safe());

    /* [5] autogroup 归属: TLPI 时代没有的机制 (需内核 CONFIG_SCHED_AUTOGROUP) */
    FILE *f = fopen("/proc/self/autogroup", "r");
    if (f) {
        char buf[128];
        if (fgets(buf, sizeof buf, f))
            printf("[5] /proc/self/autogroup: %s", buf);
        fclose(f);
    } else {
        printf("[5] /proc/self/autogroup: ENOENT"
               " (本内核未开 CONFIG_SCHED_AUTOGROUP)\n");
    }
    return 0;
}

代码自测

1. nice 值在内核里的完整换算链是什么？终点是哪个字段？

nice → NICE_TO_PRIO（+120）→ static_prio(100..139) → USER_PRIO（-100）→ 权重表下标(0..39) → 查 sched_prio_to_weight[40]（core.c:11542）→ task_struct.se.load.weight。CFS 用最终权重分配 CPU 时间比例；nice 从不直接参与"谁先跑"的比较。

2. getpriority() 为什么可能返回 -1 却不算出错？syscall 层返回什么？

nice = -1 是合法值。内核 syscall 返回的是 rlimit 风格 1..40（sys.c:282-287 注释："returns 40..1 instead of -20..19"），glibc 再转回 nice——转换后的 -1 与错误码撞车，所以必须 errno = 0 后调用再检查 errno。

3. setpriority() 返回 EACCES 和 EPERM 分别说明什么？

EPERM：目标进程不是你的（uid/euid 不匹配且无 CAP_SYS_NICE，set_one_prio_perm sys.c:178 拒绝）；EACCES：是你自己的进程，但你试图降低 nice 数值（提权）且 RLIMIT_NICE 不允许、也无 CAP_SYS_NICE（set_one_prio sys.c:203）。

4. 为什么说"给 SCHED_FIFO 任务设 nice"是无效操作？内核怎么处理的？

set_user_nice()（core.c:7209-7212）对 RT/DL 任务只更新 static_prio 后直接返回，注释原话 "it won't have any effect on scheduling"。RT 的优先级只由 sched_setscheduler 的 1..99 决定。

5. TLPI 说"同终端两个 nice 0 任务平分 CPU"，v6.6 上还成立吗？

组内成立，但多会话场景被 autogroup（v2.6.38+，默认开，autogroup.c:7）修正：CFS 先在会话组之间公平，再在组内按 nice 权重分。跨终端的 nice 互相不可见；组级份额用 /proc/<pid>/autogroup 调整。

实时调度概述

源码核验：Linux v6.6 · include/linux/sched/rt.h（RR_TIMESLICE:57、rt_task:16）· include/linux/sched/prio.h（MAX_RT_PRIO:16）· kernel/sched/core.c（__normal_prio:2144）· kernel/sched/rt.c（task_tick_rt:2639、sched_rt_runtime_exceeded:998、sysctl:33-56）· kernel/sched/sched.h（rt_rq:665、for_class_range:2323）

本章：TLPI 第 35 章 — 进程优先级与调度 - 上一节：35.1 进程优先级与 nice 值 - 下一节：35.3 实时调度 API 详解

本节讲什么

  1. "实时优先级 1 压过 nice -20"在内核里是怎么实现的？——答案是一个 0..139 的统一优先级空间和一个反向映射；
  2. SCHED_FIFO 和 SCHED_RR 各自的精确行为——每一条规则都能指到 rt.c 的具体行号；
  3. RT throttling（实时限流）——为什么满负荷 FIFO 任务每秒会被强制冻结 50ms，这在 HFT 生产上意味着什么。

一、为什么需要实时策略：CFS 的盲区

CFS 的目标是公平：所有任务按权重分享 CPU，谁都不特殊。它对"某个任务必须在 50µs 内响应"没有任何承诺——唤醒延迟取决于就绪队列长度、CPU 占用、cache 状态，微秒到毫秒级抖动。

实时策略的目标相反：牺牲公平换确定性。只要 RT 任务就绪，CFS 任务立刻让路；同级 RT 任务之间才谈秩序。两类任务的典型分工（HFT 机器上）：

任务 策略 原因
行情收包→策略→下单关键路径 SCHED_FIFO 需要微秒级确定唤醒
落盘/统计/监控 SCHED_OTHER + nice 降权 吞吐型，可容忍抖动

二、两个世界，一个 prio 空间

内核 task_struct 里有两套"优先级"字段，分工严格：

字段 取值 谁写 用途
rt_priority 用户语义 1..99（越大越优先） __setscheduler_params（core.c:7536 直存用户值） sched_getparam() 读回给用户
prio 内核语义 0..139（越小越优先） 调度核心 每次调度比较的唯一依据

用户 RT 值到内核 prio 的换算在 __normal_prio()（core.c:2144）：

if (rt_policy(policy))
        return MAX_RT_PRIO-1 - rt_prio;      /* 99→0, 50→49, 1→98 */
return NICE_TO_PRIO(nice);                   /* -20→100, 0→120, +19→139 */

内核 prio 空间（唯一比较依据，越小越优先）
  0   1        98 99  100      120      139
  │RT │   RT   │RT│ │  CFS(nice)段  │
  ▼   ▼        ▲  ▲   ▲          ▲        ▲
 用户值 99 … 2  1  0  nice -20   0      +19
      (rt_priority, 越大越优先)  (反向: 100=MAX_RT_PRIO)

  ── 任何就绪 RT (prio ≤ 98) 即刻抢占所有 CFS (prio ≥ 100) ──

为什么反着存？为了让"RT 永远压过 CFS"成为数字比较的自然结果：RT 段 0..98 与 CFS 段 100..139 之间隔着 99（prio == 99 留给 RT 优先级 0 的边界值），p->prio < rq->curr->prio 一条判断通吃两个世界（见 switched_to_rt 的抢占调用，rt.c:2557）。

三、调度类链：先到先得的"阶级"

策略之上还有一层调度类（sched_class），按优先级从高到低排列：

stop_sched_class   (CPU 热插拔/migration 等内核内部线程，用户不可用)
   ▼
dl_sched_class     (SCHED_DEADLINE, EDF)
   ▼
rt_sched_class     (SCHED_FIFO / SCHED_RR)      ← 本章
   ▼
fair_sched_class   (SCHED_OTHER / BATCH / IDLE)
   ▼
idle_sched_class   (无事可做时的空转)

__schedule() 从最高类往下找第一个有可运行任务的类（sched.h:2323 for_class_range(class, __sched_class_highest, __sched_class_lowest)）。高阶级的整体压制低阶级——这就是"两个世界"的机器级实现。

RT 类内部选任务用优先级位图（rt_rq.active 是 rt_prio_array，sched.h:666）：100 个优先级各配一个链表 + 一个 100bit 位图，找最高优先级就绪任务 = 找位图最高置位 bit，O(1)，与任务数无关。pick_task_rt()（rt.c:1802）就是查这张表。

位图搜索的逐行解读（pick_next_rt_entity，rt.c:1769-1785）：

static struct sched_rt_entity *pick_next_rt_entity(struct rt_rq *rt_rq)
{
        struct rt_prio_array *array = &rt_rq->active;
        struct sched_rt_entity *next = NULL;
        struct list_head *queue;
        int idx;

        idx = sched_find_first_bit(array->bitmap);   /* :1776 核心 */
        BUG_ON(idx >= MAX_RT_PRIO);

        queue = array->queue + idx;                   /* :1779 定位链表 */
        if (SCHED_WARN_ON(list_empty(queue)))
                return NULL;
        next = list_entry(queue->next, struct sched_rt_entity, run_list);
        return next;
}
  • array->bitmap：100 个 bit，第 i 个 bit 为 1 表示优先级 i 的链表非空。内核 prio 越小优先级越高，所以"最高置位 bit"就是最高优先级——sched_find_first_bit 在 x86-64 上编译成 rep bsf（TZCNT 类指令），一次内存扫描搞定；
  • array->queue[idx]：该优先级的 FIFO 链表头，取 queue->next 即队首（同优先级内部按入队顺序——这就是 RR requeue 移到队尾的载体）；
  • 外层 _pick_next_task_rt()（rt.c:1787）的 do-while 循环是为了 task_group 分层：先在根 rt_rq 挑出最高优先级的组实体（rt_se），若它是组则下钻进组的 rt_rq 继续挑，直到挑到真实任务。无组调度时循环体只跑一趟。

顺带一提位图结构 rt_prio_array（sched.h:666）的定义：DECLARE_BITMAP(bitmap, MAX_RT_PRIO) + struct list_head queue[MAX_RT_PRIO]——100 个链表头加一个 100bit 位图，共约 1.6KB，per-CPU 每个 rt_rq 一份。优先级数固定、无动态排序，这是 RT 调度 O(1) 的全部秘密（对比 CFS 的红黑树 O(log n)——两种数据结构选择直接反映了"固定优先级"vs"动态 vruntime"的语义差异）。

四、SCHED_FIFO：五条精确规则

每条规则都直接对应 rt.c 源码：

# 规则 内核证据
1 无时间片：同级任务不轮转，先跑的一直跑 task_tick_rt:2652 if (p->policy != SCHED_RR) return; ——tick 直接触发，FIFO 连时间片递减都不做
2 阻塞/让出才交出 CPU（对同级而言） 阻塞 → 出队；sched_yield() → requeue 到同级队尾（yield_task_rt:1590，仅此而已，低优先级任务仍无机会）
3 高优先级就绪，立即抢占 切入 RT 类的瞬间：p->prio < rq->curr->prio → resched_curr(rq)（switched_to_rt，rt.c:2557）；唤醒同理
4 醒来插队：睡醒的 FIFO 任务回到队首参与下一轮选择 enqueue 走 enqueue_task_rt 正常入队；由于规则 3，通常直接抢回 CPU
5 被信号打断不改变优先级，处理完 handler 继续 信号是打断不是降级；与 Ch33 信号模型衔接

推论（TLPI 强调）：两个同优先级 FIFO 任务 + 一个 CPU = 第二个永远饿死（除非第一个阻塞/yield）。设计 FIFO 系统时，同核同优先级只放一个任务。

五、SCHED_RR：FIFO + 100ms 时间片

RR 只在 FIFO 上加一条规则：同优先级任务按时间片轮转。

  • 时间片常量：RR_TIMESLICE = (100 * HZ / 1000)（include/linux/sched/rt.h:57）= 100ms；运行时可通过 /proc/sys/kernel/sched_rr_timeslice_ms 调整（rt.c:49）。
  • 递减机制（task_tick_rt，rt.c:2639）：每个调度 tick --p->rt.time_slice；减到 0 → 重灌 100ms（:2658）→ 仅当同优先级队列里还有别人才 requeue + resched（:2664-2667，rt_se->run_list.prev != rt_se->run_list.next 判定队列非空）。
  • 时间片从不跨优先级：RR 50 与 RR 51 之间只有 51 跑。
  • 用户态查询：sched_rr_get_interval()（core.c:9131）。

注意 100ms 是巨大的时间片——它为"多个中粒度实时任务共存"设计，不是低延迟工具。HFT 里 RR 几乎不用（要么 FIFO 独占核，要么根本不该是 RT 任务）。

六、RT throttling：内核的自我保护

它防什么

一个 bug 的 SCHED_FIFO 任务满核自旋 → 内核线程（包括 ksoftirqd、watchdog）全部饿死 → RCU 超时/soft lockup → 整机挂死。这在 2.6.25 之前是真实威胁（TLPI 35.5 讨论的"过载"问题的现代答案）。

机制（v6.6 全坐标）

每 1 个周期 (sysctl_sched_rt_period = 1000000µs, rt.c:19)
   允许 RT 总共跑 ≤ 950000µs (sysctl_sched_rt_runtime, rt.c:25)

RT 任务运行时: update_curr_rt() 累计 rt_rq->rt_time   rt.c:1045
   │
   ▼  每次调度事件检查
sched_rt_runtime_exceeded()  rt.c:998
   │ rt_time > runtime ?
   ├─ 否 → 继续跑
   └─ 是 → rt_rq->rt_throttled = 1                        :1021
           printk "sched: RT throttling activated\n"       :1022
           sched_rt_rq_dequeue()  ← 整个 RT 队列下架!       :1033
              │
              ▼  CFS 立刻接管该 CPU
周期起点 hrtimer 到期: do_sched_rt_period_timer()  rt.c:901
   → rt_time 清零, 解除 throttled, RT 队列重新上架

关键点：

  1. 节流单位是"每 CPU 的 rt_rq"（sched.h:665，rt_throttled:686/rt_time:687），但配额全局共享（rt_bandwidth，sched.h:278）；
  2. 被节流的是该 CPU 上全部 RT 任务（整队列下架），不是超额的那个；
  3. 默认 950ms/1000ms：每秒最坏冻结 50ms——对"以为自己在跑 FIFO 就有硬保证"的任务，这是一个 50ms 的延迟悬崖；
  4. 三个 sysctl（rt.c:33-56）：kernel/sched_rt_period_us、kernel/sched_rt_runtime_us（设 -1 = 关闭限流，自担风险）、kernel/sched_rr_timeslice_ms。

dmesg 实证（两次独立实测）

throttling 触发时 rt.c:1022 的 printk 会在内核日志里留痕——生产排障的标准指纹：

# 把 runtime 从 950000 改为 100000 后满核 FIFO 2s:
结果: 墙钟 2.14s, 获得 CPU 0.30s (14%)
$ dmesg | grep -i throttling
[  239.912405] sched: RT throttling activated

同一实验两次跑分别得到 CPU 0.20s(10%) 和 0.30s(14%)——配额兑现量在 2×100ms 附近浮动（0.2~0.3s）：任务起点与 period hrtimer 相位的相对位置决定了第一段能跑多长（若起点恰在周期边界后，第一段就能吃满 100ms；若周期边界临近，第一段很短）。这是做 throttling 实验时必须意识到的相位噪声——单次读数不可较真，数量级才可信。

第二道防线：RLIMIT_RTTIME

throttling 之外还有按任务的 watchdog（rt.c:2604）：RT 任务累计 CPU 时间超过 RLIMIT_RTTIME（软限制）会收到 SIGKILL（默认）——防止单任务失控烧配额。

HFT 生产要点：专用核上业务量远低于满核时 throttling 永不触发（rt_time 到不了 950ms）；但压测/回放满负荷场景必须知道 50ms 悬崖的存在——要么调大 runtime、要么把容量规划在 95% 以下。

HFT / 嵌入式关联

路线 要点
嵌入式 电机控制/采集任务用 FIFO 保证"就绪即运行"；多任务分优先级（传感 80 > 控制 70 > 通信 60），同级用 RR；务必给每任务设 RLIMIT_RTTIME 兜底
HFT ① 关键路径 FIFO + 绑核（35.4）+ 每核一个任务（规则 1/4）；② 满核回放会撞 950ms/1s 限流，压测结论要打折或显式调 sched_rt_runtime_us；③ FIFO 99 别乱用——它压过内核线程（ksoftirqd 收包软中断都排后面），网卡 busy-poll 线程通常 80-95 留余量

代码示例

/* rr_interval.c — 查询调度策略与 SCHED_RR 时间片（无需特权即可查询；
 * root 身份下额外演示切换 SCHED_RR 后的读数对照）。
 * 编译: gcc -O2 -Wall -Wextra -o rr_interval rr_interval.c
 */
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static const char *polname(int p)
{
    return p == SCHED_OTHER ? "SCHED_OTHER" :
           p == SCHED_FIFO  ? "SCHED_FIFO"  :
           p == SCHED_RR    ? "SCHED_RR"    : "other";
}

static void dump(const char *tag)
{
    struct timespec ts = {0, 0};
    int pol = sched_getscheduler(0);
    struct sched_param sp = {0};
    sched_getparam(0, &sp);
    if (sched_rr_get_interval(0, &ts) == -1) {
        printf("[%s] policy=%s prio=%d rr_interval: %s\n",
               tag, polname(pol), sp.sched_priority, strerror(errno));
        return;
    }
    printf("[%s] policy=%s prio=%d rr_interval=%ldms\n",
           tag, polname(pol), sp.sched_priority, ts.tv_nsec / 1000000);
}

int main(void)
{

代码自测

1. 用户 RT 优先级 50 对应内核 prio 多少？为什么反向？

MAX_RT_PRIO-1-50 = 49（core.c:2144）。反向存储使内核只需一条 p->prio < q->prio 就能跨两个世界比较：RT 段 0..98 恒小于 CFS 段 100..139，"任何就绪 RT 压过全部 CFS"成为数字上的自然结论。

2. 两个 SCHED_FIFO 同优先级任务绑同一核会发生什么？怎么破？

先跑者独占（task_tick_rt:2652 对 FIFO 直接 return，不轮转），第二个饿死。破法：不同优先级、或改 RR、或各绑各核——工程上首选"每核一个 FIFO 任务"。

3. RT throttling 的默认参数是什么？被节流的到底是谁？

950000µs / 1000000µs（rt.c:25/:19）。被节流的是该 CPU 上整个 RT 队列（sched_rt_runtime_exceeded:1033 整队 dequeue），不是超标的那一个任务——所以一个失控任务会拖累同核所有 RT 任务。

4. SCHED_RR 时间片多大？在哪两个对象之间轮转？

100ms（RR_TIMESLICE，rt.h:57；可经 /proc/sys/kernel/sched_rr_timeslice_ms 调）。只在同优先级 RR 任务间轮转：tick 递减（rt.c:2655），归零后仅当同级队列非空才 requeue+resched（:2664-2667）。

5. HFT 满核回放测试时为什么会出现 50ms 的诡异延迟尖峰？

RT throttling：满核 FIFO 线程 1 秒内累计 rt_time 超过 950ms 后，整队被冻结到下个周期起点（最坏 50ms 窗口，CFS 接管）。压测要么调 sched_rt_runtime_us（-1 关闭，自担风险），要么把负载规划在 95% 以内。

一、API 全家桶

三、权限判据全表（user_check_sched_setscheduler 原文逻辑）

先看原文（core.c:7557-7611，节选关键分支）——它是一串"放行即 return 0，全不满足才 goto req_priv"的检查：

/* Allow unprivileged RT tasks to decrease priority.  :7557 注释 */
static int user_check_sched_setscheduler(struct task_struct *p, ...)
{
        if (fair_policy(policy)) {                     /* :7566 */
                if (attr->sched_nice < task_nice(p) &&
                    !is_nice_reduction(p, attr->sched_nice))
                        goto req_priv;
        }
        if (rt_policy(policy)) {                       /* :7572 */
                unsigned long rlim_rtprio = task_rlimit(p, RLIMIT_RTPRIO);
                if (policy != p->policy && !rlim_rtprio)      /* 切策略 */
                        goto req_priv;
                if (attr->sched_priority > p->rt_priority &&  /* 升优先级 */
                    attr->sched_priority > rlim_rtprio)
                        goto req_priv;
        }
        if (dl_policy(policy))                         /* :7591 DL 一律拒 */
                goto req_priv;
        if (task_has_idle_policy(p) && !idle_policy(policy)) {  /* :7598 */
                if (!is_nice_reduction(p, task_nice(p)))
                        goto req_priv;                 /* IDLE 视作 nice 20 */
        }
        if (!check_same_owner(p))                      /* :7604 别人的任务 */
                goto req_priv;
        if (p->sched_reset_on_fork && !reset_on_fork)  /* :7608 取消 ROF */
                goto req_priv;
        return 0;
req_priv:
        return capable(CAP_SYS_NICE) ? 0 : -EPERM;     /* :7614 兜底 */
}

逐条翻译成表格（满足左侧任一即放行，全部不满足 → 请求 CAP_SYS_NICE，没有则 EPERM）：

想做的事 非特权放行条件 内核行
fair 策略下降低 nice 数值（提权） RLIMIT_NICE 允许（is_nice_reduction） :7566-7570
切入/切换 RT 策略（OTHER→FIFO 等） RLIMIT_RTPRIO != 0 :7576
RT 任务升高 rt_priority 新值 ≤ 当前值，或 ≤ RLIMIT_RTPRIO :7580-7582
RT 任务降低 rt_priority 无条件放行（"Allow unprivileged RT tasks to decrease priority"，:7557 注释） :7572 起
SCHED_IDLE 任务逃离 IDLE RLIMIT_NICE 允许"相当于 nice 20 → 更低"（:7594-7601，内核把 IDLE 视作 nice 20） :7598
改别人的任务 check_same_owner（我的 euid == 对方 uid 或 euid） :7604
取消 sched_reset_on_fork 普通用户不允许（:7607-7609） :7608
任何一条不满足时 capable(CAP_SYS_NICE) → 放行 :7614

要点提炼：

  • RLIMIT_RTPRIO（ulimit -r，单位 = RT 优先级数）为 0 时（默认），非特权用户与 RT 策略完全绝缘——既进不去也升不了；
  • 降级自由是内核的显式设计：RT 任务把自己调低、甚至调回 OTHER，不需要任何特权；
  • SCHED_DEADLINE 目前非特权完全不可设（:7591）。

四、SCHED_RESET_ON_FORK：只管一代的防火墙

语义：带此 flag 设置后，该任务 fork 出的子进程调度属性被重置（core.c:4748-4763）：

if (unlikely(p->sched_reset_on_fork)) {
        if (task_has_dl_policy(p) || task_has_rt_policy(p)) {
                p->policy = SCHED_NORMAL;           /* 回 CFS */
                p->static_prio = NICE_TO_PRIO(0);   /* nice 0 */
                p->rt_priority = 0;
        } else if (PRIO_TO_NICE(p->static_prio) < 0)
                p->static_prio = NICE_TO_PRIO(0);   /* 负 nice 也归零! */
        ...
        p->sched_reset_on_fork = 0;                 /* flag 只管一代 */
}

三个精确细节：

  1. 负 nice 一并重置——RESET_ON_FORK 不只是"防 RT 遗传"，也防 CAP_SYS_NICE 进程的负 nice 遗传（TLPI 35.3 专门提醒）；
  2. flag 本身在子进程清零（:4763）——孙进程继承的是子进程的重置后状态，不需要也不应该累积；
  3. 用户态的写法是 sched_setscheduler(0, SCHED_FIFO | SCHED_RESET_ON_FORK, &sp)（glibc 层 hack，内核 _sched_setscheduler:7850 拆开转成 attr flag；查询得用 sched_getattr）。

隔代实测（rof_grand，root；完整代码见 35.6 实验 6）：

父(设置后) pid=384    policy=SCHED_FIFO+ROF   rt_priority=50
子      pid=385    policy=SCHED_OTHER      rt_priority=0    ← 被重置, ROF 位已清
子进程自行设 FIFO 40 (无ROF): OK
子(重设后) pid=385    policy=SCHED_FIFO       rt_priority=40
孙      pid=386    policy=SCHED_FIFO       rt_priority=40   ← 原样继承!
父(最终) pid=384    policy=SCHED_FIFO+ROF   rt_priority=50  ← 父不受影响

这张四行输出是"flag 只管一代"的完整证据链：父带位 → 子被重置（ROF 位同步清零）；子重设 FIFO 不带位 → 孙原样继承 FIFO 40，不再有重置发生。如果 flag 会遗传，孙进程也该被重置成 OTHER——实测否决。RESET_ON_FORK 是"出生时的一次性产钳"，不是写进基因的遗传病。

为什么需要它：一个 FIFO 99 服务（比如以 root 运行的采集守护）fork/exec 到第三方脚本时，脚本意外继承了 FIFO 99——任何它里面的死循环都是整机级灾难。RESET_ON_FORK 是 fork 边界上的"防遗传手术"。

五、SCHED_BATCH / SCHED_IDLE：CFS 的两个变体

策略 语义 内核依据
SCHED_BATCH "批处理"：交互性补偿关闭（唤醒不奖励），其余同 OTHER。适合纯 CPU 密集任务 fair 类内部行为差异
SCHED_IDLE 极低优先级：权重取 WEIGHT_IDLEPRIO（set_load_weight:1313-1317），比 nice +19 还低一档；逃离它按"从 nice 20 提升"审查（:7598） core.c:1313

注意 SCHED_IDLE ≠ idle 调度类（idle_sched_class 是 CPU 空转，用户不可达）——SCHED_IDLE 任务仍在 fair 类，只是权重被压到最低。

SCHED_IDLE 是普通用户的"单向门"（idle_weight 实测，完整代码见 35.6 实验 5）：

$ ./idle_weight                        # 普通用户, RLIMIT_NICE=0
[单向门] RLIMIT_NICE={soft=0, hard=0}
[1] 切入 SCHED_IDLE (预写: 免特权成功)...
  当前 policy=SCHED_IDLE (euid=1000)          ← 切进去: 免费
[2] 切回 SCHED_OTHER (预写: 非特权 EPERM)...
    切回失败: Operation not permitted (EPERM=1) —— 单向门!

为什么进去免费、出来要特权？两个方向走的检查分支不同： - 切入 IDLE：user_check 的 fair 分支（:7566）只拦"降低 nice 数值"——切 IDLE 不带 nice 变更，一路放行； - 切回 OTHER：命中 :7598 的专门分支 task_has_idle_policy(p) && !idle_policy(policy)——内核把"IDLE → 非 IDLE"等价于"从 nice 20 提升"，需要 is_nice_reduction（即 RLIMIT_NICE ≥ 40，默认 0 必然不够）或 CAP_SYS_NICE。

工程含义：普通用户进程可以主动"自沉"到 SCHED_IDLE 让出 CPU，但沉下去就浮不上来了（除非 exec 一个新映像——exec 不改调度策略，所以其实也浮不上来；唯一出路是重新启动进程）。把它当"礼貌开关"用之前想清楚。

六、sched_yield()：一个 API，三种语义

do_sched_yield()                     core.c:8528

当前策略 yield 的实际效果 内核
SCHED_FIFO / RR 重排到同优先级队列尾部——低优先级任务仍然没机会 yield_task_rt:1590（requeue_task_rt(rq, rq->curr, 0)）

HFT / 嵌入式关联

路线 要点
嵌入式 ① 常驻 RT 服务 fork/exec 外部脚本前，用 RESET_ON_FORK 切断属性遗传（脚本永远不该继承 FIFO 99）；② 多优先级设计（采集 80 > 控制 70 > 通信 60）从 sched_setparam 单独调优先级，不用反复换策略
HFT ① 启动序列：mlockall → 绑核 → FIFO（本节 API）→ 再开始热路径——次序错不了；② 交易二进制以 capability 方式授权（setcap cap_sys_nice）而非裸 root；③ RT 线程降优先级是特权自由（:7557）——优雅降级路径（比如过载时自降到 50）可以无条件实现

代码示例

/* rt_setup.c — sched_setscheduler 全流程: 权限边界 + 即时生效验证
 *              + SCHED_RESET_ON_FORK 隔代重置实测
 * 普通用户运行: 观察 EPERM; root 运行: 全流程成功。
 * 编译: gcc -O2 -Wall -Wextra -o rt_setup rt_setup.c
 */
#define _GNU_SOURCE               /* SCHED_RESET_ON_FORK 需要 __USE_GNU */
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

static const char *polname(int p)
{
    int reset = p & SCHED_RESET_ON_FORK;   /* Linux 2.6.39+: 返回值带此位 */
    p &= ~SCHED_RESET_ON_FORK;
    static char buf[32];
    const char *base =
        p == SCHED_OTHER ? "SCHED_OTHER" :
        p == SCHED_FIFO  ? "SCHED_FIFO"  :
        p == SCHED_RR    ? "SCHED_RR"    : "other";
    snprintf(buf, sizeof buf, "%s%s", base, reset ? "+ROF" : "");
    return buf;
}

static void dump(const char *tag)
{
    struct sched_param sp = {0};
    sched_getparam(0, &sp);
    printf("  %-12s policy=%-14s rt_priority=%d\n",
           tag, polname(sched_getscheduler(0)), sp.sched_priority);
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);  /* fork 前防缓冲复制丢输出 */

    struct rlimit rl;
    getrlimit(RLIMIT_RTPRIO, &rl);
    printf("[0] uid=%d  RLIMIT_RTPRIO={soft=%lu, hard=%lu}\n",
           geteuid(), (unsigned long)rl.rlim_cur,
           (unsigned long)rl.rlim_max);

    /* [1] 切入 SCHED_FIFO 80: 权限判据 user_check:7576 */
    struct sched_param sp = {.sched_priority = 80};
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == -1) {
        printf("[1] sched_setscheduler(FIFO,80): %s (EPERM=%d)\n",
               strerror(errno), errno == EPERM);
        return 0;                        /* 普通用户: 到此为止 */
    }
    printf("[1] sched_setscheduler(FIFO,80): OK\n");
    dump("父进程");

    /* [2] RT 降优先级自由: 80 -> 30, 无需任何特权 (core.c:7557) */
    sp.sched_priority = 30;
    if (sched_setparam(0, &sp) == 0) {
        printf("[2] sched_setparam(80->30): OK (RT 降优先级自由)\n");
        dump("父进程");
    }

    /* [3] RESET_ON_FORK: 子进程属性应被重置回 OTHER/nice0 */
    sp.sched_priority = 60;
    if (sched_setscheduler(0, SCHED_FIFO | SCHED_RESET_ON_FORK, &sp) == -1) {
        perror("[3] setscheduler(RESET_ON_FORK)");
        return 1;
    }
    dump("父进程");

    pid_t pid = fork();
    if (pid == 0) {
        dump("子进程");                   /* 期望: OTHER, 0 */
        fflush(stdout);                  /* _exit 不 flush stdio, 手动刷 */
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    dump("父进程");                       /* 期望: 仍是 FIFO, 60 */
    return 0;
}

代码自测

1. 非特权用户 RLIMIT_RTPRIO=20 时，哪些 RT 操作仍会被拒？

① 从 OTHER 切入 RT：放行（rlim≠0）；② FIFO 10 → FIFO 30：拒（新值 > 当前值且 > rlim，core.c:7580-7582）；③ FIFO 30 → FIFO 15：放行（降优先级无条件自由）；④ 改另一个用户的任务：拒（check_same_owner 失败）。全部条目的最终兜底是 CAP_SYS_NICE。

2. SCHED_RESET_ON_FORK 会重置什么？孙进程呢？

RT/DL 父进程的子进程：policy→SCHED_NORMAL、static_prio→nice 0、rt_priority→0（core.c:4750-4752）；CFS 父进程的负 nice 也会归零（:4753-4754）。flag 在子进程出生时自清（:4763），所以只管一代——孙进程继承的是子进程的重置后状态。

3. FIFO 99 任务调用 sched_yield() 后，同核的 nice 0 任务能跑了吗？

不能。yield_task_rt（rt.c:1590）只是把当前任务重排到同优先级队列尾部，低优先级任务依旧排不上。sched_yield 从不给低优先级任务让路。

4. sched_setparam 和 sched_setscheduler 的区别？

setparam 只改 rt_priority、保留现有策略（内核用 SETPARAM_POLICY=-1 哨兵值表示"不改策略"，core.c:7514/:7521-7522）；setscheduler 策略+优先级一起换。另有细节：RESET_ON_FORK 只能经 setscheduler 的 policy 位设置，且普通用户不能取消已置位的 flag（:7607-7609）；sched_getscheduler() 返回值会带回已置位的 RESET_ON_FORK 位（2.6.39+ 扩展）。

5. 为什么说 sched_setscheduler 返回的瞬间任务可能已经在 CPU 上了？

__sched_setscheduler 末尾 check_class_changed（:7825）→ switched_to_rt（rt.c:2536）：若新 prio < 当前任务 prio，直接 resched_curr（:2557）设置重调度标志——返回用户态的路径上就会发生抢占，新晋 FIFO 任务即刻上核。

一、为什么绑核：三个独立动机

动机 机制 收益对象
cache 局部性 线程留在同核，L1/L2 命中率稳定 所有热路径

二、API 与掩码操作

参数语义（TLPI 强调，容易踩坑）：

  • pid 同样是 TID 粒度（线程级）——多线程要逐线程设；
  • cpusetsize = sizeof(cpu_set_t)，内核只取 min(cpusetsize, cpumask_size())，多余高位要求为 0否则 EINVAL（防误把栈上垃圾当掩码）；
  • 掩码是替换语义：新掩码完全覆盖旧掩码，不是"追加允许的核"。

命令行对照：taskset -c 3 ./app（启动即绑核 3）、taskset -pc 3 <pid>（改运行中进程）；taskset -p <pid> 只读查询。

"搬家"到底怎么发生的——内核在 core.c:2497-2509 有一段罕见的自白注释，值得逐行读：

/*
 * This is how migration works:
 *
 * 1) we invoke migration_cpu_stop() on the target CPU using stop_one_cpu().
 * 2) stopper starts to run (implicitly forcing the migrated thread off the CPU)
 * 3) it checks whether the migrated task is still in the wrong runqueue.
 * 4) if it's in the wrong runqueue then the migration thread removes it
 *    and puts it into the right queue.
 * 5) stopper completes and stop_one_cpu() returns and the migration is done.
 */

翻译成时间线：

核 A (旧)                        核 B (新)
──────                          ──────
目标线程正在运行
    │ stop_one_cpu(A, migration_cpu_stop)
    ▼
migration/XX stopper 线程          [stopper 是 SCHED_CLASS 最顶级的
被投递到核 A                        内核线程——见 35.2 类链图,
    │                              它一就绪, 目标线程必然被挤下]
    ▼
目标线程在上下文切换点下核 ──────► __migrate_task():
    (此刻 cache 还热, 但已       deactivate(旧 rq) → set_task_cpu
     不属于它)                    → activate(新 rq)
    │                              (move_queued_task:2516 实操:
    ▼                               dequeue→改 cpu→enqueue)
stopper 收工,
syscall 返回                      目标线程下次被调度时在核 B 上醒来
                                  (cache 全冷——迁移的物理代价)

三个细节值得抠：

  1. stopper 是最高调度类的内核线程（migration/N，stop_sched_class）——它上核的方式就是"把别人挤下去"，这保证了迁移不需要目标线程配合（它可能正关中断/自旋，根本没法配合）；
  2. move_queued_task()（core.c:2516-2533）的四步 deactivate_task → set_task_cpu → 换 rq 锁 → activate_task 是原子搬队列的最小实现——旧核出队、新核入队，中间不会有两个 rq 同时持有该任务；
  3. __do_set_cpus_allowed()（core.c:2748 起）在改掩码本身时还有一段 dequeue/enqueue 的舞蹈（:2781-2789 put_prev_task → set_cpus_allowed → enqueue_task）——因为任务的调度类钩子 set_cpus_allowed 可能因掩码变化失效（比如 RT 任务被迫换核后的 push/pull 状态）。

与 35.3 的组合：sched_setscheduler 切 FIFO 后 switched_to_rt 只 resched_curr——但跨核的 RT 唤醒还有 push/pull 平衡逻辑（rt.c 的 pushable_tasks，sched.h:681），亲和掩码限制它只能在允许的核里挑。

五、绑核 ≠ 独占：HFT 的完整隔离栈

sched_setaffinity 只管"我只去哪些核"，管不了"别人不许来"。负载均衡器照样把内核线程、其他进程放到你的核上。完整的核隔离是四层叠加（TLPI 时代讲了 isolcpus，v6.6 语义更新如下）：

层 手段 效果
1. 普通负载均衡不走开 isolcpus=<cpulist> 启动参数 指定核从调度域剔除，用户任务默认不上去（要 taskset 显式指定才进）
2. 时钟 tick 不打扰 nohz_full=<cpulist> 核上只有 1 个任务运行时停止周期 tick（每秒数百次的中断消失），需配套 rcu_nocbs 卸载 RCU 回调
3. 网卡中断绕行 irqbalance 停用 + 写 /proc/irq/<n>/smp_affinity 硬中断钉到"杂务核"，业务核零中断
4. 内核线程搬家 rcu_nocbs、per-cpu kthread 亲和（或 cgroup v2 cpuset 分区） ksoftirqd/rcu 等离场

v6.6 现状：isolcpus 仍是主流做法（内核文档 isolcpus 已标注"deprecated in favour of cpuset"，但启动参数依然有效）；新一代方案是 cgroup v2 cpuset 的 partition（cpuset.cpus.partition = root），把一段核从父域独立出去，效果等价且可在线调整。

HFT / 嵌入式关联

路线 要点
嵌入式 采集线程绑核 2 + 中断也钉核 2（同核 cache 热），控制线程绑核 3——单 SoC 上的"软分区"；注意与 RT 策略配合：绑核解决"在哪跑"，FIFO 解决"何时跑"，二者缺一不可
HFT ① 标准拓扑：核 0-1 系统杂务，核 2-3 网卡中断/收包，核 4 起每核一个策略线程（FIFO + taskset 进 isolcpus 核 + nohz_full）；② 绑核后首次访存的 cache 冷启动是预期内的抖动源——热身循环（warm-up）要写进启动序列；③ 验收指标：/proc/interrupts 业务核计数应长期为 0

#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void show(const char *tag)
{
    cpu_set_t set;
    CPU_ZERO(&set);
    if (sched_getaffinity(0, sizeof set, &set) == -1) {
        perror("sched_getaffinity");
        return;
    }
    int last = -1, n = CPU_COUNT(&set);
    for (int i = 0; i < CPU_SETSIZE; i++)
        if (CPU_ISSET(i, &set))
            last = i;
    /* 与 /proc/self/status 交叉验证 */
    char procline[256] = "";
    FILE *f = fopen("/proc/self/status", "r");
    if (f) {
        char line[256];
        while (fgets(line, sizeof line, f))
            if (strncmp(line, "Cpus_allowed_list:", 18) == 0) {
                char *p = line + 18;
                while (*p == ' ' || *p == '\t') p++;
                snprintf(procline, sizeof procline, "%s", p);
                procline[strcspn(procline, "\n")] = 0;
                break;
            }
        fclose(f);
    }
    printf("  %-10s count=%d max=%d /proc: %s\n", tag, n, last, procline);
}

int main(void)
{
    long ncpu = sysconf(_SC_NPROCESSORS_ONLN);
    printf("[0] 在线核数: %ld\n", ncpu);
    show("初始掩码");

    /* [1] 绑到最后一核 */
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(ncpu - 1, &set);
    if (sched_setaffinity(0, sizeof set, &set) == -1)
        perror("[1] setaffinity");
    else
        printf("[1] 绑核 %ld OK\n", ncpu - 1);
    show("绑后");

    /* [2] 空掩码: 与允许集交集为空 → EINVAL (core.c:8332) */
    CPU_ZERO(&set);
    if (sched_setaffinity(0, sizeof set, &set) == -1)
        printf("[2] 空掩码: %s (EINVAL=%d)\n", strerror(errno),
               errno == EINVAL);

    /* [3] 恢复全核, 观察掩码替换语义 (不是追加) */
    CPU_ZERO(&set);
    for (int i = 0; i < ncpu; i++)
        CPU_SET(i, &set);
    if (sched_setaffinity(0, sizeof set, &set) == -1)
        perror("[3] setaffinity");
    else
        printf("[3] 恢复全核 OK (替换语义)\n");
    show("恢复后");
    return 0;
}

1. sched_setaffinity 给的掩码与 cgroup cpuset 允许集无交集时，返回什么？为什么不静默截断？

EINVAL（__sched_setaffinity:8332-8355）。静默截断会让"以为绑到了核 8"的任务实际继承旧掩码或落回别处，对延迟敏感程序是隐形灾难；显式报错把决策权还给调用者。

2. 绑核后线程正在另一核上运行，sched_setaffinity 内核侧如何完成"搬家"？

__set_cpus_allowed_ptr 发现目标不在新掩码内 → 通过 IPI/stop_one_cpu 在目标线程的上下文切换点强制迁移。迁移瞬间 cache 全冷——这是绑核后第一次访存变慢的原因，热身循环应写进启动序列。

3. taskset 绑核后，为什么该核上还会出现别的任务？HFT 怎么补齐？

affinity 只约束"我不去别的核"，不约束"别人不来我的核"——负载均衡仍会往该核派活。补齐：isolcpus（调度域剔除）+ nohz_full（停 tick）+ IRQ affinity 绕行 + rcu_nocbs，或 cgroup v2 cpuset partition。

4. sched_getaffinity 的返回值什么情况下会小于你当初设置的掩码？

CPU 热插拔：内核返回 p->cpus_mask ∩ cpu_active_mask（core.c:8482）——离线核被剔出。所以"读回来 ≠ 设进去"也可能不是 bug 而是拓扑变化。

5. 多线程进程里，主线程 sched_setaffinity(0, …) 影响谁？

只影响主线程自己（pid 参数是 TID 粒度）。要让整个进程收拢到某核，要么在创建每个线程前设好（继承），要么逐 TID 设置（pthread_setaffinity_np / sched_setaffinity(tid, …)）。

落盘/统计/日志 SCHED_OTHER + nice 10-19 同会话内有效（autogroup 边界！）
批处理/回放 SCHED_BATCH 关闭交互补偿
最低限度后台 SCHED_IDLE 逃离它按 nice 20 提权审查

三、四个反直觉真相

  1. RT 优先级 1 > nice -20。不是"接近"，是碾压：两个世界在 p->prio 数轴上永不相交（98 vs 100 之间隔着 99）。给关键任务 nice -20 是自我安慰，给杂务任务 nice 19 也挡不住它被任何就绪 RT 任务踩。

  2. FIFO 任务的 sched_yield() 只是排队尾。rt.c:1590 的 requeue 只在同优先级队列内生效——低优先级任务依旧没机会。"yield 一下让系统喘口气"在 RT 世界是错觉。

  3. 满负荷 FIFO 会被系统强制冻结 50ms/秒。RT throttling（950ms/1s）是内核的自我保护，冻结的是该核全部 RT 任务。压测里出现的周期性 50ms 延迟尖峰，先查 dmesg | grep "RT throttling"——实测确会在内核日志里留下 sched: RT throttling activated（rt.c:1022）。

  4. SCHED_IDLE 是普通用户的单向门。切进去免特权（不过是一次没有 nice 变更的策略切换），切回来却按"从 nice 20 提权"审查（core.c:7598）——RLIMIT_NICE=0 的普通用户永远回不去。把 sched_setscheduler(0, SCHED_IDLE, …) 写进"可回收后台任务"之前，先想想它的退出机制：唯一出路是重启进程。实测见 35.6 实验 5。

四、五条铁律

  1. nice 管比例，FIFO 管抢占——需要"必定先跑"就上 RT 策略，nice 只是 CFS 内部的蛋糕切分。
  2. 权限判据读表不背口诀：切入 RT 要 RLIMIT_RTPRIO≠0 或 CAP_SYS_NICE；RT 降优先级无条件自由（core.c:7557 注释原文）。
  3. 同核同级 FIFO 只放一个任务——第二个会饿死，这是设计行为不是 bug。
  4. RT 服务 fork/exec 外部代码前设 RESET_ON_FORK——继承的 FIFO 99 是整机级炸弹（负 nice 也一样被重置）。
  5. 绑核 + FIFO 才是完整答案：FIFO 解决"何时跑"，绑核解决"在哪跑"，isolcpus 解决"谁不许来"——三层缺一不可。

代码自测

1. 为什么"给杂务进程 nice 19"挡不住它干扰 FIFO 任务，而"给杂务进程调到别的核"可以？

nice 只在 CFS 内部分蛋糕；FIFO 任务根本不与 CFS 任务竞争（prio 0-98 vs 100-139 两个世界）。而核是物理资源——同核的 FIFO 任务再高优先级，也要与该核的 cache/TLB/功耗状态共享。隔离靠 affinity/调度域，不靠 nice。

2. 一台 12 核 HFT 机的最小可用调度配置是什么？

isolcpus=4-11 nohz_full=4-11 rcu_nocbs=4-11（4-11 隔离）+ IRQ 全部钉到核 0-3 + 每个策略线程 taskset 进 4-11 之一 + sched_setscheduler(0, SCHED_FIFO, 80-95) + mlockall。nice 在这套配置里只剩"杂务内部排序"一个角色。

3. sched_yield、sleep、futex 阻塞对 FIFO 任务分别意味着什么？

yield：排队尾（同级才有意义）；sleep/nanosleep：主动离核，醒来按优先级立即抢回；futex 阻塞：睡眠等待事件，唤醒路径经 switched_to_rt 的 resched_curr——等待共享资源永远用 futex/条件变量，永远不用 yield 空转（还烧 RT 配额）。

实验 1：FIFO 99 满负荷 vs SCHED_OTHER 饿死

问题：核 11 上一个 FIFO 99 任务满负荷跑 2 秒，同核的 SCHED_OTHER 任务每 100ms 醒来记一次心跳，能记几次？实验用 busy_done 原子信号对齐双方时间窗，心跳全部落在 FIFO 占核期内，排除收尾自由段的干扰。

/* fifo_starve.c — FIFO 满负荷 vs OTHER 饿死 (root, 绑核 11, 全程 ~2.5s)
 * 编译: gcc -O2 -Wall -Wextra -o fifo_starve fifo_starve.c -pthread
 */
#define _GNU_SOURCE
#include <errno.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

static double now_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static double cpu_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_THREAD_CPUTIME_ID, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static atomic_int busy_done;

static void *worker(void *arg)
{
    long *beats = arg;
    const struct timespec nap = {.tv_sec = 0, .tv_nsec = 100000000};
    while (!atomic_load(&busy_done)) {
        nanosleep(&nap, NULL);
        (*beats)++;                 /* 醒得来 + 拿得到 CPU 才有心跳 */
    }
    return NULL;
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);

    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(11, &set);
    if (sched_setaffinity(0, sizeof set, &set) == -1) {
        perror("setaffinity(cpu11)");
        return 1;
    }

    long beats = 0;
    pthread_t tid;
    pthread_create(&tid, NULL, worker, &beats);

    struct sched_param sp = {.sched_priority = 99};
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == -1) {
        fprintf(stderr, "sched_setscheduler(FIFO,99): %s (需要 root)\n",
                strerror(errno));
        atomic_store(&busy_done, 1);
        pthread_join(tid, NULL);
        return 1;
    }

    double t0 = now_s(), c0 = cpu_s();
    while (now_s() - t0 < 2.0)
        ;                            /* FIFO 99 满负荷自旋 2s */
    double wall = now_s() - t0, cpu = cpu_s() - c0;

    atomic_store(&busy_done, 1);    /* 先停表, 再恢复 OTHER */
    sp.sched_priority = 0;
    sched_setscheduler(0, SCHED_OTHER, &sp);
    pthread_join(tid, NULL);

    printf("FIFO 线程: 墙钟 %.2fs, 获得 CPU %.2fs (%.0f%%)\n",
           wall, cpu, 100 * cpu / wall);
    printf("OTHER 线程: FIFO 占核 2s 内心跳 %ld 次"
           " (无限流理想 OTHER 应 20 次; FIFO 无限流则趋 0)\n", beats);
    return 0;
}

实测输出（root · 核 11）：

# ./fifo_starve
FIFO 线程: 墙钟 2.00s, 获得 CPU 1.90s (95%)
OTHER 线程: FIFO 占核 2s 内心跳 4 次

观察点： - FIFO 拿到 95% 而非 100%——RT throttling（950ms/1s，35.2 节六）在两秒内切出了约 100ms 的非 RT 窗口； - OTHER 心跳 4 次 ≈ 每个周期 50ms 窗口里挤进 2 次——饿死不是绝对的，throttling 是 OTHER 的活命通道。把 sched_rt_runtime_us 设为 -1 关闭限流再跑，心跳将归零（读者自证）； - dmesg | grep throttling 可见 sched: RT throttling activated（rt.c:1022）——本实验在 dmesg 里留下了它。

实验 2：RR 时间片轮转 vs FIFO 独占

问题：同优先级两个任务绑同一核，RR 和 FIFO 各是什么命运？ 设计要点：worker 各自上报 TID，主线程通过 TID 跨线程设置两个 worker 的策略（演示 35.3 的「pid 参数是 TID」），再统一放行——避免"先升级者满核压制后升级者"的起跑线污染。

/* rr_alt.c — 同优先级双子对比: ./rr_alt rr|fifo (root, worker 绑核 11)
 * 编译: gcc -O2 -Wall -Wextra -o rr_alt rr_alt.c -pthread
 */
#define _GNU_SOURCE
#include <errno.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

static double now_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static atomic_int ready, start;
static pid_t g_tids[2];
static long cnt1, cnt2;
static int g_policy;

static void *spin(void *arg)
{
    long idx = (long)arg;
    long *cnt = idx ? &cnt2 : &cnt1;
    g_tids[idx] = syscall(SYS_gettid);      /* 上报 TID */
    atomic_fetch_add(&ready, 1);
    while (!atomic_load(&start))
        ;                                   /* 策略由主线程经 TID 设置 */
    double end = now_s() + 2.0;
    while (now_s() < end)
        (*cnt)++;
    return NULL;
}

int main(int argc, char **argv)
{
    setvbuf(stdout, NULL, _IOLBF, 0);
    g_policy = (argc > 1 && strcmp(argv[1], "fifo") == 0)
               ? SCHED_FIFO : SCHED_RR;

    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(11, &set);                      /* worker: 核 11 */
    pthread_attr_t attr;
    pthread_attr_init(&attr);
    pthread_attr_setaffinity_np(&attr, sizeof set, &set);

    pthread_t t1, t2;
    pthread_create(&t1, &attr, spin, (void *)0);
    pthread_create(&t2, &attr, spin, (void *)1);

    CPU_ZERO(&set);
    CPU_SET(10, &set);                      /* 主线程: 核 10 */
    sched_setaffinity(0, sizeof set, &set);
    while (atomic_load(&ready) < 2)
        usleep(1000);

    /* 跨线程设置: sched_setscheduler 的 pid 参数传 TID (35.3 节) */
    struct sched_param sp = {.sched_priority = 50};
    if (sched_setscheduler(g_tids[0], g_policy, &sp) == -1 ||
        sched_setscheduler(g_tids[1], g_policy, &sp) == -1) {
        perror("sched_setscheduler(worker)");
        return 1;
    }
    printf("T1(tid=%d) T2(tid=%d) 已设为 %s/50, 同时起跑\n",
           g_tids[0], g_tids[1],
           g_policy == SCHED_FIFO ? "FIFO" : "RR");
    atomic_store(&start, 1);

    for (int s = 1; s <= 2; s++) {
        sleep(1);
        printf("t=%ds  cnt1=%-12ld cnt2=%-12ld\n", s, cnt1, cnt2);
    }
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("policy=%s: cnt1=%ld cnt2=%ld\n",
           g_policy == SCHED_FIFO ? "SCHED_FIFO" : "SCHED_RR",
           cnt1, cnt2);
    return 0;
}

实测输出（root · worker 核 11 / 采样核 10）：

# ./rr_alt rr
T1(tid=7413) T2(tid=7414) 已设为 RR/50, 同时起跑
t=1s  cnt1=33223410     cnt2=33230171
t=2s  cnt1=66377555     cnt2=66431802
policy=SCHED_RR: cnt1=66377555 cnt2=66431802     ← 严格平分

# ./rr_alt fifo

t=1s  cnt1=67668599     cnt2=1254
t=2s  cnt1=135437204    cnt2=1254

解读： - RR：两计数器每一秒都几乎相等——task_tick_rt 每 100ms（RR_TIMESLICE，rt.h:57）requeue 轮转（rt.c:2655-2667），双子平分秋色； - FIFO：cnt2 ≈ 0 恒定——tick 对 FIFO 直接 return（rt.c:2652），同级无轮转。cnt2 的非零余量（1254 次 ≈ 微秒级）来自设置成功到 T1 独占之间的毫秒级空隙，之后彻底归零； - 两组的 cnt 绝对值差 ≈ 2 倍：RR 版每个任务只拿到一半核时间——轮转的"税"直接可见（135M vs 66M）。

实验 3：RT throttling 直击（改配额 → 观察 → 恢复）

问题：把 sched_rt_runtime_us 从 950000 改成 100000（100ms/1s），FIFO 99 满负荷 2 秒能拿到多少 CPU？ 设计要点：先改配额再切 FIFO（消除设置间隙的积累），并跨周期边界 sleep 2 秒（让核 11 的 rt_time 被 period timer 清零，排除上一实验残留）。

/* rt_throttle.c — RT throttling 配额实验 (root, 绑核 11, 自动恢复 sysctl)
 * 编译: gcc -O2 -Wall -Wextra -o rt_throttle rt_throttle.c -pthread
 */
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

static double now_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static double cpu_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_THREAD_CPUTIME_ID, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static int write_sysctl(const char *val)
{
    FILE *f = fopen("/proc/sys/kernel/sched_rt_runtime_us", "w");
    if (!f)
        return -1;
    int r = fputs(val, f) == EOF ? -1 : 0;
    fclose(f);
    return r;
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);

    char orig[32] = "?";
    FILE *f = fopen("/proc/sys/kernel/sched_rt_runtime_us", "r");
    if (!f || !fgets(orig, sizeof orig, f)) {
        perror("读 sched_rt_runtime_us");
        return 1;
    }
    fclose(f);
    orig[strcspn(orig, "\n")] = 0;
    printf("当前配额: runtime=%s / period=1000000 (µs)\n", orig);

    /* 先改配额, 再切 FIFO: 消除切换间隙的 rt_time 积累 */
    if (write_sysctl("100000") == -1) {
        perror("写 sysctl");
        return 1;
    }
    printf("配额改为 100000 (100ms/1s)\n");

    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(11, &set);
    sched_setaffinity(0, sizeof set, &set);

    /* 跨周期边界: 清掉本核 rt_time 的历史残留 (前一实验的 FIFO 留下的账) */
    sleep(2);

    struct sched_param sp = {.sched_priority = 99};
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == -1) {
        perror("sched_setscheduler(FIFO,99)");
        write_sysctl(orig);
        return 1;
    }
    printf("FIFO 99 满负荷 2s...\n");

    double t0 = now_s(), c0 = cpu_s();
    while (now_s() - t0 < 2.0)
        ;
    double wall = now_s() - t0, cpu = cpu_s() - c0;

    write_sysctl(orig);                      /* 无论结果如何都恢复 */
    printf("结果: 墙钟 %.2fs, 获得 CPU %.2fs (%.0f%%)\n",
           wall, cpu, 100 * cpu / wall);
    printf("已恢复 runtime=%s (验证: cat /proc/sys/kernel/sched_rt_runtime_us)\n",
           orig);
    return 0;
}

实测输出（root · 核 11）：

# ./rt_throttle
当前配额: runtime=950000 / period=1000000 (µs)
配额改为 100000 (100ms/1s)
FIFO 99 满负荷 2s...
结果: 墙钟 2.03s, 获得 CPU 0.20s (10%)
已恢复 runtime=950000 (验证: cat /proc/sys/kernel/sched_rt_runtime_us)

解读：2.03s 墙钟只拿到 0.20s——恰好 = 2 个周期 × 100ms 配额。rt_time 一超 100ms（sched_rt_runtime_exceeded rt.c:1013），整队下架冻结到周期起点（hrtimer sched_rt_period_timer 补给，rt.c:66/:901）。这就是 35.2 那张限流图的数值版。

$ dmesg | grep -i throttling
[  239.912405] sched: RT throttling activated          ← rt.c:1022 printk

相位噪声警告：同一程序重跑一次得到的是 墙钟 2.14s / CPU 0.30s (14%) 而非 0.20s——任务起点与 period hrtimer 的相位关系决定了第一段配额窗口的可用长度（起点恰在周期边界后 vs 边界临近，第一段能差出约一个配额）。做 throttling 实验看数量级（约 2×runtime），别较真个位数百分比。

实验教训（第一版踩坑记）：本实验第一版把"切 FIFO"放在"改配额"之前，且没有跨周期 sleep——实测得到 墙钟 8.06s / CPU 0.00s 的诡异数据：上一实验（rr_alt fifo）留在核 11 的 rt_time 残余让本任务上线即超限，几乎没跑就被冻结；随后 hypervisor 层的 vCPU 唤醒延迟让每次解冻都迟到，形成"冻结 900ms→解冻跑几微秒→再冻结"的循环，墙钟膨胀 4 倍。两处顺序修正（先改配额、跨周期清账）之后数据立即回到理论值。rt_rq 的账本是每 CPU 持久的，做 throttling 实验必须先"清账"。

实验 4：CFS 权重比——nice 0 vs nice 5 同核对撞（预写→实测）

问题：35.1 说"nice 差 5 ≈ 1.25⁵ ≈ 3.06 : 1 的 CPU 时间比"。同核上真跑出来是多少？ 设计要点：两个 worker 绑同一核（核 11，主线程躲核 10），各自 setpriority(PRIO_PROCESS, 0, n) 给自己设 nice（顺带验证 pid 参数的 TID 粒度），atomic 发令对齐起跑，各跑 4s 墙钟后报告 CLOCK_THREAD_CPUTIME_ID。

/* nice_race.c — CFS 权重比实测: 同核 nice 0 vs nice 5
 * 预写结论: CPU 时间比 ≈ 1024:335 ≈ 3.06:1 (1.25^5)
 * 关键设计: worker 各自 setpriority(PRIO_PROCESS, 0, n) 作用于自身线程
 *           —— PRIO_PROCESS 的 pid 参数是 TID 粒度 (sys.c:219 task_pid_vnr(current))
 * 编译: gcc -O2 -Wall -Wextra -o nice_race nice_race.c -pthread
 */
#define _GNU_SOURCE
#include <errno.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdio.h>
#include <string.h>
#include <sys/resource.h>
#include <time.h>
#include <unistd.h>

static double now_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static double cpu_s(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_THREAD_CPUTIME_ID, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static atomic_int go;
static double cpu0, cpu5;

static void *spin_target(void *arg)
{
    long want_nice = (long)arg;
    /* nice 对自身线程设置: PRIO_PROCESS + who=0 → 调用线程自己 */
    if (setpriority(PRIO_PROCESS, 0, (int)want_nice) == -1) {
        fprintf(stderr, "worker(nice %ld) setpriority: %s\n",
                want_nice, strerror(errno));
        return NULL;
    }
    errno = 0;
    int got = getpriority(PRIO_PROCESS, 0);
    printf("  worker: 请求 nice %ld, 读回 nice %d\n", want_nice, got);

    while (!atomic_load(&go))
        ;                        /* 等发令 */
    double end = now_s() + 4.0;  /* 各自跑 4s 墙钟 */
    double c0 = cpu_s();
    while (now_s() < end)
        ;
    double used = cpu_s() - c0;
    if (want_nice == 0)
        cpu0 = used;
    else
        cpu5 = used;
    return NULL;
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);
    printf("[nice_race] 预写: nice0/nice5 CPU 比 ≈ 1024/335 = %.3f\n",
           1024.0 / 335.0);

    cpu_set_t wset, mset;
    CPU_ZERO(&wset);
    CPU_SET(11, &wset);          /* worker: 核 11 */
    CPU_ZERO(&mset);
    CPU_SET(10, &mset);          /* 主线程: 核 10 */

    pthread_attr_t attr;
    pthread_attr_init(&attr);
    pthread_attr_setaffinity_np(&attr, sizeof wset, &wset);

    pthread_t t0, t5;
    pthread_create(&t0, &attr, spin_target, (void *)0);
    pthread_create(&t5, &attr, spin_target, (void *)5);

    if (sched_setaffinity(0, sizeof mset, &mset) == -1) {
        perror("主线程 setaffinity(核10)");
        return 1;
    }
    usleep(100000);              /* 等 worker 报告 nice 读回 */
    atomic_store(&go, 1);

    pthread_join(t0, NULL);
    pthread_join(t5, NULL);

    printf("实测: nice0 = %.2fs, nice5 = %.2fs, 比值 = %.2f : 1\n",
           cpu0, cpu5, cpu0 / cpu5);
    printf("偏差: 实测 %.2f vs 理论 3.06 (%.1f%%)\n",
           cpu0 / cpu5, 100.0 * (cpu0 / cpu5) / 3.057 - 100.0);
    return 0;
}

实验 6：RESET_ON_FORK 隔代验证（预写→实测）

问题：flag "只管一代"到底是什么意思——孙进程会怎样？ 预写：子进程被重置（OTHER/0，ROF 位清零）；子进程若重设 FIFO 不带 ROF，孙进程应原样继承 FIFO 40（不再有重置发生）。

/* rof_grand.c — SCHED_RESET_ON_FORK 隔代验证 (root)
 * 预写: flag 只管一代 (core.c:4763 子进程出生时清零)
 *   子进程: policy=OTHER, rt_priority=0, 无 ROF 位 (被重置)
 *   孙进程: 继承子进程的 FIFO 40 原样 (无重置) —— 重置不是遗传病
 * 编译: gcc -O2 -Wall -Wextra -o rof_grand rof_grand.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static const char *polname(int p)
{
    int reset = p & SCHED_RESET_ON_FORK;
    p &= ~SCHED_RESET_ON_FORK;
    static char buf[32];
    const char *base =
        p == SCHED_OTHER ? "SCHED_OTHER" :
        p == SCHED_FIFO  ? "SCHED_FIFO"  :
        p == SCHED_RR    ? "SCHED_RR"    : "other";
    snprintf(buf, sizeof buf, "%s%s", base, reset ? "+ROF" : "");
    return buf;
}

static void dump(const char *who)
{
    struct sched_param sp = {0};
    sched_getparam(0, &sp);
    printf("  %-8s pid=%-6d policy=%-16s rt_priority=%d\n",
           who, getpid(), polname(sched_getscheduler(0)), sp.sched_priority);
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);
    printf("[rof_grand] 预写: ROF 位只管一代, 孙进程不再带位\n");

    /* 父: FIFO 50 + RESET_ON_FORK */
    struct sched_param sp = {.sched_priority = 50};
    if (sched_setscheduler(0, SCHED_FIFO | SCHED_RESET_ON_FORK, &sp) == -1) {
        printf("需要 root: %s\n", strerror(errno));
        return 1;
    }
    dump("父(设置后)");

    pid_t child = fork();
    if (child == 0) {
        dump("子");              /* 预写: OTHER/0, 无 ROF 位 (被重置) */

        /* 子进程自行重设 FIFO 40 —— 注意不带 ROF 位。
         * 孙进程将原样继承 FIFO 40 (无重置) —— 这才是
         * "flag 不遗传"的直接证据: 重置只发生在父带位的那一次 fork */
        struct sched_param sp2 = {.sched_priority = 40};
        if (sched_setscheduler(0, SCHED_FIFO, &sp2) == 0) {
            printf("  子进程自行设 FIFO 40 (无ROF): OK\n");
            dump("子(重设后)");
        }

        pid_t grand = fork();
        if (grand == 0) {
            dump("孙");          /* 预写: FIFO/40 原样继承, 无 ROF 位 */
            _exit(0);
        }
        waitpid(grand, NULL, 0);
        sched_setscheduler(0, SCHED_OTHER, &(struct sched_param){0});
        _exit(0);
    }
    waitpid(child, NULL, 0);
    dump("父(最终)");            /* 预写: FIFO+ROF, 50 不变 */
    return 0;
}

# ./rof_grand
[rof_grand] 预写: ROF 位只管一代, 孙进程不再带位
  父(设置后) pid=384    policy=SCHED_FIFO+ROF   rt_priority=50
  子      pid=385    policy=SCHED_OTHER      rt_priority=0
  子进程自行设 FIFO 40 (无ROF): OK

解读： - 预写命中：五条记录构成"只管一代"的完整证据链—— 1. 父带位 → 子出生即重置（OTHER/0），sched_reset_on_fork 位同步清零（core.c:4763）； 2. 子重设 FIFO 40（无 ROF）→ 孙原样继承 FIFO 40——如果 flag 会遗传，孙也该被重置成 OTHER，实测否决； - ROF 的本质是出生时的一次性产钳，不是写进基因的遗传病——每一次 fork 是否重置，只看父进程此刻有没有带位； - 注意 sched_getscheduler 返回值的坑（35.3）：父显示 SCHED_FIFO+ROF 是 Linux 2.6.39+ 的扩展行为（返回值带 flag 位），polname() 里的 p &= ~SCHED_RESET_ON_FORK 先剥位再判断才是可移植写法。

习题 7：推演——为什么 nice -20 救不了"必须先跑"

某同学把策略线程设为 SCHED_OTHER + nice -20，理由是"已经是普通进程最高优先级"。

参考答案

两个世界：策略线程的内核 prio = NICE_TO_PRIO(-20) = 100；而任何就绪 RT 任务 prio ≤ 98。调度类层面 fair 整体被 rt 压制（sched.h:2323 类链从高往低扫），数值层面 100 > 98 恒成立。机器上任何一个失控的 SCHED_FIFO 1（哪怕 nice -20 的 CFS 负载为零）都能把它踩进土里。"必须先跑"只有 RT 策略能承诺，nice 的极限只是"其他 CFS 任务让着我"。

习题 8：设计——RT 服务的 fork 边界

一个 FIFO 90 的数据采集守护进程（root 运行）需要在收到外部指令时 fork/exec 执行 /usr/local/bin/reload.sh。给出三道防线防止调度属性泄漏到脚本。

参考答案
  1. SCHED_RESET_ON_FORK：主服务 sched_setscheduler(0, SCHED_FIFO|SCHED_RESET_ON_FORK, &sp)——fork 出的子进程 policy→SCHED_NORMAL、nice→0、rt_priority→0（core.c:4750-4752），连负 nice 也一并归零（:4753-4754）。注意 flag 只管一代、且普通用户不能取消它（:7607-7609）；
  2. exec 前显式降级：fork 后、exec 前在子进程里 sched_setscheduler(0, SCHED_OTHER, &{0})——RT 任务降优先级/降级是无特权自由（core.c:7557），双保险；
  3. 能力最小化：整个服务只给 cap_sys_nice（setcap）而非裸 root；脚本以专用低权账号跑——就算属性泄漏，泄漏的 FIFO 90 也撞不上任何别的破坏面。

风险点：巡检时注意 sched_getscheduler 返回值会带回 RESET_ON_FORK 位（2.6.39+ 扩展，35.3 实验 3 实测），先剥位再判断。

习题 9：综合设计——trader 双线程启动序列

行情线程（必须微秒级响应）+ 落盘线程（可拖延）。写出两个线程各自的调度配置与完整启动序列，并说明每一步为什么在这个次序。

参考答案

配置：行情线程 = SCHED_FIFO 85 + 绑隔离核 4 + mlockall；落盘线程 = SCHED_OTHER + nice 15 + 绑核 8（杂务核）。

序列与理由：

步 操作 为什么必须在此时
1 mlockall(MCL_CURRENT\|MCL_FUTURE) 趁代码还在 CFS 下、页错误还廉价时锁页；RT 之后一次缺页 = 微秒级悬崖
2 预触/预热所有热路径内存 + cache 同上，且绑核后的迁移会冷 cache，预热应在最终绑核后补一轮
3 sched_setaffinity 绑核 策略切换前先定"在哪跑"，避免切 FIFO 后任务先在错核上抢到 CPU
4 行情线程 sched_setscheduler(0, SCHED_FIFO, 85) 即时生效（switched_to_rt → resched_curr，rt.c:2557）；之后才允许开始热路径
5 落盘线程 setpriority(PRIO_PROCESS, tid, 15) 最后降权——它不抢即可，顺序无碍
6 行情线程设 RLIMIT_RTTIME 兜底 防 bug 自旋烧配额触发 throttling 连累全核（35.2 节六）

为什么行情线程 85 而不是 99：内核线程（ksoftirqd 等）在 99 附近有关键活动；网络收包链路若被自家线程踩住，延迟反而恶化。留头部余量是工程纪律（同 35.2 关联表）。
