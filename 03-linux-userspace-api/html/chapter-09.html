代码示例

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

/* Ch9 进程凭证 — real/effective/saved-set uid/gid。
 * getresuid/getresgid 同时获取三种 uid/gid。
 * 编译: gcc -o ch9_demo ch9_demo.c */

int main(void) {
    uid_t ruid, euid, suid;
    gid_t rgid, egid, sgid;

    if (getresuid(&ruid, &euid, &suid) == 0)
        printf("uid: real=%u, effective=%u, saved=%u\n",
               ruid, euid, suid);

    if (getresgid(&rgid, &egid, &sgid) == 0)
        printf("gid: real=%u, effective=%u, saved=%u\n",
               rgid, egid, sgid);

    /* setuid 特殊语义：
     * - 以 root 运行: 三者都设
     * - 以普通用户运行: 只设 effective（且只能在 real/saved 范围内）
     */
    printf("\nIf running as root, all three uid become the target.\n");
    printf("If running as normal user, only effective uid changes.\n");
    return 0;
}

9.1

五类凭证

本章：TLPI 第 09 章 — Process Credentials - 上一节：本章首页 - 下一节：9.2 –9.3 Set-User-ID / Set-Group-ID

本节讲什么

Demo：code/print_credentials.c ---

要点

1. Real UID / GID（RUID / RGID）
含义 真正属于谁（登录者身份）
继承 fork 继承；exec 默认不变
用途 发送信号权限、资源归属等
获取 getuid() / getgid()

2. Effective UID / GID（EUID / EGID）
含义 权限检查用的 ID（文件、IPC 等）
特权 EUID == 0 → 特权进程（root 能力意义上的）
获取 geteuid() / getegid()

3. Saved set-user-ID / set-group-ID（SUID / SGID）
用途 专为 set-UID / set-GID 程序
exec 新 EUID/EGID 复制到 Saved-ID
作用 允许在「普通身份 ↔ 文件属主身份」间多次切换

4. File-system UID / GID（FUID / FGID · Linux 专有）
历史 早期想把「文件权限」与「其它」检查拆开
现状 自 2.2 起 默认恒等于 EUID/EGID
修改 setfsuid() / setfsgid()（现代代码几乎不用）
移植 POSIX 无此概念，跨平台勿依赖

5. Supplementary group IDs（补充组）
含义 用户所属多个组；权限检查一并计入
获取 getgroups(size, list)
修改 setgroups() — 仅特权进程

Demo：code/print_credentials.c

HFT / 嵌入式关联

路线 要点
嵌入式 五类凭证 在嵌入式系统的应用场景

代码示例

#include <unistd.h>
#include <stdio.h>

int main(void) {
    /* 获取三类凭证: Real / Effective / Saved */
    uid_t ruid, euid, suid;
    gid_t rgid, egid, sgid;

    /* getresuid 一次拿全 R/E/S (Linux 扩展) */
    if (getresuid(&ruid, &euid, &suid) != 0) {
        perror("getresuid");
        return 1;
    }
    if (getresgid(&rgid, &egid, &sgid) != 0) {
        perror("getresgid");
        return 1;
    }

    printf("=== 进程凭证 ===\n");
    printf("Real    UID=%d  GID=%d  (真正属于谁)\n", ruid, rgid);
    printf("Effective UID=%d  GID=%d  (权限检查用)\n", euid, egid);
    printf("Saved   UID=%d  GID=%d  (切换用)\n", suid, sgid);

    /* 补充组 */
    gid_t groups[32];
    int n = getgroups(32, groups);
    if (n > 0) {
        printf("补充组: ");
        for (int i = 0; i < n; i++) printf("%d ", groups[i]);
        printf("\n");
    }

    if (euid == 0) printf("→ 特权进程\n");
    return 0;
}

9.2

Effective User ID and Effective Group ID

本章：TLPI 第 9 章

本节讲什么

Effective UID/GID 决定进程的权限检查。

Real vs Effective

  • Real UID：启动进程的用户
  • Effective UID：权限检查使用的 UID
  • 通常 real == effective
  • set-user-ID 程序：real != effective

示例

ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root ...  # set-user-ID bit (s)

运行 passwd 时：real=普通用户，effective=root → 可以写 /etc/shadow

相关 API

  • geteuid()/getegid() — 获取 effective ID
  • seteuid()/setegid() — 设置 effective ID

9.2

–9.3 Set-User-ID / Set-Group-ID

本章：TLPI 第 09 章 — Process Credentials - 上一节：9.1 五类凭证 - 下一节：9.4 Saved-ID 升降权流程

本节讲什么

可执行文件权限位： chmod u+s program # set-user-ID chmod g+s program # set-group-ID

要点

可执行文件权限位：

chmod u+s program   # set-user-ID
chmod g+s program   # set-group-ID
ls -l               # 常见显示 -rwsr-xr-x / -rwxr-sr-x

execve 加载该程序时：

变化 结果
EUID = 文件属主 UID（若 setuid 位开）
EGID = 文件属主 GID（若 setgid 位开）
Saved-ID ← 拷贝新的 EUID/EGID
RUID 不变（仍是启动者）

经典例子：passwd（属主 root + setuid）
普通用户运行 → EUID=0 可改 shadow；RUID 仍是普通用户。

⚠️ setuid 程序是高危攻击面 → Ch38 安全编写。

路线 要点
嵌入式 –9.3 Set-User-ID / Set-Group-ID 在嵌入式系统的应用场景

代码示例

#include <unistd.h>
#include <stdio.h>

/* 编译后需 chmod u+s 设 setuid 位才能看到效果:
 *   gcc -o demo 9.2-set-user-id.c
 *   sudo chown root demo
 *   sudo chmod u+s demo
 *   ./demo
 */
int main(void) {
    uid_t ruid = getuid();   /* 启动者 (不变) */
    uid_t euid = geteuid();  /* 文件属主 (可能变) */

    printf("RUID = %d (启动者)\n", ruid);
    printf("EUID = %d (有效身份)\n", euid);

    if (euid != ruid) {
        printf("→ setuid 程序! EUID = 文件属主\n");
        printf("→ 拥有属主的权限 (如 root)\n");
    } else {
        printf("→ 普通程序, RUID == EUID\n");
        printf("→ 设 setuid 位后 EUID 会变成文件属主\n");
    }

    /* 经典例子: passwd 命令
     * ls -l /usr/bin/passwd → -rwsr-xr-x (s = setuid)
     * 普通用户运行 → EUID=0 → 可改 /etc/shadow
     */
    return 0;
}

9.4

Saved-ID 升降权流程

本章：TLPI 第 09 章 — Process Credentials - 上一节：9.2 –9.3 Set-User-ID / Set-Group-ID - 下一节：9.5 获取凭证 API

本节讲什么

典型：普通用户跑 root 属主 setuid 程序 初始: RUID=1000 EUID=0 SUID=0 seteuid(1000):

要点

典型：普通用户跑 root 属主 setuid 程序

初始:  RUID=1000  EUID=0     SUID=0
seteuid(1000):
       RUID=1000  EUID=1000  SUID=0     ← 临时降权
seteuid(0):
       RUID=1000  EUID=0     SUID=0     ← 靠 Saved-ID 再提权

若无 Saved-ID，降权后无法再回到 0。

永久丢弃特权（对外 SUID 程序推荐）

业务结束后不要保留可恢复 root：

setuid(getuid());   /* 特权进程：R/E/S 全部钉成 RUID，无法再 seteuid(0) */

临时降权用 seteuid(getuid())（Saved 仍为 0，可再提权）——仅内部可信阶段使用。

Demo：code/seteuid_drop_restore.c · code/setuid_permanent_drop.c

HFT / 嵌入式关联

路线 要点
嵌入式 Saved-ID 升降权流程 在嵌入式系统的应用场景
HFT Saved-ID 升降权流程 对低延迟和性能的影响

代码示例

#include <stdio.h>
#include <unistd.h>
/* saved-set uid: 保存 effective uid 以便恢复 */
int main(void) {
    uid_t ruid, euid, suid;
    getresuid(&ruid, &euid, &suid);
    printf("real=%u effective=%u saved=%u\n",
           (unsigned)ruid, (unsigned)euid, (unsigned)suid);

    /* seteuid: 临时切换 effective uid */
    if (euid == 0) {
        seteuid(ruid);  /* 降为普通用户 */
        printf("after seteuid(ruid): euid=%u\n", (unsigned)geteuid());
        seteuid(0);     /* 恢复 root (saved-set 允许) */
        printf("after seteuid(0): euid=%u\n", (unsigned)geteuid());
    }
    return 0;
}

9.5

File-System User ID and File-System Group ID

本章：TLPI 第 09 章 — Process Credentials

本节讲什么

介绍 Linux 特有的 FS UID/GID（文件系统用户/组 ID），其历史由来（NFS 服务器需求）、与 effective UID 的关系，以及为何在现代系统中基本被废弃。

要点

FS UID 的定义

概念 说明
FS UID Linux 特有凭证，用于文件系统权限检查
FS GID 同上，组级别
默认值 始终等于 effective UID/GID
修改 API setfsuid(uid) / setfsgid(gid) — 仅 Linux，非 POSIX

历史背景：NFS 场景

NFS 客户端进程             NFS 服务器进程
effective UID = alice     需要 access 检查 FS UID
                          但 effective UID = root（NFS 服务以 root 运行）
                          FS UID = alice（来自客户端请求）
                          → 文件系统权限检查用 FS UID = alice
  • NFS 服务器以 root 身份运行（effective UID = 0）
  • 但文件访问检查需要用客户端用户身份
  • FS UID 允许 NFS 服务器将文件系统身份临时切换到客户端用户，而保持 effective UID = root
  • 这样 NFS 能正确代表远程用户做权限检查

setfsuid 语义

int old_fsuid = setfsuid(new_uid);
/* 返回旧的 FS UID，不报错（总是"成功"） */
  • 无错误返回：setfsuid 没有 errno，即使参数非法
  • 规则：非特权进程只能设为 current real/effective/saved/setfsuid UID；root 可设任意
  • 现代行为：从 Linux 2.0 开始，setuid 同时修改 effective 和 FS UID

为什么被废弃

原因 说明
NFS 重构 现代 NFS 使用 nfsd 内核线程或用户态服务，不再依赖 FS UID
安全性差 无错误返回，容易误用
复杂性 多一组凭证增加理解负担和出错可能
POSIX 不兼容 非 POSIX 标准，移植性差

现代 Linux 的行为

setuid(x)  →  同时修改 effective UID 和 FS UID  (非特权进程)
setuid(0)  →  同时修改 real, effective, saved, FS UID  (root)
seteuid(x) →  同时修改 effective UID 和 FS UID

FS UID 始终跟随 effective UID，没有单独设置的必要。

HFT / 嵌入式关联

  • 不推荐使用：HFT 和嵌入式场景都不应使用 setfsuid，依赖标准 POSIX 凭证管理
  • 嵌入式：精简系统通常没有 NFS，FS UID 完全无意义
  • 安全审计：代码审查中遇到 setfsuid 应视为可疑代码

代码示例

/* 不推荐的做法（仅用于理解历史） */
#include <unistd.h>

void nfs_access_demo(void) {
    /* NFS 服务器接收客户端请求，代表 alice 做文件检查 */
    uid_t client_uid = 1000;   /* alice */
    setfsuid(client_uid);       /* 文件系统权限用 alice */
    /* 但 effective UID 仍为 root */
    int fd = open("/shared/file", O_RDONLY);
    /* 权限检查使用 FS UID = alice */
    setfsuid(0);                /* 恢复 */
}

代码自测

1. FS UID 和 effective UID 有什么区别？什么时候会不同？
  • 默认情况下完全相同——setuid/seteuid 同时修改两者
  • 唯一不同的情况：程序显式调用 setfsuid() 单独修改 FS UID
  • 历史上 NFS 服务器这样做：effective=root（需要特权操作），FS UID=客户端用户（正确做文件权限检查）
  • 现代 Linux 不推荐这种做法
2. 为什么 setfsuid 没有错误返回？

setfsuid 的接口设计返回旧的 FS UID 值，没有专门的错误指示。即使传入非法 UID，函数也返回旧值而不报错。这是因为 FS UID 的设计较早，API 不够严谨。这也使得它容易误用——调用者无法确定设置是否成功。

3. 现代 Linux 程序应该用什么方式管理文件系统身份？

完全通过标准 POSIX 凭证：setuid/seteuid/setgid/setegid。不使用 setfsuid/setfsgid。如果需要细粒度权限控制，使用 Linux capabilities（Ch39）而非 UID 切换。NFS 服务器身份映射在现代内核中使用 nfsd 文件系统接口。

9.6

Supplementary Group IDs

本章：TLPI 第 09 章 — Process Credentials

本节讲什么

介绍附属组（supplementary groups）机制：进程除主 GID 外还可以属于多个组，这些组在文件权限检查时一并考虑。涵盖 getgroups/setgroups/initgroups API。

要点

附属组的作用

用户 alice 的组信息：
  主组: dev (gid=1000)
  附属组: docker(900), finance(2000), admin(3000)

进程启动时加载：
  effective GID = 1000 (dev)
  supplementary groups = [900, 2000, 3000]

文件权限检查：
  文件 group = docker(900), mode = rw-rw----
  → 进程有附属组 900 → 允许读写

核心 API

函数 原型 说明 权限
getgroups(size, list) int getgroups(int size, gid_t list[]) 获取附属组列表 无特权要求
setgroups(size, list) int setgroups(size_t size, const gid_t *list) 设置附属组列表 CAP_SETGID
initgroups(user, group) int initgroups(const char *user, gid_t group) 从 /etc/group 加载用户附属组 CAP_SETGID

getgroups 使用模式

/* 正确用法：先查数量，再分配 */
int n = getgroups(0, NULL);       /* 查数量 */
if (n > 0) {
    gid_t *groups = malloc(n * sizeof(gid_t));
    getgroups(n, groups);          /* 获取列表 */
    /* 使用 groups[] */
    free(groups);
}

权限检查流程（内核）

进程访问文件 →
1. effective UID == 0 (root)?
   → 是：允许（除非文件权限无任何位）
2. 文件 owner UID == effective UID?
   → 是：检查 owner 权限位 (rwx)
3. 文件 group == effective GID 或在 supplementary groups 中?
   → 是：检查 group 权限位
4. 否则检查 other 权限位

注意：如果 owner 权限位不满足，不会继续检查 group/other。每个身份只检查对应的一组权限位。

setgroups 的安全约束

场景 可否调用 setgroups
root (effective UID=0) 可以
有 CAP_SETGID 的进程 可以
普通用户 不可以 — EPERM

顺序重要性：drop privilege 时的正确顺序

1. setgroups(0, NULL)     ← 先清空附属组！
2. setgid(new_gid)        ← 再修改 GID
3. setuid(new_uid)        ← 最后修改 UID（不可逆）

为什么：如果先 setuid，非特权后 setgroups 失败（EPERM），附属组仍保留 root 组，权限未完全放下。

HFT / 嵌入式关联

  • 权限隔离：HFT 多组件用不同用户+附属组控制数据访问（行情组只读策略目录）
  • 安全降权：setuid 程序 drop privilege 时必须先 setgroups(0, NULL)
  • 嵌入式：精简系统通常只有 root + 一个用户，附属组较少使用
  • Docker 容器：容器内用户映射可能涉及 setgroups，/etc/subuid//etc/subgid

代码示例

#include <unistd.h>
#include <grp.h>
#include <stdio.h>

/* 打印当前进程的所有附属组 */
void print_groups(void) {
    int n = getgroups(0, NULL);
    if (n <= 0) { printf("no supplementary groups\n"); return; }

    gid_t *groups = malloc(n * sizeof(gid_t));
    getgroups(n, groups);

    printf("supplementary groups (%d):", n);
    for (int i = 0; i < n; i++) {
        struct group *gr = getgrgid(groups[i]);
        printf(" %s(%d)", gr ? gr->gr_name : "???", groups[i]);
    }
    printf("\n");
    free(groups);
}

/* 安全降权：完全放弃所有特权 */
int drop_privileges(uid_t new_uid, gid_t new_gid) {
    /* 1. 先清空附属组 */
    if (setgroups(0, NULL) != 0) {
        perror("setgroups");
        return -1;
    }
    /* 2. 设 GID */
    if (setgid(new_gid) != 0) {
        perror("setgid");
        return -1;
    }
    /* 3. 设 UID（不可逆，root → 普通用户） */
    if (setuid(new_uid) != 0) {
        perror("setuid");
        return -1;
    }
    return 0;
}

代码自测

1. setgroups 为什么必须在 setgid 之前调用？

因为 setgroups 需要 CAP_SETGID 权限。如果先执行 setuid（从 root 降为普通用户），进程失去 root 权限，setgroups 会返回 EPERM。结果：主 GID 已改但附属组仍包含 root 组，权限未完全放下，构成安全漏洞。正确顺序：先 setgroups(0, NULL) 清空，再 setgid，最后 setuid。

2. getgroups(0, NULL) 的返回值含义？

返回当前附属组的数量。如果为 0 表示没有附属组。返回 -1 表示错误。这是"先查数量再分配"的标准模式，避免硬编码数组大小。

3. initgroups 的作用是什么？什么时候需要调用？

initgroups(user, gid) 读取 /etc/group，找出用户 user 所属的所有组，加上 gid 作为主组，调用 setgroups 设置完整附属组列表。通常在 setgid/setuid 切换到目标用户后调用，确保新身份的附属组正确加载。如：su 命令切换用户后需要 initgroups。

#include <unistd.h>
#include <stdio.h>

/* setuid-root 程序示范: 临时降权 → 做普通工作 → 恢复特权
 * 编译: gcc -o demo 9.6-credentials.c
 * 设置: sudo chown root demo && sudo chmod u+s demo
 */
int main(void) {
    uid_t ruid = getuid();
    uid_t euid = geteuid();

    printf("初始: RUID=%d EUID=%d\n", ruid, euid);

    if (euid == 0) {
        /* 有特权 → 临时降为普通用户 */
        printf("降权: seteuid(%d)\n", ruid);
        if (seteuid(ruid) != 0) { perror("seteuid drop"); return 1; }
        printf("现在: RUID=%d EUID=%d (普通权限)\n", getuid(), geteuid());

        /* 在普通权限下做不安全的操作... */

        /* 恢复特权 (因为 Saved-ID 仍为 0) */
        printf("恢复: seteuid(0)\n");
        if (seteuid(0) != 0) { perror("seteuid restore"); return 1; }
        printf("现在: RUID=%d EUID=%d (恢复特权)\n", getuid(), geteuid());

        /* 永久丢弃特权 (做完后) */
        printf("永久丢弃: setuid(%d)\n", ruid);
        if (setuid(ruid) != 0) { perror("setuid permanent"); return 1; }
        printf("现在: RUID=%d EUID=%d (无法恢复)\n", getuid(), geteuid());
    } else {
        printf("非特权进程, 演示需要 setuid-root\n");
    }
    return 0;
}

进程凭证一览

凭证 用途 修改 API 非 root 限制

setuid/seteuid/setresuid 行为对比

操作 root (euid=0) 非特权进程
setuid(x) 同时设 real=effective=saved=x 只设 effective=x（等于 seteuid）
seteuid(x) 设 effective=x 设 effective=real 或 saved 之一
setresuid(r,e,s) 同时设 real/eff/saved 三个中每个必须是 real/eff/saved 之一

凭证在 fork/exec 时的传递

事件 Real Effective Saved
fork() 继承父 继承父 继承父
exec()（无 setuid 位） 不变 不变 = effective 设为 effective
exec()（有 setuid 位） 不变 设为文件 owner 设为 effective

set-user-ID 程序工作流程

1. 程序文件 setuid 位 + owner=root
2. exec → effective UID = root, saved UID = root
3. 程序以 root 身份执行特权操作
4. 完成后 seteuid(real_uid) → 临时降权
5. 需要时 seteuid(saved_uid=0) → 恢复特权
6. 最终 setuid(real_uid) → 永久降权（不可逆）

代码自测

1. setuid 程序如何安全地临时降权和恢复特权？ 
uid_t real = getuid();     /* 启动用户 */
uid_t saved = geteuid();   /* exec 后 saved = effective = root */

/* 临时降权 */
seteuid(real);             /* effective = real, saved 不变 */

/* 恢复特权 */
seteuid(saved);            /* effective = saved = root */

/* 永久降权 */
setuid(real);              /* real=eff=saved = real, 不可逆 */

关键：saved 保存了 exec 时的 effective UID，即使临时降权也能恢复。永久降权用 setuid 而非 seteuid。

2. fork 后子进程的凭证是什么？

fork 后子进程继承父进程的所有凭证：real UID/GID、effective UID/GID、saved set-UID/GID、附属组列表。父子进程凭证相同。但父子进程是独立的进程，之后各自修改自己的凭证互不影响。

3. 为什么 drop privilege 必须按 setgroups → setgid → setuid 顺序？
  • setgroups 需要 root 权限。如果先 setuid（降为普通用户），setgroups 返回 EPERM
  • 结果：主 GID 改了但附属组列表仍包含 root 组，权限未完全放下
  • 正确顺序：先 setgroups(0, NULL) 清空，再 setgid，最后 setuid
  • setuid 从 root→普通用户是不可逆的（无法回到 root）

练习 3 参考代码

#include <unistd.h>
#include <grp.h>

int drop_priv_forever(uid_t uid, gid_t gid) {
    /* 1. 清空附属组 */
    if (setgroups(0, NULL) != 0) return -1;
    /* 2. 设 GID（real=eff=saved=gid） */
    if (setgid(gid) != 0) return -1;
    /* 3. 设 UID（real=eff=saved=uid，不可逆） */
    if (setuid(uid) != 0) return -1;

    /* 验证 */
    if (geteuid() != uid || getegid() != gid) return -1;
    return 0;
}

    drop_priv_forever(1000, 1000);  /* 永久降为普通用户 */
    /* 此后无法恢复 root */
    serve_requests();
}
