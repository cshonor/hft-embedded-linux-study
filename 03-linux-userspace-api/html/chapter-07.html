章节目标

理解堆与 program break、brk/sbrk；掌握 malloc/calloc/realloc/free；分清用户态分配器与内核虚拟内存交互；虚拟地址 ≠ 立刻占用物理页。

易错清单

  1. brk/sbrk = syscall（内核入口 mm/mmap.c:178）；malloc/free = 库函数（glibc 的 ptmalloc）。
  2. 虚拟 ≠ 物理；抬 break 不立刻吃物理页（延迟分配，见 6.4）。
  3. free 不保证还内核；别用 sbrk(0) 当「真实占用」仪表 —— 用 VmRSS（6.4）。
  4. 勿写 ptr = realloc(ptr, …)：失败时原指针丢失 → 泄漏。用临时变量接。
  5. malloc 返回值满足最大基本对齐（x86-64 上是 16）；要更大对齐用 posix_memalign / aligned_alloc。
  6. 书内 mmap 章是 Ch49，不是 Ch48（Ch48 是 SysV 共享内存）。
  7. 「大块走 mmap」不完整：判据是 nb >= mmap_threshold 且 top chunk 也满足不了（malloc/malloc.c:2564）。见 7.1 要点五。
  8. malloc 不清零，但 glibc 的 tcache 会覆写用户区头部 16 字节 —— 调试时别被前 16 字节骗了。
  9. realloc(p, 0) 标准不统一（C17 及以前实现定义、C23 起 UB）；一律改写 free(p); p = NULL;。
  10. alloca 没有失败返回值，栈不够直接 SIGSEGV；且在循环里不回收（回收粒度是函数返回）。

在堆上分配内存：program break、malloc 族与两条路径

源码核验：Linux v6.6 · mm/mmap.c（SYSCALL_DEFINE1(brk) :178、do_mmap :1203、vm_brk_flags :3150）· glibc 2.39 · malloc/malloc.c（request2size :1314、sysmalloc :2531、mmap 判据 :2564、tcache_put :3157、do_set_mmap_threshold :5442） 本节 6 个演示均在 Compiler Explorer 上真实编译 + 运行（gcc 13.3.0 / x86-64） 本章：TLPI 第 07 章 — Memory Allocation - 上一节：本章首页 - 下一节：7.2 在栈上分配：alloca()

本节讲什么

堆是地址空间里唯一能在运行期自由伸缩的那一段。把它弄清楚，只需要回答四个问题：

  1. 堆的上界在哪，谁在动它？—— program break，入口只有 brk / sbrk。
  2. 日常写的 malloc 到底做了什么？—— 它是库函数，在「扩主堆」和「新开 mmap」之间自己挑。
  3. 为什么 free 之后 sbrk(0) 常常一动不动？—— 小块留在空闲链表里等着被复用。
  4. 写错了会怎样？—— 五类典型错误，用 ASan 抓现场。

要点

一、program break 与两个入口

program break = 进程堆的当前上边界（书里叫「program break」，内核侧就是 mm->brk）。

动作 效果
上移 break 扩大堆，拿到更多虚拟地址
下移 break 缩小堆，把虚拟地址还给内核 
#include <unistd.h>
int   brk(void *end_data_segment);   /* 设成绝对地址：成功 0，失败 -1 */
void *sbrk(intptr_t increment);      /* 相对移动；成功返回「调整前」的 break */
规则 说明
sbrk(0) 不移动断点，只返回当前值 —— 用户态唯一的「查看」手段
sbrk(n) > 0 抬高 n 字节，返回值 = 抬高前的断点（也就是新区域的起点）
失败 返回 (void *) -1，并设 errno = ENOMEM
抬高 ≠ 占物理页 只改虚拟地址；首次访问才通过缺页分配物理页（见 6.4）
下移过猛 把断点压到「glibc 已经用过的堆」下面 → 直接 SIGSEGV（下面有实测）
业务代码 禁止直接用 brk / sbrk —— 堆是 glibc 的地盘，不是你的

最后一条不是教条，是实测出来的：glibc 自己的 stdio 缓冲区就住在堆上，你把 break 降回去，等于把它的数据还给了内核。见 c7_1 的 B 段。

二、malloc / free 的语义

#include <stdlib.h>
void *malloc(size_t size);   /* 未初始化；失败返回 NULL 并设 errno */
void  free(void *ptr);

用户拿到的指针不含分配器头部，元数据躺在用户区前方：

低地址 ┌──────────────────┐
       │ chunk 头（size/   │  ← 分配器私有：大小、bin 链表指针、标志位
       │  bin 指针、标志） │     你越界写这里 → free 时直接崩
       ├──────────────────┤ ← malloc 返回的指针从这里开始
       │ 用户数据          │
       ├──────────────────┤
       │ 对齐填充          │
       └──────────────────┘ 高地址

free 的四条事实：

事实 说明
ptr 必须来自 malloc/calloc/realloc 否则 UB；free 栈地址会被 glibc 的检查拦下（实测见 c7_6）
free(NULL) 安全，空操作
不保证下调 break 小块进空闲链表等着复用；只有堆顶那一大段连续空闲才可能触发 sbrk(-n)
不清零 内容原样留着（信息残留面）；但 glibc 的 tcache 会覆写头部 16 字节，见 c7_4

三、calloc / realloc

函数 语义 要点
calloc(n, s) 分配 n × s 并清零 会检查 n × s 整数溢出 —— 这是它比 malloc + memset 真正强的地方
realloc(p, n) 调整大小 可能原地，也可能「新块 + 拷贝 + 释放旧块」；旧指针一律视为失效
realloc(NULL, n) ≡ malloc(n) 实测确认
realloc(p, 0) 不要用 C17 及以前是实现定义、C23 起是未定义行为；glibc 上等于 free(p) 并返回 NULL 
/* ❌ 失败时原指针丢失 → 泄漏 */
ptr = realloc(ptr, newsize);

/* ✅ 用临时变量接 */
void *np = realloc(ptr, newsize);
if (np == NULL) { /* ptr 仍然有效，自己决定继续用还是 free */ }
else            { ptr = np; }

四、malloc(0)

POSIX 允许返回 NULL 或 一个可 free 的非空指针。glibc 返回非空，所以：

void *p = malloc(0);
free(p);                        /* 必须 free，不能当失败处理 */
/* 但绝不可解引用：请求 0 字节，访问就是 UB */

判断「分配是否失败」的正确姿势是看 errno 或统一判 NULL 并保证 size > 0，而不是拿 malloc(0) 的返回值当信号。

五、两条路径：sbrk 还是 mmap（源码级判据）

glibc 的 malloc 有两条完全不同的取内存路径：

路径 触发时机 特征
扩主堆（sbrk） 请求能从现有 bin / top chunk 满足，或 sysmalloc 判定 nb < mmap_threshold 动 [heap]，free 后常留在空闲链表
新开 mmap sysmalloc 走到 mmap 分支 多一段匿名映射，free 时 munmap 直接还给内核

判据就一句（glibc 2.39 malloc/malloc.c:2564-2565，位于 sysmalloc() 内）：

if ((unsigned long) (nb) >= (unsigned long) (mp_.mmap_threshold)
    && (mp_.n_mmaps < mp_.n_mmaps_max))

这句话有三个必须注意的细节，缺一个就会得出错误结论：

  1. 比的是 nb（chunk 大小），不是请求的 size —— nb = (size + 8 + 15) & ~15（request2size，malloc.c:1314：含 8 字节头，再按 16 对齐）。代入阈值 131072 反推：请求 131049 字节时 nb 恰好够上阈值，131048 的 nb 只有 131056 —— 所以 128 KB 从来不是「请求字节数」的分界线。（这两个数字是按公式推算的，不是观测值；真要观测还得先把 top chunk 耗掉，见 c7_3。）
  2. 它只在 sysmalloc() 里 —— 也就是说，只有现有 bin 和 top chunk 都满足不了时才会被走到。这才是「为什么 16 KB 的分配从来没走 mmap」的真正原因：top 够。
  3. 阈值默认 128 KB（DEFAULT_MMAP_THRESHOLD_MIN，malloc.c:946），且 free() 一个大块时会动态调高它（malloc.c:3380-3384）。要复现实验就必须先 mallopt(M_MMAP_THRESHOLD, 128*1024) 钉死 —— 该调用同时把 mp_.no_dyn_threshold 置 1（malloc.c:5442-5447）。

⚠️ 所以「大块走 mmap」这句简化说法不完整。准确的表述是：当现有空闲空间不够时，看 nb 和 mmap_threshold 谁大。一个 200 KB 的请求也可能先从 top chunk 里切出来。

六、对齐

接口 保证的对齐 备注
malloc / calloc / realloc _Alignof(max_align_t)，x86-64 上 = 16 够放任何标量类型
posix_memalign(&p, align, size) align（必须是 2 的幂且是 sizeof(void*) 的倍数） 成功返回 0，非法对齐返回 EINVAL（不是崩溃）
aligned_alloc(align, size)（C11） align 要求 size 是 align 的整数倍，否则 UB

为什么要更严格的对齐？SIMD（AVX-512 要 64 字节）、DMA / O_DIRECT（要页对齐 4096）、缓存行（要 64 字节，防 false sharing）。

c7_1 归位可以，降过头就崩

完整程序见 ../code/c7_1_program_break.c：先演示 sbrk / brk 的正常语义，再把「break 降过头」放进子进程看后果。

/* Ch7 §7.1 — program break 的查询与调整（brk / sbrk）
 * 编译: gcc -O2 -Wall -Wextra -o c7_1_program_break c7_1_program_break.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

#define PAGE 4096

/* ── A. 安全用法：只在「当前 break 之上」要内存，并只归还到自己的出发点 ── */
static void safe_use(void)
{
    /* 先输出一次，让 stdio 的缓冲区落到堆上。
     * 若把首次输出留到后面，归还 break 时会把 glibc 尚未分配的堆一并砍掉。 */
    printf("A. 安全用法\n");

    char *base = (char *) sbrk(0);      /* 此刻的 break 已包含 stdio 缓冲 */
    printf("   起始 break            = %p\n", (void *) base);

    /* sbrk(+n)：相对移动，成功时返回「调整前」的断点 */
    char *old = (char *) sbrk(16 * PAGE);
    if (old == (char *) -1) { perror("sbrk"); return; }
    printf("   sbrk(+%ld) 返回旧断点 = %p\n", 16L * PAGE, (void *) old);
    printf("   抬高后 break          = %p\n", sbrk(0));
    printf("   返回值 == 旧断点吗    = %s\n", old == base ? "是" : "否");

    /* 新区域可以随意读写：虚拟地址已到手，物理页还没分配 */
    old[0] = 'A';
    old[16 * PAGE - 1] = 'Z';
    printf("   首尾各写一字节        = %c ... %c\n", old[0], old[16 * PAGE - 1]);

    /* 归还：只回到 base（自己的出发点），一字节都不多降 */
    if (brk(base) != 0) { perror("brk"); return; }
    printf("   brk(起始) 后 break    = %p  ← 回到出发点\n\n", sbrk(0));
}

/* ── B. 危险用法：把 break 降到程序启动时的位置，会砍掉 glibc 自己的堆 ── */
static char *g_earliest;        /* main 第一行读到的 break：那时 stdio 缓冲还没分配 */

static void reckless_use(void)
{
    printf("B. 危险用法：把 break 降回「还没用到 stdio」时的位置\n");
    fflush(stdout);
    brk(g_earliest);            /* 连 glibc 的 stdio 缓冲区一起还给内核 */
    printf("   这一行若能看到，说明缓冲区恰好没被砍到\n");
}

int main(void)
{
    g_earliest = (char *) sbrk(0);

    safe_use();

    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) { reckless_use(); return 0; }

    int st = 0;
    waitpid(pid, &st, 0);
    if (WIFSIGNALED(st))
        printf("B. 子进程被信号 %d 杀死。用户态的 stdio 缓冲区也住在堆上，\n"
               "   把 break 降过头 = 把 glibc 自己的数据也还给了内核。\n"
               "   这正是「业务代码禁止直接 brk/sbrk」最硬的理由。\n",
               WTERMSIG(st));
    else
        printf("B. 子进程 exit = %d（这次没崩）\n", WEXITSTATUS(st));
    return 0;
}

   sbrk(+65536) 返回旧断点 = 0x1913000
   抬高后 break          = 0x1923000
   返回值 == 旧断点吗    = 是
   首尾各写一字节        = A ... Z

B. 危险用法：把 break 降回「还没用到 stdio」时的位置
B. 子进程被信号 11 杀死。用户态的 stdio 缓冲区也住在堆上，

解读

  1. sbrk(+65536) 的返回值 0x1913000 等于调用前的 break —— 这不是巧合，是 sbrk 的契约：返回新区域的起始地址。
  2. 0x1913000 → 0x1923000 正好差 0x10000 = 65536，sbrk 按字节数精确移动。
  3. A 段能安全归位，是因为 base 是在首次 printf 之后读的 —— 那时 stdio 的缓冲区（malloc 出来的，就在堆上）已经在 base 以下了。
  4. B 段故意的：g_earliest 在 main 第一行读，那时 stdio 缓冲还没分配；再 brk(g_earliest) 就把 glibc 后来分配的东西全砍了。子进程 SIGSEGV(11) 就是证据。这就是「破坏性使用 brk」的真实代价，比任何警告都有说服力。

c7_2 free 不一定下调 break（TLPI Listing 7-1 精神）

完整程序见 ../code/c7_2_free_and_sbrk.c：分两阶段 —— 1000 个 1 KB 小块、1 个 256 KB 大块，各自看 break 怎么动。

/* Ch7 §7.1 — free() 不一定下调 program break（TLPI Listing 7-1 精神）
 * 编译: gcc -O2 -Wall -Wextra -o c7_2_free_and_sbrk c7_2_free_and_sbrk.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

#define N 1000

static char *g_base;

static void show(const char *tag)
{
    char *now = (char *) sbrk(0);
    printf("%-30s break = %p   (较起点 %+8ld B)\n",
           tag, (void *) now, (long) (now - g_base));
}

int main(void)
{
    static char *ptr[N];

    g_base = (char *) sbrk(0);
    show("启动");

    /* 阶段 1：大量小块 —— 走主堆 */
    for (int i = 0; i < N; i++) {
        ptr[i] = malloc(1024);
        if (ptr[i] == NULL) { perror("malloc"); return 1; }
        ptr[i][0] = 'x';            /* 触碰一下，确保真的占了页 */
    }
    show("malloc(1000 x 1KB) 之后");

    for (int i = 0; i < N; i++)
        free(ptr[i]);
    show("全部 free 之后");

    /* 阶段 2：一个大块 —— 走 mmap，与 program break 无关 */
    char *big = malloc(256 * 1024);
    if (big == NULL) { perror("malloc"); return 1; }
    big[0] = 'y';
    show("malloc(256KB) 之后");

    free(big);
    show("free(256KB) 之后");
    return 0;
}

c7_3 两条路径：[heap] 台阶式长，还是新开匿名段

完整程序见 ../code/c7_3_two_paths.c：A 段连续分配 16 KB × 10，B 段连续分配 256 KB × 4，全程记录 break、[heap] 段、匿名段三个量。

/* Ch7 §7.1 — malloc 的两条路：扩主堆 [heap]，还是新开一段 mmap
 * 编译: gcc -O2 -Wall -Wextra -o c7_3_two_paths c7_3_two_paths.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>

/* 直接 open/read 读 /proc/self/maps。
 * 不用 fopen —— 它自己会 malloc 一块缓冲，反而污染我们要观测的堆。 */
static long maps_kb(int which)          /* which: 0 = 匿名段, 1 = [heap] */
{
    int fd = open("/proc/self/maps", O_RDONLY);
    if (fd < 0) return -1;

    static char buf[65536];             /* 静态区，不占堆 */
    ssize_t n = read(fd, buf, sizeof buf - 1);
    close(fd);
    if (n <= 0) return -1;
    buf[n] = '\0';

    long kb = 0;
    char *line = buf;
    while (line != NULL && *line != '\0') {
        char *nl = strchr(line, '\n');
        if (nl != NULL) *nl = '\0';

        unsigned long a = 0, b = 0;
        if (sscanf(line, "%lx-%lx", &a, &b) == 2) {
            long size = (long) ((b - a) / 1024);
            if (which == 1) {
                if (strstr(line, "[heap]") != NULL) kb += size;
            } else {
                char *last = strrchr(line, ' ');
                if (last == NULL || *(last + 1) == '\0')
                    kb += size;         /* 没有名字 = 匿名映射 */
            }
        }
        line = (nl != NULL) ? nl + 1 : NULL;
    }
    return kb;
}

int main(void)
{
    printf("初始    break=%p   [heap]=%5ld KB   匿名段=%5ld KB\n\n",
           sbrk(0), maps_kb(1), maps_kb(0));

    /* A. 连续小块：主堆一台阶一台阶地长 */
    puts("A. malloc(16KB) x 10，都不 free：");
    for (int i = 0; i < 10; i++) {
        char *p = malloc(16 * 1024);
        if (p == NULL) { perror("malloc"); return 1; }
        memset(p, 'a', 16 * 1024);
        printf("   #%-2d   break=%p   [heap]=%5ld KB   匿名段=%5ld KB\n",
               i + 1, sbrk(0), maps_kb(1), maps_kb(0));
    }

    /* B. 大块：每次都在别处新开一段匿名映射，主堆纹丝不动 */
    puts("\nB. malloc(256KB) x 4，都不 free：");
    for (int i = 0; i < 4; i++) {
        char *p = malloc(256 * 1024);
        if (p == NULL) { perror("malloc"); return 1; }
        memset(p, 'b', 256 * 1024);
        printf("   #%-2d   break=%p   [heap]=%5ld KB   匿名段=%5ld KB\n",
               i + 1, sbrk(0), maps_kb(1), maps_kb(0));
    }
    return 0;
}

c7_4 malloc 家族语义实测

完整程序见 ../code/c7_4_malloc_family.c：8 个小实验，把 malloc(0)、不清零、calloc 溢出保护、realloc 的四种情形一次测完。

/* Ch7 §7.1 — malloc / calloc / realloc / malloc(0) 的语义实测
 * 编译: gcc -O2 -Wall -Wextra -o c7_4_malloc_family c7_4_malloc_family.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>

int main(void)
{
    /* 1) malloc(0)：glibc 返回可 free 的非空指针，不能当失败处理 */
    void *z = malloc(0);
    printf("1) malloc(0) = %p (%s)\n", z,
           z ? "非 NULL，必须 free" : "NULL");
    free(z);

    /* 2) malloc 不清零 —— 但 glibc 的 tcache 会覆写块的头部 16 字节 */
    char *a = malloc(32);
    memcpy(a, "SECRET-TOKEN-1234", 17);
    memcpy(a + 16, "LEFTOVER!", 9);     /* 放到 tcache 元数据之后 */
    printf("2) free 后重新 malloc：a = %p\n", (void *) a);
    free(a);
    char *b = malloc(32);               /* 大概率拿到同一个块 */
    printf("   b = %p  (与 a 同址 = %s)\n", (void *) b, a == b ? "是" : "否");
    printf("   b 的前 32 字节:");
    for (int i = 0; i < 32; i++)
        printf(" %02x", (unsigned char) b[i]);
    printf("\n");
    printf("   b[16] 起的字符串 = %.8s   <- 残留未被清零\n", b + 16);
    free(b);

    /* 3a) calloc 清零 */
    int *arr = calloc(8, sizeof(int));
    printf("3a) calloc(8, 4) 全零 = %s\n",
           (arr[0] | arr[7]) == 0 ? "是" : "否");
    free(arr);

    /* 3b) calloc 的溢出保护：n*s 回绕时返回 NULL，而不是「成功」一个小块。
     * 用非 const 变量传参，绕开编译器的静态检查，让行为在运行期体现。 */
    volatile size_t nmemb = SIZE_MAX, elem = 2;
    void *ovf = calloc(nmemb, elem);
    printf("3b) calloc(SIZE_MAX, 2) = %p (%s)\n", ovf,
           ovf == NULL ? "溢出被拦下" : "竟然成功 → 危险");
    free(ovf);

    /* 4) realloc(NULL, n) 等价 malloc(n) */
    int *p = realloc(NULL, 64);
    printf("4) realloc(NULL, 64) = %p (%s)\n", (void *) p,
           p ? "等价 malloc" : "失败");
    p[0] = 7;

    /* 5) realloc 缩容：通常原地，指针不变。
     * 旧地址先存成整数；返回值另起一个变量接，
     * 免得编译器把「realloc 之后还碰旧指针」判成 use-after-free。 */
    uintptr_t b5 = (uintptr_t) p;
    int *q5 = realloc(p, 16);
    if (q5 == NULL) { perror("realloc"); return 1; }
    printf("5) realloc(64->16) 指针%s: %p -> %p\n",
           ((uintptr_t) q5 == b5) ? "不变" : "改变",
           (void *) b5, (void *) q5);
    p = q5;

    /* 6) realloc 扩容：旧数据保留，指针通常变（跨区搬移） */
    for (int i = 0; i < 4; i++) p[i] = i + 1;
    uintptr_t b6 = (uintptr_t) p;
    int *q6 = realloc(p, 1024 * 1024);
    if (q6 == NULL) { perror("realloc"); return 1; }
    printf("6) realloc(16->1MB) 指针%s: %p -> %p; 旧数据 = %d %d %d %d\n",
           ((uintptr_t) q6 == b6) ? "不变" : "改变",
           (void *) b6, (void *) q6, q6[0], q6[1], q6[2], q6[3]);
    p = q6;
    free(p);

    /* 7) realloc(p, 0)：glibc 释放 p 并返回 NULL（此后 p 已成悬垂） */
    void *q = malloc(128);
    void *r = realloc(q, 0);
    printf("7) realloc(p, 0) = %p (%s)\n", r,
           r == NULL ? "glibc：已释放并返回 NULL" : "返回了非 NULL 指针");
    if (r != NULL) free(r);             /* 非 glibc 实现下才需要 */

    /* 8) free(NULL) 是空操作 */
    free(NULL);
    printf("8) free(NULL) 未崩溃\n");
    return 0;
}

解读

所以「malloc 不清零」这句话要修正得更精确：用户区头部 16 字节会被 glibc 自己覆写，16 字节之后才是原样残留。安全上是坏事（信息泄漏面），调试时是好事（能看出这块内存的上一个住户）。 2. 第 3b 条是 calloc 存在的真正理由：SIZE_MAX × 2 回绕后是 SIZE_MAX - 1，一个天真的实现会「成功」返回一个巨块 —— calloc 内部做了溢出检查，直接返回 NULL。malloc(n*s) + memset 没有这层保护。 3. 第 5 / 6 条的对照说明 realloc 的行为不统一：缩容原地（指针不变），扩容跨区搬移（指针从 0x1c6b8330 跳到 mmap 区的 0x7c5874aff010，旧数据 1 2 3 4 完整带过去）。所以旧指针必须视为失效。 4. 第 7 条实测确认 glibc 的 realloc(p, 0) = free(p) + 返回 NULL。 5. ⚠️ 这份源码在 -O2 -Wall -Wextra 下会报 2 条 -Wuse-after-free（"pointer 'p'/'q5' may be used after 'realloc'"）。它不是代码写错 —— 我们只是把 realloc 前后的地址都拿去打印，而 GCC 的指针分析无法区分「打印地址值」和「解引用」。但这条警告指向的规则是真的：realloc 之后旧指针失效。生产代码里如果它真的报了，请当成真 bug 查。

c7_5 对齐

/* Ch7 §7.1 — 对齐分配：malloc 的默认对齐 vs posix_memalign / aligned_alloc
 * 编译: gcc -O2 -Wall -Wextra -o c7_5_memalign c7_5_memalign.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stddef.h>
#include <stdint.h>

int main(void)
{
    /* malloc 保证的对齐 = max_align_t 的对齐（x86-64 上为 16） */
    printf("_Alignof(max_align_t) = %zu\n\n", _Alignof(max_align_t));

    /* 连续 8 次 malloc(1)，看地址低 4 位 */
    printf("malloc(1) 连续 8 次的地址（低 4 位应恒为 0）:\n");
    void *ps[8];
    for (int i = 0; i < 8; i++) {
        ps[i] = malloc(1);
        printf("   %p   低4位 = %zu\n", ps[i], (uintptr_t) ps[i] & 0xf);
    }
    for (int i = 0; i < 8; i++) free(ps[i]);

    /* posix_memalign：成功返回 0，失败返回 errno 值（不是设 errno） */
    size_t align = 4096;
    void *pg = NULL;
    int rc = posix_memalign(&pg, align, 100);
    if (rc != 0) { fprintf(stderr, "posix_memalign: %s\n", strerror(rc)); return 1; }
    printf("\nposix_memalign(4096, 100) = %p,  %% 4096 = %zu\n",
           pg, (uintptr_t) pg % align);
    free(pg);

    /* 非法对齐（不是 2 的幂）→ 返回 EINVAL，不是崩溃 */
    void *bad = NULL;
    rc = posix_memalign(&bad, 100, 64);
    printf("posix_memalign(100, 64) rc = %d (%s)\n", rc,
           rc ? "EINVAL，被拒绝" : "竟然成功");
    free(bad);

    /* aligned_alloc (C11)：要求 size 是 align 的整数倍 */
    void *av = aligned_alloc(64, 64 * 4);
    printf("aligned_alloc(64, 256) = %p,  %% 64 = %zu\n",
           av, (uintptr_t) av % 64);
    free(av);
    return 0;
}

{
    char *raw = malloc(8);
    volatile char *p = raw;
    p[16] = 'x';                        /* 越界 8 字节，落在 ASan 的 redzone 里 */
    free(raw);
}

/* 2. use-after-free */
static void case_uaf(void)
{
    char *p = malloc(32);
    free(p);
    printf("     (uaf) 释放后读到的字节 = %d\n", p[0]);
}

/* 3. double free */
static void case_double_free(void)
{
    char *p = malloc(32);
    printf("     (df) 第一块 %p\n", (void *) p);
    free(p);
    free(p);
}

/* 4. 内存泄漏：
 *    大多数 ASan 环境在进程退出时由 LSan 汇报泄漏，但有些容器里
detect_leaks 默认是关的（实测 Compiler Explorer 就是）。
 *    所以这里换成不依赖工具的观测法：看 RSS 涨不涨。 */
static long rss_kb(void)
{
    FILE *f = fopen("/proc/self/statm", "r");
    if (f == NULL) return -1;
    long total = 0, resident = 0;
    if (fscanf(f, "%ld %ld", &total, &resident) != 2) resident = -1;
    fclose(f);
    return resident * (sysconf(_SC_PAGESIZE) / 1024);
}

static void case_leak(void)
{
    long before = rss_kb();
    for (int i = 0; i < 1000; i++) {
        void *p = malloc(4096);         /* 指针当场丢失 */
        if (p != NULL) memset(p, 1, 4096);  /* 真碰，否则物理页不会到手 */
    }
    printf("     (leak) 1000 x 4KB 分配后不释放：RSS %+ld KB\n",
           rss_kb() - before);
    fflush(stdout);                     /* LSan 报错后直接 _exit，缓冲会丢 */
#ifdef __SANITIZE_ADDRESS__
    __lsan_do_leak_check();             /* 环境若开了 LSan，这里会额外报一份 */
#endif
}

/* 5. free 一个非堆指针（这里是栈地址） */
static void case_invalid(void)
{
    int on_stack = 42;
    free(&on_stack);
}

static const struct { const char *name; void (*fn)(void); } CASES[] = {
    { "(无)",                            NULL },
    { "越界写     heap-buffer-overflow",  case_oob },
    { "释放后使用 heap-use-after-free",   case_uaf },
    { "重复释放   double-free",           case_double_free },
    { "内存泄漏   leak",                  case_leak },
    { "free 非堆  bad-free",              case_invalid },

int main(void)
{

}

解读

  1. 五类错误里，glibc 自己能立刻拦下的只有 double-free 和 bad-free —— 它检查 tcache key、检查指针是否真的有 chunk 头，不合法就直接 abort。而越界写和 use-after-free 在默认配置下可以悄无声息地活很久（碰坏了邻居的 chunk 头，往往到下一次 free 才炸）；泄漏则永远不报。ASan 的价值就是把其中 4 类提前到现场。
  2. 每一类都给了从分配到出错的完整调用栈（上面省略了中间的 frame）：allocated by → freed by → READ of size 1。这是 ASan 相对 valgrind 的优势（不用跑两遍、报告更短）。
  3. 踩到的坑：Compiler Explorer 上 ASan 的 detect_leaks 默认是关的 —— 程序正常退出时不会报泄漏。解法是显式调用 __lsan_do_leak_check()（<sanitizer/lsan_interface.h>，用 #ifdef __SANITIZE_ADDRESS__ 包起来）。实测这样就能拿到 4096000 byte(s) in 1000 object(s) 的精确报告。
  4. 另一个坑：ASan 报错后直接 _exit，不 flush stdio —— 前面 printf 的内容会全部丢失。所以 CASE 4 里在 __lsan_do_leak_check() 之前加了 fflush(stdout)。（c7_1 的 B 段也是另一种「输出突然没了」，但那里的机制是缓冲区被 unmap 掉，不是没 flush —— 两个坑别混。）
  5. 泄漏还有个不依赖任何工具的证据：RSS 涨了 5796 KB（1000 × 4 KB = 4096 KB 用户数据，其余是 ASan 的 redzone / 影子内存 / 分配器元数据等开销）。泄漏 的本质就是「这些页一直占着不还」。

HFT / 嵌入式关联

  • 热路径上不要有 malloc。分配器最坏情况是 O(链长) 的搜索 + 不可预测的 sbrk / mmap 系统调用 —— 后者在 HFT 里就是几十微秒的抖动。做法是预分配 arena / 固定大小对象池，启动时一次性拿到。
  • 想避免碎片就绕开主堆：大于阈值的分配直接走去 mmap（free 时完整归还内核），这也是 jemalloc / tcmalloc 按 size class 切分的思路。
  • 大页：HFT 的关键数据结构用 mmap(MAP_HUGETLB) 或 madvise(MADV_HUGEPAGE)，直接降低 TLB miss —— 那是 Ch49 / Ch50 的地盘。
  • 嵌入式：无 MMU 的平台（uClinux）没有 brk，heap 只能靠 mmap 或静态池。堆上还有一个隐形代价 —— 碎片在长时间运行的小内存设备上是致命伤，通常直接禁用 malloc。
  • malloc(0) / realloc(p, 0) 这类边角在跨平台代码里是雷：标准不统一，glibc / BSD 行为不同。写法上统一成显式 free + malloc 最省心。
  • ASan 要进 CI：本节五类错误里有三类在默认 glibc 下不会立刻报错，靠人眼 review 是抓不住的。

自测题

1. free(p) 之后 sbrk(0) 完全没变，说明内存没被释放吗？

不是。 free 把一个块标记为空闲并交回 glibc 的空闲链表，只改分配器自己的数据结构，不碰 program break。只有「堆顶那一段连续空闲」大到值得归回时，glibc 才可能调 sbrk(-n)。

实测（c7_2）：malloc(1000 × 1KB) 把 break 抬高 1081344 字节，全部 free 之后只降到 +143360 字节 —— 还留着 140 KB 在链表里复用。这正是「分配器用空间换系统调用」的策略。

要判断内存是否真被释放，看 free 之后能不能被下一次 malloc 复用，或者读 /proc/self/status 的 VmRSS。

2. 一个 200 KB 的 malloc，一定会走 mmap 吗？

不一定。 判据不是「请求大小 vs 128 KB」，而是（malloc.c:2564）：

if ((unsigned long)(nb) >= (unsigned long)(mp_.mmap_threshold) && ...)

三处关键： 1. 比的是 nb（chunk 大小，含 8 字节头部并向上取整 16），不是请求的 size； 2. 这句话只在 sysmalloc() 里，也就是只有现有 bin 和 top chunk 都满足不了时才会被走到； 3. 阈值还会被 free() 大块时的动态调整改掉（malloc.c:3380）。

所以如果进程的 top chunk 里恰好有 200 KB 空闲，这个请求会直接从 top 切，两条系统调用路径都不走。实测中 256 KB 的请求每次都走 mmap，是因为 nb ≈ 262176 比 [heap] 里剩余的可用空间大得多（初始 [heap] 映射 132 KB，A 段再消耗 160 KB 之后更少）。

3. calloc(n, s) 和 malloc(n*s) + memset 相比，安全性上强在哪？

整数溢出检查。

n * s 在 size_t 上回绕后可能变成一个小数字。天真的实现 malloc(n*s) 会「成功」返回一个远小于预期的块，随后按原尺寸写就越界 —— 这是一类经典的可利用漏洞。

实测（c7_4 第 3b 条）：calloc(SIZE_MAX, 2) 返回 NULL（溢出被拦下），而不是返回一个回绕后的小块。

性能上还有个附带好处：大块 calloc 走 mmap 时，内核给的匿名页本来就是清零的，glibc 可以省掉 memset。

4. 为什么说「业务代码禁止直接调用 brk / sbrk」？

因为堆不是你一个人的。glibc 的分配器在你的进程里维护着一整套状态（top chunk、各个 bin、tcache），stdio 的缓冲区、fopen 的 FILE 结构等全都在堆上。

你要是直接把 break 降回去，就等于把它们脚下的虚拟地址还给了内核。实测（c7_1 B 段）：子进程在 brk(最早记录的值) 之后 被信号 11 杀死 —— 它连一行 printf 都写不出来了。

要拿更多内存，用 malloc；要拿一段独立的大内存，用 mmap。brk / sbrk 只在读（sbrk(0) 看边界、理解 malloc 行为）时才有用。

7.2

在栈上分配：`alloca()`

源码核验：glibc 2.39 · stdlib/alloca.h:32（extern void *alloca (size_t __size)）· :35（GCC 下 #define alloca(size) __builtin_alloca (size)）· include/alloca.h:18（__libc_use_alloca）/ :22（__MAX_ALLOCA_CUTOFF 65536） 本节数据由 Compiler Explorer 实测（gcc 13.3.0 / x86-64） 本章：TLPI 第 07 章 — Memory Allocation - 上一节：7.1 在堆上分配内存 - 下一节：7.3 本章小结

本节讲什么

alloca 走的是和 malloc 完全相反的路线：不动堆，只挪栈指针。

一句话语义（glibc 头文件里的注释原文）：

/* Allocate a block that will be freed when the calling function exits.  */
extern void *alloca (size_t __size) __THROW;

#ifdef  __GNUC__
# define alloca(size)   __builtin_alloca (size)
#endif /* GCC.  */

记住这句注释里的两个词：freed when the calling function exits —— 回收的粒度是函数返回，不是作用域结束，更不是 free。这一节的所有反直觉现象都从这句话长出来。

⚠️ 首先明确：alloca 不是标准 C，也不是 POSIX。它是编译器扩展 —— glibc 只是提供了一个头文件把它接到 GCC 的 __builtin_alloca（stdlib/alloca.h:35）。换编译器（MSVC 没有，一些嵌入式工具链也没有）就不存在，跨平台代码里不要用。

要点

一、它比 malloc 快在哪

维度 alloca malloc
分配动作 调整 rsp（一条 sub，通常无函数调用） 查 bin / top chunk，必要时 sbrk / mmap
分配位置 当前函数的栈帧 堆（或新的 mmap 段）
释放动作 函数返回时自动（leave 一条指令弹回） 手动 free，进空闲链表
释放粒度 整个函数（不是作用域！） 任意时刻、任意顺序
能否泄漏 不可能 可能
上限 RLIMIT_STACK（默认 8 MB） 虚拟地址空间 + 物理内存 + swap
失败表现 没有失败 —— 直接 SIGSEGV 返回 NULL + errno
标准性 ❌ 非标准扩展 ✅ C 标准

为什么快：malloc 最坏情况要沿着 bin 链找块，再可能要一次系统调用；alloca 只是把栈指针往下挪 size 字节（还要按 16 对齐处理一下）。

二、和 C99 VLA 的关系

C99 的变长数组（VLA）和 alloca 是同一种机制的两张皮 —— 都在栈上、都靠挪 rsp：

int n = 10;
int arr[n];             /* VLA：一次分配 n*sizeof(int)，随作用域结束失效 */
void *p = alloca(n * sizeof(int));   /* 等价，但指针活到函数返回 */
VLA alloca
标准 C99 起是标准（C11 起可选） 非标准
存活期 作用域（C99 说声明所在块的末尾） 函数返回
位置 栈 栈
能否返回指针给调用者 不能 不能

⚠️ 别被「VLA 随作用域结束」误导成「栈内存被回收了」—— 它只是名字不可见了，rsp 并没有动。两者在物理上都没回收。

三、三条硬限制（每一条都有实测）

1. 没有任何错误检查

malloc 失败会返回 NULL，你可以处理。alloca 没有返回值可以判：栈不够就直接撞进 guard page → SIGSEGV。

实测（c7_7 的 C 段，8 MB 栈上要 16 MB）：

C. alloca(16MB)，栈只有 8MB ...
C. 子进程被信号 11 (SIGSEGV) 杀死 → 栈溢出没有「优雅失败」的途径

2. 不能跨函数

void *bad(void) {
    return alloca(100);      /* ❌ 返回的指针指向已经消失的栈帧 */
}

alloca 申请的内存在当前函数返回时就被弹掉了。把指针传出去（返回、存进全局、塞进链表），调用者一用就踩别人的栈帧 —— 而且这种 bug 常常「看起来能跑」，直到调用栈变了才崩。

3. 循环里不回收，会累积

回收粒度是函数返回，所以循环里每次 alloca 都真的往下走一段，一路不回头：

实测（c7_7 的 B 段，循环 5 次 alloca(4096)）：

B. 循环里 alloca(4096) 五次：
   i=0  p=0x7ffd2a1c8d60  与前次相差 +0
   i=1  p=0x7ffd2a1c7d50  与前次相差 -4112
   i=2  p=0x7ffd2a1c6d40  与前次相差 -4112
   i=3  p=0x7ffd2a1c5d30  与前次相差 -4112
   i=4  p=0x7ffd2a1c4d20  与前次相差 -4112

每次固定下移 4112 字节（4096 + 16 对齐开销），5 次就是 20 KB，全部留在栈上。所以「循环里用 alloca」等于「手写一个会爆栈的循环」—— 循环次数不可控时这是致命的。

/* Ch7 §7.2 — alloca：栈上分配，函数返回才回收
 * 编译: gcc -O2 -Wall -Wextra -o c7_7_alloca c7_7_alloca.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <signal.h>
#include <alloca.h>
#include <sys/resource.h>
#include <sys/wait.h>

static volatile char g_sink;

/* ── A. alloca 的地址落在哪个区 ── */
static void where_is_alloca(void)
{
    char local[16];
    char *h = malloc(16);
    char *s = alloca(16);

    printf("A. 栈上局部变量 local = %p\n", (void *) local);
    printf("   alloca(16)        = %p   ← 与 local 同区，即栈\n", (void *) s);
    printf("   堆上 malloc(16)   = %p   (与 local 相距 %ld 字节)\n",
           (void *) h, (long) ((char *) h - (char *) local));
    printf("   alloca 与 local 相距 %ld 字节\n\n", (long) (s - local));
    free(h);
}

/* ── B. 循环里 alloca：不会在每次迭代结束回收 ── */
static void alloca_in_loop(void)
{
    printf("B. 循环里 alloca(4096) 五次：\n");
    char *prev = NULL;
    for (int i = 0; i < 5; i++) {
        char *p = alloca(4096);
        memset(p, i, 4096);             /* 防优化：真去碰这块内存 */
        printf("   i=%d  p=%p  与前次相差 %+ld\n", i, (void *) p,
               prev ? (long) (p - prev) : 0L);
        prev = p;
    }
    printf("   → 差值是个固定量：上一轮的块没有被回收。\n");
    printf("     alloca 只挪 sp，回收要等整个函数返回时一次性弹回。\n");
    printf("     （栈向低地址增长，所以差值是负的；多出的部分是对齐开销。）\n\n");
}

/* ── C. alloca 超大 → 直接 SIGSEGV，没有任何返回值可检查 ── */
static void alloca_huge(void)
{
    size_t mb = 16;                     /* 默认栈只有 8MB */

    printf("C. alloca(%zuMB)，栈只有 8MB ...\n", mb);
    fflush(stdout);

    size_t bytes = mb * 1024 * 1024;
    char *p = alloca(bytes);

    /* 逐页用 volatile 写：否则编译器会把「只写不读」的这段当死代码删掉，
     * 一页都不会真碰到，栈也就永远溢不出去。 */
    volatile char *vp = p;
    for (size_t i = 0; i < bytes; i += 4096)
        vp[i] = 'x';
    g_sink = vp[0];
    printf("   竟然没崩\n");
}

/* ── D. VLA 与 alloca 都在栈上，方向相反 ── */
static void vla_demo(int n)
{
    char vla[n];                        /* C99 VLA，同样在栈上 */
    memset(vla, 'v', sizeof vla);
    char *a = alloca(sizeof vla);
    printf("D. VLA[%d] = %p, alloca 同尺寸 = %p, 相差 %ld\n",
           n, (void *) vla, (void *) a, (long) (a - vla));
    printf("   （都落在栈上；栈向低地址增长，所以后分配的在更低处）\n\n");
}

int main(void)
{
    struct rlimit rl;
    if (getrlimit(RLIMIT_STACK, &rl) == 0) {
        if (rl.rlim_cur == RLIM_INFINITY)
            printf("本进程 RLIMIT_STACK = 不限制\n\n");
        else
            printf("本进程 RLIMIT_STACK = %lu MB\n\n",
                   (unsigned long) (rl.rlim_cur / 1024 / 1024));
    }

    where_is_alloca();
    alloca_in_loop();
    vla_demo(256);

    /* C 段放子进程里跑，父进程负责报告死因 */
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) { alloca_huge(); return 0; }

解读

  1. A 段一眼看出「在栈上」：alloca(16) 拿到 0x7ffd2a1c9d40，和局部变量 local（0x7ffd2a1c9d60）同一个 0x7ffd... 区间，只差 32 字节；而 malloc(16) 在 0x21a372b0 —— 两地相差约 1.4 × 10¹⁴ 字节。这就是「堆在低地址、栈在高地址」的字面形态（见 6.3）。 - alloca 与 local 相差 −32：负数说明向低地址（x86-64 栈向下长），32 是 alloca 的对齐调整量。
  2. B 段的 −4112 是本节最值得记的数字：4096 是请求量，多出的 16 是对齐开销。五次迭代一次都没回收 —— 这就是「回收粒度是函数返回」的实测形态。若把 5 换成 100000，在 8 MB 栈上就会中途崩掉。
  3. D 段证明 VLA 与 alloca 同为栈分配：VLA[256] 与 alloca(256) 相差 −272，两者都在 0x7ffd... 区间。272 = 256 + 16 的对齐与临时变量开销。
  4. C 段是「没有错误检查」的实证：16 MB > RLIMIT_STACK（8 MB），子进程被 信号 11 杀死。对比 malloc(16MB) —— 那个会成功返回（虚拟地址而已，物理页欠着，实测见 6.4：malloc(128MB) 后 RSS 只涨 0.1 MB），根本不会崩。这是两种分配方式最根本的分野。
  5. 为什么 C 段要放进子进程：栈溢出会杀掉整个进程，父进程负责 wait 并报告 WTERMSIG，这样「死因」还能被打印出来（同样的手法见 6.5 的爆栈实验）。
  6. 为什么 C 段要逐页用 volatile 写：alloca 只挪 rsp，若不真去碰内存，GCC 会把这个「只分配不使用」的调用当成死代码删掉 —— 一页都不碰，栈自然也溢不出去。这一点调试时很容易被误导。

HFT / 嵌入式关联

  • alloca 是「确定性分配」：一条 sub rsp 指令，没有锁、没有 bin 搜索、没有系统调用 —— 延迟是可预测的常量。这是它对 HFT 唯一的吸引力。
  • 但它把风险从「运行期失败」换成了「崩溃」：malloc 失败你能降级（拒绝这笔报单），alloca 失败直接 SIGSEGV 丢掉整个进程。在交易系统里后者通常更不可接受，所以热路径的常见做法是预分配固定池，而不是 alloca。
  • 栈大小是被线程限定的：主线程用 RLIMIT_STACK（默认 8 MB），每个新线程的栈默认只有 8 MB 甚至更小（pthread_attr_setstacksize 可调）。在多线程里用 alloca 要按那个线程的栈算，别按主线程的算。
  • 嵌入式：很多小型工具链根本没有 alloca（非 GCC 系）。而且任务是长期运行的，一次栈溢出的后果比一次 malloc 失败严重得多 —— 所以嵌入式代码里 alloca 更是罕见。
  • 例外：alloca 在信号处理器里是危险动作（信号可能在任何栈深度上到达），TLPI 在讲信号时专门提过。若信号处理器需要缓冲，用静态缓冲区或 sigaltstack。

自测题

1. alloca(4096) 在循环里跑 1000 次，会怎样？

栈上会累积 1000 × 4112 ≈ 4 MB，一路不回收 —— 因为 alloca 的回收粒度是函数返回，不是循环体结束、也不是作用域结束。

实测（5 次迭代）：每次固定下移 4112 字节（4096 请求 + 16 对齐开销）。

在 8 MB 栈上跑 1000 次就会中途撞进 guard page → SIGSEGV。而且没有任何办法提前知道（没有返回值、没有 errno）。

正确做法：把 alloca 挪到循环外（分配一次，复用它），或者改用 malloc / 固定大小的栈上数组。

2. 为什么 alloca 失败时不返回 NULL？

因为它根本不是函数调用。glibc 把它映射成 GCC 的 __builtin_alloca（stdlib/alloca.h:35），编译器直接生成「调整 rsp」的指令序列 —— 没有函数体、没有返回值路径，自然也没有检查失败的机会。

后果：栈不够时，新的 rsp 会落在内核为栈预留的 guard page 上。硬件在真正访问时发现页不可读写 → 触发页错误 → 内核送 SIGSEGV。

对比 malloc：堆的上限可以检查（sbrk 返回 -1），所以 malloc 有失败路径。这就是「栈分配快但不安全」的本质。

3. glibc 自己在 64 KB 以上就不敢用 alloca 了，这说明什么？

看 include/alloca.h:18/:22：

extern int __libc_use_alloca (size_t size) __attribute__ ((const));
#define __MAX_ALLOCA_CUTOFF 65536

printf 这类需要临时缓冲的 glibc 函数，会先用 __libc_use_alloca(size) 判断：size 超过 64 KB 就走 malloc。

这说明两点：

  1. alloca 的甜区是「小块 + 临时 + 同一函数内」 —— 大到一定程度，栈溢出的风险就压过了「快」的收益，连 libc 作者都选择退回到 malloc。
  2. 它给了一个保守的工程阈值参考：你自己写代码时，若某个 alloca 的尺寸可能超过几 KB 且来源不可控，就该考虑换方案。

自测题

1. calloc(n, sz) 和 malloc(n*sz) + memset 的区别？
  • 安全性：calloc 会检查 n × sz 的整数溢出（实测 calloc(SIZE_MAX, 2) 返回 NULL）；malloc(n*sz) 会回绕成一个小值然后「分配成功」，随后按原尺寸写就越界。
  • 性能：大块 calloc 走 mmap 时，内核给的匿名页本来就是清零的（见 6.4 的零页机制），glibc 可以省掉实际的 memset。
  • 语义：一次调用 vs 两次调用，后者在中间窗口里指针未初始化。
2. realloc 搬移内存后，原指针是什么状态？

失效（dangling）。只要 realloc 返回了一个新地址，旧块就已经被自动释放，旧指针不可再解引用 —— 标准里连"访问旧指针"都算 UB，即使这次刚好原地没搬。

如果 realloc 失败（返回 NULL），原内存仍然有效，需要你自己 free。

实测（c7_4 第 6 条）：realloc(16 → 1MB) 把指针从堆区的 0x1c6b8330 换成 mmap 区的 0x7c5874aff010，旧数据 1 2 3 4 完整带了过去。

3. alloca 的优势和硬限制？

优势：只挪一下 sp（一条指令），比 malloc 快一个数量级；函数返回自动回收，不可能泄漏。

硬限制（三条都是实测确认的）：

  1. 没有错误检查 —— 不像 malloc 返回 NULL，栈不够时直接 SIGSEGV（实测 alloca(16MB) 在 8MB 栈上被信号 11 杀死）。
  2. 不能跨函数 —— 返回指向栈的指针，调用者一用就踩别人的栈帧。
  3. 循环里不回收 —— 回收粒度是函数返回，不是作用域结束。实测循环 5 次 alloca(4096)，地址每次固定下移 4112 字节，一路涨不回头。

另外它是非标准扩展（POSIX 也没有）；GCC 下 glibc 把它映射到 __builtin_alloca（stdlib/alloca.h:35）。

4. 为什么「大块走 mmap」这句话不严谨？

因为 mmap 判据在 sysmalloc() 里（malloc/malloc.c:2564），只有现有 bin 和 top chunk 都满足不了时才会被走到；而且比的是 nb（chunk 大小），不是请求的 size，阈值还会被 free() 大块时动态调高。

所以一个 200 KB 的请求，如果 top chunk 里正好有地方，它会直接从 top 切 —— 既不动 [heap] 的系统调用，也不开匿名映射。

实测（c7_3）：16 KB × 10 全都从 [heap] 里切（[heap] 只在 top 用尽时台阶式跳两级）；256 KB × 4 每次都走 mmap，因为 nb ≈ 262176 远比 [heap] 里剩下的可用空间大。

ALIGN_UP(100) 112 (100 + 15) & ~15
ALIGN_UP(200) 208 (200 + 15) & ~15

于是 my_malloc(200) 与 my_malloc(100) 的地址差应该是 32 + 208 = 240，而 my_malloc(100) 和它前面那块的差是 32 + 112 = 144。这两个数字下面有实测核对。

⚠️ 第一版草稿最容易错的地方就是忘了把 META 也对齐：sizeof(block_t) = 24 不是 16 的倍数，直接用它做步长，第二块的地址就不再是 16 对齐了，后面 malloc 出来的指针一用 SIMD 就崩。

完整实现

完整程序见 ../code/ex7_1_simple_malloc.c。

/* TLPI Ch7 练习 1 参考实现：用 sbrk + 空闲链表做 my_malloc / my_free
 * 编译: gcc -O2 -Wall -Wextra -o ex7_1 ex7_1_simple_malloc.c
 */
#include <stdio.h>
#include <unistd.h>
#include <stdint.h>

typedef struct block {
    size_t size;                /* 数据区大小（字节） */
    int free;                   /* 是否空闲 */
    struct block *next;         /* 下一个块（含已分配的，方便遍历） */
} block_t;

#define ALIGN       16
#define ALIGN_UP(x) (((x) + (ALIGN - 1)) & ~((size_t) ALIGN - 1))
#define META        ALIGN_UP(sizeof(block_t))   /* 头部也要对齐到 16 */

static block_t *g_head;

void *my_malloc(size_t size)
{
    size = ALIGN_UP(size);
    if (size == 0) size = ALIGN;

    /* 第一遍：在链表里找一块够大且空闲的 */
    for (block_t *b = g_head; b != NULL; b = b->next) {
        if (!b->free || b->size < size) continue;

        /* 剩得够多就切开，后半段变成新的空闲块 */
        if (b->size >= size + META + ALIGN) {
            block_t *split = (block_t *) ((char *) b + META + size);
            split->size = b->size - size - META;
            split->free = 1;
            split->next = b->next;
            b->next = split;
            b->size = size;
        }
        b->free = 0;
        return (char *) b + META;
    }

    /* 第二遍：没有合适的，直接向内核要 */
    block_t *b = (block_t *) sbrk(0);
    if (sbrk((intptr_t) (META + size)) == (void *) -1)
        return NULL;

    b->size = size;
    b->free = 0;
    b->next = g_head;           /* 头插，省事 */
    g_head  = b;
    return (char *) b + META;
}

void my_free(void *ptr)
{
    if (ptr == NULL) return;

    block_t *b = (block_t *) ((char *) ptr - META);
    b->free = 1;

    /* 合并「当前块 + 紧邻的下一块」这一种情况，够用了 */
    if (b->next != NULL && b->next->free
        && (char *) b + META + b->size == (char *) b->next) {
        b->size += META + b->next->size;
        b->next = b->next->next;
    }
}

int main(void)
{
    char *a = my_malloc(100);
    char *b = my_malloc(200);
    char *c = my_malloc(100);

    printf("a=%p  b=%p  c=%p\n", (void *) a, (void *) b, (void *) c);
    printf("b - a = %ld   (期望 32 + 112 = 144)\n", (long) (b - a));
    printf("c - b = %ld   (期望 32 + 208 = 240)\n", (long) (c - b));

    for (int i = 0; i < 100; i++) a[i] = 'a';
    for (int i = 0; i < 200; i++) b[i] = 'b';
    for (int i = 0; i < 100; i++) c[i] = 'c';

    my_free(b);                     /* 中间那块先还 */
    char *d = my_malloc(200);       /* 应该原地复用 b */
    printf("my_free(b) 后 my_malloc(200) = %p  （复用 b = %s）\n",
           (void *) d, d == b ? "是" : "否");

    printf("邻居没被踩坏: a[0]=%c a[99]=%c  c[0]=%c c[99]=%c  d[0]=%c\n",
           a[0], a[99], c[0], c[99], d[0]);

    my_free(a); my_free(c); my_free(d);
    printf("收尾 sbrk(0) = %p\n", sbrk(0));
    return 0;
}

四个核对点

  1. 地址差与理论值精确吻合：b − a = 144 = 32 + 112，c − b = 240 = 32 + 208。这同时验证了「头部 32 字节」和「16 字节对齐」两件事。
  2. free 之后能原地复用：my_free(b) 把中间那块还回链表，紧接着 my_malloc(200) 返回的正是 b 的地址 0x3eeba0b0。—— 这正是 glibc 的真实行为（c7_2 里 free 后 break 不降）。
  3. 切分逻辑没把邻居踩坏：a[0]/a[99]/c[0]/c[99] 全是自己写进去的值，d[0] = 'b' 说明 b 那块的内容还在（my_free 不擦数据）。
  4. sbrk(0) 收尾值 0x3eedc000 比首块地址高得多，因为这个简化实现从不归还内存 —— 它只做「复用 + 合并」，不调 sbrk(-n)。真实分配器才有 trim 逻辑。

这个练习为什么值得做：做完它，malloc 就不再是黑盒了。你会发现 glibc 里那些看起来很绕的东西 —— chunk 头、bin 链表、对齐要求、trim 阈值 —— 全都是为了解决这里已经露头的两个问题：碎片（切分后剩下的零头怎么办）和寻址（怎么快速找到够大的块）。生产级实现无非是把「线性找」换成「按 size 分桶」（fastbin / smallbin / largebin），把「只合并 next」换成「双向合并」。

练习 2：calloc 与 malloc + memset 的区别

从安全性、性能、实现三个角度分析。

角度 calloc(n, s) malloc(n*s) + memset
安全性 内部检查 n × s 整数溢出，溢出时返回 NULL n*s 在 size_t 上回绕成小值，会「分配成功」，随后按原尺寸写就越界
性能 大块走 mmap 时，内核给的匿名页本来就是清零的，可省掉 memset 必须实打实写一遍 ·n×s· 字节（还要多吃一次页错误）
实现 走 glibc 的 calloc → 小块走 _int_malloc + 置零，大块直接 mmap 两次函数调用，中间还有一个指针已分配但未初始化的窗口
语义 一次调用，语义完整 两步之间若被信号打断/长跳转，会留下未初始化的敏感数据

实测支撑（见 c7_4）：calloc(SIZE_MAX, 2) 返回 (nil) —— 溢出被拦下。同样尺寸若写 malloc(SIZE_MAX * 2)，SIZE_MAX * 2 会回绕成 SIZE_MAX - 1，看起来「成功」。

结论：要清零就用 calloc，不要手写 malloc + memset —— 前者免费拿到了溢出检查和（大块时）内核零页的优惠。

练习 3：为什么 realloc(ptr, 0) 的行为不统一？

标准怎么说的

标准 规定
C89 / C99 / C11 实现定义：要么返回 NULL，要么返回一个不能用于访问对象的非空指针
C17 同上，且标记为 deprecated（C DR 400）
C23 未定义行为（undefined behavior）

C17 §7.22.3.5 的原文：

If size is zero and memory for the new object is not allocated, it is implementation-defined whether the old object is deallocated. If the old object is not deallocated, its value shall be unchanged.

为什么会这样：realloc 的语义是「调整一块已有对象的大小」，它的返回值契约是「指向新对象的指针」。大小为 0 时，「新对象」是什么？—— 既可以说「没有对象，返回 NULL」，也可以说「有一个 0 字节对象，返回它的地址」。标准当初（C89）为了照顾下面这种写法才允许 0 长度：

OBJ *p = calloc(0, sizeof(OBJ));    /* "零长度占位符" */
while (1) {
    p = realloc(p, c * sizeof(OBJ));  /* 反复调整直到尺寸稳定 */
    /* 中间可能改 c 或 break */
}

结果两种解释都活了下来，行为就分裂了。

各家实测/实测来源

实现 realloc(p, 0) 的行为
glibc（Linux） 释放 p 并返回 NULL —— 本章 c7_4 实测确认，输出 7) realloc(p, 0) = (nil)
BSD / macOS 释放 p，但可能返回一个指向最小分配块的非空指针
一些嵌入式 libc 可能什么都不做并返回 NULL（此时 p 仍然有效 → 直接泄漏）

结论

永远不要写 realloc(ptr, 0)。 想释放就写：

free(ptr);
ptr = NULL;         /* 顺手防悬垂 */

这样语义在所有实现上都确定，也不会在「返回非空」的实现上悄悄泄漏一个最小块。

收尾自测

1. 为什么练习 1 里的 META 要做 ALIGN_UP，直接用 sizeof(block_t) 不行吗？

不行。sizeof(block_t) = 24，不是 16 的倍数。如果直接用 24 做步长，第二块的起始地址 = 第一块 + 24 + size（size 已按 16 对齐）→ 偏移 24，不是 16 的倍数，用户拿到的指针就此失去 16 字节对齐。

后果不是立刻崩溃，而是：double / SIMD 类型的访问可能触发未对齐访问的惩罚甚至 SIGBUS（某些架构上），而且 free 之后所有块的地址全歪 —— 这类 bug 排查起来极痛。

对齐到 32 之后，每块步长 = 32 + 16k，永远是 16 的倍数。这也是 glibc 里 chunk 大小永远 16 字节对齐的原因。

2. 练习 1 的实现从不归还内存，为什么还能叫「malloc」？

因为 「归还」不是 malloc 的契约。malloc 的契约是「给我一块至少 size 字节的、可写的内存，或者告诉我失败」。复用空闲块完全满足这个契约，而且比每次都找内核更快。

glibc 也是这么想的：它只在「堆顶出现一大段连续空闲」时才考虑 sbrk(-n) 归回（c7_2 里 free 掉 1000 个块后，break 仍留着 140 KB）。

真正要「把这些页还给内核」的场景，用的是 mmap + munmap（c7_3 的 B 段：256 KB 的块 free 时直接 munmap）。
