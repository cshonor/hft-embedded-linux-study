31.1

线程安全与可重入

本章：TLPI 第 31 章 — Thread Safety and Per-Thread Storage - 上一节：本章首页 - 下一节：31.2 pthread_once 一次性初始化

源码核验：Linux v6.6 · 无专属内核路径（本章是纯用户态 API 章）· TLS 的内核参与点见 31.4（arch/x86/kernel/process.c copy_thread():159）· glibc 侧：errno 是 TLS 变量（本节 §三）

本节讲什么

  1. 线程安全与可重入是两个不同的概念——线程安全管"多线程并发调用"，可重入管"信号打断自己后再次进入"。可重入 ⊂ 线程安全（更强），反向不成立。这个区分直接决定信号处理器里能调什么（Ch21 的伏笔在这里收口）。
  2. 不安全函数家族全景——strtok/localtime/ctime/gethostbyname 这类"内部藏静态状态"的函数清单，以及 _r 家族的对照替换表。
  3. 把不安全函数改造成线程安全的四种方法——加锁、TLS、TSD、调用者提供缓冲，各自适用场景与代价，本章后续三节就是后三种的展开。

一、两个正交的概念

概念 定义 敌人 手段
线程安全（thread-safe） 多线程并发调用同一函数不产生 UB、不破坏数据 调度器在两条线程间交错 互斥锁 / 原子操作 / TLS / 无状态
可重入（reentrant） 函数执行到一半被信号打断，信号处理器里再次调用同一函数也安全 信号处理器嵌套进入 不持有任何"再次进入会冲突"的资源：无静态可变状态、不自锁

四象限矩阵（本节的骨架，值得背下来）：

线程安全 非线程安全
可重入 strtok_r / localtime_r / 纯函数 （不存在——可重入蕴含线程安全*）
不可重入 strtok 加一把 mutex（见下） strtok / localtime

* 严格说可重入函数天然线程安全：既然连"自己打断自己"都安全，两条线程交替执行（对函数视角等价于被交错打断）自然也安全。

1.1 线程安全但不可重入：加锁版的死穴

static char buf[32];
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

char *locked_inet_ntoa(struct in_addr addr)      /* 线程安全 ✓ 不可重入 ✗ */
{
    pthread_mutex_lock(&m);
    strcpy(buf, inet_ntoa(addr));                 /* 临界区里改静态 buf */
    pthread_mutex_unlock(&m);
    return buf;
}

多线程并发调用：互斥保证了 buf 的使用串行化，安全。

现在把它放进信号处理器：主线程刚 lock(&m) 进入临界区 → 信号到达 → 处理器里再次调用 → lock(&m) 第二次加锁 → 自锁死锁（普通锁，同线程二次 lock 永久等待，30.1 §4.1）。锁只能防"别的线程"，防不了"自己"。

1.2 可重入的三个纪律

  1. 不使用静态/全局可变数据（只读常量表可以，如 strerror 的字符串表本身）；
  2. 不调用任何不可重入函数（级联污染：你调了 printf，你就不可重入）；
  3. 不自锁、不持有"再次进入需要"的锁/资源。

信号处理器是异步打断的极端场景（Ch21 已建立清单：只允许 write、_exit、sig_atomic_t 等异步信号安全操作），本节把它泛化成工程判断：任何可能被嵌套进入的代码路径（信号处理器、中断处理、回调风暴）都要求可重入，而不只是线程安全。

二、不安全函数家族与 _r 替换表

不安全的根源只有一句话：函数把状态藏在了调用者看不见、控制不了的地方（static 缓冲、全局变量、返回值指向内部存储）。

不安全函数 藏的状态 线程安全替代 替代思路
strtok(str, delim) 内部 static char *saveptr，逐次推进 strtok_r(str, delim, &saveptr) 状态交给调用者保管
localtime(time_t *) 内部 static struct tm localtime_r(t, &result) 同上 + 返回值改为传出参数
ctime(t) static char buf[26] ctime_r(t, buf, len) 同上
asctime(tm) static char buf[26] asctime_r(tm, buf) 同上
gethostbyname(name) 内部 static struct hostent getaddrinfo()（现代 API） 新协议族 + 状态外置
rand() 内部种子序列（全局状态） rand_r(&seed) / 自己的 PRNG 种子每线程一份
readdir(dirp) dirp 内部的偏移（DIR* 本身非线程安全） readdir_r（已废弃！） 用 fdopendir + 目录流每线程独立
strerror(err) 返回内部静态字符串指针 strerror_r(err, buf, len) 缓冲外置（本章 31.3 的改造主角）
getenv(name) / setenv 全局 environ（读安全/写不安全） —（POSIX 保证 getenv 读并发安全） 修改环境须全局锁

两条工程规则：

  1. _r 后缀 = "reentrant"，但语义上是线程安全——名字来自历史（先有信号可重入需求），别被字面骗了。
  2. 不是所有 _r 都值得用：readdir_r/strtok_r 中 strtok_r 常用，readdir_r 已被 POSIX.1-2008 标记废弃（缓冲区尺寸无法可移植地确定）——用每线程独立 DIR* 代替。替换前查 man 页的废弃标记。

2.1 为什么 strerror 是本节的完美标本

char *strerror(int errnum);          /* 返回指向静态字符串的指针 */

三宗罪齐备：返回内部静态缓冲（多线程拿到同一个 buf 各自覆盖）；snprintf(buf, ..., strerror(e)) 这种常见写法里 strerror 的求值与写入交错；POSIX 甚至不规定它线程安全。31.3 会用 TSD 把它改造成线程安全版——那是"接口签名不能改"时唯一的老接口改造范式。

三、errno：教科书级的 TLS 案例

C 标准说 errno 是个可修改的左值；POSIX 进一步规定它必须每线程一份——否则线程 A 的系统调用失败会污染线程 B 刚检查的 errno。

glibc 的实现（<errno.h>）：

extern int *__errno_location(void) __THROW __attribute__((const));
#define errno (*__errno_location())     /* errno 是"函数返回的 TLS int"的解引用 */

而 __errno_location 返回的是 glibc 内部的 __thread int（nptl/errno.c）。也就是说你写的每一条 if (errno == EINTR)，展开后是一次 __errno_location() 调用，而函数内部（libc 的编译单元里）是一次 TLS 访问——x86-64 上是 %fs 段寻址（31.4 §2.2 有两层实测反汇编）。

这正是本章的逻辑链：errno 的线程安全 = TLS 的存在意义；pthread_key_*（TSD）和 __thread（TLS）是同一目标的两种实现——运行时动态 vs 编译期静态。

四、改造不安全函数的四种方法

方法 代价 适用 对应章节
① 全局互斥锁 每次调用 +7~70 ns；仍然不可重入 保护频率低、冲突小的遗留接口 Ch30
② 调用者提供缓冲 改接口签名（所有调用点要改） 接口还能改时首选（_r 家族路线） 本节
③ TSD（pthread_key_*） 每次访问一次函数调用查表；需要析构器 接口签名不能动时的老接口改造 31.3
④ TLS（__thread） 变量声明加关键字即可；最快 新代码 / 已知每线程数据的全局/静态 31.4

选型直觉：

  • 能改签名 → ②（localtime_r 路线），最简单、零运行时开销、还顺带可重入；
  • 不能改签名、数据要跟线程走完生命周期（退出时释放）→ ③；
  • 不能改签名、只是"每线程一个缓冲/上下文"、无需运行时创建 → ④（HFT 默认）；
  • 一切之上的问题：这个全局状态真的需要存在吗——最好的改造往往是消灭它（把状态收进调用者的结构体）。

/* reent_demo.c — Ch31.1：静态缓冲串台、strtok 竞态、加锁版的自锁死穴

#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <pthread.h>
#include <unistd.h>

/* ---------- 演示 1：静态缓冲串台 ---------- */
static char sbuf[64];
static char *unsafe(void){                     /* 返回内部静态缓冲 */
    snprintf(sbuf, sizeof sbuf, "thread-%lu",
             (unsigned long)pthread_self());
    return sbuf;
}
static void *uworker(void *a){(void)a;
    for (int i = 0; i < 3; i++) {
        const char *r = unsafe();              /* r 与别的线程的 sbuf 是同一块内存 */
        usleep(1000);                          /* 拉大窗口：让别的线程覆盖 sbuf */
        printf("[demo1] 拿到 \"%s\"\n", r);
    }
    return NULL;}
static void demo_static_buf(void){
    pthread_t t[2];
    for (int i = 0; i < 2; i++) pthread_create(&t[i], NULL, uworker, NULL);
    for (int i = 0; i < 2; i++) pthread_join(t[i], NULL);
}

/* ---------- 演示 2：strtok 竞态 vs strtok_r ---------- */
static char line[128];
static void *tok_bad(void *a){(void)a;
    char *w = strtok(line, ",");               /* 两个线程共用同一个内部 saveptr */
    while (w) {
        printf("[demo2-bad ] %s\n", w);
        w = strtok(NULL, ",");
    }
    return NULL;}
static void *tok_good(void *a){(void)a;
    char save[128];
    strcpy(save, line);
    char *saveptr = NULL;                      /* saveptr 由本线程独占 */
    char *w = strtok_r(save, ",", &saveptr);
    while (w) {
        printf("[demo2-good] %s\n", w);
        w = strtok_r(NULL, ",", &saveptr);
    }
    return NULL;}
static void demo_strtok(void){
    strcpy(line, "AA,BB,CC,DD");
    pthread_t t[2];
    for (int i = 0; i < 2; i++) pthread_create(&t[i], NULL, tok_bad, NULL);
    for (int i = 0; i < 2; i++) pthread_join(t[i], NULL);

    for (int i = 0; i < 2; i++) pthread_create(&t[i], NULL, tok_good, NULL);
    for (int i = 0; i < 2; i++) pthread_join(t[i], NULL);
}

     * 用 trylock 避免真死锁，但换成 lock 就是永久挂死 */
    printf("[demo3] 主线程已持锁，现在同线程再 trylock：\n");
    int r = pthread_mutex_trylock(&m3);
    printf("[demo3] trylock = %d (%s) —— 若换成 lock 就是永久死锁\n",
           r, r ? "EBUSY：锁被占" : "成功");
    pthread_mutex_unlock(&m3);
}

31.2

一次性初始化：`pthread_once`

本章：TLPI 第 31 章 — Thread Safety and Per-Thread Storage - 上一节：31.1 线程安全与可重入 - 下一节：31.3 TSD：pthread_key_*

源码核验：Linux v6.6 · 无专属内核路径 · glibc 侧：pthread_once 用原子 CAS + futex 实现（与 Ch30 mutex 同一套底座）

本节讲什么

  1. "初始化恰好一次"为什么是个难题——if (!inited) { init(); inited = 1; } 在多线程下的检查-执行-标记竞态，以及"用锁包住检查"的代价（每次路过都要付锁钱）。
  2. pthread_once 的语义与用法——哪个线程执行 init_routine（不定！）、其他线程在干什么（阻塞等待）、为什么 once_control 必须零初始化且不能是 malloc 出来的。
  3. 它在 TSD 范式里的位置——pthread_once + pthread_key_create 是改造老接口的标准开场（31.3 的第一块积木）。

一、"恰好一次"是个难题

1.1 朴素写法的竞态

static int inited = 0;

void ensure_init(void) {
    if (!inited) {          /* ① 检查：两个线程同时看到 0 */
        do_init();          /* ② 执行：两个线程各跑一遍 init！ */
        inited = 1;         /* ③ 标记：来晚了 */
    }
}

do_init 常常有副作用：打开同一个文件两次、注册同一个 atexit 处理器两次、把计数器重置两次。①②③ 的窗口在多线程下必然被踩。

1.2 用锁修复的代价

static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
void ensure_init(void) {
    pthread_mutex_lock(&m);
    if (!inited) { do_init(); inited = 1; }
    pthread_mutex_unlock(&m);
}

正确，但每一次调用（包括初始化早已完成的亿万次）都要走一遍锁的快路径（~7 ns 无竞争，争抢时 70 ns+）。对高频接口这是纯浪费——初始化只发生一次，凭什么每次都查？

pthread_once 就是把"锁 + 检查 + 执行 + 标记"整个封装成专用原语：已完成后的再次调用只剩一条原子读（几乎零成本）。

二、API 与语义

#include <pthread.h>

pthread_once_t once_control = PTHREAD_ONCE_INIT;      /* 必须静态/零初始化 */

int pthread_once(pthread_once_t *once_control,
                 void (*init_routine)(void));

四条语义（每条都有坑点）：

# 语义 坑点
1 多线程并发调用时，init_routine 恰好执行一次 保证的是"一次"，不是"谁执行"——哪个线程跑 init 不确定（通常是第一个到的）
2 其他线程阻塞直到 init 完成 init 里不能做"等所有线程都到齐"的事 → 自死锁
3 once_control 必须 PTHREAD_ONCE_INIT（全零）初始化 不能 malloc：内存未必零填充；栈上/静态区天然可行
4 返回值恒为 0（不设 errno） init 本身失败如何反馈？——init_routine 无参无返回，失败信息要走全局（如 static int init_err;，init 里写，调用方事后查）

关于第 2 条的深坑：init_routine 执行期间，其他调用 pthread_once 的线程睡在 futex 上（Ch30 的机制）。如果 init 内部又需要"另一个还没到达 pthread_once 的线程"的结果——死锁。init 必须自包含。

2.1 glibc 实现一瞥（呼应 Ch30）

glibc 的 pthread_once（简化）：

/* 状态：0=未开始 1=进行中 2=完成 */
int pthread_once(pthread_once_t *once, void (*fn)(void)) {
    if (atomic_load_acquire(&once->__data) == 2)   /* 快路径：一条原子读 */
        return 0;
    /* 慢路径：CAS 0→1 成功者执行 fn；失败者 futex 等待 */
    ...futex(FUTEX_WAIT / FUTEX_WAKE)...           /* 与 mutex 同一套底座 */
}

正是 30.1 §3.1 那套"快路径用户态原子 + 慢路径 futex"哲学的又一个应用：一次性事件的常见情形是"早已完成"，所以快路径只做一次原子读；只有初始化窗口期的竞争者才付出睡眠成本。

2.2 与 C11 call_once 的关系

C11 线程库（<threads.h>）提供了语义等价的 call_once(flag, fn)（once_flag = 全零初始化）。glibc 两者都提供，实现共用。新代码可以按项目风格二选一，但别混用两种 flag 类型（pthread_once_t 和 once_flag 不是同一种东西）。

2.3 更朴素的替代：静态初始化

static GType g_x = COMPILE_TIME_VALUE;    /* 编译期完成，天生无竞态 */

能用编译期常量初始化的全局量，根本不需要 pthread_once。PTHREAD_ONCE_INIT 本身就是全零——glibc 大量 *_initializer 宏（mutex/cond/key 创建的第一步）都在利用"零初始化的静态存储天然免竞态"这一 C 语言保证。先问能不能静态初始化，再考虑 once。

三、TSD 范式中的位置

31.3 的标准开场（先睹）：

static pthread_key_t strerror_key;
static pthread_once_t once = PTHREAD_ONCE_INIT;

static void destructor(void *buf) { free(buf); }
static void create_key(void) {                 /* 只跑一次 */
    pthread_key_create(&strerror_key, destructor);
}

char *my_strerror(int errnum) {
    pthread_once(&once, create_key);           /* ⭐ 每线程都调用，key 只建一次 */
    char *buf = pthread_getspecific(strerror_key);
    if (buf == NULL) {                         /* 本线程第一次：分配 */
        buf = malloc(256);
        pthread_setspecific(strerror_key, buf);
    }
    ...
}

为什么 key 的创建必须恰好一次：pthread_key_create 每次返回新的 key（编号递增）。两个线程各自 create，拿到两个不同的 key，各自的 setspecific 写进不同的格子——"每线程一份"变成"每线程两份"，析构、读取全部错位。pthread_once 在这里的职责是保证全局的 key 唯一。

HFT / 嵌入式关联

路线 要点
HFT 首选静态初始化/C++ 静态对象（启动期单线程完成一切初始化是 HFT 的常规架构——开盘前 init，盘中零初始化路径）；pthread_once 用于无法静态化的惰性初始化，其快路径一条原子读对热路径无害
HFT · 失败语义 init_routine 无返回值 → 失败状态要落在静态变量里；热路径检查"初始化失败"应与检查"未初始化"合并为同一次原子读（状态机：0 未跑 / 1 进行 / 2 成功 / 3 失败）
嵌入式 RTOS 上 pthread_once 看线程库支持；裸机不存在此问题（main 单线程顺序初始化）；静态初始化在嵌入式是默认美德——少一条运行时分支，少一个竞态面
嵌入式 · init 里的耗时操作 once 阻塞语义意味着 init 期间所有调用者排队——把设备探测、固件加载这类百毫秒级 init 放进 once，会让并发首调用的线程集体停顿，注意超时预算

    once_count++;

}

static void *once_worker(void *a){(void)a;
    pthread_barrier_wait(&bar);
    pthread_once(&once, real_init);        /* 其余线程在此阻塞等待 */

static void demo_once(void){

           "执行者是 worker 线程(%d)\n",

31.3

线程特定数据：`pthread_key_*`

本章：TLPI 第 31 章 — Thread Safety and Per-Thread Storage - 上一节：31.2 pthread_once - 下一节：31.4 静态 TLS：__thread / _Thread_local

源码核验：Linux v6.6 · 无专属内核路径（TSD 完全在 glibc 用户态实现，数据结构挂在 struct pthread 上）· 线程退出时析构由 glibc 的 __nptl_deallocate_tsd 驱动 · 析构循环上限 PTHREAD_DESTRUCTOR_ITERATIONS = 4

本节讲什么

  1. TSD 解决什么——接口签名不能改、又需要"每线程一份私有数据"时的标准机制：进程全局一个 key，每个线程在 key 对应的格子里放自己的指针。
  2. 四个 API 的完整语义——尤其是 destructor 的生命周期：线程退出时调用、最多 4 轮迭代、pthread_key_delete 的不析构陷阱。
  3. glibc 怎么实现——key 表 + struct pthread 里的二级数组；以及为什么访问一次 TSD 要付一次函数调用的钱（与 31.4 TLS 的一条段寄存器寻址对比）。
  4. strerror 改造实战——pthread_once + key_create + 惰性分配 + 析构，四步范式完整落地。

一、问题：接口不能改，状态又不能共享

31.1 的方法②（调用者提供缓冲）要求改签名。但现实中大量接口改不了：

  • POSIX 规定的 char *strerror(int) 签名动不了；
  • 老库的 ABI 被几十个二进制依赖；
  • 回调函数的原型由框架定死。

TSD（Thread-Specific Data）的思路：保留全局的名字（key），把"值"做成每线程一份。

                进程全局（所有线程共享）
        ┌──────────────────────────────────────┐
        │  key 表（pthread_key_t = 下标 0..1023）│
        │  key[k] → { in_use, destructor }      │
        └──────────────────────────────────────┘
                     ▲ ▲ ▲
        ┌────────────┘ │ └────────────┐
   线程 A 的格子   线程 B 的格子   线程 C 的格子
   specific[k]=p1  specific[k]=p2   specific[k]=NULL
   （各自 malloc， 各自 malloc，    还没碰过这个 key
    析构时 free）   析构时 free）

key 是全局的（所有线程看到同一个编号 k），值是每线程的（各自格子里的指针互不可见）。

二、四个 API 的完整语义

int   pthread_key_create  (pthread_key_t *key, void (*destructor)(void *));
int   pthread_setspecific (pthread_key_t key, const void *value);
void *pthread_getspecific (pthread_key_t key);
int   pthread_key_delete  (pthread_key_t key);

2.1 pthread_key_create

  • key 是全局资源：整个进程只能创建 PTHREAD_KEYS_MAX（glibc = 1024）个 key。每线程每 key 一个 void* 格子。
  • destructor 可为 NULL（值不需要清理时）。destructor 收到的是该线程自己的 value。
  • 必须恰好一次（31.2）：两个线程各自 create 会拿到两个不同 key，"每线程一份"变成"每线程两份"。

2.2 setspecific / getspecific

  • getspecific 对"该线程从未设置过"返回 NULL——这个 NULL 正是惰性分配范式的判据。
  • setspecific(key, NULL) 是合法的"清除本线程的值"（析构不会再跑）。
  • 值本身是 void*：想放 int 就塞 (void*)(intptr_t)x 出来再转回（前提是 int 能塞进指针；大结构体还是 malloc 指针）。

2.3 destructor 的生命周期（本节最容易考的语义）

线程退出时（pthread_exit 或从 start 例程 return，不是进程 _exit），glibc 对该线程扫所有格子：

对每个 value != NULL 的 key：
    取出 value，先把格子清 NULL，再调 destructor(value)
    （清空再调用——防析构器里 getspecific 拿到旧值）
再来一轮：析构器可能又 setspecific 了新值 → 对非 NULL 的格子再析构
最多 PTHREAD_DESTRUCTOR_ITERATIONS = 4 轮，之后放弃（剩余内存泄漏）

四轮上限的原因：destructor 完全可能在清理过程中又往本线程的格子里塞了新值（比如析构一个对象时懒加载了另一个 TSD 依赖）。内核/glibc 不做环检测，只数轮次——四轮后仍有非 NULL 格子就随线程结构体一起丢弃（泄漏），不无限循环。

2.4 pthread_key_delete：不析构！

  • delete 只把 key 标记为可复用（进程视角），不会对任何线程的现存值跑 destructor。
  • 已设置的线程数据全部成为"不可达内存"——典型泄漏源。delete 的正确用途只有一个：key 不再需要了且你确信所有线程的值都已为 NULL。
  • key 删除后编号可能被新的 key_create 复用——别拿着旧 key 继续用（UB）。

2.5 glibc 实现速览

  • key 表：全局数组，in_use 标记 + destructor 指针；
  • 每线程格子：struct pthread->specific_1stblock[32]（一级直接块）+ 需要更多 key 时动态分配的二级块（specific 指针数组，每块 32 格）——访问第 k 个 key：k < 32 ? 1stblock[k] : specific[k/32-1][k%32]；
  • 这套结构就长在 29.8 讲过的 struct pthread（TCB，栈底）里——线程死则格子死，析构在 __nptl_deallocate_tsd（线程退出路径）里驱动；
  • 所以 pthread_getspecific 是一次真正的函数调用（查表逻辑 + 原子读），不是编译期寻址——这就是 31.4 TLS 性能优势的来源。

三、strerror 改造实战（四步范式）

目标：char *my_strerror(int errnum)——签名与 strerror 一致，但线程安全。

#define BUFLEN 128

static pthread_key_t key;                       /* 全局一个 key */

static void create_key(void)                    /* ① 恰好一次地创建 key */

    pthread_key_create(&key, destructor);
}

char *my_strerror(int errnum)                   /* 接口签名与 strerror 相同 */
{
    pthread_once(&once, create_key);            /* ① once 保护 key 唯一 */
    char *buf = pthread_getspecific(key);       /* ② 查本线程格子 */
    if (buf == NULL) {                          /* ③ 本线程第一次：惰性分配 */
        buf = malloc(BUFLEN);
        pthread_setspecific(key, buf);
    }
    snprintf(buf, BUFLEN, "(unknown error %d)", errnum);  /* 兜底 */
    return buf;
}

四步范式（把 TSD 用法背下来）：

步 代码 语义
① pthread_once(&once, create_key) key 全进程恰好建一次
② pthread_getspecific(key) 查本线程格子，NULL = 未初始化
③ malloc + pthread_setspecific 首次惰性分配并登记
④ destructor 里 free 线程退出自动回收，不泄漏

加锁版对比：同样的接口用 mutex 也能做（31.1 方法①），但①每次调用串行化（争抢点）②返回的指针在下次调用前就失效（还是共享缓冲）。TSD 版每线程一块缓冲，永不互相覆盖，返回指针长期有效——这是"线程安全"之外的第二重收益。

四、什么时候该用 TSD（而不是 TLS）

判断 TSD TLS（31.4）
数据是编译期已知的全局/静态变量？ 不适用 ✓ __thread 一行搞定
需要运行时决定"哪些数据"（如插件注册的 key）？ ✓ ✗
需要 destructor（堆分配、复杂清理）？ ✓ 原生支持 ✗（__thread 变量无析构；C++ thread_local 有）
需要值可以为 NULL 表示"未初始化"的惰性语义？ ✓ getspecific 返回 NULL 要自己另设标志
数量上限？ 1024 个 key 无硬限（受链接期 TLS 块大小约束）
访问成本？ 一次函数调用（~2 ns 级） 一条段寄存器寻址（~1 ns 级，可内联）
能否用于 dlopen 加载的库？ ✓ 受限（见 31.4 §四，initial-exec 模型耗尽后 dlopen 失败）

HFT / 嵌入式关联

路线 要点
HFT TSD 在热路径的两个成本：函数调用不可内联 + getspecific 查表。已知的数据结构一律 __thread（每线程上下文结构体）；TSD 留给"运行时才确定的注册制数据"（如回调注册的统计槽）
HFT · 生命周期 destructor 在线程退出时跑——不要在 destructor 里做跨线程通信（其他线程可能已退出，锁/cond 已销毁）；析构只做 free 本线程资源
嵌入式 1024 key 上限在嵌入式绰绰有余，但要防"库各自 create 一堆 key"的碎片化；TSD 完全是用户态实现，不依赖内核版本，可移植性极好（连 musl 都有）
嵌入式 · 泄漏审计 长命进程反复 create 线程 + key_delete 使用不当 = 慢性泄漏。规则：key 与进程同寿（启动建、永不删），线程值靠 destructor 收

{

}

    pthread_t t[3];

        pthread_create(&t[i], NULL, worker, (void*)(intptr_t)(i+1));
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);

    free(v);
    if (destruct_rounds < 10)                   /* 故意再塞一个新值 */

}

static void *rearm_worker(void *a){(void)a;
    pthread_setspecific(k2, malloc(16));
    return NULL;}

static void demo_rearm(void){

    pthread_t t;
    pthread_create(&t, NULL, rearm_worker, NULL);

           "（上限 PTHREAD_DESTRUCTOR_ITERATIONS=4，超出后放弃→泄漏）\n",
           destruct_rounds);

}

static void demo_key_limit(void){
    pthread_key_t ks[1100];
    int n = 0;
    for (int i = 0; i < 1100; i++) {
        if (pthread_key_create(&ks[i], NULL) != 0) break;
        n++;
    }
    printf("[demo4] 本进程还能创建 %d 个 key（PTHREAD_KEYS_MAX 上限之内，"
           "demo1/3 已占用）\n", n);
    for (int i = 0; i < n; i++) pthread_key_delete(ks[i]);
}

    printf("==== 演示 1+2：strerror 改造 + 析构时机 ====\n");
    demo_destructor();
    printf("==== 演示 3：析构器重塞值的轮次上限 ====\n");
    demo_rearm();
    printf("==== 演示 4：key 数量上限 ====\n");
    demo_key_limit();

31.4

静态 TLS：`__thread` / `_Thread_local`

本章：TLPI 第 31 章 — Thread Safety and Per-Thread Storage - 上一节：31.3 TSD：pthread_key_* - 下一节：31.5 总结

源码核验：Linux v6.6 · arch/x86/kernel/process.c（copy_thread():159 · fsbase 继承 :184 · CLONE_SETTLS → set_new_tls():254）· arch/x86/kernel/process_64.c（ARCH_SET_FS:828）· include/uapi/linux/sched.h（CLONE_SETTLS:22）

本节讲什么

  1. __thread 用法与限制——一条关键字把全局/静态变量变成"每线程一份"；只能修饰编译期已知、可用常量初始化的变量。
  2. 它为什么快——x86-64 上 TLS 变量通过 FS 段基址寻址（一条 mov 搞定，可内联），对比 TSD 的函数调用查表；本节有实测反汇编和实测计时。
  3. 内核在哪参与——内核不实现 TLS API，但 clone(CLONE_SETTLS) 为每个新线程设置 FS base；本节把 glibc → 系统调用 → wrmsr/wrfsbase 的完整链路核到 v6.6 源码。

一、用法与限制

__thread int x;                       /* GCC 扩展（TLS 诞生于此）*/
_Thread_local int y;                  /* C11 标准（等价，优先用于新代码）*/
static __thread char buf[256];        /* static 也可以 */
__thread struct ctx *g_ctx = NULL;    /* 指针可以（NULL 是常量）*/

四条硬限制：

# 限制 原因
1 只能修饰全局或静态变量（块内 auto 不行） TLS 模型要求变量在链接期就分配进每线程镜像
2 初始化必须是编译期常量（或默认零） 模板在创建线程时 memcpy，没有"跑代码"的机会
3 C 的 __thread 变量没有析构器（与 TSD 最大差别） 退出时模板怎么来的怎么丢；堆指针要自己收（C++ 的 thread_local 有动态初始化和析构）
4 取地址 &x 合法——地址每线程不同，但只在取它的线程生命周期内有效 传给别的线程 = 传了一个悬挂语义的指针（数据是那线程的副本，但它退出后失效）

初始化限制的破解法：__thread struct ctx *ctx; + 惰性 if (!ctx) ctx = init();——指针本身零初始化，指向的对象按需构造（这就是"TLS 放指针、堆放本体"的 HFT 标准姿势，也顺带绕开限制 2 和 3）。

二、为什么快：FS 段基址寻址

2.1 原理图

x86-64 上，每个线程有一个专属的 FS 基址（FSB ASE 寄存器，多数实现走 MSR 或 wrfsbase 指令），指向本线程的 TCB（Thread Control Block，glibc 的 struct pthread，见 29.8：它就在线程栈底）。TLS 变量的地址 = FS 基址 + 编译期偏移：

   线程 A                                线程 B
   FS base ──┐                           FS base ──┐
             ▼                                      ▼
   ┌─────────────────┐                 ┌─────────────────┐
   │ struct pthread   │                 │ struct pthread   │
   │ (TCB)            │                 │ (TCB)            │
   ├─────────────────┤                 ├─────────────────┤
   │ TLS 模板副本      │                 │ TLS 模板副本      │
   │  my_counter @-8  │◄── 偏移固定      │  my_counter @-8  │
   │  err_buf  @-264 │                 │  err_buf  @-264 │
   └─────────────────┘                 └─────────────────┘
   访问 my_counter：                    访问 my_counter：
   mov %fs:-8, %eax                     mov %fs:-8, %eax
   （同一条指令，不同线程的 FS → 不同内存）

同一条指令，因 FS 不同而落到不同内存——这就是"零运行时查找成本"的全部秘密：偏移在链接期定死，基址在硬件里。

2.2 实测反汇编

源码：

int global_counter;              /* 外部链接：gcc 不能折叠加载 */
__thread int tls_counter;

int read_global(void){ return global_counter; }
int read_tls   (void){ return tls_counter;   }

gcc -O2 -S 实测输出（WSL gcc）：

read_global:
        movl    global_counter(%rip), %eax     ; RIP 相对寻址：普通全局，所有线程同一地址
        ret

read_tls:
        movl    %fs:tls_counter@tpoff, %eax    ; ⭐ FS 段前缀 + 链接期偏移：每线程不同地址
        ret

%fs: 前缀 + @tpoff（thread pointer offset）就是 TLS 的机器级形态。

顺带解剖 errno 的两层：

;; 你的代码里：errno 宏展开成一次函数调用（errno 在 libc 的 TU 里，跨 TU 看不见）
        call    __errno_location@PLT
        movl    (%rax), %eax
;; libc 自己的 TU 里（模拟同 TU 编译 __errno_location）：
        movq    __libc_errno@gottpoff(%rip), %rax   ; GOT 里取偏移（initial-exec 模型）
        addq    %fs:0, %rax                          ; + FS 基址 → 本线程的 errno 地址

所以准确说法是：errno 的实际存储访问（在 libc 内部）是 %fs 段寻址；你的代码经过一次 PLT 调用拿到地址。这也解释了为什么频繁读 errno 的热路径可以先把 errno 存进局部变量——省掉的是 PLT 调用那层，而不是 TLS 本身（TLS 那层本来就免费）。

2.3 实测计时：TLS vs TSD vs 全局

访问方式 实测（每线程 1 亿次读，ns/次） 机制
普通全局 ~0.4 RIP 相对寻址（还能被缓存进寄存器）
__thread TLS ~0.5 %fs:偏移 寻址，可内联可缓存
pthread_getspecific ~2.0 函数调用 + 二级数组查表
pthread_getspecific + once ~2.0 once 完成态只多一条原子读

（量级参考：TLS 与普通全局几乎同价，TSD 慢约一个函数调用——热路径上 TLS 免费原则成立。）

2.4 TLS 四种链接模型（链接器自动选择，读 ELF 时会遇见）

模型 场景 成本
local-exec 可执行文件自己的变量 最快：%fs:偏移 一条指令
initial-exec 主程序加载时就确定（含启动期加载的 .so） 快：GOT 里一次间接
local-dynamic 同一 .so 内多个变量共享一个偏移块 中：调 __tls_get_addr
global-dynamic dlopen 运行时才加载的 .so 里的 TLS 最慢：每次 __tls_get_addr 查 DTV

工程含义：dlopen 一个大量使用 TLS 的 .so，不仅它的 TLS 访问走最慢模型，还要消耗"静态 TLS 剩余额度"——额度耗尽时 dlopen 直接失败（cannot allocate memory in static TLS block）。这是动态加载策略插件的 HFT 系统踩过的真实坑：插件要么少用 __thread，要么编译时 -ftls-model=global-dynamic 显式走慢路径换取可加载性。

三、内核侧链路（v6.6 核验）

内核不认识 __thread——TLS 的创建由 glibc 与内核协作完成：

pthread_create
  └─ glibc: 分配线程栈 + TLS 模板副本 + TCB(struct pthread)
  └─ clone(CLONE_VM|CLONE_THREAD|...|CLONE_SETTLS, tls=TCB地址)
       └─ kernel/fork.c: kernel_clone()
            └─ copy_process()
                 └─ arch/x86/kernel/process.c: copy_thread():159
                      · :184  p->thread.fsbase = current->thread.fsbase  ← 先继承父线程
                      · :254  if (clone_flags & CLONE_SETTLS)
                                 ret = set_new_tls(p, tls);               ← 再被新值覆盖
                           set_new_tls():130
                            └─ do_set_thread_area_64(p, ARCH_SET_FS, tls):137
                                 └─ x86_fsbase_write_task(p, tls)  ← 写进新任务的 thread 结构
  （新线程第一次被调度上 CPU 时，switch_to 会装载它的 FS base）
  （运行时改 FS base 的通用入口：arch_prctl(ARCH_SET_FS) → process_64.c:828，
   preempt_disable → selector 清 0 → wrfsbase/wrmsrl → preempt_enable）

两个细节：

  1. copy_thread():184 先继承 fsbase、:254 再被 CLONE_SETTLS 覆盖——没传 SETTLS 的 clone（比如普通 fork）子进程继承父的 FS base 值，但注意 fork 出的新进程有自己的 mm 和新的 TLS 块，这个继承值在单线程子进程里语义无害；真正的每线程差异完全由 SETTLS 路径决定。
  2. ARCH_SET_FS:828 里的 preempt_disable()：改段寄存器/FSB ASE 必须在不可抢占区完成（防止改到一半被切走，别的代码用错基址）；selector 清 0 是 FSGSBASE 时代的规范做法（基址全权交给 fsbase，段选择器退位）。

3.1 TLS 变量的初始化时机（把三条链拼起来）

  1. 程序启动：动态链接器把所有 TLS 变量收进模板（.tdata 有初值 / .tbss 零值）；
  2. pthread_create：glibc 为新线程栈分配 TLS 块，memcpy 模板（这一步在用户态完成，"每线程一份初值"由此而来）；
  3. clone(CLONE_SETTLS)：内核把 FS base 指向它；
  4. 此后该线程的每一次 my_var 访问 = %fs:偏移。

主线程的 TLS 块在程序加载时由动态链接器静态安置（栈头附近），不走 clone。

四、TSD vs TLS 终极对比表（本章收口）

HFT / 嵌入式关联

路线 要点
HFT · 标准姿势 static __thread struct engine_ctx *ctx;——TLS 放指针（零初始化免费），堆放本体（启动时构造）；热路径访问 ctx->field 全部内联成一条 FS 寻址 + 一次间接寻址
HFT · 一核一线程 每线程上下文（订单簿视图、内存池、统计槽）全进 TLS，跨线程零共享 = 零锁零伪共享；再把线程钉核（29.8），上下文永驻该核 L1/L2
HFT · 插件 dlopen 型策略插件的 __thread 用量要审计（§2.4 静态 TLS 额度问题）；或插件接口显式传 ctx 指针，不用 TLS
嵌入式 · 工具链 __thread 需要 TLS 重定位 + 运行时支持：Linux 用户态齐全；裸机（无 MMU/no libc）看工具链（GCC 支持 emutls 软件模拟，但慢且占 ROM）；RTOS 上 pthread 库（如 Zephyr/FreeRTOS+POSIX 层）通常同时提供 TSD 与 TLS

static __thread int tls_counter = 100;          /* 带初值：每线程都从 100 开始 */

二、选型决策树

接口/数据需要每线程独立？
├─ 能消灭全局状态（收进调用者结构体）？── 是 ──▶ 就地消灭（最好的同步是没有共享）
├─ 能改函数签名？
│   └─ 是 ──▶ 调用者提供缓冲（_r 家族路线，顺带可重入）
├─ 数据在编译期已知（全局/静态变量）？
│   └─ 是 ──▶ __thread / _Thread_local（TLS，~0.5ns，热路径免费）
│        └─ 初值不是常量？──▶ __thread 放指针 + 惰性构造
├─ 需要 destructor / 运行时决定 key / dlopen 插件？
│   └─ 是 ──▶ TSD（pthread_key_*，~2ns，1024 个上限）
└─ 以上都不适用（遗留接口 + 低频调用）？
    └─ 全局锁（Ch30）——记得它防不了重入

三、铁律

  1. 能消灭的全局状态就消灭——同步问题的最低成本解法是让问题不存在。
  2. 老接口（strtok/localtime/ctime/strerror...）在多线程里一律换成 _r/等价现代版；审计用 grep。
  3. 信号处理器/中断上下文里只进可重入代码——加锁版"线程安全"在这里是死锁。
  4. pthread_once_t 必须 PTHREAD_ONCE_INIT，不能 malloc；init 里不能等其他线程。
  5. key 创建必须 once 保护；pthread_key_delete 不析构——key 与进程同寿，值靠 destructor。
  6. destructor 里别再 setspecific（4 轮后泄漏）；别做跨线程通信（别人可能已退出）。
  7. __thread 只放全局/静态 + 常量初始化；大对象放堆、TLS 放指针。
  8. C 的 __thread 无析构——堆资源每线程自己收（worker 退出前 free）。
  9. TLS 变量地址每线程不同且随线程消亡——不跨线程传递 &tls_var。
  10. dlopen 插件慎用 __thread（initial-exec 额度），必要时 -ftls-model=global-dynamic。

自测题

题目 1（辨析）："strtok 加一把全局 mutex 就线程安全了，所以信号处理器里也可以用它。"找出这句话的两处错误。

参考答案

① 加 mutex 只解决跨线程互斥，不解决重入：处理器若打断了正持有该 mutex 的代码路径（很可能就是 strtok 自己的调用链），再次 lock = 同线程二次加锁 = 永久死锁（普通锁）。② 即使不考虑锁，strtok 被打断时内部 saveptr 处于中间状态，处理器里再调会破坏原调用者的解析进度。正确做法：处理器里根本不做字符串解析（只置标志，29.9/Ch21 原则）；正常代码用 strtok_r。

题目 2（设计）：一个热路径函数 order_id_t next_order_id(void)（无参无返回指针），要每线程独立序号、高并发下不加锁。写出实现并说明初始化方案。

参考答案 
static __thread uint64_t seq = 0;     /* 每线程一份，零初始化满足"常量初始化" */

    return (order_id_t)((uint64_t)thread_slot() << 48 | ++seq);  /* 高位线程槽 + 低位序号 */
}

__thread 零初始化即合法；序号从 1 开始避免 0 值歧义；线程槽号在建线程时分配（全局原子计数器 +1，一次性成本）。TSD 不选：函数调用查表 +1024 上限 + 需要析构；锁不选：热路径争抢。若要求全局严格递增则退化为原子 fetch_add（25 ns 级，见 30.3 成本账本）——先确认"每线程独立"是否真的满足业务。

题目 3（机制）：__thread 变量的访问为什么是一条指令？从"编译期偏移 + FS 基址"解释，并说明 FS 基址在创建线程时由谁、在哪一步设置。

参考答案

链接器把每个 TLS 变量分配成相对线程指针（FS base）的固定偏移（@tpoff），编译器生成 mov %fs:偏移, %eax——偏移编译期定死，基址在硬件寄存器里，零运行时查找。创建链路：glibc 分配线程栈与 TLS 模板副本 → clone(CLONE_SETTLS, tls=TCB) → 内核 copy_thread()（arch/x86/kernel/process.c:159）在 :254 调 set_new_tls() → do_set_thread_area_64(p, ARCH_SET_FS, tls) 把基址写进新任务的 thread 结构 → 新线程首次调度上 CPU 时由 switch_to 装载。运行时修改走 arch_prctl(ARCH_SET_FS)（process_64.c:828，preempt_disable 保护）。

题目 4（排错）：进程长期运行内存持续增长。每 10 秒创建一个短命线程做日志 flush（用了 TSD 存格式化缓冲，destructor 里 free）。另一模块每 100 万条日志 pthread_key_delete 后重建 key。哪个环节泄漏？

参考答案

pthread_key_delete 是泄漏点：delete 不对任何线程现存值跑 destructor。重建 key 的周期内，尚在运行的线程（以及 delete 时刻还活着的 flush 线程）格子里可能还挂着旧缓冲指针；key 标记可复用后这些指针成为不可达内存（析构器关联也没了）。修法：key 与进程同寿（启动建一次，永不删）；或 delete 前确保所有线程该 key 的值已清空（实际做不到时就是设计错误）。顺带检查 destructor 是否可能 4 轮上限泄漏（31.3 demo3 场景）。

综合题：线程安全的错误报告模块（完整可运行）

需求：const char *errfmt(int code) 返回格式化错误串（线程安全、每线程缓冲、支持嵌套调用 errfmt(errfmt(...)) 场景的安全分析）。参考实现：

/* errfmt.c — Ch31.6 综合题：TSD+once 惰性缓冲 + 嵌套安全性分析
 * 编译：gcc -O2 -Wall -Wextra -o errfmt errfmt.c -pthread
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>             /* intptr_t */
#include <pthread.h>

#define EBUF_LEN 128
#define NBUF 4                      /* 每线程 4 个缓冲轮转：支持 4 层嵌套 */

static pthread_key_t ekey;
static pthread_once_t eonce = PTHREAD_ONCE_INIT;

typedef struct {
    char bufs[NBUF][EBUF_LEN];
    int  next;
} errpool_t;

static void epool_dtor(void *p){ free(p); }

static void ekey_create(void){
    pthread_key_create(&ekey, epool_dtor);        /* key 全局恰好一次 */
}

static errpool_t *my_pool(void){
    errpool_t *p = pthread_getspecific(ekey);
    if (p == NULL) {                              /* 本线程首次：惰性分配 */
        p = calloc(1, sizeof *p);
        pthread_setspecific(ekey, p);
    }
    return p;
}

/* 线程安全 + 支持最多 NBUF 层嵌套（轮转缓冲） */
const char *errfmt(int code)
{
    pthread_once(&eonce, ekey_create);
    errpool_t *p = my_pool();
    char *buf = p->bufs[p->next];
    p->next = (p->next + 1) % NBUF;               /* 下次嵌套调用用下一块 */
    snprintf(buf, EBUF_LEN, "[err %d] %s", code, strerror(code));
    return buf;
}

static void *worker(void *a){
    long id = (long)(intptr_t)a;
    /* 嵌套调用：外层 errfmt 的结果被内层 errfmt 安全地拼进 printf */
    printf("[T%ld] 嵌套：%s / 单层：%s\n",
           id, errfmt((int)id), errfmt(100 + (int)id));
    return NULL;   /* 退出 → epool_dtor 整池回收 */
}

int main(void){
    pthread_t t[3];
    for (long i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, worker, (void*)(intptr_t)(i+1));
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    printf("主线程直接调用：%s\n", errfmt(42));
    pthread_key_delete(ekey);      /* 演示用：进程退出前 delete（值已全空/析构过）*/
    return 0;
}

实测输出（WSL2 / 12 核）：

[T3] 嵌套：[err 3] No such process / 单层：[err 103] Software caused connection abort
[T2] 嵌套：[err 2] No such file or directory / 单层：[err 102] Network dropped connection on reset
[T1] 嵌套：[err 1] Operation not permitted / 单层：[err 101] Network is unreachable
主线程直接调用：[err 42] No message of desired type

思考点（做完题再看）：

  1. 为什么 NBUF=4 而不是 1：printf("%s", errfmt(x)) 单次调用只需要 1 块；但 snprintf(buf, n, "%s-%s", errfmt(a), errfmt(b)) 里两个 errfmt 求值先后未知，1 块缓冲会互相覆盖（第二个覆盖第一个）。轮转缓冲让嵌套/多重求值各自拿不同块——glibc 老式 strerror 连这层保护都没有。
  2. 轮转的边界：超过 NBUF 层嵌套仍会覆盖最旧的——工程上按实际嵌套深度设 NBUF，或接口文档明示"返回值有效期到下一次第 N 次调用"。
  3. key_delete 放在最后只是演示：所有线程已 join、值已析构，此时 delete 不泄漏（31.3 §2.4 的正确用法）。
