代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

/* Ch5 深入文件 I/O — dup/dup2/fcntl/lseek/pread/pwrite。
 * 演示 dup2 重定向 + lseek 随机访问。
 * 编译: gcc -o ch5_demo ch5_demo.c */

int main(void) {
    int fd = open("/tmp/ch5_test.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }

    /* 写入数据 */
    const char *data = "ABCDEFGHIJ";
    write(fd, data, 10);

    /* lseek 到开头，用 pread 读特定位置（不影响文件偏移量） */
    char buf[4];
    pread(fd, buf, 3, 5);  /* 从偏移5读3字节 */
    buf[3] = '\0';
    printf("pread at offset 5: %s\n", buf);

    /* dup2: 将 fd 复制到 STDOUT_FILENO，重定向输出 */
    lseek(fd, 0, SEEK_SET);
    dup2(fd, STDOUT_FILENO);
    close(fd);

    /* printf 现在写入文件而不是终端 */
    printf("This goes to the file via dup2!\n");
    fflush(stdout);
    return 0;
}

5.1

原子性与竞争条件（Atomicity and Race Conditions）

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/open.c:1222 build_open_flags、:1308 O_APPEND、:1315-1318 O_CREAT|O_EXCL；fs/namei.c:3885 lookup_one_qstr_excl、:3896-3897 -EEXIST） - 上一节：本章首页 - 下一节：5.2 fcntl()

本节讲什么

多进程/多线程同时操作文件时，两个「看起来没问题的操作」可能因为执行顺序交错而互相踩踏。本节回答三个问题：

  1. 「原子性（atomicity）」到底指什么？为什么文件 I/O 里它如此关键？
  2. O_EXCL | O_CREAT 和 O_APPEND 这两个标志，各自解决了哪类竞态？
  3. 什么是 TOCTOU（time-of-check, time-of-use），以及为什么「先检查再操作」的写法几乎总是错的？

1. 竞态条件与原子性

竞态条件（race condition）：多个进程/线程的执行结果，取决于它们指令的相对执行顺序。只要有一个交错顺序会导致错误结果，代码就是有 bug 的——哪怕它 99% 的时候都对。

原子性（atomicity）：一个操作「要么完全执行、要么完全不执行」，中间状态对其他进程不可见。原子操作天然免疫竞态，因为不存在「执行到一半被打断」的窗口。

文件 I/O 里最常见的两类竞态，TLPI 5.1 各给了原子化解法：

场景 非原子（错误）写法 原子（正确）写法
独占创建文件（如 PID 锁文件） access(path) 检查不存在 → open(O_CREAT) open(path, O_CREAT \| O_EXCL)
多进程追加日志 lseek(fd, 0, SEEK_END) → write(fd, ...) open(path, O_APPEND)，直接 write

下面分别拆解。

2. O_EXCL | O_CREAT：原子独占创建

为什么 access() + open() 是错的

/* 反例：TOCTOU —— check 和 use 之间被别的进程插入 */
if (access(path, F_OK) == -1) {         /* check：现在还不存在 */
    fd = open(path, O_CREAT, 0644);     /* use：另一个进程可能已抢先创建 */
}

两个进程同时执行这段代码：A 检查「不存在」，B 也检查「不存在」，然后 A、B 都去 open(O_CREAT)。结果两个进程都以为自己独占创建成功，最后只有一个文件，两个「锁持有者」同时存在——这正是 TOCTOU：check（access）和 use（open）之间的时间窗就是竞态窗口。

内核如何做到原子

O_EXCL 的原子性不在用户态，而在内核的路径查找（namei）层——它在目录项锁保护下一次性完成「查无此文件则创建，有则失败」：

用户态 open(path, O_CREAT | O_EXCL)
      ▼
SYSCALL_DEFINE3(open)                    fs/open.c:1441
      ▼
do_sys_openat2 → build_open_flags()      fs/open.c:1222
      ├─ O_CREAT → op->intent |= LOOKUP_CREATE      :1315
      └─ O_EXCL  → op->intent |= LOOKUP_EXCL        :1317
                        （并附带 O_NOFOLLOW，防符号链接攻击）
      ▼
namei 层 lookup_one_qstr_excl()          fs/namei.c:3885
      create_flags = LOOKUP_CREATE | LOOKUP_EXCL    :3866
      inode_lock_nested(parent)          ← 父目录 inode 锁，串行化「查+建」
      ├─ d_is_positive(dentry) 已存在？
      │     └─ 是 → return -EEXIST                    :3896-3897
      └─ 否 → 原子创建新 dentry + inode

关键在于 inode_lock_nested(parent)：「查目录项是否存在」和「创建新目录项」发生在同一把父目录锁内，其他进程无法插入。O_EXCL 保证「若文件已存在，open 失败返回 EEXIST；若成功返回，则一定是我创建的」。这就是原子性——没有中间状态可被观察。

典型用途

  • PID 锁文件 / 单例守护进程：open("/var/run/foo.pid", O_CREAT|O_EXCL|O_WRONLY) 失败即「已有实例在跑」。
  • 临时唯一文件名（配合 O_TMPFILE 或 mkstemp 的思想）。

3. O_APPEND：原子追加

为什么 lseek(SEEK_END) + write() 是错的

/* 反例：两个进程共享同一打开描述时（或各自打开但用 lseek 定位） */
off_t end = lseek(fd, 0, SEEK_END);   /* A 读到末尾 = 100 */
/* —— 此时 B 也 lseek 到 100，并 write 了 10 字节 —— */
write(fd, buf, 20);                   /* A 从 100 写 20 字节，覆盖 B 刚写的 */

lseek 和 write 是两个独立 syscall，中间的窗口里另一进程可能已经移动了偏移或写了数据。A 的 20 字节会覆盖 B 刚写的内容，而不是接在真正的末尾。

O_APPEND 的原子语义

以 O_APPEND 打开后，每次 write() 前，内核会原子地把文件偏移设为「当前文件末尾」，再执行写——「定位」和「写」被合并进同一次写操作，中间没有可被抢占的窗口：

open(path, O_APPEND)
      ▼
build_open_flags()                       fs/open.c:1308
      O_APPEND → acc_mode |= MAY_APPEND  （LSM 据此区分 append vs write）
      ▼
后续每次 write：
      file->f_flags 里保留 O_APPEND
      → 写路径在写前原子地把 ki_pos 设为 i_size_read(inode)
        （「原子定位 + 写」由内核在单次写操作内完成，无用户态 lseek 窗口）

注：O_APPEND 的「写前定位到 EOF」发生在通用写路径（mm/filemap.c 的 generic_file_write_iter 通过 IOCB_APPEND 标志处理，kiocb_set_rw_flags 依据 file->f_flags & O_APPEND 设置）。缓存未收录 mm/filemap.c，此处作架构说明；用户态语义（write 前原子定位到 EOF）是 POSIX 明确规定、且被 build_open_flags 的 MAY_APPEND 与 f_flags 保留所支撑的。

关键推论

特性 说明
追加永远接在末尾 多个进程各自 O_APPEND 打开同一文件并 write，数据不会互相覆盖
原子性边界 单次 write() 原子；若一次写 > PIPE_BUF 级别的大块，仍建议依赖 O_APPEND 而非手动定位
与偏移的关系 O_APPEND 下 lseek 基本无用——每次写都会回到末尾
典型场景 多进程日志聚合（如多 worker 写同一 log 文件）、数据库 WAL 追加

4. HFT / 嵌入式关联

场景 本节机制的兑现
单实例守护进程 O_CREAT\|O_EXCL 的 PID 锁文件，避免交易进程被重复拉起
多 worker 聚合日志 O_APPEND 让多个撮合/风控进程写同一日志而不互相覆盖，无需加锁
回测结果落盘 并行回测分片各自 O_APPEND 写结果文件，天然串行化追加
防 TOCTOU 安全漏洞 嵌入式设备上以 root 写配置文件时，O_EXCL 防止「检查→创建」窗口被符号链接攻击（O_NOFOLLOW 附带生效）
少一次 syscall O_APPEND 省去每次 lseek(SEEK_END)，HFT 高频写路径更省

5. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>

/* 5.1 原子性：O_EXCL 独占创建 + O_APPEND 原子追加 */
int main(void) {
    /* 1) O_EXCL|O_CREAT：独占创建，已存在则失败 */
    int fd = open("/tmp/single.lock", O_CREAT | O_EXCL | O_WRONLY, 0644);
    if (fd < 0) {
        if (errno == EEXIST)
            printf("已有实例在运行（锁文件已存在）\n");
        else
            perror("open O_EXCL");
        return 1;
    }
    printf("独占创建成功，取得锁\n");

    /* 2) O_APPEND：每次 write 原子追加到末尾 */
    int logfd = open("/tmp/app.log", O_WRONLY | O_APPEND | O_CREAT, 0644);
    const char *line = "one more line\n";
    /* 无需 lseek(SEEK_END)，write 直接接到文件末尾 */
    write(logfd, line, strlen(line));

    close(logfd);
    close(fd);
    return 0;
}

代码自测（Q&A）

Q1：什么是 TOCTOU？为什么 access() + open(O_CREAT) 是它的典型例子？ A：TOCTOU = time-of-check, time-of-use，即「检查」和「使用」之间存在可被其他进程插入的时间窗。access(path) 判断「文件不存在」后、到 open(O_CREAT) 真正创建之间，另一进程可能已抢先创建，导致两个进程都误以为自己独占成功。O_EXCL|O_CREAT 把「检查 + 创建」合并成内核里一次原子操作，消除了这个窗口。

Q2：open(path, O_CREAT | O_EXCL) 在文件已存在时返回什么？ A：返回 -1，errno = EEXIST。这正是它作为「锁文件」判据的价值——失败即代表已有人创建。

Q3：O_APPEND 为什么能避免 lseek(SEEK_END) + write 的覆盖问题？ A：lseek 和 write 是两个独立 syscall，中间窗口内偏移可能被其他进程改变。O_APPEND 让内核在单次 write 操作内先原子地把偏移定位到文件末尾再写，不存在可被抢占的中间态，因此多进程追加不会互相覆盖。

Q4：O_EXCL 为什么不带 O_CREAT 就无意义？ A：O_EXCL 的语义是「创建时若已存在则失败」，它只约束创建这个动作。单独 O_EXCL（不带 O_CREAT）在多数系统上会被忽略或报错——POSIX 规定 O_EXCL 仅与 O_CREAT 组合使用，build_open_flags 里也是在 if (flags & O_CREAT) 分支内才检查 O_EXCL 并设置 LOOKUP_EXCL。

Q5：O_EXCL | O_CREAT 还有防符号链接攻击的附加作用吗？ A：有。build_open_flags 在设置 LOOKUP_EXCL 的同时会附带 flags |= O_NOFOLLOW（fs/open.c:1317-1318），即不跟随符号链接，防止攻击者用符号链接把「独占创建」重定向到任意文件。这是独占创建安全语义的一部分。

5.2

`fcntl()` — 文件控制

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/fcntl.c:316 do_fcntl、:441 SYSCALL_DEFINE3(fcntl)、:465 SYSCALL_DEFINE3(fcntl64)、:37 setfl） - 上一节：5.1 原子性与竞争条件 - 下一节：5.3 打开文件状态标志

本节讲什么

fcntl() 是文件描述符的「万能控制开关」。本节回答三个问题：

  1. fcntl() 的 cmd 有哪些，各自操作哪一层？
  2. 「fd 标志」和「文件状态标志」两组标志为什么不能混？各存在哪、各用什么 cmd 读写？
  3. F_SETFL 为什么改不了读写模式（O_RDONLY/O_WRONLY/O_RDWR）？

1. 原型与内核链路

#include <fcntl.h>

用户态 fcntl(fd, cmd, arg)
      ▼
SYSCALL_DEFINE3(fcntl, fd, cmd, arg)   fs/fcntl.c:441
      ▼
do_fcntl(fd, cmd, arg, filp)           fs/fcntl.c:316
      switch (cmd) {
        F_DUPFD         → f_dupfd(argi, filp, 0)            :326
        F_DUPFD_CLOEXEC → f_dupfd(argi, filp, O_CLOEXEC)    :329
        F_GETFD         → get_close_on_exec(fd) ? FD_CLOEXEC : 0   :331
        F_SETFD         → set_close_on_exec(fd, argi & FD_CLOEXEC) :334

        F_SETFL         → setfl(fd, filp, argi)             :342

2. 主要 cmd 一览

cmd 作用 操作哪一层
F_DUPFD 复制 fd（类似 dup，返回 ≥ arg 的最小可用 fd） 进程 fd 表
F_DUPFD_CLOEXEC 复制 fd 并置 FD_CLOEXEC 进程 fd 表
F_GETFD / F_SETFD 读 / 写 fd 标志（主要是 FD_CLOEXEC） 进程 fd 表项
F_GETFL / F_SETFL 读 / 写 文件状态标志（O_APPEND/O_NONBLOCK…） 打开文件描述的 f_flags
F_GETLK / F_SETLK / F_SETLKW 记录锁（字节范围锁） 见 Ch55

3. 两组标志勿混（高频考点）

存在哪 例子 dup 后共享？ 读写 cmd
fd 标志 进程 fd 表项 FD_CLOEXEC 每个 fd 私有 F_GETFD / F_SETFD
文件状态标志 打开文件描述 O_APPEND、O_NONBLOCK 共享 F_GETFL / F_SETFL

FD_CLOEXEC：exec 时内核自动关闭该 fd，防止句柄泄漏到子程序。

4. 常见陷阱

陷阱 1：F_SETFL 改不了访问模式

fcntl(fd, F_SETFL, O_WRONLY);  /* 无效！ */

F_SETFL 只能改 O_APPEND/O_NONBLOCK/O_ASYNC/O_DIRECT 等状态标志，不能改 O_RDONLY/O_WRONLY/O_RDWR——访问模式在 open 时确定，由 setfl()（fs/fcntl.c:37）校验，它会拒绝改变 f_flags 中的访问模式位。

陷阱 2：F_GETFL 解析访问模式要 O_ACCMODE

int flags = fcntl(fd, F_GETFL);
int acc = flags & O_ACCMODE;   /* 正确 */
/* 错误：flags & O_WRONLY，因为 O_RDONLY == 0，永远测不出 */

O_RDONLY 通常是 0，O_WRONLY=1，O_RDWR=2，必须用 O_ACCMODE 掩码取低 2 位判断。

陷阱 3：F_SETFL 会覆盖，不是按位或

fcntl(fd, F_SETFL, O_NONBLOCK);   /* 覆盖了 O_APPEND 等其他标志！ */
fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK);  /* 正确：先读再或 */

陷阱 4：open + F_SETFD(FD_CLOEXEC) 有竞态窗口

int fd = open(...);
fcntl(fd, F_SETFD, FD_CLOEXEC);  /* open 与 fcntl 之间 exec 可能泄漏 fd */

多线程下另一线程可能在此间隙 exec。用 open(path, O_CLOEXEC) 一步到位（见 5.3）。

场景 本节机制的兑现
非阻塞 fd F_SETFL 设 O_NONBLOCK 是所有事件驱动网络代码（epoll）的前置
防 exec 泄漏 F_SETFD(FD_CLOEXEC) / O_CLOEXEC 防交易子进程继承不该有的 socket/文件句柄
重定向 F_DUPFD 实现安全复制 fd，避免 dup2 前 close 的竞态

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

/* fcntl: 获取/设置 fd 属性 */

    /* F_GETFL：读文件状态标志 */

           (fcntl(fd, F_GETFD) & FD_CLOEXEC) ? "yes" : "no");

    close(fd);
    return 0;
}

代码自测（Q&A）

Q1：fcntl(fd, F_SETFL, flags) 能改哪个标志？ A：只能改文件状态标志：O_APPEND、O_NONBLOCK、O_ASYNC、O_DIRECT 等。不能改访问模式 O_RDONLY/O_WRONLY/O_RDWR（open 时确定），也不能改 O_CREAT/O_EXCL/O_TRUNC 这些只在 open 时有意义的标志。

Q2：FD_CLOEXEC 是文件状态标志，存在打开文件描述里吗？ A：不是。FD_CLOEXEC 是 fd 标志，存在进程 fd 表项里（每个 fd 私有，dup 不共享）。文件状态标志（O_APPEND 等）才存在打开文件描述的 f_flags 里。读写 FD_CLOEXEC 用 F_GETFD/F_SETFD，不是 F_GETFL/F_SETFL。

Q3：fcntl(fd, F_SETFL, O_NONBLOCK) 有什么问题？ A：F_SETFL 会整体覆盖 f_flags，把已有的 O_APPEND 等其他标志一并清掉。正确做法是先 F_GETFL 读回，再 | O_NONBLOCK：fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK)。

Q4：F_GETFL 拿到 flags 后怎么判断访问模式？ A：用 flags & O_ACCMODE 取低 2 位，再与 O_RDONLY(0)/O_WRONLY(1)/O_RDWR(2) 比较。不能直接 flags & O_RDONLY，因为 O_RDONLY == 0，任何 flags 与它相与都是 0。

Q5：F_DUPFD 和 dup 有什么区别？ A：dup(fd) 返回最小可用 fd；F_DUPFD 返回 ≥ 指定参数 的最小可用 fd（可指定下限），且 F_DUPFD_CLOEXEC 能同时设 FD_CLOEXEC，避免了「复制 + 设标志」两步之间的竞态。

5.3

打开文件状态标志（Open File Status Flags）

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/fcntl.c:338 F_GETFL → filp->f_flags、:342 F_SETFL → setfl、:37 setfl） - 上一节：5.2 fcntl() - 下一节：5.4 fd 与打开文件

本节讲什么

上一节讲了 fcntl() 的 F_GETFL/F_SETFL，本节聚焦它们操作的对象——打开文件状态标志（open file status flags）。回答三个问题：

  1. F_GETFL 拿回来的 f_flags 里到底有哪些位？怎么正确解析访问模式？
  2. 哪些标志可以事后用 F_SETFL 改，哪些只能在 open 时定死？
  3. 内核 setfl() 在真正修改前做了哪些校验？

1. 状态标志的归属

文件状态标志存在打开文件描述（struct file 的 f_flags 字段）里，与 fd 标志（FD_CLOEXEC，存进程 fd 表项）是两回事（见 5.2）。F_GETFL 直接读 filp->f_flags：

/* fs/fcntl.c:338 */
case F_GETFL:
    err = filp->f_flags;   /* 返回打开文件描述的状态标志 */
    break;
case F_SETFL:
    err = setfl(fd, filp, argi);   /* :342 */
    break;

2. 获取：F_GETFL 与访问模式解析

int flags = fcntl(fd, F_GETFL);
if (flags & O_APPEND)    /* 追加模式 */
if (flags & O_NONBLOCK)  /* 非阻塞模式 */

/* 访问模式必须用 O_ACCMODE 掩码 */
int acc = flags & O_ACCMODE;   /* O_RDONLY(0) / O_WRONLY(1) / O_RDWR(2) */

陷阱：O_RDONLY == 0，所以 flags & O_RDONLY 恒为 0，必须 flags & O_ACCMODE 再比较。

3. 设置：F_SETFL 可改 vs 不可改

可修改（F_SETFL） 不可修改（只在 open 时设定）
O_APPEND O_RDONLY / O_WRONLY / O_RDWR（访问模式）
O_NONBLOCK O_CREAT
O_ASYNC O_TRUNC
O_DIRECT O_EXCL
O_NOATIME（需 owner） O_CLOEXEC（那是 fd 标志，用 F_SETFD）

4. 内核 setfl() 的校验链（fs/fcntl.c:37）

F_SETFL 不是无脑赋值，内核 setfl() 在修改前做多重校验：

static int setfl(int fd, struct file *filp, unsigned int arg)
{
    /* 1) O_APPEND 不能被清除，若 inode 标记为 append-only（chattr +a） */
    if (((arg ^ filp->f_flags) & O_APPEND) && IS_APPEND(inode))
        return -EPERM;

    /* 2) O_NOATIME 只能由 owner 或特权用户设置 */
    if ((arg & O_NOATIME) && !(filp->f_flags & O_NOATIME))
        if (!inode_owner_or_capable(...))
            return -EPERM;

    /* 3) 兼容：O_NDELAY 等同 O_NONBLOCK */
    if (O_NONBLOCK != O_NDELAY)
        if (arg & O_NDELAY)  arg |= O_NONBLOCK;

    /* 4) O_DIRECT 需要底层支持 FMODE_CAN_ODIRECT */
    if (!S_ISFIFO(inode->i_mode) && (arg & O_DIRECT) &&
        !(filp->f_mode & FMODE_CAN_ODIRECT))
        return -EINVAL;

    /* 5) 交给具体文件系统的 check_flags 钩子（若有） */
    if (filp->f_op->check_flags)
        error = filp->f_op->check_flags(arg);
    ...
}

注意：setfl 不校验访问模式位——因为 F_SETFL 传入的 arg 里访问模式位根本不会被应用（内核只取状态标志位，访问模式在 open 时已固化在 f_mode 里）。

5. HFT / 嵌入式关联

场景 本节机制的兑现
运行时切换非阻塞 F_SETFL 动态开关 O_NONBLOCK，网络/管道 I/O 常用（见 5.9）
O_APPEND 追加日志 打开后可用 F_SETFL 追加 O_APPEND（但注意 append-only 文件不可清除）
O_DIRECT 绕过页缓存 HFT 低延迟落盘场景，需底层设备支持 FMODE_CAN_ODIRECT，否则 setfl 返回 EINVAL
先 F_GETFL 再或 避免 F_SETFL 覆盖已有标志，是并发安全设置状态标志的唯一正确姿势

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/flags.txt", O_RDWR | O_CREAT, 0644);

    /* 读回状态标志，正确解析访问模式 */
    int flags = fcntl(fd, F_GETFL);
    printf("access mode: %d (0=RDONLY 1=WRONLY 2=RDWR)\n",
           flags & O_ACCMODE);

    /* 追加 O_APPEND（先读再或，避免覆盖） */
    fcntl(fd, F_SETFL, flags | O_APPEND);

           (fcntl(fd, F_GETFL) & O_APPEND) ? "yes" : "no");

    return 0;
}

代码自测（Q&A）

Q1：F_GETFL 拿到的 flags，怎么判断文件是以 O_WRONLY 打开的还是 O_RDWR？ A：用 flags & O_ACCMODE 取低 2 位：0→O_RDONLY、1→O_WRONLY、2→O_RDWR。不能 flags & O_WRONLY（O_WRONLY 恰好是 1 可以测出，但 O_RDONLY==0 会漏判），统一用 O_ACCMODE 最稳妥。

Q2：哪些标志可以用 F_SETFL 修改？哪些只能 open 时定死？ A：可改：O_APPEND、O_NONBLOCK、O_ASYNC、O_DIRECT、O_NOATIME（需 owner）。不可改：访问模式（O_RDONLY/O_WRONLY/O_RDWR）、O_CREAT、O_TRUNC、O_EXCL。O_CLOEXEC 是 fd 标志，用 F_SETFD 而非 F_SETFL。

Q3：setfl() 为什么会对「清除 O_APPEND」返回 EPERM？ A：当文件被标记为 append-only（chattr +a，即 IS_APPEND(inode) 为真）时，内核禁止通过 F_SETFL 把 O_APPEND 位从 f_flags 清掉，防止绕过强制追加语义。setfl 检测到 O_APPEND 位被翻转且 inode 是 append-only 时返回 -EPERM。

Q4：F_SETFL 设 O_DIRECT 一定成功吗？ A：不一定。setfl 检查 !(filp->f_mode & FMODE_CAN_ODIRECT) 时返回 -EINVAL——底层文件系统/设备不支持 direct I/O 就无法设置。O_DIRECT 也不是「更快」的万能药，见 Ch13 对页缓存的讨论。

Q5：O_NDELAY 和 O_NONBLOCK 什么关系？ A：两者语义相同（非阻塞），历史遗留两个名字。内核 setfl 里有 if (O_NONBLOCK != O_NDELAY) if (arg & O_NDELAY) arg |= O_NONBLOCK;——即传 O_NDELAY 会自动补上 O_NONBLOCK，保证二者等价。新代码应统一用 O_NONBLOCK。

5.4

fd 与打开文件的关系（Relationship Between File Descriptors and Open Files）

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（include/linux/fdtable.h:27 struct fdtable、:49 struct files_struct；include/linux/fs.h:992 struct file、:1007 f_pos） - 上一节：5.3 打开文件状态标志 - 下一节：5.5 dup / dup2 / dup3

本节讲什么

lseek 改的到底是「fd 数字」还是别的什么？为什么 dup 出来的两个 fd 会互相影响偏移，而两次 open 同一路径却互不影响？本节回答三个问题：

  1. 内核里与「一个打开的文件」相关的三层结构分别是什么、各存什么？
  2. 文件偏移（lseek 改的那个）到底存在哪一层？
  3. dup / fork / 两次 open 分别导致「共享偏移」还是「独立偏移」？

1. 内核三层结构

进程里一个「打开的文件」在内核里不是一层，而是三层。这是本章所有「怪现象」的总根源：

进程级                内核级                     磁盘级
┌─────────────┐   ┌──────────────────┐   ┌──────────────┐
│ fd 表        │   │ 打开文件描述       │   │ inode        │
│ (files_struct│   │ (struct file)    │   │ (磁盘上的真实 │
│  内的 fdtable)│──▶│  f_pos  偏移      │──▶│  文件元数据)   │
│  + fd 标志    │   │  f_flags 状态标志 │   │  size/权限/块  │
│ (FD_CLOEXEC) │   │  f_mode 访问模式  │   │  链接计数      │
└─────────────┘   │  f_op   操作表    │   └──────────────┘
                  └──────────────────┘
层 谁持有 存什么 内核结构
1. 进程 fd 表 每进程独有 指向 struct file 的指针 + fd 标志（主要是 FD_CLOEXEC） files_struct → fdtable（include/linux/fdtable.h:49 / :27）
2. 打开文件描述 内核全局，可被多个 fd 共享 文件偏移 f_pos（lseek 改的就是它）、状态标志（f_flags：O_APPEND/O_NONBLOCK…）、访问模式（f_mode）、操作表（f_op）、引用计数 f_count struct file（include/linux/fs.h:992，f_pos 在 :1007）
3. inode 磁盘上的真实文件 大小、权限、磁盘块位置、链接计数 struct inode

关键结论：lseek 改的是「打开文件描述」里的 f_pos，不是「fd 数字本身」，更不是 inode。fd 数字只是一个索引，指向打开文件描述。

2. 共享 vs 独立：偏移的关键推论（高频面试点）

操作 打开文件描述 偏移
同一进程两次独立 open() 同一路径 两个 各自独立
dup / dup2 / fcntl(F_DUPFD) 同一个（引用计数 +1） 共享
fork 后子进程继承 共享父进程的打开描述 共享（子进程复制 fd 表，但表项指向同一个 struct file）
O_APPEND 写前内核原子定位到 EOF 再写 见 5.1 原子性 
两次 open 同一文件：            dup / fork：
fd3 ──▶ [struct file A] pos=0   fd4 ──┐
fd5 ──▶ [struct file B] pos=0         ├──▶ [struct file C] pos=共享
        （各自独立偏移）        fd6 ──┘   （lseek fd4 会影响 fd6）

3. 为什么 dup 共享而 open 不共享

  • open()：每次调用都会 do_filp_open 出一个新的 struct file，初始 f_pos = 0，再挂到 fd 表。两次 open = 两个 struct file，偏移自然独立。
  • dup()：不创建新 struct file，只是让新 fd 表项指向同一个 struct file，并把它的 f_count 引用计数 +1。既然指向同一个 struct file，f_pos 就只有一个，lseek 通过任一 fd 都会改到它。
  • fork()：子进程复制父进程的 files_struct（fd 表），但表项指针原样复制——父子的 fd 指向同一个 struct file。所以父子共享偏移，直到一方 close（close 只是让 f_count -1，减到 0 才真正释放 struct file）。

4. HFT / 嵌入式关联

场景 本节机制的兑现
多线程共享 fd 的坑 两个线程用同一 fd 做 lseek+read 会互相踩偏移，用 pread/pwrite 规避（见 5.6）
fork 后父子抢日志 父子共享打开描述，都会从同一 f_pos 继续写，可能交错；必要时 O_APPEND 或各自 open
重定向不泄漏 dup2 后新 fd 与旧 fd 共享描述，理解 f_count 才能正确配对 close（见 5.5）
嵌入式设备 fd 紧张 三层结构意味着「一个打开描述可被多个 fd 引用」，正确 dup/close 能复用底层资源

5. 代码示例

#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

/* 5.4 三层结构：dup 共享偏移，两次 open 独立偏移 */
int main(void) {
    int fd = open("/tmp/sparse.txt", O_RDWR | O_CREAT, 0644);
    write(fd, "ABCDE", 5);

    /* dup 后 fd 和 fd2 指向同一个打开文件描述 → 共享偏移 */
    int fd2 = dup(fd);

    lseek(fd, 0, SEEK_SET);
    char buf[3];
    read(fd, buf, 2);                       /* fd 读 2 字节 → 偏移变 2 */
    printf("fd  偏移: %ld\n", lseek(fd, 0, SEEK_CUR));   /* 2 */
    printf("fd2 偏移: %ld (共享)\n", lseek(fd2, 0, SEEK_CUR)); /* 2 */

    /* 两次独立 open → 各自独立偏移 */
    int fd3 = open("/tmp/sparse.txt", O_RDONLY);
    printf("fd3 偏移: %ld (独立)\n", lseek(fd3, 0, SEEK_CUR)); /* 0 */

    close(fd); close(fd2); close(fd3);
    return 0;
}

代码自测（Q&A）

Q1：lseek 修改的偏移到底存在哪一层？ A：存在打开文件描述（struct file 的 f_pos，include/linux/fs.h:1007）里，不是 fd 数字本身，也不是 inode。fd 只是指向 struct file 的索引。所以「同一个 struct file 被多个 fd 引用」时，lseek 通过任一 fd 都会改到同一个 f_pos。

Q2：两次 open() 同一路径，偏移共享吗？为什么？ A：不共享。每次 open 都会 do_filp_open 出一个新的 struct file（f_pos 各自初始为 0），再挂到 fd 表。两个 struct file = 两个独立偏移。

Q3：fork 后父子进程的 fd 偏移共享吗？ A：共享。fork 复制的是 fd 表（files_struct），但表项指针原样复制，父子的 fd 指向同一个 struct file，所以 f_pos 共享。一方 close 只是 f_count 减 1，减到 0 才释放 struct file。

Q4：dup 出来的新 fd 和旧 fd，close 一个会影响另一个吗？ A：close 只是把 struct file 的 f_count 减 1，并清掉该 fd 表项。只要 f_count 未减到 0，struct file 就还活着，另一个 fd 仍可正常读写同一打开描述（共享偏移）。

Q5：O_APPEND、O_NONBLOCK 这些状态标志存在哪一层？FD_CLOEXEC 呢？ A：O_APPEND/O_NONBLOCK 存在打开文件描述的 f_flags 里（dup 共享）；FD_CLOEXEC 存在进程 fd 表项里（每个 fd 私有）。这是两组标志的归属差异，详细见 5.2 fcntl() 和 5.3。

5.5

`dup` / `dup2` / `dup3` — 复制文件描述符

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/fcntl.c:316 do_fcntl、:326 F_DUPFD → f_dupfd、:329 F_DUPFD_CLOEXEC；dup/dup2/dup3 的 SYSCALL_DEFINE 位于 fs/file.c，缓存未收录该文件，作架构说明） - 上一节：5.4 fd 与打开文件 - 下一节：5.6 pread / pwrite

本节讲什么

dup 家族用来「复制文件描述符」，是 shell 管道、I/O 重定向的基石。本节回答三个问题：

  1. dup / dup2 / dup3 三者的区别是什么？复制后新旧 fd 共享什么？
  2. 为什么 dup2 的「先关目标再复制」是原子的，而 close + fcntl(F_DUPFD) 不是？
  3. dup2 复制出的 fd 为什么不继承 FD_CLOEXEC？该怎么处理？

1. 原型与内核链路

#include <unistd.h>

2. 三者的区别

函数 目标编号 已占用时 FD_CLOEXEC
dup(oldfd) 最小可用 — 不继承（新 fd 无 FD_CLOEXEC）
dup2(oldfd, newfd) 指定 newfd 原子关闭再复制 不继承
dup3(oldfd, newfd, flags) 指定 newfd 原子关闭再复制 可 O_CLOEXEC 一步设置

3. 典型用途：I/O 重定向

/* shell 的 `cmd > file.txt` 核心 */

dup2(fd, STDOUT_FILENO);   /* stdout 指向 file.txt */
close(fd);                 /* 关掉多余副本 */
execvp(cmd, argv);         /* 新程序继承重定向后的 stdout */

4. 常见陷阱

陷阱 1：dup2 复制出的 fd 不继承 FD_CLOEXEC

dup2(oldfd, newfd);   /* newfd 没有 FD_CLOEXEC */

dup2 的语义是「复制 oldfd 到 newfd」，而 FD_CLOEXEC 是 fd 表项的标志，不会被复制。若希望 exec 时自动关闭，需 dup3(oldfd, newfd, O_CLOEXEC) 或事后 fcntl(newfd, F_SETFD, FD_CLOEXEC)。

陷阱 2：dup2 目标已打开会先关

dup2(oldfd, newfd);   /* newfd 已开 → 先 close(newfd) 再复制 */

这是原子的（内核 do_dup2 里完成），不存在「关闭后、复制前」被信号/线程插入的窗口。若不想覆盖，用 fcntl(F_DUPFD) 选一个空闲编号。

陷阱 3：共享偏移的意外

int fd2 = dup(fd1);
lseek(fd1, 0, SEEK_SET);   /* fd2 的偏移也变了！ */

dup 复制的是「指向同一 struct file 的指针」，偏移共享。想要独立偏移请用 open 重新打开。

Q1：dup2(oldfd, newfd) 和 dup(oldfd) 的区别？ A：dup 返回最小可用 fd；dup2 指定目标编号 newfd（已占用则先原子关闭再复制）。dup2 用于重定向（把 fd 钉在 stdin/stdout 等固定编号上），dup 用于随便复制一个。

Q2：dup 复制的 fd 有独立的文件偏移吗？ A：没有。dup 复制的 fd 指向同一个打开文件描述（同一个 struct file），共享 f_pos 和 f_flags。lseek 通过任一 fd 都会影响另一个。

Q3：以下代码在 exec 后，stdin 指向什么？为什么？

int fd = open("f.txt", O_RDONLY);
dup2(fd, STDIN_FILENO);
execvp("cat", argv);

A：exec 后 stdin（fd 0）仍指向 f.txt，因为 dup2 复制出的 fd 默认没有 FD_CLOEXEC，exec 不会关闭它。这正是 shell 重定向的原理——子程序继承被重定向的 fd。

Q4：dup2(fd, 2) 和 close(2); fcntl(fd, F_DUPFD, 2) 为什么前者更安全？ A：dup2 的「关 2 + 复制」在内核 do_dup2 里原子完成，中间无窗口；close(2) 和 fcntl 是两步，中间可能被信号中断或另一线程抢占 fd 2，导致复制到错误位置。多线程/信号环境应优先 dup2/dup3。

Q5：想复制 fd 且 exec 后自动关闭，有几种写法？ A：三种：① dup3(oldfd, newfd, O_CLOEXEC)；② fcntl(oldfd, F_DUPFD_CLOEXEC, min)；③ dup2 后 fcntl(newfd, F_SETFD, FD_CLOEXEC)（但③有竞态窗口，不推荐多线程下用）。①和②是原子的。

5.6

`pread` / `pwrite` — 指定偏移读写

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/read_write.c:652 ksys_pread64、:672 SYSCALL_DEFINE4(pread64)、:686 ksys_pwrite64、:706 SYSCALL_DEFINE4(pwrite64)） - 上一节：5.5 dup / dup2 / dup3 - 下一节：5.7 readv / writev

本节讲什么

pread/pwrite 是「在指定偏移处读写、但不改变文件当前偏移」的原子 I/O。本节回答三个问题：

  1. pread 和 lseek+read 组合到底差在哪？为什么多线程下前者安全、后者会乱？
  2. 内核里 pread 为什么能做到「用参数偏移、不碰 f_pos」？
  3. pread 有哪些限制（哪些对象不能用）？

1. 原型与内核链路

#include <unistd.h>
ssize_t pread(int fd, void *buf, size_t count, off_t offset);
ssize_t pwrite(int fd, const void *buf, size_t count, off_t offset);

用户态 pread(fd, buf, count, pos)
      ▼
SYSCALL_DEFINE4(pread64, fd, buf, count, pos)   fs/read_write.c:672
      ▼
ksys_pread64(fd, buf, count, pos)               fs/read_write.c:652
      if (pos < 0)  return -EINVAL;
      f = fdget(fd);
      ret = -ESPIPE;
      if (f.file->f_mode & FMODE_PREAD)         ← 对象必须支持「指定偏移读」
          ret = vfs_read(f.file, buf, count, &pos);   ← 传 &pos，不是 f_pos！
      fdput(f);

关键点：vfs_read(file, buf, count, &pos) 传入的是局部变量 pos 的地址，而不是 file->f_pos 的地址。所以读完后，struct file 的 f_pos 原封不动——这正是 pread 与 read 的本质区别。pwrite 对称（ksys_pwrite64 → vfs_write(..., &pos)）。

2. 核心语义

特性 说明
偏移来源 参数 offset，不读也不写 文件的 f_pos
原子性 单次调用内「定位 + 读写」原子完成
与 lseek+read 的差异 lseek+read 是两次调用，中间 f_pos 可能被其他线程改掉
返回后偏移 文件 f_pos 保持不变

3. 多线程安全：为什么 pread 比 lseek+read 强

共享 fd 的偏移（f_pos）只有一个，多线程用 lseek+read 会互相踩：

线程 A: lseek(fd, 100, SEEK_SET)  → f_pos = 100
线程 B: lseek(fd, 500, SEEK_SET)  → f_pos = 500   ← 覆盖了 A！
线程 A: read(fd, buf, 10)         → 从 500 读！错误

pread(fd, buf, 10, 100) 用局部 pos，不碰共享的 f_pos，多线程调用互不干扰，天然线程安全。

4. 限制

限制 原因
不可用于管道/socket/终端 这些对象不可 seek，没有「指定偏移」的概念，内核返回 -ESPIPE（f_mode 无 FMODE_PREAD/FMODE_PWRITE）
offset 不能为负 ksys_pread64 里 if (pos < 0) return -EINVAL

5. HFT / 嵌入式关联

场景 本节机制的兑现
多线程回测引擎 多个线程各自 pread 同一历史数据文件的不同偏移，互不干扰
并发写日志槽位 按「记录号 × 记录大小」计算偏移，用 pwrite 定点写入，无需锁偏移
减少 syscall pread 一次调用替代 lseek+read 两次，降低陷入内核的延迟
数据库页读取 按页号随机 pread 是 DB 引擎（如 SQLite/LevelDB）随机读的标准姿势

6. 代码示例

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/tmp/pread_test.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    write(fd, "0123456789ABCDEF", 16);

    /* pread 从偏移 5 读 3 字节，不改变 f_pos */

    pread(fd, buf, 3, 5);
    buf[3] = '\0';

           (long)lseek(fd, 0, SEEK_CUR));   /* 16 */

    pwrite(fd, "XYZ", 3, 10);

    printf("pwrite(10,XYZ): %s\n", buf);

    close(fd);
    return 0;
}

代码自测（Q&A）

Q1：pread 和 lseek(SEEK_SET) + read 的本质区别是什么？ A：pread 把「定位 + 读」合并成一次原子调用，用参数 offset 定位、不修改文件 f_pos。lseek+read 是两次调用，中间 f_pos 可能被其他线程/信号打断后改变，导致读到错误位置。多线程共享 fd 时 pread 线程安全，lseek+read 不安全。

Q2：pread 读完后，文件的当前偏移（f_pos）是多少？ A：不变。内核 ksys_pread64 调用 vfs_read(file, buf, count, &pos)，传入的是局部变量 pos 的地址，而非 file->f_pos。所以 f_pos 保持 pread 调用前的值。

Q3：对管道调用 pread 会怎样？ A：返回 -1，errno = ESPIPE。管道/socket/终端不可 seek，没有「指定偏移」语义。内核 ksys_pread64 里 if (!(f_mode & FMODE_PREAD)) return -ESPIPE，普通文件才有 FMODE_PREAD。

Q4：pread 的 offset 传负数会怎样？ A：返回 -1，errno = EINVAL。ksys_pread64 开头 if (pos < 0) return -EINVAL。偏移必须是合法非负值。

Q5：preadv/pwritev 是什么？ A：pread/pwrite 的「散布/聚集」版本，一次系统调用在指定偏移处读写多个不连续缓冲区（struct iovec 数组），内核入口 do_preadv/do_pwritev（fs/read_write.c:994/:1017），结合了 5.6 的「指定偏移」和 5.7 的「多缓冲」两个特性。

5.7

`readv` / `writev` — 散布/聚集 I/O

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/read_write.c:940 do_readv、:964 do_writev、:905 vfs_readv、:922 vfs_writev、:1040 SYSCALL_DEFINE3(readv)、:1046 SYSCALL_DEFINE3(writev)） - 上一节：5.6 pread / pwrite - 下一节：5.8 truncate / ftruncate

本节讲什么

readv/writev 用一次系统调用读写多个不连续缓冲区。本节回答三个问题：

  1. struct iovec 是什么？「散布读（scatter）/ 聚集写（gather）」分别指什么？
  2. 内核怎么把用户态的 iovec 数组变成一次 I/O？
  3. 相比循环多次 read/write，readv/writev 的优势和原子性边界在哪？

1. 原型与内核链路

  • 聚集写（gather write）：writev 把多个缓冲区的数据聚集成一段连续写出。

      ▼

3. 优势与原子性边界

优势 说明
减少 syscall 1 次 writev 替代 N 次 write，降低用户态/内核态切换开销
单次操作完整性 一次 writev 传输的数据块，对普通文件而言不会被其他进程的 write 从中间交错（单次调用原子）
协议友好 固定头 + 变长体（header + payload）一次写出，天然对应协议帧格式

⚠️ 原子性边界：writev 的原子性是「单次调用内不与其他 write 交错」，但返回值仍可能小于所有 iov_len 之和（部分写/短读，需按返回值判断实际传了多少）。它不保证「要么全写、要么不写」。

场景 本节机制的兑现
协议帧组装 writev 一次写出「帧头 + 载荷」，避免拼大缓冲区的内存拷贝

减少上下文切换 HFT 热点路径上少一次 syscall 就是少一次陷入内核的延迟
与 sendmsg/recvmsg 同源 socket 的 sendmsg/recvmsg 内部也用 iovec/iov_iter（见 Ch56-61）

2. 行为语义

场景 结果

length > 当前大小 扩展，新增区域填充 0（读出来是 \0），磁盘上形成稀疏文件（空洞不占块）
length == 当前大小 无大小变化（但可能更新 mtime）

3. 典型用途

  • 清空文件：ftruncate(fd, 0) 等价于「删内容、保留 inode」，比 open(O_TRUNC) 重开更直接。
  • 预分配空间：先 ftruncate 到目标大小，再随机写各槽位（配合 pwrite），适合定长记录文件。
  • 共享内存：ftruncate 设置共享内存对象大小（SysV 共享内存 Ch48、POSIX 共享内存 Ch54）。
  • 创建稀疏文件：ftruncate(fd, 10GB) 得到一个「逻辑 10GB、物理几乎不占块」的文件。

代码自测（Q&A）

Q1：truncate 和 ftruncate 的区别？ A：truncate(path, length) 按路径定位文件，不需要先打开（但需要目录写权限）；ftruncate(fd, length) 按已打开的 fd 操作，要求 fd 以写方式打开（f_mode & FMODE_WRITE），且是普通文件。两者最终都落到 do_truncate。

Q2：把文件 ftruncate 到比当前更大的大小会怎样？ A：文件被扩展，新增区域填充 0（读出来是 \0）。若扩展幅度大，中间形成文件空洞（sparse）——逻辑大小很大，但空洞区不分配磁盘块，实际占用极小。

Q3：ftruncate 一个 append-only 文件会怎样？ A：返回 -1，errno = EPERM。do_sys_ftruncate 检查 IS_APPEND(inode)，append-only 文件（chattr +a）禁止截断，防止绕过强制追加语义。

Q4：ftruncate 需要什么权限？ A：fd 必须以写方式打开（FMODE_WRITE），且对象必须是普通文件（S_ISREG），否则 -EINVAL。此外 do_truncate 会清除文件的 suid/sgid/capabilities（dentry_needs_remove_privs），防止特权位残留。

Q5：mmap 一个文件前为什么常先 ftruncate？ A：mmap 映射的长度不能超过文件大小，否则访问映射区超出文件末尾的部分会触发 SIGBUS。先 ftruncate(fd, target_size) 把文件撑到目标大小，再 mmap，映射区内才能安全读写（详见 Ch49）。

5.9

非阻塞 I/O（`O_NONBLOCK`）

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/fcntl.c:37 setfl 中 O_NDELAY → O_NONBLOCK 归一；O_NONBLOCK 存于 file->f_flags，由管道/socket 的 read/write 实现检查） - 上一节：5.8 truncate / ftruncate - 下一节：5.10 大文件 LFS

本节讲什么

O_NONBLOCK 让「可能阻塞」的 I/O 变成「立即返回」。本节回答三个问题：

  1. O_NONBLOCK 对哪些对象生效？为什么对普通磁盘文件通常无效？
  2. 非阻塞读/写失败时返回什么、errno 是什么？和真正的错误怎么区分？
  3. O_NONBLOCK 为什么不等于异步 I/O（AIO）？

1. 语义：不睡、立刻返回

O_NONBLOCK 的核心是轮询式语义：当操作无法立即完成时，内核不把进程挂起睡眠，而是立刻返回 -1 + errno = EAGAIN/EWOULDBLOCK，让调用方稍后重试。

对象 非阻塞行为
普通磁盘文件 通常无效果——磁盘读不靠「非阻塞」变快，read 几乎总能立即返回（页缓存命中）或短暂等待
管道 / FIFO 读端无数据时 read 立即 -1 + EAGAIN；写端满时 write 立即 -1 + EAGAIN
socket 无数据可读/发送缓冲满时，read/write 立即 -1 + EAGAIN（EWOULDBLOCK 同值）
终端 读不到数据时立即返回

O_NONBLOCK ≠ 异步 AIO。它只是「不睡、立刻返回」的同步轮询语义；真正的异步是「发起请求后立即返回，完成时内核通知」（见 Ch63 epoll / POSIX AIO）。

2. 如何设置

两种方式，效果相同（都写进 file->f_flags）：

/* 方式 1：open 时指定 */
int fd = open(path, O_RDWR | O_NONBLOCK);

/* 方式 2：fcntl 动态切换（先读再或，避免覆盖） */
int flags = fcntl(fd, F_GETFL);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

内核 setfl（fs/fcntl.c:37）里有 if (arg & O_NDELAY) arg |= O_NONBLOCK;——历史别名 O_NDELAY 被归一为 O_NONBLOCK（见 5.3）。

3. 非阻塞读写的返回值判断

ssize_t n = read(fd, buf, sizeof(buf));
if (n < 0) {
    if (errno == EAGAIN || errno == EWOULDBLOCK)
        /* 只是「现在没数据」，不是错误，稍后重试 */
    else
        /* 真错误 */
}
返回 含义
> 0 读到/写了 n 字节
0 EOF（读端）/ 对端关闭
-1 + EAGAIN/EWOULDBLOCK 暂时无数据/无空间，非错误，可重试
-1 + 其他 errno 真错误

4. HFT / 嵌入式关联

场景 本节机制的兑现
事件驱动网络 O_NONBLOCK + epoll 是 HFT 网络代码的标准骨架（见 Ch63）
非阻塞连接 connect 设 O_NONBLOCK 可并发发起多路连接，避免串行阻塞
忙轮询替代睡眠 嵌入式实时采集时用非阻塞读 + 轮询，避免进程睡眠引入调度延迟
避免死锁 双向管道（父子双向通信）用非阻塞避免双方同时阻塞等待

5. 代码示例

#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>

/* O_NONBLOCK: 管道读端设为非阻塞 */
int main(void) {
    int pipefd[2];
    if (pipe(pipefd) < 0) { perror("pipe"); return 1; }

    /* 读端设非阻塞 */
    int flags = fcntl(pipefd[0], F_GETFL);
    fcntl(pipefd[0], F_SETFL, flags | O_NONBLOCK);

    char buf[64];
    ssize_t n = read(pipefd[0], buf, sizeof(buf));
    if (n < 0) {
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            printf("read 返回 -1, errno=EAGAIN（无数据可读）\n");
        else
            perror("read");
    }

    /* 写入数据后非阻塞读就能拿到 */
    write(pipefd[1], "hi", 2);
    n = read(pipefd[0], buf, sizeof(buf));
    printf("第二次 read: %zd 字节: %.*s\n", n, (int)n, buf);

    close(pipefd[0]); close(pipefd[1]);
    return 0;
}

代码自测（Q&A）

Q1：O_NONBLOCK 对普通磁盘文件有效吗？ A：通常无效。普通文件的 read/write 几乎总能立即返回（页缓存命中或短暂等待），O_NONBLOCK 主要针对可能阻塞的对象——管道/FIFO/socket/终端。磁盘 I/O 的「非阻塞」要靠 AIO/O_DIRECT 等机制，不是 O_NONBLOCK。

Q2：非阻塞 read 返回 -1 + EAGAIN 是错误吗？ A：不是。EAGAIN（与 EWOULDBLOCK 同值）表示「现在没有数据可读」，是正常信号，调用方应稍后重试或交给 epoll 等待。真正的错误是其他 errno（如 EBADF、EFAULT）。

Q3：O_NONBLOCK 和异步 I/O（AIO）是一回事吗？ A：不是。O_NONBLOCK 是同步语义——调用立即返回 EAGAIN，但数据并未被读，要你自己重试；AIO 是异步语义——发起读请求后立即返回，内核在后台完成，完成时通知你。前者是「不睡」，后者是「不等」。

Q4：open(path, O_RDWR | O_NONBLOCK) 和 fcntl(F_SETFL) 设非阻塞，效果一样吗？ A：一样，最终都写进 file->f_flags 的 O_NONBLOCK 位。区别是 open 一次性、fcntl 可运行时动态开关（配合 F_GETFL 先读回再或）。fcntl 方式适合「同一 fd 有时阻塞有时非阻塞」的场景。

Q5：双向管道父子通信为什么要用非阻塞？ A：若父子都用阻塞模式读写同一管道，可能双方同时阻塞等待对方（父等读、子等读），造成死锁。设 O_NONBLOCK 让「无数据时立即返回」，配合轮询或 select/epoll 打破死锁（详见 Ch44 管道）。

5.10

大文件支持（I/O on Large Files，LFS）

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（fs/open.c:157 do_sys_ftruncate 中 O_LARGEFILE/MAX_NON_LFS 判定、:217/:222 truncate64/ftruncate64；fs/read_write.c:672/:706 pread64/pwrite64） - 上一节：5.9 非阻塞 I/O - 下一节：5.11 /dev/fd

本节讲什么

「大文件」指超过 32 位偏移表示范围（约 2GB）的文件。本节回答三个问题：

  1. 32 位 off_t 的上限到底是多少？为什么是「约 2GB」？
  2. 如何让程序支持大文件？_FILE_OFFSET_BITS=64 做了什么？
  3. 内核侧为什么有 *64 系列 syscall 和 O_LARGEFILE？

1. 问题根源：32 位 off_t

历史上 off_t 是 32 位有符号整数，可表示范围约 −2GB ~ +2GB（精确是 −2³¹ ~ 2³¹−1 字节）。于是：

  • 32 位 off_t 的文件最大只能到 2GB − 1（约 2.1 GB）；
  • 超过 2GB 的文件，lseek 定位、truncate 设置大小都会溢出。

32 位平台上，老代码需要「显式开启」大文件支持（LFS，Large File Support）；64 位平台（如 x86-64/aarch64）默认 off_t 就是 64 位，无需特别处理。

2. 开启大文件支持

做法 说明
推荐：-D_FILE_OFFSET_BITS=64 编译期把 off_t 及相关函数（lseek→lseek64 等）自动切到 64 位版本
备选：off64_t / open64 / lseek64 / pread64 显式调用 64 位版本函数 
#define _FILE_OFFSET_BITS 64   /* 或编译时 gcc -D_FILE_OFFSET_BITS=64 */
#include <fcntl.h>
#include <unistd.h>
/* 之后 off_t 自动为 64 位，lseek 等自动映射到 64 位版本 */

3. 内核侧：*64 syscall 与 O_LARGEFILE

内核为兼容 32 位用户态，提供了 64 位偏移的 syscall，并在 32 位进程打开大文件时要求 O_LARGEFILE 标志：

用户态 lseek(fd, huge_offset, SEEK_SET)
      ▼  （_FILE_OFFSET_BITS=64 时 glibc 转调 lseek64）
SYSCALL_DEFINE3(lseek)                    fs/read_write.c:311（off_t 在 64 位内核里本就是 64 位）

truncate 的 LFS 版本：
SYSCALL_DEFINE2(truncate64)               fs/open.c:217
SYSCALL_DEFINE2(ftruncate64)              fs/open.c:222

do_sys_ftruncate（fs/open.c:157）里的大文件判定：

if (f.file->f_flags & O_LARGEFILE)
    small = 0;                          /* 以 O_LARGEFILE 打开，按大文件处理 */
...
if (small && length > MAX_NON_LFS)      /* 未开 LFS 且超 2GB → -EINVAL */
    goto out_putf;

要点：32 位程序若不设 _FILE_OFFSET_BITS=64（即 small=1），ftruncate 超过 MAX_NON_LFS（2GB−1）会失败。设了 _FILE_OFFSET_BITS=64 后，glibc 自动带上 O_LARGEFILE，small=0，即可操作大文件。

场景 本节机制的兑现

跨 32 位平台移植 嵌入式 32 位 ARM 上操作大文件必须显式开 LFS，否则静默失败

5.11

`/dev/fd` — 通过路径访问已打开的 fd

本章：TLPI 第 05 章 — File I/O: Further Details 源码核验：Linux v6.6（/dev/fd 是 /proc/self/fd 的符号链接；open("/dev/fd/N") 由 procfs 魔符号链接机制解析为「复制 fd N」，实现位于 fs/proc/fd.c，缓存未收录，作架构说明） - 上一节：5.10 大文件 LFS - 下一节：5.12 临时文件

本节讲什么

/dev/fd/N 让你「用路径名」去访问一个已经打开的文件描述符 N。本节回答三个问题：

  1. open("/dev/fd/N") 到底做了什么？和 dup(N) 是一回事吗？
  2. /dev/fd 在 Linux 上的真实实现是什么？
  3. 为什么 shell 脚本里会看到 cmd < /dev/fd/3 这种写法？

1. 语义：open("/dev/fd/N") ≈ 复制 fd N

int fd = open("/dev/fd/0", O_RDONLY);   /* 约等于 dup(0)，得到 stdin 的副本 */

open("/dev/fd/N") 返回一个新的 fd，它指向与 fd N 相同的打开文件描述——等价于 dup(N) 的效果（共享偏移与状态标志，见 5.4 / 5.5）。

⚠️ 细节差异：open("/dev/fd/N", flags) 不是无条件等于 dup(N)——open 传入的 flags（如访问模式）必须与 fd N 的打开方式兼容。例如 fd N 是只读的，open("/dev/fd/N", O_WRONLY) 会失败。且 /dev/fd/N 走的是路径解析（procfs 符号链接），而 dup 直接复制 fd 表项，二者语义近似但路径不同。

2. Linux 实现：/dev/fd → /proc/self/fd

Linux 上 /dev/fd 本身是一个符号链接，指向 /proc/self/fd：

/dev/fd          ──(符号链接)──▶  /proc/self/fd
/dev/fd/0        ──▶  /proc/self/fd/0   ← fd 0（stdin）的「魔符号链接」
/dev/fd/1        ──▶  /proc/self/fd/1   ← fd 1（stdout）

/proc/self/fd/N 是 magic symlink（魔符号链接）：内核不按普通路径解析它，而是识别出「这是当前进程的 fd N」，进而把 open 变成对 fd N 的复制（引用同一个 struct file）。实现位于 fs/proc/fd.c（procfs 的 proc_fd_link / tid_fd_revalidate）。

3. 用途

  • shell 重定向：cmd < /dev/fd/3 让 cmd 的 stdin 指向「当前 shell 的 fd 3」——常用于把已打开的文件描述符传给子进程。
  • 弥补 exec 无法传 fd：exec 只能继承 fd 0/1/2 或 FD_CLOEXEC 未设的 fd，/dev/fd/N 提供了一种「用路径间接引用 fd」的补充手段。
  • C 里复制 fd 的路径化写法：open("/dev/fd/1", O_WRONLY) 得到 stdout 副本。

4. HFT / 嵌入式关联

场景 本节机制的兑现
shell 编排进程 交易脚本用 /dev/fd/N 在管道间传递 fd，避免 dup 手写
调试/工具链 把已打开的 socket/日志 fd 以路径形式交给子工具
嵌入式脚本 busybox shell 下用 /dev/fd/N 做重定向（若无 /proc 挂载则不可用）

#include <unistd.h>
#include <stdio.h>

    /* 打开 /dev/fd/1 得到 stdout 的副本 */

    if (fd2 < 0) { perror("open /dev/fd/1"); return 1; }
    write(fd2, "via /dev/fd/1\n", 14);
    printf("open(\"/dev/fd/1\") = fd %d\n", fd2);

    close(fd2);
    return 0;
}

代码自测（Q&A）

Q1：open("/dev/fd/N", O_RDONLY) 和 dup(N) 是一回事吗？ A：效果近似但不完全等价。两者都得到「指向同一打开文件描述」的新 fd（共享偏移/状态标志）。但 open("/dev/fd/N") 走路径解析（procfs 魔符号链接），传入的 flags 必须与 fd N 的打开方式兼容；dup(N) 直接复制 fd 表项，无 flags 校验。dup 更快更直接，/dev/fd/N 主要用于「用路径引用 fd」的场景。

Q2：Linux 上 /dev/fd 的真实实现是什么？ A：/dev/fd 是符号链接，指向 /proc/self/fd。/proc/self/fd/N 是「魔符号链接（magic symlink）」，内核不按普通路径解析，而是把它识别为当前进程的 fd N，把 open 变成对 fd N 的引用复制。实现位于 fs/proc/fd.c。

Q3：open("/dev/fd/N", O_WRONLY) 在什么情况下会失败？ A：当 fd N 不是以可写方式打开时（如 stdin 是只读的），open("/dev/fd/0", O_WRONLY) 会失败——因为请求的访问模式与 fd N 的实际打开模式不兼容。dup 则无此限制。

Q4：shell 里 cmd < /dev/fd/3 是什么意思？ A：让 cmd 的 stdin 指向「当前 shell 的 fd 3」。即把 shell 已打开的 fd 3 以路径方式传给子进程，等价于把 fd 3 重定向到 cmd 的 stdin（fd 0）。

Q5：嵌入式环境用 /dev/fd/N 有什么前提？ A：需要 /proc 文件系统已挂载（因为 /dev/fd 指向 /proc/self/fd）。若嵌入式/busybox 环境未挂载 /proc，/dev/fd/N 不可用，此时应直接用 dup/dup2 复制 fd。

创建临时文件（Creating Temporary Files）

本节讲什么

临时文件无处不在（编译器中间产物、日志轮转、下载缓存），但「怎么安全地建」是个经典陷阱。本节回答三个问题：

  1. mkstemp / tmpfile / mkdtemp 各自怎么用、什么场景选哪个？
  2. 为什么 tmpnam / mktemp 是不安全的，本质缺陷是什么？
  3. 如何让临时文件「关闭时自动删除」？

1. 安全 API 一览

函数 原型 返回 删除时机
mkstemp int mkstemp(char *template) fd（已创建，0600） 需手动 unlink
tmpfile FILE *tmpfile(void) FILE* 关闭时自动删除
mkdtemp char *mkdtemp(char *template) 目录名 需手动 rmdir
  • mkstemp：模板末尾必须是 XXXXXX（6 个 X），函数原子地创建文件并用唯一随机串替换 X。文件权限 0600，返回 fd。
  • tmpfile：创建匿名临时文件（O_TMPFILE 或 mkstemp+立即 unlink 的等价物），返回 FILE*，关闭时自动删除。
  • mkdtemp：创建唯一临时目录。

2. 为什么不安全：tmpnam / mktemp 的 TOCTOU

char *name = tmpnam(NULL);        /* 返回一个「看似可用」的文件名 */
int fd = open(name, O_CREAT);     /* 竞态！另一进程可能已抢先创建/替换 */

tmpnam 只返回一个可预测/未保留的文件名，open 是独立的第二步。两步之间另一进程可能： - 抢先创建同名文件（你 open 到别人的文件）； - 用符号链接把名字指向敏感文件（如 /etc/passwd）。

这正是 5.1 讲的 TOCTOU。mkstemp 用 O_CREAT | O_EXCL 在内核一次调用内「生成随机名 + 独占创建」，消除竞态窗口。

3. 让临时文件「关闭时自动删除」

mkstemp 创建的文件要手动删。技巧：创建后立即 unlink，利用「文件被 unlink 后仍可被已打开的 fd 访问，最后一个 fd 关闭时真正删除」的语义：

char template[] = "/tmp/myappXXXXXX";
int fd = mkstemp(template);   /* 创建 + 返回 fd */
unlink(template);             /* 立即 unlink：目录里看不到，但 fd 仍可读写 */
/* ... 用 fd 读写 ... */
close(fd);                    /* 最后一个引用关闭 → 文件被真正回收 */

这等价于 tmpfile() 的行为（匿名临时文件），但用 fd 而非 FILE*。

4. HFT / 嵌入式关联

场景 本节机制的兑现
原子写配置文件 先写临时文件，再 rename 覆盖，避免进程崩溃留下半写文件
多进程唯一临时名 mkstemp 的 O_EXCL 保证并发下每个进程拿到不同文件
敏感数据落盘 mkstemp 的 0600 权限 + 立即 unlink，避免临时文件被其他进程读取
嵌入式 tmpfs 临时文件放 tmpfs（内存），重启自动消失，无需清理

5. 代码示例

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>

/* mkstemp: 安全创建临时文件 + 立即 unlink 实现自动删除 */
int main(void) {
    char template[] = "/tmp/myappXXXXXX";
    int fd = mkstemp(template);
    if (fd == -1) { perror("mkstemp"); return 1; }
    printf("创建临时文件: %s\n", template);

    unlink(template);          /* 立即删除目录项，关闭 fd 时自动回收 */

    write(fd, "temp data", 9); /* fd 仍可正常读写 */
    close(fd);                 /* 关闭 → 文件真正被删除 */
    return 0;
}

代码自测（Q&A）

Q1：mkstemp 的 template 格式是什么？ A：以 XXXXXX（恰好 6 个大写 X）结尾的字符串，如 "/tmp/myappXXXXXX"。mkstemp 会用唯一随机串替换这 6 个 X，并原地写回 template。注意 template 必须是可写的字符数组（char template[] = ...），不能是字符串字面量（char * 指向只读段会崩）。

Q2：为什么不能用 tmpnam？ A：tmpnam 只返回一个未保留的文件名，真正创建靠后续独立的 open，两步之间存在 TOCTOU 竞态——另一进程可能抢先创建同名文件或符号链接攻击。mkstemp 用 O_CREAT|O_EXCL 在单次调用内原子完成「生成名 + 独占创建」，无竞态窗口。

Q3：如何创建「关闭时自动删除」的临时文件？ A：两种：① tmpfile()（返回 FILE*，关闭自动删除）；② mkstemp() 后立即 unlink——文件目录项被移除，但已打开的 fd 仍可读写，最后一个 fd 关闭时内核真正回收该文件。

Q4：mkstemp 创建的临时文件权限是多少？ A：0600（仅 owner 可读写）。这是安全设计——临时文件常含敏感数据，默认不开放给同组/其他用户。

Q5：mkstemp 和 tmpfile 怎么选？ A：需要路径名（如后续要 rename 成正式文件）用 mkstemp；只需要一个匿名临时文件、用 FILE* 流操作、关闭即删，用 tmpfile（等价于 mkstemp+立即 unlink，但封装成 stdio 流）。

代码自测

1. dup2(fd, 2) 和 close(2); fcntl(fd, F_DUPFD, 2) 的区别？

dup2(fd, 2) 原子地关闭 fd 2 并将 fd 复制到 2。close(2); fcntl(fd, F_DUPFD, 2) 分两步，中间可能被信号中断或另一线程抢占 fd 2。在多线程或信号处理程序中应使用 dup2 或 F_DUPFD_CLOEXEC。

2. F_GETFL 返回的 access mode 怎么判断？

不能直接 & O_RDONLY（O_RDONLY 是 0）。需用 mask = result & O_ACCMODE，然后判断 mask 是 O_RDONLY(0)、O_WRONLY(1) 还是 O_RDWR(2)。

3. readv 如何实现一次读取头部+数据体？ 
struct iovec iov[2];
iov[0].iov_base = &header;  iov[0].iov_len = sizeof(header);
iov[1].iov_base = body_buf; iov[1].iov_len = body_len;
ssize_t n = readv(fd, iov, 2);

一次系统调用完成两个不连续缓冲区的读取，比分两次 read 更高效。
