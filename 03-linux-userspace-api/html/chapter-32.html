章节目标

pthread_cancel 的异步请求语义（join 拿 PTHREAD_CANCELED）；状态/类型 2×2 组合；取消点的定义与 glibc 2.28 机制变革；pthread_testcancel 检查站纪律；cleanup 栈（宏本质、LIFO、return 陷阱、持锁睡眠保险）；异步取消为什么禁用；HFT 的协作退出替代。

一句话内核视角：取消 = glibc 在目标线程置标志 + tgkill(tgid, tid, SIGCANCEL=32) 踹醒阻塞中的系统调用（内核 do_send_specific():3935，tgkill 双重校验防 PID 复用误杀）+ 目标在取消点/系统调用包装层自查标志后展开清理并 pthread_exit。

易错清单

  1. 以为 cancel = 立即终止 → 不 join 就收资源（僵尸/泄漏）
  2. 纯计算循环不加 testcancel → 杀不死
  3. 临界区 DISABLE 恢复成硬编码 ENABLE → 拆掉上游保护
  4. cleanup push 后直接 return → 编译错（宏花括号）——读懂这是保护
  5. 以为 return 会展开 cleanup → POSIX 明确不展开
  6. cleanup push 放在 lock 前 → 取消时 unlock 未持有的锁（UB）
  7. ASYNC 用在持锁/碰堆的线程 → 死锁/堆损坏
  8. join 无超时的关停序列 → 一个卡死全线挂死
  9. pthread_sigmask 挡了 32 号（SIGCANCEL）→ 取消请求被屏蔽
  10. 拿 kill(tid) 杀线程 → tid 不是进程；用 pthread_cancel 或 tgkill

32.1

取消线程

本章：TLPI 第 32 章 — Threads: Thread Cancellation - 上一节：本章首页 - 下一节：32.2 取消状态与类型

源码核验：Linux v6.6 · kernel/signal.c（do_send_specific():3935 · do_tkill():3962 · SYSCALL_DEFINE3(tgkill):3988）· glibc 侧：pthread_cancel 以 tgkill(tgid, tid, SIGCANCEL) 投递，SIGCANCEL = 32（__SIGRTMIN，glibc 保留）

本节讲什么

  1. pthread_cancel 的真实语义——它只是异步投递一个请求，不是"立即杀死"；默认（延迟）模式下要等目标线程走到取消点才真正终止。
  2. 取消 vs 三种"亲缘"终止方式——pthread_exit（自愿）、pthread_cancel（外部请求）、进程级信号（粗暴）；以及为什么取消是它们中间唯一的"线程粒度 + 可清理"方案。
  3. 内核视角——glibc 用 tgkill 发 SIGCANCEL(32) 实现取消请求；tgkill 的注释原文正好解释了为什么要带 tgid。

一、API 与语义

#include <pthread.h>
int pthread_cancel(pthread_t thread);          /* 返回 0 = 请求已投递（≠已终止）*/

四条语义：

# 语义 推论
1 异步投递：立即返回，不等待目标终止 想确认死透，必须 pthread_join
2 默认延迟模式：请求挂起（pending），目标走到取消点才执行 走不到取消点的线程（纯计算循环）永不死
3 被取消线程以 pthread_exit(PTHREAD_CANCELED) 收场 join 的 retval == PTHREAD_CANCELED = 被取消铁证
4 可接合线程被取消后仍要 join 回收 与普通退出一样走 zombie→join 流程（29.2/29.4）

1.1 与亲缘机制对比

机制 发起方 粒度 能否清理 风险
return / pthread_exit 线程自己 线程 ✓（自然收尾） —
pthread_cancel 其他线程 线程 ✓（cleanup 栈，32.5） 延迟模式下安全；异步模式危险（32.6）
kill(pid, sig) 默认处理 其他进程/线程 进程 ✗（信号处理器都不一定跑完） 杀一个线程 = 杀全进程
_exit 本线程 进程 ✗ 无

一句话：pthread_cancel 是 POSIX 里唯一"线程粒度 + 异步发起 + 目标可清理"的终止原语——代价是它的语义复杂度（状态/类型/取消点/cleanup 四件套，本章全部）。

1.2 内核视角：请求是怎么送到的

glibc 的 pthread_cancel（2.28+ 的 futex-cancel 设计）：

pthread_cancel(t)
  1. 在目标线程 struct pthread 里置取消标志（tid 置为特殊值 → 目标在
     系统调用取消包装里自查）
  2. tgkill(tgid, tid, SIGCANCEL=32)      ← 强制打断目标可能正阻塞的系统调用
     └─ 内核：SYSCALL_DEFINE3(tgkill):3988 (kernel/signal.c)
         └─ do_tkill():3962   si_code = SI_TKILL, si_pid = 调用者 TGID
             └─ do_send_specific():3935
                 ├─ find_task_by_vpid(pid)           按线程 PID 找任务
                 ├─ check_kill_permission():3943     权限检查
                 └─ do_send_sig_info():3948          挂到目标线程的信号队列
  3. 目标线程被信号唤醒 → glibc 的取消包装代码检查标志 →
     到取消点/立即执行取消（展开 cleanup → pthread_exit(PTHREAD_CANCELED)）

为什么用 tgkill 而不是 kill？内核注释（kernel/signal.c:3982）原文就是答案：

"This syscall also checks the @tgid and returns -ESRCH even if the PID exists but it's not belonging to the target process anymore. This method solves the problem of threads exiting and PIDs getting reused."

kill(pid) 的 pid 是进程（TGID）级；线程 ID 撞上 PID 复用时可能误杀别的进程。tgkill(tgid, tid, sig) 双重校验"tid 必须仍属于 tgid"——和 29.5 讲的 pthread_t 复用问题同源，POSIX 线程模型在内核里的最后一道身份校验。

SIGCANCEL = 32 = SIGRTMIN（glibc 首个实时信号）：glibc 保留 RT 信号 32/33（取消 / setuid 广播），用户程序从 SIGRTMIN 拿到的其实是 34 起（man 7 signal）。

HFT / 嵌入式关联

路线 要点
HFT 不推荐用 cancel 停策略线程：延迟模式的取消点时序不受控（可能停在 read 半途）；HFT 用协作式退出——退出标志（原子）+ condvar 唤醒 + 线程自己在选定的安全边界收尾（当前订单处理完再退）。cancel 只用于"失控线程的最后一招"
HFT · 关停顺序 若用 cancel：先停止喂任务 → cancel → join → 检查 PTHREAD_CANCELED → 收全局资源。直接 cancel 正在持锁写订单簿的线程 = 数据结构永久损坏
嵌入式 RTOS 一般没有"取消"（任务删除是硬杀）：要么 pthread_cancel 的清理栈不可用，要么干脆删除任务 → 泄漏。嵌入式惯例同 HFT：协作退出 + 超时升级（软退 → 硬杀）
嵌入式 · 信号号 若平台无 glibc 的 SIGCANCEL 保留机制（musl 有自己的实现），跨 libc 移植别假设 32/33 可用

/* cancel_demo.c — Ch32.1/32.2/32.3/32.4：取消请求、状态屏蔽、取消点、testcancel

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>
#include <string.h>

/* ---------- 演示 1（32.1）：请求是异步的，join 拿 PTHREAD_CANCELED ---------- */
static void *sleeper(void *a){(void)a;
    printf("  [worker] 开始 sleep(10)，必经取消点\n");
    sleep(10);                       /* 取消点 */
    printf("  [worker] 不可能到达这里\n");
    return NULL;}

static void demo_cancel_sleep(void){
    pthread_t t;
    pthread_create(&t, NULL, sleeper, NULL);
    usleep(100000);
    pthread_cancel(t);               /* 异步投递请求，立即返回 */
    printf("[demo1] cancel 已投递（请求≠终止）\n");
    void *res;
    pthread_join(t, &res);
    printf("[demo1] join 结果 %s\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED：确认被取消" : "正常返回？");
}

/* ---------- 演示 2（32.2）：DISABLE 期间请求挂起，恢复后生效 ---------- */
static void *shielded(void *a){(void)a;
    pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, NULL);
    printf("  [worker] 取消已 DISABLE，进入 3 段不可打断工作\n");
    for (int i = 1; i <= 3; i++) { sleep(1); printf("  [worker] 关键段 %d/3 完成\n", i); }
    pthread_setcancelstate(PTHREAD_CANCEL_ENABLE, NULL);
    sleep(1);                        /* 恢复后第一个取消点：这里被取消 */
    printf("  [worker] 不应到达\n");
    return NULL;}

static void demo_state_shield(void){
    pthread_t t;
    pthread_create(&t, NULL, shielded, NULL);
    usleep(100000);
    pthread_cancel(t);
    printf("[demo2] 取消请求已发出（此时目标 DISABLE，请求挂起）\n");
    void *res;
    pthread_join(t, &res);
    printf("[demo2] join 结果 %s\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED：关键段跑完才被取消"
                                    : "正常返回？");
}

/* ---------- 演示 3（32.3/32.4）：纯计算循环没有取消点 → testcancel 补位 ---------- */
static volatile long sink;
static void *spinner(void *a){(void)a;
    long x = 0;
    for (;;) {                       /* 纯计算：没有任何取消点 */
        for (int i = 0; i < 1000000; i++) x += i;
        sink = x;
        pthread_testcancel();        /* ⭐ 手动取消点：不加这里就永远杀不掉 */
    }
    return NULL;}

static void demo_spinner(void){
    pthread_t t;
    pthread_create(&t, NULL, spinner, NULL);
    usleep(200000);
    pthread_cancel(t);
    void *res;
    pthread_join(t, &res);
    printf("[demo3] 纯计算循环 %s\n",
           res == PTHREAD_CANCELED
               ? "被取消（pthread_testcancel 补位生效）" : "没被取消？");
}

int main(void){
    printf("==== demo1：异步请求 + join 验证 ====\n");
    demo_cancel_sleep();
    printf("==== demo2：DISABLE 屏蔽 + 恢复生效 ====\n");
    demo_state_shield();
    printf("==== demo3：纯计算 + pthread_testcancel ====\n");
    demo_spinner();
    return 0;
}

取消状态与类型

本章：TLPI 第 32 章 — Threads: Thread Cancellation - 上一节：32.1 取消线程 - 下一节：32.3 取消点

本节讲什么

  1. 两个正交的开关——状态（ENABLE/DISABLE：要不要接受请求）与类型（DEFERRED/ASYNCHRONOUS：接受后何时执行），2×2 组合决定线程的"死亡资格"。
  2. 临界区屏蔽模式——持锁/半改数据的区段 DISABLE 取消，出来再恢复；这是延迟取消工程化的核心用法。
  3. 异步类型为什么几乎不可用——任意指令边界被杀的三宗罪（持锁死、堆锁死、数据结构残缺）。

一、两个开关

int pthread_setcancelstate(int state,    int *oldstate);
/*   PTHREAD_CANCEL_ENABLE（默认）/ PTHREAD_CANCEL_DISABLE           */

int pthread_setcanceltype(int type,      int *oldtype);
/*   PTHREAD_CANCEL_DEFERRED（默认）/ PTHREAD_CANCEL_ASYNCHRONOUS    */

两个开关正交，逐线程设置（每线程自己的状态，不是进程级）：

状态 \ 类型 DEFERRED ASYNCHRONOUS
ENABLE（默认格） 到取消点才执行（工程默认） 任意指令边界可执行（危险）
DISABLE 请求挂起（pending），恢复 ENABLE 后到取消点执行 同左——DISABLE 优先于类型

三条规则：

  1. DISABLE 时请求只是挂起，不丢；恢复 ENABLE 后在下个取消点执行。挂起的取消无法撤销（POSIX 无 "uncancel"）——pthread_cancel 是单向门。
  2. 状态/类型开关本身不是取消点（setcancelstate 不会触发挂起的请求；但恢复 ENABLE 后紧跟的取消点会）。
  3. oldstate/oldtype 出参建议保存并在临界区结束时恢复原值（而不是硬编码 ENABLE）——你可能运行在一个本来就被上游 DISABLE 的上下文里。

二、临界区屏蔽模式（本节的工程主菜）

void update_order_book(void) {
    int oldstate;
    pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, &oldstate); /* ① 进禁区 */
    pthread_mutex_lock(&book->lock);                            /* ② 持锁 */
    book_apply(book, delta);            /* ③ 半改数据的中途死 = 结构永久残缺 */
    pthread_mutex_unlock(&book->lock);
    pthread_setcancelstate(oldstate, NULL);                     /* ④ 出禁区恢复 */
}

为什么必须屏蔽：延迟模式下 pthread_mutex_lock 不是取消点，但 read/sleep/pthread_testcancel 是——若临界区内部（或未来有人加的调试输出）踩中取消点，线程死在"已锁未解"状态：

lock(book) ✓
  book_apply 改了一半
  printf(...)         ← 取消点！
  ✗ 线程在此被取消
  → book->lock 永远锁着（除非 cleanup 栈救场，32.5）
  → 数据结构半新半旧，其他线程读到的就是残缺账本

两条工程守则：

  • 守则 1：临界区（持锁段）一律 DISABLE/恢复包裹——防御"今天不是取消点、明天被加成了取消点"的演化风险。
  • 守则 2：更彻底的替代是 cleanup 栈（32.5）配对 push/pop unlock——即使被取消也能解锁。DISABLE 是"防"，cleanup 是"治"，生产代码常常双保险。

三、异步取消的三宗罪

PTHREAD_CANCEL_ASYNCHRONOUS 下，取消可在任意两条指令之间生效（实现上是收到信号立即展开）：

罪 场景 后果
① 持锁死 死在 lock 与 unlock 之间 其他线程永久死等；若死在 glibc 内部锁（malloc 的 arena 锁）→ 全进程 malloc 死锁
② 堆残缺 死在 malloc/free 的链表操作中途 堆元数据损坏，之后随机 crash
③ 数据残缺 死在"改两个字段"的第一个字段后 不变量破坏（账本借贷不平），静默错误比崩溃更贵

因此异步取消的安全前提极其苛刻：纯计算 + 不碰锁 + 不碰堆 + 不碰共享数据 + 不调任何库函数——满足全部条件的应用场景几乎只剩"专门的数学打杂线程"。而且即便如此，异步模式下的取消路径不保证 cleanup 栈完整执行（32.6）。

工程结论：类型永远用默认 DEFERRED；需要"算到一半能被打断"的线程，用 pthread_testcancel（32.4）在安全边界手动开检查点。

HFT / 嵌入式关联

路线 要点
HFT HFT 主流做法是整个系统不使用 pthread_cancel，协作退出（原子标志 + condvar）天然没有"死亡时机"问题。若遗留代码里必须用 cancel：所有临界区按守则 1 包 DISABLE；关停顺序 = 停喂 → cancel → join → 验证 PTHREAD_CANCELED
HFT · 演化防御 "今天不是取消点"是脆弱假设——glibc 版本升级会把新函数变成取消点（2.28 后 futex 系统调用全面取消化）。守则 1 的 DISABLE 包裹是对未来的一劳永逸保险
嵌入式 RTOS 任务删除 ≈ 异步取消（无清理机会）——嵌入式经验法则直接映射到本节：硬杀只配"可丢弃"任务；有资源的任务必须给退出路径（消息队列退出命令 / 信号量握手）

代码示例

见 32.1 的 cancel_demo.c 演示 2（DISABLE 屏蔽 3 段关键工作、恢复后到取消点才死亡的完整实测）：请求挂起 → 关键段 1/3、2/3、3/3 全部完成 → ENABLE 后第一个取消点被取消。本节配套的临界区包裹模式（可编译片段）：

/* shield_critsec.c — 临界区 DISABLE/恢复包裹模式 */
#include <pthread.h>

static pthread_mutex_t book_lock = PTHREAD_MUTEX_INITIALIZER;
static int book[8];

void update_book(int idx, int val)
{
    int oldstate;
    pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, &oldstate);  /* 进禁区 */
    pthread_mutex_lock(&book_lock);
    book[idx] = val;                 /* 半改数据的中途死 = 结构永久残缺 */
    pthread_mutex_unlock(&book_lock);
    pthread_setcancelstate(oldstate, NULL);                      /* 恢复原值 */
}

自测题

题目 1：线程 B 处于 DISABLE 状态时收到 cancel 请求，随后 B 恢复 ENABLE 并立刻进入一个长计算循环（无任何取消点）。B 会被取消吗？

参考答案

不会立刻被取消。恢复 ENABLE 后请求仍处于挂起状态，要等 B 走到取消点（标准取消点函数或 pthread_testcancel）才执行。长计算循环里没有取消点 → 请求一直挂着，B 继续跑。这正是"挂起不丢失、但也不提前生效"的语义。

题目 2：为什么 pthread_setcancelstate 恢复时推荐恢复 oldstate 而不是硬编码 PTHREAD_CANCEL_ENABLE？

参考答案

当前代码可能运行在一个本来就被上游调用者 DISABLE 的上下文里（比如上层函数把整段逻辑设为不可取消）。硬编码 ENABLE 会把上游的保护悄悄拆掉——恢复操作必须对称：谁改的谁恢复，恢复成进来时的值。

题目 3：异步取消模式下，一个线程正在 malloc 内部（持有 arena 锁）被取消，会发生什么？

参考答案

线程死在 malloc 内部：① arena 锁不会被释放，其他任何线程再调 malloc/free 都死锁在同一个 arena 上——全进程堆瘫痪；② 堆的空闲链表/tcache 可能正处于半更新状态，即使锁能释放，堆元数据也已损坏。这就是异步取消三宗罪里最致命的"内部锁死"。

32.3

取消点

本章：TLPI 第 32 章 — Threads: Thread Cancellation - 上一节：32.2 取消状态与类型 - 下一节：32.4 主动检查：pthread_testcancel

源码核验：Linux v6.6 · 取消点本质是 glibc 的系统调用包装（SYS_cancel 路径属 glibc；内核只负责被信号打断的阻塞调用）· 32.1 的 tgkill 链路是打断机制的内核侧

本节讲什么

  1. 取消点的定义与两大类——延迟取消的"检查站"：可能无限阻塞的函数（必须检查）+ 部分其他函数（实现可选）；一张主表 + 一张"不是取消点"的反表。
  2. glibc 2.28 的机制变革——futex-cancel 设计：取消点从"函数清单"变成"系统调用包装层"，为什么这让取消点的实际集合比 man 页更大、更依赖版本。
  3. 工程含义——"我的线程会不会被卡在永不取消的循环里"的排查法。

一、取消点是什么

延迟取消（默认类型）下，挂起的取消请求只在取消点执行。POSIX 把取消点分成两档：

  • 必须是取消点的函数：可能无限期阻塞的——被取消请求唤醒是线程逃出生天的唯一途径（否则 sleep(365天) 的线程永远杀不死）。
  • 可能是取消点的函数：标准允许实现自选（printf、malloc 在 glibc 里不是，别的 libc 可能是）。

主表（工程上够用版，完整表见 man 3 pthreads 取消点一节）：

类别 取消点函数
定时 sleep · nanosleep · clock_nanosleep · usleep
I/O read · write · pread · pwrite · aio_suspend
多路复用 select · pselect · poll · ppoll · epoll_wait
网络 accept · accept4 · connect · send · recv · sendto · recvfrom
文件/目录 open（部分实现）· close（可选）· fsync · fdatasync · getdents/readdir
进程/同步 wait · waitpid · waitid · pthread_join · pthread_cond_wait · pthread_cond_timedwait · sem_wait · sem_timedwait
信号 sigwait · sigwaitinfo · sigtimedwait · pause
消息队列/锁 mq_receive · mq_send · pthread_mutex_lock（部分实现可选，glibc 一般不检查）

反表（常见误认，不是取消点）：

函数 为什么不是
malloc / free 不无限阻塞（持内部锁但会返回）；设为取消点会在堆半更新时死线程
memcpy / sin / 纯计算 不阻塞
pthread_mutex_lock（glibc） 快路径不阻塞；慢路径 futex 睡眠在新 glibc 里可以被打断处理取消（见 §二），但语义上不算标准取消点
自旋循环 / 忙等 没有函数调用就没有检查——这是"线程杀不死"的第一大原因

记忆钩子：取消点 ≈ "可能睡死的函数"。线程睡在系统调用里时，取消请求用信号（32.1 的 SIGCANCEL）把它踹醒——醒来的包装层检查标志、决定展开。不睡的代码根本没有被踹的机会。

1.1 排查"线程杀不死"

症状：pthread_cancel + join 永远不返回
排查顺序：
 1. 目标是不是纯计算/自旋循环？        → 无取消点，加 pthread_testcancel（32.4）
 2. 目标是不是 DISABLE 忘了恢复？      → 请求在挂起（32.2）
 3. 目标是不是死了但没 join？          → cancel 不等于回收（32.1）
 4. 目标是不是被信号屏蔽挡住 SIGCANCEL？→ pthread_sigmask 别挡 32 号
 5. 循环里调用的"阻塞"函数是不是宏/内联后的忙等包装？（如自实现的 sleep 轮询）

二、glibc 2.28+：取消点搬进了系统调用包装层

老设计（glibc < 2.28）：每个取消点函数手动调 pthread_testcancel + 特殊的 futex 处理——覆盖不全、且取消阻塞中的 futex 系统调用（condvar 睡眠）要靠内核配合重启。

新设计（glibc ≥ 2.28，futex-cancel）：

  1. pthread_cancel 置标志 + tgkill(SIGCANCEL)（32.1 §1.2）；
  2. 所有可取消的系统调用都走 __syscall_cancel 包装：进入时查标志、syscall 执行中信号可打断、返回路径再查标志；
  3. 被信号打断的 syscall 按 Linux 的 restart_syscall 语义重启或返回 EINTR——取消包装在 EINTR 路径上二次检查标志，命中即展开取消。

工程推论：

  • 取消点的实际集合随 glibc 版本变化（2.28 后显著变大：任何可取消的系统调用阻塞中都能被取消唤醒）——man 页的静态清单只是下界；
  • "这个函数是不是取消点"的争论，答案常常是看版本。这就是 32.2 守则 1（临界区 DISABLE 包裹）成为一劳永逸方案的原因：不赌清单，直接免疫。

HFT / 嵌入式关联

路线 要点
HFT 取消点= 系统调用边界 = 调度/IO 抖动点。热路径线程本来就禁止 IO 和睡眠（一核一线程 + 无锁），也就天然"没有取消点"——再次印证 HFT 用协作退出而不是 cancel 的架构选择
HFT · 关停 关停序列里的 join 要设超时（pthread_timedjoin_np，GNU 扩展）——万一某个线程卡在非取消点，别让关停流程整个挂死

/* cancel_read.c — read() 阻塞中被取消（可编译片段，配套主函数自加 timeout 保护） */
#include <pthread.h>
#include <unistd.h>
#include <stdio.h>

static int fd[2];

static void *reader(void *a){(void)a;
    char buf[16];
    printf("  [reader] 阻塞在 read()（无人写）\n");
    ssize_t r = read(fd[0], buf, sizeof buf);   /* 阻塞 = 取消点 */
    (void)r;
    return NULL;}

/* main: pipe(fd); create(reader); usleep(100ms); cancel; join */

实测行为：reader 阻塞在 read 的系统调用里，pthread_cancel 的 SIGCANCEL 信号把它踹醒，glibc 取消包装在返回路径上展开——join 得到 PTHREAD_CANCELED，管道缓冲没人消费也无所谓（进程随后退出）。这正是"可能无限阻塞的函数必须是取消点"的设计动机：没有取消点，阻塞在 IO 上的线程就永远杀不死。

自测题

题目 1：一个工作线程的主循环是 while (running) { for (i=0;i<1e9;i++) sum += i; check_heartbeat(); }，check_heartbeat 里没有任何函数调用。pthread_cancel 后这个线程会终止吗？

参考答案

不会。整个循环没有任何取消点（纯计算 + 无函数调用），挂起的取消请求永远等不到执行机会。修法：在 check_heartbeat（或每轮外层）加 pthread_testcancel()，或把循环改成周期性睡 1µs / poll 一个唤醒 fd。这是"线程杀不死"第一大原因的标准形态。

题目 2：为什么 POSIX 规定"可能无限阻塞"的函数必须是取消点，而 malloc 不可以是？

参考答案

必须：无限阻塞的函数若不检查取消，线程睡在里面永远无法响应取消请求——取消机制对这些函数失效（sleep 百年的线程杀不死）。不可以：malloc/free 操作的是进程级堆元数据，中途被取消会留下半更新的链表（堆损坏），且它持内部 arena 锁——死在锁内 = 全进程堆瘫痪。取消点集合的设计原则就是"醒得安全"：睡死函数必须醒，内部锁函数绝不能醒。

题目 3：glibc 2.28 之后，"某函数是不是取消点"为什么变得更难静态回答？工程上如何免疫这种不确定性？

参考答案

因为取消检查搬进了系统调用包装层（__syscall_cancel）：任何可取消的系统调用在阻塞中被 SIGCANCEL 打断后都会走取消检查——实际可取消的行为集合由运行时路径决定，man 页清单只是下界，且随 glibc 版本变化。免疫方法：不赌清单——需要保证不被打断的代码段用 pthread_setcancelstate(DISABLE) 包裹（32.2 守则 1），需要保证能被打断的循环手动加 pthread_testcancel（32.4）。

32.4

主动检查：`pthread_testcancel`

本章：TLPI 第 32 章 — Threads: Thread Cancellation - 上一节：32.3 取消点 - 下一节：32.5 清理处理器

本节讲什么

  1. pthread_testcancel 是什么——一个手动安插的取消点：检查挂起请求，有则立即执行取消（走完 cleanup 栈 → pthread_exit(PTHREAD_CANCELED)）。
  2. 它解决什么——纯计算/自旋循环没有自然取消点，"线程杀不死"的标准修复。
  3. 安插的工程规范——放哪、放多密、和状态开关怎么配合。

一、API 与语义

#include <pthread.h>
void pthread_testcancel(void);   /* 无返回值：要么返回继续跑，要么不返回（被取消）*/

语义一句话："现在是不是一个安全死亡点？是就死。" 它的行为完全等价于"到达一个取消点"：

  • 无挂起请求 → 立即返回，开销近似一次内存读（快路径）；
  • 有挂起请求 且 state==ENABLE 且 type==DEFERRED → 在此处执行取消（cleanup 栈展开、TSD 析构、pthread_exit(PTHREAD_CANCELED)）；
  • state==DISABLE → 不检查直接返回（DISABLE 免疫一切取消点，包括手动这个）。

"无返回值"的函数在 C 里很少见——pthread_testcancel 和 longjmp/exit 一个家族：正常路径返回，取消路径不返回。写代码时把它理解为"关卡"而不是"函数调用"。

二、给纯计算循环开检查站

2.1 标准形态

void *number_cruncher(void *arg) {
    (void)arg;
    for (;;) {                          /* 长计算：没有自然取消点 */
        crunch_one_chunk();             /* 安全边界：块与块之间 */
        pthread_testcancel();           /* ⭐ 检查站 */
    }
    return NULL;                        /* 实际不可达（靠取消或外部退出标志）*/
}

2.2 安插三原则

原则 说明
放安全边界，不放代码中间 块与块之间（数据一致点）；绝不放在持锁段/半改数据中段——它的语义就是"死在这也安全"
密度 = 响应延迟预算 两个检查站之间隔多久，cancel 的生效就最多延迟多久。100ms 一次 → 最坏 100ms 才死；配 join 超时时按这个预算设
和退出标志二选一或并存 新代码推荐协作退出（while (running)）；testcancel 用于必须支持 pthread_cancel 的库代码，或作为协作退出失效时的兜底

2.3 典型 bug 形态

/* bug：检查站安插在持锁段内 */
pthread_mutex_lock(&m);
for (...) {
    crunch();
    pthread_testcancel();     /* ✗ 死在这 = m 永远锁着 */
}
pthread_mutex_unlock(&m);

/* 修复 1：移到锁外/循环外层 */
pthread_mutex_lock(&m); ...; pthread_mutex_unlock(&m);
pthread_testcancel();         /* ✓ 无锁无半改数据 */

/* 修复 2：cleanup 栈托底（32.5）后保留原地检查 */

三、与状态开关的配合（把 32.1–32.4 串起来）

完整的心智模型——一个请求从投递到执行的路径：

pthread_cancel(t) ──投递──▶ [挂起的请求] ──────────────────────────┐
                                                                   ▼
目标线程 t 的每次"取消点"（标准取消点 or pthread_testcancel）：
    state == DISABLE ？ ──是──▶ 请求继续挂起（本次不执行）
    type == DEFERRED  ？ ──是──▶ 【在当前取消点执行】
                                   ├─ 展开清理栈（LIFO，32.5）
                                   ├─ 跑 TSD 析构（31.3）
                                   └─ pthread_exit(PTHREAD_CANCELED)
    type == ASYNCHRONOUS ──▶ 不等取消点，信号到达即执行（32.6，危险）

HFT / 嵌入式关联

路线 要点
HFT 热路径循环里加 pthread_testcancel 等于白送一次分支预测（近似免费），但纪律上 HFT 不引入 pthread_cancel 依赖——退出检查用业务自己的 running 原子标志，语义一致且可审计。testcancel 真正的位置是非热路径的长任务线程（回测、重算、归档）
HFT · 关停预算 检查站密度 = 关停延迟上界。回测框架约定"每 chunk 检查一次 + chunk ≤ 50ms"，运维 kill 脚本的超时按 3×chunk 预算设置，超时升级为 SIGKILL（进程级）
嵌入式 RTOS 无 pthread_cancel 时，testcancel 的等价物是 if (kthread_should_stop()) break;（内核线程）或任务消息队列里的退出命令轮询——"定期在安全边界问一句该不该退"是跨平台的通用纪律

见 32.1 的 cancel_demo.c 演示 3：百万次迭代的纯计算循环 + 每轮 pthread_testcancel()，cancel 后 200ms 内被取消（join 得 PTHREAD_CANCELED）；去掉那一行，同一程序 join 永远不返回——一行之差，就是"杀得死"与"杀不死"的分界。

自测题

题目 1：pthread_testcancel 的返回值为什么是 void？调用它之后紧接着的代码在什么情况下不会执行？

参考答案

因为存在两条路径：无挂起请求（或 DISABLE）时立即返回、代码继续；有挂起请求且 ENABLE+DEFERRED 时在调用点执行取消（cleanup 栈展开 + TSD 析构 + pthread_exit(PTHREAD_CANCELED)）——函数不返回，调用点之后的代码不执行。它与 exit/longjmp 同属"可能不返回"的函数。

题目 2：pthread_setcancelstate(PTHREAD_CANCEL_DISABLE) 之后调用 pthread_testcancel() 会发生什么？

参考答案

什么都不发生：DISABLE 优先于一切取消点（包括手动的），testcancel 直接返回，挂起的请求继续等。这保证了 32.2 临界区包裹模式对 testcancel 同样免疫——即使在临界区里误调了它也不会死在锁内。

题目 3：设计一个回测 worker：每 chunk 计算约 30ms，要求 cancel 后 100ms 内必定退出（安全边界为块间）。写出循环骨架。

参考答案 
for (;;) {
    crunch_one_chunk();              /* ~30ms，安全边界为块间 */
    pthread_testcancel();            /* 最坏 30ms 后生效 ✓ 100ms 预算内 */
    /* 协作退出标志与 testcancel 并存：库外用户用 cancel，库内用标志 */

}

32.5

清理处理器

本章：TLPI 第 32 章 — Threads: Thread Cancellation - 上一节：32.4 pthread_testcancel - 下一节：32.6 异步取消

本节讲什么

  1. cleanup 栈的 API 与宏本质——pthread_cleanup_push/pop 是宏不是函数，必须同词法块配对；LIFO 栈在取消/pthread_exit 时自动展开。
  2. 三种触发路径与一个陷阱——cancel ✓、pthread_exit ✓、pop(非0) ✓；return 不触发（本章第一大坑）。
  3. 标准范式——"持锁睡眠"场景（condvar wait 被取消时解锁）与 push/pop 对的写法。

一、API 与宏本质

#include <pthread.h>

void pthread_cleanup_push(void (*routine)(void *), void *arg);
void pthread_cleanup_pop(int execute);

它们是宏（{ 和 } 的一部分！）：

/* 展开近似 */
#define pthread_cleanup_push(r, arg) \
    do { __pthread_cleanup_class __clframe(r, arg); {
#define pthread_cleanup_pop(execute) \
    } __clframe.__setdoit(execute); } while (0)

推论（每条都有人踩）：

# 规则 原因
1 push/pop 必须同词法块配对 push 带 {，pop 带 }——少一个编译器报"花括号不匹配"式的奇怪错误
2 push 后必须 pop 才能 return 词法块没闭合，return 语法上就不合法（这反而是保护：强迫你走完配对）
3 不能跨函数/不能 goto 跳出块 同上
4 pop(0) 只弹出、pop(非0) 弹出并执行 常规收尾路径手动触发

二、三种触发 + 一个陷阱

退出路径 cleanup 栈
pthread_cancel（到取消点执行） 自动展开（LIFO：最后 push 的最先执行）
pthread_exit(v) 自动展开
pthread_cleanup_pop(非0) 手动执行该处理器的
return v 不展开！

return 不展开是 POSIX 的设计决定（return = 正常路径，应当用 pop 显式收尾），不是 bug——但它是本章第一大坑：

void *worker(void *arg) {
    pthread_cleanup_push(unlock_helper, &m);       /* push */
    pthread_mutex_lock(&m);
    ...
    if (error)
        return NULL;        /* ✗ 编译都过不了：块没闭合 —— 宏设计恰好挡住这一坑 */
    pthread_cleanup_pop(1); /* ✓ 正确：pop(1) = 弹出并执行 unlock */
    return NULL;
}

宏的 {} 结构强迫 return 前必须先 pop——词法上杜绝了"忘记收尾"。这是 pthreads API 设计里少有的"用宏的丑换纪律"的范例。

顺带：cleanup 展开顺序 LIFO（栈）；处理器里还可以继续 push/pop（嵌套清理）；处理器内部如果被再次取消……理论可能、实际极难，别依赖。

三、标准范式：持锁睡眠

本章最重要的应用场景：线程持锁睡在 condvar 上，被取消时必须解锁——否则其他等锁的线程全部陪葬。

/* 反面：裸 wait */
pthread_mutex_lock(&m);
while (!ready)
    pthread_cond_wait(&cond, &m);   /* 取消点！死在这 → m 永远锁着 */
...
pthread_mutex_unlock(&m);

/* 正面：cleanup 托底 */
static void unlock_mutex(void *p) {
    pthread_mutex_unlock((pthread_mutex_t *)p);
    log("cancelled: mutex unlocked by cleanup");
}

pthread_mutex_lock(&m);
pthread_cleanup_push(unlock_mutex, &m);     /* 挂保险 */
while (!ready)
    pthread_cond_wait(&cond, &m);           /* 被取消 → cleanup 先解锁 */
...
pthread_cleanup_pop(0);                     /* 正常路径：只摘保险不执行 */
pthread_mutex_unlock(&m);                   /* 正常解锁 */

范式要点：

  1. push 在 lock 之后（锁还没拿到就挂保险，取消时 unlock 一把没锁的锁 = UB）；
  2. 正常路径 pop(0) + 手动 unlock；取消路径 cleanup 自动 unlock——两条路径一个保险；
  3. 处理器参数只能带一个 void*——要清理多个资源就传结构体指针，或者 push 多层（LIFO 保证逆序释放，与获取顺序相反，天然正确）。

三层对比（资源保护的完整工具箱）：

手段 时机 适用
DISABLE 取消（32.2） 事前预防 临界区短、可整体延迟
cleanup 栈（本节） 事后收尸 持锁睡眠、多资源逆序释放
协作退出标志 根本不让取消发生 新代码首选，HFT 标准

HFT / 嵌入式关联

路线 要点
HFT HFT 线程池关停若必须支持 cancel：每个"持锁 + 可能睡"的 wait 点一律 cleanup 托底（本节范式）+ 32.2 的 DISABLE 双保险。审计方法：grep pthread_cond_wait / pthread_mutex_lock，检查同函数内是否有配对的 cleanup_push
HFT · C++ 视角 C++ 的 RAII 析构在线程被取消时同样执行（取消展开走 C++ 的 unwind）——C++ 项目用 RAII 锁（std::unique_lock）自动获得本节语义，这是 C++ 线程代码不怕 cancel 的原因
嵌入式 RTOS 任务删除无 cleanup 栈 → 嵌入式的等价纪律：任务入口先注册"清理回调表"，删除前由删除方逐项调用（或任务自己在消息循环里收 CLEANUP 命令自清）——LIFO 逆序释放的纪律不变

代码示例

cleanup_demo.c（gcc -O2 -Wall -Wextra 零告警编译通过）：

/* cleanup_demo.c — Ch32.5：LIFO 逆序、cond_wait 取消解锁、return 不展开
 * 编译：gcc -O2 -Wall -Wextra -o cleanup_demo cleanup_demo.c -pthread
 */
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

/* ---------- 演示 1：LIFO 逆序 + 三种触发路径 ---------- */
static void handler(void *arg) {
    printf("  cleanup: %s\n", (char *)arg);
}

static void *path_exit(void *a){(void)a;
    pthread_cleanup_push(handler, (void*)"A-最先push");
    pthread_cleanup_push(handler, (void*)"B-其次push");
    pthread_cleanup_push(handler, (void*)"C-最后push");
    /* 栈：C 顶。pthread_exit 自动展开 → C、B、A 逆序 */
    pthread_exit((void *)1);
    pthread_cleanup_pop(0);        /* 消除 noreturn 警告（不可达）*/
    pthread_cleanup_pop(0);
    pthread_cleanup_pop(0);
}

static void *path_pop(void *a){(void)a;
    pthread_cleanup_push(handler, (void*)"X-唯一push");
    pthread_cleanup_pop(1);        /* pop(1)：手动执行 → "X-唯一push" 打印 */
    printf("  [path_pop] pop(1) 手动触发后，线程正常 return\n");
    return NULL;                   /* return 不再展开（栈已空）*/
}

static void demo_order(void){
    pthread_t t1, t2;
    void *r;
    printf("  --- pthread_exit 路径（自动 LIFO 展开）---\n");
    pthread_create(&t1, NULL, path_exit, NULL);
    pthread_join(t1, &r);
    printf("  --- pop(1) 手动路径 ---\n");
    pthread_create(&t2, NULL, path_pop, NULL);
    pthread_join(t2, &r);
    (void)r;
}

/* ---------- 演示 2：cond_wait 被取消 → cleanup 解锁救场 ---------- */
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  cv = PTHREAD_COND_INITIALIZER;
static int ready;

static void unlock_mutex(void *p) {
    pthread_mutex_unlock((pthread_mutex_t *)p);
    printf("  [cleanup] 被取消了：cleanup 已解锁 mutex\n");
}

static void *waiter(void *a){(void)a;
    pthread_mutex_lock(&m);
    pthread_cleanup_push(unlock_mutex, &m);    /* 挂保险 */
    while (!ready)
        pthread_cond_wait(&cv, &m);            /* 取消点：死在这 */
    pthread_cleanup_pop(0);                    /* 正常路径：摘保险 */
    pthread_mutex_unlock(&m);
    return NULL;}

static void demo_cancel_wait(void){
    pthread_t t;
    void *res;
    pthread_create(&t, NULL, waiter, NULL);
    usleep(100000);
    printf("  [main] 发出取消（waiter 正持锁睡在 condvar 上）\n");
    pthread_cancel(t);
    pthread_join(t, &res);
    printf("  [main] join: %s\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED" : "正常?");

    /* 验证锁真的被 cleanup 释放了：主线程现在必须能拿到它 */
    struct timespec ts = {0, 50*1000*1000};
    printf("  [main] 尝试拿锁（若 cleanup 没解锁这里就死锁）...");
    fflush(stdout);
    pthread_mutex_lock(&m);
    printf("成功：锁是自由的 ✓\n");
    pthread_mutex_unlock(&m);
    nanosleep(&ts, NULL);
}

int main(void){
    printf("==== demo1：触发路径与 LIFO 顺序 ====\n");
    demo_order();
    printf("==== demo2：cond_wait 取消 + cleanup 解锁 ====\n");
    demo_cancel_wait();
    return 0;
}

==== demo1：触发路径与 LIFO 顺序 ====
  --- pthread_exit 路径（自动 LIFO 展开）---
  cleanup: C-最后push
  cleanup: B-其次push
  cleanup: A-最先push
  --- pop(1) 手动路径 ---
  cleanup: X-唯一push
  [path_pop] pop(1) 手动触发后，线程正常 return
==== demo2：cond_wait 取消 + cleanup 解锁 ====
  [main] 发出取消（waiter 正持锁睡在 condvar 上）
  [cleanup] 被取消了：cleanup 已解锁 mutex
  [main] join: PTHREAD_CANCELED
  [main] 尝试拿锁（若 cleanup 没解锁这里就死锁）...成功：锁是自由的 ✓

三点解读：

  1. demo1：pthread_exit 自动展开且严格 LIFO（C→B→A，与 push 顺序相反）；pop(1) 手动执行该层处理器。正常 return 路径栈已空——不展开。
  2. demo2：waiter 死在 pthread_cond_wait（取消点），cleanup 处理器把 mutex 解开——主线程随后 pthread_mutex_lock(&m) 成功，证明锁确实被"死后收尸"释放。没有 cleanup 的版本，这一步就是永久死锁。
  3. pthread_exit 版本里 pop(0)×3 不可达（exit 已发生），只用来平衡宏的花括号——__attribute__((noreturn)) 场景下的标准写法。

自测题

题目 1：pthread_cleanup_push 之后直接 return，会发生什么？

参考答案

编译失败。push/pop 是宏：push 展开含 {，pop 展开含 }——不 pop 就 return，词法块没闭合，编译器报花括号/语法错误。这个"丑"是故意的：强迫每个 return 路径都显式经过 pop（决定执行与否），从语言层面杜绝"忘记收尾"。C++ 的 RAII 析构自动覆盖所有 return 路径，是更优雅的等价物。

题目 2：线程 push 了 A、B、C 三个处理器后被取消。执行顺序？如果 A 是 unlock、B 是 free、C 是 close，这个顺序为什么是正确的？

参考答案

LIFO：C→B→A。正确性在于资源获取顺序通常是 A（lock）→ B（malloc）→ C（fd），释放必须逆序：先关 fd（不再使用内存）、再 free（脱离了临界区语义上的数据）、最后 unlock。栈结构天然编码了"逆序释放"，与 C 语言 goto cleanup 惯用法、C++ 析构顺序完全一致。

题目 3：写出"持锁睡 condvar + 可被取消"的最小安全骨架，并指出保险挂在哪一步。

参考答案 
pthread_mutex_lock(&m);
pthread_cleanup_push(unlock_mutex, &m);   /* 保险：lock 成功之后立刻挂 */
while (!ready)
    pthread_cond_wait(&cv, &m);           /* 取消点 */
pthread_cleanup_pop(0);                   /* 正常路径摘保险 */
pthread_mutex_unlock(&m);

保险必须挂在 lock 之后（拿到锁才有"解锁"可托底；lock 之前挂，取消时 unlock 一把未持有的锁 = UB）。while 谓词、pop(0)、手动 unlock 与 30.2 的条件变量范式完全同构——cleanup 只是给"被取消"这条异常路径加了出口。

32.6

异步取消

本章：TLPI 第 32 章 — Threads: Thread Cancellation - 上一节：32.5 清理处理器 - 下一节：32.7 总结

本节讲什么

  1. 异步取消的语义与唯一合法场景——任意指令边界可被杀；只有"纯计算 + 零资源依赖"的线程配得上它。
  2. 实测对照——同一个无取消点的计算循环：DEFERRED 杀不死、ASYNCHRONOUS 秒杀。
  3. 工程结论——为什么本节的存在意义是"让你有底气永远不用它"。

一、语义回顾与深化

pthread_setcanceltype(PTHREAD_CANCEL_ASYNCHRONOUS, &oldtype);
  • 取消请求到达即执行（信号处理器路径直接展开），不等取消点；
  • 与 DISABLE 仍正交：DISABLE 时挂起（32.2 矩阵）；
  • cleanup 栈执行不保证：展开发生在任意指令边界，栈本身的状态可能不一致；处理器可能只跑了一半；
  • TSD 析构同样不可靠。

三宗罪（32.2 §三）在这里从"理论风险"变成"必然触发面"：任意边界 = 你迟早死在 malloc 里、死在锁里、死在半改数据的中间。

1.1 唯一合法场景的画像

async-安全线程的合同：
  ✓ 只碰自己的栈和寄存器
  ✓ 不 malloc/free（不碰堆）
  ✓ 不 lock/unlock（不碰任何锁，包括 glibc 内部锁）
  ✓ 不读写共享全局（除非用纯原子且能容忍任意截断点）
  ✓ 不调用任何库函数（printf/memcpy 都不行——内部可能有锁）
  ✓ 结果通过 volatile 原子变量或 pipe 交付

典型画像：无界数学搜索（素数打杂、蒙特卡洛抽样的 worker、密码学穷举）——算到哪算哪，死了就死了，结果不完整也无妨。HFT/嵌入式的业务线程没有一条满足此合同。

二、实测对照

配套 async_demo.c（gcc -O2 -Wall -Wextra 零告警编译通过）：

/* async_demo.c — Ch32.6：同一个无取消点循环，DEFERRED 杀不死 vs ASYNC 秒杀
 * 编译：gcc -O2 -Wall -Wextra -o async_demo async_demo.c -pthread
 */
#define _GNU_SOURCE             /* pthread_tryjoin_np */
#include <stdio.h>
#include <errno.h>
#include <pthread.h>
#include <unistd.h>
#include <time.h>
#include <stdlib.h>

static volatile unsigned long sink;

static unsigned long crunch_step(void);        /* 先声明后使用 */

/* 纯计算：无任何取消点、无锁、无堆、无库调用 */
static void *crunch_deferred(void *a){(void)a;
    unsigned long x = 0;
    for (;;) x += crunch_step();
    return NULL;}                     /* 不可达 */

static void *crunch_async(void *a){(void)a;
    pthread_setcanceltype(PTHREAD_CANCEL_ASYNCHRONOUS, NULL);   /* ⭐ */
    unsigned long x = 0;
    for (;;) x += crunch_step();
    return NULL;}                     /* 不可达 */

static unsigned long crunch_step(void){
    unsigned long s = 0;
    for (int i = 1; i < 200000; i++) s += (unsigned long)i * 1103515245u;
    return s;
}

int main(void){
    struct timespec ts100ms = {0, 100*1000*1000};

    printf("== DEFERRED（默认）：无取消点 → 杀不死 ==\n");
    pthread_t t1;
    pthread_create(&t1, NULL, crunch_deferred, NULL);
    nanosleep(&ts100ms, NULL);
    pthread_cancel(t1);
    int r = pthread_tryjoin_np(t1, NULL);        /* 非阻塞试探 */
    if (r == EBUSY) {
        printf("  cancel 已发出 100ms，线程仍在跑（没有取消点）\n");
        printf("  演示结束——线程留在后台跑（进程退出时一并消亡）\n");
    } else {
        printf("  线程已死？(意外)\n");
    }

    printf("== ASYNCHRONOUS：任意边界 → 秒杀 ==\n");
    pthread_t t2;
    pthread_create(&t2, NULL, crunch_async, NULL);
    nanosleep(&ts100ms, NULL);
    pthread_cancel(t2);
    void *res;
    pthread_join(t2, &res);
    printf("  join: %s（无需取消点，指令边界即死）\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED" : "正常?");

    (void)sink;
    return 0;
}

实测输出（WSL2 / 12 核）：

== DEFERRED（默认）：无取消点 → 杀不死 ==
  cancel 已发出 100ms，线程仍在跑（没有取消点）
  演示结束——线程留在后台跑（进程退出时一并消亡）
== ASYNCHRONOUS：任意边界 → 秒杀 ==
  join: PTHREAD_CANCELED（无需取消点，指令边界即死）

解读：同一个循环，唯一的差别是一行 setcanceltype。DEFERRED 的取消请求在无取消点的循环里永远挂起（32.3/32.4 的主题）；ASYNC 在信号到达的任意指令边界立即执行。这组对照是"类型开关决定生死时机"的最直观演示——也顺带展示了 pthread_tryjoin_np（GNU 扩展）做非阻塞探测的用法。

三、工程结论：本节的正确用法是"不用"

如果你想… 正确做法
杀掉卡在计算里的线程 给循环加 pthread_testcancel（32.4），保持 DEFERRED
快速停止 worker 协作退出标志 + 周期检查（HFT 标准）
清理已死线程的资源 cleanup 栈（32.5）——但 ASYNC 下它不可靠，所以又回到 DEFERRED
真·不可中断的长计算 fork 子进程做，超时 kill(pid)——进程边界比线程边界硬得多，内核保证全回收

异步取消在认真写的系统里的出场率应为零。它存在的价值：① POSIX 完整性；② 面试与考试；③ 让你理解"为什么取消机制要设计成延迟+取消点+清理栈这么复杂"——全是为了把"死亡时机"约束到安全边界，而 ASYNC 把这个约束整个扔掉了。

路线 要点

自测题

题目 1：为什么 ASYNC 模式下 cleanup 栈的保证不可靠？

参考答案

cleanup 展开发生在信号到达的任意指令边界：处理器自身执行到一半可能再被打断（嵌套取消）、栈顶指针可能处于不一致状态、处理器访问的资源可能正是"当前指令正在半改"的那个。DEFERRED 的全部设计（取消点=安全边界）就是为了让展开发生在一致点——ASYNC 摧毁了这个前提，因此一切建立在"边界安全"上的保证（cleanup、TSD 析构、锁配对）同时失效。

题目 2：需求："一个计算密集线程必须能被立刻停止，且它持有 8MB 堆缓冲"。给出两个方案并比较。

参考答案

方案 A（线程内）：DEFERRED + 循环内 pthread_testcancel + 缓冲放 TSD/局部，由 cleanup 栈释放。停止延迟=检查站间隔；资源保证完整释放。方案 B（进程边界）：fork worker 进程做计算，8MB 缓冲在子进程内，停止= kill(pid)+waitpid——立刻生效（信号打断任意指令，进程死亡由内核全回收），缓冲随地址空间消亡。比较：A 停止有延迟但零进程开销；B 即停即净但创建/通信成本高。生产常选 B（超时兜底），交互场景选 A。

三、铁律

  1. cancel 是请求不是死刑：join + PTHREAD_CANCELED 才是死亡证明。
  2. 临界区（持锁段）一律 DISABLE/恢复包裹——恢复 oldstate，不硬编码。
  3. 类型永远 DEFERRED；ASYNC 只配"纯计算零依赖"线程，生产代码出场率应为零。
  4. 纯计算循环必加 pthread_testcancel，放块间安全边界，密度=取消延迟预算。
  5. cleanup push/pop 是宏：同块配对、push 在 lock 后、正常路径 pop(0)+手动收尾。
  6. return 不展开 cleanup——宏的 {} 会逼你先 pop（这是保护，不是障碍）。
  7. 持锁睡 condvar 必挂 cleanup 保险（32.5 范式）。
  8. 新代码优先协作退出（原子标志+condvar），cancel 只做遗留/兜底。
  9. 关停 join 设超时（pthread_tryjoin_np/timedjoin_np 探测），别让关停流程挂死。
  10. 杀不死排查五连：无取消点？忘了 ENABLE？没 join？SIGCANCEL 被屏蔽？忙等伪装成阻塞？

自测题

题目 1：复述取消的完整生命周期五步，并指出哪一步可能"永远不发生"。

参考答案

①cancel 投递（tgkill SIGCANCEL）→ ②到达取消点（或 ASYNC 任意边界）→ ③展开 cleanup 栈 + TSD 析构 → ④pthread_exit(PTHREAD_CANCELED) → ⑤join 回收并确认。可能永远不发生的：②（无取消点的循环，32.3/32.4）以及 DISABLE 忘记恢复导致的挂起（32.2）——两者症状相同（join 挂死），排查方向不同。

题目 2：同事的线程池关停代码：cancel 全部 worker → join 全部 → 关闭队列。偶发关停挂死。给出三个候选原因和对应修复。

参考答案

① worker 主循环是纯计算/自旋（无取消点）→ 挂起的请求永不执行：加 testcancel 或改协作退出；② worker 在临界区 DISABLE 后某路径忘了恢复 → 请求一直挂起：审查所有 return 路径，用 oldstate 恢复模式；③ worker 死在持锁状态且无 cleanup → 其他 worker 等 lock 陪葬，join 挂死：持锁睡眠点挂 cleanup 保险（32.5 范式）。另外兜底：join 全部改 timedjoin/tryjoin + 超时升级进程级信号。

题目 3：为什么说"glibc 2.28 的取消机制改革"反而加强了 DISABLE 包裹的必要性？

参考答案

改革把取消检查从"函数清单"扩展到"系统调用包装层"：过去不是取消点的阻塞路径（各种 futex 睡眠）现在也可能响应取消。清单随版本变大的方向不会逆转——任何"这个函数现在不是取消点"的假设都是脆弱的。DISABLE 包裹使代码不依赖清单：无论未来哪行代码变成取消点，临界区内部都免疫取消。一劳永逸 > 逐版本审计。
