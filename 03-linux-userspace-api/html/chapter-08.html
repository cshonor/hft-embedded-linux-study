章节目标

理解 Linux 的用户/组数据库：/etc/passwd / /etc/shadow / /etc/group 三个文本文件的字段语义与权限要求；掌握查询这三套库的 API 家族（含 _r 可重入版与静态缓冲的生命周期）；掌握 crypt() 认证链路以及它的三个陷阱；为 Ch9 的「进程运行时凭证」铺垫。

易错清单

全部有实测支撑（细节见各节与 8.6）：

  1. /etc/passwd 是 644 不是"配置不严"，是设计使然（ls -l 要把 uid 翻译成名字）；反过来 /etc/shadow 是 644 就是确凿的错误（shadow(5)："must not be readable by regular users"）。
  2. pw_passwd 只是占位符 x；拿它直接 crypt() 会得到 *0。认证前必须用 sp_pwdp 覆盖它。
  3. 非 _r 版本返回静态缓冲，getpwent / getpwnam / getpwuid 共用同一块；「读一批存数组」直接是 bug。
  4. 地址不可假设：fgetpwent 连续三次返回同一地址，但 getpwnam("ce") 与 getpwuid(10240)（同一用户）地址不同。
  5. errno 范式有条件：后端起不开时（/etc/group 不存在）errno 会是 ENOENT，无法与「真的出错」区分。man 明确列了 0 / ENOENT / EBADF / ESRCH / EPERM 都可能。
  6. _r 版「不存在」= s == 0 且 *result == NULL，只看 s 不够；且 _r 不动 errno，别再对它用 errno 范式。
  7. 空数字字段（shadow）= -1，不是 0（getspnam(3)：putspent() 把 -1 写成空串）。sp_max == 0 与 sp_max < 0 语义完全不同。
  8. 空组的 gr_mem 不是 NULL，而是「首元素为 NULL 的数组」。写 if (gr->gr_mem != NULL) 会走错分支。
  9. crypt() 失败可能返回 *0 而不是 NULL（libxcrypt 的实现与 man 的描述不一致），必须两种都判。
  10. crypt() 的返回值绝不能当盐再喂回去：会得到 *1，两边变成同一块内存 → strcmp 恒等 → 任何口令都"通过"。
  11. DES 只吃口令前 8 字符（不足补 0），盐只有 2 字符 / 4096 种 —— 两个限制合起来判了 DES-crypt 的死刑。
  12. glibc ≥ 2.28 用 _DEFAULT_SOURCE，不是老教程的 _XOPEN_SOURCE；glibc 2.39 本身不带 crypt()，靠 libxcrypt，要链 -lcrypt。
  13. 本章不涉及 RUID/EUID/SUID 与 setuid() —— 那是 Ch9。
  14. getgrgid / getpwuid 的路径编译期写死（nss/files-XXX.c:42 的 #define DATAFILE "/etc/" DATABASE）；想读自己造的文件只能用 fgetpwent / fgetgrent / fgetspent。

8.1

The Password File：`/etc/passwd`

权威依据：passwd(5)（Linux man-pages 6.19）· getpwnam(3)（man-pages 6.19）· glibc 2.39 NSS files 后端（nss/files-pwd.c、nss/files-XXX.c、nss/files-parse.c、nss/getXXbyYY.c） 本节演示在 Compiler Explorer 上真实编译 + 运行（gcc 13.3.0 / x86-64） 本章：TLPI 第 08 章 — Users and Groups - 上一节：本章首页 - 下一节：8.2 The Shadow Password File：/etc/shadow

本节讲什么

Linux 把「系统里有哪些用户」这件事放在一个纯文本文件里。这一节只要回答四个问题：

  1. 一行 /etc/passwd 有哪七段？每个字段的权威定义在哪？
  2. 它为什么必须全局可读？（这个「必须」直接决定了 8.2 的存在）
  3. C 程序拿到的 struct passwd 和文本行是什么关系？
  4. 读它的 API 为什么是 O(n) 的，返回值为什么不能留住？

要点

一、七个字段：以 man 原文为准

passwd(5) DESCRIPTION 原文：

Each line of the file describes a single user, and contains seven colon-separated fields:

name:password:UID:GID:GECOS:directory:shell

# 字段 passwd(5) 原文 要点
1 name "This is the user's login name. It should not contain capital letters." 登录名
2 password "This is either the encrypted user password, an asterisk (*), or the letter 'x'." 有 shadow 时是 x
3 UID "The privileged root login account (superuser) has the user ID 0." 0 = root
4 GID "This is the numeric primary group ID for this user. (Additional groups for the user are defined in the system group file; see group(5))." 主组；附属组在 /etc/group
5 GECOS "This field (sometimes called the "comment field") is optional and used only for informational purposes." 纯注释，不参与认证
6 directory "the initial directory where the user is placed after logging in. The value in this field is used to set the HOME environment variable." 只是初始化 HOME
7 shell "This is the program to run at login (if empty, use /bin/sh)." 初始化 SHELL

第 2 字段有四个特殊值，全部出自 passwd(5)，含义差别很大：

值 含义 原文
x 真密文搬到 /etc/shadow 了 "the letter 'x'"
* 这一账号不能用口令登录 "many system administrators use an asterisk (*) in the encrypted password field to make sure that this user can not authenticate themself using a password"
*NP* 影子记录应从 NIS+ 取 "If the encrypted password in /etc/passwd is *NP* (without the quotes), the shadow record should be obtained from an NIS+ server."
空串 不口令直接放行 "If the encrypted password, whether in /etc/passwd or in /etc/shadow, is an empty string, login is allowed without even asking for a password."

⚠️ 最后一行是真的安全口子，不是笔误。它也是各种「登录绕过」漏洞的常见形态：一个手滑留下来的空密码字段 = 一个无需口令的账号。

二、「必须全局可读」是被需求逼出来的

passwd(5) 第一段原文：

The /etc/passwd file is a text file that describes user login accounts for the system. It should have read permission allowed for all users (many utilities, like ls(1) use it to map user IDs to usernames), but write access only for the superuser.

这句话把 8.2 的动机说尽了：ls -l 必须能把 uid=10240 显示成 ce —— 这个「数字 ↔ 名字」的映射表就得人人可读。而一旦人人可读，第 2 字段里就不能放密文。

所以「/etc/passwd 是 644、/etc/shadow 是 600/640」不是风格习惯，是这两条约束的必然结果。

三、struct passwd：文本行 → 内存结构

getpwnam(3) DESCRIPTION 给出的定义（<pwd.h>）：

struct passwd {
    char  *pw_name;    /* username */
    char  *pw_passwd;  /* user password */
    uid_t  pw_uid;     /* user ID */
    gid_t  pw_gid;     /* group ID */
    char  *pw_gecos;   /* user information */
    char  *pw_dir;     /* home directory */
    char  *pw_shell;   /* shell program */
};

字段顺序和文件一一对应，区别只是：行 → 结构体，: → 各自独立的指针，十进制文本 → uid_t / gid_t 整数。getpwnam() 没有任何魔法，它就是 NSS 后端里的一次 fopen + 按 : 切分。

⚠️ getpwnam(3) VERSIONS 段明确说：pw_gecos "is not specified in POSIX, but is present on most implementations." 用它要接受可移植性折扣。

四、三个不显眼但会咬人的文件层事实（本容器实测）

事实 证据（见下文实测输出）
末行可能没有换行符 == 记录 1：字段数 7（文件末行没有换行符） —— 本容器 /etc/passwd 只有 1 条记录，末尾没有 \n
有 UID 0 的进程 ≠ 有 UID 0 的记录 进程 uid=0，但 getpwuid(0) -> NULL（errno=0）
没有 /etc/group 条目就等于没有这个组 passwd(5) NOTES："If you want to create user groups, there must be an entry in /etc/group, or no group will exist."（8.3 实测 getgrgid(10240) 返回 NULL）

第一条的杀伤力最直接：自己写解析器时若假设「每行都以 \n 结尾」再无条件 line[len-1] = '\0'，就会把最后一个字符吃掉 —— 本例里会把 10240 削成 1024。

五、谁真的在读它：glibc NSS files 后端

路径是编译期写死的（glibc 2.39 nss/files-XXX.c:42）：

#define DATAFILE    "/etc/" DATABASE

所以 getpwnam() / getpwuid() / getpwent() 永远读 /etc/passwd，没有任何环境变量或参数能改。想读自己造的测试文件，唯一的正规入口是 fgetpwent(FILE *)。

查询是 O(n) 线性扫描。所有 getXXbyYY 由一个宏生成（nss/files-XXX.c:198-222，此处节选主体）：

/* DB_LOOKUP 宏生成的函数体（删去宏拼接细节） */
{
  enum nss_status status;
  FILE *stream = NULL;

  /* Open file.  */
  status = internal_setent (&stream);

  if (status == NSS_STATUS_SUCCESS)
    {
      while ((status = internal_getent (stream, result, buffer, buflen, errnop)) 
         == NSS_STATUS_SUCCESS)
    { break_if_match }          /* ← 读到匹配就 break */

      fclose (stream);
    }

  return status;
}

三件事一次说清：

  1. 每次调用都要 fopen + 逐行读 + fclose —— 没有索引、没有缓存（除非跑 nscd）。
  2. 匹配就是 strcmp，记录数 n 就是最坏 O(n) 次 readline。
  3. 比较里带 NIS 兼容判断（nss/files-pwd.c:33-38）：
DB_LOOKUP (pwnam, '.', 0, ("%s", name),
       {
         if (name[0] != '+' && name[0] != '-'
         && ! strcmp (name, result->pw_name))
           break;
       }, const char *name)

+ / - 开头的行是 NIS 的 include/exclude 语法，files 后端主动跳过它们。这是「NSS 把多个数据源拼在一起」留下的化石 —— 账号库从来不止一个文件。

代码

c8_1 手工切一遍 /etc/passwd，再和 getpwnam() 对照

完整程序见 ../code/c8_1_passwd_parse.c：自己按 : 切 7 段、自己剥 \n，再把同一行交给 getpwnam()，两侧逐字段对照。

/* c8_1_passwd_parse.c —— 8.1：/etc/passwd 的 7 字段格式
 *
 * 手工按 ':' 切分每一行，再和 getpwnam() 的结果逐字段对照：
 * 「账户库 API」说到底就是对这几个文本文件的封装。
 *
 * 编译：cc -Wall -Wextra -o c8_1_passwd_parse c8_1_passwd_parse.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define NFIELD 7

static const char *fieldname[NFIELD] = {
    "登录名", "密文占位", "UID", "主 GID", "注释(GECOS)", "家目录", "登录 shell"
};

/* 就地把 line 按 ':' 切成最多 NFIELD 段，把 ':' 改成 '\0'；返回实际段数 */
static int split_fields(char *line, char **f)
{
    int n = 0;
    char *p = line;

    if (n < NFIELD)
        f[n++] = p;
    for (; *p != '\0' && n < NFIELD; p++) {
        if (*p == ':') {
            *p = '\0';
            f[n++] = p + 1;
        }
    }
    return n;
}

int main(void)
{
    FILE *fp = fopen("/etc/passwd", "r");
    if (fp == NULL) {
        perror("fopen /etc/passwd");
        return 1;
    }

    char line[512];
    int rec = 0;
    while (fgets(line, sizeof line, fp) != NULL) {
        size_t len = strlen(line);
        int had_nl = (len > 0 && line[len - 1] == '\n');

        if (had_nl)
            line[len - 1] = '\0';       /* 自己剥掉换行，别让 strtol 撞上 */

        rec++;
        char *f[NFIELD];
        int n = split_fields(line, f);
        printf("== 记录 %d：字段数 %d%s\n", rec, n,
               had_nl ? "" : "（文件末行没有换行符）");
        for (int i = 0; i < n; i++)
            printf("   %d %-12s = %s\n", i + 1, fieldname[i], f[i]);

        if (n >= 3) {
            char *end;
            long uid = strtol(f[2], &end, 10);
            printf("   -> strtol(f[2]) = %ld（UID 在文件里只是十进制文本）\n", uid);
        }
    }
    fclose(fp);
    printf("共读到 %d 条记录\n", rec);

    /* ---- 同一份数据，走 API ---- */
    struct passwd *pw = getpwnam("ce");
    if (pw != NULL) {
        printf("\ngetpwnam(\"ce\") -> pw_name=%s pw_passwd=%s pw_uid=%ld pw_gid=%ld\n",
               pw->pw_name, pw->pw_passwd, (long) pw->pw_uid, (long) pw->pw_gid);
        printf("                    pw_gecos=%s pw_dir=%s pw_shell=%s\n",
               pw->pw_gecos, pw->pw_dir, pw->pw_shell);
        printf("pw_passwd 是占位符还是真密文：%s\n",
               strcmp(pw->pw_passwd, "x") == 0 ? "占位符 \"x\"" : "真密文");
    } else {
        printf("\ngetpwnam(\"ce\") -> NULL\n");
    }

    /* ---- 「UID 0」不等于「passwd 里有 0 号记录」 ---- */
    errno = 0;
    pw = getpwuid(0);
    printf("getpwuid(0) -> %s（errno=%d）\n", pw ? pw->pw_name : "NULL", errno);

    return 0;
}

解读

  1. 第一行括号里的「文件末行没有换行符」不是装饰：这份 /etc/passwd 的最后一行确实没有 \n。程序里 had_nl 就是靠 strlen(line) 之后看最后一个字符得出的，剥换行前先判断 —— 无条件剥就会吃掉一个真实字符。
  2. 手工切出的 7 段与 getpwnam("ce") 的 7 个字段一一对应（pw_uid=10240、pw_gid=10240、pw_gecos=Not a real account、pw_dir=/app、pw_shell=/bin/bash）。这就是"账户库 API = 对几个文本文件的封装"的实证。
  3. pw_passwd 是占位符 "x"，不是密文。所以拿 pw_passwd 直接 crypt() 必然失败（会得到 libxcrypt 的失败哨兵 *0，见 8.5）—— 正确的做法是先 getspnam() 覆盖它，这正是原书 Listing 8-2 第 67 行干的事。
  4. 最后一行 getpwuid(0) -> NULL（errno=0） 是本节第二个坑：进程 uid=0，库里却没有 0 号记录。「我是 root」是进程属性，「库里有 root 这条记录」是数据库内容，两者互不推导。评测容器恰好把这两件事拆开了，是个难得的教学样本。
  5. 「UID 在文件里只是十进制文本」：文件里存的是字符串 10240，struct passwd 里是 uid_t。转换发生在 libc 内部（nss/files-parse.c:96 的 parse_line），所以任何手工解析都得自己 strtol 并检查溢出 —— 这正是程序里那行 strtol(f[2]) 想点出的。

HFT / 嵌入式关联

  • 绝不在热路径上查账户库。getpwuid() 在本容器里要走一趟 fopen("/etc/passwd") + 线性扫描；在接了 LDAP/SSSD 的机器上它是一次网络往返。日志线程里顺手 getpwuid 就是把行情线程拖进 DNS/网络超时。
  • 审计的正确姿势：记录数字 uid，展示时才翻译（并且翻译结果要缓存 —— 账户表在进程生命周期里几乎不变）。反过来「先把 uid 翻成名字再写日志」会把 I/O 带进热路径。
  • 嵌入式：BusyBox 系统常省掉 /etc/shadow，甚至把账号编译进二进制（CONFIG_USE_BB_PWD_GRP 直接内置 passwd/group 解析）。这类系统的 getpwnam() 不碰文件系统 —— 所以「getpwnam 会读文件」不是可以依赖的语义，只是 glibc + nsswitch.conf: files 下的实现。
  • nsswitch.conf 决定一切：改成 passwd: ldap files，路径写死的就不是 /etc/passwd 了。排障时 getent passwd <name> 是比 cat /etc/passwd 更接近程序视角的检查手段。
  • *NP* / +/- 这类 NIS 遗留语法在现代发行版里已经没有任何东西会去解析，但 files 后端仍在跳过它们。读交叉编译出来的老系统镜像时见到 +:::::: 这类行，不要当成损坏数据。

自测题

1. 为什么 /etc/passwd 必须对所有用户可读，而密文必须搬去 /etc/shadow？

两句 man 原文拼起来就是答案：

  • passwd(5)："/etc/passwd ... It should have read permission allowed for all users (many utilities, like ls(1) use it to map user IDs to usernames), but write access only for the superuser."
  • shadow(5)："This file must not be readable by regular users if password security is to be maintained."

ls -l 要把 uid 显示成名字，映射表就得人人可读；映射表人人可读，密文就不能放里面。这两个约束是因果关系，不是两条独立约定。

顺带解释了一个常见误解：/etc/passwd 是 644 不是「配置不严」，而是设计使然；反过来说，/etc/shadow 若是 644 就是确凿的配置错误（见 8.2 的实测）。

2. 进程 getuid() 返回 0，是不是就说明 getpwuid(0) 一定能拿到记录？

不是。 这是两个不同的数据库视角：

  • getuid() 读的是内核里的进程凭证（task_struct 的 uid 字段）；
  • getpwuid(0) 查的是用户空间的账户库（/etc/passwd、NIS、LDAP…）。

本容器实测就把它拆开了：进程 uid=0，而 getpwuid(0) -> NULL（errno=0） —— /etc/passwd 里只有一条 ce(10240)，压根没有 0 号记录。

写代码时的实际影响：不要用 getpwuid(getuid())->pw_name 来做日志前缀而不判 NULL。容器（尤其是精简基础镜像）里这条链断掉是常态。安全写法见本节 c8_1 与 8.4。

3. 为什么 getpwnam() 读不到我临时造的那份 passwd 文件？

因为 glibc files 后端的路径是编译期常量（nss/files-XXX.c:42）：

#define DATAFILE    "/etc/" DATABASE

getpwnam() 走到 _nss_files_getpwnam_r()，里面的 internal_setent() 固定 fopen("/etc/passwd")。既没有环境变量能重定向，也没有参数能传路径。

要读自己造的文件，用 fgetpwent(FILE *)（8.4 有实测）。另一条路是改 nsswitch.conf 走向别的后端 —— 那已经不属于"读一个文件"了。

8.2

The Shadow Password File：`/etc/shadow`

本节讲什么

  3. 第 2 字段的 5 种形态 —— ! 和 * 到底差在哪？

要点

一、唯一的硬要求：一句话

shadow(5) DESCRIPTION 原文：

shadow is a file which contains the password information for the system's accounts and optional aging information.

This file must not be readable by regular users if password security is to be maintained.

来历见 getspnam(3) DESCRIPTION：

Long ago it was considered safe to have encrypted passwords openly visible in the password file. When computers got faster and people got more security-conscious, this was no longer acceptable. Julianne Frances Haugh implemented the shadow password suite that keeps the encrypted passwords in the shadow password database (e.g., the local shadow password file /etc/shadow, NIS, and LDAP), readable only by root.

所以正确说法不是「/etc/shadow 通常只有 root 能读」，而是「只有 root 能读」是它成立的前提。权限一旦放宽，这个文件就退化成了一个「名字更长的 /etc/passwd」。

二、九个字段

shadow(5)："Each line of this file contains 9 fields, separated by colons (":")"。

# 字段 shadow(5) 原文要点
1 login name "It must be a valid account name, which exists on the system."
2 encrypted password 见下一节（5 种形态）
3 date of last password change "expressed as the number of days since 1970-01-01 00:00:00 UTC"；"The value 0 indicates that the user must change their password the next time they log in"；"An empty field means that password aging features are disabled."
4 minimum password age "the number of days the user must wait before they can change their password again"；"An empty field and value 0 mean that there is no minimum password age."
5 maximum password age "the number of days after which the user must change their password"
6 password warning period "The number of days before a password expires ... during which the user is warned."
7 password inactivity period 口令过期后仍接受的天数，之后必须找管理员
8 account expiration date "The date when the account expires"；"account expiration differs from password expiration: Account expiration prevents the user from logging in, whereas password expiration only prevents users from logging in with their password."
9 reserved field "This field is reserved for future use."（struct spwd 里就是 sp_flag）

⚠️ 第 3 字段的 0 是个陷阱："The value 0 should not be used"（第 8 字段）—— 在不同工具眼里它既可能表示「永不过期」也可能表示「1970-01-01 就过期了」。

三、第 2 字段的四种形态（! 是最需要记住的）

shadow(5) 原文逐条：

形态 含义 原文
空串 允许无口令登录 "If the password field is empty, the user can log in without a password. However, some applications that read the /etc/shadow file might block access if the password field is empty."
合法 crypt() 结果 正常口令 "Refer to crypt(3) for details on how this string is interpreted."
! 开头 账号被锁定，且原密文还留在后面 "If the password field begins with an exclamation mark !, the password is locked. The remaining characters on the line represent the password field before the password was locked."
其它非法串（如 *） 不能用 UNIX 口令登录 "If the password field contains a string that is not a valid result of crypt(3), for instance ! or *, the user cannot use a UNIX password to log in. However, the user may log in the system by other means."

第三行是本文件里信息量最大的一句：

  • 锁定 = 在密文前面插一个 !，所以 usermod -L / passwd -l 是可逆的，-U 把 ! 删掉就恢复；
  • 「锁定」这个状态里带着原密文。于是如果 /etc/shadow 被普通用户读到，泄露的不只是"有人被锁了"，还有他能解开的那份哈希；
  • 第四行的 "may log in by other means" 也很要紧 —— 锁的是口令这条路，不是账号本身（SSH key、su、rsh 都可能照常）。passwd(5) NOTES 说同一件事："the user will be unable to login using login(1), but may still login using rlogin(1), run existing processes and initiate new ones through rsh(1), cron(8), at(1), or mail filters, etc."

四、struct spwd 与「空字段 = -1」

getspnam(3) 给的 <shadow.h> 定义：

struct spwd {
    char          *sp_namp;   /* Login name */
    char          *sp_pwdp;   /* Encrypted password */
    long           sp_lstchg; /* Date of last change (days since 1970-01-01 UTC) */
    long           sp_min;    /* Min # of days between changes */
    long           sp_max;    /* Max # of days between changes */
    long           sp_warn;   /* # of days before password expires */
    long           sp_inact;  /* # of days after password expires until disabled */
    long           sp_expire; /* Date when account expires (days since 1970-01-01 UTC) */
    unsigned long  sp_flag;   /* Reserved */
};

9 个字段一一对应。而空字段在内存里是什么，getspnam(3) DESCRIPTION 里 putspent() 那句给了权威答案：

The putspent() function writes the contents of the supplied struct spwd *p as a text line in the shadow password file format to stream. String entries with value NULL and numerical entries with value -1 are written as an empty string.

-1 就是「这个字段没写」的内存表示。 所以判断策略时不能只看有没有 0：

/* ✗ 错：把 -1 当成「0 天」→ 会算出「口令立刻过期」 */
if (sp->sp_max == 0) { /* 永不过期 */ }

/* ✓ 对：先分「没写」再分「写了 0」 */
if (sp->sp_max < 0)      { /* 字段为空：不检查 */ }
else if (sp->sp_max == 0) { /* 显式写了 0：由策略决定语义，别自己猜 */ }

代码

c8_2 权限位、降权实验与 ! / * 语义

完整程序见 ../code/c8_2_shadow_file.c：先 stat() 看权限位；再 fork() 出子进程降权复现「普通用户视角」；最后用 fgetspent() 解析一份合成 shadow，把 ! / * 的语义跑出来。

/* c8_2_shadow_file.c —— 8.2：为什么密文要搬到 /etc/shadow
 *
 * 三件事一起做：
 *   1. stat() 看 /etc/shadow 的权限位（密文只给 root + shadow 组）
 *   2. 以 root 读一次；再 fork 出子进程 setuid() 降权到普通账号读一次，
 *      把「普通用户读不到」从书上的一句话变成可复现的实验
 *   3. fgetspent() 解析一份合成 shadow，看字段含义与 ! / * 的锁定语义
 *
 * 编译：cc -Wall -Wextra -o c8_2_shadow_file c8_2_shadow_file.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <pwd.h>
#include <shadow.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/wait.h>
#include <unistd.h>

static void try_shadow(const char *who)
{
    errno = 0;
    FILE *fp = fopen("/etc/shadow", "r");
    printf("[%s] fopen(/etc/shadow) -> %s  errno=%d(%s)\n",
           who, fp ? "ok" : "NULL", errno, strerror(errno));
    if (fp != NULL)
        fclose(fp);

    errno = 0;
    struct spwd *sp = getspnam("ce");
    printf("[%s] getspnam(\"ce\")   -> %s  errno=%d(%s)\n",
           who, sp ? "non-NULL" : "NULL", errno, strerror(errno));
    if (sp != NULL)
        printf("[%s]     sp_pwdp=%s lstchg=%ld min=%ld max=%ld warn=%ld\n",
               who, sp->sp_pwdp, sp->sp_lstchg, sp->sp_min, sp->sp_max, sp->sp_warn);
}

int main(void)
{
    struct stat st;
    if (stat("/etc/shadow", &st) == 0) {
        printf("/etc/shadow mode=%04o uid=%ld gid=%ld size=%ld\n",
               (unsigned) (st.st_mode & 07777), (long) st.st_uid,
               (long) st.st_gid, (long) st.st_size);
    } else {
        perror("stat /etc/shadow");
    }

    try_shadow("root");

    struct passwd *pw = getpwnam("ce");
    if (pw == NULL) {
        puts("找不到 ce 账号，跳过降权实验");
        return 0;
    }

    printf("\n尝试降权到 %s(%ld) 复现「普通用户视角」…\n",
           pw->pw_name, (long) pw->pw_uid);

    fflush(stdout);                     /* fork 前刷缓冲，否则子进程会复制一份未 flush 的输出 */
    pid_t pid = fork();
    if (pid == 0) {
        if (setgid(pw->pw_gid) != 0 || setuid(pw->pw_uid) != 0) {
            printf("[child] setuid(%ld) 失败：errno=%d(%s)\n",
                   (long) pw->pw_uid, errno, strerror(errno));
            puts("[child] 评测容器跑在 user namespace 里，只映射了 uid 0，");
            puts("[child] 所以 setuid 到别的 uid 直接 EINVAL —— 这条实验在这里做不成。");
            puts("[child] 「普通用户读不到 shadow」的结论改由文件权限位 + man 5 shadow 说明。");
            fflush(stdout);             /* _exit 不 flush stdio */
            _exit(0);
        }
        printf("[child] 降权后 uid=%ld\n", (long) getuid());
        try_shadow("ce");
        fflush(stdout);
        _exit(0);
    }
    wait(NULL);

    /* ---- 合成一份 shadow，看字段与锁定语义 ---- */
    const char *sf = "/tmp/c8_shadow_demo";
    FILE *w = fopen(sf, "w");
    if (w != NULL) {
        fputs("alice:$6$abcdefgh$abc:19000:0:99999:7:14:20000\n"
              "bob:!:19000:0:99999:7:::\n"
              "carol:*:19000:0:99999:7:::\n", w);
        fclose(w);
    }

    puts("\n-- fgetspent() 解析合成 shadow --");
    FILE *f = fopen(sf, "r");
    struct spwd *sp;
    while (f != NULL && (sp = fgetspent(f)) != NULL) {
        const char *verdict = "正常";
        if (sp->sp_pwdp[0] == '!')
            verdict = "已锁定（! 开头）";
        else if (sp->sp_pwdp[0] == '*')
            verdict = "禁用（* 开头，无口令）";
        printf("%-6s pwdp=%-24s lstchg=%-6ld max=%-6ld inact=%-4ld expire=%-6ld %s\n",
               sp->sp_namp, sp->sp_pwdp, sp->sp_lstchg, sp->sp_max,
               sp->sp_inact, sp->sp_expire, verdict);
    }
    if (f != NULL)
        fclose(f);

    return 0;
}

解读

  1. mode=0644 —— 这是确凿的配置错误。shadow(5) 的要求是 "must not be readable by regular users"，而 0644 意味着任何用户都能读到 $1$rockyou$hty8SH9lK4mcCQXKENxaa1。这台机器的等价安全等级 = 完全没有 shadow。生产环境上这一条要用配置管理钉死，不能靠人工 chmod。
  2. size=55 与这条记录的字符数正好相等：ce(2) + $1$rockyou$hty8SH9lK4mcCQXKENxaa1(33) + 18723(5) + 0(1) + 99999(5) + 7(1) = 47，再加 8 个字段分隔冒号 = 55。也就是说这份 /etc/shadow 的单行记录末尾同样没有换行符（和 8.1 的 /etc/passwd 一样）。解析器必须两种都吃。
  3. sp_pwdp = $1$rockyou$hty8SH9lK4mcCQXKENxaa1 —— 前缀 $1$ 是 MD5-crypt，本容器上单核能跑 8910 次/秒（8.5 的实测表）。盐还被起名叫 rockyou（经典口令字典），基本等于明示「这份哈希是拿字典跑出来的」。这行输出就是我们把 0644 列为"确凿错误"的实证理由。
  4. 降权实验在这台机器上做不成，输出如实报告了原因：setuid(10240) 返回 EINVAL(22)。原因是评测容器跑在 user namespace 里，只映射了 uid 0，内核不允许切到一个未映射的 uid。所以「普通用户读不到 shadow」这个结论不能靠这段代码证明，只能靠：① 文件权限位（第 1 行）；② shadow(5) 原文；③ getspnam(3) 的 EACCES 条款。把做不成的实验如实写出来，比编一个漂亮输出有用得多。
  5. bob / carol 两行是本节的关键对照：! 和 * 都被 fgetspent() 原样读进 sp_pwdp，程序按首字符判定为「已锁定 / 禁用」。
  6. 注意 inact=-1 expire=-1 —— 这两个字段在文件里是空的（bob:!:19000:0:99999:7:::），读回来就是 -1，正是第四节那句 putspent() 规则的镜像。空字段 ≠ 0 天。

HFT / 嵌入式关联

  • 权限就是全部。lckpwdf() 是协作式锁，fopen() 不认；所以 /etc/shadow 的防线只有文件权限位和「谁能当 root」。审计一件部署时，stat -c %a /etc/shadow 应该出现在 checklist 里，和「服务不能以 root 跑」并列。
  • 0644 的 shadow 在容器镜像里非常常见。基础镜像构建脚本用 chmod -R 644、或者把宿主机的 /etc 整个 COPY 进去，都会造成这个状态。CI 里加一条断言成本极低： bash # 非 root 组可读即视为错误 [ "$(stat -c %a /etc/shadow)" = "640" ] || [ "$(stat -c %a /etc/shadow)" = "600" ]
  • ! 是运维最爱的"临时停用"手段，但它不是禁用账号。shadow(5) 和 passwd(5) 都说被锁的用户仍可能从其它路径进来。要真断掉，得同时处理 shell、SSH key、/etc/securetty、PAM 的 account 栈。
  • 嵌入式：BusyBox 的 passwd/login 可以走 CONFIG_USE_BB_SHADOW，也可以完全不用 shadow（密文留在 /etc/passwd）。读这类镜像时先判断用的是哪套：/etc/shadow 存在但只有 root:x 这种占位行时，真密文可能还在 /etc/passwd 里。
  • 不要自己解析 /etc/shadow。字段语义（尤其是 -1 ↔ 空串、0 对第 3/第 8 字段含义不同）在 getspnam(3) 里，不在文件格式里；用 fgetspent() / sgetspent() 解析字符串是更省事的路径，而且 putspent() 能把结果原样写回去。
  • HFT 场景下大概率根本不该有 shadow：交易节点用固定服务账号 + SSH key + 一次性镜像，口令登录通常直接关掉。此时正确的加固是让 /etc/shadow 里没有任何合法 crypt() 结果（全 ! 或 *），而不是留一堆能登的账号。

自测题

1. /etc/shadow 是 0644，这算"宽松"还是"错误"？

是错误，不是宽松。

shadow(5) 的措辞是命令式的："This file must not be readable by regular users if password security is to be maintained." 换句话说，「普通用户读不到」是这个文件能成立的先决条件，不是一个可调的强度档位。

0644 的等价后果是本容器实测到的状态：任何一个能起进程的账号都能 cat /etc/shadow，把 $1$rockyou$hty8SH9lK4mcCQXKENxaa1 拿到手里做离线爆破（MD5-crypt 单核 8910 次/秒，见 8.5）。此时引入 shadow 的全部安全收益归零 —— 只是把密文从一个全局可读的文件搬到了另一个全局可读的文件。

正确值：600（root:root）或 640（root:shadow，配合 shadow 组成员）。

2. 一个账号的密文是 !$6$abc$...，这个账号到底能不能登录？

取决于登录路径，不是一个简单的"能/不能"。

shadow(5) 对 ! 的定义是："the password is locked. The remaining characters on the line represent the password field before the password was locked."

  • 口令这条路：不能。 !$6$... 整体不是合法的 crypt() 结果，crypt() 会返回失败哨兵（8.5 实测为 *0），strcmp 永远不会相等。
  • 其它路径：可能能。 shadow(5) 自己写了："the user may log in the system by other means"，passwd(5) NOTES 列了 rlogin(1) / rsh(1) / cron(8) / at(1) / mail filters，以及已有的进程。

实践结论：! 是停用口令，不是停用账号。要停用账号，改 shell + 清理 authorized_keys + 上 PAM account 策略。

3. fgetspent() 读回来 sp_max == -1，和 sp_max == 0 有什么不一样？

-1 是"字段没写"，0 是"写了 0"。

getspnam(3) 里 putspent() 的说明给出对应关系："numerical entries with value -1 are written as an empty string"。所以 -1 是 libc 表示「文件里这段是空的」的内部约定。

shadow(5) 对 maximum password age（第 5 字段）说的是："An empty field means that there are no maximum password age, no password warning period, and no password inactivity period."

本容器实测就出现了这个值：bob 那行是 bob:!:19000:0:99999:7:::，两个空字段读回来 inact=-1 expire=-1。

写法上的直接影响：if (sp->sp_max == 0) { /* 永不过期 */ } 是错的 —— 它把「字段为空」误当成「0 天」。正确做法是先判 < 0。

The Group File：`/etc/group`

权威依据：group(5)（man-pages 6.19）· getgrnam(3)（man-pages 6.19）· passwd(5) · glibc 2.39 NSS files 后端（nss/files-grp.c、nss/files-XXX.c） 本节演示在 Compiler Explorer 上真实编译 + 运行（gcc 13.3.0 / x86-64） 本章：TLPI 第 08 章 — Users and Groups - 上一节：8.2 The Shadow Password File：/etc/shadow - 下一节：8.4 Retrieving User and Group Information

本节讲什么

组比用户多一层麻烦：同一个「用户属于哪些组」的信息，被拆在两个文件里。这一节回答：

  1. /etc/group 的 4 个字段分别是什么？
  2. 主组（primary）和附属组（supplementary）分别写在哪？为什么必须这么拆？
  3. 「没有 /etc/group 条目」会发生什么？
  4. gr_mem 对空组返回 NULL 吗？
  5. errno 范式在这里的一个真实失效点。

要点

一、四个字段

group(5) DESCRIPTION 原文：

The /etc/group file is a text file that defines the groups on the system. There is one entry per line, with the following format:

group_name:password:GID:user_list

# 字段 group(5) 原文
1 group_name "the name of the group."
2 password "the (encrypted) group password. If this field is empty, no password is needed."（实际几乎总是 x 或 *）
3 GID "the numeric group ID."
4 user_list "a list of the usernames that are members of this group, separated by commas."

group(5) 自己带一段 BUGS，值得抄下来：

As the 4.2BSD initgroups(3) man page says: no one seems to keep /etc/group up-to-date.

这不是玩笑。第 4 字段是手工/脚本维护的冗余信息，它和「用户实际的附属组集合」只在 initgroups() 跑过之后才一致 —— 这也是下面第四节要说清「附属组其实是进程凭证，不是文件内容」的原因。

二、主组 vs 附属组：一个用户的组身份拆在两处

存在哪 每个用户能有几个 权威原文
主组（primary GID） /etc/passwd 的 第 4 字段 恰好一个（字段只有一个） passwd(5)："This is the numeric primary group ID for this user."
附属组（supplementary） /etc/group 的 user_list 多个，且一个用户可出现在多行 passwd(5)："(Additional groups for the user are defined in the system group file; see group(5))."

两者在权限判定时一起参与：内核检查文件权限时，看的是「有效 GID == 文件 GID」或「文件 GID ∈ 附属组集合」。完整机制（getgroups / setgroups / initgroups、以及主组与附属组的互斥关系）属于 Ch9 §9.6 附属组 ID，本节只把文件侧说清楚。

⚠️ 所以「这个用户属于哪些组」这个问题，没有单一权威来源：一半在 /etc/passwd，一半在 /etc/group。想看进程当前真正持有的组，只能问内核（getgroups()）。

三、「没有条目」= 「没有这个组」

passwd(5) NOTES 原文：

If you want to create user groups, there must be an entry in /etc/group, or no group will exist.

这是一句很强的表述：/etc/passwd 里写了 gid=10240 不代表 10240 这个组存在。组存在与否只看 /etc/group。

本容器正好是这个状态（下面实测第一行）：fopen(/etc/group) 返回 NULL，getgrent() 遍历到 0 个组，而 ce 的 pw_gid 明明写着 10240。于是 getgrgid(10240) -> NULL —— 用户有主组号，但那个组不存在。

四、struct group 与空组的 gr_mem

getgrnam(3) 给出的 <grp.h> 定义：

struct group {
    char   *gr_name;   /* group name */
    char   *gr_passwd; /* group password */
    gid_t   gr_gid;    /* group ID */
    char  **gr_mem;    /* NULL-terminated array of pointers
                          to names of group members */
};

gr_mem 是「以 NULL 结尾的指针数组」。这里有个真实的坑：

空组的 gr_mem 不是 NULL，而是「首元素为 NULL 的数组」。 本节实测的 emptygrp 行给出了铁证：

(gr_mem==NULL? no ; gr_mem[0]==NULL? yes)

所以下面这种「教科书式」写法是错的：

/* ✗ 错：空组时 gr_mem 非 NULL，这段会打印一行空内容而不是跳过 */
if (gr->gr_mem != NULL) {
    for (char **m = gr->gr_mem; *m != NULL; m++)
        printf("%s ", *m);
}

正确写法是直接遍历 NULL 结尾数组，或者两级都判：

/* ✓ 直接遍历：空组自然一次都不进循环 */
for (char **m = gr->gr_mem; m != NULL && *m != NULL; m++)
    printf("%s ", *m);

五、一个真实的 errno 陷阱（本容器实测）

很多资料会告诉你这个范式：

errno = 0;
gr = getgrgid(gid);
if (gr == NULL) {
    if (errno == 0)  /* 没有这个组 */;
    else             /* 系统错误 */;
}

它在 /etc/group 不存在时会给出错误结论。 本节实测里 getgrgid(10240) 返回 NULL 且 errno = 2 (ENOENT)，按上面的写法会被判成「系统错误」，而真相是「确实没有这个组」。

原因在标准里写得很清楚。getgrnam(3) ERRORS 第一条居然是：

0 or ENOENT or ESRCH or EBADF or EPERM or ... The given name or gid was not found.

getpwnam(3) NOTES 讲得更透：

One might argue that according to POSIX errno should be left unchanged if an entry is not found. Experiments on various UNIX-like systems show that lots of different values occur in this situation: 0, ENOENT, EBADF, ESRCH, EWOULDBLOCK, EPERM, and probably others.

机制层面（glibc 2.39 nss/files-XXX.c）：

路径 代码 errno 行为
文件打不开 internal_setent() :69-85：*stream == NULL → status = errno == EAGAIN ? TRYAGAIN : UNAVAIL 完全不碰 errno → open() 留下的 ENOENT 一路透传给你
文件打开、扫完没匹配 internal_getent() :130：__set_errno (saved_errno);（saved_errno 在 :112 采集） 把你调用前设的 0 还回来 → errno 不变
缓冲太小 internal_getent() :114-119：*errnop = ERANGE ERANGE

所以准确的结论表是：

情况 返回值 errno 能否与「出错」区分
文件在，没有该 GID NULL 不变（0） ✅ 能
文件不在 / 打不开 NULL ENOENT / EACCES … ❌ 不能
内存不足 NULL ENOMEM ✅ 能

「errno 范式」只能区分「文件在、没这条」和「出问题了」。它区分不了「文件不在」和「出问题了」 —— 因为「文件不在」本身就是通过 errno 报上来的。

要稳妥，就得多做一步显式检查：

/* 想区分「没有这个组」和「组数据库不可用」，得自己看文件在不在 */
if (gr == NULL) {
    if (errno == 0)
        puts("没有这个组");
    else if (access("/etc/group", R_OK) != 0)
        puts("组数据库不可用（/etc/group 不存在或不可读）");
    else
        perror("getgrgid");     /* 真正的系统错误 */
}

或者接受更简单的工程取舍：NULL 一律按「没有这个组」处理，并把 errno 写进日志。

c8_3 真实环境的组查询 + 合成 group 文件的字段解析

完整程序见 ../code/c8_3_group_file.c：前半段如实报告真实环境的 API 行为（getgrent 计数、getgrgid 返回 NULL）；后半段用 fgetgrent() 解析一份合成 group，把 gr_mem 的空组语义跑出来。

/* c8_3_group_file.c —— 8.3：/etc/group 与「主组 / 附属组」
 *
 * 本容器里 /etc/group 根本不存在（第一条输出就是证据），所以这里做两件事：
 *   1. 如实报告真实 API 的行为（getgrent 计数、getgrgid 返回 NULL）
 *   2. 用 fgetgrent() 解析一份合成 group 文件，看 4 字段格式与 gr_mem 语义
 *
 * 编译：cc -Wall -Wextra -o c8_3_group_file c8_3_group_file.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <grp.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    /* ---- 1. 真实环境 ---- */
    errno = 0;                          /* errno 必须在调用前清零！ */
    FILE *f = fopen("/etc/group", "r");
    printf("fopen(/etc/group) -> %s  errno=%d(%s)\n",
           f ? "ok" : "NULL", errno, strerror(errno));
    if (f != NULL)
        fclose(f);

    int n = 0;
    struct group *gr;
    setgrent();
    while ((gr = getgrent()) != NULL)
        n++;
    endgrent();
    printf("getgrent() 遍历到 %d 个组\n", n);

    errno = 0;
    gr = getgrgid(10240);
    printf("getgrgid(10240) -> %s（errno=%d）—— passwd 里写了 gid 10240，\n"
           "                  但 group 文件不存在，所以查不到\n",
           gr ? gr->gr_name : "NULL", errno);

    struct passwd *pw = getpwnam("ce");
    if (pw != NULL) {
        const char *gname = NULL;
        struct group *g2 = getgrgid(pw->pw_gid);
        if (g2 != NULL)
            gname = g2->gr_name;
        printf("用户 ce 的主组 gid=%ld -> 组名 %s\n", (long) pw->pw_gid,
               gname ? gname : "(查不到)");
    }

    /* ---- 2. 合成 group 文件：看格式与 gr_mem ---- */
    const char *gf = "/tmp/c8_group_demo";
    FILE *w = fopen(gf, "w");
    if (w == NULL) {
        perror("fopen for write");
        return 1;
    }
    fputs("rocket:x:500:alice,bob\n"
          "toolchain:x:501:carol\n"
          "emptygrp:x:502:\n", w);      /* 空组：冒号后面什么都没有 */
    fclose(w);

    puts("\n-- fgetgrent() 解析合成 group（格式 name:x:gid:member,member） --");
    f = fopen(gf, "r");
    while (f != NULL && (gr = fgetgrent(f)) != NULL) {
        printf("组名=%-12s 组密文=%-3s gid=%-5ld 成员数=",
               gr->gr_name, gr->gr_passwd, (long) gr->gr_gid);

        if (gr->gr_mem == NULL) {
            printf("gr_mem==NULL");
        } else {
            int cnt = 0;
            for (char **m = gr->gr_mem; *m != NULL; m++)
                cnt++;
            printf("%d", cnt);
        }
        printf("  成员=");
        if (gr->gr_mem != NULL) {
            for (char **m = gr->gr_mem; *m != NULL; m++)
                printf("[%s]", *m);
        }
        /* 空组的 gr_mem 不是 NULL，而是「首元素为 NULL 的数组」 */
        printf("   (gr_mem==NULL? %s ; gr_mem[0]==NULL? %s)\n",
               gr->gr_mem == NULL ? "yes" : "no",
               (gr->gr_mem == NULL || gr->gr_mem[0] == NULL) ? "yes" : "no");
    }
    if (f != NULL)
        fclose(f);

    puts("\n主组：写在 /etc/passwd 的 gid 字段（每个用户恰好一个）");
    puts("附属组：写在 /etc/group 的成员列表里（一个用户可以出现在多行）");
    return 0;
}

解读

  1. 前三行是「文件为空」的真实后果：/etc/group 不存在 → getgrent() 遍历到 0 个组 → getgrgid(10240) 返回 NULL。而 ce 明明有 pw_gid=10240。这就是 passwd(5) 那句 "there must be an entry in /etc/group, or no group will exist" 的实证。
  2. errno=2 是本节的陷阱样本。按教科书写法它会被判成「系统错误」，真相是「没有这个组」。详见要点第五节：internal_setent() 在 fopen 失败时不碰 errno，而成功扫完没匹配时反而会把 errno 还回 0。
  3. fgetgrent() 解析合成文件得到三组：rocket（2 人）、toolchain（1 人）、emptygrp（0 人）。格式 name:x:gid:m1,m2 被逐字段还原，和 8.1 的 passwd 一样：「组数据库 API」就是对这一行的封装。
  4. emptygrp 那一行是本节的第二个坑：gr_mem==NULL? no 但 gr_mem[0]==NULL? yes。空组的 gr_mem 是一个首元素为 NULL 的数组，不是 NULL 指针。任何写 if (gr->gr_mem != NULL) 就认为「有成员」的代码都会在这里走错分支。
  5. 最后两行是在提醒：「用户属于哪些组」没有单一权威来源。/etc/passwd 只给一个主组号，/etc/group 给的是名单（从组视角看）；两者都不等于「这个进程此刻持有哪些组」（那要问内核，见 Ch9 §9.6）。

HFT / 嵌入式关联

  • 不要在热路径上做「组名 ↔ gid」翻译。getgrgid() 和 getpwuid() 一样要 fopen + 线性扫描；接了 LDAP/SSSD 的机器上还会变成网络往返。日志、审计、权限报错信息里优先写数字 gid。
  • 权限排查要问内核，不要读文件。用户抱怨「明明在组里却没权限」时，正确的检查顺序是：① id（看进程/登录会话实际持有的组）；② getgroups() 的输出；③ 才去看 /etc/group。group(5) 的 BUGS 段说明文件内容经常是过期的。
  • getgrent() 遍历是 O(n) 且每次重开文件，/etc/group 在大量用户/组的机器上可以很大。要枚举全系统组，读一次 fgetgrent() 或直接缓存。
  • 嵌入式：BusyBox 系统里 /etc/group 常常只有 root:x:0: 一行，甚至根本不存在。依赖「gid → 组名」做展示或策略判断的代码在嵌入式上必须能接受 NULL，否则会打印一堆 (null) 或直接崩在 gr_name 解引用上。
  • gr_mem 的空组语义是真会咬人的：写「打印组成员」这类工具时，用 for (m = gr->gr_mem; m && *m; m++) 而不是 if (gr->gr_mem) { ... }，可以省掉一个只在空组上出现的 bug。
  • + / - 开头的组行是 NIS 语法，files 后端会主动跳过（nss/files-grp.c 的 break_if_match 里带 name[0] != '-' && name[0] != '+'）。交叉编译的老发行版镜像里见到这类行不要当损坏数据删掉。

自测题

1. 一个用户的 /etc/passwd 里写着 gid=10240，是否说明 10240 这个组存在？

不说明。

passwd(5) NOTES 原文："If you want to create user groups, there must be an entry in /etc/group, or no group will exist." 组的存在性只看 /etc/group；/etc/passwd 的 GID 字段只是一个数字。

本容器就是活样本：ce 的 pw_gid = 10240，而 /etc/group 根本不存在 → getgrent() 遍历到 0 个组，getgrgid(10240) -> NULL。

工程影响：任何"先把 gid 翻成组名再展示/判断"的代码都必须能接受 NULL。这个状态在精简容器镜像里非常常见（FROM scratch 或只 COPY 应用程序的那种镜像里根本没有 /etc/group）。

2. 空组的 gr_mem 是 NULL 吗？

通常不是。 glibc 的 files 后端给出的空组 gr_mem 是「首元素为 NULL 的数组」—— 指针本身非 NULL，但 gr_mem[0] == NULL。

本节实测（emptygrp 行）：(gr_mem==NULL? no ; gr_mem[0]==NULL? yes)。

所以：

/* ✗ 会走错分支 */
if (gr->gr_mem != NULL) { /* 这里会以为"有成员" */ }

/* ✓ 两种都覆盖 */
for (char **m = gr->gr_mem; m != NULL && *m != NULL; m++)
    printf("[%s]", *m);

注意 gr_mem 的契约本来就是 "NULL-terminated array"（getgrnam(3)）——「以 NULL 结尾」意味着空数组只含一个 NULL，而不是「没有数组」。按这个契约写，空组自然一次循环都不进。

3. errno = 0; getgrgid(gid); 之后 errno == ENOENT，是「没有这个组」还是「出错了」？

在这个场景下分不清 —— 而 ENOENT 恰恰是「没有这个组」的常见取值之一。

getgrnam(3) ERRORS 第一条把这个可能性直接列出来了：

0 or ENOENT or ESRCH or EBADF or EPERM or ... The given name or gid was not found.

getpwnam(3) NOTES 也承认这一点："Experiments on various UNIX-like systems show that lots of different values occur in this situation: 0, ENOENT, EBADF, ESRCH, EWOULDBLOCK, EPERM, and probably others."

机制（glibc 2.39 nss/files-XXX.c）：文件打不开时 internal_setent() 只设 NSS_STATUS_UNAVAIL，不碰 errno，于是 open() 留下的 ENOENT 透传给你；反过来「文件打开、扫完没匹配」的路径会在 :130 用 __set_errno(saved_errno) 把你设的 0 还回来。

也就是说，除了 ENOENT 这种"后端不可用"的取值外，errno 范式是成立的。要稳妥就加一步 access("/etc/group", R_OK) 做存在性检查，或者接受「NULL 一律按没有这个组处理」并把 errno 记进日志。

Retrieving User and Group Information

本节讲什么

前三节讲的是文件，这一节讲接口。同一个「查账号」需求，libc 给了三层能力：

  1. 单条查（getpwnam / getpwuid / getgrnam / getgrgid）—— 返回值语义怎么读？
  2. 顺序遍历（setpwent / getpwent / endpwent 家族）—— 怎么从头扫到尾？
  3. 可重入版（getpwnam_r 家族）—— 多线程、以及一个全新的错误：ERANGE。

再加两个只在「测试/迁移」时用得到的入口：fgetpwent(FILE *) / fgetgrent(FILE *)。

要点

一、errno 范式：怎么读，以及它什么时候失效

getpwnam(3) RETURN VALUE 原文：

The getpwnam() and getpwuid() functions return a pointer to a passwd structure, or NULL if the matching entry is not found or an error occurs. If an error occurs, errno is set to indicate the error. If one wants to check errno after the call, it should be set to zero before the call.

于是有了这个范式：

errno = 0;                          /* ← 必须先清零，否则读到的是上一次的残留 */
struct passwd *pw = getpwnam("nobody");
if (pw == NULL) {
    if (errno == 0)   /* 确实"没有这条记录" */;
    else              /* 出错了 */;
}

但它有一个真实的失效点：errno 在「没找到」时的取值标准根本没有规定。getpwnam(3) NOTES 原文：

It does not call "not found" an error, and hence does not specify what value errno might have in this situation. But that makes it impossible to recognize errors. One might argue that according to POSIX errno should be left unchanged if an entry is not found. Experiments on various UNIX-like systems show that lots of different values occur in this situation: 0, ENOENT, EBADF, ESRCH, EWOULDBLOCK, EPERM, and probably others.

getgrnam(3) ERRORS 索性把 ENOENT 直接列进了「没找到」的取值：

0 or ENOENT or ESRCH or EBADF or EPERM or ... The given name or gid was not found.

所以这条范式的适用边界是：当后端数据库文件本身能正常打开时，它是可靠的（本节实测中 /etc/passwd 存在，getpwnam("nosuchuser") 就是干净的 errno=0）；当后端文件缺失/不可读时（/etc/group 不存在的情况），errno 会被 open() 的 ENOENT 污染。机制见 8.3 第五节。

二、静态缓冲：指针「有效到下一次同类调用为止」

getpwnam(3) RETURN VALUE 原文：

The return value may point to a static area, and may be overwritten by subsequent calls to getpwent(3), getpwnam(), or getpwuid(). (Do not pass the returned pointer to free(3).)

三件事要分清楚：

事实 说明
不要 free 它不是 malloc 出来的
不要存 「下一次同类调用」就会覆写 —— 这个「同类」比想象中宽：getpwent / getpwnam / getpwuid 共用同一块
不要跨线程 getpwnam(3) ATTRIBUTES 明确标 MT-Unsafe race:pwnam locale

实现就在 nss/getXXbyYY.c:93：一个模块级 static char *buffer;，首次调用时懒分配（:123-126），所有非 _r 版本的 getpwnam / getpwuid / getgrnam / getgrgid 都从同一个转换单元生成。

⚠️ 地址不可假设。本节实测里 fgetpwent() 三次拿到的是同一个地址，但 getpwnam("ce") 和 getpwuid(10240)（同一个用户！）拿到的是两个不同地址。所以正确结论是「指针的有效期到下一次同类调用为止」，而不是「同一个账户总是同一块内存」。

fgetpwent(FILE *) 这一层很关键：因为 getpwnam() 的路径是编译期写死的（nss/files-XXX.c:42 的 #define DATAFILE "/etc/" DATABASE），想读自己造的测试文件，这是唯一的正规入口。本节四个演示里就有三个用了它。

四、_r 版本的语义变化：三个必须记住的点

getpwnam(3) RETURN VALUE 对 _r 版本的定义：

On success, getpwnam_r() and getpwuid_r() return zero, and set *result to pwd. If no matching password record was found, these functions return 0 and store NULL in *result. In case of error, an error number is returned, and NULL is stored in *result.

# 变化 后果
1 返回错误号，不是 -1 不要再对它用 errno 范式；s == ERANGE 而不是 s == -1 && errno == ERANGE
2 「不存在」= s == 0 且 res == NULL 只看 s 是不够的 —— 成功和"没找到"都返回 0
3 多了一种全新错误 ERANGE 你给的缓冲太小 → 必须自己加大重试

缓冲怎么定大小？getpwnam(3) DESCRIPTION：

The call sysconf(_SC_GETPW_R_SIZE_MAX) returns either -1, without changing errno, or an initial suggested size for buf. (If this size is too small, the call fails with ERANGE, in which case the caller can retry with a larger buffer.)

注意两个细节：sysconf 返回 -1 时不能去看 errno（man 明说 "without changing errno"），要自己给个兜底值（man 3 getpwnam 的 EXAMPLES 用的是 16384）；以及那个「建议值」只是建议，ERANGE 重试不是可选项。非 _r 版本则由 libc 自己干这件事（nss/getXXbyYY.c:139-158：while (... == ERANGE) { buffer_size *= 2; realloc(...); }）。

c8_4 返回值语义：errno 范式 vs 静态缓冲

完整程序见 ../code/c8_4_lookup_api.c：先演示 errno 范式，再用 fgetpwent() 读三条合成记录，把「指针被覆写」这件事打印成地址证据。

/* c8_4_lookup_api.c —— 8.4：查询 API 的返回值语义
 *
 * 三个必须记住的点，全部实测：
 *   1. 「查不到」= 返回 NULL 且 errno 不变（要把 errno 先清零才能区分）
 *   2. 返回的指针指向静态缓冲，下一次调用就把它改写掉
 *   3. 静态缓冲的地址由 libc 决定，两次调用可能不同
 *
 * 编译：cc -Wall -Wextra -o c8_4_lookup_api c8_4_lookup_api.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <grp.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    /* ---- 1. errno 范式 ---- */
    errno = 0;
    struct passwd *pw = getpwnam("nosuchuser");
    printf("errno=0; getpwnam(\"nosuchuser\") -> %s  errno=%d  => %s\n",
           pw ? "non-NULL" : "NULL", errno,
           (pw == NULL && errno == 0) ? "「用户不存在」" : "「系统错误」");

    errno = 0;
    pw = getpwuid(0);
    printf("errno=0; getpwuid(0)              -> %s  errno=%d  => %s\n",
           pw ? pw->pw_name : "NULL", errno,
           (pw == NULL && errno == 0) ? "「无此 UID 的记录」" : "「系统错误」");

    errno = 0;
    pw = getpwnam("ce");
    if (pw != NULL)
        printf("errno=0; getpwnam(\"ce\")           -> uid=%ld gid=%ld gecos=%s\n",
               (long) pw->pw_uid, (long) pw->pw_gid, pw->pw_gecos);

    /* ---- 2. 静态缓冲：连续读两条记录，前一个指针的内容被改写 ---- */
    const char *pf = "/tmp/c8_passwd_demo";
    FILE *w = fopen(pf, "w");
    if (w == NULL) {
        perror("fopen for write");
        return 1;
    }
    fputs("alice:x:1001:1001:Alice:/home/alice:/bin/bash\n"
          "bob:x:1002:1002:Bob:/home/bob:/bin/sh\n"
          "carol:x:1003:1003:Carol:/home/carol:/sbin/nologin\n", w);
    fclose(w);

    puts("\n-- 静态缓冲实测：fgetpwent() 读三条记录 --");
    FILE *f = fopen(pf, "r");
    struct passwd *p1 = fgetpwent(f);
    printf("第 1 条: p1=%p p1->pw_name=\"%s\"\n", (void *) p1, p1->pw_name);

    struct passwd *p2 = fgetpwent(f);
    printf("第 2 条: p2=%p p2->pw_name=\"%s\"\n", (void *) p2, p2->pw_name);
    printf("        此刻再用 p1 读 -> p1->pw_name=\"%s\"  (p1==p2? %s)\n",
           p1->pw_name, p1 == p2 ? "是" : "否");

    struct passwd *p3 = fgetpwent(f);
    printf("第 3 条: p3=%p p3->pw_name=\"%s\"\n", (void *) p3, p3->pw_name);
    printf("        此刻 p1->pw_name=\"%s\"，p2->pw_name=\"%s\" —— 三个指针是同一块内存\n",
           p1->pw_name, p2->pw_name);
    fclose(f);

    /* ---- 3. 地址由 libc 决定，别做任何假设 ---- */
    struct passwd *a = getpwnam("ce");
    struct passwd *b = getpwuid(10240);
    printf("\ngetpwnam(\"ce\")=%p  getpwuid(10240)=%p  (同一用户，地址%s)\n",
           (void *) a, (void *) b, a == b ? "相同" : "不同");

    puts("\n结论：返回的指针「有效到下一次同类调用为止」，要留住内容就得自己拷一份；");
    puts("      多线程里必须换 _r 版本（见 c8_5_lookup_r.c）。");
    return 0;
}

解读

  1. errno 范式在本容器上是可用的（前两行）：/etc/passwd 存在，所以「没找到」走的是「文件打开、扫完没匹配」那条路，internal_getent() 在 nss/files-XXX.c:130 用 __set_errno(saved_errno) 把调用前设的 0 还了回来 → errno=0 干净地表示"不存在"。这个干净是有条件的：换成 /etc/group（文件不存在）就不是这样了，见 8.3。
  2. getpwuid(0) 又一次返回 NULL：进程 uid=0，/etc/passwd 里没有 0 号记录。这不是错误，errno=0 说得很清楚。
  3. 三行地址完全相同（0x7da0e6211240），这是「静态缓冲」最硬的证据。注意第 2 条那行：用 p1 去读，读到的是 "bob" —— p1、p2、p3 指向同一块内存，后一次调用把前一次的字段全改写了。所以「读一批记录存进数组」的写法在这种 API 上直接是 bug，必须 strdup 或者换成 _r 版本。
  4. 最后一行才是最容易踩的：getpwnam("ce") 与 getpwuid(10240) 查的是同一个用户，地址却不同（0x...320 vs 0x...380）。所以「同一个账户 = 同一个指针」不成立；唯一能依赖的契约是 man 的那句「下一次同类调用就会覆写」。任何基于地址相等的缓存都会在某些 libc / NSS 后端上翻车。

c8_5 _r 版本：错误号、*result 与 ERANGE 重试

完整程序见 ../code/c8_5_lookup_r.c：成功路径、「不存在」的两种表达、以及缓冲从 8 字节指数增长到 64 字节才成功的全过程。

/* c8_5_lookup_r.c —— 8.4：_r 版本（可重入）与 ERANGE 重试
 *
 * 非 _r 版本把结果放在静态缓冲里；_r 版本由调用者提供 struct 与缓冲，
 * 因此线程安全。代价是要自己处理「缓冲不够」这一种全新的错误。
 *
 * 编译：cc -Wall -Wextra -o c8_5_lookup_r c8_5_lookup_r.c
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <grp.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    long pw_max = sysconf(_SC_GETPW_R_SIZE_MAX);
    long gr_max = sysconf(_SC_GETGR_R_SIZE_MAX);
    printf("_SC_GETPW_R_SIZE_MAX=%ld  _SC_GETGR_R_SIZE_MAX=%ld\n", pw_max, gr_max);

    struct passwd pw, *res = NULL;
    char *buf = malloc((size_t) pw_max);

    /* ---- 成功路径 ---- */
    int s = getpwnam_r("ce", &pw, buf, (size_t) pw_max, &res);
    printf("getpwnam_r(\"ce\", bufsize=%ld) -> s=%d res=%s", pw_max, s,
           res ? "non-NULL" : "NULL");
    if (res != NULL)
        printf("  pw_name=%s pw_uid=%ld pw_gecos=%s", pw.pw_name,
               (long) pw.pw_uid, pw.pw_gecos);
    else if (s == ENOENT || s == ESRCH)
        printf("  （errno 风格：s=ENOENT 表示不存在）");
    putchar('\n');

    /* ---- 「不存在」在 _r 里的表达方式变了 ---- */
    res = (struct passwd *) 0x1;        /* 故意塞个非 NULL，看库里会不会改它 */
    s = getpwnam_r("nosuchuser", &pw, buf, (size_t) pw_max, &res);
    printf("getpwnam_r(\"nosuchuser\")     -> s=%d res=%s"
           "   （s==0 且 res==NULL 才是「不存在」；只看 s 是不够的）\n",
           s, res ? "non-NULL" : "NULL");
    free(buf);

    /* ---- 缓冲太小：ERANGE，指数增长重试 ---- */
    puts("\n-- 缓冲从小往大试，直到不再 ERANGE --");
    size_t sz = 8;
    while (sz <= 8192) {
        char *b = malloc(sz);
        if (b == NULL)
            break;
        res = NULL;
        s = getpwnam_r("ce", &pw, b, sz, &res);
        printf("bufsize=%-5zu -> s=%-3d %-28s res=%s\n", sz, s,
               s == ERANGE ? "ERANGE（缓冲不够）" : strerror(s),
               res ? "non-NULL" : "NULL");
        free(b);
        if (s != ERANGE)
            break;
        sz *= 2;
    }

    puts("\n注意：_r 版本失败时返回的是「错误号」，不是 -1；");
    puts("      它不会去动 errno —— 所以不要再对它用 errno 范式。");
    return 0;
}

  2. ERANGE 是有真实下界的：bufsize = 8 / 16 / 32 全部 s=34（ERANGE 的数值就是 34），到 64 才成功。注意 sysconf 给的"建议值"是 1024 —— 比实际需要大得多。man 只说它是 "an initial suggested size"，不是保证值；反过来，比建议值小也可能成功。所以正确写法是「从建议值开始，失败就翻倍重试」，而不是"必须给 1024"。
  3. _r 版本不动 errno（第五行注释）。所以 if (errno == 0) 不存在 这类写法在 _r 上完全无效，必须看返回值 s 和出参 res 的组合。
  4. 常见误写是把 ERANGE 重试写成「给个更大的固定值再来一次」。真到临界点上，一次可能还是不够；nss/getXXbyYY.c:139-158 里 libc 自己的做法就是 while 循环 + buffer_size *= 2 + realloc，照抄这个形状。

uid_t           /* Return UID corresponding to 'name', or -1 on error */
userIdFromName(const char *name)
{
    struct passwd *pwd;
    uid_t u;
    char *endptr;

    if (name == NULL || *name == '\0')  /* On NULL or empty string */
        return -1;                      /* return an error */

    u = strtol(name, &endptr, 10);      /* As a convenience to caller */
    if (*endptr == '\0')                /* allow a numeric string */
        return u;

    pwd = getpwnam(name);
    if (pwd == NULL)
        return -1;

    return pwd->pw_uid;
}

/* t_ugid.c —— 验收原书 Listing 8-1 的四个助手函数

#include "ugid_functions.h"

int main(void)
{
    const char *names[] = { "ce", "1000", "0", "nosuchuser", "" };
    for (size_t i = 0; i < sizeof names / sizeof names[0]; i++) {
        uid_t u = userIdFromName(names[i]);
        gid_t g = groupIdFromName(names[i]);

  2. -1 打印出来是 4294967295。函数失败返回 (uid_t) -1，而 uid_t 是无符号的，printf("%ld", (long) u) 就把 32 位的 0xFFFFFFFF 显示成 4294967295。判断失败必须写 if (u == (uid_t) -1)，不能写 if (u == -1)（虽然等价，但读代码的人会以为 uid_t 是有符号的），更不能用 > 0 之类的关系判断。
  3. "" 和 NULL 都返回 (uid_t) -1，不打数据库 —— 函数开头的 if (name == NULL || *name == '\0') return -1; 拦住了。这是好设计：调用方不用自己判空。

 *
 * 原书说明：This file is not printed in the book; it is a supplementary file
 * for Chapter 8.（即它不是 Listing，只是随章发布的示例。）
 *
 * 演示 getpwnam_r()：可重入版本，结果写进调用者提供的 struct passwd 与缓冲。
 * 原书依赖 tlpi_hdr.h（取 usageErr/errExitEN/malloc 包装），此处内联最小实现，

 *

 *     printf("Name: %s\n", pwd.pw_gecos);

 * 也是 "Name: %s" 配 pwd.pw_gecos。对本容器的 ce 账号，pw_gecos =
 * "Not a real account" —— 输出看着像出错，其实标签与字段本来就不对应。
 * 详见 notes/8.4-retrieving-info.md。
 *
 * 编译：cc -Wall -Wextra -o t_getpwnam_r t_getpwnam_r.c
 */
#define _DEFAULT_SOURCE
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

int
main(int argc, char *argv[])
{
    if (argc != 2 || strcmp(argv[1], "--help") == 0) {
        fprintf(stderr, "Usage: %s username\n", argv[0]);
        exit(EXIT_FAILURE);

    size_t bufSize = sysconf(_SC_GETPW_R_SIZE_MAX);
    char *buf = malloc(bufSize);

        fprintf(stderr, "malloc %zu failed\n", bufSize);
        exit(EXIT_FAILURE);

    struct passwd pwd;

        printf("Name: %s\n", pwd.pw_gecos);
    else
        printf("Not found\n");

HFT / 嵌入式关联

  • getXXbyYY 系列一律不可以在热路径上调用。不仅是 O(n) 文件扫描：接了 SSSD/LDAP 之后它就是一次网络往返（可能几百毫秒）。行情/风控线程里一次 getpwuid 足以造成可观测的抖动。
  • 「一次读一批」必须自己拷。非 _r 版本的返回值是同一块静态内存，struct passwd 里的 char * 也指向那块内存里的字符串。要留住就必须 strdup 每个字段（或整块 memcpy），否则整批记录会退化成"最后一条复制 N 遍"。这是这类 API 最经典的 bug。
  • 多线程服务启动时用 _r 版，并且按 nss/getXXbyYY.c 的形状写重试（while (ERANGE) buffer_size *= 2）。给个固定 1024 在接了 LDAP 的机器上会被打脸 —— 后端返回的 gecos/dir 可以很长。
  • sysconf(_SC_LOGIN_NAME_MAX) / _SC_GETPW_R_SIZE_MAX 都可能返回 -1，而且 sysconf 在返回 -1 时不保证设置 errno（getpwnam(3) 明说 "without changing errno"）。原书 Listing 8-2 里就写了兜底值 256。别拿 errno 去判 sysconf 失败。
  • 嵌入式：uClibc/musl 的 getpwent 家族行为与 glibc 有差异，尤其是「_r 版在"没找到"时返回什么」和「静态缓冲有几块」。跨 libc 的代码只依赖 man 里写下的契约（返回值、*result、NULL 结束），不要依赖实测到的地址行为。
  • 每次调用都重开文件这一点在嵌入式上尤其贵（/etc/passwd 可能在只有几十 KB/s 的 jffs2/squashfs 上）。枚举用户的代码应该 setpwent() 打开一次、endpwent() 关掉，而不是循环里 getpwnam。

自测题

1. 把 getpwnam() 返回的指针存进数组，循环读 100 个用户，会得到什么？

会得到「100 份最后一条记录」。

getpwnam(3) RETURN VALUE："The return value may point to a static area, and may be overwritten by subsequent calls to getpwent(3), getpwnam(), or getpwuid()."

本节实测把这件事打成了地址证据：fgetpwent() 三次返回的都是 0x7da0e6211240，而且用第 1 个指针 p1 去读，读到的是第 2 条记录的 "bob"。

注意坑比 "同一个指针" 更深一层：struct passwd 里的 char *pw_name 等字段也指向同一块静态内存里的偏移。所以即使你把 struct passwd 按值拷出来（struct passwd copy = *p;），里面的 char * 依然会被下一次调用改掉。

正确做法： - 每条记录立刻把需要的字段 strdup / snprintf 存下来； - 或者改用 getpwnam_r()，自己提供 struct passwd 和 buffer（多线程下也是必须的）。

2. getpwnam_r() 返回 0，是成功还是没找到？

都可能是。必须同时看出参 *result。

getpwnam(3) RETURN VALUE 原文把两种情形都写成返回 0：

On success, getpwnam_r() and getpwuid_r() return zero, and set *result to pwd. If no matching password record was found, these functions return 0 and store NULL in *result. In case of error, an error number is returned, and NULL is stored in *result.

所以判定表是：

s *result 含义
0 非 NULL ✅ 成功
0 NULL 没有这条记录
非 0（如 ERANGE=34） NULL 出错

本节实测两行正好覆盖前两种：s=0 res=non-NULL（成功）与 s=0 res=NULL（不存在）。程序里还故意把 res 预置成 (struct passwd *)0x1 再调第二次，结果库里把它改成了 NULL —— 说明这个出参每次都会被写。

另一种常见误写是拿 _r 版本去用 errno 范式：_r 版本不动 errno，errno 在这里没有任何意义。

3. sysconf(_SC_GETPW_R_SIZE_MAX) 返回 1024，是不是就说明 1024 一定够？给 8 / 16 / 32 / 64 会怎样？

不是。它只是 "an initial suggested size"。

getpwnam(3) DESCRIPTION："returns either -1, without changing errno, or an initial suggested size for buf. (If this size is too small, the call fails with ERANGE, in which case the caller can retry with a larger buffer.)"

本节实测（用同一个 getpwnam_r("ce", ...)）：

bufsize=8     -> s=34  ERANGE（缓冲不够）     res=NULL
bufsize=16    -> s=34  ERANGE（缓冲不够）     res=NULL
bufsize=32    -> s=34  ERANGE（缓冲不够）     res=NULL
bufsize=64    -> s=0   Success                      res=non-NULL

两个反直觉点：

  1. s 是 34，不是 -1 —— _r 版本返回的是错误号本身（ERANGE 的数值就是 34）。
  2. 64 就够了，比建议值 1024 小得多。说明建议值是偏保守的上界（struct pwent_data 预留给最长行），不是"必须给这么多"。

正确写法照抄 glibc 自己（nss/getXXbyYY.c:139-158）：从建议值开始，ERANGE 就 buffer_size *= 2 重试。另外 sysconf 返回 -1 时不要看 errno —— man 明说 "without changing errno"，要自己给兜底值。

4. userIdFromName("1000") 返回 1000 —— 它查库了吗？

没有。这是函数里特意留的「数字快捷路径」。

原书 ugid_functions.c 的函数体：

u = strtol(name, &endptr, 10);      /* As a convenience to caller */
if (*endptr == '\0')                /* allow a numeric string */
    return u;

pwd = getpwnam(name);               /* 只有不是纯数字才走到这里 */

strtol 把整串都吃掉（*endptr == '\0'）就直接返回，完全不碰数据库。所以本容器里（根本没有 1000 号用户）userIdFromName("1000") 照样返回 1000。

三条推论：

  • userIdFromName("0") 永远返回 0，即使 0 号记录不存在（实测里 userNameFromId(0) -> (NULL) 与它并存）。
  • 想区分「这个数字真的对应一个用户的 uid」和「只是个数字」，得另调一次 getpwuid() 验证。
  • 这也是这类 helper 的常见取舍：方便调用方写 ./tool 1000 和 ./tool wzp 都行，代价是丢失了一次存在性校验。
5. 为什么 t_getpwnam_r ce 打出的是 Name: Not a real account？

因为那一行打的是 pw_gecos（注释字段），不是 pw_name。

原书 t_getpwnam_r.c 的源码：

if (result != NULL)
    printf("Name: %s\n", pwd.pw_gecos);     /* ← 字段名是 _gecos */
else
    printf("Not found\n");

pw_gecos 对应 /etc/passwd 的第 5 字段（passwd(5) 称它为 "comment field ... used only for informational purposes"）。本容器的 /etc/passwd 里 ce 的 gecos 就是 Not a real account，所以输出看着像报错，实际只是标签写的是 Name、值来自注释字段。

这一点已核对上游：man7.org 上 TLPI 官方源码里确实是 pwd.pw_gecos；man 3 getpwnam 的 EXAMPLES 里也是同样的 printf("Name: %s\n", pwd.pw_gecos)。这是上游一路传下来的写法，不是本仓库抄错。

顺带它可以当 _r 的调用骨架模板：sysconf 拿建议大小 → malloc → getpwnam_r(name, &pwd, buf, bufSize, &result) → 判 s != 0（错误）/ 判 result != NULL（找到）。

Password Encryption and User Authentication

本节讲什么

要点

一、接口与那个过时的宏

crypt(3) SYNOPSIS 与 Feature Test Macro 原文：

#include <unistd.h>

char *crypt(const char *key, const char *salt);

#include <crypt.h>

char *crypt_r(const char *key, const char *salt, struct crypt_data *restrict data);

Feature Test Macro Requirements for glibc (see feature_test_macros(7)):

crypt(): Since glibc 2.28: _DEFAULT_SOURCE glibc 2.27 and earlier: _XOPEN_SOURCE

crypt_r(): _GNU_SOURCE

这就是「老教程为什么不能用」的典型：网上大量示例（以及原书 Listing 8-2）写的是 #define _XOPEN_SOURCE，那是 glibc 2.27 及更早的要求。在 glibc ≥ 2.28 上要用 _DEFAULT_SOURCE。

还有一层容易忽略的：glibc 自己已经不提供 crypt() 了。crypt(3) HISTORY 段原文：

The crypt(), encrypt(3), and setkey(3) functions are part of the POSIX.1-2008 XSI Options Group for Encryption and are optional. If the interfaces are not available, then the symbolic constant _XOPEN_CRYPT is either not defined, or it is defined to -1 and availability can be checked at run time with sysconf(3). This may be the case if the downstream distribution has switched from glibc crypt to libxcrypt. When recompiling applications in such distributions, the programmer must detect if _XOPEN_CRYPT is not available and include <crypt.h> for the function prototypes; otherwise libxcrypt is an ABI-compatible drop-in replacement.

本容器就是这条路径：LIBRARY 段写的是 "Password hashing library (libcrypt, -lcrypt)"，所以编译要加 -lcrypt。（-lcrypt 在 Debian/Ubuntu 上是必需的，glibc 2.39 已经不再带这个库。）

二、盐 = 算法标识 + 轮数 + 随机前缀

盐看着像「一串随机字符」，实际是带格式的。crypt(3) NOTES 原文：

If salt is a character string starting with the characters "$id$" followed by a string optionally terminated by "$", then the result has the form:

$id$salt$hashed

id identifies the hashing method used instead of DES ... The following values of id are supported:

ID Method
1 MD5
2a Blowfish (not in mainline glibc; added in some Linux distributions)
5 SHA-256 (since glibc 2.7)
6 SHA-512 (since glibc 2.7)

「hashed 部分长度是固定的」也有原文：

"salt" stands for the up to 16 characters following "$id$" in the salt. The "hashed" part of the password string is the actual computed password. The size of this string is fixed: MD5 22 characters SHA-256 43 characters SHA-512 86 characters

轮数可调（自 glibc 2.7）：

the SHA-256 and SHA-512 implementations support a user-supplied number of hashing rounds, defaulting to 5000. If the "$id$" characters in the salt are followed by "rounds=xxx$" ... the result has the form $id$rounds=yyy$salt$hashed ... The number of rounds actually used is 1000 if xxx is less than 1000, 999999999 if xxx is greater than 999999999, and is equal to xxx otherwise.

这些长度和实测完全对得上（见下文 c8_6 的输出）：

$5$ 与 $6$ 差的 43 字符不是「加密更强」，是摘要更长而已 —— 后面成本表会说明「长度 ≠ 慢」。

三、DES 的三个硬限制

crypt(3) DESCRIPTION 原文：

salt is a two-character string chosen from the set [a-zA-Z0-9./]. This string is used to perturb the algorithm in one of 4096 different ways.

By taking the lowest 7 bits of each of the first eight characters of the key, a 56-bit key is obtained. ... The returned value points to the hashed password, a series of 13 printable ASCII characters ...

Warning: the key space consists of 2**56 equal 7.2e16 possible values. Exhaustive searches of this key space are possible using massively parallel computers.

三个直接后果：

限制 数值 后果
盐只有 2 字符、字符集 64 个 64² = 4096 种（12 bit） 彩虹表 / 预计算完全可行
口令只用前 8 个字符 「第 9 个字符起完全不影响结果」 长口令白设
密钥空间 2^56 ≈ 7.2×10¹⁶ 今天的专用硬件能穷举

crypt(3) 还专门警告不要拿它做别的密码学用途：

The DES algorithm itself has a few quirks which make the use of the crypt() interface a very poor choice for anything other than password authentication. If you are planning on using the crypt() interface for a cryptography project, don't do it.

四、⭐ 失败返回值不是 NULL —— 以及由此产生的漏洞

crypt(3) RETURN VALUE 只说：

On success, a pointer to the hashed password is returned. On error, NULL is returned.

但实测不是这样。 本容器（libxcrypt）在盐无法识别时返回的是字符串 *0（c8_6 输出里 $y$ 那一行，长度 2）。源码层面的确切实现是 libxcrypt 4.4.36 lib/util-make-failure-token.c：

void
make_failure_token (const char *setting, char *output, int size)
{
  if (size >= 3)
    {
      output[0] = '*';
      output[1] = '0';
      output[2] = '\0';

      if (setting && setting[0] == '*' && setting[1] == '0')
        output[1] = '1';
    }

  /* If there's not enough space for the full failure token, do the
     best we can.  */
  else if (size == 2)
    {
      output[0] = '*';
      output[1] = '\0';
    }
  else if (size == 1)
    {
      output[0] = '\0';
    }
}

两个哨兵的分工很明确：

返回值 含义
*0 盐无效 / 算法无法识别 → 算不出来
*1 输入本身就是 *0 → 连'"试算"都拒绝（防止拿失败结果再喂回来）

*1 这条分支就是漏洞的入口。 crypt() 和 getpwnam() 一样返回静态缓冲（crypt(3)："The return value points to static data whose content is overwritten by each call."），于是下面这种「看起来和教科书一样」的认证函数会被绕过：

/* ❌ 只要 stored 恰好指向 crypt() 自己的静态缓冲，任何口令都"通过" */
static int bad_verify(const char *password, const char *stored)
{
    return strcmp(crypt(password, stored), stored) == 0;
}

失效链条，三步：

  1. stored 是上一次 crypt() 的返回值（同一块静态缓冲）；
  2. 本次 crypt(password, stored) 检测到 stored 以 *0 开头 → 返回 *1，并且这块内存上原来那串密文被覆写成了 *1；
  3. strcmp("*1", stored) 两边指向同一块内存 → 恒等 → 返回 1（通过）。

本节实测把这条链完整跑出来了：bad_verify("definitely-wrong", stored_ptr) = 1，而且紧接着打印 stored_ptr 的内容，它已经变成 *1。

安全的写法必须做四件事（c8_8 的 good_verify）：

static int good_verify(const char *password, const char *stored)
{
    char salt[256];

    if (password == NULL || stored == NULL)
        return 0;
    if (snprintf(salt, sizeof salt, "%s", stored) >= (int) sizeof salt)
        return 0;                       /* ① 密文长得离谱，直接拒绝 */
    if (salt[0] == '!' || salt[0] == '*')
        return 0;                       /* ② 先挡锁定 / 无口令 */

    char *got = crypt(password, salt);  /* ③ 用副本作盐，不用原缓冲 */
    if (got == NULL)
        return 0;
    if (got[0] == '*')
        return 0;                       /* ④ 再挡 *0 / *1，绝不当成匹配 */

    return strcmp(got, salt) == 0;      /* 此时两边是两块不同的内存 */
}

① 是 snprintf 的溢出防护；② 是 shadow(5) 的 ! / * 语义；③ 是切断别名；④ 是 make_failure_token 对应的哨兵检查。少任何一条都有洞：只做 ③ 不做 ④，crypt() 返回 *0 时和 stored 的比较仍然是"两块不同内存"，能挡住，但如果 stored 本身就是 *0（某些工具留下的占位），strcmp("*0","*0")==0 又成立了。

五、成本：为什么 $1$ 必须淘汰

shadow(5) 与 passwd(5) 只规定格式，不规定强度。强度体现在每次验证要花多少 CPU —— 因为攻击者拿到盐之后只能逐词试（彩虹表被随机盐废掉了，但「同盐同口令必然同结果」这一点也说明盐只挡预计算，不挡字典）。

本节 c8_7 用 CLOCK_MONOTONIC 实测了单核吞吐（同一个口令换不同算法，各跑约 300 ms），详见下文代码段的输出。结论一句话：

MD5-crypt 比 SHA-512-crypt 便宜约 14 倍，比 bcrypt(cost=8) 便宜约 534 倍。

而且 $2b$（bcrypt）的 cost 是每 +1 翻一倍，所以 cost=12 又比 cost=8 慢 16 倍 —— 一千万词字典从「6.94 天」变成「110.97 天」。这就是「成本可调」的意义：同样的代码，在不同年代的机器上自动保持相同的破解难度。

crypt(3) ERRORS 里还有一条与部署相关的：

errno 含义
EINVAL "salt has the wrong format."
ENOSYS "The crypt() function was not implemented, probably because of U.S.A. export restrictions."
EPERM "/proc/sys/crypto/fips_enabled has a nonzero value, and an attempt was made to use a weak hashing type, such as DES."

/* c8_6_crypt_schemes.c —— 8.5：crypt() 的算法由盐决定
 *
 * 同一个口令配不同的盐，输出长度、前缀、算法全都不一样。
 * 盐不是「随机数」，它是「算法标识 + 轮数参数 + 随机前缀」的打包串。
 *
 * 编译：cc -Wall -Wextra -o c8_6_crypt_schemes c8_6_crypt_schemes.c -lcrypt
 */
#define _DEFAULT_SOURCE
#include <crypt.h>
#include <stdio.h>
#include <string.h>

/* 从密文前缀反推算法 —— 认证程序要干的第一件事 */
static const char *algo_of(const char *h)
{
    if (h == NULL)
        return "NULL（crypt 失败）";
    if (h[0] == '*')
        return "失败哨兵 *0 / *1";
    if (h[0] != '$')
        return "DES-crypt（13 字符、无前缀）";
    if (strncmp(h, "$1$", 3) == 0)
        return "MD5-crypt";
    if (strncmp(h, "$5$", 3) == 0)
        return "SHA-256-crypt";
    if (strncmp(h, "$6$", 3) == 0)
        return "SHA-512-crypt";
    if (strncmp(h, "$2", 2) == 0)
        return "bcrypt";
    if (strncmp(h, "$y$", 3) == 0)
        return "yescrypt";
    return "未知";
}

int main(void)
{
    const char *salt[] = {
        "ab",                            /* 经典 DES：2 字符盐 */
        "$1$abc",                        /* MD5 */
        "$5$abc",                        /* SHA-256，默认 5000 轮 */
        "$6$abc",                        /* SHA-512，默认 5000 轮 */
        "$6$rounds=1000$abc",            /* 显式指定轮数 */
        "$2b$08$abcdefghijklmnopqrstuv", /* bcrypt cost=8 */
        "$y$j9T$abcdefghij",             /* yescrypt（新发行版默认） */
    };

    for (size_t i = 0; i < sizeof salt / sizeof salt[0]; i++) {
        char *h = crypt("secret123", salt[i]);
        printf("\n盐 %-32s\n  密文 %s\n  长度 %zu  算法 %s\n",
               salt[i], h ? h : "NULL", h ? strlen(h) : 0, algo_of(h));
    }

    /* ---- 盐相同 → 结果必然相同（这就是不能只靠加密防彩虹表的原因） ---- */
    char d1[256], d2[256];
    snprintf(d1, sizeof d1, "%s", crypt("secret123", "$6$fixedsalt"));
    snprintf(d2, sizeof d2, "%s", crypt("secret123", "$6$fixedsalt"));
    printf("\n同一口令 + 同一盐两次：%s\n", strcmp(d1, d2) == 0 ? "完全相同" : "不同");

    snprintf(d1, sizeof d1, "%s", crypt("secret123", "$6$fixedsalt"));
    snprintf(d2, sizeof d2, "%s", crypt("secret123", "$6$otherslat"));
    printf("同一口令 + 不同盐：  %s\n", strcmp(d1, d2) == 0 ? "相同" : "不同");

    /* ---- DES 只吃口令的前 8 个字符 ---- */
    char e1[64], e2[64], e3[64];
    snprintf(e1, sizeof e1, "%s", crypt("12345678AAA", "ab"));
    snprintf(e2, sizeof e2, "%s", crypt("12345678ZZZ", "ab"));
    snprintf(e3, sizeof e3, "%s", crypt("1234567", "ab"));
    printf("\nDES \"12345678AAA\" -> %s\n", e1);
    printf("DES \"12345678ZZZ\" -> %s  %s\n", e2,
           strcmp(e1, e2) == 0 ? "（一模一样：第 9 个字符根本没进算法）" : "（不同）");
    printf("DES \"1234567\"     -> %s  %s\n", e3,
           strcmp(e1, e3) == 0 ? "（也一模一样：不足 8 字符按 0 补齐）" : "（不同）");

    /* ---- 锁定账号：密文以 ! 或 * 开头 ---- */
    puts("\n-- 锁定 / 禁用账号的哨兵 --");
    const char *lock[] = { "!", "!!", "*", "!$6$abc" };
    for (size_t i = 0; i < sizeof lock / sizeof lock[0]; i++) {
        char *h = crypt("anything", lock[i]);
        printf("stored=\"%-8s\" -> crypt() 返回 \"%s\"  %s\n", lock[i],
               h ? h : "NULL", algo_of(h));
    }
    puts("（*0 永远不可能等于 stored 的密文，所以认证必然失败 —— 这就是锁定的实现方式）");
    return 0;
}

-- 锁定 / 禁用账号的哨兵 --
stored="!       " -> crypt() 返回 "*0"  失败哨兵 *0 / *1
stored="!!      " -> crypt() 返回 "*0"  失败哨兵 *0 / *1
stored="*       " -> crypt() 返回 "*0"  失败哨兵 *0 / *1
stored="!$6$abc " -> crypt() 返回 "*0"  失败哨兵 *0 / *1
（*0 永远不可能等于 stored 的密文，所以认证必然失败 —— 这就是锁定的实现方式）

解读

  1. 密文长度是「格式自带」的，不是随机。13 / 29 / 50 / 93 / 105 —— 后四个都能用 $id$(3) + 盐(3) + $(1) + 固定摘要长（22 / 43 / 86 / 86）算出来，和 crypt(3) NOTES 里那句 "The size of this string is fixed" 完全一致。$6$rounds=1000$ 比 $6$ 多出的 12 字符，就是 rounds=1000$ 这 12 个字符本身（105 − 93 = 12），摘要长度没变。
  2. $y$（yescrypt）在本容器上直接失败，返回 *0。原因是 crypt(3) NOTES 那张 id 表只列了 1 / 2a / 5 / 6（glibc 的视角），而 $y$ 是 libxcrypt 新增的；本容器的 libxcrypt 构建没启用 yescrypt。这正好演示了「man 与实现不同源」：man 是 man-pages 项目的，实现是 libxcrypt 的，两者的能力集可以不重合。
  3. 注意这里的返回是 *0 而不是 NULL —— 与 man 的 "On error, NULL is returned" 不一致。所以认证代码必须同时处理 NULL 和 * 开头（第二节的 good_verify 就是按这个写的）。
  4. DES 那三行是本节最直观的一击："12345678AAA" 与 "12345678ZZZ" 密文完全相同，因为 DES-crypt 只看前 8 个字符。而 "1234567"（7 个字符）结果不同 —— 说明不足 8 字符是按 0 补齐，不是直接截断。这两个现象合起来能推出完整语义：取前 8 个字符，不足补 0，第 9 字符起丢弃。
  5. 「同一口令 + 同一盐两次：完全相同 / 不同盐：不同」这两行在说清盐的作用边界：盐不是密钥，它挡的是预计算（彩虹表），挡不住「拿到盐之后逐词试」。逐词试只能靠「每次验证更贵」拖，见 c8_7。
  6. 最后四行是锁定机制的实现原理：无论 stored 是 !、!!、* 还是 !$6$abc，crypt() 一律返回 *0。而 *0 这个 2 字符串永远不可能等于 stored 那串密文（长度都对不上），所以 strcmp 必然不等 → 认证必然失败。「锁定」不需要在 crypt() 里做任何特殊分支，它只是「让比较必然失败」。
  7. ⚠️ 但第 6 点有个前提：比较的两边必须是两块不同的内存。一旦 stored 就是 crypt() 的返回值（第三节那个别名陷阱），*0 会被就地改写成 *1，恒等成立 —— 同样的哨兵机制从「必然拒绝」翻转成「必然通过」。

c8_7 单核成本实测：把「安全强度」量化

完整程序见 ../code/c8_7_crypt_cost.c：各算法跑约 300 ms 数吞吐，再用同一次运行实测到的速率推算一千万词字典的耗时。

/* c8_7_crypt_cost.c —— 8.5：crypt() 的计算成本，就是离线爆破的成本
 *
 * 单核吞吐实测：同一个口令，换不同算法各跑 0.3 秒，换算成「次/秒」。
 * 第二张表由**同一次运行实测到的速率**推算（不是抄来的常数），
 * 回答「为什么 $1$（MD5）必须淘汰、为什么现代发行版默认 $y$」。
 *
 * 编译：cc -O2 -Wall -Wextra -o c8_7_crypt_cost c8_7_crypt_cost.c -lcrypt
 */
#define _DEFAULT_SOURCE
#include <crypt.h>
#include <stdio.h>
#include <time.h>

#define NSCHEME 4

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1000.0 + ts.tv_nsec / 1e6;
}

int main(void)
{
    const char *schemes[NSCHEME] = {
        "$1$abcdefgh",                   /* MD5-crypt */
        "$5$abcdefgh",                   /* SHA-256-crypt, 5000 轮 */
        "$6$abcdefgh",                   /* SHA-512-crypt, 5000 轮 */
        "$2b$08$abcdefghijklmnopqrstuv", /* bcrypt cost=8 */
    };
    const char *names[NSCHEME] = {
        "$1$（MD5-crypt）", "$5$（SHA-256-crypt）",
        "$6$（SHA-512-crypt）", "$2b$（bcrypt cost=8）",
    };
    double rate[NSCHEME];
    const double budget_ms = 300.0;
    const double wordlist = 1e7;         /* 一千万词的字典，只用于「换算」 */

    puts("算法                            口令数   总耗时      每次耗时     次/秒");
    for (int i = 0; i < NSCHEME; i++) {
        int n = 0;
        double t0 = now_ms();
        while (now_ms() - t0 < budget_ms) {
            crypt("benchmark-pw", schemes[i]);
            n++;
        }
        double dt = now_ms() - t0;
        rate[i] = n * 1000.0 / dt;
        printf("%-30s %-8d %8.1fms %10.1f us %9.0f\n",
               schemes[i], n, dt, dt * 1000.0 / n, rate[i]);
    }

    printf("\n把上面的速率换算成「跑完一千万词字典要多久」（单核，纯算术推算）：\n");
    for (int i = 0; i < NSCHEME; i++) {
        double sec = wordlist / rate[i];
        printf("  %-26s %8.0f 次/秒 -> %10.0f 秒 = %6.2f 小时 = %6.2f 天\n",
               names[i], rate[i], sec, sec / 3600, sec / 86400);
    }

    /* bcrypt 的特点是「成本可调」：每 +1 就翻一倍 */
    double bc12 = rate[3] / 16.0;
    double sec12 = wordlist / bc12;
    printf("  %-26s %8.2f 次/秒 -> %10.0f 秒 = %6.2f 小时 = %6.2f 天\n",
           "$2b$（bcrypt cost=12）", bc12, sec12, sec12 / 3600, sec12 / 86400);

    printf("\n结论：同一份口令字典，MD5-crypt 比 SHA-512-crypt 便宜约 %.0f 倍，\n",
           rate[0] / rate[2]);
    printf("      比 bcrypt(cost=8) 便宜约 %.0f 倍。加一个随机盐只挡预计算（彩虹表），\n",
           rate[0] / rate[3]);
    puts("      挡不住「拿到盐之后逐词试」—— 后者只能靠「每次验证更贵」来拖。");
    puts("      注意 $5$（SHA-256）在本容器上反而比 $6$（SHA-512）慢，");
    puts("      这是 libxcrypt 实现细节，别把「位数越大越慢」当成定律。");
    return 0;
}

解读

  1. $1$ 是 8910 次/秒。这个数字直接判了 MD5-crypt 的死刑：一千万词的字典 0.31 小时跑完，也就是半天不到就能试掉一部中等字典。而 /etc/shadow 是不是 0644（8.2 实测这台机器就是 0644）决定攻击者能不能开始 —— 权限和算法是两道独立的门。
  2. $5$（SHA-256）比 $6$（SHA-512）还慢（405 vs 656 次/秒）。这违反直觉，所以程序特意把它写成结论的一部分：$6$ 摘要更长却更快，是 libxcrypt 的具体实现所致（轮函数结构不同）。不要把「位数越大/摘要越长越慢」当定律 —— 强度只能实测，不能靠命名推。
  3. $2b$08 那一行只有 11 次、耗时 659 ms，超过了 300 ms 的预算。原因很直接：单次耗时 ≈ 60 ms，循环体每次执行后才检查时间，所以最后一次必然冲出去。这也说明 bcrypt 比两个 SHA 变种贵得多（60 ms vs 1.5–2.5 ms），这正是它作为口令哈希的设计目标。
  4. 第二张表是「纯算术推算」，程序里写得很清楚：用的是同一次运行实测到的 rate[]，不是抄来的常数。第一版曾经用手抄常数导致与本次实测不符（差近一倍），改成同批数据推算之后才自洽 —— 笔记里凡是有"换算"的地方，都要指明分子分母是不是同一次测量。
  5. $2b$ 的 cost 每 +1 翻倍：cost=12 = rate[3] / 16，于是从 6.94 天变成 110.97 天。这是 bcrypt/yescrypt 相对 MD5/SHA 家族的结构性优势 —— 可以用一个参数把成本跟着硬件一起涨，而 $1$/$5$/$6$ 只有 5000 轮这个几乎固定的值。

c8_8 三个 crypt() 陷阱（含一个真实的安全漏洞）

完整程序见 ../code/c8_8_crypt_traps.c：静态缓冲、*1 哨兵、以及「错误口令也认证通过」的复现，最后给出正确的 good_verify()。

/* c8_8_crypt_traps.c —— 8.5：crypt() 的三个坑，其中一个是安全漏洞
 *
 * 坑 1：crypt() 和 getpwnam() 一样返回静态缓冲 —— 前一次的结果会被后一次改写
 * 坑 2：把 crypt() 自己返回的指针当「盐」再喂回去，crypt() 会失败返回 "*1"
 * 坑 3：此时 strcmp(返回值, stored) 两边指向同一块内存 → 恒等 → 任何口令都"通过"
 *
 * 编译：cc -Wall -Wextra -o c8_8_crypt_traps c8_8_crypt_traps.c -lcrypt
 */
#define _DEFAULT_SOURCE
#include <crypt.h>
#include <stdio.h>
#include <string.h>

/* ❌ 看起来和原书 Listing 8-2 一模一样，但存的是 crypt() 自己的返回值时就废了 */
static int bad_verify(const char *password, const char *stored)
{
    return strcmp(crypt(password, stored), stored) == 0;
}

/* ✅ 正确写法：盐拷成副本、先挡锁定账号、再挡 *0 与 *1 这两个失败哨兵 */
static int good_verify(const char *password, const char *stored)
{
    char salt[256];

    if (password == NULL || stored == NULL)
        return 0;
    if (snprintf(salt, sizeof salt, "%s", stored) >= (int) sizeof salt)
        return 0;                       /* 密文长得离谱，直接拒绝 */
    if (salt[0] == '!' || salt[0] == '*')
        return 0;                       /* 锁定 / 无口令 */

    char *got = crypt(password, salt);
    if (got == NULL)
        return 0;
    if (got[0] == '*')
        return 0;                       /* crypt 失败（*0 / *1），绝不当成匹配 */

    return strcmp(got, salt) == 0;
}

int main(void)
{
    /* ---- 坑 1：静态缓冲 ---- */
    char *h1 = crypt("pw-one", "$6$saltAAAA");
    char keep1[256];
    snprintf(keep1, sizeof keep1, "%s", h1);    /* 先拷一份 */

    char *h2 = crypt("pw-two", "$6$saltBBBB");
    printf("h1=%p  h2=%p  (%s)\n", (void *) h1, (void *) h2,
           h1 == h2 ? "同一块内存" : "不同内存");
    printf("h1 现在指向的内容 = %.22s...\n", h1);
    printf("调用前拷下来的 keep1 = %.22s...\n", keep1);

    /* ---- 坑 2 + 坑 3：别名导致「任何口令都通过」 ---- */
    char *stored_ptr = crypt("secret123", "$6$rounds=5000$abc");
    char stored_copy[256];
    snprintf(stored_copy, sizeof stored_copy, "%s", stored_ptr);

    printf("\nstored_ptr（crypt 静态缓冲）= %.30s...\n", stored_ptr);
    printf("stored_copy（副本）          = %.30s...\n", stored_copy);

    printf("\n[❌ bad_verify] 直接把 crypt 的返回值当 stored\n");
    printf("bad_verify(\"definitely-wrong\", stored_ptr) = %d   <- 错口令本该返回 0\n",
           bad_verify("definitely-wrong", stored_ptr));
    printf("此刻 stored_ptr 的内容变成了 = %s\n", stored_ptr);

    printf("\n[✅ good_verify] 用副本，且检查哨兵\n");
    printf("good_verify(\"secret123\", stored_copy)        = %d\n",
           good_verify("secret123", stored_copy));
    printf("good_verify(\"definitely-wrong\", stored_copy) = %d\n",
           good_verify("definitely-wrong", stored_copy));
    printf("good_verify(\"x\", \"!\")   （锁定账号）          = %d\n",
           good_verify("x", "!"));
    printf("good_verify(\"x\", \"*\")   （无口令）            = %d\n",
           good_verify("x", "*"));

    puts("\n一句话：认证代码里绝不能把 crypt() 的返回值再当盐喂回去；");
    puts("        也不能只看 strcmp 的结果，必须先排除 *0/*1 与 !/* 这两类哨兵。");
    return 0;
}

实测输出（另在 Compiler Explorer 复核，gcc 13.3）：

此刻 stored_ptr 的内容变成了 = *1

一句话：认证代码里绝不能把 crypt() 的返回值再当盐喂回去；
        也不能只看 strcmp 的结果，必须先排除 *0/*1 与 !/* 这两类哨兵。

解读

  1. 前两行是坑 1 的证据：h1 == h2（0x7009aa8ea0e0）。而且注意 h1 现在指向的内容 已经变成 h2 那次的 SHA-512 结果（$6$saltBBBB$...），只有调用前拷下来的 keep1 还留着 $6$saltAAAA$...。crypt() 的返回值和 getpwnam() 一样是静态缓冲（crypt(3)："The return value points to static data whose content is overwritten by each call."）。
  2. bad_verify("definitely-wrong", stored_ptr) = 1 —— 错误口令返回了「通过」。这是功能级的安全漏洞，不是理论风险。和 8.4 里 getpwnam 的静态缓冲是同一个根因，但后果严重得多：那边是数据被改写，这边是认证被绕过。
  3. 此刻 stored_ptr 的内容变成了 = *1 这一行补上了因果链的最后一环：crypt() 检测到输入以 *0 开头，于是就地把这块内存写成了 *1（lib/util-make-failure-token.c 里 if (setting && setting[0] == '*' && setting[1] == '0') output[1] = '1';）。于是 strcmp 的两边指向同一块内存，恒等成立。 - 注意一个反直觉点：这里第一步的 *0 不是因为口令错，而是因为 stored 是别的密文时 crypt() 把它当成了盐，而它不是合法盐格式 → 返回 *0。也就是说漏洞的触发条件与口令内容无关，只看「stored 和 crypt() 返回值是否同一块内存」。
  4. good_verify 四行全对（1 / 0 / 0 / 0），其中后两行说明它也顺手挡住了 shadow(5) 的两种哨兵：!（锁定）和 *（无口令）。这是纵深防御：即使 stored 被污染成了 ! 或 *，也不会出现「比较两边恰好相等」。
  5. 一句话总结：「先拷贝再比较」和「先排除哨兵再比较」两件事都要做。只做前者，stored 是 *0（合法占位场景）时仍会 *0 == *0；只做后者，别名问题还在。

c8_9 把整章串成一条认证流水线

完整程序见 ../code/c8_9_auth_pipeline.c：原书 Listing 8-2 需要交互输入，跑不了自动化测试，所以这是它的可自动化等价物 —— 现算一份合成 shadow，再走 fgetspent() 读回来逐条验证。

/* c8_9_auth_pipeline.c —— 8.5：把整章串成一条可自动跑的认证流水线
 *
 * 原书 Listing 8-2 需要交互输入，无法在评测环境里跑；本程序是它的
 * 可自动化等价物：自己造一份合成 shadow，再走 getspnam()/fgetspent()
 * 把记录读回来，逐条验证候选口令。
 *
 * 编译：cc -Wall -Wextra -o c8_9_auth_pipeline c8_9_auth_pipeline.c -lcrypt
 */
#define _DEFAULT_SOURCE
#include <crypt.h>
#include <pwd.h>
#include <shadow.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

/* 安全版校验：副本作盐 + 排除锁定账号 + 排除 *0 与 *1 哨兵（同 c8_8_crypt_traps.c） */
static int verify(const char *password, const char *stored)
{
    char salt[256];

    if (password == NULL || stored == NULL)
        return 0;
    if (snprintf(salt, sizeof salt, "%s", stored) >= (int) sizeof salt)
        return 0;
    if (salt[0] == '!' || salt[0] == '*')
        return 0;

    char *got = crypt(password, salt);
    if (got == NULL || got[0] == '*')
        return 0;

    return strcmp(got, salt) == 0;
}

static int days_since_epoch(void)
{
    return (int) (time(NULL) / 86400);
}

int main(void)
{
    /* ---- 1. 造一份合成 shadow（alice 的密文现算） ---- */
    char alice_hash[256];
    snprintf(alice_hash, sizeof alice_hash, "%s", crypt("hunter2", "$6$tlpidemo$"));

    const char *sf = "/tmp/c8_shadow_pipeline";
    FILE *w = fopen(sf, "w");
    if (w == NULL) {
        perror("fopen for write");
        return 1;
    }
    fprintf(w, "alice:%s:%d:0:99999:7:14:21000\n", alice_hash, days_since_epoch());
    fputs("bob:!:19500:0:99999:7:::\n", w);         /* 锁定 */
    fputs("carol:*:19500:0:99999:7:::\n", w);       /* 无口令 */
    fclose(w);

    printf("今天距 1970-01-01 = %d 天\n", days_since_epoch());
    printf("alice 的密文（$6$ 前缀 = SHA-512-crypt）= %s\n\n", alice_hash);

    /* ---- 2. 走 shadow 查询路径读回来，逐条验证 ---- */
    struct { const char *user, *pw; } attempts[] = {
        { "alice", "hunter2" },     /* 正确 */
        { "alice", "Hunter2" },     /* 大小写不同 */
        { "alice", "" },            /* 空口令 */
        { "bob",   "hunter2" },     /* 账号被 ! 锁定 */
        { "carol", "hunter2" },     /* 账号被 * 禁用 */
    };

    FILE *f = fopen(sf, "r");
    struct spwd *sp;
    while (f != NULL && (sp = fgetspent(f)) != NULL) {
        int cnt = sp->sp_max;
        const char *policy = (cnt == 0 || cnt >= 99999)
                                 ? "永不过期（0 或 99999 都表示不检查）"
                                 : "有最长有效期";
        printf("账号 %-6s 密文前缀=%-4.4s 最长有效=%ld 天（%s）\n",
               sp->sp_namp, sp->sp_pwdp, sp->sp_max, policy);

        for (size_t i = 0; i < sizeof attempts / sizeof attempts[0]; i++) {
            if (strcmp(attempts[i].user, sp->sp_namp) != 0)
                continue;
            printf("   口令 \"%s\" -> %s\n", attempts[i].pw,
                   verify(attempts[i].pw, sp->sp_pwdp) ? "✅ 认证通过" : "❌ 拒绝");
        }
    }
    if (f != NULL)
        fclose(f);

    /* ---- 3. 真实环境对照：本容器以 root 运行，能读到真的 shadow ---- */
    puts("\n-- 真实 shadow（本容器） --");
    struct passwd *pw = getpwnam("ce");
    if (pw == NULL) {
        puts("getpwnam(\"ce\") 失败，跳过");
        return 0;
    }
    struct spwd *real = getspnam(pw->pw_name);
    if (real == NULL) {
        printf("getspnam(\"%s\") = NULL —— 普通用户读 shadow 会 errno=EACCES\n",
               pw->pw_name);
    } else {
        printf("%s 的密文 = %s\n", real->sp_namp, real->sp_pwdp);
        printf("前缀 $1$ = MD5-crypt。它的验证速度比 $6$ 快一个数量级（见 c8_7_crypt_cost.c\n");
        printf("里的同机实测表），所以这种哈希在字典攻击面前最脆弱 ——\n");
        printf("这正是现代发行版把默认算法换成 $6$/$y$ 的原因。\n");
        printf("账号未锁定：%s\n", verify("wrong-password", real->sp_pwdp) ? "错误口令也通过了（！）"
                                                                          : "错误口令被正确拒绝");
    }
    return 0;
}

解读

  1. alice 的密文是现算的：crypt("hunter2", "$6$tlpidemo$")。所以那串 $6$tlpidemo$SHcfts... 可以被任何人在任何机器上复现（盐是固定的 tlpidemo）—— 这也顺便印证了「同盐同口令必然同结果」，即「盐不等于密钥」。
  2. "hunter2" 通过、"Hunter2" 拒绝、"" 拒绝。第三行值得注意：空口令不是"跳过验证"，它会走完整的 crypt("", salt) 再比较 —— 因为 alice 的密文不是空串，必然不相等。反过来说，如果 shadow 里那格是空的（shadow(5)："the user can log in without a password"），结论就完全相反。空口令的安全性完全取决于文件里那一格，不取决于认证代码。
  3. bob（! 锁定）和 carol（* 无口令）都被拒绝，走的是 good_verify 里的哨兵检查（第 ② 步），根本不需要调用 crypt()。这比"算了再比"更快也更安全。
  4. 最长有效=99999 天 是程序对 sp_max 的解读。注意这句注释里的坑：「0 或 99999 都表示不检查」。而 8.2 说过空字段读回来是 -1 —— 三种取值（-1 / 0 / 99999）语义各不相同，程序里只处理了后两种，属于有意简化，生产代码不能这么写。
  5. 最后一段是真实环境对照：ce 的密文是 $1$rockyou$hty8SH9lK4mcCQXKENxaa1。盐被起名叫 rockyou（经典口令字典名）基本等于明示「这份哈希是拿字典跑出来的」，而 $1$（MD5-crypt）在本容器上是 8910 次/秒（c8_7）。「格式合法」和「安全」是两件事：这行输出就是最好的例子。
  6. 注意程序里 verify("wrong-password", real->sp_pwdp) 返回 0，打印「错误口令被正确拒绝」—— 说明 ce 没有被锁定，$1$... 是真实可验证的密文，不是 ! 占位。

HFT / 嵌入式关联

  • 认证路径上不要用 crypt() 家族。想自建校验，用 libsodium 的 crypto_pwhash（Argon2id）或至少 crypt_r() + yescrypt/bcrypt。crypt() 的接口契约本身就容易用错（静态缓冲 + *0/*1），错误代价是整个认证被绕过。
  • $1$ 一律当"已经泄露"处理。8910 次/秒意味着 8 位以内的小写字母+数字口令能在小时级被穷举。迁移方案是 authconfig / pam_unix 的 sha512（或 yescrypt）配合下次登录时重算密文，而不是全量重置口令。
  • 空口令那格是运维红线：shadow(5) 明说空串允许无口令登录，passwd(5) 说 /etc/passwd 里空串也一样。CI 里加一条断言扫 /etc/shadow / /etc/passwd 第 2 字段是否为空，成本很低，拦住的是一类极严重的配置事故。
  • FIPS 环境：开了 /proc/sys/crypto/fips_enabled 之后 DES-crypt 直接 EPERM（crypt(3) ERRORS）。老系统升级到 FIPS 模式时，/etc/shadow 里的 $1$ 甚至无前缀的密文会导致所有登录失败，而错误信息只是「口令错」。迁移前先统计算法分布。
  • 嵌入式：BusyBox 的 crypt 支持面比 libxcrypt 小得多（常见只有 DES 和 MD5）。在交叉编译环境里用 $6$ 生成的密文，到板上可能直接 *0。要么板上也用同一套 libxcrypt，要么统一算法，别在构建机和目标机之间赌兼容性。
  • 成本参数要跟着硬件走。bcrypt 的 cost / yescrypt 的 N/r/p 应该按「单次验证 ≈ 50–100 ms」来定；本容器实测 bcrypt cost=8 已经 ~60 ms，cost=12 就是 ~960 ms —— 在同一台机器上给登录接口加 1 秒延迟，用户是能感觉到的。安全参数和体验参数是同一个旋钮。
  • getpass() 只能算"够用"。它返回静态缓冲（原书那段清零 for 循环就是在处理这个），且不处理超长输入。生产代码用 readpassphrase() 或 termios 自己关回显。

自测题

1. 现代 glibc（≥ 2.28）上编译用 crypt() 的程序，该写哪个 feature test macro？

_DEFAULT_SOURCE。

crypt(3) 的 Feature Test Macro 原文：

crypt(): Since glibc 2.28: _DEFAULT_SOURCE glibc 2.27 and earlier: _XOPEN_SOURCE

网上大量示例（以及 TLPI 原书 Listing 8-2）写的是 _XOPEN_SOURCE，那是 ≤ 2.27 的要求。在 glibc ≥ 2.28 上虽然还能编过，但已经不是推荐写法。

另外两件容易漏的：

  • glibc 2.39 已经不带 crypt() 实现，改成依赖 libxcrypt（crypt(3) LIBRARY 段写的是 "Password hashing library (libcrypt, -lcrypt)"）。所以必须链 -lcrypt，并且要 #include <crypt.h> 拿原型 —— crypt(3) HISTORY 段明确要求「检测 _XOPEN_CRYPT 不可用时改用 <crypt.h>」。
  • crypt_r() 要的是 _GNU_SOURCE，比 crypt() 的宏更严格。
2. crypt() 失败时一定返回 NULL 吗？

不一定 —— 本容器实测返回的是字符串 *0。

crypt(3) RETURN VALUE 确实写着 "On error, NULL is returned"，但那是 man-pages 项目的描述，实际实现是 libxcrypt。libxcrypt 4.4.36 lib/util-make-failure-token.c 里：

output[0] = '*';
output[1] = '0';
output[2] = '\0';

if (setting && setting[0] == '*' && setting[1] == '0')
    output[1] = '1';

本节 c8_6 的实测印证了这一点：$y$（本容器的 libxcrypt 没启用 yescrypt）那一行返回 密文 *0、长度 2，不是 NULL。

所以认证代码的正确形态是三种都挡：

char *got = crypt(password, salt);
if (got == NULL)    return 0;   /* man 说的那种失败 */
if (got[0] == '*')  return 0;   /* 实测到的 *0 / *1 */

只看 NULL 会在 libxcrypt 上放过 *0，而 *0 一旦和同样是 *0 的 stored 比较就成立了。

3. 这段代码有什么问题？return strcmp(crypt(password, stored), stored) == 0;

它会在特定条件下让任何口令都通过。

这是本节 c8_8 复现的漏洞。触发条件不是「口令错」，而是 stored 与 crypt() 的返回值是同一块内存（crypt() 返回静态缓冲）：

  1. crypt(password, stored) 把 stored 当盐。如果它不是合法盐格式（比如它本身是另一串 $6$... 之外的产物），libxcrypt 返回 *0，并就地覆写那块静态缓冲；
  2. 但在此之前，如果静态缓冲里本来就存着 *0，make_failure_token 会返回 *1（if (setting[0]=='*' && setting[1]=='0') output[1]='1';）；
  3. strcmp(返回的指针, stored) —— 两边指向同一块内存，strcmp(x, x) == 0 恒真 → 返回 1。

实测：bad_verify("definitely-wrong", stored_ptr) = 1（本该是 0），且随后 stored_ptr 的内容打印为 *1。

正确写法要同时做四件事（good_verify）： 1. 用 snprintf 把 stored 拷成副本再当盐（切断别名）； 2. 先挡 ! / * 开头（shadow(5) 的锁定 / 无口令语义）； 3. got == NULL 判失败； 4. got[0] == '*' 判失败（*0 / *1 绝不能当成匹配）。

4. $5$（SHA-256）和 $6$（SHA-512）哪个更慢？

按本容器实测：$5$ 更慢，而且是明显更慢。

$5$abcdefgh                    122         301.5ms     2471.6 us       405
$6$abcdefgh                    197         300.4ms     1525.1 us       656

$5$ 405 次/秒，$6$ 656 次/秒 —— 摘要更长的 $6$ 反而快约 60%。这是 libxcrypt 的具体实现差异（SHA-256 与 SHA-512 的轮函数结构、以及 libxcrypt 对两者的展开方式不同），不是「位数越大越慢」的反例那么简单。

启示有两条：

  • 强度只能实测，不能靠命名或长度推。文档里能确定的只有格式（摘要 43 vs 86 字符）和默认轮数（都是 5000）。
  • 但这也不构成"选 $5$ 更好"：$6$ 更快意味着攻击者也更快，同时它的摘要更长、抗碰撞余量更大。选型看的是「验证成本」这个可调量（轮数 / bcrypt cost），而不是摘要长度。
5. 为什么原书 Listing 8-2 要写 pwd->pw_passwd = spwd->sp_pwdp; 这一句？

因为不写就会拿到占位符 "x"，crypt() 必然失败。

getpwnam() 返回的 struct passwd.pw_passwd 来自 /etc/passwd 的第 2 字段。在用了 shadow 的系统上那格是 x（passwd(5)："This is either the encrypted user password, an asterisk (*), or the letter 'x'."），真密文在 /etc/shadow 的 sp_pwdp。

8.1 的实测直接给出了这个值：pw_passwd=x。

原书那句的上下文是：

spwd = getspnam(username);
if (spwd == NULL && errno == EACCES)
    fatal("no permission to read shadow password file");

if (spwd != NULL)                                /* If there is a shadow password record */
    pwd->pw_passwd = spwd->sp_pwdp;              /* Use the shadow password */

三个细节：

  1. 是 pwd->pw_passwd = ...，不是修改 spwd —— 往 struct passwd 里塞密文，后面 crypt(password, pwd->pw_passwd) 才拿到正确的盐。这也顺便绕开了「getpwnam 和 getspnam 各自有静态缓冲」的问题，因为之后只用一个指针。
  2. spwd == NULL 且 errno == EACCES 才是「没权限读 shadow」；其他情况（比如用户根本没有 shadow 记录）不算致命，代码会继续用 /etc/passwd 里那一格。这个区分对应 getspnam(3) ERRORS 的 EACCES 条目。
  3. 本容器的 shadow 是 0644（8.2），所以以 root 跑时 getspnam 一定成功 —— 这条 EACCES 分支在评测环境里走不到。这提醒我们：能跑通不等于分支被覆盖过。

易错清单

本批全部有实测支撑：

  1. /etc/passwd 是 644 不是"配置不严"，是设计使然（ls -l 要翻译 uid）；反过来 /etc/shadow 是 644 就是确凿错误。
  2. pw_passwd 是占位符 x，拿它直接 crypt() 会得到 *0。认证前必须用 sp_pwdp 覆盖。
  3. 非 _r 版本返回静态缓冲，getpwent / getpwnam / getpwuid 共用同一块；「读一批存数组」直接是 bug。
  4. 地址不可假设：fgetpwent 连续三次同址，但 getpwnam 与 getpwuid 查同一用户却不同址。
  5. 空数字字段 = -1（不是 0）；sp_max == 0 与 sp_max < 0 语义完全不同。
  6. 空组的 gr_mem 不是 NULL，而是首元素为 NULL 的数组。写 if (gr->gr_mem != NULL) 会走错分支。
  7. errno 范式有条件：后端起不开时（/etc/group 不存在）errno 会是 ENOENT，无法与「真的出错」区分。man 明确列了 0 / ENOENT / EBADF / ESRCH / EPERM 都可能。
  8. _r 版「不存在」= s == 0 且 *result == NULL，只看 s 不够；且 _r 不动 errno。
  9. crypt() 失败可能返回 *0 而不是 NULL（libxcrypt），必须同时处理；crypt() 的返回值绝不能当盐再喂回去（会得到 *1，导致任何口令"通过"）。
  10. userIdFromName("1000") 不查库；失败返回 (uid_t)-1（打印为 4294967295），而 groupNameFromId 失败返回 NULL —— 两个方向约定不同。
  11. DES 只吃口令前 8 字符（不足补 0），盐只有 2 字符 / 4096 种 —— 这两个限制合起来判了 DES-crypt 的死刑。
  12. 本章不涉及 RUID/EUID/SUID 与 setuid() —— 那是 Ch9；附属组的 API（getgroups/setgroups）也不在本章，在 Ch9 §9.6。
  13. glibc ≥ 2.28 用 _DEFAULT_SOURCE，不是老教程里的 _XOPEN_SOURCE；glibc 2.39 本身不带 crypt()，靠 libxcrypt，要链 -lcrypt。

自测题

1. 为什么引入 /etc/shadow？

因为 /etc/passwd 必须全局可读。

passwd(5) 原文："It should have read permission allowed for all users (many utilities, like ls(1) use it to map user IDs to usernames), but write access only for the superuser." —— ls -l 要把 uid 显示成名字，映射表就得人人可读。

于是：

  1. 安全：密文如果留在 /etc/passwd，任何用户都能拿到哈希做离线字典攻击（本容器 $1$ 单核 8910 次/秒）。
  2. 策略：shadow 多了有效期/警告/宽限/锁定等字段（9 个字段），passwd 的 7 个字段表达不了。
  3. 历史：passwd(5) 自己回顾了原因 —— "In the good old days ... the hardware was too slow to crack a well-chosen password ... These days many people run some version of the shadow password suite, where /etc/passwd has an 'x' character in the password field, and the encrypted passwords are in /etc/shadow, which is readable by the superuser only."

详细推导见 8.1 与 8.2。

2. getpwuid() 返回的指针需要 free 吗？能存起来吗？

不需要 free，也绝对不能存。

getpwnam(3) RETURN VALUE："The return value may point to a static area, and may be overwritten by subsequent calls to getpwent(3), getpwnam(), or getpwuid(). (Do not pass the returned pointer to free(3).)"

实测证据（8.4 c8_4）：fgetpwent() 三次返回同一个地址 0x7da0e6211240，而且用第 1 个指针 p1 去读，读到的是第 2 条记录的 "bob"。

坑比"同一个指针"更深一层：struct passwd 里的 char * 字段也指向同一块静态内存，所以即使按值拷贝结构体，里面的指针仍会被下一次调用改掉。

要留住内容：立刻 strdup 需要的字段，或者改用 getpwnam_r()（多线程下也是必须的）。

3. 附属组（supplementary groups）怎么查？

文件侧：附属组是 /etc/group 第 4 字段 user_list 里的名字列表（group(5)："a list of the usernames that are members of this group, separated by commas"）。一个用户可以出现在多行。主组则是 /etc/passwd 第 4 字段，每人恰好一个。

但「这个进程此刻持有哪些组」不是文件能回答的 —— 那是进程凭证。要问内核：

#include <grp.h>
int n = getgroups(0, NULL);         /* 先问有几个 */
gid_t list[n];
getgroups(n, list);                 /* 再取出来 */

推进凭证的是 setgroups()（特权操作）和 initgroups()（按 /etc/group 把用户的全部组一次装好）。

⚠️ 这套 API 属于 Ch9 §9.6 附属组 ID，本章只讲文件侧。另外 group(5) 的 BUGS 段提醒：文件里的名单常年过期，判断"用户是否在某组"要以 getgroups() 的输出为准。

4. 认证代码里比较密文时，最容易犯的两个错是什么？

① 把 crypt() 的返回值当盐再喂回去；② 只判 NULL 不判 *0 / *1。

第 ① 个会造出真实漏洞（8.5 c8_8 实测）：

/* ❌ 错口令 bad_verify("definitely-wrong", stored_ptr) 返回 1 —— 认证被绕过 */
return strcmp(crypt(password, stored), stored) == 0;

链条：crypt() 返回静态缓冲 → 本次调用把 stored 当盐、盐非法 → 返回 *0 → 但若这块内存里原本就是 *0，libxcrypt 返回 *1 并就地覆写 → strcmp 两边同一块内存 → 恒等成立。

第 ② 个：crypt(3) 的 man 说 "On error, NULL is returned"，但实测（libxcrypt）返回的是字符串 *0。

正确的 verify 要四步俱全：

if (password == NULL || stored == NULL) return 0;                 /* 空指针 */
if (snprintf(salt, sizeof salt, "%s", stored) >= (int) sizeof salt) return 0;  /* 超长 */
if (salt[0] == '!' || salt[0] == '*') return 0;                   /* 锁定 / 无口令 */
char *got = crypt(password, salt);                                /* 用副本作盐 */
if (got == NULL) return 0;                                        /* man 的失败 */
if (got[0] == '*') return 0;                                      /* 实测的 *0 / *1 */
return strcmp(got, salt) == 0;

练习 1：UID → 用户信息（含三类失败的分辨）

编写程序，接受一个 UID 参数，打印用户名、主组名和该进程当前持有的附属组数量。要求：

  • 使用 getpwuid() 查用户信息；
  • 使用 getgrgid() 查主组名；
  • /etc/group 里查不到该 GID 时，程序不能当成"失败"退出；
  • UID 在 /etc/passwd 里没有记录时，同样不能当成"失败"退出。

提示：本节真正要练的不是 API 调用，而是把三种情况分开——① 记录不存在（不是错误）；② 组数据库不可用（也不是"这条不存在"）；③ 真正的系统错误。

参考实现

完整代码见 ../code/ex8_1_uid_info.c：

/* ex8_1_uid_info.c —— Ch08 自测题 1 参考实现
 *
 * 给定一个 UID，打印：用户名、主组名、以及该进程当前持有的附属组。
 *
 * 关键点在于「三种失败要分开」：
 *   - UID 在 /etc/passwd 里没有记录  -> getpwuid 返回 NULL，errno 不变
 *   - /etc/group 里没有该 GID        -> getgrgid 返回 NULL，errno 不变
 *   - 真正的系统错误                 -> errno 被设成非 0
 * 把第一种当成「失败」退出是本类程序最常见的 bug。
 *
 * 编译：cc -Wall -Wextra -o ex8_1_uid_info ex8_1_uid_info.c
 * 运行：./ex8_1_uid_info [uid]        （不带参数则查当前进程的 uid）
 */
#define _DEFAULT_SOURCE
#include <errno.h>
#include <grp.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[])
{
    uid_t uid = (argc > 1) ? (uid_t) strtol(argv[1], NULL, 10) : getuid();

    /* ---- 第 1 步：查用户（errno 必须自己清零） ---- */
    errno = 0;
    struct passwd *pw = getpwuid(uid);
    if (pw == NULL) {
        if (errno == 0) {
            printf("UID %ld：/etc/passwd 里没有这条记录（这不算出错）\n",
                   (long) uid);
        } else {
            perror("getpwuid");
        }
        return 0;       /* 「查不到」不是程序失败，正常退出 */
    }

    printf("UID %ld -> 用户名 %s\n", (long) uid, pw->pw_name);
    printf("            注释   %s\n", pw->pw_gecos);
    printf("            家目录 %s\n", pw->pw_dir);
    printf("            壳     %s\n", pw->pw_shell);

    /* ---- 第 2 步：主组。来自 passwd 的 gid 字段 ---- */
    errno = 0;
    struct group *gr = getgrgid(pw->pw_gid);
    if (gr != NULL)
        printf("主组   %s(%ld)\n", gr->gr_name, (long) gr->gr_gid);
    else
        printf("主组   (%ld) —— /etc/group 里查不到该 GID（errno=%d）\n",
               (long) pw->pw_gid, errno);

    /* ---- 第 3 步：附属组。来自进程凭证，与上面的文件无关 ---- */
    int n = getgroups(0, NULL);
    if (n < 0) {
        perror("getgroups");
        return 1;
    }

    printf("附属组 %d 个", n);
    if (n > 0) {
        gid_t *gs = malloc((size_t) n * sizeof(gid_t));
        if (gs == NULL) {
            perror("malloc");
            return 1;
        }
        if (getgroups(n, gs) != n) {    /* 两次调用之间组数可能变，以第二次为准 */
            perror("getgroups");
            free(gs);
            return 1;
        }
        for (int i = 0; i < n; i++) {
            struct group *g = getgrgid(gs[i]);      /* 结果立即用掉，不留指针 */
            if (g != NULL)
                printf(" %s(%ld)", g->gr_name, (long) gs[i]);
            else
                printf(" ?(%ld)", (long) gs[i]);
        }
        free(gs);
    }
    putchar('\n');

    printf("主组 %ld 是否也在附属组里：%s\n", (long) pw->pw_gid,
           (n > 0) ? "看上面列表（内核不保证互斥）" : "列表为空，无从判断");
    puts("注：附属组由进程凭证携带，内核对它一无所知地放在 /etc/passwd 里 ——");
    puts("    真正把它塞进凭证的是 setgroups() / initgroups()，属 Ch9 §9.6。");
    return 0;
}

UID 0：/etc/passwd 里没有这条记录（这不算出错）

解读

  1. UID 0 那一次是本题的核心考点：进程自身 uid=0，但 /etc/passwd 里只有 ce(10240)，getpwuid(0) 返回 NULL 且 errno=0。程序打印一句人话后 return 0 —— 「查不到」不是程序失败。任何把这种情况当错误退出的实现，在精简容器里都会立刻翻车。
  2. 主组 (10240) —— /etc/group 里查不到该 GID（errno=2）：注意这里 errno 不是 0，而是 ENOENT。原因是 /etc/group 这个文件本身不存在，open() 留下的 errno 透传了出来（机制见 8.3 第五节）。所以本题的正确做法是：只要 getgrgid 返回 NULL 就按「没有这个组」处理，把 errno 打进日志而不是拿它做分支判断。
  3. 附属组 1 个 ?(0) —— 这个结果很有意思：getgroups(0, NULL) 返回 1，那一个附属组的 GID 是 0；而 getgrgid(0) 同样翻不出名字（没有 /etc/group），所以显示 ?。这说明附属组来自进程凭证，与 /etc/group 无关 —— 文件里没记录，进程依然持有它。
  4. 最后两行注释是给读者的定位指引：附属组的 API 属于 Ch9 §9.6，本节只是"顺手看一眼"，不作展开。
  5. 程序里 free(gs) 之前的所有 getgrgid() 结果都是立即使用的 —— 因为在 free 之后，那些 struct group * 指向的静态缓冲随时可能被下一次调用改写（8.4）。

练习 2：/etc/shadow 的必要性

解释为什么 /etc/shadow 的引入是必要的。如果没有 shadow 文件，会带来什么安全问题？

参考答案

没有 shadow 时：

  1. /etc/passwd 必须全局可读 —— passwd(5)："It should have read permission allowed for all users (many utilities, like ls(1) use it to map user IDs to usernames), but write access only for the superuser."。ls -l 要把 uid 显示成名字，映射表就躲不开人人可读。
  2. 密文因此落在任何用户都能读的文件里 → 可以离线做字典 / 彩虹表攻击。攻击者不需要任何权限，也不受登录失败次数限制。
  3. 无法表达口令生命周期策略。passwd(5) 只有 7 个字段，没有"上次修改日期""最长有效天数""过期前警告""账号过期日"的位置 —— 这正是 shadow(5) 需要有 9 个字段的原因。
  4. passwd(5) 自己回顾了历史："In the good old days there was no great problem with this general read permission. Everybody could read the encrypted passwords, but the hardware was too slow to crack a well-chosen password, and moreover the basic assumption used to be that of a friendly user-community." —— 随着 CPU 变快、社区变大，这个假设两边都塌了。

shadow 之后：

  1. 哈希只对 root（以及 shadow 组成员）可读。shadow(5)："This file must not be readable by regular users if password security is to be maintained." —— 注意这是命令式的要求，不是"建议"。
  2. 策略字段齐备（第 3–8 字段）。
  3. 即便 /etc/passwd 被读到，也只是用户名和 uid，没有可爆破的目标。

⚠️ 但要注意一个常见误解：本容器（以及很多容器镜像）的 /etc/shadow 是 0644（8.2 实测）。这种情况下「引入 shadow」的安全收益是零 —— 只是把密文从一个全局可读的文件搬到了另一个全局可读的文件。所以正确的表述是：shadow 的安全性来自「权限位」，不是来自「文件叫什么名字」。

练习 3：遍历所有用户

编写程序遍历 /etc/passwd，打印所有用户的 UID 和用户名。

参考答案

8.4 已经实测过原书配套程序 t_getpwent.c（输出只有一行 ce 10240，因为该文件只有 1 条记录；见 8.4）。在它基础上加一个过滤条件即可：

/* 在 t_getpwent.c 的基础上加一个 uid 过滤（原书的 while 循环一字未改） */
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[])
{
    uid_t floor = (argc > 1) ? (uid_t) strtol(argv[1], NULL, 10) : 0;
    struct passwd *pwd;

    while ((pwd = getpwent()) != NULL) {          /* 原书原样 */
        if (pwd->pw_uid < floor)
            continue;                              /* 常见的"只看普通用户"过滤 */
        printf("%-8s %5ld\n", pwd->pw_name, (long) pwd->pw_uid);   /* 原书原样 */
    }
    endpwent();
    exit(EXIT_SUCCESS);
}

这段没有单独实跑（它只是给已实测的 t_getpwent.c 加了一个 if），所以不带实测输出。要真跑，把 t_getpwent.c 的 main 换成上面这段即可。

要点

  1. getpwent() 是"顺序遍历"，必须配对 endpwent()（getpwent(3)：遍历完应调用 endpwent() 以释放资源）。忘了它 = 一直持有一个打开的 FILE *。
  2. 不要用循环里的 getpwnam() 代替 getpwent()。getpwnam() 每次调用都要重新 fopen + 从文件头线性扫描（nss/files-XXX.c 的 DB_LOOKUP 宏）；getpwent() 保持流打开，是唯一适合"扫全表"的接口。
  3. pwd->pw_name 不能存。它指向静态缓冲，下一次 getpwent() 就会把它改写。要留着就必须 strdup。
  4. %-8s %5ld 这个格式来自原书，不是随手排的：名字左对齐 8 列、uid 右对齐 5 列。跟原书输出对齐时别改它。
  5. 「只看普通用户」的常见判据是 pw_uid >= 1000（或 >/etc/login.defs 里的 UID_MIN）。但这是发行版约定，不是内核或 libc 的约定 —— 为了可移植性，最好从 login.defs 读，或者干脆别过滤。

练习 4：复现并修复 crypt() 的别名漏洞

下面的认证函数「看起来和教科书一样」，但它有一个可被利用的漏洞。请说明漏洞的触发条件、复现它，并写出安全版本。

static int verify(const char *password, const char *stored)
{
    return strcmp(crypt(password, stored), stored) == 0;
}

参考答案（含实测复现）

触发条件不是"口令错"，而是「stored 与 crypt() 的返回值是同一块内存」。

完整复现程序见 ../code/c8_8_crypt_traps.c：

/* c8_8_crypt_traps.c —— 8.5：crypt() 的三个坑，其中一个是安全漏洞
 *
 * 坑 1：crypt() 和 getpwnam() 一样返回静态缓冲 —— 前一次的结果会被后一次改写
 * 坑 2：把 crypt() 自己返回的指针当「盐」再喂回去，crypt() 会失败返回 "*1"
 * 坑 3：此时 strcmp(返回值, stored) 两边指向同一块内存 → 恒等 → 任何口令都"通过"
 *
 * 编译：cc -Wall -Wextra -o c8_8_crypt_traps c8_8_crypt_traps.c -lcrypt
 */
#define _DEFAULT_SOURCE
#include <crypt.h>
#include <stdio.h>
#include <string.h>

/* ❌ 看起来和原书 Listing 8-2 一模一样，但存的是 crypt() 自己的返回值时就废了 */
static int bad_verify(const char *password, const char *stored)
{
    return strcmp(crypt(password, stored), stored) == 0;
}

/* ✅ 正确写法：盐拷成副本、先挡锁定账号、再挡 *0 与 *1 这两个失败哨兵 */
static int good_verify(const char *password, const char *stored)
{
    char salt[256];

    if (password == NULL || stored == NULL)
        return 0;
    if (snprintf(salt, sizeof salt, "%s", stored) >= (int) sizeof salt)
        return 0;                       /* 密文长得离谱，直接拒绝 */
    if (salt[0] == '!' || salt[0] == '*')
        return 0;                       /* 锁定 / 无口令 */

    char *got = crypt(password, salt);
    if (got == NULL)
        return 0;
    if (got[0] == '*')
        return 0;                       /* crypt 失败（*0 / *1），绝不当成匹配 */

    return strcmp(got, salt) == 0;
}

int main(void)
{
    /* ---- 坑 1：静态缓冲 ---- */
    char *h1 = crypt("pw-one", "$6$saltAAAA");
    char keep1[256];
    snprintf(keep1, sizeof keep1, "%s", h1);    /* 先拷一份 */

    char *h2 = crypt("pw-two", "$6$saltBBBB");
    printf("h1=%p  h2=%p  (%s)\n", (void *) h1, (void *) h2,
           h1 == h2 ? "同一块内存" : "不同内存");
    printf("h1 现在指向的内容 = %.22s...\n", h1);
    printf("调用前拷下来的 keep1 = %.22s...\n", keep1);

    /* ---- 坑 2 + 坑 3：别名导致「任何口令都通过」 ---- */
    char *stored_ptr = crypt("secret123", "$6$rounds=5000$abc");
    char stored_copy[256];
    snprintf(stored_copy, sizeof stored_copy, "%s", stored_ptr);

    printf("\nstored_ptr（crypt 静态缓冲）= %.30s...\n", stored_ptr);
    printf("stored_copy（副本）          = %.30s...\n", stored_copy);

    printf("\n[❌ bad_verify] 直接把 crypt 的返回值当 stored\n");
    printf("bad_verify(\"definitely-wrong\", stored_ptr) = %d   <- 错口令本该返回 0\n",
           bad_verify("definitely-wrong", stored_ptr));
    printf("此刻 stored_ptr 的内容变成了 = %s\n", stored_ptr);

    printf("\n[✅ good_verify] 用副本，且检查哨兵\n");
    printf("good_verify(\"secret123\", stored_copy)        = %d\n",
           good_verify("secret123", stored_copy));
    printf("good_verify(\"definitely-wrong\", stored_copy) = %d\n",
           good_verify("definitely-wrong", stored_copy));
    printf("good_verify(\"x\", \"!\")   （锁定账号）          = %d\n",
           good_verify("x", "!"));
    printf("good_verify(\"x\", \"*\")   （无口令）            = %d\n",
           good_verify("x", "*"));

    puts("\n一句话：认证代码里绝不能把 crypt() 的返回值再当盐喂回去；");
    puts("        也不能只看 strcmp 的结果，必须先排除 *0/*1 与 !/* 这两类哨兵。");
    return 0;
}

失效链条（bad_verify("definitely-wrong", stored_ptr) = 1 是怎么来的）：

  1. crypt() 的返回值指向静态缓冲（crypt(3)："The return value points to static data whose content is overwritten by each call."），而 stored_ptr 恰好就是上一次 crypt() 的返回值 → 两者是同一块内存；
  2. 本次调用把 stored_ptr 当盐，但它不是合法盐格式 → libxcrypt 返回失败哨兵 *0，并就地覆写那块缓冲；
  3. 若那块内存里原本就是 *0，libxcrypt 的 make_failure_token() 会返回 *1（源码：if (setting && setting[0] == '*' && setting[1] == '0') output[1] = '1';）；
  4. strcmp(返回的指针, stored) —— 两边指向同一块内存，strcmp(x, x) == 0 恒真 → 返回 1。

实测第 4 行 此刻 stored_ptr 的内容变成了 = *1 补上了最后一环。

安全版本必须四步俱全：

static int good_verify(const char *password, const char *stored)
{
    char salt[256];

    if (password == NULL || stored == NULL)
        return 0;
    if (snprintf(salt, sizeof salt, "%s", stored) >= (int) sizeof salt)
        return 0;                       /* ① 密文长得离谱，拒绝 */
    if (salt[0] == '!' || salt[0] == '*')
        return 0;                       /* ② 先挡锁定 / 无口令 */

    char *got = crypt(password, salt);  /* ③ 用副本作盐，切断别名 */
    if (got == NULL)
        return 0;                       /* man 所述的失败 */
    if (got[0] == '*')
        return 0;                       /* ④ 再挡 *0 / *1 */

    return strcmp(got, salt) == 0;      /* 此时两边是两块不同的内存 */
}

实测四行结果：1 / 0 / 0 / 0 —— 正确口令通过，错口令、锁定账号、无口令账号全部拒绝。

延伸

这道题背后是三个独立的坑叠加：

# 坑 单独出现的后果
1 crypt() 返回静态缓冲 数据被改写（和 getpwnam() 一样）
2 失败返回 *0 而非 NULL（与 man 不一致） 只判 NULL 的实现会漏掉
3 *1 是"输入已是 *0"的回环标记 与 ① 叠加 → 认证被绕过

任何一个单独都不致命，叠起来就是一个安全漏洞。所以最终写法要"四道闸门全关"，不能依赖对某个实现的观察。
