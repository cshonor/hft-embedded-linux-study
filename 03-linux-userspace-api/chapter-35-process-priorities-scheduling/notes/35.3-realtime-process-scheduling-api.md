> 源码核验：Linux v6.6 · kernel/sched/core.c（sched_setscheduler:8052、__sched_setscheduler:7620、user_check_sched_setscheduler:7562、__setscheduler_params:7516、RESET_ON_FORK fork 路径:4748、sched_yield:8553、get_priority_max:9039）· kernel/sched/rt.c（yield_task_rt:1590）

## 本节讲什么

1. `sched_setscheduler()` 从 glibc 调用到任务真正换调度类，内核里走哪条链、每步校验什么？
2. 权限判据的**精确**边界——`RLIMIT_RTPRIO` 到底放行哪些操作、"RT 任务降优先级自由"写在内核哪行注释里；
3. `SCHED_RESET_ON_FORK` 与 `SCHED_BATCH`/`SCHED_IDLE` 这些"边角策略"的准确语义。

---

## 一、API 全家桶

```c
#include <sched.h>
struct sched_param { int sched_priority; };        /* 就一个字段 */

int sched_setscheduler(pid_t pid, int policy, const struct sched_param *param);
int sched_getscheduler(pid_t pid);                 /* 返回策略 */
int sched_setparam(pid_t pid, const struct sched_param *param);
int sched_getparam(pid_t pid, struct sched_param *param);
int sched_get_priority_max(int policy);            /* FIFO/RR → 99 */
int sched_get_priority_min(int policy);            /* FIFO/RR → 1  */
int sched_rr_get_interval(pid_t pid, struct timespec *tp);
int sched_yield(void);
```

| API | 语义要点 | 内核入口 |
|-----|----------|----------|
| `sched_setscheduler` | 策略+优先级一起换；policy 可 `\|` 上 `SCHED_RESET_ON_FORK` | core.c:8052 |
| `sched_setparam` | **只改优先级，保留当前策略** | core.c:8067（内部传 `SETPARAM_POLICY=-1`，:7514） |
| `sched_getscheduler` / `sched_getparam` | 查询；**Linux 扩展：getscheduler 返回值会带上 `SCHED_RESET_ON_FORK` 位**（2.6.39+），判断策略前要先剥掉 flag 位 | core.c:8121/:8150 |
| `sched_get_priority_max/min` | FIFO/RR → 99/1；OTHER/BATCH/IDLE/DL → 0/0；非法策略 EINVAL | core.c:9039/:9066 |

**pid 参数的真相**：NPTL 下这组系统调用作用对象是 **task（线程）**，pid 实为 TID——每个线程各自持有 policy/rt_priority（与 Ch29"每线程调度属性"呼应）。传主线程 TID 才影响进程语义上的"主线程"。

## 二、sched_setscheduler 内核调用链

```
sched_setscheduler(pid, policy, param)          glibc → syscall
   │ SYSCALL_DEFINE3  core.c:8052
   ▼
do_sched_setscheduler()                          pid→task 查找 (ESRCH)
   │
   ▼
__sched_setscheduler()  core.c:7620
   │
   ├─[1] 策略合法性: valid_policy()              :7644
   ├─[2] 优先级范围双向校验:                      :7656-7660
   │      FIFO/RR: 1..98 (MAX_RT_PRIO-1)
   │      OTHER/BATCH/IDLE: 必须 0
   │      (rt_policy(policy) != (sched_priority != 0) → EINVAL)
   ├─[3] 权限: user_check_sched_setscheduler()   :7562 (user=true)
   ├─[4] 取 rq 锁, 重读策略(recheck:7636 竞态自愈)
   ├─[5] __setscheduler_params()  :7516
   │      p->policy = policy
   │      p->rt_priority = 用户值直存             :7536
   │      p->normal_prio = __normal_prio() 反向映射 :7537
   │      set_load_weight() (fair 才有意义)
   └─[6] check_class_changed()  :7825
          → switched_to_rt(): p->prio < curr->prio
            → resched_curr()                     rt.c:2557
            ⇒ 设置返回的瞬间, 本任务就可能立刻抢占 CPU!
```

两个容易被忽略的行为：

1. **竞态自愈**：步骤 [4] 会在锁内重读目标策略，若与锁外快照不一致就放弃重来（:7762-7768）——并发 setpriority/sched_setscheduler 不会产生撕裂状态；
2. **即时生效**：切到 RT 类后 `switched_to_rt` 直接 `resched_curr`——新晋 FIFO 任务不用等下一次调度事件。

> 工程边角（v6.6）：kernel/sched/rt.c 顶部没有一行 `#include`——v6.6 把调度类实现拆给 `build_policy.c` 聚合编译，rt.c 是被 include 的"碎片"。读源码时从 rt.c 找不到头文件不是你眼花。

## 三、权限判据全表（user_check_sched_setscheduler 原文逻辑）

先看原文（core.c:7557-7611，节选关键分支）——它是一串"放行即 return 0，全不满足才 goto req_priv"的检查：

```c
/* Allow unprivileged RT tasks to decrease priority.  :7557 注释 */
static int user_check_sched_setscheduler(struct task_struct *p, ...)
{
        if (fair_policy(policy)) {                     /* :7566 */
                if (attr->sched_nice < task_nice(p) &&
                    !is_nice_reduction(p, attr->sched_nice))
                        goto req_priv;
        }
        if (rt_policy(policy)) {                       /* :7572 */
                unsigned long rlim_rtprio = task_rlimit(p, RLIMIT_RTPRIO);
                if (policy != p->policy && !rlim_rtprio)      /* 切策略 */
                        goto req_priv;
                if (attr->sched_priority > p->rt_priority &&  /* 升优先级 */
                    attr->sched_priority > rlim_rtprio)
                        goto req_priv;
        }
        if (dl_policy(policy))                         /* :7591 DL 一律拒 */
                goto req_priv;
        if (task_has_idle_policy(p) && !idle_policy(policy)) {  /* :7598 */
                if (!is_nice_reduction(p, task_nice(p)))
                        goto req_priv;                 /* IDLE 视作 nice 20 */
        }
        if (!check_same_owner(p))                      /* :7604 别人的任务 */
                goto req_priv;
        if (p->sched_reset_on_fork && !reset_on_fork)  /* :7608 取消 ROF */
                goto req_priv;
        return 0;
req_priv:
        return capable(CAP_SYS_NICE) ? 0 : -EPERM;     /* :7614 兜底 */
}
```

逐条翻译成表格（**满足左侧任一即放行**，全部不满足 → 请求 `CAP_SYS_NICE`，没有则 EPERM）：

| 想做的事 | 非特权放行条件 | 内核行 |
|----------|----------------|--------|
| fair 策略下**降低** nice 数值（提权） | `RLIMIT_NICE` 允许（is_nice_reduction） | :7566-7570 |
| **切入/切换** RT 策略（OTHER→FIFO 等） | `RLIMIT_RTPRIO != 0` | :7576 |
| RT 任务**升高** rt_priority | 新值 ≤ 当前值，或 ≤ `RLIMIT_RTPRIO` | :7580-7582 |
| RT 任务**降低** rt_priority | **无条件放行**（"Allow unprivileged RT tasks to decrease priority"，:7557 注释） | :7572 起 |
| SCHED_IDLE 任务逃离 IDLE | RLIMIT_NICE 允许"相当于 nice 20 → 更低"（:7594-7601，内核把 IDLE 视作 nice 20） | :7598 |
| 改**别人的**任务 | check_same_owner（我的 euid == 对方 uid 或 euid） | :7604 |
| 取消 sched_reset_on_fork | 普通用户**不允许**（:7607-7609） | :7608 |
| 任何一条不满足时 | `capable(CAP_SYS_NICE)` → 放行 | :7614 |

要点提炼：

- `RLIMIT_RTPRIO`（`ulimit -r`，单位 = RT 优先级数）为 0 时（默认），**非特权用户与 RT 策略完全绝缘**——既进不去也升不了；
- **降级自由**是内核的显式设计：RT 任务把自己调低、甚至调回 OTHER，不需要任何特权；
- SCHED_DEADLINE 目前非特权完全不可设（:7591）。

## 四、SCHED_RESET_ON_FORK：只管一代的防火墙

语义：带此 flag 设置后，**该任务 fork 出的子进程**调度属性被重置（core.c:4748-4763）：

```c
if (unlikely(p->sched_reset_on_fork)) {
        if (task_has_dl_policy(p) || task_has_rt_policy(p)) {
                p->policy = SCHED_NORMAL;           /* 回 CFS */
                p->static_prio = NICE_TO_PRIO(0);   /* nice 0 */
                p->rt_priority = 0;
        } else if (PRIO_TO_NICE(p->static_prio) < 0)
                p->static_prio = NICE_TO_PRIO(0);   /* 负 nice 也归零! */
        ...
        p->sched_reset_on_fork = 0;                 /* flag 只管一代 */
}
```

三个精确细节：

1. **负 nice 一并重置**——RESET_ON_FORK 不只是"防 RT 遗传"，也防 CAP_SYS_NICE 进程的负 nice 遗传（TLPI 35.3 专门提醒）；
2. **flag 本身在子进程清零**（:4763）——孙进程继承的是子进程的重置后状态，不需要也不应该累积；
3. 用户态的写法是 `sched_setscheduler(0, SCHED_FIFO | SCHED_RESET_ON_FORK, &sp)`（glibc 层 hack，内核 `_sched_setscheduler`:7850 拆开转成 attr flag；查询得用 `sched_getattr`）。

**隔代实测**（rof_grand，root；完整代码见 [35.6 实验 6](35.6-exercises.md)）：

```
父(设置后) pid=384    policy=SCHED_FIFO+ROF   rt_priority=50
子      pid=385    policy=SCHED_OTHER      rt_priority=0    ← 被重置, ROF 位已清
子进程自行设 FIFO 40 (无ROF): OK
子(重设后) pid=385    policy=SCHED_FIFO       rt_priority=40
孙      pid=386    policy=SCHED_FIFO       rt_priority=40   ← 原样继承!
父(最终) pid=384    policy=SCHED_FIFO+ROF   rt_priority=50  ← 父不受影响
```

这张四行输出是"flag 只管一代"的完整证据链：**父带位 → 子被重置（ROF 位同步清零）；子重设 FIFO 不带位 → 孙原样继承 FIFO 40，不再有重置发生**。如果 flag 会遗传，孙进程也该被重置成 OTHER——实测否决。RESET_ON_FORK 是"出生时的一次性产钳"，不是写进基因的遗传病。

**为什么需要它**：一个 FIFO 99 服务（比如以 root 运行的采集守护）fork/exec 到第三方脚本时，脚本意外继承了 FIFO 99——任何它里面的死循环都是整机级灾难。RESET_ON_FORK 是 fork 边界上的"防遗传手术"。

## 五、SCHED_BATCH / SCHED_IDLE：CFS 的两个变体

| 策略 | 语义 | 内核依据 |
|------|------|----------|
| `SCHED_BATCH` | "批处理"：交互性补偿关闭（唤醒不奖励），其余同 OTHER。适合纯 CPU 密集任务 | fair 类内部行为差异 |
| `SCHED_IDLE` | 极低优先级：权重取 `WEIGHT_IDLEPRIO`（set_load_weight:1313-1317），**比 nice +19 还低一档**；逃离它按"从 nice 20 提升"审查（:7598） | core.c:1313 |

注意 SCHED_IDLE ≠ idle 调度类（idle_sched_class 是 CPU 空转，用户不可达）——SCHED_IDLE 任务仍在 fair 类，只是权重被压到最低。

**SCHED_IDLE 是普通用户的"单向门"**（idle_weight 实测，完整代码见 [35.6 实验 5](35.6-exercises.md)）：

```
$ ./idle_weight                        # 普通用户, RLIMIT_NICE=0
[单向门] RLIMIT_NICE={soft=0, hard=0}
[1] 切入 SCHED_IDLE (预写: 免特权成功)...
  当前 policy=SCHED_IDLE (euid=1000)          ← 切进去: 免费
[2] 切回 SCHED_OTHER (预写: 非特权 EPERM)...
    切回失败: Operation not permitted (EPERM=1) —— 单向门!
```

为什么进去免费、出来要特权？两个方向走的检查分支不同：
- **切入 IDLE**：user_check 的 fair 分支（:7566）只拦"降低 nice 数值"——切 IDLE 不带 nice 变更，一路放行；
- **切回 OTHER**：命中 :7598 的专门分支 `task_has_idle_policy(p) && !idle_policy(policy)`——内核把"IDLE → 非 IDLE"等价于"从 nice 20 提升"，需要 `is_nice_reduction`（即 RLIMIT_NICE ≥ 40，默认 0 必然不够）或 CAP_SYS_NICE。

工程含义：**普通用户进程可以主动"自沉"到 SCHED_IDLE 让出 CPU，但沉下去就浮不上来了**（除非 exec 一个新映像——exec 不改调度策略，所以其实也浮不上来；唯一出路是重新启动进程）。把它当"礼貌开关"用之前想清楚。

## 六、sched_yield()：一个 API，三种语义

```c
do_sched_yield()                     core.c:8528
   → current->sched_class->yield_task(rq)   :8536 按类分发
```

| 当前策略 | yield 的实际效果 | 内核 |
|----------|------------------|------|
| SCHED_FIFO / RR | **重排到同优先级队列尾部**——低优先级任务仍然没机会 | yield_task_rt:1590（`requeue_task_rt(rq, rq->curr, 0)`） |
| SCHED_OTHER | 让出 CPU，CFS 正常挑下一个（可能还是自己） | fair 类 yield |
| 任何 | **绝不保证别人一定跑**——若队列里没有同级/更高任务，立刻跑回来 | 通用 |

TLPI 与本章共同的忠告：**sched_yield 不是同步原语**。等资源用 futex/条件变量（Ch30），自旋等待用带 backoff 的原子操作——依赖 yield 的"礼让"在任何策略下都没有可移植保证。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① 常驻 RT 服务 fork/exec 外部脚本前，用 RESET_ON_FORK 切断属性遗传（脚本永远不该继承 FIFO 99）；② 多优先级设计（采集 80 > 控制 70 > 通信 60）从 sched_setparam 单独调优先级，不用反复换策略 |
| HFT | ① 启动序列：mlockall → 绑核 → FIFO（本节 API）→ 再开始热路径——次序错不了；② 交易二进制以 capability 方式授权（setcap cap_sys_nice）而非裸 root；③ RT 线程降优先级是特权自由（:7557）——优雅降级路径（比如过载时自降到 50）可以无条件实现 |

## 代码示例

```c
/* rt_setup.c — sched_setscheduler 全流程: 权限边界 + 即时生效验证
 *              + SCHED_RESET_ON_FORK 隔代重置实测
 * 普通用户运行: 观察 EPERM; root 运行: 全流程成功。
 * 编译: gcc -O2 -Wall -Wextra -o rt_setup rt_setup.c
 */
#define _GNU_SOURCE               /* SCHED_RESET_ON_FORK 需要 __USE_GNU */
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

static const char *polname(int p)
{
    int reset = p & SCHED_RESET_ON_FORK;   /* Linux 2.6.39+: 返回值带此位 */
    p &= ~SCHED_RESET_ON_FORK;
    static char buf[32];
    const char *base =
        p == SCHED_OTHER ? "SCHED_OTHER" :
        p == SCHED_FIFO  ? "SCHED_FIFO"  :
        p == SCHED_RR    ? "SCHED_RR"    : "other";
    snprintf(buf, sizeof buf, "%s%s", base, reset ? "+ROF" : "");
    return buf;
}

static void dump(const char *tag)
{
    struct sched_param sp = {0};
    sched_getparam(0, &sp);
    printf("  %-12s policy=%-14s rt_priority=%d\n",
           tag, polname(sched_getscheduler(0)), sp.sched_priority);
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);  /* fork 前防缓冲复制丢输出 */

    struct rlimit rl;
    getrlimit(RLIMIT_RTPRIO, &rl);
    printf("[0] uid=%d  RLIMIT_RTPRIO={soft=%lu, hard=%lu}\n",
           geteuid(), (unsigned long)rl.rlim_cur,
           (unsigned long)rl.rlim_max);

    /* [1] 切入 SCHED_FIFO 80: 权限判据 user_check:7576 */
    struct sched_param sp = {.sched_priority = 80};
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == -1) {
        printf("[1] sched_setscheduler(FIFO,80): %s (EPERM=%d)\n",
               strerror(errno), errno == EPERM);
        return 0;                        /* 普通用户: 到此为止 */
    }
    printf("[1] sched_setscheduler(FIFO,80): OK\n");
    dump("父进程");

    /* [2] RT 降优先级自由: 80 -> 30, 无需任何特权 (core.c:7557) */
    sp.sched_priority = 30;
    if (sched_setparam(0, &sp) == 0) {
        printf("[2] sched_setparam(80->30): OK (RT 降优先级自由)\n");
        dump("父进程");
    }

    /* [3] RESET_ON_FORK: 子进程属性应被重置回 OTHER/nice0 */
    sp.sched_priority = 60;
    if (sched_setscheduler(0, SCHED_FIFO | SCHED_RESET_ON_FORK, &sp) == -1) {
        perror("[3] setscheduler(RESET_ON_FORK)");
        return 1;
    }
    dump("父进程");

    pid_t pid = fork();
    if (pid == 0) {
        dump("子进程");                   /* 期望: OTHER, 0 */
        fflush(stdout);                  /* _exit 不 flush stdio, 手动刷 */
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    dump("父进程");                       /* 期望: 仍是 FIFO, 60 */
    return 0;
}
```

实测输出（WSL2 · Ubuntu 24.04 · gcc 13.3 零告警）：

```
# 普通用户 (RLIMIT_RTPRIO=0, 无 CAP_SYS_NICE)
$ ./rt_setup
[0] uid=1000  RLIMIT_RTPRIO={soft=0, hard=0}
[1] sched_setscheduler(FIFO,80): Operation not permitted (EPERM=1)

# root (wsl -u root)
# ./rt_setup
[0] uid=0  RLIMIT_RTPRIO={soft=0, hard=0}
[1] sched_setscheduler(FIFO,80): OK
  父进程       policy=SCHED_FIFO   rt_priority=80
[2] sched_setparam(80->30): OK (RT 降优先级自由)
  父进程       policy=SCHED_FIFO   rt_priority=30
  父进程       policy=SCHED_FIFO+ROF rt_priority=60
  子进程       policy=SCHED_OTHER  rt_priority=0
  父进程       policy=SCHED_FIFO+ROF rt_priority=60
```

解读：[1] 的 EPERM 正是 `user_check_sched_setscheduler:7576` 的"RLIMIT_RTPRIO=0 且无 CAP_SYS_NICE"分支；root 侧 [2] 证明降优先级无特权门槛；[3] 子进程 OTHER/0 而父进程 FIFO/60——`core.c:4750-4752` 的重置三连逐字兑现。注意父进程的 policy 显示为 **`SCHED_FIFO+ROF`**：Linux 2.6.39 起 `sched_getscheduler()` 返回值会带上 `SCHED_RESET_ON_FORK` 位——这是与 POSIX 不同的内核扩展行为，判断策略前要先剥掉 flag 位（demo 的 `polname()` 演示了正确写法）。

## 代码自测

<details>
<summary>1. 非特权用户 RLIMIT_RTPRIO=20 时，哪些 RT 操作仍会被拒？</summary>

① 从 OTHER 切入 RT：放行（rlim≠0）；② FIFO 10 → FIFO 30：拒（新值 > 当前值且 > rlim，core.c:7580-7582）；③ FIFO 30 → FIFO 15：放行（降优先级无条件自由）；④ 改另一个用户的任务：拒（check_same_owner 失败）。全部条目的最终兜底是 CAP_SYS_NICE。
</details>

<details>
<summary>2. SCHED_RESET_ON_FORK 会重置什么？孙进程呢？</summary>

RT/DL 父进程的子进程：policy→SCHED_NORMAL、static_prio→nice 0、rt_priority→0（core.c:4750-4752）；CFS 父进程的负 nice 也会归零（:4753-4754）。flag 在子进程出生时自清（:4763），所以只管一代——孙进程继承的是子进程的重置后状态。
</details>

<details>
<summary>3. FIFO 99 任务调用 sched_yield() 后，同核的 nice 0 任务能跑了吗？</summary>

不能。yield_task_rt（rt.c:1590）只是把当前任务重排到**同优先级**队列尾部，低优先级任务依旧排不上。sched_yield 从不给低优先级任务让路。
</details>

<details>
<summary>4. sched_setparam 和 sched_setscheduler 的区别？</summary>

setparam 只改 rt_priority、保留现有策略（内核用 SETPARAM_POLICY=-1 哨兵值表示"不改策略"，core.c:7514/:7521-7522）；setscheduler 策略+优先级一起换。另有细节：RESET_ON_FORK 只能经 setscheduler 的 policy 位设置，且普通用户不能取消已置位的 flag（:7607-7609）；`sched_getscheduler()` 返回值会带回已置位的 RESET_ON_FORK 位（2.6.39+ 扩展）。
</details>

<details>
<summary>5. 为什么说 sched_setscheduler 返回的瞬间任务可能已经在 CPU 上了？</summary>

__sched_setscheduler 末尾 check_class_changed（:7825）→ switched_to_rt（rt.c:2536）：若新 prio < 当前任务 prio，直接 resched_curr（:2557）设置重调度标志——返回用户态的路径上就会发生抢占，新晋 FIFO 任务即刻上核。
</details>
