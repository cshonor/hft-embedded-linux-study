# 35.4 CPU 亲和性

## 本节讲什么

1. `sched_setaffinity()` 的掩码在内核里与什么做了**交集**、空交集为什么是 EINVAL 而不是截断？
2. 从 syscall 到任务真正搬到新核，中间经过哪几站？正在运行的线程怎么"被搬家"？
3. **绑核 ≠ 独占核**——HFT 的完整核隔离栈（isolcpus / nohz_full / IRQ 绕行）差在哪几层？

---

## 一、为什么绑核：三个独立动机

| 动机 | 机制 | 收益对象 |
|------|------|----------|
| **cache 局部性** | 线程留在同核，L1/L2 命中率稳定 | 所有热路径 |
| **NUMA 局部性** | 核与内存节点绑定，避免跨节点访问延迟（~1.5-2x） | 大内存任务 |
| **干扰隔离** | 把关键线程与杂务（内核线程/中断/其他进程）分核 | 延迟敏感路径 |

对 HFT，第三个动机是主要矛盾——前两个绑核就够，第三个要的是"别人不许来"，这就超出 affinity API 的能力范围（见第五节）。

---

## 二、API 与掩码操作

```c
#define _GNU_SOURCE
#include <sched.h>

typedef struct { unsigned long __bits[128]; } cpu_set_t;   /* 概念上 1024 bit */

void CPU_ZERO(cpu_set_t *set);
void CPU_SET(int cpu, cpu_set_t *set);
void CPU_CLR(int cpu, cpu_set_t *set);
int  CPU_ISSET(int cpu, cpu_set_t *set);
int  CPU_COUNT(cpu_set_t *set);

int sched_setaffinity(pid_t pid, size_t cpusetsize, const cpu_set_t *mask);
int sched_getaffinity(pid_t pid, size_t cpusetsize, cpu_set_t *mask);
```

参数语义（TLPI 强调，容易踩坑）：

- `pid` 同样是 **TID 粒度**（线程级）——多线程要逐线程设；
- `cpusetsize` = `sizeof(cpu_set_t)`，内核只取 `min(cpusetsize, cpumask_size())`，**多余高位要求为 0**否则 EINVAL（防误把栈上垃圾当掩码）；
- 掩码是**替换**语义：新掩码完全覆盖旧掩码，不是"追加允许的核"。

命令行对照：`taskset -c 3 ./app`（启动即绑核 3）、`taskset -pc 3 <pid>`（改运行中进程）；`taskset -p <pid>` 只读查询。

## 三、五个语义细节（全部有内核出处）

| # | 细节 | 内核证据 |
|---|------|----------|
| 1 | **亲和掩码永远先与 cpuset/cgroup 允许集求交集**——你给的掩码只是"意愿"，cgroup 才是"权限" | __sched_setaffinity:8317-8318 `cpumask_and(new_mask, ctx->new_mask, cpus_allowed)` |
| 2 | 交集为空 → **EINVAL**（不是截断、不是静默全允许） | :8332-8355（竞态兜底后仍空则 `retval = -EINVAL`） |
| 3 | 改**别人的**任务 → check_same_owner 或 CAP_SYS_NICE，否则 **EPERM** | :8389-8397 |
| 4 | 某些内核线程带 `PF_NO_SETAFFINITY` 不可改 → EINVAL | :8384-8387 |
| 5 | `getaffinity` 返回的是 `p->cpus_mask ∩ cpu_active_mask`——CPU 热插拔后可能比你设的小 | sched_getaffinity:8482 |

继承语义：fork 复制父线程掩码；exec 保留。多线程进程里**主线程改掩码不影响已创建线程**（各自独立）。

## 四、内核链路：正在运行的线程怎么搬家

```
SYSCALL sched_setaffinity        core.c:8448
   │ get_user_cpu_mask(): 用户掩码拷入 + 截断到 cpumask_size
   ▼
sched_setaffinity()              core.c:8365
   │ find_process_by_pid (ESRCH)
   │ PF_NO_SETAFFINITY? → EINVAL            :8384
   │ check_same_owner / CAP_SYS_NICE → EPERM :8389
   ▼
__sched_setaffinity()            core.c:8304
   │ cpumask_and(新掩码, cpuset允许集)       :8317   ← 交集!
   │ 交空(竞态窗口) → 重取允许集再试 → EINVAL :8332
   ▼
__set_cpus_allowed_ptr()
   │ 任务在旧核上正运行?
   ├─ 否: 改 cpus_mask, 入队新核, 完事
   └─ 是: 发 IPI/stop_one_cpu 上下文切换点强制迁移   ← "搬家"现场
         (迁移瞬间: cache 冷启动, 这就是绑核后首次访问慢的原因)
```

"搬家"到底怎么发生的——内核在 core.c:2497-2509 有一段罕见的自白注释，值得逐行读：

```c
/*
 * This is how migration works:
 *
 * 1) we invoke migration_cpu_stop() on the target CPU using stop_one_cpu().
 * 2) stopper starts to run (implicitly forcing the migrated thread off the CPU)
 * 3) it checks whether the migrated task is still in the wrong runqueue.
 * 4) if it's in the wrong runqueue then the migration thread removes it
 *    and puts it into the right queue.
 * 5) stopper completes and stop_one_cpu() returns and the migration is done.
 */
```

翻译成时间线：

```
核 A (旧)                        核 B (新)
──────                          ──────
目标线程正在运行
    │ stop_one_cpu(A, migration_cpu_stop)
    ▼
migration/XX stopper 线程          [stopper 是 SCHED_CLASS 最顶级的
被投递到核 A                        内核线程——见 35.2 类链图,
    │                              它一就绪, 目标线程必然被挤下]
    ▼
目标线程在上下文切换点下核 ──────► __migrate_task():
    (此刻 cache 还热, 但已       deactivate(旧 rq) → set_task_cpu
     不属于它)                    → activate(新 rq)
    │                              (move_queued_task:2516 实操:
    ▼                               dequeue→改 cpu→enqueue)
stopper 收工,
syscall 返回                      目标线程下次被调度时在核 B 上醒来
                                  (cache 全冷——迁移的物理代价)
```

三个细节值得抠：

1. **stopper 是最高调度类的内核线程**（migration/N，stop_sched_class）——它上核的方式就是"把别人挤下去"，这保证了迁移不需要目标线程配合（它可能正关中断/自旋，根本没法配合）；
2. `move_queued_task()`（core.c:2516-2533）的四步 `deactivate_task → set_task_cpu → 换 rq 锁 → activate_task` 是原子搬队列的最小实现——旧核出队、新核入队，中间不会有两个 rq 同时持有该任务；
3. `__do_set_cpus_allowed()`（core.c:2748 起）在改掩码本身时还有一段 dequeue/enqueue 的舞蹈（:2781-2789 `put_prev_task → set_cpus_allowed → enqueue_task`）——因为任务的调度类钩子 `set_cpus_allowed` 可能因掩码变化失效（比如 RT 任务被迫换核后的 push/pull 状态）。

与 35.3 的组合：`sched_setscheduler` 切 FIFO 后 `switched_to_rt` 只 `resched_curr`——但**跨核**的 RT 唤醒还有 push/pull 平衡逻辑（rt.c 的 pushable_tasks，sched.h:681），亲和掩码限制它只能在允许的核里挑。

## 五、绑核 ≠ 独占：HFT 的完整隔离栈

`sched_setaffinity` 只管"**我**只去哪些核"，管不了"**别人**不许来"。负载均衡器照样把内核线程、其他进程放到你的核上。完整的核隔离是四层叠加（TLPI 时代讲了 isolcpus，v6.6 语义更新如下）：

| 层 | 手段 | 效果 |
|----|------|------|
| 1. 普通负载均衡不走开 | `isolcpus=<cpulist>` 启动参数 | 指定核从调度域剔除，**用户任务默认不上去**（要 taskset 显式指定才进） |
| 2. 时钟 tick 不打扰 | `nohz_full=<cpulist>` | 核上只有 1 个任务运行时**停止周期 tick**（每秒数百次的中断消失），需配套 `rcu_nocbs` 卸载 RCU 回调 |
| 3. 网卡中断绕行 | `irqbalance` 停用 + 写 `/proc/irq/<n>/smp_affinity` | 硬中断钉到"杂务核"，业务核零中断 |
| 4. 内核线程搬家 | `rcu_nocbs`、per-cpu kthread 亲和（或 cgroup v2 `cpuset` 分区） | ksoftirqd/rcu 等离场 |

> v6.6 现状：isolcpus 仍是主流做法（内核文档 `isolcpus` 已标注"deprecated in favour of cpuset"，但启动参数依然有效）；新一代方案是 cgroup v2 cpuset 的 **partition**（`cpuset.cpus.partition = root`），把一段核从父域独立出去，效果等价且可在线调整。

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 采集线程绑核 2 + 中断也钉核 2（同核 cache 热），控制线程绑核 3——单 SoC 上的"软分区"；注意与 RT 策略配合：绑核解决"在哪跑"，FIFO 解决"何时跑"，二者缺一不可 |
| HFT | ① 标准拓扑：核 0-1 系统杂务，核 2-3 网卡中断/收包，核 4 起每核一个策略线程（FIFO + taskset 进 isolcpus 核 + nohz_full）；② 绑核后**首次**访存的 cache 冷启动是预期内的抖动源——热身循环（warm-up）要写进启动序列；③ 验收指标：`/proc/interrupts` 业务核计数应长期为 0 |

## 代码示例

```c
/* affinity_pin.c — 绑核/查询/错误路径实测 (无需特权)
 * 编译: gcc -O2 -Wall -Wextra -o affinity_pin affinity_pin.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void show(const char *tag)
{
    cpu_set_t set;
    CPU_ZERO(&set);
    if (sched_getaffinity(0, sizeof set, &set) == -1) {
        perror("sched_getaffinity");
        return;
    }
    int last = -1, n = CPU_COUNT(&set);
    for (int i = 0; i < CPU_SETSIZE; i++)
        if (CPU_ISSET(i, &set))
            last = i;
    /* 与 /proc/self/status 交叉验证 */
    char procline[256] = "";
    FILE *f = fopen("/proc/self/status", "r");
    if (f) {
        char line[256];
        while (fgets(line, sizeof line, f))
            if (strncmp(line, "Cpus_allowed_list:", 18) == 0) {
                char *p = line + 18;
                while (*p == ' ' || *p == '\t') p++;
                snprintf(procline, sizeof procline, "%s", p);
                procline[strcspn(procline, "\n")] = 0;
                break;
            }
        fclose(f);
    }
    printf("  %-10s count=%d max=%d /proc: %s\n", tag, n, last, procline);
}

int main(void)
{
    long ncpu = sysconf(_SC_NPROCESSORS_ONLN);
    printf("[0] 在线核数: %ld\n", ncpu);
    show("初始掩码");

    /* [1] 绑到最后一核 */
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(ncpu - 1, &set);
    if (sched_setaffinity(0, sizeof set, &set) == -1)
        perror("[1] setaffinity");
    else
        printf("[1] 绑核 %ld OK\n", ncpu - 1);
    show("绑后");

    /* [2] 空掩码: 与允许集交集为空 → EINVAL (core.c:8332) */
    CPU_ZERO(&set);
    if (sched_setaffinity(0, sizeof set, &set) == -1)
        printf("[2] 空掩码: %s (EINVAL=%d)\n", strerror(errno),
               errno == EINVAL);

    /* [3] 恢复全核, 观察掩码替换语义 (不是追加) */
    CPU_ZERO(&set);
    for (int i = 0; i < ncpu; i++)
        CPU_SET(i, &set);
    if (sched_setaffinity(0, sizeof set, &set) == -1)
        perror("[3] setaffinity");
    else
        printf("[3] 恢复全核 OK (替换语义)\n");
    show("恢复后");
    return 0;
}
```

实测输出（WSL2 · 12 核 · gcc 13.3 零告警）：

```
$ ./affinity_pin
[0] 在线核数: 12
  初始掩码   count=12 max=11 /proc: 0-11
[1] 绑核 11 OK
  绑后       count=1 max=11 /proc: 11
[2] 空掩码: Invalid argument (EINVAL=1)
[3] 恢复全核 OK (替换语义)
  恢复后     count=12 max=11 /proc: 0-11
```

解读：[2] 的 EINVAL 来自 `__sched_setaffinity:8332` 的空交集检查；`/proc/self/status` 的 `Cpus_allowed_list` 与 `sched_getaffinity` 完全一致——排查生产问题时从 status 文件读最方便（无需 ptrace 权限）。

## 代码自测

<details>
<summary>1. sched_setaffinity 给的掩码与 cgroup cpuset 允许集无交集时，返回什么？为什么不静默截断？</summary>

EINVAL（__sched_setaffinity:8332-8355）。静默截断会让"以为绑到了核 8"的任务实际继承旧掩码或落回别处，对延迟敏感程序是隐形灾难；显式报错把决策权还给调用者。
</details>

<details>
<summary>2. 绑核后线程正在另一核上运行，sched_setaffinity 内核侧如何完成"搬家"？</summary>

__set_cpus_allowed_ptr 发现目标不在新掩码内 → 通过 IPI/stop_one_cpu 在目标线程的上下文切换点强制迁移。迁移瞬间 cache 全冷——这是绑核后第一次访存变慢的原因，热身循环应写进启动序列。
</details>

<details>
<summary>3. taskset 绑核后，为什么该核上还会出现别的任务？HFT 怎么补齐？</summary>

affinity 只约束"我不去别的核"，不约束"别人不来我的核"——负载均衡仍会往该核派活。补齐：isolcpus（调度域剔除）+ nohz_full（停 tick）+ IRQ affinity 绕行 + rcu_nocbs，或 cgroup v2 cpuset partition。
</details>

<details>
<summary>4. sched_getaffinity 的返回值什么情况下会小于你当初设置的掩码？</summary>

CPU 热插拔：内核返回 p->cpus_mask ∩ cpu_active_mask（core.c:8482）——离线核被剔出。所以"读回来 ≠ 设进去"也可能不是 bug 而是拓扑变化。
</details>

<details>
<summary>5. 多线程进程里，主线程 sched_setaffinity(0, …) 影响谁？</summary>

只影响主线程自己（pid 参数是 TID 粒度）。要让整个进程收拢到某核，要么在创建每个线程前设好（继承），要么逐 TID 设置（pthread_setaffinity_np / sched_setaffinity(tid, …)）。
</details>
