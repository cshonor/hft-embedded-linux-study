# 35.1 进程优先级与 nice 值

> 源码核验：Linux v6.6 · include/linux/sched/prio.h（MAX_RT_PRIO:16、nice_to_rlimit:32）· kernel/sys.c（set_one_prio:194、getpriority:288）· kernel/sched/core.c（set_user_nice:7187、sched_prio_to_weight:11542）· kernel/sched/autogroup.c（sysctl_sched_autogroup_enabled:7）

## 本节讲什么

1. **nice 值到底改了内核里的什么？**——它不是"优先级"，是 CFS 权重表的查表下标；
2. **为什么非特权进程只能调大 nice（降权）？**——内核在哪一行、用哪个 rlimit 做判定；
3. **`getpriority()` 为什么必须先 `errno = 0`？**——内核侧有一条专门为此写的注释，读完就忘不掉。

---

## 一、nice 值的真实身份：CFS 权重，不是优先级

用户视角：nice ∈ **[-20, +19]**，默认 0，**越小越优先**。
内核视角：nice 从头到尾不直接参与"谁先跑"的比较——它被换算三次，最后变成 `task_struct.se.load.weight`（一个正整数权重），CFS 用它分配 CPU 时间比例：

```
nice 值 (-20 … +19)
   │  NICE_TO_PRIO(nice) = nice + DEFAULT_PRIO(120)      prio.h:26
   ▼
static_prio (100 … 139)      ← 内核统一优先级空间的 CFS 段
   │  USER_PRIO(prio) = prio - MAX_RT_PRIO(100)
   ▼
权重表下标 (0 … 39)
   │  set_load_weight() → sched_prio_to_weight[prio]     core.c:1326
   ▼
se.load.weight (88761 … 15)   ← CFS 真正拿来分蛋糕的数
```

权重表 `sched_prio_to_weight[40]`（core.c:11542，摘录）：

| nice | -20 | -10 | -5 | 0 | +5 | +10 | +15 | +19 |
|------|-----|-----|----|----|----|-----|-----|-----|
| weight | 88761 | 9548 | 3121 | **1024** | 335 | 110 | 36 | **15** |

core.c:11531-11540 的注释写明了设计意图：**每差 1 级 nice，CPU 份额约 -10%；一方 -10%、另一方 +10%，相对差距就是 25%**（即权重比 1.25）。所以"nice 差 5"的两任务，CPU 时间比约为 1.25⁵ ≈ 3.05 : 1，而不是线性的 5 : 1。

> **实测验证**（nice_race，WSL2 核 11 单核对撞，两线程各自 `setpriority(PRIO_PROCESS, 0, n)` 后自旋 4s）：
> ```
> 预写: nice0/nice5 CPU 比 ≈ 1024/335 = 3.057
> 实测: nice0 = 3.06s, nice5 = 1.01s, 比值 = 3.03 : 1 (偏差 -0.8%)
> ```
> 权重表不是纸面理论——3% 以内的误差说明 CFS 的 vruntime 分蛋糕确实严格按 `se.load.weight` 比例执行（完整实验见 [35.6 实验 4](35.6-exercises.md)）。同表还有一对倒影 `sched_prio_to_wmult[40]`（core.c:11560）——预计算的 2³²/x 逆权重，把除法变乘法：权重不变时 CFS 用它加速 `vruntime += delta * NICE_0_LOAD / weight` 的换算。

> ⚠️ 关键推论：nice 是**比例调节**，不是**抢占保证**。nice -20 的任务与 nice 19 的任务公平分享 CPU（88761 : 15 ≈ 5918 : 1，但仍是"分享"）。任何就绪的实时任务都能瞬间抢占所有 CFS 任务，与 nice 无关——见 35.2。

## 二、三个 API 与 `which` 三粒度

```c
#include <sys/resource.h>
int getpriority(int which, id_t who);            /* 读：返回 nice 值 */
int setpriority(int which, id_t who, int prio);  /* 写：prio 就是目标 nice 值 */
#include <unistd.h>
int nice(int inc);                               /* 当前进程：nice += inc */
```

| which | 作用对象 | who = 0 时 |
|-------|----------|-----------|
| `PRIO_PROCESS` | 单个进程 | 当前进程 |
| `PRIO_PGRP` | 进程组内**所有**进程 | 调用者所在进程组 |
| `PRIO_USER` | **某真实 UID 的所有**进程 | 调用者的 RUID |

三个语义细节（全部有内核出处）：

1. **批量设置**：`setpriority(PRIO_PGRP/PRIO_USER, …)` 对组/用户内每个任务逐一执行（sys.c:253 `do_each_pid_thread` / :268 `for_each_process_thread`）——一次调用改一群。
2. **静默钳制**：传入 `prio = 50` 不报错，内核直接 clamp 到 19（sys.c:232-235 `if (niceval > MAX_NICE) niceval = MAX_NICE;`）；`nice(inc)` 同样先 clamp 增量再 clamp 结果（core.c:7285-7288）。**返回 0 ≠ 你设的值生效了**，读回验证才是可靠做法。
3. **`nice()` 是相对调整**：`nice(0)` 是查询当前值的惯用法；`nice(5)` 是在当前值上加 5。

第四个细节（TLPI 未展开，多线程程序必知）：

4. **`PRIO_PROCESS` 的 pid 参数是 TID 粒度**：sys.c:219 对 `who == 0` 执行 `who = task_pid_vnr(current)`——取的是**调用线程自己**的 pid 字段（即 TID），而 `find_task_by_vpid(who)` 找到的也是单个 task（线程），**不是整个线程组**。所以多线程进程里 `setpriority(PRIO_PROCESS, 0, 10)` 只降权当前线程；想给"另一个线程"降权必须传它的 TID，想全进程降权要逐线程设（或干脆在创建前设置让 fork 继承）。这与 `sched_setscheduler` 的 pid 参数语义一致（35.3）。实测证据：nice_race 实验里两个 worker 各自 `setpriority(PRIO_PROCESS, 0, n)`，读回各自独立生效（worker0=nice 0、worker1=nice 5 互不干扰）。

## 三、getpriority() 的三重陷阱（TLPI 经典）

### 陷阱 1：内核 syscall 返回的根本不是 nice 值

sys.c:282-287 有一条堪称"教科书注释"的原话：

> **Ugh. To avoid negative return values, "getpriority()" will not return the normal nice-value, but a negated value that has been offset by 20 (ie it returns 40..1 instead of -20..19) to stay compatible.**

即：内核 syscall 返回 **rlimit 风格值 1..40**（= `20 - nice`，prio.h:32 `nice_to_rlimit`），glibc 包装层再转回 nice 值。所以"syscall 返回值"和"库函数返回值"是两个东西——追溯 strace 输出时会看到差 20 的偏移。

### 陷阱 2：-1 是合法返回值 → errno 惯用法

nice = -1 时 `getpriority()` 返回 -1，与错误返回值撞车。标准写法：

```c
errno = 0;
int n = getpriority(PRIO_PROCESS, 0);
if (n == -1 && errno != 0)
    perror("getpriority");   /* 真·出错 */
```

### 陷阱 3：多目标时返回最高优先级的那个

`PRIO_PGRP/PRIO_USER` 命中多个任务时，内核取 `nice_to_rlimit` **最大**的那个（sys.c:309 `if (niceval > retval) retval = niceval;`）——rlimit 值大 = nice 值小 = **优先级最高**的任务的 nice。

## 四、权限：谁能改谁的 nice

判定链（setpriority 路径）：

```
setpriority(which, who, prio)
   │ sys.c:218
   ▼
set_one_prio()  sys.c:194
   │
   ├─ set_one_prio_perm()  sys.c:178
   │    ├─ 我的 euid == 目标 uid 或 euid？ → 通过
   │    └─ ns_capable(CAP_SYS_NICE)？      → 通过
   │    都不是 ──────────────► -EPERM   （"不是你的进程"）
   │
   └─ niceval < task_nice(p) && !can_nice(p, niceval)？
        can_nice()  core.c:7262 = is_nice_reduction() || capable(CAP_SYS_NICE)
        is_nice_reduction()  core.c:7249：
            nice_to_rlimit(nice) <= task_rlimit(p, RLIMIT_NICE)
        都不满足 ────────────► -EACCES （"是你的进程，但提权被拒"）
```

**EPERM 与 EACCES 的分界**（TLPI 强调，内核一一对应）：

| errno | 含义 | 触发条件 |
|-------|------|----------|
| `EPERM` | 动不了别人的进程 | `set_one_prio_perm()` 失败（非 owner 且无 CAP_SYS_NICE） |
| `EACCES` | 是自己的进程，但想**降低 nice 数值**（提权）被拒 | `can_nice()` 失败 |

**RLIMIT_NICE 的换算**（prio.h:32）：它的单位不是 nice 值，是 rlimit 风格 1..40。默认 0 → `is_nice_reduction()` 恒为假 → 非特权进程**只能调大 nice**。要让普通用户能设到 nice -10，需 `RLIMIT_NICE = 20 - (-10) = 30`。

## 五、nice 对实时任务无效 + autogroup 修正

### 对 FIFO/RR 任务：只写不生效

`set_user_nice()`（core.c:7187）对 RT/DL 任务的处理是原代码 + 原注释的铁证（core.c:7204-7208）：

> The RT priorities are set via sched_setscheduler(), but we still allow the 'normal' nice value to be set - **but as expected it won't have any effect on scheduling** until the task is SCHED_DEADLINE, SCHED_FIFO or SCHED_RR:

即：给 SCHED_FIFO 任务 setpriority 只是改了 `static_prio`（:7210）就返回——调度决策完全不看它。

### 继承与 exec

fork 复制父进程的 `static_prio`（→ nice 继承）；exec 不改。所以"shell 里 `nice -n 10 ./app`"是把 shell 的 nice+10 传给 fork 出的子进程。

### TLPI 之后的 autogroup（2011, v2.6.38+）

TLPI 出版（2010）时描述的语义是：**同一终端里 nice 0 的 A 和 nice 0 的 B 平分 CPU；A nice 10 则按权重 1.25¹⁰ 分**。v6.6 默认行为已被 autogroup 修改（autogroup.c:7 `sysctl_sched_autogroup_enabled = 1`）：

- 每个**会话**（setsid，通常 = 每个终端/SSH 登录）自动建一个 task_group；
- CFS 先在**组间**公平分配，再在组内按 nice 分——**你把 A nice 10，只影响你所在会话组内部**，对其它终端里的任务毫无影响；
- 组级调整入口：写 `/proc/<pid>/autogroup`（autogroup.c:231 `proc_sched_autogroup_set_nice`），用的正是同一张权重表（:255-256）；
- 关闭：启动参数 `noautogroup`（:227）或 `echo 0 > /proc/sys/kernel/sched_autogroup_enabled`。

> HFT 视角的讽刺：厂商在建议你 nice 降权"后台任务"时，autogroup 可能让这招在跨会话场景下完全失效——这正是要读源码而不是背 man 的理由。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 日志/监控等杂务进程**调高 nice 降权**，保护控制任务。但记住：nice 只是 CFS 内部的比例调节，控制任务真正要确定性仍须 SCHED_FIFO（35.3） |
| HFT | ① nice 给**落盘、统计、日志线程**降权可用（同进程/同会话内有效）；② 关键路径**绝不能**靠 nice -20 求"高优先"——它是权重不是抢占；③ 交易机上多终端（多 autogroup）并存时，nice 跨会话不生效，用 cgroup 做资源隔离更可靠 |

## 代码示例

```c
/* nice_probe.c — nice 三 API + getpriority 陷阱 + 权限边界实测
 * 普通用户运行演示 EACCES；root 运行演示全通（对照）。
 * 编译: gcc -O2 -Wall -Wextra -o nice_probe nice_probe.c
 */
#include <errno.h>
#include <stdio.h>
#include <sys/resource.h>
#include <unistd.h>

static int get_nice_safe(void)
{
    errno = 0;
    int n = getpriority(PRIO_PROCESS, 0);
    return (n == -1 && errno != 0) ? -999 : n;   /* -999 = 真·出错 */
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);  /* stderr 无缓冲, 行缓冲防输出乱序 */
    /* [1] 两种读法 + errno 惯用法演示 */
    errno = 0;
    int raw = getpriority(PRIO_PROCESS, 0);
    printf("[1] nice(0)=%d  getpriority(raw)=%d errno=%d\n",
           nice(0), raw, errno);

    /* [2] 非特权降权（调大 nice）: 应当成功 */
    if (setpriority(PRIO_PROCESS, 0, 10) == -1)
        perror("[2] setpriority(10)");
    printf("[2] after setpriority(10): nice=%d\n", get_nice_safe());

    /* [3] 回到 5 = 降低 nice 数值 = 提权: 普通用户应 EACCES, root 成功 */
    errno = 0;
    if (setpriority(PRIO_PROCESS, 0, 5) == -1)
        perror("[3] setpriority(5)");
    printf("[3] after setpriority(5): nice=%d\n", get_nice_safe());

    /* [4] 越界值: 内核静默钳制到 19, 不报错 */
    if (setpriority(PRIO_PROCESS, 0, 99) == -1)
        perror("[4] setpriority(99)");
    printf("[4] after setpriority(99): nice=%d (clamped, no error)\n",
           get_nice_safe());

    /* [5] autogroup 归属: TLPI 时代没有的机制 (需内核 CONFIG_SCHED_AUTOGROUP) */
    FILE *f = fopen("/proc/self/autogroup", "r");
    if (f) {
        char buf[128];
        if (fgets(buf, sizeof buf, f))
            printf("[5] /proc/self/autogroup: %s", buf);
        fclose(f);
    } else {
        printf("[5] /proc/self/autogroup: ENOENT"
               " (本内核未开 CONFIG_SCHED_AUTOGROUP)\n");
    }
    return 0;
}
```

实测输出（WSL2 · Ubuntu 24.04 · gcc 13.3，`-O2 -Wall -Wextra` 零告警）：

```
# 普通用户 (uid=1000, RLIMIT_NICE=0, 无 CAP_SYS_NICE)
$ ./nice_probe
[1] nice(0)=0  getpriority(raw)=0 errno=0
[2] after setpriority(10): nice=10
[3] setpriority(5): Permission denied
[3] after setpriority(5): nice=10
[4] after setpriority(99): nice=19 (clamped, no error)
[5] /proc/self/autogroup: ENOENT (本内核未开 CONFIG_SCHED_AUTOGROUP)

# root (uid=0) 对照: 同一程序
# ./nice_probe
[1] nice(0)=0  getpriority(raw)=0 errno=0
[2] after setpriority(10): nice=10
[3] after setpriority(5): nice=5
[4] after setpriority(99): nice=19 (clamped, no error)
[5] /proc/self/autogroup: ENOENT (本内核未开 CONFIG_SCHED_AUTOGROUP)
```

解读：[3] 是本节权限链的活标本——普通用户 `EACCES`（是自己的进程、提权被拒），root 畅通。[4] 证明钳制发生在内核（sys.c:232-235）。[5] 是个意外收获：**Microsoft 的 WSL2 内核（6.6.87.2-microsoft-standard）没有编译 CONFIG_SCHED_AUTOGROUP**——/proc/self/autogroup 与 /proc/sys/kernel/sched_autogroup_enabled 都不存在，autogroup 机制整体关闭。也就是说 WSL 里的 nice 行为反而回归 TLPI 描述的"原始 CFS"语义；在标准发行版内核上此行会输出类似 `/autogroup-2 nice 0`。

## 代码自测

<details>
<summary>1. nice 值在内核里的完整换算链是什么？终点是哪个字段？</summary>

nice → `NICE_TO_PRIO`（+120）→ static_prio(100..139) → `USER_PRIO`（-100）→ 权重表下标(0..39) → 查 `sched_prio_to_weight[40]`（core.c:11542）→ `task_struct.se.load.weight`。CFS 用最终权重分配 CPU 时间比例；nice 从不直接参与"谁先跑"的比较。
</details>

<details>
<summary>2. getpriority() 为什么可能返回 -1 却不算出错？syscall 层返回什么？</summary>

nice = -1 是合法值。内核 syscall 返回的是 rlimit 风格 1..40（sys.c:282-287 注释："returns 40..1 instead of -20..19"），glibc 再转回 nice——转换后的 -1 与错误码撞车，所以必须 `errno = 0` 后调用再检查 errno。
</details>

<details>
<summary>3. setpriority() 返回 EACCES 和 EPERM 分别说明什么？</summary>

EPERM：目标进程不是你的（uid/euid 不匹配且无 CAP_SYS_NICE，set_one_prio_perm sys.c:178 拒绝）；EACCES：是你自己的进程，但你试图降低 nice 数值（提权）且 RLIMIT_NICE 不允许、也无 CAP_SYS_NICE（set_one_prio sys.c:203）。
</details>

<details>
<summary>4. 为什么说"给 SCHED_FIFO 任务设 nice"是无效操作？内核怎么处理的？</summary>

set_user_nice()（core.c:7209-7212）对 RT/DL 任务只更新 static_prio 后直接返回，注释原话 "it won't have any effect on scheduling"。RT 的优先级只由 sched_setscheduler 的 1..99 决定。
</details>

<details>
<summary>5. TLPI 说"同终端两个 nice 0 任务平分 CPU"，v6.6 上还成立吗？</summary>

组内成立，但多会话场景被 autogroup（v2.6.38+，默认开，autogroup.c:7）修正：CFS 先在会话组之间公平，再在组内按 nice 权重分。跨终端的 nice 互相不可见；组级份额用 /proc/&lt;pid&gt;/autogroup 调整。
</details>
