# 41.8 Compatible versus Incompatible Libraries

> 本章：[TLPI 第 41 章](../README.md)

## 本节讲什么

共享库的兼容性规则：何时需要递增版本号，何时可以安全替换。区分 ABI 兼容与不兼容的变更类型。

## 要点

### 兼容性分级

| 级别 | 定义 | 处理 |
|------|------|------|
| 源码兼容 | 重新编译即可工作 | 更新次版本号 |
| ABI 兼容 | 二进制不需重编译 | 可直接替换 .so |
| 不兼容 | 二进制接口改变 | 递增主版本号 |

### ABI 不兼容的变更

| 变更类型 | 示例 | 兼容性 |
|----------|------|--------|
| 删除导出符号 | 删除 `foo()` | 不兼容 |
| 添加必需参数 | `foo(int)` → `foo(int, int)` | 不兼容 |
| 改变字段大小 | struct 增加/移除字段 | 不兼容 |
| 改变字段偏移 | 调整 struct 字段顺序 | 不兼容 |
| 改变枚举值 | `enum {A=0, B=1}` → `{A=0, B=2}` | 不兼容 |
| 改变函数返回类型 | `int foo()` → `long foo()` | 不兼容 |
| 改变 ABI 调用约定 | cdecl → stdcall | 不兼容 |

### 兼容的变更

| 变更类型 | 条件 |
|----------|------|
| 添加新导出符号 | 不影响现有使用者 |
| 增加函数参数（带默认值） | C 无默认值，不适用 |
| 修改函数内部实现 | 不改签名 |
| 增加 struct 末尾字段 | 使用者不直接分配该 struct |

### 版本号规则

```
libfoo.so.MAJOR.MINOR.PATCH
        │      │      │
        │      │      └─ 补丁：bug 修复，完全兼容
        │      └──── 次版本：新增功能，向后兼容
        └───────── 主版本：ABI 破坏性变更
```

| 变更类型 | 主版本 | SONAME | 旧程序 |
|----------|--------|--------|--------|
| bug 修复 | 不变 | 不变 | 正常工作 |
| 新增接口 | 不变 | 不变 | 正常工作 |
| ABI 破坏 | +1 | `libfoo.so.N+1` | 需重新编译 |

### 符号版本控制（GNU 扩展）

```
libfoo.so.1
├── VERSION_1.0 {  ← 初始版本
│     foo;
│     bar;
│ }
├── VERSION_1.1 {  ← 新增接口
│     baz;
│ } VERSION_1.0;   ← 依赖 1.0
└── VERSION_2.0 {  ← 不兼容版本
│     foo;  ← 签名改变
│ }
```

## HFT / 嵌入式关联

- 行情解析库 ABI 变更需通知所有策略程序重新编译
- 使用符号版本控制同时支持新旧接口，平滑迁移
- 嵌入式设备固件升级需验证库版本兼容性

## 代码示例

### 版本脚本示例

```c
/* version.map */
LIBHFT_1.0 {
    global: parse_msg; encode_msg; init;
    local: *;
};
LIBHFT_1.1 {
    global: parse_msg_v2; get_stats;
} LIBHFT_1.0;
```

```bash
gcc -shared -fPIC -Wl,-version-script,version.map \
    -Wl,-soname,libhft.so.1 -o libhft.so.1.1.0 *.o
```

### 检查符号版本

```bash
# 查看库的符号版本
objdump -T libhft.so | grep parse_msg
# 输出: ... parse_msg  (LIBHFT_1.0)

# 查看程序依赖的版本
readelf -V app | grep HFLT
```

## 代码自测

<details>
<summary>struct 末尾增加字段是否 ABI 兼容？</summary>

不一定。如果调用者直接在栈上或堆上分配该 struct，增加字段会导致分配大小不足，写入新字段时越界。但如果 struct 只由库内部分配（如 `struct foo *foo_create()`），则使用者不关心大小，是兼容的。应配合 `opaque pointer` 模式或 `*_sizeof()` 函数来安全扩展。

</details>
