## 本章回顾：围绕同一个 `struct file` 的十一件事

Ch4 讲的是「怎么用」——`open/read/write/close/lseek` 五个动词。Ch5 讲的是**这套模型下面的机关**：同一个 `struct file` 身上还有哪些可以动的东西、动它们会牵动谁。

| 节 | 动的对象 | 内核入口 | 一句话结论 |
|----|---------|---------|-----------|
| 5.1 | `open` 的**标志组合** | `fs/open.c:1315-1320` | `O_EXCL` 消灭 TOCTOU；`O_APPEND` 让「定位+写」变成一步原子操作 |
| 5.2 | `fcntl()` 的**命令** | `fs/fcntl.c:316` `do_fcntl` | 一个「万金油」接口，命令分了 8 组；未知命令 `EINVAL`（`ioctl` 是 `ENOTTY`） |
| 5.3 | **状态标志**（`f_flags`） | `fs/fcntl.c:37` `setfl` | 能用 `F_SETFL` 改的只有 5 个位（`SETFL_MASK`）；`O_CREAT/O_TRUNC/O_EXCL` 改不动、且**不报错** |
| 5.4 | **三层结构** | `fdtable.h:27/49` · `fs.h:992/639` | fd 表 → `struct file` → inode；**「怪现象」全部来自这一层错位** |
| 5.5 | **fd 的复制** | `fs/file.c:1232/1266/1301` | `dup`/`dup2`/`dup3`/`F_DUPFD` 是同族的四个入口，差异只在「目标号怎么定」和「CLOEXEC」 |
| 5.6 | **偏移的来源** | `fs/read_write.c:602/652` | `pread/pwrite` 用 `fdget`（不带 `_pos`）→ 不碰共享游标；这是**线程安全的定位读写** |
| 5.7 | **buffer 的形态** | `fs/read_write.c:905/922` | `readv/writev` 把「N 段不连续内存」合成 1 次系统调用；段数上限 `IOV_MAX = 1024` |
| 5.8 | **文件长度** | `fs/open.c:40/71/157` | `truncate` 按路径、`ftruncate` 按 fd；变长产生**洞**，逻辑与物理占用分道扬镳 |
| 5.9 | **等待行为** | `fs/pipe.c:231/417` | `O_NONBLOCK` 把「挂起」换成 `EAGAIN`；被信号打断是 `EINTR`（两回事） |
| 5.10 | **偏移的宽度** | `fs/open.c:1443` + glibc `x86/bits/fcntl.h:23-25` | 64 位平台上 `off_t` 天然是 8 字节；真正拦你的是 `RLIMIT_FSIZE` / `s_maxbytes` |
| 5.11 | **fd 的路径化身** | `fs/proc/fd.c:169` | `/dev/fd/N` 只是指向 `/proc/self/fd/N`；它是「打开那个文件」而**不是** `dup` |
| 5.12 | **名字与 inode 的分离** | `fs/dcache.c:3249` · `fs/namei.c:3669` | `mkstemp` 靠 `O_EXCL` 原子化；`O_TMPFILE` 的文件**从来没有名字**，`d_tmpfile` 直接 `nlink--` |

一条贯穿全章的主线：

> **用户态看到的一个 `int`，是内核里三层结构的入口。**
> **Ch5 的每一个「反直觉」，都能定位到「你动的是哪一层」。**

```
进程 fd 表（每进程一份）        打开文件表项（struct file）        inode 表（全局共享）
┌───────────────┐              ┌──────────────────────┐          ┌──────────────────┐
│ 0 ──┐         │              │ f_pos      偏移游标   │          │ i_ino    inode 号 │
│ 1 ──┼──┐      │   dup/fork   │ f_flags    状态标志   │          │ i_mode   类型权限 │
│ 3 ──┼──┼──┐   │ ───────────▶ │ f_count    引用计数   │ ───────▶ │ i_size   逻辑长度 │
│     │  │  │   │   共享它      │ f_op       操作表     │          │ 数据块映射/洞     │
│ FD_CLOEXEC ◀──┼──「哪一个 fd」 │                      │          │                  │
└───────────────┘              └──────────────────────┘          └──────────────────┘
   ①                          ②                                  ③
```

| 层 | 谁共享它 | 本节实测证据 |
|----|---------|-------------|
| ① 进程 fd 表 | **不共享**（各进程一份） | 对 fd2 设 `FD_CLOEXEC`，fd1 的 `F_GETFD` 仍是 `0x0`（`ex5_5`） |
| ② `struct file` | `dup` / `dup2` / `dup3` / `F_DUPFD` / `fork` | 对 dup-fd 设 `O_APPEND`，原 fd 的 `F_GETFL` 一起变成 `0x08401`（`c5_3`、`c5_4`） |
| ③ inode | **所有打开者**（含不同进程各自 `open`） | `fd1` 与 `fd3` 是不同表项，但 `st_ino` 都是 `2`（`c5_4`） |

## 「反直觉」清单：本章最值钱的十条

都是**跑出来才知道**的，光读书容易想反：

| # | 反直觉点 | 真实行为 | 证据 |
|---|---------|---------|------|
| 1 | `F_SETFL` 会给未知/不可改的标志报错 | **不报错，静默忽略**。`O_CREAT\|O_TRUNC\|O_EXCL` 返回 0 但一位没变 | `0x08001` → `0x08001`，变化 `0x00000` |
| 2 | `F_SETFL(O_ASYNC)` 一定会打开异步通知 | **普通文件上静默失败**——`FASYNC` 位要由 `f_op->fasync` 钩子来设，普通文件没有 | 同代码在管道上生效（`0x02000`） |
| 3 | `dup2(old,new)` 会先关掉 `new` | 当 `old == new` 时**一个字节都不动**（既不关也不复制），但要校验 `old` 有效 | `dup2(fd,fd) -> 3`；`dup2(999,999) -> EBADF` |
| 4 | `dup3` 是 `dup2` 的加强版 | `dup3(fd, fd, 0)` 直接 **`EINVAL`**（内核不允许 old==new） | `fs/file.c:1241-1242` |
| 5 | `FD_CLOEXEC` 也是「打开文件」的属性 | **不是**。它在**层 ①**（fd 表项），所以 dup 出来的 fd **不**继承它 | 对 fd2 设，fd1 `F_GETFD=0x0` |
| 6 | `pread/pwrite` 只是「方便版」 | 它是**唯一**能在多线程下安全做定位读写的方式——因为它用 `fdget` 而不是 `fdget_pos` | `fs/read_write.c:661` vs `:604` |
| 7 | `ftruncate` 只会失败于权限 | **只读 fd 上是 `EINVAL`（22），不是 `EACCES`** | 实测 `-1 errno=22` |
| 8 | `truncate` 变长会写一堆 0 | 是**洞**：逻辑 `8192` 而物理只占 `4096`；真写满则占 `8192` | 同样 8192 逻辑长度，物理差 2 倍 |
| 9 | `open("/dev/fd/N")` 等于 `dup(N)` | **Linux 上不等价**：新 fd 有新表项、独立偏移 | 原 fd 的 `f_pos` 仍是 0 |
| 10 | `O_EXCL` 永远是「已存在就失败」 | 配 `O_TMPFILE` 时含义被**重定义**成「不许挂名」（控制 `I_LINKABLE`） | `fs/namei.c:3700-3704`、`:4598` |

## 沙箱环境限制表（CE 实测）

本章所有实测都在 Compiler Explorer 的公开沙箱里完成。**沙箱有几条硬限制，直接影响某些 demo 只能测到「被拦住的那一步」**，读表时别把它们当成内核行为：

| 限制 | 实测值 | 影响 |
|------|--------|------|
| **`RLIMIT_FSIZE` 只有 16 MiB** | soft = hard = `16777216` | 5.10 / 习题 5-1 里「写出 4 GiB 大文件」**必然被 `SIGXFSZ` 杀掉**。这恰好演示了「拦住你的不是 `off_t` 宽度而是 rlimit」，但**不能**用来验证文件真的能长到 4 GiB |
| **没有 `/dev/fd`** | `stat` → `ENOENT` | 它只是 MAKEDEV 建的符号链接。5.11 全程改用 `/proc/self/fd` |
| **没有 `/bin/sh`** | `system()` 返回 `32512` | 原书 `multi_descriptors.c` 在沙箱里**完全无输出**——它会 `system("ls -l ...")`。要复现请看 5.4 里本仓库复刻的版本 |
| **没有 tty** | `TIOCGWINSZ` → `ENOTTY` | Ch4 的现象；Ch5 的 `F_GETOWN`/`F_SETOWN` 不受影响 |
| `/proc/self/maps`、`/proc/version` 可读 | — | 原书 `t_readv.c` 需要「一个够长、一个够短」的两个文件，用它们正好（`248/248` vs `248/219`） |
| `/proc/*` 只读 | `t_truncate /proc/version 10` → `EACCES` | 正好演示原书 `t_truncate` 的失败路径 |
| **管道默认容量 65536**，但可改 | `F_GETPIPE_SZ=65536`；`F_SETPIPE_SZ(4096)` 生效 | 5.7 / 5.9 测「写满」时必须显式设容量，否则要准备 64 KiB 数据才触发 `EAGAIN` |
| `sizeof(struct stat) = 144` | — | 原书 `t_readv.c` 的 `totRequired = sizeof(struct stat) + 100` = **248**，就是上面那个数字的来源 |
| `sysconf(_SC_IOV_MAX) = 1024` | — | 与 `include/uapi/linux/uio.h:28` 的 `UIO_MAXIOV` 一致 |
| `/tmp` 是 **tmpfs** 且支持 `O_TMPFILE` | `tmpfile()` 显示 `/tmp/#4 (deleted)` | 5.12 走的是 `__gen_tempfd()` 第一条路，**没**走「`mkstemp`+`unlink`」那条退路 |
| 沙箱每次都是**全新容器** | inode 号从低值开始 | `#4`/`#5` 这类 inode 号在沙箱里稳定，但**换环境就会变**，不要当常量写进断言 |

## HFT / 嵌入式关联

| 要点 | 兑现 |
|------|------|
| **`O_APPEND` 是唯一的原子追加** | 多进程/多线程写同一份日志、同一份 tape，只有它保证不丢（实测丢 8236 字节 vs 一个不丢）。自己 `lseek(SEEK_END)+write` 一定出事 |
| **`pread`/`pwrite` 是并发读写的正解** | 行情快照文件、共享内存落盘文件，多线程各读各的区间；`lseek+read` 会被别的线程改掉共享游标 |
| **`O_NONBLOCK` + `epoll` 是事件驱动的底座** | 网络/管道/串口全部走这条路。要分清 `EAGAIN`（现在没数据，**重试**）和 `EINTR`（被信号打断，**重试**）——两者处理相似但成因不同 |
| **`ftruncate` 是「预分配」的对偶** | 日志轮转要 `ftruncate(fd, 0)` 而不是 `unlink`，因为别的进程还握着 fd（[5.11](5.11-dev-fd.md)）；反过来「先 `ftruncate` 撑大再写」得到的是**洞**，物理不占空间但读出来全是 0 |
| **`IOV_MAX = 1024` 是硬上限** | 批量收发（`sendmsg`/`recvmsg` 同样受限）时不能无限堆段；超了要自己分批 |
| **`O_CLOEXEC` 防 fd 泄漏** | 长跑进程 `fork+exec` 拉起子工具（风控脚本、上报器）时，不设 `O_CLOEXEC` 会把行情 fd 泄露给子进程，子进程持有期间老文件删不掉、端口关不了 |
| **`mkstemp` 是原子写配置的唯一正确开头** | 「`mkstemp` 同目录 → 写 → `fsync` → `rename`」。崩溃只会留孤儿临时文件，**永不出现半写配置**——这是嵌入式设备最怕的场景 |
| **嵌入式 `/tmp` 是 tmpfs** | 重启即消失、不需要清理任务；但容量 = 内存，写大文件要盯 `ENOSPC`。掉电丢失是特性不是 bug |
| **`RLIMIT_FSIZE` 在嵌入式上常被设死** | 5.10 的杀手不是 `off_t` 而是 rlimit；设备上写日志/录制要显式检查 `ulimit -f`，否则被 `SIGXFSZ` 静默杀掉 |
| **`/proc/PID/fd` 是排障第一手段** | 没有 `strace` 的嵌入式环境里，`readlink /proc/PID/fd/*` 能直接看出「这个进程握着哪些设备节点、哪些是匿名 `O_TMPFILE` 对象（显示 `#N`）」 |
| **`O_DIRECT` 要绕着走** | `F_SETFL` 能设它（在 `SETFL_MASK` 里），但**缓冲区必须按块对齐**，否则 `EINVAL`。HFT 想绕页缓存，优先考虑 `mmap` 或 `io_uring` 而不是裸 `O_DIRECT` |

<summary>代码自测（Q&A）</summary>

**Q1：本章所有「反直觉」能不能用一句话概括？**
A：能——**先问「我动的是三层里的哪一层」**。动 fd 表 → 只影响一个 fd（`FD_CLOEXEC`）；动 `struct file` → 影响所有共享它的 fd（`dup`/`fork`，包括偏移和状态标志）；动 inode → 影响所有打开者（`truncate`、`unlink` 减链接数）。

**Q2：为什么 `F_SETFL` 改不动 `O_CREAT`，而且还不报错？**
A：`setfl()` 只认 `SETFL_MASK`（`fs/fcntl.c:35`：`O_APPEND \| O_NONBLOCK \| O_NDELAY \| O_DIRECT \| O_NOATIME`），其余位在 `filp->f_flags = (arg & SETFL_MASK) \| (filp->f_flags & ~SETFL_MASK)`（`:81`）里被**悄悄丢掉**。而且 `O_CREAT/O_EXCL/O_NOCTTY/O_TRUNC` 在 `do_dentry_open()` 里就已经被清掉（`fs/open.c:945`），它们本来就是「`open` 时的一次性开关」，不是持续状态。

**Q3：`O_ASYNC` 为什么在普通文件上设不上？**
A：因为 `FASYNC` 不在 `SETFL_MASK` 里，它由 `file_operations->fasync` 钩子负责设。`fs/fcntl.c:71` 的注释原话：「`->fasync() is responsible for setting the FASYNC bit.`」普通文件没有这个钩子 → 静默失败；管道有（`fs/pipe.c:1230` `.fasync = pipe_fasync`）→ 生效（实测 `0x02000`）。

**Q4：`dup` 出的两个 fd，哪些东西共享、哪些不共享？**
A：**共享**：偏移 `f_pos`、状态标志 `f_flags`（因为都在 `struct file` 里）。**不共享**：`FD_CLOEXEC`（在 fd 表项里）。实测：对 dup-fd 设 `O_APPEND`，原 fd 的 `F_GETFL` 一起变 `0x08401`；但只对 fd2 设 `FD_CLOEXEC`，fd1 的 `F_GETFD` 仍是 `0x0`。

**Q5：`dup2(a, a)` 和 `dup3(a, a, 0)` 为什么结果不同？**
A：`dup2` 对 `old == new` 有专门的特例处理（`fs/file.c:1273-1282`：只校验 `old` 有效，然后原样返回，不关也不复制）；`dup3` 是 Linux 特化版，在 `fs/file.c:1241-1242` 直接 `-EINVAL`。实测：`dup2(fd,fd) -> 3`，`dup3(fd,fd,0) -> -1 EINVAL`。

**Q6：什么时候必须用 `pread` 而不是 `lseek`+`read`？**
A：多线程/多进程共享同一个 fd 时。`pread` 走 `fdget()`（不加 pos，`fs/read_write.c:661`）并把偏移当**参数**传下去，所以不碰共享游标；`ksys_read` 走 `fdget_pos()` 并在 `:615` 回写 `f_pos`。实测同一个 fd 上并发读 `[0,3)/[5,8)/[10,13)` 三段，`f_pos` 始终是 `10`。

**Q7：`truncate` 和 `ftruncate` 的失败原因为什么不一样？**
A：`truncate` 按**路径**走，要先过 `inode_permission(MAY_WRITE)` → 权限不足是 `EACCES`；`ftruncate` 按 **fd** 走，权限在 `open` 时就检查过了，所以它只在 `!S_ISREG \|\| !FMODE_WRITE` 时报 `EINVAL`（`fs/open.c:179`）。实测：只读 fd 上 `ftruncate` → `errno=22`；`t_truncate /proc/version` → `EACCES`。

**Q8：`ftruncate` 把文件撑大之后，多出来的部分占磁盘吗？**
A：**不占**。逻辑长度 `st_size` 涨了，物理 `st_blocks` 不涨——那一段是**洞**，读出来全是 0 但没分配块。实测：撑到 8192 时物理仍是 4096；而真写 4096 个 0 之后物理变成 8192，**同样 8192 逻辑长度，物理差两倍**。

**Q9：`EAGAIN` 和 `EINTR` 怎么区分处理？**
A：成因不同：`EAGAIN` = 非阻塞模式下「现在没数据/没空间」，是**正常状态**；`EINTR` = 慢系统调用被信号打断，是**外部事件**。两者都该重试，但 `EINTR` 要额外考虑 `SA_RESTART`（设了会自动重启，见 5.9 的对照表）。实测：空管道非阻塞读 → `11`；清掉 `O_NONBLOCK` 后被 `SIGALRM` 打断 → `4`。

**Q10：`open("/dev/fd/N")` 到底等不等于 `dup(N)`？**
A：**Linux 上不等价**。`/dev/fd` 只是指向 `/proc/self/fd` 的符号链接，而 `/proc/self/fd/N` 是一个「符号链接到实际文件」的 magic link，`proc_fd_link()` 只复制 `f_path`（`fs/proc/fd.c:181-182`），后续 `open` 会创建**全新的 `struct file`**。实测：经由它读 4 字节后，原 fd 的 `f_pos` 仍是 `0`（`dup` 的话会变成 4）。

**Q11：`mkstemp` 的原子性、`0600`、模板改写分别来自哪一行？**
A：全在 `try_file()`（`sysdeps/posix/tempname.c:174-181`）：`O_CREAT\|O_EXCL` 提供原子性、`S_IRUSR\|S_IWUSR` 提供 `0600`；模板改写来自 `__gen_tempname(..., 6)` 的最后一个参数 6（`:333-336`），它替换掉末尾 6 个 X。

**Q12：`tmpfile()` 为什么会显示 `/tmp/#4 (deleted)`？**
A：因为它走的是 `O_TMPFILE` 而不是「`mkstemp`+`unlink`」（`stdio-common/tmpfile.c:45` 先试 `__gen_tempfd`，Linux 实现是 `open(P_tmpdir, O_RDWR\|O_TMPFILE\|O_EXCL, 0600)`）。`#4` 由 `d_tmpfile()` 写（`fs/dcache.c:3259-3260`：`sprintf(d_name, "#%llu", i_ino)`），`(deleted)` 由 `d_path()` 追加（`fs/d_path.c:287-288`）。`nlink` 在 `:3253` 被直接减到 0——它**从来没有过名字**。

**Q13：沙箱里为什么造不出真正的 4 GiB 大文件？**
A：因为 `RLIMIT_FSIZE` 被限成 16 MiB（soft = hard = `16777216`）。`lseek` 到 4 GiB 是成功的（`4294967296`），但 `write` 会先收到 `SIGXFSZ`（默认动作杀进程），装了 handler 之后得到 `errno=27 (EFBIG)`。真实机器上 `ulimit -f unlimited` 就能写出来。**这条恰好证明了「拦你的是 rlimit，不是 `off_t` 宽度」**。

**Q14：`F_SETFL(fd, O_DIRECT)` 能设上吗？**
A：能在 `setfl()` 里设上（`O_DIRECT` 在 `SETFL_MASK` 里），但有个硬前提：`fs/fcntl.c:60-63` 对**非 FIFO 文件**校验 `f_op->check_flags`，文件系统支持才放行，否则 `-EINVAL`。另外 `O_DIRECT` 真正的痛点在**缓冲区必须按块对齐**，设上了也可能在 `read`/`write` 时 `EINVAL`。
