## 本节讲什么

「大文件」指超过 32 位偏移表示范围（约 2GB）的文件。本节回答三个问题：

1. 32 位 `off_t` 的上限到底是多少？为什么是「约 2GB」？
2. 如何让程序支持大文件？`_FILE_OFFSET_BITS=64` 做了什么？
3. 内核侧为什么有 `*64` 系列 syscall 和 `O_LARGEFILE`？

---

## 1. 问题根源：32 位 `off_t`

历史上 `off_t` 是 32 位**有符号**整数，可表示范围约 **−2GB ~ +2GB**（精确是 −2³¹ ~ 2³¹−1 字节）。于是：

- 32 位 `off_t` 的文件最大只能到 **2GB − 1**（约 2.1 GB）；
- 超过 2GB 的文件，`lseek` 定位、`truncate` 设置大小都会溢出。

32 位平台上，老代码需要「显式开启」大文件支持（LFS，Large File Support）；64 位平台（如 x86-64/aarch64）默认 `off_t` 就是 64 位，无需特别处理。

## 2. 开启大文件支持

| 做法 | 说明 |
|------|------|
| **推荐**：`-D_FILE_OFFSET_BITS=64` | 编译期把 `off_t` 及相关函数（`lseek`→`lseek64` 等）自动切到 64 位版本 |
| 备选：`off64_t` / `open64` / `lseek64` / `pread64` | 显式调用 64 位版本函数 |

```c
#define _FILE_OFFSET_BITS 64   /* 或编译时 gcc -D_FILE_OFFSET_BITS=64 */
#include <fcntl.h>
#include <unistd.h>
/* 之后 off_t 自动为 64 位，lseek 等自动映射到 64 位版本 */
```

## 3. 内核侧：`*64` syscall 与 `O_LARGEFILE`

内核为兼容 32 位用户态，提供了 64 位偏移的 syscall，并在 32 位进程打开大文件时要求 `O_LARGEFILE` 标志：

```
用户态 lseek(fd, huge_offset, SEEK_SET)
      ▼  （_FILE_OFFSET_BITS=64 时 glibc 转调 lseek64）
SYSCALL_DEFINE3(lseek)                    fs/read_write.c:311（off_t 在 64 位内核里本就是 64 位）

truncate 的 LFS 版本：
SYSCALL_DEFINE2(truncate64)               fs/open.c:217
SYSCALL_DEFINE2(ftruncate64)              fs/open.c:222
```

`do_sys_ftruncate`（`fs/open.c:157`）里的大文件判定：

```c
if (f.file->f_flags & O_LARGEFILE)
    small = 0;                          /* 以 O_LARGEFILE 打开，按大文件处理 */
...
if (small && length > MAX_NON_LFS)      /* 未开 LFS 且超 2GB → -EINVAL */
    goto out_putf;
```

要点：32 位程序若不设 `_FILE_OFFSET_BITS=64`（即 `small=1`），`ftruncate` 超过 `MAX_NON_LFS`（2GB−1）会失败。设了 `_FILE_OFFSET_BITS=64` 后，glibc 自动带上 `O_LARGEFILE`，`small=0`，即可操作大文件。

## 4. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| 大行情/回测数据文件 | 历史行情文件轻松超 2GB，`_FILE_OFFSET_BITS=64` 是编译标配 |
| 跨 32 位平台移植 | 嵌入式 32 位 ARM 上操作大文件必须显式开 LFS，否则静默失败 |
| 随机定位 | 64 位 `off_t` 保证 `lseek`/`pread` 到任意偏移不溢出 |

## 5. 代码示例

```c
#define _FILE_OFFSET_BITS 64
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

/* 编译: gcc -D_FILE_OFFSET_BITS=64 lfs_demo.c */
int main(void) {
    printf("sizeof(off_t) = %zu\n", sizeof(off_t));   /* 应为 8 */

    int fd = open("/tmp/bigfile.dat", O_WRONLY | O_CREAT, 0644);
    off_t target = (off_t)5 * 1024 * 1024 * 1024;     /* 5 GB */
    lseek(fd, target, SEEK_SET);
    write(fd, "x", 1);                               /* 空洞文件 */

    off_t size = lseek(fd, 0, SEEK_END);
    printf("文件大小: %lld bytes (%.1f GB)\n",
           (long long)size, (double)size / (1024.0 * 1024 * 1024));
    close(fd);
    return 0;
}
```

<details>
<summary>代码自测（Q&A）</summary>

**Q1：32 位 `off_t` 的文件大小上限是多少？**
A：约 **2GB − 1 字节**（精确是 2³¹−1 = 2147483647 字节）。因为 32 位有符号整数范围是 −2³¹ ~ 2³¹−1。超过此大小的文件在 32 位偏移下无法正确定位。

**Q2：`_FILE_OFFSET_BITS=64` 做了什么？**
A：编译期宏，让 `off_t` 变为 64 位，并把 `lseek`、`pread`、`pwrite`、`truncate` 等函数**自动映射**到 64 位版本（`lseek64`/`pread64`/`truncate64`…），同时让 `open` 带上 `O_LARGEFILE`。这样源码不用改，重新编译即可支持大文件。

**Q3：`off64_t` / `open64` / `lseek64` 和 `_FILE_OFFSET_BITS=64` 是什么关系？**
A：前者是**显式**的 64 位 API（函数名带 `64`），后者是**自动映射**（源码不改成 `64` 名字，编译器自动切）。推荐用 `_FILE_OFFSET_BITS=64`，代码可移植、无需 `#ifdef`。

**Q4：32 位程序不开 LFS，`ftruncate` 超过 2GB 会怎样？**
A：返回 `-1`，`errno = EINVAL`。`do_sys_ftruncate` 里 `if (small && length > MAX_NON_LFS) goto out_putf;`——`small=1`（未开 `O_LARGEFILE`）且长度超 2GB 直接拒绝。

**Q5：64 位平台（x86-64/aarch64）还需要 `_FILE_OFFSET_BITS=64` 吗？**
A：通常**不需要**，64 位平台默认 `off_t` 就是 64 位，`lseek` 等天然支持大文件。但为了**可移植性**（代码可能编到 32 位平台），显式加 `_FILE_OFFSET_BITS=64` 是稳妥习惯。

</details>
