## 本节讲什么

「大文件」指**超过 2 GiB** 的文件（32 位 `off_t` 的表示极限）。本节回答五个问题：

1. 32 位时代为什么要 LFS API？现在还需要吗？
2. `_FILE_OFFSET_BITS=64` 到底做了什么（**它必须放在哪一行**）？
3. 64 位系统上「打开大文件」已经天然成立——那么**真正会拦住你的是什么**？
4. 为什么超限 `write` 是「**先收到 `SIGXFSZ` 被杀**」，而不是直接返回 `EFBIG`？
5. `F_GETFL` 里那个 `0x8000`（`O_LARGEFILE`）为什么在 glibc 的宏里是 **0**？（Ch4 遗留之谜的答案）

---

## 1. 两个时代的做法

| 年代 | 做法 | 问题 |
|------|------|------|
| 32 位时代的 LFS API | 显式用 `open64()` / `lseek64()` / `off64_t`（需要 `_LARGEFILE64_SOURCE`） | 代码里到处是 `64` 后缀，接口不通用 |
| **现代推荐做法** | 编译期加 `#define _FILE_OFFSET_BITS 64`，然后**照常写 `open` / `lseek` / `off_t`** | 无（编译器替你换成 64 位版本） |

`_FILE_OFFSET_BITS=64` 是**编译期重定向**：它让 glibc 把 `off_t` 定义成 8 字节的 `off64_t`，并把 `open`/`lseek`/`truncate` 等符号重定向到 `*64` 版本。**同一份源码，在 32 位平台上也能处理大文件。**

> **踩坑前提**：`#define _FILE_OFFSET_BITS 64`（以及任何 `_*_SOURCE` 特性宏）**必须出现在任何头文件之前**。本仓库把 `tlpi_hdr.h` 拼在源码前面的编译模型下，原书 `large_file.c` 里的 `#define _LARGEFILE64_SOURCE`（源码第 17 行）就来不及生效——必须改用编译旗标 `-D_LARGEFILE64_SOURCE=`。**这不是书上的坑，是本仓库编译模型的坑**，详见第 4 节。

## 2. 64 位系统上的现实

在 x86-64 上：

| 事实 | 值 |
|------|----|
| `sizeof(off_t)` | **8** 字节（实测） |
| `sizeof(long)` | **8** 字节 |
| `MAX_NON_LFS` | `((1UL<<31) - 1)` = 2 GiB − 1（`include/linux/fs.h:1048`） |

所以**「能不能表示 4 GiB 的偏移」这个问题在 64 位平台上不存在**——`off_t` 本来就够宽。真正会拦住你的是**别的两样东西**：

| 拦路者 | 表现 | 源码 |
|--------|------|------|
| `RLIMIT_FSIZE`（`ulimit -f`） | 写超限 → **`SIGXFSZ`**（默认杀进程）；装了 handler 才拿到 `EFBIG` | `fs/read_write.c:1633-1639` |
| `O_LARGEFILE` 未设（32 位） | 长度超 `MAX_NON_LFS` → `EFBIG`；打开已超限的文件 → `EOVERFLOW` | `fs/read_write.c:1643-1647`、`fs/open.c:1622-1623` |

## 3. 代码：五段实测

完整源码 [`code/c5_10_large_files.c`](../code/c5_10_large_files.c)：

```c
/* c5_10_large_files.c — §5.10 大文件：off_t 不够宽会怎样，以及 RLIMIT_FSIZE
 *
 * 32 位 off_t 最大表示到 2 GiB - 1。要碰更大的文件有两种办法：
 *   1) 编译期 #define _FILE_OFFSET_BITS 64 —— 把 off_t 悄悄换成 64 位（推荐）
 *   2) 用显式的 LFS API：open64() / lseek64() / off64_t（已过时）
 * 在 64 位系统上 off_t 本来就是 8 字节，所以"打开大文件"这件事天然成立——
 * 真正会拦住你的是别的东西：**RLIMIT_FSIZE**。
 *
 * 本 demo 演示五件事：
 *   1) 编译期事实：sizeof(off_t) / sizeof(long) / _FILE_OFFSET_BITS
 *   2) 运行时事实：RLIMIT_FSIZE（CE 沙箱里是 16 MiB）
 *   3) lseek() 到 4 GiB 是允许的，而且**不会**让文件变大（游标不等于文件大小）
 *   4) 在超限位置 write()：默认动作是收到 SIGXFSZ 被杀；装了 handler 才是 EFBIG
 *   5) F_GETFL 里的 O_LARGEFILE（0x8000）是内核补的，不是你 open 时写的
 *
 * 编译: gcc -O0 -Wall -Wextra -o c5_10_large_files c5_10_large_files.c
 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/stat.h>
#include <sys/wait.h>
#include <unistd.h>
#include <errno.h>

#define FOUR_GB ((off_t) 4 * 1024 * 1024 * 1024)

/* 注意这里有个「错位」：x86-64 上 glibc 把 O_LARGEFILE 定义成 **0**
   （off_t 本来就是 64 位，用户态没什么要做的），而内核侧的位仍是 0x8000。
   下面两个宏分别代表两边，别混。 */
#ifndef O_LARGEFILE
#define O_LARGEFILE 0
#endif
#define KERNEL_O_LARGEFILE 0x8000

static volatile sig_atomic_t xfsz_hit = 0;

static void on_xfsz(int sig)
{
    (void) sig;
    xfsz_hit = 1;                       /* 只记一笔，系统调用本身会返回 EFBIG */
}

int main(void)
{
    const char *p = "/tmp/c5_large.bin";
    int fd;
    struct stat st;
    struct rlimit rl;

    printf("== 1. 编译期事实 ==\n");
    printf("    sizeof(off_t) = %zu 字节, sizeof(long) = %zu 字节\n",
           sizeof(off_t), sizeof(long));
    printf("    _FILE_OFFSET_BITS = %d（本文件里没自定义，看编译器默认）\n",
#ifdef _FILE_OFFSET_BITS
           _FILE_OFFSET_BITS
#else
           0
#endif
          );
    printf("    O_LARGEFILE 这个宏 = 0x%x\n", O_LARGEFILE);

    printf("\n== 2. 运行时事实：RLIMIT_FSIZE ==\n");
    if (getrlimit(RLIMIT_FSIZE, &rl) == 0)
        printf("    soft = %lld   hard = %lld（字节）\n",
               (long long) rl.rlim_cur, (long long) rl.rlim_max);
    printf("    超过这个大小写文件，内核会先发 SIGXFSZ，再让 write 返回 EFBIG\n");

    fd = open(p, O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) {
        perror("open");
        return 1;
    }
    write(fd, "small", 5);

    printf("\n== 3. lseek() 到 4 GiB：允许，且文件不会变大 ==\n");
    {
        off_t o = lseek(fd, FOUR_GB, SEEK_SET);

        printf("    lseek(fd, 4 GiB, SEEK_SET) -> %lld\n", (long long) o);
        fstat(fd, &st);
        printf("    此时 st_size = %lld（还是 5）、st_blocks*512 = %lld\n",
               (long long) st.st_size, (long long) st.st_blocks * 512);
        printf("    f_pos 是「游标」，不是「文件长度」——两者可以差很远\n");
    }

    printf("\n== 4. 在 4 GiB 处 write(). 两条路 ==\n");
    printf("  (a) 不处理 SIGXFSZ（默认动作 = 杀进程）：\n");
    fflush(stdout);
    {
        pid_t pid = fork();

        if (pid == 0) {
            signal(SIGXFSZ, SIG_DFL);       /* 子进程用默认动作 */
            if (write(fd, "test", 4) == -1)
                _exit(1);
            _exit(0);
        } else if (pid > 0) {
            int status = 0;

            waitpid(pid, &status, 0);
            if (WIFSIGNALED(status))
                printf("      子进程被信号 %d (%s) 杀死\n",
                       WTERMSIG(status), strsignal(WTERMSIG(status)));
            else if (WIFEXITED(status))
                printf("      子进程正常退出，code=%d\n", WEXITSTATUS(status));
        }
    }

    printf("  (b) 装上 SIGXFSZ 处理函数：write 自己返回 EFBIG\n");
    {
        struct sigaction sa;

        memset(&sa, 0, sizeof sa);
        sa.sa_handler = on_xfsz;
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = 0;
        sigaction(SIGXFSZ, &sa, NULL);

        errno = 0;
        ssize_t n = write(fd, "test", 4);

        printf("      write -> %ld errno=%d (%s)，handler 被调用 = %d\n",
               (long) n, errno, strerror(errno), (int) xfsz_hit);
        fstat(fd, &st);
        printf("      文件没被写脏：st_size = %lld（还是 5）\n", (long long) st.st_size);
    }

    printf("\n== 5. O_LARGEFILE：glibc 的宏是 0，内核的位是 0x8000 ==\n");
    printf("    glibc 的 O_LARGEFILE 宏        = 0x%x\n", (int) O_LARGEFILE);
    printf("    内核侧的位 (F_GETFL & 0x8000)  = %d\n",
           !!(fcntl(fd, F_GETFL) & KERNEL_O_LARGEFILE));
    printf("    F_GETFL = 0x%05x\n", fcntl(fd, F_GETFL));
    printf("    两边不一致不是 bug：用户态这个宏在 x86-64 上被定成 0（没事可做），\n");
    printf("    内核侧的 0x8000 由 fs/open.c 自己补，所以在 F_GETFL 里看得见、\n");
    printf("    在 glibc 的宏里看不见 —— 这个错位正是 Ch4 里 0x8000 之谜的答案\n");

    close(fd);
    unlink(p);
    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c5_10_large_files c5_10_large_files.c && ./c5_10_large_files
```

CE（gcc 13.3.0 / x86-64 / Ubuntu 24.04）实测：

```text
== 1. 编译期事实 ==
    sizeof(off_t) = 8 字节, sizeof(long) = 8 字节
    _FILE_OFFSET_BITS = 0（本文件里没自定义，看编译器默认）
    O_LARGEFILE 这个宏 = 0x0

== 2. 运行时事实：RLIMIT_FSIZE ==
    soft = 16777216   hard = 16777216（字节）
    超过这个大小写文件，内核会先发 SIGXFSZ，再让 write 返回 EFBIG

== 3. lseek() 到 4 GiB：允许，且文件不会变大 ==
    lseek(fd, 4 GiB, SEEK_SET) -> 4294967296
    此时 st_size = 5（还是 5）、st_blocks*512 = 4096
    f_pos 是「游标」，不是「文件长度」——两者可以差很远

== 4. 在 4 GiB 处 write(). 两条路 ==
  (a) 不处理 SIGXFSZ（默认动作 = 杀进程）：
      子进程被信号 25 (File size limit exceeded) 杀死
  (b) 装上 SIGXFSZ 处理函数：write 自己返回 EFBIG
      write -> -1 errno=27 (File too large)，handler 被调用 = 1
      文件没被写脏：st_size = 5（还是 5）

== 5. O_LARGEFILE：glibc 的宏是 0，内核的位是 0x8000 ==
    glibc 的 O_LARGEFILE 宏        = 0x0
    内核侧的位 (F_GETFL & 0x8000)  = 1
    F_GETFL = 0x08002
    两边不一致不是 bug：用户态这个宏在 x86-64 上被定成 0（没事可做），
    内核侧的 0x8000 由 fs/open.c 自己补，所以在 F_GETFL 里看得见、
    在 glibc 的宏里看不见 —— 这个错位正是 Ch4 里 0x8000 之谜的答案
```

逐条看：

| 观察 | 说明 |
|------|------|
| `sizeof(off_t) = 8`、`O_LARGEFILE 宏 = 0x0` | 两个关键事实同时拿到：`off_t` 已经够宽，而**这个宏在你的源码里就是「没东西」** |
| `RLIMIT_FSIZE` soft = hard = **16777216**（16 MiB） | 这是 CE 沙箱的限制。它才是本 demo 里真正拦住 4 GiB 写入的那道墙——**不是 `off_t` 宽度** |
| `lseek(fd, 4 GiB, SEEK_SET)` → **4294967296** 成功 | 越过 2 GiB 的偏移**可以**定位。但 `st_size` 还是 5——**游标 ≠ 文件长度** |
| 4 GiB 处 `write`，不处理 `SIGXFSZ` | 子进程**被信号 25 杀死**（`File size limit exceeded`）。这是 `fs/read_write.c:1637` 的 `send_sig(SIGXFSZ, current, 0)` 生效 |
| 4 GiB 处 `write`，装了 handler | `write` 返回 `-1 errno=27 (EFBIG)`，handler 被调用 **1** 次。文件**没被写脏**（`st_size` 仍是 5） |
| glibc 宏 `0x0` vs `F_GETFL` 里的 `0x8000` | 见第 5 节——这是**用户态与内核态对同一个概念的两种表达**，不是 bug |

/* large_file.c

   Demonstrate the use of the (obsolete) Large File System API.

   This program is Linux-specific.
*/
#define _LARGEFILE64_SOURCE
#include <sys/stat.h>
#include <fcntl.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int fd;
    off64_t off;

    if (argc != 3 || strcmp(argv[1], "--help") == 0)
        usageErr("%s pathname offset\n", argv[0]);

    fd = open64(argv[1], O_RDWR | O_CREAT, S_IRUSR | S_IWUSR);
    if (fd == -1)
        errExit("open64");

    off = atoll(argv[2]);
    if (lseek64(fd, off, SEEK_SET) == -1)
        errExit("lseek64");

    if (write(fd, "test", 4) == -1)
        errExit("write");
    exit(EXIT_SUCCESS);
}

它用的是**已被淘汰的显式 LFS API**——源码第 13 行的自述就是 `Demonstrate the use of the (obsolete) Large File System API.`，关键三行：

```c

off = atoll(argv[2]);

```

CE 实测（exit code = 153）：

```text
Program terminated with signal SIGXFSZ (25)
```

**为什么没有 `EFBIG` 的输出？** 因为这个程序**没有装 `SIGXFSZ` 处理函数**，默认动作是终止进程——它在 `write` 返回之前就死了。这正是「必须先处理信号，才能看到 `EFBIG`」的现场演示。

> **为什么要写 `-D_LARGEFILE64_SOURCE=` 而不是靠源码里的 `#define`？** 原书源码第 17 行确实有 `#define _LARGEFILE64_SOURCE`，但本仓库的编译模型是「`tlpi_hdr.h` 拼在源码之前」，特性宏来不及生效 → 出现 13 条 `unknown type name 'off64_t'` 诊断。**改旗标、不改逐字镜像的源码**是本仓库处理这类冲突的统一做法；写成 `NAME=`（空值）与源码里的空定义完全一致，**不触发重定义告警**。

完整的**习题 5-1 解答**（改用标准接口 + `off_t` + `_FILE_OFFSET_BITS=64`）见 [`code/ex5_1_large_file_offset_bits.c`](../code/ex5_1_large_file_offset_bits.c)，实测：

```text
== 习题 5-1：标准接口 + _FILE_OFFSET_BITS=64 ==
    _FILE_OFFSET_BITS = 64
    sizeof(off_t) = 8 字节（32 位平台默认 4；靠上面的宏变 8）
    RLIMIT_FSIZE soft=16777216 hard=16777216

    请求偏移 = 4294967296（4 GiB 的 off_t 只有 8 字节类型才装得下）
    lseek -> 4294967296 成功
    write -> -1 errno=27 (File too large)，SIGXFSZ handler=1
    ↑ 拦住它的是 RLIMIT_FSIZE（沙箱 16 MiB），不是 off_t 宽度
      在真实机器上把 ulimit -f 放开，这一步就能写出真正的大文件
```

**这一段的结论最重要**：在 64 位平台上，`_FILE_OFFSET_BITS=64` 只是「确认」而非「改变」——`off_t` 早就是 8 字节（`sizeof(off_t) = 8`）。**拦住你的永远是 `RLIMIT_FSIZE`。**

## 5. `0x8000` 之谜：两端各自怎么定义

这是本仓库从 Ch4 一路带过来的疑问：`F_GETFL` 里多出来的 `0x8000` 是什么？答案要分**内核侧**和**用户态侧**两份源码才说得清。

**内核侧**（`fs/open.c`）——`open` 入口自己补上：

```c
/* ex5_1_large_file_offset_bits.c — 原书习题 5-1
 *
 * 题目（逐字）：
 *   Modify the program in listing 5-3 to use standard file I/O system
 *   calls (open() and lseek()) and the off_t data type.  Compile the
 *   program with the _FILE_OFFSET_BITS macro set to 64, and test it to
 *   show that a large file can be successfully created.
 *
 * 原书 Listing 5-3（large_file.c）用的是**显式 LFS API**：open64()/lseek64()/off64_t。
 * 本题要求改成标准接口 + off_t，靠编译期宏 _FILE_OFFSET_BITS=64 把 off_t 悄悄换成
 * 64 位——这样同一份源码在 32 位平台上也能处理大文件。
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex5_1_large_file_offset_bits ex5_1_large_file_offset_bits.c
 */
#define _FILE_OFFSET_BITS 64        /* 关键：让 off_t / lseek / open 全部走 64 位 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <unistd.h>
#include <errno.h>

static volatile sig_atomic_t xfsz = 0;

static void on_xfsz(int sig)
{
    (void) sig;
    xfsz = 1;
}

int main(int argc, char *argv[])
{
    const char *path;
    off_t off;
    int fd;
    struct rlimit rl;

    if (argc != 3) {
        fprintf(stderr, "Usage: %s pathname offset\n", argv[0]);
        return 1;
    }
    path = argv[1];
    off = (off_t) atoll(argv[2]);

    printf("== 习题 5-1：标准接口 + _FILE_OFFSET_BITS=64 ==\n");
    printf("    _FILE_OFFSET_BITS = %d\n", _FILE_OFFSET_BITS);
    printf("    sizeof(off_t) = %zu 字节（32 位平台默认 4；靠上面的宏变 8）\n",
           sizeof(off_t));
    if (getrlimit(RLIMIT_FSIZE, &rl) == 0)
        printf("    RLIMIT_FSIZE soft=%lld hard=%lld\n",
               (long long) rl.rlim_cur, (long long) rl.rlim_max);

    fd = open(path, O_RDWR | O_CREAT, S_IRUSR | S_IWUSR);
    if (fd == -1) {
        perror("open");
        return 1;
    }

    printf("\n    请求偏移 = %lld（4 GiB 的 off_t 只有 8 字节类型才装得下）\n",
           (long long) off);
    if (lseek(fd, off, SEEK_SET) == (off_t) -1) {
        perror("lseek");
        return 1;
    }
    printf("    lseek -> %lld 成功\n", (long long) lseek(fd, 0, SEEK_CUR));

    /* 装个 handler，好让超限时 write 返回 EFBIG 而不是把进程杀掉 */
    {
        struct sigaction sa;

        memset(&sa, 0, sizeof sa);
        sa.sa_handler = on_xfsz;
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = 0;
        sigaction(SIGXFSZ, &sa, NULL);
    }

    errno = 0;
    {
        ssize_t n = write(fd, "test", 4);

        if (n == -1) {
            printf("    write -> -1 errno=%d (%s)，SIGXFSZ handler=%d\n",
                   errno, strerror(errno), (int) xfsz);
            printf("    ↑ 拦住它的是 RLIMIT_FSIZE（沙箱 16 MiB），不是 off_t 宽度\n");
            printf("      在真实机器上把 ulimit -f 放开，这一步就能写出真正的大文件\n");
        } else {
            printf("    write -> %ld 字节，文件创建成功\n", (long) n);
        }
    }

    close(fd);
    return 0;
}
```

**用户态侧**（glibc 2.39）——宏的值是 **0**，而且是分两层定出来的：

```c
/* sysdeps/unix/sysv/linux/x86/bits/fcntl.h:23-25 */
#ifdef __x86_64__
# define __O_LARGEFILE  0
#endif
/* sysdeps/unix/sysv/linux/x86/bits/fcntl.h:27-28 */
#ifdef __x86_64__
/* Not necessary, we always have 64-bit offsets.  */
# define F_GETLK64      5
```

```c
/* sysdeps/unix/sysv/linux/bits/fcntl-linux.h:74-76 —— 其他平台才用这个值 */
#ifndef __O_LARGEFILE
# define __O_LARGEFILE  0100000        /* = 0x8000，与内核位一致 */
#endif

/* sysdeps/unix/sysv/linux/bits/fcntl-linux.h:137-139 —— 宏的开关 */
#ifdef __USE_LARGEFILE64
# define O_LARGEFILE __O_LARGEFILE
#endif
```

把这条链读通，就得到完整解释：

| 问题 | 答案 |
|------|------|
| 内核里的 `O_LARGEFILE` 位是什么？ | `0x8000`（`fs/open.c:1444` 补，`F_GETFL` 里能看到） |
| glibc 的 `O_LARGEFILE` 宏为什么是 `0`？ | x86-64 的 `bits/fcntl.h:23-25` 把它定成 `0`，理由就在同文件 `:28` 的注释：**`Not necessary, we always have 64-bit offsets.`** |
| 为什么不把宏定成 `0x8000`？ | 因为用户态**不需要**自己传这个位——内核按平台条件补（`force_o_largefile()`）。用户态设成非 0 反而会在 32 位上造成重复/冲突 |
| 宏是 `0` 为什么还能编译通过？ | 它是被**定义成 0**（不是「未定义」），所以 `F_GETFL & O_LARGEFILE` 这种表达式合法，只是恒为 0 |
| 为什么有时「找不到这个宏」？ | 它只在 `#ifdef __USE_LARGEFILE64` 时才被定义（`fcntl-linux.h:137-139`）。`_GNU_SOURCE` 会隐式打开 `_LARGEFILE64_SOURCE`，带了就能编过 |
| `__libc_open` 里有 LFS 逻辑吗？ | 在 x86-64 上**整块被 `#ifndef __OFF_T_MATCHES_OFF64_T` 排除**（`glibc_open.c:26` 开始、`:50` 的 `#endif` 收尾），64 位平台上根本不参与编译 |

> **一句话总账**：`0x8000` 是**内核**的位，`0` 是**用户态宏**的值。两者不一致不是 bug，而是「64 位平台上用户态什么都不用做」的正常表现。**别去 glibc 里找 `0x8000`，它在 `fs/open.c`。**

## 6. 常见坑

| 坑 | 说明 |
|------|------|
| 把 `_FILE_OFFSET_BITS 64` 写在 `#include` 之后 | 无效（或部分无效）。特性宏必须在**任何头文件之前** |
| 以为 64 位平台上还需要 LFS API | 不需要。`off_t` 已是 8 字节；`open64`/`lseek64` 属淘汰接口（原书源码注释自述 obsolete） |
| 以为 `lseek` 到 4 GiB 会立刻产生大文件 | 不会，`st_size` 不变（实测仍是 5）。**游标 ≠ 文件长度** |
| 不处理 `SIGXFSZ` 就往超限位置写 | 进程**直接被杀死**（实测 signal 25），连错误码都拿不到 |
| 装了 handler 就以为万事大吉 | handler 会**先被调用一次**，然后 `write` 才返回 `EFBIG`——两者都要处理 |
| 把 `RLIMIT_FSIZE` 和「磁盘空间」混为一谈 | `RLIMIT_FSIZE` 是**进程级资源限制**（`ulimit -f`），与磁盘剩余空间无关；`EFBIG` 也可能来自文件系统上限 `s_maxbytes`（`fs/read_write.c:1632`） |
| 32 位平台上忘了 `O_LARGEFILE` | 长度超 `MAX_NON_LFS`（2 GiB−1，`include/linux/fs.h:1048`）直接 `EFBIG`（`fs/read_write.c:1646-1647`） |
| 32 位平台上打开已超 2 GiB 的文件却没 `O_LARGEFILE` | `generic_file_open` 返回 `-EOVERFLOW`（`fs/open.c:1622-1623`）——**连打开都失败** |

## 7. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| 全量行情归档 | 单日 tick 数据动辄几十 GB。**必须**确认工具链没有 32 位 `off_t`——一句 `sizeof(off_t)` 静态断言是极廉价的保险 |
| 嵌入式 32 位 ARM | 大量嵌入式 SoC 仍是 32 位 → `_FILE_OFFSET_BITS=64` 不是「可选项」而是**必备**。忘加会在跨过 2 GiB 那一刻突然 `EOVERFLOW`/`EFBIG` |
| 交叉编译一致性 | `_FILE_OFFSET_BITS` 影响 `struct stat` 等结构的**大小与布局**（[5.6](5.6-pread-pwrite.md) 里 `sizeof(struct stat)=144` 就是这个结构）。宿主与目标不一致会出 ABI 问题 |
| 服务进程写日志 | 生产环境常设 `ulimit -f` 防「日志把盘写满」。此时**必须**处理 `SIGXFSZ`，否则进程被信号直接杀死（比「写失败」严重得多） |
| 信号安全性 | 低延迟路径上装 `SIGXFSZ` handler 要小心：信号会打断 syscall 引发 `EINTR`（[5.9](5.9-nonblocking-io.md)）。更稳的做法是**提前 `setrlimit` 自设上限并主动检查**，而不是等信号 |
| 文件系统上限 | `s_maxbytes`（`fs/read_write.c:1632`）是另一个天花板（某些 FS 单文件上限远小于磁盘容量）；`EFBIG` 可能来自它而非 `RLIMIT_FSIZE` |

<summary>代码自测（Q&A）</summary>

**Q1：`_FILE_OFFSET_BITS=64` 做了什么？**
A：它让 glibc 把 `off_t` 定义成 8 字节（`off64_t`），并把 `open`/`lseek`/`truncate` 等符号重定向到 64 位版本。**必须写在任何 `#include` 之前。** 在 64 位平台上 `off_t` 本来就是 8 字节，所以它主要是为 32 位平台准备的。

**Q2：64 位平台上，「大文件」还有障碍吗？**
A：有，但**不是 `off_t` 宽度**。实测 `sizeof(off_t) = 8`，`lseek` 到 4 GiB 直接成功（返回 `4294967296`）。真正的障碍是 `RLIMIT_FSIZE`（CE 沙箱 16 MiB，`fs/read_write.c:1633`）和文件系统的 `s_maxbytes`（`:1632`）。

**Q3：超过 `RLIMIT_FSIZE` 时 `write` 返回什么？**
A：**先收到 `SIGXFSZ`**（`fs/read_write.c:1637` 的 `send_sig(SIGXFSZ, current, 0)`）。若进程没装 handler，默认动作是**终止进程**（实测 `Program terminated with signal SIGXFSZ (25)`，exit code 153）。装了 handler 之后 `write` 才返回 `-1 errno=27 (EFBIG)`（`:1638`）。

**Q4：`lseek` 到 4 GiB 会立刻产生一个 4 GiB 的文件吗？**
A：不会。实测 `lseek(fd, 4 GiB, SEEK_SET)` 返回 `4294967296`，但 `st_size` 仍是 **5**。**游标是「下一次读写的起点」，不是「文件有多长」**（[4.7](../../chapter-04-file-io-universal/notes/4.7-lseek.md)）；要真的变长，要么再写数据、要么用 `ftruncate`（[5.8](5.8-truncate-ftruncate.md)）。

**Q5：glibc 的 `O_LARGEFILE` 宏为什么是 `0`？**
A：因为 x86-64 上 `sysdeps/unix/sysv/linux/x86/bits/fcntl.h:23-25` 把它定成 `0`，理由就在同文件 `:28` 的注释里：**`Not necessary, we always have 64-bit offsets.`** 用户态不需要自己传这个位——内核在 `open` 入口按平台条件补（`fs/open.c:1443-1444`）。

**Q6：那 `F_GETFL` 里的 `0x8000` 从哪来？**
A：来自内核：`if (force_o_largefile()) flags |= O_LARGEFILE;`（`fs/open.c:1443-1444`，`openat` 是 `:1451-1452`，`openat2` 是 `:1475-1476`）。它不是你传的，也不是 glibc 宏给的——**所以「`F_GETFL` 的返回值 ≠ 你传给 `open` 的 flags」**。

**Q7：`O_LARGEFILE` 为什么有时候「找不到这个宏」？**
A：因为它只在 `#ifdef __USE_LARGEFILE64` 时才被定义（`sysdeps/unix/sysv/linux/bits/fcntl-linux.h:137-139`）。`_GNU_SOURCE` 会隐式打开 `_LARGEFILE64_SOURCE`，所以带 `_GNU_SOURCE` 的代码能编过；不带就可能报「未声明」。

**Q8：32 位平台上，打开一个已经超过 2 GiB 的文件会怎样？**
A：`generic_file_open` 返回 `-EOVERFLOW`（`fs/open.c:1620-1623`）：`if (!(filp->f_flags & O_LARGEFILE) && i_size_read(inode) > MAX_NON_LFS) return -EOVERFLOW;`。**连打开都失败**，不只是写失败。
