## 本节讲什么

临时文件几乎每个程序都要用（编译中间产物、下载缓存、原子写配置、`sort` 的溢写盘）。但「怎么安全地建」是一道经典陷阱题——**建错了不是功能 bug，而是安全隐患**。本节回答四个问题：

1. `mkstemp` 的原子性到底从哪来？为什么它的模板会被**就地改写**、权限又一定是 `0600`？
2. `tmpfile()` 是什么东西的身影？（本节的实测会给出 `/tmp/#4 (deleted)` 这种奇怪路径——本节把这个 `#4` 追到内核源码）
3. `O_TMPFILE` 造出的「无名文件」怎么在**事后**获得名字？`O_EXCL` 在 `O_TMPFILE` 语境下为什么**不是**「已存在就失败」的意思？
4. `mktemp` / `tmpnam` 为什么被官方判了死缓（glibc 每次链接都给你吼一句 warning）？

---

## 1. 三个工具，一条血缘

| 接口 | 原型 | 返回 | 名字 | 消失时机 |
|------|------|------|------|---------|
| `mkstemp` | `int mkstemp(char *template)` | fd | **有**（模板被改写） | 得自己 `unlink` |
| `mkostemp` | `int mkostemp(char *template, int flags)` | fd | **有** | 得自己 `unlink` |
| `tmpfile` | `FILE *tmpfile(void)` | `FILE *` | **没有** | `fclose` 或进程退出 |
| `mkdtemp` | `char *mkdtemp(char *template)` | 目录名 | 有（目录） | 得自己 `rmdir` |

它们**共用同一个底层**：`__gen_tempname()`。glibc 的包装薄到只剩一行（`misc/mkstemp.c:30-34`）：

```c
int
mkstemp (char *template)
{
  return __gen_tempname (template, 0, 0, __GT_FILE);
}
```

`mkostemp` 只多了一个 `flags`（`misc/mkostemp.c:30-34`）：

```c
int
mkostemp (char *template, int flags)
{
  return __gen_tempname (template, 0, flags, __GT_FILE);
}
```

`mkdtemp` 唯一区别是 kind 换成 `__GT_DIR`（`misc/mkdtemp.c:26-33`）：

```c
char *
mkdtemp (char *template)
{
  if (__gen_tempname (template, 0, 0, __GT_DIR))
    return NULL;
  else
    return template;
}
```

最后一个参数 6 就是「末尾 6 个 X」的由来（`sysdeps/posix/tempname.c:333-336`）：

```c
int
__gen_tempname (char *tmpl, int suffixlen, int flags, int kind)
{
  return gen_tempname_len (tmpl, suffixlen, flags, kind, 6);
}
```

> `mktemp` 走的是另一条 kind：`__GT_NOCREATE`（`misc/mktemp.c:24-32`）——**它只挑名字，不创建**，所以后面必须再 `open`，也就必然有竞态窗口（见第 6 节）。

## 2. `mkstemp` 的原子性从哪来

真正干活的是 `try_file()`（`sysdeps/posix/tempname.c:174-181`）：

```c
static int
try_file (char *tmpl, void *flags)
{
  int *openflags = flags;
  return __open (tmpl,
                 (*openflags & ~O_ACCMODE)
                 | O_RDWR | O_CREAT | O_EXCL, S_IRUSR | S_IWUSR);
}
```

四个信息全在这一行里：

| 代码 | 含义 |
|------|------|
| `(*openflags & ~O_ACCMODE)` | 先**清掉**调用者传进来的访问模式（`O_ACCMODE` = `O_RDONLY\|O_WRONLY\|O_RDWR`），再 `\| O_RDWR` 强制成读写。这就是 man 说的「往 `mkostemp` 的 flags 里传 `O_RDWR/O_CREAT/O_EXCL` 是多余的，某些系统上还会报错」的原因 |
| `\| O_CREAT \| O_EXCL` | **原子性来源**：内核在一次 `open` 里完成「不存在才建」（[5.1](5.1-atomicity-race-conditions.md) 的 `fs/open.c:1315-1320`） |
| `S_IRUSR \| S_IWUSR` | 权限 `0600`，不是 `0644` |
| `__open` 返回值 | 直接就是 fd，**创建与打开不可分割** |

`sysdeps/posix/tempname.c:212-213` 的注释把这件事写得很直白：

```c
   __GT_FILE:           create the file using open(O_CREAT|O_EXCL)
                        and return a read-write fd.  The file is mode 0600.
```

### 为什么是 `0600` 而不是 `0644`

官方 `mkstemp(3)` 原文：

> The file is created with permissions **0600**, that is, read plus write for owner only. The returned file descriptor provides both read and write access to the file. The file is opened with the open(2) **O_EXCL** flag, guaranteeing that the caller is the process that creates the file.

`mkstemp(3)` 的 HISTORY 段落还留了这段黑历史：

> In glibc versions 2.06 and earlier, the file is created with permissions **0666**, that is, read and write for all users. This old behavior may be a security risk, especially since other UNIX flavors use 0600, and somebody might overlook this detail when porting programs. POSIX.1-2008 adds a requirement that the file be created with mode 0600.

所以你在任何一本老书/老代码里看到 `mkstemp` 后跟一句 `chmod`/`umask` 补丁，来源就是 glibc 2.6 之前那个 `0666` 的坑。

> **注意 `umask` 仍然生效**（`open` 的 mode 参数永远要过 umask）。`mkstemp(3)` 原文提醒：「the application should make sure its file mode creation mask (see umask(2)) is set appropriately」。`umask` 里若有 `0600` 位，结果会是 `0000`。

## 3. 实测

完整源码 [`code/c5_12_temp_files.c`](../code/c5_12_temp_files.c)：

```c
/* c5_12_temp_files.c — §5.12 创建临时文件：mkstemp / tmpfile / O_TMPFILE
 *
 * 三种做法的取舍：
 *   mkstemp(template)  —— 有名字、有 fd；模板末尾 6 个 X 由内核填随机串，
 *                         创建与打开是原子的（不会被人抢名字）。用完自己 unlink。
 *   tmpfile()          —— 无名文件，FILE* 接口，**关闭即消失**（glibc 内部
 *                         用 O_TMPFILE 或"创建后立刻 unlink"实现）。
 *   O_TMPFILE + linkat —— 真正匿名的文件，连名字都不曾有过；
 *                         需要正式名字时用 linkat 从 /proc/self/fd/N 挂上去。
 *
 * 演示五件事：
 *   1) mkstemp：模板被就地改写、fd 可用、权限是 0600（不是 0644）
 *   2) mkostemp 加 O_CLOEXEC
 *   3) tmpfile：readlink 看真名（通常显示 "(deleted)"）
 *   4) O_TMPFILE：写进匿名文件，再用 linkat 挂一个正式名字出来
 *   5) 三者的"清场"验证：unlink 之后旧的 fd 仍然可读
 *
 * 编译: gcc -O0 -Wall -Wextra -o c5_12_temp_files c5_12_temp_files.c
 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>
#include <errno.h>

static void show_link(const char *tag, int fd)
{
    char path[64];
    char buf[256];
    ssize_t r;

    snprintf(path, sizeof path, "/proc/self/fd/%d", fd);
    r = readlink(path, buf, sizeof buf - 1);
    if (r >= 0)
        buf[r] = '\0';
    printf("    [%-18s] fd=%d 指向 %s\n", tag, fd, r >= 0 ? buf : "?");
}

int main(void)
{
    printf("== 1. mkstemp()：有名字、0600、原子创建 ==\n");
    {
        char tmpl[] = "/tmp/c5tmpXXXXXX";
        int fd = mkstemp(tmpl);
        struct stat st;

        if (fd < 0) {
            perror("mkstemp");
            return 1;
        }
        printf("    内核把模板改写成 \"%s\"\n", tmpl);
        fstat(fd, &st);
        printf("    权限 = 0%o（mkstemp 强制 0600，避免他人抢先读写）\n",
               (unsigned) (st.st_mode & 07777));
        if (write(fd, "secret", 6) != 6)
            perror("write");
        printf("    再读回：");
        {
            char b[16];
            ssize_t n;

            lseek(fd, 0, SEEK_SET);
            n = read(fd, b, sizeof b - 1);
            b[n > 0 ? n : 0] = '\0';
            printf("\"%s\"\n", b);
        }
        printf("    unlink 之后 fd 依然可读（名字没了、inode 还活着）：");
        unlink(tmpl);
        {
            char b[16];
            ssize_t n;

            lseek(fd, 0, SEEK_SET);
            n = read(fd, b, sizeof b - 1);
            b[n > 0 ? n : 0] = '\0';
            printf("\"%s\"\n", b);
        }
        close(fd);
    }

    printf("\n== 2. mkostemp()：要加 O_CLOEXEC ==\n");
    {
        char tmpl[] = "/tmp/c5tmpXXXXXX";
        int fd = mkostemp(tmpl, O_CLOEXEC);

        if (fd < 0)
            perror("mkostemp");
        else {
            printf("    fd=%d，F_GETFD=0x%x（FD_CLOEXEC=0x%x 已置）\n",
                   fd, fcntl(fd, F_GETFD), FD_CLOEXEC);
            close(fd);
            unlink(tmpl);
        }
    }

    printf("\n== 3. tmpfile()：返回 FILE*，名字通常已经不存在 ==\n");
    {
        FILE *tf = tmpfile();

        if (tf == NULL) {
            perror("tmpfile");
        } else {
            int fd = fileno(tf);

            show_link("tmpfile", fd);
            fputs("hello from tmpfile\n", tf);
            fflush(tf);
            rewind(tf);
            printf("    读回来：");
            {
                char b[64];

                if (fgets(b, sizeof b, tf) != NULL)
                    printf("\"%s\"", b);
            }
            printf("    fclose 之后文件自动消失（内部用的是匿名/已 unlink 的文件）\n");
            fclose(tf);
        }
    }

    printf("\n== 4. O_TMPFILE + linkat：先匿名写，想留名时再挂上去 ==\n");
    {
        int fd = open("/tmp", O_RDWR | O_TMPFILE, 0600);

        if (fd < 0) {
            printf("    open(\"/tmp\", O_TMPFILE) 失败：errno=%d (%s)\n",
                   errno, strerror(errno));
        } else {
            char path[64];
            int re;

            show_link("O_TMPFILE", fd);
            if (write(fd, "anonymous!", 10) != 10)
                perror("write");
            snprintf(path, sizeof path, "/proc/self/fd/%d", fd);
            errno = 0;
            re = linkat(AT_FDCWD, path, AT_FDCWD, "/tmp/c5_linked.txt", AT_SYMLINK_FOLLOW);
            if (re == -1) {
                printf("    linkat 挂名失败：errno=%d (%s)\n", errno, strerror(errno));
            } else {
                printf("    挂上名字后 readlink(\"/tmp/c5_linked.txt\") 之外还能读：");
                {
                    int rf = open("/tmp/c5_linked.txt", O_RDONLY);
                    char b[32];
                    ssize_t n;

                    n = rf < 0 ? -1 : read(rf, b, sizeof b - 1);
                    b[n > 0 ? n : 0] = '\0';
                    if (rf >= 0)
                        close(rf);
                    printf("\"%s\"\n", b);
                }
                unlink("/tmp/c5_linked.txt");
            }
            close(fd);
        }
    }

    printf("\n== 5. 小结 ==\n");
    printf("    要名字 + fd        → mkstemp / mkostemp（记得 unlink）\n");
    printf("    只是临时放点数据    → tmpfile / O_TMPFILE（天然不留痕迹）\n");
    printf("    安全要点：不要用 mktemp()（不原子）、也不要用固定文件名 + O_CREAT\n");
    return 0;
}
```

```bash

```

逐条看：

| 观察 | 说明 |
|------|------|
| 模板 `"/tmp/c5tmpXXXXXX"` **被就地改写**成 `"/tmp/c5tmpEE7wgl"` | 这是函数契约的一部分：`template` 必须是**可写的字符数组**。官方原文：「Since it will be modified, template must not be a string constant, but should be declared as a character array」——传字符串字面量会段错误 |
| 权限 = `0600` | `try_file()` 的 `S_IRUSR\|S_IWUSR`（`:180`） |
| `unlink` 之后 fd 仍能读回 `"secret"` | 目录项没了、**inode 还活着**（还有 fd 引用着，`i_count > 0`）。这和 [5.11](5.11-dev-fd.md) 里 `unlink` 后还能从 `/proc/self/fd/N` 重新打开是同一个机制 |
| `mkostemp(tmpl, O_CLOEXEC)` → `F_GETFD = 0x1` | 证明 `flags` **穿透**到了 fd 表项。注意 `O_CLOEXEC` 落在**第 ① 层**（fd 表项），所以只能从 `F_GETFD` 看，看不到在 `F_GETFL` 里（[5.3](5.3-open-file-status-flags.md) 实测过） |
| `tmpfile()` → `/tmp/#4 (deleted)` | **本节最有意思的一行**。这不是「创建后 unlink」的产物，而是 `O_TMPFILE` 造出的**无名 inode**——`#4` 是内核在**没有任何名字可用时**给它编的临时名字（追源见第 5 节） |
| `O_TMPFILE` → `/tmp/#5 (deleted)` | 同上。`#5` 里的数字是 `/tmp` 文件系统上的 **inode 号**（沙箱里从 1 开始递增，所以两次调用拿到 4 和 5；这个数字会随运行环境变化，**不要当常量**） |
| `linkat` 挂名后读回 `"anonymous!"` | 匿名文件在**拿到名字之后**就变成普通文件了，`open` 它当然能读到内容 |

## 4. `tmpfile()` 为什么会长成 `#4` 这个样子

直接看 glibc `stdio-common/tmpfile.c`（全文 77 行）的核心：

```c
  /* First try a system specific method.  */
  fd = __gen_tempfd (flags);                    /* :45 */

  if (fd < 0)
    {
      char buf[FILENAME_MAX];

      if (__path_search (buf, sizeof buf, NULL, "tmpf", 0))   /* :51 */
	return NULL;

      fd = __gen_tempname (buf, 0, flags, __GT_FILE);         /* :54 */
      if (fd < 0)
	return NULL;

      /* Note that this relies on the Unix semantics that
	 a file is not really removed until it is closed.  */    /* :58-59 */
      (void) __unlink (buf);                                   /* :60 */
    }

  if ((f = __fdopen (fd, "w+b")) == NULL)                      /* :63 */
    __close (fd);
```

**两条路**：先试 `__gen_tempfd()`（系统相关的快速路），失败才退回「`mkstemp` + 立刻 `unlink`」。Linux 上的 `__gen_tempfd()` 就是 `O_TMPFILE`（`sysdeps/unix/sysv/linux/gentempfd.c:24-34`）：

```c
int
__gen_tempfd (int flags)
{
  int fd = __open (P_tmpdir, O_RDWR | O_TMPFILE | O_EXCL | flags,
		   S_IRUSR | S_IWUSR);
  if (fd < 0 && errno == ENOENT && strcmp (P_tmpdir, "/tmp") != 0)
    fd = __open ("/tmp", O_RDWR | O_TMPFILE | O_EXCL | flags,
		 S_IRUSR | S_IWUSR);

  return fd;
}
```

于是实测看到 `#4` 就得到了解释：**`__gen_tempfd()` 成功了**（`/tmp` 是 tmpfs，支持 `O_TMPFILE`），根本没走 `unlink` 那条退路。`#4` 是内核对无名 inode 的渲染。

官方 `tmpfile(3)` 对行为只说了一句：

> The tmpfile() function opens a unique temporary file in binary read/write (**w+b**) mode. The file will be **automatically deleted when it is closed or the program terminates**.

`w+b` 就在 `:63` 的 `__fdopen (fd, "w+b")` 里。VERSIONS 段落则解释了路径：

> The standard does not specify the directory that tmpfile() will use. glibc will try the path prefix **P_tmpdir** defined in `<stdio.h>`, and if that fails, then the directory **/tmp**.

——正好对应 `gentempfd.c:27-31` 那两行：先 `P_tmpdir`，`ENOENT` 且 `P_tmpdir != "/tmp"` 时退到 `"/tmp"`。

## 5. `#4` 从哪来：`d_tmpfile()` 给无名 inode 编了个名字

`O_TMPFILE` 走的是 `path_openat()` 里的一条**专用分支**（`fs/namei.c:3777`、`fs/open.c:1273` 已保证 `O_DIRECTORY` 一定被置上）：

```c
	if (unlikely(file->f_flags & __O_TMPFILE)) {
		error = do_tmpfile(nd, flags, op, file);
	} else if (unlikely(file->f_flags & O_PATH)) {
```

`do_tmpfile()` → `vfs_tmpfile()`（`fs/namei.c:3669`）：

```c
	error = dir->i_op->tmpfile(idmap, dir, file, mode);    /* :3691 */
	...
	inode = file_inode(file);
	if (!(open_flag & O_EXCL)) {                           /* :3700 */
		spin_lock(&inode->i_lock);
		inode->i_state |= I_LINKABLE;
		spin_unlock(&inode->i_lock);
	}
```

`dir->i_op->tmpfile` 由各个文件系统提供。CE 沙箱里 `/tmp` 是 tmpfs，所以落到 `mm/shmem.c:3244` 的 `shmem_tmpfile()`（注册在 `:4500` `.tmpfile = shmem_tmpfile`），它最后调 `d_tmpfile(file, inode)`（`:3265`）。

而 `d_tmpfile()` 就是 `#4` 的出生地（`fs/dcache.c:3249-3265`）：

```c
void d_tmpfile(struct file *file, struct inode *inode)
{
	struct dentry *dentry = file->f_path.dentry;

	inode_dec_link_count(inode);                       /* :3253 */
	BUG_ON(dentry->d_name.name != dentry->d_iname ||
		!hlist_unhashed(&dentry->d_u.d_alias) ||
		!d_unlinked(dentry));
	spin_lock(&dentry->d_parent->d_lock);
	spin_lock_nested(&dentry->d_lock, DENTRY_D_LOCK_NESTED);
	dentry->d_name.len = sprintf(dentry->d_iname, "#%llu",   /* :3259 */
				(unsigned long long)inode->i_ino);   /* :3260 */
	spin_unlock(&dentry->d_lock);
	spin_unlock(&dentry->d_parent->d_lock);
	d_instantiate(dentry, inode);
}
```

三行看懂：

- **`:3253` `inode_dec_link_count(inode)`** —— 「匿名」的本质在这里：`nlink` 被**直接减到 0**。它**不是**「先创建再 `unlink`」的结果，每一步都不同——从头到尾就没有过归属它的目录项。
- **`:3259-3260` `sprintf(d_name, "#%llu", i_ino)`** —— 给一个没有名字的 dentry 硬编一个 `#<inode 号>`。这就是 `#4` / `#5`。
- **`:3254-3256` 的 `BUG_ON`** —— 内核在这里断言「它确实是一个 unlinked、未散列、名字装在 `d_iname` 里的 dentry」，否则直接崩。**这说明「匿名」是一个内核强保证的状态，不是约定**。

`(deleted)` 后缀则是 `d_path()` 加的（`fs/d_path.c:265`、`:287-288`）：

```c
	if (unlikely(d_unlinked(path->dentry)))
		prepend(&b, " (deleted)", 11);
	else
		prepend_char(&b, 0);
```

`:255-256` 的注释老实承认这个后缀**有歧义**：「If the entry has been deleted the string " (deleted)" is appended. **Note that this is ambiguous.**」——因为文件名本身就可以叫 `xxx (deleted)`。所以脚本里别拿这个后缀当判据。

## 6. `O_EXCL` 在 `O_TMPFILE` 语境下的另一层含义

通常 `O_EXCL` = 「已存在就 `EEXIST`」。但官方 `open(2)` 明确说这层含义**在这里被重定义了**：

> **Specifying O_EXCL in conjunction with O_TMPFILE prevents a temporary file from being linked into the filesystem in the above manner.** (Note that the meaning of O_EXCL in this case is different from the meaning of O_EXCL otherwise.)

机制就在上面 `vfs_tmpfile()` 的 `:3700-3704` 和 `vfs_link()` 的 `:4598`：

```c
	/* Make sure we don't allow creating hardlink to an unlinked file */
	if (inode->i_nlink == 0 && !(inode->i_state & I_LINKABLE))
		error =  -ENOENT;
```

| | `open(dir, O_TMPFILE\|O_RDWR)` | `open(dir, O_TMPFILE\|O_RDWR\|O_EXCL)` |
|---|---|---|
| `I_LINKABLE` | **置上**（`fs/namei.c:3702`） | **不置** |
| `linkat(fd, "", ..., AT_EMPTY_PATH)` | 可以 | `-ENOENT`（`fs/namei.c:4598-4599`） |
| `linkat(AT_FDCWD, "/proc/self/fd/N", ..., AT_SYMLINK_FOLLOW)` | 可以 | 可以（走的是**解析符号链接**，不看 `I_LINKABLE`） |

`vfs_link()` 在成功挂名后还会把 `I_LINKABLE` 清掉（`:4608-4612`）——**匿名文件只能被挂名一次**，这是内核防止「一个 fd 反复生成多个硬链接」的措施。

官方 `open(2)` 给的标准姿势（原样抄）：

```c
char path[PATH_MAX];
fd = open("/path/to/dir", O_TMPFILE | O_RDWR,
                        S_IRUSR | S_IWUSR);

/* File I/O on 'fd'...  */

linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH);

/* If the caller doesn't have the CAP_DAC_READ_SEARCH
   capability (needed to use AT_EMPTY_PATH with linkat(2)),
   and there is a proc(5) filesystem mounted, then the
   linkat(2) call above can be replaced with:

snprintf(path, PATH_MAX,  "/proc/self/fd/%d", fd);
linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file",
                        AT_SYMLINK_FOLLOW);
*/
```

**本节的 demo 用的是后面那条**（`AT_SYMLINK_FOLLOW` + `/proc/self/fd/N`），因为 `AT_EMPTY_PATH` 需要 `CAP_DAC_READ_SEARCH`：

```c
	if (flags & AT_EMPTY_PATH && !capable(CAP_DAC_READ_SEARCH)) {
		error = -ENOENT;                                  /* fs/namei.c:4648-4649 */
		goto out_putnames;
	}
```

另外 `do_linkat()` 只认两个 flag，多传一个就 `-EINVAL`（`:4639-4642`）：

```c
	if ((flags & ~(AT_SYMLINK_FOLLOW | AT_EMPTY_PATH)) != 0) {
		error = -EINVAL;
		goto out_putnames;
	}
```

> 注意 glibc 的 `__gen_tempfd()` 传的是 `O_TMPFILE | **O_EXCL**`（`gentempfd.c:27`）。这不是笔误：它要的正是一个**连自己都挂不上名字**的文件——`tmpfile()` 语义就是「绝不留痕」，谁也拿不到名字才最安全。

## 7. 为什么 `mktemp` / `tmpnam` 不安全

`mktemp` 只挑名字、不创建（`misc/mktemp.c:24-32`）：

```c
char *
__mktemp (char *template)
{
  if (__gen_tempname (template, 0, 0, __GT_NOCREATE) < 0)
    ...
    template[0] = '\0';

  return template;
}
```

`__GT_NOCREATE` 对应的 `try_nocreate()`（`sysdeps/posix/tempname.c:189-197`）只做 `lstat` 确认名字**当前**不存在：

```c
static int
try_nocreate (char *tmpl, _GL_UNUSED void *flags)
{
  struct_stat64 st;

  if (__lstat64_time64 (tmpl, &st) == 0 || errno == EOVERFLOW)
    __set_errno (EEXIST);
  return errno == ENOENT ? 0 : -1;
}
```

于是经典 TOCTOU（[5.1](5.1-atomicity-race-conditions.md)）：

```c
char *name = mktemp(template);     /* ① 只检查了「不存在」 */
int fd = open(name, O_CREAT, 0600);/* ② 与 ① 之间有窗口 */
```

窗口里攻击者可以抢先建同名文件（你 open 到别人的东西），或用符号链接把它指到 `/etc/passwd`。**`mkstemp` 用一次 `open(O_CREAT|O_EXCL)` 把 ①② 合并成内核里的一个原子步骤**，窗口不存在。

glibc 的态度写在链接警告里（`misc/mktemp.c:36-37`）——只要你用了 `mktemp`，链接器每次都吼：

```c
link_warning (mktemp, "the use of `mktemp' is dangerous, "
		      "better use `mkstemp' or `mkdtemp'")
```

`tmpnam()` 更糟：它返回的名字甚至**可能指向静态缓冲区**（多线程下互相覆盖），且同样不保留名字。

## 8. 常见坑

| 坑 | 说明 |
|------|------|
| 把字符串字面量传给 `mkstemp` | 模板会被**就地改写** → 写只读段 → 段错误。必须 `char tmpl[] = "/tmp/xXXXXXX"` |
| 用 `mktemp` / `tmpnam` / `tempnam` | 都是「先取名后创建」的 TOCTOU，官方判了死缓（`link_warning`） |
| 以为 `mkstemp` 的 `0600` 是「最终权限」 | 仍要过 `umask`；`umask` 设错会得到 `0000`。另外 glibc ≤2.6 是 `0666` |
| `mkstemp` 后忘了 `unlink` | 文件会一直留在 `/tmp`。要「关闭即消失」就 `mkstemp` 后立刻 `unlink`（[5.11](5.11-dev-fd.md) 同机制），或直接用 `tmpfile()`/`O_TMPFILE` |
| 直接把 `tmpfile()` 的 fd 传给别人 | 它 `O_TMPFILE` 路径下**连名字都没有**，别的进程无法通过路径拿到它——这是特性不是 bug：`/proc/PID/fd/N` 是唯一入口（且需 ptrace 权限） |
| 以为 `O_TMPFILE` 到处都有 | 需要底层文件系统支持。官方 `open(2)` 列了清单：初版支持 ext2/ext3/ext4/UDF/Minix/**tmpfs**；后续 XFS(3.15)/Btrfs(3.16)/F2FS(3.16)/ubifs(4.9)。**NFS 之类不行**，`open` 会 `EOPNOTSUPP`（`fs/namei.c:3683-3684`） |
| 用 `O_TMPFILE` 时忘了 `O_DIRECTORY` | 用户态写 `O_TMPFILE` 就已经含 `O_DIRECTORY`（`include/uapi/asm-generic/fcntl.h:93` `#define O_TMPFILE (__O_TMPFILE \| O_DIRECTORY)`）。内核还专门校验这一点（`fs/open.c:1279-1280`），**就是为了让你在旧内核上拿到明确的 `EINVAL` 而不是莫名行为** |
| 用 `O_TMPFILE` 却只给只读 | `fs/open.c:1281-1282` 要求 `acc_mode & MAY_WRITE`，否则 `-EINVAL`。官方：`O_TMPFILE must be specified with one of O_RDWR or O_WRONLY` |
| 拿 ` (deleted)` 后缀当「已删除」的判据 | `fs/d_path.c:255-256` 注释自己说了「**this is ambiguous**」——文件名本身可以叫 `xxx (deleted)` |
| 想把 `#4` 当固定值 | 那是 **inode 号**，随文件系统状态变。它只是「没有名字时内核编的展示名」 |

## 9. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| **原子写配置文件** | 「写临时文件 → `fsync` → `rename` 覆盖」是唯一安全的配置更新方式。前半段就用 `mkstemp`（同目录，保证 `rename` 不跨设备）；崩溃只会留下一个孤儿临时文件，**永不出现半写状态的文件** |
| **多进程/多线程并发临时的唯一名** | `O_EXCL` 保证「谁创建谁负责」（`mkstemp(3)` 原文：「guaranteeing that the caller is the process that creates the file」）——[5.1](5.1-atomicity-race-conditions.md) 里 `bad_exclusive_open` 的反面教材在这里被修正 |
| **敏感数据不落盘留痕** | `tmpfile()` / `O_TMPFILE\|O_EXCL` 造出的文件**从未有过名字**（`fs/dcache.c:3253` 直接 `nlink--`），`ls /tmp` 看不到、`find` 也找不到，只有持 fd 的进程能读写 |
| **嵌入式 `/tmp` 是 tmpfs** | 落在内存里，重启即消失，不需要清理任务；但**容量有限**，写大文件要盯 `ENOSPC`（`tmpfile(3)` 的错误表就有这一条）。掉电丢失是特性 |
| **嵌入式只读根文件系统** | `P_tmpdir` 若指向只读区，`tmpfile()` 会 `EROFS`。要么挂 `tmpfs` 到 `/tmp`，要么用 `TMPDIR` 类机制显式指定可写目录 |
| **不可靠文件系统（NFS/老 FLASH）** | 官方 `open(2)` 提醒 `O_EXCL` 在 NFS 上「supported only when using NFSv3 or later」；`O_TMPFILE` 在 NFS 直接不支持。跨网络/老内核的临时文件要走 `mkstemp` 这条最保守的路 |
| **沙箱/容器里的 `/tmp`** | 本节实测 `/tmp` 是 tmpfs 且支持 `O_TMPFILE`；若换到 `overlayfs` 上的老内核，`tmpfile()` 会自动退到「`mkstemp`+`unlink`」那条路（`stdio-common/tmpfile.c:47-61`）——**glibc 已经替你做了兼容**，不需要自己判断 |
| **审计「进程握着什么」** | `#4`/`#5` 这类名字出现在 `/proc/PID/fd` 的 `readlink` 里时，含义就是「匿名 / O_TMPFILE 对象」，不是普通文件——排查泄露时别把它当路径去 `stat` |

<summary>代码自测（Q&A）</summary>

**Q1：`mkstemp` 的模板格式要求是什么？为什么必须用字符数组？**
A：末尾必须是恰好 6 个 `XXXXXX`（改自 `__gen_tempname(..., 6)`，`sysdeps/posix/tempname.c:333-336`）。函数会把这 6 个 X **就地替换**成唯一串并写回模板，所以官方要求「template must not be a string constant, but should be declared as a character array」。实测里 `"/tmp/c5tmpXXXXXX"` 变成了 `"/tmp/c5tmpEE7wgl"`。模板不合规返回 `-1` 且 `errno = EINVAL`，**模板内容不变**。

**Q2：`mkstemp` 创建的临时文件权限是多少？为什么？**
A：`0600`。来源是 `try_file()` 里 `open(..., S_IRUSR|S_IWUSR)`（`sysdeps/posix/tempname.c:180`），注释也写明「The file is mode 0600」。`mkstemp(3)` 官方原文：「The file is created with permissions 0600, that is, read plus write for owner only」。安全动机：临时文件常含敏感数据（session、密钥、中间计算结果），默认不给同组/其他用户。**注意仍要过 `umask`**。

**Q3：`tmpfile()` 返回的 FILE* 背后到底是什么？**
A：glibc 先试 `__gen_tempfd()`（Linux 上 = `open(P_tmpdir, O_RDWR|O_TMPFILE|O_EXCL, 0600)`，`gentempfd.c:27`），失败才退回「`__gen_tempname` + `__unlink`」（`stdio-common/tmpfile.c:45-61`）。CE 沙箱里第一条路成功，所以 `readlink(/proc/self/fd/3)` 显示 `/tmp/#4 (deleted)`——一个 **`O_TMPFILE` 无名 inode**，不是「被 unlink 掉的文件」。

**Q4：`#4` 这个数字是谁写的？**
A：`d_tmpfile()`（`fs/dcache.c:3249`）。它先 `inode_dec_link_count(inode)`（`:3253`）把 `nlink` 减到 0，再用 `sprintf(dentry->d_iname, "#%llu", inode->i_ino)`（`:3259-3260`）给这个**没有名字**的 dentry 编一个展示名。所以 `#` 后面是 **inode 号**，会随环境变化，不能当常量。`(deleted)` 后缀由 `d_path()` 追加（`fs/d_path.c:287-288`）。

**Q5：`O_TMPFILE` 造出的文件怎么在事后获得名字？**
A：两种（官方 `open(2)` 原样给出）：① `linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH)`——需要 `CAP_DAC_READ_SEARCH`，否则 `-ENOENT`（`fs/namei.c:4648-4649`）；② `snprintf(path, PATH_MAX, "/proc/self/fd/%d", fd); linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file", AT_SYMLINK_FOLLOW)`——不需要特权，本仓库 demo 用的就是这条。

**Q6：`open(..., O_TMPFILE|O_EXCL)` 里的 `O_EXCL` 是什么意思？**
A：**不是**「已存在就失败」。官方原文：「Specifying O_EXCL in conjunction with O_TMPFILE **prevents a temporary file from being linked into the filesystem** in the above manner. (Note that the meaning of O_EXCL in this case is different from the meaning of O_EXCL otherwise.)」机制：不带 `O_EXCL` 时 `vfs_tmpfile()` 会给 inode 置 `I_LINKABLE`（`fs/namei.c:3700-3704`），而 `vfs_link()` 对 `i_nlink == 0 && !I_LINKABLE` 的 inode 返回 `-ENOENT`（`:4598-4599`）。所以 glibc 的 `__gen_tempfd()` 故意加上 `O_EXCL`——它要的就是一个谁都挂不上名字的文件。

**Q7：`I_LINKABLE` 挂名成功后还在吗？**
A：**不在了**。`vfs_link()` 在成功后在 `:4608-4612` 把它清掉。含义：一个匿名 inode **只能被挂名一次**，防止同一 fd 反复造出多个硬链接。（若同一 inode 的 `nlink` 已 > 0，`:4598` 的第一个条件就不成立，也就不会再走 `I_LINKABLE` 分支了。）

**Q8：为什么 `mktemp` 不安全？glibc 怎么表态？**
A：`mktemp` 用 `__GT_NOCREATE` → `try_nocreate()`，只做一次 `lstat` **确认名字当前不存在**，**不创建**（`sysdeps/posix/tempname.c:189-197`）。检查与后续 `open` 之间有 TOCTOU 窗口。glibc 直接给了链接期警告：`link_warning (mktemp, "the use of `mktemp' is dangerous, better use `mkstemp' or `mkdtemp'")`（`misc/mktemp.c:36-37`）。

**Q9：往 `mkostemp` 的 flags 里传 `O_RDWR|O_CREAT|O_EXCL` 会怎样？**
A：多余。glibc 自己会强制加上：`(*openflags & ~O_ACCMODE) | O_RDWR | O_CREAT | O_EXCL`（`sysdeps/posix/tempname.c:178-180`）——**访问模式位会被先清掉**。官方 `mkstemp(3)` 原文：「including these values in the flags argument given to mkostemp() is unnecessary, **and produces errors on some systems**」。`mkostemp` 真正接受的只有 `O_APPEND`、`O_CLOEXEC`、`O_SYNC`。

**Q10：`O_TMPFILE` 的可用性有什么前提？失败时是什么错误？**
A：三层前提：① 文件系统支持（官方清单：ext2/ext3/ext4/UDF/Minix/tmpfs 初版；XFS 3.15、Btrfs 3.16、F2FS 3.16、ubifs 4.9）——不支持时 `fs/namei.c:3683-3684` 返回 `-EOPNOTSUPP`；② 必须带 `O_DIRECTORY`（`O_TMPFILE` 宏本身已含，`include/uapi/asm-generic/fcntl.h:93`）；③ 必须有写权限（`fs/open.c:1281-1282` 查 `acc_mode & MAY_WRITE`），缺任一项 → `-EINVAL`。

**Q11：`mkstemp` 之后立刻 `unlink`，和 `tmpfile()` 有什么区别？**
A：**结果相似、过程不同**。`mkstemp`+`unlink` 是「先有名字、再删掉」，中间那一瞬名字在目录里可见（极小窗口）；`tmpfile()` 走 `O_TMPFILE` 时**从头到尾没有名字**（`nlink` 直接为 0）。另外 `mkstemp` 返回 fd、`tmpfile` 返回 `FILE*`（`__fdopen(fd, "w+b")`，`tmpfile.c:63`）。要「路径名」选前者，只要「一堆临时字节」选后者。
