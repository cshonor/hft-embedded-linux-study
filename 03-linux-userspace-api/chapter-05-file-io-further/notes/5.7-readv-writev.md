## 本节讲什么

`readv` / `writev` 把**多段内存**一次交给内核：`writev` 是「聚集」（gather，多段 → 一次写），`readv` 是「散布」（scatter，一次读填多段）。本节回答四个问题：

1. `struct iovec` 是什么？`iovcnt` 有什么自由度？
2. 它到底省了什么——「省系统调用」这个说法准确吗？
3. 段数上限是多少？内核对 `iov` 数组做了什么（有没有中间缓冲区）？
4. `readv` / `writev` 会不会像 `read` / `write` 一样发生**部分读/部分写**？

---

## 1. 原型与 `struct iovec`

```c
#include <sys/uio.h>
ssize_t readv (int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
/* 成功返回读/写的总字节数；失败返回 -1 并设 errno */
```

```c
struct iovec {
        void  *iov_base;    /* 起始地址 */
        size_t iov_len;     /* 这一段的长度 */
};
```

内核对 `iovcnt` 的约束（`include/uapi/linux/uio.h`）：

| 常量 | 值 | 位置 | 含义 |
|------|----|------|------|
| `UIO_FASTIOV` | 8 | `include/uapi/linux/uio.h:27` | 内核在**栈上**预置这么多个 `iovec`；段数不多时**不 `kmalloc`** |
| `UIO_MAXIOV` | **1024** | `include/uapi/linux/uio.h:28` | 一次调用最多几段（超了报 `EINVAL`） |

## 2. 「省系统调用」这个说法准确吗

准确，但**不全**。`vfs_readv` 的实现（`fs/read_write.c:905`）：

```c
static ssize_t vfs_readv(struct file *file, const struct iovec __user *vec,
                         unsigned long vlen, loff_t *pos, rwf_t flags)
{
        struct iovec iovstack[UIO_FASTIOV];       /* fs/read_write.c:908 栈上 8 个 */
        struct iovec *iov = iovstack;
        struct iov_iter iter;
        ssize_t ret;

        ret = import_iovec(ITER_DEST, vec, vlen, ARRAY_SIZE(iovstack), &iov, &iter);
        if (ret >= 0) {                            /* fs/read_write.c:913 */
                ret = do_iter_read(file, &iter, pos, flags);
                kfree(iov);
        }
        return ret;
}
```

`import_iovec` 把**用户态的 `iov` 数组**（每项 16 字节的地址+长度，**不是数据**）拷进内核——段数 ≤ 8 时直接用栈上的 `iovstack`，多出来的才 `kmalloc`。真正的数据是内核通过 `iov_iter` **逐段**搬进/搬出的，**没有中间的连续缓冲**。

所以「省了什么」有三层：

| 省的东西 | 说明 |
|---------|------|
| **系统调用次数** | 写「头 + 体 + 尾」本来 3 次 `write`，现在 1 次 `writev`。HFT 热路径上这是主要收益 |
| **内存拷贝的「次数」不变，但少一次「先拼起来」的拷贝** | 手写版必须 `memcpy` 到一块连续缓冲再 `write`（多一次全量拷贝）；`readv`/`writev` 直接按段搬，**没有这一趟** |
| **`iov` 数组本身的拷贝很小** | 只有描述符（16 字节/段）进内核，不是数据 |

这就是 [习题 5-7](5.14-exercises.md) 的意义：用 `malloc` + `read`/`write` 手写一版，你会**看见**那多出来的一次 `malloc` 和一次全量拷贝。

## 3. 代码：五段实测

完整源码 [`code/c5_7_readv_writev.c`](../code/c5_7_readv_writev.c)：

```c
/* c5_7_readv_writev.c — §5.7 分散/聚集 I/O：readv() / writev()
 *
 * 把 N 段内存一次交给内核：writev 是"聚集"（gather，多段 → 一次写），
 * readv 是"分散"（scatter，一次读填多段）。好处是**省系统调用**：
 * 写「头 + 体 + 尾」本来要 3 次 write，现在 1 次。
 *
 * 演示五件事：
 *   1) 一次 writev 写三段（头部 / 载荷 / 尾部）
 *   2) 一次 readv 把同样的三段读回来，逐字节比对
 *   3) iov 数组本身也能加下标（iovcnt 可以小于数组长度）
 *   4) IOV_MAX 上限是多少
 *   5) 管道上的部分写：readv/writev 一样会"写多少算多少"，返回值才是真相
 *
 * 编译: gcc -O0 -Wall -Wextra -o c5_7_readv_writev c5_7_readv_writev.c
 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/uio.h>
#include <unistd.h>
#include <errno.h>

#define BODY_LEN 100

int main(void)
{
    const char *p = "/tmp/c5_iov.bin";
    const char *hdr = "HDR:";
    const char *tail = ":END";
    char body_w[BODY_LEN], body_r[BODY_LEN];
    ssize_t n;

    for (int i = 0; i < BODY_LEN; i++)
        body_w[i] = (char) ('a' + i % 26);

    printf("== 1. 一次 writev() 写三段 ==\n");
    {
        int fd = open(p, O_RDWR | O_CREAT | O_TRUNC, 0644);
        struct iovec iov[3];
        struct stat st;
        ssize_t want;

        iov[0].iov_base = (void *) hdr;   iov[0].iov_len = strlen(hdr);
        iov[1].iov_base = body_w;         iov[1].iov_len = BODY_LEN;
        iov[2].iov_base = (void *) tail;  iov[2].iov_len = strlen(tail);
        want = (ssize_t) (iov[0].iov_len + iov[1].iov_len + iov[2].iov_len);

        n = writev(fd, iov, 3);
        printf("   writev(fd, iov, 3) -> %ld（三段合计 %ld 字节，一次系统调用搞定）\n",
               (long) n, (long) want);
        fstat(fd, &st);
        printf("   文件 st_size=%lld\n", (long long) st.st_size);

        printf("\n== 2. 一次 readv() 读回来，逐字节比对 ==\n");
        lseek(fd, 0, SEEK_SET);
        {
            char h[8], t[8];
            struct iovec riov[3];

            memset(h, 0, sizeof h);
            memset(t, 0, sizeof t);
            memset(body_r, 0, sizeof body_r);
            riov[0].iov_base = h;      riov[0].iov_len = strlen(hdr);
            riov[1].iov_base = body_r; riov[1].iov_len = BODY_LEN;
            riov[2].iov_base = t;      riov[2].iov_len = strlen(tail);
            n = readv(fd, riov, 3);
            printf("   readv(fd, riov, 3) -> %ld\n", (long) n);
            printf("   三段分别是 \"%s\" / %d 字节 / \"%s\"\n", h, BODY_LEN, t);
            printf("   memcmp 载荷 -> %s\n",
                   memcmp(body_w, body_r, BODY_LEN) == 0 ? "相同" : "不同");
        }

        printf("\n== 3. iovcnt 可以小于数组长度（iov 数组就是个普通数组）==\n");
        {
            struct iovec two[3];
            char b[16];

            memset(b, 0, sizeof b);
            two[0].iov_base = b;      two[0].iov_len = 7;
            two[1].iov_base = body_r; two[1].iov_len = 4;
            two[2].iov_base = b + 7;  two[2].iov_len = 4;   /* 这个不会被用到 */
            lseek(fd, 0, SEEK_SET);
            n = readv(fd, two, 2);                          /* 只取前 2 段 = 11 字节 */
            b[11] = '\0';
            printf("   readv(fd, two, 2) -> %ld，读到 \"%s\"\n", (long) n, b);
        }
        close(fd);
    }

    printf("\n== 4. IOV_MAX：一次最多几段 ==\n");
    printf("   sysconf(_SC_IOV_MAX) = %ld\n", sysconf(_SC_IOV_MAX));

    printf("\n== 5. 管道上的部分写：writev 一样会「写多少算多少」==\n");
    {
        int pp[2];

        if (pipe(pp) == 0) {
            char chunk[1024];
            struct iovec iov[2];
            ssize_t w;

            memset(chunk, 'f', sizeof chunk);
            fcntl(pp[1], F_SETFL, O_NONBLOCK);
            /* 把管道容量压到一页（4096），再塞 3000 字节，留出 1096 的空隙 ——
               这样 writev 请求 4096 既不会阻塞、也不会全写进去，正好看到部分写 */
            if (fcntl(pp[1], F_SETPIPE_SZ, 4096) == -1)
                printf("   F_SETPIPE_SZ(4096) 失败: %s（下面结果会不同）\n", strerror(errno));
            printf("   管道容量 F_GETPIPE_SZ = %d\n", fcntl(pp[1], F_GETPIPE_SZ));
            w = write(pp[1], chunk, 1024);
            w += write(pp[1], chunk, 1024);
            w += write(pp[1], chunk, 952);
            printf("   已先塞入 %ld 字节\n", (long) w);

            iov[0].iov_base = chunk; iov[0].iov_len = 2048;
            iov[1].iov_base = chunk; iov[1].iov_len = 2048;
            errno = 0;
            w = writev(pp[1], iov, 2);
            if (w >= 0)
                printf("   writev 请求 4096 字节 -> 返回 %ld（部分写！剩下的自己补）\n",
                       (long) w);
            else
                printf("   writev 请求 4096 字节 -> -1 errno=%d (%s)（一点空间都没有了）\n",
                       errno, strerror(errno));
            close(pp[0]);
            close(pp[1]);
        }
    }

    return 0;
}
```

逐条看：

| 观察 | 说明 |
|------|------|
| `writev(fd, iov, 3)` → **108** | 三段是 `"HDR:"`(4) + 100 字节载荷 + `":END"`(4)。一次系统调用写完，`st_size=108` |
| `readv(fd, riov, 3)` → **108**，`memcmp` 相同 | 「散布」读回来：同样的三段、同样的切分。**读写是对称的** |
| `readv(fd, two, 2)` → **11**，读到 `HDR:abc` | `iov` 就是普通数组，`iovcnt` 可以**小于**数组长度——只处理前 2 段（`"HDR:"` 4 字节 + `"abc"` 7 字节）。这是「按需取前几段」的常用手法 |
| `sysconf(_SC_IOV_MAX)` = **1024** | 与内核 `UIO_MAXIOV`（`include/uapi/linux/uio.h:28`）**一致**。注意 glibc 的 `IOV_MAX` 宏也是 1024，但**运行时用 `sysconf` 更保险**（理论上平台可不同） |
| 管道上 `writev` 请求 4096 → `-1 errno=11 (EAGAIN)` | 管道容量 4096、已塞 3000 字节，**一点空间都没有**了。注意这是 `EAGAIN` 而不是「部分写」——因为剩余空间为 0 |

> **关于第 5 段的重要澄清**：`writev` 与 `write` 一样会**部分写**（写多少算多少），返回值才是真相。这个 demo 里恰好剩余空间为 0，所以直接 `EAGAIN`（非阻塞模式）。想看真正的「部分写」应给管道留一点空间——[Ch4 的 `ex4_3_partial_write.c`](../../chapter-04-file-io-universal/notes/4.10-exercises.md) 用 `write` 做过这件事（容量压到 4096、请求 8192 → 返回 **4096**）。**`writev` 的语义完全相同**：只要返回值小于请求总长，就必须继续写。

```c
/* t_readv.c

   Demonstrate the use of the readv() system call to perform "gather I/O".

   (This program is merely intended to provide a code snippet for the book;
   unless you construct a suitably formatted input file, it can't be
   usefully executed.)
*/
#include <sys/stat.h>
#include <sys/uio.h>
#include <fcntl.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int fd;
    struct iovec iov[3];
    struct stat myStruct;       /* First buffer */
    int x;                      /* Second buffer */
#define STR_SIZE 100
    char str[STR_SIZE];         /* Third buffer */
    ssize_t numRead, totRequired;

    if (argc != 2 || strcmp(argv[1], "--help") == 0)
        usageErr("%s file\n", argv[0]);

    fd = open(argv[1], O_RDONLY);
    if (fd == -1)
        errExit("open");

    totRequired = 0;

    iov[0].iov_base = &myStruct;
    iov[0].iov_len = sizeof(struct stat);
    totRequired += iov[0].iov_len;

    iov[1].iov_base = &x;
    iov[1].iov_len = sizeof(x);
    totRequired += iov[1].iov_len;

    iov[2].iov_base = str;
    iov[2].iov_len = STR_SIZE;
    totRequired += iov[2].iov_len;

    numRead = readv(fd, iov, 3);
    if (numRead == -1)
        errExit("readv");

    if (numRead < totRequired)
        printf("Read fewer bytes than requested\n");

    printf("total bytes requested: %ld; bytes read: %ld\n",
            (long) totRequired, (long) numRead);
    exit(EXIT_SUCCESS);
}
```

它把「一次读三样东西」写成 `readv`：`struct stat`（144 字节）+ `int`（4 字节）+ 100 字节字符串，总计 **248 字节**，正好是 `UIO_FASTIOV` 之上的常规用法。

```bash
gcc -O0 -Wall -Wextra -o t_readv t_readv.c
./t_readv /proc/self/maps      # 够长 → 读满
./t_readv /proc/version        # 只有 219 字节 → 短读
```

CE 实测（两次，对应两个输入文件）：

```text
total bytes requested: 248; bytes read: 248
```

```text
Read fewer bytes than requested
total bytes requested: 248; bytes read: 219
```

**这两行是整个 §5.7 最值得记住的东西**：`readv` **不保证**读满你请求的总长。第二次运行里 `/proc/version` 只有 219 字节，`readv` 老老实实返回 **219** 并**不动后面那些段**（不算错误）。程序自己打印 `Read fewer bytes than requested` 就是在提示这件事——原书源码里那句 `if (numRead < totRequired) printf(...)` 正是为此而写。

> `totRequired = 248` 的来历：CE 上 `sizeof(struct stat) = 144`（`t_readv_full` 实测），144 + 4 + 100 = 248。在别的平台上 `struct stat` 大小不同，这个数会变——**别把它当常数记**。

## 5. 常见坑

| 坑 | 说明 |
|----|------|
| 以为 `readv` 一定读满 | **不保证**。返回小于总请求长度是正常结果（实测 219 < 248）。必须循环或用返回值判断 |
| 以为 `writev` 一定写满 | 同上。管道/非阻塞/信号都会造成部分写 |
| `iovcnt` 传超限值 | > `UIO_MAXIOV`（1024，`include/uapi/linux/uio.h:28`）→ `EINVAL` |
| 把 `iov_base` 指向已释放内存 | 内核在**读/写过程中**才逐段访问这些地址（`import_iovec` 只拷描述符），所以缓冲必须在使用期间一直有效 |
| `iov_len` 很大导致地址和溢出 | 内核会检查各段合计长度，但用户态自己拼接时要注意 `size_t` 溢出 |
| 忘了 `#include <sys/uio.h>` | `struct iovec` 在这里；只包含 `unistd.h` 会编译不过 |
| 想要「指定偏移 + 多段」 | `preadv` / `pwritev`（`fs/read_write.c:1052` / `:1072`），还有带 `flags` 的 `preadv2` / `pwritev2`（`:1060` / `:1080`） |

## 6. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| 行情报文发送 | 「固定头 + 变长体」用 `writev` 一次发出，省一半系统调用、少一次 `memcpy`——这是网络库（如 `libevent`、`muduo`）的标准做法 |
| 协议解析 | `readv` 一次把「头部结构体 + 载荷缓冲」填好，不需要先读进大缓冲再切分 |
| 定长记录批量写 | `iov` 数组各段指向循环缓冲里的不同记录，`iovcnt` 按当前积压条数填——**「按需取前 N 段」**（第 3 段实测）正是这个用法的依据 |
| `iovcnt` 上限保护 | 1024 段意味着最多一次交 1024 个缓冲；HFT 里常自己限制更小（如 64），避免 `import_iovec` 走 `kmalloc` 路径（`fs/read_write.c:908` 栈上只放 8 个） |
| 嵌入式小内存 | `writev` 免去「拼一个连续大缓冲」的峰值内存——在内存紧张的设备上，这可能就是能不能用大报文的分界线 |
| 非阻塞 + `writev` | 必须处理部分写：非阻塞 socket 上 `writev` 返回小于总长时，要**记录写到第几段**并下次续写（`struct iovec` 可原地瘦身） |

**Q1：`writev` 到底省了什么？**
A：三层：① **系统调用次数**（3 次 `write` → 1 次 `writev`，实测三段共 108 字节一次写完）；② **少一次「先拼成连续缓冲」的内存拷贝**——手写版必须 `memcpy` 到一个大缓冲再 `write`，内核版直接按段搬；③ `iov` 数组本身只拷**描述符**（`import_iovec`，`fs/read_write.c:913`），不是数据。

**Q2：`readv` 能保证读满请求的总长度吗？**
A：**不能**。原书 `t_readv.c` 读 `/proc/version`（219 字节）时请求 248 字节，实测返回 **219**，并打印 `Read fewer bytes than requested`。和 `read` 一样，返回小于请求值是正常结果。

**Q3：`iovcnt` 可以小于 `iov` 数组的实际长度吗？**
A：可以。`iov` 就是个普通数组，`iovcnt` 只告诉内核「这次用前几个」。实测 `readv(fd, two, 2)` 只读了前两段共 11 字节。

**Q4：一次最多能交几段？在哪里定义的？**
A：`UIO_MAXIOV = 1024`，定义在 `include/uapi/linux/uio.h:28`；运行时可用 `sysconf(_SC_IOV_MAX)` 查询，实测返回 `1024`。另外 `UIO_FASTIOV = 8`（`:27`）是内核**栈上**预置的段数（`fs/read_write.c:908`），超过 8 段才会 `kmalloc`。

**Q5：`writev` 会部分写吗？**
A：会，和 `write` 同样的语义——返回值才是真相。第 5 段实测里管道剩余空间为 0，所以直接 `EAGAIN`（非阻塞）；若还剩一点空间，`writev` 就会返回「写了多少」。

**Q6：`preadv` / `pwritev` 和 `readv` / `writev` 是什么关系？**
A：`preadv` / `pwritev` = 「多段 + 指定偏移」，即把 `readv` 的多段能力和 `pread` 的「不动 `f_pos`」能力合起来。实现在 `fs/read_write.c:1052` / `:1072`（内部走 `do_preadv` `:994` / `do_pwritev` `:1017`，用 `fdget` 而非 `fdget_pos`）。

**Q7：为什么说「段数别开太大」？**
A：段数 ≤ 8 时 `vfs_readv` 用栈上的 `iovstack`（`fs/read_write.c:908`），超了就走 `kmalloc`/`kfree`（`:913`、`:916`）——在热路径上这是一次内存分配。所以 HFT 代码常把每批段数压到 8 以内。
