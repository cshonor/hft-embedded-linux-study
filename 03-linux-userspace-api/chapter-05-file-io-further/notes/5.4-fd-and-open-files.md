# 5.4 fd 与打开文件的关系（Relationship Between File Descriptors and Open Files）

## 本节讲什么

`lseek` 改的到底是「fd 数字」还是别的什么？为什么 `dup` 出来的两个 fd 会互相影响偏移，而两次 `open` 同一路径却互不影响？本节回答三个问题：

1. 内核里与「一个打开的文件」相关的三层结构分别是什么、各存什么？
2. 文件偏移（`lseek` 改的那个）到底存在哪一层？
3. `dup` / `fork` / 两次 `open` 分别导致「共享偏移」还是「独立偏移」？

---

## 1. 内核三层结构

进程里一个「打开的文件」在内核里不是一层，而是三层。这是本章所有「怪现象」的总根源：

```
进程级                内核级                     磁盘级
┌─────────────┐   ┌──────────────────┐   ┌──────────────┐
│ fd 表        │   │ 打开文件描述       │   │ inode        │
│ (files_struct│   │ (struct file)    │   │ (磁盘上的真实 │
│  内的 fdtable)│──▶│  f_pos  偏移      │──▶│  文件元数据)   │
│  + fd 标志    │   │  f_flags 状态标志 │   │  size/权限/块  │
│ (FD_CLOEXEC) │   │  f_mode 访问模式  │   │  链接计数      │
└─────────────┘   │  f_op   操作表    │   └──────────────┘
                  └──────────────────┘
```

| 层 | 谁持有 | 存什么 | 内核结构 |
|----|--------|--------|---------|
| **1. 进程 fd 表** | 每进程独有 | 指向 `struct file` 的指针 + **fd 标志**（主要是 `FD_CLOEXEC`） | `files_struct` → `fdtable`（`include/linux/fdtable.h:49` / `:27`） |
| **2. 打开文件描述** | 内核全局，可被多个 fd 共享 | **文件偏移 `f_pos`**（`lseek` 改的就是它）、状态标志（`f_flags`：`O_APPEND`/`O_NONBLOCK`…）、访问模式（`f_mode`）、操作表（`f_op`）、引用计数 `f_count` | `struct file`（`include/linux/fs.h:992`，`f_pos` 在 `:1007`） |
| **3. inode** | 磁盘上的真实文件 | 大小、权限、磁盘块位置、链接计数 | `struct inode` |

> 关键结论：**`lseek` 改的是「打开文件描述」里的 `f_pos`，不是「fd 数字本身」，更不是 inode**。fd 数字只是一个索引，指向打开文件描述。

## 2. 共享 vs 独立：偏移的关键推论（高频面试点）

| 操作 | 打开文件描述 | 偏移 |
|------|-------------|------|
| 同一进程两次独立 `open()` 同一路径 | **两个** | **各自独立** |
| `dup` / `dup2` / `fcntl(F_DUPFD)` | **同一个**（引用计数 +1） | **共享** |
| `fork` 后子进程继承 | **共享**父进程的打开描述 | **共享**（子进程复制 fd 表，但表项指向同一个 `struct file`） |
| `O_APPEND` | 写前内核原子定位到 EOF 再写 | 见 [5.1 原子性](5.1-atomicity-race-conditions.md) |

```
两次 open 同一文件：            dup / fork：
fd3 ──▶ [struct file A] pos=0   fd4 ──┐
fd5 ──▶ [struct file B] pos=0         ├──▶ [struct file C] pos=共享
        （各自独立偏移）        fd6 ──┘   （lseek fd4 会影响 fd6）
```

## 3. 为什么 `dup` 共享而 `open` 不共享

- **`open()`**：每次调用都会 `do_filp_open` 出一个**新的 `struct file`**，初始 `f_pos = 0`，再挂到 fd 表。两次 `open` = 两个 `struct file`，偏移自然独立。
- **`dup()`**：不创建新 `struct file`，只是让新 fd 表项**指向同一个 `struct file`**，并把它的 `f_count` 引用计数 +1。既然指向同一个 `struct file`，`f_pos` 就只有一个，`lseek` 通过任一 fd 都会改到它。
- **`fork()`**：子进程复制父进程的 `files_struct`（fd 表），但**表项指针原样复制**——父子的 fd 指向**同一个** `struct file`。所以父子共享偏移，直到一方 `close`（`close` 只是让 `f_count` -1，减到 0 才真正释放 `struct file`）。

## 4. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| 多线程共享 fd 的坑 | 两个线程用同一 fd 做 `lseek`+`read` 会互相踩偏移，用 `pread`/`pwrite` 规避（见 [5.6](5.6-pread-pwrite.md)） |
| `fork` 后父子抢日志 | 父子共享打开描述，都会从同一 `f_pos` 继续写，可能交错；必要时 `O_APPEND` 或各自 `open` |
| 重定向不泄漏 | `dup2` 后新 fd 与旧 fd 共享描述，理解 `f_count` 才能正确配对 `close`（见 [5.5](5.5-duplicating-fds.md)） |
| 嵌入式设备 fd 紧张 | 三层结构意味着「一个打开描述可被多个 fd 引用」，正确 `dup`/`close` 能复用底层资源 |

## 5. 代码示例

```c
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

/* 5.4 三层结构：dup 共享偏移，两次 open 独立偏移 */
int main(void) {
    int fd = open("/tmp/sparse.txt", O_RDWR | O_CREAT, 0644);
    write(fd, "ABCDE", 5);

    /* dup 后 fd 和 fd2 指向同一个打开文件描述 → 共享偏移 */
    int fd2 = dup(fd);

    lseek(fd, 0, SEEK_SET);
    char buf[3];
    read(fd, buf, 2);                       /* fd 读 2 字节 → 偏移变 2 */
    printf("fd  偏移: %ld\n", lseek(fd, 0, SEEK_CUR));   /* 2 */
    printf("fd2 偏移: %ld (共享)\n", lseek(fd2, 0, SEEK_CUR)); /* 2 */

    /* 两次独立 open → 各自独立偏移 */
    int fd3 = open("/tmp/sparse.txt", O_RDONLY);
    printf("fd3 偏移: %ld (独立)\n", lseek(fd3, 0, SEEK_CUR)); /* 0 */

    close(fd); close(fd2); close(fd3);
    return 0;
}
```

<summary>代码自测（Q&A）</summary>

**Q1：`lseek` 修改的偏移到底存在哪一层？**
A：存在**打开文件描述**（`struct file` 的 `f_pos`，`include/linux/fs.h:1007`）里，不是 fd 数字本身，也不是 inode。fd 只是指向 `struct file` 的索引。所以「同一个 `struct file` 被多个 fd 引用」时，`lseek` 通过任一 fd 都会改到同一个 `f_pos`。

**Q2：两次 `open()` 同一路径，偏移共享吗？为什么？**
A：不共享。每次 `open` 都会 `do_filp_open` 出一个**新的 `struct file`**（`f_pos` 各自初始为 0），再挂到 fd 表。两个 `struct file` = 两个独立偏移。

**Q3：`fork` 后父子进程的 fd 偏移共享吗？**
A：共享。`fork` 复制的是 fd 表（`files_struct`），但表项指针原样复制，父子的 fd 指向**同一个** `struct file`，所以 `f_pos` 共享。一方 `close` 只是 `f_count` 减 1，减到 0 才释放 `struct file`。

**Q4：`dup` 出来的新 fd 和旧 fd，`close` 一个会影响另一个吗？**
A：`close` 只是把 `struct file` 的 `f_count` 减 1，并清掉该 fd 表项。只要 `f_count` 未减到 0，`struct file` 就还活着，另一个 fd 仍可正常读写同一打开描述（共享偏移）。

**Q5：`O_APPEND`、`O_NONBLOCK` 这些状态标志存在哪一层？`FD_CLOEXEC` 呢？**
A：`O_APPEND`/`O_NONBLOCK` 存在**打开文件描述**的 `f_flags` 里（`dup` 共享）；`FD_CLOEXEC` 存在**进程 fd 表项**里（每个 fd 私有）。这是两组标志的归属差异，详细见 [5.2 `fcntl()`](5.2-fcntl.md) 和 [5.3](5.3-open-file-status-flags.md)。

</details>
