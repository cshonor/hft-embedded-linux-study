## 本节讲什么

多进程/多线程同时操作文件时，两个「看起来没问题的操作」会因为执行顺序交错而互相踩踏。本节回答四个问题：

1. 「原子性（atomicity）」到底指什么？为什么文件 I/O 里它如此关键？
2. `O_APPEND` 的原子性**在内核哪一行**兑现？它和用户态 `lseek(SEEK_END) + write()` 差在哪？
3. `O_CREAT | O_EXCL` 为什么能防 TOCTOU？内核靠什么锁保证「查 + 建」不可分割？
4. `O_EXCL` 那句「顺便带上 `O_NOFOLLOW`」是不是都市传说？

本节把两条竞态**真的跑出来**：并发写 40 万字节，`O_APPEND` 一个不丢、`lseek + write` 丢了几千字节；以及两个进程**同时**声称「我创建了它」。

---

## 1. 竞态条件与原子性

**竞态条件（race condition）**：多个进程/线程的执行结果取决于它们指令的**相对执行顺序**。只要存在一个交错顺序能导致错误结果，代码就是有 bug 的——哪怕它 99% 的时候都对。

**原子性（atomicity）**：一个操作「要么完全执行、要么完全不执行」，中间状态对其他执行者**不可见**。原子操作天然免疫竞态，因为不存在「执行到一半被打断」的窗口。

文件 I/O 里最常见的两类竞态及各自的原子化解法：

| 场景 | 非原子（错误）写法 | 原子（正确）写法 |
|------|-------------------|-----------------|
| 独占创建文件（PID 锁文件） | `open(O_WRONLY)` 探测 → 再 `open(O_CREAT)` 创建 | `open(path, O_CREAT \| O_EXCL)` |
| 多进程追加日志 | `lseek(fd, 0, SEEK_END)` → `write(fd, ...)` | `open(path, O_APPEND)` 后直接 `write` |

两件事的共同点：**「检查」和「使用」被拆成了两步，中间有窗口**。原子化就是把它们压进内核的同一个不可分割的步骤里。

## 2. 代码：把两条竞态真的跑出来

原书用两条 shell 命令并发跑同一个程序来演示：

```bash
atomic_append f1 1000000 & atomic_append f1 1000000     # O_APPEND
atomic_append f2 1000000 x & atomic_append f2 1000000 x # lseek+write
```

CE 的执行模型是「一个进程跑一次」，敲不了两条 shell 命令，所以自编 demo 用 `fork()` 把两个写者放进同一进程树，复现同一个竞态。

完整源码 [`code/c5_1_atomicity.c`](../code/c5_1_atomicity.c)：

```c
/* c5_1_atomicity.c — §5.1 原子性与竞态条件：两种经典"非原子"写法
 *
 * 原书用两条 shell 命令并发跑同一个程序来演示竞态：
 *     atomic_append f1 1000000 & atomic_append f1 1000000       → 正好 2 000 000 字节
 *     atomic_append f2 1000000 x & atomic_append f2 1000000 x   → 少一截（丢数据）
 * CE 的执行模型是「一个进程跑一次」，没法敲两条 shell 命令，所以这里用 fork()
 * 把两个写者放进同一进程树，复现同一个竞态。
 *
 * 演示三段：
 *   1) O_APPEND 与 lseek+write 的差别（内核是否帮你把「定位+写」做成一步）
 *   2) 检查文件是否存在、再创建 —— 两步之间被别人插队（Listing 5-1 的坑）
 *   3) 用 O_CREAT|O_EXCL 让「检查+创建」变成一个原子操作
 *
 * 编译: gcc -O0 -Wall -Wextra -o c5_1_atomicity c5_1_atomicity.c
 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/wait.h>
#include <unistd.h>
#include <errno.h>

#define PER_WRITER 200000       /* 每个写者写这么多字节；两个一起 400000 */

enum job { JOB_APPEND, JOB_LSEEK, JOB_CREATE_NOEXCL, JOB_CREATE_EXCL };

/* 子进程要做的事 */
static int do_job(enum job j, const char *path)
{
    if (j == JOB_CREATE_NOEXCL) {
        int fd = open(path, O_WRONLY);              /* 第一步：它存在吗？ */

        if (fd >= 0) {
            printf("  [PID %5ld] 文件已存在，我没创建它\n", (long) getpid());
            close(fd);
            return 0;
        }
        sleep(1);                                   /* 两步之间的窗口（原书用 sleep 放大） */
        fd = open(path, O_WRONLY | O_CREAT, 0644);  /* 第二步：那我来创建 */
        if (fd < 0)
            return 5;
        printf("  [PID %5ld] 不存在 → 我创建了它！\n", (long) getpid());
        close(fd);
        return 0;
    }

    if (j == JOB_CREATE_EXCL) {
        int fd = open(path, O_WRONLY | O_CREAT | O_EXCL, 0644);

        if (fd < 0) {
            printf("  [PID %5ld] O_EXCL 失败 errno=%d (%s)：别人抢先创建了\n",
                   (long) getpid(), errno, strerror(errno));
            return 0;
        }
        printf("  [PID %5ld] O_EXCL 成功：确实是我创建的（唯一赢家）\n", (long) getpid());
        close(fd);
        return 0;
    }

    /* 一次一字节地写：JOB_APPEND 用 O_APPEND，JOB_LSEEK 用 lseek+write */
    {
        int flags = O_WRONLY | O_CREAT | (j == JOB_APPEND ? O_APPEND : 0);
        int fd = open(path, flags, 0644);

        if (fd < 0)
            return 2;
        for (int i = 0; i < PER_WRITER; i++) {
            if (j == JOB_LSEEK) {
                /* 非原子版本：先定位到末尾…… */
                if (lseek(fd, 0, SEEK_END) == (off_t) -1)
                    return 3;
            }
            /* ……再写。这两步之间别的进程可能也在往里写，于是互相覆盖 */
            if (write(fd, "x", 1) != 1) {
                close(fd);
                return 4;
            }
        }
        close(fd);
        return 0;
    }
}

static long long size_of(const char *p)
{
    struct stat st;

    return stat(p, &st) == 0 ? (long long) st.st_size : -1;
}

/* 两个子进程并发跑同一件事，父进程等它们都结束 */
static void run_twins(enum job j, const char *path)
{
    for (int i = 0; i < 2; i++) {
        if (fork() == 0) {
            int rc = do_job(j, path);

            /* 子进程继承的是块缓冲（stdout 被重定向时），_exit() 不刷缓冲，
               所以子进程自己的 printf 必须手动 flush，否则整段输出丢失 */
            fflush(NULL);
            if (rc != 0)
                fprintf(stderr, "child rc=%d\n", rc);
            _exit(0);
        }
    }
    while (wait(NULL) > 0)
        ;
}

int main(void)
{
    const char *fa = "/tmp/c5_append.bin";
    const char *fb = "/tmp/c5_lseek.bin";
    const char *fc = "/tmp/c5_race_noexcl";
    const char *fd = "/tmp/c5_race_excl";
    long long want = 2LL * PER_WRITER;

    unlink(fa); unlink(fb); unlink(fc); unlink(fd);

    printf("== 1. 两个写者并发写同一文件（各 %d 字节，一次一字节）==\n", PER_WRITER);
    fflush(stdout);

    printf("\n-- O_APPEND：内核把「移到末尾 + 写」做成不可分割的一步 --\n");
    fflush(stdout);
    run_twins(JOB_APPEND, fa);
    printf("  写完后 st_size = %lld（期望 %lld）\n", size_of(fa), want);

    printf("\n-- lseek+write：两步之间有窗口，两个进程会互相踩 --\n");
    fflush(stdout);
    run_twins(JOB_LSEEK, fb);
    printf("  写完后 st_size = %lld（期望 %lld）-> 丢 %lld 字节\n",
           size_of(fb), want, want - size_of(fb));

    printf("\n== 2. 先 open 检查、再 open 创建（没有 O_EXCL）==\n");
    fflush(stdout);
    run_twins(JOB_CREATE_NOEXCL, fc);
    printf("  两个进程都声称「我创建了它」——但它们只创建了一个文件\n");

    printf("\n== 3. 换成 O_CREAT|O_EXCL：检查与创建合成一个原子操作 ==\n");
    fflush(stdout);
    run_twins(JOB_CREATE_EXCL, fd);

    return 0;
}
```

编译运行：

```bash
gcc -O0 -Wall -Wextra -o c5_1_atomicity c5_1_atomicity.c && ./c5_1_atomicity
```

CE（gcc 13.3.0 / x86-64 / Ubuntu 24.04）实测：

```text
== 1. 两个写者并发写同一文件（各 200000 字节，一次一字节）==

-- O_APPEND：内核把「移到末尾 + 写」做成不可分割的一步 --
  写完后 st_size = 400000（期望 400000）

-- lseek+write：两步之间有窗口，两个进程会互相踩 --
  写完后 st_size = 391764（期望 400000）-> 丢 8236 字节

== 2. 先 open 检查、再 open 创建（没有 O_EXCL）==
  [PID     7] 不存在 → 我创建了它！
  [PID     8] 不存在 → 我创建了它！
  两个进程都声称「我创建了它」——但它们只创建了一个文件

== 3. 换成 O_CREAT|O_EXCL：检查与创建合成一个原子操作 ==
  [PID     9] O_EXCL 成功：确实是我创建的（唯一赢家）
  [PID    10] O_EXCL 失败 errno=17 (File exists)：别人抢先创建了
```

逐条看：

| 观察 | 说明 |
|------|------|
| `O_APPEND` 并发写 40 万字节 → **恰好 400000** | 一次一字节地写、两个进程抢，一字节都没丢。因为「定位到末尾」和「写」在内核里是同一步 |
| `lseek + write` 并发写 40 万字节 → **391764**，丢 **8236** | 这是**真丢数据**（不是覆盖）：A 定位到末尾 100、B 也定位到 100，A 写完在 101、B 却从 100 开始写，把 A 刚写的那一字节盖掉。**首轮跑这个 demo 时丢的是 192145 字节**——每次数字都不同，这本身就是竞态的铁证 |
| 第 2 节两个 PID 都打印「我创建了它！」 | `open(path, O_WRONLY)` 探测「不存在」→ `sleep(1)` 放大窗口 → 再 `open(..., O_CREAT)`。两个进程都在窗口内通过了检查 |
| 第 3 节只有一个「唯一赢家」，另一个 `errno=17 (EEXIST)` | `O_EXCL` 把「查 + 建」压进内核一次不可分割的操作，窗口消失了 |

> **丢字节的机制是「覆盖」，不是「写出半个字节」。** 在这个 demo 里两个子进程各自 `open`（没有 `O_APPEND`），于是各有各的打开文件表项、各有各的 `f_pos`。危险序列是：
>
> ```
> A: lseek(fd,0,SEEK_END) -> 100        B: lseek(fd,0,SEEK_END) -> 100
> A: write(fd,"x",1) 写在第 100 字节，文件变 101
>                                       B: write(fd,"x",1) 也写在第 100 字节 ← 把 A 那字节盖掉
> ```
>
> 单字节 `write` 本身在普通文件上是原子的（不会撕裂），但 **`lseek` 与 `write` 这一对不是**：两次 `lseek` 可能读到同一个末尾。丢失量 = 两个进程「撞在同一个偏移上」的次数，所以每轮数字都不一样。`O_APPEND` 把这两步合进内核一次写操作（`fs/read_write.c:1666-1667`），碰撞窗口直接消失。

## 3. `O_APPEND` 的原子性在内核哪一行兑现

这是本节的**核心证据链**。用户态的 `lseek(fd, 0, SEEK_END)` 与 `write()` 是两个独立系统调用；`O_APPEND` 则把「定位」下沉进了 `write` 的内核路径：

```
open(path, O_APPEND)
      ▼
build_open_flags()                          fs/open.c:1308
      if (flags & O_APPEND)
              acc_mode |= MAY_APPEND;         ← 供 LSM/权限检查区分 append 与 write
      ▼
该标志被存进 struct file->f_flags（打开文件表项）
      ▼
后续每次 write 走到写入公共路径：
      generic_write_checks_count()            fs/read_write.c:1655
          if (iocb->ki_flags & IOCB_APPEND)   fs/read_write.c:1666
                  iocb->ki_pos = i_size_read(inode);   ← 就在这一行「原子定位到末尾」
```

`fs/read_write.c:1666-1667` 那两行就是答案：

```c
if (iocb->ki_flags & IOCB_APPEND)
        iocb->ki_pos = i_size_read(inode);
```

它在**同一次写操作内部**把位置设为当前文件末尾，用的是内核 `inode` 锁保护下读到的 `i_size`——用户态没有对应的两次系统调用之间的窗口可插。**这就是「用户态复刻不了 `O_APPEND`」的确切含义**：不是「编译器优化」或「概率小」，而是原子性的兑现点在进内核之后。

> 旧版笔记此处写的是「缓存未收录 `mm/filemap.c`，作架构说明」。本仓库下载 v6.6 源码后已定位到真实行号（`fs/read_write.c:1666-1667`），**架构说明换成源码坐标**——这也是本仓库「内核断言必须查真实行号」的一例。

## 4. `O_CREAT | O_EXCL`：原子独占创建

### 4.1 为什么「先检查再创建」是错的

```c
/* 反例：TOCTOU —— check 和 use 之间被别的进程插入 */
if (access(path, F_OK) == -1) {         /* check：现在还不存在 */
    fd = open(path, O_CREAT, 0644);     /* use：另一个进程可能已抢先创建 */
}
```

两个进程同时执行：A 检查「不存在」，B 也检查「不存在」，然后 A、B 都去 `open(O_CREAT)`。结果**两个进程都以为自己独占创建成功**，而磁盘上只有一个文件、却有两个「锁持有者」。

TOCTOU = **t**ime-**o**f-**c**heck, **t**ime-**o**-**u**se：**check 与 use 之间的时间窗就是竞态窗口**。`sleep(1)` 只是把这个窗口放大到肉眼可见（实测第 2 节）。

### 4.2 内核如何做到原子

```
用户态 open(path, O_CREAT | O_EXCL)
      ▼
SYSCALL_DEFINE3(open, ...)                            fs/open.c:1441
      ▼
build_open_flags()                                    fs/open.c:1222
      │  fs/open.c:1315   if (flags & O_CREAT) {
      │  fs/open.c:1316           op->intent |= LOOKUP_CREATE;
      │  fs/open.c:1317           if (flags & O_EXCL) {
      │  fs/open.c:1318                   op->intent |= LOOKUP_EXCL;
      │  fs/open.c:1319                   flags |= O_NOFOLLOW;
      ▼
namei 层：lookup_one_qstr_excl()                       fs/namei.c:1590
      inode_lock_nested(parent)   ← 父目录 inode 锁，把「查 + 建」串行化
      ├─ 目录项已存在 → return -EEXIST                  fs/namei.c:3896
      └─ 不存在 → 在同一把锁内原子创建 dentry + inode
```

关键在 `fs/open.c:1319` 那一行：

```c
flags |= O_NOFOLLOW;
```

**`O_EXCL` 顺手给自己加了 `O_NOFOLLOW`**——这不是都市传说，是源码原文。它拦掉「用符号链接把独占创建重定向到任意文件」的攻击路径。所以 `O_CREAT|O_EXCL` 的安全语义是**两条**：唯一赢家 + 不跟随符号链接。

### 4.3 典型用途

- **PID 锁文件 / 单例守护进程**：`open("/var/run/foo.pid", O_CREAT|O_EXCL|O_WRONLY, 0644)` 失败（`EEXIST`）即「已有实例在跑」。
- **临时唯一文件名**（`mkstemp` 的底层思想，见 [5.12](5.12-temporary-files.md)）。
- **防符号链接攻击**：以 root 写 `/tmp` 下文件时，配合 `O_NOFOLLOW` 生效。

## 5. 原书程序：`bad_exclusive_open.c`（Listing 5-1）与 `atomic_append.c`（习题 5-3 解答）

本章代码目录**逐字镜像**了原书 6 个文件，其中两个直接对应本节：

完整源码 [`code/bad_exclusive_open.c`](../code/bad_exclusive_open.c)（原书 **Listing 5-1**，p.90）：

```c
/*************************************************************************\

*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *

\*************************************************************************/

/* bad_exclusive_open.c

   The following code shows why we need the open() O_EXCL flag.

   This program to tries ensure that it is the one that creates the file
   named in its command-line argument. It does this by trying to open()
   the filename once without the O_CREAT flag (if this open() succeeds
   then the program know it is not the creator of the file), and if
   that open() fails, it calls open() a second time, with the O_CREAT flag.

   If the first open() fails, the program assumes that it is the creator
   of the file. However this may not be true: some other process may have
   created the file between the two calls to open().
*/
#include <sys/stat.h>
#include <fcntl.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int fd;

    if (argc < 2 || strcmp(argv[1], "--help") == 0)
        usageErr("%s file\n", argv[0]);

    fd = open(argv[1], O_WRONLY);       /* Open 1: check if file exists */
    if (fd != -1) {                     /* Open succeeded */
        printf("[PID %ld] File \"%s\" already exists\n",
                (long) getpid(), argv[1]);
        close(fd);
    } else {
        if (errno != ENOENT) {          /* Failed for unexpected reason */
            errExit("open");
        } else {
            printf("[PID %ld] File \"%s\" doesn't exist yet\n",
                    (long) getpid(), argv[1]);
            if (argc > 2) {             /* Delay between check and create */
                sleep(5);               /* Suspend execution for 5 seconds */
                printf("[PID %ld] Done sleeping\n", (long) getpid());
            }
            fd = open(argv[1], O_WRONLY | O_CREAT, S_IRUSR | S_IWUSR);
            if (fd == -1)
                errExit("open");

            printf("[PID %ld] Created file \"%s\" exclusively\n",
                    (long) getpid(), argv[1]);          /* MAY NOT BE TRUE! */
        }
    }

    exit(EXIT_SUCCESS);
}
```

它演示的正是「错误写法」：先 `open(path, O_RDONLY)` 探测，失败后才 `open(path, O_WRONLY|O_CREAT|O_EXCL, ...)`。CE 两种参数各跑一次：

```text
[PID 2] File "/dev/null" already exists
```

```text
[PID 2] File "/tmp/c5_excl_new" doesn't exist yet
[PID 2] Created file "/tmp/c5_excl_new" exclusively
```

分别是「已存在 → 拒绝」与「不存在 → 独占创建成功」两条分支。

完整源码 [`code/atomic_append.c`](../code/atomic_append.c)（原书**习题 5-3 解答**，p.110）：

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* atomic_append.c

   Demonstrate the difference between using nonatomic lseek()+write()
   and O_APPEND when writing to a file.

   Usage: file num-bytes [x]

   The program write 'num-bytes' bytes to 'file' a byte at a time. If
   no additional command-line argument is supplied, the program opens the
   file with the O_APPEND flag. If a command-line argument is supplied, the
   O_APPEND is omitted when calling open(), and the program calls lseek()
   to seek to the end of the file before calling write(). This latter
   technique is vulnerable to a race condition, where data is lost because
   the lseek() + write() steps are not atomic. This can be demonstrated
   by looking at the size of the files produced by these two commands:

        atomic_append f1 1000000 & atomic_append f1 1000000

        atomic_append f2 1000000 x & atomic_append f2 1000000 x
*/
#include <sys/stat.h>
#include <fcntl.h>
#include <stdbool.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    if (argc < 3 || strcmp(argv[1], "--help") == 0)
        usageErr("%s file num-bytes [x]\n"
                 "        'x' means use lseek() instead of O_APPEND\n",
                 argv[0]);

    bool useLseek = argc > 3;
    int flags = useLseek ? 0 : O_APPEND;
    int numBytes = getInt(argv[2], 0, "num-bytes");

    int fd = open(argv[1], O_RDWR | O_CREAT | flags, S_IRUSR | S_IWUSR);
    if (fd == -1)
        errExit("open");

    for (int j = 0; j < numBytes; j++) {
        if (useLseek)
            if (lseek(fd, 0, SEEK_END) == -1)
                errExit("lseek");
        if (write(fd, "x", 1) != 1)
            fatal("write() failed");
    }

    printf("%ld done\n", (long) getpid());
    exit(EXIT_SUCCESS);
}
```

## 6. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| 单实例交易进程 | `O_CREAT\|O_EXCL` 的 PID 锁文件，避免撮合进程被重复拉起（重复拉起 = 双份下单，事故级） |
| 多 worker 聚合日志 | `O_APPEND` 让多个风控/行情进程写同一 log 而不互相覆盖，**无需加锁**——锁会引入优先级反转与延迟抖动 |
| 回测结果落盘 | 并行回测分片各自 `O_APPEND` 写结果文件，内核替你做串行化 |
| 减一次系统调用 | `O_APPEND` 省掉每次 `lseek(SEEK_END)`；HFT 热路径上「少一次 syscall」是实打实的延迟 |
| 嵌入式 root 写配置 | `O_EXCL` 附带 `O_NOFOLLOW`（`fs/open.c:1319`）——在 `/tmp`、`/run` 等可写目录下防符号链接提权 |
| 裸 flash / 无日志文件系统 | 「丢 8236 字节」在普通 FS 上只丢数据；在没有 journal 的介质上可能出现更糟的元数据不一致——所以**永远不用 `lseek+write` 做追加** |

<summary>代码自测（Q&A）</summary>

**Q1：什么是 TOCTOU？为什么 `access()` + `open(O_CREAT)` 是它的典型例子？**
A：TOCTOU = time-of-check, time-of-use，即「检查」和「使用」之间存在可被其他执行者插入的时间窗。`access(path)` 判断「不存在」后、到 `open(O_CREAT)` 真正创建之间，另一进程可能已抢先创建，导致两个进程都误以为自己独占成功。实测第 2 节里两个 PID 都打印了「我创建了它！」。

**Q2：`O_APPEND` 的原子性在内核哪一行兑现？**
A：`fs/read_write.c:1666-1667`——`generic_write_checks_count()` 里的 `if (iocb->ki_flags & IOCB_APPEND) iocb->ki_pos = i_size_read(inode);`，即每次写之前在同一次写操作内部把位置设为当前 `i_size`。用户态的 `lseek(SEEK_END)` + `write()` 是两个独立系统调用，做不到这一点（实测丢 8236 字节）。

**Q3：`open(path, O_CREAT | O_EXCL)` 在文件已存在时返回什么？**
A：返回 `-1`，`errno = EEXIST`（实测 `errno=17`）。来源在 `fs/namei.c:3896` 的 `error = -EEXIST;`。

**Q4：为什么实测里 `lseek+write` 丢的字节数每轮都不一样？**
A：因为丢数据来自两个进程的相对执行顺序（竞态），不是确定性错误。本仓库首轮跑丢 `192145` 字节，定稿这轮丢 `8236` 字节——**数字不同本身就是「这是竞态」的证据**。凡是有所谓「固定丢失量」的说法都值得怀疑。

**Q5：`O_EXCL` 只带 `O_CREAT` 才有意义吗？**
A：是。`fs/open.c:1315` 是 `if (flags & O_CREAT) {`，`O_EXCL` 的检查在它内层（`:1317`）。POSIX 规定 `O_EXCL` 与 `O_CREAT` 组合使用；单独给 `O_EXCL` 无意义。

**Q6：`O_EXCL` 还有额外作用吗？**
A：有，而且是源码明文：`fs/open.c:1319` 的 `flags |= O_NOFOLLOW;`。设置 `LOOKUP_EXCL` 的同时自动带上不跟随符号链接，防止用符号链接把独占创建重定向到别的文件。

**Q7：为什么说「多进程日志必须用 `O_APPEND`」而不是「用锁保护 `lseek+write`」？**
A：锁能解决正确性，但引入额外开销与死锁/优先级反转风险；`O_APPEND` 把原子性下沉到内核（`fs/read_write.c:1666-1667`），用户态一次 `write` 即可，没有锁、没有第二次系统调用。对 HFT 这种延迟敏感场景，这是标准做法。

</details>
