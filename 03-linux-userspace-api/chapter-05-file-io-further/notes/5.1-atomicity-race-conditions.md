## 本节讲什么

多进程/多线程同时操作文件时，两个「看起来没问题的操作」可能因为执行顺序交错而互相踩踏。本节回答三个问题：

1. 「原子性（atomicity）」到底指什么？为什么文件 I/O 里它如此关键？
2. `O_EXCL | O_CREAT` 和 `O_APPEND` 这两个标志，各自解决了哪类竞态？
3. 什么是 TOCTOU（time-of-check, time-of-use），以及为什么「先检查再操作」的写法几乎总是错的？

---

## 1. 竞态条件与原子性

**竞态条件（race condition）**：多个进程/线程的执行结果，取决于它们指令的**相对执行顺序**。只要有一个交错顺序会导致错误结果，代码就是有 bug 的——哪怕它 99% 的时候都对。

**原子性（atomicity）**：一个操作「要么完全执行、要么完全不执行」，中间状态对其他进程**不可见**。原子操作天然免疫竞态，因为不存在「执行到一半被打断」的窗口。

文件 I/O 里最常见的两类竞态，TLPI 5.1 各给了原子化解法：

| 场景 | 非原子（错误）写法 | 原子（正确）写法 |
|------|-------------------|-----------------|
| 独占创建文件（如 PID 锁文件） | `access(path)` 检查不存在 → `open(O_CREAT)` | `open(path, O_CREAT \| O_EXCL)` |
| 多进程追加日志 | `lseek(fd, 0, SEEK_END)` → `write(fd, ...)` | `open(path, O_APPEND)`，直接 `write` |

下面分别拆解。

## 2. `O_EXCL | O_CREAT`：原子独占创建

### 为什么 `access()` + `open()` 是错的

```c
/* 反例：TOCTOU —— check 和 use 之间被别的进程插入 */
if (access(path, F_OK) == -1) {         /* check：现在还不存在 */
    fd = open(path, O_CREAT, 0644);     /* use：另一个进程可能已抢先创建 */
}
```

两个进程同时执行这段代码：A 检查「不存在」，B 也检查「不存在」，然后 A、B 都去 `open(O_CREAT)`。结果**两个进程都以为自己独占创建成功**，最后只有一个文件，两个「锁持有者」同时存在——这正是 TOCTOU：**check（access）和 use（open）之间的时间窗就是竞态窗口**。

### 内核如何做到原子

`O_EXCL` 的原子性不在用户态，而在内核的路径查找（namei）层——它在**目录项锁保护下**一次性完成「查无此文件则创建，有则失败」：

```
用户态 open(path, O_CREAT | O_EXCL)
      ▼
SYSCALL_DEFINE3(open)                    fs/open.c:1441
      ▼
do_sys_openat2 → build_open_flags()      fs/open.c:1222
      ├─ O_CREAT → op->intent |= LOOKUP_CREATE      :1315
      └─ O_EXCL  → op->intent |= LOOKUP_EXCL        :1317
                        （并附带 O_NOFOLLOW，防符号链接攻击）
      ▼
namei 层 lookup_one_qstr_excl()          fs/namei.c:3885
      create_flags = LOOKUP_CREATE | LOOKUP_EXCL    :3866
      inode_lock_nested(parent)          ← 父目录 inode 锁，串行化「查+建」
      ├─ d_is_positive(dentry) 已存在？
      │     └─ 是 → return -EEXIST                    :3896-3897
      └─ 否 → 原子创建新 dentry + inode
```

关键在于 `inode_lock_nested(parent)`：**「查目录项是否存在」和「创建新目录项」发生在同一把父目录锁内**，其他进程无法插入。`O_EXCL` 保证「若文件已存在，`open` 失败返回 `EEXIST`；若成功返回，则一定是我创建的」。这就是原子性——没有中间状态可被观察。

### 典型用途

- **PID 锁文件 / 单例守护进程**：`open("/var/run/foo.pid", O_CREAT|O_EXCL|O_WRONLY)` 失败即「已有实例在跑」。
- **临时唯一文件名**（配合 `O_TMPFILE` 或 mkstemp 的思想）。

## 3. `O_APPEND`：原子追加

### 为什么 `lseek(SEEK_END)` + `write()` 是错的

```c
/* 反例：两个进程共享同一打开描述时（或各自打开但用 lseek 定位） */
off_t end = lseek(fd, 0, SEEK_END);   /* A 读到末尾 = 100 */
/* —— 此时 B 也 lseek 到 100，并 write 了 10 字节 —— */
write(fd, buf, 20);                   /* A 从 100 写 20 字节，覆盖 B 刚写的 */
```

`lseek` 和 `write` 是**两个独立 syscall**，中间的窗口里另一进程可能已经移动了偏移或写了数据。A 的 20 字节会**覆盖** B 刚写的内容，而不是接在真正的末尾。

### `O_APPEND` 的原子语义

以 `O_APPEND` 打开后，每次 `write()` 前，内核会**原子地**把文件偏移设为「当前文件末尾」，再执行写——「定位」和「写」被合并进同一次写操作，中间没有可被抢占的窗口：

```
open(path, O_APPEND)
      ▼
build_open_flags()                       fs/open.c:1308
      O_APPEND → acc_mode |= MAY_APPEND  （LSM 据此区分 append vs write）
      ▼
后续每次 write：
      file->f_flags 里保留 O_APPEND
      → 写路径在写前原子地把 ki_pos 设为 i_size_read(inode)
        （「原子定位 + 写」由内核在单次写操作内完成，无用户态 lseek 窗口）
```

> 注：`O_APPEND` 的「写前定位到 EOF」发生在通用写路径（`mm/filemap.c` 的 `generic_file_write_iter` 通过 `IOCB_APPEND` 标志处理，`kiocb_set_rw_flags` 依据 `file->f_flags & O_APPEND` 设置）。缓存未收录 `mm/filemap.c`，此处作架构说明；用户态语义（`write` 前原子定位到 EOF）是 POSIX 明确规定、且被 `build_open_flags` 的 `MAY_APPEND` 与 `f_flags` 保留所支撑的。

### 关键推论

| 特性 | 说明 |
|------|------|
| 追加永远接在末尾 | 多个进程各自 `O_APPEND` 打开同一文件并 `write`，数据不会互相覆盖 |
| 原子性边界 | 单次 `write()` 原子；若一次写 > `PIPE_BUF` 级别的大块，仍建议依赖 `O_APPEND` 而非手动定位 |
| 与偏移的关系 | `O_APPEND` 下 `lseek` 基本无用——每次写都会回到末尾 |
| 典型场景 | 多进程日志聚合（如多 worker 写同一 log 文件）、数据库 WAL 追加 |

## 4. HFT / 嵌入式关联

| 场景 | 本节机制的兑现 |
|------|----------------|
| 单实例守护进程 | `O_CREAT\|O_EXCL` 的 PID 锁文件，避免交易进程被重复拉起 |
| 多 worker 聚合日志 | `O_APPEND` 让多个撮合/风控进程写同一日志而不互相覆盖，无需加锁 |
| 回测结果落盘 | 并行回测分片各自 `O_APPEND` 写结果文件，天然串行化追加 |
| 防 TOCTOU 安全漏洞 | 嵌入式设备上以 root 写配置文件时，`O_EXCL` 防止「检查→创建」窗口被符号链接攻击（`O_NOFOLLOW` 附带生效） |
| 少一次 syscall | `O_APPEND` 省去每次 `lseek(SEEK_END)`，HFT 高频写路径更省 |

## 5. 代码示例

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>

/* 5.1 原子性：O_EXCL 独占创建 + O_APPEND 原子追加 */
int main(void) {
    /* 1) O_EXCL|O_CREAT：独占创建，已存在则失败 */
    int fd = open("/tmp/single.lock", O_CREAT | O_EXCL | O_WRONLY, 0644);
    if (fd < 0) {
        if (errno == EEXIST)
            printf("已有实例在运行（锁文件已存在）\n");
        else
            perror("open O_EXCL");
        return 1;
    }
    printf("独占创建成功，取得锁\n");

    /* 2) O_APPEND：每次 write 原子追加到末尾 */
    int logfd = open("/tmp/app.log", O_WRONLY | O_APPEND | O_CREAT, 0644);
    const char *line = "one more line\n";
    /* 无需 lseek(SEEK_END)，write 直接接到文件末尾 */
    write(logfd, line, strlen(line));

    close(logfd);
    close(fd);
    return 0;
}
```

<details>
<summary>代码自测（Q&A）</summary>

**Q1：什么是 TOCTOU？为什么 `access()` + `open(O_CREAT)` 是它的典型例子？**
A：TOCTOU = time-of-check, time-of-use，即「检查」和「使用」之间存在可被其他进程插入的时间窗。`access(path)` 判断「文件不存在」后、到 `open(O_CREAT)` 真正创建之间，另一进程可能已抢先创建，导致两个进程都误以为自己独占成功。`O_EXCL|O_CREAT` 把「检查 + 创建」合并成内核里一次原子操作，消除了这个窗口。

**Q2：`open(path, O_CREAT | O_EXCL)` 在文件已存在时返回什么？**
A：返回 `-1`，`errno = EEXIST`。这正是它作为「锁文件」判据的价值——失败即代表已有人创建。

**Q3：`O_APPEND` 为什么能避免 `lseek(SEEK_END) + write` 的覆盖问题？**
A：`lseek` 和 `write` 是两个独立 syscall，中间窗口内偏移可能被其他进程改变。`O_APPEND` 让内核在**单次 write 操作内**先原子地把偏移定位到文件末尾再写，不存在可被抢占的中间态，因此多进程追加不会互相覆盖。

**Q4：`O_EXCL` 为什么不带 `O_CREAT` 就无意义？**
A：`O_EXCL` 的语义是「创建时若已存在则失败」，它只约束**创建**这个动作。单独 `O_EXCL`（不带 `O_CREAT`）在多数系统上会被忽略或报错——POSIX 规定 `O_EXCL` 仅与 `O_CREAT` 组合使用，`build_open_flags` 里也是在 `if (flags & O_CREAT)` 分支内才检查 `O_EXCL` 并设置 `LOOKUP_EXCL`。

**Q5：`O_EXCL | O_CREAT` 还有防符号链接攻击的附加作用吗？**
A：有。`build_open_flags` 在设置 `LOOKUP_EXCL` 的同时会附带 `flags |= O_NOFOLLOW`（`fs/open.c:1317-1318`），即不跟随符号链接，防止攻击者用符号链接把「独占创建」重定向到任意文件。这是独占创建安全语义的一部分。

</details>
