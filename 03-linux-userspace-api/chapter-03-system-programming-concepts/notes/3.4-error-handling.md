## 本节讲什么

系统调用和库函数**失败时返回 -1 并设置 `errno`**，正确读写 `errno` 是所有系统编程的底线。本节回答三个问题：

1. `errno` 是什么？为什么「成功不会清零它」？
2. 内核的「负错误码」怎么变成 glibc 的「-1 + errno」？
3. `perror`/`strerror`/`strerror_r` 该怎么选？HFT 的错误处理有什么讲究？

---

## 1. `errno` 机制：成功不清零、失败才赋值

| 规则 | 说明 |
|------|------|
| 成功 | **不会**把 `errno` 清零（保留上一次的值） |
| 失败 | 才被赋为有意义的值 |
| 线程局部 | 现代 glibc 里 `errno` 是**线程局部**变量（每线程独立，见 2.12） |
| 类型 | `int`（`<errno.h>`），值是 `E*` 宏（如 `ENOENT`=2） |

**关键坑**：不能「先调函数、再看 errno」，必须「先看返回值、失败才读 errno」：

```c
/* ❌ 错误：成功路径也可能留下旧 errno */
open(path, O_RDONLY);
if (errno != 0) { ... }      /* errno 可能是上一次失败留下的脏值！ */

/* ✅ 正确：先看返回值，失败再读 errno */
int fd = open(path, O_RDONLY);
if (fd == -1) {
    /* 此时 errno 才有意义 */
    perror("open");
}
```

因为成功时内核/glibc **不碰 errno**，它保留的是**上一次**失败的值。用 `if (errno)` 判断成功与否是经典 bug。

## 2. 底层机制：`MAX_ERRNO` 与负错误码

「返回 -1 + 设 errno」是 glibc 的**翻译结果**，内核实际返回的是 `-errno`：

```
内核返回：成功 → 返回值（fd ≥ 0 / 指针）
          失败 → rax = -errno（落在 [-4095, -1]）
                  ↑ MAX_ERRNO = 4095（include/linux/err.h:17）
      │
glibc 判断 rax ∈ [-4095, -1] ?
      ├─ 是 → errno = -rax，返回 -1
      └─ 否 → 返回 rax（合法值）
```

所以直接 `syscall(SYS_open, ...)` 拿到的返回值是 **`-2`（-ENOENT）**，不是 `-1`——因为你绕过了 glibc 的翻译层（见 3.3）。这也是「错误码都是小负数」的由来：`-1 ~ -4095` 被内核保留给错误码，`0` 以上的才是合法返回值（fd、指针、字节数）。

## 3. 常见错误码速查（HFT 高频）

| errno | 值 | 含义 | 典型场景 |
|-------|-----|------|----------|
| `EPERM` | 1 | 权限不足（无 capability） | 绑低端口、改系统参数 |
| `ENOENT` | 2 | 文件/目录不存在 | 配置文件路径写错 |
| `EINTR` | 4 | 被信号打断 | `read`/`epoll_wait` 被信号中断 |
| `EAGAIN`/`EWOULDBLOCK` | 11 | 非阻塞操作暂无数据 | 非阻塞 fd 读空 |
| `ENOMEM` | 12 | 内存不足 | 分配失败 |
| `EACCES` | 13 | 权限拒绝 | 打开无权限文件 |
| `EFAULT` | 14 | 传给内核的指针非法 | 野指针传给 syscall |
| `EBUSY` | 16 | 资源忙 | 文件锁冲突、设备占用 |
| `EINVAL` | 22 | 参数无效 | flags 传错 |
| `EMFILE` | 24 | 进程 fd 数达上限 | fd 泄漏 |
| `ENOSPC` | 28 | 磁盘满 | 写盘失败 |
| `EPIPE` | 32 | 读端已关闭的管道 | 写已关闭的 socket |

> **`EINTR` 是系统编程最常被忽略的错误码**：系统调用被信号打断时返回 -1 + `EINTR`，这是**正常情况不是错误**，应重试而不是报错退出（见 Ch21 信号、Ch63 epoll）。

## 4. 打印 / 退出工具

| 函数 | 作用 | 注意 |
|------|------|------|
| `perror(msg)` | 打印 `msg: strerror(errno)` 到 stderr | 用当前 errno，最简单 |
| `strerror(errnum)` | 错误码 → 字符串 | **非线程安全**（静态缓冲区） |
| `strerror_r(errnum, buf, len)` | 线程安全版 | GNU 语义返回 `char*`，POSIX 语义返回 `int`（musl 差异点） |
| TLPI `errExit(msg)` | 打印 + `exit` | 原书封装 |
| TLPI `errMsg(msg)` | 只打印不退出 | 原书封装 |
| TLPI `fatal(msg)` | 逻辑错误（非 syscall） | 原书封装 |

TLPI 全书示例统一用 `tlpi_hdr.h` + `error_functions.c`（`errExit`/`errMsg`/`fatal`/`usageErr`），见 man7 源码包。核心是「错误消息带上 errno 文本」，方便定位。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| `EINTR` 打断热路径 | `recv`/`epoll_wait` 被信号打断返回 EINTR，必须重试，否则漏掉行情/事件 |
| fd 泄漏排查 | 长期运行报 `EMFILE` = fd 泄漏，用 `/proc/[pid]/fd` 数 fd（见 2.19） |
| 非阻塞读空 | `EAGAIN` 是「暂无数据」的正常信号，不是错误，循环里要区分处理 |
| 错误日志 | 用 `strerror_r`（线程安全）+ 完整上下文（哪个 syscall、哪个参数、errno） |
| 野指针传内核 | `EFAULT` 说明把非法地址传给了 syscall，是内存 bug 而非 I/O 错误 |

## 6. 代码示例

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    /* 1. 标准错误处理：先返回值，失败读 errno */
    int fd = open("/no/such/file", O_RDONLY);
    if (fd == -1) {
        perror("open failed");                       /* "open failed: No such file..." */
        fprintf(stderr, "errno=%d (%s)\n", errno, strerror(errno));
    }

    /* 2. 线程安全版 strerror_r（GNU 语义返回 char*） */
    char buf[128];
    fprintf(stderr, "thread-safe: %s\n",
            strerror_r(ENOENT, buf, sizeof(buf)));

    /* 3. EINTR 重试模式 */
    char rbuf[16];
    ssize_t n;
    do {
        n = read(STDIN_FILENO, rbuf, sizeof(rbuf));
    } while (n == -1 && errno == EINTR);   /* 被信号打断，重试 */
    if (n == -1) perror("read");

    return 0;
}
```

编译：`gcc -o err err.c && ./err`。观察 `perror` 的「前缀 + errno 文本」格式，以及 `strerror_r` 的线程安全用法。

<summary>代码自测（Q&A）</summary>

**Q1：为什么「成功不会清零 errno」？这会导致什么 bug？**
A：因为成功时内核/glibc 不去碰 `errno`（省一次写），它保留的是**上一次失败**留下的旧值。这导致 `if (errno != 0)` 判断成败是错的——可能上一次失败的脏值还在。正确做法是**先看返回值**（如 `fd == -1`），失败后才读 `errno`。

**Q2：系统调用失败，为什么「返回 -1」而具体原因在 errno？底层机制是什么？**
A：内核实际返回的是**负错误码**（`-errno`，如 `-ENOENT`=`-2`，落在 `[-4095,-1]`，`MAX_ERRNO=4095`）。glibc 包装判断返回值是否在这个范围：是则 `errno = -返回值`、返回 `-1`，否则当作合法返回值。所以「-1 + errno」是 glibc 翻译的结果——直接 `syscall()` 拿到的是 `-2` 不是 `-1`。

**Q3：`EINTR` 是什么？为什么它不是真正的「错误」？**
A：`EINTR`（=4）表示系统调用被**信号**打断了——某个信号处理函数执行完，被阻塞的系统调用（`read`/`epoll_wait` 等）返回 -1 + `EINTR`。这是**正常情况**，不是 I/O 失败，应该**重试**（`while (n==-1 && errno==EINTR)`），而不是当作错误退出。忽略它会导致热路径偶发漏读事件。

**Q4：`perror`、`strerror`、`strerror_r` 有什么区别？多线程该用哪个？**
A：`perror(msg)` 打印 `msg: 错误文本` 到 stderr（用当前 errno，最简单）；`strerror(errnum)` 把错误码转成字符串，但用**静态缓冲区**，**非线程安全**；`strerror_r` 是**线程安全**版（写入调用者提供的 buf）。多线程程序（HFT 交易系统）必须用 `strerror_r`，避免多个线程同时调 `strerror` 互相覆盖缓冲区。

**Q5：`EAGAIN` 和 `EACCES` 分别是什么？如何区分处理？**
A：`EAGAIN`（=11，非阻塞模式下 =`EWOULDBLOCK`）表示「资源暂时不可用、稍后重试」——如非阻塞 fd 读空、socket 发送缓冲满，是**可恢复的暂时状态**，应重试或进 epoll 等待；`EACCES`（=13）表示「权限不足」，是**永久性失败**，重试也没用，应报错或换权限。两者本质不同：一个「等一会再来」，一个「根本没权限」。
