## 本节讲什么

同一份 C 代码，为什么在 Linux 能编译、换到别的 Unix 就报「未声明函数」？为什么手册里总让你在开头定义 `_GNU_SOURCE`？为什么文件偏移不能写死 `long`？本节回答三个问题：

1. 功能测试宏（`_POSIX_C_SOURCE` / `_XOPEN_SOURCE` / `_GNU_SOURCE`）是什么？为什么必须放在**所有 `#include` 之前**？
2. 标准 typedef（`off_t` / `pid_t` / `size_t`）为什么比裸 `int` / `long` 可移植？`_FILE_OFFSET_BITS=64` 解决什么？
3. SUSv3 / POSIX 这套标准到底规定了什么？glibc 怎么用 `features.h` 落实「方言切换」？

---

## 1. 可移植性到底难在哪

「可移植」不是「写一次到处跑」，真正的障碍是这三件事：

| 障碍 | 例子 | 后果 |
|------|------|------|
| **API 存在性** | `epoll` 只有 Linux；`kqueue` 只有 BSD | 直接调用 → 别的平台编译不过 |
| **类型宽度** | `long` 在 32 位平台是 4 字节、64 位平台是 8 字节 | 文件偏移 / ID 溢出，ABI 不匹配 |
| **语义细节** | `strerror_r` 返回值：glibc 是 `char*`、musl 是 `int` | 同一函数不同 C 库行为不同 |

Linux 世界解决这三件事的标准武器，就是**功能测试宏**（管「暴露哪些 API」）+ **标准 typedef**（管「类型宽度跨平台一致」）。

## 2. 功能测试宏（Feature Test Macros）

glibc 里藏着一大堆非标准 / 各标准版本的函数。默认情况下 glibc 只暴露**最保守的一批**（ISO-C + 基础 POSIX）。要解锁更多 API，得先「声明自己要用哪个标准」——这就是功能测试宏。

| 宏 | 取值示例 | 解锁什么 | 谁定义 |
|----|----------|----------|--------|
| `_POSIX_C_SOURCE` | `200809L` | POSIX.1-2008 标准接口 | POSIX |
| `_XOPEN_SOURCE` | `700` | SUSv4（X/Open 扩展，POSIX 超集） | SUS |
| `_GNU_SOURCE` | （有定义即可） | 全部 + Linux/GNU 扩展（`epoll`、GNU 版 `strerror_r`） | glibc |
| `_DEFAULT_SOURCE` | （有定义即可） | 恢复 glibc 默认暴露的杂项 BSD/Linux 函数 | glibc |

**两条铁律：**

1. **必须放在所有 `#include` 之前**——功能测试宏在 `<features.h>` 里被读一次就「定型」，先 `#include` 了别的头再定义宏 = 无效。

```c
/* ❌ 错误：宏定义太晚，前两个 include 已经按默认方言展开过了 */
#include <stdio.h>
#include <unistd.h>
#define _GNU_SOURCE        // 到这里才定义，前面的头已经定死

/* ✅ 正确：宏必须在最前面，或在编译命令里 -D_GNU_SOURCE */
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
```

2. **`_GNU_SOURCE` 最省心但最不「可移植」**——它解锁了所有 Linux 专属函数，代价是写出来的代码一旦用了 `epoll` / GNU 版 `strerror_r`，换到非 glibc 环境就可能编译不过。追求「只在 Linux 上跑」就用 `_GNU_SOURCE`；追求「严格 POSIX 可移植」就只用 `_POSIX_C_SOURCE=200809L`。

编译期等价写法：

```bash
gcc -D_GNU_SOURCE -o prog prog.c          # 等价于源码里 #define _GNU_SOURCE
gcc -D_POSIX_C_SOURCE=200809L -o prog prog.c   # 严格 POSIX，锁掉 GNU 扩展
```

## 3. 标准 typedef：别写死 int / long

系统调用的参数和返回值大量用**标准 typedef**，而不是裸 `int`/`long`，就是为了让类型宽度在跨平台时**由头文件统一决定**：

| 类型 | 用途 | 定义处（glibc） |
|------|------|-----------------|
| `pid_t` | 进程 ID | `<bits/types.h>` → `__pid_t` |
| `off_t` | 文件偏移 | `<bits/types.h>` → `__off_t` |
| `size_t` / `ssize_t` | 无符号 / 有符号长度 | `<stddef.h>` / `<sys/types.h>` |
| `uid_t` / `gid_t` | 用户 / 组 ID | `<bits/types.h>` |
| `mode_t` | 文件权限位 | `<bits/types.h>` |
| `dev_t` / `ino_t` | 设备号 / inode 号 | `<bits/types.h>` |

**最经典的坑是 `off_t` 与大文件**：32 位平台上 `off_t` 默认是 32 位，`lseek` 无法处理 >2GB 的偏移。解决办法是定义 `_FILE_OFFSET_BITS=64`，让 `off_t` 变成 64 位：

```c
#define _FILE_OFFSET_BITS 64   /* 32 位平台也要能操作 >2GB 大文件 */
#include <sys/types.h>
#include <unistd.h>

off_t pos = lseek(fd, 0, SEEK_END);   /* 现在 off_t 是 64 位，不会溢出 */
```

**为什么别写死 `long`**：`long` 的宽度跟平台走（LP64 下 8 字节，ILP32 下 4 字节），而 `off_t` 的宽度由 `_FILE_OFFSET_BITS` 决定，两者可能不一致。写死 `long` 当偏移，在 32 位平台 + 大文件场景下必然溢出或错位。用标准 typedef，让头文件替你管宽度。

## 4. SUSv3 / POSIX 标准演进

| 年份 | 标准 | 说明 |
|------|------|------|
| 1988 | POSIX.1-1988 | 第一版，系统接口 + shell |
| 1990 | POSIX.1-1990 (ISO 9945-1) | 成为 ISO 标准 |
| 1996 | POSIX.1-1996 | 实时扩展（信号量、时钟、调度） |
| 2001 | **POSIX.1-2001 = SUSv3** | 合并 X/Open，TLPI 全书基线 |
| 2008 | **POSIX.1-2008 = SUSv4** | 当前主流，`_POSIX_C_SOURCE=200809L` |

TLPI 全书以 **SUSv3** 为基线，并标注「这是 Linux 扩展」的地方。读 TLPI 时遇到「SUSv3 规定……」意味着：这是 POSIX 保证的接口，任何合规 Unix 都有；而「Linux 特有」意味着：换平台要自己找替代（如 `epoll` ↔ `kqueue`）。

## 5. glibc 怎么落实方言切换：features.h

功能测试宏的真正机制在 `<features.h>`——所有 glibc 标准头文件开头都 `#include <features.h>`，它读一遍功能测试宏，据此 `#define` 或 `#undef` 一堆 `__USE_*` 内部开关，后续头文件再按这些开关决定「这个函数声明要不要露出来」。

```
#include <unistd.h>
      │  开头 #include <features.h>
      ▼
features.h 读 _GNU_SOURCE / _POSIX_C_SOURCE / _XOPEN_SOURCE ...
      │  换算成 __USE_GNU / __USE_POSIX / __USE_XOPEN ... 内部开关
      ▼
后续头文件按 __USE_* 决定暴露哪些声明（如 epoll_create 只在 __USE_GNU 时声明）
```

这就是「功能测试宏必须在最前面」的底层原因：`<features.h>` 只会被有效处理一次，先 include 别的头就会用「默认方言」把开关定死。

## 6. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 静态可移植二进制 | 用 musl + 严格 POSIX（`_POSIX_C_SOURCE`）编译，摆脱 glibc 方言依赖（见 glibc 节） |
| 大文件 / 大偏移 | 行情回放、日志文件 >2GB 时必须 `_FILE_OFFSET_BITS=64`，否则 `lseek` 溢出 |
| 锁死 GNU 扩展 | 用 `epoll`/`io_uring` 时需 `_GNU_SOURCE`；这是「只在 Linux 跑」的显式声明 |
| 交叉编译 | 功能测试宏 + 标准 typedef 保证目标平台 ABI 正确，不依赖宿主机类型宽度 |
| 类型宽度敏感 | HFT 里用 `int64_t` 存时间戳/序号，别用可能 32 位的 `long` |

## 7. 代码示例

```c
#define _GNU_SOURCE            /* 1. 功能测试宏必须在最前面 */
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main(void) {
    /* 2. 编译期查看已生效的功能测试宏 */
#ifdef _POSIX_C_SOURCE
    printf("_POSIX_C_SOURCE = %ldL\n", (long)_POSIX_C_SOURCE);
#else
    printf("_POSIX_C_SOURCE 未定义\n");
#endif

#ifdef _GNU_SOURCE
    printf("_GNU_SOURCE 已定义 → epoll 等 GNU 扩展可用\n");
#endif

    /* 3. 标准 typedef：pid_t 不写死 int */
    pid_t pid = getpid();
    printf("pid = %d (pid_t)\n", (int)pid);

    /* 4. sysconf 查询系统限制（POSIX 保证的接口） */
    printf("sysconf(_SC_OPEN_MAX) = %ld\n", sysconf(_SC_OPEN_MAX));
    return 0;
}
```

编译验证方言差异：

```bash
gcc -o a a.c                              # 默认：GNU 扩展不可见
gcc -D_GNU_SOURCE -o b a.c                # 解锁 GNU 扩展
gcc -D_POSIX_C_SOURCE=200809L -o c a.c    # 严格 POSIX，锁掉 GNU 扩展
```

<summary>代码自测（Q&A）</summary>

**Q1：功能测试宏为什么必须放在所有 `#include` 之前？**
A：因为 glibc 的所有标准头文件开头都会 `#include <features.h>`，它读取功能测试宏并**一次性**换算成 `__USE_*` 内部开关。如果你先 `#include` 了别的头，`features.h` 已经在「默认方言」下把开关定死了，之后再 `#define _GNU_SOURCE` 也不生效。所以宏必须在最前面，或编译期用 `-D` 传入。

**Q2：`_GNU_SOURCE`、`_POSIX_C_SOURCE`、`_XOPEN_SOURCE` 分别解锁什么？**
A：`_POSIX_C_SOURCE`（如 `200809L`）解锁 POSIX.1-2008 标准接口；`_XOPEN_SOURCE`（如 `700`）解锁 SUSv4（POSIX 超集，X/Open 扩展）；`_GNU_SOURCE` 解锁全部 + Linux/GNU 扩展（`epoll`、GNU 版 `strerror_r`）。`_GNU_SOURCE` 最省心但最不「可移植」——用了 GNU 扩展的代码换到非 glibc 环境可能编译不过。

**Q3：`off_t` 为什么不能写死成 `long`？`_FILE_OFFSET_BITS=64` 干嘛的？**
A：`long` 的宽度跟平台走（32 位 4 字节、64 位 8 字节），而 `off_t` 的宽度由 `_FILE_OFFSET_BITS` 决定。32 位平台上 `off_t` 默认 32 位，无法处理 >2GB 的文件偏移；定义 `_FILE_OFFSET_BITS=64` 后 `off_t` 变 64 位。写死 `long` 当偏移，在 32 位 + 大文件场景必然溢出或错位。用标准 typedef，让头文件替你管宽度。

**Q4：标准 typedef（`pid_t`/`off_t`/`mode_t` 等）本质是什么？在哪定义的？**
A：本质是「类型宽度的跨平台抽象」——用 `pid_t` 而不是 `int`，让头文件根据平台决定实际宽度。glibc 里它们在 `<bits/types.h>` 定义为 `__pid_t`/`__off_t` 等底层类型，再由 `<sys/types.h>` 等标准头 `typedef` 成公开名字。开发者只认公开的 `pid_t`/`off_t`，不关心底层是 `int` 还是 `long`。

**Q5：SUSv3 和 POSIX 是什么关系？TLPI 为什么以 SUSv3 为基线？**
A：SUSv3（Single UNIX Specification v3）= POSIX.1-2001，是 POSIX 与 X/Open 标准合并后的统一标准；SUSv4 = POSIX.1-2008 是当前主流。TLPI 以 SUSv3 为基线，遇到「SUSv3 规定……」意味着这是 POSIX 保证的接口（任何合规 Unix 都有），而「Linux 特有」意味着换平台要自己找替代（如 `epoll` ↔ `kqueue`）。

</details>
