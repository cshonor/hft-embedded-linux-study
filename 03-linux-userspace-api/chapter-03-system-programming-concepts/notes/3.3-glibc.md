## 本节讲什么

TLPI 第 3.3 节标题里其实藏着三层身份，很多人读到这里会把它们混成一句话：

| 层 | 是什么 | 由什么标出 |
|----|--------|------------|
| **C 语言标准** | ISO C / C99 / C11 / C17 —— 语言层面的库函数规格 | `__STDC_VERSION__` |
| **POSIX / SUS** | 操作系统接口规范（`open`/`read`/`fork`…） | `_POSIX_VERSION`（来自 `<unistd.h>`） |
| **具体实现** | glibc / musl / uClibc / bionic —— 上面两者的落地 | glibc 用 `__GLIBC__` + `gnu_get_libc_version()` 标出自己 |

本节回答三个问题：

1. glibc 到底提供了什么？它和「C 标准库」「POSIX」是什么关系？
2. glibc 封装系统调用时，怎么把内核的**负错误码**翻译成 `errno` + `-1`？
3. 怎么在代码里**认出**当前是哪个实现？为什么这件事在交叉编译时很值钱？

---

## 1. glibc 的角色：一个库，三种身份

| 身份 | 提供什么 | 例子 |
|------|----------|------|
| **ISO-C 标准库实现** | C 语言标准要求的函数 | `printf` / `malloc` / `strcpy` / `qsort` |
| **POSIX 封装层** | 系统调用的薄外壳 | `open` / `read` / `write` / `fork` / `mmap` |
| **glibc 扩展** | Linux 专属的非标准函数与语义 | `epoll` 系列、GNU 版 `strerror_r`、`%m` 格式符 |

所以「glibc」**不是**「C 标准库」的同义词——它**包含** C 标准库，还**多出** POSIX 封装和一堆 Linux 扩展。换个 C 库（musl），C 标准库函数还在，但扩展函数和某些行为细节会变。

## 2. glibc 怎么封装系统调用：`MAX_ERRNO` 错误翻译

glibc 的 `open()` 不是把内核返回值原样传回，而是做一次**错误翻译**。关键在内核的错误返回约定：

```c
/* include/linux/err.h:17 —— 内核错误码的取值范围 */
#define MAX_ERRNO	4095
```

完整往返流程：

```
用户态调 open(path, flags)
      │  glibc 包装：rax=2(调用号), rdi=path, rsi=flags, rdx=mode
      ▼
syscall 指令陷入内核（arch/x86/entry/entry_64.S:87）
      │  arch/x86/entry/common.c:50  regs->ax = sys_call_table[nr](regs)
      ▼
内核返回：成功 → rax = 新 fd（≥ 0）
          失败 → rax = -errno（如 -2 = -ENOENT，落在 [-4095, -1]）
      ▼
glibc 包装判断：rax 是否落在 [-4095, -1]？
      ├─ 是 → errno = -rax（如 2），返回 -1
      └─ 否 → 返回 rax（合法 fd）
```

**这就是「系统调用失败返回 -1、具体原因看 `errno`」的底层机制。** 顺带解释了 [3.1](3.1-system-calls.md) 里那条反直觉的实测：绕过 glibc 之后拿到的返回值是**负错误码**（`-9`/`-38`），不是 `-1`——因为翻译那一步没了。

### glibc 版本 vs 内核版本

两者**没有** 1:1 对应关系：

- glibc 封装系统调用，但**滞后于内核**。新内核特性（`io_uring`、`close_range`、`pidfd_*`）要等 glibc 出新版本提供封装才能直接用；等不及时就自己 `syscall(SYS_xxx, ...)`（见 [3.1](3.1-system-calls.md) ③⑥ 段）。
- 老 glibc 跑在新内核上通常没问题（内核 ABI 向后兼容），但用不到新 syscall 的现成封装。
- 反过来：**新 glibc 编出的二进制跑在老 glibc 上会报 `GLIBC_2.xx not found`**——它链接了对旧版本不存在的符号版本。

## 3. 代码示例：认出你用的是哪个实现

源码：[../code/c3_3_glibc.c](../code/c3_3_glibc.c)

```c
/* TLPI 第 03 章 §3.3 —— 标准 C 库 vs GNU C 库：怎么认出你用的是哪一个
 *
 * 三层身份要分开：
 *   ① C 语言标准（ISO C / C99 / C11…）—— 由 __STDC_VERSION__ 标出
 *   ② POSIX / SUS 规范            —— 由 _POSIX_VERSION 标出（来自 unistd.h）
 *   ③ 具体实现（glibc / musl / uClibc / bionic）—— glibc 会定义 __GLIBC__ 并给出
 *      gnu_get_libc_version()、confstr(_CS_GNU_LIBC_VERSION)
 *
 * 嵌入式/HFT 的用处：交叉编译时「板上跑的是 glibc 还是 musl」决定了一堆行为差异
 * （NSS、locale、malloc 实现、dlopen 语义），所以部署脚本里认一下版本很值。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_3 c3_3_glibc.c
 */
#define _GNU_SOURCE
#include <features.h>
#include <gnu/libc-version.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    printf("=== ① 实现身份：这是 glibc 吗？ ===\n");
#ifdef __GLIBC__
    printf("  __GLIBC__       = %d\n", __GLIBC__);
    printf("  __GLIBC_MINOR__ = %d\n", __GLIBC_MINOR__);
#else
    printf("  未定义 __GLIBC__ → 不是 glibc（可能是 musl / uClibc / bionic）\n");
#endif

#ifdef __GLIBC_PREREQ
    printf("  __GLIBC_PREREQ(2, 34) = %d  (运行期/编译期都可用于条件编译)\n",
           __GLIBC_PREREQ(2, 34) ? 1 : 0);
#else
    printf("  未定义 __GLIBC_PREREQ\n");
#endif

    printf("\n=== ② 运行期问库自己（比宏更可信：宏只反映头文件版本） ===\n");
#ifdef __GLIBC__
    printf("  gnu_get_libc_version()          = %s\n", gnu_get_libc_version());
    printf("  gnu_get_libc_release()          = %s\n", gnu_get_libc_release());
#endif
    char cbuf[64] = {0};
    if (confstr(_CS_GNU_LIBC_VERSION, cbuf, sizeof cbuf) > 0) {
        printf("  confstr(_CS_GNU_LIBC_VERSION)   = %s\n", cbuf);
    } else {
        printf("  confstr(_CS_GNU_LIBC_VERSION)   不可用\n");
    }

    printf("\n=== ③ C 语言标准版本 ===\n");
#ifdef __STDC_VERSION__
    printf("  __STDC_VERSION__ = %ldL  (199901L=C99, 201112L=C11, 201710L=C17)\n",
           (long) __STDC_VERSION__);
#else
    printf("  __STDC_VERSION__ 未定义 → 编译器在 C89/C90 模式\n");
#endif
#ifdef __STDC__
    printf("  __STDC__         = %d\n", __STDC__);
#endif

    printf("\n=== ④ POSIX 规范版本（来自 unistd.h） ===\n");
#ifdef _POSIX_VERSION
    printf("  _POSIX_VERSION   = %ldL  (200809L = POSIX.1-2008)\n", (long) _POSIX_VERSION);
#else
    printf("  _POSIX_VERSION 未定义\n");
#endif

    printf("\n=== ⑤ 编译器身份 ===\n");
#ifdef __GNUC__
    printf("  __GNUC__         = %d  (gcc 主版本)\n", __GNUC__);
    printf("  __GNUC_MINOR__   = %d\n", __GNUC_MINOR__);
#endif
#ifdef __clang__
    printf("  __clang__        = %d.%d\n", __clang_major__, __clang_minor__);
#endif

    printf("\n=== ⑥ 同一个动作在两个实现下的差异（只列判据，不下结论）===\n");
    printf("  getpwnam() 走 NSS      → glibc 有；musl 只有简化实现、不支持 nsswitch\n");
    printf("  dlopen() 语义          → glibc 支持 RTLD_DEEPBIND 等 GNU 扩展；musl 不支持\n");
    printf("  %%m 格式符            → glibc 私有（printf 里输出 strerror(errno)），"
           "其它实现没有\n");
    printf("  __GLIBC__ / gnu_get_libc_version → glibc 独有，跨实现代码里要 #ifdef 包起来\n");
    return 0;
}
```

编译与运行（CE 复核，gcc 13.3.0 / x86-64 / Ubuntu 24.04，`-O0 -Wall -Wextra`，**build code = 0，diagnostics = 0**）：

```text
=== ① 实现身份：这是 glibc 吗？ ===
  __GLIBC__       = 2
  __GLIBC_MINOR__ = 39
  __GLIBC_PREREQ(2, 34) = 1  (运行期/编译期都可用于条件编译)

=== ② 运行期问库自己（比宏更可信：宏只反映头文件版本） ===
  gnu_get_libc_version()          = 2.39
  gnu_get_libc_release()          = stable
  confstr(_CS_GNU_LIBC_VERSION)   = glibc 2.39

=== ③ C 语言标准版本 ===
  __STDC_VERSION__ = 201710L  (199901L=C99, 201112L=C11, 201710L=C17)
  __STDC__         = 1

=== ④ POSIX 规范版本（来自 unistd.h） ===
  _POSIX_VERSION   = 200809L  (200809L = POSIX.1-2008)

=== ⑤ 编译器身份 ===
  __GNUC__         = 13  (gcc 主版本)
  __GNUC_MINOR__   = 3

=== ⑥ 同一个动作在两个实现下的差异（只列判据，不下结论）===
  getpwnam() 走 NSS      → glibc 有；musl 只有简化实现、不支持 nsswitch
  dlopen() 语义          → glibc 支持 RTLD_DEEPBIND 等 GNU 扩展；musl 不支持
  %m 格式符            → glibc 私有（printf 里输出 strerror(errno)），其它实现没有
  __GLIBC__ / gnu_get_libc_version → glibc 独有，跨实现代码里要 #ifdef 包起来
```

### 逐条解读

| 段 | 读数 | 说明 |
|----|------|------|
| ① | `__GLIBC__=2`、`__GLIBC_MINOR__=39` | 这是**头文件**版本，不是运行库版本 |
| ① | `__GLIBC_PREREQ(2,34) = 1` | 编译期条件编译的判据，写法见下 |
| ② | `gnu_get_libc_version() = 2.39` | **运行期**问库自己。宏只反映编译时的头文件，动态链接时真正加载的 `.so` 可能是另一版 |
| ② | `confstr(_CS_GNU_LIBC_VERSION) = "glibc 2.39"` | 同一信息的 POSIX 入口（`<unistd.h>`），不用 `<gnu/libc-version.h>` |
| ③ | `__STDC_VERSION__ = 201710L` | 编译器默认就是 C17（不指定 `-std=` 时的 gcc 13 默认）。`-std=c99` 会把它改成 `199901L`，并带来下一节要讲的连锁反应 |
| ④ | `_POSIX_VERSION = 200809L` | POSIX.1-2008，由 `<unistd.h>` 提供；这是**规范版本**，与 glibc 版本是两件独立的事 |
| ⑤ | `__GNUC__ = 13` | 注意 clang 也会定义 `__GNUC__`，要排除 `__clang__` 才能确认真假（见 [3.6](3.6-portability.md) `c3_11` ① 段） |

### 编译期版本检查的写法

```c
#include <features.h>
#if __GLIBC_PREREQ(2, 17)
    /* glibc >= 2.17：clock_gettime 不再需要 -lrt */
#endif
```

运行期查询：

```bash
ldd --version                 # 或：getconf GNU_LIBC_VERSION
```

## 4. glibc vs musl

| 维度 | glibc | musl |
|------|-------|------|
| 定位 | 功能最全、性能最优 | 极致精简、静态链接友好 |
| 体积 | 大（约 2MB+） | 小（约 500KB） |
| 扩展 | 最多（GNU 扩展、NSS、`%m`） | 严格 POSIX，少扩展 |
| 适用 | 桌面 / 服务器 / 通用 | 嵌入式、容器（Alpine 默认）、静态可移植二进制 |
| 许可 | LGPL | MIT |

嵌入式 / HFT 若要做**静态链接、跨发行版可移植**的单文件二进制，常选 musl；通用场景用 glibc。

**典型可移植性差异是 `strerror_r`**：glibc 有**两套签名**——默认（不定义任何 FTM）给的是 **POSIX 版**（返回 `int`，把描述写进你给的缓冲），只有 `_GNU_SOURCE` 才切到 **GNU 版**（返回 `char *`）；musl 只有 POSIX 版。也就是说，**同一个 glibc 换一个 FTM 就可能换一套 ABI**（完整实测见 [3.6.1](3.6-portability.md) 的五组旗标矩阵：只有 `-D_GNU_SOURCE` 那组走 `string.h:448` 的 GNU 版，其余四组都走 `string.h:428` 的 POSIX 版）。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 手写 `syscall` 指令拿负错误码 | 绕过 glibc 翻译层后返回值是 `-errno`（`-9`/`-38`），须自己判断 `[-4095,-1]`。**注意 `syscall(2)` 这个库函数自己带翻译层**，调它仍拿到 `-1`+`errno`（见 [3.1](3.1-system-calls.md) ④ 段实测） |
| 静态链接可移植二进制 | 用 musl 静态编译，摆脱目标机 glibc 版本依赖（代价是行为差异要重测） |
| 新 syscall 没封装 | 等不及 glibc 时用 `syscall(SYS_xxx, ...)` 直接发 |
| 部署机报 `GLIBC_x.yy not found` | 编译机 glibc 比目标机新 → 在目标同版本环境编译 / 静态链接 / 容器锁定环境 |
| 交叉编译认实现 | 板上是 glibc 还是 musl 决定 NSS、locale、`dlopen` 语义、`malloc` 行为 —— 用本节的 `#ifdef __GLIBC__` 与 `gnu_get_libc_version()` 在启动日志里打一行，排查问题时省很多时间 |

<summary>代码自测（Q&A）</summary>

**Q1：glibc 是「C 标准库」吗？**
A：不完全是。glibc **包含** C 标准库（ISO-C 要求的 `printf`/`malloc` 等），但还**多出** POSIX 系统调用封装（`open`/`read`/`fork`）和大量 Linux/GNU 扩展（`epoll`、GNU 版 `strerror_r`、`%m`）。换 musl 时 C 标准库函数还在，但扩展和部分行为会变。「glibc」是「C 库的一种具体实现」，范围比「C 标准库」大。

**Q2：为什么系统调用失败是「返回 -1 + 设 errno」，而不是直接返回错误码？**
A：这是 glibc 的**错误翻译**约定。内核实际返回 `-errno`（落在 `[-4095,-1]`，见 `include/linux/err.h:17` 的 `MAX_ERRNO=4095`）。glibc 包装检查返回值是否在这个范围：是则 `errno = -返回值` 并返回 `-1`，否则当合法值返回。所以直接发 `syscall` 指令拿到的是 `-2` 而不是 `-1`（[3.1](3.1-system-calls.md) ④ 段实测）。

**Q3：`__GLIBC__` 和 `gnu_get_libc_version()` 有什么区别？该用哪个？**
A：`__GLIBC__`/`__GLIBC_MINOR__` 是**编译期宏**，反映的是**编译时头文件**的版本；`gnu_get_libc_version()` / `confstr(_CS_GNU_LIBC_VERSION)` 是**运行期**查询，反映**实际加载的 `.so`** 版本。静态链接时两者一致；动态链接时可能不一致（编译用新头文件、运行加载老库），所以「部署环境检查」要用运行期那个。

**Q4：`__GLIBC_PREREQ` 是干嘛的？glibc 版本和内核版本是什么关系？**
A：`__GLIBC_PREREQ(major, minor)` 是编译期检查 glibc 版本的宏，用于条件编译（如 `clock_gettime` 在 glibc 2.17 起不用 `-lrt`）。glibc 版本 ≠ 内核版本：glibc 封装系统调用但**滞后**——新内核特性要等 glibc 提供封装才能直接用，否则自己 `syscall()` 绕过；它也不会因为内核升级就变版本。

**Q5：部署机报 `GLIBC_2.38 not found` 是什么原因？怎么解决？**
A：编译机的 glibc 比部署机**新**，二进制链接了对旧 glibc 不存在的符号版本。解决：① 在部署机同版本环境编译；② 静态链接（`-static`，或 musl 静态编译）；③ 用容器锁定编译/运行环境一致；④ 降低用到的 glibc 特性（避免新符号）。核心原则是「**编译环境 glibc ≤ 运行环境 glibc**」。

</details>
