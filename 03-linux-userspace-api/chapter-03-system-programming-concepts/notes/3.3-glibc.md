## 本节讲什么

glibc 是 Linux 上**事实标准的 C 库**——既实现 ISO-C 标准库，又封装 POSIX 系统调用。本节回答三个问题：

1. glibc 到底提供了什么？它和「C 标准库」「POSIX」是什么关系？
2. glibc 封装系统调用时，怎么把内核的「负错误码」翻译成 `errno` + `-1`？
3. glibc 和 musl 有什么区别？`__GLIBC_PREREQ` 是干嘛的？

---

## 1. glibc 的角色：一个库，三种身份

| 身份 | 提供什么 | 例子 |
|------|----------|------|
| **ISO-C 标准库实现** | C 语言标准要求的函数 | `printf`/`malloc`/`strcpy`/`qsort` |
| **POSIX 封装层** | 系统调用的薄外壳 | `open`/`read`/`write`/`fork`/`mmap` |
| **glibc 扩展** | Linux 专属的非标准函数 | `epoll` 系列、`strerror_r` 的 GNU 语义 |

所以「glibc」不是「C 标准库」的同义词——它**包含** C 标准库，还**多出** POSIX 封装和一堆 Linux 扩展。换个 C 库（如 musl），C 标准库函数还在（`printf`/`malloc` 都有），但扩展函数和某些行为细节会变。

## 2. glibc 怎么封装系统调用：`MAX_ERRNO` 错误转换

glibc 的 `open()` 不是把内核返回值原样传回，而是做一次**错误翻译**。关键在内核的错误返回约定：

```c
/* include/linux/err.h:17 —— 内核错误码的取值范围 */
#define MAX_ERRNO	4095
```

完整的往返流程：

```
用户态调 open(path, flags)
      │  glibc 包装：rax=2(syscall号), rdi=path, rsi=flags, rdx=mode
      ▼
syscall 指令陷入内核
      │  内核 sys_open 干活，返回值放进 rax
      ▼
内核返回：成功 → rax = 新 fd（≥0）
          失败 → rax = -errno（如 -2 = -ENOENT，落在 [-4095, -1]）
      ▼
glibc 包装判断：rax 是否在 [-4095, -1]？
      ├─ 是 → errno = -rax（如 2），返回 -1
      └─ 否 → 返回 rax（合法 fd）
```

**这就是「为什么系统调用失败返回 -1，具体原因看 `errno`」的底层机制**——内核返回的是 `-errno`（负错误码），glibc 拆成「返回 -1 + 设 `errno`」两件事。所以直接 `syscall()` 拿到的返回值是**负错误码**（不是 -1），这就是绕过 glibc 时要自己判断的原因。

```c
long ret = syscall(SYS_open, "/nonexistent", O_RDONLY);
/* ret == -2（-ENOENT），而不是 -1！因为跳过了 glibc 的翻译层 */
```

## 3. glibc 版本与特性检查

```bash
ldd --version          # 查看 glibc 版本
getconf GNU_LIBC_VERSION
```

编译时检查 glibc 特性用 `__GLIBC_PREREQ`：

```c
#include <features.h>
#if __GLIBC_PREREQ(2, 17)
    /* glibc >= 2.17：clock_gettime 不再需要 -lrt */
#endif
```

**glibc 版本 ≠ 内核版本**：glibc 封装系统调用，但不是 1:1 映射——一个新内核特性（如 `io_uring`、`close_range`）要等 glibc 出新版本提供对应封装才能直接用；等不及时可以自己 `syscall()` 绕过（见 3.1）。老 glibc 跑在新内核上通常没问题（ABI 向后兼容），但用不到新 syscall 的现成封装。

## 4. glibc vs musl

| 维度 | glibc | musl |
|------|-------|------|
| 定位 | 功能最全、性能最优 | 极致精简、静态链接友好 |
| 体积 | 大（约 2MB+） | 小（约 500KB） |
| 扩展 | 最多（GNU 扩展） | 严格 POSIX，少扩展 |
| 适用 | 桌面/服务器/通用 | 嵌入式、容器（Alpine 默认）、静态可移植二进制 |
| 许可 | LGPL | MIT |

嵌入式/HFT 若要做**静态链接、跨发行版可移植**的单文件二进制，常选 musl；通用场景用 glibc。注意：musl 下 `strerror_r` 是 POSIX 语义（返回 int），glibc 默认是 GNU 语义（返回 char*）——这是两者可移植性差异的典型例子。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 直接 `syscall()` 拿负错误码 | 绕过 glibc 时返回值是 `-errno`，须自己判断 `[-4095,-1]`，不能当 -1 处理 |
| 静态链接可移植二进制 | 用 musl 静态编译，摆脱目标机 glibc 版本依赖 |
| 新 syscall 没封装 | 等不及 glibc 时用 `syscall(SYS_xxx, ...)` 直接发（如早期的 `io_uring`） |
| glibc 版本兼容 | 部署机 glibc 老于编译机会报 `GLIBC_x.yy not found`，需静态链接或用容器锁定版本 |

## 6. 代码示例

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <fcntl.h>
#include <errno.h>

int main(void) {
    /* 正常路径：glibc 的 open() 返回 -1 + 设 errno */
    int fd = open("/nonexistent", O_RDONLY);
    if (fd == -1)
        printf("glibc open(): errno=%d (%s)\n", errno, strerror(errno));

    /* 绕过 glibc：syscall() 返回的是负错误码 */
    long ret = syscall(SYS_open, "/nonexistent", O_RDONLY);
    printf("raw syscall: ret=%ld (就是 -ENOENT)\n", ret);

    /* 手动还原成 errno 语义 */
    if (ret < 0 && ret >= -4095) {
        int e = -(int)ret;
        printf("manual: errno=%d (%s)\n", e, strerror(e));
    }
    return 0;
}
```

运行：`gcc -o g g.c && ./g`。你会看到 glibc 的 `open` 返回 -1 + `errno=2`，而 `syscall(SYS_open, ...)` 直接返回 `-2`——印证了「glibc 做了错误翻译」这一层。

<summary>代码自测（Q&A）</summary>

**Q1：glibc 是「C 标准库」吗？它到底提供了什么？**
A：不完全是。glibc **包含** C 标准库（ISO-C 要求的 `printf`/`malloc` 等），但还**多出** POSIX 系统调用封装（`open`/`read`/`fork`）和大量 Linux/GNU 扩展（`epoll`、GNU 版 `strerror_r`）。换 musl 时 C 标准库函数还在，但扩展和部分行为会变。所以「glibc」是「C 库的一种具体实现」，比「C 标准库」范围大。

**Q2：为什么系统调用失败「返回 -1 + 设 errno」，而不是直接返回错误码？**
A：这是 glibc 的**错误翻译**约定。内核实际返回的是 `-errno`（如 `-2` = `-ENOENT`，落在 `[-4095, -1]`，见 `include/linux/err.h` 的 `MAX_ERRNO=4095`）。glibc 包装检查返回值是否在这个范围：是则设 `errno = -返回值` 并返回 `-1`，否则当作合法值返回。所以直接 `syscall()` 拿到的返回值是**负错误码**（`-2`），不是 `-1`。

**Q3：`__GLIBC_PREREQ` 是干嘛的？glibc 版本和内核版本是什么关系？**
A：`__GLIBC_PREREQ(major, minor)` 是编译期检查 glibc 版本的宏，用于条件编译（如 `clock_gettime` 在 glibc 2.17 起不用 `-lrt`）。glibc 版本 ≠ 内核版本：glibc 封装系统调用但非 1:1——新内核特性（`io_uring`、`close_range`）要等 glibc 提供封装才能直接用，否则自己 `syscall()` 绕过。老 glibc 跑新内核通常兼容（ABI 向后兼容），但用不到新 syscall 的现成封装。

**Q4：glibc 和 musl 有什么区别？什么场景选 musl？**
A：glibc 功能最全、性能最优、扩展最多（LGPL）；musl 极致精简（约 500KB）、严格 POSIX 少扩展、静态链接友好（MIT）。做**静态链接、跨发行版可移植**的单文件二进制（嵌入式、容器如 Alpine）常选 musl；通用场景用 glibc。注意两者 `strerror_r` 语义不同（musl 是 POSIX 返回 int，glibc 默认 GNU 返回 char*），是典型可移植性差异。

**Q5：部署机报 `GLIBC_x.yy not found` 是什么原因？怎么解决？**
A：编译机的 glibc 比部署机**新**，二进制链接了对旧 glibc 不存在的符号版本。解决：① 在部署机同版本环境编译；② 静态链接（`-static`，或用 musl 静态编译）；③ 用容器（Docker）锁定编译/运行环境一致；④ 降低用到的 glibc 特性（避免新符号）。核心是「编译环境 glibc ≤ 运行环境 glibc」。

</details>
