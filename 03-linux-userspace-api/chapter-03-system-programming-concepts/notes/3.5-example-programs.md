## 本节讲什么

系统调用的参数从用户态传到内核态，不是「直接共享内存」那么简单。本节回答三个问题：

1. x86-64 上系统调用的参数怎么传？（寄存器约定）
2. 为什么内核**不能直接解引用**用户态传来的指针？`copy_from_user` 在防什么？
3. 一个用户指针如果传错了，会发生什么（`EFAULT`）？

完整机制在 05 Ch5.4，这里建立「用户态/内核态数据传递要拷贝 + 校验」的核心心智。

---

## 1. 系统调用的参数传递：寄存器约定

系统调用号 + 参数都通过**寄存器**传（不是栈）。x86-64 约定：

| 寄存器 | 内容 |
|--------|------|
| `rax` | 系统调用号（如 `write`=1） |
| `rdi` | 第 1 个参数 |
| `rsi` | 第 2 个参数 |
| `rdx` | 第 3 个参数 |
| `r10` | 第 4 个参数 |
| `r8` | 第 5 个参数 |
| `r9` | 第 6 个参数 |

```c
/* write(fd, buf, count) 的底层：rax=1, rdi=fd, rsi=buf, rdx=count */
long my_write(int fd, const void *buf, size_t count) {
    long ret;
    asm volatile (
        "syscall"
        : "=a"(ret)
        : "a"(1), "D"(fd), "S"(buf), "d"(count)   /* 1=SYS_write */
        : "rcx", "r11", "memory"
    );
    return ret;
}
```

> 注意：系统调用最多 6 个参数（寄存器就这么多）。超过 6 个参数的系统调用很少见，必要时内核会定义结构体指针一次性传入（如 `clone`、`io_uring_setup`）。

系统调用号表（`syscall_64.tbl`）决定了「号码 → 内核函数」的映射：

```
0   read            sys_read
1   write           sys_write
2   open            sys_open
9   mmap            sys_mmap
57  fork            sys_fork
228 clock_gettime   sys_clock_gettime
257 openat          sys_openat
```

## 2. 为什么内核不能直接解引用用户指针

内核拿到用户态传来的指针（如 `write` 的 `buf`），**不能直接 `*buf` 解引用**。因为：

| 风险 | 说明 |
|------|------|
| **指向内核内存** | 恶意程序传一个内核地址，直接解引用 = 内核被读/写攻击 |
| **指向其他进程** | 用户指针可能指向别的进程的地址空间（内核态下无此隔离） |
| **未映射/已换出** | 指针指向的页可能根本不存在，解引用触发内核态缺页异常 → panic |

所以内核必须**先校验范围 + 拷贝**，用 `copy_from_user`/`copy_to_user`：

```c
/* include/linux/uaccess.h —— 用户态↔内核态数据拷贝（内部先 access_ok 校验） */
static __always_inline __must_check unsigned long
__copy_from_user(void *to, const void __user *from, unsigned long n);   /* :93 */
static __always_inline __must_check unsigned long
__copy_to_user(void __user *to, const void *from, unsigned long n);     /* :120 */
```

完整流程：

```
用户态 write(fd, buf, count)
      │  glibc：buf 是用户态指针，塞进 rsi
      ▼
内核 sys_write
      │  拿到 buf（用户态指针），先 access_ok() 校验 buf 指向用户态合法范围
      ▼
copy_from_user(kernel_buf, buf, count)    ← 把数据从用户态拷贝到内核态缓冲区
      │  （若拷贝失败/越界，返回剩余未拷贝字节数，syscall 报 EFAULT）
      ▼
内核用 kernel_buf 干活（写文件/发网络）
```

**为什么必须拷贝**：内核不能信任用户指针，拷贝到内核缓冲区后，数据就在内核自己的内存里了，用户态再怎么改原指针也不影响。这就是「用户态↔内核态边界」的核心安全模型。

## 3. `EFAULT`：用户指针传错的信号

当用户态传了一个非法指针（野指针、未映射地址、指向内核的地址）给系统调用，`copy_from_user`/`access_ok` 校验失败，系统调用返回 -1 + `EFAULT`（=14）。

```c
char *bad = (char *)0x1;            /* 非法地址 */
ssize_t n = write(1, bad, 10);      /* → 返回 -1，errno = EFAULT */
perror("write");                    /* "write: Bad address" */
```

**关键区分**：`EFAULT` 是「你传的指针有问题」（内存 bug），不是「I/O 出错了」。排查时先看是不是野指针/悬空指针/缓冲区越界，别去查磁盘或网络。

## 4. 系统调用的参数类型：标准 typedef

系统调用的参数和返回值大量用**标准 typedef**（而非裸 `int`/`long`），保证跨平台可移植：

| 类型 | 用途 | 例子 |
|------|------|------|
| `size_t` | 无符号长度 | `write` 的 count |
| `ssize_t` | 有符号长度（可返回 -1） | `read`/`write` 返回值 |
| `off_t` | 文件偏移 | `lseek` |
| `pid_t` | 进程 ID | `fork`/`getpid` |
| `uid_t`/`gid_t` | 用户/组 ID | `chown` |

**别写死 `int`/`long` 当 ID/偏移**——`off_t` 在 32 位平台需 `_FILE_OFFSET_BITS=64` 才是 64 位，裸 `long` 会在大文件（>2GB）上溢出。这是可移植编程的基础（见 3.6）。

## 5. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 野指针传内核 | `EFAULT` 说明传了非法地址给 syscall，是内存 bug，先查指针生命周期 |
| 大数据拷贝开销 | `write` 大缓冲时 `copy_from_user` 有拷贝成本，超大块考虑 `mmap` 零拷贝（见 2.8） |
| 6 参数上限 | 系统调用最多 6 个参数，复杂调用用结构体指针（如 `clone`、`io_uring_setup`） |
| 内核态安全 | 内核不信任用户指针，是「用户态崩溃不能拖垮内核」的隔离基石 |

## 6. 代码示例

```c
#include <stdio.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

int main(void) {
    /* 正常：buf 指向合法用户态内存 */
    char buf[] = "hello kernel\n";
    write(STDOUT_FILENO, buf, strlen(buf));

    /* 非法指针：触发 EFAULT */
    char *bad = (char *)0x1;          /* 未映射地址 */
    ssize_t n = write(STDOUT_FILENO, bad, 10);
    if (n == -1)
        printf("write(bad_ptr) → errno=%d (%s)\n", errno, strerror(errno));

    /* 空指针：同样 EFAULT */
    n = write(STDOUT_FILENO, NULL, 10);
    if (n == -1)
        printf("write(NULL)    → errno=%d (%s)\n", errno, strerror(errno));

    return 0;
}
```

运行：`gcc -o p p.c && ./p`。两个非法指针调用都返回 `errno=14`（`EFAULT`）——内核的 `access_ok` 校验拦下了它们，而不是让内核去解引用非法地址。

<details>
<summary>代码自测（Q&A）</summary>

**Q1：x86-64 系统调用的参数怎么传？最多几个参数？**
A：通过**寄存器**传（不是栈）：`rax`=系统调用号，`rdi`/`rsi`/`rdx`/`r10`/`r8`/`r9` = 第 1~6 个参数。所以最多 **6 个参数**。超过 6 个参数的系统调用（如 `clone`、`io_uring_setup`）会改用结构体指针，一次传入所有参数。

**Q2：为什么内核不能直接解引用用户态传来的指针？**
A：三个风险：① 恶意程序传内核地址，直接解引用 = 内核被读/写攻击；② 用户指针可能指向其他进程地址空间（内核态下无此隔离）；③ 指针指向的页可能未映射/已换出，解引用触发内核态缺页异常导致 panic。所以内核必须 `access_ok` 校验 + `copy_from_user` 拷贝到内核缓冲区。

**Q3：`copy_from_user` 和 `copy_to_user` 分别干什么？为什么必须拷贝？**
A：`copy_from_user` 把数据从**用户态拷贝到内核态**（如 `write` 的 buf），`copy_to_user` 反之（如 `read` 把数据拷回用户缓冲）。必须拷贝是因为内核**不信任用户指针**——拷到内核缓冲区后数据就在内核自己的内存里，用户态再改原指针也不影响内核操作，这是「用户态崩溃不能拖垮内核」的隔离基石。

**Q4：`EFAULT` 是什么？它说明什么问题？**
A：`EFAULT`（=14）表示传给内核的指针非法——`access_ok`/`copy_from_user` 校验失败（野指针、未映射地址、指向内核的地址）。它说明是**用户态的内存 bug**（指针生命周期/越界问题），不是 I/O 错误。排查时先查是不是野指针/悬空指针/缓冲区越界，别去查磁盘网络。

**Q5：为什么 `off_t` 不要写死成 `long`？**
A：因为 `off_t` 的宽度依赖平台和编译选项——32 位平台需定义 `_FILE_OFFSET_BITS=64` 才让 `off_t` 是 64 位，否则裸 `long` 在文件 >2GB 时会**溢出**，导致 `lseek` 偏移错误。用标准 typedef（`off_t`/`pid_t`/`ssize_t`）而不是裸 `int`/`long`，是跨平台可移植的基础（见 3.6）。

</details>
