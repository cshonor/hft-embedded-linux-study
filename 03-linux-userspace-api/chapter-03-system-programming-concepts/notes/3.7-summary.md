## 1. 五个核心概念速查

| 概念 | 一句话 | 关键点 | 详细 |
|------|--------|--------|------|
| 系统调用 | 用户态进内核的受控入口 | 编号 + 寄存器 + `syscall` 指令，远贵于普通函数调用 | [3.1](3.1-system-calls.md) |
| 库函数 | glibc 的高层封装 | 纯用户态函数（`strcpy`）不进内核；`fopen` 内部才调 `open` | [3.2](3.2-library-functions.md) |
| glibc | 一个库三种身份 | ISO-C 实现 + POSIX 封装 + Linux 扩展；`MAX_ERRNO` 错误翻译 | [3.3](3.3-glibc.md) |
| 错误处理 | 失败返回 -1 + 设 `errno` | 成功不清零；`EINTR` 要重试；`strerror_r` 线程安全 | [3.4](3.4-error-handling.md) |
| 可移植性 | 功能测试宏 + 标准 typedef | 宏放 `#include` 前；`off_t` 别写死 `long` | [3.6](3.6-portability.md) |

## 2. 系统调用完整往返（本章全景）

```
用户态代码
   │  调 glibc 包装（如 open/read/write/fork）
   ▼
glibc 包装：rax=调用号, rdi/rsi/rdx/r10/r8/r9=参数
   │  功能测试宏决定这个包装函数是否被声明（features.h → __USE_*）
   ▼
syscall 指令陷入内核（用户态 → 内核态）
   │  内核 sys_call_table[号] 分发到 __x64_sys_xxx
   │  copy_from_user 校验并拷贝用户指针（防 EFAULT / 内核被攻击）
   ▼
内核干活，返回值放进 rax：
   成功 → 合法返回值（fd>=0 / 指针 / 字节数）
   失败 → -errno（落在 [-4095, -1]，MAX_ERRNO=4095）
   ▼
回用户态，glibc 包装判断 rax：
   ∈[-4095,-1] → errno = -rax，返回 -1   （错误翻译）
   否则        → 返回 rax（合法值）
   ▼
用户代码：先看返回值，失败才读 errno（成功不清零！）
```

## 3. 代码示例：系统调用到底贵多少

原书这个程序（`progconc/syscall_speed.c`，**无 Listing 编号**）用 `getppid()` 与 `syscall(SYS_getppid)` 各跑 N 次比较耗时。本 demo 在原书基础上加了两条对照——普通函数调用（零点）与纯用户态库函数——把「贵在哪」分离出来。

源码：[../code/c3_12_syscall_speed.c](../code/c3_12_syscall_speed.c)

```c
/* TLPI 第 03 章 §3.7（成本全景）—— 系统调用到底贵多少：复刻原书 progconc/syscall_speed.c
 *
 * 本 demo 给 §3.7 小结做量化收束：把「系统调用 / glibc 包装 / 普通函数 / 纯用户态库函数」
 * 四种调用的单次耗时并排量出来，说明「贵的是跨特权级，不是库函数」。
 *
 * 原书这个程序（无 Listing 编号，属「supplementary file」）的做法：
 *   用 getppid() 与 syscall(SYS_getppid) 各跑 N 次，比较耗时，证明
 *   「glibc 包装 + 真正陷入内核」比普通函数调用贵一到两个数量级。
 *
 * 本 demo 在原书基础上加了两条对照：
 *   ③ 普通函数调用（同一进程内，无特权级切换）—— 作为「零点」
 *   ④ 纯用户态库函数调用（strlen 这种也被编译成函数调用）—— 验证「库函数也是零成本」
 *
 * 计时用 CLOCK_MONOTONIC：它只受 NTP 频率微调（adjtime）影响，不会被墙上时钟回拨搞乱。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_12 c3_12_syscall_speed.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

#define ITERS 2000000L

static volatile long sink;    /* 防止优化把整个循环删掉 */

static long nop_call(long x)  /* 普通函数调用：不陷入内核 */
{
    return x + 1;
}

static double now_sec(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double) ts.tv_sec + (double) ts.tv_nsec / 1e9;
}

static void bench(const char *tag, long (*fn)(long), long arg)
{
    double t0 = now_sec();
    long acc = 0;
    for (long i = 0; i < ITERS; i++) {
        acc += fn(arg);
    }
    double dt = now_sec() - t0;
    sink = acc;
    printf("  %-30s %7.1f ms  →  %6.1f ns/次\n", tag, dt * 1e3, dt / (double) ITERS * 1e9);
}

/* ---- 四种被测目标，签名统一成 long(long) 便于复用同一个 bench() ---- */

static long f_nop(long x)                 /* ③ 普通函数调用 */
{
    return nop_call(x);
}

static long f_userlib(long x)             /* ④ 纯用户态库函数（无内联，-O0 下是真调用） */
{
    char buf[16];
    snprintf(buf, sizeof buf, "%ld", x & 1);
    return buf[0];
}

static long f_glibc_wrapper(long x)       /* ① glibc 包装的 getppid() */
{
    (void) x;
    return (long) getppid();
}

static long f_syscall2(long x)            /* ② syscall(2) 通用入口 */
{
    (void) x;
    return (long) syscall(SYS_getppid);
}

int main(void)
{
    setvbuf(stdout, NULL, _IONBF, 0);

    printf("=== 系统调用开销实测（%ld 次，CE 容器 / gcc 13.3 / x86-64）===\n", ITERS);
    printf("  %-30s %7s     %8s\n", "被测对象", "总耗时", "单次");

    bench("① glibc 包装 getppid()", f_glibc_wrapper, 1);
    bench("② syscall(SYS_getppid)", f_syscall2, 1);
    bench("③ 普通函数调用 nop_call()", f_nop, 1);
    bench("④ 纯用户态库函数 snprintf()", f_userlib, 1);

    printf("\n=== 怎么读这张表 ===\n");
    printf("  · ①和②都在「真正陷入内核」那一档；两者的差距 = syscall(2) 自己套的那层壳\n");
    printf("    （存参、查表、把 -errno 翻成 -1+errno），不涉及特权级切换\n");
    printf("  · ③是零点：同一特权级内的 call/ret\n");
    printf("  · ④说明「库函数」本身不贵，贵的是**跨特权级**；atoi/strlen/snprintf 都是用户态\n");
    printf("  · 单次纳秒数是**这台机器**的绝对值，不能当你的机器/你的板的数值；\n");
    printf("    可迁移的结论只有**比值**：系统调用约比普通调用贵一到两个数量级\n");

    printf("\n=== 对 HFT / 嵌入式的直接推论 ===\n");
    printf("  1. 热路径别逐字节 read/write：一次批量调用替代 N 次小调用\n");
    printf("  2. 能用 vDSO 的调用（clock_gettime/gettimeofday/time/getcpu）不陷入内核\n");
    printf("  3. 同机通信优先 AF_UNIX/共享内存，省掉整个网络栈的系统调用序列\n");
    printf("  4. 别用 gettimeofday 之外的「看起来免费」的库函数做高频日志：printf 的代价在\n");
    printf("     格式化（用户态）而不是 write，但它会写很多字节 → 仍要批量化\n");
    return 0;
}
```

编译与运行（CE 复核，gcc 13.3.0 / x86-64 / Ubuntu 24.04，`-O0 -Wall -Wextra`，**build code = 0，diagnostics = 0**）：

```text
=== 系统调用开销实测（2000000 次，CE 容器 / gcc 13.3 / x86-64）===
  被测对象                   总耗时       单次
  ① glibc 包装 getppid()      1625.9 ms  →   812.9 ns/次
  ② syscall(SYS_getppid)        2550.6 ms  →  1275.3 ns/次
  ③ 普通函数调用 nop_call()    14.0 ms  →     7.0 ns/次
  ④ 纯用户态库函数 snprintf()   150.4 ms  →    75.2 ns/次

=== 怎么读这张表 ===
  · ①和②都在「真正陷入内核」那一档；两者的差距 = syscall(2) 自己套的那层壳
    （存参、查表、把 -errno 翻成 -1+errno），不涉及特权级切换
  · ③是零点：同一特权级内的 call/ret
  · ④说明「库函数」本身不贵，贵的是**跨特权级**；atoi/strlen/snprintf 都是用户态
  · 单次纳秒数是**这台机器**的绝对值，不能当你的机器/你的板的数值；
    可迁移的结论只有**比值**：系统调用约比普通调用贵一到两个数量级

=== 对 HFT / 嵌入式的直接推论 ===
  1. 热路径别逐字节 read/write：一次批量调用替代 N 次小调用
  2. 能用 vDSO 的调用（clock_gettime/gettimeofday/time/getcpu）不陷入内核
  3. 同机通信优先 AF_UNIX/共享内存，省掉整个网络栈的系统调用序列
  4. 别用 gettimeofday 之外的「看起来免费」的库函数做高频日志：printf 的代价在
     格式化（用户态）而不是 write，但它会写很多字节 → 仍要批量化
```

### 逐条解读

| 被测对象 | 单次耗时 | 相对于零点(③) | 说明 |
|----------|----------|---------------|------|
| ① glibc 包装 `getppid()` | 812.9 ns | **≈ 116×** | 跨特权级：真正陷入内核 |
| ② `syscall(SYS_getppid)` | 1275.3 ns | **≈ 182×** | ①的 1.57 倍——差值就是 `syscall(2)` 自己那层壳（存参、查表、把 `-errno` 翻成 `-1+errno`），**不涉及特权级切换** |
| ③ 普通函数调用 `nop_call()` | 7.0 ns | 1×（零点） | 同一特权级内的 `call`/`ret` |
| ④ 纯用户态库函数 `snprintf()` | 75.2 ns | ≈ 11× | 比 `nop_call` 贵一个数量级，但**仍然没有一次系统调用**——「库函数贵」是格式化本身的开销，不是特权级切换 |

**三个可迁移的结论**（绝对值不可迁移，比值可以）：

1. **系统调用比普通函数调用贵**一到两个数量级。①/③ ≈ 116 倍。
2. **`syscall(2)` 比 glibc 包装还慢**——它是「通用入口」，要遍历参数、查表、做错误翻译。所以「用 `syscall()` 绕开 glibc 更快」是错的直觉；它只在你需要 glibc 没包装的调用时才有价值（见 [3.1](3.1-system-calls.md) ⑥ 段）。
3. **库函数本身不贵**。贵的是**跨特权级**。④ 组用 `snprintf` 证明了这一点：同样是「格式化」，`fprintf` 到文件才会触发 `write`（见 [3.2](3.2-library-functions.md) 实测第 5 段）。

> ⚠️ **这张表的数字不能当基准用**：单次纳秒数是 **CE 容器**上的绝对值，换机器、换编译器优化级别（本 demo 是 `-O0`）、换负载都会变。能带走的是**比值**和**机制**。要测你自己的机器/板子，得在目标环境重跑。

## 4. 五个必须记住的坑

| # | 坑 | 正确认知 |
|---|----|----------|
| 1 | **成功不清 `errno`** | 判成败只能看返回值，不能 `if (errno)` |
| 2 | **`EINTR` 不是错误** | 被信号打断，`while (n == -1 && errno == EINTR)` 重试 |
| 3 | **`EFAULT` 是内存 bug** | 传了非法指针给内核，查野指针/越界，别查 I/O |
| 4 | **`EAGAIN` 是暂时状态** | 非阻塞「暂无数据」，重试或进 epoll，别当失败 |
| 5 | **直接 `syscall()` 拿负错误码** | 绕过 glibc 时返回值是 `-2`（`-ENOENT`）而不是 `-1` + `errno` |

## 5. HFT / 嵌入式收束

| 路线 | 本章的落地 |
|------|------------|
| **HFT 低延迟** | 少 syscall（逐字节 `read` = N 次陷入，① 的 812.9 ns 就是单价）；区分 glibc 包装成本 vs 真陷入（② − ① ≈ 462 ns）；能用 vDSO 的调用（`clock_gettime`）根本不陷入内核；错误处理用 `strerror_r`（线程安全）+ 完整上下文 |
| **嵌入式** | 严格返回值 + `errno` 检查；musl 静态编译摆脱 glibc 依赖；`_FILE_OFFSET_BITS=64` 处理大日志；交叉编译前先确认 `__aarch64__` 分支与 `char` 符号性 |
| **共同** | 功能测试宏决定「哪些 API 可见」——`-std=c99` 会**减少**可见声明，不是增加 |

<summary>代码自测（Q&A）</summary>

**Q1：用一句话串起本章五个概念。**
A：系统调用是「用户态进内核的受控入口」（编号 + 寄存器 + 陷阱指令，比普通函数调用贵一到两个数量级），库函数是 glibc 在其上的高层封装（纯用户态函数不进内核）；系统调用失败返回 -1 并设 `errno`（成功不清零、`EINTR` 重试）；参数通过寄存器传递且内核必须 `copy_from_user` 拷贝校验；跨平台靠功能测试宏 + 标准 typedef 保证 API 可见性与类型宽度一致。

**Q2：为什么「判断成功失败要看返回值，不能看 errno」？**
A：因为成功时内核/glibc **不会清零** `errno`，它保留的是上一次失败留下的旧值。用 `if (errno != 0)` 判断成败会误判。正确姿势：`fd = open(...); if (fd == -1) { /* 这时才读 errno */ }`。

**Q3：系统调用失败，用户看到「-1 + errno」，内核实际返回了什么？**
A：内核实际返回 `-errno`（负错误码，如 `-ENOENT` = `-2`，落在 `[-4095,-1]`，`MAX_ERRNO=4095`）。glibc 包装检测返回值是否在此范围，是则 `errno = -返回值` 并返回 `-1`。所以「-1 + errno」是 glibc 翻译的结果——直接 `syscall()` 拿到的是 `-2` 而不是 `-1`。

**Q4：`EINTR`、`EAGAIN`、`EFAULT` 三个错误码怎么区分处理？**
A：`EINTR`(=4) 被信号打断 → **重试**（`while (n == -1 && errno == EINTR)`）；`EAGAIN`(=11) 非阻塞暂时无数据 → **稍后重试或进 epoll**；`EFAULT`(=14) 传给内核的指针非法 → **查内存 bug**（野指针/越界），不是 I/O 错误。前两个是「可恢复的暂时状态」，最后一个是「程序 bug」。

**Q5：`fopen` 和 `open` 的本质区别是什么？**
A：`fopen` 是 ISO-C 标准库函数，返回带用户态缓冲的 `FILE*`，跨平台（Windows 用 msvcrt 实现）；`open` 是 POSIX 系统调用包装，返回内核整数 `fd`，无用户态缓冲，Unix/Linux 限定。`fopen` 内部最终会调用 `open`（Linux 上），但多了一层用户态缓冲管理。注意**两者不是一一对应**：本仓库 [3.2](3.2-library-functions.md) 的 0b 段实测了同一个 `/dev/null` 上 `open(O_WRONLY)` 成功而 `fopen("w")` 失败（`fopen` 隐含 `O_CREAT`）。

**Q6：本节的实测说「系统调用贵 116 倍」，这个数字能直接拿去用吗？**
A：**不能**。它是 CE 容器上 `-O0` 编译的绝对值（① `getppid()` 812.9 ns / ③ `nop_call()` 7.0 ns）。换机器、换优化级别（`-O2` 下 `nop_call` 可能被内联成 0 成本）、换负载都会变。可迁移的只有**比值与机制**：系统调用比普通函数调用贵一到两个数量级；`syscall(2)` 比 glibc 包装还慢（多一层壳，约 1.57 倍）；库函数本身不贵，贵的是跨特权级。要测自己的板子就在目标环境重跑。

**Q7：为什么「用 `syscall()` 绕开 glibc 更快」是错的直觉？**
A：因为 `syscall(2)` 是一个**通用入口**：它要存参、查表、把内核返回的 `-errno` 翻成 `-1`+`errno`，这一层壳本身有成本。 本节实测 ② 比 ① 慢约 462 ns/次（1275.3 vs 812.9）。它的真正价值是「glibc 没给你包装的调用也能发」（如 `SYS_gettid`），不是性能。

</details>
