## 本节讲什么

**系统调用 = 用户进程请求内核做受保护操作的唯一受控入口。**

一次 `write(1, "x", 1)` 表面上是调了个函数，实际上要走完「用户态寄存器准备 → 特权级切换 → 内核查表 → 服务例程 → 返回」这条路。本节把这条路拆成能实测的四件事：

1. 同一次写操作的**三条路径**（glibc 包装 / `syscall(2)` / 手写 `syscall` 指令）——它们的差别不是「快慢」，而是**谁替你翻译错误码**。
2. 失败时到底谁在说话：内核用 **`[-4095, -1]` 表示错误**，glibc 把它翻成 `-1 + errno`，手写指令拿到的是裸的 `-errno`。
3. 系统调用号从哪来（`syscall_64.tbl` → `sys_call_table[]`）。
4. 一种「不是错误码的失败」：**SIGPIPE**——写一个读端已关闭的管道，默认不是给你 `EPIPE`，而是把整个进程杀掉。

> 本节只讲「怎么进去、怎么出来、参数怎么过界」。内核入口的汇编细节见 [05/Ch5 系统调用](../../../05-linux-kernel/chapter-05-system-calls/README.md)。

## 1. 三条调用路径

| 路径 | 写法 | 谁翻译错误码 | 什么时候用 |
|------|------|--------------|------------|
| **glibc 包装** | `write(1, buf, n)` | glibc：`-1` + 设 `errno` | **99% 的场合**，唯一推荐 |
| **`syscall(2)`** | `syscall(SYS_write, 1, buf, n)` | `syscall(2)` 自己也翻译：`-1` + 设 `errno` | glibc 没提供包装的调用（如 `SYS_gettid`、早期的 `io_uring`） |
| **手写指令** | 内联汇编 `syscall` | **没人翻译**：拿到裸的 `-errno` | freestanding（裸机 / 固件 / 内核模块）、没有 libc 的场合 |

第一条最反直觉的是：**`syscall(2)` 并不是「裸接口」**。它自己就套了一层壳（存参、查表、把 `-errno` 翻成 `-1` + `errno`）。真正裸的是第三条。

## 2. 错误返回约定：为什么是 `[-4095, -1]`

内核不能「返回 -1 同时设一个全局变量」——内核态没有 `errno` 这个概念。它的约定是：**返回值直接就是 `-errno`**，并且用 `MAX_ERRNO` 保证这个区间永远不和合法返回值冲突。

| 层 | 成功 | 失败 |
|----|------|------|
| 内核（裸 `syscall` 指令） | `rax` = 结果（fd / 字节数 / 指针，≥ 0） | `rax` = `-errno`，落在 `[-4095, -1]` |
| glibc 包装 | 原样返回 | `errno = -rax`，返回 `-1` |

```c
/* include/linux/err.h:17 */
#define MAX_ERRNO	4095
```

**为什么是 4095**：这个上界要同时满足两件事——① 比任何平台的 `errno` 最大值都大；② 小到让「合法返回值」永远不会落进来。内核里所有合法指针都在内核地址空间的低半区之上，`0` 以上、`-4095` 以下的整数不受影响，所以 `[-4095,-1]` 可以安全地当错误码专用区间。这也是为什么内核里到处能看到 `if (IS_ERR(ptr))` 这种写法（`IS_ERR` 就是在判这个区间）。

## 3. 代码示例：三条路径 + 失败分支 + SIGPIPE

源码：[../code/c3_1_syscall_path.c](../code/c3_1_syscall_path.c)

```c
/* TLPI 第 03 章 §3.1 —— 同一次写操作的「三条路径」+ 失败分支 + SIGPIPE
 *
 *   ① glibc 包装函数      write(1, ...)            唯一推荐用法
 *   ② syscall(2) 通用入口  syscall(SYS_write, ...)  给「glibc 没给包装」的调用兜底
 *   ③ 手写 syscall 指令    寄存器约定：rax=调用号，rdi/rsi/rdx/r10/r8/r9=参数，
 *                          返回值也在 rax；内核的失败约定是 rax 落在 [-4095, -1]
 *
 * 本节最反直觉的两条：
 *   1. syscall(2) 这个「通用入口」本身就做了一层翻译 —— 它把内核的 -errno 变成
 *      -1 并把 errno 设上；手写指令拿到的是裸返回码 -9，errno 根本没人碰。
 *   2. 往「没有读端的管道」里写，默认不是收到一个错误码，而是**整个进程被
 *      SIGPIPE(13) 杀掉**。这是网络服务必须第一行就忽略它的原因。
 *
 * 编译：gcc -O0 -Wall -Wextra -o c3_1 c3_1_syscall_path.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>

/* 内核把 [-4095, -1] 这一段保留给错误码。范围上界来自
 * include/linux/err.h 的 MAX_ERRNO = 4095 —— 拿到裸返回码时，
 * 落在这个区间里就意味着失败，-ret 就是 errno 的值。 */
#define KERNEL_ERR_MAX (-4095)

/* 把三种调用方式的返回值放在一起读：同一个错误，三种「报法」 */
static void report(const char *tag, long ret, int err)
{
    if (ret >= 0) {
        printf("  %-34s ret=%-6ld (成功)\n", tag, ret);
    } else if (ret == -1) {
        printf("  %-34s ret=-1      errno=%d (%s)   ← glibc 约定：-1 + errno\n",
               tag, err, strerror(err));
    } else if (ret >= KERNEL_ERR_MAX) {
        printf("  %-34s ret=%-6ld  ← 裸返回码：-ret = %d 才是 errno 该有的值，而 errno 仍是 %d\n",
               tag, ret, (int) -ret, err);
    } else {
        printf("  %-34s ret=%-6ld  ← 超出内核错误码区间 [-4095,-1]\n", tag, ret);
    }
}

/* ③ 手写 syscall 指令：只传 3 个参数，足够覆盖 write 这组实验。
 *    clobber 里必须写 rcx / r11 —— syscall 指令会把返回地址放 rcx、
 *    把 rflags 放 r11，编译器不知道，所以要显式告诉它。 */
static long raw_syscall3(long nr, long a1, long a2, long a3)
{
    long ret;
    __asm__ volatile ("syscall"
                      : "=a"(ret)
                      : "a"(nr), "D"(a1), "S"(a2), "d"(a3)
                      : "rcx", "r11", "memory");
    return ret;
}

/* ⑧ 往「读端已关闭的管道」写一次，看 SIGPIPE 的两种处置 */
static void sigpipe_child(sighandler_t how, const char *label)
{
    int p[2];
    if (pipe(p) != 0) {
        printf("  %-16s → pipe 创建失败\n", label);
        return;
    }
    fflush(NULL);
    pid_t pid = fork();
    if (pid == 0) {                       /* ---- 子进程 ---- */
        signal(SIGPIPE, how);
        close(p[0]);                      /* 本进程里把读端关掉 → 管道再无读者 */
        errno = 0;
        ssize_t w = write(p[1], "x", 1);
        printf("  %-16s → 子进程没被杀死：write 返回 %zd，errno=%d (%s)  EPIPE=%d\n",
               label, w, errno, strerror(errno), EPIPE);
        _exit(0);
    }
    close(p[0]);
    close(p[1]);
    int status = 0;
    waitpid(pid, &status, 0);
    if (WIFSIGNALED(status)) {
        printf("  %-16s → 子进程被信号 %d 终止   （shell 里 $? = 128+%d = %d）\n",
               label, WTERMSIG(status), WTERMSIG(status), 128 + WTERMSIG(status));
    } else if (WIFEXITED(status)) {
        printf("  %-16s → 子进程 exit(%d)\n", label, WEXITSTATUS(status));
    }
}

int main(void)
{
    /* 容器里 stdout 是 socket → 默认全缓冲。混用 printf 与直接 write(1,...) 会乱序，
     * 这里显式关掉缓冲，让每一行的先后顺序真实可读。 */
    setvbuf(stdout, NULL, _IONBF, 0);

    const char *msg = "[3.1] hello from three paths\n";
    const long n = (long) strlen(msg);
    long ret;
    int err;

    printf("=== ① glibc 包装函数 write(2) ===\n");
    errno = 0;
    ret = (long) write(STDOUT_FILENO, msg, (size_t) n);
    err = errno;
    report("write(1, msg, n)", ret, err);

    printf("=== ② syscall(2) 通用入口 ===\n");
    errno = 0;
    ret = syscall(SYS_write, STDOUT_FILENO, msg, (size_t) n);
    err = errno;
    report("syscall(SYS_write, ...)", ret, err);

    printf("=== ③ 手写 syscall 指令 ===\n");
    errno = 0;
    ret = raw_syscall3(SYS_write, STDOUT_FILENO, (long) (uintptr_t) msg, n);
    err = errno;
    report("raw syscall 指令", ret, err);
    printf("\n");

    printf("=== ④ 失败分支 A：写一个「只读方式打开的 fd」===\n");
    /* pipe(2) 返回的 p[0] 只能读、p[1] 只能写。往 p[0] 里写，必然 EBADF(9)。
     * 这个靶子不需要文件系统配合，任何 UN*X 上都成立。 */
    int p[2];
    if (pipe(p) != 0) {
        printf("  pipe 创建失败\n");
        return 1;
    }
    errno = 0;
    ret = (long) write(p[0], msg, (size_t) n);
    err = errno;
    report("write(读端) [glibc]", ret, err);

    errno = 0;
    ret = syscall(SYS_write, p[0], msg, (size_t) n);
    err = errno;
    report("syscall(SYS_write, 读端)", ret, err);

    errno = 0;
    ret = raw_syscall3(SYS_write, p[0], (long) (uintptr_t) msg, n);
    err = errno;
    report("raw syscall 写读端", ret, err);

    /* 换一个「只读打开的普通文件」当靶子，证明不是 pipe 特有 */
    int rfd = open("/proc/self/status", O_RDONLY);
    if (rfd >= 0) {
        errno = 0;
        ret = syscall(SYS_write, rfd, msg, (size_t) n);
        err = errno;
        report("syscall 写只读普通文件", ret, err);
        close(rfd);
    } else {
        printf("  %-34s (跳过：/proc/self/status 打不开)\n", "只读普通文件靶子");
    }
    printf("    ↑ glibc 与 syscall(2) 都返回 -1 并把 errno 设成 9；\n"
           "      手写指令拿到的是 -9 —— 这就是「薄封装」与「裸接口」的分界\n\n");

    printf("=== ⑤ 失败分支 B：无效系统调用号 9999 ===\n");
    errno = 0;
    ret = syscall(9999);
    err = errno;
    report("syscall(9999)", ret, err);
    errno = 0;
    ret = raw_syscall3(9999, 0, 0, 0);
    err = errno;
    report("raw 9999", ret, err);
    printf("    ↑ 号超出 NR_syscalls，内核查表落到 __x64_sys_ni_syscall()，统一回 ENOSYS(38)\n\n");

    printf("=== ⑥ syscall(2) 真正的用武之地：glibc 没给包装的调用 ===\n");
    /* SYS_gettid 在 glibc 里没有等价函数（pthread_self 返回的是 pthread_t，
     * 不是内核 tid），只能靠 syscall(2)。 */
    errno = 0;
    ret = syscall(SYS_gettid);
    err = errno;
    printf("  %-34s ret=%-6ld (系统调用号 %d，无 glibc 包装)\n",
           "syscall(SYS_gettid)", ret, (int) SYS_gettid);
    printf("    ↑ 和上面 ④⑤ 的失败分支对照读：同一个 syscall(2) 入口，成功走 ret，失败走 errno\n\n");

    printf("=== ⑦ 号是怎么来的：arch/x86/entry/syscalls/syscall_64.tbl ===\n");
    printf("  SYS_read          = %d\n", (int) SYS_read);
    printf("  SYS_write         = %d\n", (int) SYS_write);
    printf("  SYS_openat        = %d\n", (int) SYS_openat);
    printf("  SYS_clock_gettime = %d\n", (int) SYS_clock_gettime);
    printf("  可见号的最大值 + 1 ≈ NR_syscalls 的量级 = %d（表里有大量空洞/已废弃号）\n\n",
           (int) SYS_clock_gettime + 1);

    printf("=== ⑧ 往「读端已关闭的管道」里写：默认不是错误码，是死刑 ===\n");
    sigpipe_child(SIG_DFL, "SIG_DFL（默认）");
    sigpipe_child(SIG_IGN, "SIG_IGN（忽略）");
    printf("    ↑ 网络服务为什么启动时就 signal(SIGPIPE, SIG_IGN)：\n"
           "      对端断开后自己再 write，默认行为是**整个进程被信号杀掉**，\n"
           "      而不是拿到一个能处理的错误码。本 demo 第一版就是直接在主进程里\n"
           "      写了一个只读 fd，结果进程被 13 号信号带走、exit code = 141，\n"
           "      后面 ⑤⑥⑦ 三段一行都没跑到 —— 现在把这段关进子进程才看得全。\n"
           "    注：SIG_IGN 会被 fork 继承，所以上面第一个子进程必须显式\n"
           "        signal(SIGPIPE, SIG_DFL) 才能还原「默认处置」。\n");
    return 0;
}
```

### 逐条解读

| 段 | 现象 | 说明 |
|----|------|------|
| ① ② ③ | 三条都 `ret=29` | 三条路径**干的是同一件事**；`29` = 消息长度 |
| ④ | glibc / `syscall(2)` → `-1` + `errno=9`；手写 → `-9`，**`errno` 仍是 0** | 最关键的一行：`errno` 是被 glibc 那一层设的，绕过它就没有 `errno` 可用 |
| ④ 靶子 | `pipe()` 的读端 `p[0]` | 选它是因为**不需要文件系统配合**：`p[0]` 只能读，往里写必然 `EBADF`。另拿只读打开的普通文件验证同一结论 |
| ⑤ | 号 9999 → `ENOSYS(38)` | 号超出 `NR_syscalls`，内核查表的默认项是 `__x64_sys_ni_syscall`，统一回 `ENOSYS` |
| ⑦ | `SYS_read=0`、`SYS_write=1` | 号是**表里的行号**，不是「按字母排」也不是「按功能分段」 |
| ⑧ | `SIG_DFL` → 被信号 13 终止 | `$? = 141 = 128 + 13`，这是 shell 对「被信号 N 杀掉」的编码 |

**⑦ 号表的坑**：`SYS_clock_gettime + 1 = 229` **不是** `NR_syscalls`，只是「当前能看到的最大号 + 1」。表里大量号是空洞（已废弃或被移除），真实 `NR_syscalls` 由内核构建时按表长度生成，比这个数大。写代码时永远不要用「最大号」推算表长度。

**⑧ 为什么这条必须单独记**：写系统调用失败有两种形态——**返回错误码**（可处理）和**被信号杀掉**（不可处理）。`SIGPIPE` 是后者。第一次跑本 demo 时没有隔离这段，结果进程被 13 号信号带走、`exit code = 141`，`⑤⑥⑦` 三段一行都没打印出来。同时这也暴露了一个真实的工程问题：**SIG_IGN 会被 `fork` 继承**，所以想演示「默认处置」必须在子进程里显式 `signal(SIGPIPE, SIG_DFL)`。

## 4. 参数怎么进内核：寄存器约定

系统调用的号与参数走**寄存器**，不走栈。x86-64 的约定：

| 寄存器 | 内容 |
|--------|------|
| `rax` | 系统调用号（如 `write`=1） |
| `rdi` `rsi` `rdx` `r10` `r8` `r9` | 第 1 ~ 6 个参数 |
| `rcx` `r11` | **被 `syscall` 指令破坏**（分别存返回地址与 `rflags`），所以内联汇编里必须写进 clobber 列表 |

两个容易踩的点：

- **最多 6 个参数**。参数更多的调用（`clone`、`io_uring_setup`）改为「结构体指针 + 一次传进去」，本质还是 6 个以内的寄存器。
- **`r10` 而不是 `rcx` 当第 4 个参数**。见下：`syscall` 指令会把 `rcx` 拿去存返回地址，「第 4 个参数用 `rcx`」是 `int 0x80` 时代的老约定。

### 内核入口的坐标（v6.6）

| 位置 | 作用 |
|------|------|
| `arch/x86/entry/entry_64.S:87` `SYM_CODE_START(entry_SYSCALL_64)` | 内核侧入口：换栈（`:97`）、建立 `pt_regs`（`:106`）、`sysretq` 回程（`:198`） |
| `arch/x86/entry/common.c:40` `do_syscall_x64()` | `:48` 判 `unr < NR_syscalls`；`:50` `regs->ax = sys_call_table[unr](regs);` —— **就是这一步执行了服务例程** |
| `arch/x86/entry/common.c:73` `do_syscall_64()` | `:76` 从用户态进入（`syscall_enter_from_user_mode`）；`:82` 无效号回 `__x64_sys_ni_syscall` → `ENOSYS` |
| `arch/x86/entry/syscall_64.c:16` `const sys_call_ptr_t sys_call_table[]` | 号 → 内核函数的函数指针数组 |

所以「系统调用号」的本质就是**这张表的数组下标**。`syscall_64.tbl` 只是生成这张表的输入文件。

## 5. 数据怎么过边界：`access_ok` + `copy_from_user`

内核拿到用户态传来的指针（如 `write` 的 `buf`），**不能直接解引用**：

| 风险 | 后果 |
|------|------|
| 指向内核地址 | 恶意程序借内核之手读/写内核内存 |
| 指向别的进程 | 内核态没有「当前进程的地址空间」之外的隔离幻想 |
| 指向未映射页 | 内核态缺页 → 直接 panic，而不是给个错误码 |

所以每个带指针参数的系统调用都要：`access_ok()` 校验范围 → `copy_from_user()` 把数据拷进内核缓冲。**校验失败就是 `EFAULT(14)`**（不是 `SIGSEGV`）。这一段的完整实测见 [3.4 错误处理](3.4-error-handling.md) 的 `c3_13_efault.c`；内核侧细节见 [05/Ch5.4 实现与参数验证](../../../05-linux-kernel/chapter-05-system-calls/notes/section-5.4-实现与参数验证.md)。

## 6. HFT / 嵌入式关联

| 现象 | 本节机制的兑现 |
|------|----------------|
| 热路径少 syscall | 每次调用都要跨特权级；`c3_12_syscall_speed.c` 实测「陷入内核」比同特权级的 `call` 贵一到两个数量级 |
| 绕过 glibc 拿裸返回码 | `syscall(2)` 仍是翻译过的；只有手写指令才是裸的 —— 无 libc 环境判断错误必须自己看 `[-4095,-1]` |
| 网络服务必须先忽略 SIGPIPE | 对端断开后自己再 `write`，默认行为是**进程被 13 号信号杀掉**，而不是拿到一个错误码 |
| 新增 syscall 用不上包装 | 新内核特性（`io_uring`、`close_range`）在 glibc 提供包装前，只能自己 `syscall(SYS_xxx, ...)` |
| 参数上限 6 个 | 自己设计 syscall 或写 ioctl 时，参数超 6 个就要改成结构体指针 |

## 常见陷阱

1. **不检查返回值就往下用**

```c
int fd = open(path, O_RDONLY);
read(fd, buf, n);          /* ❌ fd == -1 时这里只会拿到 EBADF，真实原因已丢 */
```

正确写法：`if ((fd = open(...)) == -1) { perror("open"); exit(1); }`。失败原因只在 `errno` 里，而 `errno` 会被下一次调用覆盖（见 [3.4](3.4-error-handling.md)）。

2. **把 `syscall()` 当裸接口，以为它也返回负错误码**

`syscall(2)` 是 glibc 提供的**包装器的包装器**。想拿裸返回码只能手写 `syscall` 指令——但那样也就没有 `errno` 了。

3. **混淆系统调用与库函数**

`man 2` 查到的是系统调用，`man 3` 查到的是库函数。`strcpy`/`atoi`/`strlen` 是纯用户态库函数，一次内核都不进（[3.2](3.2-library-functions.md) 有实测）。

4. **忘了处理「被信号打断」**

`EINTR`（=4）是**正常情况不是错误**：`read`/`epoll_wait` 被信号打断就返回它，应该重试。

5. **把 SIGPIPE 当普通错误码**

它不是一个返回值，是一个信号。不忽略就默认杀进程——这正是本 demo 第一版挂掉的原因。

<summary>代码自测（Q&A）</summary>

**Q1：glibc 的 `write()`、`syscall(SYS_write, ...)`、手写 `syscall` 指令，三者的本质区别是什么？**
A：前两者都是**包装**：都会把内核的 `-errno` 翻译成「返回 -1 + 设 `errno`」。`syscall(2)` 不是裸接口，它自己就套了一层。只有手写 `syscall` 指令拿到的是裸返回码 `-9`，此时 `errno` 根本没被碰过——本 demo ④ 段实测三行并排，`raw` 那行 `errno=0` 就是证据。

**Q2：内核为什么要保留 `[-4095, -1]` 作为错误码区间？`4095` 是怎么定的？**
A：内核态没有 `errno` 全局变量，所以约定「返回值本身就是 `-errno`」。为了不和合法返回值冲突，用 `MAX_ERRNO=4095`（`include/linux/err.h:17`）圈出一个专用区间：上界比任何平台的 `errno` 最大值都大，下界又小到不会和合法值（fd、字节数、指针）撞上。`IS_ERR()` 判的就是这个区间。

**Q3：`sys_call_table` 是什么？系统调用号从哪来？**
A：`sys_call_table[]` 是 `arch/x86/entry/syscall_64.c:16` 定义的函数指针数组，「系统调用号 = 数组下标」。它由 `arch/x86/entry/syscalls/syscall_64.tbl` 生成。内核执行路径是 `common.c:40 do_syscall_x64()` → `:48` 判 `unr < NR_syscalls` → `:50` `regs->ax = sys_call_table[unr](regs)`；号越界就落到 `__x64_sys_ni_syscall()` 返回 `ENOSYS`（本 demo ⑤ 段实测）。

**Q4：`write()` 失败返回 `-1` 并把 `errno` 设成 `EFAULT`，为什么不是段错误？**
A：因为内核**从不直接解引用用户指针**。它先 `access_ok()` 校验地址范围，再 `copy_from_user()` 拷贝；校验失败就直接返回 `-EFAULT`。所以用户态传坏指针不会把内核搞崩，只会拿到一个错误码——这也是「用户态崩溃拖不垮内核」的隔离基石。

**Q5：往一个读端已关闭的管道里 `write`，会发生什么？网络服务为什么要忽略 SIGPIPE？**
A：默认（`SIG_DFL`）是**进程被 SIGPIPE(13) 终止**，shell 视角 `$? = 141`；只有把 `SIGPIPE` 设成 `SIG_IGN` 之后，`write` 才会像普通失败那样返回 `-1` + `errno=EPIPE(32)`。网络服务对端断开后再写就是同一情形——不忽略它，服务会被自己的日志/回包写死。见本 demo ⑧ 段。
