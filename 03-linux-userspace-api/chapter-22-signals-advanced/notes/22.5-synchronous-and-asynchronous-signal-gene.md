# 22.5 同步与异步的信号生成

## 本节讲什么

1. **同步生成**与**异步生成**的判据是什么——不看"谁发的"，看"相对于进程执行流在什么时候发生"
2. 为什么同步信号必须**定向到故障线程**，而异步信号只需要**定向到进程**
3. `si_code` 的符号如何让你在 handler 里**一眼分辨**这两类信号

---

## 一、定义：以"产生时刻"为判据

| | **同步生成**（synchronous） | **异步生成**（asynchronous） |
|--|------------------------------|--------------------------------|
| **定义** | 由进程**自己正在执行的某条指令**直接引发 | 由进程**外部的事件**引发，与当前执行流无关 |
| **时机** | **可预测、可复现**——同一输入必然在同一条指令触发 | **不可预测**——任何时刻都可能到 |
| **递送时机** | 立即（异常返回前就挂上，返回用户态前递送） | 下一次从内核态返回用户态时 |
| **目标** | **故障线程**（`PIDTYPE_PID`，私有 pending） | **进程**（`PIDTYPE_TGID`，共享 pending） |
| **可阻塞** | ❌ 阻塞被内核撤销（`force_*` 路径） | ✅ 正常阻塞 |
| **典型** | `SIGSEGV` `SIGBUS` `SIGFPE` `SIGILL` `SIGTRAP` `SIGSYS` | `SIGINT` `SIGTERM` `SIGCHLD` `SIGALRM` `SIGIO` `SIGUSR1` |

**判据的精确表述**（这是最容易讲错的地方）：

> 不是"硬件产生 = 同步、软件产生 = 异步"，而是——
> **信号是否由进程自身的执行流在某个确定的点上引发。**

反例一：`force_sig_fault()`（硬件路径）产生的信号显然是同步的。
反例二：`abort()` 内部调用 `raise(SIGABRT)`，是**软件**产生，但它是**同步**的——因为是当前线程自己、在当前位置引发的。
反例三：`perf` 产生的 `SIGTRAP` 由硬件事件触发，但它是**异步**的——采样中断与进程当前执行到哪条指令无关（内核还专门用 `TRAP_PERF_FLAG_ASYNC` 标记这种情况，见 [22.4](22.4-hardware-generated-signals.md)）。

所以内核的做法是**硬编码一个名单**，而不是推导：

```c
/* kernel/signal.c:205 */
#define SYNCHRONOUS_MASK \
        (sigmask(SIGSEGV) | sigmask(SIGBUS) | sigmask(SIGILL) | \
         sigmask(SIGTRAP) | sigmask(SIGFPE) | sigmask(SIGSYS))
```

## 二、内核如何区分：两条发送路径

### 2.1 同步路径 `force_*` → 定向线程

```c
/* kernel/signal.c:1336 */
static int
force_sig_info_to_task(struct kernel_siginfo *info, struct task_struct *t,
        enum sig_handler handler)
{
        ...
        /* :1364 —— 注意最后一个参数 */
        ret = send_signal_locked(sig, info, t, PIDTYPE_PID);
        ...
}
```

`PIDTYPE_PID` → `__send_signal_locked()` 里据此选择 pending 集合：

```c
/* kernel/signal.c:1098 */
        pending = (type != PIDTYPE_PID) ? &t->signal->shared_pending : &t->pending;
```

| `type` | 目标 | pending 集合 |
|--------|------|--------------|
| `PIDTYPE_PID` | 具体**线程** | `task_struct.pending`（私有） |
| `PIDTYPE_TGID` | **进程**（线程组） | `signal_struct.shared_pending`（共享） |

**为什么同步信号必须定向到线程？**

因为它的语义绑定在"那个线程的那个执行点上"：

1. **PC 必须正确**：sigframe 要保存触发故障的指令地址，只有故障线程能给出这个值
2. **`si_addr` 只对故障线程有意义**：别的线程没有这个上下文
3. **修复才有意义**：如果 handler 通过 `mprotect()` 修好了，重试指令的必须是**原来那个线程**
4. **正确性**：如果让别的线程处理，那个线程可能正好好好的，跑一个"段错误处理"完全是错乱的行为

### 2.2 异步路径 `send_sig_info()` → 定向进程

```c
/* kernel/signal.c:1644 */
int send_sig_info(int sig, struct kernel_siginfo *info, struct task_struct *p)
{
        ...
        return do_send_sig_info(sig, info, p, PIDTYPE_TGID);   /* ← 进程级 */
}
```

进共享 pending 后，**任何一个没有阻塞该信号的线程**都可以取走（`dequeue_signal():645-649`：先查私有，再查共享）。内核不保证哪个线程会跑 handler——这取决于调度。

这正是多线程信号模型复杂性的根源，也是 [22.10](22.10-synchronously-waiting-for-a-signal.md) 推荐"全员阻塞 + 专用线程 `sigwaitinfo`"的原因。

### 2.3 一个特殊的中间态：`send_sig_perf()`

```c
/* kernel/signal.c:1824 */
int send_sig_perf(void __user *addr, u32 type, u64 sig_data)
{
        ...
        info.si_code = TRAP_PERF;
        ...
        info.si_perf_flags = sigismember(&current->blocked, info.si_signo) ?
                                     TRAP_PERF_FLAG_ASYNC : 0;
        return send_sig_info(info.si_signo, &info, current);   /* 常规路径，非 force */
}
```

`SIGTRAP` 在 `SYNCHRONOUS_MASK` 里（断点、单步是同步的），但 **perf 事件是异步的**。内核的处理：仍然用异步路径（`send_sig_info`），但用 `si_perf_flags` 的 `TRAP_PERF_FLAG_ASYNC` 位**显式告知用户态"这次是异步的"**。

注释（`:1836-1841`）：

> *"Signals generated by perf events should not terminate the whole process if SIGTRAP is blocked, however, delivering the signal asynchronously is better than not delivering at all. But tell user space if the signal was asynchronous, so it can clearly be distinguished from normal synchronous ones."*

**这是一个重要的通用设计原则**：当同一个信号编号可能承载不同语义、且内核无法保证其中一种语义时，**用额外的标志位把不确定性显式暴露出来**，而不是让用户态去猜。

## 三、递送时的优先级：同步信号插队

既然同步信号"绑定在当前指令上"，它就必须**赶在别的信号之前**被处理：

```c
/* kernel/signal.c:209 */
int next_signal(struct sigpending *pending, sigset_t *mask)
{
        ...
        x = *s &~ *m;
        if (x) {
                if (x & SYNCHRONOUS_MASK)
                        x &= SYNCHRONOUS_MASK;      /* ← 屏蔽掉所有非同步信号 */
                sig = ffz(~x) + 1;
                return sig;
        }
        ...
}
```

`dequeue_signal()` 之前还有一层：

```c
/* kernel/signal.c:716 */
static int dequeue_synchronous_signal(kernel_siginfo_t *info)
{
        struct task_struct *tsk = current;
        struct sigpending *pending = &tsk->pending;

        /* Might a synchronous signal be in the queue? */
        if (!((pending->signal.sig[0] & ~tsk->blocked.sig[0]) & SYNCHRONOUS_MASK))
                return 0;

        /* Return the first synchronous signal in the queue. */
        list_for_each_entry(q, &pending->list, list) {
                /* Synchronous signals have a positive si_code */
                if ((q->info.si_code > SI_USER) &&
                    (sigmask(q->info.si_signo) & SYNCHRONOUS_MASK)) {
                        sync = q;
                        goto next;
                }
        }
        return 0;
        ...
}
```

`get_signal()` 里的调用顺序 + 那段必读注释（`:2763-2773`）：

```c
        /*
         * Signals generated by the execution of an instruction
         * need to be delivered before any other pending signals
         * so that the instruction pointer in the signal stack
         * frame points to the faulting instruction.
         */
        type = PIDTYPE_PID;
        signr = dequeue_synchronous_signal(&ksig->info);      /* :2770 先查同步 */
        if (!signr)
                signr = dequeue_signal(current, &current->blocked,
                                       &ksig->info, &type);   /* :2772 再查常规 */
```

```
get_signal() 的出队顺序

  ① dequeue_synchronous_signal()     只看【私有 pending】里的 SYNCHRONOUS_MASK 信号
     │                              且要求 si_code > SI_USER（即内核产生，非用户伪造）
     ├─ 命中 → 立即递送（PC 指向故障指令）
     └─ 未命中 ↓

  ② dequeue_signal()
     ├─ 先查 task_struct.pending（私有）
     └─ 再查 signal_struct.shared_pending（共享）
        在命中的那一层里：SYNCHRONOUS_MASK 优先 → 再按编号升序
```

> **注意 `dequeue_synchronous_signal()` 里的 `si_code > SI_USER` 判断**：这一条把**用户伪造的同步信号**（`kill(pid, SIGSEGV)`，其 `si_code = SI_USER = 0`）排除在外了。所以你用 `kill` 发一个 SIGSEGV，它不会享受"插队"待遇——只有内核真正 `force_*` 出来的才算。

## 四、`si_code` 的符号：用户态的判据

```c
/* include/uapi/asm-generic/siginfo.h:190 */
#define SI_FROMUSER(siptr)      ((siptr)->si_code <= 0)
#define SI_FROMKERNEL(siptr)    ((siptr)->si_code >  0)
```

| `si_code` 范围 | 来源 | 典型值 |
|----------------|------|--------|
| `> 0` | **内核 / 硬件** | `SI_KERNEL`(0x80)、`SEGV_MAPERR`(1)、`FPE_INTDIV`(1)、`ILL_ILLOPC`(1)、`CLD_EXITED`(1)、`SI_TIMER`(-2? 见下) |
| `= 0` | **用户进程用 `kill()`** | `SI_USER` = 0 |
| `< 0` | **用户进程用 `sigqueue()` / `sigaction` 的 `SA_SIGINFO`** | `SI_QUEUE`(-1)、`SI_TIMER`(-2)、`SI_MESGQ`(-3)、`SI_ASYNCIO`(-4)、`SI_SIGIO`(-5)、`SI_TKILL`(-6) |

> ⚠️ **常见混淆点**：`SI_TIMER`、`SI_MESGQ` 等虽然是"内核机制"产生的，但它们的 `si_code` 是**负数**，所以 `SI_FROMUSER()` 会返回 true。这里的 "USER" 更准确的语义是"**不是硬件/CPU 故障**"，而非"来自另一个用户进程"。POSIX 的措辞也是这个意思——`si_code <= 0` 表示"由 `kill`/`sigqueue`/`timer` 等常规机制产生"，`si_code > 0` 留给"信号特定的错误码"（`SEGV_*`/`FPE_*`/`ILL_*`/`BUS_*`/`TRAP_*`/`CLD_*`/`POLL_*`/`SYS_*`）。

**实用判据**：

```c
static void handler(int sig, siginfo_t *si, void *ctx)
{
    if (SI_FROMKERNEL(si)) {
        /* si_code > 0：真·内核/硬件产生 —— 对同步信号来说就是"真故障" */
        switch (si->si_code) {
        case SEGV_MAPERR:  /* 空指针/未映射 */ break;
        case SEGV_ACCERR:  /* 权限不足 */     break;
        ...
        }
    } else {
        switch (si->si_code) {
        case SI_USER:   /* 别人 kill() 过来的 —— 可能是伪造的 SIGSEGV！ */ break;
        case SI_QUEUE:  /* sigqueue() 过来的 */ break;
        case SI_TKILL:  /* tkill/tgkill，线程库用 */ break;
        }
    }
}
```

**安全含义**：恶意进程可以 `kill(pid, SIGSEGV)` 让目标进程"以为"自己段错误了。如果你的 handler 会因此 `abort()` 或写 core，就构成了一个**本地拒绝服务**漏洞。防御方式就是检查 `SI_FROMKERNEL(si)`——只有真正的硬件故障才 `si_code > 0`。

## 五、两类信号的处理模型对比

| 维度 | 同步信号 | 异步信号 |
|------|----------|----------|
| **何时到** | 确定的指令点 | 任意时刻（两条指令之间） |
| **被阻塞** | 内核强行撤销阻塞 | 正常挂起，解除阻塞后递送 |
| **被忽略** | 内核强行重置为 `SIG_DFL` | 正常丢弃 |
| **多线程** | 只在故障线程跑 handler | 任一未阻塞线程跑 handler（不定） |
| **handler 里能做什么** | 极少（栈可能坏了）→ 通常只记日志后 `_exit()` | 相对多（但受 async-signal-safe 约束） |
| **能否"修复后返回"** | ✅ 可以（如 `mprotect` 后重试） | 不适用（没有"重试"的概念） |
| **能否用 signalfd / sigwaitinfo 同步取** | ❌ **不行**（`force_*` 绕过阻塞，直接递送） | ✅ 可以（这是推荐模型） |
| **递送延迟** | 立即（返回用户态前必处理） | 取决于进程何时陷入内核 |

**最后两行极其重要**，展开说：

### 5.1 同步信号**不能**用 signalfd / `sigwaitinfo` 捕获

原因很直接：`force_sig_info_to_task():1352-1355` 会**解除阻塞**：

```c
        if (blocked) {
                sigdelset(&t->blocked, sig);
                recalc_sigpending_and_wake(t);
        }
```

而 signalfd 和 `sigwaitinfo` 的前提都是"信号被阻塞着，所以不会走递送路径，只能从 pending 里取"。同步信号**根本不给你阻塞的机会**——阻塞被撤销 → 信号走常规递送 → 跑 handler（或默认终止）→ signalfd 永远读不到它。

**所以**：生产环境的"signalfd 统一事件循环"方案**必须保留 SIGSEGV/SIGBUS/SIGFPE/SIGILL 的 handler 兜底**，不能指望 signalfd 全包。这是 [22.11](22.11-fetching-signals-via-a-file-descriptor.md) 那张"优势与限制"表里最容易被忽略的一条。

### 5.2 异步信号可以彻底"同步化"

这是现代服务端（尤其 HFT）的标准做法：

```
传统模型                              同步化模型
──────────                            ──────────
信号随时到达                           ① 所有线程先阻塞目标信号
  ↓                                   ② 创建专用线程
打断热路径线程                         ③ 专用线程 sigwaitinfo()/signalfd 循环
  ↓                                      ↓
handler 跑（async-signal-safe 约束）    普通同步代码：可 malloc/printf/加锁
```

这样**异步性被彻底消除**——信号从"随时打断你的中断"变成"队列里的一个消息"。代价是：延迟从"立即"变成"专用线程被调度后"（通常几十微秒），对控制信号完全可接受。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① 同步信号（`SIGSEGV`/`SIGBUS`/`SIGILL`）在无 MMU 的 MCU 上不存在，在嵌入式 Linux（Cortex-A）上是**现场崩溃的主要形态**，且现场往往无法接调试器 → 必须在 handler 里记录 `si_code`/`si_addr`/backtrace 到持久存储。② **`SIGBUS/BUS_ADRERR` 在嵌入式特别高发**：`mmap` 的配置文件/日志文件被掉电截断或被其他进程重写。掉电保护（原子写 + `fsync` + 临时文件 rename）比事后处理更重要。③ 异步信号（`SIGTERM`/`SIGUSR1`）用于优雅重启/配置重载，建议全部阻塞 + 专用线程处理，避免打断实时控制回路 |
| HFT | ① **异步信号是延迟抖动的隐藏来源**：即使 handler 什么也不做，一次信号递送也要走"陷入内核 → 建栈帧 → 跑 handler → `sigreturn`"，典型的额外开销在**微秒量级**，且伴随着 IPI（跨核中断）和缓存污染。热路径线程应该 `pthread_sigmask` 屏蔽**所有**可屏蔽信号。② **同步信号不能被 signalfd 捕获**——这是设计"生产级信号处理模块"时最容易漏的一点：signalfd 处理 `SIGTERM`/`SIGUSR1`/`SIGCHLD`，`SIGSEGV`/`SIGBUS`/`SIGFPE`/`SIGILL` **必须**保留 `SA_ONSTACK` 的 handler 兜底。③ **盘前防线**：同步信号 100% 是内存/算术 bug，用 ASan/UBSan 构建跑全量回归能拦下绝大多数——生产崩溃一次的损失远超盘前多跑几小时 |

## 代码示例

### 示例 1：用 `si_code` 符号区分"真段错误"与"伪造段错误"

```c
/* sync_async.c —— 区分同步/异步信号，识别伪造的 SIGSEGV
 * 编译: gcc -O0 -g -o sync_async sync_async.c
 * 用法: ./sync_async real      （真实硬件故障）
 *       ./sync_async fake      （kill() 伪造）
 *       ./sync_async async     （异步信号：另开终端 kill -USR1 <pid>） */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <unistd.h>

static void wr(const char *s) { write(STDOUT_FILENO, s, strlen(s)); }

static void handler(int sig, siginfo_t *si, void *ctx)
{
    (void)ctx;
    wr("\n──────── 信号到达 ────────\n");
    wr("  sig      : ");
    switch (sig) {
    case SIGSEGV: wr("SIGSEGV(11)"); break;
    case SIGUSR1: wr("SIGUSR1(10)"); break;
    default:      wr("其他");        break;
    }
    wr("\n");

    wr("  si_code  : ");
    /* 手写十进制（避免 snprintf） */
    char b[16]; int i = 0; int v = si->si_code;
    unsigned u = (unsigned)((v < 0) ? -v : v);
    if (v < 0) b[i++] = '-';
    int st = i;
    do { b[i++] = (char)('0' + u % 10); u /= 10; } while (u);
    for (int a = st, z = i - 1; a < z; a++, z--) { char t = b[a]; b[a] = b[z]; b[z] = t; }
    write(STDOUT_FILENO, b, (size_t)i);
    wr("\n");

    wr("  来源判据 : ");
    wr(SI_FROMKERNEL(si) ? "SI_FROMKERNEL (si_code > 0)  ← 内核/硬件\n"
                         : "SI_FROMUSER   (si_code <= 0) ← 常规机制\n");

    /* 关键判断：只有 si_code > 0 的 SIGSEGV 才是真硬件故障 */
    if (sig == SIGSEGV) {
        if (SI_FROMKERNEL(si)) {
            wr("  ★ 真实硬件故障（同步生成）\n");
            wr("    - 由 force_sig_fault() 发出\n");
            wr("    - 阻塞/忽略被内核撤销\n");
            wr("    - 定向到故障线程 (PIDTYPE_PID)\n");
            wr("    - signalfd/sigwaitinfo 【捕获不到】\n");
            wr("    → 记日志后 _exit()，绝不继续运行\n");
        } else {
            wr("  ⚠ 伪造的 SIGSEGV（异步生成，si_code=SI_USER=0）\n");
            wr("    - 来自 kill()/raise()，不是真故障\n");
            wr("    - 不享受 SYNCHRONOUS_MASK 插队待遇\n");
            wr("    - 若因此 abort() 就构成了本地 DoS 漏洞\n");
            wr("    → 忽略它，程序继续正常执行\n");
            return;                      /* 安全返回：没有真实故障要重试 */
        }
    } else {
        wr("  ● 普通异步信号 → 正常处理\n");
        return;
    }

    _exit(128 + sig);                    /* 真故障：绝不返回 */
}

int main(int argc, char **argv)
{
    struct sigaction sa = {0};
    sa.sa_sigaction = handler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGUSR1, &sa, NULL);

    static char alt[SIGSTKSZ * 4];
    stack_t ss = { .ss_sp = alt, .ss_size = sizeof(alt), .ss_flags = 0 };
    sigaltstack(&ss, NULL);

    const char *mode = (argc > 1) ? argv[1] : "real";

    if (!strcmp(mode, "real")) {
        wr("[实验 A] 真实硬件故障：解引用空指针\n");
        volatile int *p = (volatile int *)0;
        *p = 42;                         /* → 同步 SIGSEGV，si_code=SEGV_MAPERR(1) */
    } else if (!strcmp(mode, "fake")) {
        wr("[实验 B] 伪造：kill(getpid(), SIGSEGV)\n");
        raise(SIGSEGV);                  /* → 异步，si_code=SI_USER(0) */
        wr("程序继续正常运行 —— 伪造的 SIGSEGV 被识别并忽略\n");
    } else {
        wr("[实验 C] 异步信号：等待 SIGUSR1\n");
        wr("请另开终端执行: kill -USR1 ");
        char pidb[16];
        int n = 0; long p = (long)getpid();
        long t = p; do { n++; t /= 10; } while (t);
        pidb[n] = '\n';
        while (n > 0) { pidb[--n] = (char)('0' + p % 10); p /= 10; }
        write(STDOUT_FILENO, pidb, strlen(pidb));
        pause();
        wr("异步信号处理完毕，程序继续\n");
    }
    return 0;
}
```

### 示例 2：验证"同步信号插队"

```c
/* sync_priority.c —— 验证 SYNCHRONOUS_MASK 的插队行为
 * 编译: gcc -O0 -g -o sync_priority sync_priority.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void wr(const char *s) { write(STDOUT_FILENO, s, strlen(s)); }

/* 不同信号用不同 handler，好观察顺序 */
static void h_segv(int sig)  { (void)sig; wr("  → SIGSEGV(11) 先递送（同步，插队）\n"); _exit(0); }
static void h_usr1(int sig)  { (void)sig; wr("  → SIGUSR1(10) 递送\n"); }
static void h_alrm(int sig)  { (void)sig; wr("  → SIGALRM(14) 递送\n"); }

int main(void)
{
    struct sigaction sa = {0};
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sa.sa_handler = h_segv; sigaction(SIGSEGV, &sa, NULL);
    sa.sa_handler = h_usr1; sigaction(SIGUSR1, &sa, NULL);
    sa.sa_handler = h_alrm; sigaction(SIGALRM, &sa, NULL);

    /* 全部阻塞 */
    sigset_t all, empty;
    sigfillset(&all);
    sigdelset(&all, SIGKILL);            /* SIGKILL 本来就阻塞不住，这里只是示意 */
    sigprocmask(SIG_SETMASK, &all, NULL);
    sigemptyset(&empty);

    /* 按"编号升序会先 USR1(10)、再 SEGV(11)、再 ALRM(14)"的顺序构造 */
    raise(SIGUSR1);                      /* 异步，编号最小 */
    raise(SIGALRM);                      /* 异步，编号最大 */
    /* 用 kill() 伪造的 SIGSEGV 不享受插队（si_code=SI_USER），
     * 所以这里必须用【真实】故障才能验证插队 —— 但真实故障会打断阻塞流程。
     *
     * 折中：演示"伪造 SIGSEGV 不插队"，即按编号升序递送。 */

    wr("① 先验证：伪造的 SIGSEGV 不插队（按编号升序）\n");
    raise(SIGSEGV);                      /* si_code = SI_USER(0) → 不进同步优先队列 */

    sigsuspend(&empty);                  /* 放行一个 */
    sigsuspend(&empty);
    sigsuspend(&empty);
    sigprocmask(SIG_SETMASK, &empty, NULL);

    wr("   （若输出是 USR1(10) → SEGV(11) → ALRM(14)，说明伪造的 SEGV 没插队）\n\n");

    wr("② 真实硬件故障的插队无法在此干净地演示：\n"
       "   因为 force_sig_fault() 会【解除阻塞】并【立即递送】，\n"
       "   不等你 sigsuspend —— 这正是'同步'的含义。\n");
    return 0;
}
```

预期输出：

```
① 先验证：伪造的 SIGSEGV 不插队（按编号升序）
  → SIGUSR1(10) 递送
  → SIGSEGV(11) 先递送（同步，插队）      ← 注意：handler 名字有歧义，它其实不插队
  → SIGALRM(14) 递送
   （若输出是 USR1(10) → SEGV(11) → ALRM(14)，说明伪造的 SEGV 没插队）

② 真实硬件故障的插队无法在此干净地演示：
   因为 force_sig_fault() 会【解除阻塞】并【立即递送】，
   不等你 sigsuspend —— 这正是'同步'的含义。
```

> 第 ① 项的输出顺序 `10 → 11 → 14` 恰恰证明了：`kill()` 伪造的 SIGSEGV **没有**获得 `SYNCHRONOUS_MASK` 的优先权——因为 `dequeue_synchronous_signal():733` 要求 `q->info.si_code > SI_USER`。

## 代码自测

<details>
<summary><b>问 1：</b>"硬件产生的信号 = 同步信号"这个说法对吗？举出反例。</summary>

**不对。** 判据不是"谁产生的"，而是"相对于进程执行流在什么时刻产生"。

内核也不做推导，而是硬编码名单：

```c
/* kernel/signal.c:205 */
#define SYNCHRONOUS_MASK \
        (sigmask(SIGSEGV) | sigmask(SIGBUS) | sigmask(SIGILL) | \
         sigmask(SIGTRAP) | sigmask(SIGFPE) | sigmask(SIGSYS))
```

**反例一：软件产生但同步**

```c
abort();     /* 内部是 raise(SIGABRT) —— 软件产生，但是同步的 */
```

它是**当前线程、在当前代码位置、确定性地**引发的，同一输入必然在同一处触发。所以它是同步的（虽然 `SIGABRT` 不在 `SYNCHRONOUS_MASK` 里——内核的名单是"必须由 CPU 故障上下文保证 PC 正确"的最小集合，不等同于理论上的同步/异步分类）。

**反例二：硬件产生但异步**

`perf` 采样事件触发的 `SIGTRAP`。它由硬件（PMU 计数器溢出中断）产生，但与进程"当前正在执行哪条指令"毫无关系——是**任意时刻**插进来的。内核专门用标志位标注这一点（`kernel/signal.c:1836-1845`）：

```c
        /*
         * Signals generated by perf events should not terminate the whole
         * process if SIGTRAP is blocked, however, delivering the signal
         * asynchronously is better than not delivering at all. But tell user
         * space if the signal was asynchronous, so it can clearly be
         * distinguished from normal synchronous ones.
         */
        info.si_perf_flags = sigismember(&current->blocked, info.si_signo) ?
                                     TRAP_PERF_FLAG_ASYNC : 0;
```

注意 `SIGTRAP` **在** `SYNCHRONOUS_MASK` 里（因为断点/单步是同步的），但 perf 事件这个特例是异步的——**同一个信号编号可以承载两种语义**，内核用 `si_perf_flags` 区分。

**反例三：硬件路径的"伪造"**

```c
kill(pid, SIGSEGV);      /* SIGSEGV 是"硬件信号"，但这次是软件伪造的 */
```

`si_code = SI_USER = 0`，不享受插队待遇，也**可以**被忽略/阻塞。内核在 `dequeue_synchronous_signal():733` 明确排除了它：

```c
                /* Synchronous signals have a positive si_code */
                if ((q->info.si_code > SI_USER) &&
                    (sigmask(q->info.si_signo) & SYNCHRONOUS_MASK)) {
```

**正确表述**：

| | 同步 | 异步 |
|--|------|------|
| 判据 | 由**进程自身执行流的确定点**引发 | 由**外部事件**在任意时刻引发 |
| 例子 | CPU 异常（`#PF`/`#DE`/`#UD`）、`abort()` | `kill()`、终端 `Ctrl-C`、定时器、子进程退出、perf 采样 |

</details>

<details>
<summary><b>问 2：</b>为什么同步信号必须定向到线程，而异步信号只需要定向到进程？</summary>

根源在于**语义绑定对象不同**。

**同步信号绑定在"那个线程的那个执行点"上**：

```c
/* force_sig_info_to_task():1364 */
        ret = send_signal_locked(sig, info, t, PIDTYPE_PID);   /* ← 线程 */
```

必须如此的四个理由：

1. **PC 必须正确**——sigframe 里保存的返回地址必须指向触发故障的指令。只有故障线程的 `pt_regs` 里有这个值。内核注释（`get_signal():2763-2767`）：
   > *"Signals generated by the execution of an instruction need to be delivered before any other pending signals so that the instruction pointer in the signal stack frame points to the faulting instruction."*

2. **`si_addr` 只对故障线程有意义**——`SIGSEGV` 的 `si_addr` 是那个线程访问的地址，别的线程没有这个上下文，拿到了也无法解释。

3. **"修复后重试"必须有意义**——如果 handler 用 `mprotect()` 修好了权限，CPU 重试指令时**必须是原来那个线程**（寄存器状态也必须是原来的）。换个线程重试，指令和寄存器都不对，毫无意义。

4. **不能连坐无辜线程**——让一个好端端的线程去跑"段错误处理"，会导致它做错误的动作（比如误把自己终止）。

**异步信号不需要绑定到具体线程**：

```c
/* send_sig_info():1644 */
        return do_send_sig_info(sig, info, p, PIDTYPE_TGID);   /* ← 进程 */
```

因为它的语义是"**这个进程**该处理这件事了"——`SIGTERM` 是"请这个进程退出"，`SIGCHLD` 是"这个进程有子进程退出了"，`SIGALRM` 是"这个进程设的定时器到期了"。**哪个线程去处理都行**，只要有一个去处理。

内核出队时的规则（`dequeue_signal():641-649`）：

```c
        /* We only dequeue private signals from ourselves, we don't let
         * signalfd steal them
         */
        *type = PIDTYPE_PID;
        signr = __dequeue_signal(&tsk->pending, mask, info, &resched_timer);
        if (!signr) {
                *type = PIDTYPE_TGID;
                signr = __dequeue_signal(&tsk->signal->shared_pending,
                                         mask, info, &resched_timer);
        }
```

即：**任何线程**都能从共享 pending 里取，前提是它自己没阻塞这个信号（`next_signal()` 用该线程的 `current->blocked` 过滤）。

**由此产生的实践问题与解法**：

| 问题 | 解法 |
|------|------|
| "哪个线程跑 handler"不确定 | 全员阻塞 + 专用线程 `sigwaitinfo()`（[22.10](22.10-synchronously-waiting-for-a-signal.md)） |
| 信号可能打断热路径线程 | 同上，热路径线程 `pthread_sigmask` 全屏蔽 |
| 同步信号无法被"同步化" | 无解——它绕过阻塞。必须保留 handler 兜底 |

</details>

<details>
<summary><b>问 3：</b>用 signalfd 或 sigwaitinfo 能捕获 SIGSEGV 吗？为什么？</summary>

**不能。** 这是设计"生产级信号处理模块"时最容易忽略的一条。

**原因**：`signalfd` 和 `sigwaitinfo` 的工作前提是"**信号被阻塞，所以不会走递送路径，只能从 pending 里取**"。而同步信号**根本不给你阻塞的机会**——`force_sig_info_to_task():1352-1355` 会强行解除阻塞：

```c
        if (blocked || ignored || (handler != HANDLER_CURRENT)) {
                action->sa.sa_handler = SIG_DFL;      /* 撤销 SIG_IGN */
                if (handler == HANDLER_EXIT)
                        action->sa.sa_flags |= SA_IMMUTABLE;
                if (blocked) {
                        sigdelset(&t->blocked, sig);  /* ← 强行解除阻塞 */
                        recalc_sigpending_and_wake(t);
                }
        }
```

阻塞被撤销 → 信号走**常规递送路径** → 跑 handler（或默认终止 + core dump）→ signalfd 的 `read()` 永远读不到它。

**对比表**：

| 信号类型 | 能否被 signalfd / `sigwaitinfo` 捕获 | 处理方式 |
|----------|-------------------------------------|----------|
| `SIGTERM` / `SIGINT` | ✅ | signalfd 统一进 epoll |
| `SIGUSR1` / `SIGUSR2` | ✅ | 同上 |
| `SIGCHLD` | ✅ | 同上 |
| 实时信号（`sigqueue`） | ✅ | 同上 |
| **`SIGSEGV`** | ❌ | **必须**装 handler |
| **`SIGBUS`** | ❌ | 同上 |
| **`SIGFPE`** | ❌ | 同上 |
| **`SIGILL`** | ❌ | 同上 |
| **`SIGTRAP`**（真断点/单步） | ❌ | 同上 |
| **`SIGSYS`**（seccomp） | ❌ | 同上 |
| `SIGKILL` / `SIGSTOP` | ❌（且无法捕获） | 无解 |

**正确的混合架构**：

```
                    ┌──────────────────────────────────────┐
                    │  进程启动时的信号策略                  │
                    └───────────────┬──────────────────────┘
                                    │
        ┌───────────────────────────┴───────────────────────────┐
        │                                                       │
   异步信号（可控）                                      同步信号（不可控）
   SIGTERM/SIGINT/SIGCHLD/SIGUSR*                    SIGSEGV/SIGBUS/SIGFPE/SIGILL
        │                                                       │
        ├─ sigprocmask 全部阻塞                          ├─ sigaction 装 handler
        ├─ signalfd() 拿 fd                             ├─ SA_SIGINFO（要 si_addr）
        ├─ epoll_ctl(ADD, sfd)                         ├─ SA_ONSTACK（栈溢出也能跑）
        └─ 主循环统一处理                                └─ handler 里记日志后 _exit()
                                                              （绝不 longjmp 回主循环）
```

**代码骨架**（[Ch21.7 综合题](../../chapter-21-signal-handlers/notes/21.7-exercise.md) 有完整版）：

```c
/* 1) 异步信号：阻塞 + signalfd */
sigset_t async_set;
sigemptyset(&async_set);
sigaddset(&async_set, SIGTERM);
sigaddset(&async_set, SIGINT);
sigaddset(&async_set, SIGCHLD);
sigaddset(&async_set, SIGUSR1);
pthread_sigmask(SIG_BLOCK, &async_set, NULL);
int sfd = signalfd(-1, &async_set, SFD_CLOEXEC);
/* 把 sfd 加进 epoll ... */

/* 2) 同步信号：保留 handler 兜底（【不能】放进 async_set！） */
struct sigaction sa = {0};
sa.sa_sigaction = crash_handler;
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
sigemptyset(&sa.sa_mask);
sigaction(SIGSEGV, &sa, NULL);
sigaction(SIGBUS,  &sa, NULL);
sigaction(SIGFPE,  &sa, NULL);
sigaction(SIGILL,  &sa, NULL);
```

> **一句话记住**：`signalfd` 只解决"**可阻塞**的信号"。同步故障信号的设计意图就是"**你不许阻塞我**"，二者在语义上是对立的。

</details>

<details>
<summary><b>问 4：</b><code>SI_FROMUSER()</code> 返回 true 就一定是"另一个用户进程发的"吗？<code>SI_TIMER</code> 为什么是负数？</summary>

**不是。** 这个宏的名字有误导性，它的真实语义是"**不是硬件/CPU 故障**"。

```c
/* include/uapi/asm-generic/siginfo.h:190 */
#define SI_FROMUSER(siptr)      ((siptr)->si_code <= 0)
#define SI_FROMKERNEL(siptr)    ((siptr)->si_code >  0)
```

**`si_code` 的真实分区**（POSIX 规定）：

| 区间 | 含义 | 典型值 |
|------|------|--------|
| `si_code > 0` | **信号特定的错误码**——留给"这个信号特有的故障细分" | `SEGV_MAPERR`(1)、`SEGV_ACCERR`(2)、`FPE_INTDIV`(1)、`ILL_ILLOPC`(1)、`BUS_ADRERR`(2)、`TRAP_BRKPT`(1)、`CLD_EXITED`(1)、`POLL_IN`(1) |
| `si_code == 0` | `SI_USER`——`kill()` 产生 | `SI_USER` = 0 |
| `si_code < 0` | 其他 POSIX 排队机制的标识 | `SI_QUEUE`(-1)、`SI_TIMER`(-2)、`SI_MESGQ`(-3)、`SI_ASYNCIO`(-4)、`SI_SIGIO`(-5)、`SI_TKILL`(-6)、`SI_KERNEL` 则是 **0x80（正）** |

**`SI_TIMER` 为什么是负数？**

因为 POSIX 把负数区间定义为"**产生来源标识**"（origin codes），而正数区间留给"**故障细分码**"（fault-specific codes）。定时器到期不是一个"故障"，所以没有细分码可用，只能归到负数区间用 `SI_TIMER` 标识来源。

于是产生一个反直觉的事实：

```c
/* 定时器到期产生的 SIGALRM */
if (SI_FROMKERNEL(si))        /* si_code = SI_TIMER = -2 → 返回 false！ */
    printf("内核产生");         /* 不会执行 */
else
    printf("非内核故障类");      /* 会执行 */
```

明明是内核的定时器机制产生的，`SI_FROMKERNEL()` 却返回 false。

**正确的使用方式**——不要把它当作"来源"判断，而是当作"**是不是硬件故障**"判断：

```c
static void handler(int sig, siginfo_t *si, void *ctx)
{
    if (si->si_code > 0) {
        /* 【细分故障码】区间 —— 对同步信号来说就是真·硬件故障 */
        if (sig == SIGSEGV) {
            switch (si->si_code) {
            case SEGV_MAPERR: /* 未映射 */ break;
            case SEGV_ACCERR: /* 权限不足 */ break;
            }
            log_crash_and_exit(si);     /* 真故障，不能继续 */
        } else if (sig == SIGCHLD) {
            switch (si->si_code) {
            case CLD_EXITED:  /* 子进程正常退出 */ break;
            case CLD_KILLED:  /* 被信号杀死 */     break;
            case CLD_DUMPED:  /* 被信号杀死并 core */ break;
            case CLD_STOPPED: /* 被停止 */         break;
            case CLD_CONTINUED: /* 被 SIGCONT 恢复 */ break;
            }
        }
    } else {
        /* 【来源标识】区间 */
        switch (si->si_code) {
        case SI_USER:   /* kill() —— 可能是伪造的 SIGSEGV！ */ break;
        case SI_QUEUE:  /* sigqueue() */  break;
        case SI_TIMER:  /* timer_create/timer_settime */ break;
        case SI_MESGQ:  /* POSIX 消息队列通知 */ break;
        case SI_ASYNCIO:/* AIO 完成 */ break;
        case SI_SIGIO:  /* 异步 I/O */ break;
        case SI_TKILL:  /* tkill/tgkill，NPTL 内部用 */ break;
        }
    }
}
```

**安全含义**：恶意进程可以 `kill(pid, SIGSEGV)`（或 `sigqueue`，`si_code < 0`）。如果你的 handler 一收到 `SIGSEGV` 就 `abort()` 或写 core，就构成了一个**本地拒绝服务**漏洞——攻击者能让你的服务随时"自杀"。防御就是检查 `si_code > 0`：只有真正的 CPU 故障才会是正数。

</details>

```c
                        sync = q;
                        goto next;
                }
        }

}
```

**第二段：`get_signal()` 里的调用顺序**

```c

         * Signals generated by the execution of an instruction
         * need to be delivered before any other pending signals
```

```c
                if (x & SYNCHRONOUS_MASK)
```

**用户伪造的为什么不被优待？**

关键就是 `dequeue_synchronous_signal():733` 那一行：

```c
                /* Synchronous signals have a positive si_code */
                if ((q->info.si_code > SI_USER) &&
                    (sigmask(q->info.si_signo) & SYNCHRONOUS_MASK)) {
```

`SI_USER == 0`，所以要求 `si_code > 0`。而：

| 产生方式 | `si_code` | 通过 `si_code > SI_USER`？ |
|----------|-----------|---------------------------|
| 真实 `#PF` → `force_sig_fault(SIGSEGV, SEGV_MAPERR, addr)` | `SEGV_MAPERR` = **1** | ✅ 通过 → 插队 |
| `kill(pid, SIGSEGV)` | `SI_USER` = **0** | ❌ 不通过 → 不插队 |
| `sigqueue(pid, SIGSEGV, sv)` | `SI_QUEUE` = **-1** | ❌ 不通过 → 不插队 |

**设计意图非常清晰**：插队的理由是"**PC 必须指向故障指令**"。用户伪造的 SIGSEGV 没有真实的故障指令，PC 停在哪里毫无意义——让它插队只会破坏正常的递送顺序，没有任何收益。

**顺带说明第二个条件**：`sigmask(q->info.si_signo) & SYNCHRONOUS_MASK` 是第二道检查——即使 `si_code > 0`，如果信号编号不在同步名单里（比如 `SIGCHLD` + `CLD_EXITED` = 1），也不享受插队。两个条件**同时**满足才算真同步故障。

**注意 `pending = &tsk->pending`**：`dequeue_synchronous_signal()` 只查**私有 pending**，不查共享 pending。这与"同步信号定向到线程"（`PIDTYPE_PID`）的设计完全一致。
