# 22.10 同步等待信号

> 源码核验：Linux v6.6 · `kernel/signal.c`（`SYSCALL_DEFINE4(rt_sigtimedwait):3663` · `SYSCALL_DEFINE4(rt_sigtimedwait_time32):3696`）

## 本节讲什么

1. `sigwaitinfo()` 与 `sigsuspend()` 的本质差别——**不跑 handler**，信号被"取走"而非"递送"
2. 它如何支撑**多线程程序的标准信号模型**（主线程屏蔽 + 专用线程消费）
3. `sigtimedwait()` 的超时语义，以及 `EAGAIN` 与 `EINTR` 的区分

---

## 一、接口

```c
#include <signal.h>

int sigwaitinfo(const sigset_t *set, siginfo_t *info);
/* 无限等待；成功返回**信号编号**，失败 -1 */

int sigtimedwait(const sigset_t *set, siginfo_t *info,
                 const struct timespec *timeout);
/* 带超时；超时返回 -1，errno = EAGAIN */
```

| 参数 | 说明 |
|------|------|
| `set` | 要等待的信号集合 |
| `info` | 输出参数，接收信号详情（`si_signo`/`si_pid`/`si_uid`/`si_value`…）；可为 `NULL` |
| `timeout` | 超时时间；传 `{0,0}` 表示**轮询**（立即返回） |

两者都由同一个内核入口实现：

```c
// kernel/signal.c:3663
SYSCALL_DEFINE4(rt_sigtimedwait, const sigset_t __user *, uthese,
		siginfo_t __user *, uinfo, const struct __kernel_timespec __user *, uts,
		size_t, sigsetsize)
```

> **`sigwaitinfo` 就是 `timeout == NULL` 的 `sigtimedwait`**——glibc 把前者实现为后者的封装。

---

## 二、核心差别：信号被"取走"而非"递送"

这是 `sigwaitinfo` 与 `sigsuspend`/`pause` 的**根本区别**：

| | `sigsuspend` / `pause` | **`sigwaitinfo`** |
|--|------------------------|-------------------|
| 机制 | 挂起等待 → 信号**递送** → 跑 handler → 返回 | 直接从 pending 队列**取走**信号 |
| handler | **会执行** | **不执行** |
| 返回值 | 总是 `-1`（`EINTR`） | **信号编号**（成功） |
| `siginfo` | 需 `SA_SIGINFO` 才能拿到 | ✅ 直接通过 `info` 输出 |
| 异步信号安全 | 受 handler 限制 | ✅ **无 handler，无限制** |

```
   sigsuspend:   信号 → 递送 → handler 执行 → 唤醒
   sigwaitinfo:  信号 → pending 队列 → 被"取走" → 函数返回信号编号
                        （handler 根本不参与）
```

**为什么必须阻塞信号**：如果信号未被阻塞，内核会正常递送它（跑 handler 或执行默认动作），`sigwaitinfo` 就没机会从 pending 队列里取走——**行为未定义**。

```c
sigprocmask(SIG_BLOCK, &set, NULL);       /* ← 必须先阻塞 */
int sig = sigwaitinfo(&set, &info);
```

## 三、最重要的实践：多线程信号模型

`sigwaitinfo` 最大的价值是支撑**多线程程序的标准信号处理架构**：

```
   主线程（启动时）                    专用信号线程
   ┌──────────────────────┐          ┌──────────────────────┐
   │ pthread_sigmask      │          │                      │
   │   (SIG_BLOCK 全部)    │          │  for (;;) {          │
   └──────────────────────┘          │    sig = sigwaitinfo │
          ↓ pthread_create           │    handle(sig);      │
   ┌──────────────────────┐          │  }                   │
   │ 工作线程 1..N         │          └──────────────────────┘
   │ (继承掩码 = 全部屏蔽)  │                    ↑
   └──────────────────────┘          信号留在 pending 等待被取
```

```c
static void *sig_thread(void *arg)
{
    sigset_t *set = arg;
    siginfo_t info;
    for (;;) {
        int sig = sigwaitinfo(set, &info);      /* 同步取，不跑 handler */
        if (sig == -1) { if (errno == EINTR) continue; break; }

        /* 这里运行在普通上下文 —— 可随意 printf / malloc / 加锁 */
        printf("线程 %lu 收到信号 %d，来自 pid=%d\n",
               (unsigned long)pthread_self(), sig, info.si_pid);
        if (sig == SIGTERM) { do_shutdown(); break; }
    }
    return NULL;
}

int main(void)
{
    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, SIGTERM);
    sigaddset(&set, SIGINT);
    sigaddset(&set, SIGHUP);

    /* ① 主线程先屏蔽（在创建任何线程之前！） */
    pthread_sigmask(SIG_BLOCK, &set, NULL);

    /* ② 创建工作线程 —— 它们继承主线程的掩码，天然全屏蔽 */
    for (int i = 0; i < N; i++)
        pthread_create(&workers[i], NULL, worker_fn, NULL);

    /* ③ 起一个专用线程用 sigwaitinfo 消费 */
    pthread_t tid;
    pthread_create(&tid, NULL, sig_thread, &set);

    /* ④ 主线程继续做业务，永不被 handler 打断 */
    ...
}
```

**这个模型的四个优势**：

| 优势 | 说明 |
|------|------|
| **无 handler** | 彻底摆脱异步信号安全限制，处理代码可随意 `printf`/`malloc`/加锁 |
| **确定线程** | 信号由固定线程处理，而非"任意一个未阻塞线程" |
| **同步语义** | 信号处理变成普通函数调用，逻辑清晰、可测试 |
| **零抢占** | 工作线程全程屏蔽信号，不会被打断，延迟可预测 |

> **关键细节**：第 ① 步必须在**创建任何线程之前**完成。因为新线程会继承创建时的掩码；如果先创建线程再屏蔽，那些线程就不会被屏蔽。

## 四、`sigtimedwait` 的超时与错误码

```c
struct timespec ts = { .tv_sec = 5, .tv_nsec = 0 };
int sig = sigtimedwait(&set, &info, &ts);
if (sig == -1) {
    if (errno == EAGAIN)       /* 超时，无信号到达 */
        printf("超时\n");
    else if (errno == EINTR)   /* 被**不在 set 中**的信号打断 */
        printf("被其他信号打断\n");
}
```

| `errno` | 含义 |
|---------|------|
| `EAGAIN` | **超时**——在指定时间内 `set` 中的信号都没到达 |
| `EINTR` | 被**不在 `set` 中**的其他信号打断（该信号走了自己的 handler） |
| `EINVAL` | `timeout` 非法（如 `tv_nsec` 超出 0~999999999） |

> **`sigtimedwait` 不会返回 `EINTR` 表示"set 中的信号到达"**——那些信号会被**取走**并正常返回编号。只有 `set` **之外**的信号才可能导致 `EINTR`。

**轮询技巧**：`timeout` 传 `{0, 0}` 可实现**非阻塞查询**——队列中有信号就取走，没有立即返回 `EAGAIN`：

```c
struct timespec zero = {0, 0};
int sig = sigtimedwait(&set, &info, &zero);   /* 非阻塞轮询 */
```

## 五、其他要点

| 要点 | 说明 |
|------|------|
| **多个信号同时未决** | 返回**编号最小**的那个（与实时信号的递送顺序规则一致） |
| **多线程并发调用** | 只有一个线程会成功取走信号，其余继续阻塞 |
| **`info` 可为 `NULL`** | 不需要详情时传 `NULL`，返回值仍是信号编号 |
| **`sigwait()`** | POSIX 的简化版（`int sigwait(const sigset_t*, int*)`），只返回编号不提供 `siginfo` |
| **实时信号** | 同样适用，且能取到 `si_value`（`sigqueue` 携带的数据） |
| **`SA_RESTART` 无关** | 因为不跑 handler，不存在 syscall 被中断的问题 |

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | `sigwaitinfo` 避免 handler 的异步干扰，把信号处理变成普通的同步函数调用，逻辑大幅简化、可测试性提升。嵌入式多线程守护进程的标准架构：主线程屏蔽全部信号 → 工作线程继承 → 专用线程 `sigwaitinfo` 消费。注意信号仍会**合并**（标准信号不排队），需要一个信号对应一次处理时应用实时信号 |
| HFT | 专用信号线程用 `sigwaitinfo` 收信号，**主线程与工作线程零中断**——这是低延迟系统的标准做法。行情处理线程全程不被 handler 抢占，延迟完全可预测；管理线程在独立的 `sigwaitinfo` 循环里处理停机/重载，两者互不干扰 |

## 代码示例：多线程标准模型

```c
/* sigwait.c —— 主线程屏蔽 + 专用线程 sigwaitinfo 消费
 * 编译: gcc -D_GNU_SOURCE -pthread -o sigwait sigwait.c
 * 运行后另开终端: kill -TERM <pid> / kill -HUP <pid> / kill -USR1 <pid> */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <pthread.h>

#define N_WORKERS 2

static volatile int running = 1;

/* 工作线程：继承主线程的掩码，全程不被信号打断 */
static void *worker(void *arg)
{
    long id = (long)arg;
    while (running) {
        printf("  工作线程 %ld 正在处理业务...\n", id);
        sleep(2);
    }
    printf("  工作线程 %ld 退出\n", id);
    return NULL;
}

/* 专用信号线程：同步取信号，不跑 handler */
static void *sig_thread(void *arg)
{
    const sigset_t *set = arg;
    siginfo_t info;

    printf("信号线程启动 (tid=%lu)\n", (unsigned long)pthread_self());
    for (;;) {
        int sig = sigwaitinfo(set, &info);
        if (sig == -1) {
            if (errno == EINTR) continue;
            perror("sigwaitinfo");
            break;
        }
        /* 普通上下文 —— 可随意 printf/malloc/加锁 */
        printf("[信号线程] 收到信号 %d, si_code=%d, 来自 pid=%d\n",
               sig, info.si_code, info.si_pid);

        if (sig == SIGTERM || sig == SIGINT) { running = 0; break; }
        if (sig == SIGHUP) printf("[信号线程] → 重载配置（模拟）\n");
    }
    return NULL;
}

int main(void)
{
    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, SIGTERM);
    sigaddset(&set, SIGINT);
    sigaddset(&set, SIGHUP);
    sigaddset(&set, SIGUSR1);

    /* ① 关键：在创建任何线程之前屏蔽 —— 新线程会继承 */
    pthread_sigmask(SIG_BLOCK, &set, NULL);

    /* ② 创建工作线程（继承掩码 = 全部屏蔽） */
    pthread_t workers[N_WORKERS];
    for (long i = 0; i < N_WORKERS; i++)
        pthread_create(&workers[i], NULL, worker, (void *)i);

    /* ③ 起专用信号线程 */
    pthread_t sigtid;
    pthread_create(&sigtid, NULL, sig_thread, &set);

    printf("PID=%d — 试: kill -TERM|-HUP|-USR1 %d\n", getpid(), getpid());

    for (int i = 0; i < N_WORKERS; i++) pthread_join(workers[i], NULL);
    pthread_join(sigtid, NULL);
    printf("主进程优雅退出\n");
    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b><code>sigwaitinfo</code> 和 <code>sigsuspend</code> 的本质区别是什么？</summary>

| | `sigsuspend` / `pause` | **`sigwaitinfo`** |
|--|------------------------|-------------------|
| 机制 | 挂起等待 → 信号**递送** → 跑 handler → 唤醒 | 从 pending 队列直接**取走**信号 |
| handler | **会执行** | **不执行** |
| 返回值 | 总是 `-1`（`EINTR`） | **信号编号**（成功） |
| `siginfo` | 需 `SA_SIGINFO` 才能拿到 | ✅ 直接通过 `info` 输出参数获得 |
| 异步信号安全 | 受 handler 限制 | ✅ **无 handler，无限制** |
| 信号状态 | 被递送（handler 跑完即消耗） | 被"取走"（handler 从不参与） |

**核心**：`sigwaitinfo` 让信号彻底绕开 handler 机制，变成一次**同步的"取"操作**。这是它最大的价值——处理代码运行在普通上下文，可随意调用 `printf`/`malloc`/加锁。

**代价**：必须阻塞信号（否则内核会正常递送它，`sigwaitinfo` 行为未定义）；且它是**阻塞**的，不能同时等 I/O（需要同时等 I/O 时用 signalfd）。

</details>

<details>
<summary><b>问 2：</b>为什么多线程程序推荐「主线程屏蔽 + 专用线程 sigwaitinfo」模型？</summary>

**问题背景**（回顾 [Ch20.10](../../chapter-20-signals-fundamentals/notes/20.10-the-signal-mask-blocking-signal-delivery.md)）：

- 掩码是**线程私有**的
- 用 `kill` 给多线程进程发信号，handler 由**任意一个**未阻塞该信号的线程执行——**不可预测**

这导致 handler 的上下文（栈、TLS、锁状态）完全随机，是 bug 温床。

**模型的四个优势**：

| 优势 | 说明 |
|------|------|
| **无 handler** | 摆脱异步信号安全限制，处理代码可随意 `printf`/`malloc`/加锁 |
| **确定线程** | 信号由固定的专用线程处理，行为可预测 |
| **同步语义** | 信号处理变成普通函数调用，逻辑清晰、可测试 |
| **零抢占** | 工作线程全程屏蔽，不被 handler 打断，延迟可预测 |

**两个关键实现细节**：

1. **屏蔽必须在创建任何线程之前完成**——新线程继承创建时的掩码。若先创建线程再屏蔽，那些线程就不受保护。

```c
pthread_sigmask(SIG_BLOCK, &set, NULL);        /* ① 先屏蔽 */
for (...) pthread_create(&workers[i], ...);    /* ② 后创建 → 继承 */
pthread_create(&sigtid, NULL, sig_thread, &set);/* ③ 专用线程消费 */
```

2. **用 `pthread_sigmask` 而非 `sigprocmask`**——POSIX 规定后者在多线程下行为未定义。

</details>

<details>
<summary><b>问 3：</b><code>sigtimedwait</code> 超时返回什么？<code>EAGAIN</code> 和 <code>EINTR</code> 有什么区别？</summary>

超时返回 `-1`，`errno = EAGAIN`。

| `errno` | 含义 |
|---------|------|
| **`EAGAIN`** | **超时**——在指定时间内 `set` 中的信号都没到达 |
| **`EINTR`** | 被**不在 `set` 中**的其他信号打断（该信号走了自己的 handler） |
| `EINVAL` | `timeout` 非法（如 `tv_nsec` 超出 `0`~`999999999`） |

**关键区分**：

- `set` **之中**的信号到达 → 被**取走**，函数**正常返回信号编号**（不是 `EINTR`）
- `set` **之外**的信号到达 → 走它自己的 handler，可能打断 `sigtimedwait` → `EINTR`

```c
int sig = sigtimedwait(&set, &info, &ts);
if (sig == -1) {
    if (errno == EAGAIN)      /* 超时 */
        printf("超时无信号\n");
    else if (errno == EINTR)  /* 被 set 之外的信号打断 */
        printf("被其他信号打断\n");
}
```

**非阻塞轮询技巧**：`timeout` 传 `{0, 0}`，有信号就取走，没有立即返回 `EAGAIN`：

```c
struct timespec zero = {0, 0};
int sig = sigtimedwait(&set, &info, &zero);
```

</details>

<details>
<summary><b>问 4：</b>多个线程同时调用 <code>sigwaitinfo</code> 等待同一组信号，会怎样？</summary>

**只有一个线程会成功取走信号**，其余线程继续阻塞。

这是内核的队列语义决定的——pending 队列中的信号是"竞争消费"的，先被调度到的线程取走。

**实践含义**：

1. **单线程消费（推荐）**：只起一个专用线程 `sigwaitinfo`，逻辑简单、顺序确定。

2. **多线程消费（罕见）**：若多个线程都在 `sigwaitinfo`，信号会**分散**到不同线程——每次可能由不同线程处理。这通常不是想要的（除非做简单的负载均衡）。

3. **无法预判哪个线程**：与 handler 的"任一未阻塞线程执行"一样不可预测。所以**不要**依赖多线程消费来做负载均衡——要分发请用 self-pipe 或 eventfd 在消费者内部再分发。

**标准做法回顾**：

```
主线程屏蔽 → 工作线程继承（不消费）→ 唯一专用线程 sigwaitinfo 消费
```

</details>

<details>
<summary><b>问 5：</b><code>sigwaitinfo</code> 能接入 epoll 事件循环吗？如果不能怎么办？</summary>

**不能直接接入**。`sigwaitinfo` 是**阻塞**调用，期间无法同时监听 socket / fd。

**三种替代方案**：

| 方案 | 做法 | 适用 |
|------|------|------|
| **signalfd** | 信号变 fd，与 I/O 一起 `epoll_wait` | **Linux 首选**，最干净 |
| **专用线程 + 通知** | `sigwaitinfo` 线程收到信号后，用 `eventfd_write` / 管道通知主循环 | 需要跨平台时 |
| **`epoll_pwait`** | 在 `epoll_wait` 期间临时放行信号，handler 里设标志 | 保留 handler 的折中方案 |

**方案 2 示例**（sigwaitinfo 线程 + eventfd 桥接）：

```c
/* 信号线程 */
static void *sig_thread(void *arg)
{
    for (;;) {
        int sig = sigwaitinfo(set, &info);
        if (sig > 0) {
            last_sig = sig;                 /* 保存信号编号 */
            uint64_t one = 1;
            write(efd, &one, sizeof one);   /* 通知主循环的 epoll */
        }
    }
}

/* 主循环：efd 已加入 epoll，收到通知后读 last_sig */
```

**HFT 建议**：Linux 上直接用 **signalfd**（[22.11](22.11-fetching-signals-via-a-file-descriptor.md)）——信号与行情数据统一在一个 `epoll_wait` 里，零额外线程、零 handler、零抢占。`sigwaitinfo` 更适合「管理线程」这种可以独立阻塞的场景。

</details>
