## 一、进程睡眠的两种基本形态

进程阻塞在某个系统调用上（等待 I/O、等待锁、等待定时器）时，内核把它从运行队列摘下，设置 `task_struct.__state`，然后调用 `schedule()` 让出 CPU。

```c
/* include/linux/sched.h:85 —— "Used in tsk->__state:" */
#define TASK_RUNNING            0x00000000   /* 可运行（或在运行） */
#define TASK_INTERRUPTIBLE      0x00000001   /* 可中断睡眠：信号能唤醒 */
#define TASK_UNINTERRUPTIBLE    0x00000002   /* 不可中断睡眠：信号【不能】唤醒 */
#define __TASK_STOPPED          0x00000004
#define __TASK_TRACED           0x00000008
/* Used in tsk->exit_state: */
#define EXIT_DEAD               0x00000010
#define EXIT_ZOMBIE             0x00000020
#define TASK_PARKED             0x00000040
#define TASK_DEAD               0x00000080
#define TASK_WAKEKILL           0x00000100   /* 只被【致命】信号唤醒 */
#define TASK_WAKING             0x00000200
#define TASK_NOLOAD             0x00000400
#define TASK_NEW                0x00000800
#define TASK_RTLOCK_WAIT        0x00001000
#define TASK_FREEZABLE          0x00002000   /* 可被 freezer（休眠/迁移）打断 */
#define TASK_FROZEN             0x00008000
```

**组合宏**（`:115-123`）：

```c
/* Convenience macros for the sake of set_current_state: */
#define TASK_KILLABLE           (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)
#define TASK_STOPPED            (TASK_WAKEKILL | __TASK_STOPPED)
#define TASK_TRACED             __TASK_TRACED

#define TASK_IDLE               (TASK_UNINTERRUPTIBLE | TASK_NOLOAD)

/* Convenience macros for the sake of wake_up(): */
#define TASK_NORMAL             (TASK_INTERRUPTIBLE | TASK_UNINTERRUPTIBLE)
```

### 状态对照表（含 `ps` 显示字符）

| 内核状态 | `ps` 字符 | 信号能唤醒？ | 典型场景 |
|----------|-----------|--------------|----------|
| `TASK_RUNNING` | `R` | 不适用（本来就在跑） | 正在 CPU 上或就绪队列里 |
| `TASK_INTERRUPTIBLE` | `S` | ✅ **任何**未决信号 | `read()` 等终端/管道/网络、`sleep()`、`pause()`、`epoll_wait()`、`futex` 等锁 |
| `TASK_UNINTERRUPTIBLE` | `D` | ❌ **都不能**（包括 `SIGKILL`） | 裸块设备 I/O、`NFS` 无响应、部分 `mmap` 缺页、`vfork` 的父等待 |
| `TASK_KILLABLE` | `D`（`ps` 不区分） | ⚠️ **仅致命信号**（`SIGKILL`） | `wait_for_completion_killable()`、NFS 的部分路径 |
| `TASK_STOPPED` | `T` | `SIGCONT` 恢复；`SIGKILL` 直接杀 | `SIGSTOP` / `Ctrl-Z` / `ptrace` |
| `TASK_TRACED` | `t` | 由 tracer 控制 | 被 gdb 断点停住 |
| `EXIT_ZOMBIE` | `Z` | 不适用（已死） | 父进程尚未 `wait()` |
| `EXIT_DEAD` | `X` | 不适用 | 最终回收中 |

> **记忆口诀**：`S` = Sleep（可中断），`D` = **D**eadlock-prone / Disk sleep（不可中断，通常卡在磁盘或网络文件系统上）。

## 二、决定"该不该被唤醒"的那一处代码

整个机制浓缩成一个函数（`include/linux/sched/signal.h:414`）：

```c
static inline int signal_pending_state(unsigned int state, struct task_struct *p)
{
        if (!(state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))
                return 0;                                    /* ① */
        if (!signal_pending(p))
                return 0;                                    /* ② */

        return (state & TASK_INTERRUPTIBLE) || __fatal_signal_pending(p);   /* ③ */
}
```

三行，三个语义：

| 分支 | 逻辑 | 含义 |
|------|------|------|
| ① | `state` 既没有 `TASK_INTERRUPTIBLE` 也没有 `TASK_WAKEKILL` | **永不因信号唤醒**——纯 `TASK_UNINTERRUPTIBLE` 走这里 |
| ② | 没有未决信号 | 不唤醒（正常睡眠中） |
| ③ | 有 `TASK_INTERRUPTIBLE` 位 → 唤醒；否则只有致命信号才唤醒 | `TASK_INTERRUPTIBLE` 对**任何**信号响应；`TASK_KILLABLE` 只对致命信号响应 |

配套的"致命"判定（`:404`）：

```c
static inline int __fatal_signal_pending(struct task_struct *p)
{
        return unlikely(sigismember(&p->pending.signal, SIGKILL));
}

static inline int fatal_signal_pending(struct task_struct *p)
{
        return task_sigpending(p) && __fatal_signal_pending(p);
}
```

> **注意**：内核语境里的"致命信号"**只有 `SIGKILL` 一个**。不是 `SIGTERM`，不是 `SIGABRT`——它们都可以被捕获，所以不算致命。

而"有未决信号"的判定（`:392`）：

```c
static inline int signal_pending(struct task_struct *p)
{
        /*
         * TIF_NOTIFY_SIGNAL isn't really a signal, but it requires the same
         * behavior in terms of ensuring that we break out of wait loops
         * so that notify signal callbacks can be processed.
         */
        if (unlikely(test_tsk_thread_flag(p, TIF_NOTIFY_SIGNAL)))
                return 1;
        return task_sigpending(p);
}
```

```
                    signal_pending_state(state, p)
                              │
             ┌────────────────┴────────────────┐
             │  state & (INTERRUPTIBLE|WAKEKILL) │
             └────────────────┬────────────────┘
                        no ───┴─── yes
                         │              │
                    return 0        signal_pending(p) ?
                   (永不唤醒)              │
                                    no ───┴─── yes
                                     │              │
                                return 0     state & INTERRUPTIBLE ?
                                (继续睡)            │
                                            yes ────┴──── no (只 WAKEKILL)
                                             │              │
                                          return 1    __fatal_signal_pending()?
                                          (唤醒)        yes → 唤醒 / no → 继续睡
```

## 三、发送端：唤醒是怎么发生的

```c
/* kernel/signal.c:769 */
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
        lockdep_assert_held(&t->sighand->siglock);

        set_tsk_thread_flag(t, TIF_SIGPENDING);          /* 打上"有信号待办"标记 */

        /*
         * TASK_WAKEKILL also means wake it up in the stopped/traced/killable
         * case. We don't check t->state here because there is a race with it
         * executing another processor and just now entering stopped state.
         * By using wake_up_state, we ensure the process will wake up and
         * handle its death signal.
         */
        if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
                kick_process(t);
}
```

包装（`include/linux/sched/signal.h:450`）：

```c
static inline void signal_wake_up(struct task_struct *t, bool fatal)
{
        unsigned int state = 0;
        if (fatal && !(t->jobctl & JOBCTL_PTRACE_FROZEN)) {
                t->jobctl &= ~(JOBCTL_STOPPED | JOBCTL_TRACED);
                state = TASK_WAKEKILL | __TASK_TRACED;
        }
        signal_wake_up_state(t, state);
}
```

三个要点：

1. **无论进程睡眠状态如何，`TIF_SIGPENDING` 标记总是被打上。** 也就是说——**信号一定会被"记住"**。D 状态的进程不是"没收到信号"，而是"收到了但暂时不处理"。等它从 D 状态出来、即将返回用户态时，`get_signal()` 就会处理它（包括 `SIGKILL`）。

2. **`state | TASK_INTERRUPTIBLE`** —— 发送端在 `wake_up_state()` 里额外或上 `TASK_INTERRUPTIBLE`。结合 `wake_up_state` 的语义（`if (state & p->__state)` 匹配才唤醒），这保证了：**只要目标进程处于 `TASK_INTERRUPTIBLE`（或在 `state` 里指定的状态），就一定被唤醒**。纯 `TASK_UNINTERRUPTIBLE` 的进程因为 `__state` 里没有对应位，唤醒失败 → 走到 `kick_process(t)`。

3. **`kick_process(t)`** —— 向目标进程所在 CPU 发一个**处理器间中断（IPI）**，强制它进入内核态。这样如果目标进程正在**另一个 CPU 上跑用户态代码**，它会立刻陷入内核，从而在返回路径上看到 `TIF_SIGPENDING`。

> **重要澄清**：D 状态进程"杀不死"的准确说法是——**不是信号没送达，而是进程醒不来**。信号早就挂在 `pending` 上了；一旦底层的 I/O 完成（或超时、或拔网线），进程会立刻处理 `SIGKILL` 并死亡。所以 `kill -9` 对 D 状态进程**不是无效，是延迟生效**。

## 四、`TASK_KILLABLE`：给 D 状态开一个"紧急出口"

问题：早期内核里很多长耗时内核路径用 `TASK_UNINTERRUPTIBLE`，导致 NFS 服务器挂掉时，一堆进程卡在 D 状态，**连管理员都无法清理**，只能重启。

解决（Linux 2.6.25 引入）：`TASK_KILLABLE = TASK_WAKEKILL | TASK_UNINTERRUPTIBLE`。

| | `TASK_UNINTERRUPTIBLE` | `TASK_KILLABLE` |
|--|------------------------|-----------------|
| 普通信号（`SIGTERM`/`SIGUSR1`） | ❌ 不唤醒 | ❌ 不唤醒（**不引入 EINTR 复杂度**） |
| `SIGKILL` | ❌ 不唤醒 | ✅ **唤醒并终止** |
| 内核代码复杂度 | 低（不用处理提前返回） | 中（需要检查 `fatal_signal_pending()` 并回滚） |

对应的等待原语：

| 原语 | 行为 |
|------|------|
| `wait_for_completion(&c)` | 不可中断 |
| `wait_for_completion_interruptible(&c)` | 可中断，被信号打断返回 `-ERESTARTSYS` |
| `wait_for_completion_killable(&c)` | 只被 `SIGKILL` 打断，返回 `-ERESTARTSYS` |
| `wait_for_completion_timeout(&c, j)` | 带超时 |
| `mutex_lock(&m)` | 不可中断 |
| `mutex_lock_interruptible(&m)` | 可中断 |
| `mutex_lock_killable(&m)` | 只被 `SIGKILL` 打断 |

**为什么要有"只响应 SIGKILL"这个折中？**

因为"可中断"是有代价的：内核代码必须在每个等待点检查信号、把已分配资源回滚、返回 `-ERESTARTSYS`。对于某些路径（比如正在写文件系统的元数据、正在做 DMA），半途退出会导致状态不一致——**作者们不敢让它可中断**，但又不能让它永远卡死。于是 `TASK_KILLABLE` 成了唯一合理的选择：**不响应普通信号（保持代码简单），但给管理员留一把"紧急钥匙"**。

## 五、从用户态看：两种睡眠对系统调用的影响

```
可中断睡眠（TASK_INTERRUPTIBLE）
    read() 等数据  ──信号到达──→  内核返回 -EINTR / -ERESTARTSYS
                                    │
                                    ├─ 装了 handler 且未加 SA_RESTART → read() 返回 -1, errno=EINTR
                                    └─ 加了 SA_RESTART → 内核自动重启 syscall（对调用者透明）

不可中断睡眠（TASK_UNINTERRUPTIBLE）
    read() 等磁盘  ──信号到达──→  什么都不发生，继续等
                                  等 I/O 完成后才返回正常结果
```

用户态能观察到的事实：

| 现象 | 说明 |
|------|------|
| 对 `read(tty)` 发信号，`read` 返回 `EINTR` | 终端读是 `TASK_INTERRUPTIBLE` |
| 对 `read(磁盘文件)` 发信号，`read` **不**返回 `EINTR` | 页缓存命中/磁盘读走的是 `TASK_UNINTERRUPTIBLE`（少数情况下 `TASK_KILLABLE`） |
| `kill -9` 一个 D 状态进程，`ps` 仍显示 `D` | 信号已挂起，但进程醒不来 |
| `kill -9` 后拔掉网线/NFS 恢复，进程立刻消失 | 阻塞解除，`get_signal()` 处理挂起的 `SIGKILL` |

**诊断 D 状态进程**（运维必备）：

```bash
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'    # 看 D 状态 + 卡在哪个内核函数
cat /proc/PID/stack                                # 内核栈（需 root + CONFIG_STACKTRACE）
cat /proc/PID/wchan                                # 等待点
cat /proc/PID/syscall                              # 卡在哪个系统调用
dmesg | tail -50                                   # 常有 "hung task" / I/O error 线索
journalctl -k | grep -i 'hung\|blocked\|nfs'
```

内核还有专门的 **hung task detector**：`/proc/sys/kernel/hung_task_timeout_secs`（默认 120 秒），超时后打印 `INFO: task xxx blocked for more than N seconds.` 并带栈回溯。这是排查 D 状态的第一手材料。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **D 状态是嵌入式现场最头疼的故障形态**——SD 卡/eMMC 坏块、NFS 挂载点断网、驱动里错误的 `TASK_UNINTERRUPTIBLE` 等待，都会让进程永久卡死且**连 watchdog 的 `SIGKILL` 都杀不掉**，只能硬件复位。对策：驱动里优先用 `*_killable` / `*_timeout` 变体；关键服务用**硬件 watchdog**（不是软件 `SIGKILL`）；对网络文件系统用 `soft` + `timeo` 挂载选项，避免硬挂载（hard mount）无限等待。② `TASK_FREEZABLE`（`0x2000`）是休眠/容器迁移路径上的可冻结状态，做低功耗产品时会遇到 |
| HFT | ① **D 状态 = 延迟不可控的最坏情况**。交易进程一旦进入不可中断睡眠（比如 `mlock` 大量页时触发的缺页、`read()` 打到慢速设备、NUMA 迁移），调度器完全无法预测何时返回——**这是 HFT 必须消除的延迟源**。对策：所有内存盘前 `mlockall(MCL_CURRENT\|MCL_FUTURE)`；关键路径**零磁盘 I/O、零网络文件系统**；用 `perf sched` / `offcputime`（BPF）统计 off-CPU 时间的分布，找出 D 状态尖刺。② **`TASK_KILLABLE` 给风控留了最后一道闸门**：即使策略进程卡在内核路径上，风控系统仍能 `kill -9` 掉它（只要该路径用了 killable 变体）——所以选型时要**优先选择用 `*_killable` 的内核子系统**（如 NFS 的 `intr`/`soft` 模式），避免"想止损却杀不掉进程"的最坏局面 |

## 代码示例

### 示例 1：观察可中断睡眠被信号打断

```c
/* sleep_demo.c —— 对比可中断/不可中断睡眠对信号的响应
 * 编译: gcc -O0 -g -o sleep_demo sleep_demo.c
 * 运行: ./sleep_demo ；另开终端 kill -USR1 <pid> / kill -9 <pid> */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <stdlib.h>

static volatile sig_atomic_t got = 0;
static void h(int sig) { (void)sig; got = 1; }

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = h;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                    /* 故意不加 SA_RESTART，好观察 EINTR */
    sigaction(SIGUSR1, &sa, NULL);

    printf("pid=%ld\n", (long)getpid());
    printf("① 从终端读（TASK_INTERRUPTIBLE）——请 kill -USR1 %ld\n", (long)getpid());
    fflush(stdout);

    char buf[64];
    ssize_t n = read(STDIN_FILENO, buf, sizeof(buf));   /* 阻塞在 tty */
    if (n < 0 && errno == EINTR)
        printf("   → read 返回 EINTR（被信号打断），got=%d\n", got);
    else
        printf("   → read 返回 %zd\n", n);

    printf("② 无限 pause()（TASK_INTERRUPTIBLE）——请 kill -USR1 %ld\n", (long)getpid());
    fflush(stdout);
    got = 0;
    pause();                            /* 永远返回 -1/EINTR */
    printf("   → pause 返回，got=%d（信号跑完 handler 才返回）\n", got);

    printf("③ 现在试试 kill -9：pause() 期间进程会立即消失\n");
    fflush(stdout);
    for (;;) pause();

    return 0;
}
```

### 示例 2：制造并观察 D 状态（需要 NFS，或用伪设备演示思路）

```c
/* dstate_demo.c —— 演示"信号挂起但进程醒不来"的语义
 * 真实 D 状态需要 NFS 或慢块设备；这里用 SIGSTOP + 信号挂起来模拟"收到但不处理"
 * 编译: gcc -O0 -g -o dstate_demo dstate_demo.c */
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>

int main(void)
{
    printf("pid=%ld\n", (long)getpid());
    printf("实验：\n"
           "  1) 另开终端执行: kill -STOP %ld     → ps 显示 T（停止）\n"
           "  2) 再执行:       kill -9    %ld     → ps 仍显示 T？不，会立即死\n"
           "  3) 对比: 在没有可复现 D 状态的环境里，用 SIGSTOP 体会\n"
           "     '信号已挂起，但要等状态解除才处理' 这一语义\n\n",
           (long)getpid(), (long)getpid());
    fflush(stdout);

    /* 阻塞 SIGTERM 但不阻塞 SIGKILL（SIGKILL 根本无法阻塞），
     * 然后停住自己 —— 期间发来的 SIGTERM 会一直挂起 */
    sigset_t blk;
    sigemptyset(&blk);
    sigaddset(&blk, SIGTERM);
    sigprocmask(SIG_BLOCK, &blk, NULL);
    printf("已阻塞 SIGTERM，进程进入 pause()（可中断睡眠）\n");
    printf("现在 kill -TERM %ld → 进程【不会】动（信号只是挂起）\n", (long)getpid());
    printf("再   kill -CONT %ld 或任意其他信号 → pause 返回\n", (long)getpid());
    fflush(stdout);

    pause();

    sigset_t pend;
    sigpending(&pend);
    printf("pause 返回。SIGTERM 仍挂起? %s\n",
           sigismember(&pend, SIGTERM) ? "是（因为还阻塞着）" : "否");

    printf("解除 SIGTERM 阻塞 → 默认动作是终止，进程即将死亡\n");
    fflush(stdout);
    sigprocmask(SIG_UNBLOCK, &blk, NULL);   /* → SIGTERM 立刻递送 → 进程终止 */

    printf("NOTREACHED\n");
    return 0;
}
```

### 示例 3：内核侧 `TASK_KILLABLE` 的写法（理解原理，不要求能跑）

```c
/* 内核模块/驱动里的三种等待写法对比（示意，需内核环境） */

/* A. 不可中断 —— 简单，但 SIGKILL 也杀不掉 */
wait_for_completion(&dev->io_done);

/* B. 可中断 —— 任何信号都能打断，但要处理提前返回 */
int ret = wait_for_completion_interruptible(&dev->io_done);
if (ret == -ERESTARTSYS)
        return -ERESTARTSYS;            /* 上层会转成 EINTR 给用户态 */

/* C. 可杀 —— 折中：只对 SIGKILL 响应，代码复杂度介于两者之间 */
int ret = wait_for_completion_killable(&dev->io_done);
if (ret == -ERESTARTSYS)
        return -ERESTARTSYS;

/* 更推荐：加超时，从根本上避免无限等待 */
unsigned long j = msecs_to_jiffies(5000);
if (!wait_for_completion_timeout(&dev->io_done, j)) {
        dev_err(dev, "I/O timeout after 5s\n");
        return -ETIMEDOUT;
}
```

<summary><b>问 1：</b>为什么 <code>kill -9</code> 杀不掉 D 状态的进程？信号到底有没有送达？</summary>

**信号送达了，只是进程醒不来。**

发送端 `signal_wake_up_state()`（`kernel/signal.c:769`）无条件打上标记：

```c
set_tsk_thread_flag(t, TIF_SIGPENDING);          /* ← 无论睡眠状态，标记一定打上 */

if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
        kick_process(t);
```

`TIF_SIGPENDING` 打上后，信号已经在 `t->pending` 里了。**失败的是 `wake_up_state()`**——它的语义是"仅当 `(state & p->__state) != 0` 时才把进程设为 `TASK_RUNNING`"。D 状态进程的 `__state == TASK_UNINTERRUPTIBLE (0x02)`，而传入的 state 是 `0 | TASK_INTERRUPTIBLE (0x01)`，两者**没有交集** → 唤醒失败 → 落到 `kick_process(t)`（发 IPI 让它陷入内核，但它陷入后还是要继续等 I/O）。

真正的判定在 `signal_pending_state()`（`:414`）：

```c
if (!(state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))
        return 0;                       /* 纯 D 状态 → 直接返回 0，永不唤醒 */
```

**所以准确的表述是**：

| 说法 | 对错 |
|------|------|
| "D 状态进程收不到 `SIGKILL`" | ❌ 收到了，挂在 pending 里 |
| "`SIGKILL` 对 D 状态无效" | ❌ 有效，只是**延迟生效** |
| "D 状态进程醒不过来" | ✅ 正确——它在等一个**内核认为不能放弃**的事件 |

**什么时候会死**：等底层 I/O 完成（或出错返回）→ 进程从 D 状态出来 → 准备返回用户态 → `get_signal()` 看到 `TIF_SIGPENDING` → 取出 `SIGKILL` → 默认动作 → 立即终止。

**运维现实**：如果 NFS 服务器永久不恢复（`hard` 挂载且无 `intr`），进程可能**永远**不醒。这就是为什么运维手册会说"D 状态进程只能重启机器"——不是内核的错，是 I/O 永远不返回。

**排查命令**：

```bash
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'   # 谁在 D 状态、卡在哪
cat /proc/PID/syscall                             # 卡在哪个 syscall
cat /proc/PID/stack                               # 内核栈（需 root）
dmesg | grep -i 'hung\|blocked'                   # hung task detector 输出
```

<details>
<summary><b>问 2：</b><code>TASK_KILLABLE</code> 解决了什么问题？为什么不干脆全部改成"可中断"？</summary>

**解决的核心问题**：D 状态进程连管理员都无法清理。

历史背景：Linux 2.6.25 之前，很多内核等待路径用 `TASK_UNINTERRUPTIBLE`。NFS 服务器宕机时，访问该挂载点的进程全部进入 D 状态，**系统管理员对它们完全无能为力**——`kill -9` 无效，只能重启机器。这对服务器是不可接受的。

`TASK_KILLABLE = TASK_WAKEKILL | TASK_UNINTERRUPTIBLE`（`sched.h:116`）提供的折中：

| | `TASK_UNINTERRUPTIBLE` | `TASK_KILLABLE` | `TASK_INTERRUPTIBLE` |
|--|---|---|---|
| `SIGTERM`/`SIGUSR1` 等普通信号 | ❌ | ❌ | ✅ |
| `SIGKILL` | ❌ | ✅ **唤醒并终止** | ✅ |
| 内核代码要处理提前返回 | 不需要 | 只在致命信号时回滚 | **必须全面处理** |

**为什么不全部改成可中断？** 因为"可中断"的代价很高：

1. **返回值处理负担**：每个等待点都要检查返回值，返回 `-ERESTARTSYS`，上层再转成 `-EINTR` 传给用户态。漏一处就是 bug。

2. **状态一致性风险**：这是主要障碍。想象一个正在修改文件系统元数据的内核路径——它已经分配了块、修改了部分 inode，此时被 `SIGTERM` 打断退出，文件系统就**处于不一致状态**。要正确支持可中断，作者必须写出完整的回滚逻辑，这对很多老子系统来说是巨大的工程量和高风险改动。

3. **语义正确性**：有些等待本质上是"不可放弃"的——比如正在做 DMA，强行放弃会导致设备状态混乱。

`TASK_KILLABLE` 的精妙之处在于：

```c
return (state & TASK_INTERRUPTIBLE) || __fatal_signal_pending(p);
```

- 没有 `TASK_INTERRUPTIBLE` 位 → 普通信号**不会**导致提前返回 → 作者不必写复杂的回滚
- 但 `__fatal_signal_pending()` 为真时仍返回 1 → 进程被唤醒并终止

而"终止"这个结果对内核是**安全的**——进程要死了，无论它处于什么中间状态，都会在 `do_exit()` 里被清理（释放已分配资源、解锁、归还引用计数）。换句话说：**"让进程死掉"比"让进程半途返回"容易实现得多**。

**用户态的对应 API**：

```c
wait_for_completion_killable()      /* vs wait_for_completion_interruptible() */
mutex_lock_killable()               /* vs mutex_lock_interruptible() */
down_killable()                     /* 信号量 */
```

选择原则：**能用 killable 就不要用 uninterruptible**——至少给管理员留一把钥匙。

</details>

<details>
<summary><b>问 3：</b><code>signal_pending()</code> 和 <code>fatal_signal_pending()</code> 有什么区别？内核为什么还要区分 <code>TIF_NOTIFY_SIGNAL</code>？</summary>

三个函数（`include/linux/sched/signal.h:392-422`）：

```c
static inline int task_sigpending(struct task_struct *p)
{
        return unlikely(test_tsk_thread_flag(p, TIF_SIGPENDING));
}

static inline int signal_pending(struct task_struct *p)
{
        if (unlikely(test_tsk_thread_flag(p, TIF_NOTIFY_SIGNAL)))
                return 1;
        return task_sigpending(p);
}

static inline int __fatal_signal_pending(struct task_struct *p)
{
        return unlikely(sigismember(&p->pending.signal, SIGKILL));
}

static inline int fatal_signal_pending(struct task_struct *p)
{
        return task_sigpending(p) && __fatal_signal_pending(p);
}
```

| 函数 | 含义 | 用途 |
|------|------|------|
| `task_sigpending()` | 纯粹的 `TIF_SIGPENDING` 标志 | 内部用 |
| `signal_pending()` | `TIF_NOTIFY_SIGNAL` **或** `TIF_SIGPENDING` | 等待循环判断"该不该退出" |
| `__fatal_signal_pending()` | `pending` 里有没有 `SIGKILL` | 只看信号集，不看标志 |
| `fatal_signal_pending()` | 有 `TIF_SIGPENDING` **且** 有 `SIGKILL` | `TASK_KILLABLE` 路径判定 |

**`signal_pending()` vs `fatal_signal_pending()`**：

```c
/* signal_pending_state():414 */
return (state & TASK_INTERRUPTIBLE) || __fatal_signal_pending(p);
/*      可中断 → 任何信号都醒                    否则 → 只要 SIGKILL */
```

注意这里用的是 `__fatal_signal_pending()`（不带 `TIF_SIGPENDING` 检查），因为外层 `signal_pending(p)` 已经保证了有信号待办。

**为什么要 `TIF_NOTIFY_SIGNAL`？**

```c
/*
 * TIF_NOTIFY_SIGNAL isn't really a signal, but it requires the same
 * behavior in terms of ensuring that we break out of wait loops
 * so that notify signal callbacks can be processed.
 */
```

它**不是真信号**，而是内核用来请求"请返回用户态一趟，跑一下 task_work 回调"的机制。它的存在有两个动机：

1. **性能**：`TIF_SIGPENDING` 曾经被大量非信号场景滥用（task_work、perf、keyring 等都想让用户态陷入内核一趟），导致**每次从系统调用返回都要走一遍完整的信号处理路径**——即使根本没有信号。把这类"伪信号"分离到 `TIF_NOTIFY_SIGNAL` 后，纯 task_work 场景可以走轻量路径。

2. **语义清晰**：`task_sigpending()` 保持"真的有信号"的纯净语义，避免各处代码误判。

**实践含义**：如果你在写内核代码或读内核代码，判断"要不要退出等待循环"应该用 `signal_pending()`（覆盖两种情况）；判断"是不是真的有信号要递送"才用 `task_sigpending()` 或更具体的检查。

</details>

<details>
<summary><b>问 4：</b>用户态怎么判断一个 sleep 是"可中断"还是"不可中断"？有什么实际影响？</summary>

**没有直接的 API 查询**——用户态只能**观察行为**或**查内核状态**。

**方法 1：看 `ps` 的 STAT 列**

```bash
ps -eo pid,stat,wchan:30,comm
#  PID STAT WCHAN                          COMMAND
# 1234 S    pipe_read                      reader     ← 可中断
# 1235 D    __wait_on_buffer               writer     ← 不可中断
```

**方法 2：查看 `/proc/PID` 的辅助信息**

```bash
cat /proc/PID/stat      # 第 3 字段是状态字符（S/D/R/T/Z）
cat /proc/PID/wchan     # 等待点（内核函数名）
cat /proc/PID/syscall   # 卡在哪个系统调用 + 参数
cat /proc/PID/stack     # 内核栈（需 root + CONFIG_STACKTRACE）
```

**方法 3：行为测试（最可靠）**

发一个信号，看系统调用是否返回 `EINTR`：

```c
/* 伪代码 */
if (read(fd, buf, n) < 0 && errno == EINTR)
        printf("这次 read 是可中断的\n");
```

**实际影响**：

| 场景 | 可中断（S） | 不可中断（D） |
|------|-------------|---------------|
| `read()` 被信号打断 | 返回 `-1 / EINTR` | 不返回，继续等 |
| 代码要不要写 `EINTR` 重试循环 | **必须写** | 不需要（但也拿不到） |
| `kill -9` 能否终止 | ✅ 立即 | ❌ 延迟到 I/O 完成 |
| `ptrace`/gdb 能否附加 | ✅ | ⚠️ 能附加，但不能让它从等待中返回 |
| 超时机制 | 可用 `alarm()`/`setitimer()` 打断 | 必须用 syscall 自身的超时（`select`/`epoll_wait` 的 timeout、`SO_RCVTIMEO`） |

**实际影响最典型的一条**：很多网络程序对 `read()` 写 `EINTR` 重试循环，但对**磁盘文件**的 `read()` 也写同样的循环——这不会错（只是永不触发），但如果开发者**依赖** `EINTR` 来打断磁盘读（比如用 `alarm()` 做超时），就会**静默失效**。

```c
/* ❌ 错误：以为能用 alarm + EINTR 给磁盘读加超时 */
alarm(5);
n = read(disk_fd, buf, sizeof(buf));   /* 多数情况下不会被 EINTR 打断 */
alarm(0);
/* → 磁盘卡住时这段代码会永久阻塞 */

/* ✅ 正确：用 io_uring / O_NONBLOCK + epoll / io_submit 的超时机制 */
```

**HFT 的具体后果**：如果策略进程的热路径上出现任何 D 状态（哪怕是 1 毫秒的缺页），这段时间**完全不可控**——调度器无法抢占、信号无法唤醒、只能等硬件/存储返回。这就是 HFT 必须 `mlockall()` + 避免热路径 I/O 的根本原因。

</details>

<details>
<summary><b>问 5：</b>信号到达时进程正在另一个 CPU 上跑用户态代码，内核怎么让它尽快处理？</summary>

靠 `kick_process()`（`kernel/signal.c:782-783`）：

```c
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
        set_tsk_thread_flag(t, TIF_SIGPENDING);

        if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
                kick_process(t);          /* ← 唤醒失败时的兜底 */
}
```

**两种情况**：

**情况 A：目标进程在睡眠**（在运行队列外）

`wake_up_state()` 成功把它放回运行队列 → 返回非 0 → 不调用 `kick_process()`。进程下次被调度时，从 `schedule()` 返回，检查 `signal_pending_state()` 为真 → 退出等待循环 → 返回用户态前 `get_signal()` 处理信号。

**情况 B：目标进程正在另一个 CPU 上执行用户态代码**

此时它不在等待循环里，`wake_up_state()` 无法"唤醒"（它本来就是 `TASK_RUNNING` 或即将是），返回 0 → 调用 `kick_process(t)`：

```c
/* kernel/sched/core.c */
void kick_process(struct task_struct *p)
{
        int cpu;
        preempt_disable();
        cpu = task_cpu(p);
        if ((cpu != smp_processor_id()) && task_curr(p))
                smp_send_reschedule(cpu);      /* ← 发送 IPI：reschedule 请求 */
        preempt_enable();
}
```

`smp_send_reschedule()` 向目标 CPU 发一个**处理器间中断（IPI）**。目标 CPU 收到后：

1. 强制从用户态陷入内核态（走中断/异常处理入口）
2. 在中断返回路径上，检查 `TIF_SIGPENDING` / `TIF_NEED_RESCHED`
3. 调用 `schedule()` 或直接走 `exit_to_user_mode_loop()` → `handle_signal()`
4. 信号在**返回用户态之前**被处理

```
CPU 0                                     CPU 1
──────                                    ──────
kill(pid, SIGUSR1)                        target 正在跑用户态代码
  │                                              │
  ├─ set_tsk_thread_flag(TIF_SIGPENDING)         │
  ├─ wake_up_state() → 失败（已在运行）            │
  └─ kick_process()                              │
       └─ smp_send_reschedule(cpu1) ────────────>│ IPI 到达
                                                 ▼
                                          陷入内核态
                                                 ▼
                                          检查 TIF_SIGPENDING → 为真
                                                 ▼
                                          exit_to_user_mode_loop()
                                                 ▼
                                          handle_signal() → 跑 handler
                                                 ▼
                                          sigreturn → 回到用户态
```

**这解释了一个重要事实**：在多核系统上，给一个**正在别的 CPU 上忙跑**的进程发信号，延迟大约是**一次 IPI 的往返时间**（亚微秒级）。这比"等它自己陷入内核"快得多——如果进程在跑一个纯计算循环（`while (1);`），没有 IPI 就**永远**不会陷入内核，信号就**永远**不会递送。

**顺带回答一个经典面试题**：

> Q: `while (1);` 的进程能收到信号吗？
> A: **能**——只要发信号的 CPU 通过 `kick_process()` 发了 IPI。但如果进程在跑**纯用户态**循环且**没有 IPI**（比如信号是它自己 `raise()` 的），那就要等它自己陷入内核。实际上 `raise()` → `kill()` 路径里也会 `kick_process(current)`，即使目标就是自己（代码不特判同 CPU），所以仍能立即递送。

**HFT 视角**：IPI 是**跨核中断**，会给目标 CPU 带来一次不可预测的中断开销（通常是 100ns ~ 1µs 量级，取决于硬件和微码）。在多核绑核的交易系统里，**频繁给热路径线程发信号 = 频繁注入 IPI = 抖动源**。这再次印证了 [22.10](22.10-synchronously-waiting-for-a-signal.md) 的结论：**热路径线程应该完全屏蔽信号，信号交给专用线程处理**。

</details>
