## 本节讲什么

1. 信号作为 IPC 能传什么、**不能**传什么——一个 `int` 或一个指针，仅此而已
2. 为什么**跨进程传指针是致命错误**（不只是"不推荐"）
3. 信号 IPC 与真正的 IPC 机制怎么选，以及"信号只做通知、数据另走"的分层设计

## 一、信号能承载的信息量

```
一次 sigqueue(pid, sig, sigval) 携带的信息：

  ┌─────────────────────────────────────────┐
  │ 信号编号 sig          → 事件的"类型"      │  1 个整数
  │ union sigval          → 事件的"载荷"      │  1 个 int 或 1 个 void*
  │ si_pid / si_uid       → 发送方身份        │  内核自动填
  └─────────────────────────────────────────┘
                     总计：4~8 字节
```

```c
/* include/uapi/asm-generic/siginfo.h */
typedef union sigval {
        int     sival_int;
        void   *sival_ptr;
} sigval_t;
```

接收端（`uapi_siginfo.h:157-159`）：

```c
#define si_value        _sifields._rt._sigval   /* union sigval 本身 */
#define si_int          _sifields._rt._sigval.sival_int
#define si_ptr          _sifields._rt._sigval.sival_ptr
```

**这就是全部。** 想传一个字符串？做不到。想传一个结构体？做不到。

## 二、致命陷阱：跨进程传指针

```c
/* 发送方 —— ❌ 灾难性错误 */
typedef struct { int order_id; double price; } Order;
Order o = { .order_id = 12345, .price = 98.76 };

union sigval sv;
sv.sival_ptr = &o;                    /* ← 把【自己地址空间】的指针发出去 */
sigqueue(other_pid, MY_SIG, sv);
```

```c
/* 接收方 —— ❌ 接过来的是一个"别人家的地址" */
static void handler(int sig, siginfo_t *si, void *ctx)
{
    Order *o = (Order *)si->si_ptr;   /* 这个地址在本进程里是……什么？ */
    printf("%d\n", o->order_id);      /* → SIGSEGV，或读到完全无关的垃圾数据 */
}
```

```
进程 A 的虚拟地址空间              进程 B 的虚拟地址空间
┌────────────────────┐            ┌────────────────────┐
│ 0x7ffd1234  [Order]│            │ 0x7ffd1234  ???    │  ← 同一个数值，
│                    │   sv =     │   可能是：          │     完全不同的东西
│                    │ 0x7ffd1234 │   - 未映射 → SIGSEGV│
│                    │ ─────────> │   - 栈上的无关数据   │
│                    │            │   - 别人的关键结构   │
└────────────────────┘            └────────────────────┘
        ▲                                    ▲
        └── 每个进程有【独立】的页表 ────────┘
            同一个虚拟地址值，在两个进程里毫无关系
```

**这个错误的危险之处在于它不一定立刻崩**——如果目标地址恰好映射了，你会**静默读到错误数据**，产生极难排查的逻辑错误。

**唯一例外**：传**共享内存中的偏移量**。

```c
/* ✅ 可以：传共享内存里的【偏移】，不是指针 */
/* shm 是双方都 mmap 了的同一块共享内存 */
union sigval sv;
sv.sival_int = (int)((char *)&o - (char *)shm_base);    /* 偏移量，双方一致 */
sigqueue(other_pid, MY_SIG, sv);

/* 接收方 */
Order *o = (Order *)((char *)my_shm_base + si->si_value.sival_int);   /* ✅ */
```

**注意 ASLR**：即使双方 `mmap` 同一块共享内存，各自的**基址也可能不同**（Linux 默认开启 ASLR）。所以必须传**偏移**而不是绝对地址，或者显式让双方映射在同一地址（`mmap(addr, ...)` 且不开启随机化——不推荐）。

> **顺带说明**：`si_ptr` 在**同一进程内**是完全安全的（比如线程 A 用 `sigqueue` 把堆上对象指针发给线程 B，它们共享地址空间）。危险只在跨进程。

## 三、两种可行的信号 IPC 模式

### 模式 A：把 int 当"事件 ID"用

```c
#define EV_RELOAD_CONFIG   1
#define EV_SWITCH_MODE     2
#define EV_DEGRADE         3
#define EV_SHUTDOWN        4

/* 发送方 */
union sigval sv = { .sival_int = EV_RELOAD_CONFIG };
if (sigqueue(pid, MY_SIG, sv) == -1 && errno == EAGAIN)
    /* 队列满，降级处理 */;

/* 接收方（SA_SIGINFO handler） */
static void on_event(int sig, siginfo_t *si, void *ctx)
{
    switch (si->si_value.sival_int) {
    case EV_RELOAD_CONFIG: g_reload = 1; break;   /* 只置标志！ */
    case EV_SWITCH_MODE:   g_mode   = 1; break;
    ...
    }
    /* handler 里【不做实际工作】，主循环轮询标志后处理 */
}
```

**关键约束**：handler 里**只能置标志**（`volatile sig_atomic_t`），实际工作留给主循环——否则就受 async-signal-safe 约束了。

### 模式 B：信号只做通知，数据走别的通道

这是**唯一适合生产**的模式：

```
发送方                                     接收方
──────                                     ──────
① 把数据写进共享内存 ring buffer  ────────>  ③ 收到信号（只是"有新数据"的通知）
      （或管道 / socket / 消息队列）               ↓
② sigqueue(pid, SIG, {.sival_int = idx})   ④ 从 ring buffer 里按 idx 取数据
      （只传索引，不传数据）                       ↓
                                            ⑤ 处理数据（可 malloc/printf/加锁）
```

优势：

| | 纯信号 IPC | 信号通知 + 数据另走 |
|--|-----------|---------------------|
| 数据量 | 4~8 字节 | 无限制 |
| 队列深度 | `RLIMIT_SIGPENDING`（通常几千） | 由 ring buffer 决定 |
| 丢数据风险 | 队列满 → `EAGAIN` | 由 ring 的溢出策略决定（可控） |
| 数据结构 | 只能 int | 任意结构体 |
| async-signal-safe 约束 | handler 全程受限 | 只有"置标志"那一行受限 |
| 可调试性 | 差（信号无痕） | 好（数据在内存里可查） |

## 四、与其他 IPC 机制对比

| 机制 | 单次数据量 | 内核拷贝次数 | 顺序保证 | 可 epoll？ | 典型延迟 | 适用场景 |
|------|-----------|-------------|----------|-----------|----------|----------|
| **信号（标准）** | 0 | 0 | ❌（还会塌缩） | ❌（需 signalfd） | ~2 µs | 极简通知；**不传数据** |
| **信号（实时 + `sigqueue`）** | 4~8 B | 1 | ✅ 同号 FIFO | ✅ signalfd | ~2 µs | 低频带 ID 的控制信令 |
| **管道 / FIFO** | 64 KB（缓冲） | 2 | ✅ 字节流 | ✅ | ~3 µs | 简单字节流，父子进程 |
| **UNIX domain socket** | 任意 | 2 | ✅ | ✅ | ~5 µs | 通用；可传 fd（`SCM_RIGHTS`） |
| **eventfd** | 8 B（uint64 计数器） | 1 | ✅ 计数 | ✅ | ~1 µs | **纯通知 + 计数**（HFT 首选） |
| **POSIX 消息队列** | 任意（有优先级） | 2 | ✅ 按优先级 | ✅（`mq_notify`） | ~5 µs | 需要优先级的消息 |
| **共享内存 + 自同步** | 任意 | 0 | 需自同步 | ❌（轮询） | **<100 ns** | **高频数据通路**（HFT 首选） |
| **共享内存 + eventfd** | 任意 | 0（数据）+1（通知） | ✅ | ✅ | ~1 µs | **高频 + 低延迟的黄金组合** |

**选型决策树**：

```
要传数据吗？
├─ 否（纯通知）
│   ├─ 需要计数/合并多次事件？ → eventfd   ★
│   └─ 只要一次布尔通知？      → 管道 1 字节 / 实时信号
│
└─ 是
    ├─ 数据量 > 8 字节？
    │   ├─ 高频（>10k/s）？   → 共享内存 ring + eventfd   ★★
    │   ├─ 需要跨主机？       → TCP / UDP
    │   └─ 一般场景           → UNIX socket / 管道 / POSIX MQ
    │
    └─ ≤ 8 字节且低频（<1k/s）
        └─ 实时信号 + sigqueue（注意 EAGAIN）
```

## 五、实时信号 IPC 的六个约束

用 `sigqueue()` + 实时信号做 IPC 前，先确认这些：

| # | 约束 | 说明 |
|---|------|------|
| 1 | **编号必须用宏** | `SIGRTMIN + n`，绝不硬编码（glibc 占用 32/33，`SIGRTMIN`=34） |
| 2 | **接收端必须 `SA_SIGINFO`** | 否则拿不到 `si_value`（用 `sa_handler` 形式只有信号编号） |
| 3 | **队列会满** | `sigqueue()` 返回 `-1 / EAGAIN`；`kill()` 永不 `EAGAIN` 但会丢数据 |
| 4 | **标准信号不排队** | 用标准信号做 IPC 会**静默丢事件**（`legacy_queue():1079`） |
| 5 | **handler 受 async-signal-safe 约束** | 或者改用 `signalfd`/`sigwaitinfo` 解除约束 |
| 6 | **不能传指针** | 见第二节 |

**内核对 `sigqueue` 的安全约束**（`do_rt_sigqueueinfo():4013`）——顺带一提，root 也不能伪造内核来源：

```c
        /* Not even root can pretend to send signals from the kernel.
         * Nor can they impersonate a kill()/tgkill(), which adds source info.
         */
        if ((info->si_code >= 0 || info->si_code == SI_TKILL) &&
            (task_pid_vnr(current) != pid))
                return -EPERM;
```

这意味着 `si_code` 是**可信的**——接收方可以放心地用 `si_code > 0` 判断"是不是真内核故障"，不用担心被同级权限的进程伪造（详见 [22.5](22.5-synchronous-and-asynchronous-signal-gene.md)）。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 信号 IPC 在无 MMU 的 RTOS/裸机上不存在（改用消息队列/事件标志组）。嵌入式 Linux 上，低频控制信令（切模式、改阈值、触发采样）用 `sigqueue` + int 完全够用且省资源；但要处理 `EAGAIN`，且**绝不能跨进程传指针**。数据量大时优先 `/dev/shm` + eventfd 或 UNIX socket |
| HFT | **信号不是数据通路**——它是"低频控制通知"。① 高频数据走共享内存 ring + eventfd（零拷贝、无系统调用、可 epoll）。② 信号递送是**异步中断**，微秒级抖动 + 缓存污染 + 可能 IPI，绝不能出现在热路径。③ 若必须用信号传控制信息，用 `sival_int` 传**枚举 ID**（不是指针、不是魔数），并在接收端用 `switch` 显式处理未知值。④ 关键控制信令（如"停止下单"）**不能容忍 `EAGAIN` 丢失**——要么处理 `EAGAIN` 并降级，要么换用 eventfd（计数器永不丢） |

## 代码示例

### 示例 1：正确的信号 IPC —— 传事件 ID，不传指针

```c
/* sigipc.c —— 父子进程间用实时信号 + sival_int 传事件 ID
 * 编译: gcc -O2 -o sigipc sigipc.c
 * 运行: ./sigipc */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/wait.h>

/* ① 用宏定义自己的实时信号，绝不硬编码 */
#define MY_SIG    (SIGRTMIN + 0)

/* ② 事件 ID 用枚举，不用魔数 */
enum {
    EV_NONE = 0,
    EV_RELOAD_CONFIG = 1,
    EV_SWITCH_MODE   = 2,
    EV_DEGRADE       = 3,
    EV_SHUTDOWN      = 4,
};

static const char *ev_name(int id)
{
    switch (id) {
    case EV_RELOAD_CONFIG: return "RELOAD_CONFIG";
    case EV_SWITCH_MODE:   return "SWITCH_MODE";
    case EV_DEGRADE:       return "DEGRADE";
    case EV_SHUTDOWN:      return "SHUTDOWN";
    default:               return "UNKNOWN";
    }
}

/* 接收方：handler 只置标志，实际工作留给主循环 */
static volatile sig_atomic_t g_event = EV_NONE;
static volatile sig_atomic_t g_from_pid = 0;

static void on_event(int sig, siginfo_t *si, void *ctx)
{
    (void)sig; (void)ctx;
    int saved_errno = errno;          /* 保护 errno */

    /* si_pid / si_uid 由内核填，可信 */
    g_from_pid = si->si_pid;
    g_event    = si->si_value.sival_int;   /* 只取 int，不碰 si_ptr */

    errno = saved_errno;
}

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }

    if (pid == 0) {
        /* ── 子进程：接收方 ── */
        struct sigaction sa = {0};
        sa.sa_sigaction = on_event;
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = SA_SIGINFO | SA_RESTART;   /* ← 必须有 SA_SIGINFO */
        sigaction(MY_SIG, &sa, NULL);

        printf("[child %ld] 等待事件信号 (SIGRTMIN+0 = %d)...\n",
               (long)getpid(), MY_SIG);

        for (;;) {
            pause();                              /* 等信号 */
            if (g_event == EV_NONE) continue;     /* 被别的信号打断 */

            int ev = g_event;
            g_event = EV_NONE;

            /* ↓ 这里已经是普通同步代码：可以 printf / malloc / 加锁 */
            printf("[child] 收到事件 %d (%s), 来自 pid=%d\n",
                   ev, ev_name(ev), (int)g_from_pid);

            if (ev == EV_SHUTDOWN) {
                printf("[child] 收到关机指令，退出\n");
                _exit(0);
            }
        }
    }

    /* ── 父进程：发送方 ── */
    sleep(1);                                     /* 等子进程装好 handler */

    int events[] = { EV_RELOAD_CONFIG, EV_SWITCH_MODE, EV_DEGRADE, EV_SHUTDOWN };
    for (unsigned i = 0; i < sizeof(events)/sizeof(events[0]); i++) {
        union sigval sv;
        sv.sival_int = events[i];                 /* ← 只传 int */

        if (sigqueue(pid, MY_SIG, sv) == -1) {
            if (errno == EAGAIN) {
                fprintf(stderr, "[parent] 队列满，事件 %s 未送达！\n",
                        ev_name(events[i]));
                /* 降级策略：改发不带数据的 kill，或改用不会丢的机制 */
            } else {
                perror("sigqueue");
            }
        } else {
            printf("[parent] 已发送 %s\n", ev_name(events[i]));
        }
        usleep(200000);
    }

    waitpid(pid, NULL, 0);
    printf("[parent] 子进程已退出\n");
    return 0;
}
```

### 示例 2：生产模式 —— 数据走共享内存，信号只做通知

```c
/* shm_notify.c —— 数据放共享内存，信号只传索引
 * 编译: gcc -O2 -o shm_notify shm_notify.c -lrt
 * 运行: ./shm_notify */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/mman.h>
#include <sys/wait.h>

#define MY_SIG    (SIGRTMIN + 1)
#define RING_CAP  64

typedef struct {
    int   order_id;
    char  symbol[16];
    double price;
    int   qty;
} Order;

/* 共享内存里的 ring buffer —— 数据本体放这里 */
typedef struct {
    /* 生产者写、消费者读；单生产者单消费者下可无锁（用原子索引 + 内存屏障） */
    volatile unsigned head;                  /* 生产者写 */
    char   pad1[64];                         /* 避免 false sharing：各自独占 cacheline */
    volatile unsigned tail;                  /* 消费者写 */
    char   pad2[64];
    Order  slots[RING_CAP];
} Ring;

static Ring *g_ring;

static void producer_send(const Order *o)
{
    unsigned h = g_ring->head;
    unsigned next = (h + 1) % RING_CAP;

    /* 确保写入 slot 之前，消费者已经读过（tail 已推进） */
    __atomic_thread_fence(__ATOMIC_ACQUIRE);
    if (next == g_ring->tail) {
        fprintf(stderr, "ring 满，丢弃 order %d\n", o->order_id);
        return;                              /* 或选择阻塞/覆盖最旧 */
    }

    g_ring->slots[h] = *o;                   /* 拷贝进共享内存 */
    __atomic_thread_fence(__ATOMIC_RELEASE); /* 保证数据先于 head 可见 */
    g_ring->head = next;

    /* 信号只传【索引】，不传数据 */
    union sigval sv;
    sv.sival_int = (int)h;
    if (sigqueue(getpid() + 1, MY_SIG, sv) == -1 && errno == EAGAIN)
        fprintf(stderr, "通知队列满（数据已在 ring 里，消费端会轮询到）\n");
}

static volatile sig_atomic_t g_notify = 0;

static void on_notify(int sig, siginfo_t *si, void *ctx)
{
    (void)sig; (void)ctx;
    int saved = errno;
    g_notify = 1;                            /* 只置标志 */
    (void)si;                                /* 索引其实不必用：直接消费到 tail==head */
    errno = saved;
}

int main(void)
{
    /* 创建共享内存（父子共享） */
    g_ring = mmap(NULL, sizeof(Ring), PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (g_ring == MAP_FAILED) { perror("mmap"); return 1; }
    memset(g_ring, 0, sizeof(*g_ring));

    pid_t pid = fork();
    if (pid == 0) {
        /* ── 消费者 ── */
        struct sigaction sa = {0};
        sa.sa_sigaction = on_notify;
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = SA_SIGINFO | SA_RESTART;
        sigaction(MY_SIG, &sa, NULL);

        int consumed = 0;
        while (consumed < 5) {
            /* 先看 ring 里有没有数据（信号只是"叫醒我"，不是"数据在我这"） */
            while (g_ring->tail != g_ring->head) {
                __atomic_thread_fence(__ATOMIC_ACQUIRE);
                Order o = g_ring->slots[g_ring->tail];
                printf("[consumer] order=%d %s %.2f x%d\n",
                       o.order_id, o.symbol, o.price, o.qty);
                __atomic_thread_fence(__ATOMIC_RELEASE);
                g_ring->tail = (g_ring->tail + 1) % RING_CAP;
                consumed++;
            }
            if (consumed >= 5) break;
            g_notify = 0;
            pause();                          /* 没数据就睡，等通知 */
        }
        _exit(0);
    }

    /* ── 生产者 ── */
    sleep(1);
    for (int i = 1; i <= 5; i++) {
        Order o = { .order_id = 1000 + i, .price = 98.50 + i, .qty = 100 * i };
        snprintf(o.symbol, sizeof(o.symbol), "AAPL");
        producer_send(&o);
        usleep(100000);
    }

    waitpid(pid, NULL, 0);
    munmap(g_ring, sizeof(Ring));
    return 0;
}
```

**这个模式的三个关键点**：

1. **数据不在信号里**——信号只携带"有数据了"这一比特信息（连索引都可以不要）
2. **消费端先查 ring 再睡**——即使通知丢了（`EAGAIN`），数据仍在 ring 里，下次会消费到。**这消除了信号队列满导致的丢事件风险**
3. **内存屏障 + 独占 cacheline**——单生产者单消费者下的无锁 ring，`pad1/pad2` 避免 false sharing

<summary><b>问 1：</b>跨进程用 <code>sival_ptr</code> 传结构体指针会怎样？为什么有时候不崩但读到错数据？</summary>

**两种结果，都错。**

**结果 A：`SIGSEGV`**（运气好）

目标地址在本进程**未映射** → 访问触发 #PF → `force_sig_fault(SIGSEGV, SEGV_MAPERR, addr)` → 崩溃。至少你能发现。

**结果 B：静默读到错误数据**（运气坏，**更危险**）

目标地址在本进程**恰好映射了**——可能是：

- 一块无关的堆内存
- 栈上的局部变量
- 某个关键数据结构的内部

于是 `o->order_id` 读出来是一个**随机的、但看起来"合理"**的数字。程序继续跑，用错误数据做决策，**没有任何错误信号**。

```
进程 A                                    进程 B
0x7ffd1234: Order{12345, 98.76}           0x7ffd1234: 某个 unrelated struct
      │                                         │
      └── sv.sival_ptr = 0x7ffd1234 ──────────> │
                                                ▼
                                    Order *o = si->si_ptr;
                                    o->order_id   ← 读到的是 B 自己那个结构体
                                                    的前 4 字节，可能是任何值
```

**为什么同一个地址值在不同进程里含义不同？**

因为每个进程有**独立的页表**。虚拟地址 `0x7ffd1234` 在进程 A 里通过 A 的页表翻译成物理页 X，在进程 B 里通过 B 的页表翻译成物理页 Y——**X 和 Y 毫无关系**。这是虚拟内存最基础的性质。

**唯一可行的"传指针"场景**：

1. **同一进程内的线程间**——线程共享地址空间，`si_ptr` 完全安全
2. **共享内存里的偏移量**——传 `(char*)p - (char*)shm_base`，接收方 `my_shm_base + offset`

```c
/* ✅ 正确：传共享内存偏移 */
sv.sival_int = (int)((char *)&o - (char *)shm_base);

/* 接收方 —— 注意各自的 mmap 基址可能不同（ASLR） */
Order *o = (Order *)((char *)my_shm_base + si->si_value.sival_int);
```

> **ASLR 警告**：即使双方 `mmap` 同一块共享内存，各自的返回地址**默认不同**。所以必须传偏移，或者显式指定同一地址（`mmap(fixed_addr, ...)`）——后者不推荐（与 ASLR 的安全收益冲突）。

**实践结论**：`sival_ptr` 这个字段的存在本身就是个陷阱。**跨进程一律用 `sival_int`，传枚举/索引/偏移量，绝不传裸指针。**

</details>

<details>
<summary><b>问 2：</b>信号相比管道/共享内存做 IPC 有什么根本限制？什么时候该用它？</summary>

**根本限制**——信号的设计定位是"**通知**"，不是"**通道**"：

| 限制 | 具体表现 | 根源 |
|------|----------|------|
| **载荷极小** | 只有 `union sigval`（4~8 字节） | `siginfo_t` 结构固定 |
| **队列浅且会丢** | `RLIMIT_SIGPENDING`（默认通常几千），满了 `sigqueue()` 返回 `EAGAIN` | 内核内存受限 |
| **标准信号塌缩** | 多次同号只递送一次（`legacy_queue():1079`） | 位图结构，无计数 |
| **异步递送** | 打断接收方执行流 → async-signal-safe 约束 | 递送时机在返回用户态前 |
| **抖动** | 一次递送 ~1.5-2.5 µs + 缓存污染 + 可能 IPI | 陷入内核 + 建栈帧 + `sigreturn` |
| **不可调试** | 信号没有"内容"可查，走了就没了 | 无持久化 |
| **同步故障信号捕获不到** | `SIGSEGV` 等走 `force_*`，绕过阻塞 | 设计如此 |

**对比数据量**（一次操作）：

| 机制 | 一次能传 |
|------|----------|
| 信号 | 4~8 字节 |
| eventfd | 8 字节（一个累加计数器） |
| 管道 | 64 KB（内核缓冲） |
| UNIX socket | 任意（`SCM_RIGHTS` 还能传 fd） |
| 共享内存 | **任意（零拷贝）** |

**什么时候该用信号**：

✅ **适合**：

- 低频控制通知：重载配置、切模式、优雅退出（`SIGTERM`/`SIGINT`/`SIGHUP`）
- 进程生命周期事件：`SIGCHLD`（子进程退出）
- 异步 I/O 就绪通知：`SIGIO`（虽然现在都用 epoll）
- 定时器到期（`SIGALRM`、POSIX timer）——但 `timerfd` 更好用
- 崩溃现场捕获（`SIGSEGV`/`SIGBUS`/`SIGFPE`，只有信号能做到）

❌ **不适合**：

- 任何**高频**事件（> 1k/s）
- 任何**超过 8 字节**的数据
- 任何**不能丢**的消息（队列满会 `EAGAIN`）
- 任何**延迟敏感**路径（抖动不可控）
- 传指针（跨进程）

**信号 IPC 的唯一合理形态**：

```
信号 = 门铃；数据 = 包裹

按门铃（信号，1 bit 信息）→ 主人来开门 → 从门口拿包裹（共享内存/管道里的实际数据）
```

即**示例 2 的模式**：数据走共享内存 ring 或管道，信号只负责"叫醒对方"。这样：

- 数据不受 8 字节限制
- 通知丢了也没关系（数据在 ring 里，下次轮询会拿到）
- 接收端可以从容处理（先查 ring，再决定睡不睡）

**HFT 视角**：连"门铃"都最好换成 **eventfd**——它是一个内核计数器，`write()` 累加、`read()` 清零，**永不丢失计数**（信号队列满了会丢），且能直接进 epoll。共享内存 ring + eventfd 是 HFT 进程间通信的标准答案。

</details>

<details>
<summary><b>问 3：</b><code>sigqueue()</code> 返回 EAGAIN 意味着什么？关键控制信令（如"立即停止下单"）怎么保证不丢？</summary>

**`EAGAIN` 的含义**：实时信号队列已满，**这个信号没有被投递**。

```c
if (sigqueue(pid, MY_SIG, sv) == -1 && errno == EAGAIN)
    /* 本次通知丢失 */
```

**两个限制**（详见 [22.8](22.8-realtime-signals.md)）：

| 限制 | 作用域 | 查看 |
|------|--------|------|
| `RLIMIT_SIGPENDING` | **每个用户 UID**（不是每个进程）可排队的信号总数 | `ulimit -i` |
| `rtsig-max` | 系统级实时信号队列上限 | `/proc/sys/kernel/rtsig-max` |

**注意 `kill()` 永不返回 `EAGAIN`**（内核注释 `__send_signal_locked():1115-1123`）：

```c
        /*
         * Real-time signals must be queued if sent by sigqueue, or
         * some other real-time mechanism.  It is implementation
         * defined whether kill() does so.  We attempt to do so, on
         * the principle of least surprise, but since kill is not
         * allowed to fail with EAGAIN when low on memory we just
         * make sure at least one signal gets delivered and don't
         * pass on the info struct.
         */
```

即：`kill()` 宁可**丢掉 `siginfo` 只保留位图标记**，也不返回 `EAGAIN`。所以：

| 调用 | 队列满时 |
|------|----------|
| `kill(pid, rt_sig)` | 不报错，保证至少递送一次，但**丢 `sival` 数据** |
| `sigqueue(pid, rt_sig, sv)` | 返回 `-1 / EAGAIN`，**整个信号丢弃** |

**关键控制信令怎么保证不丢？四个方案：**

**方案 1（推荐）：换机制 —— eventfd**

```c
/* eventfd 是内核计数器，write 累加，永不丢计数 */
int efd = eventfd(0, EFD_CLOEXEC);
uint64_t one = 1;
write(efd, &one, sizeof(one));      /* 累加，不会失败（除非溢出 2^64） */
/* 接收方 epoll_wait(efd) → read() 得到累计次数 */
```

优点：永不丢、可 epoll、能计数（多次事件合并成一次唤醒）、延迟 ~1 µs。

**方案 2：处理 `EAGAIN` 并降级**

```c
int send_urgent(pid_t pid, int sig, int evid)
{
    union sigval sv = { .sival_int = evid };

    for (int retry = 0; retry < 16; retry++) {
        if (sigqueue(pid, sig, sv) == 0)
            return 0;                            /* 成功 */
        if (errno != EAGAIN)
            return -1;                           /* 真错误 */
        usleep(1000);                            /* 队列可能很快腾出空间 */
    }

    /* 降级：改用 kill —— 不保证带数据，但保证通知到达 */
    return kill(pid, sig);
}
```

**方案 3：数据与控制分离（示例 2 的模式）** —— 最稳

```
① 先把"停止下单"这个【状态】写进共享内存（一个 volatile 标志）
② 再发信号/写 eventfd 通知

即使通知丢了，接收方下次检查共享内存时仍能看到标志。
→ 通知变成了"加速唤醒"，而不是"唯一载体"
```

**方案 4：双通道冗余**

```c
/* 关键信令同时走信号和管道/eventfd，接收方去重 */
sigqueue(pid, URGENT_SIG, sv);
write(ctl_pipe[1], &evid, sizeof(evid));
```

**HFT 实践原则**：

> **"停止下单"这类指令绝不能依赖单一的、会丢的通知机制。**
>
> 正确做法是把状态写进共享内存（幂等、`volatile` 标志），通知只负责"尽快醒来看一眼"。这样即使所有通知都丢了，接收方在下一次主循环迭代（微秒级）也会看到状态变化。
>
> 换句话说：**用"轮询共享状态"保底，用"通知"降低延迟**。这是所有低延迟系统的通用模式。

</details>

<details>
<summary><b>问 4：</b>接收端忘了设 SA_SIGINFO 会怎样？</summary>

**能收到信号，但拿不到 `si_value`——所有数据都丢了，而且不报错。**

**原因**：`sa_handler` 和 `sa_sigaction` 是 **union**，同一块内存。内核按 `SA_SIGINFO` 标志决定怎么调用它：

```c
typedef struct sigaction {
        union {
                void     (*sa_handler)(int);
                void     (*sa_sigaction)(int, siginfo_t *, void *);
        } __sigaction_handler;
        sigset_t   sa_mask;
        int        sa_flags;
        void     (*sa_restorer)(void);
};
```

```c
/* 忘了 SA_SIGINFO 的写法 */
struct sigaction sa = {0};
sa.sa_sigaction = on_event;        /* ← 写进了 union，函数指针是三参数的 */
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;          /* ← ❌ 漏了 SA_SIGINFO */
sigaction(MY_SIG, &sa, NULL);
```

内核看到没有 `SA_SIGINFO` → 按 `sa_handler` 的**单参数**签名去调用那个地址：

```c
((void (*)(int))sa.sa_sigaction)(signo);      /* 只传一个参数 */
```

**实际后果**：

| 层面 | 结果 |
|------|------|
| 函数调用 | 能进去（x86-64 上第 2、3 个参数是**未初始化的寄存器值**） |
| `si` 参数 | 是**垃圾**（未初始化的寄存器） |
| `si->si_value` | 读到垃圾内存 → 可能是 `SIGSEGV`，也可能是随机数 |
| 编译器 | **不报错**（函数指针类型通过 union 转换，C 语言不做跨调用检查） |

所以这又是一个"**不一定立刻崩，但一定错**"的坑。

**更危险的反向错误**：

```c
struct sigaction sa = {0};
sa.sa_handler = simple_handler;    /* 一参数函数 */
sa.sa_flags = SA_SIGINFO;          /* ← ❌ 多了不该有的 SA_SIGINFO */
sigaction(MY_SIG, &sa, NULL);
```

内核按**三参数**调用一个只接受一参数的函数 → 在 x86-64 上通常"碰巧能跑"（多余参数在寄存器里被忽略），但**在其他 ABI（如 ARM 的某些调用约定）上可能栈失衡 → 崩溃**。而且这是未定义行为，编译器优化后任何事都可能发生。

**正确写法（二选一，绝不混用）**：

```c
/* A. 简单 handler：用 sa_handler，【不要】SA_SIGINFO */
struct sigaction sa = {0};
sa.sa_handler = simple_handler;         /* void h(int sig) */
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;
sigaction(MY_SIG, &sa, NULL);

/* B. 需要 siginfo：用 sa_sigaction，【必须】SA_SIGINFO */
struct sigaction sa = {0};
sa.sa_sigaction = info_handler;         /* void h(int, siginfo_t *, void *) */
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_RESTART;  /* ← 必须有 */
sigaction(MY_SIG, &sa, NULL);
```

**检查清单**：

- [ ] 用 `sa_handler` → **不要** `SA_SIGINFO`
- [ ] 用 `sa_sigaction` → **必须** `SA_SIGINFO`
- [ ] **绝不**同时给两者赋值（union，后者覆盖前者）
- [ ] 编译开 `-Wall -Wextra`，虽然 C 不检查，但有些场景能给出 union 相关警告
- [ ] 用封装函数统一（如 `install_handler()` / `install_siginfo_handler()`，见 [22.7](22.7-implementation-and-portability-of-signal.md) 示例 2），从源头杜绝

> **顺带**：`signal()` **完全无法**设 `SA_SIGINFO`——这是它必须被 `sigaction()` 取代的六条理由之一（见 [22.7](22.7-implementation-and-portability-of-signal.md)）。

</details>

<details>
<summary><b>问 5：</b><code>si_pid</code> / <code>si_uid</code> 可信吗？恶意进程能伪造"内核来源"的信号吗？</summary>

**可信。这是内核明确设防的一条安全边界。**

**内核代码**（`do_rt_sigqueueinfo():4013`）：

```c
        /* Not even root can pretend to send signals from the kernel.
         * Nor can they impersonate a kill()/tgkill(), which adds source info.
         */
        if ((info->si_code >= 0 || info->si_code == SI_TKILL) &&
            (task_pid_vnr(current) != pid))
                return -EPERM;
```

**规则**：

| 你想设的 `si_code` | 发给别人 | 发给自己 |
|-------------------|----------|----------|
| `>= 0`（如 `SEGV_MAPERR=1`、`SI_KERNEL=0x80`） | ❌ `-EPERM` | ✅ 允许 |
| `SI_TKILL`（-6） | ❌ `-EPERM` | ✅ 允许 |
| `< 0` 且非 `SI_TKILL`（如 `SI_QUEUE=-1`、`SI_USER=0`） | ✅ 允许 | ✅ 允许 |

注释里 "**Not even root**" 这个措辞在内核里非常罕见，说明作者认为这是一条**硬性安全边界**。

**为什么必须禁止？**

如果允许伪造 `si_code > 0`：

```c
/* 恶意进程可以这样做（假设内核不设防） */
siginfo_t info = {0};
info.si_signo = SIGSEGV;
info.si_code  = SEGV_MAPERR;        /* 伪装成"硬件段错误" */
info.si_addr  = (void *)0x1234;
/* → 目标进程的崩溃 handler 会以为自己真崩了 → 写 core / abort / 上报事故 */
```

这就构成了一个**本地拒绝服务（DoS）漏洞**：任何能发信号的进程都能让目标服务"自杀"或产生假的事故告警。

**所以用户态可以放心依赖**：

```c
static void crash_handler(int sig, siginfo_t *si, void *ctx)
{
    if (SI_FROMKERNEL(si)) {
        /* si_code > 0 → 一定是真的内核/硬件故障，不是别人伪造的 */
        log("真崩溃: sig=%d si_code=%d si_addr=%p", sig, si->si_code, si->si_addr);
        capture_backtrace();
        _exit(128 + sig);
    } else {
        /* si_code <= 0 → 别人 kill() 或 sigqueue() 过来的，忽略 */
        log("收到伪造的 %d（si_code=%d），忽略", sig, si->si_code);
        return;                          /* 安全返回 */
    }
}
```

**`si_pid` / `si_uid` 呢？**

对 `kill()` / `sigqueue()` / `SIGCHLD` 等，**内核自动填写**，用户无法伪造：

```c
/* kernel/signal.c 里多处 */
        info->si_pid = task_pid_vnr(current);          /* 发送方的 PID */
        info->si_uid = from_kuid_munged(current_user_ns(), current_uid());
```

配合 `send_signal_locked()` 里的权限检查（发送方必须有相应权限或同 UID），`si_pid`/`si_uid` 是可信的身份来源。

实践用法：

```c
static void on_control(int sig, siginfo_t *si, void *ctx)
{
    /* 只接受来自【父进程】或【同 UID】的控制信号 */
    if (si->si_pid != getppid() && si->si_uid != getuid()) {
        log("拒绝来自 pid=%d uid=%d 的控制信号", si->si_pid, si->si_uid);
        return;
    }
    handle_control(si->si_value.sival_int);
}
```

> **注意**：`si_pid` 在 PID 命名空间中可能被"翻译"（`task_pid_vnr()` 返回的是**调用者可见的** PID）。容器场景下跨 namespace 的 PID 语义要额外小心。
>
> **另外**：`si_pid` 存在 PID 复用风险——发信号的进程可能已经退出，PID 被新进程占用。高安全场景应该用 **`pidfd` + `pidfd_send_signal()`**（见 [Ch20.6](../../chapter-20-signals-fundamentals/notes/20.6-checking-for-the-existence-of-a-process.md)）。

</details>
