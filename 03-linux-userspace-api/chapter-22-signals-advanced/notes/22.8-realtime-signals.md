## 一、实时信号是什么

**实时信号** = 编号在 `SIGRTMIN` ~ `SIGRTMAX` 区间的信号，是 POSIX.1b 为实时应用引入的扩展。

```c
#define MY_SIG  (SIGRTMIN + 0)     /* ✅ 用宏 */
/* #define MY_SIG  34                 ❌ 硬编码，换 libc 就错位 */
```

> **为什么不是 32**：glibc 的 NPTL **内部占用了前两个实时信号**（32 用于 `setxid` 同步，33 用于线程取消），所以用户态可见的 `SIGRTMIN` 是 **34**。详见 [Ch20.2](../../chapter-20-signals-fundamentals/notes/20.2-signal-types-and-default-actions.md)。

### 三类差异

| | **标准信号**（1–31） | **实时信号**（`SIGRTMIN`+） |
|--|---------------------|---------------------------|
| **排队** | ❌ 不排队，阻塞时同号只留一份 | ✅ **排队**，逐个保留 |
| **携带数据** | ❌ 无 | ✅ `sigqueue()` 可带 `int` / `void*` |
| **递送顺序** | ❌ 无保证 | ✅ **小号优先**；同号 **FIFO** |
| **默认动作** | 各异 | 统一 **terminate** |
| **`si_code` 语义** | 各异 | `SI_QUEUE`(-1) 表示 `sigqueue` 发送 |

**递送顺序规则**（POSIX 要求）：

1. 多个不同编号的实时信号都未决时，**编号小的先递送**
2. 同一编号的多个实例，按**发送顺序（FIFO）**递送
3. 实时信号整体优先于标准信号

## 二、`sigqueue()`：发送带数据的信号

```c
#include <signal.h>

union sigval {
    int   sival_int;      /* 整数形态 */
    void *sival_ptr;      /* 指针形态 */
};

int sigqueue(pid_t pid, int sig, const union sigval value);
/* 返回：成功 0，失败 -1 */
```

| 对比 | `kill()` | `sigqueue()` |
|------|----------|--------------|
| 携带数据 | ❌ | ✅ `sigval`（`int` 或指针） |
| 排队保证 | ⚠️ 实时信号尝试排队但不保证 | ✅ **必须排队**（POSIX 要求） |
| 队列满时 | 静默退化为至少一个递送 | 返回 `-1`，`errno = EAGAIN` |
| 接收端 | 普通 handler 即可 | 需 `SA_SIGINFO` 才能读 `si_value` |

### 内核路径

```c
// kernel/signal.c:4032
SYSCALL_DEFINE3(rt_sigqueueinfo, pid_t, pid, int, sig,
		siginfo_t __user *, uinfo)
{
	kernel_siginfo_t info;
	int ret = __copy_siginfo_from_user(sig, &info, uinfo);
	if (unlikely(ret))
		return ret;
	return do_rt_sigqueueinfo(pid, sig, &info);
}

// kernel/signal.c:4013
static int do_rt_sigqueueinfo(pid_t pid, int sig, kernel_siginfo_t *info)
{
	/* Not even root can pretend to send signals from the kernel.
	 * Nor can they impersonate a kill()/tgkill(), which adds source info.
	 */
	if ((info->si_code >= 0 || info->si_code == SI_TKILL) &&
	    (task_pid_vnr(current) != pid))
		return -EPERM;

	/* POSIX.1b doesn't mention process groups.  */
	return kill_proc_info(sig, info, pid);
}
```

**两点值得注意**：

1. **安全约束**：`si_code >= 0` 表示「内核来源」。用户进程不能伪造内核来源的信号——**即便 root 也不行**（注释明确写着 "Not even root can pretend to send signals from the kernel"）。这防止恶意进程伪造内核事件。
2. **不支持进程组**：注释 "POSIX.1b doesn't mention process groups"——`sigqueue()` 只能发给单个进程，没有 `sigqueuepg()` 这样的群发版本。

### 内核排队机制

```c
// kernel/signal.c:1084（__send_signal_locked 内）
	if (legacy_queue(pending, sig))        /* 标准信号且已在 pending → 丢弃 */
		goto ret;
	...
	q = __sigqueue_alloc(sig, t, GFP_ATOMIC, override_rlimit, 0);   /* :1129 */
	if (q) {
		list_add_tail(&q->list, &pending->list);                   /* :1132 */
		...
	}
```

实时信号不满足 `legacy_queue` 的 `sig < SIGRTMIN` 条件，所以每次发送都会：

1. `__sigqueue_alloc()` 分配一个 `struct sigqueue`（含 `siginfo` 拷贝）
2. `list_add_tail()` 挂到 pending 链表尾部 → **FIFO**

## 三、致命陷阱：跨进程传指针

```c
union sigval sv;
sv.sival_ptr = &my_data;
sigqueue(other_pid, MY_SIG, sv);        /* ❌ 灾难 */
```

**为什么错**：不同进程有**独立的虚拟地址空间**。进程 A 的 `0x7ffd1234` 在进程 B 里可能是：

- 未映射的地址 → 进程 B 访问 → `SIGSEGV`
- **完全不同的数据** → 静默读到垃圾值（更危险，无报错）

```
   进程 A 地址空间              进程 B 地址空间
   ┌──────────────┐            ┌──────────────┐
   │ 0x7ffd1234   │            │ 0x7ffd1234   │
   │ my_data      │   ──❌──▶  │ ???（无关数据/
   └──────────────┘            │     未映射）  │
                               └──────────────┘
```

**正确做法**：

| 场景 | 做法 |
|------|------|
| **跨进程** | 只传 **`sival_int`**（小整数，如事件 ID、通道号、命令码） |
| **同进程内线程间** | 可以传指针（`pthread_sigqueue` 发给同进程线程，共享地址空间） |
| **需要传大数据** | 信号只传"索引/ID"，真实数据走共享内存 / 管道 / 消息队列 |

```c
/* ✅ 跨进程只传整数 */
union sigval sv = { .sival_int = 42 };      /* 事件 ID */
sigqueue(pid, MY_SIG, sv);

/* ✅ 同进程线程间可传指针 */
pthread_sigqueue(thread, MY_SIG, (union sigval){ .sival_ptr = obj });
```

## 四、接收端：必须用 `SA_SIGINFO`

不带 `SA_SIGINFO`，就拿不到 `si_value`：

```c
static void handler(int sig, siginfo_t *info, void *ctx)
{
    (void)ctx;
    if (info->si_code == SI_QUEUE)                  /* 确认来自 sigqueue */
        printf("值 = %d，来自 pid=%d\n",
               info->si_value.sival_int, info->si_pid);
}

struct sigaction sa = {0};
sa.sa_sigaction = handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO;                           /* ← 必须 */
sigaction(MY_SIG, &sa, NULL);
```

| `si_code` | 值 | 发送方式 |
|-----------|-----|----------|
| `SI_QUEUE` | -1 | `sigqueue()` |
| `SI_USER` | 0 | `kill()` |
| `SI_TKILL` | -6 | `tgkill()` |
| `SI_TIMER` | -2 | POSIX 定时器到期 |

## 五、队列上限

实时信号队列不是无限的，受资源限制约束：

| 限制 | 说明 |
|------|------|
| `RLIMIT_SIGPENDING` | 每个**用户**（不是每个进程）可排队的信号总数上限 |
| 默认值 | 通常等于 `RLIMIT_NPROC`（如 4096~63000，视发行版） |
| 队列满时 | `sigqueue()` 返回 `-1`，`errno = EAGAIN` |

```c
/* 查看/修改限制 */
struct rlimit rl;
getrlimit(RLIMIT_SIGPENDING, &rl);
printf("sigpending 上限: %lu\n", (unsigned long)rl.rlim_cur);
```

```bash
# shell 查看
ulimit -i          # 即 RLIMIT_SIGPENDING
cat /proc/sys/kernel/rtsig-max      # 系统级实时信号队列上限
```

> **注意**：`__sigqueue_alloc()` 在内存不足时会失败。此时内核按「**至少一个信号递送成功**」的原则处理，可能丢掉 `siginfo` 但保留信号本身——所以 `sigqueue` 的排队保证在极端内存压力下会退化。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | `sigqueue` 带 `int` 值且排队，适合嵌入式进程间传少量带编号控制消息（通道号/事件 ID），比管道轻量。但**跨进程绝不能传指针**（地址空间不同，会 `SIGSEGV` 或读到垃圾）。另注意 `RLIMIT_SIGPENDING` 在嵌入式上可能设得很小，队列容易满导致 `EAGAIN` |
| HFT | 实时信号虽排队带值，但递送仍是**异步中断**，会抢占关键路径产生延迟毛刺——HFT **不用它做高频数据通路**。仅作低频控制信令（切模式/降级），数据通路走共享内存 + eventfd。若确实需要"信号 + 数据 + 不丢"，用 signalfd（[22.11](22.11-fetching-signals-via-a-file-descriptor.md)）把信号转成可 `read()` 的事件流，既保留队列又不进 handler |

## 代码示例：验证排队与携带数据

```c
/* rtsig.c —— 对比标准信号（不排队）与实时信号（排队 + 带数据）
 * 编译: gcc -D_GNU_SOURCE -o rtsig rtsig.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#define N 5
#define MY_SIG (SIGRTMIN + 0)

static int std_count = 0;
static int rt_count  = 0;

/* 注意：为演示可读性用了 printf，生产代码应使用 write(2) */
static void std_handler(int sig) { (void)sig; std_count++; }

static void rt_handler(int sig, siginfo_t *info, void *ctx)
{
    (void)sig; (void)ctx;
    rt_count++;
    printf("  实时信号 #%d: sival_int=%d (si_code=%d %s)\n",
           rt_count, info->si_value.sival_int, info->si_code,
           info->si_code == SI_QUEUE ? "= SI_QUEUE" : "");
}

int main(void)
{
    struct sigaction sa = {0};
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;

    sa.sa_handler = std_handler;
    sigaction(SIGUSR1, &sa, NULL);

    sa.sa_sigaction = rt_handler;              /* 实时信号用 sa_sigaction */
    sa.sa_flags = SA_RESTART | SA_SIGINFO;
    sigaction(MY_SIG, &sa, NULL);

    /* 同时阻塞两者 */
    sigset_t block, save;
    sigemptyset(&block);
    sigaddset(&block, SIGUSR1);
    sigaddset(&block, MY_SIG);
    sigprocmask(SIG_BLOCK, &block, &save);

    /* 各发 N 次，实时信号携带不同数据 */
    for (int i = 1; i <= N; i++) {
        raise(SIGUSR1);                                    /* 标准：不带数据 */
        union sigval sv = { .sival_int = i * 100 };
        sigqueue(getpid(), MY_SIG, sv);                    /* 实时：带数据 */
    }

    printf("阻塞期间各发送 %d 次，现在解除阻塞：\n", N);
    sigprocmask(SIG_SETMASK, &save, NULL);

    printf("\n结果：\n");
    printf("  标准信号 SIGUSR1 : handler 执行 %d 次  ← 不排队\n", std_count);
    printf("  实时信号 SIGRTMIN: handler 执行 %d 次  ← 排队，且数据完整保留\n", rt_count);

    /* 演示队列容量 */
    struct rlimit rl;
    if (getrlimit(RLIMIT_SIGPENDING, &rl) == 0)
        printf("\nRLIMIT_SIGPENDING = %lu（队列满时 sigqueue 返回 EAGAIN）\n",
               (unsigned long)rl.rlim_cur);

    return 0;
}
```

预期输出：

```
阻塞期间各发送 5 次，现在解除阻塞：
  实时信号 #1: sival_int=100 (si_code=-1 = SI_QUEUE)
  实时信号 #2: sival_int=200 (si_code=-1 = SI_QUEUE)
  实时信号 #3: sival_int=300 (si_code=-1 = SI_QUEUE)
  实时信号 #4: sival_int=400 (si_code=-1 = SI_QUEUE)
  实时信号 #5: sival_int=500 (si_code=-1 = SI_QUEUE)

结果：
  标准信号 SIGUSR1 : handler 执行 1 次  ← 不排队
  实时信号 SIGRTMIN: handler 执行 5 次  ← 排队，且数据完整保留

RLIMIT_SIGPENDING = 63093（队列满时 sigqueue 返回 EAGAIN）
```

## 自测题

<details>
<summary><b>问 1：</b>实时信号相比标准信号有哪三个本质改进？</summary>

| 维度 | 标准信号 | 实时信号 |
|------|----------|----------|
| **排队** | ❌ 不排队，阻塞期间同号只保留一份 | ✅ 排队，逐个保留 |
| **携带数据** | ❌ 无 | ✅ `sigqueue()` 可带 `int` / 指针 |
| **递送顺序** | ❌ 无保证 | ✅ 小号优先；同号 FIFO |

**补充说明**：

- 实时信号还有第四个差异：**默认动作统一为 terminate**（标准信号各异），内核注释见 `include/linux/signal.h:385`。
- 排队的实现：实时信号不满足 `legacy_queue()` 的 `sig < SIGRTMIN` 条件（`kernel/signal.c:1079`），所以会走 `__sigqueue_alloc()` + `list_add_tail()`（`:1129-1132`），每次发送都分配节点挂链表尾。

</details>

<details>
<summary><b>问 2：</b>能跨进程用 <code>sigqueue</code> 传指针吗？为什么？</summary>

**绝对不能**。不同进程有**独立的虚拟地址空间**。

进程 A 的 `0x7ffd1234` 在进程 B 中可能是：

- **未映射** → 进程 B 解引用 → `SIGSEGV`
- **完全不同的数据** → 静默读到垃圾值（更危险，无报错）

**正确做法**：

| 场景 | 做法 |
|------|------|
| **跨进程** | 只传 **`sival_int`**（小整数：事件 ID、通道号、命令码） |
| **同进程内线程间** | ✅ 可以传指针（`pthread_sigqueue` 发给同进程线程，共享地址空间） |
| **需要传大数据** | 信号只传"索引/ID"，真实数据走**共享内存** / 管道 / 消息队列 |

```c
/* ✅ 跨进程：只传整数 */

sigqueue(pid, MY_SIG, sv);

/* ✅ 同进程线程间：可传指针 */
pthread_sigqueue(thread, MY_SIG, (union sigval){ .sival_ptr = obj });

/* ❌ 跨进程传指针：灾难 */
sigqueue(other_pid, MY_SIG, (union sigval){ .sival_ptr = &data });
```

</details>

<details>
<summary><b>问 3：</b>为什么 <code>sigqueue()</code> 的排队比 <code>kill()</code> 更可靠？</summary>

POSIX 规定 `sigqueue()` **必须排队**，而 `kill()` 对实时信号只是"尝试"排队。

内核注释明确说明了这一点（`kernel/signal.c:1115-1123`）：

```
 * Real-time signals must be queued if sent by sigqueue, or
 * some other real-time mechanism.  It is implementation
 * defined whether kill() does so.  We attempt to do so, on
 * the principle of least surprise, but since kill is not
 * allowed to fail with EAGAIN when low on memory we just
 * make sure at least one signal gets delivered and don't
 * pass on the info struct.
```

| 发送方式 | 排队保证 | 内存不足时 |
|----------|----------|-----------|
| `sigqueue()` | ✅ POSIX 要求必须排队 | 返回 `-1`，`errno = EAGAIN` |
| `kill()` | ⚠️ 尝试排队，不保证 | **不能**返回 `EAGAIN`（会破坏已有程序），退化为"至少一个递送成功"，丢掉 `siginfo` |

**根因**：`kill()` 的接口契约不允许在内存不足时返回 `EAGAIN`——大量已有代码不处理这个错误码。所以内核只能尽力而为。

**实践**：需要可靠排队 + 携带数据时，**一律用 `sigqueue()`**。

</details>

<details>
<summary><b>问 4：</b>为什么即使是 root，也不能伪造"内核来源"的信号？</summary>

内核在 `do_rt_sigqueueinfo()` 里做了显式拦截：

```c
// kernel/signal.c:4013
static int do_rt_sigqueueinfo(pid_t pid, int sig, kernel_siginfo_t *info)
{
	/* Not even root can pretend to send signals from the kernel.
	 * Nor can they impersonate a kill()/tgkill(), which adds source info.
	 */
	if ((info->si_code >= 0 || info->si_code == SI_TKILL) &&
	    (task_pid_vnr(current) != pid))
		return -EPERM;

	return kill_proc_info(sig, info, pid);
}
```

**判据**：`si_code >= 0` 表示「内核来源」（回顾 [Ch21.4](../../chapter-21-signal-handlers/notes/21.4-the-sa-siginfo-flag.md)：`SI_FROMKERNEL(info)` 即 `si_code > 0`）。

如果允许用户进程设置 `si_code >= 0`，恶意进程就能：

- 伪造 `SIGSEGV` 并附带假的 `si_addr`，诱使目标进程的崩溃诊断逻辑记录错误现场
- 伪造 `SIGCHLD` 让父进程 `wait()` 到不存在子进程的状态
- 冒充 `SI_TKILL` 假装是内核线程管理事件

**所以内核宁可限制 root 也要堵死这条路**——这是一条明确的安全边界，注释里 "Not even root" 措辞很罕见地强调了这一点。

**例外**：发给自己（`task_pid_vnr(current) == pid`）时不受限制——因为不存在欺骗第三方的问题。

</details>

<details>
<summary><b>问 5：</b>实时信号队列会满吗？满了会怎样？如何处理？</summary>

**会满**。受两个限制约束：

| 限制 | 作用域 | 查看方式 |
|------|--------|----------|
| `RLIMIT_SIGPENDING` | **每个用户**（不是每个进程）可排队的信号总数 | `ulimit -i` / `getrlimit()` |
| `rtsig-max` | 系统级实时信号队列上限 | `/proc/sys/kernel/rtsig-max` |

**满了会怎样**：

```c
if (sigqueue(pid, MY_SIG, sv) == -1 && errno == EAGAIN)
    /* 队列满，本次信号未投递 */
```

`sigqueue()` 返回 `-1`，`errno = EAGAIN`。

**注意这是**`sigqueue` **独有的错误**——`kill()` 永远不会返回 `EAGAIN`（见问 3）。

**处理策略**：

```c
/* 策略 1：重试（队列可能很快腾出空间） */
int retry = 0;
while (sigqueue(pid, sig, sv) == -1 && errno == EAGAIN && retry++ < 10)
    usleep(1000);

/* 策略 2：降级 —— 改用不带数据的 kill（保证通知至少到达） */
if (sigqueue(pid, sig, sv) == -1 && errno == EAGAIN)
    kill(pid, sig);

/* 策略 3：改机制 —— 队列频繁满说明设计有问题 */
/* 改用 eventfd / 管道 / 共享内存计数器 */
```

**设计建议**：如果实时信号队列经常满，说明**信号被当成了数据通道**——这是误用。信号的设计定位是"低频控制通知"，高频事件应走 eventfd、管道或共享内存。

**HFT 视角**：队列满导致的 `EAGAIN` 会让控制信令静默丢失，可能引发"降级指令没送达"的事故。所以关键控制路径要么处理 `EAGAIN`，要么干脆换用不会丢的机制（eventfd 的计数器永不丢）。

</details>
