## 本节讲什么

1. POSIX `sigaction` 之前的两套遗产：BSD 系与 System V 系，它们**对同一件事给出了相反的语义**
2. 为什么 `signal()` 不可移植——不是「实现质量」问题，而是**两套语义被同时写进了标准之外的历史**
3. 在老代码里认出这些 API，并给出**逐条迁移对照**（这是本节唯一有实战价值的部分）

> **立场先行**：这一节**没有任何新功能**，全部内容都是「历史的化石」。读它的唯一理由是——你会在 20 年前的嵌入式 BSP、BSD 衍生代码、以及某些第三方库的 `#ifdef` 里撞见它们。新代码一律用 POSIX 三件套：`sigaction` + `sigprocmask` + `sigsuspend`。

## 一、为什么会有两套 API：不可靠信号时代

1980 年代，两家 UNIX 分支各自解决了同一个问题——**原始 `signal()` 不可靠**：

```
原始 UNIX signal() 的三个致命缺陷（"不可靠信号"）

  ① 处置一次性：handler 被调用后自动重置为 SIG_DFL
       → 信号第二次到达就杀进程
       → handler 里第一件事必须是 signal(sig, handler) 重装
       → 重装之前有【窗口】，此处到达的信号会杀死进程

  ② 无法阻塞同类信号：handler 执行期间，下一个同类信号不自动阻塞
       → handler 重入 → 自己打断自己

  ③ 无法查询/控制 pending 集合
       → 想知道"有没有信号在等我"做不到
```

BSD 和 System V 给出了**方向相反**的答案：

| 分歧点 | BSD（4.2/4.3BSD） | System V（SVR2/3） |
|--------|-------------------|--------------------|
| handler 调用后处置 | **保持**（装一次，永久有效） | **重置为 SIG_DFL** |
| handler 执行期间 | **自动阻塞同类信号** | 不阻塞 |
| 被中断的系统调用 | **自动重启** | 返回 `EINTR` |
| 掩码表示 | `int`（32 位，`sigmask()` 宏） | `sigset_t`（SysV 引入） |
| 解决思路 | 「让 `signal()` 变可靠」 | 「另起一套 API」 |
| 代表 API | `sigvec` / `sigblock` / `sigpause(mask)` | `sigset` / `sighold` / `sigpause(sig)` |

POSIX.1-1988 最终选择了 **BSD 的语义内核 + SysV 的接口形态**，诞生了 `sigaction`：

```
        BSD 语义                     SysV 接口形态
   （处置保持/自动重启/          （struct + sigset_t +
     同类阻塞）                    显式 flags）
              \                       /
               \                     /
                ▼                   ▼
           ┌──────────────────────────────┐
           │   POSIX sigaction()          │
           │   struct sigaction {         │
           │       sa_handler             │
           │       sa_mask     ← 显式指定 │
           │       sa_flags    ← 显式控制 │
           │   }                          │
           └──────────────────────────────┘
```

关键设计：**语义不再是硬编码的**，而是由 `sa_flags` 显式声明。这样 BSD 程序员可以要 BSD 行为，SysV 程序员可以要 SysV 行为，同一个接口满足两派。

## 二、两套 API 全景与迁移对照

### 2.1 System V 系

| 遗留函数 | 原始语义 | POSIX 替代 |
|----------|----------|-----------|
| `sighold(sig)` | 把 sig 加入进程掩码（阻塞） | `sigprocmask(SIG_BLOCK, &set, NULL)` |
| `sigrelse(sig)` | 从掩码移除 sig（解除阻塞） | `sigprocmask(SIG_UNBLOCK, &set, NULL)` |
| `sigignore(sig)` | 处置设为忽略 | `sigaction(sig, &(struct sigaction){.sa_handler = SIG_IGN}, NULL)` |
| `sigset(sig, disp)` | 装 handler，**执行期间自动阻塞 sig，返回后恢复**（不是重置） | `sigaction(sig, &sa, NULL)`（默认即此行为） |
| `sigpause(sig)` | 从掩码移除 sig 后挂起等待 | `sigsuspend(&mask_without_sig)` |

**`sigset()` 值得单独说**：它已经是 SysV 对「一次性处置」缺陷的自我修正——handler 执行期间阻塞同类信号、执行完自动解除，**不重置**。所以 `sigset()` 在语义上其实**近似于** POSIX 默认 `sigaction`（`sa_flags=0` 时内核自动阻塞 sa_mask + 自身）。它是 SysV 家族里唯一还算现代的成員。

### 2.2 BSD 系

| 遗留函数 | 原始语义 | POSIX 替代 |
|----------|----------|-----------|
| `sigvec(sig, *sv, *osv)` | 装 handler，带 `sv_mask` / `sv_flags` | `sigaction()`（直接前身） |
| `sigblock(mask)` | 把 `int mask` 中的位加入掩码 | `sigprocmask(SIG_BLOCK, &set, NULL)` |
| `sigsetmask(mask)` | 掩码设为 `int mask` | `sigprocmask(SIG_SETMASK, &set, NULL)` |
| `siggetmask(void)` | 读取当前掩码（返回 `int`） | `sigprocmask(SIG_BLOCK, NULL, &set)` |
| `sigpause(mask)` | 掩码设为 `int mask` 后挂起等待 | `sigsuspend(&set)` |
| `sigmask(sig)` | 宏：`1 << (sig - 1)`，位换算 | `sigaddset(&set, sig)`（不透明类型） |

`struct sigvec` 与 `struct sigaction` 的字段映射：

```c
struct sigvec {                    /* 4.3BSD */
    void (*sv_handler)(int);       /* → sa_handler            */
    int   sv_mask;                 /* → sa_mask（int → sigset_t）*/
    int   sv_flags;                /* → sa_flags（见下表）      */
    int   sv_onstack;              /* 4.2BSD 独有 → SA_ONSTACK */
};
```

| `sv_flags` / `sv_onstack` | POSIX `sa_flags` | 说明 |
|---------------------------|------------------|------|
| `SV_ONSTACK` | `SA_ONSTACK` | 使用 `sigaltstack` 备用栈 |
| `SV_INTERRUPT` | **无对应**（语义相反！） | 要求被中断的系统调用返回 `EINTR` |
| `SV_RESETHAND` | `SA_RESETHAND` | handler 调用后重置为 `SIG_DFL` |
| — | `SA_RESTART` | BSD **默认**自动重启；POSIX **默认不重启**，要显式给 |

> **`SV_INTERRUPT` 是最阴险的一条**：BSD 默认自动重启，所以 BSD 老代码假定 `read()` 不会返 `EINTR`。POSIX 默认行为**相反**——不给 `SA_RESTART` 就会收到 `EINTR`。直接把 BSD 代码翻译成 `sigaction` 而不补 `SA_RESTART`，会在高并发下制造出一批「偶发 `EINTR` 导致连接被误关」的诡异 bug。见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)。

## 三、同名不同义：两个 `sigpause`

这是本节最需要记住的**具体陷阱**——同一个函数名，在两派里参数类型不同、语义也不同：

```
  BSD:     int sigpause(int sigmask);    ← 参数是【掩码】
  SysV:    int sigpause(int sig);        ← 参数是【信号编号】
```

```c
/* BSD 语义：把整个掩码替换成 sigmask，然后等待 */
sigpause(sigmask(SIGUSR1));        /* 只放开 SIGUSR1，其他全阻塞 */

/* SysV 语义：从当前掩码里【移除】sig，然后等待 */
sigpause(SIGUSR1);                 /* 保留现有掩码，额外放开 SIGUSR1 */
```

两者的差异在**其他信号的阻塞状态**上。glibc 头文件里通过特性测试宏区分：

```c
/* glibc: 默认（_DEFAULT_SOURCE）提供 SysV 版本 */
#define _XOPEN_SOURCE_EXTENDED   /* 或 _BSD_SOURCE */ → BSD 版本
```

**后果**：同一份 `#include <signal.h>` 代码，改一个 `-D_GNU_SOURCE` / `-D_XOPEN_SOURCE` 编译开关，行为就变了，而且**编译期不会有任何警告**——因为两个版本的参数都是 `int`。这是最难查的一类 bug。

**迁移规则**：无条件改成 `sigsuspend()`，并且**显式构造掩码**：

```c
sigset_t wait, prev;
sigemptyset(&wait);
sigaddset(&wait, SIGUSR1);
/* 想保留原有掩码？先取出，再按需要增删，然后传给 sigsuspend */
sigprocmask(SIG_BLOCK, NULL, &prev);
...
sigsuspend(&wait);
```

`sigsuspend()` 的参数是**完整的新掩码**（不是「增删」），语义明确、无二义。见 [Ch22.9](22.9-waiting-for-a-signal-using-a-mask-sigsus.md)。

## 四、Linux 与 glibc 的现实：内核是 SysV，glibc 是 BSD

这是理解 `signal()` 不可移植性的**最具体证据**——Linux 上同一个功能名，内核实现和用户态包装的语义是**相反的**。

### 4.1 内核原生 `sys_signal()` 是 System V 语义

```c
/* kernel/signal.c:4622 —— 内核提供的 signal() 系统调用 */
SYSCALL_DEFINE2(signal, int, sig, __sighandler_t, handler)
{
	struct kernel_sigaction new_sa, old_sa;
	int ret;

	siginitsetinv(&new_sa.sa.sa_mask, 0);
	new_sa.sa.sa_handler = handler;
	new_sa.sa.sa_flags = SA_ONESHOT | SA_NOMASK;   /* :4628 ← 硬编码 */
	ret = do_sigaction(sig, &new_sa, &old_sa);

	return ret ? ret : (unsigned long)old_sa.sa.sa_handler;
}
```

| 硬编码 flag | 展开 | 后果 |
|-------------|------|------|
| `SA_ONESHOT`（= `SA_RESETHAND`） | handler 跑一次后处置重置为 `SIG_DFL` | **SysV 语义**（一次性） |
| `SA_NOMASK`（= `SA_NODEFER`） | handler 执行期间**不**阻塞自身 | 可重入，比 SysV 还激进 |
| **没有** `SA_RESTART` | 被中断的系统调用返回 `EINTR` | **SysV 语义** |

也就是说：如果某个程序**绕过 glibc 直接 `syscall(SYS_signal, ...)`**（某些静态链接的 libc 实现、汇编启动代码、或极老的 LSB 二进制会这么干），它拿到的是**纯粹的 SysV 行为**。

### 4.2 glibc 的 `signal()` 是 BSD 语义

glibc 的 `signal()` **不走** `sys_signal` 系统调用，而是走 `rt_sigaction`，并加上 `SA_RESTART`：

```
  用户调用 signal(SIGINT, h)
       │
       ▼
  glibc: signal() 包装
       │  等价于：
       │    struct sigaction sa = {0};
       │    sa.sa_handler = h;
       │    sa.sa_flags = SA_RESTART;      ← BSD 语义（自动重启）
       │    sigaction(SIGINT, &sa, NULL);
       ▼
  syscall: rt_sigaction(SIGINT, &sa, NULL, 8)
       │
       ▼
  内核: do_sigaction():4123
```

所以在 **Linux/glibc 上**，`signal()` 表现为 BSD 语义：**处置保持、自动阻塞同类信号（默认 sa_mask 行为）、自动重启被中断的系统调用**。

### 4.3 三者对照表

| 平台 / 层次 | 处置是否重置 | 是否自动重启 | 是否自动阻塞同类 |
|-------------|--------------|--------------|------------------|
| Linux 内核 `sys_signal:4622` | ✅ 重置（SysV） | ❌ 返 `EINTR`（SysV） | ❌ 不阻塞（`SA_NOMASK`） |
| Linux + glibc `signal()` | ❌ 保持（BSD） | ✅ 自动重启（BSD） | ✅ 阻塞（默认行为） |
| 4.4BSD `signal()` | ❌ 保持 | ✅ 自动重启 | ✅ 阻塞 |
| System V R4 `signal()` | ✅ 重置 | ❌ 返 `EINTR` | ❌ 不阻塞 |
| glibc `sigset()` | ❌ 保持 | （依实现） | ✅ 阻塞 |

**结论**：`signal()` 的语义在**同一台机器的不同层次上都不一样**，更别说跨 UNIX。这就是为什么 [Ch22.7](22.7-implementation-and-portability-of-signal.md) 和 TLPI 反复强调「生产代码用 `sigaction`」——不是为了洁癖，是因为 `signal()` 的行为**根本没有被任何一个标准固定下来**。

> SUSv3 对 `signal()` 的原话是：行为「** unspecified **」（未规定）。而被 `sigaction()` 取代这一点是明确写在标准里的。

## 五、还有一批更老的：不可靠信号的残留

有些符号你可能在现代代码角落里还见到，它们**连 POSIX 都没进**：

| 符号 | 出处 | 现状 |
|------|------|------|
| `sigstack()` | 4.2BSD | 被 `sigaltstack()` 取代（[Ch21.3](../../chapter-21-signal-handlers/notes/21.3-handling-a-signal-on-an-alternate-stack-.md)） |
| `sigmask()` 宏 | BSD | 被 `sigset_t` + `sigaddset` 取代（不透明类型，不再暴露位布局） |
| `SV_*` 标志 | BSD | 被 `SA_*` 取代 |
| `SIGIOT` / `SIGCLD` / `SIGPOLL` | 历史别名 | 分别是 `SIGABRT` / `SIGCHLD` / `SIGIO` 的**同值别名** |
| `SIGEMT` | 历史（PDP-11 模拟器陷阱） | 大多数现代系统未定义（Linux 上用 `#ifdef SIGEMT` 保护） |

`SIGCLD` 尤其要小心：在 SysV 上它和 `SIGCHLD` **语义不同**（SysV 的 `SIGCLD` 处置为 `SIG_IGN` 时行为特殊，会导致子进程**不产生僵尸**但也可能丢失状态）。Linux 上 `SIGCLD == SIGCHLD == 17`，没有这个差异。见 [Ch26](../../chapter-26-monitoring-child-processes/README.md)。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | **这是本节唯一真正会踩到的场景**：BSP、vendor SDK、20 年历史的守护进程里，`signal()` / `sigset()` / `sighold()` 遍地都是。迁移时不要只做机械替换——**必须核对 `SA_RESTART`**：老代码若假定 `read()` 自动重启，改用 `sigaction` 不加 `SA_RESTART` 会引入 `EINTR` 路径，在串口/网络读取上表现为**偶发丢包**。交叉编译时若 vendor 提供的是 uClibc/musl 而非 glibc，`signal()` 的语义要**单独确认**（musl 的 `signal()` 走 `rt_sigaction` + `SA_RESTART`，与 glibc 一致，但不保证所有 libc 都是） |
| HFT | 新代码零容忍：CI 里加一条静态检查，`grep -nE '\b(signal|sigset|sighold|sigrelse|sigignore|sigpause|sigblock|sigvec|sigsetmask|siggetmask)\s*\(' src/ ` 命中即失败，只允许 `sigaction` / `sigprocmask` / `sigsuspend` / `sigwaitinfo` / `signalfd`。理由不是风格，而是**可审计性**：`sa_flags` 显式写出后，reviewer 才能确认「这个 handler 会不会重启 `recv()`」「会不会自动阻塞同类信号」——这些在 `signal()` 下全是隐含的、依赖平台的。第三方库（尤其是闭源行情/风控 SDK）若内部调 `signal()` 装 handler，会**覆盖你的处置**；用 `sigaction(sig, NULL, &old)` 在初始化后**读回校验**是最省事的检测手段 |

## 代码示例：遗留信号 API 的审计与迁移

```c
/* legacy_signal_audit.c —— 审计 + 演示两套语义的差异
 *
 * 编译: gcc -Wall -Wextra -O2 -o legacy_signal_audit legacy_signal_audit.c
 * 运行: ./legacy_signal_audit
 *
 * 用途：
 *   ① 在程序启动后【读回】所有关键信号的实际处置，检测第三方库是否偷偷改过
 *   ② 演示 sigaction 与 signal 在 SA_RESTART 上的差异
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <signal.h>
#include <unistd.h>
#include <errno.h>

/* ---------- ① 处置审计 ---------- */

static const int watch[] = {
    SIGINT, SIGTERM, SIGQUIT, SIGHUP, SIGSEGV, SIGBUS, SIGFPE,
    SIGILL, SIGCHLD, SIGPIPE, SIGUSR1, SIGUSR2, SIGALRM
};

static const char *disp_desc(struct sigaction *sa)
{
    if (sa->sa_handler == SIG_DFL) return "SIG_DFL (默认)";
    if (sa->sa_handler == SIG_IGN) return "SIG_IGN (忽略)";
    return "handler (已安装)";
}

/* 返回 1 = 发现可疑的自定义 handler */
static int audit_dispositions(void)
{
    int suspicious = 0;

    printf("%-10s %-16s %-6s %s\n", "信号", "处置", "RESTART", "自动阻塞本信号");
    printf("------------------------------------------------------------\n");

    for (size_t i = 0; i < sizeof(watch) / sizeof(watch[0]); i++) {
        struct sigaction sa;

        if (sigaction(watch[i], NULL, &sa) == -1) {
            printf("%-10d (查询失败: %s)\n", watch[i], strerror(errno));
            continue;
        }

        int has_handler = (sa.sa_handler != SIG_DFL && sa.sa_handler != SIG_IGN);
        int blocked     = sigismember(&sa.sa_mask, watch[i]);

        printf("%-10d %-16s %-6s %s\n",
               watch[i],
               disp_desc(&sa),
               (sa.sa_flags & SA_RESTART) ? "是" : "否",
               blocked ? "是" : "否");

        /* 挂载了 handler 却没有 SA_RESTART，且没有自身阻塞 → 高风险组合 */
        if (has_handler) {
            suspicious++;
            if (!(sa.sa_flags & SA_RESTART))
                printf("           ^^^ 警告: 无 SA_RESTART，read/recv 会返 EINTR\n");
            if (!blocked)
                printf("           ^^^ 警告: 未阻塞自身，handler 可能被同类信号重入\n");
        }
    }
    return suspicious;
}

/* ---------- ② SA_RESTART 差异演示 ---------- */

static volatile sig_atomic_t got_alarm = 0;

static void on_alarm_norestart(int sig)
{
    (void)sig;
    got_alarm = 1;
    /* 故意不用 write —— 这里只是为了打点，实际 handler 应严格 async-signal-safe */
}

int main(void)
{
    struct sigaction sa, old_sa;

    /* --- 演示 A：signal() 在 Linux/glibc 上的实际 flags --- */
    signal(SIGUSR1, SIG_IGN);
    sigaction(SIGUSR1, NULL, &sa);
    printf("\n[A] signal(SIGUSR1, SIG_IGN) 之后读回:\n");
    printf("    sa_flags = 0x%lx  (SA_RESTART=%d, SA_RESETHAND=%d, SA_NODEFER=%d)\n",
           (unsigned long)sa.sa_flags,
           !!(sa.sa_flags & SA_RESTART),
           !!(sa.sa_flags & SA_RESETHAND),
           !!(sa.sa_flags & SA_NODEFER));
    printf("    → glibc 的 signal() 走 rt_sigaction，Linux 上表现为 BSD 语义\n");
    printf("    → 但内核原生 sys_signal() 硬编码 SA_ONESHOT|SA_NOMASK (:4628)\n");

    /* --- 演示 B：sigaction 不带 SA_RESTART → EINTR --- */
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = on_alarm_norestart;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                        /* ← 关键：不给 SA_RESTART */
    sigaction(SIGALRM, &sa, &old_sa);

    printf("\n[B] sigaction(SIGALRM, flags=0) —— 无 SA_RESTART\n");
    alarm(1);

    char buf[64];
    ssize_t n = read(STDIN_FILENO, buf, sizeof(buf));   /* 阻塞读 */
    int saved = errno;

    if (n < 0 && saved == EINTR) {
        printf("    read() 返回 -1 / EINTR  (got_alarm=%d)\n", got_alarm);
        printf("    → POSIX 默认不重启；BSD 老代码假定会重启 → 迁移时必补 SA_RESTART\n");
    } else {
        printf("    read() 返回 %zd (未演示到 EINTR)\n", n);
    }

    /* --- 演示 C：已知 flag 被内核静默清除 --- */
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = SIG_IGN;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0x40000000U;              /* 瞎编的一个未定义 flag */
    sigaction(SIGUSR2, &sa, NULL);

    sigaction(SIGUSR2, NULL, &sa);
    printf("\n[C] 传入未定义 flag 0x40000000 后读回: sa_flags = 0x%lx\n",
           (unsigned long)sa.sa_flags);
    printf("    → do_sigaction():4153-4156 静默清除未识别位，【不报错】\n");
    printf("    → 所以任何 flag 都要靠读回验证，不能只看返回值\n");

    /* --- 审计 --- */
    printf("\n[D] 当前进程信号处置审计:\n");
    int suspicious = audit_dispositions();
    printf("\n共 %d 个信号安装了自定义 handler\n", suspicious);

    return 0;
}
```

### 迁移检查清单（可直接用于 code review）

- [ ] `grep -nE '\b(signal|sigset|sighold|sigrelse|sigignore|sigpause|sigblock|sigvec|sigsetmask|siggetmask)\s*\(' src/` 命中数 = 0
- [ ] 每处 `sigaction` 都**显式**写了 `sa_flags`（含 `0`），不依赖默认值
- [ ] 需要 `read`/`recv`/`accept` 自动重启的，显式写了 `SA_RESTART`

- [ ] `SIGCHLD` handler 加了 `SA_NOCLDSTOP`（只关心退出时）且内部**循环 `waitpid`**
- [ ] 初始化完成后用 `sigaction(sig, NULL, &sa)` **读回**校验，防止第三方库覆盖
- [ ] 若必须链接闭源库，在库初始化**之后**再装自己的 handler，并在主循环里周期性复查

## 代码自测

<details>
<summary><b>问 1：</b>为什么 <code>sigpause</code> 被称作「同名不同义」的陷阱？它和 <code>sigsuspend</code> 该怎么对应？</summary>

因为 BSD 和 System V 各自定义了一个 `sigpause`，**名字相同、参数类型相同（都是 `int`）、语义不同**：

| 版本 | 原型 | 语义 |
|------|------|------|
| BSD | `int sigpause(int sigmask)` | 把掩码**替换**为 `sigmask`，然后等待 |
| SysV | `int sigpause(int sig)` | 从当前掩码中**移除** `sig`，然后等待 |

差别在「其他信号怎么办」：BSD 版是**全量替换**（参数里没给的都被阻塞），SysV 版是**增量放开**（保留现有掩码）。

由于参数都是 `int`，**编译器完全无法区分**。glibc 用特性测试宏在头文件层面二选一：

- 默认（`_DEFAULT_SOURCE`）→ SysV 版本
- `_XOPEN_SOURCE_EXTENDED` 或 `_BSD_SOURCE` → BSD 版本

于是同一份代码，加个 `-D_XOPEN_SOURCE` 编译开关，行为就悄悄变了，且**零警告**。

迁移时一律改成 `sigsuspend()`，它接收**完整的新掩码**，语义无二义：

```c
sigset_t wait;
sigemptyset(&wait);
sigaddset(&wait, SIGUSR1);
sigsuspend(&wait);        /* 等待期间掩码 = wait */
```

如果想要 SysV「保留现有掩码、额外放开一个」的效果，先取出当前掩码再增删：

```c
sigset_t wait;
sigprocmask(SIG_BLOCK, NULL, &wait);   /* 取当前 */
sigdelset(&wait, SIGUSR1);             /* 移除 → 放开它 */
sigsuspend(&wait);
```

</details>

<details>
<summary><b>问 2：</b>Linux 上 <code>signal()</code> 到底表现为 BSD 语义还是 System V 语义？</summary>

**两个都对，取决于你在哪一层看**：

```c
/* kernel/signal.c:4622 —— 内核系统调用 */
SYSCALL_DEFINE2(signal, int, sig, __sighandler_t, handler)
{
	struct kernel_sigaction new_sa, old_sa;
	int ret;

	siginitsetinv(&new_sa.sa.sa_mask, 0);
	new_sa.sa.sa_handler = handler;
	new_sa.sa.sa_flags = SA_ONESHOT | SA_NOMASK;      /* :4628 */
	ret = do_sigaction(sig, &new_sa, &old_sa);

	return ret ? ret : (unsigned long)old_sa.sa.sa_handler;
}
```

- **内核 `sys_signal()` = SysV 语义**：`SA_ONESHOT` 让处置一次性（SysV），`SA_NOMASK` 让 handler 执行期间不阻塞自身（比 SysV 还激进），**没有** `SA_RESTART`（SysV，返 `EINTR`）。
- **glibc `signal()` = BSD 语义**：它**不走** `sys_signal`，而是调 `rt_sigaction` 并加上 `SA_RESTART`（处置保持 + 自动重启 + 默认 sa_mask 行为）。

所以你从 C 代码里写 `signal()`，拿到的是** BSD 语义**（glibc 包装的功劳）；只有直接 `syscall(SYS_signal, ...)` 的程序（静态链接的非 glibc libc、汇编启动代码、极老的二进制）才会撞上内核的 SysV 实现。

**这正是不可移植性的具象化**：同一个函数名，在一台 Linux 机器的两个层次上语义相反。而 SUSv3 干脆把 `signal()` 的行为定为「unspecified」——标准不保任何一边。所以结论永远是：**生产代码用 `sigaction`，把所有语义写成显式的 `sa_flags`**。

</details>

<details>
<summary><b>问 3：</b>从 BSD 老代码迁移到 <code>sigaction</code> 时，最容易遗漏的一个 flag 是什么？后果是什么？</summary>

**`SA_RESTART`**。

原因是两派在这个点上的**默认值相反**：

| | 被中断的慢系统调用 |
|---|---|
| BSD `signal()` | **默认自动重启** |
| POSIX `sigaction()`（`sa_flags=0`） | **默认不重启**，返回 `EINTR` |

BSD 时代的程序员写 `read(fd, buf, n)` 时，脑子里根本没有「可能返回 `EINTR`」这个分支——因为从来不会。把这些代码机械地翻译成：

```c
struct sigaction sa = {0};
sa.sa_handler = old_bsd_handler;
sa.sa_flags = 0;                  /* ← 漏了 SA_RESTART */
sigaction(SIGFOO, &sa, NULL);
```

于是所有阻塞的 `read` / `write` / `recv` / `accept` / `select` 都开始**偶发**返回 `-1/EINTR`。如果调用方没有处理，通常表现为：

- 网络连接被「莫名」关闭（把 `EINTR` 当错误）
- 串口读到一半丢字节
- 在信号密集时（比如装了 `SIGALRM` 做周期打点）**故障率陡增**，平时完全不复现

这类 bug 的特征是**与信号频率强相关的偶发性**，极难在测试环境复现。

修法有两种，取决于你的架构：

```c
/* 方案 A：声明要重启 */
sa.sa_flags = SA_RESTART;

/* 方案 B：显式处理 EINTR（更推荐，配合 signalfd/sigwaitinfo 架构） */
ssize_t n;
do {
    n = read(fd, buf, sizeof(buf));
} while (n == -1 && errno == EINTR);
```

注意 `SA_RESTART` **不是万能的**——有些调用内核层面就不支持重启（`poll`/`select`/`epoll_wait`/`nanosleep` 等，见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md) 的完整对照表）。另外 **`close()` 在 Linux 上返回 `EINTR` 时 fd 已经关闭，绝不能重试**。

</details>

<details>
<summary><b>问 4：</b><code>sigset()</code> 和 <code>signal()</code> 都来自 System V，它们的行为一样吗？</summary>

**不一样，而且是方向上相反的修正**。

| | 处置是否重置 | handler 期间是否阻塞同类 |
|---|---|---|
| SysV `signal()` | ✅ **重置**为 `SIG_DFL` | ❌ 不阻塞 |
| SysV `sigset()` | ❌ **保持** | ✅ **自动阻塞，返回后自动解除** |
| BSD `signal()` | ❌ 保持 | ✅ 阻塞 |
| POSIX `sigaction()`（`flags=0`） | ❌ 保持 | ✅ 阻塞（内核默认行为） |

`signal()` 正是「不可靠信号」的源头：处置一次性，导致 handler 里第一件事必须是重装 `signal(sig, h)`，而重装之前如果信号又来了 → 进程被默认动作杀死。

`sigset()` 是 SysV 自己的修正：装一次永久有效，且在 handler 执行期间自动阻塞该信号、返回时自动解除——**不再有窗口**。

有意思的是，这个语义**恰好就是** POSIX `sigaction` 在 `sa_flags = 0` 时的默认行为。内核在 `signal_delivered():2915` 处无条件把 `sa_mask` 与信号自身的掩码合入 `current->blocked`，handler 返回时由 `sigreturn` 从 sigframe 恢复原掩码。

所以 `sigset()` 是 SysV 家族里唯一「迁移到 `sigaction` 时语义等价、不需要补 flag」的成員——直接换成 `sigaction(sig, &sa, NULL)`（`sa_flags=0`）即可。

</details>

<details>
<summary><b>问 5：</b>为什么建议 CI 里禁止 <code>signal()</code>？除了风格，还有实质理由吗？</summary>

有，而且至少三条，都是**可审计性**层面的实质问题：

**① 语义不可见。** `signal(sig, h)` 里看不出三件关键的事：
- 被中断的 `read()` 会不会重启？
- handler 执行期间同类信号会不会阻塞？
- 处置会不会一次性？

这三件事在 `signal()` 下**全部由平台决定**，而平台之间**互不相同**（SysV vs BSD vs glibc vs 内核原生）。代码里写着同样的 `signal()`，在 Solaris 和 Linux 上行为不同。`sigaction` 把这些写成显式的 `sa_flags`，reviewer 一眼能确认。

**② 读不回来、也验不了。** 你想在初始化后确认「SIGTERM 的处置真的是我装的那个 handler、且带了 `SA_RESTART`」——用 `signal()` 装的根本没法问。而 `sigaction(sig, NULL, &old)` 可以把内核里实际保存的 `sa_flags` / `sa_mask` 完整读回来（[Ch20.13](../../chapter-20-signals-fundamentals/notes/20.13-changing-signal-dispositions-sigaction.md) 里的「读回验证法」）。这在**链接了闭源第三方库**时是唯一的防线——库可能在它的构造函数里偷偷装 handler，覆盖你的。

**③ 内核静默吞 flag，返回值不报错。** `do_sigaction():4153-4156` 会把未识别的 `sa_flags` 位**静默清除并返回 0**：

```c
	/* If the signal is ignored, or the handler is SIG_DFL ... */
	if (!sig_handler_ignored ... )
	...
	/* Just in case we have a flag that's not supported */
	act->sa_flags &= ~SA_UNSUPPORTED;    /* 静默，不返回错误 */
```

这意味着传错 flag（比如把 `SA_SIGINFO` 拼错、或用了某平台专有位）**不会有任何错误信号**，行为却悄悄变成了默认值。唯一可靠的验证手段是「装完立刻读回比对」——而这要求你一开始就用 `sigaction`。

**CI 规则**（可直接落地）：

```bash
# 命中即 fail
grep -nE '\b(signal|sigset|sighold|sigrelse|sigignore|sigpause|sigblock|sigvec|sigsetmask|siggetmask)\s*\(' src/
# 白名单：sigaction / sigprocmask / pthread_sigmask / sigsuspend /
#         sigwaitinfo / sigtimedwait / signalfd / sigaltstack / psignal
```

</details>
