## 本节讲什么

Ch22 是信号主题的**收官章**，它不引入新概念，而是回答四个「Ch20/Ch21 讲完基础之后必然冒出来的问题」：

1. 信号**什么时候**真的到达？先后顺序由谁决定？（22.2 / 22.3 / 22.6）
2. 除了装 handler，还有**别的**接收方式吗？（22.9 / 22.10 / 22.11）
3. 硬件异常（段错误、除零）和 `kill()` 在内核里**走的是同一条路吗**？（22.4 / 22.5）
4. 老代码里那些 `signal()` / `sigset()` 到底是什么来路？（22.7 / 22.13）

本节把全章压成一张速览表、一张 API 速查表、五条铁律和三个关键区分。

## 二、API 速查表

```c
/* ── 发送 ─────────────────────────────────────────────── */
kill(pid, sig)                     /* 发信号，不能带数据        */
sigqueue(pid, sig, sigval)         /* 发信号 + 4/8 字节数据，可排队 */
raise(sig) / tgkill(tgid, tid, sig)/* 发给自己 / 发给指定线程    */

/* ── 接收 ─────────────────────────────────────────────── */
/*  A. 异步（装 handler，信号打断正常控制流）              */
struct sigaction sa = {0};
sa.sa_sigaction = handler;         /* 注意：与 sa_handler 是 union */
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_RESTART;
sigaction(sig, &sa, NULL);

/*  B. 同步等待（不跑 handler，信号被"取走"）              */
sigsuspend(&mask)                  /* 原子：换掩码 + 睡；可跑 handler */
sigwaitinfo(&set, &info)           /* 阻塞取走，返回信号编号       */
sigtimedwait(&set, &info, &ts)     /* 带超时，超时返回 -1/EAGAIN   */

/*  C. fd 化（融进 epoll 事件循环）                        */
sigset_t mask; sigfillset(&mask);
sigprocmask(SIG_BLOCK, &mask, NULL);        /* ① 必须先阻塞 */
int sfd = signalfd(-1, &mask, SFD_NONBLOCK);/* ② 建 fd     */
read(sfd, &fdinfo, sizeof(fdinfo));         /* ③ 读（缓冲要够大）*/

/* ── 掩码与 pending ──────────────────────────────────── */
sigprocmask(how, &set, &old)       /* 多线程用 pthread_sigmask */
sigpending(&set)                   /* 查 (私有∪共享) ∩ 掩码    */

/* ── 栈与诊断 ────────────────────────────────────────── */
sigaltstack(NULL, &ss);            /* 先查当前（SS_ONSTACK 判断）*/
stack_t ss = { .ss_sp = buf, .ss_size = N, .ss_flags = SS_AUTODISARM };
sigaltstack(&ss, NULL);            /* 再设置（多线程各设各的）  */
sa.sa_flags |= SA_ONSTACK;         /* 按【信号】注册，不是全局  */
strsignal(sig) / psignal(sig, msg) /* 描述文本；handler 里不安全 */
```

## 三、五条铁律

### 铁律 1：三种接收方式，先想清楚选哪个

```
                    ┌─────────────────────────────────────┐
                    │  你的信号是用来干嘛的？              │
                    └──────────────┬──────────────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
  【崩溃兜底】              【主循环里等控制信号】      【多事件统一管理】
  SIGSEGV/SIGBUS/SIGFPE     SIGTERM/SIGHUP/SIGUSR1     任意 + socket/timer
        │                          │                          │
        ▼                          ▼                          ▼
  必须 handler            阻塞 + 专用线程              signalfd + epoll
  + SA_ONSTACK            sigwaitinfo 循环              统一事件循环
  + sigaltstack
        │
        ▼
  只能 handler：
  signalfd/sigwaitinfo
  【抓不到同步故障信号】
  （走 force_sig_fault 直投）
```

| 方式 | 跑 handler？ | 能被 epoll 管？ | 能抓 SIGSEGV？ | 典型用途 |
|------|--------------|------------------|----------------|----------|
| `sigaction` handler | ✅ 是 | ❌ | ✅ 是（唯一） | 崩溃兜底、栈溢出收尸 |
| `sigsuspend` | ✅ 是（返回后） | ❌ | ⚠️ 理论可以但不该 | 单线程简单等待 |
| `sigwaitinfo` / `sigtimedwait` | ❌ 否 | ❌ | ❌ 否 | 专用信号线程（推荐模型） |
| `signalfd` | ❌ 否 | ✅ **是** | ❌ 否 | 主事件循环统一纳管 |

### 铁律 2：等待信号必须用原子接口

```c
/* ❌ 有竞态：解除阻塞 → 信号到达（丢失）→ pause() 永远睡着 */
sigprocmask(SIG_SETMASK, &oldmask, NULL);
pause();

/* ✅ 原子：换掩码 + 睡眠，一步完成 */
sigsuspend(&oldmask);
```

内核对照（`kernel/signal.c`）：

```c
SYSCALL_DEFINE0(pause)                    /* :4639 */
{
	__set_current_state(TASK_INTERRUPTIBLE);      /* ① 睡          */
	schedule();                                   /* ② 让出 CPU    */
	return -ERESTARTNOHAND;                       /* ③ 醒来必返 -1 */
}

SYSCALL_DEFINE3(sigsuspend, ...)          /* :4650 */
{
	set_current_blocked(&new_mask);               /* ① 换掩码（先） */
	__set_current_state(TASK_INTERRUPTIBLE);      /* ② 睡（后）     */
	schedule();                                   /* ③ 让出 CPU     */
	set_restore_sigmask();                        /* ④ 恢复原掩码   */
	return -ERESTARTNOHAND;
}
```

`sigsuspend` 睡在**新掩码**上——「解除阻塞」与「进入睡眠」之间**没有窗口**，因为它根本没解除过，而是直接换了个掩码然后睡。

### 铁律 3：同步等待/信号 fd 之前，**必须先阻塞**

```
  信号到达
     │
     ├─ 未阻塞 ──→ 触发 handler / 执行默认动作 ──→ signalfd 读不到 ❌
     │
     └─ 已阻塞 ──→ 进 pending 队列 ──→ signalfd / sigwaitinfo 取走 ✅
```

这是 **`signalfd` 和 `sigwaitinfo` 最常见的失败原因**：信号没阻塞，进程直接被默认动作杀掉（或跑了 handler），fd 上永远没数据。

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGTERM);
sigaddset(&mask, SIGINT);
sigprocmask(SIG_BLOCK, &mask, NULL);     /* ← 必须在 signalfd() 之前 */
int sfd = signalfd(-1, &mask, SFD_NONBLOCK);
```

### 铁律 4：标准信号不排队，实时信号才排队

```c
/* kernel/signal.c:1079 —— 三行代码定生死 */
static bool legacy_queue(struct sigpending *signals, int sig)
{
	return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
	/*      ^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ */
	/*      标准信号才检查       已经在 pending 里 → 丢弃 */
}
```

| | 标准信号（1–31） | 实时信号（`SIGRTMIN`+, Linux=34） |
|---|---|---|
| 排队 | ❌ 位图，最多 1 个待决 | ✅ 队列，可多个 |
| 携带数据 | ❌ | ✅ `union sigval` |
| 递送顺序 | **号小者优先**（`next_signal():209`） | 同号 FIFO，号小者优先 |
| 有优先级保证 | ❌ | ✅ |

**最典型的坑——`SIGCHLD` 漏收**：

```c
static void on_child(int sig)
{
    int saved = errno;
    /* ✗ 错：三个子进程同时退出只递送一次，剩下两个永久僵尸 */
    /* waitpid(-1, NULL, WNOHANG); */

    /* ✓ 对：循环回收直到没有更多 */
    while (waitpid(-1, NULL, WNOHANG) > 0)
        ;
    errno = saved;
}
```

### 铁律 5：`signal()` 不用，遗留 API 全不用

| 平台 / 层次 | 处置是否重置 | 自动重启？ |
|-------------|--------------|-----------|
| 内核 `sys_signal:4622`（`SA_ONESHOT\|SA_NOMASK`） | ✅ 重置 | ❌ |
| Linux + glibc `signal()` | ❌ 保持 | ✅ |
| System V `signal()` | ✅ 重置 | ❌ |
| BSD `signal()` | ❌ 保持 | ✅ |

**同一台 Linux 机器的两个层次上语义相反**。SUSv3 干脆规定 `signal()` 行为「unspecified」。生产代码一律：

```c
struct sigaction sa = {0};
sa.sa_handler = h;
sigemptyset(&sa.sa_mask);          /* 必做：栈上结构体未初始化 */
sa.sa_flags = SA_RESTART;          /* 显式，不依赖默认值 */
sigaction(sig, &sa, NULL);
/* 装完读回校验（防第三方库覆盖 + 内核静默吞 flag）*/
sigaction(sig, NULL, &verify);
```

## 四、三个关键区分

### 区分 1：阻塞 vs 忽略

| | 阻塞（`sigprocmask`） | 忽略（`SIG_IGN`） |
|---|---|---|
| 信号去了哪 | 进 pending 队列 | **直接丢弃** |
| 解除后 | 立即递送 | 永远不会递送 |
| `sigpending()` 能看到 | ✅ | ❌ |
| 内核判定 | `current->blocked` 位图 | `sighand->action[].sa_handler == SIG_IGN` |

```c
/* kernel/signal.c:81 */
static bool sig_task_ignored(struct task_struct *t, int sig, bool force)
{
	if (sigismember(&t->blocked, sig) || sigismember(&t->real_blocked, sig))
		return false;                       /* 阻塞 → 不忽略，留着 */

	if (t->ptrace && sig != SIGKILL)
		return true;

	return sig_handler_ignored(sig_handler(t, sig), sig, force);
	/*          ^^^^^^^^^^^^^^^^^^^^ SIG_IGN → 真忽略 */
}
```

### 区分 2：同步 vs 异步信号

| | 同步（synchronous） | 异步（asynchronous） |
|---|---|---|
| 触发源 | 当前线程**自己执行的指令** | 别的进程 / 内核事件 |
| 代表 | `SIGSEGV` `SIGBUS` `SIGFPE` `SIGILL` `SIGTRAP` `SIGSYS` | `kill()` 来的、终端产生的、`SIGCHLD`、`SIGALRM` |
| 内核路径 | `force_sig_fault():1740` → `force_sig_info_to_task():1336` | `__send_signal_locked():1084` |
| 定向 | **线程定向**（`PIDTYPE_PID`），必落在肇事线程 | 进程级（随机挑一个不阻塞的线程） |
| 能否被忽略/阻塞 | ❌ 内核**撤销** `SIG_IGN` 并**解除阻塞** | ✅ 正常走掩码与处置 |
| `si_code` | `> 0`（`SI_FROMKERNEL`） | `kill()` 时 `<= 0`（`SI_FROMUSER`） |
| signalfd 能抓吗 | ❌ **不能** | ✅ 能 |

内核用一张位图区分（`kernel/signal.c:205`）：

```c
#define SYNCHRONOUS_MASK (\
	sigmask(SIGSEGV) | sigmask(SIGBUS) | sigmask(SIGILL) | \
	sigmask(SIGTRAP) | sigmask(SIGFPE) | sigmask(SIGSYS))
```

`get_signal()` 里优先取出同步信号：`dequeue_synchronous_signal():716`。

### 区分 3：可中断 vs 不可中断睡眠

| 状态 | 值位置 | 信号能唤醒？ | 典型场景 |
|------|--------|--------------|----------|
| `TASK_INTERRUPTIBLE` | `sched.h:87` | ✅ 任意信号 | 绝大多数阻塞 syscall |
| `TASK_UNINTERRUPTIBLE` | `sched.h:88` | ❌ **连 SIGKILL 都不行** | 磁盘 I/O、某些驱动临界区 |
| `TASK_KILLABLE` | `sched.h:116` | ⚠️ **只有致命信号**（SIGKILL） | `wait_for_completion_killable()` 等 |

```c
/* kernel/signal.c:769 */
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
	set_tsk_thread_flag(t, TIF_SIGPENDING);       /* ① 打标记 */

	if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
		kick_process(t);                          /* ② 跨 CPU 踢一脚 */
	/*                    ^^^^^^^^^^^^^^^^^^^^
	 * 只唤醒处于 INTERRUPTIBLE 的；UNINTERRUPTIBLE 的【叫不醒】 */
}
```

**实践意义**：`ps` 里看到 `D` 状态（`UNINTERRUPTIBLE`）的进程 `kill -9` 杀不掉，就是这个原因。它通常在等硬件/磁盘，等 I/O 完成才会醒——如果硬件挂了，它会**永久卡住**，只能重启。

## 五、HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **core**：目标板默认 `ulimit -c 0` + 只读根 fs，几乎拿不到 core；启动脚本里显式 `ulimit -c unlimited` 并把 `core_pattern` 指向可写分区或管道转发到开发机，用 `coredump_filter` 砍掉 framebuffer 等大映射。② **D 状态**：`kill -9` 杀不掉 `UNINTERRUPTIBLE` 进程，在缺少硬件复位的设备上意味着只能断电——设计 watchdog 时要考虑这一点。③ **遗留 API**：vendor BSP 里 `signal()` / `sigset()` 遍地，迁移时必须补 `SA_RESTART`，否则串口/网络读会偶发 `EINTR` 丢字节 |
| HFT | ① **生产关 core**（`RLIMIT_CORE=0` + `PR_SET_DUMPABLE 0`）：8GB 持仓共享内存 dump 一次会卡数秒 + 打满磁盘 I/O，反而拖垮同机进程；且 core 含客户数据，落地即合规风险。改用 `SA_ONSTACK` 的 SIGSEGV handler 写最小现场（backtrace + 关键寄存器）到预分配缓冲，微秒级完成。② **推荐架构**：主线程 `pthread_sigmask(SIG_BLOCK, ...)` 阻塞全部 → 起一个专用线程 `sigwaitinfo` 循环 → 主事件循环用 `signalfd` + `epoll` 统一纳管 socket/timer/signal。③ **同步故障信号只能 handler 抓**：`SIGSEGV`/`SIGBUS`/`SIGFPE` 走 `force_sig_fault` 线程定向直投，signalfd 抓不到，必须留 `SA_ONSTACK` handler 兜底。④ **CI 禁 `signal()`**：`sa_flags` 显式写出才可审计 |

**推荐的 HFT 生产信号架构**：

```
  main()
    │
    ├─ pthread_sigmask(SIG_BLOCK, {SIGTERM,SIGINT,SIGHUP,SIGUSR1,SIGUSR2})
    │      （所有线程继承，worker 天然不受打扰）
    │
    ├─ 崩溃兜底（唯一保留 handler 的地方）：
    │     sigaltstack + SA_ONSTACK + SA_SIGINFO
    │     SIGSEGV/SIGBUS/SIGFPE/SIGILL → 写最小现场 → _exit(128+sig)
    │
    ├─ 信号线程：
    │     for (;;) { sig = sigwaitinfo(&set, &info); handle(sig, &info); }
    │
    └─ 主事件循环：
          epoll_wait(epfd, ...)   ← 监听 [listen_fd] [timer_fd] [signalfd]
```

## 代码自测

<details>
<summary><b>问 1：</b>进程阻塞了 SIGTERM，然后别人发来 3 个 SIGTERM，解除阻塞后 handler 会跑几次？</summary>

**1 次**。

SIGTERM(15) < `SIGRTMIN`(=34)，走 `legacy_queue()`（`kernel/signal.c:1079`）：

```c
static bool legacy_queue(struct sigpending *signals, int sig)
{
	return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
	/*      标准信号            已经在 pending 位图里 → 返回 true → 丢弃 */
}
```

pending 是**位图**，不是队列，一个 bit 只能记「有/无」。第 2、3 个 SIGTERM 到达时位已经置 1，直接丢弃。

POSIX 的措辞是「至少递送一次」——它只保证不会**完全**丢失，不保证每个都递送。

**后果**（经典）：多个子进程同时退出 → 多个 SIGCHLD → 只递送一次 → handler 只 `waitpid` 一次 → 其余永久僵尸。

**修法三选一**：

```c
/* ① 循环回收（最常用）*/
while (waitpid(-1, NULL, WNOHANG) > 0)
    ;

/* ② 根本不关心子进程 → 直接 SIG_IGN，内核自动回收不产生僵尸 */
signal(SIGCHLD, SIG_IGN);        /* 或 sigaction */

/* ③ 需要可靠计数 → 用实时信号 + sigqueue（会排队）*/
sigqueue(pid, SIGRTMIN, (union sigval){ .sival_int = n });
```

</details>

<details>
<summary><b>问 2：</b><code>signalfd</code> 为什么抓不到 <code>SIGSEGV</code>？</summary>

因为**同步故障信号根本不进 pending 队列供 signalfd 取**，而是被内核**强行直投**到肇事线程。

内核路径（`kernel/signal.c`）：

```c
/* :1740 */
int force_sig_fault(int sig, int code, void __user *addr)
{
	struct kernel_siginfo info;
	clear_siginfo(&info);
	info.si_signo = sig;
	info.si_errno = 0;
	info.si_code  = code;
	info.si_addr  = addr;
	return force_sig_info(&info);
}
        ↓
/* :1336 */
static int force_sig_info_to_task(struct kernel_siginfo *info, struct task_struct *t)
{
	/* ① 撤销 SIG_IGN */
	action->sa.sa_handler = SIG_DFL;
	action->sa.sa_flags  &= ~SA_SIGINFO;
	/* ② 解除阻塞 */
	sigdelset(&t->blocked, sig);
	/* ③ 线程定向（PIDTYPE_PID）——必落在肇事线程 */
	ret = send_signal_locked(sig, info, t, PIDTYPE_PID);
	...
}
```

三件事决定了它与 signalfd 不兼容：

1. **撤销 `SIG_IGN`**：就算你设成忽略也没用，内核给你改回来
2. **解除阻塞**：就算你阻塞了也没用，内核给你删掉——所以不会进 pending 等 signalfd 取
3. **`PIDTYPE_PID` 线程定向**：直投到触发异常的那个线程

而且从语义上讲这是**必须的**：`SIGSEGV` 是 CPU 执行某条指令时同步产生的，handler 返回后 CPU 会**重试同一条指令**。如果它进了 pending 队列等别人来取，那条指令就永远停在那里（或无限重试），程序状态完全不可控。所以内核的处理是「立刻、就地、定向」地让它死或让 handler 接管。

**实践结论**：`SIGSEGV`/`SIGBUS`/`SIGFPE`/`SIGILL` 的兜底**只能**用 `sigaction` handler（配 `SA_ONSTACK` + `sigaltstack`，因为栈可能已经溢出）。`signalfd` / `sigwaitinfo` 管的是**异步**信号（控制类、`SIGCHLD`、定时器信号）。

</details>

<details>
<summary><b>问 3：</b><code>sigsuspend</code> 和 <code>sigwaitinfo</code> 的本质区别是什么？</summary>

**一个「递送」，一个「取走」**——这是最本质的差别，决定了它们能否共存于同一架构。

| | `sigsuspend(&mask)` | `sigwaitinfo(&set, &info)` |
|---|---|---|
| 信号是否跑 handler | ✅ **跑**（handler 返回后 `sigsuspend` 才返回） | ❌ **不跑**（信号被直接消费） |
| 返回值 | 永远是 `-1` / `EINTR` | 信号编号（≥1） |
| 需要装 handler 吗 | ✅ 需要（否则默认动作可能杀进程） | ❌ 不需要（但通常仍装一个兜底） |
| 掩码语义 | 睡眠期间的**完整新掩码** | 要取走的**信号集合** |
| 超时 | ❌ 无 | ✅ `sigtimedwait` 有 |
| 用途 | 单线程里的简单原子等待 | 多线程模型里的专用信号线程 |

内核对照：

```c
/* sigsuspend:4650 —— 换掩码 → 睡 → 醒来后让 handler 先跑 */
set_current_blocked(&new_mask);
__set_current_state(TASK_INTERRUPTIBLE);
schedule();
set_restore_sigmask();        /* 恢复原掩码 */

/* rt_sigtimedwait:3663 —— 直接从 pending 里摘出来返回给用户 */
ret = dequeue_signal(current, &ksig, ...);   /* 不经过 handler */
if (ret) { copy_siginfo_to_user(...); return ret; }
```

**实践推论**：

- 混用是**自找麻烦**——信号到底跑 handler 还是被取走，取决于哪个先到、哪个先调用，行为不确定
- 干净的做法是**二选一**：要么全用 handler 模型，要么全用「阻塞 + 专用线程 `sigwaitinfo`」模型
- 「阻塞 + 专用线程」是多线程程序的**推荐模型**：worker 线程天然继承阻塞掩码不受打扰，只有信号线程处理，全程无异步上下文切换、无 async-signal-safe 约束

</details>

<summary><b>问 4：</b>为什么 <code>kill -9</code> 有时候杀不掉进程？</summary>

因为进程可能在 **`TASK_UNINTERRUPTIBLE`**（`ps` 里的 `D` 状态）睡眠。

```c
/* kernel/signal.c:769 */
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
	set_tsk_thread_flag(t, TIF_SIGPENDING);

	if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
		kick_process(t);
}
```

`wake_up_state()` 只会唤醒**状态匹配**的任务。这里传入的掩码是 `state | TASK_INTERRUPTIBLE`，所以：

| 睡眠状态 | `TASK_INTERRUPTIBLE` 位 | `kill -9` 能唤醒？ |
|----------|--------------------------|---------------------|
| `TASK_INTERRUPTIBLE:87` | 有 | ✅ 能 |
| `TASK_KILLABLE:116`（`= WAKEKILL \| UNINTERRUPTIBLE`） | 有（配合 `state` 传入 `TASK_WAKEKILL`） | ✅ 能 |
| `TASK_UNINTERRUPTIBLE:88` | **无** | ❌ **不能** |

`SIGKILL` 的「不可阻挡」指的是**用户态层面**——你不能捕获、不能忽略、不能阻塞它。但**唤醒**是另一回事：一个睡在 `UNINTERRUPTIBLE` 的任务根本不会被调度，压根没机会去检查 `TIF_SIGPENDING` 标志。信号只是被挂在它的 pending 队列上，等它醒来才会处理。

常见成因：

- 等待坏掉的磁盘 / NFS 挂载（`D` 状态最典型的来源）
- 驱动里错误的 `UNINTERRUPTIBLE` 等待（应该用 `TASK_KILLABLE`）
- 某些 `vfork` / `futex` 的短暂窗口

诊断：

```bash
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'
cat /proc/PID/stack        # 需要 root，看卡在哪个内核函数
cat /proc/PID/status | grep -E 'State|SigPnd|ShdPnd'
```

如果 `SigPnd` 非零但状态是 `D`——说明 SIGKILL **已经挂上了**，只等它醒来。硬件不恢复就只能重启。

<summary><b>问 5：</b>多个不同信号同时 pending，内核按什么顺序递送？</summary>

**信号编号小的优先**——不是 FIFO，不是按到达时间。

```c
/* kernel/signal.c:209 */
static int next_signal(struct sigpending *pending, sigset_t *mask)
{
	...
	sig = find_first_bit((unsigned long *)&x, _NSIG);   /* ← 从低位找第一个置位的 */
	...
}
```

`find_first_bit` 从编号 1 开始向高位扫描，所以：

```
  pending 集合 = { SIGTERM(15), SIGUSR1(10), SIGCHLD(17), SIGIO(29) }

  递送顺序： SIGUSR1(10) → SIGTERM(15) → SIGCHLD(17) → SIGIO(29)
             ↑ 号小者先，与到达顺序无关
```

**唯一的例外**：同步故障信号优先。

```c
/* get_signal() 里 */
signr = dequeue_synchronous_signal(&ksig->info);   /* :716 —— 先取同步的 */
if (!signr)
	signr = dequeue_signal(current, &ksig->info, ...);   /* :635 —— 再取异步的 */
```

`SYNCHRONOUS_MASK:205` = `SIGSEGV | SIGBUS | SIGILL | SIGTRAP | SIGFPE | SIGSYS`。这些信号在 `next_signal` 之前就被单独摘出来了，所以总是一马当先。

**延迟的另一面**：信号不是「一到就处理」，而是在**从内核态返回用户态之前**才检查。所以：

```c
while (1);              /* 纯用户态忙等：永不进内核 → 信号永不递送 */
```

而任何一次系统调用、中断、缺页，都会让 CPU 进内核，返回时顺带检查 `TIF_SIGPENDING`。`pause()` 之所以能等信号，就是因为它调了 `schedule()` 进内核睡眠。

**实践含义**：不要用信号编号的顺序去表达业务优先级。如果需要优先级语义，用多个信号 + 自己的调度逻辑，或用 `signalfd` 一次性读出全部 pending 后自行排序（`signalfd_read():202` 的循环同样按号小优先填充缓冲区，但你可以读出来自己排）。

</details>
