## 本节讲什么

1. **core dump 是什么**——进程在某个信号下死亡时，内核把它死前那一刻的内存映像写进一个文件
2. **哪些信号会触发 core**——不是所有致命信号都 dump，内核有一张硬编码名单
3. **为什么生产环境常常没有 core**——六道开关，任何一道关掉都拿不到文件

---

## 一、Core dump 是什么

进程执行了非法操作（段错误、除零、非法指令）或被 `abort()` 时，内核的默认动作之一是**终止进程并把进程的内存映像写到磁盘**。这个文件叫 **core dump**（`core`），用调试器加载它可以还原崩溃现场：

```
进程崩溃瞬间
  ├── 所有线程的寄存器（PC/SP/各通用寄存器）
  ├── 全部可 dump 的内存映射（堆、栈、匿名映射、ELF 头）
  ├── 每个线程的调用栈（backtrace）
  └── 变量值、堆内容、锁状态
```

调试器加载：

```bash
gdb ./trader core.12345          # 或: gdb -c core.12345 ./trader
(gdb) bt                          # 崩溃线程栈
(gdb) thread apply all bt         # 所有线程栈
(gdb) info registers
(gdb) p *(Order*)0x7f...
```

> **为什么叫 core**：源自磁芯存储器（magnetic core memory）时代，"core" 就是主存的代名词。

## 二、哪些信号会触发 core

内核在 `include/linux/signal.h` 里硬编码了名单：

```c
/* include/linux/signal.h:425 */
#define SIG_KERNEL_COREDUMP_MASK (\
        rt_sigmask(SIGQUIT)   |  rt_sigmask(SIGILL)    | \
        rt_sigmask(SIGTRAP)   |  rt_sigmask(SIGABRT)   | \
        rt_sigmask(SIGFPE)    |  rt_sigmask(SIGSEGV)   | \
        rt_sigmask(SIGBUS)    |  rt_sigmask(SIGSYS)    | \
        rt_sigmask(SIGXCPU)   |  rt_sigmask(SIGXFSZ)   | \
        SIGEMT_MASK                                    )

/* :445 */
#define sig_kernel_coredump(sig)   siginmask(sig, SIG_KERNEL_COREDUMP_MASK)
```

| 信号 | 值 | 触发典型原因 |
|------|-----|--------------|
| `SIGQUIT` | 3 | 终端 `Ctrl-\`；主动要求 dump 排查死锁 |
| `SIGILL` | 4 | 非法指令：栈被踩坏后返回到垃圾地址、SIMD 指令在不支持的 CPU 上 |
| `SIGTRAP` | 5 | 断点 / `perf` 事件（`send_sig_perf():1824`） |
| `SIGABRT` | 6 | `abort()`：`assert()` 失败、glibc 检测到堆损坏（`malloc_printerr`） |
| `SIGFPE` | 8 | 整数除零；浮点异常（默认被屏蔽，需 `feenableexcept`） |
| `SIGSEGV` | 11 | 空指针、越界、栈溢出、写只读页 |
| `SIGBUS` | 7 | mmap 文件被截断后访问、未对齐访问（部分架构）、`SIGBUS/MCEERR` 硬件内存错误 |
| `SIGSYS` | 31 | seccomp 拦截了非法系统调用（`force_sig_seccomp():1858`） |
| `SIGXCPU` | 24 | 超过 `RLIMIT_CPU` |
| `SIGXFSZ` | 25 | 写入超过 `RLIMIT_FSIZE` |
| `SIGEMT` | — | 架构相关（x86 上无此信号） |

**关键反例——这些致命信号不 dump**：

| 信号 | 默认动作 | 为什么 |
|------|----------|--------|
| `SIGKILL` (9) | terminate | 不可拦截，`SIG_KERNEL_ONLY_MASK:418`，注释明确 "action is **always**, not just default" |
| `SIGTERM` (15) | terminate | 属于常规终止，不算"异常" |
| `SIGINT` (2) | terminate | 同上 |
| `SIGHUP` (1) | terminate | 同上 |
| `SIGPIPE` (13) | terminate | 正常的管道断开 |

> **推论**：`kill -9` 杀进程**拿不到 core**。想让挂死的进程留下现场，要用 `kill -QUIT` 或 `kill -ABRT`（前提是它没忽略/捕获该信号）。这是运维排障最常用的一个技巧。

## 三、内核产生 core 的完整路径

在 `get_signal()` 的 `fatal:` 分支（`kernel/signal.c:2856`）：

```c
fatal:
        spin_unlock_irq(&sighand->siglock);
        if (unlikely(cgroup_task_frozen(current)))
                cgroup_leave_frozen(true);

        /* Anything else is fatal, maybe with a core dump. */
        current->flags |= PF_SIGNALED;                    /* :2864 */

        if (sig_kernel_coredump(signr)) {                 /* :2866 ← 名单判定 */
                if (print_fatal_signals)
                        print_fatal_signal(ksig->info.si_signo);
                proc_coredump_connector(current);         /* 通知 netlink 监听者 */
                do_coredump(&ksig->info);                 /* :2878 ← 真正写文件 */
        }

        if (current->flags & PF_USER_WORKER)
                goto out;

        do_group_exit(ksig->info.si_signo);               /* :2892 ← 无论是否 dump，终归要死 */
        /* NOTREACHED */
```

```
内核态路径（同步故障信号为主）

  CPU 异常（#PF / #DE / #UD / #GP）
      │   arch/x86/mm/fault.c · arch/x86/kernel/traps.c
      ▼
  force_sig_fault(sig, code, addr)          kernel/signal.c:1740
      │
      ▼
  force_sig_info_to_task(..., HANDLER_CURRENT)   :1336
      │   ├─ 若该信号被阻塞 → 强制解除阻塞（:1352 sigdelset）
      │   ├─ 若处置是 SIG_IGN → 强制重置成 SIG_DFL（:1349）
      │   └─ send_signal_locked(..., PIDTYPE_PID)  :1364  ← 定向到故障线程
      ▼
  返回用户态前 → get_signal() :2660
      │
      ├─ 处置 = handler？ → 跑 handler（若 SA_ONSTACK 则用备用栈）
      └─ 处置 = SIG_DFL 且 sig_kernel_coredump() 成立 → fatal 分支
              ▼
         do_coredump() :2878 ──→ 写 core 文件（可能耗时数秒）
              ▼
         do_group_exit() :2892 ──→ 整个线程组退出
```

> **`force_*` 家族的语义**（注释在 `kernel/signal.c:1324-1334`）值得记住：
> *"Force a signal that the process can't ignore: if necessary we unblock the signal and change any `SIG_IGN` to `SIG_DFL`. We don't want to have recursive `SIGSEGV`'s etc."*
>
> 也就是说，你对 `SIGSEGV` 设置的 `SIG_IGN` 或阻塞**在真正的硬件故障面前无效**——内核会强行撤销，否则程序会陷入"忽略段错误→再次段错误"的死循环。

## 四、六道开关：为什么你拿不到 core

这是本节最实用的一部分。 core 需要**同时**通过六道关卡：

| # | 开关 | 检查/设置方式 | 默认 |
|---|------|---------------|------|
| 1 | **信号的默认动作必须是 core** | `SIG_KERNEL_COREDUMP_MASK:425`（见第二节表） | 只限 11 个信号 |
| 2 | **处置必须是 `SIG_DFL`** | `do_sigaction()` 装了 handler 就不再走默认动作 | 是 |
| 3 | **`RLIMIT_CORE` > 0** | `ulimit -c` / `setrlimit(RLIMIT_CORE, ...)` | 多数发行版默认 **0（关闭）** |
| 4 | **进程 dumpable** | `prctl(PR_SET_DUMPABLE, 1)`；exec setuid 程序后内核自动置 0 | 是 |
| 5 | **`core_pattern` 可用** | `/proc/sys/kernel/core_pattern`；目录可写、磁盘有空间 | `core` |
| 6 | **`coredump_filter` 没把内容全滤掉** | `/proc/PID/coredump_filter` | `0x33` |

**逐条诊断口诀**：

```bash
# 1. 你以为它在跑，其实被 systemd/容器关了
ulimit -c                         # → 0 就是没开
ulimit -c unlimited               # 当前 shell 及其子进程生效

# 2. core 文件去哪了
cat /proc/sys/kernel/core_pattern
#   core                          → 写在进程 CWD，文件名 core.PID
#   |/usr/lib/systemd/systemd-coredump ...   → 被 systemd 接管，用 coredumpctl 查

# 3. 进程是否允许 dump
cat /proc/PID/coredump_filter     # 0x33 是默认
grep -i core /proc/PID/limits     # Max core file size

# 4. systemd 发行版
coredumpctl list
coredumpctl info <PID>
coredumpctl gdb <PID>
```

> **嵌入式高频坑**：BusyBox 的 `init` 默认 `ulimit -c 0`，且目标板根文件系统往往只读或空间极小 → core 永远写不出来。要么在启动脚本里显式 `ulimit -c unlimited` 并挂一个可写分区，要么把 `core_pattern` 设成管道，把 dump 通过网络送给开发机上的 `gdbserver`/收集服务。

## 五、core 文件写到哪里

### 5.1 `core_pattern` 与占位符

```bash
cat /proc/sys/kernel/core_pattern
# 例：/var/coredump/core.%e.%p.%t
```

| 占位符 | 展开为 |
|--------|--------|
| `%%` | 字面 `%` |
| `%p` | 崩溃进程的 PID（其所在 PID namespace 内） |
| `%P` | 崩溃进程的 PID（初始 PID namespace 内） |
| `%i` / `%I` | 触发 dump 的**线程** TID（本 namespace / 初始 namespace） |
| `%u` / `%g` | real UID / real GID |
| `%s` | 导致 dump 的**信号编号** |
| `%t` | 崩溃时刻（UNIX 秒） |
| `%h` | 主机名 |
| `%e` | 进程名（`comm`，最长 15 字符） |
| `%E` | 可执行文件路径，斜杠替换成 `!` |
| `%c` | 崩溃进程的 `RLIMIT_CORE` 软限制 |
| `%d` | dump 模式（同 `PR_GET_DUMPABLE` 返回值） |

**推荐配置**（生产可追溯）：

```bash
mkdir -p /var/coredump
echo '/var/coredump/core.%e.%p.%s.%t' > /proc/sys/kernel/core_pattern
# 永久化：写 /etc/sysctl.d/99-coredump.conf
#   kernel.core_pattern = /var/coredump/core.%e.%p.%s.%t
```

### 5.2 管道模式：dump 不是文件，而是喂给一个程序

`core_pattern` **以 `|` 开头**时，内核不写文件，而是把 core 通过**管道**喂给指定程序（在**初始命名空间**以 root 身份运行）：

```bash
# systemd 发行版的典型默认
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h %e

# 也可以喂给自己的收集器
|/opt/bin/coredump-collector %p %s %t %e
```

管道模式的价值：

- **压缩 / 限流 / 转发**：不占本地磁盘，直接发到集中存储
- **按需裁剪**：只保留栈和关键段，丢弃 GB 级共享内存
- **不阻塞太久**：内核对新 core 有"并发上限"（`/proc/sys/kernel/core_pipe_limit`），超出的直接放弃，避免一堆进程同时 dump 打爆系统

### 5.3 `core_uses_pid`

```bash
cat /proc/sys/kernel/core_uses_pid    # 1 / 0
```

若 `core_pattern` 里**不含 `%p`** 且 `core_uses_pid != 0`，内核自动在文件名后附加 `.PID`。设为 1 可以避免"两个进程同时崩溃互相覆盖 core"。

## 六、控制 dump 哪些内存：`coredump_filter`

`coredump_filter` 是一个位掩码，决定**哪些类型的内存映射**会被写进 core。来自 `include/linux/sched/coredump.h:35-43`：

```c
/* coredump filter bits —— mm->flags 中的位号 */
#define MMF_DUMP_ANON_PRIVATE    2     /* 匿名私有映射（堆、栈、mmap(MAP_ANON)） */
#define MMF_DUMP_ANON_SHARED     3     /* 匿名共享映射（MAP_SHARED|MAP_ANONYMOUS） */
#define MMF_DUMP_MAPPED_PRIVATE  4     /* 文件私有映射（代码段、数据段、私有文件 mmap） */
#define MMF_DUMP_MAPPED_SHARED   5     /* 文件共享映射 */
#define MMF_DUMP_ELF_HEADERS     6     /* ELF 头 */
#define MMF_DUMP_HUGETLB_PRIVATE 7     /* 私有巨页 */
#define MMF_DUMP_HUGETLB_SHARED  8     /* 共享巨页 */
#define MMF_DUMP_DAX_PRIVATE     9     /* 私有 DAX（持久内存）映射 */
#define MMF_DUMP_DAX_SHARED     10     /* 共享 DAX 映射 */

#define MMF_DUMP_FILTER_SHIFT    MMF_DUMPABLE_BITS   /* = 2 */
#define MMF_DUMP_FILTER_DEFAULT \
        ((1 << MMF_DUMP_ANON_PRIVATE) | (1 << MMF_DUMP_ANON_SHARED) | \
         (1 << MMF_DUMP_HUGETLB_PRIVATE) | MMF_DUMP_MASK_DEFAULT_ELF)
```

`/proc/PID/coredump_filter` 中用户读写的**位号 = mm 位号 − 2**：

| 用户位 | 掩码 | 含义 |
|--------|------|------|
| 0 | `0x001` | 匿名**私有**映射（**堆、线程栈**） |
| 1 | `0x002` | 匿名**共享**映射 |
| 2 | `0x004` | 文件**私有**映射（代码段、数据段） |
| 3 | `0x008` | 文件**共享**映射（**共享内存 mmap 的文件后端**） |
| 4 | `0x010` | ELF 头（gdb 需要它才能解析 `core`） |
| 5 | `0x020` | 私有巨页 |
| 6 | `0x040` | 共享巨页 |
| 7 | `0x080` | 私有 DAX |
| 8 | `0x100` | 共享 DAX |

默认值 **`0x33`** = 位 0+1+4+5 置位 = 匿名私有 + 匿名共享 + ELF 头 + 私有巨页。

**实用裁剪**（HFT 场景最有价值的一条）：

```bash
# 排除"文件共享映射"（位 3），通常能砍掉最大的那块（共享内存/大文件 mmap）
echo 0x2b > /proc/self/coredump_filter      # 0x33 - 0x08 = 0x2b

# 极端瘦身：只留栈 + ELF 头（够 bt 用，但看不到全局变量）
echo 0x11 > /proc/self/coredump_filter      # 位 0 (匿名私有) + 位 4 (ELF 头)
```

程序内设置：

```c
/* 需要在 exec/fork 后设置；子进程继承此值 */
int fd = open("/proc/self/coredump_filter", O_WRONLY);
if (fd >= 0) { write(fd, "0x2b", 4); close(fd); }
```

> **警告**：位 4（ELF 头）**不要清掉**——没有 ELF 头，gdb 无法解析 core，文件就成了废字节。

## 七、dumpable 标志与安全

`include/linux/sched/coredump.h:7-9` 定义了三档：

```c
#define SUID_DUMP_DISABLE   0    /* 完全不 dump */
#define SUID_DUMP_USER      1    /* 以进程所有者身份 dump（正常默认） */
#define SUID_DUMP_ROOT      2    /* 允许 root dump（用于调试 setuid 程序） */
```

```c
prctl(PR_SET_DUMPABLE, 0);     /* 禁止生成 core（也禁止 ptrace 附加） */
prctl(PR_SET_DUMPABLE, 1);     /* 恢复 */
```

**内核自动置 0 的时机**（关键安全行为）：

| 时机 | 原因 |
|------|------|
| exec 一个 **setuid / setgid** 程序 | 防止通过 core 读出特权进程内存 |
| 进程改变自己的 **UID/GID**（`setuid()` 等） | 同上 |
| 执行 `PR_SET_DUMPABLE` 显式设置 | 用户主动 |

> 这意味着：**调试 setuid 程序时默认拿不到 core**。开发期可临时 `echo 2 > /proc/sys/fs/suid_dumpable`（`SUID_DUMP_ROOT`），但要清楚这会把特权进程的内存明文写到磁盘——生产环境应视为高危操作。

`PR_SET_DUMPABLE(0)` 还有一个副作用：**禁止其他进程 `ptrace` 附加**。所以生产进程常常主动设为 0，一举两得（防 dump 泄密 + 防注入调试）。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 目标板默认 `ulimit -c 0` + 只读/小容量根fs → core 几乎永远拿不到；应在启动脚本显式 `ulimit -c unlimited`，把 `core_pattern` 指向可写分区或管道转发到开发机。用 `coredump_filter` 砍掉大映射（如 framebuffer、大数据缓冲），否则 512MB 内存的设备写不出 512MB 的 core |
| HFT | **生产交易进程通常主动关 core**（`RLIMIT_CORE=0` + `PR_SET_DUMPABLE 0`）：① 持仓/订单簿在共享内存里，dump 一个 8GB core 会**卡住数秒并打满磁盘 I/O**，反而拖垮同机其他进程；② core 里含客户数据和策略内存，落地即合规风险。替代方案：**`SA_ONSTACK` 的 SIGSEGV handler 写最小现场**（backtrace + 关键寄存器，用 `backtrace_symbols_fd` 或 libunwind）到预分配缓冲，微秒级完成，不落大文件。**盘后复现环境**才开 core + `-g -O0` 构建 |

## 代码示例

### 示例 1：可控地打开 core 并触发一次段错误

```c
/* coredump_demo.c —— 演示 core dump 的开关与触发
 * 编译: gcc -g -O0 -o coredump_demo coredump_demo.c
 * 运行: ./coredump_demo ; ls -l core.* */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/resource.h>
#include <sys/prctl.h>

static void set_core_filter(const char *val)
{
    int fd = open("/proc/self/coredump_filter", O_WRONLY);
    if (fd < 0) { perror("coredump_filter"); return; }
    if (write(fd, val, strlen(val)) < 0)
        perror("write coredump_filter");
    close(fd);
}

static void show_core_pattern(void)
{
    FILE *f = fopen("/proc/sys/kernel/core_pattern", "r");
    if (!f) return;
    char buf[256] = {0};
    if (fgets(buf, sizeof(buf), f))
        printf("core_pattern = %s", buf);   /* 自带换行 */
    fclose(f);
}

int main(int argc, char **argv)
{
    /* 开关 3: RLIMIT_CORE —— 多数发行版默认是 0，必须显式打开 */
    struct rlimit rl = { .rlim_cur = RLIM_INFINITY, .rlim_max = RLIM_INFINITY };
    if (setrlimit(RLIMIT_CORE, &rl) == -1)
        perror("setrlimit(RLIMIT_CORE)");

    /* 开关 4: dumpable（exec setuid 后会被内核自动清 0） */
    prctl(PR_SET_DUMPABLE, 1);

    /* 开关 6: 只保留 匿名私有 + 匿名共享 + ELF头 + 私有巨页，剔掉文件共享映射 */
    set_core_filter("0x33");

    show_core_pattern();
    printf("pid=%ld  RLIMIT_CORE=%s  coredump_filter=0x33\n",
           (long)getpid(),
           rl.rlim_cur == RLIM_INFINITY ? "unlimited" : "limited");
    fflush(stdout);

    /* 触发 SIGSEGV（在 SIG_KERNEL_COREDUMP_MASK 名单里）→ 产生 core */
    volatile int *p = (volatile int *)0;
    if (argc > 1 && !strcmp(argv[1], "--sigabrt"))
        abort();                 /* SIGABRT，同样 dump */
    *p = 42;                     /* SIGSEGV */
    return 0;                    /* NOTREACHED */
}
```

```bash
$ gcc -g -O0 -o coredump_demo coredump_demo.c
$ ulimit -c unlimited
$ echo 'core.%e.%p.%s' | sudo tee /proc/sys/kernel/core_pattern
$ ./coredump_demo
core_pattern = core.%e.%p.%s
pid=12345  RLIMIT_CORE=unlimited  coredump_filter=0x33
Segmentation fault (core dumped)
$ ls
core.coredump_demo.12345.11
$ gdb ./coredump_demo core.coredump_demo.12345.11
(gdb) bt
#0  0x000055b... in main (argc=1, argv=0x7ffd...) at coredump_demo.c:60
```

文件名中的 `.11` 就是 `%s`（信号编号 11 = SIGSEGV）。

### 示例 2：HFT 风格——不落 core，只记最小现场

```c
/* crash_note.c —— 生产环境替代 core：SIGSEGV handler 在备用栈上写最小现场
 * 编译: gcc -O2 -o crash_note crash_note.c -rdynamic */
#define _GNU_SOURCE
#include <signal.h>
#include <execinfo.h>
#include <unistd.h>
#include <string.h>
#include <stdlib.h>
#include <stdio.h>

#define BT_DEPTH 32
static char   g_altstack[SIGSTKSZ * 4];
static int    g_crash_fd = STDERR_FILENO;

static void crash_handler(int sig)
{
    /* 只使用 async-signal-safe 调用：write / backtrace_symbols_fd */
    static const char hdr[] = "\n==== CRASH ====\n";
    write(g_crash_fd, hdr, sizeof(hdr) - 1);

    void *bt[BT_DEPTH];
    int n = backtrace(bt, BT_DEPTH);
    /* backtrace_symbols_fd 是 async-signal-safe 的（不 malloc） */
    backtrace_symbols_fd(bt, n, g_crash_fd);

    /* 恢复默认处置后重新抛出 → 让内核走正常终止路径（若 ulimit -c 允许仍会 dump） */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigaction(sig, &sa, NULL);
    raise(sig);
}

int main(void)
{
    stack_t ss = { .ss_sp = g_altstack, .ss_size = sizeof(g_altstack), .ss_flags = 0 };
    sigaltstack(&ss, NULL);                    /* 栈溢出时也能跑 */

    struct sigaction sa = {0};
    sa.sa_handler = crash_handler;
    sa.sa_flags   = SA_ONSTACK | SA_NODEFER;   /* 用备用栈；允许嵌套 */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGBUS,  &sa, NULL);
    sigaction(SIGILL,  &sa, NULL);
    sigaction(SIGABRT, &sa, NULL);
    sigaction(SIGFPE,  &sa, NULL);

    volatile int *p = (int *)0;
    *p = 1;
    return 0;
}
```

对比两种方案：

| | core dump | handler 最小现场 |
|--|-----------|------------------|
| 落地体积 | 整个进程内存（可达 GB） | 几 KB 栈回溯 |
| 写盘耗时 | 数百 ms ~ 数秒 | < 1 ms |
| 信息量 | 完整（变量值、堆、所有线程） | 只有栈回溯 |
| 合规风险 | 内存明文落地 | 通常可控 |
| 适用 | 开发 / 盘后复现 | 生产热路径 |

## 代码自测

<details>
<summary><b>问 1：</b>为什么 <code>kill -9</code> 拿不到 core，而 <code>kill -3</code>（SIGQUIT）可以？</summary>

因为是否 dump 由 `SIG_KERNEL_COREDUMP_MASK`（`include/linux/signal.h:425`）决定，而不是"是否致命"。

```c
#define SIG_KERNEL_COREDUMP_MASK (\
        rt_sigmask(SIGQUIT) | rt_sigmask(SIGILL) | rt_sigmask(SIGTRAP) | \
        rt_sigmask(SIGABRT) | rt_sigmask(SIGFPE) | rt_sigmask(SIGSEGV) | \
        rt_sigmask(SIGBUS)  | rt_sigmask(SIGSYS) | rt_sigmask(SIGXCPU) | \
        rt_sigmask(SIGXFSZ) | SIGEMT_MASK)
```

`SIGKILL` 不在这张名单里——它属于 `SIG_KERNEL_ONLY_MASK:418`（`SIGKILL | SIGSTOP`），语义上是"立即、无条件终止"，不附带诊断。内核在 `get_signal():2866` 处判定：

```c
if (sig_kernel_coredump(signr)) {
        proc_coredump_connector(current);
        do_coredump(&ksig->info);
}
do_group_exit(ksig->info.si_signo);   /* 两者最终都要死 */
```

`SIGQUIT`(3) 在名单里，所以 `kill -QUIT` 是运维上"让挂死的进程留下 core"的标准手段。前提是**该进程没有捕获或忽略 SIGQUIT**——否则走的是 handler 分支，压根不会到 `fatal:`。

顺带一提，`SIGTERM`(15) 也不在名单里，所以优雅停止不会 dump。

</details>

<details>
<summary><b>问 2：</b>代码里给 SIGSEGV 装了 <code>SIG_IGN</code>，程序空指针解引用时会怎样？</summary>

**照样死，而且照样可能 dump**。

原因在 `force_sig_info_to_task()`（`kernel/signal.c:1336`），硬件故障信号走的是"强制"路径：

```c
action = &t->sighand->action[sig-1];
ignored = action->sa.sa_handler == SIG_IGN;
blocked = sigismember(&t->blocked, sig);
if (blocked || ignored || (handler != HANDLER_CURRENT)) {
        action->sa.sa_handler = SIG_DFL;      /* ← 强行重置 */
        if (blocked) {
                sigdelset(&t->blocked, sig);  /* ← 强行解除阻塞 */
                recalc_sigpending_and_wake(t);
        }
}
```

内核注释（`:1324-1334`）直说了：

> *"Force a signal that the process can't ignore: if necessary we unblock the signal and change any `SIG_IGN` to `SIG_DFL`. … We don't want to have recursive `SIGSEGV`'s etc, for example."*

逻辑很直白：如果允许忽略段错误，CPU 回到同一条指令会**再次触发同一个异常**，形成不可跳出`SIG_IGN`死循环。内核宁可无视你的设置。

**注意区分**：

| 场景 | 走的路径 | 你的 `SIG_IGN` 有效吗 |
|------|----------|----------------------|
| `raise(SIGSEGV)` / `kill(pid, SIGSEGV)` | `send_signal_locked()` 常规路径 | ✅ 有效（被忽略，什么事都没有） |
| 真实空指针解引用 | `force_sig_fault()` 强制路径 | ❌ 无效，被内核撤销 |

这条区分是面试和 debug 的经典分水岭：**软件"伪造"的 SIGSEGV 和硬件"真"的 SIGSEGV 在内核里待遇完全不同**。

</details>

<details>
<summary><b>问 3：</b>进程崩溃了，但目录下没有 core 文件——列出至少 5 种可能原因和排查命令。</summary>

| # | 原因 | 排查 |
|---|------|------|
| 1 | `RLIMIT_CORE = 0` | `ulimit -c`；`grep -i core /proc/PID/limits` |
| 2 | 信号不在 core 名单（如 `SIGKILL`/`SIGTERM`） | 看退出码；`WIFSIGNALED(status)` + `WTERMSIG` |
| 3 | 程序自己装了 handler / 设为 `SIG_IGN` | 源码审计 `sigaction`；`strace -e signal` |
| 4 | `core_pattern` 被 systemd 接管成管道 | `cat /proc/sys/kernel/core_pattern`；`coredumpctl list` |
| 5 | 进程非 dumpable（exec 了 setuid 程序） | `cat /proc/PID/status \| grep -i dump`；`prctl(PR_GET_DUMPABLE)` |
| 6 | 目标目录不可写 / 磁盘满 / 文件已存在 | `ls -ld $(dirname $(cat /proc/sys/kernel/core_pattern))`；`df -h` |
| 7 | CWD 不对（daemon 通常 `chdir("/")`） | `ls -l /core*`；改用绝对路径的 `core_pattern` |
| 8 | 容器内 `core_pattern` 指向宿主机路径（core 落在宿主机） | 这是 namespace 共享 sysctl 的经典陷阱 |
| 9 | `coredump_filter` 把内容全滤了（文件 0 字节或极小） | `cat /proc/PID/coredump_filter` |

**一条命令自检序列**：

```bash
ulimit -c unlimited
cat /proc/sys/kernel/core_pattern
cat /proc/sys/kernel/core_uses_pid
cat /proc/self/coredump_filter
cat /proc/sys/fs/suid_dumpable
mkdir -p /tmp/cores && echo '/tmp/cores/core.%e.%p' | sudo tee /proc/sys/kernel/core_pattern
```

**父进程侧判断**（比翻目录可靠）：

```c
int status;
waitpid(pid, &status, 0);
if (WIFSIGNALED(status)) {
    printf("killed by signal %d", WTERMSIG(status));
#ifdef WCOREDUMP
    if (WCOREDUMP(status)) printf(" (core dumped)");
#endif
}
```

`WCOREDUMP` 直接告诉你内核到底有没有生成 core，不用猜。

</details>

<details>
<summary><b>问 4：</b>HFT 交易进程 8GB 内存（含大块共享内存行情库），崩溃时 dump 会有什么问题？怎么优化？</summary>

**问题**：

1. **写盘耗时不可控**：8GB 写普通 SSD 约数秒，`do_coredump()` 是在**崩溃线程的退出路径上同步执行**的（`get_signal():2878`）。期间该线程一直持有 `sighand->siglock` 之外的资源，且整机 I/O 被打满。
2. **连坐同机进程**：生产机上通常同跑行情网关、风控、其他策略，磁盘 I/O 饱和会让它们的延迟一起爆掉——一次崩溃演变成一次故障。
3. **磁盘空间**：多进程同时崩溃 → 数十 GB 瞬间占满，可能触发其他进程的写失败。
4. **合规风险**：core 里是**明文内存**，含客户委托、持仓、策略参数。落盘即形成一份不受控的敏感数据副本。

**优化方案**（按推荐度排序）：

| 方案 | 做法 | 效果 |
|------|------|------|
| **A. 生产关 core + handler 记栈** | `setrlimit(RLIMIT_CORE, 0)` + `prctl(PR_SET_DUMPABLE, 0)`；`SA_ONSTACK` 的 SIGSEGV handler 用 `backtrace_symbols_fd()` 写栈回溯 | 微秒级、KB 级、可控；看不到变量值 |
| **B. 裁剪 dump 内容** | `echo 0x2b > /proc/self/coredump_filter`（剔掉位 3 文件共享映射） | 通常能砍掉 70%+ 体积，且共享行情库本来也不需要在 core 里 |
| **C. 管道模式 + 压缩转发** | `core_pattern = \|/opt/bin/collector %p %s %t` | 不占本地盘；可限速、压缩、发到集中存储 |
| **D. 盘后复现环境开 core** | 独立环境 `-g -O0` 构建 + `ulimit -c unlimited` | 完整信息，但只用于复现，不进生产 |
| **E. 限制并发 dump** | `echo 4 > /proc/sys/kernel/core_pipe_limit` | 防止同时崩溃雪崩 |

**推荐组合**：**A（生产） + D（复现）**。A 保证崩溃时"有线索、不连坐"，D 保证"能定位"。

另外——**真正高频的线上崩溃不应该靠 core 排查**。HFT 的崩溃根因往往是内存踩坏或竞态，应该在**盘前用 ASan/UBSan/TSan 构建跑一遍**（见 03.6 用户态调试模块），而不是等生产崩溃再收尸。

</details>

<details>
<summary><b>问 5：</b>父进程如何可靠地知道子进程"是崩溃了还是正常退出"？如果崩溃了，是否生成了 core？</summary>

用 `waitpid()` 的 status 解码宏，不要用退出码猜：

```c
#include <sys/wait.h>
#include <stdio.h>
#include <string.h>     /* strsignal */

void report(int status)
{
    if (WIFEXITED(status)) {
        printf("正常退出, 退出码 = %d\n", WEXITSTATUS(status));
    } else if (WIFSIGNALED(status)) {
        int sig = WTERMSIG(status);
        printf("被信号 %d (%s) 杀死", sig, strsignal(sig));
#ifdef WCOREDUMP
        printf(", %s", WCOREDUMP(status) ? "已生成 core" : "未生成 core");
#endif
        printf("\n");
    } else if (WIFSTOPPED(status)) {
        printf("被信号 %d 停止\n", WSTOPSIG(status));
    } else if (WIFCONTINUED(status)) {
        printf("收到 SIGCONT 继续\n");
    }
}
```

要点：

| 宏 | 含义 |
|----|------|
| `WIFEXITED` | 正常/主动退出（`exit` / `return` / `_exit`） |
| `WEXITSTATUS` | 退出码的低 8 位 |
| `WIFSIGNALED` | **被信号杀死**（未被捕获、默认动作为终止） |
| `WTERMSIG` | 杀死它的信号编号 |
| `WCOREDUMP` | **是否生成了 core**（POSIX 非标准，Linux/BSD 有，需 `#ifdef`） |
| `WIFSTOPPED` / `WSTOPSIG` | 被停止（需 `WUNTRACED` 选项） |
| `WIFCONTINUED` | 收到 `SIGCONT` 恢复（需 `WCONTINUED` 选项） |

**两个常见误解**：

1. **`WIFSIGNALED` 只在"没装 handler"时成立。** 装了 handler 但 handler 里 `_exit(1)` 的，父进程看到的是 `WIFEXITED` + 退出码 1——看起来像"正常退出"。所以**崩溃自愈逻辑不能只看 `WIFSIGNALED`**，还要约定退出码语义（如"退出码 ≥ 200 表示异常终止"）。

2. **`WCOREDUMP` 说的是"内核尝试生成了"，不等于文件成功落盘。** `RLIMIT_CORE`、磁盘满、`core_pattern` 无效都会导致 `do_coredump()` 内部失败，但 `WCOREDUMP` 仍可能为 1。要确认文件存在，还得查 `core_pattern` 指向的路径。

HFT 场景：进程监控器（supervisor）用这套解码决定重启策略——`WCOREDUMP` 为真说明是内存类崩溃，应**隔离该实例、保留 core、拉起新实例**；`WIFEXITED` 且退出码为约定的"主动降级"码，则按策略静默重启。

</details>
