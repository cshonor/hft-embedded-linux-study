## 一、多个信号同时挂起：递送顺序

### 1.1 内核规则

```c
/* kernel/signal.c:205 */
#define SYNCHRONOUS_MASK \
        (sigmask(SIGSEGV) | sigmask(SIGBUS) | sigmask(SIGILL) | \
         sigmask(SIGTRAP) | sigmask(SIGFPE) | sigmask(SIGSYS))

/* kernel/signal.c:209 */
int next_signal(struct sigpending *pending, sigset_t *mask)
{
        unsigned long i, *s, *m, x;
        int sig = 0;

        s = pending->signal.sig;
        m = mask->sig;

        /*
         * Handle the first word specially: it contains the
         * synchronous signals that need to be dequeued first.
         */
        x = *s &~ *m;
        if (x) {
                if (x & SYNCHRONOUS_MASK)
                        x &= SYNCHRONOUS_MASK;
                sig = ffz(~x) + 1;
                return sig;
        }
        /* ... 后续 word 同样是找最低置位 ... */
}
```

两条规则：

| 优先级 | 规则 |
|--------|------|
| **第一优先** | **同步故障信号**（`SYNCHRONOUS_MASK`：SIGSEGV/SIGBUS/SIGILL/SIGTRAP/SIGFPE/SIGSYS）先于其他一切信号 |
| **第二优先** | 其余信号中，**信号编号最小者**先（`ffz(~x)` = 找最低置位比特） |

为什么要让同步信号插队？`get_signal()` 的注释说得很清楚（`kernel/signal.c:2763-2767`）：

```c
/*
 * Signals generated by the execution of an instruction
 * need to be delivered before any other pending signals
 * so that the instruction pointer in the signal stack
 * frame points to the faulting instruction.
 */
```

否则 `SIGSEGV` handler 里看到的 PC 早就不是出错的那条指令了，栈回溯直接失去意义。

### 1.2 还有一层：私有挂起先于共享挂起

```c
/* kernel/signal.c:635 */
int dequeue_signal(struct task_struct *tsk, sigset_t *mask,
                   kernel_siginfo_t *info, enum pid_type *type)
{
        /* We only dequeue private signals from ourselves, we don't let
         * signalfd steal them
         */
        *type = PIDTYPE_PID;
        signr = __dequeue_signal(&tsk->pending, mask, info, &resched_timer);   /* :645 私有 */
        if (!signr) {
                *type = PIDTYPE_TGID;
                signr = __dequeue_signal(&tsk->signal->shared_pending,
                                         mask, info, &resched_timer);         /* :648 共享 */
        }
        ...
}
```

```
出队顺序（三次筛选）

  ① 私有挂起 task_struct.pending       ← 定向给本线程的（tgkill / 同步故障 / raise）
       │  没有？
       ▼
  ② 共享挂起 signal_struct.shared_pending  ← 定向给进程的（kill / killpg / 定时器）
       │
       ▼
  ③ 在命中的那一层里：同步故障信号优先 → 再按编号升序
```

### 1.3 可移植性警告

> **POSIX / SUSv3 没有规定多信号挂起时的递送顺序。** "小号优先"是 Linux（以及大多数 System V 系）的**实现行为**，不是标准保证。
>
> 也就是说：**你的代码逻辑不能依赖递送顺序**。如果"先处理 A 再处理 B"对程序正确性有影响，那这个设计本身就有问题——应该把顺序信息编码进数据（如 `sigqueue` 携带序号），而不是指望内核排队顺序。
>
> 唯一有标准保证的是：**同一实时信号的多个实例按 FIFO 递送**（POSIX.1b 明确要求）。

## 二、挂起期间改处置：用哪一个？

### 2.1 信号被阻塞时，处置在解除阻塞那一刻才被读取

内核在 `get_signal()` 里这样取处置（`kernel/signal.c:2785`）：

```c
ka = &sighand->action[signr-1];

if (ka->sa.sa_handler == SIG_IGN)   /* Do nothing.  */
        continue;
if (ka->sa.sa_handler != SIG_DFL) {
        /* Run the handler.  */
        ksig->ka = *ka;
        if (ka->sa.sa_flags & SA_ONESHOT)
                ka->sa.sa_handler = SIG_DFL;
        break;
}
```

关键：**`ka` 是在信号真正出队、准备递送的那一刻才去读 `sighand->action[]` 的**。信号挂在 pending 集合里的时候，处置根本没被"锁定"。

所以：

```
t0: SIGUSR1 被阻塞
t1: kill 发来 SIGUSR1        → 进入 pending 集合（处置此时是 handler_A）
t2: sigaction(SIGUSR1, handler_B)   ← 改处置
t3: 解除阻塞                  → 递送，跑的是 handler_B  ← 新处置生效
```

**推论**：挂起中的信号用的是**解除阻塞那一刻**的处置，不是产生信号那一刻的。

### 2.2 改成"忽略"会冲刷挂起实例

这是 POSIX 3.3.1.3 明确要求的行为，内核在 `do_sigaction()` 里实现（`kernel/signal.c:4164-4181`）：

```c
        *k = *act;
        /*
         * POSIX 3.3.1.3:
         *  "Setting a signal action to SIG_IGN for a signal that is
         *   pending shall cause the pending signal to be discarded,
         *   whether or not it is blocked."
         *
         *  "Setting a signal action to SIG_DFL for a signal that is
         *   pending and whose default action is to ignore the signal
         *   (for example, SIGCHLD), shall cause the pending signal to
         *   be discarded, whether or not it is blocked"
         */
        if (sig_handler_ignored(sig_handler(p, sig), sig)) {
                sigemptyset(&mask);
                sigaddset(&mask, sig);
                flush_sigqueue_mask(&mask, &p->signal->shared_pending);  /* 冲刷共享层 */
                for_each_thread(p, t)
                        flush_sigqueue_mask(&mask, &t->pending);         /* 冲刷每线程私有层 */
        }
```

判定函数 `sig_handler_ignored()`（`:74`）：

```c
static inline bool sig_handler_ignored(void __user *handler, int sig)
{
        /* Is it explicitly or implicitly ignored? */
        return handler == SIG_IGN ||
               (handler == SIG_DFL && sig_kernel_ignore(sig));
}
```

两种情形会触发冲刷：

| 情形 | 例子 |
|------|------|
| **显式忽略** | `sa_handler = SIG_IGN` |
| **隐式忽略**：处置 = `SIG_DFL` 且该信号的默认动作就是忽略 | `SIGCHLD`、`SIGCONT`、`SIGWINCH`、`SIGURG`（`SIG_KERNEL_IGNORE_MASK:433`） |

```c
/* 典型后果：把 SIGCHLD 重置为 SIG_DFL 会丢掉挂起的子进程通知 */
struct sigaction sa = {0};
sa.sa_handler = SIG_DFL;
sigaction(SIGCHLD, &sa, NULL);     /* 挂起的 SIGCHLD 全部被冲掉 */
/* 之后再 waitpid() 仍然能回收——但"通知"没了 */
```

**注意冲刷是"两层全清"**：共享层 `shared_pending` + 每个线程的 `pending` 都被 `flush_sigqueue_mask()` 扫一遍，包括**实时信号排队的那些 `sigqueue` 节点**也一并释放。

### 2.3 反直觉的对称：被阻塞的信号**不会**因为"忽略"而丢弃

`do_sigaction()` 的冲刷只在"处置变成忽略"时发生。而常规发送路径的"忽略短路"对**被阻塞**的信号不生效——看 `sig_ignored()`（`:103`）：

```c
static bool sig_ignored(struct task_struct *t, int sig, bool force)
{
        /*
         * Blocked signals are never ignored, since the
         * signal handler may change by the time it is
         * unblocked.
         */
        if (sigismember(&t->blocked, sig) || sigismember(&t->real_blocked, sig))
                return false;
        ...
        return sig_task_ignored(t, sig, force);
}
```

注释是内核自己写的理由：**"被阻塞的信号永远不算被忽略，因为在解除阻塞之前，处置还可能变"**。

于是形成一组对称规则，记牢这四条就够了：

| 操作 | 挂起实例的下场 |
|------|----------------|
| 阻塞中，处置 = `SIG_IGN` | **保留**（不算忽略，等解除阻塞时再看） |
| 处置**改成** `SIG_IGN` | **冲刷丢弃**（POSIX 3.3.1.3） |
| 处置**改成** `SIG_DFL` 且默认忽略（如 SIGCHLD） | **冲刷丢弃** |
| 处置**改成** `SIG_DFL` 且默认终止（如 SIGTERM） | **保留**（解除阻塞时会真的终止进程） |

## 三、同号多次产生：为什么标准信号"丢"

```c
/* kernel/signal.c:1079 */
static inline bool legacy_queue(struct sigpending *signals, int sig)
{
        return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
}
```

```c
/* kernel/signal.c:1104 */
        result = TRACE_SIGNAL_ALREADY_PENDING;
        if (legacy_queue(pending, sig))
                goto ret;          /* ← 直接丢弃，不入队 */
```

```
标准信号：位图（1 bit / 信号）

  pending.signal:  ...[SIGUSR1]=1...
                        ▲
                        └── 第二次 SIGUSR1 到来 → legacy_queue() 为真 → goto ret（丢弃）

实时信号：链表（每实例一个 sigqueue 节点）

  pending.list:  [SIGRTMIN+0 #1] → [SIGRTMIN+0 #2] → [SIGRTMIN+0 #3] → ...
                        └── list_add_tail() 追加，__dequeue_signal() 从头取 → FIFO
```

**所以"挂起"对两类信号含义不同**：

| | 标准信号 | 实时信号 |
|--|----------|----------|
| 挂起 3 次，解除阻塞后递送几次 | **1 次** | **3 次**（FIFO） |
| 携带的 `siginfo` | 只有第一次的 | 每次各自的 |
| 超限行为 | 静默丢弃 | `sigqueue()` 返回 `-1 / EAGAIN` |

> 经典事故：`SIGCHLD` 不排队。父进程正在处理一个子进程退出时，另外两个子进程也退出了 → 三个 `SIGCHLD` 塌缩成一个 → 只 `waitpid()` 一次 → **剩下两个变僵尸**。正确写法见 [Ch26](../../chapter-26-monitoring-child-processes/README.md)：`while (waitpid(-1, NULL, WNOHANG) > 0) ;`。

## 四、`SIGKILL` / `SIGSTOP`：三道防线

内核用 `SIG_KERNEL_ONLY_MASK`（`include/linux/signal.h:418`）标记这两个信号，注释写的是 **"action is always, not just default"**（`kernel/signal.c:339-401` 的表头注释）——即**默认动作就是唯一动作，不可改**。

| 干预手段 | 结果 | 源码位置 |
|----------|------|----------|
| 改处置（`sigaction`/`signal`） | **`-EINVAL` 失败** | `do_sigaction():4129`：`if (!valid_signal(sig) \|\| sig < 1 \|\| (act && sig_kernel_only(sig))) return -EINVAL;` |
| 阻塞（`sigprocmask`） | 静默剔除，不进掩码 | `sigprocmask()` 路径 → `set_current_blocked()` 剔除 KILL/STOP |
| handler 期间用 `sa_mask` 屏蔽 | 静默剔除 | `do_sigaction():4161`：`sigdelsetmask(&act->sa.sa_mask, sigmask(SIGKILL) \| sigmask(SIGSTOP));` |
| 设为 `SIG_IGN` | 同"改处置"，`-EINVAL` | 同上 |

**唯一能躲过 `SIGKILL` 的进程**：

```c
/* kernel/signal.c:81 */
static bool sig_task_ignored(struct task_struct *t, int sig, bool force)
{
        /* SIGKILL and SIGSTOP may not be sent to the global init */
        if (unlikely(is_global_init(t) && sig_kernel_only(sig)))
                return true;
        ...
}
```

- **PID 1（全局 init）**：内核直接拒绝向它投递 `SIGKILL`/`SIGSTOP`。容器内的 PID 1 在**非初始 PID namespace** 中同样受此保护（这就是为什么 `docker kill` 有时候"杀不掉"容器主进程，得用 `docker kill -s KILL` 配合，或者进程自己不响应 `SIGTERM`）。
- **内核线程**：可以阻塞 `SIGKILL`（注释在 `kernel/signal.c:3086-3093`）——因为内核线程不返回用户态，没有"递送时机"。用户进程没有这个特权。
- **不可中断睡眠（`TASK_UNINTERRUPTIBLE`）中的进程**：信号已经挂上了，但要等它从 D 状态出来才会被处理。下一节 [22.3](22.3-interruptible-and-uninterruptible-proces.md) 详述。

## 五、停止信号与 `SIGCONT` 的互相抵消

作业控制相关的一组特殊规则（内核权威注释在 `kernel/signal.c:393-400`，判据宏 `SIG_KERNEL_STOP_MASK:421`）：

```c
#define SIG_KERNEL_STOP_MASK (\
        rt_sigmask(SIGSTOP)   |  rt_sigmask(SIGTSTP)   | \
        rt_sigmask(SIGTTIN)   |  rt_sigmask(SIGTTOU)   )
```

| 规则 | 说明 |
|------|------|
| **停止信号互相重叠** | 多个 stop 信号挂起，只生效一次；进程被 stop 后，挂起的 stop 信号被清除 |
| **`SIGCONT` 抵消挂起的 stop** | 发 `SIGCONT` 会先清掉挂起的停止信号，然后才恢复运行 |
| **stop 抵消挂起的 `SIGCONT`** | 反之亦然：收到 stop 时，挂起的 `SIGCONT` 被清除 |
| **`SIGCONT` 总是恢复运行** | 即使被捕获/忽略，其"恢复被停止进程"的副作用仍然发生（这是 `(+)` 类注释的语义） |
| **`SIGKILL` 压倒 stop** | 被 stop 的进程收到 `SIGKILL` 立即死亡：`signal_wake_up():450` 里 `fatal` 为真时清掉 `JOBCTL_STOPPED \| JOBCTL_TRACED` |

内核为此专设了一个 jobctl 标志位（`dequeue_signal():681-695`）：

```c
        if (unlikely(sig_kernel_stop(signr))) {
                /*
                 * Set a marker that we have dequeued a stop signal.  Our
                 * caller might release the siglock and then the pending
                 * stop signal it is about to process is no longer in the
                 * pending bitmasks, but must still be cleared by a SIGCONT
                 * (and overruled by a SIGKILL). ...
                 */
                current->jobctl |= JOBCTL_STOP_DEQUEUED;
        }
```

为什么要这个标志？因为停止信号一旦出队，它**就从 pending 位图里消失了**，但语义上"我还在处理一个停止事件"必须被记住——否则紧接着来的 `SIGCONT` 就找不到要清除的对象了。这是一个典型的"位图状态不足以表达语义，需要额外状态位"的例子。

```
时序示意

  [运行中] ──SIGSTOP──→ [停止] ──SIGCONT──→ [运行中]
                          │
                          └── 期间到达的其他信号（除 SIGKILL）保持挂起，不递送
                              直到 SIGCONT 恢复运行后才处理
```

## 六、多线程下的三个作用域

这一节的特殊情况大多源于"三套状态的作用域不同"，汇总一次：

| 状态 | 存放位置 | 作用域 | 后果 |
|------|----------|--------|------|
| **阻塞掩码** | `task_struct.blocked` | **线程私有** | 一个线程阻塞 SIGUSR1，不影响同进程其他线程 |
| **处置** | `sighand_struct.action[]` | **进程共享**（所有线程同一份） | 任一线程改处置，全进程生效 |
| **挂起集合** | `task_struct.pending`（私有）+ `signal_struct.shared_pending`（共享） | **两层** | `kill()` → 共享层，任意线程可取；`tgkill()` → 私有层，只有目标线程可取 |
| **备用信号栈** | `task_struct.sas_ss_*` | **线程私有** | 每个线程都得各自 `sigaltstack()` |

**由此产生的一个典型"特殊情况"**：多线程程序里用 `kill(getpid(), sig)` 发信号，哪个线程的 handler 会跑？

→ **任意一个没有阻塞该信号的线程**，内核挑选顺序不确定。这也是为什么多线程信号处理的推荐模型是"**所有线程先阻塞，专用线程 `sigwaitinfo()` 消费**"（见 [22.10](22.10-synchronously-waiting-for-a-signal.md)）。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 依赖递送顺序的代码在移植到非 Linux（或不同 libc）时会静默错乱——**顺序不是 POSIX 保证**。嵌入式长期维护的固件尤其要避免"先 SIGUSR1 后 SIGUSR2 代表状态机推进"这类设计。`SIGCHLD` 不排队导致僵尸进程，是长时间运行的嵌入式守护进程最典型的资源泄漏源 |
| HFT | ① **不要设计依赖信号顺序的控制流**——把顺序编码进 `sigqueue` 的 `sigval` 或用 eventfd 计数器；② 多线程策略进程必须用"全线程阻塞 + 专用线程 `sigwaitinfo`"的模型，否则信号可能打断**正在下单的热路径线程**，把 async-signal-safe 约束强加给业务逻辑；③ 被 stop（`SIGSTOP`）的进程**不处理任何信号**——如果运维用 `kill -STOP` 做"暂停交易"，要清楚行情会继续积压，恢复瞬间可能有大量超时单 |

## 代码示例

### 示例 1：验证"小号优先"与"同步信号插队"

```c
/* order_demo.c —— 观察多信号挂起时的递送顺序
 * 编译: gcc -O0 -g -o order_demo order_demo.c
 * 运行: ./order_demo */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>

static void h(int sig)
{
    /* 严格 async-signal-safe：只用 write(2)，不用 printf/snprintf（会 malloc / 加锁） */
    const char *name = NULL;
    switch (sig) {
    case SIGINT:  name = "SIGINT(2) ";   break;
    case SIGUSR1: name = "SIGUSR1(10)";  break;
    case SIGUSR2: name = "SIGUSR2(12)";  break;
    case SIGALRM: name = "SIGALRM(14)";  break;
    case SIGTERM: name = "SIGTERM(15)";  break;
    default:      name = "other      ";  break;
    }
    write(STDOUT_FILENO, "  <- 递送: ", 12);
    write(STDOUT_FILENO, name, 11);
    write(STDOUT_FILENO, "\n", 1);
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = h;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                    /* 注意：不加 SA_RESTART / SA_NODEFER */

    /* 给一批信号装同一个 handler */
    int sigs[] = { SIGUSR1, SIGUSR2, SIGTERM, SIGINT, SIGALRM, SIGCHLD };
    for (unsigned i = 0; i < sizeof(sigs)/sizeof(sigs[0]); i++)
        sigaction(sigs[i], &sa, NULL);

    /* 全部阻塞 */
    sigset_t all, old;
    sigfillset(&all);
    sigprocmask(SIG_SETMASK, &all, &old);

    printf("按降序发送: SIGALRM(14) SIGTERM(15) SIGUSR2(12) SIGUSR1(10) SIGINT(2)\n");
    /* 故意乱序发送，看内核是否按编号升序递送 */
    raise(SIGALRM);   /* 14 */
    raise(SIGTERM);   /* 15 —— 注意它是默认终止，但装了 handler 所以不会死 */
    raise(SIGUSR2);   /* 12 */
    raise(SIGUSR1);   /* 10 */
    raise(SIGINT);    /*  2 */

    /* 一次性解除阻塞 */
    printf("解除阻塞，观察顺序:\n");
    fflush(stdout);
    sigset_t empty;
    sigemptyset(&empty);
    sigsuspend(&empty);                 /* 原子地放行 + 等待 */

    /* 只会递送一个（sigsuspend 跑完 handler 就返回），
     * 剩下的仍在 pending —— 用循环把它们逐个取出 */
    for (int i = 0; i < 4; i++)
        sigsuspend(&empty);

    sigprocmask(SIG_SETMASK, &old, NULL);
    printf("完成\n");
    return 0;
}
```

预期输出（Linux，小号优先）：

```
按降序发送: SIGALRM(14) SIGTERM(15) SIGUSR2(12) SIGUSR1(10) SIGINT(2)
解除阻塞，观察顺序:
  <- 递送: 2      (SIGINT)
  <- 递送: 10     (SIGUSR1)
  <- 递送: 12     (SIGUSR2)
  <- 递送: 14     (SIGALRM)
  <- 递送: 15     (SIGTERM)
完成
```

> 注意 `SIGCHLD` 虽然也装了 handler，但没发送，不参与。另外如果你在 `sa_mask` 里加了别的信号，递送顺序会因为"handler 期间自动阻塞"而变化。

### 示例 2：验证"改成 SIG_IGN 会冲刷挂起实例"

```c
/* flush_demo.c —— POSIX 3.3.1.3：设置 SIG_IGN 会丢弃挂起信号
 * 编译: gcc -O0 -g -o flush_demo flush_demo.c */
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    sigset_t blk, pend;

    sigemptyset(&blk);
    sigaddset(&blk, SIGUSR1);
    sigprocmask(SIG_BLOCK, &blk, NULL);

    raise(SIGUSR1);                     /* 挂起 */

    sigpending(&pend);
    printf("① 挂起中? %s\n", sigismember(&pend, SIGUSR1) ? "是" : "否");

    /* 改成 SIG_IGN —— 触发 do_sigaction():4175 的 flush_sigqueue_mask() */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_IGN;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);

    sigpending(&pend);
    printf("② 设为 SIG_IGN 后还挂起吗? %s   ← 已被冲刷\n",
           sigismember(&pend, SIGUSR1) ? "是" : "否");

    /* 对照组：改成 SIG_DFL（SIGUSR1 默认动作是终止，不算 ignore） */
    raise(SIGUSR2);                     /* 用 SIGUSR2 做对照 */
    sigset_t blk2;
    sigemptyset(&blk2);
    sigaddset(&blk2, SIGUSR2);
    sigprocmask(SIG_BLOCK, &blk2, NULL);
    raise(SIGUSR2);

    struct sigaction sa2 = {0};
    sa2.sa_handler = SIG_DFL;           /* SIGUSR2 默认动作 = 终止，不触发冲刷 */
    sigemptyset(&sa2.sa_mask);
    sigaction(SIGUSR2, &sa2, NULL);

    sigpending(&pend);
    printf("③ SIGUSR2 设为 SIG_DFL(默认终止) 后还挂起吗? %s  ← 未被冲刷\n",
           sigismember(&pend, SIGUSR2) ? "是" : "否");

    /* 千万别解除 SIGUSR2 的阻塞 —— 会真的终止进程 */
    printf("（不解除 SIGUSR2 阻塞，否则进程会被默认动作杀掉）\n");
    return 0;
}
```

预期输出：

```
① 挂起中? 是
② 设为 SIG_IGN 后还挂起吗? 否   ← 已被冲刷
③ SIGUSR2 设为 SIG_DFL(默认终止) 后还挂起吗? 是  ← 未被冲刷
```

**对照组的意义**：改成 `SIG_DFL` **不一定**冲刷——只有默认动作是"忽略"的信号（`SIGCHLD`/`SIGCONT`/`SIGWINCH`/`SIGURG`）才会。`SIGUSR2` 默认动作是终止，所以挂起实例保留，解除阻塞时进程会**真的死掉**。这个区别在信号恢复逻辑里非常重要。

## 代码自测

<details>
<summary><b>问 1：</b>SIGSEGV 和 SIGTERM 同时挂起，哪个先递送？为什么内核要这样设计？</summary>

**`SIGSEGV`(11) 先**，尽管它的编号比 `SIGTERM`(15) 小这一点本身也符合"小号优先"——真正的判据是它属于 `SYNCHRONOUS_MASK`。

```c
/* kernel/signal.c:205 */
#define SYNCHRONOUS_MASK \
        (sigmask(SIGSEGV) | sigmask(SIGBUS) | sigmask(SIGILL) | \
         sigmask(SIGTRAP) | sigmask(SIGFPE) | sigmask(SIGSYS))

/* next_signal():221 —— "Handle the first word specially" */
        x = *s &~ *m;
        if (x) {
                if (x & SYNCHRONOUS_MASK)
                        x &= SYNCHRONOUS_MASK;      /* ← 屏蔽掉所有非同步信号 */
                sig = ffz(~x) + 1;
                return sig;
        }
```

**设计理由**（`get_signal():2763-2767` 的内核注释）：

> *"Signals generated by the execution of an instruction need to be delivered before any other pending signals so that the instruction pointer in the signal stack frame points to the faulting instruction."*

同步故障信号是由**某一条具体指令**触发的，它携带的 `si_addr` 和 sigframe 里的 PC 必须指向那条指令。如果先递送了别的信号（跑了别的 handler，改了栈和寄存器），等轮到 `SIGSEGV` 时 PC 早就不是现场了，`si_addr` 与栈回溯就对不上——**诊断价值归零**。

顺带构造一个反例体会这条规则：假设 `SIGUSR1`(10) 和 `SIGSEGV`(11) 同时挂起。按"小号优先"应该是 SIGUSR1 先，但因为 SIGSEGV 在 `SYNCHRONOUS_MASK` 里，**结果是 SIGSEGV 先**。

</details>

<details>
<summary><b>问 2：</b>信号被阻塞时把它的处置从 handler_A 改成 handler_B，解除阻塞后跑哪个？为什么？</summary>

**跑 `handler_B`**（新的那个）。

原因在 `get_signal()` 的实现细节：处置是在**信号出队、准备递送的那一刻**才从 `sighand->action[]` 里读出来的，而不是在信号进入 pending 集合时锁定。

```c
/* kernel/signal.c:2785 */
        ka = &sighand->action[signr-1];          /* ← 此刻才读 */

        if (ka->sa.sa_handler == SIG_IGN) continue;
        if (ka->sa.sa_handler != SIG_DFL) {
                ksig->ka = *ka;                   /* 拷一份给递送路径用 */
                if (ka->sa.sa_flags & SA_ONESHOT)
                        ka->sa.sa_handler = SIG_DFL;
                break;
        }
```

内核在 `sig_ignored():103` 里也把这个设计意图写成了注释：

```c
/*
 * Blocked signals are never ignored, since the
 * signal handler may change by the time it is
 * unblocked.
 */
```

也就是说——**"挂起"只冻结了"有一个信号没处理"这件事，没有冻结"怎么处理"**。这是信号语义里一个容易踩的点：

```c
sigprocmask(SIG_BLOCK, &{SIGUSR1}, NULL);
raise(SIGUSR1);                          /* 挂起，处置 = handler_A */
sigaction(SIGUSR1, &sa_B, NULL);         /* 改成 handler_B */
sigprocmask(SIG_UNBLOCK, &{SIGUSR1}, NULL);
/* → 跑 handler_B，不是 handler_A */
```

**实践意义**：在做"延迟处理"模式（先阻塞攒着，主循环空闲时统一放行）时，如果你在攒的期间动态改了处置，实际行为会跟着改。这既是一个坑，也是一个可用的技巧——但要**明确知道**你在依赖这个语义。

</details>

<details>
<summary><b>问 3：</b>把 SIGCHLD 的处置改回 SIG_DFL，挂起的 SIGCHLD 会怎样？如果改成 SIG_IGN 呢？</summary>

**两者都会冲刷掉挂起的 SIGCHLD**，但原因不同——而且这个"两者都冲"的现象只对默认动作为"忽略"的信号成立。

`do_sigaction():4175` 的判定：

```c
if (sig_handler_ignored(sig_handler(p, sig), sig)) {
        sigemptyset(&mask);
        sigaddset(&mask, sig);
        flush_sigqueue_mask(&mask, &p->signal->shared_pending);
        for_each_thread(p, t)
                flush_sigqueue_mask(&mask, &t->pending);
}
```

而 `sig_handler_ignored():74`：

```c
return handler == SIG_IGN ||
       (handler == SIG_DFL && sig_kernel_ignore(sig));
```

对 `SIGCHLD`：它在 `SIG_KERNEL_IGNORE_MASK:433` 里（`SIGCONT | SIGCHLD | SIGWINCH | SIGURG`），所以：

| 新处置 | `sig_kernel_ignore(SIGCHLD)` | 冲刷？ |
|--------|------------------------------|--------|
| `SIG_IGN` | 短路，直接 true | ✅ 冲刷 |
| `SIG_DFL` | true | ✅ 冲刷（"隐式忽略"） |
| 某个 handler | false | ❌ 保留 |

**换 `SIGUSR2` 就不同**——它默认动作是终止，不在忽略名单里：

| 新处置 | 冲刷？ |
|--------|--------|
| `SIG_IGN` | ✅ 冲刷 |
| `SIG_DFL` | ❌ **保留** → 解除阻塞时进程真的被杀 |

**实践陷阱**：

```c
/* 错误：想"恢复默认"，结果丢掉了所有挂起的子进程退出通知 */
sa.sa_handler = SIG_DFL;
sigaction(SIGCHLD, &sa, NULL);

/* 但由于 SIGCHLD 只是"通知"，真正的子进程状态还在内核里，
 * waitpid() 依然能回收 —— 所以这里丢的是"通知"，不是"子进程"
 *
 * 正确姿势：如果要清理，用 while (waitpid(-1, NULL, WNOHANG) > 0) ; 兜底 */
```

同理，**再收到新的 SIGCHLD 时仍会挂起**——冲刷只发生在调用 `sigaction()` 的那一刻，不是永久的。

</details>

<details>
<summary><b>问 4：</b>为什么 SIGKILL 无法被捕获或阻塞？内核具体在哪几处挡住？</summary>

三处防线，每处都是**静默或报错地拒绝**，没有任何绕过手段（用户态）：

**防线 1 —— 改处置直接报错**

```c
/* do_sigaction():4129 */
        if (!valid_signal(sig) || sig < 1 || (act && sig_kernel_only(sig)))
                return -EINVAL;
```

`SIG_KERNEL_ONLY_MASK = rt_sigmask(SIGKILL) | rt_sigmask(SIGSTOP)`（`include/linux/signal.h:418`）。所以 `signal(SIGKILL, handler)` 和 `sigaction(SIGKILL, ...)` 都返回 `-1 / EINVAL`。

**防线 2 —— 阻塞请求被静默剔除**

`sigprocmask()` → `set_current_blocked()` 会剔除 `SIGKILL`/`SIGSTOP` 位。你"以为"阻塞了，调用 `sigpending()` 检查一下就会发现它根本不在掩码里——**连错误都不报**，这是最容易踩的一处。

**防线 3 —— handler 期间的 `sa_mask` 也被剔除**

```c
/* do_sigaction():4161 */
        sigdelsetmask(&act->sa.sa_mask,
                      sigmask(SIGKILL) | sigmask(SIGSTOP));
```

所以想靠 `sa_mask = 全填满` 在 handler 里屏蔽 `SIGKILL`，也是无效的。

**为什么这样设计**（`kernel/signal.c:339-401` 表头注释的 `(+)` 标记）：

> 对 `SIGKILL`/`SIGSTOP`，"action is **always**, not just default"。

语义上的必要性很直接：`SIGKILL` 是系统管理员的**最后手段**——如果它可以被捕获或忽略，一个恶意/失控的进程就能让自己变得无法杀死，系统就失去了对它的最终控制权。`SIGSTOP` 同理，它是调试器和作业控制的底层原语。

**三个"例外"（都不是真的漏洞）**：

1. **全局 init（PID 1）**：`sig_task_ignored():88` 直接返回 true，内核拒绝投递。
2. **内核线程**：可以阻塞 `SIGKILL`——因为它们不返回用户态，压根没有"递送时机"（注释见 `kernel/signal.c:3086-3093`）。
3. **`TASK_UNINTERRUPTIBLE`（D 状态）**：信号确实挂上了，但进程不会醒来处理。这就是下一节 [22.3](22.3-interruptible-and-uninterruptible-proces.md) 的主题——也是"为什么 `kill -9` 杀不死一个卡在 NFS 上的进程"的答案。

</details>

<details>
<summary><b>问 5：</b>多线程程序里，主线程阻塞了 SIGUSR1，另一个线程没有。用 kill(getpid(), SIGUSR1) 发送，会发生什么？</summary>

**未阻塞的那个线程会跑 handler**。内核在两个层次上做出选择：

**层次 1：信号落在哪一层 pending**

`kill()` 发的是**进程级**信号 → 进入 `signal_struct.shared_pending`（共享层）。

**层次 2：哪个线程去取**

在 `__send_signal_locked()` → `signal_wake_up()` 里，内核唤醒某个线程；最终由**从内核态返回用户态的那个线程**执行 `get_signal()` → `dequeue_signal()`。

`dequeue_signal():635` 的注释点明了规则：

```c
        /* We only dequeue private signals from ourselves, we don't let
         * signalfd steal them
         */
        *type = PIDTYPE_PID;
        signr = __dequeue_signal(&tsk->pending, mask, info, &resched_timer);
        if (!signr) {
                *type = PIDTYPE_TGID;
                signr = __dequeue_signal(&tsk->signal->shared_pending, ...);
        }
```

即：**任何线程**都能从共享层取信号，前提是它自己没有阻塞这个信号（`next_signal()` 用 `mask` 参数过滤，这里的 mask 就是该线程自己的 `current->blocked`）。

所以：

```
线程 A（阻塞 SIGUSR1）  ─┐
线程 B（未阻塞）        ─┼─→ kill(getpid(), SIGUSR1) → shared_pending
线程 C（阻塞 SIGUSR1）  ─┘                                  │
                                                            ▼
                        内核唤醒一个能处理它的线程 → 只有 B 合格 → B 跑 handler
```

**关键风险**：如果此刻 B 正在**下单热路径**上，它的关键区段会被 handler 打断，于是业务逻辑被迫遵守 async-signal-safe 约束——这在 HFT 里是不可接受的。而且**哪个线程会跑 handler 是不确定的**（取决于调度），一旦 B 阻塞了或正在睡眠，可能换成别的线程。

**推荐模型**（[22.10](22.10-synchronously-waiting-for-a-signal.md) 详述）：

```
main():
    sigset_t set; sigaddset(&set, SIGUSR1); ...
    pthread_sigmask(SIG_BLOCK, &set, NULL);     ← 必须在创建线程【之前】阻塞
                                                   这样新线程继承掩码，全员阻塞
    pthread_create(&tid, NULL, sig_thread, NULL); ← 专用线程

sig_thread():
    for (;;) {
        sigwaitinfo(&set, &info);               ← 同步取，不跑 handler
        /* 这里可以随意 malloc / printf / 加锁 */
    }
```

这样信号**永远不会被递送到热路径线程**，异步性被彻底消除——handler 一次也不会跑。

**一句话总结**：`kill()` 到进程级信号时，"谁跑 handler"由内核调度决定，**不可控**。想要可控，就必须先全员阻塞 + 专用线程同步等待。

</details>
