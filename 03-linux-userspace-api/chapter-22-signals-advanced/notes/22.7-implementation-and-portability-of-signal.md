# 22.7 `signal()` 的实现与可移植性

## 本节讲什么

1. `signal()` 为什么**绝对不能用在生产代码**——不是风格问题，是语义不确定
2. Linux 的 `signal()` 有**两套实现**（内核系统调用 vs glibc 包装），行为完全相反
3. `sigaction()` 是唯一可移植的答案，以及迁移时的对应关系

---

## 一、历史根源：V7 → System V vs BSD

Unix V7（1979）的 `signal()` 有两个致命设计缺陷，后来两大流派给出了**相反**的修复：

```
                  Unix V7 原始 signal()
                  ┌──────────────────────────────┐
                  │ ① handler 跑之前，处置被重置为  │
                  │    SIG_DFL                    │
                  │ ② handler 期间【不】自动阻塞   │
                  │    该信号自己                  │
                  │ ③ 被信号打断的系统调用返回     │
                  │    EINTR（而不是自动重启）      │
                  └───────────────┬──────────────┘
                                  │
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
    BSD 4.3 修复（BSD 语义）              System V 沿用 V7（SysV 语义）
    ┌────────────────────────┐            ┌────────────────────────┐
    │ ① 处置【保持】不重置     │            │ ① 处置【重置】为 SIG_DFL │
    │ ② handler 期间【自动】   │            │ ② handler 期间【不】阻塞 │
    │    阻塞该信号（防递归）  │            │    该信号（可递归）      │
    │ ③ 被中断的系统调用       │            │ ③ 被中断的系统调用返回   │
    │    【自动重启】          │            │    EINTR                │
    └────────────────────────┘            └────────────────────────┘
              │                                       │
              └─────────── 互相不兼容 ────────────────┘
                             │
                             ▼
                  同一份代码在两种系统上行为不同
                  → 这就是"不可移植"的根源
```

**V7 的两个缺陷有多严重？**

缺陷 ①（重置）造成经典的**"不可靠信号"竞态**：

```
handler 装好（会重置）
    ↓
信号到达 → 内核把处置重置为 SIG_DFL → 跑 handler
    ↓
    ┌─────────────────────── 竞态窗口 ───────────────────────┐
    │ 如果此刻【又来一个】同样的信号：                          │
    │   处置已经是 SIG_DFL → 默认动作 → 进程【直接死亡】        │
    └───────────────────────────────────────────────────────┘
    ↓
handler 跑完（但进程可能已经在窗口里死了）
```

正确写法（V7 时代）必须**在 handler 第一件事就重装自己**：

```c
void handler(int sig)
{
    signal(sig, handler);      /* ← 重装！但重装之前仍有窗口 */
    ...
}
```

即使这样，**"重置 → 重装"之间仍有窗口**，只是缩小了。这个窗口在高负载或信号密集时**必然**被命中——这就是早期 Unix "信号不可靠"的由来。

缺陷 ②（不自动阻塞）导致**递归 handler**：handler 跑到一半，同号信号又来 → 再次进入 handler → 如果 handler 里有非重入的数据结构，直接损坏。

## 二、Linux 的两套 `signal()`，行为相反

这是本节最反直觉、也最实用的事实：**Linux 有两个 `signal()`，语义相反。**

### 2.1 内核系统调用：System V 语义

```c
/* kernel/signal.c:4622 */
/*
 * For backwards compatibility.  Functionality superseded by sigaction.
 */
SYSCALL_DEFINE2(signal, int, sig, __sighandler_t, handler)
{
        struct k_sigaction new_sa, old_sa;
        int ret;

        new_sa.sa.sa_handler = handler;
        new_sa.sa.sa_flags = SA_ONESHOT | SA_NOMASK;      /* :4628 ← 硬编码！ */
        sigemptyset(&new_sa.sa.sa_mask);

        ret = do_sigaction(sig, &new_sa, &old_sa);

        return ret ? ret : (unsigned long)old_sa.sa.sa_handler;
}
#endif /* __ARCH_WANT_SYS_SIGNAL */
```

两个内部标志别名（`include/uapi/asm-generic/signal-defs.h`）：

| 内部名 | 用户可见名 | 值 | 效果 |
|--------|-----------|-----|------|
| `SA_ONESHOT` | `SA_RESETHAND` | `0x80000000` | 递送后把处置重置为 `SIG_DFL` |
| `SA_NOMASK` | `SA_NODEFER` | `0x40000000` | handler 期间**不**阻塞该信号自己 |

内核侧的对应实现：

```c
/* get_signal():2796 —— SA_ONESHOT：跑之前就重置 */
                if (ka->sa.sa_flags & SA_ONESHOT)
                        ka->sa.sa_handler = SIG_DFL;

/* signal_delivered():2926 —— SA_NODEFER：不自动阻塞自己 */
        sigorsets(&blocked, &current->blocked, &ksig->ka.sa.sa_mask);
        if (!(ksig->ka.sa.sa_flags & SA_NODEFER))
                sigaddset(&blocked, ksig->sig);
        set_current_blocked(&blocked);
```

**所以裸 `sys_signal` 系统调用 = System V 语义 = 重置 + 不阻塞 + 不重启**。

### 2.2 glibc 包装函数：BSD 语义

glibc 的 `signal()` **不走这个系统调用**，而是包装 `sigaction()`：

```c
/* glibc 内部（示意） */
__sighandler_t signal(int sig, __sighandler_t handler)
{
    struct sigaction act, oact;

    act.sa_handler = handler;
    __sigemptyset(&act.sa_mask);
    act.sa_flags = SA_RESTART;        /* ← 只有这一个标志 */

    if (__sigaction(sig, &act, &oact) < 0)
        return SIG_ERR;
    return oact.sa_handler;
}
```

`man 2 signal` 的权威表述：

> **The situation on Linux is as follows:**
> * The kernel's `signal()` system call provides **System V** semantics.
> * By default, in glibc 2 and later, the `signal()` wrapper function **does not invoke the kernel system call**. Instead, it calls `sigaction(2)` using flags that supply **BSD** semantics. This default behavior is provided as long as a suitable feature test macro is defined: `_BSD_SOURCE` on glibc 2.19 and earlier or `_DEFAULT_SOURCE` in glibc 2.19 and later.
> * If such a feature test macro is not defined, then `signal()` provides **System V** semantics.

**对比表**：

| 行为 | 内核 `sys_signal` | glibc `signal()`（默认） |
|------|-------------------|--------------------------|
| 底层实现 | `do_sigaction(SA_ONESHOT\|SA_NOMASK)` | `sigaction(SA_RESTART)` |
| handler 跑后处置 | **重置**为 `SIG_DFL` | **保持** |
| handler 期间阻塞自己？ | ❌ **不阻塞**（`SA_NOMASK`） | ✅ **阻塞**（默认行为） |
| 被中断的系统调用 | 返回 `EINTR` | ✅ **自动重启**（`SA_RESTART`） |
| 语义归属 | System V | BSD |

> **注意第二行和第三行的组合**：裸系统调用是"重置 + 不自动阻塞"——这是**最坏的组合**：既要在 handler 里重装（有竞态窗口），又要自己防递归。

### 2.3 怎么知道你用的是哪一套

```bash
# 看符号解析
cat > t.c <<'EOF'
#include <signal.h>
#include <stdio.h>
int main(void) { signal(SIGUSR1, SIG_IGN); return 0; }
EOF
gcc -o t t.c
strace -e trace=rt_sigaction,signal ./t
# → rt_sigaction(SIGUSR1, {SIG_IGN, [], SA_RESTART}, ...)   ← glibc 包装，BSD 语义
```

**强制使用 SysV 语义**（几乎没人这么干，但要知道存在）：

```c
#define _GNU_SOURCE        /* 不行 —— 这会定义 _DEFAULT_SOURCE */
/* 正确：显式不定义 _DEFAULT_SOURCE，或者： */
#undef  _DEFAULT_SOURCE
#include <signal.h>
```

实操上，`-std=c99`（严格 ANSI，不定义任何 `_DEFAULT_SOURCE`）编译时 glibc 会提供 **SysV 语义**。这就是为什么"换个编译标准，程序行为就变了"这类诡异 bug 会存在。

## 三、`signal()` 的六个硬伤

除了语义不确定，`signal()` 还有这些**结构性缺陷**：

| # | 缺陷 | `sigaction()` 怎么解决 |
|---|------|------------------------|
| 1 | **语义不确定**（BSD vs SysV，取决于 libc 和 feature macro） | 语义完全由 `sa_flags` 显式指定 |
| 2 | **不能设置 `sa_mask`**——无法在 handler 期间屏蔽其他信号 | `sa.sa_mask` 精确控制 |
| 3 | **不能设置 `SA_SIGINFO`**——拿不到 `siginfo_t`（无 `si_code`/`si_addr`/`si_pid`） | `sa_flags \|= SA_SIGINFO` + `sa_sigaction` |
| 4 | **不能控制 `SA_RESTART`**——glibc 版本强制自动重启，无法关闭 | 显式加/不加 `SA_RESTART` |
| 5 | **不能设置 `SA_ONSTACK`**——栈溢出时无法在备用栈上跑 handler | `sa_flags \|= SA_ONSTACK` |
| 6 | **多线程下行为未规定**（POSIX 明确说 unspecified） | `sigaction()` 在多线程下语义明确 |

第 6 条有明确的 POSIX 依据：

> **POSIX.1-2008**: *"The behavior of `signal()` in a multithreaded process is unspecified."*

**另外注意 union 陷阱**（在 `sigaction` 里也有，但 `signal()` 完全无法触及）：`sa_handler` 与 `sa_sigaction` 是同一块内存的 union，绝不能同时赋值。

## 四、迁移对照表

| `signal()` 写法 | 等价的 `sigaction()` |
|-----------------|----------------------|
| `signal(sig, handler)`（glibc/BSD） | `sa.sa_handler = handler; sa.sa_flags = SA_RESTART;` |
| `signal(sig, handler)`（SysV/裸系统调用） | `sa.sa_handler = handler; sa.sa_flags = SA_RESETHAND \| SA_NODEFER;` |
| `signal(sig, SIG_IGN)` | `sa.sa_handler = SIG_IGN; sa.sa_flags = 0;` |
| `signal(sig, SIG_DFL)` | `sa.sa_handler = SIG_DFL; sa.sa_flags = 0;` |
| 无法表达 | `sa.sa_mask`（handler 期间额外屏蔽） |
| 无法表达 | `SA_SIGINFO`（拿 `siginfo_t`） |
| 无法表达 | `SA_ONSTACK`（备用栈） |
| 无法表达 | `SA_NOCLDSTOP` / `SA_NOCLDWAIT`（`SIGCHLD` 优化） |

**标准迁移模板**（这是本节唯一需要背下来的代码）：

```c
#include <signal.h>
#include <string.h>          /* memset */

int install_handler(int sig, void (*handler)(int))
{
    struct sigaction sa;

    memset(&sa, 0, sizeof(sa));          /* ① 必须清零：避免栈垃圾 */
    sa.sa_handler = handler;             /* ② 只设 sa_handler（不要同时设 sa_sigaction） */
    sigemptyset(&sa.sa_mask);            /* ③ 显式初始化掩码（内核会自动加 sig 自己） */
    sa.sa_flags = SA_RESTART;            /* ④ 显式指定，不依赖默认 */

    return sigaction(sig, &sa, NULL);    /* 0 成功 / -1 失败（errno） */
}
```

**四条"必须/禁止"**：

| | 规则 | 原因 |
|--|------|------|
| ✅ 必须 | `memset(&sa, 0, sizeof(sa))` 或 `= {0}` | 结构体在栈上，未初始化的字段是垃圾 |
| ✅ 必须 | `sigemptyset(&sa.sa_mask)` | 同上；垃圾掩码可能意外屏蔽 `SIGTERM` 等 |
| ✅ 必须 | 显式指定 `sa_flags` | 不依赖默认；默认在不同系统可能不同 |
| ❌ 禁止 | 同时给 `sa_handler` 和 `sa_sigaction` 赋值 | 它们是 **union**，后者覆盖前者 |

## 五、其他可移植性要点

### 5.1 信号编号不可硬编码

```c
#define MY_SIG 34          /* ❌ 换 libc / 换系统就错位 */
#define MY_SIG (SIGRTMIN + 0)   /* ✅ 用宏 */
```

glibc 的 NPTL 内部占用前两个实时信号（32 = `setxid` 同步，33 = 线程取消），所以用户态可见的 `SIGRTMIN` 是 **34**。详见 [Ch20.2](../../chapter-20-signals-fundamentals/notes/20.2-signal-types-and-default-actions.md)。

### 5.2 `SIGCHLD` 的默认动作是"忽略"

这在所有 POSIX 系统上都成立，但很多程序员误以为要显式 `SIG_IGN`：

```c
/* 这两行等价（对 SIGCHLD 而言） */
signal(SIGCHLD, SIG_IGN);                       /* 老写法 */
/* 或 */
sa.sa_handler = SIG_IGN; sigaction(SIGCHLD, &sa, NULL);
```

但注意：**显式 `SIG_IGN` 会让子进程【不产生僵尸】**（内核直接回收），而默认 `SIG_DFL`（也是忽略语义）**会**产生僵尸等待 `wait()`。这是"同为忽略、效果不同"的经典陷阱，详见 [Ch26](../../chapter-26-monitoring-child-processes/README.md)。

### 5.3 `SA_RESTART` 不是万能的

即使设了 `SA_RESTART`，这些系统调用**仍然**返回 `EINTR`（详见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)）：

| 一定返回 `EINTR` | 说明 |
|------------------|------|
| `select()` / `pselect()` | 从不自动重启 |
| `epoll_wait()` / `epoll_pwait()` | 从不自动重启 |
| `poll()` / `ppoll()` | 从不自动重启 |
| `connect()` | 非阻塞 socket 上不重启 |
| `accept()`（部分版本） | 行为因实现而异 |
| `read()` 于 `inotify` fd | 不重启 |
| `sendmsg()`/`recvmsg()` 带超时 | 视超时参数而定 |

**所以：永远显式处理 `EINTR`**，不要指望 `SA_RESTART`。

### 5.4 `sigaction()` 会静默清除未知 flag

```c
/* do_sigaction():4148 */
        /*
         * Clear unknown flag bits in order to allow userspace to detect missing
         * support for flag bits and to allow the kernel to use non-uapi bits
         * internally.
         */
        if (act)
                act->sa.sa_flags &= UAPI_SA_FLAGS;
```

你传进去一个内核不认识的 flag，它**不报错，只是静默清掉**。唯一可靠的验证方式是**读回来比对**：

```c
struct sigaction sa = {0}, verify;
sa.sa_handler = handler;
sa.sa_flags = MY_NEW_FLAG | SA_RESTART;
sigaction(SIGUSR1, &sa, NULL);

sigaction(SIGUSR1, NULL, &verify);        /* 读回内核实际保存的值 */
if (!(verify.sa_flags & MY_NEW_FLAG))
    fprintf(stderr, "内核不支持 MY_NEW_FLAG，已静默丢弃\n");
```

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① 老嵌入式代码库（尤其从 VxWorks / 早期 uClibc 移植来的）大量使用 `signal()`，迁移到 glibc 时必须**逐一替换为 `sigaction()`**——否则"-std=c99 编译后行为就变了"这类诡异 bug 会反复出现。② 交叉编译工具链的 libc 各不相同（uClibc / musl / glibc / newlib），`signal()` 语义差异更大——**统一用 `sigaction()` 是唯一安全选择**。③ 静态检查：在 CI 里 `grep -rn "\bsignal\s*(" src/`，命中即告警 |
| HFT | ① `signal()` 的 `SA_RESETHAND` 竞态在**高信号密度**下必然被命中——交易系统里 `SIGALRM`/`SIGUSR1` 可能每秒数十次，用 `signal()` 装 handler 等于埋一颗定时炸弹。② 无 `SA_SIGINFO` 意味着拿不到 `si_addr`/`si_code`，崩溃现场记录无从谈起——这对事后定责是致命的。③ 无 `SA_ONSTACK` 意味着栈溢出时 SIGSEGV handler 跑不起来，连最后的现场都留不下。④ 结论：**生产代码零 `signal()`**，用统一封装的 `install_handler()`；CI 静态检查拦截 |

## 代码示例

### 示例 1：复现 `SA_RESETHAND` 的竞态

```c
/* reset_race.c —— 演示 System V signal() 的"重置竞态"
 * 编译（BSD 语义，glibc 默认）: gcc -O0 -g -o reset_race reset_race.c
 * 编译（SysV 语义，强制）    : gcc -O0 -g -std=c99 -o reset_race reset_race.c
 * 运行: ./reset_race
 *
 * 关键：用 SA_RESETHAND 显式模拟"信号到达即重置"的行为，
 *       然后在 handler 里 sleep，制造第二个信号落入窗口的机会 */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>

static volatile sig_atomic_t count = 0;

static void handler(int sig)
{
    (void)sig;
    count++;
    const char m[] = "  handler 进入\n";
    write(STDOUT_FILENO, m, sizeof(m) - 1);

    /* 故意慢一点，制造竞态窗口 */
    for (volatile int i = 0; i < 30000000; i++) ;

    const char m2[] = "  handler 退出\n";
    write(STDOUT_FILENO, m2, sizeof(m2) - 1);
}

int main(void)
{
    /* 显式使用 SA_RESETHAND —— 这就是裸 sys_signal / SysV signal() 的行为 */
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESETHAND;        /* ← 递送后立即重置为 SIG_DFL */
    sigaction(SIGUSR1, &sa, NULL);

    printf("pid=%ld\n", (long)getpid());
    printf("处置带 SA_RESETHAND：第一个 SIGUSR1 进入 handler，");
    printf("期间到达的第二个会触发【默认动作 = 终止】\n\n");
    printf("请快速连发两个信号:\n");
    printf("    kill -USR1 %ld ; kill -USR1 %ld\n\n", (long)getpid(), (long)getpid());
    fflush(stdout);

    pause();                            /* 等第一个 */

    printf("pause 返回，count=%d\n", count);
    printf("如果你在 handler 期间发了第二个信号 —— 进程早就被 SIGUSR1 默认动作杀掉了\n");
    printf("根本到不了这一行。\n");

    return 0;
}
```

```bash
# 终端 1
$ ./reset_race
pid=3333
处置带 SA_RESETHAND：第一个 SIGUSR1 进入 handler，期间到达的第二个会触发【默认动作 = 终止】
请快速连发两个信号:
    kill -USR1 3333 ; kill -USR1 3333

# 终端 2 —— 立刻执行
$ kill -USR1 3333 ; kill -USR1 3333

# 终端 1
  handler 进入
User defined signal 1      ← 进程被第二个 SIGUSR1 的默认动作杀死
$ echo $?
138                        # 128 + 10
```

**对照实验**：把 `sa.sa_flags` 改成 `0`（去掉 `SA_RESETHAND`），重复同样的操作：

```bash
  handler 进入
  handler 退出
  handler 进入              ← 第二个排着队，handler 结束后再跑一次
  handler 退出
pause 返回，count=2
```

> 这就是 BSD 修复的价值：**处置保持不重置，且 handler 期间自动阻塞该信号**——第二个信号只是挂起，等 handler 结束后再递送。

### 示例 2：生产级 handler 安装函数（替换所有 `signal()`）

```c
/* sigutil.h / sigutil.c —— 统一封装，禁止直接用 signal()
 * 编译: gcc -O2 -c sigutil.c */
#define _GNU_SOURCE
#include <signal.h>
#include <string.h>
#include <stdio.h>
#include <errno.h>

/* 安装"简单"handler（不需要 siginfo） */
int install_handler(int sig, void (*handler)(int), int restart)
{
    struct sigaction sa;

    if (sig <= 0 || sig >= NSIG) { errno = EINVAL; return -1; }

    memset(&sa, 0, sizeof(sa));              /* ① 清零 */
    sa.sa_handler = handler;                 /* ② 只设 sa_handler */
    sigemptyset(&sa.sa_mask);                /* ③ 显式初始化 */
    sa.sa_flags = restart ? SA_RESTART : 0;  /* ④ 显式指定 */

    return sigaction(sig, &sa, NULL);
}

/* 安装"带 siginfo"的 handler（需要 si_code / si_addr / si_pid） */
int install_siginfo_handler(int sig,
                            void (*handler)(int, siginfo_t *, void *))
{
    struct sigaction sa;

    if (sig <= 0 || sig >= NSIG) { errno = EINVAL; return -1; }

    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = handler;               /* ← 注意是 sa_sigaction，不是 sa_handler！ */
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_RESTART;

    return sigaction(sig, &sa, NULL);
}

/* 安装"崩溃兜底"handler：备用栈 + siginfo + 不自动重启 */
int install_crash_handler(int sig,
                          void (*handler)(int, siginfo_t *, void *),
                          void *altstack, size_t altstack_sz)
{
    stack_t ss;
    struct sigaction sa;

    /* 备用栈：栈溢出时默认栈已不可用，handler 必须在另一块内存上跑 */
    ss.ss_sp    = altstack;
    ss.ss_size  = altstack_sz;
    ss.ss_flags = 0;
    if (sigaltstack(&ss, NULL) == -1)
        return -1;

    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK | SA_NODEFER;

    return sigaction(sig, &sa, NULL);
}

/* 安装后读回验证 —— 内核会【静默清除】不认识的 flag，只能靠读回来发现 */
int verify_flags(int sig, int expected_flags)
{
    struct sigaction cur;
    if (sigaction(sig, NULL, &cur) == -1)
        return -1;
    return (cur.sa_flags & expected_flags) == expected_flags ? 0 : -1;
}
```

使用：

```c
static char g_altstack[SIGSTKSZ * 4];

static void crash(int sig, siginfo_t *si, void *ctx)
{
    (void)ctx;
    /* 记日志（只用 write / backtrace_symbols_fd 等 async-signal-safe 调用） */
    ...
    _exit(128 + sig);      /* 绝不返回 */
}

int main(void)
{
    install_handler(SIGTERM, on_term, 1);                    /* 控制类：SA_RESTART */

    install_crash_handler(SIGBUS,  crash, g_altstack, sizeof(g_altstack));
    install_crash_handler(SIGFPE,  crash, g_altstack, sizeof(g_altstack));
    install_crash_handler(SIGILL,  crash, g_altstack, sizeof(g_altstack));

    /* signal(SIGTERM, on_term);       ❌ 生产代码禁止 */
    ...
}
```

## 代码自测

<details>
<summary><b>问 1：</b>为什么 <code>signal()</code> 不可移植？两个流派的具体差异是什么？</summary>

**根源**：Unix V7 的原始 `signal()` 有两处设计缺陷，System V 和 BSD 给出了**相反**的修复，此后二者再未统一。

| 行为 | BSD 4.3 语义 | System V 语义 |
|------|-------------|---------------|
| handler 跑完后处置 | **保持**（不重置） | **重置**为 `SIG_DFL` |
| handler 期间阻塞该信号自己？ | ✅ **自动阻塞**（防递归） | ❌ **不阻塞**（可递归进入） |
| 被中断的系统调用 | ✅ **自动重启** | 返回 `EINTR` |

**V7 缺陷 ①（重置）造成的竞态**——这是"不可靠信号"的由来：

```
handler 装好（带重置语义）
  ↓
信号到达 → 内核重置处置为 SIG_DFL → 跑 handler
  ↓
  ┌──── 竞态窗口 ────┐
  │ 此刻又来一个同号信号 → 处置已是 SIG_DFL → 默认动作 → 【进程死亡】
  └──────────────────┘
  ↓
handler 跑完
```

V7/SysV 时代的"正确写法"是在 handler 第一件事重装自己：

```c
void handler(int sig)
{
    signal(sig, handler);    /* 重装 —— 但"重置→重装"之间仍有窗口 */
    ...
}
```

窗口只是缩小了，**没有消除**。高信号密度下必然命中。

**V7 缺陷 ②（不自动阻塞）造成的递归**：

```c
static int depth = 0;
void handler(int sig)
{
    depth++;                 /* 非原子：读-改-写 */
    ...
    depth--;
}
/* handler 跑到一半，同号信号又来 → 递归进入 → depth 损坏 */
```

对应到 `sigaction()` 的标志：

| 语义 | 等价的 `sa_flags` |
|------|-------------------|
| BSD | `SA_RESTART` |
| System V | `SA_RESETHAND \| SA_NODEFER` |

**Linux 的特殊性**（下题详述）：两套实现并存，取决于你走的是内核系统调用还是 glibc 包装。

**结论**：`signal()` 的语义**取决于 libc、编译时的 feature macro、甚至编译标准**。同一份源码在不同构建配置下行为不同——这就是为什么它绝对不能用于生产代码。

</details>

<details>
<summary><b>问 2：</b>Linux 上 <code>signal()</code> 到底是 BSD 还是 System V 语义？</summary>

**两套都有，取决于你用的是内核系统调用还是 glibc 包装函数。**

**A. 内核系统调用 `sys_signal` = System V 语义**

```c
/* kernel/signal.c:4622 */
/*
 * For backwards compatibility.  Functionality superseded by sigaction.
 */
SYSCALL_DEFINE2(signal, int, sig, __sighandler_t, handler)
{
        struct k_sigaction new_sa, old_sa;
        int ret;

        new_sa.sa.sa_handler = handler;
        new_sa.sa.sa_flags = SA_ONESHOT | SA_NOMASK;      /* :4628 ← 硬编码 */
        sigemptyset(&new_sa.sa.sa_mask);

        ret = do_sigaction(sig, &new_sa, &old_sa);

        return ret ? ret : (unsigned long)old_sa.sa.sa_handler;
}
```

| 内部别名 | 用户可见名 | 值 | 效果 |
|----------|-----------|-----|------|
| `SA_ONESHOT` | `SA_RESETHAND` | `0x80000000` | 递送后重置为 `SIG_DFL` |
| `SA_NOMASK` | `SA_NODEFER` | `0x40000000` | handler 期间**不**阻塞自己 |

内核侧的实现：

```c
/* get_signal():2796 —— SA_ONESHOT */
                if (ka->sa.sa_flags & SA_ONESHOT)
                        ka->sa.sa_handler = SIG_DFL;

/* signal_delivered():2926 —— SA_NODEFER */
        sigorsets(&blocked, &current->blocked, &ksig->ka.sa.sa_mask);
        if (!(ksig->ka.sa_flags & SA_NODEFER))
                sigaddset(&blocked, ksig->sig);
        set_current_blocked(&blocked);
```

注意这是**最坏的组合**：既重置（有竞态）又不自动阻塞（可递归）。

**B. glibc 包装函数 = BSD 语义**

glibc 的 `signal()` **不调用这个系统调用**，而是包装 `sigaction()`：

```c
/* glibc 内部（示意） */
act.sa_handler = handler;
__sigemptyset(&act.sa_mask);
act.sa_flags = SA_RESTART;          /* ← 只有这一个标志 */
__sigaction(sig, &act, &oact);
```

`man 2 signal` 的权威表述：

> * By default, in glibc 2 and later, the `signal()` wrapper function does not invoke the kernel system call. Instead, it calls `sigaction(2)` using flags that supply BSD semantics. This default behavior is provided as long as a suitable feature test macro is defined: `_BSD_SOURCE` on glibc 2.19 and earlier or `_DEFAULT_SOURCE` in glibc 2.19 and later.
> * **If such a feature test macro is not defined, then `signal()` provides System V semantics.**

**最后一行的实际影响**：用 `-std=c99`（严格 ANSI，不定义 `_DEFAULT_SOURCE`）编译时，glibc 会给你 **SysV 语义**。这就是"换个编译标准，程序行为就变了"这类诡异 bug 的来源。

**怎么确认**：

```bash
gcc -o t t.c && strace -e trace=rt_sigaction,signal ./t
# rt_sigaction(SIGUSR1, {SIG_IGN, [], SA_RESTART}, ...)   ← glibc 包装（BSD）
# signal(SIGUSR1, SIG_IGN)                                ← 裸系统调用（SysV）
```

**实践结论**：

| 你写的 | 实际语义 | 可预测吗 |
|--------|----------|----------|
| `signal(sig, h)` + `-std=gnu11`（默认） | BSD（处置保持、自动阻塞、自动重启） | 依赖默认 feature macro |
| `signal(sig, h)` + `-std=c99` | SysV（重置、不阻塞、不重启） | 依赖编译标准 |
| `sigaction()` + 显式 `sa_flags` | **完全由你指定** | ✅ **可预测** |

**所以答案不是"Linux 上是 X 语义"，而是"如果你用 `signal()`，你得先搞清楚自己拿的是哪一套"——而这本身就是应该改用 `sigaction()` 的理由。**

</details>

<details>
<summary><b>问 3：</b><code>signal()</code> 有哪些 <code>sigaction()</code> 能做到而它做不到的事？</summary>

六个结构性缺陷：

| # | `signal()` 的缺陷 | `sigaction()` 的能力 |
|---|-------------------|----------------------|
| 1 | **语义不确定**（BSD vs SysV） | `sa_flags` 显式指定，完全可预测 |
| 2 | **不能设 `sa_mask`**——无法在 handler 期间屏蔽其他信号 | `sigaddset(&sa.sa_mask, SIGXXX)` 精确控制 |
| 3 | **不能设 `SA_SIGINFO`**——拿不到 `siginfo_t` | `sa_flags \|= SA_SIGINFO` + `sa.sa_sigaction` → 有 `si_code`/`si_addr`/`si_pid`/`si_value` |
| 4 | **不能控制 `SA_RESTART`** | 显式加/不加 |
| 5 | **不能设 `SA_ONSTACK`**——栈溢出时 handler 跑不起来 | `sa_flags \|= SA_ONSTACK` + `sigaltstack()` |
| 6 | **多线程下行为未规定** | 语义明确 |

**逐条展开**：

**缺陷 2 —— 无法保护临界区**

```c
/* sigaction：handler 期间额外屏蔽 SIGTERM，保证清理逻辑不被打断 */
struct sigaction sa = {0};
sa.sa_handler = cleanup;
sigemptyset(&sa.sa_mask);
sigaddset(&sa.sa_mask, SIGTERM);      /* ← signal() 完全无法表达 */
sigaddset(&sa.sa_mask, SIGINT);
sa.sa_flags = 0;
sigaction(SIGUSR1, &sa, NULL);
```

**缺陷 3 —— 拿不到诊断信息**（对 HFT 最致命）

```c
/* 有 SA_SIGINFO：能拿到精确故障信息 */
static void crash(int sig, siginfo_t *si, void *ctx)
{
    log("sig=%d si_code=%d si_addr=%p", sig, si->si_code, si->si_addr);
    /* SEGV_MAPERR + 0x0   → 空指针
     * SEGV_ACCERR + 高地址 → 写只读页
     * FPE_INTDIV          → 整数除零 */
}

/* 没有 SA_SIGINFO：只有一个信号编号，什么都不知道 */
static void crash(int sig)
{
    log("sig=%d", sig);     /* 就这些了 */
}
```

**缺陷 5 —— 栈溢出时无法收尸**

栈溢出 → 触发 `SIGSEGV` → 默认栈已耗尽，**无法再压栈帧** → handler 跑不起来 → 进程悄无声息地死掉，什么线索都没留下。

```c
/* 必须 sigaltstack + SA_ONSTACK，signal() 做不到 */
static char alt[SIGSTKSZ * 4];
stack_t ss = { .ss_sp = alt, .ss_size = sizeof(alt), .ss_flags = 0 };
sigaltstack(&ss, NULL);

struct sigaction sa = {0};
sa.sa_sigaction = crash;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;      /* ← 关键 */
sigaction(SIGSEGV, &sa, NULL);
```

**缺陷 6 —— POSIX 明文 unspecified**：

> **POSIX.1-2008**: *"The behavior of `signal()` in a multithreaded process is unspecified."*

`sa_flags` 完整清单（`include/uapi/asm-generic/signal-defs.h`）：

| 标志 | 值 | 作用 |
|------|-----|------|
| `SA_NOCLDSTOP` | 1 | `SIGCHLD`：子进程**停止/恢复**时不发信号 |
| `SA_NOCLDWAIT` | 2 | `SIGCHLD`：子进程退出不产生僵尸 |
| `SA_SIGINFO` | 4 | 使用 `sa_sigaction`，传递 `siginfo_t` |
| `SA_ONSTACK` | `0x08000000` | 在 `sigaltstack()` 设置的备用栈上跑 |
| `SA_RESTART` | `0x10000000` | 被中断的系统调用自动重启 |
| `SA_NODEFER` | `0x40000000` | handler 期间**不**阻塞该信号自己 |
| `SA_RESETHAND` | `0x80000000` | 递送后重置为 `SIG_DFL` |

`signal()` **一个都控制不了**（glibc 版本硬编码 `SA_RESTART`，裸系统调用硬编码 `SA_RESETHAND|SA_NODEFER`）。

</details>

<details>
<summary><b>问 4：</b>把老代码的 <code>signal(sig, handler)</code> 改成 <code>sigaction()</code>，要注意什么？</summary>

**四条"必须/禁止" + 三个迁移陷阱**。

**标准模板**：

```c
#include <signal.h>
#include <string.h>

int install_handler(int sig, void (*handler)(int))
{
    struct sigaction sa;

    memset(&sa, 0, sizeof(sa));          /* ① 必须清零 */
    sa.sa_handler = handler;             /* ② 只设 sa_handler */
    sigemptyset(&sa.sa_mask);            /* ③ 必须显式初始化 */
    sa.sa_flags = SA_RESTART;            /* ④ 显式指定，不依赖默认 */

    return sigaction(sig, &sa, NULL);
}
```

**四条规则**：

| | 规则 | 原因 |
|--|------|------|
| ✅ | `memset(&sa, 0, sizeof(sa))` | `struct sigaction` 在栈上，未初始化字段是**垃圾值** |
| ✅ | `sigemptyset(&sa.sa_mask)` | 垃圾掩码可能意外屏蔽 `SIGTERM`/`SIGINT`，导致进程无法优雅停止 |
| ✅ | 显式指定 `sa_flags` | 若老代码依赖 BSD 语义 → `SA_RESTART`；依赖 SysV → `SA_RESETHAND\|SA_NODEFER` |
| ❌ | **不要同时给 `sa_handler` 和 `sa_sigaction` 赋值** | 它们是 **union**，同一块内存，后者覆盖前者 |

**陷阱 1 —— union 覆盖**

```c
struct sigaction sa = {0};
sa.sa_handler = my_handler;        /* 写了 */
sa.sa_sigaction = my_siginfo_h;    /* 覆盖了！前一个赋值失效 */
sa.sa_flags = SA_SIGINFO;
/* 实际生效的是 sa_sigaction，但如果忘了设 SA_SIGINFO，
 * 内核会按 sa_handler 解释那块内存 → 直接跳到错误地址 → 崩溃 */
```

**陷阱 2 —— 内核静默清除未知 flag**

```c
/* do_sigaction():4148 */
        /*
         * Clear unknown flag bits in order to allow userspace to detect missing
         * support for flag bits and to allow the kernel to use non-uapi bits
         * internally.
         */
        if (act)
                act->sa.sa_flags &= UAPI_SA_FLAGS;
```

你传进去的 flag 如果不被支持，**不报错，只是静默丢弃**。唯一可靠的验证方式是**读回比对**：

```c
struct sigaction verify;
sigaction(sig, NULL, &verify);            /* 读回内核实际保存的值 */
if ((verify.sa_flags & SA_ONSTACK) == 0)
    fprintf(stderr, "SA_ONSTACK 被内核静默丢弃了！\n");
```

**陷阱 3 —— `SA_RESTART` 不是万能的**

即使设了 `SA_RESTART`，这些调用**仍然**返回 `EINTR`：

| 一定返回 `EINTR` |
|------------------|
| `select()` / `pselect()` |
| `poll()` / `ppoll()` |
| `epoll_wait()` / `epoll_pwait()` |
| `connect()`（非阻塞 socket） |
| `read()` 于 `inotify` fd |
| `semop()`、`msgrcv()` 等 SysV IPC |

所以**迁移后仍然要显式处理 `EINTR`**：

```c
ssize_t robust_read(int fd, void *buf, size_t n)
{
    ssize_t r;
    do {
        r = read(fd, buf, n);
    } while (r == -1 && errno == EINTR);
    return r;
}
```

**迁移后的回归检查清单**：

- [ ] 所有 `signal()` 调用已替换（`grep -rn '\bsignal\s*(' src/`）
- [ ] 每个 `sigaction` 前都有 `memset` / `= {0}`
- [ ] 每个 `sa_mask` 都有 `sigemptyset`
- [ ] `sa_flags` 显式指定，没有依赖默认
- [ ] 没有同时给 `sa_handler` 和 `sa_sigaction` 赋值
- [ ] 崩溃类 handler（`SIGSEGV`/`SIGBUS`/`SIGFPE`/`SIGILL`）都配了 `SA_ONSTACK` + `sigaltstack()`
- [ ] 关键 flag 用 `sigaction(sig, NULL, &verify)` 读回验证过
- [ ] 所有阻塞型 syscall 都有 `EINTR` 重试循环
- [ ] 多线程程序里用的是 `pthread_sigmask`，不是 `sigprocmask`

</details>

<details>
<summary><b>问 5：</b>把 <code>signal(sig, SIG_IGN)</code> 迁移到 <code>sigaction()</code> 时，对 SIGCHLD 有什么坑？</summary>

坑在于：**对 `SIGCHLD` 来说，"默认处置（`SIG_DFL`）"和"显式 `SIG_IGN`"虽然都表现为"忽略"，但效果完全不同。**

**先看内核判定**（`kernel/signal.c:74`）：

```c
static inline bool sig_handler_ignored(void __user *handler, int sig)
{
        /* Is it explicitly or implicitly ignored? */
        return handler == SIG_IGN ||
               (handler == SIG_DFL && sig_kernel_ignore(sig));
}
```

`SIGCHLD` 在 `SIG_KERNEL_IGNORE_MASK` 里（`include/linux/signal.h:433`），所以 `SIG_DFL` 也算"隐式忽略"——**从"信号是否被处理"的角度，两者一样**。

**但"僵尸"这一层完全不同**：

| 处置 | 子进程退出时发 `SIGCHLD`？ | 子进程变僵尸？ | 需要 `wait()` 吗？ |
|------|---------------------------|----------------|-------------------|
| `SIG_DFL`（默认，"隐式忽略"） | 发（但被忽略） | ✅ **会变僵尸** | ✅ **必须 `wait()` 回收** |
| `SIG_IGN`（显式忽略） | 发（被忽略） | ❌ **不产生僵尸**，内核自动回收 | ❌ 不需要（也 `wait` 不到） |

**这是个反直觉但极其重要的区别**。显式 `SIG_IGN` 时，内核在子进程退出时**直接把它从进程表移除**，父进程调用 `wait()` 会返回 `-1 / ECHILD`。

**迁移时的具体风险**：

```c
/* 老代码 */
signal(SIGCHLD, SIG_IGN);          /* 图省事：不想要僵尸，也不关心子进程 */

/* 迁移成 sigaction */
struct sigaction sa = {0};
sa.sa_handler = SIG_IGN;
sigemptyset(&sa.sa_mask);
sa.sa_flags = 0;
sigaction(SIGCHLD, &sa, NULL);     /* ✅ 行为一致：仍然不产生僵尸 */
```

这个迁移是**安全**的。但下面两种是**危险**的：

```c
/* ❌ 危险 1：以为"默认就是忽略"，索性不设置 */
/* 结果：子进程全部变僵尸，长时间运行后 PID 耗尽 */

/* ❌ 危险 2：装了个 handler，但里面没 wait() */
static void on_child(int sig) { /* 什么都不做 */ }
sa.sa_handler = on_child;
sigaction(SIGCHLD, &sa, NULL);
/* 结果：handler 跑了，但子进程状态没人回收 → 僵尸累积 */
```

**正确的 handler 写法**（`SIGCHLD` 不排队！）：

```c
static void on_child(int sig)
{
    (void)sig;
    int saved = errno;                    /* 保护 errno */
    /* SIGCHLD 不排队：N 个子进程同时退出只递送一次
     * → 必须循环回收，直到没有更多 */
    while (waitpid(-1, NULL, WNOHANG) > 0)
        ;
    errno = saved;
}
```

**为什么必须循环**（见 [Ch26](../../chapter-26-monitoring-child-processes/README.md)）：

```
三个子进程同时退出
  ↓
三个 SIGCHLD 产生
  ↓
标准信号不排队（legacy_queue():1079）→ 只留【一个】
  ↓
handler 跑一次
  ↓
waitpid() 一次 → 只回收一个 → 剩下两个【永久僵尸】
```

**如果需要知道是哪个子进程、退出码是什么**：

```c
struct sigaction sa = {0};
sa.sa_sigaction = on_child_info;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_SIGINFO | SA_RESTART | SA_NOCLDSTOP;   /* ← SA_NOCLDSTOP */
sigaction(SIGCHLD, &sa, NULL);

static void on_child_info(int sig, siginfo_t *si, void *ctx)
{
    (void)sig; (void)ctx;
    int saved = errno;
    int status;
    /* 仍然要循环！si_pid 只告诉你【其中一个】 */
    pid_t pid;
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        if (WIFEXITED(status))
            log("child %d exited, code=%d", pid, WEXITSTATUS(status));
        else if (WIFSIGNALED(status))
            log("child %d killed by %d%s", pid, WTERMSIG(status),
                WCOREDUMP(status) ? " (core dumped)" : "");
    }
    errno = saved;
}
```

**`SA_NOCLDSTOP` 的作用**：默认情况下，子进程被**停止**（`SIGSTOP`）或**恢复**（`SIGCONT`）时也会发 `SIGCHLD`。如果你只关心"退出"，加上 `SA_NOCLDSTOP` 可以过滤掉这些——减少无谓的 handler 调用（在高频 fork 的服务里这是有意义的优化，尤其对 HFT 这类对抖动敏感的系统）。

**迁移检查清单（SIGCHLD 专项）**：

- [ ] 明确你要的是"自动回收（不关心子进程）"还是"回收并知道退出状态"
- [ ] 前者 → `SIG_IGN`；后者 → handler + `while (waitpid(..., WNOHANG) > 0)`
- [ ] 装 handler 时考虑加 `SA_NOCLDSTOP`（只关心退出时）
- [ ] 需要详细信息时加 `SA_SIGINFO`
- [ ] 测试：并发 fork/exit 多个子进程，用 `ps -eo stat | grep Z` 检查僵尸
