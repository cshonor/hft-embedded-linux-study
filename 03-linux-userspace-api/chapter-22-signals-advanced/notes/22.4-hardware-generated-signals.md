## 本节讲什么

1. **CPU 自己产生的信号**（段错误、除零、非法指令）与 `kill()` 产生的信号走的是**两条完全不同的内核路径**
2. 为什么对 `SIGSEGV` 设 `SIG_IGN` 或阻塞**完全无效**——内核的"强制"机制
3. `si_code` / `si_addr` 里藏着的**诊断金矿**：一眼区分"空指针"和"写只读页"

---

## 一、什么是"硬件产生的信号"

信号有三大来源：

| 来源 | 机制 | 典型信号 |
|------|------|----------|
| **用户/进程** | `kill()` / `sigqueue()` / `raise()` | 任意 |
| **内核（软件事件）** | 定时器到期、子进程退出、终端、I/O 就绪 | `SIGALRM` / `SIGCHLD` / `SIGIO` |
| **硬件（CPU 异常）** | CPU 执行指令时检测到错误，触发异常向量 | `SIGSEGV` / `SIGBUS` / `SIGFPE` / `SIGILL` / `SIGTRAP` |

本节讲第三种。它们的共同特征是：**由某一条具体的指令触发**，因此天然携带"在哪条指令、访问了哪个地址、出了什么错"的精确信息。

```
用户态执行 mov %rax, (%rdx)       ← rdx = 0x0（空指针）
        │
        ▼
CPU 检测到地址 0x0 未映射 → 触发 #PF（Page Fault）异常
        │
        ▼
进入内核，走 arch/x86/mm/fault.c 的缺页处理路径
        │   ├─ 能修复？（写时复制、按需分配、换入）→ 修好，返回，用户态无感知
        │   └─ 修不了（真正的非法访问）→ 发信号
        ▼
force_sig_fault(SIGSEGV, SEGV_MAPERR, (void __user *)address)   kernel/signal.c:1740
        │
        ▼
返回用户态前 get_signal() → handler 或默认终止（+ core dump）
```

**关键区分**：缺页（page fault）**不一定**产生信号。Linux 的绝大多数 #PF 是良性的（写时复制、首次访问、页面换入），内核静默修复后用户态毫无察觉。只有**真正非法**的访问才会走到 `force_sig_fault()`。

## 二、`force_*` 家族：内核的"强制递送"通道

### 2.1 核心函数与那段必读注释

```c
/* kernel/signal.c:1324 */
/*
 * Force a signal that the process can't ignore: if necessary
 * we unblock the signal and change any SIG_IGN to SIG_DFL.
 *
 * Note: If we unblock the signal, we always reset it to SIG_DFL,
 * since we do not want to have a signal handler that was blocked
 * be invoked when user space had explicitly blocked it.
 *
 * We don't want to have recursive SIGSEGV's etc, for example,
 * that is why we also clear SIGNAL_UNKILLABLE.
 */
static int
force_sig_info_to_task(struct kernel_siginfo *info, struct task_struct *t,
        enum sig_handler handler)
{
        unsigned long int flags;
        int ret, blocked, ignored;
        struct k_sigaction *action;
        int sig = info->si_signo;

        spin_lock_irqsave(&t->sighand->siglock, flags);
        action = &t->sighand->action[sig-1];
        ignored = action->sa.sa_handler == SIG_IGN;
        blocked = sigismember(&t->blocked, sig);
        if (blocked || ignored || (handler != HANDLER_CURRENT)) {
                action->sa.sa_handler = SIG_DFL;          /* :1349 撤销 SIG_IGN */
                if (handler == HANDLER_EXIT)
                        action->sa.sa_flags |= SA_IMMUTABLE;
                if (blocked) {
                        sigdelset(&t->blocked, sig);      /* :1353 撤销阻塞 */
                        recalc_sigpending_and_wake(t);
                }
        }
        /*
         * Don't clear SIGNAL_UNKILLABLE for traced tasks, users won't expect
         * debugging to leave init killable. But HANDLER_EXIT is always fatal.
         */
        if (action->sa.sa_handler == SIG_DFL &&
            (!t->ptrace || (handler == HANDLER_EXIT)))
                t->signal->flags &= ~SIGNAL_UNKILLABLE;

        ret = send_signal_locked(sig, info, t, PIDTYPE_PID);   /* :1364 ← 定向到具体线程 */
        spin_unlock_irqrestore(&t->sighand->siglock, flags);

        return ret;
}
```

三个动作，一眼记住：

| 动作 | 代码 | 效果 |
|------|------|------|
| 撤销 `SIG_IGN` | `:1349` `action->sa.sa_handler = SIG_DFL` | 你设的忽略被抹掉 |
| 解除阻塞 | `:1353` `sigdelset(&t->blocked, sig)` | 你设的阻塞被抹掉 |
| **定向到当前线程** | `:1364` `send_signal_locked(..., PIDTYPE_PID)` | 进**私有 pending**，只有故障线程能取 |

> 最后一条最关键：`PIDTYPE_PID` 而不是 `PIDTYPE_TGID`。硬件故障信号是**线程定向**的——因为故障是那一个线程执行指令造成的，必须由它自己处理（尤其要保证 sigframe 里的 PC 指向故障指令）。对比 `kill()` 发的是进程定向（`PIDTYPE_TGID`），进共享 pending。

### 2.2 `enum sig_handler`：三种强制强度

```c
/* kernel/signal.c:1318 */
enum sig_handler {
        HANDLER_CURRENT, /* If reachable use the current handler */
        HANDLER_SIG_DFL, /* Always use SIG_DFL handler semantics */
        HANDLER_EXIT,    /* Only visible as the process exit code */
};
```

| 强度 | 语义 | 使用者 |
|------|------|--------|
| `HANDLER_CURRENT` | 尊重用户装的 handler（但撤销忽略/阻塞） | `force_sig_fault()`、大部分硬件故障 |
| `HANDLER_SIG_DFL` | **无视用户 handler**，一律走默认动作 | `force_fatal_sig():1681` |
| `HANDLER_EXIT` | 连 handler 都不跑，只作为**退出码**可见；还会打上 `SA_IMMUTABLE`（此后连 `sigaction` 都改不动） | `force_exit_sig():1694` |

`SA_IMMUTABLE` 那一行很值得注意——它保证"这个进程必须以这个信号死掉"，连后续 `sigaction()` 都无法挽救（`do_sigaction():4135` 见到 `SA_IMMUTABLE` 直接返回 `-EINVAL`）。

### 2.3 常用 `force_*` 变体一览

| 函数 | 行号 | 用途 | `si_code` |
|------|------|------|-----------|
| `force_sig(sig)` | `:1667` | 最简形式，`si_code = SI_KERNEL` | `SI_KERNEL` |
| `force_fatal_sig(sig)` | `:1681` | 强制走 `SIG_DFL`（跑不了 handler） | `SI_KERNEL` |
| `force_exit_sig(sig)` | `:1694` | 只作为退出码，handler 不跑 + `SA_IMMUTABLE` | `SI_KERNEL` |
| `force_sigsegv(sig)` | `:1713` | 信号处理自身失败时的兜底（栈帧建不起来） | `SI_KERNEL` |
| `force_sig_fault(sig, code, addr)` | `:1740` | **主力**：带故障地址 | 调用方指定 |
| `force_sig_fault_to_task(...)` | `:1721` | 同上，可指定目标线程 | 调用方指定 |
| `force_sig_fault_trapno(...)` | `:1891` | 额外带 trapno（alpha/sparc） | 调用方指定 |
| `force_sig_mceerr(code, addr, lsb)` | `:1766` | 机器检查异常（内存硬件错误） | `BUS_MCEERR_AR/AO` |
| `force_sig_bnderr(addr, lower, upper)` | `:1795` | MPX 边界检查失败 | `SEGV_BNDERR` |
| `force_sig_pkuerr(addr, pkey)` | `:1810` | 内存保护键（PKU）违规 | `SEGV_PKUERR` |
| `force_sig_seccomp(syscall, reason, coredump)` | `:1858` | seccomp 拦截系统调用 | `SYS_SECCOMP` |
| `send_sig_perf(addr, type, data)` | `:1824` | perf 事件（**非 force**，可被打断） | `TRAP_PERF` |

`force_sigsegv()` 那段注释值得单独看（`:1707`）：

```c
/*
 * When things go south during signal handling, we
 * will force a SIGSEGV. And if the signal that caused
 * the problem was already a SIGSEGV, we'll want to
 * make sure we don't even try to deliver the signal..
 */
void force_sigsegv(int sig)
{
        if (sig == SIGSEGV)
                force_fatal_sig(SIGSEGV);     /* 已经是 SEGV → 直接死，别再尝试递送 */
        else
                force_sig(SIGSEGV);
}
```

理由：如果建 SIGSEGV 栈帧时又失败（栈都溢出了），再尝试递送 SIGSEGV 只会再失败一次 → 无限递归。所以第二次直接用 `force_fatal_sig()` 让进程死掉。

## 三、`si_code`：硬件故障的"错误类型"

`si_code > 0` 表示**内核产生**（`SI_FROMKERNEL(siptr) == ((siptr)->si_code > 0)`，`uapi_siginfo.h:191`）。对硬件信号，`si_code` 精确描述了错误种类。

### 3.1 `SIGSEGV` —— 内存访问违规（`uapi_siginfo.h:232`）

| `si_code` | 值 | 含义 | 典型场景 |
|-----------|-----|------|----------|
| `SEGV_MAPERR` | 1 | **地址未映射** | 空指针（`addr = 0x0`）、野指针、已 `free` 后访问、数组越界跑到未映射区 |
| `SEGV_ACCERR` | 2 | **权限不足**（地址映射了，但不许这么访问） | 写只读页（`.rodata`、代码段、`mprotect(PROT_READ)`）、从用户态访问内核地址 |
| `SEGV_BNDERR` | 3 | MPX 边界检查失败 | Intel MPX（已废弃） |
| `SEGV_PKUERR` | 4 | 保护键（PKU）违规 | `pkey_mprotect()` + `WRPKRU` |
| `SEGV_ACCADI` | 5 | ADI 未启用（SPARC） | — |
| `SEGV_ADIDERR` / `SEGV_ADIPERR` | 6/7 | SPARC MCD 错误 | — |
| `SEGV_MTEAERR` / `SEGV_MTESERR` | 8/9 | **ARM MTE**（内存标签扩展）——异步/同步 | ARMv8.5+，硬件级内存安全 |
| `SEGV_CPERR` | 10 | 控制保护错误（CET shadow stack） | Intel CET |

**`SEGV_MAPERR` vs `SEGV_ACCERR` 是最有用的一对**：

```
SEGV_MAPERR   → 地址根本不在你的地址空间里（页表没这一项）
                → 空指针、悬垂指针、越界到未分配区

SEGV_ACCERR   → 地址在你的地址空间里，但权限不对
                → 写只读页、执行不可执行页（NX）、访问内核空间
```

### 3.2 `SIGFPE` —— 算术异常（`:212`）

| `si_code` | 值 | 含义 |
|-----------|-----|------|
| `FPE_INTDIV` | 1 | **整数除零**（最常见） |
| `FPE_INTOVF` | 2 | 整数溢出 |
| `FPE_FLTDIV` | 3 | 浮点除零 |
| `FPE_FLTOVF` | 4 | 浮点上溢 |
| `FPE_FLTUND` | 5 | 浮点下溢 |
| `FPE_FLTRES` | 6 | 浮点结果不精确 |
| `FPE_FLTINV` | 7 | 浮点非法操作（`0.0/0.0`、`sqrt(-1)`） |
| `FPE_FLTSUB` | 8 | 下标越界 |
| `FPE_FLTUNK` | 14 | 未诊断的浮点异常 |

> **注意**：IEEE 754 默认**不产生异常**——`1.0/0.0` 得到 `inf`，`0.0/0.0` 得到 `nan`，不会发 `SIGFPE`。要拿到这些信号必须显式 `feenableexcept(FE_DIVBYZERO | FE_INVALID | FE_OVERFLOW)`。**整数除零则一定会触发 `SIGFPE`，无法屏蔽。**

### 3.3 `SIGILL` —— 非法指令（`:196`）

| `si_code` | 值 | 含义 | 典型场景 |
|-----------|-----|------|----------|
| `ILL_ILLOPC` | 1 | 非法操作码 | **栈被踩坏后返回到数据区执行**；用了 CPU 不支持的指令集（AVX-512 在老 CPU 上） |
| `ILL_ILLOPN` | 2 | 非法操作数 | — |
| `ILL_ILLADR` | 3 | 非法寻址模式 | — |
| `ILL_ILLTRP` | 4 | 非法陷阱 | — |
| `ILL_PRVOPC` | 5 | 特权指令 | 用户态执行 `hlt`/`cli` 等 Ring 0 指令 |
| `ILL_PRVREG` | 6 | 特权寄存器 | 访问 `cr0`/`msr` |
| `ILL_COPROC` | 7 | 协处理器错误 | — |
| `ILL_BADSTK` | 8 | 内部栈错误 | — |

**HFT/嵌入式最常遇到 `ILL_ILLOPC`**：函数指针被踩坏、返回地址被覆盖（栈溢出攻击/内存踩坏）→ PC 跳到数据段 → 那些字节恰好不是合法指令 → `SIGILL`。此时 `si_addr` 就是那个"指令地址"，往往是 `0x41414141` 这类明显异常的值，一眼能看出是被数据覆盖了。

### 3.4 `SIGBUS` —— 总线错误（`:251`）

| `si_code` | 值 | 含义 | 典型场景 |
|-----------|-----|------|----------|
| `BUS_ADRALN` | 1 | **地址未对齐** | ARM/SPARC 上未对齐访问；x86 上 `MOVAPS` 对未对齐地址（该指令要求 16 字节对齐） |
| `BUS_ADRERR` | 2 | 物理地址不存在 | **`mmap` 的文件被截断后访问映射区**——最经典 |
| `BUS_OBJERR` | 3 | 对象特定硬件错误 | — |
| `BUS_MCEERR_AR` | 4 | 机器检查：已消费，**必须处理** | **内存条硬件故障**（ECC 无法纠正） |
| `BUS_MCEERR_AO` | 5 | 机器检查：已检测到但未消费，可选处理 | 同上有一定容忍度 |

`BUS_ADRERR` 的经典案例：

```c
int fd = open("data.bin", O_RDWR);
ftruncate(fd, 4096);
char *p = mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
/* 另一个进程（或 shell）执行: truncate -s 0 data.bin */
p[100] = 'x';        /* → SIGBUS / BUS_ADRERR：页在，但文件没了 */
```

**注意与 SIGSEGV 的区别**：`SIGSEGV` 是"地址空间层面"的错误，`SIGBUS` 是"地址有效但后端对象出问题"。

### 3.5 `SIGTRAP` —— 陷阱（`:263`）

| `si_code` | 值 | 含义 |
|-----------|-----|------|
| `TRAP_BRKPT` | 1 | 断点（`int3`） |
| `TRAP_TRACE` | 2 | 单步跟踪 |
| `TRAP_BRANCH` | 3 | 分支陷阱 |
| `TRAP_HWBKPT` | 4 | 硬件断点/观察点（DR0-DR7） |
| `TRAP_UNK` | 5 | 未诊断陷阱 |
| `TRAP_PERF` | 6 | **perf 事件带 `sigtrap=1`** |

`send_sig_perf()`（`:1824`）有一段很能说明"同步 vs 异步"的注释（`:1836-1841`）：

```c
        /*
         * Signals generated by perf events should not terminate the whole
         * process if SIGTRAP is blocked, however, delivering the signal
         * asynchronously is better than not delivering at all. But tell user
         * space if the signal was asynchronous, so it can clearly be
         * distinguished from normal synchronous ones.
         */
        info.si_perf_flags = sigismember(&current->blocked, info.si_signo) ?
                                     TRAP_PERF_FLAG_ASYNC : 0;

        return send_sig_info(info.si_signo, &info, current);
```

注意它用的是 **`send_sig_info()` 而不是 `force_*`**——因为 perf 事件不是"必须处理"的硬件故障，只是一个采样通知。所以它**尊重用户的阻塞设置**，但通过 `si_perf_flags` 里的 `TRAP_PERF_FLAG_ASYNC` 告诉用户态"这次是异步递送的，别当成真陷阱"。这是一个很好的设计范例：**不得不用同一信号时，用额外的标志位区分语义**。

## 四、`si_addr`：故障地址

```c
/* include/uapi/asm-generic/siginfo.h:69 */
        /* SIGILL, SIGFPE, SIGSEGV, SIGBUS, SIGTRAP, SIGEMT */
        struct {
                void __user *_addr; /* faulting insn/memory ref. */
                ...
        } _sigfault;
/* :160 */
#define si_addr         _sifields._sigfault._addr
```

**注意 `si_addr` 的含义随信号变化**：

| 信号 | `si_addr` 是 |
|------|--------------|
| `SIGSEGV` | **被访问的内存地址**（读/写的那个地址） |
| `SIGBUS` | 被访问的内存地址；`BUS_MCEERR_*` 时配合 `si_addr_lsb` 表示物理地址的精度 |
| `SIGFPE` | **触发异常的指令地址**（不是数据地址！） |
| `SIGILL` | **非法指令的地址** |
| `SIGTRAP` | 相关地址（断点地址 / perf 数据相关） |

`SIGFPE` 那一行的差异反复有人搞错：**除零时 `si_addr` 是那条 `div` 指令的地址，不是什么"数据地址"**。

配套字段（`uapi_siginfo.h:161-168`）：

| 字段 | 行号 | 用途 |
|------|------|------|
| `si_trapno` | `:161` | alpha/sparc 的 trap 号 |
| `si_addr_lsb` | `:162` | `BUS_MCEERR_*` 时表示地址的最低有效位（精度） |
| `si_lower` / `si_upper` | `:163-164` | `SEGV_BNDERR` 的边界上下限 |
| `si_pkey` | `:165` | `SEGV_PKUERR` 的保护键编号 |
| `si_perf_data` / `si_perf_type` / `si_perf_flags` | `:166-168` | `TRAP_PERF` 的 perf 数据 |

## 五、硬件信号的三条铁律

### 铁律 1：不能用 `SIG_IGN` 忽略，也不能阻塞

`force_sig_info_to_task():1348-1356` 会强行撤销（见第二节）。

**但只对真正的硬件故障生效**——`kill(pid, SIGSEGV)` 走的是常规 `send_signal_locked()` 路径，**你设的 `SIG_IGN` 会生效**。这是实验室里复现这一区别的标准手法：

```c
signal(SIGSEGV, SIG_IGN);
raise(SIGSEGV);            /* 或 kill(getpid(), SIGSEGV) → 什么都不会发生 */
*(int *)0 = 1;             /* 真实硬件故障 → 照样死 */
```

### 铁律 2：如果装了 handler 并正常返回，会**无限循环**

```
CPU 执行 mov %rax,(%rdx)   ← rdx=0
     ↓
#PF → force_sig_fault(SIGSEGV, SEGV_MAPERR, 0x0)
     ↓
跑 handler
     ↓
handler 正常返回 → sigreturn → 恢复被保存的 PC
     ↓
PC 仍指向那条 mov（就是它触发的故障！）
     ↓
再执行一次 → 再 #PF → 再进 handler
     ↓
… 无限循环 …
```

> SIGSEGV handler **正常返回**只有在你**修好了故障原因**时才有意义。三种合法做法：
> 1. **修好**：`mprotect()` 把页面改成可写，然后返回 → 指令会重试并成功
> 2. **跳过**：修改 `ucontext_t` 里的 PC（`uc_mcontext.gregs[REG_RIP]`）指向下一条指令
> 3. **不返回**：`_exit()` / `abort()` / 恢复 `SIG_DFL` 后 `raise()` 重新抛出

### 铁律 3：只在**故障线程**上递送

`send_signal_locked(..., PIDTYPE_PID)` → 私有 pending → 只有该线程能取。配合 `SYNCHRONOUS_MASK` / `dequeue_synchronous_signal()`（见 [22.2](22.2-special-cases-for-delivery-disposition-a.md)），保证 sigframe 的 PC 指向故障指令。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① 无 MMU 的 MCU（`arm-none-eabi` 裸机 / RTOS）**没有硬件信号机制**，这类诊断要换成 HardFault 异常处理；有 MMU 的嵌入式 Linux（ARM Cortex-A）才有完整的 `SIGSEGV`/`SIGBUS`。② `SIGBUS/BUS_ADRERR` 在嵌入式极常见：日志写到 SD 卡、`mmap` 的配置文件被覆盖、掉电导致文件截断 → 访问映射区必然 `SIGBUS`。③ `BUS_MCEERR_*` 是**内存硬件故障**的直接信号，工控/车载设备应监控它并上报（ECC 纠错失败意味着硬件要换了） |
| HFT | ① **`ILL_ILLOPC` 是热路径内存踩坏的头号信号**——订单簿/内存池被越界写坏后，函数指针或返回地址被覆盖，PC 跳飞执行数据。生产 SIGSEGV/SIGILL handler 应记录 `si_addr` + `si_code` + 完整 backtrace，这是事后定责的唯一线索。② **盘前用 ASan/UBSan 构建跑全量回归**，把踩坏类 bug 拦在上线前——生产崩溃的排查成本是盘前的百倍。③ 千万不要在 SIGSEGV handler 里 `longjmp` 回主循环"继续交易"——内存状态已损坏，继续下单可能造成真实亏损，正确做法是**立即 `_exit()` 并触发风控平仓** |

## 代码示例

### 示例 1：捕获硬件信号，打印精确诊断信息

```c
/* hw_signal.c —— 用 SA_SIGINFO 捕获硬件信号，打印 si_code / si_addr
 * 编译: gcc -O0 -g -o hw_signal hw_signal.c
 * 用法: ./hw_signal segv | fpe | ill | bus */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <unistd.h>
#include <ucontext.h>

/* 严格 async-signal-safe：只用 write(2)。
 * （snprintf 在部分实现里会 malloc / 用 locale 锁，生产 handler 里不要依赖它） */
static void wr(const char *s) { write(STDOUT_FILENO, s, strlen(s)); }

/* 手写无符号十六进制输出，避免 snprintf */
static void wr_hex(const void *p, const char *prefix, const char *suffix)
{
    unsigned long v = (unsigned long)p;
    char buf[32];
    int i = 0;
    buf[i++] = '0'; buf[i++] = 'x';
    if (!v) {
        buf[i++] = '0';
    } else {
        int start = i;
        while (v) {
            unsigned d = (unsigned)(v & 0xF);
            buf[i++] = (char)((d < 10) ? ('0' + d) : ('a' + d - 10));
            v >>= 4;
        }
        /* 反转十六进制部分 */
        for (int a = start, b = i - 1; a < b; a++, b--) {
            char t = buf[a]; buf[a] = buf[b]; buf[b] = t;
        }
    }
    write(STDOUT_FILENO, prefix, strlen(prefix));
    write(STDOUT_FILENO, buf, (size_t)i);
    write(STDOUT_FILENO, suffix, strlen(suffix));
}

/* 手写十进制输出（si_code 最多两位数） */
static void wr_dec(int v, const char *prefix, const char *suffix)
{
    char buf[16];
    int i = 0;
    unsigned u = (unsigned)((v < 0) ? -v : v);
    if (v < 0) buf[i++] = '-';
    int start = i;
    do { buf[i++] = (char)('0' + (u % 10)); u /= 10; } while (u);
    for (int a = start, b = i - 1; a < b; a++, b--) {
        char t = buf[a]; buf[a] = buf[b]; buf[b] = t;
    }
    write(STDOUT_FILENO, prefix, strlen(prefix));
    write(STDOUT_FILENO, buf, (size_t)i);
    write(STDOUT_FILENO, suffix, strlen(suffix));
}

static const char *segv_code(int c)
{
    switch (c) {
    case SEGV_MAPERR: return "SEGV_MAPERR (地址未映射)";
    case SEGV_ACCERR: return "SEGV_ACCERR (权限不足)";
    case SEGV_BNDERR: return "SEGV_BNDERR (边界检查失败)";
    case SEGV_PKUERR: return "SEGV_PKUERR (保护键违规)";
    default:          return "其他 SEGV code";
    }
}

static const char *fpe_code(int c)
{
    switch (c) {
    case FPE_INTDIV: return "FPE_INTDIV (整数除零)";
    case FPE_INTOVF: return "FPE_INTOVF (整数溢出)";
    case FPE_FLTDIV: return "FPE_FLTDIV (浮点除零)";
    case FPE_FLTINV: return "FPE_FLTINV (浮点非法操作)";
    default:         return "其他 FPE code";
    }
}

static void handler(int sig, siginfo_t *si, void *ctx)
{
    (void)ctx;

    wr("\n==== 硬件信号 ====\n");
    wr("  信号      : ");
    switch (sig) {
    case SIGSEGV: wr("SIGSEGV(11)"); break;
    case SIGBUS:  wr("SIGBUS(7)");   break;
    case SIGFPE:  wr("SIGFPE(8)");   break;
    case SIGILL:  wr("SIGILL(4)");   break;
    default:      wr("其他");        break;
    }
    wr("\n  si_code   : ");

    const char *desc = "—";
    if (sig == SIGSEGV)      desc = segv_code(si->si_code);
    else if (sig == SIGFPE)  desc = fpe_code(si->si_code);
    else if (sig == SIGILL)  desc = "见 ILL_* 定义";
    else if (sig == SIGBUS)  desc = "见 BUS_* 定义";

    wr_dec(si->si_code, "", "  ");
    wr(desc);
    wr("\n");

    /* 注意 si_addr 的语义差异：
     *   SIGSEGV/SIGBUS → 被访问的【内存地址】
     *   SIGFPE/SIGILL  → 【指令地址】 */
    wr_hex(si->si_addr, "  si_addr   : ", "\n");

    wr("  来源      : ");
    wr(SI_FROMKERNEL(si) ? "内核/硬件 (si_code>0)\n" : "用户进程 (si_code<=0)\n");

    wr("  内核路径  : force_sig_fault() → force_sig_info_to_task()\n");
    wr("              撤销 SIG_IGN + 解除阻塞 + PIDTYPE_PID(线程定向)\n\n");

    /* 关键：不能正常返回！否则 CPU 重试同一条指令 → 无限循环 */
    _exit(128 + sig);
}

int main(int argc, char **argv)
{
    struct sigaction sa = {0};
    sa.sa_sigaction = handler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigemptyset(&sa.sa_mask);

    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGBUS,  &sa, NULL);
    sigaction(SIGFPE,  &sa, NULL);
    sigaction(SIGILL,  &sa, NULL);

    /* 备用栈：万一是栈溢出导致的 SIGSEGV，默认栈已经不可用了 */
    static char alt[SIGSTKSZ * 4];
    stack_t ss = { .ss_sp = alt, .ss_size = sizeof(alt), .ss_flags = 0 };
    sigaltstack(&ss, NULL);

    const char *mode = (argc > 1) ? argv[1] : "segv";

    if (!strcmp(mode, "segv")) {
        /* SEGV_MAPERR：地址未映射 */
        volatile int *p = (volatile int *)0;
        *p = 42;
    } else if (!strcmp(mode, "accerr")) {
        /* SEGV_ACCERR：地址映射了但不可写（字符串字面量在 .rodata） */
        char *ro = (char *)"read-only string";
        ro[0] = 'X';
    } else if (!strcmp(mode, "fpe")) {
        /* FPE_INTDIV：整数除零 */
        volatile int zero = 0;
        volatile int r = 100 / zero;      /* si_addr 指向这条 div 指令 */
        (void)r;
    } else if (!strcmp(mode, "ill")) {
        /* ILL_ILLOPC：跳到数据区执行 */
        unsigned char code[] = { 0xff, 0xff, 0xff, 0xff };  /* 非法操作码 */
        void (*fp)(void) = (void (*)(void))code;
        fp();
    } else {
        wr("用法: ./hw_signal {segv\|accerr\|fpe\|ill}\n");
    }
    return 0;
}
```

  来源      : 内核/硬件 (si_code>0)

  ...

### 示例 2：唯一合法的"修复后返回"——`mprotect` 落地写时复制

```c
/* segv_fix.c —— SIGSEGV handler 的正确返回姿势：修好故障原因再返回
 * 演示"写保护 + 首次写触发 SIGSEGV → handler 里 mprotect 放行"的套路
 * 这一招正是 GC 写屏障、增量快照（Redis fork 后 COW 统计）的原理
 * 编译: gcc -O0 -g -o segv_fix segv_fix.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/mman.h>

static char *g_page;
static long  g_pagesz;
static int   g_faults = 0;

static void handler(int sig, siginfo_t *si, void *ctx)
{
    (void)sig; (void)ctx;
    g_faults++;

    /* 1. 确认这个地址确实落在我们保护的那页里 —— 不是就别硬修 */
    char *addr = (char *)si->si_addr;
    char *base = (char *)((unsigned long)addr & ~(g_pagesz - 1));
    if (base != g_page) {
        const char m[] = "非预期故障地址，放弃\n";
        write(STDERR_FILENO, m, sizeof(m) - 1);
        _exit(1);
    }

    /* 2. 修好：把这一页改成可写。返回后 CPU 重试那条指令 → 成功 */
    if (mprotect(base, g_pagesz, PROT_READ | PROT_WRITE) == -1) {
        const char m[] = "mprotect 失败\n";
        write(STDERR_FILENO, m, sizeof(m) - 1);
        _exit(1);
    }
    /* 正常返回 → sigreturn → 重试触发故障的指令 → 这次成功 */
}

int main(void)
{
    g_pagesz = sysconf(_SC_PAGESIZE);

    /* mmap 一页，先设为只读 */
    g_page = mmap(NULL, g_pagesz, PROT_READ | PROT_WRITE,
                  MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (g_page == MAP_FAILED) { perror("mmap"); return 1; }
    strcpy(g_page, "hello");

    struct sigaction sa = {0};
    sa.sa_sigaction = handler;
    sa.sa_flags = SA_SIGINFO;      /* 需要 si_addr */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);

    /* 改成只读 */
    if (mprotect(g_page, g_pagesz, PROT_READ) == -1) { perror("mprotect"); return 1; }

    printf("页面已设为只读，内容 = \"%s\"\n", g_page);

    /* 写它 → SIGSEGV/SEGV_ACCERR → handler 里 mprotect 放行 → 重试成功 */
    g_page[0] = 'H';

    printf("写入成功！内容 = \"%s\"，触发 SIGSEGV 次数 = %d\n", g_page, g_faults);
    return 0;
}
```

预期输出：

```
页面已设为只读，内容 = "hello"
写入成功！内容 = "Hello"，触发 SIGSEGV 次数 = 1
```

**这个模式的三个必要条件**（缺一不可）：

1. handler **必须修好故障原因**，否则 CPU 重试同一条指令 → 无限循环
2. 必须用 `SA_SIGINFO` 拿到 `si_addr`（要知道修哪一页）
3. `mprotect()` 是 async-signal-safe 的（它是纯系统调用，不 malloc、不加锁）

> **生产应用**：Redis 的 `fork()` 后 COW 统计、JVM/Go 的 GC 写屏障、QEMU 的软 MMU、增量检查点（checkpoint）都基于这个套路。

## 代码自测

<details>
<summary><b>问 1：</b><code>signal(SIGSEGV, SIG_IGN)</code> 后解引用空指针，程序会怎样？<code>raise(SIGSEGV)</code> 呢？</summary>

**两条路径结果完全相反**，这是本节最重要的一条区分。

**A. `raise(SIGSEGV)` / `kill(getpid(), SIGSEGV)` → 被忽略，什么都不会发生**

走的是常规发送路径 `send_signal_locked()` → `prepare_signal()` → `sig_ignored()`，你设的 `SIG_IGN` 有效。

**B. 真实空指针解引用 → 照样死（并可能 core dump）**

因为硬件故障走 `force_sig_fault()` → `force_sig_info_to_task()`，后者**强行撤销你的设置**（`kernel/signal.c:1344-1356`）：

```c
action = &t->sighand->action[sig-1];
ignored = action->sa.sa_handler == SIG_IGN;
blocked = sigismember(&t->blocked, sig);
if (blocked || ignored || (handler != HANDLER_CURRENT)) {
        action->sa.sa_handler = SIG_DFL;      /* ← 抹掉 SIG_IGN */
        if (handler == HANDLER_EXIT)
                action->sa.sa_flags |= SA_IMMUTABLE;
        if (blocked) {
                sigdelset(&t->blocked, sig);  /* ← 抹掉阻塞 */
                recalc_sigpending_and_wake(t);
        }
}
```

内核注释（`:1324-1334`）给了理由：

> *"Force a signal that the process can't ignore: if necessary we unblock the signal and change any `SIG_IGN` to `SIG_DFL`. … We don't want to have recursive `SIGSEGV`'s etc, for example."*

**逻辑必然性**：如果允许忽略段错误，CPU 返回到同一条指令会再次触发同一个 #PF 异常，下一次还会被忽略 → **无限循环，CPU 100%，程序永远卡在那条指令上**。内核宁可无视用户设置也要避免这个结局。

**同理适用于阻塞**：

```c
sigset_t s; sigemptyset(&s); sigaddset(&s, SIGSEGV);
sigprocmask(SIG_BLOCK, &s, NULL);
*(int *)0 = 1;        /* 阻塞无效，照样死 */
```

**一句话总结**：

| 产生方式 | 内核路径 | 用户的 `SIG_IGN` / 阻塞 |
|----------|----------|------------------------|
| `kill()` / `raise()` / `sigqueue()` | `send_signal_locked()` | ✅ 尊重 |
| CPU 异常（#PF/#DE/#UD/#GP） | `force_sig_fault()` → `force_sig_info_to_task()` | ❌ 撤销 |

</details>

<details>
<summary><b>问 2：</b>为什么 SIGSEGV handler 正常返回会导致无限循环？什么情况下返回是合法的？</summary>

**因为 CPU 会重试触发故障的那条指令。**

硬件故障信号是在**指令执行过程中**产生的。内核建立信号帧时，保存的 PC（返回地址）指向的正是**那条触发故障的指令本身**——不是下一条。这样设计的目的是让 handler 能看到"这就是出错的指令"（`get_signal():2763-2767` 的注释专门强调这点）。

于是：

```
mov %rax,(%rdx)      ← PC 停在这里，rdx=0
   ↓ #PF
force_sig_fault(SIGSEGV, SEGV_MAPERR, 0x0)
   ↓
handler 执行
   ↓
handler 正常 return → sigreturn → 恢复 PC（仍指向那条 mov）
   ↓
CPU 重试 mov %rax,(%rdx)   ← rdx 还是 0
   ↓ #PF
… 无限循环，CPU 100%，程序永远不退出 …
```

**三种合法做法**：

| 做法 | 怎么实现 | 适用场景 |
|------|----------|----------|
| **① 修好故障原因** | handler 里 `mprotect()` / 映射新页 / 修复数据，然后返回 | 写屏障、COW 统计、按需映射（示例 2） |
| **② 跳过这条指令** | 修改 `ucontext_t` 里的 PC 指向下一条 | 模拟器、指令级容错；**需要知道指令长度**，x86 变长指令很难做对 |
| **③ 不返回** | `_exit()` / `abort()` / 恢复 `SIG_DFL` 后 `raise()` 重新抛出 | **绝大多数生产场景的正确选择** |

推荐写法（③的规范形式）：

```c
static void handler(int sig, siginfo_t *si, void *ctx)
{
    /* ... 记录 si_code / si_addr / backtrace ... */

    /* 恢复默认处置后重新抛出 → 让内核走正常终止路径（可产生 core） */
    struct sigaction sa = {0};
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sigaction(sig, &sa, NULL);
    raise(sig);
    /* 若 SIGKILL 之类不可捕获的，上面 raise 可能无效，兜底 */
    _exit(128 + sig);
}
```

**为什么不用 `exit()` 而用 `_exit()`**：`exit()` 会跑 atexit 处理器和 stdio 刷新，它们**不是 async-signal-safe** 的（会加锁，而锁可能正是崩溃现场持有的那把 → 死锁）。详见 [Ch21.2](../../chapter-21-signal-handlers/notes/21.2-other-methods-of-terminating-a-signal-ha.md)。

**HFT 特别警告**：绝对不要用 `longjmp()` 从 SIGSEGV handler 跳回主循环"继续交易"。内存已经损坏，订单簿状态不可信，继续下单可能造成真实亏损。正确动作是 `_exit()` + 触发风控平仓流程。

</details>

<details>
<summary><b>问 3：</b><code>si_addr</code> 在所有硬件信号里都表示"被访问的内存地址"吗？</summary>

**不是。** 这是最容易搞错的一点。

`uapi_siginfo.h:69` 的注释写的是：

```c
        /* SIGILL, SIGFPE, SIGSEGV, SIGBUS, SIGTRAP, SIGEMT */
        struct {
                void __user *_addr; /* faulting insn/memory ref. */
```

`faulting insn / memory ref` —— **"指令"或"内存引用"**，两者皆有。

| 信号 | `si_addr` 的含义 |
|------|------------------|
| `SIGSEGV` | **被访问的内存地址**（你要读/写的那个地址） |
| `SIGBUS` | 被访问的内存地址（`BUS_MCEERR_*` 时配合 `si_addr_lsb` 表示物理地址精度） |
| `SIGFPE` | ⚠️ **触发异常的指令地址** |
| `SIGILL` | ⚠️ **非法指令的地址** |
| `SIGTRAP` | 断点/陷阱相关地址 |

**为什么有这个差异？**

- 对 `SIGSEGV`/`SIGBUS`，故障根源是"你要访问某个内存"，CPU 把出错地址放进 `%cr2`（x86），内核从那里读到 `si_addr`——**地址本身就是诊断信息**。
- 对 `SIGFPE`/`SIGILL`，故障根源是"某条指令不合法"，数据地址无从谈起（比如除零没有"地址"这个概念），所以只能给**指令地址**。

**实战意义**：

```
SIGSEGV → si_addr=0x0           → 空指针，看代码哪里没判空
SIGSEGV → si_addr=0xdeadbeef    → 悬垂指针 / 未初始化指针
SIGSEGV → si_addr=0x41414141    → 被字符串 'AAAA' 覆盖的指针（典型的缓冲区溢出）
SIGFPE  → si_addr=0x401234      → 去 objdump -d 找 0x401234 那条 div/idiv 指令
SIGILL  → si_addr=0x7fff...     → PC 跳到栈上执行了 → 栈被踩坏，返回地址被覆盖
```

**配套字段**（`uapi_siginfo.h:161-168`）：

```c
#define si_trapno       _sifields._sigfault._trapno        /* alpha/sparc trap 号 */
#define si_addr_lsb     _sifields._sigfault._addr_lsb      /* BUS_MCEERR_* 的地址精度 */
#define si_lower        _sifields._sigfault._addr_bnd._lower   /* SEGV_BNDERR 下界 */
#define si_upper        _sifields._sigfault._addr_bnd._upper   /* SEGV_BNDERR 上界 */
#define si_pkey         _sifields._sigfault._addr_pkey._pkey   /* SEGV_PKUERR 保护键 */
#define si_perf_data    _sifields._sigfault._perf._data    /* TRAP_PERF 数据 */
#define si_perf_type    _sifields._sigfault._perf._type
#define si_perf_flags   _sifields._sigfault._perf._flags
```

注意它们共用 `union`，**同一时刻只有与 `si_code` 对应的那一个有意义**——读错字段会得到垃圾。

</details>

<details>
<summary><b>问 4：</b><code>SEGV_MAPERR</code> 和 <code>SEGV_ACCERR</code> 怎么区分？各自对应什么 bug？</summary>

```c
/* uapi_siginfo.h:232 */
#define SEGV_MAPERR     1       /* address not mapped to object */
#define SEGV_ACCERR     2       /* invalid permissions for mapped object */
```

| | `SEGV_MAPERR` | `SEGV_ACCERR` |
|--|---------------|---------------|
| 字面 | **地址未映射到任何对象** | **映射了，但权限不对** |
| 内核视角 | 页表里**没有这一项**（或该项 P 位为 0） | 页表有这一项，但权限位（R/W/X、U/S）不允许本次访问 |
| `si_addr` 常见值 | `0x0`、很小的数、随机垃圾值 | 一个"看起来正常"的地址（可能在 `.rodata`、代码段、内核空间） |

**对应的典型 bug**：

`SEGV_MAPERR`：

```c
int *p = NULL;       *p = 1;          /* 空指针 → si_addr = 0x0 */
free(q);             *q = 1;          /* 悬垂指针 → si_addr = 堆地址（可能已 munmap） */
int a[10];           a[100000] = 1;   /* 严重越界，跑到未映射区 */
struct S *s = ...;   s->field         /* 未初始化指针 → si_addr = 栈垃圾 */
```

`SEGV_ACCERR`：

```c
char *s = "literal";  s[0] = 'X';     /* .rodata 是只读的 */
/* mprotect(buf, n, PROT_READ) 之后写 buf */
((void(*)(void))code_segment)();      /* 代码段不可执行 → 但通常是 SIGSEGV/ACCERR 或 NX */
/* 从用户态访问内核地址 0xffffffff81000000 */
```

**一个有用的推论**：

> 如果 `si_addr` 是 `0x0` 或一个**非常小的值**（如 `0x8`、`0x10`），几乎可以确定是 **`SEGV_MAPERR` + 空指针/未初始化结构体指针**——因为低地址区（前几页）在 Linux 上被刻意留作未映射，专门用来捕获空指针访问。

**HFT 诊断速查**：

| `si_code` + `si_addr` 组合 | 最可能的原因 |
|---------------------------|--------------|
| `SEGV_MAPERR` + `si_addr ≈ 0` | 空指针 / 未检查的返回值 |
| `SEGV_MAPERR` + `si_addr` 是堆地址 | use-after-free |
| `SEGV_MAPERR` + `si_addr` 是栈地址 | 返回了局部变量的地址 / 栈已失效 |
| `SEGV_MAPERR` + `si_addr = 0x41414141` 等 | **缓冲区溢出覆盖了指针**（`AAAA`） |
| `SEGV_ACCERR` + `si_addr` 在 `.rodata` 区间 | 修改字符串字面量 |
| `SEGV_ACCERR` + `si_addr > 0xffff800000000000` | 试图访问内核地址 |

要确定 `si_addr` 落在哪个映射区，可以对比 `/proc/self/maps`：

```c
/* handler 里（用 open/read，不用 fopen/fgets —— 后者不是 async-signal-safe） */
int fd = open("/proc/self/maps", O_RDONLY);
/* 读出来逐行解析，找 si_addr 落在哪个区间 → 知道是堆/栈/.rodata/共享内存 */
```

<details>
<summary><b>问 5：</b>perf 事件也用 SIGTRAP，它和真正的陷阱信号有什么不同？内核是怎么处理的？</summary>

**关键差别：perf 事件用 `send_sig_info()`，不是 `force_*`**——即它**尊重**用户的阻塞设置，不会强行递送。

```c
/* kernel/signal.c:1824 */
int send_sig_perf(void __user *addr, u32 type, u64 sig_data)
{
        struct kernel_siginfo info;

        clear_siginfo(&info);
        info.si_signo     = SIGTRAP;
        info.si_errno     = 0;
        info.si_code      = TRAP_PERF;
        info.si_addr      = addr;
        info.si_perf_data = sig_data;
        info.si_perf_type = type;

        /*
         * Signals generated by perf events should not terminate the whole
         * process if SIGTRAP is blocked, however, delivering the signal
         * asynchronously is better than not delivering at all. But tell user
         * space if the signal was asynchronous, so it can clearly be
         * distinguished from normal synchronous ones.
         */
        info.si_perf_flags = sigismember(&current->blocked, info.si_signo) ?
                                     TRAP_PERF_FLAG_ASYNC : 0;

        return send_sig_info(info.si_signo, &info, current);
}
```

对比表：

| | 真陷阱（`TRAP_BRKPT` / `TRAP_HWBKPT`） | perf 事件（`TRAP_PERF`） |
|--|--------------------------------------|--------------------------|
| 内核函数 | `force_sig_fault(SIGTRAP, TRAP_BRKPT, addr)` | `send_sig_perf()` / `send_sig_info()` |
| 强制递送？ | ✅ 是（撤销忽略/阻塞） | ❌ 否（尊重用户设置） |
| 被阻塞时 | 强行解除阻塞并递送 | **延迟递送**，且 `si_perf_flags` 打上 `TRAP_PERF_FLAG_ASYNC` |
| 语义 | 必须处理（否则状态错乱） | 尽力而为（错过了就错过） |
| `si_perf_flags` | 0 | 异步时为 `TRAP_PERF_FLAG_ASYNC`（`uapi_siginfo.h:279`） |

**为什么要这样设计？**

注释说得很清楚（`:1836-1841`）：

> *"Signals generated by perf events should not terminate the whole process if SIGTRAP is blocked, however, delivering the signal asynchronously is better than not delivering at all. But tell user space if the signal was asynchronous, so it can clearly be distinguished from normal synchronous ones."*

两难处境：

- 用 `force_*`？不行——perf 采样是**高频**的（每秒数千次），如果强制解除阻塞，会严重干扰被采样程序（而且 SIGTRAP 的强制递送会让调试器逻辑混乱）。
- 用普通 `send_sig_info()`？也有问题——信号可能被延迟很久才递送，用户态拿到时**早已不是事件发生的时刻**，`si_addr`/`si_perf_data` 与当前 PC 对不上，会误判。

折中方案：**照常发送（不强制），但在 `si_perf_flags` 里明确标记"这次是异步的"**，让用户态自己决定怎么用。这是一个优秀的设计范式——**当无法保证语义时，用额外的标志位把不确定性显式暴露给使用者，而不是假装它不存在**。

**用户态该怎么用**：

```c
static void perf_handler(int sig, siginfo_t *si, void *ctx)
{
    if (si->si_code != TRAP_PERF)
        return;                          /* 不是 perf 事件 */

    if (si->si_perf_flags & TRAP_PERF_FLAG_ASYNC) {
        /* 异步递送：si_addr / si_perf_data 对应的时刻已经过去，
         * 与当前 PC 无对应关系 —— 只用于计数，不要用于精确定位 */
        g_perf_async_count++;
        return;
    }

    /* 同步递送：可以在这里安全地读取 si_perf_data，与当前上下文对应 */
    handle_perf_sample(si->si_perf_data, si->si_perf_type, si->si_addr);
}
```

**HFT 视角**：`perf` 的 `sigtrap=1` 模式常用于"采样触发式分析"——比如每 N 次 cache miss 触发一次信号，在 handler 里记录当时的调用栈。但由于**异步递送时上下文已经漂移**，这种做法的定位精度有限。更可靠的做法是让 perf 直接写 ring buffer（`perf_event_open` + `mmap`），用户态轮询读取——**零信号、零中断、零上下文漂移**。

</details>
