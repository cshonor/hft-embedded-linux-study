# 22.11 通过文件描述符获取信号（signalfd）

## 本节讲什么

1. `signalfd()` 如何把信号**变成一个文件描述符**——从此信号可以 `read()`、可以 `epoll`
2. 为什么**必须先阻塞**目标信号，不阻塞会怎样
3. `read()` 的语义细节——一次能读几个、缓冲区多小会报错

## 一、接口

```c
#include <sys/signalfd.h>

int signalfd(int fd, const sigset_t *mask, int flags);
/* fd = -1：创建新 fd；fd = 已有 signalfd：更新其 mask
 * flags：SFD_NONBLOCK、SFD_CLOEXEC（可位或）
 * 返回：成功返回 fd，失败 -1 */
```

这是 `signalfd4()` 的封装（多了 `flags` 控制非阻塞与 exec 时关闭）：

```c
// fs/signalfd.c:302
SYSCALL_DEFINE4(signalfd4, int, ufd, sigset_t __user *, user_mask,
		size_t, sizemask, int, flags)
```

## 二、为什么必须先阻塞信号

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigaddset(&mask, SIGTERM);

sigprocmask(SIG_BLOCK, &mask, NULL);        /* ← 必须！否则信号走 handler */
int sfd = signalfd(-1, &mask, 0);
```

**原因**：`signalfd` **不改变**信号的递送路径——它只是"旁路监听"。

```
   信号到达
     ├─ 未被阻塞 → 按 disposition 处理（跑 handler / 默认动作）→ signalfd 读不到
     └─ 被阻塞   → 进 pending → signalfd 可读出来 ✅
```

如果不阻塞，信号会正常触发 handler（或执行默认动作把进程杀掉），`signalfd` 根本看不到它。

> **这是使用 signalfd 最常见的错误**：忘了 `sigprocmask(SIG_BLOCK, ...)`，表现为"信号明明发了，`read` 却没反应"——实际上信号被 handler 或默认动作吃掉了（默认动作往往是终止进程）。

## 三、`read()` 的语义

```c
struct signalfd_siginfo si;
ssize_t n = read(sfd, &si, sizeof si);
```

### 缓冲区至少要有一个结构体的大小

```c
// fs/signalfd.c:211-213
	count /= sizeof(struct signalfd_siginfo);
	if (!count)
		return -EINVAL;                   /* ← 缓冲区太小 → EINVAL */
```

> **陷阱**：`read(sfd, &si, 8)` 这样的小缓冲会直接返回 `-1`，`errno = EINVAL`。缓冲区必须 **≥ `sizeof(struct signalfd_siginfo)`**（通常 128 字节）。

### 一次 `read()` 可读出多个信号

```c
// fs/signalfd.c:216-226
	do {
		ret = signalfd_dequeue(ctx, &info, nonblock);
		if (unlikely(ret <= 0))
			break;
		ret = signalfd_copyinfo(siginfo, &info);
		if (ret < 0)
			break;
		siginfo++;
		total += ret;
		nonblock = 1;                     /* ← 第一个之后强制非阻塞 */
	} while (--count);

	return total ? total: ret;
```

| 行为 | 说明 |
|------|------|
| **批量读取** | 缓冲区多大就最多读多少个（循环直到队列空或缓冲满） |
| **`nonblock = 1`** | 读出第一个后，后续强制非阻塞——**不会**在读第二个时阻塞等待 |
| 返回值 | 成功为**字节数**（`n × sizeof(struct signalfd_siginfo)`）；无信号且非阻塞时为 `-1/EAGAIN` |

**典型用法**：给一个大数组，一次把积压的信号全读出来：

```c
struct signalfd_siginfo sis[16];
ssize_t n = read(sfd, sis, sizeof sis);
for (size_t i = 0; i < n / sizeof(sis[0]); i++)
    handle(sis[i].ssi_signo);
```

## 四、`signalfd_siginfo` 字段

`read()` 出来的是 `struct signalfd_siginfo`（`include/uapi/linux/signalfd.h`），字段与 `siginfo_t` 对应但**命名加 `ssi_` 前缀**：

| 字段 | 对应 `siginfo_t` | 含义 |
|------|------------------|------|
| `ssi_signo` | `si_signo` | 信号编号 |
| `ssi_errno` | `si_errno` | 通常不用 |
| `ssi_code` | `si_code` | 来源/原因码 |
| `ssi_pid` | `si_pid` | 发送进程 PID |
| `ssi_uid` | `si_uid` | 发送进程 real UID |
| `ssi_fd` | `si_fd` | `SIGPOLL` 的就绪 fd |
| `ssi_band` | `si_band` | `SIGPOLL` 的事件掩码 |
| `ssi_addr` | `si_addr` | 故障地址（`SIGSEGV` 等） |
| **`ssi_int`** | `si_int` | `sigqueue` 携带的 `int` |
| **`ssi_ptr`** | `si_ptr` | `sigqueue` 携带的指针 |
| `ssi_status` | `si_status` | `SIGCHLD` 的子进程退出状态 |

> **注意**：`ssi_addr` 是 **64 位无符号整数**（`__u64`），不是指针类型——打印要用 `%llx` 而非 `%p`，避免编译器警告。

## 五、与 epoll 集成（核心用法）

```c
/* ① 阻塞关心的信号 */
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigaddset(&mask, SIGTERM);
sigaddset(&mask, SIGHUP);
sigprocmask(SIG_BLOCK, &mask, NULL);

/* ② 创建非阻塞 signalfd */
int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);

/* ③ 加入 epoll，与业务 socket 一起监听 */
int epfd = epoll_create1(EPOLL_CLOEXEC);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = sfd };
epoll_ctl(epfd, EPOLL_CTL_ADD, sfd, &ev);
/* ... 同时加入业务 socket ... */

/* ④ 统一事件循环 */
for (;;) {
    int n = epoll_wait(epfd, events, MAX, -1);
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == sfd) {
            struct signalfd_siginfo si;
            while (read(sfd, &si, sizeof si) == sizeof si) {
                /* 这里运行在普通上下文 —— 可随意 printf/malloc/写日志 */
                printf("信号 %d 来自 pid=%d\n", si.ssi_signo, si.ssi_pid);
                if (si.ssi_signo == SIGTERM) goto shutdown;
            }
        } else {
            handle_market_data(events[i].data.fd);
        }
    }
}
```

## 六、优势与限制

### 优势

| 优势 | 说明 |
|------|------|
| **无 handler** | 彻底摆脱异步信号安全限制——处理代码可随意 `printf`/`malloc`/加锁 |
| **无异步抢占** | 信号不会打断关键路径，只在 `epoll_wait` 返回后处理 → **延迟可预测** |
| **统一事件循环** | 信号与 I/O 同一个 `epoll_wait`，架构简洁 |
| **不丢失** | 内核维护队列（实时信号完全排队，标准信号仍合并） |
| **可获得完整信息** | `ssi_pid`/`ssi_uid`/`ssi_int` 等，等价于 `SA_SIGINFO` |
| **可 `SFD_CLOEXEC`** | exec 时自动关闭，避免 fd 泄漏到子进程 |

### 限制

| 限制 | 说明 |
|------|------|
| **Linux 专有** | 非 POSIX，BSD/Solaris 没有；可用 self-pipe 作为可移植替代 |
| **必须先阻塞** | 忘了阻塞会导致信号走 handler，signalfd 读不到 |
| **标准信号仍不排队** | `signalfd` 不解决 [Ch20.12](../../chapter-20-signals-fundamentals/notes/20.12-signals-are-not-queued.md) 的合并问题——同号标准信号多次到达仍只保留一份（实时信号才完整排队） |
| **`fork` 后需处理** | 子进程继承 fd，但通常应关闭并恢复默认处置 |
| **不能用于同步故障信号** | `SIGSEGV`/`SIGFPE`/`SIGBUS`/`SIGILL` 是**同步**信号（由指令触发，直接递送给当前线程），**不能**通过 signalfd 捕获——它们必须走 handler（配 `SA_ONSTACK`）|

> **最后一条很重要**：`SIGSEGV` 这类硬件异常信号由 CPU 异常同步产生，内核会直接递送给触发它的线程，**不会**进入 signalfd 的 pending 队列。所以崩溃诊断仍需传统 handler + 备用栈（[Ch21.3](../../chapter-21-signal-handlers/notes/21.3-handling-a-signal-on-an-alternate-stack-.md)）。

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | signalfd + epoll 统一事件循环，简化架构——告别 handler 的异步信号安全雷区。嵌入式常见的 `SIGHUP`（配置重载）、`SIGTERM`（优雅停机）都可纳入主循环。但 `SIGSEGV` 崩溃诊断**仍需要**传统 handler + `SA_ONSTACK` 备用栈，signalfd 覆盖不了同步故障信号 |
| HFT | **signal 处理的首选方案**。信号融入 epoll 避免 handler 中断热路径——把「异步抢占」变成「同步事件」，延迟完全可预测。这是低延迟系统的标准架构：交易主循环只 `epoll_wait`，停机/重载信号与行情数据在同一处处理。注意仍要屏蔽无关信号，且 `read` 时用批量数组一次读干净积压 |

## 代码示例：完整的 epoll + signalfd 事件循环

```c
/* sigfd.c —— signalfd + epoll 统一事件循环
 * 编译: gcc -D_GNU_SOURCE -o sigfd sigfd.c
 * 运行后另开终端: kill -TERM <pid> / kill -HUP <pid> / kill -USR1 <pid> */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/signalfd.h>
#include <sys/epoll.h>

#define MAX_EVENTS 8

int main(void)
{
    /* ① 阻塞关心的信号 —— 关键！不阻塞则信号走 handler */
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);
    sigaddset(&mask, SIGTERM);
    sigaddset(&mask, SIGHUP);
    sigaddset(&mask, SIGUSR1);
    sigprocmask(SIG_BLOCK, &mask, NULL);

    /* ② 创建 signalfd */
    int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
    if (sfd == -1) { perror("signalfd"); return 1; }

    /* ③ 加入 epoll */
    int epfd = epoll_create1(EPOLL_CLOEXEC);
    struct epoll_event ev = { .events = EPOLLIN, .data.fd = sfd };
    epoll_ctl(epfd, EPOLL_CTL_ADD, sfd, &ev);

    printf("PID=%d — 试: kill -TERM|-HUP|-USR1 %d （Ctrl+C 亦可）\n",
           getpid(), getpid());

    int running = 1;
    while (running) {
        struct epoll_event events[MAX_EVENTS];
        int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
        if (n == -1) {
            if (errno == EINTR) continue;      /* epoll_wait 仍可能 EINTR */
            perror("epoll_wait"); break;
        }

        for (int i = 0; i < n; i++) {
            if (events[i].data.fd != sfd) continue;

            /* ④ 批量读取：一次把积压的信号全读出来 */
            struct signalfd_siginfo sis[16];
            ssize_t bytes;
            while ((bytes = read(sfd, sis, sizeof sis)) > 0) {
                size_t cnt = (size_t)bytes / sizeof(sis[0]);
                for (size_t k = 0; k < cnt; k++) {
                    /* 普通上下文 —— 可随意 printf/malloc */
                    printf("信号 %2d  来自 pid=%d uid=%d  si_code=%d\n",
                           sis[k].ssi_signo, sis[k].ssi_pid,
                           sis[k].ssi_uid, sis[k].ssi_code);
                    if (sis[k].ssi_signo == SIGTERM ||
                        sis[k].ssi_signo == SIGINT)  running = 0;
                    else if (sis[k].ssi_signo == SIGHUP)
                        printf("  → 重载配置（模拟）\n");
                }
            }
            /* 非阻塞 fd 且无信号时 read 返回 -1/EAGAIN，正常 */
        }
    }

    printf("优雅退出\n");
    close(sfd);
    close(epfd);
    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b>为什么创建 signalfd 前必须阻塞目标信号？不阻塞会怎样？</summary>

因为 `signalfd` **不改变**信号的递送路径——它只是"旁路监听" pending 队列。

```
信号到达
  ├─ 未被阻塞 → 按 disposition 处理（跑 handler / 默认动作）→ signalfd 读不到
  └─ 被阻塞   → 进 pending → signalfd 可读出来 ✅
```

**不阻塞的后果**：

- 若注册了 handler → 信号走 handler，signalfd 永远读不到
- 若未注册（默认动作）→ 进程被终止（如 `SIGTERM` 默认 terminate），更读不到

**这是使用 signalfd 最常见的错误**，表现为"信号明明发了，`read` 却没反应"。

**正确顺序**：

```c
sigprocmask(SIG_BLOCK, &mask, NULL);        /* ① 先阻塞 */
int sfd = signalfd(-1, &mask, 0);           /* ② 再创建 */
```

**额外提醒**：阻塞之后，这些信号对**所有线程**都阻塞（若在创建线程前设置，新线程会继承）。这正是我们想要的——信号统一由 signalfd 处理，任何线程都不会被 handler 打断。

</details>

<details>
<summary><b>问 2：</b><code>read(sfd, &si, 8)</code> 这样的小缓冲会怎样？一次 <code>read</code> 能读几个信号？</summary>

**小缓冲直接报错**：

```c
// fs/signalfd.c:211-213
	count /= sizeof(struct signalfd_siginfo);
	if (!count)
		return -EINVAL;
```

缓冲区不足一个 `signalfd_siginfo`（通常 128 字节）时，`read` 返回 `-1`，`errno = EINVAL`。

**一次 `read` 可读多个**：

```c
// fs/signalfd.c:216-226
	do {
		ret = signalfd_dequeue(ctx, &info, nonblock);
		if (unlikely(ret <= 0)) break;
		ret = signalfd_copyinfo(siginfo, &info);
		if (ret < 0) break;
		siginfo++;
		total += ret;
		nonblock = 1;             /* ← 第一个之后强制非阻塞 */
	} while (--count);
```

- 缓冲区多大，就最多读多少个（循环直到队列空或缓冲满）
- **关键**：读出第一个后设置 `nonblock = 1`，所以**不会**在读第二个时阻塞等待
- 返回值是**字节数** = `n × sizeof(struct signalfd_siginfo)`

**推荐用法**：给一个数组，一次把积压读干净：

```c
struct signalfd_siginfo sis[16];
ssize_t n = read(sfd, sis, sizeof sis);
for (size_t i = 0; i < n / sizeof(sis[0]); i++)
    handle(sis[i].ssi_signo);
```

</details>

<details>
<summary><b>问 3：</b>signalfd 能捕获 <code>SIGSEGV</code> 吗？为什么？</summary>

**不能。** `SIGSEGV`/`SIGFPE`/`SIGBUS`/`SIGILL` 这类**同步故障信号**无法通过 signalfd 捕获。

**原因**：它们由 **CPU 异常同步产生**，直接递送给触发它的**那个线程**，内核走的是 `force_sig_fault()`（`kernel/signal.c:1740`）路径——**不会**进入 signalfd 监听的 pending 队列让进程去"读"。

这类信号必须走传统 handler，且必须配 `SA_ONSTACK` 备用栈（[Ch21.3](../../chapter-21-signal-handlers/notes/21.3-handling-a-signal-on-an-alternate-stack-.md)）——因为栈溢出时原栈已无空间，handler 需要备用栈才能执行。

**signalfd 能处理的是异步信号**：

| 类型 | 例子 | 能否用 signalfd |
|------|------|----------------|
| **异步**（外部产生） | `SIGTERM`、`SIGINT`、`SIGHUP`、`SIGUSR1/2`、实时信号 | ✅ |
| **同步**（CPU 异常） | `SIGSEGV`、`SIGBUS`、`SIGFPE`、`SIGILL`、`SIGTRAP` | ❌ 必须走 handler |
| **同步**（系统调用） | `SIGSYS`（seccomp）、`SIGXFSZ`、`SIGXCPU` | ❌ 一般走 handler |

**实践结论**：生产程序通常**两者都用**——signalfd 处理控制类信号（停机/重载），传统 handler + 备用栈处理崩溃诊断。

</details>

<details>
<summary><b>问 4：</b>signalfd 能解决「标准信号不排队」的问题吗？</summary>

**不能。** signalfd 只改变信号的**读取方式**，不改变**排队语义**。

标准信号（`SIGTERM`/`SIGINT`/`SIGUSR1` 等）在 pending 位图中仍只有一个位——阻塞期间同号信号到达 5 次，`read()` 出来仍只有**一份**。

排队规则取决于信号类型（回顾 [Ch20.12](../../chapter-20-signals-fundamentals/notes/20.12-signals-are-not-queued.md) 的 `legacy_queue:1079`）：

| 信号类型 | signalfd 中能 read 出几次 |
|----------|--------------------------|
| 标准信号（1–31） | **1 次**（合并） |
| 实时信号（`SIGRTMIN`+） | **N 次**（完整排队，且 `ssi_int` 数据保留） |

**如果需要不丢事件**：

1. 用**实时信号 + `sigqueue()`**——配合 signalfd 可读出每一次及其 `ssi_int`
2. 改用 **eventfd**——内核计数器，天然累计次数，永不丢
3. 改用**共享内存原子计数器**——零 syscall，HFT 热路径首选

**signalfd 真正解决的是**：异步信号安全问题、handler 抢占关键路径、无法接入事件循环——而**不是**排队问题。

</details>

<details>
<summary><b>问 5：</b>对比 signalfd、<code>sigwaitinfo</code>、self-pipe 三种「无 handler」方案。</summary>

| 方案 | 机制 | 可接入 epoll | 可移植性 | 特点 |
|------|------|-------------|----------|------|
| **signalfd** | 信号变 fd，`read()` 出来 | ✅ 原生 | ❌ Linux 专有 | **最干净**；一次 read 多个；批量处理 |
| **`sigwaitinfo`** | 同步"取"信号，返回信号编号 | ❌（需额外唤醒） | ✅ POSIX | 多线程专用线程模型；天然同步阻塞 |
| **self-pipe** | handler 写管道一字节，主流程 `read` | ✅ | ✅ POSIX | 需要保留一个极简 handler；多一次 syscall |

**选择建议**：

| 场景 | 推荐 |
|------|------|
| Linux 专用 + 事件循环架构 | **signalfd**（首选） |
| 需要跨平台 | self-pipe |
| 多线程 + 专用信号处理线程 | **`sigwaitinfo`** |
| 需要把信号当"同步函数调用" | `sigwaitinfo` |

**HFT 视角**：

- **signalfd** 是最优解——零 handler、零抢占、延迟可预测、批量读取
- `sigwaitinfo` 适合管理线程（它阻塞等待，不适合主循环）
- self-pipe 是 signalfd 不可用时的退路（但仍需一个只做 `write` 的极简 handler）

> 三者的共同价值：**把信号从"异步抢占"变成"同步事件"**——这才是低延迟系统需要的语义。
