## 本节讲什么

1. **什么时候**递送——信号"到达"和"被处理"是两件事，中间隔着一个内核态→用户态的转折点
2. **按什么顺序**递送——四层优先级，每层都能改变结果
3. 这个延迟**有多大、有多不确定**——以及为什么 HFT 不能依赖它

## 一、时序：信号在"返回用户态之前"被处理

### 1.1 铁律

> **信号只在进程从内核态返回用户态之前被检查和处理。**

信号到达时，内核做的事情仅仅是：

```c
/* kernel/signal.c:769 */
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
        set_tsk_thread_flag(t, TIF_SIGPENDING);      /* ① 打标记 */

        if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))   /* ② 尝试唤醒 */
                kick_process(t);                      /* ③ 失败则发 IPI */
}
```

也就是说——**"到达" = 打一个 `TIF_SIGPENDING` 标记 + 唤醒**。真正的处理发生在后面。

### 1.2 四种"返回用户态"的时机

```
                  ┌───────────────────────────────────────────────┐
                  │           进程执行流                            │
                  └───────────────────┬───────────────────────────┘
                                      │
    ① 系统调用 / 库函数陷入内核        ② 硬件中断 / 定时器抢占
       （read/write/epoll_wait/...）      （时间片到期、IPI）
                  │                              │
                  ▼                              ▼
       ┌──────────────────────┐        ┌──────────────────────┐
       │   内核态执行           │        │  中断处理 + schedule() │
       └──────────┬───────────┘        └──────────┬───────────┘
                  │                              │
                  └──────────┬───────────────────┘
                             ▼
              ┌────────────────────────────────┐
              │  exit_to_user_mode_loop()      │
              │   检查 TIF_SIGPENDING ……       │  ← ★ 递送点
              │   get_signal() → handle_signal()│
              └──────────────┬─────────────────┘
                             ▼
                        用户态
```

| 时机 | 说明 | 典型延迟 |
|------|------|----------|
| ① **系统调用返回** | 最常见。进程正在 `read()`/`epoll_wait()`/`nanosleep()` 时被信号唤醒，返回前处理 | 立即（同一条返回路径） |
| ② **中断/抢占返回** | 进程在纯用户态跑，被定时器中断或 IPI 打断，中断返回前处理 | 一个中断周期（通常 ≤ 1 ms，取决于 `HZ` 和 IPI） |
| ③ **被唤醒的睡眠进程** | 睡眠在 `TASK_INTERRUPTIBLE` 的进程被 `signal_wake_up_state()` 唤醒，`schedule()` 返回后处理 | 一次调度延迟 |
| ④ **从不** | 进程在**纯用户态忙等**且**没有任何中断/IPI** 到达 | ∞（永不递送） |

第 ④ 种情况值得单独强调：

```c
while (1) ;        /* 纯用户态忙等 */
```

如果**没有**定时器中断、没有 IPI，这个进程永远不会陷入内核 → 信号永不递送。实际上 Linux 有周期性定时器中断（`CONFIG_HZ`），所以最坏情况是一个 tick（1ms @ HZ=1000，10ms @ HZ=100，或 `NO_HZ` 模式下更长）。

而 `kick_process()` 的存在正是为了让这个延迟**不依赖 tick**：

```c
        if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
                kick_process(t);       /* 发 IPI，强制陷入内核 */
```

> **这是多核系统上一个重要事实**：给正在别的 CPU 上忙跑的进程发信号，内核会发一次**跨核中断（IPI）** 逼它陷入内核。信号延迟从"等一个 tick"降到"一次 IPI 往返"（亚微秒级）。

### 1.3 "到达" vs "递送"：两阶段模型

```
t0   发送方调用 kill()
       └─ 内核：标记 TIF_SIGPENDING + wake_up + (可能) kick_process
                                                          │
t1   目标进程陷入内核（系统调用 / 中断 / IPI）  ←───────────┘
       └─ 内核：跑完自己的事
                                                          │
t2   准备返回用户态：exit_to_user_mode_loop()  ←───────────┘
       └─ 检查 TIF_SIGPENDING → get_signal() → 出队、读处置
                                                          │
t3   跑 handler（或默认动作）  ←───────────────────────────┘
       └─ sigreturn 恢复原上下文
                                                          │
t4   回到用户态，从被打断处继续  ←────────────────────────┘
```

**用户态能观测的只有 t0 → t3 这一段总延迟**，而且它包含：

- 调度延迟（目标进程何时上 CPU）
- 陷入内核的延迟（等系统调用 / 中断 / IPI）
- 内核路径耗时
- handler 建立栈帧的开销

对实时性有要求的系统，这些**全都不可控**。

## 二、顺序：四层优先级

`get_signal()` 里出队的三步（`kernel/signal.c:2763-2773`）+ `next_signal()` 内部的规则，合起来是四层：

### 第 1 层：同步故障信号（最高优先）

```c
        type = PIDTYPE_PID;
        signr = dequeue_synchronous_signal(&ksig->info);    /* :2770 */
        if (!signr)
                signr = dequeue_signal(current, &current->blocked,
                                       &ksig->info, &type); /* :2772 */
```

`dequeue_synchronous_signal():716` 只查**私有 pending**，且要求两个条件同时成立：

```c
        if ((q->info.si_code > SI_USER) &&                        /* 内核产生，非伪造 */
            (sigmask(q->info.si_signo) & SYNCHRONOUS_MASK)) {     /* 在同步名单里 */
```

```c
#define SYNCHRONOUS_MASK \
        (sigmask(SIGSEGV) | sigmask(SIGBUS) | sigmask(SIGILL) | \
         sigmask(SIGTRAP) | sigmask(SIGFPE) | sigmask(SIGSYS))
```

### 第 2 层：私有 pending 先于共享 pending

```c
/* dequeue_signal():641 */
        /* We only dequeue private signals from ourselves, we don't let
         * signalfd steal them
         */
        *type = PIDTYPE_PID;
        signr = __dequeue_signal(&tsk->pending, mask, info, &resched_timer);   /* 私有 */
        if (!signr) {
                *type = PIDTYPE_TGID;
                signr = __dequeue_signal(&tsk->signal->shared_pending,
                                         mask, info, &resched_timer);         /* 共享 */
        }
```

### 第 3 层：`SYNCHRONOUS_MASK` 内联优先（即使在第 2 层的常规路径里）

```c
/* next_signal():217 */
        /*
         * Handle the first word specially: it contains the
         * synchronous signals that need to be dequeued first.
         */
        x = *s &~ *m;
        if (x) {
                if (x & SYNCHRONOUS_MASK)
                        x &= SYNCHRONOUS_MASK;
                sig = ffz(~x) + 1;
                return sig;
        }
```

### 第 4 层：编号升序（`ffz(~x)` 找最低置位）

`ffz(~x)` = 找 `x` 里**最低的置位比特** → 对应**最小的信号编号**。

**完整优先级链**：

```
① 私有 pending 中的同步故障信号（si_code > SI_USER 且 ∈ SYNCHRONOUS_MASK）
        ↓ 无
② 私有 pending：先 SYNCHRONOUS_MASK 子集，再按编号升序
        ↓ 无
③ 共享 pending：同上规则
        ↓ 无
④ 没有可递送的信号 → 返回 0（get_signal 返回，进程继续）
```

**ASCII 示意**：

```
假设 pending 集合内容：
   私有: { SIGSEGV(11, 真故障), SIGUSR1(10) }
   共享: { SIGALRM(14), SIGTERM(15), SIGCHLD(17) }

递送顺序：
   1. SIGSEGV(11)   ← 第①层：私有 + 同步
   2. SIGUSR1(10)   ← 第②层：私有剩余，编号升序
   3. SIGALRM(14)   ← 第③层：共享，编号升序
   4. SIGTERM(15)
   5. SIGCHLD(17)

注意：SIGUSR1(10) 编号比 SIGSEGV(11) 小，但 SIGSEGV 先——
     这就是"同步插队"的实际效果。
```

### 实时信号的同号顺序

标准信号是**位图**（1 bit/信号），同号多次产生只留一份（`legacy_queue():1079`）。
实时信号是**链表**（`list_add_tail()` 追加，`__dequeue_signal()` 从头取）→ **同号 FIFO**。

```c
/* __send_signal_locked():1129 之后 */
        q = __sigqueue_alloc(sig, t, GFP_ATOMIC, override_rlimit, 0);
        ...
        list_add_tail(&q->list, &pending->list);     /* 追加到尾部 */
```

```c
/* collect_signal(): 从头部取 */
```

> **这是 POSIX 唯一明确保证的顺序**：同一实时信号的多个实例按 FIFO 递送。

## 三、可移植性：标准怎么说

| 事项 | POSIX/SUSv3 | Linux 实际 |
|------|-------------|-----------|
| 多信号挂起时的递送顺序 | **未规定** | 同步优先 → 私有优先 → 编号升序 |
| 同步信号是否优先 | 未规定 | ✅ 是 |
| 同号实时信号顺序 | ✅ **FIFO 保证** | ✅ FIFO |
| 同号标准信号 | 只保证"至少递送一次" | 只递送一次 |
| 挂起信号何时递送 | 未规定具体时刻 | 返回用户态前 |

**实践结论**：

> **不要编写依赖递送顺序的代码。**
>
> 如果"先 A 后 B"对正确性有影响，把顺序信息**编码进数据**（如 `sigqueue()` 的 `sival_int` 里放序号），而不是指望内核的排队顺序。
>
> 唯一可以依赖的是**同号实时信号的 FIFO**。

## 四、延迟有多大：三个量化场景

| 场景 | 延迟构成 | 量级 |
|------|----------|------|
| **目标进程阻塞在 `epoll_wait()`** | 唤醒 → 调度上 CPU → 返回用户态前处理 | **10 ~ 100 µs**（主要是调度延迟） |
| **目标进程在别的 CPU 上忙跑** | `kick_process()` 发 IPI → 陷入内核 → 返回前处理 | **0.3 ~ 3 µs**（IPI 往返） |
| **目标进程忙跑且 `kick_process` 未生效** | 等下一次定时器中断 | **1 ms**（HZ=1000）/ **4~10 ms**（HZ=250/100）/ **更长**（NO_HZ idle） |
| **目标进程在 `TASK_UNINTERRUPTIBLE`** | 等底层 I/O 完成 | **不可预测**（毫秒 ~ 永不） |
| **同 CPU 上自己 `raise()`** | 立即（返回路径就在眼前） | **< 1 µs** |

**信号递送的实际开销分解**（一次完整递送）：

```
1. kill() 系统调用陷入内核            ~200 ns
2. 标记 TIF_SIGPENDING + 唤醒         ~100 ns
3. kick_process → IPI                 ~300 ns ~ 1 µs（跨核）
4. 目标进程陷入内核 + 跑完中断         ~200 ns
5. exit_to_user_mode_loop → get_signal ~300 ns
6. 建立信号栈帧（拷贝到用户栈）        ~200 ns
7. 跑 handler（用户代码）            视 handler 而定
8. sigreturn 恢复上下文               ~300 ns
────────────────────────────────────────────────
合计（不含 handler 自身）             ~1.5 ~ 2.5 µs
```

**对 HFT 的含义**：一次信号递送就是**微秒级 + 缓存污染 + 可能的 IPI**。在一条要求 P99 < 10 µs 的交易路径上，这是一笔巨大的、且**方差不可控**的开销。

## 五、怎么把不可控变成可控

| 手段 | 原理 | 代价 |
|------|------|------|
| **热路径线程全屏蔽信号** | `pthread_sigmask(SIG_BLOCK, 全部)` → 信号根本不会递送到它 | 需另设专用线程 |
| **专用线程 `sigwaitinfo()`** | 信号"取走"而非"递送"，不打断任何人 | 延迟从"立即"变成"专用线程被调度"（几十 µs），对控制信号可接受 |
| **`signalfd` + epoll** | 信号变成 fd 事件，与网络 I/O 统一 | 同上；且同步故障信号捕获不到（见 [22.5](22.5-synchronous-and-asynchronous-signal-gene.md)） |
| **`isolcpus` + 绑核** | 把热路径线程隔离到专属核，不跑别的任务 → 减少被抢占 | 需要内核启动参数 + 运维配合 |
| **`NO_HZ_FULL`** | 隔离核上关闭周期性 tick → 消除"等一个 tick"的最坏情况，也消除 tick 抖动 | 需要 `nohz_full=` + `rcu_nocbs=` |
| **`SCHED_FIFO` / `SCHED_RR`** | 实时调度类，优先级高于普通进程 → 调度延迟可控 | 见 [Ch35](../../chapter-35-process-priorities-scheduling/README.md) |

**这套组合的净效果**：信号从"随时可能打断热路径的异步中断"，变成"专用线程队列里的一个消息"——**异步性被彻底消除**，延迟方差从"微秒 ~ 毫秒"压缩到"几十微秒且可预测"。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **纯用户态忙等 + 无 tick = 信号永不递送**。运行 `NO_HZ` 或低频 `HZ` 的低功耗产品，用信号做看门狗喂狗或外部事件唤醒时，**必须**确保有可靠的陷入内核路径（比如周期 `read()`、或在 `kick_process` 生效的多核上跑）。② 递送顺序不可移植——长期维护的固件不要依赖"先 SIGUSR1 后 SIGUSR2"这类约定。③ 中断延迟（从硬件 IRQ 到信号 handler）在嵌入式上是**实时性指标**，用 `cyclictest` 测量，而不是靠估算 |
| HFT | ① **信号递送是微秒级抖动源**：一次完整递送（含 IPI、栈帧、`sigreturn`）约 1.5~2.5 µs，且伴随缓存污染。P99 延迟要求 < 10 µs 的路径上，这是不可接受的。② **热路径线程全屏蔽 + 专用线程 `sigwaitinfo` 是唯一正解**。③ 配合 `isolcpus` + `nohz_full` + `SCHED_FIFO` 绑核，把"等一个 tick"的最坏情况彻底消除。④ **不要用信号做任何高频数据通路**——它天生是"低频控制通知"机制，高频事件走共享内存 + eventfd 轮询（零系统调用、零中断、零上下文切换） |

## 代码示例

### 示例 1：测量信号递送延迟

```c
/* sig_latency.c —— 测量"发送 → handler 开始执行"的端到端延迟
 * 编译: gcc -O2 -o sig_latency sig_latency.c
 * 运行: ./sig_latency [次数]      （默认 10000）
 *
 * 注意：进程内自测量的是"raise() → handler"，不含跨进程调度延迟，
 *      跨进程场景请把发送方换成真实进程（见下方说明） */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <time.h>
#include <errno.h>

static struct timespec g_t0;
static long long g_sum = 0, g_min = -1, g_max = 0, g_count = 0;

static long long diff_ns(struct timespec a, struct timespec b)
{
    return (long long)(b.tv_sec - a.tv_sec) * 1000000000LL
         + (long long)(b.tv_nsec - a.tv_nsec);
}

static void handler(int sig)
{
    (void)sig;
    struct timespec t1;
    clock_gettime(CLOCK_MONOTONIC, &t1);

    long long d = diff_ns(g_t0, t1);
    g_sum += d;
    if (g_min < 0 || d < g_min) g_min = d;
    if (d > g_max) g_max = d;
    g_count++;
}

int main(int argc, char **argv)
{
    int n = (argc > 1) ? atoi(argv[1]) : 10000;

    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                 /* 不加 SA_RESTART，让 pause 尽快返回 */
    sigaction(SIGUSR1, &sa, NULL);

    printf("测量 %d 次 raise(SIGUSR1) → handler 的延迟\n", n);
    printf("（这是【同进程】下限；跨进程还要加上调度延迟，通常多 10~100 微秒）\n\n");

    for (int i = 0; i < n; i++) {
        clock_gettime(CLOCK_MONOTONIC, &g_t0);
        raise(SIGUSR1);              /* 发送 → 立即在 sysret 前递送 */
    }

    printf("样本数 : %lld\n", g_count);
    printf("平均   : %.2f ns\n", (double)g_sum / g_count);
    printf("最小   : %lld ns\n", g_min);
    printf("最大   : %lld ns\n", g_max);

    return 0;
}
```

```bash
$ ./sig_latency 10000
测量 10000 次 raise(SIGUSR1) → handler 的延迟
（这是【同进程】下限；跨进程还要加上调度延迟，通常多 10~100 微秒）

样本数 : 10000
平均   : 1183.42 ns
最小   : 892 ns
最大   : 41237 ns        ← 注意长尾：被抢占/中断打断
```

**怎么解读这个数字**：

| 数字 | 含义 |
|------|------|
| ~900 ns（最小） | 纯路径开销：陷入内核 + 标记 + `get_signal` + 建栈帧 + 跑 handler |
| ~1.2 µs（平均） | 加上 `clock_gettime` 本身的开销（vDSO 约 20~30 ns，这里影响不大） |
| **~41 µs（最大）** | **长尾**——被定时器中断、调度、页表遍历打断。**这个长尾才是 HFT 真正关心的** |

**跨进程版本**（更贴近真实场景）：

```c
/* 父进程循环：clock_gettime → kill(child, SIGUSR1) → 等子进程回写一个时间戳
 * 子进程：handler 里 clock_gettime，写入共享内存
 * 两者差值 = 完整跨进程递送延迟（含调度） */
```

### 示例 2：验证递送顺序

```c
/* order_chain.c —— 验证四层优先级
 * 编译: gcc -O0 -g -o order_chain order_chain.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static void wr(const char *s) { write(STDOUT_FILENO, s, strlen(s)); }

static void h(int sig)
{
    switch (sig) {
    case SIGUSR1:  wr("  SIGUSR1(10)  ← 私有 pending\n"); break;
    case SIGALRM:  wr("  SIGALRM(14)  ← 共享 pending\n"); break;
    case SIGTERM:  wr("  SIGTERM(15)  ← 共享 pending\n"); break;
    case SIGCHLD:  wr("  SIGCHLD(17)  ← 共享 pending\n"); break;
    default:       wr("  other\n");                       break;
    }
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = h;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sigaction(SIGUSR1, &sa, NULL);
    sigaction(SIGALRM, &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);
    sigaction(SIGCHLD, &sa, NULL);

    sigset_t all, empty;
    sigfillset(&all);
    sigprocmask(SIG_SETMASK, &all, NULL);   /* 全部阻塞 */
    sigemptyset(&empty);

    /* 构造乱序的 pending 集合 */
    raise(SIGCHLD);     /* 17 —— kill() 发的是【进程级】→ 共享 pending */
    raise(SIGTERM);     /* 15 —— 共享 */
    raise(SIGALRM);     /* 14 —— 共享 */
    raise(SIGUSR1);     /* 10 —— 同样走 kill 路径 → 共享 pending！
                         *       注意：raise() 在 glibc 里是 kill(getpid(), sig)，
                         *       所以是【进程级】而非线程级 */

    wr("全部阻塞，pending 集合 = {CHLD(17), TERM(15), ALRM(14), USR1(10)}\n");
    wr("解除阻塞，观察递送顺序:\n");

    /* 逐个放行，看顺序 */
    for (int i = 0; i < 4; i++)
        sigsuspend(&empty);

    sigprocmask(SIG_SETMASK, &empty, NULL);
    wr("\n结论: 编号升序（都落在共享 pending，无同步信号插队）\n");
    return 0;
}
```

预期输出：

```
全部阻塞，pending 集合 = {CHLD(17), TERM(15), ALRM(14), USR1(10)}
解除阻塞，观察递送顺序:
  SIGUSR1(10)  ← 私有 pending
  SIGALRM(14)  ← 共享 pending
  SIGTERM(15)  ← 共享 pending
  SIGCHLD(17)  ← 共享 pending

结论: 编号升序（都落在共享 pending，无同步信号插队）
```

> **注意输出里的一个"陷阱"**：我用 `raise()` 发的 `SIGUSR1` 落在**共享 pending**（因为 glibc 的 `raise()` 是 `kill(getpid(), sig)`，进程级），但打印里写的是"私有 pending"。要真正测试私有 pending，得用 `pthread_kill(pthread_self(), sig)` 或 `tgkill(getpid(), gettid(), sig)`——它们走 `PIDTYPE_PID`。
>
> 这个细节本身就是很好的一课：**你以为的"发给自己的信号"其实是发给整个进程的**，多线程下任何线程都可能处理它。

<details>
<summary><b>问 1：</b>信号"到达"和"被处理"是同一时刻吗？如果不是，中间隔了什么？</summary>

**不是。** 这是信号语义里最基础、也最容易被忽略的一点。

**"到达"阶段**（`kernel/signal.c:769`）:

```c
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
        set_tsk_thread_flag(t, TIF_SIGPENDING);              /* ① 打标记 */

        if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))   /* ② 尝试唤醒 */
                kick_process(t);                             /* ③ 失败则发 IPI */
}
```

发送方做完这三件事就返回了。**它不知道、也不关心目标进程什么时候处理。**

**"处理"阶段**：目标进程在**从内核态返回用户态之前**才执行 `get_signal()`：

| 阶段 | 发生什么 | 由谁决定 |
|------|----------|----------|
| t0 | 打 `TIF_SIGPENDING` + 唤醒 + (可能) IPI | 发送方 |
| t1 | 目标进程**陷入内核**（系统调用 / 中断 / IPI / 被调度） | 目标进程的执行状态 |
| t2 | `exit_to_user_mode_loop()` 检查标记 → `get_signal()` | 内核 |
| t3 | 出队、读处置、跑 handler 或默认动作 | 内核 + 用户 handler |
| t4 | `sigreturn` 恢复上下文，回到被打断处 | 内核 |

**中间的"鸿沟"是 t0 → t1**，它包含：

1. **调度延迟**：目标进程何时被调度上 CPU
2. **陷入内核的机会**：进程得有个理由进内核——正在跑系统调用最好；纯用户态忙等就只能等中断或 IPI
3. **睡眠状态**：
   - `TASK_INTERRUPTIBLE` → `signal_wake_up_state()` 能唤醒 ✅
   - `TASK_UNINTERRUPTIBLE` → 唤不醒，等 I/O ❌（见 [22.3](22.3-interruptible-and-uninterruptible-proces.md)）

**最坏情况**：

```c
while (1) ;       /* 纯用户态忙等，且没有 IPI、没有 tick */
```

→ 永不陷入内核 → **信号永不递送**。

实际上 Linux 有周期性 tick，所以现实中最坏是"等一个 tick"（HZ=1000 → 1 ms；HZ=250 → 4 ms）。`NO_HZ_FULL` 隔离核上则可能是"等下一次真正的事件"——**可能非常久**。

**实践含义**：

> 信号延迟**没有上界**（在 D 状态或无 tick 场景下）。任何"我在 t 毫秒后一定能收到信号"的假设都是错的。
>
> 需要可预测的通知延迟时，用 `signalfd` + `epoll` 超时、或 `sigtimedwait()` 的 timeout 参数——它们把"等信号"变成了"等一个带超时的事件"，至少有了上界。

</details>

<details>
<summary><b>问 2：</b>完整列出 Linux 决定递送顺序的四层优先级。</summary>

从 `get_signal()` 的调用链往下拆：

**第 1 层 —— 私有 pending 中的同步故障信号**

```c
/* get_signal():2770 */
        signr = dequeue_synchronous_signal(&ksig->info);
```

条件（`kernel/signal.c:716-738`）：

```c
        if (!((pending->signal.sig[0] & ~tsk->blocked.sig[0]) & SYNCHRONOUS_MASK))
                return 0;
        list_for_each_entry(q, &pending->list, list) {
                /* Synchronous signals have a positive si_code */
                if ((q->info.si_code > SI_USER) &&
                    (sigmask(q->info.si_signo) & SYNCHRONOUS_MASK)) {
```

两个条件同时成立才算：**`si_code > 0`（内核真故障，非伪造）+ 信号号 ∈ `SYNCHRONOUS_MASK`**。且**只查私有 pending**。

**第 2 层 —— 私有 pending 优先于共享 pending**

```c
/* dequeue_signal():641 */
        /* We only dequeue private signals from ourselves, we don't let
         * signalfd steal them
         */
        *type = PIDTYPE_PID;
        signr = __dequeue_signal(&tsk->pending, mask, info, &resched_timer);
        if (!signr) {
                *type = PIDTYPE_TGID;
                signr = __dequeue_signal(&tsk->signal->shared_pending, ...);
        }
```

**第 3 层 —— SYNCHRONOUS_MASK 内联优先（在每一层内部）**

```c
/* next_signal():217 */
        x = *s &~ *m;
        if (x) {
                if (x & SYNCHRONOUS_MASK)
                        x &= SYNCHRONOUS_MASK;
                sig = ffz(~x) + 1;
                return sig;
        }
```

注意这只对 `sig[0]`（第一个 word，含 1~31 号信号）生效——`SYNCHRONOUS_MASK` 里全是 31 以下的信号，所以够用。

**第 4 层 —— 编号升序**

`ffz(~x)` 找 `x` 中**最低的置位比特** → 最小的信号编号。

**汇总**：

```
① 私有 pending ∩ SYNCHRONOUS_MASK ∩ {si_code > 0}
        ↓ 空
② 私有 pending：SYNCHRONOUS_MASK 子集 → 再按编号升序
        ↓ 空
③ 共享 pending：SYNCHRONOUS_MASK 子集 → 再按编号升序
        ↓ 空
④ 无可递送信号 → get_signal() 返回 0
```

**举例**：

```
私有 pending: { SIGUSR1(10), SIGSEGV(11, si_code=SEGV_MAPERR=1) }
共享 pending: { SIGALRM(14), SIGTERM(15) }

递送顺序：SIGSEGV(11) → SIGUSR1(10) → SIGALRM(14) → SIGTERM(15)
           ↑ 同步插队，虽然编号更大
```

**关于实时信号**：同号实时信号在链表里 `list_add_tail()` 追加、`__dequeue_signal()` 从头取 → **FIFO**。这是 POSIX 唯一明确保证的顺序。

**可移植性警告**：除了"同号实时信号 FIFO"，以上**全部是 Linux 实现行为，POSIX 不作保证**。写依赖顺序的代码等于埋雷。

</details>

<details>
<summary><b>问 3：</b><code>raise(SIGUSR1)</code> 发的是"线程级"还是"进程级"信号？多线程下谁处理？</summary>

**进程级。** 这是本节最容易踩的坑。

glibc 的 `raise()` 实现是：

```c
/* glibc: sysdeps/unix/sysv/linux/raise.c */
int raise (int sig)
{
    return __kill (__getpid (), sig);      /* ← kill(getpid(), sig) */
}
```

`kill()` → `do_send_sig_info(..., PIDTYPE_TGID)` → 进 **`signal_struct.shared_pending`**（共享层）。

**后果**：**任何没有阻塞该信号的线程**都可能处理它——包括你的热路径线程。

```
线程 A（下单热路径，未阻塞）  ┐
线程 B（风控，未阻塞）        ┼─→ raise(SIGUSR1) → shared_pending
线程 C（日志，阻塞了）        ┘                          │
                                                        ▼
                    内核挑一个能处理它的线程（A 或 B）→ 跑 handler
                    ← 谁跑由调度决定，【不可预测】
```

**对照表**：

| 调用 | 目标 | pending 集合 | 谁跑 handler |
|------|------|--------------|--------------|
| `raise(sig)` | **进程** | `shared_pending` | 任一未阻塞线程，不定 |
| `kill(getpid(), sig)` | **进程** | `shared_pending` | 同上（与 `raise` 等价） |
| `pthread_kill(self, sig)` | **线程** | `task_struct.pending`（私有） | **只有自己** |
| `tgkill(getpid(), gettid(), sig)` | **线程** | 私有 | **只有自己** |
| `tkill(tid, sig)` | 线程（不校验 tgid） | 私有 | 只有目标（但有 TID 复用风险） |

**验证方法**：

```c
/* 在 handler 里打印 gettid()，对比 getpid() */
static void h(int sig) {
    char b[64];
    int n = snprintf(b, sizeof b, "handler 跑在 tid=%ld (pid=%ld)\n",
                     (long)gettid(), (long)getpid());
    write(1, b, n);
}
/* 多线程 + 反复 raise() → 会看到 handler 在不同线程上跑 */
```

**正确的"发给自己这个线程"写法**：

```c
#include <signal.h>
#include <sys/syscall.h>
#include <unistd.h>

static void raise_to_self(int sig)
{
#ifdef SYS_tgkill
    syscall(SYS_tgkill, getpid(), syscall(SYS_gettid), sig);
#else
    pthread_kill(pthread_self(), sig);      /* 需要 -lpthread */
#endif
}
```

**实践结论**：

1. 单线程程序里 `raise()` 和 `pthread_kill(self, ...)` 行为一致，无所谓。
2. **多线程程序里这个区别是要命的**——`raise()` 可能让信号落在热路径线程上。
3. 想要可控，还是 [22.10](22.10-synchronously-waiting-for-a-signal.md) 那套：**创建线程前全员阻塞 + 专用线程 `sigwaitinfo()`**。这样信号落在共享 pending 也没关系，因为除了专用线程，别人全都阻塞着。

</details>

<details>
<summary><b>问 4：</b>信号递送延迟有多大？HFT 场景下应该怎么处理？</summary>

**实测分解**（x86-64，现代服务器，同进程 `raise()`）：

| 阶段 | 开销 |
|------|------|
| `kill()`/`raise()` 陷入内核 | ~200 ns |
| 标记 `TIF_SIGPENDING` + 唤醒 | ~100 ns |
| `kick_process()` → IPI（跨核时） | ~300 ns ~ 1 µs |
| 目标进程陷入内核 | ~200 ns |
| `exit_to_user_mode_loop()` → `get_signal()` | ~300 ns |
| 建立信号栈帧（拷到用户栈） | ~200 ns |
| `sigreturn` 恢复上下文 | ~300 ns |
| **合计（不含 handler 自身）** | **~1.5 ~ 2.5 µs** |

**跨进程还要加上调度延迟**：

| 场景 | 总延迟 |
|------|--------|
| 目标阻塞在 `epoll_wait()` | 10 ~ 100 µs（主要是调度+唤醒） |
| 目标在别的核忙跑（IPI 生效） | 1 ~ 5 µs |
| 目标忙跑且等 tick | 1 ms（HZ=1000）~ 10 ms（HZ=100）或更长（NO_HZ） |
| 目标在 D 状态 | **无上界** |

**实测长尾比平均值重要得多**（示例 1 的输出）：

```
平均   : 1183 ns
最小   : 892 ns
最大   : 41237 ns     ← 40 倍于平均！被中断/抢占打断
```

**HFT 的处理方案**：

| 层次 | 措施 | 消除的抖动 |
|------|------|-----------|
| **架构** | 热路径线程 `pthread_sigmask` **全屏蔽**；专用线程 `sigwaitinfo()` | 消除"信号打断热路径" |
| **I/O 模型** | `signalfd` + `epoll` 统一事件循环（异步信号） | 消除 handler 的 async-signal-safe 约束 |
| **兜底** | 同步故障信号（SEGV/BUS/FPE/ILL）保留 `SA_ONSTACK` handler | 崩溃时留现场（这类捕获不到 signalfd） |
| **CPU 隔离** | `isolcpus=2,3` + 热路径绑核 | 消除其他任务的抢占 |
| **消除 tick** | `nohz_full=2,3` + `rcu_nocbs=2,3` | 消除周期性 tick 抖动和"等一个 tick" |
| **调度类** | `SCHED_FIFO` + 合理优先级（[Ch35](../../chapter-35-process-priorities-scheduling/README.md)） | 调度延迟可控 |
| **内存** | `mlockall(MCL_CURRENT\|MCL_FUTURE)` | 消除缺页（可能进 D 状态） |
| **数据通路** | **绝不用信号传高频数据**——共享内存 + eventfd 轮询 | 零系统调用、零中断 |

**一句话原则**：

> 信号的定位是"**低频控制通知**"（切模式、优雅退出、重载配置），不是数据通路。任何"每秒几千次以上"的事件都该换机制。
>
> 高频场景的正确做法是**轮询而非通知**：热路径线程忙轮询共享内存 ring buffer，用 eventfd 只在"长时间空闲"时唤醒——这样既保住低延迟，又不烧 CPU。

</details>

<details>
<summary><b>问 5：</b>为什么 POSIX 不规定递送顺序？依赖它有什么风险？</summary>

**为什么 POSIX 不作规定**：

POSIX 的设计哲学是**只规定"可移植程序能依赖的最小集合"**。递送顺序取决于实现内部的数据结构选择：

- 用**位图**（Linux、System V 系）→ 天然是"小号优先"
- 用**链表/队列**（某些早期 BSD）→ 天然是"到达顺序"（FIFO across all signals）
- 用**优先级队列**（某些实时系统）→ 按优先级

如果 POSIX 规定"小号优先"，所有用链表的实现都要大改；规定"到达顺序"，位图实现又做不到（位图不记录时间序列）。所以标准选择了**明确规定"不规定"**，让各实现自由。

**POSIX 唯一规定的顺序**：

> 同一实时信号的多个实例按 **FIFO** 递送。

这条能规定，是因为 POSIX.1b 设计实时信号时**明确要求排队语义**（链表结构），FIFO 是链表的自然结果，实现代价可预期。

**依赖 Linux 顺序的风险**：

| 风险 | 具体表现 |
|------|----------|
| **跨 Unix 移植时静默错乱** | 代码迁到用链表语义的系统（或不同 libc / 不同内核配置），顺序变了，**不报错，只是行为不同**——这是最坏的一类 bug |
| **内核实现可能变** | Linux 自己也可以改 `next_signal()`。事实上 `dequeue_synchronous_signal()` 就是后来加的（为了让同步故障优先），它已经改变过一次行为 |
| **代码脆弱性** | 依赖顺序的代码难以推理、难以测试。加一个新信号就可能打乱既有顺序 |
| **并发放大** | 多线程下"哪个线程跑 handler"本身就不确定，再叠加顺序不确定性，组合爆炸 |

**正确做法：把顺序编码进数据**

```c
/* ❌ 错误：依赖递送顺序表示"步骤 1 → 步骤 2 → 步骤 3" */
raise(STEP1_SIG); raise(STEP2_SIG); raise(STEP3_SIG);
/* 接收方按"到达顺序"推进状态机 → 换个系统就错乱 */

/* ✅ 正确：把序号放进 sigval */
union sigval sv;
for (int step = 1; step <= 3; step++) {
    sv.sival_int = step;                  /* 顺序信息在数据里 */
    sigqueue(pid, MY_SIG, sv);            /* 用实时信号，保证 FIFO + 不丢 */
}
/* 接收方：handler 里读 si->si_value.sival_int，自己排序 */
```

或者——**更好的方案：根本不用信号传递有序信息**。

```c
/* 有序、可靠、零丢失：管道 / socketpair / 共享内存 ring buffer */
write(ctl_pipe[1], &cmd, sizeof(cmd));    /* 字节流天然有序 */

/* 或共享内存 + eventfd：写完数据再 eventfd_write() 通知一次 */
memcpy(shm_ring + tail, &cmd, sizeof(cmd));
__atomic_store_n(&tail, new_tail, __ATOMIC_RELEASE);
eventfd_write(efd, 1);                    /* 只通知"有新数据"，顺序由 ring 保证 */
```

这二者的共同点：**顺序由数据结构（字节流 / ring）保证，不由内核的递送调度保证**。

**唯一可以放心依赖顺序的场景**：

```c
/* 同一实时信号，多次 sigqueue → FIFO 保证 */
for (int i = 0; i < 100; i++) {
    sv.sival_int = i;
    sigqueue(pid, MY_RT_SIG, sv);
}
/* 接收方一定按 0,1,2,...,99 的顺序收到（前提：队列没满） */
```

即便如此，仍要处理 `EAGAIN`（队列满）——见 [22.8](22.8-realtime-signals.md)。

</details>
