# 31.3 线程特定数据：`pthread_key_*`

> 本章：[TLPI 第 31 章 — Thread Safety and Per-Thread Storage](../README.md)
> - 上一节：[31.2 `pthread_once`](31.2-one-time-initialization.md)
> - 下一节：[31.4 静态 TLS：`__thread` / `_Thread_local`](31.4-thread-local-storage.md)

> 源码核验：Linux v6.6 · 无专属内核路径（TSD 完全在 glibc 用户态实现，数据结构挂在 `struct pthread` 上）· 线程退出时析构由 glibc 的 `__nptl_deallocate_tsd` 驱动 · 析构循环上限 `PTHREAD_DESTRUCTOR_ITERATIONS` = 4

---

## 本节讲什么

1. **TSD 解决什么**——接口签名不能改、又需要"每线程一份私有数据"时的标准机制：进程全局一个 key，每个线程在 key 对应的格子里放自己的指针。
2. **四个 API 的完整语义**——尤其是 destructor 的生命周期：线程退出时调用、最多 4 轮迭代、`pthread_key_delete` 的不析构陷阱。
3. **glibc 怎么实现**——key 表 + `struct pthread` 里的二级数组；以及为什么访问一次 TSD 要付一次函数调用的钱（与 31.4 TLS 的一条段寄存器寻址对比）。
4. **strerror 改造实战**——`pthread_once` + `key_create` + 惰性分配 + 析构，四步范式完整落地。

---

## 一、问题：接口不能改，状态又不能共享

31.1 的方法②（调用者提供缓冲）要求改签名。但现实中大量接口改不了：

- POSIX 规定的 `char *strerror(int)` 签名动不了；
- 老库的 ABI 被几十个二进制依赖；
- 回调函数的原型由框架定死。

TSD（Thread-Specific Data）的思路：**保留全局的名字（key），把"值"做成每线程一份**。

```
                进程全局（所有线程共享）
        ┌──────────────────────────────────────┐
        │  key 表（pthread_key_t = 下标 0..1023）│
        │  key[k] → { in_use, destructor }      │
        └──────────────────────────────────────┘
                     ▲ ▲ ▲
        ┌────────────┘ │ └────────────┐
   线程 A 的格子   线程 B 的格子   线程 C 的格子
   specific[k]=p1  specific[k]=p2   specific[k]=NULL
   （各自 malloc， 各自 malloc，    还没碰过这个 key
    析构时 free）   析构时 free）
```

key 是**全局**的（所有线程看到同一个编号 k），值是**每线程**的（各自格子里的指针互不可见）。

## 二、四个 API 的完整语义

```c
int   pthread_key_create  (pthread_key_t *key, void (*destructor)(void *));
int   pthread_setspecific (pthread_key_t key, const void *value);
void *pthread_getspecific (pthread_key_t key);
int   pthread_key_delete  (pthread_key_t key);
```

### 2.1 `pthread_key_create`

- key 是**全局资源**：整个进程只能创建 `PTHREAD_KEYS_MAX`（glibc = **1024**）个 key。每线程每 key 一个 `void*` 格子。
- destructor 可为 NULL（值不需要清理时）。destructor 收到的是**该线程自己的** value。
- **必须恰好一次**（31.2）：两个线程各自 create 会拿到两个不同 key，"每线程一份"变成"每线程两份"。

### 2.2 `setspecific` / `getspecific`

- `getspecific` 对"该线程从未设置过"返回 **NULL**——这个 NULL 正是惰性分配范式的判据。
- `setspecific(key, NULL)` 是合法的"清除本线程的值"（析构不会再跑）。
- 值本身是 `void*`：想放 int 就塞 `(void*)(intptr_t)x` 出来再转回（前提是 int 能塞进指针；大结构体还是 malloc 指针）。

### 2.3 destructor 的生命周期（本节最容易考的语义）

线程**退出**时（`pthread_exit` 或从 start 例程 return，不是进程 `_exit`），glibc 对该线程扫所有格子：

```
对每个 value != NULL 的 key：
    取出 value，先把格子清 NULL，再调 destructor(value)
    （清空再调用——防析构器里 getspecific 拿到旧值）
再来一轮：析构器可能又 setspecific 了新值 → 对非 NULL 的格子再析构
最多 PTHREAD_DESTRUCTOR_ITERATIONS = 4 轮，之后放弃（剩余内存泄漏）
```

四轮上限的原因：destructor 完全可能在清理过程中**又往本线程的格子里塞了新值**（比如析构一个对象时懒加载了另一个 TSD 依赖）。内核/glibc 不做环检测，只数轮次——四轮后仍有非 NULL 格子就随线程结构体一起丢弃（泄漏），**不无限循环**。

### 2.4 `pthread_key_delete`：不析构！

- delete 只把 key 标记为**可复用**（进程视角），**不会**对任何线程的现存值跑 destructor。
- 已设置的线程数据全部成为"不可达内存"——**典型泄漏源**。delete 的正确用途只有一个：key 不再需要了且你确信所有线程的值都已为 NULL。
- key 删除后编号可能被新的 `key_create` **复用**——别拿着旧 key 继续用（UB）。

### 2.5 glibc 实现速览

- key 表：全局数组，`in_use` 标记 + destructor 指针；
- 每线程格子：`struct pthread->specific_1stblock[32]`（一级直接块）+ 需要更多 key 时动态分配的二级块（`specific` 指针数组，每块 32 格）——访问第 k 个 key：`k < 32 ? 1stblock[k] : specific[k/32-1][k%32]`；
- 这套结构就长在 29.8 讲过的 `struct pthread`（TCB，栈底）里——线程死则格子死，析构在 `__nptl_deallocate_tsd`（线程退出路径）里驱动；
- 所以 `pthread_getspecific` 是**一次真正的函数调用**（查表逻辑 + 原子读），不是编译期寻址——这就是 31.4 TLS 性能优势的来源。

## 三、strerror 改造实战（四步范式）

目标：`char *my_strerror(int errnum)`——签名与 `strerror` 一致，但线程安全。

```c
#define _GNU_SOURCE
#include <pthread.h>
#include <string.h>
#include <stdio.h>
#include <stdlib.h>

#define BUFLEN 128

static pthread_key_t key;                       /* 全局一个 key */
static pthread_once_t once = PTHREAD_ONCE_INIT;

static void destructor(void *buf) { free(buf); }

static void create_key(void)                    /* ① 恰好一次地创建 key */
{
    pthread_key_create(&key, destructor);
}

char *my_strerror(int errnum)                   /* 接口签名与 strerror 相同 */
{
    pthread_once(&once, create_key);            /* ① once 保护 key 唯一 */
    char *buf = pthread_getspecific(key);       /* ② 查本线程格子 */
    if (buf == NULL) {                          /* ③ 本线程第一次：惰性分配 */
        buf = malloc(BUFLEN);
        pthread_setspecific(key, buf);
    }
    snprintf(buf, BUFLEN, "(unknown error %d)", errnum);  /* 兜底 */
    return buf;
}
```

四步范式（把 TSD 用法背下来）：

| 步 | 代码 | 语义 |
|----|------|------|
| ① | `pthread_once(&once, create_key)` | key 全进程恰好建一次 |
| ② | `pthread_getspecific(key)` | 查本线程格子，NULL = 未初始化 |
| ③ | `malloc` + `pthread_setspecific` | 首次惰性分配并登记 |
| ④ | destructor 里 `free` | 线程退出自动回收，不泄漏 |

加锁版对比：同样的接口用 mutex 也能做（31.1 方法①），但①每次调用串行化（争抢点）②返回的指针在下次调用前就失效（还是共享缓冲）。TSD 版**每线程一块缓冲，永不互相覆盖，返回指针长期有效**——这是"线程安全"之外的第二重收益。

## 四、什么时候该用 TSD（而不是 TLS）

| 判断 | TSD | TLS（31.4）|
|------|-----|------------|
| 数据是编译期已知的全局/静态变量？ | 不适用 | ✓ `__thread` 一行搞定 |
| 需要运行时决定"哪些数据"（如插件注册的 key）？ | ✓ | ✗ |
| 需要 destructor（堆分配、复杂清理）？ | ✓ 原生支持 | ✗（`__thread` 变量无析构；C++ thread_local 有）|
| 需要值可以为 NULL 表示"未初始化"的惰性语义？ | ✓ getspecific 返回 NULL | 要自己另设标志 |
| 数量上限？ | 1024 个 key | 无硬限（受链接期 TLS 块大小约束）|
| 访问成本？ | 一次函数调用（~2 ns 级）| 一条段寄存器寻址（~1 ns 级，可内联）|
| 能否用于 dlopen 加载的库？ | ✓ | 受限（见 31.4 §四，initial-exec 模型耗尽后 dlopen 失败）|

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | TSD 在热路径的两个成本：函数调用不可内联 + getspecific 查表。已知的数据结构一律 `__thread`（每线程上下文结构体）；TSD 留给"运行时才确定的注册制数据"（如回调注册的统计槽）|
| HFT · 生命周期 | destructor 在线程退出时跑——**不要在 destructor 里做跨线程通信**（其他线程可能已退出，锁/cond 已销毁）；析构只做 free 本线程资源 |
| 嵌入式 | 1024 key 上限在嵌入式绰绰有余，但要防"库各自 create 一堆 key"的碎片化；TSD 完全是用户态实现，不依赖内核版本，可移植性极好（连 musl 都有）|
| 嵌入式 · 泄漏审计 | 长命进程反复 create 线程 + key_delete 使用不当 = 慢性泄漏。规则：key 与进程同寿（启动建、永不删），线程值靠 destructor 收 |

## 代码示例

`tsd_demo.c`（gcc -O2 -Wall -Wextra 零告警编译通过）：

```c
/* tsd_demo.c — Ch31.3：strerror 改造、析构时机、析构四轮上限、key 上限
 * 编译：gcc -O2 -Wall -Wextra -o tsd_demo tsd_demo.c -pthread
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>             /* intptr_t */
#include <pthread.h>

#define BUFLEN 128
static pthread_key_t key;
static pthread_once_t once = PTHREAD_ONCE_INIT;

/* ---------- 演示 1：strerror 改造（每线程一块缓冲）---------- */
static void destructor(void *buf){ free(buf); }
static void create_key(void){ pthread_key_create(&key, destructor); }

static char *my_strerror(int errnum)
{
    pthread_once(&once, create_key);
    char *buf = pthread_getspecific(key);
    if (buf == NULL) {
        buf = malloc(BUFLEN);
        pthread_setspecific(key, buf);
        printf("        [线程 %lu] 首次调用，惰性分配 buf=%p\n",
               (unsigned long)pthread_self(), (void*)buf);
    }
    snprintf(buf, BUFLEN, "(error %d 的描述)", errnum);
    return buf;
}

static void *worker(void *a){
    long id = (long)(intptr_t)a;
    char *r1 = my_strerror((int)id);
    char *r2 = my_strerror((int)id);            /* 第二次：复用同一块缓冲 */
    printf("[demo1] 线程%ld: r1=%p r2=%p（同一线程内复用）%s\n",
           id, (void*)r1, (void*)r2, r1 == r2 ? "" : "✗");
    return NULL;                                /* 退出 → destructor 自动 free */
}

/* ---------- 演示 2：析构在 pthread_exit 路径触发 ---------- */
static void demo_destructor(void){
    pthread_t t[3];
    for (long i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, worker, (void*)(intptr_t)(i+1));
    for (int i = 0; i < 3; i++) pthread_join(t[i], NULL);
    printf("[demo2] 三个线程都退出了，destructor 各跑一次（见上方 free 输出）\n");
}

/* ---------- 演示 3：析构器再塞值 → 轮次统计 ---------- */
static pthread_key_t k2;
static int destruct_rounds = 0;

static void dtor_rearm(void *v){
    destruct_rounds++;
    free(v);
    if (destruct_rounds < 10)                   /* 故意再塞一个新值 */
        pthread_setspecific(k2, malloc(16));
}

static void *rearm_worker(void *a){(void)a;
    pthread_setspecific(k2, malloc(16));
    return NULL;}

static void demo_rearm(void){
    pthread_key_create(&k2, dtor_rearm);
    pthread_t t;
    pthread_create(&t, NULL, rearm_worker, NULL);
    pthread_join(t, NULL);
    printf("[demo3] 析构器故意重塞值：destructor 实际跑了 %d 次"
           "（上限 PTHREAD_DESTRUCTOR_ITERATIONS=4，超出后放弃→泄漏）\n",
           destruct_rounds);
    pthread_key_delete(k2);
}

/* ---------- 演示 4：key 数量上限 ---------- */
static void demo_key_limit(void){
    pthread_key_t ks[1100];
    int n = 0;
    for (int i = 0; i < 1100; i++) {
        if (pthread_key_create(&ks[i], NULL) != 0) break;
        n++;
    }
    printf("[demo4] 本进程还能创建 %d 个 key（PTHREAD_KEYS_MAX 上限之内，"
           "demo1/3 已占用）\n", n);
    for (int i = 0; i < n; i++) pthread_key_delete(ks[i]);
}

int main(void){
    printf("==== 演示 1+2：strerror 改造 + 析构时机 ====\n");
    demo_destructor();
    printf("==== 演示 3：析构器重塞值的轮次上限 ====\n");
    demo_rearm();
    printf("==== 演示 4：key 数量上限 ====\n");
    demo_key_limit();
    return 0;
}
```

实测输出（WSL2 / 12 核）：

```text
==== 演示 1+2：strerror 改造 + 析构时机 ====
        [线程 130898800400064] 首次调用，惰性分配 buf=0x770d30000b70
[demo1] 线程3: r1=0x770d30000b70 r2=0x770d30000b70（同一线程内复用）
        [线程 130898817185472] 首次调用，惰性分配 buf=0x770d38000b70
[demo1] 线程1: r1=0x770d38000b70 r2=0x770d38000b70（同一线程内复用）
        [线程 130898808792768] 首次调用，惰性分配 buf=0x770d28000b70
[demo1] 线程2: r1=0x770d28000b70 r2=0x770d28000b70（同一线程内复用）
[demo2] 三个线程都退出了，destructor 各跑一次（见上方 free 输出）
==== 演示 3：析构器重塞值的轮次上限 ====
[demo3] 析构器故意重塞值：destructor 实际跑了 4 次（上限 PTHREAD_DESTRUCTOR_ITERATIONS=4，超出后放弃→泄漏）
==== 演示 4：key 数量上限 ====
[demo4] 本进程还能创建 1023 个 key（PTHREAD_KEYS_MAX 上限之内，demo1/3 已占用）
```

四点解读：

1. demo1：三个线程拿到**三个不同的** `buf`（各自独立的堆块），同一线程内两次调用复用同一块——"每线程一份 + 线程内稳定"都验证了。
2. demo2：worker `return NULL` 退出时 destructor 自动跑（free），无需手动清理。
3. demo3：析构器故意再 `setspecific`，destructor 实际跑了 **4 次**就被强制停止——`PTHREAD_DESTRUCTOR_ITERATIONS` 上限的活体演示（第 4 轮后剩余值泄漏）。
4. demo4：`PTHREAD_KEYS_MAX = 1024`。demo3 的 k2 已 `key_delete`（编号回收），只剩 demo1 的 1 个 key 占用，故还能建 **1023** 个——顺带实证了"delete 后编号可复用"（31.3 §2.4）。
