## 一、全章速览

| 节 | 武器 | 一句话 | 内核参与 |
|----|------|--------|----------|
| 31.1 | 概念框架 | 可重入 ⊂ 线程安全；锁只防跨线程不防自己 | 无 |
| 31.2 | `pthread_once` | "恰好一次"专用原语；完成态一条原子读 | 无（CAS+futex 用户态）|
| 31.3 | TSD `pthread_key_*` | 运行时 key + 每线程格子 + destructor（4 轮上限）| 无（纯用户态）|
| 31.4 | TLS `__thread` | 编译期偏移 + FS 段寻址；一条指令零查表 | clone(CLONE_SETTLS) + ARCH_SET_FS |

**本章的隐形主线**：`errno` 的线程安全靠 TLS；TLS 靠内核设 FS base；FS base 在 `copy_thread():254` 的 CLONE_SETTLS 分支——POSIX 线程模型（29.1 的 `CLONE_THREAD⟹SIGHAND⟹VM`）在"每线程私有数据"上完成了最后一次闭环：**共享一切（地址空间），私有三样（栈、寄存器、TLS 块）**。

## 二、选型决策树

```
接口/数据需要每线程独立？
├─ 能消灭全局状态（收进调用者结构体）？── 是 ──▶ 就地消灭（最好的同步是没有共享）
├─ 能改函数签名？
│   └─ 是 ──▶ 调用者提供缓冲（_r 家族路线，顺带可重入）
├─ 数据在编译期已知（全局/静态变量）？
│   └─ 是 ──▶ __thread / _Thread_local（TLS，~0.5ns，热路径免费）
│        └─ 初值不是常量？──▶ __thread 放指针 + 惰性构造
├─ 需要 destructor / 运行时决定 key / dlopen 插件？
│   └─ 是 ──▶ TSD（pthread_key_*，~2ns，1024 个上限）
└─ 以上都不适用（遗留接口 + 低频调用）？
    └─ 全局锁（Ch30）——记得它防不了重入
```

---

## 三、铁律

1. **能消灭的全局状态就消灭**——同步问题的最低成本解法是让问题不存在。
2. 老接口（`strtok`/`localtime`/`ctime`/`strerror`...）在多线程里**一律换成 `_r`/等价现代版**；审计用 grep。
3. 信号处理器/中断上下文里只进**可重入**代码——加锁版"线程安全"在这里是死锁。
4. `pthread_once_t` 必须 `PTHREAD_ONCE_INIT`，不能 malloc；init 里不能等其他线程。
5. key 创建必须 once 保护；`pthread_key_delete` 不析构——key 与进程同寿，值靠 destructor。
6. destructor 里别再 setspecific（4 轮后泄漏）；别做跨线程通信（别人可能已退出）。
7. `__thread` 只放全局/静态 + 常量初始化；大对象放堆、TLS 放指针。
8. C 的 `__thread` 无析构——堆资源每线程自己收（worker 退出前 free）。
9. TLS 变量地址每线程不同且随线程消亡——不跨线程传递 `&tls_var`。
10. dlopen 插件慎用 `__thread`（initial-exec 额度），必要时 `-ftls-model=global-dynamic`。

## 四、成本账本（实测汇总）

| 操作 | 实测 | 备注 |
|------|------|------|
| 普通全局读 | ~0.4 ns | RIP 相对寻址 |
| `__thread` TLS 读 | ~0.5 ns | `%fs:偏移`，可内联 |
| `pthread_getspecific` | ~2.0 ns | 函数调用 + 二级查表 |
| `pthread_once`（完成态）| ~1 ns | 一条原子读 |
| TSD 析构上限 | 4 轮 | `PTHREAD_DESTRUCTOR_ITERATIONS` |
| key 总量上限 | 1024 | `PTHREAD_KEYS_MAX` |
| TLS 寻址反汇编 | `mov %fs:x@tpoff` | 本机 gcc 实测 |

## 自测题

**题目 1（辨析）**："`strtok` 加一把全局 mutex 就线程安全了，所以信号处理器里也可以用它。"找出这句话的两处错误。

<details>
<summary>参考答案</summary>

① 加 mutex 只解决跨线程互斥，不解决重入：处理器若打断了正持有该 mutex 的代码路径（很可能就是 strtok 自己的调用链），再次 lock = 同线程二次加锁 = 永久死锁（普通锁）。② 即使不考虑锁，`strtok` 被打断时内部 saveptr 处于中间状态，处理器里再调会破坏原调用者的解析进度。正确做法：处理器里根本不做字符串解析（只置标志，29.9/Ch21 原则）；正常代码用 `strtok_r`。

</details>

**题目 2（设计）**：一个热路径函数 `order_id_t next_order_id(void)`（无参无返回指针），要每线程独立序号、高并发下不加锁。写出实现并说明初始化方案。

<details>
<summary>参考答案</summary>

```c
static __thread uint64_t seq = 0;     /* 每线程一份，零初始化满足"常量初始化" */
order_id_t next_order_id(void){
    return (order_id_t)((uint64_t)thread_slot() << 48 | ++seq);  /* 高位线程槽 + 低位序号 */
}
```
`__thread` 零初始化即合法；序号从 1 开始避免 0 值歧义；线程槽号在建线程时分配（全局原子计数器 +1，一次性成本）。TSD 不选：函数调用查表 +1024 上限 + 需要析构；锁不选：热路径争抢。若要求全局严格递增则退化为原子 fetch_add（25 ns 级，见 30.3 成本账本）——先确认"每线程独立"是否真的满足业务。

</details>

**题目 3（机制）**：`__thread` 变量的访问为什么是一条指令？从"编译期偏移 + FS 基址"解释，并说明 FS 基址在创建线程时由谁、在哪一步设置。

<details>
<summary>参考答案</summary>

链接器把每个 TLS 变量分配成相对线程指针（FS base）的固定偏移（`@tpoff`），编译器生成 `mov %fs:偏移, %eax`——偏移编译期定死，基址在硬件寄存器里，零运行时查找。创建链路：glibc 分配线程栈与 TLS 模板副本 → `clone(CLONE_SETTLS, tls=TCB)` → 内核 `copy_thread()`（arch/x86/kernel/process.c:159）在 `:254` 调 `set_new_tls()` → `do_set_thread_area_64(p, ARCH_SET_FS, tls)` 把基址写进新任务的 thread 结构 → 新线程首次调度上 CPU 时由 switch_to 装载。运行时修改走 `arch_prctl(ARCH_SET_FS)`（process_64.c:828，preempt_disable 保护）。

</details>

**题目 4（排错）**：进程长期运行内存持续增长。每 10 秒创建一个短命线程做日志 flush（用了 TSD 存格式化缓冲，destructor 里 free）。另一模块每 100 万条日志 `pthread_key_delete` 后重建 key。哪个环节泄漏？

<details>
<summary>参考答案</summary>

`pthread_key_delete` 是泄漏点：delete 不对任何线程现存值跑 destructor。重建 key 的周期内，尚在运行的线程（以及 delete 时刻还活着的 flush 线程）格子里可能还挂着旧缓冲指针；key 标记可复用后这些指针成为不可达内存（析构器关联也没了）。修法：key 与进程同寿（启动建一次，永不删）；或 delete 前确保所有线程该 key 的值已清空（实际做不到时就是设计错误）。顺带检查 destructor 是否可能 4 轮上限泄漏（31.3 demo3 场景）。

</details>
