## 本节讲什么

1. `pause()` 做什么——最简单的「挂起等待信号」原语，以及它的返回值语义
2. 为什么**生产代码不能用 `pause()`**——那个无法消除的竞态窗口
3. 内核视角看 `pause()` 与 `sigsuspend()` 的差异——原子性是怎么来的

---

## 一、`pause()` 的行为

```c
#include <unistd.h>

int pause(void);
/* 返回：总是 -1，errno = EINTR */
```

- 挂起调用线程，直到**有信号被递送**（且该信号的处置不是忽略）
- 若信号被**忽略**或被**阻塞**，`pause()` 不会被唤醒
- 返回值永远是 `-1`，`errno` 永远是 `EINTR`

内核实现极简（`kernel/signal.c:4639`）：

```c
SYSCALL_DEFINE0(pause)
{
	while (!signal_pending(current)) {          // 有未决信号吗？
		__set_current_state(TASK_INTERRUPTIBLE); // 设为可中断睡眠
		schedule();                              // 让出 CPU
	}
	return -ERESTARTNOHAND;
}
```

`ERESTARTNOHAND` 表示「如果有 handler 就重启，没有就返回 `EINTR` 给用户态」——所以用户看到的总是 `-1 / EINTR`。

## 二、致命竞态：为什么不能用 `pause()`

典型（错误的）写法：

```c
/* ❌ 有 bug */
if (!got_signal) {
    pause();      /* ← 竞态窗口在这里 */
}
```

**竞态时序**：

```
  主流程                                信号
  ─────────────────────────────────────────────
  if (!got_signal)  → true
                                     ┌─ 信号到达并递送
  ┌─────────────────────────────────┘
  │                                   handler 执行，got_signal = 1
  │                                   handler 返回
  └→ pause();       ← 信号已经处理完了，pause 永远等不到第二次
       进程永久挂起 ❌
```

**本质问题**：「**检查条件**」和「**进入等待**」是两个独立的动作，中间存在窗口。信号在这个窗口内到达，就会被 `pause()` 错过。

这个问题**无法通过加锁或关中断解决**——因为信号的递送发生在内核返回用户态的边界，与用户态的锁无关。唯一解法是把两步合并成**一个原子操作**。

## 三、内核视角：`pause()` vs `sigsuspend()`

把两个实现并排看，差异一目了然：

```c
// kernel/signal.c:4639 —— pause()
SYSCALL_DEFINE0(pause)
{
	while (!signal_pending(current)) {
		__set_current_state(TASK_INTERRUPTIBLE);
		schedule();
	}
	return -ERESTARTNOHAND;
}

// kernel/signal.c:4650 —— sigsuspend()
static int sigsuspend(sigset_t *set)
{
	current->saved_sigmask = current->blocked;   // ① 保存当前掩码
	set_current_blocked(set);                    // ② 设置新掩码（通常解除阻塞）

	while (!signal_pending(current)) {           // ③ 与 pause 完全相同的循环
		__set_current_state(TASK_INTERRUPTIBLE);
		schedule();
	}
	set_restore_sigmask();                       // ④ 恢复原掩码
	return -ERESTARTNOHAND;
}
```

**`sigsuspend` = `pause` + 「改掩码」+「恢复掩码」，且全部在一次系统调用内完成**——这就是原子性的来源：

| 步骤 | `pause()` | `sigsuspend()` |
|------|-----------|----------------|
| 保存原掩码 | — | ✅ `saved_sigmask = blocked` |
| 设置临时掩码 | — | ✅ `set_current_blocked(set)` |
| 挂起等待 | ✅ 相同循环 | ✅ 相同循环 |
| 恢复掩码 | — | ✅ `set_restore_sigmask()` |
| **原子性** | ❌ 需用户态先调 `sigprocmask` | ✅ 单系统调用 |

> **这就是「解除阻塞 + 等待」竞态的标准解法**：进入等待前先把信号阻塞住，让它们堆积在 pending；然后 `sigsuspend()` 原子地「临时解除 → 等待 → 恢复」。信号要么在阻塞期间堆积（随后被 `sigsuspend` 递送并唤醒），要么在 `sigsuspend` 期间直接唤醒——**两条路径都不会丢**。

## 四、正确方案对照

| 方案 | 接口 | 特点 |
|------|------|------|
| **`sigsuspend()`** | `sigsuspend(&mask)` | 原子「改掩码 + 等待 + 恢复」，见 [Ch22.9](../../chapter-22-signals-advanced/notes/22.9-waiting-for-a-signal-using-a-mask-sigsus.md) |
| **`sigwaitinfo()`** | `sigwaitinfo(&set, &info)` | **同步取**信号，不跑 handler，最干净，见 [Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md) |
| **`ppoll`/`pselect`** | `ppoll(fds, n, ts, &sigmask)` | 带超时的原子等待，可同时等 I/O |
| **`epoll_pwait`** | `epoll_pwait(epfd, ev, max, tmo, &sigmask)` | 事件循环专用，HFT 标准做法，见 [Ch63.4](../../chapter-63-alternative-i-o-models/notes/63.4-the-epoll-api.md) |
| **`signalfd`** | `signalfd(...)` + `epoll` | 信号变 fd，完全融入事件循环，见 [Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md) |

### `sigsuspend` 标准用法

```c
sigset_t block, orig;
sigemptyset(&block);
sigaddset(&block, SIGINT);

/* ① 先阻塞 SIGINT —— 信号会堆积在 pending，不会丢 */
sigprocmask(SIG_BLOCK, &block, &orig);

/* ... 在此期间到达的 SIGINT 全部进入 pending ... */

/* ② 原子地：临时恢复 orig → 等待 → 回到阻塞态 */
sigsuspend(&orig);        /* pending 的 SIGINT 在此递送并唤醒 */

/* ③ 此时已回到阻塞态，可安全清理 */
sigprocmask(SIG_SETMASK, &orig, NULL);
```

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | `pause()` 只适合写 demo。嵌入式长驻服务一旦因竞态永久挂起，往往要靠 watchdog 硬复位才能恢复——而设备可能在无人值守现场。生产代码一律用 `sigsuspend()` 或 `sigwaitinfo()` |
| HFT | **绝不用 `pause()`**——竞态导致的挂起在交易时段是不可接受的事故。HFT 的正确做法是把信号纳入事件循环：`signalfd` + `epoll`，或 `epoll_pwait(..., &sigmask)`，让"等待信号"和"等待行情"变成同一个 `epoll_wait` 调用，零额外竞态、零额外延迟 |

## 代码示例：竞态复现与 `sigsuspend` 修复

```c
/* pauserace.c —— 复现 pause 竞态，并用 sigsuspend 修复
 * 编译: gcc -o pauserace pauserace.c
 * 用法: ./pauserace pause      （有竞态，可能永久挂起）
 *       ./pauserace suspend    （无竞态） */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t got = 0;
static void handler(int sig) { got = 1; }

int main(int argc, char **argv)
{
    int use_suspend = (argc > 1 && strcmp(argv[1], "suspend") == 0);

    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                     /* 故意不用 SA_RESTART */
    sigaction(SIGUSR1, &sa, NULL);

    sigset_t block, orig;
    sigemptyset(&block);
    sigaddset(&block, SIGUSR1);

    /* 先阻塞，制造"信号已到达但被阻塞"的局面 */
    sigprocmask(SIG_BLOCK, &block, &orig);
    raise(SIGUSR1);                      /* 进入 pending */

    if (use_suspend) {
        /* ✅ 原子地：临时恢复 orig → 等待 → 回到阻塞 */
        printf("[suspend] 等待中（pending 的 SIGUSR1 将立即递送）...\n");
        sigsuspend(&orig);
        printf("[suspend] 被唤醒，got=%d\n", got);
    } else {
        /* ❌ 竞态：先解除阻塞，再 pause —— 两步之间有窗口 */
        printf("[pause] 解除阻塞后 pause（若信号在此窗口被处理则永久挂起）...\n");
        sigprocmask(SIG_SETMASK, &orig, NULL);   /* 信号可能已在此处递送完毕 */
        if (!got)
            pause();                              /* 可能永远等不到 */
        printf("[pause] 被唤醒，got=%d\n", got);
    }
    return 0;
}
```

> 本例中 `raise(SIGUSR1)` 发生在阻塞期间，解除阻塞时信号会**立即递送**——所以 `pause` 版本在大多数情况下会永久挂起，直观展示了竞态。这正说明：**只要「检查/解除」与「等待」分开，就一定有窗口**。

## 自测题

<details>
<summary><b>问 1：</b><code>pause()</code> 的返回值和 <code>errno</code> 是什么？为什么？</summary>

**总是返回 `-1`，`errno` 总是 `EINTR`。**

内核实现（`kernel/signal.c:4639`）：

```c
SYSCALL_DEFINE0(pause)
{
	while (!signal_pending(current)) {
		__set_current_state(TASK_INTERRUPTIBLE);
		schedule();
	}
	return -ERESTARTNOHAND;
}
```

`pause()` 唯一的退出方式就是「有信号被递送」，而信号递送意味着系统调用被中断，所以返回值必然是 `-1 / EINTR`。

返回值 `ERESTARTNOHAND` 是内核内部的重启语义：「若该信号注册了 handler 就重启 syscall，否则返回 `EINTR` 给用户态」。因为 `pause` 的存在意义就是等信号，实际用户态总是看到 `EINTR`。

**实践**：调用 `pause()` 后不需要检查返回值——它只有一种可能。需要判断的是「为什么被唤醒」，应该通过 handler 设置的标志位来传递。

</details>

<details>
<summary><b>问 2：</b>描述 <code>pause()</code> 的竞态，并说明为什么加锁解决不了。</summary>

**竞态时序**：

```c
if (!got_signal) {
    /* ← 窗口：信号在这个瞬间到达、handler 执行、got_signal 变 1 */
    pause();      /* 信号已经处理完了，pause 永远等不到第二次 */
}
```

**为什么加锁解决不了**：

信号递送发生在**内核返回用户态的边界**（见 [20.1](./20.1-concepts-and-overview.md)），它不由用户态代码调度。用户态的互斥锁只能保护「用户态线程之间的互斥」，**无法阻止内核在任意时刻插入 handler 执行**。

具体说：即便把 `if` 和 `pause` 包在同一把锁里，handler 依然可以在 `if` 判断之后、`pause` 调用之前的任何指令边界递送——因为 handler 不需要获取你的锁。

**唯一解法**：把「检查条件」和「进入等待」合并为**单个原子操作**，即 `sigsuspend(&mask)`。它在一次系统调用内完成「改掩码 → 等待 → 恢复掩码」，没有窗口。

（对应地，如果等待条件不是信号而是共享变量，正确解法是条件变量 `pthread_cond_wait`——它同样把「解锁 + 等待」做成原子操作。）

</details>

<details>
<summary><b>问 3：</b>从内核源码看，<code>sigsuspend()</code> 比 <code>pause()</code> 多做了什么？这就是原子性的来源吗？</summary>

**是的**。对比两个实现：

```c
// kernel/signal.c:4639 —— pause()
SYSCALL_DEFINE0(pause)
{
	while (!signal_pending(current)) {
		__set_current_state(TASK_INTERRUPTIBLE);
		schedule();
	}
	return -ERESTARTNOHAND;
}

// kernel/signal.c:4650 —— sigsuspend()
static int sigsuspend(sigset_t *set)
{
	current->saved_sigmask = current->blocked;   // ① 保存
	set_current_blocked(set);                    // ② 改掩码

	while (!signal_pending(current)) {           // ③ 与 pause 完全相同的循环
		__set_current_state(TASK_INTERRUPTIBLE);
		schedule();
	}
	set_restore_sigmask();                       // ④ 恢复
	return -ERESTARTNOHAND;
}
```

`sigsuspend` 的等待循环与 `pause` **完全相同**，只是外面包了三步：保存掩码 → 设置新掩码 → 恢复掩码。

**原子性的来源**：这四步都在**同一次系统调用内**完成，内核态执行期间不会有用户态的"窗口"。用户态若自己写「`sigprocmask` 解除阻塞 → `pause()`」，两个系统调用之间就能被信号插入。

**关键洞察**：原子性不是来自"做了更多事"，而是来自"**这些事在一次系统调用里做完**"。

</details>

<details>
<summary><b>问 4：</b>写出 <code>sigsuspend()</code> 的标准用法，并解释每一步的作用。</summary>

```c
sigset_t block, orig;
sigemptyset(&block);
sigaddset(&block, SIGINT);

/* ① 先阻塞 SIGINT */
sigprocmask(SIG_BLOCK, &block, &orig);

/* ② 临界区：此期间到达的 SIGINT 堆积在 pending，不会丢 */
prepare_work();
check_and_set_flag();

/* ③ 原子地：临时恢复 orig → 等待 → 回到阻塞态 */
sigsuspend(&orig);

/* ④ 被唤醒，此时掩码已自动恢复为阻塞态，可安全清理 */
cleanup();
sigprocmask(SIG_SETMASK, &orig, NULL);
```

| 步骤 | 作用 |
|------|------|
| ① 阻塞 | 让信号**不丢失**——期间到达的信号进入 pending 而非被错过 |
| ② 临界区 | 做需要在"信号不会打断"状态下完成的工作 |
| ③ `sigsuspend(&orig)` | **原子地**：临时把掩码换成 `orig`（解除阻塞）→ 挂起等待 → 被唤醒后恢复到阻塞态 |
| ④ 清理 | 此时 `SIGINT` 已被递送，且掩码回到阻塞态，可安全收尾 |

**为什么第 ③ 步传的是 `orig`（原掩码）而不是 `block`**：`sigsuspend` 的参数是「等待期间**要生效**的掩码」。我们想在等待时**解除**对 `SIGINT` 的阻塞，所以传入不含 `SIGINT` 的 `orig`。

**关键点**：`sigsuspend` 返回后，掩码自动回到**调用前**的状态（阻塞态），无需手动恢复——内核的 `set_restore_sigmask()` 负责。

</details>

<details>
<summary><b>问 5：</b>HFT 事件循环中应该如何处理信号？为什么不用 <code>pause</code>/<code>sigsuspend</code>？</summary>

**问题**：`pause`/`sigsuspend` 都是「**专门**等信号」——期间无法同时等行情数据（socket）。HFT 事件循环需要的是「**同时**等信号和 I/O」。

**方案对比**：

| 方案 | 能否同时等 I/O | 说明 |
|------|---------------|------|
| `pause()` | ❌ | 且有毒竞态 |
| `sigsuspend()` | ❌ | 只解决竞态，仍不能同时等 I/O |
| `pselect`/`ppoll` | ✅ | 带 `sigmask` 参数，原子「改掩码 + 等 I/O + 恢复」 |
| **`epoll_pwait`** | ✅ | epoll 版本，HFT 首选 |
| **`signalfd` + `epoll`** | ✅ | 信号变 fd，完全融入事件循环，最干净 |

**推荐：signalfd**（[Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md)）

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, NULL);          /* ① 必须阻塞，否则走 handler */

int sfd = signalfd(-1, &mask, SFD_NONBLOCK);  /* ② 信号变 fd */

/* ③ 加入 epoll，与行情 socket 一起等 */
struct epoll_event ev = { .events = EPOLLIN, .data.fd = sfd };
epoll_ctl(epfd, EPOLL_CTL_ADD, sfd, &ev);

for (;;) {
    int n = epoll_wait(epfd, events, MAX, -1);
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == sfd) {
            struct signalfd_siginfo si;
            read(sfd, &si, sizeof si);        /* ④ 读出信号，不跑 handler */
            if (si.ssi_signo == SIGTERM) running = 0;
        } else {
            handle_market_data(events[i].data.fd);
        }
    }
}
```

**优势**：
- 信号与 I/O 统一在 `epoll_wait` 中等待，**零额外竞态**
- 不跑 handler，**无异步信号安全**问题（可在处理代码里随意调用 `printf`/`malloc`）
- 信号**不丢失**（内核维护队列，逐个 `read` 出来）
- 完全同步，延迟可预测——这对 HFT 至关重要

</details>
