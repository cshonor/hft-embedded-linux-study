## 本节讲什么

1. 判断一个进程是否还活着有**哪几种方法**——`kill(pid, 0)`、`/proc/PID`、`pidfd` 各自的原理与代价
2. 为什么 `kill(pid, 0)` **会把僵尸进程判为"活着"**——内核探测链路到底查了什么
3. **PID 复用**如何导致误判，以及为什么 `pidfd` 才是可靠方案

---

## 一、三种方法对比

| 方法 | 接口 | 原理 | PID 复用安全 | 僵尸进程判定 |
|------|------|------|--------------|--------------|
| `kill(pid, 0)` | `kill()` | 查 PID 哈希表 + 权限检查 | ❌ | ⚠️ **判定为"存在"** |
| 访问 `/proc/PID` | `stat()` / `access()` | procfs 查该 PID 的目录项 | ❌ | ⚠️ **存在**（僵尸也有目录） |
| `pidfd_open()` | `syscall(SYS_pidfd_open)` | 获取对进程对象的**稳定引用** | ✅ | ✅ 可用 `poll` 精确判定 |

---

## 二、`kill(pid, 0)` 的内核链路：为什么它查不出僵尸

`kill(pid, 0)` 的调用链是：`SYSCALL_DEFINE2(kill)` → `kill_proc_info` → `kill_pid_info` → `pid_task()`。

```c
// kernel/signal.c:1486
int kill_pid_info(int sig, struct kernel_siginfo *info, struct pid *pid)
{
	int error = -ESRCH;
	struct task_struct *p;

	for (;;) {
		rcu_read_lock();
		p = pid_task(pid, PIDTYPE_PID);            // ← 关键：只查 PID 哈希表
		if (p)
			error = group_send_sig_info(sig, info, p, PIDTYPE_TGID);
		rcu_read_unlock();
		if (likely(!p || error != -ESRCH))
			return error;

		/*
		 * The task was unhashed in between, try again.  If it
		 * is dead, pid_task() will return NULL, if we race with
		 * de_thread() it will find the new leader.
		 */
	}
}
```

**核心发现**：`pid_task(pid, PIDTYPE_PID)` 只回答一个问题——「PID 哈希表里有没有这个 `task_struct`」。它**完全不检查进程状态**（`p->exit_state`、`TASK_ZOMBIE` 等）。

而**僵尸进程虽然已退出，但它的 `task_struct` 仍留在进程表里等待父进程 `wait()` 收尸**，所以 `pid_task()` 照样找得到它。

```
   进程退出流程：
   调用 exit()  →  释放资源  →  变僵尸（task_struct 仍在 PID 表）  →  父进程 wait()  →  彻底消失
                                        ↑                                              ↑
                           kill(pid,0) 在这里返回成功                        kill(pid,0) 在这里返回 ESRCH
```

> **这是本节最重要的陷阱**：`kill(pid, 0)` 回答的是「**PID 是否有效**」，不是「**进程是否还在运行**」。

### 想区分僵尸怎么办？

读 `/proc/PID/stat` 的第三个字段（进程状态字符）：

```c
/* 读取 /proc/PID/stat 的 state 字段：Z = 僵尸 */
static int is_zombie(pid_t pid)
{
    char path[64], buf[256];
    snprintf(path, sizeof path, "/proc/%d/stat", pid);
    FILE *f = fopen(path, "r");
    if (!f) return -1;                  /* 进程不存在 */
    if (!fgets(buf, sizeof buf, f)) { fclose(f); return -1; }
    fclose(f);
    char *rparen = strrchr(buf, ')');   /* comm 字段可能含空格和括号 */
    return (rparen && rparen[2] == 'Z');
}
```

`/proc/PID/stat` 的状态字符：`R` 运行 / `S` 可中断睡眠 / `D` 不可中断睡眠 / `T` 停止 / **`Z` 僵尸** / `X` 死亡。

## 三、PID 复用：更隐蔽的误判

即使排除了僵尸，还有一个更危险的问题：**PID 是会被回收重用的**。

```
  t0: 监控进程记录子进程 PID = 1234
  t1: 子进程 1234 退出并被回收
  t2: 内核把 PID 1234 分配给一个完全无关的新进程（可能属于别的程序/别的容器）
  t3: 监控进程 kill(1234, 0) → 返回成功 → 误判"我的子进程还活着" ❌
  t4: 监控进程 kill(1234, SIGTERM) → 杀了一个无辜的进程 ❌❌
```

PID 上限默认由 `/proc/sys/kernel/pid_max` 决定（64 位系统通常 4194304，32 位 32768），分配是循环递增的，回绕很快。

> **现实案例**：容器 runtime 如果用 `kill(pid, 0)` 判断容器主进程存活，在 PID 快速回绕的繁忙宿主上，可能误判并把信号发给宿主的无关进程。这正是 `pidfd` 被引入内核（Linux 5.3）的主要动机之一。

---

## 四、可靠方案：`pidfd`

`pidfd` 是对**进程对象**（`struct pid`）的文件描述符引用，而不是对数字 PID 的引用。只要 fd 不关闭，内核就持有该进程的引用，**PID 绝不会被复用给别的进程**。

```c
#include <sys/syscall.h>
#include <unistd.h>
#include <signal.h>
#include <poll.h>

int pidfd = syscall(SYS_pidfd_open, pid, 0);      /* 获取稳定引用 */

/* ① 探测：用 0 号信号 */
int r = syscall(SYS_pidfd_send_signal, pidfd, 0, NULL, 0);
/* r == 0   进程存在（含僵尸）*/
/* r == -1 && errno == ESRCH   进程已被彻底回收 */

/* ② 更优雅：用 poll 等待进程退出（无信号、无竞态）*/
struct pollfd pfd = { .fd = pidfd, .events = POLLIN };
poll(&pfd, 1, -1);        /* 进程退出时 POLLIN 就绪 */
```

| 优势 | 说明 |
|------|------|
| **无 PID 复用** | 引用的是进程对象，不是数字 |
| **无竞态** | `pidfd_open` 在进程刚退出时仍成功，返回的 fd 可用于后续判断 |
| **可 poll** | 进程退出会触发 `POLLIN`，天然集成进事件循环（HFT 尤其有用） |
| **可区分** | 配合 `/proc/PID/stat` 或 `waitid` 可精确区分运行/僵尸/消失 |

内核实现：`SYSCALL_DEFINE4(pidfd_send_signal)`@`kernel/signal.c:3882`。

## 五、特殊场景信号

除了主动探测，内核还提供了两个「通知型」接口，比轮询探测高效得多：

| 接口 | 用途 |
|------|------|
| `prctl(PR_SET_PDEATHSIG, sig)` | 父进程**死亡时**内核自动给本进程发 `sig`（守护进程检测父进程消失） |
| `PR_SET_PDEATHSIG` + `getppid()` 比对 | 父进程变了说明原父进程死了，可防误触发 |

```c
/* 子进程请求：父进程退出时给我发 SIGTERM */
prctl(PR_SET_PDEATHSIG, SIGTERM);

/* 防误触发：设置后再检查一次父进程是否真的还活着 */
if (getppid() != original_ppid)
    raise(SIGTERM);      /* 父进程在 prctl 之前就已退出，手动补上 */
```

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 守护进程常用 `kill(pid, 0)` 检查 worker 存活，但**必须配合 `waitpid()` 收尸**——否则 worker 变僵尸后永远探测为"活着"，守护进程不会重启它，系统静默降级。更稳的做法是 `pidfd_open` + `poll`，把进程退出变成事件而非轮询 |
| HFT | 进程存活监控绝不能用 `kill(pid,0)` 轮询：① 系统调用开销；② PID 复用会误判；③ 僵尸会假阳性。HFT 监控链路应改用 `pidfd` + `poll`/`epoll`，把「进程退出」纳入统一事件循环，零轮询、零竞态、可精确计时 |

---

## 代码示例：三种探测方案实测对比

```c
/* probe_alive.c —— 对比 kill(pid,0) / /proc/PID / pidfd 对僵尸的判定
 * 编译: gcc -o probe_alive probe_alive.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <poll.h>
#include <sys/syscall.h>
#include <sys/wait.h>

/* 方案一：kill(pid, 0) */
static const char *probe_kill(pid_t pid)
{
    if (kill(pid, 0) == 0) return "存在（无法区分僵尸）";
    return (errno == ESRCH) ? "ESRCH 不存在" : "EPERM 存在但无权限";
}

/* 方案二：读 /proc/PID/stat 状态字符 */
static const char *probe_proc(pid_t pid)
{
    char path[64], buf[512];
    snprintf(path, sizeof path, "/proc/%d/stat", pid);
    FILE *f = fopen(path, "r");
    if (!f) return "不存在";
    if (!fgets(buf, sizeof buf, f)) { fclose(f); return "不存在"; }
    fclose(f);
    char *rp = strrchr(buf, ')');            /* comm 可能含 ")" 与空格 */
    if (!rp || rp[1] != ' ') return "解析失败";
    switch (rp[2]) {
    case 'Z': return "僵尸 Zombie";
    case 'R': return "运行 Running";
    case 'S': return "睡眠 Sleeping";
    case 'D': return "不可中断睡眠";
    case 'T': return "停止 Stopped";
    default:  return "其他状态";
    }
}

int main(void)
{
    pid_t cpid = fork();
    if (cpid == 0) _exit(0);                 /* 子进程立即退出 → 变僵尸 */

    sleep(1);                                /* 确保子进程已进入僵尸态 */

    printf("子进程 %d 已退出但未被 wait，处于僵尸态：\n\n", cpid);
    printf("  kill(pid,0)      -> %s\n", probe_kill(cpid));
    printf("  /proc/%d/stat    -> %s\n", cpid, probe_proc(cpid));

    /* 演示僵尸可被 wait 后彻底消失 */
    waitpid(cpid, NULL, 0);
    printf("\nwaitpid() 收尸后：\n");
    printf("  kill(pid,0)      -> %s\n", probe_kill(cpid));
    printf("  /proc/%d/stat    -> %s\n", cpid, probe_proc(cpid));

    /* pidfd 方案：无 PID 复用，可 poll */
    pid_t c2 = fork();
    if (c2 == 0) { sleep(2); _exit(0); }
    int pidfd = syscall(SYS_pidfd_open, c2, 0);
    if (pidfd >= 0) {
        struct pollfd pfd = { .fd = pidfd, .events = POLLIN };
        printf("\npidfd(%d) 等待子进程退出...\n", c2);
        if (poll(&pfd, 1, 5000) > 0)
            printf("  poll 返回 POLLIN -> 进程已退出（无竞态、无 PID 复用风险）\n");
        close(pidfd);
    }
    waitpid(c2, NULL, 0);
    return 0;
}
```

预期输出：

```
子进程 12345 已退出但未被 wait，处于僵尸态：

  kill(pid,0)      -> 存在（无法区分僵尸）
  /proc/12345/stat -> 僵尸 Zombie

waitpid() 收尸后：
  kill(pid,0)      -> ESRCH 不存在
  /proc/12345/stat -> 不存在

pidfd(12346) 等待子进程退出...
  poll 返回 POLLIN -> 进程已退出（无竞态、无 PID 复用风险）
```

## 自测题

<details>
<summary><b>问 1：</b>子进程已经退出但父进程还没 <code>wait()</code>，此时 <code>kill(pid, 0)</code> 返回什么？为什么？</summary>

**返回 0（成功）**，即判定为"进程存在"。

原因在 `kill_pid_info()`（`kernel/signal.c:1486`）：

```c
p = pid_task(pid, PIDTYPE_PID);        // 只查 PID 哈希表里有没这个 task
if (p)
    error = group_send_sig_info(sig, info, p, PIDTYPE_TGID);
```

`pid_task()` **只检查 PID 哈希表里有没有对应的 `task_struct`，完全不看进程状态**。

而僵尸进程虽然已经 `exit()`，但它的 `task_struct` **仍然保留在进程表里**，等待父进程 `wait()` 回收。所以 `pid_task()` 照样查得到，`kill(pid, 0)` 照样返回成功。

**结论**：`kill(pid, 0)` 回答的是「**PID 是否有效**」，不是「**进程是否还在运行**」。要区分僵尸，必须读 `/proc/PID/stat` 的状态字符（`Z`）。

</details>

<details>
<summary><b>问 2：</b>什么是 PID 复用？它会导致什么后果？</summary>

PID 是内核的**有限循环资源**，进程退出后被回收，可分配给新进程。

**危险时间线**：

```
t0: 监控进程记录子进程 PID = 1234
t1: 子进程 1234 退出
t2: 内核把 PID 1234 分配给完全无关的新进程
t3: 监控进程 kill(1234, 0) → 成功 → 误判"我的子进程还活着"
t4: 监控进程 kill(1234, SIGTERM) → 杀了一个无辜进程
```

**后果**：监控逻辑完全失效，最坏情况是向无关进程（可能是宿主上的其他服务）发送终止信号。在容器环境中尤其危险——容器内的 PID 命名空间与宿主不同，回收速度更快。

**解决**：用 `pidfd_open()` 获取对进程对象的稳定引用，用 `pidfd_send_signal()` / `poll()` 替代 `kill()`。

</details>

<details>
<summary><b>问 3：</b>为什么 <code>pidfd</code> 能避免 PID 复用问题？它的本质是什么？</summary>

**本质**：`pidfd` 是**指向进程对象（`struct pid`）的文件描述符**，而不是指向一个数字 PID。

对比：

| | `kill(pid, ...)` | `pidfd_send_signal(pidfd, ...)` |
|--|------------------|----------------------------------|
| 引用对象 | 数字 PID（会被复用） | `struct pid` 内核对象（引用计数保护） |
| 查找方式 | 每次调用重新在 PID 哈希表里查 | fd 直接持有引用，无需查找 |
| 复用风险 | ❌ 有 | ✅ 无 |

只要 `pidfd` 不关闭，内核就持有该 `struct pid` 的引用，**PID 绝不会在此期间被分配给别的进程**。

**额外好处**：进程退出会触发 `POLLIN`，可以直接 `poll()`/`epoll()` 监听，把"进程退出"变成一个事件，天然集成进事件循环——这对 HFT 的低延迟监控尤其有价值。

内核实现：`SYSCALL_DEFINE4(pidfd_send_signal)`@`kernel/signal.c:3882`（Linux 5.3+）。

</details>

<details>
<summary><b>问 4：</b>守护进程想「父进程死了就自动退出」，用什么机制？怎么做才没有竞态？</summary>

用 `prctl(PR_SET_PDEATHSIG, sig)`：父进程死亡时，内核自动给本进程发指定信号。

```c
prctl(PR_SET_PDEATHSIG, SIGTERM);
```

**竞态与解法**：如果在调用 `prctl()` **之前**父进程就已经退出了，那么这个设置永远不会生效——本进程会永远等待一个不会来的信号。

解法是设置后**再校验一次父进程 ID**：

```c
pid_t original_ppid = getppid();
prctl(PR_SET_PDEATHSIG, SIGTERM);
if (getppid() != original_ppid)     /* 父进程在 prctl 之前就死了 */
    raise(SIGTERM);                 /* 手动补上 */
```

**原理**：`getppid()` 在父进程死亡时会返回 1（被 init/systemd 收养）或新的 reparent 目标。比对即可发现父进程已变。

</details>

<details>
<summary><b>问 5：</b>对比 <code>kill(pid,0)</code>、<code>/proc/PID</code>、<code>pidfd</code> 三种探测方案，各适合什么场景？</summary>

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| `kill(pid, 0)` | 最简单、零额外 fd | **无法区分僵尸**、**PID 复用误判**、每次都是系统调用 | 快速一次性探测，且能保证 PID 不会被复用（如刚 `fork` 出来的子进程） |
| `/proc/PID/stat` | **能识别僵尸**（状态字符 `Z`） | 文件 I/O 开销更大、仍有 PID 复用问题 | 需要区分僵尸/运行状态的场景（如监控脚本、`ps` 类工具） |
| `pidfd` | **无 PID 复用**、**可 poll**、零轮询 | 需要 Linux 5.3+、占用一个 fd、代码略复杂 | 守护进程、容器 runtime、任何需要**长期**监控进程存活的生产代码 |

**一句话建议**：
- 写 demo / 一次性检查 → `kill(pid, 0)`（记住它查的是"PID 有效"而非"进程存活"）
- 需要知道是不是僵尸 → `/proc/PID/stat`
- 生产代码长期监控 → `pidfd` + `poll`

</details>
