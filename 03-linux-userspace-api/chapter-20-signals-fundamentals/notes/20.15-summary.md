## 核心 API 速查

| 类别 | API | 作用 |
|------|-----|------|
| **改变处置** | `sigaction(sig, &act, &old)` | 设置 handler / `SIG_DFL` / `SIG_IGN`（**首选**） |
| | `signal(sig, handler)` | 同上，但不可移植（仅 demo / `SIG_IGN`） |
| **发送信号** | `kill(pid, sig)` | 发给进程/进程组/广播 |
| | `raise(sig)` | 发给**调用线程**（多线程下） |
| | `killpg(pgrp, sig)` | 发给进程组 |
| | `tgkill(tgid, tid, sig)` | 发给指定线程（安全） |
| | `pidfd_send_signal(pidfd, ...)` | 经 pidfd 发送（无 PID 复用） |
| **信号集** | `sigemptyset/fillset/addset/delset/ismember` | 位图操作 |
| **掩码** | `sigprocmask(how, &set, &old)` | 阻塞/解除阻塞（单线程） |
| | `pthread_sigmask(...)` | 同上（多线程用这个） |
| **查询** | `sigpending(&set)` | 读未决集 |
| **等待** | `pause()` | 挂起等信号（**有竞态，勿用**） |
| | `sigsuspend(&mask)` | 原子「改掩码 + 等待 + 恢复」 |
| **诊断** | `strsignal(sig)` / `psignal(sig, msg)` | 编号 → 描述（非 async-signal-safe） |

## 五条铁律

| # | 铁律 | 依据 |
|---|------|------|
| 1 | **`signal()` 不可移植 → 永远用 `sigaction()`** | 内核硬编码 `SA_ONESHOT\|SA_NOMASK`（`:4628`）；BSD/SysV 语义相反 |
| 2 | **标准信号不排队 → 不能用信号计数** | `legacy_queue:1079`；阻塞期间同号只留一份 |
| 3 | **`pause()` 有竞态 → 用 `sigsuspend()`** | `pause:4639` 无掩码操作；`sigsuspend:4650` 原子四步 |
| 4 | **`SIGKILL`/`SIGSTOP` 无法阻塞/忽略/捕获** | `do_sigaction:4129`；`set_current_blocked:3066`；`do_sigaction:4161` 三重防线 |
| 5 | **handler 里只调异步信号安全函数** | handler 与被中断代码同线程同栈，共享全部状态 |

## 三个关键区分（高频混淆点）

| 对比 | A | B |
|------|---|---|
| **阻塞 vs 忽略** | 进 pending，解除后补递送（**延迟**） | 直接丢弃，永不递送（**丢弃**） |
| **掩码 vs 处置** | `task_struct.blocked`，**线程私有** | `sighand->action[]`，**进程共享** |
| **handler 上下文** | 不是新线程，在**被打断线程自己的栈**上执行 | — |

## 递送时机一图流

```
信号产生（kill/硬件/终端/软件）
        ↓
  pending 位图置位（线程私有 or 进程共享）
        ↓
  进程进入内核（syscall / 中断 / 异常）
        ↓
  返回用户态前 → get_signal()          kernel/signal.c:2660
        ├─ 取出未阻塞的信号 dequeue_signal()
        ├─ signal_delivered()：掩码 |= sa_mask ∪ {本信号}
        ├─ 搭建 sigframe（保存寄存器 + 原掩码 + sigreturn 蹦床）
        └─ 搭栈失败 → force_sigsegv()
        ↓
  执行 handler → sigreturn → 恢复原掩码与寄存器
        ↓
  回到被打断处继续执行
```

## 代码自测

<details>
<summary><b>1. 为什么 <code>signal()</code> 不如 <code>sigaction()</code> 安全？</summary>

`signal()` 的行为在不同 UNIX 实现中不一致：

| 语义 | 是否自动复位 | handler 期间是否阻塞同号信号 |
|------|-------------|---------------------------|
| **System V** | ✅ 复位为 `SIG_DFL` | ❌ 不阻塞（`SA_NOMASK`） |
| **BSD 4.3+** | ❌ 不复位 | ✅ 阻塞 |

两派语义**截然相反**。Linux 内核的 `sys_signal` 固定采用 SVr4 风格（`kernel/signal.c:4628` 硬编码 `SA_ONESHOT | SA_NOMASK`），而 glibc 的 `signal()` 包装却走 `rt_sigaction` + `SA_RESTART` 模拟 BSD——**同一台 Linux 机器上，用不用 libc 包装结果都不一样**。

`sigaction()` 是 POSIX 标准，行为在所有平台一致，且额外支持：

- `SA_RESTART`（自动重启被中断的 syscall）
- `sa_mask`（handler 期间额外屏蔽的信号）
- `SA_SIGINFO`（获取 `siginfo_t`）
- `SA_ONSTACK`（备用栈，`SIGSEGV` 处理必需）

**结论**：生产代码一律用 `sigaction()`；`signal()` 只用于 demo 或一键 `SIG_IGN`。

</details>

<details>
<summary><b>2. 标准信号不排队有什么实际后果？</summary>

阻塞期间多次发送同一信号，解除后**只递送一次**。

**后果 1（`SIGCHLD` 漏收，最常见）**：多个子进程同时退出 → 多次 `SIGCHLD` → pending 中只留一份 → handler 只执行一次 → 若 handler 里只调用一次 `waitpid`，其余子进程**永久变僵尸**。

正确写法：

```c
void handler(int sig) {
    int saved_errno = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0)   /* 循环 + WNOHANG */
        ;
    errno = saved_errno;
}
```

**后果 2（无法计数）**：`handler` 里 `count++` 会漏计，5 次信号可能只加 1。

**准确措辞**：POSIX 保证的是「**至少递送一次**」，不是「恰好一次」——某些时序下也可能递送多次。所以 handler 必须写成**幂等**的。

**需要计数时**：改用 eventfd / 管道 / 共享内存原子变量，或实时信号 + `sigqueue()`，或 signalfd。

</details>

<details>
<summary><b>3. <code>SIGKILL</code> 为什么一定能杀死进程？内核有几道防线？</summary>

三道防线，用户态无法绕过：

| # | 层 | 内核位置 | 行为 |
|---|-----|----------|------|
| ① | 改变处置 | `do_sigaction:4129` `sig_kernel_only(sig)` | 返回 `-EINVAL` |
| ② | 阻塞（掩码） | `set_current_blocked:3066` `sigdelsetmask` | 从掩码中**静默剔除** |
| ③ | handler 期间屏蔽 | `do_sigaction:4161` `sigdelsetmask(&act->sa.sa_mask, ...)` | 从 `sa_mask` 中**静默剔除** |

`SIG_KERNEL_ONLY_MASK` 只含这两个信号（`include/linux/signal.h:418`）：

```c
#define SIG_KERNEL_ONLY_MASK (\
	rt_sigmask(SIGKILL)   |  rt_sigmask(SIGSTOP))
```

**注意**：②③ 是**静默**的——不返回错误、不报错。所以即使你写了 `sigaddset(&set, SIGKILL); sigprocmask(SIG_BLOCK, &set, NULL);`，调用返回成功，但 `SIGKILL` 根本没进掩码。验证方法只能是**读回掩码比对**。

**设计意图**：保证 `kill -9` 和 `kill -STOP` 永远是管理员和 watchdog 的最后手段——无论进程怎么写（屏蔽全部信号、注册全部 handler），都能收场。

</details>

<details>
<summary><b>4. 信号递送发生在什么时刻？纯用户态忙等能收到信号吗？</b></summary>

递送发生在**进程从内核态返回用户态之前**，由 `get_signal()`（`kernel/signal.c:2660`）检查 pending 并分派处置。

**纯用户态忙等收不到信号**（会一直停留在 pending）。因为递送的触发点是「进入内核再返回」这个边界；`while(1);` 不进内核，就永远不会经过检查点。

信号会一直 pending，直到该进程因以下任一原因进入内核：

- 时间片耗尽被抢占（会进调度器，返回用户态前检查）
- 主动发起系统调用
- 触发缺页异常
- 硬件中断

**实践意义**：

1. HFT 的忙等主循环收不到停机信号——这是为什么要用 signalfd 或轮询标志位，而不是依赖 handler。
2. 反过来，阻塞在 `read()` 这类**可中断 syscall** 里的进程能立即被信号唤醒（返回 `EINTR`）。

</details>

<details>
<summary><b>5. 多线程程序应该怎么处理信号？</b></summary>

**核心事实**：

| 属性 | 作用域 |
|------|--------|
| 掩码（`blocked`） | **线程私有** |
| 处置（`sighand->action[]`） | **进程/线程组共享** |
| pending | 两层（线程私有 + 进程共享） |

**问题**：用 `kill` 给多线程进程发信号，handler 由**任意一个**未阻塞该信号的线程执行——上下文（栈、TLS、锁状态）不可控。

**推荐模型**：

```
主线程                            专用信号线程
┌──────────────────┐             ┌──────────────────┐
│ pthread_sigmask  │             │                  │
│ (BLOCK 全部)      │             │  sigwaitinfo()   │ ← 同步消费，不跑 handler
└──────────────────┘             └──────────────────┘
       ↓ pthread_create                   ↑
┌──────────────────┐             信号阻塞在 pending 中
│ 工作线程 1..N     │
│ (继承掩码=全屏蔽)  │
└──────────────────┘
```

**步骤**：

1. **主线程在创建任何线程之前** `pthread_sigmask(SIG_BLOCK, &all, NULL)`
2. `pthread_create` 工作线程——它们**继承**主线程的掩码，天然全屏蔽
3. 起一个专用线程循环 `sigwaitinfo(&set, &info)` 同步取信号

**优势**：

- 不跑 handler → 无异步信号安全问题（处理代码里可随意 `printf`/`malloc`）
- 由固定线程执行 → 行为可预测
- 同步处理 → 延迟可控

**注意**：用 `pthread_sigmask()` 而非 `sigprocmask()`（后者在多线程下行为未定义）。

</details>
