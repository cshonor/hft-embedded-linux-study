## 一、掩码是什么，存在哪里

**信号掩码（signal mask）** = 一个 `sigset_t`，表示「当前**被阻塞**的信号集合」。

- 被阻塞的信号**照常产生**，进入 pending 位图
- 但只要还在掩码里，就**不会递送**
- 解除阻塞后，pending 的信号会**立即补递送**

内核存放位置是 `task_struct.blocked`：

| 属性 | 存放位置 | 作用域 |
|------|----------|--------|
| **掩码** | `task_struct.blocked` | **线程私有** |
| **处置** | `sighand->action[sig-1]` | 进程/线程组共享（见 [20.3](./20.3-changing-signal-dispositions-signal.md)） |
| **pending** | `task_struct.pending`（私有）+ `signal_struct.shared_pending`（共享） | 两层 |

> **核心考点**：掩码是**线程属性**，不是进程属性。`sigprocmask()` 只改**调用线程**的掩码；`sigaction()` 改的是**全进程**的处置。多线程程序要统一屏蔽，必须在**创建线程之前**于主线程设好（新线程继承掩码），或每个线程各自 `pthread_sigmask()`。

### 阻塞 ≠ 忽略（再强调）

| | **阻塞**（掩码中） | **忽略**（`SIG_IGN`） |
|--|------|------|
| 信号抵达后 | 进 pending，**记着** | 直接丢弃，**忘了** |
| 解除后 | 会补递送 | — |
| 能否查出「来过」 | 能（`sigpending`） | 不能 |
| 本质 | **延迟递送** | **永不递送** |
| 设置方式 | `sigprocmask` / `pthread_sigmask` | `sigaction` 设 `SIG_IGN` |

## 二、`sigprocmask()` 与三种 `how`

```c
#include <signal.h>

int sigprocmask(int how, const sigset_t *set, sigset_t *oldset);
/* 返回：成功 0，失败 -1 */
/* 若 set 为 NULL，则只读取当前掩码到 oldset，不做修改 */
```

| `how` | 语义 | 内核实现 |
|-------|------|----------|
| `SIG_BLOCK` | 新掩码 = 旧 ∪ set（**加入**要阻塞的） | `sigorsets()`（`:3105`） |
| `SIG_UNBLOCK` | 新掩码 = 旧 − set（**移除**要解除的） | `sigandnsets()`（`:3108`） |
| `SIG_SETMASK` | 新掩码 = set（**整体替换**） | `newset = *set`（`:3111`） |
| 其他 | `-EINVAL` | `default`（`:3113`） |

内核实现（`kernel/signal.c:3094`）：

```c
int sigprocmask(int how, sigset_t *set, sigset_t *oldset)
{
	struct task_struct *tsk = current;
	sigset_t newset;

	/* Lockless, only current can change ->blocked, never from irq */
	if (oldset)
		*oldset = tsk->blocked;

	switch (how) {
	case SIG_BLOCK:
		sigorsets(&newset, &tsk->blocked, set);      // 并集
		break;
	case SIG_UNBLOCK:
		sigandnsets(&newset, &tsk->blocked, set);    // 差集
		break;
	case SIG_SETMASK:
		newset = *set;                               // 替换
		break;
	default:
		return -EINVAL;
	}

	__set_current_blocked(&newset);
	return 0;
}
```

> **用法要点**：`oldset` 参数是「保存现场 + 事后恢复」的关键。典型模式：
> ```c
> sigset_t new, old;
> sigemptyset(&new); sigaddset(&new, SIGINT);
> sigprocmask(SIG_BLOCK, &new, &old);    /* 阻塞并保存原掩码 */
> /* ... 临界区 ... */
> sigprocmask(SIG_SETMASK, &old, NULL);  /* 精确恢复，而非"解除 SIGINT" */
> ```
> 用 `SIG_SETMASK` 恢复比 `SIG_UNBLOCK` 更准确——后者会**误解除**原本就阻塞的信号（见自测题 2）。

## 三、`SIGKILL` / `SIGSTOP` 无法被阻塞

`set_current_blocked()` 是第一道防线：

```c
// kernel/signal.c:3064
void set_current_blocked(sigset_t *newset)
{
	sigdelsetmask(newset, sigmask(SIGKILL) | sigmask(SIGSTOP));   // 强制剔除
	__set_current_blocked(newset);
}
```

所以 `sigaddset(&set, SIGKILL)` + `sigprocmask` **不会生效，也不报错**——静默丢弃。

### 有趣的反例：内核线程可以阻塞 `SIGKILL`

内核注释里明确提到了这个差异：

```c
/*
 * This is also useful for kernel threads that want to temporarily
 * (or permanently) block certain signals.
 *
 * NOTE! Unlike the user-mode sys_sigprocmask(), the kernel
 * interface happily blocks "unblockable" signals like SIGKILL
 * and friends.
 */                                              // kernel/signal.c:3086-3093
```

| | 用户态 `sys_rt_sigprocmask` | 内核态 `sigprocmask()` |
|--|---------------------------|----------------------|
| 能否阻塞 `SIGKILL` | ❌ 被 `sigdelsetmask` 剔除 | ✅ **可以** |

原因是内核线程收到的 `SIGKILL` 通常是模块卸载等内部事件，需要能被临时屏蔽；而用户进程的 `SIGKILL` 必须始终是有效的最后手段。

## 四、多线程：改掩码会丢信号吗？

这是本节最深的一处机制。考虑这个场景：

```
   线程 A 和线程 B 同属一个进程
   t0: 进程级 shared_pending 里有一个 SIGTERM（由 kill() 发来）
   t1: 线程 A 调用 sigprocmask(SIG_BLOCK, {SIGTERM})
   t2: 现在 A 处理不了这个信号了 → 它被"遗忘"了？
```

**不会**——内核在 `__set_task_blocked()` 里做了重新定向（retarget）：

```c
// kernel/signal.c:3045
static void __set_task_blocked(struct task_struct *tsk, const sigset_t *newset)
{
	if (task_sigpending(tsk) && !thread_group_empty(tsk)) {
		sigset_t newblocked;
		/* A set of now blocked but previously unblocked signals. */
		sigandnsets(&newblocked, newset, &current->blocked);
		retarget_shared_pending(tsk, &newblocked);     // ← 转交给其他线程
	}
	tsk->blocked = *newset;
	recalc_sigpending();
}
```

`retarget_shared_pending()`（`kernel/signal.c:2948`）的逻辑：找出那些「刚被阻塞、但进程级 pending 里有」的信号，把它们重新发给**还能处理该信号的其他线程**：

```c
// kernel/signal.c:2948
static void retarget_shared_pending(struct task_struct *tsk, sigset_t *which)
{
	sigset_t retarget;
	struct task_struct *t;

	sigandsets(&retarget, &tsk->signal->shared_pending.signal, which);
	if (sigisemptyset(&retarget))
		return;

	t = tsk;
	while_each_thread(tsk, t) {
		if (t->flags & PF_EXITING)
			continue;
		if (!has_pending_signals(&retarget, &t->blocked))
			continue;
		/* Remove the signals this thread can handle. */
		...
	}
}
```

配套的函数注释也点明了必须走这个 helper：

```c
/**
 * set_current_blocked - change current->blocked mask
 *
 * It is wrong to change ->blocked directly, this helper should be used
 * to ensure the process can't miss a shared signal we are going to block.
 */                                              // kernel/signal.c:3057-3063
```

> **实践意义**：`sigprocmask()` 是安全的——多线程下某个线程阻塞信号不会导致进程级信号被吞掉。但**如果所有线程都阻塞了某信号，那它就真的停留在 pending 里**，直到某个线程解除阻塞。

## 五、原子地「改掩码 + 等待」：避免竞态

一个经典竞态：想在阻塞状态下等待信号。

```c
/* ❌ 有竞态：解除阻塞和 pause 之间，信号可能已经递送了 */
sigprocmask(SIG_UNBLOCK, &mask, NULL);
pause();          /* 信号若在此前到达并递送，pause 会永远沉睡 */
```

`sigsuspend()` 把两步合成一个原子操作（详见 [Ch22.9](../../chapter-22-signals-advanced/notes/22.9-waiting-for-a-signal-using-a-mask-sigsus.md)）。

Linux 还提供了一批「带 sigmask 参数」的等待接口，机制是 `set_user_sigmask()`：

```c
// kernel/signal.c:3131
/**
 * The api helps set app-provided sigmasks.
 *
 * This is useful for syscalls such as ppoll, pselect, io_pgetevents and
 * epoll_pwait where a new sigmask is passed from userland for the syscalls.
 *
 * Note that it does set_restore_sigmask() in advance, so it must be always
 * paired with restore_saved_sigmask_unless() before return from syscall.
 */
int set_user_sigmask(const sigset_t __user *umask, size_t sigsetsize)
```

| 接口 | 原子操作 |
|------|----------|
| `pselect(nfds, ..., &sigmask)` | 改掩码 + `select` + 恢复掩码 |
| `ppoll(fds, n, timeout, &sigmask)` | 改掩码 + `poll` + 恢复掩码 |
| `epoll_pwait(epfd, ..., &sigmask)` | 改掩码 + `epoll_wait` + 恢复掩码 |
| `sigsuspend(&mask)` | 改掩码 + `pause` + 恢复掩码 |

这些接口把「改掩码 → 等待 → 恢复掩码」做成**单个系统调用**，彻底消除了窗口期。HFT 事件循环里收停机信号，用 `epoll_pwait` + sigmask 是标准做法。

## 六、多线程：用 `pthread_sigmask` 而非 `sigprocmask`

POSIX 线程的掩码操作应该用：

```c
#include <pthread.h>
#include <signal.h>

int pthread_sigmask(int how, const sigset_t *set, sigset_t *oldset);
```

| 接口 | 标准 | 多线程安全 |
|------|------|-----------|
| `sigprocmask()` | POSIX，但**多线程下行为未定义** | ⚠️ |
| `pthread_sigmask()` | POSIX 线程标准 | ✅ |

**推荐的多线程信号处理模型**：

```
   主线程                          专用信号线程
   ┌──────────────────┐           ┌──────────────────┐
   │ pthread_sigmask  │           │                  │
   │ (BLOCK 全部)      │           │  sigwaitinfo()   │ ← 同步消费，不跑 handler
   └──────────────────┘           └──────────────────┘
          ↓ pthread_create                ↑
   ┌──────────────────┐           信号阻塞在 pending 中
   │ 工作线程 1..N     │
   │ (继承掩码=全屏蔽)  │
   └──────────────────┘
```

优点：信号被**同步**处理（不跑 handler，无异步信号安全问题），且由固定线程执行，行为可预测。详见 [Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md)。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 掩码是**线程属性**，多线程服务应用 `pthread_sigmask` 把信号集中到一个专用线程处理、其余线程全屏蔽，避免 handler 随机打断任意线程。临界区保护（如订单簿/共享环形缓冲区更新）用 `SIG_BLOCK`/`SIG_SETMASK` 成对包裹，防止 handler 重入导致数据结构不一致。注意必须在**创建线程前**于主线程设好掩码让新线程继承 |
| HFT | 在临界区用 `sigprocmask` 屏蔽信号可消除中断毛刺，但掩码切换本身是**系统调用**（~1μs 量级），热路径勿频繁进出。推荐：启动时一次性 `SIG_SETMASK` 屏蔽所有无关信号，之后不再改动，用 signalfd 或 `sigwaitinfo` 在专用线程消费，把信号从异步抢占变成同步事件。事件循环收停机信号用 `epoll_pwait` + sigmask，原子无竞态 |

## 代码示例：掩码阻塞与补递送

```c
/* maskdemo.c —— 验证「阻塞期间 pending，解除后立即补递送」
 * 编译: gcc -o maskdemo maskdemo.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

static volatile sig_atomic_t delivered = 0;
static void handler(int sig) { delivered = 1; }

static void show_pending(const char *tag)
{
    sigset_t p;
    sigemptyset(&p);
    sigpending(&p);
    printf("  %-22s SIGINT pending=%d  delivered=%d\n",
           tag, sigismember(&p, SIGINT) == 1, (int)delivered);
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sigaction(SIGINT, &sa, NULL);

    sigset_t mask, save;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);

    /* ① 阻塞 SIGINT，保存原掩码 */
    sigprocmask(SIG_BLOCK, &mask, &save);
    printf("1) 已阻塞 SIGINT\n");

    raise(SIGINT);
    show_pending("raise 之后");           /* pending=1 delivered=0 */

    /* ② 期间再发多次：标准信号不排队，仍只有一份 pending */
    raise(SIGINT);
    raise(SIGINT);
    show_pending("再 raise 两次");        /* pending 仍=1（不排队） */

    /* ③ 解除阻塞 → 立即补递送（仅一次） */
    sigprocmask(SIG_SETMASK, &save, NULL);
    show_pending("解除阻塞后");           /* pending=0 delivered=1 */

    /* ④ 试图阻塞 SIGKILL：被内核静默剔除 */
    sigset_t k, cur;
    sigemptyset(&k);
    sigaddset(&k, SIGKILL);
    sigprocmask(SIG_BLOCK, &k, NULL);
    sigemptyset(&cur);
    sigprocmask(SIG_BLOCK, NULL, &cur);
    printf("4) 试图阻塞 SIGKILL -> 掩码中 SIGKILL=%d (被 set_current_blocked:3066 剔除)\n",
           sigismember(&cur, SIGKILL) == 1);

    return 0;
}
```

预期输出：

```
1) 已阻塞 SIGINT
  raise 之后              SIGINT pending=1  delivered=0
  再 raise 两次           SIGINT pending=1  delivered=0      ← 不排队，只留一份
  解除阻塞后              SIGINT pending=0  delivered=1      ← 补递送仅一次
4) 试图阻塞 SIGKILL -> 掩码中 SIGKILL=0 (被剔除)
```

## 自测题

<details>
<summary><b>问 1：</b>信号掩码是进程属性还是线程属性？多线程程序要注意什么？</summary>

**线程属性**。掩码存放在 `task_struct.blocked`，每个线程一份；`sigprocmask()` 只修改**调用线程**的掩码。

对比（这是高频考点）：

| 属性 | 存放位置 | 作用域 |
|------|----------|--------|
| 掩码 | `task_struct.blocked` | **线程私有** |
| 处置 | `sighand->action[]` | **进程共享** |

**多线程要注意**：

1. 要统一屏蔽，**不能只在主线程调用一次就完事**——已经存在的线程不受影响，它们有自己的掩码副本。
2. **正确做法**：在 `pthread_create()` 之前于主线程设好掩码，**新线程会继承创建时的掩码**。
3. 多线程程序推荐使用 `pthread_sigmask()` 而非 `sigprocmask()`（POSIX 规定后者在多线程下行为未定义）。
4. 最稳妥的模型：主线程屏蔽所有关心的信号 → 创建工作线程（继承掩码）→ 起一个专用线程用 `sigwaitinfo()` 同步消费。

</details>

<details>
<summary><b>问 2：</b>为什么推荐用 <code>SIG_SETMASK</code> + 保存的 <code>oldset</code> 恢复，而不是 <code>SIG_UNBLOCK</code>？</summary>

因为 `SIG_UNBLOCK` 会**误解除调用者原本就阻塞的信号**。

考虑嵌套调用场景：

```c
void outer(void) {
    sigset_t m; sigemptyset(&m); sigaddset(&m, SIGINT);
    sigprocmask(SIG_BLOCK, &m, NULL);   /* 阻塞 SIGINT */
    inner();                            /* inner 内部也要临时屏蔽信号 */
    /* 期望此处 SIGINT 仍是阻塞的 */
}

void inner(void) {
    sigset_t m2, old; sigemptyset(&m2); sigaddset(&m2, SIGUSR1);
    sigprocmask(SIG_BLOCK, &m2, &old);
    /* ... 临界区 ... */
    sigprocmask(SIG_SETMASK, &old, NULL);   /* ✅ 精确还原 */
    /* 若写成 sigprocmask(SIG_UNBLOCK, &m2, NULL)，
       虽然只"减"了 SIGUSR1，看似无害，但一旦被改为
       SIG_SETMASK 之外的相对操作，就会破坏调用者假设 */
}
```

更直观的反例：如果 `inner()` 用的是 `sigfillset(&m2)` + `SIG_UNBLOCK`，就会把 `outer()` 阻塞的 `SIGINT` 一起解除。

**结论**：
- `SIG_SETMASK` + `oldset` = **精确还原**到进入时的状态，可安全嵌套
- `SIG_BLOCK`/`SIG_UNBLOCK` = **相对增减**，会破坏调用者的假设

**规则**：写可重入/库函数风格的代码时，**永远用 `SIG_SETMASK` + `oldset` 恢复**。

</details>

<details>
<summary><b>问 3：</b>多线程下，一个线程阻塞了某信号，会导致进程级信号丢失吗？</summary>

**不会**，内核有专门的保护机制。

`__set_task_blocked()`（`kernel/signal.c:3045`）在设置新掩码前会检查：如果有进程级 pending 信号即将被这个线程阻塞，就调用 `retarget_shared_pending()` 把它们**重新定向**给其他还能处理该信号的线程：

```c
static void __set_task_blocked(struct task_struct *tsk, const sigset_t *newset)
{
	if (task_sigpending(tsk) && !thread_group_empty(tsk)) {
		sigset_t newblocked;
		/* A set of now blocked but previously unblocked signals. */
		sigandnsets(&newblocked, newset, &current->blocked);
		retarget_shared_pending(tsk, &newblocked);
	}
	tsk->blocked = *newset;
	recalc_sigpending();
}
```

配套的 `set_current_blocked()` 注释也强调了这一点：

> "It is wrong to change ->blocked directly, this helper should be used to ensure the process can't miss a shared signal we are going to block."

**但要注意**：如果**所有线程都阻塞**了某信号，retarget 找不到目标，信号就会一直停留在 pending 里，直到某个线程解除阻塞。这是预期行为（阻塞的定义就是延迟递送）。

</details>

<details>
<summary><b>问 4：</b>什么是「解除阻塞 + 等待」竞态？怎么解决？</summary>

**竞态场景**：

```c
sigprocmask(SIG_UNBLOCK, &mask, NULL);   /* 解除阻塞 */
                                          /* ← 信号若在这个窗口到达并递送 */
pause();                                  /* 则 pause() 会永远沉睡 ❌ */
```

`sigprocmask` 返回后、进入 `pause()` 之前，如果信号已经递送完毕，那么 `pause()` 就等不到信号了——进程永久挂起。这是经典的竞态。

**三种解决方案**：

1. **`sigsuspend(&mask)`** —— 把「设置临时掩码 + 挂起等待 + 恢复原掩码」做成**单个原子系统调用**：
   ```c
   sigset_t orig; sigprocmask(SIG_BLOCK, &mask, &orig);  /* 先阻塞 */
   /* ... 临界区（信号堆积在 pending） ... */
   sigsuspend(&orig);   /* 原子地：临时恢复 orig → 等待 → 回到阻塞态 */
   ```

2. **`pselect` / `ppoll` / `epoll_pwait`** —— 这些接口带 `sigmask` 参数，在内核里用 `set_user_sigmask()`（`kernel/signal.c:3131`）原子地完成「改掩码 + 等待 + 恢复」。

3. **`sigwaitinfo()`** —— 完全不用 handler，同步地"取"信号（[Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md)），最干净。

HFT 事件循环里收停机信号，标准做法是 `epoll_pwait(epfd, events, max, timeout, &sigmask)`。

</details>

<details>
<summary><b>问 5：</b>内核线程可以阻塞 <code>SIGKILL</code>，用户进程不行——这是为什么？</summary>

内核源码注释直接说明了这个差异（`kernel/signal.c:3086-3093`）：

```c
/*
 * This is also useful for kernel threads that want to temporarily
 * (or permanently) block certain signals.
 *
 * NOTE! Unlike the user-mode sys_sigprocmask(), the kernel
 * interface happily blocks "unblockable" signals like SIGKILL
 * and friends.
 */
```

| | 用户态 `sys_rt_sigprocmask` | 内核态 `sigprocmask()` |
|--|---------------------------|----------------------|
| 阻塞 `SIGKILL` | ❌ 被 `sigdelsetmask` 剔除 | ✅ 可以 |

**原因**：

- **用户进程**的 `SIGKILL` 必须永远是有效的最后手段——管理员和 watchdog 要能保证能杀死任何失控进程。如果用户代码能屏蔽 `SIGKILL`，系统就失去了对恶意/失控程序的最终控制权。
- **内核线程**收到的 `SIGKILL` 通常是**内部管理事件**（如模块卸载、freezer 通知、kthread 停止请求），不是"处决"。内核线程本身也**不能**被用户 `kill -9` 杀死，所以屏蔽 `SIGKILL` 只是为了避免管理信号打断关键的内核路径，不涉及失控风险。

**实践推论**：用户态永远不要指望能屏蔽 `SIGKILL`；如果你的程序需要"不可被杀"，正确方向是成为内核线程，或者用其他机制（如双进程互相守护）。

</details>
