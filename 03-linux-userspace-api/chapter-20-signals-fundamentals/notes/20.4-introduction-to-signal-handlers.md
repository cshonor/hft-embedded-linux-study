# 20.4 信号处理器简介

> 源码核验：Linux v6.6 · `kernel/signal.c`（`get_signal:2660` · `signal_delivered:2915` · `signal_setup_done:2935`）
> 本章：[TLPI 第 20 章 — Signals: Fundamental Concepts](../README.md)

> - 下一节：[20.5 发送信号：kill()](20.5-sending-signals-kill.md)

## 本节讲什么

1. 信号处理器（handler）**什么时候被调用**、在什么上下文里执行——它到底是不是一个新线程
2. 内核为了执行 handler 做了**哪些幕后工作**（搭栈帧、自动阻塞、保存现场）
3. handler 执行期间**哪些信号被自动阻塞**，以及为什么必须遵守「异步信号安全」

---

## 一、handler 是一个普通函数，但不是你调用的

```c
void handler(int sig) { /* ... */ }
```

从 C 语言角度看，它就是个 `void(int)` 函数。区别在于**调用者**：

- 普通函数：被你的代码显式调用，调用点明确在控制流里
- handler：被**内核**在进程返回用户态前「安排」执行，调用点由信号递送时机决定，你的代码里看不到

这个区别带来 handler 的全部特殊性。

---

## 二、handler 不是新线程（最重要的澄清）

初学者的典型误解：「信号来了就开一个线程跑 handler」。**这是错的。**

handler 在**接收到信号的那个线程自己的用户栈上**执行，是同步的一段执行流：

```
   线程 A 的用户栈
   ┌──────────────────────┐
   │ main() 的栈帧         │
   ├──────────────────────┤
   │ 被中断处的栈帧        │  ← 被打断的执行流停在这里
   ├──────────────────────┤
   │ ✦ sigframe（内核搭）  │  ← 保存现场：寄存器、原信号掩码、返回地址
   ├──────────────────────┤
   │ handler() 的栈帧      │  ← handler 在这里跑
   └──────────────────────┘
```

**推论**：

| 推论 | 说明 |
|------|------|
| 仍然只有一个线程 | handler 跑的时候，被中断的执行流**是暂停的**，两者不并行 |
| 共享线程的全部状态 | handler 能直接读写线程的局部变量、全局变量、堆——这是**竞态的根源** |
| 用同一份栈 | 栈溢出后（如递归爆栈）信号递送会**没有栈可用**，这就是备用栈 `sigaltstack()` 存在的理由（[Ch21.3](../../chapter-21-signal-handlers/notes/21.3-handling-a-signal-on-an-alternate-stack-.md)） |
| 多线程下随机性 | 用 `kill` 给多线程进程发信号，**任意一个**未阻塞该信号的线程可能执行 handler，并非固定 |

> **多线程推论很重要**：不能假设 handler 总在「主线程」跑。生产上必须显式控制——主线程先屏蔽，再起专用线程用 `sigwaitinfo()` 消费（[Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md)）。

## 三、内核递送 handler 的完整流程

```
① 进程进入内核（syscall / 中断 / 异常）
        │
② 返回用户态前调用 get_signal()          kernel/signal.c:2660
   ├─ dequeue_signal() 取出一个未阻塞信号  kernel/signal.c:635
   └─ 按 disposition 分派
        │
③ signal_delivered()                     kernel/signal.c:2915
   ├─ 当前掩码 |= sa_mask
   ├─ 若无 SA_NODEFER：当前掩码 |= 本信号    ← 自动阻塞自身
   └─ 原掩码存入 sigframe，留给 sigreturn 恢复
        │
④ 搭建 sigframe（保存寄存器、原掩码、sigreturn 蹦床地址）
   ├─ 成功 → 修改用户态 RIP 指向 handler，返回用户态
   └─ 失败 → force_sigsegv()             kernel/signal.c:2938
        │
⑤ 用户态执行 handler
        │
⑥ handler 返回 → 跳到 sigreturn 蹦床（内核在 sigframe 里放的）
        │
⑦ 内核恢复原掩码与寄存器，回到被打断处继续执行
```

注意第 ④ 步的失败分支——`signal_setup_done()`：

```c
// kernel/signal.c:2935
void signal_setup_done(int failed, struct ksignal *ksig, int stepping)
{
	if (failed)
		force_sigsegv(ksig->sig);      // 栈帧搭不起来 → 强制 SIGSEGV
	else
		signal_delivered(ksig, stepping);
}
```

> 这解释了一个诡异现象：**备用栈（`sigaltstack`）设置得太小，进程会收到 `SIGSEGV` 而不是正常执行 handler**。因为内核在备用栈上搭建 sigframe 失败，转而强制发 `SIGSEGV`。

## 四、handler 执行期间，什么被自动阻塞？

内核在 `signal_delivered()` 里做的，注释写得很清楚：

```c
// kernel/signal.c:2905-2928
/**
 * signal_delivered - called after signal delivery to update blocked signals
 *
 * It updates the blocked signals accordingly (@ksig->ka.sa.sa_mask
 * is always blocked), and the signal itself is blocked unless %SA_NODEFER
 * is set in @ksig->ka.sa.sa_flags.
 */
static void signal_delivered(struct ksignal *ksig, int stepping)
{
	sigset_t blocked;
	...
	sigorsets(&blocked, &current->blocked, &ksig->ka.sa.sa_mask);   // ①
	if (!(ksig->ka.sa.sa_flags & SA_NODEFER))
		sigaddset(&blocked, ksig->sig);                             // ②
	set_current_blocked(&blocked);
	...
}
```

| 项 | 是否自动阻塞 | 条件 |
|----|--------------|------|
| `sa_mask` 里的信号 | **总是** | 无条件（注释里的 *is always blocked*） |
| **正在处理的这个信号本身** | **默认阻塞** | 除非设了 `SA_NODEFER` |
| 其他信号 | 不阻塞 | 仍可递送并**嵌套**进入别的 handler |

### 为什么默认阻塞自身信号？

防止**自我重入**。如果 handler 正在处理 `SIGINT`，此时又来一个 `SIGINT`，若不阻塞，handler 会被自己打断再嵌套一次——如果 handler 里改了全局数据结构，就会破坏一致性。

```
   不阻塞自身（SA_NODEFER）的危险：
   handler: 读全局 → [被同号信号打断] → handler: 读全局 → 改 → 返回 → 改 → 返回
                                                    ↑ 中间状态被覆盖，数据损坏
```

> **注意**：这里的「自动阻塞自身」是 **`sigaction()` 的行为**。回顾 [20.3](20.3-changing-signal-dispositions-signal.md)——裸 `sys_signal` 硬编码了 `SA_NOMASK`，含义正是**不**自动阻塞自身。所以老式 `signal()` 在这个维度上是危险的。

### handler 返回后掩码会恢复吗？

会。原掩码被保存在 sigframe 里，由 `sigreturn` 恢复：

```c
	/* A signal was successfully delivered, and the
	   saved sigmask was stored on the signal frame,
	   and will be restored by sigreturn.  So we can
	   simply clear the restore sigmask flag.  */        // kernel/signal.c:2919-2922
```

所以 handler 期间的阻塞是**临时的**，返回后自动还原，不需要你手动恢复。

## 五、异步信号安全（async-signal-safe）

因为 handler 可以在**任何时刻**打断主流程（只要那个时刻恰好能进内核），它面临一个致命问题：

> 如果主流程正执行到 `malloc()` 一半（持有堆锁）时信号递送，而 handler 里也调用 `malloc()`——**同一把锁被同一线程重入获取 → 死锁**。

**异步信号安全函数** = 可以安全地在 handler 里调用的函数。判据是：不持有锁、不用静态缓冲区、不依赖被中断代码的中间状态。

| 安全 ✅ | 不安全 ❌ |
|---------|-----------|
| `write()`、`read()` | `printf()`、`fprintf()`（stdio 锁） |
| `_exit()` | `exit()`（会 flush stdio、跑 atexit） |
| `kill()`、`raise()` | `malloc()`、`free()`（堆锁） |
| `sigprocmask()` | `strtok()`、`gmtime()`（静态缓冲） |
| 给 `volatile sig_atomic_t` 赋值 | 任何 `pthread_*` 函数 |

**最稳妥的写法**：handler 里只做一件事——设置一个标志，业务在主循环里检查。

```c
static volatile sig_atomic_t got_sigint = 0;
static void handler(int sig) { got_sigint = 1; }    /* 唯一安全的写法 */
```

完整清单与深入讨论见 [Ch21.5 异步信号安全](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | handler 用**被中断线程自己的栈**，栈很浅的嵌入式线程（默认 8KB 或更小）递送信号极易溢出；对 `SIGSEGV` 这类因栈溢出引发的信号，必须用 `sigaltstack()` 提供备用栈，否则 handler 根本无法执行。另注意 handler 期间自动阻塞自身，嵌入式高频同号信号会被合并丢失，别依赖信号计数 |
| HFT | 信号递送 = **异步抢占关键路径**，是延迟毛刺的经典来源。HFT 关键路径（报文解析、spinloop）应全程屏蔽无关信号；handler 若执行较久，会直接叠加到尾延迟上。更严重的是：handler 与主流程共享全部状态，任何非 `sig_atomic_t` 的共享访问都是数据竞争，[Ch21](../../chapter-21-signal-handlers/notes) 的 `volatile sig_atomic_t` 或 signalfd 才是正解 |

## 代码示例：观察 handler 的执行上下文与自动阻塞

```c
/* handlerctx.c —— 验证 handler 在同一线程执行 + 自动阻塞自身
 * 编译: gcc -o handlerctx handlerctx.c   运行后另开终端 kill -INT <pid> */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>
#include <pthread.h>

static volatile sig_atomic_t in_handler = 0;
static volatile sig_atomic_t reentered  = 0;

static void handler(int sig)
{
    in_handler = 1;

    /* 检查 handler 执行期间 SIGINT 是否已被自动阻塞 */
    sigset_t cur;
    sigemptyset(&cur);
    sigprocmask(SIG_BLOCK, NULL, &cur);
    printf("  [handler] 线程=%lu  SIGINT 已阻塞? %s\n",
           (unsigned long)pthread_self(),
           sigismember(&cur, SIGINT) ? "YES（内核自动加的）" : "NO");

    /* 在 handler 里再给自己发同号信号：因已阻塞，只会 pending 不会重入 */
    raise(SIGINT);
    if (in_handler == 1) reentered = 1;      /* 若重入，这里会先被嵌套执行 */

    printf("  [handler] raise 后仍在 handler 内，未重入\n");
    in_handler = 0;
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;                /* 未设 SA_NODEFER → 自动阻塞自身 */
    sigaction(SIGINT, &sa, NULL);

    printf("main 线程=%lu, PID=%d — 请执行: kill -INT %d\n",
           (unsigned long)pthread_self(), getpid(), getpid());
    pause();                                  /* 等待信号 */

    /* handler 返回后，掩码应已由 sigreturn 恢复 */
    sigset_t after;
    sigemptyset(&after);
    sigprocmask(SIG_BLOCK, NULL, &after);
    printf("main: handler 返回后 SIGINT 仍阻塞? %s（应 NO，sigreturn 已恢复）\n",
           sigismember(&after, SIGINT) ? "YES" : "NO");

    /* 刚才 raise 的那个 SIGINT 现在才递送 —— 证明它只是 pending */
    printf("main: pause() 返回，pending 的 SIGINT 现在被递送一次\n");
    return 0;
}
```

预期输出（handler 里的 `线程=` 与 main 相同，证明同一线程）：

```
main 线程=140...  PID=1234 — 请执行: kill -INT 1234
  [handler] 线程=140...  SIGINT 已阻塞? YES（内核自动加的）
  [handler] raise 后仍在 handler 内，未重入
main: handler 返回后 SIGINT 仍阻塞? NO（应 NO，sigreturn 已恢复）
main: pause() 返回，pending 的 SIGINT 现在被递送一次
```

## 自测题

<details>
<summary><b>问 1：</b>信号处理器是在新线程里执行的吗？为什么这个区别很重要？</summary>

**不是。** handler 在**接收到信号的那个线程自己的用户栈**上执行，是同步的一段执行流，不创建新线程。

重要性体现在：

1. **不并行**——handler 执行时，被中断的执行流是暂停的，两者不会同时跑。
2. **共享全部状态**——handler 能直接读写线程的局部变量、全局变量、堆，这是**数据竞争的根源**（所以共享变量必须声明为 `volatile sig_atomic_t`）。
3. **用同一份栈**——线程栈溢出后信号递送会没有栈可用，这就是 `sigaltstack()` 备用栈存在的原因。
4. **多线程下不确定**——用 `kill` 给多线程进程发信号，由**任意一个**未阻塞该信号的线程执行，不能假设总在主线程。

</details>

<details>
<summary><b>问 2：</b>handler 执行期间，哪些信号会被自动阻塞？依据是什么？</summary>

依据 `signal_delivered()`（`kernel/signal.c:2915`），内核注释明确写着：

```c
sigorsets(&blocked, &current->blocked, &ksig->ka.sa.sa_mask);   // ① sa_mask 总是
if (!(ksig->ka.sa.sa_flags & SA_NODEFER))
	sigaddset(&blocked, ksig->sig);                            // ② 自身，除非 SA_NODEFER
set_current_blocked(&blocked);
```

| 项 | 自动阻塞？ | 条件 |
|----|-----------|------|
| `sa_mask` 中的信号 | **总是** | 无条件 |
| 当前正在处理的信号本身 | **默认阻塞** | 除非设了 `SA_NODEFER` |
| 其他信号 | 不阻塞 | 可以递送并嵌套进别的 handler |

自动阻塞自身是**防止 handler 自我重入**：否则 handler 修改全局数据的中途又被同号信号打断，会破坏数据一致性。

</details>

<details>
<summary><b>问 3：</b>handler 返回后，被自动阻塞的信号会自动解除吗？需要手动恢复吗？</summary>

**不需要手动恢复**，内核会自动做。

原掩码被保存在 sigframe 中，handler 返回时先跳到内核在 sigframe 里放置的 `sigreturn` 蹦床，由内核恢复原掩码和全部寄存器，再回到被打断处。

内核注释（`kernel/signal.c:2919-2922`）写得很清楚：

```
/* A signal was successfully delivered, and the
   saved sigmask was stored on the signal frame,
   and will be restored by sigreturn.  So we can
   simply clear the restore sigmask flag.  */
```

所以 handler 期间的阻塞是**临时的、自动的**。这也是为什么 handler 里完全不需要（也不应该）调用 `sigprocmask()` 去改掩码。

</details>

<details>
<summary><b>问 4：</b>为什么不能在 handler 里调用 <code>printf</code>？什么情况下会真的出错？</summary>

`printf` **不是异步信号安全函数**——它内部操作 stdio 的全局缓冲区，并可能调用 `malloc`（两者都加锁）。

**真实的出错场景**：主流程正执行 `printf` 并持有 stdio 锁时信号递送，handler 又一次调用 `printf` 试图获取同一把锁。由于是**同一线程**重入（handler 不是新线程），锁不会自动让出 → **死锁**。即便侥幸不死锁，也可能破坏 stdio 缓冲区链表结构。

**正确做法**：

```c
static volatile sig_atomic_t flag = 0;
static void handler(int sig) { flag = 1; }              /* 只写标志，最安全 */

/* 或需要输出时用 write(2)，它是 async-signal-safe */
static void handler(int sig) {
    const char msg[] = "caught\n";
    write(STDOUT_FILENO, msg, sizeof(msg) - 1);
}
```

完整的异步信号安全函数清单见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)。

</details>

<details>
<summary><b>问 5：</b>备用栈（<code>sigaltstack</code>）设置得太小会发生什么？为什么？</summary>

进程会收到 **`SIGSEGV`**，而不是正常执行 handler。

原因在 `signal_setup_done()`（`kernel/signal.c:2935`）：

```c
void signal_setup_done(int failed, struct ksignal *ksig, int stepping)
{
	if (failed)
		force_sigsegv(ksig->sig);      // 栈帧搭建失败 → 强制 SIGSEGV
	else
		signal_delivered(ksig, stepping);
}
```

内核需要在栈上搭建 sigframe（保存寄存器、原信号掩码、`sigreturn` 蹦床地址）。如果备用栈空间不足，搭建失败，`failed` 为真，内核转而强制给自己发 `SIGSEGV`。

**实践意义**：备用栈必须足够大（通常 `MINSIGSTKSZ`~`SIGSTKSZ`，建议 ≥ 32KB），否则本想「优雅处理栈溢出」反而被自己的保护机制杀死。用 `SA_ONSTACK` + `sigaltstack()` 处理 `SIGSEGV` 是嵌入式系统的常见做法，这个坑必须避开。

</details>
