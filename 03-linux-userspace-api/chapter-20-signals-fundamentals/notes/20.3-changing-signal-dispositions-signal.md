# 20.3 改变信号处置：`signal()`

> 源码核验：Linux v6.6 · `kernel/signal.c` · `include/linux/signal.h`
> 本章：[TLPI 第 20 章 — Signals: Fundamental Concepts](../README.md)
> - 上一节：[20.2 信号类型与默认动作](20.2-signal-types-and-default-actions.md)
> - 下一节：[20.4 信号处理器简介](20.4-introduction-to-signal-handlers.md)

---

## 本节讲什么

1. 怎么把一个信号的默认动作**改成**忽略或自定义处理器——`signal()` 的三种取值
2. 内核里 `signal()` 到底是**怎么实现**的，为什么它是历史遗留接口
3. `signal()` 有**什么缺陷**，为什么生产代码必须改用 `sigaction()`

---

## 一、接口与三种取值

```c
#include <signal.h>

typedef void (*sighandler_t)(int);
sighandler_t signal(int sig, sighandler_t handler);
/* 返回：成功返回**旧**处置，失败返回 SIG_ERR */
```

`handler` 有三种取值：

| 取值 | 含义 |
|------|------|
| `SIG_DFL` | 恢复默认动作（[20.2](20.2-signal-types-and-default-actions.md) 的表） |
| `SIG_IGN` | 忽略该信号（内核直接丢弃，不进 pending） |
| 函数指针 | 递送时执行该函数 |

返回值是**旧处置**——这个设计让「临时替换再恢复」成为可能：

```c
sighandler_t old = signal(SIGINT, my_handler);
/* ... 做需要保护的事 ... */
signal(SIGINT, old);        /* 恢复原处置 */
```

> **注意**：`SIG_ERR` 是 `((sighandler_t) -1)`，不是 `NULL`。判断失败要写 `if (signal(...) == SIG_ERR)`。

---

## 二、内核实现：`signal()` 就是 `do_sigaction()` 的马甲

Linux 内核里 `sys_signal` 的实现只有 **13 行**，全部内容就是把参数转成 `sigaction` 再转交：

```c
// kernel/signal.c:4622 —— 注释已写明"For backwards compatibility"
SYSCALL_DEFINE2(signal, int, sig, __sighandler_t, handler)
{
	struct k_sigaction new_sa, old_sa;
	int ret;

	new_sa.sa.sa_handler = handler;
	new_sa.sa.sa_flags = SA_ONESHOT | SA_NOMASK;   // ← 硬编码，不可配置
	sigemptyset(&new_sa.sa.sa_mask);               // ← 掩码永远为空

	ret = do_sigaction(sig, &new_sa, &old_sa);

	return ret ? ret : (unsigned long)old_sa.sa.sa_handler;
}
```

那两个硬编码的 flag 就是 `signal()` 全部问题的根源：

| flag | 语义 | 后果 |
|------|------|------|
| `SA_ONESHOT` | 触发一次后自动复位为 `SIG_DFL` | **System V 语义**：想持续捕获必须在 handler 里重新 `signal()` 自己 |
| `SA_NOMASK` | handler 执行期间**不**自动阻塞同号信号 | 同号信号可以在 handler 还没跑完时重入（早期 BSD 语义） |

而另一派 Unix（BSD 4.3+）的 `signal()` 恰好相反：**不**自动复位、且**自动**阻塞同号信号。这就是 `signal()` 不可移植的由来——两派语义截然相反。

> **glibc 的实际情况**：现代 glibc 的 `signal()` **并不调用 `sys_signal`**，而是走 `rt_sigaction()` 并加上 `SA_RESTART`（模拟 BSD 语义）。所以在 Linux/glibc 上 `signal()` 表现为「不自动复位 + 自动重启被中断的 syscall」。
>
> 但这是 **glibc 的选择**，不是内核的保证。跨 libc（musl）、跨 Unix（BSD/Solaris/AIX）就会分叉。如果你直接 `syscall(SYS_signal, ...)` 绕过 glibc，拿到的就是上面那段 `SA_ONESHOT|SA_NOMASK` 的古怪行为。

## 三、`do_sigaction()`：真正的校验链

无论 `signal()` 还是 `sigaction()`，最终都落到 `do_sigaction()`。`kernel/signal.c:4123`：

```c
int do_sigaction(int sig, struct k_sigaction *act, struct k_sigaction *oact)
{
	struct task_struct *p = current, *t;
	struct k_sigaction *k;
	sigset_t mask;

	if (!valid_signal(sig) || sig < 1 || (act && sig_kernel_only(sig)))
		return -EINVAL;                              // ①

	k = &p->sighand->action[sig-1];                  // ②

	spin_lock_irq(&p->sighand->siglock);
	if (k->sa.sa_flags & SA_IMMUTABLE) {             // ③
		spin_unlock_irq(&p->sighand->siglock);
		return -EINVAL;
	}
	if (oact)
		*oact = *k;
	...
	if (act)
		act->sa.sa_flags &= UAPI_SA_FLAGS;           // ④

	if (act) {
		sigdelsetmask(&act->sa.sa_mask,
			      sigmask(SIGKILL) | sigmask(SIGSTOP));   // ⑤
		*k = *act;
		/*
		 * POSIX 3.3.1.3:
		 *  "Setting a signal action to SIG_IGN for a signal that is
		 *   pending shall cause the pending signal to be discarded"
		 */
		if (sig_handler_ignored(sig_handler(p, sig), sig)) {   // ⑥
			sigemptyset(&mask);
			sigaddset(&mask, sig);
			flush_sigqueue_mask(&mask, &p->signal->shared_pending);
			for_each_thread(p, t)
				flush_sigqueue_mask(&mask, &t->pending);
		}
	}
	spin_unlock_irq(&p->sighand->siglock);
	return 0;
}
```

### 六道校验逐个拆解

| # | 行号 | 检查 | 违反后果 |
|---|------|------|----------|
| ① | `:4129` | 信号编号合法 + **`sig_kernel_only(sig)` 拒绝** | 对 `SIGKILL`/`SIGSTOP` 设处置 → `-EINVAL` |
| ② | `:4132` | 取出 `p->sighand->action[sig-1]` | 见下方「处置共享 vs 掩码私有」 |
| ③ | `:4135` | **未被 `SA_IMMUTABLE` 锁定** | 内核内部信号（如 seccomp 的）不可改 → `-EINVAL` |
| ④ | `:4154` | 未知 flag 位被**清除**（`& UAPI_SA_FLAGS`） | 传了内核不认识的 flag 不会报错，会被悄悄抹掉 |
| ⑤ | `:4161` | `sa_mask` 里的 `SIGKILL`/`SIGSTOP` 被**强制剔除** | 想"handler 执行期间屏蔽 SIGKILL"是不可能的 |
| ⑥ | `:4175` | 新处置若等于「忽略」→ **冲刷**所有 pending | 符合 POSIX 3.3.1.3 |

> **④ 的实际影响**：如果你写了 `sa.sa_flags = SA_RESTART | 0x80000000;` 传给内核，那个 `0x80000000` 会被静默清除且不报错。**降级的正确做法**是：设置完后再 `sigaction(sig, NULL, &old)` 读回实际的 flags，比对是否还在。

### 处置是进程共享的，掩码是线程私有的（高频考点）

`do_sigaction` 的这一行藏着一个关键事实：

```c
k = &p->sighand->action[sig-1];     // kernel/signal.c:4132
```

处置存在 `sighand->action[]`，而 `sighand` 是**整个线程组共享**的结构体。对比：

| 属性 | 存在哪 | 作用域 | 设置接口 |
|------|--------|--------|----------|
| **处置**（handler） | `sighand->action[sig-1]` | **进程/线程组共享** | `sigaction()` / `signal()` |
| **掩码**（阻塞位） | `task_struct.blocked` | **线程私有** | `sigprocmask()` / `pthread_sigmask()` |
| **pending** | 两层：线程私有 + 进程共享 | 见 [20.11](20.11-pending-signals.md) | — |

**推论**：`sigaction()` 在哪个线程调用都一样，一次设置全进程生效；但 `sigprocmask()` 只影响调用它的那个线程。多线程程序要统一屏蔽，必须**每个线程都调用**一次（或在创建线程前在主线程设好，让新线程继承掩码）。

## 四、`signal()` 的缺陷清单

综合以上，这就是 TLPI 反复强调「用 `sigaction()` 而不是 `signal()`」的原因：

| 缺陷 | 说明 |
|------|------|
| **语义不统一** | 是否自动复位（SVr4 vs BSD）、handler 期间是否阻塞同号信号，各系统不同 |
| **无法控制 `SA_RESTART`** | 不能表达「被信号打断的 `read()` 要自动重启」——这是慢系统调用最常见的需求 |
| **无法设置 `sa_mask`** | 内核硬编码 `sigemptyset()`，不能指定"执行 handler 时额外屏蔽哪些信号" |
| **无法取 `siginfo`** | 拿不到发送者 PID、附加数据（`SA_SIGINFO` 见 [Ch21.3](../../chapter-21-signal-handlers/notes/21.3-handling-a-signal-on-an-alternate-stack-.md)） |
| **无法指定备用栈** | 栈溢出（`SIGSEGV`）处理需要 `SA_ONSTACK`（[Ch21.3](../../chapter-21-signal-handlers/notes/21.3-handling-a-signal-on-an-alternate-stack-.md)） |

✅ **结论**：`signal()` 只适合写 demo 和一键 `SIG_IGN`；任何生产代码都用 `sigaction()`，见 [20.13](20.13-changing-signal-dispositions-sigaction.md)。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | `signal()` 是否自动复位、handler 期间是否阻塞自身，随 libc/架构而变，嵌入式交叉编译（尤其是非 glibc 的 uClibc/musl 工具链）移植时极易踩坑；统一 `sigaction()` 显式声明所有 flag，行为才可预测 |
| HFT | 行为不确定 = 竞态不可复现，排查成本极高。HFT 生产代码统一用 `sigaction()` + `SA_RESTART` 显式控制，保证 handler 语义确定、延迟可预测。另注意**处置是线程组共享的**：任何线程 `sigaction()` 都会改全进程，热路径里误调会污染所有工作线程 |

## 代码示例

### 一、`ouch.c`（Listing 20-1）

`ouch.c` 是全书最小的信号捕获程序：用 `signal()` 把 `SIGINT` 的处置换成自定义 handler，主循环每次打印自增计数后 `sleep(3)`。它对应本节「`signal()` 的三种取值」里的**函数指针**那一种，也是后面 `sigaction()` 篇章反复拿来做对照的基准程序。

完整源码（[`code/ouch.c`](../code/ouch.c)）：

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* Listing 20-1 */

/* ouch.c

   Catch the SIGINT signal, generated by typing control-C (^C).

   Note that although we use signal() to establish the signal handler in this
   program, the use of sigaction() is always preferable for this task.
*/
#include <signal.h>
#include "tlpi_hdr.h"

static void
sigHandler(int sig)
{
    printf("Ouch!\n");                  /* UNSAFE (see Section 21.1.2) */
}

int
main(int argc, char *argv[])
{
    int j;

    /* Establish handler for SIGINT. Here we use the simpler signal()
       API to establish a signal handler, but for the reasons described in
       Section 22.7 of TLPI, sigaction() is the (strongly) preferred API
       for this task. */

    if (signal(SIGINT, sigHandler) == SIG_ERR)
        errExit("signal");

    /* Loop continuously waiting for signals to be delivered */

    for (j = 0; ; j++) {
        printf("%d\n", j);
        sleep(3);                       /* Loop slowly... */
    }
}
```

编译（macOS 26.6.2 / arm64 · clang 23.1.0）：

```bash
$CC $D -Wall -Wextra -o ouch       ouch.c            get_num.c signal_functions.c
```

实测输出（`t_kill` 连发两次 `SIGINT`，最后 `kill -TERM`）：

```text
$ t_kill <ouch的pid> 2 ; t_kill <pid> 2 ; kill -TERM <pid>
Ouch!
1
Ouch!
2
[exit=143]          ← SIGTERM 终止（默认动作），handler 对 TERM 无感
```

**逐条解读**：

| 输出行 | 含义 |
|--------|------|
| `Ouch!` | `sigHandler()` 被内核在返回用户态前调起，`printf` 是**非异步信号安全**函数（源码注释里的 `UNSAFE` 就是提醒这一点），此处只作演示 |
| `1` / `2` | 主循环里 `printf("%d\n", j)` 的计数。注意 `sleep(3)` 被打断后**不会**自动继续睡完 3 秒——`sleep()` 返回剩余秒数，循环直接进入下一轮，所以两次 `Ouch!` 之间只隔了一次 `t_kill` 往返 |
| `[exit=143]` | 143 = 128 + 15（`SIGTERM`），进程被默认动作 terminate。`ouch` 只装了 `SIGINT` 的 handler，对 `SIGTERM` **无感**——这正是「处置是逐信号独立设置」的直接证据 |

**踩坑点**：`signal()` 返回的旧处置必须与 `SIG_ERR` 比较（`(sighandler_t)-1`），不能写 `if (signal(...) == NULL)`——本节正文已强调过这一点。

**源码坐标**：原书 **Listing 20-1**；接口见 `man 2 signal`、`man 7 signal`（默认动作表）；内核侧 `sys_signal` 硬编码 `SA_ONESHOT | SA_NOMASK` 见 `kernel/signal.c:4622`。

### 二、教学补充片段（非 `code/`，未实测）

```c
/* dispose.c —— signal() 设置三种处置，并用 sigaction 等价改写
 * 编译: gcc -o dispose dispose.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>
#include <errno.h>

static volatile sig_atomic_t got = 0;
static void handler(int sig) { got = sig; }

int main(void)
{
    /* ── 1. signal() 设置捕获 ── */
    if (signal(SIGUSR1, handler) == SIG_ERR) {
        perror("signal SIGUSR1");
        return 1;
    }
    raise(SIGUSR1);
    printf("1) caught SIGUSR1: %s\n", got == SIGUSR1 ? "yes" : "no");

    /* ── 2. signal() 设置忽略 ── */
    got = 0;
    signal(SIGUSR2, SIG_IGN);
    raise(SIGUSR2);
    printf("2) SIG_IGN -> handler called? %s (未决也被冲刷，见 :4175)\n",
           got ? "yes" : "no");

    /* ── 3. 恢复默认 ── */
    signal(SIGUSR1, SIG_DFL);

    /* ── 4. 试图改 SIGKILL 的处置：内核拒绝 ── */
    errno = 0;
    if (signal(SIGKILL, SIG_IGN) == SIG_ERR)
        printf("4) signal(SIGKILL) -> SIG_ERR, errno=%d (%s)\n",
               errno, errno == EINVAL ? "EINVAL 符合 do_sigaction:4129" : "?");

    /* ── 5. 用 sigaction 等价改写第 1 步（生产写法）── */
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;            /* signal() 表达不出来 */
    got = 0;
    if (sigaction(SIGUSR1, &sa, NULL) == -1) {
        perror("sigaction");
        return 1;
    }
    raise(SIGUSR1);
    printf("5) sigaction(SA_RESTART) caught: %s\n", got == SIGUSR1 ? "yes" : "no");

    /* ── 6. 验证 sa_mask 里的 SIGKILL 被内核剔除 ── */
    struct sigaction sa2 = {0}, verify;
    sa2.sa_handler = handler;
    sigemptyset(&sa2.sa_mask);
    sigaddset(&sa2.sa_mask, SIGKILL);    /* 试图在 handler 期间屏蔽 SIGKILL */
    sigaction(SIGTERM, &sa2, NULL);
    sigaction(SIGTERM, NULL, &verify);   /* 读回内核实际保存的值 */
    printf("6) 内核实际 sa_mask 含 SIGKILL? %s (被剔除，见 :4161)\n",
           sigismember(&verify.sa_mask, SIGKILL) ? "yes" : "no");
    return 0;
}
```

> 第 6 步必须**读回**内核实际保存的值才能验证——这正是 `do_sigaction` ④ 的意义：内核会静默清除不合法的位而不报错，所以想确认 flag 是否生效，唯一可靠办法是 `sigaction(sig, NULL, &old)` 读回比对。

## 自测题

<details>
<summary><b>问 1：</b>Linux 内核里 <code>sys_signal</code> 硬编码了哪两个 flag？它们分别代表什么语义？</summary>

`kernel/signal.c:4628`：

```c
new_sa.sa.sa_flags = SA_ONESHOT | SA_NOMASK;
```

- **`SA_ONESHOT`**：handler 触发一次后自动复位为 `SIG_DFL`。这是 **System V** 语义——想持续捕获，必须在 handler 内部重新调用 `signal()` 注册自己。
- **`SA_NOMASK`**：handler 执行期间**不**自动阻塞同号信号。所以同号信号可能在 handler 还没返回时再次递送、重入执行。

而 BSD 4.3+ 的 `signal()` 语义恰好相反（不自动复位 + 自动阻塞同号）。两派行为相反，这就是 `signal()` 不可移植的根本原因。

</details>

<details>
<summary><b>问 2：</b>在现代 Linux/glibc 上，<code>signal()</code> 表现为「不自动复位」，但内核代码明明写了 <code>SA_ONESHOT</code>。为什么？</summary>

因为 **glibc 的 `signal()` 包装函数根本不走 `sys_signal` 系统调用**，而是调用 `rt_sigaction()`，并主动加上 `SA_RESTART`，模拟 BSD 语义。

`sys_signal`（`kernel/signal.c:4622`）只在 `__ARCH_WANT_SYS_SIGNAL` 开启时编译，存在的意义纯粹是**向后兼容**——给那些直接发起 `sys_signal` 系统调用的老程序（或绕过 libc 的代码）用。

所以：

| 调用路径 | 实际语义 |
|----------|----------|
| `signal()`（glibc 包装） | 走 `rt_sigaction` + `SA_RESTART`，不自动复位，syscall 自动重启 |
| `syscall(SYS_signal, ...)`（直连内核） | 走 `sys_signal`，`SA_ONESHOT|SA_NOMASK`，古旧语义 |

**但 glibc 的行为只是 glibc 的选择**，换 musl 或其他 Unix 就会分叉——这正是「`signal()` 不可移植」的实证。

</details>

<details>
<summary><b>问 3：</b>尝试 <code>signal(SIGKILL, SIG_IGN)</code> 会发生什么？内核在哪一层拦住它？</summary>

返回 `SIG_ERR`，`errno = EINVAL`。

拦截点在 `do_sigaction()` 的第一道校验：

```c
// kernel/signal.c:4129
if (!valid_signal(sig) || sig < 1 || (act && sig_kernel_only(sig)))
    return -EINVAL;
```

`sig_kernel_only(sig)` 就是 `siginmask(sig, SIG_KERNEL_ONLY_MASK)`，而 `SIG_KERNEL_ONLY_MASK` 只包含 `SIGKILL` 和 `SIGSTOP`（`include/linux/signal.h:418`）。

第二重保险在 `:4161`：即便通过其他路径设置了 `sa_mask`，内核也会 `sigdelsetmask(&act->sa.sa_mask, sigmask(SIGKILL)|sigmask(SIGSTOP))`，把这两个信号从掩码里剔除。

</details>

<details>
<summary><b>问 4：</b>「信号处置」和「信号掩码」的作用域有什么区别？多线程程序要注意什么？</summary>

| 属性 | 内核存放位置 | 作用域 | 设置接口 |
|------|--------------|--------|----------|
| **处置**（handler / SIG_DFL / SIG_IGN） | `sighand->action[sig-1]`（`do_sigaction` `:4132`） | **进程/线程组共享** | `sigaction()` / `signal()` |
| **掩码**（阻塞位） | `task_struct.blocked` | **线程私有** | `sigprocmask()` / `pthread_sigmask()` |

`struct sighand_struct` 由整个线程组共享，所以**任何线程调用 `sigaction()` 都会对全进程生效**。

而掩码是 `task_struct` 的字段，每个线程一份，`sigprocmask()` 只改调用者自己。

**多线程要注意的**：
1. 不能在某个工作线程里随意 `sigaction()` 改处置——会污染所有线程。正确做法是在**创建线程之前**于主线程统一设好。
2. 要统一屏蔽信号，**不能只在主线程调 `sigprocmask()` 就完事**——新线程会继承创建时的掩码，但已存在的线程不受影响。稳妥做法是主线程先屏蔽，再 `pthread_create`，让所有新线程继承；或用 `pthread_sigmask()` 逐个设置。
3. 更优雅的方案：主线程屏蔽所有关心的信号，然后起一个专用线程 `sigwaitinfo()` 同步消费（[Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md)）。

</details>

<details>
<summary><b>问 5：</b>把某个信号的处置改成 <code>SIG_IGN</code> 时，已经 pending 的同号信号会怎样？依据是什么？</summary>

会**被全部丢弃**，包括进程级 `shared_pending` 和每个线程的私有 `pending`。

依据在 `do_sigaction` 的第六步：

```c
// kernel/signal.c:4175-4181
if (sig_handler_ignored(sig_handler(p, sig), sig)) {
    sigemptyset(&mask);
    sigaddset(&mask, sig);
    flush_sigqueue_mask(&mask, &p->signal->shared_pending);
    for_each_thread(p, t)
        flush_sigqueue_mask(&mask, &t->pending);
}
```

代码注释直接引用了 **POSIX 3.3.1.3**：

> "Setting a signal action to SIG_IGN for a signal that is pending shall cause the pending signal to be discarded, whether or not it is blocked."

同一段还规定了 `SIG_DFL` 的情况：若设为 `SIG_DFL` 且**该信号的默认动作本身就是忽略**（如 `SIGCHLD`、`SIGURG`、`SIGWINCH`、`SIGCONT`），pending 也会被丢弃。

**实践意义**：这也解释了为什么 `signal(SIGCHLD, SIG_IGN)` 能自动回收僵尸进程——不只是丢弃通知，内核在子进程退出时直接不产生僵尸。

</details>
