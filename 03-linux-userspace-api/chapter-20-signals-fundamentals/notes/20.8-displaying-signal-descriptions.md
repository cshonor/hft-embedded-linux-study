## 本节讲什么

1. 怎么把信号**编号翻译成人类可读的字符串**——三个库函数的区别
2. `strsignal()` 的**可重入性**隐患到底是什么（常被误称为"线程安全"）
3. 为什么这些函数**都不能在信号 handler 里用**

---

## 一、三个函数

```c
#include <string.h>
char *strsignal(int sig);                        /* 返回描述字符串指针 */

#include <signal.h>
void psignal(int sig, const char *s);            /* 向 stderr 打印 "s: description" */

#define _GNU_SOURCE
#include <signal.h>
const char *sigdescr_np(int sig);                /* GNU 扩展，可重入版本 */
```

| 函数 | 头文件 | 返回/行为 | 可重入 |
|------|--------|-----------|--------|
| `strsignal(sig)` | `<string.h>` | 返回描述字符串指针（**不可重入**） | ❌ |
| `psignal(sig, prefix)` | `<signal.h>` | 向 **stderr** 打印 `prefix: description` | ❌ |
| `sigdescr_np(sig)` | `<signal.h>`（需 `_GNU_SOURCE`） | 返回**静态常量**字符串，可重入 | ✅ |

### `psignal` vs `perror`

`psignal` 的信号版本等价于 `perror` 的 errno 版本：

| | 用于 | 输出格式 |
|--|------|----------|
| `perror("msg")` | errno | `msg: <errno 描述>` |
| `psignal(sig, "msg")` | 信号 | `msg: <信号描述>` |

两者都写到 **stderr**，都是诊断工具的标准写法。

---

## 二、可重入性：真正的隐患是什么

**常见误解**：「`strsignal` 非线程安全，多线程里不能用」。

**准确说法**：POSIX 规定 `strsignal()` 的返回缓冲区**可能被后续调用覆盖**——这是**可重入性（reentrancy）**问题，不只是线程安全问题。

| 场景 | 是否危险 | 原因 |
|------|----------|------|
| 单线程顺序调用 | ✅ 安全 | 没有并发 |
| **多线程**同时调用 | ⚠️ 取决于实现 | 若共用静态缓冲区会互相覆盖 |
| **信号 handler** 里调用 | ❌ **危险** | 主流程可能正调用 `strsignal`，handler 重入覆盖同一缓冲区 |

> **glibc 的现代行为**：从 glibc 2.32 起，`strsignal()` 在 **已知信号**上返回静态常量字符串（不再使用静态缓冲区），此时是可重入的；但对**未知信号**仍需要拼装字符串（如 "Unknown signal 42"），会使用内部缓冲区。
>
> 然而 **POSIX 并不保证**这一点——换 libc（musl、uClibc）行为可能不同。所以可移植代码不应依赖。

**可移植的推荐做法**：用 GNU 扩展 `sigdescr_np()`（glibc 2.32+），它明确保证返回静态常量、可重入：

```c
#define _GNU_SOURCE
#include <signal.h>

const char *d = sigdescr_np(sig);
if (d) printf("%d = %s\n", sig, d);
else   printf("%d = <unknown>\n", sig);      /* 越界时返回 NULL */
```

## 三、关键限制：都不能在 handler 里用

> **这是本节最重要的实践要点**：`strsignal()`、`psignal()`、`sigdescr_np()` **都不是异步信号安全函数**，都不能在信号 handler 里调用。

原因：

- `strsignal()` —— 可能使用静态缓冲区（可重入性问题）
- `psignal()` —— 内部调用 stdio 的 `fprintf(stderr, ...)`，涉及 stdio 锁（同 `printf` 的死锁问题）
- `sigdescr_np()` —— 虽可重入，但不在 POSIX 的异步信号安全函数清单里

**handler 里的正确做法**：自己维护一张信号编号 → 描述的**静态表**，或用 `write(2)` 输出编号：

```c
/* 方案 A：只写编号，让调用方去翻译（推荐） */
static void handler(int sig)
{
    const char m[] = "caught signal\n";
    write(STDERR_FILENO, m, sizeof m - 1);
    /* sig 的值通过 volatile sig_atomic_t 传给主流程 */
}

static volatile sig_atomic_t last_sig = 0;
static void handler2(int sig) { last_sig = sig; }

/* 主流程里再翻译 */
if (last_sig) fprintf(stderr, "收到信号 %d: %s\n", last_sig, strsignal(last_sig));
```

```c
/* 方案 B：handler 里查自建静态表（无锁、无静态缓冲） */
static const char *const sig_names[] = {
    [SIGHUP] = "SIGHUP", [SIGINT] = "SIGINT", [SIGQUIT] = "SIGQUIT",
    [SIGKILL] = "SIGKILL", [SIGSEGV] = "SIGSEGV", [SIGTERM] = "SIGTERM",
};
static void handler3(int sig)
{
    const char *name = (sig < 32 && sig_names[sig]) ? sig_names[sig] : "?";
    write(STDERR_FILENO, "caught: ", 8);
    write(STDERR_FILENO, name, strlen(name));   /* strlen 是 async-signal-safe */
    write(STDERR_FILENO, "\n", 1);
}
```

异步信号安全函数完整讨论见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)。

## 四、常见信号描述速查

| 信号 | 编号 | `strsignal` 返回 | 默认动作 |
|------|------|------------------|----------|
| `SIGHUP` | 1 | Hangup | term |
| `SIGINT` | 2 | Interrupt | term |
| `SIGQUIT` | 3 | Quit | **core** |
| `SIGILL` | 4 | Illegal instruction | **core** |
| `SIGABRT` | 6 | Aborted | **core** |
| `SIGFPE` | 8 | Floating point exception | **core** |
| `SIGKILL` | 9 | Killed | term（不可干预） |
| `SIGSEGV` | 11 | Segmentation fault | **core** |
| `SIGPIPE` | 13 | Broken pipe | term |
| `SIGALRM` | 14 | Alarm clock | term |
| `SIGTERM` | 15 | Terminated | term |
| `SIGCHLD` | 17 | Child exited | ignore |
| `SIGSTOP` | 19 | Stopped (signal) | stop（不可干预） |
| `SIGCONT` | 18 | Continued | cont |

> **调试技巧**：shell 里 `kill -l` 可列出全部信号名与编号对应关系；`kill -l 11` 反查编号 11 对应 `SIGSEGV`。

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | `psignal` 是最小的诊断手段——无 logger、无 syslog 时直接写 stderr 就能给出可读信息。但注意它**不是异步信号安全**的：handler 里要用它必须先保存信号编号，回到主流程再翻译输出 |
| HFT | 信号处理中用 `psignal` 做最小化日志——但**必须在主流程中调用**，handler 里只记录编号。HFT 的日志本身有延迟成本，生产环境通常把信号编号写进无锁环形队列，由专用日志线程异步落盘，避免信号处理路径上的任何 I/O |

## 代码示例

```c
/* sigdescr.c —— strsignal / psignal / sigdescr_np 对比
 * 编译: gcc -D_GNU_SOURCE -o sigdescr sigdescr.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    /* ① strsignal：返回描述指针 */
    printf("strsignal(SIGINT)  = %s\n", strsignal(SIGINT));
    printf("strsignal(SIGSEGV) = %s\n", strsignal(SIGSEGV));

    /* ② psignal：直接写 stderr，等价于 perror 的信号版 */
    psignal(SIGTERM, "got signal");
    psignal(SIGKILL, "force kill");

    /* ③ sigdescr_np：GNU 扩展，可重入、越界返回 NULL */
#ifdef SIGDESCR_AVAILABLE
    printf("\nsigdescr_np(SIGINT)  = %s\n", sigdescr_np(SIGINT));
    printf("sigdescr_np(999)     = %s\n",
           sigdescr_np(999) ? sigdescr_np(999) : "(NULL) 越界");
#endif

    /* ④ 遍历常见信号 */
    const int sigs[] = {
        SIGHUP, SIGINT, SIGQUIT, SIGILL, SIGABRT, SIGFPE, SIGKILL,
        SIGSEGV, SIGPIPE, SIGALRM, SIGTERM, SIGCHLD, SIGSTOP, SIGCONT
    };
    printf("\n编号  信号描述\n");
    for (size_t i = 0; i < sizeof sigs / sizeof *sigs; i++)
        printf("  %2d   %s\n", sigs[i], strsignal(sigs[i]));

    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b><code>strsignal()</code> 的隐患到底是「线程安全」还是别的？</summary>

准确说是**可重入性（reentrancy）**问题，不只是线程安全。

POSIX 规定：`strsignal()` 返回的缓冲区**可能被后续调用覆盖**。这意味着两类风险：

| 场景 | 风险 |
|------|------|
| **多线程**并发调用 | 若共用静态缓冲区，一个线程的结果被另一个覆盖 |
| **信号 handler** 重入 | 主流程正调用 `strsignal` 时信号递送，handler 再调用会**覆盖同一缓冲区** |

第二种更隐蔽——因为它是**同一线程**的重入（handler 不是新线程，见 [20.4](./20.4-introduction-to-signal-handlers.md)），加锁也解决不了。

**glibc 现状**：2.32 起对**已知信号**返回静态常量（可重入），但**未知信号**仍需拼装字符串、使用内部缓冲区。且 POSIX **不保证**这一点，换 libc 可能不同。

**可移植方案**：用 GNU 扩展 `sigdescr_np()`（明确保证返回静态常量、可重入、越界返回 `NULL`）。

</details>

<details>
<summary><b>问 2：</b>能在信号处理函数里调用 <code>psignal()</code> 或 <code>strsignal()</code> 吗？</summary>

**都不能**——它们都不是异步信号安全函数。

| 函数 | 为什么不安全 |
|------|-------------|
| `strsignal()` | 可能使用静态缓冲区，handler 重入会覆盖主流程的结果 |
| `psignal()` | 内部调用 `fprintf(stderr, ...)`，涉及 **stdio 锁**——主流程正持锁时 handler 重入会死锁（同 `printf` 的经典问题） |
| `sigdescr_np()` | 虽可重入，但**不在** POSIX 异步信号安全函数清单里，不应在 handler 中使用 |

**正确做法**：handler 里只记录**信号编号**（写 `volatile sig_atomic_t`），回到主流程再翻译输出：

```c
static volatile sig_atomic_t last_sig = 0;
static void handler(int sig) { last_sig = sig; }     /* 只写编号，安全 */

/* 主流程 */
if (last_sig) {
    fprintf(stderr, "收到信号 %d: %s\n", last_sig, strsignal(last_sig));
    last_sig = 0;
}
```

如果确实需要在 handler 里输出可读名称，用自建的**静态字符串表** + `write(2)`（async-signal-safe）：

```c
static const char *const names[] = { [SIGINT] = "SIGINT", [SIGTERM] = "SIGTERM" };
static void handler(int sig) {
    const char *n = (sig < 32 && names[sig]) ? names[sig] : "?";
    write(STDERR_FILENO, "caught: ", 8);
    write(STDERR_FILENO, n, strlen(n));
    write(STDERR_FILENO, "\n", 1);
}
```

</details>

<details>
<summary><b>问 3：</b><code>psignal()</code> 和 <code>perror()</code> 有什么关系？</summary>

两者是**同一模式的两个版本**，都向 **stderr** 输出「前缀 + 描述」：

| | 翻译什么 | 输出格式 |
|--|----------|----------|
| `perror("msg")` | `errno` | `msg: <errno 描述>` |
| `psignal(sig, "msg")` | 信号编号 | `msg: <信号描述>` |

```c
perror("open failed");              /* open failed: No such file or directory */
psignal(SIGSEGV, "crashed");        /* crashed: Segmentation fault */
```

**两者都不是异步信号安全的**（都走 stdio），都不能在 handler 里调用。

**实践**：在诊断代码里，如果进程因信号终止，用 `psignal`；如果是系统调用失败，用 `perror`；如果需要同时看两者，先存下编号和 errno，回到主流程再输出。

</details>

<details>
<summary><b>问 4：</b><code>sigdescr_np()</code> 相比 <code>strsignal()</code> 有什么优势？有什么限制？</summary>

| | `strsignal()` | `sigdescr_np()` |
|--|---------------|-----------------|
| 标准 | POSIX | **GNU 扩展**（需 `#define _GNU_SOURCE`） |
| 可重入 | ❌ POSIX 不保证 | ✅ 明确保证（返回静态常量） |
| 越界行为 | 返回拼装的字符串（如 "Unknown signal 42"） | 返回 **`NULL`** |
| 返回值类型 | `char *` | `const char *` |
| 可用版本 | 所有 | glibc **2.32+** |

**优势**：可重入性由文档明确保证，多线程和重入场景都可以放心用。

**限制（三点）**：

1. **可移植性**——是 GNU 扩展，非 POSIX，musl/BSD 上没有（musl 在较新版本也提供了，但不能依赖）。
2. **版本要求**——glibc 2.32（2021 年）之前没有，老发行版（CentOS 7 等）用不了。
3. **越界返回 NULL**——调用方必须判空，不能直接传给 `printf("%s")`：

```c
const char *d = sigdescr_np(sig);
printf("%d = %s\n", sig, d ? d : "<unknown>");    /* 必须判空 */
```

**实践建议**：写跨平台库时用 `strsignal()`（配 `#ifdef` 做 glibc 版本检测优先用 `sigdescr_np`）；写 Linux 专用代码且 glibc 够新时，直接用 `sigdescr_np()` 更省心。

</details>

<details>
<summary><b>问 5：</b>信号编号 0 有对应的描述吗？<code>strsignal(0)</code> 会返回什么？</summary>

**信号 0 不存在**——它是 `kill(pid, 0)` 里约定的「空信号」，只用于存在性与权限探测，**永远不会被递送**。

`strsignal(0)` 通常返回类似 `"Unknown signal 0"` 或 `"Signal 0"` 的字符串（glibc 行为），属于未定义范畴，不同 libc 可能不同。

**为什么不存在 0 号信号**（回顾 [20.9](./20.9-signal-sets.md)）：

内核的位图实现做了编号到下标的一减换算：

```c
// include/linux/signal.h:64
static inline void sigaddset(sigset_t *set, int _sig)
{
	unsigned long sig = _sig - 1;             // ← 编号 → 下标
	...
	set->sig[sig / _NSIG_BPW] |= 1UL << (sig % _NSIG_BPW);
}
```

若 `_sig == 0`，则 `sig = -1`（下溢为极大的无符号数），`1UL << sig` 是未定义行为。所以信号编号从 1 开始，0 被预留为「空信号」语义。

**实践**：`kill(pid, 0)` 是合法且常用的探测手法，但不要把 `0` 当成"某种信号"，也不要对它设置处置——`sigaction(0, ...)` 会因 `sig < 1` 返回 `-EINVAL`（`do_sigaction`，`kernel/signal.c:4129`）。

</details>
