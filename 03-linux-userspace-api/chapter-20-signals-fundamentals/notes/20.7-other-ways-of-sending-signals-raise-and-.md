## 本节讲什么

1. `raise()` 在**多线程进程**里的真实语义——为什么它不等于 `kill(getpid(), sig)`

## 一、`raise()`：发信号给自己

```c
#include <signal.h>

int raise(int sig);
/* 返回：成功 0，失败非 0 */
```

### 单线程 vs 多线程（关键区别）

| 场景 | `raise(sig)` 等价写法 |
|------|----------------------|
| 单线程进程 | `kill(getpid(), sig)` —— 完全等价 |
| 多线程进程 | **`tgkill(getpid(), gettid(), sig)`** —— 只发给调用线程 |

glibc 的 `raise()` 实现用的是 `tgkill(getpid(), gettid(), sig)`，即**明确指定发给调用线程自己**。

```
   kill(getpid(), SIG)          raise(SIG)
   ┌──────────────────┐        ┌──────────────────┐
   │ 进程（线程组）     │        │ 进程（线程组）     │
   │  T1   T2   T3    │        │  T1   T2   T3    │
   │  ?    ?    ?     │        │      ↑           │
   └──────────────────┘        └──────────────────┘
    由任一未阻塞线程执行          必定是调用线程执行
```

> **实践**：多线程程序里想让**特定线程**处理信号，用 `pthread_kill(thread, sig)` 或 `tgkill(tgid, tid, sig)`，不要用 `kill(getpid(), sig)`。

### `tgkill()` vs `tkill()`：为什么后者被废弃

两个系统调用都是「发给指定线程」，但安全性不同：

```c
// kernel/signal.c:3988
SYSCALL_DEFINE3(tgkill, pid_t, tgid, pid_t, pid, int, sig)
{
	/* This is only valid for single tasks */
	if (pid <= 0 || tgid <= 0)
		return -EINVAL;

	return do_tkill(tgid, pid, sig);        // ← 带 tgid 校验
}

// kernel/signal.c:4004
SYSCALL_DEFINE2(tkill, pid_t, pid, int, sig)
{
	if (pid <= 0)
		return -EINVAL;

	return do_tkill(0, pid, sig);           // ← tgid = 0，不校验！
}
```

| 接口 | tgid 参数 | 风险 |
|------|-----------|------|
| `tgkill(tgid, tid, sig)` | 有 | 校验 tid 确实属于 tgid，**安全** |
| `tkill(tid, sig)` | 无（`0`） | 不校验；若 tid 已退出并被复用，会**发给错误的线程** |

> `tkill` 是 Linux 2.4 时代的遗留接口，因缺少 tgid 校验存在 **TID 复用**竞态，现已被 `tgkill` 取代。**新代码只用 `tgkill`（或 POSIX 的 `pthread_kill`）**。

## 二、`killpg()`：发给整个进程组

```c
#include <signal.h>

int killpg(pid_t pgrp, int sig);
/* 等价于 kill(-pgrp, sig) */
```

### 进程组、会话与控制终端

理解 `killpg` 需要三个概念：

```
   会话（Session, SID）
   ├── 控制终端（可选，一个会话最多一个）
   │
   ├── 前台进程组（FG PGRP）—— 能读终端、能收 Ctrl+C / Ctrl+Z
   │   └── P1  P2  P3
   │
   ├── 后台进程组（BG PGRP）—— 读终端会收 SIGTTIN，写可能收 SIGTTOU
   │   └── P4  P5
   │
   └── 孤儿进程组（父进程已死的组）
```

| 概念 | 标识 | 获取 | 作用 |
|------|------|------|------|
| **进程组** | PGID | `getpgrp()` | 信号可群发；作业控制单位 |
| **会话** | SID | `getsid(0)` | 一个登录会话；可绑定一个控制终端 |
| **控制终端** | — | `/dev/tty` | 产生 `SIGINT`/`SIGTSTP`/`SIGHUP` 的来源 |

> **注意**：`killpg(0, sig)` 中的 `0` 表示**调用者所在的进程组**（与 `kill(0, sig)` 一致），不是"无进程组"。

### 终端产生的信号

| 按键 / 事件 | 信号 | 发给谁 | 默认动作 |
|-------------|------|--------|----------|
| `Ctrl+C` | `SIGINT` | **前台进程组** | term |
| `Ctrl+\` | `SIGQUIT` | **前台进程组** | core |
| `Ctrl+Z` | `SIGTSTP` | **前台进程组** | stop |
| 终端断开 / SSH 掉线 | `SIGHUP` | 会话首进程及其组 | term |
| 后台进程读终端 | `SIGTTIN` | 该后台进程组 | stop |
| 后台进程写终端（取决于 `tostop`） | `SIGTTOU` | 该后台进程组 | stop |

> 这些信号的共同点是**发给整个进程组**而不是单个进程——这就是为什么在 shell 里 `Ctrl+C` 能同时终止一条管道上的所有命令（`cmd1 | cmd2 | cmd3` 同属一个前台进程组）。

内核侧的进程组广播走 `__kill_pgrp_info()`（由 `kill_something_info` 在 `pid < -1` 或 `pid == 0` 时调用，见 `kernel/signal.c:1618`）。

## 三、`SIGHUP` 与 daemon 化

`SIGHUP`（hangup）最初的含义是「调制解调器挂断」。现代 Linux 上它主要由**终端断开**触发：

```
  SSH 登录 → 启动策略进程 → 网络断开
                              ↓
                       内核给会话发 SIGHUP
                              ↓
                       默认动作 = term
                              ↓
                      ❌ 策略进程被杀
```

### daemon 必须脱离控制终端

这就是为什么所有 daemon 都要 `setsid()`：

```c
#include <unistd.h>

pid_t setsid(void);      /* 成功返回新 SID，失败返回 -1 */
```

`setsid()` 做三件事：

1. 创建一个**新会话**，调用者成为会话首进程（session leader）
2. 创建一个**新进程组**，调用者成为组长
3. **脱离原控制终端**（新会话没有控制终端）

| 有控制终端 | `setsid()` 后 |
|-----------|---------------|
| 终端断开 → 收 `SIGHUP` → 被杀 | 终端断开 → **无影响** |
| `Ctrl+C` → 收 `SIGINT` → 被杀 | `Ctrl+C` → **无影响** |
| 后台读写终端 → `SIGTTIN`/`SIGTTOU` | 无终端，不触发 |

### 标准 daemon 化骨架（double-fork）

```c
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <stdlib.h>

void daemonize(void)
{
    pid_t pid = fork();
    if (pid < 0) exit(1);
    if (pid > 0) exit(0);          /* 父进程退出 */

    setsid();                      /* ① 脱离控制终端，成为会话首进程 */

    /* ② 第二次 fork：确保不是会话首进程，永远不会重新获得控制终端 */
    pid = fork();
    if (pid < 0) exit(1);
    if (pid > 0) exit(0);

    umask(0);                      /* ③ 重置文件掩码 */
    chdir("/");                    /* ④ 避免占用可卸载的文件系统 */

    /* ⑤ 重定向 0/1/2 到 /dev/null，彻底切断与终端的关联 */
    int fd = open("/dev/null", O_RDWR);
    dup2(fd, STDIN_FILENO);
    dup2(fd, STDOUT_FILENO);
    dup2(fd, STDERR_FILENO);
    if (fd > STDERR_FILENO) close(fd);
}
```

> **为什么要 double-fork**？第一次 `fork` + `setsid()` 后，子进程成为会话首进程；而**会话首进程有可能重新打开一个终端并成为它的控制进程**。再 `fork` 一次并让父进程退出，剩下的孙子进程就**不是会话首进程**，永远无法获得控制终端。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | daemon 用 `setsid()` 脱离控制终端，避免终端关闭时误收 `SIGHUP`/`SIGINT` 被杀，是嵌入式长驻服务的第一课；`killpg()` 用于一键终止整个 worker 组（如 `killpg(getpgrp(), SIGTERM)` 做组级优雅停机） |
| HFT | 交易进程**必须**脱离控制终端（`setsid` + 重定向），否则运维 SSH 断开触发 `SIGHUP` 会杀死正在跑的策略——这是生产事故的经典来源。另注意：前台进程组收到 `Ctrl+C` 会**群杀整条交易链路**，所以交易系统启动脚本应把各组件放入**独立进程组**（`setpgid`），避免一次 Ctrl+C 全灭 |

## 代码示例：进程组与终端信号

```c
/* pgrp.c —— 观察进程组/会话，并演示 killpg 群发
 * 编译: gcc -o pgrp pgrp.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
#include <errno.h>

static volatile sig_atomic_t got = 0;
static void handler(int sig) { got = sig; }

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sigaction(SIGUSR1, &sa, NULL);

    printf("PID=%d  PGID=%d  SID=%d  (PPID=%d)\n",
           getpid(), getpgrp(), getsid(0), getppid());

    /* ① 同组子进程：killpg 会同时打到父子 */
    pid_t c1 = fork();
    if (c1 == 0) { pause(); _exit(0); }        /* 子进程继承父的 PGID */

    /* ② 独立进程组：killpg(父组) 打不到它 */
    pid_t c2 = fork();
    if (c2 == 0) {
        setpgid(0, 0);                          /* 自立门户 */
        printf("  子进程 %d 独立成组: PGID=%d\n", getpid(), getpgrp());
        pause();
        _exit(0);
    }

    sleep(1);                                    /* 等子进程 setpgid 完成 */

    /* ③ killpg 向父进程组群发 */
    got = 0;
    killpg(getpgrp(), SIGUSR1);
    printf("killpg(%d, SIGUSR1) -> 本进程 got=%d\n", getpgrp(), got);

    /* ④ 清理 */
    kill(c1, SIGTERM);
    kill(c2, SIGTERM);
    waitpid(c1, NULL, 0);
    waitpid(c2, NULL, 0);

    /* ⑤ 演示 setsid 脱离控制终端 */
    pid_t d = fork();
    if (d == 0) {
        pid_t before = getsid(0);
        setsid();
        printf("  setsid(): SID %d -> %d (新会话，脱离控制终端)\n",
               before, getsid(0));
        _exit(0);
    }
    waitpid(d, NULL, 0);
    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b>多线程进程里 <code>raise(sig)</code> 等价于 <code>kill(getpid(), sig)</code> 吗？</summary>

**不等价（多线程场景）**：

- `raise(sig)` → glibc 实现为 `tgkill(getpid(), gettid(), sig)`，**保证发给调用线程自己**
- `kill(getpid(), sig)` → 发给整个进程，由**任意一个**未阻塞该信号的线程执行 handler

| | 目标 | 执行 handler 的线程 |
|--|------|---------------------|
| `raise(sig)` | 调用线程 | 必然是调用线程 |
| `kill(getpid(), sig)` | 进程（线程组） | 任一未阻塞线程，不确定 |

**单线程进程里两者等价**（只有一个线程，发给谁都一样）。

**实践**：多线程下想精确指定线程，用 `pthread_kill(pthread_t, sig)` 或 `tgkill(tgid, tid, sig)`。

</details>

<details>
<summary><b>问 2：</b><code>tkill()</code> 和 <code>tgkill()</code> 有什么区别？为什么 <code>tkill</code> 被废弃？</summary>

两个都是「发给指定线程」，唯一区别是**有没有 tgid 校验**：

```c
// kernel/signal.c:3988
SYSCALL_DEFINE3(tgkill, pid_t, tgid, pid_t, pid, int, sig)
{
	if (pid <= 0 || tgid <= 0) return -EINVAL;
	return do_tkill(tgid, pid, sig);        // ← 带 tgid
}

// kernel/signal.c:4004
SYSCALL_DEFINE2(tkill, pid_t, pid, int, sig)
{
	if (pid <= 0) return -EINVAL;
	return do_tkill(0, pid, sig);           // ← tgid = 0，不校验
}
```

**`tkill` 的风险（TID 复用）**：

```
t0: 线程 T 的 tid = 500
t1: 线程 T 退出
t2: 内核把 tid 500 分配给另一个进程/的新线程
t3: tkill(500, SIGTERM)  →  信号发给了错误的线程 ❌
```

`tgkill(tgid, tid, sig)` 要求同时给出 tgid，内核会校验「tid 确实属于 tgid 这个线程组」，从而堵死这个竞态。

**结论**：新代码只用 `tgkill()` 或 POSIX 的 `pthread_kill()`，`tkill()` 是 Linux 2.4 遗留接口，已废弃。

</details>

<details>
<summary><b>问 3：</b>在 shell 里按 <code>Ctrl+C</code>，为什么 <code>cmd1 | cmd2 | cmd3</code> 整条管道都会被终止？</summary>

因为终端产生的信号是发给**整个前台进程组**的，不是发给单个进程。

shell 在执行 `cmd1 | cmd2 | cmd3` 时会：

1. `fork()` 出三个子进程
2. 把它们放进**同一个新进程组**（PGID = cmd1 的 PID）
3. 把这个进程组设为**前台进程组**

当按下 `Ctrl+C` 时，终端驱动向**前台进程组**发送 `SIGINT`——三个进程同属一组，所以全部收到。

内核侧的广播由 `__kill_pgrp_info()` 完成（`kill_something_info` 在 `pid == 0` 或 `pid < -1` 时调用，见 `kernel/signal.c:1618`）。

**实践意义**：交易系统启动脚本如果让多个组件共享一个进程组，一次 `Ctrl+C` 会全灭。要独立控制，需各自 `setpgid(0, 0)` 自立门户。

</details>

<details>
<summary><b>问 4：</b>为什么 daemon 要 <code>setsid()</code>？<code>SIGHUP</code> 是怎么产生的？</summary>

`SIGHUP`（hangup）最初来自「调制解调器挂断」。现代 Linux 上，**控制终端断开**（SSH 掉线、终端窗口关闭、伪终端主设备关闭）时，内核会给该会话的**首进程及其进程组**发送 `SIGHUP`，默认动作是 **term（终止）**。

所以如果服务进程绑定了控制终端，运维一断 SSH，进程就被杀了——这是生产事故的经典来源。

`setsid()` 做三件事来解决它：

1. 创建**新会话**，调用者成为会话首进程
2. 创建**新进程组**，调用者成为组长
3. **脱离原控制终端**（新会话没有控制终端）

脱离后，终端断开不再发送 `SIGHUP`，`Ctrl+C`/`Ctrl+Z` 也不再影响该进程。

**坑**：单独 `setsid()` 后进程成为会话首进程，将来仍可能重新打开一个终端并获取控制权——这就是为什么标准 daemon 化要 **double-fork**，让最终进程不是会话首进程。

</details>

<details>
<summary><b>问 5：</b>标准 daemon 化为什么要 fork 两次？</summary>

| 步骤 | 目的 |
|------|------|
| 第一次 `fork` + 父退出 | 让子进程不是进程组组长，为 `setsid()` 创造条件（`setsid` 对组长会失败） |
| `setsid()` | 创建新会话 + 新进程组，**脱离控制终端** |
| **第二次 `fork` + 父退出** | **关键**：确保最终进程**不是会话首进程** |

**为什么第二次 fork 必要**：

会话首进程有一个特权——它可以打开一个终端设备并**成为该终端的控制进程**。如果 daemon 仍是会话首进程，将来某个时刻不小心打开了一个 tty（比如打开串口、pty），就会重新获得控制终端，从而再次暴露在 `SIGHUP`/`SIGINT` 之下。

第二次 `fork` 后，存活的孙子进程**不是会话首进程**，永远无法获取控制终端，彻底杜绝了这条路径。

**完整骨架**还包含：`umask(0)`（重置文件掩码）、`chdir("/")`（避免占用可卸载文件系统）、把 0/1/2 重定向到 `/dev/null`（切断与终端的 I/O 关联）。

</details>
