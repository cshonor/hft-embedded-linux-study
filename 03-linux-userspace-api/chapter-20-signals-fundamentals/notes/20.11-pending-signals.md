# 20.11 待处理信号（Pending Signals）

## 本节讲什么

1. **未决（pending）是什么**——信号已产生但尚未递送的中间状态，内核存在哪里
2. `sigpending()` 到底返回什么——**两层 pending 的并集，再与掩码求交**
3. 为什么 `sigpending()` **查不到未被阻塞的信号**，以及这个特性该怎么用

---

## 一、两层 pending

回顾 [20.1](./20.1-concepts-and-overview.md)：未决信号存放在两个层级。

| 层级 | 位置 | 装的什么 | 谁会产生 |
|------|------|----------|----------|
| **线程私有** | `task_struct.pending` | 发给**特定线程**的信号 | `tgkill`/`pthread_kill`/`raise`（多线程）、硬件异常（`SIGSEGV`/`SIGFPE`） |
| **进程共享** | `signal_struct.shared_pending` | 发给**整个进程**的信号 | `kill`/`killpg`/终端信号，由任一线程竞争取走 |

```
   进程（线程组）
   ┌─────────────────────────────────────────┐
   │  shared_pending  { SIGTERM }            │  ← kill(pid, SIGTERM) 放这
   │                                          │
   │   线程 A               线程 B            │
   │   ┌──────────┐        ┌──────────┐      │
   │   │ pending  │        │ pending  │      │
   │   │ {SIGSEGV}│        │   { }    │      │  ← tgkill/硬件异常放这
   │   └──────────┘        └──────────┘      │
   └─────────────────────────────────────────┘
```

## 二、`sigpending()` 与 `do_sigpending()`

```c
#include <signal.h>

int sigpending(sigset_t *set);
/* 返回：成功 0，失败 -1 */
/* set 是**输出**参数：内核把当前未决集写进去 */
```

内核实现只有 6 行，却完整揭示了语义（`kernel/signal.c:3232`）：

```c
static void do_sigpending(sigset_t *set)
{
	spin_lock_irq(&current->sighand->siglock);
	sigorsets(set, &current->pending.signal,
		  &current->signal->shared_pending.signal);     // ① 私有 ∪ 共享
	spin_unlock_irq(&current->sighand->siglock);

	/* Outside the lock because only this thread touches it.  */
	sigandsets(set, &current->blocked, set);                 // ② ∩ 掩码
}
```

**完整语义**：

```
   sigpending(set)  ⟹  set = (私有 pending ∪ 共享 pending) ∩ 当前掩码
```

| 步骤 | 操作 | 含义 |
|------|------|------|
| ① | `pending.signal` **∪** `shared_pending.signal` | 把两级 pending 合起来看 |
| ② | 结果 **∩** `current->blocked` | **只保留被阻塞的那些** |

> **这是本节最反直觉的一点**：`sigpending()` 只报告**被阻塞而未递送**的信号。

原因很自然：**未被阻塞的信号会立即递送**，递送后 pending 位就被清掉了——所以它根本不会停留在 pending 集中。

```
   信号产生
     ├─ 未被阻塞 → 立即递送 → pending 清空 → sigpending 查不到 ✓（正常）
     └─ 被阻塞   → 留在 pending → sigpending 查得到 ✓
```

**实践推论**：`sigpending()` 的典型用途是检查「临界区期间有没有信号堆积」，而不是通用地"查询是否有信号"。

## 三、典型用法

```c
sigset_t pending;
sigpending(&pending);
if (sigismember(&pending, SIGINT) == 1) {   /* 注意用 == 1 比较 */
    /* SIGINT 已被阻塞并堆积在 pending 中 */
}
```

### 临界区后检查堆积

```c
sigset_t block, save, pending;
sigemptyset(&block);
sigaddset(&block, SIGTERM);
sigaddset(&block, SIGINT);

sigprocmask(SIG_BLOCK, &block, &save);      /* 进入临界区 */
/* ... 更新共享数据结构 ... */
sigpending(&pending);                       /* 检查期间有没有信号堆积 */
if (sigismember(&pending, SIGTERM) == 1)
    need_shutdown = 1;
sigprocmask(SIG_SETMASK, &save, NULL);      /* 退出临界区 → 堆积的信号补递送 */
```

> **注意顺序**：`sigpending()` 必须在**解除阻塞之前**调用。一旦 `sigprocmask(SIG_SETMASK, ...)` 恢复掩码，pending 的信号会**立即递送并被清空**，之后就查不到了。

## 四、与「不排队」的关系

标准信号**不排队**：阻塞期间同号信号到达 N 次，pending 位图中仍然只有**一个位**，解除阻塞后 handler **只执行一次**。

```c
sigprocmask(SIG_BLOCK, &mask, NULL);
raise(SIGINT); raise(SIGINT); raise(SIGINT);   /* 发了 3 次 */
sigpending(&pending);
/* sigismember(&pending, SIGINT) == 1，但无法知道是 1 次还是 3 次 */
```

这是下一节 [20.12 信号不排队](./20.12-signals-are-not-queued.md) 的主题。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 临界区结束后检查 pending，决定是否需要特殊处理（如停机信号在临界区期间到达，出临界区后立即响应）。注意 `sigpending` 必须在恢复掩码**之前**调用，否则信号已补递送、pending 被清空 |
| HFT | 长时间阻塞后检查 pending 可辅助诊断「信号事件被合并丢失」的问题——但因为它**不排队**，只能知道「来过」，无法知道「来了几次」。HFT 中若需精确计数，应改用实时信号（可排队，见 [Ch22.8](../../chapter-22-signals-advanced/notes/22.8-realtime-signals.md)）或 signalfd（[Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md)） |

## 代码示例

```c
/* pendingdemo.c —— 验证 sigpending = (私有∪共享) ∩ 掩码
 * 编译: gcc -D_GNU_SOURCE -o pendingdemo pendingdemo.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

static void show(const char *tag, const sigset_t *p)
{
    printf("  %-28s SIGINT=%d SIGUSR1=%d\n", tag,
           sigismember(p, SIGINT) == 1,
           sigismember(p, SIGUSR1) == 1);
}

int main(void)
{
    sigset_t block, save, pending;

    /* 构造要阻塞的集合：SIGINT（进程级）+ SIGUSR1（本线程） */
    sigemptyset(&block);
    sigaddset(&block, SIGINT);
    sigaddset(&block, SIGUSR1);
    sigprocmask(SIG_BLOCK, &block, &save);

    /* ① 进程级：kill 放进 shared_pending */
    kill(getpid(), SIGINT);
    /* ② 线程级：tgkill 放进本线程私有 pending */
    syscall(SYS_tgkill, getpid(), syscall(SYS_gettid), SIGUSR1);

    sigpending(&pending);
    printf("阻塞期间（私有∪共享 均应可见）:\n");
    show("  sigpending()", &pending);        /* SIGINT=1 SIGUSR1=1 */

    /* ③ 不排队验证：连发多次 SIGINT */
    raise(SIGINT); raise(SIGINT); raise(SIGINT);
    sigpending(&pending);
    printf("\n连发 3 次 SIGINT 后（仍只有一份）:\n");
    show("  sigpending()", &pending);        /* SIGINT=1（无法得知次数） */

    /* ④ 解除阻塞前必须查 pending —— 之后就被清空了 */
    sigprocmask(SIG_SETMASK, &save, NULL);
    sigpending(&pending);
    printf("\n解除阻塞后（信号已补递送，pending 清空）:\n");
    show("  sigpending()", &pending);        /* 注意：SIGINT 默认终止，实际到不了这里 */

    return 0;
}
```

> **运行提示**：`SIGINT`/`SIGUSR1` 的默认动作是 terminate，所以第 ④ 步实际运行时进程会被终止。观察 ①②③ 的输出即可；若要完整跑通，请先 `sigaction` 把两者设为 `SIG_IGN` 或自定义 handler。

## 自测题

<details>
<summary><b>问 1：</b><code>sigpending()</code> 返回的到底是什么？为什么查不到未被阻塞的信号？</summary>

内核实现（`kernel/signal.c:3232`）：

```c
static void do_sigpending(sigset_t *set)
{
	spin_lock_irq(&current->sighand->siglock);
	sigorsets(set, &current->pending.signal,
		  &current->signal->shared_pending.signal);   // 私有 ∪ 共享
	spin_unlock_irq(&current->sighand->siglock);

	/* Outside the lock because only this thread touches it.  */
	sigandsets(set, &current->blocked, set);               // ∩ 掩码
}
```

**完整语义**：

```
set = (线程私有 pending ∪ 进程共享 pending) ∩ 当前掩码
```

**为什么查不到未被阻塞的信号**：

因为未被阻塞的信号**会立即递送**——递送时内核从 pending 位图里取出该信号并清除对应位。所以未阻塞的信号在 pending 里停留的时间趋近于零，`sigpending()` 自然查不到。

**实践结论**：`sigpending()` 的准确含义是「**查询当前被阻塞、堆积着等待递送的信号**」，不是通用的"有没有信号"。

</details>

<details>
<summary><b>问 2：</b>线程私有的 pending 和进程共享的 pending 各装什么信号？<code>sigpending</code> 如何兼顾？</summary>

| 层级 | 位置 | 装的什么 |
|------|------|----------|
| **线程私有** | `task_struct.pending` | 发给特定线程：`tgkill`/`pthread_kill`/glibc 的 `raise()`（多线程下），以及**硬件异常**（`SIGSEGV`/`SIGFPE`/`SIGILL` 由当前线程触发） |
| **进程共享** | `signal_struct.shared_pending` | 发给整个进程：`kill`/`killpg`/终端信号，由任一未阻塞线程竞争取走 |

**`sigpending` 兼顾方式**：`do_sigpending` 第 ① 步就做了 `sigorsets(set, &current->pending.signal, &current->signal->shared_pending.signal)`，把两级**取并集**，所以调用方看到的是合并后的视图，无需关心信号来自哪一级。

**推论**：用 `kill()` 给多线程进程发信号，handler 由**任意一个**未阻塞该信号的线程执行——正因为信号放在 `shared_pending` 里，谁先被调度到谁取走。

</details>

<details>
<summary><b>问 3：</b>为什么必须在解除阻塞<b>之前</b>调用 <code>sigpending()</code>？</summary>

因为一旦解除阻塞，pending 的信号会**立即递送并从位图中清除**，`sigpending()` 就查不到了。

时间线：

```
sigprocmask(SIG_BLOCK, &mask, &save);
    ↓ 信号堆积在 pending
sigpending(&pending);              ← ✅ 此时能查到
    ↓
sigprocmask(SIG_SETMASK, &save, NULL);   ← 解除阻塞
    ↓ 内核立即递送 pending 信号，清除位图
sigpending(&pending);              ← ❌ 已被清空，查不到了
```

**正确模式**：

```c
sigprocmask(SIG_BLOCK, &block, &save);       /* 进入临界区 */
/* ... 更新共享数据 ... */
sigpending(&pending);                        /* 先查堆积 */
if (sigismember(&pending, SIGTERM) == 1)
    need_shutdown = 1;                       /* 记录意图 */
sigprocmask(SIG_SETMASK, &save, NULL);       /* 后解除阻塞 */
```

**更优雅的替代**：如果目的只是「不错过停机信号」，用 `sigwaitinfo()` 同步取信号（[Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md)）比「阻塞 + 查 pending + 解除」干净得多。

</details>

<details>
<summary><b>问 4：</b>阻塞期间同号信号来了 5 次，<code>sigpending</code> 能查出来是 5 次吗？</summary>

**不能**。标准信号**不排队**，pending 位图里只有**一个位**，只能表示"来过 / 没来过"，无法表示次数。

```c
sigprocmask(SIG_BLOCK, &mask, NULL);
raise(SIGINT); raise(SIGINT); raise(SIGINT);  /* 发 5 次 */
sigpending(&pending);
/* sigismember(&pending, SIGINT) == 1  ← 只知道"来过" */
sigprocmask(SIG_SETMASK, &save, NULL);
/* handler 只执行 1 次，不是 5 次 ❌ */
```

**如果需要精确计数**，三个方向：

1. **实时信号**——可排队，`sigqueue()` 可携带数据（[Ch22.8](../../chapter-22-signals-advanced/notes/22.8-realtime-signals.md)）
2. **`signalfd`**——把信号变成文件描述符事件，可 `read()` 出每一次（[Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md)）
3. **不用信号**——HFT 内部通知应走 eventfd / 共享内存原子计数器，天然支持计数

详见下一节 [20.12 信号不排队](./20.12-signals-are-not-queued.md)。

</details>

<details>
<summary><b>问 5：</b><code>do_sigpending</code> 里 <code>sigorsets</code> 加锁而 <code>sigandsets(&current->blocked, ...)</code> 不加锁，为什么？</summary>

代码里的注释直接给出了答案：

```c
static void do_sigpending(sigset_t *set)
{
	spin_lock_irq(&current->sighand->siglock);
	sigorsets(set, &current->pending.signal,
		  &current->signal->shared_pending.signal);
	spin_unlock_irq(&current->sighand->siglock);

	/* Outside the lock because only this thread touches it.  */
	sigandsets(set, &current->blocked, set);
}
```

**原因分析**：

| 数据 | 谁会修改 | 是否需要锁 |
|------|----------|-----------|
| `current->pending.signal` | **其他线程**可以往里写（用 `tgkill` 给本线程发信号） | ✅ 需要 `sighand->siglock` |
| `current->signal->shared_pending.signal` | **其他线程**竞争取走 | ✅ 需要同一把锁 |
| `current->blocked` | **只有本线程自己**能改（`sigprocmask` 只改 `current`） | ❌ 不需要锁 |

关键在注释那句 *"Outside the lock because only this thread touches it"*——`blocked` 是线程私有字段，且内核保证只有 `current` 自己会改它（源码里 `sigprocmask` 开头也有类似注释：`/* Lockless, only current can change ->blocked, never from irq */`）。

**这是一个典型的内核无锁编程模式**：通过「数据归属唯一」来消除加锁需求，而非盲目加锁。

</details>
