# 20.2 信号类型与默认动作

## 本节讲什么

1. 每个信号在不做特殊设置时**默认干什么的**——内核把 31 个标准信号分成哪几类
2. 默认动作有**哪几种**（终止 / core / 停止 / 继续 / 忽略），内核用什么判据区分
3. **标准信号与实时信号**的本质差异：排队、携带数据、递送顺序

---

## 一、默认动作的四类

`include/linux/signal.h:339-348` 的内核注释是这个问题的**权威定义**，它明确定义了三种终止语义：

```
   terminate	- kill the process, i.e. all threads in the group,
 		  similar to exit_group.  The group leader (only) reports
		  WIFSIGNALED status to its parent.
   coredump	- write a core dump file describing all threads using
		  the same mm and then kill all those threads
   stop 	- stop all the threads in the group, i.e. TASK_STOPPED state

 SIGKILL and SIGSTOP cannot be caught, blocked, or ignored.
```

加上「忽略」和作业控制的「继续」，一共是五种可观察行为：

| 默认动作 | 含义 | 进程退出后 `wait()` 状态 |
|----------|------|--------------------------|
| **term** | 终止进程（组） | `WIFSIGNALED` 为真 |
| **core** | 先写 core dump 再终止 | `WIFSIGNALED` 为真 + 产生 core 文件 |
| **stop** | 挂起进程组（`TASK_STOPPED`） | `WIFSTOPPED` |
| **cont** | 恢复被停止的进程（实际表现为「忽略」+ 额外唤醒） | — |
| **ignore** | 丢弃，无任何效果 | — |

### 内核的四张 MASK 表

内核不是用 `switch` 硬编码每种信号的默认动作，而是用**位掩码**分类，判据宏定义在 `include/linux/signal.h:418-448`：

| 宏 | 行号 | 覆盖信号 | 语义 |
|---|------|----------|------|
| `SIG_KERNEL_ONLY_MASK` | `:418` | `SIGKILL`、`SIGSTOP` | 「内核独占」，不可捕获/忽略/阻塞 |
| `SIG_KERNEL_STOP_MASK` | `:421` | `SIGSTOP`、`SIGTSTP`、`SIGTTIN`、`SIGTTOU` | 停止类 |
| `SIG_KERNEL_COREDUMP_MASK` | `:425` | `SIGQUIT`、`SIGILL`、`SIGTRAP`、`SIGABRT`、`SIGFPE`、`SIGSEGV`、`SIGBUS`、`SIGSYS`、`SIGXCPU`、`SIGXFSZ`、`SIGEMT` | 产 core 类 |
| `SIG_KERNEL_IGNORE_MASK` | `:433` | `SIGCONT`、`SIGCHLD`、`SIGWINCH`、`SIGURG` | 默认忽略类 |

其余一律为 **terminate**。

```c
// include/linux/signal.h:444-448 —— 四个判据宏
#define sig_kernel_only(sig)       siginmask(sig, SIG_KERNEL_ONLY_MASK)
#define sig_kernel_coredump(sig)   siginmask(sig, SIG_KERNEL_COREDUMP_MASK)
#define sig_kernel_ignore(sig)     siginmask(sig, SIG_KERNEL_IGNORE_MASK)
#define sig_kernel_stop(sig)       siginmask(sig, SIG_KERNEL_STOP_MASK)
#define sig_specific_sicodes(sig)  siginmask(sig, SIG_SPECIFIC_SICODES_MASK)
```

> **启发**：想快速判断「这个信号默认会不会产 core」，不用查表，看它在不在 `SIG_KERNEL_COREDUMP_MASK` 里即可。这也是 `man 7 signal` 表格的内核出处。

## 二、完整默认动作表（Linux 标准信号 1–31）

下表据 `include/linux/signal.h:351-386` 的内核注释整理：

| 信号 | 编号 | 默认动作 | 典型触发 |
|------|------|----------|----------|
| `SIGHUP` | 1 | term | 终端断开 / 控制进程终止 |
| `SIGINT` | 2 | term | Ctrl+C |
| `SIGQUIT` | 3 | **core** | Ctrl+\ |
| `SIGILL` | 4 | **core** | 非法指令 |
| `SIGTRAP` | 5 | **core** | 断点陷阱（gdb 用） |
| `SIGABRT` | 6 | **core** | `abort()` |
| `SIGBUS` | 7 | **core** | 总线错误（mmap 越界访问） |
| `SIGFPE` | 8 | **core** | 除零 / 浮点异常 |
| `SIGKILL` | 9 | term **(+)** | `kill -9`，唯一强制终止手段 |
| `SIGUSR1` | 10 | term | 用户自定义 |
| `SIGSEGV` | 11 | **core** | 段错误 |
| `SIGUSR2` | 12 | term | 用户自定义 |
| `SIGPIPE` | 13 | term | 管道/socket 对端已关闭仍写入 |
| `SIGALRM` | 14 | term | `alarm()` / `setitimer()` 到期 |
| `SIGTERM` | 15 | term | `kill` 默认信号，优雅停机 |
| `SIGSTKFLT` | 16 | term | 栈故障（Linux 上罕见） |
| `SIGCHLD` | 17 | **ignore** | 子进程退出/停止/继续 |
| `SIGCONT` | 18 | **cont** | 恢复被停止的进程 |
| `SIGSTOP` | 19 | **stop (+)** | `Ctrl+Z` 语义，不可捕获 |
| `SIGTSTP` | 20 | **stop** | Ctrl+Z |
| `SIGTTIN` | 21 | **stop** | 后台进程读终端 |
| `SIGTTOU` | 22 | **stop** | 后台进程写终端 |
| `SIGURG` | 23 | **ignore** | socket 带外数据到达 |
| `SIGXCPU` | 24 | **core** | CPU 时间超限（`RLIMIT_CPU`） |
| `SIGXFSZ` | 25 | **core** | 文件大小超限（`RLIMIT_FSIZE`） |
| `SIGVTALRM` | 26 | term | 虚拟时钟到期 |
| `SIGPROF` | 27 | term | profiling 时钟到期 |
| `SIGWINCH` | 28 | **ignore** | 终端窗口尺寸变化 |
| `SIGIO`/`SIGPOLL` | 29 | term | 异步 I/O 就绪 |
| `SIGPWR` | 30 | term | 电源故障 |
| `SIGSYS` | 31 | **core** | 非法系统调用（seccomp 拦截） |

> `(+)` 对 `SIGKILL` 与 `SIGSTOP`，内核注释特别强调：*"For SIGKILL and SIGSTOP the action is 'always', not just 'default'"*（`include/linux/signal.h:392`）——它们的动作是**永远**如此，不只是「默认」如此。

### 作业控制的特殊语义

`include/linux/signal.h:393-400` 记录了一条容易踩坑的规则：

> `SIGCONT` 恢复进程时，会**清除所有未决的 stop 类信号**（那些标记为 `stop(*)` 的）；反之，任何 stop 信号到达时，会**清除未决的 `SIGCONT`**。这两件事**无视阻塞、捕获或忽略**。

也就是说 `SIGCONT` 与停止信号会自动互相抵消，这是作业控制（shell 的 `fg`/`bg`）能正确工作的基础。

## 三、标准信号 vs 实时信号

Linux 支持两类信号，编号区间不同，语义差异很大：

| | **标准信号**（1–31） | **实时信号**（`SIGRTMIN`–`SIGRTMAX`） |
|--|---------------------|----------------------------------|
| 编号 | `1`–`31`（固定，各 Unix 略有差异） | `34`–`64`（glibc 保留 32/33 内部用） |
| 排队 | **不排队**；阻塞期间同号多次抵达**只保留一份** | **可排队**，多次抵达逐个保留 |
| 附加数据 | 无 | `sigqueue()` 可携带 `int` 或 `void*` |
| 递送顺序 | 无保证 | **小号优先**；同号 FIFO |
| 默认动作 | 各异（见上表） | 统一 **terminate** |

内核注释佐证最后一行：

```
 *	|  SIGRTMIN-SIGRTMAX |	terminate       |      // include/linux/signal.h:385
```

### 为什么 32/33 被 glibc 占用

`SIGRTMIN` 在 glibc 里是 `34` 而不是 `32`，因为 glibc 的 NPTL 线程实现**内部占用了前两个实时信号**（32 用于 `setxid` 同步、33 用于线程取消）。所以用户代码必须用 `SIGRTMIN+N` 的写法，不能硬编码 `34+N`。

```c
#define MY_SIG (SIGRTMIN + 0)     /* 正确：用宏，可移植 */
/* #define MY_SIG 34                 错误：硬编码，换 libc 就崩 */
```

> **库作者警告**：第三方库应尽量**不要**占用实时信号编号。实时信号是稀缺资源（仅 31 个），多个库各占几个极易冲突，且冲突后表现为「信号被别的库 handler 吃掉」，极难排查。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 实时信号（`SIGRTMIN`–`MAX`）可排队且经 `sigqueue` 带 `int` 值，适合嵌入式进程间传少量带编号事件；标准信号同号只留一份，高频触发会丢，**别拿它计数**。另注意 `SIGXCPU`/`SIGXFSZ` 默认是 **core** 而非简单终止，资源受限设备上触发 `RLIMIT` 会把进程打死并写 core，可能撑爆 Flash |
| HFT | 「不排队」意味着同号信号被合并，无法用信号做精确事件计数；实时信号虽排队，但递送仍是异步上下文切换。HFT 内部通知应优先用 eventfd / 共享内存原子变量，信号只留给外部运维控制（启停）。另外 `SIGPROF`（27）默认是 **terminate**——如果用 gperftools 等 profiling 工具却没注册 handler，进程会直接被自己的 profiler 杀掉 |

## 代码示例：打印并验证默认动作分类

```c
/* defaction.c —— 观察常见信号的编号与默认动作
 * 编译: gcc -o defaction defaction.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <string.h>

/* 内核 include/linux/signal.h:418-448 的四类判据（用户态等价实现） */
static const char *def_action(int sig)
{
    switch (sig) {
    case SIGKILL: case SIGSTOP:                     return "term/stop (+) 内核独占";
    case SIGTSTP: case SIGTTIN: case SIGTTOU:       return "stop";
    case SIGQUIT: case SIGILL:  case SIGTRAP:
    case SIGABRT: case SIGFPE:  case SIGSEGV:
    case SIGBUS:  case SIGSYS:  case SIGXCPU:
    case SIGXFSZ:                                   return "core";
    case SIGCONT: case SIGCHLD:
    case SIGWINCH: case SIGURG:                     return "ignore/cont";
    default:                                        return "term";
    }
}

int main(void)
{
    struct { int sig; const char *name; } t[] = {
        {SIGHUP,"SIGHUP"}, {SIGINT,"SIGINT"},   {SIGQUIT,"SIGQUIT"},
        {SIGKILL,"SIGKILL"},{SIGSEGV,"SIGSEGV"},{SIGPIPE,"SIGPIPE"},
        {SIGALRM,"SIGALRM"},{SIGTERM,"SIGTERM"},{SIGCHLD,"SIGCHLD"},
        {SIGCONT,"SIGCONT"},{SIGSTOP,"SIGSTOP"},{SIGTSTP,"SIGTSTP"},
        {SIGURG,"SIGURG"}, {SIGXCPU,"SIGXCPU"}, {SIGWINCH,"SIGWINCH"},
    };
    for (size_t i = 0; i < sizeof(t)/sizeof(t[0]); i++)
        printf("%-8s = %2d  默认动作: %s\n",
               t[i].name, t[i].sig, def_action(t[i].sig));

    /* 实时信号区间：必须用宏，不要硬编码 */
    printf("\nSIGRTMIN=%d  SIGRTMAX=%d  (可用实时信号 %d 个)\n",
           SIGRTMIN, SIGRTMAX, SIGRTMAX - SIGRTMIN + 1);
    return 0;
}
```

## 自测题

<details>
<summary><b>问 1：</b>内核区分「产 core」和「单纯终止」的判据是什么？列举会产 core 的信号。</summary>

内核用位掩码 `SIG_KERNEL_COREDUMP_MASK`（`include/linux/signal.h:425`）分类，判据宏是 `sig_kernel_coredump(sig)`。

会产 core 的信号共 11 个：

`SIGQUIT`(3)、`SIGILL`(4)、`SIGTRAP`(5)、`SIGABRT`(6)、`SIGFPE`(8)、`SIGSEGV`(11)、`SIGBUS`(7)、`SIGSYS`(31)、`SIGXCPU`(24)、`SIGXFSZ`(25)、`SIGEMT`（非 POSIX，部分架构）。

其余标准信号默认只终止不产 core。注意实时信号（`SIGRTMIN`–`SIGRTMAX`）默认也是**单纯 terminate**（`include/linux/signal.h:385`）。

</details>

<details>
<summary><b>问 2：</b>哪些信号默认是被忽略的？为什么 <code>SIGCHLD</code> 默认是忽略而不是终止？</summary>

`SIG_KERNEL_IGNORE_MASK`（`include/linux/signal.h:433`）覆盖四个：`SIGCONT`(18)、`SIGCHLD`(17)、`SIGWINCH`(28)、`SIGURG`(23)。

`SIGCHLD` 默认忽略是**历史与实用性共同决定的**：子进程退出是常态事件，如果默认终止父进程，那任何 `fork()` 一个子进程再 `wait()` 的程序都会在自己收尸前被自己孩子杀死——整个 Unix 进程模型就崩了。

但「默认忽略」不等于「处理了僵尸进程」——忽略只是丢弃通知，**子进程仍会变成僵尸**直到父进程 `wait()`。要真正自动回收，需显式 `signal(SIGCHLD, SIG_IGN)`（此时内核直接回收，不产生僵尸）或注册 handler 调用 `waitpid()`。

</details>

<details>
<summary><b>问 3：</b>标准信号和实时信号的核心差异是什么？什么场景下必须用实时信号？</summary>

| 维度 | 标准信号 | 实时信号 |
|------|----------|----------|
| 排队 | **不排队**，阻塞期间同号只保留一份 | **排队**，逐个保留 |
| 附加数据 | 无 | `sigqueue()` 可带 `int`/`void*` |
| 递送顺序 | 无保证 | 小号优先，同号 FIFO |
| 默认动作 | 各异 | 统一 terminate |

**必须用实时信号的场景**：需要「信号带参数」或「不丢事件」时。例如用 `sigqueue(pid, sig, (union sigval){.sival_int = 42})` 把一个小整数随信号传给目标进程——标准信号做不到这件事。

**反例**：如果只想要「通知到了就行」（如停机信号），标准信号完全够用，且可移植性更好。

</details>

<details>
<summary><b>问 4：</b>为什么实时信号编号要用 <code>SIGRTMIN+N</code> 而不是硬编码 <code>34+N</code>？</summary>

因为 **glibc 内部占用了前两个实时信号**（32 和 33）：

- 32 用于 NPTL 的 `setxid` 同步（多线程进程 `setuid()` 时协调各线程）
- 33 用于线程取消（`pthread_cancel`）

所以用户态可见的 `SIGRTMIN` 是 **34** 而不是 32。这个占用是 glibc 的实现细节，其他 libc（如 musl）可能不同，且占用数量未来也可能变。

硬编码 `34` 在换 libc 或 glibc 调整内部实现时会静默错位——你的信号变成别人的信号，handler 被莫名吃掉。用 `SIGRTMIN+N` 则由 libc 保证给出正确的空闲起始编号。

</details>

<details>
<summary><b>问 5：</b>作业控制里 <code>SIGCONT</code> 和 stop 类信号会互相抵消，这条规则具体是什么？受阻塞/忽略影响吗？</summary>

规则记录在 `include/linux/signal.h:393-400`：

1. 发送 `SIGCONT` 恢复进程时，会**清除所有未决的 stop 类信号**（`SIGSTOP`、`SIGTSTP`、`SIGTTIN`、`SIGTTOU`）。
2. 任何 stop 信号到达时，会**清除未决的 `SIGCONT`**。

**不受影响**——内核注释明确说 "regardless of blocking, catching, or ignoring"，即无论目标是否阻塞、捕获或忽略了这些信号，抵消都会发生。

这是 shell 作业控制（`fg`/`bg`/`Ctrl+Z`）能正确工作的基础：用户先 `Ctrl+Z`（发 `SIGTSTP` 停止），再 `fg`（发 `SIGCONT` 恢复），两步不会产生残留的未决停止信号把进程又停回去。

</details>
