## 本节讲什么

1. 信号**是什么**——内核发给进程的异步通知，本质上是一次「软件中断」
2. 信号**怎么走**——产生（generate）→ 未决（pending）→ 递送（deliver）三阶段生命周期
3. 信号**往哪去**——默认动作 / 忽略 / 捕获三种处置，以及 `SIGKILL`、`SIGSTOP` 为何无法干预

---

## 一、信号是什么

信号是**内核（或进程经内核）向目标进程投递的一个小整数通知**，携带的信息只有：

- 信号编号（`1`~`64`，其中 `1`~`31` 为标准信号，`34`~`64` 为实时信号）
- 可选的附加数据（`siginfo_t`，实时信号才常用，见 Ch22）

它不携带消息体，所以**信号不是 IPC 手段**，只是「发生了某事」的轻量提示。

### 信号的四种来源

| 来源 | 例子 | 内核入口 |
|------|------|----------|
| 终端驱动 | Ctrl+C → `SIGINT`、Ctrl+Z → `SIGTSTP`、终端断开 → `SIGHUP` | 前台进程组广播 |
| 硬件异常 | 段错误 → `SIGSEGV`、除零 → `SIGFPE`、非法指令 → `SIGILL` | `force_sig_fault()`@`kernel/signal.c:1740` |
| 软件事件 | 定时器到期 → `SIGALRM`、管道对端关闭 → `SIGPIPE`、子进程退出 → `SIGCHLD` | 内核各子系统 |
| 进程显式 | `kill()` / `raise()` / `sigqueue()` | `SYSCALL_DEFINE2(kill)`@`kernel/signal.c:3807` |

---

## 二、信号生命周期：产生 → 未决 → 递送

这是理解全部信号语义的**主干**。任何一个信号都要走完这三步：

```
 ┌──────────┐    ┌──────────────┐    ┌──────────┐    ┌──────────────┐
 │  产生     │───▶│   未决        │───▶│  递送     │───▶│  处置执行     │
 │ generate │    │  pending     │    │ deliver  │    │  disposition │
 └──────────┘    └──────────────┘    └──────────┘    └──────────────┘
  内核在目标进程   已产生但尚未递送     进程被调度到       默认动作 /
  task_struct     （通常因为被阻塞）   返回用户态前       忽略 / handler
  置 pending 位                        取出并响应
```

### 阶段 1：产生（Generation）

内核在目标进程（或线程）的 `pending` 位图中把对应位置 1，并按需唤醒它：

```c
// kernel/signal.c:1225
int send_signal_locked(int sig, struct kernel_siginfo *info,
                       struct task_struct *t, enum pid_type type, bool force)
{
    ...
    return __send_signal_locked(sig, info, t, type, force);   // 真正写入 pending
}
```

```c
// kernel/signal.c:769
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
    set_tsk_thread_flag(t, TIF_SIGPENDING);   // 打上「有信号待处理」标记
    ...
}
```

> **关键点**：产生不等于递送。信号产生后可能在 pending 里待很久，直到目标进程解除阻塞。

### 阶段 2：未决（Pending）

信号已产生但尚未递送的状态，称为**未决**。原因通常只有一个：该信号被**阻塞**了（见 [20.10 信号掩码](20.10-the-signal-mask-blocking-signal-delivery.md)）。

未决信号存在两个层级：

| 层级 | 存放位置 | 含义 |
|------|----------|------|
| 线程私有 | `task_struct.pending` | 发给**特定线程**的信号（`tkill`/`tgkill`，或硬件异常） |
| 进程共享 | `signal_struct.shared_pending` | 发给**整个进程**的信号（`kill`/`killpg`），由任一线程取走 |

### 阶段 3：递送（Delivery）

**递送时机是本节最容易被误解的地方**：信号**不是**在任意一条用户指令中间插进来的，而是在**进程从内核态返回用户态之前**才被检查和处理。

```
   用户态执行中 ────────▶ (syscall / 中断 / 异常)
                              │
                              ▼
                        内核态处理
                              │
                              ▼
                    ✦ get_signal() 检查 pending ✦   ←── 递送发生在这里
                              │
                              ▼
                    返回用户态（先执行 handler，再回到被打断处）
```

核心函数是 `get_signal()`，它决定「取出哪个信号、做什么处置」：

```c
// kernel/signal.c:2660
bool get_signal(struct ksignal *ksig)
{
    ...
    for (;;) {
        // 从 pending 中取出一个未被阻塞的信号
        signr = dequeue_signal(current, &current->blocked, &ksig->info);
        ...
        // 取出后按 disposition 分派：默认 / 忽略 / handler
        if (ka->sa.sa_handler == SIG_DFL) {
            ...                          // 默认动作
        }
        ...
    }
}
```

> **推论**：如果一个进程阻塞在某个可中断的系统调用里（如 `read` 一个慢设备），信号的递送会把它唤醒并返回 `EINTR`——这正是 [Ch21.4 EINTR 与 SA_RESTART](../../chapter-21-signal-handlers/notes/21.4-the-sa-siginfo-flag.md) 要处理的问题。反过来，如果进程在**忙等**（纯用户态循环，不进内核），信号就**永远不会递送**。

## 三、三种处置（Disposition）

每个信号都有一个「处置」——即递送时该干什么：

| 处置 | 写法 | 内核行为 |
|------|------|----------|
| **默认** | `SIG_DFL` | 每种信号不同：终止 / 终止+core / 停止 / 继续 / 忽略（见 [20.2](20.2-signal-types-and-default-actions.md)） |
| **忽略** | `SIG_IGN` | 内核在 `sig_ignored()`@`kernel/signal.c:103` 判定后**直接丢弃**，连 pending 都不进 |
| **捕获** | 函数指针 | 递送时切到用户态执行 handler，返回后恢复被中断的执行流 |

### 阻塞 ≠ 忽略（高频混淆点）

| | **阻塞**（blocked） | **忽略**（`SIG_IGN`） |
|--|------|------|
| 信号抵达后 | 进 pending，**记着** | 直接丢弃，**忘了** |
| 解除阻塞后 | 会递送 | — |
| 本质 | 延迟递送 | 永不递送 |
| 设置方式 | `sigprocmask`（[20.10](20.10-the-signal-mask-blocking-signal-delivery.md)） | `signal(sig, SIG_IGN)` / `sigaction` |

---

## 四、两个无法干预的信号：`SIGKILL` 与 `SIGSTOP`

这两个信号**不能捕获、不能忽略、也不能阻塞**。这是内核的硬性设计保证——它是系统管理员和 watchdog 的**最后手段**。

内核在两处强制这一点：

```c
// kernel/signal.c:81 —— 判定某信号是否对该任务「被忽略」
static bool sig_task_ignored(struct task_struct *t, int sig, bool force)
{
    if (sigismember(&t->blocked, sig) || sigismember(&t->real_blocked, sig))
        return !force;      // force=true 时阻塞也拦不住
    ...
    return sig_handler_ignored(handler, sig);
}
```

而 `sig_handler_ignored()` 内部对 `SIGKILL`/`SIGSTOP` 一律返回「不可忽略」。同时 `sigprocmask` 设置掩码时也会**静默过滤掉**这两个信号：

```c
// kernel/signal.c:3094
int sigprocmask(int how, sigset_t *set, sigset_t *oldset)
{
    ...
    sigdelsetmask(&newset, sigmask(SIGKILL) | sigmask(SIGSTOP));  // 强制剔除
    ...
}
```

> **意义**：无论进程怎么写、怎么卡死（哪怕是 `while(1)` 死循环屏蔽了一切信号），`kill -9` 一定能杀死它；`kill -STOP` 一定能冻结它。这是运维的兜底保障。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 信号是 Linux 最轻量的进程级异步通知，嵌入式控制环常用它做「优雅停机」（`SIGTERM`）与「超时告警」（`SIGALRM`）；`SIGKILL`/`SIGSTOP` 不可捕获，是 watchdog 强制回收失控进程的最后保障。理解「递送在返回用户态前」这一点，才能解释为什么裸机 `while(1)` 循环里信号永不生效 |
| HFT | 信号是**异步抢占**，会打断正在跑的关键路径（报文解析 / spinloop），产生不可控延迟毛刺。更隐蔽的是：递送依赖「进入内核再返回」这一边界，纯用户态忙等的热路径**根本不会触发递送**，因此停机信号可能长时间不生效。HFT 主循环应屏蔽无关信号、只留 `SIGTERM`，其余交给 signalfd（[Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md)）统一进事件循环 |

## 代码示例：观察生命周期三阶段

```c
/* lifecycle.c —— 演示 产生 → 未决 → 递送
 * 编译: gcc -o lifecycle lifecycle.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

static volatile sig_atomic_t delivered = 0;
static void handler(int sig) { delivered = 1; }   /* 只写 sig_atomic_t，安全 */

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sigaction(SIGINT, &sa, NULL);

    sigset_t mask, pending;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);

    /* ── 阶段 2：阻塞 SIGINT，使其停留在「未决」 ── */
    sigprocmask(SIG_BLOCK, &mask, NULL);

    raise(SIGINT);                       /* 阶段 1：产生 */
    printf("generated, delivered=%d\n", delivered);

    sigpending(&pending);                /* 查询未决集 */
    printf("pending: %s\n",
           sigismember(&pending, SIGINT) ? "YES" : "NO");

    /* ── 阶段 3：解除阻塞 → 返回内核边界时递送 ── */
    sigprocmask(SIG_UNBLOCK, &mask, NULL);
    printf("after unblock, delivered=%d\n", delivered);

    /* 验证 SIGKILL / SIGSTOP 无法被阻塞：掩码被内核静默过滤 */
    sigset_t cur;
    sigemptyset(&cur);
    sigaddset(&cur, SIGKILL);
    sigprocmask(SIG_BLOCK, &cur, NULL);
    sigprocmask(SIG_BLOCK, NULL, &cur);
    printf("SIGKILL blocked? %s (内核强制剔除)\n",
           sigismember(&cur, SIGKILL) ? "YES" : "NO");
    return 0;
}
```

预期输出：

```
generated, delivered=0
pending: YES
after unblock, delivered=1
SIGKILL blocked? NO (内核强制剔除)
```

## 自测题

<details>
<summary><b>问 1：</b>信号递送发生在什么时刻？如果一个进程正在纯用户态忙等（不调用任何 syscall），信号能被递送吗？</summary>

递送发生在**进程从内核态返回用户态之前**，由 `get_signal()`@`kernel/signal.c:2660` 检查 pending 并分派处置。

纯用户态忙等时**不能**递送。因为递送的触发点是内核返回用户态的边界，没有进入内核就不会经过这个检查点。信号会一直停留在 pending 位图里，直到该进程因时间片耗尽被抢占、或主动发起 syscall / 触发缺页异常而进入内核。

这也是 HFT 忙等主循环收不到停机信号、必须用 signalfd 或轮询标志位的原因。

</details>

<details>
<summary><b>问 2：</b>「阻塞」和「忽略」有什么区别？各自用哪个接口设置？</summary>

**阻塞**：信号照常产生并记入 pending 位图，只是暂时不递送；解除阻塞后会补递送。用 `sigprocmask()` / `pthread_sigmask()` 设置掩码。

**忽略**：信号产生时内核在 `sig_ignored()`@`kernel/signal.c:103` 直接判定丢弃，**完全不进入 pending**，之后也无法找回。用 `signal(sig, SIG_IGN)` 或 `sigaction` 配合 `sa_handler = SIG_IGN` 设置。

一句话：阻塞是「延迟递送」，忽略是「永不递送」。

</details>

<details>
<summary><b>问 3：</b>为什么 <code>SIGKILL</code> 一定能杀死一个进程，即使它把所有信号都屏蔽了？</summary>

内核在两个层面做了硬性保证，用户态无法绕过：

1. `sigprocmask()`@`kernel/signal.c:3094` 在设置掩码时执行 `sigdelsetmask(&newset, sigmask(SIGKILL)|sigmask(SIGSTOP))`，**静默剔除**这两个信号位，所以掩码里根本存不进去。
2. `sig_handler_ignored()` 对 `SIGKILL`/`SIGSTOP` 一律拒绝忽略；`sig_task_ignored()` 在 `force=true` 时也会无视阻塞。

因此 `SIGKILL`/`SIGSTOP` 既不能捕获、不能忽略，也不能阻塞。这是运维和 watchdog 的兜底手段。

</details>

<details>
<summary><b>问 4：</b>线程的 pending 和进程的 pending 有何区别？各自装什么信号？</summary>

| 层级 | 存放位置 | 装的什么 |
|------|----------|----------|
| 线程私有 | `task_struct.pending` | 发给**特定线程**的信号：`tkill`/`tgkill`/`pthread_kill`，或硬件异常（`SIGSEGV`/`SIGFPE` 由当前线程触发） |
| 进程共享 | `signal_struct.shared_pending` | 发给**整个进程**的信号：`kill`/`killpg`/`raise`，由任一线程竞争取走 |

`sigpending()` 返回的是**两者之并集**（当前线程视角）。

这解释了一个常见现象：用 `kill` 给多线程进程发信号，可能由**任意一个**未阻塞该信号的线程执行 handler——所以多线程程序的正确姿势是在主线程统一 `pthread_sigmask` 屏蔽，再用 `sigwaitinfo` 专用线程消费。

</details>

<details>
<summary><b>问 5：</b>在信号处理函数里调用 <code>printf</code> 有什么问题？应该怎么做？</summary>

`printf` **不是异步信号安全函数**。它内部会操作 stdio 的全局缓冲区并可能调用 `malloc`（加锁）。如果主流程正执行 `printf` 持锁时信号递送，handler 再次调用 `printf` 会因**同一把锁重入而死锁**，或破坏缓冲区结构。

正确做法是在 handler 里只做最小动作——写一个 `volatile sig_atomic_t` 标志，或用 `write(2)`（异步信号安全）直写 fd：

```c
static volatile sig_atomic_t flag = 0;
static void handler(int sig) { flag = 1; }        /* 只写标志，安全 */

/* 或 */
static void handler(int sig) {
    write(STDOUT_FILENO, "caught\n", 7);          /* write 是 async-signal-safe */
}
```

完整的异步信号安全函数清单见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)。

</details>
