# 20.12 信号不排队

> 源码核验：Linux v6.6 · `kernel/signal.c`（`legacy_queue:1079` · `__send_signal_locked:1084` · `__sigqueue_alloc:414`）
> 本章：[TLPI 第 20 章 — Signals: Fundamental Concepts](../README.md)
> - 上一节：[20.11 待处理信号](./20.11-pending-signals.md)
> - 下一节：[20.13 改变信号处置：sigaction()](./20.13-changing-signal-dispositions-sigaction.md)

## 本节讲什么

1. **标准信号不排队**意味着什么——阻塞期间同号信号来 N 次，解除后只递送 1 次
2. 内核在哪一行把这个决定做掉的——`legacy_queue()` 的三行代码
3. 由此产生的**三个经典 bug**（尤其是 `SIGCHLD` 漏收），以及对应的正确写法

---

## 一、核心事实

| 信号类型 | 排队 | 阻塞期间来 N 次 | 解除后递送 |
|----------|------|----------------|-----------|
| **标准信号**（1–31） | ❌ **不排队** | pending 位图只有**一个位** | **1 次** |
| **实时信号**（`SIGRTMIN`+） | ✅ **排队** | 链表逐个挂接 | **N 次** |

> 准确的 POSIX 措辞是「**至少递送一次**」：标准信号不保证递送次数，只保证不丢得一个不剩。

---

## 二、内核根源：`legacy_queue()`

整个「不排队」特性由**三行代码**决定：

```c
// kernel/signal.c:1079
static inline bool legacy_queue(struct sigpending *signals, int sig)
{
	return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
}
```

在 `__send_signal_locked()`（`kernel/signal.c:1084`）里被调用：

```c
	pending = (type != PIDTYPE_PID) ? &t->signal->shared_pending : &t->pending;
	/*
	 * Short-circuit ignored signals and support queuing
	 * exactly one non-rt signal, so that we can get more
	 * detailed information about the cause of the signal.
	 */
	result = TRACE_SIGNAL_ALREADY_PENDING;
	if (legacy_queue(pending, sig))          // ← 1105：判定命中就直接返回
		goto ret;                             //    不分配、不排队、丢弃

	result = TRACE_SIGNAL_DELIVERED;
	...
	if (sig < SIGRTMIN)                      // ← 1124：标准信号
		override_rlimit = (is_si_special(info) || info->si_code >= 0);
	else
		override_rlimit = 0;

	q = __sigqueue_alloc(sig, t, GFP_ATOMIC, override_rlimit, 0);
	if (q) {
		list_add_tail(&q->list, &pending->list);   // ← 1132：实时信号挂链表
		...
	}
```

**判定逻辑拆解**：

| 条件 | 含义 |
|------|------|
| `sig < SIGRTMIN` | 是**标准信号** |
| `sigismember(&signals->signal, sig)` | 该信号**已经在 pending 位图里** |
| 两者同时成立 → `legacy_queue` 为真 | **直接丢弃这次发送，不排队** |

**实时信号为什么能排队**？因为它不满足 `sig < SIGRTMIN`，`legacy_queue` 返回假，于是继续往下走到 `__sigqueue_alloc()` + `list_add_tail()`——每次发送都分配一个 `struct sigqueue` 挂到链表尾部，逐个保留。

```
   标准信号（不排队）              实时信号（排队）
   位图                            位图 + 链表
   ┌──────────────┐               ┌──────────────┐
   │ SIGINT: 1 bit│               │ SIGRTMIN: 1  │
   │              │               ├──────────────┤
   │ 来 5 次 →    │               │ list: [q1] → [q2] → [q3] → [q4] → [q5]
   │ 仍是 1 bit   │               │                                     │
   └──────────────┘               └─────────────────────────────────────┘
   解除 → 递送 1 次                解除 → 递送 5 次（FIFO）
```

> **内核注释的额外信息**（`:1115-1123`）：实时信号如果用 `kill()` 发送，内核**尝试**也排队，但因为 `kill()` 不允许在内存不足时返回 `EAGAIN`，所以只能保证「至少一个信号递送成功」，可能丢掉 `info` 结构体。想确保完整排队，用 `sigqueue()`。

## 三、三个经典后果

| 场景 | 错误行为 | 正确做法 |
|------|----------|----------|
| **多个子进程同时退出** → 多个 `SIGCHLD` | 只递送 1 次，handler 只 `wait` 一个 → **其余子进程变僵尸** | handler 里 **`while (waitpid(-1, NULL, WNOHANG) > 0);`** 循环回收 |
| **用信号做事件计数** | `handler` 里 `count++` 会**漏计** | 改用 eventfd / 管道 / 共享内存原子计数器 |
| **阻塞期间高频同号信号** | 合并为一次，无法感知频率 | 改用实时信号 + `sigqueue`，或 signalfd |

### 陷阱 1：`SIGCHLD` 漏收（最常见）

```c
/* ❌ 错误：只回收一个子进程，其余变僵尸 */
void handler(int sig) {
    wait(NULL);
}

/* ✅ 正确：循环回收所有已退出的子进程 */
void handler(int sig) {
    int saved_errno = errno;                    /* 保护 errno */
    while (waitpid(-1, NULL, WNOHANG) > 0)
        ;                                       /* 一直收，直到没有可回收的 */
    errno = saved_errno;
}
```

**为什么必须循环**：

```
  t0: 子进程 A、B、C 几乎同时退出
  t1: 内核产生 3 次 SIGCHLD → 但 SIGCHLD 是标准信号，不排队
  t2: pending 位图里 SIGCHLD 位 = 1（只有一份）
  t3: handler 执行 → waitpid 只回收 1 个（比如 A）
  t4: B、C 永远无人回收 → 僵尸 ❌
```

**为什么必须用 `WNOHANG`**：否则如果还有子进程存活未退出，`waitpid` 会阻塞在 handler 里，整个进程卡死。

**为什么保护 `errno`**：handler 可能在主流程任意位置打断执行，若修改了 `errno`，主流程后续的错误判断会出错。这是异步信号安全编码的标准要求（详见 [Ch21.5](../../chapter-21-signal-handlers/notes/21.5-interruption-and-restarting-of-system-ca.md)）。

### 陷阱 2：用信号计数

```c
/* ❌ 完全不可靠 */
volatile sig_atomic_t count = 0;
void handler(int sig) { count++; }     /* 5 次信号可能只加 1 */
```

信号的设计定位是「**通知发生了某事**」，不是「**传递数据/计数**」。需要计数请用其他 IPC。

## 四、解决方案对照

| 需求 | 方案 | 说明 |
|------|------|------|
| 回收多个子进程 | `while (waitpid(-1, NULL, WNOHANG) > 0);` | 不依赖信号次数 |
| 精确事件计数 | **eventfd** / 管道 / 共享内存原子变量 | 天然支持计数，无丢失 |
| 需要排队 + 带数据 | **实时信号 + `sigqueue()`** | 见 [Ch22.8](../../chapter-22-signals-advanced/notes/22.8-realtime-signals.md) |
| 信号进事件循环 | **signalfd** | 见 [Ch22.11](../../chapter-22-signals-advanced/notes/22.11-fetching-signals-via-a-file-descriptor.md) |
| 同步逐个取信号 | **`sigwaitinfo()`** | 见 [Ch22.10](../../chapter-22-signals-advanced/notes/22.10-synchronously-waiting-for-a-signal.md) |

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 子进程管理**必须**用 `waitpid` + `WNOHANG` 循环，绝不能靠信号计数——否则僵尸进程累积最终耗尽进程表。嵌入式设备上进程数上限往往很小（`/proc/sys/kernel/threads-max`），僵尸累积会导致无法 fork 新进程，系统静默失效 |
| HFT | **绝不用信号传递行情事件**（会丢包）。信号只适合低频、幂等的控制事件（停机、重载配置）。HFT 内部通知应走共享内存原子变量 / eventfd / 无锁环形队列——这些机制天然支持高频、可计数、无丢失 |

## 代码示例：验证不排队

```c
/* noqueue.c —— 对比标准信号（不排队）与实时信号（排队）
 * 编译: gcc -o noqueue noqueue.c */
#define _GNU_SOURCE
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

#define N 5

static volatile sig_atomic_t std_count  = 0;   /* SIGUSR1：标准信号 */
static volatile sig_atomic_t rt_count   = 0;   /* SIGRTMIN：实时信号 */

static void std_handler(int sig) { std_count++; }
static void rt_handler(int sig)  { rt_count++; }

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_flags = SA_RESTART;
    sigemptyset(&sa.sa_mask);

    /* 标准信号 SIGUSR1 */
    sa.sa_handler = std_handler;
    sigaction(SIGUSR1, &sa, NULL);

    /* 实时信号 SIGRTMIN（必须用宏，不要硬编码 34） */
    sa.sa_handler = rt_handler;
    sigaction(SIGRTMIN, &sa, NULL);

    /* 同时阻塞两者 */
    sigset_t block, save;
    sigemptyset(&block);
    sigaddset(&block, SIGUSR1);
    sigaddset(&block, SIGRTMIN);
    sigprocmask(SIG_BLOCK, &block, &save);

    /* 各发 N 次 */
    for (int i = 0; i < N; i++) {
        raise(SIGUSR1);
        raise(SIGRTMIN);
    }

    /* 解除阻塞 → 观察递送次数 */
    sigprocmask(SIG_SETMASK, &save, NULL);

    printf("各发送 %d 次：\n", N);
    printf("  标准信号 SIGUSR1 (%d) : handler 执行 %d 次  ← 不排队\n", SIGUSR1,  (int)std_count);
    printf("  实时信号 SIGRTMIN(%d) : handler 执行 %d 次  ← 排队\n",   SIGRTMIN, (int)rt_count);
    return 0;
}
```

预期输出：

```
各发送 5 次：
  标准信号 SIGUSR1 (10) : handler 执行 1 次  ← 不排队
  实时信号 SIGRTMIN(34) : handler 执行 5 次  ← 排队
```

## 自测题

<details>
<summary><b>问 1：</b>「标准信号不排队」在内核里由哪几行代码决定？</summary>

由 `legacy_queue()` 及它的调用点决定：

```c
// kernel/signal.c:1079
static inline bool legacy_queue(struct sigpending *signals, int sig)
{
	return (sig < SIGRTMIN) && sigismember(&signals->signal, sig);
}
```

在 `__send_signal_locked()`（`kernel/signal.c:1084`）中：

```c
	result = TRACE_SIGNAL_ALREADY_PENDING;
	if (legacy_queue(pending, sig))       // ← :1105
		goto ret;                          //   命中则直接返回，不分配、不排队
```

**判定条件**：信号是标准信号（`sig < SIGRTMIN`）**且**该信号已在 pending 位图中 → 本次发送被丢弃。

**实时信号为什么能排队**：不满足 `sig < SIGRTMIN`，`legacy_queue` 返回假，继续往下执行 `__sigqueue_alloc()` + `list_add_tail(&q->list, &pending->list)`（`:1129-1132`），每次发送都新分配一个节点挂在链表尾。

</details>

<details>
<summary><b>问 2：</b>多个子进程同时退出，<code>SIGCHLD</code> handler 里只调用一次 <code>wait()</code> 会怎样？正确写法是什么？</summary>

**后果**：只有一个子进程被回收，**其余变成僵尸进程**，永久占用进程表项。

**原因**：`SIGCHLD`（17）是标准信号，**不排队**。三个子进程同时退出 → 三次 `SIGCHLD` → pending 位图中只有**一个位** → handler 只执行**一次** → `wait()` 只回收一个。

**正确写法**（三个要点缺一不可）：

```c
void handler(int sig) {
    int saved_errno = errno;                        /* ① 保护 errno */
    while (waitpid(-1, NULL, WNOHANG) > 0)          /* ② 循环 + WNOHANG */
        ;
    errno = saved_errno;                            /* ③ 恢复 errno */
}
```

| 要点 | 原因 |
|------|------|
| **`while` 循环** | 一次 handler 可能对应多个已退出子进程，必须全部收完 |
| **`WNOHANG`** | 若还有子进程存活未退出，不带 `WNOHANG` 的 `waitpid` 会**阻塞在 handler 里**，整个进程卡死 |
| **保护 `errno`** | handler 可能在主流程任意位置打断执行，修改 `errno` 会破坏主流程的错误判断 |
| **`-1`** | 表示回收**任意**子进程，而不是指定 PID |

</details>

<details>
<summary><b>问 3：</b>POSIX 对标准信号的准确措辞是什么？为什么说「至少递送一次」而不是「只递送一次」？</summary>

POSIX 的措辞是「**至少递送一次**」（at least once），而非「恰好一次」。

**原因**：从信号产生到 pending 位被检查之间存在**时间窗口**。考虑这个时序：

```
t0: 信号产生，pending 位置 1
t1: 内核递送该信号，清除 pending 位，执行 handler
t2: （handler 尚未返回）同一信号再次产生 → pending 位是空的 → 又置 1
t3: handler 返回
t4: 内核再次检查 pending → 发现又有一次 → 再递送一次
```

所以标准信号**可能**递送多次——只是**不保证**递送与产生次数相同。

**实践结论**：

- 不能假设「来 N 次递送 N 次」（会少）
- 也不能假设「来 N 次只递送 1 次」（可能多，取决于时序）
- 唯一能依赖的是「**至少递送一次**」

因此 handler 必须写成**幂等**的——重复执行不能出错。这也是 `SIGCHLD` handler 用 `while (waitpid(-1, ..., WNOHANG) > 0)` 循环的原因：无论递送几次，都能把当前所有可回收的子进程收干净。

</details>

<details>
<summary><b>问 4：</b>用 <code>kill()</code> 发送实时信号，能保证全部排队吗？</summary>

**不能保证**。内核注释明确说明了这一点（`kernel/signal.c:1115-1123`）：

```
 * Real-time signals must be queued if sent by sigqueue, or
 * some other real-time mechanism.  It is implementation
 * defined whether kill() does so.  We attempt to do so, on
 * the principle of least surprise, but since kill is not
 * allowed to fail with EAGAIN when low on memory we just
 * make sure at least one signal gets delivered and don't
 * pass on the info struct.
```

**要点**：

| 发送方式 | 排队保证 |
|----------|----------|
| `sigqueue()` | ✅ **必须排队**（POSIX 要求） |
| `kill()` | ⚠️ **尝试排队，但不保证**——内存不足时会退化为「至少一个递送成功」，且丢掉 `info` 结构体 |

**原因**：`kill()` 的接口契约不允许在内存不足时返回 `EAGAIN`（会破坏大量已有程序的错误处理逻辑），所以内核只能尽力而为。

**实践**：需要可靠排队 + 携带数据时，**一律用 `sigqueue()`**：

```c
union sigval val = { .sival_int = 42 };
sigqueue(pid, SIGRTMIN, val);
```

</details>

<details>
<summary><b>问 5：</b>如果我需要「精确的事件计数」，有哪些比信号更合适的机制？</summary>

信号的设计定位是「**通知发生了某事**」，不是「传递数据或计数」。需要计数时应换机制：

| 机制 | 特点 | 适合场景 |
|------|------|----------|
| **eventfd** | 内核维护 64 位计数器，`write` 累加、`read` 读取并清零；可被 `epoll` 监听 | 线程/进程间事件通知与计数，**最轻量**，HFT 首选 |
| **管道** | 每次事件写一个字节，读端计数 | 简单场景，需要 select/poll 集成 |
| **共享内存 + 原子变量** | 零系统调用，纯用户态原子操作 | **最低延迟**，HFT 热路径首选 |
| **无锁环形队列** | 可携带完整数据，SPSC/MPMC | 需要传数据而不仅是计数 |
| **实时信号 + `sigqueue`** | 可排队、可带一个 int | 必须用信号的场景（如跨进程且已有信号基础设施） |
| **signalfd** | 信号变 fd，可读出每一次 | 已有信号，但想用 epoll 统一处理 |

**HFT 建议**：内部高频通知走**共享内存原子变量**（零 syscall，最低延迟）或 **eventfd**（需进内核但极轻）；信号只留给低频、幂等的外部控制事件（停机、重载配置）。

</details>
