# 29.7 分离线程（`pthread_detach`）

> 源码核验：Linux v6.6 · `kernel/fork.c`（`copy_process():2240` · `set_child_tid` `:2347` · `clear_child_tid` `:2351` · `mm_release():1616` → TID 清零 `:1634` + `do_futex(FUTEX_WAKE,1)` `:1635` · `kernel_clone():2868`）· `kernel/exit.c`（`exit_notify():727` · 非 leader 恒 `autoreap` `:746-751` · `do_exit():809` · `do_group_exit():999` · `exit_group:1033`）· `kernel/signal.c`（`zap_other_threads():1378` · 遍历挂 SIGKILL `:1394-1395`）· `include/uapi/linux/sched.h`（`CLONE_CHILD_CLEARTID:24` · `CLONE_CHILD_SETTID:27` · `CLONE_PARENT_SETTID:23`）· glibc NPTL（`nptl/pthread_detach.c` 的 `joinid` CAS + `IS_DETACHED()` 判定；`nptl/allocatestack.c` 的 `__free_tcb()`）

## 本节讲什么

1. `pthread_detach()` 到底改了什么——答案是**它只改了 glibc 的一个标志位，内核完全不知道**
2. 三种设置方式的**竞态差异**：为什么「线程内自 detach」是唯一无竞态的写法
3. detach 之后资源由谁回收、什么时候回收、以及为什么 detached 线程**仍然会被主线程 `return` 拖死**

## 一、接口与语义

```c
#include <pthread.h>

int pthread_detach(pthread_t thread);
/* 返回 0 成功；失败返回正错误码（ESRCH / EINVAL），不设置 errno */
```

一句话语义：**告诉 pthread 库，这个线程终止时不需要任何人来收尸，你自己把栈和线程描述符回收掉。**

对照 29.6 的 `pthread_join`，两者是**互斥的两种回收契约**：

| | `pthread_join(t, &r)` | `pthread_detach(t)` |
|---|---|---|
| 阻塞调用者？ | **是**，直到 `t` 终止 | **否**，立即返回 |
| 取返回值？ | 可以（写进 `*retval`） | **不可以**，返回值被丢弃 |
| 谁回收资源？ | join 的线程（在 join 返回时） | **pthread 库**（在线程终止时） |
| 调用次数 | 每个线程**恰好一次** | 每个线程**至多一次**（重复 → `EINVAL`） |
| 能否再 join | —（join 完 `pthread_t` 作废） | **不能再 join**（`EINVAL`） |
| 能否知道何时结束 | 天然知道（join 返回即结束） | **不知道**，需要自己加同步 |

```
                    ┌──────────────────────────────────────┐
                    │        线程终止（return / exit）      │
                    └──────────────────┬───────────────────┘
                                       │
                     ┌─────────────────┴─────────────────┐
                     ↓                                   ↓
            【joinable 默认】                    【detached】
                     │                                   │
        内核 mm_release()：                   内核 mm_release()：
          put_user(0, &tid)                     put_user(0, &tid)
          futex_wake(&tid, 1)                   futex_wake(&tid, 1)
                     │                                   │  ← 无人等待，空转一次
                     ↓                                   ↓
        struct pthread 保留                  glibc start_thread 收尾：
        （栈 + TCB 不释放）                    __free_tcb(pd)
                     │                          → munmap 栈 + TCB
          等有人来 join …                                │
                     │                                   ↓
                     ↓                              资源全释放
        pthread_join 返回 → __free_tcb()             （进程无感知）
        → munmap 栈 + TCB
                     │
                     ↓
        没人来 join → 永久泄漏
        （VIRT/RSS 持续上涨）
```

## 二、内核视角：**Linux 内核里没有「分离线程」这个概念**

这是本节最反直觉、也最值钱的一条结论。

翻遍 `kernel/fork.c`、`kernel/exit.c`，你找不到任何与 detach 相关的标志。**内核的唯一职责**是 29.6 讲过的那一对动作：

```c
/* kernel/fork.c:1616 */
static void mm_release(struct task_struct *tsk, struct mm_struct *mm)
{
	if (tsk->clear_child_tid) {
		if (atomic_read(&mm->mm_users) > 1) {
			put_user(0, tsk->clear_child_tid);      /* ① TID 写 0 */
			do_futex(tsk->clear_child_tid, FUTEX_WAKE,
					1, NULL, NULL, 0, 0);           /* ② 唤醒 1 个等待者 */
		}
		tsk->clear_child_tid = NULL;
	}
}
```

这两步**无论线程是 joinable 还是 detached 都会执行**：

| 步骤 | joinable | detached |
|------|----------|----------|
| `put_user(0, &tid)` | 执行 | 执行 |
| `do_futex(..., FUTEX_WAKE, 1, ...)` | 执行，**唤醒 joiner** | 执行，**没有等待者，白跑一趟** |

所以 detach 的**全部实现都在 glibc 用户态**：

- glibc 的 `start_thread()` 在线程 start 函数返回后做收尾，检查线程描述符里的分离标志；
- 若已分离 → 直接 `__free_tcb(pd)`：`munmap` 掉线程栈和 `struct pthread`；
- 若可接合 → 保留 TCB，等 `pthread_join` 来取返回值并释放。

### 这条结论的三个推论

| # | 推论 | 后果 |
|---|------|------|
| ① | detach 不省内核资源 | 内核侧 `task_struct` 由 `exit_notify():746-751` 的 `autoreap` 立即回收，**两种状态一模一样** |
| ② | detach 省的是 glibc 用户态内存 | 每线程默认 8MB 栈（`struct pthread` 在栈底），不回收就是泄漏 |
| ③ | detached 线程退出仍有**一次多余的系统调用** | `do_futex()` 的空唤醒；量级 ~1μs，只在海量短命线程场景才需要考虑换成线程池 |

> **对照 29.6**：29.6 说「内核里根本没有僵尸线程」——现在可以补全了。
> 内核层的 `exit_notify()` 对非线程组 leader **恒 `autoreap = true`**，两态无差别；
> 所谓「僵尸线程」泄漏的永远是 **glibc 的 `struct pthread` + 8MB 用户栈**，与内核无关。

## 三、三种设置方式，以及它们的竞态差异

这是本节最实用的部分。三种写法**表面等价，竞态安全性完全不同**。

### 方式 ①：创建后由创建者 detach

```c
pthread_t t;
pthread_create(&t, NULL, worker, arg);
pthread_detach(t);              /* ← 这里和 worker 已经跑起来了，存在竞态窗口 */
```

**问题**：`pthread_create` 返回时新线程**可能已经跑完并终止**（29.3 讲过：新线程可能在 `create` 返回前就开始执行）。

不过对 detach 而言这个窗口**实践中是安全的**——因为：

- 线程终止时 glibc 不会释放 TCB（否则 join 就没法取返回值了），TCB 一直保留到 join 或 detach；
- `pthread_detach()` 内部会检查线程是否已处于退出流程，若是则**由 detach 自己负责释放 TCB**。

真正危险的是另一种情况：**线程终止 → 另一个线程 join 成功 → TCB 被释放 → `pthread_t` 被新线程复用了**，此时你的 `pthread_detach(t)` 作用在了一个**完全不相干的线程**上。这种用法本身（既 join 又 detach）就是错的，属于程序 bug。

### 方式 ②：线程内自 detach（**推荐**）

```c
void *worker(void *arg)
{
    pthread_detach(pthread_self());     /* ← 自己 detach 自己，零竞态 */
    /* ... */
    return NULL;
}
```

**为什么这是唯一无竞态的写法**：

- 执行这行代码时，**该线程必然还活着**（活线程才能执行代码）；
- 不存在「`pthread_t` 已被回收」的可能；
- 不依赖创建者是否记得调用 detach——**自包含**，把契约写进线程自己身上。

> **工程建议**：默认用方式 ②。理由和 RAII 一样——**资源的生命周期约定写在离资源最近的地方**，
> 不会随着调用点搬移而丢失。

### 方式 ③：创建时通过属性分离

```c
pthread_attr_t attr;
pthread_attr_init(&attr);
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
pthread_create(&t, &attr, worker, arg);
pthread_attr_destroy(&attr);
```

**这是最彻底的做法**：线程**从存在的第一微秒起**就是分离状态，中间没有任何「可接合」的时间窗。

- 优点：语义最干净，没有任何竞态，且**不需要额外的 `pthread_detach` 调用**（省一次用户态调用）；
- 缺点：`attr` 需要 `init`/`destroy` 配对（详见 29.8）；
- 注意：**属性对象是创建时的一次性快照**，`pthread_attr_destroy` 之后已建线程的状态不变。

### 三种方式对照

| 方式 | 竞态 | 是否需要额外调用 | 适用场景 |
|------|------|------------------|----------|
| ① 创建后 detach | 有窗口（实践中安全） | 是 | 创建后才决定要不要 detach（如按配置切换） |
| ② 自 detach | **无** | 是 | **通用默认**，尤其库代码里创建的线程 |
| ③ 属性创建即分离 | **无** | 否 | **性能敏感**、线程数量大、明确不需要 join |

> **HFT 视角**：方式 ③ 在热路径上少一次 `pthread_detach` 调用（glibc 里是一次 CAS + 可能的 `__free_tcb`），
> 更重要的是**消除了「线程跑完了但还没被 detach」这个不确定窗口**——在延迟敏感系统里，
> 「不确定」比「慢」更贵。

## 四、错误码与失败场景

| 错误码 | 触发条件 | 说明 |
|--------|----------|------|
| `0` | 成功 | — |
| `ESRCH` | 找不到 `thread` 对应的线程 | `pthread_t` 非法 / 已被回收 / 已被 join 过且 TCB 已释放 |
| `EINVAL` | `thread` **已经是分离状态** | 重复 detach；或该线程创建时就带了 `PTHREAD_CREATE_DETACHED` |

> **注意 `EINVAL` 的语义**：POSIX 说 "the thread is not a joinable thread"。
> 也就是说**重复 detach 一次会拿到 `EINVAL`**，而不是静默成功。
> 这一条可以用来**探测**一个线程当前的分离状态——但别依赖它，`pthread_t` 复用会让它说谎。

### 一个隐蔽的坑：detach 与 join 同时发生时，detach 可能**静默成功但什么也没做**

glibc 的 `pthread_detach` 核心逻辑是（符号级，语义等价）：

```c
/* glibc/nptl/pthread_detach.c（语义等价伪码） */
if (atomic_cas(&pd->joinid, /*new=*/pd, /*expected=*/NULL)) {
    /* CAS 失败：joinid 不是 NULL —— 说明已经有人 detach 或 join 了 */
    if (IS_DETACHED(pd))
        return EINVAL;      /* 已分离 → EINVAL */
    /* 否则：已经有人在 join 了 → 返回 0，但这次 detach 什么也没做！ */
} else {
    /* CAS 成功：标记为 detached */
    if (pd->cancelhandling & EXITING_BITMASK)
        __free_tcb(pd);     /* 线程已经跑完了 → 顺便把 TCB 释放掉 */
}
return 0;
```

`joinid` 字段的三态：

| `joinid` 值 | 含义 |
|-------------|------|
| `pd`（自身指针） | 可接合，无人等待 |
| `NULL` | 已被 detach（或已被 join 完成） |
| 其他线程的指针 | 某个线程正在 join |

关键点：**如果另一个线程已经在 `pthread_join(t)` 上，你的 `pthread_detach(t)` 会返回 0，但线程实际上并没有被分离**——它仍会被 join 走。

后果：代码里「看起来 detach 成功了」，于是你不再管理这个线程；同时 joiner 那边正常返回并取到返回值。这种「双方都以为自己赢了」的写法是竞态 bug 的温床。

**结论：一个线程要么由 A 负责 join，要么由 B 负责 detach，契约必须唯一且写在代码里。**

## 五、joinable vs detached 完整对照

| 维度 | joinable（默认） | detached |
|------|------------------|----------|
| 创建成本 | 相同 | 相同 |
| 内核 `task_struct` 回收 | `exit_notify()` autoreap，立即 | **完全相同** |
| TID 清零 + futex wake | 执行 | **执行**（空唤醒） |
| glibc `struct pthread` 回收 | 等 `pthread_join` | 线程终止时 `__free_tcb()` |
| 用户栈（默认 8MB）回收 | 等 `pthread_join` | 线程终止时 `munmap` |
| 返回值 | 可取 | **丢弃** |
| 忘记处理 | **泄漏 8MB/线程** | 无泄漏 |
| 能否 join | 能（一次） | 不能（`EINVAL`） |
| 能否得知终止时刻 | join 返回即知 | 需自建同步（条件变量 / 信号量 / 原子计数） |
| 进程退出时 | 未 join 的线程被丢弃 | 正在跑的线程**同样被杀** |

最后一行值得单独强调——这是最常见的误解：

> **detached 不等于「进程会等它」。**
> 主线程从 `main` `return`（或任意线程调用 `exit()`）依然会走
> `exit_group`（`kernel/exit.c:1033`）→ `do_group_exit():999` → `zap_other_threads()`（`kernel/signal.c:1378`）
> 给所有线程挂 `SIGKILL`（`:1394-1395`），detached 线程**一样被杀**。
> 想让主线程等所有 detached 线程跑完，必须**自己实现**等待（计数器 + 条件变量，或干脆用 joinable）。

## 六、什么时候该 detach，什么时候必须 join

### 决策表

| 场景 | 选择 | 理由 |
|------|------|------|
| 需要线程的计算结果 | **joinable** | 返回值只能通过 join 取 |
| 需要知道线程何时结束（做收尾/统计） | **joinable** | join 返回即同步点 |
| 火后即忘的一次性任务（异步日志、上报、清理） | **detached** | 不需要结果，不需要知道何时结束 |
| 生命周期与进程等长的工作线程（线程池 worker） | **joinable** | 关闭时要 join 做优雅退出（29.6 的批量 join） |
| 大量短命任务（>1000/s） | **都别用，上线程池** | 创建/销毁成本才是瓶颈，detach 只是「不泄漏」 |
| 库内部创建的隐藏线程（如监控、心跳） | **detached（方式②/③）** | 调用方不该感知，也不该负责 join |
| 需要 `pthread_cancel` + 清理处理函数配合 | **joinable** | 取消后通常还要 join 确认清理完成（Ch32） |
| 信号/事件驱动的常驻观察者 | **detached（方式③）** | 进程退出时随大流，不需要显式收尸 |

### 三条判定口诀

1. **要结果 → join**；不要结果 → detach
2. **要同步点 → join**；不要同步点 → detach
3. **拿不准 → join**。join 漏了会泄漏（可观测、可修复），detach 错了会丢数据（静默、难查）

## 七、常见错误清单

| # | 错误 | 症状 | 正解 |
|---|------|------|------|
| ① | detach 后又 `pthread_join` | `EINVAL` | 二选一，别都做 |
| ② | 重复 detach | 第二次 `EINVAL` | detach 前先确认契约唯一 |
| ③ | 误以为 detached 线程进程会等 | 输出被截断 | 自建同步或用 joinable |
| ④ | 用 `pthread_t` 做身份，线程终止后 detach | 可能 detach 到**新复用该地址的线程** | detach 之后立即作废 `pthread_t`（29.5） |
| ⑤ | 线程内 `exit()` | 整个进程没了 | 用 `return` / `pthread_exit()`（29.4） |
| ⑥ | 把 detach 当「降低优先级/后台化」 | 误解 | detach 只管回收，与调度无关（29.8 才管调度） |
| ⑦ | 库里创建 joinable 线程却不告知调用方 | 调用方无法回收 → 泄漏 | 库内部一律 detached，或暴露 join 接口 |
| ⑧ | 忽略 `pthread_detach` 返回值 | `ESRCH` 说明 `pthread_t` 已失效，静默通过会掩盖 bug | 至少 `assert(rc == 0)` |

## 八、HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **HFT** | **热路径上不创建线程**。行情/撮合/风控线程全部在启动阶段建好、joinable、绑核（29.8 + Ch35），运行期零 `pthread_create`/`detach`/`join` |
| **HFT** | detach 省的是用户态 8MB 栈，不是内核资源——别为了「省内核资源」去 detach，那是错误动机 |
| **HFT** | detached 线程退出时那次**空 futex 唤醒**是内核态开销（~1μs 量级）；海量短命线程场景用线程池把它彻底消掉 |
| **HFT** | 关停序列里**不要依赖 detached**：无法确认异步刷盘 / 日志线程是否已落盘。落盘这种「必须确认」的动作一定要 joinable + 带超时 join |
| **嵌入式** | 内存紧张（几十 MB）时 8MB/线程的栈是奢侈品：detach 只是保证回收，**栈本身要先调小**（29.8 的 `pthread_attr_setstacksize`，可到 16~64KB） |
| **嵌入式** | 无 MMU 的平台（uClinux）栈不按需分页，8MB 全是**实打实的物理内存**，detached 泄漏会直接 OOM |
| **嵌入式** | 长期运行的看门狗/心跳线程用方式 ③（属性创建即分离），启动即定型，运行期零管理调用 |

## 九、代码示例：`detach_demo.c`

```c
/* detach_demo.c — 29.7 分离线程：三种设置方式、错误码、竞态与生命周期
 *
 * 编译: gcc -O2 -Wall -o detach_demo detach_demo.c -pthread
 * 运行: ./detach_demo
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <pthread.h>
#include <sys/wait.h>       /* waitpid（演示 4/5 用 fork 隔离子进程） */

static pthread_mutex_t out_mu = PTHREAD_MUTEX_INITIALIZER;

static void say(const char *fmt, ...)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    char body[512];
    va_list ap;
    va_start(ap, fmt);
    vsnprintf(body, sizeof body, fmt, ap);
    va_end(ap);

    pthread_mutex_lock(&out_mu);
    fprintf(stderr, "[%7ld.%03ld] %s\n",
            (long)ts.tv_sec, ts.tv_nsec / 1000000, body);
    pthread_mutex_unlock(&out_mu);
}

static void errsay(const char *what, int rc)
{
    say("%s 失败: %d (%s)", what, rc, strerror(rc));
}

/* ───────────────────────────────────────────────────────────
 * 演示 1：创建者 detach（方式 ①）
 * ─────────────────────────────────────────────────────────── */
static void *worker_plain(void *arg)
{
    int id = *(int *)arg;
    say("  worker#%d: 开始工作", id);
    usleep(120 * 1000);
    say("  worker#%d: 结束（资源由 detach 契约回收）", id);
    return NULL;
}

static void demo_detach_by_creator(void)
{
    say("演示1: 创建者调用 pthread_detach（方式①）");
    static int id = 1;          /* static：避免主线程栈变量生命周期问题（29.3） */
    pthread_t t;
    int rc = pthread_create(&t, NULL, worker_plain, &id);
    if (rc) { errsay("pthread_create", rc); return; }

    rc = pthread_detach(t);
    if (rc) { errsay("pthread_detach", rc); return; }
    say("  主线程: detach 成功，不等它，去做别的事");

    usleep(60 * 1000);
    say("  主线程: 我干完别的了（此刻 worker 可能还没结束）");
    usleep(120 * 1000);         /* 给它留点时间，仅为演示输出完整 */
}

/* ───────────────────────────────────────────────────────────
 * 演示 2：线程内自 detach（方式 ②，推荐）
 * ─────────────────────────────────────────────────────────── */
static void *worker_self_detach(void *arg)
{
    int id = *(int *)arg;

    /* 第一行就 detach：此刻本线程必然存活 → 零竞态 */
    int rc = pthread_detach(pthread_self());
    say("  worker#%d: 自 detach 返回 %d（0=成功）", id, rc);

    usleep(80 * 1000);
    say("  worker#%d: 结束", id);
    return NULL;
}

static void demo_self_detach(void)
{
    say("演示2: 线程内 pthread_detach(pthread_self())（方式②，推荐）");
    static int id = 2;
    pthread_t t;
    int rc = pthread_create(&t, NULL, worker_self_detach, &id);
    if (rc) { errsay("pthread_create", rc); return; }
    usleep(150 * 1000);
}

/* ───────────────────────────────────────────────────────────
 * 演示 3：属性创建即分离（方式 ③）+ 验证 join 会失败
 * ─────────────────────────────────────────────────────────── */
static void *worker_quick(void *arg)
{
    (void)arg;
    say("  worker: 极短任务，跑完就走");
    return NULL;
}

static void demo_attr_detached(void)
{
    say("演示3: pthread_attr_setdetachstate(PTHREAD_CREATE_DETACHED)（方式③）");

    pthread_attr_t attr;
    int rc = pthread_attr_init(&attr);
    if (rc) { errsay("pthread_attr_init", rc); return; }

    rc = pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
    if (rc) { errsay("pthread_attr_setdetachstate", rc);
              pthread_attr_destroy(&attr); return; }

    pthread_t t;
    rc = pthread_create(&t, &attr, worker_quick, NULL);
    pthread_attr_destroy(&attr);            /* 属性对象是快照，销毁不影响已建线程 */
    if (rc) { errsay("pthread_create", rc); return; }

    /* 睡一会儿确保它已经终止 —— 然后试着 join，应该拿到 EINVAL */
    usleep(100 * 1000);

    void *res = (void *)0xdeadbeef;
    rc = pthread_join(t, &res);
    say("  对 detached 线程 pthread_join → rc=%d（%s）",
        rc, rc == EINVAL ? "EINVAL，符合预期" : strerror(rc));
}

/* ───────────────────────────────────────────────────────────
 * 演示 4：重复 detach 拿到 EINVAL
 * ─────────────────────────────────────────────────────────── */
static void *worker_long(void *arg)
{
    (void)arg;
    usleep(300 * 1000);
    return NULL;
}

static void demo_double_detach(void)
{
    say("演示4: 重复 detach 的返回值");
    pthread_t t;
    int rc = pthread_create(&t, NULL, worker_long, NULL);
    if (rc) { errsay("pthread_create", rc); return; }

    rc = pthread_detach(t);
    say("  第 1 次 detach → rc=%d（%s）", rc, rc ? strerror(rc) : "OK");

    rc = pthread_detach(t);
    say("  第 2 次 detach → rc=%d（%s）", rc, rc ? strerror(rc) : "OK");
    say("  ↑ 注意：这个线程还很活跃，所以是 EINVAL 而不是 ESRCH");

    usleep(350 * 1000);
}

/* ───────────────────────────────────────────────────────────
 * 演示 5：detached 不能替代同步 —— 主线程 return 照样拖死它
 * ─────────────────────────────────────────────────────────── */
static void *worker_slow(void *arg)
{
    (void)arg;
    for (int i = 0; i < 10; i++) {
        say("  slow worker: 第 %d 步", i);
        usleep(50 * 1000);
    }
    say("  slow worker: 全部完成");
    return NULL;
}

static void demo_detached_not_sync(void)
{
    say("演示5: detached 线程依然会被主线程 return 拖死");
    say("  （放在子进程里跑：子进程 170ms 后就 _exit，观察 slow worker 是否跑完）");

    pid_t pid = fork();
    if (pid == 0) {
        pthread_t t;
        int rc = pthread_create(&t, NULL, worker_slow, NULL);
        if (rc) { errsay("pthread_create", rc); _exit(1); }
        rc = pthread_detach(t);
        if (rc) { errsay("pthread_detach", rc); _exit(1); }

        usleep(170 * 1000);                 /* 只等 170ms，slow worker 需要 500ms */
        say("  子进程: 我要 return 了 —— slow worker 才跑完 3/10 步");
        _exit(0);                           /* 等价于从 main return */
    }

    int st = 0;
    waitpid(pid, &st, 0);
    say("  ↑ slow worker 在第 3 步戛然而止：detach ≠ 进程会等它");
    say("    内核路径: exit_group(kernel/exit.c:1033) → do_group_exit():999");
    say("             → zap_other_threads()(kernel/signal.c:1378，挂 SIGKILL)");
}

/* 计数器 + 条件变量：这才是 detached 线程的正确等待方式 */
static pthread_mutex_t cnt_mu = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  cnt_cv = PTHREAD_COND_INITIALIZER;
static int running = 0;

static void *worker_counted(void *arg)
{
    int id = *(int *)arg;
    usleep(100 * 1000);
    say("  counted worker#%d: 完成", id);

    pthread_mutex_lock(&cnt_mu);
    if (--running == 0)
        pthread_cond_signal(&cnt_cv);       /* 最后一个完成的负责通知 */
    pthread_mutex_unlock(&cnt_mu);
    return NULL;
}

static void demo_wait_detached_properly(void)
{
    say("演示6: 用计数器 + 条件变量正确等待 detached 线程");
    enum { N = 4 };
    static int ids[N];
    pthread_t t[N];

    running = N;
    for (int i = 0; i < N; i++) {
        ids[i] = i;
        pthread_attr_t attr;
        pthread_attr_init(&attr);
        pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
        if (pthread_create(&t[i], &attr, worker_counted, &ids[i]) != 0)
            say("  create %d 失败", i);
        pthread_attr_destroy(&attr);
    }

    pthread_mutex_lock(&cnt_mu);
    while (running > 0)                     /* while 防虚假唤醒 */
        pthread_cond_wait(&cnt_cv, &cnt_mu);
    pthread_mutex_unlock(&cnt_mu);
    say("  主线程: 4 个 detached 线程全部确认完成");
}

/* ───────────────────────────────────────────────────────────
 * 演示 7：joinable 忘 join 的泄漏可观测（VIRT 上涨）
 * ─────────────────────────────────────────────────────────── */
static void *noop(void *arg) { (void)arg; return NULL; }

static void dump_statm(const char *tag)
{
    FILE *f = fopen("/proc/self/statm", "r");
    if (!f) return;
    long size = 0, resident = 0;
    if (fscanf(f, "%ld %ld", &size, &resident) == 2)
        say("  %-22s VIRT=%ld MB  RSS=%ld MB",
            tag, size * 4 / 1024, resident * 4 / 1024);
    fclose(f);
}

static void demo_leak_check(void)
{
    say("演示7: joinable 忘 join vs detach —— 用 /proc/self/statm 观察");
    enum { N = 30 };
    pthread_t t[N];

    dump_statm("起始");

    for (int i = 0; i < N; i++)
        pthread_create(&t[i], NULL, noop, NULL);
    for (int i = 0; i < N; i++)
        pthread_join(t[i], NULL);           /* 全部正常 join */
    dump_statm("join 30 个后");

    for (int i = 0; i < N; i++) {
        pthread_create(&t[i], NULL, noop, NULL);
        /* 故意不 join 也不 detach */
    }
    usleep(100 * 1000);
    dump_statm("泄漏 30 个后");
    say("  ↑ VIRT 明显上涨（每线程 8MB 栈 + TCB 不回收）");

    for (int i = 0; i < N; i++)
        pthread_join(t[i], NULL);           /* 亡羊补牢：补 join 即可回收 */
    dump_statm("补 join 后");
    say("  ↑ 补 join 立刻回落 —— 泄漏的是 glibc 资源，不是内核资源");
}

int main(void)
{
    say("=== 29.7 分离线程演示 ===");

    demo_detach_by_creator();
    demo_self_detach();
    demo_attr_detached();
    demo_double_detach();
    demo_detached_not_sync();
    demo_wait_detached_properly();
    demo_leak_check();

    say("=== 演示结束 ===");
    return 0;
}
```

## 代码自测

<details>
<summary>1. `pthread_detach` 在内核里做了什么？</summary>

**什么都没做——内核里根本没有 detach 这个概念。**

内核对每个线程（无论 joinable 还是 detached）都在 `mm_release()`（`kernel/fork.c:1616`）里做同一对动作：

1. `put_user(0, tsk->clear_child_tid)`（`:1634`）—— 把用户态 TID 写 0
2. `do_futex(..., FUTEX_WAKE, 1, ...)`（`:1635`）—— 唤醒 1 个等待者

差别只在用户态：

- **joinable**：有 joiner 睡在这个 futex 上，被唤醒后取返回值，glibc 调 `__free_tcb()` 释放栈 + `struct pthread`
- **detached**：没有等待者，这次 futex 唤醒是空转；线程的 `start_thread()` 收尾代码自己调 `__free_tcb()` 直接释放

另外内核的 `exit_notify()`（`kernel/exit.c:727`）在 `:746-751` 对**非线程组 leader 恒 `autoreap = true`**，所以 `task_struct` 本身在两种状态下都是立即回收的。

**所以 detach 省的是 glibc 的 8MB 用户栈 + TCB，不是内核资源。** 想省内核资源是错误动机。
</details>

<details>
<summary>2. 为什么「线程内 `pthread_detach(pthread_self())`」是唯一零竞态的写法？</summary>

因为**能执行这行代码的线程必然还活着**。

| 方式 | 竞态窗口 |
|------|----------|
| ① 创建者 detach | `pthread_create` 返回时新线程**可能已经跑完**（29.3：新线程可能在 create 返回前就开始执行）。虽然 glibc 会保留 TCB 使 detach 仍有效，但若期间有别的线程 join 走并释放了 TCB，`pthread_t` 可能被新线程复用，detach 会作用到错误对象 |
| ② 自 detach | **无窗口**：线程正在执行代码 ⟹ 它没终止 ⟹ TCB 一定有效 |
| ③ 属性创建即分离 | **无窗口**：线程从存在的第一刻起就是 detached，中间不存在「可接合」状态 |

② 的额外好处是**自包含**——契约写在线程自己身上，不会因为调用点搬移而丢失（类似 RAII）。库代码里创建的隐藏线程应当一律用 ② 或 ③。
</details>

<details>
<summary>3. 一个线程已经被 `pthread_join` 走了，此时再对它 `pthread_detach`，会返回什么？</summary>

**返回 0，但什么也没分离成功。** 这是 glibc 实现里最阴的一个点。

`pthread_detach` 的核心是 `joinid` 字段的 CAS（语义等价）：

```c
if (atomic_cas(&pd->joinid, pd, NULL)) {
    if (IS_DETACHED(pd)) return EINVAL;   /* 已分离 → 明确报错 */
    /* 否则：已有人在 join → 静默返回 0，本次 detach 无效 */
}
return 0;
```

`joinid` 的三态：`pd`（可接合、无人等待）/ `NULL`（已分离或已 join 完成）/ 其他线程指针（有人正在 join）。

当别人在 join 时，CAS 失败，`IS_DETACHED` 为假 → **返回 0**。

**后果**：调用方以为 detach 成功了，于是不再管理这个线程；而 joiner 那边照常取到返回值并释放资源。双方都以为自己赢了。

**结论：一个线程的回收契约必须唯一**——要么固定由 A join，要么固定由 B detach，写进代码并注释清楚，不要两边都留后手。

**对照错误码**：

- `EINVAL` = 线程已经是分离状态（重复 detach）
- `ESRCH` = 找不到该线程（`pthread_t` 已失效 / 已被 join 过且 TCB 已释放）
</details>

<details>
<summary>4. detached 线程在进程退出时会被等待吗？</summary>

**不会。detach 只解决「资源回收」，不提供任何「等待」语义。**

主线程从 `main` `return`（或任意线程调用 `exit()`）时：

```
main return
  → exit()
  → exit_group 系统调用（kernel/exit.c:1033）
  → do_group_exit()                    kernel/exit.c:999
  → zap_other_threads()                kernel/signal.c:1378
       遍历线程组，给每个线程挂 SIGKILL         :1394-1395
  → 所有线程（joinable 和 detached 一视同仁）被杀
```

**验证方式**：`detach_demo` 的演示 5 —— `slow worker` 计划跑 10 步（500ms），主线程 170ms 就 return，输出戛然而止在第 3 步。

**正确做法**（如果确实需要等 detached 线程）：自建同步，演示 6 给的是标准方案：

```c
/* worker 结尾 */
pthread_mutex_lock(&cnt_mu);
if (--running == 0)
    pthread_cond_signal(&cnt_cv);      /* 最后一个完成的负责通知 */
pthread_mutex_unlock(&cnt_mu);

/* 主线程 */
pthread_mutex_lock(&cnt_mu);
while (running > 0)                    /* while 防虚假唤醒 */
    pthread_cond_wait(&cnt_cv, &cnt_mu);
pthread_mutex_unlock(&cnt_mu);
```

> **HFT 提醒**：如果「必须确认完成」（如落盘、风控对账），**不要**用 detached + 手工计数器，
> 直接用 joinable + `pthread_timedjoin_np()` 带超时 join（29.6 第六节）。
> 少一层手写同步就少一处 bug，而且 join 自带返回值通道。
</details>

<details>
<summary>5. 生产代码里 detach 的使用清单（HFT / 嵌入式双视角）</summary>

| # | 规则 | 为什么 |
|---|------|--------|
| ① | **热路径不创建线程** | 行情/撮合/风控线程在**启动阶段**建好，运行期零 `pthread_create`/`detach`/`join`。detach 再便宜也不如不创建 |
| ② | **长驻工作线程用 joinable** | 关闭时要 `pthread_timedjoin_np` 带超时做优雅退出（29.6）。detached 无法确认收尾 |
| ③ | **一次性火后即忘任务用方式③ detached** | 属性创建即分离：省一次调用，且从第一刻起就是 detached，无中间状态 |
| ④ | **库内部隐藏线程用方式② detached** | 自包含，调用方不需要知道也不能负责回收 |
| ⑤ | **必须确认的动作一律 joinable** | 落盘、对账、清理 —— detached 丢得静悄悄 |
| ⑥ | **detach 之前先调小栈** | 嵌入式/海量线程场景，8MB 栈才是真开销。detach 只保证回收，不减少持有（29.8 的 `pthread_attr_setstacksize`） |
| ⑦ | **detach 之后立即作废 `pthread_t`** | 栈地址会被复用（29.5），保留它等于埋雷 |
| ⑧ | **永远检查 detach 返回值** | `ESRCH` 说明 `pthread_t` 已失效 —— 这是 bug 信号，不是可以吞掉的噪音 |
| ⑨ | **超过 1000 次/秒的短命任务上线程池** | detach 只解决「不泄漏」，不解决「创建贵」；而且每次 detached 退出还有一次空 futex 唤醒 |
| ⑩ | **无 MMU 平台（uClinux）栈是实打实的物理内存** | 8MB/线程会直接 OOM，先调栈再谈 detach |
</details>
