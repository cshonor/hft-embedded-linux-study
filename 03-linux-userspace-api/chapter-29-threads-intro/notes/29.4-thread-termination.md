## 本节讲什么

1. 线程的**五种**终止方式，以及哪种会**拖死整个进程**
2. `exit()` / `pthread_exit()` / 从 `main()` `return` 三者的**本质区别**——这是最高频的踩坑点
3. 为什么线程退出**不产生僵尸**、为什么**不能**用 `wait()` 回收线程（内核 `exit_notify()` 的 autoreap 分支）

## 一、五种终止方式

```c
#include <pthread.h>

void pthread_exit(void *retval);        /* 终止【当前线程】，可带返回值 */
```

| # | 方式 | 终止范围 | 说明 |
|---|------|----------|------|
| ① | `start_routine` **return** | 仅当前线程 | 返回值即退出状态（等价于 `pthread_exit(retval)`） |
| ② | `pthread_exit(retval)` | **仅当前线程** | 任意位置调用都行，包括主线程 |
| ③ | `pthread_cancel(tid)` | 目标线程（**请求**，非强制） | 详见 [Ch32](../../chapter-32-thread-cancellation/README.md) |
| ④ | 任一线程调 **`exit(status)`** | **整个进程**（所有线程） | ⚠️ 走 `exit_group` |
| ⑤ | 主线程从 **`main()` return** | **整个进程**（所有线程） | ⚠️ 等价于 `exit()` |

**关键差异图**：

```
  线程 A 调 pthread_exit()          线程 A 调 exit()
         │                                 │
         ▼                                 ▼
  ┌─────────────────┐              ┌─────────────────────────┐
  │ 只有 A 结束      │              │ do_group_exit()          │
  │ B、C 继续跑      │              │   └─ zap_other_threads() │
  │ 进程继续存活     │              │        → 给 B、C 挂 SIGKILL│
  └─────────────────┘              │ 全部线程结束，进程终止     │
                                   └─────────────────────────┘
```

## 二、`exit()` 是怎么「杀光所有线程」的

`exit()` 在 glibc 里调用的是 **`exit_group`** 系统调用（不是老的 `exit`）：

```c
/* kernel/exit.c:1033 */
SYSCALL_DEFINE1(exit_group, int, error_code)
{
	do_group_exit((error_code & 0xff) << 8);
	/* NOTREACHED */
	return 0;
}
```

```c
/* kernel/exit.c:999 */
void __noreturn
do_group_exit(int exit_code)
{
	struct signal_struct *sig = current->signal;

	if (sig->flags & SIGNAL_GROUP_EXIT)
		exit_code = sig->group_exit_code;        /* 已有人发起，沿用它的退出码 */
	else if (sig->group_exec_task)
		exit_code = 0;
	else {
		struct sighand_struct *const sighand = current->sighand;

		spin_lock_irq(&sighand->siglock);
		if (sig->flags & SIGNAL_GROUP_EXIT)
			/* Another thread got here before we took the lock.  */
			exit_code = sig->group_exit_code;
		else if (sig->group_exec_task)
			exit_code = 0;
		else {
			sig->group_exit_code = exit_code;
			sig->flags = SIGNAL_GROUP_EXIT;      /* ① 打标记 */
			zap_other_threads(current);          /* ② 干掉其他人 */
		}
		spin_unlock_irq(&sighand->siglock);
	}

	do_exit(exit_code);                              /* ③ 自己也死 */
	/* NOTREACHED */
}
```

而 `zap_other_threads()` 的手段非常直接——**给每个其他线程挂一个 `SIGKILL`**：

```c
/* kernel/signal.c:1378 */
int zap_other_threads(struct task_struct *p)
{
	struct task_struct *t = p;
	int count = 0;

	p->signal->group_stop_count = 0;

	while_each_thread(p, t) {                        /* 遍历线程组 */
		task_clear_jobctl_pending(t, JOBCTL_PENDING_MASK);
		if ((t->flags & (PF_IO_WORKER | PF_USER_WORKER)) != PF_USER_WORKER)
			count++;

		/* Don't bother with already dead threads */
		if (t->exit_state)
			continue;
		sigaddset(&t->pending.signal, SIGKILL);   /* ← 挂 SIGKILL */
		signal_wake_up(t, 1);                     /* ← 唤醒它去处理 */
	}

	return count;
}
```

**为什么这样就一定能杀死它们？** 因为 `SIGKILL` 有「三道不可干预的防线」（见 [Ch20.2](../../chapter-20-signals-fundamentals/notes/20.2-signal-types-and-default-actions.md)）：

1. **改不了处置**——`sigaction(SIGKILL, ...)` 返回 `-EINVAL`（`do_sigaction():4129`）
2. **阻塞不了**——`sigprocmask` 静默剔除（`set_current_blocked():3064`）
3. **handler 期间也屏蔽不了**——内核静默剔除（`do_sigaction():4161`）

所以被挂上 `SIGKILL` 的线程**必然**在下次返回用户态（或被唤醒）时执行默认动作：终止。

> ⚠️ 唯一的例外是 **`TASK_UNINTERRUPTIBLE`（D 状态）** 的线程——
> `signal_wake_up()` 只能唤醒 `state | TASK_INTERRUPTIBLE` 的任务，
> D 状态的线程**叫不醒**，信号只是挂在 pending 上等它自己醒。
> 这就是「进程卡死，`kill -9` 也杀不掉」的原因（见 [Ch22.3](../../chapter-22-signals-advanced/notes/22.3-interruptible-and-uninterruptible-proces.md)）。

### `group_dead`：谁来决定「整个进程结束了」

```c
/* kernel/exit.c:836 */
	group_dead = atomic_dec_and_test(&tsk->signal->live);
	if (group_dead) {
		/* ... 收尾：acct、coredump、释放 signal_struct ... */
	}
```

`signal->live` 是线程组里**存活线程数的引用计数**。每死一个线程减一，
减到 0 才代表「整个进程没了」，此时才做进程级收尾（记账、coredump、`exit_notify` 通知父进程）。

```
  线程组 4 个线程，live = 4
    A 退出 → live = 3  group_dead = false  → 只做线程级清理
    B 退出 → live = 2  group_dead = false
    C 退出 → live = 1  group_dead = false
    D 退出 → live = 0  group_dead = TRUE   → 进程级收尾 + 通知父进程
```

**实践含义**：**最后一个线程（不一定是主线程）退出时，父进程才收到 `SIGCHLD`**。
如果主线程 `pthread_exit()` 了但 worker 还在跑，父进程的 `wait()` 会一直阻塞。

## 三、为什么线程退出不产生僵尸

这是「线程」和「进程」在退出语义上最本质的差异，看 `exit_notify()`：

```c
/* kernel/exit.c:727 */
static void exit_notify(struct task_struct *tsk, int group_dead)
{
	bool autoreap;
	...
	tsk->exit_state = EXIT_ZOMBIE;                    /* 先假定要变僵尸 */
	if (unlikely(tsk->ptrace)) {
		int sig = thread_group_leader(tsk) &&
				thread_group_empty(tsk) &&
				!ptrace_reparented(tsk) ?
			tsk->exit_signal : SIGCHLD;
		autoreap = do_notify_parent(tsk, sig);
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&         /* ① 只有最后一个线程 */
			do_notify_parent(tsk, tsk->exit_signal);
	} else {
		autoreap = true;                              /* ② 普通线程：直接自动回收 */
	}

	if (autoreap) {
		tsk->exit_state = EXIT_DEAD;                  /* ← 不是 ZOMBIE，是 DEAD */
		list_add(&tsk->ptrace_entry, &dead);
	}
	...
	list_for_each_entry_safe(p, n, &dead, ptrace_entry) {
		list_del_init(&p->ptrace_entry);
		release_task(p);                              /* 立即释放 task_struct */
	}
}
```

**两条分支的含义**：

| 情况 | `autoreap` | 结果 |
|------|-----------|------|
| 普通线程（非线程组 leader） | **恒为 `true`** | 直接 `EXIT_DEAD` → 立即 `release_task()`，**从不进僵尸态** |
| 线程组 leader + `thread_group_empty()` | 取决于父进程是否 `SA_NOCLDWAIT`/`SIG_IGN` | 正常僵尸流程 |
| 线程组 leader + 还有别的线程 | `false` | **保持僵尸态等着**，等其他线程死完 |

配合另一条——`CLONE_THREAD` 时 `exit_signal = -1`（`fork.c:2632`）——
**线程退出根本不会给父进程发 `SIGCHLD`**。

### 实践推论

| 推论 | 说明 |
|------|------|
| **不能用 `wait()` 回收线程** | 线程不发 `SIGCHLD`，`wait()` 永远等不到；而且线程根本不进僵尸态 |
| **必须用 `pthread_join()` 或 `pthread_detach()`** | 二选一，否则线程的资源（栈、`task_struct`）不释放 |
| **「僵尸线程」的真相** | 严格说不存在内核僵尸线程。所谓"僵尸线程"指的是**可接合（joinable）的线程结束了但没人 join**——此时 **glibc 层的线程描述符和 8MB 栈不会释放**，但内核的 `task_struct` 已经回收了 |

```
  可接合线程结束但没人 join 时的状态：

    内核层：task_struct 已释放 ✓（exit_notify 的 autoreap）
    glibc 层：struct pthread + 8MB 栈【仍然保留】✗（等 join 来取返回值）

  → 长期运行的进程里反复这样，会【泄漏虚拟内存】，
    表现为 VIRT 不断上涨，最终 pthread_create 返回 EAGAIN
```

**这就是「必须 join 或 detach」的真正原因**——不是内核资源，是 glibc 的用户态资源。

```
$ top -p <pid>       # 看 VIRT 列
$ cat /proc/PID/status | grep Threads
```

## 四、返回值

```c
void pthread_exit(void *retval);
int  pthread_join(pthread_t thread, void **retval);
```

| 场景 | `pthread_join` 拿到的 `retval` |
|------|-------------------------------|
| `start_routine` `return p;` | `p` |
| `pthread_exit(p);` | `p` |
| 线程被 `pthread_cancel()` | **`PTHREAD_CANCELED`**（通常是 `(void *) -1`） |
| 线程是被 `exit()` 杀掉的 | 拿不到（进程已终止） |

⚠️ **`retval` 绝不能指向线程的栈**——线程结束后栈就没了：

```c
/* ✗ 致命：返回指向自己栈上变量的指针 */
static void *worker(void *arg)
{
    int result = 42;
    return &result;            /* ← 线程结束，栈释放，这个指针变野 */
}

int main(void)
{
    void *r;
    pthread_join(t, &r);
    printf("%d\n", *(int *)r);   /* 未定义行为 */
}

/* ✓ 三种正确做法 */
static int g_result;                       /* ① 全局变量 */
static void *w1(void *a) { g_result = 42; return &g_result; }

static void *w2(void *a) { return (void *)(intptr_t)42; }   /* ② 整数编码 */

static void *w3(void *a) {                 /* ③ 动态分配，join 方负责 free */
    int *p = malloc(sizeof(int));
    *p = 42;
    return p;
}
```

## 五、主线程 `pthread_exit()` 的特殊性

```c
int main(void)
{
    pthread_create(&t, NULL, worker, NULL);

    pthread_exit(NULL);       /* ← 主线程结束，但【进程继续】，worker 继续跑 */
    /* 不会到达这里 */
}
```

对比：

| 主线程怎么结束 | 结果 |
|---------------|------|
| `return 0;` | **等价 `exit(0)`** → 全进程终止，worker 被 `zap_other_threads` 杀掉 |
| `exit(0)` | 全进程终止 |
| `pthread_exit(NULL)` | **只有主线程终止**，其他线程继续，进程存活直到最后一个线程结束 |

**为什么 `main()` return 等价于 `exit()`？**

因为 C 运行时（glibc 的 `__libc_start_main`）大致是这样调用 main 的：

```c
/* glibc 的 __libc_start_main() 简化 */
int result = main(argc, argv, envp);
exit(result);          /* ← main 返回后自动调 exit()，而 exit = exit_group */
```

**什么时候需要主线程 `pthread_exit()`？**

当主线程只是"起完线程就没事干"时，用它比 `pthread_join` 所有线程更简洁：

```c
int main(void)
{
    for (int i = 0; i < N; i++)
        pthread_create(&t[i], NULL, worker, NULL);

    /* 主线程任务完成，让 worker 继续跑，自己先退 */
    pthread_exit(NULL);
}
```

不过**更推荐显式 `pthread_join`**——这样能拿到返回值、能确认所有线程都结束了，
而且 `main` 的返回值语义（退出码）更清晰。

```c
int main(void)
{
    for (int i = 0; i < N; i++)
        pthread_create(&t[i], NULL, worker, NULL);

    int failures = 0;
    for (int i = 0; i < N; i++) {
        void *r;
        pthread_join(t[i], &r);
        if (r == PTHREAD_CANCELED) failures++;
    }
    return failures ? 1 : 0;        /* 明确的进程退出码 */
}
```

## 六、线程退出时的自动清理（futex 唤醒）

glibc 创建线程时给了 `CLONE_CHILD_CLEARTID`，所以线程退出时内核会**自动**做两件事：

```c
/* kernel/fork.c:1628-1638 */
static void mm_release(struct task_struct *tsk, struct mm_struct *mm)
{
	...
	if (tsk->clear_child_tid) {
		if (atomic_read(&mm->mm_users) > 1) {          /* 还有别的线程在跑 */
			/* We don't check the error code - if userspace has
			 * not set up a proper pointer then tough luck. */
			put_user(0, tsk->clear_child_tid);      /* ① TID 写 0 */
			do_futex(tsk->clear_child_tid, FUTEX_WAKE,
					1, NULL, NULL, 0, 0);          /* ② 唤醒 1 个等待者 */
		}
		tsk->clear_child_tid = NULL;
	}
	...
}
```

这就是 `pthread_join()` 能"感知"线程结束的机制（详见 [29.6](29.6-joining-with-a-terminated-thread.md)）：

```
  join(tid):
      读线程描述符里的 tid 字段
      while (tid != 0)
          futex_wait(&tid, 当前值)          ← 睡，不轮询
      /* 线程退出 → 内核: tid = 0 + futex_wake(&tid, 1) */
      → 被唤醒，读返回值，释放资源
```

另外 `futex_exit_release()`（`kernel/fork.c:1651`，在 `exit_mm_release()` 里调用）
会处理 **robust futex**（`set_robust_list`）——如果线程持锁时死了，
内核会替它解锁并唤醒等待者，避免其他线程永久阻塞。详见 [Ch30](../../chapter-30-thread-synchronization/README.md)。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **长期运行的守护进程里，忘记 join/detach 会持续泄漏 8MB 栈/线程**，在 256MB 设备上几十次就撑爆虚拟地址空间 → 表现为 `pthread_create` 突然返 `EAGAIN`。**线程池 + 创建即 detached** 是标准解法。② 主线程 `return` 拖死所有 worker 是嵌入式最常见的"服务莫名退出"原因之一——日志里没有任何错误，因为进程是正常退出的。③ **优雅退出顺序**：先通知 worker（条件变量/标志位）→ join 等它们落盘 → 主线程再 `return`。直接 `exit()` 会丢数据 |
| HFT | ① **关键路径绝不能调 `exit()`**——它会 `zap_other_threads()` 给所有线程挂 SIGKILL，正在处理的订单/持仓状态全部丢失，且**不产生 core**（SIGKILL 不在 `SIG_KERNEL_COREDUMP_MASK` 里，见 [Ch22.1](../../chapter-22-signals-advanced/notes/22.1-core-dump-files.md)）。② **关闭序列必须显式编排**：`SIGTERM` → 主循环置停止标志 → 撤单 → 落盘 → join 所有 worker → `return`。③ **最后一个线程退出父进程才收到 SIGCHLD**，所以监控进程（supervisor）的 `wait()` 会比"主线程退出"晚很多——别用主线程的退出时间做超时判据。④ **D 状态线程会卡住整个退出流程**：`zap_other_threads` 挂的 SIGKILL 叫不醒它，进程会卡在 `exit_group` 里变成僵尸。诊断：`ps -eo pid,stat,wchan` 看 `D` 状态。⑤ 想要崩溃留现场，用 `abort()`（产生 core）而不是 `exit()` |

## 代码示例：五种终止方式的实测

```c
/* thread_exit_demo.c —— 线程/进程的五种终止方式
 *
 * 编译: gcc -Wall -Wextra -O2 -pthread -o ted thread_exit_demo.c
 * 用法: ./ted            → 演示 pthread_exit（只终止当前线程）
 *       ./ted exit       → 演示 exit()（杀光所有线程）
 *       ./ted return     → 演示 main return（等价 exit）
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>
#include <string.h>
#include <stdint.h>
#include <signal.h>
#include <pthread.h>
#include <unistd.h>
#include <errno.h>
#include <sys/syscall.h>

static pid_t gettid_(void) { return (pid_t)syscall(SYS_gettid); }

static pthread_mutex_t out = PTHREAD_MUTEX_INITIALIZER;
static void say(const char *fmt, ...)
{
    va_list ap; va_start(ap, fmt);
    pthread_mutex_lock(&out);
    vprintf(fmt, ap); fflush(stdout);
    pthread_mutex_unlock(&out);
    va_end(ap);
}

/* ── worker：跑 5 秒，看它能不能跑完 ─────────────── */
static volatile sig_atomic_t stop = 0;

static void *worker_noop(void *arg)      /* 什么都不做，立刻返回 */
{
    (void)arg;
    return NULL;
}

static void *worker(void *arg)
{
    long id = (long)arg;
    for (int i = 0; i < 10; i++) {
        if (stop) break;
        say("    worker %ld (tid=%d): 第 %d 次\n", id, gettid_(), i + 1);
        sleep(1);
    }
    say("    worker %ld: 正常结束\n", id);
    return (void *)(intptr_t)(100 + id);      /* 返回值：整数编码，安全 */
}

/* ── 演示 1：pthread_exit 只终止当前线程 ───────────── */
static void demo_pthread_exit(void)
{
    pthread_t t1, t2;
    void *r1, *r2;

    say("\n【演示 1】worker 用 return / pthread_exit 结束\n");
    pthread_create(&t1, NULL, worker, (void *)1L);
    pthread_create(&t2, NULL, worker, (void *)2L);

    pthread_join(t1, &r1);
    pthread_join(t2, &r2);
    say("  join 拿到返回值: r1=%ld r2=%ld  （ PTHREAD_CANCELED=%p ）\n",
        (long)(intptr_t)r1, (long)(intptr_t)r2, PTHREAD_CANCELED);
    say("  → 进程继续存活，main 继续往下走\n");
}

/* ── 演示 2：exit() 杀光所有线程 ─────────────────── */
static void *long_worker(void *arg)
{
    (void)arg;
    for (int i = 0; i < 60; i++) {
        say("    long_worker (tid=%d): %d 秒\n", gettid_(), i);
        sleep(1);
    }
    return NULL;      /* 永远到不了 */
}

static void demo_exit(void)
{
    pthread_t t;

    say("\n【演示 2】worker 还在跑，主线程 3 秒后调 exit()\n");
    pthread_create(&t, NULL, long_worker, NULL);

    sleep(3);
    say("  主线程: 调 exit(0) —— 所有人一起死\n");
    exit(0);
    /* long_worker 的 60 次循环永远跑不完 */
}

int main(int argc, char **argv)
{
    say("主线程: pid=%d tid=%d\n", getpid(), gettid_());

    if (argc > 1 && strcmp(argv[1], "exit") == 0) {
        demo_exit();                      /* 演示 2：exit 杀光所有 */
    } else if (argc > 1 && strcmp(argv[1], "return") == 0) {
        pthread_t t;
        say("\n【演示 3】main return —— 等价 exit()，worker 被杀\n");
        pthread_create(&t, NULL, long_worker, NULL);
        sleep(3);
        say("  主线程: return 0\n");
        return 0;                         /* ← 等价于 exit(0) */
    } else if (argc > 1 && strcmp(argv[1], "mainexit") == 0) {
        pthread_t t;
        void *r;
        say("\n【演示 4】主线程 pthread_exit —— 进程【继续存活】\n");
        pthread_create(&t, NULL, long_worker, NULL);
        pthread_join(t, &r);              /* 这里会等 60 秒 */
        say("  join 返回，main 结束\n");
        return 0;
    }

    /* 默认：演示 1 */
    demo_pthread_exit();

    /* 演示：可接合线程不 join 的资源泄漏（观察 /proc/self/status 的 VmSize）*/
    say("\n【演示 5】忘记 join/detach 的后果（看 VIRT 上涨）\n");
    {
        FILE *f;
        char line[256];
        unsigned long vmsize_before = 0, vmsize_after = 0;

        f = fopen("/proc/self/status", "r");
        while (fgets(line, sizeof(line), f))
            if (strncmp(line, "VmSize:", 7) == 0) sscanf(line + 7, "%lu", &vmsize_before);
        fclose(f);

        for (int i = 0; i < 50; i++) {
            pthread_t leak;
            pthread_create(&leak, NULL, worker_noop, NULL);   /* 从不 join */
        }
        sleep(1);

        f = fopen("/proc/self/status", "r");
        while (fgets(line, sizeof(line), f))
            if (strncmp(line, "VmSize:", 7) == 0) sscanf(line + 7, "%lu", &vmsize_after);
        fclose(f);

        say("  50 个未 join 的线程: VmSize %lu KB → %lu KB (+%lu KB)\n",
            vmsize_before, vmsize_after, vmsize_after - vmsize_before);
        say("  → 内核 task_struct 已回收，但 glibc 的栈【没释放】\n");
    }

    say("\n全部演示结束，main 返回\n");
    return 0;
}
```

**预期输出要点**：

```
$ ./ted
主线程: pid=12345 tid=12345
【演示 1】worker 用 return / pthread_exit 结束
    worker 1 (tid=12346): 第 1 次
    worker 2 (tid=12347): 第 1 次
    ...
  join 拿到返回值: r1=101 r2=102  （ PTHREAD_CANCELED=0xffffffffffffffff ）
  → 进程继续存活

【演示 5】50 个未 join 的线程: VmSize 23456 KB → 434567 KB (+411111 KB)
  → 内核 task_struct 已回收，但 glibc 的栈【没释放】

$ ./ted exit
  ... 3 秒后 ...
  主线程: 调 exit(0) —— 所有人一起死
$                          ← 立刻退出，long_worker 没有"正常结束"输出
```

<summary><b>问 1：</b>主线程从 <code>main()</code> <code>return</code> 和调 <code>pthread_exit()</code>，结果有什么不同？为什么？</summary>

| | `return 0;` 从 main | `pthread_exit(NULL)` 从 main |
|---|---|---|
| **worker 线程** | **被杀掉**（`zap_other_threads` 挂 SIGKILL） | **继续运行** |
| **进程** | 立即终止 | 存活到最后一个线程结束 |
| **父进程收到 SIGCHLD** | 立即 | 等最后一个线程退出 |
| **退出码** | `main` 的返回值 | 由最后调用 `exit` 的线程决定 |

**原因**：C 运行时（glibc 的 `__libc_start_main`）在 `main` 返回后自动调 `exit()`：

```c
/* glibc __libc_start_main 简化 */
int result = main(argc, argv, envp);
exit(result);          /* ← main 一返回就调 exit()，而 exit = exit_group */
```

而 `exit()` → `exit_group` 系统调用 → `do_group_exit()`（`kernel/exit.c:999`）：

```c
		sig->group_exit_code = exit_code;
		sig->flags = SIGNAL_GROUP_EXIT;
		zap_other_threads(current);          /* ← 给所有其他线程挂 SIGKILL */
	...
	do_exit(exit_code);
```

`zap_other_threads()`（`kernel/signal.c:1378`）的手段是直接挂 `SIGKILL`：

```c
		sigaddset(&t->pending.signal, SIGKILL);
		signal_wake_up(t, 1);
```

而 `SIGKILL` 无法被捕获、忽略、阻塞（三道防线），所以线程必死。

`pthread_exit()` 则不同——它只调 `do_exit()`（单线程版），
**不走 `do_group_exit`**，所以不影响别人。

**一个重要的推论**：最后一个线程退出时，父进程才收到 `SIGCHLD`。

```c
/* kernel/exit.c:836 */
	group_dead = atomic_dec_and_test(&tsk->signal->live);
```

`signal->live` 是存活线程计数。主线程 `pthread_exit()` 后它还没归零，
所以 `exit_notify()` 不会通知父进程（`kernel/exit.c:746-747`）：

```c
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&      /* ← 还有其他线程就 false */
			do_notify_parent(tsk, tsk->exit_signal);
```

**实践**：写守护进程时，如果主线程只负责起 worker，
用 `pthread_exit()` 会让监控进程的 `wait()` 迟迟收不到信号。
更清晰的做法是主线程**显式 join 所有 worker 再 return**。

</details>

<details>
<summary><b>问 2：</b>为什么不能用 <code>wait()</code> 回收线程？「僵尸线程」到底是什么？</summary>

### 为什么 `wait()` 不行：三道障碍

**① 线程退出时不发 `SIGCHLD`**

```c
/* kernel/fork.c:2632-2633 */
		if (clone_flags & CLONE_THREAD)
			p->exit_signal = -1;        /* 线程退出不通知父进程 */
```

`wait()` 依赖 `SIGCHLD` 才知道"有子进程状态可取"。线程压根不发，
所以 `wait()` 永远阻塞（或返回 `ECHILD`，因为压根没有"子进程"）。

**② 线程根本不进僵尸态**

```c
/* kernel/exit.c:746-751 */
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&
			do_notify_parent(tsk, tsk->exit_signal);
	} else {
		autoreap = true;                /* ← 非 leader（普通线程）恒为 true */
	}

	if (autoreap) {
		tsk->exit_state = EXIT_DEAD;    /* ← DEAD 不是 ZOMBIE */
		list_add(&tsk->ptrace_entry, &dead);
	}
	...
	release_task(p);                    /* 立即释放 task_struct */
```

普通线程是 `autoreap = true` → 直接 `EXIT_DEAD` → 立即 `release_task()`。
**内核层根本不保留它的退出状态**，也就无从 `wait()`。

**③ 唯一例外**：线程组 leader 且还有其他线程存活时，leader 会保持僵尸态
（`autoreap = false`）等着，等其他线程死完再统一通知父进程。
但这是"进程级"的僵尸，不是"线程级"的。

### 「僵尸线程」的真相

严格来说**内核里没有僵尸线程**。常见说法里的"僵尸线程"指的是：

> **可接合（joinable）的线程结束了，但没人 `pthread_join()` 它。**

此时：

```
  内核层：  task_struct 已释放 ✓（autoreap 生效）
  glibc 层：struct pthread + 8MB 栈【仍然保留】✗
            （因为退出返回值要留给 join 来取）
```

**症状**：长期运行的服务反复"创建 → 不 join → 结束"，
虚拟内存（VIRT / `VmSize`）持续上涨（每线程 8MB），
最终 `pthread_create` 返回 `EAGAIN`：

```bash
cat /proc/PID/status | grep VmSize     # 观察是否持续上涨
top -p <pid>                            # 看 VIRT 列
```

**修法（二选一）**：

```c
/* ① 需要返回值 → join */
void *r;
pthread_join(t, &r);

/* ② 不需要返回值 → detach（或创建时指定）*/
pthread_detach(t);

pthread_attr_t attr;
pthread_attr_init(&attr);
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
pthread_create(&t, &attr, w, NULL);      /* 创建即分离，不给竞态留窗口 */
pthread_attr_destroy(&attr);
```

详见 [29.6](29.6-joining-with-a-terminated-thread.md) 与 [29.7](29.7-detaching-a-thread.md)。

</details>

<details>
<summary><b>问 3：</b><code>zap_other_threads()</code> 为什么一定能杀死其他线程？有没有杀不掉的情况？</summary>

**一定能杀死（绝大多数情况）**，因为它用的是 `SIGKILL`：

```c
/* kernel/signal.c:1378 */
int zap_other_threads(struct task_struct *p)
{
	struct task_struct *t = p;
	int count = 0;

	p->signal->group_stop_count = 0;

	while_each_thread(p, t) {
		task_clear_jobctl_pending(t, JOBCTL_PENDING_MASK);
		if ((t->flags & (PF_IO_WORKER | PF_USER_WORKER)) != PF_USER_WORKER)
			count++;

		/* Don't bother with already dead threads */
		if (t->exit_state)
			continue;
		sigaddset(&t->pending.signal, SIGKILL);      /* ← 挂 SIGKILL */
		signal_wake_up(t, 1);                        /* ← 唤醒它处理 */
	}

	return count;
}
```

`SIGKILL` 有**三道不可干预的防线**（见 [Ch20.2](../../chapter-20-signals-fundamentals/notes/20.2-signal-types-and-default-actions.md)）：

| 防线 | 内核位置 | 行为 |
|------|----------|------|
| 改不了处置 | `do_sigaction():4129` | `sig_kernel_only(sig)` → 返回 `-EINVAL` |
| 阻塞不了 | `set_current_blocked():3064` | `sigdelsetmask(newset, SIGKILL\|SIGSTOP)` → **静默剔除** |
| handler 期间屏蔽不了 | `do_sigaction():4161` | `sa_mask` 里的 SIGKILL 被**静默剔除** |

所以被挂 `SIGKILL` 的线程**必然**在下次返回用户态时执行默认动作 = 终止。

### 杀不掉的例外：`TASK_UNINTERRUPTIBLE`（D 状态）

`signal_wake_up()` 只能唤醒**状态位匹配**的任务：

```c
/* kernel/signal.c:769 */
void signal_wake_up_state(struct task_struct *t, unsigned int state)
{
	set_tsk_thread_flag(t, TIF_SIGPENDING);

	if (!wake_up_state(t, state | TASK_INTERRUPTIBLE))
		kick_process(t);
	/*                    ^^^^^^^^^^^^^^^^^^^^ 只有 INTERRUPTIBLE 位能被唤醒 */
}
```

| 线程状态 | 能被 `signal_wake_up` 唤醒？ |
|----------|---------------------------|
| `TASK_INTERRUPTIBLE:87` | ✅ |
| `TASK_KILLABLE:116` | ✅（仅致命信号） |
| **`TASK_UNINTERRUPTIBLE:88`** | ❌ **叫不醒** |

**后果**：如果某个线程卡在 D 状态（等坏掉的磁盘/NFS、驱动 bug），
`exit_group()` 会**永远等它**，进程变成僵尸，父进程的 `wait()` 也不返回。

```
  $ ps -eo pid,ppid,stat,wchan:30,comm
    PID  PPID STAT  WCHAN                          COMMAND
   1234  1200 D     nfs_wait_bit_killable          myapp      ← 卡住的那个
   1234  1200 Z     -                              myapp      ← 变成僵尸（如果有其他线程死完）
```

诊断与处理：

```bash
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'   # 找 D 状态
cat /proc/PID/stack                               # 需要 root，看卡在哪个内核函数
dmesg | tail -50                                  # 找 I/O error / NFS timeout
```

硬件不恢复就只能重启。**这也是嵌入式设备必须有硬件 watchdog 的原因**。

> 还有一类「软」例外：`PF_USER_WORKER`（io_uring 的 worker）会被**跳过**
> （`zap_other_threads` 里 `count` 不计数，但仍会挂 SIGKILL；
> 代码里 `(t->flags & (PF_IO_WORKER | PF_USER_WORKER)) != PF_USER_WORKER` 的判断
> 只影响返回值 `count`，不影响挂信号）。

</details>

<details>
<summary><b>问 4：</b>线程的返回值为什么不能指向它自己的栈？</summary>

因为**线程结束后，它的栈就被释放了**。

```c
/* ✗ 致命 */
static void *worker(void *arg)
{
    (void)arg;
    int result = 42;
    return &result;            /* 指向自己栈上的局部变量 */
}

int main(void)
{
    void *r;
    pthread_create(&t, NULL, worker, NULL);
    pthread_join(t, &r);
    printf("%d\n", *(int *)r);   /* ✗ 未定义行为：栈已释放，可能已被 mmap 复用 */
}
```

```
  时间线：
    worker 运行，&result = 0x7f8a4c000e8c
    worker 返回 → 线程结束 → glibc munmap 这 8MB 栈
    join 返回，r = 0x7f8a4c000e8c   ← 指向已释放的地址
    读 *r → 可能是垃圾，也可能 SIGSEGV，也可能"碰巧还是 42"（最危险）
```

第三种子情况最危险：**本地测试一直正确（栈还没被复用），生产环境偶发错误数据**。

**三种正确做法**：

```c
/* ① 整数直接编码进指针（最省事，无内存管理问题）*/
static void *w1(void *a)
{
    (void)a;
    return (void *)(intptr_t)42;
}
/* 取值：int v = (int)(intptr_t)r; */

/* ② 返回值放在全局变量或调用方提供的缓冲区里 */
static int g_result;
static void *w2(void *a) { (void)a; g_result = 42; return &g_result; }

/* 传调用方的缓冲区（最常用）*/
struct job { int result; /* ... */ };
static void *w3(void *a)
{
    struct job *j = a;
    j->result = 42;              /* 写进调用方提供的内存 */
    return NULL;
}

/* ③ 动态分配，join 的一方负责 free */
static void *w4(void *a)
{
    (void)a;
    int *p = malloc(sizeof(int));
    *p = 42;
    return p;                    /* 调用方必须 free */
}
int main(void) {
    void *r;
    pthread_join(t, &r);
    printf("%d\n", *(int *)r);
    free(r);                     /* ← 别忘了 */
}
```

**判断规则**：`pthread_exit`/`return` 的返回值指针，
指向的内存必须在**线程结束之后依然有效**——
即：全局/静态内存、堆内存、或调用方提供的缓冲区。**绝不能是线程自己的栈**。

> 这个规则同样适用于 `pthread_cleanup_push` 的清理函数和任何跨线程传递的指针。
> 核心就是 [29.3](29.3-thread-creation.md) 讲的**生命周期覆盖原则**。

</details>

<details>
<summary><b>问 5：</b>写一个「优雅关闭」的多线程服务，正确的退出序列是什么？</summary>

**反例（最常见的错误）**：

```c
/* ✗ SIGTERM handler 里直接 exit() —— 数据全丢 */
static void on_term(int sig)
{
    (void)sig;
    cleanup();          /* ✗ 非 async-signal-safe，可能死锁 */
    exit(0);            /* ✗ zap_other_threads 杀光所有线程，正在处理的订单丢失 */
}
```

`zap_other_threads()` 给每个线程挂 `SIGKILL`，它们**没有机会**做任何清理——
撤单、落盘、关连接全都来不及。而且 `SIGKILL` 不在 `SIG_KERNEL_COREDUMP_MASK` 里，
**连 core 都不会产生**，事后无法复盘。

**正确的序列**（信号只置标志，实际动作在主循环的安全点做）：

```c
#define _GNU_SOURCE
#include <signal.h>
#include <pthread.h>
#include <stdatomic.h>

static volatile sig_atomic_t g_stop = 0;
static atomic_int g_term_count = 0;

/* ① handler 只置标志 —— 唯一允许做的事 */
static void on_term(int sig)
{
    (void)sig;
    int n = atomic_fetch_add(&g_term_count, 1) + 1;
    if (n >= 2) {
        /* 第二次：强制退出（优雅关闭卡住了）*/
        const char m[] = "第二次 SIGTERM → 强制退出\n";
        write(STDERR_FILENO, m, sizeof(m) - 1);      /* 只调 async-signal-safe */
        _exit(128 + sig);                            /* 用 _exit 不用 exit */
    }
    g_stop = 1;                                       /* 第一次：请求优雅停止 */
}

/* ② worker 定期检查停止标志，在自己的安全点退出 */
static void *worker(void *arg)
{
    (void)arg;
    while (!g_stop) {
        process_one_batch();          /* 处理一批，边界清晰 */
    }
    /* 到这里说明收到停止请求，做自己的清理 */
    flush_my_buffers();
    return NULL;
}

/* ③ 主循环编排整个关闭序列 */
int main(void)
{
    pthread_t workers[N];

    install(SIGTERM, on_term, SA_RESTART);
    install(SIGINT,  on_term, SA_RESTART);

    for (int i = 0; i < N; i++)
        pthread_create(&workers[i], NULL, worker, NULL);

    /* 主循环：等停止信号 */
    while (!g_stop)
        do_supervision();

    /* ── 优雅关闭序列（在普通上下文，随便加锁/调库）── */
    log("开始优雅关闭");

    /* ① 停止接受新工作（关门）*/
    stop_accepting();

    /* ② 等 worker 处理完手上的活并自行清理 */
    for (int i = 0; i < N; i++)
        pthread_join(workers[i], NULL);        /* 能拿返回值、能超时 */

    /* ③ 业务层清理：撤单、落盘、关连接 */
    cancel_pending_orders();
    persist_state();
    close_connections();

    /* ④ 最后才 return（触发 exit_group，此时已无其他线程）*/
    log("已退出");
    return 0;
}
```

**关键设计点**：

| 要点 | 为什么 |
|------|--------|
| handler **只置标志** | `printf`/`malloc`/锁在 handler 里都不安全；`exit()` 会杀光所有线程 |
| worker **自己检查标志并清理** | 每个线程最清楚自己手上有什么资源 |
| **先停止接收，再 join** | 否则关闭期间还会进来新工作，永远关不完 |
| **join 而不是 detach** | 需要确认每个线程都真的结束了 |
| **第二次信号强制退出** | 优雅关闭可能卡住（撤单超时），运维需要一条强制通路 |
| **用 `_exit()` 不用 `exit()`** | 强制路径上不该跑 atexit/冲刷 stdio（可能死锁） |
| 想留 core 用 `abort()` | `exit()` 和 `SIGKILL` 都不产生 core |

**顺序图**：

```
  SIGTERM → handler: g_stop = 1
                         │
  主循环检测到 g_stop ────┤
       │                  │
       ▼                  └──→ worker 检测到 g_stop → 清自己的缓冲 → return
  ① stop_accepting()
       │
       ▼
  ② pthread_join × N        ← 等所有人
       │
       ▼
  ③ cancel_pending_orders()
     persist_state()
     close_connections()
       │
       ▼
  ④ return → exit_group（此时只剩主线程，无害）
```

> **HFT 特别提示**：关闭序列里的每一步都要有**超时和降级**。
> 撤单超时（比如 500ms）就记录告警并继续，不能让整个关闭流程卡死——
> 否则运维只能 `kill -9`，那才是最糟的结果。

</details>
