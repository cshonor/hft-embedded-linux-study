## 本节讲什么

1. Pthreads 的**返回值约定**：返回错误码而不是设 `errno`——这是它和几乎所有其他 UNIX API 的**相反之处**，也是最高频的 bug 来源
2. 编译链接要 `-pthread` 而不是 `-lpthread`，以及**为什么**（glibc 2.34 之后 `-lpthread` 变成了空壳）
3. `pthread_t` 为什么是不透明的、为什么必须用 `pthread_equal()` 比较

## 一、Pthreads 是什么：标准、实现、命名

| 层次 | 内容 |
|------|------|
| **标准** | POSIX.1c-1995（线程扩展）→ POSIX.1-2001 纳入主体。定义**接口语义**，不规定实现 |
| **Linux 实现** | NPTL（glibc 2.3.2+），依赖内核 `CLONE_THREAD` / `CLONE_SETTLS` / `CLONE_CHILD_CLEARTID` / futex（见 [29.1](29.1-overview.md) 第五节） |
| **头文件** | `#include <pthread.h>` |
| **命名规律** | `pthread_` + 对象 + 动作，如 `pthread_mutex_lock`、`pthread_cond_wait`、`pthread_attr_setstacksize` |

**关键区分**：Pthreads 是 **POSIX 标准定义的 API**，不是 Linux 专有的。
Windows 上有 pthreads-win32，macOS/FreeBSD 原生支持。
但**底层实现机制完全不同**——Linux 用 `clone()`，FreeBSD 历史上用过 `rfork()` / 调度器激活。

> 本书 TLPI 讲的是 Linux 上的 NPTL 行为。有些细节（如线程栈默认大小、`SCHED_OTHER` 下的调度）
> 是 Linux 特有的，不要当成 POSIX 保证。

## 二、编译：`-pthread` 而不是 `-lpthread`

```bash
gcc -Wall -Wextra -O2 -pthread -o prog prog.c      # ← 正确
gcc -o prog prog.c -lpthread                        # ← 过时/不够
```

**`-pthread` 做三件事，`-lpthread` 只做一件（而且现在几乎是空的）**：

| | `-pthread` | `-lpthread` |
|---|------------|-------------|
| 定义 `_REENTRANT` | ✅（历史上用于启用可重入库函数） | ❌ |
| 影响代码生成（TLS 访问模型等） | ✅ 传给编译器 | ❌ 只传给链接器 |
| 链接线程库 | ✅ | ✅ |

### ⚠️ glibc 2.34 之后 `-lpthread` 已经是个空壳

glibc 2.34（2021-08）把 `libpthread.so` 的全部符号**合并进了 `libc.so.6`**：

```bash
$ ldd ./prog           # glibc >= 2.34 编译出的程序
	linux-vdso.so.1
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
	/lib64/ld-linux-x86_64-linux-gnu.so.2
# ← 没有 libpthread.so！所有 pthread_* 符号都在 libc 里

$ ldd ./old_prog       # 老系统上
	libpthread.so.0 => /lib/x86_64-linux-gnu/libpthread.so.0   ← 多这一行
```

现在的 `libpthread.so` / `libpthread.a` 只是**空的存根**（stub），保留它是为了向后兼容——
老程序链接它不会失败，但里面什么都没有。

**实践建议**：

- 新代码一律用 `-pthread`（CMake 用 `find_package(Threads)` + `Threads::Threads`，它会自动展开成 `-pthread`）
- 遇到链接错误 `undefined reference to pthread_create`：说明你只写了 `-lpthread` 但顺序不对，或者用了静态链接而存根库是空的 → **换成 `-pthread`**
- 反过来，`-pthread` 一定要加：**少了它，某些库函数的行为可能不是线程安全的**（历史上），且 TLS 访问模型可能退化

> ⚠️ 有个隐蔽的坑：如果你用**静态链接**（`-static`），且在 glibc < 2.34 的环境上，
> `-lpthread` 的顺序很重要（链接器从左往右解析）。用 `-pthread` 就没这个问题，
> 因为它会被正确放置在命令行末尾。

## 三、返回值约定：返回错误码，不设 `errno`（最高频的坑）

**这是 Pthreads 与几乎所有其他 UNIX/POSIX API 完全相反的地方**：

| | 传统 UNIX API | Pthreads 函数 |
|---|---|---|
| 成功 | 返回 0 或有效值 | 返回 **0** |
| 失败 | 返回 **-1** | 返回 **正的错误码**（如 `EAGAIN`=11） |
| 错误详情 | 设置在 `errno` | **不设置 `errno`** |

```c
/* ✗ 完全错误的写法 —— 把两套约定混了 */
pthread_t t;
if (pthread_create(&t, NULL, worker, NULL) < 0) {     /* 永远不成立！失败时返回正数 */
    perror("pthread_create");                          /* errno 根本没被设置 */
    exit(1);
}

/* ✓ 正确写法 */
int err = pthread_create(&t, NULL, worker, NULL);
if (err != 0) {                                        /* 判断 != 0，不是 < 0 */
    fprintf(stderr, "pthread_create 失败: %s\n", strerror(err));   /* 用 strerror(err) */
    exit(1);
}
```

**三个必须记住的点**：

1. **判断用 `!= 0`，不是 `< 0`**。失败返回的是正的 `EAGAIN`(11) / `EINVAL`(22) / `EPERM`(1) 等
2. **用 `strerror(err)`，不是 `perror()`**。`perror()` 读的是 `errno`，而 Pthreads 不设它
3. **`errno` 的值在这时是未定义的**——它可能还是上上次系统调用留下的旧值，`perror()` 会打印出一个**完全误导**的错误

```
  pthread_create() 失败（比如 EAGAIN，资源不够）时：

    返回值 = 11 (EAGAIN)          ← 真正的错误在这
    errno  = 0 或者某个陈旧的值   ← perror() 读的是这个

    perror("pthread_create")
      → "pthread_create: Success"   ← 灾难性的误导
```

> ⚠️ glibc 的实现细节：Pthreads 函数**不保证**不改 `errno`（它们内部也调系统调用），
> 但**也不保证**设置它。所以唯一可靠的错误来源是**返回值**。

### 统一的错误处理宏（推荐）

```c
/* 把 Pthreads 的返回值约定转成传统的 -1/errno 风格，方便统一处理 */
#include <errno.h>
#include <string.h>
#include <stdio.h>

static inline int pthread_err(int rc, const char *what)
{
    if (rc == 0)
        return 0;
    fprintf(stderr, "%s: %s\n", what, strerror(rc));
    return -1;              /* 统一成 -1 */
}

/* 或者更严格的：直接把错误码塞进 errno，让上层用 perror */
static inline int pthread_check(int rc)
{
    if (rc != 0) {
        errno = rc;         /* 手动搬运 */
        return -1;
    }
    return 0;
}

/* 用法 */
if (pthread_check(pthread_create(&t, NULL, worker, NULL)) == -1)
    perror("pthread_create");       /* 现在 errno 是对的 */
```

在 HFT/生产代码里，建议**每个 Pthreads 调用都检查返回值**。
最常见的漏检是 `pthread_mutex_lock()`——`EDEADLK`（自锁）和 `EINVAL` 在高并发下是真会出现的，
静默忽略会导致数据损坏。

## 四、`pthread_t` 是不透明的

```c
typedef unsigned long int pthread_t;    /* glibc/x86-64 上的定义 —— 但不要依赖这个 */
```

POSIX **只要求**它是一个算术类型或指针，**不规定**具体表示。实际历史实现：

| 实现 | `pthread_t` 是什么 |
|------|-------------------|
| Linux glibc（NPTL） | `unsigned long`，是**线程描述符的指针** |
| 旧 LinuxThreads | 一个整数索引 |
| 某些商业 UNIX | 一个指向结构的指针 |
| Windows pthreads-win32 | 结构体（`{ void *p; unsigned int x; }`） |

**三条硬性规则**：

```c
pthread_t t1, t2;

/* ① 不能用 == 比较，必须用 pthread_equal() */
if (pthread_equal(t1, t2))            /* ✓ */
if (t1 == t2)                          /* ✗ 不可移植 */

/* ② 不能用 printf("%lu") 打印，因为类型不确定 */
printf("%lu\n", (unsigned long)t1);    /* 仅调试用，要强转且注明不可移植 */

/* ③ 不能假设 0 是"无效"值 */
pthread_t t = 0;                       /* ✗ 0 在多数实现上不是"空" */
```

> 在 Linux/glibc 上 `pthread_t` 确实等于 `unsigned long`（就是 `struct pthread *` 强转），
> 所以 `t1 == t2` **在 Linux 上能工作**。但代码一旦要移植到别的平台就会出错，
> 而且这类错误**编译不报错、运行不崩溃**，只是比较结果错——最难查。

**调试时怎么打印线程标识？**

```c
/* 如果要一个"人类可读且跨平台"的线程标识，用 gettid() */
#define _GNU_SOURCE
#include <sys/syscall.h>
static pid_t gettid_(void) { return (pid_t)syscall(SYS_gettid); }

printf("tid=%d\n", gettid_());         /* 内核 TID，全系统唯一，可直接和 ps/top 对照 */
```

`gettid()` 返回内核的 `pid_vnr()`（[29.5](29.5-thread-ids.md)），在 `ps -eLf`、`top -H`、
`/proc/PID/task/`、perf、gdb 里看到的都是它——**调试时用 TID 而不是 `pthread_t`**，
因为前者可以直接和系统工具对照。

## 五、Pthreads 数据类型速查

全部定义在 `<pthread.h>`，全部**不透明**，一律用配套函数操作，**不要直接读写字段**。

| 类型 | 用途 | 配套函数族 |
|------|------|-----------|
| `pthread_t` | 线程标识符 | `pthread_create` / `join` / `detach` / `equal` / `self` |
| `pthread_attr_t` | 线程属性（栈大小、分离状态、调度策略…） | `pthread_attr_init` / `_setstacksize` / `_setdetachstate` / `_destroy` |
| `pthread_mutex_t` | 互斥量 | `pthread_mutex_init` / `lock` / `trylock` / `unlock` / `destroy` |
| `pthread_mutexattr_t` | 互斥量属性（类型、进程共享、优先级继承…） | `pthread_mutexattr_init` / `_settype` / `_setpshared` / `_setprotocol` |
| `pthread_cond_t` | 条件变量 | `pthread_cond_init` / `wait` / `timedwait` / `signal` / `broadcast` |
| `pthread_condattr_t` | 条件变量属性（时钟、进程共享） | `pthread_condattr_init` / `_setclock` / `_setpshared` |
| `pthread_rwlock_t` | 读写锁 | `pthread_rwlock_init` / `rdlock` / `wrlock` / `unlock` |
| `pthread_barrier_t` | 屏障 | `pthread_barrier_init` / `wait` |
| `pthread_spinlock_t` | 自旋锁 | `pthread_spin_init` / `lock` / `unlock` |
| `pthread_once_t` | 一次性初始化控制 | `pthread_once` |
| `pthread_key_t` | 线程特定数据的键 | `pthread_key_create` / `setspecific` / `getspecific` |

**不透明类型的初始化铁律**：

```c
/* ① 静态初始化（推荐，编译期完成，不需要 destroy）*/
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  cv  = PTHREAD_COND_INITIALIZER;
static pthread_once_t  once = PTHREAD_ONCE_INIT;

/* ② 动态初始化（需要属性时用，必须配对 destroy）*/
pthread_mutex_t mtx2;
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
pthread_mutex_init(&mtx2, &attr);        /* ← 有了 attr 才能动态 init */
pthread_mutexattr_destroy(&attr);
/* ... 使用 ... */
pthread_mutex_destroy(&mtx2);            /* ← 必须 */
```

⚠️ **未初始化的 mutex 是未定义行为**。栈上的 `pthread_mutex_t m;` 不 init 就 lock，
在 glibc 上是"碰巧能工作"（全零结构恰好等于默认 mutex），但这是**运气不是保证**。

## 六、线程安全与 Pthreads 自身

**所有 `pthread_*` 函数都是线程安全（MT-Safe）的**——这是 POSIX 的要求，不需要额外加锁。

但**其他库函数不一定**。判断依据是 man page 的 `ATTRIBUTES` 节：

```bash
$ man 3 strcpy          # 看 ATTRIBUTES 节
ATTRIBUTES
       ┌───────────────────────────────┬───────────────┬─────────┐
       │Interface                      │ Attribute     │ Value   │
       ├───────────────────────────────┼───────────────┼─────────┤
       │strcpy()                       │ Thread safety │ MT-Safe │
       └───────────────────────────────┴───────────────┴─────────┘

$ man 3 strtok          # 经典的非线程安全函数
       │strtok()                       │ Thread safety │ MT-Unsafe race:strtok │
```

常见**非线程安全**函数（`MT-Unsafe`）及其线程安全替代：

| 不安全 | 安全替代 | 原因 |
|--------|----------|------|
| `strtok` | `strtok_r` | 内部静态指针记住上次位置 |
| `asctime` / `ctime` | `asctime_r` / `ctime_r` | 返回静态缓冲区 |
| `gmtime` / `localtime` | `gmtime_r` / `localtime_r` | 返回静态 `struct tm` |
| `gethostbyname` | `getaddrinfo` | 返回静态结构 |
| `rand` | `rand_r` / `drand48_r` | 共享的随机数状态 |
| `getenv` | （读取通常安全，`setenv` 不安全） | 修改 environ 指针数组 |
| `printf` 族 | 本身 MT-Safe（有锁） | 但**不是 async-signal-safe** |

**`-pthread` 与线程安全的历史关系**：
早期 libc 里有些函数（如 `getpwnam`、`errno` 相关）在单线程环境下用静态缓冲更快，
需要定义 `_REENTRANT` 才启用线程安全版本。现代 glibc **默认就是线程安全的**，
`_REENTRANT` 基本成了历史遗留——但 `-pthread` 仍然会定义它，保持语义一致。

详细讨论见 [Ch31.1 线程安全与可重入](../../chapter-31-thread-safety-tsd/notes/31.1-thread-safety-and-reentrancy-revisited.md)。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **`-lpthread` 在 glibc < 2.34 的交叉工具链上仍是真库**，且静态链接时顺序敏感（必须放命令行末尾，或用 `-Wl,--start-group ... -Wl,--end-group`）。核对 toolchain 的 glibc 版本再选写法。② **uClibc/musl 的差异**：musl 从一开始就把 pthread 合在 libc 里（没有单独的 libpthread），`-lpthread` 是空存根。写跨平台构建脚本时用 `find_package(Threads)` 而不是硬编码 `-pthread`。③ 老嵌入式 glibc 上 `pthread_t` 可能是**结构体**（非算术类型），`pthread_equal` 是唯一正确的比较方式 |
| HFT | ① **必须检查每一个 Pthreads 返回值**，尤其 `pthread_mutex_lock`（`EDEADLK`/`EINVAL`）和 `pthread_create`（`EAGAIN`——线程池耗尽时真的会返回）。生产事故案例：线程池满后 `pthread_create` 返 `EAGAIN`，代码用 `if (rc < 0)` 判断 → 永远不成立 → 线程没起来但程序以为起来了 → 后续数据无人处理。② **别用 `perror` 处理 Pthreads 错误**，理由见上；统一用带 `strerror(rc)` 的日志宏，把 rc 一起打出来。③ **`pthread_t` 不要直接打日志**，记 `gettid()`（能和 `perf`/`gdb`/`ps -eLf` 对齐），排查延迟抖动时这是关键线索。④ 关键路径上 `pthread_mutex_lock` 的无竞争快路径约 15~25ns（纯用户态 cmpxchg），但一旦有竞争进 futex 就是 **2~5 µs** —— 差两个数量级，锁设计要按这个量级来 |

## 代码示例：返回值约定与错误处理

```c
/* pthread_api.c —— Pthreads API 约定的正确用法
 *
 * 编译: gcc -Wall -Wextra -O2 -pthread -o pthread_api pthread_api.c
 * 运行: ./pthread_api
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <pthread.h>
#include <errno.h>
#include <unistd.h>
#include <sys/syscall.h>

static pid_t gettid_(void) { return (pid_t)syscall(SYS_gettid); }

/* ── 统一的错误处理：把 Pthreads 的"返回错误码"转传统的 -1/errno ── */
static int pt_check(int rc, const char *what)
{
    if (rc == 0)
        return 0;
    fprintf(stderr, "  [错误] %s: %s (rc=%d)\n", what, strerror(rc), rc);
    errno = rc;                 /* 搬运到 errno，方便上层 perror */
    return -1;
}

static void *worker(void *arg)
{
    (void)arg;
    printf("    worker: pthread_self=%lu  gettid=%d\n",
           (unsigned long)pthread_self(), gettid_());
    return NULL;
}

int main(void)
{
    pthread_t t1, t2;

    printf("main:      pthread_self=%lu  getpid=%d  gettid=%d\n",
           (unsigned long)pthread_self(), getpid(), gettid_());

    /* ① 正确：判断 != 0，用 strerror(rc) */
    int rc = pthread_create(&t1, NULL, worker, NULL);
    if (rc != 0) {
        fprintf(stderr, "pthread_create 失败: %s\n", strerror(rc));
        return 1;
    }

    /* ② 用统一宏 */
    if (pt_check(pthread_create(&t2, NULL, worker, NULL), "pthread_create") == -1)
        return 1;

    /* ③ pthread_equal 比较，不用 == */
    printf("\n  pthread_equal(t1, t2) = %d   (0 = 不同)\n",
           pthread_equal(t1, t2));
    printf("  pthread_equal(t1, t1) = %d   (非0 = 相同)\n",
           pthread_equal(t1, t1));

    /* ④ 演示错误返回的真实值（不是 -1）*/
    printf("\n  【演示】重复 join 同一个线程会得到什么：\n");
    pthread_join(t1, NULL);
    printf("    第一次 join(t1) 成功 (返回 0)\n");

    rc = pthread_join(t1, NULL);
    printf("    第二次 join(t1) 返回 %d (%s)  ← 注意是【正数】不是 -1\n",
           rc, strerror(rc));
    printf("    errno 此时 = %d，若用 perror 会打印: \"%s\"  ← 完全误导\n",
           errno, strerror(errno));

    pthread_join(t2, NULL);

    /* ⑤ 演示 EAGAIN：资源耗尽 */
    printf("\n  【演示】pthread_create 的 EAGAIN：\n");
    void *huge_stack = NULL;
    pthread_attr_t attr;
    pthread_attr_init(&attr);
    pthread_attr_setstacksize(&attr, 64UL * 1024 * 1024 * 1024);  /* 64GB，必然失败 */
    rc = pthread_create(&t1, NULL, worker, NULL);                  /* 占位，避免未用告警 */
    (void)rc;
    rc = pthread_create(&t2, &attr, worker, NULL);
    printf("    请求 64GB 栈 → 返回 %d (%s)\n", rc, strerror(rc));
    pthread_attr_destroy(&attr);
    (void)huge_stack;

    /* ⑥ 静态初始化 vs 动态初始化 */
    static pthread_mutex_t static_mtx = PTHREAD_MUTEX_INITIALIZER;
    pthread_mutex_t dyn_mtx;
    pthread_mutexattr_t mattr;

    pthread_mutexattr_init(&mattr);
    pthread_mutexattr_settype(&mattr, PTHREAD_MUTEX_ERRORCHECK);
    pthread_mutex_init(&dyn_mtx, &mattr);
    pthread_mutexattr_destroy(&mattr);

    /* ERRORCHECK 类型：重复 lock 会返回 EDEADLK 而不是死锁 */
    pthread_mutex_lock(&dyn_mtx);
    rc = pthread_mutex_lock(&dyn_mtx);
    printf("\n  【演示】ERRORCHECK mutex 重复加锁 → 返回 %d (%s)\n",
           rc, strerror(rc));
    pthread_mutex_unlock(&dyn_mtx);

    /* 普通 mutex 重复加锁 = 自锁死锁（不要试）*/
    pthread_mutex_lock(&static_mtx);
    pthread_mutex_unlock(&static_mtx);

    pthread_mutex_destroy(&dyn_mtx);

    return 0;
}
```

**预期输出要点**：

```
main:      pthread_self=140...  getpid=12345  gettid=12345
    worker: pthread_self=140...  gettid=12346
    worker: pthread_self=140...  gettid=12347

  pthread_equal(t1, t2) = 0   (0 = 不同)
  pthread_equal(t1, t1) = 1   (非0 = 相同)

  【演示】重复 join 同一个线程会得到什么：
    第一次 join(t1) 成功 (返回 0)
    第二次 join(t1) 返回 3 (No such process)  ← 注意是【正数】不是 -1

  【演示】pthread_create 的 EAGAIN：
    请求 64GB 栈 → 返回 12 (Cannot allocate memory)  ← EAGAIN/EINVAL 依系统而定

  【演示】ERRORCHECK mutex 重复加锁 → 返回 35 (Resource deadlock avoided)  ← EDEADLK
```

## 代码自测

<details>
<summary><b>问 1：</b>为什么 <code>if (pthread_create(...) &lt; 0)</code> 这个判断永远是错的？</summary>

因为 Pthreads 用了**与传统 UNIX API 相反的返回值约定**：

| | 传统 UNIX API | Pthreads |
|---|---|---|
| 成功 | 0 或有效值 | **0** |
| 失败 | **-1** | **正的错误码**（`EAGAIN`=11、`EINVAL`=22、`EPERM`=1…） |
| 错误详情 | 设 `errno` | **不设** |

失败时返回的是**正数**，`< 0` 永远不成立：

```c
int rc = pthread_create(&t, NULL, worker, NULL);
/* 资源不足时 rc = 11 (EAGAIN) */
if (rc < 0)        /* 11 < 0 → false → 判断被完全跳过 */
    perror(...);   /* 永远不会执行 */
```

**后果有多严重**：程序以为线程创建成功了，继续往下跑，但线程根本不存在 →
后续的数据流无人处理。这类 bug 在**负载高、资源紧张**时才暴露，平时测不出来。

配套的两个错误：

```c
/* ✗ perror 读 errno，而 Pthreads 不设 errno */
perror("pthread_create");           /* 可能打印 "Success"，灾难性误导 */

/* ✗ 用 < 0 判断 */
if (pthread_mutex_lock(&m) < 0)     /* EDEADLK=35 也不会被捕获 */
```

**正确写法**：

```c
int rc = pthread_create(&t, NULL, worker, NULL);
if (rc != 0) {                                   /* ① 用 != 0 */
    fprintf(stderr, "失败: %s\n", strerror(rc));  /* ② 用 strerror(rc) */
    return -1;
}
```

**统一处理的推荐做法**（把 Pthreads 约定转回传统风格）：

```c
static int pt(int rc, const char *what)
{
    if (rc == 0) return 0;
    errno = rc;                                  /* 手动搬运到 errno */
    fprintf(stderr, "%s: %s\n", what, strerror(rc));
    return -1;
}
/* 之后所有调用点统一：if (pt(pthread_xxx(...), "xxx") == -1) ... */
```

`errno` 为什么"危险"：它不是被清零的，而是保留着**上一次系统调用**留下的值。
`perror()` 读它，就会打印出一个与本次错误毫无关系的描述。

</details>

<details>
<summary><b>问 2：</b>为什么必须用 <code>pthread_equal()</code> 而不是 <code>==</code>？</summary>

因为 POSIX **只要求 `pthread_t` 是「算术类型或指针」，不规定具体表示**。实际实现五花八门：

| 实现 | `pthread_t` 的真实类型 |
|------|----------------------|
| Linux glibc (NPTL) | `unsigned long`（= `struct pthread *` 强转） |
| 旧 LinuxThreads | 整数索引 |
| 某些商业 UNIX | 指向结构的指针 |
| Windows pthreads-win32 | **结构体** `{ void *p; unsigned int x; }` |

在 Linux/glibc 上 `t1 == t2` 确实能工作（因为它是标量），代码"跑得好好的"。
但移植到 `pthread_t` 是结构体的平台时：

- **编译直接报错**（结构体不能用 `==`）→ 还算好
- 或者某些平台 `pthread_t` 是**结构体指针的封装**，`==` 比较的是指针而不是线程身份 → **静默错误**

这类"编译不报错、运行不崩溃、只是结果错"的问题是最难查的。

**三条规则**：

```c
/* ① 比较 */
pthread_equal(t1, t2)        /* ✓ */
t1 == t2                     /* ✗ 不可移植 */

/* ② 打印（调试时可以强转，但要注明）*/
printf("%lu\n", (unsigned long)t);      /* Linux 上可用，注明不可移植 */

/* ③ 不要假设 0 是"空" */
pthread_t t = 0;             /* ✗ 没有任何标准保证这是无效值 */
```

**调试/日志时该用什么？**

用 `gettid()`（内核 TID）而不是 `pthread_t`：

```c
#define _GNU_SOURCE
#include <sys/syscall.h>
static pid_t gettid_(void) { return (pid_t)syscall(SYS_gettid); }
```

理由：
- 在系统范围内唯一（同进程的线程也各不相同）
- 能直接和 `ps -eLf`、`top -H`、`/proc/PID/task/`、gdb 的 `info threads`、perf 采样对照
- 是标量（`pid_t`），打印和比较都安全

在 HFT 排查延迟抖动时，记 TID 是必须的——perf 的调度事件、off-cpu 火焰图里标识线程用的都是 TID。

</details>

<details>
<summary><b>问 3：</b><code>-pthread</code> 和 <code>-lpthread</code> 现在（glibc ≥ 2.34）还有区别吗？</summary>

**有区别，而且应该用 `-pthread`。**

glibc 2.34（2021-08）把 `libpthread.so` 的**全部符号合并进了 `libc.so.6`**，
现在的 `libpthread.so`/`libpthread.a` 只是**空的存根**，保留它纯粹为了向后兼容
（老程序链接它不会失败）。

所以单看"链接"这一件事，两者现在都"能工作"。但 `-pthread` 做的更多：

| | `-pthread` | `-lpthread` |
|---|-----------|-------------|
| 定义 `_REENTRANT` | ✅ | ❌ |
| 传给编译器（影响代码生成，如 TLS 访问模型） | ✅ | ❌ 只传给链接器 |
| 链接线程库 | ✅ | ✅（现在是空存根） |

**实践建议**：

```bash
# 手写编译命令
gcc -pthread -o prog prog.c          # ← 永远用这个

# CMake（推荐，自动处理平台差异）
find_package(Threads REQUIRED)
target_link_libraries(prog PRIVATE Threads::Threads)   # Linux 上展开为 -pthread
```

**什么时候会真的出问题**：

1. **只写 `-lpthread` 且用了静态链接**：存根库是空的，可能出现
   `undefined reference to pthread_create`，尤其在 glibc < 2.34 的老工具链上
2. **链接顺序**：老 glibc 上 `-lpthread` 必须放在**目标文件之后**，
   放前面链接器会跳过（从左往右解析）。`-pthread` 会被 gcc 放到正确位置
3. **交叉编译的嵌入式工具链**：glibc 版本可能 < 2.34，`libpthread` 是真的库，
   这时 `-pthread` 的正确性更重要

**一个常见误解**：有人以为 `-lpthread` 只是"链接"，所以放哪都行。
实际上 gcc 会把 `-pthread` 同时用于**编译和链接**两个阶段，
这也是为什么 CMake 的 `Threads::Threads` 会带 `INTERFACE_COMPILE_OPTIONS`。

</details>

<details>
<summary><b>问 4：</b>栈上声明一个 <code>pthread_mutex_t</code> 不初始化就 <code>lock</code>，会怎样？</summary>

**未定义行为。在 glibc 上"碰巧能工作"，但这是运气不是保证。**

```c
void f(void)
{
    pthread_mutex_t m;          /* 栈上，内容是【垃圾】 */
    pthread_mutex_lock(&m);     /* 未定义行为 */
    /* ... 临界区 ... */
    pthread_mutex_unlock(&m);
}
```

**为什么在 Linux/glibc 上常常"能用"**：

glibc 的默认互斥量是 `PTHREAD_MUTEX_TIMED_NP`，其内部结构全零恰好表示
「未加锁、非递归、非健壮、非 PI」的默认状态。如果栈上那块内存碰巧是零
（比如函数没被深度递归调用过），就会表现正常。

**一旦出现下列情况就会崩**：

- 栈上是上次调用的残留数据（非零）→ mutex 内部状态是垃圾，`lock` 可能直接返回错误或死等
- 开了 `-fstack-protector` / 栈毒化（`-fstack-check`）调试选项 → 栈内容被填成特定模式
- 换 libc 实现（musl 的 mutex 结构不同）
- 用 `PTHREAD_MUTEX_ERRORCHECK` / `RECURSIVE` / `ROBUST` 类型时，全零**不是**有效状态

**正确写法（三选一）**：

```c
/* ① 静态存储期 + 静态初始化器（推荐，编译期完成，无需 destroy）*/
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

/* ② 动态初始化（栈上的 mutex 只能这样）*/
pthread_mutex_t m;
pthread_mutex_init(&m, NULL);       /* 必须 */
/* ... 使用 ... */
pthread_mutex_destroy(&m);          /* 必须配对 */

/* ③ 需要非默认属性时用 attr */
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
pthread_mutex_init(&m, &attr);
pthread_mutexattr_destroy(&attr);
```

**什么时候必须用动态初始化**：

- mutex 是**栈上变量**或**结构体成员**（不能靠静态初始化器）
- 需要**非默认属性**：递归锁、检错锁、健壮锁（`ROBUST`，防持有者崩溃）、
  PI（优先级继承）、进程共享（`PTHREAD_PROCESS_SHARED`）

**`destroy` 的时机**：确保所有线程都不再使用它之后。正在被等待的 mutex 上调
`destroy` 是未定义行为（glibc 返回 `EBUSY`）。

> HFT 场景补充：生产代码里建议用 `PTHREAD_MUTEX_ERRORCHECK` 或至少在 debug 构建里启用，
> 它能把「重复加锁」「解锁别人的锁」这类错误变成可捕获的 `EDEADLK`/`EPERM` 返回值，
> 而不是随机的死锁或数据损坏。开销只有快路径多几个分支。

</details>

<details>
<summary><b>问 5：</b>怎么判断一个库函数是不是线程安全的？非线程安全的怎么办？</summary>

**查 man page 的 `ATTRIBUTES` 节**：

```bash
$ man 3 localtime
ATTRIBUTES
       ┌─────────────────────────┬───────────────┬─────────────────────┐
       │Interface                │ Attribute     │ Value               │
       ├─────────────────────────┼───────────────┼─────────────────────┤
       │localtime()              │ Thread safety │ MT-Unsafe race:tmbuf│
       └─────────────────────────┴───────────────┴─────────────────────┘
```

| 标记 | 含义 |
|------|------|
| `MT-Safe` | 线程安全，多线程直接调用没问题 |
| `MT-Unsafe race:xxx` | 不安全，`xxx` 指出竞争的资源（如 `race:tmbuf`） |
| `MT-Safe env` | 安全，但会读环境变量；若其他线程同时 `setenv` 则不安全 |
| `MT-Safe locale` | 安全，但依赖 locale；若其他线程同时 `setlocale` 则不安全 |

**常见的非线程安全函数与替代**：

| 不安全 | 安全替代 | 原因 |
|--------|----------|------|
| `strtok` | `strtok_r` | 内部静态指针记住上次位置 |
| `asctime` / `ctime` | `asctime_r` / `ctime_r` | 返回静态缓冲区 |
| `gmtime` / `localtime` | `gmtime_r` / `localtime_r` | 返回静态 `struct tm` |
| `gethostbyname` | `getaddrinfo` | 返回静态结构 |
| `rand` | `rand_r` / `drand48_r` | 共享随机数状态 |
| `getenv` | （只读通常安全） | `setenv`/`putenv` 不安全 |
| `crypt` | `crypt_r` | 静态缓冲 |
| `strerror` | `strerror_r` | 返回静态字符串（glibc 的 `strerror` 实际上是线程安全的，但 POSIX 不保证） |

**没法替换时怎么办**（遇到用了静态缓冲的闭源/遗留库）：

```c
/* 方案 A：全局大锁（简单粗暴，会串行化）*/
static pthread_mutex_t lib_lock = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_lock(&lib_lock);
result = unsafe_lib_function(args);
/* 注意：如果返回指向静态缓冲的指针，必须在锁内用完！*/
copy_result(result);
pthread_mutex_unlock(&lib_lock);

/* 方案 B：每线程一份状态（若库支持上下文参数）*/

/* 方案 C：进程隔离 —— 起一个专门跑这个库的进程，用 IPC 通信 */
```

**三个容易混淆的概念**（详见 [Ch31.1](../../chapter-31-thread-safety-tsd/notes/31.1-thread-safety-and-reentrancy-revisited.md)）：

| 概念 | 含义 | 强度 |
|------|------|------|
| **线程安全**（thread-safe） | 多线程同时调用不出错 | 基础 |
| **可重入**（reentrant） | 同一线程在执行中被打断后再次进入也不出错 | 更强 |
| **异步信号安全**（async-signal-safe） | 在信号 handler 里调用也安全 | 最强 |

`printf` 是 MT-Safe 的（内部有 FILE 锁），但**不是** async-signal-safe
（信号可能在它持锁时到达 → handler 里再调 `printf` → 死锁）。

> 现代 glibc 里所有函数**默认都是线程安全的**，不需要 `_REENTRANT`。
> 但 `strtok`、`localtime` 这类**接口本身**就用了静态缓冲的函数仍然不安全——
> 这是 API 设计决定的，跟编译选项无关，必须用 `_r` 版本。

</details>
