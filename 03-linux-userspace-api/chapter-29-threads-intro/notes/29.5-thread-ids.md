# 29.5 线程 ID

> 源码核验：Linux v6.6 · `kernel/sys.c`（`SYSCALL_DEFINE0(getpid):958` = `task_tgid_vnr(current)` · `SYSCALL_DEFINE0(gettid):964` = `task_pid_vnr(current)` · `SYSCALL_DEFINE0(getppid):975`）· `kernel/fork.c`（tgid/group_leader 分派 `:2565-2572` · `kernel_clone():2868` 取 `pid_vnr` `:2921-2922` · `CLONE_PARENT_SETTID` 写 TID 回用户态 `:2924`）· `include/uapi/linux/sched.h`（`CLONE_PARENT_SETTID:23` · `CLONE_CHILD_SETTID:27`）

## 本节讲什么

1. 线程有**两套 ID**：Pthreads 的 `pthread_t` 和内核的 `TID`。它们**不是一回事**，混用会出事
2. `getpid()` 返回的是 **TGID**（线程组 ID）而不是"当前线程的 ID"——这是最容易误解的一条
3. 什么时候该用哪个：API 调用用 `pthread_t`，**调试/诊断/系统工具对照一律用 TID**

---

## 一、两套 ID 体系

| | `pthread_t`（Pthreads ID） | TID（内核线程 ID） |
|---|---|---|
| **获取** | `pthread_self()` | `gettid()`（glibc 2.30+）或 `syscall(SYS_gettid)` |
| **类型** | `pthread_t`（不透明，glibc 上是 `unsigned long`） | `pid_t`（`int`） |
| **作用域** | **进程内**唯一 | **系统范围内**唯一 |
| **分配者** | glibc（= `struct pthread *` 的地址） | 内核 PID 分配器 |
| **比较** | `pthread_equal()`（不能用 `==`） | `==`（就是个整数） |
| **打印** | 不可移植，需强转 | `%d`，随便打 |
| **系统工具可见** | ❌ `ps`/`top`/`perf` 里看不到 | ✅ `ps -eLf`、`top -H`、`/proc/PID/task/`、perf、gdb |
| **跨进程有效** | ❌（是虚拟地址，别的进程里是别的东西） | ✅ 全系统唯一 |

**一个进程里它们的实际关系**：

```
  进程 PID/TGID = 12345

  ┌──────────────────────────────────────────────────┐
  │ 线程         pthread_t (glibc)      TID (内核)    │
  ├──────────────────────────────────────────────────┤
  │ 主线程       0x7f8a5c000700        12345  │
  │ worker A     0x7f8a58000700        12346  │      ← getpid() 全都返回 12345
  │ worker B     0x7f8a4c000700        12347  │        gettid() 各返回各的
  │ worker C     0x7f8a48000700        12348  │
  └──────────────────────────────────────────────────┘
        ↑ 虚拟地址，进程间无意义          ↑ 内核 pid，全系统唯一
```

## 二、`getpid()` 返回的是 **TGID**，不是当前线程的 ID

这是本节最容易踩的坑，也是「线程」在 Linux 上的定义直接导致的：

```c
/* kernel/sys.c:958 */
SYSCALL_DEFINE0(getpid)
{
	return task_tgid_vnr(current);          /* ← tgid，不是 pid！ */
}

/* Thread ID - the internal kernel "pid" */
SYSCALL_DEFINE0(gettid)
{
	return task_pid_vnr(current);           /* ← 真·线程 ID */
}
```

注释里那句 *"Thread ID - the internal kernel pid"* 是内核自己写的——
**TID 就是内核内部的 `pid` 字段**，而 `getpid()` 返回的 `tgid` 是「线程组长的 pid」。

```
  task_struct:
      pid  = 12347       ← 内核内部的唯一标识（= gettid()）
      tgid = 12345       ← 线程组 leader 的 pid（= getpid()）
```

**后果**：所有线程调 `getpid()` 都返回**同一个值**（主线程的 TID）。
所以：

```c
/* ✗ 错误：以为这样能区分线程 */
printf("我是线程 %d\n", getpid());      /* 所有线程打印一样的值 */

/* ✓ 正确 */
printf("我是线程 %d\n", gettid());      /* 各不相同 */
```

⚠️ 这也解释了另一个常见困惑：**用 `getpid()` 做日志文件名/临时文件名会冲突**——
多线程程序里所有线程拿到同一个 PID，会写同一个文件。要用 `gettid()`。

```c
/* ✗ 多线程下所有线程生成同一个文件名 */
snprintf(path, sizeof(path), "/tmp/app-%d.log", getpid());

/* ✓ 每线程一个文件 */
snprintf(path, sizeof(path), "/tmp/app-%d-%d.log", getpid(), gettid());
```

---

## 三、内核真相：`pthread_t` 就是 `struct pthread *`

在 glibc（NPTL）上，`pthread_t` 是 `unsigned long`，其值等于**线程描述符的地址**：

```c
/* glibc: sysdeps/nptl/bits/types/struct___pthread_t（简化）*/
typedef unsigned long int pthread_t;

/* pthread_self() 的实现（x86-64，简化）*/
pthread_t __pthread_self(void)
{
    /* 从 fs 寄存器指向的 TCB 里取出自己，返回其地址 */
    return (pthread_t)THREAD_SELF;
}
```

而线程描述符是在 `pthread_create()` 里 `mmap` 出来的**线程栈底部**：

```
  高地址 ┌──────────────────────┐ ← pthread_self() 返回的就是这个地址
         │  struct pthread (TCB) │
         ├──────────────────────┤
         │  __thread 变量区      │
         ├──────────────────────┤
         │  栈（向下增长）        │
         │        ↓             │
         ├──────────────────────┤
         │  guard page          │
  低地址 └──────────────────────┘
```

**这带来两个实践推论**：

**① 线程结束后 `pthread_t` 可以被复用**

线程 A 结束 → 它的 8MB 栈被 `munmap`（或进 glibc 的栈缓存）→ 新线程 B 创建时
可能拿到**同一块地址** → `pthread_t` 相同。

所以**不要长期保存 `pthread_t` 当作身份标识**（比如做哈希表的 key），
除非你能确保对应的线程还活着。

```
  线程 A: pthread_t = 0x7f8a4c000700   结束
  线程 B: pthread_t = 0x7f8a4c000700   ← 复用了同一块栈地址！

  如果代码里还留着 A 的 pthread_t 并去 pthread_join/pthread_kill 它
  → 实际操作的是 B！这是真实的 bug 来源
```

调试/日志里要线程身份 → **用 TID**（内核分配，短时间内不复用）。

**② `pthread_t` 可以用于 pthread API，但不能当"系统级身份"**

`pthread_join` / `pthread_detach` / `pthread_kill` / `pthread_cancel` 都接受 `pthread_t`——
这些是 glibc 内部的，OK。但任何要**跨进程**或**跨工具**的场合，都用 TID。

## 四、内核怎么把 TID 交给用户态

`pthread_create()` 传了 `CLONE_PARENT_SETTID` 和 `CLONE_CHILD_SETTID`，
内核在合适时机把新 TID 写回用户态指定的地址：

```c
/* kernel/fork.c:2921-2922 */
	pid = get_task_pid(p, PIDTYPE_PID);
	nr = pid_vnr(pid);                          /* nr = 新线程的 TID */

	...
	if (clone_flags & CLONE_PARENT_SETTID)
		put_user(nr, args->parent_tid);         /* 写给父线程 */
	...
	if (clone_flags & CLONE_CHILD_SETTID)
		put_user(nr, args->child_tid);          /* 由新线程自己写给自己 */
```

而 `CLONE_CHILD_CLEARTID` 则在**线程退出时**把那个地址清零并 futex-wake
（`mm_release():1628-1638`）——这正是 `pthread_join()` 的实现基础，
详见 [29.6](29.6-joining-with-a-terminated-thread.md)。

```
  创建时：内核把 TID 写进线程描述符的 tid 字段 (CLONE_CHILD_SETTID)
            ↓
  运行中：pthread_self() 从 TCB 读（纯用户态，无系统调用）
            ↓
  退出时：内核把 tid 字段清零 + futex_wake (CLONE_CHILD_CLEARTID)
            ↓
         pthread_join() 的等待者被唤醒
```

## 五、实践：什么时候用哪个

| 场景 | 用哪个 | 理由 |
|------|--------|------|
| `pthread_join` / `detach` / `cancel` / `kill` | **`pthread_t`** | 这些是 glibc API，只认 `pthread_t` |
| 日志、调试输出 | **TID** | 能和 `ps -eLf`、`top -H`、perf、gdb 对照 |
| 临时文件/共享内存段的命名 | **TID** | `getpid()` 所有线程相同会冲突 |
| 跨进程传递线程标识 | **TID** | `pthread_t` 是虚拟地址，别的进程里无意义 |
| 哈希表 key / 长期身份标识 | **TID** | `pthread_t` 会被栈复用 |
| 判断"是不是同一个线程" | **TID**（或 `pthread_equal`） | 简单直接 |
| 给线程绑核 / 设优先级 | **TID** 或 `pthread_t` 都行 | `sched_setaffinity(pid)` 用 TID；`pthread_setaffinity_np` 用 `pthread_t` |

### 获取 TID 的两种方式

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <sys/syscall.h>

/* 方式 1：glibc 2.30+ 提供包装（推荐）*/
#include <unistd.h>
pid_t tid = gettid();

/* 方式 2：老 glibc 或者要显式系统调用 */
pid_t tid = (pid_t)syscall(SYS_gettid);
```

`syscall(SYS_gettid)` 的开销约 **几十纳秒**（一次系统调用）。
如果在热路径上频繁调用，**缓存起来**：

```c
static __thread pid_t cached_tid = 0;      /* 每线程一份 */

static pid_t my_tid(void)
{
    if (__builtin_expect(cached_tid == 0, 0))
        cached_tid = gettid();             /* 只第一次调 */
    return cached_tid;
}
```

> HFT 里日志每打一次就 `gettid()` 一次是很常见的性能问题。用 `__thread` 缓存后是纯内存读。

### 与系统工具对照

```bash
# 进程的线程数
cat /proc/PID/status | grep Threads
ls /proc/PID/task | wc -l

# 列出所有线程（-L 是关键）
ps -eLf | grep myapp
#   UID  PID  PPID   LWP  C NLWP STIME TTY   TIME CMD
#   user 1234  1200  1234  0    4 10:00 ?     0:00 ./myapp
#   user 1234  1200  1235  0    4 10:00 ?     0:00 ./myapp
#                    ↑LWP = TID（gettid() 的值）

# top 按线程显示（-H）
top -H -p <pid>

# perf 采样（输出里的 TID 就是 gettid() 的值）
perf record -g --tid=<tid> -o perf.data
perf sched record -- sleep 1     # 调度事件里也是 TID

# gdb
(gdb) info threads
#   Id   Target Id         Frame
#   1    Thread 0x7f8a5c000700 (LWP 12345) "myapp" ...
#                              ↑ LWP = TID
```

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **TID 有上限**：`/proc/sys/kernel/pid_max`（默认 32768，64 位可更大）。高频创建销毁线程会让 TID 快速回绕，虽然内核保证不复用活跃 PID，但**日志里的 TID 会重复出现**，做时间线分析时要加上时间戳。② `ps` 在 BusyBox 上可能没有 `-L`，用 `ls /proc/PID/task` 代替。③ `gettid()` 在老 uClibc 上不存在，用 `syscall(SYS_gettid)` |
| HFT | ① **日志必带 TID**：排查延迟抖动时，perf 的调度延迟、off-cpu 火焰图、内核 tracepoint 全都是按 TID 标识的，日志不带 TID 就没法对齐。② **用 `__thread` 缓存 TID**，避免每次打日志都做一次系统调用（几十 ns × 每秒几十万次 = 可观的开销）。③ **绑核/优先级用 TID 记录**：启动后把「TID → 绑哪个核 → 什么优先级」打印出来，运维核对时一目了然（`taskset -cp <tid>` 可直接验证）。④ **不要用 `pthread_t` 做哈希 key**：线程栈复用会让 key 碰撞，查出来的数据是错线程的；用 TID（或干脆用线程自己注册的编号）。⑤ 多进程架构里 TID 只在**同一 PID namespace** 内唯一，容器内外对照要小心 |

## 代码示例：两套 ID 的实测

```c
/* thread_ids.c —— pthread_t vs TID 的实测与对照
 *
 * 编译: gcc -Wall -Wextra -O2 -pthread -o tids thread_ids.c
 * 运行: ./tids
 *       # 另开终端: ps -eLf | grep tids   ← 对照 LWP 列
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>
#include <string.h>
#include <stdint.h>
#include <pthread.h>
#include <unistd.h>
#include <sys/syscall.h>

#define N 3

/* 缓存 TID，避免重复系统调用 */
static __thread pid_t cached_tid = 0;

static pid_t my_tid(void)
{
    if (__builtin_expect(cached_tid == 0, 0))
        cached_tid = (pid_t)syscall(SYS_gettid);
    return cached_tid;
}

static pthread_mutex_t out = PTHREAD_MUTEX_INITIALIZER;
static void say(const char *fmt, ...)
{
    va_list ap; va_start(ap, fmt);
    pthread_mutex_lock(&out);
    vprintf(fmt, ap); fflush(stdout);
    pthread_mutex_unlock(&out);
    va_end(ap);
}

static void *worker_noop(void *arg)      /* 什么都不做，立刻返回 */
{
    (void)arg;
    return NULL;
}

static void *worker(void *arg)
{
    long id = (long)arg;
    pthread_t self = pthread_self();

    say("  worker %ld: pthread_self=%#lx  gettid=%-6d  getpid=%-6d  "
        "pthread_self()==(struct pthread*)? %s\n",
        id,
        (unsigned long)self,
        my_tid(),
        getpid(),
        /* pthread_t 就是线程栈底的地址，验证一下局部变量是否落在同一片区域 */
        "看下方地址对比");

    /* 验证：局部变量地址 与 pthread_self() 应当很接近（同一个栈区间）*/
    char probe;
    say("            局部变量地址=%p  (与 pthread_self 相差 %ld 字节，同一栈区)\n",
        (void *)&probe,
        (long)((char *)self - &probe));

    sleep(2);            /* 留时间给 ps -eLf 观察 */
    return NULL;
}

int main(void)
{
    pthread_t t[N];

    printf("进程 PID(TGID) = %d\n", getpid());
    printf("主线程 TID     = %d   ← leader 的 pid == tgid\n\n", my_tid());

    printf("  %-10s %-20s %-10s %-10s\n",
           "线程", "pthread_self()", "gettid()", "getpid()");
    printf("  %-10s %-20s %-10s %-10s\n",
           "----------", "--------------------", "----------", "----------");
    printf("  %-10s %-#20lx %-10d %-10d\n",
           "main", (unsigned long)pthread_self(), my_tid(), getpid());

    for (long i = 0; i < N; i++)
        pthread_create(&t[i], NULL, worker, (void *)i);
    for (int i = 0; i < N; i++)
        pthread_join(t[i], NULL);

    printf("\n  观察要点：\n");
    printf("    1) getpid() 所有线程【相同】 = %d\n", getpid());
    printf("    2) gettid() 每个线程【不同】，且能在 ps -eLf 的 LWP 列找到\n");
    printf("    3) pthread_self() 是【虚拟地址】，进程外无意义\n");
    printf("    4) 局部变量地址 ≈ pthread_self()（同一个 mmap 出来的栈区）\n");

    /* 演示 pthread_t 的复用 */
    printf("\n  【演示】pthread_t 的复用：\n");
    pthread_t a, b;
    pthread_create(&a, NULL, worker_noop, NULL);
    pthread_join(a, NULL);
    pthread_create(&b, NULL, worker_noop, NULL);
    printf("    线程 A 的 pthread_t = %#lx\n", (unsigned long)a);
    printf("    线程 B 的 pthread_t = %#lx   ← %s\n",
           (unsigned long)b,
           (a == b) ? "【相同！栈被复用了】" : "不同（glibc 这次没复用）");
    pthread_join(b, NULL);
    printf("    → 所以不要用 pthread_t 做长期身份标识，用 TID\n");

    return 0;
}
```

**预期输出要点**：

```
进程 PID(TGID) = 12345
主线程 TID     = 12345   ← leader 的 pid == tgid

  线程        pthread_self()       gettid()   getpid()
  main        0x7f8a5c000700       12345      12345
  worker 0: pthread_self=0x7f8a4c000700  gettid=12346  getpid=12345
            局部变量地址=0x7f8a4c000fbf (与 pthread_self 相差 3775 字节，同一栈区)
  worker 1: pthread_self=0x7f8a44000700  gettid=12347  getpid=12345
  ...
```

## 代码自测

<details>
<summary><b>问 1：</b>所有线程调 <code>getpid()</code> 都返回同一个值，为什么？</summary>

因为 `getpid()` 返回的是 **TGID（线程组 ID）**，不是当前线程的 ID。

```c
/* kernel/sys.c:958 */
SYSCALL_DEFINE0(getpid)
{
	return task_tgid_vnr(current);          /* ← tgid */
}

/* Thread ID - the internal kernel "pid" */
SYSCALL_DEFINE0(gettid)
{
	return task_pid_vnr(current);           /* ← 真·线程 ID */
}
```

内核注释里 *"Thread ID - the internal kernel pid"* 说得非常直白：
**TID 就是内核 `task_struct.pid` 字段本身**。

而 `tgid` 是「线程组 leader 的 pid」，在 `copy_process()` 里分派
（`kernel/fork.c:2565-2572`）：

```c
	p->pid = pid_nr(pid);
	if (clone_flags & CLONE_THREAD) {
		p->group_leader = current->group_leader;
		p->tgid = current->tgid;          /* 沿用组长的 tgid */
	} else {
		p->group_leader = p;
		p->tgid = p->pid;                 /* 自己当组长：tgid = pid */
	}
```

所以同一个线程组（= 同一个进程）里，**所有 task_struct 的 `tgid` 都等于主线程的 `pid`**，
于是 `getpid()` 全返回同一个值——这是**设计意图**，不是 bug。
POSIX 要求 `getpid()` 在进程的所有线程中返回相同值。

**实践影响**：

```c
/* ✗ 用 getpid() 区分线程 → 所有线程打印同一个数 */
printf("thread %d\n", getpid());

/* ✗ 用 getpid() 构造唯一文件名 → 多线程冲突 */
snprintf(path, sizeof(path), "/tmp/app-%d.log", getpid());

/* ✓ 区分线程用 gettid() */
printf("thread %d\n", gettid());

/* ✓ 唯一文件名带上 tid */
snprintf(path, sizeof(path), "/tmp/app-%d-%d.log", getpid(), gettid());
```

另一条推论：**主线程的 `pid == tid`**（它是组长，`tgid = p->pid`）。
所以如果一个线程打印出 `getpid() == gettid()`，它就是主线程。

</details>

<details>
<summary><b>问 2：</b><code>pthread_t</code> 和 TID 有什么区别？调试时该用哪个？</summary>

| | `pthread_t` | TID |
|---|---|---|
| 获取 | `pthread_self()` | `gettid()` |
| 类型 | `unsigned long`（glibc），不透明 | `pid_t`（int） |
| 作用域 | 进程内 | 系统范围 |
| 本质 | **`struct pthread *` 的虚拟地址** | 内核 PID 分配器给的数字 |
| 比较 | `pthread_equal()` | `==` |
| 会复用吗 | **会**（线程栈被 munmap 后新线程可能拿到同地址） | 会，但内核保证不与活跃 PID 冲突 |
| `ps`/`top`/`perf`/`gdb` 能看到吗 | ❌ | ✅ |

**调试时一律用 TID**，理由是**可对照性**：

```bash
ps -eLf | grep myapp
#   UID   PID  PPID   LWP  C NLWP ... CMD
#   user 1234  1200  1234  0    4 ... ./myapp     ← LWP 列 = TID
#   user 1234  1200  1235  0    4 ... ./myapp
#                    ↑ 这个就是 gettid() 的值

top -H -p 1234                    # -H 按线程显示，PID 列显示的是 TID
ls /proc/1234/task                # 每个线程一个子目录，目录名就是 TID
cat /proc/1234/task/1235/comm     # 读/写某个线程的名字

perf record --tid=1235            # 只采某个线程
perf sched record -- sleep 1      # 调度事件里的 TID 可直接对应

(gdb) info threads
#   1  Thread 0x7f8a5c000700 (LWP 12345) "myapp" ...
#                             ↑ LWP = TID
```

`pthread_t`（那个 `0x7f8a5c000700` 地址）在**任何系统工具里都找不到**，
它是纯用户态的虚拟地址。日志里打它等于打了个没用的东西。

**另一个关键差异：`pthread_t` 会被复用**

```
  线程 A: pthread_t = 0x7f8a4c000700   结束 → 栈 munmap
  线程 B: pthread_t = 0x7f8a4c000700   ← 新线程拿到同一块地址
```

如果代码里长期保存 A 的 `pthread_t`（比如放进哈希表做 key），
之后 B 出现了，键就碰撞了——**查出来的是错线程的数据**。

所以：

| 用途 | 用 |
|------|-----|
| `pthread_join`/`detach`/`cancel`/`kill` 的参数 | `pthread_t`（API 要求） |
| 日志、诊断、监控、哈希 key、跨进程标识 | **TID** |

**获取 TID 的性能注意**：`syscall(SYS_gettid)` 是一次系统调用（几十 ns）。
在热路径（如每笔交易打日志）上要缓存：

```c
static __thread pid_t cached_tid = 0;
static pid_t my_tid(void)
{
    if (__builtin_expect(cached_tid == 0, 0))
        cached_tid = gettid();       /* 只第一次调 */
    return cached_tid;               /* 之后是纯 TLS 读，~1ns */
}
```

</details>

<details>
<summary><b>问 3：</b>为什么不能用 <code>pthread_t</code> 做「长期身份标识」？</summary>

因为 **`pthread_t` 在 glibc 上就是线程栈的地址，而栈会被回收和复用**。

```c
typedef unsigned long int pthread_t;      /* glibc 的定义 */

/* pthread_self() 返回的是 struct pthread（线程描述符）的地址，
   而它就位于线程栈的底部（高地址端）*/
```

```
  线程 A 创建 → mmap 8MB 栈 → struct pthread 在 0x7f8a4c000700
                              pthread_t = 0x7f8a4c000700
       ↓
  线程 A 结束 → munmap 这 8MB
       ↓
  线程 B 创建 → mmap 又拿到 0x7f8a4c000700（glibc 有栈缓存，概率更高）
                              pthread_t = 0x7f8a4c000700   ← 和 A 一样！
```

**真实后果**：

```c
/* ✗ 危险：用 pthread_t 当哈希表的 key */
static struct thr_stats {
    pthread_t tid;
    uint64_t  ops;
} stats[64];

/* 线程 A 结束后 B 复用了同一 pthread_t
   → stats 里 A 的记录被 B 覆盖 / B 查到 A 的数据
   → 统计数据全错，而且是【偶发】的，取决于栈是否恰好复用 */
```

另外两个相关问题：

**① 线程结束后对着旧 `pthread_t` 调 API**

```c
pthread_t old = ...;      /* 对应的线程已经 join 过了 */
pthread_join(old, NULL);  /* 未定义行为：可能 ESRCH，也可能误操作到复用了地址的新线程 */
pthread_cancel(old);      /* 更危险：可能 cancel 掉一个无辜的线程 */
```

**② 跨进程传递毫无意义**

虚拟地址在别的进程里指向完全不同的东西（或根本没映射）。

**正确做法**：

```c
/* ① 用 TID 做标识（内核分配，系统唯一，不与活跃线程冲突）*/
struct thr_stats { pid_t tid; uint64_t ops; };

/* ② 或者用自己的线程编号（最清晰）*/
static _Atomic int next_worker_id = 0;
static __thread int my_worker_id = -1;

static void *worker(void *arg)
{
    my_worker_id = atomic_fetch_add(&next_worker_id, 1);   /* 稳定、可控、可读 */
    ...
}

/* ③ 只在【明确的生命周期内】用 pthread_t */
pthread_create(&t, NULL, w, NULL);
/* ... 确定 t 还活着 ... */
pthread_join(t, NULL);      /* 之后就不再使用 t */
```

> **HFT 实践**：线程统计/监控结构一律用「worker 编号（0,1,2…）」做索引，
> 另外记一份 TID 用于和系统工具对照。`pthread_t` 只在创建→join 这段区间内使用，
> join 完就丢弃，不长期持有。

</details>

<details>
<summary><b>问 4：</b>内核是怎么把新线程的 TID 告诉用户态的？</summary>

靠三个 `CLONE_*` 标志配合，内核在**两个时机**把 TID 写进用户态指定的地址。

**时机一：创建时（写 TID）**

`pthread_create()` 传了 `CLONE_PARENT_SETTID`（写给父线程）和
`CLONE_CHILD_SETTID`（由新线程写给自己）：

```c
/* kernel/fork.c:2921-2922 —— 先算出 TID */
	pid = get_task_pid(p, PIDTYPE_PID);
	nr = pid_vnr(pid);              /* nr = 新线程在调用者 namespace 里的 TID */

/* kernel/fork.c:2924 —— 写给父线程指定的地址 */
	if (clone_flags & CLONE_PARENT_SETTID)
		put_user(nr, args->parent_tid);
```

同时 `copy_process()` 里记下「新线程自己要写哪个地址」（`kernel/fork.c:2347`）：

```c
	p->set_child_tid = (clone_flags & CLONE_CHILD_SETTID) ? args->child_tid : NULL;
```

新线程开始执行时（返回用户态前）由内核把 TID 写进去。

**时机二：退出时（清 TID + 唤醒）**

`pthread_create()` 还传了 `CLONE_CHILD_CLEARTID`，内核在 `copy_process()` 记下地址（`fork.c:2351`）：

```c
	p->clear_child_tid = (clone_flags & CLONE_CHILD_CLEARTID) ? args->child_tid : NULL;
```

线程退出时，`mm_release()` 自动处理（`kernel/fork.c:1628-1638`）：

```c
	if (tsk->clear_child_tid) {
		if (atomic_read(&mm->mm_users) > 1) {          /* 还有别的线程活着 */
			put_user(0, tsk->clear_child_tid);      /* ① TID 写 0 */
			do_futex(tsk->clear_child_tid, FUTEX_WAKE,
					1, NULL, NULL, 0, 0);          /* ② 唤醒 1 个等待者 */
		}
		tsk->clear_child_tid = NULL;
	}
```

**完整时序**：

```
  pthread_create()
      │
      ├─ clone(CLONE_PARENT_SETTID | CLONE_CHILD_SETTID | CLONE_CHILD_CLEARTID, ...)
      │
      ↓ 内核
  copy_process()
      ├─ p->set_child_tid   = args->child_tid     :2347
      ├─ p->clear_child_tid = args->child_tid     :2351
      ├─ nr = pid_vnr(...)                        :2922
      └─ put_user(nr, args->parent_tid)           :2924  ← 父线程拿到 TID
      ↓
  wake_up_new_task(p)
      ↓ 新线程跑到用户态前
  内核写 *set_child_tid = nr                              ← 自己也拿到 TID
      ↓
  ... 线程运行 ...
      ↓
  线程退出 → mm_release()
      ├─ put_user(0, clear_child_tid)             :1634   ← TID 清零
      └─ do_futex(..., FUTEX_WAKE, 1, ...)        :1635   ← 唤醒 joiner
```

**这个设计的价值**：`pthread_join()` 不需要额外系统调用去"通知"等待者——
内核在线程退出的必经之路上顺手做了。而且用 futex 意味着**无竞争的 join
路径几乎零开销**（见 [29.6](29.6-joining-with-a-terminated-thread.md)）。

> ⚠️ 注意 `atomic_read(&mm->mm_users) > 1` 这个条件：如果这是**最后一个**线程，
> 就不做清 TID + wake（因为整个进程要退出了，没人在等，而且地址空间马上拆除，
> `put_user()` 会失败）。

</details>

<details>
<summary><b>问 5：</b>多线程程序里怎么用系统工具定位某个线程？</summary>

**核心：日志里记 TID，然后一切工具都能对上。**

### 第一步：程序里记下 TID

```c
#define _GNU_SOURCE
#include <unistd.h>
static __thread pid_t cached_tid = 0;
static pid_t my_tid(void) {
    if (!cached_tid) cached_tid = gettid();   /* glibc 2.30+，或 syscall(SYS_gettid) */
    return cached_tid;
}

/* 启动时打印一张「线程 - TID - 职责」对照表 */
printf("worker[0] tid=%d role=market_data\n", ...);
printf("worker[1] tid=%d role=strategy\n", ...);
```

还可以给线程**命名**（`/proc/PID/task/TID/comm`），`ps`/`top` 里直接显示：

```c
#include <sys/prctl.h>
prctl(PR_SET_NAME, "mkt_data");       /* 只影响【当前线程】，最长 15 字节 */

/* 或者给别的线程命名（glibc 2.12+）*/
pthread_setname_np(tid_pthread, "strategy");
```

### 第二步：用工具定位

```bash
# ① 列出所有线程（LWP 列 = TID）
ps -eLf | grep myapp
ps -o pid,tid,comm,psr,stat,pcpu -p <pid>      # tid/psr(当前 CPU) 很有用

# ② 看每个线程跑在哪个核上（HFT 绑核核对必备）
ps -o pid,tid,psr,comm -p <pid>
# 或用 taskset 验证
taskset -cp <tid>                               # 打印该线程的 CPU 亲和性

# ③ /proc 下每个线程一个目录
ls /proc/<pid>/task                             # 目录名 = TID
cat /proc/<pid>/task/<tid>/comm                 # 线程名
cat /proc/<pid>/task/<tid>/status | grep -E "State|Threads"
cat /proc/<pid>/task/<tid>/stat                 # 第 39 字段 = 最后运行的 CPU

# ④ top 按线程看
top -H -p <pid>                                 # -H 关键！

# ⑤ perf 只采某个线程
perf record -g --tid=<tid> -o perf.data -- sleep 10
perf report

# ⑥ 调度延迟分析（HFT 抖动排查的核心工具）
perf sched record -- sleep 5
perf sched latency --sort max                   # 输出里有 TID

# ⑦ /proc 里看线程在等什么
cat /proc/<pid>/task/<tid>/wchan                 # 阻塞在哪个内核函数
cat /proc/<pid>/task/<tid>/stack                 # 内核栈（需 root + CONFIG_STACKTRACE）

# ⑧ gdb 连上去
gdb -p <pid>
(gdb) info threads          # LWP 列 = TID
(gdb) thread <n>
(gdb) bt
```

### 实战：HFT 抖动排查流程

```
  1. 日志发现某笔订单延迟 500µs（正常 20µs）
        ↓ 日志里有 tid=12347
  2. ps -o pid,tid,psr,comm -p <pid>    → 12347 是 strategy 线程，绑在核 3
        ↓
  3. perf sched record + latency        → 看 12347 是否被抢占/多久没被调度
        ↓
  4. 若发现被抢占 → 检查核 3 上还跑了谁（isolcpus 是否生效、有没有中断）
     cat /proc/irq/*/smp_affinity_list
        ↓
  5. 若发现是 off-cpu（在等锁/IO）→ /proc/<pid>/task/12347/wchan
```

**关键前提**：如果日志里只有 `pthread_t`（一个虚拟地址），
上述所有步骤都做不下去——**这就是记 TID 的意义**。

</details>
