## 本节讲什么

1. **内核里只有一个 `copy_process()`**——`fork`、`vfork`、`pthread_create` 走的是同一段代码，差别只是一组 `CLONE_*` 位
2. 线程切换比进程切换便宜的**真正机制原因**（不是「线程不换页表」这种模糊说法，而是 `arch/x86/mm/tlb.c:562` 的那个早退）
3. 从「性能」和「故障域」两个维度做选型，以及 HFT 里为什么答案是**两者都要**

## 一、内核视角：`fork` / `vfork` / `pthread_create` 是同一段代码

这是理解本节的地基。Linux 上**进程和线程都由 `copy_process()`（`kernel/fork.c:2240`）创建**，唯一的输入差别是 `clone_flags`：

```
  用户态 API                    clone_flags（关键位）                   内核行为
  ─────────────────────────────────────────────────────────────────────────────
  fork()                   SIGCHLD  (即 CSIGNAL 位填 SIGCHLD=17)
                           ├─ 无 CLONE_VM      → copy_mm()   走 dup_mm()  复制页表
                           ├─ 无 CLONE_FILES   → copy_files() 走 dup_fd()  复制 fd 表
                           ├─ 无 CLONE_SIGHAND → copy_sighand() 新分配 + memcpy
                           └─ 无 CLONE_THREAD  → exit_signal = SIGCHLD     会通知父进程

  vfork()                  CLONE_VFORK | CLONE_VM | SIGCHLD
                           └─ CLONE_VM 有       → mmget() 共享（父进程被挂起等 exec/exit）

  pthread_create()         CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND
                           | CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS
                           | CLONE_PARENT_SETTID | CLONE_CHILD_SETTID
                           | CLONE_CHILD_CLEARTID
                           ├─ CLONE_VM 有       → copy_mm()   走 mmget()   O(1)
                           ├─ CLONE_FILES 有   → copy_files() 走 atomic_inc O(1)
                           ├─ CLONE_SIGHAND 有 → copy_sighand() refcount_inc O(1)
                           └─ CLONE_THREAD 有  → exit_signal = -1         不发 SIGCHLD

  clone3()                 由 struct clone_args（include/uapi/linux/sched.h:92）精确指定每一位
                           └─ 上面所有 API 的公共底座
```

### 内核强制的两条依赖

```c
/* kernel/fork.c:2267 */
	if ((clone_flags & CLONE_THREAD) && !(clone_flags & CLONE_SIGHAND))
		return ERR_PTR(-EINVAL);

/* kernel/fork.c:2275 */
	if ((clone_flags & CLONE_SIGHAND) && !(clone_flags & CLONE_VM))
		return ERR_PTR(-EINVAL);
```

```
  CLONE_THREAD  ⟹  CLONE_SIGHAND  ⟹  CLONE_VM
  （同一线程组）    （共享信号处理）   （共享地址空间）
```

所以**「线程」在内核里的定义就是**：带 `CLONE_THREAD` 的一组 `task_struct`。仅此而已。

> **一句话总结**：内核不区分进程和线程，它只认识 `task_struct` 和 `CLONE_*` 位。
> 所谓「进程 vs 线程」，是**用户态给不同 flag 组合起的两种名字**。

## 二、共享 vs 私有：逐资源对照（含内核字段）

| 资源 | 内核字段 / 结构 | `fork()`（进程） | `pthread_create()`（线程） | 决定该行为的 flag | 内核函数（行号） |
|------|----------------|-----------------|---------------------------|------------------|-----------------|
| **虚拟地址空间** | `task_struct->mm` | **独立副本**（写时复制） | **共享同一 `mm_struct`** | `CLONE_VM` | `copy_mm():1708`，分支 `:1731` |
| **页表** | `mm->pgd` | 复制整棵页表树 | 共享 | `CLONE_VM` | `dup_mm()` `:1735` |
| **文件描述符表** | `task_struct->files` | 复制 `files_struct` | 共享（引用计数 +1） | `CLONE_FILES` | `copy_files():1766`，分支 `:1784` |
| **文件系统上下文**（cwd/umask/root） | `task_struct->fs` | 复制 | 共享 | `CLONE_FS` | `copy_fs():1746` |
| **信号处理器表** | `task_struct->sighand` | 复制（`kmem_cache_alloc` + `memcpy`） | 共享（引用计数 +1） | `CLONE_SIGHAND` | `copy_sighand():1799`，分支 `:1803` |
| **信号掩码** | `task_struct->blocked` | **私有** | **私有**（每线程独立） | — | 29.1 已述 |
| **pending 信号集** | `task_struct->pending` / `signal->shared_pending` | 私有 + 无共享 | 私有 + 线程组共享 | `CLONE_THREAD` | `copy_signal():1848` |
| **线程组 ID（TGID）** | `task_struct->tgid` | **新 TGID**（= 自己的 pid） | **继承父的 TGID** | `CLONE_THREAD` | `:2565-2572` |
| **内核 pid** | `task_struct->pid` | 新 pid | **新 pid**（每线程一个！） | — | 见 29.5 |
| **退出时通知谁** | `task_struct->exit_signal` | `SIGCHLD`（父进程 `wait()` 收） | **`-1`（不通知）** | `CLONE_THREAD` | `:2632-2633` |
| **命名空间** | `task_struct->nsproxy` | 按 flag 决定 | 共享 | `CLONE_NEW*` | `copy_namespaces` `:2504` |
| **IO 上下文** | `task_struct->io_context` | 复制 | 共享 | `CLONE_IO` | `copy_io` `:2507` |
| **System V sem undo** | `task_struct->sysvsem` | 复制 | 共享 | `CLONE_SYSVSEM` | `copy_semundo` `:2486` |
| **内核栈** | `task_struct->stack` | **16KB，独立** | **16KB，独立**（一视同仁） | — | `kernel/fork.c:309` |
| **CPU 寄存器 / SP / PC** | `thread_struct` | 复制（返回值不同） | 复制（指向 start 函数） | — | `copy_thread` `:2510` |
| **TLS 指针** | `thread.fs` / `fsbase` | 继承 | **由 `CLONE_SETTLS` 设为新值** | `CLONE_SETTLS` | `include/uapi/linux/sched.h:22` |
| **`errno`** | glibc `__errno_location()` | 独立 | **独立**（每线程） | — | 用户态概念 |
| **堆（`malloc`）** | `mm->brk` / arena | 独立 | **共享**（malloc 内部加锁） | `CLONE_VM` | — |

### 两个「内核不共享但用户以为共享」的反例

| 项 | 真相 |
|----|------|
| **文件描述符的**「文件偏移」 | 若 `CLONE_FILES`（线程）→ **共享同一个 `struct file`**，偏移共享；若 `fork` → `dup_fd` 复制 fd 表项，但**仍指向同一个 `struct file`**，所以偏移**也共享**。这是 Ch5 / Ch24 的经典陷阱 |
| **`getpid()` 的返回值** | 线程里返回的是 **TGID**（`kernel/sys.c:958`），所有线程相同；要区分用 `gettid()`（`:964`） |

## 三、成本对照：创建 / 切换 / 销毁

### 3.1 创建成本

主因就在 `copy_mm()`（`kernel/fork.c:1708`）：

```c
	if (clone_flags & CLONE_VM) {
		mmget(oldmm);                       /* 线程：引用计数 +1，O(1) */
		mm = oldmm;
	} else {
		mm = dup_mm(tsk, current->mm);      /* 进程：复制 mm_struct + VMA 树 + 页表 */
		if (!mm)
			return -ENOMEM;
	}
```

`dup_mm()` 要做：新分配 `mm_struct` → 复制整棵 VMA 树（每建一个 VMA 一次 `kmem_cache_alloc`）→ 逐层复制页目录/页表项 → 初始化 `mmap_lock`、`rss_stat` 等。

| 操作 | 大致耗时（x86-64，虚拟内存越大越慢） | 主因 |
|------|-----------------------------------|------|
| `pthread_create` | **~20~50 μs** | `mmap` 8MB 栈 + `clone` + futex 初始化 |
| `fork`（小进程，几 MB VM） | ~100~300 μs | `dup_mm` 复制页表 |
| `fork`（VM +512MB，**未触碰**） | 与基线**几乎无差** | 页表是空的，只多复制一个 VMA 结构体 |
| `fork`（VM +512MB，**已触碰**） | **慢 20 倍以上** | 要复制 512MB/4KB = 131072 个已建立的 PTE |
| `fork`（大进程，几 GB VM，已触碰） | **~10~100 ms** | 页表复制量与已映射页数成正比 |
| `vfork` | ~50~100 μs | 共享 mm，但父进程被挂起 |
| `posix_spawn` | 介于 fork 和 vfork 之间 | 通常用 `clone(CLONE_VM\|CLONE_VFORK)` + `exec` |

### 本机实测记录（WSL2 / 12 核）

虚拟化环境下绝对值会放大数倍，**看倍数关系而不是绝对值**：

```
  线程 create+join                      420.6 μs
  进程 fork+waitpid（基线）              986.3 μs   ← 2.3× 线程
  进程 fork+waitpid（VM +512MB 未触碰）  1044.0 μs  ← 与基线几乎无差（+6%）
  进程 fork+waitpid（VM +512MB 已触碰） 21129.3 μs  ← 21× 基线！
```

> **这两个实测数字是全章最有说服力的证据**：
>
> 1. **只 `mmap` 不触碰 → `fork` 几乎不涨价**。内核连一个 PTE 都没分配，`dup_mm()` 只是多复制一个 `vm_area_struct`。
> 2. **一旦触碰过 → 涨 20 倍**。`dup_mm()` 要逐级复制 131072 个已建立的页表项。
>
> **这直接证明：COW 省的是【物理页的拷贝】，不省【页表结构的拷贝】。**
> 即使子进程立刻 `_exit()`，父进程也已经为复制页表付过钱了。

> **实践提示**：`fork` 的开销与**父进程虚拟内存大小成正比**，不是常数。
> 一个占 32GB 虚拟内存的进程 `fork` 一次可能要几毫秒——这在 HFT 里是不可接受的，
> 这也是「大内存进程绝不用 fork 做并发」的硬理由（详见 Ch28 / Ch24 的 `posix_spawn` 讨论）。

### 3.2 切换成本：线程便宜的**真正原因**

调度器对所有 `task_struct` 一视同仁，`context_switch()`（`kernel/sched/core.c:5324`）在 `:5364` **无条件**调用 `switch_mm_irqs_off()`：

```c
	} else {                                        // to user
		membarrier_switch_mm(rq, prev->active_mm, next->mm);
		switch_mm_irqs_off(prev->active_mm, next->mm, next);   /* :5364 */
		...
	}
```

真正的分叉在 x86 的实现里（`arch/x86/mm/tlb.c:495`）：

```c
	struct mm_struct *real_prev = this_cpu_read(cpu_tlbstate.loaded_mm);   /* :497 */
	...
	if (real_prev == next) {                                /* :562 */
		/* Not actually switching mm's */
		...
		/*
		 * If the CPU is not in lazy TLB mode, we are just switching
		 * from one thread in a process to another thread in the same
		 * process. No TLB flush required.                  /* :584 */
		 */
		if (!was_lazy)                                      /* :586 */
			return;                                         /* ← 直接返回！ */
		...
	} else {                                                /* :596 */
		/*
		 * Apply process to process speculation vulnerability
		 * mitigations if applicable.
		 */
		cond_mitigation(tsk);                               /* :612 */
		...
		choose_new_asid(next, next_tlb_gen, &new_asid, &need_flush);
		...
		load_new_mm_cr3(next->pgd, new_asid, new_lam, true);   /* 写 CR3 */
	}
```

| 切换类型 | `real_prev == next`? | 写 CR3 / 换 ASID | Spectre 缓解（`cond_mitigation`） | 大致成本 |
|----------|---------------------|-----------------|----------------------------------|---------|
| **同进程 线程 → 线程** | ✔ | **否**（`:562` 早退，不执行 `load_new_mm_cr3`） | **否** | **~1 μs** |
| **进程 → 进程** | ✘ | **是**（`choose_new_asid` + `load_new_mm_cr3`） | **是**（IBPB / L1D flush / RSB 等） | **~3~10 μs**（开启缓解后更贵） |

**这就是线程切换便宜的完整机制解释**，三个层次：

1. **不写 CR3** → 不换地址空间
2. **不刷 TLB / 不换 ASID** → 页表缓存、TLB 条目、L1/L2 缓存里的热数据全部保留
3. **不跑 `cond_mitigation()`** → 省掉 IBPB（间接分支预测屏障）等 Spectre 缓解，这些在进程间切换时必须跑

> 附带一个常被忽略的点：**线程切换同样会污染 L1/L2 数据缓存**（两个线程访问的数据集不同），
> 所以「线程切换零成本」是错的。HFT 里把不同职责的线程**绑到不同物理核**，
> 就是为了连这一层都省掉（29.8 的 `pthread_attr_setaffinity_np`）。

### 3.3 销毁成本

| | 进程 | 线程 |
|---|------|------|
| 谁来收 | 父进程 `wait()` / `waitpid()` | `pthread_join()`（或 detached 自动回收） |
| 内核是否留僵尸 | **是**。`exit_notify():739` 设 `EXIT_ZOMBIE`，等父进程收 | **否**。`exit_notify():750` 对非 leader 直接 `autoreap = true`，`:753-756` 立即转 `EXIT_DEAD` |
| 通知机制 | `do_notify_parent(tsk, tsk->exit_signal)`，发 `SIGCHLD` | **无**。`exit_signal = -1`（`:2632-2633`） |
| 泄漏表现 | 僵尸进程占 PID 表项 | glibc 泄漏 8MB 栈 + TCB（29.6 / 29.7） |

```c
/* kernel/exit.c:739-756 */
	tsk->exit_state = EXIT_ZOMBIE;
	if (unlikely(tsk->ptrace)) {
		...
		autoreap = do_notify_parent(tsk, sig);
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&
			do_notify_parent(tsk, tsk->exit_signal);
	} else {
		autoreap = true;                    /* :750 ← 非线程组 leader：恒为真 */
	}

	if (autoreap) {                         /* :753 */
		tsk->exit_state = EXIT_DEAD;        /* :754 */
		list_add(&tsk->ptrace_entry, &dead);
	}
```

**注意最后一个细节**：线程组 leader 的判断是 `thread_group_empty(tsk)`——**如果 leader 自己退出时还有别的线程活着，`autoreap` 为假，leader 会短暂进僵尸态**，等最后一个线程走完才被收。

## 四、语义差异清单（比性能更重要）

性能只是选型的一半。下面这些**语义差异**往往才是决定因素：

| # | 维度 | 进程 | 线程 |
|---|------|------|------|
| 1 | **崩溃影响域** | 只死自己（`SIGSEGV` 只杀该进程） | **整个进程一起死**（信号处置是共享的） |
| 2 | **`exit()` 的作用域** | 只退自己 | **杀光整个进程的所有线程** |
| 3 | **信号处理** | `SIGSEGV` 等同步信号定向到该进程 | 同步故障信号定向到**出错的那个线程**（Ch22：`force_sig_info_to_task` + `PIDTYPE_PID`）；`kill(pid, sig)` 发给进程则由任一线程接 |
| 4 | **能否 `execve`** | ✔ 换掉整个映像 | ✘ 任何线程 `execve` 会**替换整个进程**（其他线程全部消失） |
| 5 | **`fork` 之后** | 子进程是父进程的完整副本 | 子进程**只有调用 `fork` 的那个线程**；锁状态被继承 → 极易死锁（Ch30/Ch33） |
| 6 | **资源限制（`RLIMIT_*`）** | 每进程独立计数 | **整个进程共享**（如 `RLIMIT_NPROC` 数的是线程总数） |
| 7 | **`/proc` 观察** | `/proc/<pid>/` | `/proc/<pid>/task/<tid>/`（29.5） |
| 8 | **调试** | gdb 直接 `attach` | `thread apply all bt`；竞态难复现，需 rr / TSan（03.6 用户态调试） |
| 9 | **权限/凭据切换** | `setuid` 只影响自己 | `setuid` 影响**整个进程的所有线程** |
| 10 | **内存分配失败影响** | OOM 只杀自己 | OOM 杀整个进程（cgroup 视角下也是整个进程） |
| 11 | **核心转储** | 只有自己的地址空间 | **所有线程的栈都在 core 里** |
| 12 | **可移植性** | POSIX 全支持 | Pthreads 需要 `-pthread`，某些老平台不完整 |

第 5 条要特别展开一下：**多线程程序里调用 `fork()` 是危险的**。

```
  父进程                                fork 之后的子进程
  ┌─────────────────────┐              ┌─────────────────────┐
  │ 线程 A（调用 fork）  │   ────────→  │ 线程 A（唯一存活）   │
  │ 线程 B（持有 mutex） │              │ （线程 B 不存在了）  │
  │ 线程 C（正在 IO）    │              │ （线程 C 不存在了）  │
  └─────────────────────┘              └─────────────────────┘
                                         ↓
                                mutex 仍然是「已锁」状态
                                但持有者 B 永远不可能来解锁
                                        ↓
                              子进程第一次 lock 就永久阻塞
```

对策：

- 尽量 `fork` + 立刻 `execve`（中间只调 async-signal-safe 函数）；
- 用 `pthread_atfork()` 注册 prepare/parent/child 三个处理函数（Ch33）；
- 更彻底：用 `posix_spawn()` 或**在启动阶段 fork 完再建线程**。

## 五、故障域：选型的另一半

```
  多线程模型                          多进程模型
  ┌───────────────────────┐          ┌──────┐ ┌──────┐ ┌──────┐
  │      一个进程          │          │ 进程1 │ │ 进程2 │ │ 进程3 │
  │ ┌───┐ ┌───┐ ┌───┐     │          │ 线程 │ │ 线程 │ │ 线程 │
  │ │ T1│ │ T2│ │ T3│     │          └───┬──┘ └───┬──┘ └───┬──┘
  │ └───┘ └───┘ └───┘     │              │        │        │
  │   共享地址空间          │              └─── IPC ───┴────────┘
  └───────────┬───────────┘                  （管道 / 共享内存 / socket）
              │
      T2 段错误 → 整个进程崩
      T3 内存踩踏 → 无人幸免
      T1 死锁 → 可能拖死全部
```

| 故障类型 | 多线程 | 多进程 |
|----------|--------|--------|
| 野指针踩内存 | **全灭** | 只死自己 |
| 栈溢出 | 可能踩到别的线程的栈 | 只死自己 |
| 死锁 | 整个进程的该子系统停摆 | 只停自己，可重启 |
| 内存泄漏 | 累积到 OOM 杀整个进程 | 只杀泄漏的那个，可重启 |
| fd 泄漏 | 全进程共享 fd 表 | 每进程独立 |
| 第三方库崩溃（如解析库） | **全灭** | 隔离在子进程 |
| 恶意输入触发 RCE | 直接拿到整个进程权限 | 沙箱（seccomp/namespace）隔离 |

## 六、选型决策

### 6.1 决策树

```
                    需要并发？
                        │
        ┌───────────────┴───────────────┐
        │                               │
   共享大量可变状态？               不需要共享 / 需要强隔离？
   （订单簿、行情快照、矩阵）        （第三方解析、风控、沙箱）
        │                               │
        ↓                               ↓
   【多线程】                        【多进程】
    + 共享内存零拷贝                  + 崩溃隔离
    + 切换便宜（不换 CR3）            + 可独立重启
    + 同步用锁/futex，纳秒级          + 权限可分离
    ├─ 但要自己管同步                  ├─ 但 IPC 有拷贝成本
    └─ 一个 bug 全灭                   └─ 切换贵（含 Spectre 缓解）
        │                               │
        └───────────► 混合模型 ◄─────────┘
                  （进程内多线程，进程间 IPC）
```

### 6.2 场景对照表

| 场景 | 推荐 | 理由 |
|------|------|------|
| 数值计算 / 矩阵运算 / 图像处理 | **多线程** | 共享大数组，避免拷贝 |
| 高并发网络服务（传统模型） | **多线程 + 事件驱动** | 一个连接一个线程 + epoll |
| 微服务 / 无状态服务 | **多进程** | 可独立重启、滚动升级 |
| 浏览器 / 沙箱 / 插件 | **多进程**（+ 每进程多线程） | 安全隔离是第一优先级 |
| 数据库 | **多进程 + 多线程** | PostgreSQL 是多进程；MySQL 是多线程 |
| 第三方库（XML/JSON/图片解码） | **多进程隔离** | 第三方代码 crash 不影响主流程 |
| 需要 `execve` 换程序 | **多进程** | 线程不能 exec |
| 需要不同权限（`setuid`） | **多进程** | 线程 `setuid` 影响全进程 |
| 内存受限的嵌入式设备 | **多线程**（优先）+ 关键模块多进程 | 页表复制成本高 |
| 虚拟内存很大的进程（>10GB） | **绝对不要 fork** | `dup_mm` 成本与 VM 大小成正比 |

### 6.3 常见架构模式

| 模式 | 代表 | 特点 |
|------|------|------|
| 单线程事件循环 | Redis、nginx（worker 内）、Node.js | 无锁、无竞态；但要避免阻塞调用 |
| Reactor + 线程池 | 多数 Java/C++ 服务 | IO 线程 + 工作线程分离 |
| 一核一线程 + 无锁队列 | **低延迟交易系统**、DPDK | 绑核 + 无锁 SPSC 队列，零系统调用（HFT 首选） |
| master + worker 多进程 | nginx、PostgreSQL | 隔离 + 易重启 |
| 多进程 + 每进程多线程 | Chrome、現代浏览器 | 安全隔离 + 进程内并发 |
| Actor / CSP | Erlang、Go（goroutine 多路复用到线程） | 消息传递代替共享内存 |

## 七、HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **HFT** | **默认多线程 + 绑核 + 无锁队列**：行情解码、策略、风控在同一进程内通过无锁 SPSC 环形队列传递，零拷贝零系统调用 |
| **HFT** | **共享内存是刚需**：订单簿、持仓、行情快照是 MB~GB 级的可变状态，用 IPC 传会因为拷贝而引入微秒级抖动 |
| **HFT** | **但风控 / 网关 / 日志用独立进程**：第三方协议库、复杂解析逻辑、网络栈异常放在独立进程，崩了不影响撮合主链路 |
| **HFT** | **绝不在热路径 fork**：大内存进程 `fork` 要复制页表，几毫秒级。需要子进程就**启动阶段 fork 好**，或用 `posix_spawn` |
| **HFT** | **注意 Spectre 缓解的隐性成本**：进程间切换要跑 `cond_mitigation()`（IBPB/L1D flush），线程间切换不跑。把通信密集的模块放进**同一进程**能省下这部分 |
| **HFT** | 崩溃成本不对称：交易进程崩一次可能损失巨大 → 宁愿多付一点 IPC 成本，也要把高风险组件隔离出去 |
| **嵌入式** | **优先多线程**：内存小、无 MMU 或页表复制昂贵的平台上，`fork` 的代价被放大 |
| **嵌入式** | 但**关键控制回路单独进程**（如电机控制、安全监控），满足功能安全（ISO 26262 / IEC 61508）的独立性要求 |
| **嵌入式** | 8MB 默认栈在嵌入式是奢侈品：线程数一多就爆；必须 `pthread_attr_setstacksize` 调小（29.8） |
| **嵌入式** | 守护 + 重启：多进程模型下用 `PR_SET_PDEATHSIG` 或 systemd 做崩溃重启，比多线程的"整体重启"恢复快 |

## 八、代码示例：`tp_bench.c`

实测三组开销：**创建销毁**、**切换**、**共享语义验证**。

```c
/* tp_bench.c — 29.9 线程 vs 进程：创建开销、切换开销、共享语义对比
 *
 * 编译: gcc -O2 -Wall -Wextra -o tp_bench tp_bench.c -pthread
 * 运行: ./tp_bench
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <sched.h>
#include <pthread.h>
#include <time.h>
#include <sys/wait.h>
#include <sys/mman.h>

#define N 200

static pthread_mutex_t out_mu = PTHREAD_MUTEX_INITIALIZER;

static void say(const char *fmt, ...)
{
    char body[512];
    va_list ap;
    va_start(ap, fmt);
    vsnprintf(body, sizeof body, fmt, ap);
    va_end(ap);
    pthread_mutex_lock(&out_mu);
    fprintf(stderr, "%s\n", body);
    pthread_mutex_unlock(&out_mu);
}

static double now_us(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e6 + ts.tv_nsec / 1e3;
}

/* 让优化器不敢干掉循环 */
static volatile long sink;

/* ───────────────────────────────────────────────────────────
 * 演示 1：创建 + 回收 开销对比
 * ─────────────────────────────────────────────────────────── */
static void *noop_thread(void *arg) { sink += (long)arg; return NULL; }

static void bench_thread_create(void)
{
    pthread_t t;
    double t0 = now_us();
    for (int i = 0; i < N; i++) {
        pthread_create(&t, NULL, noop_thread, (void *)(long)1);
        pthread_join(t, NULL);
    }
    double dt = (now_us() - t0) / N;
    say("  线程: pthread_create + pthread_join × %d → 平均 %.1f μs/轮", N, dt);
}

static void bench_fork(void)
{
    double t0 = now_us();
    for (int i = 0; i < N; i++) {
        pid_t p = fork();
        if (p == 0)
            _exit(0);                   /* 子进程立刻退出 */
        int st;
        waitpid(p, &st, 0);
    }
    double dt = (now_us() - t0) / N;
    say("  进程: fork + waitpid           × %d → 平均 %.1f μs/轮", N, dt);
    say("  ↑ 差距主要来自 copy_mm() 里的 dup_mm()（复制 VMA 树 + 页表）");
    say("    fork 的开销与父进程虚拟内存大小成正比，不是常数！");
}

/*
 * 故意把虚拟内存撑大，观察 fork 成本变化。
 *
 * ★ 关键：必须【触碰】每一页，把页表真正建立起来，才能看出差别。
 *   只 mmap 不触碰的话，内核连一个 PTE 都没分配，dup_mm() 只需要多复制
 *   一个 VMA 结构体 —— 成本几乎为 0，根本测不出来。
 *   这正是「COW 省的是物理页，不省页表结构」的直接证据。
 */
static void bench_fork_with_big_vm(void)
{
    size_t sz = 512UL << 20;            /* 512MB */
    size_t ps = (size_t)sysconf(_SC_PAGESIZE);
    void *p = mmap(NULL, sz, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);
    if (p == MAP_FAILED) { say("  mmap 512MB 失败: %s", strerror(errno)); return; }

    /* ① 只映射、不触碰：只有 1 个 VMA，页表是空的 */
    double t0 = now_us();
    for (int i = 0; i < N; i++) {
        pid_t c = fork();
        if (c == 0) _exit(0);
        int st;
        waitpid(c, &st, 0);
    }
    double dt_untouched = (now_us() - t0) / N;
    say("  进程(VM +512MB 未触碰): fork + waitpid → 平均 %.1f μs/轮", dt_untouched);
    say("    ↑ 与基线几乎无差：页表还是空的，dup_mm() 只多复制一个 VMA 结构");

    /* ② 触碰每一页，把 512MB/4KB = 131072 个 PTE 真正建立起来 */
    for (size_t off = 0; off < sz; off += ps)
        ((volatile char *)p)[off] = 1;

    t0 = now_us();
    for (int i = 0; i < N; i++) {
        pid_t c = fork();
        if (c == 0) _exit(0);
        int st;
        waitpid(c, &st, 0);
    }
    double dt_touched = (now_us() - t0) / N;
    say("  进程(VM +512MB 已触碰): fork + waitpid → 平均 %.1f μs/轮", dt_touched);
    say("    ↑ 明显变慢：dup_mm() 要复制 %zu 个已建立的页表项（PGD/PUD/PMD/PTE）",
        sz / ps);
    say("    ↑ COW 省的是【物理页的拷贝】，不省【页表结构的拷贝】—— 即使子进程立刻 _exit，"
        "父亲也已经付过这份钱了");

    munmap(p, sz);
}

static void demo_create_cost(void)
{
    say("演示1: 创建 + 回收 开销");
    bench_thread_create();
    bench_fork();
    bench_fork_with_big_vm();
}

/* ───────────────────────────────────────────────────────────
 * 演示 2：上下文切换开销（用 pipe 在两个执行体之间来回乒乓）
 * ─────────────────────────────────────────────────────────── */
#define PINGPONG 20000

static int ping_w, ping_r;

/* 显式吞掉返回值，避免 -Wunused-result 刷屏（这里是基准测试，重点在时序） */
static void xfer(int fd, void *buf, size_t n, int is_write)
{
    ssize_t r = is_write ? write(fd, buf, n) : read(fd, buf, n);
    (void)r;
}

/* ★ 关键：把整个进程钉在同一个 CPU 上。
 * 不绑核的话，多核空闲时两个执行体会【并行】跑在两颗核上，
 * 根本不发生上下文切换 —— 测出来的只是 pipe 的延迟，线程和进程一样快。
 * 只有钉在同一颗核上，每次乒乓才强制一次真正的 context_switch()。 */
static int pin_to_cpu(int cpu)
{
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    /* 主线程设亲和性后，后续 pthread_create / fork 都会继承 */
    return sched_setaffinity(0, sizeof set, &set);
}

static void *pingpong_thread(void *arg)
{
    (void)arg;
    char c;
    for (int i = 0; i < PINGPONG; i++) {
        xfer(ping_r, &c, 1, 0);
        xfer(ping_w, &c, 1, 1);
    }
    return NULL;
}

static double bench_switch_threads(void)
{
    int fd[2], fd2[2];
    if (pipe(fd) || pipe(fd2)) { say("  pipe 失败: %s", strerror(errno)); return 0; }
    ping_w = fd2[1]; ping_r = fd[0];

    pthread_t t;
    if (pthread_create(&t, NULL, pingpong_thread, NULL) != 0) return 0;

    double t0 = now_us();
    char c = 'x';
    for (int i = 0; i < PINGPONG; i++) {
        xfer(fd[1], &c, 1, 1);
        xfer(fd2[0], &c, 1, 0);
    }
    double dt = (now_us() - t0) / (PINGPONG * 2);
    pthread_join(t, NULL);

    close(fd[0]); close(fd[1]); close(fd2[0]); close(fd2[1]);
    say("  线程乒乓: %.2f μs/次切换（含 2 次系统调用，同核强制切换）", dt);
    return dt;
}

static double bench_switch_processes(void)
{
    int fd[2], fd2[2];
    if (pipe(fd) || pipe(fd2)) { say("  pipe 失败: %s", strerror(errno)); return 0; }

    pid_t p = fork();
    if (p == 0) {
        char c;
        close(fd[1]); close(fd2[0]);
        for (int i = 0; i < PINGPONG; i++) {
            xfer(fd[0], &c, 1, 0);
            xfer(fd2[1], &c, 1, 1);
        }
        _exit(0);
    }
    close(fd[0]); close(fd2[1]);

    double t0 = now_us();
    char c = 'x';
    for (int i = 0; i < PINGPONG; i++) {
        xfer(fd[1], &c, 1, 1);
        xfer(fd2[0], &c, 1, 0);
    }
    double dt = (now_us() - t0) / (PINGPONG * 2);
    int st; waitpid(p, &st, 0);
    close(fd[1]); close(fd2[0]);

    say("  进程乒乓: %.2f μs/次切换（含 2 次系统调用，同核强制切换）", dt);
    return dt;
}

static void demo_switch_cost(void)
{
    say("演示2: 上下文切换开销（pipe 乒乓，两个执行体同钉 CPU 0）");

    int ncpu = (int)sysconf(_SC_NPROCESSORS_ONLN);
    if (ncpu < 1) ncpu = 1;
    pin_to_cpu(0);                  /* 不绑核的话两个执行体会并行，测不到切换 */

    double th = bench_switch_threads();
    double pr = bench_switch_processes();

    say("  ── 对比 ──");
    say("  线程乒乓 = %.2f μs/次   进程乒乓 = %.2f μs/次   差值 = %+.2f μs (%.0f%%)",
        th, pr, pr - th, th > 0 ? 100.0 * (pr - th) / th : 0.0);
    say("  ↑ 进程侧多出来的 ≈ 写 CR3 + 换 ASID + cond_mitigation()");
    say("    arch/x86/mm/tlb.c:562（同 mm 早退）vs :612（进程间才跑 Spectre 缓解）");
    say("  ⚠ 注意：这是【微基准】，绝对值受机器负载、Spectre 缓解开关、CPU 频率、");
    say("    虚拟化层（WSL/云主机）影响极大。请关注【相对差值】而不是绝对值，");
    say("    并且多跑几次取趋势。虚拟化环境下这个差值可能被噪声淹没。");
}

/* ───────────────────────────────────────────────────────────
 * 演示 3：共享语义验证（地址空间 / fd 偏移 / 变量可见性）
 * ─────────────────────────────────────────────────────────── */
static int shared_var = 42;

static void *worker_share(void *arg)
{
    (void)arg;
    say("  [线程] shared_var=%d  地址=%p  → 改成 99",
        shared_var, (void *)&shared_var);
    shared_var = 99;
    say("  [线程] 改完 shared_var=%d", shared_var);
    return NULL;
}

static void demo_sharing(void)
{
    say("演示3: 共享语义验证");

    say("  ── 线程：共享地址空间 ──");
    say("  [主线程] shared_var=%d 地址=%p", shared_var, (void *)&shared_var);
    pthread_t t;
    pthread_create(&t, NULL, worker_share, NULL);
    pthread_join(t, NULL);
    say("  [主线程] 线程改完后我读到 shared_var=%d  → 同一个对象", shared_var);

    shared_var = 42;

    say("  ── 进程：独立地址空间（写时复制）──");
    pid_t p = fork();
    if (p == 0) {
        say("  [子进程] shared_var=%d 地址=%p（与父进程虚拟地址相同，但页不同）",
            shared_var, (void *)&shared_var);
        shared_var = 99;
        say("  [子进程] 改成 99 后我读到 %d", shared_var);
        _exit(0);
    }
    int st; waitpid(p, &st, 0);
    say("  [父进程] 子进程改完后我读到 shared_var=%d  → 各写各的", shared_var);

    say("  ── fd 偏移：fork 也共享 struct file！ ──");
    FILE *fp = tmpfile();
    if (fp) {
        fprintf(fp, "0123456789");
        fflush(fp);
        int fdnum = fileno(fp);
        lseek(fdnum, 0, SEEK_SET);

        pid_t q = fork();
        if (q == 0) {
            char buf[4] = {0};
            xfer(fdnum, buf, 3, 0);         /* 子进程读 3 字节，偏移从 0 → 3 */
            _exit(0);
        }
        waitpid(q, NULL, 0);
        off_t off = lseek(fdnum, 0, SEEK_CUR);
        say("  子进程读了 3 字节后，父进程看到偏移 = %ld", (long)off);
        say("  ↑ 非 0 说明 fork 复制的是 fd 表，但 struct file（含偏移）是共享的");
        fclose(fp);
    }
}

/* ───────────────────────────────────────────────────────────
 * 演示 4：崩溃影响域对比（放在子进程里演示，不炸主程序）
 * ─────────────────────────────────────────────────────────── */
static void *worker_sleep(void *arg)
{
    (void)arg;
    for (int i = 0; i < 5; i++) {
        say("  [健康线程] 我还活着，第 %d 次心跳", i);
        usleep(50 * 1000);
    }
    return NULL;
}

static void *worker_crash(void *arg)
{
    (void)arg;
    usleep(120 * 1000);
    say("  [崩溃线程] 我要踩野指针了…");
    fflush(stderr);
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Warray-bounds"      /* 故意踩低地址，触发 SIGSEGV */
    *(volatile int *)0x10 = 1;
#pragma GCC diagnostic pop
    return NULL;
}

static void demo_crash_domain(void)
{
    say("演示4: 崩溃影响域（在子进程里跑，避免炸掉主程序）");

    pid_t p = fork();
    if (p == 0) {
        pthread_t healthy, crasher;
        pthread_create(&healthy, NULL, worker_sleep, NULL);
        pthread_create(&crasher, NULL, worker_crash, NULL);
        pthread_join(healthy, NULL);        /* 永远等不到 */
        pthread_join(crasher, NULL);
        say("  [主] 不应该打印到这一行");
        _exit(0);
    }
    int st = 0;
    waitpid(p, &st, 0);
    if (WIFSIGNALED(st))
        say("  整个进程被信号 %d 杀死（SIGSEGV=11）→ 健康线程也被拖死", WTERMSIG(st));
    else
        say("  子进程正常退出（意外，检查演示逻辑）");
    say("  ↑ 多线程：一个线程段错误 = 整个进程全灭（信号处置是进程级共享的）");
    say("    多进程：只死自己，父进程可以立刻 fork 一个新的顶上");
}

/* ───────────────────────────────────────────────────────────
 * 演示 5：内核视角速查 —— 打印线程/进程的 /proc 观察点
 * ─────────────────────────────────────────────────────────── */
static void *worker_proc(void *arg) { (void)arg; usleep(300 * 1000); return NULL; }

static void demo_proc_view(void)
{
    say("演示5: /proc 视角 —— 内核把线程当作 task_struct 一视同仁");
    pthread_t t[3];
    for (int i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, worker_proc, NULL);

    say("  PID（=TGID）= %ld", (long)getpid());
    say("  TID（内核 pid）= %ld  ← 主线程的 tid == pid", (long)gettid());
    say("  观察命令（另开终端，在本进程存活期间执行）：");
    say("    ls /proc/%ld/task/          → 4 个目录（1 主 + 3 线程）", (long)getpid());
    say("    ps -eLf | grep tp_bench     → 4 行，PID 相同，LWP 不同");
    say("    cat /proc/%ld/status | grep Threads", (long)getpid());

    char cmd[256];
    snprintf(cmd, sizeof cmd,
             "echo -n '  实际线程数: '; ls /proc/%ld/task | wc -l", (long)getpid());
    if (system(cmd) != 0) say("  (system 调用失败)");

    for (int i = 0; i < 3; i++)
        pthread_join(t[i], NULL);
}

int main(void)
{
    say("=== 29.9 线程 vs 进程 ===");
    demo_create_cost();
    demo_switch_cost();
    demo_sharing();
    demo_crash_domain();
    demo_proc_view();
    say("=== 演示结束 ===");
    return 0;
}
```

| 演示 | 期望结果 |
|------|----------|
| 1 | 线程创建明显快于 `fork`（实测 2.3×）；**未触碰的 512MB 几乎不影响**，**已触碰的 512MB 让 fork 涨 20 倍** |
| 2 | 进程乒乓比线程乒乓略贵（实测 +3%，虚拟化环境下噪声大）；**关注相对差值而非绝对值** |
| 3 | 线程改 `shared_var` 主线程可见；进程改了不可见；**但 fd 偏移两者都共享** |
| 4 | 一个线程 `SIGSEGV` → 整个进程被 11 号信号杀死，健康线程戛然而止 |
| 5 | `/proc/<pid>/task` 下 4 个目录，`ps -eLf` 4 行同 PID 不同 LWP |

> **⚠ 关于演示 2 的诚实说明**：这是一个**微基准**，每次乒乓含 2 次 pipe 系统调用，
> 而 CR3 写入 + ASID 切换 + `cond_mitigation()` 只是其中一小部分（亚微秒到几微秒）。
> 在虚拟化环境（WSL / 云主机）里，系统调用本身就贵，这部分差值很容易被噪声淹没。
>
> 想看清这个差值，可以：
> - 多跑几次取趋势
> - 在**物理机**上跑（虚拟化会放大 syscall 成本）
> - 用 `perf stat -e tlb:tlb_flush,dTLB-load-misses` 观察 TLB 行为差异
> - 或直接对比 `grep bugs /proc/cpuinfo` 里的 Spectre 缓解开关前后的数值

## 代码自测

<details>
<summary>1. 「Linux 内核不区分进程和线程」具体是什么意思？</summary>

**内核只认识 `task_struct` 和 `CLONE_*` 标志位，没有独立的「线程」对象。**

`fork()`、`vfork()`、`pthread_create()`、`clone3()` **全部**走同一个 `copy_process()`（`kernel/fork.c:2240`），差别只是传入的 `clone_flags`：

```
  fork()            → 只有 CSIGNAL 位（SIGCHLD）
  vfork()           → CLONE_VFORK | CLONE_VM | SIGCHLD
  pthread_create()  → CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD
                      |CLONE_SYSVSEM|CLONE_SETTLS|CLONE_PARENT_SETTID
                      |CLONE_CHILD_SETTID|CLONE_CHILD_CLEARTID
```

`copy_process` 内部按 flag 决定每一项资源是「复制」还是「共享引用」：

| 内核函数（行号） | 有对应 flag | 无对应 flag |
|------------------|------------|------------|
| `copy_mm():1708`（分支 `:1731`） | `mmget()` +1（O(1)） | `dup_mm()` 复制页表（O(页数)） |
| `copy_files():1766`（分支 `:1784`） | `atomic_inc()`（O(1)） | `dup_fd()` 复制 fd 表 |
| `copy_sighand():1799`（分支 `:1803`） | `refcount_inc()`（O(1)） | `kmem_cache_alloc` + `memcpy` |

内核还强制两条依赖（`:2267`、`:2275`）：

```
  CLONE_THREAD  ⟹  CLONE_SIGHAND  ⟹  CLONE_VM
```

所以「进程」和「线程」是**用户态给两组不同 flag 组合起的名字**。内核层面只看到「一组共享多少东西的 `task_struct`」。
</details>

<details>
<summary>2. 线程上下文切换比进程便宜，机制上到底便宜在哪？</summary>

调度器一视同仁：**所有 `task_struct` 的切换都调用 `context_switch()`（`kernel/sched/core.c:5324`）**，而它在 `:5364` **无条件**调用 `switch_mm_irqs_off()`。

真正的分叉在 x86 实现（`arch/x86/mm/tlb.c:495`）：

```c
struct mm_struct *real_prev = this_cpu_read(cpu_tlbstate.loaded_mm);   /* :497 */
...
if (real_prev == next) {                            /* :562 */
    /* Not actually switching mm's */
    /*
     * If the CPU is not in lazy TLB mode, we are just switching
     * from one thread in a process to another thread in the same
     * process. No TLB flush required.                    /* :584 */
     */
    if (!was_lazy)
        return;                                     /* :586 ← 直接返回 */
    ...
} else {
    cond_mitigation(tsk);                           /* :612 */
    choose_new_asid(next, next_tlb_gen, &new_asid, &need_flush);
    load_new_mm_cr3(next->pgd, new_asid, new_lam, ...);   /* 写 CR3 */
}
```

**三层节省**：

| 层次 | 线程切换 | 进程切换 |
|------|---------|---------|
| ① 写 CR3 / 换页表 | **否**（`:562` 早退，不执行 `load_new_mm_cr3`） | 是 |
| ② 刷 TLB / 换 ASID | **否**，TLB 条目和页表缓存全部保留 | 是（`choose_new_asid` + 可能的 flush） |
| ③ Spectre 缓解 | **否** | **是**（`cond_mitigation():612` → IBPB / L1D flush / RSB 等） |

第 ③ 点在开启 Spectre 缓解的现代内核上尤其显著——IBPB 本身就要几百纳秒到微秒。

**但别误会**：线程切换**不是零成本**。

- 寄存器、栈指针照样要换；
- **L1/L2 数据缓存照样被污染**（两个线程数据集不同）；
- 内核栈、内核态数据结构照样要切换引用。

所以 HFT 的终极做法是把不同职责的线程**绑到不同物理核**（`pthread_attr_setaffinity_np`，29.8），连这一层都省掉。
</details>

<details>
<summary>3. 为什么线程退出不像进程那样产生僵尸？</summary>

因为内核在 `exit_notify()` 里对**非线程组 leader** 直接走 `autoreap = true`：

```c
/* kernel/exit.c:739-756 */
	tsk->exit_state = EXIT_ZOMBIE;                      /* :739 先一律标僵尸 */
	if (unlikely(tsk->ptrace)) {
		...
		autoreap = do_notify_parent(tsk, sig);
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&
			do_notify_parent(tsk, tsk->exit_signal);
	} else {
		autoreap = true;                                /* :750 ← 非 leader：恒为真 */
	}

	if (autoreap) {                                     /* :753 */
		tsk->exit_state = EXIT_DEAD;                    /* :754 立刻转 DEAD */
		list_add(&tsk->ptrace_entry, &dead);
	}
```

三个配合点：

1. **线程根本不发 `SIGCHLD`**。创建时 `CLONE_THREAD` 让 `exit_signal = -1`（`kernel/fork.c:2632-2633`），所以没有「通知父进程」这一步；
2. **`autoreap = true`** → 立即 `EXIT_DEAD` → `release_task()` 回收 `task_struct`；
3. **没有 `wait()` 接口能收线程**。`waitpid()` 只收子进程。

**所以所谓「僵尸线程」泄漏的从来不是内核资源，而是 glibc 的 `struct pthread` + 8MB 用户栈**（见 29.6 / 29.7）。

**一个容易被忽略的边界**：线程组 leader 的判断是 `thread_group_empty(tsk)`——**如果 leader 自己退出时还有别的线程活着，`autoreap` 为假**，leader 会短暂进僵尸态，等最后一个线程走完（`find_alive_thread():572`）才被收。这也是为什么「主线程 `pthread_exit()` 而不是 `return`」时进程不会立刻消失（29.4）。
</details>

<details>
<summary>4. 多线程程序里调用 `fork()` 为什么危险？</summary>

**因为子进程只会复制调用 `fork` 的**那一个线程，其他线程连同它们持有的锁一起消失。

```
  父进程                                fork 之后的子进程
  ┌─────────────────────┐              ┌─────────────────────┐
  │ 线程 A（调用 fork）  │   ────────→  │ 线程 A（唯一存活）   │
  │ 线程 B（持有 mutex） │              │ （B 不存在了）       │
  └─────────────────────┘              └─────────────────────┘
                                         ↓
                                mutex 仍是「已锁」状态
                                持有者 B 永远不会来解锁
                                        ↓
                              子进程第一次 lock 就永久阻塞
```

**其他同样会坏的东西**：

- `malloc` 的 arena 锁（glibc 内部锁可能处于已锁状态）
- stdio 的 `FILE` 锁
- 任何用互斥锁保护的全局结构（日志缓冲、连接池……）
- `pthread` 内部数据结构处于中间状态

**对策（按推荐度排序）**：

| # | 对策 | 说明 |
|---|------|------|
| ① | **`fork` 之后立刻 `execve`** | 子进程一 `exec` 就换了地址空间，脏状态全丢。中间只调 async-signal-safe 函数 |
| ② | **`pthread_atfork()` 注册三件套** | prepare（fork 前拿所有锁）→ parent（fork 后在父进程释放）→ child（fork 后在子进程重置）。详见 Ch33 |
| ③ | **用 `posix_spawn()`** | 库内部处理了这些细节，通常是 `clone(CLONE_VM|CLONE_VFORK)` + `exec` |
| ④ | **架构上规避：启动阶段 fork 完再建线程** | 最干净。进程树在并发开始前就定好 |

> **HFT 视角**：这类死锁**只在特定时序下复现**，是最贵的一类 bug。
> 架构上做到「热路径永不 fork」比事后打补丁划算得多。
</details>

<details>
<summary>5. 「`fork` 的开销是常数」这个说法对吗？给出内核依据和实际影响。</summary>

**不对。`fork` 的开销与父进程的虚拟内存大小（更准确说是 VMA 数量和页表层级深度）成正比。**

内核依据在 `copy_mm()`（`kernel/fork.c:1708`）：

```c
	if (clone_flags & CLONE_VM) {
		mmget(oldmm);                   /* 线程：O(1) */
		mm = oldmm;
	} else {
		mm = dup_mm(tsk, current->mm);  /* 进程：O(VMA 数 + 页表项数) */
		if (!mm)
			return -ENOMEM;
	}
```

`dup_mm()` 要：新分配 `mm_struct` → 遍历复制整棵 VMA 树（每个 VMA 一次 `kmem_cache_alloc`）→ 逐级复制 PGD/P4D/PUD/PMD/PTE → 初始化锁和统计。虚拟内存越大，VMA 越多、页表越深，就越慢。

**本机实测**（WSL2 / 12 核，`tp_bench` 演示 1；原生 Linux 绝对值会小很多，看倍数）：

| 场景 | 实测值 |
|------|--------|
| `pthread_create` + `join` | 420.6 μs |
| `fork` + `waitpid`（基线） | 986.3 μs（2.3×） |
| `fork` + `waitpid`（VM +512MB **未触碰**） | 1044.0 μs（+6%，几乎无差） |
| `fork` + `waitpid`（VM +512MB **已触碰**） | **21129.3 μs（21×）** |

> **这组数字纠正了一个常见误解**：很多人以为「`fork` 因为 COW 所以很便宜」。
> 实测说明——**只有没触碰过的内存才便宜**；一旦页表建立起来，`dup_mm()` 的成本就是实打实的。

**实际影响**：

| 领域 | 结论 |
|------|------|
| **HFT** | **热路径绝不用 fork**。占几十 GB 虚拟内存的交易进程 `fork` 一次要几毫秒。需要子进程就在**启动阶段 fork 好**，或用 `posix_spawn` |
| 嵌入式 | 同样避免；`vfork` / `posix_spawn` 是首选 |
| Redis | 这就是为什么 Redis 的 `BGSAVE` 要在文档里警告：`fork` 的延迟与数据集大小成正比（尽管有 COW，页表复制仍要付） |
| 一般服务 | `posix_spawn` 通常比 `fork` + `exec` 更快，因为它用 `CLONE_VFORK|CLONE_VM` 避免复制页表 |

> **顺带一个常见误解**：COW（写时复制）省的是**物理页的拷贝**，不省**页表结构的拷贝**。
> 即使子进程立刻 `_exit()`，父进程也已经为复制页表付过钱了。
</details>
