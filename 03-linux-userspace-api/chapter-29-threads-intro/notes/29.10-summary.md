## 二、五个反直觉真相（本章最值钱的部分）

| # | 直觉 | 真相 | 内核依据 |
|---|------|------|----------|
| **①** | 「线程」是内核里的一类对象 | **内核只有 `task_struct`**，`fork`/`vfork`/`pthread_create` 全是 `copy_process()` | `kernel/fork.c:2240`；差别只在 `clone_flags` |
| **②** | 忘了 join 会留「僵尸线程」占内核资源 | **内核 `autoreap` 立即回收** `task_struct`；泄漏的是 glibc 的 8MB 栈 + `struct pthread` | `kernel/exit.c:750` 非 leader 恒 `autoreap = true`；`:753-756` 立即 `EXIT_DEAD` |
| **③** | `pthread_join` 在轮询 | 它**睡在 futex 上**；线程退出时内核清 TID 并 `FUTEX_WAKE` | `kernel/fork.c:1634-1635` |
| **④** | `getpid()` 返回当前线程 ID | 返回的是 **TGID**（线程组 ID），所有线程相同；要区分用 `gettid()` | `kernel/sys.c:958` / `:964` |
| **⑤** | 线程切换因为「不换页表」而便宜 | 具体是 `real_prev == next` 时 **早退**：不写 CR3、不换 ASID、**不跑 `cond_mitigation()`**（Spectre 缓解） | `arch/x86/mm/tlb.c:562` / `:584-586` / `:612` |

### 4.2 属性

```c

pthread_attr_setdetachstate (&attr, PTHREAD_CREATE_{JOINABLE,DETACHED});
pthread_attr_setstacksize   (&attr, bytes);          /* ≥ PTHREAD_STACK_MIN(16384) */
pthread_attr_setstack       (&attr, addr, size);     /* addr = 最低地址；无保护页 */

pthread_getschedparam(t, &pol, &sp);

### 4.3 返回值约定（29.2）

| | Pthreads 系列 | 传统 libc |
|---|---|---|
| 成功 | 返回 **0** | 返回 0 或有效句柄 |
| 失败 | 返回**正错误码**（`EAGAIN`/`EINVAL`/`EPERM`/`ESRCH`/…） | 返回 -1 |
| `errno` | **不设置** | 设置 |
| 判断写法 | `if ((rc = pthread_create(...)) != 0)` | `if (... < 0)` |

## 五、十条铁律

| # | 铁律 | 违反后果 |
|---|------|----------|
| 1 | **用 `-pthread` 编译链接**，不是 `-lpthread` | glibc 2.34+ 后 `-lpthread` 是空壳，符号找不到 / 行为异常 |
| 2 | **返回值是错误码，不设 `errno`** | 判断写成 `== -1` 永远不触发，错误被吞掉 |
| 3 | **线程里禁用 `exit()`** | `exit_group` → `zap_other_threads()` 杀光所有线程 |
| 4 | **每个线程必须 join 或 detach，契约唯一** | 泄漏 8MB 栈/线程；或 detach 静默失效 |
| 5 | **不用 `==` 比较 `pthread_t`** | 类型不透明，不可移植；用 `pthread_equal()` |
| 6 | **别把即将失效的栈地址传给新线程** | 循环变量取址、局部变量取址 → 读到垃圾 |
| 7 | **`getpid()` 返回 TGID 不是线程 ID** | 日志里所有线程 ID 一样，问题定位不了 |
| 8 | **设调度属性必须同时设 `PTHREAD_EXPLICIT_SCHED`** | 静默失效，延迟特性完全不对 |
| 9 | **栈上不放 > guardsize(4KB) 的对象** | 大数组一步跨过保护页，静默踩到别的线程栈 |
| 10 | **detach ≠ 进程会等；要确认就 joinable** | 主线程 return 时 detached 线程照样被杀 |

## 六、三条隐藏成本（容易被忽略的开销）

| 项 | 数值 | 说明 |
|----|------|------|
| **用户栈** | 默认 **8MB/线程**（虚拟） | 按需分页，实际 RSS 远小于此；但 VIRT 会实打实上涨 |
| **内核栈** | **16KB/线程**（物理，立即占用） | `THREAD_SIZE = PAGE_SIZE << 2`（`arch/x86/include/asm/page_64_types.h:16`），走 `__vmalloc_node_range`（`kernel/fork.c:309`）；内核做了缓存复用（`:303-306`） |
| **退出时的空 futex 唤醒** | ~1 μs/次 | `mm_release():1635` 的 `do_futex()` 无论有没有等待者都会执行 |

**算一笔账**：1000 个线程

- 用户栈虚拟内存：8 GB（VIRT；实际 RSS 可能只有几十 MB）
- 内核栈物理内存：**16 MB**（真实占用）
- 每线程创建 ~20-50 μs：1000 个 = 20-50 ms（一次性）

**结论**：用户栈靠调小 `stacksize` 解决（29.8）；内核栈无解，是线程模型的固有成本。

       │            │     └─────────────►└─────────────►└────────────►│       │

       │            └─────────────────────────────────────────────────┼───────┘
       │                                                              │

**关键设计决策**：

| 决策 | 理由 | 对应本节/章节 |
|------|------|--------------|
| 同一进程内多线程 | 订单簿 / 持仓是 MB~GB 级可变状态，IPC 拷贝会引入微秒级抖动 | 29.9 |
| 一核一线程 + 绑核 | 连缓存污染都省掉；零上下文切换 | 29.8 `setaffinity_np` |
| SPSC 无锁队列 | 关键路径零系统调用、零锁 | Ch30 之后 |
| `SCHED_FIFO` 分层优先级 | 行情 > 策略 > 风控 > 落盘 | 29.8 + [Ch35](../../chapter-35-process-priorities-scheduling/README.md) |
| 日志 / 网关独立进程 | 第三方库、复杂解析崩溃不影响撮合主链路 | 29.9 故障域 |
| 启动期建好所有线程 | 热路径零 `pthread_create`/`join`/`detach` | 29.7 |
| 线程全部 joinable + `timedjoin_np` | 关停时能确认落盘完成 | 29.6 |
| 栈调小到 256KB~1MB + guard 64KB | 减少 VIRT；挡住常见的大帧 | 29.8 |

### 7.2 嵌入式推荐架构

| 约束 | 对策 |
|------|------|
| 内存几十 MB | `pthread_attr_setstacksize(16~64KB)`；线程数控制在 10~50 |
| 无 MMU（uClinux） | guardsize 无效，靠 `-fstack-usage` 静态分析；栈是实打实物理内存 |
| 需要功能安全独立性 | 关键控制回路单独进程（`setuid` / 命名空间隔离），主逻辑多线程 |
| 长期运行不能重启 | 看门狗 + 心跳线程（detached，方式③）；异常时独立重启子进程 |
| 实时性 | `SCHED_FIFO` + `RLIMIT_RTPRIO`（不用 root）+ 绑核 |

## 代码自测

<details>
<summary>1. 用一句话说清「Linux 里的线程是什么」，并给出内核依据。</summary>

**线程 = 一组带 `CLONE_THREAD` 标志、共享同一 `mm_struct` 的 `task_struct`。内核里没有独立的「线程」对象。**

依据三条：

1. **同一个创建入口**：`fork()`、`vfork()`、`pthread_create()`、`clone3()` 全部走 `copy_process()`（`kernel/fork.c:2240`），差别只是 `clone_flags`。
2. **每项资源按 flag 决定复制还是共享**（调用点集中在 `:2489-2510`）：

   | 资源 | 内核函数 | 有 flag | 无 flag |
   |------|----------|---------|---------|
   | 地址空间 | `copy_mm():1708`（分支 `:1731`） | `mmget()` O(1) | `dup_mm()` O(页数) |
   | fd 表 | `copy_files():1766`（分支 `:1784`） | `atomic_inc()` | `dup_fd()` |
   | 信号处理 | `copy_sighand():1799`（分支 `:1803`） | `refcount_inc()` | alloc + `memcpy` |

3. **内核强制两条依赖**（`:2267`、`:2275`）：

   ```
   CLONE_THREAD  ⟹  CLONE_SIGHAND  ⟹  CLONE_VM
   ```

所以「进程」和「线程」是**用户态给两组不同 flag 组合起的名字**。内核只看到「一组共享多少东西的 `task_struct`」。
</details>

<details>
<summary>2. 线程的生命周期在内核里是怎么闭环的？画出从创建到回收的完整路径。</summary>

```
  pthread_create(&t, &attr, fn, arg)
        │  glibc: mmap 栈(guardsize+stacksize+TCB) + mprotect guard PROT_NONE
        │         clone(CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD

        │    ├─ copy_mm / copy_fs / copy_files /

        │    ├─ put_user(0, clear_child_tid)           :1634   ← TID 清零

**三个关键分叉点**：

- `:2632-2633` — 线程 `exit_signal = -1`，所以**不发 SIGCHLD**，`wait()` 收不到
- `:750` — 非 leader 恒 `autoreap = true`，所以**内核里没有僵尸线程**
- glibc 层 — joinable 保留 TCB 等 join；detached 立即 `__free_tcb()`

**进程退出时的另一条路**（29.4）：
`exit_group:1033` → `do_group_exit():999` → `zap_other_threads()`（`kernel/signal.c:1378`，遍历挂 SIGKILL `:1394-1395`）→ 所有线程一起死。

<summary>3. 「忘了 join 会留僵尸线程」这个说法准确吗？</summary>

**不准确。内核里根本没有僵尸线程。**

内核 `exit_notify()`（`kernel/exit.c:727`）对非线程组 leader 直接走：

```c
	tsk->exit_state = EXIT_ZOMBIE;              /* :739  先一律标僵尸 */
	if (unlikely(tsk->ptrace)) {
		...
	} else if (thread_group_leader(tsk)) {
		autoreap = thread_group_empty(tsk) &&
			do_notify_parent(tsk, tsk->exit_signal);
	} else {
		autoreap = true;                        /* :750 ← 非 leader：恒为真 */
	}

	if (autoreap) {                             /* :753 */
		tsk->exit_state = EXIT_DEAD;            /* :754  立刻转 DEAD */
		list_add(&tsk->ptrace_entry, &dead);
	}
```

配合 `exit_signal = -1`（`kernel/fork.c:2632-2633`，线程不发 `SIGCHLD`），结果是：

- `task_struct` **立即**被 `release_task()` 回收
- 没有 `wait()` 接口能收线程
- `/proc/<pid>/task/` 里看不到它

**泄漏的到底是什么？** glibc 用户态的两样东西：

1. **8MB 用户栈**（虚拟内存，VIRT 实打实上涨）
2. **`struct pthread` / TCB**（在栈区高端，几 KB）

**怎么观测**：`cat /proc/self/statm` 的 VIRT 字段；或者 `pmap -x <pid>` 数匿名映射数量。
`detach_demo`（29.7 演示 7）会打出「泄漏 30 个 → VIRT 上涨 → 补 join → 立刻回落」的完整曲线。

**顺带一个边界**：leader 的判断是 `thread_group_empty(tsk)`——**leader 自己退出时若还有别的线程活着，`autoreap` 为假**，leader 会短暂进僵尸态，等最后一个线程走完（`find_alive_thread():572`）才被收。这也是「主线程 `pthread_exit()` 而不是 `return`」时进程不会立刻消失的原因（29.4）。
</details>

<details>
<summary>4. 为什么 `pthread_detach` 在内核里找不到对应实现？那 detached 线程退出的内核路径是什么？</summary>

**因为 detach 完全是 glibc 用户态的概念，内核不知道也不需要知道。**

内核对每个线程（无论 joinable 还是 detached）在 `mm_release()`（`kernel/fork.c:1616`）里执行**完全相同的**一对动作：

```c
	if (tsk->clear_child_tid) {
		if (atomic_read(&mm->mm_users) > 1) {
			put_user(0, tsk->clear_child_tid);         /* :1634  TID 写 0 */
			do_futex(tsk->clear_child_tid, FUTEX_WAKE,
					1, NULL, NULL, 0, 0);              /* :1635  唤醒 1 个等待者 */
		}
		tsk->clear_child_tid = NULL;
	}
```

差别只在**用户态谁来做收尾**：

| | joinable | detached |
|---|----------|----------|
| `put_user(0, &tid)` | 执行 | 执行 |
| `do_futex(FUTEX_WAKE, 1)` | 执行，**唤醒 joiner** | 执行，**无等待者，空转一次** |
| 谁调 `__free_tcb()` | `pthread_join` 返回时（joiner 线程） | `start_thread` 收尾（线程自己） |
| TCB 何时释放 | join 时 | 线程终止时 |

**三个推论**：

1. detach **不省内核资源**（`task_struct` 两态都是 `autoreap` 立即回收）
2. detach 省的是 **glibc 的 8MB 用户栈 + TCB**
3. detached 线程退出仍有**一次多余的 `do_futex()` 系统调用**（~1μs），海量短命线程场景要用线程池消掉

**实践结论**：想「省内核资源」而去 detach 是错误动机；正确的动机是「不需要返回值 + 不需要同步点」。
</details>

<summary>5. 从本章出发，设计一个 HFT 交易进程的线程模型。给出每个决策的机制依据。</summary>

```
┌──────────────── 交易进程（单进程多线程）─────────────────┐
│                                                          │
│  CPU2              CPU3             CPU4        CPU5     │
│ ┌────────┐       ┌────────┐       ┌────────┐  ┌────────┐│
│ │行情解码 │  SPSC │ 策略   │  SPSC │ 风控   │  │ 落盘   ││
│ │FIFO/60 │ ────► │FIFO/55 │ ────► │FIFO/50 │  │ OTHER  ││
│ └────────┘ 无锁  └────────┘ 无锁  └────────┘  └────────┘│
│                                                          │
│  共享：订单簿 / 持仓 / 行情快照（同一 mm_struct）         │
└──────────────────────────┬───────────────────────────────┘
                           │ 共享内存 / Unix socket
                    ┌──────▼───────┐
                    │ 独立进程      │ 日志聚合 / 行情网关 / 协议转换
                    └──────────────┘
```

| 决策 | 依据 |
|------|------|
| **同一进程内多线程** | 订单簿是 MB~GB 级可变状态。IPC 拷贝引入微秒级抖动；共享 `mm_struct` 是零拷贝（29.9） |
| **一核一线程 + `sched_setaffinity`** | 线程切换虽然不写 CR3（`arch/x86/mm/tlb.c:562`），但**照样污染 L1/L2 缓存**。绑核连这一层都省掉（29.8） |
| **SPSC 无锁队列** | 关键路径零系统调用、零锁竞争。互斥锁会让线程睡在 futex 上，一次等待是 μs 级 |
| **`SCHED_FIFO` 分层（60/55/50）** | 优先级分层保证行情不被策略饿死。用 `RLIMIT_RTPRIO` 设上界，不靠 root（`kernel/sched/core.c:7573`） |
| **必须设 `PTHREAD_EXPLICIT_SCHED`** | 默认 `INHERIT` 会让调度设置**静默失效**（29.8 最大坑） |
| **栈 512KB + guard 64KB** | 8MB 默认栈在几十个线程时 VIRT 就到几百 MB；64KB guard 挡住常见的中等帧（29.8） |
| **栈上不放 > 4KB 的对象** | 大数组一步跨过 guard，静默踩到别的线程栈（29.8） |
| **启动期建好所有线程，全部 joinable** | 热路径零 `pthread_create`/`join`/`detach`；关停时用 `pthread_timedjoin_np` 带超时确认落盘完成（29.6 / 29.7） |
| **日志 / 网关独立进程** | 第三方协议库、复杂解析是崩溃高发区。多线程下崩一个 = 全灭（29.9 故障域） |
| **绝不在热路径 fork** | `dup_mm()` 成本与虚拟内存大小成正比，几十 GB 的进程 fork 一次要毫秒级（29.9） |
| **不用 `pthread_t` 做长期身份** | 它是 `struct pthread *`（栈底地址），线程退出后会被新线程复用（29.5）。用 `gettid()` 或自己分配的稳定 ID |

**反面清单（不要做的事）**：

- ❌ 线程里 `exit()` → `zap_other_threads()` 杀光全进程
- ❌ 用 `-lpthread` 代替 `-pthread`
- ❌ `if (pthread_create(...) == -1)` → 错误码是正数，永远不触发
- ❌ 循环里 `pthread_create(&t[i], NULL, f, &i)` → 传的是同一个地址
- ❌ 用 `==` 比较 `pthread_t`
- ❌ 热路径 `fork()`
- ❌ 栈上放大数组或深递归
- ❌ 忘记 `setinheritsched(EXPLICIT)`
</details>
