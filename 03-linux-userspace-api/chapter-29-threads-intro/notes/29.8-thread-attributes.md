## 本节讲什么

1. `pthread_attr_t` 是**创建时的一次性快照**——它怎么被内核消费（栈地址、栈大小、TLS 三件套）
2. 栈三兄弟 `stacksize` / `stackaddr` / `guardsize` 的真实内存布局，以及**保护页只能挡小步溢出**这个要命的边界
3. 调度属性的**默认继承陷阱**：只设 `setschedparam` 不设 `setinheritsched(EXPLICIT)` 会被**静默忽略**

## 一、`pthread_attr_t` 是什么

```c
#include <pthread.h>

int pthread_attr_init(pthread_attr_t *attr);      /* 填充默认值 */
int pthread_attr_destroy(pthread_attr_t *attr);   /* 释放（可能有的）动态资源 */
```

**它是不透明对象**，POSIX 只规定了 `pthread_attr_t` 这个类型名，内部结构由实现定义。glibc 里它是一个 ~56 字节的结构体，装着 detachstate / stacksize / guardsize / schedpolicy / schedparam / inheritsched / scope / cpuset 等字段。

### 标准使用范式（四步，一步都不能少）

```c
pthread_attr_t attr;
int rc;

rc = pthread_attr_init(&attr);                    /* ① 初始化为默认值 */
if (rc) /* 处理错误 */;                            /*    ← 99% 的代码忘了检查 */

rc = pthread_attr_setstacksize(&attr, 256*1024);   /* ② 改你要改的项 */
rc = pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);

rc = pthread_create(&tid, &attr, worker, arg);     /* ③ 创建（快照生效） */

rc = pthread_attr_destroy(&attr);                  /* ④ 销毁 */
```

### 三条硬性规则

| # | 规则 | 说明 |
|---|------|------|
| ① | **`init` 之后才能用** | 未初始化的 `pthread_attr_t` 是垃圾内存，行为未定义。不能用 `memset` 代替 `init` |
| ② | **用完必须 `destroy`** | glibc 的 `destroy` 目前主要是把对象标记为不可用并释放亲和性 cpuset；漏掉在 glibc 上不泄漏，但**不可移植**（其它实现可能 malloc） |
| ③ | **`destroy` 后可以重新 `init`** | 一个对象可以反复 init/destroy；但不能 `memcpy` 复制（不透明类型） |

### 最关键的一条语义：**属性是创建时的一次性快照**

```
  pthread_attr_t attr
        │
        ├─ init → detachstate=JOINABLE, stacksize=8MB, guardsize=4KB,
        │         inheritsched=INHERIT, schedpolicy=OTHER, scope=SYSTEM
        │
        ├─ setstacksize(256KB)
        ├─ setdetachstate(DETACHED)
        │
        ├─ pthread_create(&tid, &attr, ...)   ←── 此刻 attr 被「拍照」
        │         │                                之后改 attr 不影响已建线程
        │         ↓
        │    glibc allocate_stack()：mmap 256KB+4KB+TCB，mprotect guard 为 PROT_NONE
        │    clone(CLONE_VM|CLONE_THREAD|CLONE_SETTLS|CLONE_CHILD_CLEARTID|..., stack)
        │         ↓
        │    内核 copy_process() 只认 clone 参数，不再回头看 attr
        │
        └─ attr_destroy(&attr)  ← 销毁快照，线程不受影响
```

**推论**：

- 同一个 `attr` 可以创建**任意多个**线程，每个线程得到相同配置；
- `pthread_create` 返回后立刻 `destroy` 也没问题；
- **线程一旦创建，属性就固化了**，想改调度策略只能用 `pthread_setschedparam()`（这是运行期 API，走 `sched_setattr` 系统调用，见 `kernel/sched/core.c:8078`）。

| 属性 | 设置 / 获取函数 | 默认值 | POSIX? |
|------|------------------|--------|--------|

## 三、栈三兄弟：`stacksize` / `stackaddr` / `guardsize`

### 3.1 一块线程栈的真实布局

glibc 的 `allocate_stack()` 只做**一次** `mmap`，拿到的整块区域内部这样切分（x86-64，栈向下增长）：

```
  High addr  ┌─────────────────────────────────┐ ← mem + total
             │ struct pthread (TCB)             │ ← pd，也就是 pthread_t 指向的地方（29.5）
             │ + static TLS block               │
             ├─────────────────────────────────┤ ← 线程初始 SP
             │                                  │
             │      可用栈空间                   │
             │      （向低地址增长）              │
             │                                  │
             │  ▲ 局部数组 / 递归帧 / 调用链      │
             ├─────────────────────────────────┤
             │  guard page(s)   PROT_NONE        │ ← guardsize，默认 1 页 = 4KB
  Low addr   └─────────────────────────────────┘ ← mem
             total = guardsize + stacksize + sizeof(struct pthread) + alignment
```

对照内核文档里对 `clone3` 的描述（`include/uapi/linux/sched.h:62-67`）：

> `@stack:` Specify the location of the stack for the child process.
> **Note, `@stack` is expected to point to the lowest address.**
> The stack direction will be determined by the kernel and set up appropriately based on `@stack_size`.

内核**只认最低地址 + 长度**，往哪个方向长由内核按架构决定。这和 `pthread_attr_setstack(addr, size)` 的约定完全一样：**`addr` 必须是最低地址**。

### 3.2 三个函数的语义差异（极易混淆）

| 函数 | 你提供什么 | glibc 做什么 | 保护页 |
|------|-----------|-------------|--------|
| `pthread_attr_setstacksize(&a, sz)` | 只要**可用栈**大小 | mmap `sz + guardsize + TCB`，**自动加保护页** | ✔ 有 |
| `pthread_attr_setstack(&a, addr, sz)` | **整块区域的地址和大小** | 直接用你给的，不再额外分配 | **✘ 没有**（保护页要你自己留） |
| `pthread_attr_setguardsize(&a, gs)` | 保护页大小 | 配合 `setstacksize` 生效；`gs=0` 表示关闭 | 由 `gs` 定 |

**`setstack` 的三个额外约束**：

1. `addr` 是**最低地址**，且必须页对齐（否则 `EINVAL`）；
2. 你给的 `size` **包含**将来 guard 占的空间——glibc 不会替你加；
3. `size` 不得小于 `PTHREAD_STACK_MIN`（x86-64 glibc = **16384 字节**）。

> **实践建议**：99% 的场景用 `setstacksize` 就够了。
> `setstack` 只在你要把线程栈放进**自己管理的大块内存**（比如 hugepage 池、静态数组、DPDK 式内存池）时才用，
> 代价是自己负责保护页。

### 3.3 保护页只能挡「小步溢出」——这是最危险的一条

```
  正常                          小步溢出（被 guard 挡住）        大步溢出（guard 形同虚设）
  ┌──────────┐                  ┌──────────┐                    ┌──────────┐
  │  TCB     │                  │  TCB     │                    │  TCB     │
  ├──────────┤                  ├──────────┤                    ├──────────┤
  │ 已用栈    │                  │ 已用栈    │                    │ 已用栈    │
  │    ↓     │                  │    ↓     │                    │    ↓     │
  │          │                  │ 溢出部分  │ ← 踩到 guard       │          │
  ├──────────┤                  ├──────────┤                    │  一大步   │
  │  guard   │                  │  guard   │ → SIGSEGV          │  跨过去   │  ← 直接落进
  │ PROT_NONE│                  │ PROT_NONE│   （干净死，好查）   ├──────────┤    相邻映射
  └──────────┘                  └──────────┘                    │  guard   │
                                                                ├──────────┤
                                                                │ 别的线程栈 │ ← 静默串改！
                                                                └──────────┘
```

**什么时候会大步跨过 guard**：

```c
void *worker(void *arg)
{
    char buf[64 * 1024];        /* 64KB 局部数组：一次就把 4KB 的 guard 跨过去了 */
    memset(buf, 0, sizeof buf); /* 直接写穿到相邻线程栈，无 SIGSEGV，静默破坏 */
    ...
}
```

- 默认 `guardsize = 4KB`，**任何 ≥ 4KB 的单次栈写入都可能跳过它**；
- 大局部数组、深递归里的巨型帧、VLA（`char buf[n]`）、`alloca()` 都是高危；
- 相邻的那块内存很可能就是**另一个线程的栈**（glibc 把线程栈 mmap 在一起，还会缓存复用）。

**对策**：

| 对策 | 做法 |
|------|------|
| ① | **栈上不放大对象**。超过 4KB 的缓冲区一律 `malloc` 或放静态/线程局部存储（Ch31 的 `__thread`） |
| ② | 调大 `guardsize`（如 64KB），能挡住常见的中等数组，代价是每线程多占虚拟内存 |
| ③ | 用 `ulimit -c unlimited` + 内核 `CONFIG_VMAP_STACK`（内核栈溢出检测；用户栈不适用） |
| ④ | 编译期 `-Wstack-usage=N` / `-fstack-usage` 静态估算每函数栈用量 |
| ⑤ | 运行期 `pthread_getattr_np()` 取栈基址 + 当前局部地址，算出已用百分比并打点告警 |

### 3.4 「子线程栈固定，主线程栈可增长」——两者的溢出行为完全不同

| | 主线程栈 | 新建线程栈 |
|---|---------|-----------|
| 谁分配 | 内核在 `execve` 时建立 | glibc `mmap` |
| 大小 | 受 `RLIMIT_STACK`（`ulimit -s`，默认 8MB）限制 | `pthread_attr_t` 里的 `stacksize`（默认 8MB） |
| 能否增长 | **能**。内核按需向下扩展（`expand_downwards`），直到撞上 `RLIMIT_STACK` 或相邻 VMA | **不能**。mmap 时就定死了 |
| 溢出后果 | 触发 `expand_downwards()` 失败 → 内核送 `SIGSEGV`（或 `SIGBUS`） | 撞 guard → `SIGSEGV`；跨过 guard → **静默破坏** |
| 观察方式 | `cat /proc/self/maps` 里带 `[stack]` 标记 | 不带标记，就是普通匿名映射 |

**这一行最关键**：**新线程栈是固定大小的**，没有「不够了再长」这回事。所以给新线程定 `stacksize` 时，必须留出足够的余量。

> **HFT 视角**：「固定」恰恰是我们想要的——**主线程栈的动态增长会在故障路径上引入一次缺页 + VMA 扩展**，
> 延迟不可预测。关键线程用固定栈 = 可预测的延迟。代价是要自己把栈算清楚。

### 3.5 内核栈：每个线程还有一份隐藏的 16KB

用户栈之外，内核为每个 `task_struct`（含每个线程）**额外**分配一份内核栈：

```c
/* arch/x86/include/asm/page_64_types.h:15-16 */
#define THREAD_SIZE_ORDER	(2 + KASAN_STACK_ORDER)
#define THREAD_SIZE  (PAGE_SIZE << THREAD_SIZE_ORDER)     /* = 4 页 = 16KB */
```

分配路径（`kernel/fork.c:309`）：

```c
	stack = __vmalloc_node_range(THREAD_SIZE, THREAD_ALIGN,
				     VMALLOC_START, VMALLOC_END,
				     THREADINFO_GFP & ~__GFP_ACCOUNT,
				     PAGE_KERNEL,
				     0, node, __builtin_return_address(0));
```

而且内核还做了优化（`:303-306` 注释）：

> Allocated stacks are cached and later reused by new threads, so memcg accounting is performed manually on assigning/releasing stacks to tasks.

**所以「线程比进程轻」这句话要打折**：每个线程除了 8MB 用户栈（虚拟内存，按需分页），还有 **16KB 真正的内核栈（物理内存，立即占用）**。1000 个线程 = 16MB 内核栈。

## 四、调度属性：三个字段 + 一个巨大的默认陷阱

### 4.1 三件套

```c
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);        /* ① 策略 */
struct sched_param sp = { .sched_priority = 50 };
pthread_attr_setschedparam (&attr, &sp);               /* ② 优先级 */
pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);  /* ③ 生效开关 */
```

### 4.2 ⚠️ 默认陷阱：`inheritsched = PTHREAD_INHERIT_SCHED`

**这是本节最容易踩的坑，没有之一。**

默认值是 `PTHREAD_INHERIT_SCHED`，含义是：**忽略 attr 里的 policy 和 param，直接继承创建线程的调度属性。**

也就是说：

```c
/* ❌ 错误：policy 和 param 会被静默忽略，不报错、不警告 */
pthread_attr_init(&attr);
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);
param.sched_priority = 50;
pthread_attr_setschedparam(&attr, &param);
pthread_create(&tid, &attr, worker, NULL);
/* → 新线程跑在 SCHED_OTHER，优先级 0。程序照常跑，只是延迟特性完全不对 */
```

```c
/* ✅ 正确：必须显式打开 EXPLICIT */
pthread_attr_init(&attr);
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);
param.sched_priority = 50;
pthread_attr_setschedparam(&attr, &param);
pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);   /* ← 必须有这一行 */
pthread_create(&tid, &attr, worker, NULL);
```

**危害**：静默失败。`pthread_create` 返回 0，线程跑得好好的，只是**完全不是你要的调度行为**。在 HFT 场景里这表现为「延迟偶发尖刺但查不出原因」。

**检查手段**：创建后用 `pthread_getschedparam(tid, &pol, &sp)` **读回来验证**——这是唯一可靠的确认方式（和 22.6 里 `do_sigaction` 静默吞 flag 的对策一模一样）。

### 4.3 策略与优先级速查

| 策略 | 值 | 优先级范围 | 说明 | Ch35 |
|------|-----|-----------|------|------|
| `SCHED_OTHER`（=`SCHED_NORMAL`） | `0` | 固定 0，用 `nice` 值 | 默认 CFS 完全公平调度 | — |
| `SCHED_FIFO` | `1` | **1 ~ 99** | 实时先进先出，无时间片，一直跑到主动让出或被更高优先级抢占 | ✔ |
| `SCHED_RR` | `2` | **1 ~ 99** | 实时轮转，同优先级有时间片 | ✔ |
| `SCHED_BATCH` | `3` | 固定 0 | 批处理，不参与交互性唤醒补偿 | — |
| `SCHED_IDLE` | `5` | 固定 0 | 比 nice +19 还低 | — |
| `SCHED_DEADLINE` | `6` | 固定 0，用 `runtime/deadline/period` | EDF + CBS，需 `sched_setattr` | ✔ |

（常量的内核定义：`include/uapi/linux/sched.h:114-120`）

**优先级上界要用运行期查询，不要硬编码**：

```c
int pmax = sched_get_priority_max(SCHED_FIFO);   /* x86-64 Linux = 99 */
int pmin = sched_get_priority_min(SCHED_FIFO);   /* = 1 */
```

### 4.4 权限：为什么 `pthread_create` 会返回 `EPERM`

设 `SCHED_FIFO`/`SCHED_RR` 需要特权，内核的判定在 `kernel/sched/core.c:7562` 的 `user_check_sched_setscheduler()`：

```c
static int user_check_sched_setscheduler(struct task_struct *p,
					 const struct sched_attr *attr,
					 int policy, int reset_on_fork)
{
	...
	if (rt_policy(policy)) {
		unsigned long rlim_rtprio = task_rlimit(p, RLIMIT_RTPRIO);   /* :7573 */

		/* Can't set/change the rt policy: */
		if (policy != p->policy && !rlim_rtprio)                     /* :7576 */
			goto req_priv;

		/* Can't increase priority: */
		if (attr->sched_priority > p->rt_priority &&
		    attr->sched_priority > rlim_rtprio)
			goto req_priv;
	}
	...
req_priv:
	if (!capable(CAP_SYS_NICE))          /* :7614 */
		return -EPERM;

	return 0;
}
```

翻译成人话，**两条路任意一条**即可：

| 路径 | 设置方式 | 上限 |
|------|----------|------|
| `RLIMIT_RTPRIO` | `ulimit -r N` / `setrlimit(RLIMIT_RTPRIO, N)` | RT 优先级 ≤ N，**不需要 root** |
| `CAP_SYS_NICE` | `sudo` / `setcap cap_sys_nice=ep ./prog` | 无上限 |

> **生产建议**：用 `RLIMIT_RTPRIO` 而不是 root。给二进制打 `cap_sys_nice=ep` 或配 `ulimit -r`，
> 遵循最小权限原则。`RLIMIT_RTPRIO` 还有一个好处：**它天然限制了 RT 优先级的上界**，
> 防止代码里写错一个 99 把整个系统锁死。

### 4.5 SCHED_FIFO 的自杀风险

`SCHED_FIFO` 线程**没有时间片**：它会一直跑，直到

1. 阻塞（I/O、锁、futex），或
2. 主动让出（`sched_yield()`），或
3. 被**更高**优先级的 RT 线程抢占

**后果**：一个 `SCHED_FIFO` 优先级 99 的死循环线程，会把同核上所有东西（包括 sshd、内核的 migration 线程之外的普通线程）**全部饿死**，鼠标键盘无响应，只能硬重启。

**防御清单**：

| # | 措施 |
|---|------|
| ① | RT 线程里**禁止**无界循环；必须有阻塞点或显式 yield |
| ② | 优先级从低往高调，先试 50，别一上来 99 |
| ③ | 用 `RLIMIT_RTPRIO` 设硬上界 |
| ④ | 内核 `/proc/sys/kernel/sched_rt_runtime_us`（默认 950000 = 0.95s/s）给非 RT 留 5% 的兜底时间片 |
| ⑤ | 开发期开 `sudo sysctl kernel.sched_rt_runtime_us=-1` 关掉兜底前先想清楚——关掉就真的救不回来了 |

### 4.6 亲和性（`_np` 扩展）

```c
#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>

cpu_set_t cpuset;
CPU_ZERO(&cpuset);
CPU_SET(3, &cpuset);                                  /* 绑定到 CPU 3 */
pthread_attr_setaffinity_np(&attr, sizeof(cpuset), &cpuset);
```

- 非 POSIX（glibc 扩展），必须 `_GNU_SOURCE`；
- 线程创建后也可以改：`pthread_setaffinity_np(tid, ...)`；
- **HFT 核心手段**：把行情线程、策略线程、日志线程绑到**不同物理核**，杜绝互相抢占和缓存污染（详见 Ch35 与 `sched_setaffinity`）；
- 注意 NUMA：绑核后内存访问可能跨 NUMA 节点，配合 `mbind`/`numactl` 使用。

## 五、属性设置速查（可直接抄）

```c
/* 模板：一次配置多属性，并做读回校验 */
static int create_rt_worker(pthread_t *tid, int cpu, int prio,
                            size_t stack_kb, void *(*fn)(void *), void *arg)
{
    pthread_attr_t attr;
    int rc = pthread_attr_init(&attr);
    if (rc) return rc;

    /* 1. 栈：先调小，再留保护页 */
    rc = pthread_attr_setstacksize(&attr, stack_kb * 1024);
    if (rc) goto out;
    rc = pthread_attr_setguardsize(&attr, 64 * 1024);
    if (rc) goto out;

    /* 2. 分离状态：火后即忘就 DETACHED，需要 join 就保持 JOINABLE */
    /* rc = pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED); */

    /* 3. 调度：三件套，EXPLICIT 一行都不能少 */
    rc = pthread_attr_setschedpolicy(&attr, SCHED_FIFO);
    if (rc) goto out;
    struct sched_param sp = { .sched_priority = prio };
    rc = pthread_attr_setschedparam(&attr, &sp);
    if (rc) goto out;
    rc = pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);
    if (rc) goto out;

    /* 4. 绑核（glibc 扩展） */
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    rc = pthread_attr_setaffinity_np(&attr, sizeof(set), &set);

out:
    int rc2 = pthread_attr_destroy(&attr);
    if (rc) return rc;
    return rc2;
}
```

## 六、常见错误清单

| # | 错误 | 症状 | 正解 |
|---|------|------|------|
| ① | 设了 `schedpolicy`/`schedparam` 却没设 `EXPLICIT_SCHED` | 静默失效，调度行为完全不对 | 三件套一起设 |
| ② | 用 `memset` / 未初始化就直接用 `attr` | 未定义行为 | 必须 `pthread_attr_init` |
| ③ | 忘了 `pthread_attr_destroy` | glibc 上不泄漏，但不可移植 | 养成配对习惯 |
| ④ | `setstacksize` 小于 `PTHREAD_STACK_MIN`（16KB） | `EINVAL` | 用 `PTHREAD_STACK_MIN` 做下界钳制 |
| ⑤ | 以为 guard page 能挡所有栈溢出 | ≥ guardsize 的单次写入会跨过去，静默破坏相邻线程栈 | 栈上不放 >4KB 的对象；必要时调大 guardsize |
| ⑥ | `setstack` 时忘留保护页 | 无保护，溢出直接踩邻居 | 自己额外 mprotect 一页 `PROT_NONE`，或改用 `setstacksize` |
| ⑦ | 在 RT 线程里写无界循环 | 系统假死，只能硬重启 | 加阻塞点/yield；用 `RLIMIT_RTPRIO` 限上界 |
| ⑧ | 硬编码 RT 优先级 99 | 抢占掉内核关键线程 | 用 `sched_get_priority_max()` 查询，从低往高调 |
| ⑨ | 把 `attr` 当持久配置，创建后继续改 | 对已建线程无效 | 属性是快照；运行期改调度用 `pthread_setschedparam` |
| ⑩ | `attr` 是栈上局部变量，`pthread_create` 后立刻离开作用域 | 其实**没问题**（快照语义），但很多人以为有问题而改成堆分配 | 保持栈上局部 + `destroy` 即可 |
| ⑪ | 用 `pthread_attr_setscope(PTHREAD_SCOPE_PROCESS)` | Linux 返回 `ENOTSUP` | Linux 只支持 `PTHREAD_SCOPE_SYSTEM` |
| ⑫ | 只调小栈却不管递归深度 | 深递归直接踩 guard → SIGSEGV | 用 `-fstack-usage` 或运行期打点估算 |

## 七、HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **HFT** | **启动期一次性配置**：绑核 + `SCHED_FIFO` + 固定栈，全部在 `pthread_create` 之前定好，运行期零调度系统调用 |
| **HFT** | **固定栈 = 可预测延迟**。主线程栈的动态扩展（`expand_downwards`）会在故障路径引入不确定缺页，关键线程不要走这条路 |
| **HFT** | **guard page 调大到 64KB**：HFT 代码里常见 8~32KB 的行情快照缓冲区，4KB 的默认 guard 挡不住 |
| **HFT** | **RT 优先级分层**：行情解码 > 策略 > 风控 > 日志；用 `RLIMIT_RTPRIO` 设硬上界，防止写错一个 99 锁死机器 |
| **HFT** | **栈上禁放大对象**：订单簿快照用预分配的堆/静态池，栈上只留指针和标量 |
| **HFT** | 内核栈 16KB/线程是真实物理内存开销；1000 线程 = 16MB，规划容量时要算进去 |
| **嵌入式** | **栈是最大头**：8MB/线程在几十 MB 内存的设备上是奢侈品。`pthread_attr_setstacksize(16~64KB)` 是刚需 |
| **嵌入式** | 无 MMU 平台（uClinux）`guardsize` 可能无效（无页保护），栈溢出**完全无检测** → 更要靠静态分析 `-fstack-usage` |
| **嵌入式** | `MAP_STACK`（`include/uapi/asm-generic/mman-common.h:28`）在 Linux 上是**空标志**，别指望它做任何事；架构相关的栈优化在其他 OS 上才有意义 |
| **嵌入式** | 深递归（如协议解析、JSON/XML 树遍历）在 RTOS 式小栈上必挂，改写成显式栈的迭代版本 |

/* ───────────────────────────────────────────────────────────
 * 演示 3：实测线程栈的真实布局（基址 / 大小 / guard / 当前用量）
 * ─────────────────────────────────────────────────────────── */
/* 用整数存 SP 值，避免把局部变量的地址存进外层的 void*（GCC -Wdangling-pointer） */
struct layout { void *base; size_t size; size_t guard;
                uintptr_t entry_sp, deep_sp; };

/*
 * 关键技巧：用 volatile 函数指针做递归调用。
 * 直接写 recurse_and_measure(depth-1, ...) 时，GCC 在 -O2 下会做
 * 【尾递归消除】（带累加器变换），把它变成循环 —— 循环复用同一栈帧，
 * SP 就不会下降，测出来的"栈用量"是 0 甚至负数。
 * 走 volatile 函数指针，编译器看不见调用目标，无法做 TCO，栈才真的往下长。
 */
static int recurse_and_measure(int depth, struct layout *L, char *top_hint);
static int (*volatile recurse_fp)(int, struct layout *, char *) = recurse_and_measure;

static int recurse_and_measure(int depth, struct layout *L, char *top_hint)
{
    volatile char probe;                       /* 取地址，量出当前 SP 附近 */
    if (depth == 0) {
        L->deep_sp = (uintptr_t)(void *)&probe;
        return 0;
    }
    if (top_hint) { (void)top_hint[depth & 0xfff]; }
    return recurse_fp(depth - 1, L, top_hint) + 1;
}

static void *worker_layout(void *arg)
{
    struct layout L;
    memset(&L, 0, sizeof L);

    pthread_attr_t ga;
    if (pthread_getattr_np(pthread_self(), &ga) == 0) {
        pthread_attr_getstack(&ga, &L.base, &L.size);
        pthread_attr_getguardsize(&ga, &L.guard);
        pthread_attr_destroy(&ga);
    }

    volatile char local_at_entry;
    L.entry_sp = (uintptr_t)(void *)&local_at_entry;

    recurse_and_measure(200, &L, NULL);        /* 递归 200 层，看掉下去多深 */

    size_t used = (L.deep_sp && L.entry_sp > L.deep_sp)
                      ? (size_t)(L.entry_sp - L.deep_sp) : 0;
    size_t left = (L.size > used) ? L.size - used : 0;

    say("  stack base(最低地址) = %p", L.base);
    say("  stack size           = %zu KB", L.size / 1024);
    say("  guardsize            = %zu KB", L.guard / 1024);
    say("  TCB/pthread_t        ≈ %p （栈区高端，见 29.5）", (void *)pthread_self());
    say("  入口 SP              = 0x%lx", (unsigned long)L.entry_sp);
    say("  递归 200 层后 SP     = 0x%lx  → 已用 %zu 字节（每层约 %zu 字节）",
        (unsigned long)L.deep_sp, used, used ? used / 200 : 0);
    say("  剩余可用             ≈ %zu KB（水位 %.1f%%）",
        left / 1024, L.size ? 100.0 * used / L.size : 0.0);
    (void)arg;
    return NULL;
}

static void demo_layout(void)
{
    say("演示3: 线程栈的真实布局（pthread_getattr_np 实测）");
    pthread_attr_t a;
    pthread_attr_init(&a);
    pthread_attr_setstacksize(&a, 512 * 1024);
    pthread_attr_setguardsize(&a, 64 * 1024);

    pthread_t t;

}

 * 演示 4：guard page 挡不住「大步溢出」——放在子进程里跑，不炸主程序
 * ─────────────────────────────────────────────────────────── */
static void *worker_big_frame(void *arg)
{
    size_t kb = *(size_t *)arg;
    volatile char big[256 * 1024];             /* 256KB 栈上大数组 */
    memset((void *)big, 0xAB, kb * 1024);      /* 一次跨过 4KB 的 guard */
    say("  写入 %zu KB 栈上大数组完成（没崩 = guard 被跨过去了）", kb);
    return NULL;
}

static void demo_guard_bypass(void)
{
    say("演示4: guard page 挡不住大步溢出（在子进程里跑，避免炸掉主程序）");

    size_t kb = 200;
    pid_t pid = fork();
    if (pid == 0) {
        pthread_attr_t a;
        pthread_attr_init(&a);
        pthread_attr_setstacksize(&a, 256 * 1024);   /* 栈故意只给 256KB */
        /* 不调 guardsize → 默认 4KB */
        pthread_t t;
        if (pthread_create(&t, &a, worker_big_frame, &kb) == 0)
            pthread_join(t, NULL);
        else
            say("  create 失败");
        _exit(0);
    }
    int st = 0;
    waitpid(pid, &st, 0);
    if (WIFSIGNALED(st))

    say("  ↑ 教训：栈上不要放超过 guardsize 的对象；把 guardsize 调大也只是缓解");
}

{

        say("  create 失败");
    pthread_attr_destroy(&a);
    say("  ↑ HFT 用法：行情/策略/日志线程各绑一个物理核，杜绝互相抢占 + 缓存污染");
}

/* ───────────────────────────────────────────────────────────
 * 演示 8：一次性配置 + 读回校验（生产模板）
 * ─────────────────────────────────────────────────────────── */
static int create_configured(pthread_t *tid, int cpu, int prio,
                             size_t stack_kb, size_t guard_kb,
                             void *(*fn)(void *), void *arg,
                             int use_rt)
{
    pthread_attr_t a;
    int rc = pthread_attr_init(&a);
    if (rc) return rc;

    if ((rc = pthread_attr_setstacksize(&a, stack_kb * 1024))) goto out;
    if ((rc = pthread_attr_setguardsize(&a, guard_kb * 1024))) goto out;

    if (use_rt) {
        if ((rc = pthread_attr_setschedpolicy(&a, SCHED_FIFO))) goto out;
        struct sched_param sp = { .sched_priority = prio };
        if ((rc = pthread_attr_setschedparam(&a, &sp))) goto out;
        if ((rc = pthread_attr_setinheritsched(&a, PTHREAD_EXPLICIT_SCHED))) goto out;
    }

    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu % (sysconf(_SC_NPROCESSORS_ONLN) > 0 ?
                   sysconf(_SC_NPROCESSORS_ONLN) : 1), &set);
    if ((rc = pthread_attr_setaffinity_np(&a, sizeof set, &set))) goto out;

    rc = pthread_create(tid, &a, fn, arg);

out:
    pthread_attr_destroy(&a);
    return rc;
}

static void *worker_final(void *arg)
{
    (void)arg;
    int pol; struct sched_param sp;
    pthread_getschedparam(pthread_self(), &pol, &sp);

    size_t ss = 0, gs = 0; void *base = NULL;
    pthread_attr_t ga;
    if (pthread_getattr_np(pthread_self(), &ga) == 0) {
        pthread_attr_getstack(&ga, &base, &ss);
        pthread_attr_getguardsize(&ga, &gs);
        pthread_attr_destroy(&ga);
    }

    cpu_set_t cs; CPU_ZERO(&cs);
    pthread_getaffinity_np(pthread_self(), sizeof cs, &cs);

    say("    ✔ 读回校验: policy=%s prio=%d stack=%zuKB guard=%zuKB cpus=%d",
        polname(pol), sp.sched_priority, ss/1024, gs/1024, CPU_COUNT(&cs));
    return NULL;
}

static void demo_final_template(void)
{
    say("演示8: 生产模板 —— 一次配置 + 创建后读回校验");
    pthread_t t;
    int rc = create_configured(&t, 0, 50, 512, 64, worker_final, NULL, 0);
    if (rc) { say("  create_configured 失败: %s", strerror(rc)); return; }
    pthread_join(t, NULL);
    say("  ↑ 校验必须在创建后立刻做，别等到查延迟毛刺时才想起");
}

int main(void)
{
    say("=== 29.8 线程属性演示 ===");
    demo_defaults();
    demo_stack_bounds();
    demo_layout();
    demo_guard_bypass();
    demo_inheritsched_trap();
    demo_rt_privilege();
    demo_affinity();
    demo_final_template();
    say("=== 演示结束 ===");
    return 0;
}

## 代码自测

<details>
<summary>1. 为什么设了 `schedpolicy`/`schedparam` 却完全没生效，而且没有任何报错？</summary>

因为 **`pthread_attr_t` 默认的 `inheritsched` 是 `PTHREAD_INHERIT_SCHED`**。

这个默认值的含义是：「忽略 attr 里填写的 `schedpolicy` 和 `schedparam`，新线程直接继承创建者的调度属性」。

所以这段**看起来正确**的代码其实是无效的：

```c
pthread_attr_init(&attr);
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);     /* 被忽略 */
param.sched_priority = 50;
pthread_attr_setschedparam(&attr, &param);          /* 被忽略 */
pthread_create(&tid, &attr, worker, NULL);
/* → 新线程跑 SCHED_OTHER，prio=0，pthread_create 返回 0，一切"正常" */
```

必须补上第三件：

```c
pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);   /* ★ 打开开关 */
```

**危害**：静默失效。`pthread_create` 返回 0，线程跑得好好的，只是延迟特性完全不是你要的。在 HFT 里表现为「偶发延迟毛刺、查不出原因」。

**检测**：创建后用 `pthread_getschedparam(tid, &pol, &sp)` **读回来验证**——这是唯一可靠的确认方式。

> 这个模式和 Ch22 里 `do_sigaction()` 静默吞掉未知 `sa_flags`（`kernel/signal.c:4153-4156`，不报错）如出一辙：
> **内核/POSIX 里"静默忽略"的约定，唯一对策都是"写进去再读回来比对"。**
</details>

<details>
<summary>2. `setstacksize` 和 `setstack` 有什么区别？保护页呢？</summary>

| | `pthread_attr_setstacksize(&a, sz)` | `pthread_attr_setstack(&a, addr, sz)` |
|---|---|---|
| 你给的是 | **可用栈**的大小 | **整块区域的地址和大小** |
| glibc 做什么 | `mmap(sz + guardsize + TCB)`，自动 `mprotect(guard, PROT_NONE)` | 直接用你给的那块，**不再额外分配** |
| 保护页 | **自动有**（默认 4KB，可 `setguardsize` 调） | **没有**，要你自己留并 `mprotect` |
| 地址对齐 | glibc 负责 | 你自己负责（页对齐，否则 `EINVAL`） |
| 下界 | ≥ `PTHREAD_STACK_MIN`（x86-64 = 16384） | 同 |

内存布局（x86-64，栈向下增长）：

```
  High addr  ┌──────────────────────┐
             │ struct pthread (TCB) │ ← pthread_t 指向这里（29.5）
             ├──────────────────────┤ ← 初始 SP
             │   可用栈（向下增长）   │
             ├──────────────────────┤
             │ guard page PROT_NONE  │ ← guardsize
  Low addr   └──────────────────────┘ ← addr（setstack 传的就是这个最低地址）
```

内核侧对 `clone3` 的约定完全一致（`include/uapi/linux/sched.h:62-67`）：

> `@stack:` Specify the location of the stack for the child process.
> **Note, `@stack` is expected to point to the lowest address.**

**结论**：99% 场景用 `setstacksize`。`setstack` 只在要把线程栈放进自管理内存池（hugepage 池、静态数组）时才用，代价是保护页自理。
</details>

<details>
<summary>3. 保护页（`guardsize`）能防止栈溢出吗？</summary>

**只能防「小步溢出」，防不住「大步跨越」。**

- **小步溢出**（逐帧递归、多次小写入）：必然先踩到 guard 页 → `SIGSEGV`，干净死、好定位。✔
- **大步跨越**：一次写入 ≥ `guardsize` 的字节，SP 直接跳过 guard 页落到相邻映射 → **无信号、静默破坏**。✘

典型的大步跨越：

```c
void *worker(void *arg)
{
    char buf[64 * 1024];             /* 64KB 大数组，默认 guard 只有 4KB */
    memset(buf, 0, sizeof buf);      /* 一步跨过 guard，写进相邻线程栈 */
}
```

高危写法：大局部数组、VLA（`char buf[n]`）、`alloca()`、深递归里的巨型帧。

**对策**：

| # | 对策 |
|---|------|
| ① | 栈上不放 > 4KB 的对象；大缓冲区用 `malloc` 或 `__thread` 静态池 |
| ② | 调大 `guardsize`（如 64KB），只是缓解，不是根治 |
| ③ | 编译期 `-fstack-usage` / `-Wstack-usage=N` 静态估算每个函数的栈帧 |
| ④ | 运行期 `pthread_getattr_np()` 取基址 + 当前局部地址，算出已用百分比打点告警 |

**另外注意**：新线程栈是**固定大小**的（mmap 时定死，不会自动增长），而主线程栈可以由内核按需向下扩展（受 `RLIMIT_STACK` / `ulimit -s` 限制）。两者溢出行为不同，但都不能依赖 guard 兜底。
</details>

<details>
<summary>4. 设 `SCHED_FIFO` 失败返回 `EPERM`，内核是怎么判定的？有哪些提权路径？</summary>

判定在 **`kernel/sched/core.c:7562` 的 `user_check_sched_setscheduler()`**：

```c
if (rt_policy(policy)) {
    unsigned long rlim_rtprio = task_rlimit(p, RLIMIT_RTPRIO);      /* :7573 */

    /* Can't set/change the rt policy: */
    if (policy != p->policy && !rlim_rtprio)                        /* :7576 */
        goto req_priv;

    /* Can't increase priority: */
    if (attr->sched_priority > p->rt_priority &&
        attr->sched_priority > rlim_rtprio)
        goto req_priv;
}
...
req_priv:
    if (!capable(CAP_SYS_NICE))                                     /* :7614 */
        return -EPERM;
```

**两条路，任意一条即可**：

| 路径 | 设置 | 上限 | 是否需 root |
|------|------|------|------------|
| `RLIMIT_RTPRIO` | `ulimit -r N` / `setrlimit(RLIMIT_RTPRIO, N)` | RT 优先级 ≤ N | **否** |
| `CAP_SYS_NICE` | `sudo` / `setcap cap_sys_nice=ep` | 无上限（1~99） | 是 |

**推荐 `RLIMIT_RTPRIO`**，理由两个：

1. 遵循最小权限原则，不需要 root；
2. **它天然是 RT 优先级的上界**——防止代码里写错一个 99 把系统锁死。

**顺带的安全警告**：`SCHED_FIFO` 线程**没有时间片**，会一直跑到阻塞、主动 yield、或被更高优先级抢占。一个优先级 99 的死循环线程会把同核所有东西饿死（sshd 无响应，只能硬重启）。防御：加阻塞点、优先级从低往高调、`RLIMIT_RTPRIO` 限上界、别随便动 `kernel.sched_rt_runtime_us`（默认给非 RT 留 5% 兜底）。
</details>

<details>
<summary>5. 「线程比进程轻量」——这句话在内核层面要打哪些折扣？</summary>

对，但要算清楚三笔账：

**账 ①：地址空间（线程确实省）**

```c
/* kernel/fork.c:1731 */
if (clone_flags & CLONE_VM) {
    mmget(oldmm);           /* 线程：引用计数 +1，O(1) */
    mm = oldmm;
} else {
    mm = dup_mm(tsk, current->mm);   /* 进程：复制页表 + 所有 VMA，O(页数) */
    if (!mm) return -ENOMEM;
}
```

`dup_mm()` 要分配新 `mm_struct`、复制整棵 VMA 树、逐层复制页表项——这是 `fork` 比 `pthread_create` 慢一个量级的**主因**。

**账 ②：切换成本（线程确实省，但不是"线程切换不换页表"这么简单）**

`context_switch()`（`kernel/sched/core.c:5324`）在 `:5364` 无条件调用 `switch_mm_irqs_off()`，但真正的判断在 x86 的实现里（`arch/x86/mm/tlb.c:495`）：

```c
if (real_prev == next) {
    /* Not actually switching mm's */
    ...
    /*
     * If the CPU is not in lazy TLB mode, we are just switching
     * from one thread in a process to another thread in the same
     * process. No TLB flush required.
     */
    if (!was_lazy)
        return;                 /* ← 同进程线程切换：直接返回，不写 CR3 */
} else {
    cond_mitigation(tsk);       /* ← 进程间切换才跑 IBPB / L1D flush 等缓解 */
    ...
    choose_new_asid(next, next_tlb_gen, &new_asid, &need_flush);
    load_new_mm_cr3(...);       /* 写 CR3 = TLB/ASID 切换，几百 ns 级 */
}
```

所以：

| 切换类型 | 是否写 CR3 | 是否跑 Spectre 缓解 | 大致成本 |
|----------|-----------|-------------------|---------|
| 同进程线程 → 线程 | **否**（`:562` 早退） | **否** | ~1μs |
| 进程 → 进程 | 是 | **是**（`cond_mitigation:612`） | ~5μs 甚至更高 |

**这是线程切换便宜的真正机制原因**，不是「线程不换页表」这种模糊说法。

**账 ③：内核栈（线程并不省）**

每个 `task_struct` 都有一份内核栈，**线程和进程一样多**：

```c
/* arch/x86/include/asm/page_64_types.h:15-16 */
#define THREAD_SIZE_ORDER	(2 + KASAN_STACK_ORDER)
#define THREAD_SIZE  (PAGE_SIZE << THREAD_SIZE_ORDER)   /* = 16KB */
```

分配路径 `kernel/fork.c:309` 走 `__vmalloc_node_range(THREAD_SIZE, ...)`，是**立即占用的物理内存**（不像用户栈 8MB 那样按需分页）。不过内核做了缓存复用（`:303-306` 注释：*Allocated stacks are cached and later reused by new threads*），所以反复创建销毁不会持续膨胀。

**1000 个线程 = 16MB 内核栈（物理内存）**，规划容量时必须算进去。

**总结**：线程省的是**地址空间复制**和**切换时的 CR3/TLB 刷新**，但**内核栈、文件描述符表引用、信号处理结构引用**这些成本一视同仁。
</details>
