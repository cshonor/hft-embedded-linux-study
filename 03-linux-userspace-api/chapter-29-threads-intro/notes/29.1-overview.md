## 本节讲什么

1. 线程到底**共享什么、私有什么**——这是并发 bug 的地基，含最容易被误解的 `errno`
2. **Linux 内核里根本没有「线程」这种对象**——只有 `task_struct` 和一组决定「共享什么」的 `CLONE_*` 位
3. 为什么要有线程：`fork()` 的代价在哪，线程省下了什么、又**没省下**什么

---

## 一、一句话定义

> **线程 = 共享同一份地址空间和其他资源的「执行流」；进程 = 一组线程 + 一份资源容器。**

```
  单线程进程                        多线程进程
  ┌──────────────────┐              ┌──────────────────────────────┐
  │  地址空间         │              │  地址空间（1 份，共享）        │
  │  ├─ 代码/数据/堆  │              │  ├─ 代码/数据/堆              │
  │  ├─ 栈（1 个）    │              │  ├─ 栈 A  栈 B  栈 C（各 1 个）│
  │  └─ 内核数据结构  │              │  └─ 内核数据结构（1 份）      │
  │                   │              │                              │
  │  执行流：1 个      │              │  执行流：3 个（各自有 PC/寄存器）│
  └──────────────────┘              └──────────────────────────────┘
```

关键点：**「栈」是每线程一份，「堆」是全体共享**。栈上变量天然线程安全，堆上的和全局的不然。

## 二、共享 vs 私有（本节最重要的一张表）

### 线程之间**共享**的

| 类别 | 具体内容 |
|------|----------|
| 内存 | **整个虚拟地址空间**：代码段、数据段、堆、所有 `mmap` 映射、共享内存 |
| 标识 | 进程 ID（TGID）、父进程 ID、进程组 ID、会话 ID、控制终端 |
| 文件 | **打开的文件描述符表**（含文件偏移！）、`umask`、当前工作目录、根目录 |
| 信号 | **信号处置**（`sighand->action[]`）、pending 的**共享**部分 |
| 定时 | 间隔定时器（`setitimer`）、POSIX 定时器、闹钟 |
| 资源 | 资源限制（`RLIMIT_*`）、`nice` 值、CPU 时间与资源用量（`getrusage`） |
| 同步 | 互斥量、条件变量、读写锁、屏障（都是普通内存对象） |
| 其他 | 进程凭证（UID/GID/补充组）、文件系统信息、System V `SEM_UNDO` 值 |

### 每线程**独有**的（这是坑的来源）

| 类别 | 具体内容 | 为什么重要 |
|------|----------|-----------|
| **线程 ID**（TID） | 内核的 `pid`，`gettid()` | 与 `getpid()`（TGID）不同！ |
| **栈** | 局部变量、函数调用链 | 栈上变量天然安全；栈大小默认 8MB（glibc） |
| **寄存器 / PC** | 执行到哪了 | 调度的单位 |
| **信号掩码** | `task_struct.blocked` | ⚠️ **每个线程独立**，见 [Ch33.2](../../chapter-33-threads-further/notes/33.2-threads-and-signals.md) |
| **`errno`** | 每线程一份 | ⚠️ **最容易被误解**：见下方 |
| **备用信号栈** | `sas_ss_*` | 每线程独立，`copy_process():2550` 在共享 VM 时重置 |
| **线程局部存储** | `__thread` / `__declspec(thread)` | 见 [Ch31.4](../../chapter-31-thread-safety-tsd/notes/31.4-thread-local-storage.md) |
| **调度策略与优先级** | `sched_setscheduler` 作用于单线程 | [Ch35](../../chapter-35-process-priorities-scheduling/README.md) |
| **CPU 亲和性** | `sched_setaffinity` | 每线程独立设置 |
| **能力集**（Linux） | `capset()` | Linux 特有，每线程 |
| **浮点环境** | `fenv`、FPU/SIMD 寄存器状态 | 上下文切换时保存恢复 |

### ⚠️ `errno` 是每线程独立的——这是最反直觉的一条

新手常以为 `errno` 是个全局变量。它不是：

```c
/* glibc 里 errno 的实际展开（简化）*/
#define errno (*__errno_location())

/* __errno_location() 返回一个【每线程】的地址，
 * 通常来自线程控制块 TCB（x86-64 上通过 fs 寄存器访问）*/
```

```
      线程 A ──→ __errno_location() ──→ 0x7f1234500000  （A 的 errno）
      线程 B ──→ __errno_location() ──→ 0x7f6789000000  （B 的 errno）
                       ↓
              同一个名字，不同地址 —— 各写各的，互不干扰
```

**这带来一个必须养成的习惯**：

```c
/* ✗ 危险：两次系统调用之间可能有别的线程/信号改了 errno */
if (read(fd, buf, n) == -1 && errno == EINTR)
    /* ... */
    perror("read");          /* ← 这时的 errno 可能已经不是 read 设的了 */

/* ✓ 正确：立刻保存 */
int saved = errno;           /* 出错后【第一件事】就是存起来 */
```

> 有意思的是：正因为 `errno` 是每线程的，所以**信号 handler 里仍要保存/恢复 `errno`**——
> handler 是在**被打断的那个线程**的栈上执行的，它改的是**同一个** `errno`。

## 三、内核视角：Linux 里没有「线程」对象

这是理解 Linux 线程最重要的一点，也是它和很多其他 UNIX 的根本差异。

```
  用户/标准视角                      Linux 内核视角

  ┌─────────────────────┐           ┌────────────────────────────────┐
  │  进程 (PID = 1234)   │           │  4 个独立的 task_struct：       │
  │  ├─ 主线程           │           │                                │
  │  ├─ 线程 A           │    ←→     │   pid=1234  tgid=1234 (leader) │
  │  ├─ 线程 B           │           │   pid=1235  tgid=1234          │
  │  └─ 线程 C           │           │   pid=1236  tgid=1234          │
  └─────────────────────┘           │   pid=1237  tgid=1234          │
                                    │                                │
     一个"进程"，                    │   调度器看到 4 个可运行实体，   │
     4 条执行流                      │   【没有】"线程"这种结构体      │
                                    └────────────────────────────────┘
```

内核里只有一种可调度对象：`struct task_struct`。「线程」和「进程」的区别**仅仅是创建时传的 `CLONE_*` 标志不同**，导致某些资源是**拷贝**还是**共享引用**。

这段就是全部真相（`kernel/fork.c:2565-2572`）：

```c
	/* ok, now we should be set up.. */
	p->pid = pid_nr(pid);
	if (clone_flags & CLONE_THREAD) {
		p->group_leader = current->group_leader;   /* ← 沿用创建者的组长 */
		p->tgid = current->tgid;                   /* ← 沿用同一个 tgid */
	} else {
		p->group_leader = p;                       /* ← 自己是组长 */
		p->tgid = p->pid;                          /* ← 自己的 pid 就是 tgid */
	}
```

**三行代码定义了「线程」**：`tgid` 相同、组长相同 → 就是同一个"进程"里的线程。

`fork()` 和 `pthread_create()` 在内核里走的**是同一条路**：

```c
/* kernel/fork.c:2868 —— 两者唯一的入口 */
pid_t kernel_clone(struct kernel_clone_args *args)
{
	...
	p = copy_process(NULL, trace, NUMA_NO_NODE, args);    /* :2909 */
	...
	pid = get_task_pid(p, PIDTYPE_PID);                   /* :2921 */
	nr = pid_vnr(pid);                                    /* :2922 */
	...
}
```

区别只在 `args->flags`：

| | `fork()` | `pthread_create()`（NPTL） |
|---|-----------|---------------------------|
| `CLONE_VM` | ❌ 拷页表（COW） | ✅ **共享地址空间** |
| `CLONE_FILES` | ❌ 拷 fd 表 | ✅ 共享 fd 表 |
| `CLONE_FS` | ❌ 拷 fs 信息 | ✅ 共享 cwd/umask/root |
| `CLONE_SIGHAND` | ❌ 拷处置表 | ✅ **共享信号处置** |
| `CLONE_THREAD` | ❌ | ✅ **同一线程组** |
| `CLONE_SETTLS` | ❌ | ✅ **设置新 TLS** |
| `CLONE_CHILD_CLEARTID` | ❌ | ✅ **退出时清 TID 并 futex-wake** |
| `CLONE_CHILD_SETTID` | ❌ | ✅ 启动时写 TID |
| `CLONE_PARENT_SETTID` | ❌ | ✅ 让父线程拿到 TID |
| `exit_signal` | `SIGCHLD` | **`-1`（不发信号）** |

`CLONE_*` 标志（`include/uapi/linux/sched.h`）：

```c
#define CSIGNAL		0x000000ff	/* exit 时发的信号掩码 */
#define CLONE_VM	0x00000100	/* 共享 VM */
#define CLONE_FS	0x00000200	/* 共享 fs 信息 */
#define CLONE_FILES	0x00000400	/* 共享打开文件表 */
#define CLONE_SIGHAND	0x00000800	/* 共享信号处置与阻塞掩码 */
#define CLONE_THREAD	0x00010000	/* 同一线程组？ */
#define CLONE_SETTLS	0x00080000	/* 为子进程创建新 TLS */
#define CLONE_CHILD_CLEARTID 0x00200000	/* 子进程退出时清 TID */
#define CLONE_CHILD_SETTID   0x01000000	/* 启动时把 TID 写进 child_tid */
```

### 三条强制的依赖关系（写 `clone()` 前必看）

内核不接受任意组合（`kernel/fork.c:2267-2296`）：

```c
	/* 线程组必须共享信号处置，且 detached 线程只能在线程组内启动 */
	if ((clone_flags & CLONE_THREAD) && !(clone_flags & CLONE_SIGHAND))
		return ERR_PTR(-EINVAL);              /* :2267 */

	/* 共享信号处置隐含共享 VM。由上一条，线程组也隐含共享 VM */
	if ((clone_flags & CLONE_SIGHAND) && !(clone_flags & CLONE_VM))
		return ERR_PTR(-EINVAL);              /* :2275 */

	/* 线程组不能跨 PID/USER namespace */
	if (clone_flags & CLONE_THREAD) {
		if ((clone_flags & (CLONE_NEWUSER | CLONE_NEWPID)) ||
		    (task_active_pid_ns(current) != nsp->pid_ns_for_children))
			return ERR_PTR(-EINVAL);      /* :2292 */
	}
```

推导链：**`CLONE_THREAD` ⟹ `CLONE_SIGHAND` ⟹ `CLONE_VM`**。

> 这解释了一个常见的困惑：为什么线程之间**共享信号处置**却**各有各的信号掩码**？
> 因为 `CLONE_SIGHAND` 共享的是 `sighand->action[]`（处置表），
> 而掩码 `task_struct.blocked` 从来不共享——它始终是每线程一份。

### 线程退出时**不发** `SIGCHLD`（又一个关键差异）

```c
	/* CLONE_PARENT re-uses the old parent */
	if (clone_flags & (CLONE_PARENT|CLONE_THREAD)) {
		p->real_parent = current->real_parent;      /* 线程的"父"是进程的父 */
		p->parent_exec_id = current->parent_exec_id;
		if (clone_flags & CLONE_THREAD)
			p->exit_signal = -1;                /* ← 不发任何信号！ */
		else
			p->exit_signal = current->group_leader->exit_signal;
	} else {                                            /* 普通 fork */
		p->real_parent = current;
		p->parent_exec_id = current->self_exec_id;
		p->exit_signal = args->exit_signal;         /* SIGCHLD */
	}
```

`exit_signal = -1` 意味着**线程退出时不会给父进程发 `SIGCHLD`**，所以：
- 你**不能**用 `wait()` 回收线程（必须用 `pthread_join()`）
- 线程退出**不产生僵尸**（见 [29.6](29.6-joining-with-a-terminated-thread.md) 的 `exit_notify():746-751`）

而且注意 `real_parent = current->real_parent`：**线程的"父亲"不是创建它的那个线程，而是进程之父**。

## 四、为什么需要线程：三个理由 + 一个反面

| 理由 | 说明 |
|------|------|
| **① 共享数据方便** | 多线程直接读写同一地址空间的全局变量；多进程要走 shm / mmap / pipe，还得自己处理同步 |
| **② 创建/切换更快** | `fork()` 要拷页表（即使 COW，页表本身也要拷）；`pthread_create()` 只是新建 `task_struct` + 分配栈 |
| **③ 天然配合多核** | 一个进程的多条线程可以同时在多个核上跑，共享缓存的数据 |

```
  fork() 的代价（内核要做的事）
    copy_process()
      ├─ dup_task_struct()        拷 task_struct + 内核栈（2 页）
      ├─ copy_mm() → dup_mmap()   ⚠️ 拷【整个页表】+ 每个 VMA 的 vm_area_struct
      ├─ copy_files()             拷 fd 表（除非 CLONE_FILES）
      ├─ copy_fs()                拷 fs 信息
      ├─ copy_sighand()           拷信号处置表
      └─ copy_signal()            拷 signal_struct

  pthread_create() 的代价（CLONE_VM|FILES|FS|SIGHAND|THREAD 全开）
    copy_process()
      ├─ dup_task_struct()        同样要拷（task_struct 不共享）
      ├─ copy_mm() → 共享 mm      ✅ 只增引用计数，【不拷页表】
      ├─ copy_files() → 共享       ✅ 只增引用计数
      ├─ copy_fs() → 共享          ✅ 只增引用计数
      ├─ copy_sighand() → 共享     ✅ 只增引用计数
      └─ 分配栈（glibc 管，mmap 8MB 一段）
```

**量级参考**（x86-64 常见机器，数量级而非精确值）：

| 操作 | 量级 |
|------|------|
| `fork()` + `exit()` | ~100 µs 级（页表越大越慢） |
| `pthread_create()` + `join()` | ~20~30 µs 级 |
| 上下文切换（同进程线程间） | ~1~2 µs |
| 上下文切换（不同进程间） | ~2~3 µs（多一次 CR3 切换 + TLB 冲刷） |

> ⚠️ 别高估线程的优势：**调度开销几乎一样**（内核调度的是 `task_struct`，不看你是线程还是进程）。
> 进程间切换唯一多出来的代价是**换页表**（CR3 重载 + TLB 失效）。
> 线程真正的优势在**创建/销毁**和**共享数据的便利**，不在于切换。

### 反面：什么时候不该用线程

| 场景 | 理由 |
|------|------|
| 需要**故障隔离** | 一个线程段错误 → **整个进程死**（`SIGSEGV` 是线程定向但内核会 `zap_other_threads`）。多进程则只死一个 |
| 需要**独立的资源配额/权限** | 线程共享 fd 表、RLIMIT、UID。要隔离就得用进程 |
| 代码**不是线程安全的** | 用了 `strtok`、`getenv`、静态缓冲的第三方库 → 多线程直接数据竞争 |
| 需要**独立的可重启单元** | 线程无法单独重启；进程可以（supervisor / systemd 拉起） |

**HFT 里的典型取舍**：交易系统的**风控/行情解析**常用多线程（共享订单簿，延迟低），但**策略沙箱/回测**常用多进程（一个策略崩溃不能拖垮主进程）。

## 五、NPTL：glibc 这层做了什么

Linux 的线程实现经历过两代，这是历史包袱的来源：

| 实现 | 年代 | 模型 | 问题 |
|------|------|------|------|
| **LinuxThreads** | 内核 2.0~2.4 | 用 `clone(CLONE_VM\|...)` 但**没有** `CLONE_THREAD` | 每线程一个 PID；`getpid()` 各返回各的；信号语义不符 POSIX；`SIGCHLD` 满天飞 |
| **NPTL** | 内核 2.6+（glibc 2.3.2+） | 引入 `CLONE_THREAD` / `CLONE_SETTLS` / `CLONE_CHILD_CLEARTID` / futex | 现代实现，符合 POSIX |

**NPTL（Native POSIX Threads Library）依赖内核提供的四件套**：

| 内核能力 | 用途 |
|----------|------|
| `CLONE_THREAD` | 让所有线程共享同一个 `tgid`，`getpid()` 全组一致 |
| `CLONE_SETTLS` | 每个线程设置自己的 TLS 指针（`errno`、TSD 的基础） |
| `CLONE_CHILD_CLEARTID` + `CLONE_CHILD_SETTID` | 线程退出时内核自动清 TID 并 **futex-wake**（`pthread_join` 的实现基础） |
| **futex** | 用户态快路径的锁原语（`pthread_mutex` 的底层） |

其中第三条特别精巧（`kernel/fork.c:1616-1647`）：

```c
static void mm_release(struct task_struct *tsk, struct mm_struct *mm)
{
	...
	if (tsk->clear_child_tid) {
		if (atomic_read(&mm->mm_users) > 1) {      /* 还有别的线程在跑 */
			put_user(0, tsk->clear_child_tid);  /* ① 把 TID 写 0 */
			do_futex(tsk->clear_child_tid, FUTEX_WAKE,
					1, NULL, NULL, 0, 0);      /* ② futex 唤醒 1 个等待者 */
		}
		tsk->clear_child_tid = NULL;
	}
	...
}
```

**这就是 `pthread_join()` 能"等到"线程结束的全部秘密**——glibc 在创建线程时把 `CLONE_CHILD_CLEARTID` 指向线程描述符里的 `tid` 字段，线程退出时内核帮它清零 + 唤醒。不需要额外的系统调用去轮询。详见 [29.6](29.6-joining-with-a-terminated-thread.md)。

> **实践含义**：现代 Linux（glibc ≥ 2.3.2）上，`pthread_create()` 最终落到 `clone()`，
> 线程在内核里是**真正的调度实体**，可以被 `taskset`/`chrt` 单独设置亲和性与优先级。
> 这跟「用户态协程（coroutine）」或「绿色线程」是完全不同的东西——后者内核看不见。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | ① **默认栈 8MB 在嵌入式上是灾难**：256MB 内存的设备开 20 个线程就 160MB 栈（虽然是虚拟内存、按需提交，但 `ulimit -s` 和 overcommit 配置要核对）。`pthread_attr_setstacksize()` 显式设 64KB~1MB。② **线程数上限**：`RLIMIT_NPROC` 是针对**线程**计数的（`copy_process():2366` 检查 `UCOUNT_RLIMIT_NPROC`），嵌入式上常设得低，起线程池要注意。③ 无 MMU 的 MCU（如 Cortex-M）跑 Linux 是不行的（ucLinux 另说），那里只有 RTOS 的任务概念 |
| HFT | ① **线程是延迟隔离的天然单位**：行情、策略、风控、日志各占一个线程并**绑核**（`pthread_setaffinity_np` + 内核 `isolcpus`），避免互相抢占 cache。② **`errno` 每线程**这点在 HFT 里是好事——每线程的错误状态不会串，但要养成「出错立刻存 `errno`」的习惯。③ **故障隔离是线程的硬伤**：任一线程段错误 → `zap_other_threads()` 杀掉整个进程（[29.4](29.4-thread-termination.md)）。所以**策略逻辑常放独立进程**，通过共享内存通信，崩了重启不影响行情接收。④ **别迷信"线程比进程快"**：创建快是真的，切换几乎无差别；真正优势是共享地址空间省掉一次序列化/拷贝。⑤ 线程数 ≈ 核数（I/O 线程另算），过多线程只会增加调度抖动 |

## 代码示例：验证共享与私有

```c
/* share_or_not.c —— 实测哪些东西是共享的、哪些是每线程独立的
 *
 * 编译: gcc -Wall -Wextra -O2 -pthread -o share_or_not share_or_not.c
 * 运行: ./share_or_not
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <pthread.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>              /* O_RDONLY */
#include <sys/syscall.h>

/* 共享区 */
static int      g_counter   = 100;      /* 全局数据段 → 共享 */
static int     *g_heap      = NULL;     /* 堆 → 共享 */

/* 每线程独立区 */
static __thread int tls_var = 0;        /* TLS → 每线程一份 */

static pid_t gettid_(void) { return (pid_t)syscall(SYS_gettid); }

static void *worker(void *arg)
{
    long id = (long)arg;
    int  local = 0;                     /* 栈上 → 每线程一份 */

    /* ① 共享验证：改全局变量和堆 */
    g_counter++;
    (*g_heap)++;

    /* ② 私有验证：改栈变量和 TLS */
    local = (int)id * 10;
    tls_var = (int)id * 100;

    /* ③ errno 每线程独立：故意制造一个错误 */
    errno = 0;
    int fd = open("/nonexistent/file", O_RDONLY);   /* 必然失败，ENOENT */
    int my_errno = errno;

    sleep(1);                           /* 让所有线程都跑到这里 */

    printf("  线程%ld: tid=%-6d &g_counter=%p val=%d | &local=%p val=%d | "
           "&tls_var=%p val=%d | errno=%d(%s)\n",
           id, gettid_(),
           (void *)&g_counter, g_counter,
           (void *)&local,    local,
           (void *)&tls_var,  tls_var,
           my_errno, strerror(my_errno));
    (void)fd;
    return NULL;
}

int main(void)
{
    pthread_t t[3];

    g_heap = malloc(sizeof(int));
    *g_heap = 500;

    /* 主线程也制造一次错误，设成不同的 errno */
    errno = 0;
    if (open("/also/nonexistent", O_RDONLY) == -1)
        printf("主线程: tid=%-6d errno=%d(%s)\n", gettid_(), errno, strerror(errno));

    printf("\n  getpid() (TGID) 全部一样，gettid() 各不相同：\n");
    printf("  主线程: pid=%d tid=%d  （leader: pid == tid）\n\n", getpid(), gettid_());

    for (long i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, worker, (void *)i);
    for (int i = 0; i < 3; i++)
        pthread_join(t[i], NULL);

    printf("\n  最终: g_counter=%d (100+3=103，说明【共享】), *g_heap=%d (500+3=503)\n",
           g_counter, *g_heap);
    printf("  &g_counter / &tls_var 的地址说明：\n");
    printf("    g_counter 所有线程打印【同一个地址】 → 共享\n");
    printf("    local / tls_var 每个线程【地址都不同】 → 私有\n");

    free(g_heap);
    return 0;
}
```

**预期输出（关键观察点）**：

```
主线程: pid=12345 tid=12345  （leader: pid == tid）
  线程0: tid=12346 ... &g_counter=0x60104c val=103 | &local=0x7f...  | &tls_var=0x7f...  | errno=2
  线程1: tid=12347 ... &g_counter=0x60104c val=103 | &local=0x7f...  | &tls_var=0x7f...  | errno=2
  线程2: tid=12348 ... &g_counter=0x60104c val=103 | &local=0x7f...  | &tls_var=0x7f...  | errno=2
                              ↑ 地址相同（共享）      ↑ 地址不同（私有）  ↑ 地址不同（私有）
```

- `pid` 全是 12345，`tid` 各不相同 → **TGID 相同 = 同一进程**
- `g_counter` 地址相同、值是累加后的 103 → **共享**
- `local` / `tls_var` 地址各异 → **私有**
- 每个线程的 `errno` 各是各的，互不干扰

## 代码自测

<details>
<summary><b>问 1：</b>内核里「线程」和「进程」的结构体区别是什么？</summary>

**没有区别——都是 `struct task_struct`，内核里根本不存在「线程对象」。**

唯一的区别是创建时传的 `CLONE_*` 标志不同，导致某些资源是**拷贝**还是**共享引用**。
这个真相浓缩在三行代码里（`kernel/fork.c:2565-2572`）：

```c
	p->pid = pid_nr(pid);
	if (clone_flags & CLONE_THREAD) {
		p->group_leader = current->group_leader;   /* 沿用创建者的组长 */
		p->tgid = current->tgid;                   /* 沿用同一个 tgid */
	} else {
		p->group_leader = p;                       /* 自己是组长 */
		p->tgid = p->pid;                          /* pid == tgid */
	}
```

- `CLONE_THREAD` 置位 → `tgid` 沿用别人的 = "线程"
- 没置位 → `tgid` 用自己的 `pid` = "进程"（即使它是某个进程 fork 出来的）

`fork()` 和 `pthread_create()` 走的是**同一个函数** `kernel_clone()`（`:2868`），
最终都调 `copy_process()`（`:2909`）。

配套的两个可观测差异：

```c
/* ① 线程退出时不发 SIGCHLD（kernel/fork.c:2632-2633）*/
	if (clone_flags & CLONE_THREAD)
		p->exit_signal = -1;          /* 普通 fork 这里是 SIGCHLD */

/* ② 线程的"父亲"不是创建它的线程，而是进程之父（kernel/fork.c:2629-2630）*/
	if (clone_flags & (CLONE_PARENT|CLONE_THREAD))
		p->real_parent = current->real_parent;
```

第 ① 条解释了为什么**不能 `wait()` 线程**——线程退出压根不发 `SIGCHLD`，
`wait()` 永远等不到。要等线程结束只能用 `pthread_join()`。

`SYSCALL_DEFINE0(getpid)` 返回 `task_tgid_vnr(current)`，
`SYSCALL_DEFINE0(gettid)` 返回 `task_pid_vnr(current)`（kernel/sys.c:958/964）
——对同一进程的所有线程，前者相同、后者不同，这就是「同一进程」的内核定义。

</details>

<details>
<summary><b>问 2：</b>为什么 <code>CLONE_THREAD</code> 必须配合 <code>CLONE_SIGHAND</code>，而 <code>CLONE_SIGHAND</code> 又必须配合 <code>CLONE_VM</code>？</summary>

内核在 `copy_process()` 里做了两道强制检查（`kernel/fork.c`）：

```c
	/* 线程组必须共享信号处置，且 detached 线程只能在线程组内启动 */
	if ((clone_flags & CLONE_THREAD) && !(clone_flags & CLONE_SIGHAND))
		return ERR_PTR(-EINVAL);                    /* :2267 */

	/* 共享信号处置隐含共享 VM。由上一条，线程组也隐含共享 VM */
	if ((clone_flags & CLONE_SIGHAND) && !(clone_flags & CLONE_VM))
		return ERR_PTR(-EINVAL);                    /* :2275 */
```

形成推导链：**`CLONE_THREAD` ⟹ `CLONE_SIGHAND` ⟹ `CLONE_VM`**。

**为什么 `CLONE_THREAD` ⟹ `CLONE_SIGHAND`？**

因为 POSIX 要求**信号处置是进程级**的。如果同一进程的两个线程对 `SIGTERM` 有不同处置，
那么 `kill(pid, SIGTERM)` 该听谁的？内核在 `do_sigaction()` 里操作的是
`sighand->action[]`，而同一个线程组必须共享同一个 `sighand_struct`——
否则 `kill()` 的语义就崩了。

**为什么 `CLONE_SIGHAND` ⟹ `CLONE_VM`？**

源码注释说得很清楚：*"Blocking this case allows for various simplifications in other code."*
理由很实在：信号处置是**函数指针**。如果两个任务共享处置表但不共享地址空间，
那么一个任务改了 handler 指向自己地址空间的某个函数，另一个任务跳过去执行时
那个地址在它的地址空间里可能是完全不同的东西（甚至是无效地址）。

这是**实质性的安全约束**，不是偷懒。

**那为什么线程却有各自的信号掩码？**

因为 `CLONE_SIGHAND` 共享的是 `sighand->action[]`（**处置表**），
而掩码是 `task_struct.blocked` 字段——**它从来不在共享之列**。

```
  共享的（CLONE_SIGHAND）：sighand->action[]  处置表
  私有的（永远）：          task_struct.blocked  掩码
                            task_struct.pending  私有 pending
```

这个设计非常有用，是多线程信号处理的基石：
**主线程阻塞全部信号 → 所有 `pthread_create` 出来的线程继承该掩码 → worker 天然不受打扰**，
同时**处置仍是全进程共享的**（任何线程装 handler 全体生效）。

完整模型见 [Ch33.2](../../chapter-33-threads-further/notes/33.2-threads-and-signals.md)。

</details>

<details>
<summary><b>问 3：</b><code>errno</code> 是全局的吗？为什么多线程下不会串？</summary>

**不是全局的——每个线程一份。**

glibc 里 `errno` 是个宏：

```c
#define errno (*__errno_location())
```

`__errno_location()` 返回一个**每线程**的地址，通常来自线程控制块（TCB）。
在 x86-64 上，TCB 通过 `fs` 段寄存器访问（由 `arch_prctl(ARCH_SET_FS)` 设置，
`CLONE_SETTLS` 创建线程时内核会帮忙设置）。

```
      线程 A → __errno_location() → 0x7f1234500000   （A 的 errno）
      线程 B → __errno_location() → 0x7f6789000000   （B 的 errno）
                     ↓
            同名不同址，各写各的，互不干扰
```

**但有两个必须注意的陷阱：**

**陷阱一：出错后必须立刻保存 `errno`**

虽然线程之间不会串，但**同一线程内**的后续调用会覆盖它：

```c
/* ✗ 危险 */
if (read(fd, buf, n) == -1)
    fprintf(stderr, "read 失败了\n");   /* fprintf 内部可能改 errno */
    /* 之后再用 errno 就错了 */

/* ✓ 正确：第一件事就是存起来 */
if (read(fd, buf, n) == -1) {
    int saved = errno;
    fprintf(stderr, "read 失败: %s\n", strerror(saved));
    /* 用 saved，不用 errno */
}
```

**陷阱二：信号 handler 里也要保护 `errno`**

这一点常被忽略。handler 是在**被打断的那个线程**的栈上跑的，
所以它访问的是**同一个** `errno`：

```c
static void handler(int sig)
{
    int saved = errno;        /* ← 必须 */
    (void)sig;
    /* ... handler 逻辑，可能调系统调用改 errno ... */
    errno = saved;            /* ← 必须 */
}
```

**实践规则**：任何会修改 `errno` 的地方（handler、复杂函数），如果调用方可能依赖
之前的 `errno`，就要**先存后恢复**。这条规则与单线程/多线程无关，是通用的。

顺带一提：这也是**线程局部存储（TLS）最经典的应用**。`__thread int x` 用的
是同一套机制。见 [Ch31.4](../../chapter-31-thread-safety-tsd/notes/31.4-thread-local-storage.md)。

</details>

<details>
<summary><b>问 4：</b>线程一定比进程快吗？快在哪、不快在哪？</summary>

**要分开看三件事，结论各不相同：**

| 维度 | 线程 vs 进程 | 原因 |
|------|-------------|------|
| **创建/销毁** | ✅ **线程明显快**（数倍~10 倍） | 不用拷页表和各种表，只增引用计数 |
| **上下文切换** | ⚠️ **几乎一样快** | 内核调度的是 `task_struct`，不看你是线程还是进程 |
| **共享数据** | ✅ **线程快得多** | 直接读写同一地址空间；进程要 shm/mmap/pipe + 序列化 |

**创建快在哪**（`copy_process()` 的分支）：

```
  fork()：        copy_mm() → dup_mmap() → 拷【整个页表】+ 每个 VMA
                  copy_files() / copy_fs() / copy_sighand() → 各拷一份

  pthread_create()：CLONE_VM|FILES|FS|SIGHAND 全开
                  → 全部只【增引用计数】，一份都不拷
```

页表越大，`fork()` 越慢。一个占 8GB 内存的进程 `fork()` 一次可能要毫秒级——
这就是为什么 Redis 的 `BGSAVE` 会被吐槽（虽然后来用了别的技术）。

**切换为什么不快多少**：

```c
/* 内核调度器只认 task_struct，线程的 task_struct 和进程的完全同构 */
/* context_switch() 里的关键差异只有一处：*/
	if (!next->mm) {                       /* 内核线程 */
		...
	} else {
		switch_mm_irqs_off(prev->mm, next->mm, next);   /* 换页表 */
	}
```

即使是**不同进程**之间切换，代价也只是：
- 一次 CR3 寄存器重载
- TLB 中该进程 ASID 之外的条目失效（有 PCID 时大幅缓解）

在 x86-64 上这是**纳秒级**的事。线程的"切换快"在实测中往往测不出差别。

> ⚠️ 但有个例外：**TLB 与 cache 的局部性**。同一进程的线程共享页表，
> 切换后 TLB 命中率更高；共享数据的线程切换后 cache 也是热的。
> 在**内存访问密集**的负载下这部分收益是可观的。

**所以选型的真正理由应该是**：

| 选线程 | 选进程 |
|--------|--------|
| 需要频繁共享/传递大量数据 | 需要故障隔离（一个崩了不拖垮其他） |
| 需要频繁创建销毁执行单元 | 需要独立的资源配额/权限/RLIMIT |
| 延迟敏感、要避免序列化/拷贝 | 需要独立重启、热升级 |
| 用了非线程安全的库 → **反而要选进程** | 需要跨机器/容器边界 |

**HFT 实践**：行情解析与订单簿维护用**多线程 + 绑核**共享内存；
策略逻辑放**独立进程**（崩了能重启，不拖垮行情）；
两者通过共享内存 + `eventfd` 通知通信——把线程的"共享快"和进程的"隔离稳"都要了。

</details>

<details>
<summary><b>问 5：</b>NPTL 依赖内核的四个能力分别解决什么问题？缺一个会怎样？</summary>

NPTL（Native POSIX Threads Library）能符合 POSIX 语义，是因为内核（2.6 起）提供了四件套。
前一代 **LinuxThreads** 就是因为缺这些，才有一堆不兼容问题。

| 内核能力 | 解决的问题 | 缺了会怎样（LinuxThreads 的实际症状） |
|----------|-----------|--------------------------------------|
| **`CLONE_THREAD`** | 让同组线程共享一个 `tgid` | 每线程一个**不同的 PID** → `getpid()` 各返回各的；`kill(pid, sig)` 只能发给特定线程而非进程；`ps` 里看到一堆"进程" |
| **`CLONE_SETTLS`** | 为每线程设置独立的 TLS 指针 | `errno` 和 TSD 无法高效实现（要靠笨重的 per-thread 数组 + 系统调用查） |
| **`CLONE_CHILD_CLEARTID`**（+ `CLONE_CHILD_SETTID`） | 线程退出时内核**自动**清 TID 并 **futex-wake** 等待者 | `pthread_join()` 要靠额外机制（信号/轮询）实现，慢且复杂 |
| **futex** | 用户态快路径 + 内核态慢路径的混合锁 | 所有 `pthread_mutex` 操作都得进内核（`sys_futex` 之前的年代用信号量），无竞争时也要几微秒 |

其中第三条最精巧，值得看一眼内核实现（`kernel/fork.c:1628-1638`）：

```c
static void mm_release(struct task_struct *tsk, struct mm_struct *mm)
{
	...
	if (tsk->clear_child_tid) {
		if (atomic_read(&mm->mm_users) > 1) {          /* 还有别的线程在跑 */
			put_user(0, tsk->clear_child_tid);      /* ① TID 写 0 */
			do_futex(tsk->clear_child_tid, FUTEX_WAKE,
					1, NULL, NULL, 0, 0);          /* ② 唤醒 1 个等待者 */
		}
		tsk->clear_child_tid = NULL;
	}
	...
}
```

`pthread_join()` 的实现就是：

```
  join(tid):
      读该线程的 tid 字段
      while (tid != 0)                       ← 线程还活着
          futex_wait(&tid, 预期值)            ← 进内核睡，不轮询
      /* 线程退出时内核帮我们：tid = 0 + futex_wake(&tid, 1) */
      → 被唤醒，tid == 0，join 返回
```

**这个设计的价值**：线程退出时**不需要**额外系统调用去通知 joiner，
内核在 `mm_release()`（每个任务退出必经之路）顺手就做了。
而且用 futex 意味着**无竞争的 join 路径几乎零开销**。

> ⚠️ 注意 `atomic_read(&mm->mm_users) > 1` 这个条件：如果这是**最后一个**线程
> （整个进程要退出了），就不做清 TID + wake——因为已经没人在等了，
> 而且地址空间马上要被拆除，`put_user()` 会失败。

**实践含义**：现代 Linux（glibc ≥ 2.3.2）上线程在内核里是**真正的一等公民**，
每个线程都是可独立调度、可设亲和性与优先级的实体。这与 Go 的 goroutine、
Erlang 的 process 这类**用户态调度**的"绿色线程"有本质区别——后者内核看不见，
也就不可能被 `taskset`/`chrt` 单独设置。

</details>
