# 32.6 异步取消

> 本章：[TLPI 第 32 章 — Threads: Thread Cancellation](../README.md)

## 本节讲什么

1. **异步取消的语义与唯一合法场景**——任意指令边界可被杀；只有"纯计算 + 零资源依赖"的线程配得上它。
2. **实测对照**——同一个无取消点的计算循环：DEFERRED 杀不死、ASYNCHRONOUS 秒杀。
3. **工程结论**——为什么本节的存在意义是"让你有底气永远不用它"。

---

## 一、语义回顾与深化

```c
pthread_setcanceltype(PTHREAD_CANCEL_ASYNCHRONOUS, &oldtype);
```

- 取消请求到达即执行（信号处理器路径直接展开），**不等取消点**；
- 与 DISABLE 仍正交：DISABLE 时挂起（32.2 矩阵）；
- **cleanup 栈执行不保证**：展开发生在任意指令边界，栈本身的状态可能不一致；处理器可能只跑了一半；
- TSD 析构同样不可靠。

三宗罪（32.2 §三）在这里从"理论风险"变成"必然触发面"：任意边界 = 你迟早死在 malloc 里、死在锁里、死在半改数据的中间。

### 1.1 唯一合法场景的画像

```
async-安全线程的合同：
  ✓ 只碰自己的栈和寄存器
  ✓ 不 malloc/free（不碰堆）
  ✓ 不 lock/unlock（不碰任何锁，包括 glibc 内部锁）
  ✓ 不读写共享全局（除非用纯原子且能容忍任意截断点）
  ✓ 不调用任何库函数（printf/memcpy 都不行——内部可能有锁）
  ✓ 结果通过 volatile 原子变量或 pipe 交付
```

典型画像：无界数学搜索（素数打杂、蒙特卡洛抽样的 worker、密码学穷举）——算到哪算哪，死了就死了，结果不完整也无妨。**HFT/嵌入式的业务线程没有一条满足此合同。**

## 二、实测对照

配套 `async_demo.c`（gcc -O2 -Wall -Wextra 零告警编译通过）：

```c
/* async_demo.c — Ch32.6：同一个无取消点循环，DEFERRED 杀不死 vs ASYNC 秒杀
 * 编译：gcc -O2 -Wall -Wextra -o async_demo async_demo.c -pthread
 */
#define _GNU_SOURCE             /* pthread_tryjoin_np */
#include <stdio.h>
#include <errno.h>
#include <pthread.h>
#include <unistd.h>
#include <time.h>
#include <stdlib.h>

static volatile unsigned long sink;

static unsigned long crunch_step(void);        /* 先声明后使用 */

/* 纯计算：无任何取消点、无锁、无堆、无库调用 */
static void *crunch_deferred(void *a){(void)a;
    unsigned long x = 0;
    for (;;) x += crunch_step();
    return NULL;}                     /* 不可达 */

static void *crunch_async(void *a){(void)a;
    pthread_setcanceltype(PTHREAD_CANCEL_ASYNCHRONOUS, NULL);   /* ⭐ */
    unsigned long x = 0;
    for (;;) x += crunch_step();
    return NULL;}                     /* 不可达 */

static unsigned long crunch_step(void){
    unsigned long s = 0;
    for (int i = 1; i < 200000; i++) s += (unsigned long)i * 1103515245u;
    return s;
}

int main(void){
    struct timespec ts100ms = {0, 100*1000*1000};

    printf("== DEFERRED（默认）：无取消点 → 杀不死 ==\n");
    pthread_t t1;
    pthread_create(&t1, NULL, crunch_deferred, NULL);
    nanosleep(&ts100ms, NULL);
    pthread_cancel(t1);
    int r = pthread_tryjoin_np(t1, NULL);        /* 非阻塞试探 */
    if (r == EBUSY) {
        printf("  cancel 已发出 100ms，线程仍在跑（没有取消点）\n");
        printf("  演示结束——线程留在后台跑（进程退出时一并消亡）\n");
    } else {
        printf("  线程已死？(意外)\n");
    }

    printf("== ASYNCHRONOUS：任意边界 → 秒杀 ==\n");
    pthread_t t2;
    pthread_create(&t2, NULL, crunch_async, NULL);
    nanosleep(&ts100ms, NULL);
    pthread_cancel(t2);
    void *res;
    pthread_join(t2, &res);
    printf("  join: %s（无需取消点，指令边界即死）\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED" : "正常?");

    (void)sink;
    return 0;
}
```

实测输出（WSL2 / 12 核）：

```text
== DEFERRED（默认）：无取消点 → 杀不死 ==
  cancel 已发出 100ms，线程仍在跑（没有取消点）
  演示结束——线程留在后台跑（进程退出时一并消亡）
== ASYNCHRONOUS：任意边界 → 秒杀 ==
  join: PTHREAD_CANCELED（无需取消点，指令边界即死）
```

解读：**同一个循环，唯一的差别是一行 `setcanceltype`**。DEFERRED 的取消请求在无取消点的循环里永远挂起（32.3/32.4 的主题）；ASYNC 在信号到达的任意指令边界立即执行。这组对照是"类型开关决定生死时机"的最直观演示——也顺带展示了 `pthread_tryjoin_np`（GNU 扩展）做非阻塞探测的用法。

## 三、工程结论：本节的正确用法是"不用"

| 如果你想… | 正确做法 |
|-----------|----------|
| 杀掉卡在计算里的线程 | 给循环加 `pthread_testcancel`（32.4），保持 DEFERRED |
| 快速停止 worker | 协作退出标志 + 周期检查（HFT 标准）|
| 清理已死线程的资源 | cleanup 栈（32.5）——但 ASYNC 下它不可靠，所以又回到 DEFERRED |
| 真·不可中断的长计算 | fork 子进程做，超时 kill(pid)——进程边界比线程边界硬得多，内核保证全回收 |

**异步取消在认真写的系统里的出场率应为零**。它存在的价值：① POSIX 完整性；② 面试与考试；③ 让你理解"为什么取消机制要设计成延迟+取消点+清理栈这么复杂"——全是为了把"死亡时机"约束到安全边界，而 ASYNC 把这个约束整个扔掉了。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | 明令禁止：代码规范里写死 "PTHREAD_CANCEL_ASYNCHRONOUS 禁用"（连同整个 pthread_cancel 一起，只在遗留路径开白名单）。热路径的"随时可停"用 SPSC 环 + 消费侧检查实现 |
| HFT · 回测集群 | 唯一接近合法的场景是外包给**进程**：无界搜索 worker 跑在独立进程里，超时 `kill -9`——硬边界 + 内核级回收，比 ASYNC 线程取消的语义干净一个数量级 |
| 嵌入式 | RTOS 任务删除 ≈ ASYNC 取消且**连信号投递都没有**（直接调度移除）：嵌入式更早学会了同一课——可丢弃任务随便删，有资源任务必须自杀式退出 |

## 自测题

**题目 1**：为什么 ASYNC 模式下 cleanup 栈的保证不可靠？

<details>
<summary>参考答案</summary>

cleanup 展开发生在信号到达的任意指令边界：处理器自身执行到一半可能再被打断（嵌套取消）、栈顶指针可能处于不一致状态、处理器访问的资源可能正是"当前指令正在半改"的那个。DEFERRED 的全部设计（取消点=安全边界）就是为了让展开发生在一致点——ASYNC 摧毁了这个前提，因此一切建立在"边界安全"上的保证（cleanup、TSD 析构、锁配对）同时失效。

</details>

**题目 2**：需求："一个计算密集线程必须能被立刻停止，且它持有 8MB 堆缓冲"。给出两个方案并比较。

<details>
<summary>参考答案</summary>

方案 A（线程内）：DEFERRED + 循环内 `pthread_testcancel` + 缓冲放 TSD/局部，由 cleanup 栈释放。停止延迟=检查站间隔；资源保证完整释放。方案 B（进程边界）：fork worker 进程做计算，8MB 缓冲在子进程内，停止= kill(pid)+waitpid——立刻生效（信号打断任意指令，进程死亡由内核全回收），缓冲随地址空间消亡。比较：A 停止有延迟但零进程开销；B 即停即净但创建/通信成本高。生产常选 B（超时兜底），交互场景选 A。

</details>
