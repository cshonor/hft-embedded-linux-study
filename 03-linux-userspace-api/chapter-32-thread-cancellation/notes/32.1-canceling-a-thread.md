# 32.1 取消线程

> 本章：[TLPI 第 32 章 — Threads: Thread Cancellation](../README.md)
> - 上一节：本章首页
> - 下一节：[32.2 取消状态与类型](32.2-cancellation-state-and-type.md)

> 源码核验：Linux v6.6 · `kernel/signal.c`（`do_send_specific():3935` · `do_tkill():3962` · `SYSCALL_DEFINE3(tgkill):3988`）· glibc 侧：`pthread_cancel` 以 `tgkill(tgid, tid, SIGCANCEL)` 投递，SIGCANCEL = 32（`__SIGRTMIN`，glibc 保留）

---

## 本节讲什么

1. **`pthread_cancel` 的真实语义**——它只是**异步投递一个请求**，不是"立即杀死"；默认（延迟）模式下要等目标线程走到取消点才真正终止。
2. **取消 vs 三种"亲缘"终止方式**——`pthread_exit`（自愿）、`pthread_cancel`（外部请求）、进程级信号（粗暴）；以及为什么取消是它们中间唯一的"线程粒度 + 可清理"方案。
3. **内核视角**——glibc 用 `tgkill` 发 SIGCANCEL(32) 实现取消请求；`tgkill` 的注释原文正好解释了为什么要带 tgid。

---

## 一、API 与语义

```c
#include <pthread.h>
int pthread_cancel(pthread_t thread);          /* 返回 0 = 请求已投递（≠已终止）*/
```

四条语义：

| # | 语义 | 推论 |
|---|------|------|
| 1 | **异步投递**：立即返回，不等待目标终止 | 想确认死透，必须 `pthread_join` |
| 2 | 默认延迟模式：请求**挂起（pending）**，目标走到取消点才执行 | 走不到取消点的线程（纯计算循环）永不死 |
| 3 | 被取消线程以 `pthread_exit(PTHREAD_CANCELED)` 收场 | `join` 的 retval == `PTHREAD_CANCELED` = 被取消铁证 |
| 4 | 可接合线程被取消后仍要 join 回收 | 与普通退出一样走 zombie→join 流程（29.2/29.4） |

### 1.1 与亲缘机制对比

| 机制 | 发起方 | 粒度 | 能否清理 | 风险 |
|------|--------|------|----------|------|
| `return` / `pthread_exit` | 线程自己 | 线程 | ✓（自然收尾）| — |
| `pthread_cancel` | 其他线程 | **线程** | ✓（cleanup 栈，32.5）| 延迟模式下安全；异步模式危险（32.6）|
| `kill(pid, sig)` 默认处理 | 其他进程/线程 | **进程** | ✗（信号处理器都不一定跑完）| 杀一个线程 = 杀全进程 |
| `_exit` | 本线程 | 进程 | ✗ | 无 |

一句话：`pthread_cancel` 是 POSIX 里唯一"线程粒度 + 异步发起 + 目标可清理"的终止原语——代价是它的语义复杂度（状态/类型/取消点/cleanup 四件套，本章全部）。

### 1.2 内核视角：请求是怎么送到的

glibc 的 `pthread_cancel`（2.28+ 的 futex-cancel 设计）：

```
pthread_cancel(t)
  1. 在目标线程 struct pthread 里置取消标志（tid 置为特殊值 → 目标在
     系统调用取消包装里自查）
  2. tgkill(tgid, tid, SIGCANCEL=32)      ← 强制打断目标可能正阻塞的系统调用
     └─ 内核：SYSCALL_DEFINE3(tgkill):3988 (kernel/signal.c)
         └─ do_tkill():3962   si_code = SI_TKILL, si_pid = 调用者 TGID
             └─ do_send_specific():3935
                 ├─ find_task_by_vpid(pid)           按线程 PID 找任务
                 ├─ check_kill_permission():3943     权限检查
                 └─ do_send_sig_info():3948          挂到目标线程的信号队列
  3. 目标线程被信号唤醒 → glibc 的取消包装代码检查标志 →
     到取消点/立即执行取消（展开 cleanup → pthread_exit(PTHREAD_CANCELED)）
```

为什么用 `tgkill` 而不是 `kill`？内核注释（`kernel/signal.c:3982`）原文就是答案：

> *"This syscall also checks the @tgid and returns -ESRCH even if the PID exists but it's not belonging to the target process anymore. **This method solves the problem of threads exiting and PIDs getting reused**."*

`kill(pid)` 的 pid 是**进程**（TGID）级；线程 ID 撞上 PID 复用时可能误杀别的进程。`tgkill(tgid, tid, sig)` 双重校验"tid 必须仍属于 tgid"——和 29.5 讲的 `pthread_t` 复用问题同源，POSIX 线程模型在内核里的最后一道身份校验。

> SIGCANCEL = 32 = `SIGRTMIN`（glibc 首个实时信号）：glibc **保留** RT 信号 32/33（取消 / setuid 广播），用户程序从 `SIGRTMIN` 拿到的其实是 34 起（`man 7 signal`）。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | **不推荐**用 cancel 停策略线程：延迟模式的取消点时序不受控（可能停在 read 半途）；HFT 用协作式退出——退出标志（原子）+ condvar 唤醒 + 线程自己在**选定的安全边界**收尾（当前订单处理完再退）。cancel 只用于"失控线程的最后一招" |
| HFT · 关停顺序 | 若用 cancel：先停止喂任务 → cancel → join → 检查 PTHREAD_CANCELED → 收全局资源。直接 cancel 正在持锁写订单簿的线程 = 数据结构永久损坏 |
| 嵌入式 | RTOS 一般没有"取消"（任务删除是硬杀）：要么 pthread_cancel 的清理栈不可用，要么干脆删除任务 → 泄漏。嵌入式惯例同 HFT：协作退出 + 超时升级（软退 → 硬杀） |
| 嵌入式 · 信号号 | 若平台无 glibc 的 SIGCANCEL 保留机制（musl 有自己的实现），跨 libc 移植别假设 32/33 可用 |

## 代码示例

`cancel_demo.c`（gcc -O2 -Wall -Wextra 零告警编译通过；timeout 保护防挂）：

```c
/* cancel_demo.c — Ch32.1/32.2/32.3/32.4：取消请求、状态屏蔽、取消点、testcancel
 * 编译：gcc -O2 -Wall -Wextra -o cancel_demo cancel_demo.c -pthread
 */
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>
#include <string.h>

/* ---------- 演示 1（32.1）：请求是异步的，join 拿 PTHREAD_CANCELED ---------- */
static void *sleeper(void *a){(void)a;
    printf("  [worker] 开始 sleep(10)，必经取消点\n");
    sleep(10);                       /* 取消点 */
    printf("  [worker] 不可能到达这里\n");
    return NULL;}

static void demo_cancel_sleep(void){
    pthread_t t;
    pthread_create(&t, NULL, sleeper, NULL);
    usleep(100000);
    pthread_cancel(t);               /* 异步投递请求，立即返回 */
    printf("[demo1] cancel 已投递（请求≠终止）\n");
    void *res;
    pthread_join(t, &res);
    printf("[demo1] join 结果 %s\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED：确认被取消" : "正常返回？");
}

/* ---------- 演示 2（32.2）：DISABLE 期间请求挂起，恢复后生效 ---------- */
static void *shielded(void *a){(void)a;
    pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, NULL);
    printf("  [worker] 取消已 DISABLE，进入 3 段不可打断工作\n");
    for (int i = 1; i <= 3; i++) { sleep(1); printf("  [worker] 关键段 %d/3 完成\n", i); }
    pthread_setcancelstate(PTHREAD_CANCEL_ENABLE, NULL);
    sleep(1);                        /* 恢复后第一个取消点：这里被取消 */
    printf("  [worker] 不应到达\n");
    return NULL;}

static void demo_state_shield(void){
    pthread_t t;
    pthread_create(&t, NULL, shielded, NULL);
    usleep(100000);
    pthread_cancel(t);
    printf("[demo2] 取消请求已发出（此时目标 DISABLE，请求挂起）\n");
    void *res;
    pthread_join(t, &res);
    printf("[demo2] join 结果 %s\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED：关键段跑完才被取消"
                                    : "正常返回？");
}

/* ---------- 演示 3（32.3/32.4）：纯计算循环没有取消点 → testcancel 补位 ---------- */
static volatile long sink;
static void *spinner(void *a){(void)a;
    long x = 0;
    for (;;) {                       /* 纯计算：没有任何取消点 */
        for (int i = 0; i < 1000000; i++) x += i;
        sink = x;
        pthread_testcancel();        /* ⭐ 手动取消点：不加这里就永远杀不掉 */
    }
    return NULL;}

static void demo_spinner(void){
    pthread_t t;
    pthread_create(&t, NULL, spinner, NULL);
    usleep(200000);
    pthread_cancel(t);
    void *res;
    pthread_join(t, &res);
    printf("[demo3] 纯计算循环 %s\n",
           res == PTHREAD_CANCELED
               ? "被取消（pthread_testcancel 补位生效）" : "没被取消？");
}

int main(void){
    printf("==== demo1：异步请求 + join 验证 ====\n");
    demo_cancel_sleep();
    printf("==== demo2：DISABLE 屏蔽 + 恢复生效 ====\n");
    demo_state_shield();
    printf("==== demo3：纯计算 + pthread_testcancel ====\n");
    demo_spinner();
    return 0;
}
```

实测输出（WSL2 / 12 核）：

```text
==== demo1：异步请求 + join 验证 ====
  [worker] 开始 sleep(10)，必经取消点
[demo1] cancel 已投递（请求≠终止）
[demo1] join 结果 PTHREAD_CANCELED：确认被取消
==== demo2：DISABLE 屏蔽 + 恢复生效 ====
  [worker] 取消已 DISABLE，进入 3 段不可打断工作
[demo2] 取消请求已发出（此时目标 DISABLE，请求挂起）
  [worker] 关键段 1/3 完成
  [worker] 关键段 2/3 完成
  [worker] 关键段 3/3 完成
[demo2] join 结果 PTHREAD_CANCELED：关键段跑完才被取消
==== demo3：纯计算 + pthread_testcancel ====
[demo3] 纯计算循环被取消（pthread_testcancel 补位生效）
```

三点解读：

1. demo1：`sleep` 是取消点，请求投递后目标在睡眠中被唤醒并立即终止——`join` 拿到 `PTHREAD_CANCELED` 是唯一的死亡证明。
2. demo2：请求在 DISABLE 期间**挂起**，三段关键工作全部完成后（ENABLE + 到达 `sleep` 取消点）才执行——"先忙完要紧事再死"。
3. demo3：百万次迭代的纯计算循环里没有任何标准取消点，没有 `pthread_testcancel` 的版本 join 会永远等下去（这正是 32.4 的主题）。
