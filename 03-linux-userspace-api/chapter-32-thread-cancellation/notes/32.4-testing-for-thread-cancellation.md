# 32.4 主动检查：`pthread_testcancel`

## 本节讲什么

1. **`pthread_testcancel` 是什么**——一个手动安插的取消点：检查挂起请求，有则立即执行取消（走完 cleanup 栈 → `pthread_exit(PTHREAD_CANCELED)`）。
2. **它解决什么**——纯计算/自旋循环没有自然取消点，"线程杀不死"的标准修复。
3. **安插的工程规范**——放哪、放多密、和状态开关怎么配合。

---

## 一、API 与语义

```c
#include <pthread.h>
void pthread_testcancel(void);   /* 无返回值：要么返回继续跑，要么不返回（被取消）*/
```

语义一句话：**"现在是不是一个安全死亡点？是就死。"** 它的行为完全等价于"到达一个取消点"：

- 无挂起请求 → 立即返回，开销近似一次内存读（快路径）；
- 有挂起请求 且 state==ENABLE 且 type==DEFERRED → 在**此处**执行取消（cleanup 栈展开、TSD 析构、`pthread_exit(PTHREAD_CANCELED)`）；
- state==DISABLE → 不检查直接返回（DISABLE 免疫一切取消点，包括手动这个）。

> "无返回值"的函数在 C 里很少见——`pthread_testcancel` 和 `longjmp`/`exit` 一个家族：正常路径返回，取消路径不返回。写代码时把它理解为"关卡"而不是"函数调用"。

## 二、给纯计算循环开检查站

### 2.1 标准形态

```c
void *number_cruncher(void *arg) {
    (void)arg;
    for (;;) {                          /* 长计算：没有自然取消点 */
        crunch_one_chunk();             /* 安全边界：块与块之间 */
        pthread_testcancel();           /* ⭐ 检查站 */
    }
    return NULL;                        /* 实际不可达（靠取消或外部退出标志）*/
}
```

### 2.2 安插三原则

| 原则 | 说明 |
|------|------|
| **放安全边界，不放代码中间** | 块与块之间（数据一致点）；绝不放在持锁段/半改数据中段——它的语义就是"死在这也安全" |
| **密度 = 响应延迟预算** | 两个检查站之间隔多久，cancel 的生效就最多延迟多久。100ms 一次 → 最坏 100ms 才死；配 join 超时时按这个预算设 |
| **和退出标志二选一或并存** | 新代码推荐协作退出（`while (running)`）；`testcancel` 用于必须支持 pthread_cancel 的库代码，或作为协作退出失效时的兜底 |

### 2.3 典型 bug 形态

```c
/* bug：检查站安插在持锁段内 */
pthread_mutex_lock(&m);
for (...) {
    crunch();
    pthread_testcancel();     /* ✗ 死在这 = m 永远锁着 */
}
pthread_mutex_unlock(&m);

/* 修复 1：移到锁外/循环外层 */
pthread_mutex_lock(&m); ...; pthread_mutex_unlock(&m);
pthread_testcancel();         /* ✓ 无锁无半改数据 */

/* 修复 2：cleanup 栈托底（32.5）后保留原地检查 */
```

## 三、与状态开关的配合（把 32.1–32.4 串起来）

完整的心智模型——一个请求从投递到执行的路径：

```
pthread_cancel(t) ──投递──▶ [挂起的请求] ──────────────────────────┐
                                                                   ▼
目标线程 t 的每次"取消点"（标准取消点 or pthread_testcancel）：
    state == DISABLE ？ ──是──▶ 请求继续挂起（本次不执行）
    type == DEFERRED  ？ ──是──▶ 【在当前取消点执行】
                                   ├─ 展开清理栈（LIFO，32.5）
                                   ├─ 跑 TSD 析构（31.3）
                                   └─ pthread_exit(PTHREAD_CANCELED)
    type == ASYNCHRONOUS ──▶ 不等取消点，信号到达即执行（32.6，危险）
```

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | 热路径循环里加 `pthread_testcancel` 等于白送一次分支预测（近似免费），但纪律上 HFT 不引入 pthread_cancel 依赖——退出检查用业务自己的 `running` 原子标志，语义一致且可审计。testcancel 真正的位置是非热路径的长任务线程（回测、重算、归档） |
| HFT · 关停预算 | 检查站密度 = 关停延迟上界。回测框架约定"每 chunk 检查一次 + chunk ≤ 50ms"，运维 kill 脚本的超时按 3×chunk 预算设置，超时升级为 SIGKILL（进程级）|
| 嵌入式 | RTOS 无 pthread_cancel 时，`testcancel` 的等价物是 `if (kthread_should_stop()) break;`（内核线程）或任务消息队列里的退出命令轮询——"定期在安全边界问一句该不该退"是跨平台的通用纪律 |

## 自测题

**题目 1**：`pthread_testcancel` 的返回值为什么是 void？调用它之后紧接着的代码在什么情况下不会执行？

<details>
<summary>参考答案</summary>

因为存在两条路径：无挂起请求（或 DISABLE）时立即返回、代码继续；有挂起请求且 ENABLE+DEFERRED 时**在调用点执行取消**（cleanup 栈展开 + TSD 析构 + pthread_exit(PTHREAD_CANCELED)）——函数不返回，调用点之后的代码不执行。它与 exit/longjmp 同属"可能不返回"的函数。

</details>

**题目 2**：`pthread_setcancelstate(PTHREAD_CANCEL_DISABLE)` 之后调用 `pthread_testcancel()` 会发生什么？

<details>
<summary>参考答案</summary>

什么都不发生：DISABLE 优先于一切取消点（包括手动的），testcancel 直接返回，挂起的请求继续等。这保证了 32.2 临界区包裹模式对 testcancel 同样免疫——即使在临界区里误调了它也不会死在锁内。

</details>

**题目 3**：设计一个回测 worker：每 chunk 计算约 30ms，要求 cancel 后 100ms 内必定退出（安全边界为块间）。写出循环骨架。

<details>
<summary>参考答案</summary>

```c
for (;;) {
    crunch_one_chunk();              /* ~30ms，安全边界为块间 */
    pthread_testcancel();            /* 最坏 30ms 后生效 ✓ 100ms 预算内 */
    /* 协作退出标志与 testcancel 并存：库外用户用 cancel，库内用标志 */
    if (!atomic_load(&running)) break;
}
```
关键：检查站必须在块间（数据一致点）；chunk 时长即取消延迟上界（30ms ≤ 100ms ✓）。若单个 chunk 无法压到预算内，就得在 chunk 内部找次级安全边界加检查。

</details>
