## 本节讲什么

1. **取消点的定义与两大类**——延迟取消的"检查站"：可能无限阻塞的函数（必须检查）+ 部分其他函数（实现可选）；一张主表 + 一张"不是取消点"的反表。
2. **glibc 2.28 的机制变革**——futex-cancel 设计：取消点从"函数清单"变成"系统调用包装层"，为什么这让取消点的实际集合比 man 页更大、更依赖版本。
3. **工程含义**——"我的线程会不会被卡在永不取消的循环里"的排查法。

---

## 一、取消点是什么

延迟取消（默认类型）下，挂起的取消请求只在**取消点**执行。POSIX 把取消点分成两档：

- **必须**是取消点的函数：**可能无限期阻塞**的——被取消请求唤醒是线程逃出生天的唯一途径（否则 sleep(365天) 的线程永远杀不死）。
- **可能**是取消点的函数：标准允许实现自选（`printf`、`malloc` 在 glibc 里不是，别的 libc 可能是）。

主表（工程上够用版，完整表见 `man 3 pthreads` 取消点一节）：

| 类别 | 取消点函数 |
|------|-----------|
| 定时 | `sleep` · `nanosleep` · `clock_nanosleep` · `usleep` |
| I/O | `read` · `write` · `pread` · `pwrite` · `aio_suspend` |
| 多路复用 | `select` · `pselect` · `poll` · `ppoll` · `epoll_wait` |
| 网络 | `accept` · `accept4` · `connect` · `send` · `recv` · `sendto` · `recvfrom` |
| 文件/目录 | `open`（部分实现）· `close`（可选）· `fsync` · `fdatasync` · `getdents`/`readdir` |
| 进程/同步 | `wait` · `waitpid` · `waitid` · `pthread_join` · `pthread_cond_wait` · `pthread_cond_timedwait` · `sem_wait` · `sem_timedwait` |
| 信号 | `sigwait` · `sigwaitinfo` · `sigtimedwait` · `pause` |
| 消息队列/锁 | `mq_receive` · `mq_send` · `pthread_mutex_lock`（**部分实现可选**，glibc 一般不检查）|

**反表（常见误认，不是取消点）**：

| 函数 | 为什么不是 |
|------|-----------|
| `malloc` / `free` | 不无限阻塞（持内部锁但会返回）；设为取消点会在堆半更新时死线程 |
| `memcpy` / `sin` / 纯计算 | 不阻塞 |
| `pthread_mutex_lock`（glibc）| 快路径不阻塞；慢路径 futex 睡眠在新 glibc 里**可以**被打断处理取消（见 §二），但语义上不算标准取消点 |
| 自旋循环 / 忙等 | 没有函数调用就没有检查——**这是"线程杀不死"的第一大原因** |

> 记忆钩子：**取消点 ≈ "可能睡死的函数"**。线程睡在系统调用里时，取消请求用信号（32.1 的 SIGCANCEL）把它踹醒——醒来的包装层检查标志、决定展开。不睡的代码根本没有被踹的机会。

### 1.1 排查"线程杀不死"

```
症状：pthread_cancel + join 永远不返回
排查顺序：
 1. 目标是不是纯计算/自旋循环？        → 无取消点，加 pthread_testcancel（32.4）
 2. 目标是不是 DISABLE 忘了恢复？      → 请求在挂起（32.2）
 3. 目标是不是死了但没 join？          → cancel 不等于回收（32.1）
 4. 目标是不是被信号屏蔽挡住 SIGCANCEL？→ pthread_sigmask 别挡 32 号
 5. 循环里调用的"阻塞"函数是不是宏/内联后的忙等包装？（如自实现的 sleep 轮询）
```

## 二、glibc 2.28+：取消点搬进了系统调用包装层

老设计（glibc < 2.28）：每个取消点函数手动调 `pthread_testcancel` + 特殊的 futex 处理——覆盖不全、且取消阻塞中的 `futex` 系统调用（condvar 睡眠）要靠内核配合重启。

新设计（glibc ≥ 2.28，futex-cancel）：

1. `pthread_cancel` 置标志 + `tgkill(SIGCANCEL)`（32.1 §1.2）；
2. **所有**可取消的系统调用都走 `__syscall_cancel` 包装：进入时查标志、syscall 执行中信号可打断、返回路径再查标志；
3. 被信号打断的 syscall 按 Linux 的 `restart_syscall` 语义重启或返回 EINTR——取消包装在 EINTR 路径上二次检查标志，命中即展开取消。

工程推论：

- **取消点的实际集合随 glibc 版本变化**（2.28 后显著变大：任何可取消的系统调用阻塞中都能被取消唤醒）——man 页的静态清单只是下界；
- "这个函数是不是取消点"的争论，答案常常是**看版本**。这就是 32.2 守则 1（临界区 DISABLE 包裹）成为一劳永逸方案的原因：不赌清单，直接免疫。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | 取消点= 系统调用边界 = 调度/IO 抖动点。热路径线程本来就禁止 IO 和睡眠（一核一线程 + 无锁），也就天然"没有取消点"——再次印证 HFT 用协作退出而不是 cancel 的架构选择 |
| HFT · 关停 | 关停序列里的 join 要设超时（pthread_timedjoin_np，GNU 扩展）——万一某个线程卡在非取消点，别让关停流程整个挂死 |
| 嵌入式 | 嵌入式的"取消点"直觉：任何可能睡的调用（消息队列收、信号量等）就是任务能被删除的唯一安全位置——RTOS 任务删除的工程规范同构于 POSIX 取消点纪律 |

## 代码示例

见 [32.1 的 cancel_demo.c](32.1-canceling-a-thread.md)：demo1（`sleep` 取消点内被取消）、demo3（纯计算循环无取消点，靠 `pthread_testcancel` 补位）正是本节两面的实测。

补充一个"读管道被取消"的经典验证（可与 Ch30 阻塞队列对照）：

```c
/* cancel_read.c — read() 阻塞中被取消（可编译片段，配套主函数自加 timeout 保护） */
#include <pthread.h>
#include <unistd.h>
#include <stdio.h>

static int fd[2];

static void *reader(void *a){(void)a;
    char buf[16];
    printf("  [reader] 阻塞在 read()（无人写）\n");
    ssize_t r = read(fd[0], buf, sizeof buf);   /* 阻塞 = 取消点 */
    (void)r;
    return NULL;}

/* main: pipe(fd); create(reader); usleep(100ms); cancel; join */
```

实测行为：reader 阻塞在 `read` 的系统调用里，`pthread_cancel` 的 SIGCANCEL 信号把它踹醒，glibc 取消包装在返回路径上展开——join 得到 `PTHREAD_CANCELED`，管道缓冲没人消费也无所谓（进程随后退出）。这正是"可能无限阻塞的函数必须是取消点"的设计动机：**没有取消点，阻塞在 IO 上的线程就永远杀不死**。

## 自测题

**题目 1**：一个工作线程的主循环是 `while (running) { for (i=0;i<1e9;i++) sum += i; check_heartbeat(); }`，check_heartbeat 里没有任何函数调用。pthread_cancel 后这个线程会终止吗？

<details>
<summary>参考答案</summary>

不会。整个循环没有任何取消点（纯计算 + 无函数调用），挂起的取消请求永远等不到执行机会。修法：在 check_heartbeat（或每轮外层）加 `pthread_testcancel()`，或把循环改成周期性睡 1µs / poll 一个唤醒 fd。这是"线程杀不死"第一大原因的标准形态。

</details>

**题目 2**：为什么 POSIX 规定"可能无限阻塞"的函数**必须**是取消点，而 `malloc` 不可以是？

<details>
<summary>参考答案</summary>

必须：无限阻塞的函数若不检查取消，线程睡在里面永远无法响应取消请求——取消机制对这些函数失效（sleep 百年的线程杀不死）。不可以：malloc/free 操作的是进程级堆元数据，中途被取消会留下半更新的链表（堆损坏），且它持内部 arena 锁——死在锁内 = 全进程堆瘫痪。取消点集合的设计原则就是"醒得安全"：睡死函数必须醒，内部锁函数绝不能醒。

</details>

**题目 3**：glibc 2.28 之后，"某函数是不是取消点"为什么变得更难静态回答？工程上如何免疫这种不确定性？

<details>
<summary>参考答案</summary>

因为取消检查搬进了系统调用包装层（__syscall_cancel）：任何可取消的系统调用在阻塞中被 SIGCANCEL 打断后都会走取消检查——实际可取消的行为集合由运行时路径决定，man 页清单只是下界，且随 glibc 版本变化。免疫方法：不赌清单——需要保证不被打断的代码段用 pthread_setcancelstate(DISABLE) 包裹（32.2 守则 1），需要保证能被打断的循环手动加 pthread_testcancel（32.4）。

</details>
