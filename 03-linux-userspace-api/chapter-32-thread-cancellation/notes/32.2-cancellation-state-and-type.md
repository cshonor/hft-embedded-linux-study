# 32.2 取消状态与类型

## 本节讲什么

1. **两个正交的开关**——状态（ENABLE/DISABLE：要不要接受请求）与类型（DEFERRED/ASYNCHRONOUS：接受后何时执行），2×2 组合决定线程的"死亡资格"。
2. **临界区屏蔽模式**——持锁/半改数据的区段 DISABLE 取消，出来再恢复；这是延迟取消工程化的核心用法。
3. **异步类型为什么几乎不可用**——任意指令边界被杀的三宗罪（持锁死、堆锁死、数据结构残缺）。

---

## 一、两个开关

```c
int pthread_setcancelstate(int state,    int *oldstate);
/*   PTHREAD_CANCEL_ENABLE（默认）/ PTHREAD_CANCEL_DISABLE           */

int pthread_setcanceltype(int type,      int *oldtype);
/*   PTHREAD_CANCEL_DEFERRED（默认）/ PTHREAD_CANCEL_ASYNCHRONOUS    */
```

两个开关正交，**逐线程**设置（每线程自己的状态，不是进程级）：

| 状态 \ 类型 | DEFERRED | ASYNCHRONOUS |
|------------|----------|--------------|
| **ENABLE**（默认格） | 到**取消点**才执行（工程默认）| **任意指令边界**可执行（危险）|
| **DISABLE** | 请求挂起（pending），恢复 ENABLE 后到取消点执行 | 同左——DISABLE 优先于类型 |

三条规则：

1. **DISABLE 时请求只是挂起**，不丢；恢复 ENABLE 后在下个取消点执行。挂起的取消**无法撤销**（POSIX 无 "uncancel"）——`pthread_cancel` 是单向门。
2. 状态/类型开关本身**不是取消点**（`setcancelstate` 不会触发挂起的请求；但恢复 ENABLE 后紧跟的取消点会）。
3. `oldstate`/`oldtype` 出参建议保存并在临界区结束时**恢复原值**（而不是硬编码 ENABLE）——你可能运行在一个本来就被上游 DISABLE 的上下文里。

## 二、临界区屏蔽模式（本节的工程主菜）

```c
void update_order_book(void) {
    int oldstate;
    pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, &oldstate); /* ① 进禁区 */
    pthread_mutex_lock(&book->lock);                            /* ② 持锁 */
    book_apply(book, delta);            /* ③ 半改数据的中途死 = 结构永久残缺 */
    pthread_mutex_unlock(&book->lock);
    pthread_setcancelstate(oldstate, NULL);                     /* ④ 出禁区恢复 */
}
```

为什么必须屏蔽：延迟模式下 `pthread_mutex_lock` **不是取消点**，但 `read`/`sleep`/`pthread_testcancel` 是——若临界区内部（或未来有人加的调试输出）踩中取消点，线程死在"已锁未解"状态：

```
lock(book) ✓
  book_apply 改了一半
  printf(...)         ← 取消点！
  ✗ 线程在此被取消
  → book->lock 永远锁着（除非 cleanup 栈救场，32.5）
  → 数据结构半新半旧，其他线程读到的就是残缺账本
```

两条工程守则：

- **守则 1**：临界区（持锁段）一律 DISABLE/恢复包裹——防御"今天不是取消点、明天被加成了取消点"的演化风险。
- **守则 2**：更彻底的替代是 cleanup 栈（32.5）配对 push/pop unlock——即使被取消也能解锁。DISABLE 是"防"，cleanup 是"治"，生产代码常常双保险。

---

## 三、异步取消的三宗罪

`PTHREAD_CANCEL_ASYNCHRONOUS` 下，取消可在**任意两条指令之间**生效（实现上是收到信号立即展开）：

| 罪 | 场景 | 后果 |
|----|------|------|
| ① 持锁死 | 死在 `lock` 与 `unlock` 之间 | 其他线程永久死等；若死在 glibc 内部锁（malloc 的 arena 锁）→ 全进程 malloc 死锁 |
| ② 堆残缺 | 死在 malloc/free 的链表操作中途 | 堆元数据损坏，之后随机 crash |
| ③ 数据残缺 | 死在"改两个字段"的第一个字段后 | 不变量破坏（账本借贷不平），静默错误比崩溃更贵 |

因此异步取消的安全前提极其苛刻：**纯计算 + 不碰锁 + 不碰堆 + 不碰共享数据 + 不调任何库函数**——满足全部条件的应用场景几乎只剩"专门的数学打杂线程"。而且即便如此，异步模式下的取消路径**不保证** cleanup 栈完整执行（32.6）。

> 工程结论：**类型永远用默认 DEFERRED**；需要"算到一半能被打断"的线程，用 `pthread_testcancel`（32.4）在安全边界手动开检查点。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | HFT 主流做法是**整个系统不使用 pthread_cancel**，协作退出（原子标志 + condvar）天然没有"死亡时机"问题。若遗留代码里必须用 cancel：所有临界区按守则 1 包 DISABLE；关停顺序 = 停喂 → cancel → join → 验证 PTHREAD_CANCELED |
| HFT · 演化防御 | "今天不是取消点"是脆弱假设——glibc 版本升级会把新函数变成取消点（2.28 后 futex 系统调用全面取消化）。守则 1 的 DISABLE 包裹是对未来的一劳永逸保险 |
| 嵌入式 | RTOS 任务删除 ≈ 异步取消（无清理机会）——嵌入式经验法则直接映射到本节：硬杀只配"可丢弃"任务；有资源的任务必须给退出路径（消息队列退出命令 / 信号量握手）|

## 代码示例

见 [32.1 的 cancel_demo.c 演示 2](32.1-canceling-a-thread.md)（DISABLE 屏蔽 3 段关键工作、恢复后到取消点才死亡的完整实测）：请求挂起 → 关键段 1/3、2/3、3/3 全部完成 → ENABLE 后第一个取消点被取消。本节配套的临界区包裹模式（可编译片段）：

```c
/* shield_critsec.c — 临界区 DISABLE/恢复包裹模式 */
#include <pthread.h>

static pthread_mutex_t book_lock = PTHREAD_MUTEX_INITIALIZER;
static int book[8];

void update_book(int idx, int val)
{
    int oldstate;
    pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, &oldstate);  /* 进禁区 */
    pthread_mutex_lock(&book_lock);
    book[idx] = val;                 /* 半改数据的中途死 = 结构永久残缺 */
    pthread_mutex_unlock(&book_lock);
    pthread_setcancelstate(oldstate, NULL);                      /* 恢复原值 */
}
```

## 自测题

**题目 1**：线程 B 处于 DISABLE 状态时收到 cancel 请求，随后 B 恢复 ENABLE 并立刻进入一个长计算循环（无任何取消点）。B 会被取消吗？

<details>
<summary>参考答案</summary>

不会立刻被取消。恢复 ENABLE 后请求仍处于挂起状态，要等 B 走到**取消点**（标准取消点函数或 pthread_testcancel）才执行。长计算循环里没有取消点 → 请求一直挂着，B 继续跑。这正是"挂起不丢失、但也不提前生效"的语义。

</details>

**题目 2**：为什么 `pthread_setcancelstate` 恢复时推荐恢复 `oldstate` 而不是硬编码 `PTHREAD_CANCEL_ENABLE`？

<details>
<summary>参考答案</summary>

当前代码可能运行在一个本来就被上游调用者 DISABLE 的上下文里（比如上层函数把整段逻辑设为不可取消）。硬编码 ENABLE 会把上游的保护悄悄拆掉——恢复操作必须对称：谁改的谁恢复，恢复成进来时的值。

</details>

**题目 3**：异步取消模式下，一个线程正在 `malloc` 内部（持有 arena 锁）被取消，会发生什么？

<details>
<summary>参考答案</summary>

线程死在 malloc 内部：① arena 锁不会被释放，其他任何线程再调 malloc/free 都死锁在同一个 arena 上——全进程堆瘫痪；② 堆的空闲链表/tcache 可能正处于半更新状态，即使锁能释放，堆元数据也已损坏。这就是异步取消三宗罪里最致命的"内部锁死"。

</details>
