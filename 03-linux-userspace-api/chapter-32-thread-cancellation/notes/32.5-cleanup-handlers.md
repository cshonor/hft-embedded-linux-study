# 32.5 清理处理器

## 本节讲什么

1. **cleanup 栈的 API 与宏本质**——`pthread_cleanup_push/pop` 是**宏**不是函数，必须同词法块配对；LIFO 栈在取消/`pthread_exit` 时自动展开。
2. **三种触发路径与一个陷阱**——cancel ✓、`pthread_exit` ✓、`pop(非0)` ✓；**`return` 不触发**（本章第一大坑）。
3. **标准范式**——"持锁睡眠"场景（condvar wait 被取消时解锁）与 push/pop 对的写法。

---

## 一、API 与宏本质

```c
#include <pthread.h>

void pthread_cleanup_push(void (*routine)(void *), void *arg);
void pthread_cleanup_pop(int execute);
```

**它们是宏**（`{` 和 `}` 的一部分！）：

```c
/* 展开近似 */
#define pthread_cleanup_push(r, arg) \
    do { __pthread_cleanup_class __clframe(r, arg); {
#define pthread_cleanup_pop(execute) \
    } __clframe.__setdoit(execute); } while (0)
```

推论（每条都有人踩）：

| # | 规则 | 原因 |
|---|------|------|
| 1 | push/pop 必须**同词法块**配对 | push 带 `{`，pop 带 `}`——少一个编译器报"花括号不匹配"式的奇怪错误 |
| 2 | push 后**必须** pop 才能 return | 词法块没闭合，return 语法上就不合法（这反而是保护：强迫你走完配对）|
| 3 | 不能跨函数/不能 goto 跳出块 | 同上 |
| 4 | pop(0) 只弹出、pop(非0) 弹出**并执行** | 常规收尾路径手动触发 |

---

## 二、三种触发 + 一个陷阱

| 退出路径 | cleanup 栈 |
|----------|-----------|
| `pthread_cancel`（到取消点执行） | **自动展开**（LIFO：最后 push 的最先执行）|
| `pthread_exit(v)` | **自动展开** |
| `pthread_cleanup_pop(非0)` | 手动执行该处理器的 |
| `return v` | **不展开！** |

`return` 不展开是 POSIX 的设计决定（return = 正常路径，应当用 pop 显式收尾），不是 bug——但它是**本章第一大坑**：

```c
void *worker(void *arg) {
    pthread_cleanup_push(unlock_helper, &m);       /* push */
    pthread_mutex_lock(&m);
    ...
    if (error)
        return NULL;        /* ✗ 编译都过不了：块没闭合 —— 宏设计恰好挡住这一坑 */
    pthread_cleanup_pop(1); /* ✓ 正确：pop(1) = 弹出并执行 unlock */
    return NULL;
}
```

宏的 `{}` 结构强迫 return 前必须先 pop——**词法上杜绝了"忘记收尾"**。这是 pthreads API 设计里少有的"用宏的丑换纪律"的范例。

> 顺带：cleanup 展开顺序 LIFO（栈）；处理器里还可以继续 push/pop（嵌套清理）；处理器内部如果被再次取消……理论可能、实际极难，别依赖。

---

## 三、标准范式：持锁睡眠

**本章最重要的应用场景**：线程持锁睡在 condvar 上，被取消时必须解锁——否则其他等锁的线程全部陪葬。

```c
/* 反面：裸 wait */
pthread_mutex_lock(&m);
while (!ready)
    pthread_cond_wait(&cond, &m);   /* 取消点！死在这 → m 永远锁着 */
...
pthread_mutex_unlock(&m);

/* 正面：cleanup 托底 */
static void unlock_mutex(void *p) {
    pthread_mutex_unlock((pthread_mutex_t *)p);
    log("cancelled: mutex unlocked by cleanup");
}

pthread_mutex_lock(&m);
pthread_cleanup_push(unlock_mutex, &m);     /* 挂保险 */
while (!ready)
    pthread_cond_wait(&cond, &m);           /* 被取消 → cleanup 先解锁 */
...
pthread_cleanup_pop(0);                     /* 正常路径：只摘保险不执行 */
pthread_mutex_unlock(&m);                   /* 正常解锁 */
```

范式要点：

1. push 在 **lock 之后**（锁还没拿到就挂保险，取消时 unlock 一把没锁的锁 = UB）；
2. 正常路径 `pop(0)` + 手动 unlock；取消路径 cleanup 自动 unlock——**两条路径一个保险**；
3. 处理器参数只能带一个 `void*`——要清理多个资源就传结构体指针，或者 push 多层（LIFO 保证逆序释放，与获取顺序相反，天然正确）。

三层对比（资源保护的完整工具箱）：

| 手段 | 时机 | 适用 |
|------|------|------|
| DISABLE 取消（32.2）| 事前预防 | 临界区短、可整体延迟 |
| cleanup 栈（本节）| 事后收尸 | 持锁睡眠、多资源逆序释放 |
| 协作退出标志 | 根本不让取消发生 | 新代码首选，HFT 标准 |

---

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | HFT 线程池关停若必须支持 cancel：每个"持锁 + 可能睡"的 wait 点一律 cleanup 托底（本节范式）+ 32.2 的 DISABLE 双保险。审计方法：grep `pthread_cond_wait` / `pthread_mutex_lock`，检查同函数内是否有配对的 cleanup_push |
| HFT · C++ 视角 | C++ 的 RAII 析构在线程被取消时**同样执行**（取消展开走 C++ 的 unwind）——C++ 项目用 RAII 锁（std::unique_lock）自动获得本节语义，这是 C++ 线程代码不怕 cancel 的原因 |
| 嵌入式 | RTOS 任务删除无 cleanup 栈 → 嵌入式的等价纪律：任务入口先注册"清理回调表"，删除前由删除方逐项调用（或任务自己在消息循环里收 CLEANUP 命令自清）——LIFO 逆序释放的纪律不变 |

## 代码示例

`cleanup_demo.c`（gcc -O2 -Wall -Wextra 零告警编译通过）：

```c
/* cleanup_demo.c — Ch32.5：LIFO 逆序、cond_wait 取消解锁、return 不展开
 * 编译：gcc -O2 -Wall -Wextra -o cleanup_demo cleanup_demo.c -pthread
 */
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

/* ---------- 演示 1：LIFO 逆序 + 三种触发路径 ---------- */
static void handler(void *arg) {
    printf("  cleanup: %s\n", (char *)arg);
}

static void *path_exit(void *a){(void)a;
    pthread_cleanup_push(handler, (void*)"A-最先push");
    pthread_cleanup_push(handler, (void*)"B-其次push");
    pthread_cleanup_push(handler, (void*)"C-最后push");
    /* 栈：C 顶。pthread_exit 自动展开 → C、B、A 逆序 */
    pthread_exit((void *)1);
    pthread_cleanup_pop(0);        /* 消除 noreturn 警告（不可达）*/
    pthread_cleanup_pop(0);
    pthread_cleanup_pop(0);
}

static void *path_pop(void *a){(void)a;
    pthread_cleanup_push(handler, (void*)"X-唯一push");
    pthread_cleanup_pop(1);        /* pop(1)：手动执行 → "X-唯一push" 打印 */
    printf("  [path_pop] pop(1) 手动触发后，线程正常 return\n");
    return NULL;                   /* return 不再展开（栈已空）*/
}

static void demo_order(void){
    pthread_t t1, t2;
    void *r;
    printf("  --- pthread_exit 路径（自动 LIFO 展开）---\n");
    pthread_create(&t1, NULL, path_exit, NULL);
    pthread_join(t1, &r);
    printf("  --- pop(1) 手动路径 ---\n");
    pthread_create(&t2, NULL, path_pop, NULL);
    pthread_join(t2, &r);
    (void)r;
}

/* ---------- 演示 2：cond_wait 被取消 → cleanup 解锁救场 ---------- */
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  cv = PTHREAD_COND_INITIALIZER;
static int ready;

static void unlock_mutex(void *p) {
    pthread_mutex_unlock((pthread_mutex_t *)p);
    printf("  [cleanup] 被取消了：cleanup 已解锁 mutex\n");
}

static void *waiter(void *a){(void)a;
    pthread_mutex_lock(&m);
    pthread_cleanup_push(unlock_mutex, &m);    /* 挂保险 */
    while (!ready)
        pthread_cond_wait(&cv, &m);            /* 取消点：死在这 */
    pthread_cleanup_pop(0);                    /* 正常路径：摘保险 */
    pthread_mutex_unlock(&m);
    return NULL;}

static void demo_cancel_wait(void){
    pthread_t t;
    void *res;
    pthread_create(&t, NULL, waiter, NULL);
    usleep(100000);
    printf("  [main] 发出取消（waiter 正持锁睡在 condvar 上）\n");
    pthread_cancel(t);
    pthread_join(t, &res);
    printf("  [main] join: %s\n",
           res == PTHREAD_CANCELED ? "PTHREAD_CANCELED" : "正常?");

    /* 验证锁真的被 cleanup 释放了：主线程现在必须能拿到它 */
    struct timespec ts = {0, 50*1000*1000};
    printf("  [main] 尝试拿锁（若 cleanup 没解锁这里就死锁）...");
    fflush(stdout);
    pthread_mutex_lock(&m);
    printf("成功：锁是自由的 ✓\n");
    pthread_mutex_unlock(&m);
    nanosleep(&ts, NULL);
}

int main(void){
    printf("==== demo1：触发路径与 LIFO 顺序 ====\n");
    demo_order();
    printf("==== demo2：cond_wait 取消 + cleanup 解锁 ====\n");
    demo_cancel_wait();
    return 0;
}
```

实测输出（WSL2 / 12 核）：

```text
==== demo1：触发路径与 LIFO 顺序 ====
  --- pthread_exit 路径（自动 LIFO 展开）---
  cleanup: C-最后push
  cleanup: B-其次push
  cleanup: A-最先push
  --- pop(1) 手动路径 ---
  cleanup: X-唯一push
  [path_pop] pop(1) 手动触发后，线程正常 return
==== demo2：cond_wait 取消 + cleanup 解锁 ====
  [main] 发出取消（waiter 正持锁睡在 condvar 上）
  [cleanup] 被取消了：cleanup 已解锁 mutex
  [main] join: PTHREAD_CANCELED
  [main] 尝试拿锁（若 cleanup 没解锁这里就死锁）...成功：锁是自由的 ✓
```

三点解读：

1. demo1：`pthread_exit` 自动展开且**严格 LIFO**（C→B→A，与 push 顺序相反）；`pop(1)` 手动执行该层处理器。正常 `return` 路径栈已空——不展开。
2. demo2：waiter 死在 `pthread_cond_wait`（取消点），cleanup 处理器把 mutex 解开——主线程随后 `pthread_mutex_lock(&m)` 成功，证明锁确实被"死后收尸"释放。没有 cleanup 的版本，这一步就是永久死锁。
3. `pthread_exit` 版本里 `pop(0)×3` 不可达（exit 已发生），只用来平衡宏的花括号——`__attribute__((noreturn))` 场景下的标准写法。

## 自测题

**题目 1**：`pthread_cleanup_push` 之后直接 `return`，会发生什么？

<details>
<summary>参考答案</summary>

编译失败。push/pop 是宏：push 展开含 `{`，pop 展开含 `}`——不 pop 就 return，词法块没闭合，编译器报花括号/语法错误。这个"丑"是故意的：强迫每个 return 路径都显式经过 pop（决定执行与否），从语言层面杜绝"忘记收尾"。C++ 的 RAII 析构自动覆盖所有 return 路径，是更优雅的等价物。

</details>

**题目 2**：线程 push 了 A、B、C 三个处理器后被取消。执行顺序？如果 A 是 unlock、B 是 free、C 是 close，这个顺序为什么是正确的？

<details>
<summary>参考答案</summary>

LIFO：C→B→A。正确性在于资源获取顺序通常是 A（lock）→ B（malloc）→ C（fd），释放必须逆序：先关 fd（不再使用内存）、再 free（脱离了临界区语义上的数据）、最后 unlock。栈结构天然编码了"逆序释放"，与 C 语言 goto cleanup 惯用法、C++ 析构顺序完全一致。

</details>

**题目 3**：写出"持锁睡 condvar + 可被取消"的最小安全骨架，并指出保险挂在哪一步。

<details>
<summary>参考答案</summary>

```c
pthread_mutex_lock(&m);
pthread_cleanup_push(unlock_mutex, &m);   /* 保险：lock 成功之后立刻挂 */
while (!ready)
    pthread_cond_wait(&cv, &m);           /* 取消点 */
pthread_cleanup_pop(0);                   /* 正常路径摘保险 */
pthread_mutex_unlock(&m);
```
保险必须挂在 lock **之后**（拿到锁才有"解锁"可托底；lock 之前挂，取消时 unlock 一把未持有的锁 = UB）。while 谓词、pop(0)、手动 unlock 与 30.2 的条件变量范式完全同构——cleanup 只是给"被取消"这条异常路径加了出口。

</details>
