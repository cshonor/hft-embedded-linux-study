# 32.7 Summary

> 本章：[TLPI 第 32 章 — Thread Cancellation](./README.md)

## 本章回顾

### 取消 API 速查

| 函数 | 功能 |
|------|------|
| `pthread_cancel(thread)` | 请求取消线程 |
| `pthread_setcancelstate(state, *old)` | ENABLE / DISABLE |
| `pthread_setcanceltype(type, *old)` | DEFERRED / ASYNCHRONOUS |
| `pthread_testcancel()` | 显式取消点 |
| `pthread_cleanup_push(routine, arg)` | 注册清理函数 |
| `pthread_cleanup_pop(execute)` | 弹出并可选执行清理函数 |

### 取消流程

```
pthread_cancel(thread)
    │
    ▼
线程收到取消请求（挂起或立即）
    │
    ├─ DISABLE → 请求挂起，等恢复后处理
    ├─ DEFERRED → 到取消点执行
    └─ ASYNCHRONOUS → 任意时刻执行
    │
    ▼
执行清理函数栈（LIFO 顺序）
    │
    ▼
pthread_exit(PTHREAD_CANCELED)
```

### 清理函数

```c
pthread_cleanup_push(cleanup_func, arg);
/* ... 代码 ... */
pthread_cleanup_pop(0);  /* 0=不执行，非0=执行 */
```

| 触发清理函数的情况 | 说明 |
|-------------------|------|
| `pthread_cancel()` 成功 | DEFERRED 在取消点，ASYNCHRONOUS 任意时刻 |
| `pthread_exit()` | 线程主动退出 |
| `pthread_cleanup_pop(非0)` | 手动执行 |

**不触发**：`return` 不会执行清理函数（这是常见陷阱）

### 取消状态/类型组合

| State | Type | 行为 |
|-------|------|------|
| ENABLE | DEFERRED | 到取消点才取消（最安全，默认） |
| ENABLE | ASYNCHRONOUS | 任意时刻取消（危险） |
| DISABLE | 任意 | 请求挂起，不取消 |

## HFT / 嵌入式关联

- **HFT 不用 pthread_cancel**：用协作式退出（atomic flag + 循环检查）
- **嵌入式**：RTOS 用任务删除 + cleanup callback
- **清理函数**：用于释放锁/内存，但 return 不触发，必须用 pthread_exit

## 代码自测

<details>
<summary>1. 为什么 return 不会触发清理函数？</summary>

POSIX 规定 `pthread_cleanup_push/pop` 必须在同一函数中成对出现（宏实现）。`return` 跳过了 `pthread_cleanup_pop`，清理函数不被执行。只有 `pthread_exit()` 或被取消时才触发。这是一个常见的内存/锁泄漏陷阱——应确保退出路径经过 `pthread_exit` 或显式 `pop(1)`。
</details>

<details>
<summary>2. 异步取消为什么几乎总是危险的？</summary>

1. 可能在持有 mutex 时被取消 → 死锁
2. 可能在 malloc 中间被取消 → 堆损坏
3. 可能在修改数据结构中间被取消 → 数据不一致
4. 清理函数本身可能也需要取消点，但异步取消下不安全
5. 任何库函数内部状态可能不一致
</details>
