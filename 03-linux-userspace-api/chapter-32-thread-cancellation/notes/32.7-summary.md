## 二、完整生命周期（五步图）

```
  A 线程                                B 线程（目标）
─────────                              ─────────────────────────────
pthread_cancel(B)
  │ glibc: 置标志 + tgkill(SIGCANCEL)
  └─①请求投递（异步，立即返回）──────▶ [挂起的请求 pending]
                                                  │
                              state==DISABLE ──▶ 继续挂起（32.2）
                                                  │ ENABLE+DEFERRED
                              ② 到达取消点（标准取消点 / testcancel / ③ASYNC 任意边界）
                                                  │
                              ④ 展开清理栈（LIFO，32.5）+ TSD 析构（31.3）
                                                  │
                              ⑤ pthread_exit(PTHREAD_CANCELED)
pthread_join(B, &res)
  └─ res == PTHREAD_CANCELED ──────▶ 死亡确认，资源回收完毕
```

状态×类型行为表：

| State | Type | 行为 |
|-------|------|------|
| ENABLE | DEFERRED | 到取消点执行（默认，唯一工程推荐）|
| ENABLE | ASYNCHRONOUS | 任意指令边界执行（危险，禁用）|
| DISABLE | 任意 | 挂起等待（临界区保护）|

## 三、铁律

1. **cancel 是请求不是死刑**：join + `PTHREAD_CANCELED` 才是死亡证明。
2. 临界区（持锁段）一律 DISABLE/恢复包裹——**恢复 oldstate，不硬编码**。
3. 类型永远 DEFERRED；ASYNC 只配"纯计算零依赖"线程，生产代码出场率应为零。
4. 纯计算循环必加 `pthread_testcancel`，放块间安全边界，密度=取消延迟预算。
5. cleanup push/pop 是宏：同块配对、push 在 lock 后、正常路径 pop(0)+手动收尾。
6. **return 不展开 cleanup**——宏的 `{}` 会逼你先 pop（这是保护，不是障碍）。
7. 持锁睡 condvar 必挂 cleanup 保险（32.5 范式）。
8. 新代码优先协作退出（原子标志+condvar），cancel 只做遗留/兜底。
9. 关停 join 设超时（`pthread_tryjoin_np`/timedjoin_np 探测），别让关停流程挂死。
10. 杀不死排查五连：无取消点？忘了 ENABLE？没 join？SIGCANCEL 被屏蔽？忙等伪装成阻塞？

## 四、HFT 决策表（本章收口）

| 需求 | 方案 | 出处 |
|------|------|------|
| 优雅停止策略线程 | 协作退出：原子 running + condvar 唤醒 + 线程在安全边界自查 | HFT 标准 |
| 遗留库必须 cancel | 临界区 DISABLE 包裹 + cleanup 托底 + join 验证 | 32.2/32.5 |
| 无界计算超时 | **进程**边界：fork + kill + waitpid（硬回收）| 32.6 |
| 关停兜底 | join 超时 → 升级 SIGTERM/SIGKILL | 32.4 |
| 嵌入式任务删除 | 只删可丢弃任务；有资源任务给退出命令自杀 | 32.2/32.6 |

## 自测题

**题目 1**：复述取消的完整生命周期五步，并指出哪一步可能"永远不发生"。

<details>
<summary>参考答案</summary>

①cancel 投递（tgkill SIGCANCEL）→ ②到达取消点（或 ASYNC 任意边界）→ ③展开 cleanup 栈 + TSD 析构 → ④pthread_exit(PTHREAD_CANCELED) → ⑤join 回收并确认。可能永远不发生的：②（无取消点的循环，32.3/32.4）以及 DISABLE 忘记恢复导致的挂起（32.2）——两者症状相同（join 挂死），排查方向不同。

</details>

**题目 2**：同事的线程池关停代码：cancel 全部 worker → join 全部 → 关闭队列。偶发关停挂死。给出三个候选原因和对应修复。

<details>
<summary>参考答案</summary>

① worker 主循环是纯计算/自旋（无取消点）→ 挂起的请求永不执行：加 testcancel 或改协作退出；② worker 在临界区 DISABLE 后某路径忘了恢复 → 请求一直挂起：审查所有 return 路径，用 oldstate 恢复模式；③ worker 死在持锁状态且无 cleanup → 其他 worker 等 lock 陪葬，join 挂死：持锁睡眠点挂 cleanup 保险（32.5 范式）。另外兜底：join 全部改 timedjoin/tryjoin + 超时升级进程级信号。

</details>

**题目 3**：为什么说"glibc 2.28 的取消机制改革"反而加强了 DISABLE 包裹的必要性？

<details>
<summary>参考答案</summary>

改革把取消检查从"函数清单"扩展到"系统调用包装层"：过去不是取消点的阻塞路径（各种 futex 睡眠）现在也可能响应取消。清单随版本变大的方向不会逆转——任何"这个函数现在不是取消点"的假设都是脆弱的。DISABLE 包裹使代码不依赖清单：无论未来哪行代码变成取消点，临界区内部都免疫取消。一劳永逸 > 逐版本审计。

</details>
