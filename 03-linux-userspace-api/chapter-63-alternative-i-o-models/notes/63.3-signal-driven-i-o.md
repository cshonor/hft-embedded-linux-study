## 本节讲什么

信号驱动 I/O 的核心思想是：**进程不主动问内核"fd 好了没"，而是让内核在 fd 就绪时
主动给它发一个信号**。本节回答四层问题：

1. **接口层**：要建立这套通知，用户态需要几步 `fcntl()`？每步在内核里改了什么字段？
2. **机制层**：内核用什么数据结构记住"该给谁发、发哪个信号"？
3. **⭐ 语义层（本节核心）**：内核真的每来一个包就发一次 `SIGIO` 吗？—— 答案是**否**，
   有两道被几乎所有中文资料忽略的**去重闸门**
4. **工程层**：为什么它最终被 epoll 取代？在 HFT / 嵌入式里还有没有残余价值？

> 🔗 **本篇只讲信号驱动 I/O 的 API 与内核实现**；
> epoll 主场在 [63.4 epoll API](./63.4-the-epoll-api.md)；
> `io_uring` 作为现代替代方案主场在 [12.5 现代网络](../../../12.5-modern-networking/)
> （该模块 io_uring 命中 121 处）。

## 要点

### 1. 五步建立流程 —— 以及每一步在内核里改了什么

教科书给的建立步骤是 5 步，但通常不解释每步的**内核副作用**。补齐这一层：

| 步骤 | 用户态调用 | 内核落点（v6.6） | 改了什么 |
|------|-----------|-----------------|---------|
| ① 设属主 | `fcntl(fd, F_SETOWN, getpid())` | `f_setown()` `fcntl.c:115` → `__f_setown` `:107` → `f_modown` `:88` | `file->f_owner.pid` / `.pid_type` / `.uid` / `.euid` |
| ② 设非阻塞 | `fcntl(fd, F_SETFL, O_NONBLOCK)` | `setfl()` `fcntl.c:37` | `file->f_flags |= O_NONBLOCK` |
| ③ 开异步通知 | `fcntl(fd, F_SETFL, O_ASYNC)` | `setfl()` `fcntl.c:37` → `filp->f_op->fasync()` `:74` | **不是直接置位**，见下节 |
| ④ 装 handler | `sigaction(SIGIO, ...)` | 进程 `sighand` | 注册信号处理函数 |
| ⑤ （可选）换信号 | `fcntl(fd, F_SETSIG, signum)` | `do_fcntl` `fcntl.c:393` | `file->f_owner.signum` |

**步骤 ② 不是可选项，而是让通知机制正常工作的前提** —— 原因在第 6 节「两道闸门」里解释，
那是本节最反直觉的一块。

> ⚠️ **顺序有讲究**：必须先 `F_SETOWN` 再开 `O_ASYNC`。
> 因为 `O_ASYNC` 一开，设备/协议栈**立刻**就可能发信号；若此时 `f_owner.pid` 还是 NULL，
> `send_sigio()` 会在 `fcntl.c:783` 的 `if (!pid) goto out_unlock_fown;` 直接静默返回 ——
> 通知被丢掉，且**没有任何错误提示**。

### 2. ⭐ `O_ASYNC` 在内核头文件里根本不存在

这是本节第一个"凭记忆必错"的点。去内核 uapi 里找 `O_ASYNC`，是找不到的：

```c
/* include/uapi/asm-generic/fcntl.h:44-45 */
#ifndef FASYNC
#define FASYNC		00020000	/* fcntl, for BSD compatibility */
#endif
```

v6.6 的 `include/uapi/asm-generic/fcntl.h` 里 **只有 `FASYNC`，没有 `O_ASYNC`**。
x86 也没有自己的覆盖版本（`arch/x86/include/uapi/asm/fcntl.h` 在该版本不存在）。

那我们代码里写的 `O_ASYNC` 从哪来？**glibc 自己定义的**（`bits/fcntl-linux.h`）：

| 名字 | 来源 | 值（八进制） | 值（十进制/十六进制） |
|------|------|-------------|---------------------|
| `FASYNC` | 内核 uapi `fcntl.h:45` | `00020000` | 8192 / `0x2000` |
| `O_ASYNC` | **glibc** `bits/fcntl-linux.h` | `020000` | 8192 / `0x2000` |

**两者数值完全相同**（八进制前导零不影响数值），所以它们是同义的：
`O_ASYNC` 是 POSIX 叫法，`FASYNC` 是 BSD 遗留叫法，内核只认后者。

> 📌 实践含义：**不要指望内核头文件给你 `O_ASYNC`**。
> 写内核代码（或做 `F_SETFL` 的位运算推理）时用 `FASYNC`；写用户态程序用 `O_ASYNC` 没问题，
> 但要明白它是 libc 的礼物。

#### `setfl()` 里 FASYNC 的诡异处理

更值得注意的是 `setfl()` 怎么处理这个位。看 `fs/fcntl.c:35` 的掩码：

```c
/* fs/fcntl.c:35 */
#define SETFL_MASK (O_APPEND | O_NONBLOCK | O_NDELAY | O_DIRECT | O_NOATIME)
```

**`FASYNC` 不在 `SETFL_MASK` 里**。所以 `:81` 那行赋值根本不会把 FASYNC 写进 `f_flags`：

```c
/* fs/fcntl.c:71-81 */
	/*
	 * ->fasync() is responsible for setting the FASYNC bit.
	 */
	if (((arg ^ filp->f_flags) & FASYNC) && filp->f_op->fasync) {
		error = filp->f_op->fasync(fd, filp, (arg & FASYNC) != 0);
		if (error < 0)
			goto out;
		if (error > 0)
			error = 0;
	}
	spin_lock(&filp->f_lock);
	filp->f_flags = (arg & SETFL_MASK) | (filp->f_flags & ~SETFL_MASK);
	filp->f_iocb_flags = iocb_flags(filp);
	spin_unlock(&filp->f_lock);
```

FASYNC 位是由**驱动/协议栈的 `->fasync()` 回调**设置的，最终落到
`fasync_insert_entry()` 的这一行：

```c
/* fs/fcntl.c:934 —— fasync_insert_entry() 末尾 */
	filp->f_flags |= FASYNC;
```

**为什么要这么绕？** 因为「开启异步通知」不是改一个标志位就完事 —— 它要**分配一个
`struct fasync_struct` 并挂进队列**。这个操作可能失败（`-ENOMEM`），
如果先置位再分配，失败后标志位就撒谎了。所以内核让回调来负责置位，
**保证 `FASYNC` 位与"这个 filp 确实在 fasync 队列里"严格等价**。

源码里那句注释就是铁律（`fs/fcntl.c:908-910`）：

```c
/*
 * NOTE! It is very important that the FASYNC flag always
 * match the state "is the filp on a fasync list".
 */
```

> 🔍 **由此得出一个可观测的结论**：
> 若 `f_op->fasync` 为 NULL（该设备不支持异步通知），
> `setfl()` 里 `filp->f_op->fasync` 的判空会让整个 if 跳过 ——
> **`fcntl(fd, F_SETFL, O_ASYNC)` 返回 0（成功），但什么都没发生**。
> 这是信号驱动 I/O 最隐蔽的失败模式：**开了但没真开，且无报错**。

### 3. `F_SETOWN` / `F_SETOWN_EX` / `F_SETSIG` 三个命令

#### 3.1 `F_SETOWN`（cmd = 8）

```c
/* fs/fcntl.c:115 */
int f_setown(struct file *filp, int who, int force)
{
	enum pid_type type;
	struct pid *pid = NULL;
	int ret = 0;

	type = PIDTYPE_TGID;
	if (who < 0) {
		/* avoid overflow below */
		if (who == INT_MIN)
			return -EINVAL;

		type = PIDTYPE_PGID;
		who = -who;
	}

	rcu_read_lock();
	if (who) {
		pid = find_vpid(who);
		if (!pid)
			ret = -ESRCH;
	}

	if (!ret)
		__f_setown(filp, pid, type, force);
	rcu_read_unlock();

	return ret;
}
```

三个要点：

1. **`who > 0` → 发给单个线程组（TGID）**；**`who < 0` → 发给进程组 PGID**（取绝对值）
2. **`who == 0` → 撤销属主**（`pid = NULL`，此后 `send_sigio` 静默返回）
3. 🔒 **信号量语义是"覆盖"不是"追加"** —— 一个 fd 只有一个属主。
   与 epoll 不同（一个 epoll fd 可以监听 N 个 fd），**信号驱动 I/O 天然是 1:1 的**

#### 3.2 `F_SETOWN_EX`（cmd = 15）—— 补上线程粒度

`F_SETOWN` 只能发到「线程组」或「进程组」，**发不到单个线程**。
`F_SETOWN_EX` 传一个结构体解决：

```c
/* include/uapi/asm-generic/fcntl.h:151-158 */
#define F_OWNER_TID	0
#define F_OWNER_PID	1
#define F_OWNER_PGRP	2

struct f_owner_ex {
	int	type;
	__kernel_pid_t	pid;
};
```

内核侧的分派（`fs/fcntl.c:181-193`）：

| `owner.type` | 内核 `enum pid_type` | 含义 |
|-------------|---------------------|------|
| `F_OWNER_TID = 0` | `PIDTYPE_PID` | **单个线程**（`F_SETOWN` 做不到） |
| `F_OWNER_PID = 1` | `PIDTYPE_TGID` | 线程组（等价于 `F_SETOWN` 正值） |
| `F_OWNER_PGRP = 2` | `PIDTYPE_PGID` | 进程组（等价于 `F_SETOWN` 负值） |

> ⚠️ **注意 `F_OWNER_TID` 与 `F_OWNER_PID` 的编号容易记反**：
> 直觉上 "PID" 更像单线程，但 `F_OWNER_PID` 是**线程组**（1），
> 单个线程是 `F_OWNER_TID`（0）。

#### 3.3 `F_SETSIG`（cmd = 10）—— 把 SIGIO 换成排队信号

```c
/* fs/fcntl.c:390-397 —— do_fcntl() 内 */
	case F_GETSIG:
		err = filp->f_owner.signum;
		break;
	case F_SETSIG:
		/* arg == 0 restores default behaviour. */
		if (!valid_signal(argi)) {
			break;
		}
		err = 0;
		filp->f_owner.signum = argi;
		break;
```

- `F_SETSIG 0` = **恢复默认**（发 `SIGIO`）
- 传**实时信号**（`SIGRTMIN` ~ `SIGRTMAX`）才有意义：实时信号**会排队**

关于错误处理的一个细节：`do_fcntl()` 的 `err` 初值是 **`-EINVAL`**（`fs/fcntl.c:352`）：

```c
static long do_fcntl(int fd, unsigned int cmd, unsigned long arg,
		struct file *filp)
{
	...
	long err = -EINVAL;
```

所以 `F_SETSIG` 传非法信号时那个 `break` 并不是"静默成功"——
它跳出 switch 后 `return err`，拿到的正是初值 **`-EINVAL`**。
（这一点很容易看错：如果默认以为 `err` 初值是 0，就会得出"无效信号被静默忽略"的错误结论。）

### 4. 内核怎么记住"发给谁、发什么" —— 两个结构体

```
   struct file                         struct socket
   ┌──────────────────────┐            ┌──────────────────────┐
   │ f_owner: fown_struct │            │ wq: struct socket_wq │
   │  ├─ lock   (rwlock)  │            │  ├─ wait (wq_head)   │
   │  ├─ pid    ──────────┼──► struct pid
   │  ├─ pid_type         │            │  ├─ fasync_list ─────┼──┐
   │  ├─ uid / euid       │            │  ├─ flags  ★闸门位    │  │
   │  └─ signum  (F_SETSIG)│           │  └─ rcu              │  │
   │                      │            └──────────────────────┘  │
   │ f_flags: FASYNC 位   │                                      │
   │ f_op->fasync()       │            struct fasync_struct  ◄───┘
   └──────────────────────┘             ├─ fa_lock  (rwlock)
                                        ├─ magic  (FASYNC_MAGIC)
                                        ├─ fa_fd   ★ si_fd 的来源
                                        ├─ fa_next ──► 下一个（单链表）
                                        ├─ fa_file ──► 回指 struct file
                                        └─ fa_rcu  (RCU 延迟释放)
```

#### `struct fown_struct` —— 记录"发给谁、发什么信号"

```c
/* include/linux/fs.h（v6.6） */
struct fown_struct {
	rwlock_t lock;          /* protects pid, uid, euid fields */
	struct pid *pid;	/* pid or -pgrp where SIGIO should be sent */
	enum pid_type pid_type;	/* Kind of process group SIGIO should be sent to */
	kuid_t uid, euid;	/* uid/euid of process setting the owner */
	int signum;		/* posix.1b rt signal to be delivered on IO */
};
```

> ⭐ **`struct fown_struct` 里没有 `fd` 字段**。
> 直觉上"设了属主就该记住是哪个 fd"，但内核**不在这里存 fd** ——
> fd 记在 `fasync_struct.fa_fd` 里（见下）。
> 实测 v4.19 / v5.10 / v5.15 / v5.16 / v5.17 / v6.6 六个版本的
> `struct fown_struct` **全部不含 fd 字段**，这不是某个版本的变化，是一直如此。

#### `struct fasync_struct` —— 记录"这个 fd 在通知队列里"

```c
/* include/linux/fs.h（v6.6） */
struct fasync_struct {
	rwlock_t		fa_lock;
	int			magic;
	int			fa_fd;
	struct fasync_struct	*fa_next; /* singly linked list */
	struct file		*fa_file;
	struct rcu_head		fa_rcu;
};
```

注意 `fa_next` 是**单链表**而不是 epoll 的红黑树 —— 每个设备/套接字维护自己的
fasync 队列，**查找是 O(n) 线性扫描**。这是信号驱动 I/O 扩展性差的**结构性原因**之一
（对比 epoll 的 `rb_root_cached` 是 O(log n)）。

`magic` 字段用于校验（`FASYNC_MAGIC`），`kill_fasync_rcu()` 里会检查：

```c
/* fs/fcntl.c:993-997 */
		if (fa->magic != FASYNC_MAGIC) {
			printk(KERN_ERR "kill_fasync: bad magic number in "
			       "fasync_struct!\n");
			return;
		}
```

#### `struct socket_wq` —— socket 侧的通知总控

```c
/* include/linux/net.h（v6.6） */
struct socket_wq {
	/* Note: wait MUST be first field of socket_wq */
	wait_queue_head_t	wait;
	struct fasync_struct	*fasync_list;
	unsigned long		flags; /* %SOCKWQ_ASYNC_NOSPACE, etc */
	struct rcu_head		rcu;
} ____cacheline_aligned_in_smp;
```

`flags` 就是第 6 节那两道闸门的位置。它历史上不在 `socket_wq` 里，
源码注释交代了迁移动机（`include/linux/net.h:35-37`）：

```c
/* Historically, SOCKWQ_ASYNC_NOSPACE & SOCKWQ_ASYNC_WAITDATA were located
 * in sock->flags, but moved into sk->sk_wq->flags to be RCU protected.
 * Eventually all flags will be in sk->sk_wq->flags.
 */
```

> 📌 迁移到 `sk_wq->flags` 的目的是**让它能被 RCU 保护**（`sk_wq` 本身是 RCU 指针
> `rcu_dereference(sk->sk_wq)`），这样读侧不用持 `sk` 锁就能安全读闸门位。

### 5. 注册链路：从 `fcntl(O_ASYNC)` 到挂进队列

socket 的 `->fasync()` 回调是 `sock_fasync()`：

```c
/* net/socket.c */
static int sock_fasync(int fd, struct file *filp, int on)
{
	struct socket *sock = filp->private_data;
	struct sock *sk = sock->sk;
	struct socket_wq *wq = &sock->wq;

	if (sk == NULL)
		return -EINVAL;

	lock_sock(sk);
	fasync_helper(fd, filp, on, &wq->fasync_list);

	if (!wq->fasync_list)
		sock_reset_flag(sk, SOCK_FASYNC);
	else
		sock_set_flag(sk, SOCK_FASYNC);

	release_sock(sk);
	return 0;
}
```

整条链路：

```
用户态 fcntl(fd, F_SETFL, O_ASYNC)
   │
   ▼
SYSCALL fcntl  ─►  do_fcntl()  ─►  F_SETFL 分支  ─►  setfl()      [fs/fcntl.c:37]
   │
   ▼  setfl() 发现 FASYNC 位翻转 → 调 filp->f_op->fasync()
sock_fasync()                                                     [net/socket.c]
   │
   ├─► fasync_helper(fd, filp, on, &wq->fasync_list)               [fs/fcntl.c:975]
   │        │
   │        ├─ on = 0 → fasync_remove_entry()                      [fs/fcntl.c:864]
   │        └─ on = 1 → fasync_add_entry() → fasync_insert_entry() [fs/fcntl.c:912]
   │                        ├─ 已存在（同 filp）→ 只更新 fa_fd，返回旧条目
   │                        └─ 不存在 → 新分配、挂链表头、filp->f_flags |= FASYNC
   │
   └─► 根据 wq->fasync_list 是否为空，设/清 SOCK_FASYNC 标志
```

`fasync_insert_entry()` 的完整实现：

```c
/* fs/fcntl.c:912 */
struct fasync_struct *fasync_insert_entry(int fd, struct file *filp, struct fasync_struct **fapp, struct fasync_struct *new)
{
        struct fasync_struct *fa, **fp;

	spin_lock(&filp->f_lock);
	spin_lock(&fasync_lock);
	for (fp = fapp; (fa = *fp) != NULL; fp = &fa->fa_next) {
		if (fa->fa_file != filp)
			continue;

		write_lock_irq(&fa->fa_lock);
		fa->fa_fd = fd;
		write_unlock_irq(&fa->fa_lock);
		goto out;
	}

	rwlock_init(&new->fa_lock);
	new->magic = FASYNC_MAGIC;
	new->fa_file = filp;
	new->fa_fd = fd;
	new->fa_next = *fapp;
	rcu_assign_pointer(*fapp, new);
	filp->f_flags |= FASYNC;

out:
	spin_unlock(&fasync_lock);
	spin_unlock(&filp->f_lock);
	return fa;
}
```

三个可观察的性质：

1. **按 `fa_file` 去重**：同一个 `struct file` 只占一个队列条目，重复调用只更新 `fa_fd`
2. **插入是头插**（`new->fa_next = *fapp`），无排序
3. **RCU 发布**（`rcu_assign_pointer`），因为发送侧 `kill_fasync_rcu()` 只持 RCU 读锁

`fasync_helper()` 的返回值语义（常被忽略）：

| 返回 | 含义 |
|------|------|
| `< 0` | 出错（如 `-ENOMEM`） |
| `0` | **什么都没改，只是更新了已有条目**（`fasync_add_entry` 的注释："did no changes"） |
| `> 0` | **真的新增/删除了条目** |

注意 `setfl()` 里 `if (error > 0) error = 0;` —— 把正数返回值**统一收敛成 0**，
因为 `fcntl()` 对用户态只该返回 0 或负 errno。

### 6. ⭐⭐ 两道去重闸门 —— 内核并不是每来一个包就发信号

这是本节**最重要、也最容易被跳过**的一块。

普遍的说法是「信号驱动 I/O 里，TCP 每个事件都会触发 SIGIO，所以信号太频繁」。
**按 v6.6 源码，这个说法不准确** —— 内核在 socket 层放了两道闸门，
会**主动抑制**大部分重复通知。

看 `sock_wake_async()`（`net/socket.c`）：

```c
/* net/socket.c */
int sock_wake_async(struct socket_wq *wq, int how, int band)
{
	if (!wq || !wq->fasync_list)
		return -1;

	switch (how) {
	case SOCK_WAKE_WAITD:
		if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
			break;
		goto call_kill;
	case SOCK_WAKE_SPACE:
		if (!test_and_clear_bit(SOCKWQ_ASYNC_NOSPACE, &wq->flags))
			break;
		fallthrough;
	case SOCK_WAKE_IO:
call_kill:
		kill_fasync(&wq->fasync_list, SIGIO, band);
		break;
	case SOCK_WAKE_URG:
		kill_fasync(&wq->fasync_list, SIGURG, band);
	}

	return 0;
}
```

`how` 的取值（`include/linux/net.h:241-246`）：

```c
enum {
	SOCK_WAKE_IO,
	SOCK_WAKE_WAITD,
	SOCK_WAKE_SPACE,
	SOCK_WAKE_URG,
};
```

调用点全在 `net/core/sock.c` 的默认回调里：

| `how` | 调用处 | band | 触发场景 |
|-------|--------|------|---------|
| `SOCK_WAKE_WAITD` | `sock_def_readable` `:3326` | `POLL_IN` | 数据到达（默认 `sk->sk_data_ready`） |
| `SOCK_WAKE_SPACE` | `sock_def_write_space` `:3346`、`sock_def_write_space_wfree` `:3371` | `POLL_OUT` | 发送缓冲区腾出空间 |
| `SOCK_WAKE_IO` | `sock_def_error_report` `:3311` | `POLL_ERR` | 出错 |
| `SOCK_WAKE_URG` | `sk_send_sigurg` `:3383` | `POLL_PRI` | 紧急数据（`SIGURG` 专用） |

（`sock_def_readable` 被设为默认值的位置：`net/core/sock.c:3447`
`sk->sk_data_ready = sock_def_readable;`）

#### 闸门 A：可写方向 —— `SOCKWQ_ASYNC_NOSPACE`（边沿触发）

```c
	case SOCK_WAKE_SPACE:
		if (!test_and_clear_bit(SOCKWQ_ASYNC_NOSPACE, &wq->flags))
			break;      /* 位本来就是 0 → 不欠账 → 不发信号 */
		fallthrough;
```

这是**记账式**的：

- **置位（欠账）**：发送侧发现写不下时
  - `sock_alloc_send_pskb()` `net/core/sock.c:2786`
    —— `sk_wmem_alloc_get(sk) >= sk->sk_sndbuf` 时置位，紧跟着 `set_bit(SOCK_NOSPACE, ...)`
  - `tcp_poll()` `net/ipv4/tcp.c:569` —— poll 发现不可写时置位，注释写得很直白：
    ```c
    		} else {  /* send SIGIO later */
    			sk_set_bit(SOCKWQ_ASYNC_NOSPACE, sk);
    			set_bit(SOCK_NOSPACE, &sk->sk_socket->flags);
    ```
- **清零（还账）**：`sock_wait_for_wmem()` `:2740`、`tcp_sendmsg_locked()` `tcp.c:1121`

⭐ **语义 = 边沿触发（edge-triggered）**：
只有发生「**可写 → 不可写 → 可写**」的跃变，才会发一次 `SIGIO/POLL_OUT`。
缓冲区一直可写时，**一个信号都不会发**。

> 这与 epoll 的 `EPOLLET` 是同一类设计哲学：
> 只在状态**跃变**时通知一次，避免"水平条件一直成立 → 疯狂通知"。

#### 闸门 B：可读方向 —— `SOCKWQ_ASYNC_WAITDATA`（在场者抑制）

```c
	case SOCK_WAKE_WAITD:
		if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
			break;      /* 位已置 → 有人在阻塞等 → 不发信号 */
		goto call_kill;
```

这个位的置位点**极其反直觉** —— 它只在**阻塞等待**路径里被置位：

```c
/* net/core/sock.c:3019 —— sk_wait_data() */
int sk_wait_data(struct sock *sk, long *timeo, const struct sk_buff *skb)
{
	DEFINE_WAIT_FUNC(wait, woken_wake_function);
	int rc;

	add_wait_queue(sk_sleep(sk), &wait);
	sk_set_bit(SOCKWQ_ASYNC_WAITDATA, sk);
	rc = sk_wait_event(sk, timeo, skb_peek_tail(&sk->sk_receive_queue) != skb, &wait);
	sk_clear_bit(SOCKWQ_ASYNC_WAITDATA, sk);
	remove_wait_queue(sk_sleep(sk), &wait);
	return rc;
}
```

⭐⭐ **语义解读**：`SOCKWQ_ASYNC_WAITDATA` 的真名应该叫「**有人正在阻塞等数据**」。

- 位**已置** → 说明某线程正卡在 `sk_wait_data()` 里 → 它自己会被唤醒，**不需要额外发信号**
- 位**未置** → 没人在阻塞等 → 才发 `SIGIO` 通知用户态

**由此推出本节最有实践价值的一条规律**：

| socket 模式 | `SOCKWQ_ASYNC_WAITDATA` 状态 | SIGIO 行为 |
|------------|---------------------------|-----------|
| **阻塞**（无 `O_NONBLOCK`），线程卡在读 | 置位 | ❌ **几乎收不到** SIGIO（被闸门 B 挡住） |
| **阻塞**，但线程没在读（在干别的） | 未置 | ✅ 每个报文一次 SIGIO |
| **非阻塞**（`O_NONBLOCK`）+ 事件循环 | **永远未置** | ✅✅ **每个报文一次 SIGIO** —— 这才是"过于频繁"的真正来源 |

> 🔑 **这就解释了建立流程里第 ② 步（设 `O_NONBLOCK`）的真实作用**：
> 它不是"为了避免 read 阻塞"这种泛泛的理由，而是
> **让闸门 B 永远处于"开启"状态，从而保证通知不会被抑制**。
> 反过来说：**阻塞 socket 配 `O_ASYNC` 是一个自相矛盾的组合** ——
> 你一边阻塞等、一边又要异步通知，内核的闸门 B 会让通知几乎不出现。

#### 两道闸门的意义：与 epoll 的设计对照

| | 信号驱动 I/O | epoll |
|---|---|---|
| 去重的责任方 | **内核**（`sk_wq->flags` 两位） | **内核**（rdllist + ovflist） |
| 可读语义 | 每个报文一次（非阻塞时） | LT：不读就一直报；ET：跃变才报 |
| 可写语义 | **只有跃变才报**（闸门 A，`EPOLLET` 式） | 取决于 LT/ET 注册 |
| 漏通知的代价 | 信号可能被合并/丢弃（见 §8.3） | 事件在 rdllist 里不会丢 |

> ⚠️ 一个值得注意的不对称：
> **可写方向是边沿触发式的（闸门 A），可读方向默认却不是**（闸门 B 只在阻塞时挡）。
> 于是在非阻塞场景下，可读通知可能远多于可写通知 ——
> 这与 epoll 的默认行为（两个方向都是 LT）正好相反。

### 7. 投递链路：从 `kill_fasync()` 到进程

```
设备/协议栈事件（数据到达、缓冲区腾空、出错…）
   │
   ▼
sk->sk_data_ready  ==  sock_def_readable()                    [net/core/sock.c:3315]
   │    （同时也会 wake_up 阻塞等待者；这里只看异步分支）
   ▼
sk_wake_async(sk, SOCK_WAKE_WAITD, POLL_IN)                   [include/net/sock.h]
   │    ├─ if (sock_flag(sk, SOCK_FASYNC))  ← 闸门 0：没开 O_ASYNC 直接返回
   │    └─ rcu_read_lock() → sock_wake_async() → rcu_read_unlock()
   ▼
sock_wake_async()          ★闸门 A / 闸门 B                    [net/socket.c]
   ▼
kill_fasync(&wq->fasync_list, SIGIO, band)                    [fs/fcntl.c:1012]
   │    ├─ if (*fp)  ← 无锁快查：链表通常为空，省一次 RCU 读锁
   │    └─ rcu_read_lock() → kill_fasync_rcu() → rcu_read_unlock()
   ▼
kill_fasync_rcu()  遍历 fasync 单链表                          [fs/fcntl.c:987]
   │    ├─ 校验 magic
   │    ├─ read_lock_irqsave(&fa->fa_lock)

send_sigio()       拿 fown->lock，按 pid_type 展开             [fs/fcntl.c:773]
   │    ├─ type <= PIDTYPE_TGID  → 单个 task
   │    └─ type == PIDTYPE_PGID  → 持 tasklist_lock 遍历进程组
   ▼
send_sigio_to_task()  ★构造 siginfo、检查权限、投递            [fs/fcntl.c:717]
   ▼

```

`kill_fasync()` 的两个工程细节：

```c
/* fs/fcntl.c:1012 */
void kill_fasync(struct fasync_struct **fp, int sig, int band)
{
	/* First a quick test without locking: usually
	 * the list is empty.
	 */
	if (*fp) {
		rcu_read_lock();
		kill_fasync_rcu(rcu_dereference(*fp), sig, band);
		rcu_read_unlock();
	}
}
EXPORT_SYMBOL(kill_fasync);
```

1. **无锁快查**：先裸读 `*fp`，为空就直接返回。这是给「绝大多数 fd 没开 O_ASYNC」
   的常见情况做优化 —— 否则每个包的接收路径都要白拿一次 RCU 读锁
2. **`EXPORT_SYMBOL`**：`kill_fasync` 是**驱动可见的公开 API**，
   字符设备驱动在自己的中断处理里直接调它（这也是它必须快的原因）

#### SIGURG 的特判

```c
/* fs/fcntl.c:1000-1006 */
		if (fa->fa_file) {
			fown = &fa->fa_file->f_owner;
			/* Don't send SIGURG to processes which have not set a
			   queued signum: SIGURG has its own default signalling
			   mechanism. */
			if (!(sig == SIGURG && fown->signum == 0))
				send_sigio(fown, fa->fa_fd, band);
		}
```

即：**如果用户没用 `F_SETSIG` 指定信号，就不要送 `SIGURG`**。
因为 `SIGURG` 有自己默认的处理机制（`sk_send_sigurg()` 会先试 `send_sigurg()` 直接走
`f_owner`），重复送会造成语义混乱。

注意 `sk_send_sigurg()` 的写法：

```c
/* net/core/sock.c:3380 */
void sk_send_sigurg(struct sock *sk)
{
	if (sk->sk_socket && sk->sk_socket->file)
		if (send_sigurg(&sk->sk_socket->file->f_owner))
			sk_wake_async(sk, SOCK_WAKE_URG, POLL_PRI);
}
```

只有当 `send_sigurg()` 失败（返回 0）时，才回落到 `sk_wake_async()` 这条通用路径。

### 8. ⭐ 信号里到底携带什么 —— `siginfo` 的三个关键字段

这是原笔记里**需要修正**的一处。原笔记说「标准 SIGIO 不携带 fd 信息」，
这个说法**对一半**：

- ❌ 错的一半：用 `F_SETSIG` + `SA_SIGINFO` 时，信号**明确携带 fd 和事件类型**
- ✅ 对的一半：**默认情况**（`signum == 0`，走普通 `SIGIO`）确实不携带 —— 见 §8.3

#### 8.1 构造 siginfo 的代码

```c
/* fs/fcntl.c:717-773 —— send_sigio_to_task()  */
static void send_sigio_to_task(struct task_struct *p,
			       struct fown_struct *fown,
			       int fd, int reason, enum pid_type type)
{
	/*
	 * F_SETSIG can change ->signum lockless in parallel, make
	 * sure we read it once and use the same value throughout.
	 */
	int signum = READ_ONCE(fown->signum);

	if (!sigio_perm(p, fown, signum))
		return;

	switch (signum) {
		default: {
			kernel_siginfo_t si;

			clear_siginfo(&si);
			si.si_signo = signum;
			si.si_errno = 0;
		        si.si_code  = reason;
			/*
			 * Posix definies POLL_IN and friends to be signal
			 * specific si_codes for SIG_POLL.  Linux extended
			 * these si_codes to other signals in a way that is
			 * ambiguous if other signals also have signal
			 * specific si_codes.  In that case use SI_SIGIO instead
			 * to remove the ambiguity.
			 */
			if ((signum != SIGPOLL) && sig_specific_sicodes(signum))
				si.si_code = SI_SIGIO;

			/* Make sure we are called with one of the POLL_*
			   reasons, otherwise we could leak kernel stack into
			   userspace.  */
			BUG_ON((reason < POLL_IN) || ((reason - POLL_IN) >= NSIGPOLL));
			if (reason - POLL_IN >= NSIGPOLL)
				si.si_band  = ~0L;
			else
				si.si_band = mangle_poll(band_table[reason - POLL_IN]);
			si.si_fd    = fd;
			if (!do_send_sig_info(signum, &si, p, type))
				break;
		}
			fallthrough;	/* fall back on the old plain SIGIO signal */
		case 0:
			do_send_sig_info(SIGIO, SEND_SIG_PRIV, p, type);
	}
}
```

三个字段：

| 字段 | 内容 | 来源 |
|------|------|------|
| `si_signo` | 你用 `F_SETSIG` 设的信号号 | `READ_ONCE(fown->signum)` |
| `si_code` | 事件原因：`POLL_IN`/`POLL_OUT`/`POLL_ERR`/… 或 `SI_SIGIO` | `reason` 参数 |
| `si_band` | **poll 位掩码**（`POLLIN`/`POLLOUT`/… 的位组合） | `mangle_poll(band_table[...])` |
| `si_fd` | **就绪的文件描述符** | `fasync_struct.fa_fd` |

#### 8.2 `si_band` 是怎么算出来的 —— 两级映射

事件原因（reason）是紧凑的 `POLL_IN..POLL_HUP` 编号：

```c
/* include/uapi/asm-generic/siginfo.h:295-301 */
#define POLL_IN		1	/* data input available */
#define POLL_OUT	2	/* output buffers available */
#define POLL_MSG	3	/* input message available */
#define POLL_ERR	4	/* i/o error */
#define POLL_PRI	5	/* high priority input available */
#define POLL_HUP	6	/* device disconnected */
#define NSIGPOLL	6
```

**第一级**：`band_table[]` 把编号翻译成内核内部的 `EPOLL*` 位掩码：

```c
/* fs/fcntl.c:692 */
static const __poll_t band_table[NSIGPOLL] = {
	EPOLLIN | EPOLLRDNORM,			/* POLL_IN */
	EPOLLOUT | EPOLLWRNORM | EPOLLWRBAND,	/* POLL_OUT */
	EPOLLIN | EPOLLRDNORM | EPOLLMSG,		/* POLL_MSG */
	EPOLLERR,				/* POLL_ERR */
	EPOLLPRI | EPOLLRDBAND,			/* POLL_PRI */
	EPOLLHUP | EPOLLERR			/* POLL_HUP */
};
```

**第二级**：`mangle_poll()` 把 `EPOLL*` 位翻成用户态看到的 `POLL*` 位（`__u16`）：

```c
/* include/linux/poll.h */
static inline __u16 mangle_poll(__poll_t val)
{
	__u16 v = (__force __u16)val;
#define M(X) __MAP(v, (__force __u16)EPOLL##X, POLL##X)
	return M(IN) | M(OUT) | M(PRI) | M(ERR) | M(NVAL) |
		M(RDNORM) | M(RDBAND) | M(WRNORM) | M(WRBAND) |
		M(HUP) | M(RDHUP) | M(MSG);
#undef M
}
```

所以 `POLL_IN` 最终给到用户态的 `si_band` 是 `POLLIN | POLLRDNORM`。

> 📌 注意 `POLL_HUP` 映射成 `EPOLLHUP | EPOLLERR` —— **挂断同时带错误位**。
> 处理 `si_band` 时不能只判 `POLLHUP`。

#### 8.3 ⭐ 什么时候 `si_code` 会退化成 `SI_SIGIO`

```c
	if ((signum != SIGPOLL) && sig_specific_sicodes(signum))
		si.si_code = SI_SIGIO;
```

`sig_specific_sicodes()` 查的是这个掩码（`include/linux/signal.h:437-448`）：

```c
#define SIG_SPECIFIC_SICODES_MASK (\
	rt_sigmask(SIGILL)    |  rt_sigmask(SIGFPE)    | \
	rt_sigmask(SIGSEGV)   |  rt_sigmask(SIGBUS)    | \
	rt_sigmask(SIGTRAP)   |  rt_sigmask(SIGCHLD)   | \
	rt_sigmask(SIGPOLL)   |  rt_sigmask(SIGSYS)    | \
	SIGEMT_MASK                                    )

#define sig_specific_sicodes(sig)	siginmask(sig, SIG_SPECIFIC_SICODES_MASK)
```

**这些信号已经有自己专属的 `si_code` 取值空间**（比如 `SIGSEGV` 的 `SEGV_MAPERR`），
`POLL_IN`（=1）这种值会与之冲突。所以内核把 `si_code` 改成 `SI_SIGIO`（= -5），
**代价是丢失了事件类型信息** —— 用户态只能去看 `si_band`。

> ⚠️ **实践结论**：`F_SETSIG` 应该选**普通实时信号**（`SIGRTMIN+n`），
> **不要选** `SIGILL/SIGFPE/SIGSEGV/SIGBUS/SIGTRAP/SIGCHLD/SIGPOLL/SIGSYS`。
> 选了后者，`si_code` 会退化成 `SI_SIGIO`。

#### 8.4 ⭐⭐ 默认 SIGIO 不排队 —— `fallthrough` 降级

```c
			if (!do_send_sig_info(signum, &si, p, type))
				break;
		}
			fallthrough;	/* fall back on the old plain SIGIO signal */
		case 0:
			do_send_sig_info(SIGIO, SEND_SIG_PRIV, p, type);
```

两条路径的差别巨大：

| | 默认（`signum == 0`） | `F_SETSIG` 指定实时信号 |
|---|---|---|
| 走哪条 | `case 0` 分支 | `default` 分支 |
| 携带 siginfo | ❌ `SEND_SIG_PRIV`（**无 siginfo**） | ✅ 完整 `si_fd`/`si_band`/`si_code` |
| **是否排队** | ❌ **不排队**（标准信号，多个合并成一个） | ✅ **排队**（实时信号，逐个保留） |
| 溢出行为 | 合并 → **丢事件** | 队列满 → `fallthrough` 降级为普通 SIGIO |

⭐ **这就是原笔记"不携带 fd 信息"说法成立的唯一场景**：
默认 `SIGIO`（`signum=0`）走 `SEND_SIG_PRIV`，**根本没有 siginfo**，
所以 handler 里拿不到 `si_fd`。

也正因为不排队：**连续到达 10 个报文，进程可能只收到 1 个 SIGIO**。
用 `F_SETSIG` 换成实时信号后，10 个报文会排 10 个信号 —— 但队列满了仍会降级。

> 🔑 **这是信号驱动 I/O 与 epoll 最本质的差距**：
> epoll 的事件存在内核的 `rdllist` 里，**不会因为"用户还没取"就丢**；
> 而信号（尤其默认的 `SIGIO`）会被合并，**通知数量与事件数量不再一一对应**。
> 对 HFT 这类要求"每个事件都可追溯"的场景，这是致命的。

#### 8.5 权限检查 —— `sigio_perm()`

```c
/* fs/fcntl.c:702 */
static inline int sigio_perm(struct task_struct *p,
                             struct fown_struct *fown, int sig)
{
	const struct cred *cred;
	int ret;

	rcu_read_lock();
	cred = __task_cred(p);
	ret = ((uid_eq(fown->euid, GLOBAL_ROOT_UID) ||
		uid_eq(fown->euid, cred->suid) || uid_eq(fown->euid, cred->uid) ||
		uid_eq(fown->uid,  cred->suid) || uid_eq(fown->uid,  cred->uid)) &&
	       !security_file_send_sigiotask(p, fown, sig));
	rcu_read_unlock();
	return ret;
}
```

规则：设置属主时记录的 `uid`/`euid`，必须与被通知进程的 `uid` 或 `suid` **之一**匹配
（或是 root），并且还要过 LSM 钩子 `security_file_send_sigiotask()`（SELinux/AppArmor 的接入点）。

> 📌 这防止的是：**A 进程给 B 进程的 fd 设属主，让内核替自己骚扰 B**。
> 不过注意判据是 uid 匹配而不是"同一进程"—— 同一 uid 下的跨进程通知是允许的。

#### 8.6 并发保护：三把锁 + 一处 `READ_ONCE`

| 保护对象 | 机制 | 位置 |
|---------|------|------|
| `fown_struct.pid/uid/euid` | `rwlock_t fown->lock` | `send_sigio` 读侧 `:778`、`f_modown` 写侧 `:91` |
| `fasync_struct.fa_fd` | `rwlock_t fa->fa_lock` | `kill_fasync_rcu` 读侧 `:998`、`fasync_insert_entry` 写侧 `:925` |
| fasync 链表本身 | **RCU**（`rcu_assign_pointer` / `rcu_dereference`） | `:931` / `:1011` |
| `fown->signum` | **`READ_ONCE`**，无锁 | `:724` |

最后一行的注释解释了为什么用 `READ_ONCE` 而不是加锁：

```c
	/*
	 * F_SETSIG can change ->signum lockless in parallel, make
	 * sure we read it once and use the same value throughout.
	 */
	int signum = READ_ONCE(fown->signum);
```

`F_SETSIG` 是在 `do_fcntl` 里**无锁直写** `filp->f_owner.signum` 的（`:396`），
而发送侧可能同时在读。内核的做法是：写侧不管，读侧用 `READ_ONCE` 保证
**读到的是一个完整的、前后一致的值**（不会读到撕裂的半写值，且整段逻辑复用同一个值）。

> 这是内核里典型的"**乐观无锁读 + 允许读到稍旧的值**"模式：
> 最坏情况是这一次信号用了旧 signum，下一次用新的 —— 可接受。

#### 9.2 `SOCKWQ_ASYNC_*` 从 `sock->flags` 迁到 `sk->sk_wq->flags`

前引 `include/linux/net.h:35-37` 的注释已经交代：这两位**历史上在 `sock->flags`**，
后来才搬到 `socket_wq.flags`。它俩的值是 **0 和 1** —— 这个低位编号正是
"早期和 `sock->flags` 共用同一套位编号"留下的痕迹：

```c
#define SOCKWQ_ASYNC_NOSPACE	0
#define SOCKWQ_ASYNC_WAITDATA	1
```

> 📌 查代码时的实践提示：
> 老资料里若出现 `sk->sk_socket->flags` 与 `SOCKWQ_ASYNC_*` 混用，
> 那是**迁移前**的写法。v6.6 一律走 `sk->sk_wq->flags`，
> 通过 `sk_set_bit()` / `sk_clear_bit()` / `sk_test_bit()` 这些包装访问。

#### 9.3 `struct fown_struct` 从未有过 `fd` 字段

实测六个版本的 `include/linux/fs.h`：

| 版本 | `struct fown_struct` 字段 |
|------|--------------------------|
| v4.19 | `lock, pid, pid_type, uid, euid, signum` |
| v5.10 | 同上 |
| v5.15 | 同上 |
| v5.16 | 同上 |
| v5.17 | 同上 |
| **v6.6** | 同上 |

**全部不含 `fd`。** 所以"`F_SETOWN` 记录了 fd"是错的 ——
fd 存在于 `fasync_struct.fa_fd`，而 `fasync_struct` 是**开 `O_ASYNC` 时才创建**的。

这也解释了一个行为差异：**只 `F_SETOWN` 而不开 `O_ASYNC`，什么都不会发生**，
因为压根没有 `fasync_struct`，`send_sigio()` 永远不会被调用到。

### 10. 优缺点（修正版）

原笔记的优缺点表基本成立，但需要补上机制层的根据：

| 优势 | 机制依据 |
|------|---------|
| 无需轮询 | 事件由中断/协议栈直接触发 `sk->sk_data_ready` → `kill_fasync()` |
| 不阻塞 | 进程继续执行，信号 handler 异步跑 |
| 内核侧有去重 | ⭐ **两道闸门**（§6）—— 可写方向是跃变触发，可读方向在阻塞时被抑制 |
| 注册成本低 | 一个 fd 一个 `fasync_struct`（对比 epoll 的 epitem + 红黑树节点） |

| 劣势 | 机制依据 |
|------|---------|
| **默认信号不排队** | ⭐ `SEND_SIG_PRIV` 无 siginfo 且不排队（§8.4）→ **会丢事件** |
| 队列满会降级 | rt signal 排队失败 → `fallthrough` 到普通 SIGIO（§8.4） |
| 每个信号一次上下文切换 | 信号投递走 `do_send_sig_info` → 设置 TIF_SIGPENDING → 返回用户态前进入 handler |
| 查找是 O(n) | `fasync_struct` 是**单链表**（`fa_next`），`kill_fasync_rcu` 线性遍历 |
| 1:1 限制 | `fown_struct` 只有一个 `pid`（+`pid_type`），**一个 fd 只能通知一个目标**（§3.1） |
| 默认不携带 fd | 只有 `F_SETSIG` + `SA_SIGINFO` 才有 `si_fd`（§8） |
| 信号处理函数的限制 | handler 里只能调 async-signal-safe 函数；用 `signalfd`/自管道才能安全做复杂操作 |

> 🔑 第 1、2 条（**丢事件**）是它不适合严肃场景的**决定性原因**，
> 而不是常说的"信号开销大"。开销大的问题可以靠批量处理缓解，
> **丢事件无法缓解**。

### 11. 与 epoll 的对比（修正原笔记的三处错误）

原笔记的对比表里有三处需要按 v6.6 源码修正：

| 维度 | 信号驱动 I/O | epoll | 原笔记的说法 | 修正 |
|------|-------------|-------|-------------|------|
| 通知方式 | 信号（SIGIO / 实时信号） | `epoll_wait()` 返回事件数组 | ✅ 对 | — |
| fd 信息 | **默认无**，`F_SETSIG`+`SA_SIGINFO` 时有 `si_fd` | `epoll_data_t`（8 字节自由携带） | 「不携带」 | ⚠️ **不准确**：配好了能携带 |
| 事件类型 | `si_band`（`POLL*` 位） | `epoll_event.events`（`EPOLL*` 位） | — | 两者位编码**不同**，需 `mangle_poll`/`demangle_poll` 转换 |
| 内核结构 | `fasync_struct` **单链表** | `epitem` + **红黑树** `rb_root_cached` + 就绪链表 `rdllist` | — | 查找 O(n) vs O(log n) |
| 复杂度 | 遍历 O(n) | `epoll_ctl` **O(log n)**，取事件 O(k) | 「O(1)」 | ❌ **错**：epoll_ctl 是 O(log n)（见 63.4 Q1） |
| 实现载体 | 纯粹的信号队列 | **系统调用 + 内核数组拷贝** | 「共享内存事件表」 | ❌ **错**：epoll **没有共享内存**，事件是 `copy_to_user` 拷出来的（见 63.4） |
| 丢事件 | ⭐ **会丢**（信号合并且可能降级） | 不丢（事件挂在 `rdllist` 上） | 未提 | ⭐ **这才是最关键的差距** |
| 一对多 | ❌ 一个 fd 一个属主 | ✅ 一个 epoll fd 监听 N 个 fd | 未提 | — |
| 扩展性 | 差 | 好 | ✅ 对 | — |
| 推荐度 | 不推荐（除特定场景） | 强烈推荐 | ✅ 对 | — |

> 📌 关于"epoll 用共享内存"这个常见误解：
> epoll 的**接口**是 `epoll_wait(epfd, events, maxevents, timeout)`，
> 内核把就绪事件**拷贝到**用户提供的 `events` 数组里。
> 全程没有 mmap，没有共享内存页。真正用共享内存做 I/O 的是 **`io_uring`**
> （SQ/CQ 环形缓冲区 mmap 到用户态）—— 那属于
> [12.5 现代网络](../../../12.5-modern-networking/) 的范畴。

### 12. 现代内核里还有哪些残余用途

原笔记说「被 epoll 完全取代」，方向上对，但有几个它**仍在被使用**的场景值得知道：

| 场景 | 说明 |
|------|------|
| **终端设备 / 串口** | tty 层是最经典的 fasync 用户：键盘输入、modem 状态变化。`SIGIO` 在 POSIX 终端语义里有规范地位 |
| **`SIGURG`** | 带外数据通知**只有信号这一条路**（`sk_send_sigurg()`），epoll 的 `EPOLLPRI` 是另一套机制，不能互相替代 |
| **文件租约（file lease）** | `F_SETLEASE` / `F_NOTIFY` 这套机制**复用 fasync 基础设施**（`fasync_helper` 的注释里明确写了 "and for regular files by the file lease code"） |
| **字符设备驱动** | 自定义硬件（FPGA、ADC、GPIO 中断）在驱动里调 `kill_fasync()` 通知用户态，是最省事的方案 |
| **`signalfd()`** | ⭐ 把信号转成 fd，配合 epoll 使用 —— 这反而是"信号机制在现代程序里的最佳归宿"（见 63.5） |

> 🔑 **最有价值的一条**：**`signalfd()` + epoll** 的组合让信号重新变得可用 ——
> 信号变成可读的 fd，塞进同一个 epoll 事件循环，
> 既保留了信号的语义，又摆脱了"handler 里能干什么"的限制。
> 这是 63.5 的主题。

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| **HFT · 结论** | **不用信号驱动 I/O 做行情/订单主路径**。三条硬伤见下 |
| **HFT · 硬伤 1：丢事件** | 默认 SIGIO 不排队（§8.4），多个报文合并成一个信号。行情链路要求**每个 tick 可追溯**，信号语义天然不满足 |
| **HFT · 硬伤 2：抖动** | 信号投递要设置 `TIF_SIGPENDING` 并在返回用户态前进入 handler；若进程正在跑热路径（或持有锁），handler 的插入点是**不可预测的**。抖动量级是**微秒到几十微秒**，且**无上界** |
| **HFT · 硬伤 3：handler 限制** | handler 里只能调 async-signal-safe 函数。不能分配内存、不能加锁（会死锁）、不能调大多数库函数 —— 这对复杂业务逻辑是致命约束 |
| **HFT · 唯一可用场景** | 用它做**低频旁路通知**（如"风控阈值被触发"、"运维信号"），主路径仍走 epoll / busy-poll |
| **HFT · 该用什么** | 行情：`epoll` + `SO_BUSY_POLL` / `AF_XDP`；订单：`io_uring`。见 [63.4](./63.4-the-epoll-api.md) 与 [12.5 现代网络](../../../12.5-modern-networking/) |
| **嵌入式 · 串口/传感器** | ⭐ **这里信号驱动 I/O 是合理选择**：数据量低（KB/s 级）、事件稀疏、CPU 弱（不能跑轮询浪费 cycles）、丢事件的后果可控。比起开一个线程阻塞 `read()`，SIGIO 省一个栈 |
| **嵌入式 · 自定义驱动** | 在字符设备驱动里 `kill_fasync()` 通知用户态，是 Linux 驱动教材的标准范式，代码量远小于实现 poll/epoll 回调 |
| **嵌入式 · 实时性** | ⚠️ 注意：`SIGIO` 的投递**不保证优先级**。若需要硬实时，应配合 `sched_setscheduler(SCHED_FIFO)` + 信号优先级（实时信号号越小优先级越高：`SIGRTMIN` 最高） |
| **通用 · 迁移建议** | 旧代码里见到 `O_ASYNC`，优先改 `epoll`；若必须保留信号语义，改 `signalfd()` 再并入 epoll |

> 📌 **一个容易忽略的点**：实时信号的**投递优先级由信号号决定，号越小越优先**。
> 所以 `F_SETSIG(SIGRTMIN)` 不只是"能排队"，还意味着**最高投递优先级**。
> 这在 RT 场景下是有意义的调优手段。

## 代码示例

### 示例 1：最小可用骨架 —— 带 `SA_SIGINFO` 拿到 `si_fd` / `si_band`

```c
/* sigio_min.c —— 信号驱动 I/O 最小骨架（UDP）
 * 编译: gcc -O2 -Wall -o sigio_min sigio_min.c
 * 要点: 用 SA_SIGINFO + F_SETSIG 才能拿到 si_fd / si_band
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <netinet/in.h>
#include <sys/socket.h>

static volatile sig_atomic_t got = 0;

static void sigio_handler(int sig, siginfo_t *si, void *uc)
{
    (void)sig; (void)uc;
    /* si->si_code 是 POLL_IN/POLL_OUT/POLL_ERR...（若被退化则为 SI_SIGIO）
     * si->si_band 是 POLL* 位掩码（POLLIN|POLLRDNORM 等）
     * si->si_fd   是就绪的 fd —— 这正是原笔记说"不携带"的那个信息 */
    printf("SIGIO: fd=%d code=%d band=0x%x (POLLIN=%d)\n",
           si->si_fd, si->si_code, si->si_band,
           !!(si->si_band & POLLIN));
    got = 1;
}

int main(void)
{
    int fd = socket(AF_INET, SOCK_DGRAM, 0);
    if (fd < 0) { perror("socket"); return 1; }

    struct sockaddr_in a = {0};
    a.sin_family = AF_INET;
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    a.sin_port = htons(9999);
    if (bind(fd, (struct sockaddr *)&a, sizeof a) < 0) {
        perror("bind"); return 1;
    }

    /* ① 装 handler —— 必须 SA_SIGINFO，否则拿不到 siginfo */
    struct sigaction sa = {0};
    sa.sa_sigaction = sigio_handler;
    sa.sa_flags = SA_SIGINFO | SA_RESTART;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGIO, &sa, NULL) < 0) { perror("sigaction"); return 1; }

    /* ② 设属主 —— 必须早于 O_ASYNC，否则首批通知会被静默丢弃 */
    if (fcntl(fd, F_SETOWN, getpid()) < 0) { perror("F_SETOWN"); return 1; }

    /* ③ 换成一个实时信号：既排队、又带 siginfo
     *    注意别用 SIGSEGV/SIGILL/SIGCHLD/SIGPOLL 等有专用 si_code 的信号，
     *    否则 si_code 会被内核改成 SI_SIGIO，丢失事件类型 */
    int rt = SIGRTMIN;                      /* 实时信号中优先级最高 */
    if (fcntl(fd, F_SETSIG, rt) < 0) { perror("F_SETSIG"); return 1; }

    /* ④ 非阻塞 + 异步通知
     *    O_NONBLOCK 不是可选项：它保证闸门 B(SOCKWQ_ASYNC_WAITDATA) 永远开启，
     *    否则数据到达时通知会被抑制 */
    int fl = fcntl(fd, F_GETFL);
    if (fcntl(fd, F_SETFL, fl | O_NONBLOCK | O_ASYNC) < 0) {
        perror("F_SETFL"); return 1;
    }

    printf("waiting on UDP 127.0.0.1:9999  (rt signal = %d)\n", rt);
    printf("try:  echo hello | nc -u 127.0.0.1 9999\n");

    /* 生产环境不会这么写（pause 无法与业务逻辑组合），
     * 这里只为演示。真实用法见示例 3 的 signalfd 方案 */
    while (!got)
        pause();

    char buf[1500];
    ssize_t n = recv(fd, buf, sizeof buf, 0);       /* 不会阻塞：有数据 */
    printf("recv %zd bytes\n", n);

    close(fd);
    return 0;
}
```

### 示例 2：观测两道闸门 —— 计数而非猜

下面这个程序用 `poll()` 把"可写跃变"和"实际收到 SIGIO"的次数对照起来，
直观展示闸门 A 的边沿语义。

```c
/* sigio_gate.c —— 验证闸门 A(SOCKWQ_ASYNC_NOSPACE) 的边沿语义
 * 做法：不断向一个 UDP socket 发送数据直到发送缓冲满（置位 NOSPACE），
 *       再读掉，观察 POLL_OUT 类型的 SIGIO 只出现一次，而不是每次腾空都来一次。
 * 编译: gcc -O2 -Wall -o sigio_gate sigio_gate.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <netinet/in.h>
#include <sys/socket.h>

static volatile sig_atomic_t n_pollin = 0, n_pollout = 0;

static void h(int sig, siginfo_t *si, void *uc)
{
    (void)sig; (void)uc;
    /* 注意：内核给的是 POLL* 位（mangle_poll 之后），不是 EPOLL* */
    if (si->si_band & (POLLOUT | POLLWRNORM)) n_pollout++;
    if (si->si_band & (POLLIN  | POLLRDNORM)) n_pollin++;
}

static int setup_async(int fd, int signum)
{
    struct sigaction sa = {0};
    sa.sa_sigaction = h;
    sa.sa_flags = SA_SIGINFO;
    sigemptyset(&sa.sa_mask);
    if (sigaction(signum, &sa, NULL) < 0) return -1;
    if (fcntl(fd, F_SETOWN, getpid()) < 0) return -1;
    if (fcntl(fd, F_SETSIG, signum) < 0) return -1;
    int fl = fcntl(fd, F_GETFL);
    return fcntl(fd, F_SETFL, fl | O_NONBLOCK | O_ASYNC);
}

int main(void)
{
    /* 用 socketpair 造一对 UDP 式的对端，简化实验 */
    int sv[2];
    if (socketpair(AF_UNIX, SOCK_DGRAM, 0, sv) < 0) { perror("socketpair"); return 1; }

    int sig = SIGRTMIN;
    if (setup_async(sv[0], sig) < 0) { perror("setup_async"); return 1; }

    char buf[64 * 1024];
    memset(buf, 'x', sizeof buf);

    /* ① 不停写，直到 EAGAIN —— 此刻内核置位 SOCKWQ_ASYNC_NOSPACE（欠账） */
    long wrote = 0, bytes = 0;
    for (;;) {
        ssize_t n = send(sv[0], buf, sizeof buf, MSG_DONTWAIT);
        if (n < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break;
            if (errno == ENOBUFS) break;
            perror("send"); return 1;
        }
        bytes += n;
        if (++wrote > 100000) { fprintf(stderr, "sendbuf never filled?\n"); break; }
    }
    printf("filled send buffer: %ld bytes, %ld sends  -> NOSPACE 位已置\n",
           bytes, wrote);

    /* ② 从对端把数据读掉，让发送侧腾出空间 —— 触发 sock_def_write_space()
     *    → sk_wake_async(SOCK_WAKE_SPACE, POLL_OUT)
     *    → test_and_clear_bit(NOSPACE)：欠账则发一次 SIGIO 并清账 */
    size_t drained = 0;
    for (;;) {
        ssize_t n = recv(sv[1], buf, sizeof buf, MSG_DONTWAIT);
        if (n <= 0) break;
        drained += (size_t)n;
    }
    printf("drained %zu bytes from peer\n", drained);

    /* ③ 让信号有机会投递 */
    usleep(200 * 1000);

    printf("SIGIO 计数: POLLIN=%d  POLLOUT=%d\n", n_pollin, n_pollout);
    printf("\n预期解读:\n");
    printf("  - POLLOUT 是 '跃变' 语义：缓冲区由满变空才通知一次，\n");
    printf("    而不是每腾出一块就通知一次（闸门 A: test_and_clear_bit）\n");
    printf("  - 若你在同一 socket 上 O_NONBLOCK 且持续收数据，\n");
    printf("    POLLIN 会远多于 POLLOUT（闸门 B 在非阻塞时不抑制）\n");

    close(sv[0]); close(sv[1]);
    return 0;
}
```

> ⚠️ 两个例子里的 `printf()` **不是** async-signal-safe 的，
> 仅用于演示。生产代码里 handler 只应做 `write()` 到一个
> `O_NONBLOCK` 的**自管道**，或干脆用示例 3 的 `signalfd` 方案。

### 示例 3：现代写法 —— `signalfd()` 把信号并进 epoll

```c
/* sigio_signalfd.c —— 推荐的现代形态：信号 → fd → epoll
 * 好处: ① 不再受 async-signal-safe 限制
 *       ② 信号与 socket 在同一个 epoll 循环里，无竞态
 *       ③ 可用 epoll_pwait2 做纳秒级超时
 * 编译: gcc -O2 -Wall -o sigio_signalfd sigio_signalfd.c
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <sys/signalfd.h>
#include <sys/epoll.h>
#include <netinet/in.h>
#include <sys/socket.h>

int main(void)
{
    int udp = socket(AF_INET, SOCK_DGRAM, 0);
    if (udp < 0) { perror("socket"); return 1; }

    struct sockaddr_in a = {0};
    a.sin_family = AF_INET;
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    a.sin_port = htons(9998);
    if (bind(udp, (struct sockaddr *)&a, sizeof a) < 0) { perror("bind"); return 1; }

    /* ① 先把 SIGIO 屏蔽掉 —— signalfd 只接管"被阻塞"的信号 */
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGIO);
    if (sigprocmask(SIG_BLOCK, &mask, NULL) < 0) { perror("sigprocmask"); return 1; }

    /* ② 信号变 fd */
    int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
    if (sfd < 0) { perror("signalfd"); return 1; }

    /* ③ socket 侧照旧设属主 + O_ASYNC（信号不再进 handler，而是排队等 signalfd 读） */
    if (fcntl(udp, F_SETOWN, getpid()) < 0) { perror("F_SETOWN"); return 1; }
    int fl = fcntl(udp, F_GETFL);
    if (fcntl(udp, F_SETFL, fl | O_NONBLOCK | O_ASYNC) < 0) { perror("F_SETFL"); return 1; }

    /* ④ 两个 fd 进同一个 epoll */
    int ep = epoll_create1(EPOLL_CLOEXEC);
    if (ep < 0) { perror("epoll_create1"); return 1; }

    struct epoll_event ev = {0};
    ev.events = EPOLLIN;
    ev.data.fd = sfd;   epoll_ctl(ep, EPOLL_CTL_ADD, sfd, &ev);
    ev.data.fd = udp;   epoll_ctl(ep, EPOLL_CTL_ADD, udp, &ev);

    printf("epoll + signalfd ready on UDP 127.0.0.1:9998\n");

    struct epoll_event out[16];
    for (int i = 0; i < 20; ) {
        int n = epoll_wait(ep, out, 16, 5000);
        if (n < 0) { if (errno == EINTR) continue; perror("epoll_wait"); break; }
        if (n == 0) { printf("(timeout)\n"); break; }

        for (int k = 0; k < n; k++) {
            if (out[k].data.fd == sfd) {
                /* 读一个 signalfd_siginfo —— 这里能拿到完整的 si_fd / si_band */
                struct signalfd_siginfo si;
                while (read(sfd, &si, sizeof si) == sizeof si) {
                    printf("[signal] signo=%u code=%d band=0x%x fd=%d\n",
                           si.ssi_signo, si.ssi_code, si.ssi_band, si.ssi_fd);
                }
                i++;
            } else if (out[k].data.fd == udp) {
                char buf[1500];
                ssize_t r;
                while ((r = recv(udp, buf, sizeof buf, 0)) > 0)
                    printf("[udp] %zd bytes\n", r);
                i++;
            }
        }
    }

    close(ep); close(sfd); close(udp);
    return 0;
}
```

> 🔑 示例 3 才是**信号驱动 I/O 在 2026 年该有的样子**：
> 底层的 `fasync` / `kill_fasync` / 两道闸门机制一点没变，
> 但**消费信号的方式**从"异步 handler"变成了"同步读 fd"。
> 这样既保留了 `O_ASYNC` 的语义，又拿到了 epoll 的可控性。
> 这是 63.5「同时等待信号和 fd」要展开的主题。

**Q1.** 内核头文件里有 `O_ASYNC` 吗？`O_ASYNC` 和 `FASYNC` 是什么关系？

<details>
<summary>答案</summary>

**内核 uapi 里没有 `O_ASYNC`**，只有 `FASYNC`：

```c
/* include/uapi/asm-generic/fcntl.h:44-45 */
#ifndef FASYNC
#define FASYNC		00020000	/* fcntl, for BSD compatibility */
#endif
```

`O_ASYNC` 由 **glibc** 定义（`bits/fcntl-linux.h`）为 `020000`。
两者数值完全相同（都是 8192 / `0x2000`，八进制前导零不影响数值），
只是叫法不同：`O_ASYNC` 是 POSIX 叫法，`FASYNC` 是 BSD 遗留。

**实践含义**：写内核代码或做 `F_SETFL` 位运算推理时用 `FASYNC`；
写用户态程序用 `O_ASYNC` 没问题，但要知道它是 libc 提供的。

> 📌 顺带一提：v6.6 的 `arch/x86/include/uapi/asm/fcntl.h` **不存在**，
> x86 直接用 asm-generic 版本，所以这个结论在 x86 上没有例外。
</details>
</details>

**Q2.** 建立信号驱动 I/O 时，`F_SETOWN` 和 `F_SETFL(O_ASYNC)` 的先后顺序有影响吗？为什么？

<details>
<summary>答案</summary>

**有，必须先 `F_SETOWN` 再开 `O_ASYNC`。**

原因是 `send_sigio()` 开头就检查 pid：

```c
/* fs/fcntl.c:773-783 */
void send_sigio(struct fown_struct *fown, int fd, int band)
{
	...
	read_lock_irqsave(&fown->lock, flags);

	type = fown->pid_type;
	pid = fown->pid;
	if (!pid)
		goto out_unlock_fown;      /* ← 属主未设：静默返回，什么都不做 */
```

`O_ASYNC` 一开启，设备/协议栈**立刻**就可能触发通知。
若此时 `f_owner.pid` 还是 NULL，通知会被**静默丢弃** ——
`fcntl()` 返回 0，没有任何 errno，也没有任何日志。

> ⚠️ 这类"返回成功但没生效"的问题最难排查，因为**所有系统调用都成功了**。
> 排查手法：`F_GETOWN` 回读确认属主真的设上了。
</details>

**Q3.** `fcntl(fd, F_SETFL, O_ASYNC)` 内部是怎么设置 `FASYNC` 标志位的？如果设备不支持异步通知会怎样？

<details>
<summary>答案</summary>

**`setfl()` 自己不设 FASYNC 位。** 看掩码：

```c
/* fs/fcntl.c:35 */
#define SETFL_MASK (O_APPEND | O_NONBLOCK | O_NDELAY | O_DIRECT | O_NOATIME)
```

`FASYNC` **不在** `SETFL_MASK` 里，所以 `:81` 的赋值不会碰它。
真正的置位在驱动的 `->fasync()` 回调尽头：

```c
/* fs/fcntl.c:934 —— fasync_insert_entry() */
	filp->f_flags |= FASYNC;
```

**为什么要绕这一圈？** 因为开启异步通知要**分配 `fasync_struct` 并挂进队列**，
可能失败（`-ENOMEM`）。若先置位再分配，失败后标志位就与事实不符了。
源码把这写成铁律（`:908-910`）：

```c
/*
 * NOTE! It is very important that the FASYNC flag always
 * match the state "is the filp on a fasync list".
 */
```

**如果 `f_op->fasync` 为 NULL（设备不支持）**：

```c
	if (((arg ^ filp->f_flags) & FASYNC) && filp->f_op->fasync) {
```

判空让整个 if 跳过 → **`fcntl()` 返回 0（成功），但什么都没发生**。
这是最隐蔽的失败模式：开了但没真开，且无报错。
</details>
</details>

**Q5.** ⭐ 内核真的每来一个包就发一次 `SIGIO` 吗？描述 `sock_wake_async()` 里的两道闸门。

<details>
<summary>答案</summary>

**不是。** `sock_wake_async()`（`net/socket.c`）里有两道闸门主动抑制重复通知：

```c
int sock_wake_async(struct socket_wq *wq, int how, int band)
{
	if (!wq || !wq->fasync_list)
		return -1;

	switch (how) {
	case SOCK_WAKE_WAITD:
		if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
			break;                    /* 闸门 B：位已置 → 不发 */
		goto call_kill;
	case SOCK_WAKE_SPACE:
		if (!test_and_clear_bit(SOCKWQ_ASYNC_NOSPACE, &wq->flags))
			break;                    /* 闸门 A：不欠账 → 不发 */
		fallthrough;
	case SOCK_WAKE_IO:
call_kill:
		kill_fasync(&wq->fasync_list, SIGIO, band);
		break;
	case SOCK_WAKE_URG:
		kill_fasync(&wq->fasync_list, SIGURG, band);
	}

	return 0;
}
```

**闸门 A（可写方向）`SOCKWQ_ASYNC_NOSPACE` —— 记账式 / 边沿触发**

- 置位（欠账）：`sock_alloc_send_pskb()` `net/core/sock.c:2786`、
  `tcp_poll()` `net/ipv4/tcp.c:569`（注释 `/* send SIGIO later */`）
- 消费：`test_and_clear_bit()` —— **只有真欠账才发，发完清账**
- → 语义是「**可写 → 不可写 → 可写**」跃变才通知一次，缓冲区一直可写一个都不发

**闸门 B（可读方向）`SOCKWQ_ASYNC_WAITDATA` —— 在场者抑制**

- 置位点**只在阻塞等待路径**：`sk_wait_data()` `net/core/sock.c:3019-3029`
  （`sk_set_bit` 进 / `sk_clear_bit` 出）
- → 这个位的真名该叫「**有人正在阻塞等数据**」
- 位已置 → 某人卡在读里、自己会被唤醒 → 不发信号

<details>
<summary>按 v6.6 修订/补充</summary>

原笔记（扩写前）的说法是「主要用于 UDP socket（**TCP 的信号过于频繁**）」。
按 v6.6 源码，这个说法**不精确** —— 频繁与否不取决于 TCP/UDP，
而取决于**是否 `O_NONBLOCK`**：

| socket 模式 | 闸门 B 状态 | SIGIO 行为 |
|------------|------------|-----------|
| 阻塞 + 线程卡在读 | 置位 | ❌ **几乎收不到** |
| 阻塞 + 线程没在读 | 未置 | ✅ 每个报文一次 |
| **非阻塞** + 事件循环 | **永远未置** | ✅✅ 每个报文一次 ← "过于频繁"的真正来源 |

所以建立流程里「设 `O_NONBLOCK`」这一步的真实作用是
**让闸门 B 永远处于开启状态，保证通知不被抑制**，
而不只是"避免 read 阻塞"这种泛泛理由。
</details>
</details>

**Q6.** ⭐ 一个**阻塞** socket 配 `O_ASYNC` 会怎样？这是合理的组合吗？

<details>
<summary>答案</summary>

**不合理，几乎收不到通知。**

`SOCKWQ_ASYNC_WAITDATA` 只在 `sk_wait_data()` 里被置位，
而 `sk_wait_data()` 是**阻塞等待**路径：

```c
/* net/core/sock.c:3019 */
int sk_wait_data(struct sock *sk, long *timeo, const struct sk_buff *skb)
{
	DEFINE_WAIT_FUNC(wait, woken_wake_function);
	int rc;

	add_wait_queue(sk_sleep(sk), &wait);
	sk_set_bit(SOCKWQ_ASYNC_WAITDATA, sk);        /* ← 进阻塞前置位 */
	rc = sk_wait_event(sk, timeo, skb_peek_tail(&sk->sk_receive_queue) != skb, &wait);
	sk_clear_bit(SOCKWQ_ASYNC_WAITDATA, sk);      /* ← 出阻塞后清零 */
	remove_wait_queue(sk_sleep(sk), &wait);
	return rc;
}
```

而发送侧：

```c
	case SOCK_WAKE_WAITD:
		if (test_bit(SOCKWQ_ASYNC_WAITDATA, &wq->flags))
			break;      /* 有人在阻塞等 → 不发，他自己会被唤醒 */
```

**逻辑是自洽的**：线程既然已经卡在 `read()` 里等数据，
内核会直接 `wake_up_interruptible_sync_poll()` 唤醒它（见 `sock_def_readable()` `:3323`），
再额外发一个 `SIGIO` 就是纯粹的浪费。

> 🔑 所以「阻塞 socket + `O_ASYNC`」是**自相矛盾的组合**：
> 一边阻塞等、一边要异步通知，闸门 B 会让通知几乎不出现。
> 这也解释了为什么所有信号驱动 I/O 的示例代码都同时设 `O_NONBLOCK`。
</details>
</details>

**Q8.** 用 `F_SETSIG` 选信号时，选哪些会导致 `si_code` 退化？为什么？

<details>
<summary>答案</summary>

选 **有专属 `si_code` 取值空间**的信号会导致退化：

```c
			if ((signum != SIGPOLL) && sig_specific_sicodes(signum))
				si.si_code = SI_SIGIO;
```

`sig_specific_sicodes()` 查的掩码（`include/linux/signal.h:437-442`）：

```c
#define SIG_SPECIFIC_SICODES_MASK (\
	rt_sigmask(SIGILL)    |  rt_sigmask(SIGFPE)    | \
	rt_sigmask(SIGSEGV)   |  rt_sigmask(SIGBUS)    | \
	rt_sigmask(SIGTRAP)   |  rt_sigmask(SIGCHLD)   | \
	rt_sigmask(SIGPOLL)   |  rt_sigmask(SIGSYS)    | \
	SIGEMT_MASK                                    )
```

**黑名单**：`SIGILL` / `SIGFPE` / `SIGSEGV` / `SIGBUS` / `SIGTRAP` /
`SIGCHLD` / `SIGSYS` / `SIGEMT`（以及非 `SIGPOLL` 时的 `SIGPOLL`）。

**原因**：这些信号已有自己的 `si_code` 语义（如 `SIGSEGV` 的 `SEGV_MAPERR`），
`POLL_IN`（= 1）这种值会与之冲突。内核把 `si_code` 改成 `SI_SIGIO`（= -5）来消除歧义。

**代价**：丢失事件类型信息，用户态只能去看 `si_band`。

> ✅ **实践结论**：`F_SETSIG` 选普通实时信号（`SIGRTMIN + n`）。
> 顺带：实时信号**号越小投递优先级越高**，所以 `SIGRTMIN` 既排队又优先级最高。
</details>

**Q9.** `si_band` 的值是怎么算出来的？为什么内核要存一张 `band_table`？

<details>
<summary>答案</summary>

**两级映射**。

**第一级**：`band_table[]` 把紧凑的事件编号翻译成内核内部的 `EPOLL*` 位掩码：

```c
/* fs/fcntl.c:692 */
static const __poll_t band_table[NSIGPOLL] = {
	EPOLLIN | EPOLLRDNORM,			/* POLL_IN  = 1 */
	EPOLLOUT | EPOLLWRNORM | EPOLLWRBAND,	/* POLL_OUT = 2 */
	EPOLLIN | EPOLLRDNORM | EPOLLMSG,		/* POLL_MSG = 3 */
	EPOLLERR,				/* POLL_ERR = 4 */
	EPOLLPRI | EPOLLRDBAND,			/* POLL_PRI = 5 */
	EPOLLHUP | EPOLLERR			/* POLL_HUP = 6 */
};
```

（`NSIGPOLL == 6`，`include/uapi/asm-generic/siginfo.h:301`）

**第二级**：`mangle_poll()` 把 `EPOLL*` 位翻成用户态的 `POLL*` 位（`__u16`）：

```c
/* include/linux/poll.h */
static inline __u16 mangle_poll(__poll_t val)
{
	__u16 v = (__force __u16)val;
#define M(X) __MAP(v, (__force __u16)EPOLL##X, POLL##X)
	return M(IN) | M(OUT) | M(PRI) | M(ERR) | M(NVAL) |
		M(RDNORM) | M(RDBAND) | M(WRNORM) | M(WRBAND) |
		M(HUP) | M(RDHUP) | M(MSG);
#undef M
}
```

**为什么要这么绕？** 因为内核内部统一用 `EPOLL*` 位（`__poll_t`，`poll` 回调的返回类型），
而 POSIX 的 `SIGIO` 约定 `si_band` 用 `POLL*` 位。两套编码**位值不同**，必须转换。
反向转换是 `demangle_poll()`。

⚠️ **两个易错点**：

1. `POLL_HUP` 映射成 `EPOLLHUP | EPOLLERR` —— **挂断同时带错误位**，
   处理 `si_band` 时不能只判 `POLLHUP`
2. 转换后是 `__u16`，只覆盖 12 个位（`IN/OUT/PRI/ERR/NVAL/RDNORM/RDBAND/WRNORM/WRBAND/HUP/RDHUP/MSG`），
   `EPOLL*` 里超出这个范围的位**会被丢掉**
</details>
</details>
