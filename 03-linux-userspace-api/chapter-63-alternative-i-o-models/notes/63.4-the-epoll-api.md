## 本节讲什么

`epoll` 是 Linux 的高性能 I/O 多路复用机制。本节回答四层问题：

1. **接口层**：6 个 syscall 各自是什么关系（不止"三件套"）
2. **机制层**：内核里到底用什么数据结构撑起它 —— 红黑树、就绪链表、以及一个常被忽略的 `ovflist`
3. **语义层**：水平触发 / 边沿触发 / oneshot 三种模式在**代码上**差在哪一行
4. **工程层**：HFT 低延迟场景下的精度、惊群、选型陷阱

> 🔗 **本篇只讲 epoll API 与实现**；`io_uring` 作为现代替代方案主场在
> [12.5 现代网络](../../../12.5-modern-networking/)（该模块 io_uring 命中 121 处）。

## 要点

### 1. 不是"三件套"，是 6 个 syscall

教科书常说 epoll 有 3 个函数，实际 v6.6 的 `fs/eventpoll.c` 里注册了 **6 个**：

| syscall | 定义位置 | 签名要点 | 用途 |
|---------|---------|---------|------|
| `epoll_create1` | `:2073` `SYSCALL_DEFINE1` | `(int flags)` | **推荐**。flags 仅接受 `EPOLL_CLOEXEC` |
| `epoll_create` | `:2078` `SYSCALL_DEFINE1` | `(int size)` | 历史遗留，**`size` 参数已被忽略** |
| `epoll_ctl` | `:2267` `SYSCALL_DEFINE4` | `(epfd, op, fd, event*)` | 增 / 删 / 改监听 |
| `epoll_wait` | `:2325` `SYSCALL_DEFINE4` | `(epfd, events, maxevents, timeout)` | 等待事件，**timeout 单位毫秒** |
| `epoll_pwait` | `:2359` `SYSCALL_DEFINE6` | 多 `sigmask, sigsetsize` | 原子地替换信号掩码再等待 |
| `epoll_pwait2` | `:2370` `SYSCALL_DEFINE6` | timeout 是 `struct __kernel_timespec *` | **纳秒精度超时**（v5.11+） |

```c
/* fs/eventpoll.c:2370 */
SYSCALL_DEFINE6(epoll_pwait2, int, epfd, struct epoll_event __user *, events,
		int, maxevents, const struct __kernel_timespec __user *, timeout,
		const sigset_t __user *, sigmask, size_t, sigsetsize)
{
	struct timespec64 ts, *to = NULL;
	if (timeout) {
		if (get_timespec64(&ts, timeout))
			return -EFAULT;
		to = &ts;
		if (poll_select_set_timeout(to, ts.tv_sec, ts.tv_nsec))
			return -EINVAL;
	}
	return do_epoll_pwait(epfd, events, maxevents, to, sigmask, sigsetsize);
}
```

**为什么要有 `pwait`？** 因为「设置信号掩码 → 调用 epoll_wait」这两步之间，
信号可能在掩码生效**之前**到达并被丢弃（经典竞态）。`pwait` 把两步合成一个原子 syscall。
`pwait2` 再进一步把毫秒改成 `timespec`。

> ⚠️ `epoll_pwait` 名字里的 `p` 是 "pselect-style signal mask"，**不是** "poll"。

### 2. `epoll_create1` 的 flags 只有一种合法值

```c
/* fs/eventpoll.c:2030-2039 */
static int do_epoll_create(int flags)
{
	/* Check the EPOLL_* constant for consistency.  */
	BUILD_BUG_ON(EPOLL_CLOEXEC != O_CLOEXEC);

	if (flags & ~EPOLL_CLOEXEC)
		return -EINVAL;
	...
```

- `BUILD_BUG_ON(EPOLL_CLOEXEC != O_CLOEXEC)` —— **编译期断言**：`EPOLL_CLOEXEC` 的值
  必须等于 `O_CLOEXEC`。头文件里确实如此：`uapi:23` `#define EPOLL_CLOEXEC O_CLOEXEC`
- `flags & ~EPOLL_CLOEXEC` → 传任何其他 flag 直接 **`-EINVAL`**
- 传 `0` 合法（不设 CLOEXEC）

### 3. `epoll_ctl` 的 op：只有 3 个，没有第 4 个

```c
/* include/uapi/linux/eventpoll.h:25-28 */
/* Valid opcodes to issue to sys_epoll_ctl() */
#define EPOLL_CTL_ADD 1
#define EPOLL_CTL_DEL 2
#define EPOLL_CTL_MOD 3
```

| op | 值 | 作用 |
|----|----|----|
| `EPOLL_CTL_ADD` | 1 | 添加 fd 到监听集合 |
| `EPOLL_CTL_DEL` | 2 | 移除 |
| `EPOLL_CTL_MOD` | 3 | 修改监听事件掩码 |

> ⚠️ **没有 `EPOLL_CTL_DISABLE`** —— v6.6 的 `fs/eventpoll.c` 与 uapi 头文件里
> **`EPOLL_CTL_DISABLE` 均 0 处命中**。网上一些旧资料提到的这个 op 在当前内核已不存在。
> 想临时禁用某个 fd，正确做法是用 `EPOLLONESHOT` 或 `EPOLL_CTL_MOD` 改掩码。

`epoll_ctl` 的实现（`:2267`）只对「需要 event 参数的 op」做 `copy_from_user`：

```c
if (ep_op_has_event(op) &&
    copy_from_user(&epds, event, sizeof(struct epoll_event)))
	return -EFAULT;
```

### 4. 事件位全表（含两个"高位"新/内部标志）

```c
/* include/uapi/linux/eventpoll.h:31-42 */
#define EPOLLIN		(__force __poll_t)0x00000001
#define EPOLLPRI	(__force __poll_t)0x00000002
#define EPOLLOUT	(__force __poll_t)0x00000004
#define EPOLLERR	(__force __poll_t)0x00000008
#define EPOLLHUP	(__force __poll_t)0x00000010
#define EPOLLNVAL	(__force __poll_t)0x00000020
#define EPOLLRDNORM	(__force __poll_t)0x00000040
#define EPOLLRDBAND	(__force __poll_t)0x00000080
#define EPOLLWRNORM	(__force __poll_t)0x00000100
#define EPOLLWRBAND	(__force __poll_t)0x00000200
#define EPOLLMSG	(__force __poll_t)0x00000400
#define EPOLLRDHUP	(__force __poll_t)0x00002000
```

**注意 `0x800` 是空的** —— 从 `0x400`（`EPOLLMSG`）直接跳到 `0x2000`（`EPOLLRDHUP`）。

高位（bit 27–31）是**行为修饰符**，不是 I/O 事件：

| 标志 | 值 | 引入 | 说明 |
|------|----|----|------|
| `EPOLL_URING_WAKE` | `1U << 27` | io_uring 时代 | **内部标志**（uapi:45-48 注释写明 "Internal flag"），io_uring 用它检测递归回到自己的 poll handler |
| `EPOLLEXCLUSIVE` | `1U << 28` | **v4.5** | 独占唤醒，解决惊群 |
| `EPOLLWAKEUP` | `1U << 29` | — | 阻止系统挂起，**需要 `CAP_BLOCK_SUSPEND`** |
| `EPOLLONESHOT` | `1U << 30` | — | 触发一次后自动禁用 |
| `EPOLLET` | `1U << 31` | — | 边沿触发 |

> 🔑 **`EPOLLERR` / `EPOLLHUP` 无需注册也会上报** —— 它们是 `ep_item_poll()`
> 每次调用时由底层 `file->f_op->poll()` 返回的，不受注册掩码控制。所以即使只注册
> `EPOLLIN`，对端关闭连接时照样会收到 `EPOLLIN | EPOLLRDHUP`。

### 5. `struct epoll_event` 只有 12 字节 —— 因为 x86-64 上被 packed

```c
/* include/uapi/linux/eventpoll.h:71-86 */
/*
 * On x86-64 make the 64bit structure have the same alignment as the
 * 32bit structure. This makes 32bit emulation easier.
 *
 * UML/x86_64 needs the same packing as x86_64
 */
#ifdef __x86_64__
#define EPOLL_PACKED __attribute__((packed))
#else
#define EPOLL_PACKED
#endif

struct epoll_event {
	__poll_t events;   /* 32 位 */
	__u64 data;        /* 64 位 */
} EPOLL_PACKED;
```

| 布局 | `events` | `data` | `sizeof` |
|------|---------|-------|---------|
| 未 packed（64 位默认对齐） | 4B + 4B padding | 8B（8 字节对齐） | **16** |
| **packed（x86-64 实际）** | 4B | 8B（紧跟，无 padding） | **12** |

**为什么要 packed？** 32 位程序里 `__u64` 只有 4 字节对齐，结构体就是 12 字节；
64 位程序里按默认规则会变成 16 字节。两个 ABI 不一致会让 **32 位兼容层（compat）很难受**。
于是 x86-64 上强制 packed，让两者都是 12 字节。

> 📌 这个 12 字节直接决定了 `EP_MAX_EVENTS`（见第 9 节）。

### 6. 内核里的两个核心结构体

#### `struct eventpoll`（`fs/eventpoll.c:178`）—— 一个 epoll 实例

```c
struct eventpoll {
	struct mutex mtx;              /* :185 保护 file 不被移除；ctl / 收集循环 / 清理路径持有 */
	wait_queue_head_t wq;          /* :188 sys_epoll_wait() 用的等待队列 */
	wait_queue_head_t poll_wait;   /* :191 file->poll() 用的等待队列（嵌套 epoll 时用） */
	struct list_head rdllist;      /* :194 就绪 fd 链表 */
	rwlock_t lock;                 /* :197 保护 rdllist 和 ovflist */
	struct rb_root_cached rbr;     /* :200 监听 fd 的红黑树根 */
	struct epitem *ovflist;        /* :207 传输事件期间的无锁溢出单链表 */
	struct wakeup_source *ws;      /* :210 ep_scan_ready_list 运行时用 */
	struct user_struct *user;      /* :212 创建者，用于 max_user_watches 配额 */
	struct file *file;             /* :214 */
	u64 gen;                       /* :217 循环检测优化 */
	struct hlist_head refs;
	refcount_t refcount;           /* :228 与 epitem->dying 配合做销毁编排 */
#ifdef CONFIG_NET_RX_BUSY_POLL
	unsigned int napi_id;          /* :232 busy poll 的 napi_id 跟踪 */
#endif
#ifdef CONFIG_DEBUG_LOCK_ALLOC
	u8 nests;                      /* :236 lockdep 校验唤醒嵌套 */
#endif
};
```

**注意 `rb_root_cached`**（不是普通的 `rb_root`）—— 它在红黑树根之外额外缓存了
**最左节点**，让"取最小值"变成 O(1)。epoll 用它做遍历与循环检测优化。

#### `struct epitem`（`:130`）—— 一个被监听的 fd

```c
struct epitem {
	union {
		struct rb_node rbn;        /* :133 挂到 eventpoll 红黑树 */
		struct rcu_head rcu;       /* :134 释放时复用同一块内存 */
	};
	struct list_head rdllink;      /* :139 挂到就绪链表 rdllist */
	struct epitem *next;           /* :145 挂到 ovflist 单链表 */
	struct epoll_filefd ffd;       /* :148 fd + file 二元组 */
	bool dying;                    /* :155 已从 file 的 items 链表摘除，待释放 */
	struct eppoll_entry *pwqlist;  /* :158 poll 等待队列链表 */
	struct eventpoll *ep;          /* :160 所属的 eventpoll */
	...
	struct epoll_event event;      /* 用户注册的事件掩码 + data */
};
```

> 🔑 `rbn` 和 `rcu` 是 **union** —— 一个 epitem 要么在红黑树里，要么正在被 RCU 释放，
> 不可能同时。这是内核常见的省内存技巧（同一个技巧在 `struct epitem` 的
> `rdllink` / `next` 上没有复用，因为它们可能同时挂在两个链表上）。

### 7. 三大数据结构如何协作

```
                    ┌─────────────────────────────────────┐
                    │        struct eventpoll             │
                    ├─────────────────────────────────────┤
                    │  rbr   (rb_root_cached)             │  ← 监听全集（红黑树）
                    │  rdllist (list_head)                │  ← 就绪集合（双链表）
                    │  ovflist (epitem*)                  │  ← 扫描期溢出（无锁单链表）
                    │  lock  (rwlock_t)                   │  ← 保护上面两个 list
                    │  mtx   (mutex)                      │  ← 保护 ctl 与收集循环
                    └─────────────────────────────────────┘
                              │                    ▲
              epoll_ctl ADD ──┘                    │ 就绪时回调
              （O(log n) 插入）                      │
                              ▼                    │
                     ┌────────────────┐    ┌───────────────────┐
                     │  struct epitem │───▶│ ep_poll_callback  │
                     │  rbn / rdllink │    │  (挂在 file 的     │
                     │  next / event  │    │   wait queue 上)   │
                     └────────────────┘    └───────────────────┘
```

关键分工：

| 结构 | 存什么 | 谁写 | 复杂度 |
|------|-------|------|-------|
| `rbr` 红黑树 | **所有**被监听的 fd | `epoll_ctl` | 插入/删除 O(log n) |
| `rdllist` | **当前就绪**的 fd | `ep_poll_callback`（生产）、`ep_send_events`（消费） | 取一个 O(1) |
| `ovflist` | 扫描期间新就绪的 fd | `ep_poll_callback`（无锁） | 头插 O(1) |

### 8. 回调：`ep_poll_callback`（`:1167`）—— 五步判定

当被监听的 fd 状态变化，内核通过 `file->f_op->poll()` 注册的等待队列回调到这里：

```c
static int ep_poll_callback(wait_queue_entry_t *wait, unsigned mode, int sync, void *key)
{
	struct epitem *epi = ep_item_from_wait(wait);
	struct eventpoll *ep = epi->ep;
	__poll_t pollflags = key_to_poll(key);

	read_lock_irqsave(&ep->lock, flags);          /* ① 读锁 + 关中断 */

	/* ② EPOLLONESHOT 禁用判定 */
	if (!(epi->event.events & ~EP_PRIVATE_BITS))
		goto out_unlock;

	/* ③ 事件过滤（key 可能为 NULL，此时不过滤） */
	if (pollflags && !(pollflags & epi->event.events))
		goto out_unlock;

	/* ④⑤ 决定挂到 rdllist 还是 ovflist */
	if (READ_ONCE(ep->ovflist) != EP_UNACTIVE_PTR) {
		if (chain_epi_lockless(epi))             /* ⑤a 扫描中 → 无锁挂 ovflist */
			ep_pm_stay_awake_rcu(epi);
	} else if (!ep_is_linked(epi)) {
		if (list_add_tail_lockless(&epi->rdllink, &ep->rdllist))  /* ⑤b 常态 */
			ep_pm_stay_awake_rcu(epi);
	}
	...
```

几个要点：

- **① `read_lock_irqsave`**：用的是 `rwlock_t` 的**读侧**，因为回调可能并发发生（多个 fd 同时就绪），
  读侧可以并行；只有 `ep_send_events` 的扫描路径才需要写侧。
- **② `~EP_PRIVATE_BITS`**：把私有位（ONESHOT/ET/EXCLUSIVE/WAKEUP 等）去掉后，
  如果剩下的事件掩码为 **0**，说明这个 epitem 被 `EPOLLONESHOT` 清空过 → 直接忽略。
- **③ `pollflags && ...` 的短路**：注释（`:1189-1193`）明确说「并非所有设备都在 `key`
  里上报事件」，所以 `key == NULL` 时**跳过过滤**，全部当作就绪。
- **④⑤ 无锁**：`chain_epi_lockless` / `list_add_tail_lockless` 都是 lockless 版本，
  这正是 epoll 可扩展的关键。

### 9. `ovflist` 三态：为什么传输事件时不用持锁

`ep->ovflist` 有三个状态：

| 值 | 含义 | 回调行为 |
|----|------|---------|
| `EP_UNACTIVE_PTR`（`(void *) -1L`，`:96`） | **常态** | 直接入 `rdllist` |
| `NULL` | **正在扫描**（`ep_start_scan` 设置） | 无锁挂到 `ovflist` 单链表 |
| 链表头指针 | 有溢出事件待回收 | 同上，继续挂 |

```c
/* fs/eventpoll.c:616 */
static void ep_start_scan(struct eventpoll *ep, struct list_head *txlist)
{
	write_lock_irq(&ep->lock);
	list_splice_init(&ep->rdllist, txlist);   /* "偷走"就绪链表，原链表置空 */
	WRITE_ONCE(ep->ovflist, NULL);            /* 进入扫描态 */
	write_unlock_irq(&ep->lock);
}
```

```c
/* fs/eventpoll.c:633 */
static void ep_done_scan(struct eventpoll *ep, struct list_head *txlist)
{
	write_lock_irq(&ep->lock);
	/*
	 * ovflist 是 LIFO（头插），这里用 list_add 头插回 rdllist 实现反转 → 保持 FIFO
	 */
	for (nepi = READ_ONCE(ep->ovflist); (epi = nepi) != NULL;
	     nepi = epi->next, epi->next = EP_UNACTIVE_PTR) {
		if (!ep_is_linked(epi)) {
			list_add(&epi->rdllink, &ep->rdllist);
			ep_pm_stay_awake(epi);
		}
	}
	WRITE_ONCE(ep->ovflist, EP_UNACTIVE_PTR);  /* 恢复常态 */
	list_splice(txlist, &ep->rdllist);         /* 未处理完的重新注入 */
	__pm_relax(ep->ws);
	write_unlock_irq(&ep->lock);
}
```

**为什么要这么绕？** 因为 `ep_send_events` 在遍历就绪链表时要做两件
**不能持锁**的事：

1. 调用 `ep_item_poll(epi, &pt, 1)` —— 可能触发驱动代码，耗时不可控
2. `epoll_put_uevent()` 拷贝数据到**用户空间** —— 可能缺页、可能被信号打断

如果全程持有 `ep->lock`，一个慢速 fd 会阻塞所有其他 CPU 上的回调。
`ovflist` 让回调**在无锁情况下**照样能入队，扫描结束后一次性回收。

> 📌 **LIFO → FIFO 反转**是个容易忽略的细节：ovflist 用头插（LIFO），
> 回收时也用 `list_add` 头插回 rdllist，两次反转抵消，最终保持 FIFO 顺序。

### 10. ⭐ LT / ET / ONESHOT 的唯一分叉点（`ep_send_events`，`:1745-1755`）

这是整篇最重要的一段代码 —— 三种触发模式的差异**全在这里**：

```c
/* fs/eventpoll.c:1676 ep_send_events() 循环体内 */
res++;
if (epi->event.events & EPOLLONESHOT)
	epi->event.events &= EP_PRIVATE_BITS;        /* ① ONESHOT：清空事件掩码 */
else if (!(epi->event.events & EPOLLET)) {
	/*
	 * ② LT：重新插回就绪链表，下次 epoll_wait 会再检查一次
	 */
	list_add_tail(&epi->rdllink, &ep->rdllist);
	ep_pm_stay_awake(epi);
}
/* ③ ET：什么都不做 —— 已经从 rdllist 摘掉了，不回来 */
```

| 模式 | 这行代码做什么 | 后果 |
|------|--------------|------|
| **ET** | 无操作 | 已 `list_del_init` 从 rdllist 摘除，**不回来**。下次只靠 `ep_poll_callback` 重新入队 |
| **LT** | `list_add_tail` 回 rdllist | 下次 `epoll_wait` **再检查一次** |
| **ONESHOT** | `events &= EP_PRIVATE_BITS` | 事件掩码清零 → `ep_poll_callback` 第②步直接 return，直到 `EPOLL_CTL_MOD` 重新武装 |

> 🔑 **ONESHOT 的"禁用"不是移除监听，只是把事件掩码清空**。
> epitem 还留在红黑树里，直到 `EPOLL_CTL_MOD` 重新设置掩码。

同一个循环里还有两个关键行为：

```c
list_del_init(&epi->rdllink);                /* 先摘下来 */
revents = ep_item_poll(epi, &pt, 1);         /* 重新 poll 一次，确认真的就绪 */
if (!revents)
	continue;                                /* 已不就绪 → 不报告，也不重新入队 */
```

> ⚠️ **即使是 LT 模式、fd 已经在就绪链表上，内核还是会重新 `poll()` 一次**。
> 如果这次 poll 返回 0（比如数据已被别的线程读走），就 `continue` —— 既不报告用户，
> 也不会因为 LT 重新入队。这解释了"为什么 LT 下 fd 状态变了就不再重复报"。

以及开头的短路：

```c
/* Always short-circuit for fatal signals to allow threads to make a
 * timely exit without the chance of finding more events available and
 * fetching repeatedly. */
if (fatal_signal_pending(current))
	return -EINTR;
```

### 11. `ep_modify` 里的教科书级并发细节（`:1598`）

修改一个 fd 的监听掩码时，内核**先改掩码、再 poll**：

```c
static int ep_modify(struct eventpoll *ep, struct epitem *epi,
		     const struct epoll_event *event)
{
	/*
	 * Set the new event interest mask before calling f_op->poll();
	 * otherwise we might miss an event that happens between the
	 * f_op->poll() call and the new event set registering.
	 */
	epi->event.events = event->events;   /* need barrier below */
	epi->event.data = event->data;       /* protected by mtx */

	smp_mb();                            /* ← 关键内存屏障 */

	if (ep_item_poll(epi, &pt, 1)) {
		write_lock_irq(&ep->lock);
		if (!ep_is_linked(epi)) {
			list_add_tail(&epi->rdllink, &ep->rdllist);
			...
```

那句 `smp_mb()` 注释（`:1622-1638`）说得很清楚，它有两个作用：

1. **把 epi 的改动刷到其他 CPU** —— 因为改 `epi->event.events` 时**没有**持 `ep->lock`，
   而 `ep_poll_callback` 是持 `ep->lock` 的，需要屏障保证它看到新掩码，否则可能漏事件
2. **确保不漏"过去"的事件** —— 这个屏障与 `wq_has_sleeper()` 里的屏障配对

> 📌 这类"改状态与 poll 的顺序 + 配对屏障"是内核并发正确性的经典范式，
> 和 05 模块 [Ch4.4 休眠与唤醒](../../../05-linux-kernel/chapter-04-process-scheduling/notes/section-4.4-休眠与唤醒.md)
> 里「先入队再查条件」是同一类问题：**防止丢失唤醒/事件**。

### 12. 复杂度真相：epoll 并不是"O(1)"

> ⚠️ **按 v6.6 源码修订**：常见的"epoll 是 O(1)"说法过于笼统，需要按操作拆开看。

| 操作 | 复杂度 | 依据 |
|------|-------|------|
| `epoll_ctl(ADD/DEL/MOD)` | **O(log n)** | `rbr` 是红黑树（`rb_root_cached`） |
| `epoll_wait` 取回 k 个就绪事件 | **O(k)** + 常数 | 遍历 `rdllist` 前 k 个 |
| `epoll_wait` 判断是否无事件 | **O(1)** | 只需看 `rdllist` 是否为空 |
| 每个 epitem 的就绪判定 | O(1) | 回调直接挂链表 |

**epoll 相对 select/poll 的真正优势不是"O(1)"，而是：**

1. **无需每次重复传递 fd 集合** —— select/poll 每次调用都要把整个 fd 数组从用户态拷到内核态，
   epoll 的监听集合由内核长期持有（`rbr`）
2. **返回的都是就绪的** —— select/poll 返回后用户还得 O(n) 遍历一遍找出谁就绪；
   epoll 只把就绪的拷回来
3. **就绪通知是事件驱动的** —— 靠回调挂链表，不是每次调用时轮询所有 fd

select/poll 的开销是 **O(总 fd 数)**，epoll 是 **O(就绪 fd 数)**。
当总 fd 很多而每轮就绪很少时（典型的高并发空闲连接场景），差距才体现出来。

### 13. 限制与常量

| 常量 | 位置 | 值 | 说明 |
|------|------|----|------|
| `EP_MAX_NESTS` | `:93` | **4** | epoll 嵌套监听的最大深度 |
| `EP_MAX_EVENTS` | `:95` | `INT_MAX / sizeof(struct epoll_event)` = **178,956,970** | `maxevents` 上限 |
| `EP_UNACTIVE_PTR` | `:96` | `(void *) -1L` | ovflist 常态哨兵 |
| `EP_ITEM_COST` | `:99` | `sizeof(epitem) + sizeof(eppoll_entry)` | 每个监听项的内存成本 |
| `max_user_watches` | `:248` | 见下 | **每用户**可监听的总数上限 |

**嵌套深度限制**（`:1361`、`:1976`）：

```c
if (depth > EP_MAX_NESTS)   /* too deep nesting */
```

即：epoll A 监听 epoll B，B 监听 C……最多 **4 层**。超过就拒绝。
注释（`:491`）说明这是为了避免递归时的无限循环和资源消耗。

> 📌 这个限制也和 epoll 的循环检测有关 —— `eventpoll` 里的 `u64 gen`（`:217`）
> 就是用于"优化 loop detection check"的。

**`max_user_watches` 怎么算出来的**（`:2455-2456`）：

```c
max_user_watches = (((si.totalram - si.totalhigh) / 25) << PAGE_SHIFT) /
	EP_ITEM_COST;
```

即：**可用内存的 1/25，除以每个监听项的成本**。默认约等于总内存的 4% 能用于 epoll 监听。
超过后 `epoll_ctl(ADD)` 返回 **`-ENOSPC`**（`:1492`）。

运行时可通过 sysctl 调整（`:317`）：

```bash
cat /proc/sys/fs/epoll/max_user_watches
```

> ⚠️ 注意这是**每 uid** 的配额（`:212` `struct user_struct *user`），不是每进程。
> 用同一个 uid 跑多个服务时容易撞到这个上限。

### 15. 与 select / poll 的对比

| | select | poll | epoll |
|--|--------|------|-------|
| fd 上限 | 1024（`FD_SETSIZE`） | 无限制 | 无限制（受 `max_user_watches`） |
| 每次调用的拷贝 | 整个 `fd_set` | 整个 `pollfd` 数组 | **无**（集合常驻内核） |
| 内核侧复杂度 | O(总 fd) | O(总 fd) | O(就绪 fd) |
| 返回后用户侧 | 需 O(n) 遍历找就绪 | 需 O(n) 遍历 | **只返回就绪的** |
| 触发模式 | 仅 LT | 仅 LT | LT / ET / ONESHOT |
| 超时精度 | 微秒（`timeval`） | 毫秒（int） | 毫秒（int）/ **纳秒（`pwait2`）** |

## HFT / 嵌入式关联

| 关注点 | epoll 的现实 | HFT 含义 |
|--------|-------------|---------|
| **超时精度** | `epoll_wait` 是 **int 毫秒**；`epoll_pwait2` 才是 `timespec` **纳秒** | 需要精确超时控制时用 `epoll_pwait2`（v5.11+），否则毫秒粒度对 HFT 太粗 |
| **syscall 开销** | 每次 `epoll_wait` 都是一次真正的系统调用 | 极致延迟场景会被 `io_uring`（提交/完成环形队列、可轮询无 syscall）取代 |
| **惊群** | 多线程 `epoll_wait` 同一 epfd 时，一个事件可能唤醒所有线程 | 用 **`EPOLLEXCLUSIVE`**（v4.5+）只唤醒一个；或每线程独立 epfd + `SO_REUSEPORT` |
| **busy poll** | `eventpoll` 有 `napi_id` 字段（`CONFIG_NET_RX_BUSY_POLL`，`:231-233`） | 与 `SO_BUSY_POLL` 配合可在软中断前就直接收包，降延迟但吃 CPU |
| **ET + 非阻塞** | ET 必须循环读到 `EAGAIN` | HFT 标准做法：一次事件尽量把数据读完，减少 `epoll_wait` 往返次数 |
| **ONESHOT 多线程** | 触发一次后自动禁用 | 保证同一个 fd 不会被两个线程同时处理，避免加锁 |
| **嵌套 epoll** | 上限 **4 层** | 分层 event loop 设计时别超 |
| **嵌入式** | 无 `EPOLLWAKEUP` 需求时不要设（需要 `CAP_BLOCK_SUSPEND`） | 嵌入式省电场景反而可能要用 `EPOLLWAKEUP` 防止处理中挂起 |

> ⚠️ **HFT 选型提醒**：epoll 是**事件通知**机制，不是零拷贝机制。
> 数据仍要通过 `read()`/`recv()` 从内核拷到用户态。若追求极致，
> 现代替代是 `io_uring`（12.5 模块）或内核旁路（13 DPDK 模块）。

## 代码示例

### 示例 1：ET 模式正确读法（循环到 EAGAIN）

```c
/* ET 模式：必须循环读到 EAGAIN，否则剩余数据要等下一次事件 */
void handle_et_read(int fd) {
    char buf[4096];
    for (;;) {
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n > 0) {
            /* 处理 n 字节 */
            continue;
        }
        if (n == 0) {
            /* EOF：对端关闭 */
            close(fd);
            return;
        }
        /* n < 0 */
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            return;              /* 本次事件数据已读完 —— ET 下必须到这里 */
        if (errno == EINTR)
            continue;            /* 被信号打断，重试 */
        perror("read");
        close(fd);
        return;
    }
}
```

> ⚠️ **ET 下 fd 必须是非阻塞的**。阻塞 fd + ET = 最后一次 `read()` 会永久阻塞
> （因为数据已读完但 ET 不会再通知）。

### 示例 2：`epoll_pwait2` 纳秒超时（v5.11+）

```c
#define _GNU_SOURCE
#include <sys/epoll.h>
#include <signal.h>
#include <stdio.h>

/* glibc 较老版本可能没有 epoll_pwait2 包装，用 syscall() 直接调 */
#include <sys/syscall.h>
#include <unistd.h>

#ifndef SYS_epoll_pwait2
#define SYS_epoll_pwait2 441      /* x86-64 */
#endif

static int my_epoll_pwait2(int epfd, struct epoll_event *ev, int maxev,
                           const struct timespec *to, const sigset_t *sig)
{
    return (int)syscall(SYS_epoll_pwait2, epfd, ev, maxev, to, sig,
                        (size_t)(sig ? sizeof(*sig) : 0));
}

int main(void)
{
    int epfd = epoll_create1(EPOLL_CLOEXEC);   /* 唯一合法的非零 flag */
    if (epfd < 0) { perror("epoll_create1"); return 1; }

    struct epoll_event events[64];
    struct timespec to = { .tv_sec = 0, .tv_nsec = 500000 };  /* 500 微秒 */
    sigset_t mask;
    sigemptyset(&mask);

    int n = my_epoll_pwait2(epfd, events, 64, &to, &mask);
    if (n < 0) { perror("epoll_pwait2"); return 1; }
    printf("%d events ready\n", n);
    return 0;
}
```

### 示例 3：ONESHOT + 多线程（避免加锁）

```c
/* 注册时带 EPOLLONESHOT */
struct epoll_event ev = {
    .events  = EPOLLIN | EPOLLONESHOT,
    .data.fd = cfd,
};
epoll_ctl(epfd, EPOLL_CTL_ADD, cfd, &ev);

/* 工作线程处理完后必须重新武装，否则这个 fd 再也不会被通知 */
void rearm(int epfd, int cfd) {
    struct epoll_event ev = {
        .events  = EPOLLIN | EPOLLONESHOT,
        .data.fd = cfd,
    };
    epoll_ctl(epfd, EPOLL_CTL_MOD, cfd, &ev);   /* MOD 重新武装 */
}
```

> 🔑 重新武装用的是 **`EPOLL_CTL_MOD`**（因为 `EPOLL_CTL_DISABLE` 在 v6.6 不存在），
> 它会走 `ep_modify()` 路径（第 11 节），内部会重新 `poll()` 一次，
> 如果此刻又有数据到了会立刻重新入就绪链表。

**Q1.** epoll 常被说成"O(1) 复杂度"。按 v6.6 源码，这个说法准确吗？三个主要操作各自的复杂度是什么？

<summary>答案</summary>

不准确，需要按操作拆开：

| 操作 | 复杂度 | 依据 |
|------|-------|------|

| `epoll_wait` 取 k 个事件 | **O(k)** | 遍历 `rdllist` 前 k 个 |
| 判断"有无事件" | **O(1)** | 只看 `rdllist` 空否 |

1. 监听集合常驻内核，不必每次调用重传
2. 只返回就绪的 fd，用户侧不用 O(n) 扫描
3. 就绪判定是回调驱动（事件到达时挂链表），不是调用时轮询

select/poll 是 O(总 fd 数)，epoll 是 O(就绪 fd 数)。
</details>

<summary>自测题 2（点击展开）</summary>

**Q2.** 一个 epitem 已经在就绪链表 `rdllist` 上了，`ep_send_events` 会直接把它报告给用户吗？

<details>
<summary>答案</summary>

**不会直接报告** —— 会先摘下来再重新 poll 一次：

```c
list_del_init(&epi->rdllink);
revents = ep_item_poll(epi, &pt, 1);
if (!revents)
	continue;              /* 已不就绪 → 不报告 */
```

`fs/eventpoll.c:1729-1735`。所以"在 rdllist 上"只是**候选**，不代表最终会报告。

这带来一个实际后果：如果数据已被别的线程读走（多线程 LT 场景），
`revents` 为 0，这次不会报告给用户，**也不会因为 LT 重新入队**。
</details>
</details>

<details>
<summary>自测题 3（点击展开）</summary>

**Q3.** `ep->ovflist` 有哪三种状态？为什么需要它？

<details>
<summary>答案</summary>

三态（`EP_UNACTIVE_PTR` 定义在 `:96`，值为 `(void *) -1L`）：

| 值 | 状态 | 回调行为 |
|----|------|---------|
| `EP_UNACTIVE_PTR` | 常态 | 直接 `list_add_tail_lockless` 入 `rdllist` |
| `NULL` | 扫描中（`ep_start_scan` 设置，`:616`） | 无锁 `chain_epi_lockless` 挂到 `ovflist` |
| 链表头 | 有溢出待回收 | 继续挂 |

**为什么需要**：`ep_send_events` 在遍历就绪链表时要做两件不能持锁的事：
1. `ep_item_poll()` 可能触发驱动代码，耗时不可控
2. `epoll_put_uevent()` 拷贝到用户空间，可能缺页

如果全程持有 `ep->lock`，一个慢 fd 会阻塞其他 CPU 上的回调。
ovflist 让回调在无锁情况下照样入队，扫描结束后由 `ep_done_scan`（`:633`）一次性回收。

**额外细节**：ovflist 是 LIFO（头插），回收时用 `list_add` 头插回 rdllist，**两次反转抵消保持 FIFO**。
</details>
</details>

**Q4.** 水平触发（LT）和边沿触发（ET）在内核代码上的差异具体在哪几行？

<details>
<summary>答案</summary>

差异集中在 `ep_send_events()` 的 `fs/eventpoll.c:1745-1755`：

```c
res++;
if (epi->event.events & EPOLLONESHOT)
	epi->event.events &= EP_PRIVATE_BITS;
else if (!(epi->event.events & EPOLLET)) {
	list_add_tail(&epi->rdllink, &ep->rdllist);   /* ← 只有 LT 会执行这行 */
	ep_pm_stay_awake(epi);
}
```

- **ET**：两个分支都不进，epi 已被 `list_del_init` 摘除且不回来 → 只靠下次回调重新入队
- **LT**：执行 `list_add_tail`，插回 rdllist 尾部 → 下次 `epoll_wait` 再检查一次

两者在此之前都会先 `list_del_init(&epi->rdllink)` 摘除。
</details>
</details>

**Q5.** `EPOLLONESHOT` 是怎么实现"触发一次后自动禁用"的？epitem 被移出红黑树了吗？

<details>
<summary>答案</summary>

**没有移出红黑树**，只是清空了事件掩码：

```c
if (epi->event.events & EPOLLONESHOT)
	epi->event.events &= EP_PRIVATE_BITS;      /* 只保留私有位，I/O 事件位清零 */
```

（`:1746-1747`）

配合 `ep_poll_callback` 的第②步判定（`:1186`）：

```c
if (!(epi->event.events & ~EP_PRIVATE_BITS))
	goto out_unlock;        /* 掩码去掉私有位后为空 → 视为已禁用，直接忽略 */
```

于是后续事件到达时回调直接返回，epitem 不再入就绪链表。

重新武装必须用 **`EPOLL_CTL_MOD`**（v6.6 没有 `EPOLL_CTL_DISABLE`），
它会走 `ep_modify()` 重新设置掩码并立即 poll 一次。
</details>

**Q7.** `sizeof(struct epoll_event)` 是多少？为什么 x86-64 上要用 `packed`？

<details>
<summary>答案</summary>

**12 字节**（x86-64 上）。

```c
struct epoll_event {
	__poll_t events;   /* 4 字节 */
	__u64 data;        /* 8 字节 */
} EPOLL_PACKED;        /* x86-64 上 = __attribute__((packed)) */
```

不 packed 的话，64 位下 `__u64 data` 会按 8 字节对齐 → `events` 后补 4 字节 padding → 16 字节。

**为什么 packed**（uapi 头文件 `:71-75` 注释）：
> On x86-64 make the 64bit structure have the same alignment as the
> 32bit structure. This makes 32bit emulation easier.

32 位程序里 `__u64` 只有 4 字节对齐，结构体天然是 12 字节。为了让 32/64 位
ABI 一致（简化 compat 兼容层），x86-64 上强制 packed。

**连带影响**：`EP_MAX_EVENTS = INT_MAX / sizeof(struct epoll_event)`（`:95`）
= `2147483647 / 12` = **178,956,970**（若按 16 字节算则是 134,217,727）。
</details>
</details>

<details>
<summary>答案</summary>

**会发生惊群（thundering herd）**：一个 fd 就绪时，挂在 `ep->wq` 等待队列上的
所有线程都可能被唤醒，但最终只有一个能拿到事件，其余白白被调度。

解决方式有三种：

1. **`EPOLLEXCLUSIVE`**（v4.5+，`1U << 28`）—— 注册时加上，
   唤醒时只唤醒**一个**等待者，而不是全部
2. **`SO_REUSEPORT`** —— 每线程/进程独立 epfd，由内核做负载均衡
3. **`EPOLLONESHOT`** —— 保证同一 fd 在重新武装前只被一个线程处理

> 📌 `EPOLLEXCLUSIVE` 实测：**v4.4 的 `fs/eventpoll.c` 中 0 处命中，v4.5 中 10 处**
> → v4.5 引入。

注意：`EPOLLEXCLUSIVE` **只对 `EPOLL_CTL_ADD` 生效**，对 `MOD` 无效；
且它不改变"谁拿到事件"，只减少无谓唤醒。
</details>
</details>

<summary>自测题 10（点击展开）</summary>

**Q10.** `/proc/sys/fs/epoll/max_user_watches` 的默认值是怎么算出来的？超限后 `epoll_ctl` 返回什么？

<details>
<summary>答案</summary>

**计算方式**（`fs/eventpoll.c:2455-2456`）：

```c
max_user_watches = (((si.totalram - si.totalhigh) / 25) << PAGE_SHIFT) /
	EP_ITEM_COST;
```

其中 `EP_ITEM_COST`（`:99`）= `sizeof(struct epitem) + sizeof(struct eppoll_entry)`。

即：**可用内存（totalram - totalhigh）的 1/25，除以每个监听项的内存成本**。

**超限返回 `-ENOSPC`**（`:1492` 的检查）。

⚠️ 两个易错点：
1. 这是**每 uid** 的配额，不是每进程（`:212` `struct user_struct *user`）。
   同一 uid 下跑多个服务会共享这个额度
2. 计数单位是"监听项"而非"epoll 实例"—— 一个 epfd 里监听 10 万个 fd 就算 10 万
</details>
</details>

<summary>自测题 11（点击展开）</summary>

**Q11.** `ep_modify()` 里为什么**先**设置新的事件掩码、**后**调用 `f_op->poll()`？中间那句 `smp_mb()` 有什么用？

<details>
<summary>答案</summary>

**顺序原因**（`fs/eventpoll.c:1612-1615` 注释）：
> Set the new event interest mask before calling f_op->poll();
> otherwise we might miss an event that happens between the
> f_op->poll() call and the new event set registering.

如果先 poll 后改掩码，那么 poll 返回后、掩码生效前这段时间里到达的事件会丢失。

**`smp_mb()` 的两个作用**（`:1622-1638` 注释）：

1. **把 epi 的改动刷到其他 CPU** —— 改 `epi->event.events` 时**没有**持 `ep->lock`，
   而 `ep_poll_callback` 是持 `ep->lock` 的。屏障保证回调能看到新掩码，否则可能漏事件
2. **确保不漏"过去"的事件** —— 这个屏障与 `wq_has_sleeper()` 里的屏障配对

> 📌 这是内核里典型的"防丢事件"范式，与
> [Ch4.4 休眠与唤醒](../../../05-linux-kernel/chapter-04-process-scheduling/notes/section-4.4-休眠与唤醒.md)
> 里「先把自己加入等待队列、再检查条件」是同一个问题的两种表现。
</details>

<summary>自测题 12（点击展开）</summary>

**Q12.** 下面哪些说法是对的？
① `epoll_ctl` 支持 `EPOLL_CTL_DISABLE`
② `EPOLL_CLOEXEC` 的值等于 `O_CLOEXEC`
③ `EPOLLERR` 需要先注册才会上报
④ `epoll_create(size)` 的 `size` 参数现在还有意义

<details>
<summary>答案</summary>

**只有 ② 对。**

| 说法 | 判定 | 依据 |
|------|------|------|
| ① 支持 `EPOLL_CTL_DISABLE` | ❌ | v6.6 的 `fs/eventpoll.c` 与 uapi 头文件中均 **0 处命中**。合法 op 只有 `ADD=1 / DEL=2 / MOD=3`（uapi `:26-28`） |
| ② `EPOLL_CLOEXEC == O_CLOEXEC` | ✅ | uapi `:23` 直接 `#define EPOLL_CLOEXEC O_CLOEXEC`；且 `:2037` 有编译期断言 `BUILD_BUG_ON(EPOLL_CLOEXEC != O_CLOEXEC)` |
| ③ `EPOLLERR` 需注册 | ❌ | 它由 `ep_item_poll()` 底层返回，不受注册掩码控制。同理 `EPOLLHUP` |
| ④ `epoll_create(size)` 的 size 有意义 | ❌ | 历史遗留参数，v6.6 已忽略（但传 0 仍可能报错，保留兼容语义） |

> ⚠️ ①是最容易凭印象答错的 —— 网上部分旧资料提到过 `EPOLL_CTL_DISABLE`，
> 但**当前内核源码里查不到**。凡写"有 X 这个 op/flag"，必须 grep 源码确认。
</details>
</details>
