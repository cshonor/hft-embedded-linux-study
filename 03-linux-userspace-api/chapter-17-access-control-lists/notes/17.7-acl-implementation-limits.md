# 17.7 ACL Implementation Limits 实现限制

> 本章：[TLPI 第 17 章 — Access Control Lists](../README.md)
> 平台标注：Linux 专有实现；数字以 kernel/ext4 为准
> 源码核验：man-pages **6.19** `acl(5)`（实现限制段）+ Linux **v6.6** `fs/ext4/xattr.c`
> - 上一节：[17.6 Default ACLs](17.6-default-acls-and-file-creation.md)
> - 下一节：[17.8 The ACL API](17.8-the-acl-api.md)

---

## 要点

| 限制 | 值 | 出处 |
|------|-----|------|
| named 条目数 | **≥ 32**（POSIX 最低保证）；ext4 实际上限远高于此（受 xattr 空间约束） | acl(5) |
| ACL 存储 | `system.posix_acl_access` xattr（Ch16 的 64KiB 单值上限 + FS 的 xattr 空间） | 16.2 |
| FS 支持面 | ext4/xfs/btrfs/tmpfs ✅；squashfs/sysfs 等无 ❌ | 各 FS 文档 |
| NFS | 跨端映射语义有损（v4 ACL ≠ draft ACL） | RFC |

三条工程推论：

1. **条目数不是问题**（32 条的下限对"人组授权"够用，超量说明建模错了——应该用组而不是逐人 named 条目）；
2. **FS 支持面才是问题**：部署脚本要探测（setfacl 试一下 + getfacl 回读验证），squashfs 只读镜像上的 ACL 是幻觉；
3. **备份必须带 ACL**：tar 默认不带（需 `--acls`），rsync 需 `--acls`；漏掉的恢复 = 权限模型蒸发。

---

## 常见坑

| 坑 | 正解 |
|----|------|
| 在不支持 FS 上静默降级 | setfacl 成功 ≠ 生效（回读验证）；overlayfs 叠加层也要验证 |
| named 条目当"用户表"用 | 上百条 named 说明该用组；条目多也伤 getfacl 可读性 |

## HFT / 嵌入式关联

| 场景 | 本节机制怎么兑现 |
|------|----------------|
| 固件镜像 | squashfs 只读 + 无 ACL：部署权限模型只能靠传统位，设计期就要想清楚 |
| 灾备演练 | 恢复后的 getfacl 快照 diff 是验收项，别只对文件内容做 md5 |
