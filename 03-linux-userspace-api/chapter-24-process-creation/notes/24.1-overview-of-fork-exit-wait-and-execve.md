## 本节讲什么

原书 §24.1 只有 **一张图**（Figure 24-1）。它把「进程从哪来、怎么走」压缩成**四个调用**：

```
fork() ──► 复制出一个新进程
exit() ──► 结束自己，留下一个 8 位状态码
wait() ──► 父进程取回子进程的终止状态
execve() ► 用另一个程序**替换**当前进程的映像
```

后面三章就是在把这四个调用逐个展开：**Ch25**（进程终止）、**Ch26**（监控子进程）、**Ch27**（程序执行）。本节只做两件事：把职责边界画清，把四个调用的最小闭环跑通。

⚠️ **原书这一节没有任何 Listing、也没有配套程序**，只有图。本仓库为此写了一个程序
（`c24_lifecycle.c`，见下），把 Figure 24-1 变成一串**可运行的真实输出**——
这样后面三章每深入一个调用时，都有一个共同的地基可以对照。

---

## 1. 四个调用各自的职责与「展开在哪一章」

| 调用 | 一句话职责 | 谁创建/销毁了什么 | 原书展开 |
|------|-----------|------------------|---------|
| `fork()` | 复制出一个**几乎一模一样**的新进程 | 内核克隆 `task_struct` + 复制页表（COW） | 本章 §24.2；细节在 **Ch28** |
| `exit()` / `_exit()` | **主动**结束自己 | 释放内存/fd，状态码留在一个 8 位字段里 | **Ch25** |
| `wait()` / `waitpid()` | 父进程**取回**终止状态 | 回收僵尸（zombie） | **Ch26** |
| `execve()` | 用另一个程序**替换**当前映像 | 保留 PID、fd 表、PID/会话；换掉代码段 | **Ch27** |

⭐ 一句话记住四者的关系：**`fork` 负责「多一个」，`exec` 负责「变一个」，`exit` 负责「少一个」，`wait` 负责「知道少的那一个怎么走的」。**

## 2. Figure 24-1 的文字版

原书那张图的核心信息量，用表格重画一遍（这是后面三章的坐标系）：

| 时刻 | 调用者 | 动作 | 谁还在跑 |
|------|--------|------|---------|
| ① | 父进程 | 走到 `fork()` | 父进程阻塞在 `fork()` 里 |
| ② | 内核 | 克隆出子进程；**两个进程都从 `fork()` 返回** | 父、子都就绪 |
| ③ | 子进程 | 走到 `exit()`/`_exit()` | 只剩父进程 |
| ④ | 父进程 | `fork()` 返回子进程 PID，继续跑；需要时调 `wait()` 取状态 | 父进程 |
| ⑤ | 子进程 | （另一条路）走到 `execve()`——**不创建新进程**，只是换映像 | 同一个 PID 在跑新程序 |

⚠️ ② 那一步有个容易说错的点：`fork()` 是**一次调用、两次返回**。父进程拿到的返回值是**子进程的 PID**，子进程拿到的是 **0**；失败时只有父进程拿到 **-1**。所以 `if (pid == 0)` 是「我是子进程」的判据，不是「fork 成功了」。

---

## 3. 先给三条结论（后面几节会一一钉死）

1. **fork 的复制是「写时才复制」**（COW）。所以「父子的全局变量互不影响」不是靠一开始就拷贝，而是靠**写**触发缺页。§24.2 的 Listing 24-1、24-3 演示这件事。
2. **fd 表被复制，但 `struct file` 是共享的**。父子写同一个 fd，**文件偏移是同一个**。§24.2.1 的 Listing 24-2 演示这件事。
3. **fork 之后谁先跑是不确定的**。要靠 `wait()`/信号来定序，不能靠 `sleep()`。§24.4、§24.5 演示这件事。

## 完整源码（本仓库自写）

⚠️ **原书没有这个程序**（§24.1 只有 Figure 24-1）。本仓库按图写了一个最小闭环。

[`code/c24_lifecycle.c`](../code/c24_lifecycle.c)

```c
/* c24_lifecycle.c

   ⚠️ 本仓库自写 —— 原书 §24.1 **只有一张 Figure 24-1**（"Overview of the use of
      fork(), exit(), wait(), and execve()"），既没有 Listing，也没有配套程序。

   本程序把 Figure 24-1 从"一张图"变成"一串可运行的真实输出"：

     ① 单进程：报自己的 pid / ppid
     ② fork()  —— 一次调用，两个返回值（父得子 pid，子得 0）
     ③ _exit(7) —— 子进程带一个状态码退出
     ④ wait(&status) —— 父进程取回状态，并把它**解码**（很多人只会用 WEXITSTATUS
        却不知道 status 里还有什么）
     ⑤ fork() + execve() —— 再起一个子进程，用 exec 把它的**程序映像**换掉；
        对照 ③：这次子进程不是"_exit"，而是"变成了另一个程序"

   ⚠️ ⑤ 为什么 exec 的是「自己」（/proc/self/exe）而不是 /bin/echo：
      CE 的 executor 沙箱里 **PATH 是空的、/bin 和 /usr/bin 下什么都没有**
      （实测见 code/probe24.c：`access("/bin/echo", X_OK) == -1`）。
      而 exec 自己恰好是最干净的演示 —— 同一个可执行文件，换一副 argv 就是
      「另一个程序」；并且能顺便看到 **exec 不换 PID**（对比 fork 会换）。

   ⚠️ 没写 exit() vs _exit() 的区别：那是 §25.1 的主题（exit() 会刷 stdio 缓冲、
      会跑 atexit 处理器，_exit() 不会）。这里两个都用 `_exit()`。

   编译（自包含）：
     gcc -O0 -Wall -Wextra -o c24_lifecycle c24_lifecycle.c
*/

#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

int main(int argc, char *argv[])
{
    pid_t childPid;
    int status;

    setvbuf(stdout, NULL, _IONBF, 0);   /* 关缓冲，父子输出不互相夹杂 */

    /* ---- 被 ⑤ 里的 exec 拉起来时走这条分支：说明"我已经是另一个映像了" ---- */
    if (argc > 1 && strcmp(argv[1], "--after-exec") == 0) {
        printf("⑤★ exec 之后  pid 还是 %ld —— execve 换映像但**不换 PID**\n",
                (long) getpid());
        printf("     （能走到这一行，本身就证明 execve 成功了：\n");
        printf("      同一个可执行文件，靠 argv[1]=\"%s\" 走了不同分支）\n", argv[1]);
        return 0;
    }

    /* ---------------- ① ---------------- */
    printf("① 单进程      pid=%ld ppid=%ld\n", (long) getpid(), (long) getppid());

    /* ---------------- ② ③ ④ ------------- */
    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:                                  /* ③ 子进程 */
        printf("② 子进程      pid=%ld  fork() 返回 0（这是子进程的判据）\n",
                (long) getpid());
        printf("③ 子进程      _exit(7) —— 带 7 退出\n");
        _exit(7);                            /* 注意：不是 exit() */

    default:                                 /* ② 父进程 */
        printf("② 父进程      pid=%ld  fork() 返回 %ld（= 子进程 pid）\n",
                (long) getpid(), (long) childPid);

        if (wait(&status) == -1)             /* ④ */
            die("wait");

        /* status 不是"退出码"，是内核打包的一整块信息 */
        printf("④ 父进程      wait() 拿到 status=%d\n", status);
        printf("   WIFEXITED   = %d\n", WIFEXITED(status));
        printf("   WEXITSTATUS = %d   （子进程 _exit 的那个 7）\n",
                WEXITSTATUS(status));
        printf("   WIFSIGNALED = %d   （0 = 不是被信号杀死的）\n",
                WIFSIGNALED(status));
        printf("   —— 7 << 8 = %d，所以直接看 status 会看到 %d 而不是 7\n",
                7 << 8, 7 << 8);
        break;
    }

    /* ---------------- ⑤ execve 把子进程换成另一个程序 ------------- */
    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:
        printf("⑤ 子进程      pid=%ld 即将 exec —— 下面两行的输出来自新映像\n",
                (long) getpid());
        execl("/proc/self/exe", "c24_lifecycle", "--after-exec", (char *) NULL);
        die("execl(/proc/self/exe)");        /* exec 成功则永远到不了这里 */

    default:
        if (wait(NULL) == -1)
            die("wait");
        printf("⑤ 父进程      第二个子进程（pid=%ld）也收完了\n", (long) childPid);
        break;
    }

    printf("── 结束：Figure 24-1 的四个调用都跑过一遍了 ──\n");
    return 0;
}
```

## 逐条解读

**① `pid=2 ppid=1`** —— 不是笔误，是**容器 PID namespace** 的直接证据。这个程序是
新 PID namespace 里的第 2 个进程（1 号是 namespace 的 init），它的父进程是
namespace 外的进程，映射进来就是 1。所以本章后面所有日志里的 PID 都是 2、3、4……
这种一位数。⚠️ **这不代表「PID 不会超过几」** —— probe24 实测
`_SC_CHILD_MAX = 54956`、`RLIMIT_NPROC = 54956`，能开的进程多得很。

**② 一次调用、两次返回** —— 父进程拿到 `3`（子进程的 PID），子进程拿到 `0`。
注意输出顺序：**父进程那行先出现**。这不是保证，只是这次调度如此（§24.4 会把这件事
量化）。原书 Listing 24-1 里用 `sleep(3)` 在父进程侧来"保证"子进程先打印，原书自己
也承认这**不是可靠办法**（书 p.517 原话：*"Using sleep() in this manner is not a
foolproof method of guaranteeing this result"*）。

**③ `_exit(7)`** —— 用的是 `_exit()` 而不是 `exit()`。本文刻意如此：`exit()` 会
**刷 stdio 缓冲**，而 stdout 在 CE 上是 socket（8KB 全缓冲），两者的差别会立刻
体现出来。这条差异是 **Ch25 §25.1** 的主题，本节只留个钩子。

**④ `status=1792` 而有用的退出码是 7** —— 这是**最容易踩的坑**：`wait(&status)`
给回来的 `status` **不是退出码**，而是内核打包的一整块终止信息。退出码只占
**8 位**，放在 `status` 的**高 8 位**里（`7 << 8 == 1792`），低 7 位留给信号编号等。
所以必须用 `WEXITSTATUS(status)` 取，不能直接 `printf("%d", status)`。

⚠️ 为什么是 8 位？因为内核里这个字段本身只有 8 位：进程的 `exit_code` 是
`int`，但 `wait()` 只把低 8 位（`0xFF`）当作退出状态交给父进程（见「源码坐标」）。
所以 `_exit(256)` 和 `_exit(0)` 在父进程看来是**同一个值 0**。

**⑤ exec 把映像换掉、但 PID 不变** —— 这一行 `⑤★ exec 之后 pid 还是 4` 是本节
最有价值的一条对照：
* `fork()` 出来的是**新 PID**（②里 2 → 3）；
* `execve()` **不创建进程**，所以 PID 不变（⑤里 4 → 4）。

⚠️ 为什么 exec 的是**自己**（`/proc/self/exe`）而不是 `/bin/echo`：CE 的 executor
沙箱里 **PATH 是空的**，`/bin`、`/usr/bin` 下的常规程序**一个都不存在**。这不是
猜测，是 `code/probe24.c` 的实测（见下）。而「exec 自己 + 用一个 argv 走另一条分支」
反而把 `execve` 的语义演示得更纯：**同一个可执行文件，换一副 argv 就是另一个程序**。

| 机制 | 坐标（Linux v6.6） |
|------|-------------------|
| `fork()` 的总入口 | `kernel/fork.c:2868` `kernel_clone()` → `kernel/fork.c:2240` `copy_process()` |

`(((status) & 0xff00) >> 8)`，所以「8 位」这个结论在**用户态就能验**——`_exit(256)`
在父进程里看到的是 0。本仓库没有单独为这一条跑实验（Ch26 讲 `wait()` 时会补），
这里只把机制坐标留全。

| # | 坑 | 说明 |
|---|----|------|
| 1 | 把 `wait(&status)` 的 `status` 当退出码打印 | 应 `WEXITSTATUS(status)`；否则看到的是 `退出码 << 8` |

## HFT / 嵌入式关联

* **`fork()+execve()` 是 shell 的骨架，也是交易所网关"冷启动"的骨架**：行情网关
  常把一个策略进程 `fork` 出来再 `exec` 成目标二进制，好处是**新映像的地址空间、
  fd、PID namespace 都是干净的**。理解「exec 不换 PID」才知道为什么 `setsid()` /
  进程组管理要在 `fork` 之后、`exec` 之前做（否则新程序一启动就是组长，`setsid` 会失败）。
* **`WEXITSTATUS` 只有 8 位 = 子进程的"错误码"只能塞 0–255**：HFT 里常用它把子进程
  （比如行情录制进程）的失败原因带回来。超过 255 就要走别的通道（pipe / 共享内存 /
  退出日志），本仓库 §24.7 的习题 24-1、24-5 都会碰到这个约束。
* **嵌入式**：BusyBox 的 init 就是 `fork+exec` 的循环；`vfork()+exec` 在
  `NOMMU`（无 MMU）的架构上是**唯一**可行的组合，因为那种平台没有 COW 需要的
  MMU 支持（见 §24.3）。
* **PID namespace（本节 ① 的 `pid=2`）** 是容器隔离的基础；HFT 里用它把策略进程
  的 PID 空间与宿主机上的运维工具隔开，副作用是 `/proc` 里的 PID 与宿主机不同 —— 
  排查问题时要记得看 NSpid 而不是 Pid。

<summary>代码自测（Q&A）</summary>

**Q1：`fork()` 返回 `-1` 时，子进程存在吗？**

A：不存在。失败时**只有调用者一侧**会从 `fork()` 返回，返回 -1 并把 `errno` 设好
（常见是 `EAGAIN`/`ENOMEM`）。所以「一次调用两次返回」只在**成功**时成立。

**Q2：为什么本节 ② 里父进程那行先打印？这是保证吗？**

A：不是。这是**调度器的临时决定**。原书 p.517 用 `sleep(3)` 在父进程侧来"保证"
子进程先跑完，并且自己说明这**不是 foolproof**（因为 `sleep` 到期后调度谁、以及
子进程是否已经跑完，都不受你控制）。§24.4 用 1000 次 fork 把这个不确定性量化了。

**Q3：`_exit(7)` 之后父进程拿到 `status=1792`，为什么不是 7？**

A：因为 `wait(&status)` 交回的是**内核打包的一整块终止信息**，退出码只占**高 8 位**。
`7 << 8 == 1792`。要用 `WEXITSTATUS(status)` 取。反过来说，**只有 0–255 能被带出去**：
`_exit(256)` 父进程会看到 0。

**Q4：⑤ 里 exec 之后 PID 没变，那「exec 也算创建了个进程」这种说法错在哪？**

A：错在「进程」的判定标准。`execve()` **不调用 `copy_process()`**，它只在当前进程里
换掉 `mm_struct` 指向的代码/数据映像（PID、`task_struct`、fd 表、PID/会话都留着）。
所以进程**个数**不变 —— 这正是 Figure 24-1 把 `fork` 和 `execve` 画成两个不同分支的原因。

**Q5：本节为什么不用 `/bin/echo` 做 exec 演示，而要 exec 自己？**

A：因为 CE 的 executor 沙箱里 **PATH 是空的、`/bin` 和 `/usr/bin` 下什么都没有**
（`probe24.c` 实测：`access("/bin/echo", X_OK) == -1`）。所以 `execlp()` 一定失败
（`ENOENT`），而 `execl()` 只能给绝对路径。`/proc/self/exe` 是探测中唯一可执行的
绝对路径 —— 而且拿它做演示更干净：**同一个文件、不同 argv = 不同程序**，还顺带
把「exec 不换 PID」显示出来了。

**Q6：`pid=2 ppid=1` 说明这台机器上只有几个进程吗？**

A：完全不是。这是**容器 PID namespace** 造成的：这个程序是它所在 namespace 里
第 2 个进程，1 号是 namespace 的 1 号进程。probe24 实测
`_SC_CHILD_MAX = 54956`、`RLIMIT_NPROC = 54956` —— 能开的进程一点都不少。
把 namespace 的 PID 当成"机器上的序号"是排查容器问题时的经典翻车点。
