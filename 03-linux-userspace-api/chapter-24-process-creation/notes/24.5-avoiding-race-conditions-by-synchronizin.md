## 本节讲什么

§24.4 的结论是「`fork()` 之后谁先跑靠不住」。那**要保证顺序该怎么办**？原书给的第一种
答案是**信号**（书 p.527）：

> *"If we need to guarantee a particular order, we must use some kind of synchronization
> technique. We describe several synchronization techniques in later chapters, including
> semaphores, file locks, and sending messages between processes using pipes. One other
> method, which we describe next, is to use signals."*

信号同步的骨架只有三步：

```
① 在 fork() 之前，先把同步信号**屏蔽**掉
② fork()
③ 子进程做完事 → kill(父进程, 同步信号)
   父进程 → sigsuspend() 睡下等这个信号
```

⭐ **整个方案的正确性，全部压在「第 ① 步必须在 fork 之前」这一点上**。这一节的重点
就是把这个「为什么」讲透。

```c
/* fork_sig_sync.c

   Demonstrate how signals can be used to synchronize the actions
   of a parent and child process.
*/
#include <signal.h>
#include "curr_time.h"                  /* Declaration of currTime() */
#include "tlpi_hdr.h"

#define SYNC_SIG SIGUSR1                /* Synchronization signal */

static void             /* Signal handler - does nothing but return */
handler(int sig)
{
}

int
main(int argc, char *argv[])
{
    pid_t childPid;
    sigset_t blockMask, origMask, emptyMask;
    struct sigaction sa;

    setbuf(stdout, NULL);               /* Disable buffering of stdout */

    sigemptyset(&blockMask);
    sigaddset(&blockMask, SYNC_SIG);    /* Block signal */
    if (sigprocmask(SIG_BLOCK, &blockMask, &origMask) == -1)
        errExit("sigprocmask");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = handler;
    if (sigaction(SYNC_SIG, &sa, NULL) == -1)
        errExit("sigaction");

    switch (childPid = fork()) {
    case -1:
        errExit("fork");

    case 0: /* Child */

        /* Child does some required action here... */

        printf("[%s %ld] Child started - doing some work\n",
                currTime("%T"), (long) getpid());
        sleep(2);               /* Simulate time spent doing some work */

        /* And then signals parent that it's done */

        printf("[%s %ld] Child about to signal parent\n",
                currTime("%T"), (long) getpid());
        if (kill(getppid(), SYNC_SIG) == -1)
            errExit("kill");

        /* Now child can do other things... */

        _exit(EXIT_SUCCESS);

    default: /* Parent */

        /* Parent may do some work here, and then waits for child to
           complete the required action */

        printf("[%s %ld] Parent about to wait for signal\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        if (sigsuspend(&emptyMask) == -1 && errno != EINTR)
            errExit("sigsuspend");
        printf("[%s %ld] Parent got signal\n", currTime("%T"), (long) getpid());

        /* If required, return signal mask to its original state */

        if (sigprocmask(SIG_SETMASK, &origMask, NULL) == -1)
            errExit("sigprocmask");

        /* Parent carries on to do other things... */

        exit(EXIT_SUCCESS);
    }
}
```

注意代码顺序：**`sigprocmask(SIG_BLOCK)` 和 `sigaction()` 都在 `fork()` 之前**。
这不是风格问题，是必需（见第 3 节）。

### 逐条解读

**① 后两行是被**保证**的，前两行是自由的。**

| 行 | 谁先谁后有保证吗 | 依据 |
|----|------------------|------|
| `Parent about to wait for signal` vs `Child started - doing some work` | **没有** | 这两行都在 `fork()` 刚返回的位置；§24.4 已证顺序不定 |
| `Child about to signal parent` vs `Parent got signal` | **有** | 父进程 `sigsuspend()` 必须等到 `kill()` 的那一发才醒；子进程必须先 `sleep(2)` 再发 |

所以程序**对**与**不对**，只取决于后两行的顺序有没有成立 —— 而它成立。
这就是「同步」的含义：**不消除不确定性，而是把不确定性赶出关键区**。

⭐ **和原书的示例对照**（书 p.528，书上的 shell session 日志）：

```
$ ./fork_sig_sync
[17:59:02 5173] Child started - doing some work
[17:59:02 5172] Parent about to wait for signal
[17:59:04 5173] Child about to signal parent
[17:59:04 5172] Parent got signal
```

书上是 **child 先**，我们是 **parent 先** —— 前两行反了。**但两次都对**。
而且这次「parent 先」正好与 §24.4 测到的 91.6% 一致。

**② 时间戳给的证据**：`05:40:18` → `05:40:20`，整整 2 秒，就是子进程那句 `sleep(2)`。
`execTime = 2047` 毫秒与之一致。父进程在这一段时间里**什么都没干**（睡在 `sigsuspend` 里）。

**③ 两行的 pid：父 `2`、子 `3`** —— 和 Ch24 其它作业一样（容器 PID namespace，见 §24.1）。
`getppid()` 在子进程里拿到的是 `2`，就是父进程。

**④ `sigsuspend(&emptyMask)` 这一句有三个动作，是原子的**：

| 步骤 | 说明 |
|------|------|
| 1. 把信号掩码**设为** `emptyMask`（空集 = 不屏蔽任何信号） | 于是 `SIGUSR1` 从「屏蔽」变成「可递送」 |
| 2. 挂起进程，直到有信号被递送 | 睡在这里等 |
| 3. 信号处理完后，把掩码**恢复**成调用前的值 | 所以调用者不用自己恢复 |

⚠️ 这里传的是**空集**，意思是「任何信号都能唤醒我」。原书这么做是因为这个程序里没别的
信号；**更严谨的写法是只解屏蔽 `SYNC_SIG`**（把 `origMask` 拷一份、`sigdelset(SYNC_SIG)`），
这样其它信号仍被屏蔽。真实程序里应该这么写。

**⑤ `SA_RESTART` 在这段代码里其实用不上**（`sigsuspend` 无论如何都返回 `EINTR`），
它真正的价值是在后面被信号打断的 `read()`/`write()` 之类的调用上。原书把 `sa_flags`
设成 `SA_RESTART` 是通用习惯。

## 2. 为什么「在 fork 之前屏蔽」是**唯一正确**的写法

原书只用一句话点出来（书 p.528）：

> *"Note that we block the synchronization signal (`SIGUSR1`) before the `fork()` call in
> Listing 24-6. If the parent tried blocking the signal after the `fork()`, it would remain
> vulnerable to the very race condition we are trying to avoid."*

把「如果反过来写」的时序摊开看，就知道它为什么是致命的：

```
❌ 错误写法：fork 之后才 sigprocmask(SIG_BLOCK)

  父进程                              子进程
  ─────────                           ─────────
  fork() ──────────────────────────>  fork() 返回
   │                                   │
   │ ←── 危险窗口 ──→                   sleep(2)……（这里还看不出问题）
   │                                   │
  sigprocmask(SIG_BLOCK)               │
   │                                   │
  sigsuspend()  ← 已经睡下，等信号      │
                                       │
                                      kill(父, SIGUSR1) ──> ✔ 正常唤醒
```

上面这段推演看起来还行 —— 因为子进程 `sleep(2)` 拖长了时间，父进程有充足的时间
完成 `sigprocmask`。**问题出在「子进程不 sleep 就发信号」的情形**：

```
❌ 错误写法（子进程不做耗时工作）

  父进程                              子进程
  ─────────                           ─────────
  fork() ──────────────────────────>  fork() 返回
   │                                   │
   │                                 kill(父, SIGUSR1)
   │                                   │
   │  ← 此刻父进程还【没有】屏蔽 SIGUSR1
   │  ← 信号立刻递送 → handler 空转一下 → 信号【用掉了】
   │                                   _exit(0)
   │
  sigprocmask(SIG_BLOCK)   ← 现在才屏蔽（已经晚了，信号已经消费掉）
   │
  sigsuspend()  ← ★ 永远等不到信号，【永久挂起】
```

⭐ **这个 bug 比「顺序错了」更恶劣 —— 它是死锁。** 而且它**只在子进程跑得足够快时
才出现**，也就是说：

* 平时（子进程稍慢）跑一百次都对；
* 机器一空闲、子进程抢得先（§24.4 里那 8.4%）→ 父进程挂死；
* 而且这个 bug 在 §24.4 那种「本机负载随时变」的环境里**看起来像随机现象**。

**正确写法的时序**（`fork` 之前就已经屏蔽）：

```
✔ 正确写法

  父进程                              子进程
  ─────────                           ─────────
  sigprocmask(SIG_BLOCK, SIGUSR1)
  sigaction(SIGUSR1, handler)
  fork() ──────────────────────────>  fork() 返回（掩码继承：SIGUSR1 也是屏蔽的）
   │                                   │
   │                                 kill(父, SIGUSR1)
   │                                   │
   │  ← 信号到达，但父进程【屏蔽着它】⇒ 停在 pending，不丢
   │                                   _exit(0)
   │
  sigsuspend(&emptyMask)  ← 原子地解屏蔽 → pending 里的 SIGUSR1 立刻递送 → 唤醒
   │
  ✔ 无论子进程多快都不会丢
```

关键差别：**信号在到达时就已经被拦住（pending 起来），而不是靠运气赶在它到达之前
把门关上。**

### ⭐ 用 §24.2 的实测支撑这条推理

「掩码会被子进程继承」这件事不是猜的。§24.2 的延伸 demo `c24_sigmask_inherit` 实测过：

```text
父进程 pid=2 ppid=1
  掩码 中 SIGUSR1 = 1   （1 = 屏蔽）
  pending 中 SIGUSR1 = 1   （1 = 有未递送信号）
子进程 pid=3 ppid=2
  掩码 中 SIGUSR1 = 1   （继承来的）
  pending 中 SIGUSR1 = 0   （不继承）
父进程 fork 之后：pending 中 SIGUSR1 = 1（自己的还留着）
```

三行结论：

| 项 | fork 之后 | 机制 |
|----|-----------|------|
| 信号**掩码** | **继承** | `kernel/fork.c:1091` `*dst = *src;`（`arch_dup_task_struct()` 把整个 `task_struct` 拷一份，`blocked` 跟着走） |
| **pending** 信号集 | **不继承（清零）** | `kernel/fork.c:2391` `init_sigpending(&p->pending);` |
| 信号**处置**（handler 表） | **继承** | `kernel/fork.c:2495` `copy_sighand(clone_flags, p)` |

因为掩码继承，子进程**天然也是屏蔽着 `SIGUSR1` 的**。这对本程序没有影响（子进程不给自己
发信号），但如果你打算在子进程里用同一个信号做别的事，**记得先 `sigsuspend`/`sigprocmask`
把它解开** —— 这正是原书那句括号里的话（书 p.528）：

> *"(In this program, we assume that the state of the signal mask in the child is irrelevant;
> if necessary, we can unblock `SIGUSR1` in the child after the `fork()`.)"*

## 3. 反过来用：让**子进程**等父进程 / 双向握手

原书（书 p.528）说这个模式是对称的：

> *"In this program, we assume that it is the parent that must wait on the child to carry out
> some action. The signal-related calls in the parent and child can be swapped if the child
> must wait on the parent. It is even possible for both parent and child to signal each other
> multiple times in order to coordinate their actions, although, in practice, such
> coordination is more likely to be done using semaphores, file locks, or message passing."*

这就是习题 24-5 的题面。本仓库自写了一份双向握手的解（原书**没有**这一节的代码）：

[`code/ex24_5_fork_sig_sync2.c`](../code/ex24_5_fork_sig_sync2.c)

```c
/* ex24_5_fork_sig_sync2.c

   ⚠️ 本仓库自写 —— 原书习题 24-5 **没有官方解答文件**
      （官方只给了习题 24-2 的解：procexec/vfork_fd_test.c）。

   习题 24-5：如果**子进程也要等父进程**完成某个动作，Listing 24-6
              （fork_sig_sync.c）需要怎么改？

   答：一个信号不够了，要**两个**信号做双向握手：
         子 → 父 用 SIGUSR1（"我干完了"）
         父 → 子 用 SIGUSR2（"我干完了"）
       并且**两个信号都要在 fork() 之前屏蔽**。原因是 Listing 24-6 里
       已经写明的那条：如果先 fork 再屏蔽，那么"信号已经发出"与"我开始屏蔽"
       之间存在窗口，对方那一枪可能在你 sigsuspend 之前就打完了 ——
       这正是要避免的那个竞态。

   本程序的输出**顺序是确定的**（靠信号保证），这跟 Listing 24-5 的
   fork_whos_on_first 形成对照：那里没有同步，先后完全看调度器。

   编译（需要 curr_time.c 提供 currTime()，见 code/README.md）：
     gcc -O0 -Wall -Wextra -o ex24_5_fork_sig_sync2 \
         ex24_5_fork_sig_sync2.c curr_time.c
*/

#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#include "curr_time.h"          /* currTime() */

#define CHILD_READY SIGUSR1     /* 子 → 父 */
#define PARENT_DONE SIGUSR2     /* 父 → 子 */

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

static void handler(int sig)    /* 什么都不做，只为让 sigsuspend 醒过来 */
{
    (void) sig;
}

static void waitFor(sigset_t *emptyMask)
{
    if (sigsuspend(emptyMask) == -1 && errno != EINTR)
        die("sigsuspend");
}

int main(void)
{
    pid_t childPid;
    sigset_t blockMask, emptyMask;
    struct sigaction sa;

    setvbuf(stdout, NULL, _IONBF, 0);

    /* ---------- 屏蔽**两个**信号：必须在 fork() 之前 ---------- */
    sigemptyset(&blockMask);
    sigaddset(&blockMask, CHILD_READY);
    sigaddset(&blockMask, PARENT_DONE);
    if (sigprocmask(SIG_BLOCK, &blockMask, NULL) == -1)
        die("sigprocmask(SIG_BLOCK)");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = handler;
    if (sigaction(CHILD_READY, &sa, NULL) == -1)
        die("sigaction(SIGUSR1)");
    if (sigaction(PARENT_DONE, &sa, NULL) == -1)
        die("sigaction(SIGUSR2)");

    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:   /* ---------- 子进程 ---------- */
        printf("[%s %ld] Child  started - working\n",
                currTime("%T"), (long) getpid());
        sleep(2);                                   /* 模拟干活 */

        printf("[%s %ld] Child  -> SIGUSR1 to parent\n",
                currTime("%T"), (long) getpid());
        if (kill(getppid(), CHILD_READY) == -1)
            die("kill(SIGUSR1)");

        /* 反过来等父进程（习题 24-5 新增的部分）*/
        printf("[%s %ld] Child  waiting for parent\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);

        printf("[%s %ld] Child  got SIGUSR2 -> done\n",
                currTime("%T"), (long) getpid());
        _exit(EXIT_SUCCESS);

    default:  /* ---------- 父进程 ---------- */
        printf("[%s %ld] Parent waiting for child\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);                        /* 等 SIGUSR1 */

        printf("[%s %ld] Parent got SIGUSR1 - working\n",
                currTime("%T"), (long) getpid());
        sleep(1);                                   /* 模拟干活 */

        printf("[%s %ld] Parent -> SIGUSR2 to child\n",
                currTime("%T"), (long) getpid());
        if (kill(childPid, PARENT_DONE) == -1)
            die("kill(SIGUSR2)");

        if (wait(NULL) == -1)
            die("wait");
        printf("[%s %ld] Parent done\n", currTime("%T"), (long) getpid());
        exit(EXIT_SUCCESS);
    }
}
```

CE 实测（`ex24_5_fork_sig_sync2`）：

```text
[05:40:31 2] Parent waiting for child
[05:40:31 3] Child  started - working
[05:40:33 3] Child  -> SIGUSR1 to parent
[05:40:33 3] Child  waiting for parent
[05:40:33 2] Parent got SIGUSR1 - working
[05:40:34 2] Parent -> SIGUSR2 to child
[05:40:34 3] Child  got SIGUSR2 -> done
[05:40:34 2] Parent done
```

`execTime = 3018` 毫秒，`exit code = 0`，`diagnostics = 7`。

**双向握手要多想一步**：两个方向各需要一个信号，而且**必须在 `fork()` 之前把两个都屏蔽**。
本仓库的实现用：

| 信号 | 方向 | 用于 |
|------|------|------|
| `SIGUSR1` | 子 → 父 | 「我干完了，该你了」 |
| `SIGUSR2` | 父 → 子 | 「我干完了，收工」 |

用**两个不同的信号**而不是一个信号互相发，是因为一个信号无法表达「这是你发给我的还是
我发给你的」；用一个信号做双向握手会分不清方向，很容易写出自己唤醒自己的逻辑。

## 4. 信号同步的局限（为什么后面还要学管道/信号量）

原书在 p.528 那句带了前半句很重要：

> *"Although, in practice, such coordination is more likely to be done using semaphores,
> file locks, or message passing."*

信号能同步，但代价不小：

| 局限 | 说明 |
|------|------|
| 一次只能传「一个 bit」 | 信号不带数据。要说「我算出来 42」还得另找地方放 |
| 标准信号会**合并** | 连续两次 `SIGUSR1` 到达而还没被处理，只会 pending 一次 —— 计数会丢 |
| 需要处理信号语义 | 掩码、`EINTR`、`SA_RESTART`、异步信号安全（handler 里只能调 `write()` 之类的少数函数） |
| 与多线程交互复杂 | 信号可以投递到进程里的**任意一个**线程（Ch33 详述） |
| 不适合高频通信 | 每次 `kill()` 都是一次系统调用 + 一次调度器唤醒 |

⭐ 原书还提到一种工程习惯（书 p.528，引 Stevens）：

> *"[Stevens & Rago, 2005] suggests encapsulating such synchronization steps (block signal,
> send signal, catch signal) into a standard set of functions for process synchronization.
> The advantage of such encapsulation is that we then later replace the use of signals by
> another IPC mechanism, if desired."*

**「封装成 sync 函数对」这个建议很实用**：把「屏蔽 + 发 + 等」包成
`syncInit() / syncSignal() / syncWait()`，之后就只是换个实现，调用点一个字不用改。

| `kill()`（发信号） | `kernel/signal.c:3807` `SYSCALL_DEFINE2(kill, pid_t, pid, int, sig)` |
| └ 投递路径 | `kernel/signal.c:1225` `send_signal_locked()` → `kernel/signal.c:1084` `__send_signal_locked()` → `kernel/signal.c:1004` `complete_signal()` |
| └ 唤醒目标进程 | `kernel/signal.c:1075` `signal_wake_up(t, sig == SIGKILL)` |
| `sigsuspend()`（原子解屏蔽 + 睡下） | `kernel/signal.c:4669` `SYSCALL_DEFINE4(rt_sigsuspend, ...)` |
| └ 信号真正被取走的地方 | `kernel/signal.c:635` `dequeue_signal()` |
| └ 信号处置（跑 handler / 默认动作） | `kernel/signal.c:2660` `bool get_signal(struct ksignal *ksig)` |
| **掩码继承** | `kernel/fork.c:1091` `*dst = *src;`（`arch_dup_task_struct()`，`kernel/fork.c:1088`） |
| **pending 清零** | `kernel/fork.c:2391` `init_sigpending(&p->pending);` |
| **handler 表继承** | `kernel/fork.c:2495` `copy_sighand(clone_flags, p)` |

⭐ 一句话：**`fork` 复制整个 `task_struct`（含 `blocked` 掩码、含 handler 表），但
`p->pending` 被显式清零**。「掩码继承 + pending 不继承」这个组合，正是
「在 fork 之前屏蔽」这一招能成立的机制基础。

## 常见坑

| # | 坑 | 说明 |
|---|----|------|
| 1 | 在 `fork()` **之后**屏蔽同步信号 | 原书 p.528 明确点名的错误。子进程跑得快时信号会被 handler 空转掉，父进程**永久挂起** |
| 2 | `fork()` 之后才 `sigaction()` 装 handler | 若信号在装 handler 之前就解屏蔽递送，`SIGUSR1` 的**默认动作是终止进程** → 父进程直接被杀 |
| 3 | 用 `pause()` 代替 `sigsuspend()` | `pause()` 不是原子的：信号可能在 `sigprocmask`/`pause` 之间到达并丢失。**这是经典竞态**，必须用 `sigsuspend` |
| 4 | 忘了检查 `errno != EINTR` | `sigsuspend` 正常被信号唤醒时**也返回 -1** 并设 `errno = EINTR`。直接 `if (sigsuspend(...) == -1) errExit()` 会把正常路径当错误 |
| 5 | 在子进程里忘了掩码是继承来的 | 子进程同样屏蔽着 `SYNC_SIG`；要在子进程里用这个信号，得先解屏蔽 |
| 6 | 用标准信号做「计数」 | 标准信号会合并：发两次只 pending 一次。要计数得用 **实时信号**（`SIGRTMIN` 系列，Ch22 有详述） |
| 7 | handler 里调 `printf` | handler 必须**异步信号安全**。`printf` 会用锁，不安全；`write()` 才行 |
| 8 | 双向握手共用一个信号 | 分不清方向，容易自己唤醒自己。**一个方向一个信号**（实测解用 `SIGUSR1` + `SIGUSR2`） |
| 9 | 把信号同步当高性能方案 | 每次握手 = `kill()` 系统调用 + 唤醒调度，比管道/`eventfd`/`futex` 都重 |

## HFT / 嵌入式关联

* **「同步点必须在 fork 之前建立」是通用的启动纪律**：任何「父进程先准备好、子进程再
  接手」的启动序列（HFT 里的预热 / 建连 / mmap 共享行情缓冲 / 绑核），都必须
  **在 fork 前**把同步原语建好（pipe / eventfd / 信号掩码）。反过来写就是
  §24.5 那个「父进程永久挂起」的 bug —— 而它在低负载测试机上永远不出现。
* **信号 vs `eventfd`/`pipe` 的取舍**：信号的优势是**不占 fd、开销小**；劣势是**不带
  数据、会合并、与线程交互复杂**。HFT 里更常用 `eventfd` 或 `futex`（Ch30 的
  `futex()` + Ch53 的 POSIX 信号量），信号多用于「进程被杀 / 配置重载」这类低频事件。
* **`SIGUSR1`/`SIGUSR2` 的工程约定**：很多低延迟系统用 `SIGUSR1` 做「停止交易」、
  `SIGUSR2` 做「强制平仓」，配合 `signalfd`（Ch22）把信号变成 fd 事件塞进 `epoll` ——
  这样就统一到一套事件循环里，不会打乱 `epoll` 的等待。**`signalfd` 是「信号」与
  「fd 事件」的桥**，值得记住。
* **嵌入式 / 守护进程**：`daemon` 化的经典流程里，父进程 `fork` 之后**必须等子进程
  发信号再退出**（BSD 的「双 fork + 父等子」），否则调用者拿不到「服务已就绪」的
  保证。那套 `setsid()` + `kill(getppid(), SIGUSR1)` 的写法，机制就是本节这一套。
* **单核 MCU / RTOS 里的对应物**：信号 ≈ RTOS 的「事件标志 / 任务通知」。同样有
  「一次只传一个 bit、会合并」的问题，同样要求**在创建任务之前把同步对象建好**
  （否则中断可能在对象初始化完成前就发通知）。**这是同一类竞态在不同抽象层的复现。**
* **信号是「异步事件」，永远要按异步来处理**：handler 里只做「记个标志 / 写个
  `eventfd`」，真正的工作放到主循环 —— 这就是 `signalfd` / `self-pipe trick`
  的来由，也是 Ch63（alternative I/O）要讲的东西。

<summary>代码自测（Q&A）</summary>

**Q1：为什么后两行（`Child about to signal parent` / `Parent got signal`）的顺序一定有保证，
前两行没有？**

A：后两行的顺序是 `sigsuspend()` 造出来的 —— 父进程必须等到子进程 `kill()` 那一发才醒。
前两行都在 `fork()` 刚返回的位置，谁先跑取决于调度器（§24.4 实测：parent 先 91.6%）。
同步的作用是**把不确定性赶出关键区**，不是消灭它。

**Q2：如果在 `fork()` 之后才 `sigprocmask(SIG_BLOCK)`，最坏会怎样？**

A：子进程若在父进程完成屏蔽之前就 `kill()`，信号会**立刻递送**并被空的 handler 消费掉；
父进程随后才屏蔽、再 `sigsuspend()` —— 此时信号已经用掉了，**父进程永久挂起**。
这个 bug 只在子进程抢得够快时出现，所以看起来像随机故障。

**Q3：`sigsuspend()` 为什么不能用 `pause()` 代替？**

A：`pause()` 和「解屏蔽」是两步，中间有窗口：信号可能在这两步之间到达并丢失。
`sigsuspend()` 把「改掩码 + 挂起」做成**一个原子操作**，堵住了这个窗口。
原书 Ch22 专门讲这个经典竞态。

**Q4：`sigsuspend()` 正常被唤醒时返回什么？**

A：返回 **-1**，`errno = EINTR`。所以代码里必须写成
`if (sigsuspend(&emptyMask) == -1 && errno != EINTR) errExit(...)` ——
直接判 `== -1` 就报错会把正常路径当成错误。

**Q5：为什么 `sigaction()` 也要放在 `fork()` 之前？**

A：因为信号可能在任何时刻到达。若 handler 还没装好而信号已经被解屏蔽递送，
`SIGUSR1` 的**默认动作是终止进程** → 父进程直接被杀。
放在 fork 之前，子进程也顺带继承了 handler（虽然它用不到）。

**Q6：子进程需要自己去解屏蔽 `SIGUSR1` 吗？**

A：本程序不需要（子进程不用这个信号）。但**掩码是继承来的，子进程同样屏蔽着 `SIGUSR1`**，
这一点必须知道。原书 p.528 括号里就提了：需要的话，在 `fork()` 之后在子进程里解屏蔽。

**Q7：双向握手为什么用两个信号？**

A：一个信号无法区分方向。用 `SIGUSR1`（子→父）+ `SIGUSR2`（父→子）各管一个方向，
逻辑才不会自己唤醒自己。实现时**两个信号都必须在 `fork()` 之前屏蔽**。

**Q8：这个方案能不能用来传数据？**

A：不能。信号只传「发生了」这一个 bit，而且标准信号会**合并**（连发两次只 pending 一次）。
要传数据用管道 / 共享内存 / `eventfd`，信号只当「通知」。这也正是原书说「实践中更常用
信号量、文件锁、消息传递」的原因。
