## 本节讲什么

`vfork()` 也创建子进程，但它和 `fork()` 有**两条**根本差异：

| 差异 | `fork()` | `vfork()` |
|------|----------|-----------|
| **地址空间** | 复制（COW） | **不复制** —— 子进程**跑在父进程的地址空间里** |
| **谁先跑** | 不确定（调度器定） | **子进程保证先跑**；父进程**被挂起**，直到子进程 `exec()` 或 `_exit()` |

结论先给：**原书的态度是「能不用就别用」**。原因不是性能（COW 之后 vfork 的性能优势
基本没了），而是它的语义让"写错"变成"直接把父进程搞崩"。

⭐ 本节的核心证明只需要两行输出对比：**子进程 `sleep(3)` 之后仍然先打印**
（说明父进程真的被挂起了），以及**父进程读到的 `istack` 是子进程改过的值**
（说明内存真的共享）。

## 1. 先看接口

```c
#include <unistd.h>

pid_t vfork(void);
```

原书（书 p.523）对返回值的说明与 `fork()` 相同：
*"In parent: returns process ID of child on success, or –1 on error; in successfully
created child: always returns 0"*。

## 2. §24.3 的语义：子进程"借住"在父进程的地址空间里

原书把 vfork 的语义总结成两点（书 p.524）：

> *"Listing 24-4 shows the use of vfork(), demonstrating both of the semantic features
> that distinguish it from fork(): the child shares the parent's memory, and the parent
> is suspended until the child terminates or calls exec()."*

### 完整源码（Listing 24-4，原书书页 524）

[`code/t_vfork.c`](../code/t_vfork.c)

```c
/*************************************************************************\
*                  Copyright (C) Michael Kerrisk, 2026.                   *
*                                                                         *
* This program is free software. You may use, modify, and redistribute it *
* under the terms of the GNU General Public License as published by the   *
* Free Software Foundation, either version 3 or (at your option) any      *
* later version. This program is distributed without any warranty.  See   *
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* t_vfork.c

   Demonstrate the use of vfork() to create a child process.
*/
#define _BSD_SOURCE     /* To get vfork() declaration from <unistd.h>
                           in case _XOPEN_SOURCE >= 700 */
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int istack = 222;

    switch (vfork()) {
    case -1:
        errExit("vfork");

    case 0:             /* Child executes first, in parent's memory space */
        sleep(3);                   /* Even if we sleep for a while,
                                       parent still is not scheduled */
        write(STDOUT_FILENO, "Child executing\n", 16);
        istack *= 3;                /* This change will be seen by parent */
        _exit(EXIT_SUCCESS);

    default:            /* Parent is blocked until child exits */
        write(STDOUT_FILENO, "Parent executing\n", 17);
        printf("istack=%d\n", istack);
        exit(EXIT_SUCCESS);
    }
}
```

### 编译命令

```bash
gcc -O0 -Wall -Wextra -o t_vfork t_vfork.c get_num.c
```

### CE 实测（`t_vfork`）

```text
Child executing
Parent executing
istack=666
```

`execTime = 3027` 毫秒，`exit code = 0`，`diagnostics = 18`。

### 逐条解读

**① `Child executing` 出现在 `Parent executing` 前面** —— 而子进程里面明明有
`sleep(3)`。也就是说：父进程**等了整整 3 秒**才轮到打自己那行。
`execTime = 3027` 就是这 3 秒的证据。这是「父进程被挂起」最直接的观察。

对照 §24.4 的 `fork_whos_on_first`：那里用 `fork()` 时**谁先跑完全没准**（实测
父先 91.6%）。`vfork` 把这件事变成了**确定**的 —— 这就是它当年被拿来做
`fork+exec` 快路径的原因。

**② `istack=666`** —— 父进程的变量**被子进程改了**。`istack` 初值 222，
子进程 `istack *= 3` 得到 666，父进程打印出来的就是 666。这直接证明子进程
**没有自己的 `istack`**：它写的是父进程栈上那一个。

**③ 代码里的小心思，值得单独看**：

| 位置 | 写法 | 为什么这么写 |
|------|------|-------------|
| 子进程 | `write(STDOUT_FILENO, "Child executing\n", 16)` | 用**裸 `write`** 而不是 `printf` —— 因为 stdio 的缓冲区在**共享的**地址空间里，父子用同一个 `FILE` 状态会互相破坏 |
| 父进程 | `write(...)` 之后才 `printf("istack=%d\n")` | 父进程这边已经等到子进程走了，用 `printf` 安全 |
| 子进程 | `_exit(EXIT_SUCCESS)` | **必须** `_exit`，不能 `return`，也不能 `exit()`（见第 4 节） |

**④ ⚠️ 关于那个 `sleep(3)`：它其实"违规"了。**

原书在注释里写 *"Even if we sleep for a while, parent still is not scheduled"* —— 这个
`sleep(3)` 是**故意**放的：它让"父进程被挂起"从"一瞬间的事"变成"肉眼可见的 3 秒"。

但严格按 SUSv3 说，`sleep()` 属于*"calls any other function before successfully
calling `_exit()` or performing an `exec()`"*，也就是**行为未定义**的那一类。
在 glibc/Linux 上它**恰好**能工作（因为 `sleep` 只是个系统调用，不碰栈上的复杂状态），
但这是"能跑"，不是"保证能跑"。**读原书代码时要能分辨这种"演示性违规"。**

## 3. 为什么 vfork 里能安全做的事只有"操作 fd"

原书（书 p.525）明确列了边界：

> *"There are a few things that the child process can do between vfork() and exec()
> without affecting the parent. Among these are operations on open file descriptors
> (but not stdio file streams). Since the file descriptor table for each process is
> maintained in kernel space (Section 5.4) and is duplicated during vfork(), the child
> process can perform file descriptor operations without affecting the parent."*

拆开看就三句：

1. **fd 表在内核里**（`struct files_struct` 挂在 `task_struct` 上，不在用户地址空间）；
2. vfork **仍然复制** fd 表（和 fork 一样走 `copy_files()`）；
3. 所以子进程 `close(0)` 只改自己那张表，**父进程不受影响**。

⚠️ 但 **stdio 流（`FILE *`）不行** —— `stdin`/`stdout` 这些 `FILE` 结构和它们的缓冲区
**就在共享的用户地址空间里**。子进程往里写，父进程醒来后看到的是**被改过的**状态。
这就是原书 Listing 24-4 里子进程用 `write()` 而不用 `printf()` 的原因。

这一条正是**习题 24-2** 的题面，官方给了参考解 `vfork_fd_test.c`（见 §24.7）。

## 4. SUSv3 规定的「未定义行为」三条

原书（书 p.525）原样引了这三条：

> *"SUSv3 says that the behavior of a program is undefined if it:*
> *a) modifies any data other than a variable of type `pid_t` used to store the return
> value of `vfork()`;*
> *b) returns from the function in which `vfork()` was called; or*
> *c) calls any other function before successfully calling `_exit()` or performing an
> `exec()`."*

为什么是这三条？逐条对上内核机制：

| 违规 | 后果 | 机制 |
|------|------|------|
| a) 改别的数据 | 直接改到**父进程**的内存 | 共享 `mm_struct`（`CLONE_VM`） |
| b) 从函数返回 | **栈被搞坏**，典型 SIGSEGV | 父子共用**同一段栈**；子进程返回时把父进程的栈帧弹掉了 |
| c) 调别的函数 | 同上（大多是栈操作）；还可能破坏 libc 状态 | 库函数的局部变量/缓冲区都在共享栈上 |

原书为此举了个类比（书 p.525）：*"This is similar to the example described in
Section 6.8 of trying to `longjmp()` into a function from which a return has already
been performed."* —— 对应本仓库 [C 语言模块的 §6.8](../../../01-c-language/README.md)
那节讲的"跳回已返回的函数"。

## 5. 为什么现在不该用它

| 年代 | 情况 |
|------|------|
| 早期 UNIX / 无 COW 的 `fork` | `fork` 要**真的拷**整个地址空间，`vfork+exec` 省掉这一大笔开销，是刚需 |
| 有 COW 之后 | `fork` 只复制页表、不拷内存 ⇒ **省下的那点开销不再重要** |
| 今天 | `vfork` 语义危险（上面三条 UB）、且**可移植性差**（POSIX 曾一度把它移除又加回）。原书建议：**除非有明确理由，否则用 `fork()`** |

⭐ 现在唯一还"必须有"的场景是 **NOMMU 平台**（uClinux 之类）：没有 MMU 就没有 COW，
`fork()` 根本实现不了，只能 `vfork()+exec`。

## 源码坐标

| 机制 | 坐标（Linux v6.6） |
|------|-------------------|
| **`vfork()` 就是一次特定标志的 `clone`** | `kernel/fork.c:3006` `SYSCALL_DEFINE0(vfork)`：`.flags = CLONE_VFORK \| CLONE_VM`，`.exit_signal = SIGCHLD` |
| 共享地址空间（不复制） | `kernel/fork.c:1708` `copy_mm()`：`kernel/fork.c:1731` `if (clone_flags & CLONE_VM) { mmget(oldmm); mm = oldmm; }` —— **与 fork 的分水岭就在这一行** |
| 父进程被挂起 | `kernel/fork.c:2946` `if (clone_flags & CLONE_VFORK) { if (!wait_for_vfork_done(p, &vfork)) ... }`；挂起点 `kernel/fork.c:1583` `wait_for_vfork_done()` |
| 子进程何时唤醒父进程 | `kernel/fork.c:1645` `mm_release()` 里 `if (tsk->vfork_done) complete_vfork_done(tsk);` —— 子进程 **`exec()` 或退出**时释放 mm，就在这一刻唤醒父进程 |
| 唤醒实现 | `kernel/fork.c:1570` `complete_vfork_done()` |
| `vfork_done` 字段置位 | `kernel/fork.c:2927` `if (clone_flags & CLONE_VFORK) { p->vfork_done = &vfork; ... }` |
| fd 表仍然复制 | `kernel/fork.c:1766` `copy_files()` → `fs/file.c:316` `dup_fd()`（与 fork 同一条路径） |
| 无 MMU 上的 `fork` | `kernel/fork.c:3001` 附近（`SYSCALL_DEFINE0(fork)` 的 `#ifndef CONFIG_MMU` 分支返回 `-EINVAL`，注释写着 `/* can not support in nommu mode */`） |

⭐ 把上面几行连起来就是一句话：**`vfork() == clone(CLONE_VM | CLONE_VFORK | SIGCHLD)`**。
`CLONE_VM` 负责"共享内存"（`copy_mm` 少走 `dup_mm`），`CLONE_VFORK` 负责"父进程睡到
子进程 exec/exit"（`wait_for_vfork_done` + `mm_release` 里的 `complete_vfork_done`）。

## 常见坑

| # | 坑 | 说明 |
|---|----|------|
| 1 | 在 vfork 子进程里 `return` | SUSv3 明说未定义；实际后果通常是 SIGSEGV（栈被拆） |
| 2 | 在 vfork 子进程里 `exit()` | `exit()` 会刷 stdio、跑 `atexit`，都碰共享状态。必须 `_exit()` |
| 3 | 以为「子进程改的东西父进程看不到」 | 恰恰相反，**看得到**（本节 `istack=666`） |
| 4 | 以为 `vfork` 也复制 fd 表 → 想拿它当"fd 隔离"用 | fd 表**确实复制**，但那是"顺便"，别依赖它做设计 |
| 5 | 以为 `vfork` 比 `fork` **快**所以该用 | COW 之后差距很小；原书结论是**避免使用** |
| 6 | 把 `sleep()`/`printf()` 放在 vfork 子进程里学样子 | 原书是为了"让挂起可见"故意违规的演示；生产代码别抄 |
| 7 | 在 NOMMU 平台上用 `fork` | 内核里直接 `-EINVAL`（`kernel/fork.c` 的 `#ifndef CONFIG_MMU` 分支） |

## HFT / 嵌入式关联

* **`vfork` 是 `posix_spawn` 类实现的底层手法之一**：glibc 的 `posix_spawn` 在没有
  `clone3(CLONE_VM|CLONE_VFORK)` 快路径时，就走"vfork 一个子进程 → 子进程里只做
  fd 操作 → `exec`"。理解"子进程在 exec 之前只能碰 fd"，就知道为什么 `posix_spawn`
  的 `file_actions` 能精确表达"重定向 fd"却表达不了太复杂的东西。
* **HFT 冷启动延迟**：策略进程 fork+exec 的启动路径上，`fork` 的页表复制成本与
  父进程地址空间大小成正比。实测手法是把"父进程地址空间做小"（别在父进程里
  mmap 大块行情缓冲），而不是换 vfork —— 因为 COW 下 `dup_mm` 仍要复制**页表**。
* **嵌入式 / NOMMU（uClinux、部分 Cortex-M + Linux 变体）**：`fork()` 直接不可用
  （内核返回 `-EINVAL`），`vfork()+exec()` 是唯一路径。这也是 BusyBox 在 NOMMU 下
  会编译出不同代码的原因。
* **`vfork` 与"共享栈"的坑在裸机/RTOS 移植里换个名字出现**：本质是"两个执行流用
  同一段栈" —— 任何中断服务例程在共享栈上做函数调用都会踩到同一类问题。
  理解了 vfork 为什么禁止 `return`，就理解了中断上下文的栈纪律。

<summary>代码自测（Q&A）</summary>

**Q1：`t_vfork` 里子进程 `sleep(3)`，为什么 `Parent executing` 还是排在它后面？**

A：因为 `vfork` 的语义是**父进程挂起，直到子进程 `exec()` 或 `_exit()`**。
这 3 秒里父进程根本没被调度。`execTime = 3027` 毫秒就是这段挂起时间；
`fork` 版本（Listing 24-1）里那 3 秒是父进程**自己** `sleep` 的，性质完全不同。

**Q2：`istack=666` 说明了什么？**

A：说明子进程**没有**自己的 `istack`。它写的是父进程栈上的那一个变量
（`222 * 3 = 666`）。这是"共享地址空间"（`CLONE_VM`）的直接观察。

**Q3：为什么子进程用 `write()` 而父进程能用 `printf()`？**

A：stdio 的 `FILE` 对象和缓冲区**在用户地址空间**，而 vfork 子进程和父进程共用这段
空间。子进程动 stdio 就等于动父进程的 stdio 状态。用裸 `write()` 绕过 stdio 才安全。
父进程那侧已经等子进程结束了（`wait` 语义由 vfork 自动保证），所以 `printf` 没问题。

**Q4：vfork 子进程里 `close(0)` 会不会把父进程的 0 号 fd 也关掉？**

A：不会。fd **表**在内核里（`struct files_struct`），vfork 仍然通过
`copy_files()`→`dup_fd()` 复制它。这正是习题 24-2 的答案，官方解
`vfork_fd_test.c` 里父进程连关两次 stdout：第一次成功、第二次失败（`EBADF`），
说明子进程那次 `close` 没影响到父进程。

**Q5：既然 COW 让 fork 很便宜，vfork 还剩什么价值？**

A：两个：① **NOMMU 平台**（没有 MMU 就没法 COW，`fork` 直接不可用）；
② **极端的 fork+exec 快路径**（`posix_spawn`/`clone3` 的实现里省掉复制页表那一步）。
除此之外，原书的态度是**避免使用**。

**Q6：为什么 vfork 子进程里调 `sleep()` 是"违规"的？**

A：SUSv3 允许的只有「操作 fd」和「执行 `_exit`/`exec`」，其他函数调用一律 UB
（条款 c）。原书放 `sleep(3)` 是为了让"父进程被挂起"这件事**看得见** ——
是一个刻意为之的演示性违规。生产代码里不要在 vfork 子进程里调任何库函数。

**Q7：vfork 之后父进程是"睡在"哪里？**

A：睡在内核里的一个 completion 上：`kernel/fork.c:2946` 的
`wait_for_vfork_done(p, &vfork)`。子进程在 `exec()` 或退出时释放自己的 `mm`，
`mm_release()`（`kernel/fork.c:1645`）发现 `tsk->vfork_done` 非空就
`complete_vfork_done()` 把父进程唤醒。

</details>
