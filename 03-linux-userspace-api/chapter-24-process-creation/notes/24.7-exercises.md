## 24-1：`fork(); fork(); fork();` 之后有几个新进程？

### 答案

**新产生 7 个进程，加上原来那个一共 8 个。**

为什么是 `2³` 而不是 3？因为**每一次 `fork()` 都被「当时已经存在的所有进程」各执行一遍**：

| 第几次 `fork()` | 执行它的进程数 | 之后总进程数 |
|-----------------|----------------|--------------|
| 开始 | 1 | 1 |
| 第 1 次 | 1 | 2 |
| 第 2 次 | 2 | 4 |
| 第 3 次 | 4 | **8** |

新产生的进程数 = 8 − 1 = **7**。

⭐ 这就是「fork 炸弹」的数学形式：`fork()` 的次数是线性增长，进程数却是**指数增长**。

### 实测（`ex24_1_fork_count`，本仓库自写解）

程序用一根**在任何 `fork()` 之前就建好的管道**把 7 个新进程的 `pid`/`ppid` 收集回来
（管道要在 fork 之前建，否则后 fork 出来的进程看不到它 —— 见 `code/ex24_1_fork_count.c` 里的注释）：

```text
原始进程 pid=2
--- 开始 fork(); fork(); fork(); ---
新进程 pid=4      ppid=2
新进程 pid=3      ppid=2
新进程 pid=5      ppid=2
新进程 pid=6      ppid=4
新进程 pid=7      ppid=1
新进程 pid=9      ppid=7
新进程 pid=8      ppid=1
--- 新进程行数 = 7 ---
--- 进程总数   = 8 ---
（2^3 = 8 个进程并存；新产生 8 - 1 = 7 个。行的顺序不定，
  因为 fork 之后父子谁先跑由调度器决定 —— 见 §24.4）
```

`execTime = 31` 毫秒，`exit code = 0`，`diagnostics = 7`。

### 逐条解读

**① 「新进程行数 = 7」与推导一致。** 三个 `fork()` 之后 8 个进程，其中 7 个是新的。

**② `pid` 的出现顺序是乱的**：`4, 3, 5, 6, 7, 9, 8`。这就是 §24.4 讲的
「fork 之后谁先跑不确定」的又一个现场 —— **连往管道里写一行这么小的动作，顺序都不保证**。

**③ `ppid=1` 出现了两次**（`pid=7` 和 `pid=8`）。这不是 bug，而是**孤儿进程被收养**：

* 这两个进程在打印时，它们的**父进程已经退出了**；
* 内核在父进程退出时把子进程的父指针改指向 `init`（`PID 1`）—— 实测沙箱里 `init` 在
  容器 PID namespace 里的编号就是 **1**；
* 于是它们读到 `getppid() == 1`。

这正好是 **Ch26（Monitoring Child Processes）** 的引子：**父进程必须 `wait()` 子进程**，
否则子进程会变僵尸；而如果父进程自己先死，子进程就变孤儿，由 `init` 兜底。

**④ `ppid` 链本身也能看出 fork 的树形结构**：`pid=4` 的 ppid 是 `2`（原始进程），
`pid=6` 的 ppid 是 `4`（它是 pid=4 那个进程 fork 出来的）。
**8 个进程构成一棵三层的二叉树**（每个进程最多 fork 出 2 个孩子）。

## 24-2：证明 vfork 之后子进程 `close` 不影响父进程

### 官方解（`procexec/vfork_fd_test.c`）

```c
* the file COPYING.gpl-v3 for details.                                    *
\*************************************************************************/

/* vfork_fd_test.c

   Demonstrate that a vfork()ed child has a separate set of file descriptors
   from its parent.
*/
#define _BSD_SOURCE     /* To get vfork() declaration from <unistd.h>
                           in case _XOPEN_SOURCE >= 700 */
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    switch (vfork()) {
    case -1: errExit("vfork");

    case 0: if (close(STDOUT_FILENO) == -1)
                errMsg("close - child");
            _exit(EXIT_SUCCESS);

    default: break;
    }

    /* Now parent closes STDOUT_FILENO twice: only the second close
       should fail, indicating that the close(STDOUT_FILENO) by the
       child did not affect the parent. */

    if (close(STDOUT_FILENO) == -1)
        errMsg("close");
    if (close(STDOUT_FILENO) == -1)
        errMsg("close");

    exit(EXIT_SUCCESS);
}
```

### 编译命令

```bash
gcc -O0 -Wall -Wextra -o vfork_fd_test vfork_fd_test.c get_num.c
```

### CE 实测（`vfork_fd_test`）

程序的全部输出都在 **stderr**（因为 stdout 被关掉了）：

```text
  ERROR [?UNKNOWN? Bad file descriptor] close
```

`execTime = 17` 毫秒，`exit code = 0`，`diagnostics = 18`。

### 逐条解读

**① 为什么只有**一行**错误 —— 这正是证明的关键。**

程序里父进程**连关两次** stdout：

| 父进程的第几次 `close(STDOUT_FILENO)` | 期望结果 | 如果 fd 表是**共享**的会怎样 |
|--------------------------------------|----------|------------------------------|
| 第 1 次 | **成功**（无输出） | 失败 → 会多打一行 `close` 错误 |
| 第 2 次 | 失败（`EBADF`）→ **打一行** | 失败 → 打一行 |

实测**只有一行** ⇒ 父进程第 1 次 `close` 成功了 ⇒ **子进程那次 `close` 没有影响父进程**
⇒ vfork 之后父子各有**自己的 fd 表**。

**② 机制：fd 表在内核里，vfork 仍然复制它。**

| 层 | 说明 |
|----|------|
| 用户地址空间 | vfork **不复制**（`CLONE_VM`）—— 所以 `istack` 那种变量是共享的 |
| fd 表（`struct files_struct`） | **在内核**，挂在 `task_struct` 上，vfork 走的是和 fork 一样的 `copy_files()` → `dup_fd()` |

原书 p.525 对这条的措辞很精确：

> *"Since the file descriptor table for each process is maintained in kernel space
> (Section 5.4) and is duplicated during `vfork()`, the child process can perform file
> descriptor operations without affecting the parent."*

**③ 但 `FILE *`（stdio 流）不行。** stdio 的 `FILE` 结构体和缓冲区都在**用户地址空间**，
vfork 子进程和父进程共用这一段 —— 子进程动 stdio 就等于动父进程的 stdio。
这就是原书 Listing 24-4（`t_vfork.c`）里子进程用**裸 `write()`** 而不是 `printf()` 的原因。
**「可以操作 fd，不可以操作 stdio 流」** —— 记住这条边界。

**④ `[?UNKNOWN? Bad file descriptor]` 里的 `[?UNKNOWN?]` 是本仓库替身的产物**：
CE 上的 `tlpi_hdr.h` 是精简替身，没有 `ename[]` 这张错误名表，所以 `errMsg()` 拿不到
`EBADF` 的符号名，退化成了 `?UNKNOWN?`。**`Bad file descriptor` 才是真正的 `strerror(errno)`。**

## 24-3：怎么在某一刻拿到 core dump，同时让进程继续跑？

### 思路

**`fork()` 一个子进程，让子进程去死。**

* 子进程的地址空间是父进程**那一刻的副本**（COW）⇒ 子进程崩溃产生的 core 里，
  就是父进程当时的完整内存映像；
* 父进程 `wait()` 收尸之后**继续执行** —— 这正是题目要求的
  *"while letting the process continue execution"*。

**不能**用「直接给自己发 `SIGSEGV`」也不行的原因：那样进程就死了，谈不上「继续执行」。
所以「复制一份来死」是唯一干净的做法。

### 自写解（原书没有给这一题的答案）

[`code/ex24_3_core_dump.c`](../code/ex24_3_core_dump.c)

```c
/* ex24_3_core_dump.c

   ⚠️ 本仓库自写 —— 习题 24-3 的解，**原书没有给这一题的答案，也没有配套程序**。

   习题 24-3（原书书页 530）：
     "Assuming that we can modify the program source code, how could we get a
      core dump of a process at a given moment in time, while letting the
      process continue execution?"

   思路：**fork 一个子进程，让子进程去死。**
        子进程的地址空间是父进程那一刻的副本（写时复制），所以子进程崩溃产生的
        core 文件里，就是父进程当时的完整内存映像。父进程 `wait()` 收尸后继续跑。

   本程序顺便实测三件事（这些是「能不能拿到 core」的硬前提）：
     ① 当前 RLIMIT_CORE 是多少 —— 是 0 就根本写不出 core 文件
     ② 能不能把它抬上去（非 root 提升 hard limit 会被拒）
     ③ wait() 的 status 怎么表达「被信号杀死」和「有没有 core」

   编译（自包含）：
     gcc -O0 -Wall -Wextra -o ex24_3_core_dump ex24_3_core_dump.c
*/

#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

static void showFile(const char *path)
{
    char buf[256];
    ssize_t n;
    int fd = open(path, O_RDONLY);

    if (fd == -1) {
        printf("  %-34s = <打不开> errno=%d (%s)\n", path, errno, strerror(errno));
        return;
    }
    n = read(fd, buf, sizeof(buf) - 1);
    if (n < 0)
        n = 0;
    buf[n] = '\0';
    while (n > 0 && (buf[n - 1] == '\n' || buf[n - 1] == '\r'))
        buf[--n] = '\0';
    printf("  %-34s = \"%s\"\n", path, buf);
    close(fd);
}

static void showCoreLimit(const char *tag)
{
    struct rlimit rl;

    if (getrlimit(RLIMIT_CORE, &rl) == 0)
        printf("  %s RLIMIT_CORE = %ld / %ld   （soft / hard，单位字节；0 = 不写 core）\n",
               tag, (long) rl.rlim_cur, (long) rl.rlim_max);
}

int main(void)
{
    struct rlimit rl;
    pid_t pid;
    int status;

    setbuf(stdout, NULL);

    printf("=== ① 动手之前的状态 ===\n");
    showCoreLimit("[初始]");
    showFile("/proc/sys/kernel/core_pattern");

    printf("\n=== ② 试着把 soft 和 hard 一起抬到无限 ===\n");
    rl.rlim_cur = RLIM_INFINITY;
    rl.rlim_max = RLIM_INFINITY;
    if (setrlimit(RLIMIT_CORE, &rl) == -1)
        printf("  setrlimit(INFINITY / INFINITY) 失败：errno=%d (%s)\n",
               errno, strerror(errno));
    else
        printf("  setrlimit(INFINITY / INFINITY) 成功\n");
    showCoreLimit("[之后]");

    printf("\n=== ③ 退一步：只把 soft 抬到 hard 允许的上限 ===\n");
    if (getrlimit(RLIMIT_CORE, &rl) == 0) {
        rl.rlim_cur = rl.rlim_max;      /* hard 是 0 的话，抬完还是 0 */
        if (setrlimit(RLIMIT_CORE, &rl) == -1)
            printf("  setrlimit(soft -> hard) 失败：errno=%d (%s)\n",
                   errno, strerror(errno));
        else
            printf("  setrlimit(soft -> hard) 成功（soft 现在 = hard）\n");
    }
    showCoreLimit("[之后]");

    printf("\n=== ④ 关键一步：fork 一个子进程让它崩，父进程继续跑 ===\n");
    pid = fork();
    if (pid == -1) {
        printf("  fork 失败 errno=%d (%s)\n", errno, strerror(errno));
        return 1;
    }

    if (pid == 0) {                     /* 子进程：替父进程去死 */
        printf("  子进程 pid=%ld —— 即将 abort()（SIGABRT 的默认动作是终止 + core）\n",
               (long) getpid());
        fflush(NULL);
        abort();                        /* 不返回 */
        _exit(99);                      /* 万一 abort 返回了，别继续往下跑 */
    }

    if (wait(&status) == -1) {
        printf("  wait 失败 errno=%d (%s)\n", errno, strerror(errno));
        return 1;
    }

    printf("  父进程收尸：子进程 pid=%ld  status=%d\n", (long) pid, status);
    printf("    WIFSIGNALED = %d   （1 = 子进程是被信号杀死的）\n", WIFSIGNALED(status));
    printf("    WTERMSIG    = %d   （6 = SIGABRT）\n", WTERMSIG(status));
    printf("    WCOREDUMP   = %d   （= status & 0x80：非 0 = 内核走完了 coredump 流程，"
           "但**不等于**磁盘上有 core 文件）\n", WCOREDUMP(status));

    printf("\n=== ⑤ 父进程还活着，继续往下执行 ===\n");
    printf("  父进程 pid=%ld —— 这一行能打出来，就是习题要求的"
           "「while letting the process continue execution」\n", (long) getpid());

    printf("\n=== ⑥ 找找看有没有 core 文件落盘 ===\n");
    showFile("./core");
    showFile("/core");
    printf("  access(\"./core\", F_OK) = %d   （0 = 存在）\n", access("./core", F_OK));

    return 0;
}
```

### CE 实测（`ex24_3_core_dump`）

```text

  [初始] RLIMIT_CORE = 0 / 0   （soft / hard，单位字节；0 = 不写 core）
  /proc/sys/kernel/core_pattern      = "|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -F%F -- %E"

=== ② 试着把 soft 和 hard 一起抬到无限 ===

  父进程 pid=2 —— 这一行能打出来，就是习题要求的「while letting the process continue execution」

=== ⑥ 找找看有没有 core 文件落盘 ===
  ./core                             = <打不开> errno=2 (No such file or directory)
  /core                              = <打不开> errno=2 (No such file or directory)
  access("./core", F_OK) = -1   （0 = 存在）
```

`execTime = 172` 毫秒，`exit code = 0`，`diagnostics = 0`。

### 逐条解读

**① 第 ⑤ 段就是题目的答案**：父进程活着走到了下一行 —— 「拿到 core」和「进程继续跑」
这两件事同时做到了。

**② `status = 134`，拆开看是 `0x86`**：

| 位 | 值 | 含义 |
|----|----|------|
| 低 7 位 | `134 & 0x7f = 6` | `WTERMSIG` = **6** = `SIGABRT`（`abort()` 发的信号） |
| bit 7 | `0x80` | `WCOREDUMP` 位被置上 |

**③ `WCOREDUMP` 不是布尔值，是位掩码。** glibc 里它长这样
（`glibc 2.39`，`bits/waitstatus.h`）：

```c
#define	__WCOREDUMP(status)	((status) & __WCOREFLAG)   /* 第 53 行 */
#define	__WCOREFLAG		0x80                       /* 第 59 行 */
```

所以它的取值**只能是 0 或 128**。实测拿到 128 是正常的 —— **别以为哪里出错了**。

**④ ⭐ 但 `WCOREDUMP = 128` **不代表**磁盘上有 core 文件。** 实测第 ⑥ 段：
`./core` 和 `/core` 都 `ENOENT`，`access()` 返回 −1。

原因有两个，都在实测输出里：

| 原因 | 实测证据 |
|------|----------|
| `RLIMIT_CORE` 是 **0** | 第 ① 段 `RLIMIT_CORE = 0 / 0` |
| 而且**提不上去** | 第 ② 段 `setrlimit(INFINITY/INFINITY)` → `errno=1 (Operation not permitted)`（非 root 不能提 hard limit）；第 ③ 段退一步只提 soft，因为 hard 就是 0，抬完还是 0 |
| `core_pattern` 是**管道**（以 `\|` 开头） | 第 ① 段：`\|/usr/share/apport/apport -p%p -s%s ...` |

**⑤ 为什么 `WCOREDUMP` 位还是被置上了？** 因为 `core_pattern` 是管道模式，
而**管道模式下内核根本不看 `RLIMIT_CORE`**（`fs/coredump.c:613`）：

```c
	if (ispipe) {
		...
		if (cprm.limit == 1) {
			/* See umh_pipe_setup() which sets RLIMIT_CORE = 1. ...
			 * Normally core limits are irrelevant to pipes, since
			 * we're not writing to the file system, but we use
			 * cprm.limit of 1 here as a special value, this is a
			 * consistent way to catch recursive crashes.
			 */
			...
			goto fail_unlock;
		}
		cprm.limit = RLIM_INFINITY;
```

—— `cprm.limit = RLIM_INFINITY` 这一行（`fs/coredump.c:613`）把 `RLIMIT_CORE = 0` 抹掉了。
于是内核认为 coredump 流程走完了，在收尾时置位（`fs/coredump.c:438`）：

```c
	if (core_dumped && !__fatal_signal_pending(current))
		current->signal->group_exit_code |= 0x80;
```

**这就是那个 `0x80` 位的来源。** 至于数据实际写去了哪儿（apport 在容器里能不能跑、
写不写得进 `/var/crash`），**内核不管** —— 所以「置位」和「磁盘上有文件」是两件事。

**⑥ 对照：文件模式（`core_pattern` 不以 `\|` 开头）** 下 `RLIMIT_CORE = 0` 会**直接放弃**
（`fs/coredump.c:654`）：

```c
		if (cprm.limit < binfmt->min_coredump)
			goto fail_unlock;
```

**⑦ 工程结论**：要在容器里真的拿到 core 文件，得同时满足
**（a）`RLIMIT_CORE` > 0**（且 hard limit 允许）**（b）`core_pattern` 指向一个容器内可写、
可执行的落盘路径**（而不是宿主上的 apport）。这两条在多数容器默认配置下都不满足 ——
**所以「core dump 拿不到」在容器里是常态，不是程序写错了。**

⭐ 顺带一个实用替代方案：不追求 core 文件，而是用 `gdb -p <pid>` 的 `gcore` 命令
在**另一个进程**里抓快照 —— 那才是生产环境里更常用的手法（进程完全不受影响）。

## 24-4：在别的 UNIX 实现上实验 Listing 24-5

### 题目要求

拿 §24.4 的 `fork_whos_on_first.c` 到别的 UNIX 实现上跑，看它们怎么调度父子。

### 本仓库怎么做的

CE 沙箱只有 Linux，**没法跑别的 UNIX**（Solaris / macOS / BSD 都不在）。所以这里
换了一个**同时代对照**：**跨内核版本**。做法是抓 upstream 各版本的
`kernel/sched/fair.c` 直接看代码（这也是原书那句「2.6.32 起又改回 parent 先」能验证的
唯一途径 —— 我们没有 2.6.32 的机器）。

结果（详见 §24.4 第 3.3 节）：

| 版本 | `sysctl_sched_child_runs_first` | 行为 |
|------|--------------------------------|------|
| v6.5 | 有定义 + **有消费点** | 开关真的能改顺序 |
| v6.6 | 有定义 + **零消费点** | 开关已成空壳 |
| v6.7 起 | **定义已删除** | 连文件都没有了 |
| 实测沙箱（内核 7.0.0-1012-aws） | —— | `/proc/sys/kernel/sched_child_runs_first` → **`ENOENT`** |

### 原书给的对照数据（书 p.526–527）

| 系统 | 条件 | 结果 |
|------|------|------|
| Linux/x86-32 **2.2.19** | 100 万子进程 | parent 先 **99.97%**（仅 332 例 child 先） |
| Linux/x86-32 **2.6.30** | 100 万子进程、机器较忙 | child 先 **99.98%** |
| 本仓库实测（6.6+ / EEVDF） | 1000 子进程、2 核、`nice=19` | parent 先 **91.6%** / child 先 **8.4%** |

⭐ 原书特别提醒**百分比依赖系统负载**：

> *"Using the program in Listing 24-5 to create 1 million child processes on one busy
> Linux/x86-32 system running kernel 2.6.30 showed that, in 99.98% of cases, the child
> process displayed its message first. (The precise percentage depends on factors such as
> system load.)"*

本仓库的实测把这条**看得很清楚**：`j ∈ [800, 860]` 那 61 次里 56 次 child 先（92%），
紧接的 `j ∈ [861, 999]` 共 139 次**一次都没有**。**同一台机器、同一个程序、相邻的时间**，
结论完全相反 —— 这就是「依赖系统负载」。

### 如果你真的要在别的 UNIX 上跑

方法（原书的脚本思路，`procexec/fork_whos_on_first.count.awk`）：

1. 先确认那个系统上 `vfork`/`fork` 的语义，以及有没有 `sched_child_runs_first` 之类开关；
2. 把子进程数开大（原书用 **100 万**），因为单次运行看不出分布；
3. 统计方式：按 `j` 配对，看每对里谁先出现；
4. **记录机器负载和 CPU 数** —— 否则数字没有可比性。

本仓库的实测就是按这四条做的（只是子进程数降到 1000，因为 CE 有 **32 KB 采集上限**）。

## 24-5：让**子进程**也等父进程（双向握手）

### 题目要求

在 Listing 24-6（`fork_sig_sync.c`）里，子进程也要等父进程完成某些动作，程序要怎么改？

### 自写解（原书没有给这一题的答案）

[`code/ex24_5_fork_sig_sync2.c`](../code/ex24_5_fork_sig_sync2.c)

```c
/* ex24_5_fork_sig_sync2.c

   ⚠️ 本仓库自写 —— 原书习题 24-5 **没有官方解答文件**
      （官方只给了习题 24-2 的解：procexec/vfork_fd_test.c）。

   习题 24-5：如果**子进程也要等父进程**完成某个动作，Listing 24-6
              （fork_sig_sync.c）需要怎么改？

   答：一个信号不够了，要**两个**信号做双向握手：
         子 → 父 用 SIGUSR1（"我干完了"）
         父 → 子 用 SIGUSR2（"我干完了"）
       并且**两个信号都要在 fork() 之前屏蔽**。原因是 Listing 24-6 里
       已经写明的那条：如果先 fork 再屏蔽，那么"信号已经发出"与"我开始屏蔽"
       之间存在窗口，对方那一枪可能在你 sigsuspend 之前就打完了 ——
       这正是要避免的那个竞态。

   本程序的输出**顺序是确定的**（靠信号保证），这跟 Listing 24-5 的
   fork_whos_on_first 形成对照：那里没有同步，先后完全看调度器。

   编译（需要 curr_time.c 提供 currTime()，见 code/README.md）：
     gcc -O0 -Wall -Wextra -o ex24_5_fork_sig_sync2 \
         ex24_5_fork_sig_sync2.c curr_time.c
*/

#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#include "curr_time.h"          /* currTime() */

#define CHILD_READY SIGUSR1     /* 子 → 父 */
#define PARENT_DONE SIGUSR2     /* 父 → 子 */

static void die(const char *msg)
{
    fprintf(stderr, "ERROR: %s: %s\n", msg, strerror(errno));
    exit(EXIT_FAILURE);
}

static void handler(int sig)    /* 什么都不做，只为让 sigsuspend 醒过来 */
{
    (void) sig;
}

static void waitFor(sigset_t *emptyMask)
{
    if (sigsuspend(emptyMask) == -1 && errno != EINTR)
        die("sigsuspend");
}

int main(void)
{
    pid_t childPid;
    sigset_t blockMask, emptyMask;
    struct sigaction sa;

    setvbuf(stdout, NULL, _IONBF, 0);

    /* ---------- 屏蔽**两个**信号：必须在 fork() 之前 ---------- */
    sigemptyset(&blockMask);
    sigaddset(&blockMask, CHILD_READY);
    sigaddset(&blockMask, PARENT_DONE);
    if (sigprocmask(SIG_BLOCK, &blockMask, NULL) == -1)
        die("sigprocmask(SIG_BLOCK)");

    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sa.sa_handler = handler;
    if (sigaction(CHILD_READY, &sa, NULL) == -1)
        die("sigaction(SIGUSR1)");
    if (sigaction(PARENT_DONE, &sa, NULL) == -1)
        die("sigaction(SIGUSR2)");

    switch (childPid = fork()) {
    case -1:
        die("fork");

    case 0:   /* ---------- 子进程 ---------- */
        printf("[%s %ld] Child  started - working\n",
                currTime("%T"), (long) getpid());
        sleep(2);                                   /* 模拟干活 */

        printf("[%s %ld] Child  -> SIGUSR1 to parent\n",
                currTime("%T"), (long) getpid());
        if (kill(getppid(), CHILD_READY) == -1)
            die("kill(SIGUSR1)");

        /* 反过来等父进程（习题 24-5 新增的部分）*/
        printf("[%s %ld] Child  waiting for parent\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);

        printf("[%s %ld] Child  got SIGUSR2 -> done\n",
                currTime("%T"), (long) getpid());
        _exit(EXIT_SUCCESS);

    default:  /* ---------- 父进程 ---------- */
        printf("[%s %ld] Parent waiting for child\n",
                currTime("%T"), (long) getpid());
        sigemptyset(&emptyMask);
        waitFor(&emptyMask);                        /* 等 SIGUSR1 */

        printf("[%s %ld] Parent got SIGUSR1 - working\n",
                currTime("%T"), (long) getpid());
        sleep(1);                                   /* 模拟干活 */

        printf("[%s %ld] Parent -> SIGUSR2 to child\n",
                currTime("%T"), (long) getpid());
        if (kill(childPid, PARENT_DONE) == -1)
            die("kill(SIGUSR2)");

        if (wait(NULL) == -1)
            die("wait");
        printf("[%s %ld] Parent done\n", currTime("%T"), (long) getpid());
        exit(EXIT_SUCCESS);
    }
}
```

**核心改动三处**：

| # | 改动 | 为什么 |
|---|------|--------|
| 1 | 用**两个**信号：`SIGUSR1`（子→父）、`SIGUSR2`（父→子） | 一个信号分不清方向，容易自己唤醒自己 |
| 2 | **两个信号都要在 `fork()` 之前屏蔽** | 与 §24.5 同一个理由：必须赶在信号可能到达之前把门关上 |
| 3 | 父子的 `sigsuspend()` / `kill()` 各写两遍 | 握手是**两轮**：子做完 → 通知父 → 父做完 → 通知子 |

### CE 实测（`ex24_5_fork_sig_sync2`）

```text
[05:40:31 2] Parent waiting for child
[05:40:31 3] Child  started - working
[05:40:33 3] Child  -> SIGUSR1 to parent
[05:40:33 3] Child  waiting for parent
[05:40:33 2] Parent got SIGUSR1 - working
[05:40:34 2] Parent -> SIGUSR2 to child
[05:40:34 3] Child  got SIGUSR2 -> done
[05:40:34 2] Parent done
```

`execTime = 3018` 毫秒，`exit code = 0`，`diagnostics = 7`。

### 逐条解读

**① 8 行输出，顺序是**确定**的**（从第 3 行开始）：

```
子做完 → SIGUSR1 → 父开始
父做完 → SIGUSR2 → 子结束
```

每一个「箭头」都由一次 `kill()` + 一次 `sigsuspend()` 完成 —— **谁都不可能越过对方先走**。

**② 前两行的顺序仍然自由**（`Parent waiting for child` 在 `Child started - working` 前面，
但这一次恰好父进程先跑）—— 和 §24.5 一样：**同步消除的是关键区里的不确定性，
不是全部不确定性**。

**③ 时间戳显示两段等待**：`31` → `33`（子进程干活 2 秒），`33` → `34`（父进程干活 1 秒）。
`execTime = 3018` 毫秒 ≈ 3 秒，与两段等待之和一致。

**④ 为什么不用「一个信号来回发」？** 因为接收方无法区分「这个信号是我在等的那一发，
还是我刚发出去绕回来的」。用两个信号，语义就一对一了：
**`SIGUSR1` 永远只表示「子进程就绪」，`SIGUSR2` 永远只表示「父进程就绪」。**

⭐ 原书在 p.528 提过这类封装的工程价值（引 Stevens）：

> *"[Stevens & Rago, 2005] suggests encapsulating such synchronization steps (block signal,
> send signal, catch signal) into a standard set of functions for process synchronization.
> The advantage of such encapsulation is that we then later replace the use of signals by
> another IPC mechanism, if desired."*

本仓库这个自写解就是照这个思路写的：把「屏蔽 + 发 + 等」包成宏/函数，
将来换成 `eventfd` 或管道，调用点不用改。

<summary>代码自测（Q&A）</summary>

**Q1：`fork(); fork(); fork();` 为什么是 8 个进程而不是 4 个？**

A：因为每次 `fork()` 都会被**当时所有已存在的进程**执行一遍：1 → 2 → 4 → 8。
新产生的进程数是 8 − 1 = 7。

**Q2：`ex24_1_fork_count` 的输出里 `ppid=1` 是怎么来的？**

A：那两个进程在打印时父进程已经退出了。父进程退出时内核把子进程的父指针改指向
`init`（容器 PID namespace 里的 PID 1）—— 这叫**孤儿进程被收养**。
另外 `pid=6` 的 `ppid=4` 说明 8 个进程构成一棵三层的 fork 树。

**Q3：`vfork_fd_test` 只输出了一行错误，怎么就能证明 fd 表是独立的？**

A：程序里父进程连关两次 stdout：第一次**期望成功**、第二次期望失败。
如果 fd 表共享，子进程那次 `close` 会让父进程的第一次 `close` 也失败 → 会多打一行。
实测只有一行 ⇒ 父进程第一次 `close` 成功了 ⇒ 子进程的 `close` 没影响父进程。

**Q4：`WCOREDUMP(status)` 返回 128，是 bug 吗？**

A：不是。glibc 里它是 `status & 0x80`（`bits/waitstatus.h`），只能取 **0 或 128**。
它由内核在 `fs/coredump.c:438` 用 `group_exit_code |= 0x80` 置上。

**Q5：既然 `WCOREDUMP` 被置位了，为什么磁盘上没有 core 文件？**

A：两个原因叠加：① `RLIMIT_CORE = 0/0`（且 hard limit 是 0，非 root 提不动，
实测 `setrlimit` 报 `EPERM`）；② `core_pattern` 是**管道**（`|/usr/share/apport/apport ...`），
管道模式下内核不看 `RLIMIT_CORE`（`fs/coredump.c:613` 直接 `cprm.limit = RLIM_INFINITY`），
所以流程走完、位置上了，但数据交给 apport 之后落到哪里、有没有落地，内核不管。

**Q6：为什么双向握手非要用两个信号？**

A：一个信号分不清方向 —— 接收方无法区分「我等的信号」和「我刚发出去又绕回来」。
用 `SIGUSR1`（子→父）+ `SIGUSR2`（父→子），每个信号只有一个含义。
两个信号**都必须在 `fork()` 之前屏蔽**，否则会重演 §24.5 那个「父进程永久挂起」的坑。

**Q7：24-4 要求换别的 UNIX，本仓库为什么改成对照内核版本？**

A：CE 沙箱只提供 Linux，跑不了别的 UNIX。而原书那句话本身（「2.6.32 起又改回 parent 先」）
本身就跨越了内核版本 —— 用 upstream 源码做**跨版本对照**是能验证它的唯一途径，
而且比「在别人的机器上跑一次」更可复核（每一行都能给出文件和行号）。

</details>
