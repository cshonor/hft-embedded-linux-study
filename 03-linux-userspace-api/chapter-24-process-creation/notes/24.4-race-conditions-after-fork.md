## 本节讲什么

`fork()` 返回之后，**谁先拿到 CPU**？

原书给的答案只有三个字：**不确定**。

> *"After a `fork()`, it is indeterminate which process—the parent or the child—next has
> access to the CPU. (On a multiprocessor system, they may both simultaneously get
> access to a CPU.)"*（书 p.525）

"不确定"听起来像废话，但它有三个非常具体的后果：

| 后果 | 说明 |
|------|------|
| 不能靠顺序写程序 | 任何「假设父进程先做 A、子进程再做 B」的代码都是**竞态**（race condition） |
| 错误难复现 | 出不出错取决于**外部负载**，不取决于代码 —— 本地跑一万次都对，生产上偶发 |
| 随内核版本漂移 | 同一个程序在 Linux 2.2.19 / 2.6.30 / 6.6 上，行为可以**完全相反** |

本节做三件事：

1. 跑原书 Listing 24-5，看**实测分布** —— 结论不是「均匀随机」，而是**成簇**的；
2. 把原书那句「可以改 `/proc/sys/kernel/sched_child_runs_first`」**当场验证** ——
   结论是：**这个文件在今天的实测内核上已经不存在了**；
3. 由此说明「顺序」这件事正确的解法是什么（引到 §24.5）。

```c
/* fork_whos_on_first.c

   Parent repeatedly creates a child, and then processes both race to be the
   first to print a message. (Each child terminates after printing its message.)
   The results of running this program give us an idea of which of the two
   processes--parent or child--is usually scheduled first after a fork().

   Whether the child or the parent is scheduled first after fork() has
   changed a number of times across different kernel versions.
*/
#include <sys/wait.h>
#include "tlpi_hdr.h"

int
main(int argc, char *argv[])
{
    int numChildren, j;
    pid_t childPid;

    if (argc > 1 && strcmp(argv[1], "--help") == 0)
        usageErr("%s [num-children]\n", argv[0]);

    numChildren = (argc > 1) ? getInt(argv[1], GN_GT_0, "num-children") : 1;

    setbuf(stdout, NULL);               /* Make stdout unbuffered */

    for (j = 0; j < numChildren; j++) {
        switch (childPid = fork()) {
        case -1:
            errExit("fork");

        case 0:
            printf("%d child\n", j);
            _exit(EXIT_SUCCESS);

        default:
            printf("%d parent\n", j);
            wait(NULL);                 /* Wait for child to terminate */
            break;
        }
    }

    exit(EXIT_SUCCESS);
}
```

## 2. 逐条解读

### ① 输出为什么总是**成对**出现，而且是 `0 0 1 1 2 2 …`

这不是巧合，是父进程那个 `wait(NULL)` 造出来的结构。

```
j=0: 父 fork ──┬─> 父打印 "0 parent"  ──> 父 wait(NULL) ←──┐
               └─> 子打印 "0 child"  ──> _exit() ──────────┘
j=1: 父 fork（此时 j 已经 ++ 到 1）……
```

父进程**必须等这一轮的子进程退出**，才会进 `for` 的下一轮去 fork 下一个。
所以：

* 每一对 `j parent` / `j child` 一定属于**同一个** `j`；
* 第 `j+1` 轮一定在第 `j` 轮**父子都打完**之后才开始。

**这个设计是刻意的** —— 它把 1000 次实验变成**串行**的，每次实验互不干扰，
统计出来的百分比才有意义。否则 1000 个进程同时抢一个 stdout，输出会乱成一团。

### ② 那 8.4% 不是「均匀随机」，是**成簇**的

把 84 次 child 先的 `j` 按区间摊开：

| `j` 区间 | child 先的次数 | 区间长度 | 占比 |
|----------|---------------|----------|------|
| 0 – 599 | 25 | 600 | 4.2% |
| 600 – 699 | 3 | 100 | 3.0% |
| 700 – 799 | **0** | 100 | **0%** |
| 800 – 860 | **56** | 61 | **92%** |
| 861 – 999 | **0** | 139 | **0%** |

最刺眼的是 **`j ∈ [800, 860]`** 那 61 次里，有 **56 次**是子进程先打印；
而紧跟着的 `j ∈ [861, 999]` 共 139 次，**一次都没有**。

再看 `j ∈ [800, 860]` 里**没有**发生反转的 5 个位置，它们也是散的：
`818`、`822`、`832`、`840`、`857`。

这说明什么？

> 「父/子谁先跑」在这台机器上**不是掷骰子**。它在一段时间内会**稳定地偏向一边**，
> 而偏哪一边取决于**那一刻宿主机在忙什么**。

这正是原书那句话的实测版：

> *"Such bugs can be hard to find, as their occurrence depends on scheduling decisions
> that the kernel makes according to system load."*（书 p.525）

⭐ **对写程序的人来说，这个"成簇"比"随机"更危险。** 随机会让你在本地测试时立刻
发现问题；成簇意味着：**你测试的那 10 分钟机器刚好不忙 → 全绿；上线后遇到一段忙的
时间窗 → 连续翻车**。而且忙闲状态一过去，问题又消失了，根本抓不到现场。

### ③ `setbuf(stdout, NULL)` 不是可选项

把这一行删掉会怎样？——`printf` 的输出去全缓冲，父子两个进程**各持一份缓冲区副本**，
输出顺序会被缓冲彻底搅乱，而且 `fork()` 之后子进程缓冲区里可能**残留父进程还没刷的
内容**，导致同一行被打印两次（这个现象在 Ch25 的 Listing 25-2 里有专门演示）。

想测「谁先跑」，就必须让 `printf` **当场变成 `write(2)`**。`setbuf(stdout, NULL)` 就是干
这个的。

### ④ 实测环境画像：`nice = 19`、2 个 CPU

`probe24` / `probe24_sched` 两个探针给出的环境事实：

| 项 | 实测值 |
|----|--------|
| `_SC_NPROCESSORS_ONLN` | **2** |
| `sched_getscheduler(0)` | **0**（`SCHED_OTHER`） |
| `sched_priority` | 0 |
| `nice` | **19**（`getpriority(PRIO_PROCESS, 0)`） |

`nice = 19` 是 nice 取值范围的**最低**一端（-20 到 19）。这解释了两件事：

* **为什么 91.6% 而不是接近 100%**：执行进程优先级被压到最低，父进程打完那行
  `printf` 之前被宿主上其它进程抢走的概率显著上升；
* **为什么会出现 800–860 那样的连续反转**：那一段宿主机负载变了。

⭐ **这条数字不能外推。** 在一台独占的、`nice = 0` 的机器上，parent 先的比例会明显
更高。**「本机实测 xx%」永远要连同调度环境一起说**，否则就是编数据。

## 3. 内核版本史：原书那套说法今天还成立吗

### 3.1 原书列的四个年代（书 p.526–527）

| 内核 | 行为 | 原书给数字（100 万个子进程） |
|------|------|------------------------------|
| Linux/x86-32 **2.2.19** | parent 先（几乎总是） | parent 先 **99.97%**（仅 332 例例外） |
| Linux **2.4** 系列 | 短暂试过 "child first after fork()" 补丁 | —— |
| Linux **2.6** | 采纳了 child first | Linux/x86-32 **2.6.30**：child 先 **99.98%** |
| Linux **2.6.32** 起 | **又改回 parent 先**，并给了个开关 | —— |

原书对 2.2.19 那 0.03% 的解释很值得看，它讲的正是**竞态为什么难抓**：

> *"The reason that the child occasionally printed its message first was that, in 0.03%
> of cases, the parent's CPU time slice ran out before it had time to print its message.
> In other words, if this example represented a case where we were relying on the parent
> to always be scheduled first after fork(), then things would usually go right, but one
> time out of every 3000, things would go wrong. Of course, if the application expected
> that the parent should be able to carry out a larger piece of work before the child was
> scheduled, the possibility of things going wrong would be greater."*

「每 3000 次错一次」和「父进程要做的事越多、错得越多」——把「依赖顺序」的代价算得
明明白白。

### 3.2 两派各自的论据

**为什么要 child first（2.6 采纳它的理由）** —— 书 p.527：

> *"...consider what happens with copy-on-write semantics when the child of a `fork()`
> performs an immediate `exec()`. In this case, as the parent carries on after the `fork()`
> to modify data and stack pages, the kernel duplicates the to-be-modified pages for the
> child. Since the child performs an `exec()` as soon as it is scheduled to run, this
> duplication is wasted. According to this argument, it is better to schedule the child
> first, so that by the time the parent is next scheduled, no page copying is required."*

一句话：**父进程 `fork` 之后继续跑会触发 COW 复制；而子进程反正马上 `exec`（把整个地址
空间扔掉）⇒ 这些复制白做了。让子进程先跑，父进程再动页面时子进程已经不管这块内存了。**

**为什么 2.6.32 又改回 parent first** —— 书 p.527：

> *"The argument for switching back to "parent first after fork()" in Linux 2.6.32 was
> based on the observation that, after a `fork()`, the parent's state is already active in
> the CPU and its memory-management information is already cached in the hardware memory
> management unit's translation look-aside buffer (TLB). Therefore, running the parent
> first should result in better performance. This was informally verified by measuring the
> time required for kernel builds under the two behaviors."*

一句话：**父进程"热"** —— 它在 CPU 上、页表项还在 TLB 里。子进程是"冷"的，切过去
等于 TLB/缓存全部重来。

原书最后自己给了个台阶（书 p.527）：

> *"In conclusion, it is worth noting that the performance differences between the two
> behaviors are rather small, and won't affect most applications."*

所以**别把「谁先跑」当成性能优化点**。它是个**语义陷阱**，不是性能旋钮。

### 3.3 ⭐ 实测：原书点名的那个开关，今天已经不存在了

原书（书 p.526）说：

> *"This default can be changed by assigning a nonzero value to the Linux-specific
> `/proc/sys/kernel/sched_child_runs_first` file."*

这句话写在 2010 年。今天到底还灵不灵？直接去问（`probe24_sched`，本仓库自写探针）：

```text
  /proc/sys/kernel/sched_child_runs_first       <打不开> errno=2 (No such file or directory)
```

**`ENOENT` —— 文件根本不存在。**

而同一目录下别的 `sched_*` 开关都好好地在那儿（同一份实测输出）：

| 路径 | 实测值 |
|------|--------|
| `/proc/sys/kernel/sched_autogroup_enabled` | `1` |
| `/proc/sys/kernel/sched_cfs_bandwidth_slice_us` | `5000` |
| `/proc/sys/kernel/sched_rt_runtime_us` | `950000` |
| `/proc/sys/kernel/sched_deadline_period_max_us` | `4194304` |

所以不是「沙箱没挂 `/proc/sys`」，是**这个文件真的没了**。

#### 它在哪一版没的？—— 跨版本源码对照

抓 upstream 各版本的 `kernel/sched/fair.c`，搜 `child_runs_first`：

| 版本 | 定义（`unsigned int sysctl_sched_child_runs_first`） | 消费点（真的有代码读它） |
|------|------------------------------------------------------|--------------------------|
| **v6.5** | 有 | **有** —— `fair.c:12183` `if (sysctl_sched_child_runs_first && curr && entity_before(curr, se))` → `swap(curr->vruntime, se->vruntime)` + `resched_curr(rq)` |
| **v6.6** | 有（`fair.c:85`） | **无** |
| **v6.7** | **无** | 无 |
| v6.10 / v6.11 / v6.12 / v6.13 / v6.16 | 无 | 无 |

**v6.6 是最后一个还留着这个名字的版本，而它那时候已经是个空壳。**
把 v6.6 里所有出现点列全（已核 `kernel/sched/fair.c`、`kernel/sched/sched.h`、
`kernel/sched/debug.c`、`kernel/sched/core.c`、`kernel/fork.c` 五个文件）：

| 位置 | 内容 | 性质 |
|------|------|------|
| `kernel/sched/fair.c:85` | `unsigned int sysctl_sched_child_runs_first __read_mostly;` | 定义（注释还写着 *"After fork, child runs first. If set to 0 (default) then parent will (try to) run first."*） |
| `kernel/sched/fair.c:147-154` | `sched_fair_sysctls[]` 里的 `.procname = "sched_child_runs_first"` | 注册成 `/proc/sys/kernel/sched_child_runs_first` |
| `kernel/sched/fair.c:178-183` | `sched_fair_sysctl_init()` + `late_initcall(...)` | 启动时挂上 |
| `kernel/sched/sched.h:112` | `extern unsigned int sysctl_sched_child_runs_first;` | 声明 |
| `kernel/sched/debug.c:867` | `P(sysctl_sched_child_runs_first);` | **只是把它打印到 `/proc/sched_debug` 给人看** |
| **（没有别处了）** | —— | **零个消费点** |

对照 v6.5 还在读它的那一段（`fair.c:12181-12190`）：

```c
	place_entity(cfs_rq, se, 1);

	if (sysctl_sched_child_runs_first && curr && entity_before(curr, se)) {
		/*
		 * Upon rescheduling, sched_class::put_prev_task() will place
		 * 'current' within the tree based on its new key value.
		 */
		swap(curr->vruntime, se->vruntime);
		resched_curr(rq);
	}
```

而 v6.6 的同一函数（`fair.c:12410-12426`）缩成了：

```c
static void task_fork_fair(struct task_struct *p)
{
	struct sched_entity *se = &p->se, *curr;
	struct cfs_rq *cfs_rq;
	struct rq *rq = this_rq();
	struct rq_flags rf;

	rq_lock(rq, &rf);
	update_rq_clock(rq);

	cfs_rq = task_cfs_rq(current);
	curr = cfs_rq->curr;
	if (curr)
		update_curr(cfs_rq);
	place_entity(cfs_rq, se, ENQUEUE_INITIAL);
	rq_unlock(rq, &rf);
}
```

——**那个 `if` 整块没了**。v6.6 是新调度器 **EEVDF** 落地的版本，`place_entity()` 被整体
重写成按「虚拟 deadline」排队的策略，`fork` 出来的任务只保留一个特殊照顾：

```c
	/*
	 * When joining the competition; the exisiting tasks will be,
	 * on average, halfway through their slice, as such start tasks
	 * off with half a slice to ease into the competition.
	 */
	if (sched_feat(PLACE_DEADLINE_INITIAL) && (flags & ENQUEUE_INITIAL))
		vslice /= 2;
```

> `kernel/sched/fair.c:5060-5066` —— **新任务只拿半个时间片「轻轻挤进竞争」**，
> 而不是 v6.5 那种直接 `swap` 把当前任务的 vruntime 换走。

#### 结论

| 问题 | 答案 |
|------|------|
| 书上的 99.97% / 99.98% 还能复现吗 | **不能**。那是 2.2.19 / 2.6.30 的实测值 |
| 能靠 `sched_child_runs_first` 把顺序掰回来吗 | **不能**。v6.7 起该文件已不存在，实测内核上 `ENOENT` |
| 那今天的「谁先跑」由什么决定 | `wake_up_new_task()`（`kernel/sched/core.c:4848`）里那句 `check_preempt_curr(rq, p, WF_FORK)`（`core.c:4874`）→ 进到 `check_preempt_wakeup()`（`kernel/sched/fair.c:8055`），按 **EEVDF 的虚拟 deadline** 决定要不要当场抢占 |
| 所以顺序能靠得住吗 | **靠不住，而且以后也靠不住** —— 这正是 §24.5 要解决的问题 |

⭐ 这一节的价值不在「原书错了」——原书写的时候是对的，而且它自己就说了这句话有时效性。
价值在于：**「内核参数 + 版本」是笔记里最容易腐烂的一类知识**。书上给了一个
`/proc` 路径，十年后它连文件都没了。所以看到「改这个文件就能改行为」时，
**先 `ls` 一下**。

## 4. 原书给的统计脚本

原书提到统计用的脚本（书 p.526）：

> *"The results from running the program in Listing 24-5 were analyzed using the script
> `procexec/fork_whos_on_first.count.awk`, which is provided in the source code distribution
> for this book."*

这次实测没有用那个 awk（脚本在原始发行包里，CE 上没有 awk 可用），而是把输出拉回本地
用 Python 按 `j` 配对统计。思路与 awk 版一致：

1. 逐行读，按空格切成 `(j, who)`；
2. 以 `j` 为键，记录**同一 `j` 下先出现的那一行**；
3. 先出现的是 `parent` 就计入「parent 先」，否则计入「child 先」。

| └ CFS/EEVDF 的实现 | `kernel/sched/fair.c:8055` `check_preempt_wakeup()` |
| 新任务放到哪个 CPU | `kernel/sched/core.c:4866` `__set_task_cpu(p, select_task_rq(p, task_cpu(p), WF_FORK))` |
| `sysctl_sched_child_runs_first` 定义 | `kernel/sched/fair.c:85`（v6.6 起**无人使用**） |
| ├ sysctl 表项 | `kernel/sched/fair.c:147-154` |
| ├ 注册 | `kernel/sched/fair.c:178-183` `late_initcall(sched_fair_sysctl_init)` |
| └ 唯一残留的读点（仅打印） | `kernel/sched/debug.c:867` `P(sysctl_sched_child_runs_first);` |
| **v6.5 里它还在干活** | `kernel/sched/fair.c:12183-12190`（v6.5）—— v6.6 已删 |
| `sched_child_runs_first` 彻底消失 | **v6.7 起**（upstream `kernel/sched/fair.c` 里再无该符号） |

⭐ 一句话串起来：**`task_fork_fair` 只负责「排队」，`wake_up_new_task` 里那句
`check_preempt_curr(..., WF_FORK)` 才负责「插队」**。v6.5 之前插队的规则里有一条
「如果是 fork 且开关打开，就让子进程插队」；v6.6（EEVDF）把这条规则换成了
「新任务只拿半个时间片」，v6.7 把残留的名字也删了。

## 常见坑

| # | 坑 | 说明 |
|---|----|------|
| 1 | 以为 fork 之后**父进程一定先跑** | 只在 2.2.19 上近乎成立（99.97%）；2.6 上相反（child 先 99.98%）；今天按 EEVDF 排 |
| 2 | 以为 fork 之后**子进程一定先跑** | 这是 vfork 的语义（§24.3），**fork 没有这个保证** |
| 3 | 拿「本机多次运行都一样」当「行为确定」 | 实测 800–860 段 92% child 先、861–999 段 0% —— 机器一忙，结论就翻 |
| 4 | `printf` 到 stdout 却没 `setbuf(stdout, NULL)` | 父子各持一份全缓冲副本，顺序被缓冲吃掉；严重时同一行打印两次 |
| 5 | 依赖 `fork` 后的顺序做初始化（父建管道、子写管道…） | 典型竞态。正确做法见 §24.5（信号同步）或 Ch44（管道） |
| 6 | 照抄书上的 `sched_child_runs_first` 调参 | 实测内核上该文件 **`ENOENT`**；v6.7 起 upstream 已删 |
| 7 | 把「谁先跑」当性能优化点 | 原书自己说两个方向「performance differences are rather small」 |
| 8 | 在多核上讨论「谁先」 | 书 p.525 明说多处理器上两者可能**同时**拿到 CPU —— 这时「先后」本身没有意义 |
| 9 | 用统一百分比描述「本机行为」 | 必须连同 `nice`（实测 19）、CPU 数（实测 2）、宿主负载一起说 |

## HFT / 嵌入式关联

* **启动路径上的顺序依赖是实盘事故的高发点**：策略进程 `fork` 出子进程去做
  「预热 / 建连 / mmap 行情缓冲」，父进程紧接着用自己的 fd 或共享内存 —— 如果父进程
  假设「子进程已经初始化好了」，这段代码在测试机上永远是对的（机器闲、parent 先、
  子进程那点活还没开始）。**唯一正确做法是握手**：pipe / eventfd / 信号，见 §24.5。
* **`nice = 19` 的启示**：本仓库的实测数字是在一个 `nice = 19`、2 核、共享宿主的沙箱里
  采到的。**任何「调度顺序」类的百分比都必须连同调度环境一起记录**，否则换台机器就
  无法复现，也无法解释。做延迟敏感系统时，这条同样适用于「本机 benchmark 数字」。
* **实时调度（`SCHED_FIFO` / `SCHED_RR`）下不要用 fork 做热路径**：新任务继承父进程的
  调度策略与优先级，`fork` 本身就带页表复制。HFT 的通行做法是**启动时一次性
  fork/exec 好、之后只做进程间通信**，或者干脆单进程多线程 + CPU 亲和。
* **嵌入式 / 单核 ARM**：单核上「谁先跑」只有两种可能，分布比多核更容易观察，但**更容易
  被误解成"确定行为"**（因为单核上成簇效应更明显、更容易复现）。加进 BSP 的
  `sched_child_runs_first` 在 v6.7 之后已经无效，老 BSP 打补丁时要核对内核版本。
* **内核版本是运维风险**：一个假设 「child first」（2.6 时代）或 「parent first」
  （2.2 时代）的老程序，升级内核就可能静默改变行为。**真实系统里这类 bug 的表现形式
  往往是"某次内核升级后偶发失败"**，而没人会想到是 24 年前的内核行为差异。
* **这条经验可迁移到任何「不确定顺序」的场合**：多核内存序、`malloc` 之后的地址、
  `select`/`epoll` 返回的事件顺序 —— 共同点是**依赖它 = 埋雷**，正确做法都是显式同步。

<summary>代码自测（Q&A）</summary>

**Q1：`whos_first_1` 里 `0 parent` 排在 `0 child` 前面，是不是说明父进程一定先跑？**

A：不是。原书自己用的措辞是 *"we might see"*。这一次确实是父进程先打印，
但那是当时调度器的决定。同一份代码在 2.6.30 内核上有 99.98% 的概率反过来。

**Q2：为什么输出总是成对、而且是 `0 0 1 1 2 2 …`？**

A：父进程在 `default` 分支里有个 `wait(NULL)` ——它必须等这一轮的子进程退出，
才进入 `for` 的下一轮。所以 1000 次实验是**串行**的，`j` 相同的两行必然相邻。

**Q3：那 8.4% 的 child 先为什么集中在 `j ∈ [800, 860]`？**

A：因为「谁先跑」不是掷骰子，而是由**外部负载**和调度器的虚拟 deadline 决定的。
那 61 次里 56 次反转（92%），而它前后两段分别是 3% 和 0% —— 说明中间那段时间
宿主机状态变了。这正是原书说的 *"depends on scheduling decisions that the kernel
makes according to system load"*。

**Q4：把 `setbuf(stdout, NULL)` 删掉会怎样？**

A：stdout 变全缓冲，父子各有一份缓冲区副本，输出顺序被缓冲搅乱，甚至出现同一行
打印两次（子进程继承了父进程缓冲区里未刷出的内容）。要观察「谁先跑」就必须让
`printf` 立刻落成 `write(2)`。

**Q5：原书说改 `/proc/sys/kernel/sched_child_runs_first` 就能改行为，现在还行吗？**

A：不行。实测沙箱（内核 7.0.0-1012-aws）上该文件 **`ENOENT`**；源码对照显示
v6.6 里它已经没有消费点（只剩定义 + 一个打印），**v6.7 起 upstream 连定义都删了**。
这句话只对 2.6.32 ~ 6.5 的内核有效。

**Q6：v6.6 的 `task_fork_fair()` 只剩一行 `place_entity(...)`，那「谁先跑」到底谁定？**

A：两步。① `task_fork_fair()`（`fair.c:12410`）给新任务算 vruntime / deadline，
`ENQUEUE_INITIAL` 让它只拿**半个时间片**；② `wake_up_new_task()`（`core.c:4848`）
里 `check_preempt_curr(rq, p, WF_FORK)`（`core.c:4874`）→ `check_preempt_wakeup()`
（`fair.c:8055`）按虚拟 deadline 决定要不要当场切过去。

**Q7：为什么 `whos_first_help` 打印的是 `./output.s` 而不是程序真名？**

A：因为 CE 沙箱里执行产物的名字就是 `output.s`，`argv[0]` 跟着它走。
`usageErr()` 用的是 `argv[0]`，所以报文里出现的是 `./output.s`。
这也顺便说明 `usageErr()` 的退出码是 **1**（`exit(EXIT_FAILURE)`）——
实测 `exit code = 1`，与之一致。

**Q8：代码里子进程用 `_exit()` 而不是 `exit()`，为什么？**

A：`exit()` 会刷 stdio 缓冲区。由于 `fork` 让子进程持有一份父进程缓冲区的副本，
子进程 `exit()` 会把这份副本刷一遍 —— 结果是本该只打印一次的内容出现两次。
`_exit()` 直接走 `exit_group` 系统调用，不碰 stdio。
