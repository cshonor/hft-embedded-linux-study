## 本节讲什么

前六节讲的都是「**现在几点**」。本节换一个完全不同的维度：

> **这个进程烧掉了多少 CPU？**

看起来只是「换个指标」，实际上是**两套互不相干的计时体系**：

| | 墙上时间（wall clock） | CPU 时间（CPU time） |
|---|---|---|
| 回答的问题 | 「从 A 到 B 过了多久」 | 「这段代码占用了多少处理器时间」 |
| 进程被抢占/睡眠时 | **照涨** | **不涨** |
| 多核并行时 | 只算流逝的那一份 | **把所有核的时间累加** |
| 谁提供 | `CLOCK_MONOTONIC` / `CLOCK_REALTIME` | `times(2)` / `clock(3)` / `CLOCK_PROCESS_CPUTIME_ID` / `getrusage(2)` |

本章的四个 API 各自覆盖不同的「范围」和「精度」：

| API | 范围 | 精度（实测） | 备注 |
|-----|------|-------------|------|
| `times(&tms)` | 本进程 + 已 wait 的子进程 | **1/USER_HZ = 10 ms** | 四个字段分 user/sys × self/children |
| `clock()` | 本进程（user + sys） | **1 ns**（Linux 上） | 单位是 `CLOCKS_PER_SEC` = 1000000 |
| `clock_gettime(CLOCK_PROCESS_CPUTIME_ID)` | 本进程 | **1 ns** | 推荐的高精度路径 |
| `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` | 本线程 | **1 ns** | 多线程下才有区别 |
| `getrusage(RUSAGE_SELF, &ru)` | 本进程 | μs | 还带缺页/上下文切换/IO 计数 |
| `getrusage(RUSAGE_CHILDREN, &ru)` | 已 wait 的子进程 | μs | 与 `tms_c*` 同源 |
| `getrusage(RUSAGE_THREAD, &ru)` | 本线程 | μs | Linux 扩展，`kernel/sys.c:1793` |

## 0. 三个「每秒多少个 tick」的常数：`CLOCKS_PER_SEC` 的同名不同值

源码：[../code/c10_7_process_time.c](../code/c10_7_process_time.c)

```c
/* TLPI 第 10 章 §10.7 Process Time
 * 进程时间：times(2) 的四个字段 / clock(3) / CLOCK_PROCESS_CPUTIME_ID /
 * CLOCK_THREAD_CPUTIME_ID / getrusage 的两个 RUSAGE_*
 *
 * 编译: gcc -O0 -Wall -Wextra -o c10_7_process_time c10_7_process_time.c
 * 运行: ./c10_7_process_time                   (无需参数；跑一两秒)
 *
 * ⭐ 关键区分：
 *     墙上时间(wall)  —— CLOCK_MONOTONIC，睡 100 ms 就涨 100 ms；
 *     进程 CPU 时间   —— times()/clock()/CLOCK_PROCESS_CPUTIME_ID，睡 100 ms
 *                        期间进程没在跑，**一点都不涨**。
 *   然后 times() 的粒度是 1/HZ，所以「很小的循环」会读到 0 tick ——
 *   这不是没耗 CPU，是刻度太粗。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/resource.h>
#include <sys/times.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

static long tck;
static struct timespec wall0;

static double wall_now(void)
{
    struct timespec ts;

    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double) (ts.tv_sec - wall0.tv_sec)
         + (double) (ts.tv_nsec - wall0.tv_nsec) / 1e9;
}

static double cpu_now(void)
{
    struct timespec ts;

    clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &ts);
    return (double) ts.tv_sec + (double) ts.tv_nsec / 1e9;
}

static void snapshot(const char *label)
{
    struct tms t;
    clock_t c = clock();

    if (times(&t) == (clock_t) -1) {
        printf("times() 失败\n");
        return;
    }
    printf("  %-22s wall=%6.3f s  cpu=%6.3f s | "
           "utime=%5.2f stime=%5.2f cutime=%5.2f cstime=%5.2f | "
           "clock()=%.3f s | ticks=%ld/%ld/%ld/%ld\n",
           label, wall_now(), cpu_now(),
           (double) t.tms_utime / tck, (double) t.tms_stime / tck,
           (double) t.tms_cutime / tck, (double) t.tms_cstime / tck,
           (double) c / CLOCKS_PER_SEC,
           (long) t.tms_utime, (long) t.tms_stime,
           (long) t.tms_cutime, (long) t.tms_cstime);
}

int main(void)
{
    clock_gettime(CLOCK_MONOTONIC, &wall0);
    tck = sysconf(_SC_CLK_TCK);

    printf("== 0. 时间刻度的三个常数 ==\n");
    printf("sysconf(_SC_CLK_TCK) = %ld   <- times() 的单位：每秒 %ld 个 tick\n", tck, tck);
    printf("CLOCKS_PER_SEC       = %ld   <- clock() 的单位，和上面**不是一个数**\n",
           (long) CLOCKS_PER_SEC);
    printf("sizeof(clock_t)      = %zu\n\n", sizeof(clock_t));

    printf("== 1. 各阶段的时间账 ==\n");
    snapshot("启动");

    /* (a) 纯用户态忙等：utime 应涨、stime 不该涨 */
    {
        volatile unsigned long long s = 0;
        for (long i = 0; i < 20000000L; i++)
            s += (unsigned long long) i;
        (void) s;
    }
    snapshot("纯用户态忙等后");

    /* (b) 系统调用密集：stime 应涨 */
    {
        long j;
        for (j = 0; j < 3000000L; j++)
            (void) getppid();
    }
    snapshot("300 万次 getppid");

    /* (c) 睡眠：wall 涨、cpu 不涨 */
    {
        struct timespec req = { 0, 300 * 1000 * 1000 };   /* 300 ms */

        nanosleep(&req, NULL);
    }
    snapshot("nanosleep(300ms)");

    printf("\n");
    printf("== 2. CLOCK_PROCESS_CPUTIME_ID vs CLOCK_THREAD_CPUTIME_ID ==\n");
    {
        struct timespec p, t;

        clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &p);
        clock_gettime(CLOCK_THREAD_CPUTIME_ID, &t);
        printf("  单线程进程里两者几乎相同：\n");
        printf("    进程 CPU = %ld.%09ld s\n", (long) p.tv_sec, (long) p.tv_nsec);
        printf("    线程 CPU = %ld.%09ld s\n", (long) t.tv_sec, (long) t.tv_nsec);
        printf("    差       = %+ld ns\n",
               (long) ((p.tv_sec - t.tv_sec) * 1000000000L + (p.tv_nsec - t.tv_nsec)));
    }
    printf("\n");

    printf("== 3. 主动报出「刻度太粗」这件事 ==\n");
    {
        struct tms a, b;

        times(&a);
        { volatile int x = 0; for (int i = 0; i < 1000; i++) x += i; (void) x; }
        times(&b);
        printf("  跑一个 1000 次的小循环，tms_utime 的增量 = %ld tick = %.1f ms\n",
               (long) (b.tms_utime - a.tms_utime),
               (double) (b.tms_utime - a.tms_utime) * 1000.0 / (double) tck);
        printf("  → 常常是 0。不代表没耗 CPU，只代表不到 1 个 tick（%.1f ms）。\n",
               1000.0 / (double) tck);
        printf("  要测这种量级只能用 CLOCK_PROCESS_CPUTIME_ID（纳秒分辨率）。\n");
    }
    printf("\n");

    printf("== 4. 子进程的时间记在 tms_c* 里（RUSAGE_CHILDREN） ==\n");
    {
        pid_t pid = fork();

        if (pid == 0) {
            volatile unsigned long long s = 0;
            for (long i = 0; i < 40000000L; i++)
                s += (unsigned long long) i;
            _exit(0);
        } else if (pid > 0) {
            int st;
            struct rusage ru;

            wait(&st);
            snapshot("子进程烧完 CPU 后");
            if (getrusage(RUSAGE_CHILDREN, &ru) == 0) {
                printf("  getrusage(RUSAGE_CHILDREN): user=%ld.%06ld s  sys=%ld.%06ld s\n",
                       (long) ru.ru_utime.tv_sec, (long) ru.ru_utime.tv_usec,
                       (long) ru.ru_stime.tv_sec, (long) ru.ru_stime.tv_usec);
            }
            printf("  → 子进程的 CPU 时间只累加到**父进程**的 tms_cutime，"
                   "本进程自己的 tms_utime 不变\n");
        } else {
            printf("  fork 失败\n");
        }
    }

    printf("\n三个必须记住的点：\n");
    printf("  1) times() 与 clock() 单位**不同**：前者是 1/_SC_CLK_TCK，后者是 1/CLOCKS_PER_SEC；\n");
    printf("  2) 只要进程没在跑，CPU 时间就不涨 —— 测「服务响应延迟」要用墙上时间，\n");
    printf("     测「这段算法花了多少 CPU」才用 CPU 时间；\n");
    printf("  3) 所有 CPU 时间的口径都是**多核累加**：4 核跑满 1 秒，"
           "CLOCK_PROCESS_CPUTIME_ID 涨 4 秒。\n");
    return 0;
}
```

编译 + 运行：

```bash
gcc -O0 -Wall -Wextra -o c10_7_process_time c10_7_process_time.c
./c10_7_process_time
```

实测（CE，gcc 13.3.0）：

```text
== 0. 时间刻度的三个常数 ==
sysconf(_SC_CLK_TCK) = 100
CLOCKS_PER_SEC       = 1000000
sizeof(clock_t)      = 8
```

`CLOCKS_PER_SEC` 这一行**必须停下来看**：分值是 `1000000`，但 [10.6](10.6-the-software-clock-jiffies.md) 讲内核时我说过 `CLOCKS_PER_SEC = USER_HZ = 100`。**两边都没错，因为是两个不同的宏**：

| 谁定义的 | 位置 | 值 | 谁在用 |
|---------|------|-----|--------|
| **内核**侧 | `include/asm-generic/param.h:10` `# define CLOCKS_PER_SEC  (USER_HZ)` | **100** | `times(2)` 的返回值、`auxv` 里的 `AT_CLKTCK` |
| **glibc** 侧 | glibc 的 `<time.h>`（`bits/time.h`） | **1000000** | `clock(3)` 的返回值 |

glibc 甚至在编译期把这件事钉死了（`sysdeps/unix/sysv/linux/clock.c:28-29`）：

```c
  _Static_assert (CLOCKS_PER_SEC == 1000000,
		  "CLOCKS_PER_SEC should be 1000000");
```

### 关键推论：`clock()` 在 Linux 上完全不经过 `times()`

glibc 有**两份** `clock()` 实现，取决于平台：

| 实现 | 位置 | 做法 | 粒度 |
|------|------|------|------|
| **Linux 专用**（本机走这条） | `sysdeps/unix/sysv/linux/clock.c:24-36` | `__clock_gettime64(CLOCK_PROCESS_CPUTIME_ID, &ts)` → `ts.tv_sec * CLOCKS_PER_SEC + ts.tv_nsec / (1000000000 / CLOCKS_PER_SEC)` | **1 ns** |
| POSIX 通用（非 Linux 兜底） | `sysdeps/posix/clock.c:23-31` | `__times(&buf)` → `return buf.tms_utime + buf.tms_stime;` | 1/USER_HZ |

`sysdeps/unix/sysv/linux/clock.c:31-35` 原文：

```c
  if (__glibc_unlikely (__clock_gettime64 (CLOCK_PROCESS_CPUTIME_ID, &ts) != 0))
    return (clock_t) -1;

  return (ts.tv_sec * CLOCKS_PER_SEC
	  + ts.tv_nsec / (1000000000 / CLOCKS_PER_SEC));
```

**所以 `clock()` 在 Linux 上根本不是 `times()` 的简化版，而是 `CLOCK_PROCESS_CPUTIME_ID` 的重新标度版。** 这个结论在第 1 节的实测里会被数字证实（`clock()` 和 `CLOCK_PROCESS_CPUTIME_ID` 数值完全一致，而和 `times()` 有几十毫秒的偏差）。

> 这也是为什么 POSIX 说 `clock()` 「不适合」——它**没有** `sys`/`user` 的区分，也没有子进程字段，纯属历史遗留的便捷接口。要用就上 `CLOCK_PROCESS_CPUTIME_ID`。

## 1. 各阶段的时间账：`wall` 和 `cpu` 分道扬镳的那一行

demo 在四个阶段各打一次快照：

```text
== 1. 各阶段的时间账 ==
  启动                 wall= 0.000 s  cpu= 0.001 s | utime= 0.00 stime= 0.00 cutime= 0.00 cstime= 0.00 | clock()=0.001 s | ticks=0/0/0/0
  纯用户态忙等后  wall= 0.059 s  cpu= 0.059 s | utime= 0.05 stime= 0.00 cutime= 0.00 cstime= 0.00 | clock()=0.059 s | ticks=5/0/0/0
  300 万次 getppid     wall= 3.388 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.00 cstime= 0.00 | clock()=1.852 s | ticks=134/50/0/0
  nanosleep(300ms)       wall= 3.688 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.00 cstime= 0.00 | clock()=1.852 s | ticks=134/50/0/0
```

逐阶段读这张表：

| 阶段 | wall 增量 | cpu 增量 | 读出来的事 |
|------|----------|---------|-----------|
| 启动 | 0.000 | 0.001 | 进程刚起来就已经有 1 ms 的 CPU 时间（动态链接、`libc` 初始化） |
| 纯用户态忙等 | **+0.059** | **+0.059** | `utime` 从 0 → 5 tick（= 50 ms），`stime` 仍然 0 —— **纯计算不产生 sys 时间** |
| 300 万次 `getppid` | **+3.329** | **+1.793** | `stime` 从 0 → 50 tick（= 500 ms）：`getppid()` 是真 syscall，**每次系统调用都要算 sys 时间** |
| `nanosleep(300ms)` | **+0.300** | **+0.000** | ⭐ **两条线彻底分开** |

### 最后一行是本节的核心

```text
  nanosleep(300ms)       wall= 3.688 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.00 cstime= 0.00 | clock()=1.852 s | ticks=134/50/0/0
```

`wall` 从 `3.388 → 3.688`（涨了 0.300 s，正好是睡眠时长），但 `cpu` **停在 `1.852` 一动不动**，`ticks=134/50/0/0` 也**一个都没变**。

原因在 `nanosleep()` 的实现里：进程把自己挂到定时器上，然后**让出 CPU**。这 300 ms 里：

- 调度器把 CPU 给了别的进程 → 本进程**不在运行**，不消耗 CPU 时间；
- `wall` 时间由 `CLOCK_MONOTONIC` 提供 → **不管你在不在跑，时间都在走**。

> **一句话规则**：
> **「等」出来的时间算 wall，不算 CPU；只有真的占用处理器才累积 CPU 时间。**
>
> 所以：
> - 测「服务响应延迟 / 超时 / 吞吐」 → **墙上时间**（`CLOCK_MONOTONIC`）
> - 测「这段算法/这个函数有多贵」 → **CPU 时间**（`CLOCK_PROCESS_CPUTIME_ID`）

### 第 3 行还能读出「系统调用有多贵」

| 指标 | 值 | 推算 |
|------|-----|------|
| 300 万次 `getppid()` 的 wall | 3.329 s | 单次 ≈ **1109 ns**（含调度抖动） |
| 同期的 cpu | 1.793 s | 单次 ≈ **598 ns** |
| 其中 `stime` | 0.50 s | 单次 sys ≈ **167 ns** |
| 其中 `utime` | 0.84 s | 单次 user ≈ **280 ns**（循环开销 + `glibc` 包装） |

`stime ≈ 167 ns/syscall` 和 [10.6](10.6-the-software-clock-jiffies.md) 量的「一次真 syscall 数百 ns」量级一致（Ch03 里 `getppid()` 是 812.9 ns，但那是 `syscall(2)` 包装版，这里是 libc 直接封装的 `getppid()`）。

## 2. `times()` 的两个「反直觉」：返回值是什么 + 刻度有多粗

### 2.1 `times()` 的第一个返回值不是进程时间

原书只写「返回自开机以来的 clock tick 数」，容易记成「进程启动以来的 tick」。看内核源码（`kernel/sys.c:1023-1034`）：

```c
SYSCALL_DEFINE1(times, struct tms __user *, tbuf)
{
	if (tbuf) {
		struct tms tmp;

		do_sys_times(&tmp);
		if (copy_to_user(tbuf, &tmp, sizeof(struct tms)))
			return -EFAULT;
	}
	force_successful_syscall_return();
	return (long) jiffies_64_to_clock_t(get_jiffies_64());
}
```

返回值是 **`jiffies_64_to_clock_t(get_jiffies_64())`** —— `get_jiffies_64()` 是**开机以来的全局 jiffy 总数**，和当前进程毫无关系。进程时间全在第二个参数 `tbuf` 里。

`do_sys_times()` 只有 4 行赋值（`kernel/sys.c:1010-1021`）：

```c
static void do_sys_times(struct tms *tms)
{
	u64 tgutime, tgstime, cutime, cstime;

	thread_group_cputime_adjusted(current, &tgutime, &tgstime);
	cutime = current->signal->cutime;
	cstime = current->signal->cstime;
	tms->tms_utime = nsec_to_clock_t(tgutime);
	tms->tms_stime = nsec_to_clock_t(tgstime);
	tms->tms_cutime = nsec_to_clock_t(cutime);
	tms->tms_cstime = nsec_to_clock_t(cstime);
}
```

三个要点：

| 代码 | 含义 |
|------|------|
| `thread_group_cputime_adjusted(current, ...)` | 取**整个线程组**（= 进程的所有线程）的累计 CPU 时间，**纳秒精度** |
| `nsec_to_clock_t(...)` | 只在**出口处**换算成 `USER_HZ` 单位（÷10000000） |
| `current->signal->cutime` / `cstime` | 子进程时间直接从 `signal_struct` 里读，**已经预先累加好** |

> **最后一行值得记住**：`cutime` / `cstime` 是内核**在子进程退出时主动累加到父进程**的（`kernel/exit.c` 的 `wait_task_zombie()`），不是 `times()` 现算的。所以 `RUSAGE_CHILDREN` 和 `tms_c*` 天然同源。

### 2.2 换算公式：`jiffies_64_to_clock_t()` 就是「÷ (HZ/USER_HZ)」

`kernel/time/time.c:705-725`：

```c
u64 jiffies_64_to_clock_t(u64 x)
{
#if (TICK_NSEC % (NSEC_PER_SEC / USER_HZ)) == 0
# if HZ < USER_HZ
	x = div_u64(x * USER_HZ, HZ);
# elif HZ > USER_HZ
	x = div_u64(x, HZ / USER_HZ);
# else
	/* Nothing to do */
# endif
#else
	x = div_u64(x * TICK_NSEC, (NSEC_PER_SEC / USER_HZ));
#endif
	return x;
}
```

本容器 `HZ = 1000 > USER_HZ = 100`，所以走 `x = div_u64(x, 10)`：**内核每秒 1000 个 jiffy，用户态每秒看到 100 个 tick，中间有个 10 倍的分频。** 这解释了 [10.6](10.6-the-software-clock-jiffies.md) 里那个「`sysconf(_SC_CLK_TCK)` 推算 vs `COARSE` 实测差 10 倍」的谜题 —— **同一个 10 倍**。

`struct tms` 本身非常朴素（`include/uapi/linux/times.h:7-12`）：

```c
struct tms {
	__kernel_clock_t tms_utime;
	__kernel_clock_t tms_stime;
	__kernel_clock_t tms_cutime;
	__kernel_clock_t tms_cstime;
};
```

### 2.3 「刻度太粗」：`tms_utime` 常常读到 0

```text
== 3. 主动报出「刻度太粗」这件事 ==
  跑一个 1000 次的小循环，tms_utime 的增量 = 0 tick = 0.0 ms
  → 常常是 0。不代表没耗 CPU，只代表不到 1 个 tick（10.0 ms）。
  要测这种量级只能用 CLOCK_PROCESS_CPUTIME_ID（纳秒分辨率）。
```

**这里必须把「精度」和「分辨率」分开**：

| | 内核内部怎么记 | 用户态看到的单位 |
|---|---|---|
| `times()` | `u64` **纳秒**累加（`tgutime`） | `clock_t`，单位 `1/USER_HZ` = 10 ms |
| `CLOCK_PROCESS_CPUTIME_ID` | 同一份 `u64` 纳秒累加 | `struct timespec`，单位 **ns** |

也就是说：**内核一直在用纳秒精度记账**，`times()` 只是「在出口把它除成 10 ms」丢掉了精度。所以：

- 1000 次循环的 CPU 时间 < 10 ms → `times()` 看到 0；
- 但 `CLOCK_PROCESS_CPUTIME_ID` **能看到**（本 demo 实测 `cpu = 0.059 s`，`ticks = 5`）。

> **工程结论**：任何「测一段代码耗时」的需求，**不要用 `times()` / `clock()` 里的 `tms_*`**，直接用 `CLOCK_PROCESS_CPUTIME_ID`。`times()` 只适合做「进程总共烧了多少 CPU」这种宏观统计。

## 3. `CLOCK_PROCESS_CPUTIME_ID` vs `CLOCK_THREAD_CPUTIME_ID`

```text
== 2. CLOCK_PROCESS_CPUTIME_ID vs CLOCK_THREAD_CPUTIME_ID ==
  单线程进程里两者几乎相同：
    进程 CPU = 1.851586704 s
    线程 CPU = 1.851587622 s
    差       = -918 ns
```

单线程进程里两者必然几乎相同 —— **进程只有一个线程，两个口径覆盖同一个执行体**。那 918 ns 的差是「两次读之间进程又跑了一会儿」造成的，不是误差。

多线程下才有本质区别：

| 口径 | 覆盖范围 | 多线程（3 个线程各烧 1 s）时 |
|------|---------|---------------------------|
| `CLOCK_PROCESS_CPUTIME_ID` | **整个线程组**的累加 | ≈ **3 s** |
| `CLOCK_THREAD_CPUTIME_ID` | **仅调用线程** | ≈ **1 s** |

对应的内核实现（`kernel/time/posix-cpu-timers.c:1629-1636`）：

```c
#define PROCESS_CLOCK	make_process_cpuclock(0, CPUCLOCK_SCHED)
#define THREAD_CLOCK	make_thread_cpuclock(0, CPUCLOCK_SCHED)

static int process_cpu_clock_getres(const clockid_t which_clock,
				    struct timespec64 *tp)
{
	return posix_cpu_clock_getres(PROCESS_CLOCK, tp);
}
```

两个宏的区别只在第一个参数（`0` = 当前线程 / `PID` = 整个线程组）。真正的取值逻辑在 `posix_cpu_clock_getres()`（`:160-177`）：

```c
static int
posix_cpu_clock_getres(const clockid_t which_clock, struct timespec64 *tp)
{
	int error = validate_clock_permissions(which_clock);

	if (!error) {
		tp->tv_sec = 0;
		tp->tv_nsec = ((NSEC_PER_SEC + HZ - 1) / HZ);
		if (CPUCLOCK_WHICH(which_clock) == CPUCLOCK_SCHED) {
			/*
			 * If sched_clock is using a cycle counter, we
			 * don't have any idea of its true resolution
			 * exported, but it is much more than 1s/HZ.
			 */
			tp->tv_nsec = 1;
		}
	}
	return error;
}
```

**这段代码解释了 [10.6](10.6-the-software-clock-jiffies.md) 实测表里一个乍看矛盾的地方**：

| 时钟 | `clock_getres` 报的 | 为什么 |
|------|-------------------|--------|
| `CLOCK_PROCESS_CPUTIME_ID` | **1 ns** | 走 `CPUCLOCK_SCHED` 分支 → `:173` 把它改写成 `1` |
| `times()` 的同一份数据 | **10 ms** | 走 `nsec_to_clock_t()`，粒度是 `USER_HZ` |

**同一个 CPU 时间，两个 API 报出两个不同量级的精度** —— 差 7 个数量级。这就是「读数精度」和「时钟分辨率」必须分开讲的原因。

### `CPUCLOCK_SCHED` 是什么意思

`CPUCLOCK_SCHED` 表示「用**调度器时钟**（`sched_clock()`，通常是 TSC 或 `CNTVCT`）来采样」。内核注释直接说了：如果 `sched_clock` 用周期计数器，它的真实分辨率**远优于 1/HZ**，所以干脆报 `1 ns`。

另两个可选口径是 `CPUCLOCK_VIRT`（只算 user）和 `CPUCLOCK_PROF`（user + sys，即 `ITIMER_PROF` 用的）—— 见 `kernel/time/posix-cpu-timers.c:155-156` 里三个 `bases[]`。

> 用户态**无法**选择这三个口径：`clock_gettime(CLOCK_PROCESS_CPUTIME_ID)` 固定用 `SCHED`。想区分 user/sys，只能用 `times()` / `getrusage()`（但它们精度低）或者读 `/proc/self/stat` 的 `utime`/`stime` 字段（也是 `USER_HZ` 粒度）。

## 4. 子进程的时间：只累加到父进程的 `c*` 字段

```text
== 4. 子进程的时间记在 tms_c* 里（RUSAGE_CHILDREN） ==
  子进程烧完 CPU 后 wall= 3.795 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.10 cstime= 0.00 | clock()=1.852 s | ticks=134/50/10/0
  getrusage(RUSAGE_CHILDREN): user=0.105959 s  sys=0.000998 s
```

对照第 1 节的同一行（`nanosleep(300ms)` 之后）：

| 字段 | 子进程跑之前 | 子进程跑之后 | 变化 |
|------|-------------|-------------|------|
| `wall` | 3.688 | **3.795** | +0.107（子进程的墙上耗时） |
| `cpu`（`CLOCK_PROCESS_CPUTIME_ID`） | 1.852 | **1.852** | **完全不变** ⭐ |
| `utime` / `stime` | 1.34 / 0.50 | 1.34 / 0.50 | **完全不变** ⭐ |
| `cutime` | 0.00 | **0.10** | +0.10 s |
| `ticks` 第 3 位 | 0 | **10** | 10 tick = 100 ms |

**这就是「CPU 时间不跨进程传递」的实证**：子进程烧的 CPU **不会**算进父进程的 `CLOCK_PROCESS_CPUTIME_ID`，只会进入 `tms_cutime` / `RUSAGE_CHILDREN`。

内核里的对应代码（`kernel/sys.c:1803-1823`）：

```c
	switch (who) {
	case RUSAGE_BOTH:
	case RUSAGE_CHILDREN:
		utime = p->signal->cutime;
		stime = p->signal->cstime;
		...
		if (who == RUSAGE_CHILDREN)
			break;
		fallthrough;

	case RUSAGE_SELF:
		thread_group_cputime_adjusted(p, &tgutime, &tgstime);
		utime += tgutime;
		stime += tgstime;
```

三条结论：

| 结论 | 依据 |
|------|------|
| `RUSAGE_SELF` **不含**子进程 | `RUSAGE_SELF` 分支只加 `thread_group_cputime_adjusted(p, ...)` |
| `RUSAGE_CHILDREN` **只含**子进程 | `if (who == RUSAGE_CHILDREN) break;` 提前跳出，不走累加 |
| `RUSAGE_BOTH` = 两者之和 | `RUSAGE_BOTH` 不 `break`，直接 `fallthrough` 进 `RUSAGE_SELF` 累加 |

### `getrusage` 里那些 `times()` 没有的字段

```text
  getrusage(RUSAGE_CHILDREN): user=0.105959 s  sys=0.000998 s
```

`getrusage` 的 `struct rusage` 比 `struct tms` 丰富得多，而且**精度是微秒**（远好于 `times()` 的 10 ms）：

| 字段 | 含义 | `times()` 有吗 |
|------|------|---------------|
| `ru_utime` / `ru_stime` | user / sys CPU 时间（**μs**） | 有（但 10 ms 粒度） |
| `ru_maxrss` | 峰值 RSS（KB） | ❌ |
| `ru_minflt` / `ru_majflt` | 次缺页 / 主缺页 | ❌ |
| `ru_nvcsw` / `ru_nivcsw` | 自愿 / 非自愿上下文切换 | ❌ |
| `ru_inblock` / `ru_oublock` | 块输入 / 输出次数 | ❌ |

> **HFT 用法**：`ru_nivcsw`（非自愿上下文切换）持续增长 = 进程在被抢占，是「延迟抖动」的直接证据。`ru_minflt` 增长 = 在发生缺页，说明有内存没锁住（没 `mlock`）。这两个指标比 CPU 时间更有诊断价值。

## 5. `struct tms` / `struct rusage` / `CLOCK_*` 的字段对应

同一份内核数据（`thread_group_cputime_adjusted()` 的纳秒累加值），三套出口：

| 内核源头 | `times()` 出口 | `getrusage()` 出口 | `clock_gettime()` 出口 |
|---------|---------------|-------------------|----------------------|
| `thread_group_cputime_adjusted` → `tgutime` | `tms_utime`（÷10⁷） | `ru_utime`（μs） | `CLOCK_PROCESS_CPUTIME_ID`（ns） |
| `thread_group_cputime_adjusted` → `tgstime` | `tms_stime` | `ru_stime` | 同上（**不区分** user/sys） |
| `signal->cutime` | `tms_cutime` | `RUSAGE_CHILDREN` 的 `ru_utime` | ❌ 没有对应时钟 |
| `signal->cstime` | `tms_cstime` | `RUSAGE_CHILDREN` 的 `ru_stime` | ❌ |
| 本线程 | ❌ | `RUSAGE_THREAD` | `CLOCK_THREAD_CPUTIME_ID` |

**选型建议**：

| 需求 | 用什么 |
|------|--------|
| 给某个函数计时 | `CLOCK_PROCESS_CPUTIME_ID`（或 `CLOCK_THREAD_CPUTIME_ID`，多线程下更准） |
| 要 user/sys 拆分 | `times()` 或 `getrusage()`（后者精度高 4 个数量级） |
| 要缺页/切换/IO 计数 | `getrusage()` |
| 要子进程总账 | `RUSAGE_CHILDREN` |
| 测延迟/超时 | **不要用 CPU 时间**，用 `CLOCK_MONOTONIC` |

## HFT / 嵌入式关联

| 场景 | 结论 |
|------|------|
| **延迟 vs 吞吐** | 「延迟」是墙上时间概念，「CPU 占用」是 CPU 时间概念。行情网关的「单笔处理耗时」必须用 `CLOCK_MONOTONIC`；「每笔占多少 CPU」才用 `CLOCK_PROCESS_CPUTIME_ID` |
| **忙等（busy-wait）** | 忙等的 1 ms 是 100% CPU 时间；`nanosleep` 的 1 ms 是 0% CPU 时间。**HFT 用忙等换延迟，代价就记在 `utime` 上**——这是「低延迟 vs 省电」的定量交换 |
| **`CLOCK_THREAD_CPUTIME_ID` 更实用** | HFT 程序常把热路径钉在专用线程上（`pthread_setaffinity_np`）。此时线程 CPU 时间 = 热路径开销，比进程口径干净得多 |
| **`ru_nivcsw` 是抖动指标** | 非自愿上下文切换 = 被抢占。**持续不为 0 就说明有别人在抢你的核** → 要上 `isolcpus` / `nohz_full` / `SCHED_FIFO` |
| **`ru_minflt` 是缺页指标** | 热路径上缺页 = 几十 µs 的尖峰。修法：`mlockall(MCL_CURRENT|MCL_FUTURE)` + 预热所有缓冲 |
| **`times()` 别用在热路径** | 它的真实开销是「遍历整个线程组的 `signal_struct`」+ 拿 `siglock`，**比 `clock_gettime` 贵得多**，而且粒度 10 ms |
| **内核里的 CPU 时钟** | `CLOCK_PROCESS_CPUTIME_ID` 同时是**定时器**：`timer_create(CLOCK_PROCESS_CPUTIME_ID, ...)` 可以在「进程累计烧掉 N 秒 CPU」时触发信号。这是 POSIX 的 CPU-time 定时器，Ch23 会讲 |
| **嵌入式（无 tickless）** | 老内核上 `HZ=100` 时 `times()` 粒度就是 10 ms；有些 ARM 板子还把 `USER_HZ` 定成 100 而 `CONFIG_HZ=100`，此时 `jiffies_to_clock_t()` 走「Nothing to do」分支，两者粒度相同 |
| **`clock()` 跨平台陷阱** | 非 Linux 平台上 glibc 会退回 `sysdeps/posix/clock.c` 的 `times()` 版本 → **同一份代码在不同平台上精度差 10⁴ 倍**。跨平台代码请直接用 `CLOCK_PROCESS_CPUTIME_ID` |

## 代码自测

<details>
<summary>1. `times()` 的第一个返回值是什么？为什么容易记错？</summary>

它是 **`jiffies_64_to_clock_t(get_jiffies_64())`** —— **开机以来的总 tick 数**（换算成 `USER_HZ` 单位），**和当前进程无关**。

源码（`kernel/sys.c:1023-1034`）：

```c
SYSCALL_DEFINE1(times, struct tms __user *, tbuf)
{
	if (tbuf) {
		struct tms tmp;

		do_sys_times(&tmp);
		if (copy_to_user(tbuf, &tmp, sizeof(struct tms)))
			return -EFAULT;
	}
	force_successful_syscall_return();
	return (long) jiffies_64_to_clock_t(get_jiffies_64());
}
```

进程自己的时间**全在第二个参数里**（`struct tms` 的四个字段）。

本 demo 实测（`ex10_1` 也量到）：

```text
  times() 返回值（开机以来总 tick）= 429840505
    tms_utime=0 tms_stime=0 tms_cutime=0 tms_cstime=0
```

返回值是 4 亿多 tick，四个进程字段全是 0 —— 一眼就能看出两者不是一个东西。

**为什么容易记错**：POSIX 把「返回值」和「出参」放在一起，而返回值语义是「自任意时刻起的 elapsed time」，和 `clock()`（返回**进程** CPU 时间）恰好相反。**`times()` 返回全局，`clock()` 返回进程** —— 两个函数名字相近、语义正好互换。

**怎么用**：两次调用 `times()` 的返回值相减，得到「这段时间内系统跑了多少个 tick」→ 可以推系统负载。进程时间就只看 `struct tms`。

</details>

<details>
<summary>2. `CLOCKS_PER_SEC` 到底是 100 还是 1000000？</summary>

**两个都是真的，因为是两个不同的宏**：

| 谁定义 | 位置 | 值 |
|-------|------|-----|
| 内核 | `include/asm-generic/param.h:10` `# define CLOCKS_PER_SEC  (USER_HZ)` | **100** |
| glibc | glibc `<time.h>` | **1000000** |

内核侧的 `CLOCKS_PER_SEC` 只用来做一件事：填 `auxv` 里的 `AT_CLKTCK`（`fs/binfmt_elf.c:262`），也就是 `sysconf(_SC_CLK_TCK)` 的来源。它代表 `times(2)` 的单位。

用户态看到的 `1000000` 是 `clock(3)` 的单位。glibc 还专门 `_Static_assert` 钉住它（`sysdeps/unix/sysv/linux/clock.c:28-29`）：

```c
  _Static_assert (CLOCKS_PER_SEC == 1000000,
		  "CLOCKS_PER_SEC should be 1000000");
```

**所以绝对不要用 `CLOCKS_PER_SEC` 去换算 `times()` 的结果，也不要用 `sysconf(_SC_CLK_TCK)` 去换算 `clock()` 的结果。** 两条链完全独立：

| API | 单位来源 |
|-----|---------|
| `times()` / `getrusage()` | `sysconf(_SC_CLK_TCK)` = `USER_HZ` = 100 |
| `clock()` | `CLOCKS_PER_SEC` = 1000000 |

本 demo 实测两者差了 **10000 倍**（`sysconf(_SC_CLK_TCK) = 100` vs `CLOCKS_PER_SEC = 1000000`）。

</details>

<details>
<summary>3. `clock()` 和 `times()` 在 Linux 上到底是什么关系？</summary>

**没关系。** `clock()` 在 Linux 上**不调用 `times()`**。

glibc 有**两份** `clock()` 实现：

| 实现 | 位置 | 做法 | 粒度 |
|------|------|------|------|
| Linux 专用 | `sysdeps/unix/sysv/linux/clock.c:24-36` | `__clock_gettime64(CLOCK_PROCESS_CPUTIME_ID, &ts)` → 乘 `CLOCKS_PER_SEC` | **ns** |
| POSIX 通用兜底 | `sysdeps/posix/clock.c:23-31` | `__times(&buf)` → `buf.tms_utime + buf.tms_stime` | 1/USER_HZ |

Linux 上走第一条，源码（`sysdeps/unix/sysv/linux/clock.c:31-35`）：

```c
  if (__glibc_unlikely (__clock_gettime64 (CLOCK_PROCESS_CPUTIME_ID, &ts) != 0))
    return (clock_t) -1;

  return (ts.tv_sec * CLOCKS_PER_SEC
	  + ts.tv_nsec / (1000000000 / CLOCKS_PER_SEC));
```

实测可以验证这一点：

```text
  300 万次 getppid     wall= 3.388 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.00 cstime= 0.00 | clock()=1.852 s | ticks=134/50/0/0
```

- `clock() = 1.852 s` —— 与同一行 `cpu = 1.852 s`（`CLOCK_PROCESS_CPUTIME_ID`）**完全一致**；
- 而 `times()` 的 `utime + stime = 1.34 + 0.50 = 1.84 s` —— **差 12 ms**（就是 10 ms 粒度的圆整损失）。

**结论**：

| 想要 | 用什么 |
|------|--------|
| 高精度「本进程总共烧了多少 CPU」 | `clock_gettime(CLOCK_PROCESS_CPUTIME_ID)`（跨平台稳定） |
| 只是懒得写 `timespec` 减法 | `clock()`（但**没有** user/sys 拆分，也没有子进程字段） |
| user/sys 拆分 | `times()` / `getrusage()` |
| 要可移植 | 别用 `clock()` —— 非 Linux 平台上它会退回 10 ms 粒度的实现 |

</details>

<details>
<summary>4. 为什么 `nanosleep(300ms)` 之后 `wall` 涨了 0.3 s 但 `cpu` 一点没涨？</summary>

因为 CPU 时间的定义是「**处理器真正为本进程工作的时间**」。

`nanosleep()` 把进程挂到 hrtimer 上然后**主动让出 CPU**。这 300 ms 里进程处于**不可运行**状态，调度器根本没给它时间片，所以：

| 指标 | 变化 | 谁提供 |
|------|------|--------|
| `wall`（`CLOCK_MONOTONIC`） | **+0.300 s** | 时钟中断 / 硬件时钟源，**与进程状态无关** |
| `cpu`（`CLOCK_PROCESS_CPUTIME_ID`） | **+0.000 s** | 内核在 `context_switch` 时按实际占用累加 |
| `tms_utime` / `tms_stime` | **不变** | 同上 |

实测对照：

```text
  300 万次 getppid     wall= 3.388 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.00 cstime= 0.00 | clock()=1.852 s | ticks=134/50/0/0
  nanosleep(300ms)       wall= 3.688 s  cpu= 1.852 s | utime= 1.34 stime= 0.50 cutime= 0.00 cstime= 0.00 | clock()=1.852 s | ticks=134/50/0/0
```

两行之间 `wall` 差 `+0.300`，`cpu` 差 `0.000`，`ticks` 一字未变。

**反过来的例子（忙等）**：

```text
  纯用户态忙等后  wall= 0.059 s  cpu= 0.059 s | utime= 0.05 stime= 0.00 ...
```

忙等时 `wall ≈ cpu`，因为进程 100% 占用 CPU。

**工程推论**：

| 想测什么 | 用什么时钟 |
|---------|-----------|
| 「这个服务响应一次请求要多久」（含等 IO、等锁、等网络） | `CLOCK_MONOTONIC` |
| 「这个算法本身要消耗多少处理器时间」 | `CLOCK_PROCESS_CPUTIME_ID` |
| 「这个进程今天一共吃了多少 CPU（可以拿去算成本）」 | `times()` / `getrusage()` |

**用错会得出相反结论**：比如一个「耗 CPU 很低但等 IO 很慢」的服务，用 CPU 时间看是「性能优秀」，用墙上时间看是「延迟灾难」。

</details>

<details>
<summary>5. 为什么 `CLOCK_PROCESS_CPUTIME_ID` 报 1 ns，`times()` 报 10 ms？</summary>

因为**内核内部一直是纳秒精度记账**，差别只在「出口怎么换算」。

| API | 内核内部 | 出口换算 | 用户态看到的粒度 |
|-----|---------|---------|----------------|
| `CLOCK_PROCESS_CPUTIME_ID` | `u64` 纳秒累加 | 直接返回 `timespec` | **1 ns** |
| `times()` | **同一份** `u64` 纳秒累加 | `nsec_to_clock_t()` → ÷10⁷ | **10 ms**（`USER_HZ`） |

`times()` 的换算（`kernel/sys.c:1014-1020`）：先拿到纳秒级的 `tgutime`，再 `nsec_to_clock_t()` 除成 tick。

`CLOCK_PROCESS_CPUTIME_ID` 之所以报 `1 ns` 还有第二个原因 —— `posix_cpu_clock_getres()` 里有个分支（`kernel/time/posix-cpu-timers.c:160-177`）：

```c
	if (!error) {
		tp->tv_sec = 0;
		tp->tv_nsec = ((NSEC_PER_SEC + HZ - 1) / HZ);
		if (CPUCLOCK_WHICH(which_clock) == CPUCLOCK_SCHED) {
			/*
			 * If sched_clock is using a cycle counter, we
			 * don't have any idea of its true resolution
			 * exported, but it is much more than 1s/HZ.
			 */
			tp->tv_nsec = 1;
		}
	}
```

`CLOCK_PROCESS_CPUTIME_ID` / `THREAD_CPUTIME_ID` 走 `CPUCLOCK_SCHED` 分支（`:1629-1630` 的两个宏），所以 `tv_nsec` 被从 `1/HZ`（= 1000000 ns）**改写成 1**。

**所以严格说**：

| 说法 | 对不对 |
|------|--------|
| 「`CLOCK_PROCESS_CPUTIME_ID` 的分辨率是 1 ns」 | 勉强对 —— 它是**声明值**，实际取决于 `sched_clock` 的时间源 |
| 「`times()` 的分辨率是 10 ms」 | 对 —— 它确实在 `nsec_to_clock_t()` 处丢掉了精度 |
| 「内核账本只有 10 ms 精度」 | **错** —— 内核账本是纳秒 |

**实践结论**：要测「小于 10 ms 的代码」必须用 `CLOCK_PROCESS_CPUTIME_ID`，`times()` 会把结果抹成 0。

</details>
