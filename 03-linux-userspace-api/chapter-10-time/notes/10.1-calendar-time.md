## 本节讲什么

「日历时间」（calendar time）就是**从 Epoch 起算的秒数**——一个绝对时间点，不具备任何「人类可读」的含义。本节只解决一个问题：**怎么把它读出来，三种读法各差在哪。**

| 读法 | 容器 | 分辨率 | 现在的状态 |
|------|------|--------|-----------|
| `time()` | `time_t` | **1 秒** | 仍然推荐（只要秒） |
| `gettimeofday()` | `struct timeval`（秒 + 微秒） | 1 μs | POSIX 已标记 **废弃** |
| `clock_gettime(CLOCK_REALTIME)` | `struct timespec`（秒 + 纳秒） | 1 ns | 推荐 |

三个函数读的是**同一个内核变量**，区别只在「截到哪一位」。

| 本节的 demo | 演示什么 |
|-------------|----------|
| `c10_1_calendar_probe.c` | 三种读法同秒、Epoch 原点、`time_t` 真实宽度、2038 边界 |
| `calendar_time.c` | 原书 **Listing 10-1**（p.191），逐字复刻 |

## 1. 三种读法读的是同一个时钟

### 代码示例 A

源码：[../code/c10_1_calendar_probe.c](../code/c10_1_calendar_probe.c)

```c
/* TLPI 第 10 章 §10.1 Calendar Time
 * 日历时间的三种读法 / Epoch 原点 / time_t 的真实宽度与 2038 边界
 *
 * 编译: gcc -O0 -Wall -Wextra -o c10_1_calendar_probe c10_1_calendar_probe.c
 * 运行: ./c10_1_calendar_probe            (无需参数、无需权限)
 *
 * 要钉住的四件事：
 *   1. time() / gettimeofday() / clock_gettime(CLOCK_REALTIME) 读的是**同一个**
 *      墙上时钟，只是分辨率与容器类型不同；
 *   2. time() 的分辨率**恰好是 1 秒**——它就是把精确时钟的 tv_sec 截下来；
 *   3. Epoch 原点是 1970-01-01 00:00:00 **UTC**，但 ctime() 按**本地时区**渲染；
 *   4. 2038 问题在这台机器上**不存在**（time_t 已是 64 位），把 INT32_MAX
 *      当时间戳喂进去才能看到那个著名的边界。
 */
#define _GNU_SOURCE
#include <limits.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/time.h>
#include <time.h>

/* 照抄原书 Listing 10-1 的常量：一个回归年的秒数（用 365.24219 天） */
#define SECONDS_IN_TROPICAL_YEAR (365.24219 * 24 * 60 * 60)

static void show_three_reads(void)
{
    time_t t = time(NULL);
    struct timeval tv;
    struct timespec ts;

    gettimeofday(&tv, NULL);
    clock_gettime(CLOCK_REALTIME, &ts);

    printf("== 1. 同一个墙上时钟的三种读法 ==\n");
    printf("time()                  = %ld\n", (long) t);
    printf("gettimeofday()          = %ld s + %ld us  (tv_usec 上限 999999)\n",
           (long) tv.tv_sec, (long) tv.tv_usec);
    printf("clock_gettime(REALTIME) = %ld s + %ld ns  (tv_nsec 上限 999999999)\n",
           (long) ts.tv_sec, (long) ts.tv_nsec);
    printf("三者 tv_sec 同秒?         %s\n",
           (t == tv.tv_sec && tv.tv_sec == ts.tv_sec) ? "是" : "否（恰好跨秒）");
    printf("time() 丢掉的小数部分    = 0.%09ld s\n\n", (long) ts.tv_nsec);
}

static void show_epoch(void)
{
    time_t zero = 0;
    time_t neg = -1;
    struct tm z;
    char buf[64];

    printf("== 2. Epoch 原点与「负数时间」 ==\n");
    /* ctime() 的日字段是右对齐两位，1 号前面有两个空格 */
    printf("time_t  0 -> ctime()  = %s", ctime(&zero));
    gmtime_r(&zero, &z);
    strftime(buf, sizeof buf, "%F %T", &z);
    printf("time_t  0 -> UTC 格式 = %s\n", buf);
    /* -1 落在 Epoch 前一秒：1969-12-31 23:59:59 */
    printf("time_t -1 -> ctime()  = %s", ctime(&neg));
    printf("\n");
}

static void show_width(void)
{
    time_t t32 = (time_t) INT32_MAX;
    struct tm tm32;
    char buf[64];

    printf("== 3. time_t 的真实宽度与 2038 边界 ==\n");
    printf("sizeof(time_t) = %zu 字节   sizeof(long) = %zu 字节\n",
           sizeof(time_t), sizeof(long));
    printf("sizeof(time_t) == sizeof(long)? %s\n",
           sizeof(time_t) == sizeof(long) ? "是" : "否");
    if (sizeof(time_t) == 8) {
        printf("time_t 是 64 位 -> 本机**没有** 2038 问题（上界约 2924 亿年后）\n");
    } else {
        printf("time_t 是 32 位 -> 本机**有** 2038 问题\n");
    }
    if (gmtime_r(&t32, &tm32) != NULL) {
        strftime(buf, sizeof buf, "%F %T", &tm32);
        printf("把 INT32_MAX 当时间戳（即 32 位 time_t 的上界）:\n");
        printf("  %ld = 0x%08lx -> %s UTC\n",
               (long) t32, (unsigned long) t32 & 0xffffffffUL, buf);
    }
    printf("  同一个值按本地时区看      -> %s", ctime(&t32));
    printf("  这个值就是 2038 问题的引爆点\n\n");
}

int main(void)
{
    show_three_reads();
    show_epoch();
    show_width();

    {
        time_t t = time(NULL);
        printf("== 4. Epoch 起算的绝对时间（原书 Listing 10-1 的开场计算） ==\n");
        printf("seconds since the Epoch = %ld\n", (long) t);
        printf("  about %6.3f years\n", t / SECONDS_IN_TROPICAL_YEAR);
    }
    return 0;
}
```

编译 + 运行：

```bash
gcc -O0 -Wall -Wextra -o c10_1_calendar_probe c10_1_calendar_probe.c
./c10_1_calendar_probe
```

实测（CE，gcc 13.3.0 / Ubuntu 24.04）：

```text
== 1. 同一个墙上时钟的三种读法 ==
time()                  = 1789370857
gettimeofday()          = 1789370857 s + 187898 us  (tv_usec 上限 999999)
clock_gettime(REALTIME) = 1789370857 s + 187901923 ns  (tv_nsec 上限 999999999)
三者 tv_sec 同秒?         是
time() 丢掉的小数部分    = 0.187901923 s
```

逐条解读：

| 输出 | 说明 |
|------|------|
| `time()` = `1789370857` | 纯秒数。它**不是**「另一个时钟」，就是把纳秒读数的小数部分切掉 |
| `gettimeofday()` 的 `187898 us` | `tv_usec` 是**微秒**，上界 999999；它不是「小数部分 ×10⁶ 后再取整」的精确换算 |
| `clock_gettime()` 的 `187901923 ns` | 纳秒。注意它比 `tv_usec×1000`（= 187898000）**多了 3923 ns** —— 两次调用中间真的过了几微秒 |
| `三者 tv_sec 同秒? 是` | 三次调用落在同一秒内。这个「是」是**概率性**的：恰好跨秒就会变「否」，所以 demo 里刻意写了两种文案 |

> ⚠️ 一个容易踩的点：`time()` 返回的是 `time_t`，而 `printf` 它要显式转换。本 demo 统一写 `(long) t`，因为本机 `sizeof(time_t) == sizeof(long) == 8`（见第 3 段）；在 32 位平台上这仍是合法的（`long` 也是 4 字节）。

## 2. Epoch 原点与「负数时间」

```text
== 2. Epoch 原点与「负数时间」 ==
time_t  0 -> ctime()  = Thu Jan  1 00:00:00 1970
time_t  0 -> UTC 格式 = 1970-01-01 00:00:00
time_t -1 -> ctime()  = Wed Dec 31 23:59:59 1969
```

三个必须记住的细节：

| 现象 | 原因 |
|------|------|
| `ctime()` 的输出**自带换行**（所以 demo 里没有在 `%s` 后补 `\n`） | C 标准就是这么定的；`asctime()` 同理 |
| `Thu Jan  1` 里 `1` 前面有**两个空格** | 日字段是右对齐宽度 2（`%e` 风格），不是排版错误 |
| `time_t -1` 是合法的 | `time_t` 是有符号类型，Epoch 之前的时刻就是负数；`ctime()` 会正常渲染成 1969 年 |

---

## 3. `time_t` 的真实宽度与 2038 边界

```text
== 3. time_t 的真实宽度与 2038 边界 ==
sizeof(time_t) = 8 字节   sizeof(long) = 8 字节
sizeof(time_t) == sizeof(long)? 是
time_t 是 64 位 -> 本机**没有** 2038 问题（上界约 2924 亿年后）
把 INT32_MAX 当时间戳（即 32 位 time_t 的上界）:
  2147483647 = 0x7fffffff -> 2038-01-19 03:14:07 UTC
  同一个值按本地时区看      -> Tue Jan 19 03:14:07 2038
  这个值就是 2038 问题的引爆点
```

> **2038 问题的准确表述**：「32 位有符号 `time_t` 在 `INT32_MAX`（= 2147483647 秒）处溢出」。这台机器上 `time_t` 已是 64 位，所以**问题不存在**——必须像 demo 那样把 `INT32_MAX` 显式赋给 `time_t` 才能看到那个边界。
>
> **不是「2038 年之后所有机器都会坏」**：64 位 Linux 从 3.0 起就把 `time_t` 定成 64 位；真正的风险在**仍用 32 位 `time_t` 的老平台 / 嵌入式**，以及**跨平台二进制协议**（一端按 4 字节序列化时间戳，另一端按 8 字节读）。

`time_t` 在 glibc 里的定义是「实现定义」（C 标准只说它得是「算术类型」）。**所以代码里不要假设它是 `long`**——这是可移植性的老坑（Ch03 §3.6.2 讲过同一类问题）。

## 4. 原书 Listing 10-1：绝对时间的开场计算

原书用 Listing 10-1 开场，做的事就是「打印 Epoch 起的秒数，再换算成多少年」。逐字复刻在 [`../code/calendar_time.c`](../code/calendar_time.c)，配套头文件替身是 [`../code/tlpi_hdr.h`](../code/tlpi_hdr.h)。

```c
/* calendar_time.c

   Demonstrate the use of functions for working with calendar time.

   This program retrieves the current time and displays it in various forms.
*/
#include <locale.h>
#include <time.h>
#include <sys/time.h>
#include "tlpi_hdr.h"

#define SECONDS_IN_TROPICAL_YEAR (365.24219 * 24 * 60 * 60)

int
main(int argc, char *argv[])
{
    time_t t;
    struct tm *gmp, *locp;
    struct tm gm, loc;
    struct timeval tv;

    /* Retrieve time, convert and display it in various forms */

    t = time(NULL);
    printf("Seconds since the Epoch (1 Jan 1970): %ld", (long) t);
    printf(" (about %6.3f years)\n", t / SECONDS_IN_TROPICAL_YEAR);

    if (gettimeofday(&tv, NULL) == -1)
        errExit("gettimeofday");
    printf("  gettimeofday() returned %ld secs, %ld microsecs\n",
            (long) tv.tv_sec, (long) tv.tv_usec);

    gmp = gmtime(&t);
    if (gmp == NULL)
        errExit("gmtime");

    gm = *gmp;          /* Save local copy, since *gmp may be modified
                           by asctime() or gmtime() */
    printf("Broken down by gmtime():\n");
    printf("  year=%d mon=%d mday=%d hour=%d min=%d sec=%d ", gm.tm_year,
            gm.tm_mon, gm.tm_mday, gm.tm_hour, gm.tm_min, gm.tm_sec);
    printf("wday=%d yday=%d isdst=%d\n", gm.tm_wday, gm.tm_yday, gm.tm_isdst);

    /* The TZ environment variable will affect localtime().
       Try, for example:

                TZ=Pacific/Auckland calendar_time
    */

    locp = localtime(&t);
    if (locp == NULL)
        errExit("localtime");

    loc = *locp;        /* Save local copy */

    printf("Broken down by localtime():\n");
    printf("  year=%d mon=%d mday=%d hour=%d min=%d sec=%d ",
            loc.tm_year, loc.tm_mon, loc.tm_mday,
            loc.tm_hour, loc.tm_min, loc.tm_sec);
    printf("wday=%d yday=%d isdst=%d\n\n",
            loc.tm_wday, loc.tm_yday, loc.tm_isdst);

    printf("asctime() formats the gmtime() value as: %s", asctime(&gm));
    printf("ctime() formats the time() value as:     %s", ctime(&t));

    printf("mktime() of gmtime() value:    %ld secs\n", (long) mktime(&gm));
    printf("mktime() of localtime() value: %ld secs\n", (long) mktime(&loc));

    exit(EXIT_SUCCESS);
}
```


| 输出行 | 说明 |
|--------|------|
| `about 56.703 years` | 原书常量 `SECONDS_IN_TROPICAL_YEAR = 365.24219 * 24 * 60 * 60`（**回归年**，不是 365 或 365.25） |
| `year=126` | `struct tm.tm_year` = 真实年份 − 1900 → 2026 |
| `mon=8` | `tm_mon` = 0..11 → 9 月 |
| `yday=256` | `tm_yday` = 0..365 → 第 257 天（**从 0 起算**） |
| `wday=1` | `tm_wday`：0 = 星期日，所以 1 = 星期一 |
| `isdst=0` | `gmtime()` 恒为 0（UTC 没有夏令时）；`localtime()` 才可能有 1 |
| `mktime() of gmtime() value` 也等于原值 | 这台容器时区是 UTC，所以 `mktime`（按本地解释）和 `timegm` 等价；**换到东八区这一行就会差 28800 秒**——这是 `mktime` 常见误解的来源，见 [10.3](10.3-timezones.md) 第 5 段实测 |

| 参数 | 为什么必须加 |
|------|-------------|
| `-Wno-unused-parameter` | 原书 `main(argc, argv)` 没用这两个参数，`-Wextra` 会告警。**改源码就破坏了「逐字复刻」**，所以只能动编译参数 |
| `-D_XOPEN_SOURCE=700`（仅 `strtime.c` 需要） | 原书 `strtime.c` 写的是 `#define _XOPEN_SOURCE`（**不给值**），2010 年的 glibc 认，现代 glibc 不认 → `strptime` 的声明不可见。这本身就是一条可移植性结论 |

## 5. 内核坐标：这两个 syscall 长在哪

| 事实 | 源码位置（v6.6） |
|------|-----------------|
| `time()` 的 syscall 定义 | `kernel/time/time.c:62` `SYSCALL_DEFINE1(time, __kernel_old_time_t __user *, tloc)` |
| `gettimeofday()` 的 syscall 定义 | `kernel/time/time.c:140` `SYSCALL_DEFINE2(gettimeofday, struct __kernel_old_timeval __user *, tv, ...)` |
| 32 位兼容版 | `kernel/time/time.c:105`（`time32`）、`:224`（`COMPAT_SYSCALL_DEFINE2(gettimeofday, ...)`） |
| `struct timespec` 的 uapi 定义 | `include/uapi/linux/time.h:11` |

但**在 x86-64 上这三个函数通常根本不进内核**：glibc 会让它们走 **vDSO**（用户态直接读内核映射出来的 `vdso_data` 共享页），所以 `clock_gettime` 一次只要十几纳秒（见 [10.6](10.6-the-software-clock-jiffies.md) 的开销实测）。真正陷入内核的是 `read` 这类必须走设备的调用。

## HFT / 嵌入式关联

| 场景 | 结论 |
|------|------|
| **延迟/超时测量** | 绝不用这里的任何一个时钟——它们都是 `CLOCK_REALTIME` 家族，会被 NTP 拨。用 `CLOCK_MONOTONIC`（[10.7](10.7-process-time.md)） |
| **日志时间戳** | 要「人可读」就用 `CLOCK_REALTIME`，但同时**必须**再记一个 `CLOCK_MONOTONIC` 用于算间隔 |
| **纳秒戳的落地格式** | `tv_sec` + `tv_nsec` 两字段拼接；不要先转成 `double`——`double` 在 1.7e9 秒附近的有效位只到 ~238 ns，会丢精度 |
| **嵌入式（32 位 ARM / RISC-V）** | 先确认 `sizeof(time_t)`。`time64` 迁移没做干净的板子上，`time_t` 仍是 4 字节 → 2038 问题是现实问题 |
| **安全提示** | `time_t -1` 是**合法**值，所以「用 -1 表示失败」在 `time()` 上不成立；`time()` 本身没有失败路径（它返回 `time_t` 而不是 -1） |

## 代码自测

<details>
<summary>1. 为什么 `time()` 的分辨率恰好是 1 秒，而不是「1 秒 ± 一点」？</summary>

因为内核里 `time()` 返回的就是同一个墙上时钟的 `tv_sec` 字段——它没有自己的时钟源，只是把纳秒读数**截断**到秒。实测：`time()` 与同一瞬间的 `clock_gettime(CLOCK_REALTIME)` 的 `tv_sec` 完全相等（本 demo 第 1 段 `三者 tv_sec 同秒? 是`），而两者相差的正是被丢掉的那 `0.187901923 s`。

注意「截断」而非「四舍五入」：Epoch 之后 0.9 秒时 `time()` 返回 0，不是 1。

</details>

<details>
<summary>2. `sizeof(time_t) == sizeof(long)` 在 x86-64 Linux 上成立，能不能据此把 `time_t` 当 `long` 用？</summary>

**能过编译，但不能算对**。三个理由：

1. **C 标准只说 `time_t` 是「算术类型」，没说宽度**。ILP32 平台上 `long` 是 4 字节，`time_t` 可能是 4 也可能是 8（取决于有没有走 time64 接口）。
2. **`printf` 的格式符要跟着变**。写死 `%ld` 在 `time_t` 是 4 字节的平台上会读错栈上的位宽（UB）。规范做法是转成 `intmax_t` 打 `%jd`。
3. **这属于 Ch03 §3.6.2 那类「实现定义」问题**——换平台就静默出错，没有编译期保护。

</details>

<details>
<summary>3. 把 `INT32_MAX` 喂给 64 位 `time_t` 得到 2038-01-19 03:14:07。为什么是这个时刻？</summary>

`INT32_MAX = 2³¹ − 1 = 2147483647` 秒。从 1970-01-01 00:00:00 UTC 起算 2147483647 秒：

- 2147483647 / 86400 ≈ 24855.13 天 ≈ 68.05 年
- 1970 + 68 = 2038 年，落在 1 月 19 日 03:14:07

秒数 `07` 会被 `ctime()` 排成 `:07`——这不是巧合也不是排版问题，就是 2³¹−1 的个位。

**再补一刀**：如果 `time_t` 是 32 位**无符号**（某些老实现），上界变成 4294967295 → 2106-02-07；这解释了为什么「2038 问题」有时被写成「2106 问题」——**取决于有符号还是无符号**。

</details>

<details>
<summary>4. `ctime()` 的输出末尾有换行，导致输出里多一个空行。这是 bug 吗？怎么避开？</summary>

不是 bug。`ctime()` / `asctime()` 的返回值**总是**以 `\n` 结尾（C 标准明确定义），因为它们诞生于「打印到终端」的年代。

避开方式按推荐度排序：

| 做法 | 说明 |
|------|------|
| 用 `strftime()` 自己格式化 | 最干净，且可控（`%F %T` → `2026-09-14 08:43:35`） |
| 用 `%s` 打完后 `printf("\n")` 不要再补 | 本 demo 第 2 段就是这么做的 |
| 打完后 `s[strlen(s) - 1] = '\0'` | **要小心**：`ctime()` 返回的是静态缓冲区，改它会污染后续调用 |
| 用 `ctime_r()` + 自己的缓冲区 | 线程安全版，但同样带 `\n` |

</details>

<details>
<summary>5. 本 demo 有 4 段，其中第 1 段的 `三者 tv_sec 同秒?` 输出「是」。这个结果可复现吗？</summary>

**不可复现——它是概率性的**，这正是 demo 里为什么准备了两套文案（`"是"` / `"否（恰好跨秒）"`）。三次调用间隔不到 1 μs，但落在一秒的**边界**上就会跨秒（概率约 3 μs / 1 s ≈ 3×10⁻⁶）。

这一点在写笔记时很重要：**凡是依赖「同一秒内完成」的输出都不能当作稳定事实引用**。本仓库的约定是——会被抄进笔记的输出必须**可逐字复现**，所以其它 demo（`c10_2_strftime` / `c10_3_timezone` / `ex10_2`）全部改用**固定时间戳** `1700000000` 而不是 `time(NULL)`。

</details>
