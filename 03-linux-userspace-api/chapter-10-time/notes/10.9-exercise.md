## 练习 1（原书 10-1）：`clock_t` 的回绕周期

### 题干（原文逐字）

> **10-1.** Assume a system where the value returned by the call `sysconf(_SC_CLK_TCK)` is 100. Assuming that the `clock_t` value returned by `times()` is an unsigned 32-bit integer, how long will it take before this value cycles so that it restarts at 0? Perform the same calculation for the `CLOCKS_PER_SEC` value returned by `clock()`.

**中译**：假设某系统的 `sysconf(_SC_CLK_TCK)` 返回 100；又假设 `times()` 返回的 `clock_t` 是无符号 32 位整数。那么：

1. 这个值要多久才会**回绕到 0**？
2. 对 `clock()` 使用的 `CLOCKS_PER_SEC` 做同样的计算。

### 解

源码：[../code/ex10_1_clock_cycle.c](../code/ex10_1_clock_cycle.c)

```c
/* TLPI 第 10 章 §10.9 练习 10-1（原书唯一的一道习题）
 *
 * 题干（原书 §10.9，逐字）：
 *   "Assume a system where the value returned by the call sysconf(_SC_CLK_TCK)
 *    is 100. Assuming that the clock_t value returned by times() is an unsigned
 *    32-bit integer, how long will it take before this value cycles so that it
 *    restarts at 0? Perform the same calculation for the CLOCKS_PER_SEC value
 *    returned by clock()."
 *
 * 中译：假设 sysconf(_SC_CLK_TCK) 返回 100；再假设 times() 返回的 clock_t
 * 是**无符号 32 位**整数，那么这个值回绕到 0 需要多久？对 clock() 返回的
 * CLOCKS_PER_SEC 值做同样的计算。
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex10_1_clock_cycle ex10_1_clock_cycle.c
 * 运行: ./ex10_1_clock_cycle                    (无需参数、无需权限)
 *
 * 这道题真正要你发现的是：**times() 和 clock() 的时钟频率不一样**，
 * 所以同样宽度的 clock_t，回绕周期差了两个数量级。
 * 顺带把「假想 32 位」与「本机真实 clock_t」对照一下。
 */
#include <limits.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/times.h>
#include <time.h>
#include <unistd.h>

static void human(double secs, char *out, size_t n)
{
    if (secs >= 365.0 * 24 * 3600)
        snprintf(out, n, "%.2f 年", secs / (365.0 * 24 * 3600));
    else if (secs >= 24 * 3600)
        snprintf(out, n, "%.2f 天", secs / (24 * 3600));
    else if (secs >= 3600)
        snprintf(out, n, "%.4f 小时", secs / 3600);
    else if (secs >= 60)
        snprintf(out, n, "%.2f 分钟", secs / 60);
    else
        snprintf(out, n, "%.3f 秒", secs);
}

int main(void)
{
    long tck = sysconf(_SC_CLK_TCK);
    char h1[40], h2[40], h3[40];
    double cycle_times, cycle_clock, cycle_real;

    printf("== 0. 本机的三个常数 ==\n");
    printf("sysconf(_SC_CLK_TCK) = %ld      <- times() 的每秒 tick 数\n", tck);
    printf("CLOCKS_PER_SEC       = %ld  <- clock() 的每秒 tick 数\n",
           (long) CLOCKS_PER_SEC);
    printf("sizeof(clock_t)      = %zu 字节   <- 本题前提说它是 32 位\n\n",
           sizeof(clock_t));

    /* --- 题干的假设：clock_t 是无符号 32 位 --- */
    {
        double max32 = 4294967296.0;      /* 2^32，回绕点的值就是它 */

        cycle_times = max32 / (double) tck;
        cycle_clock = max32 / (double) CLOCKS_PER_SEC;
        human(cycle_times, h1, sizeof h1);
        human(cycle_clock, h2, sizeof h2);

        printf("== 1. 按题干的假设算（clock_t = 无符号 32 位，2^32 = %.0f）==\n", max32);
        printf("  times() 按 _SC_CLK_TCK=%ld 计：\n", tck);
        printf("    %.0f / %ld = %.2f 秒 = %s\n", max32, tck, cycle_times, h1);
        printf("  clock() 按 CLOCKS_PER_SEC=%ld 计：\n", (long) CLOCKS_PER_SEC);
        printf("    %.0f / %ld = %.4f 秒 = %s\n", max32, (long) CLOCKS_PER_SEC,
               cycle_clock, h2);
        printf("  → 同样的位宽，频率越高回绕越快，两者差了 %.0f 倍\n\n",
               (double) CLOCKS_PER_SEC / (double) tck);
    }

    /* --- 本机真实情况 --- */
    printf("== 2. 本机真实情况（clock_t 其实是 %zu 字节的有符号整数）==\n", sizeof(clock_t));
    {
        int bits = (int) (sizeof(clock_t) * 8);

        printf("  clock_t 是 %d 位有符号 -> 上界 %.0f\n",
               bits, (double) ((uint64_t) 1 << (bits - 1)) - 1);
        cycle_real = ((double) ((uint64_t) 1 << (bits - 1)) - 1) / (double) tck;
        human(cycle_real, h3, sizeof h3);
        printf("  times() 的回绕周期 = %.0f / %ld = %.3e 秒 = %s\n",
               ((double) ((uint64_t) 1 << (bits - 1)) - 1), tck, cycle_real, h3);
        printf("  → 在这台机器上「回绕」不是现实问题；题干里的 32 位是**教学假设**，\n");
        printf("    也是嵌入式老平台（32 位 time_t + 32 位 clock_t）的真实处境。\n\n");
    }

    printf("== 3. 现场看一眼真实的 tick 值 ==\n");
    {
        struct tms t;
        clock_t c;

        if (times(&t) == (clock_t) -1) {
            printf("  times() 失败\n");
            return 1;
        }
        c = clock();
        printf("  times() 返回值（开机以来总 tick）= %ld\n", (long) times(&t));
        printf("    tms_utime=%ld tms_stime=%ld tms_cutime=%ld tms_cstime=%ld\n",
               (long) t.tms_utime, (long) t.tms_stime,
               (long) t.tms_cutime, (long) t.tms_cstime);
        printf("  clock() 返回值（本进程 CPU tick）= %ld\n", (long) c);
        printf("  → times() 的第一个返回值是 **开机以来的 clock_t 计数**，\n");
        printf("     不是进程时间；进程时间在 struct tms 里。这是这道题的隐藏考点。\n");
    }
    return 0;
}
```

编译 + 运行：

```bash
gcc -O0 -Wall -Wextra -o ex10_1_clock_cycle ex10_1_clock_cycle.c
./ex10_1_clock_cycle
```

实测（CE，gcc 13.3.0）：

```text
== 0. 本机的三个常数 ==
sysconf(_SC_CLK_TCK) = 100
CLOCKS_PER_SEC       = 1000000
sizeof(clock_t)      = 8 字节

== 1. 按题干的假设算（clock_t = 无符号 32 位，2^32 = 4294967296）==
  times() 按 _SC_CLK_TCK=100 计：
    4294967296 / 100 = 42949672.96 秒 = 1.36 年
  clock() 按 CLOCKS_PER_SEC=1000000 计：
    4294967296 / 1000000 = 4294.9673 秒 = 1.1930 小时
  → 同样的位宽，频率越高回绕越快，两者差了 10000 倍
```

### 答案

| 问题 | 计算 | 答案 |
|------|------|------|
| `times()` 的 `clock_t` 多久回绕 | `2³² / 100 = 42949672.96 s` | **约 497.1 天 ≈ 1.36 年** |
| `clock()` 的 `clock_t` 多久回绕 | `2³² / 1000000 = 4294.9673 s` | **约 1.193 小时** |

**关键观察：位宽相同，频率越高回绕越快。** `CLOCKS_PER_SEC / _SC_CLK_TCK = 1000000 / 100 = 10000`，所以两个周期差 **10000 倍**。

这也说明一件事：**`clock_t` 这个类型名完全不能告诉你单位**（[10.7 §0](10.7-process-time.md) 讲过）——`times()` 用它表示 10 ms 刻度，`clock()` 用它表示 1 µs 刻度，同一个名字、差 10000 倍。

### 三个容易被扣分的细节

**① `2³²` 还是 `2³² − 1`？**

| 量 | 值 | 含义 |
|----|-----|------|
| 无符号 32 位的**最大值** | `2³² − 1 = 4294967295` | 能表示的最大数 |
| **回绕周期**（回到 0 需要多少个数） | `2³² = 4294967296` | 从 0 数到最大值共 2³² 个数 |

问的是「**回绕到 0** 需要多久」，所以用 **2³²**。这两个数差 1，算出来的周期差 `1/100` 秒——虽然不影响结论，但概念上必须分清。（不少公开解答把「最大值是 4294967296」写错，其实是把**周期**说成了**最大值**。）

**② 题干假设的 32 位在本机**不成立**。**

```text
sizeof(clock_t)      = 8 字节
```

本机 `clock_t` 是 **64 位有符号**，周期约 **29.2 亿年**：

```text
== 2. 本机真实情况（clock_t 其实是 8 字节的有符号整数）==
  clock_t 是 64 位有符号 -> 上界 9223372036854775808
  times() 的回绕周期 = 9223372036854775808 / 100 = 9.223e+16 秒 = 2924712086.78 年
```

所以：

| 平台 | `clock_t` 宽度 | `times()` 回绕周期 |
|------|---------------|-------------------|
| 题干假设 | 32 位无符号 | 1.36 年 |
| 本机（x86-64 Linux） | 64 位有符号 | ≈ 29.2 亿年 |
| **嵌入式老平台 / 32 位系统** | 32 位 | **1.36 年** ⚠️ |

> **这才是这道题的真实意义**：不是算一个数学题，而是让你意识到 **32 位平台上 `times()` 的返回值一年半就会回绕**。
>
> 后果：如果拿两次 `times()` 的**返回值**（开机 tick 数）相减算「系统运行了多久」，在 32 位机器上跨过回绕点会得到**负数或巨大的错误值**。正确做法是用 `CLOCK_BOOTTIME` 或 `jiffies` 的 64 位版本（`get_jiffies_64()`）。

**③ 「隐藏考点」：`times()` 的返回值不是进程时间。**

```text
== 3. 现场看一眼真实的 tick 值 ==
  times() 返回值（开机以来总 tick）= 429840505
    tms_utime=0 tms_stime=0 tms_cutime=0 tms_cstime=0
  clock() 返回值（本进程 CPU tick）= 540
```

`times()` 返回 **429840505**（开机以来的 tick，约 4972 天？不——`429840505 / 100 = 4298405 s ≈ 49.7 天`，容器宿主机已运行约 50 天），而四个进程字段全是 **0**。

**返回值 4 亿 + 字段全 0** 这个对比就是最直观的证据：**[10.7 §2](10.7-process-time.md) 讲的那个 `jiffies_64_to_clock_t(get_jiffies_64())` 就在眼前。**

## 练习 2（自编）：打印 ISO 8601 带时区偏移的时间戳

### 题目

写一个函数，把一个 `struct timespec` 输出成 ISO 8601 格式，**带毫秒/微秒和时区偏移**：

```text
2023-11-15T06:13:20.123456+08:00
```

要求：

1. 在 `TZ=UTC` / `Asia/Shanghai` / `America/New_York` 下都正确（含负偏移）；
2. 在**半刻钟时区**（`Asia/Kolkata` = +05:30、`Asia/Kathmandu` = +05:45）下也正确；
3. 亚秒部分要能选微秒或纳秒；
4. 对比一下「硬编码 `+0800`」会错成什么样。

### 解

源码：[../code/ex10_2_utc_offset.c](../code/ex10_2_utc_offset.c)

```c
/* TLPI 第 10 章 §10.3/§10.8 配套自编练习（非原书习题）
 * 正确地把「纳秒时间戳」打成带时区偏移的 ISO 8601 字符串
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex10_2_utc_offset ex10_2_utc_offset.c
 * 运行: ./ex10_2_utc_offset                     (无需参数、无需权限)
 *
 * 这道题针对的是一个非常常见的写法错误：把时区偏移**硬编码**成 "+0800"。
 * 正确做法是从 struct tm 的 tm_gmtoff 字段（glibc/BSD 扩展）算出来，
 * 它自动带正负号、也自动处理半小时/三刻钟时区（如 +05:30、+05:45）。
 *
 * 全部用固定时间戳，只有 TZ 在变 → 输出可复现。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

#define FIXED 1700000000L   /* 2023-11-14 22:13:20 UTC */

static const char *tzs[] = {
    "UTC", "Asia/Shanghai", "America/New_York", "Asia/Kolkata",
    "Asia/Kathmandu", "Australia/Adelaide", NULL
};

/* 错误写法：偏移写死 */
static void wrong_way(time_t t, char *out, size_t n)
{
    struct tm tm;
    char base[64];

    localtime_r(&t, &tm);
    strftime(base, sizeof base, "%Y-%m-%d %H:%M:%S", &tm);
    /* 硬编码「中国是 +8」，换任何别的时区都错 */
    snprintf(out, n, "%s +0800", base);
}

/* 正确写法：偏移从 tm_gmtoff 算 */
static void right_way(const struct timespec *ts, const struct tm *tm,
                      char *out, size_t n)
{
    char base[64];
    long off = tm->tm_gmtoff;
    char sign = (off < 0) ? '-' : '+';
    long ao = (off < 0) ? -off : off;

    strftime(base, sizeof base, "%Y-%m-%dT%H:%M:%S", tm);
    snprintf(out, n, "%s.%06ld%c%02ld:%02ld",
             base, (long) (ts->tv_nsec / 1000), sign, ao / 3600, (ao % 3600) / 60);
}

int main(void)
{
    struct timespec ts = { FIXED, 123456789L };   /* 故意给个非零纳秒 */
    char w[80], r[80];

    printf("== 1. 错误写法 vs 正确写法（同一个时间戳，逐个时区看） ==\n");
    printf("  固定时间戳 %ld，纳秒 123456789 -> 微秒 %ld\n\n",
           (long) ts.tv_sec, (long) (ts.tv_nsec / 1000));

    for (int i = 0; tzs[i] != NULL; i++) {
        struct tm tm;
        char z1[80], z2[80];

        setenv("TZ", tzs[i], 1);
        tzset();
        localtime_r(&ts.tv_sec, &tm);

        wrong_way(ts.tv_sec, w, sizeof w);
        right_way(&ts, &tm, r, sizeof r);
        strftime(z1, sizeof z1, "%Z", &tm);     /* 缩写，没有冒号 */
        strftime(z2, sizeof z2, "%z", &tm);     /* +0800，没有冒号 */

        printf("  TZ=%-22s %%-Z=%-5s %%-z=%-6s\n", tzs[i], z1, z2);
        printf("      错误: %s\n", w);
        printf("      正确: %s\n", r);
    }
    printf("\n");

    printf("== 2. 想要「带冒号」的偏移？%%:z 这条路走不通 ==\n");
    {
        /* ⚠️ 这段要**用变量格式串**才能观察到两件事：
             ① gcc 的 strftime 格式检查器（-Wformat=）不认 %:z，写字面量直接告警；
             ② 实测 glibc 2.39 **根本不实现** %:z / %::z / %:::z ——
                strftime 把它当成「无法识别的转换」，原样吐字面量
                （返回值 = 字面量长度 3，输出就是那三个字符）。
           所以网上说的「glibc 支持 %:z」在本机是**假的**：要冒号只能自己拼。 */
        static const char *colon_fmt = "%:z";

        for (int i = 0; tzs[i] != NULL; i++) {
            struct tm tm;
            char b1[80], b2[80], mine[80];
            long off;
            size_t n;

            setenv("TZ", tzs[i], 1);
            tzset();
            localtime_r(&ts.tv_sec, &tm);

            strftime(b1, sizeof b1, "%z", &tm);
            n = strftime(b2, sizeof b2, colon_fmt, &tm);

            /* 自己拼带冒号的版本：偏移从 tm_gmtoff 算，符号与分种数都自动对 */
            off = tm.tm_gmtoff;
            snprintf(mine, sizeof mine, "%c%02ld:%02ld",
                     off < 0 ? '-' : '+', labs(off) / 3600, labs(off % 3600) / 60);

            printf("  TZ=%-22s %%-z=%-7s %%-:z=\"%s\"(ret=%zu)  自己拼=%s\n",
                   tzs[i], b1, b2, n, mine);
        }
    }
    printf("\n");

    printf("== 3. 半/三刻钟时区是最容易写错的地方 ==\n");
    for (int i = 0; tzs[i] != NULL; i++) {
        struct tm tm;
        long off;

        setenv("TZ", tzs[i], 1);
        tzset();
        localtime_r(&ts.tv_sec, &tm);
        off = tm.tm_gmtoff;
        if (off % 3600 == 0)
            continue;
        printf("  %-22s tm_gmtoff = %+ld s -> %+03ld:%02ld\n",
               tzs[i], off, off / 3600, labs(off % 3600) / 60);
    }
    printf("\n");

    printf("== 4. 结论 ==\n");
    printf("  * 时区偏移必须从 tm_gmtoff 取（或从 %%z 取），**不要硬编码**；\n");
    printf("  * 亚秒部分要自己打：strftime 的 %%S 只到秒，纳秒/微秒得单独拼；\n");
    printf("  * 纳秒 -> 微秒是**截断**除法（/1000），不是四舍五入；\n");
    printf("  * ISO 8601 的偏移推荐带冒号（+08:00），%%z 给的是无冒号形式（+0800）；\n");
    printf("    glibc 2.39 的 strftime **不认** %%:z（原样吐字面量，见第 2 段实测），\n");
    printf("    要冒号只能像 right_way() 那样从 tm_gmtoff 自己拼。\n");
    return 0;
}
```

```text
      正确: 2023-11-15T08:43:20.123456+10:30
```

**「错误」那一列是故意写死的 `+0800`**：它在 `TZ=UTC` 下就把 `+0800` 安到了一个 UTC 时间上，在 `Asia/Kathmandu` 下把 `+05:45` 的时间标成了 `+0800` —— **时间戳彻底失去意义**（同一时刻可以被解析成 5 个多小时之前的另一个瞬间）。

### 三个要点

**① 偏移只能从 `tm_gmtoff` 取（或从 `%z` 取），永远不要硬编码。**

`%z` 输出的原始形式是**无冒号**的 `+0800` / `-0500`。**ISO 8601 推荐带冒号**（`+08:00`）——那怎么拿到？

**② `%:z` 这条路走不通。**

```text
== 2. 想要「带冒号」的偏移？%:z 这条路走不通 ==
  TZ=UTC                    %-z=+0000   %-:z="%:z"(ret=3)  自己拼=+00:00
  TZ=Asia/Shanghai          %-z=+0800   %-:z="%:z"(ret=3)  自己拼=+08:00
  TZ=America/New_York       %-z=-0500   %-:z="%:z"(ret=3)  自己拼=-05:00
```

`strftime` 返回 **3**，输出就是字面的 **`%:z`** 三个字符——**它没被替换**。

这是 **glibc 2.39 的真实行为**，不是用法错误。`%z` 之外带修饰符的变体（`%:z` / `%::z` / `%:::z`）glibc **一个都不支持**：

| 格式串 | glibc 2.39 实测 `ret` | 输出 |
|--------|---------------------|------|
| `%z` | 5 | `+0530` ✔ |
| `%:z` | 3 | `%:z` ✘ 原样吐字面量 |
| `%::z` | 4 | `%::z` ✘ |
| `%:::z` | 5 | `%:::z` ✘ |
| `%Ez` | 5 | `+0530` ✔（POSIX 的 `E` 修饰符是支持的） |
| `%Oz` | 5 | `+0530` ✔ |

源码依据在 glibc 的 `time/strftime_l.c:1437-1447`：

```c
	default:
	  /* Unknown format; output the format, including the '%',
	     since this is most likely the right thing to do if a
	     multibyte string has been misparsed.  */
	bad_format:
	  {
	    int flen;
	    for (flen = 1; f[1 - flen] != L_('%'); flen++)
	      continue;
	    cpy (flen, &f[1 - flen]);
	  }
	  break;
```

**「无法识别的转换就原样输出」**——所以 `%:z` 被当成「`%` + 非格式字符」，原样打出来。

> **注意别和 `date +%:z` 搞混**：GNU coreutils 的 `date` **支持** `%:z`（它自己解析格式串），但 **libc 的 `strftime` 不支持**。所以 `date` 里能用的写法，搬到 C 程序里就是错的。这是很常见的一个坑。

**③ 要冒号只能自己拼，而且必须处理负数取模。**

demo 里的做法（从 `tm_gmtoff` 算）：

```c
off = tm.tm_gmtoff;
snprintf(mine, sizeof mine, "%c%02ld:%02ld",
         off < 0 ? '-' : '+', labs(off) / 3600, labs(off % 3600) / 60);
```

两个坑：

| 坑 | 说明 |
|----|------|
| **必须先 `labs()` 再取模** | `-18000 % 3600 = -0`（C 里负数取模结果符号跟随被除数），直接算会得到 `-05:-0` |
| **不能只除 3600** | 半刻钟时区（`+05:30`）的偏移是 `19800 s`，`19800 / 3600 = 5.5` 取整是 5 —— 剩下那 1800 秒必须单独算成分钟 |

实测的半刻钟 / 三刻钟时区：

```text
== 3. 半/三刻钟时区是最容易写错的地方 ==
  Asia/Kolkata           tm_gmtoff = +19800 s -> +05:30
  Asia/Kathmandu         tm_gmtoff = +20700 s -> +05:45
  Australia/Adelaide     tm_gmtoff = +37800 s -> +10:30
```

`+20700 s = 5×3600 + 45×60` —— **不整除 3600**，所以任何「偏移一定是整小时」的假设都会错。

**④ 亚秒部分也别指望 `strftime`。**

`%S` 只到秒、`%T` 只到秒。微秒/纳秒必须自己拼（demo 的做法）：

```c
snprintf(..., "%s.%06ld", buf, ts.tv_nsec / 1000);   /* 纳秒 → 微秒 */
```

**注意是截断除法**：`123456789 ns / 1000 = 123456 µs`（丢掉了 789 ns），**不是四舍五入**。要四舍五入得写 `(ts.tv_nsec + 500) / 1000`，但那会在 `tv_nsec = 999999999` 时进位到 `1000000`，产生 7 位微秒——**必须额外处理进位**。

## 练习 3（自编）：`nanosleep` 的精度边界与 `EINTR` 补睡

### 题目

1. `nanosleep` 请求 1 µs 能睡着吗？（提示：1 个 jiffy 是 10 ms）
2. `sleep(1)` 的实际误差有多大？`sleep` 的返回值是什么含义？
3. `nanosleep` 被信号打断后怎么办？为什么不能「掐头重睡」？

### 解

源码：[../code/ex10_3_sleep_precision.c](../code/ex10_3_sleep_precision.c)

```c
/* TLPI 第 10 章 §10.6/§10.8 配套自编练习（非原书习题）
 * 睡眠到底准不准：nanosleep 的亚 jiffy 能力 / sleep(1) 的误差 / 被信号打断怎么补
 *
 * 编译: gcc -O0 -Wall -Wextra -o ex10_3_sleep_precision ex10_3_sleep_precision.c
 * 运行: ./ex10_3_sleep_precision                (无需参数；跑几秒)
 *
 * 三个要看的点：
 *   1. 请求 1 us、10 us 这种远小于 1 个 jiffy（本机 10 ms）的睡眠，
 *      **确实能睡着** —— 这是 hrtimer 而不是 jiffies 在支撑；
 *   2. 但「睡得短」不等于「睡得准」：请求越小，固定开销占比越大，
 *      实测值普遍大于请求值（只能晚了醒，不能早了醒）；
 *   3. nanosleep 被信号打断会返回 -1/EINTR 并报出**剩余时长**，
 *      补睡要用这个剩余量，不能掐头重睡。
 */
#define _GNU_SOURCE
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/time.h>
#include <time.h>
#include <unistd.h>

static double now(void)
{
    struct timespec ts;

    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double) ts.tv_sec + (double) ts.tv_nsec / 1e9;
}

static void probe_nanosleep(long ns)
{
    struct timespec req = { ns / 1000000000L, ns % 1000000000L };
    double t0, d;
    int rc;

    t0 = now();
    rc = nanosleep(&req, NULL);
    d = now() - t0;
    printf("  请求 %9ld ns (%8.3f us) -> 实际 %10.3f us  超出 %+9.3f us   rc=%d\n",
           ns, (double) ns / 1000.0, d * 1e6, d * 1e6 - (double) ns / 1000.0, rc);
}

static volatile sig_atomic_t got_alarm = 0;

static void on_alarm(int sig)
{
    (void) sig;
    got_alarm = 1;
}

int main(void)
{
    long tck = sysconf(_SC_CLK_TCK);
    struct sigaction sa;
    struct itimerval it;
    struct timespec req, rem;
    double t0, d;
    int rc;

    printf("== 0. 参照刻度 ==\n");
    printf("sysconf(_SC_CLK_TCK) = %ld  ->  1 个 jiffy = %.1f ms\n",
           tck, 1000.0 / (double) tck);
    printf("（下面请求 1 us 只有 1 个 jiffy 的 %.4f%%）\n\n",
           100.0 * 0.001 / (1000.0 / (double) tck));

    printf("== 1. nanosleep 的亚 jiffy 能力 ==\n");
    probe_nanosleep(1000L);            /* 1 us   */
    probe_nanosleep(10000L);           /* 10 us  */
    probe_nanosleep(100000L);          /* 100 us */
    probe_nanosleep(1000000L);         /* 1 ms   */
    probe_nanosleep(10000000L);        /* 10 ms  = 1 个 jiffy */
    probe_nanosleep(100000000L);       /* 100 ms */
    printf("  → 1 us 也叫得醒，说明走的不是 jiffies；但 1 us 的实测普遍在\n");
    printf("    几十 us 量级 —— 那部分是与调度器往返的固定开销，不是精度问题。\n\n");

    printf("== 2. sleep(1) 的误差 ==\n");
    t0 = now();
    rc = sleep(1);
    d = now() - t0;
    printf("  sleep(1) 实际 %.4f s，误差 %+.4f s，返回值 rc=%d（未被打断应为 0）\n",
           d, d - 1.0, rc);
    printf("  → sleep 的参数是秒，返回的是「剩余未睡完的秒数」，被打断时 != 0。\n\n");

    printf("== 3. 被信号打断：返回 EINTR 并给出剩余量 ==\n");
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = on_alarm;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                   /* 关键：不设 SA_RESTART，才看得到 EINTR */
    if (sigaction(SIGALRM, &sa, NULL) != 0) {
        printf("  sigaction 失败: %s\n", strerror(errno));
        return 1;
    }

    it.it_interval.tv_sec = 0;
    it.it_interval.tv_usec = 0;
    it.it_value.tv_sec = 0;
    it.it_value.tv_usec = 50000;       /* 50 ms 后发一次 SIGALRM */
    setitimer(ITIMER_REAL, &it, NULL);

    req.tv_sec = 0;
    req.tv_nsec = 500 * 1000 * 1000;   /* 想睡 500 ms */
    rem.tv_sec = rem.tv_nsec = 0;

    errno = 0;
    t0 = now();
    rc = nanosleep(&req, &rem);
    d = now() - t0;
    printf("  nanosleep(500 ms) -> rc=%d  errno=%d (%s)\n", rc, errno, strerror(errno));
    printf("    实际睡了   %.1f ms\n", d * 1000);
    printf("    remaining   %.1f ms   <- 这就是「还差多少没睡」\n",
           (double) rem.tv_sec * 1000 + (double) rem.tv_nsec / 1e6);
    printf("    信号到了吗? %s\n", got_alarm ? "到了" : "没到");
    printf("\n  正确补睡写法（用 remaining 原地重启，而不是重新睡 500 ms）：\n");
    printf("      while (nanosleep(&req, &req) == -1 && errno == EINTR)\n");
    printf("          ;   /* 用返回的剩余量覆盖 req */\n");

    printf("\n== 4. 现场演示「原地重启」 ==\n");
    it.it_value.tv_usec = 30000;       /* 30 ms */
    setitimer(ITIMER_REAL, &it, NULL);
    got_alarm = 0;
    req.tv_sec = 0;
    req.tv_nsec = 200 * 1000 * 1000;   /* 目标：睡满 200 ms */
    t0 = now();
    while (nanosleep(&req, &req) == -1 && errno == EINTR)
        ;                              /* 被 SIGALRM 打断就带着剩余量再来 */
    d = now() - t0;
    printf("  目标 200 ms，实际 %.3f ms，期间被打断 %s\n",
           d * 1000, got_alarm ? "过（已自动补睡）" : "没被打断");
    printf("  → 补睡的正确终点是「累计睡满」，不是「睡过一次就完事」。\n");
    return 0;
}
```

编译 + 运行：

```bash
gcc -O0 -Wall -Wextra -o ex10_3_sleep_precision ex10_3_sleep_precision.c
./ex10_3_sleep_precision
```

实测（CE，gcc 13.3.0）：

```text
== 0. 参照刻度 ==
sysconf(_SC_CLK_TCK) = 100  ->  1 个 jiffy = 10.0 ms
（下面请求 1 us 只有 1 个 jiffy 的 0.0100%）

== 1. nanosleep 的亚 jiffy 能力 ==
  请求      1000 ns (   1.000 us) -> 实际     63.360 us  超出   +62.360 us   rc=0
  请求     10000 ns (  10.000 us) -> 实际     66.643 us  超出   +56.643 us   rc=0
  请求    100000 ns ( 100.000 us) -> 实际    156.888 us  超出   +56.888 us   rc=0
  请求   1000000 ns (1000.000 us) -> 实际   1056.793 us  超出   +56.793 us   rc=0
  请求  10000000 ns (10000.000 us) -> 实际  10060.130 us  超出   +60.130 us   rc=0
  请求 100000000 ns (100000.000 us) -> 实际 100064.804 us  超出   +64.804 us   rc=0
```

### 结论 1：`nanosleep` 不受 jiffy 限制（[10.6](10.6-the-software-clock-jiffies.md) 的现场验证）

请求 **1 µs** 也**真的能醒来**（`rc=0`，实际 63.360 µs）。如果 `nanosleep` 是 jiffies 定时器，1 µs 会被圆整到 **10 ms**——实测只有 63 µs，**差了 158 倍**。这直接证明了 `nanosleep` 走 **hrtimer**。

但「能睡着」≠「睡得准」。把「超出量」那一列拿出来看：

| 请求 | 超出量 | 相对误差 |
|------|--------|---------|
| 1 µs | +62.360 µs | 6236% |
| 10 µs | +56.643 µs | 566% |
| 100 µs | +56.888 µs | 57% |
| 1000 µs | +56.793 µs | 5.7% |
| 10000 µs | +60.130 µs | 0.6% |
| 100000 µs | +64.804 µs | 0.065% |

⭐ **超出量几乎是常数（56 – 65 µs）**。这非常关键：

| 观察 | 含义 |
|------|------|
| 超出量不随请求时长变化（恒 ≈ 60 µs） | 它是**固定开销**（进入/退出调度器 + hrtimer 中断处理 + 上下文切换），**不是分辨率问题** |
| 相对误差只在短请求时才大 | 所以「1 µs 睡得不准」的原因是「开销比请求时长还大」，而不是「时钟太粗」 |
| 请求越长，绝对误差的**占比**越小 | 工程上：请求 < 100 µs 的睡眠基本没有意义，误差 > 50% |

> **HFT 推论**：**任何小于 100 µs 的睡眠都不该用 `sleep`/`nanosleep`**。要在这个量级做等待，只能忙等（`rdtsc` 自旋）或用无锁队列自旋——因为那 60 µs 的固定开销本身就是延迟。

### 结论 2：`sleep(1)` 与返回值语义

```text
== 2. sleep(1) 的误差 ==
  sleep(1) 实际 1.0001 s，误差 +0.0001 s，返回值 rc=0（未被打断应为 0）
```

| 项 | 说明 |
|----|------|
| 精度 | `sleep(1)` 实测误差只有 **+0.1 ms**，比 `nanosleep` 的相对误差好得多（因为请求时长足够长，60 µs 开销可忽略） |
| 返回值 | **未睡完的剩余秒数**。正常睡完返回 `0`；被信号打断返回**剩余整数秒** |
| 与 `nanosleep` 的区别 | `sleep` 只能整秒，而且**返回值的粒度是秒**；要看剩余量必须用 `nanosleep` 的第二个参数 |

### 结论 3：`EINTR` 与「原地重启」

```text
== 3. 被信号打断：返回 EINTR 并给出剩余量 ==
  nanosleep(500 ms) -> rc=-1  errno=4 (Interrupted system call)
    实际睡了   50.0 ms
    remaining   450.0 ms   <- 这就是「还差多少没睡」
```

`nanosleep` 被打断时：

| 输出 | 含义 |
|------|------|
| `rc=-1` / `errno=4 (EINTR)` | 被信号中断 |
| `rem = 450.0 ms` | **还剩多少没睡**（请求 500 ms，已睡 50 ms） |

**正确的补睡写法**（把剩余量作为下一次的输入）：

```c
while (nanosleep(&req, &req) == -1 && errno == EINTR)
    ;   /* 用返回的剩余量覆盖 req */
```

`&req` 同时作为输入和输出——内核把剩余量写回 `req`，下一轮就从剩余量继续。

**为什么不能重睡 500 ms**：

| 写法 | 结果 |
|------|------|
| ❌ `nanosleep(&req500, NULL)` 重来一遍 | 总睡眠 = 已睡的 + 500 ms > 目标，**迟到** |
| ✅ `while (nanosleep(&req, &req) == -1 && errno == EINTR)` | 累计睡满就退出，**准时** |

实测验证：

```text
== 4. 现场演示「原地重启」 ==
  目标 200 ms，实际 200.117 ms，期间被打断 过（已自动补睡）
```

目标 200 ms，实际 200.117 ms，中间被 `SIGALRM` 打断过一次——**误差只有 117 µs**。如果用「掐头重睡」，结果会是 230 ms 以上。

还有一个细节值得注意（源码 `:90`）：

```c
    sa.sa_flags = 0;                   /* 关键：不设 SA_RESTART，才看得到 EINTR */
```

**`SA_RESTART` 会让被中断的系统调用自动重启**，那样就看不到 `EINTR` 了。实验「`EINTR` 怎么处理」时必须显式不设 `SA_RESTART`；反过来，生产代码里如果**不想**处理 `EINTR`，给 `sigaction` 加 `SA_RESTART` 是更省事的选择（但会改变语义，要清楚自己在做什么）。

## 练习 4（自编）：写一个「只用 `CLOCK_MONOTONIC` 的带超时循环」

### 题目

实现一个循环，最多跑 `timeout` 秒就退出。**要求不能用 `alarm()` / `setitimer()` / `SIGALRM`**，也不能用 `time()`。并说明为什么不能用 `CLOCK_REALTIME`。

<details>
<summary>参考答案</summary>

```c
#include <errno.h>
#include <stdio.h>
#include <time.h>

/* 返回 0 = 正常结束；-1 = 超时 */
int run_with_timeout(double timeout_sec)
{
    struct timespec start, now;
    long long limit_ns = (long long) (timeout_sec * 1e9);
    long long elapsed_ns;

    if (clock_gettime(CLOCK_MONOTONIC, &start) != 0)
        return -1;

    for (;;) {
        /* ... 这里做真正的工作 ... */

        if (clock_gettime(CLOCK_MONOTONIC, &now) != 0)
            return -1;
        elapsed_ns = (long long) (now.tv_sec - start.tv_sec) * 1000000000LL
                   + (long long) (now.tv_nsec - start.tv_nsec);
        if (elapsed_ns >= limit_ns)
            return -1;                      /* 超时 */
    }
    return 0;
}

int main(void)
{
    printf("timeout 300ms -> %s\n",
           run_with_timeout(0.300) ? "超时" : "正常结束");
    return 0;
}
```

**为什么必须是 `CLOCK_MONOTONIC`：**

| 用 `CLOCK_REALTIME` 的后果 | 说明 |
|--------------------------|------|
| NTP 往回 slew 一下 → 循环**多跑**一会儿 | 每秒钟 slewing 几十 ns 到几百 ns，长时间运行会累积 |
| 有人 `clock_settime()` 往回调 1 小时 → 循环**永远不超时**（或立刻超时） | 这是最危险的：`elapsed_ns` 可能变成负数 |
| 往回调 → `elapsed_ns` 为负 | 表达式是 `long long` 有符号，负数会让判断永远不成立 |

**为什么不用 `alarm()`/`setitimer()`：**

| 问题 | 说明 |
|------|------|
| 全局性 | `alarm()` 是**进程级唯一的**，别的库（如 `gethostbyname` 的历史实现）也在用，会互相覆盖 |
| 信号处理复杂 | 需要 `sigaction` + `sig_atomic_t` + `EINTR` 处理，而且信号处理器里能干的事非常少 |
| 多线程无效 | 信号只会投递到**某一个**线程，不一定是你要打断的那个 |

**三个实现细节：**

1. **`start` 要取一次、`now` 每次重取**——不要每次算「从现在起还剩多少」（那样会漂移）。
2. **时间差用 `long long` 纳秒**——`tv_nsec` 相减可能为负，必须先转成「总纳秒」再相减。写成 `(now.tv_nsec - start.tv_nsec)` 直接用会得到错误结果。
3. **超时判断要 `>=` 而不是 `==`**——`clock_gettime` 不会正好落在边界上。

**生产版本还要加的两件事：**

| 补充 | 原因 |
|------|------|
| 计算「还能睡多久」并 `nanosleep` | 纯自旋会 100% 占 CPU；但如果这是 HFT 热路径，**故意自旋**反而是对的 |
| 用 `CLOCK_MONOTONIC_COARSE` | 如果循环跑得极频繁，用 COARSE 可以省 4 倍开销（[10.6](10.6-the-software-clock-jiffies.md) 实测 4.9 ns vs 18.9 ns），代价是 1 ms 粒度 |

</details>

## 练习 5（自编）：设计一个 `CLOCK_REALTIME` 跳变监控

### 题目

写一个函数，检测 `CLOCK_REALTIME` 是否被 `clock_settime()` **跳过**（而不是被 NTP 平滑校时）。给出判据和一个可运行的实现。

<details>
<summary>参考答案</summary>

**核心思路**：`CLOCK_REALTIME` 和 `CLOCK_MONOTONIC` 都以「每秒 1 秒」前进，所以它们之差的**变化**只可能来自「REALTIME 被改了」。

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define STEP_THRESHOLD_NS  (100 * 1000000LL)   /* 100 ms 以上算跳变 */

static struct timespec base_rt, base_mo;
static long long base_diff_ns;

/* 初始化基线：第一次调用时建立 */
static void clock_jump_init(void)
{
    clock_gettime(CLOCK_REALTIME, &base_rt);
    clock_gettime(CLOCK_MONOTONIC, &base_mo);
    base_diff_ns = (long long) (base_rt.tv_sec - base_mo.tv_sec) * 1000000000LL
                 + (long long) (base_rt.tv_nsec - base_mo.tv_nsec);
}

/* 每次调用返回「自从基线以来 REALTIME 被跳变了多少纳秒」 */
static long long clock_jump_check(void)
{
    struct timespec rt, mo;
    long long diff_ns;

    clock_gettime(CLOCK_REALTIME, &rt);
    clock_gettime(CLOCK_MONOTONIC, &mo);
    diff_ns = (long long) (rt.tv_sec - mo.tv_sec) * 1000000000LL
            + (long long) (rt.tv_nsec - mo.tv_nsec);

    return diff_ns - base_diff_ns;
}

int main(void)
{
    long long d;

    clock_jump_init();

    /* 正常情况：两次调用之间差值只会有几百纳秒的抖动 */
    d = clock_jump_check();
    printf("基线差值漂移 = %+lld ns  %s\n", d,
           (llabs(d) < STEP_THRESHOLD_NS) ? "（正常：NTP slew 范围内）"
                                          : "（异常：检测到跳变！）");
    return 0;
}
```

**判据表：**

| `clock_jump_check()` 的返回值 | 结论 | 处理 |
|------------------------------|------|------|
| `0 ~ 几百 ns` | 正常。抖动来自两次 `clock_gettime` 之间的间隔 | 忽略 |
| 缓慢单向增长（每秒几十 ns） | NTP 正在 slewing | 记日志，不要告警 |
| **单次跳变 > 100 ms** | **有人 `clock_settime()` 了** | **告警** |
| 跳变 > 1 s | 严重：可能有人手工 `date -s` 或虚拟机时钟同步 | **告警 + 检查所有 `TIMER_ABSTIME` 定时器** |

**为什么阈值取 100 ms：**

| 校时来源 | 典型做法 | 单次最大步进 |
|---------|---------|-------------|
| NTP slewing（[10.5](10.5-updating-the-system-clock.md)） | 每秒最多约 500 µs | 单次几百 ns |
| NTP stepping | 跳变 | **±128 ms**（ntpd 的经典阈值） |
| `date -s` / `clock_settime` | 任意跳变 | 可能几小时 |

所以 **100 ms 的阈值能把「NTP step」和「人为 step」也区分出来**：128 ms 附近是 NTP step，远大于它就是人为操作。

**三个容易写错的地方：**

1. **要先建立基线再比较**——直接看 `rt - mo` 的绝对值毫无意义（两个起点不同，见 [10.8 §1](10.8-summary.md)）。
2. **时间差必须用 `long long` 纳秒**——`tv_nsec` 相减可能为负。
3. **`clock_gettime` 两次调用之间有时间间隔**——所以正常抖动不是 0，而是「两次调用耗时的差」（十几到几十 ns）。阈值不能设成 0。

**进阶：用 `CLOCK_MONOTONIC_RAW` 替代 `CLOCK_MONOTONIC` 更好。** 因为 `RAW` **完全不受 NTP 影响**，`REALTIME − RAW` 的漂移就**只有** REALTIME 被改这一个来源，判据更干净（但要注意 `RAW` 自身速率可能和真实时间有长期偏差，见 [10.8 §1](10.8-summary.md)）。

</details>

## 练习 6（自编）：「该用哪个时钟」判断题

### 题目

下面六个需求各该用哪个时钟（或哪个 API）？说明理由。

| # | 需求 |
|---|------|
| a | 记录一条订单的接收时间戳，要能和人看到的日期对上 |
| b | 测「从发包到收到响应」的往返延迟 |
| c | 给高频日志打时间戳，每秒 200 万条，1 ms 粒度够用 |
| d | 算一个加密函数消耗了多少处理器时间 |
| e | 测一个**长时间运行**（4 小时）的任务的实际耗时 |
| f | 在笔记本上算「系统已经运行了多久」（包含合盖休眠的时间） |

<details>
<summary>参考答案</summary>

| # | 答案 | 理由 |
|---|------|------|
| a | `CLOCK_REALTIME` | 需要人可读的绝对时刻（能直接格式化成本地/UTC 日期时间） |
| b | `CLOCK_MONOTONIC` | 测间隔。绝不能用 `REALTIME`（会被 NTP/`clock_settime` 动） |
| c | `CLOCK_MONOTONIC_COARSE` | 高频 + 容忍 1 ms 粒度 → 4.9 ns/call，比精确版快 4 倍。测间隔也可用 `MONOTONIC`，但 200 万条/秒下 COARSE 更划算 |
| d | `CLOCK_PROCESS_CPUTIME_ID` | CPU 时间口径；`times()` 的 10 ms 粒度会把小函数抹成 0 |
| e | ⚠️ **`CLOCK_MONOTONIC`**，**不要**用 `CLOCK_MONOTONIC_RAW` | `RAW` 完全不被 NTP 校正，长期（小时级）会和真实时间产生**累积偏差**。测长期耗时必须用被校正的 `MONOTONIC` |
| f | `CLOCK_BOOTTIME` | 唯一会**累加 suspend 时间**的时钟（[10.8 §1](10.8-summary.md) 实测 `BOOTTIME − MONO = +68 ns`，那是没挂起过；挂起过就是几分钟） |

**重点讲解 e —— 这是最容易做错的一道：**

`CLOCK_MONOTONIC_RAW` 听起来「更纯净、不被打扰」，所以很多人第一反应是「测长期耗时应该用它」。**这是错的**：

| 时钟 | NTP 校正 | 用途 |
|------|---------|------|
| `CLOCK_MONOTONIC` | ✅ 被 slewing 校正（速率被微调对齐真实时间） | **测间隔**（尤其是长期） |
| `CLOCK_MONOTONIC_RAW` | ❌ 完全不校正 | 基准测试（排除 NTP 抖动）；**不适合长期** |

原因：`RAW` 直接是硬件时间源的原始换算，硬件振荡器有**频率漂移**（普通晶振误差 20~100 ppm）。不被 NTP 校正意味着：

```
100 ppm × 4 小时 = 1.44 秒的累积误差
```

测一个 4 小时的任务，`RAW` 可能告诉你「跑了 4 小时 1.44 秒」——**误差比你要测的抖动还大**。

**正确分工：**

| 场景 | 用 |
|------|-----|
| 测**微秒到秒级**的间隔，且在乎 NTP 抖动 | `CLOCK_MONOTONIC_RAW`（短窗口，漂移可忽略） |
| 测**秒到小时级**的间隔 | `CLOCK_MONOTONIC` |
| 测**跨天**的耗时 | `CLOCK_BOOTTIME` 或 `CLOCK_MONOTONIC`（都行，看要不要含休眠） |

**f 的补充说明（嵌入式角度）**：

`CLOCK_BOOTTIME` 在**容器里等于 `CLOCK_MONOTONIC`**（因为容器的「挂起」和宿主机的 suspend 是两回事，容器看不到）。要在容器里准确测含休眠的运行时长，必须由宿主机提供。

</details>

## HFT / 嵌入式关联

| 主题 | 结论 |
|------|------|
| **时钟选择** | 延迟/超时 → `CLOCK_MONOTONIC`；时间戳 → `CLOCK_REALTIME`（+ 跳变监控）；CPU 成本 → `CLOCK_PROCESS_CPUTIME_ID` |
| **短睡眠无意义** | < 100 µs 的 `nanosleep` 误差 > 50%（固定开销 ≈ 60 µs）。这个量级只能自旋 |
| **`EINTR` 补睡** | 一律用 `while (nanosleep(&req, &req) == -1 && errno == EINTR);` |
| **时间戳格式** | ISO 8601 带偏移：偏移从 `tm_gmtoff` 取、冒号自己拼（glibc 不认 `%:z`）、亚秒自己拼且注意截断 |
| **`clock_t` 回绕** | 32 位平台 1.36 年就回绕；**永远用 64 位**（`get_jiffies_64` / `CLOCK_BOOTTIME`） |
| **容器陷阱** | 容器里 `CLOCK_BOOTTIME == CLOCK_MONOTONIC`；`CAP_SYS_TIME` 默认没有 |
| **嵌入式陷阱** | 32 位 `time_t` / `clock_t` + 老内核（无 hrtimer）→ 本章一半的「现代结论」都要打回原书的版本 |

## 代码自测

<details>
<summary>1. 为什么 32 位平台上「两次 `times()` 返回值相减」是危险的？</summary>

因为 32 位平台上 `times()` 的**返回值**（开机以来的 tick 数）大约 **1.36 年**就会回绕到 0（练习 1 的答案）。

```
2^32 / 100 = 42949672.96 秒 ≈ 497 天 ≈ 1.36 年
```

如果拿两次返回值相减来算「距上次检查过了多久」，**跨越回绕点时**：

| 情况 | 相减结果 |
|------|---------|
| 未跨回绕 | 正常（正的小数值） |
| 跨了回绕 | **负数**（如 `100 - 4294967290 = -4294967190`） |

负数再被当成 `unsigned` 或塞进 `int`，就会变成几十亿的荒谬值。

**修法**：

| 做法 | 说明 |
|------|------|
| 用 `CLOCK_BOOTTIME` | 64 位 `timespec`，本机约 2920 亿年才回绕 |
| 用 `get_jiffies_64()` | 内核侧的 64 位版本（`kernel/time/jiffies.c:48` 的 `u64 get_jiffies_64()`） |
| 用无符号减法的环绕语义 | `(uint32_t)(now - then)` —— 只要间隔 < 2³²/2 个 tick 就正确（C 的无符号溢出是定义良好的） |

**最常见的错误**是第三种写对了却用 `int` 收结果（有符号溢出是 UB）。

**再提醒一次练习 1 的隐藏考点**：`times()` 的**返回值**和它的**出参**是两个完全不同的东西。返回值是全局 tick，出参才是本进程的 CPU 时间。想测进程时间，不该用返回值做减法。

</details>

<details>
<summary>2. 为什么 ISO 8601 的时区偏移一定要从 `tm_gmtoff` 取，不能硬编码？</summary>

因为硬编码会**在绝大多数时区下产生错误的时间戳**。

demo 实测的对照：

```text
  TZ=UTC                    %-Z=UTC   %-z=+0000
      错误: 2023-11-14 22:13:20 +0800
      正确: 2023-11-14T22:13:20.123456+00:00
  TZ=Asia/Kathmandu         %-Z=+0545 %-z=+0545
      错误: 2023-11-15 03:58:20 +0800
      正确: 2023-11-15T03:58:20.123456+05:45
```

**「错误」那一列把本地时间配上了一个错误的偏移**。时间戳 `2023-11-14 22:13:20 +0800` 解析出来是 UTC `14:13:20`，而真实瞬间是 UTC `22:13:20` —— **差了 8 小时**。

在 **`Asia/Kathmandu`**（+05:45）下更糟：本地时间是 `03:58:20`，却标成 `+0800` → 解析出的 UTC 是前一天 `19:58:20`，**差了 9 小时 45 分钟**。

**三个具体理由：**

| 理由 | 说明 |
|------|------|
| 时区是**运行环境**决定的 | 同一份二进制可能在 `TZ=UTC` 的服务器和 `TZ=Asia/Shanghai` 的容器里都跑 |
| **DST 会让偏移在同一台机器上变化** | `America/New_York` 是 `-0500`（冬）/ `-0400`（夏），半刻钟时区还有 `+05:30` / `+05:45` / `+10:30` |
| **偏移不是整小时** | 实测 `tm_gmtoff = 20700 s` 对应 `+05:45`，任何「除以 3600」的算法都会错 |

**正确做法**（任意一个）：

| 方式 | 代码 |
|------|------|
| 用 `%z` | `strftime(buf, n, "%Y-%m-%dT%H:%M:%S%z", &tm)` → `+0800`（无冒号，可接受） |
| 从 `tm_gmtoff` 自己拼 | `snprintf(..., "%c%02ld:%02ld", off<0?'-':'+', labs(off)/3600, labs(off%3600)/60)` |
| 存 UTC + 单独存时区名 | 数据库里存 UTC，另存 `tz_name`；展示时再换算（**最推荐**） |

**注意 `%:z` 是陷阱**：glibc 2.39 **不支持**（实测原样输出 `%:z`），GNU `date` 支持。别把 `date` 的用法搬到 C 里。

</details>

<details>
<summary>3. 一个 4 小时的任务，该用 `CLOCK_MONOTONIC` 还是 `CLOCK_MONOTONIC_RAW` 测耗时？</summary>

**用 `CLOCK_MONOTONIC`。**

`CLOCK_MONOTONIC_RAW` 听起来更「纯净」（不被 NTP 动），但这个纯净恰恰是它在**长期测量**上的缺陷：

| | `CLOCK_MONOTONIC` | `CLOCK_MONOTONIC_RAW` |
|---|---|---|
| 是否被 NTP 校正 | ✅ slewing 校正（速率对齐真实时间） | ❌ 完全不校正 |
| 长期准确性 | **好**（被持续拉回真实时间） | **差**（受硬件晶振漂移影响） |
| 短期稳定性 | 略差（NTP 会微调速率） | **好** |
| 适合 | 测间隔（尤其长期） | 基准测试（排除 NTP 抖动） |

**定量估算**：普通晶振的频率误差在 **20–100 ppm** 量级。

```
100 ppm × 4 小时 = 100e-6 × 14400 s = 1.44 秒
```

也就是说，用 `RAW` 测 4 小时的任务，**结果可能偏差 1.44 秒**——这个偏差远大于大多数被测抖动。

`MONOTONIC` 则因为持续被 NTP 拉向真实时间，长期偏差在**毫秒级以内**。

**实测依据**（[10.8 §1](10.8-summary.md)）：

```text
  RAW - MONO         = -32586189 ns    ← NTP 累计 slew 掉的量
```

本机的 NTP 已经累计把 `MONOTONIC` 拉慢了 **32.6 ms**。这 32.6 ms 正是「NTP 在修正硬件漂移」的证据——`RAW` 没有这个修正。

**通用规则：**

| 测量窗口 | 用 |
|---------|-----|
| < 1 秒 | `MONOTONIC_RAW`（排除 NTP 抖动，漂移可忽略） |
| 1 秒 – 小时 | `MONOTONIC`（两者都行，`MONOTONIC` 更安全） |
| > 小时 | **`MONOTONIC`**（`RAW` 会累积漂移） |

</details>
