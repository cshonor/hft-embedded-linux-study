## 本节讲什么

前面五节讲的全是「用户态怎么拿时间」。本节往下钻一层，回答一个问题：

> **内核手上的时间，粒度到底是多少？**

原书 2010 年给的答案是「**软件时钟的分辨率 = 1/HZ**」。这句话在当年是对的，**在今天只对一半**——本节的 demo 把这个「一半」现场量出来。

| 术语 | 是什么 | 谁用它 |
|------|--------|--------|
| **HZ** | 内核**时钟中断的频率**（次/秒），编译期由 `CONFIG_HZ` 定 | 内核 |
| **jiffy** | 一个时钟滴答的时长 = `1/HZ` 秒 | 内核 |
| **jiffies** | 全局计数器 `unsigned long volatile jiffies`，每来一次时钟中断 `+1` | 内核 |
| **USER_HZ** | **写死的 100**，只服务于「用户态接口」 | 用户态接口（`times()`） |
| **CLOCKS_PER_SEC** | `clock(3)` 的单位 = `1000000` | `clock(3)` |
| **hrtimer** | 高分辨率定时器，不依赖 jiffies，直接走硬件时钟源 | 现代内核 |

> 这一节最值钱的一句话先放这儿：**`sysconf(_SC_CLK_TCK)` 给的 `100` 不是 `CONFIG_HZ`**。它是内核写死的 `USER_HZ`。本容器的真实 `CONFIG_HZ` 是 **1000**（第 4 节会用 `clock_getres()` 反推出来）。

## 0. 三个「每秒几个 tick」的常数：先把名字分清

源码：[../code/c10_6_clockres.c](../code/c10_6_clockres.c)

```c
/* TLPI 第 10 章 §10.6 The Software Clock (Jiffies)  —— 本 demo 是本章最该看的一个
 * clock_getres 到底报多少？原书说「1/HZ」，现代内核还这样吗？
 *
 * 编译: gcc -O0 -Wall -Wextra -o c10_6_clockres c10_6_clockres.c
 * 运行: ./c10_6_clockres                      (无需参数、无需权限；跑一会儿)
 *
 * ⭐ 结论先给：原书（2010 年，2.6 内核）说 CLOCK_REALTIME / CLOCK_MONOTONIC 的
 *    分辨率是 1/HZ（HZ=250 时 4 ms）。**在启用了高分辨率定时器（hrtimer）的
 *    现代内核上，这两个时钟报的是 1 ns**；只有 *_COARSE 那两个才还是 1/HZ。
 *    本 demo 把这两件事都现场量出来。
 */
#define _GNU_SOURCE
#include <errno.h>
#include <limits.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

static void show_clock_getres(clockid_t id, const char *name, long tck)
{
    struct timespec res;
    long ns;

    errno = 0;
    if (clock_getres(id, &res) != 0) {
        printf("  %-24s clock_getres 失败: %s\n", name, strerror(errno));
        return;
    }
    ns = (long) res.tv_sec * 1000000000L + res.tv_nsec;
    printf("  %-24s res = %ld.%09ld s = %9ld ns  %s\n",
           name, (long) res.tv_sec, res.tv_nsec, ns,
           (ns == 1000000000L / tck) ? "<-- 正好 1/HZ（jiffy 粒度）"
                                     : (ns == 1 ? "<-- 1 ns（hrtimer）" : ""));
}

/* 连续两次读同一个时钟，统计「有没有前进」以及「最小正增量是多少 ns」。
   COARSE 时钟在一个 jiffy 内根本不动 → 会出现大量 0 增量。 */
static void probe_granularity(clockid_t id, const char *name, long iters)
{
    struct timespec a, b;
    long best = -1, changed = 0;

    for (long i = 0; i < iters; i++) {
        clock_gettime(id, &a);
        clock_gettime(id, &b);
        long d = (long) (b.tv_sec - a.tv_sec) * 1000000000L
               + (long) (b.tv_nsec - a.tv_nsec);
        if (d != 0) {
            changed++;
            if (best < 0 || d < best)
                best = d;
        }
    }
    printf("  %-24s %ld 次连续读里 %8ld 次有前进   最小正增量 = %ld ns\n",
           name, iters, changed, best);
}

int main(void)
{
    long tck = sysconf(_SC_CLK_TCK);

    printf("== 0. 三个很容易混的「每秒几个 tick」 ==\n");
    printf("sysconf(_SC_CLK_TCK) = %ld        <- USER_HZ：内核写死的 100，\n", tck);
    printf("                                     **不是** CONFIG_HZ！第 4 段会现场撞上这个坑\n");
    printf("CLOCKS_PER_SEC       = %-8ld <- clock(3) 的单位，又是另一个数\n",
           (long) CLOCKS_PER_SEC);
    printf("CLOCK_{REALTIME,MONOTONIC}_COARSE  <- 真正的 1/CONFIG_HZ，第 1 段直接量\n");
    printf("\n");

    printf("== 1. clock_getres(): 每个时钟自己报的分辨率 ==\n");
    show_clock_getres(CLOCK_REALTIME, "CLOCK_REALTIME", tck);
    show_clock_getres(CLOCK_MONOTONIC, "CLOCK_MONOTONIC", tck);
    show_clock_getres(CLOCK_MONOTONIC_RAW, "CLOCK_MONOTONIC_RAW", tck);
    show_clock_getres(CLOCK_REALTIME_COARSE, "CLOCK_REALTIME_COARSE", tck);
    show_clock_getres(CLOCK_MONOTONIC_COARSE, "CLOCK_MONOTONIC_COARSE", tck);
    show_clock_getres(CLOCK_BOOTTIME, "CLOCK_BOOTTIME", tck);
    show_clock_getres(CLOCK_PROCESS_CPUTIME_ID, "CLOCK_PROCESS_CPUTIME_ID", tck);
    show_clock_getres(CLOCK_THREAD_CPUTIME_ID, "CLOCK_THREAD_CPUTIME_ID", tck);
    printf("\n");

    printf("== 2. 实际能分辨多少：连续两次读的最小正增量 ==\n");
    probe_granularity(CLOCK_MONOTONIC, "CLOCK_MONOTONIC", 2000000);
    probe_granularity(CLOCK_MONOTONIC_RAW, "CLOCK_MONOTONIC_RAW", 2000000);
    probe_granularity(CLOCK_REALTIME, "CLOCK_REALTIME", 2000000);
    probe_granularity(CLOCK_MONOTONIC_COARSE, "CLOCK_MONOTONIC_COARSE", 2000000);
    probe_granularity(CLOCK_REALTIME_COARSE, "CLOCK_REALTIME_COARSE", 2000000);
    printf("\n");

    printf("== 3. 把时钟值本身摊开看 ==\n");
    {
        struct timespec ts;

        clock_gettime(CLOCK_REALTIME, &ts);
        printf("  REALTIME  = %ld.%09ld\n", (long) ts.tv_sec, (long) ts.tv_nsec);
        clock_gettime(CLOCK_MONOTONIC, &ts);
        printf("  MONOTONIC = %ld.%09ld   <- 起点未定义，通常是开机时刻\n",
               (long) ts.tv_sec, (long) ts.tv_nsec);
        clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
        printf("  RAW       = %ld.%09ld\n", (long) ts.tv_sec, (long) ts.tv_nsec);
        clock_gettime(CLOCK_BOOTTIME, &ts);
        printf("  BOOTTIME  = %ld.%09ld\n", (long) ts.tv_sec, (long) ts.tv_nsec);
        clock_gettime(CLOCK_MONOTONIC_COARSE, &ts);
        /* ⚠️ 别以为 COARSE 的值是 jiffy 的整数倍 —— 实测看着不像。它只是
           「一个 jiffy 之内不变」（见第 2 段的最小正增量 ≈ 1 ms），
           具体取值不对齐任何边界。 */
        printf("  COARSE    = %ld.%09ld   <- 一个 jiffy 内不变，但取值不对齐边界\n",
               (long) ts.tv_sec, (long) ts.tv_nsec);
    }
    printf("\n");

    printf("== 4. 结论：原书的「1/HZ」在今天要拆成两个数 ==\n");
    {
        struct timespec res;
        long coarse_ns = 0, from_tck = 1000000000L / tck;

        if (clock_getres(CLOCK_MONOTONIC_COARSE, &res) == 0)
            coarse_ns = (long) res.tv_sec * 1000000000L + res.tv_nsec;

        printf("  原书 §10.6（2010 年，2.6 内核）的表述是「分辨率 = 1/HZ」。本机实测：\n");
        printf("    CLOCK_REALTIME / MONOTONIC / RAW / BOOTTIME / *_CPUTIME_ID\n");
        printf("        -> 1 ns。它们走 hrtimer，内核把时间源直接换算到纳秒，HZ 管不着。\n");
        printf("    CLOCK_{REALTIME,MONOTONIC}_COARSE\n");
        printf("        -> %ld ns。这两个仍然被 tick 限住。\n\n", coarse_ns);

        printf("  ⚠️ 但**不能**用 sysconf(_SC_CLK_TCK) 去推它：\n");
        printf("     _SC_CLK_TCK = %ld -> 推算 %ld ns，实测 %ld ns，差了 %ld 倍。\n",
               tck, from_tck, coarse_ns, coarse_ns ? from_tck / coarse_ns : 0);
        printf("     原因是 _SC_CLK_TCK 给的**不是 CONFIG_HZ**，而是写死的 USER_HZ=100：\n");
        printf("       内核把 AT_CLKTCK 塞进 auxv 时写的是 CLOCKS_PER_SEC，\n");
        printf("       CLOCKS_PER_SEC 又等于 USER_HZ（include/asm-generic/param.h:10）。\n");
        printf("       COARSE 的粒度才是真 1/CONFIG_HZ —— 本容器 CONFIG_HZ = %ld。\n\n",
               coarse_ns ? 1000000000L / coarse_ns : 0);

        printf("  所以「软件时钟粒度限制一切」只对**非 hrtimer 路径**成立：\n");
        printf("    定时器接口（nanosleep / timer_settime）走 hrtimer，可以远小于 1 jiffy\n");
        printf("    （见 ex10_3：请求 1 us 的 nanosleep 确实能醒来）。\n");
    }
    return 0;
}
```

```bash

./c10_6_clockres
```

实测（CE，gcc 13.3.0）：

```text

sysconf(_SC_CLK_TCK) = 100
CLOCKS_PER_SEC       = 1000000
CLOCK_{REALTIME,MONOTONIC}_COARSE
```

三个数，三个来源，**谁都不等于 `CONFIG_HZ`**：

| 名字 | 实测值 | 定义位置（v6.6） | 服务于 |
|------|--------|-----------------|--------|
| `HZ`（= `CONFIG_HZ`） | **1000**（本容器，第 4 节反推） | `include/asm-generic/param.h:8` `# define HZ  CONFIG_HZ` | 内核时钟中断、jiffies |
| `USER_HZ` | `100` | `include/asm-generic/param.h:9` `# define USER_HZ  100` | `times(2)`、`getrusage(2)` 等**老接口** |
| `CLOCKS_PER_SEC` | `1000000` | `include/asm-generic/param.h:10` `# define CLOCKS_PER_SEC  (USER_HZ)` | `clock(3)` |

**注意 `CLOCKS_PER_SEC` 的定义**：在**内核**头文件里它等于 `USER_HZ`（=100），但在**用户态 glibc** 里它是 `1000000`。同名不同值，这是 C 里少见的「语义分叉」。demo 打在用户态，所以看到 `1000000`——见 [10.7](10.7-process-time.md) 会把这件事彻底讲清。

## 1. `clock_getres()`：每个时钟自己报的分辨率

```text
== 1. clock_getres(): 每个时钟自己报的分辨率 ==
  CLOCK_REALTIME           res = 0.000000001 s =         1 ns
  CLOCK_MONOTONIC          res = 0.000000001 s =         1 ns
  CLOCK_MONOTONIC_RAW      res = 0.000000001 s =         1 ns
  CLOCK_REALTIME_COARSE    res = 0.001000000 s =   1000000 ns
  CLOCK_MONOTONIC_COARSE   res = 0.001000000 s =   1000000 ns
  CLOCK_BOOTTIME           res = 0.000000001 s =         1 ns
  CLOCK_PROCESS_CPUTIME_ID res = 0.000000001 s =         1 ns
  CLOCK_THREAD_CPUTIME_ID  res = 0.000000001 s =         1 ns
```

**这张表就是本节的核心结论**：八个时钟分成两档。

| 档位 | 时钟 | 报的分辨率 | 谁来定 |
|------|------|-----------|--------|
| **纳秒档** | `REALTIME` / `MONOTONIC` / `MONOTONIC_RAW` / `BOOTTIME` / `*_CPUTIME_ID` | **1 ns** | `HIGH_RES_NSEC` |
| **jiffy 档** | `REALTIME_COARSE` / `MONOTONIC_COARSE` | **1000000 ns**（= 1 ms） | `TICK_NSEC` = `1/CONFIG_HZ` |

### 源码上这两档是怎么分开的

`clock_getres(2)` 只做一件事：按 `clockid` 查到一张 `k_clock` 表，调表里的 `clock_getres` 回调。

| 步骤 | 位置（v6.6） | 内容 |
|------|-------------|------|
| ① syscall 入口 | `kernel/time/posix-timers.c:1252` | `SYSCALL_DEFINE2(clock_getres, ...)` |
| ② 分派 | `kernel/time/posix-timers.c:1262` | `error = kc->clock_getres(which_clock, &rtn_tp);` |
| ③ `CLOCK_REALTIME` 的回调 | `kernel/time/posix-timers.c:1430` | `.clock_getres = posix_get_hrtimer_res,` |
| ④ `CLOCK_REALTIME_COARSE` 的回调 | `kernel/time/posix-timers.c:1471` | `.clock_getres = posix_get_coarse_res,` |

两个回调体：

```c
/* kernel/time/posix-timers.c:216-221 —— 纳秒档 */
static int posix_get_hrtimer_res(clockid_t which_clock, struct timespec64 *tp)
{
	tp->tv_sec = 0;
	tp->tv_nsec = hrtimer_resolution;
	return 0;
}
```

```c
/* kernel/time/posix-timers.c:187-191 —— jiffy 档 */
static int posix_get_coarse_res(const clockid_t which_clock, struct timespec64 *tp)
{
	*tp = ktime_to_timespec64(KTIME_LOW_RES);
	return 0;
}
```

所以「1 ns 还是 1 ms」完全取决于这两个符号：

| 符号 | 定义位置（v6.6） | 值 |
|------|-----------------|-----|
| `HIGH_RES_NSEC` | `include/linux/hrtimer_defs.h:15` | `1` |
| `LOW_RES_NSEC` | `include/vdso/ktime.h:13` | `TICK_NSEC` |
| `KTIME_LOW_RES` | `include/vdso/ktime.h:14` | `(LOW_RES_NSEC)` |
| `TICK_NSEC` | `include/vdso/jiffies.h:9` | `((NSEC_PER_SEC+HZ/2)/HZ)` |

代进 `HZ = 1000`：`(1000000000 + 500) / 1000 = 1000000` ✔ 与实测的 `1000000 ns` 一致。

### `hrtimer_resolution` 是怎么从 jiffy 档「升级」到纳秒档的

`hrtimer_resolution` 不是一个常量，它是一个**会被运行时改写的全局变量**：

```c
/* kernel/time/hrtimer.c:711 */
unsigned int hrtimer_resolution __read_mostly = LOW_RES_NSEC;
```

开机时它是 `LOW_RES_NSEC`（= 1/HZ）。什么时候变成 1 ns：

```c
/* kernel/time/hrtimer.c:737-747 */
static void hrtimer_switch_to_hres(void)
{
	struct hrtimer_cpu_base *base = this_cpu_ptr(&hrtimer_bases);

	if (tick_init_highres()) {
		pr_warn("Could not switch to high resolution mode on CPU %u\n",
			base->cpu);
		return;
	}
	base->hres_active = 1;
	hrtimer_resolution = HIGH_RES_NSEC;
	...
}
```

**这就解释了原书那句话为什么「只对一半」**：

| 条件 | `hrtimer_resolution` | `clock_getres(CLOCK_REALTIME)` |
|------|---------------------|-------------------------------|
| 内核**没**配 `CONFIG_HIGH_RES_TIMERS` | `LOW_RES_NSEC` = 1/HZ | 1/HZ（原书的答案） |
| 用户传了 `highres=0` 启动参数（`hrtimer.c:722` 的 `__setup("highres=", ...)`） | `LOW_RES_NSEC` | 1/HZ |
| 现代内核 + 时钟源支持 + 切换成功 | `HIGH_RES_NSEC` = 1 | **1 ns**（实测答案） |

> 原书 2010 年写的是 2.6 内核时代、且默认没开高分辨率定时器；今天 `CONFIG_HIGH_RES_TIMERS=y` 是发行版标配，所以 `CLOCK_REALTIME` 报的是 `1 ns`。**结论没变，但前提变了**——这就是「书要对着源码读」的典型例子。

还有一个细节值得知道：`include/linux/hrtimer.h:338` 有 `if (IS_ENABLED(CONFIG_TIME_LOW_RES) && timer->is_rel)`。也就是说内核还留了一个 `CONFIG_TIME_LOW_RES` 开关，**专门把「相对定时器」强行圆整到 1/HZ**（用于极省电场景）。

## 2. 实测粒度：连续两次读，最小正增量是多少

`clock_getres()` 报的是「声明值」。真正能分辨到多少，要看连续两次读之间最小的正差值：

```text
== 2. 实际能分辨多少：连续两次读的最小正增量 ==
  CLOCK_MONOTONIC          2000000 次连续读里  2000000 次有前进   最小正增量 = 17 ns
  CLOCK_MONOTONIC_RAW      2000000 次连续读里  2000000 次有前进   最小正增量 = 17 ns
  CLOCK_REALTIME           2000000 次连续读里  2000000 次有前进   最小正增量 = 17 ns
  CLOCK_MONOTONIC_COARSE   2000000 次连续读里        9 次有前进   最小正增量 = 999979 ns
  CLOCK_REALTIME_COARSE    2000000 次连续读里        4 次有前进   最小正增量 = 999979 ns
```

> ⚠️ **这一组是「单次极值」测量，每次跑都不一样**。同机重跑会得到 `17~20 ns` / `10~12 次` / `9999xx ns` 这类小幅漂移（因为它取的是 200 万次里的**最小值**，直接受当时 CPU 频率、缓存、邻居干扰影响）。表里的数字取自本轮 CE 日志；作为结论用的只有**数量级**，别把具体数值当常量。
>
> 反面对照：下面第 3 节的**单次调用耗时**是 200 万次平均，重复跑几乎不变（2.3 / 2.9 / 19.0 / 18.9 / 4.9 / 10.5 ns），那是稳定的。

三行读数各说明一件事：

| 观察 | 含义 |
|------|------|
| 精确时钟「**2000000 次里 2000000 次**都有前进」 | 每一次读都拿到不同的值——**没有缓存、没有圆整** |
| 精确时钟的最小正增量是 **17 ns** | 声明 `1 ns` 不等于「处处能分辨 1 ns」。17 ns 是**读一次时钟本身的耗时下限**：两次 `clock_gettime()` 之间必然过了十几 ns，所以差值不可能比这更小 |
| COARSE 的「2000000 次里只有 **4~9 次**有前进」 | 一格 jiffy（1 ms）内值是**完全不动**的；2000000 次循环跑完只跨了几个 jiffy |
| COARSE 的最小正增量 **999979 ns** | ≈ 1 ms，**不是整数 1000000** |

> **最后一行是个容易想当然的地方**：COARSE 的值**不对齐 jiffy 边界**。`999979` 而不是 `1000000`，说明每次更新是「在旧值上加 `TICK_NSEC`」，起点本身是任意的。所以**不要**用 `tv_nsec % 1000000 == 0` 去判断一个时间戳是不是 COARSE 来的。

### 内核里 COARSE 是怎么算的

`kernel/time/time.c:600-620` 有一段专门的注释，讲的就是「圆整」的正确做法：

```c
/*
 * The TICK_NSEC - 1 rounds up the value to the next resolution.  Note
 * ...
 * nsec -= nsec % TICK_NSEC; is NOT a correct resolution rounding.
 */
...
	long nsec = value->tv_nsec + TICK_NSEC - 1;
```

`s:620` 的 `+ TICK_NSEC - 1` 是**向上取整**到下一个 tick（`nsec / TICK_NSEC` 的整数上界），而不是向下截断。差别在于：向下截断会让「刚好落在边界上的值」提前一个 tick 可见。

## 3. 读一次时间有多贵（COARSE 到底省在哪）

光有「粒度」还不够，工程上还要知道「代价」。第二个 demo 用 200 万次调用把六条读法量一遍：

源码：[../code/c10_6_coarse_cost.c](../code/c10_6_coarse_cost.c)

```c
/* TLPI 第 10 章 §10.6 The Software Clock (Jiffies)（开销一侧）
 * 「读一次时间」到底多贵：六条读法的单次耗时对照
 *
 * 编译: gcc -O0 -Wall -Wextra -o c10_6_coarse_cost c10_6_coarse_cost.c
 * 运行: ./c10_6_coarse_cost                    (无需参数；跑几秒)
 *
 * ⚠️ 必须 -O0：本 demo 要量的是「函数调用真的发生」的代价，-O2 会把
 *    nop_call() 和好几处读时钟全部内联/消除掉，测出来是 0。
 *
 * 要看的结论：
 *   * time() / gettimeofday() / clock_gettime(REALTIME 或 MONOTONIC) 都走
 *     **vDSO**（用户态直接读内核共享页），所以都在几十 ns 量级，**不陷内核**；
 *   * 但 *_COARSE 比对应的精确版更便宜 —— 它连时间源都不用换算，直接取
 *     上次 jiffy 更新时缓存下来的值；
 *   * nop_call() 是基线（纯循环 + 一次空调用），任何一条读法减去它就得到净开销。
 */
#define _GNU_SOURCE
#include <stdint.h>
#include <stdio.h>
#include <sys/time.h>
#include <time.h>

#define N 2000000L

/* 基线：一个保证不被内联、且不产生任何副作用的空函数 */
static __attribute__((noinline)) void nop_call(void)
{
    __asm__ __volatile__("");
}

/* 把「取两个 MONOTONIC 读数」的开销从各测里扣掉 —— 方法是用同一套
   计时框架包住空循环体，只比总时长。 */

static double per_call_clock_gettime(clockid_t id, long n, volatile long *sink)
{
    struct timespec a, b, tmp;

    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long i = 0; i < n; i++) {
        clock_gettime(id, &tmp);
        *sink += tmp.tv_nsec;
    }
    clock_gettime(CLOCK_MONOTONIC, &b);
    return (double) ((b.tv_sec - a.tv_sec) * 1000000000LL + (b.tv_nsec - a.tv_nsec)) / (double) n;
}

static double per_call_gettimeofday(long n, volatile long *sink)
{
    struct timespec a, b;
    struct timeval tv;

    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long i = 0; i < n; i++) {
        gettimeofday(&tv, NULL);
        *sink += tv.tv_usec;
    }
    clock_gettime(CLOCK_MONOTONIC, &b);
    return (double) ((b.tv_sec - a.tv_sec) * 1000000000LL + (b.tv_nsec - a.tv_nsec)) / (double) n;
}

static double per_call_time(long n, volatile long *sink)
{
    struct timespec a, b;

    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long i = 0; i < n; i++) {
        time_t t = time(NULL);
        *sink += (long) t;
    }
    clock_gettime(CLOCK_MONOTONIC, &b);
    return (double) ((b.tv_sec - a.tv_sec) * 1000000000LL + (b.tv_nsec - a.tv_nsec)) / (double) n;
}

static double per_call_nop(long n, volatile long *sink)
{
    struct timespec a, b;

    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long i = 0; i < n; i++) {
        nop_call();
        *sink += 1;
    }
    clock_gettime(CLOCK_MONOTONIC, &b);
    return (double) ((b.tv_sec - a.tv_sec) * 1000000000LL + (b.tv_nsec - a.tv_nsec)) / (double) n;
}

#if defined(__x86_64__)
static double per_call_rdtsc(long n, volatile long *sink)
{
    struct timespec a, b;

    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long i = 0; i < n; i++) {
        uint32_t lo, hi;
        __asm__ __volatile__("rdtsc" : "=a"(lo), "=d"(hi));
        *sink += (long) ((uint64_t) hi << 32 | lo) & 0xffffL;
    }
    clock_gettime(CLOCK_MONOTONIC, &b);
    return (double) ((b.tv_sec - a.tv_sec) * 1000000000LL + (b.tv_nsec - a.tv_nsec)) / (double) n;
}
#endif

int main(void)
{
    volatile long sink = 0;
    double base, v;

    printf("每组 %ld 次调用，-O0 编译（防止内联/消除）\n\n", N);

    base = per_call_nop(N, &sink);
    printf("  %-34s %8.1f ns/call   <- 基线：纯循环 + 一次空函数调用\n",
           "nop_call()", base);

    v = per_call_time(N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "time(NULL)", v, v - base);

    v = per_call_gettimeofday(N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "gettimeofday()", v, v - base);

    v = per_call_clock_gettime(CLOCK_REALTIME, N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "clock_gettime(REALTIME)", v, v - base);

    v = per_call_clock_gettime(CLOCK_MONOTONIC, N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "clock_gettime(MONOTONIC)", v, v - base);

    v = per_call_clock_gettime(CLOCK_MONOTONIC_RAW, N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "clock_gettime(MONOTONIC_RAW)", v, v - base);

    v = per_call_clock_gettime(CLOCK_REALTIME_COARSE, N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "clock_gettime(REALTIME_COARSE)", v, v - base);

    v = per_call_clock_gettime(CLOCK_MONOTONIC_COARSE, N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "clock_gettime(MONOTONIC_COARSE)", v, v - base);

#if defined(__x86_64__)
    v = per_call_rdtsc(N, &sink);
    printf("  %-34s %8.1f ns/call   净 %+8.1f ns\n", "rdtsc 指令", v, v - base);
#endif

    (void) sink;
    printf("\n三条要点：\n");
    printf("  1) time()/gettimeofday()/clock_gettime() 全是几十 ns 量级 —— 它们走\n");
    printf("     vDSO，是**用户态**读内核共享页，没有 syscall 指令、没有特权级切换；\n");
    printf("  2) COARSE 变体最便宜：它不碰硬件时间源，直接返回上个 jiffy 缓存的值，\n");
    printf("     代价是精度掉到 1/HZ；\n");
    printf("  3) rdtsc 是最便宜的「高分辨率」读法（一条指令），但它的单位是 CPU 周期，\n");
    printf("     要自己用频率换算，且跨核/变频下不一定可比 —— 所以 HFT 里\n");
    printf("     「测延迟用 MONOTONIC，测开销用 rdtsc」是常见分工。\n");
    return 0;
}
```

```bash
./c10_6_coarse_cost
```

实测（CE，gcc 13.3.0）：

```text
每组 2000000 次调用，-O0 编译（防止内联/消除）

  nop_call()                              2.3 ns/call
  time(NULL)                              2.9 ns/call   净     +0.6 ns
  gettimeofday()                         19.0 ns/call   净    +16.7 ns
  clock_gettime(REALTIME)                18.8 ns/call   净    +16.5 ns
  clock_gettime(MONOTONIC)               18.9 ns/call   净    +16.6 ns
  clock_gettime(MONOTONIC_RAW)           19.3 ns/call   净    +17.0 ns
  clock_gettime(REALTIME_COARSE)          4.9 ns/call   净     +2.6 ns
  clock_gettime(MONOTONIC_COARSE)         4.9 ns/call   净     +2.6 ns
  rdtsc 指令                           10.5 ns/call   净     +8.2 ns
```

把这张表读懂，有三个层次：

**① 全是几十 ns 量级 → 因为它们走 vDSO，没有陷入内核。**

| 对比 | 耗时（Ch03 实测，同一台 CE 机器） |
|------|----------------------------------|
| `getppid()`（真 syscall） | **812.9 ns** |
| `gettimeofday()`（vDSO） | **19.0 ns** |
| 比值 | 约 **43 倍** |

如果 `gettimeofday()` 真的走 `syscall` 指令，开销应该和 `getppid()` 同量级（数百 ns）。实测只有 19 ns，**说明它根本没进内核**——`vdso`（`arch/x86/entry/vdso/`）把「读内核共享页 + 换算」的代码映射到了用户态，`clock_gettime` 只是在那里跑了一遍。

**② COARSE 便宜的原因不是「少做事」，而是「不做事」。**

| 读法 | 要做什么 |
|------|---------|
| `clock_gettime(CLOCK_MONOTONIC)` | 读硬件时钟源（TSC）+ 应用 `timekeeper` 的多项式换算（`mult`/`shift`，见 `include/vdso/datapage.h` 的 `struct vdso_data`） |
| `clock_gettime(CLOCK_MONOTONIC_COARSE)` | 直接取**上一次 tick 中断时缓存好的** `xtime_coarse` / `monotonic_coarse`，一次内存读 |

省掉的是「读 TSC + 64 位乘加换算」，所以从 18.9 ns 掉到 4.9 ns（**约 4 倍**）。代价就是粒度变成 1 ms。

**③ `rdtsc` 是「高分辨率里最便宜的」，但它不是时间。**

`rdtsc` 只有一条指令（10.5 ns），单位是 **CPU 周期**，不是纳秒。要用它必须先知道 TSC 频率，而且：

| 坑 | 说明 |
|----|------|
| 变频 | CPU 调频时 TSC 是否恒定，取决于 `constant_tsc` / `nonstop_tsc` CPU 标志 |
| 跨核 | 多路机器上不同 socket 的 TSC 可能不同步，Linux 启动时会做 TSC 同步检查 |
| 精度 | `rdtsc` 不可序列化，要精确得用 `rdtscp`（但会牺牲一点性能） |

所以 HFT 里的常见分工是：**测「两端之间的延迟」用 `CLOCK_MONOTONIC`，测「某个函数的开销」用 `rdtsc`**。

## 4. 原书的「1/HZ」在今天要拆成两个数 —— 以及 `USER_HZ ≠ CONFIG_HZ` 的完整证据链

demo 最后一段主动把这个坑摊开：

```text
== 4. 结论：原书的「1/HZ」在今天要拆成两个数 ==
  原书 §10.6（2010 年，2.6 内核）的表述是「分辨率 = 1/HZ」。本机实测：
    CLOCK_REALTIME / MONOTONIC / RAW / BOOTTIME / *_CPUTIME_ID
        -> 1 ns。它们走 hrtimer，内核把时间源直接换算到纳秒，HZ 管不着。
    CLOCK_{REALTIME,MONOTONIC}_COARSE
        -> 1000000 ns。这两个仍然被 tick 限住。
     _SC_CLK_TCK = 100 -> 推算 10000000 ns，实测 1000000 ns，差了 10 倍。
     原因是 _SC_CLK_TCK 给的**不是 CONFIG_HZ**，而是写死的 USER_HZ=100：
       内核把 AT_CLKTCK 塞进 auxv 时写的是 CLOCKS_PER_SEC，
       CLOCKS_PER_SEC 又等于 USER_HZ（include/asm-generic/param.h:10）。
       COARSE 的粒度才是真 1/CONFIG_HZ —— 本容器 CONFIG_HZ = 1000。
```

### 完整证据链：从 `/proc/self/auxv` 到 `sysconf(_SC_CLK_TCK)`

这是 10.6 最值得记住的一条链。**`_SC_CLK_TCK = 100` 完全是「内核 → 用户态」传过去的**：

| 步骤 | 位置（v6.6 / glibc 2.39） | 内容 |
|------|--------------------------|------|
| ① 内核在 exec 时构造 `auxv` | `fs/binfmt_elf.c:262` | `NEW_AUX_ENT(AT_CLKTCK, CLOCKS_PER_SEC);` |
| ② `CLOCKS_PER_SEC` 是什么 | `include/asm-generic/param.h:10` | `# define CLOCKS_PER_SEC  (USER_HZ)` |
| ③ `USER_HZ` 是什么 | `include/asm-generic/param.h:9` | `# define USER_HZ  100` |
| ④ 动态链接器读走 `AT_CLKTCK` | glibc `sysdeps/unix/sysv/linux/dl-sysdep.c` | 存进 `GLRO(dl_clktck)` |
| ⑤ `sysconf(_SC_CLK_TCK)` 落到哪 | glibc `sysdeps/unix/sysv/linux/getclktck.c:28-32` | `return GLRO(dl_clktck) ?: SYSTEM_CLK_TCK;` |
| ⑥ 拿不到 auxv 时的兜底 | 同上，`:23-25` | `#ifndef SYSTEM_CLK_TCK` → `# define SYSTEM_CLK_TCK  100` |

看第 ⑥ 步——**连 glibc 的兜底常量也是 100**。也就是说 `sysconf(_SC_CLK_TCK)` 在 Linux 上**永远是 100**，无论内核 `CONFIG_HZ` 配成多少。

> 所以那句流行的说法「`sysconf(_SC_CLK_TCK)` 就是 HZ」是**错的**。准确说法是：
> **它是 `USER_HZ`，一个为了「用户态 ABI 稳定」而刻意写死的 100。**
> 真要知道 `CONFIG_HZ`，只能：① 读 `/boot/config-$(uname -r)`；② 量 `CLOCK_MONOTONIC_COARSE` 的分辨率反推（本节第 1 节就是这么干的）；③ 读 `/proc/timer_list`（需要 root）。

### 为什么内核要容忍这种「两个 HZ」

因为**用户态 ABI 不能改**。`/proc/stat` 里的 `cpu` 行、`times(2)`、`getrusage(2)` 全部以 `USER_HZ` 为单位，历史上任何一次改动都会让所有已编译的程序算错。所以内核把这个数字**永久冻结在 100**，内部该怎么算（`CONFIG_HZ` 可以 250/300/1000）就怎么算，只在**出口处**用 `jiffies_to_clock_t()` 换算一次——`kernel/time/time.c:664` 那段 `#if (TICK_NSEC % (NSEC_PER_SEC / USER_HZ)) == 0` 就是在选「整除」还是「除法」两条换算路径。

## 5. `CONFIG_HZ` 有哪些选项

`kernel/Kconfig.hz` 是全局唯一的 HZ 配置入口（v6.6）：

| 配置 | 值 | 文件行 | 说明 |
|------|-----|--------|------|
| （默认） | `HZ_250` | `kernel/Kconfig.hz:8` | `default HZ_250` |
| `CONFIG_HZ_100` | `100` | `:20-21` | `bool "100 HZ"` |
| `CONFIG_HZ_250` | `250` | `:27-28` | `bool "250 HZ"` |
| `CONFIG_HZ_300` | `300` | `:35-36` | `bool "300 HZ"` |
| `CONFIG_HZ_1000` | `1000` | `:43-44` | `bool "1000 HZ"` |

```c
/* kernel/Kconfig.hz:51-56 */
config HZ
	int
	default 100 if HZ_100
	default 250 if HZ_250
	default 300 if HZ_300
	default 1000 if HZ_1000
```

| HZ | jiffy | 代价 / 收益 |
|----|-------|------------|
| 100 | 10 ms | 中断开销最小，吞吐好；定时器粒度粗 |
| 250 | 4 ms | 上游默认，折中 |
| 300 | 3.33 ms | 被 `sched_rt` 的 `sched_rt_period_us=1000000` 整除，实时调度友好的折中 |
| 1000 | 1 ms | 粒度最细，中断开销最大；桌面/低延迟常用 |

**注意 `CONFIG_HZ` 只影响「非 hrtimer 路径」**。这是本节最实用的一条推论：

| 路径 | 受 HZ 限制？ |
|------|-------------|
| `CLOCK_REALTIME` / `MONOTONIC` 的**读数** | ❌ 不受限（hrtimer 换算到 ns） |
| `CLOCK_*_COARSE` 的读数 | ✅ 受限（就是 `TICK_NSEC`） |
| `nanosleep()` / `clock_nanosleep()` / `timer_settime()` | ❌ 不受限（走 hrtimer，见 [ex10_3](10.9-exercise.md)） |
| `/proc/stat` 的 `cpu` 行、`times(2)` | ✅ 受限（而且是 `USER_HZ` 不是 `CONFIG_HZ`） |
| 老 `setitimer(2)` / `alarm(2)` | ✅ 受限（jiffies 定时器） |

## HFT / 嵌入式关联

| 场景 | 结论 |
|------|------|
| **打时间戳** | 一次 `clock_gettime(CLOCK_MONOTONIC)` 约 **19 ns**；若每秒百万条消息、每条打两次，就是 3.8% 的 CPU。此时该换 `CLOCK_MONOTONIC_COARSE`（4.9 ns）或 `rdtsc`（10.5 ns） |
| **COARSE 的正确用法** | 精度要求 ≤ 1 ms 的场景（日志、统计、看门狗心跳）用 COARSE；**绝不**用它算微秒级延迟 |
| **不能靠 `sysconf(_SC_CLK_TCK)` 推 HZ** | 它恒为 100。想知道真实 `CONFIG_HZ` 就读 `/boot/config-$(uname -r)` |
| **调优 HFT 内核** | `CONFIG_HZ=1000` 的实际收益在现代内核上**主要来自调度器 tick**，不再是定时器精度（定时器已归 hrtimer 管）。所以「HFT 必须 HZ=1000」要打个折：更关键的是 `CONFIG_NO_HZ_FULL`（tickless）+ `CONFIG_PREEMPT` / `CONFIG_PREEMPT_RT` |
| **tickless 与 jiffies** | `CONFIG_NO_HZ_IDLE` / `NO_HZ_FULL` 下空闲 CPU 不再每 jiffy 中断，但 `jiffies` 仍会被「按需补齐」（`jiffies` 的更新走 `tick_nohz`），所以 `CLOCK_MONOTONIC` 照样准 |
| **时钟源选择** | `cat /sys/devices/system/clocksource/clocksource0/current_clocksource` → 常见 `tsc` / `hpet` / `acpi_pm`。`acpi_pm` 只有约 2.8 MHz，会显著拉低读数精度 |
| **嵌入式（ARM）** | aarch64 的 `CNTVCT_EL0`（Generic Timer）等价于 x86 的 TSC；`CNTFRQ_EL0` 给出频率。注意很多板子的 `CNTFRQ` 是**写死的假值**（如 25 MHz），要靠 `arch_timer` 从 DT 的 `clock-frequency` 纠正 |
| **没有 RTC 的板子** | 上电后 `jiffies` 从 0 起算，`CLOCK_MONOTONIC` 有意义、`CLOCK_REALTIME` 是垃圾。必须先 `clock_settime`（见 [10.5](10.5-updating-the-system-clock.md)） |
| **减少时间开销** | Linux 5.10+ 的 `vdso` 支持 `CLOCK_MONOTONIC` 无锁读（`vdso_data->seq` 序列计数），但如果内核在频繁 `adjtime`，序列会一直变，读者会反复重试——**校时频率过高会拖慢打时间戳的热路径** |

## 代码自测

<details>
<summary>1. 为什么 `sysconf(_SC_CLK_TCK)` 恒为 100，而不是 `CONFIG_HZ`？</summary>

因为它是**用户态 ABI 的一部分**，不是内核参数。

内核在 `exec` 时把 `AT_CLKTCK` 放进 `auxv`（`fs/binfmt_elf.c:262`）：

```c
NEW_AUX_ENT(AT_CLKTCK, CLOCKS_PER_SEC);
```

而 `CLOCKS_PER_SEC` 在内核头文件里等于 `USER_HZ`（`include/asm-generic/param.h:9-10`）：

```c
# define USER_HZ	100		/* some user interfaces are */
# define CLOCKS_PER_SEC	(USER_HZ)       /* in "ticks" like times() */
```

glibc 侧读到这个值，`sysconf(_SC_CLK_TCK)` 直接返回它（`sysdeps/unix/sysv/linux/getclktck.c:28-32`）：

```c
int
__getclktck (void)
{
  return GLRO(dl_clktck) ?: SYSTEM_CLK_TCK;
}
```

而 `SYSTEM_CLK_TCK` 的兜底也是 `100`。

**原因**：`times(2)`、`getrusage(2)`、`/proc/stat` 的 `cpu` 行全部以 `USER_HZ` 为单位。一旦改这个数字，**所有已编译的二进制都会算错**。所以内核把它永久冻结在 100，只在输出时用 `jiffies_to_clock_t()` 换算。

| 想知道什么 | 怎么拿 |
|-----------|--------|
| `USER_HZ`（= `sysconf(_SC_CLK_TCK)`） | `sysconf(_SC_CLK_TCK)`，恒 100 |
| 真实 `CONFIG_HZ` | `grep '^CONFIG_HZ=' /boot/config-$(uname -r)` |
| 真实 `CONFIG_HZ`（无 config 文件时） | 量 `clock_getres(CLOCK_MONOTONIC_COARSE)`，`1/HZ` = 那个纳秒值 |

本容器实测：`clock_getres(CLOCK_MONOTONIC_COARSE) = 1000000 ns` → `CONFIG_HZ = 1000`。

</details>

<details>
<summary>2. `clock_getres(CLOCK_REALTIME)` 报 1 ns，那这个时钟真的精确到 1 ns 吗？</summary>

**不是。** 报的 1 ns 是「**接口分辨率**」，不是「实际可分辨量」。

三组实测数字对照：

| 指标 | 实测值 | 说明 |
|------|--------|------|
| `clock_getres(CLOCK_REALTIME)` | `1 ns` | 内核声明的接口精度（`HIGH_RES_NSEC`） |
| 连续两次读的最小正增量 | **17 ns** | 这是**读一次的成本**造成的下限，不是时钟的极限 |
| `clock_gettime()` 单次耗时 | `18.8 ns` | 两次调用之间必然过了 ≈ 17 ns |

也就是说：**时钟本身的分辨率确实在 1 ns 量级，但你在用户态「通过 `clock_gettime()` 去用」它的下限是十几纳秒**。

要真正逼近 1 ns，只能：

1. 用 `rdtsc`（10.5 ns，单位是周期而不是时间）；
2. 用 `clock_gettime` 的批处理接口 `clock_gettime64` + vDSO 的批量读（仍受同一成本限制）；
3. 让硬件打时间戳（网卡 PHC / PTP），时间戳由硬件在收包瞬间生成，**完全不经过用户态调用**。

> 这就是为什么 `clock_getres` 只能当「数量级参考」用，不能当 SLA 承诺。

</details>

<details>
<summary>3. 为什么 `CLOCK_MONOTONIC_COARSE` 比 `CLOCK_MONOTONIC` 快 4 倍？</summary>

因为 COARSE **不做换算**。

| 读法 | 内核/用户态要做的动作 |
|------|---------------------|
| `CLOCK_MONOTONIC` | ① 读硬件时钟源（TSC）；② 用 `timekeeper` 的 `mult`/`shift` 做 64 位乘加，把周期换成纳秒；③ 用 seqcount 保证读到的 `vdso_data` 一致 |
| `CLOCK_MONOTONIC_COARSE` | 直接取上一次 tick 中断时**缓存好**的 `monotonic_coarse` 字段——一次内存读 |

源码上是两个不同的回调：`posix_get_hrtimer_res`（纳秒档）vs `posix_get_coarse_res`（jiffy 档），后者返回 `KTIME_LOW_RES = TICK_NSEC = 1/CONFIG_HZ`。

实测：

```text
  clock_gettime(MONOTONIC)               18.9 ns/call
  clock_gettime(MONOTONIC_COARSE)         4.9 ns/call
```

代价就是粒度变成 1 ms。**这不是「精度低一点」，是「一格之内完全不动」**：

```text
  CLOCK_MONOTONIC_COARSE   2000000 次连续读里        9 次有前进   最小正增量 = 999979 ns
```

200 万次读只有 9 次拿到新值。

**选型口诀**：要算「多长时间」（延迟、超时、耗时）→ 精确版；要「给事件盖个时间章」（日志、统计）→ COARSE。

</details>

<details>
<summary>4. `rdtsc` 只有一条指令，为什么 HFT 不全都用它？</summary>

因为它给的**不是时间，是 CPU 周期计数**。三个必须处理的问题：

| 问题 | 说明 | 应对 |
|------|------|------|
| **单位换算** | 要除以 TSC 频率才能得到秒。而 TSC 频率不写在任何标准寄存器里，得自己标定 | 用 `CLOCK_MONOTONIC` 标定一次：`freq = tsc_delta / mono_delta` |
| **变频** | 老 CPU 上调频会改变 TSC 增速，导致「同一段代码在不同 P-state 下读数不同」 | 检查 CPU 标志 `constant_tsc`（TSC 以固定速率走）+ `nonstop_tsc`（C-state 下不停）；现代服务器 CPU 一般都有 |
| **跨核 / 跨 socket** | 不同物理 CPU 的 TSC 起点可能不同；Linux 启动时若检测到不可靠，会**禁用 TSC 作为时钟源** | 检查 `/sys/devices/system/clocksource/clocksource0/current_clocksource` 是不是 `tsc` |
| **不可序列化** | `rdtsc` 不保证「之前的指令都已执行完」，测量边界可能漂移 | 用 `rdtscp`（带 `lfence` 语义）或手工插 `lfence` |

实测开销：

```text
  rdtsc 指令                           10.5 ns/call
```

比 `CLOCK_MONOTONIC_COARSE`（4.9 ns）慢、比 `CLOCK_MONOTONIC`（18.9 ns）快。

**所以真正的分工是**：

| 目的 | 用什么 |
|------|--------|
| 测「从 A 到 B 的延迟」 | `CLOCK_MONOTONIC`（跨进程/跨机器可比） |
| 测「这个函数花了多少周期」 | `rdtsc`（细粒度、便宜） |
| 给行情/订单打时间戳 | 硬件 PHC（网卡时间戳，`SO_TIMESTAMPING`），不要用软件读 |

</details>

<details>
<summary>5. 现代内核对定时器精度的限制到底在哪？原书说「1/HZ 限制一切」还成立吗？</summary>

**只对一半成立**。要按路径分开看：

| 路径 | 受限 | 依据 |
|------|------|------|
| `nanosleep()` / `clock_nanosleep()` / `timer_settime()` | ❌ 不受 1/HZ 限制 | 走 hrtimer；`ex10_3` 实测请求 1 µs 的 `nanosleep` 能醒来（实际 ~63 µs，是调度往返开销而非粒度） |
| `CLOCK_REALTIME` / `MONOTONIC` / `RAW` / `BOOTTIME` / `*_CPUTIME_ID` 读数 | ❌ 不受限 | `clock_getres` 实测报 `1 ns`（`hrtimer_resolution = HIGH_RES_NSEC`） |
| `CLOCK_*_COARSE` 读数 | ✅ 受限 | `clock_getres` 实测报 `1000000 ns` = `TICK_NSEC` |
| `times(2)` / `getrusage(2)` / `/proc/stat` | ✅ 受限 | 粒度是 `USER_HZ` = 100（10 ms），而且**不是 `CONFIG_HZ`** |
| `alarm(2)` / `setitimer(2)` | ✅ 受限 | 走 jiffies 定时器，不是 hrtimer |
| `poll()` / `select()` / `epoll_wait()` 的**超时参数** | 部分 | 内核会把超时值向上圆整到时钟源精度（`poll` 用 `timespec64` 精度，但底层调度仍是 hrtimer） |

所以准确表述是：

> **「软件时钟粒度」这个限制，今天只落在「jiffies 路径」上（COARSE 时钟、老定时器接口、`USER_HZ` 统计接口）。所有走 hrtimer 的接口都不受 `CONFIG_HZ` 限制。**

原书那句话的「前提」是 2010 年那批内核里 hrtimer 还不是所有路径的默认。**对着源码读，才知道哪一句还成立。**
</details>
