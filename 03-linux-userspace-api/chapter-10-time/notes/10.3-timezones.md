## 本节讲什么

[10.2](10.2-time-conversion-functions.md) 里 `localtime()` 和 `gmtime()` 的输出**恰好相同**，因为那个容器是 UTC。本节回答：`localtime()` 到底从哪儿知道「本地」是哪儿。

先立一条最重要的事实：

> **Linux 内核完全没有时区概念。** 时区是**纯粹的 glibc 用户态**行为：glibc 读 `TZ` 环境变量或 `/etc/localtime`（一个 tzfile 二进制），自己做换算。内核只提供 UTC 秒数和一堆 `CAP_SYS_TIME` 保护的写接口。

这条事实的证据在第 4 段（`gettimeofday` 的 `struct timezone` 参数内核根本不填）和 [10.5](10.5-updating-the-system-clock.md) 的实测里。

本节的 demo：`c10_3_timezone.c`，五段——时区来源 / 三个全局变量 / 9 种 `TZ` 写法 / DST 两季 / 双向互证。

## 1. 系统时区是从哪儿读来的

源码：[../code/c10_3_timezone.c](../code/c10_3_timezone.c)

```c
/* TLPI 第 10 章 §10.3 Timezones
 * 时区怎么被定下来：tzset() / tzname[] / 全局 timezone 与 daylight /
 * tm_gmtoff / TZ 环境变量的四种写法 / POSIX TZ 的符号陷阱 / DST 切换
 *
 * 编译: gcc -O0 -Wall -Wextra -o c10_3_timezone c10_3_timezone.c
 * 运行: ./c10_3_timezone                     (无需参数、无需权限)
 *
 * 全部用**固定时间戳**，只有 TZ 是我们主动改的变量 → 输出可复现。
 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

#define SUMMER 1688169600L   /* 2023-07-01 00:00:00 UTC */
#define WINTER 1701388800L   /* 2023-12-01 00:00:00 UTC */

static void show_localtime_file(void)
{
    char link[256];
    ssize_t n = readlink("/etc/localtime", link, sizeof link - 1);

    printf("== 1. 系统时区是从哪儿读来的 ==\n");
    if (n > 0) {
        link[n] = '\0';
        printf("/etc/localtime -> %s\n", link);
    } else {
        printf("/etc/localtime 读不到（readlink 返回 %zd）\n", n);
    }
    /* 不带前导冒号的 TZ 值 glibc 会去 /usr/share/zoneinfo/ 下查这个文件 */
    printf("/usr/share/zoneinfo/Asia/Shanghai 是否可读: %s\n",
           (access("/usr/share/zoneinfo/Asia/Shanghai", R_OK) == 0) ? "是" : "否");
    printf("TZ 环境变量 = %s\n\n",
           getenv("TZ") ? getenv("TZ") : "(未设置)");
}

/* 用两个独立途径算同一个偏移，互相印证 */
static void show_offset_two_ways(time_t t, const char *label)
{
    struct tm l;
    long via_gmtoff, via_diff;

    localtime_r(&t, &l);
    via_gmtoff = l.tm_gmtoff;
    /* 把本地分解时间当成 UTC 再解释一次，差值就是偏移 */
    via_diff = (long) mktime(&l) - (long) timegm(&l);

    /* ⚠️ 这里刻意把「一致?」写成「== -tm_gmtoff?」：
       mktime() 把字段当**本地时间**解释，timegm() 当 **UTC** 解释，
       两者之差 = -偏移。所以正确的互证条件是 via_diff == -via_gmtoff，
       而不是相等 —— 第一次写成「相等」时这四行全是「否」，看着像 bug。 */
    printf("  %-6s %s  %-3s  %+03ld%02ld   tm_gmtoff=%+ld s  "
           "mktime-timegm=%+ld s  互为相反数? %s\n",
           label, l.tm_zone, tzname[l.tm_isdst > 0 ? 1 : 0],
           via_gmtoff / 3600, labs(via_gmtoff % 3600) / 60,
           via_gmtoff, via_diff, (via_diff == -via_gmtoff) ? "是" : "否");
}

static void show_globals(void)
{
    printf("== 2. tzset() 与三个全局变量 ==\n");
    tzset();
    printf("tzname[0] = \"%s\"   tzname[1] = \"%s\"\n", tzname[0], tzname[1]);
    printf("全局 timezone = %ld s（UTC 以西为正，注意符号！）\n", timezone);
    printf("全局 daylight = %d\n", daylight);
    printf("（这三个都是 glibc 的全局变量，靠 tzset() 刷新 —— "
           "别人改了 TZ 你这里不会自动变）\n\n");
}

static void show_tz_switch(void)
{
    static const char *tzs[] = {
        "UTC",
        "Asia/Shanghai",
        "America/New_York",
        "Europe/London",
        ":Asia/Tokyo",
        "XXX-8",
        "UTC+8",
        "IST-5:30",
        "EST5EDT,M3.2.0,M11.1.0",
        NULL
    };

    printf("== 3. 进程内切换 TZ：setenv + tzset ==\n");
    for (int i = 0; tzs[i] != NULL; i++) {
        struct tm l;
        char buf[80];
        time_t wt = (time_t) WINTER;

        setenv("TZ", tzs[i], 1);
        tzset();
        printf("TZ=%-26s tzname[0]=%-12s timezone=%6ld  daylight=%d\n",
               tzs[i], tzname[0], timezone, daylight);
        localtime_r(&wt, &l);
        strftime(buf, sizeof buf, "%F %T %Z %z", &l);
        printf("%-34s -> %s\n", "", buf);
    }
    printf("\n");
}

static void show_dst(void)
{
    struct tm s, w;
    char bs[80], bw[80];
    time_t st = (time_t) SUMMER, wt = (time_t) WINTER;

    printf("== 4. DST：同一时区、两个季节 ==\n");
    setenv("TZ", "America/New_York", 1);
    tzset();
    localtime_r(&st, &s);
    localtime_r(&wt, &w);
    strftime(bs, sizeof bs, "%F %T %Z %z", &s);
    strftime(bw, sizeof bw, "%F %T %Z %z", &w);
    printf("2023-07-01 -> %s   tm_isdst=%d\n", bs, s.tm_isdst);
    printf("2023-12-01 -> %s   tm_isdst=%d\n", bw, w.tm_isdst);
    printf("偏移差了 %ld 分钟\n\n", (w.tm_gmtoff - s.tm_gmtoff) / 60);

    printf("== 5. 两个季节在两个时区上的偏移 ==\n");
    setenv("TZ", "Asia/Shanghai", 1);
    tzset();
    show_offset_two_ways((time_t) SUMMER, "summer");
    show_offset_two_ways((time_t) WINTER, "winter");
    setenv("TZ", "America/New_York", 1);
    tzset();
    show_offset_two_ways((time_t) SUMMER, "summer");
    show_offset_two_ways((time_t) WINTER, "winter");
    printf("\n");
}

int main(void)
{
    show_localtime_file();
    show_globals();
    show_tz_switch();
    show_dst();

    printf("⚠️ 两个必须记住的陷阱：\n");
    printf("  1) POSIX TZ 的符号是**反的**。TZ=XXX-8 表示「比 UTC 早 8 小时」\n");
    printf("     （即东八区，offset = +0800）；所以 TZ=UTC+8 得到的是 -08。\n");
    printf("  2) 不带前导冒号的 TZ 值会被 glibc 先去 /usr/share/zoneinfo 找同名\n");
    printf("     文件；加冒号（TZ=:Asia/Tokyo）是强制走「文件路径」语义。\n");
    return 0;
}
```

编译 + 运行：

```bash
gcc -O0 -Wall -Wextra -o c10_3_timezone c10_3_timezone.c
./c10_3_timezone
```

实测（CE，gcc 13.3.0）：

```text
== 1. 系统时区是从哪儿读来的 ==
/etc/localtime 读不到（readlink 返回 -1）
/usr/share/zoneinfo/Asia/Shanghai 是否可读: 是
TZ 环境变量 = (未设置)
```

glibc 的时区解析优先级（自高到低）：

| 顺序 | 来源 | 说明 |
|------|------|------|
| 1 | `TZ` 环境变量 | 一旦设置，**完全覆盖** `/etc/localtime` |
| 2 | `/etc/localtime` | 通常是指向 `/usr/share/zoneinfo/<区域>/<城市>` 的**符号链接**（也可能是一条 `TZif2...` 二进制内容） |
| 3 | 兜底 | 两者都没有 → 按 **UTC** 处理（本容器就是这种：`readlink` 返回 -1，没有环境变量，所以 `tzname[0]` 后来实测为 `"UTC"`） |

注意 `readlink` 返回 **-1**（不是 0 也不是空串）——这是「这个路径根本不是符号链接」的错误码 `EINVAL`。所以 demo 里的判断写成 `n > 0` 而不是 `n >= 0`。

**为什么 `/usr/share/zoneinfo/<名>` 能不能读很重要**：`TZ=Asia/Shanghai` 这种「看起来像路径但不是绝对路径」的写法，glibc 会去 `/usr/share/zoneinfo/` 下拼出文件名去找。这台容器里 `Asia/Shanghai` 存在 → 所以后面第 3 段那 9 种 TZ 里带地名的那几个才能成功。

## 2. `tzset()` 与三个全局变量

```text
== 2. tzset() 与三个全局变量 ==
tzname[0] = "UTC"   tzname[1] = "UTC"
全局 timezone = 0 s（UTC 以西为正，注意符号！）
全局 daylight = 0
（这三个都是 glibc 的全局变量，靠 tzset() 刷新 —— 别人改了 TZ 你这里不会自动变）
```

| 全局对象 | 类型 | 含义 | 坑 |
|----------|------|------|----|
| `tzname[0]` | `char *` | 标准时间的缩写（`"CST"`、`"EST"`） | 是**指针数组**，指向内部静态字符串；换 TZ 后旧指针可能失效 |
| `tzname[1]` | `char *` | 夏令时的缩写（`"CDT"`、`"EDT"`） | 有些时区没有 DST，`tzname[1]` 会和 `tzname[0]` 一样 |
| `timezone` | `long` | 标准时间与 UTC 的差，**秒** | ⚠️ **符号与 `tm_gmtoff` 相反**：`timezone` 是「UTC 以西为正」（POSIX 老约定） |
| `daylight` | `int` | 该时区**是否使用** DST（不是「现在是否在 DST 里」） | 名字很好骗人：看的是**这年的规则有没有 DST** |

上面两条符号/语义的坑，在本 demo 的第 3 段有对照实测：

| TZ | `timezone` | 实际偏移（`%z`） |
|----|-----------|-----------------|
| `Asia/Shanghai` | `-28800` | `+0800` ← **反号** |
| `America/New_York` | `18000` | `-0500` ← **反号** |

`tzset()` 的两个关键行为：

| 行为 | 说明 |
|------|------|
| **`localtime()` 会自动调一次 `tzset()`** | POSIX 要求「就像调过 `tzset()` 一样」；所以改完 `TZ` 后即使忘了 `tzset()`，下一次 `localtime()` 也会刷新 |
| **但 `tzname` / `timezone` / `daylight` 不会自己刷** | 这三个是**读的时候的值**。改完 `TZ` 必须显式 `tzset()`，否则你读到的是上一次的快照 |

这解释了 demo 里为什么每次 `setenv("TZ", ...)` 后面都紧跟一个 `tzset()`。

## 3. 九种 `TZ` 写法（含两个陷阱）

```text
== 3. 进程内切换 TZ：setenv + tzset ==
TZ=UTC                        tzname[0]=UTC          timezone=     0  daylight=0
                                   -> 2023-12-01 00:00:00 UTC +0000
TZ=Asia/Shanghai              tzname[0]=CST          timezone=-28800  daylight=1
                                   -> 2023-12-01 08:00:00 CST +0800
TZ=America/New_York           tzname[0]=EST          timezone= 18000  daylight=1
                                   -> 2023-11-30 19:00:00 EST -0500
TZ=Europe/London              tzname[0]=GMT          timezone=     0  daylight=1
                                   -> 2023-12-01 00:00:00 GMT +0000
TZ=:Asia/Tokyo                tzname[0]=JST          timezone=-32400  daylight=1
                                   -> 2023-12-01 09:00:00 JST +0900
TZ=XXX-8                      tzname[0]=XXX          timezone=-28800  daylight=0
                                   -> 2023-12-01 08:00:00 XXX +0800
TZ=UTC+8                      tzname[0]=UTC          timezone= 28800  daylight=0
                                   -> 2023-11-30 16:00:00 UTC -0800
TZ=IST-5:30                   tzname[0]=IST          timezone=-19800  daylight=0
                                   -> 2023-12-01 05:30:00 IST +0530
TZ=EST5EDT,M3.2.0,M11.1.0     tzname[0]=EST          timezone= 18000  daylight=1
                                   -> 2023-11-30 19:00:00 EST -0500
```

九种写法归三类：

| 类 | 例子 | 含义 |
|----|------|------|
| **地名（找文件）** | `Asia/Shanghai`、`America/New_York`、`Europe/London` | glibc 去 `/usr/share/zoneinfo/<名>` 读 tzfile。**DST 规则也在文件里**，所以 `daylight=1` |
| **`:` 前缀（强制按路径）** | `:Asia/Tokyo` | 前导冒号 = 「后面的字符串是**文件路径**，别做其它解释」。对 `Asia/Tokyo` 这种相对路径效果和上面一样；对**绝对路径**（`:/etc/mytz`）才有区别 |
| **POSIX TZ 字符串** | `XXX-8`、`UTC+8`、`IST-5:30`、`EST5EDT,M3.2.0,M11.1.0` | 自解释的「缩写 + 偏移 [+ DST 规则]」格式。**不查任何文件**（所以 `daylight` 取决于字符串里有没有 DST 规则） |

### 陷阱 ①：POSIX TZ 的符号是**反的**

对照这两行（本 demo 实测）：

| TZ 值 | 得到的偏移 | `timezone` |
|-------|-----------|-----------|
| `XXX-8` | `+0800`（**东八区**） | `-28800` |
| `UTC+8` | `-0800`（**西八区**） | `28800` |

也就是说 `TZ=XXX-8` 里的 `-8` 表示「**比 UTC 早 8 小时**」，不是「UTC 减 8」。POSIX 这个格式的定义是：

```
std offset
```

其中 `offset` 是「**要加到本地时间上才能得到 UTC** 的量」——所以东八区的本地时间要**减** 8 小时才是 UTC，offset 记作 `-8`。

> 记忆法：POSIX TZ 里的符号，和你在手表上看到的方向**相反**。想要「+08:00」得写 `XXX-8`。

顺带一个真实例子：`TZ=IST-5:30` 得到 `+0530`，证明**半小时偏移在这个格式里也是支持的**（`offset` 允许 `hh:mm:ss`）。

### 陷阱 ②：`%Z` 在 POSIX TZ 字符串下可能不是「时区名」

看 `TZ=Asia/Kathmandu` 那一行（在 [10.9](10.9-exercise.md) 的 demo 里）：

```text
  TZ=Asia/Kathmandu         %-Z=+0545 %-z=+0545 
```

`%Z` 打出的是 **`+0545`**，不是某个缩写。原因是尼泊尔的 tzfile 里 `abbrev` 字段就存的是 `+0545` 这种形式（这个时区没有通行的字母缩写）。**所以不要拿 `%Z` 当机器可读的时区标识**——它只是给人看的字符串，长度和内容都没有保证。要机器可读就用 `%z` 或 `tm_gmtoff`。

### 顺带：`EST5EDT,M3.2.0,M11.1.0` 的读法

```
EST 5 EDT , M3.2.0 , M11.1.0
 │   │  │     │        └─ 结束：11 月第 1 个周日
 │   │  │     └────────── 开始：3 月第 2 个周日
 │   │  └──────────────── 夏令时缩写
 │   └─────────────────── 偏移（小时）
 └─────────────────────── 标准时缩写
```

这是**教科书级的美国东部时区规则**，纯字符串、不查文件，因此可以拿来做「跨平台可复现的时区测试」。

## 4. DST：同一时区、两个季节

```text
== 4. DST：同一时区、两个季节 ==
2023-07-01 -> 2023-06-30 20:00:00 EDT -0400   tm_isdst=1
2023-12-01 -> 2023-11-30 19:00:00 EST -0500   tm_isdst=0
偏移差了 -60 分钟
```

三个要点：

| 要点 | 说明 |
|------|------|
| **DST 是「时区的属性」，不是「时间戳的属性」** | 同一个 `TZ=America/New_York`，同一份代码，只因为时间戳落在 7 月还是 12 月，`tm_gmtoff` 就差了 3600 秒 |
| `tm_isdst` 真的会变 | 1 vs 0（这就是 [10.2](10.2-time-conversion-functions.md) 里强调三态的原因） |
| 输入的 UTC 时间戳是「同一天的不同点」 | `1688169600` = 2023-07-01 00:00 UTC → 纽约当地 6 月 30 日 20:00；`1701388800` = 2023-12-01 00:00 UTC → 纽约 11 月 30 日 19:00 |

> 因为 DST 的存在，**「本地时间 → UTC 秒数」这个函数（`mktime`）是不单调的**。DST 切换那一小时里，本地时间会出现「重复」或「空缺」，`mktime` 只能挑一个（glibc 的行为依赖 `tm_isdst` 的取值）。这是所有「用本地时间做唯一时间标识」的方案必然踩的坑——**日志和协议一律用 UTC**。

## 5. 双向互证：`tm_gmtoff` 与 `mktime - timegm`

```text
== 5. 两个季节在两个时区上的偏移 ==
  summer GMT  CST  +0800   tm_gmtoff=+28800 s  mktime-timegm=-28800 s  互为相反数? 是
  winter GMT  CST  +0800   tm_gmtoff=+28800 s  mktime-timegm=-28800 s  互为相反数? 是
  summer GMT  EST  -0400   tm_gmtoff=-14400 s  mktime-timegm=+14400 s  互为相反数? 是
  winter GMT  EST  -0500   tm_gmtoff=-18000 s  mktime-timegm=+18000 s  互为相反数? 是
```

这段在算一件很简单的事：拿同一个 `struct tm`，**用两种方式**解释它，看差值是不是就是时区偏移。

| 函数 | 怎么解释 `struct tm` 的字段 |
|------|---------------------------|
| `mktime(&tm)` | 当成**本地时间**（会查 TZ，并可能按 `tm_isdst` 调整） |
| `timegm(&tm)` | 当成 **UTC**（GNU/BSD 扩展，`gmtime` 的逆运算） |

如果本地时间 = UTC + `off`，那么把这个 `tm` 当本地解释得到的秒数，就比当 UTC 解释得到的秒数**少** `off`。所以：

```
mktime(&tm) - timegm(&tm) == -tm_gmtoff
```

四个 `互为相反数? 是` 就是在验证这条恒等式。

> **这是本 demo 修过的一个 bug，值得记下来。** 第一版把判断写成 `via_gmtoff == via_diff`（期望「相等」），结果四行全是「否」——**看着像 demo 坏了，其实是推导错了符号**。修法是改成 `via_diff == -via_gmtoff`，并在源码里写了一行注释说明为什么。
>
> 教训：**「实测输出与预期不符」时，先怀疑自己的推导，再怀疑库。** 如果当时图省事把「否」写成「两者不同（这是正常的）」，就会把一个真结论埋进一句含糊的话里。

> 另一个细节：`timegm()` **不是 POSIX 标准**，是 GNU/BSD 扩展。所以移植代码里要么接受「只在 glibc/BSD 上可用」，要么用 `TZ=UTC; tzset(); mktime()` 的方式模拟（这正是原书习题 10-1 参考答案里采用的做法）。

## HFT / 嵌入式关联

| 场景 | 结论 |
|------|------|
| **延迟测量** | 时区与 `CLOCK_MONOTONIC` 无关。**任何间隔计算都不要经过时区** |
| **交易日志** | 一律 UTC；本地时区只在「给人看的前端」加。中国没有 DST 是幸运，但要和跨市场（美国有 DST）的系统对齐时，别把「本地时间」当唯一标识 |
| **时间同步** | NTP/PTP 校的是 UTC（`CLOCK_REALTIME`）；`tzset` 这件事跟同步完全无关 |
| **容器环境** | 容器里常出现 `/etc/localtime` 不存在（本 demo 实测就是），此时程序静默按 UTC 运行。**上线前必须显式设 `TZ`**，否则「开发机（东八区）日志和线上（UTC）日志差 8 小时」 |
| **嵌入式** | 很多精简 rootfs **不带** `/usr/share/zoneinfo`（几十 MB）。这时只能用 POSIX TZ 字符串（`TZ=CST-8`）——代价是**没有 DST 规则**，有 DST 的地区会错一小时 |
| **性能** | 第一次 `tzset()` 要读文件 + 解析，是 **磁盘 I/O**；改 TZ 之后的热路径上不要反复 `setenv`/`tzset`。glibc 会缓存已解析的 tzfile |
| **安全性** | `TZ` 是**环境变量**——被控环境（`sudo`、setuid 程序）里它可能被攻击者设置。setuid 程序应当**主动 `unsetenv("TZ")`**，或至少不依赖它做安全判断 |

## 代码自测

<details>
<summary>1. 想得到「东八区」，`TZ` 应该写 `UTC+8` 还是 `XXX-8`？为什么？</summary>

**`XXX-8`**（或 `CST-8`），不是 `UTC+8`。

POSIX TZ 的格式是 `std offset`，其中 `offset` 的定义是「**加到本地时间上得到 UTC** 的那个量」：

```
UTC = 本地时间 + offset
```

东八区里，本地 08:00 对应 UTC 00:00，所以 `0 = 8 + offset` → `offset = -8`。

本 demo 的实测正好一对反例：

| TZ | `%z` | 意图是否达成 |
|----|------|-------------|
| `XXX-8` | `+0800` | ✔ 东八区 |
| `UTC+8` | `-0800` | ✘ 变成西八区 |

顺带注意 `est5edt` 那个著名写法：美国的 `EST5EDT` 里的 `5` 也是这个道理——纽约在 UTC−5，`offset` 写 `5`（正数），读作「比 UTC 晚 5 小时」。

</details>

<details>
<summary>2. 为什么 `timezone` 全局变量和 `tm_gmtoff` 符号相反？该用哪个？</summary>

因为它们是两条不同年代、不同约定的产物：

| 对象 | 符号约定 | 来源 |
|------|---------|------|
| `timezone`（全局） | **UTC 以西为正**（`Asia/Shanghai` → `-28800`） | 老 POSIX / SysV 约定，现在**已被 POSIX 标记为废弃**（`obsolescent`） |
| `tm_gmtoff` | **本地相对 UTC 的偏移**（`Asia/Shanghai` → `+28800`，即「+08:00」） | BSD 扩展，语义与 `%z` 一致，符合直觉 |

**用 `tm_gmtoff`**。三个理由：

1. `timezone` 是全局变量——多线程下随时被别的线程的 `tzset()` 改掉。
2. 它是废接口，换 libc（musl）不一定有。
3. 它的符号跟 `%z` 和 ISO 8601 都相反，写代码时手工转换极易出错。

正确取偏移的方式（本仓库 [10.9](10.9-exercise.md) 练习 2 的 `right_way()` 就是这个）：

```c
struct tm tm;
localtime_r(&t, &tm);
long off = tm.tm_gmtoff;             /* 秒，东八区 = +28800 */
int  hh  = off / 3600, mm = labs(off % 3600) / 60;
```

</details>

<details>
<summary>3. `TZ=Asia/Shanghai` 和 `TZ=:Asia/Shanghai` 有区别吗？</summary>

对**相对名字**（不含 `/` 开头的）**没有实际区别**：两者都会去 `/usr/share/zoneinfo/Asia/Shanghai` 找文件。本 demo 里 `TZ=:Asia/Tokyo` 与 `TZ=Asia/Shanghai` 的表现形式完全一致（都成功读出 `JST` / `CST`）。

前导冒号真正起作用的是这两种情况：

| 写法 | 冒号的作用 |
|------|-----------|
| `:/etc/mytzfile`（**绝对路径**） | 告诉 glibc「这是一个文件路径，别去 `zoneinfo/` 下拼名字」 |
| `:XXX-8` | 强制按 POSIX 字符串解释，**跳过**「先找同名文件」这一步 |

第二点是很实际的一条：如果不加冒号，`TZ=UTC` 会**先去找** `/usr/share/zoneinfo/UTC` 这个文件；加了冒号就保证不会被同名的 ZoneInfo 文件「截胡」。

顺带：`TZ=""`（空串）也是合法输入，含义是「按 UTC 处理」，和未设置**不同**（未设置是「读 `/etc/localtime`」）。

</details>

<details>
<summary>4. 为什么说「用本地时间当唯一时间标识」的方案一定会坏？</summary>

因为 DST 让「本地时间 → UTC」这个映射**不是双射**，两个方向都会出问题：

| 情况 | 现象 |
|------|------|
| **春天「跳过」** | 某地 02:00 直接跳到 03:00 → 本地时间 `02:30` **不存在**。解析它时 `mktime` 只能猜 |
| **秋天「重复」** | 某地 02:00 走两次 → 本地时间 `01:30` 对应**两个**不同 UTC 时刻。只写「本地 01:30」就丢失了区分信息 |

真实后果：

1. 日志按本地时间排序 → 秋天 DST 那一个小时里**顺序会颠倒**。
2. 用本地时间做去重/主键 → 秋天会误判为重复事件。
3. 定时任务「每天 02:30 执行」→ 春天那天**不会执行**（该时刻不存在）。

所以正确做法是**内部一律 UTC（或 `CLOCK_MONOTONIC` 计单调秒），只在展示层加时区**。这也正是 RFC 3339 / ISO 8601 要求带 `Z` 或 `±hh:mm` 偏移的原因。

本项目 [10.9](10.9-exercise.md) 练习 2 的实测也顺带证明了这件事的另一面：`%z` 拿出来是 `+0545`（尼泊尔）、`+1030`（南澳）这些**非整数小时**的偏移——如果你的代码里写的是 `off * 3600`，这些时区直接错。

</details>
