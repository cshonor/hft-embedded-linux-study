# 49.9 MAP_NORESERVE 与 swap space overcommit

> 源码核验：Linux v6.6 · `mm/mmap.c`（`accountable_mapping` 记账 · `security_vm_enough_memory_mm` 检查 · `mmap_region():2662` 内 `charged` 分支）· `mm/util.c`（`vm_commit_limit` / `__vm_enough_memory` overcommit 判定）

## 本节讲什么

私有可写映射默认要**预留 swap**（承诺「你最坏情况全写满也放得下」）；`MAP_NORESERVE` 放弃这个承诺。三个灵魂问题：

1. 预留的是什么？（swap 空间的记账数字，不是真实分配——commit 只动计数器）
2. 三种 overcommit 模式怎么选？（0 启发式 / 1 全放行 / 2 按公式严格）
3. 什么时候会死？（写爆 commit → **OOM killer**，按 oom_score 挑受害者）

---

## 要点

### 预留机制：VM_ACCOUNT

`mmap_region()` 对**私有可写**映射走 `accountable_mapping`：commit 字节数进 `mm->committed_vm`，全局对照 `CommitLimit`（`/proc/meminfo`）。预留失败 → mmap 返回 `ENOMEM`。`MAP_NORESERVE` 跳过整个记账（v6.6 中该标志本身已在多数模式被弱化，见下表）。

### 三种 overcommit 模式（`/proc/sys/vm/overcommit_memory`）

| 模式 | 语义 | MAP_NORESERVE 的效果 |
|------|------|---------------------|
| **0（默认）: 启发式** | 明显离谱的请求拒绝（单次 > RAM+swap），合理的放行 | 基本等效（启发式本来就宽松） |
| **1: 总是允许** | 不检查，来者不拒 | 无差别 |
| **2: 严格模式** | 总 commit ≤ `swap + RAM × overcommit_ratio` | 被忽略——严格模式下人人都必须记账 |

严格模式的公式（`vm_commit_limit()`）：

```
CommitLimit = SwapTotal + (RAMTotal - RAMKernelReserved) × overcommit_ratio/100
```

### 死亡路径：写爆 commit

```
承诺了 8GB（committed） ← mmap 时只记数字，没占真内存
   ↓ 进程真写满
物理内存 + swap 全线耗尽
   ↓
page fault 分配不出页 → out_of_memory() → OOM killer
   ↓ 按 oom_score（RSS、nice、运行时间…）选牺牲品 → SIGKILL
```

**被杀的不一定是肇事进程**——oom_score 偏向大 RSS，谁胖谁死。生产事故经典形态：「稀疏大映射的进程活得好好的，隔壁无辜的数据库被 OOM 了」。

### 何时用 MAP_NORESERVE

| 场景 | 判断 |
|------|------|
| 稀疏数组（大部分页永不写） | ✅ 用——不写就不占真内存，预留是浪费 |
| 预留大虚拟区 + 按需 populate（HFT 常见） | ✅ 用 |
| 共享内存大块 | ⚠️ 谨慎——SHARED 映射本身不记账（无 swap 可换），但真写满照样挤爆 RAM |
| 正常分配 | ❌ 不用——默认记账是免费保险 |
| 要可靠的 OOM 行为 | ❌ 不用 |

### 观测工具

```bash
grep -i commit /proc/meminfo    # CommitLimit / Committed_AS（承诺 vs 上限）
cat /proc/<pid>/status | grep VmSize   # 虚拟 vs RSS：稀疏映射的差值就是「画而未用」
```

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| 嵌入式 | 无 swap 设备时 CommitLimit ≈ RAM×ratio——严格模式直接把多数大 mmap 拒掉；嵌入式常开 overcommit=1（反正没有 swap 可承诺，记账是自欺） |
| HFT | 预留超大虚拟区（如 64GB 订单池地址空间）+ `MAP_NORESERVE` + 按需 mlock/populate——**虚拟区白拿，物理页按工作集付账**；但必须配监控：`Committed_AS` 贴近 `CommitLimit` = 全系统 OOM 前兆，比等毛刺可靠 |

## 代码示例

```c

/* MAP_NORESERVE：稀疏大映射的「画而不占」
 * 实测（WSL Ubuntu，gcc -O2 -Wall -Wextra，2026-09-05）：
 *   mapped 1GB with MAP_NORESERVE
 *   Rss=0 kB（只写 2 页前）→ 写 2 页后 Rss=8 kB
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>

static long smaps_rss(void *addr)
{
    FILE *fp = fopen("/proc/self/smaps", "r");
    if (!fp) return -1;
    char line[300];
    unsigned long lo, hi, a = (unsigned long)addr;
    long rss = -1;
    int in_target = 0;
    while (fgets(line, sizeof line, fp)) {
        if (sscanf(line, "%lx-%lx", &lo, &hi) == 2)
            in_target = (a >= lo && a < hi);
        else if (in_target && strncmp(line, "Rss:", 4) == 0) {
            sscanf(line + 4, "%ld", &rss);
            break;
        }
    }
    fclose(fp);
    return rss;
}

int main(void)
{
    size_t size = 1UL << 30;                  /* 1GB 虚拟 */
    char *p = mmap(NULL, size, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    printf("mapped 1GB MAP_NORESERVE at %p, Rss=%ld kB（画而不占）\n",
           (void *)p, smaps_rss(p));

    p[0] = 'x';
    p[4096] = 'y';                            /* 只碰 2 页 */
    printf("写 2 页后 Rss=%ld kB（只有真写的页进物理内存）\n", smaps_rss(p));
    /* 注意：若写满 1GB 且系统无余量 → OOM killer 可能杀掉本进程或邻居 */

    munmap(p, size);
    return 0;
}
```

## 自测题

**题目 1（选择）：** overcommit_memory=2（严格模式）下，`MAP_NORESERVE` 的效果？

A. 完全跳过记账　B. 被忽略，照样记账　C. mmap 必定失败　D. 只影响 RSS

<details>
<summary>参考答案</summary>

**B**。严格模式的语义就是「人人都记账、总承诺不超公式」——MAP_NORESERVE 在此模式下形同虚设。反过来在模式 1（总是允许）下记账本来就不查，NORESERVE 也无意义。**该标志只在默认启发式模式下有实际差别**。

</details>

**题目 2（判断）：** `Committed_AS` 是当前真实占用的内存量。

<details>
<summary>参考答案</summary>

错误。`Committed_AS` 是**承诺总量**——所有进程「最坏情况全写满」的加总（虚拟内存记账），真实占用看 RSS/MemAvailable。Committed_AS 完全可以远超 RAM（overcommit 0/1 下常态），它逼近 CommitLimit 才是危险信号。

</details>

**题目 3（应用）：** 8GB RAM + 4GB swap 的机器，进程 A 按默认模式 mmap 12GB 私有匿名映射，会发生什么？overcommit_memory 分别为 0/1/2 时？

<details>
<summary>参考答案</summary>

- 模式 0（启发式）：单次请求 12GB > RAM+swap=12GB 的边界判定（「明显过度」），大概率 `ENOMEM`；若分成多次小块 mmap 则各块都能过（启发式只看单次）。
- 模式 1：mmap 成功（不检查）；写满时物理耗尽 → OOM killer 开杀。
- 模式 2：记账 12GB > CommitLimit（=swap 4GB + RAM×ratio），`ENOMEM`——在 mmap 调用点就失败，不拖到写的时候。这是三种模式的责任分界：2 = 当场拒绝，1 = 事后偿命（OOM），0 = 介于中间。

</details>
