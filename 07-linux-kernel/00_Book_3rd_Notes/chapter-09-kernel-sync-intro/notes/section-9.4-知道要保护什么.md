## ④ 知道要保护什么 · Knowing What to Protect

同步的第一步不是选锁类型，而是 **识别哪些数据是共享的、谁可能并发访问** — LKD 强调：**保护数据，而不是保护代码**。

#### 按存储类别

| 数据 | 是否需要锁 | 说明 |
|------|-------------|------|
| **局部自动变量** | **通常否** | 各线程 **独立栈** — `int x` 在函数内 |
| **静态局部 / 全局** | **几乎都要** | 全内核可见 |
| **堆上动态分配** | **视指针是否共享** | 若仅一线程持有指针 → 可能不需 |
| **per-CPU 变量** | **通常 per-CPU 内不需锁** | 其他 CPU 各有一份 — Ch 8 |
| **设备寄存器（MMIO）** | **硬件语义** | 可能需 **顺序** 或 **锁护 shadow 状态** |

#### 基本原则

| 规则 | 说明 |
|------|------|
| 其他执行线程 **能访问** 的数据 | **需要同步** |
| **保护数据，不是保护代码** | **lock data, not code** |
| **问五个并发源** | 中断、BH、抢占、睡眠、SMP — Ch 9.3 |

| 反例（保护代码） | 正例（保护数据） |
|------------------|------------------|
| 「给整个 `foo()` 加一把大锁」 | 明确 **`struct dev->stats`** 字段被 ISR 与 read 共享 → **只锁 stats** |
| 锁函数入口但 **回调** 裸访数据 | 回调也走 **同一锁** 或 **RCU 读侧** |
| 复制指针出来 **解锁后** 仍用 | 持锁期间完成访问或 **refcount** |

#### 识别共享数据的检查清单

```
对每个全局/嵌入结构字段：
  □ 进程上下文 read/write 会碰吗？
  □ ISR 会碰吗？
  □ tasklet/softirq 会碰吗？
  □ workqueue 会碰吗？
  □ 其他 CPU 上的同样代码会碰吗？
  ── 任一「是」→ 需要同步方案
```

#### 粒度权衡（预告 Ch 9.6 / Ch 10）

| 粒度 | 优点 | 缺点 |
|------|------|------|
| **一把大锁** | 简单、不易漏 | 争用高、扩展差 |
| **每字段/每队列一把锁** | 争用低 | 复杂、死锁风险、开销 |
| **per-CPU + 周期性合并** | 热路径无锁 | 实现难 |

#### 特殊手段（减少「需要锁的数据」）

| 手段 | 思路 |
|------|------|
| **per-CPU 变量** | 每 CPU 一份计数 — softirq 统计（Ch 8） |
| **RCU** | 读多写少 — 读者 **无锁**（Ch 10） |
| **无锁 ring（kfifo）** | 单生产者单消费者 — Ch 6 |
| **只读发布后不变** | 初始化后 `const` — 无需锁 |

#### 常见遗漏

| 遗漏 | 后果 |
|------|------|
| **只保护写、不保护读** | 读者看到不一致快照 |
| **联合体 / 位域** | 部分更新 torn |
| **`current` 相关 per-task 数据** | 误以为全局 — 通常 **不需** 全局锁 |
| **模块参数 / sysfs** | 用户写 sysfs 与 ISR **并发** |

**HFT：** 行情 **order book** 若在内核与用户态共享 mmap 区，必须明确 **谁写谁读** — 单写多读可用 **seqlock** 或 **双缓冲**；多写必须 **细粒度锁** 或 **分片 per-symbol**。
