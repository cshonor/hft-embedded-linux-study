## ② 加锁 · Locking

当临界区 **多于一条指令**、或涉及 **复杂数据结构** 时，硬件原子指令 alone 不够 — 靠 **锁（lock）** 保证 **同一时刻只有一个线程** 进入临界区。

| 比喻 | 说明 |
|------|------|
| **房间门锁** | 一次只允许一人进房修改共享数据；其他人 **等待** 或 **自旋** |

#### 锁的基本语义

| 操作 | 效果 |
|------|------|
| **`lock()` / acquire** | 若锁空闲则占有；否则 **等待** |
| **`unlock()` / release** | 释放锁，唤醒等待者 |
| **不变量** | 持锁期间 **独占** 访问被保护的数据 |

#### 锁争用时的两种等待策略

| 类型 | 行为 | 典型锁（Ch 10） | 适用 |
|------|------|-----------------|------|
| **忙等（spin）** | 线程 **空转** 直到锁释放 | **`spinlock_t`** | 临界区 **极短**、持有者可能在 **另一 CPU** 运行 |
| **睡眠** | 当前任务 **阻塞**，**让出 CPU** | **`mutex`** | 临界区 **较长**、持有者可能在 **本 CPU** 且会睡眠 |

```
spinlock（另一 CPU 持锁）：
  CPU0: while (!trylock) ;  ←  burning cycles，但持有者仍在跑

mutex（本 CPU 持锁且睡眠）：
  CPU0: lock → schedule 出去  ← 不浪费 CPU 空转
```

#### 建议性与自愿性（Advisory & Voluntary）

| 事实 | 含义 |
|------|------|
| 内核锁是 **advisory** | **编程约定** — 内核 **不会** 自动给数据结构加锁 |
| **voluntary** | 程序员 **必须主动** `lock` / `unlock` |
| **保护对象** | **数据**，不是「某函数」（→ Ch 9.4） |

| 反模式 | 后果 |
|--------|------|
| 路径 A 加锁、路径 B **裸访** 同一数据 | 锁 **完全无效** |
| 只锁 **写**、不锁 **读**（无 RCU 等） | 读者可能看到 **半更新** 状态 |
| 忘记 **unlock** | 死锁 |

#### 锁与上下文（Ch 7/8 衔接）

| 上下文 | 可用锁 |
|--------|--------|
| **hardirq / softirq / tasklet** | **`spinlock`** — 不可睡眠 |
| **进程上下文** | **spinlock** 或 **mutex** — 视临界区长度 |
| **ISR + 进程共享** | **`spin_lock_irqsave`** |

#### 设计原则（作者）

| 原则 | 说明 |
|------|------|
| **从简单开始** | 一把锁护整个结构 — 先正确 |
| **锁顺序全局一致** | 防 ABBA — Ch 9.5 |
| **临界区尽量短** | 持锁时不做 **无关工作** |
| **有争用再优化** | Ch 9.6 粒度 |

**HFT：** 热路径 **mutex** 在争用下会 **睡眠唤醒** — P99 杀手。短临界区用 **spinlock**；读多写少考虑 **RCU**（Ch 10）。用户态等价物：`std::mutex` vs `spinlock` vs `atomic`。
