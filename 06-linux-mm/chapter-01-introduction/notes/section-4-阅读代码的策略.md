# Ch 1 §4 阅读代码的策略 (Reading the Code)

> **Understanding the Linux Virtual Memory Manager** · Mel Gorman · **选读 🟡**
> 源码核验：Linux **v6.6**（`mm/oom_kill.c` / `mm/vmalloc.c` / `mm/page_alloc.c` / `mm/mmap.c`）

---

## 本节讲什么

本节回答一个核心问题：**第一次打开 `mm/`，从哪个文件开始读？**

作者给出了一条「由简入深」的路线，并明确反对从初始化代码读起。理解「为什么是这个顺序」，比记住「先读哪个文件」重要得多——因为它揭示的是**每个子系统的耦合度与独立性**。

---

## 1. 为什么不从「初始化代码」读起

很多老手建议从 boot / init 读（`start_kernel()` → `setup_arch()` → `paging_init()`），但作者认为**对 VM 不优**：

| 从 init 读 | 问题 |
|-----------|------|
| `arch/x86/kernel/setup.c` 的 `setup_arch()` | 高度依赖架构，`EFI`、`e820`、`SRAT`（NUMA 表）混在一起 |
| `paging_init()` | 依赖页表、`memblock`、内存模型的**前置知识**，而这些恰恰是你还没读的 |
| 早期分配 | 会撞上 `memblock`（Ch5）这种**临时分配器**，不是最终 VM 的常态 |

**核心判断：init 代码是「所有子系统第一次协同」的现场，耦合度最高。** 新手一头扎进去，会被架构细节和「还没建立的概念」同时淹没。作者的选择是**先读耦合度低、独立性强的子系统**，把基础概念逐个点亮，再回头去看 init 怎么把它们串起来。

---

## 2. 作者推荐的 VM 阅读路线（由简入深）

| 顺序 | 主题 | 源码入口 | 全书章节 | 为什么先读它（耦合度视角） |
|:----:|------|----------|----------|--------------|
| **1** | **OOM 管理器** | `mm/oom_kill.c` | [Ch 13](../../chapter-13-out-of-memory-management/) | 牵涉面广但逻辑**温和**：不碰页表、不碰 slab，只做「选一个进程杀掉」，是窥见 VM 一角的低门槛入口 |
| **2** | **非连续内存分配器** | `mm/vmalloc.c` | [Ch 7](../../chapter-07-noncontiguous-memory-allocation/) | 功能**基本封装在一个文件**，独立性强，且会用页表（学完 Ch3 可回头深化） |
| **3** | **物理页分配器** | `mm/page_alloc.c` | [Ch 6](../../chapter-06-physical-page-allocation/) | 代码**相对集中**：伙伴系统、zone、水位都在这里，是 VM 的「供血心脏」 |
| **4** | **VMA 与进程内存区域** | `mm/mmap.c` 等 | [Ch 4](../../chapter-04-process-address-space/) | 与用户态 `mmap`、进程地址空间直接相关，**贯通 syscall 到页表** |

```
推荐阅读流（本书作者 · 非 HFT 捷径）：

  oom_kill.c  →  vmalloc.c  →  page_alloc.c  →  mmap / VMA (Ch 4)
       │              │              │                    │
     Ch 13          Ch 7           Ch 6                 Ch 4
     "温和入口"    "单文件独立"   "供血心脏"          "贯通用户态"
```

**为什么这个顺序「由简入深」成立？** 四个子系统逐个看：

1. **OOM** 只做「选进程 → 杀进程」，几乎不依赖你还没读的页表/slab，**概念成本最低**；
2. **vmalloc** 是「分配一段虚拟连续、物理不连续的地址」，**把物理页分配器当黑盒用**，正好卡在「已懂 OOM、还没懂 page_alloc」之间；
3. **page_alloc** 是真正的**物理页供应者**，读完它，前面 vmalloc「黑盒」就打开了；
4. **VMA/mmap** 把**用户态请求**一路连到 page_alloc，是「全貌」的收口。

## 3. 每个入口点各自揭示什么

这条路线不只是「读四个文件」，每个入口点会**带出下一层概念**：

| 入口 | 读它时点亮的概念 | 通往 |
|------|------------------|------|
| `oom_kill.c` | `oom_score`/`oom_score_adj`、内存压力分级 | Ch13 OOM 全貌 |
| `vmalloc.c` | 虚拟地址空间 vs 物理页分离、`vm_struct` 区间树 | Ch7 + Ch9（kmap） |
| `page_alloc.c` | 伙伴系统、`struct zone` 水位、`per_cpu_pages` | Ch2（节点/区域）+ Ch6 |
| `mmap.c` | `vm_area_struct`、`mm_struct`、缺页路径 | Ch4 地址空间 + Ch3 页表 |

**读法要点：第一遍不求全懂，求「建立地图」。** 每个文件先抓「入口函数 → 核心数据结构 → 出口」三件事，细节留给对应章节精读。这正是本书「先读方法论、再逐章深入」的意图。

## 4. 与本仓库 HFT 精读捷径的对照

[README · HFT 精读捷径](../../README.md#hft-精读捷径) 按 **性能相关度** 排序：

```
Ch 2 → Ch 3 (+ THP) → Ch 8 → Ch 4 → Ch 10
```

| | **Ch 1 作者路线** | **HFT 捷径** |
|---|-------------------|--------------|
| 目标 | 第一次 **读源码** 不迷路 | **NUMA / 大页 / slab / 布局** 的理论依据 |
| 起点 | OOM → vmalloc → page_alloc | 物理内存描述 → 页表 → slab |
| 排序依据 | **耦合度**（由简入深） | **性能影响**（谁最影响延迟） |
| 关系 | 补「打开 `mm/` 从哪 FILE 开始」 | 补「为什么 HFT 要 mlock / 大页 / 绑 NUMA」 |

两条路**不矛盾**，是两个正交的维度：

- **作者路线**答「**怎么读**」——按**耦合度**从独立子系统切入，建立地图；
- **HFT 捷径**答「**读什么**」——按**性能影响**挑高价值章节精读。

**实际操作**：用 HFT 捷径挑**章节**，用作者路线决定**打开源码时从哪个 FILE 入手**。例如你要精读 Ch2（物理内存描述），先按作者路线快速扫一眼 `page_alloc.c` 建地图，再回头啃 `mmzone.h` 的 `struct zone` 字段。

<details>
<summary>代码自测（Q&A）</summary>

**Q1：为什么作者把 OOM 排在第一位，而不是「最重要」的 page_alloc？**
A：因为排序依据是**耦合度/概念成本**，不是重要性。OOM 逻辑**温和且独立**——不依赖页表、slab 这些你还没读的概念，先把「VM 里有哪些角色、内存压力怎么衡量」建立起来，再读耦合度更高的 page_alloc 就不慌。这跟「先学会走路再学跑」同理。

**Q2：`vmalloc` 为什么被描述为「把物理页分配器当黑盒」？**
A：`vmalloc` 的目标是「分配**虚拟连续**的地址」，它内部**调用** `__alloc_pages()` 拿物理页、再建页表映射，但它**不关心**这些页怎么来、伙伴系统怎么运作。所以你可以先把它当一个「能给我一段虚拟内存」的黑盒读，等读了 page_alloc 再回头打开这个黑盒。

**Q3：「从 init 读」错在哪，具体会卡在什么？**
A：`setup_arch()` / `paging_init()` 是**所有子系统第一次协同**的地方，同时依赖 EFI/e820/SRAT（架构）、memblock（临时分配器）、页表——**三个前置概念你都没读**。读 init 等于「一上来就做综合题」，而作者路线是「先做分项题」。

**Q4：作者路线和 HFT 捷径的「排序依据」本质区别是什么？**
A：作者路线按**耦合度**（谁独立先读谁），目的是**建立地图、不迷路**；HFT 捷径按**性能影响**（谁最影响延迟先读谁），目的是**快速拿到 HFT 需要的理论依据**。一个是「怎么读」，一个是「读什么」，正交不冲突。

**Q5：读 `page_alloc.c` 时，作者建议「第一遍只抓入口→数据结构→出口」，为什么？**
A：因为 `page_alloc.c` 是几千行的大文件，第一遍求全懂会陷进去。先抓三件事——**入口函数**（`__alloc_pages`）、**核心数据结构**（`struct zone`、`free_area`）、**出口**（返回 `struct page*`），建立「这个文件干什么」的骨架，细节留给 Ch2/Ch6 精读时再逐字段展开。

</details>
