# Learning eBPF · 第 1 章：什么是 eBPF，它为何重要

> 底本：`../LEARNING-EBPF-BILINGUAL.pdf`（Liz Rice, O'Reilly 2023，GPT 双语版）
> 本章是全书的地基章：讲清 eBPF 的来历、它与"改内核/写模块"两条老路的本质区别。

## 本章目标

1. 说清 eBPF 的定义：**可动态加载进内核、改变内核行为的自定义代码**
2. 从 BPF → eBPF 的演进时间线
3. 为什么传统路径（改内核源码、写内核模块）不能快速安全地扩展内核
4. eBPF 的三大用例：观测（observability）、网络、安全

## 1. 起源：1993 年的 BSD Packet Filter 论文

McCanne & Van Jacobson（劳伦斯伯克利实验室）提出"伪机器"运行过滤器程序——
用一套 32 位指令集（类汇编）决定网络包的接收/丢弃。论文原文示例：

```
ldh     [12]                       # 从包偏移 12 处加载 2 字节（以太网帧的 ethertype 字段）
jeq     #ETHERTYPE_IP, L1, L2      # 是 IP 包则跳 L1，否则跳 L2
L1:     ret     #TRUE              # 非零返回值 = 接收该包
L2:     ret     #0                 # 0 = 丢弃
```

**要点**：从第一天起，BPF 的核心思想就是"作者写自定义程序在内核里执行"——这比"抓包过滤器"这个名字的含义深远得多。

## 2. 演进时间线（记住这几个节点）

| 年份 | 内核 | 事件 |
|------|------|------|
| 1993 | — | BPF 论文（伪机器 + 指令集） |
| 1997 | 2.1.75 | BPF 进入 Linux，用于 tcpdump 高效抓包 |
| 2012 | 3.5 | **seccomp-bpf**：BPF 程序决定是否允许用户态系统调用——BPF 第一次跳出"包过滤" |
| 2014 | 3.18 | **eBPF**：指令集为 64 位重写、引入 maps、`bpf()` 系统调用、helper 函数、**验证器**。官方生日 2014-09-26（验证器+bpf syscall+maps 补丁集被接受） |
| 2015 | — | eBPF 可挂 **kprobes**，追踪革命起点；网络栈开始加 hook |
| 2016 | — | eBPF 工具进生产（Netflix/Brendan Gregg "superpowers"）；**Cilium** 发布（容器环境整条 datapath 换 eBPF） |
| 2017 | — | Facebook 开源 **Katran**（L4 负载均衡）；此后 facebook.com 每个包都过 eBPF/XDP |
| 2018 | — | eBPF 成为内核独立子系统（维护者 Borkmann/Starovoitov，后加 Nakryiko）；**BTF** 引入（可移植性） |
| 2020 | — | **LSM BPF**：第三大用例（安全）确立 |

指令数上限从 4096 → 100 万条已验证指令；尾调用/函数调用让限制实际失效。

## 3. eBPF 与 BPF 的称呼

- 内核源码和编程界面统一用 **BPF**：`bpf()`、`bpf_` 前缀 helper、`BPF_PROG_TYPE_*`
- 内核社区之外流行 **eBPF**（ebpf.io、eBPF Foundation）
- 两者如今可互换——现代内核全都支持"extended"部分

## 4. 内核与用户空间（底层视角）

- 应用跑在非特权用户态，通过 **syscall 接口**请求内核做事（文件、网络、内存、进程协调）
- `strace -c echo "hello"` 实测：一个 echo 触发 **111 次系统调用**（openat 30、mmap 20、newfstatat 19、close 20…）
- **推论**：应用与内核的交互面几乎等于应用的全部外部行为——在内核里插桩 = 看穿一切应用，且应用无感知、无需修改

## 5. 传统扩展内核的两条路（以及为什么不行）

**路径 A：改内核源码**
- 内核约 3000 万行代码，门槛极高
- 只有约 **1/3 的补丁被接受**，通常耗时 3-6 个月（Jiang et al. 2013 研究）
- 进入主线后还要等发行版采纳：写书时 RHEL 8.5（2021-11）用的还是 2018-08 的 4.18 内核——**从想法到生产环境以年计**

**路径 B：内核模块（LKM）**
- 不用进主线，可独立分发
- 但仍是**完整内核编程**：模块崩溃 = 整机崩溃；恶意/有漏洞的模块拥有全部特权数据访问权
- 用户天然不敢装陌生模块——没有安全性证明

**eBPF 的答案：验证器（verifier）**
- 加载时静态验证：不会崩溃、不会死循环锁死机器、不会越界访问数据
- 详见第 6 章

## 6. eBPF 的三大优势

1. **动态加载**：加载即生效，挂到事件上后**无论事件来自哪个进程都触发**——包括程序加载前就在跑的老进程；容器环境 = 节点上所有 Pod 的进程全可见
2. **高性能**：JIT 编译为本地机器指令执行；事件在内核里就被过滤，不用每个事件都付出内核态↔用户态切换代价。XDP 论文（CoNEXT '18）实测：XDP 路由比常规内核栈快 **2.5×**，负载均衡比 IPVS 快 **4.3×**
3. **零侵入**：不修改应用代码、不改配置、不重启

## 7. 云原生环境：对比 sidecar 模型

sidecar（如 Envoy 注入）的固有缺陷：
- 加 sidecar 要**重启 Pod**
- 依赖 YAML 注入流程，标注错了就漏掉 → 未被插桩
- Pod 内多容器 ready 顺序不可预测 → 启动变慢、竞态（Open Service Mesh 文档承认：Envoy ready 前应用流量全丢）
- 服务网格走 sidecar = 应用流量必须绕内核网络栈进代理容器，**加延迟**

eBPF 模型：内核插桩 → 节点全进程可见、动态加载、恶意程序逃不过（挖矿程序不会"贴心地"帮你注入 sidecar，但 eBPF 网络安全能监管主机所有流量）。

## HFT 关联

- **内核态过滤是核心卖点**：交易系统每秒百万级事件（ syscall、网卡包、调度事件），eBPF 在内核里先过滤再上送，避免了每事件一次 user/kernel 切换——这正是 HFT 观测工具（如 Pixie、Parca、Hubble）低开销的原因
- XDP 2.5×/4.3× 的数字是评估"内核栈 vs DPDK 旁路"时的基准参照：eBPF 拿到接近旁路的收益却保留内核栈的通用性
- 延迟抖动定位：eBPF 挂调度器/中断/网卡队列的 tracepoint，可以抓到 ntpd、页回收、内核锁竞争这类"偶发毫秒级毛刺"的元凶——传统 perf 抓不到的盲区
