# 2.1 图释 BPF

> 底本：《BPF之巅》第 2 章技术背景，2.1 节（印刷 p17）

## 本节定位

全书第二章开篇用一张图回答一个问题：**BPF 程序到底运行在哪里、和事件源、缓冲区、前端工具是什么关系**。这张"BPF 图释"是理解后续所有章节的地图——后面每一章的工具（CPU、内存、网络……）都是往这张图的不同事件源上"挂"程序。

## 图中的四个组成部分

| 组成部分 | 作用 | 对应技术 |
|---|---|---|
| 事件源 | 触发 BPF 程序执行的契机 | kprobes / uprobes / tracepoint / USDT / PMC / perf_events |
| 内核态 BPF 程序 | 事件发生时在内核中运行的小程序 | 经验证器校验后的 eBPF 字节码 |
| 缓冲区 | 内核态 → 用户态的数据传输 | perf_events 环形缓冲区 / BPF map |
| 前端工具 | 编译、加载、呈现结果 | BCC / bpftrace / perf(1) |

## 关键认知

1. **BPF 程序是"事件驱动"的**——不是常驻循环，而是事件发生时被调起运行的小程序。这决定了它天然适合观测（可观测性），而不是通用计算。
2. **数据处理尽量在内核完成**——直方图、计数、聚合都通过 map 在内核态做完，只把"结果"传回用户态，避免了传统跟踪器每事件一次内核↔用户态往返的开销（这也是 2.3 节论证 BPF 优于旧方案的核心）。
3. **事件源是可插拔的**——同一套 BPF 程序框架，换一个事件源就是另一类工具。第 2 部分各章的差异本质上就是事件源和所读内核状态的不同。

## HFT 关联

- HFT 低延迟系统的观测全景可以按这张图分类：哪个事件源最接近你的问题（收包 → 网卡/网络层探针；调度延迟 → sched tracepoint；锁竞争 → futex/uprobe）。
- "内核态聚合、只回传结果"对 HFT 尤其重要：行情风暴时每秒百万级事件，若每事件都拷贝到用户态，观测本身就会拖垮被观测系统。

## 自测

<details>
<summary>1. BPF 程序的执行时机是什么？</summary>

事件驱动的：事件源（探针/跟踪点/PMC 溢出等）触发时，内核调用挂载在该事件上的 BPF 程序。程序非常驻运行。
</details>

<details>
<summary>2. 为什么 BPF 工具强调"在内核态做聚合"？</summary>

避免每个事件一次内核↔用户态数据拷贝和系统调用开销。高频事件下（每秒百万级），用户态处理会把观测开销放大到不可接受，内核态直方图/map 聚合后只回传摘要。
</details>
