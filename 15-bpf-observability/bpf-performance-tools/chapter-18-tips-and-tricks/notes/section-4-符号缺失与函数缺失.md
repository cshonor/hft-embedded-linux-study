# 4. 常见问题二：符号缺失与函数缺失（18.9–18.10）

> 底本：《BPF之巅》第 18 章，18.9–18.10 节（印刷 p767–769）

## 18.9 打印时符号缺失（函数名称）

**症状**：调用栈或符号查找无法正确打印符号——不显示函数名，而是十六进制数字或 `[unknown]`。

三个原因：

1. **堆栈损坏**（18.8 节已解释）
2. **短命进程**：在 BPF 工具读取其地址空间并查询符号表之前就停止运行了
3. **没有可用的符号表信息**

JIT 运行时和 ELF 二进制文件的解决方法不同。

### 18.9.1 修复符号缺失：JIT 运行时（Java、Node.js…）

JIT 编译器有自己的**运行时会改变的符号表**，不是二进制文件预编译符号表的一部分。通常的修复方法：使用运行时生成的额外符号表，放在 **`/tmp/perf-<PID>.map`** 文件中，可被 perf(1) 和 BCC 读取。（注意事项与未来工作见 12.3 节。）

### 18.9.2 修复符号缺失：ELF 二进制文件（C、C++…）

编译好的二进制可能缺符号，**尤其是打包分发的**——它们被 `strip(1)` 处理过以降低文件大小。两种修复：

1. 调整构建过程**避免去除符号**
2. 使用另外的符号信息来源：**debuginfo** 或 **BTF**（BCC 和 bpftrace 支持 debuginfo 符号）

（注意事项与未来工作见 12.2 节。）

## 18.10 跟踪时函数缺失

**症状**：一个已知函数不能用 uprobes/uretprobes/kprobes/kretprobes 跟踪——表现为缺失或没有触发。问题可能是符号缺失（前面介绍过），也可能是**编译器优化**：

| 原因 | 机制 | 表现 |
|---|---|---|
| **内联（inlining）** | 函数指令被包含进调用函数内（少指令的函数为节省调用/返回/序言开销） | 函数符号可能完全消失，或存在但那段代码不触发 |
| **尾调用优化（TCO）** | A→B→C 且 C 是 B 的最后调用时，编译器让 C 直接返回给 A | C 的 **uretprobe/kretprobe 不会触发** |
| **静态和动态链接** | uprobe 在库中定义了函数，但目标软件从动态链接切到静态链接（函数位置变了，现在位于二进制文件中）；反之亦然 | 探针地址失效 |

**处理方法**：跟踪一个**不同的事件**——父函数、子函数或邻居函数。kprobes 和 uprobes 也支持**指令偏移跟踪**（bpftrace 将来也应该支持）：如果知道偏移量，内联函数的位置也可以被插桩。

## HFT 关联

- 交易系统二进制**构建时保留符号**（不 strip，或单独分发 debuginfo/BTF 包）是 BPF 可观测性的前提；发布流程要显式检查这一点
- Java 策略服务：确保 perf-map 代理（如 perf-java-flames）可用，否则栈全是地址
- 排查"探针不触发"先查三件事：内联（objdump 看符号）、尾调用（retprobe 不触发）、静态链接（ldd / nm 定位函数实际位置）
