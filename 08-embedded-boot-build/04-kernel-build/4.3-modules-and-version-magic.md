# 模块版本魔法：`insmod` 报 `version magic` 到底在说什么

> **本节讲什么：** 内核模块与运行内核之间的"版本契约"，以及模块是怎么被自动加载的。
> **前置：** [4.2 交叉编译实战](./4.2-cross-compile-pi5.md)  
> **下一节点：** [05-rootfs](../05-rootfs/)  
> **卡住查书：** MELP Ch4 · LDD3 Ch2

## 一个必然会遇到的问题

```bash
$ sudo insmod mydrv.ko
insmod: ERROR: could not insert module mydrv.ko: Invalid module format
$ dmesg | tail -3
mydrv: version magic '6.12.20-v8-16k SMP preempt mod_unload aarch64' should be
'6.12.25-v8+ SMP preempt mod_unload aarch64'
```

**含义：** 这个 `.ko` 是为 `6.12.20-v8-16k` 编的，但当前跑的是 `6.12.25-v8+`。内核拒绝加载。

---

## vermagic 里有什么

```
6.12.20-v8-16k   SMP   preempt   mod_unload   aarch64
└── 版本号 ──┘   └SMP┘ └抢占模式┘ └允许卸载┘   └─ 架构 ─┘
```

| 字段 | 来源 | 说明 |
|------|------|------|
| 版本号 | `uname -r`（`UTS_RELEASE`） | 内核源码树版本 + `CONFIG_LOCALVERSION` |
| SMP | `CONFIG_SMP` | 是否对称多处理 |
| preempt | `CONFIG_PREEMPT*` | 抢占模型（`preempt` / `none` / `rt`） |
| mod_unload | `CONFIG_MODULE_UNLOAD` | 是否允许 `rmmod` |
| aarch64 | 架构 | — |

**任何一项不同 → 拒绝加载。** 这不是内核"太挑剔"：模块直接链接到内核符号、使用内核内部结构布局，配置不同意味着**内存布局可能不同**，强行加载 = 随机踩内存。

```bash
# 查看模块的 vermagic
modinfo mydrv.ko | grep vermagic

# 查看当前内核
uname -r
```

## 怎么保证匹配

| 做法 | 说明 |
|------|------|
| **同一棵树编译** | 模块用的内核源码树 == 目标运行内核的源码树（推荐） |
| 用目标内核的 headers | `KDIR=/lib/modules/$(uname -r)/build`（本机编译时最稳） |
| **本机编译** | 在 Pi 上直接 `make`，天然一致，最省心 |
| 交叉编译时 | `INSTALL_MOD_PATH` 指向目标 rootfs，且**内核与模块一次构建** |

```makefile
# 本机编译（Pi 上）—— 最不容易出错
KDIR ?= /lib/modules/$(shell uname -r)/build
all:
	make -C $(KDIR) M=$(PWD) modules
```

```bash
# 交叉编译（主机上）—— KDIR 指向你编译的那棵树
make -C /path/to/rpi-linux M=$(PWD) ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules
```

## `/lib/modules/$(uname -r)` 目录结构

```
/lib/modules/6.12.25-v8+/
├── kernel/              # 各子系统的 .ko
│   ├── drivers/...
│   └── net/...
├── modules.dep          # 依赖关系（depmod 生成）★
├── modules.alias        # 设备别名 -> 模块（自动加载靠它）★
├── modules.symbols
├── modules.builtin      # 编进内核的模块清单
└── build -> /path/to/src   # 指向源码树（编译外部模块时需要）
```

**改了模块必须重跑 `depmod`：**

```bash
sudo depmod -a                          # 当前内核
sudo depmod -a 6.12.25-v8+              # 指定版本
```

## 模块是怎么被自动加载的

```
内核枚举设备（PCI / DT / USB / ACPI）
        │
        ▼
生成 modalias 字符串，如：
   pci:v00001106d00003038sv...
   of:NmydevT(null)Cwzp,my-device      ← 设备树设备的 modalias
        │
        ▼
内核发 uevent 给用户态 udev
        │
        ▼
udev 查 /lib/modules/.../modules.alias，找到匹配的 .ko
        │
        ▼
modprobe <module>    ← 自动解析依赖并加载
```

### `insmod` vs `modprobe`

| | `insmod` | `modprobe` |
|--|---------|-----------|
| 依赖处理 | ❌ **不管**，缺依赖直接失败 | ✅ 自动先加载依赖 |
| 模块查找 | 需要完整路径 | 按名字在 `/lib/modules/$(uname -r)` 下找 |
| 用途 | 调试、开发 | **日常使用** |

```bash
sudo modprobe mydrv          # 自动处理依赖
sudo modprobe -r mydrv       # 卸载（含不再被依赖的依赖）
lsmod                        # 看已加载
modinfo mydrv                # 看模块信息（依赖、参数、vermagic）
```

**模块参数：**

```c
static int debug = 0;
module_param(debug, int, 0644);       /* /sys/module/mydrv/parameters/debug */
MODULE_PARM_DESC(debug, "Enable debug output");
```

```bash
sudo modprobe mydrv debug=1
# 或运行时（若权限允许）
echo 1 | sudo tee /sys/module/mydrv/parameters/debug
```

## `CONFIG_MODVERSIONS`：可选的宽容模式

开启后，内核为每个导出符号记录 **CRC 校验值**，模块加载时比对：

- 只有**实际用到的符号**变了才拒绝；
- 允许小版本差异（只要 API 语义未变）。

**代价：** 需要在**同一个 `.config`** 下编译模块；而且它只检查符号 CRC，**不检查结构体布局**。发行版常用，嵌入式/自研内核通常**不开**（宁可严格失败也不要随机崩溃）。

---

## HFT / 嵌入式关联

- **"版本即契约"这条纪律在部署里反复出现**：容器镜像 tag、HFT 交易二进制与其链接的库版本、FPGA bitstream 与驱动版本——**不一致就快速失败**，好过运行期随机出错。内核的 vermagic 是这种设计哲学最严格的体现。
- **`modprobe` 的依赖解析** 本质是静态图拓扑排序，与包管理器、systemd 的依赖解析同源。理解一次，到处能用。
- 生产环境常把关键驱动编进内核（`=y`）而非模块：省掉加载环节、避免 rootfs 损坏导致驱动缺失，**启动路径更短更确定**。

## 代码自测

<details>
<summary>Q1：<code>insmod</code> 报 <code>version magic</code> 不匹配，最快的解决方式是什么？</summary>

**在目标机上用 `/lib/modules/$(uname -r)/build` 重编模块**（本机编译），天然一致。
若必须交叉编译，则内核源码树必须与目标运行内核**完全一致**（同一次 checkout + 同 `.config` + 同 `LOCALVERSION`）。
临时绕过可用 `modprobe --force-vermagic`（** debug 用，生产禁用 **）。
</details>

<details>
<summary>Q2：拷了 .ko 到目标板，<code>modprobe</code> 却说找不到该模块？</summary>

`modprobe` 按名字在 `/lib/modules/$(uname -r)/` 下查找，需要：
1. `.ko` 放到 `/lib/modules/$(uname -r)/kernel/...` 下（不是随便一个目录）；
2. **跑过 `depmod -a`** 生成 `modules.dep` / `modules.alias`。

用完整路径 `insmod /path/to/mydrv.ko` 可绕过，但不处理依赖。
</details>

<details>
<summary>Q3：为什么不推荐用 <code>--force-vermagic</code>？</summary>

vermagic 不匹配意味着内核配置/版本不同，**结构体布局、函数签名可能已经变了**。
强行加载后模块会按错误的偏移读写内核内存 → 随机崩溃、数据损坏，而且**极难排查**（症状与原因相隔很远）。
宁可构建流程做对，也不要运行期赌运气。
</details>
