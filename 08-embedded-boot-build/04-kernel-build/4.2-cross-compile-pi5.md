# Pi 5 交叉编译实战：从拉源码到替换运行内核

> **本节讲什么：** 在 x86 主机（或 WSL）上交叉编译 Pi 5 内核并让它真正启动起来，**含回滚方案**。
> **前置：** [4.1 Kconfig](./4.1-defconfig-and-kconfig.md) · [02-toolchain](../02-toolchain/)  
> **动手：** [P5 · B1](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)  
> **卡住查书：** MELP Ch4 · 官方 [Building the kernel](https://www.raspberrypi.com/documentation/computers/linux_kernel.html)

---

## 一句话流程

```
拉源码 → bcm2712_defconfig → (裁剪) → 交叉编译 → 装模块 → 拷镜像/DTB → 改 config.txt → 重启
```

---

## 1. 拉源码

```bash
# 官方树（分支随版本调整，写本文时是 rpi-6.12.y）
git clone --depth=1 --branch rpi-6.12.y https://github.com/raspberrypi/linux
cd linux
```

`--depth=1` 省时间省空间（完整树几个 GB）。**注意分支要与板子上的固件版本大致匹配。**

---

## 2. 配置

```bash
export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

make bcm2712_defconfig          # Pi 5 的厂商基线
make menuconfig                 # 可选：裁剪
```

想基于**当前运行内核**的配置起步（最省事）：

```bash
# 在 Pi 上导出当前配置
zcat /proc/config.gz > .config      # 需要 CONFIG_IKCONFIG_PROC
# 拷回主机后
make olddefconfig
```

---

## 3. 编译

```bash
make -j$(nproc) Image.gz modules dtbs
```

| 目标 | 产物 | 说明 |
|------|------|------|
| `Image.gz` | `arch/arm64/boot/Image.gz` | 压缩内核镜像 |
| `modules` | 各目录 `.ko` | 可加载模块 |
| `dtbs` | `arch/arm64/boot/dts/broadcom/*.dtb` | 设备树二进制，**必须与内核同源** |

**校验产物：**

```bash
file arch/arm64/boot/Image.gz                       # gzip compressed data
ls -la arch/arm64/boot/dts/broadcom/bcm2712-rpi-5-b.dtb
```

---

## 4. 安装模块与头文件

```bash
# 挂载 Pi 的 rootfs（SD 卡第二分区）到 /mnt/rootfs
sudo mount /dev/sdb2 /mnt/rootfs

sudo make INSTALL_MOD_PATH=/mnt/rootfs modules_install
# -> /mnt/rootfs/lib/modules/6.12.x-v8-16k/
```

`modules_install` 会顺带跑 `depmod`，生成 `modules.dep`、`modules.alias` 等（若交叉环境没跑，需在 Pi 上补一次 `sudo depmod -a`）。

---

## 5. 部署镜像与 DTB

```bash
sudo mount /dev/sdb1 /mnt/boot      # boot 分区（FAT）

# 内核：换个名字，不要覆盖官方的，方便回滚
sudo cp arch/arm64/boot/Image.gz /mnt/boot/kernel-my.img
sudo cp arch/arm64/boot/dts/broadcom/bcm2712-rpi-5-b.dtb /mnt/boot/
sudo cp -r arch/arm64/boot/dts/overlays /mnt/boot/
```

**`config.txt` 里指定：**

```
kernel=kernel-my.img
```

> **★ 回滚方案（必须先准备好）：** 不覆盖原 `kernel8.img`，用独立文件名 + `kernel=` 指定。  
> 起不来时把 SD 卡插回电脑，改回 `kernel=kernel8.img`（或删掉这一行）即可。  
> **别一上来就覆盖原内核 —— 刷坏内核虽然不如刷坏 EEPROM 严重，但一样要重刷卡。**

---

## 6. 验证

```bash
uname -a                 # 应显示你编译的版本与编译时间
cat /proc/version        # 含 GCC 版本、SMP PREEMPT 等
zcat /proc/config.gz | grep CONFIG_PREEMPT   # 确认配置生效
dmesg -T | head -30      # 看早期启动消息
```

## 常见错误对照表

| 现象 | 原因 / 处理 |
|------|------------|
| `aarch64-linux-gnu-gcc: command not found` | 没装交叉编译器（见 [02-toolchain](../02-toolchain/)） |
| `make: *** No rule to make target 'bcm2712_defconfig'` | 分支不对（拉错树）或 ARCH 没设 |
| 编译出的镜像是 x86 的 | 忘了 `ARCH=arm64` / `CROSS_COMPILE` |
| 启动卡在 `Starting kernel ...` | DTB 与内核不匹配 / 串口配置错 / `config.txt` 里 kernel 路径错 |
| `Kernel panic - VFS: Unable to mount root fs` | 存储或文件系统驱动编成了 `=m`（见 [4.1](./4.1-defconfig-and-kconfig.md)） |
| 模块版本不匹配 `version magic` | `.ko` 与运行内核不是同一次构建（见 [4.3](./4.3-modules-and-version-magic.md)） |
| 启动后外设不工作 | DTB 没更新，或 `overlays` 没拷 |

## 时间预期（参考）

| 环境 | 首次全量编译 |
|------|------------|
| 8 核 x86 主机 | 10–25 分钟 |
| 4 核笔记本 | 30–60 分钟 |
| **Pi 5 本机编译**（`make -j4`） | **1–2 小时** |

改一个驱动后增量编译通常几十秒。**但改了 `.config` 会触发大面积重编。**

---

## HFT / 嵌入式关联

- **"别覆盖原内核"这条纪律**，与 HFT 部署的"蓝绿发布 / 快速回退"是同一个原则：任何变更都要有**一次操作即可回退**的路径。
- **本机编译 vs 交叉编译**：Pi 5 其实够快，本机编译能省掉"版本不匹配"的一大类问题（模块、头文件天然一致）。只有需要频繁构建或做 CI 时才必须交叉。
- 编译产物必须与**运行内核严格同源** —— 这个"版本即契约"的纪律后面在 rootfs（[05-rootfs](../05-rootfs/)）和模块（[4.3](./4.3-modules-and-version-magic.md)）会反复遇到。

## 代码自测

<details>
<summary>Q1：为什么 <code>dtbs</code> 必须和内核一起编？</summary>

DTB 里的 `compatible` 字符串要与驱动里的 `of_device_id` 表匹配，而驱动是内核的一部分。
内核与 DTB 版本不一致 → 某些节点匹配不上 → 设备不 probe 或行为异常，**且不报错**。
所以官方流程里 `make ... modules dtbs` 是一体的。
</details>

<details>
<summary>Q2：不覆盖原内核、用 <code>kernel=</code> 指定的好处是什么？</summary>

**回滚成本降到一次文本编辑**：新内核起不来时，把 SD 卡插回电脑改 `config.txt`（或删掉 `kernel=` 行回落到默认），立刻能启动。
若直接覆盖原内核，则必须重新编译或从备份恢复。这是 bring-up 阶段最重要的保险。
</details>

<details>
<summary>Q3：<code>INSTALL_MOD_PATH</code> 不设会怎样？</summary>

模块会被安装到**主机**的 `/lib/modules/$(uname -r)` —— 可能污染甚至破坏主机系统。
交叉编译时**必须**指向目标 rootfs 的挂载点。这是最容易酿成事故的疏忽之一。
</details>
