# sysroot 与 C 库：交叉编译里最容易搞错的一件事

> **本节讲什么：** sysroot 是什么、为什么它是「目标板的根文件系统副本」，以及 glibc / musl / 静态链接怎么选。
> **前置：** [2.1 为什么交叉](./2.1-why-cross-and-triple.md)
> **动手：** [P5 · D1](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch2 · Primer Ch13

## 一句话

**sysroot = 目标系统根目录的一份拷贝。** 编译器找头文件和库时，不是去宿主机的 `/usr/include`、`/usr/lib`，而是去 `<sysroot>/usr/include`、`<sysroot>/usr/lib`。

```
宿主机                                    sysroot（目标板的 /）
/usr/include/stdio.h   ← 不找这里        <sysroot>/usr/include/stdio.h  ← 找这个
/usr/lib/libc.so.6     ← 不找这里        <sysroot>/usr/lib/libc.so.6    ← 找这个
```

**不设 sysroot 会怎样？** 交叉 gcc 一般不会去吃宿主机的 x86 头文件（binutils 编好了不会），它会报 `cannot find -lc` / `stdio.h: No such file` —— 这是**好消息**，因为它报错了。真正危险的是**设错 sysroot**（指向了错误版本的目标根），那才是编译通过、运行崩溃。

## 搜索路径是怎么算出来的

```bash
# 看编译器到底去哪些目录找头文件
aarch64-linux-gnu-gcc -print-sysroot                    # 默认 sysroot（可能为空）
aarch64-linux-gnu-gcc --sysroot=/opt/pi-rootfs -E -v -  < /dev/null 2>&1 | sed -n '/#include <...>/,/End of search/p'

# 看它链接时搜哪些库目录
aarch64-linux-gnu-gcc --sysroot=/opt/pi-rootfs -print-search-dirs | tr ':' '\n' | head -20
```

`--sysroot=DIR` 的效果等价于：把 `/usr/include`、`/lib` 这些**绝对路径**都重定向到 `DIR/usr/include`、`DIR/lib`。

⭐ 一个附带好处：**`-I` 和 `-L` 也可以写成绝对路径，但一旦用了 `--sysroot`，那些绝对路径也会被重定向** —— 这在移植第三方包时经常造成"我明明指定了路径却找不到"的困惑，记得先 `-print-sysroot`。

## 三种 C 库怎么选

| | glibc | musl | 静态链接（任一） |
|--|-------|------|-----------------|
| 体积 | 大（几 MB） | 小（几百 KB） | 最大（每份二进制各带一份） |
| 兼容性 | 最好，闭源模块/NSS 都行 | 部分软件不支持（尤其 NSS、部分 locale） | 无运行时依赖 |
| 启动速度 | 一般 | **略快**（无 NSS 动态加载） | **最快**（无 `ld.so` 符号解析） |
| 适合 | 通用 Linux、Pi OS | 极简 rootfs、容器 | 单二进制工具、initramfs 里的急救程序 |

**嵌入式 bring-up 阶段的实用选择：**

- 学习主线 → **glibc**（跟发行版一致，遇到问题资料最多）
- 做极小 rootfs → **musl**（Buildroot 里一个配置项的事）
- initramfs 里的 `/init`、急救 shell → **静态 busybox**（rootfs 还没挂起来时，动态库根本不存在）

## 静态 vs 动态：怎么判断自己该用哪个

```bash
# 静态
aarch64-linux-gnu-gcc -O2 -static -o hello_s hello.c
file hello_s          # statically linked, ... not stripped

# 动态（默认）
aarch64-linux-gnu-gcc -O2 -o hello_d hello.c
aarch64-linux-gnu-readelf -d hello_d | grep NEEDED   # → libc.so.6
aarch64-linux-gnu-readelf -d hello_s | grep NEEDED   # → 无输出（不依赖任何 .so）
```

| 场景 | 选 | 理由 |
|------|----|------|
| initramfs 里的程序 | **静态** | 真正的根还没挂，动态库找不到 |
| 应用（rootfs 已就绪） | 动态 | 省空间，多个程序共享一份 libc 页框 |
| 只有一个程序的产品 | 静态 | 整个 rootfs 就是它自己 |
| 大量 fork/exec 的系统 | 动态 | 共享库页框能显著降低内存与页缓存压力 |

⚠️ **`-static` 不是万能的**：glibc 的 `getaddrinfo()`、`getpwnam()` 这类走 **NSS**（动态加载 `libnss_*.so`）的函数，静态链接时会告警 `warning: Using 'getaddrinfo' in statically linked applications requires at runtime the shared libraries from the glibc version used for linking`。这不是可忽略的警告 —— 目标板上 glibc 版本不同就会失败。**要静态就用 musl，不要静态 glibc。**

## 内核头文件 vs libc 头文件（两回事）

```
<sysroot>/usr/include/linux/*.h     ← 内核 UAPI 头文件：给内核和用户程序看的 ABI 契约
<sysroot>/usr/include/sys/*.h       ← glibc 头文件：C 库接口
```

规则：**写用户态程序不要 include 内核源码树里的头文件**，要用发行版/工具链提供的、已 sanitize 过的 UAPI 头（`make headers_install` 产出的那套）。混用会导致结构体定义冲突（`struct stat`、`struct sigset_t` 都是重灾区）。

内核模块编译则是另一回事 —— 它需要**内核源码树**里 `include/` 下的**内部**头（不是 UAPI），而且必须与运行内核同一版本（见 [4.3 vermagic](../04-kernel-build/4.3-modules-and-version-magic.md)）。

## 实操：用 Buildroot 拿一份"同源"工具链

```bash
git clone https://github.com/buildroot/buildroot && cd buildroot
make raspberrypi5_defconfig
make menuconfig          # Toolchain → 选 glibc/musl、gcc 版本、是否开启 C++
make sdk                 # 产出工具链 SDK（一个自解压包）

ls output/images/*sdk-buildroot*.tar.gz
tar -xzf output/images/*sdk-buildroot*.tar.gz -C /opt
/opt/*/bin/*-gcc --version
```

⭐ 这条路的唯一理由：**工具链的 glibc 和 rootfs 的 glibc 是同一次构建产出的**，从根上消灭 `GLIBC_2.xx not found`。代价是要先会一点点 Buildroot（见 [05-rootfs](../05-rootfs/)）。

## HFT / 嵌入式关联

- **sysroot 就是"环境 pin"的实体形态**。HFT 生产机上同样需要一个"这台机器到底装了什么"的确定答案 —— 区别在于 HFT 用容器/镜像固化，嵌入式用 sysroot 固化，**本质是同一件事：把依赖从"主机状态"变成"显式声明的产物"**。
- **静态链接省掉 `ld.so` 的动态符号解析**对启动延迟敏感的场景是有意义的：进程启动时 `ld.so` 要做符号重定位（尤其 C++ 大量模板符号），这是几十到几百微秒的纯开销。交易进程通常用**静态链接 + 预链接**或直接避免频繁 exec。
- 「编译期不报、运行期才炸」的成本在交易系统里是**按秒计费的停机**。所以交叉编译养成的习惯（查 `NEEDED`、查 `GLIBC_x.yy` 需求、记录编译选项）直接可以平移到生产发布检查清单里。

<details>
<summary>Q1：不设 <code>--sysroot</code> 时，交叉 gcc 会去哪找头文件？</summary>

取决于发行版怎么打包它。Debian/Ubuntu 的 `gcc-aarch64-linux-gnu` 通常是**把目标头文件装到 `/usr/aarch64-linux-gnu/`** 下，binutils 内部就认这个前缀（等价于内置了一个 sysroot）。

所以你会看到"没设 sysroot 也能编过"—— 那是因为**工具链自带了一个默认 sysroot**，它里面有一份目标 libc（通常由 `libc6-dev-arm64-cross` 包提供）。

⚠️ 危险在于：**这份默认 sysroot 的 glibc 版本，未必等于你目标板 rootfs 的 glibc 版本**。所以它只是"能编过"，不代表"能在板子上跑"。
</details>

<details>
<summary>Q2：为什么静态链接 glibc 时 <code>getaddrinfo()</code> 会告警？</summary>

因为它走 **NSS（Name Service Switch）**，运行时会 `dlopen("libnss_files.so.2")` 之类的模块。`dlopen` 在静态二进制里不可用，所以要么功能失效，要么强依赖"板子上的 glibc 版本恰好和编译时一样"。

glibc 官方文档明确说：**静态链接的 glibc 程序，用到 NSS/iconv/locale 的功能是 unsupported**。

→ 结论：**要静态就用 musl**（它把 NSS 简化掉了），别跟 glibc 的静态链接较劲。
</details>

<details>
<summary>Q3：内核模块编译为什么不能用 sysroot 里的头文件？</summary>

因为模块是**内核的一部分**，它要用的不是"用户态看到的 ABI 契约"（UAPI 头），而是**内核内部数据结构**（`struct task_struct`、`struct file_operations` 的完整定义）。

这些东西：
1. 不在 UAPI 头里（`include/uapi/` 只是对外契约，内部头在 `include/linux/`）；
2. **逐版本变化**，必须和目标运行内核**逐字节同源**。

所以模块编译走的是 `make -C /lib/modules/$(uname -r)/build M=$PWD`，指向**内核源码树**而不是 sysroot。这也是 [4.3 vermagic](../04-kernel-build/4.3-modules-and-version-magic.md) 要解决的"版本魔法"问题的根源。
</details>
