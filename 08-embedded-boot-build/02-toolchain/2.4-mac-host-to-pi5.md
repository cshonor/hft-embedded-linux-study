# 宿主机是 Mac（Apple Silicon）：三种构建路径怎么选

> **本节讲什么：** 你手边最快的机器是 M 系列 Mac，它跑 macOS；目标是 Linux/aarch64。
> 这一节回答「**什么东西该在哪台机器上编**」，给出每条路径的确切命令，以及各路径里**唯一会让你白干一天的那个坑**。
> **前置：** [2.1 三元组](./2.1-why-cross-and-triple.md) · [2.2 sysroot 与 C 库](./2.2-sysroot-and-libc.md) · [2.3 三道检查](./2.3-verify-and-pitfalls.md)
> **动手：** [P5 · Phase B](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch2 · Primer Ch12

---

## 先看结论：按产物选机器，不按"哪台快"

| 要编的东西 | 在哪编 | 为什么是它 |
|---|---|---|
| 用户态 C 程序 / 库 | **Mac 上的 arm64 Linux 容器** | 原生速度（不模拟）+ ABI 天然一致 |
| **内核模块 / 驱动** | ★ **Pi 上本地编译** | 必须与**运行中的内核**同源，交叉编零收益、纯受罪 |
| 完整内核 / U-Boot / DTB | arm64 Linux 容器（或 Pi 本地，慢） | macOS 原生编有两个硬伤，见路径 B |
| 整包 rootfs | Buildroot，跑在容器里 | 见 [05-rootfs](../05-rootfs/) |

⚠️ 最后一行"整包 rootfs"里的 Buildroot **也别在 macOS 原生跑**（同样的大小写问题）。

## 为什么 Mac 原生编的不能直接丢给 Pi：三重不匹配

常见说法是"架构一样，只是 libc 不同"，**这个说法只对了一小部分**。真实隔阂有三层：

| 层 | macOS（Apple clang） | Linux/aarch64 |
|---|---|---|
| **二进制格式** | **Mach-O** | **ELF** |
| **系统调用接口** | Darwin syscall（Mach 陷阱） | Linux `svc #0` + `x8` 存调用号 |
| **C 库 / ABI** | libSystem（dyld） | glibc / musl（ld.so） |

> 第三层还有个细节：Darwin 的 arm64 调用约定**把 `x18` 保留给平台**（AAPCS64 里它是临时寄存器）。
> 所以严格说连 ABI 都不是同一套，只是绝大多数 C 代码碰不到这个差别。

**于是"架构相同"真正带来的好处只有一个，但很值钱：**

> Apple Silicon 上 Docker Desktop 起的 Linux VM 本身就是 aarch64。
> 跑 **arm64 镜像时不需要 QEMU 翻译，是原生速度**。
> 这是 Mac 相对 x86 宿主机的巨大优势——x86 机器上同样的容器要全指令模拟，慢 3–4 倍。

**别把"架构相同"理解成"可以不用交叉"。** 你仍然需要一套 Linux 目标环境，只是这次它可以跑得飞快。

## 路径 A：Mac 上跑 arm64 Linux 容器（推荐）

### 一键命令

```bash
# 宿主机（macOS）
docker run -it --rm --platform linux/arm64 \
  -v "$PWD:/work" -w /work \
  debian:trixie bash

# ---- 容器内 ----
apt update && apt install -y build-essential file

gcc -o hello hello.c
file hello
# hello: ELF 64-bit LSB executable, ARM aarch64, dynamically linked ...
```

⭐ **一个常见误解：** 容器里**不需要**装 `gcc-aarch64-linux-gnu`。
那个包是"在 x86 机器上交叉编 arm64"用的；**arm64 容器里的发行版 `gcc` 本身就是 aarch64 目标**，
再装一个交叉编译器只会让你分不清自己到底在用哪个。

```bash
# 容器内确认一下，心里有底
gcc -dumpmachine      # → aarch64-linux-gnu
```

### ★ 唯一会让你白干一天的坑：容器其实是 x86_64

如果容器跑的是 **amd64** 镜像（在 QEMU / Rosetta 下模拟），里面的 gcc 就是 x86-64 编译器，
**产出的 ELF 拷到 Pi 上直接 `Exec format error`**——而编译过程一切正常，零警告。

怎么踩进去的：

- 该镜像只有 amd64 版本，Docker 自动降级；
- **或者你的 `~/.zshrc` 里还留着 `export DOCKER_DEFAULT_PLATFORM=linux/amd64`**
  ——这是 M1 早期广为流传的"万能修复"，很多人的配置里至今还躺着，它会让你**所有**容器都跑模拟。

**三重验证（每次开新容器花 10 秒）**：

```bash
docker run --rm debian:trixie uname -m                       # 必须 aarch64
docker image inspect debian:trixie --format '{{.Architecture}}'   # 必须 arm64
file ./hello                                                 # 必须 ARM aarch64
```

启动时的告警就是信号，看见它立刻停手：

```
WARNING: The requested image's platform (linux/amd64) does not match
         the detected host platform (linux/arm64/v8)
```

> **体感判据**：如果你没开 Rosetta、编译又莫名慢得离谱——你大概率在模拟。
> 这个信号比任何命令都快。

### 另外两条

- **大工程别在 bind mount 里编。** `-v` 挂进去的目录走 virtiofs，跨文件系统 I/O 很慢。
  编内核这类活，放**容器内的命名卷**，或者干脆去 Pi 上编。
- **产物仍要走 [2.3 的三道检查](./2.3-verify-and-pitfalls.md)。** 容器只是让第一道（架构）更容易对，
  第二道（glibc 版本需求）照样可能翻车——容器里 `debian:trixie` 的 glibc 比你 Pi 上的新时，就会翻。

## 路径 B：macOS 原生交叉工具链（不装 Docker 时）

```bash
brew tap messense/macos-cross-toolchains
brew install aarch64-unknown-linux-gnu

aarch64-unknown-linux-gnu-gcc -o hello hello.c
file hello     # → ELF ... ARM aarch64
```

**优点**：不用起容器，编译速度快，编辑器/IDE 里直接就能用。
它是 crosstool-NG 编出来的完整 glibc 工具链，**自带 sysroot**，
不像 2.2 里说的"手工拼 sysroot"那么麻烦。

**★ 版本核对（这是 2.1 那条铁律的实际用法）：**

这套工具链的 glibc 是 **2.28**（tap 构建配方里写死的）。你的 Pi 5 跑 Debian 13（trixie），glibc 在 2.4x 量级：

```bash
# 在 Pi 上确认
ldd --version | head -1
```

`2.28 ≤ 2.4x` —— **满足"工具链 glibc ≤ 目标 glibc"，所以编出来的程序能跑。**
反过来（目标比工具链老）才会踩 `version 'GLIBC_2.xx' not found`。
这就是为什么这一条一定要拿数字对，而不是"感觉差不多"。

**适合**：用户态程序、库、CI 构建。

### ⚠️ 不适合编内核，而且原因不是工具链不行

是 **macOS 作为 host** 有两个硬伤：

**1. APFS 默认不区分大小写，而内核源码树里有仅大小写不同的文件。**

典型的如 `xt_connmark.h` 与 `xt_CONNMARK.h`。在不区分大小写的卷上 clone，
这两个文件**只剩一个**——于是某处 `#include` 报"头文件找不到"，
而你在源码树里 `ls` 分明看见了它。这类报错能把人绕晕半天。

内核文档自己都为此打了补丁（`Documentation/translations/zh_CN/how-to.rst`），原话大意是：
> macOS 默认使用不区分文件名大小写的 APFS 卷，而内核源码树中存在仅大小写不同的文件。

解法是建一个大小写敏感卷，在上面重新 clone：

```bash
diskutil apfs list                        # 找到容器标识符，如 disk3
diskutil apfs addVolume disk3 APFSX Linux # 新建大小写敏感卷
# 然后把内核源码 clone 到 /Volumes/Linux 下
```

**2. Apple 自带的 `make` 是 3.81，内核要求 GNU make ≥ 4.0。**

```bash
brew install make     # 装完叫 gmake，不叫 make
gmake ARCH=arm64 ...  # 必须敲 gmake
```

外加一堆 host 侧工具依赖（openssl 头、libelf 等）版本也和 Linux 发行版不一致。

> **结论：内核别在 macOS 原生编。** 用容器，或者在 Pi 上本地编。
> 你在 macOS 上"省下"的时间，会加倍还给这两条。

## ★ 路径 C：内核模块 / 驱动就在 Pi 上编（这条最容易被搞反）

常见建议是"Pi 性能弱，编译慢，所以能交叉就交叉"。
**对完整内核成立，对内核模块不成立。**

原因是模块不是普通程序：它被链接进**内核地址空间**，必须和运行中的内核**同源**——
同版本、同 `.config`、同编译器族。见
[4.3 vermagic](../04-kernel-build/4.3-modules-and-version-magic.md)。

交叉编一个模块意味着：

1. 把整棵**已配置好**的内核构建树（几 GB）搬到 Mac 上；
2. 保证 Mac 上的编译器版本与编内核那台一致；
3. 保证 `.config` 一字不差。

**收益为零，风险很高。** 而 Pi 5 上编一个模块就几秒：

```bash
# Raspberry Pi OS
sudo apt install raspberrypi-kernel-headers
# Debian 通用
sudo apt install linux-headers-$(uname -r)

# 驱动目录下
make -C /lib/modules/$(uname -r)/build M=$PWD modules
sudo insmod mydrv.ko
```

`/lib/modules/$(uname -r)/build` 就是 Pi 自己准备好的那棵树——
**用它编出来的模块不可能版本不匹配，这是最省心的做法。**

> **Pi 5 的额外一点：** 它的内核是 **16K 页**（`CONFIG_ARM64_16K_PAGES=y`），
> 详见 [3.4 Pi 5 启动链](../03-u-boot/3.4-pi5-boot-chain.md)。
> `PAGE_SHIFT` 变了，结构体布局跟着变——
> 本地编自动带上这个配置；交叉编若用了 4K 的 config，编译照样过，
> **`insmod` 时才报 `invalid module format`**。

什么时候才需要交叉编模块：**量产镜像构建**（Buildroot/Yocto 出整包）。学习阶段不需要。

## 决策树

```
要编什么？
│
├─ 内核模块 / 驱动 ──────────► Pi 本地编
│                              KDIR=/lib/modules/$(uname -r)/build
│
├─ 用户态程序 / 库 ──────────► Mac 上 arm64 Linux 容器（首选）
│                              或 macOS 交叉工具链（无 Docker 时）
│
├─ 完整内核 / U-Boot / DTB ──► arm64 Linux 容器
│                              ⚠ 不要在 macOS 原生编（大小写 + gmake）
│                              或 Pi 本地（约 30–60 min，但零配置）
│
└─ 整包 rootfs ──────────────► Buildroot，跑在容器里（见 05-rootfs）
```

## 错误对照表

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 板子上 `Exec format error` | 容器其实是 amd64，编出 x86-64 | `uname -m` 必须 `aarch64`；显式 `--platform linux/arm64` |
| 编译莫名慢 3–4 倍 | 在 QEMU/Rosetta 下跑 amd64 容器 | 同上；检查 `DOCKER_DEFAULT_PLATFORM` |
| `GLIBC_2.xx not found` | 工具链/容器 glibc 比目标新 | [2.3 第二道检查](./2.3-verify-and-pitfalls.md)；换工具链或静态链接 |
| 编内核报"头文件找不到"，但 `ls` 看得到 | APFS 大小写不敏感 | 大小写敏感卷上重新 clone |
| `GNU Make >= 4.0 is required` | 用了 Apple 的 make 3.81 | `brew install make`，敲 `gmake` |
| `insmod: invalid module format` | vermagic 不匹配（版本/配置/页大小） | 在 Pi 上用 `/lib/modules/$(uname -r)/build` 重编 |
| `no matching manifest for linux/arm64` | 该镜像无 arm64 版本 | 换镜像；**别**随手加 `--platform linux/amd64`，那会产出 x86 产物 |

## HFT / 嵌入式关联

**构建环境本身必须是版本化的输入。** "在我机器上能跑"在交易系统里不是段子，
是 P&L 风险——二进制要连同它链接的库版本、目标内核版本一起被锁定和记录。
内核的 vermagic 是"版本即契约"最严格的体现，值得当成设计范本。

**容器交叉编译的真正价值不是"快"，是把构建环境变成了可复现的声明**
（Dockerfile + image digest），而不是"某台装了一堆东西的 Mac"。

**但要看到容器的边界：它解决不了"产物必须匹配运行中的内核"这件事。**
内核模块、eBPF 程序、需要精确匹配内核数据结构的观测工具，都得在目标机上编，
或至少用目标机的 kernel headers。CO-RE/BTF 本来是想解决这个问题的
——可你的 Pi 5 内核是 `DEBUG_INFO_NONE=y`，**没有 BTF**，这条路也断了。
所以现阶段：模块就在 Pi 上编，别绕。

<details>
<summary>Q1：arm64 容器里还需要 <code>gcc-aarch64-linux-gnu</code> 吗？</summary>

不需要。那个包是给**x86 宿主机交叉编 arm64** 用的。

arm64 容器里的发行版 `gcc` 目标就是 aarch64，用 `gcc -dumpmachine` 可以确认
（输出 `aarch64-linux-gnu`）。再装一个交叉编译器只会多出一个名字相近的二进制，
让你在 Makefile 里分不清到底调用了哪个。

判据很简单：**交叉编译器的定义是"build ≠ host 或 host ≠ target"**。
arm64 容器里 host = target = aarch64，它不是交叉编译器。
</details>

<details>
<summary>Q2：既然容器是 arm64 且原生运行，为什么仍要跑 2.3 的三道检查？</summary>

因为三道检查查的是**三件不同的事**，容器只帮忙保证第一件：

1. **架构** —— 容器是 arm64 时基本自动对（但仍要用 `uname -m` 确认没在模拟）；
2. **glibc 版本需求** —— 容器保证不了。`debian:trixie` 的 glibc 可能**比你 Pi 上的新**，
   编出来的二进制会带上 `GLIBC_2.4x` 需求，拷到旧系统上就 `version not found`。
   **这一道最容易漏，也最该查**（`readelf -V` 看 `.gnu.version_r`）；
3. **能不能真跑** —— 只有执行才算数，能在宿主机用 `qemu-aarch64` 先跑一遍最好。

一句话：容器解决了"交叉"，没解决"与目标系统版本对齐"。
</details>

<details>
<summary>Q3：为什么说内核模块"交叉编零收益"？编完整内核不也一样要匹配吗？</summary>

不一样，关键差别在**匹配已经由谁保证了**。

编完整内核时，你**就是**那个定义版本的人——内核和模块一起编出来，天然一致，
所以"在 Mac 上交叉编内核"从技术上完全成立，只是 macOS 作为 host 有大小写和 gmake 两个硬伤。

编模块时，版本是**运行中的那个内核**定义的，`uname -r` 已经固定：
- 在 Pi 上：`/lib/modules/$(uname -r)/build` 就是那棵树的精确副本，
  `.config`、编译器版本、`Module.symvers` 全自动对齐，**不可能不匹配**；
- 交叉编：你得把这棵树搬到 Mac，再手动复现编译器版本和 config，
  **任何一处偏差都编译期无感、`insmod` 时才炸**。

所以：编内核是"我来定义契约"，交叉可以；编模块是"我去满足别人定的契约"，
在契约方本地编最省事。**这不是性能问题，是谁持有真相的问题。**
</details>
