# 产物验证与踩坑清单：交叉编译的三道检查

> **本节讲什么：** 编译"成功"不等于产物正确。这一节给出交叉编译后**必做的三道检查**，以及一份可复用的踩坑清单。
> **前置：** [2.2 sysroot 与 C 库](./2.2-sysroot-and-libc.md)
> **动手：** [P5 · D1](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch2 · Primer Ch12

## 为什么"能编译过"不算证据

交叉编译的失败分三层，**越往后越贵**：

| 层次 | 什么时候暴露 | 典型表现 | 检测成本 |
|------|------------|---------|---------|
| 1. 编译/链接失败 | 立刻 | `cannot find -lc` | 几乎为零 |
| 2. **ELF 层面不对** | 拷到板子那一刻 | `Exec format error`、`GLIBC_2.38 not found` | 一条命令 |
| 3. **ABI / 语义层面对** | 跑起来之后 | 算错、`Illegal instruction`、偶发段错误 | 最贵，可能潜伏数周 |

**第 2 层是完全可以用一条命令提前消灭的**，成本近乎为零却不做的代价是整个 bring-up 流程被打断。这一节就是把第 2 层变成肌肉记忆。

## 第一道检查：架构对不对（5 秒）

```bash
# ① file 看三件事：位数、字节序、架构
$ file hello
hello: ELF 64-bit LSB executable, ARM aarch64, version 1 (SYSV), dynamically linked,
       interpreter /lib/ld-linux-aarch64.so.1, ...

# ② readelf 看机器类型（比 file 更权威，不受 file 数据库版本影响）
$ aarch64-linux-gnu-readelf -h hello | grep -E 'Machine|Class|Data'
  Class:                             ELF64
  Data:                              2's complement, little endian
  Machine:                           AArch64
```

| 你要看到的 | 如果看到这个 → 说明 |
|-----------|-------------------|
| `Machine: AArch64` | ✅ 目标架构正确 |
| `Machine: Advanced Micro Devices X86-64` | ❌ 用了宿主 gcc，scp 上去必 `Exec format error` |
| `Machine: ARM` | ⚠️ 编成了 32 位（`arm-linux-gnueabihf-` 混进来了） |

⭐ **把这条做成 Makefile 的强制步骤**：

```make
check-arch: $(BIN)
	@if $(READELF) -h $(BIN) | grep -q 'AArch64'; then \
		echo "OK: aarch64"; else echo "FAIL: wrong arch"; exit 1; fi
```

## 第二道检查：依赖哪些库、要求哪个版本（10 秒）

```bash
# ① NEEDED：运行时必须存在哪些 .so
$ aarch64-linux-gnu-readelf -d hello | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]

# ② 版本需求：要求 libc 至少是哪个版本  ★ 最容易漏的一步
$ aarch64-linux-gnu-readelf -V hello | grep -o 'GLIBC_[0-9.]*' | sort -Vu
GLIBC_2.34
```

然后**去板子上核对**：

```bash
# 在 Pi 5 上
$ ldd --version | head -1          # 看板子上的 glibc 版本
$ ls /lib/aarch64-linux-gnu/libc.so.6
```

规则：**`readelf -V` 出来的最高版本 ≤ 板子 glibc 版本** 才安全。

> 补充：`NEEDED` 里的 `libc.so.6` 只是一个 **soname**，不是文件名。真正加载时找的是 `/lib/aarch64-linux-gnu/libc.so.6`（通过 `ld.so.cache` 或 `ldd` 能看到解析结果）。

## 第三道检查：能不能真的跑（1 分钟）

**不用板子的办法（快）：qemu-user**

```bash
# 宿主机上（需要 qemu-user-static）
qemu-aarch64-static -L <sysroot> ./hello
# -L 指定"解释器根"，否则找不到 ld-linux-aarch64.so.1 和 libc
```

**有板子的办法（准）：scp 上去跑**

```bash
scp hello wzp@pi5:/tmp/ && ssh wzp@pi5 /tmp/hello
```

| | qemu-user | 真机 |
|--|-----------|------|
| 速度 | 快，不用折腾硬件 | 慢，要网络/串口 |
| 能验证 | CPU 指令、libc 语义、程序逻辑 | **全部** |
| 不能验证 | GPIO/DMA/中断/时序/时钟源、性能 | — |

⭐ **推荐流程：qemu 先过一遍逻辑，真机只跑最后那一次。** bring-up 阶段来回 scp 是最耗时间的环节。

## 可复用踩坑清单

### 坑 1：混合使用宿主与目标的 binutils

```bash
gcc 编的          → aarch64
objdump 用的宿主  → 可能没有 aarch64 后端
```
**症状**：`objdump: hello: File format not recognized`
**解法**：所有命令带 `aarch64-linux-gnu-` 前缀。

### 坑 2：Makefile 里硬编码了 `gcc`

很多开源包的 Makefile 写死 `CC = gcc`。交叉时要么覆盖：

```bash
make CROSS_COMPILE=aarch64-linux-gnu-         # 内核和一些规范的包支持
make CC=aarch64-linux-gnu-gcc                 # 通用
make CC="aarch64-linux-gnu-gcc --sysroot=/opt/pi-rootfs"
```

要么（autotools）：
```bash
./configure --host=aarch64-linux-gnu --prefix=/usr
make DESTDIR=/opt/pi-rootfs install            # DESTDIR = 装到哪；prefix = 运行时在哪
```

⭐ **`DESTDIR` 和 `--prefix` 的区别必须分清**：`prefix` 是**运行时**路径（会被写进二进制），`DESTDIR` 是**安装时**的临时根（不写进二进制）。交叉安装时永远是 `make DESTDIR=<staging> install`。

### 坑 3：`-march` / `-mcpu` 用错

```bash
# Pi 5 是 Cortex-A76，支持 armv8.2-a
aarch64-linux-gnu-gcc -O2 -march=armv8.2-a -o x x.c
```

用太新的 `-march` → 目标 CPU 上没有这条指令 → **`Illegal instruction`**（而且是跑到那一行才崩，不是启动就崩，很难定位）。
**保守做法：不指定 `-march`，用工具链默认值**（一般为基线 armv8-a，兼容性最好）。

### 坑 4：浮点 ABI 混用（32 位 ARM 特有）

`-mfloat-abi=soft / softfp / hard` 三者**不能混着链接**，否则能链接但运行结果错（参数通过不同寄存器传）。
**aarch64 没有这个问题**（只有硬浮点一种），这也是 64 位省心的地方之一。

### 坑 5：编译选项没记录

```bash
# 让 ELF 自己记住它是怎么编出来的
aarch64-linux-gnu-gcc -O2 -frecord-gcc-switches -o hello hello.c

# 半年后反查
aarch64-linux-gnu-readelf -p .GCC.command.line hello
```

## HFT / 嵌入式关联

- **三道检查 = 发布流水线里的"门禁"**。HFT 的发布流程同样应该有三道：静态（编译/单测）→ 契约（ABI/配置/依赖版本核对）→ 影子盘（真跑一次）。**没有第二道门禁是很多线上事故的根源** —— 编译通过就直接上，等于把 ABI 问题留给实盘去发现。
- **qemu 先跑、真机后跑** 对应 HFT 的「回测 → 仿真 → 影子 → 实盘」四级：越便宜的环境越早用，把错误挡在贵的环境外面。
- `-frecord-gcc-switches` 的思路可以直接平移：**让产物自带 provenance（来源证据）**。交易二进制出问题时，第一个要回答的就是"这个二进制是哪次构建、用什么选项编出来的"。

<details>
<summary>Q1：<code>file</code> 已经说了 aarch64，为什么还要 <code>readelf -h</code>？</summary>

`file` 靠 magic 数据库猜测，数据库版本不同、或遇到非标准 ELF（比如某些 RTOS 的）可能判错；`readelf` 是直接解析 ELF 头里的 `e_machine` 字段，**是权威值**。

另外 `readelf` 能同时看到 **Class（32/64 位）** 和 **Data（字节序）**，这两项错了也会导致运行失败，而 `file` 输出太长容易看漏。
</details>

<details>
<summary>Q2：<code>NEEDED</code> 里的 <code>libc.so.6</code> 和 <code>readelf -V</code> 里的 <code>GLIBC_2.34</code> 是什么关系？</summary>

两回事：

- `NEEDED` 是 **soname**（库的名字），`ld.so` 拿它去找文件；
- `GLIBC_2.34` 是 **符号版本需求**，来自 ELF 的 `.gnu.version_r` 段，意思是"我引用的某些符号是从 glibc 2.34 才开始有的"。

**只有 soname 存在还不够**，版本需求也必须被满足，否则 `ld.so` 报 `version 'GLIBC_2.xx' not found`。这就是为什么"板子上明明有 libc.so.6 却跑不起来"。
</details>

<details>
<summary>Q3：<code>DESTDIR</code> 与 <code>--prefix</code> 弄混会造成什么后果？</summary>

- 只用 `--prefix=/opt/pi-rootfs/usr` 安装：路径被**写进二进制**（比如程序内部去 `/opt/pi-rootfs/usr/share/...` 找数据），拷到板子上路径不存在 → 运行失败，且很难查。
- 正确做法：`--prefix=/usr`（运行时路径）+ `make DESTDIR=/opt/pi-rootfs install`（装到 staging 目录）。

这样二进制里记的是 `/usr/share/...`，实际文件被放到 `/opt/pi-rootfs/usr/share/...`，等这个 staging 目录变成板子上的 `/` 时，两者就对上了。
</details>
