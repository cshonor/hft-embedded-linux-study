8.0

新增外设：DTS 必改，驱动分三档

FAQ · 锚定 Primer Ch7（DTB）· Ch8（驱动入门）· 09 驱动·DT
相关：DT ≠ UEFI · BSP 模板

核心结论（两层分开）

  1. 板子新加硬件 → 几乎 100% 要改/增 DTS 节点（启用片内模块则常是改 status，见下）。
  2. 不等于一定要从零写驱动 — 有现成驱动就只配 DTS；要适配就改几行；没有才写完整驱动。

一、为什么必须动设备树？

内核靠 DTB 里的信息认硬件：compatible、reg（物理基址）、中断、供电、时钟、复位等。

U-Boot 负责 DDR/Flash 等上电初始化，不会把「你焊了什么外设」完整交给内核；启动后内核的主硬件清单来源就是 DTB（现代 ARM 嵌入式主路径）。

例：GPIO 按键

  • 硬件：键接 GPIO ↔ GND
  • DTS：加 gpio-keys（或等价）节点 — GPIO、键名、触发电平
  • 驱动：内核 gpio_keys 等通用驱动 → 可零行自写驱动，只写 DTS

例：板外独立 GPU / 显示控制器（非 SoC 内置）

  • DTS：compatible、reg、电源、时钟、复位、总线（PCIe/I2C…）
  • 驱动：
  • 内核已有 → 只 DTS
  • 冷门/自研 → DTS + 完整平台/字符驱动（Ch8 入门 → 12 深挖）

二、三档工作量

场景 DTS 驱动
1. 内核已有标准驱动（LED、gpio-keys、常见 I2C 传感器、多数屏/PHY/UART…） 必写节点：compatible / reg / interrupts / clocks / regulator / reset… 不写；编 DTB、替换启动用的 dtb
2. 有通用驱动，参数略不同（同系列屏分辨率/时序等） 必写接线 少量改驱动或用 DT 属性吃参数，不从头造
3. 无现成驱动（自研采集、冷门芯片） 先建节点写地址/中断/电源 完整开发；驱动从 DT 读资源再做读写/IRQ

操作骨架（场景 1）：改 .dts → 出新 .dtb → boot 加载新 DTB（多数情况 不必 重编 U-Boot，见下）。

为何场景 1 这么多： 标准协议 + 厂商合入主线/BSP — 8.4。

三、片内模块 vs 外挂器件

类型 DTS 常见动作
SoC 片上（内置 UART/ETH MAC/内置 GPU…） 原厂 dtsi/dts 已有节点；多用 status = "okay" / "disabled"，不必从零「发明」节点
板外新挂（按键、外置 GPU、I2C 模组、外接 Flash…） 评估板 dts 没有 → 新增完整节点

四、和 U-Boot 的联动（承接 DT FAQ）

你加的东西 U-Boot
普通外设：按键、传感器、屏（内核阶段才用） 通常只改 DTS，不重编 U-Boot
影响启动期：DDR、NAND/启动介质、U-Boot 就要用的 PHY/串口时序 还要改 U-Boot — 7.0 场景 B

五、一句话

多焊硬件 → DTS 必动；写驱动看内核有没有货。
有货只配树；没货先写树再写驱动。

深入：Madieu platform + DT → 12；绑定细节 → 8.1；本书 Ch8 仅入门，勿当主教材（见 OUTLINE）。

8.1

设备树与驱动：分工、compatible、probe、启动链路

完整关系拆解 · Primer Ch7（DTB）+ Ch8（驱动入门）· 深挖 12
相关：加外设三档 · DT ≠ UEFI

一、定位：配置表 vs 操作代码

设备树（DTS→DTB） 驱动
本质 静态数据，无可执行逻辑 C 代码：读写寄存器、IRQ、协议、业务
内容 地址、中断、时钟、电源、复位、compatible、拓扑、板级参数 初始化、收发、ISR、/dev / sysfs
目的 接线/资源与驱动解耦 — 换板多半只改树 真正操作外设

比喻： 驱动 = 电器说明书；设备树 = 插座分布图（位置、电压）。换插座位置改图即可，不必重写说明书。

二、绑定钥匙：compatible

  1. DTS 节点：compatible = "vendor,part"（可多字符串，按优先匹配）
    例：compatible = "fsl,imx6ul-uart";
  2. 驱动：of_match_table 注册相同字符串，挂到 platform_driver（或同类）上：
static const struct of_device_id uart_of_match[] = {
    { .compatible = "fsl,imx6ul-uart" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, uart_of_match);

static struct platform_driver uart_drv = {
    .probe = uart_probe,
    .driver = {
        .name = "imx6-uart",
        .of_match_table = uart_of_match,
    },
};
  1. 内核：解析 DTB → 对每个节点的 compatible 在已注册驱动里找匹配 → 命中则调 probe()。

probe = 驱动读树、申请资源、初始化硬件的入口。

三、probe 里怎么读树（of_*）

API（示意） 用途
of_address_to_resource / platform_get_resource reg → 物理/IO 资源
of_irq_get / platform_get_irq 中断号
of_clk_get 时钟
of_property_read_u32 等 自定义属性（分辨率、速率…）
of_get_named_gpio / gpiod 族 GPIO

例：只加按键（不改驱动）

gpio_keys {
    compatible = "gpio-keys";
    key1 {
        gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
        label = "user_btn";
    };
};

内核自带 gpio-keys 驱动匹配 "gpio-keys" → probe → of_* 读 GPIO/标签 → 申请中断、上报按键。
全程只改 DTS（场景见 8.0）。

四、分工边界

设备树只填数据（不做操作）

  • MMIO 基址、IRQ、时钟、供电、复位
  • 总线拓扑（I2C 下挂哪些从设备）
  • 板级参数（屏时序、波特率、分区大小）
  • status = "okay" / "disabled"

驱动只写逻辑（不把板级地址写死）

  • 寄存器/中断/上下电与初始化
  • 协议与数据路径
  • 用户态接口（/dev、sysfs、net…）

解耦收益： 同驱动多板复用，改地址/引脚改树即可。
无 DT 的老做法：地址硬编码在 .c → 换板改驱动重编。

五、新增硬件时的联动（摘要）

场景 DTS 驱动
内核已有标准驱动 增/改节点 不写
无驱动 先建节点（含 compatible） 写 of_match_table + probe + of_*

片内模块：原厂节点多已在，常只改 status。
板外新芯片：常需新建完整节点；无驱动再开发。详表 → 8.0。

六、启动交互链路（极简）

U-Boot 加载 DTB → 交给内核
    → 内核展开设备节点
    → compatible ↔ of_match_table
    → probe()
    → of_* 取资源 → 初始化硬件 → 暴露 /dev 等

U-Boot 不替代 DTB 当「完整外设清单」；它负责启动期硬件初始化并把 DTB 指针交给内核（7.0）。

七、一句话

DT = 静态资源清单；驱动 = 操作逻辑。
靠 compatible 绑在一起，靠 of_* 在 probe 里读树 — 板级移植成本主要落在改树上，而不是改遍驱动源码。

实操主线：12 Madieu · Platform + DTS；本书 Ch8 仅概念预告。

8.2

驱动为什么在内核（built-in / .ko）

FAQ · 锚定 Primer Ch2（内核/用户上下文）· Ch4（drivers/）· Ch8（模块）
相关：DT↔驱动 · 三层图

一、根本原因：硬件权限只在内核

Linux 分 内核态 / 用户态。寄存器、IRQ、DMA、内存控制器等，用户态不能直接摸。

谁 权限
内核 完整硬件访问；能注册并跑中断处理
用户进程 经系统调用间接请求；直访 MMIO 通常 → 缺页/被杀

因此「读写寄存器、ISR、真正控外设」的主体必须是 内核里的驱动代码。

两种打包形式（本质都是内核代码）

形式 .config 形态 运行期
built-in =y 链进 vmlinux 开机即在，一般不能 rmmod
可加载模块 =m 独立 .ko insmod/modprobe 加载，rmmod 卸载

「内核模块」常特指 .ko；口语里「驱动是内核模块」= 跑在内核空间（含 built-in）。

二、驱动 · 内核 · 设备树协作

U-Boot 交 DTB
  → 内核解析节点，compatible 匹配驱动
  → 调 probe（内核态）
  → of_* 读地址/中断/时钟
  → 驱动操作硬件、注册 IRQ、创建 /dev/xxx
  → 用户态 APP：open/read/write… 系统调用 → 再进驱动

设备树不是驱动：只给内核驱动喂静态参数。
APP 不直连硬件：只跟 /dev（或 net/socket 等）说话。

例：按键

  • gpio_keys（.ko 或 built-in）在内核跑
  • DTS 只描述 GPIO 等
  • APP read → 陷入内核 → 驱动读电平 → 结果回用户态

三、不在「内核 .c 驱动」里的两类东西（易混）

类型 澄清
用户态「驱动」（少见） 如经 /dev/i2c-N、spidev 在用户态协议；总线控制器驱动仍在内核
固件 blob（GPU/Wi‑Fi 等） 文件在 rootfs；由内核驱动加载进芯片 — 固件 ≠ Linux 驱动

核心硬件控制逻辑仍落在内核侧。

四、为何不能把驱动主体写进普通 APP

  1. 权限 / MMU：用户态乱碰物理地址 → 崩溃或被杀
  2. 中断：硬中断由内核接；用户进程接不到「原味」硬件 IRQ 路径
  3. 隔离：用户崩溃默认杀进程；硬件控制若全在用户态，异常易把外设锁死、拖垮整机

（专用框架如 UIO/VFIO、DPDK 是刻意旁路的另一条课，先把标准内核驱动路径学清。）

五、对应本书章节

章 要点
Ch2 内核上下文 vs 用户上下文；驱动/ISR 在内核侧
Ch4 源码 drivers/；=y / =m 进镜像或 .ko
Ch8 字符/平台驱动、insmod/lsmod — 操作的是内核模块

仓库：Project #1 三层图 · 09 驱动深挖

六、总结

  1. 寄存器 / 中断 / 总线底层操作必须在内核 → 驱动主体是内核代码
  2. built-in 与 .ko 只是链接方式不同
  3. DT 给驱动提供参数，本身不是驱动
  4. 应用只通过系统调用委托内核驱动，不能替代它

与 8.1 合读：树负责描述，驱动（内核里）负责操作。
与 8.3 合读：操作覆盖 全生命周期 + 中断，不单是 probe 初始化。

8.3

驱动管硬件全生命周期（含中断）

FAQ · 承接 8.2 为何在内核 · 8.1 DT↔驱动
印证：驱动 ≠「只开机初始化一下」

结论（你的理解成立）

驱动对硬件是 全权、全时段 接管：上电初始化、日常读写、中断、异常、休眠/关机释放。
中断是驱动与硬件双向通道的核心职责之一，不是可选项。

一、全生命周期拆细

阶段 驱动做什么
开机 / probe 从 DT 取 reg/时钟/供电等 → 上电、配寄存器、初始化总线 → 硬件可用（「启动硬件」）
日常交互 APP open/read/write/ioctl… → 系统调用进驱动 → 真正收发（屏、传感器、网包…）
中断响应 按键、RX 完成、DMA 结束、硬件报错等 → 仅驱动注册的 ISR 处理；用户态收不到原生 IRQ
异常 溢出、总线错、超时、电压类报错 → 驱动捕获并处理/上报
休眠 / 关机 关时钟、切供电、释放 IRQ/GPIO/DMA 等资源

二、中断路径（按键例）

按键 → GPIO 硬件拉 IRQ → CPU 进内核中断上下文
  → 跳到驱动已 request 的 handler
  → 辨来源、记状态、唤醒等待中的读者
  → APP read / poll 拿到事件

没有驱动注册 IRQ：内核视作未处理中断，事件等于丢掉。

三、常见中断场景

硬件 事件 驱动侧
网口 收包 NIC 驱动收描述符 → 交协议栈
UART 收到字节 串口驱动读 FIFO
触摸 按下 触控驱动上报坐标
NAND/SD 完成/出错 MTD/块层处理

四、用户态怎么「感知」中断？

  1. APP 不能直接注册原生硬件中断
  2. 驱动必须封装：/dev、sysfs、信号、poll/epoll 等待队列等，把事件间接递给应用
  3. 无驱动注册 → 硬件 IRQ 对系统无意义

（UIO 等是特例框架，仍要内核侧桩；先把标准路径记牢。）

五、一句话

驱动不是开机脚本；运行期每一次硬件打断、数据搬运、故障与释放，都走内核驱动。
中断 = 驱动核心职责。与 8.2（为何必须在内核）同一条线。

8.4

为何多数外设不用自己写驱动（主线 + 标准协议）

FAQ · 承接 8.0 三档工作量 · 8.1 绑定
结论：标准化硬件 → 厂商写进主线 / BSP；你多数时候 只配 DTS

1. 主流通用外设：驱动已在主线，开箱复用

串口、以太 PHY、常见 I2C 温感、LCD 面板族、SD、USB HID、GPIO 按键/LED 等：
芯片原厂（NXP、TI、ST…）常把驱动合进 Linux 主线（kernel.org）。

原因： 协议与寄存器行为有行业规范（或事实标准），硬件逻辑相对固定，不必每块板重写一套驱动。一次合入，全球复用。

2. 「标准」如何变成「一套驱动 + 多块板」

例子 统一的是什么 板间差什么
UART 收发 / 中断 / 时钟控制模型相近 DTS：reg、IRQ、时钟、引脚
I2C EEPROM 标准读写时序 地址、页大小等属性
千兆 PHY IEEE 以太 PHY 模型 PHY 地址、复位脚、接口模式
按键 / LED gpio-keys / leds-gpio 逻辑固定 哪个 GPIO、高低有效

→ 操作逻辑在驱动里写死一套；接线与资源在树上改。

3. SoC 私有模块：靠原厂 BSP，仍常「零自写驱动」

片内专属块（某家通信引擎、多媒体加速等）未必是「全球开放标准」，但原厂 BSP / 内核树里 已带驱动。
你通常：开节点、status、填资源 — 不是从零写驱动（除非要深度改行为）。

与 BSP = 模板 一致：评估板开箱；自研板主要改树与配置，不是每片外设都重写 .c。

4. 反例：什么时候必须自己写

  1. 自研采集/控制芯片，无公开标准协议
  2. 小众工业件：无主线、无开源驱动
  3. 全新外设，无可参考同类驱动

此时：新建 DTS + 完整内核驱动（8.2 / 8.3）→ 深挖 12。

5. 落到日常工作

硬件类型 你干什么
通用成熟外设 只改/加 DTS，零驱动编码
私有/自研/无驱动 DTS + 自写内核驱动

总结

绝大多数标准化外设：行业规范 + 厂商已合入主线/BSP → 开发者用设备树配资源即可，不必重复造驱动轮子。
「会写驱动」仍是刚需，但用在 没有现成驱动 的那一档，而不是每个 LED 从零写起。

8.5

GPIO 通俗讲解（Linux · 设备树 · 驱动）

基础外设 · 对齐 Primer Ch8 FAQ · Pi Labs / Project #1
相关：8.0 只配 DTS · 8.4 主线复用 · 8.3 中断

一、全称

GPIO = General Purpose Input/Output
SoC 引出的可编程通用引脚，嵌入式最基础、最简单的一类「外设」。

二、两大模式 + 常用配置

模式 做什么 例子
输出 软件拉高/拉低 LED、继电器、给别的芯片拉复位
输入 读外部电平 按键、简单传感器高低电平

额外常见：

  • 上拉 / 下拉：默认电平，减少悬空抖动
  • 边沿/电平中断：变化时 IRQ（按键用中断，不必死轮询）— 见 8.3

三、硬件层

  • 一块 SoC（树莓派、i.MX…）常有几十～上百 GPIO
  • 常分组：如 gpio1 组里的第 5 脚 → 口语 GPIO1_5
  • 每脚可独立配方向、上下拉、中断

Pi5：应用核 + RP1 管大量用户 GPIO — 查官方 GPIO/RP1，勿死背 Pi4 寄存器课。Pi Labs §0

四、Linux：通用驱动 + 设备树（多数不用自写驱动）

内核有现成框架（如 gpio-keys、leds-gpio、gpiolib）。
板级差在哪根脚 → 改 DTS，逻辑在主线驱动里（8.4）。

示意（按键）：

gpio_keys {
    compatible = "gpio-keys";
    key1 {
        gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
        label = "user_btn";
    };
};

含义：gpio1 第 5 脚，低有效；gpio-keys 匹配后 probe，常自动走中断路径。

片内 GPIO 控制器节点一般在原厂 dtsi 里已有；你加的是消费者节点（keys/leds/…）。

五、用户态怎么碰（仍经内核）

常见路径：

  • sysfs（老）：/sys/class/gpio 导出后读写
  • 字符设备 / libgpiod（更推荐的现代路）：/dev/gpiochipN

APP 读写的是内核接口；真正改引脚电平的是内核 GPIO 子系统，不是用户态直写 MMIO（8.2）。

六、和 UART / I2C / SPI 的差别

GPIO UART/I2C/SPI
协议 无固定报文协议，软件自由定高低 有标准时序/帧格式
复杂度 最低 控制器 + 协议驱动更重

GPIO = 最简单的「一根线」；总线 = 带协议的专用口。

七、开发例子

  1. 板载 LED → 输出（或 leds-gpio）
  2. 功能键 → 输入 + 中断（gpio-keys）
  3. 外设复位脚 → 输出脉冲
  4. 插拔检测 → 输入（可中断）

八、一句话

GPIO = 可自由编程的芯片引脚：能出电平、能读电平、能中断。
Linux 上多数场景：主线 GPIO 驱动 + DTS 配脚，应用走 sysfs/libgpiod，不必从零写驱动。

与 8.6 合读：板边排针是物理引出；DTS 声明你用了哪一根。

8.6

GPIO 排针 ↔ 设备树：物理接线与软件声明

承接 8.5 GPIO 基础 · 8.0 加外设
板级：Pi Labs（Pi 40-pin header）

一、板子上那两排针是什么？

行业常称 GPIO Header / 扩展排针：把 SoC（及伴随 I/O 芯片）里的信号 引到板边，方便杜邦线外接 LED、按键、传感器等。

针上常见内容 说明
多数：GPIO 可编程输入/输出/中断
电源 / GND 如 3.3V、5V、地 — 不是 GPIO
复用脚 默认可当 UART/I2C/SPI 等；也可再配成普通 GPIO（视 SoC/引脚复用）

例：树莓派 40-pin 双排 — GPIO + 电源/地 + 串口/I2C 等复用。
做成双排：省 PCB 面积、高密度引出几十根脚。

结论： 不是每根针都是 GPIO；但多数简单外设确实用排针上的 GPIO 针 接到板子。

二、硬件接线 ↔ 设备树（缺一不可）

层 你做什么
硬件 杜邦线：排针某脚 ↔ LED/按键/…，电路连通
软件（DTS） 声明用了 哪一组、第几号 GPIO，通用驱动才能认、才能控

例：排针对应 GPIO1 第 5 脚接按键（对 GND，低有效）：

user_key {
    compatible = "gpio-keys";
    /* … 子节点里： */
    gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
};
  • 排针 = 物理引线（把芯片脚露出来）
  • 设备树 = 软件配置（告诉内核「你用了哪一根」）

只接线不改树 → 内核不知道；只改树不接线 → 电气没通。

三、三类针脚，别混

  1. GPIO：可配方向/上下拉/中断；DTS 里作 gpios = <&gpioX N …>
  2. 电源 / GND：只供电；不能当 GPIO 写进消费者节点乱控
  3. 复用总线脚：优先作 I2C/SPI/UART；改成 GPIO 要查复用/overlay，避免和总线冲突

查脚图：以该板官方 pinout 为准（Pi5 查官网 + RP1 说明，勿混用别板编号）。

四、外接 LED 最短闭环

  1. 硬件： LED（经电阻）接到某 GPIO 针 + 合适电源/地（极性与电路按原理图，勿短路 5V 进 3.3V GPIO）
  2. 软件： DTS 增加 leds / gpio-leds 类节点，指定同一 gpioX N
  3. 内核 leds-gpio（等）匹配
  4. 用户态：/sys/class/leds/… 或 libgpiod 控亮灭

→ 典型「只改 DTS、不写驱动」场景（8.4）。

五、回答你的两点

  1. 外接简单件（键、灯）：经排针 GPIO 物理连接，并在 DTS 声明同一脚
  2. 双排金属针 = 扩展插座，引出 GPIO / 电源 / 总线；针 ≠ 全是 GPIO

与 8.5 合读：先懂 GPIO 是什么，再懂「板边那排针」只是把它接到你手里。
