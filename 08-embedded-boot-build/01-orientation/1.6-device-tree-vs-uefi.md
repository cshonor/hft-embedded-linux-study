# UEFI ≈ U-Boot，不是 DTS · ACPI 与 DTB 才是对位关系

> FAQ · 锚定 Primer Ch2（固件对比）· Ch7（U-Boot 交权）· [09 DT](../../09-device-drivers-dt)  
> 相关：[U-Boot vs BIOS vs UEFI](../03-u-boot/3.1-uboot-bios-uefi.md) · [BSP 模板](./1.5-bsp-is-template-not-product.md)

---

## 一、结论：先分两层，再谈对比

最容易犯的错，是**拿 UEFI 跟设备树比**。它们根本不在同一层。正确的分法是：

| 层级 | 通用计算（PC / 服务器） | 嵌入式（ARM SoC 等） |
|------|------------------------|----------------------|
| **① 可执行引导固件**<br>上电就跑的**代码** | **UEFI 固件** | **U-Boot** |
| **② 硬件描述数据**<br>交给内核的**清单** | **ACPI 表** | **DTB** |

于是对位关系一目了然：

```
U-Boot  +  DTB    ≈    UEFI 固件  +  ACPI
 ↑          ↑            ↑           ↑
引导代码   硬件清单     引导代码    硬件清单
```

**一句话：UEFI 其实更像 U-Boot，而不是 DTS。**

> **UEFI 不需要 DTS。** UEFI 上电后会自己枚举硬件、自动分配设备的内存资源，并把硬件信息通过 ACPI 整套表交给操作系统。

---

## 二、UEFI：固件自带硬件描述

UEFI 是一个**完整的可执行固件体系**，不只是"一段引导代码"：

1. **上电独立运行**：CPU/内存初始化、驱动、分区（GPT）、网络、Secure Boot、甚至图形界面  
2. **主动枚举硬件**：扫 PCIe / USB 等总线，发现"插槽上插了什么"  
3. **自动分配资源**：给设备分配内存/IO 窗口（即 BAR 分配）  
4. **交付 ACPI 表**：把枚举结果与硬件信息装进 ACPI 整套表，递给操作系统  
5. **Runtime Services**：内核起来后仍可能回调固件接口  

关键点是**自包含**——硬件描述是固件自己产出的，**不需要外部再喂一份 DTS**。

---

## 三、U-Boot：只是引导代码，硬件描述靠外部 DTB

U-Boot 是**引导程序**，它本身**不自带完整的硬件描述**：

- U-Boot 负责：初始化 DDR、时钟树、启动介质，把内核镜像和 DTB 载入 RAM，然后 `bootm`/`booti` 交权  
- 硬件清单则来自**搭配的 DTB**（Device Tree Blob）  
- DTB 告诉内核：板载有哪些外设、寄存器基址在哪、中断号是多少、供电/复位脚、时钟、总线拓扑等  

**DTB 由 DTS 编译得到**：

```
DTS（文本源码）  ──dtc 编译──▶  DTB（二进制 blob）  ──U-Boot 载入 RAM──▶  内核解析
```

注意区分：**U-Boot 自己初始化 DDR/时钟/Flash，那是它的代码在做，不是 DTB 在做。** DTB 只在交权那一刻才被内核消费。

与 UEFI 的另一处差异：U-Boot 交权后通常**不再保留**运行时服务，要再进 U-Boot 多半只能复位（对比 UEFI 的 Runtime Services）。

---

## 四、DTS 到底是什么：文本源码，不是可执行程序

这是"错层比较"的根源。三者关系：

| 名称 | 形态 | 是否可执行 | 作用 |
|------|------|-----------|------|
| **DTS** | 纯文本源码 | **否** | 人写的硬件描述，**编译**成 DTB |
| **DTB** | 二进制 blob | **否**（数据，非代码） | 内核启动时解析的硬件清单 |
| **U-Boot** | 可执行的固件镜像 | **是** | 上电跑起来、初始化、加载并交权 |
| **UEFI** | 可执行的固件体系 | **是** | 上电跑起来、枚举、分配、交 ACPI |

> **DTS 只是用来生成 DTB 的文本源码，它不是可执行程序，和 UEFI 不在同一层级。**

打个比方：DTS 之于 DTB，就像 `.c` 之于 `.o`——**源码与产物**，不是两个平级方案。把 DTS 和 UEFI 并列比较，等于拿 `.c` 文件跟一个操作系统比。

---

## 五、为什么 UEFI 能「分配」而 DT 只能「登记」

顺着前面的资源分配问题往下看一层，会发现这不是能力差异，而是**硬件形态差异**决定的：

| | PC / 服务器（UEFI + ACPI） | 嵌入式 SoC（U-Boot + DT） |
|---|---|---|
| 设备从哪来 | **可插拔**： PCIe/USB 插槽，开机才知道插了什么 | **焊死在硅上**：SoC 内部外设，出厂即定 |
| 地址谁定 | 设备插入后由固件**枚举并分配** BAR 窗口 | 硅上**硬连线固定**，手册写死 |
| 固件动作 | 必须枚举 + 分配 | 只需照抄手册登记 |
| 描述载体 | ACPI 表 | DTB |

所以：

1. SoC **MMIO 基址**在硅上固定（手册写死），你改不了"串口到底焊在哪段物理地址"  
2. DTS 是把手册/原理图**抄成机器可读配置**，告诉内核 UART@`0x…`、ETH@`0x…`  
3. **虚拟内存、页框、进程地址空间**由内核 + MMU 管，不是 DT  
4. **DDR 物理颗粒**由 U-Boot 初始化控制器；DT 常只标注"这块 DRAM 从哪到哪、多大"供内核建 memblock  

例：以太控制器硬件窗口永远是手册上 `0x20000000` 那类地址——DTS 是**登记**它，不是 DT **分配**出这块窗口。

> 反过来，PC 上 PCIe 网卡插哪个槽、分到哪段 BAR，**事先无人知道**，只能靠 UEFI 上电枚举后动态分配——这就是为什么 UEFI 世界需要 ACPI 这一层，而嵌入式照抄固定地址就够了。

## 六、改 DT 要不要动 U-Boot？

### 场景 A — 只改设备描述 → **通常只重编 DTB，不改 U-Boot 源码**

例如：换 GPIO/中断/供电脚；增删 LED/按键/传感器/屏节点；改 Flash **分区表标注**；改内存 **大小标注**（且 DDR 初始化仍匹配现硬件）。

流程：`改 .dts` → `make dtbs`（或厂商等价）→ boot 加载**新 DTB** → 旧 U-Boot 二进制往往仍可用。

### 场景 B — 底层初始化参数变了 → **必须改并重编 U-Boot**

DT 管不了这些"上电第一拍"：

1. **DDR** 型号 / 频率 / 位宽 / 时序（控制器初始化在 U-Boot）  
2. **Flash/eMMC** 型号、片选、时序（boot 阶段读写介质）  
3. **晶振 / PLL / 主频** 启动时钟树  
4. U-Boot **自己就要用** 的串口、网口 PHY 等时序/引脚  
5. 启动脚本里的 **镜像/DTB 加载地址**、env、bootcmd  

只改 DTS **救不了** 内存训不开、Flash 读不出。

### 配合流程（Ch7 骨架）

```
U-Boot：初始化 DDR / 时钟 / 启动介质   ← DT 插不上手
    → 加载 内核镜像 + DTB 到 RAM
    → bootm/booti … 把 DTB 指针交给内核
内核：解析 DTB → 绑驱动 / 建设备
```

**分界线：** 可执行固件（U-Boot / UEFI）负责上电初始化；描述数据（DTB / ACPI）负责告诉内核硬件长什么样。

## 七、常见误解速查

| 说法 | 判定 | 正解 |
|------|------|------|
| UEFI 更像设备树 | ❌ 错层 | UEFI 更像 **U-Boot**，都是上电跑的可执行固件 |
| UEFI 需要 DTS | ❌ | UEFI 用 **ACPI**，自带硬件描述，不需要 DTS |
| ACPI 和 DTB 是一回事 | ⚠️ 不完全 | **角色相同**（都向内核传硬件信息），**机制不同**（ACPI 含可执行 AML 字节码，DTB 是纯数据） |
| DTS 是 UEFI 的嵌入式替代 | ❌ | DTS 是**文本源码**，DTB 才是产出的清单；UEFI 是**可执行固件** |
| 改了 DT 就得重编 U-Boot | ⚠️ 看情况 | 只改描述 → 重编 DTB；改 DDR/Flash/时钟 → 必须动 U-Boot |

---

## 八、一句话

1. **UEFI ≈ U-Boot**（可执行引导固件，上电运行）；**ACPI ≈ DTB**（向内核传递硬件信息的数据）  
2. **U-Boot + DTB ≈ UEFI 固件 + ACPI**；UEFI 不需要 DTS，它自带 ACPI 硬件描述  
3. **DTS 只是生成 DTB 的文本源码**，不是可执行程序，与 UEFI 不在同一层级  
4. DT **记录**固定物理信息，不当 MMU/分配器；只改外设描述 → 重编 DTB 即可；DDR/Flash/时钟/boot 介质变 → **同步改 U-Boot**

> **极简版（适合直接进知识库）**：UEFI 不需要 DTS——UEFI 本身是固件，自带 ACPI 硬件描述；U-Boot 只是引导代码，硬件信息要靠 DTS 编译得到的 DTB 提供。

树莓派：官方固件链与"纯开源 U-Boot 板"细节不同，但 **「boot 固件初始化 ↔ DT/配置描述内核」** 分工仍成立；Pi5 查官方 DT / overlay，见 [Pi Labs](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)。
