# 存储介质与文件系统：为什么 NAND 不能用 ext4

> **本节讲什么：** 选介质、选文件系统，以及理解**块设备与裸 Flash 的根本区别** —— 这是嵌入式与 PC 存储最大的认知差异。
> **前置：** [06-boot-to-shell](../06-boot-to-shell/)
> **卡住查书：** MELP Ch9–10 · Primer Ch10（MTD）

---

## 先分两类：块设备 vs 裸 Flash

```
                  ┌─ 块设备（Block Device）── ext4 / f2fs / squashfs / btrfs
存储 ─────────────┤     有控制器：擦写均衡、坏块管理都在里面做
                  │     对外表现为"可读可写的 512B/4K 扇区数组"
                  │
                  └─ 裸 Flash（MTD）───────── UBI / UBIFS / JFFS2
                        无控制器：擦写均衡、坏块管理**必须由软件做**
                        对外表现为"必须先擦除（按块）再写入（按页）"
```

⭐ **这就是"NAND 不能用 ext4"的全部理由**：ext4 假设底层是"随时可覆盖写的扇区数组"，而裸 NAND **必须先擦后写，且擦除单位是写入单位的几十倍**。ext4 会在原地改写元数据，NAND 上这么做既错又慢，还会迅速写坏块。

## 介质选型

| 介质 | 类型 | 容量 | 特点 | 用在哪 |
|------|------|------|------|--------|
| **microSD** | 块设备 | GB 级 | 便宜、可换、有控制器；**掉电易损坏、写入寿命有限** | 开发、原型 |
| **eMMC** | 块设备 | GB 级 | 焊死、比 SD 可靠、工业级温度 | **工业产品首选** |
| **NOR Flash** | MTD | MB 级 | 读快、可直接 XIP（就地执行）、贵 | **存 bootloader** |
| **NAND Flash** | MTD | GB 级 | 便宜、密度高、**有坏块、需要 ECC** | 大容量存储 |
| **NVMe（Pi 5 有 PCIe）** | 块设备 | 百 GB | 快、可做根分区；需要配置启动顺序 | 高性能/日志密集 |

### 判据表

| 你的需求 | 选 |
|---------|----|
| 学习/原型 | microSD（坏了换一张） |
| 量产、无人值守 | **eMMC** |
| 启动代码 | **NOR**（小、可靠、可 XIP） |
| 大容量低成本 | NAND + **UBI/UBIFS** |
| 高写入吞吐（日志、行情落盘） | NVMe / eMMC，**避开 SD 卡** |

⚠️ **microSD 的隐藏成本**：它的控制器为"相机/手机的顺序大文件写入"优化，对**小随机写**（数据库、日志、文件系统元数据）表现极差，且掉电时正在写的块可能损坏 —— 这会让只读 rootfs + 独立 data 分区的设计从"可选"变成"必需"。

## 文件系统选型

| 文件系统 | 介质 | 特点 | 用在哪 |
|---------|------|------|--------|
| **ext4** | 块设备 | 通用、成熟、有日志 | 通用 rootfs / data |
| **f2fs** | 块设备（Flash 友好） | 为 Flash 的追加写优化，**日志型** | eMMC/SD 上的 data 分区 |
| **squashfs** | 块设备 | **只读压缩**，体积减半 | **只读 rootfs 首选** |
| **overlayfs** | 叠加在其他 fs 上 | 只读底 + 可写上层 | "看起来可写"的只读系统 |
| **UBIFS** | **裸 Flash（UBI 卷）** | 擦写均衡 + 坏块管理 + 压缩 | NAND 上的 rootfs |
| **tmpfs** | 内存 | 掉电即失、极快 | `/tmp`、`/run` |

### 决策树

```
是裸 Flash（无控制器）吗？
   ├─ 是 → UBIFS（必须先建 UBI 卷）
   └─ 否（块设备）
        ├─ 分区需要写吗？
        │    ├─ 否 → squashfs（只读、省空间、防篡改）
        │    └─ 是 → 写入模式是？
        │              ├─ 大量小随机写 → f2fs
        │              └─ 通用           → ext4
        └─ 想要"看起来可写"的只读系统 → squashfs + overlayfs
```

## 关键命令

```bash
# 看块设备与挂载
lsblk -f                                   # 带文件系统类型和 UUID
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS    # 看挂载选项（有没有 ro）
blkid                                      # UUID / PARTUUID（写 fstab 用）

# 看 MTD 设备（裸 Flash）
cat /proc/mtd
mtdinfo /dev/mtd0

# 健康度
dmesg | grep -i -E 'mmc|ext4-fs error|I/O error'
smartctl -a /dev/nvme0n1                   # NVMe
mmc extcsd read /dev/mmcblk0 | grep LIFE   # eMMC 寿命（需 mmc-utils）
```

⭐ **`PARTUUID` 比 `/dev/mmcblk0p2` 可靠**：设备名会因插拔顺序、枚举时序变化；`PARTUUID` 写死在分区表里。

```bash
# /etc/fstab 推荐写法
PARTUUID=12345678-02  /      ext4   ro,noatime  0  1
PARTUUID=12345678-01  /boot  vfat   defaults    0  2
```

## 三个实践要点

### 1. `noatime`（几乎白送的性能）

每次读文件都要更新 `atime` → 每次读变成一次写。**对 Flash 是双倍伤害**（性能 + 寿命）。

```
defaults,noatime
```

现代内核默认 `relatime`（折中方案），但 `noatime` 更彻底，嵌入式上直接用它。

### 2. 日志（journal）的取舍

ext4 的 journal 保证崩溃一致性，代价是**额外的写入放大**。

```
# 关掉（省写入、省时间，但崩溃可能损坏）
mkfs.ext4 -O ^has_journal /dev/sdX1
tune2fs -O ^has_journal /dev/sdX1

# 或 data=writeback（只保护元数据，不保护数据）
mount -o data=writeback
```

⭐ **只读 rootfs 根本不需要 journal**（它永远不写），这也是 squashfs 更快的原因之一。

### 3. 对齐与块大小

Flash 的擦除块通常 128 KB ~ 几 MB。分区**起始地址不对齐**会导致一次逻辑写变成两次物理擦写。

```bash
# 分区时对齐到 1MiB（parted）
parted -a optimal /dev/mmcblk0 mkpart primary ext4 1MiB 100%
```

## HFT / 嵌入式关联

- **存储层次的选择本质是延迟与持久性的权衡**。HFT 里同样的取舍：行情落盘用 NVMe（持久化）还是共享内存（快但掉电即失）？判据是**丢了之后能不能重放** —— 能从撮合流重建就别落盘。
- **"写入放大"在两者都是成本中心**：嵌入式关心 Flash 寿命，HFT 关心写盘延迟抖动（fsync 卡住主线程）。解法同构：**批量写、追加写、避开原地改写元数据**。
- **只读 + 独立可写区**的设计在 HFT 生产机上同样成立：二进制和配置在只读挂载点（防误改、防篡改），日志和状态在独立分区。这是"不可变基础设施"的落地形态。

<details>
<summary>Q1：为什么 NAND 必须"先擦后写"，而 eMMC 不用？</summary>

物理特性决定了它：NAND 的**写**只能把位从 1 改成 0，**擦**才能把位从 0 改回 1，而擦除的最小单位（block，通常 128KB~几 MB）远大于写入单位（page，2~16KB）。所以想改写一个 page，必须擦掉整个 block。

**eMMC/SD 卡内部有一个控制器**（FTL：Flash Translation Layer），它把这套"先擦后写 + 擦写均衡 + 坏块替换"全藏在里面，对外只暴露"可读写的扇区数组"—— 所以上层可以跑 ext4。

**裸 NAND 没有这层**，所以必须由软件（MTD + UBI）来做。这就是"能不能用 ext4"的分界线：**看有没有 FTL，而不是看是不是 Flash。**
</details>

<details>
<summary>Q2：squashfs 压缩会不会让启动变慢？</summary>

不一定，甚至可能更**快**：

- **读取量变小**：压缩后 I/O 量减少，而嵌入式上 I/O（尤其 SD 卡）往往比 CPU 解压慢
- **顺序读**：启动是顺序读，压缩对顺序读友好

代价是**单次随机读需要解压整个块**（squashfs 默认 128KB 块），所以：

- ✅ 适合：整个 rootfs（顺序读为主）
- ❌ 不适合：数据库、频繁随机访问的数据

**实测才是判据** —— 用 [6.3 启动耗时](../06-boot-to-shell/6.3-boot-timing.md) 的方法量一次，别猜。
</details>

<details>
<summary>Q3：<code>/proc/mtd</code> 里有设备，能用 <code>mkfs.ext4 /dev/mtd0</code> 吗？</summary>

不能，而且会报错或产生一个坏的文件系统。

`/dev/mtdX` 是**字符设备**（按字节访问裸 Flash），不是块设备。ext4 需要"可随机覆盖写的扇区"，裸 Flash 给不了。

正确路径是三层：

```
/dev/mtd0  （裸 Flash 分区）
   ↓  ubiattach / ubiformat
/dev/ubi0  （UBI 设备：做擦写均衡 + 坏块管理 + 逻辑卷）
   ↓  ubimkvol
/dev/ubi0_0 （UBI 卷：表现为块设备）
   ↓  mkfs.ubifs / mount -t ubifs
文件系统
```

**UBI 就是软件实现的 FTL** —— 它把裸 Flash 变成"看起来像块设备"的东西，之后才能在其上建文件系统。
</details>
