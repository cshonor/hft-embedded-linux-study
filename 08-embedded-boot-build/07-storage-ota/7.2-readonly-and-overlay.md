# 只读 rootfs 与 overlayfs：让系统不怕掉电

> **本节讲什么：** 为什么产品都用只读 rootfs、overlayfs 的三层结构怎么搭、以及"看起来可写"这个技巧的代价。
> **前置：** [7.1 介质与文件系统](./7.1-media-and-filesystem.md)
> **卡住查书：** MELP Ch9–10

---

## 为什么只读

| 理由 | 说明 |
|------|------|
| **掉电安全** | 不写就不会写坏。SD 卡上 90% 的损坏来自"掉电时正在写元数据" |
| **防误改/防篡改** | 攻击者或误操作改不了 `/usr/bin`；配合 dm-verity 还能检测篡改 |
| **可复现** | 所有同型号设备跑的是**逐字节相同**的系统 |
| **配合 A/B 升级** | 只读分区才能整体替换（见 [7.3](./7.3-ab-update.md)） |
| **省写入寿命** | Flash 擦写次数有限 |

⭐ **一句话：把"会变的东西"和"不变的东西"分开。** 系统会变（配置、日志、数据），系统本身不该变（二进制、库）。

---

## 分区布局

```
┌──────────┬─────────────┬─────────────┬──────────────┐
│  boot    │  rootfs A   │  rootfs B   │    data      │
│  (FAT)   │  (ro)       │  (ro)       │    (rw)      │
│  固件/内核│  当前系统    │  升级目标    │ 配置/日志/状态│
└──────────┴─────────────┴─────────────┴──────────────┘
                 ↑                           ↑
           升级整体替换                  升级时保留
```

| 分区 | 挂载 | 内容 | 大小 |
|------|------|------|------|
| boot | `rw`（升级时才写） | 内核、DTB、bootloader 配置 | 几十~几百 MB |
| rootfs A/B | **ro** | squashfs 或 ext4(ro) | 系统大小 ×1 |
| data | rw | `/etc` 配置、日志、应用数据 | 按需求 |

```bash
# /etc/fstab 示例（ro rootfs + 独立 data）
PARTUUID=...-02  /       squashfs  ro,noatime    0  1
PARTUUID=...-04  /data   ext4      rw,noatime    0  2
```

⚠️ **注意 `/etc` 的问题**：很多程序默认往 `/etc` 写配置（如 `sshd` 生成 host key）。rootfs 只读时就写不了。三种解法：

| 解法 | 做法 | 适合 |
|------|------|------|
| **符号链接** | `/etc/xxx` → `/data/etc/xxx` | 少量已知文件 |
| **bind mount** | `mount --bind /data/etc /etc` | 整个 `/etc` 都要可写 |
| **overlayfs** | 见下 | 想"整体看起来可写" |

## overlayfs：把只读和可写叠起来

```
              /merged  ← 用户看到的是这个（挂载点）
                 │
      ┌──────────┴──────────┐
      │                     │
  upperdir              lowerdir
  (rw, 可写层)          (ro, 只读底层)
      │                     │
      └──────────┬──────────┘
                 │
            workdir（必须是同一文件系统的空目录）
```

**规则：**

| 操作 | 行为 |
|------|------|
| **读** | upper 有就用 upper，否则读 lower |
| **写**（修改已有文件） | **先复制到 upper**（copy-up），再在 upper 上改；lower 不变 |
| **删** | 在 upper 建一个 **whiteout**（字符设备 0:0）遮住 lower 的文件 |
| **建目录** | 在 upper 建；若 lower 有同名目录则建 **opaque 目录**（合并两边内容） |

### 挂载

```bash
mkdir -p /data/overlay/{upper,work} /merged

mount -t overlay overlay \
      -o lowerdir=/,upperdir=/data/overlay/upper,workdir=/data/overlay/work \
      /merged

# 然后 pivot_root 或 chroot 到 /merged
```

**fstab 写法：**

```
overlay / overlay lowerdir=/,upperdir=/data/overlay/upper,workdir=/data/overlay/work 0 0
```

### 三个必踩的坑

| 坑 | 现象 | 解法 |
|----|------|------|
| **workdir 必须与 upperdir 同一文件系统** | `mount: wrong fs type` | 都放 `/data` 下 |
| **upperdir 满了** | 写操作 `ENOSPC`，系统"突然变砖" | 监控 upper 用量；或限制只有特定目录可写 |
| **copy-up 丢失文件元数据** | 第一次写大文件时慢（整个文件要复制） | 提前把需要写的文件放进 upper |

⚠️ **overlayfs 不是免费的**：

1. **copy-up 的首次写有延迟抖动**（复制整个文件）
2. **upper 层无界增长**（所有改动都累积）
3. **lower 变了，upper 的 whiteout 可能遮住新文件**（升级后旧配置"消失"）

⭐ **所以 overlayfs 最适合"开发/调试期让只读系统可用"，产品上更推荐"明确的 data 分区 + 符号链接"** —— 显式的东西比隐式的好排查。

## 实践：找出"到底谁在写"

```bash
# ① 简单粗暴：把 / 挂 rw，跑一段时间，看哪个文件新
find / -xdev -newermt '-10 minutes' -not -path '/proc/*' -not -path '/sys/*' 2>/dev/null

# ② 精确：fatrace（文件访问跟踪）
fatrace -t -c            # -c 只看当前进程树

# ③ 内核级：ftrace 的 vfs_write 事件
trace-cmd record -e vfs_write && trace-cmd report
```

**流程**：先让它可写 → 跑一遍完整业务 → 找出所有被写的文件 → 逐个决定"移到 data 分区 / 符号链接 / 干脆不要写"。

## HFT / 嵌入式关联

- **只读 = 不可变基础设施**：HFT 生产机上交易二进制通常也在只读挂载点，防止运行期被改（无论是恶意还是误操作）。**"能改"本身就是风险面。**
- **"把会变的和不变的分开"是架构级原则**：对应到交易系统 = 代码（不可变）vs 配置/状态（可变）。配置要能热更新，代码不能。
- **overlayfs 的 copy-up 抖动值得警惕**：它在嵌入式上只是"首次写慢一点"，在 HFT 上可能是**一次 p99 尖刺**。所以 HFT 系统宁愿用**显式的双缓冲 / 预分配**，也不用"按需复制"这种延迟不可预测的机制。**可预测的延迟比平均延迟重要。**
- **掉电保护**这件事在嵌入式是物理约束（真的会断电），在 HFT 机房是 UPS + 持久化日志 —— **问题同构，解法不同**，值得对照着看。

<details>
<summary>Q1：copy-up 是什么意思，为什么会慢？</summary>

overlayfs 的 lower 层是只读的。当你修改一个只存在于 lower 的文件时，它必须先**把整个文件复制到 upper**，然后才能在 upper 上修改。这就是 copy-up。

**慢在哪**：一个 100 MB 的文件，你只改 1 个字节，也要先复制 100 MB。

**触发条件的坑**：即使你只是 `chmod`（改元数据）或 `truncate`，也会触发 copy-up。

**规避**：把确定要写的大文件**预先放进 upper**，或干脆用 bind mount 指向 data 分区。
</details>

<details>
<summary>Q2：为什么 workdir 必须和 upperdir 在同一个文件系统？</summary>

因为 overlayfs 需要在**同一个文件系统内做原子重命名**（`rename(2)`）。它的实现要先把内容写进 workdir，再原子地 rename 到 upper —— 这保证了"要么看到旧版本，要么看到新版本"，不会看到写了一半的文件。

跨文件系统无法原子 rename，所以内核直接拒绝挂载。

**这是"用原子 rename 实现原子更新"的经典手法** —— 后面 [7.3 A/B 升级](./7.3-ab-update.md) 和很多配置热更新方案用的都是同一招。
</details>

<details>
<summary>Q3：只读 rootfs 了，怎么打补丁/修 bug？</summary>

**不要打补丁，整体替换。** 这正是只读设计的意图：

1. 在构建机出新镜像
2. 写进备用分区（rootfs B）
3. 切换 bootloader 指向
4. 失败自动回退到 rootfs A

这就是 A/B 升级。如果你需要"现场改一个文件然后重启生效"，说明**那个文件根本不该在 rootfs 里** —— 它应该属于 data 分区。

⭐ **判据**：问自己"这个文件是系统的一部分，还是系统的输入？" 输入（配置、数据）放 data 分区，系统（代码、库）放只读 rootfs。
</details>
