# A/B 升级与回滚：设备出场之后怎么活

> **本节讲什么：** 设计一套"升级失败也能自己爬起来"的机制。硬件在客户手里，你没有第二次机会。
> **前置：** [7.2 只读 rootfs 与 overlayfs](./7.2-readonly-and-overlay.md)
> **卡住查书：** MELP Ch10 · 实战框架 RAUC / SWUpdate / Mender

---

## 核心问题

```
设备在现场，你要升级
   ├─ 升级包传一半断了        → 不能留下半个系统
   ├─ 新系统起不来            → 必须自动回到能用的那个
   ├─ 新系统起来了但功能坏了  → 需要"确认"机制
   └─ 升级中途掉电            → 不能变砖
```

**A/B 的全部设计都是围绕这四件事。** 关键洞察：**永远不要覆盖正在运行的那个系统。**

---

## 基本流程

```
                  ┌──────────────────────────────────────┐
                  │                                      │
   ① 写备用分区   │  rootfs A (ro, 运行中)  rootfs B      │
      （随便写，  │      ↑ 当前                 ↑ 写这里  │
       写坏了也  │                                      │
       不影响）  └──────────────────────────────────────┘
                  │
   ② 校验         │  sha256 + 签名（必须！）
                  ↓
   ③ 切换指针     │  改 bootloader 环境变量 / boot 计数
                  ↓
   ④ 重启         │
                  ↓
   ⑤ 新系统起来   │  → 用户态"确认"（标记成功）
                  │     ├─ 确认 → 常驻 A/B 角色互换
                  │     └─ 未确认（超时/崩溃）→ 下次重启自动回退
```

⭐ **第 ⑤ 步的"确认"是整套机制里最容易被忽略的一步。** 没有它，系统"能启动但服务全挂"的情况不会被检测 —— 而这是最常见的升级失败形态。

---

## 切换指针：三种实现

| 方式 | 机制 | 适合 |
|------|------|------|
| **bootloader 环境变量** | U-Boot `boot_part=2`，用户态 `fw_setenv` 改 | 有 U-Boot 的板子 |
| **boot 计数** | `bootcount` + `altbootcmd`：连续失败 N 次自动切 | ⭐ **最可靠**，不依赖用户态 |
| **GPT 分区属性** | 改分区的 `priority`/`successful` 标志 | 无 U-Boot（如 Pi 的固件启动） |

### U-Boot 的 bootcount（推荐）

```
# 环境变量
bootcount=0
bootlimit=3
altbootcmd=run altboot        # 失败后的备用启动命令

# 逻辑
#   每次启动：bootcount++
#   成功启动后：用户态执行 fw_setenv bootcount 0
#   bootcount >= bootlimit → 执行 altbootcmd（切到另一个分区）
```

⭐ **为什么它最可靠**：**失败检测完全在 bootloader 里**，不依赖新系统能不能跑起来。新系统连用户态都进不去时，bootcount 照样累加，照样回退。

## 校验：签名不是可选项

```bash
# 生成签名（构建机）
openssl dgst -sha256 -sign private.pem -out image.sig image.squashfs

# 设备上验证（升级前）
openssl dgst -sha256 -verify public.pem -signature image.sig image.squashfs
```

| 威胁 | 不签名的后果 |
|------|------------|
| 传输损坏 | 装上一个坏系统（sha256 能挡） |
| **恶意固件** | 攻击者刷入后门系统（**只有签名能挡**） |
| 版本降级 | 刷回有漏洞的旧版本攻击（需要**版本号防回滚**） |

⭐ **完整的升级包至少要包含三样东西**：镜像本体 + 签名 + **单调递增的版本号**。防回滚（anti-rollback）常被漏掉，但它和签名同等重要。

## 用什么框架（不要自己造轮子）

| 框架 | 特点 | 适合 |
|------|------|------|
| **RAUC** | 成熟、支持 U-Boot/GRUB/GPT、有 D-Bus API、签名与防回滚齐全 | ⭐ **首选** |
| **SWUpdate** | 灵活、支持多种 handler、可定制 UI | 复杂场景 |
| **Mender** | 带服务端，可管理设备群 | 有 OTA 管理平台需求 |
| **手写脚本** | 几十行 shell + `fw_setenv` | 学习/理解原理 |

⚠️ **自己写的第一版几乎必然漏掉**：原子性（写一半掉电）、签名、防回滚、确认机制、bootcount。**至少先读一遍 RAUC 的设计文档再决定要不要自己写。**

### 最小手写实现（理解用）

```sh
#!/bin/sh
# 极简 A/B：当前在 A，写到 B
set -e

CUR=$(fw_printenv -n boot_part)          # 1 或 2
[ "$CUR" = "1" ] && TGT=2 || TGT=1

DEV="/dev/mmcblk0p$TGT"

# ① 写（这一步失败无所谓，反正没切换）
openssl dgst -sha256 -verify /etc/ota/pub.pem \
        -signature /data/ota/image.sig /data/ota/image.img || exit 1

dd if=/data/ota/image.img of=$DEV bs=4M conv=fsync
sync

# ② 切换（原子：只改一个环境变量）
fw_setenv boot_part $TGT
fw_setenv bootcount 0
fw_setenv upgrade_pending 1              # 等用户态确认

# ③ 重启
reboot
```

启动后由服务确认：

```sh
# 健康检查通过
fw_setenv upgrade_pending 0
```

而 U-Boot 侧：
```
if test "${upgrade_pending}" = "1" && test "${bootcount}" -ge 3; then
    # 没确认 + 失败 3 次 → 回退
    fw_setenv boot_part <上一个>
fi
```

## 测试升级方案必须测的四件事

| 场景 | 怎么模拟 | 期望 |
|------|---------|------|
| 传输中断 | 写到一半 `kill -9` | 系统仍从原分区启动 |
| 镜像损坏 | 改坏一个字节再装 | 签名验证失败，拒绝安装 |
| 新系统起不来 | 装一个坏的内核 | bootcount 到阈值后自动回退 |
| **新系统能起但功能坏** | 装一个能启动但服务崩的版本 | 确认超时 → 回退 |

⭐ **第四个场景是最容易被漏测的**，而它恰恰是现实中最常见的失败形态。

## HFT / 嵌入式关联

- **A/B + 快速回退 就是灰度发布**：新版本出问题要能在**一次心跳内**回退，而不是现场重刷。交易系统的灰度同样是"新旧并存、可快速切回"，而不是"停机升级、失败重装"。
- **"永远不要覆盖正在运行的那个"** —— 这条在 HFT 部署里是铁律：新二进制部署到**新目录/新容器**，切换只改一个符号链接或负载均衡指向。覆盖式部署（`cp` 到原路径）会导致"部分更新"的中间态，在高频场景下就是灾难。
- **bootcount 的"失败检测放在观察者里"设计**值得借鉴：HFT 的健康检查也应该**独立于被检查的对象**（外部心跳、独立监控进程），而不是让进程自己报告"我很健康" —— 进程崩了就没法报告了。
- **防回滚（版本号单调）** 在金融系统里对应**审计与合规**：不能悄悄退回有问题的旧版本，每一次变更都要可追溯。

<details>
<summary>Q1：为什么不能"直接覆盖当前系统"？</summary>

因为覆盖过程有**中间态**：写了一半的系统既不是旧的也不是新的。这时掉电或者崩溃，设备就砖了。

A/B 的本质是：**写操作发生在一个"没人用"的分区上**，写坏了也不影响当前运行。切换是最后一步，而且切换本身必须是**原子的**（改一个环境变量 / 一个 GPT 标志位 / 一次原子 rename）。

**这就是"用原子操作提交非原子变更"的通用模式** —— 数据库 WAL、overlayfs 的 workdir、配置热更新用的都是同一招。
</details>

<details>
<summary>Q2：bootcount 和用户态确认，有两个不就够了吗？</summary>

不够，它们**检测的是不同层面的失败**：

| 机制 | 能检测 | 不能检测 |
|------|--------|---------|
| bootcount | 系统**起不来**（内核 panic、挂不上根） | 系统起来了但服务崩了 |
| 用户态确认 | 系统起来了但**功能不正常** | 系统根本起不来（没人去确认） |

现实中最常见的是"能启动但服务挂了" —— 内核好好的，但你的应用因为配置不兼容起不来。bootcount 永远不会累加（系统"成功"启动了），只有**用户态健康检查 + 确认超时**能抓住它。

**两者都要有。**
</details>

<details>
<summary>Q3：防回滚（anti-rollback）为什么重要？</summary>

假设 v1.0 有个已修复的漏洞，你升级到 v2.0 修好了。攻击者拿到设备后，**刷回 v1.0 就能重新利用那个漏洞**。

没有版本号检查的话，A/B 机制**恰好给了攻击者这个能力** —— 它本来就是为了"能回退到旧分区"设计的。

解法：把**当前已接受的最低版本号**写进一次性可编程区域（OTP / eFuse）或受保护的环境变量，升级时检查 `new_version >= min_version`。

⭐ 这体现了安全的一般原则：**任何回退机制本身都是一个攻击面。**
</details>
