# initramfs：内核启动时的"临时根"

> **本节讲什么：** initramfs 是什么、为什么需要它、以及它和老的 initrd 有什么本质区别。理解它，才能看懂"为什么我的内核挂不上根分区"。
> **前置：** [5.1 最小 rootfs](./5.1-minimal-rootfs-by-hand.md)
> **动手：** [P5 · B2](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch5 · Primer Ch6

---

## 一句话

**initramfs = 一个 cpio 归档，内核启动时把它解压到一个 tmpfs 里当作第一个根文件系统。**

它存在的唯一理由是：**内核要挂载真正的根，可能需要驱动和工具，而驱动和工具在根上。**

```
鸡生蛋问题：
  根分区在 NVMe 上    → 需要 nvme 驱动
  nvme 驱动是模块     → 在 /lib/modules 里
  /lib/modules 在根上 → 在 NVMe 上 ← 循环了
```

initramfs 打破这个循环：把必要的模块和挂载工具**塞进内核镜像本身**，先用它把真根挂起来，再切换过去。

---

## initramfs vs initrd（不是一回事）

| | initrd（老，已淘汰） | initramfs（现代） |
|--|---------------------|------------------|
| 形态 | 一个**块设备镜像**（有文件系统） | 一个 **cpio 归档**（打包即归档） |
| 内核需要 | 必须有对应文件系统驱动 + ramdisk 驱动 | **零驱动**（tmpfs 是内核内置的） |
| 内存 | 固定大小，用不完也占着 | 随用随长，删文件能释放 |
| 缓存 | 走了两层缓存（ramdisk + 页缓存） | 直接是页缓存，**更省** |
| 位置 | 独立文件，bootloader 加载 | **可以编进内核镜像** |

⭐ **现代内核只有 initramfs**。你看到的 `/boot/initrd.img-*` 文件名，内容其实也是 cpio（名字是历史遗留）。

## 内核源码里的关键判据（v6.6 `init/main.c`）

这是理解 initramfs 最重要的一段，值得记住：

```c
/* init/main.c:1558 */
if (init_eaccess(ramdisk_execute_command) != 0) {
        ramdisk_execute_command = NULL;
        prepare_namespace();          /* ← 没有 /init 才去挂真正的根设备 */
}
```

翻译成人话：

```
内核启动到这儿时，rootfs 里已经塞好了 initramfs 的内容
        │
        ├─ 有 /init 且可执行  → 就把 /init 当 PID 1，真根由它自己去挂（pivot_root）
        │
        └─ 没有 /init         → 内核自己调 prepare_namespace()，按 root= 参数挂设备
```

⭐ **这条判据解释了两件常见困惑**：

1. 为什么有 initramfs 时 `root=` 参数常常看起来"没用" → 因为真根是 initramfs 里的脚本挂的，`root=` 只是被那个脚本读去用。
2. 为什么**去掉 initramfs 后系统起不来** → 内核直接去挂 `root=`，但需要的驱动是模块、还在没挂上的根上 → 死锁。

## 三种用法，按阶段选

| 用法 | 命令 | 适合 |
|------|------|------|
| **编进内核**（bring-up 首选） | `CONFIG_INITRAMFS_SOURCE=/path/to/rootfs` | 单镜像，bootloader 不用管；**改一次要重编内核** |
| **独立文件** | bootloader 加载 `initrd.img` | 发行版做法，换 initramfs 不用重编内核 |
| **不用** | `CONFIG_INITRAMFS_SOURCE=""` | 内核自己挂根（驱动必须全 `=y` 编进内核） |

**Pi 5 的特殊情况**：默认走固件启动 + `config.txt`，通常**不用 initramfs**（内核驱动都编进去了，根直接在 SD 卡上）。想用它就加一行：

```
# /boot/firmware/config.txt
initramfs initrd.img followkernel
```

## 制作：三种打包方式

```bash
cd /tmp/rootfs

# ① 经典 cpio（最通用）
find . | cpio -o -H newc | gzip > /tmp/initrd.img

# ② 内核自带脚本（推荐：会处理权限、设备节点）
/usr/src/linux/scripts/gen_initramfs_list.sh -o /tmp/initrd.img /tmp/rootfs

# ③ 内核直接编进去
#    make menuconfig → General setup → Initramfs source file(s) → /tmp/rootfs
#    或者写进 defconfig：
#    CONFIG_INITRAMFS_SOURCE="/tmp/rootfs"
```

| 参数 | 说明 |
|------|------|
| `-H newc` | **必须用 newc 格式**，内核只认这一种（"new ASCII with checksum"） |
| `gzip` | 可选；内核能自动解压 gzip/xz/lz4/zstd（需开对应 `CONFIG_RD_*`） |
| `find .` | **要在 rootfs 根目录里执行**，否则路径会带前缀导致 `/init` 找不到 |

## 怎么验证做对了

```bash
# ① 解开来检查（不破坏原文件）
mkdir /tmp/chk && cd /tmp/chk && zcat /tmp/initrd.img | cpio -idmv
ls -l /tmp/chk/init /tmp/chk/dev/console     # 关键两项要在

# ② 启动时加内核参数看看内核怎么说
#    cmdline 加： rdinit=/bin/sh
#    如果直接进 shell，说明 initramfs 被正确解开了

# ③ 看内核日志
dmesg | grep -i -E 'initramfs|unpacking|rootfs|Trying to unpack'
# 正常会看到：Trying to unpack rootfs image as initramfs
#            Freeing initrd memory: xxxxK
```

## 常见故障对照

| 现象 | 原因 | 修法 |
|------|------|------|
| `Failed to execute /init (error -2)` | cpio 里没有 `/init`（或路径带了前缀） | 在 rootfs 根执行 `find .`；确认 `/init` 存在 |
| `Warning: unable to open an initial console.` | 缺 `/dev/console` | `mknod dev/console c 5 1` |
| `Kernel panic - not syncing: VFS: Unable to mount root fs` | 无 initramfs 且 `root=` 指错/驱动是模块 | 做 initramfs，或把磁盘/文件系统驱动改成 `=y` |
| 起来后 shell 一敲命令就 `not found` | 只有 busybox 没建符号链接 | `busybox --install -s` |
| 改了 initramfs 内容但启动后没变 | **它编进内核了**，改文件没用 | 要么重编内核，要么改成独立文件加载 |

## HFT / 嵌入式关联

- **initramfs 是"最小可信执行环境"的原型**：它的价值在于**不依赖外部状态就能把系统拉到可用**。HFT 的灾备设计同理 —— 恢复流程不能依赖"那个坏掉的盘上还有什么"。
- **`CONFIG_INITRAMFS_SOURCE` 让 rootfs 变成内核的一部分**，代价是改一次重编一次。这跟"把配置编进二进制 vs 运行时读取"是同一个权衡：**启动可靠性 vs 迭代速度**。bring-up 期选可靠，产品期选可迭代。
- 「鸡生蛋」的解法（**用一个小的自足层去引导大的层**）在系统设计里反复出现：bootloader → 内核 → initramfs → 真根 → 服务。每一层都只解决"让下一层能跑起来"这一个问题。

<details>
<summary>Q1：initrd 和 initramfs 名字这么像，怎么快速区分？</summary>

看它是不是**块设备镜像**：

```bash
file /boot/initrd.img-6.6.0
# initramfs → ASCII cpio archive (SVR4 with no CRC)  或 gzip compressed data
# initrd    → Linux rev 1.0 ext2 filesystem data
```

现代发行版（包括名字还叫 initrd 的那些）**都是 cpio**，initrd 那套已经在内核 2.6 时代被取代了。文件名只是历史遗留。
</details>

<details>
<summary>Q2：为什么有的系统可以完全不用 initramfs？</summary>

因为它**不需要任何模块就能挂上根**：

- 存储控制器驱动编进内核（`=y` 而不是 `=m`）
- 文件系统驱动编进内核（ext4 等）
- 根设备可以直接用**内核认识的标识**指定（`root=/dev/mmcblk0p2` 或 `root=PARTUUID=...`）

这种情况下内核 `prepare_namespace()` 能一步到位，跳过 initramfs。**代价是内核变大、驱动无法按需加载。**

发行版不能这么做（要支持千奇百怪的硬件，驱动只能做成模块）→ 所以必须有 initramfs。
**嵌入式往往可以这么做**（硬件固定）→ 这也是嵌入式系统启动更快的根本原因之一。
</details>

<details>
<summary>Q3：<code>rdinit=</code> 和 <code>init=</code> 有什么区别？</summary>

| 参数 | 设置谁 | 用在哪 |
|------|--------|--------|
| `rdinit=` | `ramdisk_execute_command`（默认 `/init`） | **initramfs 里的** PID 1 |
| `init=` | `execute_command` | **最终 rootfs 里的** PID 1 |

两个都在 `init/main.c` 里有 `__setup()` 注册（`:587` 和 `:599`）。

调试时 `rdinit=/bin/sh` 极好用：内核解完 initramfs 直接给你一个 shell，**在它去挂真根之前** —— 这时你能用 `blkid`、`mount` 手动排查为什么根挂不上。
</details>
