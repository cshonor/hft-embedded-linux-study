# Buildroot：从零到一个可启动镜像

> **本节讲什么：** 用 Buildroot 在几十分钟内出一个能启动的镜像，理解它的目录结构与 Kconfig 逻辑，以及**它与 Yocto 到底该怎么选**。
> **前置：** [5.1 最小 rootfs](./5.1-minimal-rootfs-by-hand.md) · [5.2 initramfs](./5.2-initramfs.md)
> **动手：** [P5 · B2](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch6 · Primer Ch6

---

## Buildroot 是什么（一句话）

**一个用 Kconfig + make 把「交叉工具链 + 内核 + bootloader + rootfs」全编出来的构建系统。**

它的核心卖点：**概念栈和内核完全同构**。你学会 `menuconfig` 一次，内核和 Buildroot 都能用。这一点对学习阶段的价值远超"省事"。

---

## 三件套怎么选（为什么主线走 Buildroot）

| | Buildroot | Yocto | 手工 |
|--|-----------|-------|------|
| 首个可启动镜像 | **几十分钟** | 数小时起 | 几小时（但学到最多） |
| 磁盘占用 | 几个 GB | **几十 GB** | 几百 MB |
| 概念栈 | **Kconfig + make**（与内核同构） | recipe / layer / bitbake（另学一套） | 无 |
| 产物 | **一个完整镜像** | 一个可长期演进的发行版 | 一个 rootfs |
| 包管理 | 无（改配置重编） | 有（rpm/ipk/deb，可增量升级单个包） | 无 |
| 适合 | 学启动链、快速迭代、固定硬件产品 | 多机型、产品化、需要在线升级包 | 理解原理 |

> ⭐ **Yocto 是量产的事实标准，但不是学习入口。** 它的复杂度是为"几十种机型 + 长期维护 + 合规审计"设计的，你一个人一块板子用不上，却要为它付出几小时构建 + 几十 GB 磁盘 + 一整套新概念。
> **做产品镜像那天再上 Yocto，别让它占掉主线时间。**

## 第一次构建（可直接抄）

```bash
git clone https://github.com/buildroot/buildroot
cd buildroot

# ① 选基线配置（Pi 5）
make raspberrypi5_defconfig

# ② 按需调整
make menuconfig
#   Target options      → 一般 defconfig 已设好，别乱动
#   Toolchain           → glibc/musl、C++ 支持、gcc 版本   ★ 常改
#   System configuration→ root 密码、hostname、/etc/issue   ★ 常改
#   Target packages     → BusyBox/OpenSSH/dropbear/i2c-tools...
#   Filesystem images   → 输出格式（ext4 / tar / cpio / sdcard.img）

# ③ 编（首次几十分钟，之后增量很快）
make -j$(nproc) 2>&1 | tee build.log

# ④ 产物
ls output/images/
#   sdcard.img      ← 直接 dd 到 SD 卡的完整镜像
#   rootfs.tar      ← rootfs 归档
#   Image / zImage  ← 内核
#   bcm2712-rpi-5-b.dtb
```

## 目录结构（出问题时知道去哪找）

```
buildroot/
├── output/
│   ├── build/        ← 每个包的源码与构建目录  ★ 排查编译失败看这里
│   ├── host/         ← 主机工具 + 生成的交叉工具链
│   ├── images/       ← 最终产物
│   ├── target/       ← ★ 未打包的 rootfs（想改文件就直接改这里再 make）
│   └── staging/      ← sysroot（头文件和库）
├── package/          ← 所有软件包的 recipe（.mk + Config.in）
├── board/            ← 板级配置（内核配置片段、genimage.cfg、post-build 脚本）
└── configs/          ← defconfig 文件
```

⚠️ **`output/target/` 里的改动会在下次 `make` 时被覆盖**（它是从各包安装出来的）。要持久修改，用后面讲的 **rootfs overlay** 或 **post-build script**。

## 四个必知的定制手段

### ① rootfs overlay（最常用）

```
my-overlay/
└── etc/
    ├── inittab
    └── network/interfaces
```

```bash
make menuconfig
# System configuration → Root filesystem overlay directories → /path/to/my-overlay
```

overlay 里的文件会**覆盖** target 里的同名文件，其余合并。改配置、改脚本都靠它。

### ② post-build script

```bash
# System configuration → Custom scripts to run before creating filesystem images
# 例：把交叉编译好的自研程序拷进 rootfs
cat > board/pi5/post-build.sh <<'EOF'
#!/bin/sh
cp "$BR2_EXTERNAL/../app/myapp" "$TARGET_DIR/usr/bin/"
chmod +x "$TARGET_DIR/usr/bin/myapp"
EOF
```

`$TARGET_DIR` 是环境变量，**永远是它**，不要写死路径。

### ③ 保存自己的 defconfig

```bash
make savedefconfig                 # 产出 defconfig（去冗余）
cp defconfig configs/myboard_defconfig
```

⭐ **`make savedefconfig` 而不是直接拷 `.config`** —— 前者只保存与默认值不同的项，可移植；后者几千行，升级 Buildroot 后容易冲突。

### ④ BR2_EXTERNAL（把自定义内容放在 Buildroot 树之外）

```
my-project/
├── Config.in
├── external.mk
├── configs/myboard_defconfig
├── board/myboard/{post-build.sh,genimage.cfg,rootfs-overlay/}
└── package/myapp/{Config.in,myapp.mk}
```

```bash
make BR2_EXTERNAL=/path/to/my-project myboard_defconfig
```

⭐ **正经项目一定要用 `BR2_EXTERNAL`**。直接改 Buildroot 源码树会导致 `git pull` 升级时冲突，也没法把自己的东西单独版本管理。

## 常见故障对照

| 现象 | 原因 | 修法 |
|------|------|------|
| 编译某包失败 | 依赖缺/源码下载失败 | 看 `output/build/<pkg>/` 下的日志；`make <pkg>-dirclean` 后重试 |
| 下载慢/失败 | 源码在境外服务器 | 设 `BR2_PRIMARY_SITE` 镜像；或手动把 tarball 放进 `dl/` |
| 改了 target/ 里的文件，重编后没了 | 它本来就是生成物 | 改用 overlay 或 post-build |
| 镜像能起但没网络 | 没开 DHCP 客户端 / 没配 interface | 开 `ifupdown` 或 `systemd-networkd`，配 `/etc/network/interfaces` |
| root 登录不了 | `/etc/shadow` 里 root 没密码、或 getty 没起 | System configuration 里设 root 密码；检查 inittab |
| `make` 报 host 缺工具 | 缺 `which/sed/make/gcc/g++` 等 | 看官方文档 "Mandatory packages"，apt 装齐 |

**排查第一定律**：`make` 失败时，真正的错误信息在**它调用的那条命令的输出里**，往往被几百行 make 噪音盖住。用 `make 2>&1 | tee build.log` 再 `grep -i error build.log`，或直接看 `output/build/<pkg>-<ver>/` 下的日志。

## HFT / 嵌入式关联

- **Buildroot 的"整体重建"哲学值得借鉴**：它不追求增量升级单个包，而是**每次产出一个完整、可复现的镜像**。HFT 的交易镜像同样如此 —— 你不会在生产机上 `apt upgrade` 一个库，而是重新出一个镜像整体替换。**"不可变基础设施"在嵌入式是默认形态，在数据中心是最佳实践。**
- **构建时间 vs 迭代速度的权衡**：Buildroot 首次慢、之后快（ccache 可进一步加速）。HFT 的 C++ 项目同样要靠 ccache / 分布式编译把迭代周期压到分钟级 —— **反馈周期决定了你能试错多少次，也就决定了最终质量。**
- `BR2_EXTERNAL` 的"自定义与上游分离"是标准的工程纪律：**不改上游、把差异外置**。这条在任何依赖管理场景都成立。

<details>
<summary>Q1：什么时候该从 Buildroot 换到 Yocto？</summary>

出现下面任一信号：

1. **需要在线升级单个包**（不能整机重刷）
2. **要支持多款硬件**，且希望复用 recipe
3. **需要合规审计**（SPDX、许可证清单、CVE 追踪 —— Yocto 原生支持）
4. **团队 > 1 人**，需要 layer 来划分职责边界
5. 有长期维护需求（几年甚至十年）

一个人的学习项目、一块板子、一个固定形态的产品镜像 —— **Buildroot 完全够，而且更省命。**
</details>

<details>
<summary>Q2：<code>output/target/</code> 里的文件我明明改了，为什么重编后没了？</summary>

因为它不是源码，是**生成物**：每个包 `make install` 到 staging/target，最后打包成镜像。你改的是中间产物，下次 `make` 会重新生成。

**正确的持久化方式有三种**：

| 方式 | 适合 |
|------|------|
| rootfs overlay | 改配置文件（`/etc/...`） |
| post-build script | 拷自研二进制、建目录、改权限 |
| 写自己的 package（`.mk` + `Config.in`） | 从源码编一个第三方/自研软件 |

判据：**这个改动需要"被版本管理"吗？** 需要就做成 overlay 或 package；临时调试可以直接改 target 再 `make` 一次（不重编包，只重打包）。
</details>

<details>
<summary>Q3：<code>savedefconfig</code> 和直接拷贝 <code>.config</code> 差在哪？</summary>

`.config` 是**完整快照**（几千行，包含所有默认值）；`defconfig` 只保存**与默认值不同的项**（通常几十行）。

后果差异：
- Buildroot / 内核**升级**后，配置项的名字和默认值可能变化。完整 `.config` 会因为"某项已不存在"而报错或产生怪异行为；`defconfig` 会自动套用新默认值，冲突最小。
- `defconfig` 能一眼看出"我到底改了什么"—— **这才是配置该有的样子**。

**永远 `make savedefconfig`。**
</details>
