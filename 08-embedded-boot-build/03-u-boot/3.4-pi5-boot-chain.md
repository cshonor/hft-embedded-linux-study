# Pi 5 从上电到 `start_kernel`：七级接力，与「谁把 DTB 交给内核」

> **本节讲什么：** 把 Pi 5 从按下电源到 Linux 内核第一行 C 代码之间的每一级都列出来——每一级是谁、跑在哪个核上、存在什么介质里、能不能被你换掉。核心结论：**Pi 5 与 Pi 4 的启动链不是"小改"，`start*.elf` 这一级整个消失了。**
> **前置：** [01-orientation](../01-orientation/) · [1.3 先盯住 SoC](../01-orientation/1.3-focus-on-soc.md)
> **动手：** [P5 · B1/B3](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch4–5 · Primer Ch7 · Primer Ch10
> **对应验收：** 03-u-boot 第 1 条「能画出 Pi 5 从上电到 `start_kernel` 的完整链路」

---

## 一句话

Pi 5 的启动是 **VPU（VideoCore GPU）先醒，ARM 后醒**：GPU 把内核和 DTB 搬到内存、把 ARM 核从复位里放出来、给它一小段 `armstub` 当"引路人"，然后 ARM 才第一次执行指令。

**这和 PC 完全不同**——PC 是 CPU 从 reset vector 直接开跑，自己去找固件。Pi 上 ARM 核是被"喂"起来的。

---

## 完整链路（Pi 5 / BCM2712）

```
┌─ 第 0 级：片内 ROM（OTP，烧死在 SoC 里，不可改）───────────────┐
│  上电 → VPU 先复位并开跑（ARM 核此时还在复位中）                  │
│  只会做一件事：从板载 SPI EEPROM 里把下一级读出来                 │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ 第 1 级：EEPROM bootloader（板载 SPI Flash，可更新）───────────┐
│  rpi-eeprom-update 更新的就是它                                 │
│  能力很弱：只会读 FAT 分区，找启动介质（SD / NVMe / USB / 网络）  │
│  ⚠️ 这就是为什么 /boot 必须独立成 FAT 小分区                      │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ 第 2 级：VPU 固件（★ Pi 5 起在 EEPROM 里，不再在 SD 卡上）─────┐
│  Pi 4 及更早：start.elf / start4.elf + fixup.dat，躺在 SD 卡      │
│  Pi 5：所有 VPU blob 已移入 EEPROM，SD 卡上**没有** elf 文件      │
│  干活：初始化内存/时钟/外设 → 读 config.txt → 应用 dtoverlay       │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ 第 3 级：armstub（armstub8-2712.bin，ARM 代码）────────────────┐
│  一小段在 EL3 跑的 ARM 程序，默认存在固件里按型号自动选           │
│  Pi 5 用的是 TF-A BL31，负责 PSCI（核启动、电源管理、reboot）      │
│  官方文档原话：Its job is to set up low-level hardware like the   │
│                interrupt controller before passing control to the │
│                kernel.                                            │
│  收尾：把异常级别降到 EL2，跳内核                                 │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ 第 4 级：Linux arm64 早期汇编（arch/arm64/kernel/head.S）───────┐
│  primary_entry → record_mmu_state → preserve_boot_args(x0=DTB)   │
│                → create_idmap → init_kernel_el → __cpu_setup      │
│                → __primary_switch → __primary_switched            │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ 第 5 级：start_kernel()（init/main.c）—— 第一行 C 代码 ──────────┐
│  从这里开始才是你熟悉的内核世界：initcall、驱动、挂根、找 init      │
│  → 详见 [06-boot-to-shell/6.1](../06-boot-to-shell/6.1-kernel-init-search.md) │
└────────────────────────────────────────────────────────────────┘
```

## 逐级对照表

| 级 | 谁 | 存在哪 | 跑在哪个核 | 你能改吗 |
|---|---|---|---|---|
| 0 | 片内 ROM（OTP） | SoC 掩膜 | VPU | ❌ 烧死不可改 |
| 1 | EEPROM bootloader | **板载 SPI Flash** | VPU | ✅ `rpi-eeprom-update` |
| 2 | VPU 固件 | **EEPROM**（Pi 4 在 SD 卡） | VPU | ❌ 闭源 |
| 3 | armstub（TF-A BL31） | 固件内 / SD 卡可覆盖 | ARM @ EL3 | ✅ `armstub=` 指定 |
| 4 | Linux head.S | `kernel_2712.img` | ARM @ EL2 | ✅ 你编的内核 |
| 5 | `start_kernel()` | 同上 | ARM @ EL2 | ✅ |

⭐ **"能不能改"这一列是排查时的分水岭**：第 0–2 级出问题你只能换固件/换卡；第 3 级往上才是你的地盘。

## ⭐ Pi 5 与 Pi 4 的三处关键差别

这三处**凭 Pi 4 经验推 Pi 5 必错**：

| | Pi 4（BCM2711） | Pi 5（BCM2712） |
|---|---|---|
| **VPU 固件位置** | SD 卡上的 `start4.elf` + `fixup4.dat` | **移入 EEPROM**，SD 卡上没有 elf 文件 |
| **bootcode.bin** | 不需要（同 Pi 5） | 不需要（已被 EEPROM 取代） |
| **config.txt** | 可选 | ⚠️ **必须存在且非空**，否则不启动 |

依据（官方文档原话）：

> The Raspberry Pi 5 does not use elf files. The firmware is self-contained within the bootloader EEPROM.

依据（TF-A 官方移植文档）：

> The boot process is essentially the same, the only notable difference being that **all VPU blobs have been moved into EEPROM** (former `start4.elf` & `fixup4.dat`). There's also a custom BL31 TF-A armstub included for PSCI.

> ⚠️ **我之前的笔记写错过这里。** 3.2 里那句「上电 → 片内 ROM → SD 卡上的 start4.elf」和 3.3 里把 `start4.elf / fixup4.dat` 标成"第一阶段"，都是 Pi 4 的写法被搬到了 Pi 5。**Pi 5 的 SD 卡上根本没有这两个文件**（可以去 `/boot/firmware/` 自己 `ls` 验证）。

## 内核镜像：为什么有两个

| 文件 | 页大小 | 适用 |
|---|---|---|
| `kernel_2712.img` | **16 KB** | Pi 5 / CM5 / Pi 500 首选 |
| `kernel8.img` | 4 KB | 通用 64 位兜底（Pi 2–5 都能跑） |

固件**优先加载 `kernel_2712.img`，不存在才退回 `kernel8.img`**。

差别只在 defconfig 的一项（`bcm2712_defconfig` vs `bcm2711_defconfig`）：

```diff
-CONFIG_LOCALVERSION="-v8"
+CONFIG_LOCALVERSION="-v8-16k"
+CONFIG_ARM64_16K_PAGES=y
+CONFIG_ARCH_MMAP_RND_BITS=18
+CONFIG_ARCH_MMAP_RND_COMPAT_BITS=11
```

⭐ **自编内核时最容易踩的坑：页大小不一致。** 你用 `bcm2711_defconfig`（4K）编出来的内核能启动，但**用同一份源码编的模块如果和内核页大小不同，加载会失败**——因为 `PAGE_SHIFT` 变了，`struct page` 布局、`mmap` 粒度全跟着变。

> 判据：`uname -r` 里带 **`-v8-16k`** 才是 16K 页内核。看到 `-v8` 说明你跑到 `kernel8.img` 上了。

另外：**Pi 5 只支持 64 位内核**，`arm_64bit` 这个开关在 Pi 5 及之后被忽略（官方文档：Models that only support a 64-bit kernel ignore this flag）。

## 交接约定：内核接过来时手里有什么

固件跳进内核的那一刻，ARM 的状态是被**约定死的**（arm64 boot protocol）：

| 约定 | 值 |
|---|---|
| `x0` | **DTB 的物理地址** ← 设备树就是这么来的 |
| `x1`–`x3` | 必须为 0 |
| MMU | 关 |
| D-cache | 关（I-cache 无要求） |
| 异常级别 | EL2（或 EL1） |

对应源码（v6.6 `arch/arm64/kernel/head.S:163`）——`preserve_boot_args` 第一件事就是把 `x0` 存进 `x21`：

```asm
SYM_CODE_START_LOCAL(preserve_boot_args)
	mov	x21, x0				// x21=FDT
	adr_l	x0, boot_args
	stp	x21, x1, [x0]			// x0 .. x3 at kernel entry
	stp	x2, x3, [x0, #16]
```

⭐ **这就是"DTB 由谁生成、放在哪、内核怎么用"的答案**：DTB 由 **VPU 固件**在加载阶段放进内存（文件名 `bcm2712-rpi-5-b.dtb`，地址由 VPU 选，`config.txt` 里可用 `device_tree_address=` 改），内核只通过 `x0` 拿到一个地址，**它不知道这个文件叫什么、在哪个分区**。

所以「换 DTB」= 换 `/boot/firmware/` 里的那个文件 + 重启，内核本身不需要重新编译，但**必须同源**——见 [04-kernel-build/4.2](../04-kernel-build/4.2-cross-compile-pi5.md)。

## 内核侧的 EL2 处理（源码核对）

`init_kernel_el`（v6.6 `head.S:547`）第一件事是读当前异常级别，然后分流：

```asm
SYM_FUNC_START(init_kernel_el)
	mrs	x1, CurrentEL
	cmp	x1, #CurrentEL_EL2
	b.eq	init_el2          /* 走 EL2 分支 */

SYM_INNER_LABEL(init_el1, ...)   /* 否则按 EL1 起步 */
	...
	mov	w0, #BOOT_CPU_MODE_EL1
	eret
```

走 EL2 分支时它会：

1. 设 `HCR_EL2 = HCR_HOST_NVHE_FLAGS`
2. 装 `__hyp_stub_vectors` 到 `VBAR_EL2`
3. 检查 `HCR_EL2.E2H` 决定是否走 VHE 路径

⭐ **这解释了 Pi 上的两个常见困惑：**

- 为什么 `CurrentEL` 是 **EL2 而不是 EL1** → 因为固件/armstub 交到 EL2，内核保留它（为了能跑 KVM / VHE）
- 为什么同一份内核在 QEMU `-M virt` 上可能跑到 EL1 → 那边没 armstub，直接 EL1 起步

## 卡在哪一级，对应什么现象

| 现象 | 卡住的级 | 为什么 |
|---|---|---|
| 绿灯完全不闪 / 无任何串口输出 | 0–1 | EEPROM 没找到启动介质，或介质没 FAT 分区 |
| 绿灯闪几下后规律闪 4 次 | 1–2 | `start*.elf` 缺失——**但 Pi 5 上是 config.txt 缺失/空**（Pi 5 必须非空 config.txt） |
| 有固件日志但停在 `Starting kernel ...` | 3–4 | DTB 与内核不匹配 / `armstub` 错 / 串口配置错 |
| 内核开始解压后崩 | 4 | 页大小不匹配、内核编译配置错 |
| 进了内核但外设全不工作 | 2 的 DTB 环节 | DTB 没更新或 `overlays` 没拷 |

> 判据：**看串口（UART debug port，115200 8n1）**。HDMI 出图是第 2 级之后的事，卡在 0–2 级时屏幕永远是黑的——这也是为什么做嵌入式必须先接串口，见 [06-boot-to-shell/6.2](../06-boot-to-shell/6.2-console-and-serial.md)。

## HFT / 嵌入式关联

- **16K 页大小的真实代价/收益**：更大的页 = 同样 TLB 条目数覆盖 4 倍内存 → 大工作集场景（行情回放、盘口重建）TLB miss 显著下降。代价是 mmap 粒度变 16K、小对象浪费更多，以及**模块必须与内核页大小同源编**。做低延迟内存池时 `mmap` 的对齐假设要跟着改。
- **启动链长 = 启动慢 + 故障面大**。HFT 网关关注的是稳态延迟，不是启动速度，但**"能不能在 30 秒内恢复服务"**是运维指标——链路越短可控性越强。这也是量产设备愿意上 U-Boot 的理由：**把 0–2 级这三段闭源黑盒换成可读可控的一段**。
- **EEPROM 可更新是双刃剑**：能修启动 bug，也意味着**攻击者有持久化的落点**（Secure Boot 就是要堵这个）。做产品时 EEPROM 要锁版本并校验。
- **`x0` 传 DTB 这个约定的普适性**：所有 arm64 平台都一样。搞懂一次，换到瑞芯微/全志/飞腾的板子上同样成立。

## 自测

<details>
<summary>Q1：Pi 5 的 SD 卡 boot 分区里，有没有 start4.elf？</summary>

**没有。** 官方文档明确：Pi 5 不用 elf 文件，固件自包含在 EEPROM 里。

Pi 4 及更早才有 `start4.elf` + `fixup4.dat` 在 SD 卡上。

验证方法：`ls /boot/firmware/*.elf` → Pi 5 上无输出。
</details>

<details>
<summary>Q2：上电后第一个执行指令的是 ARM 核还是别的？</summary>

**是 VPU（VideoCore GPU），不是 ARM。**

ARM 核一开始被保持在复位状态，由 VPU 固件初始化完内存/时钟后释放，并喂给它 armstub 的入口地址。

这是树莓派 boot 与 PC 最本质的区别——PC 的 CPU 自己从 reset vector 开跑并找固件。
</details>

<details>
<summary>Q3：内核是怎么知道设备树在哪的？它去读 /boot/firmware/bcm2712-rpi-5-b.dtb 了吗？</summary>

**它不知道文件名，也不知道分区。** 内核只在 `x0` 寄存器里收到一个**物理地址**——DTB 已经被 VPU 固件搬进内存了。

`head.S:163` 的 `preserve_boot_args` 第一句 `mov x21, x0  // x21=FDT` 就是在保存这个地址。

所以：换 DTB 只要换文件（VPU 会重新搬），但**内核与 DTB 必须同源同版本**，否则 `compatible` 对不上、设备不 probe 且不报错。
</details>

<details>
<summary>Q4：为什么 Pi 5 必须有一个非空的 config.txt？</summary>

Pi 5 的固件把配置读取作为启动流程的一个**必需环节**——找不到（或空）就直接停在第 1–2 级。

这也是 Pi 5「绿灯规律闪 4 次」最常见的原因：不是内核坏了，是 config.txt 没了。

实践含义：**别把 config.txt 当可选文件删掉**，哪怕里面只写一行 `enable_uart=1`。
</details>

<details>
<summary>Q5：自编内核用 bcm2711_defconfig 会怎样？</summary>

能启动，但跑在 **4K 页**上（`uname -r` 显示 `-v8` 而不是 `-v8-16k`），且：

- 丢掉 Pi 5 的页大小优化
- **如果模块用 16K 页编、内核用 4K 页（或反之），模块加载失败**——`PAGE_SHIFT` 不同导致结构体布局不一致

正确做法：`make bcm2712_defconfig`，并且内核与模块用同一份配置一次编全（见 [4.2 交叉编译](../04-kernel-build/4.2-cross-compile-pi5.md)）。
</details>
