导读

本节讲什么： 拉内核树、选配置、交叉编译、装模块与 DTB，最终替换板子上的运行内核。 对应动手： P5 · B1（bcm2712_defconfig 级配置 / 裁剪 / 交叉编译 / 替换运行内核）

要点

概念 说明
defconfig 厂商给的基线配置。永远从它开始，不要从零 menuconfig
裁剪的意义 少一个驱动 = 少一份代码进内核 = 少一次 probe = 启动更快、攻击面更小
=y vs =m 编进内核 vs 编成可加载模块。板级必要驱动（如 MMC、串口）必须 =y，否则 initrd 都救不了
DTB 要一起编 内核和 DTB 必须同源同版本，否则 compatible 对不上
modules_install 模块要装到 rootfs 的 /lib/modules/$(uname -r)，版本号必须完全一致

关键命令（Pi 5 · aarch64）

# 拉源码
git clone --depth=1 --branch rpi-6.12.y https://github.com/raspberrypi/linux
cd linux

# 配置
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- bcm2712_defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- menuconfig   # 按需裁剪

# 编译（镜像 + 模块 + DTB）
make -j$(nproc) ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- Image.gz modules dtbs

# 安装模块到 rootfs 挂载点
sudo make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     INSTALL_MOD_PATH=/mnt/rootfs modules_install

校验产物：

file arch/arm64/boot/Image.gz                 # gzip compressed
ls arch/arm64/boot/dts/broadcom/*.dtb | head

回滚预案： 永远保留原内核副本（config.txt 里用 kernel= 指向新内核，改名即可回退）。刷坏 bootloader 的代价远大于刷坏内核。

HFT / 嵌入式关联

  • 裁剪 = 延迟确定性：无关驱动越少，中断处理路径上的不确定性越少。
  • PREEMPT_RT：低延迟场景要开 CONFIG_PREEMPT_RT，但它会牺牲一部分吞吐——这是 HFT 里"延迟 vs 吞吐"经典权衡在内核配置层的体现（深入见 05-linux-kernel / 05.5）。
  • 内核版本号必须和模块路径严格对应，这个"版本即契约"的思路在 02-toolchain 的 sysroot 那里已经出现过一次。

4.1

Kconfig 与 defconfig：内核配置的三种符号与裁剪思路

本节讲什么： .config 是怎么生成的、=y / =m / =n 的区别、以及裁剪内核到底在裁什么。 前置： 02-toolchain（交叉编译器就位）
后续： 4.2 Pi 5 交叉编译实战 · 4.3 模块与版本魔法
卡住查书： MELP Ch4 · Primer Ch4

配置从哪来

arch/arm64/configs/defconfig        ← 架构默认（通用，很大）
arch/arm64/configs/bcm2712_defconfig  ← 厂商基线（Pi 5，★ 从这里开始）
        │  make bcm2712_defconfig
        ▼
     .config                        ← 实际生效的配置（隐藏文件）
        │  make menuconfig 修改
        ▼
     .config（更新） → make savedefconfig → defconfig（最小化回写）

永远从厂商 defconfig 开始，不要从 make defconfig 或 allnoconfig 起步。 前者是"能跑的基线"，后者是"学术练习"。

三种符号

符号 含义 产物 后果
=y 编进内核镜像 代码进 Image，启动时就在 功能一定可用；镜像变大
=m 编成可加载模块 生成 .ko，需要 insmod 或自动加载 镜像小；但依赖 rootfs 里有对应 .ko
=n 不编译 — 功能不存在

关键判断：哪些必须 =y？

内核启动 → 挂载 rootfs → 才能读 .ko 文件
                    ↑
        这一步之前需要的功能，必须编进内核（=y）

所以这些必须 =y：

类别 例子
存储/文件系统 MMC/SD 控制器、ext4、NVMe（若根分区在 NVMe）
块设备层 CONFIG_BLK_DEV_*
控制台 串口驱动（8250 / amba-pl011）、CONFIG_SERIAL_*
网络启动相关 NFS root 时需要网卡驱动 + CONFIG_IP_PNP

反例： 把 ext4 编成 =m，内核启动挂载 rootfs 时找不到模块文件（因为 rootfs 还没挂上）→ Kernel panic - not syncing: VFS: Unable to mount root fs。这是新手最经典的启动失败原因。

常用配置命令

命令 作用
make bcm2712_defconfig 载入厂商基线
make menuconfig 交互式（ncurses）修改
make nconfig 新版交互界面（支持跳转搜索）
make oldconfig 基于旧 .config 补问新增选项
make olddefconfig 同上，新增选项全取默认值（脚本/CI 用这个）
make savedefconfig 把当前 .config 最小化后回写 defconfig
make localmodconfig 只保留当前已加载的模块（裁剪利器） 
# 裁剪流程（本机已跑着目标系统的前提下）
make localmodconfig     # 按当前加载的模块大幅裁剪
make menuconfig         # 手工确认
make savedefconfig      # 回写成最小 defconfig
cp defconfig arch/arm64/configs/my_custom_defconfig

menuconfig 里按 / 可以搜索符号名，显示结果里有 Symbol: XXX [=y] 和依赖关系。
找不到某个选项，99% 是它的依赖没满足 —— 看搜索结果里的 Depends on:。

裁剪到底在裁什么

裁掉的东西 收益
用不到的驱动 镜像变小；少一次 probe；少一份代码占内存
用不到的子系统（如 CONFIG_BT、CONFIG_WIRELESS） 启动更快；攻击面更小
调试选项（CONFIG_DEBUG_*、CONFIG_KASAN） 显著提升性能，但丢掉调试能力
CONFIG_MODULES=n（全静态） 无模块加载开销；但失去灵活性

反面：=m 不是万能的。 模块相比 =y：

  • ✅ 不占内核镜像空间
  • ✅ 可以单独更新
  • ❌ 有加载开销（启动时 udev 遍历 + 加载）
  • ❌ 依赖 rootfs 里有对应文件（版本还必须匹配，见 4.3）

HFT / 嵌入式关联

  • 裁剪 = 减少不确定性。 每少一个驱动，就少一个可能在中断上下文跑、抢锁、制造延迟尖刺的代码路径。HFT 生产内核基本都是"什么都不开"的极简配置。
  • PREEMPT_RT 是配置层的第一个大抉择：CONFIG_PREEMPT_RT 把大部分自旋锁变成可抢占的 rt_mutex、把中断线程化。用吞吐换延迟确定性 —— 这是"延迟 vs 吞吐"权衡在配置层的体现（深入见 05.5-modern-kernel）。
  • 配置即契约：.config 决定了内核 ABI，模块必须与之匹配。这个"版本一致"的思路在容器镜像、在 HFT 的部署包里都是同一条纪律。

代码自测

Q1：把根文件系统所在的磁盘驱动编成 =m 会怎样？

启动失败：Kernel panic - not syncing: VFS: Unable to mount root fs。 因为加载 .ko 需要先挂载 rootfs，而挂载 rootfs 需要该驱动 —— 死锁。 解决：用 initramfs/initrd 先加载模块再挂载真 rootfs，或者干脆把驱动改回 =y。

Q2：menuconfig 里搜不到某个配置项，最常见原因是什么？

依赖未满足。 按 / 搜索，看结果里的 Depends on: XXX，先把依赖项打开（且依赖项自身也要满足其依赖）。 其次是搜索时用了错的名字（不带 CONFIG_ 前缀搜）。

Q3：make oldconfig 和 make olddefconfig 的区别？
  • oldconfig：遇到 .config 里没有的新选项时，逐个交互式询问；
  • olddefconfig：新增选项全部取默认值，不问。

脚本/CI 里必须用 olddefconfig，否则会卡在交互提示上。

4.2

Pi 5 交叉编译实战：从拉源码到替换运行内核

本节讲什么： 在 x86 主机（或 WSL）上交叉编译 Pi 5 内核并让它真正启动起来，含回滚方案。 前置： 4.1 Kconfig · 02-toolchain
动手： P5 · B1
卡住查书： MELP Ch4 · 官方 Building the kernel

一句话流程

拉源码 → bcm2712_defconfig → (裁剪) → 交叉编译 → 装模块 → 拷镜像/DTB → 改 config.txt → 重启

1. 拉源码

# 官方树（分支随版本调整，写本文时是 rpi-6.12.y）
git clone --depth=1 --branch rpi-6.12.y https://github.com/raspberrypi/linux
cd linux

--depth=1 省时间省空间（完整树几个 GB）。注意分支要与板子上的固件版本大致匹配。

2. 配置

export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

make bcm2712_defconfig          # Pi 5 的厂商基线
make menuconfig                 # 可选：裁剪

想基于当前运行内核的配置起步（最省事）：

# 在 Pi 上导出当前配置
zcat /proc/config.gz > .config      # 需要 CONFIG_IKCONFIG_PROC
# 拷回主机后
make olddefconfig

3. 编译

make -j$(nproc) Image.gz modules dtbs
目标 产物 说明
Image.gz arch/arm64/boot/Image.gz 压缩内核镜像
modules 各目录 .ko 可加载模块
dtbs arch/arm64/boot/dts/broadcom/*.dtb 设备树二进制，必须与内核同源

校验产物：

file arch/arm64/boot/Image.gz                       # gzip compressed data
ls -la arch/arm64/boot/dts/broadcom/bcm2712-rpi-5-b.dtb

4. 安装模块与头文件

# 挂载 Pi 的 rootfs（SD 卡第二分区）到 /mnt/rootfs
sudo mount /dev/sdb2 /mnt/rootfs

sudo make INSTALL_MOD_PATH=/mnt/rootfs modules_install
# -> /mnt/rootfs/lib/modules/6.12.x-v8-16k/

modules_install 会顺带跑 depmod，生成 modules.dep、modules.alias 等（若交叉环境没跑，需在 Pi 上补一次 sudo depmod -a）。

5. 部署镜像与 DTB

sudo mount /dev/sdb1 /mnt/boot      # boot 分区（FAT）

# 内核：换个名字，不要覆盖官方的，方便回滚
sudo cp arch/arm64/boot/Image.gz /mnt/boot/kernel-my.img
sudo cp arch/arm64/boot/dts/broadcom/bcm2712-rpi-5-b.dtb /mnt/boot/
sudo cp -r arch/arm64/boot/dts/overlays /mnt/boot/

config.txt 里指定：

kernel=kernel-my.img

★ 回滚方案（必须先准备好）： 不覆盖原 kernel8.img，用独立文件名 + kernel= 指定。
起不来时把 SD 卡插回电脑，改回 kernel=kernel8.img（或删掉这一行）即可。
别一上来就覆盖原内核 —— 刷坏内核虽然不如刷坏 EEPROM 严重，但一样要重刷卡。

6. 验证

uname -a                 # 应显示你编译的版本与编译时间
cat /proc/version        # 含 GCC 版本、SMP PREEMPT 等
zcat /proc/config.gz | grep CONFIG_PREEMPT   # 确认配置生效
dmesg -T | head -30      # 看早期启动消息

常见错误对照表

现象 原因 / 处理
aarch64-linux-gnu-gcc: command not found 没装交叉编译器（见 02-toolchain）
make: *** No rule to make target 'bcm2712_defconfig' 分支不对（拉错树）或 ARCH 没设
编译出的镜像是 x86 的 忘了 ARCH=arm64 / CROSS_COMPILE
启动卡在 Starting kernel ... DTB 与内核不匹配 / 串口配置错 / config.txt 里 kernel 路径错
Kernel panic - VFS: Unable to mount root fs 存储或文件系统驱动编成了 =m（见 4.1）
模块版本不匹配 version magic .ko 与运行内核不是同一次构建（见 4.3）
启动后外设不工作 DTB 没更新，或 overlays 没拷

时间预期（参考）

环境 首次全量编译
8 核 x86 主机 10–25 分钟
4 核笔记本 30–60 分钟
Pi 5 本机编译（make -j4） 1–2 小时

改一个驱动后增量编译通常几十秒。但改了 .config 会触发大面积重编。

HFT / 嵌入式关联

  • "别覆盖原内核"这条纪律，与 HFT 部署的"蓝绿发布 / 快速回退"是同一个原则：任何变更都要有一次操作即可回退的路径。
  • 本机编译 vs 交叉编译：Pi 5 其实够快，本机编译能省掉"版本不匹配"的一大类问题（模块、头文件天然一致）。只有需要频繁构建或做 CI 时才必须交叉。
  • 编译产物必须与运行内核严格同源 —— 这个"版本即契约"的纪律后面在 rootfs（05-rootfs）和模块（4.3）会反复遇到。

代码自测

Q1：为什么 dtbs 必须和内核一起编？

DTB 里的 compatible 字符串要与驱动里的 of_device_id 表匹配，而驱动是内核的一部分。 内核与 DTB 版本不一致 → 某些节点匹配不上 → 设备不 probe 或行为异常，且不报错。 所以官方流程里 make ... modules dtbs 是一体的。

Q2：不覆盖原内核、用 kernel= 指定的好处是什么？

回滚成本降到一次文本编辑：新内核起不来时，把 SD 卡插回电脑改 config.txt（或删掉 kernel= 行回落到默认），立刻能启动。 若直接覆盖原内核，则必须重新编译或从备份恢复。这是 bring-up 阶段最重要的保险。

Q3：INSTALL_MOD_PATH 不设会怎样？

模块会被安装到主机的 /lib/modules/$(uname -r) —— 可能污染甚至破坏主机系统。 交叉编译时必须指向目标 rootfs 的挂载点。这是最容易酿成事故的疏忽之一。

4.3

模块版本魔法：`insmod` 报 `version magic` 到底在说什么

本节讲什么： 内核模块与运行内核之间的"版本契约"，以及模块是怎么被自动加载的。 前置： 4.2 交叉编译实战
下一节点： 05-rootfs
卡住查书： MELP Ch4 · LDD3 Ch2

一个必然会遇到的问题

$ sudo insmod mydrv.ko
insmod: ERROR: could not insert module mydrv.ko: Invalid module format
$ dmesg | tail -3
mydrv: version magic '6.12.20-v8-16k SMP preempt mod_unload aarch64' should be
'6.12.25-v8+ SMP preempt mod_unload aarch64'

含义： 这个 .ko 是为 6.12.20-v8-16k 编的，但当前跑的是 6.12.25-v8+。内核拒绝加载。

vermagic 里有什么

6.12.20-v8-16k   SMP   preempt   mod_unload   aarch64
└── 版本号 ──┘   └SMP┘ └抢占模式┘ └允许卸载┘   └─ 架构 ─┘
字段 来源 说明
版本号 uname -r（UTS_RELEASE） 内核源码树版本 + CONFIG_LOCALVERSION
SMP CONFIG_SMP 是否对称多处理
preempt CONFIG_PREEMPT* 抢占模型（preempt / none / rt）
mod_unload CONFIG_MODULE_UNLOAD 是否允许 rmmod
aarch64 架构 —

任何一项不同 → 拒绝加载。 这不是内核"太挑剔"：模块直接链接到内核符号、使用内核内部结构布局，配置不同意味着内存布局可能不同，强行加载 = 随机踩内存。

# 查看模块的 vermagic
modinfo mydrv.ko | grep vermagic

# 查看当前内核
uname -r

怎么保证匹配

做法 说明
同一棵树编译 模块用的内核源码树 == 目标运行内核的源码树（推荐）
用目标内核的 headers KDIR=/lib/modules/$(uname -r)/build（本机编译时最稳）
本机编译 在 Pi 上直接 make，天然一致，最省心
交叉编译时 INSTALL_MOD_PATH 指向目标 rootfs，且内核与模块一次构建 
# 本机编译（Pi 上）—— 最不容易出错
KDIR ?= /lib/modules/$(shell uname -r)/build
all:
    make -C $(KDIR) M=$(PWD) modules

# 交叉编译（主机上）—— KDIR 指向你编译的那棵树
make -C /path/to/rpi-linux M=$(PWD) ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules

/lib/modules/$(uname -r) 目录结构

/lib/modules/6.12.25-v8+/
├── kernel/              # 各子系统的 .ko
│   ├── drivers/...
│   └── net/...
├── modules.dep          # 依赖关系（depmod 生成）★
├── modules.alias        # 设备别名 -> 模块（自动加载靠它）★
├── modules.symbols
├── modules.builtin      # 编进内核的模块清单
└── build -> /path/to/src   # 指向源码树（编译外部模块时需要）

改了模块必须重跑 depmod：

sudo depmod -a                          # 当前内核
sudo depmod -a 6.12.25-v8+              # 指定版本

模块是怎么被自动加载的

内核枚举设备（PCI / DT / USB / ACPI）
        │
        ▼
生成 modalias 字符串，如：
   pci:v00001106d00003038sv...
   of:NmydevT(null)Cwzp,my-device      ← 设备树设备的 modalias
        │
        ▼
内核发 uevent 给用户态 udev
        │
        ▼
udev 查 /lib/modules/.../modules.alias，找到匹配的 .ko
        │
        ▼
modprobe <module>    ← 自动解析依赖并加载

insmod vs modprobe

insmod modprobe
依赖处理 ❌ 不管，缺依赖直接失败 ✅ 自动先加载依赖
模块查找 需要完整路径 按名字在 /lib/modules/$(uname -r) 下找
用途 调试、开发 日常使用 
sudo modprobe mydrv          # 自动处理依赖
sudo modprobe -r mydrv       # 卸载（含不再被依赖的依赖）
lsmod                        # 看已加载
modinfo mydrv                # 看模块信息（依赖、参数、vermagic）

模块参数：

static int debug = 0;
module_param(debug, int, 0644);       /* /sys/module/mydrv/parameters/debug */
MODULE_PARM_DESC(debug, "Enable debug output");

sudo modprobe mydrv debug=1
# 或运行时（若权限允许）
echo 1 | sudo tee /sys/module/mydrv/parameters/debug

CONFIG_MODVERSIONS：可选的宽容模式

开启后，内核为每个导出符号记录 CRC 校验值，模块加载时比对：

  • 只有实际用到的符号变了才拒绝；
  • 允许小版本差异（只要 API 语义未变）。

代价： 需要在同一个 .config 下编译模块；而且它只检查符号 CRC，不检查结构体布局。发行版常用，嵌入式/自研内核通常不开（宁可严格失败也不要随机崩溃）。

HFT / 嵌入式关联

  • "版本即契约"这条纪律在部署里反复出现：容器镜像 tag、HFT 交易二进制与其链接的库版本、FPGA bitstream 与驱动版本——不一致就快速失败，好过运行期随机出错。内核的 vermagic 是这种设计哲学最严格的体现。
  • modprobe 的依赖解析 本质是静态图拓扑排序，与包管理器、systemd 的依赖解析同源。理解一次，到处能用。
  • 生产环境常把关键驱动编进内核（=y）而非模块：省掉加载环节、避免 rootfs 损坏导致驱动缺失，启动路径更短更确定。

代码自测

Q1：insmod 报 version magic 不匹配，最快的解决方式是什么？

在目标机上用 /lib/modules/$(uname -r)/build 重编模块（本机编译），天然一致。 若必须交叉编译，则内核源码树必须与目标运行内核完全一致（同一次 checkout + 同 .config + 同 LOCALVERSION）。 临时绕过可用 modprobe --force-vermagic（ debug 用，生产禁用 ）。

Q2：拷了 .ko 到目标板，modprobe 却说找不到该模块？

modprobe 按名字在 /lib/modules/$(uname -r)/ 下查找，需要： 1. .ko 放到 /lib/modules/$(uname -r)/kernel/... 下（不是随便一个目录）； 2. 跑过 depmod -a 生成 modules.dep / modules.alias。

用完整路径 insmod /path/to/mydrv.ko 可绕过，但不处理依赖。

Q3：为什么不推荐用 --force-vermagic？

vermagic 不匹配意味着内核配置/版本不同，结构体布局、函数签名可能已经变了。 强行加载后模块会按错误的偏移读写内核内存 → 随机崩溃、数据损坏，而且极难排查（症状与原因相隔很远）。 宁可构建流程做对，也不要运行期赌运气。
