导读

本节讲什么： 内核挂载 rootfs 之后发生什么——PID 1 怎么选、init 怎么把系统拉起来、控制台从哪来。 对应动手： P5 · B2/B3（串口进 shell，理解 init；启动参数与 DTB 传入）

启动时序

start_kernel()  →  rest_init()
                      ↓
               kernel_init()   ← 找 init
                      ↓
        /sbin/init → /etc/init → /bin/init → /bin/sh   （内核的查找顺序）
                      ↓
        init 挂 /proc /sys，按 inittab 或 unit 起服务
                      ↓
               getty 开控制台 → 登录 shell

内核通过 init= 启动参数可以指定别的 PID 1（如 init=/bin/sh 是最常用的救砖手段）。

init 三选一

init 特点 何时用
BusyBox init 读 /etc/inittab，几十 KB 最小系统、恢复环境、理解原理
systemd 并行启动、依赖图、journal 发行版/产品（Pi OS 默认）
runit / s6 极简 supervise，适合容器与嵌入式 想要确定性又不想上 systemd

BusyBox inittab 的样子：

::sysinit:/etc/init.d/rcS
::respawn:/sbin/getty -L 115200 ttyAMA0 vt100
::ctrlaltdel:/sbin/reboot
::shutdown:/bin/umount -a -r

关键命令

# 看启动耗时分布（systemd）
systemd-analyze
systemd-analyze blame | head -20
systemd-analyze critical-chain

# 看内核启动消息（含 early boot）
dmesg -T | head -60

# 谁是 PID 1
ps -p 1 -o pid,comm,args
cat /proc/cmdline

HFT / 嵌入式关联

  • systemd-analyze critical-chain 是启动耗时的火焰图入口，与后面 06.6-systems-performance 的方法论同源：先量化，再优化。
  • 生产环境常把关键进程做成 PID 1 直管的最小 init（不要 systemd 的不确定性），或干脆用 init=/opt/app 直接跑交易进程——这是"去掉一切不必要"的极致形态。

6.1

内核怎么找 init：四级尝试与「init= 失败会 panic」

本节讲什么： 从源码层面（init/main.c v6.6）讲清 PID 1 是怎么被选出来的，以及为什么 init= 写错路径会导致直接 panic 而不是回退。 前置： 05-rootfs · 5.2 initramfs 动手： P5 · B2 卡住查书： MELP Ch13 · Primer Ch6

源码级流程（v6.6 init/main.c）

rest_init()  →  kernel_thread(kernel_init)          ← PID 1 诞生（内核线程）
                     │
                     ├─ kernel_init_freeable()      ← 干活：驱动、挂根、开 console
                     │      ├─ do_basic_setup()     （initcall：驱动全在这初始化）
                     │      ├─ wait_for_initramfs()
                     │      ├─ console_on_rootfs()  ← 打开 /dev/console  :1552
                     │      └─ if (init_eaccess("/init") != 0)           :1558
                     │             ramdisk_execute_command = NULL;
                     │             prepare_namespace();   ← 没有 initramfs 才挂真根
                     │
                     └─ kernel_init()               ← 选 PID 1         :1428
                            ① ramdisk_execute_command   （默认 /init）
                            ② execute_command           （init= 指定）
                            ③ CONFIG_DEFAULT_INIT
                            ④ /sbin/init /etc/init /bin/init /bin/sh
                            全失败 → panic

四级尝试（源码 :1462–1499）

/* ① initramfs 的 init（rdinit= 覆盖，默认 "/init"） */
if (ramdisk_execute_command) {
        ret = run_init_process(ramdisk_execute_command);
        if (!ret) return 0;
        pr_err("Failed to execute %s (error %d)\n", ramdisk_execute_command, ret);
}

/* ② init= 命令行指定 */
if (execute_command) {
        ret = run_init_process(execute_command);
        if (!ret) return 0;
        panic("Requested init %s failed (error %d).", execute_command, ret);   /* ★ */
}

/* ③ 编译期默认（CONFIG_DEFAULT_INIT，通常为空） */
if (CONFIG_DEFAULT_INIT[0] != '\0') { ... }

/* ④ 硬编码的四个兜底路径 */
if (!try_to_run_init_process("/sbin/init") ||
    !try_to_run_init_process("/etc/init")  ||
    !try_to_run_init_process("/bin/init")  ||
    !try_to_run_init_process("/bin/sh"))
        return 0;

panic("No working init found.  Try passing init= option to kernel. ...");

两条反直觉的规则

规则一：①② 失败的处理完全不同。

层级 失败后 后果
① /init（initramfs） 打日志，继续往下试 容错，会回退到 ②③④
② init= 指定 ⭐ 直接 panic 不回退！
④ 四个兜底 试完仍失败 → panic 最终兜底

⚠️ 这是最容易踩的坑：init=/bin/bash 写错成 init=/bin/bas，系统不会"好心"地回退到 /sbin/init，而是直接 panic。 因为 init= 是用户显式要求，内核认为"你要的东西我给不了，给别的没意义"。

规则二：④ 的兜底里 /bin/sh 是故意设计的。

源码注释写得很直白：

* The Bourne shell can be used instead of init if we are
* trying to recover a really broken machine.

所以 内核自带救砖机制：什么都不做，只要 /bin/sh 存在，系统就能起来给你一个 shell。

run_init_process vs try_to_run_init_process

static int run_init_process(const char *init_filename)
{
        argv_init[0] = init_filename;
        pr_info("Run %s as init process\n", init_filename);
        return kernel_execve(init_filename, argv_init, envp_init);
}

static int try_to_run_init_process(const char *init_filename)
{
        int ret = run_init_process(init_filename);
        if (ret && ret != -ENOENT)
                pr_err("Starting init: %s exists but couldn't execute it (error %d)\n",
                       init_filename, ret);
        return ret;
}
函数 用在 区别
run_init_process ①②③ 失败就返回错误码，不打额外日志
try_to_run_init_process ④ 额外判断：非 -ENOENT 的错误（即"文件存在但执行不了"）会明确告警

⭐ 这个区别是给排错用的：

  • -ENOENT（文件不存在）→ 静默，因为"试下一个路径"本来就是预期行为
  • 其他错误（EACCES 没执行权限、ENOEXEC 不是可执行格式、EFAULT）→ 明确报 exists but couldn't execute it

看到 exists but couldn't execute it 就该去查权限和架构，而不是怀疑路径。

init= 的一个隐藏行为

static int __init init_setup(char *str)
{
        execute_command = str;
        /* ... 忽略 init= 之前的所有参数 ... */
        for (i = 1; i < MAX_INIT_ARGS; i++)
                argv_init[i] = NULL;
        return 1;
}
__setup("init=", init_setup);

init= 之后的所有命令行参数会被清空（argv_init[1..] 置 NULL）。

这意味着：

init=/sbin/init foo=bar        → foo=bar 不会传给 init 进程

想给 init 传参，要显式写：

init=/sbin/init -- arg1 arg2   （不同 init 语法不同）

历史原因：LILO 会在 cmdline 前面塞一个 auto，内核为了兼容把它清掉。

常用命令行参数速查

参数 作用 典型用法
init= 指定最终 rootfs 的 PID 1 init=/bin/sh（救砖）· init=/opt/app（直跑应用）
rdinit= 指定 initramfs 里的 PID 1 rdinit=/bin/sh（排查挂根失败）
root= 真根设备 root=/dev/mmcblk0p2 · root=PARTUUID=xxxx-02
rootfstype= 根文件系统类型 rootfstype=ext4
rootwait 等根设备出现（SD/USB 必须） rootwait
ro / rw 只读/可写挂载 ro（配合 initramfs 里 fsck）

Pi 5 的 cmdline 在 /boot/firmware/cmdline.txt（必须是一整行，不能换行）。

故障对照

内核消息 含义 排查方向
Failed to execute /init (error -2) initramfs 里没有 /init 打包时路径错了（find . 要在根执行）

HFT / 嵌入式关联

  • init=/opt/app 直跑交易进程是"去掉一切不必要"的极致形态：没有 systemd、没有 getty、没有 cron，PID 1 就是你的交易进程。启动时间从秒级降到百毫秒级，也消除了所有"谁在后台抢 CPU"的不确定性。代价是失去进程管理 —— 交易进程自己得处理重启与监控。
  • "显式指定失败就 panic，不回退"这个设计值得品味：它来自"显式意图优先于隐式兜底"的原则。HFT 系统的配置校验也该如此 —— 配置写错应该拒绝启动，而不是悄悄用默认值跑出错误的结果。静默降级在生产系统里是事故来源。
  • try_to_run_init_process 区分 -ENOENT 与其他错误的做法，是一个可观测性设计范例：预期内的失败静默，预期外的失败告警。写自己的重试逻辑时同样该区分"没有"和"坏了"。
Q1：为什么 init= 失败要 panic，而 /init 失败只是打日志继续？

语义不同：

  • ramdisk_execute_command（/init）是内核的默认猜测 —— initramfs 里可能压根没有它（很多 initramfs 靠 pivot_root 后由 init= 指定）。所以失败是预期内的，继续试下一个合理。
  • execute_command（init=）是用户的显式指令。如果内核悄悄换一个别的程序跑，你根本不知道"我要的 init 没跑起来"，系统看起来正常但行为完全不对 —— 这比 panic 危险得多。

原则：隐式兜底可以容错，显式意图失败必须暴露。

Q2：内核先挂根还是先找 init？

先有 rootfs，再找 init。 但"rootfs"在内核里分两个阶段：

  1. 内核一启动就有一个空的 rootfs（tmpfs），initramfs 的内容被解压到这里 → 这是 wait_for_initramfs() 之后的状态
  2. 然后 init/main.c:1558 判断： - 有 /init → 就停在阶段 1，让 /init 自己去挂真根并 pivot_root - 没有 /init → 内核自己 prepare_namespace() 按 root= 挂设备，然后 mount 到 /

所以 root= 参数只在"没有 initramfs init"时才由内核直接使用。 有 initramfs 时，root= 只是被 initramfs 里的脚本读走、由脚本决定怎么用。

Q3：kernel_execve 之后那个"内核线程"去哪了？

它变成了用户态进程，PID 仍是 1。

kernel_execve() 在内核里构造好 pt_regs（用户态入口、栈指针），然后走正常的返回到用户态路径。区别在于：普通 fork 出来的进程是从 ret_from_fork 返回用户态，而这里是直接篡改内核线程的执行上下文，让它"返回"到 init 的入口。

这就是为什么 PID 1 永远不会变（除非它退出 → panic）：它是从内核第一个线程直接变身的，不是 fork 出来的。

Q4：PID 1 退出了会怎样？

内核 panic：panic("Attempted to kill init!")。

因为 PID 1 是所有孤儿进程的"收养者"，它没了整个进程树就没有根。

⭐ 这正是 systemd / supervisor 类进程必须自己保证不崩的原因，也是容器里"PID 1 要正确处理信号、要 wait 掉僵尸进程"的根源 —— 普通程序被放进 PID 1 位置会踩一堆坑（比如默认忽略没有 handler 的信号）。

6.2

控制台从哪来：console= / /dev/console / 串口

本节讲什么： 你看到的启动信息是怎么出来的、串口控制台怎么配、/dev/console 到底是什么。bring-up 阶段没有串口等于瞎子，这是必须搞懂的一节。 前置： 6.1 内核怎么找 init 动手： P5 · B2 卡住查书： MELP Ch13 · Primer Ch6、Ch7

三件事别搞混

概念 是什么 谁在用
内核 console 内核 printk 输出的目的地 内核（printk、panic 信息、Oops）
/dev/console 一个设备节点（字符设备 5:1） 用户态程序的 stdin/stdout/stderr
tty 终端（物理串口 / 虚拟终端 / SSH pty） 登录会话

关键理解：内核 console 和 /dev/console 是两件独立的配置，只是恰好通常指向同一个地方。

内核 console：printk 往哪打

printk("...")  →  内核 console 链表  →  每个注册的 console 驱动
                                        ├─ ttyAMA0（串口）
                                        ├─ tty0  （虚拟终端/屏幕）
                                        └─ netconsole（UDP 网络）

由 console= 内核参数指定：

console=ttyAMA0,115200          # 串口 0，波特率 115200
console=tty0                    # 当前虚拟终端（HDMI 屏幕）
console=ttyAMA0,115200 console=tty0    # 两个都要（最后一个才是 /dev/console）

⭐ console= 可以出现多次，所有列出的都会收到 printk 输出。但 /dev/console 只绑定最后一个 console= 指定的设备 —— 这个是规定，记住就行。

Pi 5 上的实际配置

Pi 5 的串口是 ttyAMA0（PL011，在 40pin 排针的 GPIO14/15 上）。

# /boot/firmware/cmdline.txt（必须一整行）
console=serial0,115200 console=tty1 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait
#      ↑ serial0 是固件提供的别名，通常指向 ttyAMA0

# /boot/firmware/config.txt
enable_uart=1          # 启用串口（Pi 5 默认可能关闭以省电）

⚠️ Pi 5 常见坑：enable_uart=1 不加，串口完全没输出，你会以为"内核没起来"。

earlycon：在驱动初始化之前就有输出

内核启动 → console 驱动还没注册 → 这期间的 printk 去哪了？
                                    ↓
                          存在 printk 缓冲区里，驱动就绪后**补打**

这意味着"启动早期崩溃"你可能什么都看不到（缓冲区里的东西来不及输出）。

解决：earlycon

earlycon console=ttyAMA0,115200

earlycon 提供一个极简的、写死寄存器地址的输出通道，不需要完整驱动、不需要设备树解析，能在内核解压缩之后立刻工作。

用 boot_delay 排查"刷屏看不到"

boot_delay=100        # 每条 printk 之间延迟 100ms

启动信息刷太快看不清时用；代价是启动变慢（100 条消息 = 10 秒）。

/dev/console：用户态的"标准输出"

内核在 init/main.c:1504：

/* Open /dev/console, for stdin/stdout/stderr, this should never fail */
void __init console_on_rootfs(void)
{
        struct file *file = filp_open("/dev/console", O_RDWR, 0);
        ...
        pr_err("Warning: unable to open an initial console.\n");
}

PID 1 的 fd 0/1/2 就是这个文件，之后所有子进程继承。

⚠️ 失败不 panic，只打一行 Warning —— 后果是：

  • 系统"起来了"，但一个字都不打印
  • 你以为死机了，其实 init 跑得好好的
  • 这是 bring-up 阶段最折磨人的故障之一

所以 rootfs 里必须有 /dev/console（mknod dev/console c 5 1，或开 devtmpfs）。

有日志之后：看什么

⭐ 第一件事永远是 cat /proc/cmdline —— 确认你以为传进去的参数真的在。很多时候改了 cmdline.txt 但改错了分区（Pi 5 的 boot 分区是 /boot/firmware/，不是 /boot/）。

HFT / 嵌入式关联

  • "不致命的 Warning 让你看起来像死机" —— 这条在 HFT 里对应告警静默失效。监控链路自己挂了却没告警，是最危险的状态。所以生产系统要有 dead man's switch（心跳缺失即告警），不能依赖"出问题会有人喊"。
  • 串口是唯一不依赖网络、不依赖文件系统、不依赖驱动的观测通道。HFT 生产机的等价物是独立的管理网口 / IPMI / 带外管理：交易网断了、系统卡死了，你还能进去看。这条通道必须事先验证可用，不能等出事才发现没接。
  • earlycon 的思路（在完整机制就绪前先给一个最小可用通道）值得借鉴：任何复杂系统都应该有一个"最小可观测层"，它简单到几乎不可能坏。
Q1：为什么我加了 console=ttyAMA0,115200 还是没输出？

按概率排查：

  1. TX/RX 接反了（最常见）→ 交换试试
  2. 电平不匹配（5V 模块接 3.3V）→ 换模块或确认拨到 3.3V
  3. Pi 5 的 enable_uart=1 没加（config.txt）
  4. 波特率不对（不是 115200）
  5. 流控没关（终端软件里 Flow Control 要设 None）
  6. 内核参数没生效 → cat /proc/cmdline 确认（改了 /boot/cmdline.txt 而不是 /boot/firmware/cmdline.txt）

判据：如果连 U-Boot/固件的启动信息都看不到，问题在 1–5（硬件层）；如果固件信息看得到、内核的看不到，问题在 6 或内核配置。

Q2：/dev/console 和 /dev/ttyAMA0 有什么区别？
  • /dev/ttyAMA0 是具体的串口设备
  • /dev/console 是系统控制台的别名（字符设备 5:1），它指向哪个实际设备，由最后一个 console= 参数决定

直接往 /dev/ttyAMA0 写，永远写到那个串口；往 /dev/console 写，写到"当前系统控制台"。

好处：程序不需要知道自己跑在什么硬件上，写 /dev/console 就对了。这是间接层的典型用法。

Q3：printk 的日志级别和"为什么有的消息没打出来"？

每条 printk 有级别（0 emerg … 7 debug）。内核只把级别 ≤ console_loglevel 的消息送到 console：

cat /proc/sys/kernel/printk
#   7    4    1    7
#   ↑    ↑    ↑    ↑
#  控制台级别  默认消息级别  最低允许  启动时默认

第一个数是 console_loglevel：只有级别比它更紧急（数值更小）的消息才会显示。

调试时临时放开：echo 8 > /proc/sys/kernel/printk（显示全部，含 debug）。 或用 dmesg -n 8。

6.3

启动耗时怎么测：initcall_debug / bootgraph / systemd-analyze

本节讲什么： 把"启动慢"从感觉变成数字。三种手段分别覆盖内核早期、内核整体、用户态，三段必须分开测。 前置： 6.2 控制台 动手： P5 · B3 卡住查书： MELP Ch13–14 · 方法论见 06.6-systems-performance

先分三段，再谈优化

① 固件/bootloader   （上电 → 内核入口）      ← 嵌入式特有，PC 上通常是 UEFI
② 内核              （内核入口 → PID 1 exec） ← initcall_debug
③ 用户态            （PID 1 → 服务就绪）      ← systemd-analyze / init 自带计时

⭐ 这三段的观测手段完全不同，不能混。 最常见错误是拿 systemd-analyze 的数字说"启动慢"，结果瓶颈根本在内核 initcall 或固件阶段。

① 固件阶段：grabserial（需要有串口）

# 主机侧把串口输出加上时间戳
pip install grabserial
grabserial -d /dev/ttyUSB0 -b 115200 -t -m "^Linux version"
#   -t 打时间戳   -m 匹配到这行时重新开始计时

输出是每条消息的相对时间，能看出：

  • 上电到第一条固件输出：多快
  • 固件加载内核：多久（SD 卡读取速度）
  • 内核解压缩：多久

⚠️ 波特率 115200 下串口本身有带宽开销（约 11.5 KB/s）。大量输出会拖慢启动 —— 测完记得关掉额外日志。

② 内核阶段：initcall_debug（最有用的一招）

内核参数加：

initcall_debug  （可选配合：printk.time=1 或 initcall_debug 自带时间戳）

启动后：

dmesg | grep -E 'initcall .* (returned|after)'

输出长这样：

[    0.482913] initcall nvme_init+0x0/0x1000 returned 0 after 12345 usecs

按耗时排序找出前 10：

dmesg | sed -n 's/.*initcall \([^+]*\).*after \([0-9]*\) usecs.*/\2 \1/p' \
  | sort -rn | head -20
常见的大头 说明
pci_、xhci_、nvme_ 设备枚举与总线扫描
*_initcall 里的 mdelay/msleep 驱动里的硬等待（很多是给硬件复位留时间）
calibrating delay loop 校准 loops_per_jiffy（可用 lpj= 参数跳过）
random: crng init done 熵池初始化（可用 rng 硬件或 jitterentropy）

⭐ 实测手段：把某个可疑驱动的 initcall 耗时减掉一半，看总时间是不是也减一半 —— 优化要能被测量验证，否则是玄学。

画成图（直观但需要主机侧处理）

# 内核自带脚本（源码树里）
scripts/bootgraph.pl boot.log > boot.svg
# 或用 bootchart / systemd-bootchart

生成的 SVG 按时间轴列出所有 initcall，一眼看出哪个最长。

③ 用户态阶段

systemd

systemd-analyze                     # 总时间（kernel + initrd + userspace）
# Startup finished in 3.2s (kernel) + 8.1s (userspace) = 11.3s

systemd-analyze blame | head -20    # 各 unit 耗时，从慢到快
systemd-analyze critical-chain      # ★ 关键路径（真正卡住启动的那条依赖链）
systemd-analyze plot > boot.svg     # 可视化

⭐ blame 会骗人：它列的是"每个 unit 自己花了多久"，但并行启动的 unit 不会累加到总时间。

真正要看的是 critical-chain —— 那条串行依赖链决定了总时长。优化并行部分毫无用处。

BusyBox init（无 systemd）

# 自己加时间戳：在 /etc/init.d/rcS 里
echo "[$(cat /proc/uptime)] starting network" > /dev/kmsg
...
echo "[$(cat /proc/uptime)] network up" > /dev/kmsg

或者更简单：看 dmesg 里 Run /sbin/init as init process 之后到"服务就绪"之间的墙钟时间（串口日志里自带时间戳）。

⚠️ 没有 systemd 就没有免费的可观测性 —— 这也是选择 systemd 的现实理由之一。选择 BusyBox init 就得自己造轮子。

通用：内核提供的两个计时点

# 内核启动到现在的秒数（含小数）
cat /proc/uptime
#   123.45  98.76
#   ↑ 系统运行秒数   ↑ 空闲秒数

# 配合 /proc/stat 能算出"启动过程消耗了多少 CPU 时间"

⭐ 最实用的"服务就绪"判定：不要用"我能 ping 通"，要用应用自己的健康检查端点（比如交易进程起来后监听一个端口）。ping 通只说明网络栈起来了。

优化手段清单（按性价比）

手段 省多少 代价
lpj=<值> 跳过 delay loop 校准 几十~几百 ms 需要预先测好值，换硬件要重测
去掉不用的驱动（=n） 每个几十 ms 起 需要明确知道哪些不用
把非关键驱动改成模块（=m） 移到用户态并行 需要 initramfs 或自动加载
关掉 quiet 之外的启动日志 串口慢时明显 失去可观测性，不推荐
关掉/合并不必要的 systemd unit 秒级 要理清依赖
disable_splash / 关 Plymouth 几百 ms —
静态 IP（跳过 DHCP） 1~5 秒 网络拓扑要固定
只读 rootfs + 跳过 fsck 几百 ms~几秒 见 07-storage-ota

⭐ 性价比最高的是关掉不需要的东西（驱动、服务），而不是"优化"已有的东西。删代码永远比优化代码有效。

HFT / 嵌入式关联

  • critical-chain 的思维方式直接可用于交易链路：链路总延迟由最长的串行依赖决定，不是所有环节之和。先画依赖图，找出关键路径，否则优化并行分支是白费力气。
  • "启动快"对 HFT 的价值是故障恢复时间（MTTR）：网关掉线按秒计费，重启快 = 少亏钱。这与嵌入式"掉电后尽快恢复"是同一目标。
  • 观测手段本身会改变被测对象（串口输出拖慢启动、perf 采样有开销）。这条在 HFT 里是硬约束：生产环境的埋点必须足够轻，否则你测到的是埋点的开销而不是真实延迟。对应到启动测量：测完关掉 initcall_debug。
Q1：systemd-analyze blame 的第一名耗时 5 秒，但总启动时间只有 8 秒，为什么？

因为它是并行跑的。blame 报告的是每个 unit 自己的墙钟耗时，多个 unit 同时跑时，这些时间是重叠的，不累加。

所以要优化的是 critical-chain（关键路径）—— 那是一条串行链，链上任何一环慢了总时间就慢了。

判据：blame 里排第一但不在 critical-chain 上的 unit，优化它对总时长零贡献。

Q2：initcall_debug 会不会自己拖慢启动？

会，但很轻：每个 initcall 多两次 printk（开始/结束）。

  • 输出到串口时影响明显（串口带宽低），可能拖慢几百 ms
  • 输出到内存缓冲区（默认，串口只是转发）时影响极小

正确用法：测量时开着，测完关掉。永远报告"开 initcall_debug 时"的数字，并注明测的是相对值而非绝对值。

同理适用于所有 profiler —— 这是 06.6 里 "observer effect" 的又一个实例。

Q3：我想让启动快，第一步该做什么？

先测，再删，最后才优化。

  1. initcall_debug + systemd-analyze critical-chain 拿到三段各自的耗时
  2. 找出占比最大的那一段（通常是用户态服务或某个慢驱动）
  3. 先问"这个能不能不要" —— 删掉一个 2 秒的服务比优化它到 1 秒省事得多，且没有回归风险
  4. 剩下的才考虑并行化 / 延迟加载

⭐ 反模式：一上来就 systemctl disable 一堆东西，结果某个服务是别的服务隐式依赖的，系统起了一半。改一个，测一次。
