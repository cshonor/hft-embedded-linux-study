导读

本节讲什么： 内核启动最后一步要跑 init，而 init 必须来自某个文件系统。这一节做出来这个文件系统。 对应动手： P5 · B2（最小 rootfs，串口进 shell，理解 init）

一个 rootfs 最少需要什么

组成 作用
/sbin/init（或 /init） PID 1，内核启动的终点、用户空间的起点
busybox 提供 sh + 一百多个常用命令（单二进制 + 符号链接）
/dev console、null、ttyAMA0… 否则 shell 打不开终端
/lib + /lib/modules C 库与内核模块（见 04-kernel-build）
/etc/inittab（BusyBox init） 定义开哪些 getty、跑哪些启动脚本

三条路怎么选

方式 适合 说明
initramfs 调试、早期 bring-up 直接编进内核（CONFIG_INITRAMFS_SOURCE），无需块设备；改动要重新编内核
Buildroot 本模块主线 Kconfig + make，与内核同构；几十分钟出可启动镜像
Yocto 量产、长期维护 recipe/layer/bitbake 另学一套；几小时 + 几十 GB。学习阶段不要碰

Buildroot vs Yocto（为什么主线走 Buildroot）

Buildroot Yocto
首个可启动镜像 几十分钟 数小时起
磁盘占用 几个 GB 几十 GB
概念栈 Kconfig + make（与内核同构，学一次用两次） recipe / layer / bitbake
产物 一个完整镜像 一个可长期演进的发行版
适合 搞懂启动链、快速迭代 多机型、产品化、需要包管理

Yocto 是量产的事实标准，但不是学习入口。等真要做产品镜像再上，别让它占掉主线时间。

关键命令

# Buildroot 快速路线
git clone https://github.com/buildroot/buildroot && cd buildroot
make raspberrypi5_defconfig          # 或 qemu_aarch64_virt_defconfig 练手
make menuconfig                       # 按需加包、设 root 密码、选 init
make -j$(nproc)
ls output/images/                     # sdcard.img / rootfs.tar / Image

最小手工 rootfs（理解用）：

mkdir -p rootfs/{bin,sbin,dev,etc,proc,sys,lib}
cp $(which busybox) rootfs/bin/        # 静态编译版更省事
ln -s busybox rootfs/bin/sh
sudo mknod rootfs/dev/console c 5 1

HFT / 嵌入式关联

  • 启动即恢复：HFT 网关掉线按秒计费，rootfs 越小、init 越简单，重启越快。这条线后面接到 07-storage-ota（只读 rootfs + A/B 分区）。
  • 最小化 = 确定性：rootfs 里少一个守护进程，就少一个可能抢 CPU、抖 p99 的源头。

5.1

手工搭一个最小 rootfs：内核启动到底需要什么

本节讲什么： 不用 Buildroot，纯手工拼出一个能进 shell 的 rootfs。目的是把"必需"和"可有可无"的边界看清楚 —— 这一步跳过，后面调 Buildroot 出问题就只会瞎猜。 前置： 04-kernel-build · 2.2 sysroot 与 C 库 动手： P5 · B2 卡住查书： MELP Ch5 · Primer Ch6、Ch11

先回答：内核启动最后一步在找什么

内核挂上 rootfs 之后，只做一件事：找一个可执行文件当 PID 1（查找顺序见 6.1 init 查找顺序）。

所以 rootfs 的绝对底线是：

必须有一个内核能 exec 起来的文件（/sbin/init / /init / /bin/sh 之一）

就这一条。 其他一切（/proc、/dev、/etc、共享库…）都是"这个 init 想做点正经事"之后才需要的。

极简实验：只有一个静态 busybox 就能起来

mkdir -p /tmp/miniroot/bin
cp /path/to/busybox-static /tmp/miniroot/bin/busybox     # 静态编译版
ln -s busybox /tmp/miniroot/bin/sh

# 打成 initramfs（下一节详讲）或直接作为 root= 的文件系统
cd /tmp/miniroot && find . | cpio -o -H newc | gzip > /tmp/mini.cpio.gz

内核带 rdinit=/bin/sh 启动，你会直接掉进 shell —— 但很快会发现：

你敲的命令 结果 为什么
ls bin/sh: ls: not found 只有 sh 一个符号链接
ps 报错或空 /proc 没挂
mount 报错 /proc 没挂，读不到挂载表
echo hi > /dev/null 报错 /dev 是空的，没有 null 设备

这就是"最小"的真实代价 —— 它能证明启动链通了，但不能算"可用系统"。

补齐到「可用」：六个必需项

路径 内容 缺了会怎样
/bin/sh + /bin/busybox shell 与 ~100 个命令的符号链接 只能跑 init 自己
/sbin/init PID 1（可以是 busybox 的软链） 内核 panic：No working init found
/dev/console 主控制台设备节点 Warning: unable to open an initial console.
/dev/null、/dev/zero 标准工具依赖 各种 "not found" / 重定向失败
/lib（+ 解释器） 动态程序的 C 库 not found（动态链接的程序全部跑不了）
/proc、/sys 内核信息导出 ps / mount / sysctl 全废

⭐ /dev/console 是硬要求：内核在 kernel_init_freeable() 里主动 filp_open("/dev/console")（v6.6 init/main.c:1506），失败就打 Warning: unable to open an initial console. —— 这不是致命错误，但 PID 1 的 stdin/stdout/stderr 就全没了，你会看到"系统起来了但一个字都不打"。

完整手工流程（可直接抄）

ROOT=/tmp/rootfs
BUSYBOX=/path/to/busybox          # 动态或静态都行

mkdir -p $ROOT/{bin,sbin,dev,etc,proc,sys,lib,tmp,var}

# ① busybox 本体
cp $BUSYBOX $ROOT/bin/busybox
chmod +x $ROOT/bin/busybox

# ② 建符号链接（busybox --install 会自动做，前提目标目录存在）
$ROOT/bin/busybox --install -s $ROOT/bin        # -s = symbolic links
ln -sf /bin/busybox $ROOT/sbin/init             # PID 1

# ③ 设备节点（★ 必须在 rootfs 里真实存在，内核不会自动建）
sudo mknod $ROOT/dev/console c 5 1              # 主控制台  5,1
sudo mknod $ROOT/dev/null    c 1 3              # 空设备    1,3
sudo mknod $ROOT/dev/zero    c 1 5              # 零设备    1,5
sudo mknod $ROOT/dev/tty     c 5 0              # 当前 tty  5,0
sudo mknod $ROOT/dev/ttyAMA0 c 204 64           # Pi 的串口（串口控制台时用）
chmod 666 $ROOT/dev/null $ROOT/dev/zero

# ④ 动态库（静态 busybox 可跳过这一段）
#    用 readelf 看它到底需要什么，再一个个拷
aarch64-linux-gnu-readelf -d $ROOT/bin/busybox | grep NEEDED
cp -a <sysroot>/lib/ld-linux-aarch64.so.1 $ROOT/lib/
cp -a <sysroot>/lib/aarch64-linux-gnu/libc.so.6 $ROOT/lib/
# ... 以及 NEEDED 里列出的全部

# ⑤ BusyBox init 的配置文件
cat > $ROOT/etc/inittab <<'EOF'
::sysinit:/etc/init.d/rcS
::respawn:/sbin/getty -L 115200 ttyAMA0 vt100
::ctrlaltdel:/sbin/reboot
::shutdown:/bin/umount -a -r
EOF

mkdir -p $ROOT/etc/init.d
cat > $ROOT/etc/init.d/rcS <<'EOF'
#!/bin/sh
mount -t proc  proc  /proc
mount -t sysfs sysfs /sys
mount -t devtmpfs devtmpfs /dev 2>/dev/null || echo "devtmpfs 不可用，用静态 /dev"
EOF
chmod +x $ROOT/etc/init.d/rcS

mknod 需要 root 权限（或在 fakeroot 里做）。这是它在容器/CI 里常失败的原因。 替代方案：让内核挂 devtmpfs（CONFIG_DEVTMPFS=y + CONFIG_DEVTMPFS_MOUNT=y），/dev 由内核自动填充 —— 这是现代做法，手工 mknod 主要用于理解原理。

验证：三问

# ① 二进制架构对不对（交叉编译的老规矩）
aarch64-linux-gnu-readelf -h $ROOT/bin/busybox | grep Machine     # → AArch64

# ② 动态依赖有没有全拷进去（★ 最常漏）
for f in $ROOT/bin/* $ROOT/sbin/*; do
  aarch64-linux-gnu-readelf -d "$f" 2>/dev/null | grep NEEDED
done | sort -u
# 逐个确认 $ROOT/lib 下都有

# ③ 大小（心里有数，后面做镜像要预留空间）
du -sh $ROOT

「最小」到底多小

组成 大致体积
静态 busybox 单文件 ~1 MB
动态 busybox + glibc ~2.5 MB
上述最小 rootfs（含库） ~4 MB
Buildroot 默认最小系统 10~30 MB
Pi OS Lite ~500 MB
带桌面的发行版 几 GB

数量级差距就是"确定性"的差距 —— 每多一个守护进程，就多一个可能抢 CPU、抖 p99 的源头。

HFT / 嵌入式关联

  • 最小化 = 确定性：这套原则在 HFT 生产机上同样成立。交易主机的镜像通常也是"能跑交易进程的最少集合"，不装桌面、不装无关服务，连 cron 都要审视。
  • /dev/console 的教训值得记住：一个"不致命的 Warning"可能让整个系统看起来像死机。日志/控制台是系统的神经，HFT 里对应的是监控与告警链路 —— 它不参与赚钱，但它挂了你就瞎了。
  • mknod 需要特权这件事，说明有些 rootfs 构建步骤必须在受控环境里做。对应到生产：镜像构建要在 CI 里做，不能在跑着的机器上"手工改一下"。
Q1：为什么内核不自动创建 /dev 下的设备节点？

其实可以，而且现代系统就是这么做的 —— devtmpfs：内核在启动时自动挂载一个 tmpfs 到 /dev，驱动注册时（device_create() / devtmpfs_create_node()）自动在里面建节点。

前提条件： 1. 内核开 CONFIG_DEVTMPFS=y（大多数发行版内核都开） 2. 要么内核自动挂载（CONFIG_DEVTMPFS_MOUNT=y），要么用户态 mount -t devtmpfs devtmpfs /dev

手工 mknod 的场景只剩两个：① 教学习惯；② 早期 bring-up，devtmpfs 还没起来就要用 /dev/console（这正是为什么 /dev/console обычно 仍然静态存在于 initramfs 里）。

Q2：动态 busybox 报 not found 但文件明明在，怎么回事？

两个可能，都不是文件不存在：

  1. 缺解释器：readelf -l busybox | grep interpreter 会显示它要 /lib/ld-linux-aarch64.so.1。这个解释器不在的话，内核 execve 直接失败，shell 报 not found（极具误导性）。
  2. 缺某个 NEEDED 的 .so：同理，报的也是 not found。

判据：用 readelf -d 列出全部 NEEDED，再逐个确认 rootfs 里有。ldd 在交叉环境不可靠（它会去跑目标程序），必须手工核对。

Q3：BusyBox init 的 inittab 里 respawn 和 sysinit 有什么区别？
action 语义
sysinit 只跑一次，且是 init 起来后最先执行的（挂文件系统、设主机名等）
respawn 进程退出就自动重启 —— getty 必须用它，否则你 logout 一次就再也登不进去
once 只跑一次，但 orderly（在 sysinit 之后）
wait 跑一次，init 等它结束才继续
shutdown 关机/重启时执行
ctrlaltdel 按 Ctrl-Alt-Del 时执行

⭐ respawn 是"服务永不掉线"的最原始形态 —— 后来的 systemd Restart=always、容器编排的重启策略，都是同一个思想的工业化版本。

5.2

initramfs：内核启动时的"临时根"

本节讲什么： initramfs 是什么、为什么需要它、以及它和老的 initrd 有什么本质区别。理解它，才能看懂"为什么我的内核挂不上根分区"。 前置： 5.1 最小 rootfs 动手： P5 · B2 卡住查书： MELP Ch5 · Primer Ch6

一句话

initramfs = 一个 cpio 归档，内核启动时把它解压到一个 tmpfs 里当作第一个根文件系统。

它存在的唯一理由是：内核要挂载真正的根，可能需要驱动和工具，而驱动和工具在根上。

鸡生蛋问题：
  根分区在 NVMe 上    → 需要 nvme 驱动
  nvme 驱动是模块     → 在 /lib/modules 里
  /lib/modules 在根上 → 在 NVMe 上 ← 循环了

initramfs 打破这个循环：把必要的模块和挂载工具塞进内核镜像本身，先用它把真根挂起来，再切换过去。

initramfs vs initrd（不是一回事）

initrd（老，已淘汰） initramfs（现代）
形态 一个块设备镜像（有文件系统） 一个 cpio 归档（打包即归档）
内核需要 必须有对应文件系统驱动 + ramdisk 驱动 零驱动（tmpfs 是内核内置的）
内存 固定大小，用不完也占着 随用随长，删文件能释放
缓存 走了两层缓存（ramdisk + 页缓存） 直接是页缓存，更省
位置 独立文件，bootloader 加载 可以编进内核镜像

⭐ 现代内核只有 initramfs。你看到的 /boot/initrd.img-* 文件名，内容其实也是 cpio（名字是历史遗留）。

内核源码里的关键判据（v6.6 init/main.c）

这是理解 initramfs 最重要的一段，值得记住：

/* init/main.c:1558 */
if (init_eaccess(ramdisk_execute_command) != 0) {
        ramdisk_execute_command = NULL;
        prepare_namespace();          /* ← 没有 /init 才去挂真正的根设备 */
}

翻译成人话：

内核启动到这儿时，rootfs 里已经塞好了 initramfs 的内容
        │
        ├─ 有 /init 且可执行  → 就把 /init 当 PID 1，真根由它自己去挂（pivot_root）
        │
        └─ 没有 /init         → 内核自己调 prepare_namespace()，按 root= 参数挂设备

⭐ 这条判据解释了两件常见困惑：

  1. 为什么有 initramfs 时 root= 参数常常看起来"没用" → 因为真根是 initramfs 里的脚本挂的，root= 只是被那个脚本读去用。
  2. 为什么去掉 initramfs 后系统起不来 → 内核直接去挂 root=，但需要的驱动是模块、还在没挂上的根上 → 死锁。

三种用法，按阶段选

用法 命令 适合
编进内核（bring-up 首选） CONFIG_INITRAMFS_SOURCE=/path/to/rootfs 单镜像，bootloader 不用管；改一次要重编内核
独立文件 bootloader 加载 initrd.img 发行版做法，换 initramfs 不用重编内核
不用 CONFIG_INITRAMFS_SOURCE="" 内核自己挂根（驱动必须全 =y 编进内核）

Pi 5 的特殊情况：默认走固件启动 + config.txt，通常不用 initramfs（内核驱动都编进去了，根直接在 SD 卡上）。想用它就加一行：

# /boot/firmware/config.txt
initramfs initrd.img followkernel

制作：三种打包方式

cd /tmp/rootfs

# ① 经典 cpio（最通用）
find . | cpio -o -H newc | gzip > /tmp/initrd.img

# ② 内核自带脚本（推荐：会处理权限、设备节点）
/usr/src/linux/scripts/gen_initramfs_list.sh -o /tmp/initrd.img /tmp/rootfs

# ③ 内核直接编进去
#    make menuconfig → General setup → Initramfs source file(s) → /tmp/rootfs
#    或者写进 defconfig：
#    CONFIG_INITRAMFS_SOURCE="/tmp/rootfs"
参数 说明
-H newc 必须用 newc 格式，内核只认这一种（"new ASCII with checksum"）
gzip 可选；内核能自动解压 gzip/xz/lz4/zstd（需开对应 CONFIG_RD_*）
find . 要在 rootfs 根目录里执行，否则路径会带前缀导致 /init 找不到

怎么验证做对了

# ① 解开来检查（不破坏原文件）
mkdir /tmp/chk && cd /tmp/chk && zcat /tmp/initrd.img | cpio -idmv
ls -l /tmp/chk/init /tmp/chk/dev/console     # 关键两项要在

# ② 启动时加内核参数看看内核怎么说
#    cmdline 加： rdinit=/bin/sh
#    如果直接进 shell，说明 initramfs 被正确解开了

# ③ 看内核日志
dmesg | grep -i -E 'initramfs|unpacking|rootfs|Trying to unpack'
# 正常会看到：Trying to unpack rootfs image as initramfs
#            Freeing initrd memory: xxxxK

常见故障对照

现象 原因 修法
Failed to execute /init (error -2) cpio 里没有 /init（或路径带了前缀） 在 rootfs 根执行 find .；确认 /init 存在
Warning: unable to open an initial console. 缺 /dev/console mknod dev/console c 5 1
Kernel panic - not syncing: VFS: Unable to mount root fs 无 initramfs 且 root= 指错/驱动是模块 做 initramfs，或把磁盘/文件系统驱动改成 =y
起来后 shell 一敲命令就 not found 只有 busybox 没建符号链接 busybox --install -s
改了 initramfs 内容但启动后没变 它编进内核了，改文件没用 要么重编内核，要么改成独立文件加载

HFT / 嵌入式关联

  • initramfs 是"最小可信执行环境"的原型：它的价值在于不依赖外部状态就能把系统拉到可用。HFT 的灾备设计同理 —— 恢复流程不能依赖"那个坏掉的盘上还有什么"。
  • CONFIG_INITRAMFS_SOURCE 让 rootfs 变成内核的一部分，代价是改一次重编一次。这跟"把配置编进二进制 vs 运行时读取"是同一个权衡：启动可靠性 vs 迭代速度。bring-up 期选可靠，产品期选可迭代。
  • 「鸡生蛋」的解法（用一个小的自足层去引导大的层）在系统设计里反复出现：bootloader → 内核 → initramfs → 真根 → 服务。每一层都只解决"让下一层能跑起来"这一个问题。
Q1：initrd 和 initramfs 名字这么像，怎么快速区分？

看它是不是块设备镜像：

file /boot/initrd.img-6.6.0
# initramfs → ASCII cpio archive (SVR4 with no CRC)  或 gzip compressed data
# initrd    → Linux rev 1.0 ext2 filesystem data

现代发行版（包括名字还叫 initrd 的那些）都是 cpio，initrd 那套已经在内核 2.6 时代被取代了。文件名只是历史遗留。

Q2：为什么有的系统可以完全不用 initramfs？

因为它不需要任何模块就能挂上根：

  • 存储控制器驱动编进内核（=y 而不是 =m）
  • 文件系统驱动编进内核（ext4 等）
  • 根设备可以直接用内核认识的标识指定（root=/dev/mmcblk0p2 或 root=PARTUUID=...）

这种情况下内核 prepare_namespace() 能一步到位，跳过 initramfs。代价是内核变大、驱动无法按需加载。

发行版不能这么做（要支持千奇百怪的硬件，驱动只能做成模块）→ 所以必须有 initramfs。 嵌入式往往可以这么做（硬件固定）→ 这也是嵌入式系统启动更快的根本原因之一。

Q3：rdinit= 和 init= 有什么区别？
参数 设置谁 用在哪
rdinit= ramdisk_execute_command（默认 /init） initramfs 里的 PID 1
init= execute_command 最终 rootfs 里的 PID 1

两个都在 init/main.c 里有 __setup() 注册（:587 和 :599）。

调试时 rdinit=/bin/sh 极好用：内核解完 initramfs 直接给你一个 shell，在它去挂真根之前 —— 这时你能用 blkid、mount 手动排查为什么根挂不上。

5.3

Buildroot：从零到一个可启动镜像

本节讲什么： 用 Buildroot 在几十分钟内出一个能启动的镜像，理解它的目录结构与 Kconfig 逻辑，以及它与 Yocto 到底该怎么选。 前置： 5.1 最小 rootfs · 5.2 initramfs 动手： P5 · B2 卡住查书： MELP Ch6 · Primer Ch6

Buildroot 是什么（一句话）

一个用 Kconfig + make 把「交叉工具链 + 内核 + bootloader + rootfs」全编出来的构建系统。

它的核心卖点：概念栈和内核完全同构。你学会 menuconfig 一次，内核和 Buildroot 都能用。这一点对学习阶段的价值远超"省事"。

三件套怎么选（为什么主线走 Buildroot）

Buildroot Yocto 手工
首个可启动镜像 几十分钟 数小时起 几小时（但学到最多）
磁盘占用 几个 GB 几十 GB 几百 MB
概念栈 Kconfig + make（与内核同构） recipe / layer / bitbake（另学一套） 无
产物 一个完整镜像 一个可长期演进的发行版 一个 rootfs
包管理 无（改配置重编） 有（rpm/ipk/deb，可增量升级单个包） 无
适合 学启动链、快速迭代、固定硬件产品 多机型、产品化、需要在线升级包 理解原理

⭐ Yocto 是量产的事实标准，但不是学习入口。 它的复杂度是为"几十种机型 + 长期维护 + 合规审计"设计的，你一个人一块板子用不上，却要为它付出几小时构建 + 几十 GB 磁盘 + 一整套新概念。 做产品镜像那天再上 Yocto，别让它占掉主线时间。

第一次构建（可直接抄）

git clone https://github.com/buildroot/buildroot
cd buildroot

# ① 选基线配置（Pi 5）
make raspberrypi5_defconfig

# ② 按需调整
make menuconfig
#   Target options      → 一般 defconfig 已设好，别乱动
#   Toolchain           → glibc/musl、C++ 支持、gcc 版本   ★ 常改
#   System configuration→ root 密码、hostname、/etc/issue   ★ 常改
#   Target packages     → BusyBox/OpenSSH/dropbear/i2c-tools...
#   Filesystem images   → 输出格式（ext4 / tar / cpio / sdcard.img）

# ③ 编（首次几十分钟，之后增量很快）
make -j$(nproc) 2>&1 | tee build.log

# ④ 产物
ls output/images/
#   sdcard.img      ← 直接 dd 到 SD 卡的完整镜像
#   rootfs.tar      ← rootfs 归档
#   Image / zImage  ← 内核
#   bcm2712-rpi-5-b.dtb

目录结构（出问题时知道去哪找）

buildroot/
├── output/
│   ├── build/        ← 每个包的源码与构建目录  ★ 排查编译失败看这里
│   ├── host/         ← 主机工具 + 生成的交叉工具链
│   ├── images/       ← 最终产物
│   ├── target/       ← ★ 未打包的 rootfs（想改文件就直接改这里再 make）
│   └── staging/      ← sysroot（头文件和库）
├── package/          ← 所有软件包的 recipe（.mk + Config.in）
├── board/            ← 板级配置（内核配置片段、genimage.cfg、post-build 脚本）
└── configs/          ← defconfig 文件

⚠️ output/target/ 里的改动会在下次 make 时被覆盖（它是从各包安装出来的）。要持久修改，用后面讲的 rootfs overlay 或 post-build script。

四个必知的定制手段

① rootfs overlay（最常用）

my-overlay/
└── etc/
    ├── inittab
    └── network/interfaces

make menuconfig
# System configuration → Root filesystem overlay directories → /path/to/my-overlay

overlay 里的文件会覆盖 target 里的同名文件，其余合并。改配置、改脚本都靠它。

② post-build script

# System configuration → Custom scripts to run before creating filesystem images
# 例：把交叉编译好的自研程序拷进 rootfs
cat > board/pi5/post-build.sh <<'EOF'
#!/bin/sh
cp "$BR2_EXTERNAL/../app/myapp" "$TARGET_DIR/usr/bin/"
chmod +x "$TARGET_DIR/usr/bin/myapp"
EOF

$TARGET_DIR 是环境变量，永远是它，不要写死路径。

③ 保存自己的 defconfig

make savedefconfig                 # 产出 defconfig（去冗余）
cp defconfig configs/myboard_defconfig

⭐ make savedefconfig 而不是直接拷 .config —— 前者只保存与默认值不同的项，可移植；后者几千行，升级 Buildroot 后容易冲突。

④ BR2_EXTERNAL（把自定义内容放在 Buildroot 树之外）

my-project/
├── Config.in
├── external.mk
├── configs/myboard_defconfig
├── board/myboard/{post-build.sh,genimage.cfg,rootfs-overlay/}
└── package/myapp/{Config.in,myapp.mk}

make BR2_EXTERNAL=/path/to/my-project myboard_defconfig

⭐ 正经项目一定要用 BR2_EXTERNAL。直接改 Buildroot 源码树会导致 git pull 升级时冲突，也没法把自己的东西单独版本管理。

常见故障对照

现象 原因 修法
编译某包失败 依赖缺/源码下载失败 看 output/build/<pkg>/ 下的日志；make <pkg>-dirclean 后重试
下载慢/失败 源码在境外服务器 设 BR2_PRIMARY_SITE 镜像；或手动把 tarball 放进 dl/
改了 target/ 里的文件，重编后没了 它本来就是生成物 改用 overlay 或 post-build
镜像能起但没网络 没开 DHCP 客户端 / 没配 interface 开 ifupdown 或 systemd-networkd，配 /etc/network/interfaces
root 登录不了 /etc/shadow 里 root 没密码、或 getty 没起 System configuration 里设 root 密码；检查 inittab
make 报 host 缺工具 缺 which/sed/make/gcc/g++ 等 看官方文档 "Mandatory packages"，apt 装齐

排查第一定律：make 失败时，真正的错误信息在它调用的那条命令的输出里，往往被几百行 make 噪音盖住。用 make 2>&1 | tee build.log 再 grep -i error build.log，或直接看 output/build/<pkg>-<ver>/ 下的日志。

HFT / 嵌入式关联

  • Buildroot 的"整体重建"哲学值得借鉴：它不追求增量升级单个包，而是每次产出一个完整、可复现的镜像。HFT 的交易镜像同样如此 —— 你不会在生产机上 apt upgrade 一个库，而是重新出一个镜像整体替换。"不可变基础设施"在嵌入式是默认形态，在数据中心是最佳实践。
  • 构建时间 vs 迭代速度的权衡：Buildroot 首次慢、之后快（ccache 可进一步加速）。HFT 的 C++ 项目同样要靠 ccache / 分布式编译把迭代周期压到分钟级 —— 反馈周期决定了你能试错多少次，也就决定了最终质量。
  • BR2_EXTERNAL 的"自定义与上游分离"是标准的工程纪律：不改上游、把差异外置。这条在任何依赖管理场景都成立。
Q1：什么时候该从 Buildroot 换到 Yocto？

出现下面任一信号：

  1. 需要在线升级单个包（不能整机重刷）
  2. 要支持多款硬件，且希望复用 recipe
  3. 需要合规审计（SPDX、许可证清单、CVE 追踪 —— Yocto 原生支持）
  4. 团队 > 1 人，需要 layer 来划分职责边界
  5. 有长期维护需求（几年甚至十年）

一个人的学习项目、一块板子、一个固定形态的产品镜像 —— Buildroot 完全够，而且更省命。

Q2：output/target/ 里的文件我明明改了，为什么重编后没了？

因为它不是源码，是生成物：每个包 make install 到 staging/target，最后打包成镜像。你改的是中间产物，下次 make 会重新生成。

正确的持久化方式有三种：

方式 适合
rootfs overlay 改配置文件（/etc/...）
post-build script 拷自研二进制、建目录、改权限
写自己的 package（.mk + Config.in） 从源码编一个第三方/自研软件

判据：这个改动需要"被版本管理"吗？ 需要就做成 overlay 或 package；临时调试可以直接改 target 再 make 一次（不重编包，只重打包）。

Q3：savedefconfig 和直接拷贝 .config 差在哪？

.config 是完整快照（几千行，包含所有默认值）；defconfig 只保存与默认值不同的项（通常几十行）。

后果差异： - Buildroot / 内核升级后，配置项的名字和默认值可能变化。完整 .config 会因为"某项已不存在"而报错或产生怪异行为；defconfig 会自动套用新默认值，冲突最小。 - defconfig 能一眼看出"我到底改了什么"—— 这才是配置该有的样子。

永远 make savedefconfig。
