导读

本节讲什么： 从掉电到内核拿到控制权之间的全过程，以及 U-Boot 在其中扮演的角色。 核心提醒： 树莓派不是标准 U-Boot 启动。Pi 的启动链是 BootROM → EEPROM → armstub/TF-A →（可选 U-Boot）→ 内核。拿通用 ARM 开发板的经验硬套 Pi 会踩坑。 对应动手： P5 · B3（U-Boot / 固件启动参数 + cmdline）

启动链（通用 ARM vs 树莓派）

阶段 通用 ARM 板 树莓派
1 SoC 内部 BootROM 同（片内 ROM）
2 SPL → U-Boot proper（多在 SPI Flash） EEPROM bootloader（板载，可 rpi-eeprom-update）
3 — 读 SD 卡 config.txt / cmdline.txt + 加载 armstub / TF-A
4 U-Boot 加载内核 + DTB armstub 直接跳内核（默认不走 U-Boot）
5 bootz/booti kernel= 指定镜像

结论： Pi 上"bootloader 配置"的实际载体是 config.txt 和 cmdline.txt，不是 U-Boot 环境变量。要做 U-Boot 实验得在 config.txt 里显式指定 kernel=u-boot.bin。

DTB 是怎么进内核的

bootloader 把 DTB 物理地址放进寄存器 / 按 arm64 boot protocol 传入
        ↓
内核早期解析 DT → 展开成 device_node 树
        ↓
platform/i2c/spi 总线按 compatible 匹配驱动

这是 09 驱动 03-platform-dt 的前置——驱动能 probe 成功，前提是 DTB 里有正确的节点。

关键命令

# 运行时看内核收到的 cmdline 与 DT
cat /proc/cmdline
dtc -I fs -O dts /proc/device-tree | head -50   # 反编译运行时 DT

# Pi 固件与启动配置
vcgencmd version
cat /boot/firmware/config.txt
sudo rpi-eeprom-update

HFT / 嵌入式关联

  • 启动时间就是故障恢复时间。HFT 网关重启一次的成本按秒算，所以理解启动链不只是"能起来"，还要知道每一段能不能砍（去掉 U-Boot 交互延时、裁剪内核、跳过 initrd）。
  • cmdline 里的 isolcpus、nohz_full、rcu_nocbs 是后面做绑核/隔离的入口，属于 06-boot-to-shell 和 14-hft-engineering 的内容。

3.1

U-Boot · BIOS · UEFI：能类比，不能等同

FAQ · 锚定 Primer Ch2 §2.1.2 BIOS vs Bootloader
章摘要：notes.md · 深挖 Boot → Ch7

1. 核心结论

说法 对不对
U-Boot 与 UEFI 都是「上电固件 → 交权给内核」 功能同源可类比
U-Boot 等于 UEFI 否 — 定位、标准、运行时、体积、生态都不同
BIOS 是老 x86 固件，UEFI 是其现代化替代 是
书中「BIOS ↔ Bootloader」今天改读「UEFI ↔ U-Boot」 逻辑仍成立

2. 三者共性（都是引导固件一类）

  1. 上电极早执行：初始化 CPU / 内存 / 关键外设
  2. 常有命令行、存储读写、网络拉镜像等能力（具体强弱差很多）
  3. 最终加载 OS 内核并移交控制权
  4. 向内核递硬件描述：UEFI 侧常见 ACPI；嵌入式 U-Boot 侧常见 Device Tree

3. 关键区别

（1）适用硬件

固件 典型平台
传统 BIOS 老旧 x86 PC（已淘汰叙事）
UEFI 现代 PC/服务器；部分 ARM/RISC-V 通用计算板
U-Boot 嵌入式 SoC（ARM/MIPS/Power…）：路由、工控、车载、开发板

（2）标准化

  • UEFI：统一规范（驱动模型、Runtime、Secure Boot、GPT 等）
  • U-Boot：开源实现，无等同强制国际规范；各 SoC 厂移植，命令与内存布局差异大

（3）内核起来之后还在不在

内核启动后
UEFI 可保留 Runtime Services（运行中仍可能调固件接口）
U-Boot 交权后固件资源通常丢弃；要再进 U-Boot 多半只能复位 — 与书中对 BIOS/Bootloader 的对比一致
BIOS 亦非「像 UEFI Runtime 那样」长期给 OS 当服务总线

（4）体积与生态

体量 嵌入式相关
UEFI 常很大（可达百 MB 级叙事），可有图形、安全启动、分区管理 对小 Flash 不友好
U-Boot 可裁到很小（KB～MB 级视配置） 原生贴近 NAND/JFFS2/UBIFS、TFTP/NFS 开发流

（5）硬件描述

  • UEFI 世界：ACPI 表为主
  • U-Boot + 嵌入式 Linux：device tree（DTS/DTB）
  • DT ≠ UEFI（DT 是图纸，U-Boot 是工具箱）— 7.0 FAQ · 09 驱动·DT

4. 书为何拿 BIOS 比 Bootloader（2010 语境）

当年 PC 主流叙事仍是 BIOS：

  1. PC 有相对标准的固件，开发者很少从零写 BIOS
  2. 自定义嵌入式板 没有 统一固件，必须移植 U-Boot 等
  3. 今天：把参照物换成 UEFI，对比逻辑不变 — 通用计算板吃标准固件；自定义 SoC 板吃 U-Boot 移植

5. 嵌入式何时会碰到 UEFI？

  • 高端 ARM 服务器、部分工控/国产计算平台、要 Windows+Linux 双系统等
  • 绝大多数消费/工控小系统（路由、传感器网关、Pi 类开发板启动链）仍是 U-Boot 或厂商精简 boot 链，不上笨重 UEFI

树莓派：官方固件 + config.txt 路径与经典「纯 U-Boot 板」不完全相同，但 「固件阶段 → 内核 → rootfs」 四阶段骨架仍适用（见 notes 2.2.3）。

3.2

U-Boot 环境变量与 bootcmd：启动脚本到底怎么跑

本节讲什么： U-Boot 的"大脑"就是环境变量。搞懂 bootcmd / bootargs / boot_targets，你就知道"改一行配置让系统换个方式启动"是怎么发生的。 前置： 3.1 U-Boot vs BIOS/UEFI 动手： P5 · B3 卡住查书： MELP Ch3 · Primer Ch7

一句话

U-Boot 启动 = 执行 bootcmd 这个环境变量里的一串命令。

上电 → U-Boot 初始化 → 等 bootdelay 秒（可按键打断进命令行）
                            ↓
                    执行 bootcmd
                            ↓
        （加载内核、DTB、initramfs → 设置 bootargs → bootm/booti 启动内核）

打断后你就在 U-Boot 命令行里，可以 printenv、setenv、saveenv、run —— 这就是"引导加载器的 shell"。

三个最核心的变量

变量 作用 谁在用
bootcmd 自动执行的启动脚本 U-Boot 自己
bootargs 传给内核的命令行 内核（等价于 x86 上 GRUB 的 linux ... 行）
boot_targets 尝试从哪些设备启动，按序 U-Boot 的 distro_bootcmd 
# U-Boot 命令行里
=> printenv bootcmd
bootcmd=run distro_bootcmd

=> printenv bootargs
bootargs=console=ttyAMA0,115200 root=/dev/mmcblk0p2 rootwait

=> printenv boot_targets
boot_targets=mmc0 usb0 pxe dhcp

bootcmd 的执行模型

bootcmd 通常不是一长串命令，而是调用别的变量（U-Boot 里的"函数"）：

bootcmd = run distro_bootcmd
              │
              └─ distro_bootcmd = for target in ${boot_targets}; do run bootcmd_${target}; done
                                        │
                                        └─ bootcmd_mmc0 = ... 加载内核并启动

关键机制：

命令 作用
run <var> 把变量的内容当脚本执行（U-Boot 的"函数调用"）
${var} 变量展开
if <cmd>; then ...; else ...; fi 条件（依赖命令的返回值，不是表达式）
for v in <list>; do ...; done 循环

⭐ U-Boot 的 if 判断的是命令是否执行成功（返回码 0 = 成功），不是布尔表达式。这是它跟普通 shell 最大的不同：

if load mmc 0:1 ${kernel_addr_r} /Image; then echo "OK"; else echo "FAIL"; fi
#  ↑ 判的是 load 命令的成败

bootargs：内核命令行从哪来

bootargs=console=ttyAMA0,115200 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait

U-Boot 启动内核时（booti / bootz / bootm）会自动把 bootargs 塞进设备树的 /chosen/bootargs 属性（或直接传给内核），内核解析后出现在 /proc/cmdline。

# 启动后核对（永远先看这个）
cat /proc/cmdline

常见参数：

参数 作用
console= 内核 printk 输出到哪（见 6.2）
root= 根设备
rootwait / rootdelay= 等设备就绪（SD/USB 必须）
init= / rdinit= 指定 PID 1（见 6.1）
earlycon 早期控制台
initcall_debug 打印每个 initcall 耗时（见 6.3）

环境存储：环境变量存在哪

saveenv  → 写到持久化存储（SPI NOR / eMMC 的 boot 分区 / SD 卡的固定偏移）
printenv → 从内存读（启动时从存储加载）

⚠️ 最常见的坑：setenv 只改内存，不 saveenv 重启就丢。

=> setenv bootargs "...新参数..."
=> saveenv                      # ← 漏了这步就白改
Saving Environment to SPI Flash...

配置文件是 include/configs/<board>.h 里的 CONFIG_EXTRA_ENV_SETTINGS，或 CONFIG_ENV_OFFSET / CONFIG_ENV_SIZE 指定存储位置。

从 Linux 用户态改（不用进 U-Boot）：

fw_printenv bootargs
fw_setenv bootargs "console=ttyAMA0,115200 root=PARTUUID=...-02 rootwait"

⚠️ fw_setenv 需要一个 /etc/fw_env.config 描述环境区的位置和大小 —— 这个文件写错会写坏存储，务必对照 U-Boot 配置里的 CONFIG_ENV_OFFSET/SIZE。

Pi 5 的现实：默认不走 U-Boot

⚠️ 重要：Pi 5 默认用闭源固件启动，不是 U-Boot：

上电 → 片内 ROM → SD 卡上的 start4.elf（GPU 固件）
                    → 读 config.txt
                    → 加载 kernel8.img + DTB
                    → 启动内核

等价物：

U-Boot 概念 Pi 5 对应
bootcmd 固化在固件里，不可编程
bootargs /boot/firmware/cmdline.txt（一整行）
环境变量 /boot/firmware/config.txt（key=value）
saveenv 直接编辑那两个文本文件 
# Pi 5 上改内核命令行
sudo vi /boot/firmware/cmdline.txt     # 一整行！不能换行
sudo vi /boot/firmware/config.txt      # enable_uart=1 等
sudo reboot

⭐ 学习建议：Pi 5 上先按 cmdline.txt 的方式玩（成本低），要理解 U-Boot 的完整机制，用 QEMU 虚拟 ARM 板（qemu-system-aarch64 -M virt + U-Boot）练手，那里能真正进 U-Boot 命令行。

HFT / 嵌入式关联

  • bootcmd 是"启动脚本即配置"的范例：整条启动流程是可读、可版本管理、可回滚的文本。HFT 的部署配置同样该是声明式的文本，而不是"某台机器上跑过一堆命令"。
  • "改内存不 saveenv 就丢" 对应生产环境的经典事故：改了配置没持久化 / 改了配置没生效。判据永远是"重启后 cat /proc/cmdline 看到的是什么"，而不是"我记得我改了"。
  • bootcount + altbootcmd 的自动回退（见 7.3）是"失败检测独立于被检测对象"的典范 —— 这条原则在交易系统的健康检查里同样关键。
Q1：为什么 setenv 了但重启后没变？

因为 setenv 只改内存中的环境副本。U-Boot 启动时从持久存储（SPI Flash / eMMC / SD 卡固定偏移）加载环境到 RAM，所有修改都在 RAM 里，掉电即失。

必须 saveenv 才会写回存储。

排查：printenv 看当前内存值，重启后再 printenv 对比 —— 如果不同，说明没保存成功（也可能是存储写保护或 CONFIG_ENV_OFFSET 与实际不符导致写到了错误位置）。

Q2：U-Boot 的 if 和普通 shell 的 if 有什么不同？

U-Boot 的 if 只能判断命令的退出码（0 = 成功），没有 test 之外的表达式能力，而且语法细节不同：

# U-Boot（then/else 前要有分号或换行，fi 结尾）
if load mmc 0:1 ${loadaddr} /Image; then echo OK; else echo FAIL; fi

# 判断字符串相等要用专门的 test 命令
if test "${boot_part}" = "2"; then ...; fi

常见陷阱： - ${var} 展开后为空会导致语法错误 → 用 "${var}" 加引号 - U-Boot 的 if 不支持 [ ]，要用 test 命令 - 没有 && / || 的短路组合（部分版本支持 ; 串联）

调试技巧：先在命令行单独跑那条命令，看它返回什么，再包进 if。

Q3：booti / bootz / bootm 有什么区别？
命令 镜像格式 用在哪
booti Image（未压缩的原始 ARM64 内核） ⭐ ARM64 现代内核
bootz zImage（自解压的 32 位 ARM 内核） ARM32
bootm uImage（U-Boot 封装格式，带 64 字节头） 老式/多镜像（bootm <kernel> <ramdisk> <dtb>）

参数格式：

booti <内核地址> - <dtb地址>          # "-" 表示没有 initramfs
booti ${kernel_addr_r} - ${fdt_addr_r}

选错了内核不会启动，通常报 Bad Linux ARM64 Image magic! —— 这不是镜像坏了，是你用错了命令。

3.3

编译与烧录 U-Boot（以及 Pi 5 为什么可以不做这一步）

本节讲什么： 从源码编出一个 U-Boot、烧到板上；以及诚实地说明 Pi 5 为什么通常跳过 U-Boot。知道何时可以不做一件事，和知道怎么做同样重要。 前置： 3.2 环境变量与 bootcmd · 02-toolchain 动手： P5 · B3 卡住查书： MELP Ch3 · Primer Ch7

先决定：你这步到底需不需要做

你的目标 要不要编 U-Boot
让 Pi 5 启动、进 shell、跑驱动 ❌ 不用，用官方固件即可
理解启动流程、改启动参数 ❌ 改 cmdline.txt / config.txt 就够
做 A/B 升级 + 自动回退 ✅ 需要（bootcount 依赖 U-Boot）
学 U-Boot 本身 / 面试 / 通用技能 ✅ 用 QEMU 虚拟板练手（零硬件风险）
做自己的板子 ✅ 必须

⭐ Pi 5 的现实：它用闭源 GPU 固件（start4.elf）启动，U-Boot 不是必需的。强行在 Pi 5 上跑 U-Boot 是"可行但增加复杂度"的事，而你现在的目标是搞懂启动链并尽快开始写驱动。

推荐路径：Pi 5 上跳过 U-Boot → 用 QEMU 学 U-Boot 机制 → 真需要时再往 Pi 上移植。

路径 A：Pi 5 用官方固件（默认，推荐）

ls /boot/firmware/
#   config.txt      ← 硬件配置（相当于 U-Boot 环境变量）
#   cmdline.txt     ← 内核命令行（相当于 bootargs）
#   kernel8.img / kernel_2712.img  ← 内核
#   bcm2712-rpi-5-b.dtb            ← 设备树
#   start4.elf / fixup4.dat        ← GPU 固件（真正的"第一阶段"）

改启动参数：

# 内核命令行（★ 必须一整行）
sudo sh -c 'echo "console=serial0,115200 root=PARTUUID=xxxx-02 rootfstype=ext4 rootwait initcall_debug" > /boot/firmware/cmdline.txt'

# 硬件配置
sudo sh -c 'echo "enable_uart=1" >> /boot/firmware/config.txt'

这就是 Pi 5 上"改 bootloader 配置"的全部。 没有编译、没有烧录、还能随时用读卡器在电脑上改回来。

路径 B：QEMU 虚拟板（学 U-Boot 机制的最佳环境）

# ① 装工具
sudo apt install qemu-system-arm gcc-aarch64-linux-gnu device-tree-compiler

# ② 编 U-Boot
git clone https://github.com/u-boot/u-boot
cd u-boot
export CROSS_COMPILE=aarch64-linux-gnu-
make qemu_arm64_defconfig
make -j$(nproc)
#   产物：u-boot.bin（还有 u-boot-nodtb.bin、u-boot.dtb）

# ③ 跑起来
qemu-system-aarch64 \
  -M virt -cpu cortex-a57 -m 1G -nographic \
  -bios u-boot.bin

启动后你会看到：

U-Boot 2024.xx (...)
Hit any key to stop autoboot:  3  ← 赶紧按回车
=>                                ← U-Boot 命令行

然后就能练：

=> printenv                       # 看所有环境变量
=> printenv bootcmd bootargs
=> setenv bootargs "console=ttyAMA0 root=/dev/vda"
=> saveenv                        # QEMU 里可能没有持久存储，会报错（正常）
=> mmc list / usb start / dhcp    # 设备操作
=> help                           # 所有命令

⭐ QEMU 的最大好处：刷坏了不花钱。真实板子上把 bootloader 写坏会变砖（需要 SWD/JTAG 救），QEMU 里重启一次就好。

路径 C：真板子烧录（要点，不做详细步骤）

# 编 U-Boot（以厂商 defconfig 为准）
make <board>_defconfig
make -j$(nproc) CROSS_COMPILE=aarch64-linux-gnu-

# 烧到 SD 卡的固定偏移（不同 SoC 不同，必须查手册）
#   例：某些全志/瑞芯微平台 SPL 在 8KB 偏移处
sudo dd if=u-boot-sunxi-with-spl.bin of=/dev/sdX bs=1024 seek=8 conv=fsync

# 或烧到 SPI NOR（需要编程器或已有系统里用 flashrom）
sudo flashrom -p linux_spi:dev=/dev/spidev0.0 -w u-boot.bin

⚠️ 三条保命规则：

  1. of=/dev/sdX 一定要确认设备名（lsblk）。写错盘 = 主机系统报废。这是嵌入式新手最惨的一次性学费。
  2. 烧之前先备份原来的 bootloader：dd if=/dev/sdX of=bootloader.bak bs=1M count=4
  3. 保留一个可回退的启动方式（SD 卡启动优先于 SPI，或者留着串口 + SWD 接口）

产物说明（编出来的一堆文件是什么）

文件 是什么
u-boot.bin 完整 U-Boot（含 DTB，QEMU/多数平台用这个）
u-boot-nodtb.bin 不含设备树的纯代码
u-boot.dtb U-Boot 自己用的设备树
u-boot-spl.bin / *-with-spl.bin SPL：第一阶段，片内 SRAM 里跑，负责初始化 DRAM
u-boot.itb FIT 镜像（把多个组件打包成一个，带签名）

为什么要有 SPL

片内 ROM → SPL（在片内 SRAM 里，几十 KB） → 初始化 DRAM
                                              ↓
                                       真正的 U-Boot（加载到 DRAM，几百 KB）

鸡生蛋 again：U-Boot 太大，片内 SRAM（通常几十 KB）放不下；而 DRAM 还没初始化。所以先跑一个极小的 SPL 把 DRAM 初始化好。

这与 5.2 initramfs 的"用小自足层引导大层"是同一个模式。

常见故障

现象 原因
串口完全无输出 串口没接对/没启用；或镜像烧错偏移
输出乱码 波特率不对（常见：实际是 115200 而你设了 9600）
Bad Linux ARM64 Image magic! 用了 bootm 而不是 booti（见 3.2 Q3）
卡在 Hit any key to stop autoboot 正常，按回车进命令行，或等它继续
Wrong Image Format for bootm command 内核镜像格式不对（zImage vs Image vs uImage）
Saving Environment to... Failed 环境区未配置或写保护（QEMU 里正常）

HFT / 嵌入式关联

  • "先决定要不要做"比"怎么做"更重要。嵌入式学习最大的时间陷阱就是在 bring-up 细节上耗尽热情，却没摸到真正想学的东西（你这里的目标是驱动与低延迟，不是 bootloader）。识别并主动跳过非关键路径，是工程判断力的一部分。
  • dd 写错盘的教训：破坏性命令要先确认目标再执行。HFT 里等价的是"生产环境命令必须先 dry-run / 先在影子环境验证"。一次性学费能免则免。
  • SPL 的"分层引导" 是系统设计的通用手法：每一层只负责"让下一层能跑"。bootloader→内核→initramfs→真根→服务，五层同构。
Q1：U-Boot 和 SPL 都要烧吗？

看平台：

  • 有 SPL 的平台（全志、瑞芯微、部分 NXP）：烧 u-boot-with-spl.bin 到 SPL 的偏移（通常 8KB 或 32KB 处），SPL 会自己加载后续部分。
  • 无 SPL 的平台（QEMU virt、部分有片内 ROM 能直接加载完整 U-Boot 的）：只烧 u-boot.bin。
  • 多阶段（ARM Trusted Firmware）：顺序是 ROM → SPL → ATF(BL31) → U-Boot(BL33) → Linux，每个烧到不同偏移。

判据：查 SoC 的启动手册或 U-Boot 的 board/ 目录下该板子的 README。 不要猜 —— 偏移量错一个字节都不启动。

Q2：为什么 QEMU 里 saveenv 会失败？

因为 qemu_arm64_defconfig 没有配置环境存储位置（没有 SPI NOR、没有指定 MMC 环境分区），U-Boot 不知道往哪存。

这不是 bug，是 QEMU 环境的正常状态 —— 它本来就用于"跑一次看看"，环境不持久化。

想练 saveenv：给 QEMU 加一个虚拟磁盘并在 U-Boot 里配置 CONFIG_ENV_IS_IN_MMC，或者直接接受"内存里改着玩就行"。

Q3：把 bootloader 刷坏了怎么救？

按救援难度递增：

  1. SD 卡优先的板子：拔掉/换一张好卡即可（eMMC 里的坏 bootloader 不会被用到）
  2. 串口 + U-Boot 还能进：命令行里重刷
  3. SWD/JTAG（STM32、部分 NXP）：用调试器直接写 Flash，绕过 bootloader
  4. MaskROM / 下载模式（全志的 FEL、瑞芯微的 MaskROM）：SoC 片内 ROM 支持的 USB 下载，专门用来救砖
  5. 拆芯片编程器：最后的手段

⭐ 所以 bring-up 阶段的第一件事应该是：确认救援路径存在并且你练过一次。 这跟"上线前先验证回滚方案"是同一个道理 —— 没验证过的备份等于没有备份。
