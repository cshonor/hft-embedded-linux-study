导读

本节讲什么： 选存储介质、设计分区、让系统在无人值守环境下安全升级。 为什么放最后： 这一节是"能跑"到"能交付"的分界线。前面六节让板子起来，这一节让它能在现场活下去。

介质选型

介质 特点 注意
microSD 便宜、可换 有写入寿命，掉电易损坏文件系统。不适合写入密集
eMMC 焊死、比 SD 可靠 工业级首选
NOR/NAND Flash 走 MTD 子系统 需要 UBI/UBIFS，不是块设备，不能用 ext4
NVMe（Pi 5 有 PCIe） 快、可做根分区 Pi 5 可经 RP1 的 PCIe 挂 NVMe，需配置启动顺序

文件系统： ext4（块设备通用） · squashfs（只读压缩，防篡改） · overlayfs（只读底 + 可写上层） · UBIFS（裸 Flash）。

分区策略：为什么产品都用只读 rootfs

[ boot (FAT) ] [ rootfs A (ro) ] [ rootfs B (ro) ] [ data (rw) ]
                    ↑ 当前           ↑ 升级目标
设计 目的
只读 rootfs 掉电不损坏；防误改；与"配置与代码分离"同构
A/B 双分区 升级写到备用分区，失败自动回退
独立 data 分区 日志与配置独立，升级不丢
overlayfs 需要"看起来可写"时，用内存层承接写操作

关键命令

# 看分区与挂载
lsblk -f
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS

# overlay 结构
mount -t overlay overlay -o lowerdir=/ro,upperdir=/rw/upper,workdir=/rw/work /merged

# 只读切换（救急）
mount -o remount,ro /

HFT / 嵌入式关联

  • 只读 rootfs 是"不可变基础设施"在嵌入式的形态：HFT 生产机上，交易二进制通常也放在只读挂载点，防止运行期被改。
  • A/B 升级 + 快速回退 对应交易系统的灰度发布：新版本出问题要能在一次心跳内回退，而不是现场重刷。
  • 掉电保护这件事在嵌入式是物理约束，在 HFT 机房是 UPS + 持久化日志——问题同构，解法不同，值得对照着看。

7.1

存储介质与文件系统：为什么 NAND 不能用 ext4

本节讲什么： 选介质、选文件系统，以及理解块设备与裸 Flash 的根本区别 —— 这是嵌入式与 PC 存储最大的认知差异。 前置： 06-boot-to-shell 卡住查书： MELP Ch9–10 · Primer Ch10（MTD）

先分两类：块设备 vs 裸 Flash

                  ┌─ 块设备（Block Device）── ext4 / f2fs / squashfs / btrfs
存储 ─────────────┤     有控制器：擦写均衡、坏块管理都在里面做
                  │     对外表现为"可读可写的 512B/4K 扇区数组"
                  │
                  └─ 裸 Flash（MTD）───────── UBI / UBIFS / JFFS2
                        无控制器：擦写均衡、坏块管理**必须由软件做**
                        对外表现为"必须先擦除（按块）再写入（按页）"

⭐ 这就是"NAND 不能用 ext4"的全部理由：ext4 假设底层是"随时可覆盖写的扇区数组"，而裸 NAND 必须先擦后写，且擦除单位是写入单位的几十倍。ext4 会在原地改写元数据，NAND 上这么做既错又慢，还会迅速写坏块。

介质选型

介质 类型 容量 特点 用在哪
microSD 块设备 GB 级 便宜、可换、有控制器；掉电易损坏、写入寿命有限 开发、原型
eMMC 块设备 GB 级 焊死、比 SD 可靠、工业级温度 工业产品首选
NOR Flash MTD MB 级 读快、可直接 XIP（就地执行）、贵 存 bootloader
NAND Flash MTD GB 级 便宜、密度高、有坏块、需要 ECC 大容量存储
NVMe（Pi 5 有 PCIe） 块设备 百 GB 快、可做根分区；需要配置启动顺序 高性能/日志密集

判据表

你的需求 选
学习/原型 microSD（坏了换一张）
量产、无人值守 eMMC
启动代码 NOR（小、可靠、可 XIP）
大容量低成本 NAND + UBI/UBIFS
高写入吞吐（日志、行情落盘） NVMe / eMMC，避开 SD 卡

⚠️ microSD 的隐藏成本：它的控制器为"相机/手机的顺序大文件写入"优化，对小随机写（数据库、日志、文件系统元数据）表现极差，且掉电时正在写的块可能损坏 —— 这会让只读 rootfs + 独立 data 分区的设计从"可选"变成"必需"。

文件系统选型

文件系统 介质 特点 用在哪
ext4 块设备 通用、成熟、有日志 通用 rootfs / data
f2fs 块设备（Flash 友好） 为 Flash 的追加写优化，日志型 eMMC/SD 上的 data 分区
squashfs 块设备 只读压缩，体积减半 只读 rootfs 首选
overlayfs 叠加在其他 fs 上 只读底 + 可写上层 "看起来可写"的只读系统
UBIFS 裸 Flash（UBI 卷） 擦写均衡 + 坏块管理 + 压缩 NAND 上的 rootfs
tmpfs 内存 掉电即失、极快 /tmp、/run

决策树

是裸 Flash（无控制器）吗？
   ├─ 是 → UBIFS（必须先建 UBI 卷）
   └─ 否（块设备）
        ├─ 分区需要写吗？
        │    ├─ 否 → squashfs（只读、省空间、防篡改）
        │    └─ 是 → 写入模式是？
        │              ├─ 大量小随机写 → f2fs
        │              └─ 通用           → ext4
        └─ 想要"看起来可写"的只读系统 → squashfs + overlayfs

关键命令

# 看块设备与挂载
lsblk -f                                   # 带文件系统类型和 UUID
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS    # 看挂载选项（有没有 ro）
blkid                                      # UUID / PARTUUID（写 fstab 用）

# 看 MTD 设备（裸 Flash）
cat /proc/mtd
mtdinfo /dev/mtd0

# 健康度
dmesg | grep -i -E 'mmc|ext4-fs error|I/O error'
smartctl -a /dev/nvme0n1                   # NVMe
mmc extcsd read /dev/mmcblk0 | grep LIFE   # eMMC 寿命（需 mmc-utils）

⭐ PARTUUID 比 /dev/mmcblk0p2 可靠：设备名会因插拔顺序、枚举时序变化；PARTUUID 写死在分区表里。

# /etc/fstab 推荐写法
PARTUUID=12345678-02  /      ext4   ro,noatime  0  1
PARTUUID=12345678-01  /boot  vfat   defaults    0  2

三个实践要点

1. noatime（几乎白送的性能）

每次读文件都要更新 atime → 每次读变成一次写。对 Flash 是双倍伤害（性能 + 寿命）。

defaults,noatime

现代内核默认 relatime（折中方案），但 noatime 更彻底，嵌入式上直接用它。

2. 日志（journal）的取舍

ext4 的 journal 保证崩溃一致性，代价是额外的写入放大。

# 关掉（省写入、省时间，但崩溃可能损坏）
mkfs.ext4 -O ^has_journal /dev/sdX1
tune2fs -O ^has_journal /dev/sdX1

# 或 data=writeback（只保护元数据，不保护数据）
mount -o data=writeback

⭐ 只读 rootfs 根本不需要 journal（它永远不写），这也是 squashfs 更快的原因之一。

3. 对齐与块大小

Flash 的擦除块通常 128 KB ~ 几 MB。分区起始地址不对齐会导致一次逻辑写变成两次物理擦写。

# 分区时对齐到 1MiB（parted）
parted -a optimal /dev/mmcblk0 mkpart primary ext4 1MiB 100%

HFT / 嵌入式关联

  • 存储层次的选择本质是延迟与持久性的权衡。HFT 里同样的取舍：行情落盘用 NVMe（持久化）还是共享内存（快但掉电即失）？判据是丢了之后能不能重放 —— 能从撮合流重建就别落盘。
  • "写入放大"在两者都是成本中心：嵌入式关心 Flash 寿命，HFT 关心写盘延迟抖动（fsync 卡住主线程）。解法同构：批量写、追加写、避开原地改写元数据。
  • 只读 + 独立可写区的设计在 HFT 生产机上同样成立：二进制和配置在只读挂载点（防误改、防篡改），日志和状态在独立分区。这是"不可变基础设施"的落地形态。
Q1：为什么 NAND 必须"先擦后写"，而 eMMC 不用？

物理特性决定了它：NAND 的写只能把位从 1 改成 0，擦才能把位从 0 改回 1，而擦除的最小单位（block，通常 128KB~几 MB）远大于写入单位（page，2~16KB）。所以想改写一个 page，必须擦掉整个 block。

eMMC/SD 卡内部有一个控制器（FTL：Flash Translation Layer），它把这套"先擦后写 + 擦写均衡 + 坏块替换"全藏在里面，对外只暴露"可读写的扇区数组"—— 所以上层可以跑 ext4。

裸 NAND 没有这层，所以必须由软件（MTD + UBI）来做。这就是"能不能用 ext4"的分界线：看有没有 FTL，而不是看是不是 Flash。

Q2：squashfs 压缩会不会让启动变慢？

不一定，甚至可能更快：

  • 读取量变小：压缩后 I/O 量减少，而嵌入式上 I/O（尤其 SD 卡）往往比 CPU 解压慢
  • 顺序读：启动是顺序读，压缩对顺序读友好

代价是单次随机读需要解压整个块（squashfs 默认 128KB 块），所以：

  • ✅ 适合：整个 rootfs（顺序读为主）
  • ❌ 不适合：数据库、频繁随机访问的数据

实测才是判据 —— 用 6.3 启动耗时 的方法量一次，别猜。

Q3：/proc/mtd 里有设备，能用 mkfs.ext4 /dev/mtd0 吗？

不能，而且会报错或产生一个坏的文件系统。

/dev/mtdX 是字符设备（按字节访问裸 Flash），不是块设备。ext4 需要"可随机覆盖写的扇区"，裸 Flash 给不了。

正确路径是三层：

/dev/mtd0  （裸 Flash 分区）
   ↓  ubiattach / ubiformat
/dev/ubi0  （UBI 设备：做擦写均衡 + 坏块管理 + 逻辑卷）
   ↓  ubimkvol
/dev/ubi0_0 （UBI 卷：表现为块设备）
   ↓  mkfs.ubifs / mount -t ubifs
文件系统

UBI 就是软件实现的 FTL —— 它把裸 Flash 变成"看起来像块设备"的东西，之后才能在其上建文件系统。

7.2

只读 rootfs 与 overlayfs：让系统不怕掉电

本节讲什么： 为什么产品都用只读 rootfs、overlayfs 的三层结构怎么搭、以及"看起来可写"这个技巧的代价。 前置： 7.1 介质与文件系统 卡住查书： MELP Ch9–10

为什么只读

理由 说明
掉电安全 不写就不会写坏。SD 卡上 90% 的损坏来自"掉电时正在写元数据"
防误改/防篡改 攻击者或误操作改不了 /usr/bin；配合 dm-verity 还能检测篡改
可复现 所有同型号设备跑的是逐字节相同的系统
配合 A/B 升级 只读分区才能整体替换（见 7.3）
省写入寿命 Flash 擦写次数有限

⭐ 一句话：把"会变的东西"和"不变的东西"分开。 系统会变（配置、日志、数据），系统本身不该变（二进制、库）。

分区布局

┌──────────┬─────────────┬─────────────┬──────────────┐
│  boot    │  rootfs A   │  rootfs B   │    data      │
│  (FAT)   │  (ro)       │  (ro)       │    (rw)      │
│  固件/内核│  当前系统    │  升级目标    │ 配置/日志/状态│
└──────────┴─────────────┴─────────────┴──────────────┘
                 ↑                           ↑
           升级整体替换                  升级时保留
分区 挂载 内容 大小
boot rw（升级时才写） 内核、DTB、bootloader 配置 几十~几百 MB
rootfs A/B ro squashfs 或 ext4(ro) 系统大小 ×1
data rw /etc 配置、日志、应用数据 按需求 
# /etc/fstab 示例（ro rootfs + 独立 data）
PARTUUID=...-02  /       squashfs  ro,noatime    0  1
PARTUUID=...-04  /data   ext4      rw,noatime    0  2

⚠️ 注意 /etc 的问题：很多程序默认往 /etc 写配置（如 sshd 生成 host key）。rootfs 只读时就写不了。三种解法：

解法 做法 适合
符号链接 /etc/xxx → /data/etc/xxx 少量已知文件
bind mount mount --bind /data/etc /etc 整个 /etc 都要可写
overlayfs 见下 想"整体看起来可写"

overlayfs：把只读和可写叠起来

              /merged  ← 用户看到的是这个（挂载点）
                 │
      ┌──────────┴──────────┐
      │                     │
  upperdir              lowerdir
  (rw, 可写层)          (ro, 只读底层)
      │                     │
      └──────────┬──────────┘
                 │
            workdir（必须是同一文件系统的空目录）

规则：

操作 行为
读 upper 有就用 upper，否则读 lower
写（修改已有文件） 先复制到 upper（copy-up），再在 upper 上改；lower 不变
删 在 upper 建一个 whiteout（字符设备 0:0）遮住 lower 的文件
建目录 在 upper 建；若 lower 有同名目录则建 opaque 目录（合并两边内容）

挂载

mkdir -p /data/overlay/{upper,work} /merged

mount -t overlay overlay \
      -o lowerdir=/,upperdir=/data/overlay/upper,workdir=/data/overlay/work \
      /merged

# 然后 pivot_root 或 chroot 到 /merged

fstab 写法：

overlay / overlay lowerdir=/,upperdir=/data/overlay/upper,workdir=/data/overlay/work 0 0

三个必踩的坑

坑 现象 解法
workdir 必须与 upperdir 同一文件系统 mount: wrong fs type 都放 /data 下
upperdir 满了 写操作 ENOSPC，系统"突然变砖" 监控 upper 用量；或限制只有特定目录可写
copy-up 丢失文件元数据 第一次写大文件时慢（整个文件要复制） 提前把需要写的文件放进 upper

⚠️ overlayfs 不是免费的：

  1. copy-up 的首次写有延迟抖动（复制整个文件）
  2. upper 层无界增长（所有改动都累积）
  3. lower 变了，upper 的 whiteout 可能遮住新文件（升级后旧配置"消失"）

⭐ 所以 overlayfs 最适合"开发/调试期让只读系统可用"，产品上更推荐"明确的 data 分区 + 符号链接" —— 显式的东西比隐式的好排查。

实践：找出"到底谁在写"

# ① 简单粗暴：把 / 挂 rw，跑一段时间，看哪个文件新
find / -xdev -newermt '-10 minutes' -not -path '/proc/*' -not -path '/sys/*' 2>/dev/null

# ② 精确：fatrace（文件访问跟踪）
fatrace -t -c            # -c 只看当前进程树

# ③ 内核级：ftrace 的 vfs_write 事件
trace-cmd record -e vfs_write && trace-cmd report

流程：先让它可写 → 跑一遍完整业务 → 找出所有被写的文件 → 逐个决定"移到 data 分区 / 符号链接 / 干脆不要写"。

HFT / 嵌入式关联

  • 只读 = 不可变基础设施：HFT 生产机上交易二进制通常也在只读挂载点，防止运行期被改（无论是恶意还是误操作）。"能改"本身就是风险面。
  • "把会变的和不变的分开"是架构级原则：对应到交易系统 = 代码（不可变）vs 配置/状态（可变）。配置要能热更新，代码不能。
  • overlayfs 的 copy-up 抖动值得警惕：它在嵌入式上只是"首次写慢一点"，在 HFT 上可能是一次 p99 尖刺。所以 HFT 系统宁愿用显式的双缓冲 / 预分配，也不用"按需复制"这种延迟不可预测的机制。可预测的延迟比平均延迟重要。
  • 掉电保护这件事在嵌入式是物理约束（真的会断电），在 HFT 机房是 UPS + 持久化日志 —— 问题同构，解法不同，值得对照着看。
Q1：copy-up 是什么意思，为什么会慢？

overlayfs 的 lower 层是只读的。当你修改一个只存在于 lower 的文件时，它必须先把整个文件复制到 upper，然后才能在 upper 上修改。这就是 copy-up。

慢在哪：一个 100 MB 的文件，你只改 1 个字节，也要先复制 100 MB。

触发条件的坑：即使你只是 chmod（改元数据）或 truncate，也会触发 copy-up。

规避：把确定要写的大文件预先放进 upper，或干脆用 bind mount 指向 data 分区。

Q2：为什么 workdir 必须和 upperdir 在同一个文件系统？

因为 overlayfs 需要在同一个文件系统内做原子重命名（rename(2)）。它的实现要先把内容写进 workdir，再原子地 rename 到 upper —— 这保证了"要么看到旧版本，要么看到新版本"，不会看到写了一半的文件。

跨文件系统无法原子 rename，所以内核直接拒绝挂载。

这是"用原子 rename 实现原子更新"的经典手法 —— 后面 7.3 A/B 升级 和很多配置热更新方案用的都是同一招。

Q3：只读 rootfs 了，怎么打补丁/修 bug？

不要打补丁，整体替换。 这正是只读设计的意图：

  1. 在构建机出新镜像
  2. 写进备用分区（rootfs B）
  3. 切换 bootloader 指向
  4. 失败自动回退到 rootfs A

这就是 A/B 升级。如果你需要"现场改一个文件然后重启生效"，说明那个文件根本不该在 rootfs 里 —— 它应该属于 data 分区。

⭐ 判据：问自己"这个文件是系统的一部分，还是系统的输入？" 输入（配置、数据）放 data 分区，系统（代码、库）放只读 rootfs。

7.3

A/B 升级与回滚：设备出场之后怎么活

本节讲什么： 设计一套"升级失败也能自己爬起来"的机制。硬件在客户手里，你没有第二次机会。 前置： 7.2 只读 rootfs 与 overlayfs 卡住查书： MELP Ch10 · 实战框架 RAUC / SWUpdate / Mender

核心问题

设备在现场，你要升级
   ├─ 升级包传一半断了        → 不能留下半个系统
   ├─ 新系统起不来            → 必须自动回到能用的那个
   ├─ 新系统起来了但功能坏了  → 需要"确认"机制
   └─ 升级中途掉电            → 不能变砖

A/B 的全部设计都是围绕这四件事。 关键洞察：永远不要覆盖正在运行的那个系统。

基本流程

                  ┌──────────────────────────────────────┐
                  │                                      │
   ① 写备用分区   │  rootfs A (ro, 运行中)  rootfs B      │
      （随便写，  │      ↑ 当前                 ↑ 写这里  │
       写坏了也  │                                      │
       不影响）  └──────────────────────────────────────┘
                  │
   ② 校验         │  sha256 + 签名（必须！）
                  ↓
   ③ 切换指针     │  改 bootloader 环境变量 / boot 计数
                  ↓
   ④ 重启         │
                  ↓
   ⑤ 新系统起来   │  → 用户态"确认"（标记成功）
                  │     ├─ 确认 → 常驻 A/B 角色互换
                  │     └─ 未确认（超时/崩溃）→ 下次重启自动回退

⭐ 第 ⑤ 步的"确认"是整套机制里最容易被忽略的一步。 没有它，系统"能启动但服务全挂"的情况不会被检测 —— 而这是最常见的升级失败形态。

切换指针：三种实现

方式 机制 适合
bootloader 环境变量 U-Boot boot_part=2，用户态 fw_setenv 改 有 U-Boot 的板子
boot 计数 bootcount + altbootcmd：连续失败 N 次自动切 ⭐ 最可靠，不依赖用户态
GPT 分区属性 改分区的 priority/successful 标志 无 U-Boot（如 Pi 的固件启动）

U-Boot 的 bootcount（推荐）

# 环境变量
bootcount=0
bootlimit=3
altbootcmd=run altboot        # 失败后的备用启动命令

# 逻辑
#   每次启动：bootcount++
#   成功启动后：用户态执行 fw_setenv bootcount 0
#   bootcount >= bootlimit → 执行 altbootcmd（切到另一个分区）

⭐ 为什么它最可靠：失败检测完全在 bootloader 里，不依赖新系统能不能跑起来。新系统连用户态都进不去时，bootcount 照样累加，照样回退。

校验：签名不是可选项

# 生成签名（构建机）
openssl dgst -sha256 -sign private.pem -out image.sig image.squashfs

# 设备上验证（升级前）
openssl dgst -sha256 -verify public.pem -signature image.sig image.squashfs
威胁 不签名的后果
传输损坏 装上一个坏系统（sha256 能挡）
恶意固件 攻击者刷入后门系统（只有签名能挡）
版本降级 刷回有漏洞的旧版本攻击（需要版本号防回滚）

⭐ 完整的升级包至少要包含三样东西：镜像本体 + 签名 + 单调递增的版本号。防回滚（anti-rollback）常被漏掉，但它和签名同等重要。

用什么框架（不要自己造轮子）

框架 特点 适合
RAUC 成熟、支持 U-Boot/GRUB/GPT、有 D-Bus API、签名与防回滚齐全 ⭐ 首选
SWUpdate 灵活、支持多种 handler、可定制 UI 复杂场景
Mender 带服务端，可管理设备群 有 OTA 管理平台需求
手写脚本 几十行 shell + fw_setenv 学习/理解原理

⚠️ 自己写的第一版几乎必然漏掉：原子性（写一半掉电）、签名、防回滚、确认机制、bootcount。至少先读一遍 RAUC 的设计文档再决定要不要自己写。

最小手写实现（理解用）

#!/bin/sh
# 极简 A/B：当前在 A，写到 B
set -e

CUR=$(fw_printenv -n boot_part)          # 1 或 2
[ "$CUR" = "1" ] && TGT=2 || TGT=1

DEV="/dev/mmcblk0p$TGT"

# ① 写（这一步失败无所谓，反正没切换）
openssl dgst -sha256 -verify /etc/ota/pub.pem \
        -signature /data/ota/image.sig /data/ota/image.img || exit 1

dd if=/data/ota/image.img of=$DEV bs=4M conv=fsync
sync

# ② 切换（原子：只改一个环境变量）
fw_setenv boot_part $TGT
fw_setenv bootcount 0
fw_setenv upgrade_pending 1              # 等用户态确认

# ③ 重启
reboot

启动后由服务确认：

# 健康检查通过
fw_setenv upgrade_pending 0

而 U-Boot 侧：

if test "${upgrade_pending}" = "1" && test "${bootcount}" -ge 3; then
    # 没确认 + 失败 3 次 → 回退
    fw_setenv boot_part <上一个>
fi

测试升级方案必须测的四件事

场景 怎么模拟 期望
传输中断 写到一半 kill -9 系统仍从原分区启动
镜像损坏 改坏一个字节再装 签名验证失败，拒绝安装
新系统起不来 装一个坏的内核 bootcount 到阈值后自动回退
新系统能起但功能坏 装一个能启动但服务崩的版本 确认超时 → 回退

⭐ 第四个场景是最容易被漏测的，而它恰恰是现实中最常见的失败形态。

HFT / 嵌入式关联

  • A/B + 快速回退 就是灰度发布：新版本出问题要能在一次心跳内回退，而不是现场重刷。交易系统的灰度同样是"新旧并存、可快速切回"，而不是"停机升级、失败重装"。
  • "永远不要覆盖正在运行的那个" —— 这条在 HFT 部署里是铁律：新二进制部署到新目录/新容器，切换只改一个符号链接或负载均衡指向。覆盖式部署（cp 到原路径）会导致"部分更新"的中间态，在高频场景下就是灾难。
  • bootcount 的"失败检测放在观察者里"设计值得借鉴：HFT 的健康检查也应该独立于被检查的对象（外部心跳、独立监控进程），而不是让进程自己报告"我很健康" —— 进程崩了就没法报告了。
  • 防回滚（版本号单调） 在金融系统里对应审计与合规：不能悄悄退回有问题的旧版本，每一次变更都要可追溯。
Q1：为什么不能"直接覆盖当前系统"？

因为覆盖过程有中间态：写了一半的系统既不是旧的也不是新的。这时掉电或者崩溃，设备就砖了。

A/B 的本质是：写操作发生在一个"没人用"的分区上，写坏了也不影响当前运行。切换是最后一步，而且切换本身必须是原子的（改一个环境变量 / 一个 GPT 标志位 / 一次原子 rename）。

这就是"用原子操作提交非原子变更"的通用模式 —— 数据库 WAL、overlayfs 的 workdir、配置热更新用的都是同一招。

Q2：bootcount 和用户态确认，有两个不就够了吗？

不够，它们检测的是不同层面的失败：

机制 能检测 不能检测
bootcount 系统起不来（内核 panic、挂不上根） 系统起来了但服务崩了
用户态确认 系统起来了但功能不正常 系统根本起不来（没人去确认）

现实中最常见的是"能启动但服务挂了" —— 内核好好的，但你的应用因为配置不兼容起不来。bootcount 永远不会累加（系统"成功"启动了），只有用户态健康检查 + 确认超时能抓住它。

两者都要有。

Q3：防回滚（anti-rollback）为什么重要？

假设 v1.0 有个已修复的漏洞，你升级到 v2.0 修好了。攻击者拿到设备后，刷回 v1.0 就能重新利用那个漏洞。

没有版本号检查的话，A/B 机制恰好给了攻击者这个能力 —— 它本来就是为了"能回退到旧分区"设计的。

解法：把当前已接受的最低版本号写进一次性可编程区域（OTP / eFuse）或受保护的环境变量，升级时检查 new_version >= min_version。

⭐ 这体现了安全的一般原则：任何回退机制本身都是一个攻击面。
