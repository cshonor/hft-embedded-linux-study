导读

本节讲什么： 建立 aarch64 交叉工具链，理解 target triple / sysroot / ABI 三件事，并能在 x86 主机上产出板子能跑的二进制。 对应动手： P5 · D1（交叉编译 C/C++ 部署到板）

要点

概念 说明
为什么必须交叉 目标板算力弱、存储小、无开发环境；且编译器本身要跑在宿主机
target triple aarch64-linux-gnu = 架构(aarch64) - 厂商(none) - OS(linux) - ABI(gnu)
sysroot 目标板的"根文件系统副本"——头文件和库从这里找，而不是宿主机的 /usr/include。弄错 sysroot 是最常见的隐性错误
ABI 匹配 浮点调用约定（hard-float）、sizeof(long)、结构体对齐必须与目标内核一致，否则能跑但结果错
验证 file 看 ELF 架构 + readelf -h 看 Machine，比"能编译过"更可靠

关键命令

# 装工具链（Ubuntu/WSL）
sudo apt install gcc-aarch64-linux-gnu g++-aarch64-linux-gnu

# 编译 + 检查产物
aarch64-linux-gnu-gcc -O2 -o hello hello.c
file hello                      # ELF 64-bit LSB executable, ARM aarch64
aarch64-linux-gnu-readelf -h hello | grep Machine

# 看它到底链了哪些库
aarch64-linux-gnu-readelf -d hello | grep NEEDED

坑： 用 gcc 编出 x86 二进制再 scp 到板子上跑，会报 Exec format error——这不是权限问题。

HFT / 嵌入式关联

  • 生产环境虽然同为 x86，但交叉/远程构建的思路一致：构建机与运行机分离，产物必须可复现（-frecord-gcc-switches、固定 sysroot）。
  • sysroot 的概念直接对应后面 05-rootfs 里的"根文件系统必须先于应用存在"。

2.1

为什么要交叉编译：build / host / target 与三元组

本节讲什么： 搞清交叉编译的四个坐标（build / host / target / sysroot），理解「为什么不能在板子上编译」，以及坐标搞混时会产生哪一类编译期不报、运行期才炸的错误。 前置： 01-orientation · 1.4 Pi 就是一块 SoC 动手： P5 · D1 卡住查书： MELP Ch2 · Primer Ch12

一句话定义

native 编译：编译器跑在 A 机，产出的程序也跑在 A 机
cross  编译：编译器跑在 A 机，产出的程序跑在 B 机

只有「编译器跑在哪」和「产出跑在哪」这两件事不同，才叫交叉。 跟源码语言、跟你在哪敲命令都无关。

三个名字必须分清（GNU 的坑）

配置 gcc 时会看到 --build= / --host= / --target=，这三个词的含义对「普通程序」和「编译器」是反的：

名字 含义 本例
build 编译这个软件包的机器 x86_64 笔记本
host 这个软件包将来运行的机器 gcc 自己 → x86_64；你的 hello → aarch64
target 这个软件包的产出物运行的机器 只有编译器才有，= aarch64

规则：

  • 编普通程序：--build=x86_64 --host=aarch64（没有 target）
  • 编交叉编译器：--build=x86_64 --host=x86_64 --target=aarch64 —— 编译器自己跑在 x86，产出跑在 aarch64

⭐ 记忆法：target 只有"造工具的工具"才有。你写一个 hello.c，它不会产出代码，所以没有 target。

为什么嵌入式非交叉不可

理由 说明
算力 Pi 5 四核 vs 主机 8~16 核；完整编一次内核在板子上是小时级，主机上是十分钟级
存储 内核源码 + 构建产物 20~40 GB，SD 卡/eMMC 放不下，而且大量读写会提前耗尽寿命
自举问题 新板子上还没有可运行的系统 —— 你拿什么编出第一个系统？先有鸡
可复现 构建机固定、依赖固定，产物才能复现；在板子上编，每台板子环境都不一样

⚠️ 但交叉不是免费的，最大的代价是 autotools 类软件（./configure）：

configure 的很多检查靠"编一个小程序，跑一下，看它返回什么"来判断特性
→ 交叉环境下这个小程序跑不了（是 aarch64 的）
→ 只能靠 --host= 声明 + 手写 config.cache 告诉它答案

这是移植第三方开源包最烦的一步，心里要有准备。

target triple 拆解

aarch64-linux-gnu 的标准切分是 arch - vendor - os - abi：

 aarch64   -  linux  -  gnu
   ↑           ↑        ↑
  架构       OS/内核   ABI（这里指 C 库：gnu = glibc）
（vendor 常省略，或写 none / unknown）
triple 用在哪 关键差异
aarch64-linux-gnu 64 位 ARM + Linux + glibc Pi 5 用这个
arm-linux-gnueabihf 32 位 ARM + 硬浮点 + glibc Pi 2/3 用这个
arm-none-eabi 裸机（无 OS），newlib STM32；不能调 open()，没有 OS 可陷
aarch64-linux-musl musl libc，静态链接友好 容器/极简 rootfs
x86_64-linux-gnu 本机 对照组

⭐ arm-none-eabi 与 arm-linux-gnueabihf 的差别不在架构（都是 ARM 32 位），而在有没有 OS、用哪个 C 库。前者编出来的 printf 走 newlib 的桩函数，需要你自己实现 _write() 才能输出。

一套工具链里到底有什么

交叉工具链不是只有 gcc，是一整组都带前缀的 binutils：

命令 作用 用在哪
aarch64-linux-gnu-gcc / -g++ 编译（也兼驱动链接） 天天用
aarch64-linux-gnu-ld 链接（一般由 gcc 间接调用） 手写链接脚本时
aarch64-linux-gnu-as 汇编 启动代码
aarch64-linux-gnu-objdump 反汇编（验证内联、看指令） 调优/查 bug
aarch64-linux-gnu-readelf 看 ELF 头、段、NEEDED 验证产物
aarch64-linux-gnu-nm 看符号表（有没有 t kept） 查符号冲突
aarch64-linux-gnu-strip 去掉符号，缩小体积 出镜像
aarch64-linux-gnu-gdb 远程调试（配合板上的 gdbserver） 调试

⚠️ 不要混用宿主和目标的 binutils。 宿主的 objdump 未必编译了 aarch64 的 BFD 后端，会报 File format not recognized。所有命令都带前缀是最省心的习惯。

工具链从哪来（四种途径怎么选）

途径 适合 代价
发行版包（apt install gcc-aarch64-linux-gnu） 学习、快速起步 版本跟随发行版，够用
Linaro / ARM 官方预编译 需要特定 gcc 版本 下载即可用
crosstool-NG 需要精确控制 gcc/glibc/binutils 版本 从源码编工具链，几小时
Buildroot / Yocto 生成 ⭐ 与 rootfs 同源 跟着 rootfs 一起出

⭐ 最该记住的一条：工具链的 glibc 版本必须 ≤ 目标 rootfs 的 glibc 版本。

反过来的话：编译时一切正常，scp 到板子上运行时报 ./hello: /lib/aarch64-linux-gnu/libc.so.6: version 'GLIBC_2.38' not found —— 编译期零报错，运行期才炸。这类"验证环境与运行环境不一致"的错误，是交叉编译里最贵的一类。 用 Buildroot 生成工具链就是为了从根上消除它（工具链和 rootfs 用同一份源码编出来）。

错误对照表（对号入座）

现象 真实原因 修法
板子上 Exec format error 用宿主 gcc 编出了 x86 二进制 换带前缀的 gcc；file 确认
cannot find -lc / crt1.o: No such file sysroot 没设，或没装目标 libc 开发包 --sysroot=...；或装 libc6-dev-arm64-cross
运行报 GLIBC_2.xx not found 工具链 glibc 比目标新 换工具链 / 静态链接 / 升 rootfs
Illegal instruction -march/-mcpu 用了目标 CPU 没有的指令 查 /proc/cpuinfo 后改 -march
能链接能启动，但结果算错 ABI 不匹配（软硬浮点混用、结构体对齐不同） 统一 -mfloat-abi=hard
编译慢得离谱 没开并行 make -j$(nproc)

HFT / 嵌入式关联

  • 生产交易系统虽然是 x86 native，「构建机与运行机分离 + 产物可复现」的思路完全同构：把 gcc -v、sysroot 内容哈希、链接的所有库版本打进产物元信息，出问题时能精确定位"是哪个二进制"。
  • 「编译期不报、运行期才炸」在 HFT 里的同构失败模式是 回测通过、实盘炸：回测环境的 tick 对齐、时钟源、撮合假设都跟实盘不同。解法也一样——让验证环境逼近运行环境，而不是反过来放宽检查。
  • -frecord-gcc-switches 会把完整编译选项写进 ELF 的 .GCC.command.line 段，出线上问题时可以 readelf -p .GCC.command.line <bin> 反查它是怎么编出来的。这个习惯值得从第一天就养成。
Q1：--host 和 --target 到底哪个是"程序跑在哪"？

取决于你在编什么。

  • 编普通程序：--host = 程序跑在哪。--target 不存在。
  • 编编译器：--host = 编译器自己跑在哪（一般 = --build），--target = 编译器产出的程序跑在哪。

判据很简单：这个软件的"输出"是什么？ 如果输出是可执行文件，那它有 target；如果输出只是"干了一件事"，它没有。

Q2：为什么 arm-none-eabi 编出来的 printf 不输出？

因为它连的是 newlib，没有 OS 可以陷进去。printf 最终会调到 newlib 的一个弱符号桩 _write()，裸机上这个函数默认是空实现（或返回错误），所以什么也不打印。

你要么自己实现 _write() 把字节写进 UART（这就是嵌入式里常说的 retarget / syscall 重定向），要么换个带 OS 的 triple。

对比：arm-linux-gnueabihf 的 printf 最终走到 write() syscall → svc #0 陷入 Linux 内核 → 内核写 tty。"有没有 OS" 是这两个 triple 的根本分界。

Q3：工具链 glibc 比目标 rootfs 新，为什么编译期能过？

因为链接器只检查符号是否存在，不检查版本。编译时链接的是你工具链 sysroot 里的 libc.so.6，符号都在，链接通过。

但 ELF 里会记录一个版本需求（.gnu.version_r 段里的 GLIBC_2.38）。运行时动态链接器 ld.so 会拿它跟板子上实际的 libc 比对，缺失就直接报错退出。

这就是"静态检查覆盖不到的运行时契约" —— 用 readelf -V hello | grep GLIBC 可以提前看到这个需求，交叉编译后建议例行查一次。

Q4：在 x86 主机上用 aarch64-linux-gnu-gcc 编出的程序，能直接在本机跑吗（假如装了 qemu-user）？

能，但要显式：qemu-aarch64-static -L <sysroot> ./hello（-L 指定解释器根，否则找不到 ld.so 和 libc）。

这是低成本验证交叉产物的好办法：不用真的 scp 到板子上，就能确认"至少能启动、能跑完主流程"。注意它验证不了硬件相关行为（GPIO、DMA、时序），只验证 CPU 指令与 libc 语义。

2.2

sysroot 与 C 库：交叉编译里最容易搞错的一件事

本节讲什么： sysroot 是什么、为什么它是「目标板的根文件系统副本」，以及 glibc / musl / 静态链接怎么选。 前置： 2.1 为什么交叉 动手： P5 · D1 卡住查书： MELP Ch2 · Primer Ch13

一句话

sysroot = 目标系统根目录的一份拷贝。 编译器找头文件和库时，不是去宿主机的 /usr/include、/usr/lib，而是去 <sysroot>/usr/include、<sysroot>/usr/lib。

宿主机                                    sysroot（目标板的 /）
/usr/include/stdio.h   ← 不找这里        <sysroot>/usr/include/stdio.h  ← 找这个
/usr/lib/libc.so.6     ← 不找这里        <sysroot>/usr/lib/libc.so.6    ← 找这个

不设 sysroot 会怎样？ 交叉 gcc 一般不会去吃宿主机的 x86 头文件（binutils 编好了不会），它会报 cannot find -lc / stdio.h: No such file —— 这是好消息，因为它报错了。真正危险的是设错 sysroot（指向了错误版本的目标根），那才是编译通过、运行崩溃。

搜索路径是怎么算出来的

# 看编译器到底去哪些目录找头文件
aarch64-linux-gnu-gcc -print-sysroot                    # 默认 sysroot（可能为空）
aarch64-linux-gnu-gcc --sysroot=/opt/pi-rootfs -E -v -  < /dev/null 2>&1 | sed -n '/#include <...>/,/End of search/p'

# 看它链接时搜哪些库目录
aarch64-linux-gnu-gcc --sysroot=/opt/pi-rootfs -print-search-dirs | tr ':' '\n' | head -20

--sysroot=DIR 的效果等价于：把 /usr/include、/lib 这些绝对路径都重定向到 DIR/usr/include、DIR/lib。

⭐ 一个附带好处：-I 和 -L 也可以写成绝对路径，但一旦用了 --sysroot，那些绝对路径也会被重定向 —— 这在移植第三方包时经常造成"我明明指定了路径却找不到"的困惑，记得先 -print-sysroot。

三种 C 库怎么选

glibc musl 静态链接（任一）
体积 大（几 MB） 小（几百 KB） 最大（每份二进制各带一份）
兼容性 最好，闭源模块/NSS 都行 部分软件不支持（尤其 NSS、部分 locale） 无运行时依赖
启动速度 一般 略快（无 NSS 动态加载） 最快（无 ld.so 符号解析）
适合 通用 Linux、Pi OS 极简 rootfs、容器 单二进制工具、initramfs 里的急救程序

嵌入式 bring-up 阶段的实用选择：

  • 学习主线 → glibc（跟发行版一致，遇到问题资料最多）
  • 做极小 rootfs → musl（Buildroot 里一个配置项的事）
  • initramfs 里的 /init、急救 shell → 静态 busybox（rootfs 还没挂起来时，动态库根本不存在）

静态 vs 动态：怎么判断自己该用哪个

# 静态
aarch64-linux-gnu-gcc -O2 -static -o hello_s hello.c
file hello_s          # statically linked, ... not stripped

# 动态（默认）
aarch64-linux-gnu-gcc -O2 -o hello_d hello.c
aarch64-linux-gnu-readelf -d hello_d | grep NEEDED   # → libc.so.6
aarch64-linux-gnu-readelf -d hello_s | grep NEEDED   # → 无输出（不依赖任何 .so）
场景 选 理由
initramfs 里的程序 静态 真正的根还没挂，动态库找不到
应用（rootfs 已就绪） 动态 省空间，多个程序共享一份 libc 页框
只有一个程序的产品 静态 整个 rootfs 就是它自己
大量 fork/exec 的系统 动态 共享库页框能显著降低内存与页缓存压力

⚠️ -static 不是万能的：glibc 的 getaddrinfo()、getpwnam() 这类走 NSS（动态加载 libnss_*.so）的函数，静态链接时会告警 warning: Using 'getaddrinfo' in statically linked applications requires at runtime the shared libraries from the glibc version used for linking。这不是可忽略的警告 —— 目标板上 glibc 版本不同就会失败。要静态就用 musl，不要静态 glibc。

内核头文件 vs libc 头文件（两回事）

<sysroot>/usr/include/linux/*.h     ← 内核 UAPI 头文件：给内核和用户程序看的 ABI 契约
<sysroot>/usr/include/sys/*.h       ← glibc 头文件：C 库接口

规则：写用户态程序不要 include 内核源码树里的头文件，要用发行版/工具链提供的、已 sanitize 过的 UAPI 头（make headers_install 产出的那套）。混用会导致结构体定义冲突（struct stat、struct sigset_t 都是重灾区）。

内核模块编译则是另一回事 —— 它需要内核源码树里 include/ 下的内部头（不是 UAPI），而且必须与运行内核同一版本（见 4.3 vermagic）。

实操：用 Buildroot 拿一份"同源"工具链

git clone https://github.com/buildroot/buildroot && cd buildroot
make raspberrypi5_defconfig
make menuconfig          # Toolchain → 选 glibc/musl、gcc 版本、是否开启 C++
make sdk                 # 产出工具链 SDK（一个自解压包）

ls output/images/*sdk-buildroot*.tar.gz
tar -xzf output/images/*sdk-buildroot*.tar.gz -C /opt
/opt/*/bin/*-gcc --version

⭐ 这条路的唯一理由：工具链的 glibc 和 rootfs 的 glibc 是同一次构建产出的，从根上消灭 GLIBC_2.xx not found。代价是要先会一点点 Buildroot（见 05-rootfs）。

HFT / 嵌入式关联

  • sysroot 就是"环境 pin"的实体形态。HFT 生产机上同样需要一个"这台机器到底装了什么"的确定答案 —— 区别在于 HFT 用容器/镜像固化，嵌入式用 sysroot 固化，本质是同一件事：把依赖从"主机状态"变成"显式声明的产物"。
  • 静态链接省掉 ld.so 的动态符号解析对启动延迟敏感的场景是有意义的：进程启动时 ld.so 要做符号重定位（尤其 C++ 大量模板符号），这是几十到几百微秒的纯开销。交易进程通常用静态链接 + 预链接或直接避免频繁 exec。
  • 「编译期不报、运行期才炸」的成本在交易系统里是按秒计费的停机。所以交叉编译养成的习惯（查 NEEDED、查 GLIBC_x.yy 需求、记录编译选项）直接可以平移到生产发布检查清单里。
Q1：不设 --sysroot 时，交叉 gcc 会去哪找头文件？

取决于发行版怎么打包它。Debian/Ubuntu 的 gcc-aarch64-linux-gnu 通常是把目标头文件装到 /usr/aarch64-linux-gnu/ 下，binutils 内部就认这个前缀（等价于内置了一个 sysroot）。

所以你会看到"没设 sysroot 也能编过"—— 那是因为工具链自带了一个默认 sysroot，它里面有一份目标 libc（通常由 libc6-dev-arm64-cross 包提供）。

⚠️ 危险在于：这份默认 sysroot 的 glibc 版本，未必等于你目标板 rootfs 的 glibc 版本。所以它只是"能编过"，不代表"能在板子上跑"。

Q2：为什么静态链接 glibc 时 getaddrinfo() 会告警？

因为它走 NSS（Name Service Switch），运行时会 dlopen("libnss_files.so.2") 之类的模块。dlopen 在静态二进制里不可用，所以要么功能失效，要么强依赖"板子上的 glibc 版本恰好和编译时一样"。

glibc 官方文档明确说：静态链接的 glibc 程序，用到 NSS/iconv/locale 的功能是 unsupported。

→ 结论：要静态就用 musl（它把 NSS 简化掉了），别跟 glibc 的静态链接较劲。

Q3：内核模块编译为什么不能用 sysroot 里的头文件？

因为模块是内核的一部分，它要用的不是"用户态看到的 ABI 契约"（UAPI 头），而是内核内部数据结构（struct task_struct、struct file_operations 的完整定义）。

这些东西： 1. 不在 UAPI 头里（include/uapi/ 只是对外契约，内部头在 include/linux/）； 2. 逐版本变化，必须和目标运行内核逐字节同源。

所以模块编译走的是 make -C /lib/modules/$(uname -r)/build M=$PWD，指向内核源码树而不是 sysroot。这也是 4.3 vermagic 要解决的"版本魔法"问题的根源。

2.3

产物验证与踩坑清单：交叉编译的三道检查

本节讲什么： 编译"成功"不等于产物正确。这一节给出交叉编译后必做的三道检查，以及一份可复用的踩坑清单。 前置： 2.2 sysroot 与 C 库 动手： P5 · D1 卡住查书： MELP Ch2 · Primer Ch12

为什么"能编译过"不算证据

交叉编译的失败分三层，越往后越贵：

层次 什么时候暴露 典型表现 检测成本
1. 编译/链接失败 立刻 cannot find -lc 几乎为零
2. ELF 层面不对 拷到板子那一刻 Exec format error、GLIBC_2.38 not found 一条命令
3. ABI / 语义层面对 跑起来之后 算错、Illegal instruction、偶发段错误 最贵，可能潜伏数周

第 2 层是完全可以用一条命令提前消灭的，成本近乎为零却不做的代价是整个 bring-up 流程被打断。这一节就是把第 2 层变成肌肉记忆。

第一道检查：架构对不对（5 秒）

# ① file 看三件事：位数、字节序、架构
$ file hello
hello: ELF 64-bit LSB executable, ARM aarch64, version 1 (SYSV), dynamically linked,
       interpreter /lib/ld-linux-aarch64.so.1, ...

# ② readelf 看机器类型（比 file 更权威，不受 file 数据库版本影响）
$ aarch64-linux-gnu-readelf -h hello | grep -E 'Machine|Class|Data'
  Class:                             ELF64
  Data:                              2's complement, little endian
  Machine:                           AArch64
你要看到的 如果看到这个 → 说明
Machine: AArch64 ✅ 目标架构正确
Machine: Advanced Micro Devices X86-64 ❌ 用了宿主 gcc，scp 上去必 Exec format error
Machine: ARM ⚠️ 编成了 32 位（arm-linux-gnueabihf- 混进来了）

⭐ 把这条做成 Makefile 的强制步骤：

check-arch: $(BIN)
    @if $(READELF) -h $(BIN) | grep -q 'AArch64'; then \
        echo "OK: aarch64"; else echo "FAIL: wrong arch"; exit 1; fi

第二道检查：依赖哪些库、要求哪个版本（10 秒）

# ① NEEDED：运行时必须存在哪些 .so
$ aarch64-linux-gnu-readelf -d hello | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]

# ② 版本需求：要求 libc 至少是哪个版本  ★ 最容易漏的一步
$ aarch64-linux-gnu-readelf -V hello | grep -o 'GLIBC_[0-9.]*' | sort -Vu
GLIBC_2.34

然后去板子上核对：

# 在 Pi 5 上
$ ldd --version | head -1          # 看板子上的 glibc 版本
$ ls /lib/aarch64-linux-gnu/libc.so.6

规则：readelf -V 出来的最高版本 ≤ 板子 glibc 版本 才安全。

补充：NEEDED 里的 libc.so.6 只是一个 soname，不是文件名。真正加载时找的是 /lib/aarch64-linux-gnu/libc.so.6（通过 ld.so.cache 或 ldd 能看到解析结果）。

第三道检查：能不能真的跑（1 分钟）

不用板子的办法（快）：qemu-user

# 宿主机上（需要 qemu-user-static）
qemu-aarch64-static -L <sysroot> ./hello
# -L 指定"解释器根"，否则找不到 ld-linux-aarch64.so.1 和 libc

有板子的办法（准）：scp 上去跑

scp hello wzp@pi5:/tmp/ && ssh wzp@pi5 /tmp/hello
qemu-user 真机
速度 快，不用折腾硬件 慢，要网络/串口
能验证 CPU 指令、libc 语义、程序逻辑 全部
不能验证 GPIO/DMA/中断/时序/时钟源、性能 —

⭐ 推荐流程：qemu 先过一遍逻辑，真机只跑最后那一次。 bring-up 阶段来回 scp 是最耗时间的环节。

可复用踩坑清单

坑 1：混合使用宿主与目标的 binutils

gcc 编的          → aarch64
objdump 用的宿主  → 可能没有 aarch64 后端

症状：objdump: hello: File format not recognized 解法：所有命令带 aarch64-linux-gnu- 前缀。

坑 2：Makefile 里硬编码了 gcc

很多开源包的 Makefile 写死 CC = gcc。交叉时要么覆盖：

make CROSS_COMPILE=aarch64-linux-gnu-         # 内核和一些规范的包支持
make CC=aarch64-linux-gnu-gcc                 # 通用
make CC="aarch64-linux-gnu-gcc --sysroot=/opt/pi-rootfs"

要么（autotools）：

./configure --host=aarch64-linux-gnu --prefix=/usr
make DESTDIR=/opt/pi-rootfs install            # DESTDIR = 装到哪；prefix = 运行时在哪

⭐ DESTDIR 和 --prefix 的区别必须分清：prefix 是运行时路径（会被写进二进制），DESTDIR 是安装时的临时根（不写进二进制）。交叉安装时永远是 make DESTDIR=<staging> install。

坑 3：-march / -mcpu 用错

# Pi 5 是 Cortex-A76，支持 armv8.2-a
aarch64-linux-gnu-gcc -O2 -march=armv8.2-a -o x x.c

用太新的 -march → 目标 CPU 上没有这条指令 → Illegal instruction（而且是跑到那一行才崩，不是启动就崩，很难定位）。 保守做法：不指定 -march，用工具链默认值（一般为基线 armv8-a，兼容性最好）。

坑 4：浮点 ABI 混用（32 位 ARM 特有）

-mfloat-abi=soft / softfp / hard 三者不能混着链接，否则能链接但运行结果错（参数通过不同寄存器传）。 aarch64 没有这个问题（只有硬浮点一种），这也是 64 位省心的地方之一。

坑 5：编译选项没记录

# 让 ELF 自己记住它是怎么编出来的
aarch64-linux-gnu-gcc -O2 -frecord-gcc-switches -o hello hello.c

# 半年后反查
aarch64-linux-gnu-readelf -p .GCC.command.line hello

HFT / 嵌入式关联

  • 三道检查 = 发布流水线里的"门禁"。HFT 的发布流程同样应该有三道：静态（编译/单测）→ 契约（ABI/配置/依赖版本核对）→ 影子盘（真跑一次）。没有第二道门禁是很多线上事故的根源 —— 编译通过就直接上，等于把 ABI 问题留给实盘去发现。
  • qemu 先跑、真机后跑 对应 HFT 的「回测 → 仿真 → 影子 → 实盘」四级：越便宜的环境越早用，把错误挡在贵的环境外面。
  • -frecord-gcc-switches 的思路可以直接平移：让产物自带 provenance（来源证据）。交易二进制出问题时，第一个要回答的就是"这个二进制是哪次构建、用什么选项编出来的"。
Q1：file 已经说了 aarch64，为什么还要 readelf -h？

file 靠 magic 数据库猜测，数据库版本不同、或遇到非标准 ELF（比如某些 RTOS 的）可能判错；readelf 是直接解析 ELF 头里的 e_machine 字段，是权威值。

另外 readelf 能同时看到 Class（32/64 位） 和 Data（字节序），这两项错了也会导致运行失败，而 file 输出太长容易看漏。

Q2：NEEDED 里的 libc.so.6 和 readelf -V 里的 GLIBC_2.34 是什么关系？

两回事：

  • NEEDED 是 soname（库的名字），ld.so 拿它去找文件；
  • GLIBC_2.34 是 符号版本需求，来自 ELF 的 .gnu.version_r 段，意思是"我引用的某些符号是从 glibc 2.34 才开始有的"。

只有 soname 存在还不够，版本需求也必须被满足，否则 ld.so 报 version 'GLIBC_2.xx' not found。这就是为什么"板子上明明有 libc.so.6 却跑不起来"。

Q3：DESTDIR 与 --prefix 弄混会造成什么后果？
  • 只用 --prefix=/opt/pi-rootfs/usr 安装：路径被写进二进制（比如程序内部去 /opt/pi-rootfs/usr/share/... 找数据），拷到板子上路径不存在 → 运行失败，且很难查。
  • 正确做法：--prefix=/usr（运行时路径）+ make DESTDIR=/opt/pi-rootfs install（装到 staging 目录）。

这样二进制里记的是 /usr/share/...，实际文件被放到 /opt/pi-rootfs/usr/share/...，等这个 staging 目录变成板子上的 / 时，两者就对上了。

2.4

宿主机是 Mac（Apple Silicon）：三种构建路径怎么选

本节讲什么： 你手边最快的机器是 M 系列 Mac，它跑 macOS；目标是 Linux/aarch64。 这一节回答「什么东西该在哪台机器上编」，给出每条路径的确切命令，以及各路径里唯一会让你白干一天的那个坑。 前置： 2.1 三元组 · 2.2 sysroot 与 C 库 · 2.3 三道检查 动手： P5 · Phase B 卡住查书： MELP Ch2 · Primer Ch12

先看结论：按产物选机器，不按"哪台快"

要编的东西 在哪编 为什么是它
用户态 C 程序 / 库 Mac 上的 arm64 Linux 容器 原生速度（不模拟）+ ABI 天然一致
内核模块 / 驱动 ★ Pi 上本地编译 必须与运行中的内核同源，交叉编零收益、纯受罪
完整内核 / U-Boot / DTB arm64 Linux 容器（或 Pi 本地，慢） macOS 原生编有两个硬伤，见路径 B
整包 rootfs Buildroot，跑在容器里 见 05-rootfs

⚠️ 最后一行"整包 rootfs"里的 Buildroot 也别在 macOS 原生跑（同样的大小写问题）。

为什么 Mac 原生编的不能直接丢给 Pi：三重不匹配

常见说法是"架构一样，只是 libc 不同"，这个说法只对了一小部分。真实隔阂有三层：

层 macOS（Apple clang） Linux/aarch64
二进制格式 Mach-O ELF
系统调用接口 Darwin syscall（Mach 陷阱） Linux svc #0 + x8 存调用号
C 库 / ABI libSystem（dyld） glibc / musl（ld.so）

第三层还有个细节：Darwin 的 arm64 调用约定把 x18 保留给平台（AAPCS64 里它是临时寄存器）。 所以严格说连 ABI 都不是同一套，只是绝大多数 C 代码碰不到这个差别。

于是"架构相同"真正带来的好处只有一个，但很值钱：

Apple Silicon 上 Docker Desktop 起的 Linux VM 本身就是 aarch64。 跑 arm64 镜像时不需要 QEMU 翻译，是原生速度。 这是 Mac 相对 x86 宿主机的巨大优势——x86 机器上同样的容器要全指令模拟，慢 3–4 倍。

别把"架构相同"理解成"可以不用交叉"。 你仍然需要一套 Linux 目标环境，只是这次它可以跑得飞快。

路径 A：Mac 上跑 arm64 Linux 容器（推荐）

一键命令

# 宿主机（macOS）
docker run -it --rm --platform linux/arm64 \
  -v "$PWD:/work" -w /work \
  debian:trixie bash

# ---- 容器内 ----
apt update && apt install -y build-essential file

gcc -o hello hello.c
file hello
# hello: ELF 64-bit LSB executable, ARM aarch64, dynamically linked ...

⭐ 一个常见误解： 容器里不需要装 gcc-aarch64-linux-gnu。 那个包是"在 x86 机器上交叉编 arm64"用的；arm64 容器里的发行版 gcc 本身就是 aarch64 目标， 再装一个交叉编译器只会让你分不清自己到底在用哪个。

# 容器内确认一下，心里有底
gcc -dumpmachine      # → aarch64-linux-gnu

★ 唯一会让你白干一天的坑：容器其实是 x86_64

如果容器跑的是 amd64 镜像（在 QEMU / Rosetta 下模拟），里面的 gcc 就是 x86-64 编译器， 产出的 ELF 拷到 Pi 上直接 Exec format error——而编译过程一切正常，零警告。

怎么踩进去的：

  • 该镜像只有 amd64 版本，Docker 自动降级；
  • 或者你的 ~/.zshrc 里还留着 export DOCKER_DEFAULT_PLATFORM=linux/amd64 ——这是 M1 早期广为流传的"万能修复"，很多人的配置里至今还躺着，它会让你所有容器都跑模拟。

三重验证（每次开新容器花 10 秒）：

docker run --rm debian:trixie uname -m                       # 必须 aarch64
docker image inspect debian:trixie --format '{{.Architecture}}'   # 必须 arm64
file ./hello                                                 # 必须 ARM aarch64

启动时的告警就是信号，看见它立刻停手：

WARNING: The requested image's platform (linux/amd64) does not match
         the detected host platform (linux/arm64/v8)

体感判据：如果你没开 Rosetta、编译又莫名慢得离谱——你大概率在模拟。 这个信号比任何命令都快。

另外两条

  • 大工程别在 bind mount 里编。 -v 挂进去的目录走 virtiofs，跨文件系统 I/O 很慢。 编内核这类活，放容器内的命名卷，或者干脆去 Pi 上编。
  • 产物仍要走 2.3 的三道检查。 容器只是让第一道（架构）更容易对， 第二道（glibc 版本需求）照样可能翻车——容器里 debian:trixie 的 glibc 比你 Pi 上的新时，就会翻。

路径 B：macOS 原生交叉工具链（不装 Docker 时）

brew tap messense/macos-cross-toolchains
brew install aarch64-unknown-linux-gnu

aarch64-unknown-linux-gnu-gcc -o hello hello.c
file hello     # → ELF ... ARM aarch64

优点：不用起容器，编译速度快，编辑器/IDE 里直接就能用。 它是 crosstool-NG 编出来的完整 glibc 工具链，自带 sysroot， 不像 2.2 里说的"手工拼 sysroot"那么麻烦。

★ 版本核对（这是 2.1 那条铁律的实际用法）：

这套工具链的 glibc 是 2.28（tap 构建配方里写死的）。你的 Pi 5 跑 Debian 13（trixie），glibc 在 2.4x 量级：

# 在 Pi 上确认
ldd --version | head -1

2.28 ≤ 2.4x —— 满足"工具链 glibc ≤ 目标 glibc"，所以编出来的程序能跑。 反过来（目标比工具链老）才会踩 version 'GLIBC_2.xx' not found。 这就是为什么这一条一定要拿数字对，而不是"感觉差不多"。

适合：用户态程序、库、CI 构建。

⚠️ 不适合编内核，而且原因不是工具链不行

是 macOS 作为 host 有两个硬伤：

1. APFS 默认不区分大小写，而内核源码树里有仅大小写不同的文件。

典型的如 xt_connmark.h 与 xt_CONNMARK.h。在不区分大小写的卷上 clone， 这两个文件只剩一个——于是某处 #include 报"头文件找不到"， 而你在源码树里 ls 分明看见了它。这类报错能把人绕晕半天。

内核文档自己都为此打了补丁（Documentation/translations/zh_CN/how-to.rst），原话大意是：

macOS 默认使用不区分文件名大小写的 APFS 卷，而内核源码树中存在仅大小写不同的文件。

解法是建一个大小写敏感卷，在上面重新 clone：

diskutil apfs list                        # 找到容器标识符，如 disk3
diskutil apfs addVolume disk3 APFSX Linux # 新建大小写敏感卷
# 然后把内核源码 clone 到 /Volumes/Linux 下

2. Apple 自带的 make 是 3.81，内核要求 GNU make ≥ 4.0。

brew install make     # 装完叫 gmake，不叫 make
gmake ARCH=arm64 ...  # 必须敲 gmake

外加一堆 host 侧工具依赖（openssl 头、libelf 等）版本也和 Linux 发行版不一致。

结论：内核别在 macOS 原生编。 用容器，或者在 Pi 上本地编。 你在 macOS 上"省下"的时间，会加倍还给这两条。

★ 路径 C：内核模块 / 驱动就在 Pi 上编（这条最容易被搞反）

常见建议是"Pi 性能弱，编译慢，所以能交叉就交叉"。 对完整内核成立，对内核模块不成立。

原因是模块不是普通程序：它被链接进内核地址空间，必须和运行中的内核同源—— 同版本、同 .config、同编译器族。见 4.3 vermagic。

交叉编一个模块意味着：

  1. 把整棵已配置好的内核构建树（几 GB）搬到 Mac 上；
  2. 保证 Mac 上的编译器版本与编内核那台一致；
  3. 保证 .config 一字不差。

收益为零，风险很高。 而 Pi 5 上编一个模块就几秒：

# Raspberry Pi OS
sudo apt install raspberrypi-kernel-headers
# Debian 通用
sudo apt install linux-headers-$(uname -r)

# 驱动目录下
make -C /lib/modules/$(uname -r)/build M=$PWD modules
sudo insmod mydrv.ko

/lib/modules/$(uname -r)/build 就是 Pi 自己准备好的那棵树—— 用它编出来的模块不可能版本不匹配，这是最省心的做法。

Pi 5 的额外一点： 它的内核是 16K 页（CONFIG_ARM64_16K_PAGES=y）， 详见 3.4 Pi 5 启动链。 PAGE_SHIFT 变了，结构体布局跟着变—— 本地编自动带上这个配置；交叉编若用了 4K 的 config，编译照样过， insmod 时才报 invalid module format。

什么时候才需要交叉编模块：量产镜像构建（Buildroot/Yocto 出整包）。学习阶段不需要。

决策树

要编什么？
│
├─ 内核模块 / 驱动 ──────────► Pi 本地编
│                              KDIR=/lib/modules/$(uname -r)/build
│
├─ 用户态程序 / 库 ──────────► Mac 上 arm64 Linux 容器（首选）
│                              或 macOS 交叉工具链（无 Docker 时）
│
├─ 完整内核 / U-Boot / DTB ──► arm64 Linux 容器
│                              ⚠ 不要在 macOS 原生编（大小写 + gmake）
│                              或 Pi 本地（约 30–60 min，但零配置）
│
└─ 整包 rootfs ──────────────► Buildroot，跑在容器里（见 05-rootfs）

HFT / 嵌入式关联

构建环境本身必须是版本化的输入。 "在我机器上能跑"在交易系统里不是段子， 是 P&L 风险——二进制要连同它链接的库版本、目标内核版本一起被锁定和记录。 内核的 vermagic 是"版本即契约"最严格的体现，值得当成设计范本。

容器交叉编译的真正价值不是"快"，是把构建环境变成了可复现的声明 （Dockerfile + image digest），而不是"某台装了一堆东西的 Mac"。

但要看到容器的边界：它解决不了"产物必须匹配运行中的内核"这件事。 内核模块、eBPF 程序、需要精确匹配内核数据结构的观测工具，都得在目标机上编， 或至少用目标机的 kernel headers。CO-RE/BTF 本来是想解决这个问题的 ——可你的 Pi 5 内核是 DEBUG_INFO_NONE=y，没有 BTF，这条路也断了。 所以现阶段：模块就在 Pi 上编，别绕。

Q1：arm64 容器里还需要 gcc-aarch64-linux-gnu 吗？

不需要。那个包是给x86 宿主机交叉编 arm64 用的。

arm64 容器里的发行版 gcc 目标就是 aarch64，用 gcc -dumpmachine 可以确认 （输出 aarch64-linux-gnu）。再装一个交叉编译器只会多出一个名字相近的二进制， 让你在 Makefile 里分不清到底调用了哪个。

判据很简单：交叉编译器的定义是"build ≠ host 或 host ≠ target"。 arm64 容器里 host = target = aarch64，它不是交叉编译器。

Q2：既然容器是 arm64 且原生运行，为什么仍要跑 2.3 的三道检查？

因为三道检查查的是三件不同的事，容器只帮忙保证第一件：

  1. 架构 —— 容器是 arm64 时基本自动对（但仍要用 uname -m 确认没在模拟）；
  2. glibc 版本需求 —— 容器保证不了。debian:trixie 的 glibc 可能比你 Pi 上的新， 编出来的二进制会带上 GLIBC_2.4x 需求，拷到旧系统上就 version not found。 这一道最容易漏，也最该查（readelf -V 看 .gnu.version_r）；
  3. 能不能真跑 —— 只有执行才算数，能在宿主机用 qemu-aarch64 先跑一遍最好。

一句话：容器解决了"交叉"，没解决"与目标系统版本对齐"。

Q3：为什么说内核模块"交叉编零收益"？编完整内核不也一样要匹配吗？

不一样，关键差别在匹配已经由谁保证了。

编完整内核时，你就是那个定义版本的人——内核和模块一起编出来，天然一致， 所以"在 Mac 上交叉编内核"从技术上完全成立，只是 macOS 作为 host 有大小写和 gmake 两个硬伤。

编模块时，版本是运行中的那个内核定义的，uname -r 已经固定： - 在 Pi 上：/lib/modules/$(uname -r)/build 就是那棵树的精确副本， .config、编译器版本、Module.symvers 全自动对齐，不可能不匹配； - 交叉编：你得把这棵树搬到 Mac，再手动复现编译器版本和 config， 任何一处偏差都编译期无感、insmod 时才炸。

所以：编内核是"我来定义契约"，交叉可以；编模块是"我去满足别人定的契约"， 在契约方本地编最省事。这不是性能问题，是谁持有真相的问题。
