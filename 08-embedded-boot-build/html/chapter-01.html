导读

本节讲什么： 在动手之前先钉死几个容易混淆的概念——嵌入式 Linux 不是"小一号的桌面 Linux"，RTOS 不是"更快的 Linux"，SoC 不是"CPU + 主板"。 为什么要先定这个： 后面所有步骤（编内核、做 rootfs、写驱动）的选择，都取决于这块板子属于哪一类系统。定位错了，后面全是白工。 对应动手： P5 Phase A（把板子当 Linux 机器熟悉起来）

要点

概念 结论
Linux vs RTOS Linux 有 MMU、有用户/内核隔离、延迟是统计意义上的；RTOS 延迟是确定性的。要硬实时得打 PREEMPT_RT，且仍不是 RTOS
SoC vs CPU BCM2712 是 SoC：CPU 核 + 外设控制器 + 内存控制器全在一颗芯片上。没有"南北桥"，没有 PCIe 枚举那一套 PC 叙事
BSP 是什么 板级支持包只是模板，不是产品。拿到自研 PCB 时，BSP 能给的是"能起来"，不是"能用好"
DT vs UEFI 两种向内核描述硬件的机制。ARM 世界主流是 Device Tree（静态编译的 DTB 由 bootloader 传给内核）；x86 是 UEFI + ACPI
LSB / POSIX 嵌入式常常"不完整 POSIX"——BusyBox 是裁剪版，别指望桌面 Linux 那套工具链齐全

HFT / 嵌入式关联

  • 延迟量级：Linux 的调度抖动是尾延迟问题（p99.9 刺尖），RTOS 是上限保证。HFT 生产环境走 x86 + 内核旁路（13-dpdk），Pi 5 上练的是思想（绑核、中断隔离、缓存友好），不是生产指标。
  • SoC 视角很重要：因为外设控制器在片内，驱动面对的是 MMIO 寄存器 + 设备树节点，而不是"插在总线上的卡"。这决定了后面 03-platform-dt 为什么是驱动的核心。

1.1

Linux 逐步替代传统 RTOS：动因、差异、边界与混合架构

扩展精读 · 锚定 Embedded Linux Primer Ch1（Why Linux）+ 行业实践
实时改造细节 → Ch17 Linux and Real Time
章内摘要：notes.md

一、书中背景（Ch1 观点）

传统商用专有 RTOS 曾长期垄断嵌入式；Linux 凭 零按设备授权费、宽硬件覆盖、完整开源生态 快速渗透。手机、网关、工业 HMI、车载娱乐、通信交换机等大量从 VxWorks / QNX 等迁到 Linux。

底层驱动力（与 Ch1 §1.1 对齐）：

  1. 专有 RTOS 按终端收费，量产摊销高
  2. 社区迭代快，新芯片 / 外设驱动落地快
  3. 内置 TCP/IP、FS、图形、多媒体，少从零开发
  4. 从低端网关到电信级设备均可伸缩（含 CGL 叙事）
  5. GPL 允许修改与定制（同时带来分发义务，见 notes §1.3）

二、相对传统 RTOS 的核心优势

1. 成本

  • 无每设备 OS 授权（对比 VxWorks、部分商用 ThreadX 等）
  • 工具链、中间件、大量驱动开源，少买第三方协议栈 / GUI 授权

2. 软件生态（差距最大）

域 Linux 典型 RTOS
网络 TCP/IP、MQTT、VPN、蜂窝/以太等成熟栈 常需外购组件
存储 ext4 / UBIFS / JFFS2、NFS、MTD… 多为轻量 FS 或第三方
应用 Qt、OpenCV、DB、Web、脚本语言 能力薄
调试 gdb / strace / ftrace…（本书 Ch13–15） 工具链往往厂商绑定

3. 硬件适配广度

内核驱动海量；ARM / MIPS / Power / x86 等；TI、NXP 等官方 Linux BSP 周期通常短于 RTOS 全平台移植。

4. MMU 与隔离

无 MMU 的经典 RTOS：任务共地址空间，一崩易拖死整机。
Linux：内核态 / 用户态 + 进程空间隔离，应用崩溃默认不毁内核（运维友好）。

5. 开发与维护

POSIX 可复用桌面经验；Buildroot / Yocto 管依赖与整包；社区修漏洞；网关/边缘可上容器与虚拟化做业务隔离。

6. 伸缩性

可裁到小型路由，也可撑电信级冗余设备——多产品线共用一套软件骨架。

三、原生短板（不能「无脑替换」的约束）

短板 表现 影响
实时性弱（核心） CFS 偏吞吐；中断/调度延迟与抖动大，最坏可达 ms 级 无硬实时确定性
资源门槛 需 MMU（如 Cortex-A）；RAM 通常数十 MB+，Flash 百 MB 量级 几 KB RAM 的 MCU 上不了
启动偏慢 秒级常见 vs RTOS 毫秒级 极速上电控制不友好
功能安全认证难 代码体量大，IEC 61508 / DO-178 等成本高 航空/医疗关键路径更爱精简 RTOS
GPL 分发修改内核须履约公开源码 纯闭源策略有合规摩擦

对照：VxWorks / FreeRTOS 等优先级抢占，中断延迟可到 µs 级，时间行为更可预测。

四、实时化：PREEMPT_RT（指向 Ch17）

弥补实时短板的主路径（细节精读 本书第 17 章）：

  1. 提高可抢占性：缩小不可抢占临界区、中断线程化等
  2. 实时调度：SCHED_FIFO / SCHED_RR / SCHED_DEADLINE
  3. 削减延迟源：后台回收、日志、定时器等（按场景调）
  4. 测量：cyclictest、ftrace 量化调度延迟

改造后工业 HMI、机器人、音视频等 软实时 常可落到数十 µs 量级（视板级与负载而定）。

边界： 内核后台、换页、文件 I/O 仍可引入抖动 → 不适合安全关键硬实时（动力总成、伺服闭环等）。
仓库侧：Pi Labs Phase D 的实时调度入门与 11 运动控制 再对照。

五、适合用 Linux 替代 RTOS

  1. 复杂网络设备：工业/物联网关、路由、多协议并发
  2. 图形 / 多媒体：工业 HMI、车机、广告屏、智能相机
  3. 电信级通信：基站、交换机（高可用、多业务、远程运维）
  4. 边缘计算：视觉、本地库、容器多服务
  5. 中高端消费电子：电视、中控等
  6. 多产品线、要共用 BSP / 快迭代的团队

→ 与本仓库主线（用户态 → 驱动 → 板级项目）一致。

六、不适合直接用 Linux 替代

  1. 硬实时安全关键：动力 ECU、伺服、航空/生命支持控制
  2. 低成本无 MMU MCU 节点（RAM 极小）
  3. 要求毫秒级极速启动的安全切断类装置
  4. 严苛功能安全认证（如 SIL3/4 路径）
  5. 仅简单 IO、无网络无 GUI 的极简板

本仓库 排除 STM32 裸机 / 纯 RTOS-only 项目，正是划在这条边界外。

七、主流折中：异构多核混合

A 核 Linux + M/R 核 RTOS（如 i.MX、同类异构 SoC）：

核 典型职责
Linux 网络、GUI、日志、OTA、业务、数据库
RTOS 协核 电机、高速采集、安全硬实时闭环

兼顾生态与确定性；车载、工业机器人常见。选型不是「二选一」，而是 分工。

八、总结：趋势与选型口诀

判断 选
有 MMU，要网络 / 图形 / 复杂应用 Linux（需要再加 PREEMPT_RT）
极简控制、硬实时、低成本 MCU RTOS
两者同时要 异构多核混合

趋势： 能跑应用处理器且业务复杂的产品，从商用 RTOS 迁 Linux 基本不可逆（成本 + 生态）。
边界： 硬实时、超低成本、高安全认证 → RTOS（或协核）仍刚需。

参考

  • Hallinan, Embedded Linux Primer, 2nd ed, Ch1 · Ch17

1.2

为何书还讲 LSB · LSB 与 POSIX 的区别

FAQ · 锚定 Primer Ch1 §1.4 · 对照 TLPI Ch1 标准化
章摘要：notes.md

1. 事实：LSB 已废，工程不用

事实 说明
末版 LSB 5.0 ≈ 2015，此后无实质更新
维护 约 2023 年侧公开承认项目实质废弃
发行版 RHEL / Debian / Ubuntu 等陆续去掉 lsb_release、LSB 兼容层与认证路径

消亡原因： 发行版迭代远快于标准；为兼容老二进制要背大量兼容层，负担过重，厂商弃坑。

本仓库结论（与 TLPI 一致）：现代嵌入式 / HFT 工程忘掉 LSB。

2. 为何 Embedded Linux Primer（2011）仍专节讲 LSB

书成书约 2010 / 出版 2011，时间线不同：

  1. 当年是硬规范：Linux 基金会主推；RHEL、SUSE、MontaVista 等商用/嵌入式发行常谈 LSB 认证；跨发行版二进制交付、客户验收会抠它
  2. 书面向商用嵌入式：电信 / 工业交付语境里，LSB 是工程师常识
  3. 章节逻辑：Ch1 扫基金会规范矩阵（CGL、Moblin、LSB、SA Forum）；用 LSB 衬出「POSIX = 源码 API」vs「LSB = Linux 发行版 ABI 扩展」两层标准

读老书：理解历史定位即可，不必落地认证。

3. LSB vs POSIX（纠正常见误区）

POSIX（IEEE 等） LSB（Linux Standard Base）
层级 源码级 API 可移植标准 建在 POSIX 之上的 Linux 专属二进制 / ABI / 布局 补充
范围 类 Unix 通吃（Linux、BSD、macOS、不少 RTOS 宣称子集） 只针对 Linux 发行版
目标 源码符合 → 重编译可迁 二进制 不重编 跨发行版跑
今日 仍有效；Linux 长期跟 POSIX 接口 已废
认证 无「交钱才用 POSIX」这回事 当年有厂商认证路径

关键纠正：
不存在「Linux 不给钱就不用 POSIX」。Linux 接口上遵循 POSIX；没去买 UNIX 商标认证 ≠ 抛弃 POSIX API。POSIX 与 LSB 不是替代关系：POSIX 是底座，LSB 曾是 Linux 上层二进制兼容补丁，现已卸掉。

（「POSIX 6」若指某版号叙事：以现行 POSIX / SUS 文档为准；学习重心是 接口语义，不是背 LSB 表。）

4. 现在怎么学、怎么替代当年 LSB 目标

态度 做法
读 Primer / 老嵌入式书 知「当年强制、用来对照 POSIX」→ 速览翻过
写代码 按 POSIX + Linux 扩展（见 TLPI）；固定发行版或自建 rootfs
跨环境交付 容器、静态链接、Yocto/Buildroot 定制根文件系统 — 替代「一份 LSB 二进制通吃发行版」

参考

  • Hallinan, Embedded Linux Primer, 2nd ed, §1.4
  • TLPI Ch1 · POSIX / SUS / LSB
1.3

学习重心：绝大多数嵌入式项目盯 SoC

选型 / 求职优先级 · 锚定 Primer Ch3
分类标准：notes.md · 树莓归类：3.2-raspberry-pi-is-soc.md

结论

普通嵌入式 Linux：重心放在 SoC。
独立处理器（+南北桥）只作拓展；除高端电信/刀片等赛道，不必当核心课。

一、约九成以上项目：SoC（必学）

典型产品

域 例子
消费 树莓派、手机/平板、路由、机顶盒、相机、车机、智能屏
工业 HMI、小型网关、采集终端、运动控制主板
通信中端 家用 / 中小企业交换类
开发板 Beagle（OMAP）、i.MX、树莓、全志 / 瑞芯微等

为何行业押 SoC

  1. BOM / PCB：单片集成 CPU、内存控制器、网/USB/显示/串口等，免经典南北桥，成本与面积友好
  2. 周期：原厂 BSP（U-Boot、内核、驱动）齐，少从零啃芯片组
  3. 匹配需求：低功耗、小体积；GPU/多媒体/以太正好喂 Linux 图形与网络
  4. 贴合本书：i.MX、OMAP、Broadcom MIPS、AMCC PPC440 等案例都是 SoC；U-Boot / 裁核 / rootfs / 驱动主线按 SoC 讲

工程师日常（几乎都围着 SoC）

  • U-Boot、设备树
  • 内核裁剪、外设驱动（网、USB、LCD、SD、Camera…）
  • rootfs（BusyBox、Buildroot / Yocto）
  • 应用 / GUI / 网络 / 多媒体
  • 功耗、启动时间、（软）实时调优

本仓库对齐：11 Primer→MELP · 09 驱动·DT · 13 Pi Labs · 07 ARM。

二、独立处理器 + 芯片组：小众高端

适用 代表（书中年代）
ATCA 机架、大型刀片、高性能信号处理、高端工控主机 Atom / Pentium M、MPC7448、IBM 970FX 等

中小项目少选的原因： 板子复杂（北桥+南桥）、调试面大（内存/PCI/总线）、功耗与尺寸不友好。
谁做： 大型通信设备等高端团队；消费 / 常规工业岗基本碰不到。Ch3 §3.1、§3.4（cPCI/ATCA）→ 速览 / 按需 即可。

三、学习与求职优先级

通用嵌入式 Linux（主流岗位）

全力吃透 SoC：

  1. 硬件：ARM（及下面 RISC-V）SoC、片内外设
  2. 软件：U-Boot、DT、内核配置、闪存/MTD 或 eMMC/SD、BusyBox、交叉编译、GDB
  3. 板子：树莓派、i.MX、全志等上手

工控、车载、网关、AI 终端等招聘叙事，绝大多数基于 SoC。

特殊赛道（高端通信 / 服务器工控）

再补：独立 CPU + 芯片组、ATCA/cPCI、PCIe 与桥片总线——细分技能，非通用刚需。

四、新趋势：仍是 SoC

RISC-V SoC（各家应用处理器）是新增主流，分类仍是集成 SoC；学习逻辑与 ARM SoC 同构（工具链 / DT / U-Boot / 内核），继续当重点，不必退回南北桥课。

对照 Ch3 怎么读

节 态度
§3.2 SoC（尤其 ARM） 精读 / 主线
§3.1 Stand-Alone 速览：知道「还有这类」
§3.3–3.4 小众架构 / 背板 按需

一句话： 入门与求职押 SoC；独立处理器不当核心。

1.4

树莓派 BCM：按本书标准属于 SoC，不是独立处理器

FAQ · 锚定 Primer Ch3 分类 · 章摘要：notes.md
板级动手：Pi Labs

结论

树莓派核心 Broadcom BCM 系列是 ARM 架构集成 SoC（Integrated Processor），
不属于 Ch3 定义的 Stand-Alone Processor（独立 CPU + 南北桥）。

一、书中二分法（对照 Ch3）

类型 书中标准 例子
独立处理器 几乎只有算力核；无内置内存控制器 / 以太 / USB / GPU / 串口等完整外设集；必须配北桥、南桥（或等价桥片） Pentium M、Atom、MPC7448、IBM 970FX
SoC 单片：CPU + 内存控制器 + 通信/多媒体/IO；板级只需电源、Flash/SD、PHY 等少量辅芯片 TI OMAP、Freescale i.MX、Broadcom MIPS 线；树莓 BCM 同属此类

二、BCM 系列即 SoC 证据

板 SoC CPU（均带 MMU，可跑 Linux）
初代 / Zero BCM2835 ARM1176
Pi 2 BCM2836 4× Cortex-A7
Pi 3 BCM2837 4× A53
Pi 4 BCM2711 4× A72
Pi 5 BCM2712 4× A76

单片内常见集成（无需南北桥）：

  • ARM CPU（+ MMU）
  • VideoCore GPU / 编解码
  • LPDDR 内存控制器
  • HDMI / DSI、CSI、USB 控制器
  • 以太 MAC、I2C / SPI / UART / GPIO
  • 片内总线与中断控制

PCB： 主板上无南北桥大芯片；辅件多为 PHY、电源、Wi‑Fi/BT 模组、（Pi5）RP1 等南桥式 I/O 伴侣——那是 SoC 生态里的外设芯片，不是 Ch3 那种「独立 CPU 必备南北桥芯片组」叙事。

Pi5：应用核在 BCM2712，丰富 GPIO/外设常经 RP1；分类上整机仍是 SoC 方案，不是 Stand-Alone + 经典南北桥。

三、与书中 ARM 小节对标

Ch3 的 OMAP / i.MX：消费多媒体 SoC、CPU+GPU+IO、跑嵌入式 Linux、开发板形态。
树莓 BCM 定位同一格；只是厂商从 TI/Freescale 换成 Broadcom，年代更新到 BCM2712。

四、易混概念

说法 澄清
SoM（如 Compute Module） 小电路板模组 = SoC + 内存/eMMC 等；上面那颗核仍是 SoC，SoM ≠ SoC
独立 CPU + 南北桥 老式 x86 工控 / 书中 Stand-Alone
单颗（或 SoC+RP1）集成方案 树莓、手机、路由、机顶盒

Bootloader 侧：这类板走 厂商固件 / U-Boot 嵌入式路径，不是 PC BIOS/UEFI 独立 CPU 故事 → 2.1 FAQ。

五、一句话

按 Primer Ch3：树莓派 Broadcom BCM = ARM 集成 SoC；读独立处理器节时用它当反例即可，精读应对齐 §3.2 SoC / ARM。

1.5

原厂 BSP：开箱能跑，量产仍要大量改

FAQ · 锚定 Primer Ch3（SoC）· Ch4（内核工程）· Ch7（Boot / DT）
重心 SoC：3.0-focus-on-soc.md · 树莓归类：3.2-raspberry-pi-is-soc.md

结论

原厂确实给完整 BSP（内核、U-Boot、驱动、参考 DTS、工具链 / Yocto·Buildroot…），
但只保证 官方评估板 / 参考设计 开箱可用。
自研 PCB = 以 BSP 为模板做二次开发；不是「拷贝即量产」。

一、原厂会交什么（BSP 常见内容）

SoC 厂（NXP i.MX、TI、Broadcom、全志、瑞芯微等）板级支持包通常含：

  1. Linux 内核（源码和/或预编译）
  2. U-Boot（或厂商等价 boot）
  3. 片内外设驱动：USB、以太、SD、LCD、Camera、I2C/SPI/UART、编解码、PMIC…
  4. 参考设备树（绑在评估板原理图上）
  5. 工具链、Buildroot / Yocto 脚本、rootfs 模板
  6. 原理图、寄存器/TRM 类文档

评估板现实： i.MX / Beagle 等 — 按文档编镜像烧录，外设基本通。
树莓派： 官方镜像 + 内核树；不改板则刷机即用（Pi Labs）。

二、自研硬件：改在哪里（工作量主战场）

原厂 DTS/驱动对齐的是他们的板，不是你的原理图。

1. 设备树 — 几乎必改（Ch7 / 09 DT）

常见差异：

  • GPIO / 串口 / LED / 按键换脚
  • 存储：eMMC → NAND（MTD 分区重配）或换 SD 方案
  • 网：PHY 型号、复位脚不同
  • 屏 / Camera 换料
  • PMIC 电压与上电时序
  • 删掉不用的节点（多余 USB、音频）省资源与攻击面

改一脚也要动 DTS；严重时驱动时序一起调。

2. 驱动 — 分三档

类型 你通常做什么
片内模块（MAC、SDHC、UART、GPU…） 少重写；DTS 配引脚、时钟、DMA
板级外接芯片（PHY、屏、Codec、传感器） 原厂驱动当参考；换料就改驱动或重移植
自研外设 无现成驱动 → 字符/平台驱动从零写（本书 Ch8 · 12）

3. 内核裁剪与产品化（Ch4）

原厂 .config 求「演示全绿」→ 体积大、模块杂。量产常要：关无用驱动/协议/调试；可选 PREEMPT_RT；开机 logo / 日志策略；分区与 Flash FS 参数（JFFS2/UBIFS 等）。

4. U-Boot（Ch7）

DDR 颗粒、Flash/eMMC、环境变量、启动介质一变，就要改初始化与分区/env；不是「评估板 u-boot.bin 直接量产」。

三、两种人，两种工作量

路径 底层改动量 日常重心
只用不画板（树莓 / 原厂 EVK） 极小 应用、业务、偶尔 overlay
自研 PCB（同款 SoC 也一样） U-Boot + DTS + 部分驱动 + 内核配置 大规模 硬件适配 = 嵌入式 Linux 岗核心产出

四、两个误区

  1. 「SoC 内部固定 → 软件不用改」
    片内互联固定；引脚接到 PCB 的方式由原理图决定。换脚 = 改 DTS（常还要改时序/驱动）。

  2. 「厂家给了内核 → 不用懂底层」
    量产要抠启动时间、功耗、实时、磨损、安全。默认 BSP 达不到指标时，不懂内核 / DT / 存储 / FS 就无法调优。

你现在 含义

  1. 原厂 BSP 完整且能跑自家评估板
  2. 自研硬件：DTS 必改；外接驱动常改；Boot/内核必裁剪适配

1.6

设备树 ≠ UEFI · DT 不「规划」内存 · 何时改 U-Boot

FAQ · 锚定 Primer Ch2（固件对比）· Ch7（U-Boot 交权）· 09 DT
相关：U-Boot vs BIOS vs UEFI · BSP 模板

一、结论：DT 和 UEFI 不是一类东西

功能上只有一点交集——都要让内核知道板上有什么——载体与体量完全不同。

1. UEFI：整套可运行固件（PC / 通用计算）

  • 上电独立跑：驱动、分区、网络、Secure Boot、可有图形等
  • 硬件描述主体是 ACPI 表（不是「UEFI 文件 = 设备树」）
  • 可有 Runtime Services：内核起来后仍可能调固件
  • 流程概览：UEFI 初始化 → 准备 ACPI 等 → 交权给内核

「提前规划内存映射 / 设备地址」在 UEFI 世界里，主要是 ACPI（及固件内存图） 的叙事，不要说成「UEFI = 设备树」。

2. 设备树（DTS → DTB）：静态硬件清单

  • 纯描述数据，无独立「跑起来的 OS」
  • 自己不初始化 显卡/硬盘/网卡；上电初始化在 U-Boot（或厂商 boot）
  • 交给内核解析后，DTB 作为启动参数消费；不是 UEFI 那种长期 Runtime 服务
  • 主战场：ARM / 多数嵌入式 SoC（MIPS/Power 等也曾用）；与 x86 主流 ACPI 是两套标准

典型内容：外设 物理基址、中断、供电/复位脚、时钟、总线拓扑、Flash 分区、内存起止大小、compatible（驱动匹配）。

UEFI 设备树 DT
本质 可执行固件体系 静态配置（DTS/DTB）
谁初始化硬件 固件自己大量做 不做；U-Boot 做
描述载体 ACPI 等 DTB
内核后 可残留 Runtime 启动时解析，非 UEFI 式固件服务
类比 工具箱 + 图纸（ACPI） 只有图纸；工具箱 = U-Boot

二、纠正：「设备树规划内存」

DT 不主动分配、规划 运行时内存。

  1. SoC MMIO 基址 在硅上固定（手册写死），你改不了「串口到底焊在哪段物理地址」
  2. DTS 是把手册/原理图 抄成机器可读配置，告诉内核：UART@0x…、ETH@0x…
  3. 虚拟内存、页框、进程地址空间 由内核 + MMU 管，不是 DT
  4. DDR 物理颗粒 由 U-Boot（等）初始化控制器；DT 常只标注「这块 DRAM 从哪到哪、多大」供内核建 memblock

例：以太控制器硬件窗口永远是手册上的 0x20000000 一类地址——DTS 登记它，不是 DT 分配出这块窗口。

三、改 DT 要不要动 U-Boot？

场景 A — 只改设备描述 → 通常只重编 DTB，不改 U-Boot 源码

例如：换 GPIO/中断/供电脚；增删 LED/按键/传感器/屏节点；改 Flash 分区表标注；改内存 大小标注（且 DDR 初始化仍匹配现硬件）。

流程：改 .dts → make dtbs（或厂商等价）→ boot 加载新 DTB → 旧 U-Boot 二进制往往仍可用。

场景 B — 底层初始化参数变了 → 必须改并重编 U-Boot

DT 管不了这些「上电第一拍」：

  1. DDR 型号 / 频率 / 位宽 / 时序（控制器初始化在 U-Boot）
  2. Flash/eMMC 型号、片选、时序（boot 阶段读写介质）
  3. 晶振 / PLL / 主频 启动时钟树
  4. U-Boot 自己就要用 的串口、网口 PHY 等时序/引脚
  5. 启动脚本里的 镜像/DTB 加载地址、env、bootcmd

只改 DTS 救不了 内存训不开、Flash 读不出。

配合流程（Ch7 骨架）

U-Boot：初始化 DDR / 时钟 / 启动介质   ← DT 插不上手
    → 加载 内核镜像 + DTB 到 RAM
    → bootm/booti … 把 DTB 指针交给内核
内核：解析 DTB → 绑驱动 / 建设备

分界线： 底层上电初始化 = U-Boot；静态硬件清单 = DT。这与 UEFI「固件自己初始化 + ACPI 描述」不是同一套积木。

四、一句话

  1. UEFI ≠ DT；UEFI 用 ACPI，嵌入式用 DT；DT 无执行能力
  2. DT 记录 固定物理信息，不 当 MMU/分配器
  3. 只改外设描述 → 重编 DTB 即可；DDR/Flash/时钟/boot 介质变 → 同步改 U-Boot

树莓派：官方固件链与「纯开源 U-Boot 板」细节不同，但 「boot 固件初始化 ↔ DT/配置描述内核」 分工仍成立；Pi5 查官方 DT / overlay，见 Pi Labs。
