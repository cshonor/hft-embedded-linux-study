# init 之后：`inittab` 的四个字段，与 `respawn` 为什么能 fork 炸机器

> **本节讲什么：** 内核把 PID 1 拉起来之后（见 [6.1](./6.1-kernel-init-search.md)），用户态由谁接手。以 **BusyBox init** 为对象，按源码逐个字段拆 `/etc/inittab`，说清 `sysinit` / `wait` / `once` / `respawn` 的执行时机差别，以及两个反直觉点：**runlevel 字段是被彻底忽略的**、**BusyBox 不做 respawn 频率抑制**。
> **前置：** [6.1 内核怎么找 init](./6.1-kernel-init-search.md) · [05-rootfs/5.1 手工最小 rootfs](../05-rootfs/5.1-minimal-rootfs-by-hand.md)
> **动手：** [P5 · B2](../../projects/P5-raspberry-pi-embedded/RASPBERRY-PI5-LABS.md)
> **卡住查书：** MELP Ch13–14 · Primer Ch6
> **对应验收：** 06 第 3 条「写过 `inittab`，知道 `respawn` 与 `sysinit` 的区别」

## 一句话

`inittab` 就是一张**"什么时候该跑什么"的表**。四个字段里真正起作用的只有三个——**第二个字段（runlevel）是历史遗迹，BusyBox 直接无视**。

---

## 四个字段（源码注释原文）

BusyBox `init/init.c` 里 `parse_inittab()` 的注释写得比任何文档都清楚：

```c
/* optional_tty:ignored_runlevel:action:command
 * Delims are not to be collapsed and need exactly 4 tokens
 */
```

| 字段 | 含义 | 例子 |
|---|---|---|
| `id` / `optional_tty` | 该进程的**控制终端**。留空 = 用 console | `ttyAMA0` |
| `runlevel` | ⚠️ **被忽略**，见下 | （留空） |
| `action` | 什么时候跑、跑完怎么办 | `sysinit` / `respawn` |
| `command` | 要执行的命令 | `/etc/init.d/rcS` |

对应 06 README 里那两行：

```
::sysinit:/etc/init.d/rcS                        ← id 空、runlevel 空
::respawn:/sbin/getty -L 115200 ttyAMA0 vt100    ← id 空、runlevel 空
```

> `id` 留空意味着进程继承 init 自己的 console——所以 `respawn` 一个 shell 时，**日志会直接打在你接的串口上**。

---

## ⭐ 反直觉点 1：runlevel 字段被完全忽略

BusyBox 官方 usage 原文：

> BusyBox init doesn't support multiple runlevels. **The runlevels field of the `/etc/inittab` file is completely ignored** by BusyBox init.

**实践含义（两个方向都有坑）：**

1. **照抄 SysV 的写法不会生效。** 从网上抄来 `1:2345:respawn:/sbin/getty ...`，那个 `2345` 只是被当作分隔用的占位符——不是"只在 2/3/4/5 级别跑"。BusyBox **没有 runlevel 概念**，所有条目都跑。
2. **别指望用它做"维护模式"。** 想切换运行级别，得自己写脚本逻辑（读 `cmdline.txt` 里的参数 / 读某个文件 / 按 GPIO 按键），`inittab` 帮不了你。

## 八个 action：位掩码与执行时机

源码里 action 是位掩码，注释直接说明了时序：

```c
#define SYSINIT     0x01   /* Start these first */
#define WAIT        0x02   /* Start these after SYSINIT and wait for completion */
#define ONCE        0x04   /* Start these after WAIT and *dont* wait for completion */
#define RESPAWN     0x08   /* Start these after ONCE are started, restart on exit */
#define ASKFIRST    0x10   /* Like RESPAWN, but wait for <Enter> to be pressed on tty */
#define CTRLALTDEL  0x20
#define SHUTDOWN    0x40
#define RESTART     0x80
```

字符串表顺序与之一一对应（`init.c:706`）：

```c
static const char actions[] ALIGN1 =
    "sysinit\0""wait\0""once\0""respawn\0""askfirst\0"
    "ctrlaltdel\0""shutdown\0""restart\0";
```

### 时序图

```
时间 ──────────────────────────────────────────────────────────►

① SYSINIT   顺序执行，★ 等它跑完
   │  例：::sysinit:/etc/init.d/rcS   ← 挂 /proc /sys、配网络、起守护进程
   ▼
② WAIT      顺序执行，★ 也等跑完（与 sysinit 的差别只在"阶段"）
   ▼
③ ONCE      启动，★ 不等（fire-and-forget）
   ▼
④ RESPAWN / ASKFIRST   启动后进入无限循环：
   │      进程退出 → 立刻重启（ASKFIRST 多一步"等回车"）
   │      ★ 这一阶段永不结束，init 就停在这当"守护者"
   ▼
   ♾️ （Ctrl-Alt-Del → CTRLALTDEL；关机 → SHUTDOWN；SIGQUIT → RESTART）
```

### 逐个说明

| action | 是否等待完成 | 退出后 | 典型用途 |
|---|---|---|---|
| `sysinit` | ✅ 等 | 不重启 | **系统初始化脚本**（挂文件系统、配网络）—— 必须最先、且必须跑完 |
| `wait` | ✅ 等 | 不重启 | 需要完成才能继续的一次性任务（如格式化/校验） |
| `once` | ❌ 不等 | 不重启 | 后台一次性任务 |
| `respawn` | ❌ 不等 | ✅ **立刻重启** | **getty（登录终端）、关键服务守护** |
| `askfirst` | ❌ 不等 | ✅ 重启（先等回车） | 控制台上的 shell，防刷屏 |
| `ctrlaltdel` | — | — | 按 Ctrl-Alt-Del 时执行 |
| `shutdown` | — | — | 关机/重启时执行（`umount -a -r`、`swapoff -a`） |
| `restart` | — | — | 收到 SIGQUIT 时，init **exec 自己替换成它**（只用第一条） |

---

## `sysinit` vs `respawn`：一句话差别

| | `sysinit` | `respawn` |
|---|---|---|
| **时机** | 最先，且**阻塞**后续所有阶段 | 最后，进入永久守护循环 |
| **退出后** | 不重启（跑了就跑了） | **立刻重启** |
| **典型对象** | 一次性初始化脚本 | 需要"活着"的东西：getty、服务 |
| **写错的后果** | 卡在这儿，后面全不执行 | fork 炸弹（见下） |

> ⭐ 验收项问的就是这个：**`sysinit` = "开机做一次，做完才准继续"；`respawn` = "这东西必须一直活着，死了就拉起来"。**
> 把 getty 写成 `sysinit` → 登出后就没终端了；把 `rcS` 写成 `respawn` → 初始化脚本反复执行。

---

## ⭐⭐ 反直觉点 2：BusyBox **不做** respawn 频率抑制

官方 usage 原文：

> When a process started with a 'respawn' action exits, init automatically restarts it. **Unlike sysvinit, BusyBox init does not stop processes from respawning out of control.**

**实践含义：** 如果你 `respawn` 一个**启动即失败**的程序（配置错、依赖还没起、二进制缺库），BusyBox 会**以最快速度无限重启它**——CPU 打满、日志刷爆，真机能把串口控制台彻底淹掉，你连敲命令的机会都没有。

**怎么救：**

| 手段 | 做法 |
|---|---|
| **临时停手** | `kill -TSTP 1` —— 官方支持：`TSTP: stop respawning until CONT`。修好后 `kill -CONT 1` 恢复 |
| **改配置** | 从 `respawn` 改成 `once` + 在脚本里自己 `sleep`；或让脚本失败时 `sleep 5` 再退 |
| **根治** | `respawn` 的对象应该是"简单、几乎不会失败"的东西（getty / supervise），**业务逻辑不要直接 respawn**，交给 runit/s6 这类带退避的 supervisor |

> ⚠️ 这正是为什么产品级系统不会把业务进程直接写进 `inittab` 的 `respawn`——**需要一个自带 backoff 的监督层**。

## 没有 `/etc/inittab` 时会怎样

源码 `parse_inittab()` 里有完整兜底（`init.c:679`）：

```c
if (parser == NULL) {
    /* No inittab file - set up some default behavior */
    new_init_action(SYSINIT,  INIT_SCRIPT, "");              // /etc/init.d/rcS
    new_init_action(ASKFIRST, bb_default_login_shell, "");   // console
    new_init_action(ASKFIRST, bb_default_login_shell, VC_2); // tty2
    new_init_action(ASKFIRST, bb_default_login_shell, VC_3); // tty3
    new_init_action(ASKFIRST, bb_default_login_shell, VC_4); // tty4
    new_init_action(CTRLALTDEL, "reboot", "");
    new_init_action(SHUTDOWN,   "umount -a -r", "");
    new_init_action(SHUTDOWN,   "swapoff -a", "");
    new_init_action(RESTART,    "init", "");
    return;
}
```

⭐ **所以：手写最小 rootfs 时如果没建 `/etc/inittab`，系统照样能起来**——BusyBox 会跑 `/etc/init.d/rcS` 并在 console 上给一个 shell。

⚠️ **但别依赖它**：默认行为会在 tty2/3/4 各开一个 askfirst shell。做产品时这是**安全隐患**（物理接键盘就能进 shell），应显式写自己的 `inittab`。

## 重读 `inittab`（SIGHUP）的陷阱

源码注释（`init.c:170`）：

> SIGHUP ("reread /etc/inittab") will be processed only after each group of actions. **If new inittab adds, say, a SYSINIT action, it will not be run, since init is already "past SYSINIT stage".**

**实践含义：** `kill -HUP 1` 能让你加的 `respawn` 条目生效，但**新加的 `sysinit` 条目不会被执行**——init 已经过了那个阶段。想跑初始化逻辑，得手动执行或重启。

---

## 其它源码级细节

- **`initdefault` 不被支持。** 官方 usage：Unrecognized actions (like `initdefault`) will cause init to emit an error message, and then go along with its business. —— 抄 SysV 配置时这个关键字会报一行错然后被跳过。
- **所有条目按文件里的出现顺序执行**（All actions are run in the order they appear in `/etc/inittab`）—— 所以 `sysinit` 写两行时，顺序就是你写的顺序。
- **少于 4 个 token = 坏条目**（`if (!token[3]) goto bad_entry`），会被跳过并告警。
- **init 支持的信号**：

| 信号 | 作用 |
|---|---|
| `HUP` | 重读 `/etc/inittab` |
| `TSTP` | 停止 respawn，直到收到 `CONT` |
| `QUIT` | re-exec 另一个 init（走 `restart` 条目） |
| `USR1`/`TERM`/`USR2`/`INT` | halt / reboot / poweroff / Ctrl-Alt-Del |

## HFT / 嵌入式关联

- **进程监督是低延迟系统的基础设施。** 交易网关里"行情断流"和"进程死了"是两件事——前者要报警，后者要立刻拉起。`respawn` 提供的是最朴素的 liveness，但**没有 backoff 就没有保护**。生产环境要么用带退避的 supervisor（runit/s6），要么在 entrypoint 脚本里自己做 `sleep` 退避。
- **`sysinit` 阶段是串行的，会直接计入启动时间。** 想在 30 秒内恢复服务，`rcS` 里每一条命令都是临界路径上的成本。测量方法见 [6.3 启动耗时怎么测](./6.3-boot-timing.md)。
- **别在 `respawn` 里放会打日志的东西。** 串口 115200 大约只有 11 KB/s，一个疯狂重启的进程能把 console 彻底堵死，让你失去唯一的调试通道。这也是 [6.2](../06-boot-to-shell/6.2-console-and-serial.md) 强调"先接串口"的配套注意事项。
- **默认 inittab 的 tty2/3/4 shell 是攻击面。** 量产镜像必须覆盖。

## 自测

<details>
<summary>Q1：`inittab` 第二个字段（runlevel）写 2345 会怎样？</summary>

**完全被忽略。** BusyBox 官方 usage 原文：the runlevels field of the `/etc/inittab` file is completely ignored by BusyBox init.

BusyBox 没有 runlevel 概念，所有条目都会执行。那个字段只是为了满足四字段格式而存在的占位符（源码注释直接叫它 `ignored_runlevel`）。

要做"维护模式"必须自己写逻辑。
</details>

<details>
<summary>Q2：`sysinit` 和 `wait` 都"等待完成"，区别在哪？</summary>

**阶段不同，语义不同。**

- `sysinit`：最先执行的一批，代表"系统初始化"，阻塞后续所有阶段
- `wait`：在 sysinit **之后**执行，同样等待完成

功能上都能阻塞，差别是**语义分组**——把"初始化"和"依赖初始化完成的一次性任务"分开写，可读性和可维护性更好。真正需要区分的是 `wait`（等）vs `once`（不等）。
</details>

<details>
<summary>Q3：把 getty 写成 `sysinit` 会怎样？</summary>

**登出一次就再没有终端了。**

`sysinit` 条目执行完（进程退出）后不会重启。getty 在用户 logout 时退出 → 没有 respawn → 该终端永久失效 → 串口/控制台再也进不去。

正确写法是 `::respawn:/sbin/getty -L 115200 ttyAMA0 vt100`。
</details>

<details>
<summary>Q4：一个配置错误的程序被写成 `respawn`，启动后立刻崩溃。会发生什么？</summary>

**fork 炸弹。** 官��� usage 原文：Unlike sysvinit, BusyBox init does not stop processes from respawning out of control.

BusyBox 会以最快速度无限重启它，CPU 打满、串口被日志淹没，你可能连敲命令的机会都没有。

**急救**：`kill -TSTP 1` 让 init 停止 respawn（修好后 `kill -CONT 1` 恢复）。

**根治**：只把简单可靠的东西（getty / supervisor）放进 `respawn`；业务进程交给带 backoff 的 supervisor，或在脚本里失败时先 `sleep` 再退出。
</details>

<details>
<summary>Q5：手工 rootfs 忘了建 /etc/inittab，系统能起来吗？</summary>

**能。** BusyBox 有兜底（`init.c:679`）：跑 `/etc/init.d/rcS`，在 console 和 tty2/3/4 上各开一个 askfirst shell，另加 `reboot`/`umount -a -r`/`swapoff -a`/`init` 四条默认动作。

但**别在产品里依赖它**：tty2/3/4 上那几个 shell 意味着物理接触即可获得 root shell，是明确的安全隐患。
</details>
