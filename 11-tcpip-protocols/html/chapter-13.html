引言

章级精读：../study.md · TCP 基础：ch12

本节核心目标

理解 TCP 连接的完整生命周期：建立 → 数据传输 → 关闭。

连接状态机

CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
              ↑                                    ↑
         SYN_RCVD ← LISTEN → ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED

三个关键阶段

阶段 机制 报文
建立 三次握手 SYN → SYN+ACK → ACK
数据传输 序号+ACK+窗口 数据段
关闭 四次挥手 FIN → ACK → FIN → ACK

HFT 关联

阶段 HFT 关注
连接建立 预热连接避免握手延迟
TIME_WAIT 释放端口资源（tcp_tw_reuse）
RST 异常断开排查
Keepalive 交易链路保活

13.2

TCP 连接建立

章级精读：../study.md

本节核心目标

掌握三次握手的详细流程和每个报文的作用。

三次握手流程

Client                              Server
  |                                   |
  | --- SYN (seq=x) ---------------> |  LISTEN → SYN_RCVD
  |                                   |
  | <-- SYN+ACK (seq=y, ack=x+1) --- |  SYN_RCVD
  |                                   |
  | --- ACK (ack=y+1) -------------> |  SYN_RCVD → ESTABLISHED
  |                                   |
  |        数据传输开始                |
步骤 报文 作用
1 SYN (seq=x) 客户端发起，初始序号 x
2 SYN+ACK (seq=y, ack=x+1) 服务端确认 x，发起自己的序号 y
3 ACK (ack=y+1) 客户端确认 y

为什么是三次而非两次

两次握手的问题:
1. Client → SYN(x) → Server → 确认 → ESTABLISHED
2. 如果 SYN(x) 是旧的重传 → Server 错误建立连接 → 浪费资源

三次握手解决:
3. Client 收到 SYN+ACK → 检查是否匹配当前请求 → 不匹配则 RST

核心：第三次 ACK 确认了双方的接收能力。

初始序号 (ISN)

  • 随机生成（防序号预测攻击）
  • 32-bit 循环空间
  • 每秒递增 + 随机偏移

SYN Flood 攻击

攻击者发大量伪造源 IP 的 SYN → 服务器为每个 SYN 分配资源等第三次 ACK → 资源耗尽。

# 防御: SYN Cookies
sysctl net.ipv4.tcp_syncookies    # 默认 1
# SYN Cookies: 不预分配资源，在 SYN+ACK 中编码状态

HFT 关联

HFT 系统应预热连接——提前完成三次握手，避免交易时握手延迟（1.5 RTT）。

# 连接复用
sysctl net.ipv4.tcp_tw_reuse=1    # 允许复用 TIME_WAIT 端口

13.3

TCP 选项

章级精读：../study.md · TCP 首部：ch12 §12.3

本节核心目标

掌握 MSS、WSCALE、SACK、Timestamps 四个核心 TCP 选项。

选项概览

选项 握手阶段 作用
MSS SYN 最大段大小（常 1460）
WSCALE SYN 窗口缩放（突破 64KB）
SACK-Permitted SYN 允许选择性确认
Timestamps SYN RTTM + PAWS

MSS (Maximum Segment Size)

MTU 1500 = 20(IP) + 20(TCP) + 1460(MSS)
  • 仅在 SYN 中协商
  • 双方可宣布不同 MSS
  • 路径 MTU 可能更小 → PMTUD

WSCALE (Window Scale)

TCP Window 字段仅 16-bit → 最大 64KB。高 BDP 链路不够。

Window 字段值 = 实际窗口 >> shift_count
实际窗口 = Window 字段值 << shift_count

示例: shift=7 → 实际窗口 = Window × 128 → 最大 ~1GB

sysctl net.ipv4.tcp_window_scaling=1   # 默认开启

SACK (Selective ACK)

允许接收方告知发送方已收到的不连续区间 → 精确重传。

  • 仅在 SYN 中协商是否允许
  • 实际 SACK 块在数据段中携带
  • 最多 ~3-4 个块（选项区 40B 限制）
sysctl net.ipv4.tcp_sack=1   # 默认开启

Timestamps (TSOPT)

每个段携带发送时间戳 → 接收方在 ACK 中回显。

功能 说明
RTTM 精确测量 RTT，绕过 Karn 限制
PAWS 防止序号回绕（32-bit 序号在高速链路上会回绕） 
sysctl net.ipv4.tcp_timestamps=1   # 默认开启

HFT 关联

选项 HFT 必要性
MSS 必须——避免分片
WSCALE 高 BDP 必须
SACK 高 BDP 必须
Timestamps 必须——RTTM + PAWS

所有四个选项都应启用——现代 Linux 默认全部开启。

  2. WSCALE 如何突破 64KB 窗口限制？shift=7 时最大窗口多大？
  3. Timestamps 的两个功能是什么？

13.4

TCP 与 PMTUD

章级精读：../study.md · UDP PMTUD：ch10 §10.8

本节核心目标

理解 TCP 如何通过 MSS 协商和 PMTUD 避免分片。

TCP 的优势

TCP 通过 MSS 协商在握手阶段就限制段大小 → 尽量避免 IP 分片：

1. 握手: 双方宣布 MSS（常 1460）
2. 发送: TCP 段 ≤ MSS → IP 总长 ≤ MTU → 不分片
3. 若路径 MTU 更小 → PMTUD 动态调整

对比 UDP：无 MSS 协商 → 应用一次发太多 → IP 被动分片。

TCP PMTUD 流程

1. 发送 MSS 大小的段（DF=1）
2. 中间路由器超 MTU → ICMP PTB（含下一跳 MTU）
3. TCP 收到 PTB → 降低 MSS → 重发
4. 缓存路径 MTU

黑洞问题

ICMP PTB 被防火墙过滤 → TCP 不知道该降 MSS → 持续发大包 → 持续被丢。

# Linux: PMTUD 黑洞检测
sysctl net.ipv4.tcp_mtu_probing
# 0=禁用, 1=黑洞时启用, 2=始终启用

HFT 关联

TCP PMTUD 比 UDP 更可靠（内核自动处理），但黑洞检测有延迟。HFT 交易链路应确保路径 MTU 已知且固定。

TCP 状态与 TIME_WAIT

章级精读：../study.md

本节核心目标

理解 TIME_WAIT 状态的作用、持续时间和工程调优。

TIME_WAIT

主动关闭方在四次挥手后进入 TIME_WAIT，持续 2×MSL（常 60-120s）。

Client → FIN → Server
Client ← ACK ← Server
Client ← FIN ← Server
Client → ACK → Server → CLOSED
Client → TIME_WAIT (2×MSL) → CLOSED

为什么需要 TIME_WAIT

原因 说明
防旧报文 网络中残留的旧段不会影响新连接
确保对端关闭 最后的 ACK 若丢失，对端重发 FIN，TIME_WAIT 方可响应

TIME_WAIT 的代价

  • 每个 TIME_WAIT 占用端口+内存
  • 高并发短连接服务器 → 大量 TIME_WAIT → 端口耗尽
# 查看 TIME_WAIT 数量
ss -s | grep TIME-WAIT

# 调优
sysctl net.ipv4.tcp_tw_reuse=1      # 允许复用 TIME_WAIT 端口（推荐）
sysctl net.ipv4.tcp_tw_recycle=0    # 已废弃（NAT 环境有问题）
sysctl net.ipv4.tcp_max_tw_buckets  # TIME_WAIT 上限

HFT 关联

HFT 系统使用长连接（预热+复用），一般不产生大量 TIME_WAIT。但短连接场景（如 HTTP API）需调优。

TCP RST

章级精读：../study.md

本节核心目标

理解 TCP RST（重置）的触发条件和影响。

RST 触发场景

场景 说明
端口未监听 SYN 到未开放端口 → RST
异常关闭 进程崩溃 → 内核发 RST
序号越界 收到不在窗口内的段 → RST
SO_LINGER=0 close() 时立即发 RST（非优雅关闭）
防火墙拦截 防火墙发 RST 中断连接

RST vs FIN

FIN RST
语义 优雅关闭 异常中断
数据交付 缓冲区数据发完 直接丢弃
状态 四次挥手 立即 CLOSED
应用感知 EOF ECONNRESET

代码示例

// SO_LINGER: close() 时发 RST
struct linger lg = { .l_onoff = 1, .l_linger = 0 };
setsockopt(fd, SOL_SOCKET, SO_LINGER, &lg, sizeof(lg));
close(fd);  // 不发 FIN，直接发 RST

HFT 关联

RST 场景 HFT 影响
交易服务器崩溃 RST → 客户端立即感知
防火墙拦截 RST → 连接中断
序号异常 RST → 可能是攻击

排查：Wireshark 过滤 tcp.flags.reset == 1 查看所有 RST。

监听队列与 Backlog

章级精读：../study.md

本节核心目标

理解 TCP 监听队列的组成和 backlog 参数的作用。

两个队列

                    ┌─── 完全建立队列 (Completed) ───┐
Client → SYN → Server → SYN+ACK → Client → ACK → ┌─── 半连接队列 (SYN) ───┐
队列 内容 状态
SYN 队列（半连接） 收到 SYN，发 SYN+ACK，等 ACK SYN_RCVD
Accept 队列（完全建立） 三次握手完成，等 accept() ESTABLISHED

Backlog 参数

listen(fd, backlog);
// backlog = Accept 队列最大长度
// SYN 队列大小由 /proc/sys/net/ipv4/tcp_max_syn_backlog 控制
  • 队列满 → 新连接被丢弃或 RST
  • somaxconn 限制 backlog 上限
# 查看/调整
sysctl net.ipv4.tcp_max_syn_backlog    # SYN 队列上限
sysctl net.core.somaxconn              # Accept 队列上限（默认128，建议调大）

HFT 关联

HFT 交易服务器一般用长连接，backlog 不需要太大。但管理/API 端口可能需要调优：

# 高并发建议
sysctl net.core.somaxconn=65535
sysctl net.ipv4.tcp_max_syn_backlog=65535
