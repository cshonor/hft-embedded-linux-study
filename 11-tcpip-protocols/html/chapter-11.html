11.1

引言

章级精读：../study.md#ch11-1 · 应用层入口：§2.4

本节核心目标

理解 DNS 作为 Internet 分布式电话簿的角色，以及它为什么必须分布式。

核心要点

  • 人类用域名（www.example.com），协议栈用 IP
  • DNS 提供 名字 ↔ 地址（及邮件路由等）映射
  • 与 ch10 UDP/53 承载查询/应答

为什么必须分布式

因素 说明
规模 全球数十亿节点，单库无法维护
延迟 单点查询延迟不可接受
容错 单点故障 = 全网瘫痪
管理 各域自治，不可能全球统一写入

解决方案：分层命名空间 + 委派 + 缓存。

DNS 在协议栈中的位置

应用层:  HTTP → 需要解析 www.example.com
         ↓ 调用 getaddrinfo()
DNS 层:  解析器 → UDP/53 → 递归服务器 → 权威服务器
         ↓ 返回 IP
传输层:  TCP 连接到该 IP

DNS 是应用层的「基础设施」——几乎所有网络应用启动时都需要它。

HFT 关联

场景 DNS 角色
交易服务器连接 预解析 IP，避免运行时 DNS 延迟
行情源发现 组播地址固定，但控制面可能用 DNS
容灾切换 DNS TTL 控制切换速度（但 60s 仍是 HFT 的 eternity）

HFT 最佳实践：启动时解析 + /etc/hosts 硬编码 + 禁用运行时 DNS 查询。

  2. 分布式 DNS 如何保证不同递归器返回一致结果？
  3. HFT 系统为什么应该避免运行时 DNS 查询？

11.2

DNS 名称空间

章级精读：../study.md#ch11-2

本节核心目标

掌握 DNS 倒置树状名称空间结构和委派（Delegation）机制。

树状结构

. (根)
├── TLD (.com, .cn, .org, …)
│   └── SLD (example.com)
│       └── 子域 / 主机名 (www, mail, api, …)
└── ccTLD (.uk, .jp, …)
术语 说明
域 (Domain) 名称空间中的一棵子树，逻辑管理边界
标签 (Label) 点分每一段；单标签 ≤ 63 字节
FQDN 叶到根的完整名，标准以 . 结尾（www.example.com.）
TLD 根下第一层：gTLD（.com）、ccTLD（.cn）

命名语法

  • 单标签 ≤ 63 B；FQDN（含点）≤ 255 B
  • 字符：经典 L-D-H（Letter-Digit-Hyphen）；现代 IDN 国际化域名用 Punycode 编码
www.example.com.       ← FQDN（末尾点表示根）
  │   │      │  │
  │   │      │  └─ 根标签（空）
  │   │      └──── TLD: com
  │   └─────────── SLD: example
  └─────────────── 主机名: www

委派机制

父域通过 NS 记录将子域管理权交给子域的名称服务器：

.com 的 NS 记录中:  example.com → ns1.example.com, ns2.example.com
→ .com 不再管理 example.com 下的具体记录
→ 查询 www.example.com 时，.com 返回 NS 委派信息

核心效果：无单一机构持有全网数据；管理权逐级下放。

域名 vs 主机名

域名 主机名
含义 行政/管理边界 具体节点
关系 可无主机（仅父节点） 必属某域
例子 example.com www.example.com

11.3

名称服务器与区域

章级精读：../study.md#ch11-3

本节核心目标

区分权威服务器与递归服务器，理解区域（Zone）概念和递归解析流程。

Zone（区域）

Zone = 某机构实际托管的连续名称空间（可小于一个"域"）。

术语 说明
委派点 父区通过 NS 把子区管理权交出
Primary 区域唯一写入点（主服务器）
Secondary 区域传输（AXFR/IXFR）同步副本（从服务器）

权威 vs 递归

递归服务器 权威服务器
角色 替客户端跑腿迭代查询 对本区数据负责
典型 ISP/8.8.8.8/企业递归 域名注册商/自托管权威
数据来源 缓存 + 迭代查询 本地区域文件
响应标志 常无 AA AA=1（Authoritative Answer）

根服务器

  • 13 个根 IP（字母 a–m.root-servers.net）
  • 广泛 Anycast → 每 IP 对应全球多物理节点，降延迟、抗 DDoS
  • 并非 13 台机器，而是数百个 Anycast 节点共享 13 个 IP

递归解析五步

1. Client → 递归器 (UDP/53)
2. 递归器 → 根服务器 → 返回 TLD NS 地址
3. 递归器 → TLD NS → 返回权威 NS 地址
4. 递归器 → 权威 NS → 返回 A/AAAA 记录
5. 递归器 → Client (返回结果，可缓存)

每一步递归器都会缓存结果（按 TTL），后续相同查询直接命中缓存。

代码示例

# 追踪完整递归过程
dig +trace www.example.com

# 查询权威服务器
dig @a.iana-servers.net example.com NS

# 查看缓存
dig www.example.com +stats | grep "Query time"

HFT 关联

HFT 系统不应依赖递归 DNS——启动时解析一次，缓存到本地。若必须查询： - 指定可信递归器（dig @8.8.8.8） - 设短超时 + fallback IP - 避免在交易热路径上做 DNS 查询

  3. dig +trace 展示了什么过程？

11.4

DNS 缓存

章级精读：../study.md#ch11-4

本节核心目标

理解 DNS 缓存的弱一致性模型、TTL 机制和迁移实践。

核心概念

术语 说明
TTL 权威设定的记录生存时间（秒）
负缓存 缓存 NXDOMAIN，避免反复无效查询
缓存层级 浏览器 → OS → 递归器 → 权威

TTL 的影响

权威设定 TTL=3600s
  → 递归器缓存 1 小时
  → 全球所有递归器最长 1 小时后刷新
  → 迁移 IP 后最长 1 小时内旧 IP 仍被使用

TTL 是延迟与一致性的折中： - TTL 长 → 缓存命中率高、延迟低 → 但迁移慢 - TTL 短 → 迁移快 → 但查询负载高、延迟增加

迁移实践

1. 迁移前 24-48h: 降低 TTL 到 60s
2. 等待旧 TTL 过期（全球缓存刷新）
3. 切换 IP（更新权威记录）
4. 验证全球递归器返回新 IP
5. 迁移后: 恢复 TTL 到正常值

权威应答 vs 缓存应答

权威应答 缓存应答
AA 标志 AA=1 无 AA
数据来源 本地区域文件 上游递归查询
TTL 原始设定值 剩余倒计时

缓存投毒风险

伪造响应匹配 Transaction ID + 源端口 → 缓存恶意记录。

缓解： - 随机化 Transaction ID（16-bit） - 随机化源端口（16-bit） - DNSSEC 签名验证 - 0x20 编码（大小写随机化）

HFT 关联

场景 策略
交易服务器 IP /etc/hosts 硬编码，跳过 DNS
容灾切换 不依赖 DNS TTL——用 VIP/Anycast 即时切换
监控端点 短 TTL + 主动刷新

  2. 负缓存（NXDOMAIN）有什么价值？TTL 如何设定？
  3. DNS 迁移前为什么要提前降低 TTL？

11.5

DNS 协议

章级精读：../study.md#ch11-5

本节核心目标

掌握 DNS 报文格式、UDP/TCP 选择、EDNS0、核心 RR 类型。

报文结构

┌─────────────────────────────┐
│ Header (12 bytes)            │
│   ID(2) + Flags(2)          │
│   QDCOUNT(2) + ANCOUNT(2)   │
│   NSCOUNT(2) + ARCOUNT(2)   │
├─────────────────────────────┤
│ Question Section             │
├─────────────────────────────┤
│ Answer Section               │
├─────────────────────────────┤
│ Authority Section            │
├─────────────────────────────┤
│ Additional Section           │
└─────────────────────────────┘

首部标志位

位 含义
QR 0=查询，1=响应
Opcode 0=标准 QUERY
AA 权威回答
TC 截断（UDP>512 且无 EDNS0）
RD 期望递归
RA 支持递归
RCODE 0 NoError，2 ServFail，3 NXDOMAIN

传输选择

场景 协议 原因
常规查询 UDP/53 低延迟，一问一答
应答 TC 截断 TCP/53 UDP 容纳不下
区域传输 AXFR/IXFR TCP/53 可靠传输大量数据
DNS over TLS TCP/853 加密
DNS over HTTPS TCP/443 加密 + 穿防火墙

EDNS0

经典 UDP DNS 限制 512B 应答。EDNS0 通过 OPT 伪 RR 扩展：

  • UDP 可 >512B（如 4096）
  • 携带 DNSSEC 数据
  • 扩展 RCODE 空间
# 查询时请求 EDNS0
dig @8.8.8.8 example.com +dnssec +bufsize=4096

核心 RR 类型

类型 用途 示例
A IPv4 example.com. A 93.184.216.34
AAAA IPv6 example.com. AAAA 2606:2800:220:1:...
CNAME 别名 → 规范名 www.example.com CNAME example.com
MX 邮件；含 Preference example.com MX 10 mail.example.com
NS 子区域委派 example.com NS ns1.example.com
SOA 区权威起点 Serial/Refresh/Retry/Expire
PTR 反向解析 34.216.184.93.in-addr.arpa PTR example.com
SRV 服务发现 _sip._tcp.example.com SRV 10 60 5060 sip.example.com
TXT 验证/SPF example.com TXT "v=spf1 -all"

代码示例

# Python: 手动构造 DNS 查询
import socket, struct

def dns_query(domain, dns_server='8.8.8.8'):
    # DNS header: ID=0x1234, RD=1, QDCOUNT=1
    header = struct.pack('!HHHHHH', 0x1234, 0x0100, 1, 0, 0, 0)
    # Question: example.com type=A class=IN
    qname = b''.join(bytes([len(l)]) + l.encode() for l in domain.split('.')) + b'\x00'
    question = qname + struct.pack('!HH', 1, 1)  # type=A, class=IN

    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.sendto(header + question, (dns_server, 53))
    data, _ = sock.recvfrom(512)
    # 解析响应...
    return data

HFT 关联

DNS 特性 HFT 影响
UDP/53 低延迟查询，但无加密
EDNS0 大应答避免 TCP 切换
getaddrinfo 阻塞 网关/代理用 miekg/dns 异步查询
TTL 预解析 + 硬编码避免运行时 DNS

DNS 流量实践

章级精读：../study.md#ch11-6

本节核心目标

理解 DNS 负载均衡、动态更新和工程实践。

DNS 负载均衡

Round Robin

;; 权威返回多条 A 记录，递归器轮转顺序
example.com.  A  1.2.3.4
example.com.  A  1.2.3.5
example.com.  A  1.2.3.6

客户端通常选第一个 → 不同客户端得到不同顺序 → 简单负载均衡。

基于地理/延迟的 DNS

  • GeoDNS：根据客户端 IP 地理位置返回最近服务器
  • 延迟路由：探测 RTT 返回最低延迟节点
  • 健康检查：移除不可用节点的记录

动态更新（DDNS）

DHCP 分配 IP 后，客户端向权威服务器提交 RR 变更：

# nsupdate 命令
nsupdate <<EOF
server ns1.example.com
zone example.com
update delete host1.example.com. A
update add host1.example.com. 300 A 192.168.1.100
send
EOF

关联：ch06 DHCP

区域传输

类型 说明
AXFR 全量区域传输（整个 zone 文件）
IXFR 增量区域传输（仅变更部分）
传输协议 TCP/53
触发 Secondary 检测 SOA Serial 增大

Go/Rust 高并发 DNS

// Go: 使用自定义解析器
resolver := &net.Resolver{
    PreferGo: true,
    Dial: func(ctx context.Context, network, address string) (net.Conn, error) {
        d := net.Dialer{Timeout: 2 * time.Second}
        return d.DialContext(ctx, "udp", "8.8.8.8:53")
    },
}
ips, err := resolver.LookupHost(ctx, "example.com")
  • getaddrinfo 阻塞 → 高并发用 miekg/dns 或 hickory-dns 自实现 UDP 查询
  • Go net.Resolver 支持 context 超时 + 自定义 Dial

HFT 关联

实践 HFT 应用
GeoDNS 交易节点选择最近的行情源
健康检查 DNS 自动剔除故障节点
短 TTL 容灾切换（但不如 VIP 即时）

OpenDNS / DynDNS

章级精读：../study.md#ch11-6

本节核心目标

公共 DNS 解析器

服务 IP 特色
Google 8.8.8.8 / 8.8.4.4 全球 Anycast、EDNS0
Cloudflare 1.1.1.1 / 1.0.0.1 隐私优先、DoH/DoT
OpenDNS 208.67.222.222 过滤恶意域名

动态 DNS (DDNS)

动态 IP 环境（家庭宽带、移动网络）中，客户端 IP 会变化。DDNS 让域名自动跟踪 IP 变化：

1. 客户端检测公网 IP 变化
2. 向 DDNS 服务商发送更新请求
3. 服务商更新权威 DNS 记录
4. 外部用户通过域名连接到新 IP

常见 DDNS 服务：DynDNS、No-IP、DuckDNS。

HFT 关联

HFT 系统一般不使用公共 DNS 或 DDNS——数据中心环境 IP 固定，DNS 仅用于初始发现。

但跨数据中心 WAN 连接可能涉及： - 动态路由 + DNS fallback - 公网 DNS 做健康检查探针

11.9

DNS 与 IPv6 过渡

章级精读：../study.md#ch11-9

本节核心目标

理解双栈环境下的 DNS 查询策略和 Happy Eyeballs 机制。

双栈 DNS

记录类型 地址 查询顺序
A IPv4 递归器并行或先查
AAAA IPv6 递归器并行或后查

双栈主机同时发起 A + AAAA 查询，选择策略因实现而异。

Happy Eyeballs (RFC 6555)

问题：IPv6 查询先返回但连接失败 → 白等 IPv6 超时再回退 IPv4。

解决方案：

1. 并行解析 A + AAAA
2. 优先尝试 IPv6 连接（如有 AAAA 记录）
3. 设短超时（~250ms）→ v6 失败快速回退 v4
4. 后续连接优先使用成功的地址族

// getaddrinfo 的 RFC 6555 实现
struct addrinfo *result;
getaddrinfo("example.com", "443", &hints, &result);
// 现代系统在 connect 时实现 Happy Eyeballs
// 幕后: 并行尝试 v6 + v4，先连上的赢

NAT64/DNS64

IPv6-only 客户端访问 IPv4-only 服务：

                                    ↑ NAT64 前缀

HFT 建议：固定使用 IPv4 或 IPv6，不做 Happy Eyeballs fallback。

mDNS / LLMNR

章级精读：../study.md#ch11-10 · 组播：ch09

本节核心目标

理解局域网零配置名称解析协议：mDNS 和 LLMNR。

协议对比

协议 端口 地址 特点
mDNS (RFC 6762) UDP/5353 224.0.0.251 / FF02::FB .local，Apple Bonjour
LLMNR (RFC 4795) UDP/5355 224.0.0.252 / FF02::1:3 Microsoft，更广 TLD

mDNS 工作原理

1. 主机 A 查询: "printer.local" → 组播 224.0.0.251:5353
2. 打印机收到 → 单播响应: "printer.local A 192.168.1.50"
3. 主机 A 直接连接
  • 无需 DNS 服务器
  • 无需配置
  • 仅限局域网（组播 TTL=1）

.local 域名

  • .local 是 mDNS 的保留 TLD
  • 查询 .local 时系统优先用 mDNS 而非传统 DNS
  • 注意：企业环境中 .local 可能冲突

HFT 关联

HFT 系统一般不使用 mDNS——所有地址应预配置。但数据中心运维工具（如 IPMI/BMC 发现）可能用到 mDNS/Bonjour。

LDAP 概述

章级精读：../study.md#ch11-10

本节核心目标

DNS vs LDAP

DNS LDAP
定位 名 → IP 快速映射 复杂属性查询
数据模型 扁平树 + 简单 RR 层次目录 + 丰富属性

[邮件服务器] → LDAP 查询 → 获取邮件路由地址

DNS 安全威胁

章级精读：../study.md#ch11-12 · 网络安全：ch18

本节核心目标

掌握 DNS 主要攻击面及缓解策略。

缓存投毒

原理：伪造 DNS 响应，匹配 Transaction ID + 源端口 → 递归器缓存恶意记录。

攻击变体 机制
Kaminsky 攻击 发海量伪造响应，提高 Transaction ID 碰撞概率
生日攻击 大量并行查询 + 伪造响应 → 概率碰撞

缓解： - 随机化 Transaction ID（16-bit → 65536 种可能） - 随机化源端口（16-bit → ~64000 种可能） - 合计搜索空间 ~2^32 → 投毒难度大幅提高 - DNSSEC 签名验证（终极方案） - 0x20 编码（查询名大小写随机化） - QNAME 最小化

放大 DDoS

攻击者 → DNS 服务器（伪造源 IP = 受害者）
  查询: "ANY ." + EDNS0（30B 请求）
  响应: 3000B → 打向受害者
  放大率: ~100x

缓解： - BCP38 源地址校验 - 服务器限速 - 禁用 ANY 查询（现代 DNS 服务器默认）

DNSSEC

概念 说明
签名链 根 → TLD → 权威，逐级签名
RRSIG 记录的数字签名
DNSKEY 公钥
DS 委派签名（父区对子区公钥的哈希签名）
验证 递归器验证签名链 → 拒绝伪造应答

DNSSEC 不加密 DNS 流量，仅验证数据完整性 + 来源真实性。

HFT 关联

威胁 HFT 影响
缓存投毒 交易流量被导向恶意服务器 → 信息泄露/伪造交易
放大 DDoS 网络拥塞 → 行情/交易延迟
DNSSEC 验证延迟 增加 DNS 查询时间

HFT 建议：硬编码 IP + VPN/专线 + 不依赖公网 DNS。
