15.1

引言

章级精读：../study.md#ch15-1 · TCP 基础：ch12

本节核心目标

理解 TCP 作为闭环反馈控制系统的核心矛盾：交互式低延迟 vs 成块高吞吐。

数据流类型

类型 目标 典型
交互式 低延迟 SSH 按键、远程 shell
成块 高吞吐（填满 BDP） FTP、大文件、视频

矛盾：交互产生大量 tinygram（1B 数据 + 40B 头 → 开销极高）；需抑制小包又不致用户可感延迟。

发送决策

可发数据量 = min(Advertised Window, Congestion Window) - Flight Size
             ↑ 接收方限制        ↑ 网络限制            ↑ 已发未确认

综合 Flight Size（在途）与 Advertised Window（对端通告）判断是否可发新数据。

HFT 关联

场景 流控影响
交易订单（小包） Nagle + Delayed ACK 死锁 → 延迟毛刺
行情回放（大包） 窗口大小决定吞吐
TCP 控制面 rwnd 过小 → 限制指令速率

  2. 发送决策中 rwnd 和 cwnd 各自限制什么？
  3. HFT 交易订单为什么容易遇到 Nagle 死锁？

15.2

交互式通信

章级精读：../study.md#ch15-2

本节核心目标

理解交互式数据流的开销和延迟特征。

交互模式

  • 每键一字节 → 一包（Rlogin/SSH）
  • 有效载荷占比：1B 数据 + ~40B 头（20 IP + 20 TCP）→ PPS 压力巨大

Rlogin 回显四步

1. Client → Server: 按键 1B
2. Server → Client: ACK
3. Server → Client: 回显数据
4. Client → Server: ACK

高 RTT 下每键可见延迟 ≈ 2×RTT；10 键/s ≈ 40 报文/s（未优化时）。

优化

优化 效果
Delayed ACK 减少 ACK 数量（合并第2/3步）
Nagle 合并小包
TCP_NODELAY 禁用 Nagle → 交互延迟降低

HFT 关联

HFT 的 TCP 控制面（如管理指令、日志）类似交互式流——小包、延迟敏感。TCP_NODELAY 是标准配置。

自测题

  1. Rlogin 回显为什么需要 4 步？如何减少到 2 步？
  2. 交互式流的头部开销占比有多大？
  3. 为什么 SSH 默认开启 TCP_NODELAY？

15.3

延时确认 (Delayed ACK)

章级精读：../study.md#ch15-3

本节核心目标

理解 Delayed ACK 的工作原理及其与 Nagle 的死锁问题。

核心概念

接收端暂缓纯 ACK，提高带宽利用率、支持捎带。

概念 说明
Delayed ACK 计时器 常 200ms 量级
捎带（Piggybacking） ACK 嵌入本端反向数据段
触发立即 ACK 收到第二个全尺寸 MSS 段

规则

  1. 收到数据后不立即 ACK，短时等待本端响应数据
  2. 必须发 ACK：计时器到点；或收到第二个 MSS 段

与 Nagle 的经典死锁

1. 发送方: 发 1B → 等 ACK（Nagle 阻塞后续小包）
2. 接收方: 收 1B → 启动延迟 ACK，应用暂无数据可捎带
3. 发送方: 应用再产生小数据 → Nagle 仍禁止发
4. 直至接收方 ~200ms 后强发 ACK → 发送方才能继续

结果：交互应用可出现 ~200ms 卡顿。

Linux 参数

# 快速 ACK 数量（初始阶段发送的立即 ACK 数）
sysctl net.ipv4.tcp_quickack     # 默认 0（关闭快速 ACK）
# 注意: tcp_quickack=1 不是持久设置，内核会自动回退到延迟 ACK

HFT 关联

Delayed ACK 的 200ms 延迟对 HFT 不可接受。解决： - TCP_NODELAY 禁用 Nagle（发送方） - TCP_QUICKACK 禁用 Delayed ACK（接收方，需定期重设） - 或直接用 UDP

自测题

  1. Delayed ACK 为什么能减少 ACK 数量？
  2. Delayed ACK + Nagle 死锁的根因是什么？如何解除？
  3. TCP_QUICKACK 为什么不是持久的？

15.4

Nagle 算法

章级精读：../study.md#ch15-4

本节核心目标

掌握 Nagle 逻辑、与 Delayed ACK 死锁及 TCP_NODELAY 的工程选择。

核心逻辑

发送端整形：自时钟 — 「链路上最多一个未确认的小分组」。

规则：若待发 < MSS 且仍有在途未确认数据 → 缓存，不立即发。

if (待发数据 < MSS && 有在途未确认数据)
    缓存，等 ACK 或攒够 MSS 再发
else
    立即发

目的：抑制 tinygram 风暴（RFC 896）

Nagle + Delayed ACK 死锁

方 行为
发送方 (Nagle) 等 ACK 才发下一小包
接收方 (Delayed ACK) 等更多数据才回 ACK

→ 周期性 几十～几百 ms 延迟毛刺

禁用 Nagle

// C: 禁用 Nagle
int val = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &val, sizeof(val));

// Go: TCPConn 默认已 NoDelay=true
conn.SetNoDelay(true)  // 实际上 Go 默认就是 true

// Rust: TcpStream 默认 Nagle 开启 → 需显式禁用
stream.set_nodelay(true)?;

何时开/关 Nagle

场景 Nagle 原因
交互/实时（SSH, 游戏, RPC） 关 (NODELAY) 延迟优先
大文件传输 开 合并小包提高效率
HFT 交易订单 关 延迟绝对优先
批量数据导入 开 吞吐优先

HFT 关联

HFT 交易系统必须 TCP_NODELAY——一个 200ms 的 Nagle 延迟可能导致错失套利机会。但同时要确保对端不做 Delayed ACK，否则即使关了 Nagle 仍有延迟。

  1. Nagle 算法的"自时钟"是什么意思？
  2. 为什么 Go 的 net.Dial 默认 NoDelay=true？
  3. 关掉 Nagle 后仍可能有延迟毛刺，原因是什么？

15.5

流量控制与窗口管理

章级精读：../study.md#ch15-5 · WSCALE：ch13

本节核心目标

掌握 Advertised Window（rwnd）机制、滑动窗口、零窗口、SWS、Autotuning。

滑动窗口

| 已确认 | 已发未确认(在途) | 可发(可用窗口) | 不可发 |
  ^左沿      ^SND.NXT          ^右沿
  ← ACK 推进左沿          ← rwnd 限制右沿
术语 含义
Advertised Window (rwnd) 接收方通告的接收能力
Usable Window rwnd − 已发未确认
左沿 已确认边界；随 ACK 右移
右沿 左沿 + rwnd
SND.NXT 下一待发送字节

rwnd vs cwnd

rwnd cwnd
解决 接收方慢 网络堵
谁通告 接收方 TCP 首部 发送方自行估算
有效发送 min(rwnd, cwnd) 同左

零窗口与 Persist Timer

通告窗口 = 0 → 发送方停发。若窗口更新丢失 → 永久死锁。

Persist Timer：周期发 Window Probe（1 字节探测），迫使对端 ACK 中带新窗口。

糊涂窗口综合征 (SWS)

接收方通告极小窗口 + 发送方发极小段 → 链路被头部占满。

方 对策
接收方（Clark） 除非可增 ≥1 MSS 或 ≥缓冲区一半，否则不增大通告窗
发送方 仅当数据达 MSS、收到 ACK、或满足 Clark 阈值才发

大缓存与 Autotuning

LFN / 大 BDP 需 Window Scale（突破 64KB）。

# Linux Autotuning
sysctl net.ipv4.tcp_window_scaling    # 默认 1
sysctl net.ipv4.tcp_rmem              # 接收缓冲 min/default/max
# Autotuning 动态调 SO_RCVBUF，填满管道

HFT 关联

机制 HFT 策略
TCP_NODELAY 交易控制面必开
窗口大小 确保足够大，不限制吞吐
Autotuning 数据中心低延迟环境一般够用
零窗口 监控接收方是否读太慢

紧急机制 (Urgent)

章级精读：../study.md#ch15-6

本节核心目标

理解 TCP 紧急数据机制的原理和现代使用状况。

机制

字段 说明
URG 标志 存在紧急数据
Urgent Pointer 指向紧急数据末字节之后的偏移（加在 SEQ 上）

接收方可 SIGURG 等异步通知。

与带外数据的区别

TCP 的"紧急"并非真正的带外数据——紧急数据仍在正常数据流中，只是用 Urgent Pointer 标记位置。真正的带外数据需要不同的机制。

现代使用

场景 是否使用
Telnet 中断信号 历史用途
新设计 不推荐——用独立连接或应用层信令
跨平台兼容性 差——OS 实现各异 
// 发送紧急数据（不推荐新设计使用）
send(fd, "X", 1, MSG_OOB);
// 接收方收到 SIGURG 信号

HFT 关联

HFT 系统不使用 TCP 紧急机制——用独立 UDP 信令或专用控制连接更可靠。

窗口相关攻击

章级精读：../study.md#ch15-7 · 安全：ch18

本节核心目标

理解针对 TCP 窗口机制的攻击及防御。

窗口缩减攻击

伪造 ACK 使通告窗口异常缩小（右沿左移）→ 发送方已发数据超出收缩后窗口 → 状态紊乱 → RST 或截断 → DoS。

防御

防御 说明
序列号验证 检查 ACK 序列号在窗口内
窗口收缩限制 RFC 7323 等规范限制窗口缩减行为
加密 TLS/IPSec 防止注入伪造 ACK

HFT 关联

HFT 交易链路应使用加密（TLS/专线）防止窗口攻击——未加密的 TCP 在公共网络上易受此类攻击。

本章总结

章级精读：../study.md#ch15-exam · QUICKREF：../QUICKREF.md

核心算法矩阵

机制 责任方 目标 影响
Nagle 发送方 抑制小包 交互延迟；与延迟 ACK 死锁
延迟 ACK 接收方 少纯 ACK、捎带 可能拖慢窗口滑动
滑动窗口 双方 端到端流控 理论吞吐上界（与 cwnd 取 min）
Persist 发送方 破零窗口死锁 极端负载存活
Clark / SWS 接收方 防糊涂窗口 成块传输效率

工程清单

  • 交互延迟：NODELAY + 考虑对端延迟 ACK
  • 大文件：勿 NODELAY；开 WSCALE、Autotuning
  • 零窗口：查 Persist / 应用读太慢

HFT 核心关联

机制 HFT 策略
Nagle 必须 TCP_NODELAY
Delayed ACK TCP_QUICKACK 或用 UDP
窗口大小 确保不限制吞吐
SWS 内核自动处理
