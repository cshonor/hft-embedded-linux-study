16.1

引言

章级精读：../study.md#ch16-1 · 流控：ch15

本节核心目标

理解拥塞控制与流量控制的区别，掌握 cwnd 的角色。

核心概念

术语 说明
拥塞 入网流量逼近/超过链路或缓冲能力 → 时延↑、丢包
cwnd 发送方据网络状况限制在途数据
发送窗口 W W = min(cwnd, awnd)（awnd = 通告窗口）

流控 vs 拥塞控制

流量控制 拥塞控制
反馈 显式（rwnd） 隐式（丢包、时延、ECN）
范围 端到端接收能力 全网路径
谁负责 接收方 发送方自行估算

工作点

吞吐
 ↑         ╱ ← 理想工作点（膝部 Knee）
 │       ╱
 │     ╱
 │   ╱
 │ ╱ ← 崖部 (Cliff) 拥塞崩溃
 └────────────→ 负载

膝部：高吞吐、低时延；崖部：拥塞崩溃。

HFT 关联

拥塞控制 HFT 影响
cwnd 限制 TCP 吞吐受限 → 大文件传输慢
AIMD 降速 丢包后吞吐突降 → 延迟增加
ECN 可提前降速避免丢包

HFT 行情用 UDP 组播，不受 TCP AIMD 影响——这是选择 UDP 的关键原因之一。

16.2

经典算法

章级精读：../study.md#ch16-2

本节核心目标

掌握 慢启动、拥塞避免、Tahoe/Reno 与 AIMD 哲学。

AIMD 哲学

无拥塞时加性增，拥塞时乘性减：

无拥塞: cwnd += 1/RTT  (线性增长)
拥塞:   cwnd *= 0.5    (减半)

为什么不是线性减？因为拥塞是"全员"问题——乘性减让所有流同时降速，快速缓解拥塞。

慢启动 (Slow Start)

  • 初值：cwnd = 1×SMSS（量级）
  • 每收到一个 ACK → cwnd +1 → 每个 RTT 约翻倍（指数增长）
  • 直至 cwnd ≥ ssthresh → 切换到拥塞避免

「慢」是相对旧协议一次发满 awnd 而言——实际增长很快（指数）。

RTT 0: cwnd=1
RTT 1: cwnd=2
RTT 2: cwnd=4
RTT 3: cwnd=8
RTT 4: cwnd=16

拥塞避免 (Congestion Avoidance)

  • cwnd ≥ ssthresh：每 RTT cwnd += 1（每 ACK +1/cwnd）→ 线性增长
RTT 0: cwnd=16
RTT 1: cwnd=17
RTT 2: cwnd=18

拥塞检测

信号 典型反应
超时 cwnd→1，ssthresh=cwnd/2（最狠）
3 dup ACK 快速重传/恢复（较温和）

Tahoe vs Reno

算法 丢包信号 反应
Tahoe 3 dup ACK 或超时 cwnd=1，慢启动
Reno 3 dup ACK 快速恢复：ssthresh=cwnd/2，cwnd=ssthresh+3
Reno 超时 cwnd=1，慢启动（同 Tahoe）

快速恢复细节：恢复期每多 1 dup ACK → cwnd+1；收到新 ACK → cwnd=ssthresh，退出。

代码示例

# 查看 Linux 拥塞控制算法
sysctl net.ipv4.tcp_congestion_control
# 输出: cubic (默认)

# 查看可用算法
sysctl net.ipv4.tcp_available_congestion_control
# 输出: reno cubic bbr

# 查看连接的 cwnd
ss -ti
# 输出示例: cubic wscale:7,7 rto:280 rtt:12.5/5 cwnd:10 ssthresh:20

HFT 关联

算法 HFT 影响
慢启动 新连接初始吞吐低 → 预热连接
AIMD 丢包后吞吐减半 → 延迟增加
CUBIC Linux 默认，HFT 控制面够用

16.3

对标准算法的改进

章级精读：../study.md#ch16-3

本节核心目标

了解 NewReno、SACK+CC、FACK、Limited Transmit、CWV 等改进。

NewReno

问题：Reno 在多包同窗丢失时可能多次减半。

解决：用部分 ACK（Partial ACK）在快速恢复中连续补洞，不退出直到所有丢失段确认。

Reno: 丢3个包 → 3次快速恢复 → cwnd 减半3次 = 1/8
NewReno: 丢3个包 → 1次快速恢复 → cwnd 减半1次 = 1/2

SACK + 拥塞控制

Scoreboard 精确定位空洞 → 少无效重传 → 丢包期维持较高有效利用率。

FACK (Forward ACK)

用 SACK 信息更激进推断丢包 → 更快调整 cwnd。

Rate Halving

拥塞后每 2 ACK 发 1 新包 → 平滑替代 Reno 瞬时 cwnd 跳变。

Limited Transmit

窗口小、dup ACK 1–2 个时允许发 1 新段 → 凑够 3 dup ACK → 触发快速重传 → 避免 RTO。

CWV (Congestion Window Validation)

长闲置连接 缩小陈旧 cwnd，避免闲置后突发冲击。

# Linux: 闲置后 cwnd 验证
sysctl net.ipv4.tcp_slow_start_after_idle  # 默认 1
# 设为 0 可禁用闲置后慢启动（HFT 可能需要）

HFT 关联

改进 HFT 价值
NewReno 多包丢失恢复更好
SACK 高 BDP 链路必备
Limited Transmit 小窗口场景避免 RTO
CWV 预热连接后保持 cwnd

自测题

  1. NewReno 的 Partial ACK 是什么？它如何避免多次减半？
  2. Limited Transmit 如何帮助小窗口连接？
  3. CWV 解决了什么问题？

16.4

伪 RTO：Eifel 响应

章级精读：../study.md#ch16-4 · 伪超时：ch14 §14.7

本节核心目标

理解伪超时对拥塞控制的影响和 Eifel 响应的撤销机制。

问题

无线等导致 RTT 尖峰 → 伪超时 → cwnd 无谓减半 → 性能雪崩。

正常: cwnd=20, ssthresh=∞
伪超时: cwnd=1, ssthresh=10 → 吞吐崩塌
即使发现是伪超时 → cwnd 已被错误降低 → 需要时间恢复

Eifel 检测

用时间戳（TSOPT）判断 ACK 对应原传还是重传：

原始段 TS=1000 → 丢失
重传段 TS=1000 → 到达
ACK TSecr=1000 → 但到达时间极早 → 原始段其实到了（伪超时）

Eifel Response

伪超时确认后 → 撤销 ssthresh/cwnd 削减 → 恢复到超时前的拥塞状态。

HFT 关联

HFT 有线环境伪超时少见，但跨数据中心 WAN 可能遇到路径切换尖峰。保持 tcp_timestamps=1 是基础。

自测题

  3. Eifel Response 撤销了什么操作？

16.5

扩展示例

章级精读：../study.md#ch16-5

本节核心目标

通过多丢包 + SACK 的完整状态机走查，理解算法协作。

场景

发送 10 个段 (seq=1 ~ 10001)
丢失: seq=1001, seq=5001
SACK: [2001:5000] [6001:10000]

状态机流转

1. 3 dup ACK (SACK: [2001:5000]) → 快速重传 seq=1001
2. cwnd 减半, ssthresh = cwnd/2
3. SACK 更新: [2001:5000] [6001:10000]
4. 重传 seq=5001
5. 收到新 ACK (确认到 10001) → 退出快速恢复
6. 拥塞避免: cwnd 线性增长

NewReno 在步骤 2-4 之间不退出快速恢复，直到所有空洞补完。

16.7

TCP 友好性

章级精读：../study.md#ch16-5

本节核心目标

理解非 TCP 流量为何需要自律，以及"TCP 友好"的含义。

问题

非 TCP（如 UDP 视频流、实时流）若不降速 → 饿死 TCP 流（TCP 丢包就减半，UDP 不减）。

TCP 友好定义

非 TCP 流量的长期吞吐不超过同条件下 TCP 流的吞吐。即模拟 AIMD 自律。

UDP 流量: 监测丢包 → 主动降速（类似 TCP AIMD）
→ 与 TCP 公平共享带宽

实践

协议 友好策略
RTP/RTCP 基于 RTCP 反馈调整编码速率
WebRTC GCC (Google Congestion Control)
QUIC 内置拥塞控制（CUBIC 或 BBR）

HFT 关联

HFT UDP 组播行情不做 TCP 友好——行情必须以最低延迟送达，不能因网络拥塞而降速。但应通过 QoS/DSCP 标记和专用带宽隔离，避免影响其他流量。

16.8

高速 TCP：CUBIC

章级精读：../study.md#ch16-8

本节核心目标

理解标准 TCP 在高 BDP 链路的瓶颈和 CUBIC 算法。

LFN 问题

标准 TCP 线性增 cwnd → 填满高 BDP 需数千 RTT。

BDP = 10Gbps × 100ms = 125MB → cwnd 需 ~87000 MSS
线性增长: 87000 RTT ≈ 8700s ≈ 2.4 小时才填满！

BIC / CUBIC

CUBIC（Linux 默认）：W(t) = C(t-K)³ + W_max

  • 三次函数曲线
  • 远离上次丢包点：快增
  • 接近推测容量（W_max）：缓增
  • 超过 W_max 后继续探测新上限
cwnd
 ↑          ╱ ← 超过 W_max 继续探测
 │        ╱
 │      ╱ ← 接近 W_max 缓增
 │    ╱
 │  ╱ ← 远离 W_max 快增
 │╱ ← 丢包后从 W_max/2 开始
 └────────────→ 时间

Linux 配置

# 查看当前算法
sysctl net.ipv4.tcp_congestion_control
# 输出: cubic

# 切换到 BBR
sysctl -w net.ipv4.tcp_congestion_control=bbr

# BBR 需要 fq qdisc
tc qdisc add dev eth0 root fq

HFT 关联

算法 HFT 影响
CUBIC Linux 默认，控制面够用
BBR 基于带宽探测，丢包不降速 → 可能影响延迟可预测性
HFT 专用 行情走 UDP 不受影响

16.9

基于延迟的拥塞控制

章级精读：../study.md#ch16-8

本节核心目标

理解 Vegas / FAST 等基于延迟的拥塞控制算法。

丢包型 vs 延迟型

丢包型（Reno/CUBIC） 延迟型（Vegas）
信号 事后丢包 RTT 微增预测
反应 cwnd 减半 cwnd 微调
竞争 — 常对 CUBIC 过早谦让

Vegas 原理

ExpectedRate = cwnd / BaseRTT  (最小 RTT 时的理论速率)
ActualRate = cwnd / RTT        (当前实际速率)

Diff = ExpectedRate - ActualRate
  Diff < α → cwnd 增 (未拥塞)
  Diff > β → cwnd 减 (开始拥塞)
  α < Diff < β → cwnd 保持

核心思想：RTT 开始增大但还没丢包时，就认为拥塞即将来临 → 提前降速。

为什么 Vegas 不流行

Vegas 在与 CUBIC 竞争时过早谦让——CUBIC 不看延迟一直增长直到丢包 → Vegas 先退让 → 带宽被 CUBIC 抢占。

BBR (Google)

BBR 不是传统延迟型，而是基于带宽探测： - 测量瓶颈带宽 + 最小 RTT - cwnd = BDP × gain - 丢包不降速（与传统 TCP 根本不同）

# 启用 BBR
sysctl -w net.ipv4.tcp_congestion_control=bbr
# 需要 kernel 4.9+

HFT 关联

BBR 对 HFT 控制面可能有利——丢包不降速意味着延迟更可预测。但 BBR 的探测行为可能引入周期性延迟波动。

16.10

Bufferbloat

章级精读：../study.md#ch16-10

本节核心目标

理解路由器过大缓冲导致的 Bufferbloat 问题。

问题

路由器过大缓冲 → 排队时延秒级 → TCP 反馈迟钝。

传统: 路由器缓冲小 → 丢包快 → TCP 快速降速
Bufferbloat: 路由器缓冲大 → 排队不丢包 → RTT 暴涨 → TCP 不降速 → 延迟堆积

影响： - 交互延迟（SSH/游戏/交易）可达秒级 - TCP 拥塞控制失效（丢包信号来得太晚） - "网络感觉很慢"但带宽没用满

AQM (Active Queue Management)

机制 作用
RED 队列介于 min_th–max_th 时概率丢/标；减全局同步
CoDel 基于队列停留时间而非长度丢包
FQ-CoDel Flow Queue + CoDel → 公平 + 低延迟
fq Linux 默认 qdisc，配合 BBR

Linux QoS

# 查看 qdisc
tc qdisc show dev eth0

# 设置 fq-codel（推荐）
tc qdisc replace dev eth0 root fq_codel

# 设置 fq（配合 BBR）
tc qdisc replace dev eth0 root fq

HFT 关联

Bufferbloat 对 HFT 致命——交换机/路由器大缓冲导致微秒级行情延迟变毫秒级。数据中心应： - 配置交换机小缓冲 / AQM - 使用 PFC（Priority Flow Control）而非大缓冲 - HFT 流量标记高优先级 DSCP

  2. RED 如何减少全局同步？
  3. FQ-CoDel 的优势是什么？

16.11

AQM 与 ECN

章级精读：../study.md#ch16-10 · IP DS/ECN：ch05 §5.2

本节核心目标

理解 AQM（主动队列管理）和 ECN（显式拥塞通知）的工作原理。

ECN 流程

1. 路由器: 队列增长 → 在 IP 头标 CE (Congestion Experienced)
2. 接收端: 收到 CE 标记 → TCP ACK 中设 ECE 标志
3. 发送方: 收到 ECE → 降 cwnd → 在后续段设 CWR (Congestion Window Reduced)
4. 接收端: 收到 CWR → 停止设 ECE

核心价值：不丢包就降速 → 避免重传开销 → 延迟更低。

ECN 标记位

IP 头 DSCP 字段 含义
00 Not-ECT（不支持 ECN）
01/10 ECT(1)/ECT(0)（支持 ECN）
11 CE（拥塞经历）
TCP 标志 含义
ECE ECN-Echo：告知对端"我收到了 CE 标记的包"
CWR Congestion Window Reduced：告知"我已降速"

Linux 配置

# 启用 ECN
sysctl net.ipv4.tcp_ecn    # 默认 1 (启用)
# 0=禁用, 1=启用(主动), 2=启用(被动)

# qdisc 配合
tc qdisc replace dev eth0 root fq_codel ecn

HFT 关联

ECN 对 HFT 有价值——不丢包就降速意味着延迟更可预测。但需要全路径（所有路由器/交换机）支持 ECN 标记。数据中心内部通常可以做到。

16.12

拥塞相关攻击

章级精读：../study.md#ch16-10 · 安全：ch18

本节核心目标

理解利用 TCP 拥塞控制机制的攻击及防御。

攻击类型

攻击 机制 防御
ACK 分割 拆 ACK 诱导按个数增 cwnd 按 ACK 确认的字节数更新 cwnd
Opt-ACK 数据未到先发 ACK → 发送方疯狂增 cwnd 验证序号合理性
LDoS 周期性脉冲触发超时退避 加密 + 限速
ECN 伪造 伪造 CE 标记 → 发送方误降速 加密 (TLS/IPSec)

ACK 分割攻击

正常: 收到 1000B → 1 个 ACK → cwnd +1
攻击: 收到 1000B → 拆成 1000 个 1B ACK → cwnd +1000
→ 发送方 cwnd 暴涨 → 网络拥塞

防御：按 ACK 确认的字节数（而非 ACK 个数）更新 cwnd。现代 TCP 实现已修复。

HFT 关联

攻击 HFT 影响
LDoS 交易连接周期性中断
ECN 伪造 交易连接降速
Opt-ACK cwnd 暴涨导致突发 → 延迟波动

防御：加密 + 专线 + 监控 cwnd 异常变化。

易混速记

问题 要点
rwnd vs cwnd rwnd=接收方限制，cwnd=网络限制
发送窗口 min(rwnd, cwnd)
慢启动 指数增长（每 RTT 翻倍），"慢"是相对旧协议
拥塞避免 线性增长（每 RTT +1）
超时 vs 快速重传 超时 cwnd=1（狠）；快速恢复 cwnd/2（温和）

HFT 核心关联

拥塞控制机制 HFT 策略
AIMD 降速 行情走 UDP 不受影响
慢启动 预热 TCP 控制面连接
CUBIC/BBR 控制面够用，热路径不依赖
ECN 数据中心可启用，减少丢包
Bufferbloat 交换机小缓冲 + AQM

核心结论：TCP 拥塞控制为"公共资源公平"设计，与 HFT"最低延迟优先"理念冲突。HFT 热路径用 UDP + QoS 隔离。
