14.1

引言

章级精读：../study.md#ch14-1 · TCP 基础：ch12

本节核心目标

理解 TCP 可靠性的两层防御：快速重传（主动）和 RTO 计时器（被动）。

两层防御

层次 机制 触发条件 反应速度
主动 快速重传 3 个重复 ACK ~1 RTT
被动 RTO 计时器 无 ACK 到达 RTO（常 200ms-1s+）

主动防御快但需要足够多的在途数据产生 dup ACK；被动防御慢但覆盖所有场景。

为什么需要两层

场景1: 单包丢失，窗口大 → 3 dup ACK → 快速重传（快）
场景2: 尾包丢失，无后续数据 → 无 dup ACK → RTO 超时（慢）
场景3: 窗口极小 → 1-2 dup ACK 不足 → RTO 超时

HFT 关联

场景 影响
TCP 交易链路重传 RTO 过大 → 订单延迟尖峰
丢包检测 快速重传 vs RTO 差距可达 10x
调优 tcp_retries2 控制最大重传次数

HFT 更倾向 UDP + 应用层可靠性——TCP 重传的指数退避对延迟敏感场景不友好。

  2. 为什么窗口极小时 RTO 是唯一兜底？
  3. tcp_retries2 和 tcp_syn_retries 的区别是什么？

14.2

简单超时与重传

章级精读：../study.md#ch14-2

本节核心目标

理解基本的超时重传机制和指数退避。

超时重传流程

0.000s  发送 seq=1:1025
1.500s  超时 → 第1次重传 seq=1:1025（间隔 RTO）
4.500s  超时 → 第2次重传（间隔 ×2 = 3s）
10.500s 超时 → 第3次重传（间隔 ×2 = 6s）
22.500s 超时 → 第4次重传（间隔 ×2 = 12s）

指数退避

重传次数 间隔（初 RTO≈1.5s） 累计等待
1 1.5s 1.5s
2 3s 4.5s
3 6s 10.5s
4 12s 22.5s
5 24s 46.5s

本质：拥塞时主动降注入（保守）。RTO 过小 → 伪重传浪费带宽；过大 → 吞吐崩塌。

Linux 参数

# tcp_retries2: 已建立连接的最大重传次数（默认15）
#   超过后放弃连接
sysctl net.ipv4.tcp_retries2

# tcp_retries1: 重传次数达到后开始报告错误（默认3）
sysctl net.ipv4.tcp_retries1

HFT 关联

TCP 指数退避对 HFT 不友好——丢包后第二次重传就等 3s，远超交易容忍。这就是为什么 HFT 倾向： - UDP 组播 + 应用层 FEC - 专线/Dedicated Link 无丢包 - TCP 仅用于非延迟敏感的控制面

  1. 指数退避为什么是乘性增加而非固定间隔？
  2. tcp_retries2=15 大约会等多久才放弃连接？
  3. 为什么 HFT 系统不适合用 TCP 做行情传输？

14.3

设置重传超时 (RTO)

章级精读：../study.md#ch14-3 · 时间戳：ch13 §13.3

本节核心目标

掌握 RTT 估计 → RTO 计算、Jacobson/Karels 算法、Karn 算法、RTTM。

RTT 与 RTO

网络动态变化 → 持续测量 RTT，推导 RTO。RTO 不能是固定常数。

经典方法 (RFC 793)

SRTT ← α·SRTT + (1-α)·RTT_sample    （α 常 0.8~0.9）
RTO  ← f(SRTT)

问题：对方差/抖动不敏感 → 抖动网络易误重传。

Jacobson / Karels（主流）

步骤 公式
误差 Err = M − SRTT（M 为本次 RTT）
平滑 RTT SRTT ← SRTT + g·Err（g≈1/8）
方差 RTTVAR ← RTTVAR + h·(|Err|−RTTVAR)（h≈1/4）
RTO RTO = SRTT + 4×RTTVAR

为何 ×4？ 工程上覆盖多数 RTT 波动；延迟升高时 RTO 快速抬高，减少伪重传。

Karn 算法

问题：段重传后收到 ACK → 无法判断 ACK 对应原段还是重传段（歧义）。

规则：重传段的 RTT 样本不用于更新 SRTT/RTTVAR。

代价：重传后 RTO 无法自适应 → 下一次超时仍用旧 RTO。

RTTM（时间戳选项）

时间戳选项（TSOPT）让每个段携带发送时间戳 → 重传时仍可测 RTT → 绕过 Karn 限制。

段1 (TS=1000) → 丢失
重传段1 (TS=1000) → 到达 → ACK (TSecr=1000)
→ RTT = now - 1000（正确，不歧义）

兼 PAWS 防序号回绕 → ch13

Linux 实践

参数 典型值
初始 RTO 1s（旧实现 3s）
最小 RTO 200ms 下限
时钟粒度 可达 1ms（旧系统 500ms 级） 
# 查看 TCP 定时器信息
ss -ti
# 输出示例: rto:280 rtt:12.5/5 mss:1448

HFT 关联

RTO 特性 HFT 影响
最小 RTO 200ms 远超交易容忍——TCP 重传 = 灾难
时间戳 必须 enable（tcp_timestamps=1）
SRTT 自适应 反映网络延迟趋势，可用于监控

自测题

  1. Jacobson/Karels 算法中 RTO = SRTT + 4×RTTVAR，为什么是 4 倍？
  2. Karn 算法为什么不用重传段的 RTT 样本？时间戳如何解决这个问题？
  3. Linux 最小 RTO 是多少？为什么不能设得更小？

14.4

基于计时器的重传

章级精读：../study.md#ch14-4

本节核心目标

理解 TCP 重传计时器的工作机制：启动、重启、超时。

计时器规则

条件 动作
有未确认在途数据 启动/维持重传计时器
收到推进左边界的新 ACK 重启计时器，超时 = 当前 RTO
计时器溢出 重传最老未确认段 + 指数退避
所有数据已确认 关闭计时器

关键：始终盯住最老未确认段。ACK 推进左边界后，计时器重置为剩余最老段的 RTO。

重传队列管理

发送窗口:
| 已确认 | 待ACK(在途) | 可发 | 不可发 |
         ^最老未确认段
         ↑ 计时器盯这个段
  • 重传后 RTO ×2（指数退避）
  • 不立即重传所有在途段——只重传最老的
  • SACK 模式下可选择性地重传多个空洞

与快速重传的协作

1. 段丢失 → dup ACK 开始累积
2. 3 dup ACK → 快速重传（不等 RTO）→ 进入快速恢复
3. 如果快速重传也失败 → RTO 计时器溢出 → 超时重传

  2. 收到部分 ACK（推进但未完全确认）时计时器如何处理？
  3. 为什么重传后 RTO 要翻倍？

14.5

快速重传 (Fast Retransmit)

章级精读：../study.md#ch14-5 · 拥塞控制：ch16

本节核心目标

掌握快速重传的触发条件、工作流程和与 RTO 的协作。

核心思想

不依赖 RTO 计时器——通过重复 ACK 推断丢包，立即重传。

触发条件

条件 动作
3 个重复 ACK（dup ACK） 认为该序号后数据丢失，立即重传
为何是 3？ 1–2 个 dup ACK 常由失序引起；3 个更可能真丢包

dup ACK 的产生

发送方发出: seq=1, seq=1001, seq=2001, seq=3001
seq=1001 丢失

接收端收到 seq=1 → ACK 1001 (正常)
接收端收到 seq=2001 → ACK 1001 (dup #1，期望 1001 但收到 2001)
接收端收到 seq=3001 → ACK 1001 (dup #2)
发送方再发 seq=4001 → 接收端 ACK 1001 (dup #3)
→ 触发快速重传 seq=1001

快速重传 + 快速恢复

1. 3 dup ACK → 重传丢失段
2. ssthresh = cwnd / 2
3. cwnd = ssthresh + 3（3 个 dup ACK 说明 3 个段已离开网络）
4. 恢复期: 每收到 1 dup ACK → cwnd +1（可发新段）
5. 收到新 ACK → cwnd = ssthresh → 退出快速恢复

与超时的区别：超时 cwnd=1（粗暴）；快速恢复 cwnd 减半（温和）。

Limited Transmit

窗口小、dup ACK 仅 1–2 个时也允许发 1 新段 → 凑够 3 dup ACK 触发快速重传，避免 RTO。

HFT 关联

特性 HFT 影响
快速重传 ~1 RTT 比 RTO 快 10-100x
3 dup ACK 阈值 小窗口场景可能无法触发
cwnd 减半 吞吞吐量突降

自测题

  1. 为什么是 3 个 dup ACK 而非 1 个？这个阈值如何平衡误判和延迟？
  2. 快速恢复中 cwnd 为什么加 3？
  3. Limited Transmit 解决了什么问题？

14.6

带 SACK 的重传

章级精读：../study.md#ch14-6 · SACK 协商：ch13

本节核心目标

理解 SACK（Selective ACK）如何精确定位丢失段，避免不必要的重传。

累积 ACK 的局限

标准 TCP ACK 只说「连续收到 X 之前」→ 发送方不知中间空洞的具体位置。

发送: seq=1, 1001, 2001, 3001, 4001
丢失: seq=1001, seq=3001

累积 ACK: "我收到了 seq=1 之前" (ACK=1001)
→ 发送方不知道 2001/4001 是否到达
→ 可能重传已收到的段（浪费）

SACK 选项

接收方在 ACK 中携带 SACK 块，描述已收到的不连续区间：

ACK=1001 (累积: 期望 1001)
SACK: [2001:3000] [4001:5000]
→ 发送方知道: 1001 丢失, 2001 已收到, 3001 丢失, 4001 已收到
→ 只重传 1001 和 3001

限制：TCP 选项区常限 ~40B（与时间戳等共存）→ 每段约 3–4 个 SACK 块。

Scoreboard（发送端）

发送端维护 Scoreboard——基于 SACK 信息跟踪每个段的状态：

段 状态 动作
seq=1 已确认 跳过
seq=1001 丢失（SACK 无覆盖） 重传
seq=2001 SACK 确认 跳过
seq=3001 丢失（SACK 无覆盖） 重传
seq=4001 SACK 确认 跳过

同窗多丢时远优于纯快速重传（避免逐个超时）。

Linux SACK

# 确认 SACK 已启用
sysctl net.ipv4.tcp_sack    # 默认 1
sysctl net.ipv4.tcp_timestamps  # 时间戳也应启用（RTTM + PAWS）

HFT 关联

SACK 对高 BDP 链路至关重要——窗口大时同窗多丢概率高，无 SACK 则逐个 RTO 恢复，延迟灾难性。

自测题

  1. SACK 块描述的是什么？为什么最多只能携带 3-4 个块？
  2. Scoreboard 如何帮助发送方决定重传哪些段？
  3. 如果 SACK 选项被防火墙剥离，会有什么后果？

14.7

伪超时 (Spurious Timeout)

章级精读：../study.md#ch14-7 · Eifel：ch16 §16.4

本节核心目标

理解伪超时的成因、检测方法和撤销机制。

什么是伪超时

RTO 溢出但数据未丢——只是延迟了（延迟尖峰、路径切换）→ 伪重传。

0.000s  发送 seq=1
0.200s  RTO 超时 → 重传 seq=1
0.210s  原始 seq=1 的 ACK 到达 → 才发现没丢！
→ 已经错误地减半了 cwnd（性能损失）

检测方法

方法 原理
DSACK 接收方标明收到重复数据 → 若对应刚超时重传 → 伪超时
Eifel 时间戳 TSecr 指向原段而非重传段 → 原段其实到了
F-RTO 无时间戳时，超时后先发新数据，观 ACK 推断伪超时

Eifel 检测详解

原始段: TS=1000
重传段: TS=1000 (相同，因为是重传)

ACK 回来: TSecr=1000 → 对应原始段
         (如果对应重传段，TSecr 仍是 1000，但时序不同)

关键: Eifel 比较 ACK 到达时间与重传时间
     → 如果 ACK 在重传后极短时间到达 → 很可能是原始段的 ACK → 伪超时

Eifel Response

伪超时确认后 → 撤销误缩的 cwnd / ssthresh → 避免性能雪崩。

HFT 关联

无线/移动网络延迟尖峰常见 → 伪超时频发。HFT 有线环境相对稳定，但跨数据中心 WAN 仍可能遇到路径切换尖峰。

自测题

  1. 伪超时和真超时的区别是什么？如何区分？
  2. DSACK 如何检测伪超时？
  3. Eifel Response 撤销了什么？为什么重要？

14.8

包失序与包重复

章级精读：../study.md#ch14-8

本节核心目标

理解 TCP 如何处理网络层引入的失序和重复。

失序

现象 原因 TCP 行为
seq=2001 先于 seq=1001 到达 IP 多路径（ECMP）、队列差异 产生 dup ACK；3 阈值屏蔽轻微失序 
发送: 1, 1001, 2001
到达: 1, 2001, 1001 (失序)

接收端:
  收到 1    → ACK 1001 (正常)
  收到 2001 → ACK 1001 (dup #1，期望 1001)
  收到 1001 → ACK 3001 (跳过 2001，确认到 3001)

3 dup ACK 阈值：1-2 个 dup ACK 可能只是失序，3 个更可能真丢包。

重复

现象 原因 TCP 行为
同一 seq 收到两次 链路层重传、拷贝 SEQ 去重；可能触发 DSACK

DSACK：接收方告知发送方「你发的东西我已经有了」→ 发送方推断伪重传。

ECMP 与失序

数据中心常用 ECMP（等价多路径）→ 同一流量可能走不同路径 → 延迟差异 → 失序。

flow A → path 1 (1ms)
flow A 的某些包 → path 2 (3ms) → 失序

缓解：现代交换机支持 per-flow ECMP（同一五元组走同一路径）。

HFT 关联

现象 HFT 影响
ECMP 失序 行情包乱序 → 应用层序号重组
重复包 极少发生，但需序号去重
3 dup ACK 可能触发不必要的快速重传

  1. 为什么 1-2 个 dup ACK 不触发快速重传？
  2. ECMP 为什么会导致 TCP 失序？如何缓解？
  3. DSACK 和 SACK 的区别是什么？

缓存内容

重新组包重传

章级精读：../study.md#ch14-9

本节核心目标

理解重传时可以合并小段为大段，提高效率。

重新组包

原始发送: 3 个小段 (200B + 200B + 200B = 600B)
全部丢失 → 超时重传
重传时: 合并为 1 个大段 (600B，≤ PMTU)

好处： - 减少报文数量 → 降低头部开销 - 减少 ACK 数量 → 降低反向链路压力 - 提高重传效率

限制

  • 合并后总长不能超过 PMTU
  • 仅超时重传时触发（快速重传不合并）
  • 发送缓冲区中待发数据必须连续

14.11

重传相关攻击

章级精读：../study.md#ch14-9 · 安全：ch18

本节核心目标

理解利用 TCP 重传机制的攻击及防御。

LDoS (Low-rate DoS)

原理：周期性脉冲诱发连续指数退避 → 吞吐趋 0。

攻击者: 周期性发送短脉冲 → 触发 RTO 超时
TCP: cwnd=1 → 慢启动 → 刚恢复 → 再次被攻击脉冲触发超时
→ 吞吐永远在恢复中，无法达到稳态

特点：攻击流量低（不像传统 DDoS 暴力），但效果显著。

伪造重传攻击

攻击 机制 防御
伪造 dup ACK 诱导发送方误判丢包 → 不必要重传 序列号验证
伪造 RST 重置连接 → DoS 序列号在窗口内检查
ACK 窗口攻击 伪造 ACK 推进左边界 → 数据被截断 RST 检查

HFT 关联

攻击 HFT 影响
LDoS 交易连接周期性中断 → 策略失效
伪造 RST 交易连接被重置 → 订单丢失
伪造 dup ACK 不必要的重传 → 延迟增加

防御：专线/VPN + 加密（TLS/IPSec）+ 序列号随机化。

易混速记

问题 要点
超时 vs 快速重传 超时重置 cwnd 更狠；快速恢复较温和
Karn 重传段 RTT 不采样（无时间戳时）
3 dup ACK 丢包 vs 失序的工程折中
伪超时 无线/移动网常见；需 DSACK/Eifel
SACK 精确定位空洞，避免不必要重传

HFT 核心关联

机制 HFT 影响
RTO 最小 200ms 远超交易容忍
指数退避 丢包后延迟雪崩
快速重传 ~1 RTT 仍比 UDP + FEC 慢
SACK 高 BDP 链路必备
