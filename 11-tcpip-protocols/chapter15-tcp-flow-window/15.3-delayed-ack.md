# 15.3 延时确认 (Delayed ACK)

> 章级精读：[../study.md#ch15-3](study.md#ch15-3)

## 本节核心目标

理解 Delayed ACK 的工作原理及其与 Nagle 的死锁问题。

---

## 核心概念

接收端**暂缓纯 ACK**，提高带宽利用率、支持**捎带**。

| 概念 | 说明 |
|------|------|
| **Delayed ACK 计时器** | 常 **200ms** 量级 |
| **捎带（Piggybacking）** | ACK 嵌入本端反向数据段 |
| **触发立即 ACK** | 收到第二个全尺寸 MSS 段 |

---

## 规则

1. 收到数据后**不立即** ACK，短时等待本端响应数据
2. **必须发 ACK**：计时器到点；或收到**第二个 MSS** 段

---

## 与 Nagle 的经典死锁

```
1. 发送方: 发 1B → 等 ACK（Nagle 阻塞后续小包）
2. 接收方: 收 1B → 启动延迟 ACK，应用暂无数据可捎带
3. 发送方: 应用再产生小数据 → Nagle 仍禁止发
4. 直至接收方 ~200ms 后强发 ACK → 发送方才能继续
```

**结果**：交互应用可出现 **~200ms 卡顿**。

---

## Linux 参数

```bash
# 快速 ACK 数量（初始阶段发送的立即 ACK 数）
sysctl net.ipv4.tcp_quickack     # 默认 0（关闭快速 ACK）
# 注意: tcp_quickack=1 不是持久设置，内核会自动回退到延迟 ACK
```

---

## HFT 关联

Delayed ACK 的 200ms 延迟对 HFT 不可接受。解决：
- `TCP_NODELAY` 禁用 Nagle（发送方）
- `TCP_QUICKACK` 禁用 Delayed ACK（接收方，需定期重设）
- 或直接用 UDP
