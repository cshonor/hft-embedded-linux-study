# 10.9 分片与 ARP/ND 陷阱

> 章级精读：[../study.md#ch10-7](study.md#ch10-7) · ARP：[ch04](../chapter04-arp-protocol/study.md)

## 本节核心目标

理解大 UDP 报文分片后与 ARP/ND 解析的竞态条件。

---

## 问题场景

```
1. 应用发送 4000B UDP → 内核分 3 片
2. 第一片发送时，目标 IP 的 ARP 还未解析
3. ARP 请求发出，等待回复...
4. 第二片、第三片排队等待（ARP 队列有限）
5. ARP 超时或队列满 → 后续片被静默丢弃
6. 接收端收不齐 → 整报文丢弃
```

**结果**：应用看到「网络极差」，但实际是 ARP 竞态。

---

## 缓解策略

| 策略 | 实现 |
|------|------|
| **预热邻居缓存** | 发送前先 `ping` 目标，触发 ARP 解析 |
| **connect() UDP** | `connect()` 固定五元组，提前解析路由 |
| **应用层分包** | 控制包大小 ≤ MTU，避免分片 |
| **调整 ARP 队列** | `net.ipv4.neigh.*.unres_qlen`（默认 3，可调大） |

```bash
# 查看邻居缓存
ip neigh show
# 调整 ARP 未解析队列长度
sysctl net.ipv4.neigh.eth0.unres_qlen=10
```

---

## IPv6 的对应问题

IPv6 用 ICMPv6 邻居发现（ND）替代 ARP，但竞态条件相同：

- 组播 `Solicited-Node` 地址 → 等待 NA 回复
- ND 缓存未建立时分片同样会丢

---

## HFT 关联

HFT 系统启动时应**预热所有对端的邻居缓存**——避免首次发送行情/订单时触发 ARP/ND 解析延迟。这是「冷启动抖动」的常见来源。
