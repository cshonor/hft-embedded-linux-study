## 4.4 sar 工具

### 本节讲什么

sar 是 sysstat 包里最老牌的工具——**表面上是一个实时统计命令，本质上是「时间机器」**。本节讲清它的三重身份（实时采样器 / 历史回放器 / sadc 归档系统的前端）、为什么有了 BPF 之后它反而更重要、输出字段的精读方法，以及 HFT 场景下采样间隔的取舍。

### 要点

| # | 要点 | 一句话展开 |
|---|------|-----------|
| 1 | sar = 实时 + 历史双模 | 实时模式 `sar -u 1`；历史模式 `sar -f` 读 sadc 归档 |
| 2 | 独有价值是「上周同一时段对比」 | BPF 工具全都是「现在时」，只有 sar 有时间轴 |
| 3 | sadc 是真正在干活的后台进程 | sysstat cron 定期调 sadc 落盘，sar 只负责读 |
| 4 | 归档路径与轮转有默认约定 | `/var/log/sysstat/saDD`，按天轮转，默认保留 7~28 天 |
| 5 | 采样间隔是开销 vs 分辨率的权衡 | 10s 归档够趋势分析；微秒级尖刺 sar 原理上看不到 |
| 6 | 与 USE 方法字段高度重合 | 附录 B 的 USE 清单几乎每行都能用一条 sar 子命令覆盖 |

---

### 一、三重身份

**身份 1：实时采样器**（和 vmstat/mpstat 同类，但一个命令覆盖所有子系统）：

```bash
sar -u 1 5          # CPU（1 秒间隔，采 5 次）
sar -n DEV 1 5      # 网络接口
sar -q 1 5          # 运行队列与 load
sar -r 1 5          # 内存
sar -B 1 5          # 分页统计
sar -d 1 5          # 块设备
sar -W 1 5          # swap 换入换出
```

**身份 2：历史回放器**——这是 vmstat/mpstat 做不到的：

```bash
sar -u -f /var/log/sysstat/sa28      # 看 28 号那天的 CPU
sar -q -s 09:30:00 -e 10:30:00       # 只看某个时间窗
sar -n DEV -f /var/log/sysstat/sa28  # 回放当天的网络
```

**身份 3：sadc 归档系统的前端**。架构上真正在持续干活的是 `sadc`（System Activity Data Collector）：

```
sysstat 的 cron/systemd-timer
   │  (默认每 10 分钟)
   ▼
sadc ——读——> /proc, /sys ——写——> /var/log/sysstat/saDD
   │                                    (按天一个文件，自动轮转)
   ▼
sar -f <file>  <──  人类可读回放  <──  sadf -d <file>（CSV 导出）
```

日常说的「sar 历史数据」其实是 sadc 采的；sar 只是读取器。`sadf -d` 能导 CSV 喂给其它分析工具，`sadf -j` 导 JSON。

### 二、为什么有了 BPF，sar 反而更重要

一个反直觉的判断：**现代观测工具越强，历史基线越值钱**。原因在对比表里：

| 维度 | BPF 工具（runqlat/biolatency…） | sar/sadc |
|------|--------------------------------|----------|
| 时间维度 | 现在（attach 即开始累积） | **过去（从归档任意回放）** |
| 分辨率 | 事件级、纳秒级时间戳 | 采样级，默认 10 分钟 |
| 部署前提 | 内核版本/BTF 配合 | 只读 /proc，几乎零依赖 |
| 开销 | 可编程（可控可不小） | 固定极低（读几个 /proc 文件） |
| 回答的问题 | 「现在延迟长在哪」 | **「这事上周有没有发生过？什么时候开始的？」** |

性能调查最常见的问题形态其实是第二种：「P99 是从什么时候开始劣化的？那天改了什么？」——BPF 工具对此无能为力（事件已经过去了），sar 归档是唯一的答案来源。这就是 Gregg 在 2011 年（BPF 出现之前）就在推 sar、今天仍然推 sar 的原因：**工具的价值不在分辨率，在于你出事时它已经在场**。

### 三、输出精读：sar -u 与 sar -q

**sar -u 1（CPU）：**

```text
Linux 6.6.0 (hft-bare) 	08/31/2026 	_x86_64_	(24 CPU)

14:22:01     CPU     %user     %nice   %system   %iowait    %steal     %idle
14:22:02     all      3.10      0.00      1.85      0.42      0.00     94.63
```

| 字段 | 精读 | 红线 |
|------|------|------|
| %user | 应用代码（含自旋锁自旋计入 system 之外的路径） | HFT 热路径核不应看全局，用 `sar -P 3,4` 看指定核 |
| %system | 内核态（syscall、softirq） | 异常抬升先想 softirq / syscall 风暴 |
| %iowait | **空闲且有待完成磁盘 I/O 的 CPU 时间占比** | 注意稀释机制：分母是空闲时间（见 [9.1 核心概念](../../chapter-09-disks/notes/section-9.1-9.3-核心概念与模型.md)） |
| %steal | 虚拟化被宿主偷走的时间 | 物理机恒为 0；云上 >2% 就要找云厂商 |
| %idle | 空闲 | **高 idle ≠ 无问题**——热路径核被空出来才是隔离的目标 |

**sar -q 1（队列与 load）：**

| 字段 | 精读 |
|------|------|
| runq-sz | 运行队列长度——**>0 即有排队**，HFT 热核上应恒为 0~1 |
| plist-sz | 进程/线程总数——持续上涨 = 泄漏信号 |
| ldavg-1/5/15 | 1/5/15 分钟负载——**分钟级指数平滑，对秒级事件天然失明** |
| blocked | 等待 I/O 的不可中断任务数——配合 %iowait 看 |

`-P ALL`（或 `-P 0,3,4`）分核视图是 sar 相对 top 的优势：归档也是分核落盘的，可以回放「上周三下午 3 核和 4 核的 load 是多少」。

### 四、采样间隔：开销、分辨率、用途三角

| 间隔 | 开销 | 能看到 | 典型用途 |
|------|------|--------|----------|
| 1s（`sa1 1`） | 仍很低，但归档变大 | 秒级趋势 | 上线后第一周摸底 |
| **10s（默认）** | 可忽略 | 分钟级趋势 | 常规基线，够用 |
| 10min（老默认） | 零 | 小时级趋势 | 只够容量规划 |

关键认知：**sar 的分辨率天花板是采样间隔，与工具无关**。10s 采样下，一次持续 2s 的 CPU 尖刺要么完全错过、要么被稀释成一个不痛不痒的半高样本。这不是 bug 而是设计——sar 的使命是趋势与基线，微秒级尖刺是 BPF 工具（runqlat、drsnoop）的辖区。**两个分辨率层次解决两类问题，缺一不可**：

```
「上周开始 P99 变差」 ──> sar 归档定位到天/小时
        │
        ▼（下钻）
「变差的那个小时里延迟堆在哪」 ──> BPF 工具现场复现
```

**HFT 建议：** 热路径机器 sadc 间隔设 ≥10s（低开销换长期基线），微秒级诊断不指望 sar 而指望常驻的超时计数器与 BPF。危机处置时用实时 `sar`（1s 间隔）看当下，复盘用归档。

### 五、常见坑

| 坑 | 现象 | 处理 |
|----|------|------|
| sadc 根本没在跑 | `sar` 报 `no such file`，归档目录空 | 启用 `sysstat` 服务 / systemd-timer；容器环境尤其要主动配 |
| 归档被 logrotate 清掉 | 想看两周前，文件已删 | 调 `HISTORY` 参数；重要节点归档外发 |
| 云镜像默认不装 sysstat | 新机器全是盲区 | 烘进基础镜像——这正是 [4.1 危机工具](./section-4.1-工具覆盖范围与危机工具.md) 的预装清单 |
| 用 load average 判断 HFT 状况 | ldavg 全绿但 P99 已爆 | load 是分钟级平滑均值，热核排队要看 runq-sz 实时值 |
| `%iowait 高 = 磁盘慢` | 误判 | %iowait 是「空闲+有未完成 I/O」占比，被空闲稀释（见 ch9） |

### HFT / 嵌入式关联

- **「上周同一时段对比」是容量规划的原始输入**：报单速率翻倍前后的 sar 曲线对比，直接给出 λ 变化对排队的影响——与 [2.6 排队论](../../chapter-02-methodologies/notes/section-2.6.1-排队论概览与Kendall记号.md)的拐点估算闭环。
- **steal 列是云上 HFT 的免费体检**：共置机器若非裸机，%steal 直接量化「邻居税」（见 [11.2 硬件虚拟化](../../chapter-11-cloud-computing/notes/section-11.2-硬件虚拟化Hardware-Virtualization.md)）。
- **嵌入式：** sysstat 体积小、只读 /proc，适合进嵌入式镜像做长期基线；交叉板卡上常是唯一可用的「历史」来源。

### 常见陷阱

1. sar 只看历史不告警——sar 记录历史但不主动告警，需要配合 Prometheus/Grafana 做实时告警
2. sar 默认粒度太粗——10 分钟平均看不到 HFT 微秒级尖刺，秒级趋势要 10s 采样，微秒级要换 BPF
3. 不存 sar 历史数据——出事才想看昨天的趋势，但 sadc 没配或被清理了
4. load average 当实时指标——1 分钟 load 也是分钟级指数平滑，秒级排队要看 runq-sz
5. 云镜像不装 sysstat——新机器零历史基线，要烘进基础镜像
