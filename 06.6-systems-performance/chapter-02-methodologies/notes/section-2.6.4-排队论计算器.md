## 2.6.4 · 排队论计算器

← [概览](./section-2.6.1-排队论概览与Kendall记号.md) · [M/M/1](./section-2.6.2-M-M-1-拐点与预警线.md) · [M/M/c](./section-2.6.3-M-D-1-M-M-c-M-G-1.md#mm/c)

---

### 本节讲什么

把前三节的模型变成**手边的工具**：计算器吃什么输入、吐什么输出、输出里哪些可信哪些要校准。核心认知是定位问题——**排队论计算器是「拐点估算器」和「容量规划起点」，不是「延迟预测器」**。闭式解给均值，tail 要靠仿真或压测校准，这个边界划不清就会误用。

### 要点

| # | 要点 | 一句话展开 |
|---|------|-----------|
| 1 | 两类输出：延迟与拐点 | 前者看均值 W，后者找 knee 定限流/告警线 |
| 2 | 输入三个数：λ、μ、c | 单位一致性是第一坑（每秒 vs 每毫秒差 1000×） |
| 3 | 闭式解只给均值 | P99/P999 要仿真或压测 histogram 校准 |
| 4 | 拐点做告警要再打折 | knee - 10~15 个百分点做预警线 |
| 5 | 模型是估算不是真理 | cache/调度/锁的非线性因素模型不管 |
| 6 | 计算器的归宿是压测的对照组 | 拐点估出来 → Ch12 压测验证 → 回填修正 |

---

### 一、两类输出

| 类型 | 输入 | 输出 | 用途 |
|------|------|------|------|
| **① 延迟** | c、λ、1/μ | **W**（均值逗留时间）、Wq（纯排队时间）、L（队长） | 「这个利用率下平均多慢」的量级感 |
| **② 拐点** | 同上 | CPU **knee** → 定限流 / 告警 | **不试不知道会爆炸的那条线** |

两类输出的可信度不同：**W 的绝对值经常不准**（真实系统的服务时间不是指数分布、到达不是泊松），但**knee 的位置相当鲁棒**——不同分布的拐点都在 70%~85% 这个带里，因为「排队长度随 ρ→1 发散」是结构性质不是分布性质。这就是计算器的主用途是找拐点而非算延迟的原因。

**预警线 + 缓冲：**

| 模型 | 拐点 | 建议告警 |
|------|------|----------|
| M/M/1 | ~70% | ~55%~60% |
| M/D/1 | ~80% | ~65%~70% |
| M/M/8 | ~75%~80% | ~65%~70% |

> 闭式解给 **均值 W**；P99 须仿真或压测 histogram **校准 tail**。

---

### 二、实战：8 核报单引擎（M/M/c，c=8）

| CPU ρ | P99（示意） | 读法 |
|-------|-------------|------|
| 50% | ~8 µs | 日常 |
| **75%** | **~50 µs** | 拐点 — 相对 ~5 µs 跳数量级 |
| 85% | ms 级 | 不可接受 |

```
拐点（预警线）  ≈ 75%~80%
Grafana 告警      ≈ 65%~70%
限流/扩容         在 P99 5→50 µs 之前
```

**M/M/1 对照：** 拐点 70% → 告警 ~60%。

三行纪律的层次关系：**拐点是物理事实**（过了这条线延迟结构性恶化）、**告警线是拐点打折**（留出反应时间）、**限流线在告警之前**（保护系统不进入拐点区）。三者不能倒置——最常见的错误是把告警线设在拐点上（等报警时已经在深渊里了）。

### 三、工具

| 类型 | 示例 | 适用 |
|------|------|------|
| Python | [`queueing-tool`](https://pypi.org/project/queueing-tool/) | 需要可复现的计算进脚本/CI |
| 心算 | M/M/1 五行（下） | 会议桌上五秒钟出量级 |
| Web | `M/M/c calculator` | 一次性查询 |
| 仿真 | SimPy | 非 M 分布 / 要 tail 分位数时 |

**M/M/1 五行心算**（λ=7000/s，μ=10000/s 的例子）：

```python
lam, mu = 7000, 10_000
rho = lam / mu            # 0.7 —— 先看这个，过 0.7 立刻紧张
L = rho / (1 - rho)       # 2.33 —— 系统内平均任务数
W = 1 / (mu - lam)        # 0.333 ms —— 平均逗留时间
Wq = rho / (mu - lam)     # 0.233 ms —— 平均排队时间（W - 1/μ）
```

五行里最有信息量的是 `rho` 本身和 `1/(mu-lam)` 的形态：**分母 (μ-λ) 是「富余容量」，W 与富余容量成反比**——λ 贴近 μ 的过程中，富余容量线性缩小、延迟反比例爆炸。这就是拐点曲线的全部直觉。

**批量扫描找拐点**（这才是「计算器」的完整用法）：

```python
for rho in [0.5, 0.6, 0.7, 0.75, 0.8]:
    W, P99 = calculator_mm_c(rho * c * mu, mu, c=8)
knee ≈ 75~80%  →  告警 ≈ 65~70%  →  Ch12 压测验证
```

### 四、P99 校准：从闭式解到真实 tail 的三步路

闭式解的 W 是均值；HFT 要的是 P99/P999。补齐的路线：

| 步骤 | 做法 | 产出 |
|------|------|------|
| ① 仿真 | SimPy / queueing-tool 按真实分布（服务时间用压测采到的分布，不是教科书指数）跑 Monte Carlo | 模型内的 P99 |
| ② 压测 | Ch12 方法：真实 workload 打到各利用率档位，记录 histogram | 系统真实 P99 |
| ③ 对比回填 | 仿真 vs 压测的 P99 差多少 → 模型缺的非线性因素（锁、cache、调度）量化 | 修正系数 |

经验规律：**真实系统的 P99 通常比 M/M/c 理论 tail 更差**——因为模型假设里「服务时间独立同分布」「到达平稳」在真实系统都不成立（行情风暴 = 突发相关到达，风暴期服务时间也变长——相关性放大 tail）。所以模型给的 P99 当**下限**用，不是中心估计。

---

### 五、单位一致性与输入来源

最蠢也最常见的错——λ 用「每毫秒」μ 用「每秒」，算出的延迟差 1000 倍。防御性写法：**先统一到每秒，再进公式**：

```python
def to_per_second(rate, unit):
    return rate * {"s": 1, "ms": 1e3, "us": 1e6}[unit]
```

输入的合法来源也要注意：

| 参数 | 从哪来 | 常见错 |
|------|--------|--------|
| λ（到达率） | 生产监控：订单/秒、tick/秒 | 用峰值均值而不是风暴期瞬时值 |
| 1/μ（服务时间） | 压测或 perf 剖析：单次处理耗时 | 用均值代分布——服务时间方差大时 tail 被低估（Kingman 公式：等待≈方差项的函数） |
| c（并行度） | 实际绑定的核数 | 用机器核数而不是**热路径实际可用核数**（隔离后剩几个算几个） |

→ [Ch 12 压测](../../chapter-12-benchmarking/) · [2.5 histogram](./section-2.5-性能分析方法论.md)

### HFT / 嵌入式关联

| 场景 | 应用 |
|------|------|
| 容量规划 | 「行情翻倍后当前核数扛得住吗」——2.7.2 三步法的计算核心就是本节 |
| 限流阈值 | 网关层限流设在拐点前，保护报单引擎不进 ρ>0.8 区 |
| 扩容决策 | 盯 ρ 而不是 CPU%——ρ 是排队论口径的利用率，与「CPU 忙」不同（M/M/c 的 ρ = λ/(cμ)） |
| 嵌入式 | 单核/少核场景 c=1~4，M/M/1 直接可用；中断风暴 = 相关到达，模型偏乐观要注意 |

### 常见陷阱

1. 计算器输入不校验——λ 和 μ 单位不一致（每秒 vs 每毫秒），算出来的数字差 1000 倍；防御写法是先统一到每秒再进公式
2. 只算平均延迟——计算器还能输出 P90/P99，HFT 必须看分位数不看平均；闭式解只有均值，tail 要仿真或压测校准
3. 把模型当真理——排队论是近似模型，实际系统有 cache/调度/锁等非线性因素，模型用于估算拐点而非精确预测
4. 模型 P99 当中心估计——真实系统到达相关（风暴）、服务时间方差大，P99 通常比理论差；模型 tail 当下限用
5. c 用机器核数——要用热路径隔离后实际可用的核数
6. 告警线设在拐点上——拐点是物理事实，告警要打折 10~15 个点留反应时间；限流再前置一层

1. 排队论计算器的输入参数有哪些？
   <details><summary>答</summary>到达率 λ、服务率 μ（或服务时间 1/μ）、服务台数 c——输出利用率、排队长度、延迟；输入要先统一单位（每秒），c 用隔离后实际可用核数</details>

   <details><summary>答</summary>模型假设独立到达/服务、平稳过程，实际有 cache 局部性、调度抖动、锁竞争等非线性因素；且真实系统到达相关（风暴）、服务时间方差大——模型 tail 当下限用</details>
3. HFT 用排队论计算器的主要目的是什么？
   <details><summary>答</summary>估算拐点（利用率多少时延迟指数上升）和容量规划，而非精确预测延迟值——拐点位置比均值鲁棒（「ρ→1 排队发散」是结构性质），这是计算器主用途是找拐点的原因</details>
4. 从闭式解到真实 P99 的三步路是什么？
   <details><summary>答</summary>①仿真（SimPy，用实测服务时间分布而非指数）得模型内 P99；②压测（Ch12 方法打各利用率档位）得真实 histogram；③对比回填——差值就是模型缺的非线性因素的量化</details>
5. W = 1/(μ-λ) 这个公式给出什么直觉？
   <details><summary>答</summary>分母是「富余容量」——延迟与富余容量成反比；λ 贴近 μ 的过程中富余容量线性缩小、延迟反比例爆炸，这就是拐点曲线的全部直觉</details>
6. 拐点、告警线、限流线的层次关系？
   <details><summary>答</summary>拐点是物理事实（过了这条线延迟结构性恶化）、告警线=拐点打折 10~15 点（留反应时间）、限流在告警之前（保护系统不进拐点区）——三者不能倒置</details>
