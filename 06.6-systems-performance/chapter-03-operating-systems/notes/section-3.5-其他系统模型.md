## 3.5 其他系统模型

> [3.1 核心术语](./section-3.1-核心术语.md) · [3.3–3.4 内核演进与 Linux 特性](./section-3.3-3.4-内核演进与-Linux-特性.md) · [3.6 内核比较](./section-3.6-内核比较.md)

---

### 本节讲什么

宏内核 Linux 之外的三种「组织操作系统的另一种方式」：PGO 编译的内核、Unikernel、微内核/混合内核。对 HFT 学习者的价值不在「要去用」，而在**理解每个模型在交易什么**——每一条都是「用通用性换延迟」或「用延迟换安全」的不同配比。看懂了这些极端方案，反过来更明白 Linux 宏内核 + 调优/旁路这条主路为什么这样选。

### 要点

| # | 要点 | 一句话展开 |
|---|------|-----------|
| 1 | PGO：让编译器知道热路径在哪 | 用剖析数据引导代码布局，I-cache/branch 预测受益 |
| 2 | Unikernel：应用即内核，单地址空间单特权级 | 消灭 syscall/切换/隔离——延迟地板最低的通用模型 |
| 3 | 微内核：最小内核 + 用户态服务 | 隔离与可验证性最强，IPC 往返是延迟代价 |
| 4 | 三者共同的交易货币是「通用性」 | 越快的模型越挑 workload |
| 5 | HFT 现实主线 = 宏内核 + 旁路 | DPDK/XDP 把「数据面搬出内核」的收益拿到手，保留 Linux 生态 |
| 6 | Unikernel 的死穴是观测 | 没有第二层系统就没有旁观者——无观测即无调优 |

---

### 一、三种模型对照

| 维度 | PGO 内核 | Unikernel | 微内核 / 混合内核 |
|------|----------|-----------|-------------------|
| **核心思想** | 用 CPU 剖析数据**配置文件引导编译**，热路径布局更优 | 应用与内核**编译为一体**（单地址空间、单特权级） | 最小内核 + 用户态服务进程；Mach + BSD 层（早期 macOS） |
| **syscall** | 还在，只是更快 | **不存在**——函数直接调用 | 还在，且服务间还要 IPC |
| **上下文切换** | 还在 | 只剩「协作让出」 | 更多（服务边界即切换边界） |
| **隔离/安全** | 与普通内核相同 | **无进程隔离**——一行野指针毁全机 | **最强**——服务崩溃不连坐 |
| **通用性** | 高（无感） | **极低**——单应用、专用镜像 | 中（生态始终没起来） |
| **Linux 关系** | 可选 profile-guided 构建 | 独立路线（MirageOS、Unikraft） | Linux 为宏内核，不走此路 |
| **代表** | 内核构建系统的 PGO 选项 | MirageOS（OCaml）、Unikraft | QNX、seL4（微）；XNU（混合） |

---

### 二、PGO：低风险的「白捡」优化

原理三步：

```
① 插桩构建内核 → ② 跑代表性 workload（收集分支/路径频率） → ③ 按数据重排代码布局
```

热函数被放到一起（I-cache 局部性↑）、高频分支被编译器排成直通路径（branch 预测↑）、冷路径挪远。**不改变任何语义，只改布局**——这是它与后两个模型的本质区别：PGO 是「把现有内核调快」，不是「换一种操作系统」。

局限：剖析数据必须**代表生产 workload**（用错 workload 的 PGO 可能负优化）；内核版本升级要重新采集。对 HFT：发行版若提供 PGO 内核可测一轮 tick-to-trade 对比；自维护内核的团队优先级不高（同样的精力投到绑核/隔离收益更大）。

---

### 三、Unikernel：延迟地板最低的通用模型

把应用、libc、必要的内核子系统（网络栈、内存分配器）**编译成一个单一特权级镜像**，直接跑在 hypervisor 上。消灭的东西：

| 消灭的层 | 换来的延迟收益 |
|----------|---------------|
| syscall（用户↔内核切换） | 函数调用替代陷入——ns 级 |
| 进程隔离（地址空间切换） | 单地址空间，无切换成本 |
| 通用调度器 | 通常协作式或极简调度 |
| 通用驱动的抽象层 | 只编入用到的驱动 |

**代价同样极端**：无进程隔离（一次越界写 = 全机死）、生态封闭（每换应用重编镜像）、**调试观测基础设施近乎为零**。最后一条是性能工程视角的决定性弱点——**无观测即无调优**：出性能问题时没有 perf/bpftrace 的落脚点（没有「内核」这个第二层可以旁观你的应用）。见 [4.6 观测的观测](../../chapter-04-observability-tools/notes/section-4.6-观测的观测Observing-Observability.md) 的反面。

Unikernel 的正确打开方式是**吸收其思想而非整体采用**：Linux 上「单进程 + 绕过不必要抽象」的设计（专用网卡驱动、用户态栈、避免 fork）拿的是同类收益。11.5 节的 Unikernel 哲学与 DPDK 对比有展开。

---

### 四、微内核：隔离最强、延迟最贵的模型

内核只留最小集（IPC、调度、基础内存管理），文件系统、网络栈、驱动全跑在用户态服务进程里。收益是**可验证性与故障隔离**（seL4 形式化验证过正确性；QNX 在车载/航空广泛认证）——但每帧网络包、每次文件读都要跨服务 IPC：

```
宏内核：  应用 --syscall--> 内核网络栈（一次模式切换）
微内核：  应用 --IPC--> 网络服务 --IPC--> 驱动服务 --IPC--> 内核最小层（多次切换+多次拷贝）
```

对延迟敏感的 HFT 是天然不适合的（IPC 往返叠加）；对**功能安全认证**优先的场景（车载、医疗）是正确选择。混合内核（XNU）是两者的折中——把最性能敏感的服务塞回内核，其余留用户态。

---

### 五、HFT 的现实选择：宏内核 + 旁路

三个模型各取所需的精华，都汇入同一条现实主线：

| 模型的思想 | Linux 主线上的对应物 |
|-----------|---------------------|
| PGO 的「热路径布局优化」 | 编译器 PGO 用于**应用**（策略引擎二进制）比用于内核更常见 |
| Unikernel 的「消灭不必要的层」 | **DPDK / 用户态栈**（数据面整个搬出内核）；XDP 在内核内走类似思路 |
| 微内核的「故障隔离」 | 进程模型 + systemd 看门狗（简单粗暴版） |

**HFT 现实：** 主流仍是 **Linux 宏内核 + 绑核/旁路（DPDK/XDP）**；Unikernel 多见于研究或极专用部署；微内核不用于延迟路径。判断依据回到 [12.2 保真度-可控性](../../chapter-12-benchmarking/notes/section-12.2-基准测试的类型.md) 同款的权衡思维：**每消掉一层抽象，就少一层通用性**——交易系统的复杂度通常付不起这个价，除非整个系统已经收敛到一个极简单的专用 workload。

### 常见陷阱

1. 把 Unikernel 当「更快的 Linux」——它是不带的 Linux 的另一物种：无进程隔离、无通用生态、几乎无观测工具
2. 微内核=更快——相反，服务间 IPC 往返是延迟叠加；微内核卖点是隔离与可验证性
3. PGO 数据一劳永逸——剖析数据必须代表生产 workload；workload 演化或升级内核要重采，用错数据可能负优化
4. 「消灭抽象层」只有好处——每消一层少一层通用性；旁路（DPDK）的代价是放弃内核网络栈的全部设施（/proc 统计、eBPF 插桩、拥塞控制）
5. 忽视「无观测即无调优」——Unikernel 类方案的性能上限高但可维护性差，出问题时没有第二层系统可以旁观诊断

   <details><summary>答</summary>DPDK/用户态栈（数据面整体出内核）、XDP（内核内极早处理点）、单进程避免 fork 的设计、专用驱动——都是「消灭不必要的层」这个思想的落地</details>
