## 案例背景：An Unexplained Win

> **出处：** Gregg《性能之巅》Ch 16 · Netflix 生产案例「无法解释的性能提升」— 全书收官演习，无新理论，只有方法论的总装。
> **HFT 实操要点：** 「莫名变快」比「莫名变慢」**更危险** — 回归没人投诉，但 win 若来自邻居撤离/缓存预热，它会在最不该消失的时候消失（比如开盘竞价）。

```
     「变慢」                          「变快（Unexplained Win）」
  用户投诉 · SLA 告警              无人投诉 · 甚至无人发现
  主动排查 · 有截止时间            被动忽略 · 「反正好了」
  ─────────────────────────────────────────────────────────────
  共同点：都暴露你【不理解】的机制变化。
  你不懂为什么赢，你就不知道它什么时候会还回去。
```

---

### 一、为什么「变快了」也要查？

| # | 理由 | HFT 场景翻译 |
|---|------|--------------|
| 1 | **win 可能是假象** — 测量口径变了（采样窗口、指标定义、样本量） | P99 突降 20% 是真的，还是今天 tick 量减半导致分位数样本不足？ |
| 2 | **win 可能不可持续** — 来自缓存预热、邻居暂时撤离、CPU 未降频的偶然窗口 | 隔壁策略进程今天停机维护；明天恢复，你「优化」的效果归零 |
| 3 | **win 背后可能藏着坏消息** — 某条路径被跳过了（缓存命中掩盖了故障） | 行情处理变快是因为**部分数据根本没到**（上游丢包 / 订阅降级） |
| 4 | **无法复现 = 无法守护** — 不知成因的 win 无法写进 runbook、无法在新机器上重现 | 扩容到新节点时，为什么新机器没有这个 win？答不上来 |
| 5 | **知识不对称** — 回归逼你查根因，win 让你错过唯一的免费学习机会 | 生产环境免费做了一次 A/B 实验，不分析等于浪费 |

**Gregg 的立场（Ch 16 开篇）：** 性能工程师的目标不是「让指标变好」，而是 **理解系统行为**。指标变好但原因未知 = 系统行为未被理解 = 排查能力有缺口。

---

### 二、「变快」的五类真相（Taxonomy）

> 排查的第一步：把「unexplained」拆成 **可检验的候选类别**。这继承 Ch 2 的科学方法——先列假设，再逐个证伪。

| # | 真相类型 | 典型信号 | 首选验证手段 | 对应章 |
|---|----------|----------|--------------|--------|
| ① | **负载变化** | 请求率/数据量同时下降；workload 特征变了 | `mpstat`/应用 counter：吞吐分母变了吗？ | [Ch 2](../../chapter-02-methodologies/) |
| ② | **环境变化** | 邻居（同机租户/共置进程）消失或变安静；云宿主机更换 | steal time、`/proc/pressure/*`、邻居监控 | [Ch 11 云](../../chapter-11-cloud-computing/) |
| ③ | **配置变化** | 内核升级、镜像重建、sysctl drift、库/JVM 版本变化 | 配置快照 diff（16.1.4） | [Ch 3](../../chapter-03-operating-systems/) |
| ④ | **状态变化** | 冷缓存→热缓存、预读生效、JIT 预热完成、page cache 装满 | 对比冷启动 vs 稳态（Ch 12 的 warm-up 纪律） | [Ch 12](../../chapter-12-benchmarking/) |
| ⑤ | **真实优化** | 代码/数据布局/调度真变好，且 **可复现** | PMC（IPC/cache-miss）+ profile 前后对比 | [Ch 13](../../chapter-13-perf/) |

**关键认识：** ①②③④ 四类都是「环境的偶然」——它们的特点是 **不稳定**：换台机器、换个时段、邻居回来，win 就没了。只有 ⑤ 是系统性的、值得写进 release note 的资产。区分 ①–④ 与 ⑤，就是本章整个案例研究要演示的事。

### 三、HFT 类比：P99 tick 突降的六种可能

**场景：** 新版本上线后，策略进程的 tick 处理 P99 从 8 µs → 5 µs。团队 Slack 里已经有人发 🎉 了。你的任务：在庆祝之前回答「为什么」。

| 候选 | 机制 | 怎么快速证伪 |
|------|------|--------------|
| 策略代码真的变快了 | 热路径删了分支 / 换了数据结构 | `perf diff` 前后 profile 对比（16.1.7） |
| 共置邻居撤了 | 同 NUMA 节点的兄弟进程停了，LLC/内存带宽释放 | `mpstat` 看 **其他** 核的利用率是否同时下降 |
| THP / 页表状态变化 | 昨晚 compaction 把策略的 hot pages 合成大页了，TLB miss 消失 | `/proc/<pid>/smaps` 看 AnonHugePages；[06-linux-mm ch03](../../../06-linux-mm/chapter-03-page-table-management/) |
| 绑核终于生效 | 上次部署后 taskset/isolcpus 才真正生效（之前 affinity 配错） | `taskset -pc <pid>` + `perf stat` 的 cpu-migrations |
| 行情本身变了 | 上游 throttle / 合约集合减少 / tick 量降 | 行情侧 counter：每秒 tick 数前后对比 |
| 测量口径变了 | 延迟打点代码挪了位置（比如少打了一段路径） | code review 打点 diff；直方图 **形状** 是否突变（而不仅是位置平移） |

> 注意最后一行：**直方图形状 vs 位置**。真正的优化通常改变分布的某个部分（比如消掉一个长尾 bump）；测量口径变化往往让 **整个分布** 平移。这是 Ch 12 的「基准拷问」在实战中的直接应用。

### 四、baseline 纪律：Win 的可解释性是事前准备出来的

Unexplained Win 之所以 unexplained，往往不是排查能力不够，而是 **案发时没有可比的 baseline**。Gregg 在 Ch 12/Ch 16 反复强调的事前纪律：

| 要素 | 内容 | HFT 落地 |
|------|------|----------|
| **同条件对照组** | 对比必须同 workload、同时段类型、同硬件 | 昨天的 P99 vs 今天的 P99，若两天行情波动率差 3 倍，不可比 |
| **连续采集** | sar / Prometheus 持续归档，而不是出事才采 | 案发 **前** 的系统指标是排查的本钱（16.1.3） |
| **配置快照** | 每次部署自动落一份 `sysctl -a` + `/proc` 快照 + 镜像 tag | 16.1.4 的 diff 才有得 diff |
| **测量路径固定** | 打点位置、聚合方式、分位数算法定版并版本化 | 指标代码变更 = 声明式变更，走 review |
| **可回放** | 录制行情流（pcap / 二进制 replay），能重放对比 | 新旧 binary 同一份录制流上 A/B |

> 这就是「实验设计」而非「救火」。Netflix 案例能一路走到底，靠的正是生产监控（Atlas）里的历史数据 — **证据是案发前就埋好的**。

<summary>代码自测（Q&A，先遮住答案想）</summary>

**Q1：为什么「变快」比「变慢」更少被排查？这带来什么系统性风险？**

A：变慢有外部压力（投诉/告警/SLA），变快没有——甚至会被当成「理所当然的好运」。系统性风险在于：① 无法复现的 win 会静默消失，回归时反而当成「新问题」排查，浪费一次彻底的 root cause 机会；② win 可能掩盖故障（数据没到导致处理变快）；③ 组织失去免费 A/B 实验的学习价值。

**Q2：五类真相中，哪一类最需要「事前准备」才能识别？为什么？**

A：③ 配置变化（含环境/镜像 drift）。负载、缓存、邻居都可以在案发后用观测工具追查（sar 历史还在），但配置是 **状态不是事件**——案发后只能看到「现在的配置」，除非部署时留了快照，否则永远不知道「变了什么」。这也是 16.1.4 强调配置审计的原因。

**Q3：直方图「整体平移」vs「长尾 bump 消失」，分别更可能对应什么？**

A：整体平移 → 多半是测量口径/时间基准变了（打点挪位置、时钟源变化），或全局性环境变化（如 CPU 频率）。长尾 bump 消失 → 更像真实的优化消灭了某类慢事件（如消除了偶发的 cache miss 风暴或调度迁移）。分布形状比均值携带更多因果信息。

**Q4：HFT 里「win 背后藏着坏消息」举一个具体例子。**

A：行情处理延迟突然变好，实际原因是上游组播丢包导致部分 tick 未投递——处理量下降，平均延迟自然下降。验证手段：对比上游重传/修复计数（feed handler 的 gap/repair 统计），确认 tick 量没有下降。**吞吐与延迟必须同看**（Ch 2 工作负载分析）。

</details>
