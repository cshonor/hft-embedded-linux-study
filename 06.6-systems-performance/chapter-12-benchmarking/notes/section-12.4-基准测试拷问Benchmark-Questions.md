## 12.4 基准测试拷问（Benchmark Questions）

> 章节导航：[12.3 基准测试方法论](./section-12.3-基准测试方法论.md) · 上一篇 ← · [本章导读](../README.md)

**本节讲什么**：面对别人（尤其厂商）的亮眼基准报告时的系统性拷问清单——按「工作负载 / 指标统计 / 方法可复现 / HFT 特供」四组展开，以及反向视角：怎么让自己的报告经得起同样拷问。

### 要点

| # | 要点 | 一句话 |
|---|------|--------|
| 1 | **亮眼数字默认可疑** | 拷问是义务，不是失礼 |
| 2 | 三大穿切入点 | workload 形状、统计口径、测量点位置 |
| 3 | **测量点位置**最隐蔽 | NIC 时间戳 vs 应用时间戳差整条栈 |
| 4 | 每个问题对应一个**常见作弊手法** | 知道怎么骗才知道怎么问 |
| 5 | 自己的报告要能**扛住**这清单 | 反向自检 |

---

### 一、拷问的本质：知道怎么骗，才知道怎么问

厂商基准的优化空间不在造假，而在**合法地选择对你不利的口径**：

| 优化手法 | 合法性 | 效果 |
|---------|--------|------|
| 挑自己最强的块大小/队列深度 | 完全合法 | IOPS 差 100× |
| 报均值不报 tail | 合法 | 丢包和尖刺全隐藏 |
| 测量点放在 NIC 而不是应用 | 合法 | 少算整条内核栈 |
| 预热后测最好的一轮 | 合法 | 冷启动差异消失 |
| 专用调优机 vs 你的默认配置 | 合法 | sysctl/固件差异 |
| 循环到出现最好数字为止 | 灰色 | 幸存者偏差 |

拷问清单就是把这些口子一个个堵上。

### 二、第一组：工作负载与环境

| 问题 | 为何重要 | 期待的回答 |
|------|----------|-----------|
| 测试的**具体 workload** 是什么？ | 「500k IOPS」何种块大小、随机/顺序、队列深度？ | 完整参数表 |
| 与**我们生产**有多像？ | 不像则数字仅供参考 | 访问模式对比 |
| **硬件/软件栈** 完整配置？ | 特定 NIC 驱动、特定内核的调优不可迁移 | 型号+版本+sysctl |
| 是否**专用机** / 无邻居？ | 云 shared vs 裸金属差数量级（[ch11](../../chapter-11-cloud-computing/)） | steal 数据 |
| **预热** 了吗？测的是冷还是热？ | 第一次 vs 稳态差数量级 | 预热协议 |
| **温度/功耗** 状态？ | 热降频是嵌入式和 dense 机房的隐藏变量 | 温度曲线 |

### 三、第二组：指标与统计

| 问题 | 为何重要 |
|------|----------|
| 报的是**平均**还是 **P99/P999**？ | HFT 看 tail（[12.1](./section-12.1-基准测试的背景与挑战.md)：均值对排队噪声盲） |
| 测试**时长**？样本量？ | 太短无统计意义；60 秒样本的 P999 是 36 个点 |
| 有无**错误/丢包/重传**？ | 吞吐高但丢包无意义——UDP 打满不检查=测发送能力 |
| **成本/瓦数**？ | 同吞吐不同功耗，机房成本完全不同 |
| **方差**？多轮结果一致性？ | 单轮最优 vs 多轮稳定是两个产品 |

### 四、第三组：方法与可复现

| 问题 | 为何重要 |
|------|----------|
| 工具与**完整命令行**？ | 能否复现 |
| 是否 **drop_caches** / O_DIRECT？ | 测 cache 还是测盘（[12.1 失败模式①](./section-12.1-基准测试的背景与挑战.md)） |
| 瓶颈 **profile** 在哪？ | 是否测到 intended layer——有没有火焰图/USE 数据证明瓶颈在声称的位置 |
| 与**竞品**测试条件是否一致？ | 苹果 vs 橙子 |
| 测量点在哪一层？ | 见下 |

**⭐ 测量点位置（最隐蔽的口径差异）**：同一个「延迟」，测量点从 NIC 硬件时间戳到应用层 span，中间隔着驱动 → 中断/轮询 → 协议栈 → epoll → 业务代码，每一层都有排队和处理时间：

```
NIC 硬件时间戳        ~ 最低数字（厂商最爱）
  ↓ 驱动+DMA            + 2-10µs
中断/轮询收包
  ↓ 协议栈              + 1-5µs（UDP）~ 更多（TCP）
  ↓ epoll 唤醒          + 1-20µs（调度器参与）
  ↓ 应用读到包           ← 真正的 tick-in 时间
  ↓ 解码+策略+发单       ← end-to-end（客户感知）
```

报告不写测量点 = 无法比较。对照 [ch16.1.5 的 PMC 判读](../../chapter-16-case-studies/)和 [14-HFT ch09 的延迟测量点谱系](../../../14-hft-engineering/chapter-09-latency-measurement-benchmarking/README.md)。

### 五、第四组：HFT vendor 拷问加项

- 测的是**内核栈还是 DPDK**？RX 队列几条？RSS/绑核了吗？
- **报文大小**是否像真实行情（小 UDP 多包 burst）？
- **RTT** 测量点在哪（NIC timestamp vs 应用）？
- 是否包含**交易所共置 RTT** 还是实验室回环？
- **噪声隔离**口径：isolcpus？nohz_full？中断赶走了吗？（[ch6 调优](../../chapter-06-cpus/)）
- tick 处理是**单流还是多 symbol 并发**？锁行为完全不同。
- 报价的是**发包延迟**还是**收包→决策→发单全链**？

### 六、反向自检：让自己的报告无懈可击

给自己的基准报告做一次「预拷问」：

```
□ 标题就写清：什么负载、什么口径、什么结论
□ 完整命令行 + 环境清单（12.1 的复现配置）
□ 分布图（不只表格）+ 样本量
□ 多轮结果 + 方差
□ 测量点位置图示
□ 瓶颈证据（profile/USE 数据）
□ 结论的作用域声明（适用于 X，不外推 Y）
□ 错误率/丢包/重传一并报告
```

**Gregg 精神**：极亮眼的数字默认可疑——用问题拆穿或验证；同时，**你自己交出去的每个数字，都要经得起同样的拷问**。

### HFT / 嵌入式关联

- **采购谈判**：这四组问题就是 RFP 的验收条款——vendor PPT 的 200ns 延迟和你要测的应用层延迟之间的差距，要用测量点问题当场揭穿。
- **内部汇报**：策略团队给管理层看的基准报告同样适用——「改了 X 之后快了」必须附带测量点、分布、多轮方差，否则就是给自己埋雷。
- **嵌入式**：板卡 vendor 的「支持线速」通常是最小包回环——问包大小分布、温度状态、并发流数。

### 常见陷阱

1. **只拷问别人不自检**——自己的报告同样要过这四组问题。
2. **忘记问测量点**——「延迟」两个字在 NIC 和应用层差一个数量级，这是最隐蔽的口径游戏。
3. **被单轮最优忽悠**——问方差和多轮一致性。
4. **吞吐高就下单**——不问错误率/丢包的吞吐是发送能力测试，不是服务能力测试。

1. 厂商基准最常见的三个合法口径游戏？
   <details><summary>答</summary>①挑自己最强的块大小/队列深度；②报均值不报 tail；③测量点放在 NIC 硬件层而非应用层（另外还有预热后测、专用调优机）。</details>
2. 「P99 = 3µs」报告最该追问什么？
   <details><summary>答</summary>测量点在哪一层（NIC 时间戳还是应用 span）、样本量多少、多轮方差如何——三者缺一不可比。</details>
3. 为什么 UDP 打满的高吞吐无意义？
   <details><summary>答</summary>不检查丢包的 UDP 发送测的是发送能力——接收端可能大量丢包，服务能力为零。吞吐必须和错误率一起报。</details>
4. 60 秒测试报告 P999 有什么问题？
   <details><summary>答</summary>60 秒里 P999 对应约 36 个样本点——统计意义极弱，长尾估计不稳定，需要更长时长或多轮。</details>
5. 自检清单里「结论的作用域声明」指什么？
   <details><summary>答</summary>明确写出结论适用于什么负载/环境/条件，不外推到什么——防止三个月后被人拿去当万能结论。</details>
