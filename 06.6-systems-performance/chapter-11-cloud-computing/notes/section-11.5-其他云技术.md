## 11.5 其他云技术

> 章节导航：[11.4 MicroVM](./section-11.4-轻量级硬件虚拟化MicroVM.md) · 上一篇 ← · [本章导读](../README.md)

**本节讲什么**：FaaS 的冷启动机制与观测局限、Unikernel 的极致取舍、本章云技术的性能全景收束（按延迟敏感度选部署形态）。

### 要点

| # | 要点 | 一句话 |
|---|------|--------|
| 1 | FaaS 的代价是**冷启动 + 观测降级** | 便利换控制权 |
| 2 | 冷启动三层成本 | 运行时拉起 → init → **首请求慢** |
| 3 | Unikernel 潜力大、**工具链荒漠** | 无 OS = 无观测 |
| 4 | 部署形态 = **延迟敏感度**的函数 | 裸机→容器→microVM→FaaS 阶梯 |
| 5 | HFT：偶发任务上 FaaS，热路径离云越远越好 | — |

---

### 一、FaaS（Serverless）

| 优点 | 性能代价 |
|------|----------|
| 免运维、按调用计费 | **冷启动**（容器/MicroVM 拉起 + runtime init） |
| 自动扩展到零 | **无法** SSH + 全套 perf 栈——观测靠**平台日志/Tracing** |
| 无容量规划 | 执行环境不可预测（实例复用/回收策略黑盒） |

**冷启动的三层成本**（以容器型 FaaS 为例）：

```
层 1  基础设施拉起   容器/microVM 启动           100ms ~ 秒级
层 2  运行时 init    JVM/Python 解释器/依赖加载   秒 ~ 10s（JVM 最惨）
层 3  应用 init      连接池、缓存预热、首 JIT     首 N 个请求显著变慢
```

各云的对策本质都是 [11.4 的思路](./section-11.4-轻量级硬件虚拟化MicroVM.md)：microVM 快照（Firecracker）、预置容器池（层 1 消掉）、按流量保活（层 1+2 消掉，但收闲置费）。**JVM 类运行时的层 2 是用户态问题**，快照解决不了——语言选型决定冷启动命运。

**观测降级**：没有 SSH、没有 perf/BPF、没有 [ch13/ch14/ch15 的工具箱](../../chapter-13-perf/)——只剩结构化日志 + 分布式 Tracing + 平台指标。性能工程从「系统级」降级为「应用级黑盒」：

| 传统部署 | FaaS 等价物 |
|---------|-------------|
| perf 采样 | ❌（无权限） |
| BPF/bpftrace | ❌ |
| runqlat/biolatency | ❌ |
| 应用日志 + span | ✅（唯一细粒度来源） |
| 平台指标（时长/内存/并发） | ✅（聚合口径） |

**HFT**：适合**偶发任务**（日终报表、告警处理、数据搬运）；**绝不**放 tick/发单热路径——不是冷启动一个问题，是观测不可达 + 执行环境黑盒两个结构性障碍。

### 二、Unikernels

应用 + 极简 libOS 编译成**单一镜像**，直接跑在 hypervisor/裸机上（MirageOS、Unikraft 系）：

| 特点 | 代价 |
|------|------|
| 无通用 OS——syscall 直通应用 | 极致性能潜力（启动 ms 级、内存 MB 级） |
| 攻击面极小（没有多余系统调用） | **观测工具缺乏**：没有 /proc、没有 perf、没有 BPF |
| 单地址空间单用途 | 调试难：崩溃即整机消失，无 core dump 生态 |
| | 生态窄：每换依赖要重编译镜像 |

Unikernel 的哲学是「不需要观测，因为里面没有多余的东西」——这在**已知行为**的固定功能负载（如协议网关）上成立；但性能工程的前提是**测量**，放弃观测工具链对调优工作是致命的。

**HFT**：学术/极端场景（研究型超低延迟协议栈有价值）；工程主流仍是 **Linux 裸机 + DPDK**——观测能力是工程化的生命线。同类思路的现代变体：DPDK 本身就类似「网卡旁路的 unikernel 化」——poll mode + 用户态栈，但保留完整 Linux 工具链（[13-DPDK](../../../13-dpdk/)）。

### 三、本章收束：部署形态 = 延迟敏感度的函数

```
延迟容忍度
  ns ~ µs   │ 裸金属 + 绑核 + 直通           ← HFT 热路径
   ~10µs    │ 裸机 + 容器（dedicated 核）
   ~100µs   │ 共享云 VM / microVM
   ~ms      │ 容器平台（K8s）
   ~100ms   │ FaaS（含冷启动）               ← 偶发任务
```

| 形态 | 隔离 | 性能 | 观测 | 弹性 |
|------|------|------|------|------|
| 裸机 | 物理隔离 | ★★★★★ | ★★★★★ | ❌ |
| 容器 | 共享内核 | ★★★★ | ★★★（cgroup 口径） | ★★★ |
| MicroVM | 独立内核 | ★★★ | ★★★★（Guest 内全套） | ★★★★ |
| VM | 独立内核 | ★★ | ★★★（两层盲区） | ★★★ |
| FaaS | 独立内核+平台 | ★★（冷启动） | ★（日志/tracing） | ★★★★★ |

没有「最好」的形态——每个格子是不同诉求的最优点。HFT 工程师的工作是把**自己的每个组件**放到正确的格子里。

### 常见陷阱

1. **FaaS 保活当免费午餐**——最小实例数计费是闲置费；按调用计费与常驻延迟是矛盾需求。
2. **冷启动只测层 1**——基础设施拉起快 ≠ runtime init 快，JVM 的层 2 才是大头。
3. **Unikernel 数字直接信**——无观测环境下的 benchmark 无法用第二工具交叉验证（违反 [ch12 sanity check](../../chapter-12-benchmarking/notes/section-12.3-基准测试方法论.md)）。
4. **热路径侥幸上 FaaS**——观测黑盒意味着出问题只能等，无法定位。
