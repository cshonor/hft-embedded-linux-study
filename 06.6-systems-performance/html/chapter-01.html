大白话 · 本章就三件事

先记住下面顺序，后面学工具时不迷路。

① 目标就一句：让程序跑更快、等的时间更少。

  • 书里叫降低延迟、提高吞吐量；量化里就是：行情到了 → 算完 → 发出去，整条链路上少等一点。
  • 下单少等 1ms，有时就是更好的成交价 — 这就是性能优化的业务价值。
  • 热路径 = 上面这条链路上 每个 tick 必跑 的那几段代码 → 1.4 定义

② 不同人看性能的角度不一样。

谁 主要看什么
开发 代码逻辑、程序在干什么
运维 CPU、内存、磁盘、网络够不够用
你做量化 策略计算 + 发单这两步各花了多久（够用就行，不必照搬运维全套）

③ 找问题有固定顺序 — 别一上来钻底层代码。

先看：程序要做什么工作（业务流程 / 热路径）
再看：用了多少 CPU、内存、网络（资源消耗）

对应原书两个词：工作负载分析 → 资源分析。
你现在的抓手：先看业务流程，再查资源消耗。

量化专用： 行情 tick 全链路 Checklist · HFT 10 秒检查清单（1.10 节）

下面各节是同一套内容的展开；工具名、60 秒清单等用到时再查即可。

1.1

section-1.1-1.3-系统性能角色与活动

系统性能是什么

研究对象是整个计算机系统在数据路径上的全部主要软硬件组件，而非单一进程或单块网卡。

典型目标 含义 HFT 对应
降低延迟（Latency） 缩短等待时间，改善体验 行情→决策→发单全链路 μs 级
提升吞吐量（Throughput） 单位时间处理更多工作 每秒处理更多 tick/订单
消除低效、降成本 同样硬件做更多事 裸机共置、CPU/NUMA 不浪费

参与角色

角色 关注点
系统管理员 / SRE 生产稳定性、资源、监控
应用开发者 业务逻辑、工作负载特征
网络 / DB 管理员 专项子系统
性能工程师 深入排查、开发/使用性能工具

HFT： 小团队常一人兼多角 — 既要懂策略（ workload ），又要懂绑核/网络/内核（ resource ）。

生命周期中的 11 项活动（摘要）

设定性能目标 → 原型测试 → 版本基准 → 生产调优 → 监控 → 事故回顾 ……

HFT 要点：

  • 上线前 就要有延迟/抖动 SLO（目标），不是上线后才量
  • 生产调优 与 事故回顾 对应 tail latency、P99 尖刺排查
  • 与 14-HFT ch10 延迟测量 衔接

HFT · 行情 tick 全链路 Checklist

用法： 先 workload（每段在干什么）→ 再 resource（哪段慢/抖）→ 对照下面打勾。单点 CPU 跑分不能代替这张表。

端到端数据路径（单 tick / 单订单）：

[网卡 DMA] → [驱动/NAPI] → [内核协议栈 或 bypass]
      → [copy 到用户态 / mmap ring]
      → [解码：SBE/FIX/私有二进制]
      → [策略：信号 + 风控]
      → [订单序列化 + 发单]
      → [内核/网关 → 网卡 TX]

A. 工作负载分析 — 「程序在干什么？」

段 要问的问题 常见 hot path
收包 组播还是 TCP？几路 feed？每 tick 多少字节？ 每包一次 epoll/read；batch 还是 per-packet
进用户态 copy 还是 zero-copy（mmap/DPDK/onload）？ recvmsg + 拷贝 vs ring buffer
解码 定长还是变长？版本分支？endian 按 offset 解析；避免 heap/printf
策略 热路径算什么？分支可预测吗？ 均线/价差/库存；branch-misses
风控 同步还是预检查？锁吗？ 全局 map vs 单 writer
发单 同步 write 还是队列 + 专用线程？ TCP_NODELAY；connect 是否长连

B. 资源分析 — 「哪段在等？」

段 看啥 工具 / 章节
网卡 → 内核 softirq、丢包、rx_missed_errors ethtool -S · Ch 10 网络
内核栈 协议栈延迟、锁、cross-NUMA perf、ftrace · 13-DPDK bypass
CPU IPC、frontend/backend stall、绑核是否生效 perf stat · Ch 6 CPU
内存 cache miss、page fault、false sharing perf mem · Ch 7 内存 · CSAPP Ch6
磁盘 热路径是否误触日志/sync 热路径 不应 有 disk I/O；NVMe 仅冷路径
端到端 P50/P99/P999、抖动 tail 硬件 timestamp / HFT ch10 延迟测量

C. 自检清单（上线 / 排障时逐项过）

架构 & 目标

  • [ ] 写清 SLO：tick→决策、决策→发单、端到端 P99 上限（μs/ms）
  • [ ] 能画出 单 tick 路径图（与上面框图一致，标你的实际组件名）
  • [ ] 区分 测量点：网卡硬件时间 vs 用户态 clock_gettime（含时钟源与开销）

收包 & 网络

  • [ ] 数据面网卡 NUMA 与 CPU 同节点；IRQ/RSS 与收包线程同核或明确 affinitize
  • [ ] 知悉走 内核栈还是 bypass（DPDK/onload/socket+epoll）及 tradeoff
  • [ ] 无静默丢包（drop、no_buffer 监控）

进进程 & 解码

  • [ ] 热路径 无 malloc、无 stdio、无 JSON（除非 cold path）
  • [ ] 协议解析 layout 与 spec 一致（→ CSAPP「比特+上下文」）
  • [ ] 解码 buffer 预分配 / 环形复用

策略 & CPU

  • [ ] 热路径 绑核（isolcpus / taskset / pthread_setaffinity）
  • [ ] Release 构建：-O3 -march=native -DNDEBUG，CI 与生产一致
  • [ ] 看过 hot path 汇编或 perf 火焰图，知悉 top 函数

内存

  • [ ] 热路径数据 mlock / 大页 / 启动时 pre-fault
  • [ ] 多线程共享计数器无 false sharing（cache line 对齐）

发单 & 收尾

  • [ ] 订单通道 长连接；TCP_NODELAY 等已设
  • [ ] 日志、监控、持久化在 cold path 或异步，不挡 tick
  • [ ] 实盘启动 无 shell；固定 daemon + 预热（连接、页、cache）

D. 排障顺序（别跳步）

1. 端到端计时 — tail 变长还是整体变慢？
2. workload — 哪一段逻辑变重（新功能？新分支？）
3. resource — CPU/softirq/丢包/NUMA/page fault 哪个亮红灯
4. 只优化测量到的瓶颈（阿姆达尔；→ CSAPP 1.9）

→ 方法论：Ch 2 · 工具：Ch 4 · Ch 13 perf

常见陷阱

  1. 把延迟和吞吐混为一谈——HFT 行情机吞吐够高但 P99 尖刺照样致命，两者必须分开测分开报
  2. 上线后才定性能目标——SLO 应在架构设计阶段就定义（如 tick-to-trade P99 < X us），不是出事再补
  3. 只盯单点 CPU 跑分——全链路 Checklist（DMA→协议栈→解码→策略→发单）任何一段都可能成为瓶颈，单点跑分不能代替端到端

section-1.4-热路径Resource与双视角

排障案例 → 1.5

热路径 Hot Path — 程序的「主动脉」

热路径 = 程序里 被高频反复执行、吃掉 绝大多数 CPU 时间与延迟波动 的核心代码链路。

热路径 Hot 冷路径 Cold
调用频率 每个 tick / 每包 / 每单 必跑 启动一次、偶发、后台
代码占比 往往 ~5% 行数 ~95% 行数
性能占比 ~95% CPU / 延迟 可忽略（除非误触）
HFT 例子 收包 → 解析 → 信号 → 发单 初始化、读 config、打日志、监控上报

HFT 整条热路径（一张图画死）：

网卡收行情 → 进用户态 → 解析（SBE/FIX/私有）
    → 策略信号计算 → 风控/哈希校验 → 报文打包 → 发单出网卡

感同身受的例子： 策略里 100 个函数，90 个是初始化、日志、配置 — 低频；只有下面 3 个 每个 tick 跑、每秒几万次：

  1. 行情逐笔处理
  2. 订单哈希校验
  3. 报文打包发送

这 3 个 串起来就是热路径。性能上的 二八原则：热路径是决定 80% 表现的那 20% 代码 — 做 HFT 调优 80% 精力砸这里，别在冷门逻辑上抠细节。

怎么找热路径（和后面两种视角衔接）：

perf record -g -p <pid> -- sleep 10 && perf report   # 宽栈上最宽的 = hot
# 或火焰图：顶部的「平台」函数 = 每个 tick 都经过的主动脉

→ 找到 hot 之后，才谈 resource 给这条路开没开好（下一节）· 全链路清单 1.1–1.3

Resource 是什么 — 和热路径一一对应

Resource（资源） 不是泛指的「机器配置表」，而是 热路径跑起来所依赖的那套底层软硬件：

资源层 HFT 热路径上具体指什么
CPU 绑哪几个核、isolcpus、与 IRQ/其他进程 是否抢同一核
Cache 命中率、false sharing、是否被 softirq 冲刷
内存 NUMA 哪节点分配、是否 cross-node、page fault / 大页
网卡 IRQ/RSS 绑哪核、队列深度、drop / rx_missed_errors
OS 调度、锁、syscall 频率、协议栈 vs bypass

HFT 直觉： 热路径跑不快，Often 不是代码算得慢，是底层资源没给热路径「开好路」 — 路和车要一起画。

→ 逐项对照：tick 全链路 Checklist · B 资源分析

两种分析视角 — 两个方向，拧成一股绳

视角 方向 典型角色 问法
工作负载分析 Workload analysis 自上而下 应用开发者 「这个程序在做什么？」
资源分析 Resource analysis 自下而上 系统管理员 / SRE 「CPU/内存/磁盘/网络够吗、忙吗？」

自上而下 · 从业务代码往下挖

订单/解码函数（你写的逻辑）
  → perf top / perf record -g：哪个函数占比最高？
  → 顺着调用链往下：库函数 → syscall → 驱动/硬件相关栈
  • 起点： 热路径函数（如下单、行情解析）
  • 工具： perf top、perf report、火焰图
  • 终点： 找到 哪段业务逻辑 变重，或是否意外掉进 syscall / 锁 / IO

自下而上 · 从系统资源倒推进程

mpstat：某核 %soft 飙高？策略核 usr 低但不 idle？
  → numastat：哪个进程 cross-NUMA？
  → ethtool -S：网卡 drop？
  → 倒推：是哪条 IRQ 线、哪个进程在滥用/争用这些资源
  • 起点： CPU / 内存 / 网卡 指标异常
  • 工具： mpstat、numastat、ethtool -S、perf stat、USE 法
  • 终点： 找到 哪块资源在争用，再关联到 哪个进程、哪段代码

HFT — 两方向必须交叉验证

自上而下：下单函数 perf 占比突然升高  →  「这段逻辑变慢了」
     ↓ 立刻
自下而上：它绑定的核是否 == 网卡 IRQ 核？NUMA 是否错节点？
     ↓
合并：改资源拓扑（迁 IRQ / 对齐 NUMA）+ 改热路径代码 — 见下方案例

从分工来记（问题发起者 vs 问题解决者）：

工作负载（自上而下） 资源（自下而上）
谁更常发起 应用开发者 — 写代码的人最清楚业务逻辑 运维 / 性能工程师 — 从硬件和 OS 指标反推
看什么 热路径、订单流、每 tick 干什么 CPU 饱和、softirq、NUMA、丢包、page fault
典型工具 火焰图（业务函数）、代码审查、tracing 业务 span top/perf stat/ethtool -S/USE 法

两者互补，不是二选一：症状可能是 workload 设计问题（热路径多了 JSON），也可能是 resource 瓶颈（跨 NUMA 收包）— 先 workload 定位段，再 resource 找因。

HFT — 两种视角都要会：

你写策略时  →  应用开发者  →  自上而下：解码→信号→风控→发单，各段逻辑是什么？
你调延迟时  →  性能工程师  →  自下而上：网卡/CPU/内存哪段扛不住、哪段在等？

小团队 同一个人戴两顶帽子 — 不是「选应用还是选网络」，而是 同一条 tick 链路上交替用两种问法。网络专项（RSS、IRQ 亲和）是 resource 分析里的 一块，不是和「应用开发者」并列的二选一角色。

→ 案例 1.5 · 指标 1.6 → 方法论 Ch 2（USE/RED 等）· tick 全链路清单见 1.1–1.3

常见陷阱

  1. 只看 resource 不看 workload——CPU 高但不知道在算什么，等于白看；workload 分析先于 resource 分析
  2. workload 和 resource 视角二选一——Gregg 强调互补而非互斥，排查用 workload 定位、容量规划用 resource 量化
  3. 热路径定义模糊——必须明确哪些函数/线程在 tick 关键路径上，否则优化方向跑偏
自测题（点击展开）
  1. workload 分析和 resource 分析分别问什么问题？
答

workload 问「程序在干什么」，resource 问「哪段在等/慢」

  1. HFT 热路径包括哪些段？
答

收包→进用户态→解码→策略→风控→发单，每段都有 workload 和 resource 两个维度

  1. 为什么不能只看 resource 利用率？
答

利用率高不代表在干有用的事——可能是 spin 忙等或内核锁开销，需要 workload 视角确认在做什么

案例 · 逐笔排序变慢 — 双视角怎么配合

场景： 上线「逐笔成交排序」后，端到端延迟变差。HFT 没有单一视角的解法 — 必须 workload + resource 对齐 后再改。

① 自上而下 · 工作负载（先定位「哪段业务逻辑变重」）

perf record -g -p <策略进程 PID> -- sleep 30
perf report --no-children
# 或火焰图：perf script | stackcollapse-perf.pl | flamegraph.pl > fg.svg
观察 结论
行情解析相关栈 10% → 40% 热路径确实变重 — 指向新功能
点进 call chain 「逐笔成交排序」 占大头 — workload 问题点锁定

此时结论（未完成）： 新排序逻辑拖慢了解析段 — 但别立刻只改代码。

② 自下而上 · 资源（同步核查「底层是否在拖后腿」）

命令 看什么 可能发现
mpstat -P ALL 1 每核 %soft / %usr / %idle 某核 softirq 飙高；策略核 不 idle 但也不在跑 usr
numastat -p <pid> 跨节点 内存访问 numa_foreign / other_node 偏高
ethtool -S eth0 网卡 drop / rx_missed_errors 静默丢包 or 背压

典型叠加根因（本案例）：

网卡 IRQ / softirq 绑定的核  ==  策略进程绑定的核
  → CPU cache 被中断 handler 频繁冲刷
  → 哪怕排序算法优化了，延迟仍压不下去

上层 workload 的「变慢」有时只是 表象 — 底层 资源争用 同时在放大 tail latency。

③ 合并结论 · 双管齐下

层 动作 解决什么
Resource 网卡中断 / NAPI 迁到独立核；策略进程与 feed NUMA 本地、同节点内存 消除 IRQ vs 策略的 核竞争、cross-NUMA
Workload 排序改为 预分配固定数组、无热路径 malloc；或移出 tick 热路径 降低解析段 本身 CPU 时间 
错误路径：只看 perf → 只改排序算法 → 延迟仍高（IRQ 还在抢核）
正确路径：perf 定位段 + mpstat/numa/ethtool 找争用 → 先调亲和/NUMA → 再改逻辑

HFT 原则： 上层业务逻辑与底层资源调度 完全对齐 — isolcpus、IRQ balance、RSS、进程 affinitity 要和 hot path 设计 一起画在一张拓扑图里。

→ 工具：Ch 4 观测工具 · Ch 6 CPU 绑核 · Ch 10 网络 · Ch 13 perf

新手两大痛点 · 症状 vs 病根 · 「快慢标尺」

新手最常卡： ① 不知道什么算慢 ② 单视角容易漏根因 → 必须补自下而上。

痛点 ① · 没有「快慢标尺」— 要靠 resource 锚定

同样 10μs，在不同 resource 上下文里意义完全不同：

上下文 10μs 算…
数据在 L1/L2，纯寄存器运算 偏慢 — 该抠算法或分支
数据在 DRAM / cross-NUMA，含 syscall 可能正常 — 先查 cache/NUMA 再判代码

CPU 占比也不能单独看：

指标 表面 资源上下文下的真实伤害
下单函数 30% CPU 「最大热点」 点开栈：25% 在 malloc — 病根可能是分配器
网卡中断 5% CPU 「不高」 若与策略 同物理核 → tail jitter 可能比 30% usr 更致命

标尺来自自下而上： perf mem / cache miss、numastat、每核 mpstat — 先知道跑在什么路况上，再判快慢。

痛点 ② · 单视角 — 热点往往是症状，不是病根

案例 A · 下单 30% CPU — 其实是 malloc 锁

自上而下：perf → 下单函数占 30%  ← 症状
自下而上：展开 call chain → 25% 在 malloc/free
         → 默认 glibc 分配器高频 tick 下锁竞争严重
错 对
只优化下单逻辑 预分配内存池 / 热路径禁 malloc / jemalloc·tcmalloc / -fno-builtin-malloc 等

案例 B · 行情解析「慢」— 其实是远端 NUMA

自上而下：perf → 解析函数变慢  ← 症状
自下而上：numastat → 收包 buffer 在远端节点；或进程与 feed 不同 NUMA
错 对
死抠解析算法 先把内存/进程/IRQ 绑到 feed 同 NUMA — 不对齐则事倍功半

调优陷阱 · 别陷在「调单个函数」

性能工程难在 系统联动：

你自上而下抓的热点  ≈  症状（哪个函数宽）
自下而上查 resource  ≈  病根（为什么宽：malloc？NUMA？IRQ？）

固定动作： workload 锁定 哪一段 → 立刻 resource 核查该段依赖的核/内存/网卡 → 合并改 → 再 perf 验证。

→ 分配器：Ch 7 内存 · NUMA：Ch 6 · CSAPP Ch6 缓存

性能工程为何难

挑战 说明
主观性 「够快」因用户/场景而异
复杂性 级联故障、子系统相互影响
多重原因 一个症状多个根因
多问题并存 需优先级，先修最大头

HFT： 抖动常是 「多因叠加」 — 切忌只盯一个指标、当成单点故障。

案例 · 订单延迟超阈值 — 四因叠加

症状： 端到端延迟超 SLO。新手直觉：热路径里有一个 大热点 要修。
现实： 多个 单独看都不致命 的小问题，在高频 tick 下 放大 + 互相干扰。

① 自上而下 · workload

perf record -g -p <策略 PID> -- sleep 30 && perf report
观察 第一反应（错）
下单函数里 CRC 校验占 40% CPU 「算法慢，换校验方式 / 查表优化」

② 自下而上 · resource — 拆开这 40%

# 根因 单独看 叠加效果
1 网卡 IRQ 与下单进程同物理核 IRQ 本身占比可能不高 cache 被 softirq 频繁冲刷 → CRC「变宽」
2 远端 NUMA 分配 偶发 cross-node 每次 load 多几十 cycle，tick 上万次 累积
3 峰值时后台日志刷盘 cron 任务平时无害 行情高峰 撞车 → IO + 调度抖动
4 CRC 本身 可能确实偏重 在上面三样之上 再占一份 usr 
perf 看到的「CRC 40%」≈  症状汇总
  ├─ 真·算法 usr（可能只有 ~10%）
  └─ 被 IRQ/cache miss/NUMA 放大的部分（~30% 体感在 CRC 栈里）

③ 合并处置 — 单修 CRC 不够

顺序 动作 解决
1 IRQ / NAPI 迁出策略核 停 cache 冲刷
2 收包 buffer + 策略堆 同 NUMA 预分配 减远端 load
3 日志刷盘 移出峰值 / 异步 cold path 去掉调度/IO 撞车
4 再评估 CRC — 换实现或 SIMD/查表 真 workload 优化 
错误：perf 见 CRC 40% → 只换 CRC 算法 → P99 仍超
正确：resource 拆四因 → 先拓扑/NUMA/日志 → 最后才抠 CRC

新手误区 · 不是单点故障

误区 现实
「有一个热点函数要修」 热点是 多因叠加后的宽栈顶
「5% softirq 不重要」 与同核策略 叠加 → tail 致命
「逐个函数优化总会好」 不修 resource，上层越优化越像 打地鼠

必须用自下而上补全 resource 信息 — 否则永远碰不到 真正的根因组合。

→ 排障模板：逐笔排序案例 · malloc/NUMA 案例 · tick Checklist

常见陷阱

  1. 跳过基线直接排查——没有 baseline 就无法判断什么是「异常」，每次出事都从头摸
  2. 改一处不验证全局——修了 CPU 但引入了延迟抖动，性能优化必须前后对比完整指标集
  3. 用平均延迟代替分位数——HFT 场景 P99/P999 尖刺才是致命的，mean 可能完全正常
自测题（点击展开）
  1. 性能排障的第一步应该做什么？
答

建立基线（baseline）——知道系统正常时的指标范围，才能判断异常

  1. HFT 场景为什么 mean 延迟不够用？
答

P99/P999 尖刺导致错单或漏单，mean 可能完全正常但 tail 已爆

  1. Gregg 的性能挑战核心方法论是什么？
答

科学方法——假设→实验→验证，避免盲目改参数（随机调优反模式）

section-1.6-延迟指标与读法

观测工具 → 1.7 · 实验 → 1.8

延迟 Latency — HFT 订单链路怎么读数

  • 最基本、最重要的性能指标 — 可量化问题、估算理论改进空间（Amdahl / 关键路径）
  • HFT 核心：抓长尾、拆链路 — 别在 平均延迟 上死磕；实盘怕的是 偶尔掉链子的 0.1%

三类延迟指标 — HFT 怎么分类读

类 指标 含义 典型用途
① 平均类 Mean 平均 所有请求耗时的算术平均 压测基线：优化后先看均值是否压进目标（如 10μs 以内）
② 分位类 P50 / P99 / P999 P50=中位数；P99/P999= 99%/99.9% 请求的上限 长尾：最慢 1%、0.1% — 行情峰值是否掉链子
③ 极值类 Max 最大延迟 单次最坏情况 HFT 有时 比 P999 还敏感 — 只出现 一次 >1ms 也可能实盘大亏 
平均 10μs  +  P999 150μs  +  Max 1.2ms（一天只一次）
  → 平时、P999 统计上都可能「还行」
  → 但那一次 Max 撞上跳空 → 整笔滑点吃掉一周 alpha

HFT 优化优先级（和普通业务相反）：

1. 先卡死 Max 上限          ← 绝不允许的单次灾难
2. 再压 P999 / P99 抖动     ← tail 分布
3. 最后才抠平均延迟         ← 均值再低，一次 tail 可全白搭
阶段 看什么 通过标准（举例）
压测回归 Mean ↓ 方向对了
实盘 SLO P99 / P999 绝大多数 tick 稳
红线 Max 任何一次不得超硬上限

HFT vs 普通业务：

普通业务 HFT
优化顺序 平均 → P95 常够 Max → P999 → Mean
长尾 可接受偶发慢 一次 Max 撞上峰值 = 盈亏

→ 测量：HFT ch10 延迟测量 · Ch 12 基准测试

观测工具 ↔ 三类指标 — Metrics / Tracking / Profiling

工具类 典型代表 主要盯哪类指标 干什么
Metrics 指标 histogram、Prometheus、应用内分位统计 Mean + P50/P99/P999 基线 生产/压测 持续盯分位曲线；SLO 告警
Tracking 追踪 ftrace、eBPF/bpftrace、perf trace Max / 单次 tail 偶尔冒头的那一笔 — 逐步拆 RX→栈→策略→TX
Profiling 剖析 perf、火焰图 tail 根因嫌疑 定位 那次 Max 对应的热路径函数 / 锁 / syscall

计数器（mpstat、ethtool）补 resource 基线 — 与 Metrics 一起看「路况是否正常」，不替代分位与 Max。

固定工作流：

Metrics   →  P999 曲线升高了？Max 告警？
Tracking  →  抓住那一次 spike，分段 timestamp
Profiling →  同期 perf 火焰图 / 锁分析，找根因

单笔全链路拆段（Tracking）：

网卡收包 (RX) → 内核协议栈 / bypass → 策略计算 → 网卡发包 (TX)
spike 类型 Tracking 可能看到 落地
Max +1ms 线程 换出 ~100μs+ isolcpus、绑核
偶发解析尖刺 page fault mlock、预 fault
发单尖刺 锁 / syscall 内存池、长连接

别把工具用反：

错 对
只优化 Mean，不盯 Max 先 Max 红线，再 tail，最后 Mean
只用 Metrics 平均值告警 必须 histogram + Max 捕获
Max 出现后才凭感觉改代码 Tracking 抓样本 → Profiling 定根因

常见陷阱

  1. 只看平均值——HFT 必须看 P99/P999/最大值，分布的尾部才是交易风险
  2. 延迟分解不彻底——只说「慢」不分解到 DNS/TCP/应用/内核各段，无法定位
  3. 混用不同测量点的延迟——TTFB ≠ RTT ≠ 端到端，口径不一致导致对比无意义
自测题（点击展开）
  1. TTFB 和 RTT 的区别是什么？
答

TTFB = 请求→首字节（含服务端 think time），RTT = 网络往返时间

  1. HFT 延迟分解应该覆盖哪些段？
答

signal→encode→send()→内核 TCP→NIC→wire RTT→交易所 ACK，每段独立测量

  1. 为什么 P99 比 mean 更重要？
答

HFT 中一次 P99 尖刺就可能导致错价或超限，mean 被大量正常样本稀释

Gregg 四类工具 = 从粗粒度统计到全链路追踪 的排障阶梯；HFT 一般 按顺序走，别跳层。

计数器 Counters  →  指标 Metrics  →  剖析 Profiling  →  追踪 Tracing
   「有没有异常」     「什么时候开始高」   「哪段代码宽」      「这一笔逐步花在哪」
层 是什么 典型例子 回答什么

粒度：粗 → 中 → 细 — 追踪是 HFT 抓 tail 的核心

粒度 层 你看到什么 例句
粗 计数器 + 指标 聚合统计、趋势 「每秒 平均 延迟 10μs」「P999 曲线抬升了」
中 剖析 Profiling 函数级 时间占比 「下单函数占 30% CPU」— 不知 30% 里具体哪几步
细 追踪 Tracing 每一请求 逐步耗时 + 内核事件 见下表 — 超过 P999 的 0.1% 卡在哪一步

细粒度追踪 — 单笔订单拆段（例）：

步骤 耗时 工具可见的更细事件
网卡收包 2μs DMA / softirq
内核协议栈 3μs copy、协议处理
策略计算 5μs 解码 + 信号
网卡发包 1μs TX queue
（异常叠加） +15μs 调度把线程换出 — 只有 trace 能看见 
粗粒度：「延迟高了」
细粒度：「高在 IRQ 与进程抢同一核的那 12μs + 换出 15μs」→ 可改：迁 IRQ、isolcpus

细粒度工具：ftrace、eBPF/bpftrace、perf trace

  • 把时间线拆到 ms / μs / ns 级单个事件（调度、锁、syscall、page fault）
  • 意义： 粗/中粒度只能报警；追踪才能给出可落地的「哪一步、哪一类事件」
  • 专门服务：P999 最慢 0.1%、Max 单次 spike — Metrics 发现 tail → Tracing 抓样本

section-1.8-实验与微观宏观基准

观测 → 1.7

实验 Experimentation — 微观「隔离」vs 宏观「真实」

类型 核心 测什么 HFT 例子
微观基准 Micro 隔离性 把待测部分与全链路、其他硬件干扰 隔开，看 这一块的理论极限 单独测「订单生成+哈希校验」编码组件单次耗时
宏观基准 Macro 真实性 全链路 + 真实资源竞争 下的端到端表现 行情回放 tick→解析→策略→发单；含 CPU cache/NUMA/IRQ 争用

微观 ≠ 只能测单个函数：

  • 「单组件」= 功能独立的小模块 — 如打包好的 订单编码组件、解码器、CRC 模块
  • 工具：google benchmark、自写 loop、perf stat 只跑该模块

为什么要宏观补微观：

微观：订单编码组件单独测  →  1μs（理想路况）
宏观：放进全链路          →  3μs（和行情解析抢 cache、同核 IRQ…）
微观 宏观
回答 「这块 最快能做多快？」 「实盘 实际多快？P99/Max？」
风险 过于乐观 — 忽略联动 难复现需控制变量
HFT 用法 优化 算法/实现 的方向验证 SLO 签收、上线前回放

固定套路：

1. 微观 — 改完编码/CRC/解码 → 模块级 benchmark，确认方向
2. 宏观 — 同 workload 全链路回放 → 看 Mean/P999/Max 是否真降
3. 微观快、宏观没快 → 查 resource 争用（→ [1.4](./section-1.4-热路径Resource与双视角.md)），不是继续死抠模块

HFT 注意：

  • 微观易 脱离真实（Ch 12 详述）— 禁止只用 micro 数签 SLO
  • 宏观需 生产级 workload：真实报文率、订单形状、与同机其他进程共置
  • 合成压测报文若与实盘分布不同 → P999 可能 假好或假坏

微观基准 · 硬件隔离硬核清单（HFT 圈常用）

目标：测出 纯计算耗时，尽量不受 IRQ、频率波动、page fault 干扰。

步骤 操作 目的
绑核 taskset / cpuset / pthread_setaffinity；最好 isolcpus 独占核 避开其他进程、网卡 IRQ
稳频 关 Turbo Boost；压测时关或固定 超线程 干扰核 避免频率波动污染计时
内存 大页 hugetlb、mlock、预分配全部测试 buffer page fault → 0
预热 跑几轮 warm-up，把测试数据 钉在 L1/L2 测的是 steady-state，不是 cold cache
计时 rdtsc / rdtscp 或 std::chrono + 校准；固定 -O3 -march=native 纳秒级、可重复

例：测哈希函数微观基准

# 1. 绑 isolated 核（假设核 2 已从 isolcpus 隔离）
taskset -c 2 ./hash_microbench

# 2. 程序内：mlock 输入 buffer → warm-up 1e6 次 → rdtsc 测 1e7 次 → 报 ns/op
# 3. 宏观回放验证：全链路里是否真变快

观测 vs 实验 — 「不干预」vs「控变量加压」

观测 Observability 实验 Experimentation
本质 不干预系统自然状态 控制变量、人工造场景
HFT 例 实盘跑策略，极低频采样盯 P99/Max 关掉其他逻辑，只跑 malloc 循环 测分配器
原则 采样/追踪开销 不能影响业务 主动加压、A/B 对比、可重复
工具 sar、低频 histogram、eBPF 按需 microbench、fio、行情回放压测

观测在生产：

  • perf record 频率别太高；eBPF 只钩 tail 样本
  • 观察者效应 — 测到的延迟里可能含 你的探针；HFT 实盘用 硬件 timestamp / 异步写指标

实验在 lab：

  • 「只想看内存分配影响」→ 隔离：其他热路径全关，只 loop malloc/free
  • 结论只适用于 该 synthetic 场景 — 必须再用 宏观回放 签收
风险 观测 实验
典型坑 探针太重 → 测到的不是「纯业务」 合成场景 ≠ 实盘 → 假乐观
对策 降采样、生产只 Metrics micro 隔离 + macro 验证

常见陷阱

  1. 微基准结果外推到生产——微观 bench 无并发/无干扰，生产有调度抖动/NUMA/网络争用，直接外推必翻车
  2. 宏基准不控制变量——同时改了绑核+分配器+编译选项，无法归因哪个改了起作用
  3. 压测时间太短——HFT 的 tail latency 需要足够长的采样才能暴露 P99/P999 尖刺
自测题（点击展开）
  1. 微基准和宏基准分别适合什么场景？
答

微基准适合隔离测试单个函数/组件性能，宏基准适合端到端系统级验证

  1. 为什么微基准结果不能直接外推到生产？
答

微基准无并发/无调度抖动/无 NUMA 影响，生产环境有这些干扰因素

  1. HFT 压测应该持续多久才能暴露 tail latency？
答

至少跑足够长时间覆盖 P99/P999 分位数——短压测只能看 mean，看不到尾部尖刺

顺序 查什么 命令 / 动作 异常信号
1 网卡中断绑核 grep eth /proc/interrupts；/proc/irq/*/smp_affinity；ethtool -S eth0 IRQ 与策略 同核；rx_missed_errors、drop

1.11 案例研究

两则假设案例，演示用方法论推导根因（而非猜）：

案例 表面现象 思路
Slow Disks 磁盘慢 分层排除：是否真磁盘？是否内存/网络掩盖？

HFT 迁移： 「发版后延迟变差」= Software Change；「偶发尖刺」= 多因并存 + 追踪。

常见陷阱

  1. 云环境指标直接套裸机——云有 steal time、邻居噪声、虚拟化开销，裸机 checklist 不能直接用
  2. 忽略虚拟化层开销——HFT 共置裸机 vs 云实例延迟差数量级，不可混用 SLO
  3. 云上监控盲区——hypervisor 层事件（迁移、限流）对 guest 不可见，需要宿主机级监控
自测题（点击展开）
  1. HFT 为什么通常选择裸机共置而非云实例？
答

云有 steal time、虚拟化开销、邻居噪声，HFT 需要可预测的微秒级延迟

  1. 云环境性能分析有哪些额外挑战？
答

steal time、hypervisor 迁移、cgroup 限流、邻居噪声——guest 内不完全可见

  1. 云上 Noisy Neighbor 问题如何检测？
答

看 steal time（mpstat）、PSI、cgroup throttle 事件——非零说明被宿主机或其他租户挤
