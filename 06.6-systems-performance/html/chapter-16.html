section-16.0-案例背景An-Unexplained-Win

出处： Gregg《性能之巅》Ch 16 · Netflix 生产案例「无法解释的性能提升」— 全书收官演习，无新理论，只有方法论的总装。 HFT 实操要点： 「莫名变快」比「莫名变慢」更危险 — 回归没人投诉，但 win 若来自邻居撤离/缓存预热，它会在最不该消失的时候消失（比如开盘竞价）。

     「变慢」                          「变快（Unexplained Win）」
  用户投诉 · SLA 告警              无人投诉 · 甚至无人发现
  主动排查 · 有截止时间            被动忽略 · 「反正好了」
  ─────────────────────────────────────────────────────────────
  共同点：都暴露你【不理解】的机制变化。
  你不懂为什么赢，你就不知道它什么时候会还回去。

一、为什么「变快了」也要查？

# 理由 HFT 场景翻译
1 win 可能是假象 — 测量口径变了（采样窗口、指标定义、样本量） P99 突降 20% 是真的，还是今天 tick 量减半导致分位数样本不足？
2 win 可能不可持续 — 来自缓存预热、邻居暂时撤离、CPU 未降频的偶然窗口 隔壁策略进程今天停机维护；明天恢复，你「优化」的效果归零
3 win 背后可能藏着坏消息 — 某条路径被跳过了（缓存命中掩盖了故障） 行情处理变快是因为部分数据根本没到（上游丢包 / 订阅降级）
4 无法复现 = 无法守护 — 不知成因的 win 无法写进 runbook、无法在新机器上重现 扩容到新节点时，为什么新机器没有这个 win？答不上来
5 知识不对称 — 回归逼你查根因，win 让你错过唯一的免费学习机会 生产环境免费做了一次 A/B 实验，不分析等于浪费

Gregg 的立场（Ch 16 开篇）： 性能工程师的目标不是「让指标变好」，而是 理解系统行为。指标变好但原因未知 = 系统行为未被理解 = 排查能力有缺口。

二、「变快」的五类真相（Taxonomy）

排查的第一步：把「unexplained」拆成 可检验的候选类别。这继承 Ch 2 的科学方法——先列假设，再逐个证伪。

# 真相类型 典型信号 首选验证手段 对应章
① 负载变化 请求率/数据量同时下降；workload 特征变了 mpstat/应用 counter：吞吐分母变了吗？ Ch 2
② 环境变化 邻居（同机租户/共置进程）消失或变安静；云宿主机更换 steal time、/proc/pressure/*、邻居监控 Ch 11 云
③ 配置变化 内核升级、镜像重建、sysctl drift、库/JVM 版本变化 配置快照 diff（16.1.4） Ch 3
④ 状态变化 冷缓存→热缓存、预读生效、JIT 预热完成、page cache 装满 对比冷启动 vs 稳态（Ch 12 的 warm-up 纪律） Ch 12
⑤ 真实优化 代码/数据布局/调度真变好，且 可复现 PMC（IPC/cache-miss）+ profile 前后对比 Ch 13

关键认识： ①②③④ 四类都是「环境的偶然」——它们的特点是 不稳定：换台机器、换个时段、邻居回来，win 就没了。只有 ⑤ 是系统性的、值得写进 release note 的资产。区分 ①–④ 与 ⑤，就是本章整个案例研究要演示的事。

三、HFT 类比：P99 tick 突降的六种可能

场景： 新版本上线后，策略进程的 tick 处理 P99 从 8 µs → 5 µs。团队 Slack 里已经有人发 🎉 了。你的任务：在庆祝之前回答「为什么」。

候选 机制 怎么快速证伪
策略代码真的变快了 热路径删了分支 / 换了数据结构 perf diff 前后 profile 对比（16.1.7）
共置邻居撤了 同 NUMA 节点的兄弟进程停了，LLC/内存带宽释放 mpstat 看 其他 核的利用率是否同时下降
THP / 页表状态变化 昨晚 compaction 把策略的 hot pages 合成大页了，TLB miss 消失 /proc/<pid>/smaps 看 AnonHugePages；06-linux-mm ch03
绑核终于生效 上次部署后 taskset/isolcpus 才真正生效（之前 affinity 配错） taskset -pc <pid> + perf stat 的 cpu-migrations
行情本身变了 上游 throttle / 合约集合减少 / tick 量降 行情侧 counter：每秒 tick 数前后对比
测量口径变了 延迟打点代码挪了位置（比如少打了一段路径） code review 打点 diff；直方图 形状 是否突变（而不仅是位置平移）

注意最后一行：直方图形状 vs 位置。真正的优化通常改变分布的某个部分（比如消掉一个长尾 bump）；测量口径变化往往让 整个分布 平移。这是 Ch 12 的「基准拷问」在实战中的直接应用。

四、baseline 纪律：Win 的可解释性是事前准备出来的

Unexplained Win 之所以 unexplained，往往不是排查能力不够，而是 案发时没有可比的 baseline。Gregg 在 Ch 12/Ch 16 反复强调的事前纪律：

要素 内容 HFT 落地
同条件对照组 对比必须同 workload、同时段类型、同硬件 昨天的 P99 vs 今天的 P99，若两天行情波动率差 3 倍，不可比
连续采集 sar / Prometheus 持续归档，而不是出事才采 案发 前 的系统指标是排查的本钱（16.1.3）
配置快照 每次部署自动落一份 sysctl -a + /proc 快照 + 镜像 tag 16.1.4 的 diff 才有得 diff
测量路径固定 打点位置、聚合方式、分位数算法定版并版本化 指标代码变更 = 声明式变更，走 review
可回放 录制行情流（pcap / 二进制 replay），能重放对比 新旧 binary 同一份录制流上 A/B

这就是「实验设计」而非「救火」。Netflix 案例能一路走到底，靠的正是生产监控（Atlas）里的历史数据 — 证据是案发前就埋好的。

代码自测（Q&A，先遮住答案想）

Q1：为什么「变快」比「变慢」更少被排查？这带来什么系统性风险？

A：变慢有外部压力（投诉/告警/SLA），变快没有——甚至会被当成「理所当然的好运」。系统性风险在于：① 无法复现的 win 会静默消失，回归时反而当成「新问题」排查，浪费一次彻底的 root cause 机会；② win 可能掩盖故障（数据没到导致处理变快）；③ 组织失去免费 A/B 实验的学习价值。

Q2：五类真相中，哪一类最需要「事前准备」才能识别？为什么？

A：③ 配置变化（含环境/镜像 drift）。负载、缓存、邻居都可以在案发后用观测工具追查（sar 历史还在），但配置是 状态不是事件——案发后只能看到「现在的配置」，除非部署时留了快照，否则永远不知道「变了什么」。这也是 16.1.4 强调配置审计的原因。

Q3：直方图「整体平移」vs「长尾 bump 消失」，分别更可能对应什么？

A：整体平移 → 多半是测量口径/时间基准变了（打点挪位置、时钟源变化），或全局性环境变化（如 CPU 频率）。长尾 bump 消失 → 更像真实的优化消灭了某类慢事件（如消除了偶发的 cache miss 风暴或调度迁移）。分布形状比均值携带更多因果信息。

Q4：HFT 里「win 背后藏着坏消息」举一个具体例子。

A：行情处理延迟突然变好，实际原因是上游组播丢包导致部分 tick 未投递——处理量下降，平均延迟自然下降。验证手段：对比上游重传/修复计数（feed handler 的 gap/repair 统计），确认 tick 量没有下降。吞吐与延迟必须同看（Ch 2 工作负载分析）。

section-16.1.1-16.1.2-问题陈述与分析策略

出处： Gregg《性能之巅》Ch 16.1.1–16.1.2 · 案例的前两步——先把问题写成可验证的句子，再决定先看什么。 HFT 实操要点： 90% 的排查时间浪费，源于问题陈述里混进了未验证的因果假设（「肯定是网络」）。陈述只写观测事实，假设单独列。

  问题陈述（只写事实）        分析策略（花钱的顺序）
  ─────────────────          ─────────────────────
  什么现象 · 什么范围          先便宜的观测：统计 → 配置
  从何时开始 · 影响多大        再昂贵的观测：PMC → trace
  与什么对比                  每一步前有假设，每一步后更新
  ❌ 不写「我猜是…」           假设清单 = 排查路线图

一、问题陈述（Problem Statement）：六要素格式

Gregg 在 Ch 2 给出的纪律（源自 SRE 实践）：问题没写清楚之前，不动工具。

要素 问自己 Netflix 案例精神 HFT 模板
现象 观测到什么？数字是什么？ 吞吐相对历史基线莫名改善 tick P99 从 8 µs → 5 µs（-37%）
范围 哪类实例/进程/核/时段？受影响面占多少？ 哪类实例、哪个 region、哪个时段起 哪个策略进程、哪个交易所 session、全量还是部分核
起点 从何时开始？与什么事件对齐？ 与某次镜像/部署的时间相关性 与哪次 commit / 哪台机器替换 / 哪次重启对齐
对照 「变好」相对什么 baseline？baseline 本身可信吗？ 相对监控历史均值 相对昨周同时段？昨周行情与今天可比吗？
影响 业务后果（收益 or 风险）？ 吞吐↑ → 成本/容量估计 P99↓ 但尾部风险未知 → 是否影响容量规划
非目标 本次排查不做什么？ 先不「再调一个参数」、不猜根因 不改代码、不重启进程（保现场）

写好陈述的判据： 拿给一个不了解情况的人，他能复述出「什么系统、什么指标、从什么时候、相对什么、变了多少」。做不到就重写。

反例 → 正例（HFT）：

❌ 反例：「今天系统变快了，估计是昨天内核升级的效果，看看？」
   （混入了未验证因果；「快」没有数字；没有范围）

✅ 正例：「策略进程 A（订单路径，核 8-11）的 tick→order P99 从
   8.1±0.3 µs 降至 5.2±0.2 µs（n>10⁶），起始时间 14:30 昨日部署后；
   同机行情进程无变化；对照组（未部署的进程 B）P99 不变。
   本次排查先不做任何变更，只收集证据。」

注意正例里 对照组 的价值：进程 B 没变 → 变化归因于「部署」而非「环境」（若 B 也变好，嫌疑转向机器级/邻居级）。这是 Ch 12 对照实验思想的日常化。

二、反模式清单（Ch 2 反面方法 · 案例前的预防针）

反模式 症状 对 Unexplained Win 的特殊危害
路灯法 Streetlight 只查自己熟悉的指标（CPU%） Win 常藏在你不熟的维度（缓存、邻居、频率）
随机变更法 没假设就改 sysctl「试试看」 破坏现场：改动后再测，win 消失也说不清是谁的锅
归咎他人 「肯定是网络/云厂商的问题」 未经证实的转移动机，错过真因
亲切感偏差 「上次也是这个原因」 上次的 win≠这次的 win；相关≠因果
指标崇拜 只看聚合均值 P99 的改善可能只发生在分布的一段，均值看不出来

Unexplained Win 场景下最致命的是 随机变更法：你只有一个「案发现场」（win 还在的窗口），任何配置改动都可能污染它。原则：先读后写，只读排查。

三、分析策略（Analysis Strategy）：竞争假设矩阵

科学方法（Ch 2）：列出 竞争假设（competing hypotheses），按「观测成本 × 区分能力」排执行顺序。

Hypothesis Matrix 模板（HFT 版 P99 突降）：

假设 预期观测（若为真） 验证成本 淘汰顺序
H1: 新代码热路径变短 profile 里旧热点函数占比下降 中（perf record 前后对比） ②
H2: 邻居撤离（LLC/带宽释放） mpstat 同节点其他核利用率同步下降 低（一条命令） ①
H3: 页表/THP 状态变化 smaps AnonHugePages↑；TLB miss↓ 低 ①
H4: 绑核/亲和终于生效 perf stat cpu-migrations↓ 低 ①
H5: 测量口径变化 打点 diff 非空；直方图形状突变 低（code review） ①
H6: CPU 频率/降频状态变化 perf stat GHz 行↑；turbostat 低 ①

排序原则：

  1. 便宜先行：能一条命令否定/确认的假设先做（H2/H4/H5/H6 全是低成本）。
  2. 淘汰率高优先：一个观测若能同时淘汰多个假设（如 mpstat 同时看邻居、频率、迁移），优先做。
  3. 串行不并行：昂贵的观测（PMC、trace）等便宜假设全部淘汰完再上——目标是被压缩到 1–2 个假设后做 确认性 深挖。

四、Drill-Down：四层下钻地图

  L1 系统级   vmstat/mpstat/sar/ss      「哪类资源有异常迹象？」
     ↓ 缩小：哪颗核、哪个进程、哪个时段
  L2 资源级   perf stat(PMC)/压力检查    「CPU 在微架构层发生了什么？」
     ↓ 缩小：哪个指标组合解释了「快」

代码自测（Q&A，先遮住答案想）

Q1：为什么问题陈述里禁止出现因果猜测？

A：① 猜测会污染观测选择——你会只看「支持猜测」的指标（确认偏差，路灯法的变体）；② 猜测会传染团队——「肯定是内核升级」传三遍后就成了「事实」，后续排查被锚定；③ 猜测让陈述不可验证——无法判断排查是否完成。正确做法：事实进陈述，猜测进假设清单（单独管理、逐个证伪）。

Q2：对照组（未部署的进程 B）在案例里起了什么方法论作用？

A：差分（differencing）。若 A 变好而 B 不变 → 变化与部署强相关（缩小到代码/进程配置）；若 A、B 同时变好 → 嫌疑上移到机器/环境/邻居层。一个对照，直接把假设空间砍半。这是实验设计里「控制变量」在生产排查中的最小可行版本。

Q3：为什么 Unexplained Win 场景下强调「只读排查，先读后写」？

A：Win 是一个可能随时消失的现场（邻居可能回来、缓存可能失效），而任何配置变更本身就会改变系统状态。改动后即使 win 消失，你也无法区分「改动破坏了 win」还是「win 本来就要消失」——现场被自己污染。若必须变更（比如需要重启加载追踪工具），先做完整快照。

Q4：假设排序为什么「便宜且淘汰率高」的优先，而不是「最可能为真」的优先？

A：信息论视角：排查的目标是最快缩小假设空间，不是「最先确认最喜欢的假设」。一个便宜的观测即使淘汰掉的是「不太可能」的假设，也是净收益；而贵的观测若只服务于单一假设，一旦该假设被证伪，投入全部沉没。「先验概率」决定你想什么，「成本×区分度」决定你做什么。

代码自测（Q&A，先遮住答案想）

Q1：为什么「同周同时段」对比 sar 归档，而不是昨天 vs 今天？

A：工作负载有周期性——周一开盘与周五收盘的 tick 量、夜盘与日盘的负载完全不同。随机选对照组会把「节奏差异」误判成「行为变化」。同 weekday + 同时段是最小成本的负载匹配；更严格的做法是按 tick 速率/波动率分层后对比（Ch 12 的可比性原则）。

Q2：配置是「状态不是事件」——这句话怎么理解，后果是什么？

A：事件（如 CPU 利用率）被连续采样，事后可回放；配置（如 sysctl 值）只有「当前值」，没有历史序列。若部署时不落快照，案发后就永远无法知道变过什么——这正是很多 Unexplained Win 永远 unexplained 的原因。对策是把配置快照做成部署流水线的固定步骤（事前纪律，见案例背景篇第四节的 baseline 纪律）。

Q3：mpstat 里 %steal 从 3% 变 0%，对 Unexplained Win 排查意味着什么？

A：强证据指向「云邻居假设」：宿主机上其他租户曾经抢走 3% 的物理 CPU 时间（hypervisor 侧的 steal），现在没有邻居或邻居安静了。这是「win 来自环境而非代码」的直接证据——对策不是庆祝而是：① 确认该 win 的不稳定性（邻居可能回来），容量规划不能用这个数据；② 若业务关键，考虑专属宿主机/置放群组（Ch 11）。

Q4：为什么「taskset -pc 看实际亲和性」比「检查部署配置」可靠？

A：配置声明的是意图，/proc/<pid>/status 的 Cpus_allowed 才是内核事实。中间可能断链：脚本 path 错误静默失败、容器 runtime 覆盖 affinity、cgroup cpuset 与 taskset 冲突、进程被 systemd 重启后丢了亲和。Unexplained Win 的排查全程都应遵循「观测事实优先于配置声明」——这是问题陈述纪律在执行层的延续。

Q5：配置 diff 为空时，能得出「配置没变」的结论吗？

A：不能完全得出，只能缩小范围。① 你只能 diff 采集过的 配置项——没进快照的（如 BIOS 设置、网卡固件参数、云宿主机状态）盲区仍在；② 云环境里「实例换宿主机」不会出现在任何实例内配置 diff 里。所以正确的表述是「在观测范围内的 配置假设淘汰」，残余不确定性用侧面证据（dmesg 启动时间、microcode 版本）继续压缩。

section-16.1.5-16.1.6-PMC-与软件事件

出处： Gregg《性能之巅》Ch 16.1.5–16.1.6 · 宏观统计解释不了「为什么在 CPU 上变快」时，下钻 微架构层——用 PMC（性能监控计数器）量化「哪类快」，用软件事件交叉验证内核侧原因。 HFT 实操要点： PMC 的杀手锏是 区分「频率的快」和「效率的快」——cycles 少了还是每 cycle 干的活多了？这两个答案指向完全不同的根因和完全不同的可持续性。

  perf stat = 一条命令同时拿到：
  ┌────────────────────────────────────────────────┐
  │ 硬件层：cycles / instructions / cache-miss /   │  「微架构发生了什么」
  │         branch-miss / IPC（衍生）               │
  │ 软件层：context-switches / cpu-migrations /    │  「内核行为发生了什么」
  │         page-faults / task-clock               │
  │ 频率层：GHz（cycles ÷ task-clock）              │  「CPU 到底跑没跑满频」
  └────────────────────────────────────────────────┘

一、PMC 基础：为什么它能「测效率」
是什么 CPU 硬件里的性能计数器（PMU），每个核一组——计数 cycles、instructions、各级 cache miss、分支预测失败等微架构事件
谁读它 内核 perf 子系统（perf_event_open(2)）；用户态工具（perf stat）只跟内核要数
开销 计数模式几乎为零（硬件自动累加）；采样模式（perf record）才有中断开销
限制 每核同时可用的 generic 计数器通常 4–8 个（perf stat 会自动 multiplex，输出里有 % 占比提示）；虚拟化下需 pass-through（云上常见不可用 → Ch 11 的 PMC 挑战）

关键认识：perf stat（计数）和 perf record（采样）是两个开销等级。Unexplained Win 的排查在 16.1.5 阶段应只开 stat——零成本拿全部汇总数，等假设收敛到「哪条路径」才上 record（16.1.7）。

IPC ↑ 活少效率高（workload 或剔除慢路径） 经典「效率型 win」：stall 减少 变化最大（优化+快路径）
IPC → 等比减少（频率/时间窗假象） 什么都没变（假 win，查测量） 快但周期等比增（如复制更多数据）

第一步永远是先看 GHz 行。 cycles 变少最平凡的解释是频率变了——perf stat 默认输出里 GHz = cycles ÷ elapsed，先排除这个，微架构分析才有意义。（HFT 生产机上 governor 应恒为 performance，但「应然≠实然」——16.1.4 的教训。）

三、Top-down 思想（PMC 的进阶读法）

当 IPC 变化需要更精细解释时，工业界用 Intel 的 Top-Down 分析把「每 cycle 的去向」拆成四类（工具：perf stat --topdown 或 toplev.py）：

类别 含义 典型原因 HFT 关联
Retiring 正常退休的指令占比 越高越好（>50% 算健康） 优化直接收益区
Frontend Bound 取指/译码受阻 i-cache miss、分支目标 miss 大二进制/模板代码
Backend Bound 数据供给受阻（最常见） d-cache/LLC miss、内存带宽、端口争用 随机访问模式、NUMA 跨节点
Bad Speculation 错误推测浪费的周期 分支预测失败、流水线冲刷 数据相关分支密集的策略代码

Unexplained Win 若表现为 Backend Bound 下降 → 指向数据供给（缓存/带宽/邻居）；若 Bad Speculation 下降 → 指向代码路径变化。PMC 的价值就是把「快了」翻译成「哪类微架构事件少了」，从而反推机制。

四、软件事件（Software Events）：内核侧交叉验证

硬件计数器说「CPU 层面快了」，软件事件回答「内核做了什么配合」：

事件 内核来源 关联的故事 工具
context-switches schedule() 每次被调用 +1 切换少 = 唤醒/抢占/阻塞减少 perf stat
cpu-migrations 任务换核执行 迁移少 = 亲和生效、负载均衡变稳 perf stat
page-faults do_page_fault 路径 缺页少 = 页表/THP/预取状态变化 perf stat

组合阅读矩阵（把 PMC 与软件事件拼起来）：

IPC ↑ + context-switches ↓        → 调度/绑核故事（冷 cache 效应消失）

IPC ↑ + branch-misses ↓            → 代码路径/数据分布变化故事

代码自测（Q&A，先遮住答案想）

Q1：cycles 下降 20%、instructions 不变、吞吐上升 20%——最可能的解释是什么？该怎么进一步确认？

A：先怀疑频率假象：若 GHz 上升 20%（如 governor 从 powersave 变 performance、或之前 thermal throttling），则 cycles 按比例减少、指令数不变、墙钟时间缩短——一切「看起来变快」但微架构效率（IPC）其实没变。确认：看 perf stat 的 GHz 行或 turbostat；回 16.1.4 查 governor/温度历史。这是 Unexplained Win 最经典的「假 win」形态之一。

Q2：为什么 perf stat（计数）几乎零开销而 perf record（采样）有可观开销？

A：计数模式下，事件由 PMU 硬件自动累加，CPU 只是周期性执行一条 RDPMC/寄存器读——没有中断、没有停顿。采样模式下，内核需要按采样率（如 -F 99，每秒 99 次）向 CPU 发 NMI 中断，每次中断要保存/恢复上下文、抓栈、写 ring buffer——中断本身还污染 cache。所以纪律是：stat 收敛假设，record 只做确认。

Q3：IPC 从 1.9 升到 2.4，cache-misses 降了 60%，但配置 diff 为空、代码没变——下一个最该查什么？

A：环境争用假设：LLC/内存带宽被谁分享过？① 同 NUMA 节点/同 CCX 的邻居进程是否撤离或变安静（mpstat -P ALL 看别的核）；② 云上是否换了宿主机（steal、microcode、dmesg 启动时间侧面证据）；③ compaction/THP 是否让策略工作集的物理布局变好（smaps 的 AnonHugePages 前后对比）。IPC+cache-miss 的组合强烈指向「数据供给变好」，而代码没变时数据供给的变化几乎总是环境给的。

Q4：软件事件 context-switches 里，voluntary 和 involuntary 的区分为什么对 HFT 重要？

A：voluntary（任务主动让出：等锁/IO/睡眠）和 involuntary（被抢占：时间片耗尽或更高优先级唤醒）机制完全不同。HFT 热路径上 involuntary cs 是延迟抖动主源（时间片抢占），对策是 SCHED_FIFO/绑核；voluntary cs 多说明热路径上有本不该有的阻塞，对策是消除等待（如锁换无锁结构）。「切换变少」如果只细看是 involuntary 降了，故事就指向调度策略变化；若 voluntary 降了，指向等待结构变化。

Q5：云上 PMC 全 0（不可用），如何完成 16.1.5 这一步的等价分析？

A：退化为软件路线：① perf stat 只留软件事件（context-switches/page-faults/task-clock——软件事件不经 PMU，虚拟化下可用）；② /proc/<pid>/stat 的 utime/stime 序列采样换算 CPU 时间；③ trace 侧（16.1.7）直接上 perf record（基于 NMI 的采样同样可能受限，可改用 timer 事件）或 bpftrace kprobe。信息少了「微架构哪类快」，但仍能回答「内核行为变没变」。

代码自测（Q&A，先遮住答案想）

Q1：为什么「要栈，不要计数」？

A：计数（事件发生 N 次）只能确认「变快了」这个事实，无法区分机制——200 万次 cache miss 可能集中在一条函数也可能摊在几十条。栈把事件挂到调用路径上，才能回答「哪条路径快了」，进而 diff 出「哪个变更导致的」。这是 16.1.8 结论第 1 问（什么变了）的必要证据形态。

Q2：offcputime 与 perf record 各自的盲区是什么？为什么 HFT 两个都要？

A：perf record（on-CPU 采样）只采样「CPU 正在执行」的时间——任务在等锁/等 IO/等调度时不被采到，这段时间在火焰图里不存在。offcputime 恰好相反，只记录「下 CPU 到上 CPU」的阻塞及栈。HFT 的延迟 = on-CPU 时间 + off-CPU 时间 + 排队时间，只看一边会系统性漏掉另一半故事——「变快」可能根本不是代码变快，而是阻塞消失。

Q3：追踪工具运行期间的 P99 数据为什么不能用？这带来什么流程约束？

A：trace/bpftrace 逐事件插桩（kprobe 触发、抄栈、写 ring buffer），开销直接加在被追踪路径上——观测行为本身抬高了被测延迟（观测者效应）。流程约束：① 观测窗口与测量窗口分离：追性能数据时收性能数据，但不用同窗口的 P99 下业务结论；② 追踪产出的结论（如「该函数阻塞消失了」）应拿到无插桩的复现环境验证。

Q4：五类结局里，「配置 drift」的正确收尾为什么是「固化」而不是「回滚」？

A：Unexplained Win 的 drift 意味着当前配置更好——回滚等于主动放弃 win。正确动作是把「意外的正确配置」显式写进镜像/部署脚本/基础设施代码（IaC），让 win 从「偶然状态」变成「受版本管理的必然」。同时审计同类机器是否还存在旧配置（drift 是集群性的），把盲区补成监控项（配置基线告警）。

Q5：重启实验的原理与局限？

A：原理：代码优化与数据布局优化持久，而私有状态（页表/THP 合页、page cache、锁竞争的时序相位、分支预测器的训练）在重启后归零——重启后 win 保留 → 代码论增强；win 消失 → 状态论坐实。局限：① 重启同时清掉了邻居与共置状态吗？没有——单机重启不清邻居；② 重启可能改变进程启动顺序/内存布局（ASLR），引入新变量；③ 生产机器重启成本高，通常在复现环境/同类机器上做。它是便宜的反证，不是终极证明。

代码自测（Q&A，先遮住答案想）

Q1：为什么对照组 strat-sim 在 S0 就要确认，而不是最后再看？

A：对照组是假设空间的第一刀：sim 不变 → 变化与部署强相关（进程级原因）；sim 也变好 → 嫌疑上移到机器/邻居/宿主机（环境级）。这刀切在 S0，直接决定 S1 的观测重点（若环境级，mpstat 全核和 steal 是主战场；若进程级，可直接跳配置 diff + PMC）。晚看对照组 = 前面步骤可能白做。

Q2：S3 判读顺序为什么「GHz 先于 IPC、IPC 先于 miss 明细」？

A：因果依赖关系：GHz 是 cycles 语义的前提（频率变则 cycles 数没有可比性）→ 必须最先排除；IPC 是「效率变了没有」的总判定 → 决定后续 miss/branch 明细有没有分析价值（IPC 不变时，miss 明细的波动可能只是噪声）。顺序颠倒会被局部 miss 变化带偏，得出「解释了没发生的事」的结论。

Q3：perf diff 显示某函数占比从 6.2% 降到 0，为什么还必须配 PMC 和对照组才能下「真实优化」结论？

A：占比是相对数——6.2%→0 也可能是别的函数变慢稀释（分母变大）或调用方逻辑变化跳过了它（比如错误路径提前 return，功能其实缺失）。PMC（instructions 持平 + IPC↑ + miss↓）证明总工作量没变而效率升；对照组排除机器级原因。三件套齐了，因果链才闭合。

Q4：演练里为什么重启实验放在 release note 的「验证」栏而不是排查主路径？

A：重启实验是裁决性反证（区分代码/状态），但生产机交易时段不可重启——它只能安排在盘后或灰度机执行。排查主路径（S0–S4）全程只读、可当场完成；重启验证作为结论的最后一道保险（排除缓存/预热假象）补进 release note。流程设计要区分「当场能做的」和「要排期的」。

Q5：如果 S0–S4 全部走完仍是「unexplained」——所有便宜假设淘汰、PMC 显示 IPC↑ cache-miss↓、但 perf diff 干净、配置 diff 干净——下一步怎么办？

A：进入了真 unexplained 区，通常意味着观测范围外有变量。按顺序补：① 私有状态面：smaps 前后对比（THP/页表）+ 重启实验排期；② 环境面：云宿主机更换的侧面证据（microcode、dmesg 启动时间、/proc/cpuinfo 步进）；③ 编译面：二进制本身 diff（同源码不同编译环境的布局差异，如 PGO/LTO/地址布局）；④ 记录在案——「未解释但已归档」的 win 也是资产，等下次同类 win 出现时数据可叠加。承认未知本身是方法论的一部分。
