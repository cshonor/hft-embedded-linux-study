大白话 · 本章就四件事

基准测试是实验，不是电竞跑分。

① 为什么要测 + 为什么常失败 — 先懂局限再动手。

  • 有效基准 = 可重复、可解释、与生产 workload 相关。
  • 失败模式：测错层、测到 cache、样本太少、环境不一致、结论过度推广。

② 四种类型：Micro / Simulation / Replay / Industry Standard。

  • Micro — 单组件（CPU/盘/网）；Replay — 录生产再播（架构变了可能误导）。
  • Macro 行业标准 — SPEC 等；HFT 更常 自定义 + 真实报文 replay。

③ 方法论：主动/被动、USE+Profile、阶梯负载、Sanity Check、统计、Checklist。

  • 压测时 同时 CPU 火焰图 + USE — 确认瓶颈在声称的那一层。
  • Ramping load 找拐点；Sanity Check 交叉验证工具是否在测你以为的东西。

④ 拷问报告（Benchmark Questions）— 看 vendor 亮分保持批判。

  • 工作负载是什么？预热了吗？P99 呢？与你们生产像吗？

12.1

section-12.1-基准测试的背景与挑战

章节导航：本章导读 · 下一篇 12.2 基准测试的类型

本节讲什么：为什么要做基准测试（五个真实目的）、有效基准与无效基准的分界线、六大失败模式的机制级解释——每个失败模式都不是「粗心」，而是有具体的系统原因。

要点

# 要点 一句话
1 跑分高 ≠ 生产快 基准是实验，不是电竞排名
2 有效性三支柱 相关（像生产）、可复现（环境文档化）、可解释（带 profile）
3 六大失败模式各有机制 测错层是最常见也最隐蔽的
4 报分布不报均值 均值把 tail 抹平
5 结论的作用域要标明 实验室结论 ≠ 生产结论

一、为什么要做基准测试（五个真实目的）

目的 例子 关键要求
容量规划 新机器能扛多少行情 pps 阶梯负载找拐点（12.3）
回归检测 策略改一行，P99 是否变差 固定环境 + 固定数据 + 固定判读
对比选型 NIC A vs B、内核栈 vs DPDK 单变量对照
验证调优 sysctl/绑核/中断亲和前后 改一项测一项
SLA 证明 对交易所/托管方交付证据 报分布 + 测量点声明

注意：这五个目的对「像生产」的要求不同——容量规划可以接受合成负载（外推时打折），回归检测必须用完全一致的环境与数据（否则差异来源不可判），SLA 证明必须用生产级观测口径。

二、有效基准 vs 无效基准

有效 无效 差别本质
目标明确（测什么、为谁、决策是什么） 「跑个 fio 看快不快」 没有决策的测试是娱乐
环境文档化、可复现 未说明内核/驱动/邻居 差一个 sysctl 结果就能翻倍
与生产 workload 相关 纯 synthetic 且形状完全不同 访问模式决定走哪条内核路径
报告分布（P50/P95/P99/P999） 只报一个平均值 排队论：均值对 tail 盲
结合观测解释瓶颈 只有数字无 profile 不知道瓶颈在哪层 = 不知道测了什么
结论带作用域 实验室结论直接外推生产 过度推广是最贵的错误

「可复现」的最低配置清单（照抄进 runbook）：

□ 硬件：型号/固件/BIOS 版本
□ 内核版本 + 关键 sysctl/cmdline（isolcpus/irqaffinity/nohz_full）
□ 驱动与固件版本（NIC/RAID/NVMe）
□ 工具完整命令行（一个字符都不能省）
□ 负载参数（大小/并发/时长/随机种子）
□ 环境状态（邻居负载/云实例类型/温度策略）
□ 预热协议（跑几轮丢弃）

三、六大失败模式的机制解释

失败模式不是「粗心」，每个都有具体的系统原因——理解机制才能在结果里识别出它的味道。

① 测到 cache 而非磁盘

文件大小 < RAM → page cache 全命中 → 你在测内存，不是盘

机制：Linux 读路径先查 page cache（ch8），命中即返回。1GiB 测试文件在 128GiB 机器上永远热。对策：文件 >> RAM，或 O_DIRECT 绕过 cache，或每次 echo 3 > /proc/sys/vm/drop_caches（注意这本身会扰动系统——测试间隔里做）。

② 测到空闲 CPU 而非真瓶颈

单线程 micro-bench 在 64 核空机上跑——测的是单核极限，不是生产并发下的锁竞争、cache 争用、NUMA 远端访问。机制：生产的瓶颈常常在共享资源（锁、内存带宽、LLC），空机单线程根本碰不到。对策：并发度对齐生产，或阶梯加载找拐点。

③ 冷启动 vs 稳态混淆

JIT 预热、page cache 冷热、连接建立、分支预测器学习——前 10 秒和第 10 分钟的数字差一个数量级。对策：固定预热轮数并丢弃，报告「稳态从第 N 秒起」。

④ 邻居/云 steal

多租户共享物理机，hypervisor 把你的 vCPU 调度走（%steal，ch11）。机制：噪声注入随机延迟尖刺——P999 会烂掉但 P50 完好，形成「平均看起来正常」的假象。对策：同机型同 AZ 多跑几轮看方差；裸金属对比。

⑤ 工具 bug / 错误用法

fio 的 ioengine 选错（sync vs io_uring）、块大小和队列深度不匹配、iperf3 单流 vs 多流测的是不同东西。对策：12.3 sanity check——用第二种工具或观测交叉验证。

⑥ 过度外推

实验室 100G 回环 → 生产混合流量 + 交易所共置 RTT。机制：线性外推假设瓶颈随负载平移，实际瓶颈会切换（CPU → 内存带宽 → NIC 队列）。对策：结论永远标注作用域。

四、失败的味道识别表

结果特征 首先怀疑
IOPS 高得离谱（>盘规格） 测到 page cache
P50 正常、P999 烂 邻居/steal 或周期性干扰
前后两轮差 >20% 预热不足或环境漂移
单工具结果，换工具翻倍 工具用法错误
单核跑满、多核无提升 锁/单线程瓶颈，不是平台问题
数字完美无 tail 样本太少或测错层

HFT / 嵌入式关联

  • 「testpmd 跑满 100G」≠「order book 更新 P99」——中间隔着驱动 → 内核栈/DPDK → 解码 → 策略的整条路径，micro 数字只做 capacity baseline。
  • 回归检测是 HFT 最常用的基准形态：每次发版前固定 replay 数据 + 固定环境跑一遍，比对新旧 P99 分布（全分布对比，不是均值对比）——和 ch16 的 baseline 纪律是同一套方法论。
  • 专用机的意义：HFT 生产是裸金属 + 隔离核，基准环境必须同构——云虚机上测出的调优结论搬到裸机经常反转。
  • 嵌入式：板卡算力基准（stream/lmbench）要标注温控状态——热降频会让第 10 分钟的数字变成另一台机器。

  • 方法论框架：12.3 基准测试方法论（主动观测 + 阶梯负载）

常见陷阱

  1. 均值思维——HFT 一切看 P99/P999，均值会把邻居噪声和周期性尖刺全部抹平。
  2. 环境不记录——三个月后无法复现的数字等于没测过。
  3. 把 micro 结论直接上报——「机器很快」要拆成「哪个组件在什么条件下快」。
  4. 预热轮丢弃不标注——冷热混合的数字无法和下一轮比较。
自测题（点击展开）
  1. 有效基准的三支柱？
答

相关（负载像生产）、可复现（环境文档化）、可解释（带 profile 知道瓶颈在哪层）。

  1. 为什么文件小于 RAM 时 fio 测的不是盘？
答

读路径先查 page cache，全命中即返回——测的是内存带宽和系统调用开销。对策：文件 >> RAM 或 O_DIRECT。

  1. P50 正常但 P999 烂，首先怀疑什么？
答

周期性干扰或邻居噪声（云 steal/SMI/定时器）——低频高强度事件只打击尾部。

  1. 为什么单线程 micro-bench 高分不代表生产快？
答

生产瓶颈常在共享资源（锁/内存带宽/LLC），空机单线程碰不到这些路径。

  1. 云上基准与裸金属基准的关键差异？
答

邻居噪声与 steal 注入随机延迟——同配置多轮方差大；结论不能跨平台外推。

12.2

section-12.2-基准测试的类型

章节导航：12.1 背景与挑战 · 上一篇 ← · 下一篇 12.3 基准测试方法论 · 本章导读

本节讲什么：四种基准类型（Micro / Simulation / Replay / Industry Standard）的选择矩阵、各自的失真来源、replay 的「架构漂移」陷阱、HFT 各场景的类型选配。

要点

# 要点 一句话
1 类型 = 保真度 ↔ 可控性 的权衡 越像生产越不可控
2 Micro 隔离变量，测不到交互 锁竞争/NUMA/cache 争用
3 Replay 最大的坑是架构漂移 换盘/换栈后旧 trace 语义变了
4 行业标准适合横向对比，不适合证明你的生产性能 读它的方法论
5 HFT 主力是 Simulation + Replay 组合 合成压测找极限，真实回放做回归

一、保真度—可控性权衡图

可控性（可重复、单变量）
   ▲
   │ Micro          Simulation
   │  fio/iperf      合成 tick 流
   │
   │                Replay            Industry Std
   │                 历史 tick 回放     SPEC/TPC
   ▼
   └─────────────────────────────────────────▶ 保真度（像生产）
                       ▲
              HFT 回归检测的工作区间

四种类型没有高下，只有「回答什么问题」的区别：

类型 回答的问题 不回答的问题
Micro 这个组件的物理上限？ 组件组合后表现？
Simulation 合成压力下系统拐点？ 真实流量的长尾行为？
Replay 真实流量下端到端表现？ 超出历史的新场景？
Industry 和别家机器比怎么样？ 我们的生产会怎样？

二、微观基准（Micro-Benchmarking）

针对单一组件、简化人工负载：

组件 常见工具 测什么
CPU perf bench、自定义 loop 算力、分支、syscall 开销
磁盘/FS fio IOPS、延迟分位（ch9）
网络 iperf3、netperf 吞吐、RTT（ch10）
内存 lmbench、stream 带宽、load latency
DPDK testpmd / pktgen PPS、转发路径
  • 优点：隔离变量、可重复、快速迭代调优假设。
  • 缺点：脱离真实 syscall 路径、锁、业务逻辑——组件级快 ≠ 栈级快。

典型用法（fio 测日志盘延迟，参数即文档）：

fio --name=latency --filename=/dev/nvme0n1 --direct=1 \
    --rw=randwrite --bs=4k --iodepth=1 --runtime=60 \
    --group_reporting --percentile_list=50:99:99.9
# iodepth=1 测的是「单请求往返延迟」，iodepth=32 测的是「排队吞吐」——两个不同的问题

三、模拟测试（Simulation）

合成 workload 模仿生产特征（比例、大小、并发、到达率分布）——比 raw micro 接近真实，但形状必须校准。

校准清单（合成为什么可信）：

□ 到达率：固定速率还是突发（生产是泊松/突发？）
□ 大小分布：报文/请求大小的直方图（不是均值）
□ 读写比例：与生产统计对齐
□ 并发度：连接数/线程数/队列深度
□ 时间特征：日内高峰形态（开盘 15 分钟 vs 全天平均差 10×）

HFT 例：合成 UDP 组播行情流 + 固定 order book 深度做压力回归——能找到系统的拐点和退化形态，但字段分布、包间 burstiness、symbol 相关性仍不如真实 exchange feed。所以合成测拐点、真实测回归，两者都要。

四、重放测试（Replay）

捕获生产 trace 再回放：

类型 工具/方式 HFT 场景
块 I/O trace blktrace 录制 + replay（ch9） 日志盘验收
网络 pcap tcpreplay 历史行情回放
应用请求 自定义日志/二进制 replay tick → 策略回归

⭐ 架构漂移陷阱（Gregg 警告，ch9 呼应）：replay 的前提是「重放路径的行为特征与录制时相同」。若目标系统架构或性能特征已变，replay 可能误导：

录制时的特征 换硬件/栈后 后果
HDD 队列合并模式 换 NVMe 后合并机会完全不同 trace 里的 I/O 序列不再代表真实到达模式
内核栈 pacing 换 DPDK 后无队列 网络回放的时间戳失去意义
page cache 命中序列 换内存容量 命中/穿透模式重排

规则：换后端（新盘/新 FS/新网卡/新栈）→ 重新在生产录 trace，别用旧的。

历史 tick replay 测策略逻辑不在此列——那是数据回放不是性能回放，测的是决策正确性；但测系统延迟时，replay 的注入节奏（一秒放多少 tick、burst 怎么分布）必须保真。

五、行业标准（Macro / Industry Standards）

套件 领域 用途
SPEC CPU 2017 CPU 编译/浮点 采购横向对比
SPECjbb Java 服务端 JVM 平台
TPC-C / TPC-E 数据库 OLTP DB 选型
厂商 NIC benchmark 网络转发 上限参考

特点：宏观、可对比、不一定像你的业务。正确姿势：读它的方法论（怎么控制变量、怎么报分布），用 12.4 拷问问题 穿透厂商引用的分数。

六、HFT 场景 × 类型选配总表

场景 类型 工具/方式 判读重点
日志盘验收 Micro fio direct=1 iodepth=1 P999 + 掉毛频率
网络带宽 baseline Micro iperf3 单/多流分开报 多流是否线性扩展
网卡 PPS 上限 Micro testpmd / pktgen 小包（64B）pps
系统拐点 Simulation 合成 tick 流阶梯加压 拐点位置 + 退化形态
策略回归 Replay 历史 tick + 全分布对比 P99/P999 漂移
端到端 SLA Custom + Passive 生产 span timestamp 见 14-HFT ch09
整机采购 Macro + Micro SPEC + 自有 replay 两轮 两轮结论一致性

常见陷阱

  1. micro 结论当生产结论——「fio 4k 随机写 100µs」不能推出「策略日志写 P99=100µs」，中间有 page cache、journal、邻居。
  2. simulation 不校准形状——固定速率打流量测出的吞吐，遇到生产突发直接失效。
  3. 换后端不重录 trace——NVMe 上重放 HDD 时代的 blktrace，测的是「旧 trace 在新盘上的重排」，不是生产负载。
  4. 行业标准分数直接套用——SPEC 高分机器跑你的延迟敏感负载可能很差（SPEC 奖励吞吐，不奖励 tail）。
自测题（点击展开）
  1. 四种基准类型各自回答什么问题？
答

Micro：组件物理上限；Simulation：合成压力下拐点；Replay：真实流量端到端表现；Industry：横向对比。没有一种能单独回答全部。

  1. replay 的架构漂移陷阱是什么？
答

replay 假设重放路径行为与录制时相同；换盘/FS/网卡/栈后，队列、合并、cache 特征全变，旧 trace 不再代表真实到达模式——换后端要重录。

  1. fio 的 iodepth=1 和 iodepth=32 测的是同一件事吗？
答

不是：iodepth=1 测单请求往返延迟（延迟敏感场景），iodepth=32 测排队下的吞吐上限（带宽场景）——报结果必须带 iodepth。

  1. 合成压测为什么要校准形状？
答

系统的退化形态由负载的时间特征（突发、分布）决定——固定速率测出的拐点在突发流量下不成立。

  1. 历史 tick replay 测策略和测系统延迟的区别？
答

测策略=数据回放（决策正确性，节奏无关）；测系统延迟=性能回放（注入节奏、burstiness 必须保真）。

section-12.4-基准测试拷问Benchmark-Questions

章节导航：12.3 基准测试方法论 · 上一篇 ← · 本章导读

本节讲什么：面对别人（尤其厂商）的亮眼基准报告时的系统性拷问清单——按「工作负载 / 指标统计 / 方法可复现 / HFT 特供」四组展开，以及反向视角：怎么让自己的报告经得起同样拷问。

要点

# 要点 一句话
1 亮眼数字默认可疑 拷问是义务，不是失礼
2 三大穿切入点 workload 形状、统计口径、测量点位置
3 测量点位置最隐蔽 NIC 时间戳 vs 应用时间戳差整条栈
4 每个问题对应一个常见作弊手法 知道怎么骗才知道怎么问
5 自己的报告要能扛住这清单 反向自检

一、拷问的本质：知道怎么骗，才知道怎么问

厂商基准的优化空间不在造假，而在合法地选择对你不利的口径：

优化手法 合法性 效果
挑自己最强的块大小/队列深度 完全合法 IOPS 差 100×
报均值不报 tail 合法 丢包和尖刺全隐藏
测量点放在 NIC 而不是应用 合法 少算整条内核栈
预热后测最好的一轮 合法 冷启动差异消失
专用调优机 vs 你的默认配置 合法 sysctl/固件差异
循环到出现最好数字为止 灰色 幸存者偏差

拷问清单就是把这些口子一个个堵上。

二、第一组：工作负载与环境

问题 为何重要 期待的回答
测试的具体 workload 是什么？ 「500k IOPS」何种块大小、随机/顺序、队列深度？ 完整参数表
与我们生产有多像？ 不像则数字仅供参考 访问模式对比
硬件/软件栈 完整配置？ 特定 NIC 驱动、特定内核的调优不可迁移 型号+版本+sysctl
是否专用机 / 无邻居？ 云 shared vs 裸金属差数量级（ch11） steal 数据
预热 了吗？测的是冷还是热？ 第一次 vs 稳态差数量级 预热协议
温度/功耗 状态？ 热降频是嵌入式和 dense 机房的隐藏变量 温度曲线

三、第二组：指标与统计

问题 为何重要
报的是平均还是 P99/P999？ HFT 看 tail（12.1：均值对排队噪声盲）
测试时长？样本量？ 太短无统计意义；60 秒样本的 P999 是 36 个点
有无错误/丢包/重传？ 吞吐高但丢包无意义——UDP 打满不检查=测发送能力
成本/瓦数？ 同吞吐不同功耗，机房成本完全不同
方差？多轮结果一致性？ 单轮最优 vs 多轮稳定是两个产品

四、第三组：方法与可复现

问题 为何重要
工具与完整命令行？ 能否复现
是否 drop_caches / O_DIRECT？ 测 cache 还是测盘（12.1 失败模式①）
瓶颈 profile 在哪？ 是否测到 intended layer——有没有火焰图/USE 数据证明瓶颈在声称的位置
与竞品测试条件是否一致？ 苹果 vs 橙子
测量点在哪一层？ 见下

⭐ 测量点位置（最隐蔽的口径差异）：同一个「延迟」，测量点从 NIC 硬件时间戳到应用层 span，中间隔着驱动 → 中断/轮询 → 协议栈 → epoll → 业务代码，每一层都有排队和处理时间：

NIC 硬件时间戳        ~ 最低数字（厂商最爱）
  ↓ 驱动+DMA            + 2-10µs
中断/轮询收包
  ↓ 协议栈              + 1-5µs（UDP）~ 更多（TCP）
  ↓ epoll 唤醒          + 1-20µs（调度器参与）
  ↓ 应用读到包           ← 真正的 tick-in 时间
  ↓ 解码+策略+发单       ← end-to-end（客户感知）

报告不写测量点 = 无法比较。对照 ch16.1.5 的 PMC 判读和 14-HFT ch09 的延迟测量点谱系。

五、第四组：HFT vendor 拷问加项

  • 测的是内核栈还是 DPDK？RX 队列几条？RSS/绑核了吗？
  • 报文大小是否像真实行情（小 UDP 多包 burst）？
  • RTT 测量点在哪（NIC timestamp vs 应用）？
  • 是否包含交易所共置 RTT 还是实验室回环？
  • 噪声隔离口径：isolcpus？nohz_full？中断赶走了吗？（ch6 调优）
  • tick 处理是单流还是多 symbol 并发？锁行为完全不同。
  • 报价的是发包延迟还是收包→决策→发单全链？

六、反向自检：让自己的报告无懈可击

给自己的基准报告做一次「预拷问」：

□ 标题就写清：什么负载、什么口径、什么结论
□ 完整命令行 + 环境清单（12.1 的复现配置）
□ 分布图（不只表格）+ 样本量
□ 多轮结果 + 方差
□ 测量点位置图示
□ 瓶颈证据（profile/USE 数据）
□ 结论的作用域声明（适用于 X，不外推 Y）
□ 错误率/丢包/重传一并报告

Gregg 精神：极亮眼的数字默认可疑——用问题拆穿或验证；同时，你自己交出去的每个数字，都要经得起同样的拷问。

HFT / 嵌入式关联

  • 采购谈判：这四组问题就是 RFP 的验收条款——vendor PPT 的 200ns 延迟和你要测的应用层延迟之间的差距，要用测量点问题当场揭穿。
  • 内部汇报：策略团队给管理层看的基准报告同样适用——「改了 X 之后快了」必须附带测量点、分布、多轮方差，否则就是给自己埋雷。
  • 嵌入式：板卡 vendor 的「支持线速」通常是最小包回环——问包大小分布、温度状态、并发流数。

常见陷阱

  1. 只拷问别人不自检——自己的报告同样要过这四组问题。
  2. 忘记问测量点——「延迟」两个字在 NIC 和应用层差一个数量级，这是最隐蔽的口径游戏。
  3. 被单轮最优忽悠——问方差和多轮一致性。
  4. 吞吐高就下单——不问错误率/丢包的吞吐是发送能力测试，不是服务能力测试。
自测题（点击展开）
  1. 厂商基准最常见的三个合法口径游戏？
答

①挑自己最强的块大小/队列深度；②报均值不报 tail；③测量点放在 NIC 硬件层而非应用层（另外还有预热后测、专用调优机）。

  1. 「P99 = 3µs」报告最该追问什么？
答

测量点在哪一层（NIC 时间戳还是应用 span）、样本量多少、多轮方差如何——三者缺一不可比。

  1. 为什么 UDP 打满的高吞吐无意义？
答

不检查丢包的 UDP 发送测的是发送能力——接收端可能大量丢包，服务能力为零。吞吐必须和错误率一起报。

  1. 60 秒测试报告 P999 有什么问题？
答

60 秒里 P999 对应约 36 个样本点——统计意义极弱，长尾估计不稳定，需要更长时长或多轮。

  1. 自检清单里「结论的作用域声明」指什么？
答

明确写出结论适用于什么负载/环境/条件，不外推到什么——防止三个月后被人拿去当万能结论。
