﻿# Ch 2 方法论 · Methodologies

Systems Performance 2nd · Brendan Gregg · 精读

本章定位：全书方法论基石 — 工具、内核版本、硬件会换，但术语、模型、USE/RED、排队论、统计与可视化这套「持久技能」不会过时。Ch 1 说了「先看业务再看资源」；本章给出可重复执行的套路。

大白话 · 本章就四件事

软件会变，下面这套思维不会。

① 先统一「说话方式」。

  • 延迟 / 响应时间：等多久；吞吐量：单位时间干多少活；使用率：资源忙不忙；饱和度：排队有多长；瓶颈：最卡的那一环。
  • 量化里：tick 处理延迟、发单 RTT、CPU 利用率、网卡队列深度 — 都是同一套词。

② 两个视角，别混着用 — 但要接力。

视角 问什么 工具优先级 谁常用
工作负载分析（先） 哪个环节、影响多大 埋点 counter / histogram → Prometheus / Grafana 开发 / 策略
资源分析（后） 为什么会出问题 perf、ss、ethtool、tcpdump、dmesg 运维 / SRE

HFT：先 Workload（Grafana 确认 tick 掉速、P99 10→100 μs、reject 突增）→ 再 Resource（锁定进程/链路后 perf、抓包）。

③ 别用「反面套路」，用 USE / RED / 延迟分解。

  • ❌ 只盯熟悉的工具（路灯下找钥匙）、乱改参数、甩锅给网络/DB。
  • ✅ USE：每个资源看 Utilization / Saturation / Errors → 附录 A
  • ✅ RED：每个服务看 Rate / Errors / Duration（微服务/cloud 常用）
  • ✅ 延迟分解：总延迟拆成几段，找最长那段（二分法）— 量化排查主武器。

④ 数字别只看平均值；资源别跑太满。

  • 统计 / 监控 / 可视化：mean 骗人、五种图、Prometheus+Grafana — 2.8 · 2.9 · 2.10
  • 排队论：M/M/1 ~70%、M/D/1 ~80% — 见 2.6.1 概览、2.6.2 M/M/1。
  • 容量规划：事前体检 — 定 SLO → 模型算资源 → 压测验证 — 2.7.1 · 2.7.2

2.1

section-2.1-HFT术语与团队对齐

本章定位： 建立性能分析的 统一语言 — 后面 USE、RED、延迟分解都靠这套词。
HFT 里别说「慢」，要说 平均延迟 / P999 长尾 / 抖动；别说「忙」，要说 利用率 / 饱和度。

→ 命令速查：2.2 · 时间尺度：2.3.1

HFT · 口语 → 标准术语（团队对齐用）

口语 / 模糊说法 标准术语 HFT 里具体指什么
「策略慢了」 Latency / Response time 须拆：Mean（压测基线）、P99/P999（tail）、Max（单次灾难）、Jitter（抖动 = 相邻 tick 延迟差或 P99 波动）
「行情多、单多」 Workload 工作负载 订单流量 + 撤单 + 行情 tick 的 组合：包率、订单形状、burst 时段 — 不是单一 QPS 数字
「CPU/网卡很忙」 Utilization 利用率 资源 忙碌时间占比：mpstat %usr、网卡带宽占用率 — 忙不忙
「排队、堵了」 Saturation 饱和度 超出即时处理能力后的排队：run queue、NIC TX queue、锁等待、softirq 积压 — 等多久
「卡在哪」 Bottleneck 瓶颈 限制端到端的最慢环节 — 用 延迟分解 找最长段（→ 2.5）
「每秒处理多少」 Throughput 吞吐量 ticks/s、orders/s、packets/s
「丢包、错了」 Errors 错误 USE/RED 里的 E — ethtool drop、拒单、checksum 错

和 Ch1 的衔接：

Workload（订单流组合）  →  自上而下：程序在干什么？
Utilization / Saturation  →  自下而上：资源够吗、排队多长？
Latency 三分法（Mean/P999/Max）  →  [Ch1.6](../../chapter-01-intro/notes/section-1.6-延迟指标与读法.md)

为什么要统一： 和团队 / 券商 / 运维调优时，同一词指同一指标 — 避免「慢」到底是 Mean 还是 P999、「忙」是利用率 80% 还是 TX 队列已满。

术语一句话 → 排查方向（不再纠结主观「慢」）

团队里说 大家立刻懂 先往哪查 通常 不是
「IOPS 低」 磁盘/存储 每秒 I/O 次数没跑满 容量、盘是否瓶颈、日志是否误上热路径 不是「策略代码算得慢」
「P99 延迟飙了」 最慢 1% 订单/tick 变差 tail：调度、IRQ、NUMA、锁、trace 拆单笔 不是「平均表现一直差」
「P999 / Max 超 SLO」 极端行情下有 单笔卡死 Ch1.7 追踪 抓那一次 只抠 Mean 无意义
「利用率 90%」 CPU/网卡 忙的时间占比 是否该绑核、是否多线程可扩展 还不等于「已排队」— 要看 饱和度
「饱和度高了」 TX 队列 / run queue 在等 加容量、减争用、削 peak workload 不是单纯「再优化算法」能搞定 
「慢」           →  先问：Mean？P99？Max？哪一段？
「IOPS 低」      →  资源吞吐没吃满，查 workload 是否根本没打满盘/网卡
「P99 飙了」     →  tail 问题，查极端行情窗口 + trace，不是重写整条策略

HFT 价值： 统一语言 = 指标 + 排查方向 一次说清 — 会议里直接进工具链，不花在「你觉得慢我觉得不慢」上。

关键术语（原书 + HFT）

术语 含义 HFT 举例
IOPS 每秒 I/O 操作数 日志盘、持久化；IOPS 低 = 吞吐能力未吃满，多指 资源侧 非逻辑慢
Throughput 单位时间完成的工作量 ticks/s、orders/s
Response time / Latency 一次操作从发起到完成的时间 tick→signal、signal→exchange ACK；须报 P99/Max，不单报 Mean
Utilization 资源忙碌时间占比 CPU %、网卡带宽占用 — 处理交易时的饱和程度
Saturation 超出即时处理能力后的排队程度 run queue、NIC TX queue、锁等待 — 利用率高的下一层
Bottleneck 限制整体性能的最慢环节 单核打满、跨 NUMA、TCP 栈

常见陷阱

  1. 术语不对齐——开发说「延迟」指 P50、运维说「延迟」指 mean、交易员说「延迟」指最大值，必须统一口径
  2. IOPS 和吞吐混淆——小块高 IOPS ≠ 大块高吞吐，HFT 行情包小但pps高，和存储吞吐是两回事
  3. Latency 和 Response Time 不区分——Gregg 定义 latency = 服务时间，response time = latency + queue time
自测题（点击展开）
  1. Latency 和 Response Time 的区别是什么？
答

Latency = 服务时间（处理本身），Response Time = latency + 等待队列时间

  1. HFT 团队为什么需要对齐术语？
答

不同角色（开发/运维/交易员）对「延迟」「吞吐」「IOPS」理解不同，不对齐会导致沟通失误

  1. Utilization 高是否一定意味着瓶颈？
答

不一定——利用率高但饱和度低（run queue 短）说明 CPU 在干活但没排队；饱和度高才是瓶颈信号

Errors 网卡/内核错误 ethtool -S、dmesg USE 里的 E

固定套路

1. mpstat / vmstat / ethtool  →  Utilization + Saturation（resource 扫盲）
2. sar -n DEV                 →  网卡 Throughput
3. perf top                   →  Bottleneck 嫌疑函数
4. perf record + 火焰图       →  固化 workload 热点
5. perf trace / bpftrace      →  Latency tail 拆 syscall/函数

HFT 注意

  • 热路径：mpstat、ethtool、perf 优先；iostat/dd 除非怀疑日志/回放盘
  • 实盘 perf：采样别太重 — 与 Ch1 观测 vs 实验 一致
  • P99/Max：应用内分位数 + trace 抓 spike，不单靠 perf top 平均值

→ 工具详解：Ch 4 · Ch 13 perf · Ch 15 BPF

常见陷阱

  1. 命令记不住就用复杂工具——先掌握 vmstat/mpstat/ss/iperf3 五个基础命令，再上 BPF
  2. 命令参数不记——vmstat 的 r 列、si/so 列含义不同，混淆会导致误判
  3. 只看一条命令的输出——vmstat + mpstat + iostat 三条合在一起看才能定位是 CPU/内存/IO 哪段
自测题（点击展开）
  1. vmstat 输出中 r 列和 b 列分别表示什么？
答

r = 运行队列长度（等 CPU 的线程数），b = 不可中断睡眠（通常等 I/O）的线程数

  1. HFT 排障第一反应应该跑哪几条命令？
答

vmstat 1（全局）、mpstat -P ALL 1（每核）、ss -tiepm（网络）、iostat -x 1（IO）

  1. 为什么 uptime 的 load average 不能代替 per-CPU 分析？
答

load average 是指数移动平均且混合了 D 态线程，8 核 load=8 不等于 100%，要看 mpstat 每核

2.3.1

section-2.3.1-时间尺度与排查走查

口诀： 先圈 战场量级 → 再选术语 + 命令 → 别跳档优化。

← 2.2 命令速查 · → 2.3.2 性能权衡

两层用法：

① 时间尺度  →  订单延迟落在哪个数量级？先圈定排查的「战场范围」
② 专业术语  →  在该量级上用 Throughput / RTT / Saturation 等量化、拆到具体组件

Gregg「时间放大」类比

基准：1 个 CPU 周期 ≈ 0.3 ns  →  在类比里 = 1 秒
换算：真实延迟 ÷ 0.3 ns  ≈  放大后的「秒数」
事件 真实延迟 放大后感受
L1 命中 ~1 ns ~3 秒
L2 / L3 ~10～40 ns 数分钟
主存访问 ~100 ns ~5 分钟
网络 RTT ms 级 数年～世纪级
跨核 / 跨 NUMA miss 上再翻倍 ~10 分钟
内核态 / syscall μs～ms 世纪级 
L1 不命中 → 主存  =  从「几秒」→「几分钟」
再跨网络        =  直接「几年」档 — HFT 热路径上的世纪级浪费

HFT 推论： 订单簿、持仓、风控计数器 锁在 L1/内存；tick→撮合→信号 上每多一次主存 miss，都是在抢「几秒 vs 几分钟」。

HFT · L1 命中是什么

大白话： 数据 刚好在 L1，不用去 L2/L3/主存。

概念 说明
L1 未命中 延迟翻几倍～几十倍 — 撮合从百 ns 飙到 μs
HFT 热数据 订单簿档位、最优价、持仓、风控计数器 — 布局紧凑、绑核

和时间尺度的关系： 只有锚到 路径 B（~500ns 撮合）才抠 L1；端到端 2ms 网络（路径 A）先别纠结 cache。

→ Ch 6 · Ch 4 PMC

延迟落在哪一档，就查哪一档

端到端延迟 战场 优先查 别死磕
μs 级 tick→signal CPU / cache perf、绑核、false sharing 交换机 ms 抖动
百 μs～ms 级 ACK 网卡、TCP 队列 ss -s、ethtool -S、RTT 纳秒 cache 微调
ms+ 级 网络路径、拥塞 RTT、重传、路径 单机指令级优化

反例： 只抠 cache，没解决 ms 级网络抖动 — 时间尺度锚错了。

排查顺序 vs 优化优先级

Gregg 「网络是替罪羊」 = 排查顺序，不是「网络不重要」。

规则
排查顺序 先 perf/mpstat/vmstat 排除本地 — 再碰网络
优化优先级 tcpdump/ss 实锤后 — 网络 最高优先级（年级收益）

一句话： 排查时网络是「最后怀疑对象」；实锤后是「第一个优化对象」。

路径 A · 发单→ACK 2ms（网络战场）

0. 本地排查：mpstat / vmstat / 分段计时 — 别一上来怪交易所
1. 锚量级：tcpdump / ACK 时间戳 → 2ms 在网络段
2. ss -s / ethtool -S / sar -n DEV / RTT
3. 队列满、丢包 → 迁 IRQ、换路径 — 不是改 if-else

路径 B · 撮合 500ns（CPU/cache 战场）

1. rdtsc / histogram → 锚定 ns～μs CPU 热路径
2. perf top / 火焰图 / cache-misses
3. 改数据结构、绑核 — 不是先怪交换机
量到什么 锚在哪 工具 别误闯
ACK 2ms ms·网络 ss、ethtool perf 抠 cache
撮合 500ns ns～μs·CPU perf、火焰图 tcpdump
步骤 做什么
1 P99/Max 落在 ns/μs/ms → 定战场
2 选 Utilization / Saturation / Throughput / Latency
3 用 2.2 命令表 → 定工具

优化优先级：先砍「分钟、年级」，再挤「毫秒」

你在砍什么 类比里 HFT 动作
主存 miss ~5 分钟 紧凑 order book、SoA
跨核 / NUMA ~10 分钟 绑核、减 false sharing
内核 / syscall 世纪级 DPDK、用户态栈
JVM / GC 毫秒档挤水分 大尺度清完后再碰 
错误：P99 飙了 → 先改 G1
正确：miss + 跨核 + 内核 → 算法/绑核 → 最后 JVM

常见陷阱

  1. 跳档优化——纳秒级问题用毫秒级工具查（如用 top 查微秒级抖动），工具精度不够根本看不到
  2. 时间尺度不匹配——HFT tick-to-trade 在微秒级，但 sar 默认 10 分钟粒度，完全看不到尖刺
  3. 忽略时钟源——TSC vs CLOCK_MONOTONIC vs gettimeofday 精度不同，混用导致测量不准
自测题（点击展开）
  1. HFT 延迟排查为什么要按时间尺度分层？
答

不同延迟量级需要不同精度的工具——纳秒级用 PMC/rdtsc，微秒级用 BPF，毫秒级用 vmstat

  1. 为什么 sar 默认粒度对 HFT 没用？
答

sar 默认 10 分钟平均，微秒级尖刺被完全平均掉，需要 sar -I 1 或更高频工具

  1. HFT 测量应该用哪个时钟源？
答

CLOCK_MONOTONIC 或 TSC（rdtsc），避免 gettimeofday 的闰秒/调整问题

2.3.2

section-2.3.2-性能权衡

系统设计 没有免费午餐 — 从 需求定优先级，别在参数里死抠「平衡点」。

← 2.3.1 时间尺度 · → 2.3.3 负载与架构

好 / 快 / 便宜（三选二）  →  成本 vs 质量 vs 规模
CPU ↔ 内存               →  算力 vs 容量 / 访问速度
延迟 ↔ 吞吐量            →  单条多快 vs 单位时间处理多少

1. 好 / 快 / 便宜 — 不可能三角

维度 HFT 里指 砸钱买到
好 低延迟、少 tail 专线、共置、低延迟网卡
快 高吞吐 ticks/s 多核、大内存、定制硬件
便宜 开源、普通云 —

三者不能同时成立： 又要好又要快 → 没法便宜；想便宜 → 做不到又好又快。

选型 偏向 代价
Rust / C++ 好 + 快 开发贵
Python 开发快 + 便宜 撑不起真高频
Java 生态 + 吞吐 GC 要额外调

HFT 做法： 多数 先保「好」= 尾延迟 + 稳定，再换吞吐。

2. CPU ↔ 内存

策略 得到 付出
内存换 CPU（主流） CPU 不等 IO 内存贵、false sharing
省内存 + 锁 成本低 延迟上去
落盘 省 RAM 延迟崩
压缩 少占 RAM 耗 CPU、加 ns～μs 
热路径：订单簿锁内存（cache 友好）
冷路径：日志、回放可磁盘

→ Ch 5.2 · Ch 7

3. 延迟 ↔ 吞吐量 — 队列在中间

核心： 队列 / 批处理 连接两者 — 队列越深，吞吐↑，单条等待↑。

收费站类比：

延迟 = 单车过站时间；吞吐 = 单位时间车数
凑批放行 → 吞吐↑、单车等↑；随到随走 → 延迟↓、吞吐↓
策略 单订单延迟 吞吐 适合
随到随处理 ~10 μs ~1 万/s 做市、抢 tick
攒 1ms 批量 ~1 ms ~10 万/s 清算、对账 
别既要又要：做市保延迟；清算可批量
队列是 Saturation 信号，不是免费提吞吐的旋钮

权衡怎么用

1. 写清 SLO：P99 < X μs 还是 orders/s > Y？
2. 认三角：主动放弃第三项
3. 热路径内存换 CPU；冷路径可省
4. HFT 默认延迟优先
5. 与 [优化优先级](./section-2.3.1-时间尺度与排查走查.md#优化优先级先砍分钟年级再挤毫秒水分) 衔接

→ Ch 12 基准 · 2.5 方法论

常见陷阱

  1. 延迟和吞吐同时优化——加 batch 提吞吐但增单笔延迟，HFT 通常牺牲吞吐保延迟
  2. 只优化不量化 trade-off——改了 Nagle/TCP_CORK 但没测延迟变化，无法判断改对了没有
  3. 忽略二级效应——绑核降调度延迟但增单核热点，cache miss 可能反而升高
自测题（点击展开）
  1. HFT 中延迟和吞吐的 trade-off 体现在哪里？
答

batch 合并提吞吐但增单笔等待延迟，HFT 通常选低延迟（小包直发）牺牲吞吐

  1. 为什么性能优化必须量化 trade-off？
答

没有量化就不知道改动是否真的改善——改了 CPU 但引入延迟抖动，需要前后对比完整指标

  1. 绑核的二级效应是什么？
答

绑核降调度延迟但所有负载集中到一个核，可能增 cache miss 和热点争用

负载 vs 架构（Load vs. Architecture）

加机器能解决的别重写核心；设计硬伤加资源也喂不满。

类型 定义 本质
负载过高 请求量 超过容量 → 排队 容量不够
架构问题 没法扩容 或争用严重 设计硬伤

负载 — 量大了，机器吃不消

10 万笔进来 / 每秒只能处理 1 万 → 9 万排队 → P99 飙
特征：peak 过去或扩容后恢复
信号 现象
队列变长 订单队列 ↑、vmstat r ↑
还能扩 横向加节点有效
短时过载 开盘、burst

解法： 扩容、削 peak、限流 — 不必先动核心算法。

架构 — 加核也没用

单线程撮合，100 核只吃 1 核 → 架构硬伤
多线程 + 全局锁 → 核越多越慢
信号 现象
一满一闲 单线程 / 全局锁
加资源反跌 锁、false sharing
低负载也慢 设计问题

解法： 无锁、分片 order book、绑核 — 改架构。

区分口诀

加资源能压住  →  负载
加资源没用/更慢  →  架构
实验 负载 架构
流量降一半 延迟恢复 仍慢
横向加节点 P99 改善 吞吐不涨
换更强单机 有改善 几乎无感

术语组 后面用在哪

常见陷阱

  1. 把负载问题当架构问题——加机器解决不了单线程瓶颈，先确认是负载饱和还是架构限制
  2. 已知未知不区分——已知问题（可预测的瓶颈）和未知问题（随机故障）排查路径完全不同
  3. 架构调优不改负载——先减不必要的工作（负载优化）再改架构，顺序反了浪费资源

答

负载分析看「在干多少活」，架构分析看「能干多少活」——先确认负载合理再改架构

  1. 已知未知在性能排查中如何区分？
答

已知 = 可预测的瓶颈（容量不够），未知 = 随机故障（尖刺/抖动）——排查路径不同

  1. 为什么先优化负载再改架构？
答

消除不必要的工作（负载优化）ROI 最高，架构改动成本大且可能引入新问题

2.4

section-2.4-两种分析视角

出处： Gregg《性能之巅》· 性能分析有两套 互补 路径 — 不必二选一，故障排查、容量规划通常 结合使用。
HFT 实操要点： 两者 不是割裂的两套世界，而是 有先后顺序的接力 — 先 Workload 抓业务真相，再 Resource 挖底层原因。

自上而下  Workload Analysis   业务 → 系统   「哪个环节、影响多大？」
自下而上  Resource Analysis   资源 → 业务   「为什么会这样？」
         ────────────  先上后下，不是二选一  ────────────

→ 术语对照：2.1 · 2.2 命令 · 2.3.1 走查 · 2.5 分层埋点 · 附录 A

先 Workload，后 Resource — 一句话

阶段 问什么 靠什么 优先级
① 业务定位 问题出在 哪个环节、影响多大 代码埋点 counter / histogram、Prometheus / Grafana、RED 指标 最先
② 底层下钻 为什么 会出问题 perf、ss、ethtool、tcpdump、dmesg、USE 清单 定位到进程/链路之后

不是不用 Linux 命令 — 是 靠后。Workload 的核心是先确立 业务维度的真相：「每秒 tick 掉了多少」「订单 P99 从 10 μs 涨到 100 μs」「报单 reject 率突增」—— 这些必须靠 开发阶段埋好的点 和 应用层监控 先确认；等 narrowed 到「某个进程、某段链路、某个接口」，再让底层工具上场解释机制。

Grafana / 应用 histogram     →  「报单 reject 率突增」     （Workload · 第一步）
        ↓ 锁定接口 / 进程 / 时段
tcpdump 该接口流量 · dmesg     →  内核/网络是否异常         （Resource · 第二步）
perf -p <pid> · ss -s          →  CPU 耗在哪、有无重传      （Resource · 第三步）

一、资源分析（Resource Analysis · 自下而上）
适用 系统管理员、SRE、平台工程、运维 — 也在 Workload 锁定嫌疑之后
看什么 CPU、内存、磁盘 I/O、网卡、总线 — USE：Utilization / Saturation / Errors
核心指标 利用率、队列饱和度、硬件 drop/error、软中断、重传、上下文切换
工具优先级 在「哪个进程 / 哪条链路有问题」已知之后 再开 mpstat / perf / ethtool

典型问题（回答「为什么」）：

  1. 策略进程是不是 某个核 100%、softirq 跑满？
  2. 网卡有没有 drop、硬件 error？
  3. 内存 带宽 / NUMA 是否成为瓶颈？
  4. TCP 有没有 重传（ss）？内核有没有 OOM / 驱动报错（dmesg）？

配套工具：

资源 命令 何时用
CPU mpstat -P ALL 1、perf top -p <pid> Workload 指向某 PID 后

二、工作负载分析（Workload Analysis · 自上而下）
适用 应用开发、策略/交易工程、产品性能分析

工具优先级 ① 代码埋点（counter、histogram）→ ② Prometheus / Grafana → ③ 追踪（bpftrace / trace）

典型问题（HFT）— 全部从业务指标入口：

  1. 行情每秒多少 tick？（counter / RED Rate）
  2. 下单 / 报单接口 P99 多少 μs？（histogram / RED Duration）
  3. 报错是 timeout 还是 reject？（RED Errors）

优先级 层级 工具

答

先自顶向下（workload）定位是哪段慢，再自底向上（resource）钻根因

答

只自顶向下可能漏掉内核/硬件隐藏开销，只自底向上容易无目标地收集数据

2.5

section-2.5-性能分析方法论

反面方法论（Anti-Methods）— 避免

名称 表现 HFT 版「踩坑」
路灯反面法 只用自己熟悉的工具，缺乏目标 只会 top，从不看 tick-to-trade 分段
随机修改 盲改参数看问题是否消失 乱调 -O3、绑核、TCP 参数，无 baseline
责怪他人 无数据甩锅网络/交易所/DB 「肯定是交易所慢」— 没有 RTT 分解证据

共同问题： 无假设、无度量、无复现 → 浪费共置窗口时间。

USE 方法（The USE Method）— 资源分析核心

对每个硬件或软件资源，依次问三件事：

字母 英文 问什么
U Utilization 资源有多忙？
S Saturation 排队/等待有多严重？
E Errors 有没有错误？

清单思维： CPU、每个 CPU、内存、容量、网络接口、协议栈、磁盘… 逐项过，不漏资源。

Linux 实操清单 → 附录 A
HFT 重点资源：CPU（含 NUMA）、内存带宽、网卡/NAPI 队列、锁与 run queue — 磁盘/文件系统多为 ⚪。

RED 方法（The RED Method）— 服务 / 微服务

对每个服务（或逻辑组件）：

字母 英文 问什么
R Rate 请求率多少？
E Errors 错误率多少？
D Duration 每次请求耗时分布？

与 USE 关系： RED 偏 workload（服务对外行为）；USE 偏 resource（底下资源）。网关、风控、策略服务可 RED；底层仍 USE。

工作负载特征分析（Workload Characterization）

用四个问题描述负载：

问题 内容
Who 谁产生负载（用户、市场、上游 feed）
Why 为何此时产生（开盘、事件、策略触发）
What 负载特征（读多写少、小包高频、burst）
How 随时间如何变化（日周期、波动率 regime）

Gregg 强调： 最大收益常来自 消除不必要的工作 — 少算、少发、少 syscall、少拷贝，比「把必要的工作调快 5%」更划算。

HFT 实战：业务链路分层埋点 + 工具串连

思路： 沿 tick-to-trade 从外到内 逐层加计数/计时；先 Workload（埋点 / Grafana）确立业务真相，再在数字对不上或异常已锁定时，用 Resource 工具（tcpdump / perf / ss） 交叉验证或下钻。
与 2.4 先上后下 一致 — 不是「只用命令」或「只用埋点」，是 优先级：counter / histogram 最先，Linux 命令 接力。

工具优先级（全链路通用）：

P0  开发期埋点     counter（Rate）、histogram（P99）、段间 timer、错误码分类
P1  业务监控       Prometheus / Grafana  —  「tick 掉了多少」「P99 10→100 μs」
P2  交叉 / 下钻    tcpdump、ethtool、ss   —  埋点与网卡不一致，或 reject/P99 已锁定链路
P3  根因           perf -p <pid>、dmesg    —  锁定进程后看 CPU / 内核

L2 解析入口         atomic counter（ticks/s）          ← P0 · 业务真相

大白话：排队论是什么？

排队论研究的是 「系统接请求的排队规律」。

餐厅类比：

餐厅 排队论 HFT
进店的 客人 请求（到达） 报单请求、行情 tick
服务员 + 后厨（接待上限） 服务节点 报单引擎、撮合 loop
等位多久、队排多长 排队延迟 L、逗留时间 W submit→ACK 变慢、网关对象积压
饭点会不会 爆单 利用率 ρ 过高 → 系统失稳 开盘 burst → timeout / reject
  1. 客人多久能吃上 → W
  2. 队排多长 → L
  3. 高峰期会不会炸 → λ 接近 μ 时延迟 陡增

落到 HFT： 安全水位取决于模型 — M/M/1 ≈ 70% vs M/D/1 ≈ 80%（详见各子节）。

三参数标记法：A / B / c

  A        /    B      /   c
  到达间隔      服务时间     并行节点数

第一位 · A（到达间隔）

| M（Markov） | 负指数间隔 → Poisson 到达 | 行情 tick、零散报单、开盘 burst |

第二位 · B（服务时间）

| M | 服务时间随机 | 分支、cache miss | | D | Deterministic 固定 | 纯内存查订单簿、无分支撮合 | | G | General 任意 | 快单 + 慢查混合 |

第三位 · c（节点数）

| 1 | 单线程报单引擎 | | c | 多核撮合、线程池、RSS 多队列 |

三个 HFT 常碰组合：

模型 场景 拐点参考
M/M/1 随机服务 + 单线程 ρ ≲ 70% → 详
M/D/1 固定服务 + 单线程 ρ ≲ 80% → 详
M/M/c 随机服务 + 多核 ~75%~80%（c=8）→ 详

选型速查：

服务耗时有随机波动     →  M/M/1   ~70%
纯内存、无分支热路径   →  M/D/1   ~80%
多核 / 线程池         →  M/M/c
快慢单混合            →  M/G/1

符号与 Little 定律

资源有队列时，利用率未到 100%，响应时间也会恶化 — 「CPU 才 70% 怎么 P99 爆了？」常对应 M/M/1。

符号 含义 HFT 例子
λ 到达率 报单/s、tick/s
μ 服务率（单节点上限） 单线程 orders/s
ρ = λ/μ（M/M/1） 利用率，须 < 1 λ=7000, μ=10000 → ρ=0.7
L 平均任务数（含排队） 网关积压对象
W 平均逗留时间 submit→ACK

Little 定律： L = λ × W

常见陷阱

  1. 忽略排队论直接加机器——不知道拐点在哪，可能在 70% 利用率就已经 tail latency 爆了
  2. M/M/1 套所有场景——服务时间确定型用 M/D/1，多服务台用 M/M/c，模型选错结论全错
  3. 只看利用率不看排队长度——利用率 80% 但 queue 已经很长，延迟已经在指数上升

2.6.2

section-2.6.2-M-M-1-拐点与预警线

M/M/1 = 随机到达 + 随机服务 + 1 节点。单线程网关、服务时间有波动时用此模型。
← 概览与记号 · → M/D/1 · M/M/c · 计算器

核心公式

ρ = λ / μ
L = ρ / (1 - ρ)
W = 1 / (μ - λ)
W_q = ρ / (μ - λ)
W / W₀ = 1 / (1 - ρ)     （W₀ = 1/μ）

为什么拐点在 ~70%？— 单向车道

ρ 现象
~60% 偶尔慢车，几乎不堵
~70% 一辆慢 → 排队；随机波动 快速拉长队尾
→90% 任何扰动 → 长队

HFT： λ burst + 处理耗时随机差 → ρ≈70% 时 P99 可从 μs 跳到 ms → timeout/reject。

等待倍数 W/W₀ = 1/(1-ρ)
  3× │         ╭────    ← ρ≈0.7 拐点
  2× │    ╭────
  1× │────
     └────────────── ρ
       0.6  0.7  0.8  0.9
ρ L W/W₀ HFT
60% 1.5 2.5× 开始吃 tail
70% 2.33 ~3.3× 拐点
80% 4.0 5× 危险
90% 9.0 10× 不可接受

限流示例： μ=10k/s，SLO 要求 W/W₀<3 → ρ<0.67 → λ_max ≈ 6,700/s

读法确认：到 70% 就别再往上顶

对。 70% = M/M/1 安全红线（预警线） — 不是还能再榨 30%：

水位 P99（示意） 后果
~50% ~5 μs 正常
≥70% ~50 μs 大量拒单 — 不可接受
更高 μs→ms 排队雪崩

部署留 10%~15% 缓冲：

拐点（预警线）    ≈ 70%
Grafana 告警      ≈ 60%     ← 脉冲报单不易踩拐点
限流硬顶（可选）  ≈ 65~67%

核心：在陡增前限流或扩容，别等 P99 已从 5 μs 跳到 50 μs。

→ 压测 knee：Ch 12.3

常见陷阱

  1. M/M/1 在 70% 利用率才报警——实际上 70% 时 queue 延迟已经约为服务时间的 2.3 倍，HFT 应更低
  2. 用线性外推排队延迟——M/M/1 延迟是 1/(1-ρ) 的非线性曲线，80%→90% 延迟翻倍不是线性
  3. 忽略服务时间方差——实际服务时间不是完美指数分布，方差更大时拐点更早
自测题（点击展开）
  1. M/M/1 模型中利用率和排队延迟的关系是什么？
答

延迟 = 服务时间 / (1 - ρ)，非线性——ρ=0.5 延迟翻倍，ρ=0.9 延迟 10 倍

  1. HFT 中 M/M/1 的 70% 预警线意味着什么？
答

利用率 70% 时平均排队延迟约为服务时间 2.3 倍——对微秒级系统已经不可接受

  1. 为什么不能线性外推排队延迟？
答

1/(1-ρ) 是非线性曲线，从 80% 到 90% 延迟翻倍，从 90% 到 95% 再翻倍

M/D/1 — 固定耗时纯内存报单 {#md1}

M/D/1 = 随机到达 + 固定服务 + 1 节点。拐点 ~80%，比 M/M/1 高约 10%。

M/M/1 M/D/1
服务时间 随机 固定
排队来源 到达 + 服务随机 仅到达随机
拐点 ~70% ~80% 
W / W₀ = (2 - ρ) / (2(1 - ρ))
L      = ρ + ρ² / (2(1 - ρ))
ρ M/M/1 W/W₀ M/D/1 W/W₀

HFT： 固定长度序列化 + 内存订单簿、无 DB/复杂分支 → ρ ≲ 0.8（μ=10k → 限 ~8k/s vs M/M/1 ~7k）。

M/M/c — 多核撮合集群 {#mm/c}

M/M/c = 随机到达 + 随机服务 + c 节点。

ρ = λ / (c × μ)     （系统级利用率）
对比 M/M/1 M/M/c
单核 ρ=0.7 已陡 c=4 分摊 λ，理想近 4× 吞吐
单队列 共享队列 + 锁 → 有效 c 可能 < 物理 c（→ 2.7.1 USL）

模型 拐点（参考） 告警（−10~15%）
M/M/1 ~70% ~60%
M/D/1 ~80% ~65~70%
M/M/8 ~75%~80% ~65~70%

HFT 映射： 多核撮合（c=核数）、RSS 多队列、线程池报单序列化。

实操： 扫 c=1,2,4,8… 至 ρ 低于模型安全水位且 W 达标；加核不成比例 → 争用，查 USL。

M/G/1 — 快慢单混合

G = 任意服务时间分布 — 只需 E[S] 与 Var(S) / P99。

  • Var(S) 越大 → 同样 ρ 排队 越长
  • 90% 快单 + 10% 慢查 → M/M/1 低估队列，用 M/G/1

输入： 2.5 histogram 或压测服务时间样本 → 喂计算器。

常见陷阱

  1. M/M/c 当 c 个服务台独立——实际上多核间有共享资源（cache/内存控制器），不是完美独立
  2. M/D/1 延迟和 M/M/1 一样——确定型服务时间排队更短（方差为 0），M/D/1 延迟约为 M/M/1 的一半
  3. M/G/1 不验服务时间分布——通用模型需要知道方差，不测实际分布直接套结论会错

M/M/c 有 c 个并行服务台，利用率 ρ = λ/(cμ)，多服务台下同总利用率排队更短

  1. M/D/1 比 M/M/1 排队延迟短多少？
答

约为 M/M/1 的一半——服务时间方差为 0，没有长尾服务拖累队列

  1. HFT 什么场景适合 M/D/1 模型？
答

2.6.4

section-2.6.4-排队论计算器

← 概览 · M/M/1 · M/M/c

本节讲什么

把前三节的模型变成手边的工具：计算器吃什么输入、吐什么输出、输出里哪些可信哪些要校准。核心认知是定位问题——排队论计算器是「拐点估算器」和「容量规划起点」，不是「延迟预测器」。闭式解给均值，tail 要靠仿真或压测校准，这个边界划不清就会误用。

要点

# 要点 一句话展开
1 两类输出：延迟与拐点 前者看均值 W，后者找 knee 定限流/告警线
2 输入三个数：λ、μ、c 单位一致性是第一坑（每秒 vs 每毫秒差 1000×）
3 闭式解只给均值 P99/P999 要仿真或压测 histogram 校准
4 拐点做告警要再打折 knee - 10~15 个百分点做预警线
5 模型是估算不是真理 cache/调度/锁的非线性因素模型不管
6 计算器的归宿是压测的对照组 拐点估出来 → Ch12 压测验证 → 回填修正

一、两类输出

类型 输入 输出 用途
① 延迟 c、λ、1/μ W（均值逗留时间）、Wq（纯排队时间）、L（队长） 「这个利用率下平均多慢」的量级感
② 拐点 同上 CPU knee → 定限流 / 告警 不试不知道会爆炸的那条线

两类输出的可信度不同：W 的绝对值经常不准（真实系统的服务时间不是指数分布、到达不是泊松），但knee 的位置相当鲁棒——不同分布的拐点都在 70%~85% 这个带里，因为「排队长度随 ρ→1 发散」是结构性质不是分布性质。这就是计算器的主用途是找拐点而非算延迟的原因。

预警线 + 缓冲：

步骤 做法 产出

经验规律：真实系统的 P99 通常比 M/M/c 理论 tail 更差——因为模型假设里「服务时间独立同分布」「到达平稳」在真实系统都不成立（行情风暴 = 突发相关到达，风暴期服务时间也变长——相关性放大 tail）。所以模型给的 P99 当下限用，不是中心估计。

def to_per_second(rate, unit):
    return rate * {"s": 1, "ms": 1e3, "us": 1e6}[unit]

参数 从哪来 常见错

为什么叫阿姆达尔和 USL？

阿姆达尔定律（Amdahl's Law）

核心问题： 根据现有逻辑里 必须一段段串行跑 的部分，推算 加核后整体性能最终能到哪儿 — 给容量规划划 理论天花板。

公式：

S(N) = 1 / ( f + (1-f)/N )
符号 含义 HFT 例子
S(N) 加速比（相对单核） 8 核实际能到单核的几倍
N 核心数 / 并行度 报单集群 8 核
f 必须串行 的时间占比（0~1） 撮合核心 20% 无法并行
(1−f) 可并行部分 行情推送、解码等 80%

核心数 → ∞ 时的极限（理论天花板）：

S_max = 1 / f        （N → ∞ 时，(1-f)/N → 0）

常见误区：串行 20% ≠ 能加速 20 倍

不是「串行占 10% → 最多快 10 倍；占 20% → 最多快 20 倍」。

正确逻辑： 串行占比 f 在分母 — 核再多，也只能把 可并行的 (1−f) 部分摊薄；f 那段永远单线跑。

串行占比 f S_max = 1/f（核无限多） 读法
10% (0.1) 10× 最多快 10 倍，不是「10% 所以 +10%」
20% (0.2) 5× 最多快 5 倍，不是 20 倍
5% (0.05) 20× 串行越少，天花板越高

例子 · 报单引擎 f = 20%：

  • 20% 串行：撮合核心逻辑（单订单簿锁、顺序撮合）— 再多核也要排队过这段。
  • 80% 可并行：行情推送、解码、部分策略计算。
S_max = 1 / 0.2 = 5×

不管你堆 32 核还是 64 核，整体性能最多 ≈ 单核的 5 倍 — 这就是阿姆达尔给的 性能天花板。想再快，得 减 f（拆订单簿、无锁、流水线化串行段），不是继续买机器。

有限核数下的加速（更贴采购决策）：

f S(8 核) S_max
5% ~4.7× 20×
10% ~4.3× 10×
20% ~3.3× 5×

8 核往往 远不到 S_max — 所以先看 S(8) 够不够，再决定加核；若 f=20%，加到 32 核收益极小。

加速比 vs 延迟：10 μs 能降到多少？

加速比 S = 优化后性能 / 原性能，对延迟就是 原延迟 / S — 不是「10 μs 加速 10 倍 → 减到 5 μs」这种相减。

例子 · f = 10%（90% 可并行），加「无限多核」理想情况：

S_max = 1 / 0.1 = 10×
原单线程报单总耗时     T₀ = 10 μs
理论最短（阿姆达尔）   T_min = T₀ / S_max = 10 / 10 = 1 μs
阶段 延迟 含义
单线程基线 10 μs profile 得到的 T₀
阿姆达尔理想（f=10%） 1 μs 串行 1 μs + 并行段摊到 ≈0
USL 落地 ~2–3 μs 锁争用、跨核 cache 同步、NUMA 抖动扣掉理想增益

所以： 阿姆达尔告诉你 最好理论上能到 1 μs；USL + 压测告诉你 实盘可能只到 2–3 μs — 容量规划要按 USL 落地值 留 SLO，不能按 1 μs 买机器。

HFT 工程目标： 尽量把 f 压到 5% 以内 → S_max = 20× 以上，给 USL 扣损耗后仍够 SLO 余量（理想 10 μs→0.5 μs，落地也许 2 μs 仍达标）。

用法： tick→串行风控→send — profile 量 f 与 T₀，算 S(N)、S_max、T_min；砍串行优先于加核。

Python 示例（可直接贴进脚本）

阿姆达尔 — 纯公式，无需第三方包：

def amdahl_speedup(f: float, n: int) -> float:
    """f=串行占比 0~1, n=核数 → 加速比 S(n)"""
    return 1.0 / (f + (1 - f) / n)

def amdahl_latency(T0_us: float, f: float, n: int) -> float:
    return T0_us / amdahl_speedup(f, n)

# f=10%, 8 核
print(amdahl_speedup(0.1, 8))           # ~4.3
print(1/0.1)                            # S_max = 10
print(amdahl_latency(10.0, 0.1, 9999))  # 理想 → ~1 μs

USL — 用压测数据拟合 α、β（scipy 做曲线拟合，非手推 USL 公式）：

import numpy as np
from scipy.optimize import curve_fit

def usl(n, alpha, beta):
    n = np.asarray(n, dtype=float)
    return n / (1 + alpha * (n - 1) + beta * n * (n - 1))

# 压测：核数 vs 相对单核吞吐（示例数据，换成你的 orders/s 或 tick/s）
N = np.array([1, 2, 4, 8, 16, 32])
X = np.array([1.0, 1.8, 3.2, 4.5, 4.8, 4.2])  # 16 核后反降 → USL 典型

(alpha, beta), _ = curve_fit(usl, N, X, p0=[0.01, 0.001], bounds=(0, np.inf))
print(f"α={alpha:.4f}  β={beta:.4f}")
print("N=8 预测:", usl(8, alpha, beta))

排队论 — queueing-tool（M/M/c、M/G/1；见 2.6.4）。

说明： scipy 本体 没有 内置 M/M/1 闭式解模块；常用组合是 阿姆达尔手写 3 行 + USL 用 scipy.optimize.curve_fit + 排队用 queueing-tool。

常见陷阱

  1. 阿姆达尔定律忽略串行部分——HFT 策略有全局锁/共享 order book，串行比比想象的大

答

加速比 = 1 / (s + (1-s)/n)，s = 串行比例，n = 核数——串行部分限制最大加速比

  1. USL 比阿姆达尔多了什么？
答

多了 γ（coherency）项——通信/一致性开销随核数平方增长，导致负扩展性

  1. HFT 策略加核什么时候开始降速？
答

当 γ * n^2 项超过并行收益时——USL 拐点，需要实测确定而非猜

section-2.7.2-容量规划三步法

容量规划 = HFT 系统的「事前体检」 — 不是实盘 P99 炸了再加机器，而是 上线前 从业务目标反推资源与架构。

先模型、后选型 — 别反着来

错误顺序： 先拍脑袋选 16 核、10G 网卡、写线程池 → 实盘发现算力不够、延迟炸锅。

正确顺序： SLO 定目标 → 模型算需要多少 → 反推硬件 + 软件设计 → 压测验证

类型 容量规划的 输出（模型算出来，不是猜的）
硬件 核数 c、网卡 带宽/pps、每核 内存（避 cache/NUMA 瓶颈）
软件 线程模型、队列长度、分片数、限流阈值、绑核策略

内核、带宽、线程模型、队列深度 — 都是同一套规划的产物，不是各干各的。

三步法：从业务需求到落地选型

① 定目标（SLO）     业务要扛多少、多快、tail 多严
       ↓
② 模型算资源        排队论 + 阿姆达尔 + USL → 核数 / 带宽 / 内存 / 限流
       ↓
③ 压测验证          仿真流量跑一遍 → 达标？微调 → 上线后 Grafana 迭代

第一步 · 定目标（业务 SLO）

问什么： 系统 必须 满足什么，才有意义谈买多少机器。

维度 示例（报单引擎）
吞吐 10,000 orders/s sustained；burst 15k/s
延迟 P99 < 10 μs（tick→ACK 或段间）
可用 reject 率 < 0.1%；无排队雪崩
余量 目标 2× tick 或开盘 burst 的 headroom

→ 与 2.4 Workload 先 一致 — 先业务真相，再算资源。

第二步 · 模型算资源需求

模型 输入（来自目标或粗估） 回答 资源输出

示例 · SLO：10k 报单/s，P99 < 10 μs

1. 排队论：单核 μ≈2k/s → 系统需 c≥10k/(0.7×2k)≈8 核（M/M/c，ρ 留 30%）
2. 阿姆达尔：f=8% → S_max≈12×；T₀=12μs → 理想 T_min≈1μs（上限参考）
3. USL：8 核实测等效 ~5× → 按 5× 定 SLO 余量，非按 12× 买期望
4. 网卡：10k 单 × 平均帧长 → ~X Gbps → 10G 口 + pps headroom
5. 内存：订单簿 + 队列深度 × 对象大小 → 每核 32GB 避 NUMA/cache 挤爆（压测 WSS 验证）

→ 软件反推：8 工作线程 / shard、每队列长度上限、token bucket 限 0.7×μ

第三步 · 压测验证与微调

ρ @ 10k/s < 预警线（如 65%） 限流或加核
USL 曲线 8 核在峰值前 减 α（shard）或减 N
网卡 pps / drop 无 drop 升档或减 λ

微调： 模型给 量级与初值；压测改 线程数、队列长、绑核 — 再跑一轮直到达标。

上线后： Grafana 迭代（原「第三步实盘」）— 校正 λ、μ、α、β，旺季前主动扩容/限流。

自动化： 压测脚本一键代入 f、N、α、β、λ、μ → 输出 S(N)、最优 N、ρ knee — 工具节。

2.8.1 量化性能收益

观测法（不干预）：

观测：应用请求 10 ms，其中磁盘 I/O 9 ms
建议：内存缓存，DRAM ~10 μs
收益：10 ms → 1.01 ms = ~9x

实验法（改了再量）：

改前：事务延迟均值 10 ms
改后：事务延迟均值 2 ms
收益：5x

延迟是最佳量化指标 — 可直接跨组件比较（IOPS 不行）。注意只测 同步路径 上的延迟；异步后台 I/O（如刷盘）不算。

2.8.2 平均值

类型 公式 适用场景
算术平均 Mean Σx / n 最常用，但隐藏分布
几何平均 ⁿ√(x₁×…×xₙ) 多层协议栈逐层改进的 乘积效应
调和平均 n / Σ(1/xᵢ) 速率平均：50 MB/s 跑 100MB + 10 MB/s 跑 700MB → 11.1 MB/s

时间平均的陷阱： CPU 从不「在 50%」— 是某区间内利用了 50%。5 分钟均值可能掩盖 秒级 100% 尖刺（Gregg 亲历案例：客户 CPU 饱和导致调度延迟，监控显示 ≤80% 因 5 分钟均值）。

衰减平均 Decayed Average： uptime 的 load average 就是衰减平均 — 近期权重更高，抑制短期波动。详见 Ch6.6.1。

2.8.3 标准差 · 分位数 · 中位数

指标 含义 HFT 用途
σ 标准差 偏离均值的程度 抖动量化；σ 大 = 不稳定
P99/P999 99%/99.9% 请求的上限 SLA 核心
中位数 P50 数据中间值 看 主体 在哪；不受 outlier 影响

2.8.4 变异系数 CoV

CoV = σ / mean — 用单值表达离散程度。

σ=50 单独无意义；σ=50 + mean=200 → CoV=25%，说明有中等波动。

z 值： 某值偏离均值多少个 σ。

2.8.5 多峰分布

有人淹死在平均深度六英寸的河里。 — W. I. E. Gates

系统性能常双峰： cache hit 快峰 + cache miss 慢峰；GC 前快峰 + GC 时慢峰。

场景 快峰 慢峰
Cache L1 hit ~ns miss → μs
GC 语言 ~几十 μs GC → ms
快慢路径 5 μs 慢查 500 μs

做法： histogram 看几峰；热力图看周期；热路径 C++/Rust + 对象池 消第二峰。

mean 在双峰分布上 seriously misleading — 可能恰好在两峰之间的谷底，不代表任何真实状态。

2.8.6 异常值

磁盘 I/O 多数 0-10 ms，偶发 >1000 ms — 这种 outlier mean 几乎不动，但对 HFT 致命。

  • mean 被 outlier 微移；median 几乎不动
  • σ 和 P99 有机会发现 outlier，但取决于频率
  • 唯一可靠方法： 看完整分布（histogram）+ 最大值告警

HFT： P999 不是「噪声」— 是 P&L。不删 outlier；P999/Max 告警 + 2.5 trace。

实盘：tail 不是小数点 — 交易所硬规则 + 抢单经济学

国内期货等：会员网关 → 撮合 有 超时丢弃 硬限（常见 ~500 ms 量级）。专线 固定占 几十 μs～1 ms。

总延迟 ≈ 专线(固定) + 引擎(P99/P999 盯这里) + 交易所侧
段 量级 说明
专线 ~50 μs–1 ms 减不掉
引擎 mean 50 μs 「看起来好」
引擎 P999 2 ms mean 看不见 的 1%
交易所硬限 ~500 ms 超限 → 丢弃
  1. 硬上限 — tail 叠加（雪崩、GC、重传）吃 安全余量
  2. 抢单（μs～ms） — P999 2 ms + 专线 1 ms → 错过最优档，滑点吃光利润
量级感 含义
每 1 ms 单日收益 可掉 10%+
1% 长尾 盈利 → 亏损
mean 50 μs + P99 2 ms 1% 坏单拖垮全天 P&L

统计指标优先级

优先级 指标 用途
P0 P99、P999、Max SLA、告警
P1 σ、IQR 抖动；双峰时配合 histogram
P2 Mean 仅 2.6 排队论 粗估
P3 Outlier 列表 单笔 trace

2.10.1 折线图 Line Chart

最基础的可视化 — X 轴时间，适合 趋势 和 尖峰 识别。

2.10.2 散点图 Scatter Plot

每个事件画一个点（X=时间，Y=延迟）— 看到全部数据。

优势： 暴露 outlier — 折线图看不到的 >50ms 尖刺在散点图上一目了然。

劣势： 数据量大时点重叠（"wall of paint"）；采集/存储开销大（每个 I/O 的 x,y 坐标）。

HFT： λ vs P99 散点 → 限流 / ρ 预警。工具：Grafana XY / Python Seaborn。

Gregg 示例：数据中心 300+ 台服务器、5312 CPU 的利用率表面图。每台 16 CPU 为行、60 秒为列、高度=利用率。棋盘格布局中可看出哪些服务器持续 100%。

可扩展到 6 维： hue（第 4 维）+ saturation（第 5 维）+ pattern（第 6 维）。

常见陷阱

  1. 用折线图看延迟分布——折线只显示聚合值，看不到双峰和尾部，必须用 histogram/热力图
  2. 散点图数据量太大——百万级事件点重叠成"墙"，应改用热力图（列量化）
  3. 忽视可视化工具自身开销——长时间 perf record 会产生大量数据，影响被测系统
