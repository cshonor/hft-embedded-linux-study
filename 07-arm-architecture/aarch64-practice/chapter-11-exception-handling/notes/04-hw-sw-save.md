# §11.4 硬件保存 + 软件保存

> **来源：** [Ch11 完整概述](section-0-本章完整概述.md) · [章导读](../README.md)

## 本节讲什么

异常发生时硬件自动保存 ELR（PC）和 SPSR（PSTATE），但 X0-X30 通用寄存器必须软件手动保存。本节展示完整的保存/恢复代码模式，以及 ERET 返回指令。

## 核心要点

### 硬件自动保存

| 保存到 | 原值 | 说明 |
|--------|------|------|
| `ELR_ELx` | PC | 异常发生时的指令地址（同步=触发指令；异步=下一条指令） |
| `SPSR_ELx` | PSTATE | 异常发生时的处理器状态（NZCV、DAIF、EL 等） |
| SP 切换 | — | 切到目标 EL 的 SP（SP_ELx） |

### 软件必须保存

**X0-X30 通用寄存器硬件不自动保存！** 必须在异常处理入口手动压栈。

```asm
irq_handler:
    sub sp, sp, #272          // 保存 31 个寄存器（31×8=248）+ 对齐
    stp x0,  x1,  [sp, #0]
    stp x2,  x3,  [sp, #16]
    stp x4,  x5,  [sp, #32]
    // ... 保存 x0-x29
    stp x29, x30, [sp, #232]

    // 处理中断
    bl  do_irq

    // 恢复
    ldp x0,  x1,  [sp, #0]
    // ... 恢复 x0-x29
    ldp x29, x30, [sp, #232]
    add sp, sp, #272

    eret                     // 返回：ELR→PC, SPSR→PSTATE
```

### 保存空间计算

| 项目 | 大小 |
|------|------|
| X0-X30 = 31 个寄存器 | 31 × 8 = 248 字节 |
| 对齐填充 | 24 字节 |
| 总计 | 272 字节 |

> **ERET** 是异常返回的核心：原子恢复 PC 和 PSTATE，切回原 EL。

## HFT 关联

保存/恢复 31 个寄存器需要约 16 条 STP + 16 条 LDP = 32 条访存指令，在 A76 上约 30-50ns。这是中断延迟的下限——即使 ISR 什么都不做，进出异常的 overhead 也无法消除。HFT 系统如果用中断驱动，这段保存/恢复代码是性能关键路径，应确保栈在 L1 cache 中。某些 HFT 方案用轮询（polling）替代中断，就是为了避免这段开销。

## 自测题

1. **异常发生时硬件自动保存了哪些寄存器？哪些需要软件保存？**

<details>
<summary>答案</summary>

硬件自动保存：**ELR_ELx**（PC 值）和 **SPSR_ELx**（PSTATE 值）。软件必须保存：**X0-X30**（31 个通用寄存器），因为硬件不自动保存通用寄存器，ISR 可能覆盖它们。
</details>

2. **为什么保存空间是 272 字节而不是 248 字节（31×8）？**

<details>
<summary>答案</summary>

31 个寄存器 × 8 字节 = 248 字节。额外 24 字节用于**栈对齐**（ARM64 AAPCS 要求 SP 16 字节对齐），以及可能保存的 FP/LR 等额外状态。272 = 248 + 24，保证 SP 对齐。
</details>

3. **ERET 之前如果忘记恢复 SP 会怎样？**

<details>
<summary>答案</summary>

ERET 恢复 PC 和 PSTATE，但**不恢复 SP**。如果处理中改了 SP（如 sub sp 分配栈空间）但忘记 add 回来，ERET 后 SP 指向错误地址，后续压栈会覆盖内存，导致栈损坏或崩溃。
</details>
