## 7.4 坑点清单

1. **一个接口只能挂一个 XDP 程序**——再挂报 `Device or resource busy`；多逻辑要用程序内部分发（第 2 章 PROG_ARRAY 尾调用）。注意多协议共存（freplace/mprog 框架）是新内核的演进方向，成书时（2022）通用路径仍是"单程序+内部分发"
2. kprobe 挂到被内联的函数 = **静默没有入口点**——符号表里有名字（static inline 也有符号信息），但运行时没有独立函数体可断点；先 `bpftrace -l` 验证路径（[7.1 真机](./7.1_程序类型全景.md)：猜符号名必错，`do_sys_open` 0 触发、openat 全走 `do_sys_openat2`）
3. kprobe 声明参数时只能省略**尾部**参数，不能跳过中间的——参数按内存顺序（寄存器序）排列，跳中间=后面全错位
4. tracepoint 前 4 个公共字段（common_type/flags/preempt_count/pid）访问即验证失败——ctx 访问检查按 format 文件的用户字段放行
5. uprobe 的库路径是架构全路径（`/usr/lib/aarch64-linux-gnu/libssl.so.3`），跨架构部署要分别定义；容器内路径 ≠ 宿主机路径（探针路径按容器内挂载命名空间解析）
6. Go < 1.17 二进制参数在栈上，pt_regs 取参方案失效——Go 1.17 起才改用寄存器传参；老 Go 二进制要靠 USDT 或 Frida 类方案
7. kfunc 无稳定性承诺，生产分发慎用（helper 才有 UAPI 保证）——kfunc 是内核内部函数直接暴露给 BPF，内核重构说变就变
8. （真机补充，lab06）**内核重构会改函数语义**：6.18 的 `do_sys_openat2` PARM2 直接是 `const char __user *`（旧资料说是 `struct filename *`）——kprobe 签名以真机实测为准，书上/网上的签名都可能是旧版本

## 7.5 HFT 关联

### 1. 挂点选型决策树（行情链路观测）

```
要观测什么？
├─ 内核函数路径（耗时/返回原因） ──> fentry/fexit（5.5+/ARM 6.0+）
│     开销最低 + fexit 全参+返回值一步到位，免 kprobe/kretprobe 两次挂载、跨事件配对
├─ syscall 级审计/资产盘点 ──> tp_btf（稳定接口 + 免手写结构）
│     签名来自 vmlinux.h 的 trace_event_raw_*，免版本漂移
├─ 热点内核函数计时（老内核） ──> kprobe + kretprobe 出入对
│     跨事件配对用 @start[tid] map，延迟分布进 hist map
└─ 用户态二进制关键函数 ──> uprobe/uretprobe（注意静态链接与 Go 调用约定）
```

**fexit 拿全参+返回值**对测量"某内核路径耗时与返回原因"一步到位——kretprobe 只有 ret、拿不到入参，要重建"哪个 fd 的哪次 read 慢了"得跨两个探针配对；fexit 一个探针全拿到，**配对逻辑消失 = 丢样本的风险消失**（跨事件配对在事件洪峰下会丢半边）。

### 2. XDP 单程序限制 = 交易机网口的架构约束

所有入口逻辑（黑名单、速率限制、重定向到旁路采集）必须在一个 XDP 程序内组织好——用 PROG_ARRAY 尾调用做内部分发：主程序查表决定调哪个子程序，**策略做成数据**（改黑名单改 map，不改程序不重新加载）。这是"热更新"在 eBPF 侧的标准形态。

### 3. uprobe 钩交易网关二进制

钩 SSL/加密库的思路同样适用于钩交易网关的关键函数（下单路径计时）——**不用改一行被测代码**是最大优点（对不能重编译的第三方网关是唯一选择）。三个前提：函数有符号（非 stripped）、动态链接（或接受静态地址硬编码）、C 调用约定（Go 老版本出局）。开销 ~1-2µs/次——纳秒级路径不可用，微秒级路径可用。

### 4. LSM 返回码可阻断 → 内核级行为白名单

LSM 程序返回非零直接让内核拒绝操作（区别于追踪类的返回码被忽略）——可做交易进程的**内核级行为白名单**（如禁止非交易进程 connect 交易所网段），见[第 9 章](../../chapter-09-security/notes/9.1_安全模型与syscall方案.md)。这比 iptables 强在**带进程上下文**（哪个 PID/cgroup 干的），比 seccomp 强在**动态可换**。

### 5. 真机教训的泛化：挂点验证先于程序开发

lab06 的教训（`do_sys_open` 零触发、`do_sys_openat2` 签名变了）泛化成纪律：**写程序前先用 bpftrace 一行命令验证挂点真的在目标路径上**——`bpftrace -l "*openat*"` 列挂点、`bpftrace -e 'kprobe:xxx { @[comm]=count(); }'` 数触发。挂错点的 eBPF 程序不报错、只是静默零数据，是"工具坏了还是路径错了"排查里最费时间的一类。

## 7.6 自测题

1. 程序类型决定了哪四件事？
2. `BPF_KPROBE_SYSCALL` 与 `BPF_KPROBE` 与 `BPF_PROG` 各用于什么场景？
3. fexit 相比 kretprobe 的独有优势是什么？依赖哪个内核机制、哪个版本引入（x86/ARM 各是）？
4. tracepoint 的上下文结构怎么写？tp / raw_tp / tp_btf 三者的性能与可移植性权衡？
5. SOCKET_FILTER 过滤的是什么数据？为什么说它"名不副实"？
6. LSM 程序的返回码语义与追踪类有何不同？
7. 为什么一个接口挂第二个 XDP 程序会失败？多逻辑怎么组织？
8. helper 函数和 kfunc 在兼容性承诺上的区别？

<details>
<summary>参考答案</summary>

**1.** ①可附加的事件；②上下文参数的结构（ctx 指向什么）；③可用的 helper 函数集合（验证器按此检查）；④返回码的含义（XDP：放行/丢包/重定向；追踪类：被忽略；LSM：非零=拒绝操作）。

**2.** `BPF_KPROBE_SYSCALL`：挂 **syscall 入口**（ksyscall/），参数按 syscall 签名取（稳定接口，跨内核稳）；`BPF_KPROBE`：挂**任意内核函数**（kprobe/），参数按内核函数签名取（含 struct 指针，随内核版本变）；`BPF_PROG`：fentry/fexit/tp_btf 等宏（`BPF_PROG(name, 类型化参数...)`，配合 vmlinux.h 的类型直接声明参数）。

**3.** fexit **同时拿到入参和返回值**（kretprobe 只有 ret）。依赖 **BPF trampoline** 机制（函数出入口动态生成跳板代码）。x86 5.5 引入，ARM64 要 6.0。

**4.** tp：手写结构体照抄 format 文件（offset/size 对齐），慢但兼容性最好；raw_tp：跳过参数映射直接拿原始 `__u64` 数组，最快但自己转型（架构相关）；tp_btf：BTF 自动提供 `trace_event_raw_*` 匹配结构（vmlinux.h 里），免手写、免漂移——**首选**（需要目标内核有 BTF）。

**5.** 过滤的是发给 tcpdump 等观察工具的**数据副本**（packet socket 路径），不是发给应用的数据——"SOCKET_FILTER"听起来像过滤应用流量，实际是抓包过滤；应用数据不受它影响。

**6.** LSM 返回非零 = **内核拒绝该操作**（阻断生效，安全语义）；追踪类返回码被内核**忽略**（纯观察）。

**7.** XDP 挂载点是 per-interface 的单槽位（驱动层只有一个 XDP 程序入口），第二个程序无处可放 → EBUSY。多逻辑：程序内部分发——PROG_ARRAY 尾调用（策略查表决定调谁）或 if/else 单体程序。

**8.** helper 是 **UAPI 稳定接口**：一经定义不再变化，跨内核版本可依赖；kfunc 是内核内部函数直接注册给 BPF，**无兼容性保证**（内核重构即变），生产分发要自行承担版本适配。

</details>
