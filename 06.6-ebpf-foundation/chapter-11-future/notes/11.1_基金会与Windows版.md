## 11.1 eBPF 基金会（2021）

- 由 Google、Isovalent、Meta、Microsoft、Netflix 在 Linux 基金会下创立
- 定位：**中立机构**持有资金与知识产权，让商业公司能合作；**不改变**内核社区的开发方式——eBPF 核心仍在内核邮件列表上按内核节奏演进，基金会管的是生态外围（会议、商标、跨厂商协作的法律壳）
- 治理：BPF 指导委员会，全部由技术专家组成（内核 BPF 维护者 + 核心项目代表：Alexei Starovoitov、Andrii Nakryiko、Daniel Borkmann 等维护 BPF 子树）——**技术治理而非商业投票**，避免基金会变成厂商博弈场
- 分工：基金会管**技术平台与开发工具生态**（libbpf、bpftool、规范文档）；上层应用项目归其他基金会（Cilium/Pixie/Falco → CNCF）——平台层与应用层分开托管，类比 Linux 内核（kernel.org）与云原生应用（CNCF）的关系
- 标准化动因：微软要在 Windows 上实现 eBPF，需要跨 OS 的 eBPF 标准——**单一厂商实现不可能绑架一个由多家共建的规范**，中立的规范持有者是前提

**为什么"成立基金会"值得书一章**：eBPF 从"内核子系统"变成"跨平台技术平台"的组织学标志——生态位跃迁需要法律/治理基础设施先行。观察一个技术是否长青，看它的治理结构比看它的 feature list 更准。

## 11.2 eBPF for Windows

- 成书时（2022 底）已有可运行演示：Cilium L4 负载均衡、eBPF 连接跟踪跑在 Windows 上
- 为什么可行：eBPF 本质是**内核中的虚拟机执行字节码**——VM 也可以在 Windows 里实现；网络包结构与协议栈处理在所有 OS 上是相通的（收包/过滤/转发的问题域不依赖 OS）

### 架构与许可证约束（本节最有意思的工程决策）

| 组件 | 选择 | 原因 |
|---|---|---|
| 工具链 | 复用 libbpf + Clang 的 eBPF 字节码支持 | 宽松许可，生态现成 |
| 验证器 | **PREVAIL**（非 Linux 内核验证器） | Linux 内核验证器是 **GPL**，Windows 闭源不能抄 |
| JIT | **uBPF** JIT | 宽松许可 |
| 验证/JIT 位置 | **用户态 Secure 环境**（非内核） | 内核里的 uBPF 解释器仅用于 debug 构建 |

三层工程决策值得展开：

1. **许可证驱动架构**：GPL 的 Linux 验证器不可复用 → 换 PREVAIL（微软研究院的抽象解释验证器，学术出身）——**许可约束直接改变了组件选型**，这是闭源平台使用开源生态的典型代价。连带后果：PREVAIL 与 Linux 验证器的行为**不完全一致**（验证严格度、支持的指令集有差异），同一程序可能一边过一边不过
2. **验证/JIT 放用户态**：Linux 是加载前内核内验证；Windows 把这层挪到用户态"Secure 环境"（隔离进程）——设计取向是**宁可慢也要把风险关进沙箱**。代价：加载路径多一次进程切换
3. **字节码生态直接复用**：编译器侧（Clang 的 BPF target）、ELF 格式、map 概念全部照搬——**"eBPF 是平台"的论据**（[11.2](./11.2_演进方向与平台观.md)）：字节码格式是跨 OS 的公共接口

- 别指望所有 Linux eBPF 程序都能跑在 Windows 上——但这与跨内核版本的 CO-RE 挑战本质相同：**数据结构差异要程序员优雅处理**（CO-RE 重定位在 Windows 侧同样要解决 NT 内核结构与 Linux 结构的映射）
