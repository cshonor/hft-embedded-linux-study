## 6.5 坑点清单

1. **验证器看的是字节码**：源码改了没复现预期报错，先想编译器是不是把代码优化没了（-O2 下不可达分支、常量折叠都会改写指令序列）
2. `unknown func` 先查**程序类型**是否支持该 helper，别怀疑内核版本——helper 可用性由 `get_func_proto` 按程序类型查表（[7.1](../../chapter-07-program-attachment-types/notes/7.1_程序类型全景.md)：程序类型决定 helper 集合），`bpftool feature` 一查便知
3. 循环上界来自全局变量/map 值 = 验证器无法证明有界 = 拒绝；改成常量或用 `bpf_loop()`。注意坑中有坑：**全局变量也是 map**（[3.3](../../chapter-03-anatomy-of-ebpf-program/notes/3.3_全局变量与BPFtoBPF调用.md)）——`for (i = 0; i < counter; i++)` 里 counter 是 .bss map 的值，验证器按"任意值"处理
4. `if (p != 0)` 检查必须在**解引用之前**；`bpf_map_lookup_elem` 返回值不判空直接用是最常见新手错误——验证器按指令序做值域推理，检查和解引用的**相对顺序**就是它推理的依据
5. 无 return 的函数：碰巧调过 helper 也能过验证，但返回值是 helper 的残留——语义错误验证器管不了（验证器保证"不崩溃"，不保证"干了你想要的事"）
6. 非 root：4096 指令老限制仍在（`BPF_MAXINSNS`，bpf_common.h）——同一程序 root 能过、普通用户被拒时先想这条
7. 报错里的 "map value" 未必是你建的 map——全局变量也是 map（.bss/.data/.rodata）；日志里 `map_value` + off 偏移可能指的就是你的全局变量

## 6.6 HFT 关联

### 1. 验证器 = 交易系统里"确定性执行"的守门员

程序绝无死循环（有界性被数学证明）、绝无越界读写（值域推理）、绝无野指针崩溃——这类保证对交易机近乎"停机保证"，是 eBPF 敢于上生产内核的理由。**对比内核模块**：一个 BUG 的 kmod 直接 panic 整机（交易中断）；一个 BUG 的 eBPF 程序最多加载失败——出错半径从"整机"缩到"一个 fd"。

### 2. 验证开销在加载时一次性支付，运行时零开销

与"审计在事前、执行在纳秒级"的交易系统设计哲学同构。**性能敏感路径不付验证税**——运行时执行的就是 JIT 后的机器码，与手工写的内核代码同级。这也是 eBPF 探针敢挂热路径的底气（对比：某些动态插桩方案每次触发都有检查成本）。

### 3. 验证器日志是线上探针加载失败的唯一调试入口

`R1 type=fp expected=map_ptr` 这类报错要能秒读：**R1 现在是栈指针（fp），但这条指令需要 map 指针**——顺着指令号找源码行（`-g` 编译才有），再看寄存器状态快照推断是哪次赋值引入的错误类型。值班排查时这套阅读能力就是 MTTR 的差距。

### 4. 批量统计优先回调式，不写展开式循环

在 eBPF 里做批量统计（如遍历 map 聚合延迟分布）优先用 `bpf_for_each_map_elem`/`bpf_loop` 回调式——**验证器只需验证回调体一次**，加载快、指令数省；展开式循环每个迭代都是新路径，状态空间爆炸（processed insns 暴涨）。这与 HFT 的"把复杂度从热路径挪走"是同一纪律：验证成本也是成本，也该省。

### 5. 剪枝机制的性能直觉

验证时间 = 状态数 × 每状态成本——`peak_states` 高的程序加载慢（秒级）。**写"对验证器友好"的程序**：早 return（先过滤再干活）、少分支、map lookup 后立即判空——这些习惯既让验证快，也常让运行时更快（早 return 少执行指令）。

## 6.7 自测题

1. 验证器在分支处如何处理？剪枝在什么条件下可以跳过一段路径的验证？"子集状态"是什么意思？
2. 为什么示例程序开头总是 `r6 = r1`？R6-R9 有什么特殊性质？
3. `R1 type=fp expected=map_ptr` 是怎么被验证器发现的？
4. 一个 12 字节数组，`if (c <= sizeof(arr))` 为什么错？验证器日志里哪一行给出了关键线索？
5. 5.3 前后循环处理有何不同？5.17 的 `bpf_loop()` 相比普通 for 循环的优势在哪？
6. 为什么注释掉 return 后调一次 `bpf_printk()` 就能通过验证？这暴露了什么风险？
7. 100 万指令上限是按什么计数的？为什么实际程序必须远小于 100 万条？
8. tracepoint 上下文的公共字段为什么不能访问？

<details>
<summary>参考答案</summary>

**1.** 分支处把当前全部寄存器状态**压栈**，先验证一条路径到 return（或达上限），弹栈验证另一条。剪枝：验证器在固定间隔（每 10 条指令）存状态快照，若后续以相同或**子集**状态到达同一指令，跳过剩余验证——"子集状态"指新状态的类型一致且值域是旧状态的子集（更收紧），后续推理结论必然相同，重验无意义。

**2.** R6-R9 是 callee-saved：helper 调用**不会破坏**它们（R1-R5 传参、R0 收返回值都会被调用覆盖）。程序入口 ctx 在 R1，开头 `r6 = r1` 把 ctx 备份到 R6，之后随便调 helper 都不丢——这是[6.1](../../chapter-06-verifier/notes/6.1_验证机制与日志.md) 寄存器约定表的核心行。

**3.** 验证器按序步进维护每个寄存器的**类型**（bpf_reg_type）；指令要求 R1 是 map 指针（如把 R1 传给需要 map_ptr 的 helper）时查类型不匹配——"fp"表示之前的指令把栈指针赋给了 R1（栈只能经 `r10 - off` 访问，不是 map 对象）。日志里 R1_w=fp0 的快照就是证据。

**4.** `c <= 12` 成立时 c 可以等于 12，而有效下标最大 11——`arr[c]` 在 c=12 时越界一字节。日志里 umax_value=12（而非 11）的那行寄存器状态给出关键线索：验证器推到"c 最大 12"时发现访问 `arr[c]` 的 off=12 超出 map_value/栈的 12 字节边界。修法：`c < sizeof(arr)`。

**5.** 5.3 前：循环直接被拒绝（验证器无法证明回边终止）。5.3 起：**有界循环**可验证（循环上界必须是验证器可见的常量/可推值域）。`bpf_loop()`（5.17）：循环体是回调函数，验证器**只验证回调一次**（不管迭代多少次），支持最多百万次迭代且上界可以来自变量——绕开了展开式验证的状态爆炸。

**6.** 验证器要求"所有路径必须初始化 R0 到 return"——`bpf_printk()` 的返回值恰好落在 R0（helper 返回值寄存器），充当了"已初始化的返回值"。风险：返回值是 printk 的字符数（无意语义），程序返回码完全是垃圾——**验证器保证类型安全，不保证语义正确**；XDP 程序里这种垃圾返回码可能恰好是 0=XDP_ABORTED（丢所有包）。

**7.** 按**已验证指令**计（processed insns）——有分支时同一条指令会被多条路径重复处理，processed 计数乘性地放大。所以 100 万上限对应的实际程序长度要小一两个数量级（分支密集的程序几千条指令就可能 processed 上百万）。

**8.** tracepoint 上下文的前 4 个公共字段（common_type/flags/preempt_count/pid）是 tracing 基础设施的元数据，bpf context 访问检查（`bpf_ctx_access`）按 format 文件的用户字段布局放行，公共字段不在放行范围——访问即 `invalid bpf_context access`。

</details>
