## 1.1 起源：1993 年的 BSD Packet Filter 论文

> 本节讲什么：eBPF 的"前身" cBPF 为什么诞生、它解决的性能问题是什么、以及为什么说 BPF 从第一天起就不只是"抓包工具"。

## 1. 问题背景：内核抓包为什么慢

1990 年代初，抓包工具（如 tcpdump 的前身）是这样工作的：网卡每收到一个包，**内核把整个包完整拷贝一份**给用户态的过滤进程，过滤进程再决定要不要。

问题：过滤逻辑跑在用户态，但过滤所需的数据在内核里——**每个包都要白白经历一次"内核→用户态"拷贝 + 上下文切换**，哪怕最后 99% 的包都被丢弃。当你只想抓 SSH 流量而网卡灌进来全机房流量时，这个开销是灾难性的。

**两次拷贝问题图示：**

```
   网卡 ──包──▶ 内核协议栈 ──完整包拷贝──▶ 用户态过滤进程
                                        （在这里才判断"要不要"）
                    ▲
                    └── 丢弃的包也付了全额拷贝成本
```

## 2. 论文的答案：把过滤程序搬进内核

McCanne & Van Jacobson（劳伦斯伯克利实验室，1993）提出：与其把数据搬到过滤器，不如把**过滤器编译成字节码，塞进内核执行**。内核里跑一个小"伪机器"（pseudo-machine）——一套 32 位寄存器虚拟机，解释执行（当时还没有 JIT）过滤器指令。

```
   网卡 ──包──▶ [内核: BPF 伪机器执行过滤器]
                      │
              包在此就地判决 ──只有"要"的包──▶ 拷贝给用户态
                      └──"不要"的包零拷贝成本丢弃
```

这就是 BPF 名字的由来：**BSD Packet Filter**。性能上还赢了一个隐性优势：BPF 论文的设计（两个寄存器 + 无间接寻址）比同时代对手（CSPF）的树遍历结构更容易映射成高效机器码，实测快 20 倍左右。

## 3. 论文里的示例程序

BPF 过滤器是一门"类汇编"指令集，比如"只要 IP 包"：

```
ldh     [12]                       # 从包偏移 12 处加载 2 字节（以太网帧的 ethertype 字段）
jeq     #ETHERTYPE_IP, L1, L2      # 是 IP 包则跳 L1，否则跳 L2
L1:     ret     #TRUE              # 非零返回值 = 接收该包（上送用户态）
L2:     ret     #0                 # 0 = 丢弃
```

逐行解读（你写过 ARM 汇编，这个结构应该很眼熟）：

| 指令 | 做什么 | 对应你熟悉的 ARM 概念 |
|---|---|---|
| `ldh [12]` | 从内存地址加载数据到寄存器（load half-word，2 字节） | `ldrh r0, [r1, #12]` |
| `jeq #imm, L1, L2` | 比较相等则跳 L1，否则跳 L2 | `cmp` + `b.eq` / `b.ne` |
| `ret #N` | 返回，N 就是判决结果 | `mov r0, #N` + `bx lr` |

两个细节值得注意：

- **偏移 12**：以太网帧头 = 6 字节目的 MAC + 6 字节源 MAC，第 13 字节起是 2 字节 ethertype——**过滤器和数据结构布局强耦合**。这个主题 30 年后换个面目再次出现：CO-RE 就是为了解决"内核数据结构布局变了，我的程序怎么办"（第 5 章）
- 今天 `tcpdump -d` 仍能看到这套指令：`tcpdump -d 'ip'` 输出的就是 cBPF 字节码——你没有必要手写它，libpcap 替你把过滤表达式编译出来

## 4. 深远意义

**从第一天起，BPF 的核心思想就是"作者写自定义程序在内核里执行"**——"包过滤"只是它的第一个应用场景。指令集 + 内核执行环境这两个要素 1993 年就齐了，后面 30 年的演进（64 位重写、maps、验证器、更多挂钩点）只是给这台机器不断"加装备"。理解了这一点，后面所有历史都顺理成章。

## 1.2 演进时间线（记住这几个节点）

> 本节讲什么：从 1993 到 2020 的关键节点。不用背年份，要背的是**每个节点给 BPF 加了什么新能力**——能力叠加的顺序本身就是理解 eBPF 的钥匙。

## 1. 完整时间线

| 年份 | 内核 | 事件 | 加了什么能力 |
|------|------|------|------|
| 1993 | — | BPF 论文（伪机器 + 指令集） | 内核里跑自定义字节码（仅包过滤场景） |
| 1997 | 2.1.75 | BPF 进入 Linux，用于 tcpdump 高效抓包 | Linux 获得内核态包过滤 |
| 2012 | 3.5 | **seccomp-bpf**：BPF 程序决定是否允许用户态系统调用 | **BPF 第一次跳出"包过滤"**——判决对象从"包"变成"syscall" |
| 2014 | 3.18 | **eBPF**：指令集为 64 位重写、引入 maps、`bpf()` 系统调用、helper 函数、**验证器**。官方生日 2014-09-26（验证器+bpf syscall+maps 补丁集被接受） | 现代形态确立（下表展开） |
| 2015 | — | eBPF 可挂 **kprobes**，追踪革命起点；网络栈开始加 hook | 观测任何内核函数入口/返回 |
| 2016 | — | eBPF 工具进生产（Netflix/Brendan Gregg "superpowers"）；**Cilium** 发布（容器环境整条 datapath 换 eBPF） | 工业界背书 |
| 2017 | — | Facebook 开源 **Katran**（L4 负载均衡）；此后 facebook.com 每个包都过 eBPF/XDP | 超大规模生产验证 |
| 2018 | — | eBPF 成为内核独立子系统（维护者 Borkmann/Starovoitov，后加 Nakryiko）；**BTF** 引入（可移植性） | 跨内核版本可移植的地基 |
| 2020 | — | **LSM BPF**：第三大用例（安全）确立 | 安全策略可编程 |

## 2. 2014 的 eBPF 改造：五大件分别解决什么

2014 那次重写是"从量变到质变"，五件套缺一不可：

| 新增 | 解决的问题 | 没有它会怎样 |
|---|---|---|
| 64 位指令集 + 11 个寄存器 | 32 位伪机器算不了 64 位指针/时间戳 | 无法处理现代内核数据结构（指针全是 64 位） |
| maps（内核键值存储） | 程序没有地方存状态、没法和用户态交换数据 | 只能 trace_printk 打印字符串，做不了任何"工具" |
| `bpf()` 系统调用 | 提供统一的加载/操作界面 | 用户态没有正规入口管理 BPF 对象 |
| helper 函数白名单 | 让程序有限地访问内核功能（读内存、拿 pid…） | 要么完全盲区、要么直接放开（等于内核模块） |
| **验证器** | 加载前证明程序安全（不崩、不死循环、不越界） | 内核不敢让任意人跑任意代码——这是 eBPF 和 LKM 的分水岭 |

**记忆口诀**：寄存器变宽（能算）、maps（能存）、syscall（能加载）、helper（能访问）、verifier（敢让你跑）。

## 3. 三大用例的形成

时间线读到最后，三条主线浮出水面：

```
        观测追踪 (tracing)          网络 (networking)         安全 (security)
  2014 ─ bpf syscall/verifier     2015 ─ 网络栈 hook        2012 ─ seccomp-bpf
  2015 ─ kprobes                  2017 ─ XDP/Katran         2020 ─ LSM BPF
  2016 ─ Gregg 工具集              (facebook 全量流量)       (策略可编程)
```

本书主线是第一条（观测），第 8 章讲网络，第 9 章讲安全。

## 4. 规模限制的演进

指令数上限从 4096 → 100 万条已验证指令（5.2 起）；尾调用（第 2 章）和 BPF-to-BPF 调用让单程序限制实际失效——组合起来理论上可以写任意复杂的逻辑。

## 1.3 eBPF 与 BPF 的称呼

> 本节讲什么：一个常见的困惑——资料里一会儿写 BPF 一会儿写 eBPF，是不是两个东西？结论先行：**现代语境下是同一个东西**，但用词场合有惯例。

## 1. 两个词的来历

- **BPF**：1993 年的原名（BSD Packet Filter），32 位"伪机器"时代的叫法。今天为了区分，常称 **classic BPF（cBPF）**
- **eBPF**：2014 年 64 位重写后的叫法，e = extended。内核之外的社区（ebpf.io、eBPF 基金会、O'Reilly 书名）用它强调"不只是包过滤了"

## 2. 现状：谁用哪个词

| 场合 | 用词 | 例子 |
|---|---|---|
| 内核源码、内核邮件列表 | 统一 **BPF** | `bpf()` 系统调用、`bpf_get_current_pid_tgid()` 等 helper、`BPF_PROG_TYPE_*` 程序类型——**内核里根本没有 "eBPF" 这个词** |
| 工具链（libbpf/bpftool/clang） | 统一 **BPF** | `clang -target bpf`、`bpftool prog load` |
| 内核外社区、营销、书名 | 流行 **eBPF** | ebpf.io、eBPF Summit、本书《Learning eBPF》 |
| bpftrace 等高层工具 | 混用 | 无所谓 |

## 3. 为什么内核社区坚持不加 "e"

内核维护者的立场：cBPF 在内核里已经被**完全翻译成 eBPF 再执行**（cBPF 程序加载时先被转换），也就是说内核里只有一种 BPF——即 2014 年后的那套。旧名没有独立存在的意义，所以"extended"前缀多余。

**实用结论**：
- 读内核文档/写 C 代码：心里按 BPF 理解，别找 `ebpf_xxx` 符号（不存在）
- 读博客/书：见到 eBPF 直接当 BPF 即可
- 写搜索关键词：两个都试（如 `bpf ring buffer` / `ebpf ring buffer`）
