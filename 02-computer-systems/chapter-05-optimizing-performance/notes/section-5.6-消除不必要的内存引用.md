## 5.6 消除不必要的内存引用

> **Ch5 §5.6** · [章导读](../README.md) · 上节 [§5.5 ←](./section-5.5-减少过程调用.md) · 下节 [§5.7 →](./section-5.7-现代处理器抽象模型.md)

### 问题：热循环里反复读写内存

```c
// 慢：每次迭代都读 *dest、写 *dest
for (i = 0; i < len; i++) {
    *dest = *dest OP data[i];
}
```

每轮循环：①从内存读 `*dest` → ②ALU 运算 → ③写回 `*dest`。`*dest` 在循环中是**累加器**，完全可以用寄存器保存。

### 优化：用局部变量（寄存器）累加

```c
// 快：寄存器累加，循环结束后才写一次
data_t acc = IDENT;
for (i = 0; i < len; i++) {
    acc = acc OP data[i];
}
*dest = acc;
```

| | 慢版 | 快版 |
|--|------|------|
| 每轮内存读 | 1 次（`*dest`） | **0 次** |
| 每轮内存写 | 1 次（`*dest`） | **0 次** |
| 累加器位置 | 内存 | **寄存器** |
| CPE 改善 | — | 显著降低 |

### 为什么编译器不自动做？

编译器**理论上**可以做这个优化（寄存器分配），但有两个障碍：

1. **指针别名** — 如果 `dest` 和 `data` 指向同一地址（aliasing），改写顺序会影响结果。编译器不敢假设它们不重叠。
2. **需要 `restrict`** — 加 `restrict` 关键字承诺 `dest` 和 `data` 不重叠，编译器才敢把 `*dest` 提升到寄存器。

```c
void combine(vec_ptr v, data_t *restrict dest) { ... }
```

### HFT 实践

- **热循环累加器一律用局部变量** — 不依赖编译器，手动保证寄存器累加
- **`restrict` 明确 buffer 不重叠** — 帮编译器放开手脚
- **结构体字段避免热循环里反复解引用** — `p->field` 每次是指针间接寻址，提取到局部变量

---

### 常见陷阱

1. **以为编译器会自动消除内存引用** — 如果有指针别名（`dest` 和 `data` 可能指向同一地址），编译器**不敢**把 `*dest` 提升到寄存器。必须加 `restrict` 或手动用局部变量。
2. **热循环里反复解引用结构体指针** — `p->price` 每次都是间接寻址（先读 `p` 再读 `price` 偏移），不如提取到局部变量 `double price = p->price;`。
3. **忘了写回** — 用局部变量累加后，循环结束记得写回 `*dest = acc;`，否则结果丢失。

### 自测题

<details>
<summary>1. 为什么 *dest = *dest OP data[i] 比用局部变量累加慢？</summary>

每轮循环都从内存读 `*dest`（load 指令）再写回 `*dest`（store 指令），多了两次访存。用局部变量（寄存器）累加，循环内零内存读写，只在循环结束后写一次。寄存器访问比内存快 1-2 个数量级。
</details>

<details>
<summary>2. 编译器为什么不自动把 *dest 提升到寄存器？</summary>

**指针别名**问题：如果 `dest` 和 `data` 指向同一地址，把 `*dest` 提升到寄存器会改变语义（因为 `data[i]` 的写会影响 `*dest` 的值）。编译器不敢假设它们不重叠，除非加 `restrict` 关键字。
</details>

<details>
<summary>3. HFT 热循环中，结构体指针字段 p->field 为什么要提取到局部变量？</summary>

`p->field` 每次访问都是**间接寻址**——先读指针 `p` 的值，再加偏移读 `field`。如果 `p` 本身也在内存中（参数传递），每次多一次 load。提取到 `double field = p->field;` 后，后续用局部变量（寄存器），零访存。
</details>
