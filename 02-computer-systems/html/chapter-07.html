大白话 · 本章一条线

编译器产出拼图块 (.o)，链接器按符号表拼成完整程序，加载器再塞进内存跑。

.c/.cpp  →  .o (REL)  →  a.out (EXEC)  →  execve 映射进 VM
              ↑ 符号解析 + 重定位
         静态库 .a / 动态库 .so

HFT 三件事：

  1. 生产与回测同一链接方式 — 静态/RPATH/glibc 版本一致，避免「实验室快、上线慢」
  2. 启动路径 — 动态库 + dlopen 插件 vs 单静态 blob（延迟、页 fault）
  3. 排错 — nm/readelf/ldd 读懂 undefined reference、ODR、weak symbol

7.1

section-7.1-编译器驱动程序

Ch7 §7.1 · 章导读 · 上节 — · 下节 §7.2 →

gcc 等是 驱动 (driver)，背后调用 cpp、cc1、as、ld：

  • as / ld 不属于 GCC — 它们是 GNU Binutils 独立工具；gcc 只是调度它们
  • cc1 才是 GCC 自带的 C→汇编前端

细节与四步拆解 → Ch3 §3.2.1

gcc -Og -Wall -o prog main.c sum.c
# 等价于：预处理 → cc1 → as → ld（你看不见底层进程）

常用分解：

gcc -c main.c -o main.o    # 只到目标文件（内部仍调 as）
gcc main.o sum.o -o prog   # 驱动去调 ld（并补上 crt/libc 等）

HFT： CI 显式 -c 再 link，便于 缓存 object、LTO 统一链接阶段；看指令用 Binutils 的 objdump -d。

口述巩固 · 自测

  1. as/ld 是 gcc 内置的吗？各属于哪套软件？
  2. gcc test.c -o test 背后大致调了哪几步？

自测题

1. gcc main.c 这一条命令实际上调用了哪些工具？

gcc 是驱动程序，依次调用： 1. cpp（预处理器）→ main.i 2. cc1（编译器）→ main.s 3. as（汇编器）→ main.o 4. ld（链接器）→ a.out

gcc -v 可以看到完整的调用链。理解这条链对调试编译问题（如链接错误、符号未定义）至关重要。

section-7.2-静态链接

Ch7 §7.2 · 章导读 · 上节 §7.1 ← · 下节 §7.3 →

  • 链接器 把所有需要的 .o 和库代码拷贝 进可执行文件
  • 优点： 无运行时找 .so、部署简单、启动可预测
  • 缺点： 体积大、libc/security 更新需重链

HFT 常见： 关键二进制 部分或全静态（-static 慎用 glibc；更常静态第三方、动态 libc 或 musl）；或 pinned 的 .so 版本随镜像分发。

1. 三种目标文件格式是什么？
  1. 可重定位目标文件(.o)：包含代码和数据，地址未最终确定，可与其他目标文件合并
  2. 可执行目标文件(a.out)：地址已确定，可直接加载执行

section-7.4-可重定位目标文件

ELF .o 典型节 (sections)：

节 内容
.text 已编译机器码
.data 已初始化全局/静态变量
.bss 未初始化全局（仅占位，不占文件字节）
.symtab 符号表
.rel.text / .rel.data 重定位条目
.debug_* 调试信息（-g）
  • 节 (section) — 链接器视角；段 (segment) — 加载器视角（readelf -l）

自测题

1. ELF 符号表中的三种符号是什么？
  1. 全局符号：本模块定义、可被其他模块引用（非 static 全局函数/变量）
  2. 外部符号：本模块引用、在其他模块定义（printf 等）
  3. 本地符号：本模块定义且只在本模块引用（static 函数/变量）

链接器主要处理全局符号和外部符号的解析。nm 命令可查看符号表：T=全局代码，D=全局数据，U=未定义（外部引用）。

7.6

section-7.6-符号解析与静态库

7.6.1 多重定义符号

链接器规则（C 语言）摘要：

情况 处理
多个 强符号 同名 错误
一强一弱 选强
多个弱符号 任选其一
static 文件局部 不冲突 
// 错误：两个 .c 都定义 int x;
// 正确：一个定义，其他 extern int x;

函数 必须是强符号；未初始化全局 是弱符号（尽量避免）。

7.6.2 与静态库链接

  • 静态库 = .a = 归档的 .o 集合（ar 打包）
  • 如 libc.a、libfoo.a
ar rcs libfoo.a foo.o bar.o
gcc main.o -L. -lfoo -o prog

7.6.3 链接器如何使用静态库

关键： 链接器 按命令行顺序 扫描；对 .a 仅当当前 undefined 符号需要时才拉入成员，且 每个成员最多拉一次。

gcc -L. -lfoo main.o   # 错误顺序：main.o 在前时 -lfoo 可能太晚
gcc main.o -L. -lfoo   # 推荐：需要符号的 .o 在前，库在后

技巧： 同一库写两次 -lfoo -lfoo，或 --start-group / --end-group。

HFT： 大型 monorepo 用 Bazel/CMake 管依赖顺序；静态链第三方（fmt、yaml）减少运行时 .so 漂移。

自测题

1. 链接器如何处理静态库（.a 文件）的符号解析？

链接器按命令行顺序扫描目标文件和库。维护三个集合：E（已加入可执行）、U（未解析引用）、D（已定义符号）。遇到 .a 文件时，扫描其成员 .o，如果某成员定义了 U 中的符号，就把该成员加入 E。顺序很重要——库必须在引用它的目标文件之后。gcc main.o -lm 正确，gcc -lm main.o 可能链接失败。

2. 为什么 gcc main.o -lm -lm 有时能解决链接问题？

静态库只按需提取成员——如果 libA 依赖 libB 的符号，但 libA 在命令行中排在 libB 之后，链接器已扫过 libB 不会回头。重复 -lm 或用 --start-group ... --end-group 让链接器循环扫描解决循环依赖。HFT 常用 Wl,--start-group 处理复杂的静态库依赖链。

7.7

section-7.7-重定位

Ch7 §7.7 · 章导读 · 上节 §7.6 ← · 下节 §7.8 →

链接器合并 .o 后，指令/数据里的 地址仍是相对的，需 重定位 修补丁。

7.7.1 重定位条目

.rel.text 等列出：偏移、类型、符号、加数

7.7.2 重定位符号引用

典型 ELF x86-64 PC 相对 直觉：

refaddr = S + A - P
  • S — 符号最终运行时地址
  • A — 加数
  • P — 被修补丁处的地址

链接器遍历条目，写入正确字节到 .text/.data。

objdump -r main.o    # 看重定位条目
objdump -d prog      # 看重定位后的绝对/相对地址

口述巩固 · 自测

  1. （待口述补）本节核心一句话？

自测题

1. 重定位的两种类型是什么？PC 相对寻址和绝对寻址有什么区别？
  1. PC 相对重定位(R_X86_64_PC32)：call func → 地址 = 当前 PC + 偏移。位置无关，适合共享库。
  2. 绝对重定位(R_X86_64_ABS64)：mov $global_var, %rax → 直接用绝对地址。需要重定位表修改。

共享库必须用 PIC（Position Independent Code），全部用 PC 相对寻址 + GOT（Global Offset Table）访问全局变量。

自测题

1. 可执行目标文件和可重定位目标文件有什么区别？

可执行文件：1. 有程序头表(Program Header Table)——告诉 OS 如何加载各 segment 到内存 2. 地址已确定（已重定位） 3. 有 .init/.fini section（C 运行时初始化/终止代码） 4. 有入口点地址（_start，不是 main）

section-7.9-加载可执行目标文件

Ch7 §7.9 · 章导读 · 上节 §7.8 ← · 下节 §7.10 →

  • execve 内核 创建进程地址空间，映射 PT_LOAD 段
  • .bss 分配零页；栈、堆 随后增长
  • 运行时常见布局（高→低）：栈 ↓ · 堆 ↑ · .data/.bss · .rodata · .text
  • 分区与 HFT（禁热路径 malloc）→ Ch3 · 五大内存分区
  • 细节 → Ch 9 虚拟内存

口述巩固 · 自测

  1. 加载后谁先有内容？ .text/.data 映射进来；.bss 清零；栈/堆后长
  2. .bss 为何不占文件体积？ 只记大小，运行时填 0

自测题

1. execve() 加载可执行文件时发生了什么？
  1. OS 创建新进程的虚拟地址空间
  2. 读 ELF 程序头表，把各 segment 映射到虚拟内存（.text→代码段 r-x，.data/.bss→数据段 rw-）
  3. 设置栈（argc, argv, envp）
  4. 跳到 _start（C 运行时入口）→ __libc_start_main → main()
  5. main 返回后 exit() 调用 .fini + 清理

关键：入口不是 main，而是 _start——它设置好运行时环境后才调用 main。

7.10

section-7.10-动态链接共享库

Ch7 §7.10 · 章导读 · 上节 §7.9 ← · 下节 §7.11 →

  • .so — 运行时 共享 一份物理代码（TEXT 共享、DATA 每进程副本）
  • 节省磁盘与 RAM；升级 libc 不必重编所有程序
  • 链接器 ld.so / ld-linux-x86-64.so.2 重定位共享库 并绑定符号

延迟绑定 (lazy binding)：
PLT (Procedure Linkage Table) + GOT (Global Offset Table) — 首次调用跳 ld.so 解析，之后走缓存地址。

ldd ./prog
LD_DEBUG=bindings ./prog   # 调试加载

口述巩固 · 自测

  1. （待口述补）本节核心一句话？

自测题

1. 动态链接和静态链接的区别？各自优缺点？

静态链接：库代码嵌入可执行文件。优点：独立运行、启动快、无依赖。缺点：文件大、库更新需重新编译。 动态链接：运行时加载 .so。优点：多进程共享内存、库可独立更新、文件小。缺点：启动需符号解析、PLT/GOT 跳转有开销、依赖 .so 存在。

HFT 常用静态链接减少启动不确定性和 PLT 开销，但内核/驱动只能动态。

2. .so 文件在内存中如何被多个进程共享？

共享库的 .text 段映射为只读，多进程共享同一物理页（通过页表映射到不同虚拟地址）。.data 段各进程有独立副本（COW）。这就是「共享」的含义——代码物理页只有一份，数据各进程独立。ldd 查看依赖的共享库，/proc/<pid>/maps 查看实际映射。

7.12

section-7.12-PIC位置无关代码

为何需要 PIC

  • 共享库 加载地址不固定（ASLR）— 代码段不能写死绝对地址
  • PIC — 文本段可在任意基址执行；数据引用 通过 GOT/相对寻址

实现要点（x86-64）

  • PC 相对寻址 — call/lea 相对 %rip
  • 全局变量访问常经 GOT — @GOTPCREL
  • -fPIC 编译共享库；-fPIE 可执行文件（PIE = ET_DYN + 入口）
gcc -fPIC -shared -o libfoo.so foo.c
gcc -pie -o prog main.c -L. -lfoo

HFT：

  • 生产二进制多 PIE + ASLR（安全）；极致延迟场景个别 no-pie（权衡安全，需合规）
  • 共享 行情解码 .so 必须 PIC，否则重定位破坏代码共享

自测题

1. 什么是 PIC？GOT 和 PLT 是什么？

PIC(Position Independent Code)：代码不依赖绝对地址，可在任意虚拟地址运行（共享库必须）。

GOT(Global Offset Table)：全局变量地址表，代码通过 GOT 间接访问全局变量（GOT 在 .data，各进程独立）。 PLT(Procedure Linkage Table)：函数调用跳转表，首次调用时通过 PLT → 动态链接器解析地址 → 回填 GOT。后续调用直接跳转。

HFT 注意：PLT 跳转有额外间接寻址开销，可用 -fno-plt 或静态链接消除。

1. 什么是库打桩(library interpositioning)？有哪几种方式？

库打桩 = 拦截对库函数的调用，插入自定义代码。三种方式： 1. 编译时：-Dmalloc=mymalloc 宏替换 2. 链接时：--wrap malloc 让链接器把 malloc 调用改为 __wrap_malloc 3. 运行时：LD_PRELOAD=./mymalloc.so 让动态链接器先加载你的库

用途：内存泄漏检测、性能 profiling、mock 测试。HFT：用 LD_PRELOAD 注入延迟模拟器测试系统在恶劣网络下的表现。

1. CSAPP 第 7 章对 HFT 最重要的知识点是什么？
  1. 静态 vs 动态链接：HFT 常静态链接减少 PLT 开销和启动不确定性
  2. GOT/PLT：动态函数调用的间接寻址开销（-fno-plt 可优化）
  3. 符号解析顺序：库在命令行中的顺序影响链接结果
  4. .bss 不占文件空间：大量未初始化数组不增加可执行文件大小
  5. LD_PRELOAD 打桩：注入自定义 malloc/IO 做性能分析
  6. ELF 格式：readelf/objdump 是调试链接问题的核心工具
