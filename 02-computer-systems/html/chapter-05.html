5.1

section-5.1-优化编译器的能力和局限性

Ch5 §5.1 · 章导读 · 上节 — · 下节 §5.2 →

编译器常能做：

  • 常量折叠、死代码消除、内联、强度削减（*8 → <<3）
  • 寄存器分配、循环不变量外提、公共子表达式消除
  • 自动向量化、循环展开（-O3 / -funroll-loops）

编译器不敢/不能做（除非你帮它）：

障碍 例子
指针别名 *x 与 *y 是否同一地址未知 → 不敢乱重排 store
全局可见副作用 函数可能改内存 → 不敢删「看似多余」调用
跨编译单元 无 LTO 时不知道 inline 候选
违反严格别名 int* 与 float* 互转 — UB
算法/结构级 不会替你把深 if-else 改成无分支查表；不会重排结构体消 cache miss
ABI / 屏障 无锁队列、内存屏障、参数个数压栈 — 要人按 Ch3 调用约定 写

帮编译器：

restrict  // C99：承诺指针不重叠
__restrict__
#pragma GCC ivdep   // 谨慎：声称无依赖
static inline + 同文件
__attribute__((noinline))  // 约束过度内联伤 icache
-fno-strict-aliasing  // 妥协，非首选

灵魂问题：既有 -O3，为何还要学 Ch3 机器码 / Ch4 流水线？

-O3 = 通用规则优化，有天花板。 全员 HFT 都会开 O3 — 那只是门票。拉开差距的是 O3 覆盖不到 的手动优化与排障能力。

O3 做不到 / 做不好 你要会什么 对应
分支最多重排，不会改成无分支查表 看汇编 + 控制冒险 → 手写消分支 Ch3 + Ch4
不懂 你的 cache 布局 结构体对齐、数组访问顺序、缓存行 Ch3 数据布局 + Ch6
多线程屏障 / 寄存器传参习惯 ABI、少压栈、正确屏障 Ch3 §3.7、并发章
过度内联/展开 → icache 变慢 读 objdump，加 noinline / 限展开 本节 + 工具链
「无副作用」计算被删光 懂 volatile/屏障/可观测副作用 Ch5 后续节
尾部延迟毛刺 perf stall + 对汇编定位 Ch3 读码能力

一句话： 普通业务不用全仓 O3 — CPU 不是瓶颈，编译慢、调试难、收益体感近零（→ Ch3 §3.2.1 对照表）。
HFT 必须热路径 O3，但 只靠 O3 远远不够 — 纳秒级优化与毛刺排查靠机器码 / 流水线 / 缓存知识。

HFT 实践： 热路径 .cpp 单文件或 LTO；restrict 明确 buffer；避免热循环调 未知副作用 函数。
等级：-O0/-Og 学调，-O3 热路径上线；浮点放宽用 -Ofast/-ffast-math 才需单独评估（默认 O3 ≠ 放宽 IEEE）。

常见陷阱

  1. 盲目全仓 -O3 — O3 会增加编译时间、二进制体积、调试难度；非热路径收益体感近零。普通业务用 O2，HFT 热路径单独 O3/LTO。
  2. 以为 -O3 默认放宽浮点 — O3 不破坏 IEEE 754；只有 -Ofast/-ffast-math 才放宽浮点语义，需单独评估。
  3. 忘了 restrict 导致编译器不敢优化 — 指针别名是编译器最大障碍；不加 restrict，编译器不敢重排 store、不敢向量化。HFT 热 buffer 明确加 restrict。

自测题

1. 为何后台服务多用 O2 而非全仓 O3？

编译时间增加、二进制体积膨胀、调试困难（变量被优化掉）；瓶颈通常在 IO 而非 CPU，O3 的 CPU 收益体感近零。HFT 热路径才值得 O3 + LTO。

2. 有了 -O3，为何还要学汇编和流水线？

-O3 有天花板：不会改成无分支查表、不懂你的 cache 布局、不能替你调结构体对齐、过度内联反而伤 icache。纳秒级优化与毛刺排查靠机器码/流水线/缓存知识。全员都会开 O3——那只是门票。

3. O3 默认会破坏 IEEE 754 浮点语义吗？

一般不会。 -O3 做的是通用规则优化（内联、展开、向量化等）。放宽浮点需要显式 -Ofast 或 -ffast-math，会允许重排/融合浮点运算，改变舍入行为。

5.2

section-5.2-表示程序性能

Ch5 §5.2 · 章导读 · 上节 §5.1 ← · 下节 §5.3 →

核心度量

指标 含义 HFT 场景
时钟周期 比「秒」更稳定（CPU 频率会动态变化） perf stat 默认用 cycles
CPE (Cycles Per Element) 每处理一个元素的平均周期数 行情每 tick 的 CPE
吞吐 元素/秒 撮合吞吐
延迟 单任务完成时间 发单路径 ns/op 
性能 = 工作 / 时间 = (n 元素 × CPE) / 时钟频率

CPE 的意义

不同输入长度 n 下，总周期 ≈ CPE × n + 固定开销。用 CPE 可以消除长度差异，直接比较两个实现的效率。

  • CPE 越低越好 — 每元素花的周期少
  • 线性拟合：总周期 = CPE × n + b，斜率即 CPE

HFT 特别注意

  • 别只看平均 CPE — P99 tail 才是命门；平均快但偶尔 stall 10× 会丢行情
  • 频率变化 — turbo boost / 节能模式会改变时钟频率，用周期数比用纳秒更稳
  • 测量方法 — perf stat / rdtsc / clock_gettime(CLOCK_MONOTONIC)

→ 观测工具 → Ch16 Systems Performance

常见陷阱

  1. 用「秒」而非「周期」测性能 — CPU 频率动态变化（turbo/节能），同一代码跑两次纳秒数不同。用周期数（cycles）消除频率波动。
  2. 只看平均忽略尾部 — 平均 CPE 低不代表没有毛刺。HFT 要看 P99/P999 延迟，一次 10× stall 就能丢一整批行情。
  3. 混淆吞吐与延迟 — 批处理 1000 条消息的总吞吐高，但单条延迟可能很差。HFT 热路径同时要低延迟（ns/op）和高吞吐。

自测题

1. 为什么用时钟周期而非秒来度量性能？

CPU 频率会动态变化（turbo boost、节能模式），同一代码跑两次的纳秒数不同。时钟周期是硬件固定的单位，不受频率波动影响，更适合做性能比较。

2. CPE 是什么？为什么比总周期数更适合比较？

CPE = Cycles Per Element，每处理一个元素的平均周期数。不同输入长度 n 的总周期不同，用 CPE 可以消除长度差异，直接比较两个实现的效率。总周期 ≈ CPE × n + 固定开销。

3. HFT 为什么不能只看平均 CPE？

平均 CPE 低不代表没有毛刺。HFT 要看 P99/P999 尾部延迟——一次 10× 的 stall（cache miss、分支预测失败）就能丢一整批行情。平均快但尾部差比平均慢但稳定更致命。

5.3

section-5.3-程序示例

Ch5 §5.3 · 章导读 · 上节 §5.2 ← · 下节 §5.4 →

贯穿全章的示例：向量 combine

CSAPP 用一个向量 combine 函数贯穿 Ch5 全章——从最慢的朴素写法开始，逐步优化：

// 朴素版：data 是 int 数组，IDENT 是 + 或 *
void combine1(vec_ptr v, data_t *dest) {
    long i;
    *dest = IDENT;
    for (i = 0; i < vec_length(v); i++) {
        data_t val;
        get_vec_element(v, i, &val);
        *dest = *dest OP val;
    }
}

这个示例为什么好

问题 combine1 中的体现 后续哪节修
循环内重复调用 vec_length 每次迭代都算长度 §5.4
循环内函数调用开销 get_vec_element 每次调函数 §5.5
不必要的内存引用 *dest 每次读+写内存 §5.6
指令级并行不足 单累加器串行依赖 §5.7–5.9

每一节解决一个问题，CPE 逐步降低——优化是渐进的，不是一步到位。

HFT 对应

  • combine ≈ 行情批量处理循环（遍历价位数组做聚合）
  • get_vec_element ≈ 通过抽象层访问数据（每次函数调用的开销）
  • *dest = *dest OP val ≈ 在热循环里反复读写内存而非寄存器

常见陷阱

  1. 跳过示例直接看结论 — combine1 是后续每一节优化的起点，不看示例就不知道每步优化在改什么、CPE 降了多少。
  2. 以为示例太简单不实用 — combine 虽然简单，但暴露的问题（循环低效、函数调用、内存引用、并行不足）在 HFT 热循环里完全一样。

自测题

1. combine1 有哪些性能问题？分别对应后面哪一节？
  • 循环内重复调用 vec_length → §5.4 消除循环低效率
  • 循环内函数调用 get_vec_element → §5.5 减少过程调用
  • *dest 每次读写内存 → §5.6 消除不必要的内存引用
  • 单累加器串行依赖 → §5.7–5.9 提高并行性
2. 为什么 CSAPP 用 combine 贯穿全章而非每节换例子？

优化是渐进的——同一个示例逐步改进，每步只改一个问题，CPE 逐步降低。这样能清晰看到每个优化手段的独立贡献，也说明真实优化是「一层一层剥」而非一步到位。

5.4

section-5.4-消除循环的低效率

Ch5 §5.4 · 章导读 · 上节 §5.3 ← · 下节 §5.5 →

典型杀手：循环内重复计算

// 慢：每次迭代 strlen
for (i = 0; i < strlen(s); i++) ...

// 快：不变量外提
int len = strlen(s);
for (i = 0; i < len; i++) ...
  • 归纳变量优化 — 编译器常做，但依赖 -O 与可见性
  • HFT：循环边界、buffer 长度 在循环外算好；tick 处理别每包 vector.size() 若可缓存

常见陷阱

  1. 循环内重复调用函数求边界 — for (i=0; i<strlen(s); i++) 每轮都调 strlen（O(n) 扫描），整体变成 O(n²)。提取到循环外 int len = strlen(s);。
  2. 以为编译器一定会做不变量外提 — 如果函数有副作用或指针别名，编译器不敢假设返回值不变。HFT 中 vector.size() 虽然通常可内联，但跨编译单元/虚函数不一定。
  3. 循环内构造/析构 — C++ 中循环内创建临时对象（如字符串拼接），每次迭代都分配/释放。移到循环外复用。

自测题

1. for (i=0; i<strlen(s); i++) 有什么性能问题？

strlen(s) 是 O(n) 扫描，在循环条件里每轮都调用，整体变成 O(n²)。提取到循环外 int len = strlen(s); for (i=0; i<len; i++) 降为 O(n)。这叫循环不变量外提。

2. 编译器会自动做不变量外提吗？什么情况不会？

如果函数是纯函数（无副作用）且编译器能确认返回值不变，-O2 以上通常能自动外提。但如果函数有副作用、有指针别名、或跨编译单元无 LTO，编译器不敢假设返回值不变，不会外提。

3. HFT 热循环中还有哪些类似的「隐式重复计算」？
  • vector.size() 跨编译单元可能不内联
  • 循环内反复解引用结构体指针求字段（如 order->price.level）
  • 循环内构造临时字符串/对象
  • 循环内调用 log() / printf() 等 IO 函数

5.5

section-5.5-减少过程调用

Ch5 §5.5 · 章导读 · 上节 §5.4 ← · 下节 §5.6 →

// 慢：每元素一次 call
for (i = 0; i < n; i++)
    acc = combine(acc, data[i]);

// 快：宏/内联/手写操作符在循环内
for (i = 0; i < n; i++)
    acc = acc + data[i];
  • 调用开销： 参数传递、栈、call/ret、打乱流水线
  • inline 是 C/C++ 关键字（不是汇编指令）— 请编译器把函数体嵌到调用处；成功则机器码里常 看不到 call
  • static inline + 同 TU；或 模板/宏（权衡可读性）

HFT： 热路径 禁止虚函数 per tick（或 PGO/devirtualize）；价差/小工具函数 inline/always_inline，少栈往返、寄存器更连着用。机制细节 → Ch3 §3.7.7。

常见陷阱

  1. 热循环里调虚函数 — 虚函数通过 vtable 间接调用，编译器无法内联，每次 call + vtable 查找。HFT 热路径用 PGO/devirtualize 或直接 final + 非虚接口。
  2. 以为 inline 关键字保证内联 — inline 只是建议，编译器可能拒绝（函数太大、递归、跨 TU 无 LTO）。用 __attribute__((always_inline)) 或 static inline + 同 TU 强制。
  3. 忽略 call/ret 对流水线的影响 — 每次函数调用有 call（PC 跳转→控制冒险）+ 栈帧操作 + ret（PC 恢复→控制冒险）。热循环内频繁调用 = 频繁冲刷。

自测题

1. 循环内函数调用有哪些开销？

①参数传递（压栈或寄存器）；②call 指令（PC 跳转→控制冒险）；③栈帧建立/销毁；④ret 指令（PC 恢复→控制冒险）；⑤打乱流水线（分支预测）。内联后这些开销全部消失，机器码里看不到 call。

2. inline 关键字能保证内联吗？什么情况不会？

不能。 inline 只是建议。编译器可能拒绝：函数太大、递归、跨编译单元无 LTO。用 static inline + 同 TU，或 __attribute__((always_inline)) 强制。但过度 always_inline 会增加代码膨胀和 icache 压力。

3. HFT 热路径中虚函数为什么是性能杀手？

虚函数通过 vtable 间接调用：①编译器无法内联（不知道运行时调哪个实现）；②每次调用多一次 vtable 内存读取（可能 cache miss）；③call 通过寄存器间接跳转，分支预测器更难预测。解法：PGO/devirtualize、final 关键字、或编译期多态（模板/C++)。

5.6

section-5.6-消除不必要的内存引用

Ch5 §5.6 · 章导读 · 上节 §5.5 ← · 下节 §5.7 →

问题：热循环里反复读写内存

// 慢：每次迭代都读 *dest、写 *dest
for (i = 0; i < len; i++) {
    *dest = *dest OP data[i];
}

每轮循环：①从内存读 *dest → ②ALU 运算 → ③写回 *dest。*dest 在循环中是累加器，完全可以用寄存器保存。

优化：用局部变量（寄存器）累加

// 快：寄存器累加，循环结束后才写一次
data_t acc = IDENT;
for (i = 0; i < len; i++) {
    acc = acc OP data[i];
}
*dest = acc;
慢版 快版
每轮内存读 1 次（*dest） 0 次
每轮内存写 1 次（*dest） 0 次
累加器位置 内存 寄存器
CPE 改善 — 显著降低

为什么编译器不自动做？

编译器理论上可以做这个优化（寄存器分配），但有两个障碍：

  1. 指针别名 — 如果 dest 和 data 指向同一地址（aliasing），改写顺序会影响结果。编译器不敢假设它们不重叠。
  2. 需要 restrict — 加 restrict 关键字承诺 dest 和 data 不重叠，编译器才敢把 *dest 提升到寄存器。
void combine(vec_ptr v, data_t *restrict dest) { ... }

HFT 实践

  • 热循环累加器一律用局部变量 — 不依赖编译器，手动保证寄存器累加
  • restrict 明确 buffer 不重叠 — 帮编译器放开手脚
  • 结构体字段避免热循环里反复解引用 — p->field 每次是指针间接寻址，提取到局部变量

常见陷阱

  1. 以为编译器会自动消除内存引用 — 如果有指针别名（dest 和 data 可能指向同一地址），编译器不敢把 *dest 提升到寄存器。必须加 restrict 或手动用局部变量。
  2. 热循环里反复解引用结构体指针 — p->price 每次都是间接寻址（先读 p 再读 price 偏移），不如提取到局部变量 double price = p->price;。
  3. 忘了写回 — 用局部变量累加后，循环结束记得写回 *dest = acc;，否则结果丢失。

自测题

1. 为什么 dest = dest OP data[i] 比用局部变量累加慢？

每轮循环都从内存读 *dest（load 指令）再写回 *dest（store 指令），多了两次访存。用局部变量（寄存器）累加，循环内零内存读写，只在循环结束后写一次。寄存器访问比内存快 1-2 个数量级。

2. 编译器为什么不自动把 *dest 提升到寄存器？

指针别名问题：如果 dest 和 data 指向同一地址，把 *dest 提升到寄存器会改变语义（因为 data[i] 的写会影响 *dest 的值）。编译器不敢假设它们不重叠，除非加 restrict 关键字。

3. HFT 热循环中，结构体指针字段 p->field 为什么要提取到局部变量？

p->field 每次访问都是间接寻址——先读指针 p 的值，再加偏移读 field。如果 p 本身也在内存中（参数传递），每次多一次 load。提取到 double field = p->field; 后，后续用局部变量（寄存器），零访存。

5.7

section-5.7-现代处理器抽象模型

5.7.1 整体操作 — 超标量与乱序

真 CPU（相对 Y86 PIPE）还具备：

特性 含义
多发射 / 超标量 每周期可退休多条指令
乱序执行 (OOO) 在依赖允许下重排，隐藏延迟
投机执行 分支预测失败则回滚

Latency × Operation = 吞吐瓶颈 — 功能单元有 吞吐上限（如每周期 1 个除法）。

5.7.2 功能单元的性能

  • 整数 add — 通常 1 周期延迟、高吞吐
  • 乘法 — 数周期延迟
  • 除法 — 慢，吞吐低
  • load/store — 依赖 cache 命中（→ 5.12、Ch 6）

5.7.3 处理器操作的抽象模型

原书 数据流图 / 吞吐量边界 直觉：

  • 循环携带依赖 (loop-carried dependency) — acc = f(acc, data[i]) 限制 ILP，每次迭代依赖上次 acc
  • 打破依赖 — 多累加器、重结合（→ 5.9）
  • 临界路径长度 — 决定理论最短周期

HFT： perf 看 stalled-cycles-frontend/backend；IPC 低不一定是分支，可能是 长依赖链 或 等待 load。

→ 流水线基础：Ch 4

常见陷阱

  1. 把超标量当成「自动并行一切」 — 超标量/乱序只能利用指令级并行（ILP），受数据依赖限制。如果循环携带依赖链太长，再宽的发射宽度也帮不了你。
  2. IPC 低就怪分支 — IPC < 1 可能是长依赖链（数据冒险 stall）、cache miss 等待 load、或功能单元吞吐瓶颈。用 perf 分辨 stalled-cycles-frontend vs backend。
  3. 忽略功能单元吞吐上限 — 即使无依赖，除法每周期只能做 1 个（甚至更慢），乘法有数周期延迟。多累加器打破依赖后，瓶颈可能转移到功能单元吞吐。

自测题

1. 超标量、乱序执行、投机执行分别是什么？
  • 超标量（多发射）：每周期可退休多条指令（受功能单元数量限制）
  • 乱序执行（OOO）：在数据依赖允许下重排指令顺序，隐藏延迟（如等 load 时先做其他独立运算）
  • 投机执行：沿分支预测的路径提前执行，预测正确则保留结果，错误则回滚
2. 什么是循环携带依赖？为什么它限制了 ILP？

acc = f(acc, data[i]) —— 每次迭代依赖上一次的 acc，形成串行链。即使 CPU 能每周期发射 4 条指令，这条依赖链上的指令也只能逐条执行。临界路径长度决定理论最短周期。打破方法：多累加器（§5.9）。

3. IPC 低于 1 一定是因为分支预测失败吗？

不一定。 IPC < 1 的原因可能包括：①长数据依赖链（stall 等待前一条结果）；②cache miss 导致 load 等待；③功能单元吞吐瓶颈（如除法慢）；④分支预测失败（控制冒险 flush）。用 perf stat 看 stalled-cycles-frontend/backend、branch-misses、cache-misses 分辨。

5.8

section-5.8-循环展开

Ch5 §5.8 · 章导读 · 上节 §5.7 ← · 下节 §5.9 →

手动或编译器展开：

// 2 路展开
for (i = 0; i < n-1; i += 2) {
    acc = (acc + data[i]) + data[i+1];
}
// 处理尾部 n%2

收益：

  • 减少 分支（每迭代处理多元素）
  • 增 指令级并行 — 多条独立 load/add 可并行发射
  • 常与 多累加器 联用

代价： 代码膨胀、I-cache 压力、寄存器压力（→ 5.11）

gcc -O3 -funroll-loops ...

常见陷阱

  1. 展开因子太大导致寄存器溢出 — 展开太多路，寄存器不够用，编译器把变量溢出到栈内存，反而变慢。通常 2-4 路展开收益最佳，超过后边际递减。
  2. 忘了处理尾部剩余元素 — n 不一定是展开因子的整数倍，循环后要处理 n % k 个剩余元素，否则结果错误。
  3. 手动展开干扰编译器自动优化 — -O3 -funroll-loops 已经会自动展开；手写展开可能干扰编译器的向量化和其他优化。先测编译器自动展开的效果，不够再手动。

自测题

1. 循环展开为什么能提高性能？

三个原因：①减少分支指令（每迭代处理多个元素，分支数减少）；②增加指令级并行——多条独立的 load/add 可并行发射到不同执行单元；③减少循环开销（计数器更新、条件判断）。常与多累加器联用打破串行依赖。

2. 循环展开的代价是什么？

代码膨胀（二进制变大）、I-cache 压力（指令多到放不进 cache 反而变慢）、寄存器压力（展开太多路寄存器不够用，溢出到内存）。过度展开可能负优化。

3. 手动展开还是用 -funroll-loops？

优先用 -O3 -funroll-loops 让编译器自动展开——它能处理尾部、选择最优因子、配合向量化。手动展开可能干扰编译器优化。先测自动展开效果，不够再手动，且手动展开后务必 benchmark 验证。

5.9

section-5.9-提高并行性

Ch5 §5.9 · 章导读 · 上节 §5.8 ← · 下节 §5.10 →

5.9.1 多个累积变量

// 2 路展开 + 双累加器，打破 loop-carried dep
x0 = ident; x1 = ident;
for (i = 0; i < n-1; i += 2) {
    x0 = x0 + data[i];
    x1 = x1 + data[i+1];
}
acc = (x0 + x1) + ...;

x0 与 x1 无依赖 — CPU 可并行执行。

5.9.2 重新结合变换 (Reassociation)

// 结合律对浮点不严格成立！整数 + 在数学上 OK
// (a + data[i]) + data[i+1]  vs  a + (data[i] + data[i+1])
  • 编译器在 -ffast-math 下对浮点重结合 — HFT 慎用 于价格累加
  • 整数 tick 求和、checksum 可重结合

常见陷阱

  1. 多累加器用太多导致寄存器溢出 — 2-4 路多累加器通常最佳；超过后寄存器不够用，spill 到栈内存，CPE 反弹。用 perf annotate 检查是否出现栈访问。
  2. 浮点重结合改变结果 — 浮点加法不严格满足结合律（(a+b)+c ≠ a+(b+c)）。-ffast-math 允许重结合但改变舍入。HFT 价格累加慎用；整数 tick 求和/checksum 可以。
  3. 以为打破依赖就能无限并行 — 受限于功能单元吞吐上限（如每周期最多 2 个 load）。打破依赖只是消除了串行瓶颈，实际并行度还受硬件资源限制。

自测题

1. 多累加器为什么能提高并行性？

单累加器 acc = acc + data[i] 形成循环携带依赖（loop-carried dependency）——每次迭代必须等上次的 acc。双累加器 x0 = x0 + data[i]; x1 = x1 + data[i+1] 之间无依赖，CPU 可并行执行两条独立的加法。

2. 重新结合变换（reassociation）是什么？浮点能用吗？

改变运算的括号顺序：(a + data[i]) + data[i+1] → a + (data[i] + data[i+1])。后者打破了 a 的循环携带依赖。整数可以自由重结合；浮点不严格满足结合律，-ffast-math 才允许，但会改变舍入结果，HFT 价格累加慎用。

3. 多累加器展开到几路最佳？为什么不是越多越好？

通常 2-4 路最佳。超过后：①寄存器不够用，spill 到栈内存（额外 load/store）；②代码膨胀增加 icache 压力；③受功能单元吞吐上限限制（如每周期最多 2 个 load），更多路也无法并行。用 perf 验证实际 CPE。

section-5.10-优化合并代码的结果小结

combine 优化路径回顾

从 §5.3 的朴素 combine1 到 §5.9 的高性能版本，每步优化的 CPE 变化：

版本 优化手段 解决的问题 CPE 趋势
combine1 朴素版 — 基准
combine2 循环不变量外提 §5.4 每轮调 vec_length ↓
combine3 减少过程调用 §5.5 每轮调 get_vec_element ↓
combine4 消除内存引用 §5.6 *dest 改寄存器累加 ↓
combine5 循环展开 §5.8 减少分支+增 ILP ↓

关键教训

  1. 优化是渐进的 — 每步只改一个问题，用 CPE 量化效果
  2. 先 profile 再优化 — 不要猜瓶颈，用数据驱动
  3. 最大收益来自打破依赖 — 从 combine5 到 combine6 的 CPE 下降最显著

常见陷阱

  1. 跳过中间步骤直接上最终版 — 不理解每步优化的独立贡献，出问题时不知道回退到哪一步。
  2. 只看 CPE 不看正确性 — 多累加器和重结合可能改变浮点结果；每次优化后必须验证输出正确。

自测题

1. 从 combine1 到 combine6，哪一步的 CPE 下降最显著？为什么？

combine6（多累加器） 下降最显著。因为它打破了循环携带依赖——之前每轮必须等上一轮的 acc，CPU 的超标量/乱序能力无法发挥。多累加器让多条加法独立，ILP 充分利用，CPE 大幅下降。

2. 优化是「一步到位」还是「渐进式」？为什么？

渐进式——每步只改一个问题，用 CPE 量化效果。原因：①出问题时能定位到哪一步引入的；②能理解每个优化手段的独立贡献；③有些优化相互制约（如展开太多导致寄存器溢出），需要逐步试验找到最优点。

5.11

section-5.11-寄存器溢出与分支预测

5.11.1 寄存器溢出 (Register Spilling)

  • 展开 × 多累加器 → 需要 更多寄存器
  • 寄存器不够 → spill 到栈 — 额外 load/store，CPE 反弹

现象： 展开从 4× 到 8× 反而变慢 — 用 perf annotate 看栈访问增多。

HFT： 极热循环控制 活跃变量数量；-O3 通常比瞎展开 smarter。

5.11.2 分支预测与误预测处罚

  • 展开减少 循环分支 次数
  • 但 combine 里若仍有 数据相关分支（如 if (x>0)）— branch-misses 仍致命
策略 适用
cmov / 无分支代码 简单选择
排序数据 使分支可预测
查表 / 位掩码 替代分支
__builtin_expect / [[likely]] 提示布局

→ Ch 3 cmov · Ch 4 预测

HFT： 消息类型 dispatch 用 跳转表；热路径避免 if (unlikely_error) 夹在大循环中间 — 错误处理拆到冷路径。

常见陷阱

  1. 展开太多路反而变慢 — 4× 展开可能快，8× 反而慢——寄存器不够用，spill 到栈。用 perf annotate 检查是否出现栈访问（mov %xmm0, -0x10(%rsp) 等）。
  2. 热循环里夹 if (unlikely_error) — 即使错误几乎不发生，分支预测器仍可能误预测，导致 flush。把错误处理拆到冷路径（cold 属性 / 单独函数）。
  3. 用 __builtin_expect 代替无分支 — __builtin_expect 只是提示分支布局，不消除分支。如果分支不可预测，cmov/查表/位掩码才是根本解法。

自测题

1. 寄存器溢出（spilling）是什么？怎么发现？

寄存器不够用，编译器把变量存到栈内存，每次用都要 load/store，CPE 反弹。现象：展开从 4× 到 8× 反而变慢。用 perf annotate 看汇编是否出现栈访问（mov reg, offset(%rsp)）。

2. 循环展开减少了分支，为什么 branch-misses 可能仍然很高？

展开减少的是循环分支（i < n 判断），但循环体内如果有数据相关分支（如 if (data[i] > 0)），这些分支仍然存在且可能不可预测。branch-misses 取决于所有分支的预测成功率，不只循环条件。

3. HFT 中如何处理热路径里的错误检查分支？

把错误处理拆到冷路径：①用 __attribute__((cold)) 标记错误处理函数；②if (unlikely(error)) { handle_error(); } 中 handle_error 单独成函数不被内联；③甚至用无分支方式检查（位掩码累积错误标志，循环后统一处理）。避免不可预测分支夹在热循环中间。

5.12

section-5.12-加载与存储性能

5.12.1 加载的性能

  • load 延迟 — L1 hit ~4 周期量级；miss 到 DRAM 上百周期
  • load-use — load 结果就绪前，依赖它的指令 stall（Ch4 PIPE）
  • 多条 load 并行 — 若地址独立、命中 cache，可多发射

优化方向：

  • 提高 局部性 — 顺序扫数组（→ Ch 6）
  • 预取 — __builtin_prefetch 对下一 cache line
  • 减少 指针追踪 — 链表 vs 数组

5.12.2 存储的性能

  • store 通常不阻塞 retirement（写缓冲），但 load 依赖 store 时需等地址解析
  • 写后读 (WAR) 同地址 — 内存依赖链

HFT：

  • SoA 批量写行情字段 vs AoS 单条更新 — 按访问模式选
  • false sharing — 多线程写相邻字段 → 同一 cache line（→ Ch3 3.9）
  • perf：mem-loads、L1-dcache-load-misses、cache-misses

常见陷阱

  1. load-use 冒险被忽略 — load 的数据要到 M 级才出来，紧接着的指令在 D 级就要用 → 必须 stall 一拍。热循环避免 load 后立刻依赖，或用预取/重排让编译器插入独立指令。
  2. store-load 同地址依赖 — 先 store 再 load 同一地址，CPU 必须等 store 地址解析完才能确认 load 是否读 store 的值（store-to-load forwarding）。避免在热循环中写后读同一地址。
  3. 预取用错反而变慢 — __builtin_prefetch 预取太远（数据还没到使用时间，被挤出 cache）或太近（来不及预取）都无效。正确预取距离 ≈ cache miss latency / 每元素处理时间。

自测题

1. load 延迟取决于什么？L1 hit 和 DRAM miss 差多少？

取决于cache 命中层级：L1 hit ~4 周期，L2 hit ~10-15 周期，L3 hit ~40 周期，DRAM miss 上百周期。HFT 热数据必须留在 L1/L2，一次 DRAM miss 就能导致毛刺。

2. 为什么多条独立 load 可以并行？什么情况不行？

如果多个 load 的地址独立且都命中 cache，CPU 的超标量/乱序引擎可以同时发射多条 load 指令。不行的情况：①地址依赖（load B 的地址需要 load A 的结果——指针追踪/链表）；②cache miss（miss 会占用 MSHR，限制后续 miss 并行度）；③load-use 冒险（紧接着依赖 load 结果）。

3. false sharing 是什么？HFT 中怎么避免？

多线程写同一 cache line 的不同字段 → cache line 在核心间反复 invalidate/transfer，性能暴跌。避免方法：①alignas(64) 让每个线程的独立数据独占 cache line；②SoA 布局让同一线程访问的数据连续；③只读数据共享无妨（只读不触发 invalidate）。

常见陷阱

  1. 跳过 profile 直接「优化」 — 凭直觉改代码，可能优化了非瓶颈部分（阿姆达尔定律：占 5% 的函数优化 2× 只提升 2.5%）。先 profile 找到 >10% 的热点。
  2. 优化顺序错误 — 先调系统层（hugepage/NUMA）再调算法层，本末倒置。正确顺序：算法 → 源码 → 编译 → 并行 → 系统，每层收益递减。
  3. 改完不测 — 每次优化后必须用同一 workload、同一硬件、同一编译 flags benchmark。微基准只验证 CPE，端到端用 replay 验证 P99。

自测题

1. 性能优化的正确层级顺序是什么？为什么？

算法 → 源码 → 编译 → 并行 → 系统。算法层收益最大（O(n²) → O(n) 是数量级提升）；源码层是本章内容（循环优化等）；编译层（O3/LTO/PGO）是自动化收益；并行层（多线程/绑核）需要前面打好基础；系统层（hugepage/NUMA）是最后几%的微调。每层收益递减，跳层优化是浪费。

2. 为什么不能跳过 profile 直接优化？

阿姆达尔定律：如果某函数占总时间 5%，即使优化到 0 也只提升 5%。凭直觉改代码很可能优化了非瓶颈部分。先 profile 找到占 >10% 的热点，集中精力改最大瓶颈，投入产出比最高。

3. HFT 优化的标准工作流是什么？

①生产/trace replay 收集数据 → ②perf record 采样 → ③火焰图找热点 → ④改热函数 → ⑤回归 P99 延迟（不只看平均）→ ⑥确保 binary flags 与生产对齐 → ⑦跑 regression + 压力测试。每次只改一个变量。

工具 用途

5.14.2 用剖析指导优化

  1. 找占时间 >5–10% 的函数 — 阿姆达尔
  2. 区分 CPU bound vs memory bound vs I/O wait（→ 06.6-Systems-Performance）
  3. 改完对比 同一 workload、同一硬件、同一编译 flags
  4. 避免 微观基准误导 — 微基准只验证 CPE，端到端用 replay

HFT 工作流：

生产/trace replay → perf 火焰图 → 改热函数 → 回归 P99 延迟
回测与生产 binary flags 对齐；改完跑 regression + 压力测试

常见陷阱

  1. 微基准误导 — 微基准只测单个函数的 CPE，可能跟端到端表现不一致。一个函数 CPE 降了 2× 但整体 P99 没改善——说明瓶颈在别处。用 trace replay 做端到端验证。
  2. profile 采样率太低 — perf record 默认采样率可能漏掉短热路径。HFT 纳秒级路径需要高采样率（-F 9999）或用 perf c2c/perf mem 精确定位。
  3. 改了代码但 binary flags 不一致 — 回测用 -O2，生产用 -O3，优化效果不同。确保 benchmark 和生产用完全相同的编译 flags、CPU 型号、OS 配置。

自测题

1. perf 的基本工作流是什么？

①perf record -g ./program 采样（-g 记录调用栈）→ ②perf report 看热点函数 → ③perf annotate -s hot_function 看热点汇编 → ④改代码 → ⑤重新 benchmark 对比。HFT 还需要看 branch-misses、cache-misses、stalled-cycles 等硬件计数器。

2. 如何区分 CPU bound vs memory bound？

看 perf stat 的硬件计数器：CPU bound → IPC > 1、stalled-cycles-backend 低、cache-misses 低；memory bound → IPC < 1、stalled-cycles-backend 高、cache-misses/L1-dcache-load-misses 高。也可以看 perf mem 或 perf c2c 精确定位内存访问问题。

3. 为什么微基准好但端到端没提升？

可能原因：①微基准的 workload 不代表真实场景（数据分布、分支模式不同）；②优化的函数不是端到端瓶颈（阿姆达尔定律）；③优化引入了其他开销（如代码膨胀导致 icache miss）；④binary flags 不一致。必须用 trace replay 做端到端 P99 回归验证。

常见陷阱

自测题

1. Ch5 全章最大的教训是什么？

优化是渐进的、数据驱动的。从 combine1 到 combine6，每步只改一个问题，用 CPE 量化效果。最大收益来自打破循环携带依赖（多累加器）。-O3 有天花板，纳秒级优化靠手动：读汇编、拆依赖、cache 友好、无分支。

2. HFT 性能优化的完整工具链是什么？

①perf record/report/annotate 找热点和瓶颈 → ②读汇编定位 stall（load-use? 分支? cache miss?）→ ③针对性优化（内联/寄存器累加/展开/多累加器/无分支）→ ④perf stat 验证硬件计数器改善 → ⑤trace replay 回归 P99 延迟。
