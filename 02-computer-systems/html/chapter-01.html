大白话 · 本章一条线

hello.c 怎么变成屏幕上的 hello, world？

源码 hello.c
  → 编译/链接 → 可执行文件 a.out
  → shell 加载 → 进程在 CPU 上跑
  → 读内存/缓存/磁盘 → 经 OS  syscall 写终端或 socket

你要带走的不是背图，而是四个 HFT 直觉：

  1. 比特本身无意义，上下文决定含义 — 编译器 / CPU / 内存 / 协议 layout（→ 1.1）；行情 feed 解析错 offset = 上下文错
  2. 慢的不在 CPU 算力，在等数据 — cache miss、磁盘、网络、syscall（→ 1.5–1.6，深入 Ch 6）
  3. 程序从不「直接摸硬件」 — OS 用进程/线程/虚拟内存/文件抽象隔开（→ 1.7，深入 Ch 8–9）
  4. 优化要有靶心 — 阿姆达尔：先打最慢的那段（→ 1.9，配合 Ch 5、06.6-Systems-Performance）

1.1

section-1.1-信息就是位与上下文

核心概念

  • 一切信息在机器里都是比特（0/1） — 比特本身没有「天生含义」。
  • 上下文 (context) — 这串比特当前所处的规则环境；不同环境有完全不同的解码规则。

原书 1.1 说的「上下文」，不是「调用栈上下文」或「业务场景」，而是：谁在读这些比特、按什么格式读。

同一串比特，四种读法

以 8 个比特 01000001（十六进制 0x41）为例：

上下文 解码规则 读成什么
编译器（词法分析） C 源码字符集 字符 'A'
CPU（取指） 当前 PC 指向 代码段 某条 x86 指令的一部分（如 INC ecx 的操作码片段）
内存（数据段） 类型声明为 int 整数 65
网络（TCP 载荷） 协议 layout 规定「此处是版本号」 协议字段 version = 65

关键： 比特串没变，变的是 解释它的规则。解释错了 = 把数据当指令跑、把 float 当 int 读、把 offset 8 当 offset 4 解析行情 — 结果要么崩溃，要么 silently wrong（交易里更危险）。

程序 = 比特在不同上下文间流转

磁盘上的 hello.c（文本比特，编译器上下文）
  → 预处理/编译/汇编/链接 → 可执行文件（机器码比特）
  → 加载进内存 → CPU 当指令执行（指令上下文）
  → printf 输出 → 终端当 UTF-8 字符显示（字符上下文）

行情二进制协议 = 比特 + 协议上下文

行情二进制协议 就是把价格、成交量、时间戳等字段，按 事先写死的 layout 排成比特串，经 UDP/TCP/组播发出去。接收方必须用 同一套 layout 解码 — 这就是网络层的「上下文」。

虚构极简 tick（16 字节，big-endian）：

偏移 长度 字段 示例值
0 1 B 版本 0x01
1 4 B 合约 ID 0x00001234
5 8 B 价格（fixed-point ×1e4） 0x00000000001B7740 → 1800000 → 180.0000
13 4 B 成交量 0x000003E8 → 1000

线上可能收到（十六进制）：

01 00 00 12 34 00 00 00 00 01 B7 74 00 00 00 03 E8
  • 用上面这张表当上下文 → 「合约 4660，价 180.0000，量 1000」
  • 换一套协议（比如前 4 字节是 crypto 的 symbol hash）→ 同一串比特可能解成完全不同的合约与价格

这就是 CSAPP 1.1 和 HFT 的直接连接：SBE、FIX 二进制、交易所私有 feed 都是 比特 + 协议 spec（上下文）。解析错 offset 或 endianness，等价于 C 里 类型 punning 用错 — 不会编译器报错，但实盘会错单。

协议层概念 CSAPP 对应
字段 offset / length 结构体布局、Ch 3 对齐
big-endian 线上序 Ch 2 字节序
版本号字段 协议升级时「上下文版本」不一致 → 兼容性问题
整包 CRC / 长度 比特损坏或截断 → 解码上下文错位

与后续章节

→ 整数/浮点/字节序怎么编码：Ch 2
→ 机器码、结构体对齐：Ch 3
→ socket 读入的字节如何当协议解析：Ch 11

自测题

1. 同一串比特 01000001（0x41）在不同上下文下可以有哪些解读？

比特本身无含义，上下文决定解读规则： - 编译器上下文 → 字符 'A' - CPU 取指上下文 → x86 指令操作码片段 - 数据段 int 上下文 → 整数 65 - 网络协议上下文 → 协议字段（如 version=65）

HFT 关联：行情二进制协议（SBE/FIX）就是比特 + 协议 layout。解析错 offset 或 endianness 等于类型 punning 用错——编译器不报错，但实盘会错单。

2. 什么是「上下文」？它和「调用栈上下文」有什么区别？

CSAPP 1.1 的「上下文」指谁在读这些比特、按什么格式读——是解码规则环境，不是运行时调用栈。调用栈上下文是程序执行状态（寄存器/栈帧/PC），而 CSAPP 1.1 的上下文是解释规则（把同一段内存当指令、当 int、当 float、当协议字段）。

section-1.2-1.3-程序翻译与编译系统

1.2 程序被其他程序翻译成不同格式

从 hello.c 到能在机器上跑，要经过 编译系统（compilation system） 多步翻译 — 每一步都在换 上下文（源码 → 汇编 → 机器码 → 可执行）：

hello.c  ──预处理器──►  hello.i（展开 #include/#define）
         ──编译器──►    hello.s（汇编文本）
         ──汇编器──►    hello.o（目标文件，机器码 + 符号表）
         ──链接器──►    a.out（可执行，含 CRT、libc 等）
阶段 输入 输出 工具
预处理 .c .i cpp / gcc -E
编译 .i .s cc1 / gcc -S
汇编 .s .o as
链接 .o + 库 可执行 ld / gcc

静态链接 vs 动态链接： 可执行可嵌入 libc，或运行时加载 libc.so — HFT 生产常静态/部分静态以减少依赖与启动不确定性（→ Ch 7 链接）。

预处理器 vs 前端 / AST（你问的这个节点）

预处理器（cpp） 是工具链 第一步，在 编译器前端 之前跑 — 还没碰 AST、IR、语法分析。

预处理器 cpp 编译器前端（cc1 内）
输入 hello.c + # 指令 预处理后的 hello.i（纯文本，已无 #）
在干什么 文本级 替换/裁剪 理解 C 语法：词法 → 语法 → AST → 语义
懂不懂 C 语法 ❌ 不懂 ✅ 从这里才开始懂
产出 膨胀后的 .i AST → IR
典型工作 #include 粘贴头文件、#define 宏替换、#ifdef 条件编译 类型检查、符号表、控制流结构

流程位置：

hello.c
  │  cpp 预处理器     ← 只认 # 行；宏展开是「剪切粘贴 + 替换」
  ▼
hello.i（可能几千行，stdio.h 全展开）
  │  cc1 前端         ← 词法/语法分析 → AST；语义分析 → IR
  ▼
  … IR → 后端 → .s → .o → a.out

宏的例子（预处理器不管逻辑对不对）：

#define ADD(a,b) a+b
ADD(1,2)*3   // 预处理后 → 1+2*3  （不是 (1+2)*3）
             // 要到 AST/语义阶段，编译器才按运算符优先级理解这行
  • #include 找不到文件 → 预处理 就报错
  • 宏展开后 语法不合法（少分号、括号不匹配）→ 前端 才报错
  • 宏展开后 语法合法但逻辑错 → 可能 编译通过，运行才出问题 — HFT 里慎用复杂宏，优先 constexpr / 模板 / 配置文件

和 # 的关系： 预处理器 只处理以 # 开头的指令（以及宏展开结果）；普通 C 代码它 原样往下传，不做理解。

量化用法（你提到的）：

#define LIVE 0    // 回测
// #define LIVE 1  // 实盘 — 改一行或 -DLIVE=1 切换
  • 编译期切换路径，不改业务逻辑 — 类似「文本级 feature flag」
  • 生产更常见：CMake -D、config 头文件、或运行时配置；宏切换适合 零开销、编译期定死 的分支（如 NDEBUG）

实验：

gcc -E hello.c -o hello.i    # 看膨胀后的纯文本
gcc -save-temps hello.c      # 同时留下 .i .s .o，方便逐步对照

两套划分 粒度不同，不是互相矛盾 — 先记 CSAPP 四步搭框架，编译工程课再往 cc1 里面拆细。

编译工程课（龙书等）里的编译器本体：

源码 ──前端 FE──► IR（中间表示）──后端 BE──► 目标代码（汇编或 .o）
         │                              │
    词法/语法/语义                   IR 优化、指令选择、寄存器分配
    （跟语言有关）                   （跟 CPU 有关）

CSAPP / gcc 工具链 — 四步与谁对应：

CSAPP 步骤 工具 编译 FE/BE？ 在干什么
预处理 cpp ❌ 不算 FE/BE 文本层：#include / #define 展开 → .i
编译 cc1 ✅ FE + BE 都在这里 .i → 词法/语法/语义 → IR → 优化 → .s 汇编
汇编 as ⚠️ 编译器外、工具链内 .s 助记符 → .o 机器码 + 符号表 + 重定位条目
链接 ld ❌ 不算编译器 多个 .o + 库 → 解析符号、填地址、拼成可执行

一张总图（推荐记在脑子里）：

hello.c
  │  预处理 cpp          ← 编译系统，不是编译器 FE
  ▼
hello.i
  │  cc1 ┌─ 前端：C → AST/IR
  │      └─ 后端：IR → hello.s     ← 编译工程课主要啃这里
  ▼
hello.s
  │  汇编 as                       ← 独立工具，严格说不叫 FE/BE
  ▼
hello.o（有符号 printf 未定义）
  │  链接 ld                       ← 整合资源：符号解析、重定位、静/动态链
  ▼
a.out（能 execve 跑）

容易混的三句话：

  1. 「预处理、编译、汇编是前端」 — 粗记可以，但 严格说只有 cc1 里的前半是 FE；预处理是 cpp，汇编是 as，都不在龙书的 FE/BE 框里。
  2. 「链接是后端」 — 口语上指「更贴硬件、系统」，但 课本里链接器是编译器之外的 toolchain 组件；后端停在 吐出汇编或目标文件。
  3. gcc -S 只看到 .s — 因为 FE+BE 都在 cc1 里跑完了；IR 默认不落盘（-fdump-tree-* / -emit-llvm 才能看中间产物）。

和量化 / HFT 的直接相关度（先抓哪块）：

优先级 阶段 为何
🔴 先搞懂 链接 静/动态链、符号解析、undefined reference、启动是否拉 .so — 实盘环境一致性
🟡 其次 编译 (BE 优化) -O3 / LTO / -march=native 改 hot path 指令（→ Ch 5）
🟡 其次 汇编 .o 懂「有符号、有重定位」→ 链接时在填什么
⚪ 可后补 FE / IR 细节 写策略不手写 parser；啃编译工程时再深入
⚪ 常略过 预处理 除非用宏做 compile-time 配置

LTO 模糊边界： -flto 时编译只产 带 IR 的 .o，优化延到 链接阶段 才做 — 说明「编译 vs 链接」在现代工具链里可以交叉，但 概念上仍是 FE → BE → 链接 三条线。

IR、汇编、.o 分别是什么？（别混）

你问的核心：hello.o 里的指令能不能当 IR？ — 不能。

产物 是什么 跟硬件绑定？ 谁产的
IR（GIMPLE / LLVM IR） 半成品的 程序逻辑 — 变量、运算、控制流 ❌ 无关（同一份 IR 可喂 x86 / ARM 后端） 前端 + 中端优化（在 cc1 / clang 里）
hello.s 人类可读的 助记符（mov/call/ret） ✅ 已绑定目标架构 编译器后端（指令选择、寄存器分配之后）
hello.o 二进制机器码 + 符号表 + 重定位条目 ✅ 强绑定（x86 的 .o 不能给 ARM 用） as 汇编器（把 .s 编码成字节）

串起来（以 hello.c 为例）：

hello.c
  ──前端──►  IR          「通用逻辑半成品」— 不管 x86 还是 ARM
  ──后端──►  hello.s     「某 CPU 的汇编草稿」— 已选指令、已分配寄存器
  ──as───►   hello.o     「该 CPU 的机器码字节」— 但地址还没定（call printf 是占位）
  ──ld───►   a.out       「填好地址、拼好库」的可执行文件

三句话定锚：

  1. 前端 = 高级语言 → IR（只关心语法、语义对不对）
  2. 后端 = IR → 汇编（或有的编译器直接 IR → .o）；指令长什么样、用哪个寄存器，都在这里定
  3. as 汇编 = 把 已经定好架构的 .s 编码成 .o 里的二进制 — 不做优化、不改逻辑，只做「助记符 → 机器码字节」。口语上常把它算进 「贴硬件的后半段」，但严格说它是 独立工具，不是龙书里「编译器后端」代码的一部分

链接算不算后端？

说法 对不对
「链接也是对接硬件、产出能跑的 binary」 直觉上对
「链接是编译器 后端 的一部分」 课本里通常 ❌ — 链接器是 toolchain 里、cc1 之外 的程序
实用记法 后端 管到 .o 或 .s；链接 管 多个 .o 拼成一个（符号解析、重定位、静/动态链）— 和 CSAPP Ch 7 链接 一条线

前后端分离 + 量化： 同一份策略源码 → 前端产 IR（逻辑一次写对）→ 换 不同后端 / -march 出 Intel 机房版、ARM 版 — 不用重写 alpha 逻辑。实盘里更常做的是 同一架构上 -march=native + LTO，而不是真换 CPU 族。

看一眼 IR（可选实验）：

# GCC 内部 GIMPLE/RTL  dump（略丑）
gcc -fdump-tree-optimized -S hello.c   # 同目录生成 hello.c.003t.optimized

# Clang → LLVM IR（更「教科书」）
clang -S -emit-llvm hello.c -o hello.ll

为何要懂：

  • 优化 — -O2/-O3、LTO、PGO 改的是哪一阶段产物
  • 调试 — 崩溃栈、符号、行号对应哪层翻译
  • 链接错误 — undefined reference、ODR、ABI 不匹配
  • 安全/合规 — 可重现构建

量化场景映射 · 编译链 ↔ 策略生命周期

把 CSAPP 编译链和以后写策略/引擎对照记 — 同一条「从文本到跑起来」的链：

编译链环节 在干什么 量化 / DeFi 类比
预处理 #include / #define 文本替换、头文件展开 策略参数注入：把 MAX_POSITION、SYMBOL_LIST 从 config/宏写进编译期或代码
编译 .c → .s 高级逻辑 → 汇编 策略逻辑 → 可执行决策：信号计算、风控规则变成 CPU 会执行的指令
汇编 .s → .o 助记符 → 机器码 定稿 hot path：哪几段汇编是 tick 内必须跑完的
链接 .o + 库 → 可执行 拼模块、解析符号 集成：行情解码库 + 订单网关 + 日志 + 你的 alpha 链成一个 binary
加载运行 execve OS 映射进内存、跳 _start 实盘启动：pin 核、连 feed、进入主循环收行情 
config.yaml / 宏参数     ≈  预处理
策略 C++ 源码            ≈  .c
Release -O3 -march=native ≈  编译+汇编
链 libfix + libmd        ≈  链接
systemd 拉起 pinned 进程  ≈  execve 加载运行

和 1.1 的「上下文」： 源码里 price > threshold 是 C 语法上下文；编译后是 指令上下文；线上 tick 里是 协议字段上下文 — 三条链最终在 同一进程、同一 CPU 上会合。

动手实验 · hello.c 走一遍编译链

1. 准备最小程序

// hello.c
#include <stdio.h>
int main() {
    printf("hello, world\n");
    return 0;
}

2. 看 gcc 背后调了谁（推荐第一次做）

自测题

1. 从 hello.c 到可执行文件经过哪些阶段？每步的输入输出是什么？

四个阶段： 1. 预处理 .c→.i：展开 #include/#define，条件编译 2. 编译 .i→.s：语法分析→AST→IR→生成汇编文本 3. 汇编 .s→.o：汇编器翻译成机器码 + 符号表 4. 链接 .o+库→可执行：符号决议 + 重定位

gcc -E/-S/-c 分别停在预处理/编译/汇编后。

2. 预处理器和编译器前端的区别？预处理器懂 C 语法吗？

预处理器（cpp）不懂 C 语法，只做文本级替换/裁剪（#include 粘贴、#define 宏展开、#ifdef 条件编译）。编译器前端（cc1 内）才真正理解 C 语法：词法→语法→AST→语义分析→类型检查。预处理器在前端之前跑，输入 .c 输出 .i。

3. HFT 生产环境为什么倾向静态链接？

静态链接把 libc 等库直接嵌入可执行文件，减少运行时动态链接的不确定性（地址解析、PLT 跳转、symbol lookup），启动更快且依赖更可控。动态链接的优势是共享内存和升级方便，但 HFT 更看重确定性和低延迟。

1.4

section-1.4-处理器与hello程序生命周期

本节在讲什么： 前面 1.2–1.3 产出的 机器码已经躺在内存里；1.4 开始讲 CPU 怎么一条一条把它跑起来 — 这是「编译落地 → 硬件执行」的衔接点。

指令执行模型（简化流水线）

CPU 不断重复 五级（教科书最简模型，真实 CPU 更复杂 → Ch 4）：

取指 fetch → 译码 decode → 执行 execute → 访存 memory → 写回 write back
     ↑                                                              │
     └──────────────── PC 更新，取下一条 ────────────────────────────┘
阶段 在干什么
取指 按 PC 里的地址 从内存（经 cache）读出指令字节
译码 弄清这条指令 做什么、操作哪些寄存器/立即数
执行 ALU 算数/逻辑，或算有效地址
访存 若需 load/store，访问数据内存
写回 结果写回 寄存器（不写回内存，除非 store）

和 hello 串起来：

a.out 机器码映射进内存
  → PC 指向 _start / main 的第一条指令
  → 取指…写回 循环
  → call printf → … → write syscall
  → 直到 _exit

PC（程序计数器）— 你问的这个

对：PC 是 CPU 里的一个寄存器，里面存的是「下一条要执行的指令在内存中的地址」。

PC = 0x400500   ← 举例：虚拟地址（进程视角；细节 → Ch 9）
      │
      ▼
内存[0x400500]  →  取出一串字节  →  译码成「mov / add / jmp …」

PC 怎么变：

情况 PC 更新
顺序执行 PC ← PC + 当前指令长度（x86 变长指令，不是固定 +1）
分支/跳转 if / while / call 跳转指令把 目标地址 写入 PC — 程序流在这里拐弯

和策略逻辑的对应：

  • if (price > threshold) send_order(); 编译后 → 比较 + 条件跳转
  • CPU 通过 改 PC，在「继续等行情」和「跑进下单代码块」两条指令流之间切换 — 没有魔法，就是地址跳转

寄存器 vs 内存（量化为什么要「寄存器级优化」）

寄存器 主存 DRAM
速度 ~1 cycle 量级 ~几十~几百 cycle（未命中 cache 更惨）
容量 很少（十几~几十 general-purpose） GB 级
谁用 ALU 直接读写 load/store 指令间接访问

HFT 直觉：

  • 热路径里 反复从内存读行情字段 → 流水线常被 load 延迟 打断
  • 编译器 -O3 / 人工 把常用量攒在寄存器、减 indirection → 少访存（→ Ch 5）
  • 更大一层：cache 局部性 — 下节 1.5；真正「几十倍」差距往往来自 cache miss，不只是寄存器 vs DRAM 字面倍数

注意： 「冗余计算拖慢」有时是因为 多算了（占用执行端口），有时是因为 算完放内存又反复 load — perf 要分 frontend/backend stall（→ 06.6-Systems-Performance Ch6）

控制器 + ALU — 谁指挥、谁算题

CSAPP 1.4.1 把 CPU 拆成 寄存器 · ALU · 控制器 — 可以这么记：

部件 角色 类比
控制器 (Control Unit) 译码指令，发 控制信号 协调各部件 「指挥中心 / 拿题指挥的人」
ALU 做算术、逻辑运算 「只会算题的计算器」
寄存器文件 存操作数 & 结果，离 ALU 最近 计算器旁的草稿纸

一条指令怎么跑完 — add rax, rbx（x86-64 举例）：

1. 取指/译码   控制器读懂：要把 rax 与 rbx 相加，结果写回 rax
2. 发信号      → 寄存器堆：把 rax、rbx 送到 ALU 输入端
3. 发信号      → ALU：做加法
4. 等结果      ALU 输出 sum
5. 发信号      → 寄存器堆：把 sum 写回 rax
6. 更新 PC     指向下一条指令

控制器 ≠ 只做「一条接一条」： 现代 CPU 的控制/调度逻辑还会做（1.4 只点名字，深入 → Ch 4）：

优化 干什么 和量化的关系
流水线 多条指令 重叠 在不同阶段 提高吞吐；但 hazard 会 stall
乱序执行 OoO 不等前一条慢指令完成，先执行后面无依赖的 隐藏 load miss 延迟；热路径仍要 少依赖链
分支预测 在 if/跳转结果 未算出前， 猜 走哪条分支并 预取指令 猜对 → 低延迟；猜错 → pipeline flush，代价高

分支预测 + 条件下单：

if (price > threshold)   // 编译后：cmp + 条件跳转
    send_order();
  • CPU 在比较结果出来前，会 预测 「跳 / 不跳」，并先沿预测方向取指令
  • 策略里若 绝大多数 tick 都不下单（分支 高度偏一边、且模式稳定）→ 预测器容易 猜对 → 条件下单逻辑 更顺
  • 若分支 接近 50/50、无规律（像随机噪声）→ 预测失败多 → 热路径抖动

工程直觉（不是让你手写汇编，而是写代码时心里有数）：

  • 热路径 少深层 if-else 树；能 算完再分支 就别边 load 边连环跳
  • likely/unlikely（GCC）或 把 cold path 挪到函数外 — 帮编译器排布 + 帮预测器学模式
  • 真要抠：perf stat 看 branch-misses（→ Ch5、06.6-Systems-Performance Ch6）

1.4.2 运行 hello 程序

./a.out 是什么？shell 里敲的那一下在干什么

名词 含义
hello.c 你写的源码
a.out gcc hello.c -o hello 默认名；链接好的可执行文件，里面是 机器码 + 数据 + 元数据（ELF 格式）
./a.out 告诉 shell：当前目录 下的 a.out（. = 当前目录；/ 分隔；.. = 上一级）
为何不能裸打 a.out shell 只在 PATH 列出的目录里找命令；当前目录 通常不在 PATH 里（安全原因）

整条链（把 1.2–1.4 串起来）：

hello.c
  → gcc 四步 → a.out（磁盘上的可执行文件，还是「文件上下文」的比特）
  → shell 输入 ./a.out
  → fork + execve：OS 读 a.out，建进程，映射进内存
  → PC 从入口地址开始取指 → CPU 流水线跑 main/printf/…

你敲 ./hello 的那一刻 = 软件（shell/OS） 把程序的比特从 磁盘文件 搬进 内存，再交给 CPU — 正是 CSAPP 开篇「软硬件协同」的缩影。

HFT： 实盘 不用 shell 交互启动 — 固定 pin 的 daemon / systemd 直接 execve 策略 binary，省 shell、少一层 fork 交互延迟。

shell 阶段（软件）

  1. 用户在 shell 输入 ./hello（或 ./a.out）
  2. shell 解析路径 → fork 子进程 → execve 加载可执行文件
  3. OS 创建 进程，建立 虚拟地址空间，把代码段/数据段 映射 进内存
  4. 内核设好 PC（入口地址，如 _start） → 用户态跑 main → printf → _exit

硬件阶段（与 1.5 衔接）

  • 指令从内存经 cache 进入 CPU；控制器 译码，ALU 运算
  • printf → libc → write 系统调用 → 内核把字节送到终端

虚拟地址 — 你问「是不是扩大了存储？」

部分对，但不完整。 虚拟地址 不只是 「物理内存不够所以扩空间」。

作用 大白话

自测题

1. CPU 五级流水线的五个阶段是什么？PC 在哪个阶段更新？

取指(fetch) → 译码(decode) → 执行(execute) → 访存(memory) → 写回(write back)。PC 在取指后更新——取完当前指令，PC 指向下一条指令地址（顺序执行 +4/+8，分支则跳转）。

2. PC（程序计数器）里存的是什么？它是指向当前指令还是下一条？

PC 存的是下一条要执行的指令在内存中的地址（x86-64 中叫 RIP）。取指阶段从 PC 指向的地址读取指令字节，然后 PC 更新指向下一条。分支/跳转指令会修改 PC 的值。

1.5

section-1.5-高速缓存至关重要

为何 cache 是性能第一公民

  • CPU 与主存速度差距 持续拉大（「内存墙」）
  • 缓存 (cache) — 由 SRAM 构成的小而快的存储，自动保存主存中 最近用过 的数据副本
  • 典型三级：L1（指令/数据）→ L2 → L3（LLC）→ 主存

访存路径简图（越往下容量越大、越慢）：

CPU → L1 缓存 → L2 缓存 → L3 缓存(=LLC) → 内存控制器 → RAM(DRAM)
  • miss 逐级下探；L3 再 miss 才经 内存控制器 访问主存
命中 含义 延迟量级（直觉）
L1 hit 数据已在 L1 ~1 ns 级
L2/L3 hit 逐级更慢 数 ns ~ 十数 ns
cache miss 需访问 DRAM ~50–100+ ns
跨 NUMA 远程节点 DRAM 更慢 + 不一致风险

LLC · L3 · L3C 三种叫法（别打架）

写法 全称 命名角度
L3 Level-3 Cache 层级编号
L3C Level-3 Cache 同上 + Cache 缩写成 C（文档里偶见；L1C/L2C 也能写，少用）
LLC Last Level Cache 功能定位 — 片上最后一级、再 miss 下 DRAM
  • 主流三级机：L3 = L3C = LLC，同一块硬件
  • 两级机：可能 L2 = LLC
  • HFT / 服务器文档 偏好写 LLC（强调「最后一级」）；见 L3C 时按 L3 Cache 读即可，不是第三种缓存

L1 · L2 · L3 存什么、归谁（拆开背）

1. L1 = L1I + L1D（单核私有，必须拆）

CPU 同时干两件事：取指令（代码）与 读写数据（变量）— L1 直接拆两块，互不抢通路：

缩写 全称 存什么
L1I L1 Instruction Cache 只存指令（add/mov/call…）
L1D L1 Data Cache 只存数据（变量、数组、临时值）
  • 每核 各有一套 L1I + L1D
  • 容量最小、延迟最低

为何只有 L1 拆 I/D： 取指与访数 并行双路；L2/L3 不做双路并行取，混存可简化硬件。

2. L2（单核私有，统一混存）
存 指令 + 数据 混放
作用 接 L1 miss：L1I 未命中 → L2 取指；L1D 未命中 → L2 取数
归属 仅本核；他核不能直接读你的 L2
定位 次热缓冲区；比 L1 大、延迟略高、单位成本更低 
运算单元
├─取指令 → L1I ──┐
└─读写数据 → L1D ─┘
                  ↓ miss
                L2（指令+数据混存 · 本核私有）
                  ↓ miss
                L3 (= L3C = LLC)

3. L3 / L3C / LLC（全核共享，混存）
存 指令 + 数据混放
归属 全核共享（不是私有）
容量 片上最大；延迟在三级里最高
典型内容 各核 L2 淘汰后仍复用的行；多线程共享 变量（跨核常落这里） 
Core0 [L1I+L1D]→L2 ──┐
Core1 [L1I+L1D]→L2 ──┤
Core2 [L1I+L1D]→L2 ──┼── L3C/LLC 全核共享
Core3 [L1I+L1D]→L2 ──┘
                      ↓ miss
                    DRAM

金字塔：热度 · 容量 · 造价（只看 L1/L2/L3）

规则（上→下）： 越热越贵越快、容量越小；越冷越便宜越慢、容量越大。

        L1（约 32~64KB/核 · 最热 · SRAM 单位成本极高）  ← 每核私有
           ↓ miss
        L2（约 512KB~2MB/核 · 次热 · 成本适中）        ← 每核私有
           ↓ miss
        L3（约 8~64MB 共享 · 更低频共用 · 单位成本最低）← 全核共享 = LLC
           ↓ miss
        DRAM
层级 数据热度 容量 单位造价 硬件归属
L1 最高（热点） 最小（KB） 最贵 单核私有
L2 中等（次热点） 中等（MB 级/核） 中等 单核私有
L3 相对最低（次次热/共用） 最大（十几～几十 MB） 最便宜 全核共享

多核硬件结构（4 核 · 私有并联 + 共享 L3）

Core0：[L1I+L1D] → 私有 L2 ──┐
Core1：[L1I+L1D] → 私有 L2 ──┤
Core2：[L1I+L1D] → 私有 L2 ──┼── 公共 L3（LLC）
Core3：[L1I+L1D] → 私有 L2 ──┘
  • 单核内： L1 → L2 串行查找
  • 多核间： 多组独立 (L1+L2) 并联，共一块 L3

单次访存串行流程

  1. 查 L1 — 命中则返回（绝大多数热访问止步这里）
  2. L1 miss → 查同核 L2
  3. L2 miss → 查共享 L3 / LLC
  4. L3 miss → DRAM（经内存控制器）

极简内容表：

层级 全称缩写 存储内容 归属
L1I L1 Instruction Cache 仅指令 单核私有
L1D L1 Data Cache 仅数据 单核私有
L2 L2 Cache 指令+数据混 单核私有
L3C L3 Cache（= LLC） 指令+数据混 全核共享

再往下是 DRAM（物理内存）；再往外是磁盘。虚拟内存不是这塔上又一级 SRAM，而是 OS/MMU 在 DRAM + swap 之上造的 逻辑地址抽象（→ §1.7.3 · Ch 9）。

局部性（locality）— 程序行为决定 miss 率

  1. 时间局部性 — 刚访问过的，很可能很快再访问（循环变量、热结构体）
  2. 空间局部性 — 刚访问地址附近，很可能接着访问（数组顺序扫描）

编译器/程序员能做的： 数据结构布局、SoA vs AoS、对齐、避免冷路径污染 cache line。

HFT 高频场景：

  • Order book / ring buffer 顺序访问 → 空间局部性好
  • 指针 chasing、链表跳来跳去 → miss 多，P99 抖
  • 伪共享 (false sharing) — 两线程改同一 cache line 不同字段 → 行乒乓（→ Ch 6、Ch 12）
  • perf cache-misses / perf c2c — 生产验证（→ 06.6-Systems-Performance Ch 13）
  • LLC miss — 热路径上常比 L1/L2 miss 更贵；关注共享数据布局、避免无意义的跨核踩 LLC

缓存按行 (cache line) 管理

  • 常见 64 字节一行 — 读 1 字节可能整行载入
  • 预取 (prefetch) 硬件/软件可隐藏部分延迟

→ 全书深入：Ch 6 存储器层次结构

自测题

1. L1/L2/L3/LLC 的关系？为什么 HFT 文档偏好写 LLC？

L1→L2→L3 是按层级编号，越往下容量越大、延迟越高。LLC = Last Level Cache，强调功能定位——片上最后一级缓存，再 miss 就下 DRAM。主流三级机中 L3 = LLC。HFT 文档偏好 LLC 因为它直接决定 cache miss 后是否要访问 DRAM（~100ns vs ~1ns）。

2. cache miss 的延迟代价有多大？HFT 如何避免 tick 处理中的 cache miss？

L1 hit ~1ns，L2/L3 hit 数 ns~十数 ns，cache miss 访问 DRAM ~50-100+ ns，跨 NUMA 更慢。HFT 避免 miss 的手段：数据预取（prefetch）、数据紧凑布局（struct padding 控制）、cache line 对齐（__attribute__((aligned(64)))）、热数据放 L1（减少工作集）、NUMA 绑定。缺页 on tick 是灾难，用 mlock 锁内存。

section-1.6-存储器层次结构

存储层次（金字塔）

从快到慢、从贵到便宜、从小到大的 层次结构 (memory hierarchy)：

寄存器  →  L1 → L2 → L3(=LLC)  →（内存控制器）→  主存 DRAM  →  本地磁盘  →  远程存储
  ↑ 更快、更贵、更小                                                          ↓ 更慢、更便宜、更大

图注： 框越宽 ≈ 容量越大；L3 miss 后才经 内存控制器 访问 RAM。详细 L1I/L1D 拆分见 §1.5。

设计思想： 上层是下层的 cache — 磁盘缓存页在内存，内存缓存行在 LLC，…

层级 典型用途 HFT
寄存器 / L1–L2 热路径计算、order book 热行 单核布局主战场
LLC (L3) 跨核共享、仍落片上 共享结构、避免无谓踩 LLC
DRAM 工作集、mmap 行情缓冲 NUMA 绑定、大页
SSD 日志、回放、配置 顺序写、避免热路径 sync
网络存储 备份、研究数据 不在 tick 路径

与 1.5 的关系

  • 1.5 强调 CPU–cache–DRAM 路径延迟，并分清 L1/L2/LLC（→ §1.5）
  • 1.6 把 磁盘 I/O 纳入同一图景 — I/O 慢几个数量级，必须 异步 / 批量 / 摊销

HFT 实践：

  • 热路径：零磁盘（内存 ring、预分配）
  • 冷路径：批量落盘、单独线程 + 专用核
  • 基准：区分 memory-bound vs I/O-bound（→ 06.6-Systems-Performance Ch 12 基准测试）

→ Ch 6 · Ch 10 系统级 I/O

自测题

1. 存储器层次结构的核心思想是什么？

用层次结构弥补速度-容量-成本的三角矛盾。每层都是下一层的缓存：寄存器→L1→L2→L3→DRAM→磁盘→网络。上层小快贵，下层大慢便宜。程序访问有局部性（时间+空间），所以大部分访问命中上层，平均访问时间接近上层速度。

2. 时间局部性和空间局部性分别是什么？给一个 HFT 的例子。

时间局部性：刚访问过的数据很快会再被访问（如循环变量、热点计数器）。空间局部性：被访问数据附近的数据很快也会被访问（如数组顺序扫描、行情队列连续读取）。HFT 例子：tick 队列用连续内存数组而非链表（空间局部性 → prefetcher 自动预取 → cache miss 少）。

section-1.7-操作系统管理硬件

OS 在 应用程序与硬件之间 提供统一抽象，防止进程互相踩踏，并 更高效 地使用资源。

1.7.1 进程 (Processes)

  • 进程 = 程序的一次运行实例 — 独占（逻辑上）虚拟地址空间、文件描述符、权限上下文
  • 上下文切换 (context switch) — CPU 从进程 A 换到 B：保存/恢复寄存器、切换页表、刷新 TLB（有成本）
  • 并发假象 — 单核上多进程靠 时间片轮转；多核上真并行

HFT：

  • 热路径进程 固定 CPU affinity，减少迁移与 cache 冷启动
  • 与 housekeeping（日志、监控）分进程/分核（→ 14-HFT ch05）

1.7.2 线程 (Threads)

  • 线程 — 同一进程内多个执行流，共享 地址空间与文件描述符
  • 创建/切换通常比进程轻，但引入 竞态、锁、伪共享
  • 现代 Linux：N:M 线程模型（用户线程 ↔ 内核线程）

HFT：

  • 常见模型：单进程多线程 — 收包线程 / 策略线程 / 发单线程，用 无锁队列 或 单 writer 原则 分隔
  • 深入 → Ch 12 并发编程

1.7.3 虚拟内存 (Virtual Memory)

「虚拟」= 逻辑地址，不是一块名叫「虚拟」的内存条。 深入 → Ch 9

先分清两个概念

物理内存 (DRAM) 虚拟内存
是什么 主板上真实 内存条，有真实物理地址 OS + MMU 造出的 逻辑地址空间，不是独立硬件条
容量 有限（如 16G / 32G） 每进程一套独立的 虚拟地址；程序以为自己独占超大连续空间
谁用直接地址 硬件、内核页帧 用户程序只看见虚拟地址

为何发明（四个核心作用）

# 作用 白话
① 隔离 每进程独立完整 VA 空间 A 看不见 B；崩溃不易拖垮全系统。无 VM 则大家共物理地址，乱写互相覆盖
② 扩容 (swap) DRAM 不够时把冷页挪到硬盘 swap / 页面文件 程序仍读写原 VA，无感知；可用「逻辑内存」可大于内存条 — 大众最熟的那一档
③ 按需加载 分页：只用到的页进 DRAM 程序几百 MB，不必一次装完
④ 地址统一 程序员面对整齐 VA 碎片物理布局由 MMU 做 VA→PA 翻译，对软件透明

和缓存层级怎么叠（别混）

层 属性
L1 / L2 / LLC 片上 SRAM，缓存 物理内存里的数据副本（硬件）
DRAM 真实内存条（硬件）
虚拟内存 OS 逻辑抽象，覆盖 【DRAM + 硬盘 swap】 
CPU 看 VA → MMU(+页表/TLB) → PA → L1/L2/LLC → DRAM（或再经 OS 从 swap 装回）

极简例子（物理仅 8G）

  1. 浏览器进程拿到「完整」虚拟地址空间，以为独占大内存
  2. 实际可能只用约 1G 物理页
  3. 游戏、聊天各有自己 VA，互不冲突
  4. 内存紧时后台页进 swap，VA 不变，程序无感

关键术语

词 含义
MMU CPU 内地址翻译 / 缺页硬件
缺页 (page fault) 要访问的页不在 DRAM → 进内核；可能从 swap/文件装入
页 (page) VM 管理单位，常见 4KB（另有 2M/1G 大页）

HFT：

  • 热路径数据 mlock / 大页 / 预 fault，避免 tick 上 page fault
  • NUMA： 分配与访问同节点（→ Ch 9、06-linux-mm）

1.7.4 文件 (Files)

  • Unix 哲学：一切皆文件 — 普通文件、目录、设备、socket 都用 字节 I/O 接口（read/write）
  • 内核 VFS 统一不同文件系统与设备

HFT：

  • 行情/订单：socket 也是文件描述符 — epoll 等多路复用（→ Ch 10–11、12-UNP）
  • 配置文件：启动时读一次，不在热路径 open

→ OS 专章：06.6-Systems-Performance Ch 3

自测题

1. 操作系统通过哪两个抽象来管理硬件？

虚拟机抽象（进程 = CPU + 内存 + I/O 的虚拟视图）和文件抽象（I/O 设备、网络、磁盘统一为文件）。进程给程序一个独占 CPU/内存的幻觉；文件给程序一个统一的 I/O 接口（Unix 一切皆文件）。

2. 进程的虚拟地址空间为什么要分段（代码段/数据段/堆/栈）？

分段实现隔离和保护：代码段只读可执行（防止覆盖指令），数据段可读写，栈自动增长。不同段有不同的权限和生命周期管理。OS 通过页表把虚拟地址映射到物理页，段错误 = 访问了未映射或权限不对的虚拟地址。

section-1.9-重要主题-Amdahl与并发与抽象

1.9.1 阿姆达尔定律 (Amdahl's Law)

公式（加速比）：

[ S = \frac{1}{(1 - p) + \frac{p}{k}} ]

  • (p) — 可并行/可优化部分占整体时间的比例
  • (k) — 该部分加速倍数

直觉： 若 90% 时间在一个无法优化的串行段，整体最多快 10 倍，再优化剩下 10% 收益有限。

场景 教训
优化只占 1% 时间的函数 10× 整体几乎不变
行情解析占 60%，优化 2× 整体显著变快 — 先 profile 找 p

HFT： 端到端延迟 = 收包 + 解码 + 策略 + 发单 + 排队/内核/网卡。用 14-HFT ch10 或 span 分解找 最大 p，再动刀。

→ 方法论：06.6-Systems-Performance Ch 2 延迟分解

1.9.2 并发和并行 (Concurrency and Parallelism)

概念 含义
并发 (concurrency) 多个任务在时间上交替推进（可单核）
并行 (parallelism) 同一时刻多核同时执行
  • 线程级并行 — 多核跑多线程
  • 指令级并行 (ILP) — 单核流水线/超标量（→ Ch 4、Hennessy）

HFT： 并发正确性（锁、内存序）与并行吞吐（绑核、无共享）往往 同时 要 — Ch 12。

1.9.3 计算机系统中抽象的重要性

层层抽象隐藏细节，让上层 可组合、可推理：

C 源码 → ISA 指令集 → 微架构 → 逻辑门
进程/VM/文件 → syscall → 内核 → 硬件
socket API → TCP/IP → 以太网帧

好处： 换 CPU、换磁盘、换网卡，应用大多不用重写。
代价： 抽象 leak 时难排查（page fault、cache、tail latency）。

HFT 态度：

  • 默认用抽象（libc、内核栈）写非热路径
  • 热路径 selectively 打破抽象（ hugepage、mlock、busy poll、DPDK）— 知道自己在跳过哪一层

自测题

1. Amdahl 定律是什么？举例说明它在 HFT 优化中的意义。

Amdahl 定律：系统加速比受限于不可加速部分的比例。公式 S = 1/((1-p) + p/s)，p = 可并行比例，s = 并行加速比。HFT 例子：如果行情解析占总延迟 60%，即使把解析加速 10x，总加速只有 1/((1-0.6) + 0.6/10) = 1/0.46 ≈ 2.17x。必须找到占比最大的瓶颈优化。

2. 并发和并行的区别是什么？

并发(concurrency)：多个任务在逻辑上同时进行（通过调度交替执行），单核也能并发。并行(parallelism)：多个任务在物理上同时执行（多核/多 CPU）。并发是结构设计，并行是执行方式。HFT 既需要并发（多路行情同时处理）也需要并行（多核并行解码/风控）。
