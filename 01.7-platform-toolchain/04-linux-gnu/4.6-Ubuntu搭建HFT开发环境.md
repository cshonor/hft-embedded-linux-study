# 4.6 Ubuntu 24.04 从零搭建 HFT 开发环境（一次实测）

[← 4.5 Linux 上写 C 用什么](./4.5-Linux上写C用什么.md) · 下一节：[CH5 Windows ↔ POSIX 边界 →](../05-boundary/README.md)

## 本节讲什么

新拿到一台 x86 Ubuntu 机器（本节实测机：Lenovo V15 G5 IRL，Ubuntu 24.04 noble，
kernel 6.8.0-146），要一次性配齐四条线需要的工具：

```
① C/C++ 核心工具链     gcc / g++ / clang / gdb / cmake / ninja
② HFT 低延迟分析       perf / numactl / liburing / tuned
③ eBPF 与内核调试      bpftrace / BCC / libbpf / bpftool / crash
④ ARM 嵌入式交叉编译   arm-none-eabi / openocd / QEMU
```

`apt` 一条命令能装掉 95%，但 **noble 有一个真坑**：`bpftool` 没有独立包了。
本节把可复制的命令、踩坑证据、验证清单全部固化下来，下次配新机器照抄即可。

> **实测声明**：本节所有 apt 输出、版本号、报错原文均来自 2026-10-02 在
> Lenovo noble 上的真实安装过程（含报错截图核对），不是凭文档默写。

## 要点

### 一键安装（去掉 bpftool 的最终版）

```bash
sudo apt update && sudo apt upgrade -y && \
sudo apt install -y build-essential gcc g++ gdb gdb-multiarch gdbserver \
make cmake ninja-build meson pkg-config clang clang-format clang-tidy lld lldb \
git git-lfs curl wget unzip ccache \
linux-tools-common linux-tools-generic linux-tools-$(uname -r) \
numactl hwloc cpufrequtils tuned strace ltrace valgrind \
liburing-dev libaio-dev libnuma-dev htop iotop sysstat ethtool \
linux-headers-$(uname -r) bpftrace bpfcc-tools libbpf-dev libbpf-tools \
dwarves crash kexec-tools \
gcc-arm-none-eabi binutils-arm-none-eabi openocd stlink-tools dfu-util \
picocom minicom screen device-tree-compiler u-boot-tools \
qemu-system-arm qemu-user-static \
libncurses-dev bison flex libssl-dev libelf-dev bc lz4 rsync \
python3-pip python3-venv
```

⚠️ **复制时检查：续行符 `\` 后面不能有空格**，有空格会断行，
后面的行被当成独立命令执行（本次实测真踩到了）。

### 坑①：noble 没有独立的 `bpftool` 包

把 `bpftool` 写进安装清单会直接报：

```
虚拟软件包 bpftool 由下面的软件包提供：
  linux-tools-common 6.8.0-146.146
  linux-lowlatency-tools-common 6.8.0-31.31.1
请您明确地选择安装其中一个。
E: 软件包 bpftool 没有可安装候选
```

第一反应是"universe 源没开"，但实测诊断排掉了这个假设：

```bash
grep -rh "^Components" /etc/apt/sources.list.d/   # 输出里 universe multiverse 都在
apt-cache policy bpftool                          # 已安装:(无) 候选:(无) 版本列表为空
```

**版本列表为空 = 源里根本没有这个包。** 真实原因：Ubuntu 从 23.x 起砍掉了独立的
`bpftool` 包，二进制合并进 `linux-tools-common`（apt 只把它登记为"虚拟包"）。
这跟 Debian 12 有独立 `bpftool` 包不一样，跨发行版抄命令时要注意。

**解法**：装完 linux-tools 后把二进制软链出来——

```bash
ls /usr/lib/linux-tools-*/bpftool        # 实测位于 /usr/lib/linux-tools-6.8.0-146/bpftool
sudo ln -sf $(find /usr/lib -name bpftool -type f 2>/dev/null | head -1) /usr/local/bin/bpftool
bpftool version                          # 实测：bpftool v7.7.0, using libbpf v1.7
```

### 坑②：`crash` 等包在 universe 里

noble 默认安装可能只开 `main restricted`。用清华 tuna 镜像（deb822 格式）补全：

```bash
sudo sed -i 's/^Components: main restricted/Components: main restricted universe multiverse/' \
  /etc/apt/sources.list.d/ubuntu.sources && sudo apt update
```

本次实测的机器 universe 已开，但这条命令值得留在清单里——换一台全新机器就会用到。

### 关键包干什么用（HFT 视角）

| 包 | 用途 | HFT/嵌入式关联 |
|---|---|---|
| `linux-tools-*` | `perf` + `bpftool` 本体 | CPU 热点、cache miss、IPC 分析的第一入口 |
| `numactl` / `hwloc` | NUMA 拓扑与绑核 | 低延迟系统绑核绑内存的标准工具 |
| `liburing-dev` | io_uring 开发库 | 绕过 read/write 的异步 IO，行情接入常用 |
| `tuned` | 系统调优 profile | `sudo tuned-adm profile latency-performance` 一条切换低延迟档 |
| `ethtool` | 网卡队列/中断/ring buffer | 收包路径调优 |
| `bpftrace` / `bpfcc-tools` | eBPF 观测全家桶 | 内核态延迟归因（调度、页错误、系统调用） |
| `libbpf-dev` + `dwarves` | CO-RE 开发（pahole 在 dwarves 里） | 写可移植 eBPF 程序 |
| `crash` | 内核 dump 分析 | 内核 panic 事后分析 |
| `gcc-arm-none-eabi` | Cortex-M 裸机交叉编译 | STM32 labs（Mac 侧用 clang+lld，Linux 侧可以用这个） |
| `openocd` + `stlink-tools` | ST-Link 烧录/调试 | 板子到货后的真机链路 |
| `gdb-multiarch` | 多架构 gdb | 比 arm-none-eabi-gdb 新，一个 gdb 调所有架构 |

### 验证清单（本次实测全部通过 ✅）

```bash
echo "=== 编译器 ===" && gcc --version | head -1 && clang --version | head -1
echo "=== 构建/调试 ===" && cmake --version | head -1 && gdb --version | head -1
echo "=== HFT 性能 ===" && perf --version && numactl --version
echo "=== eBPF ===" && bpftool version | head -1 && bpftrace --version && ls -l /sys/kernel/btf/vmlinux
echo "=== 嵌入式 ===" && arm-none-eabi-gcc --version | head -1 && openocd --version | head -1
```

实测输出（Lenovo noble，2026-10-02）：

| 工具 | 版本 |
|---|---|
| gcc / g++ | 13.3.0 |
| clang | 18.1.3 |
| cmake / ninja / gdb | 3.28.3 / 1.11.1 / 15.1 |
| perf / numactl | 7.0.14 / 2.0.18 |
| bpftool / bpftrace | 7.7.0（libbpf 1.7）/ 0.20.2 |
| **BTF** | `/sys/kernel/btf/vmlinux` 存在（7.1 MB）|
| arm-none-eabi-gcc | 13.2.1 |
| openocd / gdb-multiarch | 0.12.0 / 15.1 |

### BTF 这一行为什么单独看

`ls /sys/kernel/btf/vmlinux` 有输出 = 内核带了 BTF 类型信息 = **CO-RE（一次编译
到处运行）的 eBPF 程序能跑**。这台 x86 noble 机器满足条件；而 Pi 5 的定制内核
`DEBUG_INFO_NONE=y` 没有 BTF，CO-RE lab 只能在这台 x86 机器上做。
**两台机器分工因此明确：eBPF CO-RE 开发 → Lenovo，内核模块/arm64 实测 → Pi 5。**

<details>
<summary>Q&amp;A：既然 Pi 5 工具链更新（gcc 14.2 / clang 19），为什么还要配一台 x86 Ubuntu？</summary>

三个理由：

1. **架构不同**：x86_64 是 HFT 行业的目标架构（交易所撮合、服务器全是 x86），
   perf/微架构行为（cache line、NUMA、超线程）必须在 x86 上学才对口；Pi 是 aarch64，
   适合嵌入式和内核机制学习。
2. **BTF**：Pi 内核没开 BTF，CO-RE 这条路走不通；noble 官方内核默认带。
3. **发行版差异**：Debian（Pi）和 Ubuntu 的包命名/打包策略有差异（本节的 bpftool
   就是例子），两台都摸过，踩坑面才完整。
</details>

<details>
<summary>Q&amp;A：为什么不装 llvm.sh 脚本里的 clang 19？</summary>

可以装（`wget https://apt.llvm.org/llvm.sh && sudo ./llvm.sh 19`），但本次没装。
noble 自带的 clang 18.1.3 对学习和绝大多数优化对比已经够用；等真遇到需要
clang 19+ 的特性（比如某些新的 sanitizers 或 C++23 完整支持）再装不迟。
**工具够用就停手，把精力留给 TLPI。**
</details>
