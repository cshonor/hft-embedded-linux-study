# 4.2 三道防线全部沉默：gcc 这边为什么"看着正常"

[← 4.1 GNU 工具链地图](./4.1-GNU工具链地图.md) · 下一节：[4.3 实测 gdb →](./4.3-实测gdb.md)

## 本节讲什么

[3.2](../03-macos-xcode/3.2-两套clang与版本矩阵.md) 已经给出四编译器矩阵：
Linux 上的 gcc 14.2 **和 Linux 上的 clang 19 一样，`-O2` 下正常跑完、输出正常**。
这一节补上更重要的另一半 —— **你手上所有常规武器，对这个 bug 全都不报警。**

## 要点

### 防线一：`-Wall -Wextra` —— 沉默

```console
$ gcc -g -O2 -Wall -Wextra -std=c11 ptrbug.c -o ptrbug_o2
$ echo $?
0                                    # ← 零警告零错误
```

为什么？因为**编译警告是局部分析**。`sum_n(const int *a, int n)` 内部，
编译器不知道 `a` 到底指向多长的数组 —— C 里数组传参退化成指针，长度信息在门口就丢了
（这正是 `01-c-language` 主线的核心痛点之一）。调用处 `sum_n(buf, 8)` 在同一翻译单元里
理论上能推出来，但 gcc 在 `-Wall -Wextra` 级别不做这个跨点分析。

### 防线二：`-fanalyzer`（gcc 14 内置静态分析器）—— 还是沉默

```console
$ gcc -fanalyzer -Wall -std=c11 -c ptrbug.c -o /dev/null
$ echo $?
0                                    # ← 同样一声不吭
```

这个是值得记住的教训：**静态分析器不是银弹**。它擅长栈溢出、双重释放、内存泄漏、
空指针解引用这类"符号 executepath 明确"的问题；面对"数组长度靠约定、越界只读不写"的
场景，它经常无话可说。

### 防线三：不同优化级别看运气 —— 恰好也沉默

| 优化级别 | gcc 14.2 的结果 |
|---|---|
| `-O0` | 正常输出，`exit=0` |
| `-O2` | 正常输出，`exit=0` |

但请务必对照 [3.2](../03-macos-xcode/3.2-两套clang与版本矩阵.md) 的表格：
**换成 clang 23 的 `-O2` 就是永久卡住。** gcc 这次没爆，不代表代码没问题，
只说明 gcc 在这个版本、这个优化级别上没把 UB 往坏的方向推。

### 真正有用的三样工具

| 工具 | 用法 | 对这个 bug 的效果 |
|---|---|---|
| **AddressSanitizer** | `-fsanitize=address -fno-omit-frame-pointer -g -O1` | ✅ 当场抓现行，报 `global-buffer-overflow`，并给出源码行列 |
| **UBSan** | `-fsanitize=undefined` | ⚠️ 对本例作用有限（全局缓冲溢出归属 ASan 管），但对有符号溢出、除零、越界偏移等有效 |
| **valgrind** | `valgrind ./app` | ✅ 能查（更慢） |

ASan 的实际输出（和你在 [03](../03-macos-xcode/3.2-两套clang与版本矩阵.md) 看到的一致）：

```
==ERROR: AddressSanitizer: global-buffer-overflow on address ...
READ of size 4 at ... thread T0
    #0 0x... in sum_n ptrbug.c:34
    #1 0x... in main ptrbug.c:49
SUMMARY: AddressSanitizer: global-buffer-overflow ptrbug.c:34 in sum_n
```

### 由此得到的一条工程纪律

> **CI 里至少要做到：gcc 与 clang 各编译一遍，且至少一遍带 ASan。**
>
> `gcc -fanalyzer` 之类分析器可以锦上添花，但不能替代"两个编译器 + sanitizer"。
> 理由在本节的实测里已经摆得很清楚了：单编译器 + 全开分析器，照样会对真 bug 举手放行。

## 与你的关系（HFT / 嵌入式）

- 低延迟项目常**刻意在 Release 开 `-O2/-O3` 且不带 sanitizer**（性能），
  这意味着 UB 在生产环境才有机会暴露 —— 所以**开发/测试流水线必须另有一条 sanitizer 链路**；
- 你在 Pi 上就能低成本做双编译器验证（gcc 14.2 + clang 19.1.7 都在），
  这在 Mac 上反而要多装一套，见 [3.1](../03-macos-xcode/3.1-Xcode工具链地图.md)。

<details>
<summary>Q&amp;A：`-D_FORTIFY_SOURCE` 管用吗？</summary>

它对**库函数**的越界写有效（`memcpy`/`sprintf` 等会被替换成 `__memcpy_chk`），
对**手写数组下标**无效。本例是 `s += a[i]`，编译器直接生成 load 指令，
不经过任何检查函数，因此 fortify 帮不上忙 —— 这又一次印证了同一件事：
**手写边界无银弹，要的是 sanitizer + 双编译器 + 代码里的显式长度参数。**
</details>
