# 5.6 内核模块要真 Linux 吗：WSL2 到底够不够（Pi 5 全程实测）

[← 5.5 MSVC 不吃 GNU 扩展怎么办](./5.5-MSVC不吃GNU扩展怎么办.md) · [CH5 边界](./README.md)

## 本节讲什么

顺着上一节的思路往下问：既然要看 GNU C 和内核风格代码，那**内核模块实验**这一步呢？

常见的说法是"WSL2 不行，能编 .ko 但 insmod 不进去，必须上虚拟机或物理机"。
这话对了一半 —— **对的是结论（做驱动实验确实不该用 WSL2），错的是理由。**

这一节做两件事：

1. 在真机（你的 Raspberry Pi 5）上把 `make → insmod → dmesg → lsmod → rmmod` 完整跑一遍，
   每一步都贴真实输出；
2. 把"WSL2 到底差在哪"讲准 —— 差的不是 insmod 这一个命令，而是**三件别的事**。

## 要点

### 一、先把那份结论逐条核一遍

| 原话 | 判定 | 依据 / 修正 |
|---|---|---|
| 内核用 GCC + 大量 GNU C 扩展写成 | ✅ 对 | 补充：现在 `make LLVM=1` 可以用 clang 编内核，但**构建环境仍在 Linux** |
| 内核不支持 MSVC，也不用 MinGW | ✅ 对 | MSVC 无 `<linux/*.h>`，且内核 Kbuild 依赖 GNU 工具链行为 |
| 语句表达式 / 指定初始化 / `__attribute__` 是内核日常 | ✅ 对 | —— |
| 零长数组 `char buf[0]` 是内核天天在用 | ⚠️ **过时** | 见下文"一处需要更新的事实" |
| `__STRICT_ANSI__` 属于 GNU 扩展 | ❌ 错 | 已在 [5.5](./5.5-MSVC不吃GNU扩展怎么办.md) 纠错：它是严格模式下的**指示宏**，MSVC 从不定义它 |
| 驱动代码依赖 `<linux/xxx.h>`，Windows 没有 | ✅ 对 | 这不是语法问题，是**整个 API 体系不在** |
| **WSL2 不能加载自己写的 .ko** | ⚠️ **不准确** | 准确说法：默认安装的 WSL2 缺"与运行内核精确匹配的模块集/build tree"；把模块 VHDX 配好之后 insmod 走得通。见第三节 |
| 做驱动实验要用 VM 或物理机 | ✅ 对 | 但理由不是 insmod，见第四节 |

#### 一处需要更新的事实：零长数组已经被内核"退役"了

2020 年 Linus 合入 `flexible-array-member-5.7-rc2` 时，pull request 里写得很直接：

> "Kernel code should always use *flexible array members* for these cases.
> **The older style of one-element or zero-length arrays should no longer be used.**"

同一批工作从 5.7 持续到 6.x（含 UAPI 头文件树级替换），原因也写在 kernel.org 的
`process/deprecated.rst` 里：

- `sizeof(zero_len_array)` 恒等于 0，`CONFIG_FORTIFY_SOURCE` / `UBSAN_BOUNDS` 无法正确分析数组边界；
- 柔性数组成员 `buf[]` 是不完整类型，误用 `sizeof` 会在**编译期**报错。

所以现在的正确心智模型是：

| 写法 | 出处 | 内核现状 |
|---|---|---|
| `char buf[1];` | 古老的"单元素数组"技巧 | ❌ 废弃 |
| `char buf[0];` | **GNU 扩展** | ❌ 已在主线被系统性替换掉 |
| `char buf[];` | **C99 标准** | ✅ 内核现在的唯一推荐写法 |

> 这是个很好的例子：GNU 扩展不是越"老"越正宗，内核自己也在往标准 C 退。
> 学的时候要**认得出** `[0]`（读老代码一定会遇到），但**不要自己再写**。

### 二、真机实测：完整的内核模块闭环（Raspberry Pi 5）

你的 Pi 天生是最好的实验对象。先看环境是否具备三个前提：

```console
$ uname -r
6.18.39+rpt-rpi-2712

$ ls -d /lib/modules/$(uname -r)/build
/lib/modules/6.18.39+rpt-rpi-2712/build          ← 内核构建树存在

$ dpkg -l | grep linux-headers
linux-headers-6.18.39+rpt-common-rpi   1:6.18.39-1+rpt1
linux-headers-6.18.39+rpt-rpi-2712     1:6.18.39-1+rpt1

$ zcat /proc/config.gz | grep -E "CONFIG_MODULES|CONFIG_MODULE_UNLOAD|CONFIG_MODVERSIONS"
CONFIG_MODULES=y              ← 支持可加载模块
CONFIG_MODULE_UNLOAD=y        ← 支持卸载（否则只能 insmod 不能 rmmod）
CONFIG_MODVERSIONS=y          ← 启用符号 CRC 校验（会写进 vermagic）
```

**没有出现 `CONFIG_MODULE_SIG`** —— 说明这台机器不强制模块签名，自编模块可以直接加载。
这一点不是每台 Linux 都成立（开了 Secure Boot 的发行版会拦），值得先看一眼。

示例模块的源码和 Makefile 在 [demo/hello-mod/](../demo/hello-mod/)。编译：

```console
$ make
make -C /lib/modules/6.18.39+rpt-rpi-2712/build M=/home/wzp/hello-ko modules
  CC [M]  hello.o
  MODPOST Module.symvers
  CC [M]  hello.mod.o
  CC [M]  .module-common.o
  LD [M]  hello.ko

$ file hello.ko
hello.ko: ELF 64-bit LSB relocatable, ARM aarch64, version 1 (SYSV)
```

注意它**不是可执行程序，是 relocatable 目标文件** —— `.ko` 要由内核在加载时做重定位和符号绑定，
所以"—是什么格式"这一层就和普通的 `a.out` 完全不同。

加载之前先看模块自带的身份信息：

```console
$ modinfo hello.ko | grep -E "^(filename|license|vermagic|depends)"
filename:  /home/wzp/hello-ko/hello.ko
license:   GPL
depends:
vermagic:  6.18.39+rpt-rpi-2712 SMP preempt mod_unload modversions aarch64
```

**`vermagic` 这一行是整个问题的核心**，下一节展开。

加载 + 看日志 + 三重核对：

```console
$ sudo dmesg -C                      # 清 ring buffer，保证看到的都是本次的
$ sudo insmod hello.ko; echo "exit=$?"
exit=0

$ dmesg | tail -3
[1670251.974689] hello_ko: module loaded, running on real Linux

$ lsmod | grep hello
hello                  49152  0

$ cat /proc/modules | grep hello | cut -d' ' -f1,2,3
hello 49152 0

$ ls /sys/module/hello
coresize  holders  initsize  initstate  notes  ...
```

卸载，并确认三处都干净：

```console
$ sudo rmmod hello; echo "exit=$?"
exit=0
$ dmesg | tail -2
[1670251.974689] hello_ko: module loaded, running on real Linux
[1670276.473644] hello_ko: module unloaded

$ lsmod | grep hello        # 空
$ cat /proc/modules | grep hello   # 空
$ ls -d /sys/module/hello   # 目录已消失
```

这就是**只有真 Linux 才走得通的那一步**：`insmod` 走的是 `init_module(2)` 系统调用，
需要一个真的内核接住它。Windows 上没有这个 syscall，MSVC 也产不出 relocatable 的
`.ko`（ELF 重定位 + `module_layout` 符号版本校验全部对不上）。

### 三、true 门槛不是 insmod，是 build tree 和 vermagic

回到 `vermagic: 6.18.39+rpt-rpi-2712 SMP preempt mod_unload modversions aarch64`。

内核加载模块时比对的是：

| 要比的东西 | 从哪来 | 不匹配会怎样 |
|---|---|---|
| 内核版本号 + local version | `uname -r` | ` disagrees about version of symbol module_layout` |
| 关键配置（`preempt` / `mod_unload` / `modversions`） | `.config` | 同上，直接拒绝加载 |
| 架构 | `aarch64` / `x86_64` | 文件格式本身就不对 |
| 导出符号的 CRC（开了 `MODVERSIONS` 时） | `Module.symvers` | `Unknown symbol ...` |

所以要编出一个**能被当前正在运行的内核接受**的 `.ko`，你必须同时有这三样：

1. 与运行内核**完全同一份源码**（不是"同版本号就行"，`local version`、补丁都要一致）；
2. 与运行内核**完全同一份 `.config`**；
3. **相同或兼容的编译器**。

**这就是 WSL2 默认状态下真正的缺口**：它不随发行版提供 `/lib/modules/$(uname -r)/build`，
所以你连门槛都摸不到 —— 表现出来就是"编不出 / insmod 报错"。

但这个缺口是**可填的**，而且微软已经把它做成了官方流程。三条证据：

**(1) 官方 `.wslconfig` 支持 `kernelModules` 键**（Microsoft Learn《Advanced settings configuration in WSL》原文）：

```ini
[wsl2]
kernel=C:\\temp\\myCustomKernel
kernelModules=C:\\temp\\modules.vhdx     ← "Specify the modules VHD for the custom Linux kernel"
```

**(2) 微软自己的内核仓库给出了打包脚本与完整步骤**
（`microsoft/WSL2-Linux-Kernel` 的 `README-Microsoft.WSL2`，2026-07-31 刚更新过 "custom kernel packaging documentation"，
同期合入 `feature/wsl-module-script/6.18`）：

```bash
make KCONFIG_CONFIG=Microsoft/config-wsl
make INSTALL_MOD_PATH="$PWD/modules" modules_install
make headers_install INSTALL_HDR_PATH="$PWD/headers"
# → stage 到 $release 目录 → 打成 ext4 → qemu-img convert -O vhdx modules.vhdx
#   仓库自带 Microsoft/scripts/gen_modules_vhdx.sh 一步生成
```

**(3) 版本要求**：`kernelModules` 需要 **WSL ≥ 2.5.1**。更早的 2.4.x 会把它当布尔值解析，
直接报 `Invalid boolean value 'C:\modules.vhdx' for key 'wsl2.kernelModules'`。
另外目前**只支持单个 VHDX**，多个模块场景得先合并成一个。

社区（microsoft/WSL discussion #12784）里也确认了这个区分：

> "You can compile out of tree any module for the kernel. You don't need to recompile a new kernel.
> However … you need the same sources, the same configuration and the same compiler."
> —— 翻译：**限制在打包与配套资料，不在"能不能加载"。**

> ⚠️ 关于 WSL 的部分我**没有在真实 Windows 上复跑过**（你这台环境里没有 Windows），
> 依据是微软官方文档 + 内核仓库 README + 官方 issue/discussion。上面的 Pi 部分则是全程实测。

### 四、WSL2 真正的短板在哪：不是 insmod，是设备和硬件

这一条比上一条重要得多。就算你把 `modules.vhdx` 配通、`insmod hello.ko` 跑成功了，
**做不了的事情还是一大堆**：

| 你要练的东西 | WSL2 | 真 Linux（Pi / VM） |
|---|---|---|
| 用户态 GNU C demo、看预处理 `.i`、看告警 | ✅ 够 | ✅ |
| `hello.ko` 这种纯软件模块 | ⚠️ 配好 VHDX 后可行 | ✅ |
| 字符设备 + `/dev/` + `file_operations` | ⚠️ 可行（但没有真实硬件语义） | ✅ |
| **设备树（DT）、platform_driver、DT overlay** | ❌ WSL2 没有设备树，没有 `.dtb` 给你的模块匹配 | ✅ |
| **GPIO / SPI / I²C 真实外设** | ❌ 虚拟机的硬件是假的，没有可操作的控制器 | ✅ Pi 有 40pin 排针 |
| **中断号 / `request_irq` 的真触发** | ❌ | ✅ |
| 每次系统更新后的维护成本 | ❌ 每次 `wsl --update` 换内核，模块要全部重编 | 正常 |

**所以结论对，理由要换。** "WSL2 不够"的真正原因是：**它是一个没有设备树、没有真实外设、
内核还随时会被 `wsl --update` 换掉的沙箱** —— 而不是"`insmod` 这个命令被禁了"。

对你的学习路线（`09-device-drivers-dt`：字符设备 → platform driver → 设备树 → GPIO）
来说，platform driver 之后的部分在 WSL2 里**连 `probe()` 都进不去**，因为没有任何东西能 match 上你的 `of_match_table`。

### 五、顺带一个新概念：out-of-tree 必然让内核"变脏"

加载自己的模块后，你会看到一个以前没见过的东西：

```console
$ cat /proc/sys/kernel/tainted
4096
```

按 kernel.org 官方 `tainted-kernels` 文档的表解码：`4096 = bit 12 = 'O'`
—— **external-built ("out-of-tree") module was loaded**。

实测验证它是 sticky 的（**卸载也清不掉**）：

```console
$ cat /proc/sys/kernel/tainted           # insmod 之后
4096
$ sudo rmmod hello
$ cat /proc/sys/kernel/tainted           # 卸载之后，还是
4096
```

位分解输出确认只有 bit 12 被置位：

```
  bit 12 被置位（值 4096）
```

这有两个实际后果：

1. **别慌**：写自己的驱动模块时 `tainted=O` 是常态，`MODULE_LICENSE("GPL")` 也消不掉它 ——
   GPL 只影响 bit 0（proprietary），跟 bit 12 是两回事；
2. **要 reboot 才干净**：上报 bug 给上游时，人家会先看这个值。想复现"干净内核"的问题，
   只能重启后在没加载过任何 out-of-tree 模块的情况下复现。

### 六、落到你这边的行动结论

你之前给的方案是"Windows + VS2022 编辑 → WSL2 练 GNU C → 再搞台 Linux 虚拟机做驱动"。
就你的现状，这条链要改两处：

1. **VS2022 这一段用不上** —— 它是 Windows-only，而你手上没有 Windows；VS for Mac 已退役（见 [1.0](../01-common-core/1.0-先分清三个产品.md)）。
   Mac 侧的编辑器方案见 [4.5 Linux 上写 C 用什么](../04-linux-gnu/4.5-Linux上写C用什么.md)。（编辑/编译分离的原则仍然成立）
2. **第三台虚拟机不用再买了** —— 你的 Raspberry Pi 5 已经替它把活干了：

```
Debian 13 (trixie) aarch64 / kernel 6.18.39+rpt-rpi-2712
linux-headers-6.18.39+rpt-rpi-2712      已装 ✅
CONFIG_MODULES=y / MODULE_UNLOAD=y      已开 ✅
CONFIG_MODULE_SIG 未启用                      自编模块可直接加载 ✅
gcc 14.2.0 + clang 19.1.7               双编译器（正好满足"两个编译器"纪律）
40pin GPIO / DT / SPI / I²C             真实外设 ✅
```

比虚拟机还多一层：**它能真的点灯**。虚拟机里写 GPIO 驱动是模拟出来的，Pi 上 `probe()` 进来
然后拉高 GPIO17 是真的会有 3.3V。

**一句话记法**（在你那个版本上修订）：

> GNU C 语法：WSL2 够用。
> `insmod` 本身：WSL2 默认缺 build tree，配好 `modules.vhdx` 后**技术上走得通**。
> 设备树 / platform driver / GPIO / 中断：**只有真 Linux 才行**。
> 而你手上那块 Pi，已经是"真 Linux + 真实外设"的最优解。

## 代码自测

在 Pi 上（或任何装了 headers 的真 Linux）：

```bash
mkdir -p ~/hello-ko && cd ~/hello-ko
# 把 demo/hello-mod/ 里的 hello.c 和 Makefile 放进来
make                      # 应该看到 LD [M] hello.ko
modinfo hello.ko          # 核对 vermagic 是否等于 uname -r 那一串
sudo dmesg -C
sudo insmod hello.ko && dmesg | tail -3
lsmod | grep hello
cat /proc/sys/kernel/tainted          # 应为 4096（bit 12 = out-of-tree）
sudo rmmod hello && dmesg | tail -1
cat /proc/sys/kernel/tainted          # 仍为 4096 —— taint 不可清除
```

如果 `make` 报 `/lib/modules/$(uname -r)/build: No such file or directory`，
说明缺的就是第三节讲的那个 build tree：

```bash
sudo apt install linux-headers-$(uname -r)     # Debian / Ubuntu 系
```

<details>
<summary>Q&A：这两个说法到底差在哪</summary>

**Q：WSL2 到底能不能 insmod 自己写的 ko？**

A：**默认安装的不行** —— 它不提供与运行内核匹配的内核构建树（`/lib/modules/$(uname -r)/build`），
你连编都编不出来。但这是"配置缺口"，不是"架构封死"：官方文档支持在 `.wslconfig` 里写
`kernelModules=C:\...\modules.vhdx`（需 WSL ≥ 2.5.1），微软的内核仓库还自带
`Microsoft/scripts/gen_modules_vhdx.sh` 一步生成它。

**Q：那为什么结论仍然是"做驱动实验别用 WSL2"？**

A：因为真正的短板不在 insmod 这个命令，而在**有没有东西可驱动**。WSL2 没有设备树、
没有 GPIO 控制器、没有真实外设，`platform_driver` 的 `probe()` 永远不会被调用；
而且 `wsl --update` 一升级内核，所有模块要全部重编。

**Q：taint=4096 要不要管？**

A：不用管，这是 out-of-tree 模块的常态（bit 12 = `O`）。但要知道它**卸载也不清除**，
想回到干净状态只能重启 —— 上报上游 bug 时对方会查这个值。

</details>
