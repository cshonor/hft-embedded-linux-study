# 5.1 MSVC 的 C 标准到底支持到哪

[← CH5 边界](./README.md) · 下一节：[5.2 头文件与 socket →](./5.2-两套世界头文件与socket.md)

## 本节讲什么

MSVC 从 VS 2019 16.8 起正式支持 C11/C17，但**大面积不支持 C11 的可选特性**。
这一节把这些"明确不做"的东西列清楚 —— 它们全都有**官方原话**支撑，不是我的推测。

## 要点

### 官方支持的起点

Microsoft C++ Team 博客（[C11 and C17 Standard Support Arriving in MSVC](https://devblogs.microsoft.com/cppblog/c11-and-c17-standard-support-arriving-in-msvc/)）：

> C11 and C17 are becoming supported language versions in the MSVC compiler toolset
> starting with Visual Studio 2019 version 16.8 Preview 3!
> For many years Visual Studio has only supported C to the extent of it being required for C++.

两件事值得注意：

1. **起点是 VS 2019 16.8**，之前 MSVC 的 C 支持只是"C++ 要求的那部分"（即 C89 的子集）
2. `/std:c11` / `/std:c17` 会**隐式打开 `/Zc:preprocessor`**（一致性预处理器）

`__STDC_VERSION__` 的值：`/std:c11` → `201112L`，`/std:c17` → `201710L`。

### 官方明确不做的清单

Microsoft Learn 的 [`/std`](https://learn.microsoft.com/cpp/build/reference/std-specify-language-standard-version) 文档，原话：

> The compiler doesn't support most optional features of ISO C11.
> ……
> There's no conforming multithreading, atomic, or complex number support.
> `aligned_alloc` support is missing, because of the Windows heap implementation.
> The alternative is to use `_aligned_malloc`.
> DR 400 support is currently unimplemented for `realloc` because this change would break the ABI.
> Variable length array (VLA) support isn't planned.

翻译成清单：

| 特性 | MSVC 状态 | 你在代码里怎么检测 | 替代方案 |
|------|-----------|-------------------|----------|
| **VLA**（变长数组） | ❌ **明确不打算支持** | `__STDC_NO_VLA__` == 1 | `malloc` / 固定长度数组 |
| **`<threads.h>`** | ❌ 不支持 | `__STDC_NO_THREADS__` == 1 | `_beginthreadex` / C++ `std::thread` |
| **`_Atomic`** | ❌ 不合标 | `__STDC_NO_ATOMICS__` == 1 | `Interlocked*` / C++ `std::atomic` |
| **`_Complex`** | ❌ 不支持 | `__STDC_NO_COMPLEX__` == 1 | 自己定义结构体 |
| **`aligned_alloc`** | ❌ 缺 | —— | **`_aligned_malloc`** |
| **`realloc` DR 400** | ❌ 未实现 | —— | 注意 `realloc(p, 0)` 的行为不再 UB |

> 这四个 `__STDC_NO_*__` 宏在 MSVC 编译 C 且指定 `/std:c11` 或 `/std:c17` 时**会被定义为 1**
> （Microsoft Learn「预定义宏」页）。这其实是件好事 —— 你可以用预处理判断它们，做条件编译。

### 为什么明确拒绝 VLA（官方理由）

C++ Team 博客的原文：

> Variable length arrays are generally less efficient than comparable fixed sized arrays,
> and generally inefficient compared to equivalent `malloc()`, when safely and securely implemented.
> VLAs provide attack vectors comparable to those of the infamous `gets()` —
> deprecated and destined to removal — for opportunities of "shifting the stack" and other exploits.
> For these reasons we intend not to support VLAs as an optional feature in C11.

要点：微软认为 VLA 既低效、又提供类似 `gets()` 的栈攻击面，所以**无意支持**。

> **这是个值得你记住的判断分歧**：VLA 在 Linux/GNU C 里是常用写法
> （尤其内核代码和网络包处理里 `char buf[len]` 的写法），
> 但在 MSVC 里编译不过。**跨平台代码必须回避 VLA。**

### 三工具链对照：同一份 C11 代码能否通过

| 特性 | MSVC (`/std:c17`) | clang (`-std=c17`) | gcc (`-std=c17`) |
|------|-------------------|--------------------|------------------|
| VLA | ❌ | ✅ | ✅ |
| `<threads.h>` | ❌ | ✅（取决于 libc，glibc 2.28+） | ✅（glibc 2.28+） |
| `_Atomic` | ❌ | ✅ | ✅ |
| `_Complex` | ❌ | ✅ | ✅ |
| `aligned_alloc` | ❌（用 `_aligned_malloc`） | ✅ | ✅ |
| `_Generic`、`_Static_assert`、`_Alignas`、`_Alignof` | ✅ | ✅ | ✅ |
| `_Pragma`、`restrict` | ✅ | ✅ | ✅ |

> 注意 clang/gcc 侧也有自己的坑：`-std=c17`（严格）会**禁用 GNU 扩展**，
> 而 `-std=gnu17` 才会开 `__attribute__`、`typeof`、语句表达式等 ——
> 内核代码用的是 `gnu11`/`gnu17`。详见 [01-c-language/05 嵌入式与内核](../01-c-language/05-embedded-kernel-practice/)。

### 一个实用建议：怎么写出三边都能过的代码

| 做法 | 说明 |
|------|------|
| 回避 VLA | 用 `malloc` + 显式 `free`，或固定上限数组 |
| 用 `_ Static_assert` / `_Alignof` 等 C11 **必需**特性 | 三边都支持 |
| 原子/线程用 C++11 的 `std::atomic` / `std::thread` | 如果项目允许 C++，这是最省事的跨平台答案 |
| 对齐分配包一层宏 | `#ifdef _MSC_VER → _aligned_malloc #else → aligned_alloc` |
| 用 `__STDC_NO_VLA__` 等宏做特性检测 | 而不是用 `#ifdef _WIN32` 猜平台能力 |

最后一条尤其重要：**检测"有没有这个能力"，而不是"是不是这个平台"**。
`_MSC_VER` / `_WIN32` 判断的是平台，而将来 MSVC 可能支持某个特性时你的代码就白限了；
`__STDC_NO_VLA__` 判断的是能力，永远正确。
