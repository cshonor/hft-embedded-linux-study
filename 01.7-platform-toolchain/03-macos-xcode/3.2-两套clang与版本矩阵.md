# 3.2 实测：同一份 bug，四个编译器给出三种答案

[← 3.1 Xcode 工具链地图](./3.1-Xcode工具链地图.md) · 下一节：[3.3 实测 lldb →](./3.3-实测lldb.md)

## 本节讲什么

上一节留下一个疑问：「Apple clang 21」和「LLVM clang 23」是同一个东西换个版本号吗？
**不是。** 这一节用一个真实 bug 把它们钉死。

素材是 `demo/ptrbug.c`（源码见下一）：一个**故意越界读**的求和函数。
它不崩、不报错，在 `-O0` 下输出完全正常。我们把同一份源码喂给四个编译器：

| 编号 | 编译器 | 平台 |
|---|---|---|
| ① | Apple clang 21.0.0（Xcode 27） | macOS arm64（本机） |
| ② | LLVM clang 23.1.0（micromamba `cdev`） | macOS arm64（本机） |
| ③ | LLVM clang 19.1.7（Debian） | Linux aarch64（你的 Pi） |
| ④ | gcc 14.2.0（Debian） | Linux aarch64（你的 Pi） |

## 要点：实测矩阵

`-O0`（不开优化）—— **四份全部一致，全部输出完整、exit=0**：

```
sizeof(buf)      = 16 bytes, 4 elems
sum_n(buf, 4)   = 100
sum_n(buf, 8)    = 100   <-- 越界读，值不确定但通常不崩
buf=0x...        buf[0]=10  *(p+3)=40
```

`-O2`（开优化）—— **开始分裂**：

| 编译器 | ② clang 23.1.0 (macOS) | ① Apple clang 21.0.0 (macOS) | ③ clang 19.1.7 (Linux) | ④ gcc 14.2.0 (Linux) |
|---|---|---|---|---|
| 是否能跑完 | ❌ **永久卡住** | ✅ 正常退出 | ✅ 正常退出 | ✅ 正常退出 |
| 输出行数 | 只到第 1 行 | 4 行完整 | 4 行完整 | 4 行完整 |
| 加��后怎么办 | SIGKILL 强杀 | exit=0 | exit=0 | exit=0 |

### 证据一：clang 23 生成了什么

```console
$ clang -O2 -std=c11 -S ptrbug.c -o ptrbug_o2.s
$ sed -n '20,24p' ptrbug_o2.s
	bl	_printf
LBB0_1:                                 ; =>This Inner Loop Header: Depth=1
	b	LBB0_1                          ; ← 跳回自己，无限空循环
```

`main` 里**只剩一次 printf 和一个死循环**。其余所有代码，包括 `sum_n` 的调用，
全部消失了。推理链条是：

```
编译器看见 sum_n(buf, 8) 越界 → 这是 UB
    ↓
UB 在标准里意味着"任何事都可能发生"，所以优化器有权假定它从不发生
    ↓
这条路径不可达 → 后面的所有 printf 都不可能执行 → 全部删除
    ↓
但万一真的执行到那个"不可能到达"的点呢 → 编译器给个兜底：跳到自身循环
```

### 证据二：同一台 Mac 换个编译器就不一样

```console
$ /Applications/Xcode.app/.../usr/bin/clang -isysroot ... -O2 ptrbug.c -o ptrbug_ac21
$ ./ptrbug_ac21
sizeof(buf)      = 16 bytes, 4 elems
sum_n(buf, 4)   = 100
sum_n(buf, 8)    = 100   <-- 越界读，值不确定但通常不崩
buf=0x10226c000  buf[0]=10  *(p+3)=40
[正常退出]

$ grep -cE "^\s+b\s+LBB0_1" ac21.s
0                                        # ← 没有自我跳转
```

**关键结论：** ① 和 ② 在同一台机器、同一个 CPU、同一个 OS 上，
差别只有编译器版本（Apple clang 21 vs LLVM clang 23）。
所以「`-O2` 会生成死循环」**不是 macOS 的锅，是 LLVM 23 更激进的 UB 推断策略**。

### 修正上一版结论

本模块初版（提交 `ba7f13bc0`）曾写下"`-O2` 下必卡死"的断言。上面四组实测证明那是**过度概括**。
正确表述是：

> **UB 的后果取决于「编译器 + 版本 + 优化级别 + 目标平台」这四者的组合。**
> 没有任何一项能单独决定结果。同一份源码换个编译器就可能从"看起来没问题"变成"永久卡死"。

这也正好解释了为什么 C 里那么多 bug 在开发环境不复现、到 CI 或客户机器上才炸。

### 越界那 4 格为什么恰好是 0

`buf` 是 `static`，后面紧接着的内存恰好全零，所以越界读到的都是 0、
`sum_n(buf,8)` 才碰巧等于正确值 100。Mac 的 lldb 与 Pi 的 gdb 都转储到了同一幅景象：

```
0x555555570040 <buf>:  10  20  30  40      ← buf[0..3]
0x555555570050:         0   0   0   0      ← buf[4..7]，越界读的就是这里
```

**这是最坏的一种 bug**：错得无影无踪。它之所以必讲，是因为
`printf` 查不出来、`valgrind` 之外几乎无从下手，只有调试器/ sanitizer 能当场抓住。

## 与后续衔接

要抓住它，得靠工具。ASan 一句话就能定性，而拿到 Pi 上更方便的是 gdb：

```console
$ clang -g -O1 -fsanitize=address -fno-omit-frame-pointer -std=c11 ptrbug.c -o ptrbug_asan && ./ptrbug_asan
==ERROR: AddressSanitizer: global-buffer-overflow on address ...
READ of size 4 at ... thread T0
    #0 0x... in sum_n ptrbug.c:34
    #1 0x... in main ptrbug.c:49
SUMMARY: AddressSanitizer: global-buffer-overflow ptrbug.c:34 in sum_n
```

Mac 侧的完整 lldb 会话在 [3.3](./3.3-实测lldb.md)，
Linux 侧的 gdb 会话（**同样是真实输出**）在 [4.3](../04-linux-gnu/4.3-实测gdb.md)。

<details>
<summary>Q&amp;A：那我到底该用哪个编译器？</summary>

别纠结"最好"，先固定一个、并把它写进 CI：

- 学 TLPI / 写跨平台代码 → 用 **Linux 上的 gcc + clang 双跑**（你 Pi 上两个都有），
  两个都过了，才敢说代码没踩 UB；
- Mac 本机快速验证 → `cdev` 的 clang 23，**记住它比 Xcode 那套更激进**，
  所以它能跑过、clang 19 未必；反过来不成立。
</details>
