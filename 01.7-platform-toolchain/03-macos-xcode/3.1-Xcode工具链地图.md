# 3.1 Mac 的工具链在地上叠了三层

[← CH3 macOS/Xcode](./README.md) · 下一节：[3.2 两套 clang 与版本矩阵 →](./3.2-两套clang与版本矩阵.md)

## 本节讲什么

Windows 那边的麻烦是"IDE 藏得太深"，Linux 那边的麻烦是"东西太多不知道谁是谁"。
Mac 的麻烦是第三种：**苹果把工具链叠了三层，而且第三层会骗你。**

这三层是：

```
第 3 层  /usr/bin/clang、/usr/bin/gcc   ← 「转发代理」，一个 200KB 的小二进制
第 2 层  Xcode.app 或 CommandLineTools  ← 真正的编译器 + SDK + lldb
第 1 层  xcode-select 决定第 3 层指向谁 ← 唯一需要记住的开关
```

## 要点

### 三层各自是什么

| 层 | 位置 | 干什么 |
|---|---|---|
| **shim（转发代理）** | `/usr/bin/clang`、`/usr/bin/gcc`、`/usr/bin/make` | 不含任何编译器逻辑，只负责问 xcode-select：「现在该用哪套工具链？」再转发过去 |
| **工具链实体** | `/Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/` | Apple clang、`ld`、`lldb`、`swift` 的真身 |
| **SDK** | `.../Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk` | 头文件 + 库 + libc。编译器靠 `-isysroot` 找到它 |
| **选择器** | `xcode-select` | 决定 shim 转发到 Xcode.app 还是 Command Line Tools |

### 实测：这台 Mac 现在的状态

```console
$ xcode-select -p
/Applications/Xcode.app/Contents/Developer       # ← 指向完整 Xcode.app

$ xcrun --find clang
You have not agreed to the Xcode license agreements. Please run
'sudo xcodebuild -license' from within a Terminal window to review and agree
to the Xcode and Apple SDKs license.                    # ← 整条路被拦住

$ gcc --version
You have not agreed to the Xcode license agreements. ...  # ← 连 gcc 都同样是 shim
```

**注意最后一条。** Mac 上你以为在敲 GNU gcc，其实 `/usr/bin/gcc` 和 `/usr/bin/clang`
是**同一个 200560 字节的转发二进制**：

```console
$ ls -l /usr/bin/clang /usr/bin/gcc
-rwxr-xr-x  78 root  wheel  200560 ...  /usr/bin/clang
-rwxr-xr-x  78 root  wheel  200560 ...  /usr/bin/gcc
```

苹果这么做是为了兼容老脚本 —— 但它意味着 **`gcc --version` 打印 clang 的版本号时，
你看到的不是 bug，是设计**。Mac 上没有 GNU gcc（装的 brew gcc 另说）。

### 绕过许可：直接走完整路径

既然第 3 层被许可卡住，那就跳过它，直接点名第 2 层：

```console
$ /Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/usr/bin/clang --version
Apple clang version 21.0.0 (clang-2100.3.34.2)
Target: arm64-apple-darwin27.0.0
Thread model: posix
```

并且**能真的编译、真的跑**（因为没有 SDK 就找不到头文件，所以要带 `-isysroot`）：

```console
$ clang -isysroot /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk \
        hello.c -o hello && ./hello
hello from Apple clang
```

> ⚠️ **诚实交代：** 这只是绕过了许可提示，不等于你没义务同意许可。
> 正规的解锁方式还是一条 `sudo xcodebuild -license`（要 sudo + 你自己读条款，
> 所以我不替你跑）。同意之后 `xcrun` / `/usr/bin/clang` / VS Code 的 C/C++ 插件才全部恢复。

### 版本号：这里有三套编号在互相打架

和 Windows 的 `_MSC_VER`（见 [2.3](../02-windows-msvc/2.3-版本号迷宫.md)）一个德行，
Mac 这边也要对着表格换算：

| 说法 | 这台机器的值 | 谁在用 |
|---|---|---|
| **Xcode 版本** | 27.0 | App Store、`xcodebuild -version` |
| **Apple clang 版本** | 21.0.0 | `clang --version` 打印的行首 |
| **LLVM 上游构建号** | clang-2100.3.34.2 | 括号里，是 Apple 从 LLVM 某个快照打的分支 |
| **lldb 版本** | lldb-2103.0.34.103 | `lldb --version`，**又是另一套编号** |
| **Swift 版本** | Apple Swift 6.4 | `lldb --version` 顺带打印的 |

对照 Linux 那边的惯例（LLVM 版本号 = 你从官网下载的 LLVM 版本号，
见 [4.1](../04-linux-gnu/4.1-GNU工具链地图.md)），Mac 这套编号体系是**苹果自己维护的分支**，
和上游 LLVM 版本号之间**没有换算公式**，只能查表。

> 这就是为什么模块里另有一份 LLVM clang 23.1.0（micromamba `cdev`）。
> 两套 clang 并存不是冗余，它们是**不同的编译器**，下一节会用实测证明这一点。

## 与你的关系

| 场景 | 该用哪套 | 理由 |
|---|---|---|
| 学 TLPI / 系统编程 | `cdev` 的 clang 23.1.0 | 版本紧跟上游，行为与你在书上读的一致；[Pi 上的 clang 19](../04-linux-gnu/4.1-GNU工具链地图.md) 是同一族 |
| 编译 macOS GUI / 系统框架 | Apple clang + SDK | 只有它能吃下 `-framework` 和私有 SDK |
| 初学 C | 随便挑一套，**但要知道是哪一套** | 因为它们的 UB 处理不一样 —— 下一节有实测 |

<details>
<summary>Q&amp;A：为什么 xcode-select 存在？直接写死路径不行吗？</summary>

因为一台 Mac 上可能装了**多版本 Xcode**（正式版 + beta 并存），
CI、Xcode Server、命令行用户各自要用不同版本。`xcode-select -s <路径>`
就是这台机器的全局「当前 Xcode」开关。

CLI-only 的人通常刻意把它指到 Command Line Tools（体积小 20 倍）：

```bash
sudo xcode-select -s /Library/Developer/CommandLineTools
```

但你这台机器上命令会先被许可拦住，所以这条现在跑不了。
</details>
