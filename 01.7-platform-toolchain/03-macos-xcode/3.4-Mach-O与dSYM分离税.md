# 3.4 Mac 的「分离税」：Mach-O 不放调试信息

[← 3.3 实测 lldb](./3.3-实测lldb.md) · 下一节：[CH4 Linux/GNU →](../04-linux-gnu/README.md)

## 本节讲什么

Linux 上 `gcc -g a.c -o a.out`，调试信息就在 `a.out` 里，拷走这一个文件就够。
Windows 上 `cl /Zi`，调试信息进 `.pdb`，要和 exe 一起带着。
**Mac 上两样都不是**：`-g` 之后可执行文件几乎没变大，调试信息去了一个第三方 —— dSYM。

这一节专门讲这笔"分离税"，因为它踩过一次就够你找一晚上。

## 要点

### 实测：加不加 -g，可执行文件几乎一样大

```console
$ clang -O0 -std=c11 ptrbug.c -o ptrbug_nodbg      # 不带 -g
$ clang -c -g -O0 -std=c11 ptrbug.c -o ptrbug.o
$ clang -g ptrbug.o -o ptrbug                      # 带 -g（保留中间 .o）

$ ls -l ptrbug_nodbg ptrbug | awk '{print $5, $9}'
70136 ptrbug_nodbg
70544 ptrbug                                        # ← 只多了 408 字节

$ llvm-dwarfdump ptrbug | grep -c DW_TAG
0                                                   # ← 可执行文件里一个 tag 都没有
$ llvm-dwarfdump ptrbug.o | grep -c DW_TAG
35                                                  # ← 全在 .o 里
```

对比 Linux 上同一个实验（见 [4.4](../04-linux-gnu/4.4-ELF与DWARF.md)）：
`gcc -g` 让文件从 70520 → 72192 字节，`readelf` 直接在 ELF 里读到 `.debug_info`。
**Linux <｜hy_place▁holder▁no▁813｜>内嵌，macOS 靠外挂。**

### dSYM 才是调试器真正要的东西

```console
$ dsymutil ptrbug
$ ls -d ptrbug.dSYM && du -sh ptrbug.dSYM
 20K    ptrbug.dSYM

$ llvm-dwarfdump ptrbug.dSYM/Contents/Resources/DWARF/ptrbug | grep -c DW_TAG
22
$ llvm-dwarfdump ptrbug.dSYM/.../ptrbug | grep -E "DW_AT_(name|decl_line)"
DW_AT_name      ("main")
DW_AT_decl_line (39)
DW_AT_name      ("bad")
DW_AT_decl_line (49)
```

### 最大的那个坑：一步到位就再也补不回来

```console
$ clang -g ptrbug.c -o ptrbug        # 不保留 .o，clang 用临时文件，编译完就删
$ dsymutil ptrbug
error: unable to open ...            # ← 中间 .o 没了，dsymutil 无从下手
```

所以正确姿势是拆两步，或者干脆用 `-g -gsplit-dwarf` / 构建系统帮你保留：

```makefile
%.o: %.c
	$(CC) -c -g -O0 $< -o $@        # 必须落地成文件
%: %.o
	$(CC) -g $< -o $@
	dsymutil $@                     # 链接完立刻生成 dSYM
```

> `demo/Makefile` 里就是这么写的（`make all` 会自动产出 `.dSYM`）。

### 三平台调试信息容器对照

| | Windows (MSVC) | macOS (Apple clang) | Linux (gcc/clang) |
|---|---|---|---|
| 文件格式 | PE/COFF（`.exe` `.dll`） | **Mach-O** | ELF |
| 调试信息放哪 | `.pdb`（独立文件） | `.dSYM/` bundle（独立目录） | **ELF 内部 `.debug_*` 节** |
| `-g`/`/Zi` 后本体变大吗 | 基本不变 | 基本不变（实测 +408 B） | **变大**（实测 +1672 B） |
| 只拷可执行文件能调试吗 | ❌ 要带 pdb | ❌ 要带 dSYM | ✅ 可以 |
| 查看工具 | `dumpbin` / DIA | `llvm-dwarfdump`、`dsymutil` | `readelf`、`objdump`、`llvm-dwarfdump` |
| 符号剥离 | `/PDBSTRIPPED` | `strip`（dSYM 不受影响） | `strip` / `objcopy --only-keep-debug` |

### 还有一笔税：debugserver 与进程附加

lldb 在 macOS 上不是直接抓进程，它要通过一个独立服务 `debugserver`
（位于 `LLDB.framework/.../Resources/debugserver`）来 attach。两个后果：

1. **conda/micromamba 装的 lldb 通常不带 debugserver** —— 版本号能打印、能 `file` 加载，
   一到 `run` 就报找不到调试服务端；能用的是 Xcode 自带的那只
   （`/Applications/Xcode.app/Contents/Developer/usr/bin/lldb`，实测 `lldb-2103.0.34.103`）。
2. **macOS 的进程附加权限会拦住非终端里的调试器**。我在沙箱里跑 lldb 时得到：

   ```
   error: attach failed: ...
   ```
   
   脱离沙箱（真正的终端授权）后立刻正常。如果你在 VS Code / CLion 里遇到这种报错，
   多半是同一类权限问题，不是配置写错了。

<details>
<summary>Q&amp;A：Mach-O 和 ELF 的差别需要现在就学吗？</summary>

不用背结构。只要知道三条就够用现阶段：

1. 格式决定了"谁能加载它"：Mach-O 只有 macOS/iOS 的 dyld 认，ELF 只有 Linux 的 ld.so 认；
2. **不能互相运行**，哪怕同为 arm64 —— 所以你在 Mac 上编译的二进制拷到 Pi 上一定报
   `cannot execute binary file: Exec format error`（这条错误的意思是"格式不对"，不是"架构不对"）；
3. 想深挖时再看：`llvm-objdump --macho --private-headers` / `otool -l`。
</details>
