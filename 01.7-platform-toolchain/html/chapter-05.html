导读

这一章解决什么困惑： 我明明在 VS 里把 C 学得挺顺了，为什么学长都说 "要学 Linux 系统编程你得换环境"？

因为 Windows 和 POSIX 不是"同一套东西换到另一个系统"，而是两套不同的 API 世界观， 交界处从 #include 那一行就开始断裂。

本章的收获

  1. MSVC 对 C 标准的支持边界在哪 —— 官方白纸黑字说不打算支持的那些东西
  2. unistd.h / sys/socket.h 为什么不存在，以及 Windows 的对应物叫什么
  3. 编码、行尾、路径这些"不致命但烦死人"的差异
  4. 一个明确的行动方案：你的三条主线各自该在哪个环境上跑

一句话结论

MSVC 不是"缺了一点的 gcc"，它是有意选择了一条不同的路线。 这不代表它差 —— 它对 VLA 的拒绝有明确的安全理由；但它确实意味着 「在 VS 里学 C」和「在 Linux 上学系统编程」是两件不同的事，不能互相替代。

5.1

MSVC 的 C 标准到底支持到哪

← CH5 边界 · 下一节：5.2 头文件与 socket →

本节讲什么

MSVC 从 VS 2019 16.8 起正式支持 C11/C17，但大面积不支持 C11 的可选特性。 这一节把这些"明确不做"的东西列清楚 —— 它们全都有官方原话支撑，不是我的推测。

要点

官方支持的起点

Microsoft C++ Team 博客（C11 and C17 Standard Support Arriving in MSVC）：

C11 and C17 are becoming supported language versions in the MSVC compiler toolset starting with Visual Studio 2019 version 16.8 Preview 3! For many years Visual Studio has only supported C to the extent of it being required for C++.

两件事值得注意：

  1. 起点是 VS 2019 16.8，之前 MSVC 的 C 支持只是"C++ 要求的那部分"（即 C89 的子集）
  2. /std:c11 / /std:c17 会隐式打开 /Zc:preprocessor（一致性预处理器）

__STDC_VERSION__ 的值：/std:c11 → 201112L，/std:c17 → 201710L。

官方明确不做的清单

Microsoft Learn 的 /std 文档，原话：

The compiler doesn't support most optional features of ISO C11. …… There's no conforming multithreading, atomic, or complex number support. aligned_alloc support is missing, because of the Windows heap implementation. The alternative is to use _aligned_malloc. DR 400 support is currently unimplemented for realloc because this change would break the ABI. Variable length array (VLA) support isn't planned.

翻译成清单：

特性 MSVC 状态 你在代码里怎么检测 替代方案
VLA（变长数组） ❌ 明确不打算支持 __STDC_NO_VLA__ == 1 malloc / 固定长度数组
<threads.h> ❌ 不支持 __STDC_NO_THREADS__ == 1 _beginthreadex / C++ std::thread
_Atomic ❌ 不合标 __STDC_NO_ATOMICS__ == 1 Interlocked* / C++ std::atomic
_Complex ❌ 不支持 __STDC_NO_COMPLEX__ == 1 自己定义结构体
aligned_alloc ❌ 缺 —— _aligned_malloc
realloc DR 400 ❌ 未实现 —— 注意 realloc(p, 0) 的行为不再 UB

这四个 __STDC_NO_*__ 宏在 MSVC 编译 C 且指定 /std:c11 或 /std:c17 时会被定义为 1 （Microsoft Learn「预定义宏」页）。这其实是件好事 —— 你可以用预处理判断它们，做条件编译。

为什么明确拒绝 VLA（官方理由）

C++ Team 博客的原文：

Variable length arrays are generally less efficient than comparable fixed sized arrays, and generally inefficient compared to equivalent malloc(), when safely and securely implemented. VLAs provide attack vectors comparable to those of the infamous gets() — deprecated and destined to removal — for opportunities of "shifting the stack" and other exploits. For these reasons we intend not to support VLAs as an optional feature in C11.

要点：微软认为 VLA 既低效、又提供类似 gets() 的栈攻击面，所以无意支持。

这是个值得你记住的判断分歧：VLA 在 Linux/GNU C 里是常用写法 （尤其内核代码和网络包处理里 char buf[len] 的写法）， 但在 MSVC 里编译不过。跨平台代码必须回避 VLA。

三工具链对照：同一份 C11 代码能否通过

特性 MSVC (/std:c17) clang (-std=c17) gcc (-std=c17)
VLA ❌ ✅ ✅
<threads.h> ❌ ✅（取决于 libc，glibc 2.28+） ✅（glibc 2.28+）
_Atomic ❌ ✅ ✅
_Complex ❌ ✅ ✅
aligned_alloc ❌（用 _aligned_malloc） ✅ ✅
_Generic、_Static_assert、_Alignas、_Alignof ✅ ✅ ✅
_Pragma、restrict ✅ ✅ ✅

注意 clang/gcc 侧也有自己的坑：-std=c17（严格）会禁用 GNU 扩展， 而 -std=gnu17 才会开 __attribute__、typeof、语句表达式等 —— 内核代码用的是 gnu11/gnu17。详见 01-c-language/05 嵌入式与内核。

一个实用建议：怎么写出三边都能过的代码

做法 说明
回避 VLA 用 malloc + 显式 free，或固定上限数组
用 _ Static_assert / _Alignof 等 C11 必需特性 三边都支持
原子/线程用 C++11 的 std::atomic / std::thread 如果项目允许 C++，这是最省事的跨平台答案
对齐分配包一层宏 #ifdef _MSC_VER → _aligned_malloc #else → aligned_alloc
用 __STDC_NO_VLA__ 等宏做特性检测 而不是用 #ifdef _WIN32 猜平台能力

最后一条尤其重要：检测"有没有这个能力"，而不是"是不是这个平台"。 _MSC_VER / _WIN32 判断的是平台，而将来 MSVC 可能支持某个特性时你的代码就白限了； __STDC_NO_VLA__ 判断的是能力，永远正确。

5.2

头文件与 socket：两套完全不重叠的世界

← 5.1 MSVC 的 C 标准边界 · 下一节：5.3 编码行尾与路径 →

本节讲什么

你在 VS 里 #include <stdio.h> 一切正常，但你翻开 TLPI 的示例代码， 第一行 #include <unistd.h> 就编译不过。

这不是你的问题，是两个操作系统各自的 API 世界观不同。

要点

POSIX 头文件 → Windows 的对应物

POSIX / Linux 头文件 提供什么 Windows 的对应
<unistd.h> read/write/fork/exec/pipe/getpid ❌ 没有；散落在 <io.h> <process.h> <windows.h>
<sys/socket.h> socket/bind/listen/accept <winsock2.h> + -lws2_32
<netinet/in.h> sockaddr_in、htons <winsock2.h>（合并提供）
<arpa/inet.h> inet_pton、inet_ntop <ws2tcpip.h>
<fcntl.h> open、文件状态标志 <io.h>（不同语义），nonblock 用 ioctlsocket
<sys/stat.h> stat 结构体 <sys/stat.h> 存在但内容不同
<pthread.h> 线程、互斥、条件变量 ❌ 没有；CreateThread / SRWLOCK / CONDITION_VARIABLE
<sys/mman.h> mmap ❌ 没有；CreateFileMapping + MapViewOfFile
<sys/wait.h> waitpid ❌ 没有 fork 就没有 waitpid
<errno.h> errno 存在，但大多数 Windows API 不设置它，用 GetLastError()

一句话记住：Windows 上没有 fork、pthread、mmap、unistd 这四个东西的任何等价物。 它们是 POSIX 世界观的地基，而 Windows 的地基是 HANDLE + CreateProcess + WaitForSingleObject。

三套"句柄"模型，别混着用

这是最要命的一处：

POSIX Windows
文件 int fd（小整数，0/1/2 是标准流） HANDLE（指针大小的句柄）
socket int fd（和文件同类型） SOCKET（typedef，和 HANDLE 也不同）
能不能用同一个函数读写？ ✅ read(fd) / write(fd) 通用 ❌ 文件用 ReadFile，socket 用 recv/send

后果： 这段 Linux 代码在 Windows 上没有等价写法：

int fd = open("file.txt", O_RDONLY);
read(fd, buf, sizeof buf);          /* Linux: 文件和 socket 都能 read */

Winsock 必须用具名函数 recv() / send()，read() 对 socket 是无效的。

socket 程序的差异（对照一张表）

步骤 POSIX Windows (Winsock)
初始化 不需要 必须先 WSAStartup(MAKEWORD(2,2), &wsaData)
头文件 <sys/socket.h> 等 <winsock2.h> (+ <ws2tcpip.h>)
链接 通常不需要额外库 -lws2_32（VS 里 #pragma comment(lib, "ws2_32.lib")）
创建 socket(AF_INET, SOCK_STREAM, 0) 同（返回值类型是 SOCKET）
关闭 close(fd) closesocket(s) —— 写 close(s) 会出错
设非阻塞 fcntl(fd, F_SETFL, O_NONBLOCK) ioctlsocket(s, FIONBIO, &mode)
取错误 errno WSAGetLastError()
收尾 不需要 WSACleanup()

忘了 WSAStartup 是 Winsock 新手第一坑：不调用的话所有 socket 调用都返回 WSANOTINITIALISED (10093)，而且看起来"函数都存在、就是跑不通"。

另一个 MSVC 特有现象：_CRT_SECURE_NO_WARNINGS

char buf[16];
scanf("%s", buf);          /* MSVC: warning C4996: 'scanf': This function may be unsafe */

MSVC 默认会对一批标准 C 函数发 C4996 弃用警告（scanf/strcpy/sprintf/localtime…）， 推荐改成 scanf_s / strcpy_s 等 _s 后缀的安全版本。

三种处理方式的取舍：

做法 适用场景
#define _CRT_SECURE_NO_WARNINGS（在所有 include 之前） 写跨平台代码、或学教材代码时最省事
改用 scanf_s 等 只写 Windows 且希望保留安全增强
/D_CRT_SECURE_NO_WARNINGS（命令行 / CMake） 整个项目统一关闭，推荐用于 CI

⚠️ _s 系列不是标准 C 的一部分（它们源自 C11 Annex K，但 glibc 基本没实现）。 用了 scanf_s 你的代码就再也无法在 Linux 上编译。跨平台代码不要碰 _s。

对你主线的直接含义

03-linux-userspace-api（TLPI） 里几乎第一个例子就是 打开一个文件、读写它、然后 close()；03.5-unix-network-api（UNP） 从头到尾都是 socket/bind/listen/accept + read/write。

这两本书的每一行示例代码，在 MSVC 下都需要重写。这也直接铺垫了最后一节的结论。

5.3

编码、行尾与路径：不致命但天天烦人的差异

← 5.2 头文件与 socket · 下一节：5.4 为什么 TLPI 必须在 Linux 上跑 →

本节讲什么

三类差异：它们不会让你的逻辑出错，但会让你在跨 Windows ↔ macOS/Linux 协作时 反复遇到"在我机器上明明是好的"。

要点

① 源文件编码（MSVC 有个默认值坑）

Microsoft Learn 的 /utf-8 文档原话：

By default, Visual Studio detects a byte-order mark to determine if the source file is in an encoded Unicode format... If no byte-order mark is found, it assumes that the source file is encoded in the current user code page, unless you've specified a code page by using /utf-8 or the /source-charset option.

也就是说：没有 BOM 的 UTF-8 源文件，MSVC 会按当前系统代码页解读。 在简体中文 Windows 上系统代码页是 GBK (936) —— 于是 UTF-8 写的中文注释和字符串 会变成乱码，甚至导致编译错误。

平台 默认行为
clang / gcc 源文件一律按 UTF-8 处理（这是 POSIX 世界的事实标准）
MSVC 看 BOM：有 BOM 认 UTF-8，无 BOM 按当前代码页（会错）

解法三选一：

方案 说明
编译时加 /utf-8 等价于 /source-charset:utf-8 /execution-charset:utf-8，推荐
源文件存成 UTF-8 with BOM 让 MSVC 自己认出来；但某些 Linux 工具看到多余 BOM 会抱怨
避免使用非 ASCII 字符 最保守，写英语注释

⚠️ 加 /utf-8 会自动启用 /validate-charset：源文件里出现执行字符集无法表示的字符时 会报警告。这通常是你想要的（早点发现问题），需要关掉用 /validate-charset-。

这条和你的现状直接相关：你在 Mac 上用 clang 写的中文注释笔记/代码， 拿给别人用 VS 编译就可能乱码 —— 因为 Mac 上生成的 UTF-8 文件通常不带 BOM。

② 行尾符 CRLF vs LF

Windows macOS / Linux
行尾 \r\n (CRLF) \n (LF)
后果 Linux shell 脚本带 CRLF 会报 bad interpreter；某些工具把 ^M 当字符 Windows 记事本打开 LF 文件不换行（新版记事本已改善）

Git 的应对策略就是你现在正在配的那项（core.autocrlf / .gitattributes）：

配置 含义
core.autocrlf=true 检出时转 CRLF，提交时转 LF（Windows 本机开发推荐）
core.autocrlf=input 提交时转 LF，检出不变（macOS/Linux 推荐）
.gitattributes + text eol=lf 仓库层面统一，团队成员各自 override —— 比个人 core.autocrlf 可靠

推荐做法是用 .gitattributes 而不是依赖每个人的 core.autocrlf —— 后者是本地设置，不会被提交，新人加入就得重踩一遍。

③ 路径分隔符与大小写（最后一个很隐蔽）

差异 Windows macOS / Linux
分隔符 \（也可接受 /） /
盘符 C:\Users\... 无，/ 是根
文件系统大小写敏感 ❌ 不敏感 macOS 默认不敏感，Linux 敏感

前两条你一眼能看出来，第三条才是真正的坑：

#include <Sys/Socket.H>     /* Windows: ✅ 能编过（文件系统不敏感）
                               Linux:   ❌ fatal error: No such file or directory */

在 Windows / macOS 上写错大小写的代码，到 Linux CI 上会编译失败。 而开发者的本机测试完全发现不了。

这和你长期要做的事直接相关 —— 你的学习产出经常是 Mac 本地写、 推到 Linux（树莓派）去编译。在 Mac 上能编过不等于在 Pi 上能编过。

一张表收尾

项目 建议做法
源文件编码 统一 UTF-8 without BOM；MSVC 侧加 /utf-8
中文注释 想跨平台就在 Windows 侧加 /utf-8，否则别写非 ASCII
行尾 用 .gitattributes 定 *.md text eol=lf，别靠个人 core.autocrlf
#include 大小写 一律按标准写的小写原样抄（sys/socket.h 不是 Sys/Socket.h）
路径 C 代码里用 /，Windows API 也接受

4.4

结论：TLPI 为什么必须在 Linux 上跑

本节讲什么

把前面三节的碎片拼成一个判断，然后落到你现在这几台机器上具体怎么排。

要点

判断标准：看主题是不是"系统调用"

判断一件事能不能在 VS/MSVC 上做，标准很简单 —— 看它的主题是不是「系统调用」：

你的主线 主题 能不能在 VS/MSVC 上学 原因
01 C 语言（K&R / Pointers on C / Modern C） C 语法、指针、内存模型 ✅ 可以 标准库部分三边通用
01.5 CMake 构建系统描述 ✅ 可以 CMake 本来就能生成 VS 工程
03 TLPI Linux 系统调用 API ❌ 不行 open/read/fork/mmap/signal 全套 POSIX 接口
03.5 UNP Socket API ❌ 不行 Winsock 是另一套 API，read() 读 socket 不成立
05 LKD / 05.5 Linux 内核 ❌ 更不行 内核源码本身就是 Linux 的
13 DPDK 用户态高速网络 ❌ Windows 支持有限，路径完全不同 —

一句话：TLPI 这本书的名字里就写着 Linux。 它每一章都在讲某个 syscall 的行为、 边界条件、errno 取值。这些内容在 Windows 上没有对应概念，硬搬等于把书重写一遍。

你现在三台机器的分工

机器 适合做什么 备注
Mac（主力） C 语言 / 指针 / Modern C / 算法 / 概念层学习；CMake 练习；lldb 调试（CH3 已实跑通） clang 23.1.0 + Xcode 自带 lldb；不能跑 TLPI 示例代码
树莓派 5（Debian 13 / kernel 6.18） TLPI / UNP / eBPF 的主战场；aarch64 顺便让你看见和 x86 的差异 gcc 14.2 / clang 19 / gdb；真实 Linux syscall
Windows（已不具备） MSVC 对照 —— 只能靠本模块做认知层面的了解 需要时再考虑虚拟机

所以 VS 那段经历的价值在哪

你已经用 VS 学会了 C 的核心 —— 这是真实收获。但它的价值分布不均：

从 VS 学到的 迁移价值 说明
变量、指针、数组、结构体 ✅ 100% 属于语言本身
「暂停 → 看变量 → 看调用栈」的调试直觉 ✅ 接近 100% 这就是 CH3 的核心论点
「编译 → 链接 → 生成可执行」的流程感 ✅ 高 四件套在哪都一样
"要开警告、要看警告"的习惯 ✅ 中高 概念通用，拼写要换（clang -Wall vs MSVC /W4）
/MD vs /MT、.vcxproj 写法、属性页在第几层 ❌ 低 出 Windows 就没用

一句话总结： VS 帮你迈过了"不知道程序是怎么跑起来的"这道坎， 但它让你最熟悉的那些具体操作，恰恰是最不能被带走的那部分。 能带走的是心智模型 —— 本模块所有章节写的都是能带走的那一半。

行动建议（按优先级）

  1. 现在就能做：把 CH3 在你的 Mac 上跑一遍（3.3）， 建立"调试四件事"的肌肉记忆。这份能力直接服务于后面所有章节。
  2. 顺手解锁：sudo xcodebuild -license —— 让 xcrun 体系可用，Apple 官方工具链到手。
  3. TLPI 学习路径：示例代码一律在树莓派 5 上编译运行，Mac 只做笔记和阅读。 不要在 Windows 侧试图模拟。
  4. 写跨平台代码时：回避 VLA、不用 _s 后缀函数、按能力宏检测而不是平台宏检测。

5.5

MSVC 不吃 GNU 扩展：编辑器不背锅，编译器才背

← 5.4 为什么 TLPI 必须在 Linux 上跑 · CH5 边界

本节讲什么

一个很常见的困惑：我在 VS 里写了一段完全正确的 GNU C 代码（内核风格那种）， 语法高亮正常、IntelliSense 也不报错，一按生成却满屏语法错误。 不是代码写错，是编译器不对。

这一节把这件事讲透：哪些写法 MSVC 真的不支持、错觉从哪来、 以及"想让 Windows 也能编译"的三个方案怎么选。GNU 扩展本身的语法细节见 01-c-language/05-embedded-kernel-practice（CH1 语法 / CH2 语义）。

要点

一、先回答那个判断题：IDE 决定能不能编译吗？

不能。 IDE 只负责让你写文字这件事舒服：

层 谁负责 VS 的例子
编辑 IDE（文本框 + 语法高亮 + IntelliSense） 写什么都不会被拦
编译 后端编译器 cl.exe（MSVC）/ gcc / clang
链接 后端链接器 link.exe / ld

这正是 1.1 IDE 不是编译器 那条结论的延伸 —— 同一个 VS，把工具集从 MSVC 换成 WSL 的 gcc，同一份代码就能过。 所以"VS 能不能编译 GNU 扩展"这个问题的答案永远是：看你换没换后端。

二、逐条核验：五个例子里有一个不是 GNU 扩展

# 写法 MSVC 核验结论
1 int arr[] = {[0 ... 5] = 7}; 范围指定初始化 ❌ ✅ 正确。GNU 专属语法，MSVC 直接报错
2 ({ ... }) 语句表达式 ❌ ✅ 正确。GNU 专属
3 __attribute__((packed)) ❌ ✅ 正确（但要说准：MSVC 根本不认识 __attribute__ 这个关键字，对应写法是 #pragma pack(1)）
4 char buf[0]; 零长数组 ❌ ✅ 正确。MSVC 不接受零长数组，常见替代是 C99 的柔性数组成员 char buf[];
5 __STRICT_ANSI__ —— ❌ 这条不是 GNU 扩展

第 5 条必须纠正。 它不是一种语法，而是一个模式指示宏 —— GCC/Clang 在你用严格标准模式（-std=c11 而非 -std=gnu11）编译时自动定义它， 作用恰恰相反：它出现意味着"现在禁止 GNU 扩展"。 Pi 上的实测：

$ for m in gnu11 c11 gnu17 c17; do printf "gcc -std=%-6s : " $m; \
    gcc -std=$m -dM -E - </dev/null | grep -q __STRICT_ANSI__ && echo 已定义 || echo 未定义; done
gcc -std=gnu11 : 未定义
gcc -std=c11  : 已定义          ← 严格模式才定义
gcc -std=gnu17 : 未定义
gcc -std=c17  : 已定义

而 MSVC 侧没有这个宏。MSVC 的对应机制是 /Za（禁用微软扩展），官方文档原话： "The /Za compiler option ... disables the other Microsoft extensions, and automatically defines the __STDC__ predefined macro for C programs."

这条纠正有实际后果： 移植代码里常见的写法 #ifdef __STRICT_ANSI__ ... #else /* 走 Native GNU 分支 */ #endif 在 MSVC 下会永远走 #else，因为 MSVC 从不定义它。判断编译器得用 _MSC_VER， 不能靠 __STRICT_ANSI__ 的有无。

三、GNU 扩展其实是两层，实测把结构照出来了

把六项写法喂给 gcc 14.2 与 clang 19.1.7，两个编译器在三个档位上的结果完全一致：

写法 -std=gnu11 -std=c11 -std=c11 -pedantic-errors
[0 ... 5] = 7 范围初始化 ✅ ✅ ❌
({ ... }) 语句表达式 ✅ ✅ ❌
char buf[0] 零长数组 ✅ ✅ ❌
__attribute__((packed)) ✅ ✅ ✅ 居然通过
__typeof__(x) ✅ ✅ ✅ 居然通过
char buf[] 柔性数组成员（C99 标准） ✅ ✅ ✅

gcc 在 -pedantic-errors 下给的原话：

g1_range.c:1:18: error: ISO C forbids specifying range of elements to initialize [-Wpedantic]
g2_stmt.c:1:23:   error: ISO C forbids braced-groups within expressions [-Wpedantic]
g4_zero.c:1:24:   error: ISO C forbids zero-size array 'buf' [-Wpedantic]

由此得到一个非常有用的分类法：

层 成员 为什么这样区分
保留命名空间层 __attribute__、__typeof__、__builtin_* 带双下划线前缀，属于"实现保留标识符"，标准允许编译器自己用，所以连最严格模式也放行
新语法层 范围初始化、语句表达式、零长数组 改变了语法本身，标准里没有 —— 只有 -pedantic-errors 才会把它揪出来

能立刻用上的一条纪律： 想检查自己的代码有没有偷偷依赖 GNU 语法， 光写 -std=c11 不够（实测照样通过），必须加 -pedantic-errors： bash gcc -std=c11 -Wall -Wextra -pedantic-errors foo.c

四、Windows 上想跑 GNU 扩展：三个方案怎么选

方案 怎么做 优点 代价 / 坑
① MinGW-w64 仍在 VS 里编辑，后端换成 MinGW 的 gcc 拿到真的 GCC，GNU 扩展 100% 全支持 .vcxproj 对 MinGW 支持很差 —— 实际要走 CMake 项目，用 VS 打开 CMakeLists.txt（见 01.5 CMake）
② VS + WSL2（你标记的推荐） VS2022 装 WSL 组件，代码在 Windows 编辑，一键调 WSL 里的真 GCC 支持全部 GNU 扩展 / __attribute__ / 语句表达式；最接近真实 Linux 环境 需要 WSL2 可用；跨文件系统的 I/O 性能有坑（代码要放在 WSL 的 ext4 里，别放 /mnt/c）
③ Clang-CL VS2022 安装 Clang 工具集，把后端换成 clang 绝大多数 GNU 扩展可用；clang 的诊断信息比 MSVC 友好 clang-cl 默认开 MSVC 兼容模式（-fms-compatibility），极少数边缘 GNU 特性会因兼容而被关掉；它伪装成 MSVC 的命令行风格，心智负担双击

一句话：IDE 不动，动的是后端。 三个方案本质都是同一个动作 —— 把 cl.exe 换成 gcc 或 clang。

五、但对你现在来说，这三个方案都用不上

必须诚实说一句：你这边的三台/两台机器里没有 Windows，所以① ② ③ 都是纸上选项。 而你现在已经处在比 WSL 更好的位置：

你要做的事 现成的环境 相比 WSL 的优势
编译 GNU 扩展代码 Pi：gcc 14.2 / clang 19.1.7 原生 Linux，不是"Windows 里套 Linux"
验证内核风格 C Pi：Debian 13 aarch64 + v6.6 源码可对照 与 LKD3rd 主线同源
本机编辑手感 Mac + VS Code（Remote-SSH 到 Pi） 一个键盘两个世界，代码就在 Linux 上

WSL 的价值只有一个场景：将来<｜hy_place▁holder▁no▁813｜>某天必须在 Windows 机器上工作。在那之前， 直接用 Pi 更短、也更像真的 Linux。眼下真正值得打通的是 macOS 那条支线的可用路径， 见 3.1 绕过 Xcode 许可。

六、MSVC 侧的确切边界（官方口径）

微软文档 /std 条目原话：

"The default C compiler (that is, the compiler when /std:c11 or /std:c17 isn't specified) implements ANSI C89, but includes several Microsoft extensions... It isn't possible to specify strict C89 conformance. The compiler doesn't implement several required features of C99, so it isn't possible to specify C99 conformance, either."

关键几点：

事实 说明
默认 C 模式是 C89 + 微软扩展 不是 C99、也不是 C11；/Za 只能关掉一部分
/std:c11、/std:c17 需 VS 2019 16.8+ 且要用较新的 Windows SDK（10.0.20211.0+）
VLA 明确不打算支持 官方把它与 gets() 并列作为攻击面（见 5.1）
aligned_alloc 缺失 用 _aligned_malloc
__STRICT_ANSI__ 从不定义 严格模式看 __STDC__（/Za 时自动定义）

与后续衔接

至此 CH5 把这个模块的边界问题说完了：三套工具都能写 C，但能不能编译由后端编译器决定， 而三家的标准覆盖面并不重合。

回到 CH6 速查表 可以取走一张"MSVC ↔ GNU"写法对照。

Q&A：写了 GNU 扩展，怎么让代码在 MSVC、gcc、clang 三家都过？

标准做法不是"删掉 GNU 扩展"，而是把差异收进一层宏，这是 Linux 内核与很多跨平台库的做法：

#if defined(_MSC_VER)
#  define PACKED_STRUCT(s)  __pragma(pack(push, 1)) struct s; __pragma(pack(pop))
#  define MAYBE_UNUSED      __declspec(unused)
#else
#  define MAYBE_UNUSED      __attribute__((unused))
#  define pack_push_1       _Pragma("pack(push, 1)")   /* 或直接 __attribute__((packed)) */
#endif

三条原则：

  1. 判断编译器用 _MSC_VER 的存在与否，不要用 __STRICT_ANSI__、__GNUC__ 的缺席来猜；
  2. 把每一处 GNU 语法都配一个 #else 分支，宁可啰嗦也不要留未定义行为；
  3. CI 至少跑两个编译器（你 Pi 上已经有两个），让差异在提交时就暴露， 而不是等到某天换工具链才发现满屏报错。
5.6

内核模块要真 Linux 吗：WSL2 到底够不够（Pi 5 全程实测）

← 5.5 MSVC 不吃 GNU 扩展怎么办 · CH5 边界

本节讲什么

顺着上一节的思路往下问：既然要看 GNU C 和内核风格代码，那内核模块实验这一步呢？

常见的说法是"WSL2 不行，能编 .ko 但 insmod 不进去，必须上虚拟机或物理机"。 这话对了一半 —— 对的是结论（做驱动实验确实不该用 WSL2），错的是理由。

这一节做两件事：

  1. 在真机（你的 Raspberry Pi 5）上把 make → insmod → dmesg → lsmod → rmmod 完整跑一遍， 每一步都贴真实输出；
  2. 把"WSL2 到底差在哪"讲准 —— 差的不是 insmod 这一个命令，而是三件别的事。

要点

一、先把那份结论逐条核一遍

原话 判定 依据 / 修正
内核用 GCC + 大量 GNU C 扩展写成 ✅ 对 补充：现在 make LLVM=1 可以用 clang 编内核，但构建环境仍在 Linux
内核不支持 MSVC，也不用 MinGW ✅ 对 MSVC 无 <linux/*.h>，且内核 Kbuild 依赖 GNU 工具链行为
语句表达式 / 指定初始化 / __attribute__ 是内核日常 ✅ 对 ——
零长数组 char buf[0] 是内核天天在用 ⚠️ 过时 见下文"一处需要更新的事实"
__STRICT_ANSI__ 属于 GNU 扩展 ❌ 错 已在 5.5 纠错：它是严格模式下的指示宏，MSVC 从不定义它
驱动代码依赖 <linux/xxx.h>，Windows 没有 ✅ 对 这不是语法问题，是整个 API 体系不在
WSL2 不能加载自己写的 .ko ⚠️ 不准确 准确说法：默认安装的 WSL2 缺"与运行内核精确匹配的模块集/build tree"；把模块 VHDX 配好之后 insmod 走得通。见第三节
做驱动实验要用 VM 或物理机 ✅ 对 但理由不是 insmod，见第四节

一处需要更新的事实：零长数组已经被内核"退役"了

2020 年 Linus 合入 flexible-array-member-5.7-rc2 时，pull request 里写得很直接：

"Kernel code should always use flexible array members for these cases. The older style of one-element or zero-length arrays should no longer be used."

同一批工作从 5.7 持续到 6.x（含 UAPI 头文件树级替换），原因也写在 kernel.org 的 process/deprecated.rst 里：

  • sizeof(zero_len_array) 恒等于 0，CONFIG_FORTIFY_SOURCE / UBSAN_BOUNDS 无法正确分析数组边界；
  • 柔性数组成员 buf[] 是不完整类型，误用 sizeof 会在编译期报错。

所以现在的正确心智模型是：

写法 出处 内核现状
char buf[1]; 古老的"单元素数组"技巧 ❌ 废弃
char buf[0]; GNU 扩展 ❌ 已在主线被系统性替换掉
char buf[]; C99 标准 ✅ 内核现在的唯一推荐写法

这是个很好的例子：GNU 扩展不是越"老"越正宗，内核自己也在往标准 C 退。 学的时候要认得出 [0]（读老代码一定会遇到），但不要自己再写。

二、真机实测：完整的内核模块闭环（Raspberry Pi 5）

你的 Pi 天生是最好的实验对象。先看环境是否具备三个前提：

$ uname -r
6.18.39+rpt-rpi-2712

$ ls -d /lib/modules/$(uname -r)/build
/lib/modules/6.18.39+rpt-rpi-2712/build          ← 内核构建树存在

$ dpkg -l | grep linux-headers
linux-headers-6.18.39+rpt-common-rpi   1:6.18.39-1+rpt1
linux-headers-6.18.39+rpt-rpi-2712     1:6.18.39-1+rpt1

$ zcat /proc/config.gz | grep -E "CONFIG_MODULES|CONFIG_MODULE_UNLOAD|CONFIG_MODVERSIONS"
CONFIG_MODULES=y              ← 支持可加载模块
CONFIG_MODULE_UNLOAD=y        ← 支持卸载（否则只能 insmod 不能 rmmod）
CONFIG_MODVERSIONS=y          ← 启用符号 CRC 校验（会写进 vermagic）

没有出现 CONFIG_MODULE_SIG —— 说明这台机器不强制模块签名，自编模块可以直接加载。 这一点不是每台 Linux 都成立（开了 Secure Boot 的发行版会拦），值得先看一眼。

示例模块的源码和 Makefile 在 demo/hello-mod/。编译：

$ make
make -C /lib/modules/6.18.39+rpt-rpi-2712/build M=/home/wzp/hello-ko modules
  CC [M]  hello.o
  MODPOST Module.symvers
  CC [M]  hello.mod.o
  CC [M]  .module-common.o
  LD [M]  hello.ko

$ file hello.ko
hello.ko: ELF 64-bit LSB relocatable, ARM aarch64, version 1 (SYSV)

注意它不是可执行程序，是 relocatable 目标文件 —— .ko 要由内核在加载时做重定位和符号绑定， 所以"—是什么格式"这一层就和普通的 a.out 完全不同。

加载之前先看模块自带的身份信息：

$ modinfo hello.ko | grep -E "^(filename|license|vermagic|depends)"
filename:  /home/wzp/hello-ko/hello.ko
license:   GPL
depends:
vermagic:  6.18.39+rpt-rpi-2712 SMP preempt mod_unload modversions aarch64

vermagic 这一行是整个问题的核心，下一节展开。

加载 + 看日志 + 三重核对：

$ sudo dmesg -C                      # 清 ring buffer，保证看到的都是本次的
$ sudo insmod hello.ko; echo "exit=$?"
exit=0

$ dmesg | tail -3
[1670251.974689] hello_ko: module loaded, running on real Linux

$ lsmod | grep hello
hello                  49152  0

$ cat /proc/modules | grep hello | cut -d' ' -f1,2,3
hello 49152 0

$ ls /sys/module/hello
coresize  holders  initsize  initstate  notes  ...

卸载，并确认三处都干净：

$ sudo rmmod hello; echo "exit=$?"
exit=0
$ dmesg | tail -2
[1670251.974689] hello_ko: module loaded, running on real Linux
[1670276.473644] hello_ko: module unloaded

$ lsmod | grep hello        # 空
$ cat /proc/modules | grep hello   # 空
$ ls -d /sys/module/hello   # 目录已消失

这就是只有真 Linux 才走得通的那一步：insmod 走的是 init_module(2) 系统调用， 需要一个真的内核接住它。Windows 上没有这个 syscall，MSVC 也产不出 relocatable 的 .ko（ELF 重定位 + module_layout 符号版本校验全部对不上）。

三、true 门槛不是 insmod，是 build tree 和 vermagic

回到 vermagic: 6.18.39+rpt-rpi-2712 SMP preempt mod_unload modversions aarch64。

内核加载模块时比对的是：

要比的东西 从哪来 不匹配会怎样
内核版本号 + local version uname -r disagrees about version of symbol module_layout
关键配置（preempt / mod_unload / modversions） .config 同上，直接拒绝加载
架构 aarch64 / x86_64 文件格式本身就不对
导出符号的 CRC（开了 MODVERSIONS 时） Module.symvers Unknown symbol ...

所以要编出一个能被当前正在运行的内核接受的 .ko，你必须同时有这三样：

  1. 与运行内核完全同一份源码（不是"同版本号就行"，local version、补丁都要一致）；
  2. 与运行内核完全同一份 .config；
  3. 相同或兼容的编译器。

这就是 WSL2 默认状态下真正的缺口：它不随发行版提供 /lib/modules/$(uname -r)/build， 所以你连门槛都摸不到 —— 表现出来就是"编不出 / insmod 报错"。

但这个缺口是可填的，而且微软已经把它做成了官方流程。三条证据：

(1) 官方 .wslconfig 支持 kernelModules 键（Microsoft Learn《Advanced settings configuration in WSL》原文）：

[wsl2]
kernel=C:\\temp\\myCustomKernel
kernelModules=C:\\temp\\modules.vhdx     ← "Specify the modules VHD for the custom Linux kernel"

(2) 微软自己的内核仓库给出了打包脚本与完整步骤 （microsoft/WSL2-Linux-Kernel 的 README-Microsoft.WSL2，2026-07-31 刚更新过 "custom kernel packaging documentation"， 同期合入 feature/wsl-module-script/6.18）：

make KCONFIG_CONFIG=Microsoft/config-wsl
make INSTALL_MOD_PATH="$PWD/modules" modules_install
make headers_install INSTALL_HDR_PATH="$PWD/headers"
# → stage 到 $release 目录 → 打成 ext4 → qemu-img convert -O vhdx modules.vhdx
#   仓库自带 Microsoft/scripts/gen_modules_vhdx.sh 一步生成

(3) 版本要求：kernelModules 需要 WSL ≥ 2.5.1。更早的 2.4.x 会把它当布尔值解析， 直接报 Invalid boolean value 'C:\modules.vhdx' for key 'wsl2.kernelModules'。 另外目前只支持单个 VHDX，多个模块场景得先合并成一个。

社区（microsoft/WSL discussion #12784）里也确认了这个区分：

"You can compile out of tree any module for the kernel. You don't need to recompile a new kernel. However … you need the same sources, the same configuration and the same compiler." —— 翻译：限制在打包与配套资料，不在"能不能加载"。

⚠️ 关于 WSL 的部分我没有在真实 Windows 上复跑过（你这台环境里没有 Windows）， 依据是微软官方文档 + 内核仓库 README + 官方 issue/discussion。上面的 Pi 部分则是全程实测。

四、WSL2 真正的短板在哪：不是 insmod，是设备和硬件

这一条比上一条重要得多。就算你把 modules.vhdx 配通、insmod hello.ko 跑成功了， 做不了的事情还是一大堆：

你要练的东西 WSL2 真 Linux（Pi / VM）
用户态 GNU C demo、看预处理 .i、看告警 ✅ 够 ✅
hello.ko 这种纯软件模块 ⚠️ 配好 VHDX 后可行 ✅
字符设备 + /dev/ + file_operations ⚠️ 可行（但没有真实硬件语义） ✅
设备树（DT）、platform_driver、DT overlay ❌ WSL2 没有设备树，没有 .dtb 给你的模块匹配 ✅
GPIO / SPI / I²C 真实外设 ❌ 虚拟机的硬件是假的，没有可操作的控制器 ✅ Pi 有 40pin 排针
中断号 / request_irq 的真触发 ❌ ✅
每次系统更新后的维护成本 ❌ 每次 wsl --update 换内核，模块要全部重编 正常

所以结论对，理由要换。 "WSL2 不够"的真正原因是：它是一个没有设备树、没有真实外设、 内核还随时会被 wsl --update 换掉的沙箱 —— 而不是"insmod 这个命令被禁了"。

对你的学习路线（09-device-drivers-dt：字符设备 → platform driver → 设备树 → GPIO） 来说，platform driver 之后的部分在 WSL2 里连 probe() 都进不去，因为没有任何东西能 match 上你的 of_match_table。

五、顺带一个新概念：out-of-tree 必然让内核"变脏"

加载自己的模块后，你会看到一个以前没见过的东西：

$ cat /proc/sys/kernel/tainted
4096

按 kernel.org 官方 tainted-kernels 文档的表解码：4096 = bit 12 = 'O' —— external-built ("out-of-tree") module was loaded。

实测验证它是 sticky 的（卸载也清不掉）：

$ cat /proc/sys/kernel/tainted           # insmod 之后
4096
$ sudo rmmod hello
$ cat /proc/sys/kernel/tainted           # 卸载之后，还是
4096

位分解输出确认只有 bit 12 被置位：

  bit 12 被置位（值 4096）

这有两个实际后果：

  1. 别慌：写自己的驱动模块时 tainted=O 是常态，MODULE_LICENSE("GPL") 也消不掉它 —— GPL 只影响 bit 0（proprietary），跟 bit 12 是两回事；
  2. 要 reboot 才干净：上报 bug 给上游时，人家会先看这个值。想复现"干净内核"的问题， 只能重启后在没加载过任何 out-of-tree 模块的情况下复现。

六、落到你这边的行动结论

你之前给的方案是"Windows + VS2022 编辑 → WSL2 练 GNU C → 再搞台 Linux 虚拟机做驱动"。 就你的现状，这条链要改两处：

  1. VS2022 这一段用不上 —— 它是 Windows-only，而你手上没有 Windows；VS for Mac 已退役（见 1.0）。 Mac 侧的编辑器方案见 4.5 Linux 上写 C 用什么。（编辑/编译分离的原则仍然成立）
  2. 第三台虚拟机不用再买了 —— 你的 Raspberry Pi 5 已经替它把活干了：

比虚拟机还多一层：它能真的点灯。虚拟机里写 GPIO 驱动是模拟出来的，Pi 上 probe() 进来 然后拉高 GPIO17 是真的会有 3.3V。

一句话记法（在你那个版本上修订）：

GNU C 语法：WSL2 够用。 insmod 本身：WSL2 默认缺 build tree，配好 modules.vhdx 后技术上走得通。 设备树 / platform driver / GPIO / 中断：只有真 Linux 才行。 而你手上那块 Pi，已经是"真 Linux + 真实外设"的最优解。

Q&A：这两个说法到底差在哪

Q：WSL2 到底能不能 insmod 自己写的 ko？

A：默认安装的不行 —— 它不提供与运行内核匹配的内核构建树（/lib/modules/$(uname -r)/build）， 你连编都编不出来。但这是"配置缺口"，不是"架构封死"：官方文档支持在 .wslconfig 里写 kernelModules=C:\...\modules.vhdx（需 WSL ≥ 2.5.1），微软的内核仓库还自带 Microsoft/scripts/gen_modules_vhdx.sh 一步生成它。

Q：那为什么结论仍然是"做驱动实验别用 WSL2"？

A：因为真正的短板不在 insmod 这个命令，而在有没有东西可驱动。WSL2 没有设备树、 没有 GPIO 控制器、没有真实外设，platform_driver 的 probe() 永远不会被调用； 而且 wsl --update 一升级内核，所有模块要全部重编。

Q：taint=4096 要不要管？

A：不用管，这是 out-of-tree 模块的常态（bit 12 = O）。但要知道它卸载也不清除， 想回到干净状态只能重启 —— 上报上游 bug 时对方会查这个值。
