CH3 · macOS / Xcode：另一套 clang，另一套账

导读

这一章解决什么困惑： 我明明在 Mac 上，gcc 却是 clang；两份 clang 版本号对不上； -g 编译完想调试，调试信息不知道去了哪里。

原因是苹果在工具链上叠了三层，而且每层都和你在 Linux 学到的不一样。

这节的三个结论

  1. Mac 上没有 GNU gcc。 /usr/bin/gcc 是一个 200KB 的转发 shim， 大小和内容都与 /usr/bin/clang 相同。真正的选择发生在 xcode-select 那一层。

  2. 这台机器当前是"许可未同意"状态，所以 shim 和 xcrun 全线报错。 绕过方法是直接用完整路径点名 Xcode 内的二进制并在编译时带 -isysroot； 根治方法是你本人执行 sudo xcodebuild -license。

  3. 两套 clang 不是同一个编译器。 同一台 Mac、同一份源码、同样的 -O2， Apple clang 21 正常退出，LLVM clang 23 生成死循环卡住。

记熟这四条之后，你对 Mac 的困惑基本清零 —— 剩下的差别都是"表面<｜hy_place▁holder▁no▁465｜>细节"， 而不是"认知框架"级别的。这也是把三个平台并列的意义：先看差异的形状， 再去记具体的拼写。

3.1

Mac 的工具链在地上叠了三层

← CH3 macOS/Xcode · 下一节：3.2 两套 clang 与版本矩阵 →

本节讲什么

Windows 那边的麻烦是"IDE 藏得太深"，Linux 那边的麻烦是"东西太多不知道谁是谁"。 Mac 的麻烦是第三种：苹果把工具链叠了三层，而且第三层会骗你。

这三层是：

第 3 层  /usr/bin/clang、/usr/bin/gcc   ← 「转发代理」，一个 200KB 的小二进制
第 2 层  Xcode.app 或 CommandLineTools  ← 真正的编译器 + SDK + lldb
第 1 层  xcode-select 决定第 3 层指向谁 ← 唯一需要记住的开关

要点

三层各自是什么

层 位置 干什么
shim（转发代理） /usr/bin/clang、/usr/bin/gcc、/usr/bin/make 不含任何编译器逻辑，只负责问 xcode-select：「现在该用哪套工具链？」再转发过去
工具链实体 /Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/ Apple clang、ld、lldb、swift 的真身
SDK .../Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk 头文件 + 库 + libc。编译器靠 -isysroot 找到它
选择器 xcode-select 决定 shim 转发到 Xcode.app 还是 Command Line Tools

实测：这台 Mac 现在的状态

$ xcode-select -p
/Applications/Xcode.app/Contents/Developer       # ← 指向完整 Xcode.app

$ xcrun --find clang
You have not agreed to the Xcode license agreements. Please run
'sudo xcodebuild -license' from within a Terminal window to review and agree
to the Xcode and Apple SDKs license.                    # ← 整条路被拦住

$ gcc --version
You have not agreed to the Xcode license agreements. ...  # ← 连 gcc 都同样是 shim

注意最后一条。 Mac 上你以为在敲 GNU gcc，其实 /usr/bin/gcc 和 /usr/bin/clang 是同一个 200560 字节的转发二进制：

$ ls -l /usr/bin/clang /usr/bin/gcc
-rwxr-xr-x  78 root  wheel  200560 ...  /usr/bin/clang
-rwxr-xr-x  78 root  wheel  200560 ...  /usr/bin/gcc

苹果这么做是为了兼容老脚本 —— 但它意味着 gcc --version 打印 clang 的版本号时， 你看到的不是 bug，是设计。Mac 上没有 GNU gcc（装的 brew gcc 另说）。

绕过许可：直接走完整路径

既然第 3 层被许可卡住，那就跳过它，直接点名第 2 层：

$ /Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/usr/bin/clang --version
Apple clang version 21.0.0 (clang-2100.3.34.2)
Target: arm64-apple-darwin27.0.0
Thread model: posix

并且能真的编译、真的跑（因为没有 SDK 就找不到头文件，所以要带 -isysroot）：

$ clang -isysroot /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk \
        hello.c -o hello && ./hello
hello from Apple clang

⚠️ 诚实交代： 这只是绕过了许可提示，不等于你没义务同意许可。 正规的解锁方式还是一条 sudo xcodebuild -license（要 sudo + 你自己读条款， 所以我不替你跑）。同意之后 xcrun / /usr/bin/clang / VS Code 的 C/C++ 插件才全部恢复。

版本号：这里有三套编号在互相打架

和 Windows 的 _MSC_VER（见 2.3）一个德行， Mac 这边也要对着表格换算：

说法 这台机器的值 谁在用
Xcode 版本 27.0 App Store、xcodebuild -version
Apple clang 版本 21.0.0 clang --version 打印的行首
LLVM 上游构建号 clang-2100.3.34.2 括号里，是 Apple 从 LLVM 某个快照打的分支
lldb 版本 lldb-2103.0.34.103 lldb --version，又是另一套编号
Swift 版本 Apple Swift 6.4 lldb --version 顺带打印的

对照 Linux 那边的惯例（LLVM 版本号 = 你从官网下载的 LLVM 版本号， 见 4.1），Mac 这套编号体系是苹果自己维护的分支， 和上游 LLVM 版本号之间没有换算公式，只能查表。

这就是为什么模块里另有一份 LLVM clang 23.1.0（micromamba cdev）。 两套 clang 并存不是冗余，它们是不同的编译器，下一节会用实测证明这一点。

与你的关系

场景 该用哪套 理由
学 TLPI / 系统编程 cdev 的 clang 23.1.0 版本紧跟上游，行为与你在书上读的一致；Pi 上的 clang 19 是同一族
编译 macOS GUI / 系统框架 Apple clang + SDK 只有它能吃下 -framework 和私有 SDK
初学 C 随便挑一套，但要知道是哪一套 因为它们的 UB 处理不一样 —— 下一节有实测

与后续衔接

既然这台机器上能同时叫出两套 clang，那就该问：它们是同一个编译器吗？ 3.2 两套 clang 与版本矩阵 用一个真实 bug 回答这个问题。

Q&A：为什么 xcode-select 存在？直接写死路径不行吗？

因为一台 Mac 上可能装了多版本 Xcode（正式版 + beta 并存）， CI、Xcode Server、命令行用户各自要用不同版本。xcode-select -s <路径> 就是这台机器的全局「当前 Xcode」开关。

CLI-only 的人通常刻意把它指到 Command Line Tools（体积小 20 倍）：

sudo xcode-select -s /Library/Developer/CommandLineTools

但你这台机器上命令会先被许可拦住，所以这条现在跑不了。

3.2

实测：同一份 bug，四个编译器给出三种答案

← 3.1 Xcode 工具链地图 · 下一节：3.3 实测 lldb →

本节讲什么

上一节留下一个疑问：「Apple clang 21」和「LLVM clang 23」是同一个东西换个版本号吗？ 不是。 这一节用一个真实 bug 把它们钉死。

素材是 demo/ptrbug.c（源码见下一）：一个故意越界读的求和函数。 它不崩、不报错，在 -O0 下输出完全正常。我们把同一份源码喂给四个编译器：

编号 编译器 平台
① Apple clang 21.0.0（Xcode 27） macOS arm64（本机）
② LLVM clang 23.1.0（micromamba cdev） macOS arm64（本机）
③ LLVM clang 19.1.7（Debian） Linux aarch64（你的 Pi）
④ gcc 14.2.0（Debian） Linux aarch64（你的 Pi）

要点：实测矩阵

-O0（不开优化）—— 四份全部一致，全部输出完整、exit=0：

sizeof(buf)      = 16 bytes, 4 elems
sum_n(buf, 4)   = 100
sum_n(buf, 8)    = 100   <-- 越界读，值不确定但通常不崩
buf=0x...        buf[0]=10  *(p+3)=40

-O2（开优化）—— 开始分裂：

编译器 ② clang 23.1.0 (macOS) ① Apple clang 21.0.0 (macOS) ③ clang 19.1.7 (Linux) ④ gcc 14.2.0 (Linux)
是否能跑完 ❌ 永久卡住 ✅ 正常退出 ✅ 正常退出 ✅ 正常退出
输出行数 只到第 1 行 4 行完整 4 行完整 4 行完整
加��后怎么办 SIGKILL 强杀 exit=0 exit=0 exit=0

证据一：clang 23 生成了什么

$ clang -O2 -std=c11 -S ptrbug.c -o ptrbug_o2.s
$ sed -n '20,24p' ptrbug_o2.s
    bl  _printf
LBB0_1:                                 ; =>This Inner Loop Header: Depth=1
    b   LBB0_1                          ; ← 跳回自己，无限空循环

main 里只剩一次 printf 和一个死循环。其余所有代码，包括 sum_n 的调用， 全部消失了。推理链条是：

编译器看见 sum_n(buf, 8) 越界 → 这是 UB
    ↓
UB 在标准里意味着"任何事都可能发生"，所以优化器有权假定它从不发生
    ↓
这条路径不可达 → 后面的所有 printf 都不可能执行 → 全部删除
    ↓
但万一真的执行到那个"不可能到达"的点呢 → 编译器给个兜底：跳到自身循环

证据二：同一台 Mac 换个编译器就不一样

$ /Applications/Xcode.app/.../usr/bin/clang -isysroot ... -O2 ptrbug.c -o ptrbug_ac21
$ ./ptrbug_ac21
sizeof(buf)      = 16 bytes, 4 elems
sum_n(buf, 4)   = 100
sum_n(buf, 8)    = 100   <-- 越界读，值不确定但通常不崩
buf=0x10226c000  buf[0]=10  *(p+3)=40
[正常退出]

$ grep -cE "^\s+b\s+LBB0_1" ac21.s
0                                        # ← 没有自我跳转

关键结论： ① 和 ② 在同一台机器、同一个 CPU、同一个 OS 上， 差别只有编译器版本（Apple clang 21 vs LLVM clang 23）。 所以「-O2 会生成死循环」不是 macOS 的锅，是 LLVM 23 更激进的 UB 推断策略。

修正上一版结论

本模块初版（提交 ba7f13bc0）曾写下"-O2 下必卡死"的断言。上面四组实测证明那是过度概括。 正确表述是：

UB 的后果取决于「编译器 + 版本 + 优化级别 + 目标平台」这四者的组合。 没有任何一项能单独决定结果。同一份源码换个编译器就可能从"看起来没问题"变成"永久卡死"。

这也正好解释了为什么 C 里那么多 bug 在开发环境不复现、到 CI 或客户机器上才炸。

越界那 4 格为什么恰好是 0

buf 是 static，后面紧接着的内存恰好全零，所以越界读到的都是 0、 sum_n(buf,8) 才碰巧等于正确值 100。Mac 的 lldb 与 Pi 的 gdb 都转储到了同一幅景象：

0x555555570040 <buf>:  10  20  30  40      ← buf[0..3]
0x555555570050:         0   0   0   0      ← buf[4..7]，越界读的就是这里

这是最坏的一种 bug：错得无影无踪。它之所以必讲，是因为 printf 查不出来、valgrind 之外几乎无从下手，只有调试器/ sanitizer 能当场抓住。

与后续衔接

要抓住它，得靠工具。ASan 一句话就能定性，而拿到 Pi 上更方便的是 gdb：

$ clang -g -O1 -fsanitize=address -fno-omit-frame-pointer -std=c11 ptrbug.c -o ptrbug_asan && ./ptrbug_asan
==ERROR: AddressSanitizer: global-buffer-overflow on address ...
READ of size 4 at ... thread T0
    #0 0x... in sum_n ptrbug.c:34
    #1 0x... in main ptrbug.c:49
SUMMARY: AddressSanitizer: global-buffer-overflow ptrbug.c:34 in sum_n

Mac 侧的完整 lldb 会话在 3.3， Linux 侧的 gdb 会话（同样是真实输出）在 4.3。

Q&A：那我到底该用哪个编译器？

别纠结"最好"，先固定一个、并把它写进 CI：

  • 学 TLPI / 写跨平台代码 → 用 Linux 上的 gcc + clang 双跑（你 Pi 上两个都有）， 两个都过了，才敢说代码没踩 UB；
  • Mac 本机快速验证 → cdev 的 clang 23，记住它比 Xcode 那套更激进， 所以它能跑过、clang 19 未必；反过来不成立。
3.3

Mac 实测：一次完整的 lldb 会话

← 3.2 两套 clang 与版本矩阵 · CH3 macOS/Xcode · 下一节：3.4 Mach-O 与 dSYM →

本节讲什么

把 CH1 1.4 调试四件事 的四件事在你这台 Mac 上真跑一遍。 下面所有终端输出都是 2026-09-26 本机真实输出，不是示意。

⚠️ 一个前置事实（实测确认）： 你 cdev 环境里的 lldb 22.1.8 不能用 —— 它缺 debugserver：

text $ lldb --version lldb version 22.1.8 $ lldb --batch -o "breakpoint set --file ptrbug.c --line 34" -o run -- ./ptrbug (lldb) run error: could not find 'debugserver'. Please ensure it is properly installed and available in your PATH

原因：macOS 上 lldb 依赖一个叫 debugserver 的调试服务端（负责真正操作进程）， 它由 Xcode 提供，不在 LLVM/conda 的分发里。好消息是你装了 Xcode 27.0， 它自带配套的 lldb 与 debugserver：

text /Applications/Xcode.app/Contents/Developer/usr/bin/lldb (lldb-2103.0.34.103) /Applications/Xcode.app/Contents/SharedFrameworks/LLDB.framework/Versions/A/Resources/debugserver

即使没同意 Xcode 许可协议，/Applications/Xcode.app/.../bin/lldb 这个二进制也能直接调用 （✅ 实测 —— 被挡的是 xcrun，不是 lldb 本体）。 所以下文用它。

⚠️ 另一个实测约束：进程附加会被沙箱拦住，报 attach failed (attached to process, but could not pause execution)。 在终端里正常执行不受影响。

要点

准备：编译带调试信息的靶子

$ cd demo
$ clang -g -O0 -Wall -Wextra -std=c11 ptrbug.c -o ptrbug
$ ./ptrbug
sizeof(buf)      = 16 bytes, 4 elems
sum_n(buf, 4)   = 100
sum_n(buf, 8)    = 100   <-- 越界读，值不确定但通常不崩
buf=0x1020d4010  buf[0]=10  *(p+3)=40

✅ 实测。注意最后第二行：越界读竟然返回了正确的 100。 一个也不崩、一个也不错 —— 这种"看起来没事"的 bug 才是最贵的那种。

第一次断点：看四件套里的①④

    -o "breakpoint set --file ptrbug.c --line 34" \
    -o "run" -o "frame variable" -o "bt" -o "continue" -- ./ptrbug

✅ 实测。四个关键观察：

  1. 断点信息里带了行号和列号：at ptrbug.c:34:14 —— 靠 DWARF 才能有
  2. 源码上下文自动打印，-> 指着当前行 —— 这就是 VS 里那个黄色箭头
  3. frame variable 一次给出全部局部变量 + 参数（a 是 int 常量指针、n、s、i）
  4. bt 显示三层栈：sum_n ← main:48 ← dyld start

对照 VS：这段输出 = 局部变量窗口 + 调用堆栈窗口 + 编辑器里的黄色箭头，三合一。

条件断点：直达越界那一刻

sum_n 被调用两次。用条件断点只看越界那次（n==8）：

$ lldb --batch \
    -o "breakpoint set --file ptrbug.c --line 34 --condition 'n==8'" \
    -o "run" -o "continue" -o "continue" -o "continue" -o "continue" -o "continue" \
    -o "frame variable" -o "x/12w &buf" -o "bt" -o "kill" -- ./ptrbug

(lldb) frame variable
(const int *) a = 0x0000000100008010
(int) n = 8
(int) s = 100
(int) i = 5
(lldb) x/12w &buf
0x100008010: 0x0000000a 0x00000014 0x0000001e 0x00000028
0x100008020: 0x00000000 0x00000000 0x00000000 0x00000000
0x100008030: 0x00000000 0x00000000 0x00000000 0x00000000
(lldb) bt
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
   * frame #0: 0x0000000100003ea4 ptrbug`sum_n(a=0x0000000100008010, n=8) at ptrbug.c:34:14
     frame #1: 0x0000000100003df0 ptrbug`main at ptrbug.c:49:15
     frame #2: 0x0000000192837e80 dyld`start + 6688
(lldb) kill
Process 13097 exited with status = 9 (0x00000009) killed

✅ 实测。这一段是整个模块的点睛之笔，把谜底解开了：

① i = 5 —— buf 只有 4 个元素（下标 0–3），程序正在读 buf[5]，早就越界了。

② s = 100 —— 前 4 个元素的和是 100，越界那几格没改变结果。为什么？看内存：

内存地址 值（十六进制） 含义
0x100008010 0x0a buf[0] = 10 ✓
0x100008014 0x14 buf[1] = 20 ✓
0x100008018 0x1e buf[2] = 30 ✓
0x10000801c 0x28 buf[3] = 40 ✓
0x100008020 0x00 ← 越界区开始，全是 0
0x100008024 0x00 ← 0，加进 s 不影响结果
… 0x00 全是 0

buf 后面那段内存恰好是 0，所以 sum_n(buf, 8) 碰巧返回了正确答案。 这不是"程序没 bug"，这是"这一次运气好"。换变量布局、换编译器、换优化级别，随时可能翻脸。

③ bt 的 main at ptrbug.c:49:15 —— 精确告诉你越界是从第 49 行发起的， 而不是 48 行（48 行是那次正确的调用）。这个数字是 printf 调试法永远给不了你的。

同一个 bug，换个优化级别就翻脸

把 -O0 换成 -O2，同一个源文件：

$ clang -g -O2 -Wall -Wextra -std=c11 ptrbug.c -o ptrbug_o2
$ ./ptrbug_o2
sizeof(buf)      = 16 bytes, 4 elems
（然后永久卡住，3 秒后被强制终止，status=9）

✅ 实测：-O0 下 4 行正常输出、exit=0；-O2 下只吐出第 1 行就再也不返回了。

看它生成了什么（截取 main 的关键部分，✅ 实测自 --batch 的 -S 输出）：

_main:
    .cfi_startproc
; %bb.0:
    sub sp, sp, #32
    stp x29, x30, [sp, #16]
    add x29, sp, #16
    mov w8, #4
    mov w9, #16
    stp x9, x8, [sp]
    adrp    x0, l_.str@PAGE
    add x0, x0, l_.str@PAGEOFF
    bl  _printf          ← 只调用了一次 printf（第 1 行输出）
LBB0_1:                                 ; =>This Inner Loop Header: Depth=1
    b   LBB0_1          ← 无条件跳回自己：无限空循环
    .cfi_endproc

汇编里 main 只剩下一次 printf 和一个跳向自己的无限循环。 其余所有代码（第二个第三个 printf、sum_n 的调用）全部被删除了。

发生了什么：

  1. clang 看见 sum_n(buf, 8) 会读 buf[4..7] → 判定为 UB（未定义行为）
  2. 优化器的基本公理是"UB 永远不会发生"，于是推断这条路径不可达
  3. 依赖它的返回值变成 poison（无意义），所有后续 printf 被常量折叠 / 消除
  4. 但控制流真的流到了那个"不可能到达"的点，需要兜底 → 生成一个无限空循环

这才是 UB 的真正含义：不是"偶尔算错"，是编译器有权按它的假设重写你的整个程序。 MSVC 遇到同样的 UB 也会做类似推断，只是表现形式不同。

让工具替你抓：ASan

$ clang -g -O1 -fsanitize=address -fno-omit-frame-pointer -Wall -std=c11 ptrbug.c -o ptrbug_asan
$ ./ptrbug_asan
=================================================================
==13007==ERROR: AddressSanitizer: global-buffer-overflow on address 0x0001042c41f0
READ of size 4 at 0x0001042c41f0 thread T0
    #0 0x0001042bfba4 in sum_n ptrbug.c:34
    #1 0x0001042bfba4 in main ptrbug.c:49
    #2 0x000192837e7c in start+0x1a1c (dyld:arm64e+0x31e7c)

0x0001042c41f0 is located 0 bytes after global variable 'buf' defined in 'ptrbug.c' (0x0001042c41e0) of size 16
SUMMARY: AddressSanitizer: global-buffer-overflow ptrbug.c:34 in sum_n

sizeof(buf)      = 16 bytes, 4 elems
$ echo $?
134

✅ 实测。ASan 给出的信息和 lldb 完全一致，而且更明确：

  • READ of size 4 —— 越界读取 4 字节
  • in sum_n ptrbug.c:34 ← in main ptrbug.c:49 —— 精确的行号链
  • 0 bytes after global variable 'buf' ... of size 16 —— 正好落在 buf 尾部之后第 0 字节， 和我们用 x/12w &buf 看到的那片 0x00 区域严丝合缝
  • exit=134（SIGABRT）

-O0 看不出来、-O2 直接卡死、ASan 一句话命中 —— 三种手段的成本收益一目了然。 系统化的工具清单见 03.6 用户态调试。

3.4

Mac 的「分离税」：Mach-O 不放调试信息

← 3.3 实测 lldb · 下一节：CH4 Linux/GNU →

本节讲什么

Linux 上 gcc -g a.c -o a.out，调试信息就在 a.out 里，拷走这一个文件就够。 Windows 上 cl /Zi，调试信息进 .pdb，要和 exe 一起带着。 Mac 上两样都不是：-g 之后可执行文件几乎没变大，调试信息去了一个第三方 —— dSYM。

这一节专门讲这笔"分离税"，因为它踩过一次就够你找一晚上。

要点

实测：加不加 -g，可执行文件几乎一样大

$ clang -O0 -std=c11 ptrbug.c -o ptrbug_nodbg      # 不带 -g
$ clang -c -g -O0 -std=c11 ptrbug.c -o ptrbug.o
$ clang -g ptrbug.o -o ptrbug                      # 带 -g（保留中间 .o）

$ ls -l ptrbug_nodbg ptrbug | awk '{print $5, $9}'
70136 ptrbug_nodbg
70544 ptrbug                                        # ← 只多了 408 字节

$ llvm-dwarfdump ptrbug | grep -c DW_TAG
0                                                   # ← 可执行文件里一个 tag 都没有
$ llvm-dwarfdump ptrbug.o | grep -c DW_TAG
35                                                  # ← 全在 .o 里

对比 Linux 上同一个实验（见 4.4）： gcc -g 让文件从 70520 → 72192 字节，readelf 直接在 ELF 里读到 .debug_info。 Linux <｜hy_place▁holder▁no▁813｜>内嵌，macOS 靠外挂。

dSYM 才是调试器真正要的东西

$ dsymutil ptrbug
$ ls -d ptrbug.dSYM && du -sh ptrbug.dSYM
 20K    ptrbug.dSYM

$ llvm-dwarfdump ptrbug.dSYM/Contents/Resources/DWARF/ptrbug | grep -c DW_TAG
22
$ llvm-dwarfdump ptrbug.dSYM/.../ptrbug | grep -E "DW_AT_(name|decl_line)"
DW_AT_name      ("main")
DW_AT_decl_line (39)
DW_AT_name      ("bad")
DW_AT_decl_line (49)

最大的那个坑：一步到位就再也补不回来

$ clang -g ptrbug.c -o ptrbug        # 不保留 .o，clang 用临时文件，编译完就删
$ dsymutil ptrbug
error: unable to open ...            # ← 中间 .o 没了，dsymutil 无从下手

所以正确姿势是拆两步，或者干脆用 -g -gsplit-dwarf / 构建系统帮你保留：

%.o: %.c
    $(CC) -c -g -O0 $< -o $@        # 必须落地成文件
%: %.o
    $(CC) -g $< -o $@
    dsymutil $@                     # 链接完立刻生成 dSYM

demo/Makefile 里就是这么写的（make all 会自动产出 .dSYM）。

三平台调试信息容器对照

Windows (MSVC) macOS (Apple clang) Linux (gcc/clang)
文件格式 PE/COFF（.exe .dll） Mach-O ELF
调试信息放哪 .pdb（独立文件） .dSYM/ bundle（独立目录） ELF 内部 .debug_* 节
-g//Zi 后本体变大吗 基本不变 基本不变（实测 +408 B） 变大（实测 +1672 B）
只拷可执行文件能调试吗 ❌ 要带 pdb ❌ 要带 dSYM ✅ 可以
查看工具 dumpbin / DIA llvm-dwarfdump、dsymutil readelf、objdump、llvm-dwarfdump
符号剥离 /PDBSTRIPPED strip（dSYM 不受影响） strip / objcopy --only-keep-debug

还有一笔税：debugserver 与进程附加

lldb 在 macOS 上不是直接抓进程，它要通过一个独立服务 debugserver （位于 LLDB.framework/.../Resources/debugserver）来 attach。两个后果：

  1. conda/micromamba 装的 lldb 通常不带 debugserver —— 版本号能打印、能 file 加载， 一到 run 就报找不到调试服务端；能用的是 Xcode 自带的那只 （/Applications/Xcode.app/Contents/Developer/usr/bin/lldb，实测 lldb-2103.0.34.103）。
  2. macOS 的进程附加权限会拦住非终端里的调试器。我在沙箱里跑 lldb 时得到：

error: attach failed: ...

脱离沙箱（真正的终端授权）后立刻正常。如果你在 VS Code / CLion 里遇到这种报错， 多半是同一类权限问题，不是配置写错了。

Q&A：Mach-O 和 ELF 的差别需要现在就学吗？

不用背结构。只要知道三条就够用现阶段：

  1. 格式决定了"谁能加载它"：Mach-O 只有 macOS/iOS 的 dyld 认，ELF 只有 Linux 的 ld.so 认；
  2. 不能互相运行，哪怕同为 arm64 —— 所以你在 Mac 上编译的二进制拷到 Pi 上一定报 cannot execute binary file: Exec format error（这条错误的意思是"格式不对"，不是"架构不对"）；
  3. 想深挖时再看：llvm-objdump --macho --private-headers / otool -l。
