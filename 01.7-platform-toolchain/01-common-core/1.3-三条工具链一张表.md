# 1.3 三条工具链一张表

[← 1.2 四件套解剖](./1.2-四件套解剖.md) · [CH1 工具链解剖](./README.md)

## 本节讲什么

一张能贴在墙上的总表：**同一个角色，在三个世界里分别叫什么、产出什么格式**。
后面所有章节（选项对照、版本号、调试信息）都是这张表的某一行展开。

## 要点

### 主表：工具链四件套三族对照

| 角色 | Windows / MSVC | macOS / Apple-LLVM | Linux / GNU |
|------|----------------|---------------------|-------------|
| **编译器** | `cl.exe` | `clang`（Apple clang 或 LLVM clang） | `gcc` / `clang` |
| **C++ 编译器** | 同一个 `cl.exe`（靠文件后缀区分） | `clang++` | `g++` |
| **汇编器** | `ml64.exe`（一般不需要手动调用） | 集成在 `clang` 里 | `as`（一般不需要手动调用） |
| **链接器** | `link.exe` | `ld64`（Apple 专用）| `ld`（GNU bfd）/ `gold` / `lld` |
| **构建系统** | **MSBuild**（`.vcxproj` 是它的输入） | CMake / make / ninja / Xcode | CMake / make / ninja |
| **调试器** | VS 调试引擎 / WinDbg / `cdb` | `lldb` | `gdb` / `lldb` |
| **归档工具** | `lib.exe` | `ar` / `libtool` | `ar` |
| **查看目标文件** | `dumpbin.exe` | `llvm-objdump` / `otool` | `objdump` / `readelf` |

### 产出格式对照

| 产物 | Windows | macOS | Linux |
|------|---------|-------|-------|
| 目标文件 | `.obj`（COFF） | `.o`（Mach-O） | `.o`（ELF） |
| 可执行文件 | `.exe`（PE/COFF） | 无后缀（Mach-O） | 无后缀（ELF） |
| 静态库 | `.lib` | `.a` | `.a` |
| 动态库 | `.dll`（+ 导入库 `.lib`） | `.dylib` / `.framework` | `.so` |
| 调试信息 | `.pdb`（Program Database） | DWARF：留在 `.o` 里，或 `dsymutil` 抽出成 `.dSYM/` bundle | DWARF：默认直接嵌进可执行文件 |
| CRuntime | UCRT + `vcruntime140.dll` | `libSystem`（含 libc） | glibc / musl |

### 你的三台机器分别落在哪一列

| 机器 | CPU / OS | 工具链 | 备注 |
|------|----------|--------|------|
| **本机 Mac** | Apple Silicon / macOS | macOS 列：clang 23.1.0（cdev）+ Xcode 27.0 的 lldb | ✅ 主力机，本模块实测环境 |
| **树莓派 5** | aarch64 / Debian 13 | Linux 列：gcc 14.2 + clang 19 + lld 19 | eBPF 与交叉编译平台 |
| **（已失去的）Windows** | x86_64 | MSVC 列 | ⚠️ 本模块的 MSVC 内容因此**只能依据官方文档整理** |

> 三列各占一台机器不是巧合 —— 这正是"跨平台代码为什么要过三关"的现实来源。
> 同一份 C 代码在三列上的差异，[第 4 章](../05-boundary/) 会逐项列清楚。
