# 1.2 四件套解剖：按一次 F5 都惊动了谁

[← 1.1 IDE 不是编译器](./1.1-IDE不是编译器.md) · 下一节：[1.3 三条工具链一张表 →](./1.3-三条工具链一张表.md)

## 本节讲什么

把 VS 里一次「本地 Windows 调试器」按钮按下之后发生的事情，一层一层拆到 `cl.exe` 为止。
然后你会发现：这套层级在 CMake/Makefile 世界里有一个完整的对应物。

## 要点

### 一次 F5 的完整链路

```text
① 你按 F5
      ↓
② Visual Studio（IDE）读取 .sln ← 找到里面的 .vcxproj
      ↓
③ 把 .vcxproj（XML）喂给 MSBuild（构建引擎）
      ↓
④ MSBuild 判断哪些文件过期了，需要重编
      ↓
⑤ 对每个 .c 调用   cl.exe /c /Zi ... file.c   → 生成 file.obj（同时更新 .pdb）
      ↓
⑥ 全部编完后调用   link.exe *.obj /OUT:app.exe /DEBUG   → 生成 app.exe + app.pdb
      ↓
⑦ 启动 app.exe，由 VS 调试引擎接管，读取 app.pdb 才能显示源码行和变量名
```

**每层只管一件事**，这是个重要的设计原则：

| 层 | 只负责 | 不负责 |
|----|--------|--------|
| `.sln`（解决方案） | 把若干**项目**打包，定义它们的构建顺序和依赖 | 不管具体怎么编译单个文件 |
| `.vcxproj`（项目文件） | 列出源文件、编译选项、链接选项（本质是 XML） | 不管执行，只是"描述" |
| **MSBuild** | 读 XML，**增量判断**、调度真正的编译/链接命令 | 它自己不认识 C 语法 |
| `cl.exe` | 只做翻译：`.c` → `.obj` | 不管先后顺序，一次只处理一个翻译单元 |
| `link.exe` | 把 `.obj` 和 `.lib` 拼装成 `.exe`/`.dll` | 不管编译优化 |
| VS 调试引擎 | 读 `.pdb`，把机器地址和源码行/变量名对应起来 | 不管编译 |

### 逐层对照到你已经会的东西

这张表是全章最该记住的一张：

| MSVC 世界 | CMake / make 世界 | 说明 |
|-----------|-------------------|------|
| `.sln` 解决方案 | 顶层 `CMakeLists.txt` 里的多个 `add_subdirectory` / `project` | 都是"一组项目的容器" |
| `.vcxproj` 项目文件 | 每个目标的 `CMakeLists.txt` | 都是"描述一个产出物的输入清单" |
| MSBuild | `cmake` 生成 `Makefile`/`ninja` 后由 `make`/`ninja` 执行 | 都是"调度器"，决定重编谁 |
| `cl.exe` | `clang` / `gcc` | 编译器 |
| `link.exe` | `ld64`（macOS）/ `ld`（Linux）/ `lld` | 链接器 |
| `.obj` | `.o` | 目标文件（不同格式：COFF / Mach-O / ELF） |
| `.lib`（静态库） | `.a` | 静态库归档 |
| `.dll` | `.dylib` / `.so` | 动态库 |
| `.pdb` | DWARF（Linux 嵌在可执行文件；macOS 在 `.o` / `.dSYM`） | 调试信息，见 [2.5](../02-windows-msvc/2.5-调试信息三种容器.md) |
| `.exe` | 无后缀 ELF / Mach-O | 可执行文件 |

### 第三方库为什么总是「include/ + lib/」两件套

上一张表列了 `.a` `.lib` `.so` `.dylib` 这些后缀，但没回答一个更基本的问题：
**为什么 download 一个库，解压出来永远是两个目录，而不是一坨源码？**

```text
MyLib/
├── include/add.h        ← 头文件：只有一行声明  int add(int a, int b);
└── lib/
    ├── libadd.a         ← 静态库（预编译好的 .o 打包）
    └── libadd.dylib     ← 动态库
```

答案藏在上表的**分工**里：

| 角色 | 需要的东西 | 来自 |
|------|-----------|------|
| **编译器**（`clang`/`cl`）处理你的 `.cpp` | 只要知道「`add` 长什么样」→ **声明** | `include/add.h` |
| **链接器**（`ld64`/`link`）拼成品 | 要真正的机器码 / 符号表 | `lib/` 里的二进制 |
| **加载器**（运行时） | 动态库本体 | `lib/` 里的 `.dylib`/`.dll` |

所以库作者**不用给源码**：声明给编译器看，实现以编译好的二进制给链接器看——两边对上就能链接成功。这也是闭源库的标准分发形态。

```bash
clang++ -std=c++20 -c main.cpp -I MyLib/include -o main.o   # -I：告诉编译器去哪找声明
clang++ main.o -L MyLib/lib -ladd -o app                    # -L/-l：告诉链接器去哪找实现
```

**`-I` 管编译期，`-L` 管链接期**——CMake 里的 `target_include_directories` 和 `target_link_libraries` 就各自对应这两个（见 [01.5 第 3 章](../../01.5-cmake-build/03-libraries-multi-dir/README.md)）。

### 静态 vs 动态：本机实测（clang 23.1.0，macOS）

同一个 `add()` ，两种打包方式，`MyLib/include/add.h` 完全不动，只换 `lib/` 里的内容：

```bash
# 静态库：先把源码编成 .o，再用 ar 打包
ar rcs MyLib/lib/libadd.a add.o
clang++ main.o -L MyLib/lib -ladd -o app_static

# 动态库：-shared 一步生成
clang++ -std=c++20 -shared -fPIC add.cpp -o MyLib/lib/libadd.dylib
clang++ main.cpp -I MyLib/include -L MyLib/lib -ladd -o app_dyn
```

两个程序都能跑，输出都是 `7`。区别只有一串命令能看出来：

```bash
nm MyLib/lib/libadd.a          # 静态库：符号就躺在里面
  MyLib/lib/libadd.a(add.o):
  0000000000000000 T __Z3addii        ← T = 已定义的机器码

otool -L app_dyn                # 动态库：可执行文件里只留了一张"欠条"
  @rpath/libadd.dylib (compatibility version 0.0.0, current version 0.0.0)
```

**删库实验**（最有说服力的一个）：

| 操作 | `app_static` | `app_dyn` |
|------|-------------|-----------|
| 删掉 `lib/` 里的库文件后运行 | ✅ 照样输出 `7` | ❌ `dyld: Library not loaded: @rpath/libadd.dylib` |

这就是本质差别：**静态库在链接时被拷进了可执行文件**（之后自包含，删库无感）；
**动态库只有运行 dlopen 的时候才被加载**（二进制里记的只是名字，库不在就起不来）。

| 维度 | 静态库 `.a` / `.lib` | 动态库 `.dylib` / `.so` / `.dll` |
|------|---------------------|----------------------------------|
| 代码进你的程序 | 链接期拷贝进去 | 运行期才加载 |
| 分发 | 只发一个可执行文件 | 必须连库一起发 |
| 更新库 | 全量重新链接 | 换 `.so` 即可（ABI 兼容前提） |
| 磁盘/内存 | 每个程序一份拷贝 | 多进程共享一份（Linux 页面共享） |
| 找不到库的报错 | 链接期：`undefined symbols`（`-lxxx` 没给对） | 运行期：`Library not loaded` / `cannot open shared object file` |

> Linux 上等价命令：`ldd ./app` 看依赖、`readelf -d` 看 dynamic section、`nm -D` 看动态符号；
> macOS 是 `otool -L` / `nm -m`。概念完全一致，命令不同而已。

### 关键洞察：CMake 为什么能横跨两边

MSBuild 的输入是 XML，make 的输入是 Makefile，你看过去是两套完全不同的东西 ——
**CMake 的作用就是在它们之上再抽一层**：

```text
   CMakeLists.txt（你写的，平台无关）
          │
          ├─ cmake -G "Visual Studio 17 2022"  → .sln + .vcxproj   → MSBuild → cl.exe
          ├─ cmake -G "Unix Makefiles"         → Makefile           → make    → clang
          └─ cmake -G "Ninja"                  → build.ninja        → ninja   → clang
```

所以 CMake **既不是 make 的插件，也不是它的替代品**，它是"生成器"——
生成的是某个具体构建系统的输入。仓库里 [projects/CMAKE-VS-MAKEFILE.md](./../../projects/CMAKE-VS-MAKEFILE.md)
已经把这段关系讲透了，这里不重复。

> **这也意味着：** 你学过的 CMake 语法，在 Windows/MSVC 上**照样能用**。
> 而反过来,手写 `.vcxproj` 的技能，出了 Windows 就没用了。这就是投资哪边的答案。
