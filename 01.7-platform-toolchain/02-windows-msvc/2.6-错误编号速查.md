# 2.6 错误编号速查：Cxxxx 是编译期，LNKxxxx 是链接期

[← CH2 MSVC 编译器与选项](./README.md) · 上一节：[2.5 调试信息三种容器](./2.5-调试信息三种容器.md) · 下一节：[CH3 macOS / Xcode →](../03-macos-xcode/README.md)

## 本节讲什么

看到 `error C2065` 和 `error LNK2019` 时，怎么**一眼判断它发生在哪一步、该去哪儿改**。
判据很简单：**前缀 = 出问题的工具**，`C` 是编译器 `cl.exe`，`LNK` 是链接器 `link.exe`。
但前缀之外还有一堆细节——尤其"警告变错误"会让 C 编号出现在你以为不该出现的地方。

> 📌 **本节来源标注**（重要）：
> - **Cxxxx / LNKxxxx 编号与官方措辞**：来自 Microsoft Learn 官方文档（本节末尾列出了核到的页面），
>   **本机是 macOS，无 MSVC，未逐条复跑**，标 ⚠️。
> - **clang / ld64 侧**：全部为**本机实测**（Apple clang 23.1.0，arm64-apple-darwin27），标 ✅。
>   用它做"同一类错误在另一套工具链长什么样"的对照。

## 要点

### 一、前缀 = 出问题的工具（不止 C 和 LNK 两种）

你的清单只给了 `C` 和 `LNK`，实际上 VS 构建链上还有好几个前缀，撞上了要认得：

| 前缀 | 谁报的 | 阶段 | 典型编号 |
|------|--------|------|----------|
| **C** | `cl.exe` 编译器 | 编译期（单个翻译单元） | C1083 / C2065 / C4013 |
| **LNK** | `link.exe`、`lib.exe`、`dumpbin.exe`、`editbin.exe` | 链接期 / 库工具 | LNK2019 / LNK2005 / LNK1104 |
| **D** | `cl.exe` 的**命令行驱动** | 还没开始编译 | D8003 命令行选项错误、D8016 选项冲突 |
| **MSB** | MSBuild | 构建脚本层（在 C/LNK 之外） | MSB3073 自定义生成步骤失败 |
| **RC** | 资源编译器 `rc.exe` | 编译 `.rc` | RC2170 位图文件找不到 |
| **MIDL** | `midl.exe` | COM / IDL 编译 | MIDL2025 语法错误 |
| **CVT** | `cvtres.exe` | 转资源目标文件 | CVT1100 资源文件损坏 |
| **U1** | `nmake.exe` | Makefile 执行 | U1073 不知道如何生成目标 |

⚠️ **一个容易忽略的事实**：`LNK` 不是 link.exe 独占。
官方文档原话是 `LINK, LIB, DUMPBIN, and EDITBIN share a common executable`——
**它们共用同一个可执行文件**，所以 `lib.exe`（建静态库的）报错也是 `LNKxxxx`。
看到 LNK 就说"链接器"，在 `lib` 场景会误判。

### 二、C 段内部还分三档（不是"有 C 就编译失败"）

| 段 | 性质 | 代表 | 会不会终止编译 |
|----|------|------|----------------|
| **C1xxx** | **fatal error** | `fatal error C1083: Cannot open include file` | **会**，且立即停 |
| **C2xxx** | error（语法/语义） | `error C2065: 'x': undeclared identifier` | 会，该 TU 不出 `.obj` |
| **C4xxx** | **warning**（分级别 /W1–/W4） | `warning C4013`、`C4996`、`C4244` | **默认不会** |

⚠️ **你举的 C4013 其实是警告，不是错误。**
官方页面标题就是 `Compiler Warning (level 3) C4013`，原文
`'function' undefined; assuming extern returning int`。
也就是说：**默认配置下调用没声明的函数，MSVC 只警告、照样编出 `.obj`，然后到链接期才炸**
（`undefined external`）。这恰好是你后面那句"C4xxx 很多是警告"的活例子——
但前面把它列进"C 开头错误"的例子里，前后会打架。

想把 C4013 变成真错误，两条路（⚠️ 官方/社区文档）：

```bat
cl /WX hello.c           :: 所有警告视为错误
cl /we4013 hello.c       :: 只把 C4013 视为错误   ← 推荐，比 /WX 温和
```

`#pragma warning(error:4013)` 是源码内的等价写法。
用 `/WX` 时 MSVC 会**额外报一条 `C2220: warning treated as error - no object file generated`**，
这就是"编译期明明是警告，编号却仍是 C、且 `.obj` 没了"的来源。

**对照（✅ 本机实测，clang 23.1.0）**——注意 clang 的取向已经变了：

```console
$ clang -std=c17 -c e_implicit.c -o /dev/null
e_implicit.c:2:12: error: call to undeclared function 'foo'; ISO C99 and later do not support
              implicit function declarations [-Wimplicit-function-declaration]

$ clang -std=c23 -c e_implicit.c -o /dev/null
e_implicit.c:2:12: error: use of undeclared identifier 'foo'; did you mean 'for'?
```

**C23 起隐式函数声明已被标准彻底移除**，clang 23 默认就当 error（不再是 warning）。
所以"古老 C 语言问题"这个说法在今天要加一句：**在 MSVC 里它还是警告，在 clang 23 / GCC 14+ 里已经是错误。**

### 三、LNK 段内部也分档

| 编号 | 性质 | 官方措辞（要点） |
|------|------|------------------|
| **LNK2019** | error | `unresolved external symbol ... referenced in function ...` |
| **LNK2005** | error | `symbol already defined in object` |
| **LNK1104** | **fatal** | `cannot open file 'xxx.lib'` |
| **LNK1120** | **fatal** | `N unresolved externals` ← **只是计数**，告诉你共几个 |
| **LNK1169** | **fatal** | `one or more multiply defined symbols found`（紧跟 LNK2005 之后） |
| **LNK1561** | **fatal** | `entry point must be defined`（**没写 `main`** 时是这条，不是 2019） |
| **LNK4098 / LNK4099** | warning | 默认库冲突 / PDB 未找到 |

⚠️ **你的清单漏了两条最常见的链接错误**：`LNK2005`（重复定义）和 `LNK1561`（没有 main）。
LNK2019 只覆盖"声明了没定义"这一种，另外两种走别的号。

**对照（✅ 本机实测）**：

```console
$ clang d1.o d2.o -o app3                 # 两个 .c 都定义了 int g
duplicate symbol '_g' in:  d1.o / d2.o
ld: 1 duplicate symbol for architecture arm64

$ clang nm.o -o app5                      # 没有 main，只有 helper()
Undefined symbols for architecture arm64:
  "_main", referenced from:  implicit entry/start for main executable
```

注意 macOS 的 `ld64` 把这两类都塞进 "Undefined symbols" 里，**没有细分编号**——
这正是 MSVC 编号体系有优势的地方：一眼能从号上分辨"是缺符号、重复符号、还是缺入口点"。

### 四、三句话判据（你给的已经对，我压缩成一张表）

| 判据 | 编译期（Cxxxx） | 链接期（LNKxxxx） |
|------|----------------|-------------------|
| 谁报 | `cl.exe` | `link.exe` / `lib.exe` |
| 什么时候 | 逐 `.c/.cpp` 翻成 `.obj` 时 | 所有 `.obj` 已齐，合并时 |
| 典型问题 | 语法、类型、缺头文件、标识符没声明 | 符号找不到 / 重复定义 / 库缺失 / 缺入口点 |
| 出错后 | **该文件**不出 `.obj` | 不出 `.exe/.dll`（**`.obj` 都还好好在**） |
| 修的方向 | 改代码、补 `#include`、加声明 | 补实现、补 `.lib`、删重复定义、查运行时库一致性 |

⚠️ **一处要收窄的说法**：你说"C 报错，连 obj 都出不来"。
准确讲是**"该翻译单元不出 `.obj`"**——工程里别的文件照常编译、照常出 `.obj`。
所以报错后去看 `obj/` 目录，往往能看到"一半文件有 obj，一半没有"。
这也是为什么 VS 一次能列出几十条错误：它没停在整个工程的第一条上。

## 你的三道自测题：答案与一个反例

| 题 | 你的答案 | 判定 |
|----|----------|------|
| 写了函数声明，忘记写函数实现 | LNK2019 | ✅ 对，但**有条件**（见下） |
| 变量没定义直接使用 | C2065 | ✅ 对（`undeclared identifier`） |
| `#include "xxx.h"` 头文件不存在 | C1083 | ✅ 对（准确说是 **fatal error** C1083） |

**⚠️ 第 1 题的反例（这是本节最值钱的一条）：**
**声明了但没定义，只要从头到尾没人调用它 → 链接器不会报任何错。**
链接器只解析**被引用到的**符号，未被引用的声明它根本不看。

✅ 实测验证：

```console
$ cat l_unused.c
int add(int a, int b);
int main(void){ return 0; }        # 声明了，但没人调用

$ clang -c l_unused.c -o l_unused.o && clang l_unused.o -o app2
（无任何输出，链接成功）

$ cat l_undef.c
int add(int a, int b);
int main(void){ return add(3,4); } # 这次真的调了

$ clang -c l_undef.c -o l_undef.o && clang l_undef.o -o app
Undefined symbols for architecture arm64:
  "_add", referenced from: _main in l_undef.o
```

一句话：**LNK2019 的触发条件是"被引用且找不到定义"，不是"声明了没定义"。**

## 另一个高频坑：C++ 的 LNK2019 符号名是一串乱码

MSVC 的 LNK2019 在 C++ 下报的是**修饰后（mangled）**的符号名，例如
`?compute@@YAHNHPEBD@Z`。这不是乱码，是编码了参数类型的函数名。

- MSVC 侧：`undname ?compute@@YAHNHPEBD@Z` 解调（⚠️ 未实测）
- LLVM 侧：`c++filt`（✅ 实测）

```console
$ clang++ m_a.o -o appcpp     # C++：compute(int, double, const char*)
Undefined symbols: "compute(int, double, char const*)", referenced from: _main in m_a.o

$ clang   m_c.o  -o appc      # 同一份代码按 C 编
Undefined symbols: "_compute", referenced from: _main in m_c.o
```

**同一个函数，C++ 报带参数列表、C 报只加下划线。** 这条差异直接解释了一类经典事故：
C 写的库被 C++ 代码包含时，头文件没加 `extern "C" { }` → 满屏 LNK2019，
符号名前面带一串 `?...@@YA`。

## ⚠️ 坑点（你怎么说 / 实际是什么）

| 常见说法 | 实际情况 |
|----------|----------|
| "C4013 是编译错误" | **是警告**（level 3），默认不终止编译；`/we4013` 才变错误 |
| "C 报错就连 obj 都出不来" | 是**该 TU** 不出；工程里其他文件照出。VS 会继续编译别的 |
| "LNK 是链接器 link.exe 报的" | `lib.exe`/`dumpbin.exe`/`editbin.exe` 共用同一个 exe，也报 LNK |
| "声明了没实现 → LNK2019" | **必须被引用**。没人调用的纯声明不会触发 |
| "LNK2019 = 链接期所有符号问题" | 重复定义是 LNK2005，缺 main 是 LNK1561，缺库文件是 LNK1104 |
| "LNK1120 是另一种错误" | 它是**计数行**，告诉你一共几个未解析符号，紧跟 2019 出现 |
| "整个构建失败统称编译失败" | 广义口头说法没错，但编号严格区分，排障时必须分清楚 |
| "C4xxx 都是警告" | 大方向对；`/WX` 后它们仍以 C 编号出现，但升级为 error |
