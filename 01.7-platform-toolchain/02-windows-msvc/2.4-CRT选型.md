# 2.4 CRT 选型：`/MD` 还是 `/MT`

[← 2.3 版本号迷宫](./2.3-版本号迷宫.md) · 下一节：[2.5 调试信息三种容器 →](./2.5-调试信息三种容器.md)

## 本节讲什么

Linux/macOS 上你从没为"C 运行时怎么链接"纠结过，因为答案默认就一个。
Windows 上这是个**必选项**，而且选错会引发极难查的崩溃。

## 要点

### 四个开关

| 开关 | 含义 | 产物依赖 |
|------|------|----------|
| `/MD` | 动态链接多线程 Release CRT | 运行时需要 `vcruntime140.dll` + Universal CRT |
| `/MDd` | 动态链接多线程 **Debug** CRT | 同上，调试版，带额外断言检查 |
| `/MT` | **静态**链接多线程 Release CRT | 可执行文件自带 CRT 代码，不依赖 dll |
| `/MTd` | 静态链接多线程 Debug CRT | 同上，调试版 |

还有一个 `/LD` / `/LDd`：不是 CRT 开关，是"本项目产出 DLL"。

### 现代 CRT 的构成（VS 2015 之后）

微软在 VS 2015 把 CRT 拆成了两块，这解释了为什么 DLL 名字里有 "140"：

| 组件 | 内容 | 文件 |
|------|------|------|
| **vcruntime** | `printf`、`malloc`、启动代码等编译器相关部分 | `vcruntime140.dll`（lib 侧 `msvcrt.lib` 是导入库） |
| **UCRT**（Universal CRT） | 标准要求的 C 库功能，随 Windows 10 SDK 提供 | `ucrtbase.dll` / Windows 10+ 系统自带 |

"140" 就是 [2.3](./2.3-版本号迷宫.md) 里那个 MSVC `14.0` 的回响 —— 从 VS 2015 开始，
即使后面出到 14.4x，为了保持二进制兼容，**DLL 名字里的 140 一直没变**。

### 核心坑：每个 CRT 副本都有自己的堆

这是 Windows C/C++ 开发的经典必踩项：

```text
模块 A（/MT）        模块 B（/MT）
   └─ 私有堆 #1        └─ 私有堆 #2
        │                    │
        └── A 里 malloc 的指针传给 B → B 里 free  ← 崩溃
```

**规则：**

| 场景 | 结果 |
|------|------|
| 同一模块内 malloc / free | ✅ 正常 |
| 跨 DLL 边界传递内存所有权（双方都是 `/MT`） | ❌ 崩溃或堆损坏 |
| 跨 DLL 边界（双方都是 `/MD`，共享同一个 CRT DLL） | ✅ 正常，共用同一个堆 |

对应到 POSIX 世界的直觉：Linux 上一个进程里通常**只有一份 glibc**，
所以 `malloc`/`free` 天然跨 `.so` 边界安全。Windows 的 `/MT` 破坏了这个默认假设。

> **工程实践：多 DLL 的项目一律用 `/MD`。** 除非你要做"单个 exe 无依赖分发"，
> 才考虑 `/MT`，并且要严守"谁分配谁释放"、绝不跨模块传递所有权。

### 与 macOS / Linux 的对照

| 概念 | MSVC | macOS | Linux (glibc) |
|------|------|-------|---------------|
| CRT 本体 | UCRT + vcruntime | `libSystem`（含 libc） | `libc.so.6` |
| 静态链接 CRT | `/MT` | `-static`（链接 `libSystem` 不推荐） | `-static` / `-static-libgcc -static-libstdc++` |
| 这份命令你怎么记 | 编译期必须选 | 默认动态，几乎不用管 | 默认动态 |
| 跨模块堆共用 | 取决于 `/MD` vs `/MT` | 同一进程共用 | 同一进程共用 |

> macOS 上 Apple 明确**不推荐静态链接 libSystem**（系统库 ABI 的稳定性由 dyld 共享缓存保证），
> 所以你从没见过 mac 上的 "/MT 问题"。Windows 的选择面更宽，代价是多了一种崩法。
