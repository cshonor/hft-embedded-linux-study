Smart Pointers — Items 18–22

本章讲什么

裸 new/delete 是 C++ 资源泄漏与悬垂指针的头号来源。智能指针用 RAII 把"所有权"编码进类型系统：unique_ptr 表达独占、shared_ptr 表达共享、weak_ptr 打破环引用。本章讲清三者的所有权语义、性能代价与正确用法——这是 Modern C++ 区别于 C 的核心能力，也是 muduo / HFT 引擎回调与对象生命周期管理的基石。

各 Item 要点

Item 18：用 std::unique_ptr 管理独占资源

unique_ptr 是零开销抽象——大小 = 裸指针（默认），开销 = 裸指针（移动是几条指令，析构内联调用 delete）。它表达"唯一所有权"，不可拷贝、只能移动。

std::unique_ptr<Widget> make() { return std::make_unique<Widget>(); }

自定义删除器：unique_ptr<Widget, void(*)(Widget*)> 可挂自定义删除器。但删除器类型是 unique_ptr 类型的一部分——不同删除器 = 不同类型。这对接口设计有影响（函数参数要明确删除器类型）。HFT 里用它管理 FILE*、fd、DPDK rte_mbuf*（自定义删除器调 rte_pktmbuf_free）。

与 C API 互操作：unique_ptr 的 .get() 取裸指针传给 C 接口；.release() 放弃所有权交还给 C。

Item 19：用 std::shared_ptr 管理共享所有权

shared_ptr 用引用计数实现共享。控制块（control block）含强引用计数 + 弱引用计数 + 删除器 + 分配器。拷贝 shared_ptr 原子地递增计数（++ 是原子操作），析构递减，归零调用删除器。

代价： - 大小 = 2 个指针（对象指针 + 控制块指针），是裸指针的 2 倍。 - 拷贝/析构有原子操作开销——比非原子 ++ 慢一个数量级，且在多核间引发 cache 行同步。HFT 热路径绝不在每 tick 路径上拷贝 shared_ptr。

控制块创建时机（一次性，只创建一次）： 1. make_shared（推荐） 2. 从 unique_ptr 构造 3. 用裸指针 new 构造 shared_ptr——两次 new 同一裸指针会创建两个控制块，double free

enable_shared_from_this：对象需要在成员函数里返回自身的 shared_ptr 时，继承 enable_shared_from_this<T> 并调 shared_from_this()——直接 shared_ptr<T>(this) 会创建新控制块导致 double free。

Item 20：用 std::weak_ptr 指向可能悬垂的 shared_ptr

weak_ptr 不增加强引用计数，观察 shared_ptr 但不延长对象生命。要访问对象须 lock() 提升为 shared_ptr（原子地检查并获取）：

std::weak_ptr<Widget> wp = sp;
if (auto p = wp.lock()) { /* p 有效，安全使用 */ }

三大用途：缓存（对象可被回收）、观察者模式（观察者不持有被观察对象）、打破 shared_ptr 环引用（A↔B 互引导致计数永不归零、内存泄漏）。

Item 21：优先 make_unique / make_shared 而非 new

make_shared 一次分配同时建对象 + 控制块（单次堆分配），比 shared_ptr<T>(new T) 的两次分配更省且 cache 友好。

例外（不能 make 的场景）： - 需要自定义删除器 → 只能 new - 自定义分配器 - make_shared 把对象内存与控制块绑在一起——若有 weak_ptr 长期存活，对象的内存（已析构但未释放）会延迟到所有 weak_ptr 都销毁才回收。大对象 + 长期 weak_ptr 场景要用 new。

Item 22：用 Pimpl 惯用法降低编译依赖

Pimpl（Pointer to Implementation）把实现细节藏到 .cpp，头文件只留一个 unique_ptr<Impl>：

// widget.h
class Widget {
    struct Impl;
    std::unique_ptr<Impl> pImpl;   // 不需要 Impl 的完整定义
public:
    Widget();
    ~Widget();   // 必须在 .cpp 定义（unique_ptr 析构需要完整类型）
};

头文件改动减少 → 编译依赖降低 → 增量编译加速。这和《C 和指针》ch07 的 opaque pointer / PIMPL 是同一思想，C++ 版用 unique_ptr 自动管理。

HFT 关联

  • unique_ptr 管 mbuf / fd：自定义删除器让 unique_ptr 管 DPDK rte_mbuf*（删除器调 rte_pktmbuf_free）或 POSIX fd（删除器调 close）。RAII 保证异常路径也不泄漏资源——比 C 的 goto cleanup 更安全且零运行开销。
  • shared_ptr 只在对象池/策略共享：HFT 热路径不用 shared_ptr（原子计数代价），但对象池、策略对象（多线程共享、需要延迟销毁）用它管理生命周期。务必在线程入口一次性拷贝 shared_ptr，热循环内用裸引用，避免每帧原子操作。
  • weak_ptr 观察者模式：行情分发器持有策略的 weak_ptr，策略销毁后分发器 lock() 返回空自动跳过——避免策略热卸载时的悬垂回调。
  • Pimpl 降编译依赖：大型交易引擎头文件改动会触发全量重编译，Pimpl 把核心结构藏到 .cpp，增量编译从分钟级降到秒级——开发效率的直接提升。

Item 18：用 std::unique_ptr 管理独占资源

第 4 章 智能指针 · Item 18 · 下一节：Item 19 shared_ptr

为什么要学这个（先建立直觉）

C 里管理堆资源靠纪律：malloc 之后配对 free，中间有 goto cleanup、有异常路径、有早退 return——每一条路都得记得释放，漏一条就是泄漏。unique_ptr 把这条纪律变成了类型系统强制的规则：资源包进对象，对象出作用域自动释放，所有权唯一、拷贝直接被编译器拒绝。

更关键的是 Meyers 强调的卖点：零开销。unique_ptr 不是"方便但慢一点"的妥协——默认配置下它和裸指针一样大、一样快，是"不用白不用"的纯收益抽象。这一节用实测把这个"零开销"拆开看清楚，包括它在什么情况下不再零开销（有状态删除器）。

这节讲什么

  1. 零开销的实测证据：sizeof 对比、移动语义、拷贝被删的报错原文；
  2. 自定义删除器：类型成为 unique_ptr 一部分的含义，以及删除器对体积的影响（EBO）；
  3. 与 C API 互操作：.get() / .release() / .reset() 的所有权语义；
  4. 数组特化 unique_ptr<T[]> 与 make_unique。

核心用法与零开销实测

#include <memory>

std::unique_ptr<Widget> make() {
    return std::make_unique<Widget>();   // 工厂返回 unique_ptr：所有权随返回值移交
}
// 离开作用域自动 delete，异常路径也释放——RAII

clang 23.1.0（arm64）实测尺寸：

sizeof(unique_ptr<int>)                    = 8     ← 和裸指针完全一样
sizeof(unique_ptr<FILE, decltype(&fclose)>)= 16    ← 函数指针删除器：+8
sizeof(unique_ptr<int, 无捕获lambda>)       = 8     ← 无状态删除器：EBO 压掉了
sizeof(unique_ptr<int, 有捕获lambda>)       = 16    ← 有状态删除器：要存状态

两个要点直接写在数字里：

  • 默认删除器（delete）零成本：8 字节 = 一个裸指针。解引用就是指针解引用，析构就是内联 delete，无任何计数、无任何间接层。
  • 删除器占不占空间取决于它有没有状态：无捕获 lambda / 空函数对象是"无状态删除器"，靠空基类优化（EBO）压成 0 字节；函数指针（&fclose）和有捕获 lambda 要把删除器存进对象，所以 +8 字节。

移动可以，拷贝不行

auto p1 = std::make_unique<int>(42);
auto p2 = std::move(p1);
// 实测：p1 == nullptr 为 true，*p2 == 42 —— 所有权是"移交"不是"共享"

auto p3 = p1;   // 编译失败

clang 报错原文：

error: call to implicitly-deleted copy constructor of 'unique_ptr<int>'

拷贝构造被显式 = delete——"唯一所有权"不是约定，是编译期强制。想转移就 std::move，意图明明白白写在代码里。

自定义删除器：类型的一部分

std::unique_ptr<FILE, decltype(&fclose)> fp(fopen("f.txt", "r"), &fclose);
// 离开作用域自动 fclose

删除器类型是 unique_ptr 类型的第二个模板参数——unique_ptr<T, D1> 和 unique_ptr<T, D2> 是不同类型，不能互相赋值、不能放进同一个容器。推论：

  • 函数指针删除器：unique_ptr<T, void(*)(T*)>，16 字节；
  • lambda 删除器：每个 lambda 都是独一无二的匿名类型，写进函数签名要靠 auto/模板/decltype；
  • 管 C 资源的标准手法：fclose 管 FILE*、close 管 fd、库自带的 xxx_free 管库句柄。

与 C API 互操作的所有权三件套

std::unique_ptr<Widget> up = std::make_unique<Widget>();

raw_observe(up.get());        // 借出裸指针：所有权不动，up 还负责释放
Widget* p = up.release();     // 交出所有权：up 置空，p 归你管（忘了 delete 就泄漏）
up.reset(new Widget);         // 先释放当前对象，再接管新对象

一句话：.get() 是借，.release() 是给，.reset() 是换。传给只读接口用 .get()；传给"之后归 C 库管"的接口用 .release()。

数组特化

auto arr = std::make_unique<int[]>(1024);   // unique_ptr<int[]>，析构调 delete[]
arr[0] = 1;                                 // 有 operator[]，无 operator*/->

unique_ptr<T[]> 自动配对 delete[]，避免 new[]/delete 错配。但能用它的地方先想想 std::vector——vector 有尺寸、有迭代器、能进算法，unique_ptr<T[]> 只在"必须对接要裸数组所有权的 C API"时有存在价值。

常见错误（新手踩坑）

  1. 用裸 new 构造而不是 make_unique。unique_ptr<Widget> up(new Widget); 能编过，但 make_unique 更短、且避免"new 表达式求值与 unique_ptr 构造之间抛异常导致泄漏"的经典窗口（C++14 起有 make_unique，没有理由不用）。
  2. 同一裸指针构造两个 unique_ptr：Widget* p = new Widget; unique_ptr<Widget> a(p), b(p); → 双重释放。规则：裸指针交给智能指针后，立刻忘掉这个裸指针。
  3. 移动后还使用源指针。std::move 之后源 unique_ptr 是 nullptr（实测确认），解引用即崩溃。move 过的指针只剩两种合法操作：重新赋值、析构。
  4. 以为函数指针删除器也零开销。实测 16 字节——要省体积，把删除器写成无捕获 lambda 或空函数对象。

新手要点（和 C 的区别）

  • C 用 malloc/free + goto cleanup：释放靠人肉，return 早退、longjmp、错误分支每条都要记得清理。unique_ptr 把释放绑在栈对象生命周期上，任何退出路径都自动执行——这是 RAII，也是 C++ 相对 C 在资源管理上最实质的升级。
  • 零开销不是口号：默认 unique_ptr 与裸指针同大同快（实测 8 字节），优化后汇编通常与手写 new/delete 逐指令一致。"抽象不交税"是它成为默认选择的原因。
  • 不可拷贝是特性不是缺陷：拷贝被 = delete，强制单一所有权；要共享请显式换 shared_ptr 并付引用计数的税（见 Item 19）。

HFT 关联

  • 管 mbuf / fd / 库句柄：自定义删除器让 unique_ptr 管 DPDK rte_mbuf*（删除器调 rte_pktmbuf_free）、POSIX fd（删除器调 close）、库句柄。RAII 保证异常路径、早退路径都不泄漏——比 goto cleanup 干净，还零开销。
  • 热路径资源的安全网：热路径上传递所有权用 unique_ptr + std::move，无引用计数、无原子操作——这点和 shared_ptr 形成决定性对比。
  • 工厂函数返回 unique_ptr：std::unique_ptr<Strategy> make_strategy(Config) 是策略对象创建的标准签名——调用方拿到独占所有权，接口语义自文档化。

自测题

  1. 默认 unique_ptr<int> 多大？凭什么说"零开销"？什么情况下它会变成 16 字节？
  2. unique_ptr<FILE, decltype(&fclose)> 和 unique_ptr<FILE, 某lambda类型> 是同一类型吗？能放进同一个 vector 吗？
  3. .get() / .release() / .reset() 各是什么所有权语义？
  4. 为什么 unique_ptr 不可拷贝但可移动？移动后源对象处于什么状态？
  5. Widget* p = new Widget; unique_ptr<Widget> a(p), b(p); 会发生什么？根因是什么？
  6. unique_ptr<T[]> 和 std::vector<T> 怎么选？
参考答案

  1. 8 字节（64 位，实测）。"零开销"指与手写 new/delete 相比不引入额外内存或时间成本：无引用计数、无控制块、解引用与析构都是内联的指针操作，独占所有权完全靠类型系统（删除拷贝）在编译期表达。变成 16 字节的两种情况：删除器是函数指针（要存指针），或删除器是有捕获 lambda / 有状态函数对象（要存状态）。无捕获 lambda 靠 EBO 仍是 8 字节。

  2. 不是同一类型——删除器类型是第二个模板参数，删除器不同则 unique_ptr 类型不同，不能互相赋值，也不能进同一个 vector<unique_ptr<T, D>>。两个不同的 lambda 类型也互不相同（每个 lambda 都是唯一匿名类型）。

  3. .get() 借出裸指针，所有权不动（智能指针仍负责释放），适合传给只观察的接口；.release() 交出所有权并置空自身，释放责任转给接收方，忘了 delete 就泄漏；.reset(p) 先释放当前持有的对象再接管 p。记忆法：借 / 给 / 换。

  4. 语义是独占所有权：拷贝会产生两个"唯一"拥有者，析构时双重释放，所以拷贝构造/拷贝赋值被 = delete（实测报错 call to implicitly-deleted copy constructor）。移动是所有权转移：源对象把指针交出后置空（实测 p1 == nullptr 为 true），全程只有一个拥有者。移动后的源对象处于"合法但未指定"状态，只剩重新赋值和析构两种安全操作。

  5. 双重释放（UB）。两个 unique_ptr 各自以为独占 p，析构时各 delete 一次。根因是裸指针没有所有权信息，构造 unique_ptr 时编译器无法知道这个裸指针已经被别的智能指针持有。纪律：裸指针一交给智能指针就不再使用；优先 make_unique，让裸指针根本没有具名存在的机会。

  6. 默认 std::vector<T>：有尺寸、有迭代器、能进标准算法、会自己扩容。unique_ptr<T[]> 只在需要"拥有并移交一块裸数组的所有权"时考虑（对接 C API、手写内存池），它无尺寸信息、只能下标访问，是更接近裸 new[] 的薄封装。

Item 19：用 std::shared_ptr 管理共享所有权

第 4 章 智能指针 · Item 19 · 上一节：Item 18 unique_ptr

为什么要学这个（先建立直觉）

unique_ptr 覆盖"一个资源一个主人"的场景，但现实里总有"多个对象都要用、谁也不知道谁最后用完"的时候——共享配置、共享连接、缓存里的条目。手写所有权协议（"最后离开的人关灯"）在多线程下几乎是必错的，shared_ptr 用引用计数把这盏灯自动化了。

但 shared_ptr 不是 unique_ptr 的"升级版"，是另一种价格的工具：体积翻倍、每次拷贝/析构都要原子操作、对象旁边还多一块控制块。这一节的任务就是搞清楚这份价格单的每一项——以及什么时候根本不该付。

这节讲什么

  1. 价格单实测：sizeof、分配次数（make_shared vs new+shared_ptr）、原子计数开销；
  2. 控制块（control block）里有什么、什么时候创建；
  3. 最致命的用法错误：同一裸指针构造两个 shared_ptr（含 ASan 抓包现场）；
  4. enable_shared_from_this 解决什么、为什么 shared_ptr<T>(this) 是灾难。

核心机制：控制块

shared_ptr 的共享靠一块控制块（control block）实现，里面装着：

  • 强引用计数（有几个 shared_ptr 指着对象）
  • 弱引用计数（weak_ptr 数量，见 Item 20）
  • 删除器与分配器（类型擦除存放——这是 shared_ptr 删除器不进类型的原因，与 unique_ptr 相反）
  • 对象指针（或对象本身，make_shared 时）
auto sp = std::make_shared<Widget>();  // 强计数 = 1
auto sp2 = sp;                          // 拷贝 → 强计数 = 2（原子 ++）
// sp2 析构 → 强计数 = 1（原子 --）
// sp 析构  → 强计数 = 0 → 销毁 Widget → 弱计数归零后释放控制块

最后一个 shared_ptr 析构时对象被销毁——"最后离开的人关灯"，自动且线程安全（计数本身线程安全；指向的对象不自动线程安全，别混淆）。

价格单实测（clang 23.1.0，arm64）

sizeof(shared_ptr<Widget>) = 16    ← 两个指针：对象 + 控制块
sizeof(unique_ptr<Widget>) = 8     ← 对照：裸指针尺寸

分配次数（重载全局 operator new 计数实测）：

make_shared 分配次数: 1        ← 对象 + 控制块一次分配
new + shared_ptr 分配次数: 2   ← 对象一次、控制块一次

make_shared 把对象和控制块放进同一块内存：少一次堆分配、对象与控制块同 cache 行附近、少一次指针跳转。这是"优先 make_shared"的实质理由，不只是风格建议。

shared_ptr 三份成本，按频率排序：

  1. 每次拷贝/析构的原子 RMW：引用计数必须原子增减（多线程共享），一次原子加在竞争下比一个普通 store 慢一个数量级；
  2. cache 行乒乓：多个核上的 shared_ptr 副本共享同一控制块，计数所在的 cache 行在核间来回失效（false sharing 的教科书案例）；
  3. 体积与间接：16 字节/指针 + 控制块另算 + 访问对象要两次解引用。

致命错误：一个裸指针，两个控制块

Widget* p = new Widget;
auto sp1 = std::shared_ptr<Widget>(p);
auto sp2 = std::shared_ptr<Widget>(p);   // 第二个控制块！

sp1 和 sp2 各自创建控制块、各自计数为 1、互不知情。任一归零就 delete p，另一个变悬垂，随后 double free。ASan 抓包现场（clang 23.1.0 + -fsanitize=address）：

==82166==ERROR: AddressSanitizer: attempting double-free
on 0x614000000040 in thread T0:

规则：裸指针一旦交给 shared_ptr，立刻忘掉它；其余副本永远从已有 shared_ptr 拷贝（共享同一控制块）。用 make_shared 让裸指针根本没机会具名存在。

enable_shared_from_this：从对象内部交出自己

场景：对象的成员函数需要返回"指向自己的 shared_ptr"（注册回调、投递异步任务）。直接写 shared_ptr<Widget>(this) 会新建控制块——和外面已有的 shared_ptr 互不知情，又是 double free；对象若在栈上则更糟（delete 非堆对象）。

正解是继承 enable_shared_from_this：

class Widget : public std::enable_shared_from_this<Widget> {
public:
    std::shared_ptr<Widget> getPtr() { return shared_from_this(); }
    // 内部存了一个 weak_ptr，shared_from_this() 从已有控制块复制
};

// 前提：对象必须已经由 shared_ptr 管理
auto sp = std::make_shared<Widget>();
auto sp2 = sp->getPtr();   // OK：与 sp 共享控制块

Widget w;
// w.getPtr();            // 抛 std::bad_weak_ptr：没有控制块可共享

机制：enable_shared_from_this 在对象里埋一个 weak_ptr，第一个 shared_ptr 接管对象时初始化它；shared_from_this() 从这个 weak_ptr lock() 出共享同一控制块的 shared_ptr。所以它不是凭空造计数，而是找到已有的计数——前提是已经有一个。

常见错误（新手踩坑）

  1. 同一裸指针构造两个 shared_ptr。如上，ASan 实锤 double-free。最常见的变体：shared_ptr<T>(this) 和从 get() 拿回来的裸指针再包一层——shared_ptr<T>(sp.get()) 同样造第二个控制块。
  2. 在热路径拷贝 shared_ptr。每次拷贝都是原子 RMW + 潜在 cache 乒乓。热路径传引用或裸指针，只在生命周期边界拷贝。
  3. 以为 shared_ptr 让对象线程安全。线程安全的只是引用计数本身；两个线程同时写 *sp 指向的对象照样数据竞争。
  4. 循环引用泄漏。A 持 B、B 持 A，计数永远到不了 0，双方都不释放——打破循环用 weak_ptr（Item 20）。

新手要点（和 C 的区别)

  • C 没有引用计数智能指针。C 里要共享就手写计数协议（Linux 内核的 kref、refcount_t 就是这套的手写版——shared_ptr 本质是把 kref 包进了类型系统）。
  • make_shared 优先：一次分配（实测 1 vs 2）、cache 友好、还顺带消灭"裸指针对外交"的窗口。
  • 代价意识：shared_ptr 拷贝/析构带原子操作，比裸指针慢一个数量级。"能用 unique_ptr 就不用 shared_ptr"是 Meyers 的原话立场。

HFT 关联

  • 热路径绝不用 shared_ptr：原子计数 + 控制块 cache 行在多核间乒乓，是每 tick 路径上的延迟尖峰发生器。模式：线程入口拷贝一次拿到对象（或干脆裸指针/引用），热循环内零计数操作，生命周期由外层 scope 保证。
  • 非热路径的合理用途：对象池条目、策略配置快照、跨线程异步任务句柄——低频路径上 shared_ptr 换来的安全收益远大于微秒级成本。
  • make_shared 的副作用要知情：对象和控制块同块内存，意味着只要还有 weak_ptr 活着，对象占的内存也不能释放（控制块要等弱计数归零）。大对象 + 长命 weak_ptr = 内存滞留，容量敏感场景要评估。

参考答案

  1. 16 字节（64 位实测）：一个指针指向对象，一个指向控制块。控制块含强引用计数、弱引用计数、类型擦除的删除器与分配器，以及对象指针（或内嵌对象）。这些元信息必须被所有副本共享，所以每个 shared_ptr 都要多背一个控制块指针。

  2. make_shared 1 次，new+shared_ptr 2 次（重载全局 operator new 计数实测）。好处：少一次堆分配的系统调用/锁竞争；对象与控制块同块内存、局部性好，访问计数和访问对象大概率同 cache 行；还消灭了裸指针外泄的窗口。

  3. 形成两个互不知情的控制块，各自计数为 1；任一归零就 delete 对象，另一个悬垂，随后双重释放。ASan 实测报 attempting double-free。对策：副本永远从已有 shared_ptr 拷贝；优先 make_shared 让裸指针不具名。

  4. 解决"对象成员函数里要交出指向自身的 shared_ptr"的问题（注册回调、异步任务）。shared_ptr<T>(this) 会为同一对象新建控制块，与外部已有的 shared_ptr 计数互相不知道，双重释放；对象在栈上时还会 delete 非堆内存。enable_shared_from_this 在对象内埋一个 weak_ptr，shared_from_this() 从它 lock 出共享已有控制块的 shared_ptr。前提：对象已被 shared_ptr 管理，否则抛 std::bad_weak_ptr。

  5. 三部分：①拷贝/析构时对计数的原子 RMW（原子加在竞争下比普通 store 慢一个数量级）；②多核下计数所在 cache 行在核间来回失效（控制块被所有副本共享，典型 false sharing）；③16 字节体积 + 访问对象需两次解引用。核越多、拷贝越频繁，cache 乒乓越严重——开销随核数和拷贝频率放大，不是固定成本。

  6. 不准确。线程安全的只有引用计数的增减：多个线程同时拷贝/析构各自持有的 shared_ptr 副本是安全的。但指向的对象没有任何保护——两线程同时写 *sp 照样数据竞争；同一个 shared_ptr 实例本身被两线程一读一写（如一个 reset 一个拷贝）也是竞争。准确说法：控制块线程安全，对象和指针实例不线程安全。

Item 20：用 std::weak_ptr 指向可能悬垂的 shared_ptr

第 4 章 智能指针 · Item 20 · 上一节：Item 19 shared_ptr

为什么要学这个（先建立直觉）

C 程序员用裸指针"观察但不拥有"：

struct Widget* cached = NULL;
void use_cache() {
    if (cached) cached->do_work();  // 若 cached 已被 free → 悬垂指针 → UB
}

问题：C 的裸指针不知道目标是否还活着。cached 非空不代表指向的内存有效——用就是 UB，不用又没法检测。这类 bug 在长时运行系统里最致命：指针 99% 的时间指向有效内存，只有对象被释放后的那一下访问才崩。

C++ 的 weak_ptr 把"观察但不拥有"做成了可检测的语言设施：不增加强引用计数（不延长对象生命），但能通过 lock() 原子地回答"对象还活着吗"——活着就给你一个 shared_ptr 保证使用期间不死，死了就给你空指针，走降级路径而不是 UB。

另一个容易忽视的问题：shared_ptr 的引用计数解决不了环——两个对象互相持有对方的 shared_ptr，谁也放不掉谁，内存永久泄漏。weak_ptr 是标准的破环工具。

这节讲什么

weak_ptr 观察 shared_ptr 但不拥有：不增强引用计数、不能直接解引用，访问前必须 lock() 提升为 shared_ptr（原子地检查+获取）。三大用途：打破环引用、观察者模式、缓存。

循环引用：shared_ptr 的死穴

两个结构体互相持有对方的 shared_ptr，本机实测（clang 23.1.0, -std=c++17 -Wall）：

#include <memory>
#include <iostream>
struct B;
struct A {
    std::shared_ptr<B> b;
    ~A() { std::cout << "~A()\n"; }
};
struct B {
    std::shared_ptr<A> a;
    ~B() { std::cout << "~B()\n"; }
};

int main() {
    std::cout << "--- 进入作用域 ---\n";
    {
        auto pa = std::make_shared<A>();
        auto pb = std::make_shared<B>();
        pa->b = pb;
        pb->a = pa;
        std::cout << "pa.use_count() = " << pa.use_count() << "\n"
                  << "pb.use_count() = " << pb.use_count() << "\n";
    }
    std::cout << "--- 离开作用域（注意：没有任何析构打印）---\n";
}

实测输出（两个 ~ 析构打印都没出现）：

--- 进入作用域 ---
pa.use_count() = 2
pb.use_count() = 2
--- 离开作用域（注意：没有任何析构打印）---

计数推演：pa 销毁，A 的计数 2→1（还剩 pb->a）；pb 销毁，B 的计数 2→1（还剩 pa 尸体里的 b）。A 的释放依赖 B 先析构，B 的释放依赖 A 先析构——死锁式的计数环。

40 字节一块、共两块——正是 A、B 各自"对象+控制块"的合并分配（make_shared 的缘故，见 Item 21）。macOS 上 ASan 默认不开泄漏检测，要加 ASAN_OPTIONS=detect_leaks=1。

weak_ptr 破环

把环上的一条边改成 weak_ptr（通常选"子指父"或"回指"的那条边）：struct B { std::weak_ptr<A> a; ... };，本机实测输出：

--- 进入作用域 ---
pa.use_count() = 1        ← weak_ptr 不增强引用计数
pb.use_count() = 2
observer.expired() = 0
~A()                      ← pa 销毁时 A 立即析构
~B()                      ← A 析构 → b 成员销毁 → B 计数归零 → B 析构
--- 离开作用域 ---
observer.expired() = 1    ← 外部观察者正确看到"已失效"
lock() 返回空? 1

关键事实：weak_ptr 不增加强引用计数（pa.use_count() 保持 1），析构链因此能正常走完：pa 销毁 → A 计数归零 → A 析构 → 成员 b 销毁 → B 计数归零 → B 析构。

lock() 的原子性与 expired() 的局限

lock() 在一次原子操作里完成：检查强引用计数 > 0 → 递增 → 返回有效 shared_ptr；否则返回空。为什么必须原子？看反面教材：

if (!wp.expired()) {   // 检查
    // ← 另一线程在此刻 reset 了最后一个 shared_ptr，对象销毁
    auto p = wp.lock();  // 再获取——可能返回空！
    p->do_work();        // 空指针解引用
}

expired() 的返回值只能用于日志和统计——它回答的是"刚才那一刻死没死"，不是"下一秒还活着吗"。正确姿势永远是用 lock() 的返回值判断：if (auto p = wp.lock()) { p->do_work(); }——要么拿到活的，要么拿到空，没有中间态；且 p 持有强引用，使用期间对象保证不死。

三大经典场景

场景 谁持有 weak_ptr lock() 失败时怎么办
打破环引用 环上的"反向"边（子→父、prev） 不会出现（环内保证存活）
观察者模式 分发器持有观察者的 weak 跳过并顺手清理
缓存 缓存表持有值的 weak 重新加载，写回缓存

缓存场景的精妙之处：缓存不阻止对象被回收——没人用的数据自然释放，内存压力下缓存自动收缩；lock() 失败了再加载一次即可。这是裸指针缓存做不到的行为。

完整可运行例子

观察者 + 缓存 + expired 检测三合一，本机实测（clang 23.1.0, -std=c++17 -Wall）：

#include <memory>
#include <iostream>
#include <map>
#include <string>
#include <vector>

struct Observer {
    std::string name;
    explicit Observer(std::string n) : name(std::move(n)) {}
    void update(const std::string& m) { std::cout << "  [" << name << "] 收到: " << m << "\n"; }
    ~Observer() { std::cout << "  ~Observer(" << name << ")\n"; }
};

struct Subject {
    std::vector<std::weak_ptr<Observer>> observers;
    void subscribe(const std::shared_ptr<Observer>& o) { observers.push_back(o); }
    void notify(const std::string& msg) {
        for (auto it = observers.begin(); it != observers.end();) {
            if (auto sp = it->lock()) { sp->update(msg); ++it; }
            else { std::cout << "  (跳过已销毁的观察者)\n";
                   it = observers.erase(it); }       // 顺手清理
        }
    }
};

struct Quote { double bid, ask; };
std::map<std::string, std::weak_ptr<Quote>> cache;

std::shared_ptr<Quote> getQuote(const std::string& sym) {
    if (auto sp = cache[sym].lock()) { std::cout << "  缓存命中: " << sym << "\n"; return sp; }
    std::cout << "  缓存未命中，重新加载: " << sym << "\n";
    auto sp = std::make_shared<Quote>(Quote{100.25, 100.30});
    cache[sym] = sp;
    return sp;
}

int main() {
    std::cout << "== 观察者 ==\n";
    Subject subj;
    {
        auto o1 = std::make_shared<Observer>("策略A");
        auto o2 = std::make_shared<Observer>("策略B");
        subj.subscribe(o1);
        subj.subscribe(o2);
        subj.notify("行情快照#1");
    }   // o1、o2 在此销毁
    subj.notify("行情快照#2");

    std::cout << "== 缓存 ==\n";
    {
        auto q1 = getQuote("AAPL");
        auto q2 = getQuote("AAPL");
        std::cout << "  q1.use_count() = " << q1.use_count() << " (weak_ptr 不计入)\n";
    }
    auto q3 = getQuote("AAPL");   // 缓存里只剩悬垂 weak → 重新加载

    std::cout << "== expired 检测 ==\n";
    std::weak_ptr<Quote> wq = q3;
    std::cout << "  存活时 expired = " << wq.expired() << "\n";
    q3.reset();
    std::cout << "  释放后 expired = " << wq.expired() << "\n";
}

常见错误（新手踩坑）

  1. 环引用导致内存泄漏。A↔B 互相 shared_ptr，计数永不归零（本节开头实测）。修正：环上"回指"的边改 weak_ptr。工程惯例：所有权方向（父→子、next）用 shared_ptr，观察方向（子→父、prev）用 weak_ptr。
  2. 直接用 weak_ptr 访问对象。wp->doSomething(); 编译失败——weak_ptr 故意不提供 */->，逼你先 lock()。这个"不便"是设计，不是缺陷。
  3. lock() 后不检查返回值。auto p = wp.lock(); p->doSomething(); 当 wp 已悬垂时是空指针解引用。修正：if (auto p = wp.lock()) { ... }。
  4. 用 expired() 做"检查后使用"。多线程下检查和使用之间有窗口期（TOCTOU）。永远用 lock() 的原子语义。

HFT 关联

  • 策略热卸载：行情分发器持有策略回调的 weak_ptr。策略模块热更新/卸载后，分发器 lock() 返回空自动跳过——避免向已 dlclose 掉的代码段回调，这是裸指针回调表最难处理的场景。
  • 行情快照缓存：map<string, weak_ptr<Quote>> 做快照缓存，不活跃合约的快照自动回收，命中时零拷贝共享。
  • 控制块开销：每个 weak_ptr 会延长控制块寿命（对象死后控制块存活到最后一个 weak 销毁）。大对象 + 长期 weak 的内存滞留问题见 Item 21。
  • 热路径别滥用：shared_ptr/weak_ptr 的计数是原子操作，每次拷贝都是一次 atomic increment。能用 unique_ptr 就别上 shared_ptr，能保证存活期的观察就用裸指针/引用——weak_ptr 的价值恰恰是"无法保证存活期"的场景。

自测题

1. weak_ptr 为什么不能直接解引用？lock() 的原子性解决了什么问题？

答案

weak_ptr 不拥有对象，故意不提供 */->，逼你显式处理"对象可能已死"的分支。lock() 在一次原子操作里完成"检查计数 > 0 → 递增 → 返回 shared_ptr"，消除 TOCTOU 竞争：拆成 expired() 检查 + 获取两步，中间另一线程可能释放对象。返回的 shared_ptr 还保证使用期间对象不死。

2. 循环引用为什么泄漏？一句话说明计数为什么回不到零。

答案

A 的释放依赖 B 先析构（B 持有 shared_ptr<A>），B 的释放依赖 A 先析构（A 持有 shared_ptr<B>）——互相等待，谁也走不到第一步。实测离开作用域后无任何析构打印，LeakSanitizer 报 80 字节泄漏。

3. weak_ptr 会影响 use_count() 吗？破环后析构顺序如何？

答案

不影响——实测 pb->a = pa（weak）后 pa.use_count() 仍为 1。破环后链式析构：pa 销毁 → A 计数归零 → A 析构 → 成员 b 销毁 → B 计数归零 → B 析构。

4. lock() 返回空意味着什么？正确处理方式是什么？

答案

意味着对象已析构（weak_ptr expired）。正确处理是走降级路径：重新加载（缓存）、跳过并清理（观察者）——绝不能解引用返回的空 shared_ptr。

5. 为什么不能用 expired() 做"检查后使用"？

答案

expired() 与随后的访问之间有窗口期：返回 false 只代表"检查那一刻活着"，另一线程下一纳秒可能就释放了最后一个 shared_ptr。典型 TOCTOU 竞争，lock() 的原子语义才安全。

6. 观察者模式里 notify() 时 lock() 失败除了跳过还应做什么？

答案

顺手把悬垂的 weak_ptr 从列表 erase 掉。否则列表随时间积累大量死 weak（每个都还占着控制块），遍历成本越来越高。

7. 下面代码输出什么？为什么？

auto sp = std::make_shared<int>(42);
std::weak_ptr<int> wp = sp;
std::cout << sp.use_count() << "\n";
sp.reset();
std::cout << wp.expired() << "\n";
答案

输出 1 和 1（true）。weak_ptr 不增强引用计数，use_count() 保持 1；sp.reset() 后唯一强引用消失，对象析构，wp 变 expired。

Item 21：优先 make_unique / make_shared 而非 new

第 4 章 智能指针 · Item 21 · 上一节：Item 20 weak_ptr

为什么要学这个（先建立直觉）

C 程序员分配内存一步到位：

struct Widget* p = malloc(sizeof(struct Widget));
widget_init(p, args);
free(p);

C++ 的 shared_ptr 比 C 多了一样东西：控制块（强/弱引用计数、删除器等元数据）。直接用 new 包装时，对象和控制块是两次堆分配：

std::shared_ptr<Widget> sp(new Widget(args));  // new Widget 一次 + 控制块一次 = 2 次
auto sp2 = std::make_shared<Widget>(args);     // 对象+控制块合并 = 1 次

少一次分配意味着：少一次 malloc 锁竞争、对象和控制块在同一 cache 行、代码还更短。这几乎是白捡的收益——但 make 有三个不适用场景（自定义删除器、大对象+长期 weak_ptr、大括号初始化），不知道边界就会从"白捡"变成"白送bug"。

这节讲什么

优先用 make_unique（C++14）/ make_shared（C++11）而非直接 new：单次分配、异常安全、代码简洁。三个例外：需要自定义删除器、大对象且有长期 weak_ptr、需要大括号初始化。

优势一：单次堆分配（实测）

用全局 operator new/delete 计数器观察分配行为，本机实测（clang 23.1.0, -std=c++17 -Wall）。Big 是 4KB 的大对象：

// make_shared：一次分配，对象+控制块同一块内存
auto sp = std::make_shared<Big>();
// new + shared_ptr：两次分配，对象和控制块分开
std::shared_ptr<Big> sp2(new Big);

本机实测（用全局 operator new/delete 打日志，完整代码与输出见文末）：make_shared 一侧只有一行 new 4120 字节（4096 对象 + 24 控制块合并）；new 一侧是两行 new 4096 字节 + new 32 字节。malloc 次数减半，且对象与控制块相邻，增减引用计数时不会额外 cache miss。

优势二：异常安全（C++17 前的求值顺序坑）

Meyers 书里的经典例子：

void processWidget(std::shared_ptr<Widget> spw, int priority);
int computePriority();   // 可能抛异常

processWidget(std::shared_ptr<Widget>(new Widget), computePriority());

C++17 之前，编译器可以按这个顺序执行：① new Widget（裸指针产生，没人接管）→ ② computePriority()（抛异常）→ ③ shared_ptr 构造（永不执行）——new 出来的 Widget 永久泄漏。模拟这个顺序实测（-fsanitize=address -g，ASAN_OPTIONS=detect_leaks=1）：

__attribute__((noinline)) void dangerousOrder() {
    Widget* raw = new Widget;                  // ①
    int prio = computePriority();              // ② 抛异常
    processWidget(std::shared_ptr<Widget>(raw), prio);  // ③ 永不执行
}

实测输出：

Widget()
computePriority() 抛异常
caught: boom
main 结束（注意没有 ~Widget()）
=================================================================
==86433==ERROR: LeakSanitizer: detected memory leaks
Direct leak of 1 byte(s) in 1 object(s) allocated from:
    #1 in dangerousOrder() emcC_item21_order.cpp:22
SUMMARY: AddressSanitizer: 1 byte(s) leaked in 1 allocation(s).

注意 C++17 已修掉这个坑：标准规定函数实参的求值以整个实参为单位、不允许交错——shared_ptr<Widget>(new Widget) 这个实参要么完整构造好，要么还没开始。本机实测（clang 23.1.0, -std=c++17）原始写法也不泄漏：

Widget()
computePriority()
~Widget()          ← shared_ptr 实参已完整构造，栈展开时正常析构
caught: boom

但 Meyers 的建议依然成立：用 make_shared 就根本不用关心求值顺序规则，而且在 C++11/14 模式下编译老代码时这个坑仍然活着。这是"不要依赖你知道编译器怎么做"的典型案例。

局限一：不能指定自定义删除器

make_* 系列没有把删除器传进去的入口：

// 自定义删除器必须用 new + 构造函数
std::shared_ptr<FILE> fp(fopen("data.bin", "rb"), &fclose);
// make_shared 做不到这件事——没有接受删除器的重载

需要自定义分配器时同理，用 std::allocate_shared。

局限二：大对象 + 长期 weak_ptr → 内存滞留

这是单次分配的反面：make_shared 把对象和控制块放进同一块内存，而 weak_ptr 依赖控制块存活——只要还有一个 weak_ptr 活着，整块内存（包括早已析构的大对象占的部分）都不能归还。本机实测：

struct Big { char data[4096]; };
std::weak_ptr<Big> wp;
{
    auto sp = std::make_shared<Big>();   // vs shared_ptr<Big>(new Big)
    wp = sp;
}   // sp 死：Big 析构了，但内存归还了吗？
// wp 还活着 → 观察 live bytes

实测（完整输出见文末"完整可运行例子"）：make_shared 版本 sp 死后 live = 4120——对象已析构，4120 字节整块滞留，直到 wp 也析构才 delete 4120；new 版本 sp 一死立即 delete 4096 字节，只剩 32 字节控制块陪 wp 到最后。

对象 4KB、滞留时间 = 最后一个 weak_ptr 的寿命。换成 40MB 的帧缓冲 + 一个长期存活的监控 weak_ptr，滞留的就是 40MB。这种场景用 shared_ptr<Big>(new Big)。

局限三：完美转发传不了大括号

make_* 的实参是函数参数包，大括号初始化列表不是有类型的表达式，推不了导（和 Item 2 的模板推导失败同源）。本机实测报错原文：

auto bad = std::make_unique<std::vector<int>>({1, 2, 3});

error: no matching function for call to 'make_unique'
    auto bad = std::make_unique<std::vector<int>>({1, 2, 3});
               ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
note: candidate template ignored: substitution failure [with _Tp = std::vector<int>]:
      deduced incomplete pack <(no value)> for template parameter '_Args'

圆括号则一切正常（实测输出 10）：

auto v = std::make_unique<std::vector<int>>(10, 0);  // 10 个 0
// 想要大括号语义，绕道：
auto il = {1, 2, 3};
auto v2 = std::make_unique<std::vector<int>>(il);    // OK：il 有类型
// 或直接 new
std::shared_ptr<std::vector<int>> v3(new std::vector<int>{1, 2, 3});

另外注意版本差异：make_unique 是 C++14 才有的（C++11 只有 make_shared），本机实测 -std=c++11 下报 error: no member named 'make_unique' in namespace 'std'。

内存滞留对比的完整实测代码（clang 23.1.0, -std=c++17 -Wall）：

常见错误（新手踩坑）

  1. make_shared 里再套 new。make_shared<Widget>(new Widget) 把 Widget* 当构造实参转发——要么编译失败，要么 new 出来的对象没人接管直接泄漏。make_* 收的是构造参数，不是指针。
  2. 大对象 + 长期 weak_ptr 还用 make_shared。对象析构后整块内存滞留到最后一个 weak 死亡（本节实测）。修正：shared_ptr<Big>(new Big) 分离分配。
  3. 以为 make 总是异常安全的最优解而忽略版本。make_unique 是 C++14 才有；C++11 工程要么自己写一个简单的（书里有 5 行实现），要么用 unique_ptr<T>(new T) 并接受其异常安全分析。
  4. 想给 make_shared 传大括号。{1,2,3} 推不出类型（实测报错见上）。先把列表绑到 auto il = {...} 再传，或用 new。

HFT 关联

  • malloc 次数减半 + cache 局部性：每次堆分配都可能撞内存池锁；make_shared 少一次分配，且控制块与对象同块——增减 use_count() 后紧接着访问对象数据，大概率同一 cache 行。
  • 内存滞留即容量风险：4KB 实测放大到百万级订单对象，长期 weak 监控会让内存水位居高不下。HFT 里监控/审计引用如果必须长期存在，考虑分离分配或对监控侧改用裸指针+存活期协议。
  • 异常安全不依赖编译器版本：热路径上的 f(shared_ptr<T>(new T), g()) 写法在 C++11/14 编译模式下仍是泄漏隐患，make_shared 一劳永逸。

自测题

1. make_shared 比 shared_ptr<T>(new T) 省在哪？实测分配次数各是多少？

答案

省在一次堆分配：new 版本 2 次（对象 4096B + 控制块 32B），make_shared 1 次（合并 4120B）。附带收益：对象与控制块同 cache 行、代码更短、异常安全。

2. processWidget(shared_ptr<Widget>(new Widget), computePriority()) 在 C++17 前为什么可能泄漏？C++17 改了什么？

答案

C++17 前实参求值可交错：new Widget → computePriority() 抛异常 → shared_ptr 构造未执行，裸指针泄漏（实测 ASan 报 Direct leak）。C++17 规定实参求值不可交错，泄漏路径封死；但 C++11/14 模式下坑仍在，make_shared 与版本无关地安全。

3. 为什么 make_shared 不能用于需要自定义删除器的场景？

答案

make_* 的接口只有"类型 + 构造参数"，没有传入删除器的重载。删除器只能走 shared_ptr<T>(p, deleter) 构造函数，例如 std::shared_ptr<FILE> fp(fopen(...), &fclose);。

4. 大对象 + 长期 weak_ptr 为什么不宜用 make_shared？实测数据是什么？

答案

make_shared 把对象与控制块合并分配，而 weak_ptr 依赖控制块存活——只要还有 weak 活着，整块内存不能归还。实测：4KB 对象，make_shared 版本 sp 死后仍滞留 4120B；new 版本 sp 死后立即归还 4096B，只留 32B 控制块。

5. std::make_unique<std::vector<int>>({1,2,3}) 为什么编译失败？怎么绕？

答案

{1,2,3} 是 braced-init-list，不是有类型的表达式，模板的参数包 _Args 无法从中推导（实测报 deduced incomplete pack <(no value)>）。绕法：auto il = {1,2,3}; make_unique<vector<int>>(il)，或用圆括号 (10, 0)，或直接 new。

6. make_unique 是哪个标准版本引入的？C++11 下怎么办？

答案

C++14。C++11 只有 make_shared（实测 -std=c++11 报 no member named 'make_unique'）。C++11 下可手写 5 行的 make_unique（return std::unique_ptr<T>(new T(std::forward<Args>(args)...));），或直接用 unique_ptr<T>(new T(...))。

7. 下面代码有什么问题？

auto sp = std::make_shared<Widget>(new Widget(42));
答案

make_shared 把实参转发给 Widget 的构造函数，这里传的是 Widget*——若无 Widget(Widget*) 构造则编译失败；若恰有则能编译但 new 出来的对象没人接管，永久泄漏。正确写法：std::make_shared<Widget>(42)，传构造参数而不是指针。

Item 22：用 Pimpl 惯用法降低编译依赖

第 4 章 智能指针 · Item 22 · 上一节：Item 21 make 函数

为什么要学这个（先建立直觉）

C++ 的编译模型有个结构性痛点：头文件里类的私有成员也是类定义的一部分——你改一行私有实现（加个 vector 成员、换个第三方库），所有包含这个头文件的翻译单元全部重编译。大项目里改一个核心头文件触发几百个 TU 重编，"喝杯咖啡等编译"就是这么来的。

Pimpl（Pointer to Implementation）的思路釜底抽薪：头文件里只留一个指向实现结构的指针，实现整体挪进 .cpp。私有成员随便改，只有那一个 .cpp 重编译。代价是多一次间接和多一次堆分配——所以它是接口类的工具，不是热路径数据结构的工具。

这节讲什么

  1. Pimpl 的标准结构（头文件 + .cpp 两侧完整代码，实测可编译）；
  2. 核心规则：析构为什么必须在 .cpp 定义（含报错原文）；
  3. unique_ptr vs shared_ptr 做 Pimpl 的区别；
  4. 成本核算：收益（编译防火墙、ABI 稳定）与代价（间接、堆分配）。

核心结构（完整可编译）

// ============ widget.h ============
#pragma once
#include <memory>

class Widget {
    struct Impl;                    // 只有前向声明：调用方看不见实现
    std::unique_ptr<Impl> pImpl;    // 不完整类型可以做 unique_ptr 成员
public:
    Widget();
    ~Widget();                              // ★ 只声明，定义必须在 .cpp
    Widget(Widget&&) noexcept;              // ★ 移动也要去 .cpp 定义
    Widget& operator=(Widget&&) noexcept;
    Widget(const Widget&) = delete;         // 拷贝默认禁用（拷贝需要 Impl 完整）
    Widget& operator=(const Widget&) = delete;
    int get() const;
};

// ============ widget.cpp ============
#include "widget.h"
#include <vector>

struct Widget::Impl {               // 实现细节全在这里
    std::vector<int> data{1, 2, 3};
};

Widget::Widget()  : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default;        // Impl 在此处已完整，default 安全
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;
int Widget::get() const { return pImpl->data.size(); }

// ============ main.cpp ============
#include "widget.h"
int main() {
    Widget w;                    // w.get() == 3
    Widget w2 = std::move(w);    // 移动 OK
    // sizeof(Widget) == 8 —— 就装一个指针
}

clang 23.1.0 实测编译运行通过：w.get() = 3、sizeof(Widget) = 8、移动后 w2.get() = 3。

调用方视角的关键数字：sizeof(Widget) = 8。不管 Impl 里塞多少成员（vector、map、第三方库对象），Widget 永远是一个指针的大小——这正是 ABI 稳定的来源。

核心规则：析构（和移动）必须在 .cpp 定义

把上面头文件里的 ~Widget(); 声明删掉（让编译器在类内隐式生成），clang 报错原文：

error: allocation of incomplete type 'Widget::Impl'
error: invalid application of 'sizeof' to an incomplete type 'Widget::Impl'

机制：unique_ptr<Impl> 的默认删除器要 delete Impl，而 delete 需要 sizeof(Impl) 和 Impl 的析构——都要求完整类型。如果 ~Widget 在头文件隐式生成，那么每个包含该头文件、且销毁 Widget 的 TU 都会在"Impl 不完整"的上下文里实例化这个析构，全军覆没。

对策就是把会触发删除器的特殊成员函数声明在头文件、定义在 .cpp（Impl 完整之后）：

成员函数 头文件 .cpp
析构 ~Widget() 只声明 = default（Impl 完整，安全）
移动构造/移动赋值 只声明 = default
构造函数 只声明 定义（要 make_unique<Impl>）
拷贝构造/拷贝赋值 通常 = delete 要支持得手写深拷贝（Impl 逐成员复制）

注意 .cpp 里 ~Widget() = default; 是对的——"在类外 = default"让编译器在这个 TU（Impl 已完整）里生成析构体。头文件里 = default 才是错的。

用 shared_ptr 做 Pimpl 的例外

shared_ptr<Impl> 的删除器是构造时类型擦除绑定的，析构时不需要 Impl 完整——所以 shared_ptr 版 Pimpl 可以连析构声明都省掉。但代价是引用计数开销 + sizeof(Widget) 变 16。Pimpl 语境下所有权明明独占，unique_ptr 才是对价的工具，shared_ptr 版本属于"能跑但买贵了"。

成本核算

收益：

  1. 编译防火墙：头文件不再 #include 实现依赖（<vector>、第三方库头）。改 Impl 只重编一个 .cpp；包含头文件的几百个 TU 不被传染。
  2. ABI 稳定：Widget 对象布局恒为一个指针（实测 8 字节）。库升级改了私有实现，调用方不用重编译，链上新 .so/.a 就行——动态库发布的根基技术。
  3. 信息隐藏：私有成员的定义彻底不进头文件，连"看到了但访问不了"都不存在。

代价：

  1. 每次访问实现多一次指针间接（pImpl->）；
  2. 每个对象多一次堆分配（make_unique<Impl>）；
  3. 代码量翻倍（声明/定义分离，Impl 里还要搬一份成员函数）。

适用判断：对外接口类（引擎、连接、会话——构造少、活得久、接口稳定）→ 值；热路径数据结构（订单、行情 tick——每秒百万次构造/拷贝/访问）→ 不值，间接和堆分配都是热路径毒药。

常见错误（新手踩坑）

  1. 头文件里 ~Widget() = default;。最常见的 Pimpl 错误——default 在类内 = 在 Impl 不完整处生成析构体 = 每个使用者 TU 都编不过。记住口诀：声明在头，default 在 .cpp。
  2. 移动成员忘了也去 .cpp。只把析构挪走、移动构造留在类内隐式生成——unique_ptr 的移动赋值会先析构旧值，同样触发删除器实例化，同样炸。
  3. 想要拷贝又忘了深拷贝。unique_ptr 不可拷贝，Pimpl 类默认不可拷贝。要拷贝语义需在 .cpp 手写：Widget::Widget(const Widget& o) : pImpl(std::make_unique<Impl>(*o.pImpl)) {}。
  4. 在热路径类上用 Pimpl。每次访问多一次间接 + 每对象一次堆分配——tick 数据结构用 Pimpl 是把编译时间省下来、把延迟花出去。

新手要点（和 C 的区别）

  • C 的 opaque pointer 就是 Pimpl 的祖宗：头文件 typedef struct Widget Widget;，.c 里 struct Widget { ... };，调用方只摸指针。《C 和指针》ch07 讲过这个手法。C++ 版的升级是 unique_ptr 自动管理生命周期——C 版要手写 Widget_create/Widget_destroy 并祈祷调用方记得调。
  • 为什么 C++ 比 C 更需要它：C 的 struct 成员可以藏在 .c 里天经地义；C++ 的 class 私有成员必须在头文件的类定义里——Pimpl 是把 C 的隐藏能力"偷渡"回 C++ 的办法。
  • 判断口诀：这个类是"给别人用的接口"还是"热路径上的数据"？前者考虑 Pimpl，后者千万别。

HFT 关联

  • 交易引擎的编译时间：核心引擎头文件被几百个策略 TU 包含，改一行私有实现全量重编分钟级。引擎主类 Pimpl 化后，策略侧只依赖稳定接口头，增量编译秒级。
  • 商业库交付：给外部团队的 SDK（行情接入、风控前置）用 Pimpl 保持 ABI 稳定——你升级实现，对方不重编。8 字节的固定对象布局是合同的一部分。
  • 热路径反例：订单、行情 tick 这类每秒百万级构造/访问的对象绝不 Pimpl——多一次间接就是多一次潜在 cache miss，多一次堆分配就是多一次分配器锁。Pimpl 是给"少而重"的接口类的。

  1. Pimpl 里为什么析构必须在 .cpp 定义？头文件里 = default 会报什么错？
  2. 除了析构，还有哪些特殊成员函数必须挪到 .cpp？为什么？
  3. 实测 sizeof(Widget)（Pimpl 版）是多少？这个数字为什么就是 ABI 稳定的来源？
  4. 用 shared_ptr<Impl> 做 Pimpl 为什么能省掉析构声明？为什么不推荐？
  5. Pimpl 的三项代价是什么？什么样的类适合/不适合？
  6. Pimpl 和 C 的 opaque pointer 是什么关系？C++ 版升级了什么？
参考答案

  1. unique_ptr<Impl> 的默认删除器要 delete Impl，需要 sizeof(Impl) 和 Impl 的析构——都要求完整类型。析构若在头文件（类内）隐式生成，每个包含头文件并销毁 Widget 的 TU 都在 Impl 不完整的上下文实例化它，编译失败：error: invalid application of 'sizeof' to an incomplete type 'Widget::Impl'。把 ~Widget(); 只声明在头文件、.cpp 里 = default（Impl 完整之后），析构体就只在一个 TU 生成。

  2. 移动构造和移动赋值（unique_ptr 移动赋值会先析构旧值，同样触发删除器）；构造函数也要在 .cpp（make_unique<Impl> 需要完整类型，报 allocation of incomplete type）；若要拷贝语义，拷贝构造/赋值也要在 .cpp 手写深拷贝。规律：凡是会实例化删除器或创建 Impl 的函数，都得待在 Impl 完整的 TU。

  3. 8 字节（实测）——一个 unique_ptr 指针。无论 Impl 里成员怎么增删改，Widget 的对象布局不变，已有调用方代码的二进制依旧合法：改实现只需重编/重链库一侧，调用方不用动。这就是"ABI 稳定"的物理含义。

  4. shared_ptr 的删除器在构造时类型擦除绑定到控制块，析构时走的是擦除后的函数指针，不要求 Impl 完整——所以可以连析构声明都省。不推荐是因为 Pimpl 场景所有权明明独占：shared_ptr 白付原子引用计数的税，对象还变 16 字节。独占语义用 unique_ptr，这同时也是在向读者声明"不共享"。

  5. 代价：访问实现多一次指针间接；每对象多一次堆分配；声明/定义分离 + Impl 搬运的代码量翻倍。适合：构造少、活得久、接口稳定的对外接口类（引擎、连接、SDK 对象）。不适合：热路径数据结构（订单、tick）——间接是 cache miss，堆分配是分配器锁，都是延迟毒药。

  6. Pimpl 就是 C opaque pointer 惯用法的 C++ 版：C 里头文件只给 typedef struct Widget Widget;，实现藏 .c。目的相同（隐藏实现、稳定 ABI）。C++ 版的升级：①unique_ptr 自动管理释放，异常路径不泄漏，不用祈祷调用方记得调 Widget_destroy；②类成员函数语法保留，接口仍是一个 class 而不是一包 Widget_xxx(Widget*) 自由函数。

创建两个 shared_ptr 指向同一裸指针，会发生什么？

答案与复习指引

double free / 崩溃。 每个 shared_ptr 创建自己的控制块，引用计数各为 1。两个都析构时各自 delete raw → double free。

正确做法： auto p1 = std::make_shared<Widget>(); auto p2 = p1;（拷贝共享同一控制块）。

或用 enable_shared_from_this： 对象继承 enable_shared_from_this<T>，在成员函数中调 shared_from_this() 返回正确的 shared_ptr。

std::unique_ptr<FILE, decltype(&fclose)> fp(fopen("data.txt", "r"), &fclose);

fp 离开作用域后如何处理 FILE*？
