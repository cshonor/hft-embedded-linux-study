Smart Pointers — Items 18–22

本章讲什么

裸 new/delete 是 C++ 资源泄漏与悬垂指针的头号来源。智能指针用 RAII 把"所有权"编码进类型系统：unique_ptr 表达独占、shared_ptr 表达共享、weak_ptr 打破环引用。本章讲清三者的所有权语义、性能代价与正确用法——这是 Modern C++ 区别于 C 的核心能力，也是 muduo / HFT 引擎回调与对象生命周期管理的基石。

各 Item 要点

Item 18：用 std::unique_ptr 管理独占资源

unique_ptr 是零开销抽象——大小 = 裸指针（默认），开销 = 裸指针（移动是几条指令，析构内联调用 delete）。它表达"唯一所有权"，不可拷贝、只能移动。

std::unique_ptr<Widget> make() { return std::make_unique<Widget>(); }

自定义删除器：unique_ptr<Widget, void(*)(Widget*)> 可挂自定义删除器。但删除器类型是 unique_ptr 类型的一部分——不同删除器 = 不同类型。这对接口设计有影响（函数参数要明确删除器类型）。HFT 里用它管理 FILE*、fd、DPDK rte_mbuf*（自定义删除器调 rte_pktmbuf_free）。

与 C API 互操作：unique_ptr 的 .get() 取裸指针传给 C 接口；.release() 放弃所有权交还给 C。

Item 19：用 std::shared_ptr 管理共享所有权

shared_ptr 用引用计数实现共享。控制块（control block）含强引用计数 + 弱引用计数 + 删除器 + 分配器。拷贝 shared_ptr 原子地递增计数（++ 是原子操作），析构递减，归零调用删除器。

代价： - 大小 = 2 个指针（对象指针 + 控制块指针），是裸指针的 2 倍。 - 拷贝/析构有原子操作开销——比非原子 ++ 慢一个数量级，且在多核间引发 cache 行同步。HFT 热路径绝不在每 tick 路径上拷贝 shared_ptr。

控制块创建时机（一次性，只创建一次）： 1. make_shared（推荐） 2. 从 unique_ptr 构造 3. 用裸指针 new 构造 shared_ptr——两次 new 同一裸指针会创建两个控制块，double free

enable_shared_from_this：对象需要在成员函数里返回自身的 shared_ptr 时，继承 enable_shared_from_this<T> 并调 shared_from_this()——直接 shared_ptr<T>(this) 会创建新控制块导致 double free。

Item 20：用 std::weak_ptr 指向可能悬垂的 shared_ptr

weak_ptr 不增加强引用计数，观察 shared_ptr 但不延长对象生命。要访问对象须 lock() 提升为 shared_ptr（原子地检查并获取）：

std::weak_ptr<Widget> wp = sp;
if (auto p = wp.lock()) { /* p 有效，安全使用 */ }

三大用途：缓存（对象可被回收）、观察者模式（观察者不持有被观察对象）、打破 shared_ptr 环引用（A↔B 互引导致计数永不归零、内存泄漏）。

Item 21：优先 make_unique / make_shared 而非 new

make_shared 一次分配同时建对象 + 控制块（单次堆分配），比 shared_ptr<T>(new T) 的两次分配更省且 cache 友好。

例外（不能 make 的场景）： - 需要自定义删除器 → 只能 new - 自定义分配器 - make_shared 把对象内存与控制块绑在一起——若有 weak_ptr 长期存活，对象的内存（已析构但未释放）会延迟到所有 weak_ptr 都销毁才回收。大对象 + 长期 weak_ptr 场景要用 new。

Item 22：用 Pimpl 惯用法降低编译依赖

Pimpl（Pointer to Implementation）把实现细节藏到 .cpp，头文件只留一个 unique_ptr<Impl>：

// widget.h
class Widget {
    struct Impl;
    std::unique_ptr<Impl> pImpl;   // 不需要 Impl 的完整定义
public:
    Widget();
    ~Widget();   // 必须在 .cpp 定义（unique_ptr 析构需要完整类型）
};

头文件改动减少 → 编译依赖降低 → 增量编译加速。这和《C 和指针》ch07 的 opaque pointer / PIMPL 是同一思想，C++ 版用 unique_ptr 自动管理。

HFT 关联

  • unique_ptr 管 mbuf / fd：自定义删除器让 unique_ptr 管 DPDK rte_mbuf*（删除器调 rte_pktmbuf_free）或 POSIX fd（删除器调 close）。RAII 保证异常路径也不泄漏资源——比 C 的 goto cleanup 更安全且零运行开销。
  • shared_ptr 只在对象池/策略共享：HFT 热路径不用 shared_ptr（原子计数代价），但对象池、策略对象（多线程共享、需要延迟销毁）用它管理生命周期。务必在线程入口一次性拷贝 shared_ptr，热循环内用裸引用，避免每帧原子操作。
  • weak_ptr 观察者模式：行情分发器持有策略的 weak_ptr，策略销毁后分发器 lock() 返回空自动跳过——避免策略热卸载时的悬垂回调。
  • Pimpl 降编译依赖：大型交易引擎头文件改动会触发全量重编译，Pimpl 把核心结构藏到 .cpp，增量编译从分钟级降到秒级——开发效率的直接提升。

Item 18：用 std::unique_ptr 管理独占资源

第 4 章 智能指针 · Item 18 · 下一节：Item 19 shared_ptr

为什么要学这个（先建立直觉）

C 里管理堆资源靠纪律：malloc 之后配对 free，中间有 goto cleanup、有异常路径、有早退 return——每一条路都得记得释放，漏一条就是泄漏。unique_ptr 把这条纪律变成了类型系统强制的规则：资源包进对象，对象出作用域自动释放，所有权唯一、拷贝直接被编译器拒绝。

更关键的是 Meyers 强调的卖点：零开销。unique_ptr 不是"方便但慢一点"的妥协——默认配置下它和裸指针一样大、一样快，是"不用白不用"的纯收益抽象。这一节用实测把这个"零开销"拆开看清楚，包括它在什么情况下不再零开销（有状态删除器）。

这节讲什么

  1. 零开销的 sizeof 矩阵实测：数组类型、空函数对象、无/有捕获 lambda、函数指针；
  2. unique_ptr 作为工厂返回类型，以及它到 shared_ptr 的单向转换；
  3. get() / release() / reset() 所有权三件套的实测语义；
  4. 数组特化 unique_ptr<T[]>：有下标、无 *、不能转 shared_ptr<T>；
  5. 自定义删除器实战：FILE*、mmap 区域。全部论断附本机实测（clang 23.1.0，arm64-apple-darwin，libc++，-std=c++17 -Wall）。

零开销矩阵：sizeof 实测

struct EmptyDeleter { void operator()(int* p) const { delete p; } };
auto stateless = [](int* p) { delete p; };                  // 无捕获
int captured = 7;
auto stateful = [captured](int* p) { (void)captured; delete p; };  // 有捕获
using FnDel = void(*)(FILE*);
// 逐个打印 sizeof(unique_ptr<int>) / unique_ptr<int[]> / unique_ptr<int, EmptyDeleter>
// / unique_ptr<int, decltype(stateless)> / unique_ptr<int, decltype(stateful)>
// / unique_ptr<FILE, decltype(&fclose)> / unique_ptr<FILE, FnDel> / shared_ptr<int>

本机实测 clang 23.1.0 输出：

sizeof(int*)                                   = 8
sizeof(unique_ptr<int>)                         = 8
sizeof(unique_ptr<Widget>)                      = 8
sizeof(unique_ptr<int[]>)                       = 8
sizeof(unique_ptr<int, EmptyDeleter>)           = 8
sizeof(unique_ptr<int, stateless lambda>)       = 8
sizeof(unique_ptr<int, stateful lambda>)        = 16
sizeof(unique_ptr<FILE, decltype(&fclose)>)     = 16
sizeof(unique_ptr<FILE, FnDel>)                 = 16
sizeof(shared_ptr<int>)                         = 16
形态 sizeof 为什么
int*（对照） 8 裸指针基线
unique_ptr<T>（默认删除器） 8 default_delete 是空类型，EBO 压成 0
unique_ptr<T[]> 8 数组特化同样只有一个指针
unique_ptr<T, 空函数对象> 8 无状态删除器 → 空基类优化
unique_ptr<T, 无捕获lambda> 8 同上
unique_ptr<T, 有捕获lambda> 16 删除器有状态，必须存进对象
unique_ptr<FILE, decltype(&fclose)> 16 函数指针是值，运行期才确定，无法 EBO
shared_ptr<T>（对照） 16 对象指针 + 控制块指针

一句话记忆：默认配置 8 字节 = 裸指针；删除器"无状态"白送，"有状态"或"函数指针" +8。函数指针那条最容易踩——decltype(&fclose) 推导出来的是 int(*)(FILE*)，是个要在运行期读取的数据成员，不是可以 EBO 的空类型。想省这 8 字节，把删除器写成空函数对象或无捕获 lambda。

对照删除器自身尺寸（实测）：sizeof(EmptyDeleter)=1、sizeof(无捕获lambda)=1、sizeof(有捕获lambda)=4——空类型单独存在时至少 1 字节，作为基类成员时被压成 0。

工厂返回类型：所有权随返回值移交

std::unique_ptr<Widget> makeWidget(int id) {
    return std::make_unique<Widget>(id);   // 工厂返回 unique_ptr
}

这是 C++14 之后工厂函数的标准签名，三重好处：语义自文档化（"这个东西归你，别人没有"）、异常安全（make_unique 内部完成分配+构造+接管，没有裸指针裸露的窗口）、调用方可以零成本升级（unique_ptr 右值能隐式转 shared_ptr）。

unique_ptr → shared_ptr 是单向免费转换

std::shared_ptr<Widget> sp = makeWidget(4);   // OK：右值 unique_ptr 隐式转换
std::cout << sp.use_count();                  // 实测 1

关键细节：转换会把删除器一起搬进控制块——用自定义删除器的 unique_ptr<Derived, LogDel> 转出来的 shared_ptr，析构时仍然调 LogDel（实测打印 [LogDel]）。反过来 shared_ptr → unique_ptr 不存在，因为共享所有权无法降级成独占；从已 move 空的 unique_ptr 转换得到的是空 shared_ptr（实测 null）。

版本差异：make_unique 是 C++14

-std=c++11 实测报错 error: no member named 'make_unique' in namespace 'std'；-std=c++14/17/20 全部通过。C++11 项目里自己补一行 template<class T, class... A> std::unique_ptr<T> make_unique(A&&... a) { return std::unique_ptr<T>(new T(std::forward<A>(a)...)); }，不要用裸 new 凑合。

所有权三件套：get / release / reset

调用 语义 谁负责释放 记忆
up.get() 借出裸指针，up 不变 仍是 up 借
up.release() 交出所有权，up 置空 变成调用方 给
up.reset(p) 先释放旧对象，再接管 p up（新对象） 换
up.reset() 释放旧对象，置空 — 换（换成空）

实测（构造/析构带打印）：

== get(): 借出，所有权不动 ==
  observe id=1
  still owned: yes
== reset(): 先释放旧的，再接管新的 ==
  ctor #2
  dtor #1          ← reset(new Widget(2)) 时旧的 #1 立刻析构
== release(): 交出所有权，自身置空 ==
  up after release null? yes
  consume id=2
  dtor #2          ← 释放责任已经转给 consume

判断准则：传给"只读一下"的接口用 get()（所有 C API 的观察型函数）；传给"之后归对方管"的接口用 release()（交给 C 库、塞进 C 结构体、注册到回调表）。release() 之后忘了接盘就是泄漏——这是 unique_ptr 唯一会主动放弃资源的操作。

数组特化 unique_ptr<T[]>

auto arr = std::make_unique<int[]>(4);   // 实测初始值全 0：值初始化
arr[0] = 10; arr[3] = 40;
std::unique_ptr<int[]> a2 = std::move(arr);   // 可移动
std::shared_ptr<int[]> sa = std::move(a2);    // C++17 起可转 shared_ptr<int[]>

实测 arr[0]=10 arr[3]=40、a2[0]=10、sa.use_count()=1，尺寸 sizeof(unique_ptr<int[]>)=8、sizeof(unique_ptr<int[8]>)=8。

三个必须知道的差异：

  1. 有 operator[]，没有 operator* / operator->。写 *arr 实测报错：

error: indirection requires pointer operand ('unique_ptr<int[]>' invalid) int x = *arr; ^~~~

  1. 不能转成非数组的 shared_ptr<T>。shared_ptr<int> bad = std::move(arr); 实测关键诊断行 note: candidate template ignored: requirement '__compatible_with_v<int[], int>' was not satisfied，只能转 shared_ptr<int[]>（C++17 起的特化）。
  2. make_unique<T[]>(n) 是值初始化（实测全 0），不是 new T[n] 的默认初始化；要"不初始化省时间"得等 C++20 的 make_unique_for_overwrite。

和 std::vector 怎么选：默认选 vector（有尺寸、有迭代器、能进算法）。unique_ptr<T[]> 只在"必须持有裸数组所有权去对接 C API"或"尺寸固定且不想付 vector 三个指针的开销"时用。

自定义删除器实战

FILE*：两种写法，两种体积

using FilePtr1 = std::unique_ptr<FILE, decltype(&fclose)>;   // 函数指针：16 字节
struct FileCloser { void operator()(FILE* f) const { if (f) fclose(f); } };
using FilePtr2 = std::unique_ptr<FILE, FileCloser>;          // 空函数对象：8 字节

FilePtr1 f1(fopen("/tmp/demo.txt", "w"), &fclose);   // 必须显式传函数指针值
FilePtr2 f2(fopen("/tmp/demo.txt", "r"));            // 删除器默认构造即可

实测：f1 写入成功、f2 读回 hello unique_ptr、出作用域打印 [FileCloser] fclose；sizeof(FilePtr1)=16、sizeof(FilePtr2)=8。同样的功能，写法决定体积——"零开销"要靠写法人为维持。

mmap 区域：带状态删除器

struct MmapDeleter {
    size_t len;                       // ← 状态：munmap 需要长度
    void operator()(void* p) const { if (p) munmap(p, len); }
};
using MmapPtr = std::unique_ptr<void, MmapDeleter>;

const size_t len = 4096;
void* addr = mmap(nullptr, len, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANON, -1, 0);
MmapPtr region(addr, MmapDeleter{len});      // 出作用域自动 munmap

实测输出 sizeof(MmapPtr)=16（删除器带 len，+8）、region[0]=A、出作用域打印 [MmapDeleter] munmap 4096 bytes。说明删除器"有状态"是正当的：munmap 要求长度，而 unique_ptr 只存一个指针，状态只能塞进删除器对象。能无状态就无状态（长度写成编译期常量/模板参数），不能就老实付 8 字节。对照组：手写 int* p = new int[10]; delete p; 实测警告 warning: 'delete' applied to a pointer that was allocated with 'new[]' [-Wmismatched-new-delete]——unique_ptr<T[]> 从类型上杜绝了这个错配。

完整可运行例子

#include <cstdio>
#include <memory>
#include <iostream>

struct Order {
    int qty;
    explicit Order(int q) : qty(q) { std::cout << "  Order ctor qty=" << qty << "\n"; }
    ~Order() { std::cout << "  Order dtor qty=" << qty << "\n"; }
};
std::unique_ptr<Order> makeOrder(int q) { return std::make_unique<Order>(q); }   // 工厂
void inspect(const Order* o) { std::cout << "  inspect qty=" << o->qty << "\n"; }
struct FileCloser { void operator()(FILE* f) const { if (f) fclose(f); } };

int main() {
    std::cout << std::unitbuf;
    auto up = makeOrder(100);
    inspect(up.get());                 // 借
    up.reset(new Order(200));          // 换（旧的在此析构）
    Order* raw = up.release();         // 给
    std::cout << "  up 已置空? " << (up == nullptr ? "yes" : "no") << "\n";
    delete raw;

    std::shared_ptr<Order> sp = makeOrder(300);
    std::cout << "  use_count=" << sp.use_count() << "\n";

    std::unique_ptr<FILE, FileCloser> fp(fopen("/tmp/emcG_order.txt", "w"));
    fprintf(fp.get(), "qty=100\n");
    std::cout << "  sizeof(fp)=" << sizeof(fp) << "（空删除器 → EBO）\n";

    auto buf = std::make_unique<int[]>(4);
    for (int i = 0; i < 4; ++i) buf[i] = i * 10;
    std::cout << "  buf[3]=" << buf[3] << " sizeof=" << sizeof(buf) << "\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

  Order ctor qty=100
  inspect qty=100
  Order ctor qty=200
  Order dtor qty=100
  up 已置空? yes
  Order dtor qty=200
  Order ctor qty=300
  use_count=1
  sizeof(fp)=8（空删除器 → EBO）
  buf[3]=30 sizeof=8
  Order dtor qty=300

常见错误（新手踩坑）

  1. 同一裸指针构造两个 unique_ptr。Widget* p = new Widget; unique_ptr<Widget> a(p), b(p); → 双重释放。ASan（-fsanitize=address -g）实测报错 ==94325==ERROR: AddressSanitizer: attempting double-free on 0x602000000990 in thread T0（栈顶 default_delete<int>::operator() ← unique_ptr::~unique_ptr）。若析构函数会读成员（如打印 id），会先报 heap-use-after-free——同一个 bug 的两种现场。纪律：裸指针交给智能指针后立刻忘掉它；优先 make_unique。
  2. 以为函数指针删除器也零开销。实测 16 字节。要省体积，写成空函数对象或无捕获 lambda。
  3. 用裸 new 构造而不是 make_unique。能编过，但 make_unique 更短、更异常安全，且 C++14 起全标准可用。
  4. 移动后还使用源指针。std::move 之后源 unique_ptr 是 nullptr（实测确认），只剩重新赋值和析构两种合法操作。
  5. release() 之后忘了接盘。这是 unique_ptr 唯一会主动放弃资源的接口，用之前先确定谁负责释放。

HFT 关联

  • 管 mbuf / fd / 库句柄：自定义删除器让 unique_ptr 管 DPDK rte_mbuf*（删除器调 rte_pktmbuf_free）、POSIX fd（删除器调 close）、库句柄。RAII 保证异常路径、早退路径都不泄漏——比 goto cleanup 干净，还零开销。
  • 热路径资源的安全网：热路径上传递所有权用 unique_ptr + std::move，无引用计数、无原子操作——这点和 shared_ptr 形成决定性对比（见 Item 19）。
  • 工厂函数返回 unique_ptr：std::unique_ptr<Strategy> make_strategy(Config) 是策略对象创建的标准签名，接口语义自文档化。
  • 定长缓冲用 unique_ptr<T[]>：行情快照的定长档位数组（unique_ptr<Level[]>）比 vector 少 size/capacity 字段，尺寸不变时零扩容。

自测题

1. 默认 unique_ptr<int> 多大？凭什么说"零开销"？什么情况下会变成 16 字节？

答案

8 字节（实测）。"零开销"指与手写 new/delete 相比不引入额外内存或时间成本：无引用计数、无控制块，解引用与析构都是内联指针操作，独占所有权靠类型系统（删除拷贝）在编译期表达。变 16 字节的两种情况：删除器是函数指针（实测 unique_ptr<FILE, decltype(&fclose)> = 16），或删除器有状态（有捕获 lambda / 带成员的删除器 = 16）。无捕获 lambda 和空函数对象靠 EBO 仍是 8 字节。

2. unique_ptr<FILE, decltype(&fclose)> 和 unique_ptr<FILE, 某lambda类型> 是同一类型吗？能放进同一个 vector 吗？

答案

不是同一类型——删除器类型是第二个模板参数，删除器不同则 unique_ptr 类型不同，不能互相赋值，也不能进同一个 vector<unique_ptr<T, D>>；两个不同的 lambda 类型也互不相同。要进容器，统一用 unique_ptr<T, std::function<void(T*)>>（代价是变 32 字节 + 间接调用），或用 shared_ptr<T>（删除器类型擦除，不进类型）。

3. .get() / .release() / .reset() 各是什么所有权语义？

答案

.get() 借出裸指针，所有权不动（智能指针仍负责释放）；.release() 交出所有权并置空自身（实测 up == nullptr 为 true），释放责任转给接收方，忘了 delete 就泄漏；.reset(p) 先释放当前持有的对象再接管 p（实测先打印 dtor #1）。记忆法：借 / 给 / 换。

4. unique_ptr 能转成 shared_ptr 吗？反过来呢？转换时删除器怎么处理？

答案

unique_ptr 右值能隐式转 shared_ptr（实测 use_count=1），且自定义删除器会被搬进控制块（实测用 LogDel 的 unique_ptr 转出来的 shared_ptr 析构时仍打印 [LogDel]）。反过来不行——共享所有权无法降级成独占。数组特化有额外限制：unique_ptr<T[]> 只能转 shared_ptr<T[]>，转 shared_ptr<T> 实测报 requirement '__compatible_with_v<int[], int>' was not satisfied。

5. unique_ptr<T[]> 和 std::vector<T> 怎么选？数组特化缺哪些操作？

答案

默认 std::vector<T>：有尺寸、有迭代器、能进算法。unique_ptr<T[]> 只在需要"拥有并移交裸数组所有权"时考虑（对接 C API、定长缓冲）。数组特化有 operator[] 但没有 operator* 和 operator->——实测 *arr 报 error: indirection requires pointer operand ('unique_ptr<int[]>' invalid)。另外 make_unique<T[]>(n) 是值初始化（实测全 0），不是 new T[n] 的默认初始化。

6. Widget* p = new Widget; unique_ptr<Widget> a(p), b(p); 会发生什么？ASan 报什么？

答案

双重释放（UB）。ASan 实测报 ERROR: AddressSanitizer: attempting double-free；若析构函数会读成员（如打印 id），会先报 heap-use-after-free——同一 bug 的另一种现场。根因是裸指针没有所有权信息。纪律：优先 make_unique，让裸指针不具名。

7. std::make_unique 从哪个标准开始有？C++11 项目里怎么办？

答案

C++14。实测 -std=c++11 报 error: no member named 'make_unique' in namespace 'std'，-std=c++14/17/20 全部通过。C++11 项目里自己补 template<class T, class... A> std::unique_ptr<T> make_unique(A&&... a) { return std::unique_ptr<T>(new T(std::forward<A>(a)...)); }。不要用裸 new 凑合——make_unique 消灭的是"new 求值与 unique_ptr 构造之间抛异常"的泄漏窗口。

Item 19：用 std::shared_ptr 管理共享所有权

第 4 章 智能指针 · Item 19 · 上一节：Item 18 unique_ptr · 下一节：Item 20 weak_ptr

为什么要学这个（先建立直觉）

unique_ptr 覆盖"一个资源一个主人"的场景，但现实里总有"多个对象都要用、谁也不知道谁最后用完"的时候——共享配置、共享连接、缓存里的条目。手写所有权协议（"最后离开的人关灯"）在多线程下几乎是必错的，shared_ptr 用引用计数把这盏灯自动化了。

但 shared_ptr 不是 unique_ptr 的"升级版"，是另一种价格的工具：体积翻倍、每次拷贝/析构都要原子操作、对象旁边还多一块控制块。这一节的任务就是搞清楚这份价格单的每一项——以及什么时候根本不该付。

这节讲什么

  1. 控制块里有什么、什么时候创建、分配几次（呼应 Item 21 make 函数）；
  2. 引用计数的线程安全 ≠ 所指对象的线程安全（实测区分）；
  3. 循环引用：LeakSanitizer 抓泄漏现场，weak_ptr 破环（详见 Item 20）；
  4. enable_shared_from_this 机制，以及 shared_ptr<T>(this) 为什么是灾难；
  5. 性能实测：原子计数单价、多核 cache 行乒乓、make_shared 的内存滞留副作用。全部论断附本机实测（clang 23.1.0，arm64-apple-darwin，libc++，-std=c++17 -Wall）。

控制块：共享的物理载体

shared_ptr 的共享靠一块控制块（control block）实现，里面装着：强引用计数、弱引用计数（归零才释放控制块本身）、类型擦除的删除器与分配器（这就是 shared_ptr 删除器不进类型的原因，与 unique_ptr 相反），以及对象指针（make_shared 时对象内嵌在控制块后面）。

auto sp = std::make_shared<Widget>();  // 强计数 = 1
auto sp2 = sp;                          // 拷贝 → 强计数 = 2（原子 ++）
// sp 析构  → 强计数 = 0 → 销毁 Widget → 弱计数归零后释放控制块

控制块何时创建（决定了所有坑）：make_shared<T>() 新建（对象内嵌，一次分配）；shared_ptr<T>(new T) 新建（对象独立，两次分配）；从已有 shared_ptr/weak_ptr 拷贝不新建；shared_ptr<T>(rawPtr) 一定新建——哪怕这个裸指针已经被人管着。最后这条就是所有 double-free 的根源。

分配次数实测（重载全局 operator new 计数）

sizeof(shared_ptr<Widget>) = 16    ← 两个指针：对象 + 控制块
sizeof(unique_ptr<Widget>) = 8     ← 对照：裸指针尺寸

实测（重载 operator new / operator delete 统计次数与块大小，Widget 为 16 字节）：

make_shared<Widget>()            分配次数 = 1   块大小: 40
new Widget + shared_ptr          分配次数 = 2   块大小: 16 32
make_unique<Widget>()            分配次数 = 1   块大小: 16
make_shared +2copy +weak_ptr     分配次数 = 1   块大小: 40
shared_ptr(new W, custom del)    分配次数 = 2   块大小: 16 32

三个可以直接读出来的结论：①make_shared 一次分配，new+shared_ptr 两次——和 Item 21 的结论一致，这里是计数实锤；②控制块本身 32 字节（第二块），make_shared 的合并块是 40 = 16（对象）+ 24（控制块），内嵌形态省掉了一份对象指针；③拷贝和 weak_ptr 都不分配——它们只动计数。

make_shared 的好处不只是"少一次分配"：对象和控制块同块内存，访问计数与访问对象大概率落在同一 cache 行；同时消灭了"裸指针外泄"的窗口。

副作用：长命 weak_ptr 会滞留对象内存

make_shared 的合并分配是有代价的——控制块和对象同生共死。实测（统计未释放字节数）：

make_shared 后              live = 88 bytes
  ~Big（对象已析构）
所有 shared_ptr 销毁后      live = 88 bytes   wp.expired()=true
weak_ptr 也 reset 后        live = 0 bytes

~Big 已经跑了（对象析构了），但那 88 字节没有还给分配器，因为只要还有一个 weak_ptr 活着，控制块就不能释放，而对象跟控制块在同一块内存里。大对象 + 长命 weak_ptr = 内存滞留——这是 make_shared 唯一的已知劣势，new+shared_ptr 版本则会在强计数归零时立刻归还对象内存。

线程安全：计数安全 ≠ 对象安全

这是最容易被一句话带偏的地方。实测三组：

A. 引用计数本身：8 个线程各持 sp 的一份副本，各做 10 万次 auto local = sp;（原子 ++ 后立即原子 --）。实测输出 Res ctor → main 里 use_count = 1 → Res dtor，只析构一次，ASan 无报告。计数精确归位。

B. 所指对象：两线程各做 20 万次 ++(*sp)，实测输出 *sp = 255164（期望 400000）。shared_ptr 完全没有保护对象——要保护得自己加锁或用 std::atomic。

C. 同一个 shared_ptr 实例被两线程一读一写（一个 reset()、一个拷贝）——同样是数据竞争。

谁 线程安全吗
控制块里的引用计数 ✅ 原子增减，多线程同时拷贝/析构各自副本安全
同一个 shared_ptr 实例 ❌ 一线程 reset 另一线程读 = 竞争
所指对象 *sp ❌ 与普通对象无异，需自己加锁

准确说法：控制块线程安全，指针实例和所指对象不线程安全。

循环引用：LeakSanitizer 现场

struct A { std::shared_ptr<B> b; ~A(){ std::cout << "  A dtor\n"; } };
struct B { std::shared_ptr<A> a; ~B(){ std::cout << "  B dtor\n"; } };  // ← 强引用成环
auto a = std::make_shared<A>();
auto b = std::make_shared<B>();
a->b = b;  b->a = a;      // 离开作用域

实测输出（没有任何 dtor 行——计数永远到不了 0）：

  离开作用域前 use_count: a=2 b=2
  离开作用域后（↑ 若没有 A dtor/B dtor 输出 = 泄漏）

ASan 的 LeakSanitizer（ASAN_OPTIONS=detect_leaks=1）实测报告：

==94780==ERROR: LeakSanitizer: detected memory leaks
Indirect leak of 40 byte(s) in 1 object(s) allocated from:
    #8 std::__1::shared_ptr<B> std::__1::make_shared... shared_ptr.h:668
SUMMARY: AddressSanitizer: 80 byte(s) leaked in 2 allocation(s).

把 B 侧的 shared_ptr<A> 换成 weak_ptr<A> 再跑，实测输出立刻正常：

  离开作用域前 use_count: a=1 b=2     ← a 的强计数只剩 1（weak_ptr 不增计数）
  WA dtor
  WB dtor

破环的通用规则：父子关系里，子指向父用 weak_ptr（详见 Item 20 weak_ptr）。

enable_shared_from_this：从对象内部交出自己

场景：对象的成员函数需要返回"指向自己的 shared_ptr"（注册回调、投递异步任务）。直接写 shared_ptr<Widget>(this) 会新建控制块。

实测用 enable_shared_from_this：

class Widget : public std::enable_shared_from_this<Widget> {
public:
    std::shared_ptr<Widget> selfShared() { return shared_from_this(); }
    std::shared_ptr<Widget> selfWrong()  { return std::shared_ptr<Widget>(this); } // 灾难
};

实测输出：

== 正解：对象已被 shared_ptr 管理 ==
  use_count=2  同一控制块? yes
== 错误：栈对象上调 shared_from_this() ==
  caught std::bad_weak_ptr: bad_weak_ptr
== 灾难：shared_ptr<Widget>(this) ==
  use_count sp=1 sp2=1（互不知情，都是 1）

机制：enable_shared_from_this 在对象里埋一个 weak_ptr，第一个 shared_ptr 接管对象时初始化它；shared_from_this() 从这个 weak_ptr lock() 出共享同一控制块的 shared_ptr。所以它不是凭空造计数，而是找到已有的计数——前提是已经有一个（否则抛 std::bad_weak_ptr，实测捕获成功）。

selfWrong() 在 -fsanitize=address 下实测报 ==94815==ERROR: AddressSanitizer: attempting free on address which was not malloc()-ed: 0x604000000468：因为 make_shared 把对象放在合并块中间，新控制块拿到的是内部指针，最终 delete 一个非 malloc 返回的地址。栈上对象用这招则是 delete 非堆内存——同样是 UB。

性能：原子计数与 cache 行乒乓

实测（-O2，20,000,000 次循环，每次取指针并累加到 volatile 防止优化掉）：

裸指针       20000000 次: 17.3061 ms  (0.865306 ns/次)
unique_ptr   20000000 次: 13.8169 ms  (0.690844 ns/次)
shared_ptr   20000000 次: 280.235 ms  (14.0118 ns/次)
1 线程 x 2e6 shared_ptr 拷贝: 26.367 ms
4 线程 x 2e6 shared_ptr 拷贝: 392.461 ms

一次"拷贝 + 析构"约 14 ns，是裸指针的 20 倍——不是"慢一点"，是数量级差。拆开看：①原子 RMW（x86 lock xadd、ARM LL/SC 循环，无竞争也这个量级）；②cache 行乒乓——4 线程做 4 倍工作却花 14.9 倍时间（26.4 ms → 392.5 ms），单次成本从 ~13 ns 涨到 ~49 ns，控制块是所有副本的汇聚点，false sharing 的教科书案例；③体积与间接——16 字节/指针 + 控制块另算 24–32 字节 + 访问对象两次解引用。

一句话对照 intrusive 指针（boost::intrusive_ptr、内核 kref）：计数放在对象内部而非旁挂控制块，24–32 字节的控制块和第二次解引用全省了，代价是类型必须自带计数字段、且不支持 weak_ptr——shared_ptr 是"通用但贵"，intrusive 是"更快但要改造类型"。

完整可运行例子

#include <memory>
#include <iostream>

struct Node {
    std::string name;
    std::shared_ptr<Node> child;      // 强引用
    std::weak_ptr<Node>   parent;     // 弱引用：打破环
    explicit Node(std::string n) : name(std::move(n)) { std::cout << "  ctor " << name << "\n"; }
    ~Node() { std::cout << "  dtor " << name << "\n"; }
};
class Session : public std::enable_shared_from_this<Session> {
public: std::shared_ptr<Session> self() { return shared_from_this(); } };

int main() {
    std::cout << std::unitbuf;
    auto root = std::make_shared<Node>("root");
    auto leaf = std::make_shared<Node>("leaf");
    root->child = leaf;  leaf->parent = root;
    std::cout << "  root.use_count=" << root.use_count()
              << "  leaf.use_count=" << leaf.use_count() << "\n";

    std::weak_ptr<Node> w = leaf;                       // 不增强计数
    std::cout << "  leaf.use_count=" << leaf.use_count()
              << "  w.expired()=" << (w.expired() ? "true" : "false") << "\n";
    if (auto locked = w.lock()) std::cout << "  lock() 拿到 " << locked->name << "\n";

    auto s = std::make_shared<Session>();
    auto s2 = s->self();
    std::cout << "  同一控制块? " << (s.get() == s2.get() ? "yes" : "no")
              << "  use_count=" << s.use_count() << "\n";
    std::cout << "  sizeof(shared_ptr<Node>)=" << sizeof(std::shared_ptr<Node>)
              << "  sizeof(unique_ptr<Node>)=" << sizeof(std::unique_ptr<Node>) << "\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

  ctor root
  ctor leaf
  root.use_count=1  leaf.use_count=2
  leaf.use_count=2  w.expired()=false
  lock() 拿到 leaf
  同一控制块? yes  use_count=2
  sizeof(shared_ptr<Node>)=16  sizeof(unique_ptr<Node>)=8
  dtor root
  dtor leaf

注意 root.use_count=1 而 leaf.use_count=2：leaf 被 root->child 强持有，而 root 只被 leaf->parent 弱持有——环被打破了，两个对象都能正常析构。

常见错误（新手踩坑）

  1. 同一裸指针构造两个 shared_ptr。形成两个互不知情的控制块，各自计数为 1，任一归零就 delete 对象，另一个悬垂。变体包括 shared_ptr<T>(this) 和 shared_ptr<T>(sp.get())。对策：副本永远从已有 shared_ptr 拷贝；优先 make_shared。
  2. 在热路径拷贝 shared_ptr。实测 14 ns/次，多核争用更贵。热路径传引用或裸指针，只在生命周期边界拷贝。
  3. 以为 shared_ptr 让对象线程安全。线程安全的只有引用计数本身；实测两线程各 20 万次 ++(*sp) 得到 255164 而不是 400000。
  4. 循环引用泄漏。A 持 B、B 持 A，Lsan 实测报 80 byte(s) leaked in 2 allocation(s)。打破循环用 weak_ptr。
  5. 忽略 make_shared 的滞留副作用。还有 weak_ptr 活着时，对象占的内存不会归还（实测 88 bytes 一直挂着）。大对象场景要评估。

HFT 关联

  • 热路径绝不用 shared_ptr：原子计数 + 控制块 cache 行在多核间乒乓（实测 4 线程争用把单次成本从 13 ns 抬到 49 ns），是每 tick 路径上的延迟尖峰发生器。模式：线程入口拷贝一次拿到对象（或干脆裸指针/引用），热循环内零计数操作，生命周期由外层 scope 保证。
  • 非热路径的合理用途：对象池条目、策略配置快照、跨线程异步任务句柄——低频路径上 shared_ptr 换来的安全收益远大于微秒级成本。
  • 行情网关的订阅关系：Subscriber 持有 shared_ptr<Session>、Session 持有 weak_ptr<Subscriber>，既保证回调时对象还活着，又不形成环——这是本节"子指父用 weak"规则的真实落点。
  • 大对象慎用 make_shared + 长命 weak_ptr：订单簿快照这类几十 KB 的对象，若缓存持 weak_ptr，强计数归零后内存仍滞留，容量敏感场景改用 shared_ptr<T>(new T)。

自测题

1. shared_ptr 多大？控制块里有什么？控制块什么时候创建？

答案

16 字节（实测）：一个指针指向对象，一个指向控制块。控制块含强/弱引用计数、类型擦除的删除器与分配器、对象指针（make_shared 时对象内嵌，实测合并块 40 = 16 对象 + 24 控制块；独立控制块实测 32 字节）。创建时机：make_shared / shared_ptr<T>(new T) / shared_ptr<T>(裸指针) 新建；从已有 shared_ptr、weak_ptr 拷贝不新建。

2. 实测 make_shared 和 new+shared_ptr 各分配几次？差别带来什么好处和什么副作用？

答案

make_shared 1 次（实测块 40 字节），new+shared_ptr 2 次（实测 16 + 32）。好处：少一次堆分配、局部性好、消灭裸指针外泄窗口。副作用：对象与控制块同生共死，只要还有 weak_ptr 活着，对象内存就不能归还——实测 ~Big 已执行但 88 字节仍挂着，直到 wp.reset() 才归零。

3. "shared_ptr 是线程安全的"这句话准确吗？请用实测说明。

答案

不准确。线程安全的只有引用计数的增减：实测 8 线程各 10 万次拷贝/析构副本，最终 use_count 精确为 1、对象只析构一次。但所指对象没有保护——实测两线程各 20 万次 ++(*sp) 得到 255164 而不是 400000；同一个 shared_ptr 实例被一线程 reset、另一线程拷贝也是竞争。准确说法：控制块线程安全，指针实例和所指对象不线程安全。

4. 循环引用为什么泄漏？Lsan 报什么？怎么破？

答案

A 持 shared_ptr<B>、B 持 shared_ptr<A>，互相把对方计数顶到 ≥1，谁都归不了零。实测离开作用域后没有任何 dtor 输出，Lsan 报 ERROR: LeakSanitizer: detected memory leaks + SUMMARY: AddressSanitizer: 80 byte(s) leaked in 2 allocation(s)。破法：一侧改成 weak_ptr（通常"子指父"），实测改完 use_count 从 2 降到 1，两个 dtor 正常打印。

5. enable_shared_from_this 解决什么问题？为什么 shared_ptr<T>(this) 不行？调用 shared_from_this() 的前提是什么？

答案

解决"对象成员函数里要交出指向自身的 shared_ptr"（注册回调、异步任务）。shared_ptr<T>(this) 会新建控制块：实测 use_count sp=1 sp2=1 互不知情，ASan 下报 attempting free on address which was not malloc()-ed（因为 make_shared 的对象在合并块中间）。enable_shared_from_this 在对象内埋 weak_ptr，shared_from_this() 从它 lock 出共享已有控制块的 shared_ptr。前提：对象已被某个 shared_ptr 管理，否则实测抛 std::bad_weak_ptr。

6. shared_ptr 拷贝的开销由哪几部分组成？为什么核越多越糟？

答案

三部分：①对计数的原子 RMW（实测 14 ns/次，裸指针 0.87 ns、unique_ptr 0.69 ns）；②多核下计数所在 cache 行在核间来回失效——实测 4 线程做 4 倍工作却花 14.9 倍时间（26.4 ms → 392.5 ms），单次成本从 ~13 ns 涨到 ~49 ns；③16 字节体积 + 两次解引用。开销随核数和拷贝频率放大，不是固定成本。

7. 和 intrusive 指针（引用计数放在对象里）相比，shared_ptr 贵在哪、赢在哪？

答案

贵在：旁挂控制块（实测 24–32 字节）额外分配、可能两次 cache miss、指针本身 16 字节。赢在：类型无侵入（不需要自带计数字段）、支持不完整类型、支持 weak_ptr、删除器类型擦除不进类型。intrusive 更快但要改造类型且不支持 weak_ptr。

Item 20：用 std::weak_ptr 指向可能悬垂的 shared_ptr

第 4 章 智能指针 · Item 20 · 上一节：Item 19 shared_ptr

为什么要学这个（先建立直觉）

C 程序员用裸指针"观察但不拥有"：

struct Widget* cached = NULL;
void use_cache() {
    if (cached) cached->do_work();  // 若 cached 已被 free → 悬垂指针 → UB
}

问题：C 的裸指针不知道目标是否还活着。cached 非空不代表指向的内存有效——用就是 UB，不用又没法检测。这类 bug 在长时运行系统里最致命：指针 99% 的时间指向有效内存，只有对象被释放后的那一下访问才崩。

C++ 的 weak_ptr 把"观察但不拥有"做成了可检测的语言设施：不增加强引用计数（不延长对象生命），但能通过 lock() 原子地回答"对象还活着吗"——活着就给你一个 shared_ptr 保证使用期间不死，死了就给你空指针，走降级路径而不是 UB。

另一个容易忽视的问题：shared_ptr 的引用计数解决不了环——两个对象互相持有对方的 shared_ptr，谁也放不掉谁，内存永久泄漏。weak_ptr 是标准的破环工具。

这节讲什么

weak_ptr 观察 shared_ptr 但不拥有：不增强引用计数、不能直接解引用，访问前必须 lock() 提升为 shared_ptr（原子地检查+获取）。三大用途：打破环引用、观察者模式、缓存。

循环引用：shared_ptr 的死穴

两个结构体互相持有对方的 shared_ptr，本机实测（clang 23.1.0, -std=c++17 -Wall）：

#include <memory>
#include <iostream>
struct B;
struct A {
    std::shared_ptr<B> b;
    ~A() { std::cout << "~A()\n"; }
};
struct B {
    std::shared_ptr<A> a;
    ~B() { std::cout << "~B()\n"; }
};

int main() {
    std::cout << "--- 进入作用域 ---\n";
    {
        auto pa = std::make_shared<A>();
        auto pb = std::make_shared<B>();
        pa->b = pb;
        pb->a = pa;
        std::cout << "pa.use_count() = " << pa.use_count() << "\n"
                  << "pb.use_count() = " << pb.use_count() << "\n";
    }
    std::cout << "--- 离开作用域（注意：没有任何析构打印）---\n";
}

实测输出（两个 ~ 析构打印都没出现）：

--- 进入作用域 ---
pa.use_count() = 2
pb.use_count() = 2
--- 离开作用域（注意：没有任何析构打印）---

计数推演：pa 销毁，A 的计数 2→1（还剩 pb->a）；pb 销毁，B 的计数 2→1（还剩 pa 尸体里的 b）。A 的释放依赖 B 先析构，B 的释放依赖 A 先析构——死锁式的计数环。

weak_ptr 破环

把环上的一条边改成 weak_ptr（通常选"子指父"或"回指"的那条边）：struct B { std::weak_ptr<A> a; ... };，本机实测输出：

--- 进入作用域 ---
pa.use_count() = 1        ← weak_ptr 不增强引用计数
pb.use_count() = 2
observer.expired() = 0
~A()                      ← pa 销毁时 A 立即析构
~B()                      ← A 析构 → b 成员销毁 → B 计数归零 → B 析构
--- 离开作用域 ---
observer.expired() = 1    ← 外部观察者正确看到"已失效"
lock() 返回空? 1

关键事实：weak_ptr 不增加强引用计数（pa.use_count() 保持 1），析构链因此能正常走完：pa 销毁 → A 计数归零 → A 析构 → 成员 b 销毁 → B 计数归零 → B 析构。

lock() 的原子性与 expired() 的局限

lock() 在一次原子操作里完成：检查强引用计数 > 0 → 递增 → 返回有效 shared_ptr；否则返回空。为什么必须原子？看反面教材：

if (!wp.expired()) {   // 检查
    // ← 另一线程在此刻 reset 了最后一个 shared_ptr，对象销毁
    auto p = wp.lock();  // 再获取——可能返回空！
    p->do_work();        // 空指针解引用
}

expired() 的返回值只能用于日志和统计——它回答的是"刚才那一刻死没死"，不是"下一秒还活着吗"。正确姿势永远是用 lock() 的返回值判断：if (auto p = wp.lock()) { p->do_work(); }——要么拿到活的，要么拿到空，没有中间态；且 p 持有强引用，使用期间对象保证不死。

三大经典场景

场景 谁持有 weak_ptr lock() 失败时怎么办
打破环引用 环上的"反向"边（子→父、prev） 不会出现（环内保证存活）
观察者模式 分发器持有观察者的 weak 跳过并顺手清理
缓存 缓存表持有值的 weak 重新加载，写回缓存

缓存场景的精妙之处：缓存不阻止对象被回收——没人用的数据自然释放，内存压力下缓存自动收缩；lock() 失败了再加载一次即可。这是裸指针缓存做不到的行为。

完整可运行例子

观察者 + 缓存 + expired 检测三合一，本机实测（clang 23.1.0, -std=c++17 -Wall）：

#include <memory>
#include <iostream>
#include <map>
#include <string>
#include <vector>

struct Observer {
    std::string name;
    explicit Observer(std::string n) : name(std::move(n)) {}
    void update(const std::string& m) { std::cout << "  [" << name << "] 收到: " << m << "\n"; }
    ~Observer() { std::cout << "  ~Observer(" << name << ")\n"; }
};

struct Subject {
    std::vector<std::weak_ptr<Observer>> observers;
    void subscribe(const std::shared_ptr<Observer>& o) { observers.push_back(o); }
    void notify(const std::string& msg) {
        for (auto it = observers.begin(); it != observers.end();) {
            if (auto sp = it->lock()) { sp->update(msg); ++it; }
            else { std::cout << "  (跳过已销毁的观察者)\n";
                   it = observers.erase(it); }       // 顺手清理
        }
    }
};

struct Quote { double bid, ask; };
std::map<std::string, std::weak_ptr<Quote>> cache;

std::shared_ptr<Quote> getQuote(const std::string& sym) {
    if (auto sp = cache[sym].lock()) { std::cout << "  缓存命中: " << sym << "\n"; return sp; }
    std::cout << "  缓存未命中，重新加载: " << sym << "\n";
    auto sp = std::make_shared<Quote>(Quote{100.25, 100.30});
    cache[sym] = sp;
    return sp;
}

int main() {
    std::cout << "== 观察者 ==\n";
    Subject subj;
    {
        auto o1 = std::make_shared<Observer>("策略A");
        auto o2 = std::make_shared<Observer>("策略B");
        subj.subscribe(o1);
        subj.subscribe(o2);
        subj.notify("行情快照#1");
    }   // o1、o2 在此销毁
    subj.notify("行情快照#2");

    std::cout << "== 缓存 ==\n";
    {
        auto q1 = getQuote("AAPL");
        auto q2 = getQuote("AAPL");
        std::cout << "  q1.use_count() = " << q1.use_count() << " (weak_ptr 不计入)\n";
    }
    auto q3 = getQuote("AAPL");   // 缓存里只剩悬垂 weak → 重新加载

    std::cout << "== expired 检测 ==\n";
    std::weak_ptr<Quote> wq = q3;
    std::cout << "  存活时 expired = " << wq.expired() << "\n";
    q3.reset();
    std::cout << "  释放后 expired = " << wq.expired() << "\n";
}

常见错误（新手踩坑）

  1. 环引用导致内存泄漏。A↔B 互相 shared_ptr，计数永不归零（本节开头实测）。修正：环上"回指"的边改 weak_ptr。工程惯例：所有权方向（父→子、next）用 shared_ptr，观察方向（子→父、prev）用 weak_ptr。
  2. 直接用 weak_ptr 访问对象。wp->doSomething(); 编译失败——weak_ptr 故意不提供 */->，逼你先 lock()。这个"不便"是设计，不是缺陷。
  3. lock() 后不检查返回值。auto p = wp.lock(); p->doSomething(); 当 wp 已悬垂时是空指针解引用。修正：if (auto p = wp.lock()) { ... }。
  4. 用 expired() 做"检查后使用"。多线程下检查和使用之间有窗口期（TOCTOU）。永远用 lock() 的原子语义。

HFT 关联

  • 策略热卸载：行情分发器持有策略回调的 weak_ptr。策略模块热更新/卸载后，分发器 lock() 返回空自动跳过——避免向已 dlclose 掉的代码段回调，这是裸指针回调表最难处理的场景。
  • 行情快照缓存：map<string, weak_ptr<Quote>> 做快照缓存，不活跃合约的快照自动回收，命中时零拷贝共享。
  • 控制块开销：每个 weak_ptr 会延长控制块寿命（对象死后控制块存活到最后一个 weak 销毁）。大对象 + 长期 weak 的内存滞留问题见 Item 21。
  • 热路径别滥用：shared_ptr/weak_ptr 的计数是原子操作，每次拷贝都是一次 atomic increment。能用 unique_ptr 就别上 shared_ptr，能保证存活期的观察就用裸指针/引用——weak_ptr 的价值恰恰是"无法保证存活期"的场景。

自测题

1. weak_ptr 为什么不能直接解引用？lock() 的原子性解决了什么问题？

答案

weak_ptr 不拥有对象，故意不提供 */->，逼你显式处理"对象可能已死"的分支。lock() 在一次原子操作里完成"检查计数 > 0 → 递增 → 返回 shared_ptr"，消除 TOCTOU 竞争：拆成 expired() 检查 + 获取两步，中间另一线程可能释放对象。返回的 shared_ptr 还保证使用期间对象不死。

2. 循环引用为什么泄漏？一句话说明计数为什么回不到零。

答案

A 的释放依赖 B 先析构（B 持有 shared_ptr<A>），B 的释放依赖 A 先析构（A 持有 shared_ptr<B>）——互相等待，谁也走不到第一步。实测离开作用域后无任何析构打印，LeakSanitizer 报 80 字节泄漏。

3. weak_ptr 会影响 use_count() 吗？破环后析构顺序如何？

答案

不影响——实测 pb->a = pa（weak）后 pa.use_count() 仍为 1。破环后链式析构：pa 销毁 → A 计数归零 → A 析构 → 成员 b 销毁 → B 计数归零 → B 析构。

4. lock() 返回空意味着什么？正确处理方式是什么？

答案

意味着对象已析构（weak_ptr expired）。正确处理是走降级路径：重新加载（缓存）、跳过并清理（观察者）——绝不能解引用返回的空 shared_ptr。

5. 为什么不能用 expired() 做"检查后使用"？

答案

expired() 与随后的访问之间有窗口期：返回 false 只代表"检查那一刻活着"，另一线程下一纳秒可能就释放了最后一个 shared_ptr。典型 TOCTOU 竞争，lock() 的原子语义才安全。

6. 观察者模式里 notify() 时 lock() 失败除了跳过还应做什么？

答案

顺手把悬垂的 weak_ptr 从列表 erase 掉。否则列表随时间积累大量死 weak（每个都还占着控制块），遍历成本越来越高。

7. 下面代码输出什么？为什么？

auto sp = std::make_shared<int>(42);
std::weak_ptr<int> wp = sp;
std::cout << sp.use_count() << "\n";
sp.reset();
std::cout << wp.expired() << "\n";
答案

输出 1 和 1（true）。weak_ptr 不增强引用计数，use_count() 保持 1；sp.reset() 后唯一强引用消失，对象析构，wp 变 expired。

Item 21：优先 make_unique / make_shared 而非 new

第 4 章 智能指针 · Item 21 · 上一节：Item 20 weak_ptr

为什么要学这个（先建立直觉）

C 程序员分配内存一步到位：

struct Widget* p = malloc(sizeof(struct Widget));
widget_init(p, args);
free(p);

C++ 的 shared_ptr 比 C 多了一样东西：控制块（强/弱引用计数、删除器等元数据）。直接用 new 包装时，对象和控制块是两次堆分配：

std::shared_ptr<Widget> sp(new Widget(args));  // new Widget 一次 + 控制块一次 = 2 次
auto sp2 = std::make_shared<Widget>(args);     // 对象+控制块合并 = 1 次

少一次分配意味着：少一次 malloc 锁竞争、对象和控制块在同一 cache 行、代码还更短。这几乎是白捡的收益——但 make 有三个不适用场景（自定义删除器、大对象+长期 weak_ptr、大括号初始化），不知道边界就会从"白捡"变成"白送bug"。

这节讲什么

优先用 make_unique（C++14）/ make_shared（C++11）而非直接 new：单次分配、异常安全、代码简洁。三个例外：需要自定义删除器、大对象且有长期 weak_ptr、需要大括号初始化。

优势一：单次堆分配（实测）

用全局 operator new/delete 计数器观察分配行为，本机实测（clang 23.1.0, -std=c++17 -Wall）。Big 是 4KB 的大对象：

// make_shared：一次分配，对象+控制块同一块内存
auto sp = std::make_shared<Big>();
// new + shared_ptr：两次分配，对象和控制块分开
std::shared_ptr<Big> sp2(new Big);

本机实测（用全局 operator new/delete 打日志，完整代码与输出见文末）：make_shared 一侧只有一行 new 4120 字节（4096 对象 + 24 控制块合并）；new 一侧是两行 new 4096 字节 + new 32 字节。malloc 次数减半，且对象与控制块相邻，增减引用计数时不会额外 cache miss。

优势二：异常安全（C++17 前的求值顺序坑）

Meyers 书里的经典例子：

void processWidget(std::shared_ptr<Widget> spw, int priority);
int computePriority();   // 可能抛异常

processWidget(std::shared_ptr<Widget>(new Widget), computePriority());

C++17 之前，编译器可以按这个顺序执行：① new Widget（裸指针产生，没人接管）→ ② computePriority()（抛异常）→ ③ shared_ptr 构造（永不执行）——new 出来的 Widget 永久泄漏。模拟这个顺序实测（-fsanitize=address -g，ASAN_OPTIONS=detect_leaks=1）：

__attribute__((noinline)) void dangerousOrder() {
    Widget* raw = new Widget;                  // ①
    int prio = computePriority();              // ② 抛异常
    processWidget(std::shared_ptr<Widget>(raw), prio);  // ③ 永不执行
}

实测输出：

Widget()
computePriority() 抛异常
caught: boom
main 结束（注意没有 ~Widget()）
=================================================================
==86433==ERROR: LeakSanitizer: detected memory leaks
Direct leak of 1 byte(s) in 1 object(s) allocated from:
    #1 in dangerousOrder() emcC_item21_order.cpp:22
SUMMARY: AddressSanitizer: 1 byte(s) leaked in 1 allocation(s).

注意 C++17 已修掉这个坑：标准规定函数实参的求值以整个实参为单位、不允许交错——shared_ptr<Widget>(new Widget) 这个实参要么完整构造好，要么还没开始。本机实测（clang 23.1.0, -std=c++17）原始写法也不泄漏：

Widget()
computePriority()
~Widget()          ← shared_ptr 实参已完整构造，栈展开时正常析构
caught: boom

但 Meyers 的建议依然成立：用 make_shared 就根本不用关心求值顺序规则，而且在 C++11/14 模式下编译老代码时这个坑仍然活着。这是"不要依赖你知道编译器怎么做"的典型案例。

局限一：不能指定自定义删除器

make_* 系列没有把删除器传进去的入口：

// 自定义删除器必须用 new + 构造函数
std::shared_ptr<FILE> fp(fopen("data.bin", "rb"), &fclose);
// make_shared 做不到这件事——没有接受删除器的重载

需要自定义分配器时同理，用 std::allocate_shared。

局限二：大对象 + 长期 weak_ptr → 内存滞留

这是单次分配的反面：make_shared 把对象和控制块放进同一块内存，而 weak_ptr 依赖控制块存活——只要还有一个 weak_ptr 活着，整块内存（包括早已析构的大对象占的部分）都不能归还。本机实测：

struct Big { char data[4096]; };
std::weak_ptr<Big> wp;
{
    auto sp = std::make_shared<Big>();   // vs shared_ptr<Big>(new Big)
    wp = sp;
}   // sp 死：Big 析构了，但内存归还了吗？
// wp 还活着 → 观察 live bytes

实测（完整输出见文末"完整可运行例子"）：make_shared 版本 sp 死后 live = 4120——对象已析构，4120 字节整块滞留，直到 wp 也析构才 delete 4120；new 版本 sp 一死立即 delete 4096 字节，只剩 32 字节控制块陪 wp 到最后。

对象 4KB、滞留时间 = 最后一个 weak_ptr 的寿命。换成 40MB 的帧缓冲 + 一个长期存活的监控 weak_ptr，滞留的就是 40MB。这种场景用 shared_ptr<Big>(new Big)。

局限三：完美转发传不了大括号

make_* 的实参是函数参数包，大括号初始化列表不是有类型的表达式，推不了导（和 Item 2 的模板推导失败同源）。本机实测报错原文：

圆括号则一切正常（实测输出 10）：

auto v = std::make_unique<std::vector<int>>(10, 0);  // 10 个 0
// 想要大括号语义，绕道：
auto il = {1, 2, 3};
auto v2 = std::make_unique<std::vector<int>>(il);    // OK：il 有类型
// 或直接 new
std::shared_ptr<std::vector<int>> v3(new std::vector<int>{1, 2, 3});

另外注意版本差异：make_unique 是 C++14 才有的（C++11 只有 make_shared），本机实测 -std=c++11 下报 error: no member named 'make_unique' in namespace 'std'。

内存滞留对比的完整实测代码（clang 23.1.0, -std=c++17 -Wall）：

#include <memory>
#include <iostream>
#include <new>

static long g_liveBytes = 0;
void* operator new(std::size_t n) {
    g_liveBytes += n;
    std::cout << "  new " << n << " 字节\n";
    return std::malloc(n);
}
void operator delete(void* p, std::size_t n) noexcept {
    g_liveBytes -= n; std::cout << "  delete " << n << " 字节\n"; std::free(p);
}

struct Big { char data[4096]; };   // 4KB 大对象

int main() {
    std::cout << "== make_shared：对象和控制块同一块 ==\n";
    {
        std::weak_ptr<Big> wp;
        {
            auto sp = std::make_shared<Big>();
            wp = sp;
            std::cout << "  live = " << g_liveBytes << "\n";
        }
        std::cout << "  sp 死后(wp 还活着) live = " << g_liveBytes << "\n";
    }
    std::cout << "  wp 也死后 live = " << g_liveBytes << "\n";

    std::cout << "== new + shared_ptr：对象和控制块分开 ==\n";
    {
        std::weak_ptr<Big> wp;
        {
            std::shared_ptr<Big> sp(new Big);
            wp = sp;
            std::cout << "  live = " << g_liveBytes << "\n";
        }
        std::cout << "  sp 死后(wp 还活着) live = " << g_liveBytes << "\n";
    }
    std::cout << "  wp 也死后 live = " << g_liveBytes << "\n";
}

  wp 也死后 live = 0

常见错误（新手踩坑）

  1. make_shared 里再套 new。make_shared<Widget>(new Widget) 把 Widget* 当构造实参转发——要么编译失败，要么 new 出来的对象没人接管直接泄漏。make_* 收的是构造参数，不是指针。
  2. 大对象 + 长期 weak_ptr 还用 make_shared。对象析构后整块内存滞留到最后一个 weak 死亡（本节实测）。修正：shared_ptr<Big>(new Big) 分离分配。
  3. 以为 make 总是异常安全的最优解而忽略版本。make_unique 是 C++14 才有；C++11 工程要么自己写一个简单的（书里有 5 行实现），要么用 unique_ptr<T>(new T) 并接受其异常安全分析。
  4. 想给 make_shared 传大括号。{1,2,3} 推不出类型（实测报错见上）。先把列表绑到 auto il = {...} 再传，或用 new。

HFT 关联

  • malloc 次数减半 + cache 局部性：每次堆分配都可能撞内存池锁；make_shared 少一次分配，且控制块与对象同块——增减 use_count() 后紧接着访问对象数据，大概率同一 cache 行。
  • 内存滞留即容量风险：4KB 实测放大到百万级订单对象，长期 weak 监控会让内存水位居高不下。HFT 里监控/审计引用如果必须长期存在，考虑分离分配或对监控侧改用裸指针+存活期协议。
  • 异常安全不依赖编译器版本：热路径上的 f(shared_ptr<T>(new T), g()) 写法在 C++11/14 编译模式下仍是泄漏隐患，make_shared 一劳永逸。

自测题

1. make_shared 比 shared_ptr<T>(new T) 省在哪？实测分配次数各是多少？

答案

省在一次堆分配：new 版本 2 次（对象 4096B + 控制块 32B），make_shared 1 次（合并 4120B）。附带收益：对象与控制块同 cache 行、代码更短、异常安全。

2. processWidget(shared_ptr<Widget>(new Widget), computePriority()) 在 C++17 前为什么可能泄漏？C++17 改了什么？

答案

C++17 前实参求值可交错：new Widget → computePriority() 抛异常 → shared_ptr 构造未执行，裸指针泄漏（实测 ASan 报 Direct leak）。C++17 规定实参求值不可交错，泄漏路径封死；但 C++11/14 模式下坑仍在，make_shared 与版本无关地安全。

3. 为什么 make_shared 不能用于需要自定义删除器的场景？

答案

make_* 的接口只有"类型 + 构造参数"，没有传入删除器的重载。删除器只能走 shared_ptr<T>(p, deleter) 构造函数，例如 std::shared_ptr<FILE> fp(fopen(...), &fclose);。

4. 大对象 + 长期 weak_ptr 为什么不宜用 make_shared？实测数据是什么？

答案

make_shared 把对象与控制块合并分配，而 weak_ptr 依赖控制块存活——只要还有 weak 活着，整块内存不能归还。实测：4KB 对象，make_shared 版本 sp 死后仍滞留 4120B；new 版本 sp 死后立即归还 4096B，只留 32B 控制块。

5. std::make_unique<std::vector<int>>({1,2,3}) 为什么编译失败？怎么绕？

答案

{1,2,3} 是 braced-init-list，不是有类型的表达式，模板的参数包 _Args 无法从中推导（实测报 deduced incomplete pack <(no value)>）。绕法：auto il = {1,2,3}; make_unique<vector<int>>(il)，或用圆括号 (10, 0)，或直接 new。

6. make_unique 是哪个标准版本引入的？C++11 下怎么办？

答案

C++14。C++11 只有 make_shared（实测 -std=c++11 报 no member named 'make_unique'）。C++11 下可手写 5 行的 make_unique（return std::unique_ptr<T>(new T(std::forward<Args>(args)...));），或直接用 unique_ptr<T>(new T(...))。

7. 下面代码有什么问题？

auto sp = std::make_shared<Widget>(new Widget(42));
答案

make_shared 把实参转发给 Widget 的构造函数，这里传的是 Widget*——若无 Widget(Widget*) 构造则编译失败；若恰有则能编译但 new 出来的对象没人接管，永久泄漏。正确写法：std::make_shared<Widget>(42)，传构造参数而不是指针。

Item 22：用 Pimpl 惯用法降低编译依赖

第 4 章 智能指针 · Item 22 · 上一节：Item 21 make 函数 · 下一章：第 5 章 右值引用、移动语义与完美转发

为什么要学这个（先建立直觉）

C++ 的编译模型有个结构性痛点：头文件里类的私有成员也是类定义的一部分——你改一行私有实现（加个 vector 成员、换个第三方库），所有包含这个头文件的翻译单元全部重编译。大项目里改一个核心头文件触发几百个 TU 重编，"喝杯咖啡等编译"就是这么来的。

Pimpl（Pointer to Implementation）的思路釜底抽薪：头文件里只留一个指向实现结构的指针，实现整体挪进 .cpp。私有成员随便改，只有那一个 .cpp 重编译。代价是多一次间接和多一次堆分配——所以它是接口类的工具，不是热路径数据结构的工具。

这节讲什么

  1. 三文件完整可编译结构（widget.h / widget.cpp / main.cpp）；
  2. 编译防火墙收益的实测数字：预处理行数、编译耗时、改实现后用户 TU 是否重编；
  3. 核心规则：析构（和移动）为什么必须在 .cpp 定义，含报错原文；
  4. unique_ptr vs shared_ptr 做 Pimpl 的区别、运行期成本实测（一次堆分配 + 一次间接寻址）、什么时候不该用 Pimpl。

核心结构（三文件，实测可编译）

// ============ widget.h ============
#pragma once
#include <memory>

class Widget {
    struct Impl;                    // 只有前向声明：调用方看不见实现
    std::unique_ptr<Impl> pImpl;    // 不完整类型可以做 unique_ptr 成员
public:
    Widget();
    ~Widget();                              // ★ 只声明，定义必须在 .cpp
    Widget(Widget&&) noexcept;              // ★ 移动也要去 .cpp 定义
    Widget& operator=(Widget&&) noexcept;
    Widget(const Widget&) = delete;         // 拷贝默认禁用（拷贝需要 Impl 完整）
    Widget& operator=(const Widget&) = delete;
    int size() const;
    void add(int v);
    int sum() const;
};

// ============ widget.cpp ============
#include "widget.h"
#include <vector>

struct Widget::Impl {               // 实现细节全在这里
    std::vector<int> data;
};

Widget::Widget()  : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default;        // Impl 在此处已完整，default 安全
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;
int  Widget::size() const { return static_cast<int>(pImpl->data.size()); }
void Widget::add(int v)   { pImpl->data.push_back(v); }
int  Widget::sum()  const { int s = 0; for (int v : pImpl->data) s += v; return s; }

// ============ main.cpp ============
#include "widget.h"
#include <iostream>
#include <utility>
int main() {
    Widget w;
    w.add(1); w.add(2); w.add(3);
    std::cout << "sizeof(Widget) = " << sizeof(Widget) << "\n";
    std::cout << "w.size() = " << w.size() << "  w.sum() = " << w.sum() << "\n";
    Widget w2 = std::move(w);       // 移动 OK（定义在 .cpp）
    std::cout << "after move: w2.size() = " << w2.size() << " w2.sum() = " << w2.sum() << "\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）编译运行输出：

sizeof(Widget) = 8
w.size() = 3  w.sum() = 6
after move: w2.size() = 3 w2.sum() = 6

调用方视角的关键数字：sizeof(Widget) = 8。不管 Impl 里塞多少成员（vector、map、第三方库对象），Widget 永远是一个指针的大小——这正是 ABI 稳定的来源。

编译防火墙：收益实测

同一个"用户 TU"在两个 header 版本下的对比（非 Pimpl 版头文件带 <vector> <map> <string> <deque>，Pimpl 版只带 <memory>）实测：预处理后行数 35798 → 13531（2.6x），-fsyntax-only 耗时 0.270 s → 0.120 s（2.25x），改实现后用户 .o 不需要重编。

最后一条才是 Pimpl 的真正价值。实测：给 Widget::Impl 加两个成员（std::map + std::string）、widget.cpp 加两个 #include，重编 widget.o 后直接复用原来的 main.o 链接，程序照常输出 sizeof(Widget) = 8 / w.size() = 3；而用户 main.o 的 md5 前后都是 e73c115f2e5f0acb749783a55f13acf3——字节级不变，它根本不需要重编译。项目里一个核心头被 300 个 TU 包含时，这个"0"就是分钟级和秒级的差别。

核心规则：析构（和移动）必须在 .cpp 定义

把头文件里的 ~Widget(); 声明删掉（或写成 ~Widget() = default;），clang 报错原文：

error: invalid application of 'sizeof' to an incomplete type 'Widget::Impl'
    static_assert(sizeof(_Tp) >= 0, "cannot delete an incomplete type");
note: in instantiation of member function 'std::unique_ptr<Widget::Impl>::~unique_ptr' requested here
    ~Widget() = default;      // ← 错误示范：在头文件里 default
note: forward declaration of 'Widget::Impl'

机制：unique_ptr<Impl> 的默认删除器要 delete Impl，而 delete 需要 sizeof(Impl) 和 Impl 的析构——都要求完整类型。如果 ~Widget 在头文件隐式生成，那么每个包含该头文件、且销毁 Widget 的 TU 都会在"Impl 不完整"的上下文里实例化这个析构，全军覆没。

移动构造和移动赋值也一样。实测把它们 = default 写在类内、用户 TU 里 Impl 不完整：

error: invalid application of 'sizeof' to an incomplete type 'W1::Impl'
note: in instantiation of member function 'std::unique_ptr<W1::Impl>::~unique_ptr' requested here
    W1(W1&&) = default;
error: invalid application of 'sizeof' to an incomplete type 'W2::Impl'
note: in instantiation of member function 'std::unique_ptr<W2::Impl>::operator=' requested here
    W2& operator=(W2&&) = default;

移动赋值要先删除旧值（触发删除器），移动构造在 libc++ 里也会实例化析构。口诀：凡是会实例化删除器或创建 Impl 的函数，都得待在 Impl 完整的 TU。

成员函数 头文件 .cpp
析构 ~Widget() 只声明 = default（Impl 完整，安全）
移动构造/移动赋值 只声明 = default
构造函数 只声明 定义（要 make_unique<Impl>）
拷贝构造/拷贝赋值 通常 = delete 要支持得手写深拷贝（Impl 逐成员复制）

注意 .cpp 里 ~Widget() = default; 是对的——"在类外 = default"让编译器在这个 TU（Impl 已完整）里生成析构体，头文件里 = default 才是错的。另外：如果同一个 TU 里 Impl 恰好已定义（单文件 demo），类内 = default 能编过——但那等于没做 Pimpl，别拿单文件 demo 通过来证明规则不存在。

运行期成本：一次分配 + 一次间接

实测（-O2，Direct 的成员在对象里，Pimpl 的成员在堆上；方法定义在另一个 TU 保证是真实跨 TU 调用）：

sizeof(Direct) = 16   sizeof(Pimpl) = 8
构造+fill+析构 1000000 次:  Direct 12.9164 ms   Pimpl 110.309 ms   比值 8.54025x
sum() 20000000 次:  Direct 75.1448 ms  Pimpl 75.0923 ms   比值 0.999301x
  每次: Direct 3.75724 ns   Pimpl 3.75462 ns

两个结论，都值得记住：

  1. 构造代价真实且很大：8.5 倍，原因是每构造一个对象多一次 make_unique<Impl> 的堆分配。这就是"Pimpl 不适合热路径数据结构"的量化理由——订单、tick 每秒百万次构造，8.5 倍就是 8.5 倍。
  2. 访问代价在 L1 命中时几乎测不出来：20M 次 sum() 比值 0.999，多出来的那次 pImpl-> 被乱序执行和 L1 命中完全隐藏。真正的风险不在稳态带宽，而在冷 cache 时多一次可能的 cache miss 和跨 TU 无法内联。

所以成本结构是：主要在构造（堆分配），不在访问（间接）。 判断标准也就清楚了——对象构造得少、活得久，Pimpl 白赚；对象构造得频繁，Pimpl 血亏。

unique_ptr vs shared_ptr 版本

// shared_ptr 版：连析构声明都可以省
class WidgetS {
    struct Impl;
    std::shared_ptr<Impl> pImpl;
public:
    WidgetS();            // 只有构造函数需要在 .cpp
    int size() const;
    void add(int v);
};

实测输出 sizeof(WidgetS) = 16、size = 2、moved size = 2——隐式生成的析构、移动全部能编译，不需要任何 out-of-line 声明。原因是 shared_ptr 的删除器在构造时就类型擦除绑定进控制块了，析构时走的是擦除后的函数指针，不要求 Impl 完整。

三条对比：sizeof(Widget) 8 vs 16；析构/移动必须 out-of-line vs 不需要；拷贝语义——unique_ptr 版默认不可拷贝（这是对的），shared_ptr 版默认可拷贝但是浅拷贝。

最后一条是 shared_ptr 版最隐蔽的坑：它"意外地"让 Pimpl 类变得可拷贝，而那个拷贝是共享 Impl 的假拷贝——两个 Widget 改一个影响另一个，几乎总是 bug。Pimpl 语境下所有权明明独占，unique_ptr 才是对价的工具——shared_ptr 版"能跑但买贵了"，还附赠一个语义陷阱。

什么时候不该用 Pimpl

1. 模板类。 模板成员必须在使用点实例化，Impl 的定义藏不进 .cpp。实测：把 Holder<T>::Impl 和成员定义都放 .cpp 而不加显式实例化，链接报 Undefined symbols for architecture arm64 / linker command failed with exit code 1；加了 template class Holder<int>; 之后才通过（输出 h.get() = 42 sizeof=8）。也就是说每支持一个类型都要手写一行，编译防火墙的收益基本被抵消。

2. 性能热路径的数据结构。 实测构造成本 8.5 倍，加上跨 TU 不能内联。订单、行情 tick、定长环形缓冲这类每秒百万次构造的对象绝不 Pimpl——多一次堆分配就是多一次分配器锁。

3. 小类 / 值语义类。 只有两三个 int 成员的 struct，Pimpl 之后每对象多一次分配、代码量翻倍、还失去拷贝语义，纯亏。

适合的是：对外接口类——引擎、连接、会话、SDK 对象，特征是构造少、活得久、接口稳定、实现会变。

完整可运行例子

给上面的 Widget 补上深拷贝语义（单文件版便于验证；项目里同样要把这些定义放进 widget.cpp）：

class Widget {
    struct Impl;
    std::unique_ptr<Impl> pImpl;
public:
    Widget();
    ~Widget();
    Widget(const Widget& o);                 // 深拷贝：定义在 Impl 完整处
    Widget& operator=(const Widget& o);
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;
    void add(int v);
    int  sum() const;
};

struct Widget::Impl { std::vector<int> data; };

Widget::Widget() : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default;
Widget::Widget(const Widget& o) : pImpl(std::make_unique<Impl>(*o.pImpl)) {}  // 逐成员复制
Widget& Widget::operator=(const Widget& o) { *pImpl = *o.pImpl; return *this; }
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;
void Widget::add(int v) { pImpl->data.push_back(v); }
int  Widget::sum() const { int s = 0; for (int v : pImpl->data) s += v; return s; }

int main() {
    Widget a; a.add(1); a.add(2);
    Widget b = a;          // 深拷贝
    b.add(100);
    std::cout << "a.sum()=" << a.sum() << "  b.sum()=" << b.sum() << "\n";
    Widget c; c = b;       // 拷贝赋值
    std::cout << "c.sum()=" << c.sum() << "\n";
}

编译运行（本机实测 clang 23.1.0，-std=c++17 -Wall）：

a.sum()=3  b.sum()=103
c.sum()=103

b.add(100) 之后 a.sum() 仍是 3 —— 两个 Widget 各有一份 Impl，这才是正确的拷贝语义（对比 shared_ptr 版的假拷贝）。

常见错误（新手踩坑）

  1. 头文件里 ~Widget() = default;。最常见的 Pimpl 错误——default 在类内 = 在 Impl 不完整处生成析构体 = 每个使用者 TU 都编不过，报 invalid application of 'sizeof' to an incomplete type。记住口诀：声明在头，default 在 .cpp。
  2. 移动成员忘了也去 .cpp。只把析构挪走、移动构造留在类内隐式生成——实测移动构造和移动赋值都会触发删除器实例化，同样炸。
  3. 想要拷贝又忘了深拷贝。Pimpl 类默认不可拷贝，要拷贝语义需在 .cpp 手写 Widget::Widget(const Widget& o) : pImpl(std::make_unique<Impl>(*o.pImpl)) {}（实测深拷贝版 b.add(100) 后 a.sum() 仍是 3）。
  4. 用 shared_ptr 做 Pimpl 还以为拷贝是对的。它让类意外可拷贝，且拷出来是共享 Impl 的浅拷贝。
  5. 在热路径类上用 Pimpl。实测构造成本 8.5 倍，tick 数据结构用 Pimpl 是把编译时间省下来、把延迟花出去。

HFT 关联

  • 交易引擎的编译时间：核心引擎头文件被几百个策略 TU 包含，改一行私有实现全量重编分钟级。引擎主类 Pimpl 化后，策略侧只依赖稳定接口头，增量编译秒级——实测单个 TU 的预处理量从 35798 行降到 13531 行。
  • 商业库交付：给外部团队的 SDK（行情接入、风控前置）用 Pimpl 保持 ABI 稳定——你升级实现，对方不重编，实测改完 widget.cpp 后用户 .o 的 md5 字节级不变。8 字节的固定对象布局是合同的一部分。
  • 热路径反例：订单、行情 tick 这类每秒百万级构造/访问的对象绝不 Pimpl——实测构造成本 8.5 倍，多一次堆分配就是多一次分配器锁。Pimpl 是给"少而重"的接口类的。
  • 网关/会话层正例：Session、MarketDataFeed、RiskGateway 这类"进程启动时建几个、跑一整天"的对象，Pimpl 的收益远大于那一次构造期的堆分配。

自测题

1. Pimpl 里为什么析构必须在 .cpp 定义？头文件里 = default 会报什么错？

答案

unique_ptr<Impl> 的默认删除器要 delete Impl，需要 sizeof(Impl) 和 Impl 的析构——都要求完整类型。析构若在头文件（类内）隐式生成，每个包含头文件并销毁 Widget 的 TU 都在 Impl 不完整的上下文实例化它。实测报 error: invalid application of 'sizeof' to an incomplete type 'Widget::Impl'（libc++ 里是 static_assert(sizeof(_Tp) >= 0, "cannot delete an incomplete type")）。

2. 除了析构，还有哪些特殊成员函数必须挪到 .cpp？为什么？

答案

移动构造和移动赋值（实测两者都会触发删除器实例化，报同样的 sizeof to an incomplete type）；构造函数也要在 .cpp（make_unique<Impl> 需要完整类型，报 allocation of incomplete type）；若要拷贝语义，拷贝构造/赋值也要在 .cpp 手写深拷贝。规律：凡是会实例化删除器或创建 Impl 的函数，都得待在 Impl 完整的 TU。

3. 编译防火墙的收益能用哪些数字量化？实测值是多少？

答案

①预处理后行数：非 Pimpl 35798 行 vs Pimpl 13531 行（2.6x）；②-fsyntax-only 编译耗时 0.270 s vs 0.120 s（2.25x）；③最硬的指标——改完 widget.cpp 里的 Impl（加 <map>、<string> 依赖）重编 widget.o，用户 main.o 的 md5 字节级不变，可以直接复用重链接。第三条说明用户 TU 根本不需要重编译。

4. Pimpl 的运行期成本实测是多少？主要体现在哪？

答案

实测 -O2：构造+fill+析构 100 万次，Direct 12.9 ms vs Pimpl 110.3 ms（8.5 倍）；sum() 2000 万次，Direct 3.757 ns/次 vs Pimpl 3.755 ns/次（比值 0.999，几乎无差）。结论：成本主要在构造时的一次堆分配，而不在访问时的一次间接寻址——后者在 L1 命中时被乱序执行完全隐藏。所以判断标准是"构造频率"而非"访问频率"。

5. 用 shared_ptr<Impl> 做 Pimpl 为什么能省掉析构声明？为什么不推荐？

答案

shared_ptr 的删除器在构造时类型擦除绑定到控制块，析构时走擦除后的函数指针，不要求 Impl 完整——实测 WidgetS 只有构造函数声明在 .cpp，隐式生成的析构/移动全部能编译。不推荐的原因有二：①Pimpl 场景所有权明明独占，shared_ptr 白付原子引用计数的税，sizeof 从 8 变 16（实测）；②它让类意外变得可拷贝，而那个拷贝是共享同一个 Impl 的浅拷贝，改一个影响另一个，几乎总是 bug。

6. 模板类用 Pimpl 会遇到什么？实测报什么错？

答案

模板成员必须在使用点实例化，Impl 定义藏不进 .cpp。若把 Holder<T>::Impl 和成员函数都放在 .cpp 而不加显式实例化，实测链接报 Undefined symbols for architecture arm64 / linker command failed with exit code 1；加上 template class Holder<int>; 之后链接通过（实测输出 h.get() = 42 sizeof=8）。也就是说每支持一个类型都要手写一行显式实例化，编译防火墙的收益基本被抵消。

7. Pimpl 和 C 的 opaque pointer 是什么关系？C++ 版升级了什么？

答案

Pimpl 就是 C opaque pointer 惯用法的 C++ 版：C 里头文件只给 typedef struct Widget Widget;，实现藏 .c。目的相同（隐藏实现、稳定 ABI）。C++ 版的升级：①unique_ptr 自动管理释放，异常路径不泄漏，不用祈祷调用方记得调 Widget_destroy；②类成员函数语法保留，接口仍是一个 class 而不是一包 Widget_xxx(Widget*) 自由函数。代价是 C 版没有的那一次堆分配（C 版同样是 malloc——所以这点上两者持平）。

答案与复习指引

double free / 崩溃。 每个 shared_ptr 创建自己的控制块，引用计数各为 1。两个都析构时各自 delete raw → double free。

正确做法： auto p1 = std::make_shared<Widget>(); auto p2 = p1;（拷贝共享同一控制块）。

或用 enable_shared_from_this： 对象继承 enable_shared_from_this<T>，在成员函数中调 shared_from_this() 返回正确的 shared_ptr。

std::unique_ptr<FILE, decltype(&fclose)> fp(fopen("data.txt", "r"), &fclose);
