Tweaks — Items 41–42

本章讲什么

最后两条 item 是对前述机制的精细微调：可拷贝参数的传参方式选择、emplace 系列替代 insert 系列。它们看似细枝末节，却在泛型库设计和高性能容器操作中带来真实收益。

各 Item 要点

Item 41：可拷贝参数考虑按值传递

对于"会被拷贝的可拷贝形参"，传统做法是传 const T& 再在函数内拷贝。但若函数总是要拷贝这个参数，且参数可能以左值或右值传入，按值传递能简化代码：

// 传统：两个重载
void add(const T& x) { v.push_back(x); }      // 左值：一次拷贝
void add(T&& x)      { v.push_back(std::move(x)); }  // 右值：一次移动

// 按值：一个函数搞定
void add(T x) { v.push_back(std::move(x)); }  // 左值：拷贝构造形参 + 移动；右值：移动构造 + 移动

代价：按值传递对左值多了一次移动（拷贝构造形参 + 移动进容器），传统 const& 重载只拷贝一次。所以只有当移动廉价（如 string、vector、智能指针）时才值得；移动昂贵的类型（array<T,N>、BigStruct）仍用重载。

适用条件：①函数总是拷贝形参；②移动廉价；③拷贝构造与移动构造代价相近。不满足任一条，用重载或万能引用 + forward。

Item 42：优先 emplace 而非 insert

emplace_back / emplace 在容器内直接构造元素，省去临时对象 + 移动/拷贝：

v.push_back(Widget(42));     // 构造临时 Widget → 移动进 v
v.emplace_back(42);          // 直接在 v 的内存里构造 Widget

emplace 的优势：无临时对象、无移动、可传任意构造参数（含 explicit 构造）。

emplace 的限制： 1. 依赖 value_type 可直接构造：若 value_type 与传入参数间需要隐式转换且转换路径不止一条，emplace 可能选错构造函数（与 push_back 的明确转换行为不同）。 2. 资源管理顺序：push_back 先构造临时对象再插入，若插入失败（如扩容抛异常）临时对象已析构，无泄漏；emplace 直接在容器内存构造，若后续扩容/拷贝抛异常，需依赖容器的强异常保证（vector 的 emplace_back 在 noexcept 移动时才强保证）。 3. 与 unique_ptr / 共享状态：emplace_back(new Widget) 若 vector 扩容抛异常，裸指针泄漏——应 emplace_back(make_unique<Widget>()) 或 push_back(make_unique<Widget>())。

经验法则：能用 emplace 就用，除非需要明确控制转换路径或异常安全特别敏感。push_back(make_unique<T>()) 这种"先构造智能指针再插入"的模式仍是最安全的。

HFT 关联

  • emplace_back 热路径收益：行情队列 vector<Tick> 批量入队用 emplace_back 省去临时 Tick 的构造 + 移动——当 Tick 含多个字段（含 string symbol）时，省下的拷贝在每秒百万 tick 的吞吐下是可观的微秒级收益。
  • 异常安全 vs 性能：HFT 容器若在 emplace 路径抛异常（扩容 bad_alloc），裸指针资源会泄漏。规则——emplace_back 传智能指针/值类型，不传裸 new 结果。
  • 按值传参与移动：策略对象的字段（string symbol、vector<Param>）移动廉价，配置注册函数用按值传参 + std::move 进成员，代码简洁且性能可接受。
Item 41

Item 41：可拷贝参数考虑按值传递

第 8 章 微调 · Item 41 · 上一节：Item 40 atomic vs volatile · 下一节：Item 42 emplace vs insert

为什么要学这个（先建立直觉）

假设你要写一个函数，把名字存进容器。C++98 时代的老规矩是传 const&，进容器时拷贝一次：

void addName(const std::string& name) { names.push_back(name); }   // 左值右值都拷贝

后来学了移动语义，你发现传右值时那次拷贝是冤枉的，于是加成两个重载——一个接左值、一个接右值，各用最省的构造方式。代码对了，但每个这样的函数都要写两遍。

这一节给出第三种写法：按值传参，进容器时 std::move。一个函数替代两个重载，左值来就"拷贝 + 移动"，右值来就"移动 + 移动"，每种情况只比最优方案多付一次廉价的移动。这是 C++11 之后社区里广泛流行的惯用法（std::string、容器、智能指针的参数经常这么写），但它的适用边界非常清晰——搞不清边界，省下的代码行会加倍在性能上还回去。

这节讲什么

按值传参 + std::move 进容器，用一个函数替代 const& + && 两个重载。代价模型：左值多付一次移动，右值多付一次移动。用带计数器的类实测四种组合的构造次数，给出三条适用前提（可移动、move 廉价、参数总会被拷一份），以及不适用场景（只读参数、多参数重载爆炸、基类切片）。

三种写法的代价模型

// 方案 A：两个重载（性能最优，代码两份）
void add(const Widget& w) { v.push_back(w); }           // 左值：1 次拷贝
void add(Widget&& w)      { v.push_back(std::move(w)); } // 右值：1 次移动

// 方案 B：按值 + move（一份代码）
void add(Widget w) { v.push_back(std::move(w)); }
// 左值：拷贝构造形参 + 移动进容器
// 右值：移动构造形参 + 移动进容器

// 方案 C：万能引用 + forward（最优性能，模板，Item 26 的重载坑）
template<class T> void add(T&& w) { v.push_back(std::forward<T>(w)); }

理论代价表（书中版本）：

实参 A 两个重载 B 按值传递 C 万能引用
左值 1 拷贝 1 拷贝 + 1 移动 1 拷贝
右值 1 移动 2 移动 1 移动

按值传递对每种实参都多付恰好一次移动——这就是"代码简洁"的价格。值不值，取决于移动的成本。

实测：构造计数器对账（本机实测 clang 23.1.0）

用带构造/拷贝/移动计数器的 W，两种方案分别喂左值、纯右值、具名右值：

#include <cstdio>
#include <vector>

struct Cnt { int ctor = 0, copy = 0, move = 0; };
Cnt g;

struct W {
    W() { ++g.ctor; }
    W(const W&) { ++g.copy; }
    W(W&&) noexcept { ++g.move; }
};

void reset(const char* label) {
    std::printf("%-34s ctor=%d copy=%d move=%d\n", label, g.ctor, g.copy, g.move);
    g = Cnt{};
}

struct BoxA {                                // 方案 A：两个重载
    std::vector<W> v;
    void add(const W& w) { v.push_back(w); }
    void add(W&& w)      { v.push_back(std::move(w)); }
};

struct BoxB {                                // 方案 B：按值 + move
    std::vector<W> v;
    void add(W w) { v.push_back(std::move(w)); }
};

int main() {
    { BoxA a; W w; g = Cnt{}; a.add(w);             reset("A(双重载) add(左值):"); }
    { BoxB b; W w; g = Cnt{}; b.add(w);             reset("B(按值)   add(左值):"); }
    { BoxA a; g = Cnt{}; a.add(W{});                reset("A(双重载) add(纯右值 W{}):"); }
    { BoxB b; g = Cnt{}; b.add(W{});                reset("B(按值)   add(纯右值 W{}):"); }
    { BoxA a; W w; g = Cnt{}; a.add(std::move(w));  reset("A(双重载) add(std::move(w)):"); }
    { BoxB b; W w; g = Cnt{}; b.add(std::move(w));  reset("B(按值)   add(std::move(w)):"); }
    return 0;
}

clang 23.1.0 + -std=c++17 -Wall 实测输出：

A(双重载) add(左值):              ctor=0 copy=1 move=0
B(按值)   add(左值):              ctor=0 copy=1 move=1
A(双重载) add(纯右值 W{}):        ctor=1 copy=0 move=1
B(按值)   add(纯右值 W{}):        ctor=1 copy=0 move=1
A(双重载) add(std::move(w)):      ctor=0 copy=0 move=1
B(按值)   add(std::move(w)):      ctor=0 copy=0 move=2

对账结果有两个值得注意的点：

  1. 左值完全符合理论：B 比 A 多一次移动（copy=1, move=1 vs copy=1, move=0）。
  2. 纯右值 W{} 两方案打平（都是 ctor=1, move=1）！因为 C++17 起强制拷贝消除，纯右值直接原地构造进按值形参，省了书中预测的一次移动。具名右值 std::move(w) 不能消除，B 才显出 2 次移动 vs A 的 1 次。

也就是说：在现代标准 + 现代编译器上，按值传参的"右值税"比书里写的还轻——只有传具名右值时才真的多付一次移动。

适用前提与反模式

按值传参划算，需要三条同时成立：

  1. 类型可移动且移动廉价：std::string、std::vector、智能指针这类指针交接 O(1)；std::array<T, N> 的移动是逐元素拷贝 O(N)，多付的那次"移动"等于又一次拷贝，不划算。
  2. 参数总会被拷一份存起来：add 把参数放进容器/成员，拷贝必然发生。如果函数只是读参数（double norm(const Vec&)），按值传参是纯浪费。
  3. 拷贝与移动成本同量级：形参构造那一下躲不掉，若拷贝远贵于移动，左值路径依然心疼。

两个结构性限制：

  • 多参数组合爆炸：两个这样的参数用重载方案要 4 个函数（2²），n 个参数要 2ⁿ 个——这正是按值传参最大的现实动机；反过来，如果参数不一定被存（某分支提前 return），按值传参就白付了形参构造费。
  • 按值接基类会切片：void f(Base b) 收到 Derived 时切掉派生部分。实测（同一程序扩展）：
struct Base { virtual int kind() const { return 1; } };
struct Derived : Base { int kind() const override { return 2; } };
// by_value(d) = 1   by_ref(d) = 2    ← 按值接到了切剩的 Base

多态类型参数永远用引用/指针，不按值。

常见错误（新手踩坑）

错误 1：按值接收后忘了 std::move 进容器

void add(std::string name) {
    names.push_back(name);          // name 是具名左值 → 拷贝！按值的收益全没了
}

修正： names.push_back(std::move(name));——形参是左值，必须显式 move。

错误 2：移动昂贵的类型按值传递

void add(std::array<double, 1024> a) { buf.push_back(std::move(a)); }  // 移动 = O(N) 拷贝

修正： std::array、大 POD 聚合体用 const&（只读）或双重载。

错误 3：只读参数也按值传

void print_name(std::string name) { std::cout << name; }   // 白拷/白移一次

修正： 只读参数用 const std::string&。

错误 4：参数可能不存时按值传

void maybe_add(std::string s) { if (!validate(s)) return; store(std::move(s)); }
// validate 失败的路径白付了构造形参的钱

修正： 有条件存储的用 const& 接收，确定要存时再拷。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
传参 按值（拷贝）或指针 按值 / const& / && / 万能引用 多了值类别维度
"省一次拷贝" 不存在（没有移动语义） 右值走移动构造 C++11
惯用法 大结构体传指针 总会存的参数可按值 + move 一份代码 ≈ 双重载性能

一句话总结： 参数总会被拷一份、类型移动廉价时，按值传参 + std::move 用一份代码拿到接近双重载的性能；否则乖乖用引用。

HFT 关联

  • 配置/注册接口：registerSymbol(std::string sym) 这类冷路径接口按值传参最舒服——移动廉价、必然存进 map，一份代码够简洁。
  • 热路径不这么玩：on_tick(Tick t) 若 Tick 含 std::array 或大 buffer，按值形参构造就是 O(N) 拷贝，热路径用 const&。
  • 具名右值税：实测确认 f(std::move(w)) 时按值方案付 2 次移动——对象若装着堆内存池句柄，这两次移动里的指针交接虽小，在高频调用下也要计入延迟预算。
  • 多参数构造函数：订单构建器这类 4-5 个 string 参数的函数，重载方案 32 个函数不现实，按值传参是唯一可维护的选择。

自测题

1. 按值传参相比 const&+&& 双重载，对左值实参多付了什么代价？

答案

恰好一次移动构造：双重载版左值是 1 次拷贝；按值版是"拷贝构造形参 + 移动进容器"共 1 拷贝 + 1 移动。实测 A(双重载) add(左值): copy=1 move=0 vs B(按值) add(左值): copy=1 move=1。

2. 实测中传纯右值 W{} 时两种方案为什么打平？

答案

C++17 起强制拷贝消除：纯右值直接原地构造进按值形参，省掉书中预测的"移动构造形参"那一步，两方案都是 ctor=1, move=1。只有传具名右值（std::move(w)）时才显出按值版多一次移动（move=2 vs 1）。

3. 按值传参惯用法的三条适用前提是什么？

答案

①类型可移动且移动廉价（string/vector/unique_ptr，而非 std::array）；②参数总会被拷一份存入内部（不是只读、不是条件存储）；③拷贝与移动成本同量级。三条同时成立时，一份代码换接近双重载的性能是划算交易。

4. 为什么 std::array<T, N> 不适合按值传参？

答案

它的移动是逐成员拷贝 O(N)，按值方案"多付一次移动"对它等于多付一次完整拷贝，代价模型失效。这类类型用 const&（只读）或双重载。

5. 按值接收基类参数会发生什么？实测结果是什么？

答案

切片：派生对象被切成基类副本，虚函数行为丢失。实测 by_value(d)=1（Base 的 kind）vs by_ref(d)=2（Derived 的 kind）。多态类型参数必须用引用或指针。

6. 两个按值存储的参数用重载方案要写几个函数？这说明了什么？

答案

2² = 4 个，n 个参数要 2ⁿ 个。重载方案在多参数下组合爆炸，这是按值传参最大的现实动机——可维护性。反过来参数"可能不存"时，按值会在放弃的分支里白付构造费。

7. void add(std::string name) { names.push_back(name); } 错在哪？

答案

name 是具名形参，是左值——push_back(name) 走拷贝，左值实参总代价变成 1 拷贝 + 1 拷贝，按值的收益被完全抵消。必须 push_back(std::move(name))。

Item 42

Item 42：优先 emplace 而非 insert

第 8 章 微调 · Item 42 · 上一节：Item 41 按值传递

为什么要学这个（先建立直觉）

往 vector 里加一个 Widget，两种写法看着差不多：

v.push_back(Widget(42, 100));   // 先在栈上造一个临时 Widget，再移动进容器
v.emplace_back(42, 100);        // 把构造参数送进容器，在容器的内存里原地造

第一行其实干了三件事：构造临时对象、移动进容器、析构临时对象。第二行只干一件事：拿参数在容器尾部那块还没初始化的内存上 placement-new 一个对象。省掉的是整个临时对象的一生——构造、移动、析构。

但 emplace 不是无脑替换 push_back 的银弹。它用的是直接初始化语义，这意味着两件事：一是它能绕过 explicit（有时候是便利，有时候是踩进编译器都不拦你的坑）；二是参数原样转发给构造函数，传错参数时编译器给你的报错和 push_back 完全不同。再加上智能指针容器那个著名的异常泄漏陷阱，这一节的正确姿势是"优先 emplace，但知道何时不该用"。

这节讲什么

emplace_back(args...) 在容器内原地构造元素，省去临时对象的构造 + 移动 + 析构。实测对比两者构造次数；分析三类 emplace 反而更差/更危险的场景：实参已是元素类型、explicit 构造函数被直接初始化绕过（vector<regex> 实测编译差异）、智能指针容器传裸 new 的异常泄漏。

实测 1：构造次数对账（本机实测 clang 23.1.0）

带构造/拷贝/移动/析构计数器的 W，对比三种插入方式：

#include <cstdio>
#include <vector>

struct Cnt { int ctor = 0, copy = 0, move = 0, dtor = 0; };
Cnt g;

struct W {
    W(int x, int y) { ++g.ctor; (void)x; (void)y; }
    W(const W&) { ++g.copy; }
    W(W&&) noexcept { ++g.move; }
    ~W() { ++g.dtor; }
};

void report(const char* label) {
    std::printf("%-40s ctor=%d copy=%d move=%d dtor=%d\n",
                label, g.ctor, g.copy, g.move, g.dtor);
    g = Cnt{};
}

int main() {
    {
        std::vector<W> v;
        v.reserve(1);                 // 排除扩容干扰
        g = Cnt{};
        v.push_back(W(42, 100));      // 临时对象 + 移动
        report("push_back(W(42,100)):");
    }
    {
        std::vector<W> v;
        v.reserve(1);
        g = Cnt{};
        v.emplace_back(42, 100);      // 原地构造
        report("emplace_back(42,100):");
    }
    {
        std::vector<W> v;
        v.reserve(1);
        W w(42, 100);
        g = Cnt{};
        v.push_back(w);               // 传左值：两者都要拷贝
        report("push_back(w) 传左值:");
        v.pop_back();                 // 析构掉刚插入的元素（dtor 计数 +1）
        v.emplace_back(w);
        report("emplace_back(w) 传左值:");
    }
    return 0;
}

clang 23.1.0 + -std=c++17 -Wall 实测输出：

push_back(W(42,100)):                    ctor=1 copy=0 move=1 dtor=1
emplace_back(42,100):                    ctor=1 copy=0 move=0 dtor=0
push_back(w) 传左值:                  ctor=0 copy=1 move=0 dtor=0
emplace_back(w) 传左值:               ctor=0 copy=1 move=0 dtor=1

逐行解读：

  1. 临时对象场景：push_back(W(42,100)) 是 ctor=1 + move=1 + dtor=1（临时对象完整的一生）；emplace_back(42,100) 只有 ctor=1。emplace 精确省掉一次移动和一次析构——对 std::string 这种移动要交接三个指针的类型，省的是几十条指令。
  2. 左值场景：两者打平（各 copy=1）。最后一行的 dtor=1 来自中间那次 pop_back()（把上一轮插入的元素析构了），不是 emplace 的开销——实参已经是元素类型时，emplace 没有任何收益，它和 push_back 一样只是转发给拷贝/移动构造。

结论和 Item 41 的教训一致：emplace 的收益只在"用构造参数原地造"时存在，手里已经有现成对象时两者等价。

实测 2：explicit 陷阱——emplace 能编译，push_back 不能

std::regex 的 const char* 构造函数是 explicit。同一个 vector<regex>，两种插入方式编译结果不同：

#include <regex>
#include <vector>

int main() {
    std::vector<std::regex> v;
    v.emplace_back(".*");   // 编译通过
    return 0;
}

clang 23.1.0 实测：编译通过。

    v.push_back(".*");      // 换成 push_back

clang 23.1.0 实测报错原文：

error: no matching member function for call to 'push_back'
    v.push_back(".*");
    ~~^~~~~~~~~
note: candidate function not viable: no known conversion from
      'const char[3]' to 'const std::regex' for 1st argument
note: candidate function not viable: no known conversion from
      'const char[3]' to 'value_type' (aka 'std::regex') for 1st argument

原因：push_back 的形参是 const regex& / regex&&，传 ".*" 需要一次 const char* → regex 的隐式转换（拷贝初始化），explicit 禁止它；emplace_back 把参数直接转发给构造函数（直接初始化），explicit 构造函数名正言顺地被调用。

这是双刃剑。便利的一面：emplace_back 能搞定 push_back 表达不了的插入。危险的一面：拷贝初始化是你和编译器之间的默契检查——隐式转换走不通时 push_back 直接编译失败，而 emplace 会默默地直接构造。经典事故：

std::vector<std::string> vs;
vs.emplace_back(nullptr);   // 能编译！用 nullptr 构造 string → 运行时 UB/崩溃
vs.push_back(nullptr);      // 编译失败——反而安全

explicit 的设计意图是"这种转换必须显式写出"，emplace 的直接初始化把这道护栏拆掉了。参数和元素类型不完全吻合时，想清楚再 emplace。

智能指针容器：异常安全的分水岭

std::vector<std::unique_ptr<Widget>> v;
v.emplace_back(new Widget);                 // 能编译，但有泄漏窗口
v.push_back(std::make_unique<Widget>());    // 安全

第一行的问题在求值顺序：new Widget 先于 emplace_back 执行，得到一个裸指针；emplace 内部若因扩容分配抛 std::bad_alloc，这个裸指针还没被任何 unique_ptr 接管——内存泄漏。

第二行里 make_unique 在 push_back 之前就完成了 RAII 接管，即使扩容抛异常，临时 unique_ptr 析构也会把对象收走。规则一句话：往智能指针容器里插新对象，用 push_back(make_unique<T>())；emplace 的参数应该是"构造参数"，不该是裸 new 表达式。

常见错误（新手踩坑）

错误 1：emplace 传已构造好的对象

v.emplace_back(Widget(42, 100));   // 还是构造了临时对象，和 push_back 一样

修正： v.emplace_back(42, 100);——传构造参数，不是传对象。

错误 2：智能指针容器 emplace_back(new T)

v.emplace_back(new Widget);   // 扩容抛异常 → 裸指针泄漏

修正： v.push_back(std::make_unique<Widget>());

错误 3：忽略 emplace 绕过 explicit 的杀伤力

vs.emplace_back(nullptr);   // 能编译，运行时炸

修正： 参数不是元素类型时，警惕 emplace 的直接初始化语义；push_back 的编译错误有时是救命的。

错误 4：以为 emplace 一定更快

修正： 实参已是元素类型时两者等价（实测打平）；容器已持有对象、要做的是"插入现有对象"时，insert/push_back 反而更直白。收益只在原地构造场景。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
数组追加 arr[n++] = tmp（先造再拷） push_back / emplace_back 后者原地构造
构造与放置 分离（先声明再赋值） placement new 一体完成 容器内存管理

一句话总结： 有构造参数就 emplace_back(args...) 原地构造；手里已是元素对象两者等价；智能指针容器永远 push_back(make_unique<T>())。

HFT 关联

  • 行情对象入队：ticks.emplace_back(symbol, price, qty, ts) 原地构造省一次 Tick 的移动——Tick 若含 std::string symbol，高频下收益可观。
  • 预分配配合：emplace 省构造、reserve 省扩容，两者搭配才是完整优化（实测里特意 reserve(1) 排除扩容干扰）。
  • 订单簿 map：book.emplace(price, Order{...}) 避免临时 pair；但 key 已存在时 emplace 会先构造再丢弃——查插混合场景用 try_emplace（C++17）。
  • 连接池/对象池：vector<unique_ptr<Session>> 只准 push_back(make_shared/make_unique)——热路径上一次 bad_alloc 泄漏不会被立刻发现，但会慢慢吃掉内存。

自测题

1. emplace_back(42, 100) 相比 push_back(W(42, 100)) 省掉了什么？实测数据？

答案

省掉临时对象的移动构造和析构。实测：push_back 是 ctor=1, move=1, dtor=1；emplace_back 只有 ctor=1。emplace 把参数完美转发给构造函数，在容器尾部未初始化内存上 placement-new，不产生临时对象。

2. 传左值（已构造好的对象）时两者有差别吗？

答案

没有。实测两者都是 copy=1, move=0。emplace 此时只是转发给拷贝构造，和 push_back 等价。emplace 的收益只在"用构造参数原地造"时存在。

3. vector<regex> 上 emplace_back(".*") 和 push_back(".*") 的编译结果分别是什么？为什么？

答案

前者编译通过，后者报错 no known conversion from 'const char[3]' to 'const std::regex'。regex 的 const char* 构造函数是 explicit：push_back 需要隐式转换（拷贝初始化）被 explicit 拒绝；emplace 用直接初始化，explicit 构造函数可被直接调用。explicit 护栏对 emplace 无效。

4. v.emplace_back(new Widget)（v 是 vector<unique_ptr<Widget>>）有什么问题？正确写法？

答案

new Widget 先于 emplace 求值得到裸指针；若 emplace 内部扩容分配抛异常，裸指针还没被 unique_ptr 接管，内存泄漏。正确写法 v.push_back(std::make_unique<Widget>())——RAII 接管发生在 push_back 之前，栈展开时自动释放。

5. 什么场景下 push_back 反而比 emplace_back 安全？

答案

两类：①参数需要隐式转换才匹配元素类型时，push_back 的拷贝初始化会被 explicit 拦住（编译失败 = 安全），emplace 的直接初始化会默默构造（如 vector<string>::emplace_back(nullptr) 编译通过但运行时 UB）；②智能指针容器装新对象时 push_back(make_unique) 无异常泄漏窗口。

6. map 容器上 emplace 家族有什么额外注意事项？

答案

map::emplace(k, v) 在 k 已存在时仍会先构造好 value 再丢弃（白付构造费）；C++17 的 try_emplace 只在 key 不存在时才构造，查插混合场景（订单簿按价位插入）应优先 try_emplace。

7. 为什么说"emplace 一定更快"是误解？

答案

实参已是元素类型时两者实测打平（各 copy=1）；emplace 的模板完美转发会实例化更多代码（代码膨胀）；某些场景 insert 迭代器版本还能批量插入。收益精确地只来自"原地构造"这一种场景，其它场景按可读性选。

Q1emplace vs push_back
std::vector<std::string> v;
v.push_back(std::string("hello"));  // A: 几次构造/移动？
v.emplace_back("hello");            // B: 几次构造/移动？

A 和 B 分别触发几次构造/移动？

答案与复习指引

A（push_back）： 2 次——构造临时 string("hello") → 移动进 v（或 C++17 拷贝省略后只有 1 次构造） B（emplace_back）： 1 次——直接在 v 的内存里构造 string，参数 "hello" 传给 string 的构造函数

emplace 优势： 无临时对象、无移动、可传任意构造参数。 emplace 限制： 依赖 value_type 可从参数直接构造；资源管理顺序不同（异常安全敏感场景需注意）。

复习： → Item 42：优先 emplace 而非 insert

Q2emplace 异常安全
std::vector<std::unique_ptr<Widget>> v;
// v.emplace_back(new Widget);     // A: 安全吗？
v.emplace_back(std::make_unique<Widget>());  // B: 安全吗？

A 行安全吗？如果 emplace_back 扩容抛异常会怎样？

答案与复习指引

A 不安全。 emplace_back(new Widget) 先构造 unique_ptr（接管裸指针），如果此时 vector 扩容需要移动元素并抛 bad_alloc，裸指针已经被 unique_ptr 管理——实际上 emplace_back 内部可能先 new 再构造，中间异常导致裸指针泄漏。

B 安全。 make_unique<Widget>() 先构造好 unique_ptr，再传给 emplace_back。即使扩容异常，unique_ptr 的移动构造是 noexcept，不会泄漏。

规则： 不传裸 new 结果给 emplace/push_back，先包成智能指针。

复习： → Item 42：优先 emplace 而非 insert
