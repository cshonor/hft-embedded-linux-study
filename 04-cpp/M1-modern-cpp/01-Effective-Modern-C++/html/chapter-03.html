Moving to Modern C++ — Items 7–17

本章讲什么

C++11/14 在 C++ 基础语法层做了一大批改进：初始化、空指针、类型别名、枚举、特殊成员函数、noexcept、constexpr……这些不是孤立的语法点，而是相互咬合的"现代基线"。本章逐 item 给出"为什么要换 + 怎么换 + 坑在哪"。

各 Item 要点

Item 7：区别 () 和 {} 创建对象

C++11 有了大括号初始化 {}，它几乎能初始化一切，但有别于小括号 ()：

特性 () {}
窄化转换 允许（int(3.14)） 禁止（int{3.14} 编译失败）
最烦人解析 会中招（Widget w(); 被解析成函数声明） 免疫
initializer_list 构造函数 不优先 优先匹配

initializer_list 优先陷阱：

std::vector<int> v1(10, 20);   // 10 个 20 → {20,20,...,20}
std::vector<int> v2{10, 20};   // 2 个元素 → {10, 20}  匹配 initializer_list 构造

{} 会优先匹配 initializer_list 构造函数，哪怕有更优匹配。空 {} 则调用默认构造（不会造出空的 initializer_list）。

建议：对内置类型用 {} 防窄化；对容器/自定义类，先查它有没有 initializer_list 构造，再决定用 {} 还是 ()。

Item 8：优先 nullptr 而非 0 和 NULL

0 和 NULL 都是整型字面量，在指针与整型重载时会误选整型重载：

void f(int);   void f(Widget*);
f(0);          // 调 f(int)！不是 f(Widget*)
f(NULL);       // 仍可能调 f(int)（NULL 的类型依赖实现）
f(nullptr);    // 调 f(Widget*)，正确

nullptr 的类型是 std::nullptr_t，能隐式转任意指针，不能转整型——彻底消除指针/整型重载歧义。模板推导里也能正确推导出指针类型。

配套深挖：Item 8a nullptr 的硬件路径——三种判空写法汇编逐字节相同（实测）、g(NULL) 在本机直接编译失败、0 页保护对 C/C++ 一视同仁。

Item 9：优先 using 别名而非 typedef

using 支持模板化（alias template），typedef 不行：

template<class T> using Vec = std::vector<T, MyAlloc<T>>;  // OK
template<class T> typedef std::vector<T, MyAlloc<T>> Vec;  // 编译失败

using 还能避免读复杂的函数指针类型，且与 C++14 auto 返回类型推导配合更自然。

Item 10：优先限定作用域枚举（scoped enum）

enum Color { Red, Green };        // unscoped：Red 泄漏到外层作用域
enum class Color2 { Red, Green }; // scoped：必须 Color2::Red

限定作用域枚举（enum class）不隐式转整型、不污染外层命名空间、可前向声明（可指定底层类型）。HFT 协议字段用 enum class 防止误比较。

Item 11：优先 = default 声明默认构造

= default 让编译器生成默认实现，比手写空函数体更可靠（手写 C() {} 会变成"用户定义"，影响是否为 trivial 类型——影响 memcpy 合法性与 ABI）。

Item 12：把重写函数声明为 override

override 关键字让编译器检查是否真的重写了基类虚函数——签名不匹配（const 差异、参数类型差异、引用限定符差异）会编译报错，而非静默创建一个新虚函数。这是 C++11 最具性价比的防 bug 特性之一。

Item 13：优先 const_iterator 而非 iterator

C++11 引入 cbegin()/cend()，配合 auto：auto it = v.cbegin(); 拿到 const_iterator，防止意外修改。STL 算法（find/insert）在 C++14 起支持 const_iterator。

Item 14：声明 noexcept 如果函数保证不抛

noexcept 是函数接口契约的一部分。对移动构造、swap、析构标 noexcept 尤其关键——STL 容器在 push_back 扩容时会检查元素移动构造是否 noexcept：是则用移动（快），否则退回拷贝（安全）。标错 noexcept 但抛异常会 std::terminate。

Item 15：尽可能用 constexpr

constexpr 表示"编译期可求值"。constexpr 对象是编译期常量；constexpr 函数在编译期能求值时就编译期求值，否则退化为运行时。C++14 起 constexpr 函数可用 if/局部变量/循环，能力大增。HFT 用 constexpr 做编译期查表、协议字段偏移计算，零运行开销。

Item 16：让 const 成员函数线程安全

const 成员函数仍可修改 mutable 成员（如缓存、互斥锁）。如果 const 函数会读写 mutable 成员，它就不是天然线程安全的——必须加锁或用 std::atomic。否则两个线程同时调用同一个 const 对象的该方法会数据竞争。

Item 17：理解特殊成员函数的生成规则

C++11 的"大三律"扩展为"大五律"（拷贝构造、拷贝赋值、移动构造、移动赋值、析构）。生成规则：声明了任何一个，其余的生成受抑制。具体而言，声明了拷贝操作会抑制移动操作的自动生成；声明了析构会抑制移动生成（C++11）但保留拷贝生成（已废弃，C++11 起警告）。手写任何一个就应该把五个都写（或 =default/=delete）。

HFT 关联

  • noexcept 与 STL 扩容：热路径里 vector<Order> push_back 扩容时，Order 的移动构造必须 noexcept 才走移动语义——否则扩容退回拷贝，订单簿重建延迟尖峰。这是 HFT C++ 性能的隐形开关。
  • constexpr 编译期求值：协议字段偏移、校验和表、费率表用 constexpr 编译期算好，运行时零开销。比 C 的 #define / static const 更强（可用于模板参数、static_assert）。
  • enum class 防误比较：订单状态、Side(Buy/Sell) 用 enum class，编译器拒绝 Side::Buy == 1 的隐式比较，消除一类下单逻辑 bug。
  • override 检查：策略基类的虚函数（on_tick/on_fill）加 override，子类签名写错编译期暴露，避免"虚函数没被重写、策略不生效"的隐蔽 bug。

Item 7：区别 () 和 {} 创建对象

第 3 章 移步现代 C++ · Item 7 · 上一节：Item 6 auto 看不出来的显式类型初始化器

为什么要学这个（先建立直觉）

C 里初始化很简单——int x = 42;、int arr[] = {1, 2, 3};、struct Point p = {3, 4};，要么 = 要么 {}，没有第三种。C++ 有了类和构造函数重载之后，初始化出现了 () 写法，C++11 又给了 {} 一个"万能初始化"的名头：数组、容器、内置类型、成员初始化列表全都能用。听起来很美——写代码时闭着眼用 {} 就行了？

不行。std::vector<int> v(10, 20) 和 std::vector<int> v{10, 20} 一个是"10 个 20"、一个是"两个元素 10 和 20"，语义天差地别，而两行代码只差一对括号。这类 bug 编译不报错、运行不崩溃，只是容器里的内容不对——在订单簿代码里就是"预分配 1000 档"变成"两档，值是 1000 和 0"这种隐蔽事故。

本节的全部内容，其实就是回答一个问题：同一个参数列表，什么时候该用 ()，什么时候该用 {}，以及选错了会发生什么。

这节讲什么

  1. () 与 {} 的三条系统性差异（窄化防护、最恼人解析、initializer_list 优先）；
  2. initializer_list 构造函数的"劫持"行为，以及它唯一的退让条件；
  3. 为什么模板代码里 () 和 {} 语义不可互换，作者只能把选择权留给用户；
  4. 全部论断附本机实测（clang 23.1.0，arm64-apple-darwin，libc++，-std=c++17 -Wall）。

() vs {} 总览对比

特性 () {}
窄化转换 允许（int(3.14) 得 3） 禁止（编译失败，报错原文见下）
最恼人解析 会中招（Widget w(); 被解析成函数声明） 免疫
initializer_list 构造函数 不参与优先规则 优先匹配，除非完全不可行
空初始化 T x() / T x{} 函数声明（不创建对象！） 默认构造 / 值初始化
适用范围 只能调构造函数 几乎一切：数组、容器、聚合体、成员初始化、返回值

一句话：{} 更安全（防窄化、防解析歧义），但对有 initializer_list 构造函数的类，{} 会改变重载决议结果。

initializer_list 劫持：本节的核心

vector 的经典陷阱（实测）

#include <vector>
#include <iostream>

int main() {
    std::vector<int> v1(10, 20);   // 调 (count, value) 构造
    std::vector<int> v2{10, 20};   // 被 initializer_list 构造劫持
    std::vector<int> v3(10);       // 10 个 0
    std::vector<int> v4{10};       // 1 个元素 10
    std::vector<int> v5{};         // 空 vector（空 {} 走默认构造）

    std::cout << "v1.size()=" << v1.size() << " v1[0]=" << v1[0] << "\n";
    std::cout << "v2.size()=" << v2.size() << " v2[0]=" << v2[0] << " v2[1]=" << v2[1] << "\n";
    std::cout << "v3.size()=" << v3.size() << " v3[0]=" << v3[0] << "\n";
    std::cout << "v4.size()=" << v4.size() << " v4[0]=" << v4[0] << "\n";
    std::cout << "v5.size()=" << v5.size() << "\n";
}

本机实测 clang 23.1.0 输出：

v1.size()=10 v1[0]=20
v2.size()=2 v2[0]=10 v2[1]=20
v3.size()=10 v3[0]=0
v4.size()=1 v4[0]=10
v5.size()=0

{10, 20} 没有匹配"10 个 20"的构造函数，而是整体变成一个 initializer_list<int>，两个值原样入容器。注意空 {} 是特例：它不生成空 initializer_list，而是调默认构造。

劫持的优先级有多强：宁可类型转换也要走 init_list

class Widget {
public:
    Widget(int i, bool b)      { std::cout << "ctor(int,bool)\n"; }
    Widget(int i, double d)    { std::cout << "ctor(int,double)\n"; }
    Widget(std::initializer_list<long double> il) {
        std::cout << "ctor(init_list), size=" << il.size() << "\n";
    }
};

int main() {
    Widget w1(10, true);    // ?
    Widget w2{10, true};    // ?
    Widget w3(10, 5.0);     // ?
    Widget w4{10, 5.0};     // ?
}

本机实测 clang 23.1.0 输出：

ctor(int,bool)
ctor(init_list), size=2
ctor(int,double)
ctor(init_list), size=2

w2{10, true} 明明有精确匹配的 ctor(int, bool)，编译器仍然选择把 10 和 true 转成 long double 塞进 initializer_list。只要 {} 里的元素能以任何方式（除窄化外）转换成 init_list 的元素类型，init_list 构造函数就赢。这就是 Meyers 说的"劫持"。

唯一的退让：元素类型完全转不动时

std::vector<std::string> vs{10, "hi"};   // int 转不了 string

实测输出：vs.size()=10 vs[0]=hi。initializer_list<std::string> 走不通，编译器才退回普通重载决议，匹配 (size_type, const string&)。所以 {} 的语义取决于元素类型能否转换——给类新增一个 initializer_list 构造函数，可能静默改变所有已有 {} 调用点的行为。

窄化防护：{} 的安全红利

double d = 3.14;
int x1(d);       // OK：静默截断为 3
int x2{3.14};    // 编译失败
int x3{d};       // 编译失败（变量也不行）
int x4{3.0};     // 编译失败！浮点→整型一律算窄化

本机实测 clang 23.1.0 报错原文：

error: type 'double' cannot be narrowed to 'int' in initializer list [-Wc++11-narrowing]
    int x2{3.14};
           ^~~~
note: insert an explicit cast to silence this issue
           static_cast<int>( )

注意 int x4{3.0} 也报错——标准里浮点→整型的转换无条件属于窄化，没有"常量可精确表示"的豁免（豁免只存在于浮点→浮点，如 float{3.0} 合法）。网上和旧笔记里"int{3.0} 合法"的说法是错的，以编译器为准。确实需要截断时，照编译器提示写 static_cast<int>(d)，把"我知道我在丢精度"写在脸上。

列表元素类型不一致也报错

auto bad = {1, 2.0}; 实测报错 error: deduced conflicting types ('int' vs 'double') for initializer list element type——initializer_list<T> 要求单一元素类型，推不出唯一的 T 就失败（呼应 Item 2 的 auto 大括号例外）。

最恼人解析（Most Vexing Parse）

struct Widget { void hello() const {} };

Widget w1;      // OK：默认构造
Widget w2{};    // OK：{} 不会被解析成声明
Widget w3();    // 声明了一个"返回 Widget、无参"的函数！
// w3.hello(); // 解开注释会报错

本机实测 clang 23.1.0，编译期就有警告：

warning: empty parentheses interpreted as a function declaration [-Wvexing-parse]
    Widget w3();
             ^~
note: remove parentheses to declare a variable

如果解开 w3.hello(); 的注释，报错更直白：

error: base of member reference is a function;
       perhaps you meant to call it with no arguments?
    w3.hello();
    ^~
       ()

"任何能被解析成声明的语法，就会被解析成声明"——() 空参数列表踩中这条规则，而 {} 在语法上不可能是函数声明，天然免疫。

模板代码里 () 与 {} 不可互换

写一个"完美创建对象"的工厂，把参数转发给 T 的构造函数：

template<typename T, typename... Ts>
T makeParens(Ts&&... params) {
    return T(std::forward<Ts>(params)...);   // 内部用 ()
}

auto v1 = makeParens<std::vector<int>>(10, 20);   // size=10：10 个 20
std::vector<int> v2{10, 20};                      // size=2：{10, 20}

实测输出：parens: size=10 / braces: size=2。模板作者无法替调用方决定语义：用 () 就没法表达"按列表初始化"，用 {} 就没法表达"按参数调构造"。这就是为什么 std::make_shared/std::make_unique 只能选 ()，以及为什么标准库约定"花括号就是元素列表"。转发参数的代码统一用 ()，表示"列表"的代码显式用 {}，不要混。

完整可运行例子

#include <initializer_list>
#include <iostream>
#include <vector>

class Widget {
public:
    Widget() { std::cout << "default ctor\n"; }
    Widget(int i, bool b) { std::cout << "ctor(int,bool)\n"; }
    Widget(std::initializer_list<long double> il) {
        std::cout << "ctor(init_list), size=" << il.size() << "\n";
    }
};

int main() {
    Widget w0{};                       // 默认构造（Widget w0(); 会变成函数声明）
    Widget w1(1, true);                // ctor(int,bool)
    Widget w2{1, true};                // ctor(init_list)：劫持

    std::vector<int> v1(5, 42);        // 5 个 42
    std::vector<int> v2{5, 42};        // 两个元素
    std::vector<int> v3{};             // 空 {} = 默认构造
    std::cout << "v1: size=" << v1.size() << " front=" << v1.front() << "\n";
    std::cout << "v2: size=" << v2.size() << " front=" << v2.front() << "\n";
    std::cout << "v3.size()=" << v3.size() << "\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

default ctor
ctor(int,bool)
ctor(init_list), size=2
v1: size=5 front=42
v2: size=2 front=5
v3.size()=0

常见错误（新手踩坑）

  1. vector<int> v{10, 20} 以为是"10 个 20"。实测是 2 个元素 {10, 20}。规则：要 N 个相同值用 (n, val)，要逐个列元素用 {}。
  2. Widget w(); 以为创建了对象。它是函数声明，编译时 -Wvexing-parse 警告，调用成员时报 base of member reference is a function。修正：Widget w; 或 Widget w{};。
  3. 以为 int{3.0} 能过。实测 clang 23.1.0 报 cannot be narrowed——浮点→整型一律算窄化，常量也不例外。修正：static_cast<int>(3.0)。
  4. 给类新增 initializer_list 构造函数后，老代码行为静默改变。所有 {} 调用点会被劫持到新构造函数。修正：加 init_list 构造函数前 grep 一遍 {} 调用点，或改用 static 工厂函数（如 Widget::fromList(...)）避免重载集污染。

HFT 关联

  • 预分配 vs 元素列表：ring_buffer<Order> buf{capacity} 是"一个元素，值是 capacity"（若 capacity 转得动 Order 就劫持，转不动才报错），buf(capacity) 才是预分配。低延迟代码里容器预分配写错，热身阶段就会踩到 reallocation。
  • 防窄化拦真实 bug：int64_t qty{md.price} 在 price 是 double 时编译失败，逼着写下 static_cast——下单数量被静默截断成整数的 bug 类被直接消灭。
  • 聚合体 + {} 零成本初始化：协议报文结构体 struct alignas(64) Tick { int64_t ts; double bid, ask; }; 用 Tick t{ts, bid, ask}; 聚合初始化，无构造函数调用开销，布局就是 ABI 布局。
  • 工厂模板统一 ()：策略对象工厂 template<class S, class... A> S makeStrategy(A&&... a) 内部用 S(std::forward<A>(a)...)，保证语义只依赖构造函数签名，不被 init_list 劫持干扰。

自测题

1. vector<int> v(10, 20) 和 vector<int> v{10, 20} 结果有何不同？根因是什么？

答案

(10, 20) 得到 10 个值为 20 的元素；{10, 20} 得到 2 个元素 10 和 20。根因：{} 初始化时编译器优先尝试 std::initializer_list 构造函数，{10, 20} 整体匹配 initializer_list<int>；() 不参与这条优先规则，走普通重载决议匹配 vector(size_type count, const T& value)。

2. Widget w(); 声明的是什么？为什么 Widget w{}; 就没这个问题？

答案

声明了一个名为 w、无参数、返回 Widget 的函数（most vexing parse："能解析成声明就解析成声明"）。clang 实测给 -Wvexing-parse 警告。{} 在语法上不可能是函数声明，所以 Widget w{}; 一定是默认构造一个对象。

3. int x{3.14}; 和 int x{3.0}; 能编译通过吗？int x(3.14); 呢？

答案

都不能。实测 clang 23.1.0 两行都报 error: type 'double' cannot be narrowed to 'int' in initializer list——浮点→整型无条件算窄化，3.0 常量也不例外。而 int x(3.14) 编译通过，静默截断为 3。这正是 {} 的价值：把静默截断变成编译期诊断。

4. 类有 Widget(int, bool) 和 Widget(std::initializer_list<long double>) 两个构造函数，Widget w{1, true}; 调哪个？

答案

调 init_list 版本。实测输出 ctor(init_list), size=2：尽管 (int, bool) 是精确匹配，只要 {} 元素能转换成 init_list 的元素类型（int/bool → long double 非窄化），init_list 构造函数就劫持调用。

5. 什么情况下 {} 不会走 initializer_list 构造函数？

答案

两种：① 空 {}——走默认构造；② 元素类型无法转换成 init_list 元素类型时（如 vector<string> vs{10, "hi"}，int 转不了 string），退回普通重载决议，实测该例匹配 (count, value) 构造得到 10 个 "hi"。

6. 为什么模板工厂函数里不能随意把 T(args...) 改成 T{args...}？

答案

因为两者语义对同一组参数可能完全不同：makeParens<vector<int>>(10, 20) 用 () 得到 size=10，用 {} 得到 size=2（实测）。模板作者无法知道调用方想要哪种语义，所以标准工厂（make_unique 等）统一用 ()；要表达列表初始化必须在调用点显式写 {}。

7. auto bad = {1, 2.0}; 会发生什么？

答案

编译失败：error: deduced conflicting types ('int' vs 'double') for initializer list element type。initializer_list<T> 要求唯一元素类型，混合 int/double 推不出 T。

Item 8：优先 nullptr 而非 0 和 NULL

第 3 章 移步现代 C++ · Item 8 · 上一节：Item 7 () vs {}

为什么要学这个（先建立直觉）

C 里写空指针就两招：int* p = NULL; 或 int* p = 0;。在 C 里这基本没问题——C 没有函数重载，传 NULL 给函数就是传空指针，世界很单纯。

C++ 有重载，事情就变了味。f(0) 里的 0 是个如假包换的 int——如果你的重载集里恰好有 f(int) 和 f(void*)，编译器会毫不犹豫地选 f(int)，哪怕你的意图是"传个空指针"。NULL 也好不到哪去：C++ 不允许 void* 隐式转其他指针，所以 C++ 标准库只能把 NULL 定义成整型字面量（本机 macOS 上是 0L，即 long）。它从来不是指针类型。

最扎心的是模板：把 NULL 传进 template<class T> void g(T)，T 被推导成 long——函数体里拿到的是个整数，想赋给指针直接编译失败。这种 bug 在泛型代码里藏得很深。

nullptr 是 C++11 给出的答案：一个有自己的类型 std::nullptr_t 的空指针字面量，能隐式转成任何指针，但永远不能变成整数。歧义从根上消失。

这节讲什么

  1. 0 / NULL / nullptr 在重载决议下的真实走向（附实测）；
  2. NULL 在模板里被推导成整数的坑（呼应 Item 30 的完美转发失败）；
  3. std::nullptr_t 的性质：sizeof、隐式转换规则；
  4. 全部论断本机实测：clang 23.1.0，arm64-apple-darwin，libc++，-std=c++17 -Wall。

重载决议实测：三个实参三种命运

#include <iostream>

void f(int)   { std::cout << "f(int)\n"; }
void f(bool)  { std::cout << "f(bool)\n"; }
void f(void*) { std::cout << "f(void*)\n"; }

int main() {
    f(0);         // 哪个？
    // f(NULL);   // 这行根本编不过（见下）
    f(nullptr);   // 哪个？
}

本机实测 clang 23.1.0 输出：

f(int)
f(void*)
  • f(0) → f(int)：0 是 int 字面量，精确匹配整型重载，指针重载看都不看。
  • f(nullptr) → f(void*)：nullptr 只能转指针，整型重载出局。

而 f(NULL) 在这组重载下直接编译失败：

error: call to 'f' is ambiguous
    f(NULL);
    ^
note: candidate function     void f(int)
note: candidate function     void f(bool)
note: candidate function     void f(void*)

本机 NULL 展开为 0L（long）：long→int、long→bool、long→void*（0L 是空指针常量）三条转换路径同分，重载决议判平局。这就是 NULL 的尴尬处境——它既不够像整数，也不够像指针，在哪边都是半个候选人。如果重载集里碰巧没有 f(bool)，f(NULL) 会静默选中 f(int)——bug 就从编译期错误变成运行期错误。

模板推导：NULL 变成整数的地方

#include <iostream>

template<typename T>
void g(T x) { std::cout << __PRETTY_FUNCTION__ << "\n"; }

int main() {
    g(0);         // ?
    g(NULL);      // ?
    g(nullptr);   // ?
}

本机实测 clang 23.1.0 输出：

void g(T) [T = int]
void g(T) [T = long]
void g(T) [T = std::nullptr_t]

模板推导只看表达式的类型：0 是 int，NULL（0L）是 long，都和指针无关。函数体里如果写 *x 或 x->foo()，编译报错的位置在模板深处，新手很难联想到是调用点传了 NULL。只有 g(nullptr) 推出 T = std::nullptr_t，函数体里可以再隐式转成需要的任意指针类型。

这正是完美转发里"NULL/0 无法正确转发空指针"的根源，详见 Item 30 完美转发失败的情形。泛型代码里表达"空指针"只有一个选择：nullptr。

std::nullptr_t：nullptr 的类型

#include <cstddef>
#include <iostream>

int main() {
    std::cout << "sizeof(nullptr)=" << sizeof(nullptr) << "\n";
    std::cout << "sizeof(void*)=" << sizeof(void*) << "\n";
    std::cout << "sizeof(NULL)=" << sizeof(NULL) << "\n";

    std::nullptr_t np = nullptr;   // 可以声明该类型的变量
    int* p = np;                   // nullptr_t 可隐式转任意指针
    std::cout << "p==nullptr: " << (p == nullptr) << "\n";
}

本机实测 clang 23.1.0 输出：

sizeof(nullptr)=8
sizeof(void*)=8
sizeof(NULL)=8

要点：

  • std::nullptr_t 大小和指针相同（本机 8 字节），传参、存容器没有额外开销；
  • 它能隐式转任意对象指针、函数指针和成员指针，也能和任意指针比较（==/!=）；
  • 转整型是禁止的：int x = nullptr; 实测报错 error: cannot initialize a variable of type 'int' with an rvalue of type 'std::nullptr_t'；
  • 语境转换到 bool 是允许的：if (p)、if (!p) 照常工作，nullptr 判为 false。

对比表：

写法 类型（本机） 重载中像整数？ 模板推导 可读性
0 int 是（就是它） T = int 差，要看上下文
NULL long（0L） 是，还可能 ambiguous T = long 中，但语义是假的
nullptr std::nullptr_t 否 T = std::nullptr_t 一眼即空指针

完整可运行例子

#include <iostream>
#include <type_traits>

void log(int id)     { std::cout << "log(int): id=" << id << "\n"; }

    // 1. 重载走向
    log(0);         // log(int)：0 是整数
    log(nullptr);   // log(void*)：nullptr 只转指针

    deduce(0);
    deduce(NULL);
    deduce(nullptr);

    static_assert(std::is_same_v<decltype(nullptr), std::nullptr_t>);

    int* p = np;

    // 4. 禁止转整型（编译期错误，本例注释掉才能跑）
    // int bad = nullptr;   // error: cannot initialize 'int' with 'std::nullptr_t'
}

常见错误（新手踩坑）

  1. 重载集里传 0 想表达空指针。process(0) 选中的永远是 process(int) 而不是 process(Widget*)。修正：process(nullptr)。
  2. 模板里传 NULL。实测 T 被推导成 long，函数体把它当指针用时报错埋在模板实例化深处。修正：模板场景一律 nullptr。
  3. 以为 NULL 是指针类型。C 里 NULL 常是 ((void*)0)，但 C++ 禁止 void* 隐式转对象指针，所以 C++ 的 NULL 只能是整型（本机 0L）。从 C 带来的直觉在重载和模板里都会翻车。
  4. 同一文件混用三种写法。if (p == NULL) 和 if (p == nullptr) 并存，审查者要分心判断每一处有没有重载/推导陷阱。修正：全仓统一 nullptr，老代码顺手改，NULL 在 C++ 里没有任何 nullptr 不具备的优势。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
空指针写法 NULL 或 0 nullptr C++ 有重载与模板，0/NULL 是整型会误选
NULL 的定义 ((void*)0)（指针类型） 0 或 0L（整型） C++ 不允许 void* 隐式转其他指针
模板推导 不适用（C 无模板） nullptr → T = std::nullptr_t 正确表达"空指针"意图

一句话总结： C 程序员记住——C++ 的 NULL 不是 C 的 NULL（C 的是指针、C++ 的是整型），C++ 里空指针一律写 nullptr。

自测题

1. void f(int); void f(void*); 下 f(0)、f(NULL)、f(nullptr) 各调哪个？

答案

f(0) 调 f(int)（0 是 int 字面量，精确匹配）；f(nullptr) 调 f(void*)（nullptr 只能转指针）；f(NULL) 视实现而定——本机 NULL 是 0L，实测在两参重载里尚可调 f(int)，加上 f(bool) 后变成 error: call to 'f' is ambiguous。结论：只有 nullptr 的行为不依赖实现。

2. nullptr 的类型是什么？能隐式转成 int 吗？

答案

类型是 std::nullptr_t（<cstddef>）。不能转 int：实测 int x = nullptr; 报 error: cannot initialize a variable of type 'int' with an rvalue of type 'std::nullptr_t'。它能隐式转任意指针类型，语境下可转 bool（if (p)）。

3. template<class T> void g(T); g(NULL); 在本机推出 T 是什么？后果是什么？

答案

T = long（本机 NULL 是 0L）。后果：函数体里拿到的"指针"其实是个整数，任何指针运算（*x、x->、赋给指针变量）都会编译失败，且报错位置在模板深处。这就是 Item 30 讲的完美转发失败场景之一。

4. 为什么 C++ 不把 NULL 定义成 ((void*)0)，像 C 那样？

答案

因为 C++ 禁止 void* 隐式转换为其他对象指针类型。若 NULL 是 ((void*)0)，int* p = NULL; 都编不过。所以 C++ 标准规定 NULL 是整型空指针常量（0 或 0L），它进入重载决议时天然是"整数候选人"，这是一切歧义的根源。

5. sizeof(nullptr) 是多少？把代码里的 NULL 全换成 nullptr 会改变 ABI 吗？

答案

本机实测 8，与 sizeof(void*) 相同。不会改变 ABI：nullptr 的表示就是空指针值，和 NULL 生成的机器码一致（见 Item 8a 的汇编对比），替换是纯语义增强。

6. 下面代码有什么问题？

void register_cb(int id);
void register_cb(void(*cb)());
register_cb(0);
答案

register_cb(0) 选中的是 register_cb(int)——程序员意图多半是"清除回调"，实际调用的是"注册 id 0"。修正：register_cb(nullptr) 明确选中函数指针重载，编译期保证意图与行为一致。

Item 8a：nullptr 的硬件路径——判空、重载与 0 页保护（汇编实测）

第 3 章 移步现代 C++ · Item 8 配套深挖 · 上一节：Item 8 优先 nullptr

为什么要学这个（先建立直觉）

Item 8 在语言层回答了"为什么用 nullptr"（重载歧义、模板推导）。但学 C/C++ 的人迟早会问一个更底层的问题：

if (p) 这行代码到了 CPU 上到底是什么？nullptr、NULL、0 三种写法在机器层面有区别吗？

答案先说：没有区别——三种写法编出来的机器码逐字节相同。C++ 的类型系统（std::nullptr_t、重载决议）是编译期的事；到了汇编层，空指针就是数值 0，判空就是判零，和 C 走完全相同的硬件路径。

本文所有汇编均为实测（clang 23.1.0，macOS arm64；x86-64 为同编译器交叉生成）。

这节讲什么

  1. C++ 三种判空写法的汇编对照——证明 std::nullptr_t 是零开销抽象
  2. C 与 C++ 的 if (p) 汇编一致性——语言不同，硬件路径相同
  3. NULL 在本机的真实定义，以及 g(NULL) 直接编译失败的实测（比 Item 8 说的"误选 int"更糟）
  4. 重载决议实测：g(0) / g(nullptr) 各选了谁
  5. 0 页保护对 C++ 一视同仁：解引用 nullptr 照样 SIGSEGV

核心机制

实测 1：三种写法，同一份机器码

测试源码：

int f_if_p(int *p)       { if (p)            return 1; return 0; }
int f_eq_nullptr(int *p) { if (p == nullptr) return 1; return 0; }
int f_eq_NULL(int *p)    { if (p == NULL)    return 1; return 0; }

ARM64（clang -O1）实测输出：

__Z6f_if_pPi:                   // if (p)
    cmp  x0, #0
    cset w0, ne
    ret

__Z12f_eq_nullptrPi:            // if (p == nullptr)
    cmp  x0, #0
    cset w0, eq
    ret

__Z9f_eq_NULLPi:                // if (p == NULL)
    cmp  x0, #0
    cset w0, eq
    ret

三个函数体完全相同（只有 if(p) 的 ne 与另两个的 eq 是语义取反）。x86-64 同样：

_Z6f_if_pPi:                    # if (p)
    xorl  %eax, %eax
    testq %rdi, %rdi            # 判零：p AND p
    setne %al
    retq

_Z12f_eq_nullptrPi:             # if (p == nullptr)
    xorl  %eax, %eax
    testq %rdi, %rdi            # 一模一样
    sete  %al
    retq

结论：nullptr 的类型安全性在运行期成本为零。 std::nullptr_t 的全部价值发生在编译期（重载决议、模板推导），编完就消失了。

实测 2：C 与 C++ 的 if (p) 汇编一致

同一份 int f_if_p(int *p) { if (p) return 1; return 0; }：

语言 x86-64 -O1 ARM64 -O1
C testq %rdi,%rdi; setne %al cmp x0,#0; cset w0,ne
C++ testq %rdi,%rdi; setne %al cmp x0,#0; cset w0,ne

逐字节相同（除符号名 mangling）。CPU 不认识 C 也不认识 C++，只认识 64 位二进制数。

实测 3：g(NULL) 在本机直接编译失败

Item 8 说 g(NULL) "可能误选 g(int)"。macOS arm64 + clang 23.1.0 实测更狠——根本编译不过：

#include <cstdio>
void g(int)   { puts("g(int)"); }
void g(char*) { puts("g(char*)"); }

int main() {
    g(0);        // OK：g(int)
    g(NULL);     // ❌ error: call to 'g' is ambiguous
    g(nullptr);  // OK：g(char*)
}

编译器报错原文：

error: call to 'g' is ambiguous
note: candidate function: void g(int)
note: candidate function: void g(char*)

根因在本机 NULL 的定义：

$ echo | clang++ -E -dM -x c++ -include cstdio - | grep "define NULL"
#define NULL __DARWIN_NULL        # C++ 模式下展开为 clang 内建 __null

__null 是个"半指针半整数"的内建常量——到 int 和到 char* 的转换序列评级相同，重载决议无法裁决 → 歧义错误。也就是说在不同平台上 NULL 的命运有三种：误选 int（Linux 传统 0L）、编译失败（macOS __null）、碰巧正确——只有 nullptr 在所有平台上行为一致。

实测 4：重载决议

去掉 NULL 行后运行实测（本机 arm64）：

g(0)        → g(int)      ✅ 0 是 int 字面量，精确匹配整型重载
g(nullptr)  → g(char*)    ✅ nullptr 只能转指针，匹配指针重载

实测 5：解引用空指针，C++ 一样崩

int main(void) { int *p = (int*)0; return *p; }

本机运行实测：exit=139（= 128 + SIGSEGV(11)）。macOS arm64 的 __PAGEZERO 段把低 4GB 地址全部保留不映射，nullptr 解引用第一步就踩进陷阱。0 页保护对 C 和 C++ 一视同仁——它是 OS 页表设计，不认语言。

硬件路径全景

if (p)  /  if (p == nullptr)  /  if (p == NULL)     ← C++ 源码（三选一）
  ↓ 编译期：std::nullptr_t 类型检查、重载决议（C++ 特有，零运行开销）
  ↓
testq %rdi, %rdi  /  cmp x0, #0                     ← 汇编：判零
  ↓
ZF/Z 标志 → setne/sete / 条件跳转                    ← CPU 执行
─────────────────────────────────
*p（解引用）→ 地址 0 → __PAGEZERO / mmap_min_addr 无映射 → SIGSEGV

常见错误（新手踩坑）

错误 1：以为 nullptr 判空比 NULL 慢

if (p == nullptr) { ... }   // 有人担心"类型安全有代价"

事实： 实测 1 证明三种写法机器码逐字节相同。类型安全是编译期属性，运行期零开销。

错误 2：跨平台代码用 NULL 传空指针给重载函数

register_cb(NULL);   // Linux：可能静默选错；macOS：直接编译失败

修正： 一律 register_cb(nullptr);——全平台行为一致。

错误 3：以为 if (p) 会访问 p 指向的内存 事实： 判空只读 p 这个变量本身（在寄存器里），test/cmp 不访存。只有 *p 才访问地址 0。

错误 4：在 C++ 里用 (void*)0 显式模仿 C 的 NULL

int *p = (void*)0;    // ❌ C++ 不允许 void* 隐式转 int*，显式 cast 虽能编过但是恶习

修正： int *p = nullptr;。

新手要点（和 C 的区别）

维度 C C++ 汇编层
空指针写法 NULL（((void*)0)） nullptr（std::nullptr_t） 完全相同
重载歧义 无重载，无此问题 0/NULL 危险，nullptr 安全 编完就消失
模板推导 无模板 nullptr → nullptr_t 正确 编完就消失
判空机器码 test/cmp test/cmp 逐字节相同
解引用崩溃 SIGSEGV（0 页保护） SIGSEGV（同一机制） 完全相同

一句话总结： C++ 的 nullptr 是编译期的类型安全补丁；运行时它和 C 的 NULL 是同一个数值 0，走同一条硬件路径，掉同一个 0 页陷阱。

HFT 关联

  • 热路径判空零成本：if (!order_ptr) return; 编译后就是一条 test+分支，与 C 完全相同——C++ 抽象不带运行期税。
  • 回调注册的类型安全：set_handler(nullptr) 清除回调在所有平台行为一致；set_handler(NULL) 在 macOS 上编译失败、在 Linux 上可能静默选错——跨平台 HFT 基础设施代码必须 nullptr。
  • 模板工厂：template<class T> T* create() { return nullptr; } 推导正确，且 nullptr 编出的返回代码就是 xorl %eax,%eax; retq（x86）/ mov x0, xzr; ret（ARM64）——零开销。
  • 与 C 库互操作：DPDK（C 库）返回的 rte_mbuf* 在 C++ 侧判空用 if (mbuf == nullptr) 与 C 侧 if (mbuf == NULL) 生成相同代码，混写无性能顾虑。

自测题

  1. if (p)、if (p == nullptr)、if (p == NULL) 三种写法的汇编有区别吗？std::nullptr_t 的开销发生在什么时候？
  2. 本机（macOS + clang）g(NULL) 在 void g(int); void g(char*); 重载集里的结果是什么？为什么比"误选 g(int)"更能说明问题？
  3. C 的 if (p) 和 C++ 的 if (p) 汇编一致吗？这说明 CPU 层面"指针"是什么？
  4. __DARWIN_NULL 展开为什么？它导致重载歧义的机制是什么？
  5. 解引用 nullptr 的退出码 139 是怎么算出来的？macOS arm64 的低地址保护范围比 Linux 大多少倍？
参考答案

  1. 没有区别，实测逐字节相同（cmp x0, #0 / testq %rdi, %rdi）。std::nullptr_t 的开销发生在编译期：类型检查、重载决议、模板推导都在编译时完成，编完类型信息就消失了，运行时它就是一个 64 位全 0 的数值。这是 C++"零开销抽象"原则的典型样本。

  2. 直接编译失败（error: call to 'g' is ambiguous）。这比"误选 g(int)"更能说明问题：NULL 的行为依赖平台——Linux 传统定义（0L）下静默选错（最危险，不报错），macOS 定义（__null）下编译失败（走运，能发现）。同一份代码换个平台从"编不过"变成"悄悄错"，只有 nullptr 全平台一致。

  3. 完全一致（除符号名 mangling 外逐字节相同：testq %rdi, %rdi; setne %al）。说明 CPU 层面没有"指针"概念，只有二进制数——指针判空与整数判零是同一条硬件路径，语言层的指针类型系统在汇编层不复存在。

  4. __DARWIN_NULL 在 C++ 模式下展开为 clang 内建常量 __null。它是"半整数半指针"的魔法值：到 int 的转换与到 char* 的转换重载评级相同，编译器无法裁决 → ambiguity error。设计初衷是让 NULL 误用时更容易报错（相比 0L），但代价是语义仍然不精确。

  5. 139 = 128 + 11，其中 11 是 SIGSEGV 的信号编号（shell 对"被信号杀死"的进程约定退出码 = 128 + 信号号）。macOS arm64 用 __PAGEZERO 保留低 4GB，Linux 默认 mmap_min_addr 保留低 64KB——前者是后者的 65536 倍（4GB / 64KB = 2³² / 2¹⁶ = 2¹⁶）。更大的保留区还能抓住"空指针 + 大偏移"（如 p->field，field 偏移数 MB）这类野访问。

Item 9：优先 using 别名而非 typedef

第 3 章 移步现代 C++ · Item 9 · 上一节：Item 8 nullptr

为什么要学这个（先建立直觉）

C 程序员对 typedef 再熟不过：typedef unsigned long ulong;、typedef void (*Callback)(int);——给长类型起短名，天经地义。到了 C++，这套东西还能用，但会遇到一面墙：模板。

假设你写了一个自定义分配器，想让代码里的 vector 默认走内存池。你要的不是一个别名，而是一族别名——PoolVec<int>、PoolVec<Order>……typedef 在这里直接缴械：C++ 语法里根本不存在"模板 typedef"这种东西，想模板化只能包一层 struct 再取 ::type，用起来还得带 typename，又丑又绕。

C++11 的 using 把这面墙拆了：template<class T> using PoolVec = std::vector<T, MyAlloc<T>>; 一行搞定。顺手还解决了可读性问题——using Callback = void(*)(int); 从左往右读，名字就在等号左边，不像 typedef void (*Callback)(int); 把名字埋在星号括号堆里。

这节讲什么

  1. using 与 typedef 的逐条对照（普通别名二者等价）；
  2. 别名模板：using 独有的能力，typedef 的 struct+::type 绕行方案（附实测报错）；
  3. C++14 类型萃取 _t 后缀（std::add_pointer_t 等）的由来——它就是别名模板；
  4. 全部论断本机实测：clang 23.1.0，arm64-apple-darwin，libc++。

typedef vs using 逐条对照

维度 typedef using
普通别名 typedef unsigned long ulong; using ulong = unsigned long;（语义完全等价）
函数指针 typedef void (*Cb)(int); 名字埋中间 using Cb = void(*)(int); 名字在左边
模板别名 做不到（语法不存在） template<class T> using V = ...;
模板元编程 必须包 struct + typename ...::type 直接实例化
依赖类型语境 要 typename 同样要 typename（无差异）
引入版本 从 C 继承 C++11

普通别名上两者编译产物完全相同——选 using 不花一分钱，纯赚可读性和模板化能力。

普通别名：语法方向的差别

#include <string>

typedef unsigned long ulong_td;
using ulong_using = unsigned long;

// 函数指针是分水岭
typedef void (*Callback_td)(int, const std::string&);   // 名字藏在 (*...) 里
using Callback_using = void(*)(int, const std::string&); // 名字在最左，类型在最右

typedef 的声明方向和 C 一致："类型 名字"，遇到函数指针、数组就拧巴——名字被类型包在中间，读的时候要拆括号。using 是赋值式语法：新名 = 类型，和 auto x = expr; 的阅读方向一致，读长类型时视线不用来回跳。

别名模板：using 独有的能力

typedef 直接阵亡

#include <vector>

template<typename T>
typedef std::vector<T> Vec;    // 想给 vector<T> 起模板别名

int main() { Vec<int> v; }

本机实测 clang 23.1.0 报错原文（-std=c++17）：

error: a typedef cannot be a template
    4 | typedef std::vector<T> Vec;
      |                        ^
error: no template named 'Vec'

没有商量的余地：typedef 在语法上就不接受模板参数。

typedef 时代的绕行：struct + ::type

C++11 之前想达到同样效果，只能把 typedef 塞进 struct：

template<typename T>
struct Vec_t {
    typedef std::vector<T, MyAlloc<T>> type;
};

Vec_t<int>::type v;                    // 非模板语境
typename Vec_t<T>::type w;             // 模板语境还要加 typename

两个负担：使用点要写 ::type；在模板里使用还得加 typename（因为 Vec_t<T>::type 是依赖类型，编译器不知道它是类型还是静态成员）。

using 一步到位

template<typename T>
using Vec = std::vector<T, MyAlloc<T>>;

Vec<int> v1{1, 2, 3};            // 直接用，没有 ::type，没有 typename
Vec<std::string> v2;             // 每个实例化都自动带 MyAlloc

实测对比（clang 23.1.0，完整代码见下文"完整可运行例子"）：

v1.size()=3 v2.size()=3 v3.size()=1

static_assert(std::is_same_v<Vec<int>, typename Vec_t<int>::type>); 通过——两条路线产出完全相同的类型，差别全在书写和使用体验。

C++14 的 _t 后缀：别名模板的最佳广告

C++11 的类型萃取用起来很啰嗦：

typename std::remove_reference<T>::type   // C++11：三步走

remove_reference<T> 是模板，::type 取结果，typename 声明依赖类型——三个噪声一个都不能少。C++14 标准库给每个萃取都配了 _t 后缀的别名模板：

template<class T>
using remove_reference_t = typename remove_reference<T>::type;  // 标准库里就这行

使用变成一行：

std::remove_reference_t<T>        // C++14：干净
std::add_pointer_t<int> p = nullptr;   // p 是 int*

本机实测（clang 23.1.0）：

  • -std=c++11 下 std::add_pointer_t<int> 报错：error: no member named 'add_pointer_t' in namespace 'std'
  • -std=c++14 起编译通过，static_assert(std::is_same_v<decltype(p), int*>) 成立。

_t 后缀的本质就是别名模板——C++11 有 using 之后，标准库才有条件把这些便利别名批量铺出来。你自己写元编程时也该照办：每个 struct Foo { typedef ... type; }; 旁边跟一个 template<class T> using Foo_t = typename Foo<T>::type;。

完整可运行例子

#include <vector>
#include <memory>
#include <iostream>
#include <type_traits>

// 合法的自定义分配器（满足 rebind 要求，能过 libc++ 的 static_assert）
template<typename T>
struct MyAlloc {
    using value_type = T;
    MyAlloc() = default;
    template<typename U> MyAlloc(const MyAlloc<U>&) {}
    T* allocate(std::size_t n) { return std::allocator<T>{}.allocate(n); }
    void deallocate(T* p, std::size_t n) { std::allocator<T>{}.deallocate(p, n); }
};
template<typename T, typename U>
bool operator==(const MyAlloc<T>&, const MyAlloc<U>&) { return true; }
template<typename T, typename U>
bool operator!=(const MyAlloc<T>&, const MyAlloc<U>&) { return false; }

// typedef 路线：包 struct + ::type
template<typename T>
struct Vec_t { typedef std::vector<T, MyAlloc<T>> type; };

// using 路线：别名模板一步到位
template<typename T>
using Vec = std::vector<T, MyAlloc<T>>;

typedef void (*FP_td)(int, double);      // 名字藏在中间
using FP_using = void(*)(int, double);   // 名字在左边

void handler(int, double) {}

int main() {
    Vec<int> v1{1, 2, 3};                  // using 直接用
    typename Vec_t<int>::type v2{1, 2, 3}; // typedef 要带 ::type
    Vec_t<double>::type v3;
    v3.push_back(1.5);

    FP_td f1 = handler;
    FP_using f2 = handler;
    f1(1, 2.0); f2(1, 2.0);

    static_assert(std::is_same_v<Vec<int>, typename Vec_t<int>::type>);
    std::cout << "v1.size()=" << v1.size()
              << " v2.size()=" << v2.size()
              << " v3.size()=" << v3.size() << "\n";

    std::add_pointer_t<int> p = nullptr;   // C++14 的 _t 后缀
    static_assert(std::is_same_v<decltype(p), int*>);
    std::cout << "add_pointer_t<int> is int*: ok\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

v1.size()=3 v2.size()=3 v3.size()=1
add_pointer_t<int> is int*: ok

一个顺手的坑：自定义分配器如果直接 struct MyAlloc : std::allocator<T> {}，libc++ 实测会拒绝——[allocator.requirements] states that rebinding an allocator to the same type should result in the original allocator。继承来的 rebind 给出的是 std::allocator<U> 而非 MyAlloc<U>，违反 rebind 必须回到自身的要求。正确姿势如上面的独立实现（或显式提供 template<class U> struct rebind）。

常见错误（新手踩坑）

  1. 试图写模板 typedef。template<class T> typedef std::vector<T> Vec; 实测报 error: a typedef cannot be a template。修正：换 using。
  2. typedef 绕行方案忘了 typename。模板里写 Vec_t<T>::type v; 报依赖类型错误。修正：typename Vec_t<T>::type v;——或者干脆别绕行，用 using。
  3. C++11 项目里用 _t 后缀。std::add_pointer_t 等是 C++14 才有的，实测 -std=c++11 报 no member named 'add_pointer_t'。修正：C++11 下自己补一行 template<class T> using add_pointer_t = typename std::add_pointer<T>::type;。
  4. 以为 using 和 typedef 生成的类型有差别。没有——别名不产生新类型，Vec<int> 和 std::vector<int, MyAlloc<int>> 是同一个类型，static_assert(is_same_v<...>) 实测通过。要"真·新类型"得用 enum class、强类型包装 struct 等别的技术。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
类型别名 typedef using 语法直观，支持模板
模板别名 不适用（C 无模板） template<class T> using X = ... typedef 语法上做不到
函数指针别名 typedef void (*F)(int); using F = void(*)(int); 名字在左边，一眼可读

一句话总结： C 程序员把 typedef 全部换成 using 就行，语法是 using 新名 = 原类型;，从左到右读，和 auto 一样自然——还白捡模板化能力。

HFT 关联

  • 内存池容器别名：template<class T> using PoolVec = std::vector<T, PoolAlloc<T>>; 让"所有容器走对象池"这条纪律变成一行别名，策略代码里 PoolVec<Level> 比 std::vector<Level, PoolAlloc<Level>> 少一个数量级的视觉噪声。
  • 回调签名集中管理：using TickCallback = void(*)(const Tick&, SeqNo); 改签名只改一处；typedef 写法在函数指针上可读性差，评审时容易漏看参数。
  • 编译期计算的 _t 风格：低延迟代码常用类型萃取做编译期分派（if constexpr (std::is_trivially_copyable_v<T>)），自己写萃取时顺手提供 _t/_v 别名，调用点才不会被 typename ...::type 淹没。
  • ABI 注意：别名不改类型，PoolVec<int> 的 mangled name 仍含分配器类型——跨库边界改分配器就是改 ABI，别名让这件事看起来没变，部署时要清醒。

自测题

1. using X = Y; 和 typedef Y X; 生成的类型有差别吗？

答案

没有，语义完全等价，都是给既有类型起别名、不产生新类型。实测 static_assert(std::is_same_v<Vec<int>, typename Vec_t<int>::type>) 通过。差别只在可读性和模板化能力。

2. 为什么 typedef 不能定义别名模板？

答案

typedef 的语法是"为已确定的类型起名"，没有放置模板参数列表的位置。实测 template<class T> typedef std::vector<T> Vec; 报 error: a typedef cannot be a template。using 的"名字 = 类型"语法天然可以在前面加 template<...> 形成别名模板。

3. typedef 想达到别名模板的效果怎么办？代价是什么？

答案

包一层 struct：template<class T> struct Vec_t { typedef ... type; };。代价：使用点要写 ::type，模板语境还要加 typename（typename Vec_t<T>::type），可读性和书写都更繁琐。

4. using Callback = void(*)(int); 比 typedef void (*Callback)(int); 好在哪？

答案

可读性：using 名字在最左、类型在最右，与 auto x = expr 同向；typedef 把名字埋进 (*...) 里，函数签名越复杂越难拆。二者生成的类型完全相同。

5. C++14 的 std::remove_reference_t 是怎么来的？C++11 下怎么办？

答案

它就是标准库里的一行别名模板：template<class T> using remove_reference_t = typename remove_reference<T>::type;。C++11 没有这些 _t 别名（实测 add_pointer_t 报 no member named），需要自己用 using 补定义。

6. 模板里 using VT = Container::value_type; 能直接写吗？

答案

不能。Container::value_type 是依赖类型，必须写 using VT = typename Container::value_type;。using 不豁免 typename——依赖类型的 typename 要求与 typedef 相同（C++20 起部分语境可省略）。

Item 10：优先限定作用域枚举（enum class）

第 3 章 移步现代 C++ · Item 10 · 上一节：Item 9 using

为什么要学这个（先建立直觉）

C 的 enum 用起来很顺手，但它在 C++ 里有三个陈年旧伤：

enum Color { Red, Green, Blue };
enum Direction { Up, Down, Left, Right };

int x = Red;            // 枚举名直接泄进外层作用域
if (Red == Up) {}       // 编译通过！两个不同枚举的值都悄悄转成 int 再比较

第一，命名污染：枚举名 Red、Up 全部注入外围作用域，再写一个 enum Traffic { Red, Yellow }; 就是重定义错误——大项目里你不得不用 COLOR_RED、DIR_UP 这种前缀土法隔离。第二，隐式转整型：枚举和 int 之间没有任何防火墙，Red == Up（都是 0）这种语义荒谬的比较编译器一声不吭。第三，不能前向声明：底层类型由编译器在看完所有枚举值之后才定，头文件里没法只写个声明。

C++11 的 enum class（限域枚举）把三个伤一次治好：枚举名关进枚举自己的作用域、禁止隐式转整型、底层类型默认 int 所以随时可前向声明。代价只是多敲 Color:: 四个字符。

这节讲什么

  1. enum vs enum class 的逐条对照（命名泄漏、隐式转换、前向声明、底层类型）；
  2. std::underlying_type_t 取底层类型的正确姿势；
  3. 前向声明规则：scoped 直接声明，unscoped 必须指定底层类型（附实测报错）；
  4. 全部论断本机实测：clang 23.1.0，arm64-apple-darwin，libc++，-std=c++17 -Wall。

enum vs enum class 总览对比

特性 enum（unscoped） enum class（scoped）
枚举名作用域 泄漏到外层作用域 限定在枚举内，必须 Color::Red
隐式转整型 允许 禁止，必须 static_cast
不同枚举间比较 允许（都转成 int） 禁止（编译错误）
默认底层类型 编译器自选（不大于 int 且装得下） int（固定）
显式指定底层类型 C++11 起可以 可以
前向声明 必须指定底层类型 直接可以（默认 int 已知）

命名泄漏：实测重定义

enum Color { Red, Green, Blue };
enum Traffic { Red, Yellow };   // 同作用域

int main() { return Red; }

本机实测 clang 23.1.0 报错原文：

error: redefinition of enumerator 'Red'
    2 | enum Traffic { Red, Yellow };
      |                ^
note: previous definition is here
    1 | enum Color { Red, Green, Blue };
      |              ^

unscoped 枚举的枚举名住在外层作用域，两个枚举撞名就是硬错误。换成 enum class，Color::Red 和 Traffic::Red 各住各家，互不干扰——连跨类型比较都被拦下：

enum class Color { Red, Green, Blue };
enum class Traffic { Red, Yellow };

auto a = Color::Red;
auto b = Traffic::Red;
return a == b;   // 报错

实测报错：

error: invalid operands to binary expression ('Color' and 'Traffic')
note: no implicit conversion for scoped enum; consider casting to underlying type

unscoped 版本里这个比较会静默通过（都转成 int）——Red == Up 这种笑话就是从这里来的。

隐式转换：有和没有防火墙

enum class Side { Buy, Sell };

int main() {
    Side s = Side::Buy;
    int x = s;            // 编译失败
    return x;
}

本机实测 clang 23.1.0 报错原文：

error: cannot initialize a variable of type 'int' with an lvalue of type 'Side'
    int x = s;
        ^   ~

要转换就显式写出来：

int x = static_cast<int>(s);              // OK，x = 0
Side s2 = static_cast<Side>(1);           // 反向也要显式
if (s == Side::Buy) {}                    // 同类比较 OK
// if (s == 0) {}                         // 编译失败：无内建运算符

这道防火墙的工程价值：Side::Buy == 1 这种把语义比较写成数值比较的 bug，在编译期就被消灭。下单方向的枚举值和协议里的 int 字段永远不会被意外混用。

底层类型与前向声明

scoped 枚举默认底层类型是 int，且可随时前向声明；unscoped 枚举只有显式指定底层类型后才能前向声明：

#include <cstdint>

enum class Side;                 // OK：scoped 默认 int，类型完整
enum Legacy : std::uint8_t;      // OK：unscoped 但指定了底层类型
// enum Old;                     // 报错！unscoped 未指定底层类型

void useSide(Side s);            // 只凭声明就能用
void useLegacy(Legacy l);

enum Old; 的实测报错原文：

error: ISO C++ forbids forward references to 'enum' types
    2 | enum Old;
      |      ^

前向声明的意义不只是少 include 一个头文件：底层类型固定后，枚举的大小和 ABI 就锁死了——枚举值增删不需要重编译所有使用者，二进制接口也不会漂移。

sizeof 实测（clang 23.1.0）：

enum Color { Red, Green, Blue };              // unscoped
enum class Side { Buy, Sell };                // scoped，默认 int
enum class Status : unsigned char {           // 显式 1 字节
    Pending = 0, Active = 1, Closed = 255
};
// sizeof(Color) == 4   sizeof(Side) == 4   sizeof(Status) == 1

std::underlying_type_t：和底层类型打交道

scoped 枚举不能隐式转整型，代码里就少不了"取底层类型"的操作。手写 static_cast<int> 会把类型写死，换成萃取：

#include <type_traits>

auto raw = static_cast<std::underlying_type_t<Status>>(Status::Closed);
// raw 的类型自动是 unsigned char，改底层类型不用改调用点

本机实测断言通过：

static_assert(std::is_same_v<std::underlying_type_t<Side>, int>);
static_assert(std::is_same_v<std::underlying_type_t<Status>, unsigned char>);

（underlying_type_t 是 C++14 的 _t 别名，C++11 要写 typename std::underlying_type<T>::type——正是 Item 9 讲的那套。）

完整可运行例子

#include <cstdint>
#include <iostream>
#include <type_traits>

enum Color { Red, Green, Blue };          // unscoped
enum class Side { Buy, Sell };            // scoped，默认 int
enum class Status : unsigned char { Pending = 0, Active = 1, Closed = 255 };

int main() {
    int r = Red;                            // unscoped 隐式转 int
    std::cout << "Red=" << r << "\n";

    Side s = Side::Buy;
    // int x = s;                           // error: 不能隐式转
    std::cout << "static_cast<int>(Side::Buy)=" << static_cast<int>(s) << "\n";

    std::cout << "sizeof(Color)=" << sizeof(Color) << "\n";
    std::cout << "sizeof(Side)=" << sizeof(Side) << "\n";
    std::cout << "sizeof(Status)=" << sizeof(Status) << "\n";

    static_assert(std::is_same_v<std::underlying_type_t<Side>, int>);
    static_assert(std::is_same_v<std::underlying_type_t<Status>, unsigned char>);

    auto raw = static_cast<std::underlying_type_t<Status>>(Status::Closed);
    std::cout << "Status::Closed raw=" << static_cast<int>(raw) << "\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

Red=0
static_cast<int>(Side::Buy)=0
sizeof(Color)=4
sizeof(Side)=4
sizeof(Status)=1
Status::Closed raw=255

常见错误（新手踩坑）

  1. 忘了写作用域限定。enum class Side { Buy, Sell }; Side s = Buy; 编译失败——枚举名不外泄本来就是特性。修正：Side::Buy。
  2. 拿枚举值和整数直接比较。if (s == 0) 报 invalid operands 类错误。修正：if (s == Side::Buy)，语义上你也该和枚举值比而不是和魔法数字比。
  3. static_cast<int> 把底层类型写死。枚举改成 uint8_t 后所有调用点 silently 语义漂移。修正：static_cast<std::underlying_type_t<E>>(e)。
  4. unscoped enum 想前向声明却没指定底层类型。实测报 ISO C++ forbids forward references to 'enum' types。修正：enum E : std::uint8_t;，或者直接换 enum class。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
枚举声明 enum Color { Red, Green }; enum class Color { Red, Green }; 防命名污染
访问枚举值 Red Color::Red 限定作用域
和整数互转 隐式 必须 static_cast 类型安全
前向声明 不行 scoped 直接声明 减少编译依赖、锁死 ABI

一句话总结： C 程序员记住——新代码全用 enum class，除非要和 C API 互操作或者写位标志（A | B 这类运算 unscoped 更方便）。多打的 Color:: 前缀换来的是编译期类型安全。

HFT 关联

  • 订单状态机：enum class OrderState : uint8_t { Pending, PartiallyFilled, Filled, Cancelled };——1 字节存储、不能和整数误比较、switch 配 -Wall 漏分支会警告。三个特性全是白捡的。
  • 协议字段锁死大小：FIX/ITCH 报文里的标志字段用 enum class Tag : uint32_t，sizeof 可预测，序列化时 static_cast<std::underlying_type_t<Tag>>(t) 直接写进缓冲区，布局即 ABI。
  • 缓存友好：百万级订单簿条目里，状态字段从 4 字节压到 1 字节（指定 uint8_t），配合 alignas 能把热数据多塞 30%+ 进缓存行——前提是底层类型显式可控，unscoped enum 给不了这个保证。
  • 前向声明减编译依赖：交易所接口头文件只声明 enum class Side : uint8_t;，枚举值增删不触发下游重编译——对几十个子模块的 HFT 代码库是实打实的编译时间节省。

自测题

1. enum 和 enum class 的三个主要区别是什么？

答案

① 作用域：enum class 的枚举名限定在枚举内（Side::Buy），unscoped 泄漏到外层作用域；② 类型安全：enum class 不隐式转整型、不能和整数比较，unscoped 会隐式转；③ 前向声明：enum class 默认底层类型 int 可直接前向声明，unscoped 必须显式指定底层类型才行。

2. 为什么 enum class 能前向声明而 unscoped enum 不能（不指定底层类型时）？

答案

前向声明要求编译器在看不到枚举值列表时就知道类型的大小。enum class 底层类型默认 int，大小已知；unscoped enum 的底层类型要看完所有枚举值才能确定（取能装下的最小类型、不大于 int），大小未知所以不能声明。实测 enum Old; 报 error: ISO C++ forbids forward references to 'enum' types。

3. enum class Side { Buy, Sell }; Side s = Side::Buy; int x = s; 能编译吗？

答案

不能。实测报 error: cannot initialize a variable of type 'int' with an lvalue of type 'Side'。scoped 枚举到整型没有隐式转换，必须 static_cast——这就是它防止"枚举和整数误比较"类 bug 的机制。

4. enum class Status : uint8_t 显式指定底层类型有什么好处？

答案

① 控制大小：sizeof(Status)==1，协议字段和大规模数组省内存、提高缓存命中率；② ABI 稳定：布局锁死，枚举值增删不影响二进制接口；③ 可前向声明：减少编译依赖。unscoped enum 不指定时大小由编译器选，给不了这些保证。

5. 怎么把一个 scoped 枚举值转成它的底层类型值，且不写死类型名？

答案 
auto raw = static_cast<std::underlying_type_t<Side>>(s);

underlying_type_t（C++14；C++11 写 typename std::underlying_type<T>::type）在编译期取出枚举的底层类型，枚举改底层类型时调用点零改动。

6. 什么场景下仍应该用传统 unscoped enum？

答案

需要隐式转整型的场合：位标志组合（flags & A、A | B 不想到处 cast）、作为数组下标、喂给只接受 int 的 C API；以及刻意想让枚举名注入外层作用域做"命名的常量组"（如放进 struct 里模拟 scoped 效果的老技巧）。

Item 11：优先使用 =delete 而非 private 未定义

第 3 章 移步现代 C++ · Item 11 · 上一节：Item 10 scoped enum

为什么要学这个（先建立直觉）

C++ 经常需要表达"这个操作不许用"：不可拷贝的锁、不可赋值的连接句柄、不接受 double 的整数函数。C++98 时代的惯用法是把函数声明为 private 且不定义——编译器看到 private 会拦外部调用，没定义所以链接器拦内部调用。这套"组合拳"能用，但处处别扭：

第一，错误暴露得晚。外部调用确实编译期就报"private 访问"，但成员函数和友元里的调用能过编译，错误要等到链接期才炸——Undefined symbols 这种报错离真正的错误现场（哪行代码试图拷贝）隔了十万八千里。第二，手法只适用于成员函数。想禁掉一个普通函数的错误重载（比如 isLucky(double)），private 根本不适用。第三，意图藏得深：读代码的人要同时注意到"private + 没有定义"两个事实才能看懂设计意图。

C++11 的 = delete 把"禁用"变成一等语法：任何函数（成员、非成员、模板实例化）都能在声明处直接标记删除，所有调用——不管来自哪里——都在编译期得到一条清晰的 call to deleted function 报错。

这节讲什么

  1. C++98 private 未定义手法的链接期报错 vs = delete 的编译期报错（附两边实测原文）；
  2. = delete 删非成员函数：isLucky 挡 bool/char/浮点的实战；
  3. = delete 删模板实例化（private 手法做不到的）；
  4. 规则细节：= delete 必须出现在首次声明处；
  5. 全部论断本机实测：clang 23.1.0，arm64-apple-darwin，libc++，-std=c++17 -Wall。

核心对决：链接期报错 vs 编译期报错

C++98 手法：错误在链接期才爆

class Widget {
public:
    Widget() {}
    void touch(const Widget& other) {
        Widget copy(other);   // 成员函数有权访问 private → 编译期放行
        (void)copy;
    }
private:
    Widget(const Widget&);    // 只声明，不定义
};

int main() {
    Widget a;
    a.touch(a);
}

本机实测 clang 23.1.0：编译全部通过，链接期才报错：

Undefined symbols for architecture arm64:
  "Widget::Widget(Widget const&)", referenced from:
      Widget::touch(Widget const&) in emcA_item11_cpp98-23ed8d.o
ld: symbol(s) not found for architecture arm64
clang++: error: linker command failed with exit code 1

报错只告诉你"缺 Widget::Widget(Widget const&) 的定义"，至于这条调用从哪来、是故意禁用还是忘了实现，全靠自己查。而且这条路径绕过了编译期检查——意味着"禁拷贝"的纪律对成员和友元是漏的。

= delete：编译期、指名道姓

class Widget {
public:
    Widget() {}
    Widget(const Widget&) = delete;   // 声明处直接禁用
    void touch(const Widget& other) {
        Widget copy(other);
        (void)copy;
    }
};

本机实测 clang 23.1.0 报错原文：

error: call to deleted constructor of 'Widget'
    Widget copy(other);
           ^    ~~~~~
note: 'Widget' has been explicitly marked deleted here
    Widget(const Widget&) = delete;
    ^

对比一目了然：编译期而非链接期；报错直接指出"调用了被显式删除的函数"并给出删除位置；成员函数、友元、外部调用一视同仁，没有漏网之鱼。

维度 private 未定义（C++98） = delete（C++11）
报错时机 外部调用编译期；成员/友元调用链接期 一律编译期
报错信息 Undefined symbols，不指向意图 call to deleted function，指向删除处
适用范围 仅成员函数 任何函数：成员、非成员、模板实例化
意图表达 靠"private + 不定义"两个暗示 声明处一行，一目了然

删非成员函数：isLucky 实战

private 手法管不了自由函数，但自由函数恰恰最需要"禁用某些重载"——隐式转换会把你没想服务的类型吸进来：

bool isLucky(int number) { return number == 7; }
bool isLucky(char) = delete;      // 挡 char（否则 'a' 隐式转 int）
bool isLucky(bool) = delete;      // 挡 bool（否则 true 隐式转 1）
bool isLucky(double) = delete;    // 挡 double/float（否则 3.5 截断成 3）

本机实测 clang 23.1.0，isLucky('a') 报错：

error: call to deleted function 'isLucky'
    return isLucky('a');
           ^~~~~~~
note: candidate function has been explicitly deleted
    bool isLucky(char) = delete;
         ^

isLucky(3.5f) 同样被拦——float 没有精确匹配，float→double（浮点转换）优先级高于 float→int（浮点-整型转换），重载决议选中 isLucky(double)，正好撞上 = delete：

error: call to deleted function 'isLucky'
    return isLucky(3.5f);
           ^~~~~~~
note: candidate function has been explicitly deleted
    bool isLucky(double) = delete;
         ^

删掉一个 double 重载，顺手把 float 也挡了——这是利用重载决议规则"借力打力"：被删除的函数参与重载决议（可能比别人更匹配），只是选中即报错。

删模板实例化：private 手法做不到的

void* 能装任何对象指针，但有些接口不接受它（void* 丢掉了类型信息，函数体没法处理）。private 对模板特化无能为力，= delete 可以：

template<typename T>
void processPointer(T* ptr) { /* ... */ }

template<>
void processPointer<void>(void*) = delete;

template<>
void processPointer<const void>(const void*) = delete;

实测：processPointer(&x)（int*）正常走主模板输出 processPointer<T>；processPointer(vp)（void*）编译失败，报 call to deleted function。同理还能删 char*/const char* 实例化，防止"字符串指针混进只接受对象指针的泛型接口"。

规则细节：= delete 必须在首次声明处

= delete 不能像普通定义那样"类内声明、类外补"：

class Widget {
public:
    Widget();
    Widget(const Widget&);          // 首次声明没带 = delete
};
Widget::Widget(const Widget&) = delete;   // 类外补：报错

本机实测 clang 23.1.0 报错原文：

error: deleted definition must be first declaration
    Widget::Widget(const Widget&) = delete;
                                    ^
note: previous declaration is here
    Widget(const Widget&);
    ^

理由很实在：编译器必须在第一次看到函数声明时就知道它被删了，这样后面的每次调用才能立刻诊断；如果允许事后补删，调用点的合法性会随声明顺序变化，两阶段查找会变成噩梦。

顺带一句 = default：C() = default; 让编译器生成默认实现且不算"用户提供"，从而保持 trivial 性质（可 memcpy、可 constexpr），而手写 C() {} 会破坏它——详见 Item 17 特殊成员函数的生成规则。

完整可运行例子

#include <iostream>

class Connection {                       // 不可拷贝的连接句柄
public:
    explicit Connection(int fd) : fd_(fd) {}
    Connection(const Connection&) = delete;
    Connection& operator=(const Connection&) = delete;
    Connection(Connection&&) = default;  // 但允许移动
    int fd() const { return fd_; }
private:
    int fd_;
};

bool isLucky(int n) { return n == 7; }
bool isLucky(char) = delete;
bool isLucky(bool) = delete;
bool isLucky(double) = delete;

template<typename T>
void processPointer(T*) { std::cout << "processPointer<T>\n"; }
template<> void processPointer<void>(void*) = delete;

int main() {
    Connection c1(3);
    Connection c2(std::move(c1));        // 移动 OK
    std::cout << "c2.fd=" << c2.fd() << "\n";
    // Connection c3(c2);                // error: call to deleted constructor

    std::cout << "isLucky(7)=" << isLucky(7) << "\n";
    // isLucky('a');   isLucky(true);   isLucky(3.5);   // 全被 delete 拦下

    int x = 0;
    processPointer(&x);                  // OK
    // processPointer((void*)&x);        // error: deleted specialization
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

c2.fd=3
isLucky(7)=1
processPointer<T>

常见错误（新手踩坑）

  1. 类外补 = delete。实测报 error: deleted definition must be first declaration——删除标记必须写在首次声明处，修正：类内声明时直接带上。
  2. 以为被删函数不参与重载决议。恰恰相反：被删函数照常参与，而且可能因为更匹配而"胜出"，然后报 call to deleted function。这正是 isLucky(double) = delete 能顺手挡住 float 的原理，也是新手看到报错时困惑的原因。
  3. 用 private 未定义手法禁模板实例化。办不到——template<> void f<void>(void*); 声明为 private 不影响外部对主模板的实例化路径。修正：template<> void f<void>(void*) = delete;。
  4. 删拷贝构造但忘了拷贝赋值。T(const T&) = delete; 不会连带删 operator=。要禁拷贝就两个都删（或删一个声明一个，见 Item 17 的生成规则联动）。

HFT 关联

  • 句柄类禁拷贝：连接、内存池句柄、独占锁都该 = delete 拷贝构造/赋值——双重 close(fd)、双重 munmap 这类事故在编译期清零。保留 = default 移动语义，所有权转移零成本。
  • 接口收窄防隐式转换：行情解码函数 decode(const ItchMsg&) 旁边删掉 decode(const char*) = delete;，防止原始 buffer 指针被误传后按错误协议解析——低延迟系统里"解析错了但没崩"比崩溃可怕得多。
  • 热路径零开销：= delete 是纯编译期机制，生成的二进制里没有任何痕迹；相比运行时断言（assert(ptr)），它连一个分支都不占。
  • 模板实例化白名单：泛型撮合组件用 = delete 删掉不支持的类型实例化（如 void*、const char*），把"这个模板不是给所有类型用的"从文档注释升级成编译器强制。

自测题

1. C++98 禁拷贝的标准手法是什么？它最大的缺陷是什么？

答案

把拷贝构造/赋值声明为 private 且不定义。缺陷：成员函数和友元里的拷贝能通过编译，错误要到链接期才暴露（实测 Undefined symbols: "Widget::Widget(Widget const&)"），报错不指向错误意图，排查成本高。

2. = delete 相比 private 未定义，报错上有什么优势？

答案

一律编译期报错，且信息明确指向意图：实测 error: call to deleted constructor of 'Widget' + note: 'Widget' has been explicitly marked deleted here。private 手法在成员/友元调用路径上是链接期的 Undefined symbols，不含"被禁用"的语义。

3. isLucky(int) 已存在，为什么要删掉 isLucky(double) 而不是 isLucky(float)？

答案

因为重载决议中 float→double 是浮点转换，优先级高于 float→int 的浮点-整型转换——isLucky(3.5f) 会选中 isLucky(double)。删掉 double 版本后，float 实参撞到被删函数上直接报错（实测 call to deleted function），等于一个 = delete 挡住整个浮点家族。

4. 被 = delete 的函数还参与重载决议吗？

答案

参与。被删函数和其他候选一样进入候选集，甚至可能因更匹配而胜出——胜出后才报 call to deleted function。这是= delete 能用来"收窄重载集"的原理。

5. 怎么禁止某个模板被 void* 实例化？private 能做到吗？

答案

写显式特化并删除：template<> void processPointer<void>(void*) = delete;。private 做不到——它只能限制成员的访问权限，管不住模板的实例化路径。

6. Widget::Widget(const Widget&) = delete; 写在类外会怎样？

答案

编译失败：实测 error: deleted definition must be first declaration。= delete（以及类内 = default）必须出现在函数的首次声明处，编译器要求第一次看到声明就知道函数被删，否则调用点合法性会依赖声明顺序。

7. C() {} 和 C() = default; 对 trivial 性质的影响有何不同？

答案

C() {} 是用户提供的构造函数，使类型失去 trivial 性质（影响 memcpy 合法性与 ABI 传递）；C() = default; 由编译器生成、不算用户提供，成员都 trivial 时类型保持 trivial。详见 Item 17。

Item 12：把重写函数声明为 override

第 3 章 移步现代 C++ · Item 12 · 上一节：Item 11 =default

为什么要学这个（先建立直觉）

C 没有继承和虚函数，但 C 程序员一定理解"函数指针表"——那正是 vtable 的手工版本：

// C 的"多态"模拟
struct Strategy {
    void (*on_tick)(void* self, const Tick* t);
    void (*on_order)(void* self, const Order* o);
};

C++ 的虚函数就是这个模式的语言级支持。但 C++ 有一个 C 没有的坑：你以为重写了基类虚函数，实际可能没有。基类参数是 int，你写成了 double；基类带 const，你漏了——这两种情况在 C++11 之前编译器一声不吭，代码能编译、能链接、能运行，只是运行时多态不生效。

关键在于：这类 bug 只在基类虚函数提供了默认实现时才会静默。如果基类是纯虚函数，漏实现会让派生类仍是抽象类，一实例化就编译报错。真正危险的是那些"有默认实现、改了也不会崩、只是行为不对"的虚函数——override 正是为它们发明的：它让编译器检查是否真的重写了，检查不通过直接编译报错。

这节讲什么

  1. 不加 override 时虚函数"静默失效"的现场，以及它为什么只在基类有默认实现时才静默；
  2. 加 override 后的真实报错原文，逐条对照四种签名不匹配（参数类型 / const / 引用限定符 / 基类非虚）；
  3. final：既挡住重写，又给编译器去虚化（devirtualization）的机会；
  4. 引用限定符 & / &&——override 检查里最容易忽略的一项。

现场：不加 override 时虚函数静默失效

clang 23.1.0，-std=c++17 -Wall，完整可编译：

#include <iostream>

class Base {
public:
    virtual void on_tick(int x) { std::cout << "Base::on_tick(int) " << x << "\n"; }
    virtual ~Base() = default;
};

class Derived : public Base {
public:
    // 没有 override：参数写成 double，签名不匹配，但编译通过
    virtual void on_tick(double x) { std::cout << "Derived::on_tick(double) " << x << "\n"; }
};

int main() {
    Derived d;
    Base* p = &d;
    p->on_tick(42);      // 期望 Derived，实际 Base
    d.on_tick(3.14);     // 直接调派生类对象 → Derived::on_tick(double)
    return 0;
}

真实输出：

Base::on_tick(int) 42
Derived::on_tick(double) 3.14

第一行的 Base::on_tick(int) 就是事故本身——通过基类指针分发，居然落回了基类。Derived::on_tick(double) 并没有消失，它成了 Derived 自己的新虚函数，只是不在 Base::on_tick 的 vtable 槽位上。于是代码"看起来对了、编译过了、单测直接调派生类对象也能过"，只有走多态分发时才暴露。

编译器确实给了一条告警（-Wall 下）：

warning: 'Derived::on_tick' hides overloaded virtual function [-Woverloaded-virtual]
note: hidden overloaded virtual function 'Base::on_tick' declared here:
      type mismatch at 1st parameter ('int' vs 'double')

但告警不会拦住你，override 会。

加上 override：把运行时 bug 提前到编译期

class Derived : public Base {
public:
    void on_tick(double x) override { std::cout << "Derived::on_tick(double) " << x << "\n"; }
};

本机实测 clang 23.1.0 报错原文：

error: non-virtual member function marked 'override' hides virtual member function
   11 |     void on_tick(double x) override { ... }
      |                            ^
note: hidden overloaded virtual function 'Base::on_tick' declared here:
      type mismatch at 1st parameter ('int' vs 'double')
版本 编译 运行 排查成本
不加 override 通过（仅一条告警） 多态静默失效 高：需线上定位"为什么没生效"
加 override 报错 — 低：编译器直接写出 int vs double

四种签名不匹配（逐一实测）

# 不匹配类型 override 报错关键信息（clang 23.1.0 实测）
① 参数类型 type mismatch at 1st parameter ('int' vs 'double')
② 缺 const different qualifiers ('const' vs unqualified)
③ 引用限定符 hides virtual member function / cannot overload a member function without a ref-qualifier with a member function with ref-qualifier '&'
④ 基类非虚 error: only virtual member functions can be marked 'override'

②③ 的实测代码：virtual void process() const; 配 void process() override;（缺 const）、virtual void h() &; 配 void h() && override;（& vs &&）。

不做 override 的对照组（②）：编译通过，程序输出 Base::process() const——多态失效。① 最容易踩的变体是 int vs int64_t、size_t vs uint32_t：64 位 Linux 上位宽不同，但很多人凭直觉以为"反正都是整数"。

final：override 的搭档

override 说"我是重写"，final 说"到此为止"。二者正交，可同时写：

class Base    { public: virtual void f() { } };
class Derived : public Base { public: void f() override final { } };
class Deep    : public Derived { public: void f() override { } };   // 编译失败

实测报错：

error: declaration of 'f' overrides a 'final' function
note: overridden virtual function is here

final 修饰类时：class Base final { }; → 继承尝试报 error: base 'Base' is marked 'final'。

引用限定符 & 和 &&

成员函数可在参数表后加 &（只在左值对象上调）或 &&（只在右值对象上调），它和 const 一样属于函数签名，因此也在 override 检查范围内：

class Quote {
    double px_ = 0.0;
public:
    explicit Quote(double p) : px_(p) {}
    double& px() &  { return px_; }            // 左值对象：返回引用，还能接着用
    double  px() && { return std::move(px_); }  // 右值对象：可以放心搬走内部数据
};

实测输出：

lvalue object:     px() &  -> 100.5
rvalue object:     px() && -> 200.25     // Quote(200.25).px()
explicit move:     px() && -> 100.5      // std::move(q).px()

完整可运行例子

HFT 里典型的事件分发点：纯虚的 on_tick（漏了直接编译失败）＋ 有默认实现的 on_reset（漏了会静默）：

#include <iostream>
#include <memory>
#include <vector>

class Handler {
public:
    virtual void on_tick(int px) = 0;      // 纯虚：子类必须重写
    virtual void on_reset() {}             // 有默认实现：写错签名编译器不拦
    virtual ~Handler() = default;
};

class Logger : public Handler {
public:
    void on_tick(int px) override { std::cout << "  Logger::on_tick " << px << "\n"; }
    void on_reset() override { std::cout << "  Logger::on_reset\n"; }
};

class Aggregator : public Handler {
public:
    void on_tick(int px) override { sum += px; }
    void on_reset() override { sum = 0; }
    int sum = 0;
};

int main() {
    std::vector<std::unique_ptr<Handler>> hs;
    hs.push_back(std::make_unique<Logger>());
    hs.push_back(std::make_unique<Aggregator>());
    std::cout << "dispatch on_tick:\n";
    for (auto& h : hs) h->on_tick(100);
    std::cout << "dispatch on_reset:\n";
    for (auto& h : hs) h->on_reset();
    std::cout << "agg->sum after reset = "
              << static_cast<Aggregator*>(hs[1].get())->sum << "\n";
    return 0;
}

clang 23.1.0 实测输出：

dispatch on_tick:
  Logger::on_tick 100
dispatch on_reset:
  Logger::on_reset
agg->sum after reset = 0

把 Aggregator::on_reset 的 override 去掉并写错签名（比如 on_reset(int)），代码依旧能编译——只是 reset 永远不会被调用，累计值一直涨。这就是 override 存在的全部理由。

常见错误（新手踩坑）

  1. 只在纯虚函数上加 override。纯虚函数漏实现时派生类变抽象类，编译器本来就会拦（实测 error: variable type 'Impl' is an abstract class）。真正的风险在有默认实现的虚函数上。
  2. 把 -Woverloaded-virtual 当保险。它只是告警，且管不到"基类函数压根不是 virtual"的情况——那种写法不构成 hiding，一条告警都不会有。
  3. 以为在派生类写 virtual 就够了。virtual 在派生类里是冗余的（重写自动为虚），不提供任何检查；override 才检查。
  4. 改基类签名后靠全局替换。全局替换能改掉名字，改不掉"语义上这里不该改"。加了 override 后编译器会把所有受影响点一次性列出来，这才是安全重构的正确姿势。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
多态 函数指针表（手动） 虚函数（自动） C++ 语言级支持
重写检查 手动对照（容易出错） override 编译器检查 防签名不匹配
阻止重写 不适用 final 设计封闭类 + 去虚化
值类别重载 不存在 & / && 引用限定符 区分"还要用"和"马上死"

一句话总结： C 程序员学 C++ 面向对象时，override 是第一条该养成的习惯——它同时检查派生类的签名和基类的 virtual，两头都堵。不加它，重写错误就是编译期不可发现的运行时静默失败。

HFT 关联

  • 策略基类：class Strategy { virtual void on_tick(const Tick&) = 0; }; 子类加 override 后签名写错编译期暴露，避免"策略不生效"——这类 bug 在回测里常表现为"收益为 0"而不是"崩溃"，极难察觉。
  • 事件处理器：行情网关回调签名写错（如缺 const），不加 override 会导致回调不被调用。在 UDP 组播场景下等同于静默丢包，无任何告警。
  • final 优化：final 让编译器去掉虚调用的间接跳转（devirtualization），省掉一次 vtable 查找和一次潜在的 i-cache miss——HFT 热路径可以受益。

自测题

1. 不加 override 时签名写错，代码能编译吗？运行时会发生什么？

答案

能编译（clang 23.1.0 下仅一条 -Woverloaded-virtual 告警）。派生类函数不覆盖基类虚函数，而是成为一个新的虚函数，占新的 vtable 槽位。通过基类指针调用时执行基类版本，表现为"改了子类代码却没生效"。实测输出第一行是 Base::on_tick(int) 42——事故现场。

2. 加上 override 后四类签名不匹配，clang 23.1.0 的报错关键信息分别是什么？

答案
类型 报错关键信息
① 参数类型 hides virtual member function + type mismatch at 1st parameter ('int' vs 'double')
② 缺 const hides virtual member function + different qualifiers ('const' vs unqualified)
③ 引用限定符 hides virtual member function；无限定符版另报 cannot overload a member function without a ref-qualifier with a member function with ref-qualifier '&'
④ 基类非虚 error: only virtual member functions can be marked 'override'

④ 这条最有价值：它把"基类的设计意图"也纳入检查——你以为那是虚函数，但基类作者并没打算让你重写；去掉 override 后连告警都不会有。

3. 基类是 virtual void process() const，派生类写成 void process() override 会怎样？去掉 override 呢？

答案

带 override 编译失败：error: non-virtual member function marked 'override' hides virtual member function / note: ... different qualifiers ('const' vs unqualified')。去掉 override 则编译通过（带 -Woverloaded-virtual 告警），但通过基类指针调用执行的是 Base::process() const——多态失效。const 是签名的一部分，漏写等于写了另一个函数。

4. 引用限定符 & / && 的用途是什么？为什么它会影响 override 匹配？

答案

用途是按调用对象的值类别重载：左值对象（还要继续用）走 & 版本，通常返回引用；右值对象（马上销毁）走 && 版本，可以放心把内部资源搬走。实测 Quote(200.25).px() 与 std::move(q).px() 都走 && 版本。因为 & / && 和 const 一样属于函数签名，重写要求签名完全匹配，所以基类 void h() & 与派生类 void h() &&（或无限定符的 void h()）不构成重写。

5. override 和 final 能同时用吗？final 除了挡重写还有什么作用？

答案

能，写作 void f() override final;。二者正交：override = "我重写了基类虚函数"（编译期校验签名）；final = "到此为止，派生类不能再重写"（也可修饰类：class D final : public B，此时报 error: base 'Base' is marked 'final'）。额外作用：给编译器提供去虚化依据，静态绑定后省掉一次 vtable 间接跳转。

6. 为什么"纯虚函数漏实现"反而不是 override 的主要战场？

答案

因为纯虚函数漏实现（或签名写错导致没覆盖到）时，派生类仍是抽象类，一实例化编译器立刻报硬错误（实测 error: variable type 'Impl' is an abstract class + note: unimplemented pure virtual method 'on_tick' in 'Impl'），跑不掉。真正的风险在基类提供了默认实现的虚函数上：签名写错后代码完全合法，只是默认实现被悄悄沿用，往往要到生产环境才被发现。

Item 13：优先 const_iterator 而非 iterator

第 3 章 移步现代 C++ · Item 13 · 上一节：Item 12 override

为什么要学这个（先建立直觉）

C 程序员用 const 指针防止意外修改，这是刻在肌肉记忆里的习惯：

int arr[] = {1, 2, 3, 4, 5};
const int* p = arr;          // 指向 const 的指针——不能通过 p 改元素
// *p = 10;                  // 编译失败
for (const int* it = arr; it != arr + 5; ++it)
    printf("%d\n", *it);     // 只读遍历，安全

C++ 的迭代器就是"面向对象的指针"，同样分 iterator（可改）和 const_iterator（只读）。区别只在于：C++11 之前你很难方便地拿到 const_iterator——非 const 容器上 begin() 返回的是 iterator，你得先把容器转成 const&，或者写一长串 std::vector<Order>::const_iterator。结果就是大家为了省事一律 begin()，代码里到处是"其实根本没想改，但权限给满了"的遍历。

C++11 补上了成员函数 cbegin()/cend()/crbegin()/crend()，C++14 又补上了非成员版本 std::cbegin(c)——后者对原生数组和泛型容器也统一适用。配合 auto，拿 const_iterator 的成本终于降到零。这就是"最低权限原则"：你不需要写权限，就别拿写权限。多给的权限不会让代码跑得更快，只会在某天变成"谁动了我的订单簿"的线上事故。

这节讲什么

  1. 四个迭代器家族成员的对照表，全部用 static_assert 实测类型；
  2. const_iterator vs const iterator——C++ 新手第一号混淆点；
  3. C++11 起 insert/erase 接受 const_iterator（跨标准实测）；
  4. iterator → const_iterator 的单向转换；
  5. 非成员 std::cbegin/std::cend（C++14）与 C++11 下的报错原文。

四大家族 + 单向转换（static_assert 实测）

含义 正向 反向 获取方式（成员函数）
可改元素 iterator reverse_iterator begin() / rbegin()
只读元素 const_iterator const_reverse_iterator cbegin() / crbegin()

把类型钉死（clang 23.1.0，-std=c++17 -Wall 实测通过）：

#include <vector>
#include <type_traits>
using std::is_same_v;
using std::is_convertible_v;

int main() {
    std::vector<int> v = {1, 2, 3};
    using It   = std::vector<int>::iterator;
    using CIt  = std::vector<int>::const_iterator;
    using RIt  = std::vector<int>::reverse_iterator;
    using CRIt = std::vector<int>::const_reverse_iterator;
    static_assert(is_same_v<decltype(v.begin()),   It>);
    static_assert(is_same_v<decltype(v.cbegin()),  CIt>);
    static_assert(is_same_v<decltype(v.rbegin()),  RIt>);
    static_assert(is_same_v<decltype(v.crbegin()), CRIt>);
    // 单向转换：iterator → const_iterator 可以，反向不行
    static_assert(is_convertible_v<It, CIt>);
    static_assert(!is_convertible_v<CIt, It>);
    // 非 const 容器上，auto 只会如实接住 iterator，不会替你收紧权限
    auto it = v.begin();
    static_assert(is_same_v<decltype(it), It>);
    return 0;
}

最后两行是重点：非 const 容器上 auto it = v.begin() 拿到的是 iterator。auto 只负责少打字，不会替你表达只读意图——这就是必须写 cbegin() 的核心理由。反向若强行写（std::vector<int>::iterator it = v.cbegin();），clang 报 error: no viable conversion from 'const_iterator' to 'iterator'。

const_iterator ≠ const iterator

新手第一号混淆点，二者 const 修饰的层级完全不同：

std::vector<int> v = {1, 2, 3};

// const_iterator：指向 const 元素 —— 不能改元素，但能 ++ 移动
std::vector<int>::const_iterator cit = v.cbegin();
// *cit = 10;   // 编译失败：read-only variable is not assignable
++cit;          // OK

// const iterator：迭代器本身是 const —— 不能移动，但能改元素
const std::vector<int>::iterator it = v.begin();
*it = 10;       // OK！和你想的"只读"完全相反
// ++it;        // 编译失败

++it 的实测报错原文：

error: cannot increment value of type 'const std::vector<int>::iterator' (aka 'const __wrap_iter<int *>')

记忆口诀：const_iterator 修的是元素，const iterator 修的是指针变量；对应到 C 就是 const int* 与 int* const 的区别。

C++11 起 insert / erase 接受 const_iterator

C++11 之前 erase(iterator) 只接受 iterator，于是"先 find 定位、再删掉"这个最常见的组合逼着你在两种迭代器间来回倒腾。C++11 把这两个成员改成接受 const_iterator。实测（-std=c++11 编译并运行）：

#include <iostream>
#include <vector>
#include <algorithm>

int main() {
    std::vector<int> v = {10, 20, 30, 40, 50};
    auto pos = std::find(v.cbegin(), v.cend(), 30);   // const_iterator
    auto after = v.erase(pos);                       // C++11 起 OK
    std::cout << "after erase, *after = " << *after << "\n";
    auto pos2 = std::find(v.cbegin(), v.cend(), 40);
    auto inserted = v.insert(pos2, 35);              // C++11 起 OK
    std::cout << "after insert, *inserted = " << *inserted << "  ";
    for (auto x : v) std::cout << x << ' ';
    std::cout << "\n";
    auto it = v.cbegin();
    // *it = 99;   // 编译失败：read-only variable is not assignable
    return 0;
}

真实输出：

after erase, *after = 40
after insert, *inserted = 35  10 20 35 40 50

erase/insert 的返回类型跟传入的迭代器一致——传 const_iterator 就返回 const_iterator，整条链路可以一路只读到底。

非成员 cbegin/cend（C++14）

成员函数版 cbegin() 是 C++11 的；非成员 std::cbegin(c) / std::cend(c) 是 C++14 的。差别在泛型代码和原生数组：

std::vector<int> v = {1, 2, 3, 4, 5};
auto it  = std::cbegin(v);        // C++14 起 OK
int arr[] = {7, 8, 9};
auto ait = std::cbegin(arr);       // 原生数组也吃得下（成员函数版做不到）

C++14 实测输出：

*std::cbegin(v) = 1
*std::cbegin(arr) = 7

同样的代码用 -std=c++11 编译，报错原文：

error: no member named 'cbegin' in namespace 'std'; did you mean 'begin'?
note: 'begin' declared here
error: no matching function for call to 'begin'
note: candidate template ignored: could not match 'initializer_list' against 'std::vector'

C++14 那一批非成员访问函数是一整套：std::cbegin/cend/rbegin/rend/crbegin/crend。写泛型工具函数时优先用非成员版本——它对容器、原生数组、第三方容器一视同仁。

完整可运行例子

把上面的 mean / mean_of 与迭代器行为放在一起跑（-std=c++14）：

#include <iostream>
#include <vector>
#include <numeric>
#include <iterator>

// 只读算法：承诺写进签名
double mean(std::vector<double>::const_iterator first,
            std::vector<double>::const_iterator last) {
    if (first == last) return 0.0;
    return std::accumulate(first, last, 0.0) / std::distance(first, last);
}

// 泛型版：非成员 cbegin，容器与定长数组都通用
template <typename C>
double mean_of(const C& c) {
    auto first = std::cbegin(c);
    auto last  = std::cend(c);
    if (first == last) return 0.0;
    return std::accumulate(first, last, 0.0) / std::distance(first, last);
}

int main() {
    std::vector<double> px = {100.5, 101.0, 99.5, 102.25};
    std::cout << "mean(px)     = " << mean(px.cbegin(), px.cend()) << "\n";
    std::cout << "mean_of(px)  = " << mean_of(px) << "\n";
    double arr[] = {1.0, 2.0, 3.0, 4.0};
    std::cout << "mean_of(arr) = " << mean_of(arr) << "\n";
    // 非 const 容器上 begin() 拿到的是 iterator，可以改元素
    auto mutable_it = px.begin();
    *mutable_it = 999.0;
    std::cout << "px[0]        = " << px[0] << "\n";
    // 单向转换：iterator → const_iterator 可以
    std::vector<double>::const_iterator cit = px.begin();
    std::cout << "*cit         = " << *cit << "\n";
    return 0;
}

clang 23.1.0 实测输出：

mean(px)     = 100.812
mean_of(px)  = 100.812
mean_of(arr) = 2.5
px[0]        = 999
*cit         = 999

注意 mean_of(px) 与 mean_of(arr) 用的是同一份代码——非成员 std::cbegin 抹平了容器与原生数组的差异，这正是 C++14 补齐它的意义。

常见错误（新手踩坑）

  1. 混淆 const_iterator 和 const iterator。写 const auto it = v.begin(); 以为拿到了只读迭代器，结果 *it = 10 合法、++it 非法——恰好搞反。想只读就用 v.cbegin()。
  2. 以为 C++11 的非成员 std::cbegin 可用。非成员版本是 C++14 的；-std=c++11 下报 error: no member named 'cbegin' in namespace 'std'。成员函数版 v.cbegin() 才是 C++11 的。
  3. 把 cbegin() 的结果拿去改元素：*it = 42 报 error: read-only variable is not assignable。要改就用 v.begin()。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
只读指针 const int* p const_iterator（v.cbegin()） 表达"不修改"意图
指针本身不可动 int* const p const iterator（很少用） 与上面是两码事
遍历方式 指针 + 偏移 迭代器 + ++/* 面向对象抽象
算法支持 qsort（函数指针） std::sort（迭代器 + 仿函数） 泛型编程

一句话总结： const_iterator ↔ C 的 const int*（指向 const 的指针）；const iterator ↔ int* const（指针本身是 const）。只读遍历用 cbegin()/cend()，范围 for 用 for (const auto& x : v)。

HFT 关联

  • 只读遍历行情：for (auto it = ticks.cbegin(); it != ticks.cend(); ++it) 明确表达"只读"，任何写入都被编译器拦下。订单簿快照分发给多个策略时尤其重要。
  • 多策略共享数据：多个策略线程并发读同一份行情快照，用 const_iterator 确保不会有策略意外改数据——一旦有人写，编译期就失败，而不是变成一次难复现的数据竞争（另见 Item 16）。
  • 只读算法：std::find、std::count、std::accumulate 等传 cbegin()/cend()；泛型工具函数用非成员 std::cbegin，容器与定长数组都通用。

自测题

1. const_iterator 和 const iterator 有什么区别？

答案

const_iterator 是指向 const 元素的迭代器：解引用得到 const T&，不能改元素，但可以 ++ 移动。const iterator 是迭代器对象本身 const：不能 ++it，但 *it = 10 合法。二者 const 修饰的层级不同——一个修元素，一个修迭代器。对应 C：const_iterator ↔ const int*，const iterator ↔ int* const。

2. 非 const 容器上 auto it = v.begin() 和 auto it = v.cbegin() 分别得到什么类型？

答案

分别是 std::vector<T>::iterator 和 std::vector<T>::const_iterator。实测 static_assert(is_same_v<decltype(v.begin()), It>) 通过。关键在于 auto 只会如实接住 begin() 的返回类型，不会替你收紧权限——想表达只读必须写 cbegin()。

3. C++11 和 C++14 在 const_iterator 支持上分别补了什么？

答案

C++11：①容器成员函数 cbegin()/cend()/crbegin()/crend()；②insert/erase 改为接受 const_iterator。C++14：非成员版本 std::cbegin/cend/rbegin/rend/crbegin/crend，对原生数组和任何提供 begin()/end() 的容器都适用——泛型代码的通用性在 C++14 才补齐。实测 -std=c++11 下 std::cbegin 报 no member named 'cbegin' in namespace 'std'。

4. iterator 和 const_iterator 之间能互相转换吗？方向如何？

答案

单向：iterator → const_iterator 可隐式转换（加权限安全），反向不行（去掉权限不安全）。实测 static_assert(is_convertible_v<It, CIt>) 与 static_assert(!is_convertible_v<CIt, It>) 都通过。实际意义：函数参数写 const_iterator 不会给调用方带来负担。

5. 为什么推荐用 cbegin()/cend() 而非 begin()/end()？

答案

因为 begin() 的返回类型取决于容器的常量性：非 const 容器上返回 iterator，后续任何人都可以通过它改元素，与"只读遍历"的意图相悖。cbegin() 无条件返回 const_iterator，把"不修改"写进类型、由编译器强制检查，且不依赖容器本身是否 const。在 auto it = c.begin(); 这种写法下尤其重要。

6. 下面代码有什么问题？

std::vector<int> v = {1, 2, 3};
const auto it = v.begin();
*it = 10;
++it;
答案

++it 编译失败。实测报错：error: cannot increment value of type 'const std::vector<int>::iterator' (aka 'const __wrap_iter<int *>')。const auto it = v.begin(); 中 auto 推为 std::vector<int>::iterator，const 修饰的是迭代器自身，所以 ++it 非法；而 *it = 10 反而合法——const 的是迭代器不是元素。正确写法：只读遍历 auto it = v.cbegin();，改元素 auto it = v.begin();。

7. 为什么 C++14 的非成员 std::cbegin 对泛型代码是"补齐"而非"语法糖"？

答案

因为成员函数版 c.begin() 只能用于类类型容器，原生数组没有成员函数，泛型模板里还得为数组单独写一份重载。非成员 std::cbegin(c) 对 std::vector 和 double arr[4] 用同一行代码就能拿到 const_iterator——实测 mean_of(px) 与 mean_of(arr) 共用一份实现，分别输出 100.812 和 2.5。写通用工具函数时优先用非成员版本。

Item 14：声明 noexcept 如果函数保证不抛

第 3 章 移步现代 C++ · Item 14 · 上一节：Item 13 const_iterator

为什么要学这个（先建立直觉）

C 没有异常机制，C 程序员习惯用返回值表示错误：if (data == NULL) return -1;。C++ 有异常，函数可以 throw 而不返回错误码。但异常不是免费的——编译器要生成 unwind 表，运行时栈展开有开销。C++11 的 noexcept 就是给编译器的承诺："这个函数保证不抛"，编译器据此省掉异常处理代码、做更强的优化。

但 noexcept 真正值钱的地方不在优化，而在它是一份接口契约，会被标准库读取。 std::vector 在 push_back 扩容、搬移旧元素时，会检查元素的移动构造是不是 noexcept。是 → 用移动（每个元素 O(1)）；不是 → 退回拷贝（安全但慢）。这个检查是编译期的（std::is_nothrow_move_constructible + std::move_if_noexcept）。

也就是说：你写了移动构造但忘了标 noexcept，容器根本不敢用，悄悄退化成拷贝。代码能跑、单测能过、只是慢——而且慢在一个最不该慢的地方：扩容那一瞬间。

这节讲什么

  1. vector 扩容时 move_if_noexcept 的实测：移动构造标与不标 noexcept，构造次数差多少；
  2. noexcept 是承诺不是建议：标错并抛异常的后果（terminate）与编译告警；
  3. swap 与析构的隐式 noexcept；
  4. 条件 noexcept 与 noexcept 运算符。

实测一：vector 扩容走 move 还是 copy

用一个带计数器的类模板，两种实例化只差移动构造上的 noexcept（noexcept(NX) 叫条件 noexcept），其余代码完全相同：

#include <iostream>
#include <vector>
#include <type_traits>
#include <utility>

template <bool NX>
struct Counted {
    static int copies, moves;
    int id = 0;
    Counted() = default;
    explicit Counted(int i) : id(i) {}
    Counted(const Counted& o) : id(o.id) { ++copies; }
    Counted(Counted&& o) noexcept(NX) : id(o.id) { o.id = -1; ++moves; }
};
template <bool NX> int Counted<NX>::copies = 0;
template <bool NX> int Counted<NX>::moves  = 0;

template <bool NX>
void run(const char* tag) {
    std::vector<Counted<NX>> v;
    for (int i = 0; i < 9; ++i) {
        Counted<NX> c(i);
        v.push_back(std::move(c));      // 容量不足时触发搬移
    }
    std::cout << tag << "  is_nothrow_move_constructible="
              << std::is_nothrow_move_constructible<Counted<NX>>::value
              << "  copies=" << Counted<NX>::copies << "  moves=" << Counted<NX>::moves << "\n";
}

int main() {
    std::cout << std::boolalpha;
    run<true >("move ctor noexcept   ");
    run<false>("move ctor NOT noexcp ");
    return 0;
}

连续 push_back(std::move(c)) 九次，容量按 0→1→2→4→8→16 翻倍。clang 23.1.0（-std=c++17 -Wall）实测输出：

move ctor noexcept     is_nothrow_move_constructible=true  copies=0  moves=24
move ctor NOT noexcp   is_nothrow_move_constructible=false  copies=15  moves=9
版本 push_back 直接构造 扩容搬移旧元素 合计
标了 noexcept 9 次移动 1+2+4+8 = 15 次移动 moves=24, copies=0
没标 noexcept 9 次移动 15 次拷贝 moves=9, copies=15

唯一的差别就是那 15 次搬移走的是移动还是拷贝。 当元素里带着 std::string、堆缓冲区或锁句柄时，这 15 次就是 15 次深拷贝——正是 HFT 里"扩容延迟尖峰"的来源。

实测二：noexcept 是承诺，不是建议

标了 noexcept 的函数若真让异常逃逸，标准规定调用 std::terminate()——程序直接终止，没有栈展开，也没有 catch 的机会：

#include <iostream>
#include <stdexcept>

void boom() noexcept {
    throw std::runtime_error("oops");   // 从 noexcept 函数逃逸
}

int main() {
    std::cout << "before boom()\n";
    boom();
    std::cout << "after boom()\n";      // 永远不会打印
    return 0;
}

实测（clang 23.1.0）：编译期先给一条告警，运行中 abort，退出码 134（SIGABRT）。

warning: 'boom' has a non-throwing exception specification but can still throw [-Wexceptions]
note: function declared non-throwing here

before boom()
libc++abi: terminating due to uncaught exception of type std::runtime_error: oops

如果异常不是直接 throw，而是来自内部的 std::make_shared、vector::push_back（可能抛 bad_alloc），编译器未必告警——但 terminate 一样会发生。同理，析构函数自 C++11 起默认就是 noexcept，在析构里抛异常同样 terminate。

实测三：swap / 析构的默认 noexcept

有一批操作编译器会自动标 noexcept（除非成员/基类显式禁止），不需要你动手：

函数 默认是否 noexcept 说明
析构函数 是（C++11 起） 只有显式 noexcept(false) 才能改变
隐式生成的拷贝/移动构造与赋值 由成员决定 所有成员的对应操作都 noexcept 才是
隐式生成的默认构造 由成员决定 同上
operator delete / delete[] 是 释放内存不该失败

自己写 swap 时应该用条件 noexcept，让"是否不抛"跟着元素类型走：

template <typename T>
void my_swap(T& a, T& b) noexcept(std::is_nothrow_move_constructible<T>::value &&
                                  std::is_nothrow_move_assignable<T>::value) {
    T tmp = std::move(a);
    a = std::move(b);
    b = std::move(tmp);
}

noexcept(表达式) 里的操作数不会被求值，只做"这个表达式会不会抛"的编译期判断——这就是 noexcept 运算符。

实测四：C++17 起 noexcept 进入函数类型

C++17 之前 noexcept 只是函数属性，不属于类型；C++17（P0012R1）把它并入函数类型。于是函数指针的赋值规则变了：

void safe() noexcept { }
void risky() { }

void (*p1)() noexcept = safe;   // OK：noexcept → noexcept
void (*p2)()          = risky;   // OK：非 noexcept → 非 noexcept
void (*p3)() noexcept = risky;   // C++17 起：非法！非 noexcept → noexcept

跨标准实测报错原文（clang 23.1.0）：

-std=c++11 : error: target exception specification is not superset of source
-std=c++14 : error: target exception specification is not superset of source
-std=c++17 : error: cannot initialize a variable of type 'void (*)() noexcept'
                    with an lvalue of type 'void ()': different exception specifications
-std=c++20 : 同 c++17

C++11/14 也报错，但理由不同：前者是函数自身的异常规范太窄，后者是类型不匹配。类型层面的差异可以用 std::is_same 直接看到：

std::cout << std::is_same<void(), void() noexcept>::value                  // c++11/14: 1   c++17/20: 0
          << std::is_convertible<void (*)() noexcept, void (*)()>::value;  // 全部标准: 1

反向（把 noexcept 函数指针赋给普通函数指针）在所有标准下都合法——C++17 专门加了一条隐式转换，避免"加了 noexcept 反而破坏老代码"。实践含义：给已有函数加 noexcept 通常是安全的，但撤掉 noexcept 可能破坏调用方。所以它叫接口契约。

完整可运行例子

第二个程序：把"条件 noexcept + 析构默认 noexcept"两件静态性质一次打印出来（-std=c++17 -Wall）。

#include <iostream>
#include <type_traits>
#include <utility>

struct Plain         { int a = 0; double b = 0.0; };
struct WithUserDtor  { ~WithUserDtor() {} };
struct WithThrowDtor { ~WithThrowDtor() noexcept(false) {} };

struct NoexceptMove { NoexceptMove(NoexceptMove&&) noexcept {} NoexceptMove& operator=(NoexceptMove&&) noexcept { return *this; } };
struct ThrowingMove { ThrowingMove(ThrowingMove&&) {} ThrowingMove& operator=(ThrowingMove&&) { return *this; } };

// 条件 noexcept：my_swap 是否 noexcept 取决于元素类型
template <typename T>
void my_swap(T& a, T& b) noexcept(std::is_nothrow_move_constructible<T>::value &&
                                  std::is_nothrow_move_assignable<T>::value) {
    T tmp = std::move(a);
    a = std::move(b);
    b = std::move(tmp);
}

int main() {
    std::cout << std::boolalpha;
    std::cout << "Plain         nothrow dtor = " << std::is_nothrow_destructible<Plain>::value << "\n"
              << "WithUserDtor  nothrow dtor = " << std::is_nothrow_destructible<WithUserDtor>::value << "\n"
              << "WithThrowDtor nothrow dtor = " << std::is_nothrow_destructible<WithThrowDtor>::value << "\n";
    std::cout << "my_swap<NoexceptMove> noexcept = " << noexcept(my_swap(std::declval<NoexceptMove&>(), std::declval<NoexceptMove&>())) << "\n";
    std::cout << "my_swap<ThrowingMove> noexcept = " << noexcept(my_swap(std::declval<ThrowingMove&>(), std::declval<ThrowingMove&>())) << "\n";
    return 0;
}

clang 23.1.0 实测输出：

Plain         nothrow dtor = true
WithUserDtor  nothrow dtor = true
WithThrowDtor nothrow dtor = false
my_swap<NoexceptMove> noexcept = true
my_swap<ThrowingMove> noexcept = false

注意 WithUserDtor 那行：哪怕是手写空函数体的析构，也仍然是 noexcept。而 my_swap<ThrowingMove> 为 false，说明条件 noexcept 把"元素会不会抛"如实传导到了 swap 上——这正是 Item 14 想让你养成的写法。

常见错误（新手踩坑）

  1. 移动构造 / 移动赋值忘了标 noexcept。本 Item 的头号实践项。资源搬移只是拷指针、置空，本不会抛；但编译器按"可能抛"处理，容器扩容退回拷贝（实测差 15 次拷贝）。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
错误处理 返回值（return -1） 异常（throw）或返回值 C++ 有异常机制
不抛保证 不适用 noexcept 编译器优化 + 接口契约
析构抛异常 不适用 禁止（terminate） 异常安全保证

一句话总结： noexcept 是"我保证不抛"的契约，不是给编译器的提示。析构和 swap 默认就是 noexcept，你真正要动手标的是移动构造和移动赋值。

HFT 关联

  • 扩容延迟尖峰：vector<Order> 在 push_back 扩容时，Order 的移动构造必须 noexcept 才走移动，否则退回拷贝，订单簿重建时出现延迟尖峰。这是 HFT C++ 性能的隐形开关——实测同样 9 次 push_back，差 15 次拷贝。
  • move_if_noexcept 的作用：容器搬移元素时要维持强异常保证——搬移途中抛异常不能破坏原容器。移动不抛才敢用移动，否则用拷贝。所以"移动更快"不是你决定的，是 noexcept 决定的。
  • 代码体积：noexcept 让编译器省略 unwind 表，减小二进制体积，间接降低 i-cache 压力（次要收益，主要收益仍是容器分派）。

自测题

1. vector 扩容时如何决定搬移元素用移动还是拷贝？

答案

编译期判断元素类型的移动构造是否 noexcept（std::is_nothrow_move_constructible）：是 → 用移动构造搬移，快且能提供强异常保证；否 → 退回拷贝构造，因为容器必须保证"搬移途中抛异常也不破坏原容器"。实现上走的是 std::move_if_noexcept。

2. 实测里两种 Counted 的 copies/moves 分别是多少？为什么？

答案

标 noexcept：copies=0, moves=24；没标：copies=15, moves=9。9 次是 push_back(std::move(c)) 直接构造新元素（不受 noexcept 影响）；容量按 1→2→4→8→16 翻倍共搬移 15 次旧元素——这 15 次才是"移动 vs 拷贝"的分水岭。

3. 标了 noexcept 却抛了异常会怎样？编译器会拦吗？

答案

不会拦，只给 -Wexceptions 告警；运行时调用 std::terminate()，进程 abort（实测退出码 134）。若异常来自内部的 make_shared/push_back（可能抛 bad_alloc），连告警都可能没有。

4. 为什么漏标 noexcept 比错标安全？

答案

漏标的后果只是"性能没那么好"——容器退回拷贝，代码仍正确。错标（标了却可能抛）的后果是 terminate：进程崩溃、订单状态不明。所以只对确实不会抛、且经过审查的函数标注。

5. C++17 起 noexcept 进入函数类型后，函数指针赋值规则怎么变的？

答案

普通函数指针 → noexcept 函数指针变非法（C++17/20 报 different exception specifications；C++11/14 报 target exception specification is not superset of source）。反向 noexcept → 普通仍然合法（标准特意加了这条隐式转换）。std::is_same<void(), void() noexcept> 从 1 变成 0。

6. 下面代码有什么问题？

class Widget {
public:
    Widget(Widget&& o) { data_ = o.data_; o.data_ = nullptr; }
private:
    int* data_;
};
std::vector<Widget> v;
v.push_back(std::move(w));
答案

移动构造没标 noexcept。它只是搬指针、置空，本身不会抛；但编译器按"可能抛"处理，vector<Widget> 扩容（以及 resize、insert 等需要搬移的场合）会保守地改用拷贝构造，push_back(std::move(w)) 的移动优势被浪费。修正：Widget(Widget&& o) noexcept : data_(o.data_) { o.data_ = nullptr; }。

Item 15：尽可能用 constexpr

第 3 章 移步现代 C++ · Item 15 · 上一节：Item 14 noexcept

为什么要学这个（先建立直觉）

C 程序员用 #define 或 const 定义常量：

#define PI 3.14159          // 无类型，预处理替换
static const int BUF_SIZE = 4096;  // 有类型，但可能不是编译期常量

int arr[BUF_SIZE];   // 可能 OK，取决于编译器（标准 C 里这是 VLA）

两条路各有缺：#define 是编译期常量但没有类型，调试器看不见、作用域管不住；C 的 const 有类型但不保证编译期求值——const int n = get(); 完全合法，值要等运行时才知道。

C++11 的 constexpr 把两者合一：既有类型安全，又保证编译期求值。而且它不只修饰变量，还能修饰函数——让函数在编译期跑完，运行时零开销。

最实用的一点：constexpr 是"有能力编译期求值"，不是"只在编译期求值"。同一个 constexpr 函数，传字面量就编译期算，传运行期变量就退化成普通函数调用。这意味着你不需要为编译期和运行期各写一份代码。

这节讲什么

  1. constexpr 对象：const + 编译期初值，可用于数组维度、static_assert、模板参数；
  2. constexpr 函数：C++11 的"单 return"限制 vs C++14 的放开（两标准分别编译的实测对比）；
  3. constexpr 函数也能在运行期被调用；
  4. const 与 constexpr 的精确区别，以及指针上的坑；
  5. 编译期查表，以及 C++20 consteval / constinit 的前瞻。

constexpr 对象：const + 编译期初值

constexpr int MAX_ORDERS = 10000;     // 编译期常量
constexpr double PI = 3.14159;

int arr[MAX_ORDERS];                   // ① 数组大小
static_assert(MAX_ORDERS > 0);         // ② 编译期断言
template<int N> struct Buffer {};      // ③ 模板参数
Buffer<MAX_ORDERS> buf;                //    OK

三个位置都是"必须用编译期常量"的硬约束，是判断一个值到底是不是 constexpr 的试金石。反过来：如果 MAX_ORDERS 声明成 const int 但初值来自运行期函数，int arr[MAX_ORDERS] 按标准就不合法（clang 会退化成 VLA 扩展并给 -Wvla-cxx-extension 告警）。

constexpr 函数：C++11 只能一行 return

C++11 规定 constexpr 函数体只能是一条 return 语句，不能声明局部变量、不能有 if/循环、不能有多条语句。想写分支？只能用三元表达式或递归：

// C++11 合法写法
constexpr int abs11(int x) { return x < 0 ? -x : x; }

C++14 彻底放开：局部变量、多条语句、if、for/while、多个 return，还能修改自己创建的局部对象。于是"编译期算阶乘/生成查表"变得和写普通函数一样：

constexpr int factorial(int n) {
    int result = 1;
    for (int i = 1; i <= n; ++i) result *= i;
    return result;
}
static_assert(factorial(5) == 120);   // 编译期算出 120

两标准分别编译的实测对比

同一份代码，只换 -std：

clang++ -std=c++11 -Wall 编译失败

C++11 下的报错原文（clang 23.1.0）：

    5 |     int result = 1;
      |         ^

注意两者的差别：局部变量声明只是 warning（clang 把它当 C++14 扩展接受），循环语句是硬 error。所以在 -std=c++11 下写 constexpr 函数，你会看到一部分"好像能过"、一部分直接报错——这种半软半硬的状态最容易让人误判。

if 语句在 C++11 下也是"扩展"级：加 -pedantic-errors 后同样报 error：

error: use of this statement in a constexpr function is a C++14 extension [-Werror,-Wc++14-extensions]
error: multiple return statements in constexpr function is a C++14 extension [-Werror,-Wc++14-extensions]

实践结论：只要项目允许，用 C++14 或更高标准写 constexpr。在 C++11 下它只能当"能放进常量表达式的表达式宏"来用，写不了正经逻辑。

constexpr 函数也能运行期调用

这是最容易误解的一点。constexpr 修饰的是函数"可以在编译期求值"的能力，不代表它只在编译期跑：

constexpr int square(int x) { return x * x; }

constexpr int a = square(10);      // 编译期：a 是常量表达式
int n = 5;
int b = square(n);                 // 运行期：退化成普通函数调用

但是——一旦把运行期值用在要求编译期常量的语境里，编译器不会"退化"，而是直接报错：

int n = 4;
int arr[factorial(n)];   // 数组维度必须是编译期常量

clang 23.1.0 告警（注意，这里是告警而不是 error，因为 clang 默认开了 VLA 扩展）：

warning: variable length arrays in C++ are a Clang extension [-Wvla-cxx-extension]
   11 |     int arr[factorial(n)];
      |             ^~~~~~~~~~~~
note: read of non-const variable 'n' is not allowed in a constant expression
note: declared here

可移植代码不该依赖 VLA——要么把 n 声明成 constexpr，要么改用 std::vector。

指针上的坑：constexpr 修饰的是指针本身，不是指向的对象：

constexpr int* p = nullptr;   // ≡ int* const p（指针是 const）
// 而不是 const int* p（指向 const int）

完整可运行例子

编译期常量 + 编译期生成查表 + 运行期调用，一次跑完（-std=c++14 -Wall）：

#include <iostream>

// ---- 1. constexpr 函数：编译期能算，运行期也能跑 ----
constexpr int factorial(int n) {
    int r = 1;
    for (int i = 1; i <= n; ++i) r *= i;
    return r;
}

// ---- 2. constexpr 对象 = const + 编译期初值 ----
constexpr int kMaxLevels = factorial(4);      // 24，编译期确定
int arr[kMaxLevels];                          // 数组维度证据
static_assert(kMaxLevels == 24, "4! == 24");

// ---- 3. 编译期生成查表（原生数组，C++14 可用）----
struct TickTable {
    int v[8] = {};
    constexpr TickTable() {
        for (int i = 0; i < 8; ++i) v[i] = i * i;
    }
};
constexpr TickTable kt{};
static_assert(kt.v[7] == 49, "7^2 == 49");

int main(int argc, char**) {
    std::cout << "kMaxLevels = " << kMaxLevels << "\n";
    std::cout << "sizeof(arr)/sizeof(int) = " << sizeof(arr) / sizeof(int) << "\n";
    std::cout << "kt.v = ";
    for (int x : kt.v) std::cout << x << ' ';
    std::cout << "\n";
    // constexpr 函数传入运行期值 → 退化成普通函数
    int n = argc + 3;   // 运行期才知道（argc == 1 → n == 4）
    std::cout << "factorial(" << n << ") = " << factorial(n) << "  (runtime call)\n";
    return 0;
}

clang 23.1.0 实测输出：

kMaxLevels = 24
sizeof(arr)/sizeof(int) = 24
kt.v = 0 1 4 9 16 25 36 49
factorial(4) = 24  (runtime call)

kMaxLevels 能被用作数组维度、static_assert 的条件，说明它确实是编译期常量；而 factorial(n) 在 n 来自 argc 时照常运行——同一个函数，两种语境。

常见错误（新手踩坑）

  1. 以为 const 就是 constexpr。const int n = get(); 完全合法，但它不是常量表达式，不能当数组维度。需要编译期常量就显式写 constexpr。
  2. 在 C++11 下写多语句 constexpr 函数。局部变量只是 -Wc++14-extensions 告警（容易误以为能过），for/while 直接 error。要么改写为单 return + 三元/递归，要么升级标准。
  3. constexpr 函数里调了非 constexpr 函数。比如 std::rand()、std::chrono::now()——这会让函数在编译期语境下不可用，报错信息通常指向"不是常量表达式"。
  4. 把 constexpr int* p 当成 const int* p。constexpr 修饰的是指针自身（int* const），指向的对象不是 const。想指常量要写 constexpr const int*。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
常量 #define 或 const constexpr 类型安全 + 编译期求值
编译期计算 #define（仅替换） constexpr 函数 可写复杂逻辑
数组大小 #define MAX 100 constexpr int MAX = 100; 有类型
编译期断言 不适用（C 无） static_assert(cond, msg) 编译期检查

一句话总结： constexpr = #define 的编译期特性 + const 的类型安全。它修饰函数时表示"能在编译期求值"；只有当你把它用在要求常量表达式的位置（数组维度、模板实参、static_assert）时，编译期求值才会被强制发生。

HFT 关联

  • 编译期查表：协议字段偏移、tick size 表、费率表用 constexpr 在编译期算好，放进只读数据段；运行时零计算、零初始化开销，也没有静态初始化顺序问题。数据连续、cache 友好。
  • static_assert 编译期校验：static_assert(sizeof(Order) == 64); 确保订单结构体符合 cache 行对齐；static_assert(TableSize == 256); 校验查表长度。出错在编译期暴露，而不是变成线上的一次越界。

  • 模板参数：Buffer<MAX_ORDERS> 在编译期确定大小，编译器能生成最优代码（无间接寻址、可完全展开）。

自测题

1. const 和 constexpr 的区别是什么？constexpr 蕴含 const 吗？

答案

const 表达"初始化后不可修改"，初值可以在运行期确定；constexpr 表达"必须是编译期可求值的常量表达式"，可用于数组维度、模板实参、case 标签。constexpr 蕴含顶层 const（constexpr 变量本身一定 const）；反过来不成立。指针上要注意：constexpr int* p ≡ int* const p。

2. C++14 的 constexpr 函数比 C++11 强在哪里？

答案

C++11 把函数体限制为"单条 return 语句"：不能声明局部变量、不能有 if/循环/多条语句，复杂逻辑只能靠递归或三元表达式硬凑；且 constexpr 成员函数隐含 const。C++14 全部放开：局部变量、多条语句、if、for/while、多个 return，还能修改自己创建的局部对象，成员函数也不再隐含 const。这让"编译期生成查表"真正可行。

3. constexpr 函数传入运行期值会怎样？

答案

在运行期求值，退化成一次普通函数调用，返回值不再是常量表达式——因此不能用在数组维度、模板实参、case 标签等要求编译期常量的位置（那些地方会报错或退化成 VLA 扩展并告警）。也就是说 constexpr 是"有能力编译期求值"，是否真的编译期求值取决于实参是否为常量表达式以及结果是否被用在需要常量的语境。注意函数体仍必须满足 constexpr 的语法约束，与实参无关。

4. 为什么 HFT 喜欢用 constexpr 做查表？

答案

表在编译期算好并放进只读数据段，运行时零计算、零初始化开销（没有静态初始化顺序问题、没有构造/加锁成本），数据布局连续、cache 友好，还能用 static_assert 在编译期校验表内容（表长、校验和），出错在编译期暴露。对延迟敏感的路径，"查表"这件事被完全移出运行时。

5. constexpr int* p 和 const int* p 是一回事吗？

答案

不是。constexpr int* p 等价于 int* const p——const 的是指针本身（不能改指向），指向的 int 仍可修改。const int* p 是"指向 const int 的指针"（不能通过 p 改值，但可改指向）。想让指针既不可改指向、指向的也不可改，写 constexpr const int* p。

6. 下面代码能编译吗？

int x = 42;
const int cx = x;
constexpr int ce = x;
int arr1[cx];
int arr2[ce];
答案

不能，卡在第 3 行。const int cx = x; 合法（const 可以用运行期值初始化）；constexpr int ce = x; 非法：x 是非 const 局部变量，对它做左值到右值转换不属于常量表达式。正确写法是先把 x 声明为 const int x = 42;（或 constexpr），之后才能用它初始化 constexpr 变量。另外 int arr1[cx]; 按标准也不合法——clang 会当成 VLA 扩展并给 -Wvla-cxx-extension 告警，可移植代码不该依赖。

7. constexpr 函数在 C++11 下是不是完全不能写分支？

答案

不是"完全不能"，而是不能用 if/switch 语句——必须用三元条件表达式或递归来模拟。例如 constexpr int abs11(int x) { return x < 0 ? -x : x; }、constexpr int fact(int n) { return n <= 1 ? 1 : n * fact(n - 1); }。代价是代码可读性差、递归深度受编译器常量求值上限约束（clang 默认 -fconstexpr-depth=512）。所以 C++11 的 constexpr 函数适合写"表达式级"的小工具，不适合写算法。

Item 16：让 const 成员函数线程安全

第 3 章 移步现代 C++ · Item 16 · 上一节：Item 15 constexpr

为什么要学这个（先建立直觉）

C 没有 const 成员函数。C 程序员只能传 const struct Cache* 来表达"只读"，编译器会挡住 c->cached = 1 这类写操作——看起来很安全。

C++ 的 const 成员函数承诺"不修改对象状态"。但有个后门——mutable 关键字：

class Cache {
    mutable int cachedValue;
public:
    int getValue() const {              // const 函数
        if (!cachedValue) cachedValue = compute();   // 修改 mutable 成员！
        return cachedValue;
    }
};

问题来了： 如果两个线程同时调 getValue()，它们都在修改 cachedValue——这是数据竞争（data race）。标准假设 const 成员函数可能被并发调用，所以只要 const 函数写了 mutable 成员，你就必须自己加锁或用 atomic。

直觉反转点在于：const 在 C++ 里是"逻辑 const"，不是"物理只读"。它只约束编译器（this 变成 const T*），对线程安全零保证。缓存、命中率计数、延迟统计——这些"不影响逻辑状态"的东西全靠 mutable 塞进 const 函数里，也正是并发风险的藏身之处。

这节讲什么

  1. const 成员函数为什么仍可能写数据（mutable 后门）；
  2. 数据竞争实测：两线程对裸 mutable int 各增 100 万次，结果远小于 200 万；
  3. 两种修复：std::atomic（无锁）与 std::mutex（保护复合不变量）；
  4. mutable 的必要性——不加 mutable 连锁都上不了；
  5. std::atomic 成员的代价：类变成不可拷贝（报错原文）。

现场：const 函数里的数据竞争

#include <iostream>
#include <thread>

class Counter {
    mutable int count = 0;                 // 裸 mutable int
public:
    void bump() const { ++count; }         // const 函数，却在写共享状态
    int  get()  const { return count; }
};

int main() {
    constexpr int kN = 1000000;
    for (int round = 1; round <= 4; ++round) {
        Counter c;
        std::thread t1([&] { for (int i = 0; i < kN; ++i) c.bump(); });
        std::thread t2([&] { for (int i = 0; i < kN; ++i) c.bump(); });
        t1.join();
        t2.join();
        std::cout << "round " << round << ": count = " << c.get()
                  << "  (expect " << 2 * kN << ")\n";
    }
    return 0;
}

clang 23.1.0（-std=c++17 -Wall，arm64 Apple）实测输出：

round 1: count = 1000032  (expect 2000000)
round 2: count = 1006666  (expect 2000000)
round 3: count = 1000955  (expect 2000000)
round 4: count = 1010918  (expect 2000000)

关键观察：

  • 结果不是"接近 200 万"，而是接近 100 万——两个线程的更新几乎完全互相覆盖。arm64 上 ++count 是"读-改-写"三条指令，两个核各自读到同一个旧值、各自写回，一半的增量凭空消失。
  • 每次跑结果都不一样（1000032 / 1006666 / 1000955 / 1010918）。这正是数据竞争的signature：不是"结果错一点"，而是结果不确定。
  • 代码看起来完全无害：bump() 是 const 的，get() 也是 const 的，编译器一声不吭。只有 mutable 那个词是线索。

这类 bug 在 HFT 里的可怕之处：它不会让你的策略崩溃，它会让你的统计数字悄悄错掉——命中率、延迟分位数、成交量累加，全都在"看起来正常"地输出错误值。

修复方案 A：mutable std::atomic（无锁）

class Cache {
    mutable std::atomic<int>  cachedValue{0};
    mutable std::atomic<bool> cacheValid{false};
public:
    int getValue() const {
        if (!cacheValid.load(std::memory_order_acquire)) {
            int v = compute();
            cachedValue.store(v, std::memory_order_relaxed);
            cacheValid.store(true, std::memory_order_release);
        }
        return cachedValue.load(std::memory_order_relaxed);
    }
};

适用：单个变量的读-改-写（计数器、命中标记、指针交换）。开销最小、不阻塞，HFT 热路径首选。

修复方案 B：mutable std::mutex（保护复合不变量）

class Cache {
    mutable std::mutex m_;                 // 必须 mutable：const 函数里要能 lock()
    mutable int  cachedValue = 0;
    mutable bool valid = false;
public:
    int getValue() const {
        std::lock_guard<std::mutex> g(m_); // 保护 (valid, cachedValue) 这组不变量
        if (!valid) { cachedValue = compute(); valid = true; }
        return cachedValue;
    }
};

适用：多个变量要保持一致（"缓存值 + 时间戳 + 计数器"必须同时更新）。代价是阻塞与上下文切换。

为什么锁必须 mutable？ 因为在 const 成员函数里 this 是 const T*，所有非 mutable 成员都变成 const；而 mutex::lock() 是非 const 成员函数——不加 mutable 就没法在 const 函数里加锁。实测报错：

error: no matching constructor for initialization of 'std::lock_guard<std::mutex>'
note: candidate constructor not viable: 1st argument ('const std::mutex') would lose const qualifier

同一个"两线程各增 100 万次"的循环，分别用裸 mutable int / mutex / atomic 实现，程序内部连跑三轮，实测输出：

run1  raw=1001447  mutex=2000000  atomic=2000000   (expect 2000000)
run2  raw=1004449  mutex=2000000  atomic=2000000   (expect 2000000)
run3  raw=1019081  mutex=2000000  atomic=2000000   (expect 2000000)

（整个程序再跑两遍，raw 依次是 1006051 / 1000632 / 1000000 与 1006421 / 1006333 / 1005750，mutex 与 atomic 始终精确 2000000。）

裸 int 每次结果都接近 100 万且每一轮都不一样；mutex 与 atomic 每轮都精确 200 万。差别不是"精度"而是"确定性"。

完整可运行例子

一个"逻辑只读"的行情快照：第一次取加权均价（VWAP）时才计算，之后缓存。cachedVwap_ / valid_ / m_ 全都是 mutable：

#include <iostream>
#include <vector>
#include <thread>
#include <mutex>

class Snapshot {
    std::vector<double> px_, sz_;              // 价格 / 数量

    mutable std::mutex m_;                     // 必须 mutable：const 函数里要能 lock()
    mutable double cachedVwap_ = 0.0;
    mutable bool   valid_      = false;
    mutable long   hits_       = 0;

    double computeVwap() const {               // 纯计算，不改逻辑状态
        double notional = 0.0, qty = 0.0;
        for (std::size_t i = 0; i < px_.size(); ++i) {
            notional += px_[i] * sz_[i];
            qty      += sz_[i];
        }
        return qty ? notional / qty : 0.0;
    }

public:
    Snapshot(std::vector<double> p, std::vector<double> s)
        : px_(std::move(p)), sz_(std::move(s)) {}

    // const 成员函数，但会写 mutable 成员 → 必须自己保证线程安全
    double vwap() const {
        std::lock_guard<std::mutex> g(m_);
        ++hits_;
        if (!valid_) { cachedVwap_ = computeVwap(); valid_ = true; }
        return cachedVwap_;
    }
    long hits() const {
        std::lock_guard<std::mutex> g(m_);
        return hits_;
    }
};

int main() {
    Snapshot snap({100.0, 101.5, 99.25}, {100, 200, 300});
    for (int i = 0; i < 3; ++i) std::cout << "vwap = " << snap.vwap() << "\n";
    std::cout << "hits = " << snap.hits() << "\n";

    // 三个线程并发调用同一个 const 成员函数
    Snapshot shared({10.0, 20.0, 30.0}, {1, 1, 1});
    double out[3];
    std::thread t0([&] { out[0] = shared.vwap(); });
    std::thread t1([&] { out[1] = shared.vwap(); });
    std::thread t2([&] { out[2] = shared.vwap(); });
    t0.join(); t1.join(); t2.join();
    std::cout << "concurrent = " << out[0] << ' ' << out[1] << ' ' << out[2]
              << ", hits = " << shared.hits() << "\n";
}

clang 23.1.0 实测输出：

vwap = 100.125
vwap = 100.125
vwap = 100.125
hits = 3
concurrent = 20 20 20, hits = 3

三个线程拿到的是同一个值 20，hits 恰好等于 3——懒缓存只算了一次，且计数没有丢。如果把 m_ 去掉，同样的程序会在压力测试下给出随机的 hits 和撕裂的 cachedVwap_。

常见错误（新手踩坑）

  1. 以为 const = 线程安全。const 只保证"不修改逻辑状态"，编译器层面它只是把 this 变成 const T*。一旦函数通过 mutable 成员写共享数据，并发调用就是 data race。
  2. mutex 成员忘了加 mutable，结果在 const 函数里根本没法 lock()（见上节报错原文）。同理 mutable std::atomic<...>——fetch_add 也需要非 const 对象。
  3. 用 atomic 去保护"多个变量的一致性"。atomic 只保证单个对象上的操作是原子的；两个独立的原子操作之间其他线程仍可插入，跨变量不变量会被破坏。这种场景必须用 mutex。
  4. 在 const 函数里用 double-checked locking 手写懒缓存。没有正确的内存序/原子类型，编译器和 CPU 的重排会让你读到"半初始化"的缓存值。用 std::call_once 或干脆全程加锁。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
const 方法 传 const 指针 const 成员函数 面向对象封装
mutable 不存在 mutable 关键字 允许 const 函数改"不影响逻辑状态"的成员
线程安全 手动 pthread_mutex std::mutex / std::atomic C++11 标准库
锁的声明 手动管理 mutable std::mutex const 函数需要能锁

一句话总结： C 程序员记住——const 成员函数不是"只读"的绝对保证，mutable 开了后门。只要 const 函数写了 mutable 成员，你就必须自己用 atomic（单变量）或 mutex（复合不变量）保证线程安全。

HFT 关联

  • 行情缓存：const 的 get_tick() 如果内部更新 mutable 缓存，必须用 atomic 或 mutex 保护——否则多策略线程并发读会 data race，表现为缓存偶尔"算重"或读到撕裂值。
  • 原子计数器：mutable std::atomic<uint64_t> hit_count; 在 const 的 lookup() 中递增，无锁统计缓存命中率。这是 HFT 里最常见的 mutable atomic 用法——热路径上不能容忍锁。
  • 延迟统计：mutable std::atomic<int64_t> last_latency_ns; 在 const 的 process() 中记录延迟——不影响"逻辑 const"但必须线程安全。
  • 注意缓存一致性：每个 atomic 变量自身是原子的，但"缓存值 + 版本"要一起更新就得上锁；否则观测线程会看到新值配旧版本。

自测题

1. const 成员函数为什么可能不是线程安全的？mutable 在其中扮演什么角色？

答案

const 成员函数只保证"不修改对象的逻辑状态"；编译器层面它只是把 this 变成 const T*，从而禁止修改非 mutable 成员，它完全不提供任何线程安全保证。一旦函数通过 mutable 成员（缓存、计数器、延迟统计）或指针/引用间接写共享数据，多个线程同时调用这个 const 函数就是在并发写同一份数据，产生 data race。mutable 正是这个后门：让"看起来只读"的函数实际上在写状态，把并发风险藏在 const 的外衣下。

2. 修复 const 函数的数据竞争有哪两种方式？各自适用什么场景？

答案

① std::atomic（无锁）：把成员改成 mutable std::atomic<T>，适用于单个变量的读-改-写（计数器、命中 bool、指针交换），开销最小、不阻塞，HFT 热路径首选。② std::mutex（加锁）：在 const 函数里用 std::lock_guard 保护临界区，适用于需要保护多个变量或维持跨变量不变量的场景（缓存值 + 时间戳 + 计数器必须一致），代价是阻塞与上下文切换。多读少写的缓存还可考虑 std::shared_mutex。

3. 为什么 mutex 也要声明为 mutable？

答案

在 const 成员函数里 this 的类型是 const T*，所有非 mutable 成员都变成 const，而 mutex::lock() 是非 const 成员函数——不加 mutable 就没法在 const 函数里加锁。把锁声明为 mutable std::mutex m_; 是在表达"锁本身不影响对象的逻辑状态，加锁只是实现细节"，这与 mutable 的语义正好吻合。同理 mutable std::atomic<...> 也是这个道理。

4. std::atomic 能替代 std::mutex 保护多个变量的复合操作吗？

答案

不能。std::atomic 只保证单个对象上的读、写、读-改-写（如 fetch_add、compare_exchange）是原子的，并提供内存序控制；它无法让"对多个变量的一组操作"整体表现为原子——其他线程可能观察到中间状态。复合操作（缓存值 + 时间戳 + 计数器必须一致）仍然需要 std::mutex，或把所有不变量压缩进一个 atomic（例如用打包的序号/版本做校验）。

5. 实测中两个线程各加 100 万次，为什么结果接近 100 万而不是接近 200 万？

答案

++count 在 arm64 上是"读-改-写"三条指令：两个核几乎同时从内存读到同一个旧值，各自加一，再各自写回，于是两次自增只生效一次。两个线程在同一缓存行上反复互相使无效，绝大多数更新被覆盖，结果就落在 100 万附近。重点不是"少了多少"，而是每次跑都不一样——未定义行为的输出没有稳定值，这正是它比普通 bug 危险的地方。

6. 下面代码有什么问题？

class Counter {
    mutable int count = 0;
public:
    int get() const { return ++count; }
};
答案

数据竞争：count 是普通 int，++count 是"读-改-写"三步，多线程并发调用 get() 属未定义行为（丢更新、读到撕裂值），而 const 的外衣完全掩盖了这个风险。修正取决于需求：无锁计数用 mutable std::atomic<int> count{0}; 配 return count.fetch_add(1) + 1;；若需要更强一致性则加 mutable std::mutex m_; 并用 std::lock_guard<std::mutex> g(m_); 保护。

7. 给了 std::atomic 成员之后，类的拷贝/移动语义会发生什么？

答案

std::atomic 的拷贝构造与拷贝赋值被显式 = delete（原子对象不可拷贝——拷贝不是原子的，语义上说不通）。于是含有 atomic 成员的类，其隐式拷贝构造/拷贝赋值也被定义为 deleted；同时移动操作也不会自动生成。实测报错：error: call to implicitly-deleted copy constructor of 'OrderBook' + note: copy constructor ... is implicitly deleted because field ... has a deleted copy constructor。需要拷贝就得自己写一个，把 atomic 用 .load() 取出后再存到新对象里。

Item 17：理解特殊成员函数的生成规则

第 3 章 移步现代 C++ · Item 17 · 上一节：Item 16 const 线程安全

为什么要学这个（先建立直觉）

C 的结构体只有值拷贝——memcpy 语义，编译器不需要生成任何"特殊函数"：

struct Point { int x; int y; };
struct Point a = {1, 2};
struct Point b = a;    // 逐字节拷贝，没有"拷贝构造"的概念

C++ 的类有构造、析构、拷贝、移动——编译器会自动生成这些"特殊成员函数"。但生成规则很复杂，声明了其中一个会影响其余的自动生成。最常见的坑：你写了析构函数（比如要释放资源），编译器就不再自动生成移动构造，于是 vector 扩容退回拷贝（见 Item 14）——性能莫名变差，但代码能编译能运行。更阴的是：光看 std::is_move_constructible 你发现不了这个退化。

这节讲什么

  1. 六个特殊成员函数都是谁，编译器什么时候生成它们；
  2. 用 static_assert 打一张生成规则矩阵；
  3. 用计数器探针戳穿 is_move_constructible 的假象——看 move 请求到底走没走 move；
  4. 析构为什么会抑制移动（历史原因）；
  5. Rule of Zero / Rule of Five，以及 =default 写在哪里决定类是否 trivial。

六个特殊成员函数

特殊成员函数 C 术语类比
默认构造 （无——C 自动零初始化或未初始化）
析构 （无——C 靠程序员手动 free）
拷贝构造 struct B = A;（memcpy 语义）
拷贝赋值 B = A;（memcpy 语义）
移动构造 （无——C 没有移动语义）

前四个 C++03 就有，后两个 C++11 引入。C++11 的"大三律"因此扩展为"大五律"。

生成规则矩阵（static_assert 实测）

定义一组类，每种只声明一种特殊成员函数，然后用 is_copy_constructible / is_move_constructible 等 trait 打表：

#include <type_traits>

struct Empty {};
struct DtorOnly { ~DtorOnly() {} };
struct CopyCtorOnly { CopyCtorOnly() = default; CopyCtorOnly(const CopyCtorOnly&) {} };
struct MoveCtorOnly { MoveCtorOnly(MoveCtorOnly&&) {} };

// 用 static_assert 把规则钉死
static_assert( std::is_copy_constructible<Empty>::value, "");
static_assert( std::is_move_constructible<Empty>::value, "");
static_assert( std::is_copy_constructible<DtorOnly>::value, "");
static_assert( std::is_copy_constructible<CopyCtorOnly>::value, "");
static_assert(!std::is_copy_constructible<MoveCtorOnly>::value, "move 声明后 copy 被删除");
static_assert(!std::is_copy_assignable<MoveCtorOnly>::value,   "move 声明后 copy 赋值被删除");
static_assert( std::is_move_constructible<MoveCtorOnly>::value, "");

clang 23.1.0 实测（-std=c++11/14/17/20 四种标准下结果完全一致，全部 static_assert 通过）：

Empty         copyC=1  moveC=1  copyA=1  moveA=1  triviallyCopyable=1
DtorOnly      copyC=1  moveC=1  copyA=1  moveA=1  triviallyCopyable=0
CopyCtorOnly  copyC=1  moveC=1  copyA=1  moveA=1  triviallyCopyable=0
MoveCtorOnly  copyC=0  moveC=1  copyA=0  moveA=0  triviallyCopyable=0

注意 moveC 这一列：DtorOnly 和 CopyCtorOnly 都是 1（true），但它们根本没有移动构造函数。这个 trait 在这儿说谎了。

关键陷阱：is_move_constructible 会骗你

std::is_move_constructible<T> 问的是"能不能用 T&& 构造出 T"——而 T&& 完全可以绑到 const T& 上，去调拷贝构造。所以只要类可拷贝，这个 trait 就是 true，跟有没有移动构造无关。

struct Probe {
    static int copies, moves;
    Probe() = default;
    Probe(const Probe&) { ++copies; }
    Probe(Probe&&) noexcept { ++moves; }
};
int Probe::copies = 0;
int Probe::moves  = 0;

让外层的类各自持有一个 Probe p;，然后发起 W b = std::move(a); 看计数器：

struct W_Empty    { Probe p; };
struct W_Dtor     { Probe p; ~W_Dtor() {} };
struct W_CopyCtor { Probe p; W_CopyCtor() = default; W_CopyCtor(const W_CopyCtor&) = default; };
struct W_MoveCtor { Probe p; W_MoveCtor() = default; W_MoveCtor(W_MoveCtor&&) = default; };

clang 23.1.0（-std=c++17 -Wall）实测输出：

W_Empty      probe copies=0  moves=1  -> MOVE
             is_copy_constructible_v=true  is_move_constructible_v=true
W_Dtor       probe copies=1  moves=0  -> COPY(fallback)
             is_copy_constructible_v=true  is_move_constructible_v=true
W_CopyCtor   probe copies=1  moves=0  -> COPY(fallback)
             is_copy_constructible_v=true  is_move_constructible_v=true
W_MoveCtor   probe copies=0  moves=1  -> MOVE
             is_copy_constructible_v=false  is_move_constructible_v=true
类 声明了 编译器生成 结论
W_Empty 无 全部 5 个 移动请求走 Probe(Probe&&)
W_Dtor 析构 拷贝生成，移动被抑制 移动请求退化成拷贝
W_CopyCtor 拷贝构造 移动被抑制 同上
W_MoveCtor 移动构造 拷贝被删除，移动赋值也不生成 只能移动

W_Dtor 那行最扎心：is_move_constructible 是 true，copies 却是 1——编译器按"拷"给你办了。这就是 Item 17 真正的杀手锏：不显式 =default 移动操作，光有移动语义的成员也白搭。

为什么析构会抑制移动？

历史包袱。C++03 时代没有移动语义，写了析构函数说明类在手动管理资源，编译器按成员拷贝生成拷贝操作（指针成员会导致浅拷贝，那是另一回事）。

C++11 引入移动语义后，委员会选择了保守策略：如果你写了析构但没显式写移动，编译器不敢猜你的移动是否安全，干脆不生成。于是移动请求退化成拷贝。

顺带一提：声明了析构后拷贝操作仍会生成，但标准已把这一生成标记为 deprecated（因为"需要自定义析构"几乎总是意味着"需要自定义拷贝"）。实测要注意：clang 23.1.0 把这条诊断拆成了独立开关，-Wall / -Wextra 都不会触发它，必须显式加 -Wdeprecated-copy-with-user-provided-dtor。实测命令与告警原文：

$ clang++ -std=c++17 -Wall -Wdeprecated-copy-with-user-provided-dtor probe.cpp
probe.cpp:11:30: warning: definition of implicit copy constructor for 'W_Dtor'
        is deprecated because it has a user-provided destructor
        [-Wdeprecated-copy-with-user-provided-dtor]
probe.cpp:15:26: note: in implicit copy constructor for 'W_Dtor' first required here

=default 写在类内还是 .cpp：决定类是否 trivial

=default 的位置会改变类的性质。实测（clang 23.1.0，-std=c++17）：

struct Triv {};                                         // 什么都不写
struct InlineDefault { ~InlineDefault() = default; };   // 类内 = default
struct OutOfLine { ~OutOfLine(); };                     // 类内只声明
OutOfLine::~OutOfLine() = default;                      // 类外（.cpp）= default
struct UserProvided { ~UserProvided(); };
UserProvided::~UserProvided() {}                        // 类外手写空函数体

实测输出：

Triv         : trivially_destructible = true,  trivially_copyable = true
InlineDefault: trivially_destructible = true,  trivially_copyable = true
OutOfLine    : trivially_destructible = false, trivially_copyable = false
UserProvided : trivially_destructible = false, trivially_copyable = false

规律：只有"在第一次声明处就 =default"才算 trivial。 类内 ~X() = default; → trivial；先声明 ~X();、再到 .cpp 写 X::~X() = default; → 非 trivial（这在标准里叫 user-provided）。这纠正一个常见误解——"把 =default 挪到 .cpp 能保持 trivial"是错的，恰恰相反。

那为什么还要把 =default 放到 .cpp？真正的理由有三个：① pimpl 惯用法里析构必须在看到完整类型之后才能定义（见 Item 22）；② 减少头文件暴露的内联代码，控制二进制体积；③ ABI 稳定。

常见错误（新手踩坑）

  1. 写了析构忘了补移动操作。直接后果：容器扩容退回拷贝（Item 14），性能静默退化；更糟的是编译器生成的浅拷贝可能 double free。
  2. 以为 is_move_constructible == true 就说明有移动构造。错——只要可拷贝，这个 trait 就是 true。要看真实行为得用计数器探针。

维度 C 怎么做 C++ 怎么做 为什么

一句话总结： C 程序员记住——C++ 的类有 5 个（含默认构造是 6 个）特殊成员函数，声明任何一个都会影响其余的自动生成。最常踩的坑：写了析构 → 移动被抑制 → vector 扩容退回拷贝 → 性能差。优先级：先试 Rule of Zero（把资源交给标准库成员），必须自己管资源时再上 Rule of Five，移动操作记得标 noexcept。

HFT 关联

  • 移动被抑制导致扩容拷贝：Order 写了析构但没写移动构造 → 扩容退回拷贝 → 延迟尖峰。这是 HFT C++ 性能的隐形坑，而且 is_move_constructible 不会告诉你。
  • RAII 资源管理：HFT 代码大量用 RAII 管理锁、文件描述符、共享内存——写析构函数是常态，必须同时补移动操作。
  • 结构体保持 trivial：协议结构体不写任何特殊成员函数（Rule of Zero），保持 trivially copyable，可直接 memcpy 进出网络缓冲区，并用 static_assert(std::is_trivially_copyable_v<Header>) 在编译期锁死这个性质。

自测题

1. 声明了移动构造后，拷贝构造还会自动生成吗？声明了析构呢（C++11）？

答案

声明移动构造后，拷贝构造不再自动生成（被定义为 deleted）。声明析构函数（C++11 起）：移动构造与移动赋值不会生成；拷贝构造与拷贝赋值仍会生成，但这一生成已被标准标记为 deprecated——"需要自定义析构"几乎总是意味着"需要自定义拷贝"，所以不要依赖它。

2. "大五律"是哪五个特殊成员函数？

答案

析构函数、拷贝构造函数、拷贝赋值运算符、移动构造函数、移动赋值运算符。含义：如果需要自定义其中任何一个（通常因为类持有资源），就应该把五个都显式声明清楚（=default / =delete / 手写），否则编译器按抑制规则生成的行为很可能不符合意图。

3. 为什么写了析构函数后移动构造会被抑制？有什么性能影响？

答案

标准认为"用户写了析构函数"意味着该类在手动管理资源，此时逐成员移动很可能是错的，所以干脆不生成——移动请求退化成拷贝。性能影响：容器扩容、push_back、排序等搬移场合，本该 O(1) 的指针搬移退化成深拷贝，表现为扩容时的延迟尖峰，而且是静默的。

4. 为什么说 is_move_constructible 会骗人？怎么才能看到真实行为？

答案

它问的是"能否用 T&& 构造出 T"——而 T&& 能绑到 const T& 上去调拷贝构造。所以只要类可拷贝它就是 true，与是否存在移动构造无关。要看真实行为，用计数器探针：让类持有一个成员，其拷贝/移动构造分别计数，然后发起移动请求看计数器（实测 W_Dtor 的 copies=1, moves=0）。

5. "写了任何一个就五个都声明"为什么重要？

答案

因为生成规则（谁抑制谁）繁琐且随标准演进，靠记忆容易出错，漏掉某个就可能出现"编译通过但行为错误/性能退化"。显式声明五个把意图写进代码：既避免编译器生成错误的浅拷贝/缺失的移动，也让后来者一眼看清这个类的拷贝/移动语义。

6. =default 写在类内和写在 .cpp 里，对类的 trivial 性有什么影响？

答案

写在类内第一次声明处 → 仍然 trivial（非 user-provided）；先声明、再到 .cpp 写 =default → 非 trivial（user-provided）。实测：InlineDefault 的 is_trivially_copyable 为 true，OutOfLine 为 false。所以"挪到 .cpp 能保持 trivial"是错的——真正理由是 pimpl、二进制体积与 ABI 稳定。

7. 下面代码有什么问题？

class Buffer {
    char* data;  size_t size;
public:
    Buffer(size_t n) : data(new char[n]), size(n) {}
    ~Buffer() { delete[] data; }
};
std::vector<Buffer> v;  v.push_back(Buffer(64));   // 悬垂指针 + double free
答案

违反大五律，有严重 bug。有裸指针和析构函数却没有拷贝/移动操作：移动构造被抑制，编译器生成的拷贝构造做浅拷贝（只复制 data 指针）。v.push_back(Buffer(64)) 时临时对象被浅拷贝进 vector，随后临时对象析构执行 delete[] data，vector 里的元素就持有悬垂指针；后续再拷贝、扩容或析构时会重复释放同一块内存（double free）与读野指针。

修正：优先 Rule of Zero——把 char* data 换成 std::vector<char> 或 std::unique_ptr<char[]>，编译器生成的移动/拷贝天然正确（且移动自动 noexcept）。

Q1花括号 vs 圆括号
std::vector<int> v1(10, 20);   // A
std::vector<int> v2{10, 20};   // B

v1 和 v2 分别是什么？为什么不同？

答案与复习指引
  • v1 = 10 个元素，每个值 20（(count, value) 构造）
  • v2 = 2 个元素 {10, 20}（花括号优先匹配 initializer_list 构造）

根因： {} 会优先匹配 initializer_list 构造函数，即使有更精确匹配的 (int, int) 构造函数。

花括号还禁止窄化： int x{3.14}; 编译失败（double→int 窄化），int x(3.14); 合法（静默截断）。

Q2noexcept 与 vector 扩容
class Widget {
public:
    // 版本 A: 没标 noexcept
    Widget(Widget&& o) { /* 移动 */ }
    // 版本 B: 标了 noexcept
    // Widget(Widget&& o) noexcept { /* 移动 */ }
};
std::vector<Widget> v;
for (int i = 0; i < 100; ++i)
    v.push_back(Widget(i));

版本 A 和 B 在扩容时分别用移动还是拷贝？

答案与复习指引
  • 版本 A（无 noexcept）： STL 退回拷贝——因为移动构造可能抛异常，扩容中途异常会导致数据丢失。拷贝保证强异常安全。
  • 版本 B（有 noexcept）： STL 用移动——O(1) 指针交接，扩容从 O(n) 降到 O(n) 但每个元素是 O(1) 移动而非 O(n) 拷贝。

这是 HFT 性能的隐形开关： 移动构造必须标 noexcept，否则 vector 扩容退回拷贝。

Q3override 检查
class Base {
public:
    virtual void f(int x) const {}
};
class Derived : public Base {
public:
    void f(int x) override {}  // 编译成功吗？
};

这段代码编译成功吗？为什么？

答案与复习指引

编译失败。 Derived::f 缺少 const 限定符——签名与 Base::f 不匹配。override 让编译器检查：签名必须完全匹配（const、参数类型、引用限定符）。没有 override，这会静默创建一个新虚函数而非重写。

教训： 重写虚函数时始终加 override，让编译器帮你检查签名。
