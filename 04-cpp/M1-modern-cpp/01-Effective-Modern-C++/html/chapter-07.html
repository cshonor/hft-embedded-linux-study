The Concurrency API — Items 35–40

本章讲什么

C++11 把线程、原子操作、future 首次标准化。但标准并发 API 有不少"看着对、其实错"的坑：std::async 的默认启动策略、std::thread 的异常安全与析构行为、volatile 与 std::atomic 的本质区别。本章是 HFT 并发的入门必修——更深的内容在 02-Cpp-Concurrency（C++ Concurrency in Action）。

各 Item 要点

Item 35：优先 std::async 而非 std::thread

std::thread 是"手动管理线程"，std::async 是"声明并发任务，让运行时管线程"。

auto fut = std::async([]{ return 42; });  // 异步执行，future 取结果

async 的优势：返回 future，异常会通过 future 传播（thread 里抛异常直接 terminate）；运行时可决定是否真正并发（延迟到 get() 才执行，即 std::launch::deferred）。

Item 36：明确指定启动策略

async 默认策略是 async | deferred——运行时可能延迟到 get() 才同步执行，这违背"并发"初衷，且导致 .get() 阻塞。要真正异步，显式指定：

auto fut = std::async(std::launch::async, []{ ... });

launch::async 强制新线程或线程池执行；launch::deferred 强制延迟。默认的"或"策略是最容易被忽略的陷阱——你以为是异步，实际是同步阻塞。

Item 37：让 std::thread 在所有路径都不可联结（joinable）

std::thread 析构时若仍 joinable（既未 join 也未 detach）→ std::terminate。RAII 保证：

class ThreadGuard {
    std::thread t;
public:
    ~ThreadGuard() { if (t.joinable()) t.join(); }
};

或在异常路径用"先 join 后业务逻辑"的顺序，确保异常发生时线程已安全收尾。

Item 38：理解线程句柄的析构与联结行为

句柄类型 析构行为
std::thread joinable 则 terminate
std::future 阻塞等待（共享状态未就绪时）——析构会等任务完成
std::shared_future 不阻塞（多个 shared_future 共享状态）

future 析构会阻塞这一行为反直觉——它让你"忘了 get 也能拿到结果"，但也可能让程序在意外处卡住。

Item 39：单次事件用 std::future + std::promise / std::experimental::latch / condition_variable

经典模式：一个线程等另一个线程"完成一次初始化"。用 std::promise<void> 发信号 + future.get() 阻塞等待，比手写 condition_variable + flag 更不易错（无虚假唤醒、无锁泄漏）。C++20 的 std::latch / std::barrier 是这类同步原语的标准化封装。

Item 40：std::atomic 用于并发，volatile 用于特殊内存——别混用

二者完全不同：

std::atomic volatile
目的 多线程数据竞争 告诉编译器"别优化此内存访问"（MMIO）
可见性 保证（内存屏障） 不保证跨线程可见性
原子性 保证 不保证
指令重排 阻止相关重排 不阻止

volatile 在 C++ 里不是线程同步工具——它只防编译器把读写优化掉（如硬件寄存器、mmap 内存）。多线程共享变量必须用 std::atomic 或 mutex。这是 C++ 程序员最普遍的误解之一。

HFT 关联

  • std::launch::async 必显式：HFT 异步任务（如批量风控检查）若用默认 async 策略，可能被延迟到 get() 同步执行，热路径意外阻塞。务必 launch::async。
  • std::atomic 而非 volatile：行情计数器、序号用 std::atomic<uint64_t>，保证跨核可见性 + 原子性。volatile 只用于 mmap 的硬件寄存器映射（DPDK PMD 配置寄存器）。混用是经典数据竞争来源。
  • std::thread 析构 terminate：HFT 守护进程里 std::thread 析构时若仍 joinable 会直接 terminate 拉崩整个进程——用 RAII 守卫或显式 join/detach。
  • future 阻塞析构：异步风控任务用 future，但要确保不在热路径析构 future（析构会等任务完成）——把 future 存到后台线程或用 shared_future。
Item 35

Item 35：优先 std::async 而非 std::thread

第 7 章 并发 API · Item 35 · 下一节：Item 36 启动策略

为什么要学这个（先建立直觉）

std::thread 是「线程制」思维：你向操作系统要一个线程，自己管它的生（创建）死（join/detach），它跑什么、什么时候跑、跑完结果给谁，全得你自己搭管道。C 程序员对这个模型很熟——它就是 pthread_create 的 C++ 包装，连缺点都原样继承：返回值要靠 void* 强转，异常出了线程边界就是进程死刑。

std::async 是「任务制」思维：你只声明「这件事要并发做」，返回一个 future 作为结果的提货单。底层是新线程还是线程池、什么时候调度，由运行时操心。你关心的是任务和结果，不是线程这个硬件资源的账本。

这不是风格之争。三个硬差异——返回值通道、异常传播、资源管理——每一个都能在真机上立刻演示出来：thread 里抛异常的进程退出码是 134（SIGABRT），async 里抛异常的进程正常结束。下面全部实测。

这节讲什么

  1. 返回值：thread 没有任何返回值机制（要自己搭 promise），async 直接 future::get()；
  2. 异常：thread 里逃逸的异常 → std::terminate → 进程 abort（实测退出码 134）；async 的异常穿透到 get() 处 rethrow，可正常 try-catch；
  3. 资源管理：thread 是稀缺硬件资源（超订问题），async 把调度权交给运行时；
  4. 任务制 vs 线程制心智模型对比表。

返回值：async 有通道，thread 没有

std::async 返回 std::future<T>，get() 直接拿到任务的返回值。std::thread 的 lambda 返回值被直接丢弃——想拿结果得自己搭 std::promise 管道，异常还得手动 set_exception：

#include <future>
#include <iostream>
#include <thread>

int compute() { return 42; }

int main() {
    // async：一行搞定
    auto fut = std::async(std::launch::async, compute);
    std::cout << "async 返回值 = " << fut.get() << "\n";

    // thread：promise/future 管道全手动
    std::promise<int> p;
    auto pfut = p.get_future();
    std::thread t([pp = std::move(p)]() mutable {
        try {
            pp.set_value(compute());
        } catch (...) {
            pp.set_exception(std::current_exception());  // 异常也得手动传
        }
    });
    std::cout << "thread+promise 拿到 = " << pfut.get() << "\n";
    t.join();
    return 0;
}

本机实测（clang 23.1.0，-std=c++17 -Wall）输出：

async 返回值 = 42
thread+promise 拿到 = 42

两种写法结果相同，但 thread 版本多出 6 行管道代码，且每一处都是出错点（忘 set_exception、promise 提前析构等）。async 把这些全部收进标准库。

异常：thread 判死刑，async 穿透到 get()

栈展开不跨线程。thread 里没被捕获的异常没有任何人能接住，运行后直接 std::terminate：

#include <iostream>
#include <stdexcept>
#include <thread>

int main() {
    std::thread t([]{
        throw std::runtime_error("boom from thread");
    });
    t.join();
    std::cout << "这行永远不会执行\n";
    return 0;
}

本机实测（clang 23.1.0）stderr 原文与退出码：

libc++abi: terminating due to uncaught exception of type std::runtime_error: boom from thread

exit=134

退出码 134 = 128 + 6，即进程被 SIGABRT 杀死——不是优雅退出，是堕胎式终止。整个进程陪葬，包括所有无辜线程。

async 版本同一个异常，命运完全不同：

#include <future>
#include <iostream>
#include <stdexcept>

int main() {
    auto bad = std::async(std::launch::async, []() -> int {
        throw std::runtime_error("boom from async");
    });
    try {
        (void)bad.get();   // 异常在这里 rethrow，被本线程 catch
    } catch (const std::runtime_error& e) {
        std::cout << "捕获到异常: " << e.what() << "\n";
    }
    std::cout << "进程正常结束\n";
    return 0;
}

本机实测（clang 23.1.0）输出，退出码 0：

捕获到异常: boom from async
进程正常结束

机制：任务抛出的异常被 async 的实现捕获，存进 future 的共享状态；get() 时在调用方线程重新抛出，走正常的 try-catch 路径。代价是要记得 get()——没人 get()，异常就被静默丢弃（顺带一提：clang 23 的 libc++ 给 get() 标了 [[nodiscard]]，忽略它会吃 -Wunused-result 警告，实测如此）。

资源管理：线程是稀缺资源

std::thread 直接对应 OS 线程：创建有内核开销，数量有上限，创建失败抛 std::system_error。如果并发请求突然暴涨（行情风暴时风控任务激增），手动 std::thread 的版本只有两个结局：超订（oversubscription——线程数远超核数，调度抖动摧毁延迟）或直接抛异常拒绝服务。不要真去试创建十万线程——文档层面理解即可：线程是硬件资源，像文件描述符一样会被耗尽。

std::async 把「任务」和「线程」解耦：你提交任务，运行时可以新开线程、复用线程池、甚至（默认策略下）推迟执行（Item 36 的陷阱在这里埋下伏笔）。理想实现下，任务制让并发度自动匹配硬件能力。

心智模型对比：

维度 std::thread（线程制） std::async（任务制）
抽象 OS 线程的句柄 异步任务的提货单（future）
返回值 无机制，手动搭 promise future::get()
异常 逃逸即 std::terminate（实测 exit 134） 存进 future，get() 时 rethrow
线程管理 手动 join/detach，忘 join 析构即 terminate 运行时托管
资源控制 程序员自行防超订 实现可池化/延迟（默认策略下）
适用 需要精细控制线程本身（亲和性、栈大小、专用线程） 绝大多数「并发做件事」的场景

完整可运行例子

async 的两大能力合在一个程序里：

#include <future>
#include <iostream>
#include <stdexcept>

int compute() { return 42; }

int main() {
    // 1. 返回值通道
    auto fut = std::async(std::launch::async, compute);
    std::cout << "async 返回值 = " << fut.get() << "\n";

    // 2. 异常穿透：任务里 throw，get() 时 rethrow
    auto bad = std::async(std::launch::async, []() -> int {
        throw std::runtime_error("boom from async");
    });
    try {
        (void)bad.get();
    } catch (const std::runtime_error& e) {
        std::cout << "捕获到异常: " << e.what() << "\n";
    }
    std::cout << "进程正常结束\n";
    return 0;
}

本机实测（clang 23.1.0，-std=c++17 -Wall）输出：

async 返回值 = 42
捕获到异常: boom from async
进程正常结束

常见错误（新手踩坑）

  1. std::thread 里让异常逃逸。实测进程直接被 SIGABRT 杀死（exit 134），libc++abi: terminating due to uncaught exception——所有线程陪葬。修正：线程函数体内兜底 try-catch，或改用 std::async。
  2. 以为 std::thread 的 lambda 返回值能拿回来。返回值被直接丢弃。修正：要结果就用 std::async；坚持用 thread 就自己搭 std::promise 管道（含 set_exception）。
  3. std::thread 析构时忘记 join/detach。joinable 的 thread 析构即 std::terminate（Item 37 详讲）。修正：RAII 封装或改用 async。
  4. async 返回的 future 从不 get()。任务里的异常被静默丢弃，且默认/强制 async 策略下 future 析构会阻塞到任务完成（Item 38）。修正：结果和异常都要取。

HFT 关联

  • 守护任务的异常隔离：风控预检、日志落盘、快照上传这类后台任务用 std::async——任务抛异常穿透到 get()，守护进程捕获后继续跑；用裸 std::thread，一次未捕获异常就是整个交易进程 SIGABRT（实测 exit 134），盘中事故。
  • 热路径仍用专用 thread：async 是「任务制」便利，但延迟关键的行情处理线程需要钉核（CPU affinity）、实时调度、自定义栈——这些是 std::thread（或 pthread）的领域。规则：后台任务用 async，热路径专用线程用 thread 并自己管好它。
  • 防超订：行情风暴触发的瞬时任务洪峰，裸 thread 版本会超订拖垮全系统；async（尤其配合线程池实现）给出自然的并发上限。
  • future 即回执：std::async 返回的 future 天然是任务回执——下单网关异步确认、回测任务批量收集结果，get()/wait_for() 就是同步点。

自测题

1. std::async 相比 std::thread 的三个核心优势是什么？

答案

①返回值通道：async 返回 std::future<T>，get() 直接拿结果；thread 无任何机制，要自己搭 std::promise。②异常安全：任务异常被存进 future，get() 时在调用方线程 rethrow，可 try-catch；thread 里逃逸的异常直接 std::terminate（本文实测进程被 SIGABRT 杀死，exit 134）。③资源管理：async 把线程生命周期和调度交给运行时（可池化）；thread 要手动 join/detach，析构时 joinable 即 terminate，且线程是稀缺资源，手动管理有超订风险。

2. std::thread 的线程函数里抛出未捕获异常，会发生什么？退出码是多少？

答案

栈展开不跨线程，没有任何人能捕获这个异常，运行时调用 std::terminate()，进程被 SIGABRT 杀死。本机实测 stderr 输出 libc++abi: terminating due to uncaught exception of type std::runtime_error: boom from thread，退出码 134（= 128 + SIGABRT 的 6）。「这行永远不会执行」——t.join() 之后的代码没有机会跑。

3. std::async 任务的异常如何到达调用方？如果没人调用 get() 会怎样？

答案

任务抛出的异常被 async 实现捕获并存入 future 的共享状态；调用方 get() 时异常在自己的线程里被 rethrow，走正常 try-catch（本文实测捕获到 boom from async，进程 exit 0）。如果从不 get()，异常被静默丢弃——任务失败无人知晓。另外 libc++ 给 get() 标了 [[nodiscard]]，忽略返回值会有编译警告。

4. 坚持用 std::thread 又想拿返回值，怎么办？代价是什么？

答案

自己搭 std::promise<T>/std::future<T> 通道：线程里 set_value(compute())，异常路径还要 set_exception(std::current_exception())，主线程 fut.get()。本文实测该写法输出正确（42），但比 std::async 多出约 6 行管道代码，每一处（promise 移动进线程、异常转发、join）都是出错点。本质上你手工重新实现了 async 已经提供的东西。

5. 什么是超订（oversubscription）？为什么 std::async 能缓解它？

答案

超订指并发线程数远超硬件核数：每个 std::thread 直接对应 OS 线程，任务洪峰时线程暴涨，上下文切换和缓存抖动摧毁延迟，线程耗尽还会抛 std::system_error。std::async 把任务与线程解耦——实现可以用线程池让并发度匹配硬件，或（默认策略下）推迟执行；程序员只提交任务，不直接持有线程这个稀缺资源。

6. 什么场景反而应该用 std::thread 而不是 std::async？

答案

需要控制线程本身而非只是并发执行任务时：钉核（CPU affinity）、实时调度策略、自定义栈大小、线程特定的 TLS 生命周期管理、长期存活的专用线程（如 HFT 热路径的行情处理线程）。async 不暴露这些控制面。简记：要「一个听话的线程」用 thread，要「一件并发完成的事」用 async。

Item 36：明确指定启动策略

第 7 章 并发 API · Item 36 · 上一节：Item 35 async vs thread

为什么要学这个（先建立直觉）

C 程序员的并发直觉来自 pthread_create：调用返回时，新线程一定已经开始跑了。把这套直觉带进 std::async 会踩到 C++ 并发 API 最隐蔽的坑：std::async(f) 的默认启动策略不是「异步执行」，而是 std::launch::async | std::launch::deferred——标准允许实现二选一，选哪个由运行时说了算。

如果运行时选了 deferred，你的任务根本不会在新线程上跑。它被推迟到你对 future 调用 get() 或 wait() 的那一刻，在调用方的线程里同步执行。你以为「这事在后台跑着呢」，实际它安安静静躺在 future 里睡大觉；如果始终没人 get()，它就永远不执行。

这个行为因平台、因负载而异，难以复现。防御方法只有一条：把策略写出来。要么 std::launch::async（真异步），要么 std::launch::deferred（明说我要延迟），别让运行时替你掷骰子。

这节讲什么

  1. 默认策略 async | deferred 的语义：实现可二选一；
  2. deferred 实测：不 get()/wait() 就不执行，wait_for(0) 返回 future_status::deferred；
  3. 强制 launch::async：没 get() 任务已在跑（实测）；
  4. deferred 在 GUI/事件循环里的饥饿陷阱，以及本机默认策略的实际选择。

默认策略：运行时可以二选一

auto fut = std::async([]{ return heavy_work(); });
// 等价于 std::async(std::launch::async | std::launch::deferred, ...)
// 标准允许实现：
//   1. 立即在新线程执行（async）
//   2. 推迟到 get()/wait() 才在调用方线程同步执行（deferred）
// 你无法从调用代码看出选了哪条！

两条路的行为差异是本质性的：async 下任务与调用方并发；deferred 下任务与调用方串行，且执行时机被推迟到 future 被取值的那一刻。「默认策略」把并发语义变成了实现细节——这正是要避开它的原因。

deferred 实测：不 get 就不跑

显式指定 launch::deferred，用标志位观察任务是否真的执行过：

#include <chrono>
#include <future>
#include <iostream>
#include <thread>

int main() {
    bool ran = false;
    auto fut = std::async(std::launch::deferred, [&] {
        ran = true;
        std::cout << "任务体执行\n";
        return 42;
    });

    std::this_thread::sleep_for(std::chrono::milliseconds(200));
    std::cout << "创建 200ms 后 ran = " << ran << "（任务没跑）\n";

    // wait_for(0) 检测 deferred
    auto st = fut.wait_for(std::chrono::seconds(0));
    std::cout << "wait_for(0) == future_status::deferred ? "
              << (st == std::future_status::deferred) << "\n";
    std::cout << "检测后 ran = " << ran << "（wait_for 不触发执行）\n";

    std::cout << "get() = " << fut.get() << "\n";
    std::cout << "get 之后 ran = " << ran << "\n";
    return 0;
}

本机实测（clang 23.1.0，-std=c++17 -Wall）输出：

创建 200ms 后 ran = 0（任务没跑）
wait_for(0) == future_status::deferred ? 1
检测后 ran = 0（wait_for 不触发执行）
get() = 任务体执行
42
get 之后 ran = 1

三个要点全被坐实：①创建后等了 200ms，ran 仍是 0——任务根本没跑；②wait_for(0) 返回 future_status::deferred——这是检测 deferred 的标准手法，且 wait_for 不会触发执行；③get() 的那一刻任务才在当前线程同步执行（注意输出顺序：get() = 之后才是 任务体执行，然后才是返回值 42）。

强制 launch::async：真异步

#include <chrono>
#include <future>
#include <iostream>
#include <thread>

int main() {
    bool ran = false;
    auto fut = std::async(std::launch::async, [&] {
        ran = true;
        return 42;
    });
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::cout << "100ms 后 ran = " << ran << "（还没 get 就已执行）\n";
    std::cout << "get() = " << fut.get() << "\n";

    // 对照：本机默认策略实际选了哪条？
    bool ran2 = false;
    auto fut2 = std::async([&] { ran2 = true; return 1; });   // 默认策略
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::cout << "默认策略 100ms 后 ran2 = " << ran2 << "\n";
    std::cout << "fut2.get() = " << fut2.get() << "\n";
    return 0;
}

本机实测（clang 23.1.0）输出：

100ms 后 ran = 1（还没 get 就已执行）
get() = 42
默认策略 100ms 后 ran2 = 1
fut2.get() = 1

launch::async 下任务在 100ms 内已在别的线程跑完，没等 get()。本机（libc++）的默认策略这次选了 async（ran2 = 1）——但这是实现的当前选择，不是标准保证。换 STL（MSVC）、换负载、换版本都可能选 deferred；依赖默认策略就是把正确性押在你控制不了的变量上。

三种策略对比：

策略 行为 任务何时执行 适用场景
launch::async 强制新线程异步执行 async 调用后立即 真并发任务
launch::deferred 推迟到 get()/wait() 在调用方线程同步执行 取值那一刻；无人取值则永不执行 惰性求值
默认（async \| deferred） 实现二选一 不确定 不要用

deferred 的饥饿陷阱（场景描述）

deferred 最毒的用法是配 wait_for 轮询：

auto fut = std::async([]{ return heavy_work(); });   // 若被 deferred……
while (fut.wait_for(std::chrono::milliseconds(100)) != std::future_status::ready) {
    do_ui_frame();   // GUI 主线程继续渲染
}
// 循环永远出不来：deferred 任务只有 get()/wait() 才执行，
// wait_for 不算数（实测）→ ready 永远等不到 → 死循环

在 GUI / 事件循环线程上这就是饥饿：事件循环每转一圈都检查一次 future，future 永远不是 ready（deferred 任务在等待一个永远不会来的 get()），界面卡死但 CPU 占用看起来正常。同类事故在交易系统的监控线程里同样成立：「等后台任务完成再上报」的轮询循环，遇到 deferred 就是无限等待。防御手法是检测后补救：

if (fut.wait_for(std::chrono::seconds(0)) == std::future_status::deferred) {
    // 被 deferred 了：要么就地同步执行，要么改用 launch::async 重发任务
    fut.wait();   // wait() 会触发 deferred 任务执行
}

但更干净的做法仍是源头控制：创建时就写 std::launch::async。

完整可运行例子

两种策略并排对照（上文两段实测代码的精简合体）：

#include <chrono>
#include <future>
#include <iostream>
#include <thread>

int main() {
    bool a = false, d = false;

    auto fa = std::async(std::launch::async, [&] { a = true; return 1; });
    auto fd = std::async(std::launch::deferred, [&] { d = true; return 2; });

    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::cout << "100ms 后：async 任务已执行?" << a
              << "  deferred 任务已执行?" << d << "\n";
    std::cout << "fd.wait_for(0) 是 deferred? "
              << (fd.wait_for(std::chrono::seconds(0))
                  == std::future_status::deferred) << "\n";
    std::cout << "fa.get()=" << fa.get() << "  fd.get()=" << fd.get() << "\n";
    std::cout << "get 之后：d = " << d << "\n";
    return 0;
}

本机实测（clang 23.1.0，-std=c++17 -Wall）输出：

100ms 后：async 任务已执行?1  deferred 任务已执行?0
fd.wait_for(0) 是 deferred? 1
fa.get()=1  fd.get()=2
get 之后：d = 1

同一行时间点上两个任务状态相反：async 已跑完，deferred 纹丝未动——直到 fd.get() 才执行。

常见错误（新手踩坑）

  1. 用默认策略以为「一定在后台跑」。默认是 async | deferred，实现可二选一；若被 deferred，fut.get() 那一刻任务在你的线程同步执行，热路径当场阻塞一次完整计算。修正：显式写 std::launch::async。
  2. 用 wait_for(0) == ready 检测 deferred。deferred 任务永远不报 ready——检测值应是 std::future_status::deferred（实测返回的正是它）。wait_for/wait_for(0) 都不会触发 deferred 任务执行（实测）。
  3. deferred 任务配 wait_for 轮询。循环条件 wait_for(...) != ready 永远成立——死循环（GUI 饥饿陷阱，见上节）。修正：检测到 deferred 后 wait()（会触发执行），或源头改用 launch::async。
  4. 显式 launch::async 后忽略资源失败。强制 async 在系统线程资源耗尽时抛 std::system_error；高并发场景要 catch 住并降级（比如回落到同步执行）。

HFT 关联

  • 延迟确定性：HFT 最怕「不可预测的同步阻塞」——默认策略下一个本该后台跑的风控检查可能被推迟到 get() 时在关键线程同步执行，造成延迟尖峰。规则：所有 std::async 调用必须带显式策略，代码评审 grep std::async( 后面跟的不是 std::launch 的全部打回。
  • 后台任务用 launch::async：日志落盘、快照上传、异步风控——std::async(std::launch::async, ...) 保证调用后立刻离开当前线程。
  • 配置懒加载可用 launch::deferred：启动时不算、第一次用到才算的开销（如非关键路径的模型参数），用 deferred 明说「惰性求值」意图——但必须确保取值点不在热路径上。
  • 事件循环线程警惕 deferred：网关的 epoll 循环、GUI 监控线程里若用 future 轮询等待默认策略的 async 任务，撞上 deferred 就是死等——检测 future_status::deferred 或干脆只在事件循环外用 async。

自测题

1. std::async(f) 的默认启动策略是什么？为什么它危险？

答案

默认策略是 std::launch::async | std::launch::deferred——标准允许实现二选一，由运行时决定。若选了 deferred，任务不立即执行，而是推迟到 get()/wait() 时在调用方线程同步执行；始终不取值则永不执行。危险在于并发语义变成了实现细节：因平台、负载而异，难以复现，「以为在后台跑实际同步阻塞」的 bug 无法从调用代码看出。

2. 如何检测一个 future 对应的任务被 deferred 了？检测本身会触发任务执行吗？

答案

用 fut.wait_for(std::chrono::seconds(0))，返回 std::future_status::deferred 即为 deferred（真异步任务会返回 ready 或 timeout）。本文实测：deferred 任务创建 200ms 后仍未执行，wait_for(0) 返回 deferred，且检测后任务依然没跑——wait_for 不会触发执行，只有 get()/wait() 会。

3. deferred 任务在什么确切时机执行？在哪个线程？

答案

在对返回的 future 首次调用 get() 或 wait() 的那一刻执行，在发起该调用的线程上同步执行（不是新线程）。本文实测输出顺序 get() = 任务体执行 → 42 证明执行夹在 get() 调用之中。若始终无人 get()/wait()，任务永不执行。

4. 为什么 GUI/事件循环里 deferred 会导致饥饿？

答案

典型写法是 while (fut.wait_for(...) != ready) { 继续处理事件; }。deferred 任务只有 get()/wait() 才执行，wait_for 不算——所以 future 永远不会变成 ready，循环永远出不来：事件循环卡死，任务也永远没跑，界面冻结但 CPU 占用正常。本文实测确认 wait_for 不触发 deferred 任务。修正：检测到 deferred 后用 wait()，或源头显式 launch::async。

5. 强制真异步的正确写法是什么？它可能抛什么异常？

答案

auto fut = std::async(std::launch::async, f, args...);——保证任务在新线程异步执行（本文实测：100ms 后未 get() 任务已执行完）。若系统线程资源耗尽导致无法创建新执行上下文，抛 std::system_error；高并发场景应 catch 并降级（如回落到同步执行）。

6. 本机实测默认策略选了 async，能否据此在代码里放心用默认策略？

答案

不能。本机（clang 23.1.0 + libc++）这次默认策略选了 async（实测 ran2 = 1），但这只是该实现的当前选择——标准明文允许二选一，换标准库实现（libstdc++、MSVC STL）、换版本、换负载都可能变成 deferred。把正确性押在实现细节上是隐患；显式写出策略才能让行为成为代码的一部分。

Item 37：让 std::thread 在所有路径都不可联结（joinable）

为什么要学这个（先建立直觉）

C 程序员用 pthread 时，忘了 pthread_join 只是资源泄漏——进程不会崩，顶多少几个线程槽：

pthread_t tid;
pthread_create(&tid, NULL, worker, NULL);
// 忘了 pthread_join → 线程资源泄漏，但进程不崩

C++ 的 std::thread 把这条"忘了也没关系"的路径直接封死了：只要 thread 对象析构时还处于 joinable 状态（既没 join 也没 detach），标准规定调用 std::terminate——整个进程当场死亡，不只是这个线程出事。

这不是标准委员会吓唬人。没人 join 的线程几乎必然意味着：函数返回后它还在访问已销毁的栈变量，或在你以为"程序已干净退出"时还在写全局状态。与其让你悄悄拿到 UB 定时炸弹，不如当场炸给你看。核心纪律一句话：std::thread 析构前必须 unjoinable——join()、detach()、move 走、或没启动过，四选一。难点在"所有路径"：正常 return 你记得 join，异常路径、中间 return 呢？

这节讲什么

joinable 的精确定义；本机实测 joinable 析构 → std::terminate 的真实报错与退出码；五种安全写法逐条跑通（join / detach / 默认构造 / move / RAII 守卫）；RAII 析构的两种策略（join 派 vs detach 派）与各自风险。

joinable 的精确定义

一个 std::thread 对象 joinable() == true，当且仅当它关联着一个活跃的、尚未结束的执行线程。以下四种情况 joinable() 为 false：

状态 joinable() 析构行为
关联了活跃线程，未 join 未 detach true std::terminate
已 join() false 安全
已 detach() false 安全
默认构造（从未关联线程） false 安全
被 move 走（所有权已转移） false 安全

析构规则一句话：析构时 joinable() 为真 → terminate；为假 → 什么都不做。注意 join()/detach() 对已 unjoinable 的线程调用同样是错误（抛 std::system_error），所以守卫代码里必须先判断 joinable()。

实测 1：joinable 析构 → terminate（本机实测 clang 23.1.0）

#include <thread>
#include <cstdio>

void work() {
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
}

int main() {
    std::puts("main: creating thread...");
    {
        std::thread t(work);
        std::puts("main: leaving scope WITHOUT join/detach");
    }  // t 析构时仍 joinable → std::terminate
    std::puts("main: you should never see this line");
    return 0;
}

clang 23.1.0 + -std=c++17 -Wall 编译零警告，运行结果：

main: creating thread...
main: leaving scope WITHOUT join/detach
libc++abi: terminating
exit code: 134

最后一行 you should never see this line 果然没打印。退出码 134 = 128 + 6，即进程收到 SIGABRT 自杀——std::terminate 默认调用 std::abort，libc++ 在 stderr 留下一句 libc++abi: terminating 就算遗言了。注意它不会告诉你"是哪个 thread 没 join"，生产环境排查只能靠 core dump 或日志。

实测 2：五条安全路径逐一验证（本机实测 clang 23.1.0）

#include <thread>
#include <cstdio>

void work(int id) {
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
    std::printf("worker %d done\n", id);
}

// RAII 守卫：析构里 join（等线程跑完才放行）
class ThreadGuardJoin {
    std::thread t_;
public:
    explicit ThreadGuardJoin(std::thread&& t) : t_(std::move(t)) {}
    ~ThreadGuardJoin() { if (t_.joinable()) t_.join(); }
    ThreadGuardJoin(const ThreadGuardJoin&) = delete;
    ThreadGuardJoin& operator=(const ThreadGuardJoin&) = delete;
};

int main() {
    {   // 路径 1：join 后析构
        std::thread t(work, 1);
        std::printf("before join: joinable() = %d\n", t.joinable());
        t.join();
        std::printf("after join:  joinable() = %d\n", t.joinable());
    }
    std::puts("path 1 (join): survived");

    {   // 路径 2：detach 后析构
        std::thread t(work, 2);
        t.detach();
        std::printf("after detach: joinable() = %d\n", t.joinable());
    }
    std::puts("path 2 (detach): survived");
    std::this_thread::sleep_for(std::chrono::milliseconds(50));

    {   // 路径 3：默认构造，从未关联线程
        std::thread t;
        std::printf("default ctor: joinable() = %d\n", t.joinable());
    }
    std::puts("path 3 (default): survived");

    {   // 路径 4：move 转移所有权，源对象不再 joinable
        std::thread t1(work, 3);
        std::thread t2 = std::move(t1);
        std::printf("after move: t1.joinable() = %d, t2.joinable() = %d\n",
                    t1.joinable(), t2.joinable());
        t2.join();
    }
    std::puts("path 4 (move): survived");

    {   // 路径 5：RAII 守卫，离开作用域自动 join
        ThreadGuardJoin g(std::thread(work, 4));
        std::puts("guard scope: about to leave");
    }
    std::puts("path 5 (RAII guard): survived");
    return 0;
}

实测输出（关键看 joinable() 的翻转时机）：

before join: joinable() = 1
worker 1 done
after join:  joinable() = 0
path 1 (join): survived
after detach: joinable() = 0
path 2 (detach): survived
worker 2 done
default ctor: joinable() = 0
path 3 (default): survived
after move: t1.joinable() = 0, t2.joinable() = 1
worker 3 done
path 4 (move): survived
guard scope: about to leave
worker 4 done
path 5 (RAII guard): survived
exit code: 0

三条要点被输出直接证实：join()/detach() 后 joinable() 立即变 0；move 之后源对象 t1 变 0、目标 t2 为 1（责任跟着所有权走）；RAII 守卫里 worker 4 的 done 打印在 path 5 survived 之前——说明析构里的 join 是真的在等线程跑完。

RAII 守卫：join 派 vs detach 派

ThreadGuard 析构里到底调 join() 还是 detach()？这是两种设计哲学：

join 派（等线程跑完）： 安全、语义确定，但析构会阻塞——线程是死循环或长任务时守卫所在作用域退不出去，异常栈展开期间阻塞尤其危险。

detach 派（放手不管）： 不阻塞，但线程完全失控——若按引用捕获了局部变量，守卫放行后线程访问的是已销毁的栈内存，UB。

C++20 的标准答案： 标准库替你做了选择——std::jthread 析构时先 request_stop() 再 join()，线程体只要定期检查 std::stop_token 就能被协作式打断，兼顾了"不泄漏"和"不死等"。C++17 及以前就自己写 ThreadGuard，绝大多数场景选 join 派。

错误 1：异常路径忘了 join

void process() {
    std::thread t(work);

修正： 用 RAII 守卫（或 C++20 std::jthread），析构自动 join，异常路径也安全。

    int id = 42;

修正： 按值捕获 [id]，或用 shared_ptr 共享生命周期，或干脆别 detach。

错误 3：对已 unjoinable 的线程再 join

修正： 调 join()/detach() 前先判 joinable()——这正是守卫类析构里那行 if 存在的原因。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
线程创建 pthread_create std::thread RAII 对象，不是裸 ID
忘了 join 资源泄漏 terminate 进程崩溃 C++ 强制生命周期纪律

HFT 关联

  • 守护进程崩溃纪律：任何一条异常路径漏掉 join，后果不是泄漏而是整个交易进程 terminate——风控、行情线程的创建处一律 RAII 化。
  • 热路径不 join：行情回调里绝不创建需 join 的短线程（join 阻塞 = 延迟抖动）；要么线程池预创建，要么 detach 但严格按值捕获。
  • 退出码监控：进程以 134（SIGABRT）退出且日志有 terminating，优先怀疑 std::thread 的 terminate，而非段错误（139）。

自测题

1. std::thread 析构时仍 joinable 会发生什么？退出码大概是什么样？

答案

调用 std::terminate，默认进而调用 std::abort，整个进程以 SIGABRT 终止。本机实测退出码 134（128+6），stderr 输出 libc++abi: terminating。不会自动帮你 join，也不会只杀那个线程。

2. 哪四种情况下 joinable() 为 false？

答案

已 join()、已 detach()、默认构造从未关联线程、被 move 走（所有权已转移给另一个 thread 对象）。这四种状态下析构都是安全的。

3. 为什么 ThreadGuard 析构里写的是 if (t.joinable()) t.join(); 而不是直接 t.join();？

答案

对 unjoinable 的线程调 join() 会抛 std::system_error（invalid argument）。守卫对象可能被 move 过、或构造时拿到了空 thread，析构里必须先判 joinable()。而且析构函数里再抛异常（栈展开中）会直接 terminate，所以这层保护是双重的。

4. RAII 守卫析构里选 join 还是 detach，各自的风险是什么？

答案

join 派：析构阻塞，线程不结束作用域就退不出去（死循环线程 = 挂死），但语义安全。detach 派：不阻塞，但线程失控，若按引用捕获了局部变量，守卫放行后线程访问的是已销毁内存（UB）。C++20 std::jthread 用 request_stop() + join 的协作式取消给出了标准答案。

5. move 一个 std::thread 之后，源对象析构安全吗？实测中 t1/t2 的 joinable() 各是多少？

答案

安全。实测输出 after move: t1.joinable() = 0, t2.joinable() = 1——所有权（和 join 责任）转移到 t2，源对象 t1 变为 unjoinable，析构什么都不做。

6. 下面代码有什么问题？

void work() {
    int data = 42;
    std::thread t([&data]{ process(data); });
    t.detach();
}
答案

detach() 后 work() 立即返回，data 销毁，而线程按引用捕获了它——悬垂引用，UB。修正按推荐顺序：① 按值捕获 [data]；② 改用 RAII/jthread 让 work() 等线程结束；③ 数据用 shared_ptr 共享生命周期。

Item 38：理解线程句柄的析构与联结行为

第 7 章 并发 API · Item 38 · 上一节：Item 37 thread joinable · 下一节：Item 39 单次事件

为什么要学这个（先建立直觉）

std::async 的字面意思是"异步"——你发起一个任务，拿到一个 future，然后去忙别的。但下面这段代码的行为和直觉完全相反：

{
    auto fut = std::async(std::launch::async, []{ long_task(); });
    // 没调用 get()，没调用 wait()，你以为 fut 析构就是扔掉句柄
}  // 实际：程序在这一行阻塞，直到 long_task 跑完

你以为写了个"发射后不管"的异步调用，编译器却在 fut 的析构点悄悄帮你 join 了那个线程。这个阻塞出现在一个完全没有任何函数调用痕迹的地方——只是离开了一个作用域。在热路径上，这就是一次无法从代码表面看出来的同步卡顿。

更麻烦的是，这条规则不是所有 future 都遵守：只有 std::async（非 deferred）创建的那一份共享状态才有"最后一个句柄析构时阻塞"的特殊待遇，std::packaged_task 和 std::promise 产生的 future 析构时抬腿就走。不搞清楚边界，你既会在不该卡的地方卡住，也会在以为有阻塞保证的地方失去保证。

这节讲什么

future 析构的阻塞规则及其精确边界：只对 std::async（launch::async）创建的共享状态生效，且只在最后一个引用该共享状态的句柄被释放时触发——相当于隐式 join。本机实测用 chrono 计时证明：async 的 future 析构阻塞约等于任务时长，packaged_task / promise 的 future 析构零等待。

规则本身：什么时候阻塞，什么时候不阻塞

共享状态的来源 最后一个句柄析构时 类比
std::async + launch::async 阻塞，直到任务完成（隐式 join） 隐形的 t.join()
std::async + launch::deferred 不阻塞（任务根本没启动） 惰性求值被丢弃
std::packaged_task::get_future() 不阻塞 普通句柄
std::promise::get_future() 不阻塞 普通句柄

标准的措辞是：async（async 策略）创建的异步任务，其线程完成 synchronizes-with "第一个成功观察到共享状态就绪的函数的返回"或"最后一个释放该共享状态的函数的返回"，两者取先发生者。所以触发阻塞的不是"future 这个类"，而是"async 共享状态的最后一次释放"——调用 get()/wait() 已经观察到就绪的话，之后的析构自然不再等。

这也解释了为什么阻塞存在：async 任务可能按引用捕获了调用者的局部变量，如果句柄析构时拍屁股走人，任务就变成了野线程。这个隐式 join 和 Item 37 的 terminate 是同一种思路——标准库不允许你"忘记"一个正在跑的线程。

实测：四种来源的 future 析构计时（本机实测 clang 23.1.0）

任务固定 sleep 300ms，所有 future 都不调 get()/wait()，只在作用域结束处析构，用 chrono 量作用域退出时刻：

#include <chrono>
#include <cstdio>
#include <future>
#include <thread>

using Clock = std::chrono::steady_clock;
using Ms = std::chrono::milliseconds;

long long elapsed_ms(Clock::time_point t0) {
    return std::chrono::duration_cast<Ms>(Clock::now() - t0).count();
}

int slow_task() {
    std::this_thread::sleep_for(Ms(300));
    return 42;
}

int main() {
    // ---- 1. async(launch::async)：析构阻塞 ----
    {
        auto t0 = Clock::now();
        {
            std::future<int> fut = std::async(std::launch::async, slow_task);
            std::printf("[async ] about to leave scope at t=%lldms\n", elapsed_ms(t0));
        }  // fut 析构 → 阻塞等 slow_task 跑完
        std::printf("[async ] scope exited at t=%lldms\n\n", elapsed_ms(t0));
    }

    // ---- 2. packaged_task：析构不阻塞 ----
    {
        auto t0 = Clock::now();
        {
            std::packaged_task<int()> pt(slow_task);
            std::future<int> fut = pt.get_future();
            std::thread t(std::move(pt));
            t.detach();
        }  // fut 析构 → 立即返回
        std::printf("[ptask ] scope exited at t=%lldms\n\n", elapsed_ms(t0));
    }

    // ---- 3. promise：析构不阻塞 ----
    {
        auto t0 = Clock::now();
        {
            std::promise<int> p;
            std::future<int> fut = p.get_future();
            std::thread t([pr = std::move(p)]() mutable {
                std::this_thread::sleep_for(Ms(300));
                pr.set_value(42);
            });
            t.detach();
        }
        std::printf("[promis] scope exited at t=%lldms\n\n", elapsed_ms(t0));
    }

    // ---- 4. async 转 shared_future（最后一个引用）：仍然阻塞！----
    {
        auto t0 = Clock::now();
        {
            std::shared_future<int> sfut =
                std::async(std::launch::async, slow_task).share();
        }  // sfut 是该共享状态最后的引用 → 析构仍阻塞
        std::printf("[shared] scope exited at t=%lldms\n\n", elapsed_ms(t0));
    }

    // ---- 5. 对照：get() 显式等待的耗时 ----
    {
        auto t0 = Clock::now();
        int v = std::async(std::launch::async, slow_task).get();
        std::printf("[get() ] got %d at t=%lldms\n", v, elapsed_ms(t0));
    }

    std::this_thread::sleep_for(Ms(500));  // 等后台 detached 线程收尾
    return 0;
}

clang 23.1.0 + -std=c++17 -Wall 实测输出：

[async ] about to leave scope at t=0ms
[async ] scope exited at t=310ms

[ptask ] scope exited at t=0ms

[promis] scope exited at t=0ms

[shared] scope exited at t=304ms

[get() ] got 42 at t=301ms

四组对照把规则边界钉死了：

  1. async 的 future 析构阻塞 310ms——和 get() 的 301ms 一样，隐式 join 货真价实；
  2. packaged_task / promise 的 future 析构 0ms——线程还在后台跑，句柄先走了，互不等待；
  3. shared_future 也阻塞了 304ms——这是最容易记错的一点：阻塞规则挂在"共享状态的最后一次释放"上，.share() 只是换了句柄类型，共享状态还是 async 创建的，最后一个 shared_future 析构照样等。想真正躲开阻塞，办法不是换类型，而是让句柄活得比当前作用域久（存进成员变量、队列、后台收割线程）。

推论：临时 future 立即析构 = 假异步

std::async(std::launch::async, long_task);   // 返回值被丢弃
// 临时 future 在语句末尾立即析构 → 立即阻塞 → 完全同步，白 async 了

这是这条规则最坑的形态：丢弃返回值的 std::async 调用等价于直接同步调用，还额外付出了一次线程启动的开销。如果你真的想"发射后不管"，得用 std::thread + detach（并自担悬垂风险），或把 future 移交给他处保管。

常见错误（新手踩坑）

错误 1：在热路径析构 async 的 future

void on_tick(const Tick& t) {
    auto fut = std::async(std::launch::async, check_risk, t);
    process(t);
}   // fut 在函数末尾析构 → 阻塞等 check_risk 完成 → 热路径卡住

修正： 把 future 存进成员队列，由后台线程收割 get()。

错误 2：丢弃 std::async 返回值，以为实现了异步

std::async(std::launch::async, long_task);   // 临时 future 立即析构 → 同步阻塞

修正： auto fut = std::async(...); 存起来并妥善安排生命周期。

错误 3：以为所有 future 析构都阻塞（或都不阻塞）

// packaged_task 的 future 析构不阻塞——任务结果可能永远没人取
// async 的 future 析构阻塞——"扔掉句柄"不等于"取消任务"

修正： 记住规则的精确边界：只有 async 共享状态的最后一次释放才阻塞。

修正： 实测证明最后一个 shared_future 析构照样等任务跑完；要躲开阻塞得延长句柄生命周期，不是换类型。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
异步任务句柄 pthread_t 整数，离开作用域无效果 future 析构可能隐式 join RAII + 共享状态

一句话总结： std::async 的 future 析构 = 隐式 join（仅当它是该共享状态的最后一个引用且任务未就绪）；packaged_task / promise 的 future 析构无此待遇。

HFT 关联

  • 热路径零隐式阻塞：on_tick / on_order 回调里出现的任何 async future 都必须移交出去（队列、成员变量），否则析构阻塞直接变成逐笔延迟。
  • 异步风控 / 异步落盘：发射即忘的任务别用 std::async（返回值一丢就同步），用线程池或 std::thread+detach+按值捕获。
  • 后台收割线程：统一一个 reaper 线程对消费者队列里的 future 调 get()——既避开析构阻塞，也避免任务异常被静默吞掉。
  • 定位神秘卡顿：热路径出现与某任务时长吻合的延迟尖刺时，grep 作用域内是否有 async future 的析构点。

自测题

1. std::future 的析构什么时候会阻塞？精确的触发条件是什么？

答案

仅当同时满足：①共享状态由 std::async 以 launch::async 策略创建；②任务尚未就绪；③这是最后一个引用该共享状态的句柄（future 或 shared_future）被释放。此时析构相当于隐式 join，阻塞到任务完成。packaged_task / promise 的 future 永远不阻塞。

2. 实测中四种来源的 future 析构耗时各是多少？说明了什么？

答案

async future 310ms（阻塞，≈任务时长 300ms）；packaged_task 0ms；promise 0ms；shared_future（最后引用）304ms。说明阻塞规则挂在"async 共享状态的最后一次释放"上，与句柄是 future 还是 shared_future 无关。

3. std::async(std::launch::async, task);（丢弃返回值）的实际行为是什么？

答案

临时 future 在语句末尾立即析构，按规则阻塞到 task 完成——等价于同步调用，还白付一次线程启动开销。不是"发射后不管"。

4. 为什么 packaged_task 和 promise 的 future 析构不阻塞？

答案

阻塞是标准专门给 async（async 策略）共享状态加的"线程完成 synchronizes-with 最后一次释放"条款，目的是防止 async 任务变野线程。packaged_task / promise 的线程生命周期由你自己管理（你自己创建并 join/detach 了 std::thread），标准不再插手。

5. 已经调用过 get() 的 async future，析构还阻塞吗？为什么？

答案

不阻塞。get() 返回意味着共享状态已就绪——"第一个成功观察到就绪的函数"已经发生，按"两者取先"的规则，之后的释放不再承担等待义务（且 get() 后 future 已 valid()==false，不再引用共享状态）。

6. 要真正避免 async future 的析构阻塞，正确做法是什么？

答案

延长句柄生命周期：存进成员变量 / 队列 / 后台收割线程，让"最后一次释放"发生在不敏感的地方。换成 shared_future 无效——实测证明它作为最后引用照样阻塞。

7. 这条析构阻塞规则与 Item 37 的 terminate 有什么共同的设计动机？

答案

都是"不允许你忘记一个正在运行的线程"：Item 37 用 terminate 惩罚忘记 join 的 std::thread，Item 38 用隐式 join 防止 async 任务变成没人管的野线程（它可能按引用捕获了调用者的局部变量）。一个用崩溃保证，一个用阻塞保证。

Item 39：单次事件用 future + promise / condition_variable

第 7 章 · Item 39 · 上一节：Item 38 句柄析构行为

为什么要学这个（先建立直觉）

并发编程里最高频的协作模式之一是："线程 B 必须等线程 A 完成一次某件事"——等连接建好、等配置加载完、等行情首包到达。教科书的标准答案是 condition_variable + flag + mutex 三件套，但这三件套有两颗经典地雷（虚假唤醒、丢失唤醒），每颗都足以让新手写下"九成九能跑"的代码。

promise + future 把同一个模式压缩成两行，而且从机制上免疫那两颗地雷。Meyers 的立场很明确：单次事件，默认用 promise/future；condition_variable 留给真正需要它的重复事件。

这节讲什么

  1. promise/future 单次通信（实测可跑），以及它为什么免疫虚假唤醒与丢失唤醒；
  2. condition_variable + flag 的正解写法与两颗地雷的原理；
  3. C++20 std::latch：N 个事件的汇聚版（实测）；
  4. promise/future 的隐藏能力：异常穿越线程边界。

方式一：promise + future（首选，实测）

#include <future>
#include <thread>

std::promise<int> p;
auto fut = p.get_future();

std::thread t([&]{
    initSomething();        // 完成初始化
    p.set_value(42);        // 发信号，还能捎带结果
});

int result = fut.get();     // 阻塞，直到 set_value 发生
t.join();

clang 23.1.0 实测运行：主线程阻塞约 50ms 后拿到 42。

为什么它免疫两颗地雷

丢失唤醒：cv 版本里如果 A 在 B 开始 wait 之前就 notify，这次通知没人接收就丢了——B 睡到地老天荒。promise 的共享状态是持久的：set_value 先发生，fut.get() 后调用照样立刻返回结果——事件发生过就记录在案，不存在"错过"。

虚假唤醒：标准允许 condition_variable::wait 在没人 notify 的情况下莫名返回（某些平台上的实现策略），所以正确写法必须带谓词循环（见下）。future::get() 只在共享状态真正就绪时返回——没有"醒来检查一下"这个中间态，标准直接保证了语义。

此外它还少一把锁：cv 方案必须用 mutex 保护 flag，promise 的共享状态自身线程安全。外加两个赠品：能携带结果（promise<int>）、能传播异常（下文）。

方式二：condition_variable + flag（必须会读）

std::condition_variable cv;
std::mutex mtx;
bool ready = false;

// 线程 A（通知方）：
{
    std::lock_guard lk(mtx);
    ready = true;
}
cv.notify_one();

// 线程 B（等待方）：
{
    std::unique_lock lk(mtx);
    cv.wait(lk, []{ return ready; });   // ★ 谓词形式是底线，不是优化
}

两颗地雷的机理：

  • 虚假唤醒 → 必须用带谓词的 wait(lk, pred)（等价于 while (!pred()) wait(lk);）。裸 wait(lk) + 事后不检查 flag，虚假唤醒时就带着 ready == false 往下跑。
  • 丢失唤醒 → ready = true 必须在锁内写、且等待方进入 wait 前也要在锁内检查谓词（谓词形式替你做了）。notify 在 wait 之前到达时，靠"flag 已经置位"这个事实兜底，而不是靠 notify 本身。

cv + flag 真正不可替代的场景：重复事件（每来一个 tick 通知一次）、多等待方广播（notify_all）。单次事件用它纯属自找麻烦。

方式三：C++20 std::latch（N 个事件的汇聚）

promise/future 是 1 对 1 的单次信号；要等"3 个初始化线程全部就绪"这种 N 对 1 汇聚，C++20 的 latch 是专用原语（clang 23.1.0 + -std=c++20 实测运行通过）：

#include <latch>

std::latch init_done(3);                    // 计数 3
std::vector<std::thread> ts;
for (int i = 0; i < 3; ++i)
    ts.emplace_back([&, i]{
        initConnection(i);                  // 各自的初始化
        init_done.count_down();             // 完成一个，计数 -1
    });
init_done.wait();                           // 阻塞到计数归零
// 全部就绪
for (auto& t : ts) t.join();

无锁、无虚假唤醒、语义直白。latch 是一次性的（归零后不能复位）；要多轮同步用 std::barrier。

赠品：异常穿越线程边界

cv + flag 只能表达"发生了/没发生"；promise 还能把异常快递给等待方（实测）：

std::promise<void> p;
auto fut = p.get_future();
std::thread t([&]{
    try {
        connectToExchange();        // 抛 std::runtime_error("连接交易所失败")
    } catch (...) {
        p.set_exception(std::current_exception());   // 打包异常
    }
});
try {
    fut.get();                      // 异常在这里重新抛出
} catch (const std::exception& e) {
    // 实测输出：主线程捕获: 连接交易所失败
}
t.join();

工作线程的异常不会死在没人接的角落里——这是初始化场景的关键能力（初始化失败的原因必须传到主线程）。

常见错误（新手踩坑）

  1. cv 裸 wait 不带谓词。cv.wait(lk); 在虚假唤醒后直接往下跑——谓词形式 cv.wait(lk, pred) 是唯一正确写法。
  2. flag 不用锁保护或不用原子。bool ready 被两个线程一读一写是数据竞争（UB）——cv 方案的 flag 必须在 mutex 保护下读写。
  3. promise 二次 set_value。promise 只能兑现一次，第二次 set_value 抛 std::future_error——这正是"单次"语义的强制体现。
  4. future.get() 当轮询用。get() 是一次性消费——拿完 future 就失效，第二次 get() 行为未定义。要能反复查结果用 shared_future。

新手要点

  • 选型决策树：单次 1 对 1 → promise/future；单次 N 对 1 汇聚 → C++20 latch（老标准就 N 个 promise 或原子计数器 + 最后一个负责 notify）；重复事件 / 广播 → condition_variable。
  • 能拿 C++20 就用 latch：std::latch 是本场景最简洁的标准原语，比手写"计数器 + mutex + cv"少一整类错误。
  • promise/future 的共享状态有堆分配开销——所以这是"初始化/启动"级工具，不是每 tick 用的热路径工具。

HFT 关联

  • 启动序列：主线程等网络线程完成交易所连接 + 合约表下载后才开闸下单——promise<void>（或要带回连接句柄就 promise<Session*>）是标准写法；失败原因用 set_exception 带回主线程（实测异常穿越可用）。
  • 多通道就绪汇聚：等 3 个行情通道 + 2 个下单通道全部就绪 → std::latch ready(5)，每个通道初始化完 count_down()，主循环 wait() 后开工。
  • 别用在热路径：promise/future 的共享状态带堆分配和原子操作——它管"启动"不管"每 tick"。热路径的线程间通信是无锁队列（SPSC/MPMC ring buffer），不是 future。

自测题

  1. promise + future 相比 condition_variable + flag 有哪些优势？（至少说出四条）
  2. 虚假唤醒是什么？为什么 cv.wait(lk, pred) 的谓词形式是底线？promise/future 为什么免疫？
  3. 丢失唤醒是什么场景？promise 靠什么机制免疫它？
  4. std::latch 解决什么问题？和 std::barrier 的区别？
  5. 工作线程的异常怎么传到等待线程？写出关键两行。
  6. future.get() 能调用两次吗？要多次读取结果该用什么？
参考答案

  1. ①代码极简：set_value + get 两行，不需要 flag/mutex/谓词；②免疫虚假唤醒：get() 只在共享状态真正就绪时返回；③免疫丢失唤醒：共享状态持久，set_value 先于 get 也不会丢；④少一把锁：共享状态自身线程安全；⑤能捎带结果（promise<int>）；⑥能传播异常（set_exception）。

  2. 虚假唤醒：标准允许 wait 在没有任何 notify 的情况下返回（实现策略）。所以等待方醒来后必须重新检查条件——cv.wait(lk, pred) 等价于 while (!pred()) wait(lk);，虚假唤醒会被谓词挡回去再睡。裸 wait(lk) 不加检查就会在虚假唤醒时带着未就绪的状态继续跑。promise/future 免疫是因为 get() 没有"先醒来再检查"的中间态，标准保证它只在就绪时返回。

  3. 通知方在等待方进入 wait 之前就 notify——通知没人接收就丢了，等待方睡到永远。cv 方案靠"flag 已在锁内置位、wait 前先查谓词"兜底；promise 的共享状态是持久的：set_value 把结果写进共享状态，之后任何时刻 get() 都能取到——事件被记录而不是被广播，从机制上不存在错过。

  4. latch 是一次性的向下计数同步点：构造给 N，参与方各 count_down()，等待方 wait() 到归零。解决"等 N 个事件/线程全部完成"。与 barrier 的区别：latch 归零后不可复位（一次性），barrier 可重复用于多轮同步；latch 的等待方不必是参与方（一个线程等、N 个线程降计数），barrier 是所有参与方同时到达后一起放行。

  5. p.set_exception(std::current_exception());（工作线程 catch 块里打包）+ 等待方 fut.get()（异常在此处重抛，用 try/catch 接住）。实测：工作线程抛 runtime_error("连接交易所失败")，主线程 fut.get() 处原样捕获。

  6. 不能。get() 是一次性消费：取走结果后 future 失效，第二次 get() 行为未定义（通常抛 std::future_error）。要多个等待方/多次读取，用 promise 配 shared_future（p.get_future().share()）——shared_future::get() 返回 const 引用，可多次、可多方。

为什么要学这个（先建立直觉）

这可能是 C++ 里被误解最深的两个关键字。很多从 C / 嵌入式转来的程序员有个根深蒂固的习惯：线程间共享的标志位用 volatile——"告诉编译器别优化，每次都从内存读，这样另一个线程的修改就能被看见"。这个习惯在单核 + 中断的年代碰巧能用，搬到多核多线程就是一颗定时炸弹。

问题的根源是名字撞车：Java 和 C# 里的 volatile 确实有跨线程可见性语义，而 C/C++ 的 volatile 和线程一点关系都没有——它只对编译器说"这块内存可能被程序之外的东西（硬件、信号处理器）改写，不许优化我的读写"。它不管原子性，不管指令重排，不管 CPU 缓存一致性。

C++ 里表达"别的线程也会碰这个变量"的正确工具是 std::atomic：原子性、内存序、跨核可见性，一应俱全。本节用两组硬实测把这件事钉死：双线程各加 100 万次，volatile int 会丢将近一半更新，而 atomic<int> 精确等于 200 万；再用汇编对比展示 volatile 真正的本职——MMIO 寄存器轮询。

这节讲什么

std::atomic 与 volatile 是两个正交的工具：atomic 面向并发（管别的线程），volatile 面向特殊内存（管编译器优化）。用数据竞争实测证明 volatile 做不了并发，用汇编实测证明 volatile 拦得住编译器优化——以及为什么反过来用 atomic 访问硬件寄存器也不合适。

本质区别：一张表

std::atomic volatile
服务对象 多线程并发 程序之外的改写者（硬件 / 信号）
原子性 保证 不保证
跨线程可见性 / 内存序 保证（memory order） 不保证
阻止编译器优化读写 顺带做到 唯一本职
典型场景 共享计数器、无锁队列、停止标志 MMIO 寄存器、sig_atomic_t 标志

关键认知：它们解决的是两个不同维度的问题，谁也不含谁。 一个变量完全可以既 atomic 又不需要 volatile（普通共享变量），也可以只需要 volatile 而不需要原子性（单线程轮询硬件寄存器），极少数场景两者都要。

实测 1：volatile 做并发的下场（本机实测 clang 23.1.0）

两个线程各对同一个计数器自增 100 万次，分别用 volatile int 和 std::atomic<int>：

#include <atomic>
#include <cstdio>
#include <thread>

constexpr int N = 1'000'000;

volatile int v_counter = 0;          // 数据竞争：volatile 不提供原子性
std::atomic<int> a_counter{0};

void inc_volatile() {
    for (int i = 0; i < N; ++i) ++v_counter;   // 读-改-写三步，多线程交错
}

void inc_atomic() {
    for (int i = 0; i < N; ++i)
        a_counter.fetch_add(1, std::memory_order_relaxed);
}

int main() {
    for (int round = 1; round <= 3; ++round) {
        v_counter = 0;
        a_counter = 0;
        std::thread t1(inc_volatile), t2(inc_volatile);
        t1.join(); t2.join();
        std::printf("round %d: volatile = %d (期望 2000000)\n", round, v_counter);

        std::thread t3(inc_atomic), t4(inc_atomic);
        t3.join(); t4.join();
        std::printf("round %d: atomic   = %d (期望 2000000)\n", round, a_counter.load());
    }
    return 0;
}

clang 23.1.0 + -std=c++17 -Wall -O2 实测输出：

round 1: volatile = 1013244 (期望 2000000)
round 1: atomic   = 2000000 (期望 2000000)
round 2: volatile = 1000000 (期望 2000000)
round 2: atomic   = 2000000 (期望 2000000)
round 3: volatile = 1008677 (期望 2000000)
round 3: atomic   = 2000000 (期望 2000000)

volatile 组三轮分别丢了 98.7 万、100 万、99.1 万次更新——++ 是"读-改-写"三步，两个线程交错执行时互相覆盖，volatile 对此完全无能为力（它只保证每次读写真的落到内存，不保证这三步不被打断）。atomic 组三轮全部精确 200 万。注意这还是在内存模型较严格的 arm64 上的结果；而且按 C++ 标准，对非原子变量的并发读写是 data race，属于未定义行为——"结果偏小"只是它碰巧的一种表现，编译器理论上可以做任何事情。

实测 2：volatile 的本职——阻止编译器优化（汇编对比）

模拟 MMIO 轮询：循环读一个"会被硬件改写"的地址直到非零。对比加不加 volatile：

int reg_storage = 0;   // 模拟寄存器映射的地址

int poll_plain(int* reg) {
    while (*reg == 0) { }   // 编译器认为 *reg 不会变 → 提升出循环
    return *reg;
}

int poll_volatile(volatile int* reg) {
    while (*reg == 0) { }   // 每次迭代都真实读内存
    return *reg;
}

clang 23.1.0 + -O2 -S 生成的汇编（本机实测）：

_poll_plain:                        ; 不带 volatile
    ldr     w0, [x0]                ; 只读了一次……
    ret                             ; ……然后直接返回！循环被整个优化掉

_poll_volatile:                     ; 带 volatile
LBB1_1:                             ; 真正的循环
    ldr     w8, [x0]                ; 每次迭代都重新从内存加载
    cbz     w8, LBB1_1              ; 为 0 就继续转
    ldr     w0, [x0]
    ret

对比触目惊心：poll_plain 的循环被编译器整个删除——只读一次、直接返回（等价于 if (*reg==0) 死循环; else return *reg; 被进一步简化成"反正不会变，读了直接返回"）。这就是不带 volatile 轮询硬件寄存器的下场：硬件把寄存器改了一万次，你的代码还停在第一次读到的值。加上 volatile 后，每次迭代都有真实的 ldr——这才是 MMIO 轮询该有的样子。

所以 volatile 的语义精确地说只有一条："每次访问都必须真正读/写内存，编译器不许缓存、不许提升、不许删除。" 它是说给编译器听的，不是说给 CPU 或其他线程听的。

两个方向的错配

用 volatile 做并发（实测 1 已证伪）： 不保证原子性（++ 丢更新）、不插入内存屏障（不阻止 CPU/编译器对周边指令重排）、不建立 happens-before 关系。多线程共享变量请用 std::atomic 或互斥锁。

用 atomic 访问硬件寄存器（同样错）： std::atomic 的语义对象是"内存里的变量"，标准不保证它落在某个具体地址上的单次读写在总线层面是什么样子；某些平台上 atomic 操作可能带锁（is_lock_free() 为假），MMIO 场景下既无必要也不合适。寄存器映射就用 volatile，它精确表达"逐字逐句照我说的读写"。

嵌入式里的真实代码经常两者都要：一个被 DMA 改写、又被多个线程读的缓冲区描述符，地址本身是 volatile 的，并发计数用 atomic——正交需求，各用各的。

常见错误（新手踩坑）

错误 1：用 volatile 做线程停止标志

volatile bool stop = false;
// 线程 A: stop = true;
// 线程 B: while (!stop) { work(); }   // 无同步保证，可能永远看不到

修正： std::atomic<bool> stop{false};——保证跨核可见性和顺序。

错误 2：以为 volatile 能保证原子性

volatile int counter = 0;
// 多线程: ++counter;   // 读-改-写三步交错 → 丢更新（实测丢一半）

修正： std::atomic<int> counter{0}; counter.fetch_add(1);

错误 3：从 Java/C# 带来的直觉——以为 volatile 有跨线程语义

修正： C++ 的 volatile 只管编译器优化。语言间同名关键字语义完全不同，这是面试和代码评审的高频坑。

错误 4：用 atomic 访问 MMIO 寄存器

修正： 硬件寄存器用 volatile；atomic 可能不 lock-free，且语义上不针对设备内存。

新手要点（和 C 的区别）

维度 C 怎么做 C++ 怎么做 为什么
线程同步 误用 volatile（单核时代碰巧能用） std::atomic C++11 标准内存模型
硬件寄存器 volatile volatile（完全相同） 防编译器优化
原子操作 平台内建（__sync_*） std::atomic / fetch_add / CAS 跨平台可移植

一句话总结： 多线程共享变量 → std::atomic；硬件寄存器 / 信号标志 → volatile。两者是正交工具，谁也不是谁的子集。

HFT 关联

  • 竞争计数器：行情包计数、订单序列号用 std::atomic<uint64_t>（relaxed 足够时别上 seq_cst，省屏障开销）——volatile 版本在实测里直接丢一半更新。
  • 停止标志：std::atomic<bool> running{true} 替代 volatile bool，保证所有核及时看到停机指令。
  • DPDK / 网卡寄存器：mmap 的 PMD 配置与状态寄存器轮询用 volatile（或 DPDK 自己的 rte_read32 封装），不用 atomic。
  • 无锁队列：SPSC/MPMC 队列的 head/tail 指针用 atomic + 恰当的 memory order；volatile 在这里连编译器屏障都算不上（它管不了 CPU 重排）。
  • 混合场景：FPGA/网卡 DMA 写的描述符环——描述符内存 volatile，消费者索引 atomic，各管各的。

自测题

1. std::atomic 和 volatile 的本质区别是什么？

答案

atomic 面向并发：保证读写的原子性，通过 memory order 提供跨线程可见性与顺序保证。volatile 面向编译器优化：保证每次访问真实落到内存，不被缓存/提升/删除。一个管"别的线程"，一个管"程序之外的改写者"，正交。

2. 实测中双线程对 volatile int 各加 100 万次的结果是多少？为什么？

答案

约 101 万（三轮：1013244 / 1000000 / 1008677），丢了近一半更新。因为 ++ 是读-改-写三步，volatile 不提供原子性，两个线程交错时互相覆盖；且按标准这是 data race，本就是未定义行为。同测试的 atomic 组精确等于 2000000。

3. volatile 做线程同步缺哪三样东西？

答案

①原子性——复合操作可被打断；②内存序——不插屏障，不阻止 CPU/编译器对周边访问重排；③happens-before——一个线程的写对另一个线程何时可见没有标准保证。

4. 汇编实测里 poll_plain 和 poll_volatile 的区别说明了什么？

答案

-O2 下 poll_plain 的循环被整个优化成一次 ldr + ret（编译器认定 *reg 不会变）；poll_volatile 保留了每次迭代真实加载的循环。说明 volatile 的唯一本职就是阻止编译器优化内存访问——这正是 MMIO 轮询需要的，也正是它对并发无能为力的原因。

5. 为什么不该用 std::atomic 访问硬件寄存器？

答案

atomic 的语义对象是"内存变量"，不针对设备内存；某些平台上 atomic 操作可能带锁（非 lock-free），对 MMIO 既无必要也可能出错。寄存器读写用 volatile 精确表达"逐次真实访问"。

6. 为什么单核嵌入式时代的 volatile 同步"碰巧能用"，多核时代就崩了？

答案

单核 + 中断场景没有真正的并行执行，唯一问题是编译器把轮询读优化掉——volatile 恰好解决这个。多核的真正难点是 CPU 乱序、store buffer、缓存一致性带来的可见性与顺序问题，volatile 对这些一概不管。

7. 一个变量能否同时需要 atomic 和 volatile？举例。

答案

能，两者正交。例：被 DMA 引擎异步改写、又被多个工作线程并发读取的描述符环——描述符内存本身要 volatile（硬件在改），消费者/生产者索引要 atomic（多线程在争）。嵌入式驱动里这种组合很常见。

Q2volatile 不是 atomic
volatile int flag = 0;
// 线程 1: flag = 1;
// 线程 2: while (flag == 0) ;

这段代码线程安全吗？volatile 能保证什么？

答案与复习指引

不是线程安全的——数据竞争 UB。
