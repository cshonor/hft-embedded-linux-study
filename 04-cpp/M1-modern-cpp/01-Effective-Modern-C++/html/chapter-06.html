Lambda Expressions — Items 31–34

本章讲什么

Lambda 是 C++11 最受欢迎的特性之一——它让"在调用点定义回调"成为可能，替代了冗长的仿函数类。但 lambda 的捕获、闭包生命周期、auto&& 参数转发有不少陷阱。本章讲清捕获语义、初始化捕获（C++14）、泛型 lambda（C++14）与 std::bind 的取舍。

各 Item 要点

Item 31：避免默认捕获模式（[=] / [&]）

默认捕获有两大问题： 1. [=] 的误导：看着像"按值捕获一切"，但只捕获用到的变量；且对 static 局部变量、成员变量的捕获语义反直觉（成员变量实际捕获的是 this 指针，按引用！）。 2. [&] 的悬垂：按引用捕获的局部变量，闭包存活超过作用域时引用悬垂——UB。

class Widget {
    int data;
    auto make_cb() { return [=]{ return data; }; }  // 捕获的是 this，不是 data 的拷贝！
};

建议：显式列出捕获变量（[x]、[&mtx]），避免默认模式；尤其警惕 [=] 捕获 this 的隐式行为。C++17 可用 [*this] 按值捕获对象本身。

Item 32：用初始化捕获将对象移入闭包（C++14）

初始化捕获（init capture）能在捕获时执行表达式并命名：

auto pw = std::make_unique<Widget>();
auto cb = [up = std::move(pw)]{ up->doSomething(); };  // 把 unique_ptr 移入闭包

up = std::move(pw) 在闭包里创建 up（按值，即移动），彻底解决"想捕获移动语义"的需求——C++11 做不到。C++11 的变通是 std::bind 包裹，但更绕。

Item 33：对 auto&& 形参用 decltype + std::forward（泛型 lambda）

C++14 泛型 lambda 用 auto&& 参数实现完美转发：

auto f = [](auto&& x){ func(std::forward<decltype(x)>(x)); };

decltype(x) 对 auto&&（万能引用）参数保留左右值性，forward 原样转发。这让 lambda 能当泛型转发器用。

Item 34：优先 lambda 而非 std::bind

std::bind 的缺陷： - 无法内联（C++11 的 bind 是函数调用，lambda 可内联）； - 参数占位符晦涩（_1、_2）； - 重载函数 / 模板函数传给 bind 需要显式类型转换，lambda 不需要； - bind 的值传递语义对 move-only 类型（unique_ptr）不友好。

C++14 起几乎所有 bind 场景都该用 lambda 替代。bind 仅在极少数"运行时组合调用链"的场景仍有价值。

HFT 关联

  • lambda 作策略回调：HFT 策略引擎常注册 lambda 作回调（engine.on_tick([this](const Tick& t){ ... })）。注意捕获 this 的生命周期——策略对象销毁后引擎仍调闭包 = 悬垂。配合 weak_ptr 或显式注销回调规避。
  • [&] 悬垂是热路径隐患：行情循环里 [&] 捕获局部变量，若闭包被异步保存到队列稍后执行，局部变量已销毁——这是 HFT 异步日志/事件队列里最难查的 UAF。规则：跨作用域存储的闭包用值捕获或 shared_ptr。
  • lambda 内联：STL 算法（sort/for_each/transform）传 lambda 比 bind/函数指针更易内联——HFT 回测里对 tick 数组批量处理时，内联 lambda 的性能显著优于函数指针。

Item 31：避免默认捕获模式（[=] / [&]）

第 6 章 Lambda 表达式 · Item 31 · 下一节：Item 32 初始化捕获

为什么要学这个（先建立直觉）

lambda 的捕获列表是它和 C 的「函数指针 + void* userdata」最本质的区别：编译器帮你把上下文打包进闭包。但 [=] 和 [&] 这两个「默认捕获模式」相当于对编译器说「我用了什么你就给我捕获什么」——你放弃了对捕获清单的审查权。问题在闭包逃出作用域时才爆发：[&] 捕获了局部变量的 lambda 被返回、被塞进任务队列、被注册成回调，等它真正执行时，当初捕获的局部变量早就随栈帧销毁了。引用不会延长对象的生命周期——它只是一个地址，对象死了，地址还在。

更隐蔽的是 [=]：在成员函数里写 [=]，字面上是「按值捕获我用到的一切」，但成员变量根本不能被直接捕获——闭包实际捕获的是 this 指针，每次访问成员都走 this->data。你以为拿到了一份拷贝，实际拿到的是一根指针。

这节讲什么

  1. [&] 按引用捕获的悬垂实测：局部变量销毁后调用闭包，普通编译读垃圾值，ASan 抓 stack-use-after-scope；
  2. [=] 的假象：捕获成员变量实际是捕获 this 指针，ASan 帧信息指出「访问落在已析构的 w 里」；
  3. static 局部变量不被捕获（[&] 也捕获不到），用地址和 sizeof 实测证明；C++20 的 [=, this] 显式化（编译器警告原文实测）。

[&] 悬垂：闭包比局部变量活得久

经典反面教材——返回一个按引用捕获局部变量的 lambda：

#include <functional>
#include <iostream>

std::function<int()> getCounter() {
    int count = 100;                    // 局部变量
    return [&] { return ++count; };     // 按引用捕获 count —— return 后 count 销毁
}

int main() {
    auto f = getCounter();   // 栈帧已销毁，count 不复存在，闭包里只剩悬垂地址
    std::cout << "f() = " << f() << "\n";
    std::cout << "f() = " << f() << "\n";
}

本机实测（clang 23.1.0，-std=c++17 -Wall），正确输出应该是 101 102，实际却是：

f() = 2
f() = 2

栈内存被后续调用覆写，读到的是垃圾值（加 -fsanitize=address -g 再跑垃圾值变成 1807838081，但 ASan 没有报错）。std::function 的类型擦除调用链让 use-after-scope 检测漏了过去——sanitizer 不一定救你，程序甚至可能「看起来能跑」。

不经过 std::function 直接返回 lambda 时，编译器倒是会警觉（本机实测警告原文）：

warning: address of stack memory associated with local variable
         'count' returned [-Wreturn-stack-address]
note: implicitly captured by reference due to use here

编译器能看穿直接返回，但看不穿「存进 std::function / 任务队列 / 回调注册表」的间接逃逸——真实代码里闭包几乎都是间接逃逸的。不要指望警告救你，要靠纪律：显式列出捕获变量。

[=] 的假象：捕获的是 this 指针

成员变量不能单独出现在捕获列表里，[=] 用到成员时实际捕获 this：

#include <functional>
#include <iostream>

class Widget {
    int data;
public:
    explicit Widget(int d) : data(d) {}
    std::function<int()> makeCallback() {
        return [=] { return data; };   // 看着像"按值捕获 data"
                                       // 实际等价于 [this]{ return this->data; }
    }
};

int main() {
    std::function<int()> cb;
    {
        Widget w{42};
        cb = w.makeCallback();
        std::cout << "对象存活时 cb() = " << cb() << "\n";
    }   // w 析构，闭包里的 this 悬垂
    std::cout << "对象销毁后 cb() = " << cb() << "\n";  // UB
}

本机实测（clang 23.1.0，-std=c++17 -Wall）普通编译的输出是最阴险的那种结果：

对象存活时 cb() = 42
对象销毁后 cb() = 42

两次都是 42——栈内存恰好没被覆写，UB「看起来完全正常」，能在测试环境潜伏很久。同一份代码用 -fsanitize=address -g 编译，ASan 立刻现形（实测输出节选）：

==85017==ERROR: AddressSanitizer: stack-use-after-scope on address 0x00016fae6e00
READ of size 4 at 0x00016fae6e00 thread T0
    #0 Widget::makeCallback()::'lambda'()::operator()() const
    [96, 100) 'w' (line 24) <== Memory access at offset 96 is inside this variable

最后一行是铁证：闭包里的「data」访问落在了已析构的 w 的内存里——[=] 根本没有拷贝 data，它只是存了 &w。

正确做法

// 方案一（C++11 起通用）：先拷贝到局部变量，再按值捕获局部变量
std::function<int()> makeCallback() {
    int local_data = data;                       // 拷贝发生在对象存活时
    return [local_data] { return local_data; };  // 闭包持有真正的副本
}
// 方案二（C++14 起）：init capture，一步到位（Item 32 详讲）
std::function<int()> makeCallback() {
    return [d = data] { return d; };
}
// 方案三（C++17 起）：[*this] 按值捕获整个对象的副本
std::function<int()> makeCallback() {
    return [*this] { return data; };   // 闭包里存了一个 Widget 拷贝
}

三种方案的共同点是拷贝发生在对象还活着的时候，闭包此后与原对象再无瓜葛。方案三拷的是整个对象，对象大时方案二（只拷需要的成员）更省。

static 局部变量不被捕获

[&] 的语义是「按引用捕获我用到的自动存储期变量」。static 局部变量不在栈上，根本不需要捕获——lambda 里写它的名字，用的就是静态区里那一份：

#include <iostream>

void demonstrate() {
    static int s_count = 0;    // 静态区，不在栈上
    int local = 0;             // 普通局部变量
    auto lam = [&] {
        ++s_count;             // 没被捕获！直接用静态区的那份
        ++local;               // 这个才被 [&] 捕获
        std::cout << "lambda 内  &s_count = " << static_cast<void*>(&s_count)
                  << " 值 = " << s_count << "\n";
    };
    std::cout << "lambda 外  &s_count = " << static_cast<void*>(&s_count)
              << " 值 = " << s_count << "\n";
    lam();  lam();
    std::cout << "两次调用后  s_count = " << s_count
              << "  local = " << local << "\n";
    std::cout << "sizeof(lambda) = " << sizeof(lam)
              << "（只装了一个引用：local）\n";
}

int main() { demonstrate(); }

本机实测（clang 23.1.0）输出：

lambda 外  &s_count = 0x102ce0090 值 = 0
lambda 内  &s_count = 0x102ce0090 值 = 1
lambda 内  &s_count = 0x102ce0090 值 = 2
两次调用后  s_count = 2  local = 2
sizeof(lambda) = 8（只装了一个引用：local）

三个证据：lambda 内外 &s_count 完全相同，是同一份实体；sizeof(lambda) == 8 恰好一个指针大小，闭包里只装了 local 的引用；static 的递增全局可见。推论：[&] 不会「冻结」static 变量的状态，也不让它进闭包——它永远不悬垂，但多线程共享时要自行同步。

C++20 的 [=, this] 显式化

C++20 弃用了 [=] 对 this 的隐式捕获，要求你写明。本机实测（clang 23.1.0，-std=c++20）：

return [=] { return data; };        // C++20 起：弃用警告
return [=, this] { return data; };  // C++20：显式声明捕获 this

编译警告原文：

warning: implicit capture of 'this' with a capture default of '='
         is deprecated [-Wdeprecated-this-capture]
note: add an explicit capture of 'this' to capture '*this' by reference

措辞是 deprecated（弃用）而不是 error——老代码还能编译，但新标准逼你承认「我知道我捕获的是指针」。反过来 [=, this] 在 -std=c++17 下会得到 ... is a C++20 extension 的扩展警告（clang 兼容放行）。一句话：C++20 里要么 [=, this] 明示按指针捕获，要么 [*this] 按值捕获对象，别再用裸 [=] 糊过去。

完整可运行例子

安全写法汇总——临时对象造出的过滤器、逃逸出作用域的计数器，全部显式按值捕获：

#include <functional>
#include <iostream>

class Engine {
    int threshold;
public:
    explicit Engine(int t) : threshold(t) {}
    std::function<bool(int)> makeFilter() const {
        int t = threshold;                        // 拷贝发生在对象存活时
        return [t](int price) { return price > t; };
    }
};

std::function<int()> getCounter() {
    int count = 0;
    return [count]() mutable { return ++count; };  // 按值捕获 + mutable 允许改副本
}

int main() {
    std::cout << std::boolalpha;
    auto filter = Engine{100}.makeFilter();   // 临时 Engine 语句结束即析构
    std::cout << "filter(150) = " << filter(150) << "\n";  // 闭包持有 t 副本，安全
    std::cout << "filter(50)  = " << filter(50) << "\n";
    auto c = getCounter();
    std::cout << c() << " " << c() << " " << c() << "\n";  // 各改各的副本
}

本机实测（clang 23.1.0，-std=c++17 -Wall）输出：

filter(150) = true
filter(50)  = false
1 2 3

临时 Engine 析构后过滤器依然正确——闭包持有的 t 是对象存活时拷出的副本。

常见错误（新手踩坑）

  1. 成员函数里用 [=] 以为按值捕获了成员。实际捕获的是 this 指针，对象析构后闭包悬垂（上文 ASan 实测）。修正：[d = data]（C++14）或先拷到局部再 [d]，或 [*this]（C++17）。
  2. [&] 捕获局部变量后让闭包逃逸（返回、塞进队列、std::async）。局部变量销毁后引用悬垂，可能读到垃圾值也不一定被 ASan 抓到。修正：逃逸的闭包一律显式按值捕获。
  3. 以为 [&] 会捕获 static 局部变量。static 变量不进闭包，lambda 用的是静态区那一份（地址实测相同），多线程共享时要自己加同步。

HFT 关联

  • 策略回调的 this 悬垂：engine.on_tick([=](const Tick& t){ ... }) 写在成员函数里，策略对象析构后引擎仍持有闭包——热重载策略、盘中切换实例时真实会炸。评审时把成员函数里的 [=] 当红旗 grep：grep -n 'return \[=\]'。
  • UB「看起来正常」最致命：本文实测析构后仍打印 42——性能测试环境一切正常、生产环境偶发错乱。逃逸闭包的捕获清单必须人工评审，不能靠测试通过背书。
  • 异步任务显式按值捕获：std::async([config](const Tick& t){ ... }) 捕获副本而非引用——配合 Item 35 的任务制并发，每个任务自含全部上下文，无悬垂可能。

自测题

1. [=] 在成员函数里捕获成员变量时，实际捕获的是什么？为什么这是隐患？

答案

实际捕获的是 this 指针——成员变量不能单独被捕获，[=] 用到成员时等价于 [this]，闭包里每次访问都是 this->data。隐患有二：一是对象析构后 this 悬垂，闭包读写成员是 UB（本文 ASan 实测：访问落在已析构对象 w 的内存里）；二是「按值捕获」的字面语义误导读者以为拿到了副本，实际拿到的是裸指针。修正：[d = data] 或 [*this]。

2. 为什么 [&] 悬垂有时 ASan 抓不到、普通运行甚至结果「正确」？

答案

悬垂引用读的是已释放的栈内存，只要那段内存还没被覆写，读到的就是旧值——UB 不保证报错，只保证「行为无定义」。本文实测中普通编译的 [=]-this 版本析构后仍打印 42；而 std::function 类型擦除的间接调用链又让 ASan 的 use-after-scope 插桩失效，垃圾值照打不误。结论：sanitizer 是辅助，不是保险；逃逸闭包靠显式捕获清单防悬垂。

3. static 局部变量会被 [&] 捕获吗？用什么方法可以实测验证？

答案

不会。static 局部变量具有静态存储期，不在栈上，所有 lambda（包括 [&]）都直接引用静态区里那一份实体。验证方法：打印 lambda 内外的 &s_count（本文实测同为 0x102ce0090），再看 sizeof(lambda)——只有 8 字节，恰好是捕获的那个普通局部变量的引用大小，static 变量不占闭包空间。

4. C++20 对 [=] 捕获 this 做了什么改动？

答案

C++20 弃用了 [=] 对 this 的隐式捕获（-Wdeprecated-this-capture），要求显式写 [=, this] 表示「按指针捕获 this」，或写 [*this] 表示按值捕获整个对象。clang 23.1.0 实测：C++20 模式下裸 [=] 用成员变量给出弃用警告；[=, this] 在 C++17 模式下则是扩展警告。意图是让「捕获指针」这件事显式可见，堵住 [=] 的语义陷阱。

5. 下面代码有什么问题？怎么修？

std::function<void()> make_task() {
    int x = 42;
    return [&] { std::cout << x; };
}
auto t = make_task();
t();
答案

悬垂引用，UB。x 是 make_task 的局部变量，函数返回即销毁；闭包用 [&] 捕获了 x 的引用，t() 调用时读的是已销毁的栈对象——本文同类代码实测打印垃圾值，编译器对直接返回场景会给 -Wreturn-stack-address 警告，但经 std::function 间接逃逸时警告可能缺席。修正：显式按值捕获 return [x] { std::cout << x; };。

6. 想按值捕获成员的副本，C++11 / C++14 / C++17 各推荐什么写法？

答案

C++11：int local = data; return [local]{ ... };——先拷到局部变量再按值捕获。C++14：init capture 一步到位 return [d = data]{ ... };（见 Item 32）。C++17：return [*this]{ ... }; 按值捕获整个对象副本——对象大、只需个别成员时优先 C++14 写法，避免整对象拷贝。

Item 32：用初始化捕获将对象移入闭包（C++14）

第 6 章 Lambda 表达式 · Item 32 · 上一节：Item 31 避免默认捕获

为什么要学这个（先建立直觉）

C++11 的 lambda 捕获只有两种姿势：按值拷贝、按引用。这对 int、double 够用，但遇到 move-only 类型就死锁了——std::unique_ptr、std::future、std::promise、包装了大 buffer 的对象，全都不可拷贝。[pw] 编译失败，[&pw] 能编译但闭包逃逸后 pw 悬垂（Item 31 刚踩过这个坑）。你真正想要的是「把这个对象移动进闭包」，C++11 做不到。

C++14 的初始化捕获（init capture，也叫 generalized lambda capture）把捕获列表从「列变量名」升级成「写初始化语句」：[up = std::move(pw)]——等号右边是任意表达式，在 lambda 创建时求值；左边是闭包里新数据成员的名字。移动捕获只是它能做的事情之一，它还能给捕获改名、捕获计算结果、捕获 *this 的副本。

这一节短，但它是现代 lambda 的分水岭：有了 init capture，lambda 的捕获能力才追平了（实际超越了）std::bind，Item 34 才能理直气壮地说「别用 bind 了」。

这节讲什么

  1. 移动捕获 [up = std::move(pw)] 实测：unique_ptr 移入闭包，原指针变 nullptr；
  2. 表达式捕获 [n = compute()]：求值时机在 lambda 创建时而非调用时，用打印实测证明；
  3. C++11 的历史变通：用 std::bind 模拟移动捕获（展示即可，C++14 后淘汰）；
  4. init capture 的语法语义：右边在外围作用域求值，左边是闭包的新成员。

移动捕获：unique_ptr 进闭包

本机实测（clang 23.1.0，-std=c++17 -Wall）：

#include <iostream>
#include <memory>

struct Widget {
    int id;
    void work() const { std::cout << "Widget " << id << " working\n"; }
};

int main() {
    auto pw = std::make_unique<Widget>(Widget{7});
    auto cb = [up = std::move(pw)] { up->work(); };
    std::cout << "移动后 pw == nullptr ? " << (pw == nullptr) << "\n";
    cb();
    return 0;
}

实测输出：

移动后 pw == nullptr ? 1
Widget 7 working

语义拆解：[up = std::move(pw)] 在闭包类型里声明了一个名为 up 的数据成员，用 std::move(pw) 初始化它——up 的类型按 auto 规则推导为 std::unique_ptr<Widget>。移动发生后，外层 pw 被掏空（实测为 nullptr），所有权进入闭包。闭包随 std::function、任务队列走到哪里，Widget 就活到哪里——这正是异步回调需要的所有权语义。

注意语法对称性的陷阱：[up = std::move(pw)] 里等号右边在外围作用域求值（所以 pw 指外层的 pw），左边是闭包内部的新名字（和外层没有任何关系，只是恰好可以同名）。

表达式捕获：创建时求值，不是调用时

= 右边可以是任意表达式。一个必须钉死的直觉：表达式在 lambda 创建的那一刻求值一次，之后每次调用用的都是那个已存好的值：

#include <iostream>

int compute() {
    std::cout << "compute() 被调用\n";
    return 42;
}

int main() {
    std::cout << "--- 创建 lambda 前 ---\n";
    auto cb2 = [n = compute()] { return n * 2; };
    std::cout << "--- lambda 已创建，尚未调用 ---\n";
    std::cout << "cb2() = " << cb2() << "\n";
    std::cout << "cb2() = " << cb2() << "（compute 没有再次执行）\n";
    return 0;
}

本机实测（clang 23.1.0）输出：

--- 创建 lambda 前 ---
compute() 被调用
--- lambda 已创建，尚未调用 ---
cb2() = 84
cb2() = 84（compute 没有再次执行）

compute() 只在创建时跑了一次——「compute() 被调用」出现在「lambda 已创建」之前，两次 cb2() 都没有触发新的计算。这和函数参数「调用时求值」的直觉相反，写错时机（比如把本该每次调用都重算的表达式放进 init capture）会悄悄拿到过期值。

更多形态：

// 捕获 this 所指对象的副本（C++17 起更推荐 [*this]）
auto cb = [self = *this] { return self.data; };

// 按值捕获 shared_ptr：引用计数 +1，闭包保活共享对象
auto sp = std::make_shared<Config>();
auto cb2 = [config = sp] { return config->get("key"); };

// 捕获引用（少见，等价于 [&timer]）
auto cb3 = [&timer = timer] { return timer.elapsed(); };

C++11 的历史变通：std::bind

C++11 没有 init capture，想把 unique_ptr 塞进可调用对象只能用 std::bind：把要移动的对象作为实参移进 bind 对象，lambda 按引用接收：

#include <functional>
#include <iostream>
#include <memory>

struct Widget {
    int id;
    void work() const { std::cout << "Widget " << id << " working\n"; }
};

int main() {
    std::unique_ptr<Widget> pw(new Widget{7});   // C++11 没有 make_unique
    auto cb = std::bind([](std::unique_ptr<Widget>& w) { w->work(); },
                        std::move(pw));
    std::cout << "移动后 pw == nullptr ? " << (pw == nullptr) << "\n";
    cb();
    return 0;
}

本机实测（clang 23.1.0，-std=c++11 -Wall）输出：

移动后 pw == nullptr ? 1
Widget 7 working

能跑，但写法绕：要理解 bind 的实参存储语义、占位符规则（Item 34 细讲），还引入了 bind 自身的坑（默认拷贝、不可内联）。顺带实测：C++11 模式下直接写 init capture，clang 23.1.0 报（-std=c++11 -pedantic-errors）：

error: initialized lambda captures are a C++14 extension
      [-Werror,-Wc++14-extensions]
    auto cb = [y = x * 2] { return y; };
               ^

（不加 -pedantic-errors 时 clang 只给扩展警告并放行——这是编译器兼容行为，不是标准许可。）C++14 之后，bind 的这个历史使命正式结束。

把两个核心用法放一个程序里（就是上文两段实测代码的合体）：

常见错误（新手踩坑）

  1. 移动后继续使用原对象。[up = std::move(pw)] 之后 pw 是 nullptr（实测），再 pw->work() 是 UB，实际通常直接崩溃。修正：移动后把原变量当不存在。
  2. 以为表达式在调用时求值。[n = compute()] 的 compute() 只在创建 lambda 时跑一次（实测打印顺序为证）。需要每次调用重算的逻辑要放进 lambda 体内，而不是捕获列表。
  3. 给捕获起和外层相同的名字后以为改的是外层变量。[x = x]{ ++x; }（需 mutable）改的是闭包里的副本，外层 x 纹丝不动——init capture 是按值存储的，除非显式 [&x = x]。
  4. 在 C++11 代码里写 init capture。编译报 initialized lambda captures are a C++14 extension（实测原文）；要么升级标准，要么退回 std::bind 变通。

HFT 关联

  • 把重资源移进异步任务：std::async([buf = std::move(large_buffer)] { flush(buf); })——日志缓冲、行情快照这类大对象零拷贝进入后台任务，主线程交出所有权后继续跑热路径。
  • 策略对象生命周期托管给闭包：[engine = std::move(engine_ptr)] { engine->on_tick(t); } 让回调持有策略的 unique_ptr，配合 Item 31 的教训，彻底消除 this 悬垂。
  • 捕获时固定快照：[threshold = risk.current_threshold()] 在创建闭包时冻结风控阈值——创建时求值的语义恰好是「快照」，盘中改配置不影响已派发的任务。
  • shared_ptr 按值捕获的代价：[sp] 引用计数 +1 是原子操作，热路径上每微秒都计数；能 move 就 move，能拷裸值就别拷智能指针。

自测题

1. [up = std::move(pw)] 的语义是什么？等号两边分别在哪个作用域求值/生效？

答案

这是 C++14 的初始化捕获：等号右边 std::move(pw) 是在外围作用域求值的初始化表达式（在 lambda 创建时执行一次）；等号左边 up 是闭包类型的新数据成员的名字，类型按 auto 规则推导（此处为 std::unique_ptr<Widget>）。语义是把外层 unique_ptr 的所有权转移进闭包——实测移动后外层 pw == nullptr。

2. init capture 解决了 C++11 lambda 的哪些限制？

答案

三个：①移动捕获——C++11 只有按值拷贝和按引用两种捕获，unique_ptr 等 move-only 类型进不了闭包；②捕获任意表达式的结果——[n = compute()]、[p = std::make_shared<T>()]，不必先在外层造一个具名变量；③给捕获改名——[d = this->data]，绕开 [=] 实际捕获 this 的陷阱（Item 31）。

3. [n = compute()] 的 compute() 什么时候执行？每次调用 lambda 都会重算吗？

答案

在 lambda 创建时求值一次，结果存为闭包的数据成员；之后每次调用用的都是这个存好的值，不会重算。本文实测：compute() 的打印出现在「lambda 已创建，尚未调用」之前，两次 cb2() 都返回 84 且没有新的 compute() 打印。这和函数参数「调用时求值」的直觉相反。

4. C++11 没有 init capture 时，怎么把 unique_ptr 移进可调用对象？

答案

用 std::bind：std::bind([](std::unique_ptr<Widget>& w){ w->work(); }, std::move(pw))——把 unique_ptr 移进 bind 对象的实参存储，lambda 按引用接收它。本机 -std=c++11 实测可行（移动后 pw == nullptr，cb() 正常输出）。但写法绕、有 bind 自身的坑，C++14 起被 init capture 全面取代（见 Item 34）。

5. 下面代码有什么问题？

auto sp = std::make_shared<Widget>();
auto cb = [sp = std::move(sp)]{ sp->do_work(); };
sp->do_work();
答案

崩溃/UB。[sp = std::move(sp)] 把外层 shared_ptr 的所有权转移进闭包（移动后的 shared_ptr 保证为空），紧接着的 sp->do_work() 对空 shared_ptr 解引用——未定义行为，实际通常段错误。修正：想两边都用就按值拷贝捕获（[sp]，引用计数 +1）；本意是移交所有权就删掉最后一行。

6. init capture 和 [*this]（C++17）都能捕获对象的副本，怎么选？

答案

[*this] 拷贝整个对象进闭包，一行搞定但粒度粗；[d = data] 只拷需要的成员，对象大时更省。成员少/对象小用 [*this] 最简洁；只缺一两个成员、或想给捕获改个不与成员冲突的名字时用 init capture。C++14/11 代码没有 [*this]，只能用 [self = *this]（C++14）或先拷局部（C++11）。

为什么要学这个（先建立直觉）

函数模板的完美转发你已经会了：template<class T> void f(T&& x) { g(std::forward<T>(x)); }。C++14 把泛型能力给了 lambda（参数可以写 auto），问题随之而来：lambda 没有你能写的模板参数名 T——forward 需要显式模板实参，forward<???>(x) 里填什么？

Meyers 的答案：decltype(x)。形参 x 的声明类型里带着推导出的引用性，decltype 原样取出（Item 3 的规则在这里派上用场），交给 forward 正好够用。这是第 1 章（decltype）、第 5 章（万能引用 + forward）两条线在 lambda 里的合流点。

这节讲什么

  1. 泛型 lambda 的真面目：闭包类里的模板 operator()（含手写等价类对照）；
  2. 为什么完美转发必须配 std::forward<decltype(x)>(x)，std::move 错在哪（实测）；
  3. decltype(x) 为什么给出引用类型，decltype((x)) 为什么会把右值性弄丢；
  4. 返回类型推导的规则与冲突报错；
  5. C++20 显式模板参数列表 lambda（终于能写出 T）；
  6. 与 std::function 的配合，以及类型擦除的实测代价。

本机环境：clang 23.1.0，arm64-apple-darwin，libc++，默认 -std=c++17 -Wall，C++20 段落标 -std=c++20。

泛型 lambda = 闭包类里的模板 operator()

写 [](auto&& x){...} 时，编译器生成的闭包类大致是这样（手写等价版实测行为一致）：

struct CompilerClosure {
    template<class __T>
    auto operator()(__T&& x) const { return x + x; }
};

__T 是编译器内部的名字——你的 lambda 体里够不着它，这是后面所有麻烦的根源。实测同一个 lambda 被不同类型调用（这本身就是"operator() 是模板"的证据）：

twice(21)          = 42          // __T = int
twice(2.5)         = 5           // __T = double
twice(std::string) = abab        // __T = std::string
手写闭包 cc(21)     = 42
手写闭包 cc(2.5)    = 5

decltype(x) 是唯一能合法拿到这个类型的途径。

必须配 forward(x)

void func(std::string&  s);   // 左值重载
void func(std::string&& s);   // 右值重载

auto fwd = [](auto&& x){ func(std::forward<decltype(x)>(x)); };
auto bad = [](auto&& x){ func(std::move(x)); };

clang 23.1.0 实测：

fwd(s)          :  左值重载: tick-long-enough-to-beat-sso-optimization
fwd("临时")      :  右值重载: 临时
bad(s)          :  右值重载: tick-long-enough-to-beat-sso-optimization

auto&& 是万能引用（有 auto 推导，Item 24）：左值实参 → auto 推为 T&（形参折叠成 T&）；右值实参 → auto 推为 T（形参 T&&）。decltype(x) 取形参的声明类型——正是 forward 需要的输入。

decltype(x) 为什么给出引用类型

实测（nm<T>() 把类型名打印出来）：

probe(左值):
  decltype(x)   = std::string&
  decltype((x)) = std::string&
probe(右值):
  decltype(x)   = std::string&&
  decltype((x)) = std::string&

两条结论：

  • decltype(x) 走的是 Item 3 的"分支一"——x 是变量名的 id-expression，结果是它的声明类型，完整保留引用性与 cv：左值实参时 T&、右值实参时 T&&。
  • decltype((x)) 是"分支二"——(x) 是表达式，左值表达式恒给 T&。实测右值实参时它把 std::string&& 压成了 std::string&，右值性丢失，forward 退化成左值转发。转发语境永远写 decltype(x)，一个括号都不能多加。

反面教材：std::move 的代价（本机实测纠正）

std::move 是无条件转右值，左值实参也被强行移动。笔记里流传多年的说法——"SSO 短字符串 move 后内容还在"——在本机不成立：

std::string short_s = "tick";                                   // SSO：数据存在对象里
std::string long_s  = "AAPL 20260710 C 230.00 x100 @1.2345";    // 堆分配
auto takes = [](auto&& x){ std::string owned = std::move(x); ... };

  取走: tick
  move 后 short_s = '' (size=0)
  取走: AAPL 20260710 C 230.00 x100 @1.2345
  move 后 long_s  = '' (size=0)

本机 libc++ 上短串和长串移动后都被清空。标准只保证源对象处于"有效但未指定"状态——它现在恰好是空串，换实现可以直接改成别的有效值。结论不变但理由要更正：不能用"看起来没被掏空"当安全证据，得靠写法正确。对照 forward 的版本：左值实参时被拷贝进 owned，源对象内容完好（实测 lv = '左值内容-足够长-...' 保留）。

返回类型推导

泛型 lambda 的返回类型按 auto 规则推导（每次实例化独立推导）。两条分支返回类型不一致时实测报错：

auto pick = [](auto x){ if (x > 0) return x; else return 0.0; };   // int / double 冲突
std::cout << pick(1) << "\n";

error: 'auto' in return type deduced as 'double' here but deduced as 'int' in earlier return statement
note: in instantiation of function template specialization 'main()::(lambda)::operator()<int>' requested here

需要稳定分支类型时，显式写尾置返回类型：[](auto x) -> double { ... }。

C++20：终于能写 T 了

C++20 允许 lambda 带显式模板参数列表（clang 23.1.0 + -std=c++20 实测）：

auto f = []<typename T>(T&& x){ func(std::forward<T>(x)); };   // T 有名字了

auto probe = []<typename T>(T&& x){ std::cout << __PRETTY_FUNCTION__ << "\n"; };
auto conv  = []<typename T>(T x){ return static_cast<double>(x); };
conv.template operator()<long>(7);                             // 甚至可以显式指定实参
auto sum2  = []<std::integral... Ts>(Ts... xs){ return (xs + ...); };  // 变参 + 约束

实测输出：

  auto main()::(lambda)::operator()(T &&) const [T = std::string &]
  auto main()::(lambda)::operator()(T &&) const [T = std::string]
  auto main()::(lambda)::operator()(T &&) const [T = int]
conv.template operator()<long>(7): 7
sum2(1,2,3) = 6

注意 __PRETTY_FUNCTION__ 里的 (lambda)::operator()——这直接证实了"闭包类的 operator() 是模板"。另外 -std=c++17 下这段会给出 warning: explicit template parameter list for lambdas is a C++20 extension（作为扩展仍能编译），不要误以为已经在 C++17 合法。

与 std::function 的配合：类型擦除只冻结一种签名

std::function 做的是类型擦除，它必须先把"要调用什么签名"固化下来：

auto twice = [](auto&& x){ return x + x; };
std::function<int(int)> fi = twice;    // 冻结成 int(int)，此时才实例化 operator()<int>
fi(21);                                // OK：42

擦除之后泛型就消失了——实测再用别的类型调用：

error: no matching function for call to object of type 'std::function<int (int)>'
    std::cout << f2(std::string("x")) << "\n";
                 ^~
note: candidate function not viable: no known conversion from 'std::string' to 'int' for 1st argument

所以 std::function 存泛型 lambda 时，你选的那个签名就是它的全部能力。要保留泛型请用 auto 变量或模板参数传递闭包。

性能实测（-O2，取 5 轮最小值）

泛型 lambda 直调       : 0.31 ~ 0.39 ns/次
再包一层 lambda        : 0.31 ~ 0.35 ns/次
std::function 类型擦除 : 0.94 ns/次
类型擦除 / 直调 = 2.4x ~ 3.0x

auto 变量持有的 lambda 一路上都会被内联展开（实测"再包一层"没有任何额外开销）；std::function 每次调用要走一次间接跳转（通过擦除后的 invoker 指针），实测约多付 0.5-0.6 ns/次。绝对数字很小，但它决定了：回调注册可以用 std::function，热路径上逐条调用的地方要用模板传闭包。

template<class T> const char* nm() {
    if constexpr (std::is_same_v<T, std::string&>)       return "std::string&";
    else if constexpr (std::is_same_v<T, std::string>)   return "std::string";
    else if constexpr (std::is_same_v<T, std::string&&>) return "std::string&&";
    else return "?";
}

int main() {
    auto fwd = [](auto&& x){ func(std::forward<decltype(x)>(x)); };
    auto bad = [](auto&& x){ func(std::move(x)); };

    std::string s = "tick-long-enough-to-beat-sso-optimization";
    std::cout << "fwd(s)     :"; fwd(s);
    std::cout << "fwd(右值)  :"; fwd(std::string("新生"));
    std::cout << "bad(s)     :"; bad(s);

    auto probe = [](auto&& x){
        std::cout << "  decltype(x)   = " << nm<decltype(x)>()
                  << " / decltype((x)) = " << nm<decltype((x))>() << "\n";
    };
    std::cout << "probe(左值):\n"; probe(s);
    std::cout << "probe(右值):\n"; probe(std::string("y"));

    auto twice = [](auto&& x){ return x + x; };
    std::cout << "twice(21) = " << twice(21) << " / twice(std::string(ab)) = " << twice(std::string("ab")) << "\n";
    std::function<int(int)> fi = twice;
    std::cout << "std::function<int(int)>::fi(21) = " << fi(21) << "\n";
}

本机实测 clang 23.1.0（-std=c++17 -Wall）输出：

fwd(s)     :  左值重载: tick-long-enough-to-beat-sso-optimization
fwd(右值)  :  右值重载: 新生
bad(s)     :  右值重载: tick-long-enough-to-beat-sso-optimization
probe(左值):
  decltype(x)   = std::string& / decltype((x)) = std::string&
probe(右值):
  decltype(x)   = std::string&& / decltype((x)) = std::string&
twice(21) = 42 / twice(std::string(ab)) = abab
std::function<int(int)>::fi(21) = 42

常见错误（新手踩坑）

  1. 泛型 lambda 里用 std::move。实测 bad(s) 走右值重载——左值实参被允许掏空。本机实测纠正：SSO 短串移动后同样被清空（size=0），"短串看不出问题"的说法在这套 libc++ 上不成立。
  2. 试图 forward<auto>(x)——auto 不是类型，不能当模板实参。decltype(x) 是唯一通道（C++20 前）。
  3. decltype((x)) 多加一对括号。实测右值实参时它把 std::string&& 压成 std::string&，右值性丢失、转发退化。永远写 decltype(x)。
  4. 以为 std::function 能保住泛型。它只冻结一个签名，实测用别的类型调用报 no matching function for call to object of type 'std::function<int (int)>'。
  5. 返回类型推导冲突。两条 return 类型不一致时报 deduced as 'double' here but deduced as 'int' in earlier return statement——显式写 -> T。
  6. 在 -std=c++17 下用 C++20 的模板参数列表写法。能编（作为扩展），但会出 -Wc++20-extensions 警告——不要把带警告的代码当已标准化。
  7. 普通 lambda 过度泛化。参数类型明明确定（只接 const Tick&），就别写 auto&&——泛型接口的接受面越大，误用面越大。

HFT 关联

  • 回调适配层：策略引擎里把用户 lambda 包一层再接进事件循环（记日志、计时、异常吞掉）——包装层必须完美转发，否则 tick 对象在每一跳被多拷一次。[](auto&& tick){ timer.scoped([&]{ user_cb(std::forward<decltype(tick)>(tick)); }); } 是标准件。
  • std::function 别用在每 tick：实测类型擦除多付 0.5-0.6 ns/次且有间接跳转。回调注册/存储用它没问题，逐条调用的热路径要用模板传闭包（template<class F> void onTick(F&& cb)），让 operator() 内联展开。
  • decltype 全家桶的汇合点：Item 3 的 decltype 规则 + 第 5 章的万能引用 / 引用折叠 / forward，在泛型 lambda 这一个语法点上全部用上——它是检验前面内容是否真懂的试金石。

自测题

1. 泛型 lambda 的 auto&& 参数如何配合 std::forward 实现完美转发？为什么不能写 forward<T>？

答案

auto&& 是万能引用：左值实参使 auto 推为 T&（形参折叠成 T&），右值实参推为 T（形参 T&&）。decltype(x) 取出形参的声明类型——左值时 T&、右值时 T&&——交给 std::forward<decltype(x)>(x) 即可还原值类别（实测左值走左值重载、右值走右值重载）。不能写 forward<T> 是因为那个模板参数是编译器合成的内部名，源码里没有可写的 T。

2. 为什么说"泛型 lambda = 闭包类里的模板 operator()”？有什么实测证据？

答案

手写 struct CompilerClosure { template<class __T> auto operator()(__T&& x) const { return x + x; }; }; 与 [](auto&& x){ return x + x; } 行为一致（实测 cc(21)=42、cc(2.5)=5）。更直接的证据：同一个 lambda 能被 int/double/std::string 分别调用；__PRETTY_FUNCTION__ 打印出 main()::(lambda)::operator()(T &&) const [T = std::string &]——明写了 operator() 是模板。

3. decltype(x) 在 auto&& 形参上拿到什么？左右值实参时分别是什么？为什么？

答案

拿到形参 x 的声明类型，完整保留引用性与 cv：左值实参时 std::string&，右值实参时 std::string&&（实测）。因为 x 作为变量名的 id-expression，走的是 Item 3 的"分支一"——给声明类型；它不像 auto 那样剥引用。

4. decltype((x)) 有什么问题？实测证据是什么？

答案

(x) 是表达式，走 Item 3 的"分支二"——左值表达式恒给 T&。实测右值实参时 decltype(x)=std::string&& 而 decltype((x))=std::string&：右值性被压掉，forward 退化成左值转发。永远写 decltype(x)，不多不少一个括号。

5. 用 std::move 代替 forward<decltype(x)> 会发生什么？本机对 SSO 的实测结论是什么？

答案

左值实参也被强制转右值：实测 bad(s)（s 是左值）走了右值重载。关于"看起来没事"的细节需要更正——本机 libc++ 上短串（SSO）和长串移动后 size 都变成 0（实测 move 后 short_s = '' (size=0)）。标准只保证"有效但未指定"，现在是空串、换个实现可以是任何有效值。所以"没看到破坏"绝不是证据，唯一可靠的是写法正确。

6. C++20 给泛型 lambda 加了什么新写法？在 C++17 下会怎样？

答案

显式模板参数列表：[]<typename T>(T&& x){ func(std::forward<T>(x)); }——模板参数终于有了可写的名字，还能配合约束（[]<std::integral... Ts>(Ts... xs)）与显式指定实参（conv.template operator()<long>(7)）。-std=c++17 下能编但给出 warning: explicit template parameter list for lambdas is a C++20 extension，不要当成已标准化。

7. 泛型 lambda 存进 std::function 会丢什么？性能代价实测多少？

答案

丢泛型本身：std::function<int(int)> f = twice; 只冻结 int(int) 这一个实例化，再用 std::string 调用报 no matching function for call to object of type 'std::function<int (int)>'。性能上（-O2，5 轮最小值）泛型 lambda 直调约 0.31-0.39 ns/次、std::function 约 0.94 ns/次，即约 2.4-3.0 倍、多付约 0.5-0.6 ns/次；而"再包一层 lambda"没有任何额外开销（完全内联）。

Item 34：优先 lambda 而非 std::bind

第 6 章 Lambda 表达式 · Item 34 · 上一节：Item 33 泛型 lambda

为什么要学这个（先建立直觉）

std::bind 是 C++11 的产物，解决的是「把函数的部分实参先固定下来，剩下的以后再传」——C 程序员要做同样的事得手写包装函数。2011 年它是个进步，因为那一年 lambda 还不能移动捕获、没有泛型形参，有些活只有 bind 能干。

但 C++14 之后形势翻转：Item 32 的 init capture 补齐了移动捕获，Item 33 的泛型 lambda 补齐了延迟参数——bind 的每一项能力 lambda 都有，而且 lambda 可读、可内联、报错友好。bind 剩下的只有一堆坑：占位符 _1/_2 和实参的映射要靠脑补、实参在 bind 时就求值、重载函数要 static_cast 消歧、默认拷贝实参想用引用得包 std::ref。

你还会在大量 2011–2014 年的老代码（和老面试题）里见到 bind，所以要能读懂它；但新代码没有理由再写它。这一节用四个实测把 bind 的坑逐个坐实，然后给出结论。

这节讲什么

  1. bind 的占位符语义：_1 是「调用时再传」的第 1 个实参，可以重排（反直觉）；
  2. 求值时机实测：bind 的实参在 bind 时求值，lambda 的 init capture 同样在创建时求值，lambda 体内才是调用时求值；
  3. 重载函数交给 bind 必须 static_cast 消歧（报错原文实测）；
  4. bind 默认拷贝实参，要引用得 std::ref（实测对比）；
  5. 结论：lambda 全面胜出，bind 仅历史价值。

占位符语义：_1 是「洞」

std::bind(f, a, _1) 的含义：造一个可调用对象，调用它时把第 1 个实参填进 _1 这个「洞」，其余位置用 bind 时存的值。本机实测（clang 23.1.0，-std=c++17 -Wall）：

#include <functional>
#include <iostream>
#include <string>

void report(int pri, const std::string& msg) {
    std::cout << "[" << pri << "] " << msg << "\n";
}

int main() {
    using namespace std::placeholders;
    auto r = std::bind(report, 1, _1);   // pri 固定为 1，msg 留洞
    r("hello");                          // report(1, "hello")

    // 占位符还能重排——调用时的第 2 个实参填进函数的第 1 个形参
    auto swap2 = std::bind(
        [](int a, int b){ std::cout << a << "," << b << "\n"; }, _2, _1);
    swap2(1, 2);                         // 输出 2,1 —— 反直觉！
    return 0;
}

实测输出：

[1] hello
2,1

swap2(1, 2) 输出 2,1——_2 写在前面就把调用方的第 2 个实参放到了函数的第 1 个位置。读 bind 表达式要在脑子里跑一遍「占位符编号 → 调用方实参序号 → 目标函数形参位置」的两级映射，这就是它晦涩的根源。lambda 版本一眼见底：

auto swap2 = [](int a, int b) { return std::invoke(目标, b, a); };
// 或者直接：
auto swap2 = [](int a, int b){ std::cout << b << "," << a << "\n"; };

求值时机：bind 时 vs 调用时

bind 的实参（非占位符部分）在 bind 那一刻求值并存进 bind 对象；lambda 的 init capture 同样在创建时求值；只有 lambda 体内的表达式才是调用时求值。实测（带打印的 compute()）：

#include <functional>
#include <iostream>

int compute() {
    std::cout << "compute() 执行\n";
    return 42;
}
void show(const char* tag, int v) { std::cout << tag << ": " << v << "\n"; }

int main() {
    using namespace std::placeholders;
    std::cout << "== bind 版本 ==\n";
    auto f = std::bind(show, "bind", compute());    // compute() 现在就跑
    std::cout << "-- bind 对象已创建 --\n";
    f();

    std::cout << "== lambda 版本 ==\n";
    auto g = [v = compute()] { show("lambda", v); }; // init capture 也是创建时
    std::cout << "-- lambda 已创建 --\n";
    g();

    auto h = [] { show("lambda-延迟", compute()); }; // 体内调用：调用时求值
    std::cout << "-- h 已创建 --\n";
    h();
    return 0;
}

本机实测（clang 23.1.0）输出：

== bind 版本 ==
compute() 执行
-- bind 对象已创建 --
bind: 42
== lambda 版本 ==
compute() 执行
-- lambda 已创建 --
lambda: 42
-- h 已创建 --
compute() 执行
lambda-延迟: 42

bind 和 init capture 的 compute() 都在对象创建之前打印——两者语义相同；只有 lambda 体内的 compute() 延迟到了 h() 调用时。所以「bind 在 bind 时求值、lambda 在调用时求值」的流行说法只对 lambda 体成立，对 init capture 不成立——这一点 Item 32 的实测也印证了。

重载函数：bind 必须 static_cast 消歧

重载函数名在表达式里没有唯一类型，bind 推导不出来。本机实测报错原文（clang 23.1.0）：

int value(int x) { return x; }
double value(double x) { return x; }
auto f = std::bind(&value, _1);

error: no matching function for call to 'bind'
note: candidate template ignored: couldn't infer template argument '_Fp'

必须手动消歧：

auto vi = std::bind(static_cast<int(*)(int)>(&value), _1);
std::cout << vi(5) << "\n";   // 实测输出：50

lambda 天然免疫——重载决议发生在 lambda 体内正常的函数调用点，编译器按实参类型自动选：

auto vi = [](int x) { return value(x); };   // 自动选中 int 版本，无需 cast

默认拷贝实参：std::ref 的坑

bind 把非占位符实参按值拷贝进 bind 对象（准确说是 decay-copy）。想改到原件必须显式 std::ref：

struct Counter {
    int n = 0;
    void bump() { ++n; }
};

Counter c;
auto b1 = std::bind(&Counter::bump, c);            // 拷了一份 c
auto b2 = std::bind(&Counter::bump, std::ref(c));  // 持有引用
b1();  b1();
std::cout << "b1 两次后 c.n = " << c.n << "\n";
b2();  b2();
std::cout << "b2 两次后 c.n = " << c.n << "\n";

本机实测（clang 23.1.0）输出：

b1 两次后 c.n = 0（拷贝，没改到原件）
b2 两次后 c.n = 2（std::ref，改到原件）

b1 改的是 bind 对象内部那份拷贝，原件纹丝不动——忘了 std::ref 的 bug 不报错、不警告，静默无效。lambda 的捕获列表把「拷贝还是引用」写在明面上：[c] 拷贝、[&c] 引用、[c = std::move(c)] 移动，没有第三种隐藏规则。

完整可运行例子

同一任务两种写法对照：固定优先级上报消息。

#include <functional>
#include <iostream>
#include <memory>
#include <string>

void report(int pri, const std::string& msg) {
    std::cout << "[" << pri << "] " << msg << "\n";
}

int main() {
    using namespace std::placeholders;

    // bind 版本：pri 固定 1，msg 留洞
    auto b = std::bind(report, 1, _1);
    b("from bind");

    // lambda 版本：一目了然，可内联
    auto l = [](const std::string& msg) { report(1, msg); };
    l("from lambda");

    // lambda 还能做 bind 做不到/很绕的事：移动捕获（Item 32）
    auto pw = std::make_unique<std::string>("owned");
    auto m = [pw = std::move(pw)] { report(9, *pw); };
    m();
    return 0;
}

本机实测（clang 23.1.0，-std=c++17 -Wall）输出：

[1] from bind
[1] from lambda
[9] owned

常见错误（新手踩坑）

  1. 占位符重排后读错参数顺序。std::bind(f, _2, _1) 调用 g(1, 2) 实际是 f(2, 1)（实测输出 2,1）。占位符编号指「调用方的第几个实参」，不是「目标函数的第几个形参」。
  2. 忘了 std::ref 导致静默拷贝。std::bind(&Counter::bump, c) 拷了一份 c，调用改了副本，原件不变（实测 c.n 仍为 0）。不报错不警告。
  3. 重载函数直接交给 bind。std::bind(&value, _1) 报 couldn't infer template argument '_Fp'（实测原文），必须 static_cast<int(*)(int)>(&value)；lambda 写法 [](int x){ return value(x); } 无需消歧。
  4. bind 成员函数忘了传对象。std::bind(&Widget::process, _1) 漏了 this，调用签名对不上；正确是 std::bind(&Widget::process, &w, _1)。lambda 写 [&w](auto& d){ w.process(d); } 不会犯这个错。

HFT 关联

  • 热路径回调必须可内联：lambda 的闭包类型编译期已知，std::sort(v.begin(), v.end(), [](auto& a, auto& b){ ... }) 比较器直接内联进排序循环；bind/函数指针是间接调用，每 tick 成千上万次比较时差距可观。回测引擎、订单簿遍历全部用 lambda。
  • bind 的隐藏拷贝是延迟地雷：std::bind(process, big_config) 在 bind 时拷贝整个配置对象，还可能是 decay-copy 丢掉 const/引用——热路径上这种「看不见的拷贝」比显式拷贝更难排查。lambda 捕获列表把拷贝/引用/移动写在明面上。
  • 老代码迁移：2015 年前的策略框架里 bind 常见，迁移时逐条换成 lambda，顺手把 std::ref 语义改成显式 [&c]，代码评审时捕获清单一目了然。
  • 占位符重排是事故源：bind(f, _2, _1) 这类参数对调写法在 lambda 里是 [](auto a, auto b){ f(b, a); }——参数名让意图显式，code review 不用解码 _N。

自测题

1. std::bind(report, 1, _1) 中 _1 的含义是什么？std::bind(f, _2, _1) 调用 g(1, 2) 时实参如何传递？

答案

_1 是一个「洞」：表示调用 bind 返回的对象时传入的第 1 个实参。std::bind(report, 1, _1) 固定了第一个形参 pri=1，msg 留给调用方。占位符编号指调用方的实参序号而非目标函数的形参位置，所以 std::bind(f, _2, _1) 被 g(1, 2) 调用时执行的是 f(2, 1)——本文实测输出 2,1，反直觉，是 bind 可读性差的主要原因。

2. bind 的非占位符实参与 lambda 的 init capture，求值时机各是什么？「lambda 在调用时求值」的说法哪里不准确？

答案

bind 的非占位符实参在 bind 时求值并存入 bind 对象；lambda 的 init capture 在 lambda 创建时求值——两者时机相同（本文实测：compute() 的打印都在「对象已创建」之前）。「lambda 在调用时求值」只对 lambda 体内的表达式成立，对捕获列表不成立；要延迟到调用时计算，得把表达式写进 lambda 体。

3. 为什么重载函数不能直接交给 std::bind？怎么处理？lambda 为什么没有这个问题？

答案

重载函数名不对应唯一类型，bind 的模板形参 _Fp 推导失败（clang 实测报 couldn't infer template argument '_Fp'）。处理办法是 static_cast 消歧：std::bind(static_cast<int(*)(int)>(&value), _1)。lambda 里重载决议发生在 lambda 体内的普通调用点，编译器按实参类型自动选重载，[](int x){ return value(x); } 无需任何 cast。

4. std::bind(&Counter::bump, c) 调用后 c 会变吗？为什么？

答案

不会。bind 对实参做 decay-copy，c 被拷贝进 bind 对象，bump() 改的是那份拷贝（本文实测：调用两次后 c.n 仍为 0）。要改原件必须 std::ref(c)——实测 std::ref 版本两次调用后 c.n == 2。lambda 的对应语义是显式的：[c] 拷贝、[&c] 引用，不会静默选错。

5. 既然 lambda 全面胜出，bind 还有什么存在价值？

答案

历史价值为主：读懂和维护 C++11 时代的老代码（当时 lambda 没有 init capture 和泛型形参，移动捕获、延迟参数只能靠 bind）；以及极少数「多态函数对象的部分应用」场景 bind 更紧凑。Meyers 的结论是：C++14 起新代码一律 lambda——可读性、可内联性、错误信息、捕获控制全面占优。

6. lambda 可内联为什么对 HFT 重要？bind 为什么不行？

答案

lambda 的闭包类型在编译期完全已知，调用点能看到函数体，编译器可内联并进一步做常量传播、循环展开；bind 返回的对象通过内部函数指针/类型擦除间接调用目标，编译器通常看不到最终调用目标，无法内联。HFT 热路径每 tick 成千上万次调用（比较器、过滤器、回调分发），每次间接调用的分支预测失败和调用开销会累积成可观延迟。

Q1[=] 捕获 this
class Engine {
    int data = 42;
public:
    auto get_cb() {
        return [=]() { return data; };  // 捕获的是什么？
    }
};

[=] 捕获的是 data 的副本吗？

答案与复习指引

不是。 [=] 在成员函数中捕获的是 this 指针（按值），不是 data 的副本。闭包通过 this->data 访问成员——如果 Engine 对象先于闭包销毁，this 悬垂，UB。

修复（C++17）： [*this]() 按值捕获对象本身的副本。 修复（C++11/14）： auto d = data; return [d]() { return d; };（先拷贝到局部变量再捕获）。

教训： 避免用 [=] 默认捕获，显式列出要捕获的变量。

Q2初始化捕获（C++14）
auto pw = std::make_unique<Widget>();
auto cb = [up = std::move(pw)]() {
    up->doSomething();
};
// pw 现在是什么状态？

pw 在 lambda 创建后是什么状态？这个模式叫什么？

答案与复习指引

pw = nullptr（空）。 up = std::move(pw) 把 unique_ptr 移入闭包。这叫"初始化捕获"（init capture），C++14 新特性。

解决的问题： C++11 的 [=]/[&] 无法捕获移动语义——只能拷贝或引用。初始化捕获允许在捕获时执行任意表达式（包括 move），把结果存入闭包。

C++11 变通： std::bind + std::move，但更绕。
