# 条款 35：理解 C++ 标准演进的方向，写与时俱进的代码

## 本节讲什么

**Understand where C++ is heading, and write code that ages well.**
More Effective C++（1996）的这条收尾最有先见之明：书里"未来的特性"
（智能指针/移动语义/concepts）今天都是现实。本条按 2026 视角总结：
哪些写法在**升值**（越来越主流），哪些在**贬值**（正在被替代）——
写"不过时"的代码，就是站在演进方向的同侧。

## 1. 演进的主线（三十年一句话）

```
C++98（抽象机器 + RAII）→ C++11（移动语义 + 类型安全复兴）
→ C++14/17（库补全 + 编译期能力：optional/variant/string_view/if constexpr）
→ C++20（concepts/ranges/coroutines/modules：抽象表达能力换代）
→ C++23/26（expected/reflection/sender-receiver：错误处理与并发的新范式）
```

**主线**：运行期 → 编译期（计算前移）、隐式 → 显式（契约显式化）、
手写 → 标准设施（轮子收编）、继承多态 → 组合/变体（类型组合取代层次）。

## 2. 升值写法（越来越主流，新代码默认）

| 写法 | 取代什么 | 出处 |
|---|---|---|
| `unique_ptr`/值语义 RAII | 裸 new/delete | MoreEff item09/28 |
| 移动语义 + noexcept 三件套 | 手写拷贝优化 | 18.1 ② / 19.7 |
| `optional`/`variant`/`expected`（C++23） | 特殊返回值/异常滥用/错误码裸奔 | item54 |
| `string_view`/`span` 只读视图 | const string& 传参/子串拷贝 | item54 |
| `if constexpr` + concepts（C++20） | tag dispatch/enable_if 元编程 | 19.8 / item41 |
| `constexpr`/`consteval` 编译期计算 | 宏/模板元 hack | M5 |
| 结构化绑定/`auto` 明智使用 | 迭代器对/冗长类型名 | item16 ⑤ |
| `[[nodiscard]]`/属性标注 | 注释纪律 | 19.8 |

## 3. 贬值写法（正在被替代，新代码避免）

| 写法 | 现代替代 |
|---|---|
| 裸 `new`/`delete` 配对人肉管理 | RAII/容器/智能指针（item09/28/29） |
| `throw()` 动态异常规范 | `noexcept`（item14——C++17 已移除） |
| NULL/0 当空指针 | `nullptr`（类型安全的空） |
| `typedef` | `using`（可模板化别名） |
| 宏常量/宏函数 | `constexpr`/inline 函数 |
| 手写 for 循环干算法活 | `<algorithm>`/ranges（item54 ②） |
| `bind1st`/`mem_fun` 等 C++98 适配器 | lambda（已全部移除） |
| 继承当复用 | 复合/variant/策略注入（item32-35 的全部论证） |

## 4. "不过时"的判断标准（写代码时的自问）

```text
□ 这段代码表达的是"意图"还是"机制"？
  → 意图（optional/expected/concepts）抗衰；机制（手写调度）易腐
□ 它在编译期还是运行期？
  → 能前移的都该前移（编译期计算/检查只会越来越强）
□ 它的契约是类型系统强制的吗？
  → 类型强制（nodiscard/抽象类/定宽类型）比注释/文档活得久
□ 标准库/标准委员会在往这个方向走吗？
  → 同向的写法会被持续优化（实现、工具、教学全生态投入）
```

## 代码自测

**题目 1：** C++ 三十年演进的主线是什么？它如何指导"写法选择"？

<details>
<summary>参考答案</summary>

四条主线：① **运行期 → 编译期**（计算/检查前移：模板元编程 →
constexpr → consteval → reflection——能编译期做的越来越该编译期做）；
② **隐式 → 显式**（契约显式化：注释 → 类型约束 → concepts）；
③ **手写 → 标准设施**（轮子收编：bind → lambda、TR1 → std::、
手写错误码 → expected）；
④ **继承多态 → 组合**（类型组合取代层次：虚函数 → variant/策略注入/CRTP）。
写法选择的推论：**站在四条主线的同侧**——
新代码默认编译期优先、契约显式、标准设施优先、组合优先于继承；
逆势的写法（手写运行时调度、注释当契约、自造轮子、继承复用）
在五年后都会显得古老。

</details>

**题目 2：** 为什么"表达意图的代码"比"表达机制的代码"更抗衰老？

<details>
<summary>参考答案</summary>

意图代码绑定的是**问题**（"这里需要一个可空值"——optional），
机制代码绑定的是**当时的实现手段**（"用 -1 表示无效"——魔数）。
问题比手段长寿：五年后 optional 仍是答案，而魔数已经人人喊打；
concepts 表达的"T 必须可流输出"十年后仍清晰，
而 enable_if 的模板元编程嵌套五年后就没人愿意碰。
更深一层：意图代码能被**工具**理解——编译器检查 optional 的解包、
concepts 的约束、nodiscard 的忽略；机制代码对工具透明
（编译器不知道你的 -1 是什么意思）。
抗衰老的本质：**代码被理解（人 + 工具）的成本随时间不增长**——
意图直白 + 工具可查，是唯一可靠的配方。

</details>

**题目 3：** 用本条的"四问"审计：协议消息结构体 `Tick` 和设计它的新代码，怎么写最不过时？

<details>
<summary>参考答案</summary>

① 意图 vs 机制：字段语义显式（`side: Buy/Sell` 枚举类而非 0/1 魔数，
→ 19.2 的 enum class）——意图抗折旧；
② 编译期 vs 运行期：布局用 `static_assert(sizeof(Tick) == N)` 钉死
（→ 19.5 三件套）——布局漂移在编译期爆炸而不是盘中；
③ 类型强制：定宽类型（`int64_t`/`uint16_t`，→ 19.2 定宽枚举）+
trivially copyable 守卫（→ 19.8）——"可 memcpy 上网线"是类型检查
不是口头约定；
④ 演进同侧：版本字段 + 预留 + 只加不改（→ item32 协议层三原则）——
协议演进的通道从第一天就在。
结论：不过时的 Tick = **定宽 POD + enum class + static_assert +
版本化**——这套组合在 C++98 能写，在 C++26 仍然是最佳实践：
它不依赖任何"当下流行"的特性，只依赖"永远正确"的原则
（显式、可验证、兼容演进）。

</details>
