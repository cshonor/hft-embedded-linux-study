1.1

编写一个简单的 C++ 程序

第 1 章 开始 · 下一节：1.2 初识输入输出

本节讲什么

介绍 C++ 程序的基本结构。每个程序必须有一个 main 函数——操作系统通过调用它来运行程序。函数定义包含四部分：返回类型、函数名、形参列表、函数体。main 返回 0 表示执行成功。

最简单的 C++ 程序

int main() {
    return 0;  // 返回 0 表示程序正常结束
}

函数定义四要素：

部分 上例中的值 说明
返回类型 int main 必须返回 int，操作系统靠这个返回值判断程序是否成功
函数名 main 程序入口，必须叫 main（全小写）
形参列表 ()（空） 这里不带参数；1.1 节先用空列表，带参数的写法后面讲
函数体 { return 0; } 花括号包起来的语句块

程序要运行，还需经编译（源码 → 目标文件）和链接（目标文件 → 可执行文件）两步，1.5.2 会详讲。

和 C 的区别

维度 C C++ 说明
main 返回类型 int int 一样，都必须是 int
不写 return 返回值未定义（UB） main 特例：默认返回 0 C++ 只有 main 有这个豁免，其他函数不写 return 行为未定义
return 0 含义 成功 成功 一样，非 0 通常表示错误
头文件 #include <stdio.h> #include <iostream> C++ 标准库头文件不带 .h（下节讲）

一句话： C 程序员看 C++ 的 main 基本无障碍，唯一的"小惊喜"是 C++ 里 main 不写 return 也合法且默认返回 0——但别依赖这个，养成写 return 0; 的习惯更安全（也方便和 C 互移植）。

常见错误（新手踩坑）

错误 1：main 拼错或大小写不对

int Main() { return 0; }   // ❌ 编译能过，但链接报错：找不到 main
int main() { return 0; }   // ✅

为什么： 链接器找的是小写 main，Main 不会被当成入口。

错误 2：返回类型写成 void

void main() { }   // ❌ C++ 标准不允许（某些编译器放行，但不可移植）
int main() { }    // ✅

为什么： C++ 标准规定 main 必须返回 int。有些老编译器（MSVC）容忍 void main，但换编译器就崩，别养成坏习惯。

错误 3：忘 #include 就用库

main() { std::cout << "hi"; }  // ❌ 没包含 <iostream>

这节还没讲输入输出（1.2 才讲），先记住：用任何标准库设施都要先 #include 对应头文件。

动机：为什么 main 的返回值值得较真

C 程序员第一反应是"main 谁不会写"。但 main 是程序与操作系统唯一的契约接口——它决定了 CI 能不能判断成败、make 会不会继续、&& 链会不会断。三个真实的动机：

  1. 退出码是唯一的跨进程信号。日志可能没刷出来、stdout 可能被重定向到 /dev/null，但退出码一定会被父进程看到。HFT 的盘前检查脚本、嵌入式设备的看门狗脚本都靠它。
  2. main 是标准里唯一被"特殊对待"的函数（不写 return 默认 0、不能被取地址、不能被递归调用）。理解这些特例，才知道语言在哪些地方为"程序入口"开了后门。
  3. main 的返回类型直接决定 ABI。弄清"返回值怎么传出去"，后面学函数返回、结构体返回、寄存器约定都有参照。

底层实测：main 的返回值到底怎么传出去的

全部在本机 clang 23.1.0 / arm64-apple-darwin 实测。

① 退出码只保留低 8 位

源码里的 return -O2 汇编 shell 里 echo $?
return 0; mov w0, #0 0
return 3; mov w0, #3 3
return 125; mov w0, #125 125
return 256; mov w0, #256 0 ← 截断
return -1; mov w0, #-1 255
std::exit(256); 同 return 路径 0

关键： 汇编里写的是 mov w0, #256——编译器没有截断。截断发生在 OS 层（POSIX 的 waitpid 只把状态的低 8 位交给父进程）。所以自定义错误码只能用 0–125：128–255 会被信号占用，256 看起来等于 0。

② 不写 return 的 main：编译器真的补了 return 0

int main() { }              // -O2: mov w0, #0 ; ret
int main() { return 0; }    // -O2: mov w0, #0 ; ret

两份汇编 diff 完全相同。C++ 标准规定：控制流走到 main 的函数体结尾等价于 return 0;——而且这是 main 独有的豁免，其它函数漏 return 仍是 UB。仍然建议显式写 return 0;：可移植、意图清晰、和 C 互移植时不会被 C89 咬到。

③ main 不能"被使用"——标准禁止，clang 当扩展放行

int main() { if (0) main(); return 0; }        // 递归调用 main
int main() { auto p = &main; (void)p; return 0; }  // 取 main 地址

默认编译不报错（clang 扩展）。加上 -pedantic-errors：

error: referring to 'main' within an expression is a Clang extension [-Wmain]

标准 [basic.start.main] 的原话是 The function main shall not be used within a program。别这么写——换编译器就是硬错误。

④ 非法的 main 写法：实测报错原文

写法 结果
void main() { } error: 'main' must return 'int'
long main() { return 0; } error: 'main' must return 'int'
int Main() { return 0; } 编译通过，链接报错：Undefined symbols for architecture arm64: "_main", referenced from: implicit entry/start for main executable

Main 那个尤其阴险：错误发生在链接期，源码里看不出问题。clang 还会贴心地提示 ^~~~ int，意思是"你是不是想写 int"。

⑤ 头文件不是免费的

程序 二进制大小 编译耗时（3 次取最小） #include 展开行数
空 int main(){return 0;} 16 824 B 0.12 s 8 行（空）
用 <cstdio> + printf 49 960 B 0.12 s 699 行
用 <iostream> + cout 52 536 B 0.32 s 31 441 行

<iostream> 展开后 31 441 行，是 <cstdio> 的 45 倍；编译耗时约 2.7 倍。这在嵌入式交叉编译、大型项目增量编译上是实打实的成本——也是后面学"头文件分离""前置声明"的动机。

HFT / 嵌入式视角

  1. 退出码是运维契约。盘前检查程序（校验行情源连通性、检查磁盘水位、核对合约表版本）必须用不同的非 0 码区分失败原因，让上游脚本能分流处理；只用 0/1 会让排障退化成"看日志猜"。
  2. 退出码取值只用 0–125。return 256 静默变成 0，是最难查的一类 bug——脚本以为成功了。
  3. 不要用 exit() 乱杀进程。std::exit 不析构局部对象（只析构静态对象），HFT 程序里未落盘的成交回报会丢。要走正常 return 路径，或至少在 exit 前手动 flush + 落盘。
  4. 嵌入式上二进制体积直接是钱。空程序 16 KB、加个 iostream 就 50 KB——在片上 Flash 只有几百 KB 的 MCU 上，iostream 基本不可用，得走 printf 精简实现或直接写 UART。这也是为什么嵌入式 C++ 常用 -fno-exceptions -fno-rtti 且不碰 <iostream>。
  5. main 之前还有启动代码。用 otool -l 看可执行文件能看到 LC_MAIN（entryoff + stacksize），真正被操作系统调用的是 CRT 的入口，main 是被它调起来的——这解释了为什么全局对象的构造发生在 main 之前。

自测题

  1. C++ 程序的入口函数必须叫什么？返回类型必须是什么？
  2. main 函数不写 return 语句，程序行为是什么？这和 C 有什么不同？
  3. 下面哪个能作为合法的 C++ 程序入口？为什么？
(a) int main() { return 0; }
(b) void main() { }
(c) int Main() { return 0; }
  1. return 0; 和 return 1; 对操作系统意味着什么？
参考答案

  1. 入口函数必须叫 main（全小写），返回类型必须是 int。操作系统/运行时只认这一个符号：main 由启动代码调用，其返回值作为进程退出码交回父进程。函数名外的四要素里，形参列表允许 () 或 (int argc, char* argv[])，但名字和返回类型没有商量余地。

  2. C++：main 是 唯一豁免 的函数——控制流走到函数体结尾的 } 等价于 return 0;（标准规定，其它函数漏 return 仍是未定义行为）。C：C89/C90 下走到 main 结尾返回的是 未定义值（实现通常把某个寄存器的残留值当退出码，于是出现"运行结果随机"的现象）；C99 起（5.1.2.2.3）C 也规定等价于 return 0。所以真正的 C/C++ 差异只存在于 C89 及更早。仍然建议显式写 return 0;：可移植、意图清晰。

  3. 只有 (a) 能作为入口。 - (a) int main() { return 0; } ✅ 名字、返回类型都符合标准。 - (b) void main() { } ❌ 返回类型必须是 int；void main() 只是某些实现（如 MSVC）的扩展，换编译器就报错，不可移植。 - (c) int Main() { return 0; } ❌ C++ 大小写敏感，Main 是一个普通函数，链接器找不到 main 符号 → 链接期报 "undefined reference to main"。

  4. 返回值就是进程的退出状态码（exit status）：0 表示成功，非 0 表示失败（具体非零值含义由程序自己定义，如 1＝通用错误、2＝用法错误）。父进程/shell 用它决定成败：$? 查看，&&/||、set -e、make/CI 都据此判断。注意 POSIX 上只有低 8 位会被传出去（exit(256) 看起来等于 exit(0)），所以自定义错误码建议只用 0–125。

5（踩坑·高价值） 下面程序的退出码是多少？

int main() { return 256; }
  • A. 256
  • B. 0
  • C. 未定义

6（判断） int main() { } 和 int main() { return 0; } 生成的汇编完全相同。

7（应用） 你在写一个盘前检查程序，要区分"行情源连不上""磁盘水位过高""合约表版本不匹配"三种失败。退出码怎么定？为什么不能用 256、257、258？

参考答案

  1. B。编译出的汇编确实是 mov w0, #256，但 POSIX 只把进程退出状态的低 8 位交给父进程，256 & 0xFF == 0。所以 shell 里 echo $? 得到 0——看起来"成功了"。这就是为什么自定义错误码只能用 0–125。

  2. 对。-O2 下两者汇编都是 mov w0, #0 ; ret，diff 完全相同。C++ 标准规定控制流走到 main 函数体结尾等价于 return 0;，且这是 main 独有的豁免（其它函数漏 return 是 UB）。仍然建议显式写：可移植、意图清晰。

  3. 用 1 / 2 / 3（或 1/2/3 之外的任意 0–125 内的不同值），并在文档里写明映射；成功返回 0。不能用 256/257/258 是因为退出码只有低 8 位有效——256→0、257→1、258→2，会和别的错误码撞车，而且 256 会被当成"成功"。另外要避开 128–255：这一段通常被 shell 用来表示"被信号杀死"（128+信号号），比如 137 = 被 SIGKILL。同理，也不要用 std::exit 直接退——它不析构局部对象，未落盘的回报会丢。

1.2

初识输入输出

本节讲什么

C++ 通过标准库中的 iostream 提供 IO 机制，其中包含表示输入流的 istream 和表示输出流的 ostream 基础类型。讲解如何使用 std::cin 与输入运算符 >> 读取数据，使用 std::cout 与输出运算符 << 打印消息，使用 std::cerr 输出错误信息，以及使用操纵符 std::endl 结束当前行并刷新缓冲区。

要点

  • 标准库头文件 <iostream> 提供 IO 支持；istream / ostream 是输入流与输出流的基础类型
  • 管道比喻：cin/cout 是连接键盘、屏幕和程序的管道；箭头方向 = 数据流入/流出的方向
  • std::cin >> v：>> 指向变量，数据从键盘管道流进 v
  • std::cout << x：<< 指向 cout，数据从程序流出到屏幕管道
  • std::cerr << err：错误信息流出到屏幕，通常不缓冲，立刻显示
  • 变量是装数据的盒子：int v1 = 0, v2 = 0; 先声明两个能装整数的盒子；std::cin >> v1 >> v2; 让你依次敲两个数，第一个流进 v1，第二个流进 v2
  • cin >> 遇空白就停（空格 / Tab / 回车都算），不是「不按回车就一直读」；读带空格的整行用 getline（见 3.2.2 读写操作）
  • 输出顺序：从左到右，离 cout 最近的先输出
  • std::cout << v1 << " + " << v2; 从左往右读：先输出 v1，再输出 " + "，最后输出 v2
  • 若 v1=12、v2=34，屏幕显示 12 + 34
  • 把 << 看成「递给 cout」：cout 左边紧挨着的那个最先被递出去
  • std::endl：输出换行并刷新缓冲区

通俗理解：管道与数据流

可以把标准输入输出想成连接程序和外部的管道——iostream 库负责把键盘、屏幕等默认设备和你的程序连起来。

键盘 ──管道──► 程序          std::cin  +  >>
程序 ──管道──► 屏幕          std::cout +  <<
程序 ──管道──► 屏幕（错误）   std::cerr +  <<

箭头方向就是数据流的方向：

写法 数据往哪流 含义
std::cin >> v 键盘 → 变量 v 从输入通道读进程序
std::cout << x 程序 → 屏幕 从程序写出到屏幕
std::cerr << err 程序 → 屏幕 写出错误信息（通常不缓冲，立刻显示）
  • std::cin：输入管道，键盘敲的内容沿 >> 流进变量
  • std::cout：输出管道，程序里的内容沿 << 流到屏幕
  • std::cerr：错误输出管道，专门打错误/警告；不像 cout 那样先攒在缓冲区里，而是尽快显示，方便快速定位问题

连写多个 >> 或 << 时，一律从左到右依次处理：

std::cin >> v1 >> v2;
// ① 先读进 v1  ② 再读进 v2

std::cout << v1 << " + " << v2;
// ① 先输出 v1  ② 再输出 " + "  ③ 最后输出 v2
//    ▲ 紧挨 cout 的第一个，最先出现在屏幕上

输出顺序记忆法：cout 是要接东西的人，<< 是递东西的手——从左边开始递，离 cout 最近的那个最先输出，不是离得最远的先输出。

输入 vs 输出的顺序比喻：

比喻 含义
输出 cout << v1 << v2 先进先出（管道/队列） 先「放进」管道的 v1 先从另一端流到屏幕，再是 v2
输入 cin >> v1 >> v2 按顺序填格子 像铺地砖：先敲的第一个数填进 v1，第二个数填进 v2，严格按代码先后顺序

三条 IO 线：cin / cout / cerr

iostream 默认给程序连了三条线：

        ┌── cin  ──► 程序（键盘 → 程序）
键盘 ───┤
        └── （标准输入）

        ┌── cout ──► 屏幕（程序 → 屏幕，正常输出，有缓冲）
程序 ───┤
        └── cerr ──► 屏幕（程序 → 屏幕，错误输出，通常立刻显示）
线 方向 用途 缓冲
std::cin 键盘 → 程序 读入用户输入 —
std::cout 程序 → 屏幕 正常提示、结果打印 有缓冲区，可能攒一批再显示
std::cerr 程序 → 屏幕 错误、警告 无缓冲（或立即刷新），马上显示

举例（委托单）：

#include <iostream>

int main() {
    double price = 0;
    int qty = 0;

    std::cout << "请输入委托价格和数量: ";
    std::cin >> price >> qty;                    // cin：读入价格和数量

    if (price < 0) {
        std::cerr << "错误：委托价格不能为负\n";  // cerr：立刻报错，不缓冲
        return 1;
    }

    std::cout << "委托已提交：价格=" << price     // cout：正常业务提示
              << " 数量=" << qty << std::endl;
    return 0;
}
  • cin：读客户敲进来的价格和数量
  • cout：打印「委托已提交」等正常信息
  • cerr：价格非法时立刻打出错误，方便第一时间发现问题（生产环境常用专门日志库替代，但原理类似）

示例

#include <iostream>
int main() {
    std::cout << "Enter two numbers: ";

    int v1 = 0, v2 = 0;   // 两个「盒子」，用来装从键盘流进来的整数
    std::cin >> v1 >> v2; // 依次输入：第一个数 → v1，第二个数 → v2

    std::cout << v1 << " + " << v2 << " = " << v1 + v2 << std::endl;
    // 输出顺序（从左到右）：v1 → " + " → v2 → " = " → (v1+v2) → 换行
    // 例如 v1=12, v2=34 时屏幕显示：12 + 34 = 46
    return 0;
}

和 C 的区别

C 程序员第一反应：这不就是 scanf/printf 吗？是的，但 C++ 的流 IO 解决了 C 的几个老毛病：

对比点 C（stdio.h） C++（iostream） 为什么
类型安全 printf("%d", x) 写错 % 就崩 cout << x 自动按 x 的类型输出 编译期检查，不用记格式串
读入 scanf("%d", &v) 忘 & 就崩 cin >> v 不需要取地址 运算符重载替你取地址
换行刷新 printf("\n"); fflush(stdout); cout << endl;（一步到位） endl = 换行 + 刷新
错误流 fprintf(stderr, ...) cerr << ... 语法统一，且默认无缓冲
扩展性 自定义类型没法 printf 重载 << 就能 cout << obj 这才是 C++ 的核心优势

一句话总结： C 的 IO 靠"格式串 + 记类型"，C++ 靠"运算符重载自动识别类型"——写错概率大幅降低。

性能权衡（HFT 视角）： cin/cout 默认比 scanf/printf 慢，因为要同步 C 标准库。关同步：std::ios::sync_with_stdio(false); 后能接近 scanf 速度。但 HFT 热路径根本不用标准 IO，用自研二进制日志/网络库。

注释简介

第 1 章 · 上一节：1.2 初识输入输出 · 下一节：1.4 控制流

本节讲什么

C++ 的两种注释写法：单行 // 和多行 /* */。重点是一个坑——/* */ 不能嵌套，这是 C/C++ 共有的经典陷阱。

核心用法

写法 作用 适用场景
// 注释 从 // 到行尾 单行说明、临时禁用一行代码
/* 注释 */ 跨多行 模块/函数头说明、大段注释 
// 读取委托价格和数量           ← 单行注释
int qty = 0;

/*
 * 委托处理模块                  ← 多行注释
 * 负责校验、下单、回报
 */

编译器完全忽略注释——注释里的代码不会执行，纯粹是给人看的。

和 C 的区别

几乎没有区别。 这是 C 和 C++ 高度一致的地方：

对比点 C（C89） C（C99 起） C++
/* */ ✅ ✅ ✅
// ❌ 没有 ✅ 加入 ✅ 一直有
嵌套 /* */ ❌ 禁止 ❌ 禁止 ❌ 禁止

给 C 程序员的提醒： 如果你以前写 C89，// 在老 C 里不合法；但 C++ 一直支持，放心用。现代 C 项目（C99+）也都支持 // 了。

常见错误

1. /* */ 嵌套陷阱（最经典）

/*
 * 外层注释开始
 * /* 内层注释开始 */    ← 这里第一个 */ 就把外层注释关掉了！
 * 外层注释还没结束
 */                        ← 这个 */ 成了"悬空"的，编译报错

规则：第一个 */ 就关闭整个注释，不管你开了几个 /*。想临时注释掉一大段含 /* */ 的代码，用 #if 0 ... #endif（预处理指令，不受注释规则限制）：

#if 0
/* 这里的注释不会被误关闭 */
void old_code() { ... }
#endif

2. // 注释不能跨行

// 这是第一行
    这是第二行    ← 这行不是注释，编译报错

// 只管到行尾。要跨行用 // 得每行都写，或用 /* */。

3. 注释写在字符串里失效

std::cout << "价格 // 不是注释";  // 这里的 // 才是注释

字符串字面量里的 //、/* 都是普通字符，注释规则不生效。

动机：注释规则看着最无聊，却有三个真会坑人的地方

注释是全书最简单的一节，但它藏着 C/C++ 翻译阶段的顺序问题。值得较真的三个动机：

  1. 注释不是"被删除"，而是"被替换成一个空格"。这一条决定了 a/**/b 到底是一个 token 还是两个——写宏、写代码生成器时会踩。
  2. 行拼接（翻译阶段 2）发生在注释处理（阶段 3）之前。所以 // 末尾一个不起眼的反斜杠，会把下一行代码整个吃掉，而且编译器不报"注释错误"，只报"某个变量未声明"——错误信息离真凶很远。
  3. /* */ 不能嵌套导致"临时注释掉一大段代码"这个最常用的操作不可靠，必须用 #if 0。

底层实测：三个陷阱的复现与报错原文

全部在本机 clang 23.1.0 实测。

陷阱 ①：/* */ 不能嵌套——第一个 */ 就关掉整个注释

#include <iostream>
/* 外层注释开始
 * /* 内层注释开始 */
 * 外层注释还没结束
 */
int main() { std::cout << "ok\n"; return 0; }

实测报错：

nest.cpp:4:4: warning: '/*' within block comment [-Wcomment]
    4 |  * /* 内层注释开始 */
      |    ^
nest.cpp:5:4: error: a type specifier is required for all declarations
    5 |  * 外层注释还没结束
      |    ^
nest.cpp:5:28: error: expected ';' after top level declarator

注意报错位置：warning 在第 4 行（内层 /*），error 在第 5 行——因为第 4 行的 */ 已经把注释关掉了，第 5 行的 外层注释还没结束 变成了代码。而最后那个 */ 成了悬空符号。

安全做法：想整段禁用代码，用预处理指令，它不受注释规则限制：

#if 0
/* 这里的注释不会被误关闭 */
void old_code() { ... }
#endif

陷阱 ②：// 末尾的反斜杠会吃掉下一行

int main() {
    // 这行注释末尾有个反斜杠 \
    int x = 42;
    std::cout << "x=" << x << "\n";
    return 0;
}

实测：

c2.cpp:5:26: error: use of undeclared identifier 'x'
    5 |     std::cout << "x=" << x << "\n";

int x = 42; 整行被吃掉了。原因是 C/C++ 的翻译阶段顺序：

阶段 做什么
1 字符映射（trigraph 也在这一步，C++17 已移除）
2 行拼接：反斜杠 + 换行 → 删除
3 分解成 token，注释替换为一个空格
4 预处理（#include / #define）

拼接发生在注释处理之前，所以 // 后面的 \ 先把下一行拼了上来，然后整块被当注释扔掉。用 -E 看预处理结果最直观——那两行会变成空行。

陷阱 ③：注释是"一个空格"，不是"被删除"

int a = 1, b = 2;
int ab = a/**/b;        // 展开后是 `int ab = a b ;`

实测：error: expected ';' at end of declaration（^ 指向 a 后面）。a 和 b 没有粘成 ab——注释替换成的那个空格把它们分成了两个 token。

正面利用：字符串字面量的相邻拼接不受影响：

const char* s = "he"/*这句注释不影响*/"llo";   // → "hello"，sizeof == 6
int sum = a /*加号左*/ + /*加号右*/ b;        // → 3

陷阱 ④：??/ 三字符词（trigraph）——C++17 之前同样会吃掉下一行

// 注释末尾的 ??/ 在 C++11 下等于反斜杠 ??/
std::cout << "这行被吃了吗\n";
编译标准 运行结果
-std=c++11 什么都不输出（下一行被拼接进注释）
-std=c++17 输出 这行被吃了吗

??/ 是 trigraph，等价于 \。C++11/14 里它是语言的一部分；C++17 起 trigraph 已从标准移除，所以同一份代码在两个标准下行为不同。这种"换个 -std 就变语义"的东西，是跨项目移植时的暗雷。

HFT / 嵌入式视角

  1. #if 0 是唯一可靠的整段禁用手段。调试策略时临时注释掉一段下单逻辑，如果那段里有 /* 订单状态说明 */，用 /* */ 包会导致代码被"部分禁用"——编译能过、行为全错，比直接报错危险得多。团队规范里应写明：禁用代码一律 #if 0 ... #endif。
  2. 注释里的反斜杠要警惕。宏定义、多行日志字符串旁边写注释时，行尾不小心留个 \（比如从 Windows 拷过来的路径 C:\data\），会静默吃掉下一行。CI 里加 -Wall 之外的 -Wcomment（clang 默认开）能抓到嵌套 /*，但抓不到反斜杠续行——只能靠 review。
  3. 代码生成器 / 宏里别用注释分隔 token。写 #define CONCAT(a,b) a##b 这类宏或在模板代码里插注释时，记住注释是"空格"：a/**/b 不会变成 ab，但 "a"/*x*/"b" 会拼成 "ab"——字符串和标识符的规则不一样。
  4. 不要在代码里用 trigraph。C++17 已移除，但存量代码可能还有；新代码一律禁用，遇到 ?? 开头的怪序列先怀疑它。
  5. 注释不影响编译产物，但影响编译时间吗？ 不影响——注释在阶段 3 就被换成空格，预处理后的行数会保留（因为换行还在），但不产生 token。真正的编译时间大头是 #include（见 1.1 的 31 441 行实测）。

1.4

控制流

本节讲什么

介绍允许程序跳出顺序执行、实现更复杂执行路径的语句。详细讲解 while 循环（反复检测条件并执行循环体直至条件为假）、for 循环（将初始化、循环条件和变量修改集中在循环头以简化代码）以及支持条件执行的 if 语句。还演示了如何使用 while (std::cin >> value) 不断读取数量不定的输入，直至遇到文件末尾（EOF）。

要点

  • while：先判断条件，为真则重复执行循环体
  • for：循环头包含初始化、条件、迭代语句，适合计数循环
  • if / else：按条件选择执行路径
  • while (std::cin >> value)：循环读取输入，直至 EOF 或输入失败
  • Windows 下 EOF 常用 Ctrl+Z 后回车；Unix 下为 Ctrl+D
  • 条件表达式的规则（与 Rust 不同）：
  • if / while / for 的条件最终要当成布尔值来用
  • C++ 允许隐式转换：0 → 假，非 0 → 真
  • 所以 while (1) 合法，表示一直循环（1 永远为真）
  • Rust 则严格要求 bool，不能写 while 1
  • 现代 C++ 写死循环更推荐 while (true) 或 for (;;)，意图更清晰

和 C 的区别

几乎没有区别。 while/for/if 语法 C 和 C++ 完全一致。细微差异：

对比点 C C++ 说明
while (1) 死循环 ✅ ✅ 非 0 即真，C/C++ 都合法
for (int i=0; ...) 在循环外用 i ❌ 同样报错（C99 起） ❌ i 作用域只在 for 内 C99 起 C 和 C++ 行为一致；只有 C90 编译器当扩展放行（并告警）
条件必须是 bool ❌（整数即可） ❌（整数即可） C/C++ 都宽松，非 0 即真

for 变量的作用域（常见误解澄清）。 很多资料说"C 的 for 变量会泄漏到循环外，C++ 不会"——这句话只在 C90 成立。实测（clang 23.1.0）：

编译标准 for (int i=0;...){} 后在循环外用 i
C90（-std=c90） ⚠️ 仅 warning GCC does not allow variable declarations in for loop initializers before C99 [-Wgcc-compat]，放行，i 泄漏（实测 i=3）
C99（-std=c99） ❌ error: use of undeclared identifier 'i'
C11 / C17 ❌ 同上
C++（任意标准） ❌ 同上

也就是说：C99 起，C 和 C++ 在这一点上行为完全一致——for 初始化语句里声明的变量，作用域就是整个 for 语句（含循环体），出循环即销毁。

/* C99 代码 */
for (int i = 0; i < 3; i++) {}
printf("%d", i);   /* ❌ C99 也报错：use of undeclared identifier 'i' */

// C++ 代码
for (int i = 0; i < 3; i++) {}
std::cout << i;    // 编译错误：i 不在作用域内

记忆： 别再把"for 变量泄漏"当成 C/C++ 的差异——C99 之后两者一致。真正要注意的是：循环后还要用这个变量，就得提前声明。

int i = 0;
for (i = 0; i < 3; ++i) { /* ... */ }
std::cout << i;    // OK（C 和 C++ 都行）

通俗理解

  • while (1) = 死循环：1 永远是非 0，一直被当成「真」
  • HFT 行情监听：常用 while (1) 或 while (true) 做主循环，一直盯盘，满足条件时 break 退出
  • if / for 同样适用：只有 0 是假，其他整数都算真
while (1) {
    // poll_market();   // 拉行情
    // if (should_stop) break;  // 主动退出
}

示例

#include <iostream>
int main() {
    // while：累加 1 到 10
    int sum = 0, val = 1;
    while (val <= 10) {
        sum += val;
        ++val;
    }
    std::cout << "Sum 1..10 = " << sum << std::endl;

    // for：同样效果
    sum = 0;
    for (int i = 1; i <= 10; ++i)
        sum += i;
    std::cout << "Sum 1..10 = " << sum << std::endl;

    // if：按分数输出等级
    int score = 85;
    if (score >= 90)
        std::cout << "A" << std::endl;
    else if (score >= 60)
        std::cout << "Pass" << std::endl;
    else
        std::cout << "Fail" << std::endl;

    // while(1) 死循环（C++ 允许，1 当 true）
    // while (true) { /* 轮询行情 */ break; }  // 更推荐的写法

    return 0;
}

常见错误

1. while (std::cin >> value) 的结束条件搞混

int sum = 0, value = 0;
while (std::cin >> value)  // 什么时候停？
    sum += value;

结束条件：遇到 EOF（Windows Ctrl+Z 回车，Linux Ctrl+D），或输入类型不匹配（要 int 却输入字母）。cin >> value 的返回值是流本身，能转成 bool——读成功为真，失败为假。

2. for 变量在循环外误用（C 程序员的坑）

for (int i = 0; i < 10; ++i) { /* ... */ }
std::cout << i;  // 编译错误！C++ 里 i 已经销毁

C90（编译器扩展下）i 循环外可见，C99 起和 C++ 一样不可见。要循环后用，提前声明：

int i;
for (i = 0; i < 10; ++i) { /* ... */ }
std::cout << i;  // OK

3. if 悬空 else（经典陷阱）

if (a > 0)
    if (b > 0)
        std::cout << "A";
else
    std::cout << "B";  // 这个 else 配的是内层 if，不是外层！

else 总是配最近的未配对 if。要配外层，用花括号：

if (a > 0) {
    if (b > 0) std::cout << "A";
} else {
    std::cout << "B";  // 现在配外层
}

动机：控制流看着和 C 一模一样，真正的差别在"输入失败"上

while / for / if 的语法 C 程序员闭着眼都能写。这一节值得较真的是 while (std::cin >> value) 这个惯用法——它是 C 的 scanf(...) != EOF 的替代品，但语义比 scanf 丰富得多，也更容易被误用：

  1. 循环的终止条件不止 EOF。类型不匹配也会终止，而且终止后流会卡住，后续所有读取都失败——这是 C 程序员最容易懵的地方（scanf 失败后至少会跳过那个 token）。
  2. 失败后变量的值是有规则的，但规则分两种情况（实测见下），靠猜会猜错。
  3. 条件表达式的隐式转换决定了 while (1) 合法，也决定了 if (ptr)、if (flags & MASK) 这些写法在 C++ 里仍然成立——而 Rust/Java 会报错。

底层实测

全部在本机 clang 23.1.0 实测。

① for 变量作用域：C99 起 C 和 C++ 一致（见上方"和 C 的区别"已修正）

② cin >> v 失败后，v 到底是几？分两种情况

int sum = 0, v = -999;
while (std::cin >> v) sum += v;
// 循环结束后打印 v 和流的四个状态位
输入 sum 循环结束时 v good eof fail bad
1 2 3 x 6 0 0 0 1 0
1 2 3（直接 EOF） 6 3（保持原值） 0 1 1 0

为什么会不一样？ 关键在于失败发生在哪个阶段：

失败类型 sentry 阶段 num_get 阶段 v 的值
类型不匹配（读到 x） ✅ 成功 ❌ 失败 置 0（C++11 起标准规定）
纯 EOF ❌ 失败（eofbit 已置） 根本没执行 保持上一次的值

也就是说：只有 sentry 成功后提取才失败，v 才会被清零。纯 EOF 时 v 是"上一次读到的值"——如果你的代码在循环后还用 v，就会拿到一个看起来合法其实是过期数据的数字。

③ 流失败后不 clear()，后续读取全部失效

输入 x hello：

第一次读 int：fail=1
未 clear 直接读 string → 读取失败     ← 数据还在缓冲区，但流已经"锁死"
clear() 后再读 string   → 读到 "x"    ← 卡住的那个 token 被吐出来

这是 cin 与 scanf 最大的行为差异：scanf 失败后只是返回，下次调用还能继续读；cin 的 failbit 是粘滞的，不 clear() 就永远读不了。恢复流程是 clear() 清状态 + ignore() 丢掉坏数据。

④ 四种死循环写法：-O2 下汇编逐条相同

int sink;
void fn() { int i = 0; while (1)    { if (++i > 10) break; sink = i; } }
void fn() { int i = 0; while (true) { if (++i > 10) break; sink = i; } }
void fn() { int i = 0; for (;;)     { if (++i > 10) break; sink = i; } }
void fn() { int i = 0; for (;1;)    { if (++i > 10) break; sink = i; } }

四种写法在 -O2 下生成完全相同的 4 条指令：

mov  w8, #10
adrp x9, _sink@PAGE
str  w8, [x9, _sink@PAGEOFF]
ret

（循环被整个优化成 sink = 10。）所以 while(1) / while(true) / for(;;) 没有任何性能差别，选哪个纯粹是可读性问题。现代 C++ 推荐 while (true)（意图最清楚）或 for (;;)（最简短，for(;;) 里的空条件在 C 里也是惯用法）。

⑤ 悬空 else：-Wall 能抓到

if (a > 0)
    if (b > 0) r = 1;
else
    r = 2;          // ← 这个 else 属于【内层】if

clang -Wall 报：warning: add explicit braces to avoid dangling else [-Wdangling-else]。

实测行为（else 配内层 if）：

调用 结果 说明
f(1, 0) 2 外层真、内层假 → 走 else（很多人以为会是 0）
f(1, 1) 1 两层都真
f(-5, 0) 0 外层假，整个 if 跳过了

HFT / 嵌入式视角

  1. while (cin >> x) 只适合原型，不适合生产。它的失败处理是"悄悄停"，而且会把流锁死。生产代码要显式检查：if (!(in >> x)) { /* 记日志 + 决定是跳过还是中止 */ }。行情回放程序里，一条坏数据导致整个循环静默结束 = 少回放大半天行情。
  2. 循环后别用循环变量的值。实测 EOF 情形下 v 是"上一次的值"——while (cin >> price) {...} 之后用 price 做最后一笔的结算，会拿到过期价格。要么在循环体内处理完整，要么显式初始化一个 last_valid。
  3. failbit 粘滞是嵌入式串口/日志解析的常见坑。按行解析配置/报文时，一次解析失败会让后续全部失败；正确姿势是 clear() + ignore(n, '\n') 跳过坏行再继续。
  4. 死循环写法统一用 while (true)。汇编一样，但审阅时能一眼看出"这是故意的死循环"，而不是"while(1) 是不是写错了"。HFT 主循环、嵌入式 super-loop 都是这个形态，可读性直接关系排障速度。
  5. 条件里的隐式转换要显式化。if (ptr) 在 C++ 里合法，但 if (flags & MASK) 这类写法在重构时极易改错优先级。写 if (ptr != nullptr) / if ((flags & MASK) != 0)，编译器不会因为你写得更啰嗦而生成更差的代码（实测汇编一致）。

本节讲什么

核心概念

概念 例子 说明
定义对象 Sales_item item; 创建一个"盒子"
调成员函数 item.isbn() 用 . 取对象里的方法/数据
运算符操作 cin >> item / item + item2 类可以重载运算符

和 C 的区别（这是重点）

这是 C 转 C++ 的第一个大门槛：

对比点 C C++
自定义类型 struct 只装数据 class/struct 装数据 + 函数
调"方法" 函数传结构体指针：isbn(&item) 对象直接调：item.isbn()
访问控制 无（全公开） public/private 控制可见性
运算符 不能让 + 作用于自定义类型 重载 + 后 item + item2 合法

一句话： C 的 struct 是"数据包"，C++ 的 class 是"数据包 + 工具包"——数据和行为绑在一起，还能控制谁能碰。

/* C 写法：数据归数据，函数归函数 */
struct Book { char isbn[16]; int sold; double revenue; };
char* get_isbn(struct Book* b) { return b->isbn; }  // 函数操作结构体

// C++ 写法：数据和函数绑在一起
class Sales_item {
public:
    std::string isbn() const { return bookNo; }  // 方法内嵌在类里
private:
    std::string bookNo;
};
Sales_item item;
item.isbn();  // 对象.方法()，不用传 this

动机：为什么 C++ 要把函数塞进 struct 里

C 程序员的第一反应是"把函数放进结构体有什么用？不过是 isbn(&item) 换成 item.isbn() 的语法糖"。如果只是语法糖，不值得发明一整个语言。真正的动机是三条：

  1. 不变式（invariant）可以被强制。C 的 struct 全公开，任何人都能 order.price = -100；C++ 用 private 把字段藏起来，只暴露 set_price()——校验逻辑写在类里，没人能绕过。这是 C++ 相对 C 最本质的增值，语法糖只是附赠。
  2. 名字不污染全局。isbn() 在类里，就不会和别人的 isbn() 撞；C 里得靠 sales_item_isbn() 这种前缀约定。
  3. 接口和实现可以分离。public 部分是契约，private 部分可以随便改而不影响调用方（1.5.1 详讲）。

关键认知：item.isbn() 在机器层面确实就是 isbn(&item)——下面用汇编证明。所以"面向对象"在这里零运行时开销，你买的单只是编译期的组织方式，不是运行时的跳转表。

底层实测：item.isbn() 真的等于 isbn(&item) 吗

全部在本机 clang 23.1.0 / arm64 实测。

① 汇编级证明：成员函数 = 普通函数 + 隐式 this 参数

struct Box { long a, b, c; };

// C 风格：显式传指针
long free_sum(const Box* p) { return p->a + p->b + p->c; }

// C++ 风格：成员函数
struct BoxCxx {
    long a, b, c;
    long sum() const { return a + b + c; }
};
long call_member(const BoxCxx* p) { return p->sum(); }

clang++ -std=c++17 -O1 -S 后对比两个函数体：

; free_sum(const Box*)          ; call_member(const BoxCxx*)  ← 成员函数已内联进来
    ldp  x8, x9, [x0]               ldp  x8, x9, [x0]
    ldr  x10, [x0, #16]             ldr  x10, [x0, #16]
    add  x8, x9, x8                 add  x8, x9, x8
    add  x0, x8, x10                add  x0, x8, x10
    ret                             ret

逐条指令完全相同。diff 结果为空。唯一的差别是符号名：

写法 mangled name c++filt 还原
自由函数 _Z8free_sumPK3Box free_sum(Box const*)
成员函数 _ZNK3Box3sumEv Box::sum() const

注意成员函数 mangled name 里的 K（const）和结尾的 v（void 参数列表）——this 不出现在参数列表里，它是隐式的，但 name mangling 把 const 也编进去了，因为 const 成员函数和同名非 const 成员函数是两个不同的重载。

② this 就是对象的地址

Tick t{10.5, 100};
std::cout << &t << "\n" << t.me() << "\n";   // me() 里 return this;

实测输出：

  &t     = 0x16d89ac40
  t.me() = 0x16d89ac40
  this == &t ? 是

所以 this 不是"指向某个隐藏结构的指针"，就是 &对象 本身，通过 x0（arm64 第一个参数寄存器）传进去——和 isbn(&item) 里传 &item 完全一样。

③ 成员函数不占对象空间

类型 内容 sizeof
struct Empty { } 空类 1
struct DataOnly { double px; int qty; } 只有 2 个字段 16
struct WithMethods { 同上 + 3 个方法 } 字段 + 方法 16（不变）
struct WithVirtual { 同上 + 虚函数 } 字段 + 虚析构 24

三点结论： - 非虚成员函数零空间开销——加 3 个方法 sizeof 不变，因为方法不在对象里，它们在代码段，靠 this 找到数据。 - 空类是 1 字节不是 0——保证 &a != &b（两个不同对象必须有不同地址），否则数组、指针算术都会崩。 - 虚函数才加开销：arm64 上多 8 字节的 vptr（虚表指针）。所以"面向对象 = 慢"这句话只对虚函数成立，对普通成员函数完全不成立。

④ class vs struct：只有默认访问权限不同

class struct
默认成员访问 private public
默认继承方式 private public
其它（能有方法、能继承、能多态） 完全相同 完全相同

C 程序员用 struct 完全没问题（而且默认 public 更贴近 C 的直觉）；约定俗成是：纯数据用 struct，有不变式要维护的用 class。

HFT / 嵌入式视角

  1. 成员函数零开销，可以放心用。在行情回调里写 tick.mid() 而不是 mid(&tick)，汇编完全一致，但可读性和不变式保护是白赚的。不要为了"性能"把 C++ 写成带类的 C。
  2. private 是不变式的唯一强制执行点。订单的 price 必须 > 0、qty 必须 ≤ 上限——这些约束写在 set_price() 里，外部绕不过去。C 里只能靠"约定 + review"，而约定在 6 个月后的夜班改代码时一定会破。
  3. 谨慎对待虚函数。vptr 让对象从 16 字节变 24 字节（+50%），在 L1 cache 里塞行情快照时这是真金白银；而且虚调用是一次间接跳转，分支预测失败一次约 15~20 ns——对纳秒级策略是可见的。策略多态尽量用模板（编译期）或 if constexpr，把虚函数留给真正需要运行期动态分派的场合（如插件式风控）。
  4. 空类 1 字节在嵌入式上会累积。struct Tag {}; 作为成员嵌进别的结构体，会因为对齐被放大（比如嵌进 8 字节对齐的结构体，可能占 8 字节）。确认真的不需要区分身份时，用 [[no_unique_address]]（C++20）或干脆别定义空类。
  5. this 存在的意义：解释了为什么成员函数里可以直接写 px（等价于 this->px），也解释了为什么静态成员函数里不能写——静态成员函数没有 this。

  2. 错。class 和 struct 在 C++ 里唯一的区别是默认访问权限（class 默认 private，struct 默认 public）和默认继承方式。struct 一样可以有成员函数、构造/析构、继承、虚函数。约定是：纯数据用 struct，有不变式要维护的用 class。

  3. C 写法（靠约定）： c struct Order { double price; int qty; }; /* 文档写：调用前必须校验！但没人强制执行 */ C++ 写法（靠编译器强制执行）： cpp class Order { public: bool set_price(double p) { if (p <= 0) return false; price_ = p; return true; } bool set_qty(int q) { if (q > 10000) return false; qty_ = q; return true; } double price() const { return price_; } int qty() const { return qty_; } private: double price_ = 0; // 外部写不到 int qty_ = 0; }; 关键差别：C 里 order.price = -1; 是合法代码，只能靠 review 发现；C++ 里 order.price_ = -1; 是编译错误，物理上不可绕过。不变式从"约定"升级成"编译期保证"，这是 class 相对 struct 的本质增值——而运行时开销为零（成员函数与普通函数汇编一致）。

可跑例子

clang++ -std=c++17 -O2 -Wall 1.5-1-class-basics.cpp -o cls && ./cls
clang++ -std=c++17 -O1 -S 1.5-1-class-basics.cpp -o cls.s   # 汇编级证明

.1 类的使用与头文件分离

第 1 章 · 上一节：1.5 类简介 · 下一节：1.5.2 链接、编译产物与示例

本节讲什么

Sales_item 的用法，以及类的声明（.h）和实现（.cpp）为什么要分开写。

通俗理解：数据盒子 + 工具包

把 class 想成一个定制的「数据盒子 + 工具包」：

Sales_item（书） 以后 HFT 里的 Order（单）
盒子里：书号、销量、收入 盒子里：委托价、数量、订单号
工具：isbn() 取书号 工具：send() 发单、cancel() 撤单
>> 读一条销售记录 从网关读入一笔委托
+ 合并两笔销售 合并/汇总订单

不用自己拆盒子找数据——定义好对象后，用 . 调方法就行，比零散传一堆参数清晰。

Sales_item 是入门的「友好型例子」：先学会怎么用盒子，后面章节再学怎么造盒子。

头文件与实现文件

类不必全写在头文件里。常见做法是分开写：

文件 放什么 作用
Sales_item.h 类的声明（有哪些方法、长什么样） 给别人看「怎么调用」
Sales_item.cpp 方法的具体实现（函数体里怎么写） 藏实现细节，减少重复编译

HFT 项目里常把核心策略实现藏在 .cpp 或静态库/动态库里，对外只暴露头文件接口——既保护代码，又不影响别人调用。

和 C 的区别

C 程序员对 .h/.c 分工不陌生，但 C++ 的类让分工更彻底：

对比点 C C++
头文件放什么 函数声明、struct 定义 类声明（数据+函数原型）
实现文件放什么 函数定义 类的成员函数定义（要写 Class::method）
数据与函数 分离（struct 和函数各自声明） 绑定（都在类里）
访问控制 无，谁都能改 struct 字段 private 藏起来，只能通过方法改 
/* C：数据和函数分离 */
/* book.h */
struct Book { char isbn[16]; int sold; };
char* get_isbn(struct Book* b);   /* 函数声明，和 struct 没绑定关系 */

/* book.c */
char* get_isbn(struct Book* b) { return b->isbn; }

// C++：数据和方法绑定，还能控制访问
// Sales_item.h
class Sales_item {
public:                          // 外部能调的
    std::string isbn() const;
private:                         // 外部碰不到的
    std::string bookNo;
};

// Sales_item.cpp
std::string Sales_item::isbn() const { return bookNo; }  // 要带 Class::

关键： C++ 的成员函数定义在 .cpp 里要写 Sales_item::isbn()，这个 Class:: 前缀告诉编译器"这是类的成员函数"。C 没有这个概念。

常见错误

1. .cpp 里忘写 Class:: 前缀

// Sales_item.cpp
std::string isbn() const { return bookNo; }  // 错：编译器以为是普通函数

报错：bookNo 未声明。要写成 std::string Sales_item::isbn() const { ... }。

2. 头文件里直接写函数体（可能多重定义）

// Sales_item.h
class Sales_item {
public:
    std::string isbn() const { return bookNo; }  // 类内定义，隐式 inline
};

类内直接给函数体是合法的（隐式 inline），但如果这个头文件被多个 .cpp 包含，每个都生成一份定义——inline 函数允许这样。非 inline 的成员函数定义放头文件会链接报错（重复定义）。 安全做法：声明放 .h，定义放 .cpp。

3. private 成员外部直接访问

Sales_item item;
item.bookNo = "123";  // 编译错误：bookNo 是 private

private 就是"外面碰不到"，只能通过 public 方法间接操作。这是 C++ 相对 C 的核心保护机制。

动机：.h / .cpp 分开不只是"整洁"，是三条硬约束

C 程序员对 .h / .c 的分工不陌生，但 C++ 里这件事的约束力更强，因为有三个 C 里没有（或弱得多）的硬约束：

  1. ODR（单一定义规则）：一个非 inline 函数在整个程序里只能有一份定义。C 里重复定义是"常见符号"问题，链接器有时还能容忍；C++ 的 name mangling + 模板让重复定义几乎必然炸，且报错信息难读。
  2. 编译单元是独立编译的。每个 .cpp 单独编译、互不知情——头文件是它们之间唯一的"共同上下文"。头文件里写了什么，决定了所有使用者的编译结果和编译时间。
  3. 头文件是接口契约。public 部分就是给别人看的 API 文档；.cpp 可以随便改而不触发使用者的重新编译（这是大型项目能增量构建的基础）。

一句话动机： 头文件放"叫什么、长什么样"，实现文件放"怎么做"。违反这条，代价是链接错误、编译时间爆炸、接口和实现耦死。

底层实测：ODR 违规长什么样

全部在本机 clang 23.1.0 实测。

① 非 inline 的函数定义放头文件 → 链接期炸

// bad.h
#pragma once
int add_bad(int a, int b) { return a + b; }   // ← 定义（不是声明！）

// u1.cpp
#include "bad.h"
int use1() { return add_bad(1, 2); }

// u2.cpp
#include "bad.h"
int use2() { return add_bad(3, 4); }

clang++ -c u1.cpp -o u1.o ; clang++ -c u2.cpp -o u2.o
clang++ u1.o u2.o main.o -o app

实测报错：

duplicate symbol 'add_bad(int, int)' in:
    u1.o
    u2.o
ld: 1 duplicate symbol for architecture arm64
clang++: error: linker command failed with exit code 1

注意：#pragma once 只能防止同一个 .cpp 里重复包含，挡不住两个 .cpp 各生成一份。这是新手最常误解的一点——guard 解决的是"重复声明"，ODR 解决的是"重复定义"，两回事。

② 用 nm 看符号类型：external vs weak external

写法 nm -m 输出
非 inline 0000000000000000 (__TEXT,__text) external __Z7add_badii
inline 000000000000001c (__TEXT,__text) **weak** external __Z6add_okii

差别就在 weak：弱符号允许在多个目标文件里各有一份，链接器任选其一（配合 COMDAT 保证内容一致时不冲突）。inline 之所以能放进头文件，本质上就是它生成的是弱符号。

③ 三种"可以放头文件"的写法，都实测通过

写法 例子 链接结果
显式 inline inline int add_ok(int a, int b) { ... } ✅ 实测输出 10
类内定义（隐式 inline） struct Adder { int sum() const { ... } }; ✅ 实测输出 10
inline 变量（C++17） inline int g_counter = 0; ✅
只有声明 int price_of(int qty);（定义在 .cpp） ✅

反向：非 inline 的变量定义放头文件同样炸：

// var.h
int g_counter = 0;    // 每个 .cpp 都生成一个

duplicate symbol '_g_counter' in:
    w1.o
    w2.o

C++17 之前的正确写法是头文件里 extern int g_counter;，然后在某一个 .cpp 里定义。

④ 缺 include guard → 编译期炸（和 ODR 是不同的错）

// noguard.h
struct Node { int v; };

// ng.cpp
#include "noguard.h"
#include "noguard.h"     // 同一个 TU 里包含两次

error: redefinition of 'Node'

这是编译期错误（同一个翻译单元里类型重复定义），和 ① 的链接期 duplicate symbol 是两种病。防护手段：#pragma once（简单，主流编译器都支持）或传统的 #ifndef XXX_H / #define XXX_H / #endif（可移植性最好）。

⑤ 声明/实现分离的真实收益：增量编译

实测（2 个使用者，改一次实现）：

实现放在 需要重编的文件 实测耗时
.cpp 1 个（impl.cpp） 0.05 s
.h 2 个（userA.cpp + userB.cpp） 0.05 s + 0.05 s

使用者是 N 个，就是 N 倍。这就是为什么"实现藏进 .cpp"不只是洁癖——它是构建时间的可伸缩性。HFT 项目几千个文件，头文件改一行触发全量重编，一次就是几十分钟。

⑥ 漏写 Class:: 的报错

// Sales_item.cpp
std::string isbn() const { return bookNo; }     // ← 漏了 Sales_item::

编译器会把它当成自由函数，于是 bookNo 不在作用域 → 报"未声明"。而带 const 的自由函数还会额外报"非成员函数不能有 const 限定"。正确写法：

std::string Sales_item::isbn() const { return bookNo; }

HFT / 嵌入式视角

  1. 对外只暴露头文件是常态。核心策略实现编译成静态库/动态库，客户端只拿到 .h + .a——既保护知识产权，又能精确控制 ABI。这时头文件里的每一行都是契约：改一个字段顺序、加一个虚函数，都可能破坏 ABI（尤其是虚函数表布局）。
  2. 头文件里别放"会变的东西"。策略参数、阈值常量如果写在头文件里，改一次就全量重编；应该走配置加载（运行时读 JSON/二进制），头文件里只放读取接口。
  3. inline 是把双刃剑。它让函数能进头文件（解决 ODR），但会让每个调用点都展开一份代码——在 Flash 只有几百 KB 的 MCU 上，滥用 inline 会让固件体积失控。规则：1–3 行的访问器 inline，复杂逻辑放 .cpp。
  4. #pragma once vs #ifndef guard：跨平台项目用 #ifndef（#pragma once 在符号链接/同一文件多路径包含时可能失效）；只跑 clang/gcc 的项目用 #pragma once 更不容易写错（不会出现 guard 宏名撞车）。
  5. 减少头文件依赖 = 减少编译时间。能用前置声明（class Order;）解决的，就别 #include "Order.h"。配合 pimpl（第 7 章）可以把实现改动完全隔离在 .cpp 里。
  6. nm 是排查链接问题的第一工具。遇到 duplicate symbol / undefined symbol，先 nm -m xxx.o | grep 符号 看它是 external、weak external 还是 undefined，比读一屏模板报错快得多。

自测题

1（选择） 成员函数的定义应该放在哪里？ - A. 只能放 .h - B. 只能放 .cpp - C. 声明放 .h，定义放 .cpp（推荐）；类内定义的隐式 inline 可放 .h

2（踩坑） 下面代码错在哪？

// Sales_item.cpp
std::string isbn() const { return bookNo; }

3（概念） 为什么 C++ 要分 public/private？C 的 struct 没有这个，会带来什么问题？

参考答案
  1. C。声明（告诉编译器"有这个函数"）放 .h，定义（具体实现）放 .cpp。类内直接写函数体算隐式 inline，也可放 .h，但不推荐复杂逻辑这样做。
  2. 缺 Sales_item:: 前缀。编译器会把它当普通自由函数，bookNo 就找不到（不在作用域）。正确写法：std::string Sales_item::isbn() const { return bookNo; }。
  3. private 把内部数据藏起来，外部只能通过 public 方法操作——这样类的作者能控制"怎么改才安全"（比如 set_price 里校验非负）。C 的 struct 全公开，任何人都能直接改字段，容易破坏不变式（比如把价格设成负数）。

4（踩坑·高价值） 头文件已经加了 #pragma once，为什么两个 .cpp 都包含它还是链接报错 duplicate symbol？

// util.h
#pragma once
int helper(int x) { return x * 2; }     // ← 定义

5（判断） #pragma once（或 include guard）能解决"同一个头文件被两个不同 .cpp 包含导致的重复定义"问题。

6（应用） 项目里有 50 个 .cpp 都 #include "strategy.h"，你改动了策略的一处实现。实现写在 .h 和实现写在 .cpp，构建时间差多少？怎么改最划算？

参考答案

  1. 因为 #pragma once 只保证同一个翻译单元（.cpp）里这个头文件的内容只出现一次，它管不了别的 .cpp。两个 .cpp 各自编译、各生成一份 helper 的非 inline 定义（强符号），链接时就是 duplicate symbol。实测报错： duplicate symbol 'helper(int)' in: u1.o / u2.o ld: 1 duplicate symbol for architecture arm64 两种修法：① 改成 inline int helper(int x) { ... }（生成弱符号，允许重复）；② 头文件里只放 声明 int helper(int);，定义挪到某个 .cpp。

  2. 错。这正是第 4 题的陷阱。include guard 解决的是"同一个 TU 内重复包含 → redefinition"（编译期错误，实测 error: redefinition of 'Node'）；而"两个 TU 各生成一份定义 → duplicate symbol"是链接期的 ODR 问题，guard 完全无能为力。两件事，别混。

  3. 实测（2 个使用者）：实现放 .cpp 只需重编 1 个文件 0.05 s；实现放 .h 要重编 2 个文件 0.05 + 0.05 s。50 个使用者就是 1 个文件 vs 50 个文件，差距是 50 倍量级。最划算的改法： - 把实现挪进 strategy.cpp，strategy.h 只留声明和类定义 → 立即从 50 降到 1； - 顺手减少头文件依赖：能用前置声明 class Foo; 的，就别 #include "foo.h"； - 如果连类的私有成员改动都不想触发重编，用 pimpl（第 7 章）：头文件里只有一个指针成员。 注意别矫枉过正——inline 能让小函数留在头文件并获得内联优化，1–3 行的访问器留在 .h 是合理的；复杂逻辑才挪走。

1.5

.2 链接、编译产物与示例

本节讲什么

编译链接流程、.o/.exe/.lib、示例代码。

链接：编译器怎么找到实现？

main.cpp  #include "Sales_item.h"
    ↓ 编译：编译器从头文件知道 isbn() 存在 → 能通过编译
    ↓
Sales_item.cpp  → 单独编译成目标文件
    ↓ 链接：把 item.isbn() 的调用点和 .cpp 里的实现「绑」在一起
    ↓
可执行文件 → 运行时正确执行 isbn() 里的代码

你在 main 里写 item.isbn() 时： 1. 编译阶段：只看 .h，确认 isbn() 名字、参数对得上就行 2. 链接阶段：去 .cpp 编译出的模块里找到 isbn() 的真正代码并接上

所以：头文件给编译器看，实现文件给链接器接。

编译产物：从 .cpp 到「成品」

GCC、Clang、MSVC、TCC 等编译器做的事一样：把人写的代码翻译成机器码。步骤拆开看：

Sales_item.cpp  ──编译──►  Sales_item.o     （目标文件：机器码，还不能单独跑）
main.cpp        ──编译──►  main.o
                              │
                              ▼ 链接（把 .o 和库绑在一起）
                         ┌────┴────┐
                         ▼         ▼
                    book.exe    libSales.a / Sales.dll
                  （可执行程序）  （给别人用的库）
产物 常见后缀 是什么 给谁用
目标文件 .o / .obj 单个 .cpp 编译出的机器码片段 链接器内部用，一般不单独给别人
可执行文件 .exe（Windows）/ 无后缀（Linux） 能直接运行的完整程序 终端用户双击/命令行运行
静态库 .lib（MSVC）/ .a（GCC/Clang） 实现代码打包进库，链接时拷进你的程序 开发者在自己的项目里链接
动态库 .dll（Windows）/ .so（Linux） 实现代码在单独文件里，运行时加载 开发者链接 + 运行时带上 dll

给别人当「模块」调用，给什么？

不是 .exe + .h。

  • .exe：成品程序，给用户运行的，不能当 SDK 让别人链接。
  • 给别人调用你的类/函数，应提供：
场景 给别人什么
静态库 .h + .lib（或 .a）
动态库 .h + .lib（导入库）+ .dll（运行时要有）

对方在自己的项目里 #include "Sales_item.h"，链接你的 .lib，就能调 isbn() 等方法，全程看不到你的 .cpp 源码。

Windows 上记一句

想让别人「调用你的模块」  →  .h + .lib（+ .dll）
想让别人「直接跑你的程序」  →  .exe（一般不需要给 .h）

HFT 里核心策略/行情解析常做成 静态库或动态库 + 头文件，交易主程序只链接接口，实现藏在二进制里。

静态链接 vs 动态链接：工程上怎么选

上一张表只回答了"有哪几种产物"，真正的工程问题是链哪一种。下面全是实测数据（Pi 5 / Debian 13 / gcc 14.2 / g++ -std=c++17）。

一张表定选择

维度 静态链接（.a） 动态链接（.so）
代码何时合并 编译链接期，拷进产物 运行期，操作系统加载
产物大小 大 小
运行时依赖 无，自带 必须有 .so
升级库 重新编译链接整个项目 替换 .so 即可（ABI 兼容前提）
内存占用 每个程序一份副本 多进程共享同一份物理页
找不到库的报错 链接期 undefined reference 运行期 cannot open shared object file

体积实测（同样是 hello world）：

程序 动态 全静态 -static
C（printf） 70,440 B 704,944 B（约 10 倍）
C++（std::string + cout） 74,160 B 2,251,248 B（约 30 倍）

C++ 静态化的代价远大于 C——多出来的是 C++ 运行时（异常、RTTI、静态初始化）。

澄清一个常见误解：「静态链接会把整个 libc 打包进去」

结论对，机制描述错。.a 是 .o 的归档包，链接器只抽出能补齐当前未定义符号的那些成员：

# 实测：.a 里塞两个 .o，其中 unused.o 里的函数没人调用
ar rcs libadd.a mylib.o unused.o
gcc main.c -L. -ladd -o app
nm app | grep -c never_called      # → 0，根本没进产物

之所以 -static 仍然让体积暴涨，是因为 libc 的间接依赖（locale、iconv 等）被连带拉了进来，不是因为"整包拷贝"。面试时说"按需抽取 + 连带依赖"，比说"整个塞进去"更准确。

C++ 的常用折中：-static-libstdc++

C++ 全静态要 2.25 MB，工程上更常见的是只静态链 C++ 运行时，libc 保持动态：

g++ -std=c++17 hi.cpp -o app -static-libstdc++
ldd app | grep libstdc++          # → 空，libstdc++ 已不在依赖里

实测体积 1,537,168 B（比全静态的 2,251,248 B 小），而且目标机器不需要装版本匹配的 libstdc++.so.6，跨发行版分发时这一句很实用。

第三种方式：运行期手动加载 dlopen（插件化）

普通动态链接是「程序一启动 OS 自动加载 .so」；dlopen 是「运行到你这行代码才加载」：

void* h = dlopen("./libplugin.so", RTLD_LAZY);          // 打开
auto add = (int(*)(int, int))dlsym(h, "add");            // 取函数地址
printf("%d\n", add(3, 4));
dlclose(h);                                              // 卸载

g++ -std=c++17 -fPIC -shared -o libplugin.so plugin.cpp  # 插件必须 -fPIC -shared
g++ -std=c++17 host.cpp -o host -ldl                     # 主程序必须 -ldl

与主程序的链接期毫无关系——ldd host 里查不到插件。机器人上位机的插件、相机/雷达驱动模块、Qt 插件都是这个模式。

⚠ C++ 用 dlopen 必踩的坑：name mangling

C 里 dlsym(h, "add") 直接拿到；C++ 里符号名被改编了。实测：

nm -D libplugin.so | grep -E "add|mul"
  0000000000000588 T add        ← extern "C" 声明的，名字没变
  00000000000005a8 T _Z3mulii   ← 普通 C++ 函数，名字被改编

dlsym("add")  = 成功
dlsym("mul")  = 失败            ← 拿不到，返回 NULL

所以插件导出的接口必须包 extern "C"，否则 dlsym 拿空指针（1.5.2 下面「和 C 的区别」那节讲过 name mangling，这里是它在 dlopen 上的直接后果）：

extern "C" int add(int a, int b) { return a + b; }   // 插件接口的标准写法

⚠ 还有一个 C 没有的坑：C++ 动态库的 ABI

C 的 .so 只要函数签名一致就能换；C++ 远没这么轻松：

风险点 说明
std::string 有两套 ABI gcc 5 起新旧 ABI 由 _GLIBCXX_USE_CXX11_ABI 控制，库和主程序不一致就崩
STL 容器跨 .so 边界 不要在接口上传 std::string / std::vector——编译器版本一变，成员布局就可能对不上
异常 / RTTI 跨边界 跨 .so throw 需要两边运行时一致
接口建议 对外接口用 C 风格（const char*、定长 POD 结构体），内部随便用 C++

这也是很多 C++ SDK 只肯发静态库，或者把对外接口做成 C API 的原因——"换个 .so 就行"在 C++ 里是有条件的。

想往深里挖，这个主题在另外两条线上有更完整的展开： - 工具链视角（含 Windows 上 .lib 有两种身份、导入库）：01.7 1.2 四件套解剖 - C 侧深水区（链接过程、GOT/PLT 延迟绑定、SONAME 版本管理、循环依赖、符号介入）： 6.13 链接静态库 · 6.14 动态链接 · 6.15 插件的工作原理

和 C 的区别

编译链接流程 C 和 C++ 基本一样，但有几个 C++ 特有的坑：

对比点 C C++
编译产物 .o / .exe / .a / .so 完全一样
函数符号名 就是函数名（isbn） 名字改编（_ZN10Sales_item4isbnEv）
混合编程 — C++ 调 C 要 extern "C"
头文件守卫 #ifndef 守卫 #ifndef 或 #pragma once

名字改编（name mangling）： C++ 支持重载（同名函数不同参数），编译器要把参数信息编进符号名才能区分。所以 Sales_item::isbn() 在 .o 里不叫 isbn，而是一串带类名和参数的符号。

extern "C" 的用途： C 的符号名就是函数名（不改编）。C++ 要调 C 的库，得告诉编译器"这个函数按 C 规则找符号"：

extern "C" {
    #include "some_c_library.h"   // 按 C 规则链接，不做名字改编
}

HFT 里常碰：行情网关是 C 写的，C++ 策略层调它就要 extern "C"。

常见错误

1. 头文件循环包含 / 重复包含

// a.h 包含 b.h，b.h 又包含 a.h → 死循环

用头文件守卫：

#ifndef SALES_ITEM_H
#define SALES_ITEM_H
// ... 类声明
#endif

或更简洁的 #pragma once（主流编译器都支持）。

2. 链接时找不到实现（undefined reference）

undefined reference to `Sales_item::isbn() const'

原因：.cpp 没参与编译，或忘写 Sales_item:: 前缀，或实现和声明签名不一致。检查 g++ main.cpp Sales_item.cpp（两个都要列上）。

3. C++ 调 C 库忘加 extern "C"

#include "c_lib.h"           // C 头文件
c_function();                // 链接报错：找不到 _Z11c_functionv

C++ 默认按改编后的名字找，但 C 库里是原名。要 extern "C" { #include "c_lib.h" }。

4. 插件的 dlsym 拿不到函数（返回 NULL）

int (*f)(int,int) = (int(*)(int,int))dlsym(h, "mul");   // → NULL

原因：C++ 函数符号被改编成 _Z3mulii，dlsym("mul") 自然找不到。修正：插件导出接口用 extern "C" 声明，编译后 nm -D libplugin.so 看到的必须是原名 mul 而不是 _Z3mulii。

5. 升级 .so 后程序在 std::string 上崩溃

// 库接口：void set_name(std::string s);   ← 危险

原因：C++ 没有稳定的 ABI，std::string/std::vector 的成员布局随编译器版本和 _GLIBCXX_USE_CXX11_ABI 变化。库换了编译器版本，主程序没重编 → 布局对不上 → 崩。修正：接口改成 C 风格（const char* / 定长结构体 + 长度），或整体重新编译。

1.6

书店程序

第 1 章 · 上一节：1.5 类简介 · 下一节：1.7 小结与术语表

本节讲什么

全章实战总结：把变量、输入输出、控制流、Sales_item 类串起来，写一个完整程序——读多条书籍销售记录，按书号分组汇总，输出每本书的总销售额、售出册数、平均售价。

核心逻辑

程序的结构是"分组累加"模式，HFT 里也常见（按合约分组统计成交量）：

  1. 读第一条记录作为"当前组"
  2. 循环读后续记录： - 书号相同 → 累加到当前组 - 书号不同 → 输出当前组汇总，开启新组
  3. 循环结束 → 输出最后一组

示例

#include <iostream>
#include "Sales_item.h"

int main() {
    Sales_item total;
    if (std::cin >> total) {               // 读入第一条记录
        Sales_item trans;
        while (std::cin >> trans) {        // 读入剩余记录
            if (total.isbn() == trans.isbn())
                total += trans;            // 同一本书，累加
            else {
                std::cout << total << std::endl;  // 不同书，输出上一本汇总
                total = trans;             // total 重置为新书
            }
        }
        std::cout << total << std::endl;   // 输出最后一本
    }
    return 0;
}

和 C 的区别

同样的"分组累加"逻辑，C 和 C++ 的写法对比：

对比点 C 写法 C++ 写法
读记录 scanf("%s %d %lf", isbn, &sold, &price) cin >> total（一行搞定）
比较 strcmp(isbn1, isbn2) == 0 total.isbn() == trans.isbn()
累加 手动加每个字段 total += trans（运算符重载）
输出 printf("%s %d %.2f\n", ...) cout << total 
/* C 版本骨架 */
struct Record { char isbn[16]; int sold; double revenue; };
struct Record total, trans;
scanf("%s %d %lf", total.isbn, &total.sold, &total.revenue);
while (scanf("%s %d %lf", trans.isbn, &trans.sold, &trans.revenue) == 3) {
    if (strcmp(total.isbn, trans.isbn) == 0) {
        total.sold += trans.sold;
        total.revenue += trans.revenue;
    } else {
        printf("%s %d %.2f\n", total.isbn, total.sold, total.revenue);
        total = trans;
    }
}

关键差异： C++ 把"怎么读、怎么加、怎么比"藏进了类的方法和运算符重载里，主程序逻辑干净得多。C 要手动操作每个字段，容易写错（忘加某个字段、格式串写错）。

常见错误

1. 忘了处理"没有输入"的情况

Sales_item total;
std::cin >> total;        // 如果没输入，下面 total 是未定义状态
while (std::cin >> trans) { ... }  // 直接进循环，行为未定义

原书代码用 if (std::cin >> total) 先判断第一条是否读成功，这是正确的防御性写法。

2. 换组时忘了重置 total

if (total.isbn() == trans.isbn())
    total += trans;
else {
    std::cout << total << std::endl;
    // 忘了 total = trans; → 下一组还是累加在旧 total 上
}

3. 输入没按书号排序 程序假设输入是按书号排好序的（同一本书的记录连续）。如果输入乱序，0-201 0-201 0-999 0-201 里的最后一个 0-201 会被当成新书，无法合并到前面的组。要处理乱序需要更复杂的数据结构（map），第 10 章会讲。

动机："分组累加"是一个会反复出现的模式

书店程序看着只是第 1 章的综合练习，但它承载的"流式分组累加"模式在真实系统里到处都是：

书店程序 HFT 对应 嵌入式/日志对应
按 isbn 分组 按 symbol 聚合成交量 按设备 ID 汇总采样值
输入按书号有序 行情网关按合约分流后天然有序 日志按时间/来源有序
total += trans 累加成交金额 累加计数/求和
换书时输出上一本 换合约时落盘上一组合计 换设备时上报

这个模式的价值：O(n) 时间、O(1) 额外内存（不需要把所有组都留在内存里），可以处理远大于内存的数据流。代价是要求输入按 key 有序——理解这个前提，才知道什么时候该换成 map。

底层实测

全部在本机 clang 23.1.0 实测（例子 1.6-1-bookstore.cpp 可直接跑）。

① 三种输入的实测输出

有序输入（正常路径）：

$ printf '0-201-78345-X 3 20.00\n0-201-78345-X 2 25.00\n0-201-78346-X 1 99.00\n' | ./bookstore
0-201-78345-X 5 110 22      ← 3+2 册、60+50 元、均价 22
0-201-78346-X 1 99 99

空输入（防御路径）：

$ printf '' | ./bookstore ; echo "exit=$?"
No data?!
exit=255                     ← return -1 的低 8 位

如果去掉 if (std::cin >> total) 这层判断，空输入时 total 是默认构造的 Sales_item（isbn 为空串、"卖了 0 本"），程序会输出一条 0 0 0 的垃圾记录，而不是什么都不输出。这一处防御是整个程序最容易漏的地方。

乱序输入（模式的前提被破坏）：

$ printf '0-201-A 1 10.0\n0-201-B 1 20.0\n0-201-A 1 10.0\n' | ./bookstore
0-201-A 1 10 10      ← A 出现两次，但没合并
0-201-B 1 20 20
0-201-A 1 10 10

A 被拆成了两组：因为程序只比较"当前组"和"下一条"，一旦书号变化就认为换组了。这说明——这个算法保证的是"相邻同 key 能合并"，不是"全局按 key 聚合"。

② 想处理乱序？三种方案的性能代价（100 万条 / 1000 个不同 key）

方案 是否要求有序 实测耗时 相对有序归并
① 有序归并（书店程序模式） ✅ 必须有序 3.9 ~ 5.8 ms 1×
② std::map 累加（乱序输入） ❌ 不要求 63 ~ 65 ms 约 11~16 倍
③ unordered_map 累加（乱序） ❌ 不要求 12.5 ~ 14.8 ms 约 2.5~3.2 倍
②' std::map（有序输入） — 45.8 ~ 52.1 ms —
③' unordered_map（有序输入） — 6.4 ~ 8.5 ms —

几点解读： - 有序归并快是因为它什么都不建：一次线性扫描，只维护"当前组"的三个变量；map 每条记录都要做字符串比较 + 红黑树旋转。 - unordered_map 比 map 快 4~5 倍，因为哈希是 O(1) 均摊 vs 红黑树 O(log k)；而且 reserve() 预分配能省掉 rehash。 - 输入有序时 unordered_map 也更快（6.4~8.5 ms vs 63~65 ms）——因为有序输入让哈希表的缓存局部性更好（相同 key 连续访问同一桶）。 - 代价对比：有序归并 O(1) 内存；map / unordered_map 要存下所有 key 的聚合结果。数据量极大时这个差别会变成能不能跑的问题。

③ operator>> / operator<< 的关键实现细节

std::istream& operator>>(std::istream& in, Sales_item& s) {
    std::string isbn; unsigned u; double p;
    if (in >> isbn >> u >> p) s = Sales_item(isbn, u, p);   // 读失败时【不动 s】
    return in;                                              // 返回流本身 → 可转 bool
}

两个必须遵守的约定： - 返回流本身（std::istream&），这样 while (cin >> x) 才能工作——流有 operator bool()，读成功为真。 - 失败时不要修改目标对象。上面用局部临时变量读，全成功了才赋值。直接写 in >> s.bookNo_ >> s.units_sold_ >> s.revenue_ 会导致半途失败时对象处于半更新状态——这正是 1.4 讲的"流失败后状态不可信"的具体体现。

HFT / 嵌入式视角

  1. "按 symbol 聚合"优先走有序归并。行情网关通常按合约分流，同一 symbol 的 tick 天然连续；此时用 O(1) 内存的归并比建 map 快 10 倍以上，还省掉哈希表的内存抖动（HFT 里要避免运行期动态分配）。
  2. 前提要写成断言。既然算法依赖"输入有序"，就在循环里加 if (cur_key > e.key) { /* 报乱序 */ } 或在入口做一次性校验。静默产出错的聚合结果比崩掉危险得多——盘后对账才发现差了几百万。
  3. 换组时别忘了"重置"。书店程序里是 total = trans，HFT 里是"上一组合计落盘/上报后，清空累加器开始新组"。这是这类循环最常见的 off-by-one 类 bug（第一组和最后一组最容易出错：最后一组没有"换组"事件来触发输出，必须循环外补一次）。
  4. unordered_map::reserve() 是免费的性能。知道 key 数量级就先 reserve，能避免运行期的 rehash（rehash 是 O(n) 的停顿，在实时路径上 unacceptable）。
  5. 嵌入式上内存比速度更稀缺。1000 个 key 的 map 每个节点要几十字节（指针 + 颜色位 + 字符串），在几 KB RAM 的 MCU 上不现实；有序归并只要几个局部变量——这就是"流式算法"在嵌入式上的真正价值。
  6. std::endl 别用在聚合循环里。实测 endl 比 '\n' 慢 23~25 倍（见 1.7），每条记录都 flush 会把这个 O(n) 算法变成 O(n × syscall)。

参考答案
  1. B。按书号排序，同一本书的记录连续出现，程序才能正确分组。乱序会漏合并。
  2. if (std::cin >> total) 为假，跳过整个块，直接 return 0，什么都不输出。这是正确的防御性处理。
  3. 框架：读第一笔成当前组的"基准合约"；后续每笔若合约号相同则累加成交量，不同则输出当前组合计、开启新合约。和书店程序结构一模一样，只是 isbn 换成合约号、+= 换成成交量累加。

4（踩坑·高价值） 输入 A B A（同一本书不连续），程序会输出几条记录？A 的总销量对吗？

// 就是原书的书店程序
while (std::cin >> trans) {
    if (total.isbn() == trans.isbn()) total += trans;
    else { std::cout << total << std::endl; total = trans; }
}
std::cout << total << std::endl;

5（判断） 只要把 if (std::cin >> total) 去掉，空输入时程序会崩溃。

6（应用） 现在要处理乱序输入（同一 key 可能不连续），且数据量 100 万条。你有哪些选择？各自的代价是什么？

参考答案

  1. 输出 3 条记录，A 的销量是错的（被拆成两组，各 1 册，而不是合计 2 册）。实测： 0-201-A 1 10 10 0-201-B 1 20 20 0-201-A 1 10 10 因为这个算法保证的是"相邻同 key 能合并"，不是"全局按 key 聚合"——它只比较"当前组"和"下一条"，key 一变就认为换组。所以输入必须按 key 有序是它的硬前提，而且这个前提不会报错，只会静默产出错误结果。生产代码里应该显式校验（或者在入口排一次序）。

  2. 不会崩，但会输出垃圾。Sales_item 的默认构造会让 total 是"空书号、0 册、0 元"，程序会正常输出一条 0 0 0 记录，然后 return 0（退出码 0 = 看起来成功）。这比崩溃更危险——下游以为这是一笔合法数据。原书的 if (std::cin >> total) 正是防御这一点：读不到第一条就走 else 分支，什么都不输出并返回非 0。

  3. 三种选择，实测（100 万条 / 1000 个不同 key）： - ① 先排序再做有序归并：std::sort + 归并。排序 O(n log n)，但常数极小且内存可控；归并阶段仍是 3.9~5.8 ms 量级。数据量远大于内存时的首选（可以外排序）。代价：需要一次性拿到全部数据。 - ② std::unordered_map 累加：乱序直接吃，实测 12.5~14.8 ms（约有序归并的 2.5~3.2 倍）。代价：要存下所有 key 的聚合结果；运行期有哈希开销和潜在 rehash 停顿（用 reserve() 缓解）。实时流式的首选。 - ③ std::map 累加：实测 63~65 ms（约 11~16 倍），最慢——红黑树每次插入 O(log k) 且缓存局部性差。只有需要按 key 有序输出时才选它（比如要按字典序打印报表）。

决策顺序：能排序 → ①；要实时流式 → ②；要有序输出 → ③。别默认用 map（很多人的习惯），它是这里最慢的选项。

① std::endl vs '\n'：数量级的差别

写 20 万行到文件，同进程对照实测：

写法 实测耗时
ofstream << ... << '\n' 37.9 ms
ofstream << ... << std::endl 444.0 ms

慢约 12 倍（另一次独立进程测量中是 431~470 ms vs 18.3~18.5 ms，23~25 倍；差别来自目标设备与缓存状态，但数量级一致）。

原因是 std::endl 做两件事：写 '\n' + 强制 flush。一次 flush 就是一次 write 系统调用（几微秒），20 万次就是几百毫秒。endl 应该只在真正需要"立刻让对方看到"时用（比如交互式提示、崩溃前的最后一行日志）。

② printf vs std::cout

20 万行写 /dev/null：

写法 实测耗时（3 轮）
std::cout << i << " " << i*2 << '\n'（默认） 42.9 / 42.9 / 42.9 ms
std::cout + sync_with_stdio(false) 42.9 / 42.9 / 42.9 ms
printf("%d %d\n", i, i*2) 21.1 / 21.1 / 21.2 ms

写真实文件时：cout 45.8~54.4 ms、关同步 45.8~46.0 ms、printf 23.8~24.0 ms——结论一致。

两条诚实的结论： - printf 比 std::cout 快约 2 倍（在 libc++ 上）。日志热路径值得在意，但先确认瓶颈真在 IO。 - sync_with_stdio(false) 在 libc++ 上收益接近 0（42.9 vs 42.9 ms）。网上常说的"关同步快 5~10 倍"是 libstdc++（GCC）上的老经验，别盲信——换了标准库先自己测。

补充：关同步真正的意义是保证 printf 和 cout 混用时的输出顺序。开了同步，两者顺序一致；关了就各走各的缓冲，交叉输出会乱序。关同步前先确认没有混用。

第 1 章给 C 程序员的补充要点（前 5 条之外的）

  1. return 0 之外只用 0–125 做错误码 —— 256 会静默变成 0（见 1.1）
  2. 整段禁用代码用 #if 0，不要用 /* */ —— 注释不能嵌套（见 1.3）
  3. cin 失败会锁死流 —— 必须先 clear() 再 ignore()（见 1.4）
  4. class 的价值是 private，不是语法糖 —— 成员函数和普通函数汇编一样（见 1.5）
  5. #pragma once 挡不住 ODR —— 头文件里只能放声明、inline、类定义（见 1.5.1）
  6. 别用 std::endl 做换行 —— 除非你真的需要立即 flush（见本节）

HFT / 嵌入式视角（全章汇总）

  1. 日志是 HFT 最大的隐性成本之一。撮合/行情路径上每笔都 printf 一次，20 万笔就是 20~40 ms——足够吃掉一个交易日的 alpha。热路径上用无锁环形缓冲 + 后台线程落盘，而不是同步写。
  2. endl 是"看起来无害"的性能杀手。代码 review 时见到 endl 就该问一句"这里真的需要 flush 吗"。生产代码里 99% 应该是 '\n'。
  3. 别在头文件里塞实现。HFT 项目几千个文件，头文件改一行触发全量重编是几十分钟；inline 只留给 1–3 行的访问器。
  4. <iostream> 在 MCU 上基本不可用。展开 3 万行、二进制 +36 KB——片上运行的代码应该走精简 printf 或直接写 UART，C++ 这边只保留不依赖 <iostream> 的部分（这也是为什么很多嵌入式项目用 -fno-exceptions -fno-rtti）。
  5. 退出码是唯一的跨进程契约。盘前检查、看门狗、CI 全靠它，取值只用 0–125，别用 exit() 乱杀进程（不析构局部对象）。
  6. 先量化再优化。本章所有结论都来自实测数字，而不是"听说"。这个习惯比记住任何一个具体数字都重要——换了编译器/标准库/CPU，结论可能反转（比如 sync_with_stdio 那条）。
