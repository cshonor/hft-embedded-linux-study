导读

本章介绍 C++ 的控制流（flow-of-control）语句，支持程序跳出简单顺序执行，实现条件分支、循环和跳转等复杂执行路径。

章节摘要

C++ 的控制流语句：简单语句与复合语句、作用域（if/switch/for 引入块作用域）、条件语句（if/switch）、迭代语句（while/for/do-while/范围 for）、跳转语句（break/continue/goto/return）以及异常处理（try/catch/throw）。

C C++

无范围 for for (auto &x : container)

5.1

–5.2 简单语句与作用域

本节讲什么

C++ 的最基本语句形式：表达式语句、空语句、复合语句（块），以及变量在控制结构中形成的块作用域。这些是构成后面所有控制流的基础。

核心用法

五种基本语句

语句 形式 说明
表达式语句 expr; 末尾加分号，如 i = 0;、std::cout << x;
空语句 ; 只有一个分号，循环体为空时用，如 while (cin >> x) ;
声明语句 int i; C++ 中声明也是语句，可出现在任何位置
复合语句（块） { ... } 用花括号括起来的语句序列，是一个作用域
控制语句 if/for/while... 后续章节讲

语句作用域

在 if、for、while 等控制结构内部定义的变量，只在该控制结构内可见，出了结构即销毁：

while (int i = get_value()) {  // i 在整个 while 循环可见
    // i 在循环体内可见
}  // i 在这里销毁，外部不可访问

for (int i = 0; i < 10; ++i) {
    int sq = i * i;  // sq 只在本次循环体可见
    std::cout << sq << " ";
}
// i 和 sq 在这里都已销毁

和 C 的区别

维度 C（C89） C99 / C++ C++ 额外
声明位置 C89 强制声明必须在块开头，语句之后不能再声明 C99 放宽，允许声明与语句混合；C++ 一直允许 —
for 变量作用域 C89：for 里定义的变量在循环外仍可见 C99 起：循环外不可见（与 C++ 一致） C++ 从一开始就是块作用域
声明即语句 ❌ C89 不行 ✅ C99 起可以 ✅ C++ 一直可以

C 程序员最常踩的坑：从 C89 习惯过来，把所有声明堆在函数开头。C++ 鼓励"用到时再声明"，可以提升可读性，有时还能减少作用域污染。

/* C89 风格：声明全堆在开头 */
void f(void) {
    int i, sq, sum;     /* 必须在这里 */
    sum = 0;
    for (i = 0; i < 10; ++i) { sq = i*i; sum += sq; }
}

// C++ 风格：用到时再声明
void f() {
    int sum = 0;
    for (int i = 0; i < 10; ++i) {   // i 只在 for 内可见
        int sq = i * i;              // sq 只在本次循环可见
        sum += sq;
    }
}

底层实现与实测

以下均为本机实测（Apple clang 23.1.0，arm64，-std=c++17 -O2）。作用域是编译期概念——它决定「什么时候调析构函数」和「哪个名字可见」，但不保证内存复用。

实测 1：作用域什么时候结束？让析构函数告诉你

用 RAII 探针（构造/析构各打印一行）：

struct Probe {
    const char* name;
    explicit Probe(const char* n) : name(n) { printf("+ 构造 %s\n", name); }
    ~Probe() { printf("- 析构 %s\n", name); }
};

for (int i = 0; i < 2; ++i) {
    Probe p("loop-body");
    printf("i=%d\n", i);
}

实测输出：

+ 构造 loop-body      i=0
- 析构 loop-body
+ 构造 loop-body      i=1
- 析构 loop-body

循环体里的对象每轮迭代都构造 + 析构一次。 这是热路径上最容易忽略的成本：for 里写 std::string s = fmt(x); 意味着每轮一次构造 + 可能的堆分配。

手动加一对花括号可以精确控制生命周期：

+ 构造 block-a
+ 构造 block-b
- 析构 block-b        ← 内层块结束就析构
（b 已销毁）
- 析构 block-a

实测 2：出了作用域，栈内存不一定复用

{ int x = 1; printf("块1 x 地址 %p\n", (void*)&x); }
{ int x = 2; printf("块2 x 地址 %p\n", (void*)&x); }

实测：块1 0x16d222cdc / 块2 0x16d222cd8——相邻但不同。

编译器按自己的栈布局分配槽位，"变量出了作用域，它占的内存就被释放/复用"是错误直觉。真正可靠的只有一条：出了作用域，对象的析构函数已经跑过了，再访问它就是 UB（悬垂指针/引用，见 6.2 返回类型 的悬垂引用实测）。

实测 3：遮蔽（shadowing）合法，但编译器能帮你抓

int v = 100;
{ int v = 200; /* 内层 v 盖住外层 */ }

$ clang++ -std=c++17 -Wshadow x.cpp
warning: declaration shadows a local variable [-Wshadow]

注意区分两件事（详见 3.5.5 易错点）：内层块遮蔽外层变量是合法的；同一作用域里同名声明两次是 error: redefinition。

实测 4：C89 vs C++——声明位置

代码 clang -std=c89 -pedantic（C） -std=c99（C） C++
for (int i = 0; ...) warning: variable declaration in for loop is a C99-specific feature ✅ ✅（一直允许）
语句之后再声明 warning: mixing declarations and code is a C99 extension ✅ ✅

所以从 C89 移植代码时，「把声明堆在块开头」是历史习惯而不是语言要求；C++ 从一开始就允许随处声明，C99 才追上来。

实测 5：C++17 带初始化的 if / switch（C 完全没有）

if (int n = get_value(); n > 0) { /* n 可见 */ }
else                            { /* n 也可见 */ }
switch (int k = argc; k) { case 1: /* k 可见 */ break; }

实测变量在 if 的两个分支和 switch 的所有 case 里都可见，出了结构就销毁。价值：把「只给条件用的临时变量」锁死在条件结构里，避免污染外层作用域——这正是 if (auto it = m.find(k); it != m.end()) 这类写法的目的。

实测 6：空语句有专门的警告

while (j < n);   // ← 分号

warning: while loop has empty body [-Wempty-body]
note: put the semicolon on a separate line to silence this warning

把分号单独放一行（while (cond) 换行 ;）是社区惯例——明确告诉读者"这是故意的空循环体"。

HFT / 嵌入式视角

  • 作用域 = 临界区长度：std::lock_guard 的作用域就是持锁时间。实测 1 说明「块结束即析构」，把锁塞进最小块能直接缩短锁竞争窗口——低延迟代码里最常用的一招。
  • 热循环里别在循环体构造对象：实测 1 的证据——每轮一次构造 + 析构。std::string、std::vector、std::lock_guard 都算；能提到循环外就提出来（hoist）。
  • 嵌入式栈很小（常见 8–16 KB，RTOS 任务栈可能只有 1–2 KB）：块作用域变量占栈，深层嵌套 + 大数组容易爆栈；大缓冲改 static 或放全局。
  • 声明时立即初始化：int x; 在块作用域里是不确定值，读到就是 UB（ASan 未必每次都能抓到）。写 int x{};。
  • 别依赖栈内存复用（实测 2）：返回局部变量地址在任何优化等级下都是错的，哪怕"看起来还能读到旧值"。

常见错误

  1. 在控制结构外用内部变量：for (int i=0;...) {...} 之后再用 i，C89 能过、C++ 报错。这是从 C 移植代码时最常见的编译错误之一。
  2. 空语句误用导致逻辑错误：while (i < n); { ++i; } —— 末尾分号让循环体变成空语句，花括号成了独立块，导致死循环。
  3. 误以为 for 条件里的变量在整个函数可见：在 for (int i...) 后还想用 i 做别的事，应该把 i 提到循环外声明。
  4. 在循环体里构造昂贵对象：实测 1 显示循环体对象每轮构造 + 析构一次。for (...) { std::string s = fmt(x); ... } 在百万级循环里就是百万次构造/析构。修正：能复用就在循环外声明并 clear()，或改用 std::string_view / 栈上定长缓冲。
  5. 以为出了作用域内存就会被复用：实测 2（两个块的 x 落在相邻但不同的地址）。把局部变量地址返回或保存到外面，读到什么全看编译器心情，是 UB。

自测题

1. 选择题：以下代码在 C++ 中的输出是？

int i = 0;
for (int i = 0; i < 3; ++i) { /* 空 */ }
std::cout << i;
  • A) 0
  • B) 3
  • C) 编译错误
  • D) 未定义行为
答案

A) 0。for 里的 i 遮蔽了外层的 i，循环结束后内层 i 销毁，外层 i 仍为 0。这是合法但容易混淆的写法。

2. 判断题：在 C++ 中，int x = 10; std::cout << x; 可以在函数体中间直接写，不必把 int x 放在块开头。

答案

正确。C++ 允许声明语句出现在任意位置，这是 C++ 相对 C89 的一个进步（C99 也放宽了）。

3. 踩坑题：下面代码意图是累加，但运行结果是死循环，为什么？

int n = 5, sum = 0;
int i = 0;
while (i < n);
{
    sum += i;
    ++i;
}
答案

while (i < n); 末尾的分号构成空语句，循环体为空，i 永远不变化 → 死循环。下面的 { sum += i; ++i; } 是一个独立的复合语句块，不属于循环。修正：去掉 while 后的分号。

4. 应用题：把下面 C89 风格代码改写成 C++ 推荐风格（用到时再声明，最小化作用域）。

void process(int* arr, int n) {
    int i, j, tmp;
    for (i = 0; i < n; ++i)
        for (j = i+1; j < n; ++j)
            if (arr[j] < arr[i]) {
                tmp = arr[i]; arr[i] = arr[j]; arr[j] = tmp;
            }
}
答案 
void process(int* arr, int n) {
    for (int i = 0; i < n; ++i)
        for (int j = i + 1; j < n; ++j)
            if (arr[j] < arr[i]) {
                int tmp = arr[i];   // 用到时再声明
                arr[i] = arr[j];
                arr[j] = tmp;
            }
}

i、j、tmp 都限定在最小作用域内，外层不再可见，减少误用风险。

5. 输出题：下面代码里 Probe 会打印几组构造/析构？顺序如何？

struct Probe { Probe(const char*); ~Probe(); };   // 各打印一行
for (int i = 0; i < 3; ++i) {
    Probe p("body");
    if (i == 1) { Probe q("inner"); }
}
答案

body 构造/析构 3 组（每轮一次），inner 1 组（只在 i==1 那轮、且在内层块结束时析构）。顺序：

+ body   (i=0)
- body
+ body   (i=1)
+ inner      ← 进入内层块
- inner      ← 内层块结束立即析构，不等循环结束
- body       ← 循环体结束
+ body   (i=2)
- body

要点：内层块有自己的生命周期，不等外层。这正是把 std::lock_guard 塞进最小块就能缩短临界区的原理。

6. 判断题：下面两句对不对？

(a) 变量出了作用域，它占的栈内存就一定会被后面的变量复用。 (b) for 循环体里的对象只构造一次，循环结束才析构。

答案

两句都错。

(a) 实测：两个相邻块里的 int x 地址是 0x16d222cdc 和 0x16d222cd8——相邻但不同。栈槽怎么分配由编译器决定，语言只保证"出了作用域析构函数已跑过、再访问是 UB"，不保证内存复用。把局部变量地址传出去是经典 UB。

(b) 实测输出（examples/5.1-1）：+ 构造 → i=0 → - 析构 → + 构造 → i=1 → - 析构——每轮迭代都构造 + 析构一次。热循环里放昂贵对象（string/vector/lock_guard）会被放大成百万次开销。

5.3

条件语句

本节讲什么

if 与 switch 两种条件分支语句。重点讲 if-else 嵌套时的悬垂 else 问题、switch 的 case 标签与 break 穿透、以及 switch 内部定义变量的限制。

核心用法

if 语句

if (条件) 语句
if (条件) 语句1 else 语句2

else 总是与最近的未配对的 if 匹配，这就是悬垂 else 问题：

if (a > 0)              // 外层 if
    if (b > 0)          // 内层 if
        do_x();
else                    // 这个 else 属于内层 if，不是外层！
    do_y();

switch 语句

switch (整型表达式) {
    case 常量1: 语句; break;
    case 常量2: 语句;  // 没有 break → 穿透到下一个 case
    default:    语句;
}
  • case 标签必须是整型常量表达式
  • 忘了 break 会导致穿透（fall-through），有时是故意的，但必须显式注释
  • switch 内部如果要在某个 case 下定义变量，必须用 {} 把该 case 包成块

和 C 的区别

维度 C C++
if/switch 语法 完全一致 完全一致
case 标签类型 C89 起支持整型常量表达式 同 C，但 C++ 要求更严格的常量表达式（const int 可作标签，C 中 const int 不是真常量）
switch 内变量定义 C 允许跨 case 标签的自动变量（但容易 UB） C++ 禁止跨越 case 标签初始化变量，必须用 {} 块包住
case 标签用 const 变量 ❌ C 中 const int n=1; 不是常量表达式，不能作 case 标签 ✅ C++ 中可以（前提是初始化为常量）

关键差异：C 的 const 变量本质是"只读变量"而非"常量"，所以 C 中 const int n = 1; ... case n: 是非法的；而 C++ 的 const int 如果用常量初始化，就是真正的编译期常量，可作 case 标签和数组维度。

/* C：编译错误！const 不是常量表达式 */
const int N = 3;
switch (x) { case N: ...; }   // 错误：N 不是常量表达式

// C++：合法，N 是编译期常量
const int N = 3;
switch (x) { case N: ...; }   // OK

底层实现与实测

以下均为本机实测（Apple clang 23.1.0，arm64，-std=c++17 -O2）。条件语句的性能问题，九成不在语法，在分支能不能被预测 / 能不能被消掉。

实测 1：紧凑 switch 会变成查表，稀疏 switch 退化成 if-else 链

int dense(int k) {   // case 0..5，返回值刻意不连续，逼编译器不能"算术化"
    switch (k) {
        case 0: return 100; case 1: return -7; case 2: return 42;
        case 3: return 3;   case 4: return 999; case 5: return 8;
        default: return -1;
    }
}

dense(int):
    cmp   w0, #5
    b.hi  LBB0_2                          ; 越界 → default
    adrp  x8, l_switch.table._Z5densei@PAGE
    add   x8, x8, l_switch.table._Z5densei@PAGEOFF
    ldr   w0, [x8, w0, uxtw #2]           ; 一次间接取数，O(1)
    ret
LBB0_2:
    mov   w0, #-1
    ret

而 case 值跨度很大时（1 / 1000 / 100000 / 10000000），编译器不做表，变成一串 cmp + b.eq（实测汇编里是 cmp w0, #1; b.eq / cmp w0, #1000; b.ne ……），退化成 if-else 链。

补充：如果 case 的返回值本身连续（10/11/12/13/14/15），clang 连表都不用，直接算：add w8, w0, #10; cmp w0, #6; csinv——一次跳转都没有。所以"switch 一定生成跳转表"是错的，要看数据形态。

实测 2：if-else 和三元运算符生成完全相同的代码

int maxif (int a, int b) { if (a > b) return a; return b; }
int maxtri(int a, int b) { return a > b ? a : b; }

maxif(int, int):            maxtri(int, int):
    cmp  w0, w1                 cmp  w0, w1
    csel w0, w0, w1, gt         csel w0, w0, w1, gt     ← 一模一样
    ret                         ret

两者都被编译成 csel（条件选择），没有跳转指令。结论：小分支上纠结 if 还是 ?: 毫无意义，编译器会挑等价的无分支形式。

实测 3：分支预测到底值多少钱（校准一个流传很广的说法）

经典说法是「排序后比随机快 3~6 倍」。本机实测（examples/5.3-1，100 万个 int × 5 轮，if (x >= 128) 二选一）：

数据 实测（-O2） 实测（-O1）
随机数据 1.73 ms/轮 2.96 ms/轮
已排序数据 1.60 ms/轮 2.47 ms/轮
差距 1.08 倍 1.20 倍

只有 1.1~1.2 倍，不是 3~6 倍。 两个原因： 1. 现代分支预测器（TAGE 类）对"50% 随机"也不至于崩盘； 2. clang 会做 if-conversion：分支体足够简单时直接变成 csel/SIMD 选择，压根没有分支可预测。

这不代表分支预测不重要——分支体越重、越无法被无分支化，差距越大；而且一次预测失败在深流水线上是 15~20 个周期。但对"简单二选一"这种形态，编译器已经替你消掉大半。

实测 4：跨 case 初始化变量，编译器直接拒绝

error: cannot jump from switch statement to this case label

加了 {} 把变量锁在这一支里就好了——case 1: { int v = 10; ...; break; }。

实测 5：两个能救命的警告

warning: unannotated fall-through between switch labels [-Wimplicit-fallthrough]
note: insert '[[fallthrough]];' to silence this warning

warning: add explicit braces to avoid dangling else [-Wdangling-else]

warning: enumeration value 'Blue' not handled in switch [-Wswitch]     ← enum class 漏 case

C++17 起用 [[fallthrough]]; 显式声明"故意穿透"，比写 // fall through 注释更可靠（注释骗得过人骗不过编译器）。

HFT / 嵌入式视角

  • switch 稠密时是 O(1) 查表（实测 1），稀疏时是 if-else 链——消息类型分发（订单/成交/撤单）用连续枚举值，编译器就能生成跳转表；枚举值乱跳（1/1000/100000）反而更慢。
  • 热路径上优先"把分支挪出去"，而不是"把分支写快"：预计算档位表、用算术/掩码替代判断（s += (x >= 128) * x 这类）、或者按数据分桶后批量处理（排序过的批处理更快，实测 3）。
  • 别手搓 branchless 来"优化"：实测 2 说明编译器已经会做 if-conversion。手写位运算技巧常常只是让代码更难读，性能零收益，还可能挡掉编译器更好的优化。
  • 真要提示分支倾向用 [[likely]] / [[unlikely]]（C++20）或 __builtin_expect，但先测——实测 3 说明这类微优化的收益往往在噪声里。
  • 嵌入式：switch 查表会占 .rodata（Flash），if-else 链占 .text；Flash 紧张或指令 cache 小的 MCU 上，稠密 switch 的表可能反而吃亏（一次 Flash 取数 vs 几条指令），要看具体芯片。

常见错误

  1. 悬垂 else 误配对：if (a) if (b) f(); else g(); 里的 else 属于内层 if，导致逻辑与预期不符。解决：用花括号明确归属：if (a) { if (b) f(); } else g();。
  2. 忘写 break 导致意外穿透：case 1: do_a(); case 2: do_b(); 中 case 1 会顺带执行 do_b()。即使故意穿透，也要加 // fall through 注释，否则 -Wimplicit-fallthrough 会警告。
  3. switch 内跨 case 定义变量未加块：switch(x){ case 1: int v=10; f(v); break; case 2: g(v); } —— C++ 报错"不能跨越 case 标签初始化"（实测：cannot jump from switch statement to this case label）。解决：case 1: { int v=10; f(v); break; }。
  4. 以为「switch 稠密就一定生成跳转表」：实测 1 里 case 返回值连续时，clang 直接用算术算出来（add w0, w0, #10），连表都没有；case 稀疏时又退化成 cmp 链。跳转表只是编译器的一种选择，不是 switch 的定义。
  5. 照搬「排序能让分支快 3~6 倍」去做优化：本机实测只有 1.08~1.20 倍（实测 3）——现代预测器 + 编译器无分支化把差距抹平了。先 profile 再优化，别拿十年前的传说当依据。

自测题

1. 选择题：下列代码输出什么？

int x = 1;
if (x > 0)
    if (x > 10)
        std::cout << "A";
else
    std::cout << "B";
  • A) A
  • B) B
  • C) AB
  • D) 无输出
答案

B) B（实测输出 B，-Wdangling-else 同时给出警告：add explicit braces to avoid dangling else）。

else 与最近的未配对 if 配对，也就是内层 if (x > 10)。执行过程：x=1 > 0 成立 → 进入内层 → x > 10 不成立 → 走 else 打印 B。缩进完全骗人：如果真想让 else 属于外层，必须写 if (x > 0) { if (x > 10) printf("A"); } else printf("B");（那样 x=1 时什么都不打印）。

2. 判断题：在 C++ 中，下面代码合法。

const int BUF = 1024;
switch (n) { case BUF: f(); break; }
答案

正确。C++ 中用常量初始化的 const int 是编译期常量，可作 case 标签。但在 C 中同样写法是非法的（C 的 const 不是常量表达式）。

3. 踩坑题：下面代码在 C++ 中编译报错，为什么？怎么改？

switch (cmd) {
    case 1:
        int status = read_status();
        process(status);
        break;
    case 2:
        handle_other();
        break;
}
答案

报错：不能跨越 case 标签初始化变量（status 的作用域延伸到 case 2，但 case 2 可能跳过初始化）。修正：用花括号把 case 1 的内容包成块：

case 1: {
    int status = read_status();
    process(status);
    break;
}

4. 应用题：用 switch 写一个处理 HTTP 状态码的函数，要求 200/201 走成功分支、4xx 走客户端错误、5xx 走服务端错误。注意正确使用穿透和 break。

答案 
void handle_status(int code) {
    switch (code) {
        case 200:                   // 穿透
        case 201:
            handle_success();
            break;
        case 400: case 401: case 403: case 404:
            handle_client_error(code);
            break;
        case 500: case 502: case 503:
            handle_server_error(code);
            break;
        default:
            log_unknown(code);
    }
}

故意穿透的 case（200→201）可以不加注释，但建议显式写 // fall through 让 -Wimplicit-fallthrough 闭嘴。

5. 判断题：下面两句对不对？

(a) switch 稠密时一定会被编译成跳转表，所以比 if-else 链快。 (b) ?: 三元运算符比 if-else 快，因为它没有分支。

答案

两句都不准确。

(a) 稠密 case 时编译器通常会用表（实测：adrp x8, l_switch.table...; ldr w0, [x8, w0, uxtw #2]），但如果 case 的返回值本身连续，clang 连表都省了，直接算（add w8, w0, #10）；稀疏 case 又退化成 cmp + b.eq 链。所以"case 稠密 + 返回值不规则"才容易看到跳转表，而且跳转表的价值是 O(1) 与可扩展性，不是"一定更快"——分支目标可预测时 if-else 链并不慢（对比 6.5 的跳转表实测）。

(b) 实测：if (a > b) return a; return b; 与 return a > b ? a : b; 生成完全相同的汇编（cmp + csel + ret），都没有跳转。三元更快是错觉，选哪个看可读性。

6. 应用题：热路径上有这么一段：for (int x : data) if (x >= 128) s += x * 7 + 3; else s -= x * 3 + 1; 有人提议"先把 data 排序，分支预测器就能预测，能快好几倍"。请评价。

答案

实测：只有 1.08 倍（-O2）/ 1.20 倍（-O1），远不到"好几倍"，而且排序本身是 O(n log n)，比省下的时间贵得多。

原因有二：① 现代预测器对随机分支没那么脆弱；② 编译器做了 if-conversion，分支体简单时直接生成条件选择/向量选择，"分支"本身就少了。

真正有效的做法（按性价比排序）： 1. 先 profile，确认瓶颈确实在这条分支上； 2. 把分支移出循环（分桶批量处理：先 partition，再对两段分别做无分支求和）； 3. 用算术/查表替代判断（例如 s += tbl[x]）； 4. 最后才考虑 [[likely]] / __builtin_expect——收益常在噪声里。

一句话："让分支更好预测"收益有限，"让分支不存在"才有效。

迭代语句（循环）

本节讲什么

四种循环：while、传统 for、范围 for（range-for，C++11）、do-while。重点讲范围 for 的用法与限制——这是 C 程序员最该学的新东西。

核心用法

语句 形式 适用场景
while while (cond) stmt 次数未知，先判断后执行
传统 for for (init; cond; expr) stmt 按步骤迭代，可控制增量
范围 for for (decl : coll) stmt 遍历容器/数组的每个元素
do-while do stmt while (cond); 至少执行一次

范围 for（C++11）

std::vector<int> v = {1, 2, 3, 4, 5};

// 只读遍历：用 const auto&
for (const auto& x : v)
    std::cout << x << " ";

// 修改元素：用 auto&
for (auto& x : v)
    x *= 2;

// 注意：不要在范围 for 中改变容器大小（push_back/erase）

范围 for 等价于：

auto it = v.begin();
auto end = v.end();
for (; it != end; ++it) {
    auto& x = *it;
    // 循环体
}

和 C 的区别

维度 C C++
while / for / do-while 完全一致 完全一致
for 变量作用域 C89：循环外可见；C99 起：块作用域 一直是块作用域
范围 for ❌ C 没有任何等价语法 ✅ C++11 起有
遍历容器 C 要手写索引或指针循环 范围 for 一行搞定

范围 for 是 C 程序员转 C++ 最直接受益的特性之一——C 里遍历数组只能写 for (int i=0; i<n; ++i) a[i]，C++ 里直接 for (auto& x : a)，且不会越界。

/* C：手写索引，容易越界 */
int sum = 0;
for (int i = 0; i < n; ++i)   // n 维护错了就 UB
    sum += arr[i];

// C++：范围 for，无需维护索引
int sum = 0;
for (int x : arr)   // arr 是数组或容器，自动取 begin/end
    sum += x;

底层实现与实测

本机 clang 实测（-std=c++17，Apple Silicon）。这一节最容易被"经验之谈"误导——比如"迭代器比下标快""范围 for 有额外开销"，实测下来都不成立。

实测 1：五种遍历写法，性能差别几乎为零

100 万个 int 的 vector，每种写法跑 20 轮求和（-O2）：

写法 20 轮耗时（两次运行） 折合每轮
下标 v[i]（size_t i） 2.83 / 2.02 ms ≈ 0.10 ms
下标 v[i]（int i，缓存 size） 2.83 / 2.01 ms ≈ 0.10 ms
迭代器 begin()/end() 2.84 / 2.00 ms ≈ 0.10 ms
范围 for（auto x 拷贝） 2.41 / 1.94 ms ≈ 0.10 ms
范围 for（const auto& x） 2.33 / 1.74 ms ≈ 0.09 ms

结论：-O2 下这五种写法生成的机器码几乎一样，差距落在噪声范围内（1 亿次访存 ≈ 2 ms，即瓶颈是内存带宽，不是循环写法）。所以：

  • 别为了"性能"在下标和迭代器之间纠结，选可读性最好的那个；
  • 真正的性能差异只在循环体里（有没有拷贝元素、有没有分支、有没有 cache miss）。

实测 2：for (auto x) 的拷贝是真的会发生

struct Big { std::string s; int pad[8]; };   // sizeof = 56
std::vector<Big> v(3);
for (auto  x : v) x.s = "changed";   // 改的是副本
for (auto& x : v) x.s = "changed";   // 改的是元素

实测输出：

  for(auto x)     改后 v[0].s = ""        ← 一个都没改到
  for(auto& x)    改后 v[0].s = "changed"

每个元素拷贝 56 字节 × N 个，且编译器不会告诉你。对小类型（int、char）无所谓，对结构体/字符串就是实打实的开销加静默 bug。

实测 3：size_t 逆向循环会回绕而不是停下

std::vector<int> v{1,2,3};
for (size_t i = v.size() - 1; i >= 0; --i) { ... }   // ❌

实测第 6 次迭代时 i = 18446744073709551613（即 2⁶⁴−3）——i >= 0 对无符号数恒为真，减到 0 后再减就回绕。要么改成 for (size_t i = v.size(); i-- > 0; )，要么直接用有符号 ptrdiff_t/int。同源坑见 3.5.2 下标访问与越界。

HFT/嵌入式关联

  • 热循环的选型依据是循环体，不是循环头（实测 1）。行情快照遍历、order book 分层扫描这类代码，先确认有没有在循环里做无谓拷贝（实测 2）或随机访存，再谈下标 vs 迭代器。
  • 范围 for 只用于"遍历"，不用于"增删"：end() 在循环开始时缓存，任何改变容器大小的操作都让它失效（UB）。要边遍历边删，用 erase-remove 惯用法或索引循环——见 10.1 基础算法与重排。
  • 遍历前先 reserve：循环里 push_back 触发扩容会搬迁全部旧元素（实测见 3.3.5），在延迟敏感的循环里这是典型的毛刺来源。
  • 小类型用值、大类型用引用：char/int/double 走值即可（引用底层是指针，反而多一次 load，汇编证据见 6.1 实测 1）；结构体、字符串一律 const auto&。

常见错误

  1. 范围 for 用值类型导致无法修改 + 性能损耗：for (auto x : v) 会拷贝每个元素，既不能修改原元素，大对象还慢。修正：只读用 const auto&，要改用 auto&。
  2. 范围 for 中修改容器大小：for (auto& x : v) v.push_back(x); —— end() 在循环开始时缓存，扩容后迭代器失效，UB。修正：先拷贝或用索引循环。
  3. 范围 for 遍历 vector<bool> 用 auto&：vector<bool> 的元素不是真正的 bool，是代理对象，auto& 推导出的是代理引用而非 bool&。修正：用 auto 或 const auto&。
  4. 用 size_t 做逆向循环（实测 3）：for (size_t i = n-1; i >= 0; --i) 永远成立，减到 0 后回绕成 2⁶⁴−1，越界访问。修正：for (size_t i = n; i-- > 0; ) 或改用有符号下标。
  5. 循环条件里重复调用 size()：for (size_t i = 0; i < s.size(); ++i) 中 size() 理论上每次都要算。实测 1 表明 -O2 下编译器会把它提到循环外（几种写法耗时相同），所以这属于可读性问题而非性能问题——但 -O0 调试构建下确实会变慢，别拿 debug 构建测性能。

自测题

1. 选择题：下面哪种写法能正确地把 vector<int> 每个元素翻倍？ - A) for (auto x : v) x *= 2; - B) for (auto& x : v) x *= 2; - C) for (const auto& x : v) x *= 2; - D) for (auto x : v) v[x] *= 2;

答案

B。auto& 是引用绑定，能修改原元素。A 是拷贝改不动原值；C 是 const 引用不能修改；D 的 x 是元素值不是索引，逻辑错误。

2. 判断题：范围 for 循环里调用 v.clear() 是安全的。

答案

错误。clear() 让所有迭代器失效，范围 for 内部持有的 end() 和当前迭代器都会失效，属于未定义行为。范围 for 只适合"只读遍历"或"就地修改元素值"，不能增删元素。

3. 踩坑题：下面代码打印什么？为什么？

std::vector<int> v = {1, 2, 3};
for (auto x : v) {
    v.push_back(x);   // 想复制一份
}
std::cout << v.size();
答案

未定义行为。范围 for 开始时缓存了 end()，但 push_back 可能触发扩容使 end() 失效，循环无法正确终止，可能死循环或崩溃。正确做法：先记录要添加的元素，循环结束后再批量 push，或用索引循环并提前 reserve。

4. 应用题：用范围 for 统计一个 std::string 中元音字母的个数，要求高效（不拷贝）。

答案 
std::string s = "hello world";
int vowels = 0;
for (char c : s) {                 // char 是小类型，用值即可；大对象用 const auto&
    if (c=='a'||c=='e'||c=='i'||c=='o'||c=='u' ||
        c=='A'||c=='E'||c=='I'||c=='O'||c=='U')
        ++vowels;
}
std::cout << vowels;  // 3

char 是 trivially copyable 类型，用值比引用更高效（引用底层是指针，反而多一次间接寻址）。

跳转语句

本节讲什么

break、continue、goto、return 四种跳转语句。前三个改变循环/分支的控制流，return 从函数返回（函数章详讲）。

核心用法

语句 作用 作用范围
break 跳出最近的循环或 switch 只影响最内层
continue 跳过本次循环剩余部分，进入下一次迭代 只影响最内层循环
goto 无条件跳转到标签 同一函数内
return 从函数返回 退出整个函数 
// break：找到目标就停
for (int i = 0; i < n; ++i) {
    if (arr[i] == target) {
        found = true;
        break;              // 跳出整个 for
    }
}

// continue：跳过偶数
for (int i = 0; i < 10; ++i) {
    if (i % 2 == 0) continue;  // 跳过本次，进入 i+1
    std::cout << i << " ";     // 只打印奇数
}

和 C 的区别

维度 C C++
break/continue 语义 完全一致 完全一致
goto 语法 一致 一致，都不能跨函数跳
goto 跳过变量初始化 C 不限制（但容易 UB） C++ 禁止 goto 跳过带初始化的变量声明
return 一致 C++ 多了"返回引用""返回类型可推导(auto)"等

唯一实质差异：C++ 不允许 goto 向前跳过一个带初始化的变量声明，C 没这个限制（但跳过也是 UB）。

// C++：编译错误
goto label;          // 向前跳
int x = 10;          // 带初始化，goto 跳过了它
label: use(x);

实践中 goto 在 C 和 C++ 都不推荐日常使用，但有一个合法用途：错误处理路径的集中清理（Linux 内核风格 goto cleanup），因为 C 没有 RAII，C++ 有 RAII 所以更少需要 goto。

底层实现与实测

以下均为本机实测（Apple clang 23.1.0，arm64，-std=c++17 -O2）。跳转语句在汇编层就是几条 b.cond / b 指令，本身几乎不花钱——真正的坑都在语义上。

实测 1：嵌套循环里 break 只跳出最内层（附正确输出）

for (int i = 0; i < 3; ++i)
    for (int j = 0; j < 3; ++j) {
        if (i + j == 2) break;
        printf("%d%d ", i, j);
    }

实测输出：00 01 10

i j 的取值 说明
0 j=0 打印 00，j=1 打印 01，j=2 命中 0+2=2 → break 打印 2 个
1 j=0 打印 10，j=1 命中 1+1=2 → break 打印 1 个
2 j=0 就命中 2+0=2 → break 一个都没打印

修正：本笔记早期版本的自测题答案写成 00 01 10 11（选项 C），实测输出是 00 01 10——i=2 那一轮 j=0 就触发 break，压根没机会打印 11。四个选项当时全都不对，已按实测改正。

实测 2：while 里的 continue 会跳过 ++i（经典死循环）

int i = 0, guard = 0;
while (i < 5) {
    if (++guard > 20) break;    // 保险丝，否则真死循环
    if (i % 2 == 0) continue;   // ← i 恒为 0，永远走这条
    ++i;                        // ← 永远执行不到
}

实测：i=0，保险丝跑了 21 次。

为什么 for 不会这样：for (init; cond; expr) 的 continue 跳到的是 expr（++i），不是 cond；while 的 continue 直接跳回条件判断，把递增语句留在了循环体里。所以在 while 里做递增，要么放在最前面，要么改用 for。

实测 3：跳出多层循环，三种写法耗时完全相同

400×400 矩阵、命中在 (100,100)、20 轮（-O2）：

写法 实测
goto found; 0.044 ms/轮
标志位 bool hit + 外层 && !hit 0.042 ms/轮
抽成函数用 return 0.042 ms/轮

结论：性能上没有区别（编译器把三者优化成同样的代码），选可读性最好的。工程上推荐「抽成函数 + return」——既避免 goto，又让函数可以复用、可单测。goto 留到 C 风格的资源清理里。

实测 4：C++ 禁止 goto 跳过带初始化的声明，C 不管

goto label;
int x = 10;     // C++：error: cannot jump from this goto statement to its label
label:
return x;

同一个文件改成 .c 用 clang -std=c11 编译：无错误也无警告（跳过初始化后 x 是不确定值，属于 UB 风险）。

同样的限制也出现在 switch 里（跳到某个 case 会绕过前一个 case 的初始化）：

error: cannot jump from switch statement to this case label    ← case 1: int x = 10;  case 2: ...

修正办法：给 case 加一对花括号 case 1: { int x = 10; ... break; }，把变量作用域锁在这一支里。

实测 5：goto cleanup vs RAII（同一个函数的两种写法）

// C 风格：每个失败点跳到对应标签，逆序释放
int with_goto(int fail_at) {
    FILE* f = fopen(...); if (!f) return -1;
    char* buf = malloc(1024); if (!buf) { fclose(f); return -2; }
    if (fail_at == 1) goto free_buf;
    /* 业务逻辑 */
    free(buf); fclose(f); return 0;
free_buf:
    free(buf); fclose(f); return -3;
}

// C++ 风格：所有权交给对象，失败点直接 return
int with_raii(int) {
    auto f = std::unique_ptr<FILE, int(*)(FILE*)>(fopen(...), fclose);
    if (!f) return -1;
    auto buf = std::unique_ptr<char[]>(new char[1024]);
    /* 业务逻辑 */
    return 0;                      // 什么都不用手写
}

实测两者都能正确释放（valgrind 之外，最直观的证据是「新增一条失败路径时，goto 版要加一行跳转，RAII 版什么也不用改」）。维护成本才是差距所在：goto 版的清理逻辑与出错点数量成正比，RAII 版是常数。

HFT / 嵌入式视角

  • break / continue 本身的分支几乎免费：循环里的分支目标固定，CPU 分支预测器命中率极高。真正贵的是「数据依赖的分支」（分支走向由行情数据决定、无法预测），见 5.3 的分支预测实测。
  • 别用异常当跳转：throw/catch 实测约 4 μs/次，比错误码慢三个数量级（详见 5.6），在热路径上用异常跳出深层循环是灾难。
  • 嵌入式里 goto cleanup 仍是主流：很多项目 -fno-exceptions -fno-rtti，没有 RAII 的替代（或者团队禁用动态分配），Linux 内核风格就是最稳妥的选择；C++ 侧有了 RAII 之后，goto 的唯一正当理由基本消失。
  • goto 的一个真实用途：生成状态机 / 解析器，以及内核里跨越多层的错误回滚——记住它只在同一函数内可用。

常见错误

  1. break/continue 只对最内层生效：嵌套循环里 break 只跳出内层，外层继续。想一次跳出多层要用标志位或 goto，或把内层抽成函数用 return。
  2. continue 误用于 switch：continue 只对循环生效，switch 里的 continue 会作用到外层循环，不是 switch 本身。容易和 break（对 switch 生效）混淆。
  3. 滥用 goto 制造意大利面条代码：goto 用于错误清理是合理的，但用它代替正常循环/分支会让控制流不可读。C++ 有 RAII、异常、lambda 后，goto 几乎没有正当理由。
  4. 在 while 里用 continue 却把递增写在后面：while (i < 5) { if (skip) continue; ++i; } —— continue 跳回条件判断，++i 永远执行不到，直接死循环（实测 2）。修正：改用 for（continue 会先执行 ++i），或把递增移到循环体开头。
  5. 让 goto 跳过带初始化的声明：C++ 直接编译错误 cannot jump from this goto statement to its label（实测 4），switch 的 case 之间同理。修正：给 case 加 {}、把变量声明提到跳转之前，或改用 RAII + 提前 return。

1. 选择题：下面代码输出什么？

for (int i = 0; i < 3; ++i) {
    for (int j = 0; j < 3; ++j) {

        std::cout << i << j << " ";

}
  • A) 00 01 10 11 20
  • B) 00 01 10 11 20 21
  • C) 00 01 10 11
  • D) 00 01
  • E) 00 01 10
答案

E) 00 01 10（实测输出，原题 A~D 全部错误，已按实测补上 E）。

逐轮推算（break 只跳出内层 j 循环）：

i 打印 何时 break
0 00、01 j=2 时 0+2=2
1 10 j=1 时 1+1=2
2 无 j=0 时 2+0=2，一进来就 break

2. 判断题：C++ 中 goto 可以跳到另一个函数里的标签。

答案

错误。goto 只能在同一函数内跳转，不能跨函数。跨函数跳转 C 用 setjmp/longjmp（危险），C++ 有异常机制 throw/catch，都不鼓励日常使用。

3. 踩坑题：下面代码想跳过偶数只处理奇数，但有 bug，找出来。

switch (x % 2) {
    case 0: continue;     // 想跳过偶数
    case 1: process(x);
}

（这段代码在 for 循环内部）

答案

continue 不作用于 switch，它作用到外层 for 循环。这里恰好能达到"跳过本次循环"的效果，但语义混乱——读代码的人会以为 continue 作用于 switch。更严重的是：如果这段代码不在循环里，case 0: continue; 直接编译错误。建议：switch 里用 break，跳过逻辑用 if 或把 switch 抽成函数用 return。

4. 应用题：用 goto 写一个 Linux 内核风格的错误清理函数：打开文件 → 分配内存 → 加锁，任一步失败都跳到对应清理点逆序释放。体会这种模式与 C++ RAII 的对比。

答案 
int do_work() {
    FILE* f = fopen("a.txt", "r");
    if (!f) return -1;

    char* buf = (char*)malloc(1024);
    if (!buf) goto close_f;

    if (!lock()) goto free_buf;

    // ... 业务逻辑 ...
    int rc = 0;

    unlock();
free_buf:
    free(buf);
close_f:
    fclose(f);
    return rc;
}

C++ 中用 RAII（析构函数自动释放）或 unique_ptr/lock_guard，完全不需要这套 goto cleanup——这是 C→C++ 最大的解放之一。

5. 踩坑题：下面循环想统计奇数之和，实际会发生什么？

int i = 0, sum = 0;
while (i < 10) {
    if (i % 2 == 0) continue;
    sum += i;
    ++i;
}
答案

死循环。i=0 是偶数 → continue 直接跳回 while (i < 10) 的判断，++i 永远执行不到，i 恒为 0。

三种修法： 1. 改成 for (int i = 0; i < 10; ++i) { if (i % 2 == 0) continue; sum += i; } —— for 的 continue 会先执行 ++i； 2. 把 ++i 挪到循环体最前面（continue 之前）； 3. 干脆不用 continue：if (i % 2 != 0) sum += i;。

实测：在 while 里加保险丝后跑 21 次仍未退出，i 一直是 0。

6. 判断题：跳出多层循环时，goto 比标志位快得多，所以性能敏感的代码应该用 goto。

答案

错。实测（400×400 矩阵、命中在 (100,100)、20 轮 -O2）：goto 0.044 ms/轮、标志位 0.042 ms/轮、抽函数 return 0.042 ms/轮——三者持平（goto 甚至略慢一点，属于噪声）。编译器把三种写法优化成了同样的代码。

选型应该看可维护性：优先「抽成函数 + return」（可复用、可单测），其次是标志位；goto 留给 C 风格的资源清理。这条结论和 5.4 遍历写法 那组实测同源：控制流的写法几乎不影响性能，影响性能的是数据访问模式和能不能预测。

5.6

try 语句块和异常处理

本节讲什么

C++ 的异常机制：throw 抛出异常、try/catch 捕获处理、<stdexcept> 标准异常类层次。这是 C 语言完全没有的特性，是 C 转 C++ 的重要新增。

核心用法

三件套

#include <stdexcept>

// 1. throw：抛出异常
double divide(double a, double b) {
    if (b == 0)
        throw std::runtime_error("division by zero");
    return a / b;
}

// 2. try / 3. catch：捕获并处理
int main() {
    try {
        std::cout << divide(10, 0);
    } catch (const std::runtime_error& e) {
        std::cerr << "Error: " << e.what() << std::endl;
    }
}

标准异常层次（<stdexcept>）

std::exception                    // 所有标准异常的基类（<exception>）
├── std::logic_error              // 程序逻辑错误，可在编译期发现
│   ├── std::invalid_argument     // 无效参数
│   ├── std::domain_error         // 域错误
│   ├── std::length_error         // 超出最大长度
│   └── std::out_of_range         // 下标越界（vector::at 等）
└── std::runtime_error            // 运行时错误，运行期才能发现
    ├── std::overflow_error       // 上溢
    ├── std::underflow_error      // 下溢
    └── std::range_error          // 范围错误

异常与栈展开

throw 后，程序沿调用栈逐层退出（stack unwinding），直到找到匹配的 catch。沿途所有局部对象会按构造的逆序析构（这是 RAII 能工作的基础）。如果一直没匹配的 catch，调用 std::terminate 终止程序。

和 C 的区别

维度 C C++
异常机制 ❌ 完全没有 ✅ throw/try/catch
错误处理方式 返回错误码 + errno 返回码 / 异常（二选一）
跨函数跳转 setjmp/longjmp（不调用析构，危险） 异常栈展开（自动析构，安全）
资源清理 手动 goto cleanup RAII 析构自动清理
资源泄漏风险 高（忘了清理就泄漏） 低（析构保证执行）

C 程序员的核心认知转变：

  1. C 靠"检查每个函数返回值"防错，容易漏检；C++ 异常让错误"自动冒泡"，不用每层都查返回值。
  2. C 的 setjmp/longjmp 跳转不会调用析构函数（C 没有析构），但 C++ 绝不能用 longjmp 跨越有析构的对象——会跳过析构导致泄漏/不变式破坏。C++ 中只用异常，不用 longjmp。
  3. 异常的代价：抛异常时有运行时开销（栈展开），但不抛时几乎零开销（现代 C++ 实现）。HFT 热路径通常禁用异常（-fno-exceptions）。
/* C 风格：每层都要检查返回值 */
int rc = f1();
if (rc) { cleanup1(); return rc; }
rc = f2();
if (rc) { cleanup2(); cleanup1(); return rc; }

// C++ 异常风格：错误自动冒泡，RAII 自动清理
void work() {
    Resource r1 = acquire1();      // RAII，析构自动释放
    Resource r2 = acquire2();      // 抛异常时 r2 先析构，再 r1
    do_something();                // 失败则 throw，r2、r1 自动释放
}   // 正常退出也自动释放

底层实现与实测

以下均为本机实测（Apple clang 23.1.0，arm64，-std=c++17 -O2，libc++）。异常的成本要分三笔账算：写 try 的成本（≈0）/ 抛出的成本（很贵）/ 二进制与可移植性成本。

实测 1：不抛异常时，try/catch 真的是零成本

100 万次调用，被调函数 noinline 且从不抛出：

写法 实测（100 万次）
带 try { s += work(i); } catch (...) {} 2844.0 μs
不带 try（直接 s += work(i);） 2843.8 μs

差 0.2 μs / 100 万次 = 0.0002 ns/次，在噪声里。这就是所谓 zero-cost exception handling：正常路径上不执行任何指令，编译器改用一张离线的表（landing pad + 类型信息）来记录"哪里能捕获什么"，只在真正抛出时才去查表。

反面：代价转移到了二进制体积和抛出路径。表中信息常驻 .rodata/.eh_frame，所以"零成本"是零时间成本，不是零空间成本。

实测 2：抛一次异常 ≈ 4 μs，比错误码慢三个数量级

路径 实测（10 万次） 单次
throw std::runtime_error("x") + catch 423 310 μs ≈ 4.23 μs
返回错误码 int& ec 93.7 μs ≈ 0.94 ns

约 4500 倍。 4 μs 够做什么？在 3 GHz 上是 12 000 个周期；一笔订单从收包到回包的预算常常只有几微秒——在热路径上抛一次异常，等于把延迟预算整个吃掉。

原因：抛出要走 __cxa_throw → 查表找 landing pad → 逐帧析构 → malloc 异常对象（libc++ 有应急缓冲但仍要走分配路径）→ __cxa_begin_catch。这些都是不可内联、不可预测的调用。

实测 3：栈展开按构造逆序析构（RAII 的地基）

void inner() { Probe a("inner-a"); Probe b("inner-b"); throw std::runtime_error("boom"); }

实测输出：

+ 构造 inner-a
+ 构造 inner-b
- 析构 inner-b（栈展开调用）
- 析构 inner-a（栈展开调用）
catch: boom

逆序析构正是 lock_guard / unique_ptr 能在异常下正确工作的原因。C 的 longjmp 不保证这件事（它直接跳走，不跑任何清理），所以在 C++ 里跨越对象用 longjmp 是 UB。

实测 4：noexcept 函数里抛出 → std::terminate（不是"捕获不到"那么温和）

auto f = []() noexcept { throw std::runtime_error("in noexcept"); };

warning: 'operator()' has a non-throwing exception specification but can still throw [-Wexceptions]
libc++abi: terminating due to uncaught exception of type std::runtime_error: in noexcept
exit=134        ← 128 + SIGABRT(6)

编译器会在编译期警告，运行期直接 abort。所以 noexcept 是契约不是装饰：标了就得保证不抛（析构函数、swap、move 构造都该标）。

实测 5：-fno-exceptions 下异常代码根本编译不过

error: cannot use 'throw' with exceptions disabled
error: cannot use 'try' with exceptions disabled

嵌入式/低延迟项目常用这个开关（连同 -fno-rtti）。此时代码要整体改成错误码风格（std::error_code / expected<T,E> / 返回 bool），STL 容器也会退化（vector::at 不可用或行为不同）。选型要在项目初期定，后期切换成本极高。

HFT / 嵌入式视角

  • 热路径禁异常，冷路径可以用：启动/配置加载/策略初始化用异常很舒服（错误自动冒泡、信息完整）；撮合主循环、行情解析这类纳秒预算的地方一律错误码。实测 2 的 4 μs 就是分界线。
  • 异常不能跨线程、不能跨回调：抛到 C 回调（如 qsort 比较器、libcurl 回调）外面基本是 terminate；跨 shared library 边界抛异常还要求 ABI 一致。
  • -fno-exceptions 是嵌入式常态：Flash/RAM 紧、无 RTTI、启动时间敏感。替代方案是错误码 + [[nodiscard]]（强制调用方检查返回值，避免"漏检"这个 C 风格的最大弱点）。
  • noexcept 不只是文档：它让编译器省掉展开表、让 vector 扩容敢用移动构造（移动构造函数标 noexcept 才有意义，见 9.2 底层机制）。
  • 别用异常做控制流（实测 2 是硬证据）："用 throw 跳出三层循环"比 goto 慢三个数量级。

常见错误

  1. catch 按值捕获大对象 / 漏写 &：catch (std::exception e) 会拷贝切掉派生类型（slicing），丢失 what() 的真实信息。修正：用 catch (const std::exception& e) 引用捕获。
  2. 异常析构时再抛异常导致 terminate：析构函数里抛异常（栈展开过程中）会直接调用 std::terminate 终止程序。修正：析构函数必须 noexcept，内部异常要 try/catch 吞掉。
  3. 用异常做正常控制流：拿 throw 当 goto 用，性能差且语义混乱。异常只用于"真正的错误"，正常分支用返回值/optional。实测代价约 4 μs/次（比错误码慢约 4500 倍），在热路径上是灾难。
  4. 标了 noexcept 却可能抛：编译期只有警告（-Wexceptions），运行期直接 std::terminate（实测 exit=134）。noexcept 是契约——要么保证不抛，要么别标；析构函数、移动构造、swap 都应标 noexcept 并真的不抛。
  5. 以为 try/catch 本身很贵：实测 100 万次调用，带 try 2844.0 μs vs 不带 2843.8 μs——零成本。贵的是"抛出"（4 μs）和二进制体积，不是"写 try"。所以别因为怕开销而放弃异常，该判断的是抛出频率。

能否 dynamic_cast 到 logic_error   : 是
能否 dynamic_cast 到 runtime_error : 否

而且后果比"没捕获"更严重——没有任何 catch 匹配时会 std::terminate：

libc++abi: terminating due to uncaught exception of type std::out_of_range: x
exit=134

正确写法：catch (const std::logic_error&) 或直接 catch (const std::exception&)（兜底捕获所有标准异常）。基类引用捕获派生类异常这条规则本身没错（用 const& 也不 slicing），但基类必须真的是基类。

2. 判断题：C++ 中可以用 setjmp/longjmp 替代异常，效果一样。

答案

错误。longjmp 跳转时不会调用栈上对象的析构函数，会破坏 RAII 保证，导致资源泄漏或不变式破坏。C++ 中处理错误必须用 throw/catch，绝不能用 longjmp 跨越有析构的对象。

3. 踩坑题：下面代码在某些情况下会崩溃，为什么？

class Conn {
    ~Conn() {
        close(handle_);        // close 可能抛异常
        log("closed");
    }
};
void f() {
    Conn c;
    throw std::runtime_error("err");   // 栈展开，析构 c
}
答案

如果 close(handle_) 抛异常，而此时正处于异常栈展开过程（f 抛出异常正在展开），析构函数里再抛异常会导致 std::terminate 直接终止程序。修正：析构函数必须 noexcept，内部用 try/catch 吞掉 close 的异常：

~Conn() noexcept {
    try { close(handle_); } catch (...) { /* 吞掉 */ }
    log("closed");
}

4. 应用题：写一个安全的数组访问函数 at(arr, i)，越界时抛 std::out_of_range，正常时返回元素引用。说明与 C 风格"返回错误码"的对比。

答案 
int& at(std::vector<int>& v, size_t i) {
    if (i >= v.size())
        throw std::out_of_range("index " + std::to_string(i)
                                + " >= size " + std::to_string(v.size()));
    return v[i];
}

C 风格要返回错误码，但函数又想返回元素——只能用输出参数 int* out + 返回 int 错误码，调用啰嗦且容易漏检。异常版本调用者写正常路径，错误统一在 catch 处理，代码更清晰。HFT 热路径禁异常时，退回 v[i]（不检查）或自定义 expected<T,E> 类型。

5. 判断题：下面两句对不对？

(a) try/catch 块本身有可观的运行时开销，所以热路径不能写 try。 (b) 标了 noexcept 的函数如果抛异常，异常会继续往外冒泡，跟没标一样。

答案

两句都错。

(a) 实测：100 万次调用，带 try/catch 2844.0 μs vs 不带 2843.8 μs，差 0.0002 ns/次（零成本异常处理）。贵的是"抛出"——约 4.23 μs/次，比错误码的 0.94 ns 慢约 4500 倍。所以判断标准是抛出频率，不是有没有写 try。

(b) 标了 noexcept 后抛出会直接 std::terminate，进程 abort：

libc++abi: terminating due to uncaught exception of type std::runtime_error: in noexcept
exit=134

而且编译期会先给警告：'operator()' has a non-throwing exception specification but can still throw [-Wexceptions]。

6. 应用题：你的行情解析函数每秒要处理 50 万条消息，其中约 0.1% 是坏包（字段缺失）。用异常还是错误码？给出理由和大致数字。

答案

用错误码（或 expected<T,E>），不要用异常。

算一笔账：50 万条/秒 × 0.1% = 500 次坏包/秒。 - 异常方案：500 × 4.23 μs ≈ 2.1 ms/秒 花在栈展开上；更要命的是抖动——一旦坏包连续到达，单次解析延迟从几百纳秒跳到 4 μs，P99/P999 延迟直接爆掉，这在撮合系统里比吞吐损失更致命。 - 错误码方案：500 × 0.94 ns ≈ 0.5 μs/秒，且延迟恒定，不会因为坏包而抖动。

实践建议： 1. 热路径（解析、撮合、风控判定）：错误码 + [[nodiscard]]，强制调用方检查； 2. 冷路径（启动配置、策略加载、文件 IO）：用异常，代码清晰、错误信息完整； 3. 边界处做转换：冷路径的异常在模块边界 catch 掉，转成热路径的错误码； 4. 如果整个项目定了 -fno-exceptions，就统一用错误码/expected，别混用。

一句话：异常的成本不在频率，在"一旦发生就是 4 μs 的延迟尖刺"——对延迟敏感的系统，尖刺比平均值可怕得多。

Q3异常基础
#include <stdexcept>
double divide(int a, int b) {
    if (b == 0)
        throw std::runtime_error("div by zero");
    return static_cast<double>(a) / b;
}
int main() {
    try {
        std::cout << divide(10, 0);
    } catch (const std::runtime_error &e) {
        std::cout << "Error: " << e.what();
    }
}

输出是什么？catch 为什么要用引用？

答案与复习指引

输出： Error: div by zero

catch 用引用的原因： 1. 避免拷贝异常对象（可能派生类切片——按值 catch 基类会丢失派生部分） 2. 多态——catch(const std::exception&) 能捕获所有派生自 std::exception 的异常

和 C 的区别： C 用返回值/errno 错误处理，或 setjmp/longjmp（不能析构栈对象）。C++ 异常在栈展开时自动调用析构函数（RAII）。

Q4goto 与作用域
void f() {
    goto label;          // A
    std::string s = "hi";
label:
    std::cout << s;      // B: s 已构造？
}

A 行合法吗？B 行 s 的状态是什么？

答案与复习指引

A 行编译错误。 C++ 规定 goto 不能跳过带析构函数的变量的初始化（如 std::string）。因为跳过构造意味着 s 未初始化，但离开作用域时仍会析构——UB。

和 C 的区别： C 没有构造/析构概念，goto 可以跳过任何声明。C++ 的限制是 RAII 的延伸——保护对象生命周期完整性。

教训： C++ 中尽量避免 goto，用 break/continue/return/异常替代。
