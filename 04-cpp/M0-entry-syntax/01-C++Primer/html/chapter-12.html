本章探讨动态内存的分配和管理，重点推荐 C++11 智能指针机制，提高代码鲁棒性并避免内存泄漏。

章节摘要

动态内存管理：智能指针 shared_ptr（共享所有权）、unique_ptr（独占所有权）、weak_ptr（弱引用不增加引用计数），以及直接内存管理 new/delete、动态数组与 allocator。

和 C 的区别

C C++
malloc/free new/delete（调用构造/析构）
手动管理生命周期 RAII 智能指针自动释放
无弱引用 weak_ptr 打破环引用
valgrind 查泄漏 智能指针从源头避免泄漏
12.1

智能指针

本节讲什么

C++ 的智能指针：unique_ptr（独占）、shared_ptr（共享，引用计数）、weak_ptr（弱引用）。它们用 RAII 自动管理动态内存，几乎消灭内存泄漏和悬垂指针。这是 C 程序员必须重点学的——C 的 malloc/free 全靠手动，错了就泄漏或崩溃。

unique_ptr 的规则很简单（独占 + 移动），本节更多的篇幅在 shared_ptr 和 weak_ptr：控制块是什么、为什么"一个对象只能有一个控制块"、enable_shared_from_this 解决什么问题、线程安全到底安全到哪一层、以及每一次拷贝要付多少纳秒。这些是真正会在工程里咬人的地方。

核心用法

unique_ptr：独占所有权

#include <memory>
std::unique_ptr<int> p = std::make_unique<int>(42);   // C++14
*p = 10;
// p 独占，不能拷贝
// std::unique_ptr<int> p2 = p;   // 编译错误
std::unique_ptr<int> p2 = std::move(p);   // 只能移动，p 变 nullptr
// p2 出作用域自动 delete，不用手动
  • 零开销抽象（与裸指针同大小、同性能，实测见下文内存布局一节）
  • 所有权清晰：谁持有谁负责释放

构造必须显式：unique_ptr 的构造函数是 explicit

std::unique_ptr<Entity> e = new Entity();   // ❌ 编译失败

clang 23 + libc++ 实测报错，直接指向标准库源码：

error: no viable conversion from 'Entity *' to 'std::unique_ptr<Entity>'
note: explicit constructor is not a candidate
    explicit unique_ptr(pointer __p) _NOEXCEPT   ← libc++ __memory/unique_ptr.h:163

必须写成 std::unique_ptr<Entity> e(new Entity());（直接初始化）或 auto e = std::make_unique<Entity>();（C++14 起推荐）。

有意思的是标准委员会的取舍：同一个类里 unique_ptr(nullptr_t) 没有加 explicit，std::unique_ptr<Entity> e = nullptr; 实测合法。接管裸指针的所有权是危险动作，必须你显式写出来；"空就是空"语义无害，放行。 完整讨论见 7.5 构造函数 · explicit。

shared_ptr：共享所有权（引用计数）

std::shared_ptr<int> p1 = std::make_shared<int>(42);
std::shared_ptr<int> p2 = p1;       // 引用计数 +1
std::cout << p1.use_count();        // 2
// p1、p2 都释放后，引用计数归 0，对象 delete
  • 多个 shared_ptr 共享同一对象
  • 引用计数有原子操作开销（比 unique_ptr 慢，实测数据见下）
  • 适合"所有权不明确、多处共享"的场景

控制块：shared_ptr 真正的开销所在

shared_ptr 比 unique_ptr 多出来的那一根指针，指向的是控制块（control block）——一块独立的堆内存，里面大致装着：

控制块内容 作用
强引用计数（use_count） 多少个 shared_ptr 持有对象；归 0 → 析构对象
弱引用计数（weak_count） 多少个 weak_ptr 观察它；强、弱都归 0 → 释放控制块本身
删除器（deleter） 类型擦除后存在这里
分配器（allocator） 同上

这不是抽象描述，libc++ 的控制块就是两个 long（__memory/shared_count.h）：

class __shared_count {  long __shared_owners_;      };            // :50  强计数
class __shared_weak_count : public __shared_count {
    long __shared_weak_owners_;                                   // :82  弱计数
    void __add_weak() { __libcpp_atomic_refcount_increment(__shared_weak_owners_); }   // :99
    void __release_shared() {                                     // :100
        if (__shared_count::__release_shared())   // 强计数归零 → 销毁对象
            __release_weak();                     // 同时自动放掉自己占的那一份弱计数
    }
};
long use_count() const { return __atomic_load_n(&__shared_owners_, __ATOMIC_RELAXED) + 1; }  // :74

三个能从源码直接读出来的事实：

  1. 两个计数是分开的，弱计数管的是控制块本身的寿命。
  2. 强计数归零时会顺带减一次弱计数（__release_shared() 里那行）——所以"弱计数 = weak_ptr 个数 + 1（shared_ptr 群体自己占一份）"，最后一批 shared_ptr 走人时，这一份才交还。
  3. use_count() 的实现是 relaxed load——它只给一个快照，并发场景下不可靠，别拿它做判断，expired() 才是对的（libc++ 里 expired() 就是 use_count() == 0，shared_ptr.h:1228）。

控制块只在三种情况下被创建（记住这个，能避开 90% 的 shared_ptr 事故）：

  1. make_shared<T>(...) —— 对象与控制块同一块内存
  2. 从裸指针构造 shared_ptr<T>(new T) / shared_ptr<T>(raw) —— 对象独立，控制块另分配
  3. 从 unique_ptr<T>&& 移动构造 —— 接管所有权并新建控制块

铁律：同一个对象只能有一个控制块。 一旦让同一个裸指针生成两个控制块，两个计数各自归零，就会 delete 两次：

T* raw = new T{42};
std::shared_ptr<T> a(raw);
std::shared_ptr<T> b(raw);     // 第二个独立控制块

实测输出（clang 23 / libc++）：

  a.use_count=1  b.use_count=1  (都是 1 —— 各自一个控制块)
  [析构] T(42)
  [析构] T(42)            ← 析构两次，未定义行为

同样的错误换成成员函数里 return std::shared_ptr<Bad>(this); 的形式，实测直接 SIGABRT（退出码 134）。所以规则很硬：一旦把裸指针交给 shared_ptr，之后就只能通过拷贝 shared_ptr 来传播，绝不能再拿 get() 去造第二个。

删除器：shared_ptr 类型擦除，unique_ptr 不擦除

这是两者一个容易被忽略的差别，实测（同一个 64 字节的删除器类型）：

sizeof
shared_ptr<int>（配任意删除器：lambda / 函数指针 / 64 字节仿函数） 16（全一样）
unique_ptr<int> 8
unique_ptr<int, BigDeleter>（64 字节状态） 72
unique_ptr<int, void(*)(int*)> 16

unique_ptr 的删除器是类型的一部分（编译期绑定，零开销但会撑大对象）；shared_ptr 的删除器被类型擦除后塞进控制块——代价是运行时间接调用，好处是 shared_ptr<T> 的类型与删除器无关，可以放进同一个容器、跨 API 传递。

enable_shared_from_this：安全地交出"指向自己的 shared_ptr"

上面那条铁律带来一个实际问题：成员函数内部只有 this，怎么返回一个共享所有权的 shared_ptr？不能写 shared_ptr<T>(this)（那就是铁律禁止的第二个控制块），正确做法是继承 std::enable_shared_from_this<T> 后调 shared_from_this()：

struct Good : std::enable_shared_from_this<Good> {
    std::shared_ptr<Good> self() { return shared_from_this(); }   // 复用已有控制块
};

对照实测：

写法 结果
shared_ptr<Bad>(this) use_count 各为 1；析构两次 → SIGABRT 134
shared_from_this() use_count = 2（同一控制块）；析构一次 ✅
栈对象上调 shared_from_this() 抛 std::bad_weak_ptr: bad_weak_ptr
构造函数里调 shared_from_this() 同样抛 bad_weak_ptr（此时还没有任何 shared_ptr 指向它）

后两条是同一个原因：shared_from_this() 依赖对象内部那个 weak_ptr，而它要等 shared_ptr 构造完成才会被赋值。配套的工程写法是把构造函数设为私有、只暴露工厂函数，从类型层面杜绝栈对象和 shared_ptr<T>(this)：

struct Safe : std::enable_shared_from_this<Safe> {
    static std::shared_ptr<Safe> create() { return std::shared_ptr<Safe>(new Safe); }
    std::shared_ptr<Safe> self() { return shared_from_this(); }
private:
    Safe() = default;      // 强制走工厂
};

线程安全：到底安全到哪一层

"shared_ptr 线程安全"这句话是有严格边界的。用 ThreadSanitizer（-fsanitize=thread）实测三种场景：

场景 TSan 结果 结论
① 每个线程持自己的副本，并发拷贝/销毁（4 线程 × 10000 次） 无告警，use_count() 最终精确回到 1 引用计数的增减是原子的 ✅
② 每个线程持自己的副本，但并发写对象内部字段 data race（heap block） 对象本身不受任何保护 ❌
③ 多线程读写同一个 shared_ptr 变量（一个 reset、一个拷贝） data race（stack of main thread） shared_ptr 实例本身不是线程安全的 ❌

拆开说就是三条：

  1. 不同 shared_ptr 实例（哪怕指向同一对象）并发读写是安全的——计数是原子的。
  2. 同一个 shared_ptr 实例被多线程同时读写不安全（跟 int 一样需要加锁 / atomic_load 系列自由函数）。
  3. 指向的对象本身完全不受保护——shared_ptr 只管生命周期，不管数据竞争。实测 4 线程各加 2000 次，TSan 下 counter 只有 4000（应为 8000）；而 -O2 不开 TSan 时恰好是 8000——这正是竞态最阴的地方：它不保证出错。

HFT 提醒：别把 shared_ptr 当成"线程安全的对象容器"。行情回调线程与策略线程共享一个 OrderBook 时，shared_ptr 只保证它活着，读写字段该加锁还得加锁。

性能实测：每一次拷贝都在做原子操作

本机实测（clang 23.1.0，-O2，arm64，2000 万次循环）：

操作 耗时
裸指针赋值（基准） ~0 ns（被优化掉）
unique_ptr move ~0 ns（编译期所有权转移，运行时无操作）
shared_ptr 拷贝 + 析构 ≈ 14.9 ns
weak_ptr::lock() 一次 ≈ 13.8 ns
weak_ptr::expired() 一次 ≈ 0.31 ns（只读计数）
函数传值 shared_ptr ≈ 14.9 ns
函数传 const shared_ptr& ~0 ns（不计数）

单次 15 ns 看着小，但换算一下：一秒里光是拷贝 shared_ptr 6700 万次就吃掉 1 秒 CPU。热路径上的两条硬规则——

  • 函数参数能传 const shared_ptr& 就别传值（传值只是为了"参与所有权"，大多数时候并不需要）；
  • 只在跨线程移交所有权时才值得为原子计数付这个钱，其余一律 unique_ptr 或栈对象。

其他常用操作

auto po = std::make_shared<Outer>();
std::shared_ptr<int> pb(po, &po->b);   // 别名构造：指向成员 b，但共享 Outer 的控制块
// po 出作用域后对象不析构 —— pb 把整个 Outer 保活了（实测：Outer 在 pb 释放时才析构）

auto arr = std::make_shared<int[]>(5); // C++20 起 make_shared 支持数组；C++17 可用
                                       // shared_ptr<int>(new int[5], std::default_delete<int[]>())
std::shared_ptr<Outer> sp = std::move(up);   // unique_ptr → shared_ptr：此时才建控制块

别名构造那条实测很关键：shared_ptr<int> 指向的是一个 int 成员，但它持有的是整个 Outer 的控制块，所以外层对象会被延长生命周期——这是 shared_ptr 区别于裸指针的核心能力之一。

weak_ptr：弱引用（不增加计数）

std::shared_ptr<int> sp = std::make_shared<int>(42);
std::weak_ptr<int> wp = sp;    // 不增加计数
if (auto p = wp.lock()) {      // lock() 尝试升级为 shared_ptr
    std::cout << *p;           // 对象还活着
} else {
    // 对象已释放
}
  • 解决 shared_ptr 循环引用（互相引用导致永不释放）
  • 观察 shared_ptr 但不拥有

weak_ptr 的三个操作与 lock() 的原子性

weak_ptr 不能直接解引用（它没有 operator*、operator->，也没有 get()）——这是故意的：想用就必须先"升级"，而升级会失败，逼你处理"对象已经没了"这种情况。实测三种写法的报错原文：

std::weak_ptr<S> wp = sp;
wp->x;      // error: member reference type 'std::weak_ptr<S>' is not a pointer
*wp;        // error: indirection requires pointer operand ('std::weak_ptr<S>' invalid)
wp.get();   // error: no member named 'get' in 'std::weak_ptr<S>'

标准里的说法更直接（cppreference）："It is not possible to access the stored pointer in a weak_ptr without locking it into a shared_ptr." 而 lock() 的语义是临时所有权——升级成功后，即便原来的 shared_ptr 全部销毁，对象也会活到你这个临时 shared_ptr 析构为止。

操作 语义 实测耗时
expired() 对象是否已释放（use_count() == 0） ≈ 0.31 ns
lock() 原子地尝试升级；成功返回 shared_ptr（计数 +1），失败返回空 ≈ 13.8 ns
use_count() 当前强计数（只用于调试，别拿它做判断） —

lock() 的原子性是 weak_ptr 存在的全部意义：多线程下"检查"和"获取"必须是一步完成的，否则中间会被别的线程把对象释放掉。所以反模式是：

if (!w.expired()) {          // ① 检查：此刻还活着
    auto s = w.lock();       // ② 获取：中间可能已被其他线程 reset
    use(s);                  //    这里 s 可能是空的
}

两步之间是个窗口。实测（一个线程 reset()，另一个线程循环 lock() 后不判空直接解引用）：稳定 SIGSEGV，退出码 139；而改成 if (auto s = w.lock()) { ... } 的写法，200 轮 × 20 万次全部安全通过。

正确写法永远只有一种：lock() 的返回值当场判空，判空和使用之间不能有其他判断。

if (auto s = w.lock()) {   // 升级成功 + 判空，一步完成
    use(*s);               // 在 s 的作用域内，对象保证存活
}                          // s 析构 → 计数 -1

对象死了，控制块还活着

weak_ptr 指向的是控制块，不是对象。所以对象的析构和控制块的释放是两个独立时刻：

作用域内：expired=0, use_count=1
  [析构] Outer              ← 强计数归 0，对象先析构
作用域外：expired=1
  lock() 返回空? 是

对象已经析构了，weak_ptr 依然有效（expired() 正确返回 true，lock() 正确返回空）——因为控制块要等弱计数也归 0 才释放。这正是前面「make_shared 隐藏代价」那条实测的机制来源：make_shared 把对象和控制块放在同一块内存里，weak_ptr 让控制块活着，就等于让整块内存（含已经析构的对象占的那部分）活着。

思考题：只要还有 weak_ptr 存在，控制块会不会留在内存里？——会，而且是一块实打实占用着的堆内存。 用重载的 operator new/delete 把每次分配/归还的地址打出来，shared_ptr<Obj>(new Obj) 场景（Obj 含 64 字节）的完整时间线：

      [分配] 0x145604bc0  64 字节      ← 业务对象
      [分配] 0x145604c40  32 字节      ← 控制块（两个 long + vptr）
  -- sp.reset() --
    [析构] Obj（业务对象销毁）
      [归还] 0x145604bc0               ← 只还了对象那 64 字节
  归还次数 = 1（控制块没还）
  expired()=1  lock()为空? 是  use_count=0   ← weak_ptr 照样能查，查得准
      [归还] 0x145604c40               ← weak_ptr 离开作用域，控制块才还
  总分配 2 次，总归还 2 次

三个结论：

  1. 业务对象和控制块是两块独立内存（make_shared 除外），前者随强计数归零立即释放，后者要等弱计数归零。
  2. 对象没了之后 weak_ptr 还能用，靠的就是这块没被释放的控制块——expired() / lock() 查的是控制块里的计数，不碰对象内存，所以永远安全。
  3. 代价：一个 weak_ptr 至少让 32 字节（控制块）赖在堆上；用 make_shared 的话更狠——实测一次分配 88 字节（64 + 24 对齐后），reset() 后整块都不还，weak_ptr 走了才还。

和裸指针的根本区别：能不能可靠地问"你还活着吗"

这是 weak_ptr 存在的全部理由。裸指针做不到的原因不是"忘了判空"，而是释放之后它连判的资格都没有：

int* p = new int(42);
delete p;
printf("%p，p != nullptr 成立? %s\n", (void*)p, p != nullptr ? "是" : "否");   // → 是
printf("%d\n", *p);     // "看起来有判空保护"的代码，照样读野内存

实测输出 + ASan 报告：

  delete 后 p = 0x6020000009b0，p != nullptr 成立? 是
==61157==ERROR: AddressSanitizer: heap-use-after-free on address 0x6020000009b0
SUMMARY: AddressSanitizer: heap-use-after-free raw_uaf.cpp:8 in main

delete 只把内存还给分配器，不会把 p 改成 nullptr（p 是调用方栈上的一个变量，delete 碰不到它）。那块内存什么时候被复用、被写成什么，完全不受你控制——没有任何可靠手段判断它是否还有效，包括读它的内容（那是 UB，ASan 直接报错）。

weak_ptr 则反过来：它根本不存"对象在哪"这个可失效的信息用于访问，它存的是控制块地址；对象死了控制块还在，expired() 就能给出确定的正确答案。一句话——裸指针问不出"还活着吗"，weak_ptr 问得出。

多线程下的四个坑（expired() / lock()）

思考题："expired() 和 lock() 在多线程下有什么坑？"——拆开是四个，前两个致命：

坑 1：两步走 = TOCTOU 窗口。 if (!w.expired()) { auto s = w.lock(); } 的检查和获取之间，别的线程随时可能把最后一个 shared_ptr 释放掉。上面已实测：lock() 后不判空直接解引用，稳定 SIGSEGV（139）。正确写法只有 if (auto s = w.lock()) { ... } 一种。

靠"跑很多次撞运气"是不够有说服力的，所以 examples/12.1-weak-ptr-race.cpp 用两个 atomic 标志把线程顺序钉死，让这个竞态 100% 复现：

std::thread victim([&]{
    if (!wp.expired()) {        // ① 此刻还活着
        while (!released) {}    // ② 窗口：等 killer 抢先释放
        auto s = wp.lock();     // ③ 已经太晚，返回空
        printf("%d", *s);       // ④ 空指针解引用
    }
});
std::thread killer([&]{ while (!checked) {} sp.reset(); released = true; });

实测两种写法的对照：

写法 结果
if (auto s = wp.lock())（默认参数） [正确写法] lock() 返回空 —— 对象已释放，安全避开，退出码 0
if (!wp.expired()) { wp.lock() ... }（./race bad） 退出码 139（SIGSEGV），最后一行 printf 根本打不出来

注意正确写法那一行是故意等到对方释放之后才 lock() 的，照样安全——这正是"原子"的含义：它不依赖你抢得多快。

坑 2：别拿 use_count() 当判断。 libc++ 里它是 __atomic_load_n(..., __ATOMIC_RELAXED)——一次不加同步的 relaxed 读，只是个快照。而且哪怕你读到 use_count() == 1，下一刻它可能就是 0。判存活只能用 expired() / lock()，use_count() 只配出现在调试日志里。

坑 3：lock() 成功后别把裸指针存下来。 lock() 赋予的是临时所有权，只在你持有那个 shared_ptr 期间有效：

if (auto s = w.lock()) {
    cached_raw_ = s.get();     // ❌ s 一析构，cached_raw_ 就悬垂
}

要长期持有就把 shared_ptr 本身存下来（成员也是 shared_ptr），或者干脆重新设计所有权。

坑 4：weak_ptr 实例本身也不是线程安全的。 它跟 shared_ptr 一样是普通对象——多个线程读写同一个 weak_ptr 变量（一个赋值、一个 lock()）同样是 data race，需要 std::atomic<std::weak_ptr<T>>（C++20）或加锁。不同实例并发 lock() 同一个控制块则是安全的（计数是原子的）。

循环引用：父子节点的经典写法

weak_ptr 诞生的原因就是破环。最经典的模式是"父拥有子，子回看父"——父 → 子用 shared_ptr（所有权），子 → 父用 weak_ptr（只是个反向索引）：

struct Parent {
    std::vector<std::shared_ptr<Child>> children;   // 拥有
};
struct Child {
    std::weak_ptr<Parent> parent;                   // 只是回看，不参与生死
    void who_is_my_parent() const {
        if (auto p = parent.lock()) use(p->name);   // 用之前必须 lock()
        else /* 父已不在 */;
    }
};

实测对照（examples/12.1-weak-ptr-cycle.cpp，用重载的全局 operator new/delete 计数）：

父子都 shared_ptr 子用 weak_ptr
离开作用域前 parent.use_count=2、child.use_count=2 parent.use_count=**1**、child.use_count=2
析构 一个都没打 Parent、Child 都正常析构
分配 / 归还 3 次 / 0 次 3 次 / 3 次

"析构没打印"只是间接证据，更硬的是交给 LeakSanitizer：

clang++ -std=c++17 -fsanitize=address -g 12.1-weak-ptr-cycle.cpp -o /tmp/cyc_asan
ASAN_OPTIONS=detect_leaks=1 /tmp/cyc_asan
# SUMMARY: AddressSanitizer: 152 byte(s) leaked in 3 allocation(s).

152 字节、3 个分配——对象、控制块、vector 的内部缓冲区，一个都没还。

判断该在哪一侧放 weak_ptr 的规则很朴素：谁是谁的"组成部分"，谁就有所有权。Parent 消失时 Child 必然无意义 → Parent 拥有 Child；反过来 Child 只是要知道自己挂在谁下面 → 弱引用。两边都"拥有"就一定是错的（树、图、观察者列表都是这个套路）。

用途不止破环：缓存 / 观察者

weak_ptr 的经典用法确实是打破 shared_ptr 循环（见 可跑的例子），但它在"缓存"场景里同样不可替代——缓存想复用对象，但不该延长对象的生命周期：

class SnapshotCache {
    std::unordered_map<std::string, std::weak_ptr<Snapshot>> cache_;   // 只存弱引用
public:
    std::shared_ptr<Snapshot> get(const std::string& sym, long seq) {
        if (auto it = cache_.find(sym); it != cache_.end())
            if (auto hit = it->second.lock()) return hit;   // 还活着 → 复用
        auto fresh = std::make_shared<Snapshot>(sym, seq);  // 已失效 → 重建
        cache_[sym] = fresh;
        return fresh;
    }
};

实测流程：

-- 第一次取 --        [构造] 快照 600519#1
-- 第二次取 --        [命中缓存] 600519#1        同一对象? 是
-- 外部全释放后再取 -- [析构] 快照 600519#1
                     [缓存条目已失效] 600519
                     [构造] 快照 600519#2

如果这里存的是 shared_ptr，缓存就会把所有快照永远钉在内存里——那是另一种形式的泄漏。判断标准：map 只是"索引"，不参与所有权 → 用 weak_ptr。

HFT 提醒：weak_ptr 自身也是 16 字节、lock() 一次 ≈ 13.8 ns（跟 shared_ptr 拷贝同量级）。缓存命中走的是热路径，别在每次行情 tick 上都 lock()——要么把升级后的 shared_ptr 在本次处理中一直持有，要么直接裸指针 + 明确的所有权契约。

以下数据均为本机实测（clang 23.1.0 / libc++，arm64 macOS，-std=c++17），不是"据说"。

大小：谁真的零开销

分配次数：make_shared 到底省在哪

重载全局 operator new 计数后实测：

写法 分配次数
make_shared<Big>() 1
shared_ptr<Big>(new Big()) 2
make_unique<Big>() 1

make_shared 把对象和控制块放进同一块内存，少一次堆分配——这是"优先用 make_*"这条建议的实证依据，不只是异常安全那么简单。

make_shared 的隐藏代价：对象已析构 ≠ 内存已归还

少一次分配不是白来的。还是上面那个结构（Big 含 64 字节），实测对照：

A. make_shared<Big>()            → p.reset() 后：已析构，归还内存 0 次
                                   w 也销毁后：归还内存 1 次
B. shared_ptr<Big>(new Big())    → p.reset() 后：已析构，归还内存 1 次
                                   w 也销毁后：归还内存 2 次

两组的析构函数都执行了（[析构] Big 都打了），但 A 组在 reset() 之后那 64 字节并没还给系统——因为对象和控制块在同一块内存，只要还有一个 weak_ptr 活着，整块都不能释放。B 组对象内存是独立的，引用计数归零就立刻归还，只有控制块留到最后。

什么时候会真的咬到：大对象 + 长期存活的 weak_ptr（典型如"行情快照缓存"——对象不用了但缓存里还挂着弱引用）。此时内存占用会一直挂到最后一个 weak_ptr 消失。

C 程序员最该体会的转变：

C 的动态内存全靠手动，异常或提前返回时极易泄漏：

/* C：手动管理，异常路径泄漏 */
void f() {
    int* p = malloc(sizeof(int));
    do_work();           // 若失败返回
    free(p);             // 这行可能跳过 → 泄漏
}

C++ 智能指针用 RAII 把"释放"绑定到"析构"，任何路径都不泄漏：

void f() {
    auto p = std::make_unique<int>(42);
    do_work();           // 失败返回或抛异常
    // p 析构自动 delete，不泄漏
}

这是 C→C++ 在内存安全上的最大提升——把"易错的资源管理"交给语言机制。

常见错误

  1. shared_ptr 循环引用：A 持有 B 的 shared_ptr，B 持有 A 的 shared_ptr，引用计数永不归 0，内存泄漏。修正：一方用 weak_ptr 打破环。
  2. 用 new 构造 shared_ptr 多次：shared_ptr<int> p(new int); shared_ptr<int> q(new int); —— 若误写 shared_ptr<int> q(p.get()) 会创建两个独立计数，双 delete。修正：用 make_shared，或用 shared_ptr 拷贝构造。
  3. make_unique/make_shared 与直接 new 选择：优先 make_*——一次分配（对象+计数一起）、异常安全、性能更好。除非要自定义删除器或初始化列表，才用 new。
  4. make_shared 配长生命周期 weak_ptr：对象析构了但内存没还——make_shared 把对象和控制块放进同一块内存，只要还有一个 weak_ptr 活着，整块就不能释放（实测：reset() 后对象已析构，但归还内存 0 次）。修正：大对象且要长期留 weak_ptr 时改用 std::shared_ptr<T>(new T)，让对象内存独立，计数归零立即归还。
  5. 用 = 从裸指针构造：std::unique_ptr<T> p = new T(); 编译失败（构造函数是 explicit），很多人以为是"智能指针不能用 new"。修正：std::unique_ptr<T> p(new T()); 或 auto p = std::make_unique<T>();。
  6. 同一个裸指针造出两个控制块：shared_ptr<T> a(raw); shared_ptr<T> b(raw); 或成员函数里 return shared_ptr<T>(this); —— 两个计数各自归零，delete 两次（实测：析构打印两遍；换种写法直接 SIGABRT 134）。修正：传播所有权只能拷贝 shared_ptr；需要"交出指向自己的 shared_ptr"就继承 enable_shared_from_this 并调 shared_from_this()（详见上文）。
  7. expired() 之后再用 lock()：两步之间有窗口，别的线程可能已经释放对象；实测不判空直接解引用会 SIGSEGV（139）。修正：只用一步 if (auto s = w.lock()) { ... }。
  8. 以为 shared_ptr 让对象线程安全：它只保证"对象活着"，不保证"字段读写安全"。TSan 实测 4 线程各加 2000 次，结果 4000（应为 8000）。修正：对象内部字段自己加锁或用原子类型。
  9. 热路径传值 shared_ptr：每次拷贝一次原子加减，实测 ≈ 14.9 ns/次。修正：不需要参与所有权就传 const shared_ptr&（≈0 ns），能用 unique_ptr/栈对象就别升到 shared_ptr。
  10. lock() 成功后把裸指针存下来：lock() 给的是临时所有权，临时 shared_ptr 一析构，get() 出来的裸指针就悬垂。修正：要长期持有就存 shared_ptr 本身。
  11. 父子/树结构里双向都用 shared_ptr：成环泄漏。实测 ASan 报告 152 byte(s) leaked in 3 allocation(s)。修正：按"谁是谁的组成部分"确定所有权方向，反向那一侧用 weak_ptr（详见父子节点经典写法）。

自测题

1. 选择题：下面哪个智能指针不能拷贝，只能移动？ - A) shared_ptr - B) unique_ptr - C) weak_ptr - D) 都能拷贝

答案

B。unique_ptr 表达独占所有权，拷贝构造和拷贝赋值被删除，只能移动。这保证同一时刻只有一个 unique_ptr 拥有对象，所有权清晰。shared_ptr 可拷贝（引用计数+1）；weak_ptr 可拷贝（不增加计数）。

2. 判断题：std::make_shared<int>(42) 比 std::shared_ptr<int>(new int(42)) 更推荐。

答案

正确。make_shared 一次分配同时容纳对象和控制块（计数），少一次内存分配；且异常安全（不会出现"new 成功但 shared_ptr 构造前抛异常导致泄漏"。直接 new 是两次分配（对象+控制块），且 f(shared_ptr<T>(new T), g()) 中 g() 抛异常可能泄漏 new 的 T）。除非要自定义删除器，否则优先 make_shared。

3. 踩坑题：下面两个类互相引用，导致内存泄漏，为什么？怎么修？

struct B;
struct A { std::shared_ptr<B> b; ~A(){std::cout<<"~A";} };
struct B { std::shared_ptr<A> a; ~B(){std::cout<<"~B";} };
auto a = std::make_shared<A>();
auto b = std::make_shared<B>();
a->b = b;   // a 持 b
b->a = a;   // b 持 a，循环引用
// a、b 出作用域后，析构没打印（泄漏）
答案

循环引用：a 持 b（b 计数≥1），b 持 a（a 计数≥1）。出作用域后 a、b 的 shared_ptr 释放，但 a 对象被 b->a 引用（计数 1），b 对象被 a->b 引用（计数 1），互相保活，计数永不归 0，泄漏。修正：一方改用 weak_ptr：

struct B { std::weak_ptr<A> a; };   // 弱引用，不增加计数
// 用时 lock() 升级：if (auto pa = b->a.lock()) { ... }

weak_ptr 不增加计数，打破环，a 出作用域计数归 0 正常释放，b 随之释放。

4. 应用题：用 unique_ptr 管理一个动态分配的 FILE*（C 接口），自定义删除器调 fclose。说明相比 C 手动 fclose 的优势。

答案 
auto open_file(const char* path) {
    FILE* f = std::fopen(path, "r");
    if (!f) throw std::runtime_error("open failed");
    auto deleter = [](FILE* p){ if (p) std::fclose(p); };
    return std::unique_ptr<FILE, decltype(deleter)>(f, deleter);
}
void use() {
    auto f = open_file("a.txt");
    // ... 用 f.get() 调 C 函数 ...
    // 抛异常或返回，f 析构自动 fclose，不泄漏
}

优势：1) 异常安全——任何路径都 fclose；2) 不用记着 fclose；3) 所有权明确（unique_ptr 持有）。C 版要 goto cleanup 或 try/catch，繁琐易错。这是 C++ 用 RAII 包装 C 资源的典型模式。

5. 踩坑题：下面这行为什么编译失败？有几种改法？

std::unique_ptr<Entity> entity = new Entity();
答案

unique_ptr 的单参构造函数是 explicit 的（实测报错 explicit constructor is not a candidate，声明在 libc++ __memory/unique_ptr.h:163）。= new Entity() 是拷贝初始化，需要隐式转换，被 explicit 挡住。它是拷贝初始化，不是"智能指针不能用 new"。

三种改法：

std::unique_ptr<Entity> a(new Entity());   // 直接初始化：explicit 管不着
auto b = std::make_unique<Entity>();       // C++14 起推荐
std::unique_ptr<Entity> c = std::make_unique<Entity>();  // 也行（make_unique 返回的已是 unique_ptr）

顺带一个对照：std::unique_ptr<Entity> d = nullptr; 是合法的——unique_ptr(nullptr_t) 没加 explicit。标准委员会的判断是：接管裸指针所有权是危险动作，必须显式；"空"语义无害，放行。

6. 踩坑题：下面这段代码运行时崩溃（或析构两次），为什么？怎么改？

struct Node : std::enable_shared_from_this<Node> {
    std::shared_ptr<Node> child;
    void add_child(std::shared_ptr<Node> c) { child = c; }
    std::shared_ptr<Node> self_bad()  { return std::shared_ptr<Node>(this); }  // ①
    std::shared_ptr<Node> self_good() { return shared_from_this(); }           // ②
};
auto n = std::make_shared<Node>();
auto x = n->self_bad();
答案

① 制造了第二个控制块。 this 是裸指针，用裸指针构造 shared_ptr 一定是新建控制块；而 n 早就有一个控制块了。两个控制块的强计数各自为 1，各自归零时都会 delete 同一块内存 → 实测 [析构] 打印两遍，实际工程中常表现为 SIGABRT（退出码 134） 或堆损坏。

② 是对的：shared_from_this() 返回的是复用现有控制块的 shared_ptr，计数从 1 变 2，只析构一次。

铁律：一个对象只能有一个控制块。推论——把裸指针交给 shared_ptr 之后，就只能通过拷贝 shared_ptr 传播所有权，绝不能再用 get() / this 去造第二个。

另外注意：shared_from_this() 要求对象当前已被某个 shared_ptr 持有，否则抛 std::bad_weak_ptr（栈对象上调用、构造函数里调用都会抛，这两个都实测过）。

7. 判断题：4 个线程各持有一份指向同一对象的 shared_ptr 副本，并发地对 obj->counter += 1，是线程安全的。

答案

错。 要分清楚两层：

  • ✅ 引用计数是原子的——4 线程各拷贝 10000 次，TSan 无告警，use_count() 精确回到 1；
  • ❌ 对象本身没有任何保护——counter += 1 是读-改-写三步，TSan 报 data race，4 线程各加 2000 次实测只得到 4000（应为 8000）。

shared_ptr 只管生命周期，不管数据竞争。要让 counter 安全，得自己加锁或改成 std::atomic<long>。

最阴的一点是：-O2 不开 TSan 跑同一个程序，结果恰好是 8000——竞态不保证出错，只是随时可能出错。所以别用"我跑了好几遍都对"来证明线程安全。

8. 应用题：写一个"行情快照缓存"——按 symbol 缓存快照对象，外部没人持有时缓存条目自动失效（不能把对象永久钉在内存里），外部有人持有时重复取要拿到同一个对象。

答案

关键是缓存容器存 weak_ptr 而不是 shared_ptr：

class SnapshotCache {
    std::unordered_map<std::string, std::weak_ptr<Snapshot>> cache_;
public:
    std::shared_ptr<Snapshot> get(const std::string& sym, long seq) {
        if (auto it = cache_.find(sym); it != cache_.end())
            if (auto hit = it->second.lock()) return hit;          // 还活着 → 复用
        auto fresh = std::make_shared<Snapshot>(sym, seq);         // 已失效 → 重建
        cache_[sym] = fresh;
        return fresh;
    }
};

实测输出：

-- 第一次取 --        [构造] 快照 600519#1
-- 第二次取 --        [命中缓存] 600519#1        同一对象? 是
-- 外部全释放后再取 -- [析构] 快照 600519#1
                     [缓存条目已失效] 600519
                     [构造] 快照 600519#2

如果 cache_ 存的是 shared_ptr，缓存自己就把每个快照的计数永久 +1，对象永远不释放——那是另一种泄漏。判断标准：容器只是索引、不参与所有权 → weak_ptr。

注意 lock() 一次 ≈ 13.8 ns，别在每个 tick 上重复升级；一次处理中升级一次、然后一直持有那个 shared_ptr。

9. 思考题：weak_ptr 的 expired() 和 lock() 在多线程下有什么坑？

答案

四个，其中前两个会直接导致崩溃或 UB：

① 两步走有 TOCTOU 窗口。 if (!w.expired()) { auto s = w.lock(); ... } —— 检查完到 lock() 之间，别的线程可能已经把最后一个 shared_ptr 释放了。实测：lock() 后不判空直接解引用，稳定 SIGSEGV（139）。正确写法只有一种：if (auto s = w.lock()) { ... }，检查和使用必须是一步。

② use_count() 不能当判断用。 libc++ 实现是 __atomic_load_n(&__shared_owners_, __ATOMIC_RELAXED)——一次不加同步的 relaxed 读，只是快照；就算读到 1，下一刻也可能是 0。判存活只能用 expired() / lock()。

③ lock() 给的是临时所有权。 升级成功后别把 s.get() 存到成员里长期用——临时 shared_ptr 一析构，那个裸指针就悬垂了。要长期持有就存 shared_ptr 本身。

④ weak_ptr 实例本身也不是线程安全的。 多线程读写同一个 weak_ptr 变量（一个赋值、一个 lock()）同样是 data race；需要 std::atomic<std::weak_ptr<T>>（C++20）或加锁。但不同 weak_ptr 实例并发 lock() 同一控制块是安全的——计数是原子的。

一句话总结：lock() 是原子操作，所以把判断和使用合并成一次 lock()，剩下三个坑就都绕开了。

10. 思考题：weak_count 是控制块的计数。如果业务对象已经销毁、但还有 weak_ptr 活着，控制块会不会继续留在内存里？

答案

会。 这正是设计如此——控制块的寿命由 weak_count 决定，与业务对象无关。

实测时间线（shared_ptr<Obj>(new Obj)，Obj 含 64 字节，重载 operator new/delete 打印地址）：

  [分配] 0x145604bc0  64 字节     ← 业务对象
  [分配] 0x145604c40  32 字节     ← 控制块
  sp.reset()
    [析构] Obj
    [归还] 0x145604bc0            ← 只还了对象，控制块不还
  expired()=1  lock() 为空? 是    ← weak_ptr 照常查询，且查得准
    [归还] 0x145604c40            ← weak_ptr 离开作用域才还

三层含义：

  1. 业务对象与控制块是两块独立内存（make_shared 除外），强计数归零只释放前者。
  2. weak_ptr 在对象死后还能正确回答 expired() / lock()，靠的就是这块没被释放的控制块——它查的是控制块里的计数，从不碰已经失效的对象内存。
  3. 这笔内存是有代价的：一个 weak_ptr 至少让 32 字节（控制块）赖在堆上；用 make_shared 更狠，对象和控制块是同一块（实测共 88 字节），reset() 后整块都不还，直到最后一个 weak_ptr 消失。这也是前面「make_shared 隐藏代价」那条实测的机制来源。

12.2

直接内存管理

本节讲什么

C++ 的裸 new/delete（对应 C 的 malloc/free）。现代 C++ 强烈建议用智能指针而非裸 new/delete，但理解底层机制仍重要——读老代码、写底层库、与 C 互操作都用得到。

核心用法

new / delete

int* p = new int(42);      // 分配并初始化
delete p;                  // 释放
p = nullptr;               // 好习惯：防止悬垂

int* arr = new int[10];    // 动态数组
delete[] arr;              // 注意：数组用 delete[]

new 的失败

int* p = new int;          // 默认抛 std::bad_alloc
int* q = new (std::nothrow) int;   // 不抛，失败返回 nullptr

智能指针与 new 结合

// 用 new 构造智能指针（不如 make_shared 推荐）
std::shared_ptr<int> p(new int(42));

// 危险：不要用 get() 初始化另一个智能指针
std::shared_ptr<int> p(new int);
int* raw = p.get();
std::shared_ptr<int> q(raw);   // 错！q 和 p 各自计数，双 delete

placement new（定位 new）

char buf[sizeof(int)];
int* p = new (buf) int(42);   // 在 buf 处构造 int，不分配
// ... 用 ...
p->~int();                     // 手动析构（不释放内存）

delete 到底比 free 多做了什么

一句话答案：delete 不是另一套内存回收机制，它就是 free 外面包了一层析构。

把全局变量 operator new/operator delete 替换掉打印之后，实测链路（clang++ -std=c++17，例子见文末）：

写法 编译器实际展开
new T(args) void* m = operator new(sizeof(T)); → 在 m 上构造
delete p p->~T(); → operator delete(p);
operator new 的默认实现 内部就是 malloc（拿不到内存时转去调 new_handler）
operator delete 的默认实现 内部就是 free

所以同一次运行里 malloc(8) 和 new Tracked(2) 拿到的地址只相差几百字节——它们是同一个堆 arena。

正因为底层是同一个东西，「混用是 UB」通常不会当场崩溃，而是静默地少干一半活：

Widget* p = new Widget();
free(p);      // 内存确实归还了，但 ~Widget() 一次都没跑
              // → Widget 持有的那块资源泄漏，而 valgrind/ASan 未必报警

实测补充（2026-10-15，macOS + clang 23.1.0 + libc++）：-fsanitize=address 抓不到 new+free 这种混用。因为 ASan 拦截的是 malloc/free，而默认的 operator new 内部就是 malloc，在它眼里两边完全匹配，不报 alloc-dealloc-mismatch。别指望 sanitizer 替你兜这个底。（换平台/换 runtime 可能不同。）

delete nullptr 是安全的

Widget* p = nullptr;
delete p;         // 合法：标准保证什么也不做
free(nullptr);    // 同理，C 的 free(NULL) 也是 no-op

不需要写 if (p) delete p; 这种保护——标准规定 operator delete 收到空指针时必须什么都不做。C 程序员从 free 迁过来常顺手加上，属于多余代码。

sized delete：delete 比 free 多知道一件事

free 只拿到一个地址，块多大得去 malloc 头部查。delete 不一样——编译器在 delete 点静态就知道 sizeof(T)，C++14 起会优先把它传进去：

void operator delete(void* p) noexcept;              // 无 size 版
void operator delete(void* p, std::size_t n) noexcept;  // sized 版（C++14 起）

同一份代码换标准编译，实测选择的版本不同：

-std=c++17  →  [op del]  0x146e04a10 size=4   <- sized delete
-std=c++11  →  [op del]  0x136804640          <- 无 size 版本

自己写内存池重载 operator delete 时，这个 n 是白捡的信息：省掉一次从 malloc 头部反查块大小的动作，也能直接用来决定该把这块内存还给哪个 size class 的空闲链表。

new[] 多出来的那 16 个字节

delete[] 得知道要析构几个元素，所以 new[] 要在分配块头部塞一个计数字段（俗称 cookie）。实测（arm64 + libc++）：

new Tracked[3]   sizeof*3 = 12 字节，实际申请 28 字节，用户指针比起点后移 16 字节
new int[3]       sizeof*3 = 12 字节，实际申请 12 字节，偏移 0 字节

两个结论，都容易记错：

  1. 头部是 16 字节，不是 8。 它要对齐到最大对齐要求，跟 sizeof(T) 无关（sizeof 为 4 / 7 / 8 的类型实测都是 16）。
  2. 只有析构非平凡的类型才需要它。 int 这类平凡类型 delete[] 不必逐个析构，就不用记元素数——连头部都省掉了。

算内存池容量时若把这块漏了，池子会算少；按 8 字节算也会算少。

calloc：清零 ≠ 构造（UB 的判定链）

C 里 calloc 就是「malloc + 清零」的省事写法，但它在 C++ 里最会骗人：字节清得干干净净，看着规规矩矩，对象却一次都没构造。

步骤 malloc calloc new T
拿到堆内存 ✅ ✅ ✅
写字节 ❌ 脏数据 ✅ 全位零 视初始化形式
调用构造函数 ❌ ❌ ✅
对象生命周期开始 ❌ ❌ ✅
释放 free 不析构 free 不析构 delete 先析构

「calloc 之后能不能直接用」由两条标准规则决定：

  1. 生命周期开始 = 拿到存储 + 初始化完成（[basic.life]）。calloc 只完成了前一半。
  2. C++20 的隐式对象创建（P0593）确实说分配函数会「隐式创建对象」，但只对 implicit-lifetime 类型——聚合体、标量、默认构造 trivial 的类。用户写了构造函数的类不在其列，一个对象都不会被创建。

所以 struct A { int val; A() : val(42) {} }; 经 calloc 后读 p->val，实测（macOS + clang 23.1.0 + libc++，2026-10-19）：

构造函数写的是 val = 42
实际读到       val = 0        <- 读到 0 = 观测到不可能状态
is_trivially_default_constructible_v<A> = 0

「输出 0」恰恰证明它是 UB：一个合法存在的 A，val 必然是 42；读到 0 只能说明那里根本没有对象。而且 -O0 / -O2 / -fsanitize=undefined 三档输出完全一致，UBSan 一声不吭——它查的是「未初始化读」，而 calloc 确实把字节写了。

换成带虚函数的类，不用推理、当场就能看见崩溃（vptr 那 8 个字节也被清零，通过空 vptr 做虚调用）：

sizeof(V) = 16
val = 0，准备调用虚函数...
EXIT=139        <- SIGSEGV

唯一能翻盘的条件：把构造函数删掉，让类型退回 trivial 聚合体——此时 C++20 起的隐式对象创建接管，读成员是合法的（实测输出 0）。分水岭不是「用没用 calloc」，而是这个类型有没有 non-trivial 的构造函数。

正确写法：把「内存」和「构造」两件事分开结清。

void* raw = calloc(1, sizeof(A));
A*    r   = new (raw) A();    // 括号 = 值初始化；有用户构造函数则走默认构造
// ... 用 r ...
r->~A();                      // 显式析构
free(raw);                    // 归还内存（这里不能用 delete）

⚠️ calloc 清的是全位零（all-bits-zero），不是「值等于 0」。整数类型可以放心依赖（C++20 起保证纯二进制 + 二补数）；但指针成员全零位不保证是 nullptr、浮点不保证是 0.0、padding 位也不保证——实测在 arm64 + libc++ 上 ptr 确实是 0x0、double 确实是 0，但这只是这个平台的巧合，不可写成依赖。

和 C 的区别

维度 C C++

构造/析构 ❌ 不调用 ✅ 自动调用

C 程序员最该理解的两点：

  1. new 调用构造函数，malloc 不：对内置类型差别小，对类类型差别巨大——new std::string("hi") 会调用 string 构造函数，malloc(sizeof(std::string)) 只分配内存不构造，用就崩。
/* C：malloc 只分配内存，不构造 */
struct Foo* p = malloc(sizeof(struct Foo));   // 内存有了，但未初始化
foo_init(p);                                  // C 要手动调 init

// C++：new 分配 + 构造一步完成
Foo* p = new Foo();    // 构造函数自动调用
  1. delete 调用析构函数：delete p 先调析构函数（释放 p 持有的资源）再释放内存。C 的 free 不调用析构——所以 C++ 对象绝不能用 free 释放。

new/delete 与 malloc/free 不要混用

int* p = new int(42);
free(p);          // 错！未调用析构（int 没析构还行，类类型就崩）

int* q = (int*)malloc(sizeof(int));
delete q;         // 错！delete 期望 new 分配的内存

常见错误

  1. new[] 用 delete（非 delete[]）：int* a = new int[10]; delete a; —— 未定义行为，应 delete[] a。delete[] 知道要调多次析构并释放数组内存。
  2. 忘了 delete / 重复 delete：忘了 → 泄漏；delete 后再 delete → 双 delete UB。根除方法：用智能指针，根本不用裸 new/delete。
  3. delete 后继续用指针：delete p; *p = 5; —— 悬垂指针 UB。修正：delete 后置 nullptr，或用智能指针。

自测题

1. 选择题：下面哪种释放方式对 int* a = new int[10] 是正确的？ - A) delete a; - B) delete[] a; - C) free(a); - D) delete a[10];

答案

B。new[] 分配的数组必须用 delete[] 释放（方括号告诉编译器调多次析构并释放数组）。A 是 UB（对数组用非数组 delete）；C 是 C 的释放，与 new 不匹配；D 语法错误。规则：new 配 delete，new[] 配 delete[]，malloc 配 free，绝不混用。

2. 判断题：new 对内置类型（如 int）和类类型（如 string）都会调用构造函数。

答案

正确。new 对所有类型都调用构造函数——int 调默认构造（未初始化，new int）或值初始化（new int() 为 0）；string 调 string 的构造函数。这是 new 与 malloc 的根本区别。malloc 只给内存不给初始化，new 给内存+构造。

3. 踩坑题：下面代码看起来用了智能指针，但有 bug，找出来。

std::shared_ptr<int> p(new int(42));
int* raw = p.get();                  // 取裸指针
std::shared_ptr<int> q(raw);         // 用裸指针构造另一个
// p 和 q 现在都"管理"同一块内存
答案

q 和 p 各自有独立的引用计数（都从 raw 构造，互不知情）。当 p 释放（计数归 0）delete 内存后，q 还以为有效，再用 q 或 q 释放时双 delete → UB。修正：不要用 get() 的结果构造新智能指针。要共享直接 auto q = p;（拷贝，计数共享）。get() 只用于传给需要裸指针的 C 接口，且不持有所有权。

4. 应用题：说明为什么现代 C++ 建议"尽量用智能指针，少用裸 new/delete"，并指出哪些场景仍需要裸 new。

答案

建议用智能指针的原因：1) RAII 自动释放，几乎消灭泄漏；2) 异常安全；3) 所有权明确（unique 独占/shared 共享）。裸 new/delete 的问题：忘了 delete 泄漏、重复 delete UB、异常路径泄漏、悬垂指针。

仍需裸 new 的场景：1) 实现智能指针/容器底层（要手动管理）；2) placement new（在预分配内存上构造，如内存池）；3) 与 C 接口互操作（C 要裸指针）；4) 自定义内存分配器。这些是底层库的活，应用层代码应尽量用智能指针。原则：能用 make_unique/make_shared 就别裸 new。

5. 判断题：Widget* p = new Widget(); free(p); 会立刻崩溃。

答案

不会崩溃（通常），但这是 UB，而且比崩溃更危险。free 能正确把内存还回去（因为默认 operator new 底层就是 malloc），但 ~Widget() 一次都没有被调用——Widget 内部持有的文件句柄、子堆内存全部泄漏。

更麻烦的是工具不一定报警：macOS + clang + libc++ 下实测 -fsanitize=address 不报 alloc-dealloc-mismatch，因为 ASan 眼里 operator new→malloc、free→free 是一对匹配的调用。所以这条只能靠自己配对：new 配 delete，malloc 配 free。

6. 算账题：struct Data { char buf[24]; ~Data(){} };（非平凡析构），new Data[100] 实际向 operator new[] 申请了多少字节？如果把析构函数删掉呢？

答案 
new Data[100]  // 100 * 24 = 2400 字节数据 + 16 字节头部 = 2416 字节

删掉 ~Data() 后变成平凡析构类型，delete[] 不必逐个析构，就不需要记元素个数——连 16 字节头部都省了，只申请 2400 字节。

给内存池算容量时踩的两个坑：① 忘了头部 → 池子算小了；② 以为头部是 8 字节 → 还是算小了（arm64 + libc++ 实测是 16）。

7. 判断题：下面代码是否安全？

struct A { int val; A() : val(42) {} };
A* p = (A*)calloc(1, sizeof(A));
std::cout << p->val << std::endl;
  • A. 安全，输出 0
  • B. UB，未定义行为
答案

B。而且 A 选项自相矛盾：如果它真的安全合法，那对象就存在，构造函数跑过，val 就该是 42。

判定链：① 对象生命周期开始 = 拿到存储 + 初始化完成，calloc 只给了存储；② C++20 隐式对象创建只对 implicit-lifetime 类型生效，而 A 有用户提供的构造函数（is_trivially_default_constructible_v<A> == 0），不适用 → 内存上没有 A 对象 → 访问 p->val 是 UB。

实测印证：三档优化下都输出 0（不是 42），UBSan 不报错；若把 A 加上虚函数，calloc 后虚调用直接 SIGSEGV（exit 139）。反例：删掉构造函数让 A 变回 trivial 聚合体，此时 C++20 起合法，输出 0。

正确写法是 new (raw) A() 显式构造 + r->~A() 显式析构 + free(raw)。

12.3

动态数组与 allocator

本节讲什么

C++ 分配动态数组的几种方式：new[]/delete[]、智能指针管理数组（unique_ptr<T[]>）、vector（首选）、allocator（内存分配与对象构造分离，高性能场景）。重点是为什么 vector 几乎总是比 new[] 好。

核心用法

new[] / delete[]

int* arr = new int[10];    // 10 个未初始化 int
int* arr2 = new int[10](); // 10 个 0（值初始化）
delete[] arr;              // 数组用 delete[]

智能指针管理数组

std::unique_ptr<int[]> up(new int[10]);   // 自动 delete[]
up[0] = 42;                               // 支持 []
// 出作用域自动 delete[]，不泄漏

// shared_ptr 管理数组要自定义删除器（C++17 前）
std::shared_ptr<int> sp(new int[10], std::default_delete<int[]>());

vector（首选！）

std::vector<int> v(10);          // 10 个 0
v.resize(20);                    // 可变大小
v.push_back(42);                 // 追加
// 析构自动释放，RAII

allocator（内存与构造分离）

#include <memory>
std::allocator<int> alloc;
int* p = alloc.allocate(10);     // 只分配内存，不构造
alloc.construct(p, 42);          // 在 p 处构造
// ... 用 ...
alloc.destroy(p);                // 析构
alloc.deallocate(p, 10);         // 释放内存

allocator 把"分配内存"和"构造对象"分开——先分配一大块内存，按需构造，适合"先预留内存、按需构造"的高性能场景（如 vector 内部就用 allocator 实现 reserve 时不构造）。

和 C 的区别

维度 C C++
动态数组 malloc(n*sizeof(T)) new T[n] / vector
构造 ❌ malloc 不构造 new[] 构造每个元素
可变大小 realloc（手动，元素可能是浅拷贝） vector 自动安全扩容
内存/构造分离 无概念 allocator
释放 free delete[] / RAII

C 程序员最该体会的：vector 几乎总是比 new[] 好

C 的动态数组是 malloc + 手动管理大小 + realloc，繁琐易错：

/* C：手动动态数组 */
int* arr = malloc(10 * sizeof(int));
size_t size = 10;
// 要扩容
int* tmp = realloc(arr, 20 * sizeof(int));   // realloc 可能移动内存
if (!tmp) { /* 处理失败 */ }
arr = tmp;
size = 20;
// ... 还要记着 free(arr)

C++ 的 vector 把这一切自动化，且更安全：

std::vector<int> v(10);
v.resize(20);    // 自动扩容，自动处理拷贝/移动
// 析构自动释放

只有在以下情况才考虑 new[]/allocator： - 与 C 接口互操作（C 要裸指针） - 性能极致优化（allocator 分离分配与构造，避免无谓构造） - 固定大小且不想用 vector 的容量管理开销

常见错误

  1. new[] 配 delete（非 delete[]）：UB，必须 delete[]。用 unique_ptr<T[]> 可避免记错。
  2. allocator 忘了 destroy：allocate 后 construct，用完必须 destroy 再 deallocate，否则对象析构没调用，资源泄漏。
  3. 用 vector 还是 new[] 纠结：99% 情况用 vector。new[] 的唯一理由是与 C 互操作或极致性能优化。

自测题

1. 选择题：下面哪种方式管理动态数组最推荐？ - A) int* a = new int[10]; ... delete[] a; - B) std::unique_ptr<int[]> a(new int[10]); - C) std::vector<int> a(10); - D) int* a = (int*)malloc(10*sizeof(int));

答案

C。vector 最推荐：自动管理大小、RAII 释放、接口丰富、安全。B 是次选（固定大小、要裸指针语义时）。A 裸 new[] 要手动 delete[] 易错。D 是 C 方式，不调用构造/析构，C++ 中不推荐。现代 C++ 应用层动态数组默认 vector。

2. 判断题：std::allocator 的 allocate 会调用对象的构造函数。

答案

错误。allocator::allocate 只分配原始内存，不构造对象；要构造需调 construct。这正是 allocator 的设计目的——分离"分配"与"构造"，让你先开一大块内存（reserve），按需在指定位置构造，避免无谓的默认构造开销。C++17 起 construct/destroy 被弃用，推荐用 std::construct_at/std::destroy_at。

3. 踩坑题：下面代码用 allocator，但有 bug，找出来。

std::allocator<std::string> alloc;
auto p = alloc.allocate(3);
p[0] = "a"; p[1] = "b"; p[2] = "c";   // 直接赋值
// ... 用 ...
alloc.deallocate(p, 3);               // 释放
答案

allocate 只分配内存未构造对象，直接 p[0] = "a" 是对未构造内存赋值（调用 operator=，但对象还没构造），UB。正确流程：allocate → construct（每个）→ 用 → destroy（每个）→ deallocate：

auto p = alloc.allocate(3);
std::construct_at(p, "a");
std::construct_at(p+1, "b");
std::construct_at(p+2, "c");
// 用
std::destroy_at(p); std::destroy_at(p+1); std::destroy_at(p+2);
alloc.deallocate(p, 3);

这就是为什么应用层用 vector——它内部正确处理了这些。

4. 应用题：HFT 场景需要一个"预分配 N 个 Msg 对象的内存池，按需构造/析构，绝不运行期分配"。用 allocator 设计，说明为什么不直接用 vector。

答案 
class MsgPool {
    std::allocator<Msg> alloc;
    Msg* mem;
    size_t cap;
public:
    MsgPool(size_t n) : cap(n) {
        mem = alloc.allocate(n);   // 启动时一次分配，不构造
    }
    Msg* acquire(const Args&... args) {
        // 找一个空闲槽位（用位图标记），construct_at 构造
        size_t slot = find_free_slot();
        std::construct_at(mem + slot, args...);
        return mem + slot;
    }
    void release(Msg* p) {
        std::destroy_at(p);        // 析构，不释放内存
        mark_free(p - mem);
    }
    ~MsgPool() { alloc.deallocate(mem, cap); }
};

不用 vector 因为：1) vector 的 reserve 仍可能触发扩容（HFT 禁止运行期分配）；2) vector 要求元素可构造/移动，内存池想完全控制何时构造；3) allocator 分离分配与构造，启动时分配一大块，运行期零分配只构造/析构。这是 HFT/游戏引擎常见的对象池模式。

而且每次扩容都不是免费的——要「分配新内存 + 把旧元素全部搬过去 + 释放旧内存」。所以 push_back 是均摊 O(1)，但单次最坏是 O(n)。

实战：文本查询程序

本节讲什么

C++ Primer 的经典综合练习：用 vector、map、set、string、shared_ptr 构建一个文本查询程序——读入文件，查询某单词出现在哪些行，输出行号和原文。这是第二部分（标准库）的综合应用。

核心设计

需求

  • 读入一个文本文件
  • 查询某单词：输出该单词出现的所有行号 + 对应行原文
  • 不重复（同一行只报一次）

数据结构

class TextQuery {
    std::shared_ptr<std::vector<std::string>> file;   // 文件内容（每行一个 string）
    std::map<std::string, std::shared_ptr<std::set<size_t>>> wm;
    // 单词 → 出现的行号集合
};
  • file 用 shared_ptr<vector<string>>：多处共享（TextQuery 和 QueryResult 都要引用），shared_ptr 自动管理
  • 行号集合用 shared_ptr<set<size_t>>：避免拷贝整个 set，共享同一份

完整实现

#include <fstream>
#include <string>
#include <vector>
#include <map>
#include <set>
#include <memory>
#include <sstream>

class QueryResult;

class TextQuery {
public:
    TextQuery(std::ifstream& in);
    QueryResult query(const std::string& word) const;
private:
    std::shared_ptr<std::vector<std::string>> file_;
    std::map<std::string, std::shared_ptr<std::set<size_t>>> wm_;
};

class QueryResult {
    friend std::ostream& print(std::ostream&, const QueryResult&);
public:
    QueryResult(std::string s,
                std::shared_ptr<std::set<size_t>> lines,
                std::shared_ptr<std::vector<std::string>> file)
        : sought_(s), lines_(lines), file_(file) {}
private:
    std::string sought_;
    std::shared_ptr<std::set<size_t>> lines_;
    std::shared_ptr<std::vector<std::string>> file_;
};

TextQuery::TextQuery(std::ifstream& in)
    : file_(std::make_shared<std::vector<std::string>>()) {
    std::string line;
    size_t line_no = 0;
    while (std::getline(in, line)) {
        file_->push_back(line);
        std::istringstream iss(line);
        std::string word;
        while (iss >> word) {
            auto& p = wm_[word];          // 不存在则插入空 shared_ptr
            if (!p) p = std::make_shared<std::set<size_t>>();
            p->insert(line_no);
        }
        ++line_no;
    }
}

QueryResult TextQuery::query(const std::string& word) const {
    static auto nodata = std::make_shared<std::set<size_t>>();
    auto it = wm_.find(word);
    if (it != wm_.end()) return {word, it->second, file_};
    return {word, nodata, file_};
}

std::ostream& print(std::ostream& os, const QueryResult& r) {
    os << r.sought_ << " occurs " << r.lines_->size() << " times\n";
    for (auto n : *r.lines_)
        os << "\t(line " << n+1 << ") " << (*r.file_)[n] << "\n";
    return os;
}

和 C 的区别

维度 C C++
字符串 char[] + strtok string + istringstream
动态数组 malloc/realloc vector
关联查找 手写哈希表 map/set
内存共享 手动引用计数 shared_ptr
代码量 几百行易错 几十行清晰

C 程序员的体会：

用 C 实现同样功能要：1) 手写动态字符串数组存行；2) 手写哈希表存单词→行号；3) 手动管理所有内存（free 每个节点）；4) strtok 分词（破坏原串、非重入）。几百行，且内存管理极易出错。

C++ 用标准库组件组合，几十行，且 shared_ptr 自动管理共享数据。这就是"用现成组件"vs"造轮子"的差距。

常见错误

  1. shared_ptr 共享数据后修改：TextQuery 和 QueryResult 共享 file_，若 QueryResult 修改 file_ 会影响 TextQuery。这里只读没问题，但设计时要明确共享数据是否可变。
  2. wm_[word] 的副作用：query 时若用 wm_[word] 而非 find，会插入空条目。本实现用 find 正确。
  3. 行号从 0 还是 1：内部存 0-based，输出时 +1 转人友好的 1-based。易混淆。

自测题

1. 选择题：为什么 file_ 用 shared_ptr<vector<string>> 而非直接 vector<string>？ - A) vector 不能作成员 - B) TextQuery 和 QueryResult 要共享同一份文件数据，避免拷贝 - C) shared_ptr 更快 - D) vector 会泄漏

答案

B。QueryResult 要引用 TextQuery 的 file 数据来输出行原文。若 file 是普通 vector 成员，QueryResult 要么拷贝整个文件（浪费），要么存引用（TextQuery 销毁后悬垂）。shared_ptr 让两者共享同一份，引用计数管理生命周期——TextQuery 销毁但 QueryResult 还在时，file 仍存活。这是 shared_ptr 共享所有权的典型用途。

2. 判断题：std::map<std::string, std::shared_ptr<std::set<size_t>>> 中，用 shared_ptr 包 set 是为了延迟创建 set（只在单词第一次出现时创建）。

答案

正确。如果 map 的值直接是 set<size_t>，每个单词都立刻有一个空 set 对象（占内存）。用 shared_ptr<set>，初始为空 shared_ptr（不占 set 内存），单词第一次出现时才 make_shared<set>。这是"延迟分配"优化，减少不必要对象。同时 shared_ptr 也便于 QueryResult 共享同一 set。

3. 踩坑题：query 函数里 auto& p = wm_[word]; 为什么用引用？改成 auto p = wm_[word]; 会怎样？

答案

auto p = wm_[word] 会拷贝 shared_ptr（计数+1），p 是副本。虽然功能上 p->insert 仍能改到同一个 set（shared_ptr 共享对象），但拷贝有多余的原子计数操作。用 auto& 是引用，避免拷贝，直接引用 map 里的 shared_ptr。性能上 auto& 更优。不过这里功能都对（shared_ptr 拷贝仍指向同一 set），只是 auto& 省一次计数操作。

4. 应用题：扩展文本查询程序，支持"查询单词在文件中出现的总次数"。说明需要改哪里。

答案

行号 set 的大小是"出现的行数"，不是"总次数"（一行可能多次）。要总次数有两种方案： 1) 改 set<size_t> 为 multiset<size_t> 或 vector<size_t>，存每次出现的行号（允许重复），size() 就是总次数。 2) 额外维护 map<string, size_t> total_count 记录每词总出现数。

QueryResult 增加 size_t total 字段，print 输出"occurs N times in M lines"（N 总次数，M 行数）。这体现了"行数"与"次数"的区别——C++ 用 set 自动去重得行数，要次数需额外结构。

Q3weak_ptr 打破环引用
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;  // A: 环引用？
    // std::weak_ptr<Node> prev; // B: 修复方案
};
auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;
// a 和 b 离开作用域后...

用 A 行（shared_ptr prev）时，a 和 b 离开作用域后内存会释放吗？B 行如何修复？

答案与复习指引

用 A 行：不会释放。 a 离开作用域，引用计数从 2→1（b->prev 仍持有 a）；b 离开作用域，引用计数从 2→1（a->next 仍持有 b）。互引导致计数永远不为 0——内存泄漏。

用 B 行（weak_ptr）：会释放。 weak_ptr 不增加强引用计数。a 离开作用域时引用计数→0（b->prev 是 weak_ptr 不算），a 被释放；然后 b 引用计数→0，b 被释放。

规则： 双向引用时，一方用 shared_ptr（强引用），另一方用 weak_ptr（弱引用）打破环。

Q4new vs make_shared
// 方式 A:
std::shared_ptr<Widget> p1(new Widget());
// 方式 B:
auto p2 = std::make_shared<Widget>();

A 和 B 有什么区别？B 好在哪里？

答案与复习指引

B 好在： 1. 一次分配：make_shared 一次 new 同时分配对象 + 控制块；方式 A 两次 new（对象 + 控制块） 2. cache 友好：对象和控制块在同一块内存 3. 异常安全：f(shared_ptr<T>(new T), g()) 中 g() 可能在 new 和 shared_ptr 构造之间抛异常；f(make_shared<T>(), g()) 不会

B 的缺点： make_shared 把对象内存与控制块绑定，如果有 weak_ptr 长期存活，对象内存（已析构但未释放）会延迟到所有 weak_ptr 销毁才回收。大对象 + 长期 weak_ptr 场景要用 A。
