C C++

13.1

拷贝控制成员

本节讲什么

C++ 类的五个拷贝控制成员：拷贝构造、拷贝赋值、移动构造、移动赋值、析构函数。它们控制对象被拷贝/移动/销毁时的行为。这是 C 完全没有的概念——C 的 struct 赋值是浅拷贝（memcpy），含指针就出问题。C 程序员必须理解这套机制。

核心用法

五个成员

成员 何时调用 作用
拷贝构造 T(const T&) 用同类型对象初始化新对象 深拷贝
拷贝赋值 T& operator=(const T&) 已存在对象赋值 先释放旧资源再深拷贝
移动构造 T(T&&) (C++11) 用右值初始化新对象 偷资源（不拷贝）
移动赋值 T& operator=(T&&) (C++11) 已存在对象被右值赋值 释放旧资源再偷
析构 ~T() 对象销毁 释放资源

经典例子：含指针的类

class HasPtr {
public:
    HasPtr(const std::string& s) : ps(new std::string(s)) {}
    // 拷贝构造：深拷贝（new 一份新 string）
    HasPtr(const HasPtr& p) : ps(new std::string(*p.ps)) {}
    // 拷贝赋值：先 new 新的，再 delete 旧的（异常安全）
    HasPtr& operator=(const HasPtr& rhs) {
        auto newp = new std::string(*rhs.ps);  // 先分配（可能抛异常）
        delete ps;                              // 再释放旧的
        ps = newp;
        return *this;
    }
    ~HasPtr() { delete ps; }
private:
    std::string* ps;
};

为什么需要深拷贝

如果用编译器生成的默认浅拷贝（拷贝指针值），两个对象指向同一块内存，析构时双 delete → 崩溃。所以含动态资源的类必须自定义拷贝控制。

和 C 的区别

维度 C C++
struct 赋值 浅拷贝（memcpy），含指针就危险 可自定义拷贝行为
构造/析构 ❌ 无 ✅ 自动调用
深拷贝 手动写 dup 函数 拷贝构造函数
资源释放 手动 free 析构函数自动
浅拷贝双 free 常见 bug 自定义拷贝控制避免

C 程序员最该理解的问题：浅拷贝导致的 double free

C 里 struct 含指针，赋值是浅拷贝，两个 struct 指向同一块内存，都 free 就崩：

/* C：struct 赋值是浅拷贝，含指针危险 */
struct HasPtr { char* s; };
struct HasPtr a; a.s = strdup("hi");
struct HasPtr b = a;          // 浅拷贝！b.s == a.s，指向同一块
free(a.s);
free(b.s);                    // double free，崩溃！

C 里要避免，只能手动写深拷贝函数，且要记得调：

struct HasPtr b = hasptr_dup(&a);   // 手动深拷贝，容易忘

C++ 用拷贝构造函数让"深拷贝"自动发生，且编译器保证调用：

HasPtr a("hi");
HasPtr b = a;    // 自动调拷贝构造，深拷贝，安全
// 析构各自 delete 自己的 string，不双 free

这是 C→C++ 在"资源管理正确性"上的根本提升——把易错的拷贝行为交给类设计者一次性写对，使用者无脑用也不出错。

常见错误

  1. 浅拷贝导致双 delete：类含指针但没自定义拷贝控制，默认浅拷贝 → 双 free。修正：自定义拷贝构造/赋值做深拷贝，或用智能指针/值语义避免。
  2. 拷贝赋值不处理自赋值：a = a 时，若先 delete ps 再用 rhs.ps，rhs 就是 this，已 delete → UB。修正*：先 new 新的再 delete 旧的（上例写法），或检查自赋值。
  3. 拷贝赋值不异常安全：delete ps; ps = new string(*rhs.ps); —— 若 new 抛异常，ps 已 delete，对象处于无效状态。修正：先 new 成功再 delete 旧（上例写法）。

自测题

1. 选择题：下面类没定义拷贝控制成员，HasPtr b = a; 后会发生什么？

class HasPtr { public: std::string* ps; HasPtr(std::string s){ps=new std::string(s);} ~HasPtr(){delete ps;} };
  • A) 编译错误
  • B) 浅拷贝，b.ps == a.ps，析构时双 delete
  • C) 深拷贝，安全
  • D) 运行正常
答案

B。没定义拷贝构造，编译器生成默认浅拷贝，b.ps 和 a.ps 指向同一块内存。两个对象析构都 delete 同一块 → 双 free，崩溃。这是含指针类不定义拷贝控制的经典后果。修正：定义拷贝构造做深拷贝，或用 unique_ptr/string 值成员避免裸指针。

2. 判断题：拷贝赋值运算符必须处理自赋值（a = a）。

答案

正确。自赋值虽少见但会发生（如 a[i] = a[j] 当 i==j）。若实现是 delete ps; ps = new string(*rhs.ps);，自赋值时 rhs.ps 就是 ps，先 delete 了再用 → UB。异常安全写法（先 new 再 delete）天然处理自赋值：auto p = new string(*rhs.ps); delete ps; ps = p; —— 即使 rhs 是 *this，先 new 拷贝好再 delete 旧的，安全。

3. 踩坑题：下面拷贝赋值实现有 bug，找出来。

HasPtr& operator=(const HasPtr& rhs) {
    delete ps;              // 先释放自己的
    ps = new string(*rhs.ps);   // 再 new
    return *this;
}
答案

两个 bug：1) 自赋值 UB——a = a 时先 delete ps，然后 *rhs.ps（rhs 就是 this）访问已 delete 的内存；2) 不异常安全——若 new string 抛异常，ps 已 delete，对象处于"ps 悬垂"的无效状态。修正*：先 new 成功再 delete 旧：

auto newp = new string(*rhs.ps);   // 先 new（可能抛异常，此时 ps 未动）
delete ps;                          // 成功后才 delete 旧
ps = newp;
return *this;

这种写法同时解决自赋值和异常安全。

4. 应用题：用智能指针改写上面的 HasPtr，使其无需手动定义拷贝控制（用默认即可），说明原理。

答案 
class HasPtr {
public:
    HasPtr(const std::string& s) : ps(std::make_unique<std::string>(s)) {}
    // 无需自定义拷贝构造/赋值/析构？——等等，unique_ptr 不可拷贝
private:
    std::unique_ptr<std::string> ps;
};

问题：unique_ptr 不可拷贝，所以 HasPtr 也不可拷贝（默认拷贝构造被删除）。若要可拷贝，用 shared_ptr：

class HasPtr {
public:
    HasPtr(const std::string& s) : ps(std::make_shared<std::string>(s)) {}
    // 默认拷贝控制：拷贝 shared_ptr（计数+1），析构计数-1，归0才 delete
private:
    std::shared_ptr<std::string> ps;
};

shared_ptr 让多个 HasPtr 共享同一 string，引用计数管理，无需手写拷贝控制。代价是共享语义（改一个影响所有）。若要值语义（独立拷贝），还是得手写深拷贝，或用 std::string 值成员（最简单）：

class HasPtr { std::string ps; /* 默认拷贝控制即可，深拷贝 */ };

教训：优先用值成员或智能指针，让编译器生成的默认拷贝控制正确工作，避免手写易错的拷贝控制。

13.2

资源管理与三/五法则

本节讲什么

三法则（Rule of Three）和五法则（Rule of Five）：决定一个类何时需要自定义拷贝控制成员，以及它们必须作为一个整体定义。核心思想：如果你的类需要自定义其中一个（通常是析构函数），通常需要全部定义。

核心用法

三法则（C++11 前）

如果类需要自定义任一以下之一，通常需要全部三个： - 析构函数 - 拷贝构造 - 拷贝赋值

理由：需要自定义析构（释放资源）的类，浅拷贝会出错（双 free），所以也要自定义拷贝。

五法则（C++11 起）

加入移动语义后，扩展为五个： - 析构函数 - 拷贝构造 - 拷贝赋值 - 移动构造 - 移动赋值

需要自定义拷贝控制的类，通常也受益于自定义移动（避免不必要的深拷贝）。

何时需要自定义

情况 需要自定义？
类只含值成员（int/string/vector） ❌ 默认即可（深拷贝自动正确）
类含裸指针/动态资源 ✅ 需要全部五个（三五法则）
类用智能指针管理资源 ❌ 通常默认即可（智能指针处理）
类是接口/抽象基类 析构虚函数，其他看情况

现代建议：零法则（Rule of Zero）

优先让类的成员自己管理资源（用智能指针、容器、RAII 类型），让编译器生成的默认拷贝控制自动正确工作，不手写拷贝控制。

// 零法则：成员自己管资源，默认拷贝控制正确
class Good {
    std::string name;                  // string 自管
    std::vector<int> data;             // vector 自管
    std::unique_ptr<Conn> conn;        // unique_ptr 自管
public:
    // 不写任何拷贝控制，编译器生成的就对
};

和 C 的区别

维度 C C++
资源管理规则 无（全靠程序员自觉） 三/五法则 + 零法则
析构自动调用 ❌ 手动 cleanup ✅
拷贝行为可定制 ❌ 浅拷贝 ✅
RAII ❌ ✅ 智能指针/容器

C 程序员的体会：

C 里"含动态资源的 struct"全靠程序员记着：1) 拷贝时要深拷贝；2) 用完要 free；3) 没有规则约束，容易漏。

/* C：全靠自觉，没规则 */
struct Buf { char* data; size_t len; };
// 拷贝时忘了深拷贝 → 双 free
// 用完忘了 free → 泄漏
// 没有任何机制提醒你

C++ 的三/五法则是规则——需要析构的类，编译器生成的默认拷贝通常不对（浅拷贝双 free），你必须自定义。零法则更进一步：用 RAII 成员让默认拷贝控制正确，根本不用写。

常见错误

  1. 定义了析构却用默认拷贝：类有 ~T() { delete[] data; } 但没自定义拷贝构造 → 浅拷贝双 free。违反三五法则。修正：同时定义拷贝控制，或改用智能指针（零法则）。
  2. 该用移动却只定义拷贝：类定义了拷贝构造/赋值但没移动，vector 扩容时会退化为拷贝（性能差）。修正：加移动构造/赋值，或用零法则让编译器生成。
  3. 基类析构不虚：基类析构非 virtual，delete base_ptr（实际指向派生）只调基类析构，派生部分泄漏。修正：基类析构声明 virtual。

自测题

1. 选择题：下面类违反了哪条法则？

class Buf {
public:
    Buf(size_t n) : data(new char[n]) {}
    ~Buf() { delete[] data; }     // 自定义析构
    // 没定义拷贝控制
private:
    char* data;
};
Buf a(10), b = a;   // b = a 用默认拷贝
  • A) 三法则（定义了析构就该定义拷贝）
  • B) 零法则
  • C) 五法则
  • D) 没违反
答案

A。三法则：定义了析构（释放资源）就该定义拷贝构造/赋值。这里没定义，默认浅拷贝，b.data == a.data，析构双 free → 崩溃。修正：要么定义拷贝控制（深拷贝），要么用 std::vector<char>/unique_ptr<char[]> 让默认拷贝控制正确（零法则）。

2. 判断题：零法则建议"尽量不手写拷贝控制，用 RAII 成员让默认正确"。

答案

正确。零法则（Rule of Zero）是现代 C++ 的最佳实践：类的成员用智能指针、容器等 RAII 类型自管资源，编译器生成的默认拷贝/移动/析构自动正确，无需手写易错的拷贝控制。手写拷贝控制只用于"有特殊语义需求"的类（如要深拷贝但用裸指针、要自定义删除器等）。这比三/五法则更省心、更安全。

3. 踩坑题：下面基类析构没声明 virtual，delete p 会怎样？

class Base { public: ~Base() { /* ... */ } };
class Derived : public Base { int* arr; public: Derived():arr(new int[10]){} ~Derived(){delete[] arr;} };
Base* p = new Derived();
delete p;
答案

delete p 只调用 Base 的析构（非虚），Derived 的析构没调用，arr 泄漏。修正：基类析构声明 virtual：

class Base { public: virtual ~Base() { /* ... */ } };

这样 delete p 先调 Derived 析构（释放 arr），再调 Base 析构。这是"基类析构应虚"的规则，属于三五法则在继承中的延伸。C 程序员转 C++ 做 OOP 必踩的坑。

4. 应用题：把下面手写拷贝控制的类用零法则改写，说明优势。

class FileWrapper {
    FILE* f;
public:
    FileWrapper(const char* path) : f(fopen(path,"r")) {}
    ~FileWrapper() { if (f) fclose(f); }
    FileWrapper(const FileWrapper&) = delete;            // 禁拷贝
    FileWrapper& operator=(const FileWrapper&) = delete;
};
答案

其实这个已经接近零法则——用 = delete 禁用拷贝。但裸 FILE 仍要手写析构。更彻底的零法则是用智能指针管 FILE：

class FileWrapper {
    std::unique_ptr<FILE, decltype(&fclose)> f{nullptr, fclose};
public:
    FileWrapper(const char* path) : f(fopen(path,"r"), fclose) {}
    // 不用写析构——unique_ptr 自动 fclose
    // 不用写拷贝控制——unique_ptr 不可拷贝，默认 delete
};

优势：1) 不手写析构（unique_ptr 自管）；2) 不手写 = delete（unique_ptr 不可拷贝，自动传播）；3) 异常安全；4) 代码更少更安全。这就是零法则——把资源管理委托给 RAII 类型，编译器生成的默认行为就正确。

13.3

对象移动（C++11）

本节讲什么

C++11 的移动语义：通过右值引用 T&& 和 std::move，让对象在转移所有权时"偷"资源而非拷贝，大幅提升性能。这是 C 完全没有的概念——C 的所有赋值都是拷贝，对大对象代价高。

核心用法

左值 vs 右值

概念 含义 例子
左值（lvalue） 有名字、可取地址 int x; 中的 x
右值（rvalue） 临时值、不可取地址 42、x+1、std::string("hi")
左值引用 T& 绑定左值 int& r = x;
右值引用 T&& 绑定右值 int&& r = 42;

移动构造/赋值

class String {
public:
    // 拷贝构造：深拷贝（慢）
    String(const String& o) : data(new char[o.size+1]) { strcpy(data, o.data); }
    // 移动构造：偷资源（快，O(1)）
    String(String&& o) noexcept : data(o.data), size(o.size) {
        o.data = nullptr;   // 置空源对象，防止它 delete
        o.size = 0;
    }
    ~String() { delete[] data; }
private:
    char* data; size_t size;
};

std::move：把左值转成右值

String a("hello");
String b = std::move(a);   // 调移动构造，偷 a 的资源
// a 现在是空壳，不要再用 a 的值（但可析构）

std::move 其实没"移动"任何东西——它只是把左值强制转换成右值引用，从而匹配移动构造函数。真正的"偷"在移动构造函数里发生。

移动让 vector 扩容高效

std::vector<String> v;
v.push_back(String("hi"));   // 临时 String 是右值，移动进 vector（O(1)）
// 若没有移动构造，会深拷贝（O(n)）

vector 扩容时，若元素类型有移动构造，会用移动（O(1) 搬指针），否则用拷贝（O(n)）。这就是"noexcept 移动构造"对性能的关键意义。

和 C 的区别

维度 C C++
赋值语义 总是拷贝（memcpy） 可移动（偷资源）
临时对象处理 拷贝 移动（C++11）
大对象传递 指针（手动管理） 移动（自动）
资源转移 手动搬指针（易错） 移动构造封装

C 程序员最该理解的：移动 vs 拷贝

C 里"把一个大缓冲区交给另一个变量"只能 memcpy（慢）或转移指针（手动，源对象状态要自己管）：

/* C：转移大缓冲区要么 memcpy（慢），要么手动搬指针 */
struct Buf { char* data; size_t len; };
struct Buf a = make_big_buf();   // a.data 指向 1MB 内存

// 方式1：memcpy（慢，拷贝 1MB）
struct Buf b = a;                // 1MB 拷贝
// 方式2：手动搬指针（快，但要管 a 的状态）
struct Buf b; b.data = a.data; b.len = a.len;
a.data = NULL; a.len = 0;        // 手动置空 a，否则 double free

C++ 的移动语义把"方式2"封装进移动构造，自动且安全：

Buf a = make_big_buf();          // 返回值是右值
Buf b = std::move(a);            // 移动构造：O(1) 搬指针，a 自动置空
// a 是空壳，析构安全（移动构造已置空 a.data）

这就是移动语义的价值——像指针转移一样快，但像拷贝一样安全（源对象自动处于有效状态）。

常见错误

  1. 移动后用源对象：String b = std::move(a); use(a); —— 移动后 a 处于"有效但未指定"状态（通常是空壳），用 a 的值是 UB 或逻辑错误。原则：move 后只对 a 赋值或析构，不读它的值。
  2. 移动构造不加 noexcept：vector 扩容时，只有移动构造是 noexcept 才会用移动，否则退化为拷贝（保证强异常安全）。修正：移动构造应标 noexcept（它通常不抛异常）。
  3. 以为 std::move 真的移动了：std::move(x) 只是转成右值引用，不移动任何东西。若目标类型没有移动构造，仍会拷贝。移动发生在移动构造/赋值函数内。

自测题

1. 选择题：std::move(x) 做了什么？ - A) 把 x 的内容移到别处 - B) 把 x 强制转换为右值引用 - C) 销毁 x - D) 拷贝 x

答案

B。std::move 是 static_cast<T&&> 的包装，只做类型转换（左值→右值引用），不移动任何东西。真正的移动发生在匹配的移动构造/赋值函数内。若目标类型无移动构造，auto y = std::move(x) 仍会拷贝。move 这个名字有误导性，它其实是"允许移动"的标记。

2. 判断题：移动构造函数应该标记为 noexcept。

答案

正确。移动构造通常只搬指针不分配内存，不抛异常。标 noexcept 很重要——std::vector 扩容时，只有当元素类型的移动构造是 noexcept 才会用移动（保证强异常安全），否则退化为拷贝（慢）。所以"移动构造不标 noexcept 等于没移动"是常见性能陷阱。

3. 踩坑题：下面代码想用移动提升性能，但 vector 扩容时仍拷贝，为什么？

class Big {
public:
    Big(const Big&) { /* 深拷贝 */ }       // 拷贝构造
    Big(Big&&) { /* 搬指针 */ }            // 移动构造，没标 noexcept
    /* ... */
};
std::vector<Big> v;
for (int i = 0; i < 1000; ++i) v.push_back(Big());  // 临时 Big 是右值
答案

移动构造没标 noexcept，vector 扩容时为了保证强异常安全（移动途中抛异常会丢失元素），退化为拷贝。修正：Big(Big&&) noexcept { /* 搬指针 */ }。加 noexcept 后 vector 才放心用移动，扩容 O(n) 搬指针而非 O(n) 深拷贝。这是"移动性能"最常踩的坑。

4. 应用题：写一个简单的动态字符串类，实现拷贝构造（深拷贝）和移动构造（搬指针 + noexecpt），并演示 vector<String> push_back 时的移动。

答案 
class String {
    char* data_;
    size_t size_;
public:
    String(const char* s) : data_(strdup(s)), size_(strlen(s)) {}
    // 拷贝构造：深拷贝
    String(const String& o) : data_(strdup(o.data_)), size_(o.size_) {}
    // 移动构造：搬指针，noexcept
    String(String&& o) noexcept : data_(o.data_), size_(o.size_) {
        o.data_ = nullptr; o.size_ = 0;   // 置空源
    }
    ~String() { free(data_); }
    // ...
};

std::vector<String> v;
v.reserve(10);
for (int i = 0; i < 5; ++i)
    v.push_back(String("hi"));   // 临时 String 右值，调移动构造（O(1)）
// 若没移动构造，每次 push_back 深拷贝（O(n)）

C 里要做同样的事，要么 memcpy（慢），要么手动搬指针 + 管源对象状态（易错）。C++ 移动语义把"高效转移"封装成构造函数，自动且安全。

13.4

其他应用

本节讲什么

拷贝控制的其他应用：自定义 swap、消息传递模型（Message/Folder）、动态内存管理类。重点是 swap 在赋值运算符和算法中的应用。

核心用法

自定义 swap

class HasPtr {
    friend void swap(HasPtr&, HasPtr&);
public:
    HasPtr(const std::string& s) : ps(new std::string(s)) {}
    // 用 copy-and-swap 实现赋值
    HasPtr& operator=(HasPtr rhs) {   // 注意：传值（拷贝），不是引用
        swap(*this, rhs);              // 交换 this 和 rhs
        return *this;                  // rhs 析构时释放旧资源
    }
private:
    std::string* ps;
    int i;
};
inline void swap(HasPtr& a, HasPtr& b) {
    using std::swap;
    swap(a.ps, b.ps);    // 交换指针，不拷贝 string
    swap(a.i, b.i);
}

copy-and-swap 惯用法

赋值运算符传值（而非 const 引用），调用方决定拷贝还是移动，函数内 swap，rhs 析构自动释放旧资源。一次写法同时处理拷贝赋值、移动赋值、自赋值、异常安全。

Message/Folder 模型

一个 Message 可属于多个 Folder，一个 Folder 含多个 Message。增删时两边都要更新。这种"双向关系"的资源管理是拷贝控制的综合应用。

和 C 的区别

维度 C C++
swap 手写三步交换（temp=a;a=b;b=temp） std::swap + 可自定义
赋值安全 全靠手动 copy-and-swap 惯用法
双向关系管理 手动维护两边一致性 拷贝控制封装

C 程序员的体会：

C 里赋值运算符不存在（struct 赋值是浅拷贝），要安全赋值含资源的 struct 要手写函数处理自赋值、异常、资源释放：

/* C：手动写赋值函数，处理各种边界 */
int hasptr_assign(struct HasPtr* dst, const struct HasPtr* src) {
    if (dst == src) return 0;                    // 自赋值
    char* tmp = strdup(src->ps);                  // 先分配（异常安全）
    if (!tmp) return -1;
    free(dst->ps);
    dst->ps = tmp;
    return 0;
}

C++ 的 copy-and-swap 把这些边界情况一次解决，且代码简洁：

HasPtr& operator=(HasPtr rhs) {   // 传值：自动拷贝（或移动）
    swap(*this, rhs);              // 交换
    return *this;                  // rhs 析构释放旧资源
}   // 自赋值安全（拷贝再和自己交换）、异常安全（拷贝在传值时完成）

常见错误

  1. swap 不调 std::swap 成员：自定义 swap 要 using std::swap; swap(a.x, b.x); 而非 std::swap(a.x, b.x)——前者让 ADL 找到成员类型的自定义 swap，后者强制用 std 版。对含自定义 swap 的成员类型，前者更优。
  2. copy-and-swap 传引用而非传值：operator=(const HasPtr& rhs) 传引用，则需手动拷贝，失去"自动选择拷贝/移动"的好处。传值 operator=(HasPtr rhs) 让编译器按实参是左值/右值选拷贝/移动构造。
  3. Message/Folder 忘记在拷贝/析构时同步对方：拷贝 Message 要把它加入所有原 Folder；析构要从所有 Folder 移除。漏了一边就关系不一致。

自测题

1. 选择题：copy-and-swap 惯用法中，赋值运算符的参数为什么传值（HasPtr rhs）而非 const 引用？ - A) 性能更好 - B) 让编译器按实参左值/右值自动选拷贝构造或移动构造 - C) 避免自赋值 - D) 强制深拷贝

答案

B。传值时，实参是左值则拷贝构造 rhs，是右值则移动构造 rhs——一个赋值运算符同时处理拷贝赋值和移动赋值。若传 const 引用则要手动判断并分别处理。传值 + swap 让代码简洁且自动适配拷贝/移动。自赋值也安全（拷贝出 rhs 再和自己 swap）。性能上，现代编译器可优化掉多余拷贝。

2. 判断题：自定义 swap 应该调用 std::swap 来交换成员。

答案

部分正确。应写 using std::swap; swap(a.member, b.member); —— using 后的非限定 swap 会通过 ADL（参数依赖查找）优先找成员类型的自定义 swap，找不到才用 std::swap。直接写 std::swap(a.member, b.member) 强制用 std 版，忽略成员可能的自定义 swap（性能差）。这是自定义 swap 的标准写法。

3. 踩坑题：下面 copy-and-swap 实现看似正确，但有隐患吗？

HasPtr& operator=(HasPtr rhs) {
    swap(*this, rhs);
    return *this;
}

（假设 swap 实现正确）

答案

实现本身正确（传值 + swap + rhs 析构释放旧资源）。但要注意：1) 自赋值 a = a 时，rhs 是 a 的拷贝，swap 后 a 持有拷贝的资源，rhs 持有 a 原资源并析构释放——正确但有一次多余拷贝。2) 若 HasPtr 没有移动构造，传值时 rhs 总是拷贝构造（即使实参是右值），失去移动优化。改进：提供移动构造，让传值能移动。整体上 copy-and-swap 是好惯用法，隐患小。

4. 应用题：用 copy-and-swap 为一个含 char* 的简单 String 类写赋值运算符，并说明它如何同时满足自赋值安全、异常安全、拷贝/移动统一。

答案 
class String {
    char* data_;
public:
    String(const char* s) : data_(strdup(s)) {}
    String(const String& o) : data_(strdup(o.data_)) {}          // 拷贝构造
    String(String&& o) noexcept : data_(o.data_) { o.data_=nullptr; }  // 移动构造
    ~String() { free(data_); }
    friend void swap(String& a, String& b) noexcept {
        using std::swap; swap(a.data_, b.data_);
    }
    // copy-and-swap：传值
    String& operator=(String rhs) noexcept {
        swap(*this, rhs);   // this 持有 rhs 的资源，rhs 持有 this 旧资源
        return *this;       // rhs 析构 free 旧资源
    }
};

三个保证：1) 自赋值安全——a=a 时 rhs 是 a 的拷贝（或移动），swap 后 a 持拷贝资源，rhs 持旧资源析构，正确；2) 异常安全——拷贝在传值时完成（可能抛），swap 是 noexcept，赋值体内不抛，强异常安全；3) 拷贝/移动统一——实参左值拷贝构造 rhs，右值移动构造 rhs，一个运算符搞定。这是 C++ 资源管理的优雅范式，C 无对应。

Q1拷贝构造 vs 移动构造
class Buffer {
    int *data;
    size_t size;
public:
    Buffer(size_t n) : data(new int[n]), size(n) {}
    ~Buffer() { delete[] data; }
    // 拷贝构造（深拷贝）
    Buffer(const Buffer &o) : data(new int[o.size]), size(o.size) {
        std::copy(o.data, o.data + size, data);
    }
    // 移动构造（资源转移）
    Buffer(Buffer &&o) noexcept : data(o.data), size(o.size) {
        o.data = nullptr; o.size = 0;
    }
};
Buffer make_buf() { return Buffer(1000); }
Buffer b = make_buf();  // 调用哪个构造？

b = make_buf() 调用拷贝还是移动？如果没有移动构造呢？

答案与复习指引

调用移动构造。 make_buf() 返回右值（纯右值），优先匹配移动构造（Buffer&&）。

如果没有移动构造： 调用拷贝构造——C++11 之前就是这样。移动构造是 C++11 新增的优化，把 O(n) 拷贝降为 O(1) 指针交换。

noexcept 的重要性： 标记 noexcept 后，STL 容器（如 vector）扩容时会用移动而非拷贝。未标 noexcept 的移动构造，STL 退回拷贝（保证强异常安全）。

复习： → 对象移动（C++11）

Q2三五法则
class Resource {
    int *data;
public:
    Resource(int n) : data(new int(n)) {}
    ~Resource() { delete data; }
    // 没写拷贝构造和拷贝赋值
};
Resource a(42);
Resource b = a;  // 会发生什么？

b = a 后会发生什么？什么是三五法则？

答案与复习指引

double free / 崩溃。 编译器生成的默认拷贝构造是按位拷贝——b.data = a.data（指向同一块内存）。a 和 b 析构时都 delete 同一块内存 → double free。

三五法则： 如果你需要自定义以下任何一个，就应该全部定义（或 =delete/=default）： 1. 拷贝构造 2. 拷贝赋值 3. 析构 4. 移动构造（C++11） 5. 移动赋值（C++11）

根因： 需要自定义析构（释放资源）意味着类管理资源，默认的按位拷贝会出问题（浅拷贝 → double free）。

复习： → 资源管理与三/五法则

Q3std::move 不移动
std::string s = "hello";
std::string r = std::move(s);
// s 现在是什么状态？
std::cout << s;  // 合法吗？

s 在 std::move 后是什么状态？读取 s 合法吗？

答案与复习指引

s 处于"有效但未指定"状态。 std::move 只是一个 static_cast<string&&>——它不移动任何东西。真正移动发生在 string 的移动构造函数里（把 s 的内部指针转移给 r）。

读取 s 合法但值未指定——可能是空字符串，也可能有旧值（取决于实现）。标准保证对象处于有效状态（可析构、可赋值），但不保证具体值。

教训： std::move 后不要使用原对象的值（但可以赋新值或析构）。

复习： → 对象移动（C++11）

Q4赋值运算符自赋值
class String {
    char *data;
    size_t len;
public:
    String &operator=(const String &other) {
        delete[] data;                    // A: 先释放自己的
        data = new char[other.len + 1];   // B: 分配新的
        strcpy(data, other.data);
        len = other.len;
        return *this;
    }
};
String s("hello");
s = s;  // 自赋值：会出什么问题？

自赋值时会发生什么？如何修复？

答案与复习指引

问题： this == &other 时，A 行 delete[] data 释放了自己的数据，B 行 other.data 已经是悬垂指针——strcpy 读已释放内存 = UB。

修复方案： 1. 身份检查：if (this == &other) return *this; 2. 先拷贝再释放：先 new + strcpy 到临时指针，成功后再 delete[] 旧 data，再赋值 3. copy-and-swap：String &operator=(String other) { swap(*this, other); return *this; } — 按值传参自动拷贝，swap 交换，旧数据在 other 析构时释放
