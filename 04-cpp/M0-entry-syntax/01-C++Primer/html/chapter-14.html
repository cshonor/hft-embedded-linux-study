第 14 章 操作重载与类型转换

导读

本章介绍如何让自定义类类型在直观上像内置类型一样使用，核心是通过重载机制给内置运算符赋予新含义。

章节摘要

运算符重载（让自定义类型像内置类型一样使用运算符）、函数调用运算符与函数对象（lambda 的底层机制）、类型转换运算符、输入输出运算符（>> / << 的两层身份：位运算 vs 提取/插入，重载决议怎么选、cin >> x 到底是成员还是非成员、sentry→num_get→streambuf 的分层开销）。

和 C 的区别

C C++
无运算符重载 可重载 +/-/[]/()/-> 等
函数指针回调 函数对象/lambda（可内联+有状态）
(int)x C 风格转换 可自定义类型转换运算符
14.1

运算符重载

本节讲什么

C++ 的运算符重载：为自定义类型定义 +、==、<<、[] 等运算符的行为，让自定义类型能像内置类型一样用运算符。这是 C 完全没有的特性——C 只能写函数 add(a,b)，不能写 a + b。

核心用法

成员 vs 非成员

class Complex {
public:
    Complex(double r=0, double i=0) : re(r), im(i) {}
    // 成员函数重载：左操作数是 *this
    Complex operator+(const Complex& rhs) const {
        return Complex(re + rhs.re, im + rhs.im);
    }
private:
    double re, im;
    friend std::ostream& operator<<(std::ostream&, const Complex&);
};
Complex a(1,2), b(3,4);
Complex c = a + b;   // 调 a.operator+(b)

// 非成员函数重载（如 <<，左操作数是 ostream）
std::ostream& operator<<(std::ostream& os, const Complex& c) {
    return os << c.re << "+" << c.im << "i";
}
std::cout << c;      // 调 operator<<(cout, c)

可重载的运算符

类别 运算符 建议
算术 + - * / % 通常非成员，返回新对象
关系 == != < <= > >= 非成员，返回 bool
赋值 = += -= 成员，返回 *this
下标 [] 成员，返回引用
自增自减 ++ -- 成员，前置返回引用，后置返回值
解引用/成员访问 * -> 成员
函数调用 () 成员
IO << >> 非成员（自定义类型；内置类型其实是 istream/ostream 的成员——见 14.4）

不能重载的运算符

::（作用域）、.（成员访问）、.*（成员指针访问）、?:（三元）——这四个不能重载。

和 C 的区别

维度 C C++
运算符重载 ❌ 不支持 ✅
自定义类型用运算符 只能函数 add(a,b) a + b
代码可读性 函数调用堆叠 直观的运算符表达式
与标准库集成 无 operator<</== 等让自定义类型融入 STL

C 程序员最该体会的：

C 里"复数加法"只能写函数，表达式不直观：

/* C：复数运算只能函数调用 */
struct Complex { double re, im; };
struct Complex add(struct Complex a, struct Complex b) {
    struct Complex r = {a.re+b.re, a.im+b.im}; return r;
}
struct Complex c = add(add(a, b), d);   // (a+b)+d，不直观

C++ 运算符重载让自定义类型像内置类型一样自然：

Complex operator+(Complex a, Complex b);
Complex c = a + b + d;   // 直观，且可与模板/泛型代码配合

这让自定义类型能融入标准库——例如定义 operator< 后就能用 std::sort，定义 operator<< 就能用 cout。

常见错误

  1. 滥用运算符重载导致语义混乱：给 Matrix 重载 * 做矩阵乘法合理，但给 String 重载 - 做"删字符"就反直觉。原则：重载要符合运算符的常规语义，别为了炫技乱用。
  2. operator<< 做成成员函数：ostream& operator<<(ostream&, const T&) 若是成员，左操作数是 this（T），调用变成 obj << cout，反人类。修正*：IO 运算符必须是非成员。
  3. 返回类型用错：operator+ 应返回新对象（值），不能返回引用（局部对象悬垂）；operator+= 应返回 *this 引用（支持链式 a+=b+=c）；operator[] 返回引用（支持 v[i]=x）。

自测题

1. 选择题：operator<< 应该是成员函数还是非成员函数？ - A) 成员 - B) 非成员 - C) 都行 - D) 静态成员

答案

B。<< 的左操作数是 ostream&（如 cout），不是自定义类型。若做成成员，左操作数是 *this（自定义类型），调用变成 obj << cout，反人类。非成员 operator<<(ostream&, const T&) 才能实现 cout << obj。规则：左操作数不是自定义类型（如 ostream/istream）的运算符，必须非成员。

2. 判断题：C++ 中 ::、.、.*、?: 四个运算符不能重载。

答案

正确。这四个被语言保留，不能重载。原因：它们涉及语言核心机制（作用域解析、成员访问、成员指针、条件表达式），重载会破坏基本语义。其他运算符（算术、关系、赋值、下标、调用等）大多可重载。

3. 踩坑题：下面 operator+ 实现有问题吗？

Complex& operator+(const Complex& rhs) const {
    Complex result(re + rhs.re, im + rhs.im);
    return result;   // 返回局部对象的引用
}
答案

返回局部对象的引用，悬垂引用 UB。result 在函数返回时销毁，返回的引用指向已释放内存。修正：返回值类型 Complex（不是引用）：

Complex operator+(const Complex& rhs) const {
    return Complex(re + rhs.re, im + rhs.im);   // 返回值，可能 NRVO 优化
}

规则：operator+/-/* 等产生新值的运算符返回值；operator+=/==/[] 返回引用（操作已有对象）。

4. 应用题：为 Fraction（分数）类重载 +、==、<<，使其能 Fraction a(1,2), b(1,3); cout << (a+b) << (a==b);。说明哪些成员哪些非成员。

答案 
class Fraction {
public:
    Fraction(int n, int d=1) : num(n), den(d) {}
    // == 成员或非成员都行，这里用非成员（对称，允许左右都隐式转换）
    friend bool operator==(const Fraction& a, const Fraction& b) {
        return a.num*b.den == b.num*a.den;
    }
    friend std::ostream& operator<<(std::ostream& os, const Fraction& f);
    int num, den;
};
// + 非成员（对称）
Fraction operator+(const Fraction& a, const Fraction& b) {
    return Fraction(a.num*b.den + b.num*a.den, a.den*b.den);
}
// << 非成员（左操作数 ostream）
std::ostream& operator<<(std::ostream& os, const Fraction& f) {
    return os << f.num << "/" << f.den;
}

+/==/<< 都非成员：+/== 非成员保证左右操作数对称（都能隐式转换）；<< 必须非成员（左操作数是 ostream）。二元算术/关系运算符推荐非成员，赋值/下标/调用/自增等推荐成员。C 无法这样让 a + b == c 自然表达，只能 eq(add(a,b), c)。

14.2

函数调用运算符与函数对象

本节讲什么

重载 operator() 让类对象能像函数一样调用，这样的对象叫函数对象（functor）。C++11 的 lambda 本质就是编译器自动生成的函数对象。这是 C 函数指针的强力替代品——函数对象能携带状态、可内联。

核心用法

函数对象

class Adder {
public:
    Adder(int n) : n_(n) {}
    int operator()(int x) const { return x + n_; }   // 重载 operator()
private:
    int n_;
};

Adder add5(5);
std::cout << add5(10);   // 15，像函数一样调用

函数对象相比函数指针的优势：1) 能携带状态（n_ 是状态）；2) 可内联（编译器知道具体类型，能内联 operator()）。

STL 中的函数对象

std::sort(v.begin(), v.end(), std::greater<int>());   // greater 是函数对象
// greater<int> 临时对象，operator() 比较

std::accumulate(v.begin(), v.end(), 0, std::plus<int>());   // plus 函数对象

lambda 是函数对象的语法糖

int n = 5;
auto add5 = [n](int x) { return x + n; };   // lambda 捕获 n

// 等价于编译器生成：
class __lambda {
    int n;
public:
    __lambda(int n) : n(n) {}
    int operator()(int x) const { return x + n; }
} add5(n);

lambda 让你不用手写函数对象类，编译器自动生成。

标准库 function（C++11）

#include <functional>
std::function<int(int)> f = add5;       // 存函数对象
f = [](int x){ return x*2; };            // 存 lambda
f = &some_func;                          // 存函数指针
// f 统一存储任意可调用对象

和 C 的区别

维度 C C++
回调机制 函数指针 函数指针 / 函数对象 / lambda / function
携带状态 ❌（函数指针无状态） ✅ 函数对象/lambda 捕获
内联 ❌ 函数指针不可内联 ✅ 函数对象/lambda 可内联
类型统一 void(*)(int) std::function<int(int)> 统一

C 程序员最该体会的：

C 的回调只能用函数指针，无法携带状态（除非全局变量，非线程安全），且不可内联（慢）：

/* C：qsort 比较函数用函数指针，无法带状态 */
int threshold;   // 全局！非线程安全
int cmp(const void* a, const void* b) {
    return (*(int*)a > threshold) - (*(int*)b > threshold);
}
qsort(arr, n, sizeof(int), cmp);   // 间接调用，不可内联

C++ 的函数对象/lambda 携带状态 + 可内联，且类型安全：

int threshold = 5;
std::sort(v.begin(), v.end(),
    [threshold](int a, int b){ return a > threshold && !(b > threshold); });
// lambda 捕获 threshold（线程安全），编译器可内联 operator()

这是 C→C++ 在"回调表达力和性能"上的双重提升。

常见错误

  1. lambda 捕获引用后悬垂：auto f = [&x]{ return x; }; 出了 x 作用域后调 f，悬垂。修正：长期持有的 lambda 按值捕获 [x]。
  2. std::function 性能误解：std::function 有类型擦除开销（间接调用 + 可能堆分配），比直接函数对象/lambda 慢。热路径优先模板 + 函数对象，std::function 用于"需要存储异质可调用对象"的场景。
  3. lambda 的 mutable：按值捕获的变量在 lambda 内默认 const，要修改加 mutable：[n] mutable { n++; }（改的是拷贝，不影响外部）。

自测题

1. 选择题：下面关于函数对象和 lambda 的说法正确的是？ - A) lambda 不是函数对象 - B) 函数对象不能携带状态 - C) lambda 本质是编译器生成的函数对象 - D) 函数对象不能用于 STL 算法

答案

C。lambda 本质是编译器为每个 lambda 生成的未命名函数对象类的对象——捕获的变量是成员，lambda 体是 operator()。函数对象能携带状态（成员变量），能用于 STL（greater<> 等就是函数对象）。所以 A/B/D 都错。

2. 判断题：std::function 比直接用函数对象/lambda 性能更好。

答案

错误。std::function 用类型擦除存储任意可调用对象，有运行时开销（间接调用 + 可能堆分配捕获的状态），通常比直接用函数对象/lambda（编译器已知具体类型，可内联）慢。std::function 的价值是"统一存储异质可调用对象"（如存到容器、做回调接口），热路径优先模板 template<class F> void g(F f) + 直接传函数对象/lambda。

3. 踩坑题：下面 lambda 想统计调用次数，但改不动 count，为什么？

int count = 0;
auto f = [count]{ count++; return count; };
答案

按值捕获的 count 在 lambda 内默认是 const（operator() 是 const 成员），count++ 编译错误。修正：加 mutable 让 operator() 非 const，从而能改值捕获的拷贝：

auto f = [count] mutable { count++; return count; };

注意：改的是 count 的拷贝，不影响外部 count。要改外部 count 用引用捕获 [&count]。这是 lambda 的常见困惑点。

4. 应用题：用函数对象实现一个"带阈值的过滤器"，能用于 std::remove_if。对比 C 的函数指针方案。

答案 
class ThresholdFilter {
    int threshold_;
public:
    ThresholdFilter(int t) : threshold_(t) {}
    bool operator()(int x) const { return x < threshold_; }   // 携带 threshold 状态
};
int threshold = 5;
v.erase(std::remove_if(v.begin(), v.end(), ThresholdFilter(threshold)), v.end());
// 或直接 lambda：v.erase(std::remove_if(v.begin(), v.end(), [threshold](int x){return x<threshold;}), v.end());

C 的函数指针方案：threshold 只能用全局变量（非线程安全），且函数指针不可内联（慢）：

int g_threshold;   // 全局！
int filter(int x) { return x < g_threshold; }
/* remove_if 无 C 标准库等价，手写循环用 filter */

函数对象/lambda 携带状态（线程安全）+ 可内联（快），是 C 函数指针的全面升级。

14.3

类型转换运算符

本节讲什么

类型转换运算符：定义自定义类型向其他类型的转换，如 operator int() const 让对象能隐式转 int。重点是隐式转换的危险和 explicit 的作用。

核心用法

定义转换

class Fraction {
public:
    Fraction(int n, int d=1) : num(n), den(d) {}
    // 转换为 double
    operator double() const { return double(num) / den; }
private:
    int num, den;
};
Fraction f(1, 2);
double d = f;          // 隐式调用 operator double()，d = 0.5

explicit 转换（C++11）

class Fraction {
public:
    explicit operator double() const { return double(num)/den; }   // explicit
};
Fraction f(1,2);
// double d = f;          // 错误：explicit 禁止隐式转换
double d = static_cast<double>(f);   // OK：显式转换

explicit 防止意外的隐式转换，只允许显式 static_cast。

转换为 bool

class Stream {
public:
    explicit operator bool() const { return !failed_; }   // explicit bool
private:
    bool failed_ = false;
};
Stream s;
if (s) { /* s 转 bool 为真 */ }   // OK：if/while 条件中 explicit bool 仍可用
bool b = s;                       // 错误：explicit 禁止隐式

operator bool 几乎总是应该 explicit——否则对象会在各种意外处转 bool（如 int x = obj + 1 可能先转 bool 再加）。

和 C 的区别

维度 C C++
自定义类型转换 ❌ 无（只能写函数） ✅ 转换运算符
隐式转换控制 无机制 explicit 限制
内置类型互转 算术转换规则 一致 + 自定义类型可参与

C 程序员的理解：

C 里"把 Fraction 转 double"只能写函数：

double fraction_to_double(struct Fraction f) { return (double)f.num / f.den; }
double d = fraction_to_double(f);   // 显式函数调用

C++ 的转换运算符让转换"自动"发生，但这也带来风险——隐式转换可能在不经意处触发。所以 C++11 引入 explicit 限制，让你控制"只允许显式转换"。

常见错误

  1. 隐式转换导致意外行为：operator int() 让对象在任何需要 int 处隐式转换，可能引发意外（如 obj + 1 把对象转 int 再加）。修正：加 explicit，或避免定义转换运算符，改用具名函数 to_int()。
  2. 转换二义性：同时定义 operator int() 和 operator double()，在 obj + 1.0 时编译器不知道转 int 还是 double，二义性。修正：只定义一个，或都 explicit 用时显式转。
  3. operator bool 不加 explicit：非 explicit 的 bool 转换会让对象在算术运算中意外转 bool 再转 int（如 obj + 1 变成 bool(obj) + 1）。修正：explicit operator bool。

自测题

1. 选择题：下面代码合法吗？

class C { public: explicit operator int() const { return 42; } };
C obj;
int x = obj;
  • A) 合法，x=42
  • B) 编译错误：explicit 禁止隐式转换
  • C) 运行错误
  • D) 合法，x 未定义
答案

B。explicit operator int 禁止隐式转换，int x = obj 是隐式转换，编译错误。修正：int x = static_cast<int>(obj); 显式转换。例外：explicit operator bool 在 if/while/! 等条件上下文中仍可用（语言特例，称"contextual conversion"），因为 bool 转换在条件中太常用。

2. 判断题：定义 operator bool() 时建议加 explicit。

答案

正确。非 explicit 的 operator bool 会让对象在算术运算中意外转 bool 再转 int（如 obj + 1 变成 (bool)obj + 1，结果 0 或 1 加 1）。加 explicit 后，bool 转换只在条件上下文（if/while/!）触发，避免意外，同时保留 if (obj) 的便利。这是 C++11 的最佳实践。

3. 踩坑题：下面代码报"二义性"错误，为什么？

class C {
public:
    operator int() const { return 1; }
    operator double() const { return 1.0; }
};
C obj;
double d = obj + 1.0;   // 二义性
答案

obj + 1.0 中，编译器可以把 obj 转 int 再加 1.0，或转 double 再加 1.0，两个转换路径都合理，二义性报错。修正：1) 只保留一个转换运算符；2) 都加 explicit，用时显式 static_cast<double>(obj) + 1.0；3) 改用具名函数 to_int()/to_double() 避免隐式转换。原则：避免定义多个隐式转换运算符，易二义。

4. 应用题：为一个"安全 bool"的 File 类设计 operator bool（文件打开成功为真），说明为什么要 explicit。

答案 
class File {
public:
    explicit operator bool() const { return fp_ != nullptr; }
private:
    FILE* fp_ = nullptr;
};
File f("a.txt");
if (f) { /* 文件打开成功 */ }    // OK：条件上下文，explicit bool 可用
f + 1;                           // 错误：explicit 禁止算术中转 bool

要 explicit 因为：1) 防止 f + 1 这类算术意外把 f 转 bool 再转 int（0/1+1）；2) 防止 int n = f 这种意外赋值；3) 保留 if (f) 的便利（条件上下文允许 explicit bool）。这是 C++11 的"safe bool idiom"，比 C++03 的复杂 hack 简洁得多。C 里 FILE* 直接当 bool 用（NULL 检查），但 C++ 包装类需要 explicit operator bool 才安全。

14.4

输入输出运算符

本节讲什么

>> 和 << 是 C++ 里唯一一对「同一个符号、两套完全不同的语义」的运算符：

int a = 8 >> 1;      // ① 内置右移：位运算，4
std::cin >> x;       // ② 提取运算符：从流里读入数据，塞进 x

第①种和 C 一模一样；第②种是重载出来的函数。本节讲清楚三件事：

  1. 编译器是怎么区分这两种身份的（不是"看符号"，是看操作数类型的重载决议）；
  2. cin >> x 实际调用的到底是成员函数还是自由函数（答案和很多教程说的不一样）；
  3. 一次 >> 在底层走了几层，以及为什么 HFT 热路径不能用它。

前置：14.1 运算符重载（成员 vs 非成员）、8.1 IO 类体系、1.2 初识输入输出。

一句话区分：看左操作数的类型

判定规则不是"看符号长什么样"，而是看操作数里有没有类类型。

对任意 a >> b，编译器按 [over.match.oper] 组候选集：

情况 候选集 结果
a、b 都是内置算术/枚举类型 只有内置候选（整型提升后的各种 L operator>>(L, R) 组合） 位右移
至少一个是类类型/枚举 ① a.operator>>(b) 成员候选 ② 非成员 operator>>(a,b)（普通查找 + ADL） ③ 内置候选 走重载决议，选最优可行函数

所以：

  • 8 >> 1：int 和 int，没有类类型 → 只有内置候选 → 位运算，编译后就是一条 sar 指令；
  • cin >> x：cin 是 std::istream（类类型）→ 进入重载决议 → 在 istream 的成员里找到 operator>>(int&)。

⚠️ 常见误解：以为"是 IO 还是位运算"看符号在不在 cin 旁边。真正决定的是左操作数的类型。 写 my_class >> 2（左操作数是自定义类）照样会去查 my_class::operator>>，查不到才报错。

词法层面的证据：>> 曾经真的会打架

这两层身份的冲突不只是"语义上容易混淆"——C++03 时代它在词法分析阶段就是一个真 bug 源：

std::vector<std::vector<int> >  v;   // C++03 必须写 "> >"，中间加空格
std::vector<std::vector<int>>   v;   // C++03 编译错误；C++11 起合法

原因：词法用最大匹配（maximal munch），>> 是一个 token，不会被自动拆成两个 >。 C++11 在 [temp.names] 加了一条特判：>> 用于关闭两个嵌套模板参数列表时，视为两个 >。

→ 这是">> 有两层身份"最硬的证据：如果不是真的冲突过，标准根本不需要打这个补丁。

cin >> x 调的到底是谁？——不是 operator>>(cin, x)

很多教程（包括本仓库早期表述）写：cin >> x 等价于 operator>>(cin, x)。 对内置类型，这句话是错的。 精确答案分三类（签名以 cppreference/标准为准）：

右操作数类型 选中的函数 身份 声明位置
short/int/long/long long + unsigned 版、float/double/long double、bool、void* std::istream::operator>>(T&) 成员函数 <istream>
char / signed char / unsigned char operator>>(istream&, CharT&) 非成员自由函数 <istream>
char*（C++20 前）/ char (&)[N]（C++20 起） 非成员 非成员自由函数 <istream>
std::string operator>>(istream&, string&) 非成员自由函数 <string>
自定义类型 T 你自己写的 operator>>(istream&, T&) 非成员自由函数（必须） 你的头文件
操纵符，如 std::ws operator>>(istream& (*)(istream&)) 成员函数（第 17 号重载） <istream>
std::streambuf* operator>>(basic_streambuf*) 成员函数（第 18 号） <istream>

为什么会分成两半？ 一条设计约束：

左操作数是 std::istream（你已经关上源码的标准类）→ 只能用成员； 左操作数是 istream 但你没法给它加成员（char/string/自定义类型都是后加的）→ 只能用非成员。

所以 cin >> x（x 是 int）的真身是 cin.operator>>(x)，写成自由函数形式反而编不过：

int x;
std::cin >> x;                    // ✅ 成员版：std::istream::operator>>(int&)
// operator>>(std::cin, x);       // ❌ 编译错误：标准库根本没有 operator>>(istream&, int&)

验证方法（取成员函数指针，能取到就证明它是成员）： cpp std::istream& (std::istream::*pmf)(int&) = &std::istream::operator>>; // ✅ 能编译 反过来，你能给 std::string 写 operator>>(std::cin, s) 显式调用——因为那个版本确实是非成员。

⚠️ 实测状态：本仓库当前环境没有可用的 C++ 编译器（WSL 被安全策略拦截，本机 clang 无 libc 头文件、 无 MSVC），本节示例代码未实编译。上面所有签名与行为结论取自标准条款与 cppreference （basic_istream::operator>>、operator>>(std::basic_istream)、operator<<,>>(std::basic_string)、 basic_ios::operator bool），不是实测输出。

三个容易讲错的细节（cppreference 逐条核对）

  1. 第 17 号操纵符重载的返回值不是 *this，而是 func(*this) （1–16、18 都返回 *this，只有 17 直接返回操纵符的返回值；效果上等价，因为操纵符自己就返回流引用）。
  2. short / int 不是直接抽 short / int：内部先当 long 抽出来，再做范围检查 （LWG 118 / LWG 661）。越界时写 numeric_limits<T>::min() / max() 并置 failbit。
  3. operator>>(istream&, char&) 有特例：抽到流的最后一个字符时不置 eofbit （与 scanf("%c") 行为一致），但抽最后一个 int 会置 eofbit。

为什么返回 istream&：链式 + 状态

std::cin >> a >> b;        // 等价于 (cin.operator>>(a)).operator>>(b)
if (std::cin >> x) { }     // 流直接当条件用
while (std::cin >> x) { }  // 惯用输入循环

返回引用（不是值、不是 void）同时服务两件事：

需求 靠什么实现
链式调用 >> a >> b 返回 *this 的引用，下一次 >> 的左操作数还是同一个流
if (cin >> x) 能判断成败 流到 bool 的转换：explicit operator bool()，返回 !fail()

operator bool 的演化（版本断崖，C++ 程序员最爱踩）：

标准 形态 出处
C++98 原始 operator void*() 空指针 = 失败
C++98 + LWG 468 「unspecified boolean type」（Safe Bool 惯用法） 修 safe bool 问题
C++11 起（LWG 1094） explicit operator bool() const 现在的安全写法

explicit 是关键：允许 if (cin)，但禁止 int n = cin; 这类意外的整型转换。 这也是 C++ 面试常考的「为什么 C++98 不能直接用 operator bool」——答：会静默转成 int。

一次 >> 在底层走了几层

std::cin >> price        （price 是 double）
  │
  ├─ ① istream::operator>>(double&)             ← 重载决议选中（成员）
  │     ├─ ② sentry 构造：检查 good() → 若 tie() 了就 flush 对方 → 若 skipws 则跳过前导空白
  │     ├─ ③ std::num_get<char>::get(loc, ...)  ← locale facet，做真正的"字符→数字"解析
  │     │     └─ ④ 逐字符 sgetc()/sbumpc()      ← 经 basic_streambuf（虚调用）
  │     │           └─ ⑤ filebuf::underflow()   ← 缓冲空了才 refill
  │     │                 └─ ⑥ read(2)          ← 真正的系统调用
  │     ├─ 解析失败 → setstate(failbit)，value = 0
  │     └─ ⑦ 返回 *this
  • 第 ② 步 sentry 是每次格式化输入都要付的固定成本：状态检查 + tie 刷新 + 跳空白。
  • 第 ③ 步 num_get 是 locale 依赖的 facet——虚派发，且意味着解析行为随全局 locale 变化（千分位、小数点都是 facet 决定的）。
  • 第 ⑥ 步不是每次都发生：只有 streambuf 缓冲耗尽才 refill（所以 strace 里 read 次数远少于 >> 次数）。

失败语义（写代码时必知）

输入情况 写入 value 的值 流状态
类型不匹配（期望 int 来了字母） 0 failbit
有符号整型溢出（太大） numeric_limits<T>::max() failbit
有符号整型溢出（太小） numeric_limits<T>::min() failbit
无符号整型溢出（任一侧） numeric_limits<T>::max() failbit
std::string 版一个字符都没读到 先 str.erase() 清空，无字符则置位 failbit

「失败时把值置 0」不是从 C++98 就有的：原始标准写的是"value 不变"， 后来 LWG 696 改成置 0 / min / max。写跨平台老代码时要留意。 失败后不 clear() 就继续读，后续所有 >> 会静默失败——详见 8.2 管理条件状态。

自定义类型的 operator>>：规范写法

必须为非成员（左操作数是 istream，你不能给标准库加成员）。两种写法：

写法 A：委托给标准版本（推荐，自动获得 sentry 与 failbit 语义）

#include <iomanip>   // std::setw
#include <iostream>
#include <string>

// HFT 场景：一条行情快照的文本记录，格式 "AAPL 187.32 100"
struct Tick {
    char   symbol[8];     // 定长字段（HFT 里常见，避免动态分配）
    double price;
    int    qty;
};

std::istream& operator>>(std::istream& is, Tick& t) {
    // ⚠️ char 数组版本（C++20 前）不知道数组有多长 —— 必须显式 setw，否则就是缓冲区溢出
    is >> std::setw(sizeof t.symbol) >> t.symbol;
    is >> t.price >> t.qty;
    return is;                       // 返回流引用，支持链式 + while (is >> t)
}

std::ostream& operator<<(std::ostream& os, const Tick& t) {
    return os << t.symbol << ' ' << t.price << ' ' << t.qty;
}

int main() {
    Tick t;
    // while (std::cin >> t) { std::cout << t << '\n'; }
    return 0;
}

C++20 起数组版本改成 CharT (&s)[N]，编译器知道 N，上面那个 setw 就不需要了 （但 char* 指针版同时被移除）。这正是 C++20 修这个坑的方式。

写法 B：自己管 sentry（需要自定义解析逻辑时）

std::istream& operator>>(std::istream& is, Tick& t) {
    std::istream::sentry s(is);   // ① 跳空白 + 检查状态 + flush tie
    if (!s) return is;            // ② 约定：失败就原样返回，不碰 t

    std::string sym;
    double px; int q;
    is >> sym >> px >> q;
    if (is.fail() || px <= 0) {           // ③ 业务校验也算失败
        is.setstate(std::ios::failbit);   //    必须置位，否则 while (is >> t) 死循环
        return is;
    }
    std::snprintf(t.symbol, sizeof t.symbol, "%s", sym.c_str());
    t.price = px; t.qty = q;
    return is;
}

三条铁律： 1. 返回 istream&（不是 void、不是值）； 2. 失败时自己置 failbit——这是调用方 while (is >> t) 唯一的退出依据； 3. 放在与类型同一个命名空间里，靠 ADL 被找到（不要往 namespace std 里塞）。

和 C 的区别

维度 C（scanf） C++（>>）
怎么知道要读什么类型 运行期解析格式串 "%d %lf" 编译期重载决议（istream::operator>>(double&)）
写错类型的后果 %d 配 double → 静默 UB 编译期选中正确重载，不可能选错
忘 & scanf("%d", v) → 崩溃 >> 的参数声明就是 T&，不存在的错误类别
成败判断 返回成功项数（要自己比对 == 3） if (is >> a >> b)（靠 explicit operator bool）
可扩展到自定义类型 ❌ 只能另写函数 ✅ 重载 operator>>
局部性/locale setlocale 影响 LC_NUMERIC 每个流自带 locale（imbue()）
缓冲 FILE* 自带 istream → streambuf → 可换（rdbuf()）

HFT / 嵌入式关联

热路径为什么不用 >>

一次 >> 的固定开销构成（对照上面分层图）：

层 开销来源
sentry 状态检查 + tie() 的 flush（cin 默认 tie 到 cout！）
locale facet 虚派发 num_get::get，解析行为随 locale 变化
逐字符取数 每个字符一次 sgetc() 虚调用
格式化状态 flags() / width() / precision() 每轮参与

两条立刻能做、且只解决部分问题的优化：

std::ios::sync_with_stdio(false);   // 关掉与 C stdio 的同步（1.2 已提）
std::cin.tie(nullptr);              // 解掉 cin→cout 的 tie，省掉每次读之前的 flush

注意：这两条只去掉同步和 tie，facet 与逐字符虚调用一点没少。 真正的做法是别用格式化输入： - C++17 std::from_chars：无 locale、无分配、无异常，返回 errc； - 定长二进制协议：read() 直接读结构体 / 自研 SIMD 解析（见 14-hft-engineering）； - 冷路径（配置加载、回放、日志、调试输出）用 >> 完全没问题——先分清热冷，再谈优化。

量测方法（不要凭感觉下结论）：

# ① read(2) 次数 —— 验证 streambuf 缓冲确实在起作用
strace -e trace=read -c ./a.out < market.txt
# ② 采样看热点是不是落在 num_get / underflow 上
perf record -g ./a.out < market.txt && perf report | grep -i 'num_get\|underflow\|operator>>'

嵌入式视角

  • #include <iostream> 会引入 静态初始化（std::ios_base::Init 保护 cout/cin 的构造顺序）， 在看重启动时间 / 固件体积的场景是实打实的成本；
  • locale 的全局状态在无 MMU / 资源受限环境是负担，很多嵌入式工具链的 libstdc++ 裁掉了完整 locale；
  • 结论与 HFT 一致：控制面用 >>，数据面用定长解析。

常见错误

  1. 把 operator>> 写成成员函数 cpp struct Tick { std::istream& operator>>(std::istream&); }; // ❌ 成员版的左操作数是 *this（Tick），调用变成 t >> cin，语义反了。IO 运算符必须非成员。
  2. 以为 cin >> x 等于 operator>>(cin, x) —— 对 int/double 等内置类型是成员调用， 写成自由函数形式直接编译不过（见前文表格）。
  3. 忘了 >> 遇空白即停：cin >> name 只读一个词，整行要用 std::getline （见 1.2 初识输入输出）。
  4. 失败后不 clear()：failbit 一旦置位，后面所有 >> 静默失败， 典型症状是"循环只读了一次就退出"（见 8.2 管理条件状态）。
  5. 自定义 operator>> 不置 failbit：while (is >> t) 变成死循环。
  6. char buf[8]; is >> buf;（C++20 前）没加 setw —— 输入超长就是缓冲区溢出。 改用 std::string，或 is >> std::setw(sizeof buf) >> buf。
  7. 右值当目标：cin >> (a + b) 编译错误——>> 的右操作数是 T&（非 const 左值引用）。

自测题

1（选择） int x; std::cin >> x; 选中的函数是： - A. std::operator>>(std::istream&, int&) - B. std::istream::operator>>(int&) - C. 内置右移运算符 - D. 由编译器运行时决定

答案

B。 int 走的是 basic_istream 的成员重载。标准库没有 operator>>(istream&, int&) 这个自由函数 （你可以写 std::istream& (std::istream::*p)(int&) = &std::istream::operator>>; 验证它确实是成员）。 非成员版本只有 char& / char[N] / std::string& / rvalue 流这几类。 C 错：左操作数是类类型，进入重载决议不是内置运算符。D 错：重载决议在编译期完成。

2（判断） 下面两行在 C++03 里都能编译：

std::vector<std::vector<int>>  a;   // ①
std::vector<std::vector<int> > b;   // ②
答案

只有 ② 能过。 C++03 词法用最大匹配，>> 是单个 token，① 会被解析成「右移」而报错。 C++11 在 [temp.names] 加了特判，>> 在关闭两个嵌套模板参数列表时视为两个 >，① 才合法。 → 这是「>> 两层身份真的冲突过」的直接证据，不只是教学上的比喻。

3（踩坑） 输入 abc 后，这段代码的 x 是多少？

int x = 42;
std::cin >> x;      // 用户输入 abc
std::cout << x;
答案

0（不是保持 42）。类型不匹配 → 置 failbit，并把 0 写入 value（LWG 696 起的规定）。 有符号整型溢出则写 numeric_limits<T>::max() / min()。 另外：failbit 不清除，后续所有读取都会静默失败，必须 cin.clear() + cin.ignore(...)。

4（机制） 为什么 operator>> 必须返回 istream& 而不是 void？给出两个理由。

答案
  1. 链式调用：cin >> a >> b = (cin.operator>>(a)).operator>>(b)，返回引用才能把同一个流接下去；
  2. 状态判断：if (cin >> x) / while (cin >> x) 依赖流 → bool 的转换 （C++11 起是 explicit operator bool()，返回 !fail()）。 返回 void 两个都做不到；返回值（非引用）会拷贝流对象（而且 basic_istream 不可拷贝）。

5（应用） 给 struct Price { int64_t ticks; }; 写 operator>>，要求：输入 18732 表示 187.32 （即 ticks = 18732，隐含两位小数）；非法输入（负数、超范围、非数字）必须让 while (is >> p) 正常退出。

答案 
#include <cstdint>
#include <istream>
#include <charconv>     // C++17 from_chars（热路径推荐）
#include <string>

struct Price { std::int64_t ticks; };

std::istream& operator>>(std::istream& is, Price& p) {
    std::string tok;
    if (!(is >> tok)) return is;            // sentry + 跳空白 + 失败直接返回

    std::int64_t v = 0;
    const char* first = tok.data();
    const char* last  = tok.data() + tok.size();
    auto [ptr, ec] = std::from_chars(first, last, v);   // 无 locale、无分配、无异常
    if (ec != std::errc{} || ptr != last || v < 0) {    // 解析失败 / 有残留字符 / 负数
        is.setstate(std::ios::failbit);                 // ⭐ 必须置位，否则 while 死循环
        return is;
    }
    p.ticks = v;
    return is;                                          // ⭐ 返回流引用
}

三个必考点：① 非成员；② 失败时 setstate(failbit)；③ 返回 istream&。 用 from_chars 而非 stoll 的理由：stoll 会抛异常、受 locale 影响；from_chars 是热路径首选。

章节自测

Q1成员 vs 非成员
class Money {
    int cents;
public:
    Money(int c) : cents(c) {}
    Money operator+(const Money &rhs) const { return Money(cents + rhs.cents); }
};
Money m(100);
// m + 50;    // A: 合法吗？
// 50 + m;    // B: 合法吗？

A 和 B 分别合法吗？如何让 B 也合法？

答案与复习指引

A: 合法。 m + 50 等价于 m.operator+(50)，50 隐式转换为 Money(50)。 B: 编译错误。 50 + m 等价于 50.operator+(m)，int 没有 operator+ 成员接受 Money。

修复： 用非成员函数重载：

Money operator+(const Money &lhs, const Money &rhs) {
    return Money(lhs.get_cents() + rhs.get_cents());
}

非成员函数允许左右操作数都隐式转换。

规则： 如果左操作数可能需要隐式转换，用非成员函数；如果必须访问私有成员且不需要左操作数转换，用成员函数。

复习： → 运算符重载

Q2函数对象
class Multiplier {
    int factor;
public:
    Multiplier(int f) : factor(f) {}
    int operator()(int x) const { return x * factor; }
};
Multiplier triple(3);
std::cout << triple(5);  // 输出什么？

输出是什么？函数对象和函数指针有什么区别？

答案与复习指引

输出： 15 — triple(5) 调用 operator()(5) 即 5 * 3

和函数指针的区别： 1. 有状态：函数对象可保存数据（factor），函数指针不行 2. 可内联：编译器能看到函数对象类型，可内联 operator()；函数指针是间接调用，难以内联 3. STL 算法接受函数对象：std::sort(v.begin(), v.end(), Multiplier(3)) — 有状态的比较器

lambda 本质： lambda 就是匿名函数对象——编译器为每个 lambda 生成一个含 operator() 的类。

Q3类型转换运算符
class IntWrapper {
    int value;
public:
    IntWrapper(int v) : value(v) {}
    operator int() const { return value; }  // 隐式转换
};
IntWrapper w(42);
int x = w;        // A: 合法？
int y = w + 10;   // B: 合法？

A 和 B 合法吗？隐式转换有什么风险？

答案与复习指引

A 和 B 都合法。 operator int() 允许 IntWrapper 隐式转换为 int。

风险： 隐式转换可能在你不期望的地方发生——函数期望 int 参数但传了 IntWrapper，静默转换可能隐藏 bug。多个转换路径会导致二义性。

最佳实践： 用 explicit 修饰转换运算符（C++11 起），禁止隐式转换：

explicit operator int() const { return value; }
// int x = w;       // 编译错误
// int x = static_cast<int>(w);  // OK

Q4>> 的两层身份
int x = 42, a = 8 >> 1;
std::cin >> x;              // ①
// operator>>(std::cin, x); // ②

① 和 ② 等价吗？8 >> 1 和 cin >> x 的 >> 是同一个东西吗？

答案与复习指引

不等价。 ① 编译通过；② 编译错误 —— 标准库没有 operator>>(istream&, int&) 这个自由函数。

关键区分：

写法 >> 的身份 选中谁
8 >> 1 内置右移（位运算） 操作数都是 int，只有内置候选 → 一条 sar 指令
cin >> x（x 是 int/double） 提取运算符 成员 std::istream::operator>>(int&)
cin >> s（s 是 string/char/char[N]） 提取运算符 非成员 operator>>(istream&, string&) 等
cin >> my_obj 提取运算符 你自己写的非成员 operator>>（靠 ADL 找到）

判定规则：不是看符号在谁旁边，而是看左操作数的类型 —— 只要有一个操作数是类类型就进入重载决议（成员候选 + 非成员候选 + ADL + 内置候选）， 否则只有内置候选，就是位运算。

冷的证据：C++03 写 vector<vector<int>> 必须改成 > >——>> 是单个 token（最大匹配）， C++11 才在 [temp.names] 打补丁允许它关闭两个模板参数列表。说明这两层身份在词法阶段就真冲突过。
