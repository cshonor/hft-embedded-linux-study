导读

类是 C++ 最基本的特性，核心思想是数据抽象（Data Abstraction）和封装（Encapsulation）。本章引导读者从零设计类，控制对象的初始化与权限。

章节摘要

类的核心概念：数据抽象与封装。包括定义抽象数据类型、this 指针、访问控制（public/private/protected）、友元、构造函数、类的静态成员。

和 C 的区别

C struct C++ class
只有数据 数据 + 函数（成员函数）
无访问控制 public/private/protected
无构造/析构 自动调用构造/析构
无 this 隐式 this 指针
无静态成员 static 成员
7.1

定义抽象数据类型

本节讲什么

如何用 class 定义一个抽象数据类型（ADT）：把数据和相关操作捆绑在一起，对外暴露接口、对内隐藏实现。核心概念是隐式 this 指针和const 成员函数。这是 C 转 C++ 最重要的范式转变——C 的 struct 只是数据集合，C++ 的 class 是数据+行为。

核心用法

一个完整的 ADT 示例

#include <string>
#include <iostream>

class Sales_data {
public:
    // 成员函数（接口）
    const std::string& isbn() const { return bookNo; }   // const 成员函数
    Sales_data& combine(const Sales_data&);              // 返回 *this，可链式调用
    double avg_price() const;

private:
    // 数据成员（实现）
    std::string bookNo;
    unsigned units_sold = 0;   // 类内初始值（C++11）
    double revenue = 0.0;
};

// 类外定义成员函数
Sales_data& Sales_data::combine(const Sales_data& rhs) {
    units_sold += rhs.units_sold;
    revenue += rhs.revenue;
    return *this;              // 返回调用对象自身的引用
}

this 指针

成员函数内部，this 是一个隐式参数，指向调用该函数的对象：

total.combine(trans);
// 编译器把它理解为：
// Sales_data::combine(&total, trans);
// 函数内 this == &total，*this == total

从自由函数到成员函数（汇编实测）

写游戏代码常先用 C 思维组织——操作写成自由函数，显式传对象：

struct Player { int x, y; int speed; };

void Move(Player& player, int xa, int ya) {   // 自由函数：显式传 Player&
    player.x += xa * player.speed;
    player.y += ya * player.speed;
}
// 调用：Move(player, 1, -1);

把它收进类里、去掉第一个参数，就成了成员函数：

struct Player {
    int x, y;
    int speed;
    void Move(int xa, int ya) {   // 那个 Player& 参数没有消失，变成了隐藏的 this
        x += xa * speed;          // 编译器眼里：this->x += xa * this->speed
        y += ya * speed;
    }
};
// 调用：player.Move(1, -1);

成员函数 = 自由函数 + 隐藏的 Player* this 参数。实测（-target x86_64-pc-windows-msvc -O0，MSVC ABI 用 rcx/edx/r8d 传前三个参数）：

"?Move@@YAXAEAUPlayer@@HH@Z"      ; 自由函数版：参数表 (Player&, int, int)
    movq    %rcx, (%rsp)          ; ← player：显式传的引用（地址）
    imull   8(%rax), %ecx        ; xa * speed
    addl    (%rax), %ecx
    movl    %ecx, (%rax)         ; 存回 x

"?Move@PlayerM@@QEAAXHH@Z"        ; 成员函数版：参数表只有 (int, int)
    movq    %rcx, (%rsp)          ; ← this：同一个 rcx、同一个地址，但没写进参数表
    imull   8(%rax), %ecx        ; xa * speed
    addl    (%rax), %ecx
    movl    %ecx, (%rax)         ; 存回 x

rcx 里都是同一个地址——自由函数版是你手写的 Player&，成员函数版是编译器补的 this。mangled name 也印证：自由函数参数表是 AEAUPlayer@@HH（Player&, int, int），成员函数是 HH（int, int）——this 不占参数表，但真实存在。

const 成员函数

参数列表后加 const，表示"该函数不会修改对象"：

double avg_price() const;   // const 成员函数，this 类型是 const Sales_data*
  • const 对象只能调用 const 成员函数
  • 非 const 对象两种都能调
  • 这是 C++ 类型安全的重要部分——编译器保证 const 成员不修改对象

机制层推导（this 类型怎么变、为什么报 read-only object、const 为什么能参与重载）：见 2.4.4 const 在类里的传播。

和 C 的区别

维度 C C++
struct 纯数据集合，无成员函数 可以有成员函数，与 class 等价（仅默认访问不同）
class 关键字 ❌ C 没有 ✅ C++ 独有
数据+操作绑定 数据放 struct，操作是独立函数 数据和操作都在 class 内
this 指针 ❌ 无（C 函数显式传对象指针） ✅ 隐式传入
const 成员函数 ❌（C 靠程序员自觉/const T* 形参） ✅ 编译器强制
类内初始值 ❌ C89 无（C 起支持 = {0} 等） ✅ C++11 起每个成员可有默认值

C 程序员的认知转变：

C 里"一个类型+相关操作"是这样组织的——数据和函数分离：

/* C：数据是 struct，操作是独立函数，显式传对象指针 */
struct Sales_data {
    char bookNo[16];
    unsigned units_sold;
    double revenue;
};
double sales_avg(const struct Sales_data* s);          // 显式传指针
void sales_combine(struct Sales_data* lhs, const struct Sales_data* rhs);

C++ 把数据和操作绑进 class，调用时 obj.combine(rhs) 而非 combine(&obj, rhs)，且 const 成员函数由编译器保证不改对象：

// C++：数据和操作一体，this 隐式传入
total.combine(trans);   // 等价 combine(&total, trans)，但更自然

这是从"数据+自由函数"到"对象封装"的范式转变，是 OOP 的起点。

常见错误

  1. const 成员函数里修改成员：void f() const { x = 1; } —— 编译错误，const 成员函数的 this 是 const T*，不能改成员。例外：用 mutable 修饰的成员可在 const 函数中改（见 §7.4）。
  2. 返回 *this 的类型用错：Sales_data combine(...) 返回值类型会拷贝，无法链式调用 a.combine(b).combine(c)。应返回引用 Sales_data& combine(...) 返回 *this。
  3. 类内初始值用圆括号：int x(0); 在类内成员声明处非法（会被当成函数声明）。修正：用 = 0 或 {0}（C++11 起类内初始值只能用 = 或 {}）。
  4. 成员函数像自由函数那样直接调用：Move(player, 1, -1); 报 C2065: identifier "Move" is undeclared——Move 是 Player 的成员，不在全局作用域里，非静态成员函数必须通过对象调用：player.Move(1, -1)（编译器隐式传 &player）。想保留 Move(player, ...) 的调用形式，就把 Move 移出类，写成自由函数——两种写法编译出的函数体等价（见上文汇编实测）。

自测题

1. 选择题：下面关于 this 的说法正确的是？ - A) this 是成员函数的隐式参数，指向调用对象 - B) this 可以被重新赋值 - C) this 在静态成员函数中也存在 - D) this 是引用类型

答案

A。this 是 T* const（指向非 const 对象）或 const T* const（const 成员函数中）的指针，是隐式参数指向调用对象。B 错（const 指针不能改指向）；C 错（静态成员函数没有 this，因为它不属于某个对象）；D 错（this 是指针不是引用，虽然实践中常 return *this 当引用用）。

2. 判断题：const 对象可以调用非 const 成员函数。

答案

错误。const 对象只能调用 const 成员函数。因为非 const 成员函数的 this 是 T*，而 const 对象的地址是 const T*，把 const T* 转 T* 是去 const，非法。这是 C++ 类型系统的强制保护，编译期检查。

3. 踩坑题：下面代码想实现链式调用，但没生效，为什么？

class Builder {
public:
    Builder add(int x) { val += x; return *this; }   // 注意返回类型
    int val = 0;
};
Builder b;
b.add(1).add(2).add(3);   // 期望 b.val == 6
答案

b.val 实际只有 1。add 返回值类型是 Builder（不是引用），每次 return *this 都拷贝一个临时对象，后续 add 作用在拷贝上，不影响原 b。修正：返回引用 Builder& add(int x) { val += x; return *this; }，这样链式调用都作用在原对象上。

4. 应用题：把下面的 C 代码改写成 C++ class 风格，体现封装和 const 成员函数。

struct Counter { int count; };
void counter_init(struct Counter* c) { c->count = 0; }
void counter_inc(struct Counter* c) { c->count++; }
int counter_get(const struct Counter* c) { return c->count; }
答案 
class Counter {
public:
    Counter() : count_(0) {}        // 构造函数替代 init
    void inc() { ++count_; }        // 非_const_成员，可修改
    int get() const { return count_; }  // const 成员函数，只读
private:
    int count_;                     // 私有，外部不能直接访问
};
Counter c;        // 自动初始化，不用手动 init
c.inc();
std::cout << c.get();   // 1
// c.count_ = 10;        // 编译错误：private，封装

对比 C：1) 构造函数替代手动 init，不会忘；2) count_ 私有，外部无法绕过 inc 直接改，保证不变式；3) get() 是 const 成员函数，编译器保证不改对象；4) 调用语法 c.inc() 比 counter_inc(&c) 自然。

5.（踩坑） 下面代码报 C2065: identifier "Move" is undeclared，给出两种改法：

struct Player {
    int x, y;
    int speed;
    void Move(int xa, int ya) { x += xa * speed; }
};
int main() {
    Player p{1, 2, 3};
    Move(p, 1, 1);      // ❌ C2065
}
答案

Move 是 Player 的成员函数，不在全局作用域里，不能像自由函数那样直接调用。

  • 改法一（成员函数式）：p.Move(1, 1);——通过对象调用，编译器隐式传 &p 作 this。
  • 改法二（自由函数式）：把 Move 移出类：void Move(Player& player, int xa, int ya) { player.x += xa * player.speed; }，调用 Move(p, 1, 1);——显式传引用。

两种写法在汇编层面等价：成员函数版只是把第一个参数（对象的地址）藏进了 this。

可跑的例子

examples/7.1-abstract-data-type.cpp —— 看 this 指针到底是谁。

clang++ -std=c++20 examples/7.1-abstract-data-type.cpp -o /tmp/demo && /tmp/demo

真实输出（节选）：

初始: 1234.5678 元 (12345678 ticks)
链式调用 add():
  this = 0x16d177cd0（正在修改这个地址上的对象）
  this = 0x16d177cd0（正在修改这个地址上的对象）
  this = 0x16d177cd0（正在修改这个地址上的对象）

看出什么了？ 三次 add 打印的 this 一模一样——这就是成员函数知道自己在操作谁的机制：编译器把 p.add(100) 改写成 add(&p, 100)，this 就是那个隐式传进来的 &p。return *this 解引用它，才有链式调用。

7.2

访问控制与封装

本节讲什么

C++ 的访问控制符 public/private/protected，以及 class 与 struct 的唯一区别（默认访问权限）。这是实现封装——隐藏实现细节、暴露稳定接口——的语言机制。

核心用法

三个访问说明符

说明符 含义 谁能访问
public 公有接口 任何代码
private 私有实现 该类的成员函数和友元
protected 受保护 该类及派生类的成员（继承章详讲） 
class Account {
public:                                   // 外部可调用的接口
    void deposit(double amount) { balance_ += amount; }
    double balance() const { return balance_; }
private:                                  // 外部不可见的实现
    double balance_ = 0;
};

Account acc;
acc.deposit(100);          // OK，public
// acc.balance_ = 100;     // 错误：private，外部不可访问

访问说明符可以出现多次：「分区」是风格，但挂着两个硬后果

public:/private:/protected: 在一个类里可以出现任意多次——语法上 member-specification 就是递归产生式（access-specifier : member-specification_opt）。每个说明符对它之后、下一个说明符之前的所有声明生效。所以 TheCherno 说的"公共方法放一个区、公共变量放一个区、公共静态变量再放一个区"完全合法：

class Log {
public:
    static int s_InstanceCount;      // 公共静态变量一个区
public:                              // 同一个说明符写两遍也合法
    void SetLevel(int level);        // 公共方法一个区
    void Warn(const char* msg);
private:
    int m_LogLevel;
};

怎么分区对编译器基本无感——实测（clang 23.1.0，-std=c++20 与 -std=c++23 结果一致）：

写法 数据成员 a/b/c 的访问级别 sizeof is_standard_layout_v
全部成员挤一个 public: 区 全 public 12 1
a/b/c 分在 public/private/public 三个区 不同 12 0 ← 唯一的硬差别
方法分两个 public 区、数据全 private 全 private 12 1

两个关键结论：

  1. 方法随便分区，不影响布局——布局只由非静态数据成员决定，成员函数不占对象存储（见 7.1 的 this 实测）。
  2. 数据成员的访问级别一旦不同，类就丧失 standard-layout 资格。standard-layout 是"内存布局与 C 兼容"的保证（能安全 memcpy、offsetof、与 C 结构体互操作）。注意 sizeof 一个字节都没变——这个损失是纯类型系统层面的，不看 traits 根本发现不了。

HFT 关联：行情解码里的 wire-format 结构体（要 memcpy 直接落盘/上网络、要跟 C 库共享布局）必须保住 standard-layout——数据成员全部同一个访问级别（通常用全 public 的 struct），要分区只能拿方法来分。

布局顺序的标准变迁（新版标准改了规则，值得记住）：

  • C++20 及以前（N4861 [class.mem] p19，逐字）："Non-static data members of a (non-union) class with the same access control and non-zero size ... are allocated so that later members have higher addresses within a class object. The order of allocation of non-static data members with different access control is unspecified." —— 跨访问区的成员顺序，标准不保证（虽然所有主流 ABI 实际都按声明序）。
  • C++23 起（P1847R4 之后，现行草案 [class.mem.general] Note 8）："Non-variant non-static data members of non-zero size are allocated so that later members have higher addresses within a class object." —— 访问级别限定词被删掉，所有成员一律强制按声明序。

但 standard-layout 的「同一访问级别」要求并没有随 C++23 取消：实测 -std=c++23 下 is_standard_layout_v<ThreeSections> 仍为 0。C++23 改的是"顺序保证"，没改"standard-layout 资格"。

class vs struct：差别只有「默认访问级别」，而且是两处

class A { int x; };     // 成员 x 默认 private
struct B { int x; };    // 成员 x 默认 public

唯一区别是默认访问级别——而且是两处都受它影响，多数人只记得第一处：

场合 class 默认 struct 默认
成员（数据/函数）的访问权限 private public
继承方式（class D : Base） private 继承 public 继承

标准原文（C++ draft）：

§11.8.1/3：Members of a class defined with the keyword class are private by default. Members of a class defined with the keywords struct or union are public by default.

§11.8.3/2：In the absence of an access-specifier for a base class, public is assumed when the derived class is defined with the class-key struct and private is assumed when the class is defined with the class-key class.

除默认访问级别外，二者在类型系统里完全等价：struct 也是 class（std::is_class_v<B> == true）， 同样能有成员函数、构造/析构、虚函数、继承、模板。

实测：让编译器自己承认

① 默认成员访问（clang 23.1.0，class C { int x = 0; }; 后 c.x = 1;）：

error: 'x' is a private member of 'C'
note: implicitly declared private here          ← 编译器替你补的 private

② 默认继承（class D : Base {}; 后 Base* p = &d;）：

error: cannot cast 'D' to its private base class 'Base'
note: implicitly declared private here          ← 继承说明符也被隐式补成 private

同一件事也能在不触发报错的前提下测出来（std::is_convertible 静态断言）：

class  Base { public: int v = 1; };
class  D_class  : Base {};   // 默认 → private 继承
struct D_struct : Base {};   // 默认 → public  继承

static_assert(!std::is_convertible_v<D_class*,  Base*>, "");  // 外部不认「D_class 是 Base」
static_assert( std::is_convertible_v<D_struct*, Base*>, "");  // 外部认「D_struct 是 Base」

HFT 关联：默认继承这条在真实代码里最容易被忽略——写 class OrderBook : Base {} 得到的是 private 继承，外部无法把 OrderBook& 当 Base& 用（多态失效、传参编译不过）。 想让"是一种"关系成立，必须显式写 : public Base。这也是 Google C++ 风格指南要求 继承一律显式写明访问级别的原因。

实践建议

用途 选择 理由
纯数据聚合（POD、传输结构、只装字段） struct 默认 public 省事，语义上"就是一堆公开数据"
有不变式 / 有行为的对象 class 默认 private 安全，逼你显式暴露接口

注意这只是约定（C++ 核心指南 C.2/C.8 也这么建议），不是语言强制—— struct 一样能写 private：struct S { private: int x; }; 完全合法。

friend：「只有类自己能碰私有成员」的星号（Cherno 29 集）

Cherno 可见性集讲三修饰符时特意给"Only"加了个星号："Only 要给个星号，因为 C++ 里有个叫 friend 的东西"。private 的围墙不是绝对的——类自己可以签发通行证*：

class Log {
private:
    int level_ = 3;
    friend void inspect(const Log&);    // 通行证由 Log 自己发放，不是 inspect 自己要的
};
void inspect(const Log& l) {
    std::printf("%d\n", l.level_);      // 自由函数居然能碰私有成员：编译通过
}
void peek(const Log& l) {
    // (void)l.level_;                  // 没通行证：
    // error: 'level_' is a private member of 'Log'
}

注意 friend 声明写在被访问的类里——访问权是类授予的，不是请求者声明的。这是封装纪律的例外，不是漏洞：发证权在围墙里面。

friend 三大性质（clang 23 实测，每条都给了编译错误原文）：

性质 场景 结果
不互惠 A 认 B 为 friend（friend class B; 写在 A 里） B 能看 A 私有；A 看 B 私有 → error: 'y_' is a private member of 'B'
不传递 A 认 B、B 认 C C 看 A 私有 → error: 'x_' is a private member of 'A'
不继承 A 认 B；D 派生自 B D 看 A 私有 → error: 'x_' is a private member of 'A'

一句话：friend 是点对点的单向通行证，不扩散。典型正当用途是流操作符——operator<< 想读私有成员但它必须是自由函数（左操作数是 ostream&，不可能是成员函数），只能发 friend 通行证：

class Point {
    int x_, y_;
    friend std::ostream& operator<<(std::ostream& os, const Point& p);
};
std::ostream& operator<<(std::ostream& os, const Point& p) {
    return os << p.x_ << "," << p.y_;   // friend 函数能读 x_/y_
}

设计忠告（Effective C++ 思路）：friend 越多的地方封装越漏。能用成员函数/公有接口就别发通行证；必须发时，发给具体函数（friend void inspect(const Log&);）而不是整个类（friend class Anybody;），收窄泄露面。

封装的意义

  • 不变式保护：把数据设 private，只能通过成员函数访问，函数内可加校验，防止外部直接破坏不变式
  • 实现自由：private 细节可随时改，不影响使用者（ABI/接口稳定）
  • 可读性：使用者只看 public 接口，不必关心实现

成员命名约定：m_ 前缀防的是「参数遮蔽」这个真坑

典型的 private 数据 + public 接口长这样（TheCherno CLASSES 一集的 Log 例子）：

class Log {
public:
    void SetLevel(int level) {
        m_LogLevel = level;            // m_ 前缀：一眼看出这是成员，不是参数
    }
    void Warn(const char* message) { /* ... */ }
private:
    int m_LogLevel = 0;                // 私有数据
};

为什么要给成员加 m_ 前缀？Cherno 的说法是"在函数体里一眼分清哪些是类作用域的成员、哪些只是局部变量/参数"。但这不只是可读性问题——不加区分符会踩一个编译器默认不警告的真坑：

class LogBad {
public:
    void SetLevel(int level) {
        level = level;      // 想写「成员 = 参数」，实际是参数自赋值，成员根本没动
    }
private:
    int level = 0;
};

实测（clang 23.1.0，macOS arm64）：

写法 SetLevel(3) 后读回 默认编译选项下有警告吗
level = level;（参数遮蔽成员） 0（静默丢数据） 没有——连 -Wall 都不含 -Wshadow
this->level = level; 3 ——
m_LogLevel = level;（m_ 前缀） 3 ——
level_ = level;（尾随下划线） 3 ——

加 -Wshadow 后编译器才会指认：warning: declaration shadows a field of 'LogBad'。

三种主流约定，任选其一并全项目统一：

约定 例子 谁在用
m_ 前缀 m_LogLevel Cherno、大量游戏/图形代码
尾随下划线 log_level_ Google C++ 风格指南（本仓库笔记里的 balance_/count_/kelvin_ 就是这个）
不加约定，成员访问一律 this-> this->level 部分代码库；缺点是漏写一处就回到遮蔽坑

这是纯约定，语言层面没有任何规则——编译器只认作用域，不认命名。约定买不到正确性，但能买到两件事：函数体里成员/局部一眼可辨（Cherno 的理由）；从根上消除"参数与成员同名"的遮蔽类 bug（实测的 level = level; 静默失效）。工程上的兜底是把 -Wshadow 加进编译选项。

和 C 的区别

维度 C C++
struct 成员访问控制 全部公开，无 private 可有 public/private，与 class 等价
封装机制 ❌ 无（数据全公开，靠程序员自觉） ✅ 编译器强制
class 关键字 ❌ 无 ✅
private/public ❌ 无 ✅

C 程序员的认知转变：

C 里 struct 的成员全是公开的，外部可任意读写，封装全靠"约定"和文档：

/* C：数据全公开，外部可绕过函数直接改 */
struct Account {
    double balance;    // 谁都能直接访问
};
struct Account a;
a.balance = -1000;     // 没人拦你，破坏不变式

C++ 用 private 把数据藏起来，外部只能通过 public 函数访问，函数内可校验：

// C++：private 保护数据，public 函数控制访问
class Account {
public:
    bool deposit(double amt) {
        if (amt < 0) return false;   // 校验
        balance_ += amt;
        return true;
    }
private:
    double balance_ = 0;             // 外部碰不到
};
Account a;
// a.balance_ = -1000;   // 编译错误，private
a.deposit(-100);        // 运行期被拒

这是从"约定式封装"到"语言强制封装"的转变，C++ 编译器替你守不变式。

常见错误

  1. 把所有成员都 public：把 class 当 C struct 用，数据全公开，失去封装意义。建议：数据成员默认 private，只暴露必要的接口函数。
  2. class 和 struct 混用困惑：同一个类型一会儿用 class 声明一会儿用 struct 前向声明，没问题（它们是同一类型），但默认访问不同容易出错——尤其漏掉"默认继承"这一处：class D : Base {} 是 private 继承，外部无法把 D& 当 Base& 用。建议：继承一律显式写 public/private/protected；有封装需求用 class（默认 private 安全），纯数据聚合用 struct（默认 public 方便）。
  3. getter/setter 暴露一切：为每个 private 成员都写 get_x()/set_x()，本质还是公开数据，封装形同虚设。建议：接口应反映"行为"而非"字段"，只在确有必要时暴露。

自测题

1. 选择题：下面代码 main 中哪些访问合法？

class P {
public:  int a;
private: int b;
};
int main() {
    P p;
    p.a = 1;
    p.b = 2;
}
  • A) 都合法
  • B) 都非法
  • C) p.a=1 合法，p.b=2 非法
  • D) p.a=1 非法，p.b=2 合法
答案

C。a 是 public，外部可访问；b 是 private，外部不可访问（只有 P 的成员函数和友元能访问）。这是 C++ 封装的基本规则，编译期强制。

2. 判断题：C++ 中 struct 可以有构造函数、成员函数、继承，和 class 功能完全一样。

答案

正确。C++ 的 struct 和 class 唯一区别是默认访问权限（struct 默认 public，class 默认 private）和默认继承方式。功能上完全等价，struct 也能有构造函数、成员函数、虚函数、继承等。实践中：有封装用 class，纯数据聚合用 struct。

3. 踩坑题：下面类想保护 count_ 不被外部直接改，但有漏洞吗？

class Counter {
public:
    int& count() { return count_; }   // 返回 count_ 的引用
private:
    int count_ = 0;
};
答案

封装被绕过。count() 返回 int&，调用者拿到引用就能直接改 count_：Counter c; c.count() = 100; 完全绕过了私有性。修正：返回值类型 int（拷贝）或 const int&（只读引用），不要返回非 const 引用暴露内部数据。

4. 应用题：设计一个 Temperature 类，内部用开尔文存储，对外提供 set_celsius/get_celsius 和 set_fahrenheit/get_fahrenheit 接口。说明封装的好处。

答案 
class Temperature {
public:
    void set_celsius(double c) { kelvin_ = c + 273.15; }
    double get_celsius() const { return kelvin_ - 273.15; }
    void set_fahrenheit(double f) { kelvin_ = (f - 32) * 5 / 9 + 273.15; }
    double get_fahrenheit() const { return (kelvin_ - 273.15) * 9 / 5 + 32; }
private:
    double kelvin_ = 0;   // 内部统一用开尔文，外部不感知
};

封装好处：1) 内部表示（开尔文）可随时改（如换成微开尔文定点数）而不破坏接口；2) 外部无法设置低于绝对零度的非法值（可在 setter 加校验）；3) 使用者只需关心摄氏/华氏接口，不需理解内部存储。C 做不到这种"接口与实现分离"的强制。

5. 踩坑题：下面的 Cat : Animal 想表达"猫是一种动物"，Animal& a = cat; 能编过吗？为什么？怎么改？

class Animal { public: int legs = 4; };
class Cat : Animal { };
int main() {
    Cat cat;
    Animal& a = cat;      // ？
}
答案

编不过。 class 的默认继承方式是 private 继承，外部代码看不到"Cat 是一种 Animal"，编译器直接拒绝隐式向上转型：

error: cannot cast 'Cat' to its private base class 'Animal'
note: implicitly declared private here

改法一：显式写继承说明符 —— class Cat : public Animal {};（推荐，Google 风格指南也要求继承必写访问级别）。 改法二：把 Cat 声明成 struct（默认 public 继承）——struct Cat : Animal {};，但这只在"本来就想用 struct"时才合适。

注意 Animal::legs 是 public，访问它本身没问题；出问题的是派生关系本身是私有的。这就是"默认访问级别有两处"的典型踩坑点。

6. 踩坑题：下面的 SetLevel 有 bug 吗？log.SetLevel(3) 之后 GetLevel() 返回多少？默认编译选项下会有警告吗？

class Log {
public:
    void SetLevel(int level) { level = level; }
    int GetLevel() const { return level; }
private:
    int level = 0;
};
答案

有 bug，而且静默——SetLevel(3) 之后 GetLevel() 仍返回 0。

level = level; 里的两个 level 指的都是参数（参数遮蔽了同名成员），所以这行是参数自赋值，成员从头到尾没被碰过。实测默认编译选项下没有任何警告（-Wall 不含 -Wshadow），加 -Wshadow 才会报 declaration shadows a field of 'Log'。

三种修法（任选并全项目统一）：

  1. this->level = level; —— 显式指明左边是成员；
  2. 成员加 m_ 前缀：m_LogLevel = level;（Cherno 风格）；
  3. 成员加尾随下划线：level_ = level;（Google 风格，本仓库笔记统一用这种）。

工程兜底：把 -Wshadow 加进编译选项，让编译器替你盯着这类遮蔽。

7. 判断+分析题：下面两个类，sizeof 一样吗？都是 standard-layout 吗？哪个能安全地 memcpy 与 C 端结构体互操作？

class A {                              class B {
public:                                public:
    char a;                                char a;
    int  b;                            private:
    char c;                                int  b;
    void f() {}                        public:
};                                         char c;
                                           void f() {}
                                       };
答案

sizeof 一样（实测都是 12 字节）——访问分区不改变布局，布局只由非静态数据成员的类型与声明顺序决定。

standard-layout 不一样：is_standard_layout_v<A> == 1，is_standard_layout_v<B> == 0。因为 standard-layout 要求所有非静态数据成员访问级别相同，B 的 b 是 private、其余 public，资格丧失——尽管 sizeof 没变、成员函数 f() 怎么分区都无所谓。

能安全 memcpy 与 C 互操作的只有 A。B 在主流 ABI 上实际布局也和 A 一样（-std=c++20/-std=c++23 实测一致），但那是实现行为，不是标准给你的保证。

补充：C++20 及以前，跨访问区的成员分配顺序标准是 unspecified（N4861 [class.mem] p19）；C++23 起（P1847R4）所有成员一律强制按声明序——但 standard-layout 的「同一访问级别」要求没有取消。

7.3

友元（Friend）

本节讲什么

friend 关键字：让特定的外部函数或类访问某个类的私有成员。这是封装的一个"逃生舱"——在确实需要时打破封装，但要显式声明、可控。

核心用法

友元函数

class Point {
    friend std::ostream& operator<<(std::ostream& os, const Point& p);  // 声明友元
public:
    Point(int x, int y) : x_(x), y_(y) {}
private:
    int x_, y_;   // 私有
};

// 友元函数不是成员函数，但能访问 Point 的私有成员
std::ostream& operator<<(std::ostream& os, const Point& p) {
    return os << "(" << p.x_ << "," << p.y_ << ")";  // 直接访问 p.x_、p.y_
}

友元类

class Node {
    friend class List;   // List 的所有成员函数都能访问 Node 的私有成员
private:
    int data;
    Node* next;
};

友元成员函数

class Window {
    friend void Screen::refresh(const Window&);   // 只让 Screen::refresh 访问
private:
    int width, height;
};

和 C 的区别

维度 C C++
访问控制 ❌ 无封装，无友元概念 ✅ private + friend 逃生舱
友元 无（数据本就全公开） ✅

C 程序员的理解：C 里没有封装，也就不需要友元——所有数据都公开，任何函数都能访问。C++ 引入 private 后，有时确实需要让某个特定函数访问私有成员（典型场景：operator<< 不能是成员函数但需要读私有数据），友元就是为此设计的。

友元不是"成员"，它只是被授予了访问权限。一个函数可以是某类的友元但不是其成员。

常见错误

  1. 友元关系不是相互的：A 是 B 的友元，不代表 B 是 A 的友元。要双向访问，两边都要声明 friend。
  2. 友元破坏封装：滥用友元，把半个代码库都设成友元，封装形同虚设。建议：友元用于"接口需要"的场景（如运算符重载、迭代器访问容器内部），不用于偷懒。
  3. 友元声明位置混淆：友元声明可放在类的任意访问区（public/private/protected 都行，不受访问控制影响），但通常放最前面或最后，并加注释说明意图。

自测题

1. 选择题：关于友元，下面说法正确的是？ - A) 友元函数是类的成员函数 - B) 友元关系是相互的 - C) 友元函数可以访问类的私有成员 - D) 友元声明受 public/private 影响

答案

C。友元函数不是成员函数（A 错），它只是被授权访问私有成员的外部函数。友元关系不相互（B 错）。友元声明不受访问说明符影响，放哪都生效（D 错）。

2. 判断题：class A { friend class B; }; 之后，B 的所有成员函数都能访问 A 的私有成员，但 A 不能访问 B 的私有成员（除非 B 也声明 A 为友元）。

答案

正确。友元是单向授权：A 授予 B 访问权，B 能访问 A 的私有，但 A 不能访问 B 的私有（除非 B 反过来声明 friend class A）。这是友元的单向性。

3. 踩坑题：为什么 operator<< 通常要做成友元而不是成员函数？

答案

如果 operator<< 是成员函数，左操作数必须是当前对象，调用形式变成 p << std::cout（对象在左，流在右），反人类。标准用法是 std::cout << p（流在左），这要求 operator<< 的左操作数是 ostream&，所以它必须是非成员函数。但它又要读 p 的私有数据，于是用 friend 授权。这是友元最经典的用途。

class Point {
    friend std::ostream& operator<<(std::ostream&, const Point&);  // 友元
};
std::ostream& operator<<(std::ostream& os, const Point& p) { return os << p.x_; }
// 用法：std::cout << p;   ✓

4. 应用题：一个 Matrix 类想让自己的迭代器 MatrixIterator 访问其内部存储，但不想把内部存储公开。用友元设计这个关系，写出关键声明。

答案 
class Matrix {
    friend class MatrixIterator;   // 授权迭代器访问私有
public:
    MatrixIterator begin();
    MatrixIterator end();
private:
    double* data_;      // 内部存储，不公开
    size_t rows_, cols_;
};

class MatrixIterator {
public:
    double& operator*() { return mat_->data_[idx_]; }   // 访问 Matrix 私有
    // ...
private:
    Matrix* mat_;
    size_t idx_;
};

这样 Matrix 的内部存储对外保密，但 MatrixIterator 能访问实现高效遍历。这是 STL 容器和迭代器关系的简化版——迭代器通常是容器的友元。

可跑的例子

examples/7.3-friend.cpp —— 普通函数摸私有成员的唯一合法通道。

clang++ -std=c++20 examples/7.3-friend.cpp -o /tmp/demo && /tmp/demo

真实输出（节选）：

[print] 余额 = 987654
[audit] 余额 = 987654（友元类的成员函数）

看出什么了？ print 不是成员函数，却直接读了 a.balance_——friend 授权的结果。注意三条铁律都不满足：不传递、不互惠、不继承，开洞范围精确到函数/类。

比把成员改 public 整扇门小得多。日志器、序列化器是友元的正当用途。

7.4

类的其他特性

本节讲什么

类的几个进阶特性：类类型成员、内联成员函数、mutable 数据成员、返回 *this 的成员函数、类类型作为成员的初始化。这些是写好 class 的实用技巧。

核心用法

类类型作为成员

class Screen {
    std::string contents;   // 成员是另一个类类型
    pos cursor;             // 成员是类型别名
};

类类型的成员会在构造函数体执行前被自动构造（调用其默认构造函数），析构时自动析构——这是 RAII 链式工作的基础。

内联成员函数

class Screen {
public:
    char get() const { return contents[cursor]; }   // 类内定义，隐式 inline
    Screen& move(pos r, pos c);                     // 类外定义，非 inline
};
inline Screen& Screen::move(pos r, pos c) {          // 加 inline 显式
    cursor = r * width + c;
    return *this;
}

mutable 数据成员

class Screen {
public:
    void display() const {
        ++access_count_;    // 即使在 const 函数中也能改 mutable 成员
        // ... 显示内容
    }
private:
    mutable size_t access_count_ = 0;   // mutable：永远可变，即使在 const 对象中
    std::string contents;
};

mutable 用于"逻辑上不影响对象状态、但物理上需要修改"的成员（如访问计数、缓存）。

返回 *this 实现链式调用

class Screen {
public:
    Screen& set(char c) { contents[cursor] = c; return *this; }
    Screen& move(pos r, pos c) { cursor = r * width + c; return *this; }
};
// 链式调用
Screen s;
s.move(0, 0).set('A').set('B');   // 全作用在 s 上

const 成员函数返回 *this

class Screen {
public:
    Screen& display() { /* ... */ return *this; }        // 非 const 版，返回 Screen&
    const Screen& display() const { /* ... */ return *this; }  // const 版，返回 const Screen&
};

对 const 成员函数，*this 是 const Screen&，返回类型也要对应 const，否则会去 const。

和 C 的区别

维度 C C++
类类型成员自动构造/析构 ❌ C struct 成员不会自动初始化 ✅ 成员自动构造/析构（RAII 链）

C 程序员最该理解的：类类型成员的自动构造/析构。C 里 struct 嵌 struct，内层 struct 不会自动初始化，必须手动调 init：

/* C：嵌套 struct 要手动初始化每一层 */
struct Inner { int x; };
struct Outer { struct Inner inner; };
struct Outer o;
o.inner.x = 0;   // 不初始化就是垃圾值，要手动

// C++：成员自动构造，内层类类型先于外层构造
class Outer {
    Inner inner;     // Outer 构造时，inner 先调用 Inner 的默认构造
};
Outer o;             // inner 已自动构造，不用手动 init

这是 RAII 的基础——对象构造时所有成员就绪，析构时成员自动清理。

常见错误

  1. const 成员函数返回非 const *this：Screen& display() const { return *this; } —— 在 const 函数里 *this 是 const Screen&，返回 Screen& 要去 const，编译错误。修正：返回 const Screen&，或提供 const/非 const 两个重载。
  2. 滥用 mutable 破坏 const 语义：把核心数据成员设 mutable，让 const 函数能改它，const 保证形同虚设。建议：mutable 只用于"逻辑 const"的成员（缓存、计数、懒初始化标志），不用于真正影响对象状态的成员。
  3. 成员初始化顺序与声明顺序不符：构造函数初始化列表写的顺序不等于初始化顺序——按成员声明顺序初始化，与初始化列表写法无关。跨成员依赖时易错。

自测题

1. 选择题：关于 mutable，下面说法正确的是？ - A) mutable 成员在 const 对象中也能修改 - B) mutable 让任何成员都能在 const 函数中改 - C) mutable 成员不占用对象空间 - D) mutable 只能用于静态成员

答案

A。mutable 修饰的成员即使在 const 对象/const 成员函数中也可修改，用于"逻辑 const"场景（如缓存、计数）。B 错（只修饰 mutable 成员，不是所有成员）；C 错（仍占空间）；D 错（用于非静态数据成员）。

2. 判断题：成员的初始化顺序由构造函数初始化列表中写的顺序决定。

答案

错误。成员按声明顺序初始化，与初始化列表中的书写顺序无关。例如：

class C {
    int a; int b;
public:
    C(int x) : b(x), a(b) {}   // 实际先初始化 a（用未初始化的 b），再 b
};

这里 a 会用到未初始化的 b，是 UB。编译器通常会警告。

3. 踩坑题：下面 const 成员函数想返回 *this 供链式调用，编译报错，为什么？

class Builder {
public:
    Builder& append(const std::string& s) const {
        buf_ += s;       // buf_ 不是 mutable
        return *this;
    }
private:
    std::string buf_;
};
答案

两个问题：1) buf_ += s 在 const 函数中修改非 mutable 成员，编译错误；2) return *this 在 const 函数中 *this 是 const Builder&，返回 Builder& 要去 const，编译错误。修正：要么去掉 const（append 要改对象）；要么提供非 const 版做修改 + const 版只读。append 本质是修改操作，不该是 const。

4. 应用题：为一个 Logger 类设计一个带缓存的 log() const 成员函数：每次调用写入缓存（mutable），缓存满时刷盘。说明为什么用 mutable。

答案 
class Logger {
public:
    void log(const std::string& msg) const {     // const：逻辑上不改 Logger 状态
        cache_ += msg + "\n";
        if (cache_.size() > 4096) flush_();       // 缓存满刷盘
    }
private:
    void flush_() const { /* 写文件 */ cache_.clear(); }
    mutable std::string cache_;    // mutable：物理改变，逻辑上 Logger 不变
};

用 mutable 因为：log() 逻辑上是"只读"操作（Logger 的配置/状态没变），但物理上要改缓存。这是"逻辑 const vs 物理 const"的经典区分——mutable 让我们表达"这个修改不影响对象的可观察状态"。

clang++ -std=c++20 examples/7.4-mutable-and-init-order.cpp -o /tmp/demo && /tmp/demo

真实输出（节选）：

看出什么了？ 初始化列表里明明先写 b_ 再写 a_，实际却 a_ 先初始化——真实顺序只看声明顺序，与列表书写顺序无关。如果 b_ 的初值依赖 a_ 而声明顺序相反，就是一颗随机炸弹。-Wreorder 就是盯这条纪律的。mutable 则让 const 函数里唯一可写的"统计量"成为可能。

cache/延迟计数器正是"逻辑只读、物理会变"的典型 mutable 场景。

7.5

构造函数（Constructors）

本节讲什么

构造函数控制对象的初始化：构造函数初始值列表、委托构造、默认构造函数、explicit 抑制隐式转换，以及私有构造函数如何阻止/受控实例化。构造函数是 C 程序员最该认真学的——C 没有构造函数，对象初始化全靠手动 init，容易忘。

核心用法

构造函数初始值列表

class Person {
public:
    Person(std::string n, int a) : name_(std::move(n)), age_(a) {}  // 初始值列表
private:
    std::string name_;
    int age_;
};

初始值列表在函数体执行前初始化成员。如果不用初始值列表，成员会先默认构造，再在函数体里赋值——对类类型成员（如 string）是双重开销（先默认构造再赋值）。

汇编层实测（clang 23，-O0，libc++，m_Name 为 std::string）——两种写法构造函数体内真实的函数调用数：

class PlayerA { std::string m_Name;
public: PlayerA(const std::string& name) : m_Name(name) {} };   // 写法A
class PlayerB { std::string m_Name;
public: PlayerB(const std::string& name) { m_Name = name; } };  // 写法B
写法 构造函数体内的 bl（call） 符号解读
A 初始化列表 1 个：basic_string::basic_string(const basic_string&) 直接调拷贝构造，一步到位
B 函数体赋值 2 个：basic_string::basic_string() + basic_string::operator=(const basic_string&) 先默认构造空串，再赋值

mangling 对照：C1ERKS5_ = 构造函数（C1），参数 RKS5_ = const basic_string& → 拷贝构造；C1B9nqe…Ev = 无参默认构造；aSERKS5_ 中的 aS = operator=。A 版就这一个 call，没有任何临时量构造——m_Name(name) 是直接初始化：拿 name 直接调 string 的拷贝构造，不是"先造一个 std::string(name) 临时量再拷给 m_Name"（那句常见的"等价写法"是误导，拷贝初始化和直接初始化语义路径不同）。

对 int/float 这类标量成员，两种写法汇编完全一样（就是一条 str 存值），差别只在类类型成员。

初始化顺序坑的编译器证据：成员按声明顺序初始化，与列表书写顺序无关。列表写反时 clang 的警告（-Wall 下才报）：

warning: field 'm_Age' will be initialized after field 'm_Name' [-Wreorder-ctor]
    Player(const std::string& name, int age) : m_Age(age), m_Name(name) {}
                                               ^~~~~~~~~~  ~~~~~~~~~~~~

坑在哪：若 m_Age(age) 的实参依赖 m_Name（比如 : m_Age(m_Name.size()), m_Name(name)），而 m_Name 声明在前，程序会先执行 m_Name.size()——此时 m_Name 还是默认构造的空串，Age 拿到 0 而不是正确值，且不报错。规则：列表书写顺序永远照抄声明顺序，让警告无处可报。

为什么是冒号：没有第二个位置能放参数

成员和基类在构造函数体开始执行之前就已经构造完了。控制流进到 { 时，name_ 已经是一个活着的 std::string，此时再写 name_ = n 只能是赋值。所以"构造它们所需的实参"必须在进入函数体之前交出去，而语法上只有一处能交：构造函数形参表后面那个 :。

Person::Person(std::string n, int a)
    : name_(std::move(n)), age_(a)      // ctor-initializer：函数体之前执行
{ /* 走到这里，name_ 与 age_ 已经构造完毕 */ }

三处语法细节能看出它不是赋值：

  • 元素必须写成 成员(实参) 或 成员{实参}，不能写成 成员 = 实参——后者在初值列里根本不是合法语法。
  • 元素之间用逗号，整个列表不能为空（写 A() : {} 是语法错误）。
  • 初值列只能出现在构造函数的定义处，声明里不能写。

前两条有编译器原文可查（gcc 13.2）：

A(int v) : x = v {}      // 写成赋值
B() : {}                 // 写成空列表

error: expected '(' before '=' token
error: expected '{' before '=' token
error: expected identifier before '{' token

冒号后面必须紧跟至少一个 成员(...)，这条语法约束本身就说明：初值列不是"赋值语句的集合"，而是一串构造请求。

对照其他语言：Java 在函数体第一行写 super(...)，C# 写 : base(...)，都是"调用"父构造。C++ 没有这种语句，因为成员和基类不是被显式调用，而是由构造函数隐式构造，参数只能从初值列走。

「两次构造」的准确说法：一次默认构造 + 一次赋值

先纠正措辞：严格讲不是两次构造，是"默认构造 + 赋值"。但赋值对类类型成员往往等价于重新填一遍，代价和再构造一次接近，口语里就说成了"构造两次"。

实测（gcc 13.2，-std=c++17 -O0 -fno-elide-constructors，成员类带构造/赋值/析构打印）：

struct Bad  { Member m; Bad(int x)  { m = x; } };   // 函数体赋值
struct Good { Member m; Good(int x) : m(x) {} };    // 初值列

[Bad]  函数体里赋值
  Member()       默认构造
  Member(int)    转换构造
  operator=      赋值
  ~Member()
  ~Member()
[Good] 初值列
  Member(int)    转换构造
  ~Member()

Bad 版的完整轨迹：进入函数体之前，m 先被默认构造；m = x 里 x 再被转换构造成临时对象，然后调 operator=，临时对象立即析构；函数结束时成员才析构。五条记录里有两次构造、一次赋值、两次析构。Good 版只有一次构造。

代价落在哪：

成员类型 不用初值列的额外代价
int / double 等标量 无。两种写法都是一条存储指令，差别只在"已初始化"还是"未初始化"
std::string 多一次默认构造 + 一次赋值，赋值可能重新分配
std::vector 同上，赋值还可能触发扩容
自定义类型 取决于默认构造与 operator= 的实现，可能远贵于一次构造

比性能更硬的是能不能编译，见下一节。

四种必须在初值列里处理的成员

struct Member { Member(int) {} };                 // 无默认构造

struct A { Member m; A() {} };                    // ① 类类型成员无默认构造
struct B { const int v; B(int x) { v = x; } };    // ② const 成员
struct C { int& r; C(int& x) { r = x; } };        // ③ 引用成员

error: no matching function for call to 'Member::Member()'
error: uninitialized const member in 'const int' [-fpermissive]
note: 'const int B::v' should be initialized
error: assignment of read-only member 'B::v'
error: uninitialized reference member in 'int&' [-fpermissive]
note: 'int& C::r' should be initialized
情况 为什么必须在初值列 报错关键词
const 成员 构造完成后不能再赋值 uninitialized const member / read-only member
引用成员 引用必须绑定，且绑定后不能改绑 uninitialized reference member
无默认构造的类类型成员 函数体之前那一步"默认构造"根本调不到 no matching function for call to ...::Member()
无默认构造的基类 同理，基类子对象也要先构造 no matching function for call to ...::Base()

前两条是语言规则（不可赋值），后两条是类型系统（没有可用的构造）。四条的共同点是：函数体之前那一阶段必须成功，而那一阶段唯一的参数入口就是初值列。

基类与成员谁先谁后

顺序由标准规定，与列表书写顺序无关：虚基类 → 直接基类（按声明顺序）→ 成员（按声明顺序）→ 函数体；析构严格逆序。

struct D : B1, B2 {
    M1 m1; M2 m2;
    D() : m2(0), m1(1), B2(), B1() {}    // 实际执行顺序：B1, B2, m1, m2
};

写反不会报错，只在 -Wreorder 下给警告。若 m2 的初值依赖 m1，写反就是读到未初始化值——不报错，只出错值。

委托构造（C++11）

class Sales_data {
public:
    Sales_data(std::string s, unsigned n, double p)
        : bookNo(s), units_sold(n), revenue(n*p) {}      // 主构造
    Sales_data(std::string s) : Sales_data(s, 0, 0) {}   // 委托给主构造
    Sales_data() : Sales_data("") {}                      // 委托给上一个
};

一个构造函数调用另一个构造函数，避免重复初始化代码。

默认构造函数

class C {
public:
    C() = default;   // 显式要求编译器生成默认构造（C++11）
};
  • 只有当类没有声明任何构造函数时，编译器才自动生成默认构造
  • 一旦声明了带参构造，默认构造就不会自动生成，需要 = default 或手写

为什么要写默认构造——垃圾值实测（Cherno 构造集的 Entity 例子）：栈上创建对象时内存只是"分配"了，没人帮你初始化，成员就是上一位使用者留下的残骸：

class Entity {
public:
    float X, Y;
    Entity() { X = 0.0f; Y = 0.0f; }            // 默认构造：清零
    Entity(float x, float y) { X = x; Y = y; }  // 带参构造（重载）
    void Print() const { std::printf("%f, %f\n", X, Y); }
};

clang 23 -O0 实测（foo/bar 同深度调用、栈帧形状相同，bar 的 r 落在 foo 的 t 的栈槽上）：

class EntityRaw { public: float X, Y; /* 没写构造函数 */ ... };
void foo() { EntityRaw t; t.X = 123.25f; t.Y = 456.5f; t.Print(); }
void bar() { EntityRaw r; r.Print(); }          // r 从未初始化

123.250000, 456.500000                                    ← foo 的 t（初始化过）
raw: 212345931268716466679054336.000000, 0.000000         ← bar 的 r：栈残骸

r.X 读到的甚至不是 foo 留下的 123.25——中间一次 printf 又把那块栈踩了一遍。这就是"垃圾值"的真实含义：谁用过这块内存，就是谁的残骸，不保证任何值。写了 Entity() 的 a 则一定是 0,0，Entity e(10.0f, 5.0f) 一定是 10,5——构造函数的卖点是把"初始化"从"程序员记得做"变成"语言强制做"。

两点注意：① 演示依赖 -O0 和栈帧复用，垃圾值碰巧是 0 也完全可能（换了平台/优化级别就不同），所以这类 bug 阴险在"有时能跑"；② 视频里函数体赋值 X = x 对两个 float 无所谓，类类型成员就该用初始值列表（见上文），否则先默认构造再赋值是双重开销。

explicit 抑制隐式转换

class String {
public:
    explicit String(const char* s);   // explicit：禁止隐式转换
};
void f(String s);
f("hello");          // 没 explicit 时：隐式 char*→String，合法；有 explicit：编译错误
f(String("hello"));  // 显式构造，始终合法

explicit 防止"一个参数的构造函数"被编译器用来做意外的隐式类型转换。

术语：这种构造函数叫「转换构造函数」

C++ Primer §7.5.4 的说法更精确：只接受一个实参、且没有 explicit 的构造函数，定义了一条「从该实参类型到类类型」的隐式转换规则——这样的构造函数叫转换构造函数（converting constructor）。也就是说，你写一个单参构造函数的同时，等于顺手给编译器开了一条隐式转换通道，这是 C 程序员最陌生的 C++ 特性（C 的 struct 没有这种"构造函数顺带当转换器"的行为）。

class Entity {                       // Cherno 视频里的例子
    std::string m_Name; int m_Age;
public:
    Entity(const std::string& name) : m_Name(name), m_Age(-1) {}
    Entity(int age)                 : m_Name("Unknown"), m_Age(age) {}
};
void PrintEntity(const Entity&);

这个类同时开了两条口子：std::string → Entity、int → Entity。只要某个位置要求 Entity，你递一个 int 或一个 string 进去，编译器都会自己造一个临时 Entity 出来。

实测：22 真的变成了 Entity

Entity a = 22;                       // 隐式调用 Entity(int)
Entity b = std::string("Cherno");    // 隐式调用 Entity(const std::string&)
PrintEntity(22);                     // 同样：造临时 Entity 再传进去

clang 23.1.0（-std=c++17）实测输出：

Entity(Unknown, 22)      ← a = 22
Entity(Cherno, -1)       ← b = string
Entity(Unknown, 22)      ← PrintEntity(22)
Entity(Cherno, -1)

没有一个 Entity 字样出现在调用点——PrintEntity(22) 看起来像传了个数字，实际传进去的是一个 m_Name="Unknown"、m_Age=22 的对象。这就是隐式转换最阴的地方：调用点看不出发生了什么。

explicit 只挡「拷贝初始化」，不挡「直接初始化」

这是最容易记反的一条。explicit 的作用范围是"需要隐式转换的场合"，即拷贝初始化（= 和传参）；直接写出构造形式（()/{}）本来就是显式构造，不受影响：

写法 类别 不加 explicit 加 explicit
Entity a = 22; 拷贝初始化 ✅ ❌
PrintEntity(22) 传参（按拷贝初始化处理） ✅ ❌
Entity a(22); 直接初始化 ✅ ✅
Entity a{22}; 直接初始化（列表） ✅ ✅
PrintEntity(Entity(22)) 显式构造再传 ✅ ✅

加 explicit 后 clang 实测报错原文（两条构造函数都加）：

error: no viable conversion from 'int' to 'Entity'
    Entity a = 22;
           ^   ~~
note: explicit constructor is not a candidate
    explicit Entity(int age) : m_Name("Unknown"), m_Age(age) {}
            ^

注意措辞是 "explicit constructor is not a candidate"——函数在，但不参与隐式转换的候选集；改成 Entity a(22); 立刻编译通过。

反直觉的一点：字符串字面量反而不行

PrintEntity("Cherno");   // ❌ 即使构造函数不加 explicit 也编不过

"Cherno" 是 const char*，要走到 Entity 得经过 const char* → std::string → Entity，这是两次用户定义转换。C++ 规定：一条隐式转换序列里最多只允许一次用户定义转换（前后各可接若干标准转换），所以这条路直接死。实测报错：

error: no matching function for call to 'PrintEntity'
    PrintEntity("Cherno");
    ^~~~~~~~~~~
note: candidate function not viable: no known conversion from 'const char[7]' to 'const Entity'

修法只有两个：减少一次用户转换（PrintEntity(std::string("Cherno"))）或自己显式构造（PrintEntity(Entity("Cherno"))）。这条规则和另一端的转换运算符是一套东西，见 14.3 类型转换运算符。

C++11 起：多参数构造函数也能用 explicit（挡住隐式列表初始化）

explicit 不是单参构造的专利。C++11 有了列表初始化之后，f({1,2}) 这种"拿花括号列表当实参"的写法本身也是一种隐式转换（copy-list-initialization），多参构造函数加了 explicit 一样挡得住：

struct B { explicit B(int a, int b) {} };
void f(B);

f({1, 2});     // ❌ 隐式列表初始化被 explicit 挡住
f(B{1, 2});    // ✅ 显式构造

实测（clang 23.1.0，-std=c++17）：f({1,2}) 报 error: no matching function for call to 'f'；把 explicit 去掉立刻编译通过。

所以 §7.5.4 说的"单参数"只是最典型的场景，不是 explicit 的能力边界。判断标准始终只有一个：这次初始化是不是隐式发生的——是，就受 explicit 管；不是（你亲手写了 T(...)/T{...}），就不管。

和 CTAD 区分开（C++17 类模板参数推导）：两种写法都带 {}，但机制完全不同，实测对比：

写法 机制 加 explicit 后
Box b{1, 2}; CTAD：推导发生在"带初始化器的变量声明"上，本质是直接初始化 ✅ 不受影响（实测通过）
foo({1, 2}) 隐式列表初始化：函数实参位置不做 CTAD ❌ 被拦下（实测 no matching function）

再补一条：模板函数 template<class T> void g(Box<T>) 配 g({1,2}) 连推导都做不了（实测同样 no matching function for call to 'g'）——CTAD 只在"明写了类型名"的位置（变量声明、new、函数式强转）发生。

C++20：explicit(bool) 条件 explicit

C++20 允许给 explicit 传一个编译期布尔值，让"是否允许隐式"变成可计算的：

struct C { explicit(true)  C(int) {} };   // 等价普通 explicit：永远禁止隐式
struct D { explicit(false) D(int) {} };   // 等价不加：允许隐式
void g(C); void h(D);
g(1);   // ❌
h(1);   // ✅

实测（-std=c++20）：g(1) 报 no matching function for call to 'g'，h(1) 正常通过。真正的用途在模板——按类型特性决定要不要开隐式口子：

template<class T>
struct Wrapper {
    // 示意：T 能无损转成 int 才开放隐式转换，否则强制显式
    explicit(!std::is_convertible_v<T, int>) Wrapper(T) {}
};

⚠ 两件事别记混：explicit 修饰转换函数（explicit operator bool()）是 C++11 就有的（实测 -std=c++11 编译通过），C++20 新增的只是条件版 explicit(bool)。转换函数那半边见 14.3 类型转换运算符。

什么时候该加 explicit

默认都加，需要隐式时再摘。 判断依据是这个转换在语义上是否真的"等价"：

转换 该不该隐式 理由
std::string → Entity（名字） 可以商量 语义直观，但仍有歧义风险
int → Entity（年龄） ❌ 加 explicit "22" 到底是年龄还是 ID？读代码的人看不出来
const char* → std::string ✅ 标准库就没加 太常用，强制显式会很啰嗦
int → 价格/数量/时长 这类强类型 ❌ 加 explicit 单位语义不同，隐式转换是事故源头

HFT 视角：行情里的 Price、Qty、Timestamp 这类"强类型包装"（都是一个 int64_t 或 double 裹一层），构造函数一律 explicit。否则 calc(price, 100) 里的 100 会被悄悄当成价格，calc(qty, price) 也能编译通过——单位错误从"编译期报错"退化成"跑出来数字不对"，这正是隐式转换在交易系统里最贵的一类代价。宁可多写 Price{100} 几个字符。

内置类型那半边的隐式转换（整型提升、算术转换、数组退化）规则完全独立，见 4.11.1 隐式类型转换；本节只讲"类类型"这一半。

私有构造函数：阻止实例化

构造函数也有访问级别——把它放进 private，外部就不能创建对象了（Cherno 构造函数集演示）。典型场景：纯静态工具类，方法全是 static，实例化没有任何意义，干脆把构造函数私有化，谁写 Log l; 谁编译报错：

class Log {
private:
    Log() {}                        // 私有构造：禁止外部实例化
public:
    static void Write(const char* msg) { /* ... */ }
};

int main() {
    Log::Write("hello");            // OK：静态方法不需要对象
    Log l;                          // 编译错误
}

clang 23 实测报错原文：

error: calling a private constructor of class 'Log'
    Log l;
        ^
note: declared private here
    Log() {}
    ^

编译器先按重载决议选中 Log()，再做访问检查——函数能匹配、只是你没权调用，所以报错措辞是 "private"，不是 "no matching"。

C++11 现代替代：= delete。意图更直白，报错也更清楚，而且放 public 区即可（语义本来就是"谁都不能调"，不依赖访问控制）：

class Log {
public:
    Log() = delete;                 // 直接删除，比 private 空实现更明确
    static void Write(const char* msg) { /* ... */ }
};

clang 报错对比：error: call to deleted constructor of 'Log' + note: 'Log' has been explicitly marked deleted here——一眼看懂是"故意禁掉"，不像 private 还可能让人以为是封装细节。

私有构造函数更大的用途是受控创建——不是"不让你建"，而是"只能从我给的口子建"：

模式 手法 目的
纯静态工具类 Log() = delete;（或 private） 这个类根本不是拿来实例化的
单例 private 构造 + static Instance() 全程序只此一份（7.6 Meyer's Singleton 已实测）
工厂方法 private 构造 + static Conn open(...) 构造前要先做检查/分配资源

工厂版实测可跑（类内部有权访问自己的私有构造）：

class Conn {
private:
    Conn(int fd) : fd_(fd) {}              // 外部不能乱建
public:
    static Conn open(const char* path) {   // 唯一合法入口
        return Conn(42);                   // OK：类成员可访问私有构造
    }
    int fd() const { return fd_; }
private:
    int fd_;
};
// Conn c = Conn::open("/dev/tty");  // 编译运行通过
// Conn c(42);                        // error: calling a private constructor

对 C 程序员的对应物：C 没有访问控制，想"阻止直接构造"只能靠不透明指针——头文件只写 typedef struct conn Conn;，结构体定义藏进 .c 文件，外部连 sizeof 都不知道，自然无法声明实例，只能走 conn_open()。C++ 一行 private:/= delete 干的就是这件事，而且是编译器强制、不靠约定。

和 C 的区别

维度 C C++
构造函数 ❌ 无，对象用 = {0} 或手动 init ✅ 自动调用
初始化保证 ❌ 不 init 就是垃圾值 ✅ 构造后对象处于有效状态
忘记 init 常见 bug 构造函数强制调用，不会忘
explicit ❌ 无隐式转换概念 ✅ C++ 独有
阻止"直接构造" 只能靠不透明指针（结构体定义藏 .c） 构造函数 private / = delete，编译器强制

C 程序员最该体会的转变：

C 里 struct 初始化是手动且易忘的——忘了 init 就用垃圾值，是经典 bug 源：

/* C：必须手动 init，忘了就是垃圾值 */
struct Person { char name[32]; int age; };
struct Person p;          // age 是垃圾值！
person_init(&p, "Alice", 30);   // 必须记得调 init

C++ 构造函数保证对象一创建就处于有效状态，不可能"忘记初始化"：

// C++：构造函数强制调用，对象一生成就有效
class Person {
public:
    Person(std::string n, int a) : name_(std::move(n)), age_(a) {}
private:
    std::string name_;
    int age_;
};
Person p("Alice", 30);   // 创建即初始化，age_ 一定是 30

这从语言层面消除了"未初始化对象"这一整类 bug，是 C→C++ 最大的安全提升之一。

常见错误

  1. 类类型成员没用初始值列表：Person(string n, int a) { name_=n; age_=a; } —— name_ 先默认构造（空串），再赋值，多一次开销。修正：用初始值列表 : name_(std::move(n)), age_(a)。
  2. 声明带参构造后没有默认构造：class C { public: C(int); }; 然后 C obj; 编译错误——有了带参构造，默认构造不再自动生成。修正：加 C() = default; 或手写默认构造。
  3. 该用 explicit 没用：单参构造函数不加 explicit，导致意外的隐式转换。例如 String s = "x" 看着无害，但 void f(String) 接收 f("x") 会偷偷构造临时 String，可能引发性能问题或歧义。建议：单参构造默认加 explicit，确需隐式转换再去除。
  4. 纯静态工具类忘了禁实例化：class Log { public: static void Write(...); }; 什么都不加，新人随手写 Log l; 也能编译通过——生成了一个没有任何状态的死对象。修正：加 Log() = delete;（C++11 起）或把默认构造放 private，让误用在编译期暴露。

自测题

1. 选择题：下面哪种情况下编译器不会自动生成默认构造函数？ - A) 类没有任何构造函数 - B) 类只声明了一个带参构造函数 - C) 类有 const 成员但没类内初始值 - D) B 和 C 都是

答案

D。A：没有构造函数时编译器会生成默认构造。B：一旦声明任何构造函数，默认构造不再自动生成。C：有 const 成员或引用成员且没有类内初始值时，编译器无法生成默认构造（const/引用必须初始化）。所以 B 和 C 都会导致默认构造不被生成。

2. 判断题：构造函数初始值列表的书写顺序决定成员初始化顺序。

答案

错误。成员按声明顺序初始化，与初始值列表的书写顺序无关。这是常见误解。如果列表顺序与声明顺序不一致，编译器通常警告。跨成员依赖时要按声明顺序组织。

3. 踩坑题：下面代码 f(42) 能编译吗？为什么？

class Size {
public:
    Size(int n) {}    // 单参构造，没加 explicit
};
void f(Size s);
f(42);               // 传 int 给 Size 形参
答案

能编译。42 通过 Size 的单参构造函数隐式转换成临时 Size 对象。这有时是想要的，有时是 bug（你以为传的是 int，结果偷偷构造了对象）。修正：加 explicit Size(int n);，则 f(42) 编译错误，必须 f(Size(42)) 显式构造，避免意外。

4. 应用题：为一个 Vector2D 类设计构造函数：1) 默认构造 (0,0)；2) 接收 x,y；3) 接收单个值同时设 x 和 y。用委托构造减少重复，并说明哪个该加 explicit。

答案 
class Vector2D {
public:
    Vector2D(double x, double y) : x_(x), y_(y) {}        // 主构造
    Vector2D() : Vector2D(0, 0) {}                         // 委托：默认 (0,0)
    explicit Vector2D(double v) : Vector2D(v, v) {}        // 委托：单值，加 explicit
private:
    double x_, y_;
};
Vector2D a;              // (0,0)
Vector2D b(1, 2);        // (1,2)
Vector2D c(5.0);         // (5,5)，需要 explicit 也能用
// Vector2D d = 5.0;     // 编译错误：explicit 禁止隐式转换

单参构造 Vector2D(double) 应加 explicit，否则 double 会隐式转成 Vector2D，在数学运算里容易引发意外（如 v + 3.0 你以为加标量，实际加了个 Vector2D(3,3)）。双参和默认构造不需要 explicit（无法隐式转换）。

5. 判断题：栈上对象 EntityRaw r;（类没写构造函数，成员是 float X, Y;）的 X、Y 初值是 0。

答案

错误。标量类型成员的默认初始化什么都不做——内存只是分配，X、Y 是这块栈空间上一位使用者的残骸（实测打出过 2.1e26 这种天文数字，也碰巧可能是 0）。"碰巧是 0 能跑"换平台/优化级别就炸，所以未初始化 bug 极其阴险。修正：写默认构造 EntityRaw() : X(0), Y(0) {}，或 C++11 起类内初始值 float X = 0, Y = 0;。

6. 踩坑题：class Util { public: static int twice(int n) { return 2*n; } }; 有人写了 Util u; int x = u.twice(21);，能编译吗？有什么问题？怎么从类设计上杜绝？

答案

能编译——Util 没声明任何构造函数，编译器自动合成默认构造，Util u; 合法；静态成员函数也能通过对象调用（u.twice(21) 等价于 Util::twice(21)，不访问 this）。问题在于 Util 是纯静态工具类，u 是个没有状态的死对象，u.twice() 的写法还会误导读者以为它是普通成员函数。杜绝：加 Util() = delete;（或私有默认构造），Util u; 立即编译错误 call to deleted constructor of 'Util'，逼着所有人写 Util::twice(21)。

7. 踩坑题（explicit 综合）：下面哪几行编译失败？

struct Foo { explicit Foo(double d) {} };
void test(Foo f) {}

int main(){
    test(3.14);    // ①
    Foo f1(2.5);   // ②
    Foo f2 = 1.0;  // ③
    Foo f3{5.0};   // ④
}
答案

① 和 ③ 失败，②④ 通过。 实测（clang 23.1.0，-std=c++17）报错位置：

error: no matching function for call to 'test'                 ← ①（第 4 行）
error: no viable conversion from 'double' to 'Foo'             ← ③（第 6 行）

只保留 ②④ 的版本一次编译通过。

逐行理由：

  • ① test(3.14) 失败：传参按拷贝初始化处理，需要隐式转换 → 被 explicit 挡住。注意这里 3.14 就是 double，与 Foo(double) 精确匹配、一步类型转换都不需要——explicit 挡的是"隐式"这个动作本身，与要不要转换类型无关。这是最容易想错的一点：别以为"类型对得上就没事"。
  • ② Foo f1(2.5) 通过：直接初始化，你亲手写出了构造形式，不受 explicit 管。
  • ③ Foo f2 = 1.0 失败：拷贝初始化的标准形态。
  • ④ Foo f3{5.0} 通过：直接列表初始化，同样属于显式构造。

一句话判据：看等号还是括号——= 和"把值直接塞给形参"是隐式（受管），() / {} 紧跟类型名是显式（不受管）。

复习：→ explicit 抑制隐式转换

可跑的例子

examples/7.5-constructors.cpp —— 委托构造 + const/引用成员的强制初始化列表。

clang++ -std=c++20 examples/7.5-constructors.cpp -o /tmp/demo && /tmp/demo

真实输出（节选）：

  [Feed(AAPL, 0)] 真正干活的构造
  [Feed(AAPL)] 委托完毕，补点自己的事

  [Feed(MSFT, 10086)] 真正干活的构造

看出什么了？ Feed("AAPL") 自己不干活，转手委托给主构造——初始化逻辑只有一份入口。Order 里 const long id_ 和 long& book_ 在函数体里赋值直接编译失败（例子里留了错误写法的注释），初始化列表是唯一途径。

委托构造消灭初始化逻辑的复制粘贴——改一处，处处生效。

7.6

类的静态成员（Static Members）

本节讲什么

static 成员：属于整个类而非某个对象的成员。包括静态数据成员和静态成员函数。这是 C 程序员熟悉的概念——C 用文件级 static 变量/函数实现类似功能，C++ 把它纳入类作用域。

static 的三个含义：先分清这集在讲哪一个

TheCherno 的 Static 一集把 C++ 的 static 拆成两个含义——"类外 = 内部链接（只在本翻译单元可见）"、"类内 = 全实例共享一份"。严格说是三个："类外"里还藏着一种跟链接完全无关的用法：

static 出现在 含义 符号表里的样子（nm 实测） 详解
命名空间作用域（文件级"类外"） 内部链接：本翻译单元私有 小写 local（t/d），不导出 C 书 3.6.2 内部链接（C/C++ 规则相同）
类作用域（本节） 全实例共享一份，不属于任何对象 大写 global（S/D），导出后由链接器跨 TU 合并成一份 本节下文
块作用域（函数内局部 static） 静态存储期：只初始化一次、活到程序结束；与链接无关 小写 local（b），符号藏在本 TU C 书 3.8 static 关键字；Primer §6.1.1

注意中间那行和第一行的对比：同一个 static，在符号表里的可见性方向正好相反——文件级 static 是要让符号"消失"（小写 local，别的 TU 看不见），类 static 反而要导出大写 global 符号、靠链接器把各 TU 的引用合并成全程序唯一一份。实测（clang 23.1.0）：nm 里类静态成员是 S __ZN3Log7s_CountE。

纠正 Cherno 一句话："类之外使用 static 意味着内部链接"不严密——函数里的局部 static 也在"类之外"，但它跟链接没有任何关系，管的是存储期。

实测：类 static 共享一份 + 不进 sizeof

struct Log {
    static int s_Count;      // 类内声明
    int m_Level = 0;
};
int Log::s_Count = 0;        // 类外定义：全程序只有这一份

b.s_Count      = 42   （改的是 a 的 s_Count，b 也看到 → 共享一份）
&a.s_Count     = 0x102be0010
&b.s_Count     = 0x102be0010   （同一个地址）
sizeof(Log)    = 4    （静态成员不进任何对象，躺在 .data/.bss）

共享性 × 访问权限：两套正交的机制

static 决定的是存储与共享（整个继承体系一份），访问说明符决定的是谁能用名字碰到它——两者互不干涉。继承场景下实测（clang 23）：

class Base {
private:
    static int s_private;      // 类级共享，但名字只对 Base 开放
protected:
    static int s_protected;
public:
    static int s_public;
    static int peek() { return s_private; }   // 类内随便用
};
class Derived : public Base {
public:
    void poke() {
        (void)s_public;        // ✅
        (void)s_protected;     // ✅
        (void)s_private;       // ❌ 报错，见下
    }
};

error: 's_private' is a private member of 'Base'
note: declared private here

三个结论：

  1. 报错措辞证明成员真的被继承了——报的是 's_private' is a private member of 'Base'，不是 "no member named"。名字查找在继承体系里找到了它（Derived 的作用域里可见 Base 的所有静态成员），卡在访问检查这一关。"private 子类碰不到"≠"子类没有"。
  2. private static 是"访问权属于定义类"，不是"存储属于定义类"——整个继承体系仍然只有这一份。派生类对象路过 Base::peek() 这类静态成员函数照样能读到它的值（上面的 peek() 就是例证）；存储从不按继承分家。
  3. 想让子类用，只改访问级别，别复制一份——protected 让继承体系内可用，public 让全局可用；无论哪种，共享的都还是同一份。典型的家族配置是：private static 计数器 + protected static 的 nextId() 取号器。

一句话：static 管的是"存几份"，访问说明符管的是"谁能碰名字"；private 优先于 static——哪怕全体系共享，名字也只对定义它的类开放。

追加实测：子类名限定访问 = 还是父类那份

public static 在继承体系里可以经任何层级的类名限定访问（Base::s_public / Derived::s_public / GrandSon::s_public），但它们全是同一个实体：

&Base::s_public    = 0x104eb4018
&Derived::s_public = 0x104eb4018     ← 同一地址
Derived::s_public = 99;  →  Base::s_public 也变 99

符号层看得更透——.o 里只有一套符号，全部挂在 Base 名下，Derived/GrandSon 一个符号都没有：

D __ZN4Base8s_publicE      ← 唯一一份，data 段
S __ZN4Base8s_nextIdE      （protected）
S __ZN4Base9s_counterE     （private！照样是外部链接）

两个推论：

  1. Derived::s_public 不是"Derived 的成员"，只是名字查找穿透继承体系的结果——编译器沿继承链找到 Base 里的声明，剩下的和写 Base::s_public 一模一样。

  2. 访问控制不影响链接性——private static 的符号照样是外部链接（nm 大写 S，全局可见）。private 是编译期语言层面的墙，不是链接器层面的墙。实测（UB，但能编能跑）：

    cpp extern "C" int stolen __asm__("__ZN4Base9s_counterE"); // asm 标签直指 mangling 后的私有符号 stolen = 100; // 直接改 Base 的 private s_counter Base::peek() // → 100，类内读到的也被改了

    mangling 只是顺带的门槛（你得知道符号名），不是安全机制。安全边界止于源码——这正是访问说明符"封装边界"的真实含义：它防的是诚实的人写错，不是防恶意的人绕过。

局部 static 的隐藏开销：magic statics 与 guard

C++11 起局部 static 的初始化是线程安全的（"magic statics"），但这不是免费的——编译器为动态初始化的局部 static 生成守卫变量和加锁调用。实测对比：

int dyn_id()   { static int last = read_seed(); return ++last; }  // 动态初始化
int const_id() { static int last = 0;           return ++last; }  // 常量初始化
守卫变量（nm 里的 _ZGV...） 每次调用的守卫检查
dyn_id（动态初始化） 有 b __ZGVZ6dyn_idvE4last 有：ldaprb（load-acquire 原子读守卫字节）→ 未初始化走 __cxa_guard_acquire/release 慢路径
const_id（常量初始化） 没有 没有：零开销，加载期就已初始化

dyn_id 反汇编（重定位标注后）：

ldaprb  w8, [x8]                  ; 原子读 guard（ARM64 acquire 语义）
tbz     w8, #0, <慢路径>          ; guard 已置位 → 直接用
; 慢路径：
bl      ___cxa_guard_acquire      ; 抢初始化权（带锁）
bl      __Z9read_seedv            ; 真正执行初始化
bl      ___cxa_guard_release      ; 释放，置 guard

HFT 关联：热路径上的局部 static 有两笔账——每次调用都要付一次 acquire 原子读（ldaprb），首次调用还可能撞锁。能常量初始化就常量初始化（连 guard 变量都消失）；必须在热路径用动态初始化的，进热循环前先预热调一次。单例惯用法 static T instance; 吃的就是这套 guard。

应用实测：Meyer's Singleton（局部 static 版单例）

单例的另一半功夫在构造函数：把构造函数私有化（或 = delete），外部才无法绕过 Get() 自己 new 一个。纯静态工具类阻止实例化也是同一招——见 7.5 私有构造函数：阻止实例化。

Cherno 单例集给了两版写法，对比：

类静态成员指针版 Meyer's 局部静态版
写法 static Singleton* s_Instance;（类内声明） static Singleton instance;（写在 Get() 函数体内）
定义/初始化 类外手动写 Singleton* Singleton::s_Instance = new ... 无——首次调用 Get() 时自动构造（懒加载）
空指针风险 有（忘了初始化 / 提前使用就是 nullptr 解引用） 无（返回引用，不可能为空）
线程安全 自己管（双检锁等，易错） C++11 起标准保证初始化线程安全（就是上面那套 guard）
析构 自己管（delete 时机是经典难题，常干脆不删） 自动：退出阶段经 __cxa_atexit 调用 
class Singleton {
public:
    static Singleton& Get() {
        static Singleton instance;   // 局部静态：首次调用才构造，之后永远复用同一个
        return instance;             // 返回引用，不可能为空
    }
    void Hello() {}
};
// Singleton::Get().Hello() —— Get 是静态成员函数用 :: 调用；返回引用后 . 调用普通成员函数

「不在栈上」实测（clang 23.1.0，arm64）：

main 局部变量(栈)  : 0x16f446628    ← 高地址，栈区
单例 instance      : 0x1009bc060    ← 低地址，贴着镜像基址

nm 确认落在 data 段（D），旁边就是它的守卫变量：

00000000000004c8 D __ZZN9Singleton3GetEvE8instance      ← instance 本体
00000000000004d0 D __ZGVZN9Singleton3GetEvE8instance    ← magic statics 守卫

析构顺序灾难（static deinitialization order fiasco）实测——这版单例的小坑：它的析构发生在程序退出阶段，如果别的静态对象的析构函数还在用单例，顺序可能反过来。规则是「析构 = 构造完成的逆序」（局部 static 首次构造时经 __cxa_atexit 注册析构，反汇编里能看到调用）；atexit 队列像栈，后注册的先跑：

struct Logger {
    ~Logger() { Singleton::Get().Hello(); }  // 析构时还想用单例
};
Logger g_logger;   // 启动时构造（main 之前）→ 析构注册得早
int main() { Singleton::Get().Hello(); }     // instance 首次构造在 main 里 → 注册得晚

实测输出：

Logger() 构造              ← 启动时
Singleton() 构造           ← main 里首次 Get()
main 结束，进入退出阶段
~Singleton() 析构          ← ★ 单例先死（后构造的先析构）
~Logger() 析构，此时还想 Singleton::Get().Hello()：
  Hello() 被调用            ← ★ 在一具"尸体"上调用：UB，这次碰巧没崩

注意最后一行：Hello() 居然正常打印了——这正是 fiasco 最阴险的地方：UB 不等于必崩，对象内存还没被复用时"碰巧能跑"，换个平台/优化级别/构建顺序就炸。对策：静态对象的析构函数里不要用其他单例；日志这类"活到最后一刻"的基础设施要么故意泄漏（new 出来永不 delete，退出时让 OS 回收），要么保证它最后构造（最先析构）。

核心用法

静态数据成员

class Account {
public:
    static double rate() { return interest_rate; }   // 静态成员函数
    static void rate(double r);                       // 静态成员函数声明
private:
    static double interest_rate;                      // 静态数据成员声明
    double amount;
};

double Account::interest_rate = 0.05;    // 定义（类外），只能一次
void Account::rate(double r) { interest_rate = r; }
  • 静态数据成员不属于任何对象，所有对象共享一份
  • 必须在类外定义（分配存储），定义只能一次
  • 例外：constexpr 静态成员可类内初始化（C++17 起更宽松）——见下面这一节

实测：static const 整型成员能当数组大小，非 static 一个都别想

TheCherno 视频里那段 Entity 代码看着平平无奇，其实同时踩住了两个边界：

class Entity {
public:
    static const int size = 5;   // ① 全类一份  ② 编译期常量表达式
    int example[size];           // ← 只有同时满足①②才能这么写
    Entity() { for (int i = 0; i < size; i++) example[i] = 2; }
};

为什么合法：数组维度要求编译期常量表达式。static const 整型成员就地初始化后恰好满足——它既是常量，又不依赖任何对象（static 保证不进对象存储）。本机实测输出：

Entity::size      = 5
sizeof(Entity)    = 20 字节 —— 就是 5 个 int
example[0..4]     = 2 2 2 2 2
&e.size  == &e2.size ? 是（两个对象访问的是同一个实体）

删掉 static 立刻炸（clang 23.1.0 实测）：

class Entity {
public:
    const int size = 5;      // 非静态成员
    int example[size];       // ❌
};

error: invalid use of non-static data member 'size'
    4 |     int example[size];
      |                 ^~~~

注意报错理由不是「值不是常量」，而是「非静态数据成员」——类体还在定义时对象尚未存在，非静态成员连被引用做维度都不配。C 程序员的直觉（「我给了它初值 5 啊」）在这里完全不适用。

第二个坑：值有了，存储不一定有。 就地初始化只给了值，一旦有人取它的地址就发生 odr-use：

const int* p = &Entity::size;   // C++17 前：链接期 undefined reference

Undefined symbols for architecture arm64:
  "Entity::size", referenced from:
      _main in odr-xxxxx.o
ld: symbol(s) not found for architecture arm64

在 .cpp 里补一句 const int Entity::size; 即可（不能重复写初值）——这就是本节开头「必须在类外定义」那条规则的适用场景，只是它躲在「用着没事、一取地址就崩」的阴影里。

更省事的是直接换 static constexpr：C++17 起它是 inline 变量，上面同样的取地址代码链接通过（实测 &size = 0x102e1ffb4）。

结论：想拿静态成员当编译期常量用（数组维度、switch case、模板非类型参数），一律写 static constexpr。它隐含 inline，免掉类外定义，语义也更强——constexpr 强制初始值必须是编译期常量。static const int 是 C++11 时代的写法，能用但别默认用。

顺带把主线串起来：这里的 example 是对象内嵌数组，跟着对象走，sizeof(Entity) 就是实打实的 20 字节——它不需要 new，也不需要 delete。对照 12.2 直接内存管理：只有 new int[size] 出来的才需要手动释放，也才是 HFT 里要消灭的东西。

静态成员函数

// 静态成员函数
Account::rate();        // 通过类名调用（推荐）
Account acc;
acc.rate();             // 也可通过对象调用（不推荐，误导）
  • 静态成员函数没有 this 指针（不属于某个对象）
  • 因此只能访问静态成员，不能访问非静态成员
  • 不能声明为 const（const 是修饰 this 的，静态函数没 this）

实测：静态成员函数 = 自由函数 + 类作用域（连隐藏的 this 都没有）

7.1 实测过"普通成员函数 = 自由函数 + 隐藏 this"。静态成员函数更进一步——调用约定上和自由函数逐条指令相同（clang 23.1.0，-target x86_64-pc-windows-msvc -O0，MSVC ABI 用 rcx/edx 传参）：

"?LogMessage@Log@@SAXH@Z"        ; 静态成员：参数表只有 (int)，只有 ecx
    movl    %ecx, 4(%rsp)
    movl    4(%rsp), %eax
    addl    "?g@@3HA"(%rip), %eax

"?FreeFn@@YAXH@Z"                ; 自由函数：指令逐条相同
    movl    %ecx, 4(%rsp)
    movl    4(%rsp), %eax
    addl    "?g@@3HA"(%rip), %eax

"?Work@Log@@QEAAXH@Z"            ; 普通成员：rcx 收 this、edx 才是 int
    movl    %edx, 12(%rsp)
    movq    %rcx, (%rsp)         ; ← 隐藏 this 在这

mangled name 也印证（MSVC 编码）：S（static，无 this）vs QEAA（非静态成员，thiscall）vs Y（自由函数）。

调用点的对比更直白——main 里三种写法：

    callq   "?LogMessage@Log@@SAXH@Z"   ; Log::LogMessage(1)：不传任何对象
    callq   "?LogMessage@Log@@SAXH@Z"   ; log.LogMessage(2)：★ 同样没有 leaq 取 &log
    leaq    32(%rsp), %rcx                ; log.Work(3)：先取 &log 进 rcx（隐藏 this）
    callq   "?Work@Log@@QEAAXH@Z"

log.LogMessage(2) 这种"通过对象调用静态函数"的写法，编译器连 log 的地址都懒得加载——对象被完全无视。所以 7.6 前文"不推荐用对象调用"现在有汇编证据了：它不是风格问题，是这个对象在生成的代码里根本不存在。

结论：静态成员函数 ≈ 自由函数 + 类作用域 + 访问控制。和普通成员函数的差别不只是"少个 this"——它从 ABI 层面就不是成员函数那套东西。

推论：静态成员函数的地址就是普通函数指针（回调场景的门票）

"≈ 自由函数"不只是说法，类型系统里就是事实（clang 23.1.0 本机实测）：

struct Counter {
    static int count;
    static int getCount() { return count; }
    int getCountObj() const { return count; }
};
int Counter::count = 42;

typedef int (*GetterFn)(void);          // C 风格回调：只收普通函数指针
GetterFn p = &Counter::getCount;        // ✅ 直接赋值，不需要任何对象
// GetterFn q = &Counter::getCountObj;  // ❌ error: cannot initialize 'int (*)()'
                                        //    with 'int (C::*)()' —— 类型根本不同
  • &Counter::getCount 的类型经 static_assert(std::is_same_v<..., int(*)()>) 验证就是普通函数指针；传给 call_back(GetterFn) 正常返回 42。
  • 普通成员函数的地址是成员指针 int (Counter::*)() const——另一种类型，且必须配合对象（obj.*p）才能调用。
  • 大小都不一样（Itanium ABI）：sizeof(普通函数指针) = 8，sizeof(成员函数指针) = 16（成员指针要额外带一份 this 调整量，用于多继承/虚继承场景）。

HFT/嵌入式关联：C 风格的回调注册接口（qsort 的比较函数、FreeRTOS 的任务入口 void(*)(void*)、中断向量表、各类 C API 的 callback 参数）只认普通函数指针。想把"类里的逻辑"挂进去，静态成员函数是唯一不需要 trampoline/全局包装函数的入口——这也是为什么嵌入式 C++ 代码里回调一律写成 static 成员函数，需要上下文时再通过 void* 参数把对象捞回来（即 C 世界的 userdata 惯用法）。

顺带纠一个常见表述：普通成员函数也不"属于每个对象"——代码全程序一份，不占对象存储（前文 sizeof(Log)=4 已证）；差别只在调用时多收一个 this 参数。

静态成员的独特用途

静态成员可以是不完全类型（如指向自身类型的指针），非静态成员不行：

class Node {
    static Node* root;     // OK，静态成员可以是指向自身的不完全类型指针
    // Node n;             // 错误：非静态成员必须是完全类型
};

和 C 的区别

维度 C C++
类级共享变量 文件级 static 变量（无类作用域） ✅ 类的 static 成员
作用域 文件作用域（容易命名冲突） 类作用域（Account::rate）
访问控制 无（全文件可见） 受 public/private 控制
与类关联 无（只是约定放一起） ✅ 语言层面关联

C 程序员的理解：

C 里"属于某类型的共享变量"用文件级 static 实现，但它在文件作用域，不属于任何类型：

/* C：文件级 static 变量模拟"类级共享" */
static double interest_rate = 0.05;   // 文件作用域，不是 Account 的一部分
double account_get_rate(void) { return interest_rate; }

C++ 把它纳入类作用域，有访问控制，且语义上属于类：

// C++：static 成员属于类，有作用域和访问控制
class Account {
private:
    static double interest_rate;   // Account 的一部分，private 保护
};

好处：1) 命名不冲突（Account::rate vs Bank::rate）；2) 访问控制（private static 外部不可见）；3) 与类绑定，语义清晰。

常见错误

  1. 静态成员只在类内声明，忘了类外定义：static double interest_rate; 在类内声明，如果没有类外 double Account::interest_rate = 0;，链接时"undefined reference"。修正：在 .cpp 文件中定义一次。
  2. 静态成员函数访问非静态成员：static void f() { amount = 0; } —— 静态函数没 this，不知道是哪个对象的 amount，编译错误。修正：传对象引用，或把要访问的成员也设为 static。
  3. 静态成员函数声明为 const：static void f() const; —— const 修饰的是 this，静态函数没 this，编译错误。静态函数不能是 const。

自测题

1. 选择题：下面关于静态成员的说法正确的是？ - A) 静态数据成员每个对象各有一份 - B) 静态成员函数有 this 指针 - C) 静态数据成员必须在类外定义（constexpr 除外） - D) 静态成员函数可以访问非静态成员

答案

C。静态数据成员所有对象共享一份（A 错），必须类外定义（constexpr 静态成员可类内初始化）。静态函数没 this（B 错），不能访问非静态成员（D 错）。

2. 判断题：Account::rate() 和 acc.rate()（acc 是对象）调用同一个静态函数，效果完全一样。

答案

正确。两者调用的是同一个静态成员函数，效果一样。但推荐用 Account::rate()（类名调用），因为静态函数与具体对象无关，用对象调用会误导读者以为依赖该对象。

3. 踩坑题：下面代码链接时报错"undefined reference to Account::count_"，为什么？

// account.h
class Account {
public:
    Account() { ++count_; }
private:
    static int count_;    // 声明
};
// account.cpp —— 空的，没写 count_ 的定义
答案

静态数据成员在类内只是声明，必须在类外（通常 .cpp 文件）定义分配存储。缺少定义导致链接错误。修正：在 account.cpp 加：

int Account::count_ = 0;   // 定义并初始化，只能一次

例外：C++17 起可用 inline static int count_ = 0; 在类内直接定义，或 constexpr 静态成员类内初始化。

4. 应用题：用静态成员实现一个"全局唯一 ID 生成器"，每次调用 next() 返回递增 ID。说明静态成员相比 C 全局变量的优势。

答案 
class IdGen {
public:
    static long next() { return ++last_; }   // 静态函数
private:
    static long last_;                        // 静态数据，类外定义
};
long IdGen::last_ = 0;                        // 类外定义

// 使用
long a = IdGen::next();   // 1
long b = IdGen::next();   // 2

相比 C 全局变量 static long last = 0;：1) last_ 是 private，外部不能直接改（C 全局变量文件内可改）；2) IdGen::next 有类作用域，不会和别的 next 冲突；3) 语义上 ID 生成器是个概念，封装成类更清晰；4) 容易扩展为线程安全（加 mutex 成员）。C 全局变量无封装、易冲突。

5. 分析题：下面三处 static，nm 看到的符号绑定（大写 global / 小写 local）分别是什么？哪一处其实跟链接无关？

static int a;                    // ① 文件作用域
struct S { static int b; };      // ② 类作用域
int S::b = 0;
int f() { static int c = 0; return ++c; }   // ③ 块作用域
答案
  • ① 文件级 static → 小写 local（内部链接）：符号不导出，其他翻译单元看不见。这是 static 的"隐藏"语义。
  • ② 类 static → 大写 global（外部链接）：符号导出，靠链接器把各 TU 对它的引用合并成全程序唯一一份（实测 S __ZN1S1bE 这种大写符号）。注意它和①可见性方向正好相反——同一个关键字，一个是让符号消失，一个是让符号全局唯一。
  • ③ 函数内 static → 小写 local，但它跟链接无关：它管的是存储期（只初始化一次、活到程序结束），不是可见性。把它和①混为一谈正是"类外 static = 内部链接"这句话不严密的地方。

附带：③若用非常量表达式初始化（如 static int c = read_seed();），编译器还会生成 guard 变量（nm 里的 _ZGV...）和 __cxa_guard_acquire 调用——C++11 起局部 static 初始化线程安全的代价；常量初始化则完全免费。

6. 陷阱题：下面代码能不能编译？如果能，A::foo(a) 之后 a.x 是多少？

struct A {
    int x = 0;
    static void foo(A a) { a.x = 10; }
};
int main() { A a; A::foo(a); }
答案

能编译——静态成员函数没有 this，但 a 是你自己传进去的参数，通过参数访问实例成员完全合法（这正是"传对象进去"的例外用法）。

但 a.x 仍是 0——这题的第二层坑：参数是按值传递，foo 里改的是副本，调用者的 a 原封不动。clang 23.1.0 实测：

foo(a) 之后 a.x = 0（按值传参，改的是副本）
bar(a) 之后 a.x = 20（按引用传参 A&，真改了）

要真改调用者的对象，参数必须是 A& 或 A*。

第三层（顺带测了）：把 x 改成 private，static void poke(B& b) { b.secret = 99; } 照样能编译——访问控制是"类级别"不是"对象级别"：poke 是 B 的成员，对 B 的任何对象（哪怕是参数传进来的）都有 private 访问权。实测 poke(b) 后 b.secret == 99。

一句话总结：static 缺的只是 this，不是访问权，也不是"碰不到实例成员"——给它一个对象（引用/指针），它和成员函数一样能干。

8. 陷阱题：下面五条分别能不能通过？重点是④和⑤的"会不会编过"与"会不会链接过"不是一回事。

struct A { static const int size = 5;      int arr[size]; };   // ①
struct B { const int size = 5;             int arr[size]; };   // ②
struct C { static constexpr int size = 5;  int arr[size]; };   // ③
const int* pa = &A::size;    // ④
const int* pc = &C::size;    // ⑤
答案
  • ① 能通过。static const 整型就地初始化 = 编译期常量表达式，可作数组维度；size 不占对象存储，sizeof(A) = 20。
  • ② 编译错误：error: invalid use of non-static data member 'size'。理由不是"值不是常量"，是非静态成员在类定义期根本没有实体——初值写 5 也没用。
  • ③ 能通过，且比 ① 更好：C++17 起 constexpr 静态成员隐含 inline。
  • ④ 编译能过，链接崩：Undefined symbols for architecture arm64: "A::size"。就地初始化只给值不给存储，取地址构成 odr-use，必须在 .cpp 补 const int A::size;（不能再写初值）。补完就正常。（注意这是 C++17 前的写法结论；编译器对新标准下的 ODR 处理会放宽，但保留类外定义永远安全。）
  • ⑤ 能通过：static constexpr 是 inline 变量，无需类外定义（实测 &C::size = 0x102e1ffb4）。

一句话：要么别取地址（那就怎么写都行），要么写 static constexpr。

7. 分析题：Meyer's 单例 + 一个全局日志器，退出阶段会发生什么？

class Singleton {
public:
    static Singleton& Get() { static Singleton instance; return instance; }
    void Hello() {}
};
struct Logger { ~Logger() { Singleton::Get().Hello(); } };
Logger g_logger;
int main() { Singleton::Get().Hello(); }
答案

~Logger 运行时单例已经析构了——UB。析构顺序 = 构造完成的逆序：g_logger 启动时构造（main 之前），instance 首次 Get() 才构造（main 里，更晚）；所以退出阶段 instance 先析构，g_logger 后析构，它的析构函数在"尸体"上调用 Hello()。

实测这个程序没崩、Hello() 正常打印——UB 不等于必崩，对象内存还没被复用时"碰巧能跑"，这正是 static deinitialization order fiasco 最难排查的原因。对策：静态对象的析构函数不依赖其他单例；必须"活到最后"的基础设施故意泄漏（new 出来永不 delete）。

机制层面：局部 static 首次构造时编译器调用 __cxa_atexit 注册析构（反汇编可见），atexit 队列后注册先跑——和命名空间静态对象的析构混在同一个逆序队列里。

可跑的例子

examples/7.6-static-members.cpp —— 全类共享一份的存活计数器。

clang++ -std=c++20 examples/7.6-static-members.cpp -o /tmp/demo && /tmp/demo

真实输出（节选）：

初始存活订单 = 0
构造 3 个后 = 3
sizeof(Order) = 8 字节 —— 只有 id_，不含静态成员
出了作用域 = 0
通过对象调用 = 1，通过类名调用 = 1

看出什么了？ 三个对象出生计数到 3、析构回落到 0——活着的订单被精确追踪。而 sizeof(Order) 只有 8 字节：静态成员 live_ 存在 .data/.bss，不进任何对象。

这就是对象池/订单管理器核心状态的实现方式：静态计数 + 对象构造析构自动增减。
