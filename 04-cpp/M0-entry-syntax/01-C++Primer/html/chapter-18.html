18.1

异常处理（深入版）

本节讲什么

第 5 章只教了 try/catch/throw 的语法。本章把异常当工程机制讲透： 栈展开的精确顺序、noexcept 的真实作用（不只是"承诺不抛"）、 标准异常体系、异常安全三级保证。代码均经本机 g++ 13.3 / -std=c++17 实测（2026-10-07）。

① 栈展开（stack unwinding）：异常抛出后到底发生什么

throw 之后，控制流沿调用链逐层退出，每层像 return 一样销毁局部对象—— 析构函数被调用，但层内 throw 点之后的代码不再执行：

#include <iostream>
#include <stdexcept>
struct Tracer {
    const char* name;
    Tracer(const char* n) : name(n) { std::cout << "构造 " << name << "\n"; }
    ~Tracer() { std::cout << "析构 " << name << "\n"; }
};
void lvl2() { Tracer t2("lvl2"); throw std::runtime_error("boom"); }
void lvl1() { Tracer t1("lvl1"); lvl2(); std::cout << "不会到这\n"; }
int main() {
    try { lvl1(); }
    catch (const std::runtime_error& e) { std::cout << "捕获: " << e.what() << "\n"; }
}

本机实测输出：

构造 lvl1
构造 lvl2
析构 lvl2      ← 栈展开：先退 lvl2 帧
析构 lvl1      ← 再退 lvl1 帧（"不会到这"被跳过）
捕获: boom

两个推论： 1. RAII 对象（智能指针/容器/锁守卫/fstream）在异常路径上自动清理—— 这是 C++ 异常相对 C setjmp/longjmp 的本质优势（longjmp 不做任何清理）。 2. 析构函数绝不能抛异常——栈展开中再抛 = std::terminate。 所以所有标准容器的析构都是 noexcept，你写的析构也该是。

② noexcept：不是承诺，是优化许可证

标 noexcept 的函数抛异常 → std::terminate（不会展开到调用方）。 但它最大的实战价值不是语义承诺，而是给标准库发许可证：

struct MoveThrow    { MoveThrow(){} MoveThrow(const MoveThrow&){ std::cout<<"拷贝\n"; }
                      MoveThrow(MoveThrow&&){ std::cout<<"移动\n"; } };              // 移动没标 noexcept
struct MoveNoexcept { MoveNoexcept(){} MoveNoexcept(const MoveNoexcept&){ std::cout<<"拷贝\n"; }
                      MoveThrow(MoveThrow&&) = delete;
                      MoveNoexcept(MoveNoexcept&&) noexcept { std::cout<<"移动\n"; } };
std::vector<MoveThrow> v1;    v1.emplace_back(); v1.emplace_back();   // 扩容时…
std::vector<MoveNoexcept> v2; v2.emplace_back(); v2.emplace_back();

本机实测输出：v1 扩容打印 拷贝，v2 扩容打印 移动。

原因：vector 扩容要搬元素，若移动构造可能抛异常，搬到一半抛出会破坏强保证—— 于是它保守地选拷贝（拷贝抛了还能销毁新缓冲区回滚）。只有移动标了 noexcept， 扩容才敢用移动。你的值类型的移动构造/移动赋值/ swap 永远标 noexcept—— 否则全仓库的 vector<T> 都在默默拷贝。

③ 标准异常体系与捕获顺序

std::exception
├── std::runtime_error   （运行时才发现：overflow_error / system_error / ios_base::failure）
├── std::logic_error     （程序逻辑错误：invalid_argument / out_of_range / length_error）
├── std::bad_alloc       （new 失败）
├── std::bad_cast        （dynamic_cast 引用版失败）
└── std::bad_exception
  • 捕获按声明顺序匹配，派生类在前：catch (const runtime_error&) 必须写在 catch (const exception&) 前面，否则永远被基类截胡（编译器会给警告）。
  • 永远按 const 引用捕获：catch (const std::exception& e)——按值捕获会切片 （派生类被拷成基类，what() 多态失效）。
  • throw;（空 throw）在 catch 内原样重抛当前异常，保留原始类型； throw e; 会切片成静态类型。

④ 异常安全三级保证（写库时的契约）

级别 承诺 例子
基本保证 异常后对象仍可用（不泄漏、不变性不破坏），但状态可能已变 vector::push_back 分配失败
强保证 操作要么完全成功，要么回滚到调用前状态 vector 扩容失败时原内容不变
无异常保证 永不抛出 析构、移动构造、swap、vector::size

工程推论：自己写容器/资源类时，先想清楚每个操作给哪一级—— 然后"先改副本、再 noexcept swap 提交"（copy-and-swap 惯用法）就能用 基本保证的零件拼出强保证的整体。

⑤ 函数 try 块（冷但考过）

构造函数的成员初始化列表抛异常，普通函数体 catch 接不住——要包整个构造：

struct Wrap {
    Risky r;
    Wrap() try : r(make_risky()) {   // 函数 try 块：捕获初始化列表的异常
    } catch (const std::exception&) {
        // 注意：构造函数的 catch 结束时**自动重抛**——对象没建成，不能假装成功
        std::cerr << "构造失败\n";
    }
};

和 C 的区别 / 新手要点

C C++
返回值错误码 + goto cleanup throw + RAII 自动清理
setjmp/longjmp（不清理局部资源） 栈展开逐帧调析构
错误处理散在每个调用点 错误沿调用链自动冒泡到能处理的层

新手要点：① 别用异常做正常流程控制（查找失败返回 std::optional 更合适）； ② 异常的价值在跨层——同层内能处理的错误就返回值；③ 热路径不抛异常 （见 HFT 关联），异常是给"出事了"的路径用的。

HFT 关联

  • tick-to-trade 主路径零异常：throw 的开销在 µs 级（查 LSDA 表 + 逐帧展开）， 且不可预测——主路径用错误码/expected，异常只留给启动/配置/重连这类冷路径
  • noexcept 是延迟预算的一部分：标了 noexcept 的移动让 vector 扩容走移动而非拷贝， 直接影响行情队列扩容时的毛刺
  • dynamic_cast/异常都依赖 RTTI/展开表——部分 HFT 团队直接 -fno-exceptions -fno-rtti 编译热路径库，错误全靠返回码（代价是失去标准库异常的便利，要想清楚边界）

代码自测

题目 1： 以下代码的异常安全性如何？如何改进？

void f() {
    int* p = new int[100];
    do_work(p);  // 可能抛异常
    delete[] p;
}
参考答案

如果 do_work 抛异常，p 泄漏。改进：用 RAII（智能指针）：

void f() {
    auto p = std::make_unique<int[]>(100);
    do_work(p.get());  // 异常时 p 自动析构释放
}

C++ 异常安全三个级别：基本保证（不泄漏不损坏）、强保证（操作成功或回滚）、不抛保证（noexcept）。

题目 2： vector<MyType> 扩容比预期慢一倍，怀疑在拷贝而不是移动，怎么验证和修？

参考答案

验证：给 MyType 的移动构造和拷贝构造各加一行打印，观察扩容时打的是哪个。 修复：把移动构造标 noexcept——vector 只有确认移动不会抛才敢用它（本机实测：未标时扩容走拷贝）。 顺带把析构、swap、移动赋值也标上。

题目 3： 下面的 catch 链有什么问题？

try { parse(buf); }
catch (const std::exception& e)   { log(e.what()); }
catch (const std::runtime_error& e) { retry(); }
参考答案

顺序反了：runtime_error 是 exception 的派生类，会被第一个 catch 截胡， 第二个永远到不了（g++ 会给 -Wexception 警告）。派生类 catch 必须放前面。

18.2

命名空间 namespace

本节讲什么

namespace 解决的是 C 时代靠前缀硬扛的命名冲突问题。本节覆盖： 定义与嵌套、using 声明 vs 指令的坑、未命名命名空间（替代 static）、 inline 命名空间（库版本化的现代手段）、ADL（参数依赖查找——"为什么 std::swap 不写 std:: 也能调"）。 代码均经本机 g++ 13.3 / -std=c++17 实测（2026-10-07）。

① 定义与嵌套

namespace math {
    int abs(int x) { return x < 0 ? -x : x; }
    namespace detail {          // 嵌套：实现细节藏起来
        int gcd(int a, int b);
    }
}
namespace a::b::c { void f(); }  // C++17 嵌套简写，等价于三层嵌套

要点： - 命名空间可以跨文件重复打开——同一 namespace mylib 出现在 10 个头文件里， 它们拼成同一个命名空间（和类完全不同，类只能定义一次） - 命名空间成员默认外部链接（别的 TU 可见）；想限制在本文件用 ③ 的未命名命名空间

② using 声明 vs using 指令（事故高发区）

using math::abs;        // using 声明：只引入这一个名字，参与重载决议
using namespace math;   // using 指令：整个命名空间的名字都"可见"（不真正引入）

纪律： 1. 头文件里永远不写 using namespace——它会传染给每个包含者，制造无法定位的冲突 2. .cpp 里可以用，但也尽量局部用：函数体内 using std::cout; 比文件级 using namespace std; 安全 3. using namespace std; 最常见的翻车：std::count/std::find 和你的同名函数撞车， 错误消息在模板深处几十行

③ 未命名命名空间 = 现代版 static（文件内可见性）

namespace {
    int file_local = 42;     // 只在本翻译单元可见（内部链接）
    void helper() {}
}
  • 效果等价于全局 static，但还能用于类型（static 不能修饰类/模板）：
namespace { struct Impl { /* pImpl 的实现 */ }; }   // static 做不到这个
  • C++ 官方推荐用未命名命名空间代替文件级 static（static 的"内部链接"用法已被标记 deprecated 又恢复，但社区共识是 namespace 版更一致）

④ inline 命名空间：库的 ABI 版本化（C++11）

namespace mylib {
    inline namespace v_current { void f() { std::cout << "current f\n"; } }
    namespace legacy           { void f() { std::cout << "legacy f\n"; } }
}
int main() {
    mylib::f();          // ✅ 打到 v_current::f——inline 空间的名字对上层"透明"
    mylib::legacy::f();  // 老版本仍可显式访问
}

本机实测输出：current f / legacy f —— mylib::f() 自动落到 inline 的那个。

用途：库升级时把新 API 放 inline namespace v2，旧版保留在 v1—— 老代码链接的符号名带 v1（mangled name 不同），新老目标文件混链不炸。 标准库自己就在用：std::chrono 的部分符号在 std::__1::chrono（libc++ 的 inline 命名空间 __1）。

⑤ ADL（参数依赖查找 / Koenig lookup）

namespace A {
    struct S {};
    void greet(const S&) { std::cout << "ADL 找到 A::greet\n"; }
}
int main() {
    A::S s;
    greet(s);            // 没写 A:: —— 编译器按**实参类型**追加查找 s 所在的命名空间 A
}

本机实测输出：ADL 找到 A::greet。

规则：调用未限定的函数名时，除常规查找外，实参类型关联的命名空间也加入查找集。 这就是这些写法能工作的原因：

std::vector<int> v;
std::sort(v.begin(), v.end());     // 其实写 sort(...) 也可能编过（ADL 找到 std::sort）
cout << x;                         // operator<< 靠 ADL 找到（它不是你类的成员）
swap(a, b);                        // 自定义类型的 swap 惯例：靠 ADL 命中

工程推论：给你的类型写 swap/operator<</hash 时，放在类型自己的命名空间里—— 用户靠 ADL 自然命中，不用 std:: 也不用 using。

和 C 的区别 / 新手要点

C C++
前缀防冲突：mylib_queue_push namespace mylib { queue::push }
文件内私有：static void helper() namespace { void helper() {} }（还能藏类型）
无 ADL / inline namespace / 跨文件拼装

新手要点：① 头文件禁 using namespace；② 内部实现放 namespace detail 或 namespace impl（社区惯例：detail 里的东西 = 别用）；③ 全局 static 换未命名命名空间是新代码的标准姿势。

HFT 关联

  • 大型交易系统按子系统划分命名空间（md::（行情）、oms::、risk::、strat::）， 跨模块调用全限定名一眼看出依赖方向
  • inline namespace 是行情解码库版本化的标准做法：协议升级（如深交所 v1.19 → v1.22） 时老策略二进制仍可链接旧符号
  • ADL 对模板库尤其重要：写泛型代码时 using std::swap; swap(a, b); 两步走—— 让自定义类型的 swap 经 ADL 优先命中，标准 swap 兜底

代码自测

题目 1： 下面这段能编译吗？为什么？

// a.h
namespace util { void log(const char*); }
using namespace util;
// b.cpp
#include "a.h"
void log(int);   // ?
参考答案

能编译但是地雷：using namespace util 写在头文件里，每个包含 a.h 的 TU 都被污染； util::log(const char*) 和你的 log(int) 进入同一作用域——之后 log("x") / log(1) 的重载决议可能随包含顺序变化。头文件只允许 using 声明（也最好不），禁 using 指令。

题目 2： namespace { static int x; } 里的 static 多余吗？

参考答案

多余且自相矛盾：未命名命名空间已经把成员变成内部链接，再写 static 没有新效果 （语义相同，纯属冗余）。统一写成 namespace { int x; }。

题目 3： 为什么 std::cout << my_type 能找到你写的 operator<<，即使它不在 std 里？

参考答案

ADL：operator<< 的实参之一是 my_type（在你自己的命名空间 N 里）， 编译器把 N 加入查找集，命中你在 N 里定义的 operator<<。 所以自定义类型的流输出运算符就该放在类型自己的命名空间，不要图省事放全局。

18.3

多重继承与虚继承

本节讲什么

多重继承（MI）是 C++ 最有争议的特性：接口组合离不开它，菱形继承和布局复杂度又让人怕它。 本节把三件事讲清：MI 的内存布局（this 调整）、菱形问题与虚继承、 以及工程上的安全用法（混入接口 vs 数据继承）。代码均经本机 g++ 13.3 / -std=c++17 实测（2026-10-07）。

① MI 的内存布局与 this 调整（实测）

struct A { int a = 1; };
struct B { int b = 2; };
struct C : A, B { int c = 3; };
int main() {
    C obj;
    B* pb = &obj;
    // &obj == 0x...dc6c，pb == 0x...dc70（+4 偏移！）
}

本机实测：

sizeof(C) = 12                 ← A 子对象 + B 子对象 + 自身成员顺序排列
&obj = 0x7ffc...dc6c
pb   = 0x7ffc...dc70           ← B* 不指向对象开头，指向 B 子对象（this 调整 +4）

推论： 1. MI 下基类指针不等于对象首地址（除第一个基类）—— 所以 (B*)&obj 这类 C 强转在 MI 下是错的（不做偏移调整）， 必须用 static_cast<B*>(&obj)（编译器插入偏移）。 2. 每个带虚函数的基类各带一个 vptr——C : A(虚), B(虚) 的对象有两个 vptr。 3. dynamic_cast/typeid 在 MI 下要做运行时偏移计算，比单继承贵。

② 菱形继承与虚继承（实测）

     A                普通继承：D 和 E 各带一份 A → F 里有两份 A（二义 + 浪费）
    / \               虚继承：  A 只有一份，D/E 通过虚基表指针找到共享的 A
   D   E
    \ /
     F

struct D : virtual A { };
struct E : virtual A { };
struct F : D, E { };        // A 只有一份

本机实测：

sizeof(F) = 24    ← 两个 vptr（含虚基指针）+ 共享的一份 A(int) + 对齐
sizeof(D) = 16    ← vptr(8) + A::a(4) + padding
非虚版本的话，D、E 里各有一份 A → F 中 A 出现两次，sizeof 至少 8 字节纯浪费且 a 有二义

虚继承的三个代价（想清楚再用）： 1. 对象里多一个虚基表指针（vptr 变大），每次访问虚基成员多一次间接 2. 最派生类负责构造虚基：F 的构造函数直接调用 A 的构造， D/E 构造里对 A 的初始化被忽略——初始化责任跳级，新人极易踩 3. 向下转型（F* → D*）需要运行期查虚基表，static_cast 变贵

③ 工程安全用法：接口混入（mixin）而非数据共享

工业界对 MI 的共识用法是第二个及以后的基类都是"接口"（纯虚、无数据、无状态）：

struct Serializable {                        // 接口：无数据
    virtual ~Serializable() = default;
    virtual void serialize(Buffer&) const = 0;
};
struct Measurable {                          // 接口：无数据
    virtual ~Measurable() = default;
    virtual double latency_ns() const = 0;
};

struct Order : MktDataBase, Serializable, Measurable {   // 数据单继承 + 接口多继承
    void serialize(Buffer&) const override { /*...*/ }
    double latency_ns() const override { /*...*/ }
};
  • 数据继承保持单链（避开菱形），能力扩展走接口 MI—— 这就是 Java/C# interface 的 C++ 表达
  • CRTP（class T : public Base<T>）能在编译期实现类似 mixin 的效果且零虚函数开销—— 热路径优先 CRTP（见 ch16 模板），运行期多态需求才用接口 MI

④ 其他必知点

  • 名字冲突：两个基类有同名成员 → 调用处必须显式限定 obj.A::f()， 或在派生类用 using A::f; 消除二义
  • 虚函数覆盖：C::f() 可以同时覆盖 A::f 和 B::f（签名一致时）——编译器为 B 的 vtable 生成 thunk（调整 this 再跳转）的桥接函数
  • 析构顺序：与构造相反——自身 → 基类按声明逆序（先 B 后 A）
  • virtual 析构只在第一个基类声明就够吗？不——任何"可能被基类指针 delete" 的基类都必须有虚析构，否则 delete 经该基类指针 = UB

和 C 的区别 / 新手要点

C C++
结构体嵌套模拟"继承"，强转全靠布局巧合 真正的 MI + 编译器管理的 this 调整
无接口概念，函数指针表手搓 纯虚基类 = 接口，vtable 自动生成
无 虚继承/虚基表（C 完全没有对应物）

新手要点：① 默认单继承；需要"既是 A 又是 B"时先问"第二个能不能是接口"； ② 菱形出现一律虚继承 or 重构；③ 永远不用 C 强转跨 MI 类型。

HFT 关联

  • 热路径避免虚继承：虚基成员访问多一次指针间接（潜在 cache miss）， 延迟敏感的行情/订单对象坚持单链布局（→ M3 对象模型 ch03 虚继承布局详解）
  • 接口 MI 是策略框架的骨架：Strategy : MdSink, OrderGateway—— 一个策略类同时被行情驱动和下单回调驱动，两个接口都是纯虚无数据
  • this 调整意味着 回调注册时传的 this 必须按接口类型 cast 好—— C 回调风格（void*）配 MI 是经典 crash 源（→ 18.4 RTTI / M3 对象模型）

代码自测

题目 1： C 继承 A、B（均有虚函数），sizeof(C) 至少是多少（x86_64，int=4）？

参考答案

A、B 各带一个 vptr：8 + 8；A::a、B::b、C::c 三个 int：12。 合计 ≥ 8+8+12 = 28，对齐到 8 → 32 字节。 （若 A、B 无虚函数则无 vptr，就是本节的 12。）

题目 2： 下面为什么崩？

struct A { virtual ~A(){} }; struct B { virtual ~B(){} };
struct C : A, B {};
C* c = new C;
B* b = c;
delete (C*)(void*)b;     // 经 void* 来回强转
参考答案

b 指向 C 对象内的 B 子对象（地址偏移 ≠ 对象开头，见 ① 实测）。 经 void* 强转回 C* 时不会做偏移调整——delete 的地址不是对象首地址： 释放错误地址 + 析构用错 this，UB（实测大概率崩或堆损坏）。 正解：C* c2 = static_cast<C*>(b);（编译器自动减偏移）再 delete，或直接 delete c;。

题目 3： 虚继承里 F 的构造列表写 F() : D(), E(), A(42) {}，D 的构造列表里 也写了 A(1)——最终 A 用哪个值构造？

参考答案

42。虚基类由最派生类（F）直接构造；D、E 构造列表中对 A 的实参被忽略 （非最派生时 D 单独构造才会用它自己的 A(1)）。这就是"初始化责任跳级"—— 阅读虚继承体系时，虚基的初始化只看最派生类。

18.4

运行时类型识别 RTTI

本节讲什么

RTTI（Run-Time Type Identification）让你在运行时问一个多态对象"你到底是什么类型"： dynamic_cast（安全向下转型）和 typeid（类型信息）。本节讲清两者的行为差异、 实现机制（vtable 里的 type_info）、开销，以及"需要 RTTI 往往是设计信号"的工程判断。 代码均经本机 g++ 13.3 / -std=c++17 实测（2026-10-07）。

① dynamic_cast：指针版 vs 引用版（实测）

struct Base { virtual ~Base() {} };
struct Derived : Base { void special() { std::cout << "special\n"; } };
struct Other : Base {};

Base* b1 = new Derived; Base* b2 = new Other;
if (auto* d = dynamic_cast<Derived*>(b1)) d->special();      // ✅ special
dynamic_cast<Derived*>(b2);                                   // → nullptr（指针版失败）
dynamic_cast<Derived&>(*b2);                                  // → 抛 std::bad_cast（引用版）

本机实测输出：

special
b2 转 Derived*: nullptr          ← 指针版失败 = 返回空
引用版失败: bad_cast             ← 引用版失败 = 抛异常（引用不能为"空"）

使用纪律： - 前提：类型必须多态（有虚函数）——非多态类型用 dynamic_cast 是编译错误 - 指针版适合"试探"（if (auto* d = dynamic_cast<...>)），引用版适合"必须成功"（失败即 bug） - 向上转（派生→基类）永远成功且编译期就处理，dynamic_cast 的价值只在向下/横向（MI 交叉转换）

② typeid：动态类型 vs 静态类型（实测）

typeid(*b1) == typeid(Derived)    // 1 ← 多态对象：运行时动态类型
typeid(b1)  == typeid(Base*)      // 1 ← 指针本身：编译期静态类型（不发生解引用！）
typeid(i).name()                  // "i" ← 非多态：纯编译期求值

关键区分：

表达式 求值时机 结果
typeid(*多态指针) 运行时（解引用发生） 对象动态类型
typeid(指针) / typeid(非多态对象) 编译期 静态类型
typeid(类型名) 编译期 该类型本身
  • typeid 返回 const std::type_info&，用途是比较（==/!=）和调试打印 （.name() 是实现相关的 mangled 名，不可移植）
  • 想要可移植的类型名：typeid(T).name() 只用于日志，逻辑分支用 dynamic_cast 或下面的更好方案

③ 实现机制与开销

  • 多态类的 vtable 里除了虚函数指针，还存一个指向 type_info 的指针； dynamic_cast 沿继承链做运行时类型遍历（单继承快，MI/虚继承要查虚基表更慢）
  • typeid(*p) 就是解引用 vptr 读 type_info 指针——O(1)，很便宜
  • dynamic_cast 不是 O(1)：继承链越深越慢，且带一次潜在 cache miss—— 热路径循环里做 dynamic_cast 是性能反模式

④ "需要 RTTI" 常常是设计信号

优先考虑这三个替代方案，RTTI 留作最后手段：

需求 首选 次选
按类型分发行为 虚函数（把行为放进类里） std::variant + std::visit（类型集合封闭时）
从基类容器取特定派生 重新设计接口 dynamic_cast 一次转型后缓存结果
类型安全的异构容器 std::any / variant typeid 做键（std::type_index）

教科书级的坏味道：一长串 if (dynamic_cast<A*>(p)) ... else if (dynamic_cast<B*>(p)) ... ——这是在用 RTTI 手搓虚函数分发，改成虚函数或 variant visitor。

⑤ -fno-rtti 与工程边界

  • GCC/Clang 支持 -fno-rtti：typeid/dynamic_cast 禁用，vtable 里不再生成 type_info—— 省一点二进制体积和每次 RTTI 查询成本；标准库的 typeid/dynamic_cast 同样不可用
  • 与 -fno-exceptions 常一起出现在热路径库编译选项里（→ 18.1 HFT 关联）； 注意 dynamic_cast 引用版依赖异常（bad_cast），关异常后引用版也编不过

和 C 的区别 / 新手要点

C C++
枚举 tag + union 手工判别类型 dynamic_cast/typeid 语言级支持
void* + 祈祷 类型安全的向下转型
无 type_info/vtable 联动（C 没有 vtable）

新手要点：① 先想"能不能用虚函数"再问"怎么转"；② typeid(*p) 才是动态类型， typeid(p) 永远是静态指针类型（高频错题）；③ 引用版失败抛 bad_cast 不是返回空。

HFT 关联

  • 行情解码不用 RTTI：协议消息类型判别用协议头里的 msg_type 字段 + switch （查表 O(1)、分支可预测），比 dynamic_cast 的继承链遍历快一个量级且确定
  • 策略/订单对象若需要异构存储，std::variant<LimitOrder, IcebergOrder, ...> + visit 是编译期分发，无 vtable 跳转——现代 HFT C++ 的主流写法（→ M5 C++17 ch17 variant）
  • -fno-rtti 在部分团队的热路径库是默认选项；代价是失去 dynamic_cast 的调试便利， 折中：热路径库关 RTTI，外围工具链保留

题目 2： 为什么 -fno-exceptions 不能"整个仓库一刀切"？

章节自测

Q1异常安全与 RAII
void process() {
    std::vector<int> v(1000);
    std::ifstream f("data.txt");
    // ... 处理 ...
    throw std::runtime_error("error");
    // v 和 f 会泄漏吗？
}

throw 后 v 和 f 会泄漏吗？为什么？

答案与复习指引

不会泄漏。 异常抛出后栈展开（stack unwinding）——所有局部对象的析构函数自动调用。v 的析构释放内存，f 的析构关闭文件。这就是 RAII 的核心优势。

和 C 的区别： C 的 longjmp 不调用析构函数（C 也没有析构），跳转路径上的资源全泄漏。C++ 异常保证栈展开时 RAII 对象自动清理。

教训： 用 RAII 管理资源（智能指针/容器/文件流），异常安全自然得到。

Q4多重继承
class A { public: int a; };
class B { public: int b; };
class C : public A, public B { public: int c; };
C obj;
obj.a = 1; obj.b = 2; obj.c = 3;
// sizeof(C) 是多少（假设 int=4）？

sizeof(C) 是多少？多重继承的布局是什么？

答案与复习指引

sizeof(C) = 12（三个 int，通常无 padding）

布局： C 对象内存中依次排列 A 子对象（int a）、B 子对象（int b）、C 自身成员（int c）。

多重继承的代价： 1. 如果 A/B 有虚函数，各有自己的 vptr → 对象更大 2. 基类指针转换需要 this 调整：B *pb = &obj; 的 pb 不指向 obj 开头，而是指向 B 子对象的位置 3. 菱形继承（A→B, A→C, D:B,C）导致 A 的数据存两份——用虚继承解决
