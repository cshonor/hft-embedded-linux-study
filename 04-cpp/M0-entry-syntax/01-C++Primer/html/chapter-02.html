导读

数据类型是程序的基础。本章讲述 C++ 的基本内置类型、复合类型、常量限定符、类型推断机制，并初步介绍如何自定义数据结构。

章节摘要

C++ 的基本内置类型（int/double/char/bool）、变量初始化规则、复合类型（引用 & 和指针 *）、const 限定符与 constexpr、类型别名（using/typedef）以及自定义数据结构。

和 C 的区别

C C++
无引用类型，全靠指针 有引用 &（别名，不可空）
const 默认外部链接 const 默认内部链接（类似 C 的 static）

2.1

基本内置类型

本节讲什么

介绍 C++ 定义的算术类型（包括字符、整型数、布尔值和浮点数）以及空类型（void）。详细讲解字面值常量（literal）：十进制、八进制、十六进制的整型字面值，以及字符和字符串字面值等。

要点

  • 算术类型：char、int、long、bool、float、double 等，不同机器上大小可能不同
  • void：不对应具体对象，常用于函数无返回值或通用指针
  • 整型字面值：十进制 42；八进制 042（前缀 0）；十六进制 0x2A（前缀 0x/0X）
  • 浮点字面值：不带后缀默认是 double（如 3.14 → 8 字节）；3.14f / 3.14F → float；3.14L / 3.14l → long double
  • 字符字面值：'a'；字符串字面值："hello"（实际含末尾 \0）
  • 转义序列：\n、\t、\\、\" 等
  • 类型大小因平台而异：C++ 标准只规定各类型的最小取值范围，没有强制字节数；不同硬件架构、编译器下同一类型可能占不同字节

为什么同一类型在不同机器上大小不一样？

根本原因是硬件架构和编译器/ABI 规则不同。标准保证「至少能表示多大范围」，具体占几字节由实现决定。

类型 常见情况 注意
int 32 位系统通常 4 字节 16 位旧系统可能是 2 字节
long Windows 32/64 位通常都是 4 字节 Linux 64 位上通常是 8 字节
long long 一般 8 字节 跨平台相对更统一
bool 通常 1 字节 个别嵌入式平台可能自定义
float / double 通常 4 / 8 字节 相对固定，嵌入式也可能有差异
char 通常 1 字节 —

大小变了，最大值也会变吗？

会。 类型占的字节数变了，能表示的最大值、最小值通常也跟着变（浮点还有精度范围问题）。

类型 平台差异 最大值量级（有符号，约）
int 4 字节（常见） 约 ±21 亿（2³¹−1）
int 2 字节（旧 16 位机） 约 ±32767
long Windows 32/64 位，4 字节 与 32 位 int 同级
long Linux 64 位，8 字节 约 ±9×10¹⁸
float / double 大小相对固定 最大值、精度仍用 numeric_limits 查本机

同一行代码换机器，溢出行为可能不同：

int x = 2147483647;  // 在 4 字节 int 上是最大值
x + 1;               // 溢出 → 未定义行为（别依赖）

// 本机到底多大？运行时查：
std::numeric_limits<int>::max();
std::numeric_limits<long>::max();

所以 HFT 里用 int32_t / uint64_t：大小和最值在 typedef 语义下可预期；再配合 static_assert 和 numeric_limits 做范围校验。

跨平台开发时：不要假设 int、long 的字节数和最大值；需要固定宽度时用 <cstdint> 里的定宽类型。

和 C 的区别（类型大小问题）

内置类型是 C 和 C++ 最像的部分，但有几个关键差异：

对比点 C C++
基本类型 int/long/double 等 一样，大小同样因平台而异
bool C89 无（用 int），C99 有 _Bool/<stdbool.h> 一直是内置类型
定宽类型 <stdint.h> 的 int32_t 等 <cstdint> 的 int32_t 等（同源）
numeric_limits 用 <limits.h> 的 INT_MAX 宏 用 <limits> 的 std::numeric_limits<T>::max()
列表初始化 无 int x{}; 零初始化（C++11）

给 C 程序员的关键提醒： 1. int/long 大小不确定是 C 和 C++ 共同的坑，不是 C++ 独有。HFT 里都用 int32_t/int64_t 锁死宽度。 2. C++ 的 std::numeric_limits<T>::max() 替代 C 的 INT_MAX 宏——类型安全，不用记宏名。 3. bool 在 C++ 是一等公民，C99 才通过 <stdbool.h> 引入，老 C 代码用 int 当布尔。

/* C 写法 */
#include <limits.h>
#include <stdint.h>
int max = INT_MAX;              /* 宏 */
int32_t x = 42;                 /* 定宽 */

/* C++ 写法 */
#include <limits>
#include <cstdint>
int max = std::numeric_limits<int>::max();  // 类型安全
int32_t x = 42;                             // 同样可用

浮点字面值：默认是 double 还是 float？

不带后缀的浮点字面量默认就是 double。

写法 类型 常见大小
3.14 double 通常 8 字节
3.14f 或 3.14F float 通常 4 字节
3.14L 或 3.14l long double 平台相关 
float  price = 3.14;    // ⚠️ 3.14 是 double，赋给 float 可能精度损失，编译器常警告
float  price_ok = 3.14f;  // ✅ 明确 float 字面量
double fee = 5.5;       // 5.5 默认就是 double

HFT 里若变量是 float，字面量记得加 f 后缀，避免隐式从 double 窄化到 float 的警告或意外精度问题。

字符串与 '\0'（空字符）

双引号字符串 "..." 里，末尾的 '\0' 是编译器自动加的，一般不用手写。

"abc"   // 内存里实际是：'a' 'b' 'c' '\0'  共 4 字节
写法 内存里实际存什么 cout 打印
"abc" 'a' 'b' 'c' '\0'（末尾自动加） abc
"abc\0def" 'a' 'b' 'c' '\0' 'd' 'e' 'f' '\0' abc（中间 \0 被当成结束符）
"abc\\0def" 'a' 'b' 'c' '\\' '0' 'd' 'e' 'f' '\0' abc\0def（\ 和 0 是两个普通字符）
'\0'（单引号） 一个空字符 不可见

关键区分：

  • \0（一个反斜杠）：是转义，表示一个空字符（ASCII 0），会截断 C 风格字符串的「可读长度」。
  • \\0（两个反斜杠）：\\ → 一个真正的 \，后面 0 是普通字符 '0'。这才是「不想转义，就要字面量反斜杠 + 数字 0」。
"abc\0def"   // 转义：中间有一个空字符 → 打印 abc
"abc\\0def"  // 不转义成空字符：存 abc + \ + 0 + def → 打印 abc\0def
"c:\\0file"  // 若误写成 "c:\0file"，\0 会截断成 "c:"，后面丢失！
             // 路径应写 "c:\\0file" 或避免歧义

两种典型坑：

  1. 想存普通 \ 和 0，却写了 \0 → 编译器当成空字符，字符串被截断（如 "c:\0file" 只剩 "c:"）。
  2. 二进制数据里本身含 0 字节 → 不能用 strlen、strcmp（它们遇到 \0 就停）。HFT 网络字节流要用 memcpy / memcmp + 显式长度，或 std::string / vector<uint8_t>。
#include <iostream>
int main() {
    const char *s1 = "abc";
    const char *s2 = "abc\0def";   // 转义 \0
    const char *s3 = "abc\\0def";  // 字面量 \ 和 0

    std::cout << s1 << std::endl;  // abc
    std::cout << s2 << std::endl;  // abc（遇 \0 截断）
    std::cout << s3 << std::endl;  // abc\0def
    std::cout << s2[4];           // d（s2 内存里仍有 def，但 cout 看不到）

    char c = '\0';
    return 0;
}

记法：双引号是「字符串」，编译器帮你收尾 '\0'；单引号是「一个字符」，'\0' 就是那个值为 0 的字符。要字面量 \+0 写 \\0，不是 \0。HFT / 二进制协议里别用依赖 \0 结尾的 C 字符串函数处理原始字节。

转义字符是什么？

转义字符 = 反斜杠 \ + 一个普通字符，用来表示看不见或和语法冲突的字符。源码里没法直接敲换行写进字符串，就用 \n 代替。

写法 含义 干嘛用
\n 换行 cout << "a\nb" 打印两行
\t 制表符（Tab） 对齐文本
\\ 一个真正的 \ 路径 "C:\\test"，否则 \t 会被当成 Tab
\" 双引号本身 字符串里包含 "
\' 单引号本身 字符/字符串里包含 '
\0 空字符（ASCII 0） 见上一节
\x1A 十六进制字节值 表示任意 0–255 的字节，如协议里的控制符

转义字符通常写在哪？

场景 写法 例子
字符串字面量（最常见） 双引号 "..." "line1\nline2"、"C:\\data"、JSON 里的 \"
字符字面量 单引号 '...' char c = '\n';、char eof = '\x1A';
源码里写死的字节 字符/字符串里 "\x00\xFF" 表示两个原始字节（仍是字面量，不是运行时二进制）

大部分日常用法确实在字符串字面量里（日志换行、路径、带引号的文本）。单引号里同样可以用转义，表示一个特殊字符。

std::cout << "第一行\n第二行\t对齐" << std::endl;
std::cout << "路径: C:\\Users\\test" << std::endl;

char newline = '\n';       // 字符字面量里的转义
char ctrl    = '\x1A';     // 十六进制转义，值为 0x1A 的一个字节

和 \0 的关系：\n、\t、\xNN 都是转义序列；\0 表示空字符。双引号、单引号里都能用（单引号一般只包一个字符）。

HFT 注意：转义是写源码时的记号；线上收到的二进制字节流是原始数据，别和源码里的 \n 混为一谈。处理网络包用 memcpy/memcmp + 长度，不靠字符串转义规则。

开发阶段怎么「掐死」类型不符合预期？

1. sizeof + static_assert（编译期检查）

sizeof(T) 在编译期可知（对大多数类型）。配合 static_assert（C++11），可以在编译阶段就报错，而不是等到运行时才发现：

#include <cstdint>

// 本项目假定 long 为 8 字节；不符合则编译直接失败
static_assert(sizeof(long) == 8, "本项目要求 long 为 8 字节");

// 定宽类型更可预期
static_assert(sizeof(int64_t) == 8, "int64_t 必须为 8 字节");

HFT / 嵌入式项目里常在头文件或公共配置里写这类断言，避免换平台后静默出错。

2. std::numeric_limits（查类型能表示的范围）

<limits> 里的 std::numeric_limits<T> 可获取当前环境下类型的极值，例如：

#include <limits>
#include <iostream>

int main() {
    std::cout << "long max: " << std::numeric_limits<long>::max() << std::endl;
    std::cout << "long min: " << std::numeric_limits<long>::min() << std::endl;

    constexpr long kMaxRpm = 50000;  // 业务：电机转速上限
    static_assert(kMaxRpm <= std::numeric_limits<long>::max(),
                  "long 装不下所需转速范围，请改用 int64_t");
    return 0;
}

业务用法（无人机电机转速）：先查 numeric_limits 看当前类型能否承载所需范围；不够就换成 int64_t 等定宽类型，再配合 static_assert(sizeof(int64_t) == 8) 锁定布局。

手段 时机 作用
sizeof + static_assert 编译期 字节数不对 → 直接编译失败
numeric_limits<T>::max/min 编译期或运行时 判断取值范围是否够用
int32_t / int64_t 设计时 跨平台固定宽度，协议/HFT 常用

示例

#include <iostream>
#include <limits>
int main() {
    int dec = 42;
    int oct = 052;       // 八进制，值为 42
    int hex = 0x2A;      // 十六进制，值为 42

    double pi = 3.14;        // 字面量 3.14 默认是 double
    float  ratio = 0.5f;     // 明确 float 用 f 后缀

    bool flag = true;
    char ch = 'A';
    const char *msg = "hello";

    std::cout << dec << " " << oct << " " << hex << std::endl;
    std::cout << pi << " " << flag << " " << ch << " " << msg << std::endl;

    // 查看本机各类型占多少字节（结果因平台而异）
    std::cout << "sizeof(int)=" << sizeof(int)
              << " sizeof(long)=" << sizeof(long)
              << " sizeof(double)=" << sizeof(double) << std::endl;

    std::cout << "long max=" << std::numeric_limits<long>::max() << std::endl;

    return 0;
}

常见错误

1. float price = 3.14; 隐式窄化 3.14 默认是 double（8 字节），赋给 float（4 字节）会精度损失，编译器常警告。写 3.14f 明确 float。

2. 八进制陷阱

int x = 010;   // 不是 10！是八进制，值为 8

前缀 0 是八进制标记。C 程序员常在日期/时间编码上踩这个坑。现代 C++ 建议用 0b 二进制或十六进制减少歧义。

3. 有符号溢出是 UB

int x = INT_MAX;
x + 1;   // 有符号溢出 = 未定义行为，别依赖"回绕"

无符号溢出有定义（回绕），有符号溢出是 UB。HFT 里涉及大数累加要提前用 int64_t。

本节讲什么

2.1 基本内置类型 里只有一行「字符字面值 'a'；字符串字面值 "hello"」，没往下拆。这一节把它拆到底，并回答一个 C/C++ 混编项目里绕不开的问题：

char c = 'x'; sizeof(c) 和 sizeof('x') 在 C++ 里各是多少？在 C 里呢？

一句话结论（三层递进，本节最重要的一张图）：

层次 C C++ 是否相同
变量层 char c 1 字节，符号性实现定义 1 字节，符号性实现定义 ✅ 完全一致
字面量层 'x' 类型 int，sizeof = 4 类型 char，sizeof = 1 ❌ 唯一核心差异
表达式层 'x' + 'x' int，sizeof = 4 提升为 int，sizeof = 4 ✅ 殊途同归

差异只存在于孤立的字符字面量的静态类型；一旦进表达式，两边都被整数提升（integral promotion）拉回 int。

⚠️ 但有一个必须记住的例外：cout << c 不触发提升（见 §8）。C 的 printf 是无条件提升 + 格式符反推，C++ 的 cout 是不提升 + 重载决议正推——两套完全不同的机制，别把 C 的直觉套过来。

要点

0. 先把两件事分开：变量类型 ≠ 字面量类型

char c = 'x';
sizeof(c);    // 1 —— c 的类型由「声明」决定
sizeof('x');  // 1 (C++) / 4 (C) —— 'x' 的类型由「语言标准」决定
  • 变量类型是静态属性，声明那一刻就定了；
  • 字面量类型由标准规定，和它被赋给什么变量无关；
  • 整数提升是表达式求值时的临时转换，求值完就消失，不改变变量自己的类型。

所以「c 参与运算会变成 int」这句话的严格说法是：c 参与运算时用的是一个提升后的 int 临时值，c 本身仍是 char（sizeof(c) 依旧 1）。

1. 第一层：变量层 —— C/C++ 完全相同

char c;              /* 1 字节 */
signed char sc;      /* 1 字节，明确有符号：-128..127 */
unsigned char uc;    /* 1 字节，明确无符号：0..255 */

三者是三种不同的类型（重载决议会区分），但 char 的符号性由 ABI/编译器决定，标准不保证：

平台 ABI char 符号性
x86-64 Linux (gcc/clang) SysV signed
arm64 macOS（本机实测） Apple ARM64 signed
aarch64 Linux (gcc) AAPCS64 unsigned
ARM32 (gcc) AAPCS unsigned

实测印证（本机）：printf("%s", (char)-1 < 0 ? "signed" : "unsigned") → signed。

端口性铁律：需要字节数值时一律写 uint8_t / int8_t，裸 char 只用来装字符。aarch64 Linux 上 char 是无符号这条，和本机结论相反——这正是跨平台 bug 的温床，详见《C和指针》3.1.5 字符的符号性陷阱。

符号性可以被编译选项直接翻转（这也是"由编译器决定、不由 CPU 指令集决定"的直接证据）：

clang++ -std=c++17 -funsigned-char a.cpp    # char 变 unsigned
clang++ -std=c++17 -fsigned-char   a.cpp    # char 变 signed（本机默认即此项）

实测（同一份代码，只改选项）：

选项 std::is_signed<char> (int)(char)0xFF

-funsigned-char unsigned 255

注意 signed char / unsigned char 不受这两个选项影响——只有裸 char 被翻转。

向更大整型赋值时的扩展规则（实测）：

signed char / signed char 0xFF 符号扩展，高位填符号位 -1（0xFFFFFFFF）

两者只差在高位填什么。字节最高位为 0（ASCII 0~127）时两种扩展结果相同，所以纯 ASCII 场景看不出差别；一旦字节 ≥ 0x80，(int)c 到底是 128 还是 -128 就取决于符号性——这是拿 char 当数组下标（tbl[c]）这类查表代码在 aarch64 上越界的经典根因。

2. 第二层：字面量层 —— 唯一的核心差异

C 标准（C11 §6.4.4.4 / C23 §6.4.4.5）：

An integer character constant has type int.

C++ 标准（[lex.ccon]）：

A character-literal that does not have a u8、u、U、L prefix has type char.

为什么 C 这么设计？ 历史包袱：C 诞生于 PDP-11，寄存器 16 位、无单字节算术指令，字符常量天生要参与算术（'A' + 1），直接给 int 省掉一次截断。

为什么 C++ 改了？ C++ 有函数重载和模板推导，字面量类型必须与类型系统自洽：

void f(int);
void f(char);
f('A');    // C++: 调用 f(char)，精确匹配
           // 若 'A' 是 int（C 规则），只能调 f(int)

auto a = 'x';   // C++: a 是 char
sizeof(a);      // 实测 = 1

实测的类型判定表（std::is_same + 特化 tname<T>()，非 sizeof 推断）：

u8'x' char char8_t ← C++20 断裂点

3. 第三层：表达式层 —— 两边殊途同归

这是最容易被忽略的一层，也是「sizeof('x') 有差异」这条知识的边界：

sizeof('x');       /* C: 4   C++: 1 */
sizeof('x' + 'x'); /* C: 4   C++: 4  ← 一样了！ */

实测两档 C++ 标准下 sizeof('x' + 'x') 均为 4。原因：char 作为算术运算符操作数时被提升为 int，两个 int 相加结果仍是 int。

所以：C/C++ 的差异只在孤立字面量的静态类型上，一旦参与运算，char 就"膨胀"回 int。这一点在 C 侧同理——'A' 本来就是 int，无需提升。

6. 字符串字面量的两种形态：数组 vs 指针

前面几节（§1–§5）讲的是字符字面量（单引号），这一节讲字符串字面量（双引号）的两种落地形态——这是 C/C++ 共有的、也是初学者最先撞上的一组对立：

char buf[] = "hello";   // 形态 A：数组 —— 拷贝一份，可写
char *p    = "hello";   // 形态 B：指针 —— 指向只读段，不可写
维度 形态 A char buf[] = "hello" 形态 B char *p = "hello"

⚠️ "栈上"这个说法只对一半：char buf[] = "hello" 写在函数里才是栈；写成 static char buf[] 或放在文件作用域，它在 .data 段（可写），由加载器填充，同样可写，但不是栈。上面实测的 g_arr 就在 .data，g_arr[0]='H' 实测成功输出 Hello。

C 与 C++ 在这里又分道扬镳

这是比"能不能改"更根本的差异——字符串字面量的静态类型：

语言 "hello" 的类型 char *p = "hello";
C（C89→C23 全版本） char[6]（没有 const） ✅ 合法，-Wall 下零警告
C++（C++03 起） const char[6] ❌ ill-formed

实测：

$ clang   -std=c11 -Wall          t.c    # C：无警告，静默埋雷
$ clang   -std=c11 -Wwrite-strings t.c   # warning: initializing 'char *' with an
                                         # expression of type 'const char[6]' discards qualifiers
$ clang++ -std=c++17              t.cpp  # warning: ISO C++11 does not allow conversion
                                         # from string literal to 'char *' [-Wwritable-strings]
$ clang++ -std=c++17 -pedantic-errors t.cpp  # error: 同上

C++ 从类型系统层面直接把这条 UB 通道封死；C 为了向后兼容保留了 char * 赋值，所以工程上必须自觉写 const char *，并开 -Wwrite-strings。

修改只读段会发生什么（实测）

char *p = "hello";
p[0] = 'H';   /* UB */
环境 结果
macOS arm64（本机实测） SIGBUS(10)，echo $? = 138
Linux x86-64 / aarch64 通常 SIGSEGV(11)，$? = 139
裸机 MCU（常量在 Flash） 可能静默丢弃写入，也可能 HardFault

注意本机是 SIGBUS 不是 SIGSEGV——macOS arm64 对 __TEXT 段的写保护走的是 bus error。标准只保证"未定义行为"，不保证崩溃，所以别拿"跑起来没崩"当正确性的证据。

常量合并（实测）

char *s1 = "abc";
char *s2 = "abc";
printf("%d\n", s1 == s2);   /* 实测输出 1 —— 同一地址 */

编译器做字面量合并（-fmerge-constants，默认开），两个指针指向同一块只读内存。所以写 s1[0] 会连带改掉 s2。反过来，用 == 比较字符串内容永远是错的——比的是地址。

7. C++20 的 char8_t 断裂与迁移

这是 C++20 最痛的一处静默 breaking change，本机实测三个断点：

断点 1：赋值给 const char* 失败

#include <string>
const char *p = u8"x";
标准 结果
-std=c++17 ✅ 编译通过
-std=c++20 ❌ error: cannot initialize a variable of type 'const char *' with an lvalue of type 'const char8_t[2]'

断点 2：std::cout 输出 u8 串失败

std::cout << u8"hi";
标准 结果
-std=c++17 ✅ 编译通过
-std=c++20 ❌ error: overload resolution selected deleted operator '<<'
note: candidate function ... operator<<(basic_ostream<char, _Traits>&, const char8_t*) = delete

C++20 明确删除了 basic_ostream<char> << const char8_t* 重载——这是故意的，防止把 UTF-8 字节流当成执行字符集（如 GBK）打印。

断点 3：u8'x' 的类型从 char 变 char8_t（见 §2 类型表）

迁移写法：

// ① 正确姿势：用 u8 类型体系
std::u8string s = u8"你好";        // C++20 新增

// ② 与只吃 char 的老 API（send/write/fwrite）对接：字节级重解释
const char8_t *u8s = u8"x";
const char *bytes = reinterpret_cast<const char *>(u8s);
write(fd, bytes, 2);               // char* 允许别名访问任何对象，读取安全

// ③ 打印：转回 char 再输出，或用 std::u8string 逐字节
std::cout << reinterpret_cast<const char *>(u8"x");

char8_t 与 unsigned char 大小、对齐、符号性相同但是不同类型——reinterpret_cast 读取字节是安全的（C++ 的 char/unsigned char 别名豁免），但写入和 memcpy 之外的用法要谨慎。

8. cout 输出字符还是数字：由重载决议决定，不是整数提升

这是 C++ 与 C 在"输出"上最本质的分歧，也是最容易讲错的一处。

⚠️ 常见误解：「short 没有专属 operator<< 重载，所以被提升成 int 才输出数字 65。」 错。 basic_ostream 有 operator<<(short) 成员重载，是精确匹配，压根没有发生提升。 输出数字是因为 short 是整数类型、走的是数字插入器，跟提不提升无关。

标准库其实是两套插入器（本机 libc++ <ostream> 实测）：

类别 位置 形参 输出行为
数字插入器 basic_ostream 成员 bool short unsigned short int unsigned long long long float double long double const void* streambuf* nullptr_t 走 num_put，输出数字
字符插入器 非成员（ADL 找到） char signed char unsigned char 走 streambuf，输出字符
字符串插入器 非成员 const char* const signed char* const unsigned char* 输出字符串

关键细节：成员里没有 char / signed char / unsigned char。这就是为什么 cout << c 一定会去选非成员的那个字符插入器。

四条实测（clang++ 23.1.0 / libc++）：

char          c  = 'A';
short         s  = 65;
unsigned char uc = 65;
uint8_t       u8 = 65;          // == unsigned char

cout << c;    // A    非成员 operator<<(ostream&, char)        —— Identity 精确匹配
cout << s;    // 65   成员   basic_ostream::operator<<(short)  —— Identity 精确匹配，无提升
cout << +c;   // 65   +c 的类型已是 int（一元 + 真触发提升）→ 成员 operator<<(int)
cout << uc;   // A    非成员 operator<<(ostream&, unsigned char)
cout << u8;   // A    uint8_t 就是 unsigned char —— 同一条路

决定性反证：如果「提升成 int 就输出数字」这条机制成立，那 unsigned char 也会被提升成 int、也该输出 65。但实测输出 A。所以——输出形态取决于选中哪个插入器，与是否提升无关。

怎么在不背头文件的前提下证明 operator<<(short) 存在：

// ① 歧义法：只有当库里已有一个精确匹配的 short 重载时，才会二义
std::ostream& operator<<(std::ostream& os, short v) { return os; }
std::cout << s;
// error: use of overloaded operator '<<' is ambiguous
//        (with operand types 'ostream' and 'short')

// ② 成员调用法：成员语法只对成员函数有效
std::cout.operator<<(s);   // ✅ 编译通过 → short 重载是成员

顺带一个推论：正因为成员里没有 char，如果真只剩成员可用，cout << c 会陷入 char→short 与 char→int 两条同为 Promotion 等级的转换而二义。字符插入器正是为此而存在的。

⚠️ HFT / 工程第一大坑：uint8_t 打印出来是字符

uint8_t = unsigned char，int8_t = signed char——两者都有字符插入器。

uint8_t seq = 65;
std::cout << "seq=" << seq << "\n";   // seq=A   ← 日志里是 ASCII 字符，不是序号

修法三选一（都是先让它变成 int）：

std::cout << +seq;                    // 一元 +，最简洁
std::cout << unsigned(seq);
std::cout << static_cast<int>(seq);

C++20 又补了一刀：char8_t/char16_t/char32_t/wchar_t 的插入器被 = delete

代码 C++17 C++20
cout << u'A'（char16_t） ✅ ❌ deleted
cout << U'汉'（char32_t） ✅ ❌ deleted
cout << L'A'（wchar_t） ✅ 输出数字 65 ❌ deleted

实测报错是 overload resolution selected deleted operator '<<'——注意它是先选中、再发现被删除，不是"找不到重载"。这是 C++20 有意为之：禁止把宽字符/UTF 字符隐式窄化成执行字符集打印。

和 printf 的对照（这一节真正的重点）：

printf cout
机制 可变参数，默认实参提升无条件发生 函数重载，不提升，按类型精确匹配
谁决定输出形态 格式符 %c / %d 选中「字符插入器」还是「数字插入器」
char 传进去 一定先变成 int 不变，以 char 身份匹配字符插入器
类型写错的后果 运行期 UB / 乱码 编译期报错（或选错重载）

一句话收口：C 是"一定先提升，再靠格式符反推"；C++ 是"根本不提升，靠重载正推"。

常见陷阱

陷阱 1：sizeof('A') 当数组长度（C/C++ 混编头文件）

#ifdef __cplusplus
static_assert(sizeof('A') == 1, "C++: char");
#else
_Static_assert(sizeof('A') == sizeof(int), "C: int");
#endif

同一个头文件被 C 和 C++ 分别编译时，sizeof('A') 是两个不同的值。混编项目（如 C++ 包装 DPDK/内核头文件）里，绝不能用它做数组长度、static_assert 之外的任何编译期常量。

陷阱 2：以为 sizeof('x') == 1 意味着 'x' + 'x' 也是 1 字节

反直觉但实测为 4。sizeof 作用于表达式时看的是表达式结果的类型，整数提升已经发生：

static_assert(sizeof('x') == 1);        // 孤立字面量
static_assert(sizeof('x' + 'x') == 4);  // 表达式 → int

陷阱 3：多字符常量的字节顺序（《C和指针》3.1.6 的 Q4 答案有误）

'AB'    // 实测 0x4142 = 16706
'xy'    // 实测 0x7879 = 30841
'RIFF'  // 实测 0x52494646

clang/gcc 的实现是第一个字符放在最高字节（value = c1<<24 | c2<<16 | c3<<8 | c4），不是"第一个字符在低字节"。

⚠️ 现存的《C和指针》3.1.6 自测题 Q4 写的是「'A' 在低字节 → 0x4241 = 16961」，与实测相反，正确值是 0x4142 = 16706。而且这个值本来就是实现定义，跨编译器不可移植——FourCC 码请改用 uint32_t + 显式字节拼接。

陷阱 4：'0' ≠ 0 ≠ '\0'（C/C++ 通用）

写法 值 含义
'0' 48 字符"零"
0 0 整数零
'\0' 0 空字符/字符串终止符

报文解析：val = val * 10 + (buf[i] - '0')，不要写 - 48（非 ASCII 平台 '0' 不一定是 48）。

陷阱 5：C++17 → C++20 升级后老代码突然编译失败

老代码里所有 const char *s = u8"..."、printf("%s", u8"...")、std::string s = u8"..." 在 C++20 全部报错。升级编译器时的排查清单：

# 先把所有断点一次性暴露出来
clang++ -std=c++20 -fsyntax-only $(git ls-files '*.cpp')
# 报错关键词：char8_t

陷阱 6：uint8_t 进日志变成乱码字符

uint8_t qty = 200;
LOG << "qty=" << qty;     // 输出 qty=È   ← 不是 200，是 codepage 200 对应的字符

uint8_t / int8_t 就是 unsigned char / signed char，命中字符插入器。行情字段、计数器、枚举只要声明成 uint8_t，cout 一律按字符打。

LOG << "qty=" << +qty;                    // ✅ 一元 + 提升到 int
LOG << "qty=" << static_cast<int>(qty);   // ✅ 显式

反过来看这也是个特征：cout << (unsigned short)65 输出 65，cout << (uint8_t)65 输出 A。 同是 1~2 字节整数，一个走数字插入器一个走字符插入器——差别只在有没有字符插入器精确匹配。

HFT / 嵌入式关联

  1. 报文魔数：C++ 里 'T' 是 char（1 字节），赋给 uint8_t 无需转换；C 里是 int，赋值发生窄化。同一份头文件在两种语言下告警行为不同——混编项目统一用 0x54U 这类显式数值更稳。

  2. 热路径字符串：std::string_view（16 字节，ptr+len）比 std::string（24 字节 + 可能堆分配）更适合行情字段的零拷贝切片。C 侧对应物是 char * + len——两种语言的"显式长度"模型是对齐的，都不依赖 '\0'。

  3. 二进制 payload 绝不当字符串：char8_t（C++20）在类型层面把「UTF-8 文本」和「裸字节」分开了，这比 C 的裸 char 更安全。但 payload 解析仍应该用 std::byte（C++17）或 uint8_t，见《C和指针》9.1 字符串基础 的"两种存储模型"。

  4. wchar_t 不可用于网络传输：macOS/Linux 4 字节、Windows 2 字节，序列化会跨端不一致。跨端一律 UTF-8（char8_t / char）+ 显式长度。

  5. locale 隔离：HFT 进程 std::setlocale(LC_ALL, "C")，避免 is* / tolower 受环境影响（C 侧同理，见《C和指针》9.8 字符操作）。

1. - C++：sizeof(c) = 1，sizeof('x') = 1（字符字面量类型是 char） - C：sizeof(c) = 1，sizeof('x') = 4（字符常量类型是 int）

变量层一致，字面量层不同。

2. 4。'x' 是 char，但作为 + 的操作数被整数提升为 int，两个 int 相加结果仍是 int。实测 c++17/c++20 两档均为 4——这也说明 C/C++ 的差异只在孤立字面量的静态类型上。

3. - C++20：u8'x' 是 char8_t，u8"x"[0] 是 const char8_t（元素类型 char8_t） - C++17：两者都是 char

4. 编译失败：error: cannot initialize a variable of type 'const char *' with an lvalue of type 'const char8_t[4]'。 修复：

const char8_t *p = u8"abc";                        // ① 改用 char8_t
std::u8string s  = u8"abc";                        // ② 用 u8string
const char *b = reinterpret_cast<const char *>(u8"abc");  // ③ 对接只吃 char 的老 API

5. 实测 0x52494646。第一个字符 'R'(0x52) 在最高字节：value = c1<<24 | c2<<16 | c3<<8 | c4。注意这是实现定义行为，跨编译器不可移植，FourCC 请用显式 uint32_t 拼接。

6. 因为 char 的符号性标准未规定：aarch64 Linux (gcc) 是 unsigned，x86-64 Linux 和 arm64 macOS 是 signed。同一个字节 0x80 在两边分别是 128 和 -128，if (c > 0) 结论相反。数值一律用 uint8_t / int8_t。

7. - sizeof(buf) = 6（数组，含 '\0'），sizeof(p) = 8（指针本身） - buf[0]='H' ✅ 合法，实测输出 Hello；p[0]='H' ❌ UB，实测 macOS arm64 收 SIGBUS（$?=138） - 放进 C++：char buf[] = "hello"; 完全没问题（数组初始化，拷贝）；char *p = "hello"; 是 ill-formed——C++ 里字面量类型是 const char[6]，clang 报 ISO C++11 does not allow conversion from string literal to 'char *'（-pedantic-errors 下变 error）。必须写 const char *p。

8. 输出 A 65 A A。

cout << s 输出数字不是因为整数提升——这是最常见的错答。basic_ostream 有成员 operator<<(short)，short 是精确匹配（Identity），压根没提升。输出数字是因为 short 命中了数字插入器（走 num_put）。

决定性反证：uc 和 u8 同样会被提升为 int，却输出 A——它们命中了非成员字符插入器 operator<<(ostream&, unsigned char)。所以输出形态取决于选中哪个插入器，与提升无关。

  • c → 非成员字符插入器 operator<<(ostream&, char)，输出 A
  • s → 成员数字插入器 operator<<(short)，输出 65
  • uc / u8（uint8_t == unsigned char）→ 非成员字符插入器，输出 A

顺带：想让它们都输出数字，统一写 +x（一元 + 真触发提升，sizeof(+c)=4）。

9. qty 是 uint8_t（或 int8_t / unsigned char / signed char）——它们命中字符插入器，200 被当成字符码点打印。

LOG << "qty=" << +qty;                    // ① 一元 + 提升到 int
LOG << "qty=" << static_cast<int>(qty);   // ② 显式转换
LOG << "qty=" << unsigned(qty);           // ③ unsigned() 同样可以

2.2

.1 标识符与未初始化

本节讲什么

命名规则、局部内置变量 UB。

标识符命名规则

标识符 = 变量、函数、类型等的名字。编译器强制校验，违反直接报错。

硬性规则（标准规定）

  1. 允许字符：仅 a–z、A–Z、0–9、下划线 _
  2. 首字符：只能是字母或 _，不能以数字开头
  3. 大小写敏感：num、Num、NUM 是三个不同名字
  4. 附加约束： - 不能与关键字重名（int、if、for、return 等） - 内部不能有空格、Tab、换行 - __ 开头、_ + 大写字母 等属于保留名，业务代码避免使用

合法 / 非法示例

// ✅ 合法
age  Age  _age  age123  student_score  MAX_NUM

// ❌ 非法
// 123age         数字开头
// student-score  含减号
// student score  含空格
// int            关键字
// $num           非法字符

大小写独立

int a = 10;
int A = 20;
std::cout << a << " " << A;   // 10 20，完全独立

工程命名习惯（非语法强制，提升可读性）

对象 常见风格 例子
局部变量、普通函数 小写 + 下划线 user_id、submit_order
宏 / 宏常量 全大写 MAX_LEN
C++ 类 / 结构体 大驼峰 StudentInfo、SalesItem
循环变量 单字母可接受 i、j、k

一句话：只能由字母、数字、下划线组成，首字符不能是数字，区分大小写，不能用关键字。

未初始化局部内置变量（UB）

C/C++ 标准（C11/C17 §6.7.9 等）对自动存储期（普通局部变量）与静态存储期（全局 / static 局部）规则不同：

存储期 例子 未显式初始化时 读取
自动（auto） 函数内 int a; 不确定值（栈上垃圾） ❌ 未定义行为（UB）
静态 全局 int a;、static int b; 零初始化（0 / 空指针） ✅ 安全

核心概念

  • 不确定值（indeterminate value）：内存里是栈残留数据，每次运行、每次调用可能不同
  • 未定义行为（UB）：标准不约束结果——可能随机输出、逻辑错乱、崩溃，或被编译器优化掉相关代码

内存原理（直观）

  • 栈上局部变量：只分配空间，不清零 → 可能是上次函数留下的垃圾
  • 全局 / static：在 .bss 等区域，加载时整块清零 → 默认为 0

代码对比

// ❌ UB：局部内置类型未初始化就读取
int main() {
    int a;
    std::cout << a;   // 未定义行为，可能随机数，高优化下 printf 可能被删
}

// ✅ 全局：自动零初始化
int g_a;
int main() {
    std::cout << g_a;  // 稳定输出 0
}

// ✅ static 局部：零初始化
void test() {
    static int b;
    std::cout << b;    // 0
}

// C++ 安全写法
int main() {
    int x;           // 栈局部，未初始化，读 x → UB
    int y{};         // 列表初始化，置 0，安全
    int *p = new int;     // 堆，未初始化，读 *p → UB
    int *q = new int{};   // 堆，零初始化
    delete p; delete q;
}

UB 的危险（不止「随机数字」）

  1. 偶现 bug，极难复现
  2. 编译器优化：对未初始化值的判断可能被当作永远 false/true
  3. 未初始化指针 → 野指针，段错误
  4. 栈残留敏感数据 → 潜在信息泄露（安全场景）

编译器检测

  • GCC/Clang：-Wall -Wextra 报 uninitialized；-Werror 当错误
  • MSVC：C4700；/SDL 可更严格
  • 静态分析：Clang Static Analyzer、Cppcheck

工程规范

int a = 0;
float f = 0.0f;
int *p = nullptr;

int a{};      // C++ 统一列表初始化，内置类型置零
double d{};
  1. 局部内置变量定义即初始化
  2. C++ 优先 int x{}; / int x{0};
  3. malloc 后不能直读，需 calloc 或手动清零
  4. 开警告，别让未初始化变量混进发布版

一句话：函数内普通局部内置变量不初始化 → 值不确定；读取 = UB。全局、static 局部会自动零初始化，读取安全。

和 C 的区别

未初始化局部变量的 UB 问题是 C 和 C++ 共同的坑，规则几乎完全一样。差异在于 C++ 提供了更安全的初始化手段：

对比点 C C++
局部未初始化 UB（栈垃圾） UB（一样）
全局/static 零初始化 ✅ ✅（一样）
列表初始化 int x{}; ❌ 没有 ✅ C++11，零初始化
检测工具 -Wuninitialized -Wuninitialized（一样）

给 C 程序员的关键提醒： C 里习惯写 int x = 0;，C++ 推荐用 int x{};——统一、能防止窄化（int x{3.14} 会编译报错，int x = 3.14 只警告）。标识符命名规则两边完全一致，C 的经验直接搬过来。

常见错误

1. 误以为局部变量默认 0

void f() {
    int count;          // 栈上垃圾值
    if (count > 0) {}   // UB，可能任意走分支
}

全局/static 才默认 0，局部内置类型不会。

2. 指针未初始化就解引用

int *p;        // 野指针
*p = 42;       // UB，可能段错误

C++ 用 nullptr 明确"空"：int *p = nullptr;，C 用 NULL。

自测题

1（选择） 下面哪个变量读取是安全的（不是 UB）？

int g;                    // 全局

    int a;                // 局部
    static int b;         // 静态局部
}
  • A. a 安全
  • B. b 安全
  • C. a 和 b 都安全

2（判断） C++ 中 int x{}; 和 int x = 0; 效果相同。

参考答案
  1. B。g（全局）和 b（static 局部）都零初始化，读取安全；a（普通局部）未初始化，读取是 UB。
  2. 对内置类型效果相同（都置 0）。但 int x{3.14} 会编译报错（列表初始化禁止窄化），int x = 3.14 只警告不报错——这是 {} 更安全的地方。

2.2

.2 变量、常量与 static

本节讲什么

变量 vs 常量、numeric_limits、static 三种用法。

变量 vs 常量

C++ 常按能不能改来区分：

变量 常量
能否修改 可以重新赋值 定义后不能改（或编译期就定死）
例子 int price = 100; price = 200; const int max = 10000;
关键字 （无特殊关键字） const、constexpr
字面值 — 100、"hello"、3.14 等直接写在代码里的常量 
int price = 100;              // 变量：可以改
price = 200;

const int max_orders = 10000;   // 常量：运行期不可改
// max_orders = 20000;          // 错误

constexpr int kMaxLatency = 50;   // 编译期常量，HFT 里常用作阈值、上限
  • const：值不可修改；常用于参数、引用绑定常量对象
  • constexpr：编译期就能确定的常量，编译器可做优化
  • 字面值常量：如 42、"abc"，嵌在表达式里，不是带名字的变量

怎么查类型的最大值？

不用自己算，用 <limits> 里的 std::numeric_limits（详见 2.1）：

#include <limits>
#include <iostream>

int main() {
    std::cout << "int max:  " << std::numeric_limits<int>::max() << std::endl;
    std::cout << "long max: " << std::numeric_limits<long>::max() << std::endl;
    return 0;
}

注意：max() 是当前机器、当前编译环境下该类型的最大值；换平台 int/long 大小变了，最大值也会变。

static 是什么？（多面手）

static 含义取决于写在哪：

1. 函数内的 static 变量

  • 只初始化一次，生命周期延续到整个程序结束
  • 下次进函数时保留上次的值
void submit_order() {
    static int order_count = 0;  // 只初始化一次
    ++order_count;               // 累计总下单次数，不会每次调用都归零
}

2. 全局 / 命名空间里的 static

  • 限制作用域为当前源文件（内部链接）
  • 其他 .cpp 看不到这个名字，避免多文件同名冲突
  • HFT 多文件项目里常用来隐藏本文件内部实现
// foo.cpp
static int internal_counter = 0;  // 仅 foo.cpp 可见
static void helper() { /* ... */ }

（现代 C++ 也常用匿名命名空间达到类似效果。）

3. 类里的 static 成员（预告）

  • 属于类本身，不属于某个对象；所有对象共享一份
  • 例：策略类里 static 的延迟阈值，所有实例共用
  • 详细见第 7 章「类的静态成员」
class Strategy {
public:
    static int max_latency_ms;  // 类级别，共享
};
位置 作用
函数内 只初始化一次，程序全程存活
文件作用域 仅本文件可见，隐藏实现
类内 所有对象共享的类级数据

和 C 的区别

static 三种用法里，前两种（函数内、文件作用域）C 和 C++ 完全一样；第三种（类内 static 成员）是 C++ 独有（C 没有 class）。关键差异在 const：

对比点 C C++
static 函数内 一样（只初始化一次） 一样
static 文件作用域 一样（内部链接） 一样
const 全局默认链接 外部链接（和普通全局一样） 内部链接（相当于隐式 static）
constexpr ❌ 没有 ✅ C++11，编译期常量

const 链接性的差异最坑： C 里 const int x = 10; 放头文件被多文件包含会重定义；C++ 里 const 全局默认内部链接，放头文件每个 .cpp 各有一份独立副本，不会重定义。所以 C++ 头文件常放 const 定义，C 不行。

// C++ 头文件可以直接写（每个 .cpp 独立副本，不冲突）
const int kMaxOrders = 10000;   // C++: 内部链接，安全

// C 头文件这样写会重定义，要改用宏或 extern
#define MAX_ORDERS 10000        // C 的做法

常见错误

1. 误以为 constexpr 和 const 完全一样 const 只说"运行期不可改"，值可能是运行时才算出来的；constexpr 要求"编译期就能确定"。HFT 阈值用 constexpr 能让编译器优化（常量折叠）。

2. 函数内 static 变量的线程安全误区 C++11 起，函数内 static 变量的初始化是线程安全的（魔法静态局部）。但初始化后的访问不保证线程安全——多线程读写同一个 static 变量仍需加锁。

自测题

1（选择） C++ 中 const int x = 10; 写在头文件里被多个 .cpp 包含，会怎样？ - A. 链接报错：重复定义 - B. 正常，每个 .cpp 各有一份独立副本 - C. 编译报错

2（判断） constexpr int x = 42; 和 const int x = 42; 完全等价。

3（概念） 函数内 static int count = 0; 的 count 什么时候销毁？

参考答案
  1. B。C++ 的 const 全局默认内部链接（相当于隐式 static），每个 .cpp 各有一份，不冲突。C 里这样写会重定义报错——这是 C/C++ 的关键差异。
  2. 不完全等价。constexpr 强制编译期确定，const 只保证运行期不可改（值可能运行时才算出）。constexpr int x = 42; 两层都满足；const int x = get_value(); 合法但 constexpr 不行。constexpr 是 const 的"加强版"。
  3. 程序结束时销毁（和全局变量一样）。函数返回时 count 不销毁，下次调用保留上次的值。

2.2

.3 变量遮蔽

本节讲什么

嵌套作用域、shadowing、:: 穿透。

变量遮蔽（Variable Shadowing）

变量遮蔽：在嵌套作用域（代码块、函数、循环）里，内层重新声明与外层同名的变量，内层名字会屏蔽外层同名变量；在内层范围内，所有对那个名字的引用只指向内层变量，外层同名变量暂时不能直接访问。

词法作用域查找链（由内向外）：

  1. 先在当前最内层找名字，找到就用
  2. 找不到再向外层回溯
  3. 内层一旦定义同名变量，查找在此终止，不会再匹配外层
情况 结果
同一 {} 内两次 int a; ❌ 语法错误（重定义）
嵌套 {} 内外各一个 int a; ✅ 合法，内层遮蔽外层，两块独立内存

块级嵌套示例

#include <iostream>
int main() {
    int i = 0;
    std::cout << "外层 i = " << i << std::endl;  // 0

    {
        int i = 7;   // 内层 i 遮蔽外层 i
        int j = 9;
        std::cout << "内层 i = " << i << ", j = " << j << std::endl;  // 7, 9
    }   // 内层 i 销毁，遮蔽结束

    std::cout << "外层 i 恢复 = " << i << std::endl;  // 0
    return 0;
}

四种常见场景

1. 局部变量遮蔽全局变量

int x = 100;

void func() {
    int x = 50;              // 局部遮蔽全局
    std::cout << x;          // 50
}

int main() {
    func();
    std::cout << x;          // 100
}

2. 内层块遮蔽形参（同一函数体直接 int a 与形参同名会重定义报错，须包一层 {}）

void test(int a) {
    std::cout << a;          // 5（形参）
    {
        int a = 20;        // 内层块遮蔽形参
        std::cout << a;    // 20
    }
    std::cout << a;          // 5（形参恢复可见）
}

3. 循环体内遮蔽循环变量（C++11 起 for (int i ...) 的 i 仅在循环作用域内）

for (int i = 1; i < 3; ++i) {
    int i = 99;              // 循环体内局部 i 遮蔽循环头 i
    std::cout << i << " ";   // 99 99
}

4. 多层嵌套连续遮蔽

int a = 1;
{
    int a = 2;
    {
        int a = 3;
        std::cout << a;    // 3
    }
    std::cout << a;        // 2
}
std::cout << a;            // 1

C++ 特有：访问被遮蔽的全局变量

用全局作用域解析符 :: 穿透遮蔽：

int x = 10;
int main() {
    int x = 20;
    std::cout << x << std::endl;   // 20（内层）
    std::cout << ::x << std::endl; // 10（全局）
}

工程上的问题与规范

问题：

  1. 改内层变量，外层同名变量完全不变，容易误以为改到了外层
  2. 可读性差，难一眼看出用的是哪一层
  3. 内层变量出 {} 即销毁，生命周期易混淆

建议：

  1. 避免嵌套作用域用同名变量（如全局 g_x、局部 local_x）
  2. 不要与形参同名；若必须区分，用不同名字而非遮蔽
  3. 循环体内不要重复定义与控制变量同名的变量

一句话：查找由内向外；内层一旦声明同名标识符就遮蔽外层，内层范围内只能访问内层那份。

和 C 的区别

变量遮蔽的查找规则C 和 C++ 完全一样（词法作用域，由内向外）。差异在两个细节：

对比点 C C++
::x 访问全局 ✅ 有 ✅ 有（一样）
for (int i...) 的 i 出循环 C99 起仍可见（泄漏） 出循环即销毁（不泄漏）
命名空间嵌套遮蔽 ❌ 无命名空间 ✅ std::cout 可被局部 std 遮蔽

给 C 程序员的提醒： C99 的 for(int i...) 里 i 在循环外仍可见，转 C++ 后这个 i 出循环就没了——如果你习惯"循环后还用 i"，要么提前声明，要么意识到作用域变了。

1（选择） 下面代码输出什么？

    int x = 20;
    {

        std::cout << x << " " << ::x;
    }

  • A. 30 10
  • B. 30 20
  • C. 20 10

2.2

.4 extern 与头文件分工

本节讲什么

extern 声明/定义、#include 预处理文本替换、标准库声明与链接。

extern 关键字完整解析

支持分离式编译：多个 .cpp 分别编译，最后链接成一个程序。extern 用来声明「这个名字的定义在别处」。

通俗理解：external（外部的）

extern = 声明，不是定义。告诉编译器：

这个函数 / 全局变量的本体不在当前 .cpp，在别的源文件里；编译本文件时先「放行」，链接阶段再去别的 .cpp 里把它找出来拼上。

定义 extern 声明
内存 ✅ 分配 ❌ 不分配
次数 全项目一次 可多次
例子 int g_num = 10; extern int g_num;

文件 A.cpp / B.cpp 例子：

// A.cpp
int g_num = 100;   // 定义：内存在这里

// B.cpp
extern int g_num;  // 声明：g_num 在别的文件
#include <iostream>
int main() {
    std::cout << g_num;  // 编译时只知道「有个 int g_num」
    return 0;            // 链接时找到 A.cpp 里的实体，拼在一起
}

函数可以省略 extern：C++ 里函数声明默认隐式带 extern，所以跨文件调函数一般只写 void func(); 即可。

全局变量跨文件必须用 extern 声明（或在头文件里 extern 声明后 #include），否则编译器不知道去别处找。

1. 声明 vs 定义

声明（declaration） 定义（definition）
做什么 告诉编译器类型和名字 分配内存（变量）或提供函数体
出现次数 可多次 整个程序只能一处
不写的后果 — 多处定义 → 链接报 multiple definition

2. extern 修饰变量：两种写法

extern int i; —— 纯声明（引用性声明）

  • 不分配内存
  • 表示：i 的定义在其他 .cpp 或本文件更后面
  • 可在头文件、多个源文件中重复写，无冲突
// a.cpp
int i = 100;        // 唯一定义，分配内存

// b.cpp
extern int i;       // 仅声明，借用 a.cpp 的 i
#include <iostream>
void f() { std::cout << i; }

extern int i = 0; —— 带初始化 = 定义（抵消 extern）

C/C++ 规则：带显式初始化的 extern 一律视为定义，等价于 int i = 0;：

  • 会分配全局内存
  • 整个项目只能写一次
  • 违背「引用外部变量」的本意，工程中极少这么写

3. 易混对比

int i;               // 定义（C++ 中尽量避免；全局默认零初始化）
extern int i;        // 仅声明，无内存
int i = 0;           // 定义
extern int i = 0;    // 定义，等价上一行

一句话：extern int i; 只有声明含义；只要 extern 变量附带 = 初值，就是定义。

4. extern 修饰函数

函数更简单——声明默认就是 extern，可省略：

extern void func();  // 声明，无函数体
void func();         // 完全等价

有 {} 函数体 = 定义，与是否写 extern 无关：

void func() { }              // 定义
extern void func() { }       // 同样是定义，写 extern 无意义

5. 工程规范（头文件 + 单源文件定义）

头文件只写 extern 声明：

// global.h
extern int g_val;    // 仅声明，多文件 #include 无冲突

只有一个 .cpp 写定义：

// global.cpp
int g_val = 10;      // 唯一定义，分配内存

禁止在头文件写：

extern int g_val = 10;   // ❌ 定义！头文件被多个 .cpp 包含 → 重复定义
int g_val = 10;          // ❌ 同上

HFT 多文件项目里：全局配置、共享计数器等用「.h 声明 + 一个 .cpp 定义」是标准做法。

6. 什么时候会「重定义」？怎么规避？

错误写法 原因
两个 .cpp 都写 int g_num = 10; 两处定义 → 链接 multiple definition
头文件写 int g_num = 10; 并被多个 .cpp 包含 每个 .cpp 都生成一份定义
头文件写 extern int g_num = 10; 带 = 仍是定义，同上

规避：.h 里只写 extern int g_num;，恰好一个 .cpp 写 int g_num = 10;。

7. 补充：extern "C"（与变量 extern 不同）

extern "C" 用来关闭 C++ 名字修饰（name mangling），让 C++ 能调用 C 写的函数。DPDK、Linux 内核接口里很常见：

extern "C" {
    void dpdk_init();   // 按 C 规则链接，符号名不被 C++ 改写
}

这是链接方式的声明，和「全局变量 extern int g_num」不是同一类语法，后面第 18 章 / 与 C 混编时会再遇到。

#include 的本质：预编译「文本替换」

#include 是预处理指令，是编译器在正式编译之前做的第一步。可以把它理解成：

把指定文件的内容，原地复制粘贴到当前代码里——粘贴位置就是 #include 那一行。

比如你写 #include <string>，标准库里 string 类的声明、成员函数接口等文本会原封不动插在这行位置，编译器才知道 std::string 是什么、有哪些方法可以调用。

包含的不是 .cpp 实现文件，而是头文件（.h 或 C++ 标准库的 <xxx> 无后缀头）。头文件只放「告诉别人这个东西怎么用」的声明；真正的实现代码在编译器自带的预编译库（.lib / .a）里，不用你自己编译标准库源码。

编译前预处理（第一步）：
  main.cpp                    展开后（示意）
  ─────────                   ─────────────
  #include <string>    →      [ string 头里全部声明文本 ]
  #include <cctype>    →      [ cctype 头里 isalpha 等声明 ]
  int main() { ... }          int main() { ... }

标准库例子

#include <string>    // 粘贴 string 类声明、operator+ 原型等
#include <cctype>    // 粘贴 isalpha、isdigit、toupper 等函数声明

int main() {
    std::string s = "IF2406";
    for (unsigned char c : s)
        if (!std::isalpha(c)) return 1;   // include 后直接调，不用手写 ASCII 判断
    return 0;
}
  • 编译器看到 #include <string> 后，才知道 std::string、size() 等符号长什么样
  • #include <cctype> 之后，才能直接调 std::isalpha、isdigit 等（见 3.2.5 cctype）

声明 vs 实现：为什么要分离？

放在头文件（#include 进来） 藏在预编译库里
类 / 函数声明、模板声明 函数体、已优化的机器码
告诉编译器「能调什么、长什么样」 链接阶段才接上，不参与你每次 #include 的文本膨胀

这种声明与实现分离有两层好处：

  1. 编译快：头文件被多次 #include 时，不会把庞大实现重复粘贴进每个 .cpp
  2. 接口稳定、实现可换：标准库把核心实现藏起来，只暴露安全的调用接口——HFT 这类依赖稳定、高效底层组件的场景，直接复用标准库即可，不必重复造轮子、也不必碰底层细节
阶段 谁做什么
预处理 #include 复制头文件文本
编译 每个 .cpp 单独编译成 .o，只验证声明够用
链接 把 .o 与标准库 / 你的 Sales_data.cpp 等实现绑在一起

与 2.5 #include vs using、1.5.2 链接与编译产物 衔接。

#include 与 extern：分工与配合

两者原理完全不同，工程里却经常搭档使用：

#include extern
做什么 文本复制：把头文件内容粘贴进当前 .cpp 一条声明：变量本体在别的 .cpp，不复制实现
头文件里常放 函数声明、extern 变量声明、结构体、宏 全局变量的 extern 声明本身

一句话：#include 负责把 extern 声明导入本文件；extern 负责告诉编译器变量实体在别的 .cpp。

标准组合写法（三文件套路）

global.h（被 #include）

extern int g_val;   // 声明全局变量
void test();        // 函数声明（默认 extern，可省略 extern）

global.cpp（唯一定义）

int g_val = 100;    // 真正分配内存
void test() { }

main.cpp

#include "global.h"   // 把声明拿过来，不用手写 extern

int main() {
    g_val = 200;
    test();
    return 0;
}

直白区别

  1. 函数：声明写进 .h，#include 引入即可，一般不用写 extern（函数声明默认 extern）。
  2. 全局变量：头文件里写 extern int g_val;，再 #include 给其他 .cpp 共用。 - 也可以不在头文件，而在 main.cpp 手写 extern int g_val;，但项目一大就乱，工程上统一放头文件。

反面例子（必踩坑）

// bad.h  ❌ 千万不要这样
int g_val = 100;    // 这是定义！不是声明

// a.cpp
#include "bad.h"

// b.cpp
#include "bad.h"    // 两个 .cpp 各有一份 g_val 定义 → 链接重定义报错

正确：头文件只写 extern int g_val;，一个 global.cpp 写 int g_val = 100;。

示例

#include <iostream>
#include <limits>

int global_val = 10;

extern int shared_val;  // 声明：在其他 .cpp 中定义

void demo_static() {
    static int call_count = 0;
    ++call_count;
    std::cout << "called " << call_count << " times\n";
}

int main() {
    int ival = 0;
    const int limit = 100;
    constexpr int kMax = 10000;

    demo_static();
    demo_static();  // call_count 累加，不会重置

    std::cout << "int max=" << std::numeric_limits<int>::max() << std::endl;
    std::cout << ival << " " << limit << " " << kMax << std::endl;
    return 0;
}

和 C 的区别

extern、#include、声明 vs 定义的规则，C 和 C++ 几乎完全一样——这部分 C 的经验直接搬过来。唯一的 C++ 独有问题是名字改编：

对比点 C C++
extern int g; 跨文件声明 一样 一样
#include 文本替换 一样 一样
函数符号名 就是函数名（func） 改编后带参数信息（_Z4funcv）
跨语言调用 — C++ 调 C 要 extern "C"

给 C 程序员的关键提醒： C 的 .h/.c/extern 经验全部适用 C++。多出来的一件事：C++ 调 C 库要 extern "C"，因为 C++ 会改编函数名，找不到 C 库里的原名。

自测题

1（选择） 头文件里写哪个会出问题？ - A. extern int g_val; - B. int g_val = 10; - C. void func();

2（判断） extern int i = 0; 是声明还是定义？

3（踩坑） C++ 程序调一个 C 写的 void init();，直接 #include "init.h" 后调用，链接报错找不到符号，最可能的原因和解决办法？

参考答案
  1. B。int g_val = 10; 是定义，头文件被多个 .cpp 包含会重复定义。A 是声明（安全），C 是函数声明（默认 extern，安全）。
  2. 是定义。带 = 初值 的 extern 一律视为定义，会分配内存。纯声明只能写 extern int i;。
  3. C++ 把 init 改编成 _Z4initv，但 C 库里是 init，链接找不到。解决：用 extern "C" { #include "init.h" } 或在 init.h 里写 #ifdef __cplusplus extern "C" { #endif ... #ifdef __cplusplus } #endif。

2.2

.5 跨文件调用：为什么必须 #include 头文件（含 C 对照实测）

← 第 2 章 · ← 2.2.4 extern 与头文件分工

本节讲什么

一句话结论：要调用另一个 .cpp / .c 里的函数、或用它对外暴露的全局变量，编译当前文件时必须先看到它的"声明"——工程上的标准做法就是 #include 对应的 .hpp / .h。

这条规则 C++ 和 C 完全一样。2.2.4 讲了 extern 与头文件的分工细节，本节把"为什么必须"钉死： ① 没有声明时各语言到底报什么错（实测）；② #include 和 JS import 的本质区别； ③ 严格说"必须"的是声明而不是 #include 本身；④ static（内部链接）是头文件也救不了的墙。

要点

1. 规则本身：编译器只看声明，链接器才找定义

main.cpp 编译时：只认"声明"（函数原型 / extern 变量声明）
   ↓ 从哪来？→ #include "other.hpp"（把头文件文本粘贴进来）
other.cpp 编译时：独立编译单元，main.cpp 完全看不见它
链接时：把 main.o + other.o 拼起来，按名字找定义
  • 每个 .cpp 是独立编译单元（更准确的叫法：翻译单元 TU，见 2.2.6 编译单元与链接），互相天然看不见。
  • #include 是预处理期文本粘贴，不是"导入功能"——它只是把声明搬进当前文件的最方便方式。
  • 所以准确表述是：必须先有声明；#include "x.hpp" 是拿声明的标准手段。

2. 和 JS import 的区别（最容易带偏的类比）

JS import C/C++ #include
本质 模块系统加载另一个源文件的导出 预处理器文本粘贴
拿什么 导出符号（运行/打包时解析） 只有声明；定义靠链接器去 .o 里找
对方文件 直接被引用 对方 .cpp 从头到尾不知道你被谁 include 了

C++20 的 import module; 长得像 JS，但底层是预编译模块二进制，不是读源码文本，老代码普及度也低——初学阶段把头文件机制吃透即可。

3. 没有声明会发生什么：三种语言模式实测

同一份代码（main 里无声明直接调 hello()，链接命令带上 other），clang 23.1.0 实测：

模式 结果 输出
C++ ❌ 编译期硬错误 error: use of undeclared identifier 'hello'
C89/C90 ⚠️ 能编能跑 隐式声明为 int hello()，链接成功，运行返回 42
C99 起（现代默认） ❌ 硬错误 error: call to undeclared function 'hello'; ISO C99 and later do not support implicit function declarations
  • C++ 从第一版标准就"先声明后使用"，编译都过不去，带不带 other.cpp 进链接都一样死。
  • C89 的"隐式函数声明"是历史后门：没见过的调用自动假定返回 int、参数不定。返回值恰好是 int 时碰巧能跑。
  • 后门的代价（实测）：把函数改成 double pi() { return 3.14; }，C89 下照样编译通过，运行输出垃圾 1——编译器按 int 去 eax 读返回值，真值在浮点寄存器 xmm0 里。未定义行为，这就是 C99 把它踢出标准、GCC≥14 / Clang≥16 默认报错的原因。

4. C 侧三个补刀实验（clang 23.1.0 实测）

/* other.h */  extern int g_count;  int add_one(int x);
/* other.c */  int g_count = 100;  int add_one(int x){ return x+1; }
               static int secret(void){ return 7; }   /* 内部链接 */
实验 结果 说明
① main.c 里 #include "other.h"，改 g_count、调 add_one ✅ 输出 101 42 标准套路
② 不 include，main.c 里手写 extern int g_count; int add_one(int x); ✅ 输出 100 42 证明"必须"的是声明，不是 #include 这个语法
③ 声明照旧，调对方的 static 函数 ❌ ld: symbol(s) not found 内部链接符号不进符号表，头文件也救不了

5. 精确化表述（把"必须 include"说严谨）

要调用另一个 .c/.cpp 里外部链接的函数或变量，当前编译单元必须先看到它的声明。 手写声明也能编过（实验②），但工程上必须统一走头文件，因为： - 声明只有一份，改签名时所有调用方同步更新； - 实现文件自己也 #include 自己的头 → 声明与定义不一致时编译器当场报错，而不是留到链接期爆炸； - 头文件配 #ifndef 守卫 / #pragma once 防重复包含。

而 static（内部链接）的函数/变量，别的文件任何方式都够不着（实验③）——这也是"不想被外部用就加 static"的原因。

6. 变量和函数的小差异

  • 函数：声明默认隐式 extern，头文件里写 int add_one(int x); 即可。
  • 全局变量：头文件里必须写 extern int g_count;（不带初值），恰好一个 .c/.cpp 写定义 int g_count = 100;。头文件里写 int g_count = 100; 被多个文件包含 → 链接 multiple definition（见 2.2.4）。
  • C++ 特有的一处不同：C++ 有名字改编（name mangling），C++ 调 C 写的函数要 extern "C"；纯 C 项目没这回事（见 2.2.4 第 7 节）。

HFT / 嵌入式关联

  • HFT 引擎按模块拆 .cpp（行情 / 策略 / 下单），跨模块全靠头文件声明拼合；声明与定义不一致在这种工程里会立刻被"实现文件 include 自己的头"这条纪律当场抓住。
  • 嵌入式里 static 用得很凶：驱动内部的 helper 全部 static，对外只暴露 .h 里声明的几个入口——头文件就是模块的"对外合同"。
  • 裸机链接脚本时代也一样：启动汇编里的 Reset_Handler 能被 C 的 main 前的代码调用，靠的还是同一套"声明 + 符号表 + 链接"机制。

代码自测

Q1：main.cpp 不 include 头也不手写声明，链接命令带上 other.cpp，C++ 能调 hello() 吗？为什么？

不能，编译期就报 use of undeclared identifier。C++ 要求调用点必须先看到声明；编译过不去，链接器带什么都没用。C89 是例外（隐式声明），C99 起同样报错。

Q2：不 #include 头也不手写声明不行，那不 include 头、只手写声明为什么能编过？既然能编过，为什么工程上还要求必须 include 头？

因为编译器要的只是"声明"这段文本，不在乎它来自粘贴还是手写。工程上走头文件是为了：声明单点维护、实现文件 include 自己的头让编译器核对声明与定义一致、配合 include guard 防重复。手写声明在项目变大后必然与真实定义漂移，且漂移要到链接期甚至运行期才暴露。

Q3：other.c 里 static int secret(void)，在 main.c 里写了正确的声明 int secret(void);，能调用吗？

不能。声明只对编译期有效；static 使符号成为内部链接，不进全局符号表，链接期 symbol(s) not found。想跨文件用就不能加 static；反过来，不想被外部用的函数/变量应主动加 static。

Q4：C89 下隐式声明为什么"有时能跑、有时出垃圾"？

隐式声明假定函数返回 int、参数个数类型不定。真实函数若恰好返回 int 且调用约定匹配，返回值走同一寄存器，碰巧正确；若返回 double/long long 或结构体，返回值在别的寄存器/内存里，按 int 读就是垃圾——未定义行为。所以现代编译器默认把它当错误。

2.2

.6 编译单元与链接（翻译单元 TU / ODR / 头文件）

← 第 2 章 · ← 2.2.5 跨文件调用为什么必须 include 头文件

本节讲什么

把 2.2.4–2.2.5 那套"声明 / 定义 / 头文件"的机制往上抬一层，讲清楚它的理论骨架：

  • 翻译单元（Translation Unit, TU） = 一个 .cpp 源文件 + 它 #include 进来的全部头文件，经过预处理展开后得到的那一份完整文本。编译器一次只处理一个 TU。
  • 编译单元隔离：两个 .cpp 互相看不见。
  • 链接器负责把多个 TU 拼起来，于是有了单一定义规则（ODR）：哪些东西可以在多个 TU 里各写一份，哪些只能有一份。

一句话：TU 决定"编译器一次能看到多少东西"，ODR 决定"链接器能容忍你重复写几次"。

要点

1. 什么是翻译单元（TU）

标准定义：一个源文件，加上它 #include 的所有头文件与源文件，减去条件编译跳过的部分——也就是预处理之后、交给编译器本体的那一份文本。

// a.cpp  —— 这就是一个 TU（预处理展开后）
#include <iostream>   // 把整份 iostream 声明文本粘贴进来
#include "b.hpp"      // 把 b.hpp 的文本粘贴进来
int main() { ... }

要点： - 头文件自己不是 TU。它只在被某个 .cpp include 时，成为那个 TU 的一部分。 - 每个 TU 独立编译，互相看不见：main.cpp 不知道 foo.cpp 里有什么，全靠头文件里那点声明来"对齐"。 - 这也是 2.2.5 那条结论的底层原因：跨文件调用必须先有声明，因为编译器压根不去看对方文件。

2. 几个 .cpp 就是几个 TU？——三种情况

情况 TU 数 说明
两个 .cpp 分开编译 2 各自独立编译出 .o，链接器合并
a.cpp 里 #include "b.cpp" 1 b.cpp 的文本被粘贴进 a.cpp，合二为一（不推荐：重复定义 + 编译膨胀，见 2.2.5）
条件编译 #ifdef 跳过整段 仍是 1 只是这段文本没进展开结果

⚠️ 一条常见误传：预编译头（PCH）不会改变 TU 数量。PCH 只是把常用头的解析结果缓存下来加快编译，TU 边界丝毫没动；真正改变 TU 边界的只有 #include 展开与条件编译（C++20 Modules 另有一套模块语义）。

3. ODR（One Definition Rule）：什么能重复，什么不能

类别 能否在多个 TU 各写一份定义 原因
普通（非内联）函数 / 全局变量 ❌ 全局只能一份 多处定义 → 链接 duplicate symbol
inline 函数 ✅ 可以（且必须在每个用到它的 TU 里可见定义） 定义被发成 weak/COMDAT 符号，链接器去重留一份
类模板 / 函数模板 ✅ 同上 实例化后同样是 weak 符号去重
类 / 结构体 / 枚举定义 ✅ 可以（头文件里放的就是它） 类型定义不产生符号，但各 TU 必须完全一致
static / 匿名 namespace 里的东西 ✅ 每个 TU 各一份 内部链接，各自独立，互不影响

关键机制：inline 与模板之所以能重复，是因为编译器给它们打上 weak（弱符号） 标记，链接器遇到同名弱符号只保留一份。用 nm 能亲眼看到：

$ clang++ -c i1.cpp -o i1.o && llvm-nm -m i1.o | grep inl
0000000000000020 (__TEXT,__text) weak external __Z3inlv
                                  ^^^^ weak = 可被去重

4. 本节全部实测（clang 23.1.0，macOS arm64）

实验 现象 结论
clang++ -### main.cpp foo.cpp -o test 触发 2 次 -cc1（每个源文件 1 次） 2 个 TU
该命令跑完后目录里 .o 数 0（.o 落在 /var/folders/.../T/ 临时目录，链接完自动删） Quiz 答案的坑点
加 -save-temps 再编一次 留下 main.o foo.o 想看 .o 就用它
a.cpp 里 #include "b.cpp" 只触发 1 次 -cc1 1 个 TU
两个 TU 都写 int dup(){...} duplicate symbol 'dup()' in: .../d1-*.o, .../d2-*.o ODR：普通函数只能定义一次
两个 TU 都写 inline int inl(){...} 链接 OK，nm 见 weak external __Z3inlv inline 走弱符号去重
C++ 里不声明直接调函数 use of undeclared identifier 无隐式声明（见 2.2.5）

HFT / 嵌入式关联

  • HFT 引擎按模块拆 .cpp，一次构建就是几十上百个 TU 并行编译 → 头文件里多一行无关 include，会被复制进每一个 TU，这就是"头文件瘦身 / 前置声明 / PCH"这些工程手段存在的理由。
  • 模板和 inline 大量出现在行情解析、订单簿的头文件里（如 template <typename T> struct RingBuffer），它们的定义必须放在头文件，否则调用方 TU 看不到定义，只能靠弱符号在别处碰运气。
  • 嵌入式裸机同理：启动汇编 + C 文件各自一个 TU，靠链接脚本把段摆到正确地址；static 驱动内部函数不进符号表，天然不占全局命名空间。

代码自测

Q1：g++ main.cpp foo.cpp -o test 这条命令，会产生几个翻译单元、几个 .o 文件？

2 个翻译单元、2 个 .o 目标文件（每个 .cpp 一个）。 坑点：这一条命令把"编译 + 链接"一起做了，.o 是临时产物（实测落在 /var/folders/.../T/d1-*.o 这类路径），链接完就被删掉，所以你在目录里看不见它们。想留住就分开做： g++ -c main.cpp -o main.o && g++ -c foo.cpp -o foo.o && g++ main.o foo.o -o test（或一次性加 -save-temps）。

Q2：a.cpp 里写了 #include "b.cpp"，然后只编译 a.cpp，算几个 TU？为什么工程上不这么干？

1 个 TU。预处理把 b.cpp 的文本整份粘贴进 a.cpp，编译器眼里只有一份文本。 不这么干的原因：① 定义重复风险——若 b.cpp 也被单独编译，同一函数就有两份定义；② 编译膨胀——改一次 b.cpp，所有 include 它的 TU 都要重编；③ 破坏"头文件放声明、源文件放定义"的契约（见 2.2.5）。

Q3：为什么 inline 函数和模板的定义要写在头文件里？为什么普通函数不行？

inline / 模板必须在每一个用到它的 TU 里看到完整定义（否则无法内联 / 无法实例化），而头文件正是被每个 TU include 的公共文本，所以定义放头文件。 它们被允许重复，是因为编译器把它们发成 weak（弱符号），链接器去重只留一份（实测 nm 显示 weak external）。 普通函数没有这个待遇：两个 TU 各写一份定义 → duplicate symbol 硬错误。所以普通函数"声明放 .h、定义放唯一一个 .cpp"。

Q4：预编译头（PCH）会让两个 cpp 合并成一个 TU 吗？

不会。PCH 只是把常用头文件的解析结果缓存成二进制，让后续 TU 解析更快，TU 的边界完全没变，仍然每个 .cpp 一个 TU。真正改变 TU 的是 #include 展开和条件编译。

2.3

复合类型

本节讲什么

详细介绍两种基于其他类型定义的复合类型：引用（Reference）和指针（Pointer）。

  • 引用为对象起了另外一个名字（别名），引用必须被初始化，且无法重新绑定到另外的对象。
  • 指针实现了对其他对象的间接访问，它本身是一个对象，可以被赋值和拷贝。介绍空指针（推荐 C++11 的 nullptr）、解引用 *、取地址 & 以及 void* 指针。
  • 探讨复杂声明：指向指针的指针、对指针的引用等。

要点

  • 引用 int &r = i;：必须初始化，不能重新绑定，不存在空引用
  • T& / const T&：可变引用 vs 常量引用（只读）
  • 指针 int *p = &i;：可为空，可重新指向其他对象
  • nullptr：空指针字面值，优于 NULL 或 0
  • 解引用 *p：访问指针所指对象；取地址 &obj：获取对象地址
  • void*：可存放任意对象地址，但不能直接解引用
  • 复杂声明：从变量名出发，由内向外结合声明符理解，如 int *&rp 是对指针的引用

子节

  • 2.3.1 引用
  • 2.3.2 指针与 nullptr

代码自测

题目 1： 以下声明各是什么？

int* p1, p2;  // p1 和 p2 各是什么类型？
int &r;       // 合法吗？
int*& rp = p1; // ?
参考答案

2.3

.1 引用

本节讲什么

为什么需要引用、T& 与 const T&。

为什么 C++ 还要有引用？

已有指针，再引入引用，是为了解决指针在业务代码里的常见痛点。

指针的缺点

  1. 可为空（nullptr）→ 必须判空，漏了可能崩溃（HFT 里直接宕机）
  2. 可随意改指向 → 逻辑容易乱
  3. 语法繁琐 → *p 解引用、*/& 混用
  4. 可做算术（p++）→ 容易越界
int a = 1, b = 2;
int *p = &a;
p = &b;   // 随时换指向

引用：受约束的「安全版指针」

编译器实现上，引用常类似 T* const（指向 T 的常量指针——地址绑死不能改）：

特性 指针 int* 引用 int&
可为空 ✅ nullptr ❌ 必须绑定对象
改指向 ✅ p = &other ❌ 绑定后不能换
使用语法 *p 直接当变量用
指针运算 ✅ ❌ 
int a = 10;
int &ref = a;
ref = 20;              // 直接改 a，不用 *

// 底层直觉（概念模型，不是你要写的代码）：
// int *const p = &a;  // 地址固定，通过 *p 访问

一句话：引用 = 受限制、更安全、语法更简洁的间接访问；日常业务优先引用，底层内存/DPDK 才用裸指针。

取舍标准（HFT 编码习惯）

优先用引用：

  • 函数传参、避免拷贝：void f(const OrderBook &book);
  • 运算符重载（语法要求）：operator+、operator<< 等

必须用指针：

  • 后期要改变指向
  • 对象可能不存在（可选）
  • 数组、内核、DPDK 等需要地址偏移

引用：T& 与 const T&

1. 可变引用（可修改原对象）

int a = 10;
int &ref = a;
ref = 20;        // ✅ 通过 ref 修改 a
// a 现在是 20
  • int&：绑定原变量，可读可写

2. 常量引用（只读）

int a = 10;
const int &ref = a;
// ref = 20;     // ❌ 编译错误，不能通过 ref 修改
std::cout << ref; // ✅ 只读
  • const int&：只能读，不能通过引用改原对象
  • 可绑定到字面量：const int &r = 42;（普通 int& 不能绑字面量）

3. 引用的硬性规则（C++ 独有）

  1. 必须初始化，不能空着
  2. 绑定后不能改绑到其他对象（Rust 的引用可以重新绑定）
  3. 不存在「空引用」

4. 工程习惯（HFT / 日常 C++）

// 传参优先：不拷贝 + 只读
void process(const std::string &s);

// 需要改入参时才用可变引用
void adjust(int &value);
场景 用法
只读、避免拷贝 const T&
需要修改原对象 T&
可选/可为空 用指针或 std::optional（指针章节）

和 C 的区别（重点：引用是 C++ 独有）

C 没有引用——所有间接访问都靠指针。引用是 C++ 给 C 程序员的"安全糖"：

对比点 C（只有指针） C++（有引用）
间接访问 void f(int* p) 调用要 f(&x) void f(int& r) 调用直接 f(x)
判空 必须判 p != NULL 引用不能为空，不用判
改指向 p = &other 随时改 引用绑定后不能换
解引用 *p 直接用 r，像普通变量
指针运算 p++ 可越界 引用没有运算 
/* C：传参要取地址，函数里要解引用 */
void bump(int *p) { (*p)++; }
int x = 5;
bump(&x);          // 调用方要写 &，容易忘

// C++：引用让传参像普通变量
void bump(int &r) { r++; }
int x = 5;
bump(x);           // 调用方不用写 &，更自然

给 C 程序员的关键转变： 1. 函数参数优先用 const T&（只读不拷贝），替代 C 的 const T* 2. 要修改入参用 T&，替代 C 的 T* 3. 只有"可选/可为空/要改指向/数组"才用指针 4. C 里 &x 是取地址，C++ 里 int &r = x 是声明引用——同一个 & 符号，位置决定含义（声明里 & 在类型后=引用，表达式里 &x=取地址）

常见错误

1. 引用不初始化

int &ref;   // 编译错误：引用必须初始化

引用没有"空状态"，定义时必须绑定。

2. 引用绑定后试图改绑

int a = 1, b = 2;
int &ref = a;
ref = b;    // 这不是改绑！是把 b 的值赋给 a（a 变成 2）

ref = b 是赋值，不是重新绑定。引用一旦绑定 a，一辈子就是 a 的别名。

3. 局部引用返回悬空

int& bad() {
    int x = 42;
    return x;   // 悬空引用：x 出函数就销毁
}

返回引用要确保被引用的对象生命周期够长（如类的成员、静态变量、堆对象）。

2.3

.2 指针与 nullptr

本节讲什么

const 指针、nullptr、Rust 对照。

指针：int* 与 const（和引用放一起记）

写法 读法 谁能改
int* / int *p 普通指针 指针可变指向；可通过 *p 改对象
const int* / int const *p 指向常量的指针 不能通过 *p 改对象；p 可改指向
int* const p 常量指针 可通过 *p 改对象；不能改 p 的指向
const int* const p 都 const 指向和对象都不改 
int i = 0, j = 1;
const int *p = &i;   // *p 不可改，p 可指向 j
p = &j;              // ✅
// *p = 2;           // ❌

int *const cp = &i;  // cp 不可改指向，*cp 可改
*cp = 2;             // ✅
// cp = &j;          // ❌

和引用的对应：

引用 近似指针含义
int& 像绑死的 int*，必须有效，可读写 *p
const int& 像 const int*，只读，不能 *p = ...

引用不能重新绑定 ≈ 没有「改指向」这回事；指针可以 p = &other。

nullptr：为什么优于 NULL / 0（C++11）

三者分别是什么

本质 类型
0 整数零 int
NULL 宏，通常 #define NULL 0（有的编译器 (void*)0，不一致） 仍是整数语境
nullptr 关键字，专用空指针字面值 std::nullptr_t 
void func(int);
void func(char*);

func(0);        // 调用 func(int) —— 不是指针！
func(NULL);     // 同上，仍是 int 语境
func(nullptr);  // 调用 func(char*) —— 正确

核心优势

① 重载不踩坑

void foo(int)  { std::cout << "int\n"; }
void foo(char*) { std::cout << "pointer\n"; }

foo(0);        // int
foo(NULL);     // int
foo(nullptr);  // pointer ✅

② 模板推导正确 — 0/NULL 推成 int；nullptr 推成 std::nullptr_t，智能指针等接口只认后者。

③ 类型安全

int a = nullptr;  // ❌ 编译错误
int b = NULL;     // ⚠️ 往往能通过，隐藏 bug

④ 兼容所有指针类型

int *p = nullptr;
void (*fn)() = nullptr;

std::nullptr_t 可隐式转为任意指针类型，不能隐式转为整型——安全根源在此。

什么时候用哪个

写法 用途
nullptr 所有表示空指针的场景（现代 C++ 唯一推荐）
NULL 老代码遗留，新项目别写
0 只表示数字零，绝不表示空指针

极简总结：0 / NULL 是整数，重载和模板易错；nullptr 是专门的空指针类型，无歧义、类型安全。

和 C 的区别

指针是 C 和 C++ 高度重合的部分——int*、const int*、int* const、指针运算全部一样。差异主要在空指针表示和引用的存在：

对比点 C C++
指针语法/运算 一样 一样
空指针 NULL（宏，通常是 0） nullptr（关键字，专用类型）
引用 ❌ 没有 ✅ 优先用引用
void* 隐式转其他指针 ✅ 允许 ❌ 必须显式 cast

给 C 程序员的关键提醒： 1. NULL 在 C++ 里是坑——它通常是 0（整数），重载时 func(NULL) 可能匹配 func(int) 而不是 func(char*)。C++ 一律用 nullptr。 2. C 的 void* 能隐式赋给 int*，C++ 不行，要 static_cast<int*>(vp)。 3. C 程序员习惯"能用指针就别用值"，C++ 反过来——"能用引用就别用指针"。

/* C 写法 */
int *p = NULL;          // 空指针
void *vp = malloc(4);
int *ip = vp;           // void* 隐式转 int*，C 允许

// C++ 写法
int *p = nullptr;       // 专用空指针类型
void *vp = malloc(4);
int *ip = static_cast<int*>(vp);  // 必须显式 cast

const 指针四种形态（C 和 C++ 完全一样，照搬）：

写法 谁能改 记忆
int* p 都能改 普通指针
const int* p 只能改指向，不能改 *p "指向常量"
int* const p 只能改 *p，不能改指向 "常量指针"
const int* const p 都不能改 全锁

速记： const 在 * 左边管"指向的对象"，在 * 右边管"指针本身"。

示例

#include <string>

    std::cout << s << std::endl;
}

    ++n;
}

    int &refVal = ival;
    refVal = 1024;

    const int &cref = ival;
    std::cout << cref << std::endl;

    int *p = &ival;
    *p = 0;
    std::cout << ival << std::endl;  // 0

    const int *pc = &ival;           // 指向常量：不能 *pc 改值
    int *const cp = &ival;           // 常量指针：cp 不能改指向

    read_only("hello");
    bump(ival);

    return 0;
}

2.4

.1 const 基础与 constexpr

本节讲什么

顶层/底层 const、指针、constexpr。

一、普通 const 常量

const int ci = 0;
// ci = 10;   // ❌ 顶层 const，绝对不能改
// const int ci;  // ❌ 必须初始化
  • ci 是顶层 const：变量本身只读
  • 仅有 const 不保证编译期常量——若用运行时才知的值初始化，仍是运行时常量：
int x = rand();
const int ci = x;   // ci 不可改，但值运行期才确定

二、常量引用 const int &r（底层 const）

  1. 底层 const：不能通过 r 修改绑定对象 → r = 100; ❌
  2. 唯一能绑字面量的引用：
const int &r1 = 10;   // ✅
// int &r2 = 10;      // ❌ 普通引用不能绑临时/字面量
  1. 只限制「通过 r 改」，不限制原变量：
int a = 5;
const int &r = a;
a = 10;    // ✅ 直接改 a 可以
// r = 20; // ❌ 通过 r 不行
  1. 引用没有「顶层 const」说法——带 const 的引用全是底层 const

三、const 修饰指针

易混纠正：「指向常量的指针」vs「常量指针」

名字很像，锁定的对象不同：

写法 俗称 *p 能改值？ p 能改指向？
const int *p 指向常量的指针 ❌ 不能通过 p 改内容 ✅ 可以指向别的地址
int *const p 常量指针 ✅ 可以通过 p 改内容 ❌ 指向不能改 
int a = 1, b = 2;

const int *p1 = &a;   // 指向常量的指针：内容只读，指针能挪
p1 = &b;              // ✅
// *p1 = 99;          // ❌

int *const p2 = &a;   // 常量指针：指向钉死，内容可改
*p2 = 99;             // ✅
// p2 = &b;           // ❌

记法：const 靠近类型（const int *）→ 指向的内容不能改；const 靠近变量名（int *const p）→ 指针本身不能改。

与 3.2.4 string 与 C 风格字符串 里 C 风格 char* / const char* 读旧接口时也会用到。

1. 指向常量的指针：const int *p / int const *p（底层 const）

  • 不能 *p 改所指对象；p 本身可改指向
int num = 10;
const int *p = &num;
// *p = 20;   // ❌
p = &ci;      // ✅
num = 30;     // ✅ 原变量仍可改

2. 常量指针：int *const p（顶层 const）

  • 地址固定，不能换指向；可通过 *p 改值
int num = 10;
int *const p = &num;
// p = &ci;   // ❌
*p = 50;      // ✅

3. 双重 const：const int *const p

  • 顶层 + 底层：p 不能改指向，*p 不能改值

记忆口诀（从右往左读）

  • int *const p → p 是 const 指针（顶层），指向 int
  • const int *p → p 是指针，指向 const int（底层）

四、顶层 const vs 底层 const

顶层 const 底层 const
修饰谁 对象/指针自身 指针/引用所指/所绑的对象
例子 const int a、int *const p const int *p、const int &r
拷贝时 顶层 const 可丢弃 底层 const 必须匹配 
const int a = 10;
int b = a;           // ✅ 拷贝时丢弃顶层 const

const int *p1 = &x;
// int *p2 = p1;     // ❌ 不能丢失底层 const

极简：顶层 = 自己不能变；底层 = 通过它不能改指向的东西。

五、constexpr（编译期常量）

constexpr = constant expression，强制编译期求值，可作数组长度、模板实参。与 const 区别：const 只保证只读，值可能运行期才确定。

constexpr int val = 2 + 3;
int arr[val];        // ✅

int x = rand();
const int c = x;     // const 只读，但 c 是运行期常量
// constexpr int err = x;  // ❌

完整详解（变量/函数/构造、C++11/14 区别、if constexpr、数组例题）：见 2.4.3 constexpr 详解。数组维度考点见 3.5.1。

六、综合示例

#include <iostream>

int main() {
    const int ci = 0;
    // ci = 10;

    const int &r = ci;
    // r = 20;

    int num = 100;

    const int *p1 = &num;       // 底层：*p1 不可改
    // *p1 = 200;
    p1 = &ci;

    int *const p2 = &num;       // 顶层：p2 指向不可改
    // p2 = &ci;
    *p2 = 200;

    const int *const p3 = &ci; // 双重
    // p3 = &num; *p3 = 5;

    constexpr int MAX = 1024;
    int buf[MAX];

    return 0;
}

和 C 的区别

const 基本语义 C 和 C++ 一样（只读），但有几个关键差异：

对比点 C C++
const 全局默认链接 外部链接（和普通全局一样） 内部链接（相当于隐式 static）
const 能否当数组大小 ❌ 不是常量表达式（C99 变长数组除外） ✅ 整型 const 可当数组维度
constexpr ❌ 没有 ✅ C++11，编译期常量
const int &r = 42 ❌ C 无引用 ✅ 常量引用可绑字面量

给 C 程序员的关键提醒： 1. const 链接性差异最坑： C 的 const int x = 10; 放头文件被多文件包含会重定义；C++ 的 const 全局默认内部链接，放头文件每个 .cpp 各一份，不冲突。 2. C++ 的 const int N = 10; int arr[N]; 合法（const 是常量表达式）；C 里 const 不是常量表达式，int arr[N] 是变长数组（C99）或非法（C89）。C++ 要编译期大小用 constexpr。 3. constexpr 是 C++ 独有，强制编译期求值，C 没有（C 用 #define 或 enum）。

/* C：const 不能当数组大小（C89），要用 #define */
#define SIZE 10
int arr[SIZE];

/* C99 变长数组（运行期大小，不是编译期常量）*/
const int n = 10;
int arr[n];   /* C99 VLA，C++ 不支持 */

// C++：const/constexpr 可当数组大小
constexpr int N = 10;
int arr[N];   // 合法，编译期常量

常见错误

1. 搞混"指向常量的指针"和"常量指针"

const int *p;     // 指向常量：*p 不能改，p 能改指向
int *const p=&x;  // 常量指针：p 不能改指向，*p 能改

口诀：const 在 * 左边管内容，在 * 右边管指针本身。

2. 拷贝时丢底层 const

const int *p = &x;
int *q = p;   // ❌ 不能丢底层 const（否则能通过 q 改"常量"）

顶层 const 拷贝时可丢（const int → int 是值拷贝），底层 const 必须匹配。

3. const 当 C 用导致重定义

// 头文件（C++ 没问题，C 会重定义）
const int kMax = 100;   // C++: 内部链接，安全；C: 外部链接，多文件重定义

本节讲什么

三类速记、int vs int p、HFT 习惯。

三类分开记 + 指针口诀（通俗版）

先把三种形态分开，再记指针上 const 在 * 左还是右：

形态 写法 含义
普通 const 变量 const int a a 的值不能改
常量引用 const int& ref 不能通过 ref 改；绑定固定
指针 见下表 看 const 相对 * 的位置

指针口诀：

  • const 在 * 左边 → 指向的内容不可改（底层）
  • const 在 * 右边 → 指针本身不可改指向（顶层）

情况 1：const int *p（= int const *p）

int x = 10, y = 20;
const int *p = &x;
// *p = 100;  // ❌ 不能改指向的值

情况 2：int *const p

int x = 10, y = 20;
int *const p = &x;
*p = 100;     // ✅ 可改值
// p = &y;    // ❌ 不能换指向

情况 3：const int *const p

指针不能换指向，内容也不能改。

常量引用 vs 指针（底层直觉）

int a = 10;
const int &ref = a;
// ref = 20;  // ❌ 只读

概念上接近 const int *const 的语义：

  1. 绑定对象不能换（像 * 后面的 const）
  2. 不能通过引用改原值（像 * 前面的 const）
绑定/指向固定 值可改
int& ref ✅ ✅
const int& ref ✅ ❌（通过 ref）
int *const p ✅ ✅（通过 *p）
const int *p ❌（p 可换） ❌（通过 *p）

传参优先 const Order&：不拷贝，又防止函数内意外改订单——等价于「只读 + 绑定固定」的安全用法。

void on_book(const OrderBook &book);  // 推荐

const int a — ❌ 顶层

const int* p ✅ ❌ 底层
int* const p ❌ ✅ 顶层
const int* const p ❌ ❌ 顶层+底层

声明语法：int* 还是 int *p？（const 混淆的根源）

两种理解模式

模式 1：类型视角（现代写法，看着顺眼）

int* p;   // 把 int* 当成「整型指针」这一整个类型，p 是变量名

很多人习惯这么写，会误以为 * 依附于类型。

模式 2：C 原始声明规则（语法本源，分析 const 必须用这套）

int *p;

含义：*p 是一个 int；p 是指针变量——* 修饰的是后面的变量 p，不是 int。

一行定义多个名字时就能看懂为什么——经典坑：

int *a, *b, c;     // ✅ a、b 是指针，c 是普通 int
char *p, *q;       // ✅ 两个都是 char 指针

若写成 int* a, b; 或 char* p, q;，容易误以为两个都是指针，实际上只有第一个是指针，第二个仍是普通 int / char：

char* p, q;        // ❌ 经典迷惑：只有 p 是 char*，q 只是 char！
// 等价于：char *p; char q;

char *p, *q;       // ✅ 规范：星号紧挨变量名，一眼看出谁是指针

这就是 C/C++ 里著名的 「语法糖迷惑点」：char* 看起来像把「指向 char 的指针」当成一个复合类型，教材和代码里很常见，约定俗成；但语法上 * 始终绑定变量名，不是绑定 char。

写法 含义 风险
char* p 单变量时与 char *p 相同 一行多变量时易误判
char *p *p 是 char，p 是指针 语法本质，const 分析必用
char* p, q 仅 p 是指针 高频踩坑
char *p, *q 两个都是指针 多变量声明推荐

HFT / 严谨代码习惯：坚持 char *p、int *p（星号靠名字），单声明时也更不易与 const 规则搞混；需要两个指针就写 char *p, *q，不要写 char* p, q。

与 3.2.4 C 风格 char* 配合：字符串裸指针场景尤其容易在一行声明里写错。

套进 const：必须用原始规则

int *const p

  • 基础：int *p → * 属于 p
  • const 紧贴 p → 修饰指针变量 p
  • 结果：不能换指向；*p 可改

const int *p

  • const 修饰 int → *p 这个 int 是常量
  • p 本身不受 const 约束 → 可换指向

若把 int* 当成整体类型，很难分清 const int* 和 int *const——这就是之前混淆的根源。

铁则：const 修饰紧靠它的那个

记住：const 只绑定离它最近的标识符；* 是指针标记，分析时跟着变量名走。

1. const int *p

拆开：const int + *p

  • const 紧贴 int → 修饰 *p 这个 int 值
  • *p 不可改；p 本身可换指向

2. int *const p

拆开：int * + const p

  • const 紧贴 p → 修饰指针变量本身
  • p 不可换指向；*p 可改

等价写法： const int *p ≡ int const *p（都是修饰 int，与 p 无关）

通俗类比：箭头

写法 箭头（指针） 箭头戳到的东西（*p）
const int *p 可以到处跑 不能改
int *const p 钉死在原地 可以改
const int *const p 不能动 不能改

为什么直觉会反？ 直觉以为「const 在后面就约束值」，但语法是 const 绑最近的——int *const p 里 const 挨着 p，只限指针，管不到 int；要限值，必须把 const 写在 int 前。

终极口诀（左/右）

  1. const 在 * 左边 → 限制指向的值
  2. const 在 * 右边 → 限制指针本身
  3. 两边都有 → 值不能改、指针也不能改

对比常量引用

const int& ref 的语义 ≈ const int *const（概念类比）：

  • 绑定不能换（像 * 后面的 const）
  • 值只读（像 * 前面的 const）

普通 int& ≈ int *const：绑定固定，值可改。

再巩固一遍

写法 const 修饰谁 结果
const int *p / int const *p int（*p 的值） p 可换，值不可改
int *const p 指针变量 p p 不可换，值可改

一句话：

  • 分析 const / 多变量声明 / HFT 严谨代码：坚持 char *p、int *p（* 紧挨变量名）
  • 单变量、图省事：很多人仍写 char* p、int* p（当复合类型看），能读但别在一行里写 char* p, q

一句话速记

  1. const int ci → 自身不可改（顶层）
  2. const int& → 不能通过引用改；可绑字面量（底层）
  3. const int* → 内容不可改、指针可变（底层）；int* const → 地址不可变（顶层）
  4. 顶层 = 自己只读；底层 = 指向对象只读
  5. constexpr = 强制编译期算出

示例

#include <iostream>
int main() {
    const int ci = 42;
    const int &cr = ci;

    const int *p = &ci;
    int j = 0;
    int *const cp = &j;
    *cp = 100;

    constexpr int size = 64;
    char buf[size];

    std::cout << ci << " " << *cp << std::endl;
    return 0;
}

和 C 的区别

const 的声明语法、* 绑定变量名的规则，C 和 C++ 完全一样——这部分 C 的经验直接搬。int *p 还是 int* p 的争论在 C 里就存在，C++ 继承了同样的坑：

对比点 C C++
const int *p vs int *const p 一样 一样
int *a, b 的 b 是 int 不是指针 一样（经典坑） 一样
const 全局链接性 外部链接 内部链接（见 2.4.1）

给 C 程序员的关键提醒： const 指针四种形态的口诀（const 在 * 左管内容、右管指针）C 和 C++ 完全通用，你的 C 经验直接适用。唯一新增的是 C++ 的引用——const int& 类似 const int *const（绑定固定 + 只读）。

2.4

.3 constexpr 详解

本节讲什么

constexpr（constant expression，常量表达式）C++11 引入，强制值在编译期计算完成。可修饰变量、函数、构造函数。与 3.5.1 数组维度 高频考点直接相关。

核心定义

const constexpr
核心 只读，不可修改 只读 + 编译期求值
值何时确定 编译期或运行期均可 必须编译期
典型用途 禁止修改的运行期配置 数组长度、模板实参、case 标签、static_assert

一句话：需要编译期常量时用 constexpr；仅禁止修改用 const。

一、constexpr 修饰变量（数组章节高频）

硬性规则

  1. 定义时必须立刻初始化
  2. 初值必须是纯编译时常量表达式（字面量、其他 constexpr 变量、constexpr 函数返回值）
  3. 类型须为字面类型（int、double、char、数组、constexpr 构造的类对象等）
  4. 变量自带 const 属性，不能修改

合法 / 非法

// ✅ 合法
constexpr int size = 10;
constexpr int total = size * 5;
int arr[size];              // 数组维度须编译常量

// ❌ 非法
int n = 5;
// constexpr int sz = n;   // n 是运行期变量

int getNum() { return 10; }
// constexpr int a = getNum();  // 非 constexpr 函数，不行

const vs constexpr 作数组长度（必考）

// 情况 1：const + 字面量 → 可当编译常量（C++ 允许）
const int c1 = 20;
int arr1[c1];               // ✅ 多数编译器合法

// 情况 2：const + 运行期值 → 不是编译常量
const int c2 = rand();
// int arr2[c2];            // ❌ c2 运行期才确定

// constexpr：无论如何必须编译期
constexpr int ce = 30;
int arr3[ce];               // ✅ 永远合法

// 3.5 典型题：不推荐用运行期 const 当数组长度
int n = 10;
const int sz = n;
// int a[sz];               // 标准 C++ 非法；部分扩展可能放过
constexpr int arr_size = 12;
int arr[arr_size] = {1, 2, 3};  // ✅ 推荐

总结：数组长度、模板参数 → 直接用 constexpr，别赌 const 初值是不是字面量。

二、constexpr 修饰函数

基础特性

  1. 参数、返回值一般为字面类型
  2. 两用： - 传入 constexpr 实参 → 编译期计算 - 传入普通变量 → 退化为普通运行期函数
  3. 函数隐式 inline

C++11：函数体极严

通常只能一条 return，不能 if、循环（复杂逻辑不行）：

constexpr int square(int x) {
    return x * x;   // C++11 典型：单行 return
}

C++14：大幅放宽

允许 if、for、局部变量、递归：

constexpr int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
}
constexpr int f = fact(5);   // 编译期算出 120

用于数组长度

constexpr int calcLen(int a, int b) {
    return a + b;
}
constexpr int len = calcLen(4, 6);
int nums[len];               // ✅

三、constexpr 构造函数（字面类）

自定义类加 constexpr 构造，可在编译期创建对象：

struct Point {
    int x, y;
    constexpr Point(int a, int b) : x(a), y(b) {}
};
constexpr Point p(2, 3);     // 编译期对象

四、const 与 constexpr 速查表

特性 const constexpr
核心语义 只读 编译期可计算 + 只读
初始化时机 编译/运行均可 强制编译期
能否作数组长度 仅当初值为字面量等编译常量时 一定可以（若定义合法）
修饰函数 成员函数（this 只读） 普通/成员/构造函数
rand() 等运行期初始化 const int a = rand(); ✅ ❌ 完全禁止
隐含属性 无 变量自带 const；函数自带 inline

五、拓展：C++17 if constexpr

编译期分支，不满足条件的分支不参与编译（无运行开销）。详见 4-C++17 ch10 编译期 if：

template<int N>
void func() {
    if constexpr (N > 10) {
        // N<=10 时整段丢弃
    } else {
        // N>10 时丢弃
    }
}

六、使用规范（教材建议）

  1. 需要编译期常量（数组大小、模板参数、static_assert）→ constexpr
  2. 仅禁止修改、不需编译期计算 → 普通 const
  3. 常量数学工具函数 → 写成 constexpr，编译/运行两用
  4. 局部数组尺寸不要用普通变量；用 constexpr 保证标准 C++ 合法（见 3.5）

背诵极简版

constexpr = 编译期常量；const 只保证只读
数组长度、模板参数 → constexpr，别赌 const
constexpr 变量：定义即初始化，字面类型，自带 const
constexpr 函数：C++11 单行 return；C++14 可 if/递归
const 字面量初始化可当数组长度；const rand() 不行

示例

#include <iostream>

struct Point {
    int x, y;
    constexpr Point(int a, int b) : x(a), y(b) {}
};

constexpr int calcLen(int a, int b) {
    return a + b;
}

int main() {
    constexpr int arr_size = 12;
    int arr[arr_size] = {1, 2, 3};

    constexpr int len = calcLen(4, 6);
    int nums[len]{};

    constexpr Point origin(0, 0);

    std::cout << arr_size << " " << len << "\n";
    return 0;
}

和 C 的区别（constexpr 是 C++ 独有）

C 没有 constexpr。 C 要编译期常量只能用 #define 宏或 enum，都有缺陷：

对比点 C C++
编译期常量 #define SIZE 10 或 enum { SIZE = 10 }; constexpr int SIZE = 10;
宏的缺点 无类型、无作用域、调试难见 constexpr 有类型、有作用域
编译期函数 ❌ 没有 ✅ constexpr int fact(int n)
if constexpr ❌ ✅ C++17 编译期分支

给 C 程序员的关键转变： 1. C 的 #define MAX 100 换成 C++ 的 constexpr int MAX = 100;——有类型、有作用域、调试可见 2. C 的 enum { SIZE = 10 }; 换成 constexpr int SIZE = 10; 3. C++ 的 constexpr 函数能在编译期算（ factorial、查表），C 做不到（只能宏或模板元编程） 4. 数组大小：C89 只能 #define/enum，C99 变长数组是运行期；C++ 用 constexpr 保证编译期

/* C：编译期常量只能用宏或 enum */
#define MAX_ORDERS 10000          /* 无类型，宏替换 */
enum { BUF_SIZE = 1024 };         /* 有类型但只能整型 */
int arr[BUF_SIZE];

// C++：constexpr 有类型、有作用域、还能是函数
constexpr int MAX_ORDERS = 10000;
constexpr int BUF_SIZE = 1024;
constexpr int fact(int n) { return n <= 1 ? 1 : n * fact(n-1); }
constexpr int x = fact(5);        // 编译期算出 120
int arr[BUF_SIZE];

自测题

1（选择） 下面哪个 C++ 写法合法？

int n = 5;
constexpr int a = n;
  • A. 合法，a = 5
  • B. 非法，n 是运行期变量

2（判断） const int x = 42; int arr[x]; 在 C++ 中一定合法。

3（应用） 把 C 的 #define DOUBLE_BUF 2048 改成 C++ 的等价写法，并说明好处。

参考答案

  2. 不一定。const int x = 42;（字面量初始化）可当编译期常量，int arr[x] 合法；但 const int x = rand();（运行期值）不行。constexpr int x = 42; 才保证一定合法。所以数组大小优先用 constexpr。
  3. constexpr int DOUBLE_BUF = 2048;。好处：有类型（int）、有作用域（不污染全局）、调试可见符号、不会像宏那样被多次替换出问题。

2.5

处理类型

本节讲什么

针对程序中越来越复杂的类型，介绍简化类型管理的几种方法：使用 typedef 和 C++11 的 using 定义类型别名；使用 auto 让编译器自动推断变量类型；使用 decltype 根据表达式推断要定义的变量类型，而不实际计算表达式的值。

要点

  • 类型别名：using Str = std::string（C++11）；typedef 为 C 遗留
  • using 声明：using std::string; 把名字引入当前作用域（与别名不同）
  • using ≠ #include：前者只改名称可见性；后者预编译文本拷贝
  • 同名冲突 A::ABC / B::ABC：禁全局 using namespace；双库并存用全限定名
  • auto：必须初始化；默认丢弃顶层 const 和引用
  • auto&：保留 const/引用，绑定原对象；const auto& 只读、零拷贝
  • decltype(expr)：只分析类型，不执行表达式；完整保留 const/引用
  • decltype((var))：双层括号 → 左值引用

一、类型别名：typedef / using

1. typedef（C 语言遗留）

typedef int wages;
typedef double WageArr[20];   // WageArr 等价 double[20]
typedef char* CharPtr;

缺点：顺序反直觉；不支持模板别名；复合 const 易踩坑：

typedef char* CharPtr;
const CharPtr p = nullptr;   // 等价 char* const p（常量指针），不是 const char*

2. using（C++11 推荐）

using wages = int;
using IntVec = std::vector<int>;
using CharPtr = char*;

优势：左右对应直观；支持模板别名；数组、指针、const 组合更清晰。

template<typename T>
using Vec = std::vector<T>;   // typedef 做不到

3. using 声明：引入命名空间里的名字（C++98 即有）

与上面的类型别名不同，这是 using 声明（using declaration）——把某个命名空间里的已有名字引入当前作用域，省掉长前缀：

#include <string>

using std::string;    // 之后可直接写 string，不必 std::string

string name = "book"; // OK

#include <iostream>

using std::cin;       // 把 std 里的 cin 拉到当前作用域
using std::cout;

int a;
cin >> a;             // 等价 std::cin >> a
cout << a << '\n';    // 等价 std::cout << ...

还可一次引入多个（C++17）：

using std::cin, std::cout, std::endl;

using namespace std; 是把整个 std 里所有名字一次性引入当前作用域——小文件省事，大工程易命名冲突（见下节 HFT 习惯）。

4. 两种 using 对比（本质都是「引入名称」）

类型别名 using T = U using 声明 using ns::name
标准 C++11 C++98
作用 给类型起新名字 把已有名字引入当前作用域
例子 using Str = std::string; using std::string;
之后写法 Str s; string s;（省略 std::）

Rust 对照里的 type 只对应左边这一列（类型别名），不对应 using std::string 这种声明。

using 与 #include 的本质区别

两者常被一起写，但机制完全不同：

#include using / using 声明
阶段 预编译（预处理） 编译（作用域 / 类型系统）
做什么 把头文件内容原封不动拷贝进当前文件（文本替换） 只声明名称可见，不拷贝任何实现代码
例子 #include <iostream> 引入整个 iostream using std::cout; 仅让 cout 在当前作用域可用
重复 同一头文件多次包含需守卫（见 2.6.5） 同一 using 声明可写多次（有作用域规则）

典型组合（见 1.2 初识输入输出）：

#include <iostream>      // 预编译：把 iostream 声明/定义文本贴进来
using std::cin;
using std::cout;
using std::endl;

int main() {
    int a;
    cin >> a;
    cout << "hello" << endl;
    return 0;
}

#include 解决「有没有这份代码/声明」；using 解决「名字要不要写全限定名」。
与 2.2.4 #include 与 extern 也不同：extern 声明变量实体在别的 .cpp，using 不涉及跨文件链接。

HFT / 工程习惯

原则：头文件会被多个 .cpp #include，在头里写 using 等于把污染扩散到整个工程。

写法 头文件 .h 源文件 .cpp

using std::string; 等确定不冲突的声明 ❌ 不推荐 ✅ 简化常用名

  • 稳定性 + 可读性（HFT 核心）：读代码的人应能一眼定位符号来自哪个模块
  • 常见做法： 1. 头文件 / 对外接口：全限定名，或仅在 .cpp 使用命名空间别名 2. .cpp 内：using std::string;、using std::cout; —— 只引入本文件确定不会冲突的名字 3. 多个第三方库重名（如 A::Order 与 B::Order）：全限定名，从根源避免冲突 4. 长命名空间：namespace md = market_data::v2; → 写 md::Order，比全路径短，比 using namespace / 裸 using Order 更清晰 5. 类型别名 using OrderId = uint64_t;（给类型起名，不是 using 声明）

    md::Book book = o.book();   // 比 market_data::v2::Order 简洁，仍带来源信息
}

不同命名空间里的同名符号（A::ABC vs B::ABC）

命名空间要解决的核心问题就是：多个库/模块里可能出现同名类型、函数、变量。例如 A::ABC 与 B::ABC 同时存在时，不能再写：

using namespace A;   // ❌ 与 B 里同名符号大面积冲突
using namespace B;

三种精准控制方式：

方式 写法 适用
1. 只引入某一个 using A::ABC; 当前作用域只用 A 的 ABC，且不要再 using B::ABC;
2. 全限定名 A::ABC / B::ABC 两个都要用 —— HFT 最常用，一眼看出来自哪个模块
3. 命名空间别名 namespace A_alias = long_namespace_A; 长命名空间缩短前缀，仍保持清晰

方式 1 示例（本文件/本函数只关心 A 的 ABC）：

namespace A { struct ABC { /* ... */ }; }
namespace B { struct ABC { /* ... */ }; }

using A::ABC;          // 当前作用域里 ABC = A::ABC

ABC obj;               // 即 A::ABC
// B::ABC b;           // 仍须写 B::ABC，不能裸写 ABC 当 B 的

同一作用域不能同时 using A::ABC; 和 using B::ABC; —— 两个声明会把同一个裸名 ABC 拉进来，编译器报重复 / 歧义。需要同时用两个时，必须用方式 2：

void route() {
    A::ABC a_obj;
    B::ABC b_obj;      // 全限定名区分，复杂策略逻辑里不易搞混
}

方式 3：命名空间别名（C++11，与类型别名 using T = U 不同语法）：

namespace market_data::v2 {
    struct Order { /* ... */ };
}

namespace md = market_data::v2;   // 短别名，保留模块信息

md::Order o;                      // 比全路径短；比 using namespace 安全

工程选型一句话（HFT）

单库、常用、不冲突     →  .cpp 里 using std::string;
多第三方库、可能重名   →  A::Order / B::Order 全限定名（最稳）
路径太长但来源单一     →  namespace md = market_data::v2;  再用 md::Order
头文件 / 对外 API      →  全限定名或不在头里写 using

HFT 偏好：多库并存、策略逻辑复杂时，默认全限定名；using 声明只在本 .cpp 简化确定无冲突的常用名；长路径用命名空间别名兼顾简洁与可读。

详见 ch3 3.1 命名空间的 using 声明、ch18 18.2 命名空间。

二、auto 自动类型推导（C++11）

基础规则

必须初始化；根据等号右侧推导；默认丢弃顶层 const 和引用。

auto i = 42;        // int
auto d = 3.14;      // double
const int ci = 10;
auto x = ci;        // int（顶层 const 被丢弃，拷贝）

auto& — 保留引用与底层 const

const int ci = 10;

int a = 1;
auto &ra = a;       // int&

auto* — 指针推导

保留底层 const（指向常量的指针）：

int val = 5;

const int cval = 6;
auto *cp = &cval;       // const int*

三种写法对比

写法 行为 常用场景
auto 值拷贝，丢顶层 const/引用 简单局部变量
auto& 绑定左值，保留 const/引用 需要改原对象或避免拷贝
const auto& 只读引用，零拷贝 范围 for、传参式遍历 
std::vector<std::string> words{"a", "b"};
for (const auto &w : words) { /* 只读，不拷贝 string */ }

三、decltype(expr) 表达式类型推导

只分析表达式类型，不执行计算；完整保留 const、引用。

规则 1：decltype(变量名) — 不加括号

返回变量声明时的完整类型：

int i = 0;
const int ci = 10;
int &ri = i;

decltype(i) a;       // int
decltype(ci) b;        // const int
decltype(ri) c = i;  // int&（引用必须初始化）

规则 2：decltype((变量名)) — 双层括号

(var) 是左值表达式 → 结果为 T&；原变量有 const 则为 const T&：

int x = 10;
decltype((x)) rx = x;      // int&

const int cx = 20;
decltype((cx)) rcx = cx;   // const int&

其他表达式

int arr[5];
decltype(arr) arr2;         // int[5]

int num = 1;
decltype(num + 5) res;      // int（算术表达式为右值，无引用）

是否必须初始化 ✅ 必须 ❌ 不必（但引用类型须绑定）

别名：  using T = ...  优于 typedef
using 声明：using std::x;  引入名字，不是别名

和 C 的区别（重点：auto/decltype 是 C++ 独有利器）

这节是 C→C++ 的重大升级区——C 只有 typedef，C++ 多了 using 别名、auto 推导、decltype：

特性 C C++
typedef ✅ ✅（兼容，但推荐 using）
using T = U 别名 ❌ ✅ C++11，支持模板别名
auto 老含义：存储类说明符（自动存储期，局部变量默认） C++11 起改为类型推导
decltype ❌ ✅ C++11
using std::string 声明 ❌（无命名空间） ✅

auto 的含义巨变（最重要）： C 里 auto int x; 表示"自动存储期的 int"（和普通局部变量一样，几乎没人写）；C++11 把 auto 重新定义为"让编译器推导类型"。同一个关键字，C 和 C++ 含义完全不同。

/* C：auto 是存储类说明符（几乎不用，局部变量默认就是 auto）*/
auto int x = 5;   /* 等价 int x = 5; C 里合法但多余 */

// C++11：auto 是类型推导
auto x = 5;        // 推导为 int
auto it = v.begin(); // 推导为 vector<int>::iterator，不用写长类型

typedef 在 C++ 里的坑（C 程序员注意）：

typedef char* CharPtr;
const CharPtr p = nullptr;   // 等价 char* const p（常量指针），不是 const char*！

typedef 做别名时，const 修饰的是别名整体（指针本身），不是指向的对象。C++ 用 using 更直观，但这个坑 using 也有。直接用 char* const 或 const char* 写清楚最安全。

给 C 程序员的关键转变： 1. typedef 能用但推荐换 using（using IntVec = std::vector<int>; 比 typedef 直观） 2. auto 在 C++ 是推导，不是存储类——忘掉 C 的 auto 含义 3. auto 丢顶层 const/引用，要保留用 auto&/const auto& 4. decltype 能精确复刻类型，decltype((x)) 双括号变左值引用（C 没有）

2.6

.1 Sales_data 入门与聚合

本节讲什么

《C++ Primer》入门三成员 Sales_data、什么是聚合、花括号与部分赋值。

一、Sales_data 入门三成员（课本经典）

标准写法（struct 定义末尾必须有分号）：

#include <string>

struct Sales_data
{
    std::string bookNo;              // 书籍 ISBN 编号
    unsigned units_sold = 0;         // C++11 类内默认：销售册数
    double revenue = 0.0;            // C++11 类内默认：总销售额
};  // ← 分号极易漏，漏了编译报错
成员 类型 类内初值 默认构造后
bookNo std::string 无 空串 ""
units_sold unsigned = 0 0
revenue double = 0.0 0.0

什么是聚合（Aggregate）？

聚合是 C++ 对一类特殊 class / struct 的称呼——本质上就是只装数据、没有复杂行为的类型，成员布局简单透明，编译器可以像处理 C 结构体一样处理它。

一句话：满足聚合条件的类型，可以用花括号 {} 按成员声明顺序，直接把各字段一次性初始化完。

笔记里常说的「无自定义构造时，合成默认构造 + 聚合初始化」，拆开理解是：

写法 发生什么
Sales_data item; 编译器合成默认构造函数，按类内初值 / 默认初始化填成员
Sales_data data = {"978-7-115-38345-2", 23, 31}; 聚合初始化：不调用自定义构造，按顺序给 bookNo、units_sold、revenue 赋值

二者都适用于入门版，因为没有用户写的构造函数——第一种靠合成默认构造，第二种靠聚合规则。

成为聚合须同时满足（C++11/17 入门口径）：

条件 入门版 Sales_data
无 private / protected 非 static 数据成员 ✅ 全 public（struct 默认）
无用户提供的构造 / 析构 / 拷贝或移动赋值函数 ✅ 只有编译器合成的
无私有或 protected 基类 ✅ 无继承
无虚函数 ✅

常见误解：「用了 C++11 类内初始值就不是聚合」——错。units_sold = 0、revenue = 0.0 不妨碍聚合身份；入门版 有类内初值且仍是聚合。真正破坏聚合的是：用户自定义构造、private 成员、继承、虚函数等。

入门版三个成员全部满足 → 典型聚合类型：

Sales_data data = {"978-7-115-38345-2", 23, 31};
// bookNo      ← "978-7-115-38345-2"
// units_sold  ← 23
// revenue     ← 31.0（隐式转为 double）

等价写法：Sales_data d{"...", 25, 22.5}; 或 Sales_data d = {"...", 25, 22.5};

部分赋值（C++11 起）

花括号里的值不必写满所有成员；没写到的成员走类内默认值（若有）或默认初始化：

Sales_data partial = {"book123"};
// bookNo      ← "book123"
// units_sold  ← 0      （类内 = 0）
// revenue     ← 0.0    （类内 = 0.0）

{} 与类内初值：花括号里已给出的值覆盖类内默认；未给出的成员才用类内 = 0 / = 0.0（bookNo 无类内初值则默认空串）。

HFT 场景：行情快照、订单委托、成交回报等纯数据「容器」，用 {} 一次性或部分填字段，比调构造函数更简洁，初始化路径也短：

struct Order {
    uint64_t order_id = 0;
    double   price    = 0.0;
    int      qty      = 0;
};

Order o{10086, 10.05, 500};   // 全填：按声明顺序
Order o2{10086};              // 部分填：price、qty 走类内 0

一旦「破坏」聚合——加入自定义构造、private 成员、基类或虚函数（见下文完整版）——就不能再用 {} 按顺序填成员，须改用 Sales_data("...", n, p) 等构造函数。

入门版 Sales_data  ──加自定义构造/私有/虚函数──►  完整版：不再是聚合
     │                                              │
     └─ {} 按顺序初始化                              └─ 构造函数初始化

和 C 的区别

struct 是 C 程序员的老朋友，但 C++ 的 struct 比 C 的多了几个能力：

对比点 C C++
struct 成员 只有数据 数据 + 函数（和 class 一样，只是默认 public）
类内初始值 ❌ 没有 ✅ C++11 unsigned n = 0;
花括号聚合初始化 ✅（C99 designated init） ✅
部分初始化 C99 要 .field = val {val} 按顺序，未给的走类内默认

给 C 程序员的关键提醒： 1. C++ 的 struct 和 class 几乎一样（唯一区别：默认访问权限，struct 默认 public，class 默认 private）。C 的 struct 只有数据。 2. 类内初始值是 C++11 新能力——C 的 struct 不能在定义里写 int n = 0;，C++ 可以。这让"定义即有默认值"变得简单。 3. C++ 的花括号初始化 {} 比更严格（禁止窄化：int x{3.14} 报错），C 的 {} 初始化相对宽松。

/* C：struct 不能有类内初始值，要手动初始化 */
struct Order {
    int id;
    double price;
    int qty;
};
struct Order o = {1, 10.5, 100};   /* 必须全填或靠 =0 规则 */

// C++：类内初始值 + 部分初始化
struct Order {
    int id = 0;
    double price = 0.0;
    int qty = 0;
};
Order o{1};   // 只填 id，price/qty 走类内默认 0

2.6

.2 类内初始值

本节讲什么

C++11 就地成员初始化：语法、优先级、与聚合的关系。

二、C++11 类内初始值（in-class initializer）

语法限制

只能用 = 或 花括号 {}，不能用圆括号 ()（会被当成成员函数声明）：

unsigned units_sold{0};   // ✅
unsigned units_sold = 0;  // ✅
unsigned units_sold(0);   // ❌ 编译器误判为成员函数

初始化优先级

构造函数初始值列表 > 类内默认值 > 默认初始化

struct S {
    int x = 100;
    S() : x(1) {}   // 最终 x 为 1
};

对入门版 Sales_data：

  • 构造函数没写某成员 → 用类内 = 0 / = 0.0
  • bookNo 无类内初值 → 默认初始化为空串

无自定义构造函数时

编译器生成合成默认构造函数，自动应用类内初始值：

Sales_data item;
// item.bookNo     == ""
// item.units_sold == 0
// item.revenue    == 0.0

类内初值 ≠ 丧失聚合（重要纠正）

网上常见说法：「只要有类内初始值 {} / =，就不再是聚合」——不符合 C++11/17 标准。

因素 是否破坏聚合
类内初始值 units_sold{0}、revenue = 0.0 ❌ 不破坏
用户自定义构造函数 ✅ 破坏（完整版 Sales_data 因此不是聚合）
private / protected 成员 ✅ 破坏
基类 / 虚函数 ✅ 破坏

极简对比（可复制编译，g++ -std=c++11）：

#include <string>

// ① 有类内初值 —— 仍是聚合（Primer 入门版）
struct WithDefaults {
    std::string bookNo;
    unsigned    units_sold = 0;
    double      revenue    = 0.0;
};
WithDefaults a = {"978-7", 23, 31};   // ✅ 聚合初始化
WithDefaults b = {"book123"};         // ✅ 部分赋值，其余走类内默认

// ② 无类内初值 —— 也是聚合
struct NoDefaults {
    std::string bookNo;
    unsigned    units_sold;
    double      revenue;
};
NoDefaults c = {"978-7", 23, 31.0};   // ✅ 聚合初始化

// ③ 有自定义构造 —— 不是聚合（与有没有类内初值无关）
struct WithCtor {
    WithCtor() = default;
    WithCtor(std::string s, unsigned n, double r)
        : bookNo(s), units_sold(n), revenue(r) {}
    std::string bookNo;
    unsigned    units_sold = 0;
    double      revenue    = 0.0;
};
// WithCtor x = {"978-7", 23, 31};     // ❌ 不是聚合，不能这样写
WithCtor y("978-7", 23, 31);          // ✅ 用构造函数

结论：类内写 变量{值} 不会让结构体丧失聚合；自定义构造函数才会（完整版即因此改用 Sales_data(s, n, p)）。

和 C 的区别（类内初始值是 C++11 独有）

C 的 struct 不能在定义里给成员默认值。 这是 C→C++ 一个明显的能力提升：

对比点 C C++
struct S { int x = 0; }; ❌ 编译错误 ✅ C++11
默认值实现 要写初始化函数或 memset 类内直接写 = 0
初始化优先级 无（手动全填） 构造函数初始值列表 > 类内默认 > 默认初始化

给 C 程序员的关键提醒： 1. C 里要给 struct 默认值，得写 void init(S* s) { s->x = 0; } 或 memset；C++ 直接在定义里写 int x = 0;，简洁且不易漏。 2. 类内初始值用 = 或 {}，不能用 ()（会被当成成员函数声明）。 3. 有自定义构造函数后，类内初始值是"兜底"——构造函数初始值列表没写的成员才用类内默认。

/* C：struct 无默认值，要手动初始化 */
struct Order { int id; double price; };
void init_order(struct Order* o) { o->id = 0; o->price = 0.0; }

// C++：类内初始值，定义即有默认
struct Order { int id = 0; double price = 0.0; };
Order o;   // id=0, price=0.0，不用写 init 函数

        : bookNo(s), units_sold(n), revenue(p * n) {}

{
    units_sold += rhs.units_sold;
    revenue += rhs.revenue;
    return *this;
}

double Sales_data::avg_price() const
{
    if (units_sold)
        return revenue / units_sold;
    return 0;
}

Sales_data::Sales_data(std::istream& is) { read(is, *this); }

std::istream& read(std::istream& is, Sales_data& item)
{

    is >> item.bookNo >> item.units_sold >> price;

}

       << item.revenue << " " << item.avg_price();

{

能力 C C++（本例）
数据成员 ✅ ✅

构造函数 ❌ ✅ 多个重载

给 C 程序员的关键解读： 1. 成员函数：isbn() 直接写在 struct 里。C 要写 char* get_isbn(struct Sales_data* this)，C++ 把 this 隐式化了。 2. 构造函数：Sales_data(s, n, p) 替代 C 的 init 函数。创建对象时自动调用，不会忘初始化。 3. return *this：combine 返回 *this（当前对象的引用），支持链式调用 a.combine(b).combine(c)。C 做不到这种风格。 4. friend：让外部函数 read/print 能访问 private 成员。C 没有 private，也不需要 friend。

    lhs->units_sold += rhs->units_sold;
    lhs->revenue += rhs->revenue;
}

    std::string isbn() const { return bookNo; }
    Sales_data& combine(const Sales_data& rhs) {
        units_sold += rhs.units_sold;
        return *this;   // 链式调用

};

四、友元（friend）与友元前置声明

友元的含义

把全局函数声明为类的友元：

  • 正常情况：外部全局函数只能访问类的 public 成员，碰不到 private / protected 字段
  • 写 friend 函数名 之后：该全局函数可直接读、写类的私有成员，不受访问权限限制
class Secret {
    friend void peek(const Secret&);   // peek 可以访问 private
private:
    int code = 42;
};
void peek(const Secret& s) { /* 可直接用 s.code */ }

完整版 Sales_data 中 read / print / add 是全局 IO 工具，通过 friend 访问成员（教材惯例；入门版成员本为 public）。

友元前置声明规则

函数须先在 struct 定义前写函数原型（前置声明），再在 struct 内写 friend，否则：

  • struct 之前的代码（如流构造函数）找不到 read 等名字
  • 头文件分离时，其他 .cpp 看不到全局接口

完整版代码在 struct Sales_data 之前有三行：

// 友元前置声明
Sales_data add(const Sales_data&, const Sales_data&);
std::ostream& print(std::ostream&, const Sales_data&);
std::istream& read(std::istream&, Sales_data&);

随后在结构体内部用 friend 把上述全局函数指定为友元，允许它们访问非公有成员（本例成员虽为 public，但 read 需写 item.revenue 等，教材仍走友元 IO 模式）。

什么是友元前置声明

前置声明：在 struct/class 定义完成之前，先在全局域写出友元函数的原型。编译顺序：

  1. 读到三行函数原型 → 记住签名；Sales_data 作为返回/参数类型被前向声明为不完整类型（见下节「类的前置声明」）
  2. 读到 struct Sales_data { ... friend add; ... } → friend 与前面全局原型绑定，授予访问权限
  3. 在 struct 之后写函数定义（函数体）

为什么必须有？（Sales_data 的两个核心原因）

1. 函数原型写在 struct 定义之前，签名里已用到 Sales_data

教材把 add / read / print 的声明放在 struct 上面。没有这三行，就无法在定义 struct 之前写出合法函数原型；后面的

Sales_data::Sales_data(std::istream& is) { read(is, *this); }

也要求 read 在此刻已经声明。

2. 头文件 / 源文件分离：对外暴露 IO 工具接口

  • .h：三行前置声明 + struct 定义（含 friend）
  • .cpp：add / read / print 的函数体

其他 .cpp（如 main.cpp）只 #include "Sales_data.h" 即可调用 print(cout, item)，不必关心实现细节。

两种友元写法对比

写法 是否需要类前前置声明 类外能否调用
全局友元 + 类外定义（Sales_data） ✅ 需要 ✅
类内 friend 后直接写函数体 ❌ ❌（几乎仅教学用）

情况 1：全局友元（教材用法）

Sales_data add(const Sales_data&, const Sales_data&);

struct Sales_data {
    friend Sales_data add(const Sales_data&, const Sales_data&);
};

Sales_data add(const Sales_data& lhs, const Sales_data& rhs) { /* ... */ }

函数属于全局域，不属于 Sales_data；业务代码、main、其他文件都要调用 → 必须类前声明。

情况 2：类内定义友元（不需前置声明，类外不可用）

struct Test {
    friend void show(Test t) {
        std::cout << t.val;
    }
private:
    int val = 10;
};
// show(t);  // 类外调用：未声明

关键语法规则

  1. friend 声明授予访问权，但不等于完整的工程接口布局；教材在 struct 前写全局原型，是为了类型前向声明 + 分离编译。
  2. C++11 起，非定义的 friend 声明会把函数名注入外围命名空间；因此「只有 friend、没有类前原型」时，struct 之后的 main 里调用 add(a,b) 有时能通过。但 Sales_data(std::istream&) 依赖的 read 必须先声明，且头文件惯例仍要求三行写在 struct 前。
  3. friend 写在 public / private 均可，只影响类成员访问，不影响友元本身。
  4. print / read 是全局 IO 工具，主程序与其他模块频繁调用 → 必须出现在头文件的全局声明区。

错误示范：删掉前置声明 + 流构造函数

下面代码删掉 struct 前的三行声明，并保留依赖 read 的构造函数实现 —— 必然编译失败（read 未声明）：

#include <iostream>
#include <string>

struct Sales_data
{
    Sales_data() = default;
    Sales_data(std::istream& is) { read(is, *this); }  // ❌ read 尚未声明

    friend Sales_data add(const Sales_data&, const Sales_data&);
    friend std::ostream& print(std::ostream&, const Sales_data&);
    friend std::istream& read(std::istream&, Sales_data&);

正确做法：在 struct 前补上 read（及 add、print）的函数原型，或把 Sales_data(std::istream&) 的定义挪到 struct 之后、且放在 read 声明之后。

类的前置声明：普通 vs 有源

易混提醒：有源 = 有无的「有」+ 源代码的「源」（implementation 在 .cpp 里）；与上一节 友元（friend，朋友的「友」）无关，勿写成「友源」。

这里的前置声明指类型（class / struct），与上文友元函数的前置声明是两层概念。

普通前置声明——头文件里只写类型名，不暴露成员：

class Sales_data;   // 或 struct Sales_data;

此时 Sales_data 是不完整类型，编译器只知道「有这么个类型」，不知道大小和成员。因此只能用于：

  • 指针 / 引用：Sales_data* p;、Sales_data& r;
  • 函数参数 / 返回值（传引用或指针）

不能按值定义对象、不能访问成员、不能 sizeof(Sales_data)——因为定义尚未可见。

有源前置声明——语法同样是 class Sales_data;，但含义不同：

「有源」：这个声明不是空泛的类型占位，而是已经和具体实现源文件绑定——类的完整定义在某个 .cpp（或静态库 / 动态库）里，且该实现会被链接进当前工程。

典型布局：

文件 内容
Sales_data.h class Sales_data; 或只含指针成员的接口；不 #include 重依赖头
Sales_data.cpp class Sales_data { ... }; 完整定义 + 成员函数实现
main.cpp #include "Sales_data.h"，通过指针/引用或 .cpp 提供的工厂函数使用

编译期：消费方 .cpp 只看到不完整类型 → 不必拉入 Sales_data 的全部成员与依赖头，缩短编译时间。
链接期：链接器在 Sales_data.o / .lib 里找到完整实现 → 调用仍然正确。

OtherModule.h          Sales_data.h              Sales_data.cpp
  class Sales_data;  →  对外接口 / 指针成员   →   完整 class { ... }
  （有源：知道 .cpp      （编译 Other 时不          （单独编译、链入工程）
   会被链进来）           展开 Sales_data 内部）

HFT 大型工程里常用：头文件尽量前置声明 + 指针/引用（或 PIMPL），把重实现藏在 .cpp 或库里，减少头文件依赖扇出（见 Effective C++ 条款 31）。

与 Sales_data 教材示例的关系：Primer 2.6 的写法是在同一头文件里给出完整 struct Sales_data { ... }，属于「声明 + 定义都在头文件可见」的入门路径；工程化后会演进为「.h 前置声明或瘦接口 + .cpp 完整定义」的有源模式。

三概念辨析（之前易混的三件事）

概念 是什么 解决什么 彼此关系
友元 friend 把全局函数变成类的「自己人」 访问权限：外部函数可读 private 成员 —
友元前置声明 struct 前写 add/read/print 函数原型，struct 内写 friend 编译顺序 + 头文件分离；类外能调用友元函数 只和 friend 函数有关
有源前置声明 .h 里 class Sales_data;，完整定义在已链入的 .cpp 减头文件依赖、缩短编译 和 friend 无关；有=有无的「有」，勿写成「友源」
类内初始值 成员写 = 0 或 {0} 统一成员默认值 不破坏聚合（见 2.6.2 对比代码）
聚合 纯数据 struct，无用户自定义构造等 支持 {} 按顺序 / 部分初始化 与类内初值可共存；自定义构造才破坏

一句话总结：

  1. friend 友元：放开外部全局函数对 private 成员的访问；类外要用的友元函数须 struct 前声明 + struct 内 friend。
  2. 类内 变量{值}：给成员默认值；不会丧失聚合——真正破坏聚合的是自定义构造函数等。
  3. 有源前置声明：class X; + .cpp 有实现，减编译依赖，与 friend 无关。

和 C 的区别

friend 是 C++ 独有——因为 C 没有 private/访问控制，所有成员都公开，自然不需要"授权访问私有成员"的机制。前置声明两边都有：

对比点 C C++
friend ❌ 无（无 private，不需要） ✅ 授权外部函数访问 private
前置声明 struct X; ✅ 有 ✅ 有（一样）
不完整类型用法 指针/引用 指针/引用（一样）
有源前置（减编译依赖） ✅（.h 声明 + .c 实现） ✅（一样，PIMPL 更进一步）

给 C 程序员的关键提醒： 1. C 里所有 struct 成员都公开，谁都能改——没有 friend 的概念，因为不需要"破例"。 2. C++ 有了 private 后，有时需要让某个外部函数"破例"访问私有成员（如 IO 函数 read/print），就用 friend。 3. 前置声明 class X;/struct X; 的用法 C 和 C++ 完全一样——让指针/引用可以用，但定义还没见到时不能 sizeof 或访问成员。

  2. C。前置声明后 Foo 是不完整类型，只能用指针/引用，不能按值定义对象（编译器不知道大小）。Foo* p、Foo& r、函数参数 Foo& 都合法。

七、头文件重复包含保护

方案 1：#ifndef / #define / #endif（标准）

#ifndef SALES_DATA_H
#define SALES_DATA_H
// ...
#endif // SALES_DATA_H
  • 全平台兼容；宏名冲突会误屏蔽 → 建议 项目_模块_文件名_H

方案 2：#pragma once（编译器扩展）

#pragma once
  • 一行、无宏冲突；GCC/Clang/MSVC/ICC 均支持；非 C++ 标准

两种方案的机制差异（为什么 pragma once 更快）

两者效果相同（同一编译单元内头文件只展开一次），但机制完全不同——这决定了大型项目里的预处理速度差异：

#ifndef 守卫 #pragma once
判重依据 宏 SALES_DATA_H 是否已定义 预处理器按文件身份（device + inode）记录「已读过」
第二次 #include 时 文件仍被打开、逐行扫描，内容被 #ifndef 挡掉 直接跳过，不再打开文件
标准地位 纯标准 C/C++，任何编译器可移植 非标准扩展，但主流编译器全支持
典型出错面 宏名撞车（两个库都叫 UTILS_H → 后包含的那个被静默跳过） 无宏名，不存在撞名问题
适用 跨平台库、SDK 头文件、嵌入式 自己的项目、现代本地工程

#pragma once 的四个坑（按 HFT/嵌入式场景重要性排序）

  1. 硬链接 / 构建系统拷贝副本：同一头文件以两个不同 inode 存在时（构建系统 cp 了一份、或不同路径挂载），inode 判重失效 → 当成两个文件包含两次 → 重定义错误。#ifndef 靠宏名，不受路径影响。
  2. 非主流嵌入式工具链：交叉编译遇到厂商私有编译器时 #pragma once 未必支持。所以 Linux 内核、glibc 的头文件全用 #ifndef 守卫——它们必须保证任何编译器都能过。
  3. 符号链接 / 网络文件系统：不同 symlink 指向同一文件，主流编译器能正确解析到同一 inode；但早期 MSVC 和某些 NFS（inode 不稳定）有过翻车记录。
  4. 故意重复包含的场景不能用：X-Macro 技巧（头文件被包含多次、每次展开不同内容）与 #pragma once 互斥。

实践结论

  • 自己的项目（应用层、策略代码）：直接 #pragma once，一行省事；大型项目头文件被传递包含成百上千次，少 open 文件是实打实的预处理提速。
  • 对外发布的库 / SDK 头文件：用 #ifndef 守卫，可移植性优先。
  • 两者可同时写，互不冲突（很多开源库这么干）。

💡 #pragma 本身是标准给编译器留的「私货通道」：标准只定义 #pragma 这个语法壳，后面跟什么（once、pack、comment……）由各编译器自定；遇到不认识的 pragma，标准要求忽略（最多 warning）。所以 #pragma once 虽非标准，写了也不会把代码编译挂掉。

C 语言侧同一主题的完整展开（#include 的查找顺序、尖括号 vs 引号、嵌套包含）见 C 模块笔记 14.4 文件包含。

八、高频易错点

  1. struct 末尾分号不能漏
  2. 类内初值不能用 ()，只能用 = 或 {}
  3. C++11 之前不支持类内 = 0；内置类型若不初始化，局部对象可能是脏值
  4. 头文件勿写普通函数实现 / 全局变量定义 → multiple definition
  5. 加了自定义构造后，聚合 {} 三参数初始化失效，改用对应构造函数
  6. 删掉 struct 前的 add/read/print 原型 → 流构造函数等处 read 未声明
  7. 全局变量在 .h 只写 extern（见 2.2.4 extern）

九、背诵极简版

friend 友元：外部函数访问 private；struct 前原型 + 内 friend
有源前置：class X; + .cpp 链入，减编译依赖，与 friend 无关
类内初值 ≠ 丧失聚合；自定义构造才破坏聚合
聚合：{} 按顺序/部分赋值；入门 Sales_data 有类内初值仍是聚合

和 C 的区别

头文件分离、#ifndef 守卫、.h/.cpp 分工——这些 C 和 C++ 完全一样，C 的经验直接搬。唯一新增的是 C++ 的 struct/class 能放成员函数：

对比点 C C++
.h/.c 分离 ✅ ✅（一样，.cpp 替代 .c）
#ifndef 守卫 ✅ ✅（一样）
#pragma once ✅（主流编译器） ✅（一样）
头文件放什么 函数声明、struct 定义、extern 类声明、函数声明、extern、模板、inline
struct 末尾分号 必须有 必须有（一样）

给 C 程序员的关键提醒： 这部分几乎零差异。.h 放声明、.cpp 放实现、#ifndef 守卫——C 怎么做 C++ 就怎么做。多出来的只是 C++ 的 class/struct 能有成员函数，实现写在 .cpp 里要带 Class:: 前缀。

  1. B。int g = 10; 是定义，头文件被多文件包含会重定义。A 是 extern 声明（安全），C 是函数声明（安全），D 是前置声明（安全）。

本节讲什么

回顾第 2 章核心内容，建立完整知识框架。第 2 章是 C→C++ 转变的关键章——内置类型和 C 几乎一样，但引用、const 链接性、auto/decltype、类内初始值都是 C++ 的新能力。

第 2 章术语表（带 C 对照）

术语 含义 C 程序员视角
内置类型 int/double/char 等 和 C 一样，大小同样因平台而异
变量/常量 int x / const int x const 链接性不同（C++ 内部链接）
引用 int& r = x，别名 C 没有，是 C++ 独有
指针 int* p 和 C 一样，但用 nullptr 替代 NULL
顶层/底层 const 自身只读 / 指向只读 和 C 一样
constexpr 编译期常量 C 没有，C 用 #define/enum
auto/decltype 类型推导 C 没有（C 的 auto 是存储类）
struct 数据 + 函数 + 访问控制 C 的 struct 只有数据

第 2 章给 C 程序员的 8 个要点

  1. 引用是 C++ 独有 —— 函数传参优先 const T&，替代 C 的 const T*
  2. nullptr 替代 NULL —— 类型安全，重载不踩坑
  3. const 全局默认内部链接 —— 头文件可直接放 const 定义（C 不行）
  4. constexpr 替代 #define —— 有类型、有作用域、编译期求值
  5. auto 是类型推导 —— 忘掉 C 的 auto（存储类），C++11 起含义变了
  6. decltype 精确复刻类型 —— decltype((x)) 双括号变引用
  7. 类内初始值 —— struct { int x = 0; }，C 不支持
  8. struct 能有成员函数 —— 和 C 的 struct 本质不同，等于默认 public 的 class

综合示例

#include <iostream>
int main() {
    // 第 2 章综合回顾：引用、指针、auto、decltype
    int x = 10;
    int &rx = x;        // 引用（C++ 独有）
    int *px = &x;       // 指针（和 C 一样）
    rx = 20;

    auto y = 30;                // 类型推导（C++ 独有）
    decltype(y + 1) z = 31;     // 表达式类型推导

    constexpr int N = 100;      // 编译期常量（C 用 #define）
    int arr[N];

    std::cout << *px << " " << z << std::endl;
    return 0;
}

Q1引用绑定
int ival = 1024;

Q2const 与链接性
// file1.cpp
const int buf_size = 512;
// file2.cpp
const int buf_size = 1024;  // 会冲突吗？

两个文件分别定义 const int buf_size，会冲突吗？如果改成 int（非 const）呢？

答案与复习指引

不冲突。 C++ 中 const 变量默认是内部链接的（相当于加了 static），每个文件有自己的副本。

如果改成非 const int： 会冲突——非 const 全局变量是外部链接，两个文件定义同名变量会链接错误。

要共享 const 变量： 在头文件声明 extern const int buf_size;，在一个 .cpp 中定义 extern const int buf_size = 512;。

和 C 的区别： C 中 const 默认是外部链接（和普通变量一样），要加 static 才是内部链接。

Q4指针与 const
const double pi = 3.14;
// double *ptr = &pi;       // A
const double *cptr = &pi;   // B
// *cptr = 42;              // C

A、C 行分别有什么问题？"指向 const 的指针"和"const 指针"的区别是什么？

答案与复习指引

A 行错误： 不能用 double* 指向 const double——否则可以通过指针修改只读变量。 C 行错误： cptr 指向 const double，不能通过它修改值。

两种 const 指针： - const double *p：指向 const 的指针——不能通过 p 改值，但 p 可以指向别的对象（"底 const"） - double *const p = &x：const 指针——p 本身不可改（不能指向别的），但可以通过 p 改 x 的值（"顶 const"）

口诀： const 在 * 左边修饰指向的值，在 * 右边修饰指针本身。

Q5auto 类型推导
int i = 0, &r = i;
auto a = r;       // a 的类型是？
const int ci = i;
auto b = ci;      // b 的类型是？
auto &c = ci;     // c 的类型是？

a、b、c 分别是什么类型？

答案与复习指引
  • a 是 int：r 是 i 的引用，auto 推导时忽略引用性，得到 int
  • b 是 int：ci 是 const int，但 auto 按值推导会忽略顶层 const，得到 int
  • c 是 const int&：引用推导保留底层 const，c 是指向 const int 的引用

关键规则： auto 按值推导时忽略引用和顶层 const；按引用推导时保留底层 const。
