4.1

基础

本节讲什么

表达式、运算符的基本概念：一元/二元/三元运算符、操作数、结果类型、优先级与结合律、求值顺序。这些是后面 4.2–4.12 所有运算符的"地基"。

核心概念

概念 含义 例子
运算符 对操作数做运算的符号 + - *
操作数 运算符作用的对象 a + b 中 a、b 是操作数
一元运算符 1 个操作数 -x、!flag、*p
二元运算符 2 个操作数 a + b、a == b
三元运算符 3 个操作数（C++ 唯一） cond ? a : b
优先级 谁先跟谁结合 a + b * c 中 * 先
结合律 同级从左还是从右算 a - b - c 从左，a = b = c 从右
求值顺序 操作数何时算 f() + g() 中 f/g 调用顺序未指定

三个核心区分（必考）

1. 优先级 ≠ 求值顺序

int f(), g();
int h = f() + g();   // + 决定结合方式，但 f/g 哪个先调？未指定

优先级只决定"谁跟谁结合"（语法结构），不决定运行时求值顺序。f() + g() 中编译器可任意选 f 或 g 先调。

2. 有顺序保证的运算符

运算符 顺序保证
&& \|\| 左侧先，左侧为假/真时右侧不求值（短路）
?: 条件先，只算被选中的分支
, 逗号 从左到右
赋值 = 右侧先于左侧

位运算 & | ^、算术 + - * / 都没有顺序保证。

3. 未定义行为（UB）经典坑

int i = 0;
// i = i++;           // ❌ UB：i 被改两次无序
// v[i] = i++;        // ❌ UB：下标 i 与右侧 i++ 无序
// f(++i, ++i);       // ❌ UB：两个实参求值无序

HFT 工程建议：热路径表达式保持简单，需要顺序就拆成多条语句。

示例

#include <iostream>
int main() {
    int i = 3, j = 4;
    std::cout << i + j << " " << i * j << std::endl;   // 7 12
    return 0;
}

和 C 的区别（表达式基础：C/C++ 几乎一致，C++ 多了几个运算符）

C 程序员对运算符、优先级、结合律这些概念已经熟得不能再熟——C++ 继承了 C 的全部运算符语义，规则几乎一一对应：

对比点 C C++
一元/二元/三元 ✅ 一致 ✅ 一致
优先级表 C 标准定义 C++ 几乎相同，多了 :: .* ->*
结合律 ✅ 一致 ✅ 一致
求值顺序 同样未指定 f()+g() 完全一致
UB 坑（i=i++） ✅ C 也是 UB ✅ 一致
:: 作用域运算符 无 C++ 独有（最高优先级）
.* ->* 成员指针 无 C++ 独有
typeid/static_cast 等 无 C++ 独有（当运算符看）

给 C 程序员的关键提醒： 1. C 学的优先级表 C++ 直接用——99% 相同。新增的 ::、.*、->*、static_cast 等优先级最高或当后缀，日常不太会和算术/逻辑运算符混淆。 2. 求值顺序坑两边一样——f()+g() 在 C 和 C++ 都是未指定顺序，i=i++ 都是 UB。C 程序员的警惕心直接迁移过来。 3. C++ 多了"类成员访问"运算符——obj.member、ptr->member、obj.*pmem、ptr->*pmem。前两个和 C 的 struct 成员访问一致，后两个是 C++ 独有（成员指针，第 7 章详讲）。

常见错误

1. 以为优先级决定求值顺序

int side_effect();
int x = side_effect() + 1;   // 以为 side_effect 一定先调？

错。+ 的优先级决定 1 跟 side_effect() 结合，但 side_effect() 和 1 的求值顺序未指定——编译器可能先算 1（没副作用，无影响）。但如果换成 f() + g()，f/g 哪个先调未指定，若它们有共享状态副作用就 UB。

2. i = i++ 以为"先赋值再自增"

int i = 0;
i = i++;   // ❌ UB，不是"i=0 然后 i 变 1"

C 程序员也踩这个——两边都是 UB。i = i++ 在一次表达式中对 i 修改两次（一次 =、一次 ++），且两次修改无顺序保证。拆成两条语句：int tmp = i; ++i; i = tmp; 或干脆 i = i + 1;。

3. 复杂表达式不写括号，依赖记忆优先级

if (flags & mask == 0) { ... }   // ❌ 等价 flags & (mask == 0)，不是 (flags & mask) == 0

== 优先级高于 &，所以先算 mask == 0 得 bool（0 或 1），再 flags & 0/1。位运算和关系混用必加括号：if ((flags & mask) == 0)。C 程序员也踩这个，C++ 同样坑。

表达式的两个属性：类型 + 值类别（C++11 起）

每个表达式都有两个独立属性：类型（int、int&……）和值类别（lvalue / xvalue / prvalue）。类型决定"能参与什么运算"，值类别决定"有没有身份、能不能被移动"——后者是 C++11 移动语义的地基。

为什么要关心？三件事由它决定：① 能不能取地址（&x）；② 能绑给哪种引用（T& 还是 T&&）；③ 重载决议走拷贝还是移动。

实测：让编译器替你分类

用重载探测（examples/4.1-1-value-categories.cpp，clang 23.1.0 / -std=c++17）：

表达式 值类别 说明
变量 x lvalue 有名字、能取地址
字面量 42 prvalue 纯结果，没身份
x + 1 prvalue 运算结果
std::move(x) xvalue 将亡值，可移动
返回 int 的调用 prvalue 返回类型决定类别
返回 int& 的调用 lvalue 所以能写在赋值左边：g_lref() = 99;（实测生效）
返回 int&& 的调用 xvalue static_cast/move 同理
"abc"（字符串字面量） lvalue 类型是 const char[4]，在只读段，能取地址

返回类型决定值类别，这就是 T& 返回能当左值用的原因：实测 g_lref() = 99; 之后 g_storage 真的变成 99。

decltype 的两条规则（最易记混的一对）

int x = 0;
decltype(x)      // int   —— 对不带括号的"变量名"，给出它的声明类型
decltype((x))    // int&  —— 加了括号就当普通表达式，而变量作为表达式是左值 → T&
decltype("abc")  // const char(&)[4]  ← 不是 const char[4]！字符串字面量是左值

第三行是我实测才发现的：本以为 decltype("abc") 是 const char[4]，实际是数组的引用。要用数组类型本身得写 std::remove_reference_t<decltype("abc")>。

常见错误补充

自测题

  1. 以为 decltype("abc") 是 const char[4]：实测是 const char(&)[4]——字符串字面量是左值，decltype 对左值表达式给出 T&。
  2. 以为返回 T& 的函数不能赋值：g_lref() = 99; 完全合法且生效（实测 g_storage 变成 99）。这也是 v[0] = x、m[key] = v 能工作的原因。

1. 选择题　C++ 中有几个三元运算符？

  • A. 0
  • B. 1
  • C. 2
  • D. 3
答案

B。C++ 唯一的三元运算符是 ?:（条件运算符）。C 也是 1 个，完全一致。

2. 判断题　f() + g() 中，C++ 标准保证 f() 一定先于 g() 调用。

答案

错。+ 操作数的求值顺序未指定——编译器可以任意选 f 或 g 先调。C 也是同样规则。要保证顺序用 ; 拆开：int a = f(); int b = g(); int h = a + b;。

3. 踩坑题　下面这段代码在 C 和 C++ 中行为如何？

int i = 0;
int v[10];
v[i] = i++;
答案

UB（未定义行为），C 和 C++ 都是。v[i] 中的 i（左值下标）和右侧 i++（修改 i）之间没有顺序保证——i++ 可能在算 v[i] 的下标前、后、中间执行，结果不可预测。

修复：拆成两条语句：

v[i] = i;
++i;

或用范围 for / 算法库避开手写下标 + 自增的组合。

4. 应用题　写一个表达式判断"价格 p 在 [low, high] 区间内"，要求用短路求值避免 low > high 时的误判。

答案 
bool in_range = (low <= high) && (low <= p) && (p <= high);

要点： - 用 && 短路：若 low > high，第一个条件 false，后面不算（虽然这里算不算都行，但短路是好习惯） - 拆成三个比较，不用 low <= p <= high（这是 (low <= p) <= high 的常见错误） - C 程序员的 low <= p && p <= high 习惯直接用

错误写法：low <= p <= high —— 等价 (low <= p) <= high，先算 low <= p 得 bool（0/1），再和 high 比，逻辑错。

5. 选择题：以下哪些表达式是左值？（多选） - A) x（int x;） - B) 42 - C) std::move(x) - D) "abc"

答案

A 和 D。

  • A ✅ 变量名，经典左值，能取地址、能绑 int&。
  • B ❌ prvalue（没有身份）。
  • C ❌ xvalue——std::move 的返回值是 int&&，是"将亡值"，能绑 T&& 但不是左值。
  • D ✅ 字符串字面量是左值，类型 const char[4]，存在只读段，&"abc" 合法。

6. 代码题：decltype(x) 与 decltype((x)) 分别得到什么？为什么？

答案

decltype(x) → int；decltype((x)) → int&。

规则：对不带括号的标识符（id-expression），decltype 给出该标识符的声明类型；一旦加括号，它就变成普通表达式，而"变量作为表达式"是左值，于是按左值规则给出 T&。

这个差别在写泛型代码（decltype(auto) 返回值、decltype 做 traits）时经常引发"莫名其妙多了一个引用"的问题。

4.2

算术运算符

本节讲什么

二元 + - * / % 与一元 + - 的规则、整型提升与边界坑点。

+ - * /（二元）

  • 整数除法截断小数：5 / 2 == 2
  • 浮点除法保留小数：5.0 / 2 == 2.5
  • 混合类型会隐式转换（见 4.11.1）

一元 -x（取相反数）

核心语义

对操作数求相反数，数学上等价于 0 - x：

  • 正数 → 负数：-5 == -5
  • 负数 → 正数：-(-3) == 3
  • 0 不变：-0 == 0

底层规则（补码）

  1. 先对操作数执行整型提升（char / short → int，见下文一元 +）；
  2. 有符号整数：按位取反再加 1（补码）；
  3. 无符号整数：数学上 -u 等价于 2^位数 - u（仍可能再参与有符号运算，注意混合类型）。

边界坑：INT_MIN 溢出

32 位 int 范围：[-2147483648, 2147483647]。数学上 -INT_MIN == 2147483648，超出 int 上限 → 有符号整数溢出，未定义行为（UB）：

#include <climits>
int a = INT_MIN;
int b = -a;   // UB（C/C++ 标准）

HFT：对行情偏移、盈亏取反时，若数据可能取极值，先用更宽类型（long long）或显式检查，不要对 INT_MIN 直接一元取负。

适用类型

所有算术类型：char / short / int / long / float / double 等均可；浮点直接变号，不涉及补码。

一元 +x（无数学效果，触发整型提升）

数学作用：几乎无意义

+x 直接返回操作数本身，值不变：

+5 == 5;
+(-2) == -2;

日常极少单独写 +x；它与二元加法 a + b 里的 + 是不同运算符（一元 vs 二元），语法上靠上下文区分，例如 +a + b 中第一个 + 是一元，第二个是二元加。

唯一实用特性：强制整型提升

一元 +、一元 -、按位取反 ~ 都会对操作数执行整型提升（integral promotion）：

  • char / signed char / unsigned char / short / unsigned short，且其值域能完整放入 int → 提升为 int；
  • 若 int 与 unsigned int 同宽容纳所有 unsigned short 值 → unsigned short 提升为 unsigned int。
char ch = static_cast<char>(0x80);  // 有符号 char 常为 -128
auto t1 = ch;    // 类型 char
auto t2 = +ch;   // 一元 + 触发提升 → 类型 int，值仍为 -128

decltype(t1) 是 char，decltype(t2) 是 int；sizeof(t2) 通常大于 sizeof(t1)。

典型场景

  1. 只做类型提升、不改数值：把 char / short 提到 int 再参与位运算或打印；
  2. 与二元 + 区分：正负号 vs 加法；
  3. 保持表达式语法完整（教材/规范写法）。

一元 + / - 对比

特性 一元 -x 一元 +x
数学输出 数值取反 数值不变
整型提升 一定触发 一定触发
溢出风险 INT_MIN 取负 → UB 无
日常用途 取相反数 几乎只做类型提升
浮点 支持（-3.14） 支持（+2.5，少见）

% 取余

  • 仅整型；浮点不能用 %
  • 余数符号与被除数一致：-5 % 2 == -1

易错点

坑 说明
除 0 未定义行为
-INT_MIN 有符号最小值取负 → 溢出 UB
负数取余 符号跟被除数，不是数学模运算
混合类型 自动提升，可能意外变 double
一元 + 误以为会「变正」；实际只提升类型，不改变符号

HFT：价格比例用整数除法前先确认是否该用浮点；用 if (b != 0 && a / b) 防除零（见 4.3）。

示例

整数除法 vs 浮点除法

#include <iostream>

int main() {
    std::cout << 5 / 2 << "\n";      // 2  整数除法，截断小数
    std::cout << 5.0 / 2 << "\n";    // 2.5
    std::cout << 5 / 2.0 << "\n";    // 2.5  int 提升为 double

    double price = 3750.5;
    int lots = 10;
    // std::cout << price / lots;    // 375.05 浮点结果
    std::cout << static_cast<int>(price) / lots << "\n";  // 375 先截断再除
    return 0;
}

取余 %

#include <iostream>

int main() {
    std::cout << 10 % 3 << "\n";    // 1
    std::cout << -10 % 3 << "\n";   // -2  符号跟被除数
    std::cout << 10 % -3 << "\n";   // 1

    int total_qty = 25;
    int lot_size = 10;
    int full_lots = total_qty / lot_size;   // 2 整手
    int remainder = total_qty % lot_size;   // 5 零股
    std::cout << full_lots << " " << remainder << "\n";
    return 0;
}

一元 + - 与整型提升

#include <climits>
#include <iostream>
#include <type_traits>

int main() {
    char c = -10;
    short s = 100;

    std::cout << "-c = " << -c << "\n";   // 10，char 提升 int 再取反
    std::cout << "-s = " << -s << "\n";   // -100

    std::cout << "+c = " << +c << "\n";   // -10，值不变，类型变 int
    std::cout << "+s = " << +s << "\n";   // 100

    std::cout << std::boolalpha
              << std::is_same_v<decltype(c), char> << " "
              << std::is_same_v<decltype(+c), int> << "\n";  // true true

    int min = INT_MIN;
    // int bad = -min;                    // UB，勿对 INT_MIN 一元取负
    (void)min;
    return 0;
}

一元 + 与二元 + 区分

int a = 3, b = 4;
std::cout << +a + b << "\n";   // 7：+a 是一元（提升），+b 是二元加法

防除零（配合逻辑短路）

int a = 100, b = 0;
if (b != 0 && a / b > 10) {   // b==0 时不会算 a/b
    /* ... */
}
// int bad = a / b;             // ❌ b==0 → UB

与优先级结合（见 4.12.1）

int a = 2, b = 3;
std::cout << a + b * 4 << "\n";   // 14，先算 b*4 再加 a
std::cout << (a + b) * 4 << "\n"; // 20，括号改变结合

和 C 的区别（算术运算符：C/C++ 完全一致）

算术运算符是 C 和 C++ 完全共享的部分——+ - * / %、一元 + -、整型提升、有符号溢出 UB，这些规则两边一字不差：

对比点 C C++
+ - * / % ✅ 一致 ✅ 一致
整数除法截断 ✅ 5/2 == 2 ✅ 一致
% 仅整型 ✅ ✅ 一致
余数符号跟被除数 ✅ -5%2 == -1 ✅ 一致
整型提升 ✅ char/short → int ✅ 一致
有符号溢出 UB ✅ -INT_MIN UB ✅ 一致
除 0 UB ✅ ✅ 一致

给 C 程序员的关键提醒： 1. 算术运算符无需任何转变——C 的肌肉记忆直接用。5/2、-5%2、整型提升、-INT_MIN UB 这些坑两边一模一样。 2. C++ 的"差异"在类型系统——auto 推导、constexpr 编译期算术、std::numeric_limits 替代 <climits> 的宏，但这些不是算术运算符本身的差异，是 C++ 类型系统的扩展。 3. HFT 注意两边一样——除零 UB、INT_MIN 取负 UB、浮点转整型截断（非四舍五入）。C 程序员的警惕心直接迁移。

常见错误

1. 整数除法意外截断

double avg = total / count;   // 若 total、count 都是 int，先整数除法截断再转 double

C 程序员也踩这个——int / int 得 int，赋给 double 时已截断。改法：double avg = static_cast<double>(total) / count; 先转一个操作数为 double。

2. -INT_MIN 溢出 UB

#include <climits>
int a = INT_MIN;
int b = -a;   // ❌ UB，数学上 2147483648 超过 INT_MAX

32 位 int 范围 [-2147483648, 2147483647] 不对称——-INT_MIN 数学上是 2147483648，超出 int 上限。C 和 C++ 都是 UB。改法：用 long long 接收，或显式检查 if (a == INT_MIN) ...。

3. 负数取余符号混淆

int x = -5 % 2;   // -1（符号跟被除数，不是数学模 0/1）
int y = 5 % -2;   // 1（符号跟被除数）

C/C++ 的 % 余数符号跟被除数，不是数学上的非负模运算。Python 的 % 余数跟除数（非负），两者不同。C 程序员习惯了，但跨语言时容易混。

自测题

1. 选择题　5 / 2 和 5.0 / 2 在 C++ 中的结果分别是：

  • A. 2.5 和 2.5
  • B. 2 和 2.5
  • C. 2.5 和 2
  • D. 2 和 2
答案

B。5 / 2 两个操作数都是 int，整数除法截断得 2；5.0 / 2 有 double 参与，int 提升为 double，得 2.5。C 也是同样规则。

2. 判断题　-5 % 2 的结果是 1（数学上的非负模）。

答案

错。C/C++ 的 % 余数符号跟被除数，-5 % 2 == -1（不是 1）。这是 C/C++ 和 Python 的差异——Python 的 -5 % 2 == 1（余数跟除数非负）。C 程序员习惯了，但跨语言时要注意。

3. 踩坑题　HFT 代码计算平均成交价，结果总是整数，为什么？

int total_qty = 100;
double total_amount = 37505.5;
double avg_price = total_amount / total_qty;   // 期望 375.055
std::cout << avg_price;   // 打印 375，不是 375.055
答案

等等，这段代码其实是对的——total_amount 是 double，total_qty 是 int，混合运算时 int 提升为 double，结果是 375.055。

真正会出问题的是两边都 int 的情况：

int total_qty = 100;
int total_amount = 37505;       // int
double avg_price = total_amount / total_qty;   // 先整数除法得 375，再转 double 375.0

修复：double avg_price = static_cast<double>(total_amount) / total_qty; 先转一个为 double。C 程序员用 (double)total_amount，C++ 推荐 static_cast<double>(total_amount)。

4. 应用题　HFT 行情偏移计算 offset = -delta，其中 delta 是 int。如何安全处理 delta == INT_MIN 的情况？

答案 
#include <climits>

int safe_negate(int delta) {
    if (delta == INT_MIN) {
        // 方案 1：用 long long 接收
        long long neg = -static_cast<long long>(delta);   // 2147483648，安全
        // 方案 2：业务上限定，返回 INT_MAX 或报错
        return INT_MAX;   // 或抛异常、记日志
    }
    return -delta;
}

要点： - -INT_MIN 是 UB，必须显式处理 - 用更宽类型（long long）承接是常见做法 - C 程序员也踩这个，C++ 同样坑

HFT 实战里，价位/偏移常用 int64_t 或定点小数，避开 INT_MIN 边界。

底层实现与实测

环境：Apple clang 23.1.0，arm64-apple-darwin，-std=c++17。可跑版本见文末例子。

1. 算术高于移位：1 << 2 + 3 是 32 不是 7

int r1 = 1 << 2 + 3;      // 实测 32，等价 1 << (2+3)

clang 直接给出警告（这就是别背表、靠编译器的理由）：

warning: operator '<<' has lower precedence than '+'; '+' will be evaluated first
         [-Wshift-op-parentheses]

2. 位与低于相等：测位最经典的错写

unsigned flags = 0x02;
flags & 0x01 == 0      // 实测 0 —— 被解析成 flags & (0x01 == 0)，即 0x02 & 0
(flags & 0x01u) == 0   // 实测 1 —— 这才是"低 1 位为 0"

warning: & has lower precedence than ==; == will be evaluated first [-Wparentheses]

这个坑在 HFT 里特别致命：它不崩、不报错，只是永远返回 0，风控条件静默失效。

3. 结合性：- 左结合，= 与一元右结合，*p++ 是 *(p++)

a - b - c                 // 实测 65，等价 (a-b)-c；a-(b-c) 是 75
x = y = z                 // 实测 x=300 y=300 z=300，等价 x = (y = z)
int u = 5; -(u++)         // 实测 -5，等价 -(u++)，不是 (-u)++
int* p = arr; *p++        // 实测取到 arr[0]，之后 p 指向 arr[1]

后自增高于解引用，是 *p++ 能当"取当前值并前进"用的全部原因。

4. & 高于 |：加括号能改语义

1 | 4 & 2      // 实测 1（= 1 | (4&2) = 1 | 0）
(1 | 4) & 2    // 实测 0（= 5 & 2）

注意：括号改变的是语义，不是性能。加括号在 -O2 下是零成本的（编译器本来就按优先级树生成代码）——所以"多加括号"只有收益没有代价。

5. C++17 修好了一个老 UB：i = i++

int i = 5;
i = i++;        // C++17 起良定义，实测 i = 5

实测证据是警告本身：

标准 编译 i = i++ 结果
-std=c++11 warning: multiple unsequenced modifications to 'i' [-Wunsequenced] UB，结果不确定
-std=c++17 无警告 良定义，右操作数先求值

C++17 的规定：简单赋值 E1 = E2 中，右操作数先于左操作数求值，赋值本身最后发生。所以 arr[k] = (k = 2) 在 C++17 下保证写 arr[2]（实测 k=2, arr[2]=2），在此之前是 UB。

6. 但函数实参的求值顺序，C++17 仍未指定

int n = 0;
auto bump = [&]() { return ++n; };
printf("%d %d", bump(), bump());   // 实测 1 和 2（本编译器左到右）

1 和 2 的顺序不是标准保证的，只是 clang 恰好这么排。GCC 可能反过来。任何依赖实参求值顺序的代码都是 bug，不管用哪个标准。

对比：逗号运算符 , 是唯一被标准保证从左到右的运算符，这也是它至今没被废弃的原因。

三个容易记反的方向

  1. 算术 > 移位 > 关系 > 相等 > 位与 > 位异或 > 位或 > 逻辑与 > 逻辑或 > 条件 > 赋值 > 逗号。 最容易记反的是「相等 == 高于位与 &」——a & b == c 永远是 a & (b==c)。
  2. 后缀 ++ 高于一元 *，所以 *p++ 是"取当前值再前进"，不是"取前进后的值"。
  3. ?: 比赋值高、比 << 低。cout << cond ? a : b 是 C++ 里最常见的静默 bug 之一。

i = i++ 在两个标准下的差异（实测）

-std=c++17 : 编译无警告，i = 0     ← 标准保证：赋值的右操作数先于左操作数求值
-std=c++11 : warning: multiple unsequenced modifications to 'i' [-Wunsequenced]

C++17 只给赋值(=)、下标([])、<<、>>、成员访问(./->) 加了"左/右操作数谁先"的规定， 函数实参的顺序至今未指定（见上表 #6）。

HFT / 嵌入式视角

  1. 优先级错误是"静默失效"类 bug 的头号来源。flags & 0x01 == 0 不崩、不报警告（-Wall 下才报），只是永远 false。风控、权限校验、协议解析里出现这种写法，等于检查根本没生效。规矩：位运算一律带括号，-Wall -Wextra 常开。
  2. 括号是零成本的。-O2 下加括号不会多一条指令（实测第 4 条只有语义差、没有性能差）。可读性收益 100%，性能代价 0%。热路径也别省括号。
  3. C++17 的求值顺序保证要善用：arr[k] = (k = 2) 这类"边算下标边改状态"的写法现在有定义了，但可读性极差，仍然应该拆成两行。标准保证 ≠ 该这么写。
  4. 别依赖实参求值顺序。f(order_id(), seq_no()) 这种，若两个函数有共享状态就是雷。嵌入式驱动里 read_reg(addr++, read_reg(addr++)) 更是灾难。
  5. 嵌入式寄存器操作必须显式类型：1u << n 而不是 1 << n。实测 1 << 31 是 UB（给出 -2147483648），1u << 32 也是 UB（移位量 ≥ 位宽）。ARM 上这类 UB 在不同优化级别可能给出不同值。

代码自测

题目 1： 以下代码在 C 和 C++ 中的行为有什么不同？

int x = 10;
auto y = x;  // C++ 合法，C 合法吗？
参考答案

auto 在 C 中不存在（C23 才引入）。C++11 起 auto 用于类型推导。C 中需要显式写类型。C++ 的 auto 推导规则：去掉引用和 const（除非用 auto&）。C++14 起函数返回类型可用 auto，C++20 起 auto 可用于函数参数（缩写函数模板）。

2. 判断题　flags & 0x01 == 0 和 (flags & 0x01) == 0 等价。

答案

不等价，而且这是最危险的一类 bug——它不崩、不报错，只是静默算错。

== 优先级高于 &，所以 flags & 0x01 == 0 实际是 flags & (0x01 == 0)。而 0x01 == 0 恒为 false（0），于是整个表达式恒等于 0——无论 flags 是什么值，条件永远为假。

实测（flags = 0x02）：flags & 0x01 == 0 → 0；(flags & 0x01) == 0 → 1。

-Wall 下 clang 会报 warning: & has lower precedence than ==——这条警告必须当 error 处理。位运算一律加括号。

3. 应用题　你接手一段 HFT 风控代码：

if (order.qty > 0 && price & 0xFF == 0 && check_credit(account)) {   // 约 50 μs
    send_order(order);
}

指出三处问题并改写。

答案

问题 1（正确性）：price & 0xFF == 0 被解析成 price & (0xFF == 0)，恒为 0 → 整个条件恒 false → 永远不发单。必须写 (price & 0xFF) == 0。

问题 2（语义可疑）：price 是价格却用位掩码判断，大概率本来想写的是区间判断 low <= price && price <= high。位运算只该用在整数 Flags / 协议字段上，不该用在价格上。

问题 3（性能）：check_credit(account)（约 50 μs）放在 && 链的最后一位才对——这里恰好已经是最后，但如果把它挪到最前面，每个单子都要付 50 μs。实测便宜条件前置 vs 后置在 1000 万次循环下差 6.8 倍（3.9 ms vs 26.6 ms）。

改写：

if (order.qty > 0                                   // 最便宜，先算
    && (price & 0xFF) == 0                          // 加括号；如本意是区间则改 low<=price && price<=high
    && check_credit(account)) {                     // 最贵，放最后，绝大多数单子根本走不到
    send_order(order);
}

要点：&& 短路 → 条件顺序 = CPU 干活量；位运算必带括号。

关系与逻辑运算符

本节讲什么

关系比较与逻辑组合；短路求值是核心考点。

关系运算符 < <= > >= == !=

  • 结果类型为 bool（打印时可能显示 0/1）
  • 错误写法：a < b < c 等价 (a < b) < c，不是数学上的「介于两者之间」
int a = 1, b = 2, c = 3;
// if (a < b < c)  // 先 (a<b)→true→1，再 1<c，逻辑常错
if (a < b && b < c)  // ✅

逻辑运算符 ! && ||

运算符 含义 短路
! 逻辑非，优先级在 &&/|| 之上 —
&& 与 左侧为 false，右侧不执行
|| 或 左侧为 true，右侧不执行 
if (b != 0 && a / b) { /* 左侧假则不算 a/b，防除零 */ }

注意：位运算 & | 没有短路（见 4.8）。

和 C 的区别（关系/逻辑运算符：C99 起几乎一致，C++ 多了 bool 类型）

对比点 C（C89） C（C99+） C++
关系运算符 ✅ 一致 ✅ 一致 ✅ 一致
&& \|\| ! ✅ 一致 ✅ 一致 ✅ 一致
短路求值 ✅ ✅ ✅ 一致
结果类型 int（0/1） bool（_Bool） bool
true/false 关键字 无 <stdbool.h> 引入 原生关键字
a < b < c 坑 ✅ 同样错 ✅ 同样错 ✅ 一致

给 C 程序员的关键提醒： 1. C89 的关系/逻辑运算符结果是 int（0/1），C99 引入 _Bool 和 <stdbool.h> 后才有 bool。C++ 从一开始就有原生 bool 类型，true/false 是关键字。但运算符语义完全一致——短路、优先级、a < b < c 坑都一样。 2. 短路求值两边一模一样——b != 0 && a/b 防 除零在 C 和 C++ 都有效。C 程序员的肌肉记忆直接用。 3. C++ 里 bool 能隐式转 int（true→1、false→0），但反过来 int 转 bool（非 0→true、0→false）。C89 里没有 bool，用 int 代替，习惯一致。

底层实现与实测

以下均为本机实测（Apple clang 23.1.0，arm64，-std=c++17 -O2）。短路的价值不在"省一条指令"，在能不能跳过一整段计算。

实测 1：短路的证据——数一数右侧被调了几次

bool left_false(); bool left_true(); bool right_side();   // 各自 ++calls
left_false() && right_side();    // calls = 1   ← 右侧没执行
left_true()  || right_side();    // calls = 1   ← 右侧没执行
left_false() &  right_side();    // calls = 2   ← 位运算两侧都执行

这就是 p != nullptr && p->x == 5 能防崩溃、而 p != nullptr & p->x == 5 会崩的物理原因。

实测 2：a < b < c —— 编译器现在直接报错

error: chained comparison 'X < Y < Z' does not behave the same as a mathematical expression [-Wparentheses]

clang 把链式比较当成错误（不是警告）。拆开写成 (a < b) < c 才编得过，实测：

  • a=1, b=2, c=0 → (a<b)<c = 0，a<b && b<c = 0（这次碰巧一致）
  • a=5, b=10, c=3 → (a<b)<c = 1：(5<10) 得 true 提升成 1，1 < 3 为真——而数学上 5 根本不在 (10, 3) 之间

这就是最危险的地方：它（拆开写时）不报错、也不崩溃，只是安静地给出错误答案。

实测 3：短路值 2 倍性能——把便宜的判断放前面

2000 万次循环，左侧是运行时才确定的便宜检查（由 argc 派生，编译器无法折叠）， 右侧是一个 noinline 的函数调用：

写法 实测（2000 万次）
cheap && expensive(i) 8.35 ms（第二次跑 17.16 ms）
expensive(i) && cheap 21.70 ms（第二次跑 34.68 ms）

2.0–2.6 倍（复测值）。短路是唯一能"不执行右边代码"的运算符——这也是为什么防御性检查（ptr && ptr->valid）要放左边，以及为什么 HFT 代码里会把快速的 reject 条件排在最前。

实测 4：&& 不一定生成跳转指令

bool f_int(int a, int b) { return a && b; }

f_int(int, int):
    cmp  w0, #0
    ccmp w1, #0, #4, ne      ; 条件比较：只有 a!=0 时才比较 b
    cset w0, ne
    ret

ARM64 有 ccmp（条件比较），clang 用它把"短路"实现成无分支代码。而两个 bool 参数做 a && b 与 a & b，汇编完全相同（都是一条 and）——因为 bool 只有 0/1，两者数学等价。

结论：&& 与 & 的差别只在求值（短路），不在生成的指令数。别为了"省分支"把 && 改成 &——那会丢掉短路保护，收益却是零。

实测 5：bool 的几个数字

sizeof(bool) = 1
true + true  = 2        ← bool 隐式提升成 int 参与算术

bool 是整数类型，会隐式转 int——所以 flags += is_valid 这类写法合法（把布尔当计数用），但也容易掩盖意图。

实测 6（复测）：短路的真实收益是 2.0–2.6 倍，不是 5.4 倍

上面"实测 3"写的 5.4 倍，用同一份代码复测只能得到 2.0–2.6 倍，而且原测法有两个毛病：

  1. 循环里两个条件都是编译期可推断的常量（如 i >= 0），-O2 会把整段循环删掉 —— 两次实测都是 0.00 ms，比值毫无意义。
  2. 用 volatile 变量当条件也不行：volatile 读（一次内存访问）比一次取模还贵，反而让"短路版"更慢 （实测 27.60 ms vs 18.87 ms，方向都反了）。

可靠的测法：左侧用运行时才知道的量（如 argc 派生），右侧放一个不可内联的函数调用。

便宜判断在前（短路掉右侧）：    8.35 ms
昂贵判断在前（每次都调用）：   21.70 ms
比值 = 2.60x          （第二次跑得 2.02x，波动来自取模开销）

结论不变，只是量级要修正：把"大概率为假、且很便宜"的条件放最前面，能省掉整个右侧。 这条在风控链（余额 → 限额 → 价格带 → 复杂校验）上最值钱。

实测 7：有符号 / 无符号混合比较

int si = -1;  unsigned ui = 1;
si < ui        // 0  ← si 被转成 unsigned = 4294967295
si < (int)ui   // 1  ← 显式转换后符合直觉

-Wsign-compare 就是给这类代码准备的。嵌入式里 for (size_t i = v.size()-1; i >= 0; --i) 在 v 为空时 size()-1 下溢成 18446744073709551615，i >= 0 恒真 —— 直接越界。 倒序循环写 for (size_t i = v.size(); i-- > 0;) 或用反向迭代器。

实测 8：a < b < c 现在是编译错误，不只是警告

error: chained comparison 'X < Y < Z' does not behave the same as a mathematical expression [-Wparentheses]

clang 把 chained comparison 这条 -Wparentheses 子项默认判为 error（不是 warning）。 换句话说：这个坑在现代 clang 上过不了编译；但老代码、其它编译器、或 -Wno-parentheses 下仍然会静默算错。 正确写法仍是 a < b && b < c。

HFT / 嵌入式视角

  • 把最便宜、最可能失败的条件排在最前：复测得到的 2.0–2.6 倍就是排序的收益。风控链（余额 → 限额 → 价格带 → 复杂校验）按"便宜 + 高拒绝率"排序。
  • 短路可以省掉整个子系统调用：日志里 if (log_enabled && build_expensive_message()) 是标准写法；反过来写等于每次都构造消息。
  • 别用 &/| 替代 &&/|| 做"优化"（实测 4）：汇编一样，还丢了短路。
  • 链式比较一定要拆：low <= price && price <= high。clang 现在会拦，但移植的老代码和其它编译器未必。
  • 浮点比较不在此列：== 对浮点基本无效，要用 fabs(a-b) < eps；HFT 的定点价格用整数比较，反而没这个问题。

常见错误

1. a < b < c 不是"介于两者之间"

if (a < b < c)   // 等价 (a < b) < c

a < b 先算得 bool（0 或 1），再和 c 比。若 a=1, b=2, c=0，1<2 得 true（1），1<0 得 false——但数学上 1 不在 (2, 0) 区间。正确写法：a < b && b < c。C 和 C++ 都有这个坑。

2. & 误用为 &&

if (p != NULL & *p == 5)   // ❌ 先算 *p，p 为 NULL 时崩溃

& 是位与，没有短路——两侧都求值。p != NULL 为 false 时仍会算 *p，解引用 NULL 崩溃。用 && 才短路。C 程序员也踩这个，C++ 同样坑。

3. == 写成 =

if (x = 5)   // ❌ 赋值，不是比较，永远为真（5 非 0）

经典 C 坑，C++ 也有。防范： - C 习惯把常量放左边：if (5 == x)（写成 5 = x 编译报错） - C++ 习惯用 const 或 constexpr，编译器会警告某些 = 误用 - 编译器开 -Wall / /W4，会警告 if (x = 5)

自测题

1. 选择题　a < b < c 在 C++ 中等价于：

  • A. a < b && b < c（数学上的"介于两者之间"）
  • B. (a < b) < c（先比较得 bool，再和 c 比）
  • C. a < (b < c)
  • D. 编译错误
答案

B。< 左结合，a < b < c 等价 (a < b) < c。先算 a < b 得 bool（0/1），再和 c 比较。C 也是同样行为。要"介于两者之间"写 a < b && b < c。

2. 判断题　b != 0 && a / b > 1 中，若 b == 0，a / b 不会被计算。

答案

对。&& 短路求值——左侧 b != 0 为 false 时，右侧 a / b > 1 不求值，避免除零 UB。C 和 C++ 都保证短路。这是用 && 替代 if 防御的常见技巧。

3. 踩坑题　下面这段代码想"指针非空且值为 5 才执行"，哪里有问题？

int* p = get_ptr();
if (p != NULL & *p == 5) {
    do_something();
}
答案

用了 &（位与）而不是 &&（逻辑与）。& 没有短路——两侧都求值。p != NULL 为 false 时仍会算 *p == 5，解引用 NULL 指针是 UB（可能崩溃）。

修复：if (p != NULL && *p == 5)，用 && 短路。或更现代：if (p && *p == 5)（指针在条件上下文隐式转 bool）。

C 程序员也踩这个——& 和 && 的区别两边一样。

4. 应用题　HFT 代码要"订单有效（qty > 0）且价格在合理区间（low <= price <= high）才发单"，用一行表达式写。

答案 
if (order.qty > 0 && low <= order.price && order.price <= high) {
    send_order(order);
}

要点： - && 短路：qty <= 0 时后面不算（虽然这里没副作用，但是好习惯） - low <= price && price <= high 拆成两个比较，不用 low <= price <= high - 用 && 连接三个条件

C 等价写法一模一样：if (order.qty > 0 && low <= order.price && order.price <= high)。

5. 判断题：为了少一次分支跳转，把 if (p != nullptr && p->x == 5) 改成 if (p != nullptr & p->x == 5) 能提速。

答案

错，而且很危险。

  1. 安全：& 不短路，p 为空时照样解引用 p->x → 崩溃（实测：false & right() 的调用计数是 2，右侧照样执行）。
  2. 性能：实测两个 bool 做 a && b 与 a & b 生成的汇编完全相同（一条 and）；即使操作数是 int，clang 也用 cmp + ccmp + cset 把 && 做成无分支。收益为零，风险是崩溃。

6. 应用题：风控要依次检查 4 个条件：① 账户已登录（一次布尔读）② 资金充足（查缓存 map）③ 价格在当前档位（浮点区间比较）④ 历史违约评分（查库 + 计算，约 50 μs）。要求：给出条件排列顺序并说明理由；再指出 low <= price <= high 该怎么写。

答案 
if (logged_in                                   // ① 最便宜、拒绝率可能最高
    && capital_enough(account)                  // ② 内存查表，纳秒级
    && low <= price && price <= high            // ③ 拆成两个比较，别写 low <= price <= high
    && credit_score_ok(account)) {              // ④ 最贵，放最后，绝大多数单子根本走不到
    send_order(order);
}

理由：&& 短路（实测 1：右侧调用计数为 0），条件顺序直接决定 CPU 干了多少活。复测把便宜条件前置 vs 后置差 2.0–2.6 倍（8.35 ms vs 21.70 ms / 2000 万次）。把 50 μs 的查库放最后，意味着 99% 的单子在前面就被拒掉了，永远碰不到它。

区间写法：必须拆成 low <= price && price <= high。写 low <= price <= high 在 clang 下直接 error: chained comparison；即使拆开写 (low <= price) <= high，也是拿 bool（0/1）去和价格比，逻辑全错（实测：a=5, b=10, c=3 时 (a<b)<c 得 1）。

4.4

赋值运算符

本节讲什么

= 与复合赋值 += -= *= /= %= <<= >>= &= ^= |=。

基本规则

  1. = 左侧必须是可修改左值
// 10 = i;           // ❌ 字面量不能当左值
const int a = 1;
// a = 2;            // ❌ const 不可改

  1. 复合赋值等价展开：i += 2 → i = i + 2（但不是简单文本替换，复合形式对类类型可能更高效）

  2. 赋值返回左侧对象，支持连续赋值：

int a, b, c;
a = b = c = 0;   // 从右向左：c=0，返回值赋给 b，再赋给 a

复合赋值也返回左侧引用（类类型时常返回 *this）。

和 C 的区别（赋值运算符：C/C++ 完全一致，类类型有差异）

对比点 C C++
= 左值要求 ✅ 一致 ✅ 一致
复合赋值 += 等 ✅ 一致 ✅ 一致
连续赋值 a=b=c=0 ✅ 右结合 ✅ 一致
返回左侧引用 返回左值（值） 类类型返回 *this 引用
左值可以是… 变量、数组元素、解引用指针 同 C + 类成员、[]/() 重载、迭代器解引用

给 C 程序员的关键提醒： 1. 赋值运算符语义两边一模一样——=、+=、连续赋值、右结合，C 学的直接用。 2. C++ 的"差异"在类类型——string/vector/自定义类的 = 是拷贝赋值运算符（深拷贝），可能触发内存分配。C 里 struct 赋值是 memcpy 级（浅拷贝），C++ 里含 string 成员的 struct 赋值会调 string::operator=（可能分配堆）。 3. C++ 类类型的 += 可能比 = ... + ... 高效——s += "tail" 原地追加，s = s + "tail" 可能产生临时对象。C 里没这个差异（都是字节操作）。

为什么赋值要"返回左侧对象"（动机）

C 里 = 是语句，C++ 里 = 是表达式——它有值、有类型、还能当左值。这个设计不是语法糖，它撑起了三件事：

  1. 链式赋值：a = b = c = 0——靠"返回左侧对象"才写得出来。
  2. 条件里赋值：if ((fd = open(path, O_RDONLY)) < 0)——C/C++ 系统编程的标准写法，一条语句完成"赋值 + 判错"。
  3. 类类型的资源管理：std::string s2 = s1; 调的是拷贝赋值运算符，深拷贝内部缓冲区——这是 RAII 能成立的前提（见 ch13）。

而在 C++ 里比 C 多出来的关键点只有一个：赋值表达式是左值（内置类型如此，类类型靠返回 T& 模拟），以及 C++17 起求值顺序有了保证。

底层实现与实测

环境：Apple clang 23.1.0，arm64-apple-darwin，-std=c++17 -O2。可跑版本见文末例子。

1. 复合赋值不只是"少打字"：左侧只求值一次

std::vector<int> g_v{1,2,3,4,5};
int idx() { ++g_probe; return 2; }

g_v[idx()] += 10;                  // 实测 idx() 调用 1 次，g_v[2] = 13
g_v[idx()] = g_v[idx()] + 10;      // 实测 idx() 调用 2 次，g_v[2] = 23

E1 += E2 的语义是"E1 只求值一次"，不是"文本替换成 E1 = E1 + E2"。当左值表达式带副作用（函数调用、迭代器、volatile 读）时，两者行为不同——这是很多"手写展开"重构引入 bug 的地方。

2. 赋值表达式是左值（C++ 有，C 没有）

int a = 0;
(a = 5) = 7;          // C++ 合法，实测 a = 7
int x=1, y=2, z=3;
(x = y) = z;          // 实测 x=3 y=2 z=3（先 x=y 得 2，再把 z 赋进去）

同一行 C 代码会直接报错：

lv.c:1:37: error: expression is not assignable

原因是 C 的赋值结果是值（右值），C++ 的赋值结果是左值（引用）。这条差异平时用不上，但它决定了 (cond ? a : b) = v、*p = *q = 0 这些写法在 C++ 里成立。

3. C++17 起：右操作数先于左操作数求值

int arr[4] = {10,20,30,40};
int k = 0;
arr[k] = (k = 2);     // C++17 实测：k=2, arr[2]=2（保证写 arr[2]，不是 arr[0]）

C++17 之前这是 UB。规则是：E1 = E2 中，先求 E2（右），再求 E1（左），最后做赋值。同一个规则让 i = i++ 从 UB 变成良定义（i 初值 5 时结果仍是 5）。

实测提醒：clang 23.1.0 在 -std=c++17 下对 arr[k] = (k = 2) 仍然发 -Wunsequenced 警告（历史遗留的告警逻辑），但语义已由标准定死。看到这条警告时先确认标准版本。

4. 类类型 operator= 返回 T&，连续赋值零多余拷贝

struct Probe { int v=0; Probe& operator=(int x){ v=x; return *this; } };
Probe p1,p2,p3;
p1 = p2 = p3 = 99;    // 实测 p1.v=p2.v=p3.v=99

内置的 int 连续赋值在 -O2 下被完全优化掉——a = b = c = c0; g = a+b+c; 生成的汇编只有两条指令：

add  w8, w0, w0, lsl #1   ; w8 = 3 * c0
str  w8, [x9, _g_out@PAGEOFF]

编译器直接把"三次赋值 + 三次加法"折叠成一条乘 3。赋值本身零成本。

5. 但 std::string 的连续赋值是三次深拷贝

std::string s1, s2, s3;
s1 = s2 = s3 = std::string(64, 'x');   // 实测 len=64，三次 O(n) 拷贝

C 里 struct 赋值是 memcpy，C++ 里含 std::string 成员的结构体赋值要逐成员调 operator=，每个 string 都是一次可能的堆分配。热路径上别在循环里做 string 连续赋值。

6. s += x vs s = s + x：20 万次差 869 倍

写法 20 万次耗时
s = s + "a" 871.8 ms
s += "a" 1.00 ms

s = s + x 每次都：operator+ 造临时对象（可能分配）→ operator= 拷回（可能再分配）。s += x 原地追加，容量够时零分配。配合 reserve() 几乎零成本。

这是 C 程序员最该改的一个习惯：C 里 i = i + 2 和 i += 2 完全等价（都是整数），所以很多人到 C++ 还写 s = s + x——对 std::string 这是 869 倍的差距。

HFT / 嵌入式视角

  1. s += x 是唯一选择。日志拼接、FIX 报文组装这类热路径，用 += + reserve()；s = s + x 会产生 O(n) 个临时对象。实测 869 倍不是理论值，是 20 万次循环的真数字。
  2. 复合赋值用于 volatile 寄存器是刚需。REG->CR |= (1u << 3) 在 ARM 上是 ldr+orr+str 三条指令（读-改-写），而 REG->CR = REG->CR | (1u<<3) 会读两次寄存器——对"读即清"（read-to-clear）类型的状态寄存器，第二次读到的值已经变了，行为完全不同。硬件寄存器操作一律用 |= / &=。
  3. 别在 if 里随手写赋值。if ((fd = open(...)) < 0) 是合法惯用法，但 if (x = 5) 是 bug。规矩：赋值当条件时必须双层括号并开 -Wparentheses，clang 会对"疑似把 == 写成 ="报警。
  4. C++17 的求值顺序保证要会用于正确性，不要用于炫技。arr[k] = (k = 2) 有定义了，但这种代码 review 一定被打回。拆成两行零成本。
  5. 含 std::string / std::vector 成员的结构体赋值不是 memcpy。跨核共享内存、共享内存队列里放这种对象是灾难（指针指向各自进程的堆）。共享内存里只能放 POD。

常见错误

1. == 写成 =

if (x = 5)   // ❌ 赋值不是比较，永远为真

经典 C 坑，C++ 也有。防范：常量放左边 if (5 == x)，或开编译器警告。

2. 复合赋值对类类型理解错

std::string s = "hello";
s = s + " world";   // 产生临时 string，可能分配
s += " world";      // 原地追加，更高效

C 里 i = i + 2 和 i += 2 完全等价（都是整数运算）。C++ 里对 string/vector 这类管理资源的类，s = s + x 可能产生临时对象（先算 s + x 得临时，再赋给 s），s += x 原地修改，+= 通常更高效。

3. 连续赋值对类类型有性能陷阱

std::string a, b, c;
a = b = c = "init";   // 三次拷贝赋值，可能三次分配

C 里 a = b = c = 0 是整数赋值，零成本。C++ 里 string 的连续赋值是三次拷贝（每次可能分配）。热路径上避免这种写法，或用移动：a = b = c = std::string("init");（移动语义，第 13 章详讲）。

自测题

1. 选择题　a = b = c = 0 的求值顺序（结合律）是：

  • A. 从左到右：((a = b) = c) = 0
  • B. 从右到左：a = (b = (c = 0))
  • C. 未指定
  • D. 编译错误
答案

B。赋值运算符右结合，a = b = c = 0 等价 a = (b = (c = 0))。先算 c = 0 返回 0，再 b = 0 返回 0，再 a = 0。C 也是同样规则。

2. 判断题　const int x = 5; x = 10; 是合法的赋值。

答案

错。x 是 const，不可修改，x = 10 编译错误。= 左侧必须是可修改左值，const 变量不是可修改的。C 和 C++ 都一样。

3. 踩坑题　C 程序员写下面这段 C++ 代码，性能上有什么可改进？

std::string log;
for (int i = 0; i < 10; ++i) {
    log = log + "[" + std::to_string(i) + "]";
}
答案

每次循环产生多个临时 string：log + "[" 产生临时 1，+ std::to_string(i) 产生临时 2，+ "]" 产生临时 3，最后赋值给 log（可能再分配）。10 次循环约 30+ 次堆分配。

改进用 +=：

std::string log;
log.reserve(64);   // 预留容量
for (int i = 0; i < 10; ++i) {
    log += "[";
    log += std::to_string(i);
    log += "]";
}

+= 原地追加，无临时对象，配合 reserve 几乎零分配。C 程序员习惯 s = s + x（C 里等价 s += x），到 C++ 的 string 要改用 +=。

4. 应用题　C 里写 struct Point p1 = {1, 2}; struct Point p2; p2 = p1; 是合法的浅拷贝。C++ 里对一个含 std::string 成员的 struct 做同样赋值，会发生什么？

答案 
struct Person {
    std::string name;
    int age;
};
Person p1{"Alice", 30};
Person p2;
p2 = p1;   // ✅ 合法，但不是浅拷贝

C++ 里 p2 = p1 调用编译器生成的默认赋值运算符，对每个成员赋值——name 调 string::operator=（深拷贝内部 char 数组），age 直接拷贝。不是 C 的 memcpy 浅拷贝。

  • C 的 struct 赋值是 memcpy（含指针成员会共享堆 → 双 free 风险）
  • C++ 的 struct 赋值是逐成员调 operator=（string/vector 成员会正确深拷贝）

这是 C++ 比 C 安全的地方——含资源管理成员的 struct 赋值不会出错。但如果含裸指针成员，C++ 默认赋值仍是浅拷贝，要按三/五法则手写（见 3.3.5）。

5. 选择题　v[idx()] += 10 与 v[idx()] = v[idx()] + 10，在 idx() 有副作用时：

  • A. 完全等价，+= 只是语法糖
  • B. += 只调用 idx() 一次，手写展开调用两次
  • C. 都不合法
  • D. 取决于编译器
答案

B。复合赋值 E1 op= E2 的语义是 E1 只求值一次，不是文本替换。

实测（idx() 每次自增计数器）： - g_v[idx()] += 10 → idx() 调用 1 次，g_v[2] = 13 - g_v[idx()] = g_v[idx()] + 10 → idx() 调用 2 次，g_v[2] = 23

HFT/嵌入式含义：左值表达式带副作用时（函数调用、迭代器解引用、volatile 硬件寄存器），手写展开会多求值一次。对"读即清"的硬件状态寄存器，多读一次就多清一次状态——是功能性 bug，不是性能问题。

6. 应用题　下面这段是嵌入式驱动里控制寄存器的代码，指出问题并改写：

#define STATUS_REG  (*(volatile uint32_t*)0x40001000)
#define CLEAR_IRQ   0x02            // 读该位即清除中断

// 想"读状态 + 清除中断位 + 再置使能位"
uint32_t s = STATUS_REG;
STATUS_REG = (STATUS_REG | CLEAR_IRQ) | ENABLE_BIT;
答案

问题：STATUS_REG 被读了两次，而这是一个"读即清（read-to-clear）"的状态寄存器——第二次读到的值里中断位已经被第一次读清掉了，写入的结果可能丢状态。而且赋值右侧又展开了一次 STATUS_REG。

改写：一次读、就地改、一次写，全程用复合赋值：

uint32_t s = STATUS_REG;             // 唯一一次读（同时也清了中断位）
s |= ENABLE_BIT;                     // 就地改（不碰硬件）
STATUS_REG = s;                      // 一次写

或直接用复合赋值（编译器会生成 ldr/orr/str 三条指令，仍是一次读一次写）：

STATUS_REG |= ENABLE_BIT;            // 读-改-写，只读一次

要点三条： 1. volatile 的每一次出现都是一次真实访存——STATUS_REG = STATUS_REG | x 里有两次读，不是一次。 2. 复合赋值保证左值只求值一次，对 volatile 左值这是语义保证，不是优化。 3. 用 1u << n 而不是 1 << n（1 << 31 是 UB，见 4.8）。

4.5

自增自减

本节讲什么

++ -- 前置与后置的区别——重点考点。

前置 ++i / --i（推荐）

  • 先自增/自减，再返回修改后的对象
  • 返回左值（可继续链式使用）
  • 无多余临时副本，性能更好

后置 i++ / i--

  • 先返回原值的副本（右值），再修改变量
  • 多一次临时，热路径避免
int i = 10;
i += 2;      // i = 12
++i;         // i = 13
int j = i++; // j = 13，i 变为 14
// cout << i << " " << j;  →  14 13

完整示例解析

#include <iostream>

int main() {
    int i = 10;
    i += 2;    // 复合赋值，i = 12
    ++i;       // 前置自增，i = 13
    int j = i++;  // 后置：j 得 13，i 变 14
    std::cout << i << " " << j << std::endl;  // 14 13
    return 0;
}

禁忌

同一表达式中对同一变量多次自增/自减 → 未定义行为：

// int k = i++ + i++;  // ❌ UB

教材建议：默认写 前置 ++i。

为什么要分前置/后置（动机）

因为返回值不同，不是因为"修改时机不同"（两者对变量本身的修改完全一样，都加 1）：

返回值 实现
前置 ++i 修改后的左值引用 i += 1; return i;
后置 i++ 修改前的副本（右值） tmp = i; i += 1; return tmp;

后置必须"先留一份旧值再改"，所以天然多一次拷贝。这就是"推荐 ++i"的全部理由——不是风格问题，是少一次拷贝。

C++ 用参数个数区分两个重载（这是语言里唯一的"哑元参数"约定）：

T& operator++();      // 前置，无参
T  operator++(int);   // 后置，int 哑元（值永远不被使用，只为区分签名）

4. C++17 求值顺序：i = i++ 从 UB 变良定义

这是 C++17 的一次实质变化，很多老资料还没更新：

表达式 C++11/14 C++17 实测
m = m++; UB 良定义，m == 0
p = ++p; UB 良定义，p == 1
i++ + i++ UB 仍是 UB

C++17 规定：赋值运算符的右操作数先于左操作数求值。所以 m = m++ 里右侧 m++ 先算（返回 0，m 变 1），再把 0 赋给 m → 最终 m == 0。

但 i++ + i++ 仍然 UB——两个 i++ 之间没有顺序保证。规则只覆盖了 =、[]、<<、>>、->*、函数调用的部分顺序，没有覆盖同一个运算符的两个操作数之间。

-Wunsequenced 能抓到一部分这类写法，但不是全部——不要依赖编译器警告。

5. 完整语义对照

int i = 10; ++i; int j = i++;   // 实测 i=12 j=11
int i = 5; int a = ++i;         // 实测 i=6 a=6
int i = 5; int b = i++;         // 实测 i=6 b=5

HFT / 嵌入式视角

  1. 养成 ++i 的习惯仍然值得，但理由要更新。不是为了快（-O2 下汇编相同），而是为了代码换类型时不用改：今天遍历 vector 无所谓，明天换成自定义迭代器或 -O0 构建，后置就开始掏拷贝费了。零成本的一致性收益。
  2. 真正该注意的是"副本被使用"的场景。auto old = it++; 是必须的拷贝，无法优化掉。在热路径的循环里如果只是为了推进迭代器，别用后置并把返回值丢掉——虽然 -O2 会救你，但 -O0 和跨翻译单元的场景救不了。
  3. -O0 构建（debug）里后置慢 16%。如果你的基准是在 debug 下跑的，别被这个数字误导去做代码修改——把优化打开再测。
  4. 别写 i++ + i++，C++17 也没救它。实测 i++ + i++、i++ + ++i、v[i] = i++ 三个都是 UB。拆成多条语句，每个表达式只对同一变量修改一次。HFT 里这类代码在不同编译器/优化级别下会给出不同结果，是最难复现的一类 bug。
  5. i = i++ 在 C++17 下可以依赖了（实测 m == 0）。但即便合法，也不要写——读代码的人得停下来想一遍求值顺序，可读性的损失远大于省下的那一行。
  6. 嵌入式上 -Os（优化尺寸）时优化强度低于 -O2，后置的副本消除可能不完全。MCU 上 ++i 更保险。

常见错误

1. i++ + i++ 以为"先取 i 再取 i+1"

int i = 1;
int k = i++ + i++;   // ❌ UB

C 程序员也踩这个——两边都是 UB。两个 i++ 在同一表达式中对 i 修改两次，且修改无顺序保证。拆开：int tmp1 = i++; int tmp2 = i++; int k = tmp1 + tmp2;。

2. 对迭代器用后置 it++

for (auto it = v.begin(); it != v.end(); it++) { ... }   // 能跑但低效

it++ 后置要拷贝旧迭代器返回再前进，循环里每次多一次拷贝。改 ++it：

for (auto it = v.begin(); it != v.end(); ++it) { ... }

C 里 p++ 和 ++p 对裸指针一样快，但 C++ 迭代器要换习惯。

3. 误以为后置 i++ 比 ++i "更安全"

// 误以为 ++i "太激进"，i++ "更温和"

错。两者对 i 的修改效果完全相同（都让 i 加 1），区别只在返回值——++i 返回修改后的 i，i++ 返回修改前的副本。单独写 ++i; 或 i++;（不用返回值）时两者完全等价。推荐 ++i 是因为对类类型/迭代器更高效，不是"更激进"。

自测题

1. 选择题　int i = 5; int j = ++i; 之后 i 和 j 的值分别是：

  • A. i=5, j=6
  • B. i=6, j=5
  • C. i=6, j=6
  • D. i=5, j=5
答案

C。前置 ++i 先让 i 变 6，再返回 i（6），赋给 j。所以 i=6, j=6。若用后置 i++：先返回 i 的原值（5）赋给 j，再让 i 变 6，结果 i=6, j=5。C 也是同样规则。

2. 判断题　对内置 int 类型，++i 和 i++ 在性能上有显著差异。

答案

错。内置类型上 ++i 和 i++ 性能几乎无差异（编译器优化后一样）。差异主要体现在类类型和迭代器——后置 i++ 要拷贝旧值返回，前置 ++i 直接返回引用。推荐 ++i 是为了在所有类型上都高效，养成习惯。

3. 踩坑题　下面这段代码哪里是 UB？

int i = 0;
int a = i++ + ++i;       // ①
int b = i++ + i++;       // ②
v[i] = i++;              // ③
答案

三个都是 UB： - ① i++ 和 ++i 在同一表达式对 i 修改两次，无序 → UB - ② 两个 i++ 同上 → UB - ③ v[i] 的下标 i 和右侧 i++ 修改 i 无序 → UB

C 里也都是 UB。修复：拆成多条语句，每个表达式只对同一变量修改一次。

#include <string>

std::string s = "test";

string、vector、自定义类成员访问都遵循此规则（见 3.2、7.1 类基础）。

为什么要两个符号（动机）

-> 本质是 (*p). 的语法糖——先解引用再取成员。那为什么还要单独一个符号？

① 可读性。 嵌套访问时 (*(*a).b).c 这种括号地狱，-> 让 a->b->c 一眼看穿。

② 可重载性。 . 在 C++ 里不能重载（这是语言设计上的有意决定：如果 . 能重载，任何表达式的含义都可能被改变，语言将失去可推理性）。而 -> 可以重载——这正是智能指针和迭代器能"假装是指针"的原因。

std::unique_ptr<Order> up;
up->price;    // up 不是指针，是类对象；靠 operator-> 重载"假装"成指针

所以规则是：. 用于对象/引用（不可重载），-> 用于指针或重载了 operator-> 的类。

底层实现与实测

环境：Apple clang 23.1.0，libc++，-std=c++17 -O2。可跑版本见文末例子。

1. 优先级陷阱：*p.member 是编译错误，不是"取成员的值"

Order* p = new Order{};
(*p).price;   // 实测 3.5  ✅
p->price;     // 实测 3.5  ✅
*p.price;     // ❌ 编译错误

. 的优先级高于 *，所以 *p.price 被解析成 *(p.price)——先对指针 p 取 price 成员，而指针没有成员，直接编译失败。

这个坑在 C 里同样存在（*p.field 一样错），但 C++ 里踩得更多，因为类成员访问频率高得多。好消息是：它是编译错误，不是静默错误——编译器会拦住你。

2. 引用用 .，不是 ->

Order& r = *p;
r.qty;     // 实测 10  ✅
r->qty;    // ❌ 编译错误
sizeof
Order*（指针） 8
r（Order& 引用） 16（= sizeof(Order)）

sizeof(引用) 得到的是被引用对象的大小——这从侧面说明引用不占独立存储，它就是对象的别名。语法上像对象，所以用 .。

3. operator-> 会递归展开直到拿到裸指针

这是 -> 最反直觉的特性：如果 operator-> 返回的还是一个类对象（而不是裸指针），编译器会继续对它应用 ->。

struct Wrapper { Order o;  Order*    operator->() { return &o; } };
struct Wrap2   { Wrapper w; Wrapper  operator->() { return w; } };

Wrapper w;  w->qty;    // 实测 10  ← 一层：返回 Order*
Wrap2  w2; w2->qty;   // 实测 10  ← 两层：返回 Wrapper，编译器继续展开

w2->qty 实际展开成 w2.operator->().operator->()->qty。这让"代理对象"可以完全伪装成指针——迭代器和智能指针就靠这个工作。

4. 智能指针：-> 能用，但 [] 不行

auto up = std::make_unique<std::vector<int>>(std::initializer_list<int>{1,2,3});
up->size();     // 实测 3      ✅ operator-> 返回 vector<int>*
(*up)[0];       // 实测 1      ✅ 先解引用得 vector&，再下标
(*up).at(1);    // 实测 2      ✅
up[0];          // ❌ 编译错误：unique_ptr 没有 operator[]

unique_ptr 只重载了 * 和 ->，没有 []。要下标必须先解引用。这是从裸指针迁到智能指针时最常见的卡壳点——vector<int>* 能写 p[0]（因为指针自带下标），unique_ptr<vector<int>> 不能。

（如果是 unique_ptr<T[]> 数组特化，则有 operator[]。）

5. ->* 和 .*：指向成员的指针（C++ 独有）

auto pm = &Order::price;    // pm 是"指向 Order 的 price 成员"的指针
p->*pm;     // 实测 3.5  （等价 p->price）
o2.*pm;     // 实测 9.9  （对象用 .*）
运算符 左侧 用途
.* 对象/引用 用成员指针访问成员
->* 指针 同上

C 里没有对应物（C 只有 offsetof）。这两个运算符的实际用途是把"访问哪个成员"变成运行期可变的——比如按配置字段排序、通用的序列化框架。优先级上它们低于 . 和 ->，但高于 *。

6. 空指针 -> 是 UB

nullptr->member 是 UB（大多数实现直接段错误，但标准不保证）。unique_ptr 也一样：

if (up) up->size();   // 先检查

HFT / 嵌入式视角

  1. . / -> 的选择在 -O2 下零成本差异——p->m 和 (*p).m 生成完全相同的一条 load。选哪个只看可读性。
  2. *p.member 是编译错误而不是静默错误，这点很幸运。但要注意类似形态的坑：*v.begin().m 之类，括号位置错了编译器会给你一长串模板报错。
  3. operator-> 的递归展开是"零开销代理"的基础。想写一个带日志/校验的行情句柄，重载 operator-> 就能让调用方毫无感知——但要注意每一次 -> 都是一次函数调用（-O2 下会内联）。
  4. 空指针解引用在 HFT 里是最常见的 crash 来源之一。行情代码里从 map 查找拿到的指针、从缓存取出的对象引用，访问前一律判空；optional<T> / unique_ptr 比裸指针更能表达"可能没有"。
  5. 嵌入式上没有 MMU 时，空指针 -> 不会段错误，而是直接读写地址 0 附近的区域（往往是中断向量表）——后果比崩溃还糟。这类平台上智能指针的判空检查尤其重要。
  6. ->* 在通用序列化/字段映射里很有用，但热路径上它是间接访问，无法内联——字段固定的场景直接用 . 更好。

和 C 的区别（成员访问：C/C++ 一致，C++ 多了引用和重载）

对比点 C C++
. 点运算符 ✅ 一致（struct 成员） ✅ 一致（struct/class 成员）
-> 箭头运算符 ✅ 一致（指针访问成员） ✅ 一致
(*p).member ≡ p->member ✅ ✅ 一致
. 优先级高于 * ✅ ✅ 一致
作用于引用 C 无引用 C++ 独有：引用用 .，像对象
成员函数 C struct 无成员函数 C++ class/struct 有成员函数 s.size()
-> 可重载 不能 智能指针/迭代器重载 ->

给 C 程序员的关键提醒： 1. . 和 -> 的选择规则两边一致——有对象/引用用 .，有指针用 ->。C 程序员的肌肉记忆直接用。 2. C++ 多了"引用"——引用在语法上像对象，用 .：

cpp std::string s = "hi"; std::string& r = s; // r 是引用，不是指针 r.size(); // ✅ 用 .，不是 ->

C 程序员习惯了"非对象即指针"，到 C++ 要加上"还有引用，引用用 ."。 3. C++ 的 -> 可重载——智能指针（unique_ptr、shared_ptr）和迭代器重载了 ->，让它们能像裸指针一样访问成员：

cpp std::unique_ptr<std::string> up = std::make_unique<std::string>("hi"); up->size(); // ✅ up 是智能指针，重载了 ->

C 里 -> 只对裸指针生效。

常见错误

1. *p.member 优先级错

std::string *p = &s;
std::cout << *p.size();   // ❌ 等价 *(p.size())，p 是指针没有 size 成员

. 优先级高于 *，所以 *p.size() 先算 p.size()（但 p 是指针没有 size 成员，编译错误）。正确写法：(*p).size() 或 p->size()。C 里 *p.field 同样错（p 是 struct 指针时），规则一致。

2. 对引用用 ->

std::string s = "hi";
std::string& r = s;
r->size();   // ❌ r 是引用不是指针，编译错误

引用在语法上像对象，用 .：r.size()。-> 只用于指针。C 程序员没有引用概念，容易把引用当指针用。

3. 智能指针忘了 -> 能用

std::unique_ptr<std::string> up = std::make_unique<std::string>("hi");
(*up).size();   // ✅ 能用但啰嗦
up->size();     // ✅ 推荐，智能指针重载了 ->

智能指针重载了 ->，能像裸指针一样访问成员。C 程序员从裸指针迁移到智能指针时，-> 习惯不用改。

  • B. p->size()
  • C. (*p).size()
  • D. *p.size()
答案

答案

3. 踩坑题　C 程序员写下面这段 C++ 代码，哪里有问题？

struct Order { int qty; double price; };
Order* p = get_order();
if (*p.price > 0) {       // 检查价格
    send_order(*p);
}
答案

修复（两种）：

if ((*p).price > 0) { ... }   // 括号改变优先级
if (p->price > 0) { ... }     // 推荐用 ->

C 里 (*p).price 和 p->price 也都合法，C 程序员的习惯直接迁移——只是 C++ 里这个坑更容易踩，因为类类型成员访问更频繁。

4. 应用题　用智能指针 std::unique_ptr<std::vector<int>> 创建一个 vector，访问其 size() 和第一个元素。

4.7

条件运算符

本节讲什么

C++ 唯一三元运算符 cond ? expr1 : expr2。

规则

  • 条件为 真 → 计算并返回 expr1 的值
  • 条件为 假 → 计算并返回 expr2 的值
  • 两分支类型须能统一（可能隐式转换）

嵌套

// grade > 90 ? "A" : grade > 60 ? "B" : "C"

优先级陷阱（必考）

?: 优先级很低，与 << 混用时必须加括号：

int grade = 75;
std::cout << (grade < 60 ? "fail" : "pass");  // ✅
// std::cout << grade < 60 ? "fail" : "pass"; // ❌ 等价 (cout<<grade)<60 ? ...

和 C 的区别（条件运算符：C/C++ 完全一致）

条件运算符是 C 和 C++ 完全共享的语法——cond ? a : b 的语义、优先级、结合律（右结合）、类型统一规则都一样：

对比点 C C++
cond ? a : b 语法 ✅ 一致 ✅ 一致
右结合 ✅ ✅ 一致
优先级很低（仅高于 = 和 ,） ✅ ✅ 一致
两分支类型须统一 ✅（隐式转换） ✅ 一致，但 C++ 更严格（左值分支）
?: 可作左值 ❌ ✅ C++ 独有（条件表达式可作左值，见下文）

给 C 程序员的关键提醒： 1. 条件运算符 99% 一样——语法、优先级、嵌套、<< 混用加括号，C 学的直接用。 2. C++ 多了"条件表达式可作左值"——((cond) ? a : b) = value; 在 C++ 合法（条件为真改 a，假改 b），C 里不行。但这种写法可读性差，不推荐。 3. C++ 的类型检查更严——两分支类型不同时，C 会做隐式转换（可能丢信息），C++ 也会转但编译器警告更积极。

为什么需要 ?:（动机）

?: 是 C++ 唯一的三元运算符，也是唯一能在表达式里做二选一的构造。if-else 只能用在语句位置，遇到下面三种场合就写不出来：

场合 if-else 为什么不行 ?:
初始化 int x; if (c) x = a; else x = b; —— const 变量、成员初始化列表里没法这么写 const int x = c ? a : b;
函数实参 / 返回值 要先声明临时变量，多两行 f(c ? a : b)
模板 / constexpr 上下文 语句不能出现在常量表达式里 ?: 可以是常量表达式（C++11 起）

一句话：if-else 控制"执行哪段代码"，?: 计算"取哪个值"。需要的是值的时候用 ?:。

底层实现与实测

环境：Apple clang 23.1.0，arm64-apple-darwin，-std=c++17 -O2。可跑版本见文末例子。

1. 只求值选中的那个分支（和 && 一样是短路的）

int left()  { ++g_l; return 1; }
int right() { ++g_r; return 2; }

(true  ? left() : right())   // 实测：left calls=1, right calls=0
(false ? left() : right())   // 实测：left calls=0, right calls=1

这是 ?: 与函数调用的关键区别：pick(true, left(), right()) 里两个实参都会被求值（而且顺序未指定），?: 只算一个。把昂贵计算放 ?: 分支里是安全的。

2. 公共类型规则：同类型不提升，不同类型才做转换

实测 sizeof：

表达式 sizeof 说明
c ? (short)1 : (short)2 2 两分支同类型 → 结果就是 short，不整型提升
c ? (char)1 : (char)2 1 同理，不提升
c ? (short)1 : (char)2 4 类型不同 → 都提升到 int
c ? 'a' : 1 4 char → int
c ? 1 : 2.5 8 int → double
c ? 'a' : 1.5f 4 char → float
c ? 1 : 2u 4 int → unsigned

最容易错的是第一行：很多人以为 ?: 会像算术运算一样做整型提升，其实只有两分支类型不同时才走 usual arithmetic conversions。写 auto v = c ? (short)a : (short)b; 得到的就是 short。

3. C++ 独有：两分支都是同类型左值时，结果是左值

int p = 5, q = 9;
(p > 0 ? p : q) = 99;    // C++ 合法，实测 p=99 q=9

同一行 C 代码报错：

error: expression is not assignable

条件（C++ 规则）：两个分支是相同类型的左值 → 整个 ?: 结果是左值，可以赋值、可以取地址。任一分支是右值（如字面量、或两分支类型不同）→ 结果是纯右值，不能赋值。

教材和本节都建议别用这个特性——(cond ? a : b) = v 可读性极差。知道它存在是为了读懂别人的代码，不是为了写。

4. 右结合：a ? b : c ? d : e 是 a ? b : (c ? d : e)

int g = 75;
g > 90 ? 'A' : g > 60 ? 'B' : 'C'    // 实测 'B'

如果是左结合，(g>90 ? 'A' : g>60) ? 'B' : 'C' 会得 'B' 之外的东西（实际会因类型不匹配报错）。?: 与 =、一元运算符是少数右结合的。

5. 与 if-else 生成完全相同的汇编

int tern (int x) { return x > 0 ? x : -x; }
int ifver(int x) { if (x > 0) return x; else return -x; }

-O2 下两个函数的汇编逐字节相同：

cmp  w0, #0
cneg w0, w0, mi     ; 负数则取负 —— 条件选择指令，无分支
ret

现代编译器把两者都识别成"条件选择"（csel / cneg / csinc），根本不生成跳转。所以 ?: 与 if-else 之间不存在性能差异，选哪个只看可读性。

6. 优先级陷阱：?: 几乎最低，与 << 混用必炸

std::cout << grade < 60 ? "fail" : "pass";   // 解析成 (cout << grade) < 60 ? ... 
std::cout << (grade < 60 ? "fail" : "pass"); // ✅

?: 的优先级只高于 = 和 ,——比 <<、==、&& 都低。实际上第一种写法在 C++ 里编译期就报错（ostream 没有 < 运算符），算是个仁慈的失败；如果换成能和整数比较的类型，就会静默算错。

HFT / 嵌入式视角

  1. ?: 是常量表达式，能进模板参数和数组维度。std::array<int, N ? N : 1>、if constexpr 之前的编译期分支都靠它。if-else 语句在这些位置根本不合法。
  2. 把昂贵分支放后面没有意义——?: 只算选中的那个。但反过来，如果两分支都便宜，?: 与 if-else 性能完全相同（实测汇编一致），别为了"省一次分支"硬写 ?:，可读性优先。
  3. 类型统一规则会静默改变精度：c ? price_int : price_double 会把整数价格转成 double。HFT 里价格常用定点整数（int64_t 存 1e-8 精度），一旦被 ?: 提升到 double 就丢了精确性，而且没有任何警告。规矩：?: 两分支显式同类型，热路径上宁可写 static_cast。
  4. auto + ?: 是陷阱：auto v = c ? (short)a : (short)b; 得到 short（实测 sizeof=2），而 auto v = c ? (short)a : (char)b; 得到 int。加了 auto 之后类型完全由公共类型规则决定，改一个分支的类型就会静默改变 v 的类型。
  5. 别用 (cond ? a : b) = v。虽然 C++ 合法（实测可行），但这是"最需要读者停下来想三秒"的写法之一。改成 if (cond) a = v; else b = v; 零成本。

常见错误

1. ?: 与 << 混用不加括号

std::cout << grade < 60 ? "fail" : "pass";   // ❌

<< 优先级高于 ?:，等价 (std::cout << grade) < 60 ? "fail" : "pass"——先输出 grade，再把 cout 和 60 比（无意义），最后条件判断。修复：std::cout << (grade < 60 ? "fail" : "pass");。C 里 printf 没这个坑（printf("%s", grade<60?"fail":"pass")），C++ 的 << 容易踩。

2. 嵌套 ?: 不加括号可读性差

grade > 90 ? "A" : grade > 60 ? "B" : "C"   // 能跑但难读

?: 右结合，所以这等价 grade > 90 ? "A" : (grade > 60 ? "B" : "C")，逻辑对但可读性差。复杂条件用 if-else：

char grade_letter;
if (grade > 90) grade_letter = 'A';
else if (grade > 60) grade_letter = 'B';
else grade_letter = 'C';

3. 两分支类型不匹配导致意外转换

auto x = cond ? 1 : 2.5;   // x 类型是 double（1 隐式转 double）

两分支类型不同时，编译器会做隐式转换统一——1（int）和 2.5（double）统一为 double。若不注意，可能丢失信息或改变类型。显式统一：cond ? 1.0 : 2.5 或 cond ? static_cast<double>(1) : 2.5。

自测题

1. 选择题　?: 运算符的结合律是：

  • A. 左结合
  • B. 右结合
  • C. 未指定
  • D. 取决于编译器
答案

B。?: 右结合，a ? b : c ? d : e 等价 a ? b : (c ? d : e)。C 也是右结合，完全一致。赋值 =、一元运算符、?: 是少数右结合的运算符。

2. 判断题　std::cout << x < 0 ? "neg" : "pos"; 能正确打印 x 的正负。

答案

错。<< 优先级高于 ?:，等价 (std::cout << x) < 0 ? "neg" : "pos"——先输出 x，再把 cout 和 0 比（无意义），最后条件判断结果总是 "pos" 或 "neg" 但没输出。修复：std::cout << (x < 0 ? "neg" : "pos");，加括号。C 里 printf 没这个坑。

3. 踩坑题　下面这段代码想根据 flag 选 a 或 b 赋值给 target，哪里有问题？

int a = 10, b = 20;
int target = 0;
flag ? a : b = 100;   // 想把选中的变量改为 100
答案

flag ? a : b = 100 在 C 里是 UB 或语义错——?: 优先级高于 =，等价 (flag ? a : b) = 100。C++ 里条件表达式可作左值（C 不行），所以C++ 能编译（flag 为真改 a，假改 b），但可读性极差。

更清晰的写法：

if (flag) a = 100; else b = 100;
// 或
(flag ? a : b) = 100;   // C++ 合法但不推荐

C 里这种写法编译错误或行为错，C++ 能过但别这么写。

4. 应用题　用 ?: 写一个 abs 函数，返回 x 的绝对值。

答案 
int my_abs(int x) {
    return x < 0 ? -x : x;
}

要点： - x < 0 为真返回 -x，假返回 x - 注意 -INT_MIN 是 UB（见 4.2），生产代码要处理 - C 等价写法一模一样：return x < 0 ? -x : x;

C 程序员的 ?: 习惯直接迁移，C++ 无差异。

5. 判断题　?: 比 if-else 快，因为它不产生分支跳转。

答案

错。?: 和 if-else 在 -O2 下生成的汇编逐字节相同。

实测（x > 0 ? x : -x vs if (x>0) return x; else return -x;）：

cmp  w0, #0
cneg w0, w0, mi     ; 条件取负，无分支跳转
ret

两个函数都编译成这两条指令——编译器把两者都识别成"条件选择"，用 csel/cneg/csinc 这类条件选择指令实现，根本不生成跳转。

结论：选 ?: 还是 if-else 只看可读性（需要"值"用 ?:，需要"执行动作"用 if-else），性能上没有任何区别。真正要避免的是不可预测的分支（见 5.3 条件语句 的分支预测实测），而不是 ?: 这个语法形式。

6. 应用题　HFT 订单路由代码：

int64_t price_fixed = ...;          // 定点价格，1e-8 精度，整数存储
double  price_dbl   = ...;          // 某些通道只收 double

auto p = use_double_channel ? price_dbl : price_fixed;   // ①
send(route(cond ? 'B' : 'S'), p);                        // ②

指出 auto + ?: 的两处风险并给出改写。

答案

风险 ①：auto p = use_double_channel ? price_dbl : price_fixed; 两分支类型不同（double 和 int64_t）→ 公共类型是 double → p 永远是 double。定点价格被静默转成 double，int64_t 能精确表示的大整数（> 2^53）会丢精度，而且编译器一声不响。

风险 ②：cond ? 'B' : 'S' 两个 char 分支类型相同 → 结果是 char（sizeof=1），这没错；但如果哪天有人把一侧改成字符串字面量 "B"，公共类型瞬间变成 const char*，route() 的重载决议跟着变——改一个分支的类型会静默改变整条表达式的类型。

改写：显式类型 + 拆开写，别让 auto 猜。

// ① 两条通道各自明确类型，不混在一个 ?: 里
if (use_double_channel) {
    send_double(route(cond ? 'B' : 'S'), static_cast<double>(price_fixed));
} else {
    send_fixed(route(cond ? 'B' : 'S'), price_fixed);   // 保持 int64_t 精确
}

// ② 如果确实要一个值，显式声明类型，不写 auto
char side = cond ? 'B' : 'S';
const char* side_str = cond ? "B" : "S";   // 需要字符串时另写一行

要点： - 公共类型规则：同类型不提升（实测 short/short → sizeof 2），不同类型才做转换（int/double → sizeof 8）。 - auto + ?: 的组合最危险——变量类型完全由分支类型决定，改一处就静默改一片。热路径上一律显式写类型，或加 static_cast 固定。 - 定点价格绝不进 double。

4.8

位运算符

本节讲什么

~ << >> & | ^——教材建议只对无符号整数使用。

各运算符

运算符 含义
~ 按位取反
<< 左移：右侧丢弃，左侧补 0；等价 × 2ⁿ（无溢出时）
>> 右移：无符号左侧补 0；有符号补符号位（实现相关，不推荐）
& 按位与（掩码）
| 按位或
^ 按位异或 
unsigned flags = 0x01;
flags |= 0x02;           // 置位
if (flags & 0x01) { }    // 测位

与逻辑运算符区别

  • & | ^：无短路，两侧都求值
  • && ||：短路（见 4.3）

HFT 典型用途

协议标志位、权限掩码、快速 ×2 / ÷2（无符号左移/右移）；解析二进制字段时常与 unsigned 掩码配合。

和 C 的区别（位运算符：C/C++ 完全一致）

位运算符是 C 和 C++ 完全共享的部分——~ << >> & | ^ 的语义、整型提升、有符号右移实现相关，两边一字不差：

对比点 C C++
~ & \| ^ 按位运算 ✅ 一致 ✅ 一致
<< 左移补 0 ✅ ✅ 一致
>> 有符号补符号位（实现相关） ✅ ✅ 一致
>> 无符号补 0 ✅ ✅ 一致
整型提升（char/short → int） ✅ ✅ 一致
&/\| 无短路 ✅ ✅ 一致
有符号左移溢出 UB ✅ ✅ 一致

给 C 程序员的关键提醒： 1. 位运算符无需任何转变——C 学的"位运算心法"直接用。掩码、置位、测位、异或交换、x & (x-1) 消最低位 1 这些技巧两边通用。 2. 教材建议"只对无符号用位运算"两边都适用——有符号右移补符号位是实现相关（不同编译器可能不同），有符号左移溢出是 UB。用 unsigned/uint32_t 做位运算是跨平台安全的做法。 3. C++ 多了 std::bitset——固定大小位集合，比手写 unsigned flags 更安全（自带边界检查、[] 访问位、to_string/to_ulong 转换）。但 HFT 热路径仍用 uint64_t + 位运算（零开销）。

为什么位运算在 C++ 里还留着（动机）

位运算是 C 从"高级汇编"时代继承下来的低层能力，C++ 完整保留，因为它解决的是别的东西解决不了的问题：

需求 位运算方案 不用位运算要怎么写
一个字节塞 8 个布尔开关（O_RDONLY\|O_CREAT\|O_TRUNC） flags \|= 1u << n 8 个 bool 成员 = 8 字节，且不能原子操作
硬件寄存器读-改-写 REG \|= (1u<<3) 无替代，硬件就是按位定义的
二进制协议字段解包（FIX / 交易所行情） x & 0xFF、x >> 24 结构体 + memcpy，还多一层字节序问题
快速 ×2ⁿ / ÷2ⁿ x << n / x >> n 现代编译器会把 *4 也优化成 lsl，无需手写
权限/选项掩码 mode & 0777 无替代

教材建议"只对无符号用位运算"的理由很实在：有符号类型的右移是补符号位还是补 0 是标准没定的（implementation-defined），左移进符号位是 UB。用 unsigned / uint32_t 就把这两个不确定性一次性消除了。

底层实现与实测

环境：Apple clang 23.1.0，arm64-apple-darwin，-std=c++17 -O2。可跑版本见文末例子。

1. 优先级：& 比 == 低（测位最经典的静默 bug）

int x = 0x100;
x & 0xFF == 0        // 实测 0 —— 被解析成 x & (0xFF == 0)，即 0x100 & 0
(x & 0xFF) == 0      // 实测 1 —— 这才是"低 8 位全 0"

warning: & has lower precedence than ==; == will be evaluated first [-Wparentheses]

这是位运算头号 bug：不崩、不报错，只是条件永远为假。ARM 上 and 一条指令的事，语义上却整个反了。

2. 移位的三种边界（实测值）

写法 实测结果 状态
-8 >> 1 -4 实现定义（标准没定补符号位还是补 0）
1 << 31 -2147483648 UB（int 左移进符号位）
1u << 32 2147483648 UB（移位量 ≥ 位宽，clang 报 -Wshift-count-overflow）
1u << 31 2147483648 ✅ 正确写法

注意 1u << 32 的"实测值"是 2147483648——在 ARM 上移位量会被按位宽取模（32 % 32 = 0？实际得 2^31），不同架构不同。UB 的意思就是"不要依赖这个数字"，它随时可能因为优化级别变化。

3. 位运算 ≠ 乘除：负数上不等价

x =  100:  x*4=400,  x<<2=400,  x/8=12,  x>>3=12    // 正数一致
x = -100:  x/8=-12,  x>>3=-13                        // ← 负数不一致！

/ 是向零取整（-12.5 → -12），>> 是向下取整（算术右移，-12.5 → -13）。

且现代编译器会把 / 8 也编译成右移+修正序列，所以 x / 8 并不比 x >> 3 慢。别为了"快"用 >> 代替 /——你只得到了错误的行为。

4. popcount：内建 vs 手写，差 52–62 倍（复测修正）

100 万次，数据取自运行时填充的数组（避免常量折叠）：

实现 耗时 折合
__builtin_popcountll(vals[k & 255]) 0.71 ms（第二次 0.50 ms） 0.71 ns/次
手写 while (x) { n += x&1; x >>= 1; } 44.13 ms（第二次 25.87 ms） 44.13 ns/次

52–62 倍（两次实测 61.8x / 52.1x）。ARMv8 有 CNT 指令（一条指令算完 8 字节的位数），编译器把内建函数直接映射过去；手写循环是 64 次迭代。

⚠ 复测修正：原记的 34 倍偏低，原因是早先的测法把常量参数传进了纯函数，-O2 直接折叠掉整个调用，测出的其实是空循环。 改成运行时数据后（vals[k & 255]），真实差距在 50 倍以上。

（x86 上要 popcnt 指令需要 -mpopcnt，否则退化成查表。跨平台的正确做法：#if defined(__GNUC__) || defined(__clang__) 用 __builtin_popcountll。）

5. std::bitset 和手写 uint64_t 开销同量级

1000 万次 set / reset / test：

实现 耗时
uint64_t + \|= &= & 18.6 ms
std::bitset<64> 18.4 ms（0.99x）

修正一个流传很广的说法：很多资料说 bitset "更安全但稍有开销"。实测在 -O2 下两者同量级，互有胜负——bitset 的成员函数全被内联成同样的移位掩码指令。所以：

  • 需要固定宽度 + 边界检查 + to_string()/to_ulong() → 用 bitset，几乎不花钱
  • 需要热路径极致控制 / 跨语言 ABI / 放进共享内存 → 用 uint64_t（bitset 的内部表示不是标准规定的，不能跨编译器 ABI）

6. 异或交换：不快，而且有自交换陷阱

static void xor_swap(unsigned& a, unsigned& b) { a ^= b; b ^= a; a ^= b; }
场景 实测
xor_swap(x, y) 1000 万次 vs 临时变量版 5.6 ms vs 5.1 ms —— 异或版更慢（多两条指令、且破坏依赖链）
xor_swap(x, x)（同一对象） x 变成 0 —— 真陷阱
同值不同对象 xor_swap(42, 42) 正常（42, 42）

结论：异或交换是 1970 年代"省一个寄存器"的技巧。现代编译器下它不快（实测慢 10%），还有自交换归零的 bug。永远用 std::swap。

7. 常用位技巧（实测有效）

while (w) { w &= (w - 1); ++cnt; }   // 每次消掉最低位的 1
// 实测：0xF0F0F0F0F0F0F0F0 有 32 个 1，循环 32 次（不是 64 次）

n && !(n & (n - 1))                  // 判 2 的幂：8 → 1，7 → 0

x & (x-1) 的复杂度是 O(位数个数) 而不是 O(位宽)，这是它比循环移位快的原因。

HFT / 嵌入式视角

  1. 硬件寄存器操作一律 unsigned + 复合赋值。REG->CR |= (1u << 3) 在 ARM 上是 ldr/orr/str 三条指令；写成 REG->CR = REG->CR | (1u<<3) 会读两次——对"读即清"状态寄存器是功能性 bug（见 4.4 实测）。
  2. 行情/订单的 Flags 字段用 uint64_t 打包。交易所二进制协议（如 NASDAQ ITCH、上交所 FAST）普遍把多个布尔/枚举塞进一个 64 位字。解包用 >> + & 掩码，比读结构体再 memcpy 更快也更可控（不引入字节序问题——位移和掩码是字节序无关的）。
  3. 别用 >> 代替除法，别用 << 代替乘法。实测 /8 与 >>3 在负数上差 1，而编译器早就把 /8 优化成移位了——手写 >> 只带来错误，不带来速度。
  4. popcount 用内建函数。位图（bitmap）统计活跃订单、订单簿档位占用、回测里的信号向量计数——50 倍以上的差距在这种地方是实打实的。
  5. -Wall 必须开。1u << 32 会报 -Wshift-count-overflow，flags & 0x01 == 0 会报 -Wparentheses。这两条是位运算最常见也最致命的两个 bug，编译器都能免费抓到。
  6. 共享内存 / 网络传输中用固定宽度类型。uint32_t / uint64_t 而不是 unsigned（后者宽度随平台变）。嵌入式交叉编译时这一条尤其重要。

常见错误

1. 对有符号整数右移

int x = -8;
int y = x >> 1;   // 实现相关：可能是 -4（算术右移）或大正数（逻辑右移）

有符号右移补符号位（算术右移）还是补 0（逻辑右移）是实现相关——x86/GCC/Clang 补符号位，某些嵌入式平台补 0。用 unsigned 保证补 0。C 和 C++ 都有这个坑。

2. & 误用为 &&

if (flags & 0x01) { ... }      // ✅ 测位：flags 和 0x01 按位与，非 0 为真
if (flags && 0x01) { ... }     // ❌ 逻辑与：flags 非 0 且 0x01 非 0（恒真）

& 是位与，&& 是逻辑与。测位用 &，逻辑判断用 &&。C 程序员分得清，但 C++ 里 bool 和 int 隐式转换更容易混。

3. 移位位数超过类型宽度

int x = 1;
int y = x << 32;   // ❌ UB（int 通常 32 位，移 32 位未定义）

移位位数 >= 类型位宽是 UB（C 和 C++ 都一样）。int 32 位时 << 32、<< 33、<< 100 都是 UB。确保移位位数 < sizeof(T)*8。

自测题

1. 选择题　unsigned x = 0xF0; x & 0x0F 的结果是：

  • A. 0xF0
  • B. 0x0F
  • C. 0xFF
  • D. 0x00
答案

D。0xF0（11110000）和 0x0F（00001111）按位与，每位都不同，结果是 0x00。这是"掩码取低位"的反例——x & 0x0F 取 x 的低 4 位，但 x = 0xF0 的低 4 位是 0。C 也是同样运算。

2. 判断题　int x = -1; x >> 1 的结果在所有 C++ 实现上都相同。

答案

错。有符号右移是实现相关——x86/GCC/Clang 补符号位（算术右移），-1 >> 1 还是 -1；某些嵌入式平台补 0（逻辑右移），-1 >> 1 是大正数。用 unsigned 保证补 0，跨平台一致。C 也有同样问题。

3. 踩坑题　HFT 代码用位运算快速除以 2，哪里有问题？

int qty = -10;
int half = qty >> 1;   // 想得到 -5
答案

结果实现相关。qty 是 int（有符号），>> 1 在 x86/GCC/Clang 上补符号位（算术右移）得 -5，但在补 0 的平台上得大正数。修复：

// 方法 1：用除法（编译器会优化为右移）
int half = qty / 2;   // 总是 -5，跨平台一致

// 方法 2：用 unsigned（但会改变负数语义）
// unsigned 不能表示 -10，要先转

// 方法 3：HFT 常用定点小数，用 int64_t + 显式除法

C 程序员习惯用 >> 1 替代 / 2（快），但对负数不安全。现代编译器会把 / 2 优化成右移，无需手写 >>。

4. 应用题　用位运算实现"置位、清位、测位、翻转位"四个操作，操作 flags 的第 n 位。

答案 
unsigned flags = 0;
int n = 3;   // 操作第 3 位（0-indexed）

flags |= (1u << n);       // 置位：或上 1<
flags &= ~(1u << n);      // 清位：与上 ~(1<
bool set = flags & (1u << n);   // 测位：与 1<
flags ^= (1u << n);       // 翻转位：异或 1<<

要点： - 用 1u（unsigned）避免有符号移位问题 - n 必须 < sizeof(unsigned)*8（通常 32），否则 UB - C 程序员的位运算心法直接迁移，C++ 无差异

C++ 还可用 std::bitset：

std::bitset<32> flags;
flags.set(n);      // 置位
flags.reset(n);    // 清位
flags.test(n);     // 测位
flags.flip(n);     // 翻转

更安全但稍有开销，HFT 热路径仍用 unsigned + 位运算。

5. 判断题　x >> 3 比 x / 8 快，所以热路径上应该用 >> 代替除法。

答案

错，而且会算错。两方面的理由都不成立：

① 性能上没收益。现代编译器早就把 / 8 编译成右移（外加一条修正指令处理负数）。实测把 /8 换成 >>3 没有任何可测量的加速。

② 正确性上会出错。正数一致，负数不一致：

x =  100:  x/8 = 12,  x>>3 = 12    ← 一致
x = -100:  x/8 = -12, x>>3 = -13   ← 差 1！

原因：/ 向零取整（-12.5 → -12），>> 向下取整（-12.5 → -13）。

结论：写 x / 8。可读、跨平台、编译器会优化。手写 >> 只带来 bug，不带来速度。 而且 >> 对负数是实现定义行为（补符号位还是补 0 由平台定），在补 0 的嵌入式平台上 -100 >> 3 会变成一个大正数，不是 -13。

6. 应用题　交易所行情包里一个 64 位字段 raw 的位布局如下，写出解包代码，并说明为什么不能用 struct + memcpy：

bit  0..31  : price      (定点，1e-8 精度，无符号)
bit 32..39  : qty_scale  (8 位)
bit 40..47  : flags      (8 位开关)
bit 48..63  : seq        (16 位序号)
答案 
// 只用移位 + 掩码，字节序无关
struct Tick {
    uint64_t price;      // 定点价格
    uint8_t  qty_scale;
    uint8_t  flags;
    uint16_t seq;
};

Tick unpack(uint64_t raw) {
    Tick t;
    t.price     =  raw         & 0xFFFFFFFFull;   // 取低 32 位
    t.qty_scale = (raw >> 32)  & 0xFFull;
    t.flags     = (raw >> 40)  & 0xFFull;
    t.seq       = (raw >> 48)  & 0xFFFFull;
    return t;
}

// 判某个开关位
constexpr uint8_t FLAG_TRADE = 1u << 0;
bool is_trade(const Tick& t) { return (t.flags & FLAG_TRADE) != 0; }  // 括号！

为什么不用 struct + memcpy：

  1. 位域（bit-field）的布局是标准未指定的——struct { uint64_t price:32; uint64_t qty:8; ... } 各位段从低到高还是从高到低、是否跨字边界，编译器说了算。同一份代码在 GCC 和 clang 上可能解出不同结果。
  2. memcpy 引入字节序依赖——小端机（x86、ARM 默认）和大端机解出的 raw 不同。而移位和掩码是字节序无关的：它们作用在"数值"上，不在内存字节序列上。行情网关要对接多家交易所、可能跑在不同架构上，这一点是硬要求。
  3. 性能：解包是 and + lsr 各几条指令，比 memcpy 加结构体读取更快，且编译器能完全常量折叠。

要点： - 移位量必须 < 位宽（1u << 32 是 UB，实测给 2147483648） - 掩码用 ull 后缀 + & 0xFF 显式截断 - 测位写 (x & M) != 0 而不是 x & M（避免 & 低于 == 的坑）

4.9

sizeof 运算符

本节讲什么

计算类型或表达式占用的字节数；返回 size_t（无符号）。

两种写法

sizeof(int);     // 类型
sizeof(var);     // 表达式（一般不求值 var，见下）
sizeof var;      // 变量可省略括号（不推荐与类型混淆）

两大特性（必考）

1. 数组名 vs 指针

int arr[10];
sizeof(arr);     // 整个数组：10 * sizeof(int)
int *p = arr;
sizeof(p);       // 指针大小，如 8（64 位）

数组不退化的例外之一（见 3.5.3）。

2. 不对指针解引用

int *p = nullptr;
sizeof(*p);      // ✅ 只算 int 的大小，不访问 *p，不崩溃

用途

  • 估算结构体/数组占用
  • sizeof(arr)/sizeof(arr[0]) 得数组元素个数（仅当 arr 仍是数组名时）

和 C 的区别（sizeof：C/C++ 几乎一致，C++ 多了成员/类类型支持）

对比点 C C++
sizeof(type) ✅ 一致 ✅ 一致
sizeof(expr) ✅ 一致 ✅ 一致
返回 size_t ✅ ✅ 一致
数组不退化 ✅ ✅ 一致
不求值操作数 ✅ ✅ 一致
sizeof 类/struct 成员 C99 起部分支持 ✅ 完整支持
sizeof 类类型本身 C 无 class ✅
编译期常量 ✅（除 VLA） ✅（C++ 无 VLA，恒编译期）

给 C 程序员的关键提醒： 1. sizeof 语义两边几乎一致——sizeof(int)、sizeof(arr)、sizeof(arr)/sizeof(arr[0]) 这些用法 C 学的直接用。 2. C++ 多了对类类型的支持——sizeof(std::string)、sizeof(std::vector<int>)、sizeof(MyClass) 都合法。但要注意：sizeof(std::string) 是 string 对象本身的大小（通常 24/32 字节），不是字符串内容长度（用 s.size()）。 3. C 的 VLA 让 sizeof 可能是运行期——C99 的 VLA int arr[n]; 让 sizeof(arr) 在运行期求值。C++ 不支持 VLA（标准层面），sizeof 恒编译期常量。这是少数 C++ 比 C 更"静态"的地方。

常见错误

1. 数组传参后 sizeof 拿不到长度

void f(int arr[]) {
    size_t n = sizeof(arr) / sizeof(arr[0]);   // ❌ arr 退化指针，n = 8/4 = 2
}

数组传参退化为指针，sizeof(arr) 是指针大小。C 和 C++ 都有这个坑。用 std::array/vector 或模板引用避开。

2. sizeof(string) 误以为是字符串长度

std::string s = "hello";
std::cout << sizeof(s);   // 24 或 32（string 对象大小），不是 5
std::cout << s.size();    // 5（字符串长度）

sizeof(std::string) 是 string 对象本身的字节大小（固定，通常 24/32 字节，含指针/长度/容量），不是字符串内容长度。内容长度用 s.size() 或 s.length()。C 程序员习惯了 sizeof(char[]) 算字符数组长度，到 string 要改用 size()。

3. sizeof(*nullptr) 以为会崩

int* p = nullptr;
std::cout << sizeof(*p);   // ✅ 4（int 大小），不崩溃

sizeof 的操作数不求值——编译器只看类型，不执行解引用。所以 sizeof(*p) 安全，等于 sizeof(int)。但别依赖这个写运行期代码——*p 在运行期仍是 UB，只是 sizeof 上下文不求值。

九个真相（本机实测，examples/4.9-1-sizeof-traps.cpp）

# 真相 实测
1 编译期常量，不是运行时函数 int fixed[sizeof(int)*4] 合法，static_assert 可用
2 不对操作数求值 sizeof(i++) 之后 i 仍是 5 —— ++ 根本没执行
3 数组传参后退化 定义处 sizeof(arr)=40，形参里 sizeof(a)=8
4 字符串字面量含 \0 sizeof("abc")=4，strlen("abc")=3
5 结构体有对齐填充 {char;int;char}=12，换成 {int;char;char}=8（省 4 字节）
6 空类是 1 字节 若为 0，两个不同对象地址会相同
7 有虚函数 +8 vptr
8 sizeof 引用 = 被引用类型 sizeof(int&)=4，引用没有自己的大小
9 返回 size_t（无符号） sizeof(int) - 5 = 18446744073709551615（下溢）

三条最容易踩的

① 不求值——sizeof(i++) 不会执行 ++。clang 会警告：

warning: expression with side effects has no effect in an unevaluated context [-Wunevaluated-expression]

这也是 sizeof 能安全地用在模板/decltype 里的原因：只要类型，不要值。

② 数组一传参就退化——函数内部 sizeof(形参) 拿到的是指针大小。clang 也会警告：

warning: sizeof on array function parameter will return size of 'int *' instead of 'int[10]' [-Wsizeof-array-argument]

长度必须显式传（或改用 std::array / std::span）。

③ 无符号下溢——sizeof(x) - n 当 n > sizeof(x) 时是个巨大正数。if (sizeof(a) - 5 > 0) 永远是真。

标准库类型的大小（SSO 实证）

sizeof(std::string)      = 24     ← libc++：ptr + size + SSO 联合体
sizeof(std::vector<int>) = 24     ← begin + end + capacity 三指针

短字符串 "abc" 的 c_str() 距对象首地址 0 字节（就在对象内部 = SSO，无堆分配）；31 字符的长字符串则指向堆。这解释了"为什么短字符串构造没有 malloc"。

常见错误补充

  1. 以为 sizeof(i++) 会执行 ++：sizeof 是未求值操作数（unevaluated operand），++ 不执行（-Wunevaluated-expression）。
  2. sizeof 结果参与有符号运算：sizeof 返回 size_t，与 int 混算会整体提升为无符号，sizeof(a) - 10 可能是个天文数字。
  3. 以为成员顺序不影响结构体大小：实测 {char;int;char} 是 12 字节，{int;char;char} 是 8 字节——把大成员往前放。

自测题

1. 选择题　int arr[5]; int* p = arr; 下列哪个表达式返回指针大小（而非数组大小）？

  • A. sizeof(arr)
  • B. sizeof(arr[0])
  • C. sizeof(p)
  • D. sizeof(*p)
答案

C。sizeof(p) 是指针大小（如 8 字节，64 位）。sizeof(arr) 是整个数组大小（5*4=20）；sizeof(arr[0]) 是单个 int 大小（4）；sizeof(*p) 是 int 大小（4）。C 也是同样规则。

2. 判断题　std::string s = "hello"; sizeof(s) 返回 5。

答案

错。sizeof(s) 返回 std::string 对象本身的字节大小（固定，通常 24 或 32 字节，含内部指针/长度/容量），不是字符串内容长度。内容长度用 s.size()（返回 5）。C 程序员习惯 sizeof(char[]) 算字符数组长度，到 string 要改用 size()。

3. 踩坑题　C 程序员写下面这段 C++ 代码，想算数组长度，哪里有问题？

void process(int arr[]) {
    size_t n = sizeof(arr) / sizeof(arr[0]);
    for (size_t i = 0; i < n; ++i) {
        std::cout << arr[i] << " ";
    }
}
答案

sizeof(arr) 在函数内是指针大小，不是数组大小。数组传参退化为指针，sizeof(arr) 是 8（64 位指针），sizeof(arr[0]) 是 4，n = 8/4 = 2，只打印前 2 个元素。

修复（三种）：

// 方法 1：C 风格，另传长度
void process(int* arr, size_t n);

// 方法 2：C++ 模板引用数组，保留类型
template <size_t N>
void process(int (&arr)[N]) {
    for (size_t i = 0; i < N; ++i) std::cout << arr[i] << " ";
}

// 方法 3：用 std::array 或 vector
void process(const std::vector<int>& v);

C 程序员习惯了"另传 n"，C++ 推荐用容器或模板引用避开退化。

4. 应用题　写一个模板函数 array_size，编译期返回任意内置数组的元素个数。

答案 
#include <cstddef>

template <typename T, size_t N>
constexpr size_t array_size(const T (&)[N]) {
    return N;
}

// 用法
int arr[10];
constexpr size_t n = array_size(arr);   // 编译期得 10
double vals[5];
constexpr size_t m = array_size(vals);  // 5

要点： - const T (&)[N] 是"对数组的引用"，不退化 - 模板推导自动得 N，函数内返回 N - constexpr 让结果可在编译期使用（C++ 独有，替代 #define 那种宏）

C 没有这种能力——C 的数组传参必然退化，只能 #define ARRAY_SIZE(a) (sizeof(a)/sizeof((a)[0])) 用宏，但宏在传参后同样失效。

C++17 起还有 std::size(arr)，直接返回数组长度。

4. 选择题：void f(int a[10]) { ... } 里的 sizeof(a) 是多少？ - A) 40 - B) 8（int* 的大小） - C) 10 - D) 取决于实参

答案

B（64 位上是 8）。

数组作为形参时会退化成指针，void f(int a[10]) 等价于 void f(int* a)，所以 sizeof(a) == sizeof(int*) == 8。clang 会警告 -Wsizeof-array-argument。

A 是"定义处"的 sizeof（int arr[10] 才是 40）。函数内部拿不到数组长度，必须额外传 size，或用 std::array<int,10> / std::span<int>（C++20）保住尺寸信息。

5. 代码题：下面代码输出什么？

int i = 5;
size_t s = sizeof(i++);
printf("%zu %d", s, i);
答案

输出 4 5——i 没有被自增。

sizeof 的操作数是未求值的：编译器只需要它的类型，不会生成执行 ++ 的代码。clang 会给出 -Wunevaluated-expression 警告提醒你"这个副作用不会发生"。

同理 sizeof(f()) 不会真的调用 f——哪怕 f() 有副作用、哪怕 f 只有声明没有定义也能编译通过。

4.10

逗号运算符

本节讲什么

逗号运算符 , 的求值顺序与返回值；与函数参数逗号、初始化列表逗号的区别。

规则

  • 从左到右依次求值每个子表达式
  • 整个表达式的值 = 最右侧子表达式的值
  • 优先级最低（见 4.12）
int a = (1, 2, 3);   // a == 3

典型用途：for 多变量

for (int i = 0, j = 10; i < j; ++i, --j)
    /* ... */;

不是逗号运算符的情况

场景 逗号含义
f(a, b) 函数参数分隔
int a{1, 2, 3} 初始化列表（容器/数组）
int i, j; 声明分隔多个变量

教材建议：少滥用逗号运算符写复杂表达式，可读性差。

和 C 的区别（逗号运算符：C/C++ 完全一致）

逗号运算符是 C 和 C++ 完全共享的语法——求值顺序（从左到右）、返回值（最右侧）、优先级（最低），两边一字不差：

对比点 C C++
, 从左到右求值 ✅ 一致 ✅ 一致
返回最右侧值 ✅ ✅ 一致
优先级最低 ✅ ✅ 一致
for (i=0, j=10; ...; ++i, --j) ✅ ✅ 一致
函数参数逗号不是运算符 ✅ ✅ 一致
声明逗号不是运算符 ✅ ✅ 一致
重载 , 不能 C++ 能（但极少推荐）

给 C 程序员的关键提醒： 1. 逗号运算符两边完全一样——C 学的用法直接迁移。for 多变量、(expr1, expr2) 顺序求值，语义一致。 2. C++ 允许重载 ,（类类型可定义 operator,），但强烈不推荐——重载后失去短路顺序保证（无法保证左侧先求值），且语义混乱。标准库和现代 C++ 几乎不重载 ,。 3. C++ 初始化列表的逗号不是运算符——int a[] = {1, 2, 3};、vector<int> v{1, 2, 3}; 里的逗号是分隔符，不触发逗号运算符。C 里同样规则。

为什么还需要逗号运算符（动机）

教材说"少滥用逗号运算符"，但逗号运算符保留至今有它不可替代的一个理由：

逗号是 C/C++ 里唯一被标准保证"从左到右依次求值"的运算符。

函数调用的实参顺序、算术运算的操作数顺序，标准都没规定（甚至 C++17 也没规定）。只有 E1, E2 保证"先完整算完 E1，再开始算 E2"。这个属性在两处是刚需：

场合 用逗号 不用会怎样
for 的迭代表达式更新两个变量 for (i=0, j=n-1; i<j; ++i, --j) 只能塞进循环体末尾，或改用 while
需要"先做 A（有副作用），再取 B 的值"作为一个表达式 (log(x), compute(x)) 宏里没法写两条语句（除非用 do{}while(0)）
顺序敏感的副作用 (prepare(), send()) f(prepare(), send()) 顺序未指定，可能先 send

反面的共识：除了 for 头和宏，逗号运算符基本都该拆成多条语句——它换来的是"一行写完"，代价是"读者要停三秒"。

底层实现与实测

环境：Apple clang 23.1.0，arm64-apple-darwin，-std=c++17 -O2。可跑版本见文末例子。

1. 从左到右依次求值，值是最后一个

int a = (side("A"), side("B"), 3);      // 实测打印 "A B"，a = 3
int b = (i = 5, j = 6, i + j);          // 实测 11，且 i=5 j=6

side("A") 的返回值被丢弃——clang 会提醒你：

warning: left operand of comma operator has no effect [-Wunused-value]

这条警告的意思是"左侧算了但没用到"，如果左侧只有副作用（赋值、++、函数调用）那正是想要的；如果左侧真的没副作用，说明你写错了。

2. 函数实参里的逗号是分隔符，不是运算符

two_args(1, 2);          // 实测 two_args(1, 2)   —— 两个实参
two_args((1, 2), 99);    // 实测 two_args(2, 99)  —— 两个实参，第一个是逗号表达式 = 2

这是最容易被误读的一条：f(a, b) 里的逗号永远不是逗号运算符（它是参数列表语法的一部分），只有加了括号 f((a, b)) 才变成运算符。同理 int i, j; 的逗号是声明分隔符，int a[]{1,2,3} 的逗号是初始化列表分隔符。

3. 下标里的逗号：arr[i, j] 等价 arr[j]

int arr[5] = {10,20,30,40,50};
arr[1, 3]      // 实测 40，即 arr[3]

不报错、不警告（-Wall 下也没有），只是静默取了后一个下标。这是"手滑把 , 写成 . 或反之"时最难查的 bug 之一。

4. 逗号 vs 函数调用：只有逗号保证顺序（关键区别）

int n = 0;
auto bump = [&]() { return ++n; };

(bump(), bump())          // 实测 2 —— 标准保证左→右，永远是 2
pick2(bump(), bump())     // 实测 1（本编译器左→右）—— 顺序「未指定」，换编译器可能变

pick2 只返回第一个实参的值，所以它能"暴露"求值顺序：clang 给 1（左先），GCC 可能给 2（右先）。任何依赖实参顺序的代码都是 bug，不管 C++11 还是 C++17——C++17 只规定了赋值、[]、<<、>> 的顺序，实参顺序仍然是 indeterminately sequenced。

5. C++17 前后：逗号的顺序保证一直都在

用 -Wunsequenced 当探针，同一段代码在 C 和 C++17 下的警告差异能精确说明哪些顺序被标准定死了：

int i = 0; int arr[4] = {};
arr[i] = i++;        // C++17 起：右操作数先求值 → 良定义
int j = i++ + i++;   // 仍然 UB：两个 ++ 之间没有顺序保证
标准 arr[i] = i++ i++ + i++
C99 ⚠️ -Wunsequenced（UB） ⚠️ -Wunsequenced（UB）
C++17 ✅ 无警告（已定义） ⚠️ -Wunsequenced（仍是 UB）

对比之下，(bump(), bump()) 在任何标准下都没有警告——因为逗号从 C 语言第一天起就保证顺序。

6. 优先级最低：逗号表达式作实参必须加括号

int v = 1;
printf("%d", (v += 1, v * 10));   // 实测 20（v 先变 2，再 2*10）

不加括号 printf("%d", v += 1, v * 10) 会被解析成三个实参。而上面这行 -O2 下 clang 还会报 -Wunsequenced——因为 printf 的多个实参之间顺序未指定，v 的读写没有顺序保证。逗号表达式 + 多实参 = 双重顺序风险，别这么写。

7. 重载逗号后，顺序保证消失

struct Comma { void operator,(int) const { /* ... */ } };
Comma c;
c, 7;      // 实测调用 Comma::operator,(int)

一旦逗号被重载，a, b 就变成函数调用 operator,(a, b)——参数顺序退化为"未指定"，逗号最核心的那个保证（左→右）没了。这是 C++ 标准库和现代代码从不重载 , 的根本原因。

HFT / 嵌入式视角

  1. 顺序敏感的两步操作，逗号是最轻的表达。(prepare_channel(), send_order(o)) 保证 prepare 完全结束后才 send；写成 f(prepare_channel(), send_order(o)) 顺序未指定——在极端情况下会先发单再准备通道。当然，生产代码里拆成两行最清楚，逗号的价值主要在于宏和 for 头。
  2. for 头里的逗号是标准用法，不是"滥用"。for (int i = 0, j = n - 1; i < j; ++i, --j) 这种双指针写法（回测里对齐两份行情、双指针扫单）是可读性最好的写法，别改写成 while。
  3. arr[i, j] 是静默 bug，clang 连 -Wall 都不报。二维数组下标、切片参数里手滑打错一个字符就中招。Code review 时看到下标里有逗号要立刻停下。
  4. 宏里的逗号必须小心。宏参数里的逗号会被当成参数分隔符：#define LOG(a) ... 调用 LOG((x, y)) 才是一个参数。宏里需要"多件事"时用 do { ... } while(0) 而不是逗号。
  5. 绝对不要重载 ,。它唯一的价值（顺序保证）会被重载破坏，而且几乎没有正当用例。

常见错误

1. 函数参数逗号误当运算符

f(a, b);   // 这是两个参数，不是逗号运算符
f((a, b)); // 这才是一个参数：先算 a，再算 b，传 b 给 f

f(a, b) 是调用 f 传两个参数；f((a, b)) 是调用 f 传一个参数（逗号表达式的结果 b）。两者完全不同，别混淆。

2. 逗号运算符滥用降低可读性

int x = (a++, b++, a + b);   // 能跑但难读

虽然合法（先 a++、再 b++、返回 a+b），但可读性差。拆成多条语句：

++a;
++b;
int x = a + b;

3. for 的逗号混淆

for (int i = 0, j = 10; i < j; ++i, --j) { ... }

这里有两个逗号： - int i = 0, j = 10 是声明逗号（同时声明 i 和 j） - ++i, --j 是逗号运算符（顺序执行 ++i 和 --j）

别混淆。声明逗号不是运算符，不返回值。

自测题

1. 选择题　int a = (1, 2, 3); 之后 a 的值是：

  • A. 1
  • B. 2
  • C. 3
  • D. 编译错误
答案

C。逗号运算符从左到右求值，返回最右侧值。(1, 2, 3) 先算 1（丢弃）、再算 2（丢弃）、最后算 3（返回），所以 a = 3。C 也是同样规则。

2. 判断题　f(a, b) 和 f((a, b)) 等价。

答案

错。f(a, b) 调用 f 传两个参数 a 和 b；f((a, b)) 调用 f 传一个参数（逗号表达式的结果 b，a 被求值但丢弃）。两者完全不同。函数参数的逗号是分隔符，不是逗号运算符。

3. 踩坑题　下面这段代码用逗号运算符"同时更新两个变量"，可读性如何？怎么改？

for (int i = 0, j = n - 1; i < j; i++, j--) {
    swap(arr[i], arr[j]);
}
答案

这个用法是合理的——for 循环里用逗号运算符同时更新 i 和 j 是常见且可接受的写法。C 和 C++ 都这么写。

但若循环体复杂，可读性要求高时，可改用 while：

int i = 0, j = n - 1;
while (i < j) {
    swap(arr[i], arr[j]);
    ++i;
    --j;
}

要点：for 里的逗号运算符（i++, j--）是合理用法，别滥用到循环体外。

4. 应用题　C 程序员写下面这段代码，C++ 里行为如何？

int i = 0;
int x = (i++, i++, i++);
std::cout << x << " " << i;
答案

输出 2 3。

  • i++ 第一次：返回 0（i 变 1），丢弃
  • i++ 第二次：返回 1（i 变 2），丢弃
  • i++ 第三次：返回 2（i 变 3），这是逗号表达式的返回值
  • x = 2，i = 3

C 和 C++ 行为完全一致——逗号运算符从左到右，返回最右。但这种写法可读性差，生产代码别这么写，拆成多条语句更清晰。

5. 判断题　(f(), g()) 和 h(f(), g()) 一样，都不能保证 f() 在 g() 之前执行。

答案

错——两者恰恰相反，这正是逗号运算符至今存在的唯一理由。

写法 顺序 依据
(f(), g()) 保证 f() 完整执行完，才开始 g() 逗号运算符是 C/C++ 唯一被标准保证"从左到右"的运算符
h(f(), g()) 未指定（indeterminately sequenced） 函数实参的求值顺序标准不规定，C++17 也没规定

实测（bump() 每次自增并返回新值）： - (bump(), bump()) → 永远是 2 - pick2(bump(), bump()) → 本编译器给 1，换 GCC 可能给 2

注意：C++17 确实给一批运算加了顺序保证（E1 = E2 右先于左、E1[E2] 中 E1 先于 E2、<</>> 左先于右），但函数实参的顺序始终没有规定。需要顺序时只有两条路：用逗号运算符，或者拆成两条语句。

6. 应用题　你在 review 一段回测代码，它要把两份行情（按时间对齐）逐条比对，同时统计不匹配条数。指出下面代码里的两个问题并改写：

int i = 0, j = 0, bad = 0;
for (; i < n1, j < n2; ++i, ++j) {          // ①
    if (a[i].ts != b[j].ts) { ++bad; continue; }
    compare(a[i], b[j]);
}
check(a[i].ts, b[j].ts);                    // ②
答案

问题 ①（静默 bug）：i < n1, j < n2 是逗号表达式，值是 j < n2——i < n1 被求值然后丢弃。也就是说循环条件只剩 j < n2，i 越界不会被检查。越界读 a[i] 是 UB。

这是逗号运算符最阴险的用法：它看起来像"两个条件都判"，实际只判最后一个。&& 才是"两个都要"。

问题 ②：check(a[i].ts, b[j].ts) 的两个实参 a[i].ts 和 b[j].ts 求值顺序未指定——虽然这里只是读两个不相关的值，没有实际问题，但更重要的是：循环结束后 i、j 已经越过边界（见 ①），这行是在读越界数据。

改写（双指针的标准写法，逗号只用在迭代表达式——它的正当位置）：

int i = 0, j = 0, bad = 0;
while (i < n1 && j < n2) {                  // ① 用 && 表达"两个都要"
    if (a[i].ts < b[j].ts)      { ++i; continue; }   // a 落后，推进 a
    if (b[j].ts < a[i].ts)      { ++j; continue; }   // b 落后，推进 b
    compare(a[i], b[j]);                             // 时间戳相等才比对
    ++i; ++j;                                        // ← 明确两行，比 ++i, ++j 更清楚
}

要点： - 循环条件里出现逗号，99% 是 bug——本意多半是 &&（或 ||）。逗号表达式的值是最后一个。 - 逗号的正当位置是迭代表达式（++i, --j）和宏里需要顺序的多步操作。 - 双指针推进逻辑用 while 比 for 更好读，因为两个指针的推进条件不同。

题目 1： C++ 四种 cast 各用于什么场景？

4.11

.1 隐式类型转换

本节讲什么

编译器无提示、自动完成的类型转换——发生在运算、赋值、初始化、传参等场景。

1. 整型提升（最基础）

小于 int 的小整型（char / short / bool）参与运算时，先提升为 int；若 int 放不下则提升为 unsigned int。

char c = 'a';
auto res = c + 10;   // c 先提升为 int 再计算

HFT 解析单字节字段时，char 参与算术前几乎总会先变 int——与 3.2.5 unsigned char 配合，避免符号扩展坑。

提升在「比较」里同样发生：if (c == 'a') 逐步走一遍

比较运算符的操作数一样先提升——if 条件里没有按 8 bit 做的比较：

char c = 'a';
if (c == 'a') { ... }
语言 左侧 c 右侧 'a' 实际比较
C char → 提升 1 次 天生是 int（C 的字符常量类型就是 int），0 次 int == int
C++ char → 提升 1 次 是 char，再提升 1 次 int == int

殊途同归：两边都按 int 比，结果一致。C/C++ 的差异只在孤立字面量的静态类型（sizeof('a')：C 是 4、C++ 是 1），进表达式就抹平了——完整三层模型（变量/字面量/表达式）见 2.1.1 字符与字符串字面量，C 侧双平台实测见 K&R 2.3.1 字符常量的类型与整型提升。

提升保留「值」不保留「位模式」——三个比较/移位坑

提升时对 signed 类型做符号扩展：signed char 的 0xFF 那个字节，值是 -1，提升后还是 -1，不会变成 255。由此产生三个常踩的坑：

char c = 0xFF;            // signed char 平台：值为 -1
if (c == 0xFF) { ... }    // ❌ false！c 提升为 -1，0xFF 是 int 255，-1 != 255

char d = 0x80;            // signed char 平台：值为 -128
if ((d >> 1) == 0x40)     // ❌ false！提升先于移位：-128 算术右移得 -64，不是 64
if (((unsigned char)d >> 1) == 0x40)  // ✅ true：先转无符号再移位

char e = 100;
if (e < 200) { ... }      // ⚠️ 恒真：signed char 最大 127，编译器报
                          //    -Wtautological-constant-out-of-range-compare

三个坑在 C 里完全一样（提升规则两边一字不差）。处理字节时一律 uint8_t / unsigned char / std::byte，比较和移位都在无符号域里做，坑自然消失。

指令层对照：提升在 ARM 上对应 sxtb/uxtb（符号/零扩展字节），x86 上对应 movsx/movzx——选哪条由 ABI 的 char 符号性决定。提升本身零成本（寄存器本来就是 32/64 位宽），代价只在语义上。

2. 常用算术转换（混合运算）

向范围更大、精度更高的类型转换，尽量避免精度丢失：

  • 有浮点 → 全部转浮点（int + double → int 转 double）
  • 全整型：无符号优先级常高于有符号；宽度小的转宽度大的
int a = 3;
double b = 3.14;
auto sum = a + b;    // a 隐式转为 double

3. 数组 → 指针（高频）

绝大多数场景数组名退化为首元素指针。

不退化例外：sizeof(arr)、&arr、用字符串字面量初始化 char 数组（见 3.5.3）。

int arr[5];
int *p = arr;        // 等价 &arr[0]

4. 指针相关隐式转换

转换 说明
0 / nullptr → 任意指针 空指针
非 const 对象指针 → void* 通用指针
非 const 指针/引用 → 对应 const 版 只加 const，不能反向 
int i = 10;
const int &r = i;    // ✅ 普通引用 → const 引用
// int &r2 = r;      // ❌ 不能去掉 const

与 2.4.1 底层 const 一致。

5. 布尔转换（条件判断）

标量（数字、指针）在条件上下文转 bool：

  • 0、空指针 → false
  • 非 0、有效指针 → true
int x = 5;
if (x) { /* true */ }

int *p = nullptr;
while (p) { /* false，不进入 */ }

6. 赋值 / 初始化 / 传参

右侧、实参自动转为左侧、形参类型：

double d = 3.99;
int i = d;           // double → int，**截断小数**，i == 3（非四舍五入）

HFT：价格 double 隐式赋给 int 会静默丢小数——业务层应显式处理或统一用定点/整数价位。

窄化：只有 {} 能在编译期挡住

上面这些"悄悄丢数据"的转换，编译器只在源头是字面量时才会提醒。int a = 3.99; 实测会触发警告：

warning: implicit conversion from 'double' to 'int' changes value from 3.99 to 3 [-Wliteral-conversion]

但源头一旦是变量（double d; int a = d;），默认零警告——实测不开开关时一条都不报，必须 -Wconversion 才报（实测 4 条）。也就是说，日常代码里真正会踩的窄化，编译器基本是沉默的。

唯一不依赖警告开关的硬防线是列表初始化 {}——C++ 规定列表初始化不允许窄化转换（narrowing conversion），直接编不过：

int a = 3.99;      // ✅ 编译通过，a == 3（静默截断）
int b(3.99);       // ✅ 同样通过，b == 3
int c{3.99};       // ❌ 编译错误：non-constant-expression cannot be narrowed
int d = static_cast<int>(3.99);  // ✅ 你明说了要截断，编译器放行

实测（clang 23.1.0，-std=c++17）：= 与 () 两条只是 warning，{} 那条是 error：

warning: implicit conversion from 'double' to 'int' changes value from 3.99 to 3 [-Wliteral-conversion]
error: type 'double' cannot be narrowed to 'int' in initializer list [-Wc++11-narrowing]
    int c{3.99};
         ^~~~~
note: insert an explicit cast to silence this issue   ← 编译器建议写 static_cast

这条规则在函数传参上价值最大：void set_price(int); 写 set_price(37.5) 只是一条 warning（值静默变 37），而 set_price({37.5}) 是硬错误——把"数值被截断"从运行时静默错误提前成编译期错误。

判据：凡是"精度/范围可能变小"的隐式转换（浮点→整型、长整型→短整型、整型→char/bool）都算窄化。常量表达式且值能无损装下时例外（char c{65} 合法）。

和 C 的区别（隐式类型转换：C/C++ 几乎一致，C++ 对 bool 更严格）

隐式类型转换是 C 和 C++ 高度共享的部分——整型提升、算术转换、数组退化、指针转换、布尔转换，两边规则几乎一字不差：

对比点 C C++
整型提升（char/short → int） ✅ 一致 ✅ 一致
算术转换（向更宽/浮点转） ✅ 一致 ✅ 一致
数组 → 指针退化 ✅ 一致 ✅ 一致
0 → 空指针 ✅ 一致 ✅ 一致，但推荐 nullptr
指针 → void* ✅ 一致 ✅ 一致
加 const ✅ 一致 ✅ 一致
非 0 → true、0 → false ✅（C89 用 int） ✅（C++ 有原生 bool）
浮点 → 整型截断 ✅ 一致 ✅ 一致
void* → 其他指针 ✅ 隐式转换 ❌ 必须 static_cast

给 C 程序员的关键提醒： 1. 隐式转换规则两边几乎一致——整型提升、算术转换、数组退化这些 C 学的"坑"全部迁移。C 程序员的警惕心直接用。 2. C++ 比 C 严格的地方：void* 不能隐式转其他指针——C 里 int* p = malloc(...)（malloc 返回 void*）合法，C++ 里 int* p = malloc(...) 编译错误，必须 int* p = static_cast<int*>(malloc(...)); 或用 new。这是 C++ 类型系统更严格的体现。 3. C++ 推荐 nullptr 替代 0/NULL——0 在 C++ 里既是整数又是空指针（重载歧义），nullptr 是专门的空指针字面量（类型 nullptr_t），不会和整数混淆。详见 2.3.2。

常见错误

1. 浮点转整型静默截断

double price = 3750.99;
int rounded = price;   // 3750，不是 3751（截断非四舍五入）

C 程序员也踩这个——两边都是截断小数，不是四舍五入。要四舍五入用 std::lround(price) 或 static_cast<int>(price + 0.5)（正数）。HFT 价格通常用定点整数（如"厘"为单位），避开浮点。

2. 有符号和无符号混用导致负数变大正数

int i = -1;
unsigned n = 10;
if (i < n) { ... }   // ❌ false！i 转为 unsigned 变成 4294967295

有符号和无符号比较时，有符号隐式转为无符号——-1 变成 UINT_MAX（巨大正数），< n 为 false。C 和 C++ 都有这个坑。用 size_t 时尤其小心，下标和负数比较容易踩。

3. char 符号扩展

char c = 0x80;          // 有符号 char，值为 -128
int i = c;              // 符号扩展，i = -128（不是 128）
unsigned char uc = 0x80;
int j = uc;             // 零扩展，j = 128

char 是否有符号实现相关（x86 通常有符号，ARM 通常无符号）。char 转 int 时若有符号会符号扩展（高位补 1）。处理二进制字节用 unsigned char 或 std::byte。C 程序员也踩这个，C++ 同样坑。

赋值时的扩展规则同样作用于比较和移位——if ((char)0xFF == 0xFF) 在 signed char 平台上是 false（-1 ≠ 255），三个比较/移位坑的完整拆解见 §1 整型提升 末尾。

自测题

1. 选择题　int i = -1; unsigned u = 1; 下列哪个表达式为 true？

  • A. i < u
  • B. i > u
  • C. i == u
  • D. 编译错误
答案

B。i < u 比较时，i（int -1）隐式转为 unsigned，变成 UINT_MAX（4294967295），UINT_MAX > 1 为 true，所以 i > u 为 true。这是有符号/无符号混用的经典坑。C 也是同样行为。避免混用，或显式 static_cast<int>(u) 比较。

2. 判断题　double d = 3.99; int i = d; 之后 i 的值是 4（四舍五入）。

答案

错。浮点转整型是截断小数（向零取整），不是四舍五入。i = 3，不是 4。要四舍五入用 std::lround(d) 或 static_cast<int>(d + 0.5)（正数）。C 程序员也踩这个，两边一致。

3. 踩坑题　C 程序员写下面这段 C++ 代码，哪里编译失败？

void* p = malloc(100);
int* ip = p;   // 想用 malloc 分配 int 数组
答案

int* ip = p; 编译错误——C++ 不允许 void* 隐式转 int*（C 允许）。C 程序员的 int* ip = malloc(...) 习惯到 C++ 要改。

修复（三种）：

// 方法 1：C++ 显式转换
int* ip = static_cast<int*>(malloc(100 * sizeof(int)));

// 方法 2：用 new（C++ 推荐）
int* ip = new int[100];

// 方法 3：用 vector（最推荐）
std::vector<int> v(100);

C++ 的 new/vector 比 malloc 更安全（类型安全、调用构造函数、RAII），优先用。

4. 应用题　HFT 代码读一个 unsigned char 字节，想转成 int 做算术，如何避免符号扩展坑？

答案 
unsigned char byte = read_byte();   // 0..255
int value = byte;                    // ✅ 零扩展，value = 0..255

// 对比：若用 char
char c = read_byte();               // 若 byte >= 128，c 是负数
int wrong = c;                      // ❌ 符号扩展，可能变负数
int fixed = static_cast<unsigned char>(c);  // ✅ 先转 unsigned char 再转 int

要点： - 处理二进制字节用 unsigned char（或 C++17 的 std::byte），不用 char - unsigned char 转 int 是零扩展，不会变负数 - char 转 int 是符号扩展，可能变负数

C 程序员也踩这个——<cctype> 函数（isalpha 等）要求 unsigned char 转 int 参数，传 char 可能 UB。

5. 踩坑题　signed char 平台上，下面三个 if 分别成立吗？为什么？

char c = 0xFF;
char d = 0x80;
char e = 100;

if (c == 0xFF)        { /* A */ }
if ((d >> 1) == 0x40) { /* B */ }
if (e < 200)          { /* C */ }
答案

A 不成立。c 是 signed char，值为 -1；比较前提升为 int -1，而 0xFF 是 int 255，-1 != 255。

B 不成立。提升先于移位：d 先提升为 int -128，算术右移一位得 -64，不是 64。修法：((unsigned char)d >> 1) == 0x40（先转无符号，移位在 0..255 域里做）。

C 恒成立（signed char 最大 127，永远 < 200）。clang/gcc 会报 -Wtautological-constant-out-of-range-compare——条件里出现恒真/恒假，通常意味着类型选小了或边界想错了。

一句话：提升保留的是值不是位模式——signed 的字节 0xFF 值是 -1，提升后还是 -1。处理字节一律 uint8_t / unsigned char / std::byte。

4.11

.2 显式转换与四种 cast

本节讲什么

老式 C 风格强转 vs C++ 四种命名强制转换：static_cast、const_cast、reinterpret_cast、dynamic_cast。

老式转换（不推荐）

double d = 3.14;
int i1 = (int)d;     // C 风格
int i2 = int(d);     // 函数式

缺点：一次写法可同时完成去 const、指针重解释等多种语义，难以审查，易埋雷。

C++ 命名转换（推荐）

统一语法：转换名<目标类型>(表达式)

① static_cast（最常用）

温和、相对安全的编译期转换：

  • 基础算术互转（double↔int、float↔long）
  • void* 与普通指针互转
  • 继承体系父子类指针上行/下行（编译期检查有限）

不能修改 const 属性。

double d = 3.14;
int i = static_cast<int>(d);   // 3，截断小数

② const_cast（唯一能增删 const/volatile）

仅修改常量限定，不改变底层类型。

const char *str = "test";
char *p = const_cast<char*>(str);   // 去掉 const（仍须谨慎使用）

const int ci = 100;
const int *cp = &ci;
int *p2 = const_cast<int*>(cp);
// *p2 = 200;  // ❌ 若 ci 原本真是 const，这是 UB

警告：通过 const_cast 修改原本就是 const 的对象 → 未定义行为。合法典型场景：调用只接受非 const 指针的遗留 API，而对象本身可变。

③ reinterpret_cast（底层比特重解释，极高风险）

把内存二进制位直接当成另一种类型，无类型安全检查：

  • 指针与整数互转
  • 不相关类型指针互转
int num = 0x1234;
char *pc = reinterpret_cast<char*>(&num);

HFT：解析二进制报文、对齐字段时偶见；日常业务尽量少用，优先 memcpy + 明确布局（见 2.1 基本类型）。

④ dynamic_cast（运行时多态转换）

仅用于带虚函数的多态类；基类指针/引用 → 派生类，运行时校验，失败指针版返回 nullptr。

本章仅提及；详见第 7 / 15 章继承与多态。

四种 cast 速查

cast 用途 风险
static_cast 算术、void*、继承转换 低～中（浮点截断等）
const_cast 增删 const/volatile 改真 const → UB
reinterpret_cast 比特重解释 极高
dynamic_cast 多态向下转型 低（失败可检测）

和 C 的区别（显式转换：C++ 的四种 cast 替代 C 风格强转）

这是 C 转 C++ 最该改变习惯的部分之一。C 只有一种强转 (type)expr，C++ 提供四种命名 cast，让转换意图更明确、更易审查：

对比点 C C++
算术转换 (int)d 或 int(d) static_cast<int>(d)
去 const (int*)cp（同一写法） const_cast<int*>(cp)
指针重解释 (char*)&num reinterpret_cast<char*>(&num)
多态向下转型 无（C 无继承） dynamic_cast<Derived*>(bp)
void* → 其他指针 int* p = (int*)vp; 或 int* p = vp;（隐式） static_cast<int*>(vp)（必须显式）
审查难度 (type)expr 一眼看不出意图 cast 名字暴露意图

给 C 程序员的关键转变： 1. static_cast 替代 C 的 (type)expr 用于算术/指针转换——static_cast<int>(d) 比 (int)d 更显眼、更易搜索（grep static_cast 一搜一个准）。语义等价，但意图清晰。 2. const_cast 是 C++ 独有的"去 const"方式——C 里 (int*)cp 一行就能去 const，C++ 必须用 const_cast<int*>(cp)。这是有意的设计——去 const 是危险操作，命名 cast 让它在代码审查时更醒目。 3. reinterpret_cast 替代 C 的指针重解释——(char*)&num 在 C++ 用 reinterpret_cast<char*>(&num)。reinterpret_ 这个名字本身就在警告"我在重新解释比特"。 4. dynamic_cast 是 C++ 独有——C 没有继承/多态，没有这种转换。运行时检查向下转型是否安全。 5. C 风格 (type)expr 在 C++ 仍合法但不推荐——它"什么都能干"（同时去 const + 重解释），难以审查。用四种命名 cast 替代是 C 转 C++ 的重要习惯转变。

常见错误

1. 用 static_cast 去 const

const int ci = 100;
const int* cp = &ci;
int* p = static_cast<int*>(cp);   // ❌ 编译错误：static_cast 不能去 const

static_cast 不能修改 const——去 const 必须用 const_cast。这是 C++ 有意的设计——去 const 是危险操作，要用专门的 cast 名字暴露意图。C 里 (int*)cp 一行搞定，C++ 要分清。

2. const_cast 修改原本就是 const 的对象

const int ci = 100;
const int* cp = &ci;
int* p = const_cast<int*>(cp);
*p = 200;   // ❌ UB：ci 原本是 const，改它是未定义行为

const_cast 只是"骗编译器"（去掉 const 检查），但运行期对象是否真可改取决于它原本是否 const。原本 const 的对象可能存在只读内存，改它 UB。合法场景：对象本身非 const，但被 const 接口返回，调用者知道可改。

3. 用 reinterpret_cast 做不相关类型转换

double d = 3.14;
int i = reinterpret_cast<int>(d);   // ❌ 编译错误：reinterpret_cast 不能用于算术类型

reinterpret_cast 只用于指针/引用的比特重解释，不用于算术类型转换。算术转换用 static_cast。C 里 (int)d 既可用于算术也可用于指针（一锅烩），C++ 分得清。

底层实现与实测（../examples/4.11-1-four-casts.cpp）

实测 1：四种 cast 的行为边界（clang 23.1.0 / -O2 / ARM64）

cast 检查时机 实测能做什么 越界的后果
static_cast 编译期 算术互转（3.99→3、-3.99→-3，向零截断）、void*↔int* 向下转型用错是 UB：把 Other* 当 Derived* 读，编译无错、实测读到 3
const_cast 编译期 增删 const；对象本身非 const 时写入合法（7→9） 改原本是 const 的对象是 UB
reinterpret_cast 无 指针↔整数（MMIO 常用） 用它做类型双关违反严格别名；要看位模式请用 memcpy（1.0f → 0x3f800000）
dynamic_cast 运行时 成功返回非空，失败返回 nullptr；引用版抛 std::bad_cast 需要多态类型（Base 有虚函数），否则编译报错

实测 2：const_cast 的判定标准是「对象」，不是「指针」

const int ci = 10;
int* mp = const_cast<int*>(&ci);
// *mp = 20;      ← UB：ci 这个对象本身是 const

int real = 7;
const int* rp = &real;
*const_cast<int*>(rp) = 9;   // ✅ 合法：real 本身不是 const

唯一判断依据：被指向的那个对象在定义时是不是 const。 const_cast 的正当用途只有一个——对接"不会修改对象、但签名忘了写 const"的老接口。

实测 3：dynamic_cast 的开销（1e7 次成功转型）

dynamic_cast :  9.48 ms  (0.95 ns/次)
static_cast  :  8.05 ms  (0.81 ns/次)   ← 编译期完成，理论零成本
成员访问     :  7.18 ms  (0.72 ns/次)

dynamic_cast 比 static_cast 慢约 17%。这个差距看着不大，但它意味着每次转型都要走一遍 RTTI 的类型查找—— 在热路径上出现 dynamic_cast 通常说明设计有问题（该用虚函数多态，而不是"转型后再分派"）。

C 风格强转为啥必须禁用

(T)x 会按顺序尝试 const_cast → static_cast → reinterpret_cast， 也就是说一个括号可能干四件事中的任意一件（包括悄悄去掉 const）。 写的人意图不明，读的人看不出来——这是 C++ 引入四种命名 cast 的唯一理由。

自测题

1. 选择题　要去掉指针的 const 限定，应该用哪种 cast？

  • A. static_cast
  • B. const_cast
  • C. reinterpret_cast
  • D. dynamic_cast
答案

B。const_cast 是唯一能增删 const/volatile 的 cast。static_cast 不能改 const（编译错误）；reinterpret_cast 改的是比特解释不是 const；dynamic_cast 用于多态向下转型。C 里 (int*)cp 一行能去 const，C++ 要用 const_cast 暴露意图。

2. 判断题　C 风格的 (int)d 在 C++ 中是编译错误。

答案

错。C 风格 (int)d 在 C++ 仍合法（向后兼容），但不推荐——它"什么都能干"（同时去 const、重解释指针、算术转换），难以审查。C++ 推荐 static_cast<int>(d) 这种命名 cast，意图清晰、易搜索。

3. 踩坑题　C 程序员写下面这段 C++ 代码，哪里有问题？

const char* s = "hello";
char* p = (char*)s;        // C 风格强转去 const
p[0] = 'H';                 // 想改成 "Hello"
答案

两个问题： 1. C 风格强转不推荐——C++ 应该用 const_cast<char*>(s)，暴露"去 const"的意图 2. 修改字符串字面量是 UB——"hello" 是字符串字面量，存在只读内存，p[0] = 'H' 可能崩溃（段错误）

修复（若真要改字符串）：

char buf[] = "hello";      // 数组，可改
buf[0] = 'H';              // ✅ "Hello"
// 或用 std::string
std::string s = "hello";
s[0] = 'H';                // ✅

C 里这种写法也是 UB（字符串字面量只读），但 C++ 的 std::string 更安全——赋值就拷贝一份可改的。

4. 应用题　HFT 代码要从 void* 缓冲读 int 数据。C 写法 (int*)buf，C++ 应该怎么写？

答案 
// C 写法（C++ 也能编译，但不推荐）
void* buf = malloc(100 * sizeof(int));
int* ip = (int*)buf;

// C++ 推荐：static_cast
void* buf = malloc(100 * sizeof(int));
int* ip = static_cast<int*>(buf);

// C++ 更推荐：new 或 vector
int* ip = new int[100];
// 或
std::vector<int> v(100);
int* ip = v.data();

要点： - void* → int* 用 static_cast（C++ 必须显式，不能隐式） - reinterpret_cast 也能用但过头——static_cast 足够且更安全 - C++ 推荐 new/vector 替代 malloc（类型安全、RAII）

C 程序员的 (int*)buf 习惯要改成 static_cast<int*>(buf)。

4.11

.3 规范、易错点与示例

本节讲什么

教材使用规范、高频易错点、背诵版与完整可运行示例。

使用规范

  1. 优先隐式转换——能自动统一类型就不手写强转
  2. 必须强转时，用四种命名 cast，拒绝 (type)expr
  3. 精度丢失、一般指针转换 → static_cast；只改 const → const_cast；底层比特重解释 → reinterpret_cast（慎用）
  4. 浮点 → 整型截断小数，非四舍五入；编译器常给警告

高频易错点

  1. 隐式转换只能单向加 const，不能去掉 const
  2. static_cast 无法移除 const，必须用 const_cast
  3. 数组转指针有例外：sizeof(arr) 是整个数组大小，不是指针大小
  4. 浮点转整型直接截断，不是四舍五入
  5. reinterpret_cast 不做校验，误用易崩溃 / 未对齐访问

背诵极简版

隐式：整型提升、算术转换、数组→指针、加const、→bool、赋值截断
显式：static_cast 算术/void*；const_cast 改const；reinterpret 比特；dynamic 多态
拒绝 (int)d 和 int(d)；优先 static_cast
float→int 截断；static_cast 不能去 const
sizeof(arr) 不退化；&arr 类型是 int(*)[N]

完整示例

#include <iostream>

int main() {
    double d = 3.14;
    int i = static_cast<int>(d);
    std::cout << i << "\n";          // 3

    const int ci = 100;
    const int *cp = &ci;
    int *p = const_cast<int*>(cp);   // 仅演示语法；勿通过 p 改 ci

    short s = 5;
    auto sum = s + 2.5;              // short→int→double
    std::cout << sum << "\n";

    int arr[3] = {1, 2, 3};
    int *ap = arr;                   // 隐式数组→指针
    std::cout << sizeof(arr) << " " << sizeof(ap) << "\n";

    return 0;
}

和 C 的区别（类型转换章节总结：C++ 的四种 cast 是最大转变）

整个 4.11 章节是 C 转 C++ 最该改变习惯的部分。C 的转换是"一锅烩"——(type)expr 什么都能干，难以审查；C++ 拆成四种命名 cast，每种有明确用途：

场景 C 写法 C++ 推荐 区别
算术转换 (int)d static_cast<int>(d) C++ 命名 cast 更显眼
去 const (int*)cp const_cast<int*>(cp) C++ 强制命名，暴露意图
指针重解释 (char*)&n reinterpret_cast<char*>(&n) C++ 警告"重解释比特"
void* → int* 隐式或 (int*)vp static_cast<int*>(vp) C++ 禁止隐式，必须显式
多态向下转型 无（C 无继承） dynamic_cast<Derived*>(bp) C++ 独有
整型提升 ✅ 一致 ✅ 一致 无差异
算术转换 ✅ 一致 ✅ 一致 无差异
数组退化 ✅ 一致 ✅ 一致 无差异

给 C 程序员的"心法转变"： 1. 隐式转换规则两边几乎一致——整型提升、算术转换、数组退化、浮点截断这些坑 C 学的直接迁移，无需转变。 2. 显式转换要换习惯——C 的 (type)expr 在 C++ 改用四种命名 cast：static_cast（算术/void*）、const_cast（去 const）、reinterpret_cast（重解释）、dynamic_cast（多态）。 3. C++ 的 void* 不能隐式转其他指针——C 里 int* p = malloc(...) 合法（malloc 返回 void* 隐式转），C++ 编译错误，必须 static_cast<int*>(malloc(...)) 或用 new/vector。 4. C++ 推荐 nullptr 替代 0/NULL——避免重载歧义，详见 2.3.2。

常见错误

1. C 风格强转"一锅烩"

const int* cp = &some_const;
int* p = (int*)cp;        // C 风格：同时去 const + 指针类型不变，看不出意图

C 风格 (int*)cp 一行同时去 const 和保持指针类型，无法区分"只想去 const"还是"想重解释"。C++ 用 const_cast<int*>(cp) 明确"只去 const"。代码审查时，const_cast 一眼看出危险，(int*) 容易漏。

2. 有符号/无符号混用导致负数变大正数

int idx = -1;
size_t n = vec.size();
if (idx < n) { ... }   // ❌ idx 转 size_t 变成 SIZE_MAX，< n 为 false

有符号和无符号比较时，有符号隐式转无符号——-1 变成巨大正数。C 和 C++ 都有这个坑。用 int 比较或显式 static_cast<int>(n)。

3. 浮点转整型静默截断

double price = 3750.99;
int cents = price * 100;   // 375099，不是 375100（截断）

price * 100 = 375099.0（浮点），转 int 截断小数得 375099。HFT 价格用定点整数（如"厘"为单位）避开浮点，或显式 std::lround。

三个必须记住的"不是实现定义，是未定义"

  1. 浮点 → 整型越界是 UB（不是实现定义，也不是饱和）。实测 (int)1e30 得到 4—— 这个值没有任何意义，换个优化级别就会变。(int)NAN、(int)INFINITY 同理。 正确做法：先比较范围，再 static_cast。
  2. 移位量 ≥ 位宽是 UB：1 << 32 实测得 8；-1 << 1 实测得 -2。都别依赖。
  3. 通过 reinterpret_cast 做类型双关是 UB（违反严格别名规则）：看位模式一律用 memcpy。

花括号 {} 能挡住什么

char c(300);                    // 静默截断，编译无警告
char c{300};                    // ❌ error: 窄化转换（narrowing）
char c{static_cast<char>(300)}; // ✅ 写明意图后合法

这是"一律用 {} 初始化"最实际的一条理由：它把静默截断变成编译错误。

自测题

1. 选择题　下列哪种 cast 不能用于去掉 const？

  • A. const_cast<int*>(cp)
  • B. (int*)cp（C 风格）
  • C. static_cast<int*>(cp)
  • D. reinterpret_cast<int*>(const_cast<const int*>(cp))
答案

C。static_cast 不能修改 const，static_cast<int*>(cp)（cp 是 const int*）编译错误。const_cast 是唯一能去 const 的命名 cast；C 风格 (int*)cp 能去（但不推荐）；reinterpret_cast 配合 const_cast 也能去（啰嗦）。C++ 设计上让去 const 必须用 const_cast，暴露意图。

2. 判断题　void* p = ...; int* ip = p;（隐式转换）在 C++ 中合法。

答案

错。C++ 不允许 void* 隐式转其他指针类型——必须 int* ip = static_cast<int*>(p);。C 允许隐式（int* ip = malloc(...) 合法）。这是 C++ 比 C 类型系统更严格的体现，强迫程序员显式表达转换意图。

3. 踩坑题　C 程序员写下面这段 C++ 代码，编译错误，怎么改？

void* buf = malloc(100);
int* ip = buf;        // 想用 buf 当 int 数组
答案

int* ip = buf; 编译错误——C++ 不允许 void* 隐式转 int*。C 程序员的 int* ip = malloc(...) 习惯要改。

修复（三种）：

// 方法 1：static_cast
int* ip = static_cast<int*>(buf);

// 方法 2：用 new（C++ 推荐）
int* ip = new int[25];   // 100 字节 = 25 个 int

// 方法 3：用 vector（最推荐）
std::vector<int> v(25);
int* ip = v.data();

C++ 推荐 new/vector 替代 malloc——类型安全、调用构造函数、RAII 自动释放。

4. 应用题　写一个函数 safe_int_div，接受两个 double 参数，返回整数结果，要求：除零时返回 0，结果四舍五入（非截断）。

答案 
#include <cmath>

int safe_int_div(double a, double b) {
    if (b == 0.0) return 0;                         // 防除零
    double result = a / b;
    return static_cast<int>(std::lround(result));   // 四舍五入，不是截断
}

要点： - 显式判 b == 0.0 防除零 UB - std::lround 四舍五入（static_cast<int>(result) 会截断） - static_cast<int> 显式转换，不用 C 风格 (int)

C 等价写法：

int safe_int_div(double a, double b) {
    if (b == 0.0) return 0;
    return (int)lround(a / b);   // C 风格强转
}

C++ 用 static_cast 替代 (int)，意图更清晰。

4.12

运算符优先级表

本节讲什么

第 4 章收尾：运算符的优先级（precedence）、结合律（associativity），以及与之易混的求值顺序（order of evaluation）。看懂复杂表达式、避免 cout << ?:、*p.member 等经典坑。

三个概念别混

概念 决定什么
优先级 谁先跟谁「绑」在一起算——* 高于 +
结合律 同级运算符谁先算——a - b - c 从左到右
求值顺序 各操作数何时算——f() + g() 先调谁不规定

优先级高 ≠ 左侧操作数一定先求值。详见 4.12.2。

要点

  • 背粗粒度顺序即可，细节查表；复杂式子加括号
  • . -> 高于 * → *p.size() 是错写法（见 4.6）
  • ?: 很低 → cout << cond ? a : b 必加括号（见 4.7）
  • , 最低；赋值 从右向左结合
  • && || 短路且对两侧有求值顺序保证；& | 无短路

题目 1： 以下表达式的求值顺序是什么？

std::cout << x << y << std::endl;
参考答案

<< 左结合——等价于 ((std::cout << x) << y) << std::endl。cout << x 返回 cout 引用，所以可以链式调用。注意：同一表达式中不同参数的求值顺序未指定——f(g(), h()) 中 g() 和 h() 的执行顺序不确定。C++17 起部分操作数求值顺序被固定（如 << 的左操作数先于右操作数求值）。

经典例题

* 高于 +

int a = 2, b = 3;
std::cout << a + b * 4 << std::endl;  // 2 + 12 = 14，不是 20

. 高于 *

// *p.size();     // ❌ 等价 *(p.size())

和 C 的区别（优先级表：C/C++ 几乎一致，C++ 多了几个运算符）

C 程序员对 C 的运算符优先级表已经倒背如流——* 高于 +、&& 高于 ||、赋值右结合、逗号最低，这些 C++ 完全继承。C++ 只是多了几个新运算符：

运算符 C C++ 优先级位置
:: 作用域解析 无 ✅ 最高（1 级）
.* ->* 成员指针 无 ✅ 高（2 级，后缀类）
static_cast/const_cast/... 无 ✅ 后缀类（2 级）或前缀（3 级）
typeid 无 ✅ 2 级

给 C 程序员的关键提醒： 1. C 学的优先级表 95% 直接用——算术、关系、逻辑、位运算、赋值、逗号，优先级和结合律完全一致。a + b * c、a < b && b < c、a = b = c 这些 C 的肌肉记忆到 C++ 不用改。 2. C++ 多了 ::（最高优先级）——作用域解析运算符，如 std::cout、MyClass::method。它优先级最高，不会和别的运算符混淆。 3. C++ 多了 .* ->*（成员指针）——用于通过成员指针访问类成员，优先级较高（后缀类）。日常很少用，第 7 章详讲。 4. C++ 的 static_cast<...>(...) 等"看起来像函数"——优先级当后缀看，static_cast<int>(d) + 1 先算 cast 再加 1，不会出错。 5. 复杂表达式别靠背表，多加括号——C 和 C++ 共同建议。优先级表是"查"的，不是"背"的。

常见错误

1. 位运算与关系运算混用不加括号

if (flags & mask == 0) { ... }   // ❌ 等价 flags & (mask == 0)

== 优先级高于 &，先算 mask == 0 得 bool（0/1），再 flags & 0/1。正确：if ((flags & mask) == 0)。C 程序员也踩这个，C++ 同样坑。

2. << 与 ?: 混用不加括号

std::cout << x > 0 ? "pos" : "neg";   // ❌ 等价 (cout << x) > 0 ? ...

<< 优先级高于 ?:，先算 cout << x，再和 0 比。正确：std::cout << (x > 0 ? "pos" : "neg")。C 里 printf 没这个坑，C++ 的 << 容易踩。

3. 以为优先级决定求值顺序

int side_effect();
int x = side_effect() + 1;   // 以为 side_effect 一定先调？

优先级只决定"谁跟谁结合"（语法结构），不决定求值顺序。side_effect() + 1 中 + 决定结合方式，但 side_effect() 和 1 哪个先算未指定（这里没影响，但 f() + g() 就有影响）。C 和 C++ 都这样。

实测：优先级到底怎么加括号（examples/4.12-1-precedence-evalorder.cpp）

表达式 实测值 实际分组
1 + 2 << 3 24 (1+2) << 3 —— + 高于 <<
1 << 2 + 3 32 1 << (2+3) —— 同上
a & b == c（a=1,b=2,c=4） 0 a & (b == c) = 1 & 0 —— == 高于 &
x = y = z = 7 7/7/7 x = (y = (z = 7)) —— 赋值右结合

位移与位运算最容易被 -Wparentheses 抓到，因为它们的优先级低于算术和关系运算，写代码时的"视觉分组"常常就是错的：

if (flags & MASK == MASK)   // ❌ 实际是 flags & (MASK == MASK)
if ((flags & MASK) == MASK) // ✅

三档速记（够用版）

  1. 最高：::、后置 ++/--、()、[]、.、->
  2. 一元 → 算术 → 位移 → 关系 → 相等 → 位与 → 位异或 → 位或 → 逻辑与 → 逻辑或
  3. 最低：?: → 赋值 → throw → 逗号

第二条里"位移 < 关系 < 相等"是最反直觉的一段：a & b == c 编译能过、结果却是错的，属于静默 bug。

常见错误补充

  1. flags & MASK == MASK：== 高于 &，实际算的是 flags & (MASK == MASK)。位运算与关系/相等运算混用时一律加括号。
  2. 1 << n + 1：+ 高于 <<，实际是 1 << (n + 1)。位移运算的范围常常因此差一位。

自测题

1. 选择题　a & b && c 的求值顺序（结合方式）是：

  • A. (a & b) && c（先位与再逻辑与）
  • B. a & (b && c)（先逻辑与再位与）
  • C. a & b && c 未指定
  • D. 编译错误
答案

A。&（位与，9 级）优先级高于 &&（逻辑与，12 级），所以 a & b && c 等价 (a & b) && c。先算 a & b（位与，无短路），再和 c 逻辑与（有短路）。C 也是同样优先级。

2. 判断题　std::cout << x < 0 ? "neg" : "pos"; 能正确打印 x 的正负。

答案

错。<< 优先级高于 <，< 高于 ?:，所以等价 ((std::cout << x) < 0) ? "neg" : "pos"——先输出 x，再把 cout 和 0 比（无意义），最后条件判断。修复：std::cout << (x < 0 ? "neg" : "pos");，加括号。C 里 printf 没这个坑。

3. 踩坑题　下面这段代码想测试 flags 的第 3 位是否为 1，哪里有问题？

unsigned flags = 0x08;   // 二进制 1000，第 3 位是 1
if (flags & 0x08 == 0x08) {
    std::cout << "bit 3 is set";
}
答案

== 优先级高于 &，等价 flags & (0x08 == 0x08) → flags & true → flags & 1。flags = 0x08 的最低位是 0，所以 flags & 1 == 0，条件 false，不打印——但逻辑上第 3 位确实为 1。

修复（加括号）：

if ((flags & 0x08) == 0x08) { ... }
// 或更简单：
if (flags & 0x08) { ... }   // 非 0 即真

C 程序员也踩这个——位运算和关系混用必加括号。

4. 应用题　不用查表，判断 a < b == c < d 的结合方式（假设 a,b,c,d 是 int）。

答案

< 和 == 同级（关系/相等运算符，7/8 级），左结合，所以 a < b == c < d 等价 ((a < b) == (c < d))——先算 a < b 得 bool，再算 c < d 得 bool，最后比较两个 bool 是否相等。

这种写法虽然合法，但可读性差，建议加括号：((a < b) == (c < d)) 或拆成 (a < b) && (c < d)（若想表达"两个条件都成立"）。C 也是同样优先级。

4. 计算题：a=1, b=2, c=4，a & b == c 的值是多少？实际分组是什么？

答案

值为 0，实际分组是 a & (b == c) = 1 & 0 = 0。

因为相等运算符的优先级高于按位与。想表达"先与再比较"必须写 (a & b) == c。

这类 bug 是静默的：编译通过、无警告（除非开 -Wparentheses），只是结果不对——在位标志判断里尤其致命。

5. 判断题：1 + 2 << 3 等于 (1 + 2) << 3 还是 1 + (2 << 3)？

答案

(1 + 2) << 3 = 24（实测）。加法优先级高于位移；若按另一种分组则是 1 + 16 = 17。

反向的例子 1 << 2 + 3 实测是 32，即 1 << (2 + 3)——同样因为是 + 更高。

记忆法：位移的优先级低得离谱，跟它混用的算术一律要括号。

4.12

.2 求值顺序与括号规范

本节讲什么

求值顺序与优先级的区别；未指定顺序的陷阱；教材推荐的括号写法。

优先级 ≠ 求值顺序

int f(), g();
int h = f() + g();   // 先调 f 还是先调 g？**未指定**

编译器可任意选择，同一表达式多次运行结果可能一致，但不能依赖调用顺序。

有保证的情况 说明
&& || 左侧为假/真时，右侧不求值（短路）
?: 只求值被选中的分支
, 逗号 左侧先于右侧
赋值 = 右侧先于左侧（对操作数求值）

位运算 & | 没有短路顺序保证。

未定义行为经典坑

同一表达式多次修改

int i = 0;
// i = i++;           // ❌ UB
// v[i] = i++;        // ❌ UB（下标与右侧 i 无顺序）

函数实参

// f(++i, ++i);       // ❌ UB：哪个实参先求值未指定

HFT / 工程：热路径表达式保持简单；需要顺序就拆成多条语句。

括号规范（教材建议）

  1. 不靠背表解决复杂式——多加括号表达意图
  2. 混合算术、关系、逻辑时括号分组
  3. ?: 与 <<、= 混用必加括号
  4. 位运算与逻辑混用时分组：(a & mask) != 0 
// 可读性优先
bool ok = (flags & kReady) != 0 && (flags & kValid);

背诵极简版

优先级：谁跟谁先结合；结合律：同级从左/从右
求值顺序：操作数何时算——f()+g() 顺序不定
&& || ?: , 赋值右侧 有顺序保证；& | 无短路
同一式子多次改同一变量 → UB
复杂表达式加括号，别硬背

示例

#include <iostream>

int main() {
    int a = 2, b = 3;
    std::cout << a + b * 4 << "\n";           // 14

    int grade = 75;
    std::cout << (grade < 60 ? "fail" : "pass") << "\n";

    int x, y, z;
    x = y = z = 0;

    return 0;
}

和 C 的区别（求值顺序：C/C++ 完全一致，这是"共享的坑"）

求值顺序是 C 和 C++ 完全共享的"坑"——优先级不决定求值顺序、f()+g() 未指定、i=i++ UB、函数实参求值未指定，两边一字不差：

对比点 C C++
优先级 ≠ 求值顺序 ✅ 一致 ✅ 一致
f() + g() 求值顺序未指定 ✅ ✅ 一致
&& \|\| 短路 ✅ ✅ 一致
?: 只算选中分支 ✅ ✅ 一致
, 从左到右 ✅ ✅ 一致
赋值右侧先于左侧 ✅ ✅ 一致
i = i++ UB ✅ ✅ 一致
函数实参求值未指定 ✅ ✅ 一致
位运算无短路 ✅ ✅ 一致

给 C 程序员的关键提醒： 1. 求值顺序坑两边一模一样——C 学的警惕心全部迁移。f()+g() 顺序未指定、i=i++ UB、函数实参求值未指定，C 和 C++ 完全一致。 2. C++17 起对部分运算符加了顺序保证——<<、>>、赋值的右侧、后缀 ++/-- 等有了更多顺序保证（C++17 之前和 C 一样未指定）。但别依赖，老代码可能用 C++14 编译，行为不同。 3. HFT 热路径表达式保持简单——需要顺序就拆成多条语句，别在复杂表达式里赌求值顺序。C 程序员的"拆语句"习惯直接用。

常见错误

1. i = i++ 以为"先赋值再自增"

int i = 0;
i = i++;   // ❌ UB，不是"i=0 然后 i 变 1"

i = i++ 在一次表达式中对 i 修改两次（一次 =、一次 ++），且修改无顺序保证。C 和 C++ 都是 UB。拆成两条语句：int tmp = i; ++i; i = tmp; 或干脆 i = i + 1;。

2. 函数实参求值顺序依赖

int i = 0;
f(++i, ++i);   // ❌ UB：两个实参求值未指定顺序

两个 ++i 的求值顺序未指定——可能都先算 ++i（i 变 2，传 f(2, 2)），也可能分别算（传 f(1, 2) 或 f(2, 1)）。拆开：

int a = ++i;
int b = ++i;
f(a, b);

3. v[i] = i++ 下标与右侧无序

int i = 0;
std::vector<int> v(10);
v[i] = i++;   // ❌ UB：v[i] 的下标 i 和右侧 i++ 无序

v[i] 的下标 i（读）和右侧 i++（写）之间没有顺序保证——i++ 可能在算下标前、后、中间执行。拆开：v[i] = i; ++i;。C 里 arr[i] = i++ 同样 UB。

实测：哪些顺序是标准保证的（examples/4.12-1-precedence-evalorder.cpp）

用带打印的探针函数观察"谁先被求值"：

场景 有无保证 实测
&& / \|\| ✅ 短路 + 从左到右 左操作数为 0 时，右操作数根本没被求值
?: ✅ 只求值选中分支 1 ? A : B → 只有 A 被求值
, 逗号 ✅ 从左到右 step1 逗号左、step2 逗号右
<< / >> ✅ C++17 起 step1 左侧、step2 右侧
=、[]、->* ✅ C++17 起 右操作数先求值，再写入/索引
函数实参 ❌ 至今未指定 实测 clang 从左到右，但标准不保证

最容易被误以为有保证的是函数实参。实测本机 clang 是 f(A, B) 里 A 先于 B，但换个编译器、换个优化级别都可能反过来——所以绝不能在一个实参里改、另一个实参里读同一个变量。

C++14 vs C++17：同一个表达式，两种命运

int i = 0;
i = i++;      // C++14：UB（-Wunsequenced 警告）
              // C++17：定义良好 = 0（右操作数先求值并写回，再把旧值赋给 i）

C++17 给赋值运算符加了"右操作数 sequenced-before 左操作数的写入"这条规则，于是 i = i++ 从 UB 变成了有定义的行为（实测结果 0）。但注意：这只是"定义良好"，不代表"符合你的意图"——别写这种代码。

j++ + ++j 在任何标准下都是 UB（实测 2，换个优化级别可能不同）。

三句话

  1. 优先级只决定"怎么加括号"，不决定"谁先算"——这两件事由不同规则管。
  2. 有保证的只有：&&、\|\|、?:、,，以及 C++17 起的 <<、>>、=、[]、->*。
  3. 函数实参顺序至今未指定，别在一个实参里改、另一个实参里读同一个变量。

常见错误补充

  1. 依赖函数实参的求值顺序：f(g(i), ++i) 在任何标准下都未指定顺序（实测 clang 从左到右，但不可依赖）。修正：拆成两条语句。
  2. 以为 C++17 修好了所有求值顺序：C++17 只修了 <</>>/=/[]/->* 等少数几个，函数实参依然未指定。
  3. 写 i = i++：C++17 起虽然定义良好（实测结果 0），但语义反直觉，读代码的人一定会卡住。

自测题

1. 选择题　f() + g() 中 f 和 g 的调用顺序是：

  • A. f 先调
  • B. g 先调
  • C. 未指定，编译器决定
  • D. 并行调用
答案

C。+ 操作数的求值顺序未指定——编译器可以任意选 f 或 g 先调。C 和 C++ 都这样。要保证顺序用 ; 拆开：int a = f(); int b = g(); int h = a + b;。若 f/g 无副作用（不修改共享状态），顺序无所谓。

2. 判断题　i = i++ 在 C++ 中是合法的，结果是 i 自增 1。

答案

错。i = i++ 是 UB（未定义行为）——一次表达式中对 i 修改两次（= 和 ++），且修改无顺序保证。C 也是 UB。可能结果是 0、1、或任意值，甚至崩溃。拆成两条语句：i = i + 1; 或 ++i;。

3. 踩坑题　下面这段代码在 C 和 C++ 中行为如何？

int i = 0;
std::cout << i << " " << i++ << " " << i;   // 想输出 "0 0 1"
答案

UB（未定义行为），C 和 C++ 都是。<< 的多个操作数（i、i++、i）求值顺序未指定——i++ 可能在第一个 i 前、后、中间执行，输出不可预测。可能输出 0 0 1、1 0 0、0 0 0，或其他。

修复（拆成多条语句）：

int i = 0;
std::cout << i << " ";   // 0
++i;
std::cout << i - 1 << " " << i;   // 0 1

或用 C++17 的顺序保证（<< 的操作数从左到右求值，但别依赖，老编译器不支持）。

4. 应用题　HFT 代码要"自增计数器并记录前一个值"，如何安全写？

答案 
// ❌ UB：prev 和 counter++ 无序
// int prev = counter++;

// ✅ 安全：拆成两条语句
int prev = counter;
++counter;

// ✅ 或用后置 ++ 的返回值（标准保证后置 ++ 返回原值）
int prev = counter++;   // ✅ 合法！这是单独一条语句，不是混合表达式

要点： - int prev = counter++; 是合法的——后置 ++ 标准保证"返回原值，再自增"，这是一条语句不是混合表达式 - i = i++ 才是 UB（一次表达式里 i 被改两次） - 担心可读性就拆开：int prev = counter; ++counter;

C 程序员的 int prev = counter++; 习惯直接用，C 和 C++ 都合法。

4. 判断题：std::cout << i << " " << ++i; 在 C++14 和 C++17 下分别是什么行为？

答案
  • C++14：未定义行为。<< 的左右操作数求值顺序未指定，可能先算 ++i 再读 i，输出 1 1 或其他。
  • C++17：输出 0 1。C++17 规定 << 的左操作数 sequenced-before 右操作数。

教训：不要在同一个表达式里既修改又读取同一个变量——即使 C++17 修了 <<，其他运算符的求值顺序依然可能未指定。

5. 选择题：下面哪些有求值顺序保证？（多选） - A) a && b - B) f(g(), h()) 的两个实参 - C) a << b - D) cond ? x : y

答案

A、C、D（B 没有）。

  • A ✅ &&/||：短路 + 从左到右（C++ 一直如此）。
  • B ❌ 函数实参的求值顺序至今未指定，实测 clang 从左到右，但标准不保证，换编译器可能反过来。
  • C ✅ C++17 起 <</>> 的左操作数先于右操作数（C++14 及以前没有）。
  • D ✅ ?: 保证先求值条件，再只求值被选中的分支。

Q2四种 cast
const char *pc = "hello";
// char *p = static_cast<char*>(pc);      // A
char *p = const_cast<char*>(pc);           // B
p[0] = 'H';                                // C: UB?

A 行为什么编译失败？C 行是 UB 吗？

答案与复习指引

A 行失败： static_cast 不能去掉 const。去掉 const 必须用 const_cast。

C 行是 UB： 字符串字面量 "hello" 存储在只读区，通过 const_cast 去掉 const 后修改只读内存是未定义行为（可能段错误）。const_cast 只用于"原本不是 const 但被 const 接口传出来"的场景。

四种 cast 用途： - static_cast：常规类型转换（int→double, void→int） - dynamic_cast：多态向下转型（运行时检查） - const_cast：增删 const - reinterpret_cast：位模式重新解释（最危险）

Q3隐式转换陷阱
unsigned int u = 10;
int i = -42;
std::cout << i + i << std::endl;   // A
std::cout << u + i << std::endl;   // B

A 和 B 分别输出什么？为什么？

答案与复习指引

A: -84（两个 int 相加，正常） B: 4294967254（i 被隐式转换为 unsigned int，-42 变成 4294967254，再加 10 = 4294967264... 实际取决于 unsigned 的位宽）

根因： 当 int 和 unsigned 混合运算时，int 被隐式转换为 unsigned。负数转为 unsigned 会变成很大的正数。这是 C/C++ 共有的经典 bug 来源。

Q4条件运算符
int grade = 85;
std::string final = (grade < 60) ? "fail" : "pass";
// 嵌套条件运算符
std::string level = (grade >= 90) ? "A" : (grade >= 80) ? "B" : (grade >= 70) ? "C" : "F";

Q5sizeof 与类型
struct Empty {};
class Base { virtual void f() {} };
struct Derived : Base { int x; };

std::cout << sizeof(Empty) << " " << sizeof(Base) << " " << sizeof(Derived);

输出是什么（64 位系统）？为什么 sizeof(Empty) 不为 0？

答案与复习指引

输出： 1 8 16（具体取决于编译器/对齐）

  • sizeof(Empty) = 1：C++ 规定空类大小不为 0（通常为 1），保证不同对象地址唯一
  • sizeof(Base) = 8：有虚函数的类含 vptr（8 字节指针）
  • sizeof(Derived) = 16：vptr（8）+ int x（4）+ padding（4，对齐到 8）
