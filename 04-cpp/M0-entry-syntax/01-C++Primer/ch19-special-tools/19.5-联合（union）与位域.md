# 19.5 联合（union）与位域

## 本节讲什么

union（所有成员共享同一块内存）和位域（bitfield，按位打包字段）是
**协议解析和内存极致压缩**的两件底层工具——也是"写出来的结构体必须和网线上字节流
一模一样"时唯一可靠的语言手段。代码均经**本机 g++ 13.3 / -std=c++17 实测**（2026-10-07）。

## ① union：同一块内存的多种解读

```cpp
union Header {
    uint32_t raw;                    // 整个 4 字节当一个整数
    struct {                         // 或者按字段拆着看
        uint32_t type : 8;
        uint32_t seq  : 20;
        uint32_t flag : 4;
    } parts;
};
Header h{}; h.parts.type = 2; h.parts.seq = 1000;
// 本机实测：sizeof(Header)=4，h.raw=0x3e802——写 parts 立即反映到 raw
```

规则与要点：
- `sizeof(union)` = **最大成员**的尺寸（按对齐向上取整）
- 任意时刻只有**一个成员是"活"的**——写 A 读 B 在 C++ 里技术上是 UB
  （实际中"同布局重解读"（type punning）广泛用于协议解析，编译器按扩展支持；
  严格可移植的替代是 `std::memcpy` 或 C++20 `std::bit_cast`）
- C++11 起 union 可以含**非平凡成员**（string/vector），但要自己管理
  构造/析构（placement new + 手动析构）——工程上基本只放 trivial 类型

## ② struct 里的匿名 union：省一个名字，多一分类型安全

```cpp
struct Tick {
    uint8_t kind;            // tag：后面 union 里谁活着
    union {                  // 匿名：成员直接提升为 Tick 的成员
        int64_t i;
        double d;
    };
};
Tick t{}; t.d = 3.14;
// 本机实测：sizeof(Tick)=16（tag + padding + 8B union，对齐到 8）
```

这就是经典 **tagged union / discriminated union**——C 时代的 variant。
**现代替代品**：`std::variant<int64_t, double>` 自带 tag 管理、类型安全访问
（`std::get`/`std::visit`），错误的类型访问抛异常而不是 UB（→ M5 C++17 ch16）。
协议解析选裸 union（要逐字节控制布局），业务逻辑选 variant（要安全）。

## ③ 位域：按位打包（实测）

```cpp
struct alignas(1) Packed {
    uint8_t  a : 3;      // 3 位
    uint8_t  b : 5;      // 5 位——凑满 1 字节
    uint16_t c : 9;      // 9 位
};
// 本机实测：sizeof(Packed)=4（17 位按存储单元向上取整）
```

**协议头的真实形态**：

```cpp
struct /* 某交易所行情头 */ {
    uint16_t msg_len;
    uint8_t  msg_type;
    uint8_t  flags;
    uint32_t seq_num;
} __attribute__((packed));   // GCC/Clang：禁对齐填充；MSVC 用 #pragma pack(1)
```

**三个必须知道的坑**：
1. **位域的布局是实现定义的**（从高位还是低位开始排、跨单元规则）——
   跨编译器/跨平台的协议**不能只靠位域**，必须配 static_assert + 打包属性 + 抓包验证
2. 位域**没有地址**（`&p.a` 编译错误）——不能绑引用/指针
3. 位域的符号性随编译器（`int x : 1` 是 signed 还是 unsigned 不保证）——
   明确写 `uint8_t`/`int32_t` 等定宽类型

## ④ 布局三件套：协议结构体的验收纪律

```cpp
static_assert(sizeof(Packed) == 4, "布局漂移！");
static_assert(offsetof(Tick, d) == 8, "union 偏移变了");
static_assert(alignof(Header) == 4, "对齐变了");
```

协议结构体改任何字段都必须过 static_assert 三件套——
**编译期挡住布局漂移**，比上线后解码错位便宜一万倍。

## 和 C 的区别 / 新手要点

| C | C++ |
|---|---|
| union 随便用（平凡类型） | 非平凡成员要手动生命周期管理；有 variant 兜底 |
| 位域协议解析日常 | 同样日常，但多了 static_assert 编译期验收 |
| 无 | `std::bit_cast`（C++20）做严格合法的 type punning |

新手要点：① union 写谁读谁；② 位域没地址；③ 跨平台协议别裸信位域布局；
④ 业务代码用 `std::variant` 别手搓 tagged union。

## HFT 关联

- **行情解码的本质就是 union + 位域 + packed struct**：协议头按字节映射成结构体，
  `reinterpret_cast<const Header*>(buf)` 直接读（零拷贝解码）——
  比逐字段反序列化快一个数量级（→ 14-hft-engineering 行情解码）
- 缓存行预算下位域是压缩利器：订单簿一档的价格档标志位打包进 1 字节
- 跨交易所协议适配层**必须**有 static_assert 三件套 + 每协议的 golden-packet 回放测试
- 零拷贝解码的 UB 边界：严格来说要写 `std::memcpy(&h, buf, sizeof h)` 让编译器优化掉；
  `reinterpret_cast` 直读要确认对齐（`alignof(Header)` ≤ buf 对齐）与字节序（→ 03.5/hton）

## 代码自测

**题目 1：** `union { uint32_t u32; uint8_t u8[4]; }` 里写 `u32 = 0x01020304`，
小端机上 `u8[0]` 是多少？这段代码严格来说合法吗？

<details>
<summary>参考答案</summary>

`u8[0] = 0x04`（小端低地址放低字节）。
严格 C++ 语义：写 u32 读 u8 是"非活成员读取"，技术上 UB；但 `u8[N]` 有个特例——
任何对象都可以按 **char/unsigned char/std::byte 数组**检查其表示，所以读 u8 是合法的。
反过来写 u8 读 u32 同样 UB（别名规则），工程上常用但要知道边界；严格写法用
`std::memcpy` 或 C++20 `std::bit_cast<uint32_t>(u8)`。

</details>

**题目 2：** 为什么不能对位域取地址？`uint8_t& r = p.a;`（a 是 3 位的位域）为什么编译失败？

<details>
<summary>参考答案</summary>

地址的最小单位是**字节**，而位域占的是字节内的若干**位**——硬件和 ABI 都无法表达
"第 3 字节的第 2 位起"这样的地址。所以位域没有地址，也就不能绑到引用或指针。
变通：给位域配 get/set 成员函数，或用 `std::bitset` 的 `reference` 代理。

</details>

**题目 3：** 交易所升级协议，把 `seq` 从 20 位扩到 24 位，`flag` 从 4 位砍到 0 并删除——
除了改结构体，工程上还要动哪三处？

<details>
<summary>参考答案</summary>

① static_assert 三件套（布局断言按新布局更新）；
② golden-packet 回放测试（新老协议各准备样本包验证解码）；
③ 协议版本协商/识别逻辑（网关同时在线新老版本时按 msg_type 或版本字段分流，
  → 18.2 inline namespace 版本化）。
少了任何一处，布局漂移就会在开盘瞬间变成生产事故。

</details>
