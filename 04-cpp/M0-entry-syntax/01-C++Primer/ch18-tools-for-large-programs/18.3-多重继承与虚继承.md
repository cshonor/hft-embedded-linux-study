# 18.3 多重继承与虚继承

## 本节讲什么

多重继承（MI）是 C++ 最有争议的特性：接口组合离不开它，菱形继承和布局复杂度又让人怕它。
本节把三件事讲清：MI 的**内存布局**（this 调整）、**菱形问题与虚继承**、
以及工程上的安全用法（混入接口 vs 数据继承）。代码均经**本机 g++ 13.3 / -std=c++17 实测**（2026-10-07）。

## ① MI 的内存布局与 this 调整（实测）

```cpp
struct A { int a = 1; };
struct B { int b = 2; };
struct C : A, B { int c = 3; };
int main() {
    C obj;
    B* pb = &obj;
    // &obj == 0x...dc6c，pb == 0x...dc70（+4 偏移！）
}
```

**本机实测**：

```
sizeof(C) = 12                 ← A 子对象 + B 子对象 + 自身成员顺序排列
&obj = 0x7ffc...dc6c
pb   = 0x7ffc...dc70           ← B* 不指向对象开头，指向 B 子对象（this 调整 +4）
```

**推论**：
1. MI 下基类指针**不等于**对象首地址（除第一个基类）——
   所以 `(B*)&obj` 这类 C 强转在 MI 下是**错的**（不做偏移调整），
   必须用 `static_cast<B*>(&obj)`（编译器插入偏移）。
2. 每个带虚函数的基类各带一个 vptr——`C : A(虚), B(虚)` 的对象有**两个** vptr。
3. `dynamic_cast`/`typeid` 在 MI 下要做运行时偏移计算，比单继承贵。

## ② 菱形继承与虚继承（实测）

```
     A                普通继承：D 和 E 各带一份 A → F 里有两份 A（二义 + 浪费）
    / \               虚继承：  A 只有一份，D/E 通过虚基表指针找到共享的 A
   D   E
    \ /
     F
```

```cpp
struct D : virtual A { };
struct E : virtual A { };
struct F : D, E { };        // A 只有一份
```

**本机实测**：

```
sizeof(F) = 24    ← 两个 vptr（含虚基指针）+ 共享的一份 A(int) + 对齐
sizeof(D) = 16    ← vptr(8) + A::a(4) + padding
非虚版本的话，D、E 里各有一份 A → F 中 A 出现两次，sizeof 至少 8 字节纯浪费且 a 有二义
```

**虚继承的三个代价**（想清楚再用）：
1. 对象里多一个**虚基表指针**（vptr 变大），每次访问虚基成员多一次间接
2. **最派生类负责构造虚基**：`F` 的构造函数直接调用 `A` 的构造，
   `D`/`E` 构造里对 `A` 的初始化**被忽略**——初始化责任跳级，新人极易踩
3. 向下转型（`F* → D*`）需要运行期查虚基表，`static_cast` 变贵

## ③ 工程安全用法：接口混入（mixin）而非数据共享

工业界对 MI 的共识用法是**第二个及以后的基类都是"接口"**（纯虚、无数据、无状态）：

```cpp
struct Serializable {                        // 接口：无数据
    virtual ~Serializable() = default;
    virtual void serialize(Buffer&) const = 0;
};
struct Measurable {                          // 接口：无数据
    virtual ~Measurable() = default;
    virtual double latency_ns() const = 0;
};

struct Order : MktDataBase, Serializable, Measurable {   // 数据单继承 + 接口多继承
    void serialize(Buffer&) const override { /*...*/ }
    double latency_ns() const override { /*...*/ }
};
```

- 数据继承保持**单链**（避开菱形），能力扩展走**接口 MI**——
  这就是 Java/C# `interface` 的 C++ 表达
- CRTP（`class T : public Base<T>`）能在**编译期**实现类似 mixin 的效果且零虚函数开销——
  热路径优先 CRTP（见 ch16 模板），运行期多态需求才用接口 MI

## ④ 其他必知点

- **名字冲突**：两个基类有同名成员 → 调用处必须显式限定 `obj.A::f()`，
  或在派生类用 `using A::f;` 消除二义
- **虚函数覆盖**：`C::f()` 可以同时覆盖 `A::f` 和 `B::f`（签名一致时）——编译器为
  B 的 vtable 生成 **thunk**（调整 this 再跳转）的桥接函数
- **析构顺序**：与构造相反——自身 → 基类按声明**逆序**（先 B 后 A）
- `virtual` 析构只在**第一个基类**声明就够吗？不——任何"可能被基类指针 delete"
  的基类都必须有虚析构，否则 delete 经该基类指针 = UB

## 和 C 的区别 / 新手要点

| C | C++ |
|---|---|
| 结构体嵌套模拟"继承"，强转全靠布局巧合 | 真正的 MI + 编译器管理的 this 调整 |
| 无接口概念，函数指针表手搓 | 纯虚基类 = 接口，vtable 自动生成 |
| 无 | 虚继承/虚基表（C 完全没有对应物） |

新手要点：① 默认单继承；需要"既是 A 又是 B"时先问"第二个能不能是接口"；
② 菱形出现一律虚继承 or 重构；③ 永远不用 C 强转跨 MI 类型。

## HFT 关联

- **热路径避免虚继承**：虚基成员访问多一次指针间接（潜在 cache miss），
  延迟敏感的行情/订单对象坚持单链布局（→ M3 对象模型 ch03 虚继承布局详解）
- **接口 MI 是策略框架的骨架**：`Strategy : MdSink, OrderGateway`——
  一个策略类同时被行情驱动和下单回调驱动，两个接口都是纯虚无数据
- this 调整意味着 **回调注册时传的 `this` 必须按接口类型 cast 好**——
  C 回调风格（`void*`）配 MI 是经典 crash 源（→ 18.4 RTTI / M3 对象模型）

## 代码自测

**题目 1：** `C` 继承 `A`、`B`（均有虚函数），`sizeof(C)` 至少是多少（x86_64，int=4）？

<details>
<summary>参考答案</summary>

A、B 各带一个 vptr：8 + 8；`A::a`、`B::b`、`C::c` 三个 int：12。
合计 ≥ 8+8+12 = 28，对齐到 8 → **32 字节**。
（若 A、B 无虚函数则无 vptr，就是本节的 12。）

</details>

**题目 2：** 下面为什么崩？

```cpp
struct A { virtual ~A(){} }; struct B { virtual ~B(){} };
struct C : A, B {};
C* c = new C;
B* b = c;
delete (C*)(void*)b;     // 经 void* 来回强转
```

<details>
<summary>参考答案</summary>

`b` 指向 C 对象内的 **B 子对象**（地址偏移 ≠ 对象开头，见 ① 实测）。
经 `void*` 强转回 `C*` 时**不会做偏移调整**——delete 的地址不是对象首地址：
释放错误地址 + 析构用错 this，UB（实测大概率崩或堆损坏）。
正解：`C* c2 = static_cast<C*>(b);`（编译器自动减偏移）再 delete，或直接 `delete c;`。

</details>

**题目 3：** 虚继承里 `F` 的构造列表写 `F() : D(), E(), A(42) {}`，`D` 的构造列表里
也写了 `A(1)`——最终 `A` 用哪个值构造？

<details>
<summary>参考答案</summary>

**42**。虚基类由**最派生类**（F）直接构造；D、E 构造列表中对 A 的实参被忽略
（非最派生时 D 单独构造才会用它自己的 A(1)）。这就是"初始化责任跳级"——
阅读虚继承体系时，虚基的初始化只看最派生类。

</details>
