# 18.2 命名空间 namespace

## 本节讲什么

`namespace` 解决的是 C 时代靠前缀硬扛的**命名冲突**问题。本节覆盖：
定义与嵌套、`using` 声明 vs 指令的坑、未命名命名空间（替代 `static`）、
inline 命名空间（库版本化的现代手段）、ADL（参数依赖查找——"为什么 `std::swap` 不写 `std::` 也能调"）。
代码均经**本机 clang++ 23.1.0 / -std=c++17 实测**（2026-11-02 复测，早期版本为 g++ 13.3）。

⑥ 是本节的重头：**为什么全世界的 C++ 开发者都说别用 `using namespace`**——
七条理由（撞车率实测 63–75%、标准升级让源码变脆、头文件传染、ADL 被破坏……）、
一条反方澄清（它不是性能问题，实测编译与二进制均无差异）、一份白名单，
以及 C++ Core Guidelines SF.6/SF.7 与 Google Style Guide 的逐字原文。

## ① 定义与嵌套

```cpp
namespace math {
    int abs(int x) { return x < 0 ? -x : x; }
    namespace detail {          // 嵌套：实现细节藏起来
        int gcd(int a, int b);
    }
}
namespace a::b::c { void f(); }  // C++17 嵌套简写，等价于三层嵌套
```

要点：
- 命名空间**可以跨文件重复打开**——同一 `namespace mylib` 出现在 10 个头文件里，
  它们拼成同一个命名空间（和类完全不同，类只能定义一次）
- 命名空间成员默认**外部链接**（别的 TU 可见）；想限制在本文件用 ③ 的未命名命名空间

## ② using 声明 vs using 指令（事故高发区）

```cpp
using math::abs;        // using 声明：只引入这一个名字，参与重载决议
using namespace math;   // using 指令：整个命名空间的名字都"可见"（不真正引入）
```

两者最本质的差别（决定了后面所有事故）：

| | `using X::name;`（using **声明**） | `using namespace X;`（using **指令**） |
|---|---|---|
| 放进来的 | 只这一个名字 | 整个命名空间**当前所有**名字，且**未来新增的也算** |
| 是不是声明 | 是——**会隐藏**外层同名 | 否——**不隐藏**任何东西，只是把名字"摊平"到最近的公共祖先作用域 |
| 和 ADL 的关系 | 与 ADL 结果合并，外层杂音被挡住 | 外层同名 + std 的 + ADL 的，三方平级混战 |
| 影响范围 | 所在块 / 命名空间 | 从该行到作用域结束，且**跟着头文件扩散** |

**纪律**：
1. **头文件里永远不写 `using namespace`**——它会传染给每个包含者，制造无法定位的冲突（实测见 ⑥）
2. `.cpp` 里可以用，但也尽量**局部用**：函数体内 `using std::cout;` 比文件级 `using namespace std;` 安全
3. `using namespace std;` 最常见的翻车：`std::count`/`std::find` 和你的同名函数撞车，
   错误消息在模板深处几十行
4. 泛型代码里要"两步走"：`using std::swap; swap(a, b);` —— 用 using 声明，**不要**用 using 指令

## ③ 未命名命名空间 = 现代版 `static`（文件内可见性）

```cpp
namespace {
    int file_local = 42;     // 只在本翻译单元可见（内部链接）
    void helper() {}
}
```

- 效果等价于全局 `static`，但**还能用于类型**（`static` 不能修饰类/模板）：

```cpp
namespace { struct Impl { /* pImpl 的实现 */ }; }   // static 做不到这个
```

- C++ 官方推荐用未命名命名空间代替文件级 `static`（`static` 的"内部链接"用法已被标记 deprecated 又恢复，但社区共识是 namespace 版更一致）

## ④ inline 命名空间：库的 ABI 版本化（C++11）

```cpp
namespace mylib {
    inline namespace v_current { void f() { std::cout << "current f\n"; } }
    namespace legacy           { void f() { std::cout << "legacy f\n"; } }
}
int main() {
    mylib::f();          // ✅ 打到 v_current::f——inline 空间的名字对上层"透明"
    mylib::legacy::f();  // 老版本仍可显式访问
}
```

**本机实测输出**：`current f` / `legacy f` —— `mylib::f()` 自动落到 inline 的那个。

用途：库升级时把新 API 放 `inline namespace v2`，旧版保留在 `v1`——
**老代码链接的符号名带 v1**（mangled name 不同），新老目标文件混链不炸。
标准库自己就在用：`std::chrono` 的部分符号在 `std::__1::chrono`（libc++ 的 inline 命名空间 `__1`）。

## ⑤ ADL（参数依赖查找 / Koenig lookup）

```cpp
namespace A {
    struct S {};
    void greet(const S&) { std::cout << "ADL 找到 A::greet\n"; }
}
int main() {
    A::S s;
    greet(s);            // 没写 A:: —— 编译器按**实参类型**追加查找 s 所在的命名空间 A
}
```

**本机实测输出**：`ADL 找到 A::greet`。

规则：调用未限定的函数名时，除常规查找外，**实参类型关联的命名空间**也加入查找集。
这就是这些写法能工作的原因：

```cpp
std::vector<int> v;
std::sort(v.begin(), v.end());     // 其实写 sort(...) 也可能编过（ADL 找到 std::sort）
cout << x;                         // operator<< 靠 ADL 找到（它不是你类的成员）
swap(a, b);                        // 自定义类型的 swap 惯例：靠 ADL 命中
```

**工程推论**：给你的类型写 `swap`/`operator<<`/`hash` 时，**放在类型自己的命名空间里**——
用户靠 ADL 自然命中，不用 `std::` 也不用 using。

## ⑥ 为什么全世界的 C++ 开发者都说「别用 using namespace」

### 先把这句话的歧义澄清

被禁的是 **`using namespace X;`（using 指令）**，不是 `namespace` 本身。
`namespace` 是**必须用的**——它就是为了解决 C 时代靠 `mylib_queue_push` 前缀硬扛的命名冲突。
C++ Core Guidelines 的原话是"With few exceptions, place code in a namespace"（Google Style Guide）。

真正有争议的只有这一句：

```cpp
using namespace std;    // ⚠ 全世界的争议都集中在这一行
```

下面七条理由每条都附本机实测（clang++ 23.1.0 / arm64 / libc++，2026-11-02）。

### 理由 1：std 里的短名字比你想的多得多（撞车率实测）

扫描方法：对候选标识符 `W`，生成
`namespace mine { int W; } using namespace mine; using namespace std;` 然后引用 `W`——
报 `ambiguous` 就说明 `std` 里已经有同名东西了。扫了 67 个最常见的英文标识符：

| 条件 | 撞车数 | 撞车率 |
|---|---|---|
| C++17 + 8 个常用头文件（algorithm/functional/iterator/utility/memory/vector/string/numeric） | 42/67 | **63%** |
| C++17 + 17 个常用头文件 | 46/67 | **69%** |
| C++20 + 17 个常用头文件 | 50/67 | **75%** |

C++17 那 42 个撞车名单（几乎全是业务代码里天天会写的词）：

```
count find size data empty begin end next prev move forward swap
ref cref bind less greater plus minus hash min max sort copy fill
get apply invoke merge index search replace remove transform reduce
accumulate distance advance tuple pair function time
```

C++20 比 C++17 又多撞了 `visit` `erase` `log` `format` 四个。

> ⚠ 这还是**保守估计**：只扫了 17 个头文件。
> 再加上 `<ranges>` `<execution>` `<random>` `<filesystem>` 只会更糟。
> 换句话说：`using namespace std` 之后，你起的每一个短名字都在和标准库掷骰子。

### 理由 2：标准库升级会主动来找你麻烦（最强的一条）

```cpp
namespace app { template <class C> int size(const C& c) { return (int)c.size(); } }
using namespace std;
using namespace app;
size(v);            // C++14: 编过     C++17: 二义
```

本机实测（`examples/18.2-4-version-fragility.cpp`，`-DTRIAL=1`）：

| 编译命令 | 结果 |
|---|---|
| `clang++ -std=c++14 -DTRIAL=1` | ✅ 编过，输出 `3` |
| `clang++ -std=c++17 -DTRIAL=1` | ❌ `error: call to 'size' is ambiguous`（`std::size` vs `app::size`） |

原因：`std::size` 是 **C++17 才进 `<iterator>`** 的。项目从 C++14 升到 C++17 的那天，
`app::size` 突然多了一个平级对手，两边签名还一模一样——**你的代码一行没改，编译就坏了**。

同类风险名单（每次标准升级都在变长）：

| 版本 | 新增的常见短名字 |
|---|---|
| C++11 | `begin` `end` `next` `prev` `move` `forward` |
| C++17 | `size` `empty` `data` `clamp` `sample` ← **`size` 是头号杀手** |
| C++20 | `ssize` `erase` `erase_if` `ranges::count` `ranges::find` |

结论：`using namespace std` 让你的代码**依赖标准库的具体版本**；
全限定名把这个依赖一刀切断——库以后加多少新名字都动不了你。

### 理由 3：头文件里写一次，传染每一个包含者，而且罪魁不在你文件里

`examples/18.2-3-header-pollution.h` 只做错一件事：在全局作用域写了 `using namespace std`。
而包含它的 `.cpp` **从头到尾没写过 `using namespace std`，也没 include `<algorithm>`**：

```
a.cpp:13:21: error: call to 'count' is ambiguous
  candidate: std::count    (__algorithm/count.h)   <- 哪来的？头文件带进来的
  candidate: app::count    (a.cpp 自己写的)
```

这就是 C++ Core Guidelines **SF.7** 的逐字理由：

> "Doing so takes away an `#include`r's ability to effectively disambiguate and to use alternatives.
> It also makes `#include`d headers order-dependent as they might have different meaning when included in different orders."
>
> —— 剥夺了包含者"自行消歧"的能力，还让 `#include` 变成了顺序相关的。

**Enforcement 也写得极其明确：Flag `using namespace` at global scope in a header file.**

### 理由 4：有时炸、有时不炸——不可预测才是真问题

同一个 `using namespace std;`，四种结局：

| 情形 | 结果 | 实测 |
|---|---|---|
| 你自己有个全局同名**声明** | 它**隐藏** std 的版本，静默编译过 | 调到了 `::count`，编译器一声不吭 |
| 两个 using 指令，一边是非模板 | 非模板优先，静默编译过 | 非模板赢 |
| 两个 using 指令，两边都是模板且签名贴近 | **二义，报错** | `count(b,e,2)` 报 ambiguous |
| 同名的是**类成员** | 完全不受影响 | 类作用域独立 |

这才是阴险的地方：**"我写了 `using namespace std` 一直没事"推不出"以后没事"**。
多数时候重载决议恰好能救场（参数个数不同、非模板优先），直到某天两边签名凑巧对齐，或者标准库新增了一个更匹配的版本——才突然爆。

### 理由 5：它破坏 ADL 两步走（泛型代码的正确姿势）

```cpp
template <class T> void good(T& a, T& b) { using std::swap; swap(a, b); }        // ✅
template <class T> void bad (T& a, T& b) { using namespace std; swap(a, b); }    // ❌
```

实测（`examples/18.2-2-adl-two-step.cpp`，外层留了一个遗留的全局 `::swap`）：

- `using std::swap;` 是**声明**，它**隐藏**了外层遗留的 `::swap` → 候选只剩 `std::swap` + ADL 找来的 `md::swap` → 非模板精确匹配胜出，正确命中自定义版本
- `using namespace std;` **不隐藏任何东西** → `::swap` + `std::swap` + ADL 的 `md::swap` 三方平级 → 前两个签名完全相同 → `error: ambiguous`

泛型代码里写 `swap` / `begin` / `end` / `operator<<`，一律两步走，别用 using 指令。

### 理由 6：可读性——`std::` 是免费的文档

看到 `count(b, e, 2)`，读者不知道这是哪个 `count`；看到 `std::count(b, e, 2)` 立刻明白。
这条没有实测数据，但它是代码评审、跨团队协作、以及"半年后的你自己"最直接的收益。

### 理由 7：`namespace std` 本身是禁区（常被一起提起的另一条）

Google Style Guide 逐字：

> "Do not declare anything in namespace std, including forward declarations
> of standard library classes. Declaring entities in namespace std is undefined behavior,
> i.e., not portable."

（允许的是针对**你自己类型**特化 `std::hash` / `std::swap` 这类——那是标准明确开的口子。）

### 反方：先把这条堵死——它**不是**性能问题

实测（`examples/18.2-1`，400 次 `std::count` 调用、8 个标准头）：

| 指标 | 全限定 `std::` | `using namespace std` | 差 |
|---|---|---|---|
| 编译时间（`-fsyntax-only`，中位数 ×7） | 0.346 s | 0.347 s | **+0.2%（噪声级）** |
| 二进制大小（`-O2`） | 16816 字节 | 16816 字节 | **完全相同** |
| 符号表 | 一致 | 一致 | 无差别 |

**所以别拿"影响性能"当理由**——那是错的，会被人一句话拆穿。
禁它是**工程与可维护性**理由：命名冲突、版本脆弱性、传染性、可读性。

### 什么时候可以用（白名单）

| 场景 | 判定 | 依据 |
|---|---|---|
| 头文件全局作用域 | ❌ **永远禁止** | Core Guidelines SF.7，Enforcement 明确要 flag |
| `.cpp` 文件顶部 | ⚠️ 可以，但建议只用于小文件 / demo | SF.6 Note：`"A .cpp file is a form of local scope."` |
| **函数体内** | ✅ 推荐——影响范围最小 | SF.6 标题里就写了 `within a local scope (only)` |
| `using std::swap;` 两步走 | ✅ 泛型代码正解 | 见理由 5 |
| `using namespace std::literals;` | ✅ **SF.7 明文例外** | UDL 必须带 `_x` 后缀，不会与标准库撞 |
| 命名空间别名 `namespace fs = std::filesystem;` | ✅ 但头文件里要放进 internal 命名空间 | Google：头文件里的别名会成为对外 API 的一部分 |

### 权威原文（逐字）

**C++ Core Guidelines SF.6**（`### SF.6: Use using namespace directives for transition, for foundation libraries (such as std), or within a local scope (only)`）

> ##### Reason
> `using namespace` can lead to name clashes, so it should be used sparingly.
> However, it is not always possible to qualify every name from a namespace in user code (e.g., during transition)
> and sometimes a namespace is so fundamental and prevalent in a code base, that consistent qualification
> would be verbose and distracting.

它给的反面例子（这个比对编译器更严格——变量名把函数名盖掉之后调用会直接报错）：

```cpp
#include <cmath>
using namespace std;
int g(int x) {
    int sqrt = 7;
    // ...
    return sqrt(x);    // error
}
```

**C++ Core Guidelines SF.7**（`### SF.7: Don't write using namespace at global scope in a header file`）

> ##### Reason
> Doing so takes away an `#include`r's ability to effectively disambiguate and to use alternatives.
> It also makes `#include`d headers order-dependent as they might have different meaning when included in different orders.
>
> ##### Note
> An exception is `using namespace std::literals;`. …
>
> ##### Enforcement
> Flag `using namespace` at global scope in a header file.

**Google C++ Style Guide → Scoping → Namespaces**

> "With few exceptions, place code in a namespace. Namespaces should have unique names based on the project name,
> and possibly its path. **Do not use using-directives (e.g., `using namespace foo`).** Do not use inline namespaces."
>
> "You may not use a using-directive to make all names from a namespace available.
> `// Forbidden -- This pollutes the namespace.` → `using namespace foo;`"

### 一个诚实的备注：规范之间也有分歧

注意 Google 那句里还禁了 **inline namespaces**——这跟本节 ④ 把 inline namespace 当"库版本化的现代手段"是冲突的。
两边都没错，只是取舍：

- **Google 的顾虑**：inline namespace 的"透明性"容易被误用，出问题时很难定位符号到底落在哪个版本
- **实践事实**：libstdc++ / libc++ 自己大量使用 inline namespace（libc++ 的 `std::__1`），它是 ABI 版本化的事实标准
- **选型建议**：如果你所在项目遵循 Google style，改用符号版本脚本或目录分层做版本化；自主项目里用于 ABI 版本化是可以的，但要像 ④ 说的那样**只放一个 inline**，别嵌套

```bash
cd examples
clang++ -std=c++17 -Wall -O2 18.2-1-using-directive-hazards.cpp -o a && ./a   # 四类事故 + 撞车率 + 性能反证

```

## 和 C 的区别 / 新手要点

| C | C++ |
|---|---|
| 前缀防冲突：`mylib_queue_push` | `namespace mylib { queue::push }` |
| 文件内私有：`static void helper()` | `namespace { void helper() {} }`（还能藏类型） |
| 无 | ADL / inline namespace / 跨文件拼装 |

新手要点：① 头文件禁 `using namespace`；② 内部实现放 `namespace detail`
或 `namespace impl`（社区惯例：detail 里的东西 = 别用）；③ 全局 `static`
换未命名命名空间是新代码的标准姿势。

## HFT 关联

- 大型交易系统按**子系统划分命名空间**（`md::`（行情）、`oms::`、`risk::`、`strat::`），
  跨模块调用全限定名一眼看出依赖方向
- inline namespace 是**行情解码库版本化**的标准做法：协议升级（如深交所 v1.19 → v1.22）
  时老策略二进制仍可链接旧符号
- ADL 对**模板库**尤其重要：写泛型代码时 `using std::swap; swap(a, b);` 两步走——
  让自定义类型的 swap 经 ADL 优先命中，标准 swap 兜底

### 补充：using namespace 纪律的工程收益

- **跨模块全限定名就是依赖图**：`md::` `oms::` `risk::` 一眼看出调用方向；夹一个 `using namespace` 就把这层信息抹掉了
- **协议升级期风险叠加**：行情解码库从深交所 v1.19 升 v1.22、同时项目从 C++17 升 C++20 的那段时间，
  理由 2 那类"没改代码却编不过"的事故最容易集中爆发
- **把它做成 CI 规则**：`grep -rn "^\s*using namespace" --include=*.h` 非零即失败；
  clang-tidy 对应项是 `google-build-using-namespace`——比人工评审可靠得多
- **热路径不受影响**：理由 6 的实测已经证明它对运行时零影响，所以这条纪律只管源码卫生，不用跟性能做取舍

## 代码自测

**题目 1：** 下面这段能编译吗？为什么？

```cpp
// a.h
namespace util { void log(const char*); }
using namespace util;
// b.cpp
#include "a.h"
void log(int);   // ?
```

<details>
<summary>参考答案</summary>

能编译但是地雷：`using namespace util` 写在头文件里，每个包含 a.h 的 TU 都被污染；
`util::log(const char*)` 和你的 `log(int)` 进入同一作用域——之后 `log("x")` / `log(1)`
的重载决议可能随包含顺序变化。头文件只允许 `using 声明`（也最好不），禁 `using 指令`。

</details>

**题目 2：** `namespace { static int x; }` 里的 `static` 多余吗？

<details>
<summary>参考答案</summary>

多余且自相矛盾：未命名命名空间已经把成员变成内部链接，再写 `static` 没有新效果
（语义相同，纯属冗余）。统一写成 `namespace { int x; }`。

</details>

**题目 3：** 为什么 `std::cout << my_type` 能找到你写的 `operator<<`，即使它不在 `std` 里？

<details>
<summary>参考答案</summary>

ADL：`operator<<` 的实参之一是 `my_type`（在你自己的命名空间 N 里），
编译器把 N 加入查找集，命中你在 N 里定义的 `operator<<`。
所以自定义类型的流输出运算符**就该放在类型自己的命名空间**，不要图省事放全局。

</details>

**题目 4：** 你的项目一直用 C++14，`using namespace std;` 加自家 `app::size()` 配合得很好。
升级到 C++17 后编译挂了，报错是 `call to 'size' is ambiguous`。为什么？

<details>
<summary>参考答案</summary>

`std::size` 是 **C++17 才加入 `<iterator>`** 的，签名 `size(const C&) -> decltype(c.size())`
和你家 `app::size(const C&) -> int` 结构一致，partial ordering 分不出高下 → 二义。

**你一行代码都没改，编译就坏了**——这就是 `using namespace std` 让代码依赖标准库版本的具体表现。
修法有两个方向：

1. 全限定：`app::size(v)` / `std::size(v)` —— 彻底切断依赖，推荐
2. 只在函数体内 `using namespace std;` —— 缩小影响范围

同类风险：C++11 的 `begin/end/next/prev/move/forward`、C++20 的 `ssize/erase/erase_if`。
每次升标准都要重新体检一遍。

</details>

**题目 5：** 下面两个泛型函数，为什么 A 能编过、B 会二义？（外层还有一个遗留的全局 `::swap`）

```cpp
template <class T> void A(T& a, T& b) { using std::swap;      swap(a, b); }
template <class T> void B(T& a, T& b) { using namespace std;  swap(a, b); }
```

<details>
<summary>参考答案</summary>

- **A**：`using std::swap;` 是 **using 声明**，它是一条真正的声明，会**隐藏**外层遗留的 `::swap`。
  查找集 = 块内的 `std::swap` + ADL 找来的 `md::swap`；`md::swap` 是非模板精确匹配，胜出。
- **B**：`using namespace std;` 是 **using 指令**，它**不隐藏任何东西**，只是让 std 的名字"看起来也在"外层作用域。
  查找集 = `::swap` + `std::swap` + ADL 的 `md::swap`；其中 `::swap` 和 `md::swap` 签名完全相同 → **ambiguous**。

**记住这条对照**：using 声明 = 会隐藏；using 指令 = 不隐藏、只摊平。
泛型代码里的 `swap`/`begin`/`end`/`operator<<` 一律两步走。

</details>

**题目 6：** 有人说"`using namespace std` 会拖慢程序、让二进制变大"。对吗？

<details>
<summary>参考答案</summary>

**不对**，这是流传很广的错误说法。本机实测（400 次 `std::count` 调用、8 个标准头、`-O2`）：

| 指标 | 全限定 | using namespace std |
|---|---|---|
| 编译时间中位数 | 0.346 s | 0.347 s（+0.2%，噪声级） |
| 二进制大小 | 16816 字节 | 16816 字节 |
| 符号表 | 一致 | 一致 |

`using` 只影响**名字查找**（编译前端），不产生任何代码，也不改变名字修饰。

正确的理由应该落在工程层面：命名冲突（实测撞车率 63–75%）、标准升级导致源码脆弱、
头文件传染、可读性。**别用性能来解释它**——一测就被拆穿。

</details>
