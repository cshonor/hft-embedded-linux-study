# 18.2 命名空间 namespace

## 本节讲什么

`namespace` 解决的是 C 时代靠前缀硬扛的**命名冲突**问题。本节覆盖：
定义与嵌套、`using` 声明 vs 指令的坑、未命名命名空间（替代 `static`）、
inline 命名空间（库版本化的现代手段）、ADL（参数依赖查找——"为什么 `std::swap` 不写 `std::` 也能调"）。
代码均经**本机 g++ 13.3 / -std=c++17 实测**（2026-10-07）。

## ① 定义与嵌套

```cpp
namespace math {
    int abs(int x) { return x < 0 ? -x : x; }
    namespace detail {          // 嵌套：实现细节藏起来
        int gcd(int a, int b);
    }
}
namespace a::b::c { void f(); }  // C++17 嵌套简写，等价于三层嵌套
```

要点：
- 命名空间**可以跨文件重复打开**——同一 `namespace mylib` 出现在 10 个头文件里，
  它们拼成同一个命名空间（和类完全不同，类只能定义一次）
- 命名空间成员默认**外部链接**（别的 TU 可见）；想限制在本文件用 ③ 的未命名命名空间

## ② using 声明 vs using 指令（事故高发区）

```cpp
using math::abs;        // using 声明：只引入这一个名字，参与重载决议
using namespace math;   // using 指令：整个命名空间的名字都"可见"（不真正引入）
```

**纪律**：
1. **头文件里永远不写 `using namespace`**——它会传染给每个包含者，制造无法定位的冲突
2. `.cpp` 里可以用，但也尽量**局部用**：函数体内 `using std::cout;` 比文件级 `using namespace std;` 安全
3. `using namespace std;` 最常见的翻车：`std::count`/`std::find` 和你的同名函数撞车，
   错误消息在模板深处几十行

## ③ 未命名命名空间 = 现代版 `static`（文件内可见性）

```cpp
namespace {
    int file_local = 42;     // 只在本翻译单元可见（内部链接）
    void helper() {}
}
```

- 效果等价于全局 `static`，但**还能用于类型**（`static` 不能修饰类/模板）：

```cpp
namespace { struct Impl { /* pImpl 的实现 */ }; }   // static 做不到这个
```

- C++ 官方推荐用未命名命名空间代替文件级 `static`（`static` 的"内部链接"用法已被标记 deprecated 又恢复，但社区共识是 namespace 版更一致）

## ④ inline 命名空间：库的 ABI 版本化（C++11）

```cpp
namespace mylib {
    inline namespace v_current { void f() { std::cout << "current f\n"; } }
    namespace legacy           { void f() { std::cout << "legacy f\n"; } }
}
int main() {
    mylib::f();          // ✅ 打到 v_current::f——inline 空间的名字对上层"透明"
    mylib::legacy::f();  // 老版本仍可显式访问
}
```

**本机实测输出**：`current f` / `legacy f` —— `mylib::f()` 自动落到 inline 的那个。

用途：库升级时把新 API 放 `inline namespace v2`，旧版保留在 `v1`——
**老代码链接的符号名带 v1**（mangled name 不同），新老目标文件混链不炸。
标准库自己就在用：`std::chrono` 的部分符号在 `std::__1::chrono`（libc++ 的 inline 命名空间 `__1`）。

## ⑤ ADL（参数依赖查找 / Koenig lookup）

```cpp
namespace A {
    struct S {};
    void greet(const S&) { std::cout << "ADL 找到 A::greet\n"; }
}
int main() {
    A::S s;
    greet(s);            // 没写 A:: —— 编译器按**实参类型**追加查找 s 所在的命名空间 A
}
```

**本机实测输出**：`ADL 找到 A::greet`。

规则：调用未限定的函数名时，除常规查找外，**实参类型关联的命名空间**也加入查找集。
这就是这些写法能工作的原因：

```cpp
std::vector<int> v;
std::sort(v.begin(), v.end());     // 其实写 sort(...) 也可能编过（ADL 找到 std::sort）
cout << x;                         // operator<< 靠 ADL 找到（它不是你类的成员）
swap(a, b);                        // 自定义类型的 swap 惯例：靠 ADL 命中
```

**工程推论**：给你的类型写 `swap`/`operator<<`/`hash` 时，**放在类型自己的命名空间里**——
用户靠 ADL 自然命中，不用 `std::` 也不用 using。

## 和 C 的区别 / 新手要点

| C | C++ |
|---|---|
| 前缀防冲突：`mylib_queue_push` | `namespace mylib { queue::push }` |
| 文件内私有：`static void helper()` | `namespace { void helper() {} }`（还能藏类型） |
| 无 | ADL / inline namespace / 跨文件拼装 |

新手要点：① 头文件禁 `using namespace`；② 内部实现放 `namespace detail`
或 `namespace impl`（社区惯例：detail 里的东西 = 别用）；③ 全局 `static`
换未命名命名空间是新代码的标准姿势。

## HFT 关联

- 大型交易系统按**子系统划分命名空间**（`md::`（行情）、`oms::`、`risk::`、`strat::`），
  跨模块调用全限定名一眼看出依赖方向
- inline namespace 是**行情解码库版本化**的标准做法：协议升级（如深交所 v1.19 → v1.22）
  时老策略二进制仍可链接旧符号
- ADL 对**模板库**尤其重要：写泛型代码时 `using std::swap; swap(a, b);` 两步走——
  让自定义类型的 swap 经 ADL 优先命中，标准 swap 兜底

## 代码自测

**题目 1：** 下面这段能编译吗？为什么？

```cpp
// a.h
namespace util { void log(const char*); }
using namespace util;
// b.cpp
#include "a.h"
void log(int);   // ?
```

<details>
<summary>参考答案</summary>

能编译但是地雷：`using namespace util` 写在头文件里，每个包含 a.h 的 TU 都被污染；
`util::log(const char*)` 和你的 `log(int)` 进入同一作用域——之后 `log("x")` / `log(1)`
的重载决议可能随包含顺序变化。头文件只允许 `using 声明`（也最好不），禁 `using 指令`。

</details>

**题目 2：** `namespace { static int x; }` 里的 `static` 多余吗？

<details>
<summary>参考答案</summary>

多余且自相矛盾：未命名命名空间已经把成员变成内部链接，再写 `static` 没有新效果
（语义相同，纯属冗余）。统一写成 `namespace { int x; }`。

</details>

**题目 3：** 为什么 `std::cout << my_type` 能找到你写的 `operator<<`，即使它不在 `std` 里？

<details>
<summary>参考答案</summary>

ADL：`operator<<` 的实参之一是 `my_type`（在你自己的命名空间 N 里），
编译器把 N 加入查找集，命中你在 N 里定义的 `operator<<`。
所以自定义类型的流输出运算符**就该放在类型自己的命名空间**，不要图省事放全局。

</details>
