# 18.1 异常处理（深入版）

## 本节讲什么

第 5 章只教了 `try/catch/throw` 的语法。本章把异常当**工程机制**讲透：
栈展开的精确顺序、`noexcept` 的真实作用（不只是"承诺不抛"）、
标准异常体系、异常安全三级保证。代码均经**本机 g++ 13.3 / -std=c++17 实测**（2026-10-07）。

## ① 栈展开（stack unwinding）：异常抛出后到底发生什么

`throw` 之后，控制流沿调用链**逐层退出**，每层像 `return` 一样销毁局部对象——
析构函数被调用，但层内 `throw` 点之后的代码**不再执行**：

```cpp
#include <iostream>
#include <stdexcept>
struct Tracer {
    const char* name;
    Tracer(const char* n) : name(n) { std::cout << "构造 " << name << "\n"; }
    ~Tracer() { std::cout << "析构 " << name << "\n"; }
};
void lvl2() { Tracer t2("lvl2"); throw std::runtime_error("boom"); }
void lvl1() { Tracer t1("lvl1"); lvl2(); std::cout << "不会到这\n"; }
int main() {
    try { lvl1(); }
    catch (const std::runtime_error& e) { std::cout << "捕获: " << e.what() << "\n"; }
}
```

**本机实测输出**：

```
构造 lvl1
构造 lvl2
析构 lvl2      ← 栈展开：先退 lvl2 帧
析构 lvl1      ← 再退 lvl1 帧（"不会到这"被跳过）
捕获: boom
```

**两个推论**：
1. RAII 对象（智能指针/容器/锁守卫/fstream）在异常路径上**自动清理**——
   这是 C++ 异常相对 C `setjmp/longjmp` 的本质优势（longjmp 不做任何清理）。
2. **析构函数绝不能抛异常**——栈展开中再抛 = `std::terminate`。
   所以所有标准容器的析构都是 `noexcept`，你写的析构也该是。

## ② noexcept：不是承诺，是**优化许可证**

标 `noexcept` 的函数抛异常 → `std::terminate`（不会展开到调用方）。
但它最大的实战价值不是语义承诺，而是**给标准库发许可证**：

```cpp
struct MoveThrow    { MoveThrow(){} MoveThrow(const MoveThrow&){ std::cout<<"拷贝\n"; }
                      MoveThrow(MoveThrow&&){ std::cout<<"移动\n"; } };              // 移动没标 noexcept
struct MoveNoexcept { MoveNoexcept(){} MoveNoexcept(const MoveNoexcept&){ std::cout<<"拷贝\n"; }
                      MoveThrow(MoveThrow&&) = delete;
                      MoveNoexcept(MoveNoexcept&&) noexcept { std::cout<<"移动\n"; } };
std::vector<MoveThrow> v1;    v1.emplace_back(); v1.emplace_back();   // 扩容时…
std::vector<MoveNoexcept> v2; v2.emplace_back(); v2.emplace_back();
```

**本机实测输出**：v1 扩容打印 `拷贝`，v2 扩容打印 `移动`。

原因：`vector` 扩容要搬元素，若移动构造**可能抛异常**，搬到一半抛出会破坏强保证——
于是它保守地选**拷贝**（拷贝抛了还能销毁新缓冲区回滚）。只有移动标了 `noexcept`，
扩容才敢用移动。**你的值类型的移动构造/移动赋值/ swap 永远标 noexcept**——
否则全仓库的 `vector<T>` 都在默默拷贝。

## ③ 标准异常体系与捕获顺序

```
std::exception
├── std::runtime_error   （运行时才发现：overflow_error / system_error / ios_base::failure）
├── std::logic_error     （程序逻辑错误：invalid_argument / out_of_range / length_error）
├── std::bad_alloc       （new 失败）
├── std::bad_cast        （dynamic_cast 引用版失败）
└── std::bad_exception
```

- **捕获按声明顺序匹配，派生类在前**：`catch (const runtime_error&)` 必须写在
  `catch (const exception&)` 前面，否则永远被基类截胡（编译器会给警告）。
- 永远**按 const 引用捕获**：`catch (const std::exception& e)`——按值捕获会**切片**
  （派生类被拷成基类，`what()` 多态失效）。
- `throw;`（空 throw）在 catch 内**原样重抛**当前异常，保留原始类型；
  `throw e;` 会切片成静态类型。

## ④ 异常安全三级保证（写库时的契约）

| 级别 | 承诺 | 例子 |
|---|---|---|
| 基本保证 | 异常后对象仍可用（不泄漏、不变性不破坏），但状态可能已变 | `vector::push_back` 分配失败 |
| 强保证 | 操作要么完全成功，要么回滚到调用前状态 | `vector` 扩容失败时原内容不变 |
| 无异常保证 | 永不抛出 | 析构、移动构造、swap、`vector::size` |

**工程推论**：自己写容器/资源类时，先想清楚每个操作给哪一级——
然后"先改副本、再 noexcept swap 提交"（copy-and-swap 惯用法）就能用
基本保证的零件拼出强保证的整体。

## ⑤ 函数 try 块（冷但考过）

构造函数的成员初始化列表抛异常，普通函数体 catch 接不住——要包整个构造：

```cpp
struct Wrap {
    Risky r;
    Wrap() try : r(make_risky()) {   // 函数 try 块：捕获初始化列表的异常
    } catch (const std::exception&) {
        // 注意：构造函数的 catch 结束时**自动重抛**——对象没建成，不能假装成功
        std::cerr << "构造失败\n";
    }
};
```

## 和 C 的区别 / 新手要点

| C | C++ |
|---|---|
| 返回值错误码 + `goto cleanup` | `throw` + RAII 自动清理 |
| `setjmp/longjmp`（不清理局部资源） | 栈展开逐帧调析构 |
| 错误处理散在每个调用点 | 错误沿调用链自动冒泡到能处理的层 |

新手要点：① 别用异常做正常流程控制（查找失败返回 `std::optional` 更合适）；
② 异常的价值在**跨层**——同层内能处理的错误就返回值；③ 热路径不抛异常
（见 HFT 关联），异常是给"出事了"的路径用的。

## HFT 关联

- **tick-to-trade 主路径零异常**：`throw` 的开销在 µs 级（查 LSDA 表 + 逐帧展开），
  且不可预测——主路径用错误码/`expected`，异常只留给启动/配置/重连这类冷路径
- **`noexcept` 是延迟预算的一部分**：标了 noexcept 的移动让 vector 扩容走移动而非拷贝，
  直接影响行情队列扩容时的毛刺
- `dynamic_cast`/异常都依赖 RTTI/展开表——部分 HFT 团队直接 `-fno-exceptions -fno-rtti`
  编译热路径库，错误全靠返回码（代价是失去标准库异常的便利，要想清楚边界）

## 代码自测

**题目 1：** 以下代码的异常安全性如何？如何改进？

```cpp
void f() {
    int* p = new int[100];
    do_work(p);  // 可能抛异常
    delete[] p;
}
```

<details>
<summary>参考答案</summary>

如果 `do_work` 抛异常，`p` 泄漏。改进：用 RAII（智能指针）：

```cpp
void f() {
    auto p = std::make_unique<int[]>(100);
    do_work(p.get());  // 异常时 p 自动析构释放
}
```

C++ 异常安全三个级别：基本保证（不泄漏不损坏）、强保证（操作成功或回滚）、不抛保证（noexcept）。

</details>

**题目 2：** `vector<MyType>` 扩容比预期慢一倍，怀疑在拷贝而不是移动，怎么验证和修？

<details>
<summary>参考答案</summary>

验证：给 `MyType` 的移动构造和拷贝构造各加一行打印，观察扩容时打的是哪个。
修复：把移动构造标 `noexcept`——vector 只有确认移动不会抛才敢用它（本机实测：未标时扩容走拷贝）。
顺带把析构、swap、移动赋值也标上。

</details>

**题目 3：** 下面的 catch 链有什么问题？

```cpp
try { parse(buf); }
catch (const std::exception& e)   { log(e.what()); }
catch (const std::runtime_error& e) { retry(); }
```

<details>
<summary>参考答案</summary>

顺序反了：`runtime_error` 是 `exception` 的派生类，会被第一个 catch 截胡，
第二个永远到不了（g++ 会给 `-Wexception` 警告）。派生类 catch 必须放前面。

</details>
