# 抽象基类与访问控制

## 本节讲什么

本节讲解两个相关但独立的概念：(1) **纯虚函数**和**抽象基类**（abstract base class, ABC）——如何用 `= 0` 定义"接口"，强制派生类实现；(2) **`protected` 访问控制**在继承体系中的作用，以及友元与继承的交互。这是 OOP 中"接口与实现分离"的核心工具。

> **一句话定位**：抽象基类 = "只定义接口，不提供完整实现"——含纯虚函数的类不能实例化，只能作为基类；派生类必须实现所有纯虚函数才能实例化。

## 核心用法

### 1. 纯虚函数

在虚函数声明后加 `= 0`，使其成为**纯虚函数（pure virtual function）**：

```cpp
class Shape {
public:
    virtual double area() const = 0;     // 纯虚函数
    virtual void draw() const = 0;       // 纯虚函数
    virtual ~Shape() = default;          // 即使是抽象类，析构也要虚
};
```

特点：
- 纯虚函数**可以**提供定义（在类外），但通常不提供——它的意义就是"派生类必须自己实现"
- 含纯虚函数的类是**抽象类**，**不能创建对象**：
  ```cpp
  Shape s;          // ❌ 错误：Shape 是抽象类
  Shape *p;         // ✅ 可以定义指针/引用（用于多态）
  ```

**`= 0` 到底是什么——三层实测**（clang 23）：

① **编译期**：抽象类实例化被直接挡下，note 精确点名哪个纯虚函数没实现（派生类漏实现同理，note 跟到基类声明处）：

```
error: variable type 'Shape' is an abstract class
note: unimplemented pure virtual method 'area' in 'Shape'
note: unimplemented pure virtual method 'draw' in 'Shape'
error: variable type 'Circle' is an abstract class      ← 漏实现 draw() 的派生类
note: unimplemented pure virtual method 'draw' in 'Circle'
```

② **符号层**：`= 0` 不是"没有函数"——编译器给 Shape 的 vtable 里 area 槽位填的是 `__cxa_pure_virtual`（`nm` 可见 `U ___cxa_pure_virtual` 引用），一个运行时兜底 abort 函数。

    > **常见误解：槽位不是 0/nullptr**。用 `llvm-objdump -r` 看 vtable 的重定位记录可以眼见为实——`class A { virtual void foo()=0; }` 与实现者 `class B` 各自的 vtable：
    >
    > ```
    > 0000000000000060 ARM64_RELOC_UNSIGNED     ___cxa_pure_virtual   ← A 的 foo 槽位
    > 0000000000000010 ARM64_RELOC_UNSIGNED     __ZN1B3fooEv          ← B 的 foo 槽位（真函数）
    > ```
    >
    > 同一个槽位，抽象类填 `__cxa_pure_virtual`，实现类填真函数地址。MSVC ABI 对应物叫 `_purecall`。**为什么不填 nullptr**：空指针调用只会得到一个无上下文的 segfault，而 stub 函数能打出 `Pure virtual function called!` 再 abort——把"不可能的调用"变成可诊断的死亡。

③ **运行时**：绕过编译期检查的唯一路径是**基类构造/析构期间调虚函数**（此时动态类型还是基类，见 15.2 错误 3），于是真的调到那个槽位：

```cpp
class Shape {
public:
    Shape() { area(); }              // 构造期间动态类型还是 Shape
    virtual double area() const = 0;
    virtual ~Shape() = default;
};
```

```
warning: call to pure virtual member function 'area' has undefined behavior;
         overrides of 'area' in subclasses are not available in the constructor
         of 'Shape' [-Wcall-to-pure-virtual-from-ctor-dtor]    ← 默认就开，不用 -Wall
libc++abi: Pure virtual function called!                        ← 运行时 abort，exit 134
```

三层合起来就是 `= 0` 的完整机制：**编译器用"抽象类"属性挡实例化（主力），vtable 槽位填 abort 函数兜底（万一构造期漏网）**。

### 2. 抽象基类作为"接口"

抽象基类的典型用法是定义**接口契约**——规定派生类必须提供哪些操作：

```cpp
// 接口：定义"可比较"的概念
class Comparable {
public:
    virtual bool less_than(const Comparable &other) const = 0;
    virtual ~Comparable() = default;
};
// 派生类必须实现 less_than 才能实例化
class Number : public Comparable {
public:
    Number(int v) : val_(v) { }
    bool less_than(const Comparable &other) const override {
        const Number &n = dynamic_cast<const Number&>(other);
        return val_ < n.val_;
    }
private:
    int val_;
};
```

> **设计意图**：抽象基类表达"是什么能力"（Comparable、Drawable、Serializable），而非"是什么东西"。这与 Java 的 `interface` 思路一致，但 C++ 的抽象类可以含数据成员和非纯虚函数（更灵活）。

#### 逗号混入接口 = 多重继承（Cherno 28 集实测）

Cherno 的演示：主类已经有了 `Entity` 基类，"想实现接口？加一个逗号就行"——

```cpp
class Printable {                       // 纯接口：只含纯虚函数
public:
    virtual std::string GetClassName() const = 0;
    virtual ~Printable() = default;
};
class Entity : public Printable {       // 不实现 GetClassName → Entity 也是抽象类
public:
    virtual std::string GetName() const { return "Entity"; }
};
class Player : public Entity, Printable {   // ← 加逗号，混入第二个基类
public:
    std::string GetClassName() const override { return "Player"; }
    std::string GetName() const override { return "Player"; }
};
```

这句话成立，但下面三笔底层账和**一个 Cherno 没点破的坑**值得记（全部 clang 23 实测）：

**① 每个直接基类 = 一份带 vptr 的子对象**。`Player` 没有数据成员，`sizeof(Player)` 却是 **16**——两个 vptr：Entity 子对象的（偏移 0）+ 直接 Printable 子对象的（偏移 8）。`&p` 与 `(Entity*)&p` 同地址，多基下只有**主基**在偏移 0。

**② 一个 override 填满两段 vtable，次段走 thunk**。`llvm-objdump -r` 看 Player 的 vtable 重定位：

```
0000000000000010 ARM64_RELOC_UNSIGNED  __ZNK6Player12GetClassNameEv     ← 主段：真函数
0000000000000040 ARM64_RELOC_UNSIGNED  __ZThn8_NK6Player12GetClassNameEv ← 次段：thunk！
```

主段（Entity 子对象那份）填真函数；次段（偏移 8 的 Printable 子对象那份）填的是 `ZThn8_` 前缀的 **non-virtual thunk**——一个跳板：先把 `this` 减 8（从子对象地址修正回完整对象地址），再跳真函数。这是多基虚调用比单继承多的一步，纯虚函数"子类只写一遍，两个接口都满足"就是这样实现的。

**③ 顺手验证抽象传染**：Entity 的 vtable 里 GetClassName 槽还是 `___cxa_pure_virtual`（Entity 没实现 → 仍是抽象类，呼应上文规则）。

**④ 坑：这其实是菱形继承**。`Printable` 经 `Entity` 和直接继承**两条路径**进入 Player——编译器在类声明处就警告：

```
warning: direct base 'Printable' is inaccessible due to ambiguity:
    class Player -> Entity -> Printable
    class Player -> Printable [-Winaccessible-base]     ← 默认就开
```

后果：`Player` 里**有两份独立的 Printable 子对象**，转成接口指针直接报硬错误：

```
error: ambiguous conversion from derived class 'Player' to base class 'Printable'
```

Cherno 的代码能跑通只是因为演示里没做 `Printable* pp = &p;` 这种转换。**正解**：接口只经一条路径引入——要么 `Entity` 实现 `GetClassName`（Player 只继承 Entity），要么用 `virtual` 继承让两条路径共享一份子对象（虚拟继承是 Primer 18.3 的主题）。规则一句话：**逗号混入的接口，必须是对象里全新的、此前从未间接继承过的基类**。

### 3. 派生类必须实现所有纯虚函数

```cpp
class Shape {
public:
    virtual double area() const = 0;
    virtual void draw() const = 0;
    virtual ~Shape() = default;
};
class Circle : public Shape {
public:
    double area() const override { return 3.14 * r * r; }
    // ❌ 没实现 draw()，Circle 仍是抽象类，无法实例化
};
class Square : public Shape {
public:
    double area() const override { return side * side; }
    void draw() const override { /* ... */ }   // ✅ 全部实现，可实例化
};
```

若派生类漏掉一个纯虚函数，派生类自身也变成抽象类——这通常是你忘了实现的信号。

### 4. 纯虚函数的"默认实现"（少用但合法）

纯虚函数可以在类外提供定义，派生类可显式调用（以下代码 clang 23 实测可跑，输出 `default greet` / `derived greet`）：

```cpp
class Base {
public:
    virtual void f() = 0;     // 声明纯虚
};
void Base::f() { std::cout << "default\n"; }   // 类外提供定义
class Derived : public Base {
public:
    void f() override {
        Base::f();            // 显式调用基类的默认实现
        std::cout << "extended\n";
    }
};
```

这种用法较少——通常若想提供默认实现，就直接写成普通虚函数（非纯虚）。纯虚 + 默认实现的语义是"派生类必须显式决定是否用默认实现"，略显啰嗦。

**注意语法限定**：定义只能写在**类外**。想图省事写类内 `virtual void f() = 0 { ... }` 会被拒：

```
error: initializer on function does not look like a pure-specifier
error: expected ';' at end of declaration list
```

（clang 23 实测；`= 0` 后面跟函数体不是合法的成员声明形式，声明和定义必须分离。）

**实现存在 ≠ vtable 用它**（重定位记录眼见为实）：上面的代码里 `__ZN4Base4funcEv`（类外实现）确实被编译出来了（`nm` 可见 `T` 符号），`Son::func` 里的 `Base::func()` 也能静态直呼（`ARM64_RELOC_BRANCH26 __ZN4Base4funcEv`，不走 vtable）——但 **Base 自己 vtable 的 func 槽位仍然指向 `___cxa_pure_virtual`**：

```
0000000000000060 ARM64_RELOC_UNSIGNED   ___cxa_pure_virtual   ← Base 的 func 槽位（有实现也一样！）
00000000000000a4 ARM64_RELOC_BRANCH26   __ZN4Base4funcEv      ← 限定名调用直跳实现
```

机制结论：**`= 0` 一旦写下，槽位就永久绑定 pure_virtual stub，类外实现只是"存在"，只能通过限定名静态调用，永远不参与动态分派**。所以"写了类外实现，Base 还是抽象类"不是规定的武断，而是机制的自然结果——vtable 里没有可用的分派目标。

### 5. protected 访问控制

`protected` 成员：**派生类可访问，外部用户不可访问**——介于 `public` 和 `private` 之间：

```cpp
class Base {
public:
    int pub;          // 谁都能访问
protected:
    int prot;         // 派生类可访问，外部不可
private:
    int priv;         // 只有 Base 自己能访问，派生类也不行
};
class Derived : public Base {
public:
    void f() {
        pub = 1;      // ✅
        prot = 2;     // ✅ 派生类能访问 protected
        priv = 3;     // ❌ 派生类也不能访问 private
    }
};
int main() {
    Base b;
    b.pub = 1;        // ✅
    b.prot = 2;       // ❌ 外部不能访问 protected
    b.priv = 3;       // ❌
}
```

> **设计权衡**：`protected` 数据成员是"对派生类的承诺"——一旦暴露，改起来就要顾及所有派生类。**优先用 `protected` 方法（接口）而非 `protected` 数据**，保留演进自由。C++ 核心指南建议 `protected` 只放函数，数据一律 `private`。

### 6. 友元与继承

友元关系**不能继承**：

```cpp
class Base {
    friend class FriendClass;     // FriendClass 能访问 Base 的所有成员
protected:
    int prot;
};
class Derived : public Base { };
class FriendClass {
public:
    void f(Base &b) { b.prot = 1; }       // ✅ 友元可访问 Base
    void g(Derived &d) { d.prot = 1; }    // ❌ 友元不能访问 Derived 的 Base 部分
};
```

友元关系也不能传递（A 是 B 的友元，B 是 C 的友元，A 不是 C 的友元）。友元是**单向、不可继承、不可传递**的。

### 7. 派生类向基类的转换规则（受继承方式影响）

| 继承方式 | 派生→基类转换 | 派生类成员函数访问基类成员 |
|---------|-------------|----------------------|
| `public` | 用户代码、派生类成员、友元都能转 | 能访问 `public`/`protected` |
| `protected` | 只有派生类成员和友元能转 | 能访问 `public`/`protected`（都变 `protected`） |
| `private` | 只有派生类成员和友元能转 | 能访问 `public`/`protected`（都变 `private`） |

绝大多数情况下用 `public` 继承——后两者的派生→基类转换被限制在派生类内部，外部无法多态使用。

## 和 C 的区别

C 没有"抽象类"和"接口"的概念。要模拟"接口契约"，C 程序员靠**约定 + 函数指针结构体**：

| 维度 | C | C++ |
|------|---|-----|
| 定义接口 | 头文件约定 + 函数指针表 | 纯虚函数 `= 0` |
| 强制派生类实现 | 无（全靠注释约定，漏了运行崩溃） | 编译期强制（漏了无法实例化） |
| 不能实例化的"接口类" | 无（struct 总能定义） | 抽象基类编译期禁止实例化 |
| 访问控制 | 无（全靠 `static` 文件级隐藏） | `public`/`protected`/`private` |
| protected 数据隐藏 | 无（成员全公开或全文件级 static） | `protected` 限定派生类可见 |

### C 模拟"抽象接口"的写法

```c
// C：手动模拟"接口"
struct Shape;   // 不透明指针
struct ShapeOps {
    double (*area)(const struct Shape*);
    void (*draw)(const struct Shape*);
};
struct Shape {
    const struct ShapeOps *ops;   // 必须由派生类型填充
};
// 调用：s->ops->area(s)
// 若某个派生类型忘记实现 area，运行期 ops->area 是 NULL → 崩溃
// C++ 的纯虚函数让这个错误在编译期暴露
```

```cpp
// C++：抽象基类
struct Shape {
    virtual double area() const = 0;   // 派生类必须实现，否则无法实例化
    virtual void draw() const = 0;
    virtual ~Shape() = default;
};
```

C 版本的痛点：**接口契约靠注释**，漏实现是运行期崩溃；C++ 让编译器替你检查。

> **设计哲学**：C++ 的抽象基类让"接口"成为语言级概念——你定义的不只是数据布局，而是"派生类必须遵守的契约"。这是 OOP 相对 C 结构体编程的核心跃迁之一。

## 常见错误

### 错误 1：抽象基类忘记虚析构

```cpp
class Shape {
public:
    virtual double area() const = 0;
    // ❌ 没声明虚析构
};
class Circle : public Shape { /* ... */ };
Shape *p = new Circle;
delete p;   // 行为未定义！可能只调基类析构（如果有），派生部分泄漏
```

**修复**：即使是抽象类，析构也要声明为虚的：
```cpp
virtual ~Shape() = default;
```

### 错误 2：`protected` 暴露数据成员过多

```cpp
class Base {
protected:
    int x, y, z;    // ❌ 全暴露给派生类，未来改不了
    std::vector<int> data;
};
```

一旦派生类直接用了这些成员，基类演进就受牵制。**优先用 `protected` 方法暴露受控接口**：
```cpp
class Base {
public:
    virtual ~Base() = default;
protected:
    int get_x() const { return x; }      // 受控访问
    void set_x(int v) { x = validate(v); } // 可加校验
private:
    int x, y, z;                          // 数据私有
};
```

### 错误 3：派生类漏实现一个纯虚函数 → 仍是抽象类

```cpp
class Iface {
public:
    virtual void f() = 0;
    virtual void g() = 0;
    virtual ~Iface() = default;
};
class Impl : public Iface {
public:
    void f() override { }
    // ❌ 忘了 g()，Impl 仍是抽象类
};
Impl x;   // 编译错误：不能实例化抽象类
```

报错信息通常指向"cannot declare variable of abstract type"——这时去检查是不是漏了某个纯虚函数的实现。

### 错误 4：误以为友元能继承

见上文"友元与继承"。`friend class X` 只授权 `X` 访问当前类，不授权 `X` 的派生类，也不授权当前类的派生类继承这个授权。

## 自测题

**1. 选择题**：以下关于纯虚函数的说法，哪个是**错误**的？

A. 含纯虚函数的类不能创建对象
B. 纯虚函数不能在类外提供定义
C. 派生类必须实现所有纯虚函数才能实例化
D. 纯虚函数声明形式是 `virtual void f() = 0;`

<details>
<summary>答案</summary>

**B** 错误。纯虚函数**可以**在类外提供定义，派生类可通过 `Base::f()` 显式调用。只是通常不这么做——若想提供默认实现，一般直接写成普通虚函数。

</details>

**2. 判断题**：派生类可以访问基类的 `protected` 成员，但不能访问其他派生类对象的 `protected` 成员（即使它们继承自同一个基类）。

<details>
<summary>答案</summary>

**对**（这是个细微但重要的规则）。`protected` 成员只能通过"自己的对象"或"自己的派生类对象"访问，不能通过"兄弟派生类对象"访问：
```cpp
class Base { protected: int prot; };
class D1 : public Base {
public:
    void f(Base &b) { b.prot; }      // ❌ 不能通过 Base 访问
    void g(D1 &d) { d.prot; }        // ✅ 能通过 D1 访问（同类型）
};
```
这条规则防止 `protected` 变成"所有派生类共享的全局变量"。

</details>

**3. 踩坑题**：以下代码有什么问题？

```cpp
class Drawable {
public:
    virtual void draw() const = 0;
};
class Circle : public Drawable {
public:
    void draw() const override { /* 画圆 */ }
};
int main() {
    Drawable *p = new Circle();
    p->draw();
    delete p;
}
```

<details>
<summary>答案</summary>

`Drawable` 没有虚析构函数。`delete p` 时，由于基类析构非虚，行为未定义——通常只销毁 `Drawable` 部分，`Circle` 的析构不调用，若 `Circle` 持有资源就泄漏。

修复：`Drawable` 加 `virtual ~Drawable() = default;`。这是抽象基类的铁律——**即使是抽象类，析构也要声明为虚的**。

</details>

**4. 应用题**：设计一个抽象基类 `Serializer`，定义 `write(int)` 和 `write(const std::string&)` 两个纯虚函数；派生类 `JsonSerializer` 和 `BinarySerializer` 分别实现它们。要求基类安全、派生类可多态使用。

<details>
<summary>答案</summary>

```cpp
#include <string>
#include <iostream>
class Serializer {
public:
    virtual ~Serializer() = default;                      // 虚析构
    virtual void write(int v) = 0;                        // 纯虚
    virtual void write(const std::string &s) = 0;         // 纯虚（重载）
};
class JsonSerializer : public Serializer {
public:
    void write(int v) override { std::cout << v; }        // JSON 数字直接输出
    void write(const std::string &s) override {           // JSON 字符串加引号
        std::cout << '"' << s << '"';
    }
};
class BinarySerializer : public Serializer {
public:
    void write(int v) override {
        std::cout.write(reinterpret_cast<const char*>(&v), sizeof(v));  // 二进制
    }
    void write(const std::string &s) override {
        int len = static_cast<int>(s.size());
        write(len);                                        // 先写长度
        std::cout.write(s.data(), len);                    // 再写内容
    }
};
// 多态使用：
void serialize(Serializer &s) {
    s.write(42);
    s.write("hello");
}
```

要点：基类虚析构、纯虚函数声明、`override` 标注、通过基类引用多态调用、两个派生类各自实现接口。

</details>

真实输出（节选）：

```
行情 mid = 99.00:
  mid=99.00 -> 信号 -1.00 卖
  mid=99.00 -> 信号 +0.01 持有
```

**看出什么了？** 同一个 `dispatch(const Strategy&)`，对 mid=99 一个策略喊卖、一个喊持有——纯虚函数保证"实现接口才有资格实例化"（漏写 override 直接编译失败），实现细节全部藏在派生类里。加第三个策略，dispatch 一行不改。

> 依赖倒置的落地形态。注意 `virtual ~Strategy() = default`——多态基类必须虚析构（13 章的坑在这里补上）。
