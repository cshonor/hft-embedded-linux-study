# 14.1.1 运算符的候选集：成员、非成员与 ADL

[← 14.1 运算符重载](./14.1-运算符重载.md) | [第 14 章](./README.md) | [14.2 函数调用运算符 →](./14.2-函数调用运算符与函数对象.md)

## 本节讲什么

[14.1](./14.1-运算符重载.md) 讲"成员版运算符的左操作数是 `this`"。这一节回答它下游的三个问题：

- `L + R` 发生时，编译器到底会去哪些地方找 `operator+`？
- A、B 两个类各自重载了 `+`，`A + B` 与 `B + A` 分别调谁？
- 成员版和自由版同时存在，会怎样？

第二个问题的常见答案是"左操作数决定一切，B 的重载完全不会被考虑"。**这句话对成员版本成立，对自由函数版本不成立**——这是本节要纠正的核心。

## 术语：自由函数（free function）

**自由函数就是不属于任何类的普通函数**：定义在全局或命名空间作用域，没有隐式 `this`，调用时不绑定任何对象。英文 free function，标准里的正式叫法是 non-member function（非成员函数）。

```cpp
Price operator+(const Price& a, const Price& b) {   // 自由函数：谁都不属于
    return Price{a.ticks + b.ticks};
}

class Price {
public:
    Price operator+(const Price& rhs) const;    // 成员函数：属于 Price，有 this
    static Price zero();                        // 静态成员：没有 this，但仍是成员
    friend Price make_price(long t);            // 友元：自由函数 + 私有访问权
private:
    long ticks;
};

Price make_price(long t) { return Price{t}; }   // 定义在命名空间里，仍是自由函数
```

四个概念的分界：

| | 有 `this` | 名字在谁的作用域 | 能访问 private | 参与 ADL |
|---|---|---|---|---|
| 成员函数 | 有 | 类作用域（`obj.f()`） | 能 | 不参与 |
| 静态成员函数 | **没有** | 类作用域（`Price::zero()`） | 能 | 不参与 |
| 自由函数 | 没有 | 命名空间作用域（`f(a, b)`） | 不能，除非是 friend | 参与 |
| 友元函数 | 没有 | 命名空间作用域 | **能** | 参与 |

两处最容易混：

- **静态成员函数没有 `this`，但它不是自由函数。** 名字仍在类里，`Price::zero()` 才找得到；类外直接写 `zero()` 不可见（除非有 `using` 声明）。
- **友元不是"第五种函数"**，它本质就是自由函数，`friend` 只额外授予"可以访问私有成员"的权限。所以第三节那句"B 的友元会被 ADL 找到"成立——友元在名字查找上属于命名空间作用域。

从 C 看过来这件事更简单：**C 里所有函数都是自由函数**，因为没有成员函数这回事。

```c
struct price { long ticks; };
struct price price_add(struct price a, struct price b);   /* 自由函数 */
```

C++ 新增的是"成员函数"，"自由函数"这个词只是为了和它区分。对 C 程序员来说，自由函数就是原来写的那种函数，唯一的新知识是它现在参与 ADL。

运算符为什么偏爱自由函数（`cout << obj` 的左边不是本类、`10 + price` 够不着成员版、两侧都能隐式转换），见第五节。

## 一、先看四个表达式的结果

```cpp
struct A { int v; A operator+(const B&) const; };   // A 的成员
struct B { int v; B operator+(const A&) const; };   // B 的成员

struct C { int v; explicit C(int x) : v(x) {} };
C operator+(int lhs, const C& rhs);                // 自由函数：支持 int 在左边
```

```cpp
a + b;      // A{} + B{}
b + a;      // B{} + A{}
10 + c;     // int + C
```

实测（gcc 13.2，`-std=c++17 -O0`）：

```text
A::operator+(B)
B::operator+(A)
free operator+(int, C)
```

三行的去向各不相同：

| 表达式 | 选中 | 为什么 |
|---|---|---|
| `a + b` | `A::operator+(const B&)` | 左操作数是 `A`，成员候选只在 `A` 里找 |
| `b + a` | `B::operator+(const A&)` | 左操作数换成 `B`，成员候选换成 `B` 的 |
| `10 + c` | 自由函数 `operator+(int, C)` | 成员版要求左操作数是 `C`，`int` 够不着 |

前两行支持"成员版左边固定是调用者"这条结论。第三行说明成员版的硬伤：**左操作数不能是别的类型，哪怕它能隐式转换成自己**（`C(int)` 还是 `explicit` 的，本来就不许隐式转换）。

## 二、候选集是怎么来的

`L @ R` 的运算符重载决议分三步取候选（标准里是 [over.match.oper]）：

| 来源 | 内容 | 谁进候选 |
|---|---|---|
| 成员候选 | 在**左操作数类型**（含基类）里限定查找 `operator@` | 只有 `L` 的成员 |
| 非成员候选 | 非限定查找 + **ADL**（实参关联命名空间/类） | 名字空间里的自由函数、以及通过 ADL 找到的友元 |
| 内置候选 | 语言内建的运算符形式 | 基本类型运算 |

拿到候选集之后，才进入 [6.6](../ch06-functions/6.6-函数匹配（重载决议）.md) 讲的那套"可行集 → 最佳匹配 → 二义性"流程。

关键在第二行：**非成员候选是按实参做 ADL 找的，两个操作数的关联命名空间都会被查**。所以：

- `B` 的**成员** `operator+`：只有 `B` 在左边时才成为候选，因为它属于"成员候选"这一类，而成员候选只从左操作数取。
- `B` 里定义的**友元自由函数**：`A + B` 时会被 ADL 拉进候选集，因为 `B` 是实参。

原解释漏掉的就是后半句。成员和友元是两种东西，不能一起判。

## 三、反例：B 里的 friend 在 `A + B` 里确实进入候选

```cpp
struct B;

struct A {
    int v;
    A operator+(const B&) const;          // A 的成员
};

struct B {
    int v;
    friend A operator+(const A&, const B&) {   // 写在 B 里，B 在右边
        return A{0};
    }
};
```

`a + b` 编译（`-std=c++17 -pedantic-errors`）：

```text
error: ambiguous overload for 'operator+' (operand types are 'A' and 'B')
note: candidate: 'A A::operator+(const B&) const'
note: candidate: 'A operator+(const A&, const B&)'
```

报的是**二义性**，不是"找不到"。两个都进了候选集，且都是精确匹配，谁也无法胜出。这正好证明 B 的友元确实被 ADL 找到了——如果它不在候选集里，这里会安静地调 `A::operator+`。

## 四、成员 + 自由同时存在：标准说二义，gcc 默认只警告

用户那组 Quiz 就是这种形态：

```cpp
struct X {
    X operator+(const X&) const { return *this; }   // 成员
};
X operator+(const X& a, const X&) { return a; }     // 自由
```

`a + b` 的结果分三层看：

| 层面 | 行为 |
|---|---|
| 标准 | **二义性，ill-formed** |
| gcc 13.2 默认（`-Wall -Wextra`） | **只警告**，并挑自由函数执行 |
| gcc 13.2 `-pedantic-errors` | `error: ambiguous overload`，编译失败 |

默认档的警告原文：

```text
warning: ISO C++ says that these are ambiguous, even though the worst conversion
for the first is better than the worst conversion for the second:
note: candidate 1: 'X operator+(const X&, const X&)'
note: candidate 2: 'X X::operator+(const X&) const'
```

程序实际输出 `free +`——gcc 按自己的偏好选了非成员版本。

这条差异的工程含义很直接：**同一份代码在 gcc 下只是警告、在新版 clang 下可能是错误**。写库时不要同时提供成员版和自由版，也不要依赖"gcc 能过"来判定正确性。

> 注意报错里那句 `the worst conversion for the first is better`：gcc 认为非成员版的隐式对象参数不存在，所以它的"最差转换"更好。这是 gcc 的判定路径，**不是标准规则**；标准在这里没有"成员劣于非成员"的条款，因此结论就是二义。

## 五、成员版与自由版的取舍

| 维度 | 成员版 | 自由版（含友元） |
|---|---|---|
| 左操作数 | 必须是本类对象 | 任意，参数表自己定 |
| 左操作数隐式转换 | **不参与**（不会把 `10` 转成 `C` 再调 `C::operator+`） | 参与，两侧对称 |
| 访问私有成员 | 天然可以 | 需要 `friend` 或用公开接口 |
| 典型用途 | `= += -= [] () -> ++ --` | `+ - * / == < << >>` |
| 二义风险 | 只提供一种时无 | 与成员同时提供时二义 |

`10 + price` 这类"内置类型在左边"的写法，只有自由版能支持：

```cpp
Price operator+(int ticks, const Price& p);   // 10 + p 可行
Price operator+(const Price& p, int ticks);   // p + 10 可行
```

反之，`operator+=` 必须改自身，天然是成员，这一点和 `operator+` 的分工正好构成"成员负责就地改、自由负责产出新值"的惯用法（[14.1](./14.1-运算符重载.md) 的可跑例子里就是 `lhs += rhs` 复用实现）。

## 六、hidden friend：只通过 ADL 可见的写法

```cpp
class Price {
public:
    friend Price operator+(const Price& a, const Price& b) {   // 类内定义
        return Price{a.ticks + b.ticks};
    }
private:
    long ticks;
};
```

类内定义的友元有一个特殊性质：**它不进普通的名字查找，只能通过 ADL 找到**。好处是：

- 不会污染所在命名空间的候选集，减少意外匹配；
- 只在实参涉及 `Price` 时出现，`1 + 2` 之类的内置运算不受影响；
- 仍然能访问私有成员。

代价是它"隐身"：在类外直接写 `operator+(a, b)` 调用是找不到的（除非另外在命名空间作用域声明一次），只能靠运算符语法或 ADL 触发。

这与"在命名空间里写一个普通自由函数"不同：后者在非限定查找阶段就被看见，任何一次 `operator+` 决议都会把它拉进候选。

## 和 C 的区别

C 没有运算符重载，也就没有"候选集从哪来"这个问题：

```c
struct Price { long ticks; };
struct Price price_add(struct Price a, struct Price b);

struct Price c = price_add(a, b);   /* 名字唯一，没有二义 */
```

| 维度 | C | C++ |
|---|---|---|
| 运算符语义 | 语言固定 | 可按类型重定义 |
| 名字解析 | 单一函数名 | 成员候选 + 非成员候选 + ADL |
| 二义性 | 不存在 | 每个运算符表达式都可能二义 |
| 交换律写法 | 无（只能写函数） | 自由版可让 `int + T` 与 `T + int` 都成立 |

C 的"没有二义"是名字唯一换来的；C++ 的灵活性用候选集复杂度买单，代价集中在诊断信息上——遇到运算符报错，第一件事是看清候选来自哪一侧。

## HFT / 嵌入式关联

1. **运算符决议全在编译期**，两种写法生成的调用都是直接 `call`（内联后无差别）。选成员还是自由，不影响运行期开销。

2. **价格类型用自由版**：`Price + int`、`int + Price`、`Price - Price` 三种组合都要支持，成员版只能覆盖"自己在前"的一种。行情/订单簿代码里 `bid + spread` 这类混算很常见。

3. **不要在同一个类上同时提供成员版和自由版**。gcc 只警告的行为会掩盖问题，换编译器（clang / MSVC）或升级标准档位就可能变成错误；库接口尤其不能赌。

4. **hidden friend 适合库的头文件**：它把重载集限制在"实参涉及本类型"时才出现，避免用户代码里同名自由函数被意外拉进候选，减少诊断噪音。

## 常见错误

**1. 以为 `A + B` 只看 A 的重载**

成员候选确实只看左操作数，但非成员候选按 ADL 查两侧实参。B 里定义的友元 `operator+(const A&, const B&)` 会进入候选，并可能与 A 的成员构成二义。

**2. 成员版想让左操作数隐式转换**

```cpp
struct C { C(int); C operator+(const C&) const; };
10 + c;      // 仍然不可行
```

成员候选的隐式对象参数不做用户定义转换，`10` 不会被转成 `C` 再去调 `C::operator+`。要支持就写自由函数。

**3. 同时提供成员版和自由版**

标准判二义（ill-formed）。gcc 默认只警告并选自由版，clang 直接报错——跨编译器行为不一致，属于必须消除的设计。

**4. 把 `operator<<` 写成成员**

`cout << obj` 的左操作数是 `ostream`。写成成员会变成 `obj.operator<<(cout)`，语义反了。详见 [14.4](./14.4-输入输出运算符.md)。

## 代码自测

**1（判定）** 下面这行调哪个？会编译报错吗？

```cpp
struct X {
    X operator+(const X&) const { return *this; }
};
X operator+(const X& a, const X&) { return a; }
X a, b;
a + b;
```

**2（候选集）** `struct A { A operator+(const B&) const; };` 且 `B` 里定义了友元 `friend A operator+(const A&, const B&);`，`a + b` 会怎样？

**3（隐式转换）** 为什么 `10 + price` 用成员版做不到，用自由函数可以？

**4（hidden friend）** 类内定义的友元运算符，与命名空间里的普通自由函数，在查找到方式上有什么区别？

<details>
<summary>参考答案</summary>

1. 按标准是二义性（ill-formed）。实测 gcc 13.2 默认只给 `warning: ISO C++ says that these are ambiguous...` 并执行自由版（输出 `free +`）；加 `-pedantic-errors` 变成 `error: ambiguous overload for 'operator+'`。不要依赖默认档的宽容。

2. 两个候选都进候选集：`A::operator+(const B&)` 来自成员候选，`B` 里的友元来自 ADL。二者都是精确匹配，构成二义性（`-pedantic-errors` 下报 `ambiguous overload`，且两个候选都被列出）。这说明"右操作数所在的类里的友元"并非不可见。

3. 成员候选的隐式对象参数来自左操作数，且不参与用户定义转换——`10` 是 `int`，不会先转成 `Price` 再去调 `Price::operator+`。自由函数的第一形参可以直接写 `int`，所以天然支持。

4. 类内定义的友元**不进普通名字查找**，只能通过 ADL（实参涉及该类时）被找到；命名空间里的普通自由函数在非限定查找阶段就可见，任何同名运算符表达式都可能把它拉进候选集。

</details>
