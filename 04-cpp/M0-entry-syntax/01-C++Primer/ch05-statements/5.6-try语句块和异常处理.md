# 5.6 try 语句块和异常处理

## 本节讲什么

C++ 的异常机制：`throw` 抛出异常、`try/catch` 捕获处理、`<stdexcept>` 标准异常类层次。这是 **C 语言完全没有**的特性，是 C 转 C++ 的重要新增。

## 核心用法

### 三件套

```cpp
#include <stdexcept>

// 1. throw：抛出异常
double divide(double a, double b) {
    if (b == 0)
        throw std::runtime_error("division by zero");
    return a / b;
}

// 2. try / 3. catch：捕获并处理
int main() {
    try {
        std::cout << divide(10, 0);
    } catch (const std::runtime_error& e) {
        std::cerr << "Error: " << e.what() << std::endl;
    }
}
```

### 标准异常层次（`<stdexcept>`）

```
std::exception                    // 所有标准异常的基类（<exception>）
├── std::logic_error              // 程序逻辑错误，可在编译期发现
│   ├── std::invalid_argument     // 无效参数
│   ├── std::domain_error         // 域错误
│   ├── std::length_error         // 超出最大长度
│   └── std::out_of_range         // 下标越界（vector::at 等）
└── std::runtime_error            // 运行时错误，运行期才能发现
    ├── std::overflow_error       // 上溢
    ├── std::underflow_error      // 下溢
    └── std::range_error          // 范围错误
```

### 异常与栈展开

`throw` 后，程序沿调用栈**逐层退出**（stack unwinding），直到找到匹配的 `catch`。沿途所有局部对象会**按构造的逆序析构**（这是 RAII 能工作的基础）。如果一直没匹配的 catch，调用 `std::terminate` 终止程序。

## 和 C 的区别

| 维度 | C | C++ |
|------|---|-----|
| 异常机制 | ❌ 完全没有 | ✅ `throw`/`try`/`catch` |
| 错误处理方式 | 返回错误码 + `errno` | 返回码 / 异常（二选一） |
| 跨函数跳转 | `setjmp`/`longjmp`（不调用析构，危险） | 异常栈展开（自动析构，安全） |
| 资源清理 | 手动 `goto cleanup` | RAII 析构自动清理 |
| 资源泄漏风险 | 高（忘了清理就泄漏） | 低（析构保证执行） |

**C 程序员的核心认知转变**：

1. C 靠"检查每个函数返回值"防错，容易漏检；C++ 异常让错误"自动冒泡"，不用每层都查返回值。
2. C 的 `setjmp/longjmp` 跳转**不会调用析构函数**（C 没有析构），但 C++ 绝不能用 `longjmp` 跨越有析构的对象——会跳过析构导致泄漏/不变式破坏。**C++ 中只用异常，不用 longjmp。**
3. 异常的代价：抛异常时有运行时开销（栈展开），但**不抛时几乎零开销**（现代 C++ 实现）。HFT 热路径通常禁用异常（`-fno-exceptions`）。

```c
/* C 风格：每层都要检查返回值 */
int rc = f1();
if (rc) { cleanup1(); return rc; }
rc = f2();
if (rc) { cleanup2(); cleanup1(); return rc; }
```
```cpp
// C++ 异常风格：错误自动冒泡，RAII 自动清理
void work() {
    Resource r1 = acquire1();      // RAII，析构自动释放
    Resource r2 = acquire2();      // 抛异常时 r2 先析构，再 r1
    do_something();                // 失败则 throw，r2、r1 自动释放
}   // 正常退出也自动释放
```

## 底层实现与实测

> 以下均为本机实测（Apple clang 23.1.0，arm64，`-std=c++17 -O2`，libc++）。异常的成本要分三笔账算：**写 try 的成本（≈0）/ 抛出的成本（很贵）/ 二进制与可移植性成本**。

### 实测 1：不抛异常时，`try/catch` 真的是零成本

100 万次调用，被调函数 `noinline` 且从不抛出：

| 写法 | 实测（100 万次） |
|---|---|
| 带 `try { s += work(i); } catch (...) {}` | **2844.0 μs** |
| 不带 try（直接 `s += work(i);`） | **2843.8 μs** |

差 0.2 μs / 100 万次 = **0.0002 ns/次**，在噪声里。这就是所谓 **zero-cost exception handling**：正常路径上不执行任何指令，编译器改用一张离线的表（landing pad + 类型信息）来记录"哪里能捕获什么"，只在真正抛出时才去查表。

> 反面：代价转移到了**二进制体积**和**抛出路径**。表中信息常驻 `.rodata`/`.eh_frame`，所以"零成本"是零**时间**成本，不是零**空间**成本。

### 实测 2：抛一次异常 ≈ 4 μs，比错误码慢三个数量级

| 路径 | 实测（10 万次） | 单次 |
|---|---|---|
| `throw std::runtime_error("x")` + `catch` | 423 310 μs | **≈ 4.23 μs** |
| 返回错误码 `int& ec` | 93.7 μs | **≈ 0.94 ns** |

**约 4500 倍。** 4 μs 够做什么？在 3 GHz 上是 12 000 个周期；一笔订单从收包到回包的预算常常只有几微秒——**在热路径上抛一次异常，等于把延迟预算整个吃掉**。

原因：抛出要走 `__cxa_throw` → 查表找 landing pad → 逐帧析构 → `malloc` 异常对象（libc++ 有应急缓冲但仍要走分配路径）→ `__cxa_begin_catch`。这些都是不可内联、不可预测的调用。

### 实测 3：栈展开按构造逆序析构（RAII 的地基）

```cpp
void inner() { Probe a("inner-a"); Probe b("inner-b"); throw std::runtime_error("boom"); }
```

实测输出：

```
+ 构造 inner-a
+ 构造 inner-b
- 析构 inner-b（栈展开调用）
- 析构 inner-a（栈展开调用）
catch: boom
```

逆序析构正是 `lock_guard` / `unique_ptr` 能在异常下正确工作的原因。C 的 `longjmp` **不保证**这件事（它直接跳走，不跑任何清理），所以在 C++ 里跨越对象用 `longjmp` 是 UB。

### 实测 4：`noexcept` 函数里抛出 → `std::terminate`（不是"捕获不到"那么温和）

```cpp
auto f = []() noexcept { throw std::runtime_error("in noexcept"); };
```

```console
warning: 'operator()' has a non-throwing exception specification but can still throw [-Wexceptions]
libc++abi: terminating due to uncaught exception of type std::runtime_error: in noexcept
exit=134        ← 128 + SIGABRT(6)
```

编译器会在**编译期**警告，运行期直接 `abort`。所以 `noexcept` 是契约不是装饰：标了就得保证不抛（析构函数、swap、move 构造都该标）。

### 实测 5：`-fno-exceptions` 下异常代码根本编译不过

```console
error: cannot use 'throw' with exceptions disabled
error: cannot use 'try' with exceptions disabled
```

嵌入式/低延迟项目常用这个开关（连同 `-fno-rtti`）。此时代码要整体改成错误码风格（`std::error_code` / `expected<T,E>` / 返回 `bool`），STL 容器也会退化（`vector::at` 不可用或行为不同）。**选型要在项目初期定，后期切换成本极高。**

## HFT / 嵌入式视角

- **热路径禁异常，冷路径可以用**：启动/配置加载/策略初始化用异常很舒服（错误自动冒泡、信息完整）；撮合主循环、行情解析这类纳秒预算的地方一律错误码。实测 2 的 4 μs 就是分界线。
- **异常不能跨线程、不能跨回调**：抛到 C 回调（如 `qsort` 比较器、libcurl 回调）外面基本是 terminate；跨 shared library 边界抛异常还要求 ABI 一致。
- **`-fno-exceptions` 是嵌入式常态**：Flash/RAM 紧、无 RTTI、启动时间敏感。替代方案是错误码 + `[[nodiscard]]`（强制调用方检查返回值，避免"漏检"这个 C 风格的最大弱点）。
- **`noexcept` 不只是文档**：它让编译器省掉展开表、让 `vector` 扩容敢用移动构造（移动构造函数标 `noexcept` 才有意义，见 [9.2 底层机制](../ch09-sequential-containers/9.2-底层机制.md)）。
- **别用异常做控制流**（实测 2 是硬证据）："用 throw 跳出三层循环"比 goto 慢三个数量级。

## 常见错误

1. **`catch` 按值捕获大对象 / 漏写 `&`**：`catch (std::exception e)` 会拷贝切掉派生类型（slicing），丢失 `what()` 的真实信息。**修正**：用 `catch (const std::exception& e)` 引用捕获。
2. **异常析构时再抛异常导致 `terminate`**：析构函数里抛异常（栈展开过程中）会直接调用 `std::terminate` 终止程序。**修正**：析构函数必须 `noexcept`，内部异常要 `try/catch` 吞掉。
3. **用异常做正常控制流**：拿 `throw` 当 `goto` 用，性能差且语义混乱。异常只用于"真正的错误"，正常分支用返回值/`optional`。实测代价约 **4 μs/次**（比错误码慢约 4500 倍），在热路径上是灾难。
4. **标了 `noexcept` 却可能抛**：编译期只有警告（`-Wexceptions`），运行期直接 `std::terminate`（实测 `exit=134`）。`noexcept` 是契约——要么保证不抛，要么别标；析构函数、移动构造、`swap` 都应标 `noexcept` 并真的不抛。
5. **以为 `try/catch` 本身很贵**：实测 100 万次调用，带 try 2844.0 μs vs 不带 2843.8 μs——**零成本**。贵的是"抛出"（4 μs）和二进制体积，不是"写 try"。所以别因为怕开销而放弃异常，该判断的是**抛出频率**。

## 自测题

**1. 选择题**：下面 `catch` 块能捕获 `throw std::out_of_range("x")` 吗？
```cpp
try { /* throw std::out_of_range("x"); */ }
catch (const std::runtime_error& e) { ... }
```
- A) 能，`out_of_range` 是 `runtime_error` 的派生
- B) 不能，类型不匹配
- C) 能，但有 slicing
- D) 程序终止

<details><summary>答案</summary>

**B) 不能，类型不匹配**（本笔记早期版本误答成 A，已按实测改正）。

`std::out_of_range` 继承自 **`std::logic_error`**，不是 `runtime_error`（见上面的异常层次图）。实测：

```
typeid(out_of_range).name() = St12out_of_range
能否 dynamic_cast 到 logic_error   : 是
能否 dynamic_cast 到 runtime_error : 否
```

而且后果比"没捕获"更严重——没有任何 catch 匹配时会 `std::terminate`：

```console
libc++abi: terminating due to uncaught exception of type std::out_of_range: x
exit=134
```

**正确写法**：`catch (const std::logic_error&)` 或直接 `catch (const std::exception&)`（兜底捕获所有标准异常）。基类引用捕获派生类异常这条规则本身没错（用 `const&` 也不 slicing），但**基类必须真的是基类**。

</details>

**2. 判断题**：C++ 中可以用 `setjmp/longjmp` 替代异常，效果一样。

<details><summary>答案</summary>

错误。`longjmp` 跳转时**不会调用栈上对象的析构函数**，会破坏 RAII 保证，导致资源泄漏或不变式破坏。C++ 中处理错误必须用 `throw/catch`，绝不能用 `longjmp` 跨越有析构的对象。

</details>

**3. 踩坑题**：下面代码在某些情况下会崩溃，为什么？
```cpp
class Conn {
    ~Conn() {
        close(handle_);        // close 可能抛异常
        log("closed");
    }
};
void f() {
    Conn c;
    throw std::runtime_error("err");   // 栈展开，析构 c
}
```

<details><summary>答案</summary>

如果 `close(handle_)` 抛异常，而此时正处于异常栈展开过程（`f` 抛出异常正在展开），析构函数里再抛异常会导致 `std::terminate` 直接终止程序。**修正**：析构函数必须 `noexcept`，内部用 `try/catch` 吞掉 `close` 的异常：
```cpp
~Conn() noexcept {
    try { close(handle_); } catch (...) { /* 吞掉 */ }
    log("closed");
}
```

</details>

**4. 应用题**：写一个安全的数组访问函数 `at(arr, i)`，越界时抛 `std::out_of_range`，正常时返回元素引用。说明与 C 风格"返回错误码"的对比。

<details><summary>答案</summary>

```cpp
int& at(std::vector<int>& v, size_t i) {
    if (i >= v.size())
        throw std::out_of_range("index " + std::to_string(i)
                                + " >= size " + std::to_string(v.size()));
    return v[i];
}
```
C 风格要返回错误码，但函数又想返回元素——只能用输出参数 `int* out` + 返回 int 错误码，调用啰嗦且容易漏检。异常版本调用者写正常路径，错误统一在 `catch` 处理，代码更清晰。HFT 热路径禁异常时，退回 `v[i]`（不检查）或自定义 `expected<T,E>` 类型。

</details>

**5. 判断题**：下面两句对不对？
> (a) `try/catch` 块本身有可观的运行时开销，所以热路径不能写 try。
> (b) 标了 `noexcept` 的函数如果抛异常，异常会继续往外冒泡，跟没标一样。

<details><summary>答案</summary>

**两句都错。**

(a) 实测：100 万次调用，带 `try/catch` 2844.0 μs vs 不带 2843.8 μs，**差 0.0002 ns/次**（零成本异常处理）。贵的是"抛出"——约 4.23 μs/次，比错误码的 0.94 ns 慢约 4500 倍。所以判断标准是**抛出频率**，不是有没有写 try。

(b) 标了 `noexcept` 后抛出会直接 `std::terminate`，进程 abort：

```console
libc++abi: terminating due to uncaught exception of type std::runtime_error: in noexcept
exit=134
```

而且编译期会先给警告：`'operator()' has a non-throwing exception specification but can still throw [-Wexceptions]`。

</details>

**6. 应用题**：你的行情解析函数每秒要处理 50 万条消息，其中约 0.1% 是坏包（字段缺失）。用异常还是错误码？给出理由和大致数字。

<details><summary>答案</summary>

**用错误码（或 `expected<T,E>`）**，不要用异常。

算一笔账：50 万条/秒 × 0.1% = **500 次坏包/秒**。
- 异常方案：500 × 4.23 μs ≈ **2.1 ms/秒** 花在栈展开上；更要命的是**抖动**——一旦坏包连续到达，单次解析延迟从几百纳秒跳到 4 μs，P99/P999 延迟直接爆掉，这在撮合系统里比吞吐损失更致命。
- 错误码方案：500 × 0.94 ns ≈ 0.5 μs/秒，且**延迟恒定**，不会因为坏包而抖动。

**实践建议**：
1. 热路径（解析、撮合、风控判定）：错误码 + `[[nodiscard]]`，强制调用方检查；
2. 冷路径（启动配置、策略加载、文件 IO）：用异常，代码清晰、错误信息完整；
3. 边界处做转换：冷路径的异常在模块边界 catch 掉，转成热路径的错误码；
4. 如果整个项目定了 `-fno-exceptions`，就统一用错误码/`expected`，别混用。

一句话：**异常的成本不在频率，在"一旦发生就是 4 μs 的延迟尖刺"**——对延迟敏感的系统，尖刺比平均值可怕得多。

</details>
