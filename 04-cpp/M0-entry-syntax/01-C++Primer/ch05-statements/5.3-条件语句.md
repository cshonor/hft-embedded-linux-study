# 5.3 条件语句

## 本节讲什么

`if` 与 `switch` 两种条件分支语句。重点讲 `if-else` 嵌套时的**悬垂 else** 问题、`switch` 的 `case` 标签与 `break` 穿透、以及 `switch` 内部定义变量的限制。

## 核心用法

### if 语句

```cpp
if (条件) 语句
if (条件) 语句1 else 语句2
```

`else` 总是与**最近的未配对的 `if`** 匹配，这就是悬垂 else 问题：

```cpp
if (a > 0)              // 外层 if
    if (b > 0)          // 内层 if
        do_x();
else                    // 这个 else 属于内层 if，不是外层！
    do_y();
```

### switch 语句

```cpp
switch (整型表达式) {
    case 常量1: 语句; break;
    case 常量2: 语句;  // 没有 break → 穿透到下一个 case
    default:    语句;
}
```

- `case` 标签必须是**整型常量表达式**
- 忘了 `break` 会导致**穿透**（fall-through），有时是故意的，但必须显式注释
- `switch` 内部如果要在某个 `case` 下定义变量，必须用 `{}` 把该 `case` 包成块

## 和 C 的区别

| 维度 | C | C++ |
|------|---|-----|
| `if`/`switch` 语法 | 完全一致 | 完全一致 |
| `case` 标签类型 | C89 起支持整型常量表达式 | 同 C，但 C++ 要求更严格的常量表达式（`const int` 可作标签，C 中 `const int` 不是真常量） |
| `switch` 内变量定义 | C 允许跨 case 标签的自动变量（但容易 UB） | C++ **禁止**跨越 case 标签初始化变量，必须用 `{}` 块包住 |
| `case` 标签用 `const` 变量 | ❌ C 中 `const int n=1;` 不是常量表达式，不能作 case 标签 | ✅ C++ 中可以（前提是初始化为常量） |

**关键差异**：C 的 `const` 变量本质是"只读变量"而非"常量"，所以 C 中 `const int n = 1; ... case n:` 是非法的；而 C++ 的 `const int` 如果用常量初始化，就是真正的编译期常量，可作 `case` 标签和数组维度。

```c
/* C：编译错误！const 不是常量表达式 */
const int N = 3;
switch (x) { case N: ...; }   // 错误：N 不是常量表达式
```
```cpp
// C++：合法，N 是编译期常量
const int N = 3;
switch (x) { case N: ...; }   // OK
```

## 底层实现与实测

> 以下均为本机实测（Apple clang 23.1.0，arm64，`-std=c++17 -O2`）。条件语句的性能问题，九成不在语法，在**分支能不能被预测 / 能不能被消掉**。

### 实测 1：紧凑 `switch` 会变成查表，稀疏 `switch` 退化成 if-else 链

```cpp
int dense(int k) {   // case 0..5，返回值刻意不连续，逼编译器不能"算术化"
    switch (k) {
        case 0: return 100; case 1: return -7; case 2: return 42;
        case 3: return 3;   case 4: return 999; case 5: return 8;
        default: return -1;
    }
}
```

```asm
dense(int):
    cmp   w0, #5
    b.hi  LBB0_2                          ; 越界 → default
    adrp  x8, l_switch.table._Z5densei@PAGE
    add   x8, x8, l_switch.table._Z5densei@PAGEOFF
    ldr   w0, [x8, w0, uxtw #2]           ; 一次间接取数，O(1)
    ret
LBB0_2:
    mov   w0, #-1
    ret
```

而 case 值跨度很大时（1 / 1000 / 100000 / 10000000），编译器不做表，变成一串 `cmp + b.eq`（实测汇编里是 `cmp w0, #1; b.eq` / `cmp w0, #1000; b.ne` ……），退化成 if-else 链。

> 补充：如果 case 的返回值本身连续（10/11/12/13/14/15），clang 连表都不用，直接算：`add w8, w0, #10; cmp w0, #6; csinv`——**一次跳转都没有**。所以"switch 一定生成跳转表"是错的，要看数据形态。

### 实测 2：`if-else` 和三元运算符生成**完全相同**的代码

```cpp
int maxif (int a, int b) { if (a > b) return a; return b; }
int maxtri(int a, int b) { return a > b ? a : b; }
```

```asm
maxif(int, int):            maxtri(int, int):
    cmp  w0, w1                 cmp  w0, w1
    csel w0, w0, w1, gt         csel w0, w0, w1, gt     ← 一模一样
    ret                         ret
```

两者都被编译成 `csel`（条件选择），**没有跳转指令**。结论：小分支上纠结 `if` 还是 `?:` 毫无意义，编译器会挑等价的无分支形式。

### 实测 3：分支预测到底值多少钱（校准一个流传很广的说法）

经典说法是「排序后比随机快 3~6 倍」。本机实测（`examples/5.3-1`，100 万个 `int` × 5 轮，`if (x >= 128)` 二选一）：

| 数据 | 实测（-O2） | 实测（-O1） |
|---|---|---|
| 随机数据 | 1.73 ms/轮 | 2.96 ms/轮 |
| 已排序数据 | 1.60 ms/轮 | 2.47 ms/轮 |
| 差距 | **1.08 倍** | **1.20 倍** |

**只有 1.1~1.2 倍，不是 3~6 倍。** 两个原因：
1. 现代分支预测器（TAGE 类）对"50% 随机"也不至于崩盘；
2. **clang 会做 if-conversion**：分支体足够简单时直接变成 `csel`/SIMD 选择，压根没有分支可预测。

这不代表分支预测不重要——**分支体越重、越无法被无分支化，差距越大**；而且一次预测失败在深流水线上是 15~20 个周期。但对"简单二选一"这种形态，编译器已经替你消掉大半。

### 实测 4：跨 case 初始化变量，编译器直接拒绝

```console
error: cannot jump from switch statement to this case label
```

加了 `{}` 把变量锁在这一支里就好了——`case 1: { int v = 10; ...; break; }`。

### 实测 5：两个能救命的警告

```console
warning: unannotated fall-through between switch labels [-Wimplicit-fallthrough]
note: insert '[[fallthrough]];' to silence this warning

warning: add explicit braces to avoid dangling else [-Wdangling-else]

warning: enumeration value 'Blue' not handled in switch [-Wswitch]     ← enum class 漏 case
```

C++17 起用 `[[fallthrough]];` 显式声明"故意穿透"，比写 `// fall through` 注释更可靠（注释骗得过人骗不过编译器）。

## HFT / 嵌入式视角

- **`switch` 稠密时是 O(1) 查表**（实测 1），稀疏时是 if-else 链——消息类型分发（订单/成交/撤单）用连续枚举值，编译器就能生成跳转表；枚举值乱跳（1/1000/100000）反而更慢。
- **热路径上优先"把分支挪出去"**，而不是"把分支写快"：预计算档位表、用算术/掩码替代判断（`s += (x >= 128) * x` 这类）、或者按数据分桶后批量处理（排序过的批处理更快，实测 3）。
- **别手搓 branchless 来"优化"**：实测 2 说明编译器已经会做 if-conversion。手写位运算技巧常常只是让代码更难读，性能零收益，还可能挡掉编译器更好的优化。
- **真要提示分支倾向**用 `[[likely]]` / `[[unlikely]]`（C++20）或 `__builtin_expect`，但先测——实测 3 说明这类微优化的收益往往在噪声里。
- **嵌入式**：`switch` 查表会占 `.rodata`（Flash），if-else 链占 `.text`；Flash 紧张或指令 cache 小的 MCU 上，稠密 switch 的表可能反而吃亏（一次 Flash 取数 vs 几条指令），要看具体芯片。

## 常见错误

1. **悬垂 else 误配对**：`if (a) if (b) f(); else g();` 里的 `else` 属于内层 `if`，导致逻辑与预期不符。**解决**：用花括号明确归属：`if (a) { if (b) f(); } else g();`。
2. **忘写 `break` 导致意外穿透**：`case 1: do_a(); case 2: do_b();` 中 case 1 会顺带执行 `do_b()`。即使故意穿透，也要加 `// fall through` 注释，否则 `-Wimplicit-fallthrough` 会警告。
3. **`switch` 内跨 case 定义变量未加块**：`switch(x){ case 1: int v=10; f(v); break; case 2: g(v); }` —— C++ 报错"不能跨越 case 标签初始化"（实测：`cannot jump from switch statement to this case label`）。**解决**：`case 1: { int v=10; f(v); break; }`。
4. **以为「switch 稠密就一定生成跳转表」**：实测 1 里 case 返回值连续时，clang 直接用算术算出来（`add w0, w0, #10`），连表都没有；case 稀疏时又退化成 cmp 链。**跳转表只是编译器的一种选择，不是 switch 的定义**。
5. **照搬「排序能让分支快 3~6 倍」去做优化**：本机实测只有 1.08~1.20 倍（实测 3）——现代预测器 + 编译器无分支化把差距抹平了。**先 profile 再优化**，别拿十年前的传说当依据。

## 自测题

**1. 选择题**：下列代码输出什么？
```cpp
int x = 1;
if (x > 0)
    if (x > 10)
        std::cout << "A";
else
    std::cout << "B";
```
- A) A
- B) B
- C) AB
- D) 无输出

<details><summary>答案</summary>

**B) B**（实测输出 `B`，`-Wdangling-else` 同时给出警告：`add explicit braces to avoid dangling else`）。

`else` 与**最近的未配对 `if`** 配对，也就是内层 `if (x > 10)`。执行过程：`x=1 > 0` 成立 → 进入内层 → `x > 10` 不成立 → 走 else 打印 `B`。**缩进完全骗人**：如果真想让 else 属于外层，必须写 `if (x > 0) { if (x > 10) printf("A"); } else printf("B");`（那样 x=1 时什么都不打印）。

</details>

**2. 判断题**：在 C++ 中，下面代码合法。
```cpp
const int BUF = 1024;
switch (n) { case BUF: f(); break; }
```

<details><summary>答案</summary>

正确。C++ 中用常量初始化的 `const int` 是编译期常量，可作 `case` 标签。但在 C 中同样写法是非法的（C 的 const 不是常量表达式）。

</details>

**3. 踩坑题**：下面代码在 C++ 中编译报错，为什么？怎么改？
```cpp
switch (cmd) {
    case 1:
        int status = read_status();
        process(status);
        break;
    case 2:
        handle_other();
        break;
}
```

<details><summary>答案</summary>

报错：不能跨越 case 标签初始化变量（`status` 的作用域延伸到 case 2，但 case 2 可能跳过初始化）。**修正**：用花括号把 case 1 的内容包成块：
```cpp
case 1: {
    int status = read_status();
    process(status);
    break;
}
```

</details>

**4. 应用题**：用 `switch` 写一个处理 HTTP 状态码的函数，要求 200/201 走成功分支、4xx 走客户端错误、5xx 走服务端错误。注意正确使用穿透和 break。

<details><summary>答案</summary>

```cpp
void handle_status(int code) {
    switch (code) {
        case 200:                   // 穿透
        case 201:
            handle_success();
            break;
        case 400: case 401: case 403: case 404:
            handle_client_error(code);
            break;
        case 500: case 502: case 503:
            handle_server_error(code);
            break;
        default:
            log_unknown(code);
    }
}
```
故意穿透的 case（200→201）可以不加注释，但建议显式写 `// fall through` 让 `-Wimplicit-fallthrough` 闭嘴。

</details>

**5. 判断题**：下面两句对不对？
> (a) `switch` 稠密时一定会被编译成跳转表，所以比 if-else 链快。
> (b) `?:` 三元运算符比 `if-else` 快，因为它没有分支。

<details><summary>答案</summary>

**两句都不准确。**

(a) 稠密 case 时编译器**通常**会用表（实测：`adrp x8, l_switch.table...; ldr w0, [x8, w0, uxtw #2]`），但如果 case 的返回值本身连续，clang 连表都省了，直接算（`add w8, w0, #10`）；稀疏 case 又退化成 `cmp + b.eq` 链。所以"case 稠密 + 返回值不规则"才容易看到跳转表，而且**跳转表的价值是 O(1) 与可扩展性，不是"一定更快"**——分支目标可预测时 if-else 链并不慢（对比 [6.5 的跳转表实测](../ch06-functions/6.5-函数指针.md)）。

(b) 实测：`if (a > b) return a; return b;` 与 `return a > b ? a : b;` 生成**完全相同**的汇编（`cmp` + `csel` + `ret`），都没有跳转。三元更快是错觉，选哪个看可读性。

</details>

**6. 应用题**：热路径上有这么一段：`for (int x : data) if (x >= 128) s += x * 7 + 3; else s -= x * 3 + 1;`
有人提议"先把 data 排序，分支预测器就能预测，能快好几倍"。请评价。

<details><summary>答案</summary>

**实测：只有 1.08 倍（`-O2`）/ 1.20 倍（`-O1`），远不到"好几倍"**，而且排序本身是 O(n log n)，比省下的时间贵得多。

原因有二：① 现代预测器对随机分支没那么脆弱；② 编译器做了 if-conversion，分支体简单时直接生成条件选择/向量选择，"分支"本身就少了。

**真正有效的做法**（按性价比排序）：
1. 先 profile，确认瓶颈确实在这条分支上；
2. 把分支**移出循环**（分桶批量处理：先 partition，再对两段分别做无分支求和）；
3. 用算术/查表替代判断（例如 `s += tbl[x]`）；
4. 最后才考虑 `[[likely]]` / `__builtin_expect`——收益常在噪声里。

一句话：**"让分支更好预测"收益有限，"让分支不存在"才有效。**

</details>
