# 7.2 访问控制与封装

## 本节讲什么

C++ 的访问控制符 `public`/`private`/`protected`，以及 `class` 与 `struct` 的唯一区别（默认访问权限）。这是实现**封装**——隐藏实现细节、暴露稳定接口——的语言机制。

## 核心用法

### 三个访问说明符

| 说明符 | 含义 | 谁能访问 |
|--------|------|---------|
| `public` | 公有接口 | 任何代码 |
| `private` | 私有实现 | 该类的成员函数和友元 |
| `protected` | 受保护 | 该类及派生类的成员（继承章详讲） |

```cpp
class Account {
public:                                   // 外部可调用的接口
    void deposit(double amount) { balance_ += amount; }
    double balance() const { return balance_; }
private:                                  // 外部不可见的实现
    double balance_ = 0;
};

Account acc;
acc.deposit(100);          // OK，public
// acc.balance_ = 100;     // 错误：private，外部不可访问
```

### 访问说明符可以出现多次：「分区」是风格，但挂着两个硬后果

`public:`/`private:`/`protected:` 在一个类里可以出现**任意多次**——语法上 member-specification 就是递归产生式（`access-specifier : member-specification_opt`）。每个说明符对它**之后、下一个说明符之前**的所有声明生效。所以 TheCherno 说的"公共方法放一个区、公共变量放一个区、公共静态变量再放一个区"完全合法：

```cpp
class Log {
public:
    static int s_InstanceCount;      // 公共静态变量一个区
public:                              // 同一个说明符写两遍也合法
    void SetLevel(int level);        // 公共方法一个区
    void Warn(const char* msg);
private:
    int m_LogLevel;
};
```

怎么分区对编译器**基本无感**——实测（clang 23.1.0，`-std=c++20` 与 `-std=c++23` 结果一致）：

| 写法 | 数据成员 a/b/c 的访问级别 | `sizeof` | `is_standard_layout_v` |
|------|--------------------------|----------|------------------------|
| 全部成员挤一个 `public:` 区 | 全 public | 12 | **1** |
| a/b/c 分在 public/private/public 三个区 | **不同** | 12 | **0** ← 唯一的硬差别 |
| 方法分两个 public 区、数据全 private | 全 private | 12 | **1** |

两个关键结论：

1. **方法随便分区，不影响布局**——布局只由**非静态数据成员**决定，成员函数不占对象存储（见 7.1 的 this 实测）。
2. **数据成员的访问级别一旦不同，类就丧失 standard-layout 资格**。standard-layout 是"内存布局与 C 兼容"的保证（能安全 `memcpy`、`offsetof`、与 C 结构体互操作）。注意 `sizeof` 一个字节都没变——这个损失是**纯类型系统层面**的，不看 traits 根本发现不了。

> **HFT 关联**：行情解码里的 wire-format 结构体（要 `memcpy` 直接落盘/上网络、要跟 C 库共享布局）必须保住 standard-layout——数据成员**全部同一个访问级别**（通常用全 public 的 `struct`），要分区只能拿方法来分。

**布局顺序的标准变迁**（新版标准改了规则，值得记住）：

- **C++20 及以前**（N4861 [class.mem] p19，逐字）："Non-static data members of a (non-union) class **with the same access control** and non-zero size ... are allocated so that later members have higher addresses within a class object. **The order of allocation of non-static data members with different access control is unspecified.**" —— 跨访问区的成员顺序，标准不保证（虽然所有主流 ABI 实际都按声明序）。
- **C++23 起**（P1847R4 之后，现行草案 [class.mem.general] Note 8）："Non-variant non-static data members of non-zero size are allocated so that later members have higher addresses within a class object." —— 访问级别限定词被删掉，**所有成员一律强制按声明序**。

但 **standard-layout 的「同一访问级别」要求并没有随 C++23 取消**：实测 `-std=c++23` 下 `is_standard_layout_v<ThreeSections>` 仍为 0。C++23 改的是"顺序保证"，没改"standard-layout 资格"。

### class vs struct：差别只有「默认访问级别」，而且是两处

```cpp
class A { int x; };     // 成员 x 默认 private
struct B { int x; };    // 成员 x 默认 public
```

**唯一区别是默认访问级别**——而且是**两处**都受它影响，多数人只记得第一处：

| 场合 | `class` 默认 | `struct` 默认 |
|------|-------------|--------------|
| 成员（数据/函数）的访问权限 | `private` | `public` |
| 继承方式（`class D : Base`） | **`private` 继承** | **`public` 继承** |

标准原文（C++ draft）：

> **§11.8.1/3**：Members of a class defined with the keyword `class` are private by default.
> Members of a class defined with the keywords `struct` or `union` are public by default.
>
> **§11.8.3/2**：In the absence of an *access-specifier* for a base class, `public` is assumed when
> the derived class is defined with the *class-key* `struct` and `private` is assumed when the class
> is defined with the *class-key* `class`.

除默认访问级别外，**二者在类型系统里完全等价**：`struct` 也是 class（`std::is_class_v<B> == true`），
同样能有成员函数、构造/析构、虚函数、继承、模板。

#### 实测：让编译器自己承认

**① 默认成员访问**（clang 23.1.0，`class C { int x = 0; };` 后 `c.x = 1;`）：

```
error: 'x' is a private member of 'C'
note: implicitly declared private here          ← 编译器替你补的 private
```

**② 默认继承**（`class D : Base {};` 后 `Base* p = &d;`）：

```
error: cannot cast 'D' to its private base class 'Base'
note: implicitly declared private here          ← 继承说明符也被隐式补成 private
```

同一件事也能在**不触发报错**的前提下测出来（`std::is_convertible` 静态断言）：

```cpp
class  Base { public: int v = 1; };
class  D_class  : Base {};   // 默认 → private 继承
struct D_struct : Base {};   // 默认 → public  继承

static_assert(!std::is_convertible_v<D_class*,  Base*>, "");  // 外部不认「D_class 是 Base」
static_assert( std::is_convertible_v<D_struct*, Base*>, "");  // 外部认「D_struct 是 Base」
```

> **HFT 关联**：默认继承这条在真实代码里最容易被忽略——写 `class OrderBook : Base {}` 得到的是
> **private 继承**，外部无法把 `OrderBook&` 当 `Base&` 用（多态失效、传参编译不过）。
> 想让"是一种"关系成立，必须显式写 `: public Base`。这也是 Google C++ 风格指南要求
> **继承一律显式写明访问级别**的原因。

#### 实践建议

| 用途 | 选择 | 理由 |
|------|------|------|
| 纯数据聚合（POD、传输结构、只装字段） | `struct` | 默认 public 省事，语义上"就是一堆公开数据" |
| 有不变式 / 有行为的对象 | `class` | 默认 private 安全，逼你显式暴露接口 |

注意这只是**约定**（C++ 核心指南 C.2/C.8 也这么建议），不是语言强制——
`struct` 一样能写 `private`：`struct S { private: int x; };` 完全合法。

### 封装的意义

- **不变式保护**：把数据设 private，只能通过成员函数访问，函数内可加校验，防止外部直接破坏不变式
- **实现自由**：private 细节可随时改，不影响使用者（ABI/接口稳定）
- **可读性**：使用者只看 public 接口，不必关心实现

### 成员命名约定：`m_` 前缀防的是「参数遮蔽」这个真坑

典型的 private 数据 + public 接口长这样（TheCherno CLASSES 一集的 Log 例子）：

```cpp
class Log {
public:
    void SetLevel(int level) {
        m_LogLevel = level;            // m_ 前缀：一眼看出这是成员，不是参数
    }
    void Warn(const char* message) { /* ... */ }
private:
    int m_LogLevel = 0;                // 私有数据
};
```

为什么要给成员加 `m_` 前缀？Cherno 的说法是"在函数体里一眼分清哪些是类作用域的成员、哪些只是局部变量/参数"。但这不只是**可读性**问题——不加区分符会踩一个**编译器默认不警告的真坑**：

```cpp
class LogBad {
public:
    void SetLevel(int level) {
        level = level;      // 想写「成员 = 参数」，实际是参数自赋值，成员根本没动
    }
private:
    int level = 0;
};
```

实测（clang 23.1.0，macOS arm64）：

| 写法 | `SetLevel(3)` 后读回 | 默认编译选项下有警告吗 |
|------|---------------------|----------------------|
| `level = level;`（参数遮蔽成员） | **0**（静默丢数据） | **没有**——连 `-Wall` 都不含 `-Wshadow` |
| `this->level = level;` | 3 | —— |
| `m_LogLevel = level;`（m_ 前缀） | 3 | —— |
| `level_ = level;`（尾随下划线） | 3 | —— |

加 `-Wshadow` 后编译器才会指认：`warning: declaration shadows a field of 'LogBad'`。

**三种主流约定，任选其一并全项目统一**：

| 约定 | 例子 | 谁在用 |
|------|------|--------|
| `m_` 前缀 | `m_LogLevel` | Cherno、大量游戏/图形代码 |
| 尾随下划线 | `log_level_` | **Google C++ 风格指南**（本仓库笔记里的 `balance_`/`count_`/`kelvin_` 就是这个） |
| 不加约定，成员访问一律 `this->` | `this->level` | 部分代码库；缺点是漏写一处就回到遮蔽坑 |

这是**纯约定，语言层面没有任何规则**——编译器只认作用域，不认命名。约定买不到正确性，但能买到两件事：函数体里成员/局部一眼可辨（Cherno 的理由）；从根上消除"参数与成员同名"的遮蔽类 bug（实测的 `level = level;` 静默失效）。工程上的兜底是把 `-Wshadow` 加进编译选项。

## 和 C 的区别

| 维度 | C | C++ |
|------|---|-----|
| `struct` 成员访问控制 | 全部公开，无 `private` | 可有 `public`/`private`，与 `class` 等价 |
| 封装机制 | ❌ 无（数据全公开，靠程序员自觉） | ✅ 编译器强制 |
| `class` 关键字 | ❌ 无 | ✅ |
| `private`/`public` | ❌ 无 | ✅ |

**C 程序员的认知转变**：

C 里 struct 的成员全是公开的，外部可任意读写，封装全靠"约定"和文档：
```c
/* C：数据全公开，外部可绕过函数直接改 */
struct Account {
    double balance;    // 谁都能直接访问
};
struct Account a;
a.balance = -1000;     // 没人拦你，破坏不变式
```

C++ 用 private 把数据藏起来，外部只能通过 public 函数访问，函数内可校验：
```cpp
// C++：private 保护数据，public 函数控制访问
class Account {
public:
    bool deposit(double amt) {
        if (amt < 0) return false;   // 校验
        balance_ += amt;
        return true;
    }
private:
    double balance_ = 0;             // 外部碰不到
};
Account a;
// a.balance_ = -1000;   // 编译错误，private
a.deposit(-100);        // 运行期被拒
```

这是从"约定式封装"到"语言强制封装"的转变，C++ 编译器替你守不变式。

## 常见错误

1. **把所有成员都 public**：把 class 当 C struct 用，数据全公开，失去封装意义。**建议**：数据成员默认 private，只暴露必要的接口函数。
2. **`class` 和 `struct` 混用困惑**：同一个类型一会儿用 `class` 声明一会儿用 `struct` 前向声明，没问题（它们是同一类型），但默认访问不同容易出错——**尤其漏掉"默认继承"这一处**：`class D : Base {}` 是 private 继承，外部无法把 `D&` 当 `Base&` 用。**建议**：继承一律显式写 `public`/`private`/`protected`；有封装需求用 `class`（默认 private 安全），纯数据聚合用 `struct`（默认 public 方便）。
3. **getter/setter 暴露一切**：为每个 private 成员都写 `get_x()`/`set_x()`，本质还是公开数据，封装形同虚设。**建议**：接口应反映"行为"而非"字段"，只在确有必要时暴露。

## 自测题

**1. 选择题**：下面代码 `main` 中哪些访问合法？
```cpp
class P {
public:  int a;
private: int b;
};
int main() {
    P p;
    p.a = 1;
    p.b = 2;
}
```
- A) 都合法
- B) 都非法
- C) `p.a=1` 合法，`p.b=2` 非法
- D) `p.a=1` 非法，`p.b=2` 合法

<details><summary>答案</summary>

C。`a` 是 public，外部可访问；`b` 是 private，外部不可访问（只有 P 的成员函数和友元能访问）。这是 C++ 封装的基本规则，编译期强制。

</details>

**2. 判断题**：C++ 中 `struct` 可以有构造函数、成员函数、继承，和 `class` 功能完全一样。

<details><summary>答案</summary>

正确。C++ 的 `struct` 和 `class` 唯一区别是**默认访问权限**（struct 默认 public，class 默认 private）和默认继承方式。功能上完全等价，struct 也能有构造函数、成员函数、虚函数、继承等。实践中：有封装用 class，纯数据聚合用 struct。

</details>

**3. 踩坑题**：下面类想保护 `count_` 不被外部直接改，但有漏洞吗？
```cpp
class Counter {
public:
    int& count() { return count_; }   // 返回 count_ 的引用
private:
    int count_ = 0;
};
```

<details><summary>答案</summary>

封装被绕过。`count()` 返回 `int&`，调用者拿到引用就能直接改 `count_`：`Counter c; c.count() = 100;` 完全绕过了私有性。**修正**：返回值类型 `int`（拷贝）或 `const int&`（只读引用），不要返回非 const 引用暴露内部数据。

</details>

**4. 应用题**：设计一个 `Temperature` 类，内部用开尔文存储，对外提供 `set_celsius`/`get_celsius` 和 `set_fahrenheit`/`get_fahrenheit` 接口。说明封装的好处。

<details><summary>答案</summary>

```cpp
class Temperature {
public:
    void set_celsius(double c) { kelvin_ = c + 273.15; }
    double get_celsius() const { return kelvin_ - 273.15; }
    void set_fahrenheit(double f) { kelvin_ = (f - 32) * 5 / 9 + 273.15; }
    double get_fahrenheit() const { return (kelvin_ - 273.15) * 9 / 5 + 32; }
private:
    double kelvin_ = 0;   // 内部统一用开尔文，外部不感知
};
```
封装好处：1) 内部表示（开尔文）可随时改（如换成微开尔文定点数）而不破坏接口；2) 外部无法设置低于绝对零度的非法值（可在 setter 加校验）；3) 使用者只需关心摄氏/华氏接口，不需理解内部存储。C 做不到这种"接口与实现分离"的强制。

</details>

**5. 踩坑题**：下面的 `Cat : Animal` 想表达"猫是一种动物"，`Animal& a = cat;` 能编过吗？为什么？怎么改？

```cpp
class Animal { public: int legs = 4; };
class Cat : Animal { };
int main() {
    Cat cat;
    Animal& a = cat;      // ？
}
```

<details><summary>答案</summary>

**编不过。** `class` 的默认继承方式是 **private 继承**，外部代码看不到"`Cat` 是一种 `Animal`"，编译器直接拒绝隐式向上转型：

```
error: cannot cast 'Cat' to its private base class 'Animal'
note: implicitly declared private here
```

**改法一**：显式写继承说明符 —— `class Cat : public Animal {};`（推荐，Google 风格指南也要求继承必写访问级别）。
**改法二**：把 `Cat` 声明成 `struct`（默认 public 继承）——`struct Cat : Animal {};`，但这只在"本来就想用 struct"时才合适。

注意 `Animal::legs` 是 public，访问它本身没问题；出问题的是**派生关系本身是私有的**。这就是"默认访问级别有两处"的典型踩坑点。

</details>

**6. 踩坑题**：下面的 `SetLevel` 有 bug 吗？`log.SetLevel(3)` 之后 `GetLevel()` 返回多少？默认编译选项下会有警告吗？

```cpp
class Log {
public:
    void SetLevel(int level) { level = level; }
    int GetLevel() const { return level; }
private:
    int level = 0;
};
```

<details><summary>答案</summary>

有 bug，而且**静默**——`SetLevel(3)` 之后 `GetLevel()` 仍返回 **0**。

`level = level;` 里的两个 `level` 指的都是**参数**（参数遮蔽了同名成员），所以这行是参数自赋值，成员从头到尾没被碰过。实测默认编译选项下**没有任何警告**（`-Wall` 不含 `-Wshadow`），加 `-Wshadow` 才会报 `declaration shadows a field of 'Log'`。

三种修法（任选并全项目统一）：

1. `this->level = level;` —— 显式指明左边是成员；
2. 成员加 `m_` 前缀：`m_LogLevel = level;`（Cherno 风格）；
3. 成员加尾随下划线：`level_ = level;`（Google 风格，本仓库笔记统一用这种）。

工程兜底：把 `-Wshadow` 加进编译选项，让编译器替你盯着这类遮蔽。

</details>

**7. 判断+分析题**：下面两个类，`sizeof` 一样吗？都是 standard-layout 吗？哪个能安全地 `memcpy` 与 C 端结构体互操作？

```cpp
class A {                              class B {
public:                                public:
    char a;                                char a;
    int  b;                            private:
    char c;                                int  b;
    void f() {}                        public:
};                                         char c;
                                           void f() {}
                                       };
```

<details><summary>答案</summary>

**`sizeof` 一样**（实测都是 12 字节）——访问分区不改变布局，布局只由非静态数据成员的类型与声明顺序决定。

**standard-layout 不一样**：`is_standard_layout_v<A> == 1`，`is_standard_layout_v<B> == 0`。因为 standard-layout 要求**所有非静态数据成员访问级别相同**，B 的 `b` 是 private、其余 public，资格丧失——尽管 `sizeof` 没变、成员函数 `f()` 怎么分区都无所谓。

能安全 `memcpy` 与 C 互操作的只有 **A**。B 在主流 ABI 上实际布局也和 A 一样（`-std=c++20`/`-std=c++23` 实测一致），但那是实现行为，不是标准给你的保证。

补充：C++20 及以前，跨访问区的成员分配顺序标准是 **unspecified**（N4861 [class.mem] p19）；C++23 起（P1847R4）所有成员一律强制按声明序——但 standard-layout 的「同一访问级别」要求**没有**取消。

</details>

## 可跑的例子

**`examples/7.2-access-control.cpp`** —— class 和 struct 的唯一区别，以及封装的运行期成本。

```bash
clang++ -std=c++20 examples/7.2-access-control.cpp -o /tmp/demo && /tmp/demo
```

真实输出（节选）：

```
sizeof(class 版)  = 16 字节
sizeof(struct 版) = 16 字节
两者内存布局完全相同: 是
名义本金 = 1250.00
```

**看出什么了？** class/struct 内存布局逐字节相同（memcmp 验证）——差别只在**默认访问级别**这个编译期概念。直接摸 `a.qty_` 编译器直接拒绝（例子里留了注释），但生成的机器码里没有任何"访问检查"指令。

> 封装 = 编译期约束、运行期零开销。HFT 关心后者：加封装不花一个周期。
