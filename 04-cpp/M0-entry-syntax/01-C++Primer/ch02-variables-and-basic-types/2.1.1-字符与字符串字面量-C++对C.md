# 2.1.1 字符与字符串字面量：C++ 对 C 的完整对照

> 2.1 基本内置类型 · 子节 · 承接《C和指针》[3.1.6 字符常量的类型陷阱](../../../../01-c-language/02-advanced-pointers-and-memory/ch03-data/3.1-basic-data-types/3.1.6-字符常量的类型陷阱.md)

## 本节讲什么

[2.1 基本内置类型](./2.1-基本内置类型.md) 里只有一行「字符字面值 `'a'`；字符串字面值 `"hello"`」，没往下拆。这一节把它拆到底，并回答一个 C/C++ 混编项目里绕不开的问题：

> `char c = 'x'; sizeof(c)` 和 `sizeof('x')` 在 C++ 里各是多少？在 C 里呢？

**一句话结论**（三层递进，本节最重要的一张图）：

| 层次 | C | C++ | 是否相同 |
|------|---|-----|---------|
| **变量层** `char c` | 1 字节，符号性实现定义 | 1 字节，符号性实现定义 | ✅ **完全一致** |
| **字面量层** `'x'` | 类型 **`int`**，`sizeof` = 4 | 类型 **`char`**，`sizeof` = 1 | ❌ **唯一核心差异** |
| **表达式层** `'x' + 'x'` | `int`，`sizeof` = 4 | 提升为 `int`，`sizeof` = 4 | ✅ **殊途同归** |

差异只存在于**孤立的字符字面量的静态类型**；一旦进表达式，两边都被**整数提升（integral promotion）**拉回 `int`。

⚠️ 但有一个必须记住的例外：**`cout << c` 不触发提升**（见 [§8](#8-cout-输出字符还是数字由重载决议决定不是整数提升)）。C 的 `printf` 是无条件提升 + 格式符反推，C++ 的 `cout` 是不提升 + 重载决议正推——两套完全不同的机制，别把 C 的直觉套过来。

本节所有数字均为**本机实测**（clang 23.1.0，macOS arm64），不是照抄标准条文。

## 要点

### 0. 先把两件事分开：变量类型 ≠ 字面量类型

```cpp
char c = 'x';
sizeof(c);    // 1 —— c 的类型由「声明」决定
sizeof('x');  // 1 (C++) / 4 (C) —— 'x' 的类型由「语言标准」决定
```

- **变量类型**是静态属性，声明那一刻就定了；
- **字面量类型**由标准规定，**和它被赋给什么变量无关**；
- **整数提升**是表达式求值时的临时转换，求值完就消失，**不改变变量自己的类型**。

所以「`c` 参与运算会变成 `int`」这句话的严格说法是：`c` 参与运算时用的是一个**提升后的 `int` 临时值**，`c` 本身仍是 `char`（`sizeof(c)` 依旧 1）。

### 1. 第一层：变量层 —— C/C++ 完全相同

```c
char c;              /* 1 字节 */
signed char sc;      /* 1 字节，明确有符号：-128..127 */
unsigned char uc;    /* 1 字节，明确无符号：0..255 */
```

三者是**三种不同的类型**（重载决议会区分），但 `char` 的符号性**由 ABI/编译器决定**，标准不保证：

| 平台 | ABI | `char` 符号性 |
|------|-----|--------------|
| x86-64 Linux (gcc/clang) | SysV | **signed** |
| **arm64 macOS（本机实测）** | Apple ARM64 | **signed** |
| aarch64 Linux (gcc) | AAPCS64 | **unsigned** |
| ARM32 (gcc) | AAPCS | **unsigned** |

**实测印证**（本机）：`printf("%s", (char)-1 < 0 ? "signed" : "unsigned")` → `signed`。

> 端口性铁律：**需要字节数值时一律写 `uint8_t` / `int8_t`**，裸 `char` 只用来装字符。`aarch64 Linux` 上 `char` 是无符号这条，和本机结论**相反**——这正是跨平台 bug 的温床，详见《C和指针》[3.1.5 字符的符号性陷阱](../../../../01-c-language/02-advanced-pointers-and-memory/ch03-data/3.1-basic-data-types/3.1.5-字符的符号性陷阱.md)。

**符号性可以被编译选项直接翻转**（这也是"由编译器决定、不由 CPU 指令集决定"的直接证据）：

```bash
clang++ -std=c++17 -funsigned-char a.cpp    # char 变 unsigned
clang++ -std=c++17 -fsigned-char   a.cpp    # char 变 signed（本机默认即此项）
```

实测（同一份代码，只改选项）：

| 选项 | `std::is_signed<char>` | `(int)(char)0xFF` |
|------|------------------------|-------------------|
| 默认（macOS arm64） | **signed** | **-1** |
| `-funsigned-char` | **unsigned** | **255** |
| `-fsigned-char` | signed | -1 |

注意 `signed char` / `unsigned char` **不受这两个选项影响**——只有裸 `char` 被翻转。

**向更大整型赋值时的扩展规则**（实测）：

| 源 | 值 | 扩展方式 | 结果（`int`） |
|---|---|---|---|
| `signed char` / signed `char` | 0xFF | **符号扩展**，高位填符号位 | `-1`（0xFFFFFFFF） |
| `unsigned char` | 0xFF | **零扩展**，高位填 0 | `255`（0x000000FF） |

两者只差在高位填什么。**字节最高位为 0（ASCII 0~127）时两种扩展结果相同**，所以纯 ASCII 场景看不出差别；一旦字节 ≥ 0x80，`(int)c` 到底是 128 还是 -128 就取决于符号性——这是拿 `char` 当数组下标（`tbl[c]`）这类查表代码在 aarch64 上越界的经典根因。

### 2. 第二层：字面量层 —— 唯一的核心差异

C 标准（C11 §6.4.4.4 / C23 §6.4.4.5）：

> An integer character constant **has type `int`**.

C++ 标准（[lex.ccon]）：

> A character-literal that does not have a `u8`、`u`、`U`、`L` prefix **has type `char`**.

**为什么 C 这么设计？** 历史包袱：C 诞生于 PDP-11，寄存器 16 位、无单字节算术指令，字符常量天生要参与算术（`'A' + 1`），直接给 `int` 省掉一次截断。

**为什么 C++ 改了？** C++ 有**函数重载**和**模板推导**，字面量类型必须与类型系统自洽：

```cpp
void f(int);
void f(char);
f('A');    // C++: 调用 f(char)，精确匹配
           // 若 'A' 是 int（C 规则），只能调 f(int)

auto a = 'x';   // C++: a 是 char
sizeof(a);      // 实测 = 1
```

**实测的类型判定表**（`std::is_same` + 特化 `tname<T>()`，非 `sizeof` 推断）：

| 字面量 | C++17 类型 | C++20 类型 |
|--------|-----------|-----------|
| `'x'` | `char` | `char` |
| `"x"[0]` | `char` | `char` |
| `L'x'` | `wchar_t` | `wchar_t` |
| `u'x'` | `char16_t` | `char16_t` |
| `U'x'` | `char32_t` | `char32_t` |
| `u8'x'` | **`char`** | **`char8_t`** ← C++20 断裂点 |
| `u8"x"[0]` | **`char`** | **`char8_t`** ← C++20 断裂点 |
| `'xy'`（多字符） | `int` | `int` |

### 3. 第三层：表达式层 —— 两边殊途同归

这是最容易被忽略的一层，也是「`sizeof('x')` 有差异」这条知识的**边界**：

```c
sizeof('x');       /* C: 4   C++: 1 */
sizeof('x' + 'x'); /* C: 4   C++: 4  ← 一样了！ */
```

实测两档 C++ 标准下 `sizeof('x' + 'x')` 均为 **4**。原因：`char` 作为算术运算符操作数时被提升为 `int`，两个 `int` 相加结果仍是 `int`。

**所以**：C/C++ 的差异**只在孤立字面量的静态类型**上，一旦参与运算，`char` 就"膨胀"回 `int`。这一点在 C 侧同理——`'A'` 本来就是 `int`，无需提升。

> 比较运算同样先提升：`if (c == 'a')` 在 C 里 1 次提升、C++ 里 2 次，殊途同归都按 `int` 比；`if ((char)0xFF == 0xFF)` 在 signed char 平台上是 **false**（-1 ≠ 255）。比较/移位里的三个提升坑见 [4.11.1 隐式类型转换 §1](../ch04-expressions/4.11-type-conversions/4.11.1-隐式类型转换.md)。

### 5. C++ 独有的字面量家族

这些在 C 里**没有对应物**，是 C++ 侧真正的"增量"：

**① 原始字符串 `R"..."`（C++11）**

```cpp
const char *path = R"(C:\Users\a0000\data)";   // 反斜杠不用转义
const char *re   = R"(\d{3}-\d{4})";           // 正则、Windows 路径救星
const char *sql  = R"(SELECT * FROM t WHERE name = "bob")";  // 内嵌双引号
```

实测 `sizeof(R"(x)")` = 2，和普通 `"x"` 完全一样——`R` 只是**词法层**的转义开关，不影响类型和存储。

**② 字面量后缀 `s` / `sv`（C++14 / C++17）**

```cpp
using namespace std::string_literals;
using namespace std::string_view_literals;

auto a = "x"s;    // std::string，  实测 sizeof = 24（含堆/SSO 缓冲）
auto b = "x"sv;   // std::string_view，实测 sizeof = 16（ptr + len）
```

`sv` 是 HFT 热路径的首选：零拷贝、零分配，只带长度，正好匹配"显式长度"的报文模型。

**③ `u8` / `u` / `U` / `L` 前缀的演进**

| 前缀 | C++11 | C++17 | C++20 |
|------|-------|-------|-------|
| `u8"..."`（字符串） | ✅ `const char[]` | ✅ | ❗ 变 `const char8_t[]` |
| `u8'x'`（字符） | ❌ **不存在** | ✅ `char` | ❗ 变 `char8_t` |
| `u'x'` / `u"..."` | ✅ `char16_t` | ✅ | ✅ |
| `U'x'` / `U"..."` | ✅ `char32_t` | ✅ | ✅ |
| `L'x'` / `L"..."` | ✅ `wchar_t` | ✅ | ✅ |

⚠️ **实测**：`-std=c++11` 下写 `u8'x'` 直接报 `error: use of undeclared identifier 'u8'`——**`u8` 字符字面量是 C++17 才有的，字符串字面量 `u8"..."` 才是 C++11**。别记混。

### 6. 字符串字面量的两种形态：数组 vs 指针

前面几节（§1–§5）讲的是**字符**字面量（单引号），这一节讲**字符串**字面量（双引号）的两种落地形态——这是 C/C++ 共有的、也是初学者最先撞上的一组对立：

```cpp
char buf[] = "hello";   // 形态 A：数组 —— 拷贝一份，可写
char *p    = "hello";   // 形态 B：指针 —— 指向只读段，不可写
```

| 维度 | 形态 A `char buf[] = "hello"` | 形态 B `char *p = "hello"` |
|------|------------------------------|---------------------------|
| 声明的东西 | **数组**（6 字节） | **指针**（8 字节） |
| 是否拷贝 | ✅ 把字面量内容**复制**进数组 | ❌ 只存地址，无拷贝 |
| 存储位置 | 自动存储期在**栈**；`static`/全局在 **.data（可写）** | 字面量在 **.rodata / `__TEXT`（只读）** |
| 可写吗 | ✅ `buf[0]='H'` 合法 | ❌ UB（见下） |
| `sizeof` | **6**（数组长度，含 `'\0'`） | **8**（指针本身大小） |
| 是否含 `'\0'` | ✅ 自动补 | ✅ 自动补 |

**实测**（clang 23.1.0 / macOS arm64）：

```
sizeof(l_arr)   = 6        l_arr (栈)     = 0x16f06b0b4
sizeof(l_p)     = 8        literal "hello"= 0x100d93e9c   ← __TEXT 只读段
sizeof("hello") = 6        g_arr (可写)   = 0x100d98010   ← __DATA 段
```

三个地址分属不同区域，一眼能看出"拷贝"和"指过去"的区别。

⚠️ **"栈上"这个说法只对一半**：`char buf[] = "hello"` 写在函数里才是栈；写成 `static char buf[]` 或放在文件作用域，它在 **.data 段**（可写），由加载器填充，**同样可写**，但不是栈。上面实测的 `g_arr` 就在 .data，`g_arr[0]='H'` 实测成功输出 `Hello`。

#### C 与 C++ 在这里又分道扬镳

这是比"能不能改"更根本的差异——**字符串字面量的静态类型**：

| 语言 | `"hello"` 的类型 | `char *p = "hello";` |
|------|-----------------|---------------------|
| **C**（C89→C23 全版本） | **`char[6]`**（**没有 const**） | ✅ 合法，`-Wall` 下**零警告** |
| **C++**（C++03 起） | **`const char[6]`** | ❌ ill-formed |

实测：

```bash
$ clang   -std=c11 -Wall          t.c    # C：无警告，静默埋雷
$ clang   -std=c11 -Wwrite-strings t.c   # warning: initializing 'char *' with an
                                         # expression of type 'const char[6]' discards qualifiers
$ clang++ -std=c++17              t.cpp  # warning: ISO C++11 does not allow conversion
                                         # from string literal to 'char *' [-Wwritable-strings]
$ clang++ -std=c++17 -pedantic-errors t.cpp  # error: 同上
```

C++ 从类型系统层面直接把这条 UB 通道封死；C 为了向后兼容保留了 `char *` 赋值，所以**工程上必须自觉写 `const char *`**，并开 `-Wwrite-strings`。

#### 修改只读段会发生什么（实测）

```c
char *p = "hello";
p[0] = 'H';   /* UB */
```

| 环境 | 结果 |
|------|------|
| **macOS arm64（本机实测）** | **SIGBUS(10)**，`echo $?` = **138** |
| Linux x86-64 / aarch64 | 通常 **SIGSEGV(11)**，`$?` = 139 |
| 裸机 MCU（常量在 Flash） | 可能**静默丢弃写入**，也可能 HardFault |

注意本机是 **SIGBUS 不是 SIGSEGV**——macOS arm64 对 `__TEXT` 段的写保护走的是 bus error。标准只保证"未定义行为"，**不保证崩溃**，所以别拿"跑起来没崩"当正确性的证据。

#### 常量合并（实测）

```c
char *s1 = "abc";
char *s2 = "abc";
printf("%d\n", s1 == s2);   /* 实测输出 1 —— 同一地址 */
```

编译器做**字面量合并**（`-fmerge-constants`，默认开），两个指针指向同一块只读内存。所以写 `s1[0]` 会**连带改掉 `s2`**。反过来，用 `==` 比较字符串内容永远是错的——比的是地址。

### 7. C++20 的 `char8_t` 断裂与迁移

这是 C++20 最痛的一处**静默 breaking change**，本机实测三个断点：

**断点 1：赋值给 `const char*` 失败**

```cpp
#include <string>
const char *p = u8"x";
```

| 标准 | 结果 |
|------|------|
| `-std=c++17` | ✅ 编译通过 |
| `-std=c++20` | ❌ `error: cannot initialize a variable of type 'const char *' with an lvalue of type 'const char8_t[2]'` |

**断点 2：`std::cout` 输出 `u8` 串失败**

```cpp
std::cout << u8"hi";
```

| 标准 | 结果 |
|------|------|
| `-std=c++17` | ✅ 编译通过 |
| `-std=c++20` | ❌ `error: overload resolution selected deleted operator '<<'`<br>`note: candidate function ... operator<<(basic_ostream<char, _Traits>&, const char8_t*) = delete` |

C++20 明确**删除**了 `basic_ostream<char> << const char8_t*` 重载——这是故意的，防止把 UTF-8 字节流当成执行字符集（如 GBK）打印。

**断点 3：`u8'x'` 的类型从 `char` 变 `char8_t`**（见 §2 类型表）

**迁移写法**：

```cpp
// ① 正确姿势：用 u8 类型体系
std::u8string s = u8"你好";        // C++20 新增

// ② 与只吃 char 的老 API（send/write/fwrite）对接：字节级重解释
const char8_t *u8s = u8"x";
const char *bytes = reinterpret_cast<const char *>(u8s);
write(fd, bytes, 2);               // char* 允许别名访问任何对象，读取安全

// ③ 打印：转回 char 再输出，或用 std::u8string 逐字节
std::cout << reinterpret_cast<const char *>(u8"x");
```

> `char8_t` 与 `unsigned char` 大小、对齐、符号性**相同但是不同类型**——`reinterpret_cast` 读取字节是安全的（C++ 的 `char`/`unsigned char` 别名豁免），但**写入**和 `memcpy` 之外的用法要谨慎。

### 8. `cout` 输出字符还是数字：由**重载决议**决定，不是整数提升

这是 C++ 与 C 在"输出"上最本质的分歧，也是**最容易讲错**的一处。

> ⚠️ **常见误解**：「`short` 没有专属 `operator<<` 重载，所以被提升成 `int` 才输出数字 65。」
> **错。** `basic_ostream` **有** `operator<<(short)` 成员重载，是**精确匹配**，压根没有发生提升。
> 输出数字是因为 `short` 是整数类型、走的是**数字插入器**，跟提不提升无关。

**标准库其实是两套插入器**（本机 libc++ `<ostream>` 实测）：

| 类别 | 位置 | 形参 | 输出行为 |
|------|------|------|----------|
| **数字插入器** | `basic_ostream` **成员** | `bool` `short` `unsigned short` `int` `unsigned` `long` `long long` `float` `double` `long double` `const void*` `streambuf*` `nullptr_t` | 走 `num_put`，输出**数字** |
| **字符插入器** | **非成员**（ADL 找到） | `char` `signed char` `unsigned char` | 走 streambuf，输出**字符** |
| **字符串插入器** | **非成员** | `const char*` `const signed char*` `const unsigned char*` | 输出**字符串** |

关键细节：**成员里没有 `char` / `signed char` / `unsigned char`**。这就是为什么 `cout << c` 一定会去选非成员的那个字符插入器。

**四条实测**（clang++ 23.1.0 / libc++）：

```cpp
char          c  = 'A';
short         s  = 65;
unsigned char uc = 65;
uint8_t       u8 = 65;          // == unsigned char

cout << c;    // A    非成员 operator<<(ostream&, char)        —— Identity 精确匹配
cout << s;    // 65   成员   basic_ostream::operator<<(short)  —— Identity 精确匹配，无提升
cout << +c;   // 65   +c 的类型已是 int（一元 + 真触发提升）→ 成员 operator<<(int)
cout << uc;   // A    非成员 operator<<(ostream&, unsigned char)
cout << u8;   // A    uint8_t 就是 unsigned char —— 同一条路
```

**决定性反证**：如果「提升成 `int` 就输出数字」这条机制成立，那 `unsigned char` 也会被提升成 `int`、也该输出 `65`。但实测输出 **`A`**。所以——**输出形态取决于选中哪个插入器，与是否提升无关**。

**怎么在不背头文件的前提下证明 `operator<<(short)` 存在**：

```cpp
// ① 歧义法：只有当库里已有一个精确匹配的 short 重载时，才会二义
std::ostream& operator<<(std::ostream& os, short v) { return os; }
std::cout << s;
// error: use of overloaded operator '<<' is ambiguous
//        (with operand types 'ostream' and 'short')

// ② 成员调用法：成员语法只对成员函数有效
std::cout.operator<<(s);   // ✅ 编译通过 → short 重载是成员
```

> 顺带一个推论：正因为成员里没有 `char`，如果真只剩成员可用，`cout << c` 会陷入
> `char→short` 与 `char→int` 两条**同为 Promotion 等级**的转换而二义。字符插入器正是为此而存在的。

**⚠️ HFT / 工程第一大坑：`uint8_t` 打印出来是字符**

`uint8_t` = `unsigned char`，`int8_t` = `signed char`——两者都有字符插入器。

```cpp
uint8_t seq = 65;
std::cout << "seq=" << seq << "\n";   // seq=A   ← 日志里是 ASCII 字符，不是序号
```

修法三选一（都是先让它变成 `int`）：

```cpp
std::cout << +seq;                    // 一元 +，最简洁
std::cout << unsigned(seq);
std::cout << static_cast<int>(seq);
```

**C++20 又补了一刀：`char8_t/char16_t/char32_t/wchar_t` 的插入器被 `= delete`**

| 代码 | C++17 | C++20 |
|------|-------|-------|
| `cout << u'A'`（`char16_t`） | ✅ | ❌ deleted |
| `cout << U'汉'`（`char32_t`） | ✅ | ❌ deleted |
| `cout << L'A'`（`wchar_t`） | ✅ 输出数字 65 | ❌ deleted |

实测报错是 `overload resolution selected deleted operator '<<'`——注意它是**先选中、再发现被删除**，不是"找不到重载"。这是 C++20 有意为之：禁止把宽字符/UTF 字符隐式窄化成执行字符集打印。

**和 `printf` 的对照（这一节真正的重点）**：

| | `printf` | `cout` |
|---|---|---|
| 机制 | 可变参数，**默认实参提升无条件发生** | 函数重载，**不提升**，按类型精确匹配 |
| 谁决定输出形态 | 格式符 `%c` / `%d` | 选中「字符插入器」还是「数字插入器」 |
| `char` 传进去 | 一定先变成 `int` | **不变**，以 `char` 身份匹配字符插入器 |
| 类型写错的后果 | 运行期 UB / 乱码 | 编译期报错（或选错重载） |

一句话收口：**C 是"一定先提升，再靠格式符反推"；C++ 是"根本不提升，靠重载正推"。**

## 常见陷阱

### 陷阱 1：`sizeof('A')` 当数组长度（C/C++ 混编头文件）

```c
#ifdef __cplusplus
static_assert(sizeof('A') == 1, "C++: char");
#else
_Static_assert(sizeof('A') == sizeof(int), "C: int");
#endif
```

同一个头文件被 C 和 C++ 分别编译时，`sizeof('A')` 是**两个不同的值**。混编项目（如 C++ 包装 DPDK/内核头文件）里，**绝不能**用它做数组长度、`static_assert` 之外的任何编译期常量。

### 陷阱 2：以为 `sizeof('x') == 1` 意味着 `'x' + 'x'` 也是 1 字节

**反直觉但实测为 4**。`sizeof` 作用于表达式时看的是**表达式结果的类型**，整数提升已经发生：

```cpp
static_assert(sizeof('x') == 1);        // 孤立字面量
static_assert(sizeof('x' + 'x') == 4);  // 表达式 → int
```

### 陷阱 3：多字符常量的字节顺序（**《C和指针》3.1.6 的 Q4 答案有误**）

```c
'AB'    // 实测 0x4142 = 16706
'xy'    // 实测 0x7879 = 30841
'RIFF'  // 实测 0x52494646
```

clang/gcc 的实现是**第一个字符放在最高字节**（`value = c1<<24 | c2<<16 | c3<<8 | c4`），不是"第一个字符在低字节"。

> ⚠️ 现存的《C和指针》[3.1.6](../../../../01-c-language/02-advanced-pointers-and-memory/ch03-data/3.1-basic-data-types/3.1.6-字符常量的类型陷阱.md) 自测题 Q4 写的是「`'A'` 在低字节 → 0x4241 = 16961」，**与实测相反**，正确值是 **0x4142 = 16706**。而且这个值本来就是**实现定义**，跨编译器不可移植——FourCC 码请改用 `uint32_t` + 显式字节拼接。

### 陷阱 4：`'0'` ≠ `0` ≠ `'\0'`（C/C++ 通用）

| 写法 | 值 | 含义 |
|------|-----|------|
| `'0'` | 48 | 字符"零" |
| `0` | 0 | 整数零 |
| `'\0'` | 0 | 空字符/字符串终止符 |

报文解析：`val = val * 10 + (buf[i] - '0')`，**不要写 `- 48`**（非 ASCII 平台 `'0'` 不一定是 48）。

### 陷阱 5：C++17 → C++20 升级后老代码突然编译失败

老代码里所有 `const char *s = u8"..."`、`printf("%s", u8"...")`、`std::string s = u8"..."` 在 C++20 全部报错。升级编译器时的排查清单：

```bash
# 先把所有断点一次性暴露出来
clang++ -std=c++20 -fsyntax-only $(git ls-files '*.cpp')
# 报错关键词：char8_t
```

### 陷阱 6：`uint8_t` 进日志变成乱码字符

```cpp
uint8_t qty = 200;
LOG << "qty=" << qty;     // 输出 qty=È   ← 不是 200，是 codepage 200 对应的字符
```

`uint8_t` / `int8_t` 就是 `unsigned char` / `signed char`，命中**字符插入器**。行情字段、计数器、枚举只要声明成 `uint8_t`，`cout` 一律按字符打。

```cpp
LOG << "qty=" << +qty;                    // ✅ 一元 + 提升到 int
LOG << "qty=" << static_cast<int>(qty);   // ✅ 显式
```

> 反过来看这也是个特征：`cout << (unsigned short)65` 输出 `65`，`cout << (uint8_t)65` 输出 `A`。
> 同是 1~2 字节整数，一个走数字插入器一个走字符插入器——差别只在**有没有字符插入器精确匹配**。

## HFT / 嵌入式关联

1. **报文魔数**：C++ 里 `'T'` 是 `char`（1 字节），赋给 `uint8_t` 无需转换；C 里是 `int`，赋值发生窄化。**同一份头文件在两种语言下告警行为不同**——混编项目统一用 `0x54U` 这类显式数值更稳。

2. **热路径字符串**：`std::string_view`（16 字节，ptr+len）比 `std::string`（24 字节 + 可能堆分配）更适合行情字段的零拷贝切片。C 侧对应物是 `char * + len`——两种语言的"显式长度"模型是**对齐**的，都不依赖 `'\0'`。

3. **二进制 payload 绝不当字符串**：`char8_t`（C++20）在类型层面把「UTF-8 文本」和「裸字节」分开了，这比 C 的裸 `char` 更安全。但 payload 解析仍应该用 `std::byte`（C++17）或 `uint8_t`，见《C和指针》[9.1 字符串基础](../../../../01-c-language/02-advanced-pointers-and-memory/ch09-strings-characters-and-bytes/9.1-字符串基础.md) 的"两种存储模型"。

4. **`wchar_t` 不可用于网络传输**：macOS/Linux 4 字节、Windows 2 字节，序列化会跨端不一致。跨端一律 UTF-8（`char8_t` / `char`）+ 显式长度。

5. **locale 隔离**：HFT 进程 `std::setlocale(LC_ALL, "C")`，避免 `is*` / `tolower` 受环境影响（C 侧同理，见《C和指针》[9.8 字符操作](../../../../01-c-language/02-advanced-pointers-and-memory/ch09-strings-characters-and-bytes/9.8-字符操作.md)）。

## 自测题

**1（核心）** C++ 里 `char c = 'x'; sizeof(c)` 和 `sizeof('x')` 各是多少？同样的代码用 C 编译呢？

**2（反直觉）** `sizeof('x' + 'x')` 在 C++ 里是多少？为什么和 `sizeof('x')` 不一样？

**3（类型）** C++20 里 `u8'x'` 和 `u8"x"[0]` 是什么类型？C++17 里呢？

**4（升级）** 一段 C++17 代码里有 `const char *p = u8"abc";`，升级到 C++20 会怎样？给出两种修复写法。

**5（字节序）** `'RIFF'` 的值是多少？第一个字符在高字节还是低字节？（提示：先实测，别信任何笔记里的现成答案）

**6（端口性）** 为什么 HFT 代码里不该出现裸 `char` 做数值运算？举出两个 `char` 符号性相反的平台。

**7（两种形态）** `char buf[] = "hello";` 和 `char *p = "hello";` 的 `sizeof` 各是多少？`buf[0]='H'` 和 `p[0]='H'` 分别什么结果？把这两行放进 C++ 编译会怎样？

**8（重载决议）** 下面四行分别输出什么？并说明 `cout << s` 输出数字**到底是不是因为整数提升**。

```cpp
char c = 'A'; short s = 65; unsigned char uc = 65; uint8_t u8 = 65;
std::cout << c << " " << s << " " << uc << " " << u8 << "\n";
```

**9（工程）** 日志里 `LOG << "qty=" << qty` 打印出了 `qty=È` 而不是 `qty=200`。`qty` 是什么类型？给出两种修法。

- `c` → 非成员字符插入器 `operator<<(ostream&, char)`，输出 `A`
- `s` → 成员数字插入器 `operator<<(short)`，输出 `65`
- `uc` / `u8`（`uint8_t` == `unsigned char`）→ 非成员字符插入器，输出 `A`
