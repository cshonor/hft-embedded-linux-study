# 2.2.6 编译单元与链接（翻译单元 TU / ODR / 头文件）

[← 第 2 章](../README.md) · [← 2.2.5 跨文件调用为什么必须 include 头文件](./2.2.5-跨文件调用为什么必须include头文件.md)

## 本节讲什么

把 2.2.4–2.2.5 那套"声明 / 定义 / 头文件"的机制往上抬一层，讲清楚它的**理论骨架**：

- **翻译单元（Translation Unit, TU）** = 一个 `.cpp` 源文件 + 它 `#include` 进来的全部头文件，**经过预处理展开后**得到的那一份完整文本。编译器一次只处理一个 TU。
- **编译单元隔离**：两个 `.cpp` 互相看不见。
- **链接器负责把多个 TU 拼起来**，于是有了**单一定义规则（ODR）**：哪些东西可以在多个 TU 里各写一份，哪些只能有一份。

一句话：**TU 决定"编译器一次能看到多少东西"，ODR 决定"链接器能容忍你重复写几次"。**

## 要点

### 1. 什么是翻译单元（TU）

标准定义：**一个源文件，加上它 `#include` 的所有头文件与源文件，减去条件编译跳过的部分**——也就是**预处理之后、交给编译器本体的那一份文本**。

```cpp
// a.cpp  —— 这就是一个 TU（预处理展开后）
#include <iostream>   // 把整份 iostream 声明文本粘贴进来
#include "b.hpp"      // 把 b.hpp 的文本粘贴进来
int main() { ... }
```

要点：
- **头文件自己不是 TU**。它只在被某个 `.cpp` include 时，成为那个 TU 的一部分。
- **每个 TU 独立编译，互相看不见**：`main.cpp` 不知道 `foo.cpp` 里有什么，全靠头文件里那点声明来"对齐"。
- 这也是 2.2.5 那条结论的底层原因：**跨文件调用必须先有声明**，因为编译器压根不去看对方文件。

### 2. 几个 `.cpp` 就是几个 TU？——三种情况

| 情况 | TU 数 | 说明 |
|---|---|---|
| 两个 `.cpp` 分开编译 | **2** | 各自独立编译出 `.o`，链接器合并 |
| `a.cpp` 里 `#include "b.cpp"` | **1** | b.cpp 的文本被粘贴进 a.cpp，合二为一（**不推荐**：重复定义 + 编译膨胀，见 2.2.5） |
| 条件编译 `#ifdef` 跳过整段 | 仍是 **1** | 只是这段文本没进展开结果 |

> ⚠️ 一条常见误传：**预编译头（PCH）不会改变 TU 数量**。PCH 只是把常用头的解析结果缓存下来加快编译，TU 边界丝毫没动；真正改变 TU 边界的只有 `#include` 展开与条件编译（C++20 Modules 另有一套模块语义）。

### 3. ODR（One Definition Rule）：什么能重复，什么不能

| 类别 | 能否在多个 TU 各写一份定义 | 原因 |
|---|---|---|
| 普通（非内联）函数 / 全局变量 | ❌ 全局只能一份 | 多处定义 → 链接 `duplicate symbol` |
| `inline` 函数 | ✅ 可以（且**必须**在每个用到它的 TU 里可见定义） | 定义被发成 **weak/COMDAT 符号**，链接器去重留一份 |
| 类模板 / 函数模板 | ✅ 同上 | 实例化后同样是 weak 符号去重 |
| 类 / 结构体 / 枚举定义 | ✅ 可以（头文件里放的就是它） | 类型定义不产生符号，但**各 TU 必须完全一致** |
| `static` / 匿名 namespace 里的东西 | ✅ 每个 TU 各一份 | 内部链接，各自独立，互不影响 |

**关键机制**：`inline` 与模板之所以能重复，是因为编译器给它们打上 **weak（弱符号）** 标记，链接器遇到同名弱符号只保留一份。用 `nm` 能亲眼看到：

```
$ clang++ -c i1.cpp -o i1.o && llvm-nm -m i1.o | grep inl
0000000000000020 (__TEXT,__text) weak external __Z3inlv
                                  ^^^^ weak = 可被去重
```

### 4. 本节全部实测（clang 23.1.0，macOS arm64）

| 实验 | 现象 | 结论 |
|---|---|---|
| `clang++ -### main.cpp foo.cpp -o test` | 触发 **2** 次 `-cc1`（每个源文件 1 次） | 2 个 TU |
| 该命令跑完后目录里 `.o` 数 | **0**（`.o` 落在 `/var/folders/.../T/` 临时目录，链接完自动删） | Quiz 答案的坑点 |
| 加 `-save-temps` 再编一次 | 留下 `main.o` `foo.o` | 想看 `.o` 就用它 |
| `a.cpp` 里 `#include "b.cpp"` | 只触发 **1** 次 `-cc1` | 1 个 TU |
| 两个 TU 都写 `int dup(){...}` | `duplicate symbol 'dup()' in: .../d1-*.o, .../d2-*.o` | ODR：普通函数只能定义一次 |
| 两个 TU 都写 `inline int inl(){...}` | 链接 OK，`nm` 见 `weak external __Z3inlv` | inline 走弱符号去重 |
| C++ 里不声明直接调函数 | `use of undeclared identifier` | 无隐式声明（见 2.2.5） |

## HFT / 嵌入式关联

- HFT 引擎按模块拆 `.cpp`，一次构建就是几十上百个 TU 并行编译 → **头文件里多一行无关 include，会被复制进每一个 TU**，这就是"头文件瘦身 / 前置声明 / PCH"这些工程手段存在的理由。
- 模板和 `inline` 大量出现在行情解析、订单簿的头文件里（如 `template <typename T> struct RingBuffer`），它们的定义**必须放在头文件**，否则调用方 TU 看不到定义，只能靠弱符号在别处碰运气。
- 嵌入式裸机同理：启动汇编 + C 文件各自一个 TU，靠链接脚本把段摆到正确地址；`static` 驱动内部函数不进符号表，天然不占全局命名空间。

## 代码自测

<details><summary>Q1：`g++ main.cpp foo.cpp -o test` 这条命令，会产生几个翻译单元、几个 .o 文件？</summary>

**2 个翻译单元、2 个 `.o` 目标文件**（每个 `.cpp` 一个）。
坑点：这一条命令把"编译 + 链接"一起做了，`.o` 是**临时产物**（实测落在 `/var/folders/.../T/d1-*.o` 这类路径），**链接完就被删掉**，所以你在目录里看不见它们。想留住就分开做：
`g++ -c main.cpp -o main.o && g++ -c foo.cpp -o foo.o && g++ main.o foo.o -o test`（或一次性加 `-save-temps`）。
</details>

<details><summary>Q2：`a.cpp` 里写了 `#include "b.cpp"`，然后只编译 a.cpp，算几个 TU？为什么工程上不这么干？</summary>

**1 个 TU**。预处理把 b.cpp 的文本整份粘贴进 a.cpp，编译器眼里只有一份文本。
不这么干的原因：① 定义重复风险——若 b.cpp 也被单独编译，同一函数就有两份定义；② 编译膨胀——改一次 b.cpp，所有 include 它的 TU 都要重编；③ 破坏"头文件放声明、源文件放定义"的契约（见 2.2.5）。
</details>

<details><summary>Q3：为什么 inline 函数和模板的定义要写在头文件里？为什么普通函数不行？</summary>

inline / 模板必须在**每一个用到它的 TU** 里看到完整定义（否则无法内联 / 无法实例化），而头文件正是被每个 TU include 的公共文本，所以定义放头文件。
它们被允许重复，是因为编译器把它们发成 **weak（弱符号）**，链接器去重只留一份（实测 `nm` 显示 `weak external`）。
普通函数没有这个待遇：两个 TU 各写一份定义 → `duplicate symbol` 硬错误。所以普通函数"声明放 .h、定义放唯一一个 .cpp"。
</details>

<details><summary>Q4：预编译头（PCH）会让两个 cpp 合并成一个 TU 吗？</summary>

不会。PCH 只是把常用头文件的解析结果缓存成二进制，让后续 TU 解析更快，**TU 的边界完全没变**，仍然每个 `.cpp` 一个 TU。真正改变 TU 的是 `#include` 展开和条件编译。
</details>
