# 13.5 五个特殊成员函数与可移动性

## 本节讲什么

把前面 13.1–13.3 讲过的内容收拢成一张总图：**五个特殊成员函数**（析构、拷贝构造、拷贝赋值、
移动构造、移动赋值）——什么语法动作触发哪一个、编译器什么时候自动生成/不生成、
以及它们如何组合出类型的「可拷贝/可移动四分类」。
这篇是查阅用的总表 + 实测验证，细节原理回到 13.1（拷贝控制）、13.2（三/五法则）、13.3（移动语义）。

## 一、五个函数与触发时机

| # | 函数 | 签名（以 `class T` 为例） | 触发动作 |
|---|------|--------------------------|----------|
| 1 | 析构 | `~T()` | 对象寿命结束：出作用域、`delete`、容器清除元素 |
| 2 | 拷贝构造 | `T(const T&)` | **用左值造新对象**：`T b = a;` / `T b(a);` / 按值传参、按值返回 |
| 3 | 拷贝赋值 | `T& operator=(const T&)` | **左值赋给已有对象**：`b = a;`（b 已存在） |
| 4 | 移动构造 | `T(T&&) noexcept` | **用右值造新对象**：`T b = std::move(a);` / 临时量、vector 扩容搬元素 |
| 5 | 移动赋值 | `T& operator=(T&&) noexcept` | **右值赋给已有对象**：`b = std::move(a);` |

两组正交的分类标准，记这个就不会混：

- **构造 vs 赋值**：目标对象刚出生（构造）还是已存在要覆盖旧值（赋值）。
  `T b = a;` 看着有 `=`，实际是**构造**（b 此刻才出生）——新手最容易判错的地方。
- **拷贝 vs 移动**：源是左值（还有名字、还要用）还是右值（将亡值 / `std::move` 显式放弃）。
  这是重载决议在管：`const T&` 绑一切，`T&&` 优先绑右值——**右值优先选移动，移动不存在才退化为拷贝**。

```cpp
Traced a("a");
Traced b = a;            // 拷贝构造（新对象 + 左值源）
b = a;                   // 拷贝赋值（已有对象 + 左值源）
Traced c = std::move(a); // 移动构造（新对象 + 右值源）
c = std::move(b);        // 移动赋值（已有对象 + 右值源）
```

**容易被忽略的隐式触发点**：按值传参（构造）、按值返回（构造，C++17 起纯临时量有保证的省略）、
`vector` 扩容搬元素（移动构造，且只有 `noexcept` 才用移动，见 13.3）、
`std::thread` 内部存副本（构造）、lambda 按值捕获（构造）。

## 二、编译器生成规则（决定「能不能」的那张表）

| 你声明了 | 拷贝构造 | 拷贝赋值 | 移动构造 | 移动赋值 | 析构 |
|----------|:--:|:--:|:--:|:--:|:--:|
| 什么都没 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 析构 | ✅(deprecated) | ✅(deprecated) | ❌ | ❌ | — |
| 拷贝构造 | — | ✅ | ❌ | ❌ | ✅ |
| 拷贝赋值 | ✅ | — | ❌ | ❌ | ✅ |
| 移动构造 | delete | delete | — | ❌ | ✅ |
| 移动赋值 | delete | delete | ❌ | — | ✅ |

读法三条：

1. **声明了拷贝（任一）或析构 → 移动全家不生成**。规则意图：你要自定义拷贝/析构，
   多半在管资源，编译器不敢替你按位移动（会双重释放）。
2. **声明了移动（任一）→ 拷贝全家被 delete**。意图：移动语义通常意味着独占资源，不该能拷。
3. 想精确控制就五个全写 `= default` / `= delete`，别靠记这张表（写代码时），
   但读别人的类、分析「为什么这个类型不能 move」时必须会查这张表（读代码时）。

历史脉络：**Rule of Three**（C++98：析构+拷构+拷赋，管资源就三个全写）
→ **Rule of Five**（C++11：加移动两个）
→ **Rule of Zero**（现代提倡：资源交给 `unique_ptr`/`vector`/`string` 成员，五个一个都不写）。

## 三、四分类：五个函数的组合结果

| 类别 | 判定 | 代表 | 典型用途/动机 |
|------|------|------|--------------|
| 可拷可移 | 五个都有 | `int`、`std::string`、`std::vector` | 值语义默认款 |
| 只移（move-only） | 拷 delete、移有 | `unique_ptr`、`thread`、`future`、`fstream` | 独占资源，拷贝=双重释放 |
| 只拷（退化） | 移没生成 | 声明了析构/拷贝但没写移动的类 | 历史代码；`std::move` 静默退化为拷贝 |
| 都不可 | 拷移皆 delete | `mutex`、`atomic`、`scoped_lock` | 内部状态绑定地址（等待队列），挪窝即崩 |

**「只拷」类是陷阱高发区**：它没犯任何错，只是没跟上 C++11——
你对它写 `std::move(x)`，编译器不报错，**静默走拷贝构造**（const& 能吃右值）。
性能上你以为 O(1) 实际 O(n)。见下面实测。

## 四、实测验证（examples/13.3-move-degradation.cpp，clang++ 23.1 跑通）

运行输出（节选）：

```
== ① 五个函数何时被调用 ==
  [拷贝构造] a_copy <- a     [拷贝赋值] a_copy <- a
  [移动构造] a（只搬指针）    [移动赋值] a
  [析构] a / [析构]（空）     <- moved-from 对象仍要析构，且内容已空

== ② 声明析构后，std::move 退化成拷贝 ==
  HasDtor: [拷贝构造] 被调用   <- 写的是 std::move，走的是拷贝

== ③ 四分类 static_assert 全部通过 ==
```

三个实测出的坑：

1. **`std::is_move_constructible_v<T>` 会说谎**：对「声明了析构但没移动」的类型返回 `true`——
   它检查的是「能不能用右值构造」，拷贝构造的 `const&` 也能吃右值，所以通过。
   「可移动构造」≠「生成了移动操作」。拆穿方法：`is_trivially_move_constructible`（平凡性）
   或运行期打日志看实际走了哪个函数。
2. **用户声明过的 `= default` 不算平凡（trivial）**：`AllDefault` 五个全 `= default`，
   `is_trivially_move_constructible_v` 仍为 false。trivial 要求**无任何用户声明**，
   纯 `struct PlainOld { int x; };` 才是。
3. **moved-from 对象照常析构**：日志里被移动过的对象析构时内容为空——
   所以移动操作必须把源对象置于「可安全析构」状态（指针置 nullptr 等），
   析构函数也必须能处理空壳。

## 五、HFT 关联

- **热路径只要 move-only + noexcept 移动**：独占所有权（`unique_ptr<Packet>`）+
  O(1) 指针转移 + 不抛异常（`vector` 才敢用移动），三个条件一起才拿到零拷贝。
- **「只拷」退化类是隐形性能税**：老代码里声明了析构的资源类，`std::move` 静默变深拷贝，
  火焰图上表现为「莫名其妙的 memcpy」——用本节的 type traits 或日志法审计一遍。
- **`mutex`/`atomic` 都不可动**决定了同步原语只能以指针/引用/`std::ref` 共享，
  这也是线程间传参决策链（CCiA 2.2 笔记）的底层约束。

## 代码自测

### Q1: 下面每行各调用哪个函数？

```cpp
std::string a = "x";
std::string b = a;
b = std::move(a);
auto f = [](std::string s) { return s; };
std::string c = f(b);
```

<details>
<summary>答案与复习指引</summary>

1. `std::string b = a;` —— **拷贝构造**（有 `=` 但 b 是新对象）。
2. `b = std::move(a);` —— **移动赋值**（b 已存在 + 右值源）。
3. `f(b)` 传参 —— **拷贝构造**（按值传参 + 左值源）；
   `return s;` 返回 —— **移动构造**（局部变量返回时按右值处理）。
4. `c` 的初始化 —— C++17 起返回纯临时量有保证的省略，这里 `f(b)` 是临时量，
   大概率连移动构造都被省掉（ guaranteed copy elision ）。

复习：先判「构造还是赋值」（目标是否新生），再判「拷贝还是移动」（源是否右值）。
</details>

### Q2: 这个类能不能 `std::move`？`std::move` 之后会发生什么？

```cpp
class File {
    int fd;
public:
    explicit File(int fd_) : fd(fd_) {}
    ~File() { if (fd >= 0) close(fd); }
};
File a(3);
File b = std::move(a);
```

<details>
<summary>答案与复习指引</summary>

**能编译，但走的是拷贝构造**——声明了析构 → 移动不生成（规则 1），
`std::move` 的右值被编译器生成的拷贝构造（const&）接住。

后果：a 和 b 持有**同一个 fd**，析构时 `close` 两次（double close）——
这正是 Rule of Three/Five 要防的事故。正确写法：五个全管起来
（移动构造里搬 fd 并把源置 -1），或直接禁拷贝改 move-only。

复习：「只拷」退化类 + 资源管理 = 隐形炸弹。审计信号：类有析构却没有移动操作。
</details>

### Q3: 为什么 `std::mutex` 连移动都不行？

<details>
<summary>答案与复习指引</summary>

mutex 的内部状态（等待队列、内核 futex 地址）**记录着对象自己的地址**——
别的线程正等在「这个地址」上。一旦移动（对象换地址），等待者全部丢失，直接崩。
所以它把拷贝和移动全部 `= delete`（都不可分类）。

推论：含 mutex 成员的类也自动都不可动（成员的不可动会传染）。
想搬动含 mutex 的对象，得把 mutex 放进 `unique_ptr` 间接持有。

复习：「都不可」类型的动机是**地址即身份**；共享它们只能传指针/`std::ref`。
</details>
