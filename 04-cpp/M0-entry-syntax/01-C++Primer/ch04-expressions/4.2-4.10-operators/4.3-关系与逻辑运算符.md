# 4.3 关系与逻辑运算符

## 本节讲什么

关系比较与逻辑组合；**短路求值**是核心考点。

## 关系运算符 `< <= > >= == !=`

- 结果类型为 **`bool`**（打印时可能显示 `0`/`1`）
- **错误写法**：`a < b < c` 等价 `(a < b) < c`，不是数学上的「介于两者之间」

```cpp
int a = 1, b = 2, c = 3;
// if (a < b < c)  // 先 (a<b)→true→1，再 1<c，逻辑常错
if (a < b && b < c)  // ✅
```

## 逻辑运算符 `!` `&&` `||`

| 运算符 | 含义 | 短路 |
|--------|------|------|
| `!` | 逻辑非，优先级在 `&&`/`||` 之上 | — |
| `&&` | 与 | 左侧为 **false**，右侧**不执行** |
| `||` | 或 | 左侧为 **true**，右侧**不执行** |

```cpp
if (b != 0 && a / b) { /* 左侧假则不算 a/b，防除零 */ }
```

**注意**：位运算 `&` `|` **没有**短路（见 [4.8](./4.8-位运算符.md)）。

## 和 C 的区别（关系/逻辑运算符：C99 起几乎一致，C++ 多了 `bool` 类型）

| 对比点 | C（C89） | C（C99+） | C++ |
|--------|----------|-----------|------|
| 关系运算符 | ✅ 一致 | ✅ 一致 | ✅ 一致 |
| `&&` `\|\|` `!` | ✅ 一致 | ✅ 一致 | ✅ 一致 |
| 短路求值 | ✅ | ✅ | ✅ 一致 |
| 结果类型 | `int`（0/1） | `bool`（_Bool） | `bool` |
| `true`/`false` 关键字 | 无 | `<stdbool.h>` 引入 | 原生关键字 |
| `a < b < c` 坑 | ✅ 同样错 | ✅ 同样错 | ✅ 一致 |

**给 C 程序员的关键提醒：**
1. **C89 的关系/逻辑运算符结果是 `int`（0/1）**，C99 引入 `_Bool` 和 `<stdbool.h>` 后才有 `bool`。C++ 从一开始就有原生 `bool` 类型，`true`/`false` 是关键字。但**运算符语义完全一致**——短路、优先级、`a < b < c` 坑都一样。
2. **短路求值两边一模一样**——`b != 0 && a/b` 防 除零在 C 和 C++ 都有效。C 程序员的肌肉记忆直接用。
3. **C++ 里 `bool` 能隐式转 `int`**（`true→1`、`false→0`），但反过来 `int` 转 `bool`（非 0→true、0→false）。C89 里没有 `bool`，用 `int` 代替，习惯一致。

## 底层实现与实测

> 以下均为本机实测（Apple clang 23.1.0，arm64，`-std=c++17 -O2`）。短路的价值不在"省一条指令"，在**能不能跳过一整段计算**。

### 实测 1：短路的证据——数一数右侧被调了几次

```cpp
bool left_false(); bool left_true(); bool right_side();   // 各自 ++calls
left_false() && right_side();    // calls = 1   ← 右侧没执行
left_true()  || right_side();    // calls = 1   ← 右侧没执行
left_false() &  right_side();    // calls = 2   ← 位运算两侧都执行
```

这就是 `p != nullptr && p->x == 5` 能防崩溃、而 `p != nullptr & p->x == 5` 会崩的物理原因。

### 实测 2：`a < b < c` —— 编译器现在直接报错

```console
error: chained comparison 'X < Y < Z' does not behave the same as a mathematical expression [-Wparentheses]
```

clang 把链式比较当成**错误**（不是警告）。拆开写成 `(a < b) < c` 才编得过，实测：

- `a=1, b=2, c=0` → `(a<b)<c` = **0**，`a<b && b<c` = 0（这次碰巧一致）
- `a=5, b=10, c=3` → `(a<b)<c` = **1**：`(5<10)` 得 `true` 提升成 `1`，`1 < 3` 为真——而数学上 5 根本不在 (10, 3) 之间

**这就是最危险的地方：它（拆开写时）不报错、也不崩溃，只是安静地给出错误答案。**

### 实测 3：短路值 5 倍性能——把便宜的判断放前面

1000 万次循环，条件一是恒 false 的便宜检查，条件二是 200 次乘加的昂贵检查：

| 写法 | 实测（1000 万次） |
|---|---|
| `cheap && expensive(i)` | **9.1 ms** |
| `expensive(i) && cheap` | **49.1 ms** |

**5.4 倍。** 短路是唯一能"不执行右边代码"的运算符——这也是为什么防御性检查（`ptr && ptr->valid`）要放左边，以及为什么 HFT 代码里会把快速的 reject 条件排在最前。

### 实测 4：`&&` 不一定生成跳转指令

```cpp
bool f_int(int a, int b) { return a && b; }
```

```asm
f_int(int, int):
    cmp  w0, #0
    ccmp w1, #0, #4, ne      ; 条件比较：只有 a!=0 时才比较 b
    cset w0, ne
    ret
```

ARM64 有 `ccmp`（条件比较），clang 用它把"短路"实现成**无分支**代码。而两个 `bool` 参数做 `a && b` 与 `a & b`，汇编**完全相同**（都是一条 `and`）——因为 `bool` 只有 0/1，两者数学等价。

**结论**：`&&` 与 `&` 的差别**只在求值（短路）**，不在生成的指令数。别为了"省分支"把 `&&` 改成 `&`——那会丢掉短路保护，收益却是零。

### 实测 5：`bool` 的几个数字

```
sizeof(bool) = 1
true + true  = 2        ← bool 隐式提升成 int 参与算术
```

`bool` 是整数类型，会隐式转 `int`——所以 `flags += is_valid` 这类写法合法（把布尔当计数用），但也容易掩盖意图。

## HFT / 嵌入式视角

- **把最便宜、最可能失败的条件排在最前**：实测 3 的 5.4 倍就是排序的收益。风控链（余额 → 限额 → 价格带 → 复杂校验）按"便宜 + 高拒绝率"排序。
- **短路可以省掉整个子系统调用**：日志里 `if (log_enabled && build_expensive_message())` 是标准写法；反过来写等于每次都构造消息。
- **别用 `&`/`|` 替代 `&&`/`||` 做"优化"**（实测 4）：汇编一样，还丢了短路。
- **链式比较一定要拆**：`low <= price && price <= high`。clang 现在会拦，但移植的老代码和其它编译器未必。
- **浮点比较不在此列**：`==` 对浮点基本无效，要用 `fabs(a-b) < eps`；HFT 的定点价格用整数比较，反而没这个问题。

## 常见错误

### 1. `a < b < c` 不是"介于两者之间"

```cpp
if (a < b < c)   // 等价 (a < b) < c
```

`a < b` 先算得 `bool`（0 或 1），再和 `c` 比。若 `a=1, b=2, c=0`，`1<2` 得 `true`（1），`1<0` 得 `false`——但数学上 1 不在 (2, 0) 区间。**正确写法**：`a < b && b < c`。C 和 C++ 都有这个坑。

### 2. `&` 误用为 `&&`

```cpp
if (p != NULL & *p == 5)   // ❌ 先算 *p，p 为 NULL 时崩溃
```

`&` 是位与，**没有短路**——两侧都求值。`p != NULL` 为 false 时仍会算 `*p`，解引用 NULL 崩溃。**用 `&&`** 才短路。C 程序员也踩这个，C++ 同样坑。

### 3. `==` 写成 `=`

```cpp
if (x = 5)   // ❌ 赋值，不是比较，永远为真（5 非 0）
```

经典 C 坑，C++ 也有。**防范**：
- C 习惯把常量放左边：`if (5 == x)`（写成 `5 = x` 编译报错）
- C++ 习惯用 `const` 或 `constexpr`，编译器会警告某些 `=` 误用
- 编译器开 `-Wall` / `/W4`，会警告 `if (x = 5)`

## 自测题

**1. 选择题**　`a < b < c` 在 C++ 中等价于：

- A. `a < b && b < c`（数学上的"介于两者之间"）
- B. `(a < b) < c`（先比较得 bool，再和 c 比）
- C. `a < (b < c)`
- D. 编译错误

<details><summary>答案</summary>

**B**。`<` 左结合，`a < b < c` 等价 `(a < b) < c`。先算 `a < b` 得 `bool`（0/1），再和 `c` 比较。C 也是同样行为。要"介于两者之间"写 `a < b && b < c`。

</details>

**2. 判断题**　`b != 0 && a / b > 1` 中，若 `b == 0`，`a / b` 不会被计算。

<details><summary>答案</summary>

**对**。`&&` 短路求值——左侧 `b != 0` 为 false 时，右侧 `a / b > 1` 不求值，避免除零 UB。C 和 C++ 都保证短路。这是用 `&&` 替代 `if` 防御的常见技巧。

</details>

**3. 踩坑题**　下面这段代码想"指针非空且值为 5 才执行"，哪里有问题？

```cpp
int* p = get_ptr();
if (p != NULL & *p == 5) {
    do_something();
}
```

<details><summary>答案</summary>

**用了 `&`（位与）而不是 `&&`（逻辑与）**。`&` 没有短路——两侧都求值。`p != NULL` 为 false 时仍会算 `*p == 5`，解引用 NULL 指针是 UB（可能崩溃）。

**修复**：`if (p != NULL && *p == 5)`，用 `&&` 短路。或更现代：`if (p && *p == 5)`（指针在条件上下文隐式转 bool）。

C 程序员也踩这个——`&` 和 `&&` 的区别两边一样。

</details>

**4. 应用题**　HFT 代码要"订单有效（qty > 0）且价格在合理区间（low <= price <= high）才发单"，用一行表达式写。

<details><summary>答案</summary>

```cpp
if (order.qty > 0 && low <= order.price && order.price <= high) {
    send_order(order);
}
```

要点：
- `&&` 短路：qty <= 0 时后面不算（虽然这里没副作用，但是好习惯）
- `low <= price && price <= high` 拆成两个比较，不用 `low <= price <= high`
- 用 `&&` 连接三个条件

C 等价写法一模一样：`if (order.qty > 0 && low <= order.price && order.price <= high)`。

</details>

**5. 判断题**：为了少一次分支跳转，把 `if (p != nullptr && p->x == 5)` 改成 `if (p != nullptr & p->x == 5)` 能提速。

<details><summary>答案</summary>

**错，而且很危险。**

1. **安全**：`&` 不短路，`p` 为空时照样解引用 `p->x` → 崩溃（实测：`false & right()` 的调用计数是 2，右侧照样执行）。
2. **性能**：实测两个 `bool` 做 `a && b` 与 `a & b` 生成的汇编**完全相同**（一条 `and`）；即使操作数是 `int`，clang 也用 `cmp + ccmp + cset` 把 `&&` 做成无分支。**收益为零，风险是崩溃。**

</details>

**6. 应用题**：风控要依次检查 4 个条件：① 账户已登录（一次布尔读）② 资金充足（查缓存 map）③ 价格在当前档位（浮点区间比较）④ 历史违约评分（查库 + 计算，约 50 μs）。要求：给出条件排列顺序并说明理由；再指出 `low <= price <= high` 该怎么写。

<details><summary>答案</summary>

```cpp
if (logged_in                                   // ① 最便宜、拒绝率可能最高
    && capital_enough(account)                  // ② 内存查表，纳秒级
    && low <= price && price <= high            // ③ 拆成两个比较，别写 low <= price <= high
    && credit_score_ok(account)) {              // ④ 最贵，放最后，绝大多数单子根本走不到
    send_order(order);
}
```

**理由**：`&&` 短路（实测 1：右侧调用计数为 0），条件顺序直接决定 CPU 干了多少活。实测 3 把便宜条件前置 vs 后置差 **5.4 倍**（9.1 ms vs 49.1 ms / 1000 万次）。把 50 μs 的查库放最后，意味着 99% 的单子在前面就被拒掉了，永远碰不到它。

**区间写法**：必须拆成 `low <= price && price <= high`。写 `low <= price <= high` 在 clang 下直接 `error: chained comparison`；即使拆开写 `(low <= price) <= high`，也是拿 `bool`（0/1）去和价格比，逻辑全错（实测：`a=5, b=10, c=3` 时 `(a<b)<c` 得 1）。

</details>
