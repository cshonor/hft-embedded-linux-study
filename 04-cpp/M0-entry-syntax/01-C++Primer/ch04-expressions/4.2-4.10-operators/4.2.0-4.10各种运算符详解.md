## 关键通用规则

### 左值 / 右值（与赋值、自增相关）

- **左值**：有身份、可取地址；能放赋值号左侧、前置 `++`、`对象.成员`
- **右值**：临时值；后置 `++` 返回临时、多数算术/逻辑运算结果是右值

### 短路 vs 非短路

- **`&&` `||`**：短路求值（左侧能定结果则不算右侧）
- **位运算 `&` `|` `^`**：**无**短路，两侧都求值

### 优先级速记（粗粒度）

一元 > 算术 > 移位 > 关系 > 逻辑 > 赋值 > 逗号（完整表见 4.12）

### 教材编码规范

- 自增优先 **前置 `++i`**
- 位运算只用 **`unsigned`**
- 复杂表达式**多加括号**
- **少滥用**逗号运算符

类型不一致时的转换见 [4.11 类型转换](../4.11-type-conversions/4.11-类型转换.md)。

## 为什么要"这么多运算符"（动机）

运算符不是越多越好，每一类都是为了解决一类具体问题而存在。把它们按"解决什么问题"重新排一遍，比背优先级表有用得多：

| 运算符族 | 它解决什么问题 | 没有它你得怎么写 |
|----------|----------------|------------------|
| 算术 `+ - * / %` | 数值计算 | 全是函数调用，读起来像汇编 |
| 关系/逻辑 `< == && !` | 条件判断、短路 | 分支 + 临时变量 |
| 赋值 `= +=` | 修改状态 + 顺手返回结果 | 每次多写一行 |
| 自增 `++ --` | 迭代、游标前进 | `i = i + 1` |
| 成员访问 `. ->` | 取结构/对象字段 | 偏移量硬算 |
| 条件 `?:` | **表达式**里做二选一 | 只能拆成 `if-else` 语句 |
| 位运算 `& \| ^ ~ << >>` | 打包 Flags、寄存器、二进制协议 | 乘除法 + 掩码结构体 |
| `sizeof` | 跨平台拿尺寸 | 硬编码 4 / 8，换平台就崩 |
| 逗号 `,` | 一处需要"按顺序做两件事" | 拆成多条语句 |

**理解要点**：C++ 的运算符体系 = C 的全部 + 类类型可重载的那部分。基础运算符的**语义、优先级、结合律**跟 C 一字不差，所以 C 程序员在这章几乎不需要"重新学"，只需要记住三处 C++ 才有的差异（`?:`/赋值可作左值、C++17 求值顺序、`sizeof` 不求值）。

## 底层实现与实测

> 环境：Apple clang 23.1.0，arm64-apple-darwin，`-std=c++17`。可跑版本见文末例子。

### 1. 算术高于移位：`1 << 2 + 3` 是 32 不是 7

```cpp
int r1 = 1 << 2 + 3;      // 实测 32，等价 1 << (2+3)
```

clang 直接给出警告（这就是别背表、靠编译器的理由）：

```
warning: operator '<<' has lower precedence than '+'; '+' will be evaluated first
         [-Wshift-op-parentheses]
```

### 2. 位与低于相等：测位最经典的错写

```cpp
unsigned flags = 0x02;
flags & 0x01 == 0      // 实测 0 —— 被解析成 flags & (0x01 == 0)，即 0x02 & 0
(flags & 0x01u) == 0   // 实测 1 —— 这才是"低 1 位为 0"
```

```
warning: & has lower precedence than ==; == will be evaluated first [-Wparentheses]
```

这个坑在 HFT 里特别致命：**它不崩、不报错，只是永远返回 0**，风控条件静默失效。

### 3. 结合性：`-` 左结合，`=` 与一元右结合，`*p++` 是 `*(p++)`

```cpp
a - b - c                 // 实测 65，等价 (a-b)-c；a-(b-c) 是 75
x = y = z                 // 实测 x=300 y=300 z=300，等价 x = (y = z)
int u = 5; -(u++)         // 实测 -5，等价 -(u++)，不是 (-u)++
int* p = arr; *p++        // 实测取到 arr[0]，之后 p 指向 arr[1]
```

后自增高于解引用，是 `*p++` 能当"取当前值并前进"用的全部原因。

### 4. `&` 高于 `|`：加括号能改语义

```cpp
1 | 4 & 2      // 实测 1（= 1 | (4&2) = 1 | 0）
(1 | 4) & 2    // 实测 0（= 5 & 2）
```

注意：**括号改变的是语义，不是性能**。加括号在 `-O2` 下是零成本的（编译器本来就按优先级树生成代码）——所以"多加括号"只有收益没有代价。

### 5. C++17 修好了一个老 UB：`i = i++`

```cpp
int i = 5;
i = i++;        // C++17 起良定义，实测 i = 5
```

实测证据是**警告本身**：

| 标准 | 编译 `i = i++` | 结果 |
|------|----------------|------|
| `-std=c++11` | `warning: multiple unsequenced modifications to 'i' [-Wunsequenced]` | UB，结果不确定 |
| `-std=c++17` | **无警告** | 良定义，右操作数先求值 |

C++17 的规定：简单赋值 `E1 = E2` 中，**右操作数先于左操作数求值**，赋值本身最后发生。所以 `arr[k] = (k = 2)` 在 C++17 下保证写 `arr[2]`（实测 `k=2, arr[2]=2`），在此之前是 UB。

### 6. 但函数实参的求值顺序，C++17 仍未指定

```cpp
int n = 0;
auto bump = [&]() { return ++n; };
printf("%d %d", bump(), bump());   // 实测 1 和 2（本编译器左到右）
```

1 和 2 的顺序**不是标准保证的**，只是 clang 恰好这么排。GCC 可能反过来。任何依赖实参求值顺序的代码都是 bug，不管用哪个标准。

> 对比：逗号运算符 `,` 是**唯一被标准保证从左到右**的运算符，这也是它至今没被废弃的原因。

## HFT / 嵌入式视角

1. **优先级错误是"静默失效"类 bug 的头号来源**。`flags & 0x01 == 0` 不崩、不报警告（`-Wall` 下才报），只是永远 false。风控、权限校验、协议解析里出现这种写法，等于检查根本没生效。**规矩：位运算一律带括号，`-Wall -Wextra` 常开。**
2. **括号是零成本的**。`-O2` 下加括号不会多一条指令（实测第 4 条只有语义差、没有性能差）。可读性收益 100%，性能代价 0%。热路径也别省括号。
3. **C++17 的求值顺序保证要善用**：`arr[k] = (k = 2)` 这类"边算下标边改状态"的写法现在有定义了，但**可读性极差**，仍然应该拆成两行。标准保证 ≠ 该这么写。
4. **别依赖实参求值顺序**。`f(order_id(), seq_no())` 这种，若两个函数有共享状态就是雷。嵌入式驱动里 `read_reg(addr++, read_reg(addr++))` 更是灾难。
5. **嵌入式寄存器操作必须显式类型**：`1u << n` 而不是 `1 << n`。实测 `1 << 31` 是 UB（给出 `-2147483648`），`1u << 32` 也是 UB（移位量 ≥ 位宽）。ARM 上这类 UB 在不同优化级别可能给出不同值。

## 代码自测

**题目 1：** 以下代码在 C 和 C++ 中的行为有什么不同？
```cpp
int x = 10;
auto y = x;  // C++ 合法，C 合法吗？
```

<details>
<summary>参考答案</summary>

`auto` 在 C 中不存在（C23 才引入）。C++11 起 `auto` 用于类型推导。C 中需要显式写类型。C++ 的 `auto` 推导规则：去掉引用和 const（除非用 `auto&`）。C++14 起函数返回类型可用 `auto`，C++20 起 `auto` 可用于函数参数（缩写函数模板）。

</details>

**2. 判断题**　`flags & 0x01 == 0` 和 `(flags & 0x01) == 0` 等价。

<details><summary>答案</summary>

**不等价**，而且这是最危险的一类 bug——**它不崩、不报错，只是静默算错**。

`==` 优先级高于 `&`，所以 `flags & 0x01 == 0` 实际是 `flags & (0x01 == 0)`。而 `0x01 == 0` 恒为 `false`（0），于是整个表达式恒等于 0——**无论 flags 是什么值，条件永远为假**。

实测（`flags = 0x02`）：`flags & 0x01 == 0` → 0；`(flags & 0x01) == 0` → 1。

`-Wall` 下 clang 会报 `warning: & has lower precedence than ==`——**这条警告必须当 error 处理**。位运算一律加括号。

</details>

**3. 应用题**　你接手一段 HFT 风控代码：

```cpp
if (order.qty > 0 && price & 0xFF == 0 && check_credit(account)) {   // 约 50 μs
    send_order(order);
}
```

指出三处问题并改写。

<details><summary>答案</summary>

**问题 1（正确性）**：`price & 0xFF == 0` 被解析成 `price & (0xFF == 0)`，恒为 0 → 整个条件恒 false → **永远不发单**。必须写 `(price & 0xFF) == 0`。

**问题 2（语义可疑）**：`price` 是价格却用位掩码判断，大概率本来想写的是区间判断 `low <= price && price <= high`。位运算只该用在整数 Flags / 协议字段上，不该用在价格上。

**问题 3（性能）**：`check_credit(account)`（约 50 μs）放在 `&&` 链的最后一位才对——这里恰好已经是最后，但如果把它挪到最前面，每个单子都要付 50 μs。实测便宜条件前置 vs 后置在 1000 万次循环下差 **6.8 倍**（3.9 ms vs 26.6 ms）。

**改写**：

```cpp
if (order.qty > 0                                   // 最便宜，先算
    && (price & 0xFF) == 0                          // 加括号；如本意是区间则改 low<=price && price<=high
    && check_credit(account)) {                     // 最贵，放最后，绝大多数单子根本走不到
    send_order(order);
}
```

**要点**：`&&` 短路 → 条件顺序 = CPU 干活量；位运算必带括号。

</details>
