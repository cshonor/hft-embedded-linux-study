# 4.5 自增自减

## 本节讲什么

`++` `--` 前置与后置的区别——**重点考点**。

## 前置 `++i` / `--i`（推荐）

- **先**自增/自减，**再**返回修改后的对象
- 返回**左值**（可继续链式使用）
- **无**多余临时副本，性能更好

## 后置 `i++` / `i--`

- **先**返回**原值**的副本（右值），**再**修改变量
- 多一次临时，热路径避免

```cpp
int i = 10;
i += 2;      // i = 12
++i;         // i = 13
int j = i++; // j = 13，i 变为 14
// cout << i << " " << j;  →  14 13
```

## 完整示例解析

```cpp
#include <iostream>

int main() {
    int i = 10;
    i += 2;    // 复合赋值，i = 12
    ++i;       // 前置自增，i = 13
    int j = i++;  // 后置：j 得 13，i 变 14
    std::cout << i << " " << j << std::endl;  // 14 13
    return 0;
}
```

## 禁忌

**同一表达式中对同一变量多次自增/自减** → **未定义行为**：

```cpp
// int k = i++ + i++;  // ❌ UB
```

教材建议：默认写 **前置 `++i`**。

## 为什么要分前置/后置（动机）

因为**返回值不同**，不是因为"修改时机不同"（两者对变量本身的修改完全一样，都加 1）：

| | 返回值 | 实现 |
|---|---|---|
| 前置 `++i` | 修改后的**左值引用** | `i += 1; return i;` |
| 后置 `i++` | 修改**前**的**副本**（右值） | `tmp = i; i += 1; return tmp;` |

后置必须"先留一份旧值再改"，所以**天然多一次拷贝**。这就是"推荐 `++i`"的全部理由——不是风格问题，是**少一次拷贝**。

C++ 用**参数个数**区分两个重载（这是语言里唯一的"哑元参数"约定）：

```cpp
T& operator++();      // 前置，无参
T  operator++(int);   // 后置，int 哑元（值永远不被使用，只为区分签名）
```

## 底层实现与实测

> 环境：Apple clang 23.1.0，libc++，`-std=c++17`。可跑版本见文末例子。

### 1. `-O2` 下前置/后置生成**完全相同**的汇编

把两个只有 `++it` / `it++` 之差的函数编到汇编：

```cpp
long sum_pre (const std::vector<int>& v){ long s=0; for(auto it=v.begin();it!=v.end();++it)  s+=*it; return s; }
long sum_post(const std::vector<int>& v){ long s=0; for(auto it=v.begin();it!=v.end();it++) s+=*it; return s; }
```

| | 指令数 | 差异 |
|---|--------|------|
| `++it` 版本 | **83** | — |
| `it++` 版本 | **83** | **逐条完全相同**（除符号名） |

实测 1000 万次迭代遍历：`++it` 1.402 ms vs `it++` 1.402 ms，**差 0.0003 ms**。

**原因是优化器把后置那份"没人用的副本"直接消除了**。所以"对 `vector` 迭代器一定要用 `++it`"这个流传很广的建议，在 `-O2` 下**是过时的**——生成的代码一模一样。

### 2. 那后置什么时候真的慢？三种情况

| 场景 | 实测 |
|------|------|
| **副本被使用**（`auto old = it++;`） | 必须真的构造副本，无法消除 |
| **优化器看不透的类类型**（跨 TU、`-O0`、虚函数） | 见下表 |
| **`-O0` 构建** | 见下表 |

重型类 `Heavy`（`sizeof == 64`，后置要拷 64 字节再丢弃），500 万次，`-O0`：

| | 耗时 |
|---|------|
| `++h`（前置） | **53.4 ms** |
| `g++`（后置） | **62.0 ms** |
| 比值 | 后置**慢 16%** |

对 `int` 用 `volatile` 强制每次真做（2000 万次）：`++a` 与 `b++` 的比值在多次运行里是 **0.82 ~ 1.58 倍来回摆**——**差距在噪声内**。

### 3. 类类型重载：返回引用 vs 返回副本（实测 `decltype`）

```cpp
struct Counter {
    int v;
    Counter& operator++()    { ++v; return *this; }              // 前置
    Counter  operator++(int) { Counter t = *this; ++v; return t; } // 后置
};
```

| 表达式 | 实测 `decltype` |
|--------|-----------------|
| `++c` | **`Counter&`**（引用，是左值） |
| `c++` | **`Counter`**（副本，是右值） |

后果很直接：

```cpp
int k = 0;
++++k;    // ✅ 实测合法，k == 2（前置返回左值，能继续 ++）
k++++;    // ❌ 编译错误：后置返回右值，不能再 ++
```

### 4. C++17 求值顺序：`i = i++` 从 UB 变良定义

这是 C++17 的一次**实质变化**，很多老资料还没更新：

| 表达式 | C++11/14 | C++17 实测 |
|--------|----------|-----------|
| `m = m++;` | **UB** | **良定义**，`m == 0` |
| `p = ++p;` | **UB** | **良定义**，`p == 1` |
| `i++ + i++` | UB | **仍是 UB** |

C++17 规定：**赋值运算符的右操作数先于左操作数求值**。所以 `m = m++` 里右侧 `m++` 先算（返回 0，`m` 变 1），再把 0 赋给 `m` → 最终 `m == 0`。

**但 `i++ + i++` 仍然 UB**——两个 `i++` 之间没有顺序保证。规则只覆盖了 `=`、`[]`、`<<`、`>>`、`->*`、函数调用的部分顺序，**没有覆盖同一个运算符的两个操作数之间**。

`-Wunsequenced` 能抓到一部分这类写法，但不是全部——**不要依赖编译器警告**。

### 5. 完整语义对照

```cpp
int i = 10; ++i; int j = i++;   // 实测 i=12 j=11
int i = 5; int a = ++i;         // 实测 i=6 a=6
int i = 5; int b = i++;         // 实测 i=6 b=5
```

## HFT / 嵌入式视角

1. **养成 `++i` 的习惯仍然值得，但理由要更新**。不是为了快（`-O2` 下汇编相同），而是为了**代码换类型时不用改**：今天遍历 `vector` 无所谓，明天换成自定义迭代器或 `-O0` 构建，后置就开始掏拷贝费了。零成本的一致性收益。
2. **真正该注意的是"副本被使用"的场景**。`auto old = it++;` 是**必须**的拷贝，无法优化掉。在热路径的循环里如果只是为了推进迭代器，别用后置并把返回值丢掉——虽然 `-O2` 会救你，但 `-O0` 和跨翻译单元的场景救不了。
3. **`-O0` 构建（debug）里后置慢 16%**。如果你的基准是在 debug 下跑的，别被这个数字误导去做代码修改——把优化打开再测。
4. **别写 `i++ + i++`，C++17 也没救它**。实测 `i++ + i++`、`i++ + ++i`、`v[i] = i++` 三个**都是 UB**。拆成多条语句，每个表达式只对同一变量修改一次。HFT 里这类代码在不同编译器/优化级别下会给出不同结果，是最难复现的一类 bug。
5. **`i = i++` 在 C++17 下可以依赖了**（实测 `m == 0`）。但即便合法，**也不要写**——读代码的人得停下来想一遍求值顺序，可读性的损失远大于省下的那一行。
6. **嵌入式上 `-Os`（优化尺寸）时优化强度低于 `-O2`**，后置的副本消除可能不完全。MCU 上 `++i` 更保险。

## 和 C 的区别（自增自减：C/C++ 对内置类型一致，C++ 迭代器有差异）

| 对比点 | C | C++ |
|--------|----|------|
| 内置类型 `++i`/`i++` | ✅ 一致 | ✅ 一致 |
| 前置返回左值 | ✅ | ✅ 一致 |
| 后置返回右值（原值副本） | ✅ | ✅ 一致 |
| `i++ + i++` UB | ✅ UB | ✅ 一致 |
| 对**迭代器**用 `++it`/`it++` | 无迭代器 | ✅，前置更高效 |
| 对**类类型**重载 `++` | 无 | C++ 独有（前置 `++t` 返回引用，后置 `t++` 返回副本） |

**给 C 程序员的关键提醒：**
1. **内置类型上 C 和 C++ 完全一致**——`int i; ++i; i++;` 的语义、返回值、UB 坑都一样。C 的肌肉记忆直接用。
2. **C++ 的"差异"在迭代器和类类型**——对 `vector<int>::iterator` 用 `++it` 比 `it++` 高效（后置要拷贝旧迭代器）。C 里 `p++` 和 `++p` 对裸指针一样快，但到 C++ 迭代器要改习惯。
3. **HFT 热路径上 `++i` 是"免费"的优化**——内置类型虽然差异微乎其微，但迭代器/复杂类型上前置 `++` 省一次拷贝。养成 `++i` 习惯，代码换类型不用改。

## 常见错误

### 1. `i++ + i++` 以为"先取 i 再取 i+1"

```cpp
int i = 1;
int k = i++ + i++;   // ❌ UB
```

C 程序员也踩这个——两边都是 UB。两个 `i++` 在同一表达式中对 `i` 修改两次，且修改无顺序保证。**拆开**：`int tmp1 = i++; int tmp2 = i++; int k = tmp1 + tmp2;`。

### 2. 对迭代器用后置 `it++`

```cpp
for (auto it = v.begin(); it != v.end(); it++) { ... }   // 能跑但低效
```

`it++` 后置要拷贝旧迭代器返回再前进，循环里每次多一次拷贝。**改 `++it`**：

```cpp
for (auto it = v.begin(); it != v.end(); ++it) { ... }
```

C 里 `p++` 和 `++p` 对裸指针一样快，但 C++ 迭代器要换习惯。

### 3. 误以为后置 `i++` 比 `++i` "更安全"

```cpp
// 误以为 ++i "太激进"，i++ "更温和"
```

**错**。两者对 `i` 的修改效果完全相同（都让 `i` 加 1），区别只在**返回值**——`++i` 返回修改后的 `i`，`i++` 返回修改前的副本。单独写 `++i;` 或 `i++;`（不用返回值）时两者完全等价。推荐 `++i` 是因为对类类型/迭代器更高效，不是"更激进"。

## 自测题

**1. 选择题**　`int i = 5; int j = ++i;` 之后 `i` 和 `j` 的值分别是：

- A. i=5, j=6
- B. i=6, j=5
- C. i=6, j=6
- D. i=5, j=5

<details><summary>答案</summary>

**C**。前置 `++i` 先让 `i` 变 6，再返回 `i`（6），赋给 `j`。所以 `i=6, j=6`。若用后置 `i++`：先返回 `i` 的原值（5）赋给 `j`，再让 `i` 变 6，结果 `i=6, j=5`。C 也是同样规则。

</details>

**2. 判断题**　对内置 `int` 类型，`++i` 和 `i++` 在性能上有显著差异。

<details><summary>答案</summary>

**错**。内置类型上 `++i` 和 `i++` 性能几乎无差异（编译器优化后一样）。差异主要体现在**类类型和迭代器**——后置 `i++` 要拷贝旧值返回，前置 `++i` 直接返回引用。推荐 `++i` 是为了在所有类型上都高效，养成习惯。

</details>

**3. 踩坑题**　下面这段代码哪里是 UB？

```cpp
int i = 0;
int a = i++ + ++i;       // ①
int b = i++ + i++;       // ②
v[i] = i++;              // ③
```

<details><summary>答案</summary>

**三个都是 UB**：
- ① `i++` 和 `++i` 在同一表达式对 `i` 修改两次，无序 → UB
- ② 两个 `i++` 同上 → UB
- ③ `v[i]` 的下标 `i` 和右侧 `i++` 修改 `i` 无序 → UB

C 里也都是 UB。**修复**：拆成多条语句，每个表达式只对同一变量修改一次。

</details>

**4. 应用题**　C 程序员写惯了 `for (i = 0; i < n; i++)`，到 C++ 遍历 `vector` 时应该怎么改？为什么？

<details><summary>答案</summary>

```cpp
// C 习惯（能跑但低效）
for (auto it = v.begin(); it != v.end(); it++) { ... }

// C++ 推荐
for (auto it = v.begin(); it != v.end(); ++it) { ... }
```

原因：`it++` 后置要拷贝旧迭代器返回再前进，每次循环多一次拷贝。`++it` 前置直接前进返回引用，无拷贝。**对内置 `int` 无差异，对迭代器有差异**。

C 程序员习惯 `i++` 是因为 C 里只有裸指针/整数，`++` 和 `i++` 等价。到 C++ 遍历容器要改 `++it`。

更现代的写法用范围 for：

```cpp
for (auto& x : v) { ... }   // 不用手写 ++ 或 it
```

</details>

**5（判断）** "遍历 `vector` 一定要用 `++it` 而不是 `it++`，因为后置要多拷贝一次迭代器"——这个说法对吗？

**6（踩坑）** C++17 之后 `i = i++` 还是 UB 吗？`i++ + i++` 呢？实测结果是什么？

**7（应用）** 你要给一个自定义计数器类重载 `++`，前置和后置的签名分别怎么写？为什么后置要带一个 `int` 参数？

<details><summary>参考答案</summary>

5. **在 `-O2` 下这个说法是过时的**。实测：
   - 两个只有 `++it` / `it++` 之差的函数，`-O2` 汇编**都是 83 条指令且逐条相同**（除符号名）
   - 1000 万次迭代遍历：`++it` 1.402 ms vs `it++` 1.402 ms，差 0.0003 ms
   
   原因是优化器把后置那份**没人用的副本直接消除了**。
   
   后置**真的**慢的情况只有三种：
   - 副本被使用（`auto old = it++;`）——必须真拷贝，消不掉
   - 优化器看不透（跨翻译单元、`-O0`、虚函数）
   - `-O0` 构建：实测重型类（64 字节）前置 53.4 ms vs 后置 62.0 ms，**慢 16%**
   
   **结论：仍然推荐写 `++i`，但理由换成"换类型/换优化级别时不用改"，而不是"更快"。**

6. **`i = i++` 在 C++17 下不再是 UB，`i++ + i++` 仍然是 UB**。实测：
   - `int m = 0; m = m++;` → **m == 0**（良定义）
   - `int p = 0; p = ++p;` → **p == 1**（良定义）
   - `i++ + i++` → **仍是 UB**
   
   C++17 规定"赋值的**右操作数先于左操作数**求值"，所以 `m = m++` 里右侧先算得 0（`m` 变 1），再把 0 赋给 `m`。
   但这条规则**没有覆盖同一个运算符两个操作数之间**，`i++ + i++` 的两个修改依然无序。
   另外 `i++ + ++i`、`v[i] = i++` 也**都是 UB**。

7. ```cpp
   struct Counter {
       int v;
       Counter& operator++()    { ++v; return *this; }               // 前置：无参，返回引用
       Counter  operator++(int) { Counter t = *this; ++v; return t; } // 后置：int 哑元，返回副本
   };
   ```
   `int` 哑元**只为区分函数签名**（值永远不被使用）——这是 C++ 里唯一的"哑元参数"约定：
   两个函数名字相同、返回类型不同但参数列表必须不同才能重载，加个 `int` 就够了。
   实测 `decltype(++c)` 是 `Counter&`（左值，`++++c` 合法），`decltype(c++)` 是 `Counter`（右值，`c++++` 编译错误）。

</details>
