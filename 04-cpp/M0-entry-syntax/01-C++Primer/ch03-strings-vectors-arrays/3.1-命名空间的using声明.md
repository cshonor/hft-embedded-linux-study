# 3.1 命名空间的 using 声明

> 第 3 章 · 上一章：[第 2 章 小结](../ch02-variables-and-basic-types/2.7-小结.md) · 下一节：[3.2 标准库类型 string](./3.2-library-type-string/3.2-标准库类型string.md)

## 本节讲什么

用 `using std::cin;` 这样的声明把命名空间里的名字引入当前作用域，省得每次写 `std::` 前缀。

## 核心用法

| 写法 | 作用 |
|------|------|
| `using std::cin;` | 引入单个名字，之后写 `cin` 即可 |
| `using std::cin, std::cout;` | C++17 起可一次引入多个 |
| `using namespace std;` | 引入整个命名空间（**慎用**） |

```cpp
#include <iostream>
#include <string>
using std::cin;       // 之后写 cin 即可
using std::cout;
using std::endl;
using std::string;

int main() {
    string line;
    getline(cin, line);
    cout << line << endl;
    return 0;
}
```

## 和 C 的区别（命名空间是 C++ 独有）

**C 没有命名空间。** C 靠命名约定（前缀）和 `static`（文件作用域）避免名字冲突：

| 对比点 | C | C++ |
|--------|---|-----|
| 避免冲突机制 | 命名前缀（`mylib_func`）、`static` | 命名空间 `namespace mylib { }` |
| 调用写法 | `mylib_func()` | `mylib::func()` 或 `using mylib::func;` 后 `func()` |
| 头文件污染 | 用前缀规避 | `using namespace` 会污染 |

**给 C 程序员的关键提醒：**
1. C 里你给函数加前缀（`orderbook_init`、`orderbook_add`）来"模拟命名空间"；C++ 用真正的 `namespace orderbook { void init(); }`，更清晰。
2. `using namespace std;` 相当于把标准库所有名字"倒"进当前作用域——小文件省事，大工程易冲突。**头文件里绝对不要写**，会污染所有包含它的文件。
3. `.cpp` 里写 `using std::string;`（引入确定不冲突的常用名）是合理折中。

## 为什么要有 `using` 声明（动机）

C 没有命名空间，靠**命名前缀**（`orderbook_init()`）和 `static`（文件作用域）避免冲突。C++ 给了真正的命名空间，但每个名字都写 `std::` / `orderbook::` 前缀会让代码又臭又长。`using` 就是在这两者之间做取舍：

| 写法 | 引入范围 | 冲突风险 | 适用位置 |
|------|----------|----------|----------|
| `std::string`（全限定） | 无 | **零** | 头文件、库代码 |
| `using std::string;`（**using 声明**） | **一个指定名字** | 低（冲突时**编译期报错**） | `.cpp` 顶部、函数内 |
| `using namespace std;`（**using 指示**） | 整个命名空间 | 高（冲突时**调用点才报歧义**） | 小 `.cpp`、函数内；**绝不进头文件** |

**关键区别**：`using 声明` 冲突时**当场报错**（"target of using declaration conflicts with..."），`using 指示` 冲突时**要到实际调用才报 ambiguous**，而且报错点可能离引入点很远。这就是"能用 using 声明就别用 using 指示"的根据。

## 底层实现与实测

> 环境：Apple clang 23.1.0，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. using 声明 vs using 指示：冲突报错的位置完全不同

```cpp
namespace lib_a { void log(const std::string&); }
namespace lib_b { void log(const std::string&); }

using namespace lib_a;
using namespace lib_b;
log("x");        // ❌ error: call to 'log' is ambiguous   ← 在【调用点】才炸

using lib_a::log;
using lib_b::log;   // ❌ error: target of using declaration conflicts with
                    //    declaration already in scope      ← 在【引入点】就炸
```

实测：后者报错位置精确到 `using` 那一行，前者要等有人调用 `log` 才暴露——**大工程里这种延迟暴露的歧义能拖几个月**。

### 2. using 声明能覆盖 using 指示（消歧手段）

```cpp
using namespace lib_a;
using namespace lib_b;
using lib_a::log;      // 显式点名 → 歧义消失
log("ok");             // 实测走 lib_a::log
```

### 3. 函数内的 `using namespace` 作用域只到函数结束

```cpp
void f() {
    using namespace lib_a;
    log("函数内可见");
}
// log("...");   // ❌ error: use of undeclared identifier 'log'
```

**这是 `using namespace` 唯一"安全"的用法**——污染被限制在一个函数体内，不会扩散到包含它的文件。比文件级的 `using namespace std;` 好得多，但比 `using std::cout;` 差。

### 4. ADL（实参依赖查找）：`using std::swap` 惯用法的真正原因

```cpp
namespace orderbook {
    struct Book { int id; };
    void swap(Book& a, Book& b);       // 为 Book 定制的 swap
}
```

```cpp
orderbook::Book x{1}, y{2};
using std::swap;
swap(x, y);      // 实测：命中 orderbook::swap（ADL 找到的定制版）
int m = 1, n = 2;
swap(m, n);      // 实测：命中 std::swap（int 不在任何命名空间）
```

**这是 C++ 里"未限定调用 + using 兜底"的标准套路**：
- 对于**类类型**，ADL 会自动去实参所在命名空间找更匹配的 `swap` → 定制版优先
- 对于**内置类型**（`int` 不在任何命名空间），ADL 找不到任何东西 → 靠 `using std::swap` 兜底

去掉 `using std::swap;` 后，`swap(m, n)` 直接编译失败。**`using` 声明在这里不是"省前缀"，是让 ADL 有兜底。**

### 5. 名字查找顺序速记

```
块作用域 using 声明 → 块作用域普通声明 → 外层 using 声明 → using 指示（视为在最外层命名空间的"内联"）→ 全局
```

`using 指示` 的效果相当于"把那些名字声明在**最近的外层命名空间**里"，所以它引入的名字优先级很低，很容易被局部声明覆盖——这既是它的便利，也是它的陷阱（你以为在调 A 库的 `open`，实际被某个局部声明截胡了）。

## HFT / 嵌入式视角

1. **头文件里零容忍 `using`**。头文件会被几十个 `.cpp` 包含，一次 `using namespace` 污染全工程。规矩：头文件一律全限定名 `std::string`；`.cpp` 里用 `using std::string;` 这类单名字声明；`using namespace std;` 只在**函数体内**出现。
2. **`using namespace` 的歧义是"延迟爆炸"型 bug**。引入时不报错，等某天有人加了一个同名函数，几百个调用点同时崩。实测第 1 条就是证据——用 using 声明把报错提前到引入点。
3. **ADL 是定制点机制的地基**。`swap`、`begin`/`end`、`operator<<` 都靠 ADL 工作。写库代码时，`using std::swap; swap(a, b);` 是唯一正确的 swap 调用姿势（直接写 `std::swap(a,b)` 会绕过用户的定制版）。
4. **嵌入式里命名空间是替代 `static` 的正确工具**。C 靠 `static` 把函数藏进文件，C++ 用**匿名命名空间** `namespace { ... }` 或具名 `namespace detail {}`——比 `static` 更能表达"内部实现"的意图，而且能同时藏类型。
5. **别名与 using 声明别混**：`using MyVec = std::vector<int>;`（C++11 别名声明）是**类型别名**，不是引入名字。它比 `typedef` 可读，且支持模板（`template<class T> using Vec = std::vector<T>;`）。

## 常见错误

**1. 头文件里写 `using namespace std;`**
```cpp
// myheader.h
using namespace std;   // ❌ 所有包含此头的 .cpp 都被污染
```
头文件会被多个 `.cpp` 包含，污染扩散全工程。头文件用全限定名 `std::string`。

**2. `using` 了不存在的名字**
```cpp
using std::notexist;   // 编译错误：notexist 不是 std 的成员
```

**4. 选择题**　`using std::swap; swap(a, b);` 这个惯用法里，`using std::swap;` 的作用是：

- A. 只是省掉 `std::` 前缀
- B. 让 ADL 找到 `a`、`b` 所在命名空间的定制 `swap`，同时为内置类型兜底
- C. 强制调用 `std::swap`，忽略定制版
- D. 没有任何作用

<details><summary>答案</summary>

**B**。

- 对**类类型**实参：ADL（实参依赖查找）会去实参所在命名空间找 `swap`，命中定制版优先——实测 `orderbook::Book` 走的是 `orderbook::swap`。
- 对**内置类型**（如 `int`）：`int` 不在任何命名空间里，ADL 找不到任何东西，靠 `using std::swap;` 引入的 `std::swap` 兜底。

**去掉 `using std::swap;` 后**，对 `Book` 仍然能编译（ADL 找得到），但对 `int` 就报 `error: use of undeclared identifier 'swap'`。

所以这个惯用法的完整含义是"**先找定制版，找不到就用标准版**"，不是省前缀。写成 `std::swap(a, b)` 反而会**绕过**用户的定制版，是常见错误。

</details>

**5. 应用题**　你在做订单簿库，有一个 `orderbook::Book` 类型，配了定制的 `orderbook::swap`。现在要写一个泛型函数 `reset(T& a)`：把 `a` 和一个默认构造的临时对象交换。写出正确实现，并说明为什么不能写 `std::swap`。

<details><summary>答案</summary>

```cpp
template <class T>
void reset(T& a) {
    using std::swap;          // ① 兜底：内置类型 / 没有定制 swap 的类型
    T tmp{};
    swap(a, tmp);             // ② 未限定调用 → ADL 会先找 T 所在命名空间的定制版
}
```

**为什么不能写 `std::swap(a, tmp)`**：显式限定会**关掉 ADL**，永远只调用 `std::swap`。而 `std::swap` 的通用实现是"一次 move 构造 + 两次 move 赋值"，对 `orderbook::Book`（可能持有大缓冲、有更快的交换方式）可能比定制版慢很多——定制版往往只交换内部指针，是 O(1) 且无分配。

实测：`orderbook::Book` 走的是定制的 `orderbook::swap`（打印出来了），不是 `std::swap`。

**要点**：
- `using std::swap;` + 未限定 `swap(...)` = "定制优先，标准兜底"
- 显式 `std::swap(...)` = "只用标准版"，绕过 ADL
- 这个套路同样适用于 `begin`/`end`/`operator<<` 等定制点

</details>
