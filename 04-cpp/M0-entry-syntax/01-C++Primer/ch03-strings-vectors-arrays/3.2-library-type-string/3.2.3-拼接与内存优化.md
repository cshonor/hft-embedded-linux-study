# 3.2.3 拼接与内存优化

## 本节讲什么

`string` 的 `+` / `+=` / `==` / `size()`，以及 `s1+s2` 的临时对象与 HFT 热路径上的 `reserve`+`append` 优化。

## 拼接与比较

```cpp
std::string a = "buy", b = "IF2406";
std::string c = a + " " + b;   // "buy IF2406"
a += " done";

if (a == b) { /* ... */ }
if (a.size() > 0) { /* 或 !a.empty() */ }
```

## `+` 的操作数规则：至少一边是 `string`（实测）

TheCherno Strings 一集用 `std::string("Cherno") + " hello!"` 演示拼接，这里的关键限制是：**`+` 的两边不能都是字符串字面量**。

### 重载集合（`operator+` 到底给哪些组合开了门）

| 左边 | 右边 | 合法 | 例子 |
|------|:---:|:---:|------|
| `string` | `string` | ✅ | `a + b` |
| `string` | `const char*` | ✅ | `a + "bbb"` |
| `const char*` | `string` | ✅ | `"Hello" + std::string(" World")` |
| `string` | `char` | ✅ | `std::string("a") + 'b'` → `"ab"` |
| `char` | `string` | ✅ | `'a' + std::string("b")` → `"ab"` |
| `const char*` | `const char*` | ❌ | `"aaa" + "bbb"` |

```cpp
std::string res = "aaa" + "bbb";   // ❌
```
```
error: invalid operands to binary expression ('const char[4]' and 'const char[4]')
```

原因：`"aaa"` 的类型**不是** `string`，是 **`const char[4]`**（衰变成 `const char*`）。两个指针相加没有意义，标准也没给 `const char* + const char*` 定义任何重载。

所以视频里的 `std::string("Cherno") + " hello!"` 是正确写法——先造一个 `string` 临时对象，另一边是字面量也能拼。

**思考题**：`std::string test = "Hello" + std::string(" World");` 输出什么？

> **Hello World**。上表第 3 行那个 `const char* + string` 重载存在，**左右顺序无所谓**——字面量在左边照样能拼。真正不能的只有"两边都是字面量"。

### ⚠️ 比"两边字面量"更隐蔽的坑：字面量 `+` 字符 = **指针算术**

```cpp
const char* p = "abcdefgh" + 'b';   // ❌ 编译通过！只给一条 warning
```

```
warning: adding 'char' to a string does not append to the string [-Wstring-plus-int]
```

实测：`p` 比原字面量前进了 **98 字节**（`'b'` 的 ASCII 码）——`char` 被当成整数，走的是**指针算术**，不是字符串拼接。两边都不是 `string`，没有任何 `operator+` 重载参与。

**这比 `"aaa" + "bbb"` 危险**：后者编译器直接拦下（编不过），前者只是警告、程序照跑、读出来是越界垃圾。想拼字符就显式转成 string：`std::string(s) + 'b'`。

### `s += x` 和 `s = s + x` 结果相同，代价不同

- `s += x`：在 `s` 上原地扩容追加，必要时内部重分配**一次**
- `s = s + x`：先产生**临时 `string`**（分配 + 拷贝），再 move/拷贝回 `s`

热路径一律用 `+=` / `append`（见下面「`s1 + s2` 的内存细节」）。

## `s1 + s2` 的内存细节（临时对象 + 拷贝/移动）

```cpp
std::string s1 = "hello", s2 = "world";
std::string s3 = s1 + s2;
```

**逐步拆解：**

1. **`s1 + s2`**：`operator+` 生成一个**临时 `string`**，申请一块能装下 `s1+s2` 的新内存，把两边字符**拷贝**进去  
2. **初始化 `s3`**：把临时对象的内容**拷贝或移动**进 `s3`（C++11 起对临时对象多为 **move**，不是必做深拷贝，但临时仍要先分配一块）  
3. **语句结束**：临时对象**马上析构**，释放其内存  

| 阶段 | 对象 / 内存 |
|------|-------------|
| 语句前 | `s1`、`s2`（**2 个**具名对象） |
| 算 `s1 + s2` | **+1 临时** `string`（新分配 + 拷贝 s1、s2 内容） |
| 赋给 `s3` | `s3` 再分配（或 move 接管）临时的内容 |
| 语句后 | 临时析构；剩 `s1`、`s2`、`s3`（**3 个**具名对象） |

**至少 1 个临时 + 多次分配/拷贝**（C++11 前常为两次拷贝；现代编译器常 move 减少一次字符拷贝，但**临时对象的分配/析构**仍在）。

链式 `s1 + " " + s2` → **多个临时**，每个 `+` 都可能分配+释放：

```cpp
std::string c = s1 + " " + s2;
// s1+" " → 临时1；临时1+s2 → 临时2；再 move/拷贝进 c；临时1、2 析构
```

## HFT：少用在热路径上的 `+`，改用 `reserve` + `append`

频繁 `+` 拼接的问题：**临时对象分配/析构** → 延迟抖动、**内存碎片**。

```cpp
// ❌ 热路径：多次临时 + 多次分配
std::string s3 = s1 + s2;

// ✅ 更好：先预留，再一次 append（通常只扩一次容，无临时 string）
std::string s3;
s3.reserve(s1.size() + s2.size());
s3.append(s1).append(s2);
// 或：s3 = s1; s3.append(s2); 若 s3 为空且 s1 不太大也可接受
```

| 方式 | 临时 `string` | 典型分配次数（粗略） |
|------|---------------|---------------------|
| `s3 = s1 + s2` | 至少 1 个 | 临时 1 次 + `s3` 1 次（move 后临时释放） |
| `reserve` + `append` | **无** | 往往 **1 次**（预留足够时） |

传参时用 **`const std::string&`** 避免无谓拷贝（见 [2.3.1 引用](../../ch02-variables-and-basic-types/2.3-compound-types/2.3.1-引用.md)）。

## 和 C 的区别（strcat vs +/append）

string 的拼接替代了 C 的 `strcat`/`strcpy`，核心优势是**自动管理容量、不怕越界**：

| 对比点 | C（`strcat`/`strcpy`） | C++（`+`/`+=`/`append`） |
|--------|------------------------|--------------------------|
| 拼接 | `strcat(dst, src)` 怕 dst 不够大 | `s += t` / `s.append(t)` 自动扩容 |
| 比较 | `strcmp(a, b) == 0` | `a == b`（直观） |
| 长度 | `strlen(s)` 扫 `\0` | `s.size()` 直接拿 |
| 内存 | 手动 `malloc`/`realloc`/`free` | 析构自动释放 |

**给 C 程序员的关键提醒：**
1. `strcat` 最危险的 bug 是缓冲区溢出——你不知道 dst 够不够大。`s.append(t)` 自动扩容，没有这个风险。
2. C 里字符串比较要用 `strcmp`（不能 `==`，那比的是指针地址）；C++ 的 `string` 可以直接 `==` 比内容。
3. HFT 热路径上，`s1 + s2` 会产生临时对象（分配+释放），用 `reserve`+`append` 优化——这和 C 里预分配大缓冲 + `strcat` 的思路一样，只是 C++ 用 RAII 管理释放。

```c
/* C：strcat 怕越界 */
char buf[16] = "buy";
strcat(buf, " IF2406");   /* 刚好，但多一个字符就越界 */
```
```cpp
// C++：append 自动扩容
std::string s = "buy";
s.append(" IF2406");      /* 不用担心容量 */
```

**`s1 += s2`**：不新建第三个具名对象，在 **`s1` 上**扩容并追加（必要时内部重分配一次），一般比 `s3 = s1 + s2` 省临时对象。

## 底层实现与实测：到底分配了几次？

本节原文说"`s1 + s2` 会产生临时对象、多次分配"——这句话**在现代 C++（C++11 起）已经不准确了**。下面用**重载全局 `operator new`/`delete` 计数**的方法给出硬证据。

> 环境：Apple clang 23.1.0，libc++，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. 短串（SSO 内）：所有写法都是 0 次分配

`std::string s1 = "IF2406"; std::string s2 = "20260630";`（都 ≤ 22 字节）

| 写法 | `new` | `delete` |
|------|-------|----------|
| `string c = s1;` | 0 | 0 |
| `string c = s1 + s2;` | **0** | **0** |
| `string c = s1 + " " + s2;` | 0 | 0 |
| `reserve + append` | 0 | 0 |

**结论**：只要结果不超过 SSO 阈值（libc++ 22 字节），**怎么写都不分配**。合约码拼接（`IF2406` + `20260630` = 15 字节）完全免费。

### 2. 长串：单次 `+` 已经是最优，链式 `+` 才多一次

`std::string a(40,'x'), b(40,'y');`（超过 SSO）

| 写法 | `new` | `delete` |
|------|-------|----------|
| `string c = a + b;` | **1** | 1 |
| `string c = a + " " + b;`（链式） | **2** | 2 |
| `c = a; c += " "; c += b;` | 2 | 2 |
| `reserve(81) + append ×3` | **1** | 1 |

**两个重要结论**：

1. **单次 `a + b` 只要 1 次分配**——`operator+` 返回的临时对象是纯右值，`c` 直接从它初始化（**不需要额外对象**），临时对象的缓冲区被 move/elide 接管。`s1 + s2` 与 `reserve + append` **分配次数相同**。
2. **链式 `a + " " + b` 才是 2 次**——每个 `+` 都产生一个临时，第一个临时的缓冲区装不下最终结果，第二个 `+` 重新分配。

> 所以原文的"临时对象多次分配"应该精确成：**单次拼接没问题（现代编译器已优化），问题出在链式拼接和循环里反复拼接。**

### 3. 循环追加：`reserve` 的真正价值所在

20 万次 `s += "a"`：

| 写法 | `new` | `delete` | 最终 capacity |
|------|-------|----------|---------------|
| 无 `reserve` | **14** | 13 | 393215 |
| `s.reserve(200000)` | **1** | 0 | 200000 |

14 次重分配（2 倍扩容序列），每次都要 malloc 新块 + memcpy + free 旧块。

**放到热路径上**：`s = s + "a"` 在 20 万次循环下是 **871.8 ms**，`s += "a"` 是 **1.00 ms**（见 [4.4 赋值运算符](../../ch04-expressions/4.2-4.10-operators/4.4-赋值运算符.md) 实测）。869 倍不是"临时对象"造成的，而是**每次迭代都重新分配整块字符串**——`s = s + x` 每轮都是"分配新块 + 拷旧 + 拷新 + 释放旧"，`s += x` 只在扩容时搬一次，而且扩容是摊还 O(1)。

### 4. `append` 比 `+=` 多一点：可以链式

```cpp
s3.append(s1).append(" ").append(s2);   // 返回 string&，可以链式
```

`append` 返回 `string&`（左值引用），所以能链；`+` 返回新对象（右值），链一次多一次分配。这是两者在链式场景下的本质差别。

### 5. `string::operator+` 的重载集合（决定哪些组合合法）

| 左 | 右 | 合法 |
|----|----|------|
| `string` | `string` / `const char*` / `char` | ✅ |
| `const char*` / `char` | `string` | ✅ |
| `const char*` | `const char*` | ❌ 指针相加 |

**最隐蔽的坑**：`"abc" + 'b'` **能编译**（只有一条 `-Wstring-plus-int` 警告），走的是**指针算术**——`'b'` 的 ASCII 98 被当成偏移量。想拼字符必须 `std::string("abc") + 'b'`。

## HFT / 嵌入式视角

1. **短字段拼接不要优化**。合约码 + 日期（≤ 22 字节）落在 SSO 内，`+`/`+=`/`append` 都是 **0 次分配**。花时间优化它是纯粹的浪费。
2. **长报文组装用 `reserve` + `append`**。FIX 报文通常 100~500 字节，远超 SSO。先 `reserve(估算长度)` 再 `append`，**1 次分配**；链式 `+` 是 2 次以上。报文组装是每单必做的事。
3. **循环里拼接必须 `reserve`**。实测 14 次重分配 vs 1 次；热路径上 `s = s + x` 比 `s += x` 慢 **869 倍**。这是本节最重要的一条。
4. **`reserve` 估算可以保守偏大**。多 reserve 一点只浪费虚拟内存（未触及的页不占物理内存），少 reserve 就得重分配。**但别 reserve 一个巨大值**——实测 20 万次追加最终 capacity 是 393215（比 200000 多 96%），因为扩容是 2 倍序列，这是"不 reserve"的另一个隐藏代价：**内存占用翻倍**。
5. **嵌入式无堆环境**：`std::string` 的 `append` 在容量不足时会 `operator new`——这在裸机上是致命的（分配失败抛异常或直接 abort）。替代方案是固定 `char[N]` + 手写 `append`（返回 bool 表示是否溢出），或 `std::string_view` 指向静态缓冲（C++17）。

## 自测题

**1（选择）** 下面哪个写法在 HFT 热路径上更高效？
- A. `std::string s3 = s1 + s2;`
- B. `std::string s3; s3.reserve(s1.size()+s2.size()); s3.append(s1).append(s2);`

**2（判断）** C++ 中 `s1 == s2` 比较的是字符串内容，不是指针地址。

**3（踩坑）** C 的 `strcat(dst, src)` 最大的风险是什么？C++ 怎么避免？

<details><summary>参考答案</summary>
1. B。`s1 + s2` 产生临时对象（分配+析构）；`reserve`+`append` 预留容量后通常只扩容一次，无临时对象，热路径更稳。
2. 对。`string` 重载了 `==` 比较字符内容。C 里 `char*` 的 `==` 比的是指针地址，要 `strcmp` 才比内容——这是 C→C++ 的常见误解点。
3. 缓冲区溢出——`strcat` 不知道 `dst` 够不够大，超出就溢出（安全漏洞）。C++ 的 `append`/`+=` 自动扩容，无此风险。
</details>

**4. 判断题**　`std::string c = s1 + s2;` 会产生临时对象，所以一定比 `reserve + append` 多一次分配。

<details><summary>答案</summary>

**错。现代 C++ 下两者分配次数相同。**

实测（长串 40 + 40 字符，重载 `operator new` 计数）：

| 写法 | `new` 次数 |
|------|-----------|
| `std::string c = a + b;` | **1** |
| `reserve(81) + append` | **1** |
| `std::string c = a + " " + b;`（**链式**） | **2** |
| `c = a; c += " "; c += b;` | 2 |

**原因**：C++11 起，`a + b` 返回的是**纯右值**，`c` 直接从它初始化——不需要额外的中间对象，`operator+` 内部那次分配就是唯一一次。所以单次 `+` 已经是最优。

**真正多分配的是两种情况**：
1. **链式 `+`**：`a + " " + b` 有两个 `+`，第一个临时装不下最终结果，第二次重新分配 → 2 次。
2. **循环里反复拼接**：20 万次 `s += "a"` 是 14 次重分配（2 倍扩容序列），`reserve` 后是 1 次。

**要点**：别再用"临时对象"当拒绝 `+` 的理由（那是 C++98 的老印象）。正确做法是——**单次拼接随意，链式拼接和循环拼接用 `reserve` + `append`**。

</details>

**5. 应用题**　组装 FIX 新订单报文（约 300 字节），现有代码：

```cpp
std::string build_new_order(const Order& o) {
    std::string msg;
    msg = "8=FIX.4.2|" + o.cl_ord_id + "|" + o.symbol + "|"
        + std::to_string(o.qty) + "|" + std::to_string(o.price);
    return msg;
}
```

指出问题并改写（要求：1 次分配，且函数里不产生多余的 string）。

<details><summary>答案</summary>

**问题 ①**：`msg = "8=FIX..." + o.cl_ord_id + ...` 是一个**五连 `+` 的链式表达式**，实测长串链式拼接每次 `+` 都可能重新分配（2 次以上），这里五个 `+` 更糟。

**问题 ②**：`std::to_string(o.price)` 产生 `double` 的十进制表示——**HFT 里价格不该用浮点**（精度丢失 + 格式化慢）。应该用定点整数（`int64_t` 存 1e-8 精度）自己格式化。

**问题 ③**：`msg` 先默认构造再赋值，多走一步（虽然不分配，但语义冗余）。

**改写**：

```cpp
std::string build_new_order(const Order& o) {
    std::string msg;
    msg.reserve(300);                       // ① 一次分配到位（估算值，宁大勿小）
    msg.append("8=FIX.4.2|");
    msg.append(o.cl_ord_id);                // string_view 或 const string& 都行
    msg.push_back('|');
    msg.append(o.symbol);
    msg.push_back('|');
    append_fixed8(msg, o.qty);              // ② 定点整数格式化，不用 to_string(double)
    msg.push_back('|');
    append_fixed8(msg, o.price);
    return msg;                             // ③ NRVO / 移动返回，无额外拷贝
}
```

**要点**：
- `reserve(300)` + `append` → **1 次分配**（实测长串 reserve+append = 1 new）
- 分隔符用 `push_back('|')` 而不是 `append("|")`——单字符追加不构造临时 string
- **价格用定点整数**，别用 `std::to_string(double)`（精度 + 性能双输）
- 返回 `std::string` 值是安全的：NRVO 或移动，不产生拷贝
- 更极致的做法：调用方传入复用的 `std::string& out`（对象池），连那 1 次分配都省掉

</details>
