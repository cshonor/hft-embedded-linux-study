# 3.2.1 定义与初始化

> 第 3 章 · 上一节：[3.2 string](./3.2-标准库类型string.md) · 下一节：[3.2.2 读写操作](./3.2.2-读写操作.md)

## 本节讲什么

`std::string` 的多种构造方式：默认空串、字面值、拷贝、`string(n, c)` 重复字符、C++11 列表初始化。

## 核心用法

```cpp
#include <string>

std::string s1;                    // 空串 ""
std::string s2 = "hello";          // 字面值
std::string s3(s2);                // 拷贝
std::string s4(10, 'c');           // "cccccccccc"
std::string s5 = std::string(5, 'x');  // "xxxxx"
std::string s6{"IF2406"};          // C++11 列表初始化
```

| 写法 | 结果 |
|------|------|
| `string s;` | 默认构造，空串 |
| `string s = "abc";` | 从 C 风格字面量拷贝内容 |
| `string s(other);` | 深拷贝 `other` 的字符序列 |
| `string s(n, c);` | `n` 个字符 `c` |
| `string s{"abc"};` | C++11 列表初始化 |

## 和 C 的区别（string vs char 数组）

这是 C→C++ 的**核心升级**——C 用 `char[]` 手动管理，C++ 用 `string` 自动管理：

| 对比点 | C（`char[]`/`char*`） | C++（`std::string`） |
|--------|----------------------|----------------------|
| 长度 | `strlen(s)` 扫 `\0` | `s.size()` 直接拿 |
| 初始化 | `char s[] = "hello";` 固定大小 | `string s = "hello";` 自动管理 |
| 拷贝 | `strcpy(dst, src)` 怕越界 | `string s2 = s1;` 深拷贝，安全 |
| 重复字符 | `memset(buf, 'c', 10); buf[10]=0;` | `string s(10, 'c');` |
| 内存释放 | 手动 `free`/`delete[]` | 析构自动释放（RAII） |

**给 C 程序员的关键提醒：**
1. `string` 不需要你管 `\0`、不需要你算长度、不需要你手动释放——析构时自动回收内存。
2. `string s2 = s1;` 是**深拷贝**（独立内存），不是 C 里 `char* p = s` 的指针复制（浅拷贝）。
3. `string` 可变长，不用像 C 的 `char[64]` 那样提前估大小。

```c
/* C：char 数组，手动管理 */
char s1[16] = "hello";        /* 固定大小，长了截断 */
char s2[16];
strcpy(s2, s1);               /* 怕越界 */
size_t len = strlen(s2);      /* 扫 \0 */
/* 离开作用域自动回收（栈），但堆的要 free */
```
```cpp
// C++：string 自动管理
std::string s1 = "hello";     /* 可变长，不截断 */
std::string s2 = s1;          /* 深拷贝，安全 */
size_t len = s2.size();       /* 直接拿，不扫 \0 */
/* 离开作用域析构自动释放 */
```

## 同一行 `name[2] = 'a'`：string 合法、`char*` 崩（实测）

TheCherno Strings 一集里的关键切换——把 `char* name = "Cherno"` 换成 `std::string name = "Cherno"`，同一行 `name[2] = 'a';` 从**当场崩溃**变成**合法**。原因就是上表那句"从 C 风格字面量**拷贝**内容"：字面量本体仍在只读段没人碰，string 构造时把字符抄进了**自己的可写缓冲**。

实测（clang 23.1.0，macOS arm64，libc++，2026-10-16）：

```
字面量 "Cherno"      = 0x102197dac  (__TEXT 只读段)
&name（string 对象）  = 0x16dc66f78  (栈)
name.data()           = 0x16dc66f78  <- 短串 SSO：缓冲就在对象内部
long_s.data()         = 0x12d604920  <- 长串（100 字符）：堆上另分配
sizeof(std::string)   = 24
name.capacity()       = 22           (SSO 容量)
name 改后             = Charno
字面量本体            = Cherno       <- 不受影响
```

三个观察：

1. **`name.data() == &name`**——短串（≤ 22 字节，libc++ arm64）的缓冲直接嵌在 string 对象内部，**零堆分配**（SSO，短字符串优化）。改 `name[2]` 改的是栈上对象里的字节。
2. **长串才上堆**——100 个字符的 `long_s`，`data()` 落在堆区（0x12d6…），是 `operator new` 另分配的一块（→ [12.2 直接内存管理](../../ch12-dynamic-memory/12.2-直接内存管理.md)）。
3. **字面量本体没被碰**——改完 `name`，`lit` 仍输出 `Cherno`。

| 写法 | `name[2]='a'` | 原因 |
|------|:---:|------|
| `char* name = "Cherno"` | ❌ SIGBUS（exit 138） | 指针**指向**字面量本体，在 `__TEXT` 只读段（→ [2.1.1 §6](../../ch02-variables-and-basic-types/2.1.1-字符与字符串字面量-C++对C.md)） |
| `char name[] = "Cherno"` | ✅ | 数组是栈上**拷贝** |
| `std::string name = "Cherno"` | ✅ | 构造时**拷贝**进 string 自己的缓冲 |

记忆法：**指针是"指过去"，数组和 string 都是"拷过来"——只有拷过来的才能改。**

> HFT 视角：SSO 让 ≤ 22 字节的串**完全没有堆分配**——合约码、短字段白嫖这个优化；一旦超过容量就有一次 `operator new`，热路径上这就是要警惕的抖动来源（对应 [3.2.4](./3.2.4-string与C风格字符串.md) 的固定缓冲折中）。

## 为什么 `string` 要有这么多种构造方式（动机）

`std::string` 有 9 个以上的构造函数，不是设计冗余，而是因为**字符串来源五花八门**，每种来源都需要一条最短的构造路径：

| 来源 | 构造写法 | 不用它会怎样 |
|------|----------|-------------|
| 什么都没有 | `string s;` | 得先算长度再分配 |
| C 字面量 / `char*` | `string s = "IF2406";` | 手写 `strlen` + `memcpy` |
| 另一个 string | `string s2 = s1;`（深拷贝） | 手写同样逻辑，还容易写错长度 |
| 重复 n 个字符 | `string s(n, '-');` | 循环 `push_back` n 次 |
| 一段缓冲区 `[p, p+n)` | `string s(p, n);` | 同上，且容易漏 `\0` |
| C++11 统一初始化 | `string s{"IF2406"};` | 与 `()` 的语义差异见 3.3.2 |

**核心动机只有一条**：把"算长度 → 分配 → 拷贝 → 维护 `\0`"这套 C 里全手工的活，压缩成一行，并且**不可能写错长度**。

## 底层实现与实测

> 环境：Apple clang 23.1.0，arm64-apple-darwin，libc++，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. SSO 阈值实测：≥ 23 字节才上堆

```cpp
for (size_t n = 1; n <= 40; ++n) {
    std::string t(n, 'z');
    if (t.data() != (const char*)&t) { /* 打印 n */ break; }
}
```

实测输出：**长度 >= 23 才上堆**。配合 `sizeof(std::string) == 24`、`capacity() == 22`——libc++ arm64 的布局是 `{ 指针/容量 联合体, size, 内联缓冲 }`，22 字节正好塞进 24 字节对象里。

> 不同标准库不同：libstdc++（GCC）SSO 容量 15，MSVC 是 15。所以"22"是 libc++ 专属数字，**别写进可移植代码**。

### 2. SSO 让短串拷贝快 600 倍

100 万次构造：

| 场景 | 耗时 | 堆分配次数 |
|------|------|-----------|
| 拷贝 100 字符的长串 | 59.9 ms | 100 万次 `new` + `delete` |
| 拷贝 20 字符的短串（SSO 内） | **0.1 ms** | **0 次** |
| `string_view`（不拷贝） | 0.0 ms | 0 次 |

**约 600 倍**。这不是"小优化"——合约码、币种、交易时段这类短字段，用 `std::string` 存几乎零成本。

### 3. 拷贝 vs 移动：移动省的是字符拷贝，不省分配

```cpp
std::string c = src;                  // 拷贝构造：59.9 ms（100 万次）
std::string m = std::string(src);     // 临时 → 移动：35.0 ms
```

移动把"拷贝 100 字节"换成"偷指针"，但**临时对象自己还是要先分配一次**。所以移动只快 1.7 倍，不是几十倍。**真正想省分配，得从"不构造 string"入手**——即 `string_view`。

### 4. `string_view` 是零成本，但它不拥有数据

```cpp
std::string_view v(src);   // sizeof = 16（指针 + 长度），0 次分配
```

| 类型 | `sizeof` | 拥有数据 |
|------|----------|----------|
| `std::string` | 24 | ✅ 深拷贝，RAII |
| `std::string_view`（C++17） | 16 | ❌ 只是"指针 + 长度"的视图 |

`string_view` 比 `const std::string&` 更适合做**只读形参**——它不要求实参是 `string`（可以接 `char*`、子串），而且不涉及引用绑定。**代价：必须保证被指的字符串活得比 view 久**（悬垂 view 是新手最常见的 C++17 bug）。

### 5. `string s = 'c';` 的报错原文

```cpp
std::string s = 'c';   // ❌
```

```
error: no viable conversion from 'char' to 'std::string'
```

`char` 和"长度为 1 的字符串"是两回事——`'c'` 是整数 99，`string` 没有接受单个 `char` 的构造函数。正确写法是 `string s(1, 'c');` 或 `string s = "c";`。

### 6. 深拷贝的代价：改 `s2` 不影响 `s1`，但每次拷贝都分配

```cpp
std::string s1 = "IF2406";
std::string s2 = s1;      // 实测：s2.data() != s1.data()，两块独立内存
```

实测 100 万次 100 字符拷贝 = 59.9 ms，即**每次约 60 ns**——在订单热路径每秒百万次的量级下，这就是 60 ms/s 的纯浪费。**热路径上传 `const std::string&` 或 `std::string_view`，不要传值。**

## HFT / 嵌入式视角

1. **把关键短字段控制在 SSO 阈值内**。合约码（如 `IF2406` = 6 字节）、币种、方向标志——用 `std::string` 存**零堆分配**；一旦超过阈值（libc++ 22 字节），每次构造都是一次 `operator new`，是热路径延迟抖动的主要来源。
2. **只读形参用 `std::string_view`，不用 `const std::string&`**。前者能接 `char*`/字面量/子串而不产生临时 `string`；后者接 `const char*` 时会**隐式构造一个临时 string**（一次分配）。
3. **注意 SSO 阈值不可移植**。libc++ 22 / libstdc++ 15 / MSVC 15。跨平台代码不要假设"20 字节一定在 SSO 内"。
4. **嵌入式上 `std::string` 可能是禁用的**（无堆、无异常）。替代方案是固定大小的 `char[N]` + 长度，或 `std::array<char, N>`；C++17 起可用 `std::string_view` 指向静态缓冲——**它不分配，是嵌入式里唯一安全的"字符串视图"**。
5. **`string(n, c)` 比循环 `push_back` 好**：前者一次分配到位，后者可能触发多次扩容（实测 vector 扩容是 2 倍序列，见 3.3.1）。

## 常见错误

**1. 以为 `string s2 = s1` 是浅拷贝**
C 里 `char* p = s` 是指针复制（两个指针指向同一块）；C++ 的 `string s2 = s1` 是深拷贝（独立内存）。改 `s2` 不影响 `s1`。

**2. `string s = 'c';` 单字符赋值**
```cpp
std::string s = 'c';   // ❌ 不合法：单字符不是字符串
std::string s(1, 'c'); // ✅ 一个 'c'："c"
std::string s = "c";   // ✅ 字符串字面量
```

## 自测题

**1（选择）** `std::string s2 = s1;` 后修改 `s2`，`s1` 会变吗？
- A. 会变（浅拷贝）
- B. 不变（深拷贝）

**2（判断）** C++ 的 `string` 需要手动管理 `\0` 结束符。

**3（应用）** 用 C++ string 实现：创建一个 20 个 `'-'` 的字符串（分割线）。

**4（内存）** `std::string a = "xy";` 和 `std::string b(100, 'x');` 各自发生了几次堆分配？为什么 `a[0] = 'X'` 合法而 `char* p = "xy"; p[0] = 'X';` 会崩？

<details><summary>参考答案</summary>
1. B。`string` 的拷贝是深拷贝，`s2` 有独立内存，改 `s2` 不影响 `s1`。C 里 `char* p = s` 才是浅拷贝（指针复制）。
2. 错。`string` 内部维护长度和结束符，你不用管 `\0`。`size()` 返回字符数，不含 `\0`。只有调 `c_str()` 和 C 接口互操作时才关心 `\0`。
3. `std::string line(20, '-');` —— 第一个参数是数量，第二个是字符。
4. `a` **0 次**、**`b` 1 次**。libc++（arm64）SSO 容量 22 字节，"xy" 直接放进对象内部的缓冲（实测 `a.data() == &a`）；100 个字符超过容量，才 `operator new` 一块堆内存。`a[0]='X'` 合法是因为构造时字面量已**拷贝**进 string 自己的可写缓冲；`p[0]='X'` 崩是因为 `p` 指向字面量本体，躺在 `__TEXT` 只读段（macOS arm64 实测 SIGBUS，exit 138）。记忆法：指针是"指过去"，数组和 string 是"拷过来"——只有拷过来的才能改。
</details>

**5. 判断题**　`std::string` 的短字符串优化（SSO）意味着短串完全不分配内存，所以 `std::string` 在任何场景都比 `char*` 快。

<details><summary>答案</summary>

**前半句对，后半句错**。

**对的部分**（实测）：libc++ arm64 上 SSO 阈值是 22 字节（实测长度 ≥ 23 才上堆），`sizeof(string)=24`。20 字符的串拷贝 100 万次只要 **0.1 ms**（0 次堆分配），而 100 字符的串要 **59.9 ms**（100 万次 new+delete）——**差约 600 倍**。

**错的部分**：

1. **超过阈值就分配**。长串每次构造/拷贝都是一次 `operator new`，比 `char*` 只多不少（`char*` 至少还能 malloc 一次复用）。
2. **SSO 阈值不可移植**。libc++ 是 22，libstdc++/MSVC 是 15。同一份代码换标准库，行为边界就变了。
3. **`char*` 的"快"是有前提的**——它把长度计算、越界检查、内存释放全推给了你。C 里 `strcpy` 的那类溢出 bug，在 `string` 里不存在。**这个安全性通常比那几纳秒重要得多。**

**结论**：短字段（合约码、方向、币种）用 `string` 是白嫖 SSO 的最优解；长文本要小心分配；只读场景优先 `string_view`。

</details>

**6. 应用题**　订单网关里有个函数按合约码查配置，签名如下。指出两处性能问题并改写：

```cpp
std::string find_symbol_cfg(std::string code) {     // ① 值传递
    for (const auto& kv : g_cfg_table) {
        if (kv.first == code) return kv.second;      // ② 返回 string
    }
    return "";
}
// 调用：auto cfg = find_symbol_cfg("IF2406");
```

<details><summary>答案</summary>

**问题 ①：形参值传递**。调用点传的是字符串字面量 `"IF2406"`，`std::string` 形参会**隐式构造一个临时 string**。"IF2406" 只有 6 字节，落在 SSO 内（不分配），但如果调用点传的是 `std::string` 变量或更长的码，就是一次分配 + 拷贝。

**问题 ②：返回 `std::string` 值**。命中时把 `kv.second` **深拷贝**一份返回（100 字符的串约 60 ns/次）。查配置是每次下单都要做的事。

**改写**（只读语义，全部零拷贝）：

```cpp
// 形参用 string_view：能接字面量 / char* / string / 子串，都不产生临时 string
std::string_view find_symbol_cfg(std::string_view code) {
    for (const auto& kv : g_cfg_table)
        if (kv.first == code) return kv.second;   // string → string_view 隐式转换，零拷贝
    return {};                                    // 空视图，不分配
}
```

调用点：`auto cfg = find_symbol_cfg("IF2406");` —— `"IF2406"` 是静态字面量，构造 `string_view` 只是"指针 + 长度"，**0 次分配**。

**⚠️ 前提**：返回的 `string_view` 指向 `g_cfg_table` 里的字符串，**调用者必须保证 `g_cfg_table` 在 view 使用期间不被修改/销毁**。如果调用方要把结果存起来，必须显式转成 `std::string(cfg)`。

**要点**：
- 只读形参：`std::string_view` > `const std::string&`（后者接 `const char*` 时会构造临时 string）
- 返回值能返回视图就不返回拷贝，但要写清楚生命周期
- `sizeof(string_view) = 16`（指针+长度），`sizeof(string) = 24`

</details>
