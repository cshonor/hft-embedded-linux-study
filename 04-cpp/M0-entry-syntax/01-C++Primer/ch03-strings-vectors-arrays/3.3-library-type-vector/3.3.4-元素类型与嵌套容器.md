# 3.3.4 元素类型与嵌套容器

## 本节讲什么

`vector<T>` 的 **`T` 不限于基本类型**——自定义类、指针、嵌套 `vector` 等；HFT 常见元素选型。

只要满足容器要求（默认可**拷贝构造、拷贝赋值、可析构**；C++11 起移动参与增容），**任何类型**都能做元素：

| `T` 的例子 | HFT 场景 |
|------------|----------|
| `int`、`double` | 价格、数量、时间戳 |
| 自定义类 `MarketData` | 一条 tick / 快照 |
| `Tick*`、`std::unique_ptr<Order>` | 指针或智能指针（注意所有权） |
| `std::vector<int>` | **`vector<vector<int>>`**：二维订单簿深度 |

```cpp
struct MarketData {
    double bid{0}, ask{0};
    std::int64_t ts{0};
};

std::vector<MarketData> book;            // 自定义类
std::vector<MarketData*> pending;        // 指针（不拥有对象）
std::vector<std::vector<int>> levels;    // 嵌套：levels[档位][量...]
```

## 扩容与元素类型的关系（预告）

`push_back` 触发扩容时，要把已有元素**搬到新内存**——依赖 `T` 的**拷贝或移动**（详见 [3.3.5](./3.3.5-拷贝移动与扩容.md)）：

- 不可拷贝且不可移动 → 不能进 `vector`
- 拷贝/移动很慢 → 热路径延迟抖动
- **优先 `emplace_back`** 原地构造

## HFT 选型速查

| 场景 | 推荐 |
|------|------|
| 热路径 tick、档位 | `vector<Tick>`，`Tick` 为 POD 风格 struct |
| 大对象、禁拷贝 | `vector<unique_ptr<T>>` 或 `vector<T*>` |
| 二维订单簿 | `vector<vector<int>>` 或扁平 `vector<int>` + 下标换算 |

## 为什么元素类型决定 `vector` 的性能（动机）

`vector<T>` 的 `T` 不只是"存什么"，它同时决定了三件事，而这三件事都直接影响延迟：

1. **内存布局**：`vector<T>` 是 `T` 的**连续数组**。`T` 越大 → 单个 cache line（64 字节）里装的元素越少 → 遍历时 cache miss 越多。
2. **搬移成本**：扩容要把 n 个元素从旧块搬到新块。搬 `int` 是 `memcpy`（可被 SIMD 加速）；搬 `std::string` 要逐个调移动构造（可能触发原子操作、指针写回）。
3. **分配次数**：`T` 自己带堆资源（指针、`string`、内层 `vector`）时，构造 n 个元素就是 **n+1 次堆分配**，而不是 1 次。

第 3 点是嵌套容器和指针容器慢的**真正原因**——不是遍历慢，是**构造慢 + 内存碎片 + 访问时多一跳指针**。

## 底层实现与实测

> 环境：Apple clang 23.1.0，libc++，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. `sizeof` 对照（决定一个 cache line 能装几个）

| 类型 | `sizeof` | 64 字节 cache line 能装 |
|------|----------|------------------------|
| `int` | 4 | 16 个 |
| `double` | 8 | 8 个 |
| `Tick{double,double,long,long}` | **32** | 2 个 |
| `std::string` | **24** | 2 个（字符还在堆上） |
| `std::vector<int>` | **24** | 2 个（元素还在堆上） |
| `std::unique_ptr<int>` / `int*` | 8 | 8 个（对象还在堆上） |

**关键观察**：`string` 和 `vector<int>` 的**对象本身只有 24 字节**，看起来很紧凑——但它们的数据在**另一块堆内存**里。`vector<string>` 的遍历是"顺序读对象 + 随机读字符"，第二次读完全不可预测。这就是"结构体数组（AoS）"的缓存代价。

### 2. 嵌套 vs 扁平：差距在构造，不在遍历

512×512 矩阵，各跑 50 轮：

| | 构造 + 写入 | 堆分配次数/轮 |
|------|-------------|---------------|
| `vector<vector<int>>` | **4.63 ~ 5.86 ms** | **514**（1 外层 + 512 内层） |
| 扁平 `vector<int>(512*512)` | **0.66 ~ 0.95 ms** | **1** |
| 比值 | **约 7 倍** | **514 : 1** |

```cpp
std::vector<std::vector<int>> m(512, std::vector<int>(512));  // 514 次 malloc
std::vector<int> f(512 * 512);                                // 1 次 malloc，用 f[r*512+c] 访问
```

> ⚠️ 测这个要小心：如果写得不够"真实"，**clang 会把 `malloc`/`free` 配对直接消掉**，扁平那组会测出 `0.00008 ms` 这种荒谬数字（50 次 1 MB 分配不可能在 83 ns 内完成）。必须让缓冲区**逃逸**（如把 `data()` 存进 `volatile void*`）再做真实写入，否则测的是空气。

### 3. 但顺序遍历时两者一样快

| 轮次 | 嵌套遍历 | 扁平遍历 |
|------|----------|----------|
| run 0 | 0.034 ms | 0.033 ms |
| run 1 | 0.033 ms | 0.031 ms |

**这是最容易搞错的一点**：嵌套 vector 的**遍历**并不慢。因为 512 个内层 vector 各自是连续块，两层循环合起来仍然是**大段顺序读**，预取器和 SIMD 都能全速工作。**慢的是构造（514 次分配）和随机访问（跳行）**。

所以选型依据是：
- 矩阵**尺寸固定、一次构造反复遍历** → 嵌套可读性好，性能可接受
- 需要**频繁重建**（每帧/每次快照重来一遍）→ 必须扁平，省掉 514 次 malloc

### 4. 指针元素：10 万个元素 = 10 万次分配

| | 构造 10 万个 | 堆分配次数 |
|------|-------------|-----------|
| `vector<unique_ptr<Tick>>` | 4.15 ~ 9.57 ms | **100001** |
| `vector<Tick>` | 0.82 ~ 0.85 ms | **1** |
| 比值 | **5 ~ 11 倍**（多次运行波动较大） | **100001 : 1** |

**耗时那一列波动很大（多次运行 5~11 倍），但分配次数是确定的 100001 : 1**——后者才是稳定结论。除了慢，真正的问题是**内存碎片**：10 万个小块散布在堆上，遍历时每个元素都是一次潜在的 cache miss。


**`vector<unique_ptr<T>>` 的价值不在性能，而在**：元素不可拷贝（如 `mutex`）、需要多态、想让元素地址稳定（扩容时不移动对象本身）。

### 5. `vector<bool>` 是位压缩特化，慢 28 倍

```cpp
std::vector<bool> vb(10'000'000);   // 位压缩：省 8 倍内存
std::vector<char> vc(10'000'000);
```

| | 遍历 1000 万次读+写 |
|------|---------------------|
| `vector<bool>` | **46.17 ms** |
| `vector<char>` | **1.63 ms** |
| 比值 | **28 倍** |

`vector<bool>` 是标准里**唯一的容器特化**：每个元素占 1 bit，`operator[]` 返回的是代理对象 `std::vector<bool>::reference` 而不是 `bool&`。后果：

```cpp
auto& r = vb[0];              // ❌ 不是 bool&，是代理对象
bool* p = &vb[0];             // ❌ 编译错误
// 想要 vector<bool> 的替代品：
std::vector<char> flags;      // 1 字节，快 28 倍
std::vector<uint8_t> flags2;  // 同上
```

**HFT 里"订单是否有效"这类标志位字段，用 `vector<char>` 而不是 `vector<bool>`**——除非内存真的紧张到要省那 8 倍。

### 6. 不可拷贝也不可移动的类型进不了 `vector`

```cpp
std::vector<std::mutex> mv;              // ❌ 编译错误
std::vector<std::unique_ptr<std::mutex>> mv2;  // ✅ 实测 OK
```

`vector` 只在**扩容**时才需要搬元素，但这是编译期检查（模板实例化），不管你有没有真的触发扩容都会报错。`unique_ptr` 不可拷贝但**可移动**，所以能进 `vector`——这也是它比裸指针安全还几乎无额外成本的原因。

## HFT / 嵌入式视角

1. **热路径数据用"扁平 + POD"**。`vector<Tick>`（Tick 为纯标量 struct）扩容是 `memcpy` 级、遍历是纯顺序读。要 10 档买 + 10 档卖，用两个 `vector<Level>` 或干脆 `Level bids[10]`——订单簿深度上界已知，静态数组比 `vector` 更省。
2. **频繁重建的二维结构一律扁平**。`vector<vector<int>>` 每次构造 514 次 malloc，在每帧重建的深度快照里这是纯浪费。扁平后用 `m[r*W + c]` 访问，一次分配搞定。
3. **`vector<bool>` 换成 `vector<char>`**。实测 28 倍。标志位、有效性位图这类字段在 HFT 里访问极频繁，位压缩省的那点内存远不值这个延迟。
4. **`vector<unique_ptr<T>>` 只在必要时用**。11 倍的构造成本 + 碎片，是为"元素地址稳定 / 多态 / 不可拷贝"付的费。订单对象如果需要被其他地方持有指针（扩容不失效），`unique_ptr` 是对的；否则直接存值。
5. **嵌入式没有 MMU 时，O(n) 次分配会碎掉堆**。`vector<vector<int>>` 的 514 次 malloc 在 MCU 上是灾难。做法：一次性 `reserve` 大块 + 扁平布局，或者干脆静态数组。
6. **`sizeof(T)` 决定 cache 效率**。32 字节的 `Tick` 一个 cache line 只装 2 个；如果能把 `double` 换成定点 `int64_t`、或按列拆分（SoA），命中率能翻倍。这是 HFT 里"结构体数组 vs 数组结构体"（AoS vs SoA）的经典权衡。

## 和 C 的区别（元素类型与嵌套）

C 程序员对"动态数组的元素是 struct"也很熟——`malloc(n * sizeof(struct Tick))` 然后逐个填。但 C 有几个坑 `vector` 帮你绕过了：

| 对比点 | C | C++（vector） |
|--------|----|---------------|
| 元素是 struct | `struct Tick* arr = malloc(...)` | `std::vector<Tick> v;` |
| 嵌套"动态数组" | `int **p;` 手动 malloc 每行 + 行指针数组 | `vector<vector<int>> v;` 自动管理 |
| 元素类型限制 | 必须可 memcpy（POD） | 任意可拷贝/移动类型（含析构、含 `string`） |
| 元素含指针成员 | 浅拷贝共享堆块 → 双 free | 手写拷贝控制（三/五法则），见 [3.3.5](./3.3.5-拷贝移动与扩容.md) |
| 扩容搬元素 | `realloc` 可能 memcpy（仅 POD 安全） | 调拷贝构造/移动构造（任意类型正确） |

**给 C 程序员的关键提醒：**
1. **C 的 `realloc` 只对 POD 安全**——如果 struct 里有指针成员（如 `char*` 指向 malloc 的串），`realloc` 的 memcpy 会让两个 struct 共享同一块堆，析构时双 free。`vector` 扩容调用**拷贝构造**，可以让你写深拷贝逻辑。
2. **C 的"二维动态数组" `int **p`** 要先 malloc 行指针数组、再逐行 malloc 列，释放时反向操作。`vector<vector<int>>` 一行声明搞定，析构自动级联释放。
3. **`vector<unique_ptr<T>>`** 是 C 没有的能力——元素是指针且**自动释放**。C 里 `T**` 数组得自己 free 每个元素再 free 数组。

## 常见错误

### 1. `vector<vector<int>>` 旧编译器把 `>>` 当右移

```cpp
std::vector<std::vector<int>> v;   // C++11 之前编译错误
```

C++11 之前的编译器会把 `>>` 解析成右移运算符。C++11 起已修复，但旧代码里常看到 `vector<vector<int> >`（中间加空格）的写法。**新代码直接写 `>>`** 即可。

### 2. 元素类型不可拷贝导致编译失败

```cpp
std::vector<std::mutex> v;   // ❌ mutex 不可拷贝也不可移动
```

`mutex` 既不能拷贝也不能移动，**不能放进 `vector`**（扩容时无法搬动）。改用 `vector<unique_ptr<mutex>>`，搬的是指针。C 没有这个限制——`malloc` 一块内存当 `mutex` 数组，但你得自己保证不"搬动"它们。

### 3. 把 `vector<T*>` 当成"自动管理"

```cpp
std::vector<Order*> orders;
orders.push_back(new Order);
// ... 忘记 delete 每个 Order，析构只释放指针数组，不释放对象 → 泄漏
```

`vector<T*>` 析构只释放**指针本身**，不释放指针指向的对象。要么手动 `delete`，要么用 `vector<unique_ptr<T>>` 让 RAII 接管。**这是 C 程序员最容易踩的坑**——C 里你 `free` 数组前得先 `free` 每个元素，C++ 同理，但 `unique_ptr` 能帮你自动做。

## 自测题

**1. 选择题**　下列哪个类型**不能**直接作为 `std::vector` 的元素类型？

- A. `int`
- B. `std::string`
- C. `std::mutex`
- D. `std::unique_ptr<int>`

<details><summary>答案</summary>

**C**。`std::mutex` 既不可拷贝也不可移动，`vector` 扩容时无法搬动元素，编译会失败。`unique_ptr` 虽不可拷贝但**可移动**，能进 `vector`。

</details>

**2. 判断题**　`std::vector<std::vector<int>> v(3);` 创建了一个有 3 个空内层 vector 的外层 vector。

<details><summary>答案</summary>

**对**。`v(3)` 让外层 vector 有 3 个元素，每个元素是默认构造的 `vector<int>`（即空内层 vector）。可以接着 `v[0].push_back(1);` 给第 0 行追加元素。这等价于 C 里 `int** p = malloc(3 * sizeof(int*)); for (i=0;i<3;i++) p[i] = NULL;`。

</details>

**3. 踩坑题**　下面这段代码有什么问题？

```cpp
struct Order {
    char* symbol;   // 指向 malloc 的字符串
    int qty;
};

std::vector<Order> v;
Order o;
o.symbol = strdup("IF2406");
o.qty = 10;
v.push_back(o);
// ... 后续 v 析构 → 内存泄漏？双 free？
```

<details><summary>答案</summary>

**两个问题**：
1. **内存泄漏**：`vector` 析构时调 `Order` 的默认析构（什么都不做），`strdup` 分配的 `char*` 不会被 `free`。
2. **潜在双 free**：扩容时 `vector` 用**浅拷贝**搬元素，新旧 `Order` 的 `symbol` 指向同一块堆。如果手写了析构 `free(symbol)`，就会双 free。

**正确做法**：要么用 `std::string` 替代 `char*`（RAII 自动管理），要么按三/五法则手写拷贝构造/析构/赋值。详见 [3.3.5](./3.3.5-拷贝移动与扩容.md)。

</details>

**4. 应用题**　HFT 订单簿有 10 档买、10 档卖，每档是 `{price, qty}`。用 `vector` 设计数据结构，要求热路径友好。

<details><summary>答案</summary>

```cpp
struct Level { double price; int qty; };   // POD
struct OrderBook {
    std::vector<Level> bids;   // 买盘
    std::vector<Level> asks;   // 卖盘
    OrderBook() { bids.reserve(10); asks.reserve(10); }   // 预留容量
};
```

要点：
- `Level` 是 POD（全标量），扩容 memcpy 级，缓存友好
- `reserve(10)` 避免热路径扩容尖刺
- 也可扁平化为 `double bid_prices[10]; int bid_qtys[10];` 进一步提升缓存命中（HFT 实战常这么干）

</details>

**5（选择）** 512×512 的矩阵，哪种说法**正确**？
- A. 嵌套 `vector<vector<int>>` 遍历比扁平慢很多，所以一律扁平
- B. 两者**遍历**几乎一样快，差距主要在**构造**（514 次 vs 1 次分配）
- C. 嵌套更省内存

**6（踩坑）** 用 `vector<bool>` 存 1000 万个"订单是否有效"标志，实测比 `vector<char>` 慢多少？为什么？

**7（应用）** `vector<unique_ptr<Tick>>` 构造 10 万个元素要 100001 次堆分配，而 `vector<Tick>` 只要 1 次。那 `unique_ptr` 版本还有存在价值吗？什么时候该用？

<details><summary>参考答案</summary>

5. **B**。实测顺序遍历：嵌套 0.034 ms vs 扁平 0.033 ms，**几乎无差**（内层各自连续，合起来仍是顺序读）。
   真正的差距在构造：嵌套 514 次分配 / 4.6~5.9 ms，扁平 1 次 / 0.66~0.95 ms，**约 7 倍**。
   所以：**一次构造反复遍历** → 嵌套可以接受；**频繁重建** → 必须扁平。

6. **慢 28 倍**（实测 46.17 ms vs 1.63 ms，1000 万次读+写）。
   原因：`vector<bool>` 是标准里**唯一的容器特化**，按 **1 bit** 存储，每次 `operator[]` 都要做
   移位 + 掩码，且返回代理对象 `std::vector<bool>::reference` 而不是 `bool&`（`&vb[0]` 编译错误）。
   省了 8 倍内存，赔了 28 倍延迟。标志位字段改用 `vector<char>` / `vector<uint8_t>`。

7. **有价值，但要看场景**。`vector<unique_ptr<T>>` 的 11 倍构造成本和碎片，换的是三件事：
   - **元素不可拷贝**（如 `std::mutex`）——`vector<mutex>` 直接编译失败
   - **多态**：`vector<unique_ptr<Base>>` 能放不同的派生类
   - **地址稳定**：扩容时搬的是指针，`Tick` 对象本身不动 → 别处持有的裸指针/引用不失效
   
   判断规则：**需要上面任意一条** → 用 `unique_ptr`；**只是想存一堆值** → 直接 `vector<T>`。

</details>

## 可跑例子

```bash
# sizeof 对照、嵌套 vs 扁平（构造/遍历/分配次数）、指针元素、不可拷贝类型
g++ -std=c++17 -O2 -Wall 3.3.4-1-nested-vector.cpp -o nest && ./nest

# vector<bool> 位压缩特化：慢 28 倍
g++ -std=c++17 -O2 -Wall 3.3.4-2-vector-bool.cpp -o vb && ./vb
```

> 注意：嵌套 vs 扁平的基准里用了 `volatile void* escape` 让缓冲区逃逸，
> 否则 clang 会把 `malloc`/`free` 配对消除掉，扁平那组会测出 `0.00008 ms` 这种假数据。
