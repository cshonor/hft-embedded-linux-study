# 3.3.1 动态数组基础

## 本节讲什么

`vector` 是什么、与 `string` 的相似点，以及 `push_back` / `size()` / `empty()` 等基本操作。

## 是什么

`std::vector<T>` 是标准库提供的**动态数组**：

- **同类型元素**连续存放在内存中（缓存友好）
- **长度可变**：运行时 `push_back` 增、也可 `pop_back` 删（第 9 章详讲）
- **RAII**：析构时自动释放内部缓冲

与 [3.2 string](../3.2-library-type-string/3.2-标准库类型string.md) 类似：都是可变长序列容器；`string` 专用于字符，`vector` 泛用于任意类型 `T`。

## 基本用法

```cpp
#include <vector>

std::vector<int> v;           // 空 vector，size()==0
v.push_back(42);              // 末尾追加，必要时内部扩容
v.push_back(100);

std::cout << v.size();        // 2
std::cout << v.empty();       // false
std::cout << v[0];            // 42（下标访问已有元素，见 3.3.3）
```

| 操作 | 含义 |
|------|------|
| `push_back(x)` | 末尾追加元素（**正确增容方式**） |
| `emplace_back(args...)` | 末尾**原地构造**（少一次拷贝） |
| `size()` | 当前元素个数 |
| `empty()` | 是否无元素 |
| `reserve(n)` | 预留容量，减少多次扩容（见 [3.2.3 reserve](../3.2-library-type-string/3.2.3-拼接与内存优化.md)） |

增删改查完整 API 见第 9 章 [顺序容器](../../ch09-sequential-containers/)。

## 和 C 的区别（动态数组：vector vs malloc/realloc）

C 程序员对"动态数组"不陌生——`malloc` 一块、不够了 `realloc`、用完 `free`。`vector` 把这套手工流程封装进了 RAII：

| 对比点 | C（手写动态数组） | C++（std::vector） |
|--------|-------------------|--------------------|
| 分配 | `int *p = malloc(n * sizeof(int));` | `std::vector<int> v;`（按需扩） |
| 扩容 | `p = realloc(p, new_n * sizeof(int));` 手动 | `v.push_back(x);` 自动 |
| 长度 | 自己记一个 `size_t n;` 变量 | `v.size()` 始终准确 |
| 越界 | 无检查，UB | `v.at(i)` 抛异常；`v[i]` 仍 UB |
| 释放 | `free(p);` 忘了就泄漏 | 析构自动释放 |
| 内存连续 | 是 | 是（缓存友好） |

**给 C 程序员的关键提醒：**
1. **`realloc` 不是"原地扩"**——它可能分配新块、拷贝、释放旧块；`vector` 扩容也是同样套路（搬元素）。所以扩容时所有指向旧元素的指针、引用、迭代器都失效，见 [3.4.5](../3.4-introducing-iterators/3.4.5-易错点失效与考点.md)。
2. **C 的动态数组长度得自己记**，传参时常变成 `(int* p, size_t n)` 两个参数；`vector` 自带长度，传一个对象就行。
3. **`push_back` 均摊 O(1)**：偶尔扩容要搬运，但总体开销低。如果知道总量，用 `reserve(n)` 预留容量，避免多次扩容尖刺——HFT 热路径几乎必做。

## 为什么 `push_back` 要"摊还 O(1)"（动机）

动态数组要在"长度可变"和"内存连续"之间做取舍，唯一可行的方案就是**超额分配（capacity ≥ size）**：

- 每次 `push_back` 都精确分配 `size+1` → 每次都要 malloc + 拷贝全部 → **O(n²)**，不可接受
- 预留固定倍数（如 2 倍） → 扩容次数是 `log₂(n)` 次，总拷贝量 < 2n → **摊还 O(1)**

这是所有动态数组（`vector`、Java `ArrayList`、Python `list`）的通用解法。C 里手写 `realloc` 动态数组也是同一个套路，只是 `vector` 帮你把 `size`、`capacity`、搬移、释放全管了。

## 底层实现与实测

> 环境：Apple clang 23.1.0，libc++，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. 扩容序列实测：libc++ 严格 2 倍

```cpp
std::vector<int> v;
for (int i = 0; i < 40; ++i) {
    v.push_back(i);
    /* 打印 capacity 变化 */
}
```

| 第几次 push | capacity |
|-------------|----------|
| 1 | 0 → **1** |
| 2 | 1 → **2** |
| 3 | 2 → **4** |
| 5 | 4 → **8** |
| 9 | 8 → **16** |
| 17 | 16 → **32** |
| 33 | 32 → **64** |

**严格 2.0 倍**。libstdc++（GCC）也是 2.0；**MSVC 用 1.5 倍**（1.5 倍能让释放的旧块更容易被后续分配复用，代价是扩容更频繁）。标准只要求"摊还 O(1)"，具体倍数由实现自选——**别在代码里依赖 2 倍**。

### 2. `reserve` 实测：1000 万次 `push_back` 快 2.2 倍

| 写法 | 1000 万次耗时 | 最终 capacity |
|------|---------------|---------------|
| 无 `reserve` | 61.6 ms | **16777216** |
| `reserve(10'000'000)` | **27.5 ms** | 10000000 |

加速 2.2 倍，而且**省掉 64% 的内存**：无 reserve 时最终 capacity 是 16777216（2²⁴），比实际需要的 1000 万多 67%（约 256 MB vs 40 MB 的 int 缓冲）。

**这是 `reserve` 常被忽略的第二个价值**——不只是快，还**不浪费内存**。

### 3. `reserve` 不改 `size`（`resize` 才改）

```cpp
std::vector<int> v;
v.reserve(100);   // 实测：size() == 0，capacity() == 100
v.resize(100);    // size() == 100，元素值初始化为 0
```

`reserve` 只动 capacity，`resize` 动 size 并**值初始化**新元素（`vector<int>` 的元素是 0，不是垃圾——见实测第 4 条）。

### 4. `vector<int> v(10);` 是 10 个 0，不是垃圾

实测 `vector<int> v(10);` → `size=10, v[0]=0`。

C 里 `int arr[10];`（局部非静态）是未初始化垃圾，但 `vector<int> v(10)` 走的是**值初始化**（`value-initialize`），内置类型被清零。要"不初始化"只能 `reserve` + 逐个 `push_back`——但对 `int` 来说清零的成本可以忽略（实测 1000 万次 `push_back` 才 27.5 ms，清零 1000 万次也就几毫秒）。

### 5. 元素地址严格连续（缓存友好的根据）

```cpp
std::vector<int> c; c.reserve(4);
for (int i = 0; i < 4; ++i) c.push_back(i);
// 实测：&c[0]=0x...f0  &c[1]=0x...f4  相差 4 字节
```

`sizeof(int) == 4`，相邻元素地址正好差 4 字节——**真正的连续内存**。这是 `vector` 比 `list` 快一个数量级的根本原因（顺序遍历时预取器能全速工作）。

### 6. `push_back` vs `emplace_back`：对 `int` 无差别，对类类型有

对 `int`：两者生成完全相同的代码。对**类类型**：

```cpp
v.push_back(MyObj(1, 2));    // 构造临时 MyObj → 移动/拷贝到 vector
v.emplace_back(1, 2);        // 直接在 vector 的内存上构造，少一次移动
```

`emplace_back` 省的是那次移动构造。**但对内置类型零收益**，而且 `push_back(x)` 的 `x` 如果是已存在的对象，`emplace_back(x)` 反而可能更慢（要走完美转发）。

## HFT / 嵌入式视角

1. **知道总量就 `reserve`**。实测 2.2 倍加速 + 省 67% 内存。开盘前加载合约列表、回放一天的行情——这些场景的上界都是已知的，`reserve` 是零成本的收益。
2. **别在循环里 `push_back` 而不 `reserve`**。扩容那一下（malloc + memcpy 全部 + free）会带来**延迟尖刺**：实测无 reserve 时 1000 万次里有 24 次重分配，每次搬运上千万元素——在微秒级敏感的路径上，一次尖刺就是几十毫秒。
3. **`reserve` 不是 `resize`**。`reserve` 后 `size()` 还是 0，`v[0]` 仍然越界。想要"先开槽再填"用 `v(n)` 或 `resize(n)`。
4. **共享内存里不要用 `vector`**。它的三个指针指向**进程私有堆**，跨进程看到的是野指针。共享内存只能放 POD + 手动管理的索引（或用 boost::interprocess 的分配器）。
5. **嵌入式上 `vector` 的扩容 = 内存碎片**。没有 MMU 的 MCU 上，反复 malloc/free 不同大小的块会碎掉堆。做法：`reserve` 到最大值后**永不增长**，或用静态数组 + 手写长度。

## 常见错误

### 1. 用下标"添加"元素

```cpp
std::vector<int> v;     // 空，size()==0
v[0] = 42;              // ❌ 越界 UB，没有元素可写
```

C 里写 `int arr[N]; arr[0] = 42;` 是合法的（数组有 N 个槽），但 `vector` 是**动态**的——空 vector 没有任何槽位。**添加元素只能 `push_back` / `emplace_back`**，下标只用于访问已存在的元素。

### 2. 拿到 `size()` 后又 `push_back`，循环条件用错

```cpp
for (size_t i = 0; i < v.size(); ++i)
    v.push_back(v[i] * 2);   // ❌ size() 每次都变，死循环
```

`v.size()` 在循环里每次重新求值，`push_back` 让它持续增长。C 里写 `for (i=0; i<n; i++)` 习惯了 `n` 不变，到 `vector` 这里要警惕。

### 3. 误以为 `vector<int> v(10);` 是"10 个元素都是垃圾值"

```cpp
std::vector<int> v(10);     // 10 个 0，不是垃圾
```

C 里 `int arr[10];`（局部、非静态）是未初始化的垃圾值，但 `vector<int> v(10);` 会**值初始化**为 0。要"不初始化"得用 `vector<int> v; v.reserve(10);` 然后逐个 `push_back`——但内置类型 `int` 没必要省这点初始化成本。

## 自测题

**1. 选择题**　下列哪种方式**不能**让 `vector` 新增一个元素？

- A. `v.push_back(42);`
- B. `v.emplace_back(42);`
- C. `v[v.size()] = 42;`
- D. `v.insert(v.end(), 42);`

<details><summary>答案</summary>

**C**。`v[v.size()]` 是**越界访问**（合法下标是 `0` 到 `size()-1`），不会"自动扩容"，属于 UB。`push_back`、`emplace_back`、`insert` 才是新增元素的正确方式。

</details>

**2. 判断题**　`std::vector<int> v; v.reserve(100);` 之后，`v.size()` 是 100。

<details><summary>答案</summary>

**错**。`reserve` 只改**容量**（capacity），不改**大小**（size）。`v.size()` 仍是 0，但接下来的 100 次 `push_back` 不会触发扩容。容量是"已预留的空间"，大小是"实际元素个数"。

</details>

**3. 踩坑题**　C 程序员写惯了 `int arr[N]; arr[0] = 1;`，下面这段 C++ 代码会有什么问题？

```cpp
std::vector<int> v;       // 想要一个大小 5 的数组
for (int i = 0; i < 5; ++i)
    v[i] = i;             // 填 0,1,2,3,4
```

<details><summary>答案</summary>

`v` 是空 vector，`v[i]` 全部越界 UB。**两种正确写法**：

```cpp
// 方法 1：先构造 5 个元素
std::vector<int> v(5);
for (int i = 0; i < 5; ++i) v[i] = i;

// 方法 2：用 push_back 追加
std::vector<int> v;
for (int i = 0; i < 5; ++i) v.push_back(i);
```

C 的数组是"先开槽再填"，`vector` 是"边加边长"。要"先开槽"用 `v(n)` 构造。

</details>

**4. 应用题**　用 `vector` 重写下面这段 C 代码，要求功能等价但更安全：

```c
int* arr = malloc(10 * sizeof(int));
size_t n = 0;
for (int i = 0; i < 10; ++i) arr[n++] = i * i;
// ... 使用 arr, n ...
free(arr);
```

<details><summary>答案</summary>

```cpp
std::vector<int> v;
v.reserve(10);                 // 预留容量，避免扩容
for (int i = 0; i < 10; ++i)
    v.push_back(i * i);        // 或 v.emplace_back(i * i)
// 使用 v[i]、v.size()
// 无需 free，离开作用域自动析构
```

对比：无需 `malloc`/`free`、长度自动跟、不会忘记释放、不会算错字节数（`sizeof(int)` 那种坑）。

</details>

**5. 判断题**　`v.reserve(1000)` 之后 `v.size()` 是 1000，可以直接写 `v[999] = 1;`。

<details><summary>答案</summary>

**错，而且这是 UB**。

`reserve` 只改 **capacity（容量）**，不改 **size（大小）**。实测 `v.reserve(100)` 后 `size() == 0`，`v[0]` 就已然越界。

- **容量** = 已预留的空间（能装多少不用重新分配）
- **大小** = 实际元素个数（合法下标是 `0 .. size()-1`）

**想要"先开槽再填"用这两个**：

```cpp
std::vector<int> v(1000);        // 构造 1000 个元素 → size=1000，值初始化为 0
std::vector<int> w; w.resize(1000);   // 同上
v[999] = 1;                      // ✅ 合法
```

**`reserve` 的正确用法**：你知道最终要放 1000 个，但想避免中途扩容：

```cpp
std::vector<int> v;
v.reserve(1000);                 // size 仍是 0
for (int i = 0; i < 1000; ++i)
    v.push_back(i);              // 1000 次 push_back 全部不触发扩容 ✅
```

实测 1000 万次 push_back：无 reserve 61.6 ms / 最终 capacity 16777216；有 reserve 27.5 ms / capacity 10000000。**reserve 既快又省内存**（省 67%）。

</details>

**6. 应用题**　开盘前要加载一天的全部合约（约 8000 个）到 vector，现有代码：

```cpp
std::vector<Contract> load_contracts(const char* path) {
    std::vector<Contract> v;
    for (;;) {
        Contract c;
        if (!read_one(path, c)) break;
        v.push_back(c);                       // ①
    }
    return v;
}
```

指出性能问题并改写。假设 `Contract` 是 64 字节、可平凡拷贝。

<details><summary>答案</summary>

**问题**：不 `reserve`，8000 个元素会触发 **13 次扩容**（1→2→4→…→8192 的 2 倍序列），每次都要 malloc 新块 + memcpy 全部已有元素 + free 旧块。总拷贝量约 16000 个元素 × 64 字节 ≈ 1 MB，外加 13 次 malloc/free。

更要紧的是**最终 capacity 是 8192 而不是 8000**——比需要多 2.4%，这部分内存一直占着不放（除非 `shrink_to_fit`）。

**改写**（知道上界就 reserve）：

```cpp
std::vector<Contract> load_contracts(const char* path) {
    std::vector<Contract> v;
    v.reserve(MAX_CONTRACTS);          // ① 常量上界，一次分配到位
    for (;;) {
        Contract c;
        if (!read_one(path, c)) break;
        v.emplace_back(c);             // ② 或 push_back；对可平凡拷贝的类型无差别
    }
    return v;                          // NRVO / 移动，无额外拷贝
}
```

如果上界未知但能估个量级，`reserve(估计值)` 也比不 reserve 好——**多 reserve 只浪费虚拟内存**（未触及的页不占物理内存），少 reserve 就要重分配。

**实测对照**（1000 万次 int `push_back`）：
| 写法 | 耗时 | 最终 capacity |
|------|------|---------------|
| 无 reserve | 61.6 ms | 16777216 |
| `reserve(N)` | 27.5 ms | 10000000 |

**要点**：
- 加载/预热阶段（开盘前、回放前）**必做 `reserve`**——这些场景的上界几乎总是已知的
- 热路径里 `push_back` 而不 reserve，会因为偶发扩容产生**延迟尖刺**
- `reserve` 后如果实际用得更少，可 `shrink_to_fit()` 归还多余内存（非强制）

</details>
