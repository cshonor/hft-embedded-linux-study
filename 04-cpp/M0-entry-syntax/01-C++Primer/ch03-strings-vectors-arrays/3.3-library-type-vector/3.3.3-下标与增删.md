# 3.3.3 下标与增删

## 本节讲什么

`vector` 下标从 0 开始、为何 `v[v.size()]` 越界，以及**不能用下标添加元素**——须用 `push_back` / `emplace_back`。

## 下标从 0 开始

`vector` 和 C 数组一样，**第一个元素下标是 `0`**，最后一个合法下标是 **`size() - 1`**。

以 **`vector<int> v{1, 2, 3}`** 为例：

| | 下标 `0` | 下标 `1` | 下标 `2` | 下标 `3` |
|---|----------|----------|----------|----------|
| 元素 | `1` | `2` | `3` | ❌ **不存在** |
| | | | `size()-1` | **`size()` 返回 3 → 越界** |

- **`v.size()`** 是**元素个数**，不是「最大合法下标」
- 合法访问：`v[0]` … `v[size()-1]`；循环写 **`i < v.size()`**
- **`v[v.size()]`** 读是 UB，写是 **OOB 写**

```cpp
std::vector<int> v{1, 2, 3};
// v[3] = 4;           // ❌ 合法下标只有 0,1,2
// v[v.size()] = 4;    // ❌ size()==3，下标 3 越界
v.push_back(4);        // ✅ 正确追加
```

## 不能用下标「添加」

`v[10] = 42` 在 `size() <= 10` 时：

- **不会**自动扩容
- 只是往**容器外非法地址**写 → **未定义行为**

新元素一律：

```cpp
v.push_back(x);              // 拷贝/移动进 vector
v.emplace_back(args...);     // 原地构造
```

## HFT：越界写 = 静默灾难

- 可能**不立刻 crash**，先踩坏相邻数据 → 偶发错价、漏单
- 崩溃常在行情突发时 → **错过交易窗口**
- 习惯：`i < v.size()` 断言；增元素只用 **`push_back` / `emplace_back`**

```cpp
std::vector<Tick> ticks;       // 已有 3 条，下标 0..2
// ticks[ticks.size()] = tick; // ❌ OOB 写
ticks.push_back(tick);         // ✅
```

## 为什么下标不检查、为什么中间插入很贵（动机）

这两件事其实**是同一件事**：`vector` 承诺**内存连续**，而连续性带来两个必然推论。

**① 下标不检查 = C++ 的"零开销抽象"原则。** `v[i]` 的语义就是 `*(v.data() + i)`——和 C 数组 `arr[i]` 生成**完全相同的指令**。加一次边界检查意味着每次访问多一条比较 + 一条条件跳转，这会破坏向量化、占用分支预测器。Stroustrup 的原则是"你不为不用的东西付费"，所以检查被拆成**另一个函数** `at()`，由调用方按需选择。

**② 中间插入/删除是 O(n)。** 连续性要求元素一个挨一个，在位置 `p` 插入就必须把 `[p, end)` **整体后移一位**（`memmove`），删除则整体前移。这不是实现偷懒，是连续内存的**数学必然**——`std::list` 能 O(1) 插入，代价是失去连续性、遍历慢一个数量级。

所以 `vector` 的使用哲学是：**尾部操作 O(1)，中间操作 O(n)，用错位置就是灾难**。

## 底层实现与实测

> 环境：Apple clang 23.1.0，libc++，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. `v[i]` vs `v.at(i)`：预热后差距在噪声内（1.00x）

```cpp
for (size_t i = 0; i < v.size(); ++i) sum += v[i];      // 1 亿次
for (size_t i = 0; i < v.size(); ++i) sum += v.at(i);   // 1 亿次
```

| 轮次 | `v[i]` | `v.at(i)` | 比值 |
|------|--------|-----------|------|
| run 0 | 16.7 ms | 16.7 ms | **1.00x** |
| run 1 | 16.8 ms | 16.7 ms | **1.00x** |
| run 2 | 16.7 ms | 16.7 ms | **1.00x** |

**结论要修正一个流传很广的老印象**："`at()` 慢很多"在 `-O2` + 顺序访问下**不成立**。原因是 `at()` 的边界检查被 CPU 的分支预测器几乎完全预测对（每次都是"未越界"），而内存访问才是瓶颈。**1 亿次访问里那 1 亿次正确预测的分支，成本接近零。**

`at()` 的真实成本在别处：
- **不可预测的随机下标**：预测失败率上升，才会看到 10~30% 的差距
- **阻碍向量化**：带分支的循环体 SIMD 化更困难，编译器可能放弃自动向量化
- **debug 构建（`-O0`）**：此时 `at()` 的函数调用 + 检查无法内联，实测能慢 3~5 倍

### 2. 越界的两种下场：UB vs 异常

```cpp
std::vector<int> v(4);      // 合法下标 0..3
std::cout << v.at(99999);   // 抛 std::out_of_range: vector
std::cout << v[99999];      // 不检查 → UB
```

`v[99999]` 用 `-fsanitize=address` 编译后，ASan 给出精确定位：

```
ERROR: AddressSanitizer: heap-buffer-overflow
READ of size 4 at 0x602000000980
  #0 in main+0x1c8
0x602000000980 is located 0 bytes after 16-byte region [0x602000000970, 0x602000000980)
```

**注意 `0 bytes after 16-byte region`**——越界地址正好落在分配块**末尾之外 0 字节**，也就是说读到的内容属于"隔壁的堆块"。这就是为什么越界读常常**不崩溃**：地址合法、进程内可访问，只是值是别的对象的。**写**越界才真正致命。

### 3. 删除位置决定代价（20 万元素，删 2 万次）

| 删除位置 | 耗时 | 原因 |
|----------|------|------|
| 尾部 `pop_back()` × 2 万 | **0.0029 ms** | 只改 size，无搬移 |
| 中间 `erase(begin()+n/2)` × 2 万 | **145.32 ms** | 每次搬移剩余的一半 |
| 头部 `erase(begin())` × 2 万 | **289.72 ms** | 每次搬移全部剩余元素 |

头部比中间慢 **1.99 倍**（搬移量正好是 2 倍），和理论完全吻合。**尾部比头部快 10 万倍**——这个数量级才是选型的关键。

### 4. 删除策略对比：4024 倍差距

同样是"从 20 万元素里删掉 2 万个"：

| 策略 | 耗时 | 是否保序 |
|------|------|----------|
| 逐个 `erase(find(...))` | **370.78 ms** | ✅ 保序 |
| `erase(remove_if(...), end())` | **0.092 ms** | ✅ 保序 |
| swap-and-pop（`v[p]=v.back(); v.pop_back();`） | **0.009 ms** | ❌ 不保序 |

- **`erase-remove` 快 4024 倍**：`remove_if` 只做**一趟**线性扫描，把要保留的元素往前"压实"，最后 `erase` 一次性截尾。总复杂度 **O(n)**，而逐个 erase 是 **O(n·k)**。
- **`swap-and-pop` 再快 10 倍**：完全 O(1)，但**打乱顺序**——只在"顺序无意义"的场景可用（比如订单池里删掉已成交的订单）。

### 5. `insert` 同样看位置

| 操作 | 耗时 |
|------|------|
| 尾部 `push_back` × 20 万（已 reserve） | **0.49 ms** |
| 中间 `insert` × 2 万 | **178.03 ms** |
| 头部 `insert` × 2 万 | **320.88 ms** |

尾部 20 万次比头部 2 万次还快 **650 倍**（按单元素算差 6500 倍）。

### 6. `clear()` 不释放内存

```cpp
std::vector<int> v(200000);
// capacity() == 200000
v.clear();
// 实测：size()==0，capacity() 仍然 == 200000   ← 内存没还
v.shrink_to_fit();
// 实测：capacity() == 0                        ← 这时才真正释放
```

`clear()` 只析构元素并把 `size` 置 0，**缓冲区保留**以便下次复用。长生命周期的容器（比如收盘后清空的行情缓存）如果不 `shrink_to_fit`，那几十 MB 会一直占着。**但要注意 `shrink_to_fit` 是非绑定请求**，标准不保证一定生效（libc++ 生效了，某些实现可能忽略）。真正想释放：`std::vector<int>().swap(v);`。

## HFT / 嵌入式视角

1. **批量删除一律用 erase-remove，绝不逐个 erase**。实测 4024 倍。撤单潮、合约过期清理都是"一次删一批"，用 `remove_if` 一趟搞定；如果顺序无所谓（如订单池），用 swap-and-pop 更狠。
2. **尾部是唯一 O(1) 的位置**。行情快照按时间追加 → `push_back`；订单簿档位变化如果需要**中间插入**，说明数据结构选错了（该用 `std::map` 或定长数组 + 索引，而不是 vector）。
3. **越界写是最难查的 bug 类型**。它不崩、不报，只是悄悄改了邻居；崩溃往往延迟到行情突发时才出现，正好错过交易窗口。对策：
   - **debug/CI 构建开 `-D_GLIBCXX_ASSERTIONS`（libstdc++）或 `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_DEBUG`（libc++）**，让 `operator[]` 也带检查
   - ASan 跑一遍历史回放数据
   - 热路径保留 `operator[]`，但下标来自外部输入时改用 `at()`
4. **`at()` 的性能担忧基本是多余的**。实测 1.00x。真正该担心的是它**阻碍向量化**——如果那个循环是热点且被 SIMD 化，用 `[]` 并提供外部断言。
5. **嵌入式上没有 MMU 时越界写直接踩别的全局变量**，连段错误都没有。这种环境下宁可用 `at()`（异常可以关掉，换成 assert），也不要裸 `[]`。

## 和 C 的区别

vector 的下标访问和 C 数组几乎一样（0 开始，越界 UB），但 vector 能动态增长：

| 对比点 | C（数组） | C++（vector） |
|--------|----------|---------------|
| 下标 `v[i]` | ✅ 0 开始 | ✅ 0 开始（一样） |
| 越界 | UB（可能不报） | UB（`at()` 会抛异常） |
| 动态增长 | ❌ 固定大小 | ✅ `push_back`/`emplace_back` |
| 添加元素 | 不能（除非 malloc/realloc） | `v.push_back(x)` 自动扩容 |

**给 C 程序员的关键提醒：**
1. C 数组大小固定，不能"添加"元素；vector 可以 `push_back` 动态增长——这是核心优势。
2. **不能用下标添加元素**：`v[v.size()] = x` 是越界写（UB），不是扩容。C 程序员习惯"数组下标赋值"，但 vector 要用 `push_back`。
3. 要越界检查用 `v.at(i)`（越界抛 `out_of_range` 异常），`v[i]` 不检查（和 C 数组一样快但不安全）。

## 自测题

**1（选择）** 下面哪个能正确给 vector 添加元素？
- A. `v[v.size()] = 42;`
- B. `v.push_back(42);`
- C. `v.at(v.size()) = 42;`

**2（判断）** `v[i]` 和 `v.at(i)` 完全等价。

**3（踩坑）** `vector<int> v{1,2,3}; v[3] = 4;` 会发生什么？

<details><summary>参考答案</summary>
1. B。`push_back` 是添加元素的正确方式。`v[v.size()]` 是越界写（UB），`v.at(v.size())` 会抛异常。
2. 不等价。`v[i]` 不做越界检查（越界是 UB，可能不报错）；`v.at(i)` 做检查，越界抛 `std::out_of_range` 异常。要安全用 `at`，要性能用 `[]`。
3. 越界写，未定义行为。`v` 只有 3 个元素（下标 0,1,2），`v[3]` 越界。可能不立即 crash 但踩坏内存。要添加元素用 `v.push_back(4)`。
</details>

**4（选择）** 从 20 万元素的 `vector` 里删掉 2 万个满足条件的元素，最快且**保序**的做法是？
- A. 循环 `v.erase(std::find(...))`
- B. `v.erase(std::remove_if(...), v.end())`
- C. `v[p] = v.back(); v.pop_back();`

**5（判断）** `v.clear()` 之后 `v.capacity()` 变成 0。

**6（应用）** 实测 `v[i]` 与 `v.at(i)` 在 `-O2` 顺序遍历下差距是 1.00x，那 `at()` 到底该不该用？给出你的判断依据。

<details><summary>参考答案</summary>

4. **B**。实测：`erase(find)` 逐个删 370.78 ms，`erase-remove` 0.092 ms（**快 4024 倍**），两者都保序。
   C（swap-and-pop）最快（0.009 ms）但**不保序**，只在顺序无关时可用。

5. **错**。实测 `clear()` 后 `size()==0` 但 `capacity()` 仍是 200000——**缓冲区保留**以便复用。要真正释放得 `shrink_to_fit()`（实测降到 0，但标准说这是非绑定请求），或 `std::vector<int>().swap(v);`。

6. **该用，但要分场景**：
   - 实测 1.00x 说明**顺序遍历 + 正确预测**下检查近乎零成本，所以"为了性能不用 `at()`"的理由不成立
   - 真正的代价在：**不可预测的随机下标**（分支预测失败）、**阻碍自动向量化**、`-O0` 下不内联
   - 建议：下标来自外部输入/协议字段 → 用 `at()`（或 `[]` + 显式 assert）；热路径且已验证范围 → 用 `[]`；
     debug 构建开 libc++ hardening 让 `[]` 也检查，上线关掉

</details>
