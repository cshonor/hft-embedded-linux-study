# 3.4.1 为何需要迭代器

> 第 3 章 · 上一节：[3.3 vector](../3.3-library-type-vector/3.3-标准库类型vector.md) · 下一节：[3.4.2 begin、end 与常量迭代器](./3.4.2-begin-end与常量迭代器.md)

## 本节讲什么

下标的局限与迭代器的通用性——全书 STL 遍历的基础。

## 下标不够通用

| 访问方式 | `vector` / `string` | `list` | `map` / `set` |
|----------|---------------------|--------|---------------|
| **下标 `v[i]`** | ✅ | ❌ | ❌ |
| **迭代器** | ✅ | ✅ | ✅ |

下标只适合随机访问、连续序列；迭代器是**所有容器的通用句柄**。

## 迭代器是什么

- 类似**指针**：指向容器内某个元素（或尾后位置）
- 通过 **`*it`** 间接访问元素
- 通过 **`++it`** 在元素间移动
- `string` **不是**容器类型，但接口上**完整支持**与容器相同的迭代器操作

## 为什么下标不够用（动机）

下标 `v[i]` 能工作，依赖一个隐含前提：**容器支持 O(1) 随机访问**。这个前提只对"连续内存"成立：

- `vector` / `string` / `array` → 连续，`v[i]` 就是 `*(data + i)`，O(1)
- `list` → 链表，`l[i]` 要从头跳 i 次，**O(n)**；标准干脆**不提供** `operator[]`
- `map` / `set` → 树，`m[i]` 只在 `map` 里有，语义还是"查找或插入"，`set` 完全没有

于是出现一个矛盾：**算法（查找、排序、累加）逻辑上只关心"从头到尾走一遍"，却被迫依赖"能随机跳"这个额外能力**。

迭代器的设计动机就是**把"遍历"这个能力单独抽象出来**：它只承诺 `*it`（取当前值）和 `++it`（走到下一个），**不承诺能跳**。这样：

- `list` 也能被遍历（它的 `++it` 是 `node = node->next`）
- 同一个算法模板能作用于所有容器
- `vector` 的迭代器是**裸指针**（零开销），`list` 的迭代器是一个封装了 `node*` 的类

**这就是"零开销抽象"最漂亮的例子**：给 `vector` 用迭代器不比用指针慢一分钱，但同一份代码换到 `list` 上还能编译。

## 底层实现与实测

> 环境：Apple clang 23.1.0，libc++，`-std=c++17 -O2`。可跑版本见文末例子。

### 1. `vector` 的迭代器就是裸指针

```cpp
static_assert(sizeof(std::vector<int>::iterator) == sizeof(int*));   // 都是 8
```

| | 大小 |
|---|---|
| `vector<int>::iterator` | **8 字节** |
| `int*` | **8 字节** |

实测 `&*v.begin() == &v[0]` 为 **true**。libc++ 的 `vector<T>::iterator` 类型实际是 **`__wrap_iter<int*>`**（一层薄封装，不是裸 `int*`），所以：

```cpp
v.begin() == &v[0];       // ❌ 编译错误：iterator 和 int* 不能直接比较
&*v.begin() == &v[0];     // ✅ 实测 true
v.begin() == v.data();    // ❌ 同样不行（data() 返回 int*）
v.begin().base() == v.data();  // ✅ libc++ 下可以（.base() 是 libc++ 扩展，不可移植）
```

**`__wrap_iter` 的意义是类型安全**：它让 `vector<int>::iterator` 和 `int*` 成为**不同的类型**，防止你误把裸指针当迭代器用。开销是零——`sizeof` 仍是 8，`*it` 编译出来就是一次 `load`。

对比：`std::list<int>::iterator` 也是 8 字节，但它是个**类**，存的是节点指针，`++it` 编译成一次 `load`（`node = node->next`），而不是指针加法。

### 2. `end()` 是尾后哨兵

```cpp
std::vector<int> v{1,2,3,4,5};
// 实测：&v[0]=0x...b90  &*v.end()=0x...ba4  &v[4]=0x...ba0
std::cout << v.end() - v.begin();   // 5（== size()）
```

`&*v.end()` 比 `&v[4]` 大 4 字节（一个 `int`）——正好是**最后一个元素之后**。这就是 C 里 `arr + n` 的位置。

**`end()` 不可解引用**（`*v.end()` 是 UB）。上面那行打印是为了演示地址，实际代码里不能这么写。

### 3. 三种遍历写法：迭代器/范围 for 略快于下标

100 万个 `int` 求和，跑三轮：

| 轮次 | 下标 `v[i]` | 迭代器 `++it` | 范围 for | `list` 范围 for |
|------|-------------|---------------|----------|-----------------|
| rep0 | 0.106 ms | **0.076 ms** | 0.076 ms | 2.594 ms |
| rep1 | 0.091 ms | **0.076 ms** | 0.076 ms | 1.789 ms |
| rep2 | 0.090 ms | **0.076 ms** | 0.076 ms | 1.633 ms |

两个结论：
- **对 `vector`，三种写法差距很小**（0.090 vs 0.076 ms，约 15%）。下标稍慢是因为 `v[i]` 要先 `load` 一次 `v.data()` 再加偏移；迭代器把这个指针拿在手里，循环里少一次内存读。
- **范围 `for` 和手写迭代器性能完全相同**——它是纯语法糖，编译器展开成一模一样的 `begin()/end()` 循环。**用范围 for 没有任何代价。**

### 4. 迭代器统一了语法，但**没有**统一性能

| 容器 | 顺序遍历 100 万元素 |
|------|---------------------|
| `vector` 范围 for | **0.076 ms** |
| `list` 范围 for | **1.63 ~ 2.59 ms** |
| 差距 | **约 20 倍** |

**这是迭代器最容易误导人的地方**：同一套 `for (auto& x : c)` 语法，在 `vector` 上是顺序读（预取器全速、SIMD 可向量化），在 `list` 上是**逐个追指针**（每次都是不可预测的 cache miss）。语法相同不代表代价相同。

### 5. 通用性实测：一个模板函数吃两种容器

```cpp
auto count_if = [](auto first, auto last, auto pred) {
    long n = 0;
    for (; first != last; ++first) if (pred(*first)) ++n;
    return n;
};
count_if(v.begin(), v.end(), [](int x){ return x > 500000; });   // vector → 499999
count_if(l.begin(), l.end(), [](int x){ return x > 500000; });   // list   → 499999
```

同一个模板、同一份代码，`vector` 和 `list` 都能用。**如果改用下标写，第二行根本无法表达**——这就是迭代器存在的根本理由。

### 6. `string` 不是容器，但支持完整迭代器

`std::string` 在标准里归类为"basic_string"，不是序列容器，但它**提供** `begin()/end()`、`iterator`、`const_iterator`，所有容器算法都能直接用。反过来，`string` 有 `operator[]` 但没有 `back()` 之前的某些容器接口……实践上把它当"元素为 `char` 的容器"用没问题。

## HFT / 嵌入式视角

1. **默认用范围 `for`**。实测和手写迭代器完全同性能，可读性最好，还能避免 `it != v.end()` 写成 `it < v.end()`（只有随机访问迭代器才支持 `<`，换到 `list` 就编译不过）。
2. **别被"统一的语法"骗了**。`for (auto& x : my_list)` 比 `vector` 版本慢 20 倍。**选容器时看的是内存布局，不是语法是否好看**——HFT 热路径几乎只用 `vector` / 静态数组。
3. **迭代器是编译期抽象的，不引入间接层**。`vector` 的迭代器是指针，模板实例化后 `*it` 就是一次 `load`。担心"迭代器比指针慢"是多余的——但前提是你用的是 `vector`，且开了优化（`-O0` 下会有函数调用开销）。
4. **`end()` 每轮重新求值有微小成本**。手写 `for (auto it = v.begin(); it != v.end(); ++it)` 时，`v.end()` 每轮调一次（对 `vector` 是读一次成员，编译器通常能提出循环）。范围 for 天然只求一次。热到极致时可以自己缓存 `end`，但先测过再说。
5. **嵌入式上 `list` 的迭代器代价更明显**。没有 cache 或 cache 很小的 MCU，`list` 的指针追逐每次都是真实的内存访问，20 倍的差距会更大。

## 和 C 的区别（迭代器 ≈ 泛型指针）

**C 程序员对迭代器不会陌生**——它就是"泛型化的指针"。C 用指针遍历数组，C++ 用迭代器遍历所有容器：

| 对比点 | C（指针遍历数组） | C++（迭代器遍历容器） |
|--------|-------------------|----------------------|
| 起始 | `int *p = arr;` | `auto it = v.begin();` |
| 结束 | `int *end = arr + n;` | `auto end = v.end();` |
| 解引用 | `*p` | `*it` |
| 前进 | `++p` | `++it` |
| 比较 | `p != end` | `it != end` |
| 适用范围 | 只有连续数组 | **所有容器**（list/map/set...） |

```c
/* C：指针遍历数组 */
int arr[] = {1, 2, 3};
for (int *p = arr; p != arr + 3; ++p)
    printf("%d ", *p);
```
```cpp
// C++：迭代器遍历 vector（写法和 C 指针几乎一样）
std::vector<int> v{1, 2, 3};
for (auto it = v.begin(); it != v.end(); ++it)
    std::cout << *it << " ";
// 或用范围 for（底层也是迭代器）
for (int x : v) std::cout << x << " ";
```

**给 C 程序员的关键转变：**
1. 迭代器就是"升级版指针"——`*`、`++`、`!=` 的用法和 C 指针完全一样。
2. C 指针只能遍历连续内存（数组）；迭代器能遍历**所有容器**（包括 `list`、`map` 这种不连续的），统一了遍历语法。
3. `end()` 是"尾后"位置（类似 C 的 `arr + n`），**不指向有效元素**，不能解引用。

## 自测题

**1（选择）** 下面哪个容器不能用下标 `v[i]` 访问？
- A. `vector`
- B. `string`
- C. `list`
- D. `array`

**2（判断）** 迭代器的 `*it`、`++it` 用法和 C 指针完全一样。

**3（概念）** 为什么说迭代器比下标更通用？

<details><summary>参考答案</summary>
1. C。`list` 是链表，元素不连续存储，不能用下标随机访问。`vector`/`string`/`array` 都是连续存储，支持下标。所有容器都支持迭代器。
2. 对。迭代器重载了 `*`（解引用）、`++`（前进）、`!=`（比较），用法和 C 指针几乎一样。可以说迭代器就是"泛型化的指针"。
3. 下标只适合连续存储的容器（vector/string/array），`list`/`map`/`set` 不支持。迭代器是所有容器的统一接口——同一套 `*it`/`++it`/`it!=end` 语法能遍历任何容器，算法也能通用。
</details>

**4（选择）** 100 万个 `int` 的 `vector`，下面哪种遍历最快？
- A. 下标 `for (size_t i=0; i<v.size(); ++i) s += v[i];`
- B. 迭代器 `for (auto it=v.begin(); it!=v.end(); ++it) s += *it;`
- C. 范围 for `for (int x : v) s += x;`
- D. B 和 C 一样快（且都略快于 A）

**5（判断）** 迭代器统一了遍历语法，所以 `for (auto& x : c)` 在 `list` 和 `vector` 上性能差不多。

**6（踩坑）** 有人担心"迭代器是指针的封装，比直接用指针慢"。你怎么回应？

<details><summary>参考答案</summary>

4. **D**。实测（100 万 int 求和，三轮）：下标 0.090 ms，迭代器 0.076 ms，范围 for 0.076 ms。
   范围 for 是**纯语法糖**，编译器展开成和手写迭代器一模一样的 `begin()/end()` 循环，所以 B、C 完全相同。
   下标略慢的原因是每轮要 `load` 一次 `v.data()` 再加偏移，迭代器把指针拿在手里少一次内存读。
   **差距只有 15%，可读性优先——默认用范围 for。**

5. **错，这是迭代器最容易误导人的地方**。实测顺序遍历 100 万元素：
   `vector` 0.076 ms vs `list` 1.63~2.59 ms，**约 20 倍**。
   语法一样不代表代价一样：`vector` 是顺序读（预取 + SIMD），`list` 是逐个追指针（每次 cache miss）。
   **选容器看内存布局，不看语法。**

6. **对 `vector` 来说这个担心是多余的**，实测：
   - `sizeof(vector<int>::iterator) == sizeof(int*)`，都是 8 字节
   - `&*v.begin() == &v[0]` 为 true（libc++ 下是薄封装 `__wrap_iter<T*>`，注意不能写 `v.begin() == &v[0]`，编译不过）
   - `-O2` 下模板实例化后 `*it` 就是一次 `load`，零间接层
   
   例外：`list` 的迭代器是**类**（存 `node*`，`++it` 是一次指针追逐），那不是"封装开销"而是容器本身的访问代价。
   另外 **`-O0` 下确实会有函数调用开销**，所以基准测试一定要开优化再测。

</details>
