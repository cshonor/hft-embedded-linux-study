# 1.6 书店程序

> 第 1 章 · 上一节：[1.5 类简介](./1.5-a-brief-introduction-to-classes/1.5-类简介.md) · 下一节：[1.7 小结与术语表](./1.7-小结与术语表.md)

## 本节讲什么

全章实战总结：把变量、输入输出、控制流、`Sales_item` 类串起来，写一个完整程序——读多条书籍销售记录，按书号分组汇总，输出每本书的总销售额、售出册数、平均售价。

## 核心逻辑

程序的结构是"分组累加"模式，HFT 里也常见（按合约分组统计成交量）：

1. 读第一条记录作为"当前组"
2. 循环读后续记录：
   - 书号相同 → 累加到当前组
   - 书号不同 → 输出当前组汇总，开启新组
3. 循环结束 → 输出最后一组

## 示例

```cpp
#include <iostream>
#include "Sales_item.h"

int main() {
    Sales_item total;
    if (std::cin >> total) {               // 读入第一条记录
        Sales_item trans;
        while (std::cin >> trans) {        // 读入剩余记录
            if (total.isbn() == trans.isbn())
                total += trans;            // 同一本书，累加
            else {
                std::cout << total << std::endl;  // 不同书，输出上一本汇总
                total = trans;             // total 重置为新书
            }
        }
        std::cout << total << std::endl;   // 输出最后一本
    }
    return 0;
}
```

## 和 C 的区别

同样的"分组累加"逻辑，C 和 C++ 的写法对比：

| 对比点 | C 写法 | C++ 写法 |
|--------|--------|----------|
| 读记录 | `scanf("%s %d %lf", isbn, &sold, &price)` | `cin >> total`（一行搞定） |
| 比较 | `strcmp(isbn1, isbn2) == 0` | `total.isbn() == trans.isbn()` |
| 累加 | 手动加每个字段 | `total += trans`（运算符重载） |
| 输出 | `printf("%s %d %.2f\n", ...)` | `cout << total` |

```c
/* C 版本骨架 */
struct Record { char isbn[16]; int sold; double revenue; };
struct Record total, trans;
scanf("%s %d %lf", total.isbn, &total.sold, &total.revenue);
while (scanf("%s %d %lf", trans.isbn, &trans.sold, &trans.revenue) == 3) {
    if (strcmp(total.isbn, trans.isbn) == 0) {
        total.sold += trans.sold;
        total.revenue += trans.revenue;
    } else {
        printf("%s %d %.2f\n", total.isbn, total.sold, total.revenue);
        total = trans;
    }
}
```
**关键差异：** C++ 把"怎么读、怎么加、怎么比"藏进了类的方法和运算符重载里，主程序逻辑干净得多。C 要手动操作每个字段，容易写错（忘加某个字段、格式串写错）。

## 常见错误

**1. 忘了处理"没有输入"的情况**
```cpp
Sales_item total;
std::cin >> total;        // 如果没输入，下面 total 是未定义状态
while (std::cin >> trans) { ... }  // 直接进循环，行为未定义
```
原书代码用 `if (std::cin >> total)` 先判断第一条是否读成功，这是正确的防御性写法。

**2. 换组时忘了重置 `total`**
```cpp
if (total.isbn() == trans.isbn())
    total += trans;
else {
    std::cout << total << std::endl;
    // 忘了 total = trans; → 下一组还是累加在旧 total 上
}
```

**3. 输入没按书号排序**
程序假设输入是**按书号排好序**的（同一本书的记录连续）。如果输入乱序，`0-201 0-201 0-999 0-201` 里的最后一个 `0-201` 会被当成新书，无法合并到前面的组。要处理乱序需要更复杂的数据结构（map），第 10 章会讲。

## 动机："分组累加"是一个会反复出现的模式

书店程序看着只是第 1 章的综合练习，但它承载的**"流式分组累加"模式**在真实系统里到处都是：

| 书店程序 | HFT 对应 | 嵌入式/日志对应 |
|---------|---------|---------------|
| 按 `isbn` 分组 | 按 `symbol` 聚合成交量 | 按设备 ID 汇总采样值 |
| 输入按书号有序 | 行情网关按合约分流后天然有序 | 日志按时间/来源有序 |
| `total += trans` | 累加成交金额 | 累加计数/求和 |
| 换书时输出上一本 | 换合约时落盘上一组合计 | 换设备时上报 |

**这个模式的价值**：O(n) 时间、**O(1) 额外内存**（不需要把所有组都留在内存里），可以处理远大于内存的数据流。代价是**要求输入按 key 有序**——理解这个前提，才知道什么时候该换成 `map`。

## 底层实测

> 全部在本机 clang 23.1.0 实测（例子 `1.6-1-bookstore.cpp` 可直接跑）。

### ① 三种输入的实测输出

**有序输入**（正常路径）：
```
$ printf '0-201-78345-X 3 20.00\n0-201-78345-X 2 25.00\n0-201-78346-X 1 99.00\n' | ./bookstore
0-201-78345-X 5 110 22      ← 3+2 册、60+50 元、均价 22
0-201-78346-X 1 99 99
```

**空输入**（防御路径）：
```
$ printf '' | ./bookstore ; echo "exit=$?"
No data?!
exit=255                     ← return -1 的低 8 位
```
如果去掉 `if (std::cin >> total)` 这层判断，空输入时 `total` 是**默认构造的 `Sales_item`**（isbn 为空串、"卖了 0 本"），程序会输出一条 `0 0 0` 的垃圾记录，而不是什么都不输出。**这一处防御是整个程序最容易漏的地方**。

**乱序输入**（模式的前提被破坏）：
```
$ printf '0-201-A 1 10.0\n0-201-B 1 20.0\n0-201-A 1 10.0\n' | ./bookstore
0-201-A 1 10 10      ← A 出现两次，但没合并
0-201-B 1 20 20
0-201-A 1 10 10
```
**`A` 被拆成了两组**：因为程序只比较"当前组"和"下一条"，一旦书号变化就认为换组了。这说明——**这个算法保证的是"相邻同 key 能合并"，不是"全局按 key 聚合"**。

### ② 想处理乱序？三种方案的性能代价（100 万条 / 1000 个不同 key）

| 方案 | 是否要求有序 | 实测耗时 | 相对有序归并 |
|------|------------|---------|------------|
| ① 有序归并（书店程序模式） | ✅ 必须有序 | **3.9 ~ 5.8 ms** | 1× |
| ② `std::map` 累加（乱序输入） | ❌ 不要求 | **63 ~ 65 ms** | **约 11~16 倍** |
| ③ `unordered_map` 累加（乱序） | ❌ 不要求 | **12.5 ~ 14.8 ms** | **约 2.5~3.2 倍** |
| ②' `std::map`（有序输入） | — | 45.8 ~ 52.1 ms | — |
| ③' `unordered_map`（有序输入） | — | 6.4 ~ 8.5 ms | — |

几点解读：
- **有序归并快是因为它什么都不建**：一次线性扫描，只维护"当前组"的三个变量；`map` 每条记录都要做字符串比较 + 红黑树旋转。
- **`unordered_map` 比 `map` 快 4~5 倍**，因为哈希是 O(1) 均摊 vs 红黑树 O(log k)；而且 `reserve()` 预分配能省掉 rehash。
- **输入有序时 `unordered_map` 也更快**（6.4~8.5 ms vs 63~65 ms）——因为有序输入让哈希表的缓存局部性更好（相同 key 连续访问同一桶）。
- **代价对比**：有序归并 O(1) 内存；`map` / `unordered_map` 要存下所有 key 的聚合结果。数据量极大时这个差别会变成能不能跑的问题。

### ③ `operator>>` / `operator<<` 的关键实现细节

```cpp
std::istream& operator>>(std::istream& in, Sales_item& s) {
    std::string isbn; unsigned u; double p;
    if (in >> isbn >> u >> p) s = Sales_item(isbn, u, p);   // 读失败时【不动 s】
    return in;                                              // 返回流本身 → 可转 bool
}
```

两个必须遵守的约定：
- **返回流本身**（`std::istream&`），这样 `while (cin >> x)` 才能工作——流有 `operator bool()`，读成功为真。
- **失败时不要修改目标对象**。上面用局部临时变量读，全成功了才赋值。直接写 `in >> s.bookNo_ >> s.units_sold_ >> s.revenue_` 会导致半途失败时对象处于**半更新状态**——这正是 1.4 讲的"流失败后状态不可信"的具体体现。

## HFT / 嵌入式视角

1. **"按 symbol 聚合"优先走有序归并**。行情网关通常按合约分流，同一 symbol 的 tick 天然连续；此时用 O(1) 内存的归并比建 `map` 快 10 倍以上，还省掉哈希表的内存抖动（HFT 里要避免运行期动态分配）。
2. **前提要写成断言**。既然算法依赖"输入有序"，就在循环里加 `if (cur_key > e.key) { /* 报乱序 */ }` 或在入口做一次性校验。**静默产出错的聚合结果比崩掉危险得多**——盘后对账才发现差了几百万。
3. **换组时别忘了"重置"**。书店程序里是 `total = trans`，HFT 里是"上一组合计落盘/上报后，清空累加器开始新组"。这是这类循环最常见的 off-by-one 类 bug（第一组和最后一组最容易出错：最后一组没有"换组"事件来触发输出，必须循环外补一次）。
4. **`unordered_map::reserve()` 是免费的性能**。知道 key 数量级就先 `reserve`，能避免运行期的 rehash（rehash 是 O(n) 的停顿，在实时路径上 unacceptable）。
5. **嵌入式上内存比速度更稀缺**。1000 个 key 的 `map` 每个节点要几十字节（指针 + 颜色位 + 字符串），在几 KB RAM 的 MCU 上不现实；有序归并只要几个局部变量——**这就是"流式算法"在嵌入式上的真正价值**。
6. **`std::endl` 别用在聚合循环里**。实测 `endl` 比 `'\n'` 慢 23~25 倍（见 1.7），每条记录都 flush 会把这个 O(n) 算法变成 O(n × syscall)。

## 自测题

**1（选择）** 程序假设输入按什么排序？
- A. 按销量
- B. 按书号
- C. 不需要排序

**2（踩坑）** 如果输入为空（直接 EOF），原书代码会怎样？

**3（应用）** 把这个"分组累加"模式套到 HFT：按合约分组统计总成交量，伪代码怎么写？

<details><summary>参考答案</summary>
1. B。按书号排序，同一本书的记录连续出现，程序才能正确分组。乱序会漏合并。
2. `if (std::cin >> total)` 为假，跳过整个块，直接 `return 0`，什么都不输出。这是正确的防御性处理。
3. 框架：读第一笔成当前组的"基准合约"；后续每笔若合约号相同则累加成交量，不同则输出当前组合计、开启新合约。和书店程序结构一模一样，只是 `isbn` 换成合约号、`+=` 换成成交量累加。
</details>

**4（踩坑·高价值）** 输入 `A B A`（同一本书不连续），程序会输出几条记录？`A` 的总销量对吗？
```cpp
// 就是原书的书店程序
while (std::cin >> trans) {
    if (total.isbn() == trans.isbn()) total += trans;
    else { std::cout << total << std::endl; total = trans; }
}
std::cout << total << std::endl;
```

**5（判断）** 只要把 `if (std::cin >> total)` 去掉，空输入时程序会崩溃。

**6（应用）** 现在要处理**乱序**输入（同一 key 可能不连续），且数据量 100 万条。你有哪些选择？各自的代价是什么？

<details><summary>参考答案</summary>

4. 输出 **3 条**记录，`A` 的销量是**错的**（被拆成两组，各 1 册，而不是合计 2 册）。实测：
   ```
   0-201-A 1 10 10
   0-201-B 1 20 20
   0-201-A 1 10 10
   ```
   因为这个算法保证的是"**相邻**同 key 能合并"，不是"全局按 key 聚合"——它只比较"当前组"和"下一条"，key 一变就认为换组。所以**输入必须按 key 有序**是它的硬前提，而且这个前提**不会报错**，只会静默产出错误结果。生产代码里应该显式校验（或者在入口排一次序）。

5. **不会崩，但会输出垃圾**。`Sales_item` 的默认构造会让 `total` 是"空书号、0 册、0 元"，程序会正常输出一条 `  0 0 0` 记录，然后 `return 0`（退出码 0 = 看起来成功）。这比崩溃更危险——下游以为这是一笔合法数据。原书的 `if (std::cin >> total)` 正是防御这一点：读不到第一条就走 `else` 分支，什么都不输出并返回非 0。

6. 三种选择，实测（100 万条 / 1000 个不同 key）：
   - **① 先排序再做有序归并**：`std::sort` + 归并。排序 O(n log n)，但常数极小且内存可控；归并阶段仍是 3.9~5.8 ms 量级。**数据量远大于内存时的首选**（可以外排序）。代价：需要一次性拿到全部数据。
   - **② `std::unordered_map` 累加**：乱序直接吃，实测 12.5~14.8 ms（约有序归并的 2.5~3.2 倍）。代价：要存下所有 key 的聚合结果；运行期有哈希开销和潜在 rehash 停顿（用 `reserve()` 缓解）。**实时流式的首选**。
   - **③ `std::map` 累加**：实测 63~65 ms（约 11~16 倍），最慢——红黑树每次插入 O(log k) 且缓存局部性差。**只有需要按 key 有序输出时才选它**（比如要按字典序打印报表）。
   
   决策顺序：**能排序 → ①；要实时流式 → ②；要有序输出 → ③**。别默认用 `map`（很多人的习惯），它是这里最慢的选项。

</details>
