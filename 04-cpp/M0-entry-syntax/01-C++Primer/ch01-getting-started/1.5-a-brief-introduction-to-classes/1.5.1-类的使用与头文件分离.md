# 1.5.1 类的使用与头文件分离

> 第 1 章 · 上一节：[1.5 类简介](./1.5-类简介.md) · 下一节：[1.5.2 链接、编译产物与示例](./1.5.2-链接编译产物与示例.md)

## 本节讲什么

`Sales_item` 的用法，以及类的声明（`.h`）和实现（`.cpp`）为什么要分开写。

## 通俗理解：数据盒子 + 工具包

把 **class** 想成一个定制的「数据盒子 + 工具包」：

| `Sales_item`（书） | 以后 HFT 里的 `Order`（单） |
|--------------------|----------------------------|
| 盒子里：书号、销量、收入 | 盒子里：委托价、数量、订单号 |
| 工具：`isbn()` 取书号 | 工具：`send()` 发单、`cancel()` 撤单 |
| `>>` 读一条销售记录 | 从网关读入一笔委托 |
| `+` 合并两笔销售 | 合并/汇总订单 |

**不用自己拆盒子找数据**——定义好对象后，用 `.` 调方法就行，比零散传一堆参数清晰。

`Sales_item` 是入门的「友好型例子」：先学会**怎么用**盒子，后面章节再学**怎么造**盒子。

## 头文件与实现文件

类不必全写在头文件里。常见做法是分开写：

| 文件 | 放什么 | 作用 |
|------|--------|------|
| **`Sales_item.h`** | 类的**声明**（有哪些方法、长什么样） | 给别人看「怎么调用」 |
| **`Sales_item.cpp`** | 方法的**具体实现**（函数体里怎么写） | 藏实现细节，减少重复编译 |

HFT 项目里常把核心策略实现藏在 `.cpp` 或静态库/动态库里，**对外只暴露头文件接口**——既保护代码，又不影响别人调用。

## 和 C 的区别

C 程序员对 `.h`/`.c` 分工不陌生，但 C++ 的类让分工更彻底：

| 对比点 | C | C++ |
|--------|---|-----|
| 头文件放什么 | 函数声明、`struct` 定义 | 类声明（数据+函数原型） |
| 实现文件放什么 | 函数定义 | 类的成员函数定义（要写 `Class::method`） |
| 数据与函数 | 分离（`struct` 和函数各自声明） | 绑定（都在类里） |
| 访问控制 | 无，谁都能改 `struct` 字段 | `private` 藏起来，只能通过方法改 |

```c
/* C：数据和函数分离 */
/* book.h */
struct Book { char isbn[16]; int sold; };
char* get_isbn(struct Book* b);   /* 函数声明，和 struct 没绑定关系 */

/* book.c */
char* get_isbn(struct Book* b) { return b->isbn; }
```
```cpp
// C++：数据和方法绑定，还能控制访问
// Sales_item.h
class Sales_item {
public:                          // 外部能调的
    std::string isbn() const;
private:                         // 外部碰不到的
    std::string bookNo;
};

// Sales_item.cpp
std::string Sales_item::isbn() const { return bookNo; }  // 要带 Class::
```

**关键：** C++ 的成员函数定义在 `.cpp` 里要写 `Sales_item::isbn()`，这个 `Class::` 前缀告诉编译器"这是类的成员函数"。C 没有这个概念。

## 常见错误

**1. `.cpp` 里忘写 `Class::` 前缀**
```cpp
// Sales_item.cpp
std::string isbn() const { return bookNo; }  // 错：编译器以为是普通函数
```
报错：`bookNo` 未声明。要写成 `std::string Sales_item::isbn() const { ... }`。

**2. 头文件里直接写函数体（可能多重定义）**
```cpp
// Sales_item.h
class Sales_item {
public:
    std::string isbn() const { return bookNo; }  // 类内定义，隐式 inline
};
```
类内直接给函数体是合法的（隐式 `inline`），但如果这个头文件被多个 `.cpp` 包含，每个都生成一份定义——`inline` 函数允许这样。**非 inline 的成员函数定义放头文件会链接报错（重复定义）。** 安全做法：声明放 `.h`，定义放 `.cpp`。

**3. `private` 成员外部直接访问**
```cpp
Sales_item item;
item.bookNo = "123";  // 编译错误：bookNo 是 private
```
`private` 就是"外面碰不到"，只能通过 `public` 方法间接操作。这是 C++ 相对 C 的核心保护机制。

## 动机：`.h` / `.cpp` 分开不只是"整洁"，是三条硬约束

C 程序员对 `.h` / `.c` 的分工不陌生，但 C++ 里这件事的**约束力更强**，因为有三个 C 里没有（或弱得多）的硬约束：

1. **ODR（单一定义规则）**：一个非 `inline` 函数在**整个程序**里只能有一份定义。C 里重复定义是"常见符号"问题，链接器有时还能容忍；C++ 的 name mangling + 模板让重复定义几乎必然炸，且报错信息难读。
2. **编译单元是独立编译的**。每个 `.cpp` 单独编译、互不知情——头文件是它们之间**唯一**的"共同上下文"。头文件里写了什么，决定了所有使用者的编译结果和编译时间。
3. **头文件是接口契约**。`public` 部分就是给别人看的 API 文档；`.cpp` 可以随便改而不触发使用者的重新编译（这是大型项目能增量构建的基础）。

**一句话动机：** 头文件放"叫什么、长什么样"，实现文件放"怎么做"。违反这条，代价是链接错误、编译时间爆炸、接口和实现耦死。

## 底层实测：ODR 违规长什么样

> 全部在本机 clang 23.1.0 实测。

### ① 非 `inline` 的函数定义放头文件 → 链接期炸

```cpp
// bad.h
#pragma once
int add_bad(int a, int b) { return a + b; }   // ← 定义（不是声明！）

// u1.cpp
#include "bad.h"
int use1() { return add_bad(1, 2); }

// u2.cpp
#include "bad.h"
int use2() { return add_bad(3, 4); }
```

```
clang++ -c u1.cpp -o u1.o ; clang++ -c u2.cpp -o u2.o
clang++ u1.o u2.o main.o -o app
```

实测报错：

```
duplicate symbol 'add_bad(int, int)' in:
    u1.o
    u2.o
ld: 1 duplicate symbol for architecture arm64
clang++: error: linker command failed with exit code 1
```

**注意**：`#pragma once` 只能防止**同一个 `.cpp`** 里重复包含，**挡不住两个 `.cpp` 各生成一份**。这是新手最常误解的一点——guard 解决的是"重复声明"，ODR 解决的是"重复定义"，两回事。

### ② 用 `nm` 看符号类型：`external` vs `weak external`

| 写法 | `nm -m` 输出 |
|------|-------------|
| 非 `inline` | `0000000000000000 (__TEXT,__text) external __Z7add_badii` |
| `inline` | `000000000000001c (__TEXT,__text) **weak** external __Z6add_okii` |

差别就在 **`weak`**：弱符号允许在多个目标文件里各有一份，链接器任选其一（配合 COMDAT 保证内容一致时不冲突）。`inline` 之所以能放进头文件，本质上就是它生成的是弱符号。

### ③ 三种"可以放头文件"的写法，都实测通过

| 写法 | 例子 | 链接结果 |
|------|------|---------|
| 显式 `inline` | `inline int add_ok(int a, int b) { ... }` | ✅ 实测输出 `10` |
| 类内定义（隐式 `inline`） | `struct Adder { int sum() const { ... } };` | ✅ 实测输出 `10` |
| `inline` 变量（C++17） | `inline int g_counter = 0;` | ✅ |
| 只有声明 | `int price_of(int qty);`（定义在 `.cpp`） | ✅ |

反向：**非 `inline` 的变量定义**放头文件同样炸：

```cpp
// var.h
int g_counter = 0;    // 每个 .cpp 都生成一个
```
```
duplicate symbol '_g_counter' in:
    w1.o
    w2.o
```

C++17 之前的正确写法是头文件里 `extern int g_counter;`，然后在**某一个** `.cpp` 里定义。

### ④ 缺 include guard → 编译期炸（和 ODR 是不同的错）

```cpp
// noguard.h
struct Node { int v; };

// ng.cpp
#include "noguard.h"
#include "noguard.h"     // 同一个 TU 里包含两次
```
```
error: redefinition of 'Node'
```

这是**编译期**错误（同一个翻译单元里类型重复定义），和 ① 的**链接期** duplicate symbol 是两种病。防护手段：`#pragma once`（简单，主流编译器都支持）或传统的 `#ifndef XXX_H / #define XXX_H / #endif`（可移植性最好）。

### ⑤ 声明/实现分离的真实收益：增量编译

实测（2 个使用者，改一次实现）：

| 实现放在 | 需要重编的文件 | 实测耗时 |
|---------|--------------|---------|
| `.cpp` | 1 个（`impl.cpp`） | 0.05 s |
| `.h` | **2 个**（`userA.cpp` + `userB.cpp`） | 0.05 s + 0.05 s |

使用者是 N 个，就是 N 倍。这就是为什么"实现藏进 `.cpp`"不只是洁癖——**它是构建时间的可伸缩性**。HFT 项目几千个文件，头文件改一行触发全量重编，一次就是几十分钟。

### ⑥ 漏写 `Class::` 的报错

```cpp
// Sales_item.cpp
std::string isbn() const { return bookNo; }     // ← 漏了 Sales_item::
```
编译器会把它当成**自由函数**，于是 `bookNo` 不在作用域 → 报"未声明"。而带 `const` 的自由函数还会额外报"非成员函数不能有 const 限定"。正确写法：

```cpp
std::string Sales_item::isbn() const { return bookNo; }
```

## HFT / 嵌入式视角

1. **对外只暴露头文件是常态**。核心策略实现编译成静态库/动态库，客户端只拿到 `.h` + `.a`——既保护知识产权，又能精确控制 ABI。这时头文件里的**每一行都是契约**：改一个字段顺序、加一个虚函数，都可能破坏 ABI（尤其是虚函数表布局）。
2. **头文件里别放"会变的东西"**。策略参数、阈值常量如果写在头文件里，改一次就全量重编；应该走配置加载（运行时读 JSON/二进制），头文件里只放读取接口。
3. **`inline` 是把双刃剑**。它让函数能进头文件（解决 ODR），但会让**每个调用点都展开一份代码**——在 Flash 只有几百 KB 的 MCU 上，滥用 `inline` 会让固件体积失控。规则：**1–3 行的访问器 `inline`，复杂逻辑放 `.cpp`**。
4. **`#pragma once` vs `#ifndef` guard**：跨平台项目用 `#ifndef`（`#pragma once` 在符号链接/同一文件多路径包含时可能失效）；只跑 clang/gcc 的项目用 `#pragma once` 更不容易写错（不会出现 guard 宏名撞车）。
5. **减少头文件依赖 = 减少编译时间**。能用前置声明（`class Order;`）解决的，就别 `#include "Order.h"`。配合 pimpl（第 7 章）可以把实现改动完全隔离在 `.cpp` 里。
6. **`nm` 是排查链接问题的第一工具**。遇到 duplicate symbol / undefined symbol，先 `nm -m xxx.o | grep 符号` 看它是 `external`、`weak external` 还是 `undefined`，比读一屏模板报错快得多。

## 自测题

**1（选择）** 成员函数的定义应该放在哪里？
- A. 只能放 `.h`
- B. 只能放 `.cpp`
- C. 声明放 `.h`，定义放 `.cpp`（推荐）；类内定义的隐式 inline 可放 `.h`

**2（踩坑）** 下面代码错在哪？
```cpp
// Sales_item.cpp
std::string isbn() const { return bookNo; }
```

**3（概念）** 为什么 C++ 要分 `public`/`private`？C 的 `struct` 没有这个，会带来什么问题？

<details><summary>参考答案</summary>
1. C。声明（告诉编译器"有这个函数"）放 `.h`，定义（具体实现）放 `.cpp`。类内直接写函数体算隐式 `inline`，也可放 `.h`，但不推荐复杂逻辑这样做。
2. 缺 `Sales_item::` 前缀。编译器会把它当普通自由函数，`bookNo` 就找不到（不在作用域）。正确写法：`std::string Sales_item::isbn() const { return bookNo; }`。
3. `private` 把内部数据藏起来，外部只能通过 `public` 方法操作——这样类的作者能控制"怎么改才安全"（比如 `set_price` 里校验非负）。C 的 `struct` 全公开，任何人都能直接改字段，容易破坏不变式（比如把价格设成负数）。
</details>

**4（踩坑·高价值）** 头文件已经加了 `#pragma once`，为什么两个 `.cpp` 都包含它还是链接报错 duplicate symbol？
```cpp
// util.h
#pragma once
int helper(int x) { return x * 2; }     // ← 定义
```

**5（判断）** `#pragma once`（或 include guard）能解决"同一个头文件被两个不同 `.cpp` 包含导致的重复定义"问题。

**6（应用）** 项目里有 50 个 `.cpp` 都 `#include "strategy.h"`，你改动了策略的一处实现。实现写在 `.h` 和实现写在 `.cpp`，构建时间差多少？怎么改最划算？

<details><summary>参考答案</summary>

4. 因为 `#pragma once` 只保证**同一个翻译单元（`.cpp`）**里这个头文件的内容只出现一次，**它管不了别的 `.cpp`**。两个 `.cpp` 各自编译、各生成一份 `helper` 的非 `inline` 定义（强符号），链接时就是 duplicate symbol。实测报错：
   ```
   duplicate symbol 'helper(int)' in:  u1.o / u2.o
   ld: 1 duplicate symbol for architecture arm64
   ```
   两种修法：① 改成 `inline int helper(int x) { ... }`（生成弱符号，允许重复）；② 头文件里只放 **声明** `int helper(int);`，定义挪到某个 `.cpp`。

5. **错**。这正是第 4 题的陷阱。include guard 解决的是"**同一个 TU 内重复包含 → redefinition**"（编译期错误，实测 `error: redefinition of 'Node'`）；而"两个 TU 各生成一份定义 → duplicate symbol"是**链接期**的 ODR 问题，guard 完全无能为力。两件事，别混。

6. 实测（2 个使用者）：实现放 `.cpp` 只需重编 1 个文件 0.05 s；实现放 `.h` 要重编 2 个文件 0.05 + 0.05 s。**50 个使用者就是 1 个文件 vs 50 个文件**，差距是 50 倍量级。最划算的改法：
   - 把实现挪进 `strategy.cpp`，`strategy.h` 只留声明和类定义 → 立即从 50 降到 1；
   - 顺手减少头文件依赖：能用前置声明 `class Foo;` 的，就别 `#include "foo.h"`；
   - 如果连类的私有成员改动都不想触发重编，用 pimpl（第 7 章）：头文件里只有一个指针成员。
   注意别矫枉过正——`inline` 能让小函数留在头文件并获得内联优化，1–3 行的访问器留在 `.h` 是合理的；复杂逻辑才挪走。

</details>

## 可跑例子

```bash
# 1.5.1-1  单文件可跑的正面演示：inline / 类内定义 / inline 变量 / 分离实现
clang++ -std=c++17 -O2 -Wall 1.5.1-1-header-separation.cpp -o hdr && ./hdr
```

例子文件末尾以注释形式给出了 ①（duplicate symbol）、③（变量 duplicate）、④（redefinition）、⑤（增量编译）的**最小复现代码**、**完整命令**和**实测报错原文**——复制出来建几个小文件即可逐个验证。
