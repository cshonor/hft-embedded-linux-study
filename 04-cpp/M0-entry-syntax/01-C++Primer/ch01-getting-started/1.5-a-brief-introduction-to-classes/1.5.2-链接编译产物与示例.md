# 1.5.2 链接、编译产物与示例

## 本节讲什么

编译链接流程、.o/.exe/.lib、示例代码。

## 链接：编译器怎么找到实现？

```
main.cpp  #include "Sales_item.h"
    ↓ 编译：编译器从头文件知道 isbn() 存在 → 能通过编译
    ↓
Sales_item.cpp  → 单独编译成目标文件
    ↓ 链接：把 item.isbn() 的调用点和 .cpp 里的实现「绑」在一起
    ↓
可执行文件 → 运行时正确执行 isbn() 里的代码
```

你在 `main` 里写 `item.isbn()` 时：
1. **编译阶段**：只看 `.h`，确认 `isbn()` 名字、参数对得上就行
2. **链接阶段**：去 `.cpp` 编译出的模块里找到 `isbn()` 的真正代码并接上

所以：**头文件给编译器看，实现文件给链接器接。**

## 编译产物：从 .cpp 到「成品」

GCC、Clang、MSVC、TCC 等编译器做的事一样：**把人写的代码翻译成机器码**。步骤拆开看：

```
Sales_item.cpp  ──编译──►  Sales_item.o     （目标文件：机器码，还不能单独跑）
main.cpp        ──编译──►  main.o
                              │
                              ▼ 链接（把 .o 和库绑在一起）
                         ┌────┴────┐
                         ▼         ▼
                    book.exe    libSales.a / Sales.dll
                  （可执行程序）  （给别人用的库）
```

| 产物 | 常见后缀 | 是什么 | 给谁用 |
|------|----------|--------|--------|
| **目标文件** | `.o` / `.obj` | 单个 `.cpp` 编译出的机器码片段 | 链接器内部用，一般不单独给别人 |
| **可执行文件** | `.exe`（Windows）/ 无后缀（Linux） | 能直接运行的完整程序 | **终端用户**双击/命令行运行 |
| **静态库** | `.lib`（MSVC）/ `.a`（GCC/Clang） | 实现代码打包进库，链接时拷进你的程序 | **开发者**在自己的项目里链接 |
| **动态库** | `.dll`（Windows）/ `.so`（Linux） | 实现代码在单独文件里，运行时加载 | **开发者**链接 + 运行时带上 dll |

### 给别人当「模块」调用，给什么？

**不是** `.exe` + `.h`。

- **`.exe`**：成品程序，给**用户运行**的，不能当 SDK 让别人链接。
- **给别人调用你的类/函数**，应提供：

| 场景 | 给别人什么 |
|------|------------|
| **静态库** | `.h` + `.lib`（或 `.a`） |
| **动态库** | `.h` + `.lib`（导入库）+ `.dll`（运行时要有） |

对方在自己的项目里 `#include "Sales_item.h"`，链接你的 `.lib`，就能调 `isbn()` 等方法，**全程看不到你的 `.cpp` 源码**。

### Windows 上记一句

```
想让别人「调用你的模块」  →  .h + .lib（+ .dll）
想让别人「直接跑你的程序」  →  .exe（一般不需要给 .h）
```

HFT 里核心策略/行情解析常做成 **静态库或动态库 + 头文件**，交易主程序只链接接口，实现藏在二进制里。

## 静态链接 vs 动态链接：工程上怎么选

上一张表只回答了"有哪几种产物"，真正的工程问题是**链哪一种**。下面全是实测数据（Pi 5 / Debian 13 / gcc 14.2 / g++ -std=c++17）。

### 一张表定选择

| 维度 | 静态链接（.a） | 动态链接（.so） |
|------|---------------|----------------|
| 代码何时合并 | 编译链接期，拷进产物 | 运行期，操作系统加载 |
| 产物大小 | 大 | 小 |
| 运行时依赖 | 无，自带 | 必须有 .so |
| 升级库 | 重新编译链接整个项目 | 替换 .so 即可（**ABI 兼容**前提） |
| 内存占用 | 每个程序一份副本 | 多进程共享同一份物理页 |
| 找不到库的报错 | 链接期 `undefined reference` | 运行期 `cannot open shared object file` |

**体积实测**（同样是 hello world）：

| 程序 | 动态 | 全静态 `-static` |
|------|------|----------------|
| C（`printf`） | 70,440 B | 704,944 B（约 10 倍） |
| C++（`std::string` + `cout`） | 74,160 B | **2,251,248 B（约 30 倍）** |

C++ 静态化的代价远大于 C——多出来的是 C++ 运行时（异常、RTTI、静态初始化）。

### 澄清一个常见误解：「静态链接会把整个 libc 打包进去」

结论对，**机制描述错**。`.a` 是 `.o` 的归档包，链接器只抽出**能补齐当前未定义符号**的那些成员：

```bash
# 实测：.a 里塞两个 .o，其中 unused.o 里的函数没人调用
ar rcs libadd.a mylib.o unused.o
gcc main.c -L. -ladd -o app
nm app | grep -c never_called      # → 0，根本没进产物
```

之所以 `-static` 仍然让体积暴涨，是因为 libc 的间接依赖（locale、iconv 等）被连带拉了进来，不是因为"整包拷贝"。面试时说"按需抽取 + 连带依赖"，比说"整个塞进去"更准确。

### C++ 的常用折中：`-static-libstdc++`

C++ 全静态要 2.25 MB，工程上更常见的是**只静态链 C++ 运行时，libc 保持动态**：

```bash
g++ -std=c++17 hi.cpp -o app -static-libstdc++
ldd app | grep libstdc++          # → 空，libstdc++ 已不在依赖里
```

实测体积 1,537,168 B（比全静态的 2,251,248 B 小），而且目标机器不需要装版本匹配的 `libstdc++.so.6`，跨发行版分发时这一句很实用。

### 第三种方式：运行期手动加载 `dlopen`（插件化）

普通动态链接是「程序一启动 OS 自动加载 .so」；`dlopen` 是「运行到你这行代码才加载」：

```cpp
void* h = dlopen("./libplugin.so", RTLD_LAZY);          // 打开
auto add = (int(*)(int, int))dlsym(h, "add");            // 取函数地址
printf("%d\n", add(3, 4));
dlclose(h);                                              // 卸载
```

```bash
g++ -std=c++17 -fPIC -shared -o libplugin.so plugin.cpp  # 插件必须 -fPIC -shared
g++ -std=c++17 host.cpp -o host -ldl                     # 主程序必须 -ldl
```

与主程序的链接期毫无关系——`ldd host` 里查不到插件。机器人上位机的插件、相机/雷达驱动模块、Qt 插件都是这个模式。

### ⚠ C++ 用 `dlopen` 必踩的坑：name mangling

C 里 `dlsym(h, "add")` 直接拿到；C++ 里符号名被改编了。**实测**：

```bash
nm -D libplugin.so | grep -E "add|mul"
  0000000000000588 T add        ← extern "C" 声明的，名字没变
  00000000000005a8 T _Z3mulii   ← 普通 C++ 函数，名字被改编
```

```text
dlsym("add")  = 成功
dlsym("mul")  = 失败            ← 拿不到，返回 NULL
```

**所以插件导出的接口必须包 `extern "C"`**，否则 `dlsym` 拿空指针（1.5.2 下面「和 C 的区别」那节讲过 name mangling，这里是它在 `dlopen` 上的直接后果）：

```cpp
extern "C" int add(int a, int b) { return a + b; }   // 插件接口的标准写法
```

### ⚠ 还有一个 C 没有的坑：C++ 动态库的 ABI

C 的 `.so` 只要函数签名一致就能换；C++ 远没这么轻松：

| 风险点 | 说明 |
|--------|------|
| `std::string` 有两套 ABI | gcc 5 起新旧 ABI 由 `_GLIBCXX_USE_CXX11_ABI` 控制，库和主程序不一致就崩 |
| STL 容器跨 `.so` 边界 | 不要在接口上传 `std::string` / `std::vector`——编译器版本一变，成员布局就可能对不上 |
| 异常 / RTTI 跨边界 | 跨 `.so` `throw` 需要两边运行时一致 |
| 接口建议 | 对外接口用 C 风格（`const char*`、定长 POD 结构体），内部随便用 C++ |

这也是很多 C++ SDK 只肯发**静态库**，或者把对外接口做成 C API 的原因——"换个 .so 就行"在 C++ 里是有条件的。

## 头文件长什么样？（`Sales_item.h` 极简版）

```cpp
#pragma once              // 防止头文件被重复包含（也可用 #ifndef 守卫）

#include <string>

class Sales_item {
public:
    std::string isbn() const;   // 声明：有这个方法，具体实现在 .cpp
    // ... 其他 public 接口（>>、<<、+ 等）

private:
    std::string bookNo;         // 数据成员：外部不能直接改
    unsigned units_sold = 0;
    double revenue = 0.0;
};
```

别人 `#include "Sales_item.h"` 之后就知道怎么调 `isbn()`，但**看不到**函数体，也**碰不到** `private` 里的 `bookNo`。

**`Sales_item.cpp`（实现放这里）：**

```cpp
#include "Sales_item.h"

std::string Sales_item::isbn() const {
    return bookNo;              // 具体怎么取书号，写在这里
}
```

## 示例

```cpp
// 需配合书中 Sales_item 头文件使用；此处为用法示意
#include <iostream>
#include "Sales_item.h"

int main() {
    Sales_item item;
    std::cin >> item;                          // 从输入读取一条销售记录
    std::cout << item << std::endl;            // 打印该记录
    std::cout << item.isbn() << std::endl;     // 调用成员函数获取书号

    Sales_item item2;
    std::cin >> item2;
    Sales_item sum = item + item2;             // 两笔销售记录相加
    std::cout << sum << std::endl;
    return 0;
}
```

## 和 C 的区别

编译链接流程 C 和 C++ 基本一样，但有几个 C++ 特有的坑：

| 对比点 | C | C++ |
|--------|---|-----|
| 编译产物 | `.o` / `.exe` / `.a` / `.so` | 完全一样 |
| 函数符号名 | 就是函数名（`isbn`） | **名字改编**（`_ZN10Sales_item4isbnEv`） | 
| 混合编程 | — | C++ 调 C 要 `extern "C"` |
| 头文件守卫 | `#ifndef` 守卫 | `#ifndef` 或 `#pragma once` |

**名字改编（name mangling）：** C++ 支持重载（同名函数不同参数），编译器要把参数信息编进符号名才能区分。所以 `Sales_item::isbn()` 在 `.o` 里不叫 `isbn`，而是一串带类名和参数的符号。

**`extern "C"` 的用途：** C 的符号名就是函数名（不改编）。C++ 要调 C 的库，得告诉编译器"这个函数按 C 规则找符号"：
```cpp
extern "C" {
    #include "some_c_library.h"   // 按 C 规则链接，不做名字改编
}
```
HFT 里常碰：行情网关是 C 写的，C++ 策略层调它就要 `extern "C"`。

## 常见错误

**1. 头文件循环包含 / 重复包含**
```cpp
// a.h 包含 b.h，b.h 又包含 a.h → 死循环
```
用头文件守卫：
```cpp
#ifndef SALES_ITEM_H
#define SALES_ITEM_H
// ... 类声明
#endif
```
或更简洁的 `#pragma once`（主流编译器都支持）。

**2. 链接时找不到实现（undefined reference）**
```
undefined reference to `Sales_item::isbn() const'
```
原因：`.cpp` 没参与编译，或忘写 `Sales_item::` 前缀，或实现和声明签名不一致。检查 `g++ main.cpp Sales_item.cpp`（两个都要列上）。

**3. C++ 调 C 库忘加 `extern "C"`**
```cpp
#include "c_lib.h"           // C 头文件
c_function();                // 链接报错：找不到 _Z11c_functionv
```
C++ 默认按改编后的名字找，但 C 库里是原名。要 `extern "C" { #include "c_lib.h" }`。

**4. 插件的 `dlsym` 拿不到函数（返回 NULL）**
```cpp
int (*f)(int,int) = (int(*)(int,int))dlsym(h, "mul");   // → NULL
```
原因：C++ 函数符号被改编成 `_Z3mulii`，`dlsym("mul")` 自然找不到。**修正**：插件导出接口用 `extern "C"` 声明，编译后 `nm -D libplugin.so` 看到的必须是原名 `mul` 而不是 `_Z3mulii`。

**5. 升级 `.so` 后程序在 `std::string` 上崩溃**
```cpp
// 库接口：void set_name(std::string s);   ← 危险
```
原因：C++ 没有稳定的 ABI，`std::string`/`std::vector` 的成员布局随编译器版本和 `_GLIBCXX_USE_CXX11_ABI` 变化。库换了编译器版本，主程序没重编 → 布局对不上 → 崩。**修正**：接口改成 C 风格（`const char*` / 定长结构体 + 长度），或整体重新编译。

## 自测题

**1（选择）** 下面哪个是 C++ 相对 C 在编译链接上的特有问题？
- A. 头文件重复包含
- B. 函数名字改编导致调 C 库要 `extern "C"`
- C. `.o` 文件格式不同

**2（判断）** `#pragma once` 和 `#ifndef` 守卫作用相同，都是防头文件重复包含。

**3（踩坑）** 编译命令 `g++ main.cpp` 报 `undefined reference to Sales_item::isbn()`，最可能的原因是什么？

**4（判断）** 「静态链接会把整个 libc 的代码都拷进你的可执行文件」——这句话对吗？

**5（选择）** 一个用 C++ 写的插件 `.so`，主程序用 `dlsym(h, "process")` 取函数却拿到 NULL，最可能的原因是：
- A. 忘了加 `-ldl`
- B. 插件没用 `-fPIC` 编译
- C. `process` 没有用 `extern "C"` 声明，符号被改编成 `_Z7processi`
- D. `dlopen` 的路径写错了

**6（应用）** 分发一个 C++ 程序到没装开发工具的目标机，既要让它能跑、又不想体积太大，该怎么编译？

<details><summary>参考答案</summary>
1. B。名字改编是 C++ 独有（因重载），C 没有这个问题。头文件重复包含两边都有，`.o` 格式也通用。
2. 对。两者都防重复包含。`#pragma once` 更简洁但非标准（虽主流支持）；`#ifndef` 是标准 C/C++，可移植性最好。
3. `Sales_item.cpp` 没参与编译/链接。要写 `g++ main.cpp Sales_item.cpp`，或分开 `g++ -c main.cpp`、`g++ -c Sales_item.cpp` 再 `g++ main.o Sales_item.o`。
4. **不完全对**——结论对，机制错。`.a` 是 `.o` 的归档，链接器只抽取**能补齐当前未定义符号**的成员（实测：`.a` 里没人调用的 `unused.o` 不会进最终二进制）。体积暴涨是因为 `-static` 把 libc 的间接依赖（locale/iconv 等）连带拉了进来，不是整包拷贝。
5. C。name mangling：`nm -D` 里看到的是 `_Z7processi` 而不是 `process`。A 的后果是链接期报 `undefined reference to dlopen`，B 会导致 `dlopen` 阶段失败，D 会让 `dlopen` 本身返回 NULL 而不是 `dlsym` 失败。
6. `g++ -std=c++17 main.cpp -o app -static-libstdc++`。把 C++ 运行时静态链进去，目标机不必有匹配版本的 `libstdc++.so.6`；libc 仍保持动态，体积比全静态小（实测 1.5 MB vs 2.25 MB）。若要完全自包含再用 `-static`。
</details>
