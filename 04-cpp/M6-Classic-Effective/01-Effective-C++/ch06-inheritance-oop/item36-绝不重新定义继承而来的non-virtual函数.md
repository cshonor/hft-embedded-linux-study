# 条款 36：绝不重新定义继承而来的 non-virtual 函数

## 本节讲什么

**Never redefine an inherited non-virtual function.** 非虚函数没有多态——
派生类"重新定义"它，得到的不是覆盖而是**两个共存但按静态类型选择**的函数。
同一对象，基类指针调基类版、派生类指针调派生版——行为随"看谁"而分裂，
is-a 合同当场作废。

← 上一条 [item35 虚函数以外的选择](./item35-考虑virtual函数以外的其他选择.md)；
下一条 [item37 别重定义缺省参数](./item37-绝不重新定义继承而来的缺省参数值.md)。

---

## 1. 现象：静态类型决定调谁（与 item33 同源但更危险）

```cpp
class Base {
public:
    void log() { std::cout << "Base::log\n"; }       // 非虚
};
class Derived : public Base {
public:
    void log() { std::cout << "Derived::log\n"; }    // 重新定义（不是 override！）
};
Derived d;
Base& b = d;
d.log();    // Derived::log
b.log();    // Base::log  ← 同一个对象，两张面孔
```

**机制**：非虚函数的调用在**编译期**按指针/引用的**静态类型**绑定——
`b` 的静态类型是 `Base&`，就调 `Base::log`，不管对象实际是 Derived。
这与虚函数的动态绑定（看对象实际类型）相反。

与 item33（名称遮掩）的关系：这是遮掩的**可调用版本**——
签名相同的重定义不是编译错误（编译器甚至不警告），是能正常编译运行的**语义分裂**。

## 2. 为什么这破坏了 is-a（item32 联动）

非虚函数的语义是"**接口和实现都不许动**"（item34 形态三）——
基类作者用它声明"这是不可变的行为契约"。派生类重定义它 = 单方面撕毁合同：

```cpp
class Order {
public:
    uint64_t id() const { return id_; }        // 非虚：id 语义全系统统一
};
class IocOrder : public Order {
public:
    uint64_t id() const { return ioc_id_; }    // 重新定义——
};                                              // 风控系统拿 Order& 看到的是另一个 id？
```

`risk_check(const Order& o)` 里 `o.id()` 调到 `Order::id()`，
`ioc.id()` 调到 `IocOrder::id()`——**同一个对象在系统不同模块里有两个 id**，
对账对不上的灵异 bug 就这么诞生。

## 3. 正确姿势（对照表）

| 你想要什么 | 正确做法 |
|---|---|
| 行为可被派生类定制 | **虚函数**（public 或 NVI 的私有虚，item35） |
| 行为不许定制 | 非虚函数 + **派生类不碰它**（本条） |
| 派生类需要"同名不同行为" | 说明设计错了——换名字（不同语义就该不同名），或回到虚函数 |
| 复用基类实现但收窄接口 | 私有继承 + using（item33/39），不是重定义 |

**自查**：派生类写了与基类**同签名**的非虚函数 → 99% 是 bug 或设计错误。
`-Woverloaded-virtual` 抓不到它（签名相同反而像 override），
所以更要靠纪律 + `override` 关键字：**所有想覆盖的函数都标 override**——
非虚函数标 override 直接编译错误，把"误覆盖"变成编译期拦截。

## HFT 关联

- **id/seq 类访问器是非虚函数的重灾区**：全系统对"订单 id 是什么"必须零分歧——
  这类函数就该非虚 + 不许重定义，分裂的 id 语义是对账事故的种子
- 协议解码器的 `decode()` 若设计为"骨架不可变"：非虚 + NVI 定制点（item35）——
  派生类重定义 decode() 的行为分裂会让回放/实盘解析结果不一致
- 纪律落地：**派生类函数能标 override 的全标**——
  标不上（编译错误）的那一刻就是"你在重定义非虚函数"的警报

## 代码自测

**题目 1：** `Base& b = d; b.log();` 为什么调到的是 `Base::log`？虚函数的话呢？

<details>
<summary>参考答案</summary>

非虚函数的调用在**编译期静态绑定**：编译器看 `b` 的声明类型（`Base&`），
直接把调用解析为 `Base::log`——运行期对象是什么类型与此无关。
虚函数则走**动态绑定**：编译期生成"经 vtable 间接调用"的代码，
运行期查对象实际的 vptr，调到 `Derived::log`。
"静态类型管非虚，动态类型管虚"——同一行 `b.log()`，加不加 virtual，
语义天差地别。

</details>

**题目 2：** 重定义非虚函数和 item33 的名称遮掩有什么关系？为什么本条更危险？

<details>
<summary>参考答案</summary>

同签名重定义是名称遮掩的**特例**：item33 是"同名不同签名"（基类重载被藏，
调不到的那几个直接编译错误——**失败在编译期，看得见**）；
本条是"同名同签名"——两个版本都能调到（按静态类型分派），
**不报错、能运行、结果错**。编译期失败的遮掩是好遮掩（逼你面对），
运行期分裂的重定义是静默陷阱——所以本条单独成款。

</details>

**题目 3：** 基类的非虚 `id()` 在派生类里真的需要不同语义，三个出路？

<details>
<summary>参考答案</summary>

① **改名**：语义不同就该名字不同——`ioc_id()` 与 `id()` 并存，
读代码的人一眼看出两个概念（推荐，最便宜）；
② **改虚函数**：若"按类型不同 id 语义不同"是真实多态需求，
基类 `virtual uint64_t id() const` + 派生 override——
但要先回答"为什么 Order 体系里 id 会有两种语义"（多半是模型错了）；
③ **重设计**：id 语义分裂通常意味着该拆类型——
IOC 的特殊标识放自己的成员（`ioc_seq_`），别碰 id。
永远不在选项里的就是：重定义非虚函数。

</details>
