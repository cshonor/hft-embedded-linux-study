Item 32

条款 32：面向未来做程序设计（兼容与扩展的设计思想）

本节讲什么

Design for the future: extensibility and backward compatibility. 软件活的时间总比预期长——协议会升级、需求会演化、库会有 v2。 面向未来设计不是"提前实现所有功能"（YAGNI），而是让未来的变化 有地方落脚：版本协商、扩展点预留、ABI 稳定层。 本条给出协议/接口/数据三个层面的兼容手法。

← 上一条 item31 多重分派； 下一条 item33 非叶子类抽象。

1. 协议层：版本化与扩展字段

struct MsgHeader {
    uint16_t msg_len;
    uint8_t  msg_type;
    uint8_t  version;          // ← 版本字段：新老协议共存的门票
    uint32_t seq;
    uint8_t  reserved[8];      // ← 预留字段：未来扩展不破坏布局（→ 19.5 的 static_assert 钉住）
};

三原则： - 版本字段从第一天就有（哪怕永远 1——没有它，升级时新老消息无法区分） - 预留空间（reserved/padding——扩展字段时老代码按旧布局读仍正确： 老代码跳过不认识的部分，新代码读新字段） - 未知字段容忍（解析时"读我认识的，跳过其余的"—— 老版本遇到新版本消息能降级而不是爆炸）

inline namespace 版本化（→ 18.2 ④）是同思想在符号层的实现： v1/v2 库符号共存，老二进制链旧版。

2. 接口层：扩展点与回调

手法 适用 例子
回调/钩子注册 行为扩展（新策略不改框架） 引擎的规则注册表（→ item35 策略对象）
接口版本协商 插件/库跨版本 abi_version() + dynamic_cast 校验（→ item27 插件）
能力位（feature flags） 运行时特性开关 if (features & FOK_SUPPORTED)（协议能力位）
尾部预留 + 默认值 配置/参数演化 配置结构体新字段带默认值，老配置照读

反模式：为想象中的扩展性提前抽象（每个类都接口化 + 工厂 + 插件架构）—— YAGNI 的代价是复杂度爆炸。正确姿势：在"变化一定会来"的接缝处 （协议/插件/跨团队接口）留扩展点，内部实现保持简单。

3. 数据层：持久化与演进的兼容

  • 格式版本头：落盘文件/快照/日志带格式版本（回放 3 个月前的行情日志， 解码器必须认得旧格式——协议博物馆的维护义务）
  • 只加不改：持久化 schema 的演进规则（新字段可加、旧字段不改语义不删—— 删字段用"废弃标记 + 双写过渡"）
  • 回放测试：golden 数据（→ 19.2 自测三）——每次格式演进， 老数据必须能回放（兼容性不是声明出来的，是测出来的）

HFT 关联

  • 交易所协议年年升级是常态——版本字段 + 预留 + inline namespace 三件套 让"协议升级"从全所停机变成灰度切换（→ 18.2 ④ 的库版本化）
  • 策略参数 schema 的演进（回测结果要可复现）： 参数集版本化 + 快照回放——半年前的回测配置今天还能跑出同样结果， 这是研究可信度的底线
  • ABI 版本协商在插件型架构（第三方策略 .so）是生存线（→ item27 的场景一： 加载时 dynamic_cast 校验接口版本）

代码自测

题目 1： "预留字段"（reserved）和 YAGNI 矛盾吗？

参考答案

不矛盾——YAGNI 反对的是"提前实现功能"（写可能永远用不到的代码）； 预留字段是"提前留空间"（几个字节，零实现成本）。 协议布局一旦上线就被全网冻结（无数对端按当前布局解码）—— 将来加字段没有地方放，只能要么破坏兼容（老代码读错位） 要么发新 msg_type（整条消息族翻倍）。 8 字节的 reserved 是"用零成本买未来的选项"—— 和"提前实现新字段的处理逻辑"（那才是 YAGNI 反对的）完全两回事。 判别：预防的是布局/接口这种事后改不了的东西 → 预留合法； 预防的是逻辑这种随时能加的东西 → YAGNI。

题目 2： 设计"老代码读新消息"的降级兼容，三个要点？

参考答案

① 长度字段：消息头带 msg_len——老代码按长度跳过整条不认识的消息 （而不是按自己理解的布局硬解，错位读垃圾）； ② 未知字段容忍：解析器"读认识的字段，跳过 msg_len 内的其余字节"—— 新版本加的字段对老版本透明（XML/JSON 时代的"忽略未知键"的协议版）； ③ 能力探测：握手时交换版本/能力位—— 对端不支持新特性就不发（if (peer.cap & FOK_BIT) send_fok();）—— 比"发了被 NACK"优雅一个量级。 核心思想：布局里必须有"我可以不认识你"的通道—— 长度字段是这条通道的钥匙（→ 19.5 协议结构体的验收纪律配套）。

题目 3： 策略参数 schema 要支持"半年前的回测配置今天可复现"，设计要点？

参考答案

① 参数集版本化：{schema_version: 3, params: {...}}—— 加载器按版本分派解析（v2/v3 参数结构不同都能读）； ② 只加不改：新参数可加（带默认值——老配置没它也能跑）， 旧参数不改语义不删（废弃的标记 deprecated 但继续识别）； ③ 快照即证据：回测结果与完整参数快照一起落盘—— 复现 = 加载快照重跑，不是"凭记忆重新配一遍"； ④ golden 回放：每个版本的关键参数组合留 golden 输入+输出—— schema 演进后老 golden 必须跑出相同结果（兼容性测试， 不是声明）。这套的本质：研究可信度建立在"任何历史实验 可在任何未来时刻精确重演"——schema 兼容是它的技术前提。

Item 33

条款 33：把非叶子类设计为抽象类，强制约束子类实现接口

本节讲什么

Make non-leaf classes abstract. 继承体系里，"中间类"（既被继承又继承别人） 如果可以被直接实例化，常常是建模事故：它不代表任何真实概念， 却允许用户创建一个"什么都不是"的对象。 把非叶子类设计为抽象类（含纯虚函数），让"只能继承、不能实例化" 成为编译期约束。

← 上一条 item32 面向未来设计； 下一条 item35 标准演进。

1. 问题：可实例化的中间类是建模漏洞

class FeedMessage {                  // 中间类：有公共字段（seq/ts），
public:                              // 但"一条 generic 行情消息"是什么？
    uint64_t seq; int64_t ts;
    virtual ~FeedMessage() = default;
};
class SnapMsg : public FeedMessage { /*...*/ };
class TradeMsg : public FeedMessage { /*...*/ };

FeedMessage m;      // ✅ 能编译——但它是什么？既不是快照也不是逐笔，
                    //    处理代码收到它该怎么办？（语义空洞的对象合法存在）

FeedMessage 存在的意义是"公共接口 + 公共字段的载体"—— 它不对应任何真实消息。允许实例化 = 允许语义空洞的对象在系统里流动， 每个处理点都要为"这到底是什么"埋单（→ 18.4 的 RTTI 滥用正是这么开始的）。

2. 解法：纯虚函数强制抽象

class FeedMessage {
public:
    uint64_t seq; int64_t ts;
    virtual MsgType type() const = 0;        // 纯虚：派生类必须表态"我是谁"
    virtual ~FeedMessage() = default;
};
// FeedMessage m;      // ❌ 编译错误：抽象类不能实例化——
                        // 只有具体消息类型（Snap/Trade）能存在

效果： - 编译期强制：派生类必须实现 type()（否则派生类也是抽象的）—— "忘了实现"从静默 bug 变编译错误（→ Effective item34 的纯虚语义） - 语义完整：系统里流动的每个消息对象都有具体身份—— type() 字段 + switch 的分发（→ 18.4 HFT 关联）有了完整性的类型保证

3. 边界：什么时候中间类可以具体

  • 它本身就是完整概念：class IocOrder : public Order {}—— 若 Order 就是"普通限价单"（完整语义，实盘大量存在）， 它该是具体的；IOC 是特例派生——判别：这个类有独立的业务含义吗
  • CRTP 基类：StrategyBase<Derived> 本来就只为被继承存在—— 模板基类没有"直接实例化"的通道（实例化要 Derive 参数）， 不需要抽象类约束（→ Effective item35 CRTP）
  • 注意与 item32 的区别：本条管"类型层次的完整性"， item32 管"演化的兼容性"——抽象基类的 type() 字段同时服务两者 （新消息类型 = 新派生类 + 新枚举值，编译期强制各处分发更新）

HFT 关联

  • 消息体系的 type() 纯虚 + switch 分发是行情处理的骨架： "每条消息都有明确类型"由编译器保证——分发表的穷尽性检查 （-Wswitch，→ 19.2 ③）才有意义
  • 策略基类的"纯虚 on_tick"（→ Effective item34 HFT）同款： 策略对象不允许"什么都不处理"地存在——能实例化的基类策略 上线就是静默不接单的事故
  • 抽象类 + 工厂（create(msg_type) -> unique_ptr<FeedMessage>）： 反序列化的标准形态——工厂按 type 字段构造具体类， 返回类型是抽象基类指针（异构容器的入口）

代码自测

题目 1： 为什么"可实例化的中间类"是建模漏洞？它制造了什么成本？

参考答案

中间类（如 FeedMessage）的存在意义是"公共接口/字段的载体"—— 它不对应任何真实实体（没有"generic 行情消息"这种东西）。 允许实例化 = 语义空洞的对象合法存在：① 每个处理点被迫考虑 "收到一个什么都不是的对象怎么办"（防御代码扩散）； ② 它成为 RTTI/类型探测的温床（处理代码不知道它是 Snap 还是 Trade 还是"那个中间物"——18.4 的 dynamic_cast 链就是这么长出来的）； ③ 新成员的默认值埋雷（中间类的字段被"默认构造"出一个 看似合理实则无意义的值）。抽象化后：不存在成为编译期事实—— 语义完整性从"靠纪律"升级为"靠类型系统"。

题目 2： virtual ~T() = default 和"抽象类"是什么关系？纯虚析构行吗？

参考答案

正交但常相伴：虚析构管"经基类指针 delete 的安全"（Effective item21 的特例）， 抽象化管"不许直接实例化"——基类通常两个都要 （virtual ~Base() = default; + 至少一个纯虚函数）。 纯虚析构（virtual ~Base() = 0;）技术上可以——它让类抽象的同时 保留析构虚性；但必须提供定义（派生类析构会调基类析构， 链接时需要 Base::~Base() {} 的实现体）——这是个语言冷知识， 工程上更常见的是"虚析构 default + 另一个纯虚（如 type()）"的组合： 语义更清晰（type() 表达"抽象的业务原因"，析构只管安全）。

题目 3： CRTP 基类需要抽象类约束吗？为什么？

参考答案

不需要——CRTP 基类（template <typename D> class StrategyBase） 无法被直接实例化：写 StrategyBase<?> base; 时必须给出模板参数， 而参数就是派生类自己（StrategyBase<MyStrat> 只在 MyStrat 的定义语境 才有意义）——"脱离派生类实例化基类"在语法上就构造不出来。 这就是 CRTP 相对经典继承的一个隐藏优势： "只能继承不能实例化"是结构自带的，不需要纯虚函数来强制 （还顺带零 vptr——Effective item35 的编译期多态）。 对照：经典继承的中间类没有这层结构保护， "可实例化"是默认状态——所以本条（抽象化）是经典继承的义务， CRTP 体系里是免费获得的。

Item 34

条款 34：C++ 和 C 混合编程的规范、链接、命名修饰与库兼容

本节讲什么

Mix C and C++ correctly: linkage, name mangling, and library compatibility. C++ 靠名字修饰（name mangling）支持重载/命名空间——feed_handler(int) 在符号表里是 _Z12feed_handleri；C 没有修饰，符号就是 gateway_recv。 两种链接约定的交界处（C 库给 C++ 用、C++ 函数给 C 回调）， extern "C" 是唯一的桥。本机 g++ 13.3 + nm 实测修饰差异。

← 上一条 item33 非叶子类抽象； 下一条 item35 标准演进。

1. 名字修饰的实测对照（nm 证据）

void feed_handler(int x) { /*...*/ }                    // 普通 C++ 函数
extern "C" void gateway_recv(const char* data, int len) { /*...*/ }   // C 链接

本机实测（nm 输出）：

0000000000000000 T _Z12feed_handleri      ← C++：_Z + 12(名长) + feed_handler + i(int 参数)
0000000000000050 T gateway_recv           ← extern "C"：纯名字，无修饰

规则： - C++ 编译器默认修饰（重载需要签名进符号：f(int) 和 f(double) 是两个符号） - extern "C" 关闭修饰——该函数放弃重载/命名空间（同名只能有一份） - 后果：C 代码（或 C ABI 库）按纯名字 gateway_recv 找符号—— 没 extern "C" 的 C++ 函数它根本找不到（链接错误：undefined reference）

2. 三个典型场景与正确写法

场景一：C 库给 C++ 用（头文件共享）

/* feed_api.h——C 库的头文件，要同时被 C 和 C++ 包含 */
#ifdef __cplusplus
extern "C" {
#endif

int feed_connect(const char* addr);
int feed_subscribe(int channel);
void feed_close(void);

#ifdef __cplusplus
}
#endif

#ifdef __cplusplus 守卫是标准形态：C 编译器看不到 extern "C"（C 不认识它）， C++ 编译器看到并关闭修饰——同一个头，两种编译器各自正确。 （交易所 SDK、系统库的头文件全是这个形态。）

场景二：C++ 函数注册为 C 回调

extern "C" void on_tick_c(const TickC* t) {    // C 链接：C 库能按名字找到
    MyEngine::instance().on_tick(convert(t));  // 立即转入 C++ 世界
}
// 注册：c_library_set_callback(on_tick_c);——函数指针跨越语言边界

注意回调里的异常纪律：异常飞出 C 边界 = UB（→ MoreEff item13 的边界翻译层）。

场景三：C++ 库给 C 用（反向输出）

导出层（facade）：C++ 类包一层 extern "C" 的函数族 + 不透明指针——

extern "C" {
    void* engine_create(const char* cfg) { return new Engine(cfg); }
    void  engine_run(void* e) { static_cast<Engine*>(e)->run(); }
    void  engine_destroy(void* e) { delete static_cast<Engine*>(e); }
}
// C 侧：void* 就是句柄——C 永远看不到 C++ 类型（opaque handle 模式）

3. 混编的其他三个坑

坑 内容 对策
头文件语言归属 .h 被两种编译器包含时，C++ 语法（类/模板/引用）必须在 #ifdef __cplusplus 里 共享头只放 C 子集（POD/函数声明）
静态初始化顺序 C 库与 C++ 全局对象的初始化顺序跨语言不可控 显式 init 函数（gateway_init()）代替全局构造（→ Effective item47 的 NIF 手法）
ABI 细节 结构体布局（对齐/位域）、bool 尺寸、枚举底层类型跨编译器可能不同 共享结构体定宽类型 + static_assert（→ 19.5 三件套）

HFT 关联

  • 交易所 SDK 全是 C ABI（FIX 引擎/柜台 API）—— extern "C" 回调注册 + 异常边界翻译（item13）是每个网关的入门两件套
  • 策略层 C++、网关层 C 的边界用 opaque handle（场景三）： C 侧永远拿不到 C++ 类型——ABI 边界稳定（C++ 类随便改，C 侧不用重编， → Effective item31 的编译防火墙同款思想）
  • 共享行情结构体的跨语言布局：#pragma pack/定宽类型 + static_assert—— C 的解析器和 C++ 的解码器对同一字节的理解必须钉死（→ 19.5 纪律）

代码自测

题目 1： 为什么 C++ 需要名字修饰而 C 不需要？extern "C" 放弃了什么？

参考答案

C++ 支持重载（同名不同参）和命名空间（同名不同域）—— 纯函数名无法区分 f(int) 与 f(double)、a::f 与 b::f： 编译器把签名编进符号名（_Z12feed_handleri = _Z + 名长 + 名 + 参数类型码， 本机 nm 实测），链接器按修饰名精确匹配。 C 没有重载/命名空间——符号就是函数名本身，无需修饰。 extern "C" 放弃的就是这两样：该函数不能重载（同名只能一份）、 不进命名空间——换来 C ABI 兼容性（C 代码按纯名字找到它）。 所以 extern "C" 只用于"必须跨语言"的边界函数，C++ 内部函数滥用它 = 自废重载/命名空间武功。

题目 2： C 库的头文件要被 C++ 包含，标准写法是什么？各部分的原理？

参考答案 
#ifdef __cplusplus
extern "C" {
#endif
/* 函数声明（C 子集：无类/模板/引用） */
#ifdef __cplusplus
}
#endif

三段原理：① __cplusplus 宏只有 C++ 编译器定义—— C 编译器走不到 extern "C" 分支（C 不认识这个关键字，ifdef 把它藏起来）； ② extern "C" 块：C++ 编译器对块内声明关闭名字修饰—— 与 C 库编译出的纯名符号对上（否则 C++ 按 _Z... 找符号， undefined reference）； ③ 块内必须是 C 子集：函数声明用 C 类型（POD/指针/定宽整型）， 类/模板/引用参数一律不许出现（C 编译器过不去）。 系统头（stdio.h/pthread.h）和交易所 SDK 全是这个形态—— 照抄就是最稳的实践。

题目 3： C++ 的引擎要给 C 策略层用，设计导出层的三个要点？

参考答案

① opaque handle：C 侧只持有 void*（或 typedef 的句柄类型）—— C 永远看不到 C++ 类型定义，Engine 内部随便改（ABI 防火墙， → Effective item31 的编译依赖思想跨语言版）； ② 函数族导出：create/run/destroy 全套 extern "C"—— 生命周期函数（create/destroy）必须配对且文档写清所有权 （C 侧没有 RAII，泄漏防控靠纪律 + 句柄有效性校验）； ③ 异常边界：每个导出函数内部 try-catch(...)—— 异常飞出 extern "C" 边界 = UB（C 侧没有展开机制， → MoreEff item13 的位置二），错误必须翻译成返回值/错误码。 配套：版本协商函数（engine_abi_version()）—— C 策略和 C++ 引擎独立发版时，版本握手是生存线（→ item32 面向未来设计）。

Item 35

条款 35：理解 C++ 标准演进的方向，写与时俱进的代码

本节讲什么

Understand where C++ is heading, and write code that ages well. More Effective C++（1996）的这条收尾最有先见之明：书里"未来的特性" （智能指针/移动语义/concepts）今天都是现实。本条按 2026 视角总结： 哪些写法在升值（越来越主流），哪些在贬值（正在被替代）—— 写"不过时"的代码，就是站在演进方向的同侧。

← 上一条 item33 非叶子类抽象； More Effective C++ 全 35 条至此完结。

1. 演进的主线（三十年一句话）

C++98（抽象机器 + RAII）→ C++11（移动语义 + 类型安全复兴）
→ C++14/17（库补全 + 编译期能力：optional/variant/string_view/if constexpr）
→ C++20（concepts/ranges/coroutines/modules：抽象表达能力换代）
→ C++23/26（expected/reflection/sender-receiver：错误处理与并发的新范式）

主线：运行期 → 编译期（计算前移）、隐式 → 显式（契约显式化）、 手写 → 标准设施（轮子收编）、继承多态 → 组合/变体（类型组合取代层次）。

4. "不过时"的判断标准（写代码时的自问）

□ 这段代码表达的是"意图"还是"机制"？
  → 意图（optional/expected/concepts）抗衰；机制（手写调度）易腐
□ 它在编译期还是运行期？
  → 能前移的都该前移（编译期计算/检查只会越来越强）
□ 它的契约是类型系统强制的吗？
  → 类型强制（nodiscard/抽象类/定宽类型）比注释/文档活得久
□ 标准库/标准委员会在往这个方向走吗？
  → 同向的写法会被持续优化（实现、工具、教学全生态投入）

题目 1： C++ 三十年演进的主线是什么？它如何指导"写法选择"？

参考答案

四条主线：① 运行期 → 编译期（计算/检查前移：模板元编程 → constexpr → consteval → reflection——能编译期做的越来越该编译期做）； ② 隐式 → 显式（契约显式化：注释 → 类型约束 → concepts）； ③ 手写 → 标准设施（轮子收编：bind → lambda、TR1 → std::、 手写错误码 → expected）； ④ 继承多态 → 组合（类型组合取代层次：虚函数 → variant/策略注入/CRTP）。 写法选择的推论：站在四条主线的同侧—— 新代码默认编译期优先、契约显式、标准设施优先、组合优先于继承； 逆势的写法（手写运行时调度、注释当契约、自造轮子、继承复用） 在五年后都会显得古老。

题目 2： 为什么"表达意图的代码"比"表达机制的代码"更抗衰老？

参考答案

意图代码绑定的是问题（"这里需要一个可空值"——optional）， 机制代码绑定的是当时的实现手段（"用 -1 表示无效"——魔数）。 问题比手段长寿：五年后 optional 仍是答案，而魔数已经人人喊打； concepts 表达的"T 必须可流输出"十年后仍清晰， 而 enable_if 的模板元编程嵌套五年后就没人愿意碰。 更深一层：意图代码能被工具理解——编译器检查 optional 的解包、 concepts 的约束、nodiscard 的忽略；机制代码对工具透明 （编译器不知道你的 -1 是什么意思）。 抗衰老的本质：代码被理解（人 + 工具）的成本随时间不增长—— 意图直白 + 工具可查，是唯一可靠的配方。

题目 3： 用本条的"四问"审计：协议消息结构体 Tick 和设计它的新代码，怎么写最不过时？

参考答案

① 意图 vs 机制：字段语义显式（side: Buy/Sell 枚举类而非 0/1 魔数， → 19.2 的 enum class）——意图抗折旧； ② 编译期 vs 运行期：布局用 static_assert(sizeof(Tick) == N) 钉死 （→ 19.5 三件套）——布局漂移在编译期爆炸而不是盘中； ③ 类型强制：定宽类型（int64_t/uint16_t，→ 19.2 定宽枚举）+ trivially copyable 守卫（→ 19.8）——"可 memcpy 上网线"是类型检查 不是口头约定； ④ 演进同侧：版本字段 + 预留 + 只加不改（→ item32 协议层三原则）—— 协议演进的通道从第一天就在。 结论：不过时的 Tick = 定宽 POD + enum class + static_assert + 版本化——这套组合在 C++98 能写，在 C++26 仍然是最佳实践： 它不依赖任何"当下流行"的特性，只依赖"永远正确"的原则 （显式、可验证、兼容演进）。

extern "C" 的作用是什么？为什么需要它？

答案与复习指引

extern "C" 的作用： 禁止 C++ 的 name mangling（名称修饰），让 C++ 编译器生成 C 风格的符号名（c_function 而非 _Z11c_functioni），以便 C 代码链接。

为什么需要： C++ 编译器会对函数名做修饰（编码参数类型到符号名中，支持重载）。C 编译器不做修饰。混合链接时符号名不匹配 → 链接错误。

典型场景： - C++ 调用 C 库（#include <cstdint> 等 C 头文件内部已用 extern "C"） - C 调用 C++ 库（C++ 函数需 extern "C" 导出） - 嵌入式/HFT 混用 C 驱动 + C++ 业务逻辑

复习： → 条款 34：C++ 和 C 混合编程

Q2非叶子类设计为抽象类
// 方案 A: 具体基类
class Animal {
public:
    virtual void sound() { std::cout << "..."; }
    virtual ~Animal() {}
};
// 方案 B: 抽象基类
class Animal2 {
public:
    virtual void sound() = 0;  // 纯虚
    virtual ~Animal2() {}
};

为什么建议把非叶子类设计为抽象类？

答案与复习指引

抽象基类优势： 1. 强制实现接口：派生类必须实现 sound()，不能"忘记" 2. 防止误实例化：Animal2 a; 编译错误——不能创建抽象类对象。这符合"Animal 是抽象概念，不该直接实例化"的语义 3. 防止对象切片：不能值传递 Animal2，只能通过指针/引用操作

具体基类问题： Animal a; 合法——你可以创建一个"不知道发出什么声音的动物"，这在语义上是荒谬的。而且值拷贝会导致对象切片。

规则： 非叶子类（可能被继承的类）设计为抽象类（至少一个纯虚函数），叶子类（不会被继承的类）可以是具体类。
