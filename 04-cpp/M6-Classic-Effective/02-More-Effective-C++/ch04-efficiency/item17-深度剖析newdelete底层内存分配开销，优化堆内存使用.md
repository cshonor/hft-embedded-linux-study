# 条款 17：剖析 new/delete 的底层开销，优化堆内存使用

## 本节讲什么

**Understand the costs of new/delete and optimize heap usage.**
一次 `new` 的价格远超直觉：它不是"一条指令"，而是
**分配器锁 + 尺寸分档查找 + 可能的系统调用 + 构造函数**的复合体。
本条把开销拆开（→ 19.1 的机制层、06.6.5 ch07 的实测层的桥梁），
给出"什么时候必须池化"的量化判别。

## 1. 一次 new 的完整成本解剖

```
new T 的真实成本（glibc malloc，典型 x86_64）：
  ① operator new → malloc：
     - 线程缓存（tcache）命中：~20-50ns      ← 最好情况
     - tcache 未命中 → 中央堆 + 锁竞争：~100-500ns
     - 大块（>128KB）→ mmap 系统调用：~1-10µs（含页错误）
  ② T 的构造函数：类型复杂度决定（POD≈0，含 string/vector 的成员 = 又一轮 malloc）
  ③ 首次触碰页错误（新页）：~数百 ns/页
delete 的成本通常低于 new（tcache 归还），但同样参与锁竞争
```

**关键事实**：
- malloc 是**通用**分配器——为各种尺寸/线程/生存期模式折中，
  你的特定模式（固定尺寸、单线程、批量释放）它并不专门优化
- 成本**不可预测**：tcache 命中率、锁竞争、mmap 时机——
  同样一次 new，p50 和 p999 差两个数量级（→ 06.6.5 ch07 的实测）
- 析构链同样昂贵：`delete container_of_objects` 是 N 次析构 + N 次 free 的串联

## 2. 什么时候必须池化（量化判别）

```
信号①：profile 里 malloc/free 占比 > 5%（perf record，→ 06.6.5 ch06）
信号②：分配模式高度规律（固定尺寸的订单/行情对象，每秒数万次）
信号③：延迟预算 p99 < 10µs，而 malloc 的 p999 已经超过预算
信号④：多线程分配（锁竞争随核数恶化——tcmalloc/jemalloc 也救不了全部）
满足任意两条 → 池化；全不满足 → 默认分配器（别过度工程）
```

## 3. 池化的收益结构（为什么快一个量级）

| 维度 | malloc | 专用池 |
|---|---|---|
| 查找 | 尺寸分档 + 空闲链表遍历 | **freelist 头插法 O(1)**（弹一个指针） |
| 锁 | 全局/arena 锁 | 单线程域**无锁**（或 per-CPU 池） |
| 元数据 | 每块 8-16B 头 | 零（sized delete 传尺寸，→ 19.1 ②） |
| 缓存 | 块分散（年代久远） | **预分配连续**——顺序访问局部性好 |
| 可预测性 | p50/p999 差 100× | 常数时间（池空 = 显式失败，→ item49 HFT） |

## 4. 与通用优化的关系（别跳过这一步）

池化前的标准动作（→ Effective item50 ②）：
1. **先减分配次数**（临时对象治理，→ item16）——最好的池化是不需要池
2. **换通用分配器**（LD_PRELOAD jemalloc/tcmalloc，→ item50 ③）——
   零代码成本，多线程收益立竿见影
3. **再池化特定热点类型**（item49 类内重载 / item18 自定义池）——
   影响面最小、收益最集中

## HFT 关联

- 交易系统的答案从来不是"优化 malloc"而是**消灭运行期 malloc**：
  启动时池化一切（订单/回报/行情消息），运行期只剩 acquire/release
  （→ 19.1 HFT 的铁律）——本条的量化判别在交易系统里全部命中
- 池的"显式失败"语义（item49 ③：池空 = 容量事故当场爆炸）比 malloc 的
  "变慢/碎片化"诚实——容量问题在测试期暴露，不带进生产
- mmap 大块分配的页错误成本：启动预分配后 **prefault**（每页写一次
  或 `MAP_POPULATE`/`mlock`）——把页错误从运行期挪到启动期（→ 03/13 的大页实践）

## 代码自测

**题目 1：** 为什么说 malloc 的成本"不可预测"？这对延迟预算意味着什么？

<details>
<summary>参考答案</summary>

malloc 的成本依赖运行时状态：tcache 命中与否（几十 ns vs 几百 ns）、
中央堆锁竞争（随并发恶化）、尺寸是否触发 mmap（µs 级系统调用）、
碎片化程度（随运行时长恶化）——p50 和 p999 差两个数量级。
延迟预算管的是**尾延迟**（p99/p999，→ 06.6.5 ch02）：
一个 p50 很快但 p999 超预算的组件，等于预算里没有它。
这就是"运行期零分配"铁律的本质——不是 malloc 平均慢，
是它的**尾部**没有位置。池化的价值首先是**确定性**（常数时间），
其次才是平均速度。

</details>

**题目 2：** 池化前为什么要"先减分配次数、再换通用分配器、最后才池化"？

<details>
<summary>参考答案</summary>

按**成本/收益比**排序的工程顺序：
① 减分配（item16 临时对象治理）——零风险纯收益，
很多"池化需求"在临时对象清完后直接消失（本来分配就不多）；
② LD_PRELOAD 换 jemalloc/tcmalloc——零代码成本，
多线程场景的锁竞争立刻缓解（通用分配器的 15 年工业优化，别手写对抗它）；
③ 池化特定类型（item49/item18）——有正确性成本（item51/52 的常规全要守）、
维护成本、容量规划成本，只给 profile 证明的热点类型用。
跳过前两步直接池化 = 用最高的成本解决可能已经不存在的问题——
性能工程的第一课：先量化，再动手（06.6.5 ch02）。

</details>

**题目 3：** 启动预分配后为什么还要 prefault/mlock？

<details>
<summary>参考答案</summary>

池的内存来自一次性大块分配（new/mmap）——但 Linux 的分配是**懒分配**：
mmap 只建虚拟地址映射，**物理页在首次触碰时才分配**（页错误中断，
每页几百 ns + 可能缺页换出）。
不 prefault 的话，"池化"只是把页错误从 malloc 路径挪到了**首次使用路径**——
热路径第一笔订单照样吃页错误。
prefault（启动时每页写一字节）或 `mlock`/`MAP_POPULATE` 把物理页钉住：
页错误成本全部在启动期付清，运行期触碰零中断——
这是"把不可预测成本从热路径移到冷路径"的通用手法
（与 13-dpdk 大页（hugepage）同源：2MB 页把页错误数量再除 512）。

</details>
