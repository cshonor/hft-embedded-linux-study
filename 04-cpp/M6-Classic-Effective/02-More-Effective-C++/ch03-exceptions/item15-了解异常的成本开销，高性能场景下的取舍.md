# 条款 15：了解异常的成本开销，高性能场景下的取舍

## 本节讲什么

**Understand the costs of exception handling.** 异常的成本分**静态**（二进制体积、
优化阻碍）和**动态**（抛出时的查表与展开）两面——
"无异常时零成本"只说对了一半。本条把成本拆到可度量的层面，
给出高性能场景的完整取舍框架（→ 18.1 HFT 的量化版）。

← 上一条 [item14 异常规范](./item14-理解异常规范throw()的运行时机制、局限性与坑.md)；
下一章 [ch04 效率](../ch04-efficiency/)。

---

## 1. 成本一：静态面（不用异常也要付）

- **二进制体积**：每个可能抛出的函数都要生成 LSDA/展开表 + 清理动作表——
  典型可执行文件增大 5-15%（表驱动实现的"表"本身）
- **优化阻碍**：潜在的抛出点是优化的边界——
  寄存器分配/指令调度/内联决策在"可能抛"的调用前都变保守
  （noexcept 标注能把这些边界拆掉，→ item14）
- **I-cache 压力**：冷代码（异常路径）与热代码在同一函数体里——
  热循环的代码 footprint 被拉大（→ Effective item30 的 I-cache 讨论）

## 2. 成本二：动态面（抛出时才付，但付得狠）

```
throw 一次的典型成本构成（x86_64 Linux，libgcc 表驱动）：
  ① 异常对象拷贝构造          ~几十 ns（对象复杂度决定）
  ② __cxa_throw → _Unwind_RaiseException
     查 LSDA 表（personality routine 逐帧问）  ~µs 级起
  ③ 逐帧展开：每帧执行 landing pad + 局部对象析构
     深度 N 帧 ≈ N × (几十~几百 ns)
  ④ catch 匹配：RTTI 比较      ~几十 ns/catch
─────────────────────────────────────
  合计：µs 级，且**方差巨大**（表冷 cache、展开深度、析构复杂度）
```

对比：一次虚函数调用 ~1ns，一次错误码返回 ~0ns——
**一次 throw ≈ 几千次正常调用的成本，且不可预测**。
这就是为什么"tick-to-trade 预算里没有 throw 的位置"（18.1 HFT）。

## 3. "零成本"的精确含义（别被口号骗了）

表驱动实现（Itanium ABI，Linux/macOS 默认）的真实账本：

| 场景 | 成本 |
|---|---|
| 无异常抛出，正常运行 | **≈0**（表不执行）——"零成本"指这个 |
| 函数含 try/catch（即使不抛） | 微小（可能阻碍少量优化） |
| noexcept 函数 | 比零还少（展开代码被消掉） |
| **抛出** | **µs 级 + 高方差**——成本全部集中在这里 |

推论：异常的定价模型是**"免费保险，天价理赔"**——
用不用它的判断标准是"这条路会抛吗、抛得起吗"，不是"异常好不好"。

## 4. 高性能场景的取舍框架（分层决策）

| 层 | 错误机制 | 理由 |
|---|---|---|
| **热路径**（tick-to-trade） | 错误码 / `expected<T,E>`（C++23） | 显式、零成本、可预测（→ item54 expected） |
| **冷路径**（启动/配置/重连） | 异常 + RAII + 三级保证（Effective item29） | 代码清晰，µs 级成本无所谓 |
| **边界**（冷热交界） | 异常 → 错误码的**翻译层** | 冷世界的异常在边界 catch 住，转成热世界的错误码 |
| **禁用场景**（-fno-exceptions） | 全错误码 + new 的 nothrow 版（→ 19.1 ④） | 嵌入式/极致热路径库 |

**边界层示例**（交易系统标准形态）：

```cpp
int engine_reload_config() noexcept {          // 热世界入口承诺不抛
    try {
        auto cfg = load_config(path);          // 冷世界随便抛
        return apply(cfg) ? 0 : -1;
    } catch (const std::exception& e) {
        log_error("配置加载失败: {}", e.what());
        return -2;                              // 异常在边界翻译为错误码
    }
}
```

## HFT 关联

- 本条的量化结论直接支撑 18.1 HFT 的"主路径零异常"——
  预算 1-10µs 的 tick-to-trade 里，一次 throw 就是预算的几十倍
- `expected<T, E>`（C++23）把"错误的值语义"标准化：
  热路径错误的现代答案——比异常便宜、比裸错误码安全（强制检查，→ item54）
- 静态面成本（表体积）在**嵌入式/内核旁路**场景也要算账：
  `-fno-exceptions` 省的不只是运行期，还有二进制体积和 I-cache

## 代码自测

**题目 1：** "无异常时零成本"忽略了异常机制的哪些静态成本？

<details>
<summary>参考答案</summary>

① **二进制体积**：LSDA/展开表 + 清理动作表让可执行文件典型增大 5-15%——
表驱动实现把成本转移到了数据段；
② **优化阻碍**：潜在抛出点是编译器优化的边界——寄存器分配、指令调度、
内联决策在"可能抛"的调用前变保守（noexcept 能拆掉这些边界）；
③ **I-cache**：异常路径的冷代码与热代码同函数体，拉大 footprint
（→ Effective item30）。
"零成本"只描述运行期无异常路径无额外指令——
体积、优化、缓存的账一分没少。所以 noexcept（消展开代码）和
-fno-exceptions（连表都不生成）都有**即使不抛也真实存在**的收益。

</details>

**题目 2：** 一次 throw 的成本为什么"µs 级且高方差"？高方差为什么比高均值更致命？

<details>
<summary>参考答案</summary>

成本构成：查 LSDA 表（personality 逐帧问）+ 逐帧展开（每帧 landing pad +
局部对象析构）+ catch 的 RTTI 匹配——全部涉及**数据结构的指针遍历**：
表冷 cache、展开深度不定、析构复杂度不定，所以方差大。
高方差致命的原因：HFT 的延迟预算管的是 **p99/p999**（尾延迟，→ 06.6.5 ch02）——
均值 1µs 但 p99 50µs 的机制，比均值 2µs 但确定的机制**更不可接受**：
容量规划按尾延迟做，方差直接吃掉余量。
这就是热路径错误通道必须"显式 + 可预测"（错误码/expected）的根本原因——
不是异常平均慢，是异常**不可预测地慢**。

</details>

**题目 3：** 设计"冷路径用异常、热路径用错误码"的系统，边界层怎么写？

<details>
<summary>参考答案</summary>

边界层 = **noexcept 入口 + try-catch 翻译**：

```cpp
int engine_reload_config() noexcept {       // ① 对热世界承诺不抛
    try {
        auto cfg = load_config(path);       // ② 冷世界内部随便抛（RAII 兜底）
        return apply(cfg) ? 0 : -1;
    } catch (const std::exception& e) {
        log_error("配置加载失败: {}", e.what());
        return -2;                          // ③ 异常→错误码翻译（信息进日志）
    } catch (...) {
        log_error("配置加载失败: 未知异常");
        return -3;                          // ④ catch(...) 防火堤（→ item13）
    }
}
```

要点：① noexcept 是合同（违约 terminate，调用方敢 inline 敢优化）；
② 冷世界内部享受异常的全部表达力（错误从深处自然冒泡）；
③④ 两层 catch 保证**任何异常都死在边界**——热世界看到的只有错误码。
这套边界是交易系统"冷热分层错误机制"的标准形态（→ 18.1 HFT 的落地）。

</details>
