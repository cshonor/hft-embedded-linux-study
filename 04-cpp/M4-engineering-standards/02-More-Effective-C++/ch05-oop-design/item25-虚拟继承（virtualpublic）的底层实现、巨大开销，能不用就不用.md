# 条款 25：虚拟继承的底层实现与开销，能不用就不用

## 本节讲什么

**Understand virtual inheritance's implementation and costs — avoid it when possible.**
虚继承是解决菱形数据重复的语言机制，但它的实现代价（虚基表、间接访问、
构造跳级）使它成为"补救"而非"设计"。机制的完整推导与实测在 **18.3 ②**，
本条聚焦实现原理的补充与"不用它"的设计替代。

← 上一章 [ch04 效率](../ch04-efficiency/)；下一条 [item26 堆/栈创建限制](./item26-限制某个类只能在堆上创建只能在栈上创建的设计技巧.md)。

## 1. 底层实现：虚基表（vtable 之外的第二张表）

```cpp
struct A { int a; };
struct D : virtual A { };
struct E : virtual A { };
struct F : D, E { };        // A 只有一份（共享）
```

编译器的实现（Itanium ABI）：
- 每个虚继承的类，其 vptr 指向的表里除了虚函数指针，
  还有**虚基表（virtual base table）**：记录每个虚基子对象
  相对 this 的**偏移量**
- 访问虚基成员 `f.a`：`this → vptr → 虚基表查偏移 → this+偏移 → a`——
  **比直接成员访问多两次内存间接**（18.3 ② 的"虚基成员多一次指针间接"的精确机制）
- 布局上共享的 A 放在对象**尾部**（非固定位置——F 的布局里 A 偏移
  与 D 单独存在时不同，所以才需要运行期查表）

**18.3 ② 实测数据回顾**：`sizeof(F)=24`（两个 vptr + 共享 A + 对齐），
`sizeof(D)=16`——虚继承的尺寸税与间接税同时存在。

## 2. 三张税单（逐条对应免单方案）

| 税单 | 内容 | 免单方案 |
|---|---|---|
| 间接税 | 虚基成员访问 = 两次内存间接（查虚基表） | 接口 MI（基类无数据，没有"虚基成员"可访问，→ Effective item40） |
| 构造税 | **最派生类**直接构造虚基，中间层的初始化参数被忽略（18.3 ② 实测规则） | 菱形在设计上消灭——没有菱形就没有虚继承 |
| 转型税 | `F* → D*` 等向下/横向转型要查虚基表（运行期） | static_cast 只在"确定布局"的静态类型间用（热路径禁 RTTI/虚基转型） |

## 3. 设计替代（永远用不上虚继承的三种结构）

**替代一：接口 MI（首选）**

```cpp
class S : public MdSink, public OrderSink { };   // 两接口纯虚无数据——
                                                  // 无数据则无菱形，虚继承无从谈起
```

**替代二：复合拆分**（A 真的有两份语义时）

```cpp
// 菱形场景常是"两类数据硬挤一棵继承树"——
struct F { D d_; E e_; };      // 复合：d 和 e 各有自己的 A——
                                // 语义上"两份 A"本来就是对的，共享才是错误
```

**替代三：重分层**（A 的内容其实该上移/下移）

菱形继承的出现往往说明 A 装了**不属于同一层次**的东西——
把 A 的成员拆到"真正共享的基类"和"各自持有的成员"两层，
继承树退化为单链 + 接口（18.3 ③ 的工业界共识）。

## HFT 关联

- 交易系统的继承纪律一句话：**接口 MI 合法，数据 MI 报警，虚继承死刑**——
  代码库里出现 `virtual public` 就该是 design review 的红牌
  （→ Effective item40 的 HFT 关联同一结论）
- 虚基表的两次间接在热路径是双倍 cache miss 风险——
  而它常常藏在"看起来无害"的框架基类里（审查框架库的继承图，
  比审查自己的代码更重要）

## 代码自测

**题目 1：** 虚继承访问虚基成员为什么比普通成员访问慢？把访问链路写出来。

<details>
<summary>参考答案</summary>

普通成员：`this + 编译期固定偏移` → 一次内存访问。
虚基成员：`this → 加载 vptr → vptr 所指表中的**虚基表条目**（虚基偏移量）→
this + 偏移 → 成员`——**两次额外内存间接**（vptr 加载 + 虚基表查询）。
原因：共享的虚基子对象在不同派生层次下**偏移不固定**（F 里的 A 与
D 单独存在时的 A 位置不同）——编译期算不出固定偏移，只能运行期查表。
两次内存间接 = 两个潜在 cache miss——这就是"虚继承的间接税"的精确构成
（→ 18.3 ② 实测 sizeof 数据与布局）。

</details>

**题目 2：** "最派生类负责构造虚基"为什么会坑人？给个真实场景。

<details>
<summary>参考答案</summary>

规则：虚基 A 由**最派生类**（F）的构造函数直接初始化，
中间层（D/E）构造列表里给 A 的实参**被忽略**。
坑人场景：`class D : virtual A { D() : A(1) {} }`——
你单独 `new D` 时 A 用 1 构造（D 是最派生）；某天 F 继承了 D 和 E，
`F() : D(), E() {}` 忘了显式 `A(...)`——**A 被默认构造**，
D 构造里写好的 `A(1)` 静默失效：同一个 D，单独用和放进 F 里，
A 的初始值不一样（18.3 ② 自测题三的完整版）。
这类 bug 的阴险处：F 的代码看起来"什么也没做"——
但"什么也没做"恰恰是问题（虚基的初始化责任跳级到你头上了）。

</details>

**题目 3：** 已有代码里发现了菱形（A→B, A→C, D:B,C），三个处置方案的优劣？

<details>
<summary>参考答案</summary>

① **上虚继承**（最小改动）：`B/C : virtual A`——能跑，但收下全部三张税单
（间接/构造跳级/转型查表），且 ABI 变化（布局全变，依赖者重编译）——
适合"遗产代码续命"，不适合新设计；
② **拆复合**（推荐）：D 改为 `{ B b_; C c_; }`——每棵子树自己的 A 各自完整，
语义诚实（"两份 A"本来就是真实语义时），无间接税无跳级——
代价是接口要重写（D 的方法转发给 b_/c_）；
③ **重分层**（最彻底）：分析 A 的成员——真正该共享的上移为接口/单一基类，
各自特有的下沉为 B/C 的成员——继承树退化为单链 + 接口 MI，
菱形从设计上消失（→ Effective item40 的 MI 纪律）。
选型：新代码永远③；续命代码②；①只在"明天就要上线"时用——
并且把"偿还计划"写进 TODO。

</details>
