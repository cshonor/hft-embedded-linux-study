## 1. 开销总表（机制详见 18.3，实测数据引自该节）

| 特性 | 尺寸开销 | 调用开销 | 其他 |
|---|---|---|---|
| 单继承 + 虚函数 | 对象 +8B（vptr）；类一张 vtable | 间接跳转 ×1（1-5ns cache 命中） | 不可内联（item20） |
| MI（无虚继承） | 每带虚基类 +1 vptr；成员按声明序排（18.3 ① 实测 sizeof(C)=12） | 第二个基类起 **this 调整**（指针 +/- 偏移） | C 强转陷阱（18.3 ① void* 案例） |
| 虚继承（菱形） | vptr 带虚基表指针（18.3 ② 实测 F=24） | 虚基成员访问**多一次间接**；向下转型查虚基表 | 最派生类负责构造虚基（初始化跳级） |
| RTTI | 每多态类一个 type_info | dynamic_cast **沿链遍历**（18.4 ③） | -fno-rtti 可省（18.4 ⑤） |

## 2. 与决策的对应（每张成本单都有免单方案）

```text
vptr 的 8B 不可接受     → POD + 零虚函数（热路径数据结构铁律，→ 19.5）
间接跳转/不可内联        → CRTP / 查表 / variant（item20/35 的全部替代方案）
MI 的 this 调整与强转坑  → 接口 MI（数据单链 + 接口多继承，→ 18.3 ③）
菱形/虚继承             → 设计上消灭菱形（接口无数据，菱形无从形成，→ Effective item40）
dynamic_cast 链遍历     → 虚函数分发 / variant visit / msg_type 查表（item23 三方案）
```

**核心结论**：这些开销**没有一个是必须付的**——
C++ 的原则是"不用不付"（zero-overhead principle），
每一张账单都有对应的"不用"方案；本条的价值是让你**看懂账单**，
在 design review 时一眼认出"这里在为什么付费"。

## 3. 布局推理能力（review 必备）

给你一个类，能心算 sizeof——这是本条最实用的技能：

```cpp
struct A { virtual ~A(){} int a; };            // vptr(8) + int(4) + pad(4) = 16
struct B { virtual ~B(){} int b; };            // 16
struct C : A, B { int c; };                    // A 全量(16) + B 全量(16) + c(4) + pad = 40
                                               // （两个 vptr！18.3 ① 的 MI 布局）
struct D : virtual A { int d; };               // vptr(8) + d(4) + pad + 虚基 A 共享
                                               // → 18.3 ② 实测 sizeof=16（D）/ 24（F:D,E）
```

心算规则：vptr 每个带虚基类一份 → 成员按声明序 → 对齐到最大成员对齐数。
（→ M3 深度探索对象模型 ch03 有完整的布局推导；18.3 有本机实测对照。）

## HFT 关联

- **订单簿档位的尺寸账**（本条技能的实战）：目标每档 32B（两个一档 cache line）——
  有 vptr 就 40B（直接超线）：热路径类零虚函数不是洁癖是尺寸纪律
- MI 回调的 this 调整是**注册时**的坑（18.3 ① +4 实测偏移）：
  策略多接口（MdSink/OrderSink）注册 C 风格回调（void*）时，
  this 必须按接口类型 cast 好——错一次就是生产 crash
- 虚继承在交易系统**零出现**：接口 MI（Effective item40 用途二）
  让菱形在设计上不存在——不需要精通虚继承，只需要永远不写出它

## 代码自测

**题目 1：** `struct C : A, B { int c; };`（A、B 各带虚函数和 int）的 sizeof 是多少（x86_64）？布局如何？

<details>
<summary>参考答案</summary>

**40 字节**。布局：A 子对象全量 [vptr(8) + a(4) + pad(4) = 16] +
B 子对象全量 [vptr(8) + b(4) + pad(4) = 16] + c(4) + 尾部 pad(4)。
要点：MI 下**每个带虚函数的基类各带一个 vptr**（两张 vtable——
C 的对象既能当 A 用也能当 B 用，各查各的表）；
B 子对象不在对象开头——`B* pb = &c;` 的 pb 比 &c 偏移 16
（this 调整，18.3 ① 实测同类数据）。
这就是"MI 的尺寸税"：两个 vptr + 双份对齐填充。

</details>

**题目 2：** 为什么说"虚继承是补救不是设计"？

<details>
<summary>参考答案</summary>

虚继承解决的问题（菱形数据重复）是**设计错误**的症状——
两个带数据的基类被同一个派生类继承，本来就不该发生
（→ Effective item40：MI 最多一个基类带数据）。
虚继承的代价：对象带虚基表指针、虚基成员访问多一次间接、
最派生类跳级构造虚基、向下转型查虚基表（18.3 ② 全单）——
**为错误设计付的补救税**。
正确姿势是从设计上消灭菱形：接口 MI（第二及以后基类纯虚无数据）——
没有数据就没有重复，菱形无从形成，虚继承毫无用武之地。
所以本条的教学定位是"看懂它，然后永远不写出它"。

</details>

**题目 3：** 订单簿档位结构体从 40B 优化到 32B，列出要砍的三样东西。

<details>
<summary>参考答案</summary>

① **vptr（8B）**：去掉一切虚函数——档位是 POD
（→ 19.5 协议结构体纪律 + static_assert 钉布局）；
② **对齐填充**：成员按尺寸降序排列（8B → 4B → 2B → 1B），
把散落的 1-3B 填充收拢——`alignof` 由最大成员决定，
降序排列通常省 4-8B；
③ **元数据外挂**：档位本身不存"管理信息"（链表指针/标志位
挪到独立的索引结构或位域压缩，→ 19.5 ③ 位域打包）——
档位的每一寸都该是数据本体。
验收：`static_assert(sizeof(Level) == 32)` + `static_assert(alignof(Level) <= 8)`——
两个档位一条 cache line（64B），prefetch 一次拿两档（→ 06.6.5 ch06 的缓存纪律）。

</details>
