# 条款 13：合理使用 catch(...) 全局捕获，谨慎兜底

## 本节讲什么

**Use catch(...) judiciously.** `catch(...)` 捕获**一切**异常（含非 C++ 异常、
未知类型）——它是最后的防线，也是最危险的大网：
你接住了根本不知道是什么的东西，失去了按类型分派的可能。
本条给出 catch(...) 的三个合法位置与一堆滥用警告。

← 上一条 [item12 异常拷贝流程](./item12-抛出异常时，理解对象拷贝的完整流程与开销.md)；
下一条 [item14 异常规范的局限](./item14-理解异常规范throw()的运行时机制、局限性与坑.md)。

## 1. catch(...) 的三个合法位置

**位置一：线程入口的防火堤**——异常逃出线程函数 = `std::terminate`

```cpp
void worker_thread() {
    try {
        run();                      // 业务循环
    } catch (const std::exception& e) {
        log_fatal("线程异常: ", e.what());   // 先按类型拿到信息
        notify_exit(e.what());
    } catch (...) {                          // 兜底：防"非 std 异常"漏网
        log_fatal("线程异常: 未知类型");
        notify_exit("unknown");
    }
}
```

每个线程函数**必须**有这条防火堤——terminate 默认调 abort，
交易系统的一个工作线程死了整个进程陪葬（→ M3 并发）。

**位置二：库边界的异常翻译层**——C++ 异常不能跨 C ABI/语言边界飞

```cpp
extern "C" int gateway_entry(const char* req, char* resp) {   // C 回调入口
    try {
        return handle(req, resp);
    } catch (...) {                          // 一切异常都拦在边界
        set_error(resp, "internal error");
        return -1;
    }
}
```

异常飞出 C 边界 = 未定义行为（C 侧没有展开机制）——catch(...) 是边界义务。

**位置三：清理后的重抛**——`catch (...) { cleanup(); throw; }`

这里的 catch(...) 不为"处理"，只为"**经过**"：做完局部清理，
`throw;` 原样重抛（item12：不切片）——异常语义完全保留。

## 2. 滥用的四个警告

| 滥用 | 后果 |
|---|---|
| catch(...) 后**吞掉**（不记录不重抛） | 错误静默——OOM/逻辑错误全被吃，系统带病运行 |
| 用 catch(...) 替代按类型 catch | 失去分派能力（重试策略按错误类型走，→ item12） |
| 在中间层 catch(...) "以防万一" | 异常路径变隐式——上层永远不知道发生过什么 |
| 以为它能接**所有**错误 | **段错误/断言/整数除零接不住**——那些是信号不是异常（→ 03.6 ch2） |

**catch(...) 里能说的唯一信息是"出了某种异常"**——
没有 what()、没有类型、没有上下文。所以它只适合"防火堤/边界/过路清理"
三种不依赖错误内容的角色。

## HFT 关联

- 交易系统每个线程入口的三件套：`try { run(); } catch (const std::exception&) {...}
  catch (...) {...}` + **致命错误的上报通道**（监控进程，→ item48 的 OOM 预案同哲学）
- 策略回调的引擎侧包装：引擎调 `strategy.on_tick(t)` 时必须 catch(...) 兜底——
  一个策略的异常不能拖垮整个引擎（策略隔离，→ 14-hft 引擎设计）
- C 回调边界（交易所 SDK 多数是 C ABI）的异常翻译是**强制义务**：
  异常飞出 C 回调 = UB，crash 都算是好结局

## 代码自测

**题目 1：** 为什么线程函数必须有 catch(...) 防火堤？

<details>
<summary>参考答案</summary>

异常逃出线程函数 = `std::terminate` = 默认 `abort()` 整个进程——
工作线程（行情处理/订单执行）的一个未捕获异常，代价是**全系统陪葬**：
主线程、其他策略线程、网关连接全死。
防火堤（先按 std::exception 记日志，再 catch(...) 兜底未知类型）
把"线程级事故"限制在线程级：记录、上报、决定该线程是重启还是系统优雅停机。
这是 catch(...) 最无可争议的合法位置——
它不处理错误内容，只防止错误升级为进程死亡。

</details>

**题目 2：** `catch (...) { cleanup(); throw; }` 和 `catch (...) { cleanup(); }` 差在哪？

<details>
<summary>参考答案</summary>

一个 `throw;` 之差是**异常语义存亡**之别：
带 `throw;`——清理完成后异常原样继续向上（item12：空 throw 不切片），
上层的分派/重试/日志照常工作，你只是"路过清理"；
不带——异常**被吞**：上层永远不知道发生过异常，
重试策略失效、错误统计丢失、系统带病运行（错误的终态）。
规则：catch(...) 里只允许三种结局——**重抛**（过路清理）、
**转化为明确动作**（边界翻译、防火堤上报）、或**进程终止**——
"吞掉后继续"永远不在选项里。

</details>

**题目 3：** 为什么 catch(...) 接不住段错误？这暗示了什么工程实践？

<details>
<summary>参考答案</summary>

段错误（SIGSEGV）、断言失败（SIGABRT）、整数除零（SIGFPE）是**信号**，
不是 C++ 异常——它们由硬件/内核经信号机制投递，
不经过 throw/catch 的展开机制（→ 03.6 ch2 的六种崩溃实测）。
catch(...) 的"..."只管**异常类型**的任意性，管不了**错误机制**的不同。
工程实践：生产系统的崩溃捕获要**双通道**——
异常通道（try/catch 防火堤，本条）+ **信号通道**
（sigaction 安装 SIGSEGV/SIGABRT handler，至少做到写最后一行日志 + 触发 core dump，
→ 03.6 ch2 的 backtrace 实践）——两条通道各管一半，合起来才是完整的崩溃防线。

</details>
