# 条款 16：理清临时对象的产生与消除

## 本节讲什么

**Understand the origins of temporary objects.** 临时对象（无名、活一行表达式）
是 C++ 性能损耗最隐蔽的来源：它们在你看不见的地方构造、拷贝、析构——
每行"人畜无害"的代码背后可能藏着一串。本条列出临时对象的五个产地与
对应的消除手法（→ Effective item21 RVO、item26 延后定义的落地版）。

← 上一章 [ch03 异常](../ch03-exceptions/)；下一条 [item17 new/delete 开销](./item17-深度剖析newdelete底层内存分配开销，优化堆内存使用.md)。

---

## 1. 临时对象的五个产地

**产地一：按值返回的函数调用**（最常见）

```cpp
Rational operator*(const Rational&, const Rational&);
Rational r = a * b * c;     // (a*b) 产生临时1，临时1 * c 产生临时2——
                            // 两次构造+析构（RVO 只优化最后一层，中间临时照样活）
```

**产地二：隐式类型转换**（最隐蔽）

```cpp
void log(const std::string& s);
log("hello");               // const char* → string 隐式构造一个临时（含堆分配！）
int count(const std::string& s, char c);
count("hello world", 'o');  // 同上——每调用一次造一个 string
```

**产地三：表达式求值的中间结果**

```cpp
std::string s = a + b + c + d;   // 每个 + 一个临时（老实现）；
                                  // C++11 起 string 的 operator+ 有 && 重载才救回来
```

**产地四：按值传参**

```cpp
void process(Widget w);     // 调用处：实参 → w 一次拷贝构造；返回时 w 析构
process(make_widget());     // 多一层：临时对象 → w（移动构造，RVO 可消）
```

**产地五：正确但浪费的写法**

```cpp
for (const auto& kv : map) { std::string key = kv.first; ... }   // 每轮拷一个 string
// vs
for (const auto& [key, value] : map) { ... }                     // 结构化绑定，零拷贝
```

## 2. 消除手法对照表

| 产地 | 手法 |
|---|---|
| 按值返回 | RVO 信任它（→ Effective item21：C++17 强制，别加 move）；链式表达式重构为分段或输出参数 |
| 隐式转换 | 重载覆盖常见实参类型（`log(const char*)` 版）；或调用方显式复用（`const std::string s = ...; log(s);`） |
| 中间结果 | 移动语义版本（`operator+(string&&, ...)`）；`+=` 替代 `+` 链 |
| 按值传参 | const 引用（Effective item20）；要"吃掉"参数时才按值（sink 参数 + move） |
| 通用 | 结构化绑定、`string_view`/`span` 只读视图（→ item54） |

**隐式转换那条最值得展开**：`log("hello")` 的临时 string **带堆分配**
（SSO 放不下时）——热路径上一个 `log(tick.symbol)` 就是一次 malloc。
给 log 加 `std::string_view` 重载（C++17）是彻底的解法：const char*、
string、string_view 三吃，零分配。

## 3. 侦测手法：怎么找到临时对象

- **静态**：review 时盯"按值返回的表达式链"和"字符串实参"——
  两个最高产地人工筛一遍
- **动态**：给类型加带打印的构造/析构（Tracer 模式，→ 18.1 ① 的手法）——
  临时对象的"构造/析构对"在输出里一目了然
- **工具**：`perf record` 里看 `operator new`/`string 构造`的调用点占比
  （→ 06.6.5 ch06 perf 的方法论）——临时对象的分配在 profile 里藏不住

## HFT 关联

- 热路径的字符串纪律：**`string_view` 进、string 出**（→ item54 的白名单）——
  隐式转换产地（log/lookup）全部用 string_view 接口封死
- 链式表达式的拆写：`r = a * b * c` 在价格计算里常见——
  拆成 `t1 = a * b; r = t1 * c;` 并配合 RVO/移动，中间临时数量立即可数
- 别在热路径赌"编译器会优化掉"：临时对象的消除是**写法**问题——
  `-O2` 能消的是无名临时的构造（RVO/复制省略），消不掉**隐式转换的堆分配**

## 代码自测

**题目 1：** `log("hello")`（`log(const std::string&)`）的成本是什么？怎么彻底消除？

<details>
<summary>参考答案</summary>

`const char*` → `std::string` 隐式构造一个**临时 string**：
超 SSO 长度时含**一次堆分配** + 一次 strlen 拷贝 + 调用结束后的析构释放。
热路径上这就是"看不见的 malloc"。
彻底解法：接口改 `log(std::string_view)`——const char*（直接包指针+长度）、
string（零拷贝视图）、string_view 三种实参全部零分配零拷贝
（→ item54 的 string_view 白名单）。
过渡方案：补 `log(const char*)` 重载，但 string 实参仍走临时——
string_view 是一劳永逸版。

</details>

**题目 2：** `Rational r = a * b * c;` 里 RVO 能消除几个临时对象？链式运算怎么改写最省？

<details>
<summary>参考答案</summary>

RVO **只能消除最后一层**：`(a*b)` 的临时对象真实存在（它是 `*c` 的左操作数），
只有最终赋值给 r 的那层可以被 RVO/移动消掉——
两个临时至少活一个（构造 + 析构各一次）。
最省写法取决于类型：
① 有移动语义的 `operator+(T&&, ...)` 重载链（string 模式）：
`t = a * b;` 后 `t *= c;` 或 `r = std::move(t) * c`——让中间结果被"吃掉"而不是拷贝；
② 数学类型用**表达式模板**（高级：把整个表达式变成类型，求值一次完成——
Eigen/Blaze 的做法，写库才值得）；
③ 热路径直接分段 + 输出参数（`mul(a, b, t1); mul(t1, c, r);`）——
临时数量显式可控。

</details>

**题目 3：** 怎么在 profile 里确认"临时对象是瓶颈"而不是"感觉它慢"？

<details>
<summary>参考答案</summary>

三步量化（→ 06.6.5 方法论）：
① **分配路径**：`perf record -g ./app` 看 `operator new`/`malloc` 的
调用栈占比——临时对象的大头（隐式 string/容器拷贝）会在这里现形；
② **构造热点**：带符号的 profile 里 string/vector 构造函数若进前 20，
说明拷贝/临时密集；
③ **对照实验**：把怀疑的写法改成 string_view/移动版重跑基准
（`perf stat` 前后对比 instructions 与 LLC-misses）——
优化收益量化在纸面上，不靠感觉。
临时对象优化的陷阱：消除一个 10ns 的临时在 1µs 的热循环里是 1%，
先确认它在 p99 预算里真的占份额再动手（06.6.5 ch02 的优先序）。

</details>
