# 条款 20：按需选用静态绑定与动态绑定，不要无脑虚函数

## 本节讲什么

**Choose static or dynamic binding deliberately.** 虚函数不是免费的：
每次调用一次间接跳转（vtable 解引用 + 分支预测压力），
每个对象一个 vptr（8B），每个类一张 vtable——
无脑给所有函数加 virtual，是在为"可能永远用不到的多态"预付成本。
本条给出绑定方式的成本解剖与决策框架（→ item35 替代方案的量化版）。

## 1. 动态绑定的真实成本（逐项）

| 成本项 | 量化 | 说明 |
|---|---|---|
| 调用间接 | vptr 加载 + vtable 加载 + 间接跳转 | 2 次内存访问（冷 cache 时各一次 miss，→ 06.6.5 ch06） |
| 分支预测 | 间接跳转目标**不固定** | 多态程度高时 BTB 失效——比直接调用差一个量级 |
| vptr | 对象 +8B | 小对象尺寸直接翻倍（`struct { int x; }` 4B → 16B 含对齐） |
| 内联阻断 | 虚调用**不可内联** | 连带失去内联后的全部优化（→ Effective item30 ②） |
| 去虚拟化条件 | `final` 或编译器能证明具体类型 | 否则 LTO 也救不了 |

**对照**：直接调用在可预测目标下 ≈ 免费（Effective item30 实测：
1 亿次调用 inline vs noinline 差异在噪声内）；虚调用在现代 CPU 上
~1-5ns（cache 命中时）——**单次不贵，热循环里百万次就是毫秒级**。

## 2. 决策框架（什么才配得上虚函数）

```text
问①：真的需要**运行期**才知道调谁吗？
     编译期已知 → 静态绑定（普通函数/模板/if constexpr）
问②：需要异构容器吗（基类指针装不同派生）？
     类型集合封闭 → variant + visit（编译期分发，→ item35）
问③：定制点有多少？
     一两个 → 函数指针/std::function 注入（item35 替代二）
问④：以上都否、且需要开放扩展 → 才用虚函数
```

**"将来可能要扩展"不是理由**——YAGNI：静态绑定的代码改虚函数
是半小时的事，无脑虚函数的成本却从第一天就在付。

## 3. 降成本手法（必须用虚函数时）

- **`final` 类/方法**：编译器确定目标后可去虚拟化（devirtualize）——
  虚调用变直接调用进而内联（→ Effective item30 HFT 关联）
- **收窄多态面**：基类指针只在**冷边界**（注册/分发入口）使用，
  热循环内部拿具体类型（`auto* p = static_cast<Derived*>(base); p->hot_path();`
  ——静态类型已知，调用静态绑定）
- **CRTP 替代**（item35 ③）：类型集合编译期已知时，
  "多态"编译期完成，零 vptr 零间接

## HFT 关联

- 行情回调的绑定方式选择是教科书场景：
  策略基类 `on_tick` 虚函数 = 每 tick 一次间接跳转 + 不可内联——
  单策略极致优化时换 CRTP（编译期分发）；
  框架要管 N 个策略时留虚函数（异构容器是虚函数的主场，→ item35 组合用法）
- 消息解码的绑定：**switch/msg_type 查表**（静态分派，→ 19.3 成员指针表）
  优于虚函数链——间接跳转目标规律（表驱动），分支预测友好
- vptr 的 8B 在订单簿档位（每档 24-32B 目标）里是不可接受的尺寸税——
  热路径数据结构**零虚函数**（POD + static_assert，→ 19.5）

## 代码自测

**题目 1：** 虚函数调用的成本为什么"单次不贵，热循环里致命"？

<details>
<summary>参考答案</summary>

单次虚调用 ≈ 1-5ns（vptr/vtable 各一次加载 + 间接跳转，cache 命中时）——
孤立看无所谓。但热循环的账是**乘法**：每 tick 10 次虚调用 × 每天
百亿 tick = 秒级纯开销；更隐蔽的是**连带成本**：
虚调用不可内联（内联后的常量折叠/死代码消除/寄存器优化全部失去，
→ Effective item30 ②），间接跳转在多态目标下 BTB 失效
（分支预测惩罚每次 ~15-20 周期）。
热路径的真实成本模型不是"虚调用单价"，而是
"单价 × 频率 + 失去的优化机会"——后者通常是大头。

</details>

**题目 2：** `final` 关键字为什么能让虚函数变快？它的收益链是什么？

<details>
<summary>参考答案</summary>

`final`（类或方法）向编译器承诺"**没有更派生的实现了**"——
于是编译器在**调用点**能确定虚调用的真实目标（去虚拟化，devirtualization）：
`Derived d; Base& b = d; b.f();` 若 f 或 Derived 是 final，
编译器把虚调用改写成 `Derived::f` 的**直接调用**——
收益链：直接调用 → 可内联 → 内联后暴露函数体 →
常量折叠/死代码消除/寄存器分配全部解锁。
一个关键字换回整条优化链——这是 final 在热路径的真实价值
（语义价值"禁止继承"反而是赠品）。
注意条件：去虚拟化需要编译器在调用点**看到**具体类型——
经工厂/容器拿到的纯 Base& 救不了，那种场景只有 CRTP/variant。

</details>

**题目 3：** "策略基类 on_tick 用虚函数"和"msg_type 查表分发"各适合什么场景？

<details>
<summary>参考答案</summary>

**虚函数策略基类**：策略**类型开放**（第三方/插件随时新增）、
需要异构容器（引擎 `vector<unique_ptr<Strategy>>` 统一调度）——
间接跳转成本换扩展性，框架边界合理（→ item35）。
**msg_type 查表**：消息**类型封闭**（协议枚举有限）、
分发在热路径（每包一次）——`handlers[msg.type]` 一次数组索引 +
间接跳转目标高度规律（表项少且复用，BTB 友好）；
配合 constexpr 表（→ 19.3 成员指针表）甚至可被编译器优化为
跳转表（jump table，无函数调用开销）。
判别：扩展性需求在**运行期**（新策略不重启上线）→ 虚函数；
扩展性需求在**编译期**（协议升级发版）→ 查表/variant——
热路径的分发永远向编译期倾斜。

</details>
