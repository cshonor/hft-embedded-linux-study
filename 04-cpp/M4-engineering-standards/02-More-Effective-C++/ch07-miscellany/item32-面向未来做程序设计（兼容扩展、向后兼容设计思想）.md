# 条款 32：面向未来做程序设计（兼容与扩展的设计思想）

## 本节讲什么

**Design for the future: extensibility and backward compatibility.**
软件活的时间总比预期长——协议会升级、需求会演化、库会有 v2。
面向未来设计不是"提前实现所有功能"（YAGNI），而是**让未来的变化
有地方落脚**：版本协商、扩展点预留、ABI 稳定层。
本条给出协议/接口/数据三个层面的兼容手法。

## 1. 协议层：版本化与扩展字段

```cpp
struct MsgHeader {
    uint16_t msg_len;
    uint8_t  msg_type;
    uint8_t  version;          // ← 版本字段：新老协议共存的门票
    uint32_t seq;
    uint8_t  reserved[8];      // ← 预留字段：未来扩展不破坏布局（→ 19.5 的 static_assert 钉住）
};
```

**三原则**：
- **版本字段从第一天就有**（哪怕永远 1——没有它，升级时新老消息无法区分）
- **预留空间**（reserved/padding——扩展字段时老代码按旧布局读仍正确：
  老代码跳过不认识的部分，新代码读新字段）
- **未知字段容忍**（解析时"读我认识的，跳过其余的"——
  老版本遇到新版本消息能降级而不是爆炸）

inline namespace 版本化（→ 18.2 ④）是同思想在**符号层**的实现：
v1/v2 库符号共存，老二进制链旧版。

## 2. 接口层：扩展点与回调

| 手法 | 适用 | 例子 |
|---|---|---|
| 回调/钩子注册 | 行为扩展（新策略不改框架） | 引擎的规则注册表（→ item35 策略对象） |
| 接口版本协商 | 插件/库跨版本 | `abi_version()` + dynamic_cast 校验（→ item27 插件） |
| 能力位（feature flags） | 运行时特性开关 | `if (features & FOK_SUPPORTED)`（协议能力位） |
| 尾部预留 + 默认值 | 配置/参数演化 | 配置结构体新字段带默认值，老配置照读 |

**反模式**：为想象中的扩展性提前抽象（每个类都接口化 + 工厂 + 插件架构）——
YAGNI 的代价是复杂度爆炸。**正确姿势：在"变化一定会来"的接缝处**
（协议/插件/跨团队接口）留扩展点，内部实现保持简单。

## 3. 数据层：持久化与演进的兼容

- **格式版本头**：落盘文件/快照/日志带格式版本（回放 3 个月前的行情日志，
  解码器必须认得旧格式——协议博物馆的维护义务）
- **只加不改**：持久化 schema 的演进规则（新字段可加、旧字段不改语义不删——
  删字段用"废弃标记 + 双写过渡"）
- **回放测试**：golden 数据（→ 19.2 自测三）——每次格式演进，
  老数据必须能回放（兼容性不是声明出来的，是测出来的）

## HFT 关联

- 交易所协议年年升级是常态——版本字段 + 预留 + inline namespace 三件套
  让"协议升级"从全所停机变成灰度切换（→ 18.2 ④ 的库版本化）
- 策略参数 schema 的演进（回测结果要可复现）：
  参数集版本化 + 快照回放——半年前的回测配置今天还能跑出同样结果，
  这是研究可信度的底线
- ABI 版本协商在插件型架构（第三方策略 .so）是生存线（→ item27 的场景一：
  加载时 dynamic_cast 校验接口版本）

## 代码自测

**题目 1：** "预留字段"（reserved）和 YAGNI 矛盾吗？

<details>
<summary>参考答案</summary>

不矛盾——YAGNI 反对的是"提前**实现**功能"（写可能永远用不到的代码）；
预留字段是"提前留**空间**"（几个字节，零实现成本）。
协议布局一旦上线就被全网冻结（无数对端按当前布局解码）——
将来加字段没有地方放，只能要么破坏兼容（老代码读错位）
要么发新 msg_type（整条消息族翻倍）。
8 字节的 reserved 是"用零成本买未来的选项"——
和"提前实现新字段的处理逻辑"（那才是 YAGNI 反对的）完全两回事。
判别：预防的是**布局/接口**这种事后改不了的东西 → 预留合法；
预防的是**逻辑**这种随时能加的东西 → YAGNI。

</details>

**题目 2：** 设计"老代码读新消息"的降级兼容，三个要点？

<details>
<summary>参考答案</summary>

① **长度字段**：消息头带 `msg_len`——老代码按长度**跳过整条不认识的消息**
（而不是按自己理解的布局硬解，错位读垃圾）；
② **未知字段容忍**：解析器"读认识的字段，跳过 msg_len 内的其余字节"——
新版本加的字段对老版本透明（XML/JSON 时代的"忽略未知键"的协议版）；
③ **能力探测**：握手时交换版本/能力位——
对端不支持新特性就不发（`if (peer.cap & FOK_BIT) send_fok();`）——
比"发了被 NACK"优雅一个量级。
核心思想：**布局里必须有"我可以不认识你"的通道**——
长度字段是这条通道的钥匙（→ 19.5 协议结构体的验收纪律配套）。

</details>

**题目 3：** 策略参数 schema 要支持"半年前的回测配置今天可复现"，设计要点？

<details>
<summary>参考答案</summary>

① **参数集版本化**：`{schema_version: 3, params: {...}}`——
加载器按版本分派解析（v2/v3 参数结构不同都能读）；
② **只加不改**：新参数可加（带默认值——老配置没它也能跑），
旧参数不改语义不删（废弃的标记 deprecated 但继续识别）；
③ **快照即证据**：回测结果与**完整参数快照**一起落盘——
复现 = 加载快照重跑，不是"凭记忆重新配一遍"；
④ **golden 回放**：每个版本的关键参数组合留 golden 输入+输出——
schema 演进后老 golden 必须跑出相同结果（兼容性测试，
不是声明）。这套的本质：研究可信度建立在"任何历史实验
可在任何未来时刻精确重演"——schema 兼容是它的技术前提。

</details>
