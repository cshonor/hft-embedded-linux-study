# 条款 53：不要轻易忽略编译器的警告

## 本节讲什么

**Pay attention to compiler warnings.** 编译器警告是**免费的代码评审**——
它看到的很多错误（签名笔误、未使用变量、隐式转换、遮掩）在变成线上事故前
就被指出了。认真对待警告不是洁癖，是把调试成本左移到编译期的最便宜手段。
本条给出警告纪律、分级处理法、以及"警告该当错误"的工程实践。

## 1. 警告是编译器在说"这段代码我能编，但我不放心"

```cpp
if (x = 5) { /*...*/ }        // -Wparentheses：赋值当条件——想要 == 吧？
int f() { /* 忘了 return */ } // -Wreturn-type：控制流可能不返回值——UB
struct D : B { void f(); };   // -Woverloaded-virtual：遮掩基类虚函数（→ item33）
```

这些全都能编译通过——**能编译 ≠ 正确**。警告是编译器把
"合法但可疑"的代码标出来的机制；忽略它等于拒绝免费的 bug 扫描。

**本条在本书语境的回响**：item27（C 强转）、item33（遮掩）、
item36/37（静态绑定陷阱）——这些条款描述的坑，**一半都有对应警告**：
`-Woverloaded-virtual`、`-Wreorder`、`-Wshadow`、`-Wsign-compare`。
开齐警告，书里四分之一的坑编译器直接替你站岗。

## 2. 警告纪律（三档）

| 档位 | 做法 | 适用 |
|---|---|---|
| 底线 | `-Wall -Wextra` 全开，**现有警告清零** | 任何项目 |
| 标准 | 上 + `-Werror`（警告即错误）+ 关键警告（`-Wshadow -Wconversion` 按团队承受力） | 活跃开发的项目 |
| 严格 | 上 + `-Wpedantic`、sanitizer 集成 CI、定期 clang/gcc 双编译器交叉检查 | 库/交易核心代码 |

**警告清零是底线中的底线**：警告列表里躺着 200 条旧警告时，
第 201 条（真正的新 bug）会被淹没——警告只有"零"和"无数"两种稳态。

## 3. 处理警告的正确姿势（压 vs 修）

```cpp
// ❌ 压警告：强转让编译器闭嘴，问题留着
size_t n = (size_t)vec.size() - 3;   // size 小于 3 时下溢，警告没了 bug 还在

// ✅ 修警告：顺着警告的提示改代码
if (vec.size() >= 3) { use(vec[vec.size() - 3]); }
```

判别：警告指出的**代码气味**（smell）真实存在吗？
- 存在 → 改代码（警告是路标）
- 不存在（确证误报）→ **最局部**的方式压制（`#pragma` 包单行/
  `[[maybe_unused]]`/显式 `(void)x;`），并留注释说明——
  全局 `-Wno-xxx` 关掉一类警告是最差解（连真问题一起埋了）

## HFT 关联

- 交易代码的警告标配：`-Wall -Wextra -Werror -Wshadow -Wconversion`
  （`-Wconversion` 专门抓价格/数量的整型收窄——`int64_t price` 塞进
  `int32_t` 的资损路径，编译期拦比实盘拦便宜一万倍）
- 双编译器（g++ + clang++）交叉检查：两家警告集互补——
  clang 的 `-Wmost` 和 gcc 的 `-Wextra` 各能抓到对方漏的
  （本仓 03.6 的 sanitizer 实战同理：工具链多样性 = 免费的多重评审）
- CI 门禁：新警告 = 构建失败（`-Werror`）——警告零容忍只有自动化才守得住，
  靠自觉的警告纪律三个月后必然破窗

## 代码自测

**题目 1：** 为什么说警告只有"零"和"无数"两种稳态？

<details>
<summary>参考答案</summary>

警告的价值在于**信噪比**：零警告时，新出现的每一条警告都立刻被注意、被处理。
一旦容忍"反正有几条老的"，列表就会单调增长——新来的真 bug 混在旧警告里
没人翻页去看，警告机制实质失效（破窗效应）。
而 `-Werror` 把"零"变成强制稳态：新增警告直接构建失败，
破窗在第一天就关死。所以纪律只有两个可行终点：
清零 + error 门禁，或者实质上没有警告机制。

</details>

**题目 2：** `-Wsign-compare`/` -Wconversion` 这类警告在交易系统里为什么值得开到最高？

<details>
<summary>参考答案</summary>

因为交易域的数据类型错误**直接是钱**：
`int64_t` 的价格塞进 `int32_t`（大合约溢出）、`size_t` 的数量减成负数
（`size() - 3` 下溢成天量）、有符号/无符号比较让"仓位 < 0"永假——
这些全是 sign/conversion 警告的猎杀范围。
这类 bug 的共同点是**能编译、能跑、数值安静地错**——
没有异常没有崩溃，直到某天对账对不上。
编译期拦住的成本是零，实盘发现的成本是资损——
这是所有警告里 ROI 最高的一类。

</details>

**题目 3：** 确认某条警告是误报后，压制它的正确顺序是什么？

<details>
<summary>参考答案</summary>

从局部到全局，能小不大：
① **改写法让警告自然消失**（首选——多数"误报"其实是代码写得绕，
   如 `[[maybe_unused]]` 属性、`(void)x;` 显式丢弃）；
② **最局部 pragma**（`#pragma GCC diagnostic push/ignored/pop` 包住最小行数）+
   注释说明为什么这是误报；
③ 编译器特定的 suppression（`__attribute__`/`-Wno-xxx=具体实例`）；
④ ❌ 全局 `-Wno-xxx`——把一类警告整体关掉，真问题同归于尽，永远不要。
原则：压制痕迹必须**小且带理由**——三个月后的人（可能就是你自己）
要能看懂"为什么这里允许例外"。

</details>
