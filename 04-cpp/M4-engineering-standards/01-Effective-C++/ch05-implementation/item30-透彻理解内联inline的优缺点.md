# 条款 30：透彻理解内联（inline）的优缺点

## 本节讲什么

**Understand the ins and outs of inlining.** `inline` 是 C++ 里被误解最深的关键字：
它的**语法语义**是"允许同一函数在多个编译单元各有一份定义"（ODR 豁免），
它的**性能语义**只是"建议编译器内联展开"——而编译器早就把这个建议当耳旁风。
本条款讲清：inline 的真实语义、内联展开的成本与收益、以及为什么
"在头文件写函数"和"写 inline"是两回事。本机 g++ 13.3 -O2 实测。

## 1. inline 的第一语义：ODR 豁免，不是性能

```cpp
// math.h
inline int square(int x) { return x * x; }   // inline = 每个包含此头的 TU 都可有一份定义
                                              // 链接器挑一份，其余丢弃——不违反 ODR
```

**没有 inline 时在头文件定义函数**：两个 .cpp 都 include → 链接器报"重复定义"。
所以：
- **头文件里写函数体 → 必须 inline**（或 C++17 起的 `constexpr`/`consteval`，它们隐含 inline）
- 类定义体内的成员函数**隐含 inline**（`struct S { int f() { return 1; } };`）
- 模板函数也隐含可多重定义（不需要 inline 标注）

**推论**：`inline` 标注和"会不会内联展开"**没有必然关系**——
编译器对 inline 函数可能不展开（太大/递归/取地址），对非 inline 函数
同 TU 内照样展开（它有自己的启发式）。

## 2. 内联展开的收益与成本（Meyers 的里里外外）

**收益**：① 消除调用开销（参数压栈/跳转/返回）；② 让编译器看到函数体——
**常量折叠、死代码消除、寄存器分配**这些大优化都需要"看得见"（SRA/LTO 的基础）。

**成本**：
1. **代码膨胀**：展开 N 处 = N 份函数体——I-cache 压力增大，
   热循环外的冷代码膨胀反而变慢
2. **编译时间**：头文件里的函数体改动 → 所有包含者重编（→ item31 编译依赖）
3. **二进制兼容性**：库改了 inline 函数体，已编译的用户代码**不会**自动用新版本
   （旧函数体已烙进它们的二进制）——inline 函数的 ABI 稳定性是假象

**本机实测**（g++ 13.3 -O2，1 亿次调用，inline vs `__attribute__((noinline))`）：

```
inline 版:   100.9 ms
noinline 版:  96.9 ms     ← 差异在噪声内！
```

现代 CPU 对**可预测目标的直接调用**几乎零开销（BTB 命中 + 流水线）——
"inline 为了快"在微基准里都可能测不出差异。内联的真实价值在②（让后续优化看见函数体），
不在"省 call 指令"。

## 3. 内联的边界（编译器会拒绝展开的情况）

- **虚函数**（运行期才知道调谁——除非去虚拟化成功）
- 函数**被取地址**（必须有实体供指针指向）
- 太大/递归/含复杂控制流（编译器的成本模型说不划算）
- **跨 TU**：没有 LTO 时，别的 .cpp 的函数体根本看不见——
  这就是为什么"小函数放头文件（inline）"仍然是经验法则：
  不是为了 inline 关键字，而是让函数体**对调用方可见**

## 4. 现代语境下的使用准则

| 场景 | 做法 |
|---|---|
| 头文件必须定义的小函数（getter/包装） | 写 inline（或靠类内定义隐含 inline）——目的是 ODR |
| 追求"跨 TU 内联"的性能 | **LTO**（`-flto`）/ 统一构建，而不是到处贴 inline |
| 大函数/冷路径 | 放 .cpp——别污染头文件（编译依赖 + I-cache） |
| 模板/constexpr | 本来就该在头文件，inline 多余 |

## HFT 关联

- 热路径的"内联"靠**可见性**管理：行情解码/订单簿的核心小函数放头文件
  （或统一 TU），让编译器自由展开——`inline` 关键字只是顺手的 ODR 门票
- **LTO 是更大的杠杆**：`-flto` 让跨库调用也能内联（策略调撮合引擎的封装函数）——
  比手工 inline 标注有效一个数量级；代价是构建变慢、调试信息变模糊
- 关注**去虚拟化**（devirtualization）：`final` 类/final 方法让编译器把虚调用
  变成直接调用进而内联——这比 inline 标注对热路径的意义大得多
- I-cache 是真实约束：无节制 inline 让热循环的代码 footprint 超 L1i（32K 典型）——
  热路径代码"小"本身就是性能特性

## 代码自测

**题目 1：** `inline` 关键字解决了什么链接问题？它和"编译器是否内联展开"是什么关系？

<details>
<summary>参考答案</summary>

解决 **ODR（单一定义规则）**：inline 允许同一函数在多个编译单元各有定义，
链接器合并保留一份（典型场景：头文件里定义的函数被多个 .cpp 包含）。
与"是否展开"**无必然关系**：inline 是**链接层语义**，展开是**优化层决策**——
编译器可以不展开 inline 函数（太大/递归/取地址），也可以展开非 inline 函数
（同 TU 内它看得见函数体）。把 inline 当性能开关是对它的根本误解（本机实测：
inline 与 noinline 在可预测调用下差异在噪声内）。

</details>

**题目 2：** 为什么说"inline 函数的 ABI 稳定性是假象"？

<details>
<summary>参考答案</summary>

inline 函数的函数体在**编译用户代码时**就被复制（或可能展开）进了用户的二进制——
库后来改了函数体重新发布，已编译的用户程序里烙的还是**旧版函数体**：
不重编译就永远用旧逻辑。普通（非 inline）函数的实现改动只影响库自己的 .so，
用户重链即得新行为。
推论：对外发布库的接口里，**预期会演化的逻辑别放 inline**（→ item31 pImpl 同理）。

</details>

**题目 3：** 热路径想让 `engine.risk_check(order)`（定义在另一个库）被内联，有哪些手段？

<details>
<summary>参考答案</summary>

① **LTO**：`-flto` 编译+链接（最省事，跨 TU 内联）；
② **头文件化**：把 risk_check 的定义挪进头文件（inline/模板/constexpr）——
可见性换内联机会，代价是编译依赖（item31）；
③ **去虚拟化**：若是虚调用，把 RiskChecker 标 `final`（类或方法）——
编译器确定目标后才能谈内联；
④ 统一 TU（unity build）：把相关 .cpp 合并编译。
inline 关键字本身**不在此列**——它管 ODR 不管展开。

</details>
