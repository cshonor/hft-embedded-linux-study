概念详解

1. 字节序：为什么端口和 IP 要 htons/htonl

  • x86/ARM 都是 小端（低字节在低地址），网络字节序是 大端。
  • sin_port、sin_addr 在协议头部按大端解释——直接把主机 int 塞进去，抓包看到的就是"换了个端口"。
  • 记忆：进网络前转一次，出网络后转一次，其余代码一律用主机序。
#include <netinet/in.h>
uint16_t net_port = htons(10013);       // host -> network (16-bit)
uint32_t net_ip   = htonl(INADDR_ANY);  // 0.0.0.0，监听所有网卡

2. sockaddr 家族：为什么都要 cast 成 sockaddr*

struct sockaddr_in {            // AF_INET
    sa_family_t    sin_family;  // 地址族，必须与 socket() 第一个参数一致
    in_port_t      sin_port;    // 网络字节序
    struct in_addr sin_addr;    // 4 字节 IP
    char           sin_zero[8]; // 填充，让两种结构体等长
};

bind/listen/connect/accept 的签名只认通用的 struct sockaddr*（内核态里按 sa_family 再解释回来）。这个 cast 是 C 时代"穷人的继承"，C++ 不需要你写得更优雅——这套 API 就是 C 接口，理解它是为了看懂 muduo 封装的价值。

3. 五个系统调用各自的职责

调用 职责 内核侧发生什么
socket() 创建通信端点，返回 fd 分配 struct file（VFS）→ struct socket（BSD 层）→ struct tcp_sock（inet 层）
bind() 绑定本地 IP:port 把四元组的"本地半边"写进 socket；未 bind 时 connect/发送会自动选
listen() 被动打开，开始收 SYN 状态 CLOSED→LISTEN；backlog 限定 完成三次握手的连接队列 长度
connect() 主动打开 发 SYN，进程阻塞在 SYN_SENT，收到 SYN+ACK 才返回
accept() 从队列取一个已建连 返回 新的 fd（connfd），listenfd 继续收新连接

关键认知：三次握手发生在 accept 返回之前（由内核协议栈完成）。accept 只是"从成品队列里取货"——这是后面理解 SYN flood、TCP_DEFER_ACCEPT 的基础。

4. accept 返回新 fd，不是复用 listenfd

listenfd 是"前台接待"，每个 accept 出来的 connfd 是一个独立的四元组连接。关闭顺序错了（坑点 3）会把接待窗口砸了。

C++ 示例：Daytime 服务器 + 客户端

端口用 10013（非特权，不需要 root；特权端口 <1024 见坑点）。

// daytime_server.cpp — g++ -O2 -Wall daytime_server.cpp -o dtserver
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <cstdio>
#include <ctime>

int main() {
    int listenfd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
    if (listenfd < 0) { perror("socket"); return 1; }

    sockaddr_in addr{};
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);   // 监听 0.0.0.0
    addr.sin_port        = htons(10013);

    if (bind(listenfd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        perror("bind"); return 1;
    }
    listen(listenfd, 5);   // accept 队列容量（受 somaxconn 上限约束）

    for (;;) {
        sockaddr_in cli{}; socklen_t len = sizeof(cli);
        int connfd = accept4(listenfd, reinterpret_cast<sockaddr*>(&cli), &len,
                             SOCK_CLOEXEC);
        if (connfd < 0) { perror("accept"); continue; }

        time_t t = time(nullptr);
        std::string msg = ctime(&t);          // 自带 '\n'
        write(connfd, msg.data(), msg.size()); // 注：ctime 返回 char*，此处简化
        close(connfd);                         // 短连接：发完即关
    }
}

// daytime_client.cpp — g++ -O2 -Wall daytime_client.cpp -o dtclient
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>

int main(int argc, char** argv) {
    int fd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port   = htons(10013);
    inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr);   // 点分十进制 -> 4 字节

    if (connect(fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        perror("connect"); return 1;
    }

    char buf[128];
    ssize_t n;
    // read 必须循环：TCP 是字节流，一次 read 不保证收全（见 02）
    while ((n = read(fd, buf, sizeof(buf))) > 0) {
        fwrite(buf, 1, n, stdout);
    }
    close(fd);
}

内核视角

  • fd 三层结构：fd（进程 fd 表索引）→ struct file（VFS 通用层）→ struct socket → struct tcp_sock。write() 走 VFS file_operations 分发到 sock_write_iter，最终进 TCP 发送队列（sk_write_queue，元素是 sk_buff）。这条链路在 05-linux-kernel 和 12-kernel-networking 里逐层展开。
  • backlog 语义（Linux 2.2+）：listen(fd, backlog) 只控制 accept 队列；半连接（SYN 收到未握手完成）队列由 tcp_max_syn_backlog 控制，且受 SYN cookie 影响。accept 队列满了，内核会对新完成的握手 丢弃 ACK 或拒绝（tcp_abort_on_overflow=1 时直接 RST）——客户端看到"连接成功又立刻被断"的经典谜题。
  • 队列上限：backlog 实际取 min(backlog, net.core.somaxconn)，默认 somaxconn=128（旧内核），调优时要两边一起改。

坑点（PNP 常强调）

  • sin_addr = IP，sin_port = 端口（htons）——两个字段搞反/漏转是第一天的经典 bug
  • 特权端口 13：非 root 可改 10013 做实验
  • read 须循环直到 FIN（见 02 粘包）
  • SIGPIPE 默认杀死进程：对端已关闭后再 write，内核发 SIGPIPE。服务端必须 signal(SIGPIPE, SIG_IGN)（muduo 在初始化时全局忽略）或用 send(..., MSG_NOSIGNAL)
  • 忘记 close(connfd) → fd 泄漏，进程悄悄逼近 ulimit -n，然后 accept 返回 EMFILE 且不分配 fd——必须在事件循环里特殊处理（见 06）
  • inet_addr() 已废弃（INADDR_NONE 与 255.255.255.255 冲突），用 inet_pton
  • connect 被信号中断返回 EINTR，但连接 可能仍在进行——不能简单重试（见 UNP Ch4 中断的 connect）

自测题

  1. accept 返回的 connfd 和 listenfd 是什么关系？关掉 listenfd，已建立的连接会怎样？
  2. listen(fd, 512) 就能让 accept 队列到 512 吗？还要改什么？
  3. 客户端 connect 成功返回时，服务器可能还没调用 accept——为什么？
  4. 为什么 write 一个对端已关闭的连接不会返回错误而是收到 SIGPIPE？（提示：错误是 异步 到达的）
  5. INADDR_ANY 和绑定具体网卡 IP 的区别？多网卡机器上行情接收该用哪个？
参考答案

  1. listenfd 是"前台接待"：只持有四元组的本地半边（本机 IP:port），本身不承载任何数据，读它无意义。accept 从已完成握手的队列里取出一条连接，新建一个 fd（connfd），它才拥有完整四元组，代表这条具体连接；listenfd 继续留着收新连接。所以一个监听端口对应 1 个 listenfd + N 个 connfd。关掉 listenfd 不影响已建立的 connfd（它们照常收发、照常 FIN），只是不能再 accept 新连接，后续 SYN 会被拒绝/丢弃；反之误关某个 connfd 只断那一条连接。注意 fork 后 close 只是引用计数减一，计数未归零不会发 FIN。

  2. 不能。Linux 上 accept 队列的实际长度是 min(backlog, net.core.somaxconn)，旧内核 somaxconn 默认 128（新内核多为 4096），所以 listen(fd, 512) 会被截到 128。必须同时改内核：sysctl -w net.core.somaxconn=512（写进 /etc/sysctl.conf 持久化）。另外两点：glibc 的 SOMAXCONN 宏是老值 128，用宏也上不去；半连接队列是另一条队列，由 net.ipv4.tcp_max_syn_backlog 控制，抗 SYN flood 还要看 SYN cookie 与 tcp_abort_on_overflow。

  3. 因为三次握手由内核协议栈完成，不需要应用参与：客户端发完最后一个 ACK 就进入 ESTABLISHED，服务端内核把这条连接放进 listen socket 的 accept（完成）队列，connect 随即成功返回。accept 只是"从成品队列里取货"，可能几百微秒甚至更久之后才被调用。所以 connect 成功只说明握手完成，不代表对端已 accept，更不代表应用已处理——数据会先堆在接收缓冲里。这是理解 SYN flood、TCP_DEFER_ACCEPT、自连接的前提。

  4. 因为错误是异步到达的。第一次 write 只是把数据拷进发送缓冲并发出报文，此时内核还不知道对端已关闭，于是正常返回（返回值＝请求长度）。随后对端回一个 RST，本端收到后才把 socket 标记为错误：此后的 write 返回 -1/EPIPE，同时内核向进程发 SIGPIPE（默认动作是杀死进程）。所以"write 成功"既不代表对端收到，也不代表连接健康。对策：服务端 signal(SIGPIPE, SIG_IGN)（muduo 全局忽略）或 send(..., MSG_NOSIGNAL)，并永远检查 write 返回值。

  5. INADDR_ANY（0.0.0.0）是通配地址：监听本机所有网卡上的该端口，无论报文从哪张卡进来都能被接受；绑定具体 IP 则只收目的地址是该 IP 的连接（其它网卡/地址的流量到达不了这个 socket）。多网卡行情接收的结论：TCP 服务器场景通常绑具体网卡 IP，这样每条会话明确对应一张物理卡，便于隔离行情网段、避免路由非对称和"接错网"，也允许每卡起一个实例；只有"不在乎从哪张卡来、要全覆盖"时才用 INADDR_ANY。若是 UDP 组播接收，推荐直接 bind 到组播地址 + 端口（绑 INADDR_ANY 也能收，但会顺带收到该端口上的单播流量），并用 imr_interface 指定从哪张卡入组。

· TCP 字节流与粘包

目标

理解 TCP 无消息边界：一次 send 不等于一次 recv；应用层须定界（长度前缀、分隔符、固定长）。

UNP 对照

  • 1.2 客户端示例
  • Ch3 readn / writen（本仓库 Ch3 节笔记）

概念详解

1. "粘包"不是 bug，是 TCP 的本义

TCP 提供的是 字节流（byte stream） 语义，只保证：字节不丢、不乱、不重。消息边界根本不存在于协议中——"粘包/半包"是应用层视角的错觉：

  • 发 100 字节，对端第一次 read 可能拿到 40，也可能拿到 140（把你下一次的消息"粘"进来了）
  • 原因在三层都可能发生：
  • 发送端：Nagle 算法把多个小 write 合并进一个报文段
  • 网络：中间设备分段/合并没有意义，但到达顺序与发送的分段不对应
  • 接收端：应用读得太慢，数据在接收缓冲里排队，下次 read 一锅端

结论：定界是协议设计的事，不是 TCP 的事。

本机实测（clang 23，macOS 26 回环，单进程服务端线程 + 客户端）：

[client] 已发送 200000 字节
[server] 客户端 send() 了 200000 字节，一次 recv() 只拿到 65328 字节   ← 半包
[client] 服务端发了两次("abc"+"def")，一次 recv 拿到 6 字节: "abcdef"  ← 粘包

两个方向各占一边：send 一次 200KB，对端一次 recv 只能拿到回环缓冲允许的量（65328）；两次 send("abc") send("def") 却被一次 recv 合成 "abcdef"。recv 的边界与 send 的次数、大小毫无对应关系——这就是陈硕第 0 讲新手坑 #2/#3 的现场。

2. 三种定界方案对比

方案 典型协议 优点 缺点
固定长度 早期行情帧、FIX 某些字段 解析最简单 浪费带宽、不灵活
分隔符 HTTP 头（\r\n）、Redis（\r\n） 可读、可流式 内容要转义、要扫描
长度前缀（TLV） 自定义协议、protobuf RPC 帧 一次 read 长度字段即知大小，分配精确缓冲 需要先读出头部（半头部问题）

工程主流是 长度前缀：[4B length][payload]，解码器先凑齐 4 字节头，再等齐 payload。muduo 的 LengthFieldCodec、绝大多数交易网关协议都是这个思路。

3. readn / writen：把"最多 n"变成"正好 n"

read(fd, buf, n) 语义是 最多 读 n；协议解码需要"正好 n"的读法（UNP Ch3）：

// 返回 <0 出错（EINTR 重试）；==0 对端 EOF；>0 实际读到的字节数（==n）
ssize_t readn(int fd, void* buf, size_t n) {
    size_t left = n;
    char*  p    = static_cast<char*>(buf);
    while (left > 0) {
        ssize_t r = read(fd, p, left);
        if (r < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (r == 0) break;          // EOF
        left -= r; p += r;
    }
    return n - left;
}

// write 同理：可能部分写（发送缓冲满）
ssize_t writen(int fd, const void* buf, size_t n) {
    size_t left = n;
    const char* p = static_cast<const char*>(buf);
    while (left > 0) {
        ssize_t r = write(fd, p, left);
        if (r < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        left -= r; p += r;
    }
    return n;
}

注意 write 也要循环：发送缓冲区满时 write 只写入一部分（阻塞模式下）或返回 EAGAIN（非阻塞模式，见 06）。

4. muduo::net::Buffer 的设计（陈硕，重点）

muduo 用 Buffer 类解决粘包的读半边，布局：

+-------------------+------------------+------------------+
| prependable bytes |  readable bytes  |  writable bytes  |
+-------------------+------------------+------------------+
0               readerIndex_      writerIndex_          size()

三个设计决策：

  1. 前置空隙（默认 8B+）：读到长度前缀后，可以 原地 在数据前面补内容（如补长度头再转发），不用挪数据
  2. readv + 栈上 extra buf（64KB）：一次系统调用尽量多读——读满 Buffer 剩余空间的同时，溢出部分先进栈缓冲，再决定要不要扩容，避免每个连接预留 64KB 造成内存浪费
  3. 懒收缩：数据取走后不急着 memcpy 压缩，readerIndex 前移即可，写满时再统一整理

写半边由 TcpConnection::send() 处理：先尝试直接 write，写不完的剩余部分挂到 Buffer，等 EPOLLOUT（见 07 epoll）。

5. 长度前缀解码器的状态机

[等头部4B] --读满4B, 校验len合法--> [等payload len B] --读满--> 回调 onMessage, 回到初始

必须校验 len 上限（如 64MB）——恶意/错误的长度值会让 resize 直接把进程 OOM。

C++ 示例：长度前缀编解码

// 编码：[4B 大端长度][payload]
void sendFrame(int fd, const std::string& payload) {
    uint32_t len = htonl(static_cast<uint32_t>(payload.size()));
    std::string frame(reinterpret_cast<char*>(&len), 4);
    frame += payload;
    ssize_t r = writen(fd, frame.data(), frame.size());
    // 处理 r...
}

// 解码核心（配合 Buffer 的典型 muduo 写法）
void onMessage(Buffer* buf) {
    while (buf->readableBytes() >= 4) {                 // 头部够了吗
        const char* p = buf->peek();
        uint32_t len;
        memcpy(&len, p, 4);
        len = ntohl(len);
        if (len > kMaxFrameLen) { /* 协议错误，断开连接 */ return; }
        if (buf->readableBytes() < 4 + len) break;      // payload 还没到齐
        buf->retrieve(4);                               // 跳过头部
        std::string payload = buf->retrieveAsString(len);
        // dispatch(payload);
    }   // while：一次可能凑出多帧（这就是"粘包"被正确处理的现场）
}

内核视角

  • 每个连接有 发送缓冲（sk_sndbuf）和接收缓冲（sk_rcvbuf），ss -tm 可看到实时占用。write 只是拷进发送缓冲 + 唤醒内核发送任务，返回 ≠ 离开主机
  • 接收路径：网卡 → 软中断 → tcp_v4_rcv 按 四元组 找到 tcp_sock → 数据挂到 sk_receive_queue（sk_buff 链）→ 唤醒等在 sk_wq 上的进程。read 就是把 sk_buff 里的数据拷给用户——它看到的当然是 连续字节，分段信息（MSS 边界）在这一层早已抹掉
  • Nagle：小包（小于 MSS）未确认时先攒着，攒到 MSS 或收到 ACK 才发。交互式/低延迟协议必须 TCP_NODELAY（muduo 默认开启）——它同时是"粘"的制造者和延迟杀手，见 05 TTCP 和 12 TCP/IP

坑点

  • 以为「发 100 字节会一次收满 100」
  • 缓冲合并：Nagle、接收窗口、应用读太慢
  • 解决：协议设计，不是指望 TCP 帮你分包
  • 用 read 返回值当"消息"，而不是当"字节片段"
  • 长度字段不校验上限 → OOM / 越界
  • 分隔符方案忘记转义：payload 里出现分隔符立刻解析错乱
  • write 不检查返回值：部分写之后数据悄悄丢了

场景 关系

自测题

  1. 写端循环 send("A",1) 一万次，读端第一次 read(buf, 4096) 可能读到多少字节？这个数字由什么决定？
  2. 为什么 muduo Buffer 前面要留 prependable bytes？举一个"在数据前面补内容"的实际场景。
  3. 长度前缀解码器为什么要校验长度上限？攻击面是什么？
  4. readn 循环里 EINTR 为什么必须 continue 而不能报错？
  5. 关闭 Nagle 后吞吐会一定变差吗？什么场景反而更好？
参考答案

  1. 可能是 1 到 4096 之间的任意值，只保证"不少于 1 字节、不超过 4096 字节"。它取决于：① 该连接接收缓冲里此刻已到达且序号连续的字节数（受对端发送节奏、网络分段影响）；② read 的请求长度 4096；③ 是否还在持续到达（慢启动/cwnd 限制下可能只有 1~2 个 MSS，即 1460 左右）。TCP 是字节流，一次 read 的边界与 send 次数毫无关系——一万次 1 字节 send 完全可能在接收端被"粘"成几次大 read。

  2. prependable bytes 让"在已有数据前面补内容"可以原地完成，不用挪动数据、不用重新分配。典型场景：网关收到一帧 payload 后要转发给下游并加上自己的 4 字节长度头（或会话头、纳秒时间戳），可以直接把长度写到 prependable 区，然后把 [prepend 区, 数据区] 这一整段一次性 write 出去——零拷贝、零 memcpy。若没有这段空隙，就得先 memmove 腾位置或拼两个 buffer（writev 也行，但 muduo 的写法更省一次系统调用）。

  3. 因为长度值来自对端，攻击者/出错的客户端发一个 0xFFFFFFFF，resize 一下就要 4GB，进程直接 OOM 被打死；即使不 OOM，也会为一个永远等不齐的"超大帧"长期占住连接和缓冲。这是典型的"输入驱动的分配"攻击面。对策：长度必须按协议上限校验（如 kMaxFrameLen = 64MB），超限即判协议错误并断开连接；同时限制单连接的待处理字节数与解码速率。

  4. EINTR 表示这次 read 被信号打断，一个字节都没读走，连接本身完全正常，属于"重试即可"的瞬态错误。若当错误处理（返回 -1 并断开），会在收到 SIGCHLD、定时器信号、profiling 信号时误杀正常连接。所以循环里必须 continue 重新 read。补充：Linux 上阻塞 read 若已经读到了部分数据再被信号打断，会返回已读字节数而不报 EINTR——这也是 readn 能正确记账的原因。

  5. 不一定。Nagle 只在"有小于 MSS 的未确认数据"时才攒包，批量传输时每次 write 都是满 MSS 的大块，Nagle 根本不触发，所以吞吐基本无差别——测吞吐本就不该关 Nagle（会人为凑出更多小报文、头部开销变大）。反过来，小块 + 请求-响应场景（撮合回报、交互式协议）关掉 Nagle 明显更好：避免 Nagle 与对端延迟 ACK 叠加造成的最多 ~40ms 停顿，延迟大幅下降，而报文数本来就是 1:1，没有额外成本。结论：测吞吐用大块，测延迟（和线上小消息）必开 TCP_NODELAY。

· 自连接（Self-Connect）

目标

同一主机上客户端连本机监听端口时，可能出现 自连接；分清 listenfd 与 connfd，accept 返回谁。

UNP 对照

  • 1.5 服务器示例
  • Ch4 accept / connect

概念详解

1. TCP 连接的唯一身份：四元组

(本地IP, 本地port, 对端IP, 对端port)

内核用四元组在哈希表（ehash）里唯一定位一条 TCP 连接。四元组相同 = 同一条连接，这是自连接问题的根源。

2. 自连接怎么发生的

正常流程：客户端 connect(127.0.0.1:10013)，内核自动分配一个临时端口（ephemeral port，范围 net.ipv4.ip_local_port_range，默认约 32768-60999），四元组是 (127.0.0.1, 临时端口, 127.0.0.1, 10013)，与监听 socket accept 出来的 connfd 各占一端。

极端情况：端口分配器恰好选中 10013 作为临时端口（前提：你的监听绑定允许、该四元组空闲）。此时：

(127.0.0.1, 10013, 127.0.0.1, 10013)   ← 四元组两端完全相同！

SYN 发给自己，自己回 SYN+ACK 给自己，三次握手"自言自语"完成——得到一条 一端连着自己的连接：

  • connect 返回成功（它以为连上了服务器）
  • 服务器 accept 永远收不到这条连接（它不在监听的匹配规则内）
  • 客户端 getsockname() == getpeername()（源=目的）

概率很低（单次连接万分之一量级），但两类系统会真实踩中：压测工具疯狂建连（端口穷尽后重用）和 重启后立即连固定端口的服务。

确定性复现（不用撞概率）+ 平台对照：不监听，直接 bind 一个固定端口再 connect 自己：

int fd = socket(AF_INET, SOCK_STREAM, 0);
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof(one));
bind(fd, {127.0.0.1, 54321});      /* 绑定后不 listen */
connect(fd, {127.0.0.1, 54321});   /* 直接连自己 */
平台 结果
Linux 6.18.39（Pi 5, gcc 14.2 实测） connect 成功——getsockname/getpeername 都是 54321（localhost:54321 <-> localhost:54321），send("hi") 后自己能 recv 到 "hi"，一个 socket 首尾相接
macOS 26（clang 23 实测） connect 失败: Invalid argument（EINVAL，BSD 系内核直接拒绝）

成因：Linux 的 TCP 走同时打开（simultaneous open）路径，SYN 与 SYN+ACK 交叉后握手合流，连接两端是同一个 socket。跨平台代码不能依赖此行为。这正是陈硕第 0 讲列的新手坑 #5（课件端口就是 54321）。

3. listenfd vs connfd：谁是谁

listenfd ──accept()──> connfd（新 fd，代表某个具体客户端）
listenfd connfd
数量 每个监听端口 1 个 每条连接 1 个
生命周期 服务器全程 连接期间
读 无意义 收数据
关闭后果 无法再接受新连接（已建连不受影响） 断开该客户端

自连接的诡异表现：你 close 的"客户端 socket"和某条"服务端连接"其实是 同一个四元组的两端，一边的操作直接影响另一边。

C++ 实验：检测自连接

// selfconnect_probe.cpp — 不断连接本机端口，撞出四元组两端相同的情形
// g++ -O2 selfconnect_probe.cpp -o probe
// 前置：另一终端起 dtserver（见 01）
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>

int main() {
    sockaddr_in srv{};
    srv.sin_family = AF_INET;
    srv.sin_port   = htons(10013);
    inet_pton(AF_INET, "127.0.0.1", &srv.sin_addr);

    for (int i = 0; i < 200000; ++i) {
        int fd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
        if (connect(fd, reinterpret_cast<sockaddr*>(&srv), sizeof(srv)) < 0) {
            perror("connect"); close(fd); continue;
        }
        sockaddr_in self{}, peer{};
        socklen_t l1 = sizeof(self), l2 = sizeof(peer);
        getsockname(fd, reinterpret_cast<sockaddr*>(&self), &l1);
        getpeername(fd, reinterpret_cast<sockaddr*>(&peer), &l2);

        char s[64], p[64];
        inet_ntop(AF_INET, &self.sin_addr, s, sizeof(s));
        inet_ntop(AF_INET, &peer.sin_addr, p, sizeof(p));
        if (self.sin_port == peer.sin_port && strcmp(s, p) == 0) {
            printf("SELF-CONNECT hit at #%d: %s:%u <-> %s:%u\n",
                   i, s, ntohs(self.sin_port), p, ntohs(peer.sin_port));
            close(fd);
            return 0;                      // 撞到了
        }
        close(fd);
    }
    puts("no self-connect in 200k tries (normal; shrink ip_local_port_range to force)");
    return 0;
}

复现技巧：把临时端口范围改小撞概率会大幅上升（sysctl net.ipv4.ip_local_port_range="10013 10050" 实验后记得改回）。

排查现成工具：ss -tn 看到形如 127.0.0.1:10013 127.0.0.1:10013 的行就是自连接。

内核视角

  • connect() 里内核做两件事：inet_hash_connect() 选临时端口（尽量避开已用），然后发 SYN。选端口时只检查四元组冲突——四元组 (127.0.0.1,10013,127.0.0.1,10013) 若空闲就"合法"
  • SYN 到达本机回环路径，tcp_v4_rcv 找到这条已存在的 SYN_SENT socket 且正好能配对 → 握手自洽完成（tcp_rcv_state_process 处理"自己发给自己的 SYN+ACK"）
  • 内核其实有部分防护（tcp_tw_reuse、地址检查），但没有（也无法廉价地）完全禁止自连接——应用层识别是最后一道防线：connect 成功后比对 getsockname/getpeername，相同即断开重连

坑点

  • 关闭错 fd 导致监听套接字被关
  • 自连接时 getpeername / getsockname 表现反常（实验验证）
  • 压测机和服务端同机部署：自连接概率被"同机 + 高频建连"放大
  • 客户端 bind 固定源端口 + SO_REUSEADDR：四元组冲突概率人为提高，需意识到代价
  • 服务端日志里"connect 成功但 accept 没见到"的连接，先怀疑自连接/端口重用，再怀疑代码 bug

HFT 关联

场景 关系
会话身份 行情/订单会话管理以四元组为主键；自连接、端口重用会破坏"源端口=会话"的假设
压测纪律 延迟压测与被测服务 分机部署，否则自连接 + 回环带宽失真（回环不经过真实网卡栈，数据见 12-kernel-networking）

自测题

  1. 四元组相同为什么就判定是同一条连接？内核靠哪个数据结构定位？
  2. 自连接的客户端 read 自己 write 的数据会发生什么？（自己实验：会收到自己发的字节）
  3. 为什么 accept 收不到自连接？监听 socket 匹配的是四元组的哪一半？
  4. 如何用 ss/netstat 一条命令找出当前系统里的自连接？
  5. ip_local_port_range 用尽时 connect 报什么错？
参考答案

  1. 因为 TCP 连接的唯一身份就是四元组 (本地IP, 本地port, 对端IP, 对端port)，内核在连接哈希表 ehash 里按四元组查找 tcp_sock（监听侧则是 request_sock / accept 队列）。四元组相同即命中同一个 socket，因此被判定为"同一条连接"，重复的四元组无法共存——这是自连接、TIME_WAIT 不能立刻复用、SO_REUSEADDR 语义的全部根源。

  2. 会原样收到自己刚写进去的字节。自连接是一条真实 ESTABLISHED 连接，只是两端是同一个 socket：write 的数据进发送缓冲，经回环 tcp_v4_rcv 又回到自己的接收队列，read 就把这些字节读出来了（像接了一根短路的线）。若只写不读，数据堆满接收缓冲后 write 会阻塞（或返回 EAGAIN），表现为"莫名其妙卡住"。识别方法：connect 成功后比对 getsockname() 与 getpeername()，两者相同即自连接，应立刻 close 重连。

  3. 因为监听 socket 只持有四元组的本地半边（自己 bind 的 IP:port），用它匹配入站 SYN 的目的地址；而自连接的两半完全相同，那个 SYN 发出后在 ehash 里先命中处于 SYN_SENT 的自己（源=目），握手在这个 socket 内部自洽完成（tcp_rcv_state_process），从未进入 listen 的半连接/accept 队列。换句话说：匹配到的是"自己这一端那个发起方 socket"，不是 LISTEN socket，所以 accept 永远取不到它。

  4. 一条命令即可（比较"本地地址:端口"列与"对端地址:端口"列是否相同）： bash ss -tn | awk '$4==$5' # 输出形如 ESTAB 0 0 127.0.0.1:10013 127.0.0.1:10013 ss -tan state established | awk '$4==$5' # 只筛已建连 netstat -tn | awk '$4==$5' 同理（列号一致）。也可以用 ss -tnp 带上进程信息定位是谁建的连。

  5. 报 EADDRNOTAVAIL（Cannot assign requested address）：inet_hash_connect() 在 ip_local_port_range 里找不到空闲的临时端口。注意别混淆：EADDRINUSE 是指定地址/端口已被占用（bind 或四元组冲突），ECONNREFUSED 是对端无监听/回了 RST。排查命令：cat /proc/sys/net/ipv4/ip_local_port_range、ss -s（看 TIME_WAIT/已用端口量）、netstat -s | grep -i fail。缓解：调大端口范围、开启 tcp_tw_reuse、减少短连接（连接池/长连接）、重连做退避而不是无限重试。

04

· Netcat（nc）

目标

最小 双向字节管道：stdin ↔ TCP ↔ 对端；理解半关闭、shutdown、两端同时读写。

UNP 对照

  • Ch5 并发 echo、Ch6 I/O 多路复用、Ch14 高级 I/O

概念详解

1. Netcat 是什么：两个 fd 之间的泵

stdin ──read──> 缓冲 ──write──> socket ──网络──> 对端 socket ──> stdout

一句话：把任意的标准输入输出接到 TCP 上。它是网络调试的"万用表"：手工发协议帧、探测端口（nc -z host port）、传文件（nc -l 9000 > file + nc host 9000 < file）。

2. 阻塞模型的根本困境

最朴素的实现：

while ((n = read(STDIN_FILENO, buf, sizeof buf)) > 0)
    writen(sockfd, buf, n);

问题：read(stdin) 阻塞 期间，socket 上到达的数据没人读——对端等你回复，你等键盘输入，互相等死。三种解法：

方案 思路 代价
双进程/线程 各管一个方向 进程/线程同步、退出协调复杂
select/poll 同时监听 stdin + socket 单线程事件驱动（nc 与 muduo 的选择）
非阻塞轮询 循环试两个 fd 忙等烧 CPU（见 06）

这是 事件驱动模型的第一课：不止 socket，任何阻塞 fd（tty、pipe、文件描述符）都可以进 select/epoll。

3. close vs shutdown：半关闭是核心区别

close(fd) shutdown(fd, how)
语义 关闭该 fd（引用计数归零才发 FIN） 只控制连接方向，不关 fd
SHUT_WR — 发 FIN，之后仍可 read（对端 EOF 方向关闭，自己收方向保留）
SHUT_RD — 关读方向（后续 read 行为平台有差异）
SHUT_RDWR — 两方向都关，但不释放 fd
多进程 fork 后 计数未归零 → FIN 拖着不发 立即生效

典型协议用法："客户端发完请求 → shutdown(SHUT_WR) → 继续读响应"。对端 read 返回 0（EOF），明确知道"不会再有数据"，但它的发送方向还开着——这就是 优雅关闭（graceful shutdown） 的基础。

C++ 示例：select 版最小 nc（客户端方向）

// mini_nc.cpp — g++ -O2 mini_nc.cpp -o mnc ; ./mnc 127.0.0.1 9000
#include <sys/select.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>

int main(int argc, char** argv) {
    int sockfd = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port   = htons(9000);
    inet_pton(AF_INET, argv[1], &addr.sin_addr);
    if (connect(sockfd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        perror("connect"); return 1;
    }

    fd_set rset;
    int    maxfd1 = sockfd > STDIN_FILENO ? sockfd : STDIN_FILENO;
    bool   stdin_eof = false;
    char   buf[4096];

    for (;;) {
        FD_ZERO(&rset);
        if (!stdin_eof) FD_SET(STDIN_FILENO, &rset);
        FD_SET(sockfd, &rset);
        int n = select(maxfd1 + 1, &rset, nullptr, nullptr, nullptr);
        if (n < 0) { if (errno == EINTR) continue; perror("select"); break; }

        if (FD_ISSET(sockfd, &rset)) {           // socket 可读
            ssize_t r = read(sockfd, buf, sizeof(buf));
            if (r == 0) { puts("\n[peer closed]"); break; }   // 收到 EOF
            if (r < 0) { perror("read sock"); break; }
            write(STDOUT_FILENO, buf, r);
        }
        if (!stdin_eof && FD_ISSET(STDIN_FILENO, &rset)) {    // 键盘可读
            ssize_t r = read(STDIN_FILENO, buf, sizeof(buf));
            if (r == 0) {                      // 本端输入结束
                stdin_eof = true;
                shutdown(sockfd, SHUT_WR);     // 半关闭：发 FIN，但继续收
                continue;
            }
            ssize_t w = write(sockfd, buf, r);  // 简化：未处理部分写
            (void)w;
        }
    }
    close(sockfd);
    return 0;
}

注意 stdin EOF 后：从 select 集合里摘掉 stdin（否则它永久可读 → busy loop），但保留 socket 继续收对端剩余数据。muduo 对应 TcpConnection::shutdown()（关写方向）与 forceClose()（RST 硬断）的区别。

内核视角

  • shutdown(SHUT_WR) → tcp_shutdown() 立刻在发送队列尾构造 FIN 报文（不等未确认数据，FIN 排在其后），连接进入 FIN_WAIT_1；对端内核回 ACK，本端进入 FIN_WAIT_2，接收方向照常工作
  • close() 则要等发送缓冲数据全部送达（linger 未设置时内核"尽力"后台发送）才发 FIN，且 fd 引用计数为 0 才触发
  • 对端 read 返回 0 的判定：收到 FIN 只是标记 sk_shutdown |= RCV_SHUTDOWN，tcp_recvmsg 发现队列空且有该标记才返回 0
  • RST 的产生：收到 FIN 后仍向对端 write → 对端回 RST；setsockopt(SO_LINGER{1,0}) + close → 直接 RST。收到 RST 后本端再 read/write 直接报 ECONNRESET

状态机全程可用 ss -tn 观察各状态（FIN_WAIT2/CLOSE_WAIT 停留过长 = 应用层没做半关闭或没 close，见 12 TCP/IP 的连接管理章节）。

坑点

  • 只关写端 vs close 整连接（对端 read 得 0）
  • 单线程阻塞：一端堵住另一端（课程常引到非阻塞 / epoll）
  • Windows 与 POSIX 行为差异（本 Rust 版用 std::net，跨平台）
  • CLOSE_WAIT 堆积：对端发了 FIN 而本端应用从不 close ——泄漏的是代码逻辑不是 fd
  • fork 出的子进程继承 socket fd：close 不发 FIN（引用计数），必须 shutdown 或 SOCK_CLOEXEC
  • 把 read 返回 0 当错误处理（EOF 是正常语义）

自测题

  1. shutdown(fd, SHUT_WR) 之后 read 还能用吗？write 呢？
  2. fork 出的子进程里 close(sockfd)，父进程还在用——对端会收到 FIN 吗？为什么？
  3. select 返回后不处理 stdin EOF（不从集合摘除）会发生什么？
  4. CLOSE_WAIT 大量出现，是本端 bug 还是对端 bug？
  5. 收到 RST 与收到 FIN，本端 read 的表现分别是什么？
参考答案

  1. shutdown(fd, SHUT_WR) 后：还能 read，不能 write。它只关本端发送方向（内核立刻在发送队列尾排 FIN，进入 FIN_WAIT_1，对端 ACK 后 FIN_WAIT_2），接收方向照常工作，可以继续把对端的剩余数据读完直到 read 返回 0。之后再 write 会失败（EPIPE + SIGPIPE，且对端会回 RST）。这正是"发完请求 → 半关闭 → 继续读响应"的优雅关闭写法；fd 本身没关，最后仍要 close。

  2. 不会。socket 的 struct file 有引用计数，fork 后父子各持一份；子进程 close 只是计数减一，父进程的引用还在，计数未归零就不触发 FIN。这是"多进程 close 拖着不发 FIN"的经典陷阱。要立刻发 FIN 用 shutdown(fd, SHUT_WR)（作用于连接而非 fd 计数）；要从源头避免继承，用 socket(..., SOCK_CLOEXEC) 或在 fork 后的子进程里立刻关掉不用的 fd。

  3. stdin 到达 EOF 后处于永久可读状态（read 立刻返回 0），还留在 select 集合里的话 select 每次都立即返回，循环空转成 busy loop（CPU 100%），同时 timeout 语义也失效。正确做法（示例代码里的 stdin_eof）：EOF 后把 stdin 从集合摘除，并 shutdown(sockfd, SHUT_WR) 通知对端"我发完了"，但保留 socket 继续收对端的剩余数据，直到 read 返回 0 才退出。

  4. 是本端 bug。CLOSE_WAIT 的含义是：对端已发 FIN（对端主动关闭，属于正常行为），本端内核收到后标记 sk_shutdown |= RCV_SHUTDOWN，等应用层 close —— 应用不关它就一直停在 CLOSE_WAIT。大量堆积说明本端没正确响应对端关闭：常见于 read 返回 0 时忘了 close、事件循环没处理 EPOLLRDHUP/EPOLLHUP、或连接对象泄漏（泄漏的是代码逻辑不是内核参数）。反之若本端大量 FIN_WAIT_2，才是对端没关。排查：ss -tn state close-wait | head + lsof -p <pid>。

    • 收到 FIN（优雅关闭）：read 先把接收队列里已排队的数据读完，之后返回 0（EOF），这是正常语义，不是错误；可以继续 write（对端收方向还开着，除非它也关了）。
    • 收到 RST（异常终止）：read 返回 -1，errno == ECONNRESET；此后 write 同样报 ECONNRESET，继而 EPIPE + SIGPIPE。RST 是粗暴的：可能丢弃接收缓冲里未读的数据，没有"读完剩余"的机会。所以交易链路一律走 shutdown + 读完 + close 的优雅关闭，不用 SO_LINGER{1,0} 硬断。

目标

测量 TCP 吞吐；批量 read/write、禁用 Nagle、窗口与缓冲调优。

UNP 对照

  • Ch3.9 readn/writen、Ch14 高级 I/O

概念详解

1. TTCP 是什么

经典的 TCP 吞吐基准（源自 BSD test TCP）：客户端发 NBLOCKS 个 BUFSIZE 的块，先发会话头（块数+块大小），发完发长度为 0 的结束标记，等服务端回一个确认（总字节数 + 总耗时），两端各自打印吞吐。

client: [header: nblocks,bufsize][block × N][len=0 结束标记] ──> server: 读全部，回 [acks]

它的价值在于把"感觉快"变成可复现的数字，以及暴露下面所有调优点。

2. 缓冲大小 vs 系统调用次数：第一性能杠杆

传 1 GiB，不同用户态缓冲的 write 次数：

缓冲大小 write 次数 说明
1 KiB 1,048,576 每次系统调用 ~1-2µs，光陷入内核就烧掉秒级
4 KiB 262,144 默认页大小，常见起点
64 KiB 16,384 推荐量级
1 MiB 1,024 边际收益开始递减（拷贝成本上升）

经验值：8-64 KiB 的用户态缓冲在多数场景接近最优。太小 → 系统调用开销；太大 → CPU cache 失效 + 内存压力。

3. 吞吐的上限由什么决定

吞吐 ≈ min(链路带宽, 发送窗口 / RTT)
     发送窗口 ≈ min(cwnd, rwnd, sk_sndbuf)
  • RTT 大 + 窗口小 → 吞吐被窗口卡死（带宽时延积 BDP = 带宽 × RTT；跨机房 1ms × 10Gbps ≈ 1.25MB，默认 sndbuf 可能不够）
  • 调大 SO_SNDBUF/SO_RCVBUF 或依赖内核自动调优（net.ipv4.tcp_wmem/tcp_rmem 的 max 值）
  • ss -ti 现场看 cwnd、snd_wnd、rtt——先看数据再调参

4. Nagle 与小包

  • Nagle：小于 MSS 的未确认段先攒着 → 小包场景延迟激增（与延迟确认叠加可达 40ms+）
  • 吞吐测试大量写满缓冲时不触发 Nagle；但 小块 + 请求响应 模式必须 TCP_NODELAY
  • 测试纪律：测吞吐不关 Nagle（凑大段），测延迟必关 Nagle——混着谈是常见错误

C++ 示例：TTCP 核心逻辑

// ttcp_client.cpp 核心 — g++ -O2 ttcp_client.cpp -o ttcp
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>
#include <ctime>
#include <vector>
#include <cstdint>

struct SessionMsg {          // 会话头：裸结构体上线的对与错见 09
    int32_t number;          // 块数
    int32_t length;          // 每块字节数
};

ssize_t writen(int fd, const void* buf, size_t n);   // 见 02

double nowSec() {
    timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);   // 单调钟，不受 NTP 跳变影响
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

int main(int argc, char** argv) {
    const int    nblocks = 1024, buflen = 65536;
    const int    one = 1;
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port   = htons(9001);
    inet_pton(AF_INET, argv[1], &addr.sin_addr);
    if (connect(fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        perror("connect"); return 1;
    }
    setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof(one));  // 实验变量之一

    SessionMsg msg{ htonl(nblocks), htonl(buflen) };
    writen(fd, &msg, sizeof(msg));

    std::vector<char> block(buflen, 'x');
    double t0 = nowSec();
    for (int i = 0; i < nblocks; ++i)
        if (writen(fd, block.data(), buflen) < 0) { perror("write"); return 1; }
    msg.number = 0;                                  // 结束标记
    writen(fd, &msg, sizeof(msg));

    int32_t ack = 0;
    read(fd, &ack, sizeof(ack));                     // 等服务端确认
    double dt = nowSec() - t0;
    double mb = double(nblocks) * buflen / 1e6;
    printf("sent %.0f MB in %.3f s = %.1f MB/s (%.2f Gbit/s)\n",
           mb, dt, mb / dt, mb * 8 / dt / 1000);
    close(fd);
}

服务端对称：readn 头部 → 循环 readn 每块 → 读到 0 长度标记 → 回写总字节数。

内核视角

  • write() 大块数据 → 拆成 MSS 段进 sk_write_queue → 拥塞控制（cwnd）与 Nagle 决定实际发送时机；发送缓冲满时 write 阻塞（或非阻塞返回 EAGAIN）——用户态缓冲再大也受 sk_sndbuf 闸门
  • 批量读：read(fd, buf, 64K) 一次 tcp_recvmsg 把接收队列上多个 sk_buff 的数据 合并拷出——这就是"粘包"在性能上的红利：系统调用摊销
  • GSO/GRO：内核把多个段合并处理（发送/接收侧 offload），ethtool -k eth0 查看——虚拟机/云主机上这些开关对吞吐影响巨大
  • 自动调优：接收窗口由 tcp_rmem 按需增长；手工 setsockopt(SO_RCVBUF) 一旦设置反而 关掉 自动调优（设的是硬上限）

坑点

  • 小包 + Nagle → 吞吐假象
  • 用户态缓冲太小导致系统调用过多
  • 用 time()/gettimeofday 测性能（分辨率/跳变问题），应 CLOCK_MONOTONIC
  • 忘记等对端 ack 就计时结束：测的是"灌满发送缓冲的速度"不是端到端吞吐（上例的 ack 不可省）
  • 测回环当真实性能：回环无网卡/NIC offload/中断开销，数字偏乐观一个量级
  • 设置 SO_SNDBUF 反而关闭了自动调优，吞吐不升反降

自测题

  1. 为什么 write 返回成功不代表数据已离开主机？接收方什么时候才能"看到"这 1 GiB 的最后一字节？
  2. 1 KiB 缓冲与 64 KiB 缓冲传 1 GiB，系统调用差多少次？每微秒 1 次的系统调用开销总共多花多少时间？
  3. 跨机房 RTT 30ms、带宽 10Gbps，需要的 TCP 窗口至少多大（BDP）？默认 sndbuf 够吗？
  4. 什么情况下设置 SO_RCVBUF 会让吞吐下降？
  5. TTCP 结束为什么要等 ack 再计时？
参考答案

  1. write 成功只表示数据被拷进内核发送缓冲（sk_write_queue），什么时候真正上线路由拥塞窗口 cwnd、对端通告窗口 rwnd 和 sk_sndbuf 一起决定，返回时数据可能还躺在缓冲里。接收方"看到"最后一字节要经历：最后一个报文段到达对端网卡 → tcp_v4_rcv 入接收队列且序号连续（前面没有缺口，否则要先等重传）→ 应用 read 把它拷出来。所以"发送完成"和"对端收到"之间隔着一整个 RTT 级别的距离，这也是 TTCP 必须等对端回 ack 才能停表的根本原因。

  2. 传 1 GiB = 1,073,741,824 B：1 KiB 缓冲 → 1,048,576 次 write；64 KiB 缓冲 → 16,384 次。差 1,032,192 次系统调用。按每次 ~1 µs 陷入内核开销计，多花 约 1.03 秒（按 1–2 µs 算就是 1–2 秒量级）。这就是"用户态缓冲是第一性能杠杆"：太小 → 系统调用开销主导；但也不是越大越好，超过 64 KiB 后 cache 失效与拷贝成本上升，边际收益递减（8–64 KiB 通常接近最优）。

  3. BDP = 带宽 × RTT = 10 Gbps × 30 ms = (10×10⁹/8) B/s × 0.03 s ≈ 37.5 MB。TCP 窗口必须 ≥ BDP 才能填满管道（实际还要留余量）。Linux 默认 tcp_wmem/tcp_rmem 的 max 常见在 几 MB 量级（如 4–6 MB，随内核版本变化），所以默认通常不够，需要显式调大 SO_SNDBUF/SO_RCVBUF 或抬高 net.ipv4.tcp_wmem/tcp_rmem 的上限让自动调优跑到这个量级。注意窗口扩大因子（window scaling）现代内核默认开启，早已不受 64 KB 限制；调参前先 ss -ti 看 cwnd、snd_wnd、rtt 实测值。

  4. 两种典型情况：① 手工 setsockopt(SO_RCVBUF/SO_SNDBUF) 会关掉内核自动调优，你设的值成为硬上限，若比 BDP 小（或比自动调优给的值小）吞吐立刻下降；② 设得过大：每连接占用更多内核内存，接收侧应用读不及时时数据在缓冲里排队，延迟升高（bufferbloat），cache 命中率也会下降。所以纪律是"先 ss -ti 看数据再调参"，不要盲设。

  5. 因为 write 返回 ≠ 对端收到。如果计时在"最后一个 write 返回"时就停，测的是把数据灌进本机发送缓冲的速度——最后几十 MB 可能还没上线路，数字严重虚高，而且结果主要由 sk_sndbuf 大小决定，跟网络几乎无关。必须等对端收到全部数据后回一个确认（TTCP 的 ack），把"最后一字节被对端接收"这一事件纳入计时，才是真正的端到端吞吐。

· 非阻塞 I/O

目标

fcntl O_NONBLOCK；EAGAIN/EWOULDBLOCK 不是致命错误；与阻塞模型对比。

UNP 对照

  • 1.4 特殊 errno
  • Ch16 Nonblocking I/O

概念详解

1. 非阻塞是什么：把"等"从内核搬回用户态

阻塞模型：read 没数据 → 进程睡眠（挂到 socket 等待队列，上下文切换）→ 数据到达被唤醒。 非阻塞模型：read 没数据 → 立刻返回 -1 + EAGAIN，"现在没有，你稍后再来"。

一句话：非阻塞把"何时有数据"的决策权交给应用。单线程要同时伺候多个 fd（其中任何一个都可能暂时无数据），就必须非阻塞——这是 07 epoll 的前置条件。

2. 设置方法

#include <fcntl.h>
int setNonBlock(int fd) {
    int flags = fcntl(fd, F_GETFL, 0);         // 必须先读再改再写回
    if (flags < 0) return -1;
    return fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}

坑：fcntl(fd, F_SETFL, O_NONBLOCK) 不读旧值直接写——把 fd 上其他标志（如 O_APPEND）清掉了。新建 socket 更简单：socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0)，一次原子完成。

3. 各调用在非阻塞模式下的返回

调用 无数据/不能做时 说明
read -1 EAGAIN 稍后再读
write -1 EAGAIN 或部分写（返回 < n） 发送缓冲满；已写入的字节数必须记账
accept -1 EAGAIN 队列空（惊群/事件循环里常见）
connect -1 EINPROGRESS SYN 已发出，握手 正在进行，不是失败！

EAGAIN == EWOULDBLOCK（Linux 上同值），语义即"再试一次"。

4. 非阻塞 connect：唯一"进行时"的返回值

int r = connect(fd, ...);
if (r < 0 && errno != EINPROGRESS) { /* 真错误，如 EADDRNOTAVAIL */ }

// EINPROGRESS 之后：把 fd 加入 select/epoll 的写集合，
// 就绪后还要检查是否真的成功：
int err = 0; socklen_t len = sizeof(err);
getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len);
if (err) { /* connect 失败，err 是错误码，如 ECONNREFUSED */ }

为什么必须 SO_ERROR：非阻塞 connect 完成的信号是"fd 可写"，但失败（收到 RST）同样表现为可写——可写 ≠ 成功。

5. 阻塞 vs 非阻塞 vs 事件驱动

模型 单 fd 等待 多 fd CPU 占用
阻塞 + 每连接一线程/进程 内核睡眠，零开销 线程数=连接数，内存/切换成本 低
非阻塞 + 轮询 — for fd: try_read() 100% 忙等
非阻塞 + epoll — 就绪回调，只处理有事件的 低，且单线程可承万级连接

muduo 的组合拳：epoll LT + 非阻塞 fd（Ch 6.2 陈硕的选择）——epoll 保证只碰就绪的 fd，非阻塞保证碰了也不会卡住（LT 水平触发下事件可能已被处理过，重读必须能立即返回）。

C++ 示例：非阻塞读的完整姿势

// 处理一次 EPOLLIN 事件（LT 模式）
void handleRead(int fd, Buffer* out) {
    for (;;) {                                  // 循环读：一次事件尽量榨干
        char buf[65536];
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n > 0) {
            out->append(buf, n);                // 先攒着，粘包解码另做（见 02）
            continue;
        }
        if (n == 0) { /* 对端 EOF，关连接 */ return; }
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;  // 读干了：正常退出
        if (errno == EINTR) continue;
        /* 其他 errno：ECONNRESET 等 → 出错处理 */ return;
    }
}

// 非阻塞写：partial write 记账
void handleWrite(int fd, Buffer* pending) {
    while (pending->readableBytes() > 0) {
        ssize_t n = write(fd, pending->peek(), pending->readableBytes());
        if (n > 0) { pending->retrieve(n); continue; }
        if (errno == EAGAIN) {
            // 发送缓冲满：注册 EPOLLOUT，等下次可写再续（见 07）
            enableWritable(fd);
            return;
        }
        if (errno == EINTR) continue;
        return;  // 错误
    }
    disableWritable(fd);    // 全发完：立刻注销 EPOLLOUT，否则 busy loop
}

内核视角

  • O_NONBLOCK 存在 struct file->f_flags。tcp_recvmsg 检查：接收队列为空时，阻塞 → 把进程挂到 sk_wq 等待队列并 schedule()；非阻塞 → 直接 -EAGAIN 返回，全程零睡眠零切换
  • tcp_sendmsg：发送缓冲剩余空间不足以容纳全部数据时——阻塞模式等空间（可能部分写后睡）；非阻塞模式 一点空间都没有才 EAGAIN，有一点就部分写——所以非阻塞 write 返回正数 n < 请求值是常态
  • 唤醒延迟的物理成本：数据到达 → 硬中断/软中断 → 唤醒进程 → 调度器安排它上 CPU（µs 级，还要看负载）。这是内核阻塞/唤醒路径的固有开销，也是 HFT 后来发明 busy polling（SO_BUSY_POLL，进程自旋问内核"有了吗"）和 内核旁路（13 DPDK，用户态驱动直接收包）的动机
  • accept 的 EMFILE：fd 用尽时 accept 会 持续返回 EMFILE，非阻塞事件循环若不处理（如先 reserve 一个 idle fd 应急 close），listenfd 一直可读 → busy loop 拒绝服务

坑点

  • 非阻塞 connect 返回 EINPROGRESS
  • 忙等 vs 事件驱动（见 07）
  • fcntl 直接 F_SETFL 不读旧值，清掉其他标志
  • 非阻塞 write 只处理 EAGAIN 不处理 部分写——数据悄悄丢
  • 可写事件不注销 → EPOLLOUT 永远触发 → CPU 100%（LT 模式经典 bug）
  • 把 EAGAIN 当错误断开连接
  • 非阻塞 fd 交给阻塞假设的代码（如 stdio 缓冲）使用，行为混乱

自测题

  1. 为什么 muduo 用 LT 触发也必须配非阻塞 fd？（提示：同一个 fd 被两个事件循环/重入处理时）
  2. 非阻塞 write 返回 100（请求 1000），剩下 900 字节去哪了？谁负责？
  3. 非阻塞 connect 成功/失败都表现为"可写"，怎么区分？
  4. MSG_DONTWAIT 与 O_NONBLOCK 的区别？为什么热路径自旋用前者？
  5. 进程被唤醒到真正跑起来，中间发生了什么？这笔开销大概是多少？
参考答案

  1. LT 的含义是"只要缓冲里还有数据就一直报告"，这恰恰意味着同一件事可能被处理两次：两个事件循环/两个线程同时持有该 fd、回调里又同步跑了一次事件循环（重入）、或本轮只处理了部分数据。此时再 read，如果 fd 是阻塞的而数据已被前一个处理者读干，就会阻塞整个事件循环（所有其它连接一起卡死）。非阻塞 fd 保证"碰了也不会卡住"——读到 EAGAIN 就退出，最坏情况是多一次无效调用。ET 则更严格：必须循环读到 EAGAIN，强制非阻塞。

  2. 剩下 900 字节根本没进内核（tcp_sendmsg 发现发送缓冲只剩 100 字节空间，拷完就返回了），也不会自动重发。责任在应用层：必须按返回值记账——把已发出的 100 字节从 pending buffer 取走，剩下的继续挂在输出 Buffer 上，然后注册 EPOLLOUT，等可写事件再续写；全部发完立刻注销 EPOLLOUT（LT 下不注销会 100% CPU）。muduo 的 TcpConnection::send() 就是这个逻辑。牢记：非阻塞 write 是"有一点空间就部分写"，返回 0 < n < 请求值 是常态，只看 EAGAIN 不处理部分写 = 静默丢数据。

  3. 用 getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len) 取 pending error：err == 0 即连接成功；err != 0 就是失败原因（ECONNREFUSED、ETIMEDOUT、EHOSTUNREACH 等），此时应关闭 fd 并按错误处理。原因是：非阻塞 connect 成功和失败都表现为"fd 可写"——收到 RST 同样让 socket 变为可写——所以"可写 ≠ 成功"。辅助判据：成功后再次 connect 返回 EISCONN，且 getpeername() 有效。

  4. O_NONBLOCK 是 fd 上的持久标志（存在 struct file->f_flags），影响该 fd 上所有读写；MSG_DONTWAIT 是单次调用的 flag，只让这一次 recv/send 非阻塞，不改 fd 状态。热路径自旋用 MSG_DONTWAIT：自旋循环本来就是自己反复调用 recv，单次非阻塞已足够；改 fd 标志反而会波及共享同一 struct file 的其它路径（dup/fork 后标志是共享的），让别处意外拿到 EAGAIN，也破坏"阻塞/非阻塞"约定。另外 O_NONBLOCK 要用 F_GETFL→改→F_SETFL，直接 F_SETFL 会清掉 O_APPEND 等标志。

  5. 数据到达 → 网卡硬中断 → 软中断把 skb 放入接收队列 → sk_data_ready 唤醒等在 sk_wq 上的进程（置为 TASK_RUNNING 挂进 runqueue）→ 调度器择机上 CPU（可能被更高优先级任务抢占，跨核还要等 IPI/迁移）→ 恢复上下文、cache/TLB 冷启动。这笔开销通常是 微秒级（几 µs，负载高或跨核时更大）。正是这笔"唤醒 + 调度"延迟，催生了 busy polling（SO_BUSY_POLL，进程自旋问内核"有了吗"）和内核旁路（DPDK，用户态轮询驱动直接收包）。

目标

就绪通知 vs 真正 I/O；水平触发 vs 边缘触发；单线程多连接。

概念详解

1. I/O 复用解决什么

阻塞 I/O 一次只能等一个 fd；一个连接一个线程在万级连接下（C10K）线程内存与切换成本爆炸。I/O 复用 = 一次系统调用，把 N 个 fd 的"谁就绪了"问清楚，然后只对就绪 fd 做 I/O。

注意它复用的是 等待，不是 I/O 本身——epoll_wait 返回后 read/write 还是要自己做。就绪 ≠ 数据到手。

2. 三代 API 对比

select poll epoll
fd 数量上限 FD_SETSIZE（默认 1024，编译期硬编码） 无（pollfd 数组） 无（受 ulimit -n）
每次调用成本 O(n) 线性扫描 + 每次全量拷贝 fd 集进内核 同左 O(1)：注册一次，epoll_wait 只取就绪链表
fd 传递 每次重建 fd_set 每次传数组 epoll_ctl 增量注册
触发模式 LT LT LT + ET
跨平台 是（Windows 也有） POSIX 仅 Linux（BSD: kqueue）

select 至今的合理用途：同时等 超时 + 少量 fd + 信号安全的简单场景（如 nc）；连接数上量后没有理由不用 epoll。

3. LT vs ET：语义与纪律

  • LT（水平触发，默认）：只要接收缓冲 还有 数据，每次 epoll_wait 都报告 EPOLLIN。忘了读？下次还会提醒你——宽容。
  • ET（边缘触发）：仅在状态 变化（无→有）时报告一次。必须一次读到 EAGAIN（配合非阻塞 fd，循环 read 直到读干），否则残留数据再也不会有通知——连接"假死"。
LT ET
读法 一次事件读一次也行（下次还会提醒） 必须循环到 EAGAIN
fd 要求 非阻塞（陈硕建议，防重入卡死） 强制 非阻塞
epoll_wait 返回次数 多 少一点
编程复杂度 低，不易出 bug 高（漏读=死连接，EPOLLOUT 注销逻辑更绕）

muduo 明确选 LT（陈硕《Linux 多线程服务端编程》6.2）：性能差距微小，正确性差距巨大——生产系统的工程判断。

4. epoll 三件套

int epfd = epoll_create1(EPOLL_CLOEXEC);        // 内核里建一个 eventpoll
struct epoll_event ev{ .events = EPOLLIN, .data.fd = sockfd };
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev);    // 注册/修改/删除 (MOD/DEL)
struct epoll_event evs[64];
int n = epoll_wait(epfd, evs, 64, timeout_ms);  // 取就绪事件（拷回用户态）

常用事件：EPOLLIN（可读）/ EPOLLOUT（可写）/ EPOLLRDHUP（对端关写）/ EPOLLERR（出错，epoll 总会报告，无需注册）/ EPOLLET（边沿）/ EPOLLONESHOT（一次性，多线程 worker 场景防两个线程同时处理同一 fd）。

5. epoll 高效的原理（不是"内存拷贝少"这么简单）

  • 内核 eventpoll 结构里有 红黑树（注册的所有 fd）+ 就绪链表 rdllist
  • epoll_ctl(ADD) 时，在目标 socket 的等待队列上注册一个 回调；数据到达（软中断上下文）→ 回调把该 epitem 挂进 rdllist → 唤醒等在 epoll_wait 上的进程
  • 所以 epoll_wait 不需要扫描任何 fd 集合：事件发生时已经"排队"，等待者只是取号

对比 select：每次调用把 fd 集合整个拷进内核，内核线性遍历所有 fd 调用其 poll 方法——fd 越多越慢，且这个成本 每个连接每次循环都付一遍。

C++ 示例：epoll LT echo 服务器（完整骨架）

// echo_epoll.cpp — g++ -O2 echo_epoll.cpp -o echo_epoll
#include <sys/epoll.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <fcntl.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>
#include <vector>

int main() {
    int listenfd = socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0);
    int one = 1;
    setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof(one));   // 重启立绑
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons(9007);
    bind(listenfd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));
    listen(listenfd, SOMAXCONN);

    int epfd = epoll_create1(EPOLL_CLOEXEC);
    epoll_event ev{};
    ev.events = EPOLLIN;                       // listenfd：LT 足矣
    ev.data.fd = listenfd;
    epoll_ctl(epfd, EPOLL_CTL_ADD, listenfd, &ev);

    std::vector<epoll_event> evs(64);
    for (;;) {
        int n = epoll_wait(epfd, evs.data(), (int)evs.size(), -1);
        if (n < 0) { if (errno == EINTR) continue; perror("epoll_wait"); break; }

        for (int i = 0; i < n; ++i) {
            int fd = evs[i].data.fd;
            if (fd == listenfd) {                                  // 新连接
                for (;;) {                                         // LT 下读一次也行；循环收干净
                    int cfd = accept4(listenfd, nullptr, nullptr,
                                      SOCK_NONBLOCK | SOCK_CLOEXEC);
                    if (cfd < 0) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                        if (errno == EINTR) continue;
                        if (errno == EMFILE) { /* 应急 fd 技巧，见 06 */ break; }
                        break;
                    }
                    epoll_event cev{};
                    cev.events = EPOLLIN | EPOLLRDHUP;
                    cev.data.fd = cfd;
                    epoll_ctl(epfd, EPOLL_CTL_ADD, cfd, &cev);
                }
            } else {                                               // 已建连接
                if (evs[i].events & (EPOLLERR | EPOLLHUP | EPOLLRDHUP)) {
                    epoll_ctl(epfd, EPOLL_CTL_DEL, fd, nullptr);
                    close(fd);
                    continue;
                }
                if (evs[i].events & EPOLLIN) {
                    char buf[4096];
                    ssize_t r = read(fd, buf, sizeof(buf));         // LT：读一次
                    if (r > 0) {
                        ssize_t w = write(fd, buf, r);              // echo 简化：
                        (void)w;                                    // 完整版须处理 EAGAIN
                    } else if (r == 0 || errno != EAGAIN) {         // EOF 或真错误
                        epoll_ctl(epfd, EPOLL_CTL_DEL, fd, nullptr);
                        close(fd);
                    }
                }
            }
        }
    }
    return 0;
}

  • 数据到达路径：网卡中断 → softirq tcp_v4_rcv → 数据入接收队列 → sk->sk_data_ready → ep_poll_callback → epitem 链入 rdllist → 唤醒 epoll_wait。回调发生在软中断上下文，这就是"就绪通知是异步埋好的"的确切含义

自测题

  1. epoll 为什么快？把"红黑树、就绪链表、回调"串成数据到达后的一条完整路径。
  2. ET 模式下读到 3000 字节返回（缓冲还有 500 字节）没继续读，会发生什么？
  3. 为什么 muduo 选 LT？ET 的性能优势到底在哪个环节？
  4. EPOLLOUT 应该常驻注册还是按需注册？为什么？
  5. epoll_wait 返回的 fd 已被别的分支 close 了，如何防御？
参考答案

  1. 完整路径分"注册"和"通知"两段： - 注册：epoll_ctl(ADD) → ep_insert() 把 fd 包装成 epitem 插入红黑树（只做一次，后续 epoll_wait 不再传 fd 集合），同时在目标 socket 的等待队列 sk_wq 上挂回调 ep_poll_callback。 - 通知：网卡中断 → softirq tcp_v4_rcv → 数据入 sk_receive_queue → sk->sk_data_ready 触发 ep_poll_callback → 把该 epitem 挂进就绪链表 rdllist → 唤醒阻塞在 epoll_wait 的进程。回调发生在软中断上下文，等于"事件一到就已经排好队"。 - 取事件：epoll_wait 只把 rdllist 上的事件 copy_to_user，不遍历任何 fd，成本与就绪数成正比、与注册总数无关。对比 select：每次调用全量拷贝 fd 集 + O(n) 遍历，这个成本每个循环都付一遍。

  2. 那 500 字节再也不会有通知——ET 只在状态"无→有"的边沿上报一次，缓冲里一直有数据不构成新事件。结果：残留字节（以及依赖它才能凑齐的半包）被永久滞留，对端等响应、本端不读，连接假死。所以 ET 的硬纪律是：配合非阻塞 fd，循环 read 直到返回 EAGAIN（或 EPOLLIN 事件里一次读干），绝不能"一次事件只读一次"。

  3. 因为两者的性价比不对等。LT 的优势在正确性：漏读一次事件，下次 epoll_wait 还会报告（缓冲还有数据），最多是慢一点；EPOLLOUT 忘了注销也只是多几次空事件。ET 的优势仅在"epoll_wait 返回次数少一点"（每 fd 少几次系统调用），而真实成本在 read/write 与协议处理上，占比很小；代价却是漏读即死连接、EPOLLOUT 注销逻辑更绕、必须强制非阻塞。陈硕《Linux 多线程服务端编程》6.2 的判断：性能差距微小，正确性差距巨大，生产系统选 LT。

  4. 按需注册。只在输出 Buffer 有剩余数据时（上次 write 部分写或返回 EAGAIN）才 EPOLL_CTL_MOD 加上 EPOLLOUT，写完立刻 disableWriting() 注销。因为发送缓冲几乎总是可写，常驻注册会让每次 epoll_wait 都返回 EPOLLOUT → 无意义事件风暴，LT 模式下 CPU 直接打满（这是 LT 最经典的 bug）。muduo 里对应 Channel::enableWriting()/disableWriting()。ET 同理：ET 只在"不可写→可写"的边沿触发一次，常驻反而可能错过，也应按需注册 + 循环写到 EAGAIN。

  5. 核心是不要把裸 fd 号当身份——fd 号 close 后会被内核复用，旧事件里的 fd 号可能已经指向一条全新连接，按号查表就会串线。防御组合拳： - epoll_event.data 存指针（muduo 存 Channel*）而非 fd 号，处理前先校验该 Channel 仍有效、isNoneEvent 就跳过； - 关闭顺序固定为先 EPOLL_CTL_DEL 再 close； - 用引用计数/弱引用/世代号（generation）确认对象在处理期间还活着（shared_ptr<TcpConnection> 延长生命期是 muduo 的做法）； - 残留事件的来源常常是 dup/fork 让 struct file 引用未归零（epitem 不注销、通知照发），用 SOCK_CLOEXEC 并避免无谓 dup； - 对已关闭 fd 的 I/O 返回 EBADF，应当记日志忽略而不是崩溃。

· UDP 与组播

目标

无连接、丢包、MTU；组播 IP_ADD_MEMBERSHIP、TTL。

UNP 对照

  • Ch8 UDP、Ch21–22 多播

概念详解

1. UDP 的真实语义：数据报 + 尽力而为

TCP 给你的承诺（不丢、不乱、不重、流控、拥塞控制）UDP 一条都不给，换来的是：

  • 保留消息边界：一次 sendto = 一个数据报 = 对端一次 recvfrom（≤ 一次，见下）
  • 无连接：不用握手、不用 accept，发就走
  • 无 Nagle、无重传、无重排——延迟抖动小且行为可预测

数据报长度陷阱：recvfrom 缓冲如果 小于 数据报长度，只返回前 N 字节，剩余部分被丢弃（不是"下次继续读"）——和 TCP 字节流语义根本不同。Linux 专属：recvmsg 带 MSG_TRUNC 标志时返回值是完整数据报长度（哪怕被截断），可用它探测"对面发了多大"来校准缓冲。

2. connect 一个 UDP socket（不是建立连接）

UDP 的 connect() 只做一件事：固定对端地址。之后：

  • send/recv 直接用（不用每次填地址）
  • 内核收到 来自其他地址 的数据报直接丢弃（过滤器）
  • 对端 ICMP 错误（端口不可达 → ECONNREFUSED）能传回本进程——未 connect 的 UDP 收不到异步错误

单播行情/订单的单一对端场景应该 connect：省每次路由查找，还白送过滤和错误回报。

3. 丢包发生在哪：三个丢弃点

丢弃点 触发条件 观测手段
网络路径 拥塞、CRC 错误 抓包两端对比（12.5 Wireshark）
接收 socket 缓冲满 应用读太慢，sk_rcvbuf 溢出——静默丢弃，无任何报错 netstat -su 的 receive buffer errors；ss -unm 看 sk_mem
重组队列 分片丢一片则整个数据报丢弃 netstat -ip fragmentation 行

UDP 丢包没有重传——可靠性是应用层的事（序列号 + gap 检测 + 请求重传/切换备源）。

4. MTU 与分片

以太网 MTU 1500 = IP 头 20 + UDP 头 8 + payload ≤ 1472
  • payload > 1472 → IP 分片：任何一片丢失 = 整个数据报丢失，且分片/重组消耗路径设备资源
  • 现代实践：sendto 前就限制 payload ≤ 1472（或路径 MTU 发现 + IP_MTU_DISCOVER 设 IP_PMTUDISC_DO 置 DF 位）
  • 云/隧道环境 MTU 常 <1500（VXLAN 1450），HFT 部署要实测：ping -M do -s 1472 host

5. 组播：一对多分发

单播要 N 份拷贝，组播让网络设备在分叉点复制——交易所行情分发的标准形态（组播地址 224.0.0.0~239.255.255.255，MAC 层映射 01:00:5e:xx:xx:xx）。

接收端三件套：

// 加入组播组（触发 IGMP 报文，让上游交换机开始向你转发）
struct ip_mreq mreq{};
inet_pton(AF_INET, "239.255.0.1", &mreq.imr_multiaddr);
inet_pton(AF_INET, "0.0.0.0",     &mreq.imr_interface);   // 或具体网卡 IP
setsockopt(fd, IPPROTO_IP, IP_ADD_MEMBERSHIP, &mreq, sizeof(mreq));

// 发送端两个必设项
u_char ttl = 4;                          // 默认 TTL=1：出不了本网段！
setsockopt(fd, IPPROTO_IP, IP_MULTICAST_TTL, &ttl, sizeof(ttl));
u_char loop = 1;                         // 同主机是否回环给自己（调试用）
setsockopt(fd, IPPROTO_IP, IP_MULTICAST_LOOP, &loop, sizeof(loop));

同机多进程收同一组播：SO_REUSEADDR（甚至 IP_ADD_SOURCE_MEMBERSHIP 做 SSM 源过滤）。

C++ 示例：组播行情接收器骨架

// mcast_recv.cpp — g++ -O2 mcast_recv.cpp -o mrecv
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <cerrno>
#include <cstdio>
#include <cstring>

int main() {
    int fd = socket(AF_INET, SOCK_DGRAM | SOCK_CLOEXEC, 0);
    int one = 1;
    setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof(one));  // 多接收者
    int rcvbuf = 4 * 1024 * 1024;                                  // 行情突发，加大接收缓冲
    setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &rcvbuf, sizeof(rcvbuf));

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port   = htons(50000);
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    bind(fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));   // 必须先 bind 组播端口

    ip_mreq mreq{};
    inet_pton(AF_INET, "239.255.0.1", &mreq.imr_multiaddr);
    mreq.imr_interface.s_addr = htonl(INADDR_ANY);
    setsockopt(fd, IPPROTO_IP, IP_ADD_MEMBERSHIP, &mreq, sizeof(mreq));

    char buf[2048];                        // ≥ MTU 1500，防截断静默丢尾部
    for (;;) {
        ssize_t n = recvfrom(fd, buf, sizeof(buf), 0, nullptr, nullptr);
        if (n < 0) { if (errno == EINTR) continue; perror("recvfrom"); break; }
        // 行情帧处理：先读帧头里的 sequence number，检测 gap（丢包自愈的起点）
        // uint64_t seq; memcpy(&seq, buf, 8);
        // if (seq != expect) requestRetransmit(expect, seq);
        printf("datagram %zd bytes\n", n);
    }
    return 0;
}

发送端：普通 sendto 到 239.255.0.1:50000，记得设 TTL。

内核视角

  • 接收路径：udp_rcv → 按四元组（或组播组）查 UDP 哈希表（udp_table）→ __udp_enqueue_schedule_skb：接收队列满时直接 kfree_skb 丢包，仅计数（UDP_MIB_RCVBUFERRORS）——这就是"静默丢包"的现场
  • 每数据报一个 sk_buff，recvfrom 一次取走整块（保边界）；与 TCP 不同，没有 prequeue/quickack 那套状态机，路径更短、行为更可预测——HFT 喜欢它的根本原因
  • 组播接收：网卡按 MAC 组播过滤（ imperfect filtering，杂混模式兜底）→ IGMP snooping 让交换机只向成员端口转发。VM/容器 bridge 默认开 IGMP snooping 但配置不当时整组丢包——云上行情收不到，先查交换机端口
  • SO_RCVBUF 记账规则：内核把你设的值翻倍作为队列上限（多出的部分算 sk_buff 结构开销）。所以设 4MB 实际生效约 8MB（可用 ss -unm 的 sk_meminfo 验证），设的时候按"业务想要的 2 倍"估即可，不用自己预先除以 2

坑点

  • UDP「发出去」不等于「对端收到」
  • 组播在交换机 / Wi‑Fi 上的限制
  • 组播 TTL 默认 1：跨网段收不到，以为是代码 bug
  • recvfrom 缓冲小于数据报 → 静默截断（连 errno 都没有）
  • 忘 bind 组播端口直接 ADD_MEMBERSHIP → 什么也收不到
  • 接收缓冲太小 + 行情突发 → 交换机统计正常但应用层缺号——丢在内核队列里
  • 同机调试：IP_MULTICAST_LOOP 关了导致本机自测收不到

场景 关系

自测题

  1. recvfrom 用 1000 字节缓冲收 1500 字节数据报，返回值是多少？剩下的 500 字节呢？
  2. UDP connect 后哪些行为变了？为什么单对端场景应该 connect？
  3. 行情接收程序缺号（seq 跳跃），列出三个可能的丢弃点及各自的观测命令。
  4. 组播 TTL 不设会发生什么？IP_MULTICAST_LOOP 什么时候该开？
  5. 为什么 HFT 行情用 UDP 而订单常用 TCP？（从延迟确定性与可靠性职责两个角度）
参考答案

  1. recvfrom 返回 1000（它返回的是实际拷给你的字节数），多出的 500 字节被直接丢弃——UDP 是数据报语义，一次 recvfrom 消费整个数据报，截掉的尾部不会留到"下次再读"，而且没有任何 errno，是静默截断。所以接收缓冲必须 ≥ 最大数据报（以太网 MTU 1500 → 通常取 2048；jumbo 环境更大）。要探测对端到底发了多大，可用 recvmsg + MSG_TRUNC（Linux 返回完整长度）或先用 ioctl(FIONREAD) 查队列上下一个数据报的大小。

  2. UDP 的 connect() 不发任何报文，只是给 socket 打上对端标记，之后行为变化有四：① 可以用 send/recv 而不必每次填地址；② 内核过滤：来自其它地址的数据报直接丢弃（免费的安全过滤器）；③ 能收到异步 ICMP 错误，例如对端端口不可达 → 后续操作返回 ECONNREFUSED（未 connect 的 UDP 收不到这类错误）；④ 省掉每次发送的路由查找，热点路径更快。可再次 connect 改对端，或用 AF_UNSPEC 解除。单对端场景（行情/订单单播）应该 connect：更省、更安全，还白送错误回报。

  3. 三个丢弃点及观测命令： - 网络路径（交换机/链路丢包、CRC 错误、IGMP snooping 配置不当）：两端同时抓包 tcpdump -i eth0 -w a.pcap 'udp port 50000' 后对比；交换机侧看端口丢包计数。 - 网卡/驱动 ring buffer 溢出（中断跟不上收包速率）：ethtool -S eth0 | grep -iE 'drop|miss|no_bufs'、netstat -i、cat /proc/net/dev 的 drop 列。 - 内核 socket 接收缓冲满（最常见，"交换机统计正常但应用层缺号"）：cat /proc/net/udp 的 drops 列、netstat -su 的 receive buffer errors、ss -unm 看 skmem 与 sk_rcvbuf。 另有 IP 分片重组失败：netstat -ip。定位顺序建议：先看 /proc/net/udp drops 与 netstat -su → 再看网卡计数 → 最后两端抓包对比。应用层则用帧里的 sequence number 做 gap 检测，再通过 TCP 重传通道补。

  4. 组播 TTL 默认是 1：报文到第一跳路由器就被丢弃，出不了本网段——现象是"同网段能收、跨网段收不到"，常被误判成代码 bug。跨网段/跨机房必须显式设 IP_MULTICAST_TTL（≥ 需要经过的跳数，生产常设 1~几，不要盲目设大，否则报文会在网内乱窜）。IP_MULTICAST_LOOP 决定本主机发出的组播是否回环给同主机的接收者（Linux 默认开启 = 1）：同机自测/同机多进程联调必须开，否则本机接收者收不到；生产环境若同机还有其它接收者且不希望它们重复收到，可以关（关之前先确认没有本机接收者依赖它）。

  5. 两个角度： - 延迟确定性：UDP 无连接、无重传、无拥塞控制、无队头阻塞，一个数据报就是一个数据报，延迟抖动小、行为可预测；TCP 丢一个包就要等重传（RTO 或快重传），后面所有数据都被队头阻塞，抖动是毫秒级的。行情要的就是这种确定性。 - 可靠性职责：行情"最新的才有用"，丢一帧可以由应用层用序列号检测 gap、走重传通道（通常是 TCP）或 A/B 双馈互补，把可靠性放在应用层按需实现，比让 TCP 强制重传已经过期的行情划算得多；而且组播天然一对多，一份数据全网段共享带宽。 订单反过来：每一笔都必须可靠、有序、不重复地送达，丢单/重单是资金事故，TCP 的重传、排序、流控、拥塞控制正好把这些职责从应用层拿走；订单是低频点对点，建连握手/RTT 的代价可以用连接预热消化。一句话：行情要确定性 → UDP（组播）+ 应用层可靠性；订单要可靠性 → TCP。

概念详解

1. 为什么结构体不能直接 memcpy 上线

把内存里的 struct 原样发送，四个独立炸点：

本机实测（clang 23，arm64）——"改全局对齐设置 → 第三方库 core dump"现场（陈硕第 0 讲新手坑 #4 原话"Modify the global align setting causes core dump in 3rd party library"）：公共头文件定义 struct Pkt { uint8_t type; uint32_t seq; };，第三方库 lib.c 正常编译，main.c 用 -fpack-struct 全局改对齐（等价于 #pragma pack(1) 泄漏到整个 TU）：

正常（两边都不 pack）：
  [main] sizeof(Pkt)=8 offsetof(seq)=4 seq=0xAABBCCDD
  [lib]  sizeof(Pkt)=8 offsetof(seq)=4 seq=2864434397   ← 0xAABBCCDD，一致
main 加了全局 -fpack-struct：
  [main] sizeof(Pkt)=5 offsetof(seq)=1 seq=0xAABBCCDD
  [lib]  sizeof(Pkt)=8 offsetof(seq)=4 seq=6062250      ← 垃圾！

同一块内存，main 按偏移 1 写 seq，lib 按偏移 4 读——pack 是编译单元级的，ABI 契约却是链接级的。本例只是读到垃圾值；结构体若含指针/函数指针，读错位 = 野指针 = core dump。所以头文件里 #pragma pack 必须 push/pop 配对，绝不能泄漏（见下方 §"正确的二进制纪律"和 C++ 示例的 pack(push,1) 写法）。

struct Order {
    int32_t  id;        // 8B 处还轮不到它——看 padding
    int64_t  price;     // 8 字节成员要求 8 字节对齐 → id 后面垫 4 字节
    char     side;      // 1 字节
    // 编译器在末尾再垫 7 字节让 sizeof 是 8 的倍数
};                      // sizeof = 24，线上真正有用的只有 13 字节
炸点 表现
padding 不同编译器/开关下填充不同，两端布局不一致 → 字段错位
字节序 x86 小端 vs 网络大端，整数字段直接镜像互换
类型宽度 long 在 Linux LP64 是 8 字节、Windows LLP64 是 4 字节；time_t、指针字段更不能上线
对齐访问 收到字节流 (int64_t*)(buf+1) 这类未对齐 cast 在 x86 能跑，ARM/Sparc 直接 SIGBUS

2. 正确的二进制纪律（wire format 规则）

  1. 只用 定宽类型：int8/16/32/64_t，禁止 long/int/指针上协议
  2. 字节序显式化：全协议统一（大端=网络序是传统；FIX/SBE 用小端），收发两端各转一次
  3. 无隐式 padding：要么 #pragma pack(1)（代价：未对齐访问），要么手写字段级 encode/decode（推荐，编译器优化后基本免费）
  4. 版本协商：帧头带版本号 + 长度；新版本只能加字段不能改老字段含义
// 手写 encode/decode：显式、可移植、零歧义
void encodeOrder(char* p, const Order& o) {
    p = put_be32(p, o.id);         // 4B 大端
    p = put_be64(p, o.price);
    *p++ = o.side;
}
Order decodeOrder(const char* p) {
    Order o;
    o.id    = get_be32(p);  p += 4;
    o.price = get_be64(p);  p += 8;
    o.side  = *p;
    return o;
}
constexpr size_t kOrderWireSize = 4 + 8 + 1;            // id + price + side
static_assert(kOrderWireSize == 13, "wire size frozen"); // 冻结线上尺寸

3. protobuf：怎么编码的，怎么演化的

编码要点（varint + tag）：

  • 每个字段 = tag(varint) = field_number << 3 | wire_type + 值
  • 整数用 varint（每 7 位一组，高位表继续）：小数字 1 字节，代价是大数最多 10 字节
  • 未设字段 完全不占线上字节；接收端遇到未知 field number 存进 unknown fields 原样保留

演化规则（兼容性的生命线）：

改动 安全？
新增字段 安全（老端跳过，新端用默认值）
删除字段 field number 永不复用（reserved）即安全
改字段号 等于删+加，数据"消失"
改类型 int32↔int64 varint 域内兼容
改 required（proto2） 灾难：required 永远别用

4. HFT 的选择：SBE / ITCH 为什么不是 protobuf

protobuf SBE（FIX Simple Binary Encoding） ITCH（交易所原生）
布局 varint 流，必须顺序解析 固定偏移，字段直接按 offset 访问 定长消息，按消息类型查表
解码开销 varint 循环 + 分支 近零：读到 offset 直接用（flyweight，不拷贝） 近零
带宽 小数字紧凑 略大（定长字段） 定长
适用 配置/RPC/管理面 热路径行情/订单 交易所原生行情

一句话：管理面用 protobuf 的灵活性，热路径用定长二进制的确定性。

5. 定长帧 + 零拷贝解码（把 02/08/09 串起来）

[2B 类型][8B 序列号][定长 payload]  ← 组播 UDP 数据报天然保边界（08）
                                          ↓
                        校验长度 → 按类型偏移表取字段（零拷贝，SBE 式）

C++ 示例：packed 结构 + 静态断言（知道何时可用）

// wire.h — 定长线上格式：pack(1) + static_assert 双保险
#pragma pack(push, 1)                 // 线上布局：13 字节，无 padding
struct WireOrder {
    uint32_t id;                      // 大端（encode 时转）
    uint64_t price;                   // 大端
    char     side;                    // 'B'/'S'
};
#pragma pack(pop)

static_assert(sizeof(WireOrder) == 13, "wire format frozen");
static_assert(sizeof(uint32_t) == 4 && sizeof(uint64_t) == 8,
              "wire types must be fixed-width");

// 注意：pack(1) 后对 WireOrder* 取成员地址做 8 字节加载是未对齐访问——
// ARM 上要么 memcpy 取值，要么编译器 -fpack-struct 后由编译器生成安全访问
inline uint64_t load_be64(const void* p) {
    uint64_t v;
    memcpy(&v, p, 8);                 // memcpy 定宽：编译器优化成单条加载
    return __builtin_bswap64(v);      // 小端主机转大端（GCC/Clang）
}

底层视角

  • 字节序根源在 CPU：x86 mov 直接按小端解释寄存器；网络协议族历史选择大端（先传高位字节）。htonl 在 x86 上编译成 bswap 指令（~1 cycle）——字节序转换在 encode/decode 里根本不是性能问题，varint 的分支循环才是
  • 对齐根源在访存通路：CPU 按对齐边界访问 cache line；未对齐访问 x86 靠硬件拆成两次（慢），部分架构直接异常。MMIO/网卡 DMA 描述符同样要求对齐——嵌入式背景（振鹏的老朋友）在 DMA ring buffer 上见过同一件事
  • 零拷贝链条：recvfrom MSG_DONTWAIT 后不 memcpy 进业务对象，直接在收包缓冲上按偏移解出字段——配合 13 DPDK 用户态收包，"网卡到策略"全程零拷贝是 HFT 解码的终极形态

坑点

  • 结构体 memcpy 上线（对齐、32/64 位）
  • protobuf optional / packed 与旧客户端兼容
  • field number 复用（proto2 的 required 心魔）
  • long/time_t/指针字段进协议——Windows 客户端连上来的那天爆炸
  • varint 的 64 位负数占 10 字节（sint64/zigzag 才是正解）
  • 忘 static_assert 冻结线上尺寸：一次"顺手加个字段"毁掉所有兼容承诺
  • 消息加长后老版本长度校验拒绝——长度字段语义（总长 vs payload 长）要写进协议文档

自测题

  1. 上面 Order 结构体 x86-64 默认对齐下 sizeof 是多少？画出 padding 分布。
  2. 为什么 long 不能进 wire format？给出它在两种主流平台上的宽度。
  3. protobuf 新增字段，旧客户端行为是什么？未知字段存哪了、何时有用？
  4. varint 编码 -1（int64）占几字节？sint64 呢？
  5. SBE 的"固定偏移"为什么能零拷贝解码？代价是什么？
参考答案

  1. sizeof(Order) = 24。x86-64（LP64）下的布局： offset 0-3 id (int32_t，对齐 4) offset 4-7 padding ← 为了让 price 满足 8 字节对齐，垫 4 字节 offset 8-15 price (int64_t，对齐 8) offset 16 side (char，1 字节) offset 17-23 padding ← 尾部填充 7 字节：结构体整体对齐 = 最宽成员 8， sizeof 必须是 8 的倍数 → 24 真正有用的只有 13 字节（4+8+1，即 kOrderWireSize），11 字节是 padding，而且 padding 的字节内容未初始化——直接 memcpy 发出去就等于把栈上的随机字节送上线路。这正是"结构体不能 memcpy 上线"的第一个理由（另三个：字节序、类型宽度、对齐访问）。

  2. 因为 long 的宽度不是跨平台固定的：Linux/macOS 的 LP64 下是 8 字节，Windows 的 LLP64（以及 32 位 Linux 的 ILP32）下是 4 字节。同一个 struct 在两端布局不同 → 字段错位、长度不符，历史数据也无法再解释。所以 wire format 只用定宽类型 int8_t/int16_t/int32_t/int64_t；同理 int（只保证 ≥16 位）、time_t、指针、bool（宽度与取值实现相关）都禁止上协议。

  3. 旧客户端解析时遇到不认识的 field number，会把它当作未知字段（unknown fields）原样保留在消息对象里（C++ 里可通过 UnknownFieldSet/unknown_fields() 访问）；程序读该字段拿到的是类型默认值（proto3 无字段存在性语义，除非声明 optional）。所以新增字段是安全的：老端跳过它，新端用默认值。未知字段的价值在于透传：老版本程序做代理/转发/落盘再回传时，重新序列化会把未知字段原样带出去，新版本加的数据不会在中间环节被吃掉。前提：field number 永不复用（删字段要写 reserved）。

  4. 普通 int64 编码 -1：负数按补码转成 uint64 是 0xFFFFFFFFFFFFFFFF，varint 每字节只装 7 位有效位 → 64/7 向上取整 = 10 字节（这是 int64 varint 的最大长度）。sint64 用 ZigZag 编码（-1 → 1，1 → 2，-2 → 3…），-1 映射成 1，只需 1 字节。所以有符号整数（尤其可能为负的价格差、净额）应声明 sint32/sint64，正负混合场景能省掉接近 9 字节/字段。

  5. 因为 SBE 每条消息的字段偏移在 schema 里编译期就固定：解码器（flyweight）只持有一个指向报文缓冲的指针，读字段就是 base + offset 再按需 bswap——不解析、不拷贝、不分配，接近零成本（纳秒级），也天然支持"只读关心的字段"。代价：① 不灵活，字段长度/顺序/增删都要改 schema 并做版本协商，两端必须同步升级；② 带宽略大，定长字段 + 固定头，无法像 varint 那样压缩小数字；③ 失去 protobuf 那种"未知字段自动保留"的自由演化能力；④ 变长数据（字符串、数组）要额外用固定长度或偏移表处理。所以结论是：管理面用 protobuf 的灵活性，热路径用定长二进制的确定性。

目标

非阻塞网络编程里 为什么要自建应用层缓冲区（而不是直接 read/write）；inputBuffer_ / outputBuffer_ 三个索引怎么动；readFd 为什么用 readv 配一个 64 KB 栈缓冲。

UNP 对照

  • UNP Ch3.9（readn/writen）、Ch16（非阻塞）——UNP 的 I/O 函数假定"阻塞读到底"，而 Reactor + 非阻塞要求一次事件读一批、粘由应用层处理
  • 本书 📖 陈硕《Linux 多线程服务端编程》第 7 章 Buffer 设计

概念详解

1. 为什么必须有应用层 buffer

非阻塞 I/O 下，单次 read 的字节数与"一条完整消息"没有任何关系：可能来半条、可能来 3.5 条。（参见 02 TCP 字节流）

因此每个 TCP 连接必须挂两块缓存：

缓存 谁写 谁读 作用
inputBuffer_ handleRead → readFd 业务 onMessage 回调 收半包/拆包；业务一次没取完不会丢
outputBuffer_ 业务 send() handleWrite 写不下去时（EAGAIN）暂存；不能直接丢给用户自己去等

muduo 的 outputBuffer_ 是"高水位回调"存在的前提：当堆积超过 highWaterMark（默认 64 MB）触发回调通知业务限速。

2. 三索引布局（源码：muduo/net/Buffer.h）

        prependable bytes |  readable bytes  |  writable bytes
 begin()          readerIndex_        writerIndex_         end()
                  (readPtr)           (writePtr)

实测到的源码常量与成员初始化（Buffer.h:45–51，已核对）：

static const size_t kCheapPrepend = 8;    // 8 字节头部预留
static const size_t kInitialSize  = 1024; // 初始可写 1024 字节
explicit Buffer(size_t initialSize = kInitialSize)
  : buffer_(kCheapPrepend + initialSize),   // 实际 vector 大小 = 8 + 1024
    readerIndex_(kCheapPrepend),
    writerIndex_(kCheapPrepend) {}
  • kCheapPrepend = 8 的意义：让序列化时可以"往前面补长度头"。先写 body，最后 prependInt32(header) 填长度，避免为了写长度必须先知道长度而多做一次拷贝。HFT 里这与"零拷贝组包"思路同源。
  • 用 std::vector<char> 而非裸 new char[]：自动扩容、自动释放，且 hasWritten() 只是一次整数加法。

3. readFd：readv + 64 KB 栈缓冲（源码：Buffer.cc:25–57，已核对）

ssize_t Buffer::readFd(int fd, int* savedErrno) {
  char extrabuf[65536];
  struct iovec vec[2];
  const size_t writable = writableBytes();
  vec[0].iov_base = begin() + writerIndex_;  vec[0].iov_len = writable;
  vec[1].iov_base = extrabuf;                vec[1].iov_len = sizeof extrabuf;
  const int iovcnt = (writable < sizeof extrabuf) ? 2 : 1;
  const ssize_t n = sockets::readv(fd, vec, iovcnt);
  if (n < 0)                        *savedErrno = errno;
  else if (implicit_cast<size_t>(n) <= writable)  writerIndex_ += n;
  else {                            // 溢出到 extrabuf，走 append 拷贝
    writerIndex_ = buffer_.size();
    append(extrabuf, n - writable);
  }
  return n;
}

这套设计的三个工程判断，面试最容易问：

  1. 为什么不先 ioctl(FIONREAD) 查有多少字节再读？ 源码注释写死了原因：saved an ioctl()/FIONREAD call —— 一次额外系统调用的成本，比"偶尔多用点内存"更贵。
  2. 为什么不笼统地"多给 Buffer 扩容"？ 缓冲区常见的稳态是小包、writableBytes() 足够；只有突发大流量才用得上 extrabuf。用 64 KB 栈空间兜突发，避免每次 read 都撑大 vector——这是"以栈换堆"的典型手法。
  3. 为什么要 readv 两跳而不是拷 extrabuf 两次？ 一次系统调用拿上限 ault writable + 65536 ≈ 128 KB-1（源码注释原话：when extrabuf is used, we read 128k-1 bytes at most），省掉第二轮 read 的系统调用。

4. makeSpace：原地整理，而不是每次 resize

Buffer.h:390–405 的逻辑：写空间不够时，先看"已读掉的部分 + 可写部分"够不够，够就把 readable 数据整体搬到 begin()+kCheapPrepend（std::copy），腾出尾部；实在不够才 resize。

手段 触发条件 代价
搬移（整理碎片） writable + prependable >= len + kCheapPrepend 一次 memmove/`std::copy`，无系统调用
resize 扩容 上式不成立 可能内存分配 + 拷贝，稳态下应避免

C++ 示例：30 行复刻核心语义

// mini_buffer.cpp — g++ -std=c++17 -O2 mini_buffer.cpp -o mini_buffer
#include <vector>
#include <cstring>
#include <algorithm>
#include <sys/uio.h>
#include <unistd.h>
#include <cstdio>

class Buffer {
public:
  static constexpr size_t kCheapPrepend = 8;
  static constexpr size_t kInitialSize  = 1024;

  explicit Buffer(size_t initial = kInitialSize)
    : buf_(kCheapPrepend + initial), r_(kCheapPrepend), w_(kCheapPrepend) {}

  size_t readableBytes()  const { return w_ - r_; }
  size_t writableBytes()  const { return buf_.size() - w_; }
  size_t prependableBytes() const { return r_; }
  const char* peek()      const { return begin() + r_; }

  void retrieve(size_t len) {                 // 业务消费掉 len 字节
    if (len < readableBytes()) r_ += len;
    else                       retrieveAll();
  }
  void retrieveAll() { r_ = w_ = kCheapPrepend; }

  void ensureWritableBytes(size_t len) {      // 对应 muduo 的 ensure+makeSpace
    if (writableBytes() < len) makeSpace(len);
    if (writableBytes() < len) buf_.resize(w_ + len);
  }
  void append(const char* d, size_t len) { ensureWritableBytes(len); std::memcpy(begin()+w_, d, len); w_ += len; }

  ssize_t readFd(int fd, int* savedErrno) {
    char extrabuf[65536];
    iovec vec[2];
    const size_t writable = writableBytes();
    vec[0].iov_base = begin() + w_;  vec[0].iov_len = writable;
    vec[1].iov_base = extrabuf;      vec[1].iov_len = sizeof extrabuf;
    const int iovcnt = (writable < sizeof extrabuf) ? 2 : 1;
    ssize_t n;
    do { n = ::readv(fd, vec, iovcnt); } while (n < 0 && errno == EINTR);
    if (n < 0) { *savedErrno = errno; return n; }
    if (static_cast<size_t>(n) <= writable)      w_ += n;
    else { w_ = buf_.size(); append(extrabuf, n - writable); }
    return n;
  }
private:
  char* begin() { return &*buf_.begin(); }
  const char* begin() const { return &*buf_.begin(); }
  void makeSpace(size_t len) {                // 整理碎片，尽量不扩容
    if (writableBytes() + prependableBytes() < len + kCheapPrepend) return;
    size_t readable = readableBytes();
    std::copy(begin() + r_, begin() + w_, begin() + kCheapPrepend);
    r_ = kCheapPrepend; w_ = r_ + readable;
  }
  std::vector<char> buf_; size_t r_, w_;
};

int main() {
  Buffer b;
  printf("初始: read=%zu write=%zu prepend=%zu\n",
         b.readableBytes(), b.writableBytes(), b.prependableBytes());
  char buf[2] = {0};
  int err = 0;
  ssize_t n = b.readFd(STDIN_FILENO, &err); n += !!buf[0];   // 从标准输入读一段
  printf("读入 %zd 字节, read=%zu write=%zu\n", n, b.readableBytes(), b.writableBytes());
  b.retrieveAll();
  printf("retrieveAll 后: read=%zu write=%zu prepend=%zu（回到初始布局）\n",
         b.readableBytes(), b.writableBytes(), b.prependableBytes());
}

内核视角

  • readv（readv(2)）是一次系统调用填多个用户缓冲，内核按 iovec 顺序拷贝；相比两次 read，省的不是拷贝量，而是系统调用进入/退出 + socket 锁获取的成本
  • 读取上限受 SO_RCVBUF 与接收队列实际数据量约束；一次读到 tonnes 128 KB-1 意味着突发流量下不会让内核缓冲堆积（堆积 → RTT 变大 → 延迟恶化）
  • UDP/组播侧不能用这套：边界 haz durability 天然保留，见 08 UDP/组播

坑点

  • retrieve 也可能永远剩一点点（半包），此时 makeSpace 会反复搬移 —— 长连接小包场景下建议 retrieveAll 与内在standing steady-state：缓冲最终会停在"读指针 = 写指针 = 8"的稳态，不再有搬移成本，这是 retrieveAll 复位的效果
  • readv 返回 (ssize_t)-1 且 errno == EINTR 必须重试；EAGAIN 则是"没数据了"，要区分
  • extrabuf 在栈上 64 KB：每个 readFd 调用一个。若在 deep recursion 或大量小栈线程上调用要小心（Reactor 单线程调用的场景没问题）
  • n > writable 分支里 writerIndex_ = buffer_.size() 后调 append：append 内部会再走一次 ensureWritableBytes，这是唯一可能触发 resize 的路径
  • 消费语义：peek*（只看）与 retrieve*（只推进读指针）必须分离——半包时不能撤回值，见 09 序列化
  • Buffer 不是线程安全的：它只被所属 EventLoop 那一个线程触碰；跨线程要用 11 的 runInLoop 排队，不能加锁了事

  4. makeSpace 为什么不直接 resize？什么条件下还是会走到 resize？
  5. outputBuffer_ 存在的必要性是什么？"直接业务调 write、写不下重试"会有什么问题？
参考答案
  1. readn 的语义是"阻塞地读满 n 字节才返回"。在 epoll + 非阻塞下，read 返回 EAGAIN 表示暂时没数据，若继续 readn 会① 空转烧 CPU；② 更糟的是消息长度本来就是变长的，你事先不知道 n。正确的是：有数据就读一批进 inputBuffer_，由应用层按协议判断消息边界，消费不完的数据留着等下一批凑整。
  2. ioctl(FIONREAD) 是一次额外系统调用。每秒几十万次 event 的场景，"省掉一次 syscall"比"偶尔多用 64 KB 栈"划算得多——源码注释就是 // saved an ioctl()/FIONREAD call to tell how much to read。同时多段 readv 让单次 syscall 的上限提高到 ~128 KB，突发时不用反复进出内核。
  3. 让序列化事后补长度头：可以先写 body，最后 prependInt32(totalLen) 把长度填到前面，省掉"必须先算长度再 memcpy 两遍"的开销（与之对比：没有 prepend 区就得临时缓冲或二次拷贝）。这跟 HFT 里"零拷贝组包"是一类思路。
  4. makeSpace 优先把 readable 数据搬到 kCheapPrepend 位置（std::copy），复用已读掉的空间，避免长大 vector 导致分配 + 拷贝 + 后续所有访问的地址变化。只有当"可写 + 可 prepend 空间 < 需要的长度 + 8"、即碎片整理也不够时才走 resize——这是稳态下不该发生的路径；如果它频繁发生，说明业务消费太慢或单条消息大于阈值。
  5. 非阻塞 write 可能部分写（只写出去一半）。没有 outputBuffer_ 就必须让业务自己持锁/注册 EPOLLOUT 等待，等于把 I/O 状态管理丢给用户；而且"写不下就重试"会① 立刻返回忙等烧 CPU；② 无法保证多条 send 的顺序；③ 无法统计堆积量 → 没有高水位限速。muduo 由框架统一处理：有剩余就 enableWriting()，写完立刻 disableWriting()（对应 07 的血泪坑：EPOLLOUT 常驻注册会导致事件风暴）。

· EventLoop：one loop per thread 与跨线程唤醒

目标

搞清楚 muduo 的线程模型为什么是 one loop per thread；别的线程怎么安全地给 IO 线程投递任务（runInLoop / queueInLoop）；为什么唤醒要用 eventfd 而不是条件变量。

UNP 对照

  • UNP Ch16（非阻塞 I/O）、Ch26（线程）——书里罗列了几种并发模型（每连接一进程/线程、单线程 + IO 复用、领导者 follower 等），muduo 采用的是并进一步收紧的：让"线程"和"事件循环"一对一绑定，而不是让多个线程争抢同一个循环
  • 本书 📖 陈硕《Linux 多线程服务端编程》第 2 章（线程模型图）、第 4 章（EventLoop）

概念详解

1. one loop per thread 的确切含义

不是"一个线程一个 epoll 实例"这么简单，而是三条硬约束：

约束 实现手段 违反后果
一个线程至多一个 EventLoop 线程局部指针 __thread EventLoop* t_loopInThisThread，构造时若已非空直接 LOG_FATAL 源码：EventLoop.cc:29、EventLoop.cc:78–86
一个 EventLoop 只跑在创建它的那个线程 threadId_ 构造时记下 CurrentThread::tid()；assertInLoopThread() 到处拦 未定义行为、数据竞争
要改动 Connection/Channel，必须回到它所属的 loop 线程去做 runInLoop / queueInLoop 投递，而不是加锁直接改 竞态、悬垂

这条约束的工程价值是去掉了绝大部分锁：因为一个连接的生命周期事件都在自己的线程里处理，业务流程可以"假装是单线程的"。这也是 muduo 与"锁到处都是"的传统服务器最大的区别。

2. 跨线程投递：runInLoop 与 queueInLoop（源码：EventLoop.cc:148–171，已核对）

void EventLoop::runInLoop(Functor cb) {
  if (isInLoopThread()) { cb(); }                 // 本线程：直接同步执行
  else                  { queueInLoop(std::move(cb)); }
}

void EventLoop::queueInLoop(Functor cb) {
  { MutexLockGuard lock(mutex_);
    pendingFunctors_.push_back(std::move(cb)); }
  // 两种情形才需要唤醒：① 跨线程投递；② 本线程正在跑 functors（防止新任务被漏掉）
  if (!isInLoopThread() || callingPendingFunctors_) { wakeup(); }
}

两个容易答错的细节：

  1. queueInLoop 即使在本线程调用也不一定白等：如果此刻正在 doPendingFunctors() 里跑任务（callingPendingFunctors_ == true），新加的任务这一轮不会被看到，所以要补一次 wakeup()。
  2. 锁保护的范围只有那个 vector：任务本身在锁外执行。见下。

3. doPendingFunctors：swap 换出再执行（源码：EventLoop.cc:254–269）

void EventLoop::doPendingFunctors() {
  std::vector<Functor> functors;
  callingPendingFunctors_ = true;
  { MutexLockGuard lock(mutex_);
    functors.swap(pendingFunctors_); }        // 锁只覆盖一次 swap
  for (const Functor& functor : functors) functor();   // 执行期间不持锁
  callingPendingFunctors_ = false;
}

这是教科书级的减小临界区手法：

  • 不这么做的话，执行 functor 期间一直持锁 → 别的线程投递全部阻塞；
  • 更隐蔽的问题是：functor 里再调 queueInLoop 会造成死锁（同一把 mutex_ 非递归）。swap 之后锁已释放，所以回调里再投递是安全的。

4. 为什么用 eventfd 唤醒，不用条件变量

源码：EventLoop.cc:33–42, 73–74, 87–90, 234–242

int createEventfd() { return ::eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC); }
// 构造函数里：
wakeupFd_(createEventfd()),
wakeupChannel_(new Channel(this, wakeupFd_)),
// ...
wakeupChannel_->setReadCallback(std::bind(&EventLoop::handleRead, this));
wakeupChannel_->enableReading();          // "we are always reading the wakeupfd"

void EventLoop::wakeup() {
  uint64_t one = 1;
  ssize_t n = sockets::write(wakeupFd_, &one, sizeof one);   // 写 8 字节
  if (n != sizeof one) LOG_ERROR << "... writes " << n << " bytes instead of 8";
}

理由（面试高频）：

方案 问题
条件变量 + bool flag loop 正阻塞在 epoll_wait 上等 IO，条件变量救不了它——epoll_wait 看不见 pthread 的条件。必须有一个 IO 事件才能打断 epoll_wait
pipe 需要两个 fd；eventfd 只要一个，语义恰好是"计数器"，内核开销更小
eventfd ✅ 既是 fd（可被 epoll 监听）又能当计数器，多次 wakeup 合并成一次 epoll_wait 返回，天然去重

顺手记：wakeupFd_ 读到的 8 字节数据 discard 掉即可（handleRead 只读不处理）；累积计数不会溢出到 0 除非读了 2^64 次。

5. 每个 loop 的一次完整循环（源码：EventLoop.cc:103–134）

while (!quit_) {
    activeChannels_.clear();
    pollReturnTime_ = poller_->poll(kPollTimeMs /*10000*/, &activeChannels_);
    ++iteration_;
    eventHandling_ = true;
    for (Channel* ch : activeChannels_) { currentActiveChannel_ = ch; ch->handleEvent(pollReturnTime_); }
    currentActiveChannel_ = NULL; eventHandling_ = false;
    doPendingFunctors();              // ★ IO 回调之后、下一轮 poll 之前执行
}

顺序很重要：先处理 IO 事件，再执行待跑任务。如果反过来，跨线程投递的任务会在 IO 之前插队，破坏"回调顺序 ≈ 事件顺序"的直观性。

6. 线程模型全景（本书 ch2）

                ┌── main EventLoop（Acceptor 所在）── accept 新连接 ──┐
                │                                                     ↓
                │                          round-robin 分发给 sub EventLoopThreadPool
                ↓                                                     │
TcpServer ─── baseLoop_                    SubReactor#0 ── EventLoop#0 ── N 个 TcpConnection
                                           SubReactor#1 ── EventLoop#1 ── N 个 TcpConnection
                                           ...（每个一个线程、一个 epoll）
  • 连接建立后归属固定，不会在 loop 之间漂移 → 连接内部无需锁
  • TcpServer::newConnection 里按 eventLoopThreadPool_->getNextLoop() 取下一个
  • 如果线程池大小为 0，所有连接都在 baseLoop_ 里跑（单线程模式，调试用）

C++ 示例：40 行复刻「loop + eventfd 唤醒 + pending functor」

// mini_loop.cpp — g++ -std=c++17 -O2 mini_loop.cpp -o mini_loop -lpthread
#include <sys/epoll.h>
#include <sys/eventfd.h>
#include <unistd.h>
#include <functional>
#include <mutex>
#include <thread>
#include <vector>
#include <cstdio>
#include <atomic>

class Loop {
public:
  Loop() {
    ep_ = epoll_create1(EPOLL_CLOEXEC);
    wfd_ = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
    epoll_event e{}; e.events = EPOLLIN; e.data.fd = wfd_;
    epoll_ctl(ep_, EPOLL_CTL_ADD, wfd_, &e);              // 常驻监听 wakeup fd
    tid_ = std::this_thread::get_id();
  }
  bool inLoopThread() const { return tid_ == std::this_thread::get_id(); }

  void runInLoop(std::function<void()> cb) {              // 对应 EventLoop::runInLoop
    if (inLoopThread()) cb(); else queueInLoop(std::move(cb));
  }
  void queueInLoop(std::function<void()> cb) {            // 对应 queueInLoop
    { std::lock_guard<std::mutex> g(mu_); pending_.push_back(std::move(cb)); }
    if (!inLoopThread() || doing_) wakeup();
  }
  void loop(int rounds) {
    std::vector<epoll_event> evs(16);
    for (int i = 0; i < rounds; ++i) {
      int n = epoll_wait(ep_, evs.data(), (int)evs.size(), 200);
      for (int k = 0; k < n; ++k)
        if (evs[k].data.fd == wfd_) { uint64_t one; ssize_t r = read(wfd_, &one, sizeof one); (void)r; }
      doPendingFunctors();
    }
  }
  size_t queueSize() { std::lock_guard<std::mutex> g(mu_); return pending_.size(); }
private:
  bool doing_ = false;
  void wakeup() { uint64_t one = 1; ssize_t n = write(wfd_, &one, sizeof one); (void)n; }
  void doPendingFunctors() {                              // swap 换出后再执行
    std::vector<std::function<void()>> fs;
    doing_ = true;
    { std::lock_guard<std::mutex> g(mu_); fs.swap(pending_); }
    for (auto& f : fs) f();
    doing_ = false;
  }
  int ep_, wfd_; std::thread::id tid_;
  std::mutex mu_; std::vector<std::function<void()>> pending_;
};

int main() {
  Loop* L = nullptr;
  std::thread io([&]{ Loop l; L = &l; l.loop(200); });
  while (!L) std::this_thread::yield();

  L->runInLoop([]{ printf("[IO线程] task A: 跨线程投递，第一次 runInLoop\n"); });
  std::this_thread::sleep_for(std::chrono::milliseconds(50));
  L->queueInLoop([]{ printf("[IO线程] task B: queueInLoop（即使同线程也排队）\n"); });
  printf("[main] 队列剩余=%zu（投递后立刻读，可能已被取走）\n", L->queueSize());
  std::this_thread::sleep_for(std::chrono::milliseconds(500));
  io.join();
}

内核视角

  • eventfd 内部是一个 64 位计数器：write 累加，read 返回当前值并清零（EFD_SEMAPHORE 才是每次减 1）；非阻塞下计数器为 0 时 read 返回 EAGAIN
  • 由于计数器存在，多次 wakeup 在没来得及 read 之前会合并，不会丢也不会排队成一堆事件
  • read(wakeupFd_) 发生在 loop 自己线程，且必定有数据（level-triggered，写了一直可读到清）
  • eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC)：CLOEXEC 防止 fork/exec 泄露 fd，NONBLOCK 防止极端情况下阻塞写
  • 关于延迟：跨线程投递 → eventfd write(~百 ns 级) → 唤醒 → epoll_wait 返回 → doPendingFunctors。这条路径就是 microseconds 级，HFT 里尽量把处理放在同一个线程，跨线程边界越少越好（见 HFT 关联）

坑点

  • quit() 不 wakeup 就退出不了：quit_ = true 后若 loop 正睡在 epoll_wait 上，要等到下一次事件才醒；源码 EventLoop.cc:136–146 专门处理"跨线程 quit 要 wakeup"
  • 别在 functor 里持 mutex_：doPendingFunctors 的 functors 已 swap 出锁外，但如果你在 functor 里再次 queueInLoop，注意 callingPendingFunctors_ 为真会补一次 wakeup（正常行为，不是重复 bug）
  • runInLoop 在本线程是同步执行：若回调很慢，会阻塞当次 loop 迭代 —— 长任务应丢给专门的线程池，而不是塞进 IO loop
  • 每个 EventLoop 都有 timerQueue_（源码构造函数可见），定时器回调同样在 loop 线程执行
  • SOCK_CLOEXEC / EFD_CLOEXEC 别忘了：多线程 + fork/exec 场景下 fd 泄露会导致"对端不知道连接已关"的经典事故

自测题

  1. one loop per thread 里的"三条硬约束"是什么，各自靠什么机制保证？
  2. runInLoop 在本线程被调用时是同步还是异步？这带来什么风险？
  3. 为什么需要一个 fd（eventfd）来唤醒，用条件变量不行吗？
  4. doPendingFunctors 为什么要用 swap 把任务换出来再执行？直接持锁执行会怎样？
  5. queueInLoop 里 if (!isInLoopThread() || callingPendingFunctors_) 后半保护的是什么场景？
参考答案
  1. ① 一个线程至多一个 EventLoop：靠 __thread EventLoop* t_loopInThisThread，构造时发现非空就 LOG_FATAL（EventLoop.cc:29/78）。② EventLoop 只在创建它的线程 loop：构造时记 threadId_，assertInLoopThread() 处处拦。③ 改动必须在所属 loop 线程做：靠 runInLoop/queueInLoop 投递而非加锁。三条共同的结果是"业务可以假装单线程"，从而消掉绝大部分锁。
  2. 同步执行（EventLoop.cc:148–153：if (isInLoopThread()) cb();）。风险：回调耗时长会阻塞本轮 loop 迭代，所有其它连接都要等它；且回调里若再 runInLoop 会递归同步调用。所以重活应丢线程池，别塞 IO loop。注意这与 queueInLoop 的语义差别——后者保证"排队到下一轮"。
  3. 条件变量救不了阻塞在 epoll_wait 上的线程：epoll_wait 等的是 IO 事件，不是 pthread 同步原语。必须有一个可被 epoll 监听的 fd 才能把它唤醒。选 eventfd 而非 pipe：只要一个 fd，且语义天然是"计数器"——多次 wakeup 合并成一次 epoll_wait 返回，不会浪费。
  4. ① 缩小临界区：把 O(n) 的任务执行移出锁外，别的线程投递不会被长时间阻塞；② 避免死锁：functor 里再调用 queueInLoop 时，若还持着 mutex_（非递归）必然死锁；③ swap 之后锁已释放，回调里再投递是安全的。
  5. 保护"本线程正在跑 functors 时又收到新任务"的场景。doPendingFunctors 执行期间 callingPendingFunctors_ == true，此时若本线程新 queueInLoop 一个任务，它进了 pendingFunctors_ 但这一轮的 swap 已经发生过了，这一轮看不见它。若不补一次 wakeup，该任务要等到下一次有 IO 事件才被处理。所以条件里必须有 || callingPendingFunctors_。

· TcpConnection 生命期：muduo 最容易被问崩的一段

目标

回答一个听起来简单、实则决定成败的问题：连接断开的瞬间，那个 shared_ptr<TcpConnection> 到底活到什么时候？ 以及 Channel::tie()、shared_from_this()、runInLoop 三件套是怎么协同防止"回调执行到一半对象没了"的。

UNP 对照

  • UNP Ch5–6（SIGPIPE、半关闭）、Ch11/Ch14——UNP 里连接关闭是 close(fd) 一句话的事；C++ 里要处理的是对象生命期与 fd 生命期的错配
  • 本书 📖 陈硕《Linux 多线程服务端编程》第 1 章（对象生命期）、第 8 章（TcpConnection）

概念详解

1. 为什么这件事必须用 shared_ptr，而且必须是 enable_shared_from_this

连接的死亡莫名其妙地难：它要被三样东西同时引用——

引用方 目的
TcpServer::connections_ 容器 管理保活、统计、遍历
Channel（挂在 epoll 上） 事件到来时要回调它，回调期间它必须活着
用户回调（onMessage 等） 用户可能把 conn 存起来异步发数据

裸指针、或者手写 intrusive 引用计数，都解决不了"某处偷偷延长生命期"的问题。muduo 的做法是统一 shared_ptr<const TcpConnection>（TcpConnectionPtr），并在类内部需要"延长自己"的地方调 shared_from_this()——所以 TcpConnection 必须继承 enable_shared_from_this<TcpConnection>。

源码里 shared_from_this() 出现在这里：connectEstablished、connectDestroyed、handleRead/handleWrite 的回调、forceClose 等（详见地图表）。

2. 状态机（muduo/net/TcpConnection.h）

kConnecting --connectEstablished--> kConnected --shutdown--> kDisconnecting
     |                                  |                          |
     +--------------- handleClose ------+--------------------------+--> kDisconnected

handleClose 的入口 assert（TcpConnection.cc:412）：state_ == kConnected || state_ == kDisconnecting——即"连接建立过"才能走关闭流程，重复关闭会被 assert 抓到。

3. 建立：connectEstablished（源码：TcpConnection.cc:323–332，已核对）

void TcpConnection::connectEstablished() {
  loop_->assertInLoopThread();
  assert(state_ == kConnecting);
  setState(kConnected);
  channel_->tie(shared_from_this());     // ★ 关键一行
  channel_->enableReading();
  connectionCallback_(shared_from_this());
}

channel_->tie(shared_from_this()) 干了什么？看 Channel.cc:47–51, 66–81：

void Channel::tie(const std::shared_ptr<void>& obj) { tie_ = obj; tied_ = true; }

void Channel::handleEvent(Timestamp receiveTime) {
  std::shared_ptr<void> guard;
  if (tied_) {
    guard = tie_.lock();                 // weak_ptr::lock —— 升级为 shared_ptr
    if (guard) handleEventWithGuard(receiveTime);   // 还活着才调回调
  } else {
    handleEventWithGuard(receiveTime);
  }
}

tie_ 是 weak_ptr<void>：不改变所有权，只是"必要时把对象捞住"。事件到达时 lock()：

  • 捞得到 → 回调期间 guard 持 strongly reference，对象安全；回调结束后 guard 析构，引用计数归零则对象析构；
  • 捞不到（lock() 返回空）→ 说明对象已经在别处被销毁了，直接跳过回调，避免 use-after-free。

这就是 C++ 网络编程里"回调期间保活"的标准解法。注意 tie_ 存成 shared_ptr<void> 是为了抹掉类型——Channel 不需要知道 TcpConnection 是什么，避免头文件依赖与循环依赖。

4. 关闭：handleClose（源码：TcpConnection.cc:408–421，已核对）

void TcpConnection::handleClose() {
  loop_->assertInLoopThread();
  // we don't close fd, leave it to dtor, so we can find leaks easily.
  setState(kDisconnected);
  channel_->disableAll();

  TcpConnectionPtr guardThis(shared_from_this());   // ★ 保命
  connectionCallback_(guardThis);
  // must be the last line
  closeCallback_(guardThis);
}

三处注释都是考点：

  1. 为什么不在这里 close(fd)？ 源码注释：leave it to dtor, so we can find leaks easily——把 close 交给 Socket 的析构（RAII），这样凡是没被正确销毁的连接一定会留下 fd，用 lsof / /proc/<pid>/fd 一眼看到泄漏。
  2. 为什么需要 guardThis？因为 closeCallback_ 会让 TcpServer 从 connections_ 里 erase，那里可能是最后一个共享引用——如果不先用局部 guardThis 抓住自己，this 在回调返回后就悬垂了。
  3. 为什么 closeCallback_ 必须是最后一行？它之后不再触碰任何成员。TcpConnectionPtr guardThis 也是函数里最后析构的对象之一（局部变量逆序析构）。

5. 收尾：connectDestroyed 与 TcpServer 的销毁（源码已核对）

void TcpConnection::connectDestroyed() {              // TcpConnection.cc:334-345
  loop_->assertInLoopThread();
  if (state_ == kConnected) {
    setState(kDisconnected);
    channel_->disableAll();
    connectionCallback_(shared_from_this());
  }
  channel_->remove();                                 // 从 epoll 注销
}

void TcpServer::removeConnection(const TcpConnectionPtr& conn) {   // TcpServer.cc:100
  loop_->runInLoop(std::bind(&TcpServer::removeConnectionInLoop, this, conn));
}
// 注意 bind 里带着 conn（shared_ptr 拷贝），保证 removeConnectionInLoop 执行时对象仍存活

TcpServer::~TcpServer() {                             // TcpServer.cc:39-51
  loop_->assertInLoopThread();
  for (auto& item : connections_) {
    TcpConnectionPtr conn(item.second);               // 先抓一份
    item.second.reset();                              // 从容器摘掉
    conn->getLoop()->runInLoop(
        std::bind(&TcpConnection::connectDestroyed, conn));  // 送回它自己的线程销毁
  }
}

最后这段是"跨线程销毁"的范式：连接属于别的 IO 线程，绝不能在 TcpServer 所在线程直接析构（否则会出现"别的线程正在回调、这边已经析构"），要把所有权打包成 shared_ptr 送回它自己的 loop 线程再处理。

6. 一句话总结这条链路

对端 FIN / RST
  →  fd 可读 → epoll_wait 返回 → Channel::handleEvent
  →  tie_.lock() 成功（guard 出场）→ TcpConnection::handleRead
  →  inputBuffer_.readFd() 返回 0 → handleClose()
  →  TcpConnectionPtr guardThis(shared_from_this())  ← 保命
  →  closeCallback_ → TcpServer::removeConnection
  →  loop_->runInLoop(removeConnectionInLoop(conn))  ← 再保一次
  →  connections_.erase(conn) → 最后一个 shared_ptr 消失
  →  ~TcpConnection → ~Socket → close(fd)

C++ 示例：手写一遍 tie/lock 保活

// tie_guard.cpp — g++ -std=c++17 -O2 tie_guard.cpp -o tie_guard
#include <memory>
#include <cstdio>
#include <functional>

// ---- 模拟 muduo::net::Channel ----
class Channel {
public:
  void tie(const std::shared_ptr<void>& obj) { tie_ = obj; tied_ = true; }
  void handleEvent() {
    std::shared_ptr<void> guard;
    if (tied_) {
      guard = tie_.lock();               // 升级：活着才回调
      if (!guard) { printf("  [Channel] 对象已死，跳过回调（避免 UAF）\n"); return; }
    }
    cb_();                               // guard 的作用域覆盖整个回调
  }
  std::function<void()> cb_;
private:
  std::weak_ptr<void> tie_; bool tied_ = false;
};

// ---- 模拟 TcpConnection ----
struct Conn : std::enable_shared_from_this<Conn> {
  Channel ch;
  int id;
  explicit Conn(int i) : id(i) {}
  void establish() {
    auto self = shared_from_this();
    ch.tie(self);                        // weak_ptr，不影响所有权
    ch.cb_ = [self] { printf("  [Conn %d] 回调执行中，self.use_count=%ld\n",
                             self->id, self.use_count()); };
  }
};

int main() {
  auto c = std::make_shared<Conn>(1);
  c->establish();
  printf("tie 之后 use_count=%ld（tie 用 weak_ptr，不增加计数）\n", c.use_count());

  printf("正常回调：\n"); c->ch.handleEvent();

  c.reset();                              // 唯一强引用释放 → 对象析构
  printf("析构后再触发事件（模拟迟到的 epoll 事件）：\n");
  // 注意：真实代码里 Channel 也随之销毁，这里仅为演示 lock() 失败分支
  Conn* leaked = new Conn(2);
  leaked->establish();
  leaked->ch.handleEvent();
  delete leaked;
}

内核视角

  • 不主动 close(fd) 不等于不关：Socket 对象是 RAII 的，析构里会 sockets::close(sockfd_)。所以"fd 泄漏 = 对象没析构"，数 /proc/<pid>/fd 就能直接验证
  • channel_->remove() 必须在对象析构前完成：先 EPOLL_CTL_DEL 再从 epoll 注销，否则 epoll 里残留一个指向已释放对象的 Channel*（见 07 的 fd 复用坑）
  • RST 与 FIN 的差异在本层不可见——read 都返回差别：FIN → read 返回 0；RST → read 返回 -1 且 ECONNRESET（走 handleError 而不是 handleClose）

坑点

  • enable_shared_from_this 的调用时机：构造期间对象还没被 shared_ptr 接管，此时调 shared_from_this() 会抛 bad_weak_ptr。muduo 把 tie 放在 connectEstablished（已被 shared_ptr 管理之后）而不是构造函数里
  • tie 之后回调里千万别再 tie 自己形成循环引用：tie_ 是 weak_ptr，正是为了这条
  • handleClose 之后不要再触碰任何成员：源码注释 must be the last line 就是警告
  • 跨线程析构：不要在 A 线程里直接 delete/释放属于 B 线程 loop 的连接，用 runInLoop 送回去（TcpServer::~TcpServer 的写法）
  • 用户回调（onMessage）里若异步保存了 shared_ptr 并发队列逻辑，请务必同时保存 shared_ptr 而不是裸 this——这是 muduo 用户代码最常见的 UAF

自测题

  1. Channel::tie() 存的为什么是 weak_ptr<void> 而不是 shared_ptr<TcpConnection>？
  2. 事件到达时 tie_.lock() 失败（返回空）意味着什么？此时 muduo 怎么处理？
  3. handleClose 里为什么要 TcpConnectionPtr guardThis(shared_from_this())？去掉会怎样？
  4. 为什么源码特意不在 handleClose 里 close(fd)？
  5. 为什么 TcpServer::~TcpServer 不直接销毁连接，而要 runInLoop 丢给各连接自己的 loop？
  6. enable_shared_from_this 在构造函数里调用会发生什么？
参考答案
  1. 两个原因：其一，所有权语义——Channel 不应该拥有 TcpConnection（拥有者是 TcpServer::connections_ 以及用户），若存 shared_ptr 就形成引用计数环路（Channel 属于 Conn，Conn 指向 Channel），永远析构不掉；weak_ptr 不增加引用计数。其二，解耦——weak_ptr<void> 擦掉了类型，Channel 无需 include TcpConnection.h，避免头文件循环依赖。
  2. lock() 返回空意味着对象已经在其它路径被销毁（引用计数已经归零），而这是一个迟到的、陈旧的事件。muduo 直接跳过回调（Channel.cc:66–81 里 if (guard) 才执行），从而避免了 use-after-free。典型触发场景：fd 被 close 后又被 dup/fork 保留引用导致通知照发，见 07 的坑点。
  3. closeCallback_ 会被 TcpServer::removeConnection → removeConnectionInLoop 处理，而它可能持有这个连接的最后一个 shared_ptr。如果不用局部 guardThis 先抓住自己，那么回调返回的瞬间 this 就被析构，后续任何成员访问（含析构函数里）都是 UAF。所以：保命 → 通知用户 → closeCallback_ 必须是最后一行。
  4. 源码注释原话：we don't close fd, leave it to dtor, so we can find leaks easily。把 fd 的关闭放进 Socket 的析构（RAII），那么任何没被正确销毁的连接一定会留下一个 fd。泄漏检测从"看代码"变成"数 /proc/<pid>/fd"，这在长跑的服务器上是巨大的可观测性收益。
  5. 因为连接属于另一个 IO 线程的 loop，在那个线程可能正在执行它的回调（或者 epoll 里还挂着它的 Channel）。在 TcpServer 所在线程直接销毁会造成跨线程析构的数据竞争。正确做法（TcpServer.cc:39–51）：TcpConnectionPtr conn(item.second) 抓一份所有权 → item.second.reset() 从容器摘掉 → conn->getLoop()->runInLoop(bind(connectDestroyed, conn))，把析构动作连同 shared_ptr 一起送回它自己的线程执行。
  6. 抛 std::bad_weak_ptr 异常（C++17 起）或未定义行为。因为此时对象还没有被任何 shared_ptr 管理，内部的 weak_this 是空的。所以只能在"已被 shared_ptr 接管之后"（如 connectEstablished）调用 shared_from_this()，这也是 muduo 把 tie 放到 connectEstablished 而不是构造函数里的原因。

目标

理解 muduo 日志系统为什么异步、为什么需要四个 buffer、以及"日志打不出来"和"日志把进程拖垮"这两种失败如何被同时避免。

概念详解

1. 为什么业务线程不能直接 fprintf

做法 问题
业务线程直接写文件 write 是系统调用，可能因为磁盘抖动阻塞毫秒级——比网络往返还慢，直接污染延迟分布
每次加互斥锁写 多线程串行化到一次 syscall 上，吞吐崩
O_APPEND 慷慨拼内存 缓冲后再写则需要额外的buffer管理

muduo 的解法：业务线程只做内存追加（append），由一个专门的后台线程负责写盘。业务线程遭遇的最坏情况只是"一次 memcpy + 一次可能的 notify"。

2. 四个 buffer（源码：AsyncLogging.cc:25–31，已核对）

AsyncLogging::AsyncLogging(...)
  : ..., currentBuffer_(new Buffer), nextBuffer_(new Buffer), buffers_() {
  currentBuffer_->bzero();  nextBuffer_->bzero();
  buffers_.reserve(16);
}
角色 位置 作用
currentBuffer_ 前台 业务线程正在往里 append
nextBuffer_ 前台备胎 currentBuffer_ 满了立刻顶上，避免临时 new
buffers_（vector） 前后台交接 攒着装满的 buffer，后台线程来取
newBuffer1 / newBuffer2 后台持有 后台线程自己准备的两个空 buffer，用来"回填"前台

newBuffer1/2 定义在 threadFunc 内部（AsyncLogging.cc:63–65）：把新 buffer 的准备放在后台线程，前台在切换时就不需要 new（也即不需要承担内存分配的不确定性）。

3. 前台路径：append（源码：AsyncLogging.cc:34–56，已核对）

void AsyncLogging::append(const char* logline, int len) {
  muduo::MutexLockGuard lock(mutex_);
  if (currentBuffer_->avail() > len) {
    currentBuffer_->append(logline, len);          // 快路径：纯 memcpy
  } else {                                          // 慢路径：换 buffer
    buffers_.push_back(std::move(currentBuffer_));  // 满的排进队列
    if (nextBuffer_) currentBuffer_ = std::move(nextBuffer_);
    else             currentBuffer_.reset(new Buffer);   // Rarely happens
    currentBuffer_->append(logline, len);
    cond_.notify();
  }
}
  • 默认 kLargeBuffer = 4 MB（AsyncLogging.h），所以正常情况下十几次 append 才触发一次换 buffer
  • Rarely happens 那一行是亲手痕：后台线程来不及补 nextBuffer_ 才走 new。 这正是为什么要有 newBuffer1/2 这套机制——把罕见情形兜住，而不是让它成为常态
  • 注意：只有慢路径才 notify()，快路径不打扰后台线程

4. 后台路径：threadFunc（源码：AsyncLogging.cc:58–135，已核对）

后台线程一轮循环做的事：

{

三个设计点：

  1. swap 而不是逐个 pop：临界区压缩到 O(1)，和 11 doPendingFunctors 是完全同一个套路
  2. 除了"写满"还有定时兜底：即使没满，waitForSeconds(flushInterval_)（默认 3 秒）也会把 currentBuffer_ 收走，保证日志的实时性
  3. 主动丢弃策略：单次超过 25 个 buffer（≈100 MB）就丢弃中间部分并打 Dropped log messages at ... larger buffers 到 stderr——宁可丢日志也不让进程被磁盘拖死。这是服务端系统里很关键的价值判断

C++ 示例：最小双缓冲异步日志骨架

// mini_asynclog.cpp — g++ -std=c++17 -O2 mini_asynclog.cpp -o mini_asynclog -lpthread
#include <vector>
#include <memory>
#include <mutex>
#include <condition_variable>
#include <thread>
#include <chrono>
#include <cstdio>
#include <cstring>
#include <atomic>

using Buffer = std::vector<char>;
using BufferPtr = std::unique_ptr<Buffer>;

class AsyncLog {
public:
  AsyncLog(size_t cap = 1024)
    : cap_(cap),
      cur_(new Buffer()), next_(new Buffer()),
      bg_([this]{ threadFunc(); }) {
    cur_->reserve(cap_); next_->reserve(cap_);
    full_.reserve(16);
  }
  ~AsyncLog() { quit_ = true; cv_.notify_all(); bg_.join(); }

  void append(const char* line, size_t len) {          // 前台：只做 memcpy
    std::unique_lock<std::mutex> lk(mu_);
    if (cur_->size() + len <= cap_) {
      cur_->insert(cur_->end(), line, line + len);      // 快路径
      return;
    }
    full_.push_back(std::move(cur_));                   // 慢路径：换 buffer
    if (next_) { cur_ = std::move(next_); cur_->clear(); }
    else       { cur_.reset(new Buffer()); cur_->reserve(cap_); }
    cur_->insert(cur_->end(), line, line + len);
    lk.unlock();
    cv_.notify_one();
  }
private:
  void threadFunc() {
    BufferPtr b1(new Buffer()), b2(new Buffer());        // 后台自备两个空 buffer
    b1->reserve(cap_); b2->reserve(cap_);
    std::vector<BufferPtr> toWrite; toWrite.reserve(16);
    while (!quit_) {
      {
        std::unique_lock<std::mutex> lk(mu_);
        cv_.wait_for(lk, std::chrono::seconds(3));
        if (cur_ && !cur_->empty()) { full_.push_back(std::move(cur_)); }
        if (b1) { cur_ = std::move(b1); cur_->clear(); }
        toWrite.swap(full_);                             // O(1) 拿走全部
        if (!next_ && b2) { next_ = std::move(b2); next_->clear(); b2.reset(new Buffer()); b2->reserve(cap_); }
      }                                                  // 锁到此释放，写盘不持锁
      for (const auto& b : toWrite) fwrite(b->data(), 1, b->size(), stdout);
      fflush(stdout);
      // 回收两个用于下次回填（简化：直接留着）
      if (!b1 && !toWrite.empty()) { b1 = std::move(toWrite.back()); toWrite.pop_back(); b1->clear(); }
      if (!b2 && !toWrite.empty()) { b2 = std::move(toWrite.back()); toWrite.pop_back(); b2->clear(); }
      toWrite.clear();
    }
  }
  size_t cap_;
  BufferPtr cur_, next_;
  std::vector<BufferPtr> full_;
  std::mutex mu_; std::condition_variable cv_;
  std::atomic<bool> quit_{false};
  std::thread bg_;
};

int main() {
  AsyncLog log(256);
  for (int i = 0; i < 500; ++i) {
    char b[64];
    int n = snprintf(b, sizeof b, "log line %05d %s\n", i, std::string(40, '.').c_str());
    log.append(b, n);
  }
  std::this_thread::sleep_for(std::chrono::seconds(4));  // 等后台 flush
}

坑点

  • 进程异常退出会丢最后一批日志：没来得及 flush 的 buffer 在内存里。重要场景要显式清理或用更高可靠性的方案
  • 别把前后台之间的 vector 遍历放进锁：swap 是关键；一旦在锁里遍历 + 写盘，前台 append 会被卡住
  • nextBuffer_ 为空时的 new Buffer 分支（Rarely happens）：如果它真的频繁发生，说明后台线程被磁盘拖慢，要检查落盘目标（NFS/慢盘会直接暴露）
  • 日志内容自身的线程安全：LogStream 是每个业务线程自己的栈对象，跨线程不宜共享同一个 stream
  • 丢弃日志的分支会擦除 buffersToWrite 中除前 2 个以外的所有 buffer（源码：erase(begin()+2, end())），这是有意的取舍

自测题

  1. 为什么要 nextBuffer_ 和后台的 newBuffer1/2 一共 4 个 buffer，两个不够吗？
  2. 后台线程为什么要 swap 而不是逐个拷贝 buffer？
  3. 日志堆积过多时 muduo 会怎么做？为什么这么设计？
  4. 为什么 LogFile 那边传 threadSafe = false？
  5. 程序 crash 时，最后一批日志会怎样？异步日志的可靠性边界是什么？
  6. flushInterval_（默认 3 秒）解决什么问题？
参考答案
  1. 两个不够，因为要让前台永远不需要临时 new。currentBuffer_ 满了时，立刻用 nextBuffer_ 顶上（移动语义，O(1)）；后台线程还回来时也一次补两个（newBuffer1/2）。只有"后台线程也来不及补"的罕见情况才走到 new Buffer（源码注释 Rarely happens）。这套设计把内存分配从前台的高频路径上彻底挪走了——否则日志本身会带来 cmalloc 抖动。
  2. swap 是 O(1) 指针交换，能把临界区压到最短；逐个拷贝/逐个 pop 要么贵、要么在锁里做多步操作。这样所有写盘动作都在锁外执行，前台线程几乎不受后台磁盘抖动的影响。（与 11 doPendingFunctors 的手法完全一致。）
  3. 单次超过 25 个待写 buffer（约 100 MB）时，丢弃 buffersToWrite 中除前 2 个以外的所有内容，并往 stderr 和日志文件打一条 Dropped log messages at ... larger buffers 警告。这是明确的价值取舍：宁可丢日志，也不让进程因为磁盘跟不上而被拖死——服务端系统的可用性优先于日志完整性。
  4. 因为写文件的只有 AsyncLogging 的这一个后台线程，LogFile 自身再加锁纯属浪费（AsyncLogging.cc:62 构造时传的就是 false），走 append_unlocked 不加锁路径。
  5. 会丢。留在 currentBuffer_ / buffers_ 里还没落盘的内容随进程一起消失。边界是：操作系统不崩，fflush 之后数据已在内核 page cache，通常不丢；进程自己崩掉，则可能丢最近几秒。所以需要高可靠审计的场景不能只靠它（要追加 fsync 或独立日志进程）。
  6. 解决"日志量太小导致实时性差"的问题：如果只有满了才写，低流量时段可能几分钟看不到一条日志（排查时极其难受）。waitForSeconds(flushInterval_) 到期后收走未写满的 currentBuffer_，保证最多 3 秒延迟。
