1.1 起源：1993 年的 BSD Packet Filter 论文

本节讲什么：eBPF 的"前身" cBPF 为什么诞生、它解决的性能问题是什么、以及为什么说 BPF 从第一天起就不只是"抓包工具"。

1. 问题背景：内核抓包为什么慢

1990 年代初，抓包工具（如 tcpdump 的前身）是这样工作的：网卡每收到一个包，内核把整个包完整拷贝一份给用户态的过滤进程，过滤进程再决定要不要。

问题：过滤逻辑跑在用户态，但过滤所需的数据在内核里——每个包都要白白经历一次"内核→用户态"拷贝 + 上下文切换，哪怕最后 99% 的包都被丢弃。当你只想抓 SSH 流量而网卡灌进来全机房流量时，这个开销是灾难性的。

两次拷贝问题图示：

   网卡 ──包──▶ 内核协议栈 ──完整包拷贝──▶ 用户态过滤进程
                                        （在这里才判断"要不要"）
                    ▲
                    └── 丢弃的包也付了全额拷贝成本

2. 论文的答案：把过滤程序搬进内核

McCanne & Van Jacobson（劳伦斯伯克利实验室，1993）提出：与其把数据搬到过滤器，不如把过滤器编译成字节码，塞进内核执行。内核里跑一个小"伪机器"（pseudo-machine）——一套 32 位寄存器虚拟机，解释执行（当时还没有 JIT）过滤器指令。

   网卡 ──包──▶ [内核: BPF 伪机器执行过滤器]
                      │
              包在此就地判决 ──只有"要"的包──▶ 拷贝给用户态
                      └──"不要"的包零拷贝成本丢弃

这就是 BPF 名字的由来：BSD Packet Filter。性能上还赢了一个隐性优势：BPF 论文的设计（两个寄存器 + 无间接寻址）比同时代对手（CSPF）的树遍历结构更容易映射成高效机器码，实测快 20 倍左右。

3. 论文里的示例程序

BPF 过滤器是一门"类汇编"指令集，比如"只要 IP 包"：

ldh     [12]                       # 从包偏移 12 处加载 2 字节（以太网帧的 ethertype 字段）
jeq     #ETHERTYPE_IP, L1, L2      # 是 IP 包则跳 L1，否则跳 L2
L1:     ret     #TRUE              # 非零返回值 = 接收该包（上送用户态）
L2:     ret     #0                 # 0 = 丢弃

逐行解读（你写过 ARM 汇编，这个结构应该很眼熟）：

指令 做什么 对应你熟悉的 ARM 概念
ldh [12] 从内存地址加载数据到寄存器（load half-word，2 字节） ldrh r0, [r1, #12]
jeq #imm, L1, L2 比较相等则跳 L1，否则跳 L2 cmp + b.eq / b.ne
ret #N 返回，N 就是判决结果 mov r0, #N + bx lr

两个细节值得注意：

  • 偏移 12：以太网帧头 = 6 字节目的 MAC + 6 字节源 MAC，第 13 字节起是 2 字节 ethertype——过滤器和数据结构布局强耦合。这个主题 30 年后换个面目再次出现：CO-RE 就是为了解决"内核数据结构布局变了，我的程序怎么办"（第 5 章）
  • 今天 tcpdump -d 仍能看到这套指令：tcpdump -d 'ip' 输出的就是 cBPF 字节码——你没有必要手写它，libpcap 替你把过滤表达式编译出来

4. 深远意义

从第一天起，BPF 的核心思想就是"作者写自定义程序在内核里执行"——"包过滤"只是它的第一个应用场景。指令集 + 内核执行环境这两个要素 1993 年就齐了，后面 30 年的演进（64 位重写、maps、验证器、更多挂钩点）只是给这台机器不断"加装备"。理解了这一点，后面所有历史都顺理成章。

衔接：下一节看这台"伪机器"如何一步步长成今天 64 位的 eBPF——时间线上只有 5 个节点值得记。

1.2 演进时间线（记住这几个节点）

本节讲什么：从 1993 到 2020 的关键节点。不用背年份，要背的是每个节点给 BPF 加了什么新能力——能力叠加的顺序本身就是理解 eBPF 的钥匙。

1. 完整时间线

年份 内核 事件 加了什么能力
1993 — BPF 论文（伪机器 + 指令集） 内核里跑自定义字节码（仅包过滤场景）
1997 2.1.75 BPF 进入 Linux，用于 tcpdump 高效抓包 Linux 获得内核态包过滤
2012 3.5 seccomp-bpf：BPF 程序决定是否允许用户态系统调用 BPF 第一次跳出"包过滤"——判决对象从"包"变成"syscall"
2014 3.18 eBPF：指令集为 64 位重写、引入 maps、bpf() 系统调用、helper 函数、验证器。官方生日 2014-09-26（验证器+bpf syscall+maps 补丁集被接受） 现代形态确立（下表展开）
2015 — eBPF 可挂 kprobes，追踪革命起点；网络栈开始加 hook 观测任何内核函数入口/返回
2016 — eBPF 工具进生产（Netflix/Brendan Gregg "superpowers"）；Cilium 发布（容器环境整条 datapath 换 eBPF） 工业界背书
2017 — Facebook 开源 Katran（L4 负载均衡）；此后 facebook.com 每个包都过 eBPF/XDP 超大规模生产验证
2018 — eBPF 成为内核独立子系统（维护者 Borkmann/Starovoitov，后加 Nakryiko）；BTF 引入（可移植性） 跨内核版本可移植的地基
2020 — LSM BPF：第三大用例（安全）确立 安全策略可编程

2. 2014 的 eBPF 改造：五大件分别解决什么

2014 那次重写是"从量变到质变"，五件套缺一不可：

新增 解决的问题 没有它会怎样
64 位指令集 + 11 个寄存器 32 位伪机器算不了 64 位指针/时间戳 无法处理现代内核数据结构（指针全是 64 位）
maps（内核键值存储） 程序没有地方存状态、没法和用户态交换数据 只能 trace_printk 打印字符串，做不了任何"工具"
bpf() 系统调用 提供统一的加载/操作界面 用户态没有正规入口管理 BPF 对象
helper 函数白名单 让程序有限地访问内核功能（读内存、拿 pid…） 要么完全盲区、要么直接放开（等于内核模块）
验证器 加载前证明程序安全（不崩、不死循环、不越界） 内核不敢让任意人跑任意代码——这是 eBPF 和 LKM 的分水岭

记忆口诀：寄存器变宽（能算）、maps（能存）、syscall（能加载）、helper（能访问）、verifier（敢让你跑）。

3. 三大用例的形成

时间线读到最后，三条主线浮出水面：

        观测追踪 (tracing)          网络 (networking)         安全 (security)
  2014 ─ bpf syscall/verifier     2015 ─ 网络栈 hook        2012 ─ seccomp-bpf
  2015 ─ kprobes                  2017 ─ XDP/Katran         2020 ─ LSM BPF
  2016 ─ Gregg 工具集              (facebook 全量流量)       (策略可编程)

本书主线是第一条（观测），第 8 章讲网络，第 9 章讲安全。

4. 规模限制的演进

指令数上限从 4096 → 100 万条已验证指令（5.2 起）；尾调用（第 2 章）和 BPF-to-BPF 调用让单程序限制实际失效——组合起来理论上可以写任意复杂的逻辑。

衔接：历史里"eBPF"这个词从哪来、现在该怎么叫？下一节一分钟讲清。

1.3 eBPF 与 BPF 的称呼

本节讲什么：一个常见的困惑——资料里一会儿写 BPF 一会儿写 eBPF，是不是两个东西？结论先行：现代语境下是同一个东西，但用词场合有惯例。

1. 两个词的来历

  • BPF：1993 年的原名（BSD Packet Filter），32 位"伪机器"时代的叫法。今天为了区分，常称 classic BPF（cBPF）
  • eBPF：2014 年 64 位重写后的叫法，e = extended。内核之外的社区（ebpf.io、eBPF 基金会、O'Reilly 书名）用它强调"不只是包过滤了"

2. 现状：谁用哪个词

场合 用词 例子
内核源码、内核邮件列表 统一 BPF bpf() 系统调用、bpf_get_current_pid_tgid() 等 helper、BPF_PROG_TYPE_* 程序类型——内核里根本没有 "eBPF" 这个词
工具链（libbpf/bpftool/clang） 统一 BPF clang -target bpf、bpftool prog load
内核外社区、营销、书名 流行 eBPF ebpf.io、eBPF Summit、本书《Learning eBPF》
bpftrace 等高层工具 混用 无所谓

3. 为什么内核社区坚持不加 "e"

内核维护者的立场：cBPF 在内核里已经被完全翻译成 eBPF 再执行（cBPF 程序加载时先被转换），也就是说内核里只有一种 BPF——即 2014 年后的那套。旧名没有独立存在的意义，所以"extended"前缀多余。

实用结论： - 读内核文档/写 C 代码：心里按 BPF 理解，别找 ebpf_xxx 符号（不存在） - 读博客/书：见到 eBPF 直接当 BPF 即可 - 写搜索关键词：两个都试（如 bpf ring buffer / ebpf ring buffer）

衔接：术语清了，下一节回到地基问题——为什么"在内核里执行"这件事价值巨大？先看用户态/内核态的边界长什么样。

1.4 内核与用户空间（底层视角）

本节讲什么：为什么"能在内核里挂代码"约等于"能看穿一切应用"。这一节是你 TLPI 学习的复习——用户态/内核态边界，但从 eBPF 视角再看一遍。

1. 边界模型（TLPI 第 1 章的复习）

┌─────────────────────────────── 用户态（非特权）─────────────────────┐
│  应用 A      应用 B      应用 C   …                                │
│    │           │           │                                       │
│    └─────┬─────┴─────┬─────┘                                       │
│          │  syscall 接口（唯一的合法通道）                            │
└──────────┼─────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────── 内核态（特权）────────────────────────┐
│  文件系统 │ 网络协议栈 │ 内存管理 │ 调度器(CFS) │ 驱动 │ …            │
│  ↑↑↑↑↑↑↑↑ 这里发生的事，用户态只能通过 syscall 结果间接感知 ↑↑↑↑↑↑↑↑ │
└──────────────────────────────────────────────────────────────────────┘

应用要做任何"外部世界"的事（开文件、发包、分配内存、起进程），都必须陷入内核。这条边界对你的意义在 TLPI 已经建立；eBPF 补上的是最后一块拼图：

TLPI 视角： syscall 是用户态请求内核干活的协议（学的是"怎么用"）。 eBPF 视角： syscall 边界是插桩的黄金位置——所有请求的必经之路（学的是"怎么观测"）。

2. 一个 echo 有多贵：实测数据

strace -c echo "hello" 的统计：一个看似什么都没干的 echo 触发 111 次系统调用：

syscall 次数 在干什么（你在 lab02 里亲眼见过）
openat 30 加载动态库：ld.so.cache → libselinux → libc.so.6…
close 20 用完关掉
mmap 20 把库映射进地址空间
newfstatat 19 查文件元数据

你可以在树莓派上自己跑（ebpf-gate lab01 的实验之一）：

strace -c echo "hello"          # 统计表
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'  # eBPF 视角看同样的事

这两条命令看的是同一件事，但机制完全不同——strace 用 ptrace 一个进程一个进程地跟（代价：被跟踪进程慢几倍），bpftrace 在内核里对所有进程的事件计数（代价：接近零）。

全家桶分层：strace / perf / bpftrace 底下各是什么

上面这对对比放大看，是整个 Linux 追踪生态的分层问题——底层机制（地基）与用户态工具（成品）必须分开记：

底层机制（地基） 上层工具（成品） 能看什么 开销
ptrace() 系统调用 strace、gdb 系统调用、信号、断点调试 极高（每次 syscall 双方停走，线上禁用）
ftrace 框架 裸操作 tracefs（语法繁琐） 内核函数、tracepoint 低
perf_events perf（record/trace/top） 采样、tracepoint、PMC 低
eBPF 虚拟机 bpftrace / BCC / libbpf 全部探针 + 内核内自定义计算 很低

三条关系澄清（比表本身更重要，易错）：

  1. ptrace 完全独立：调试机制（暂停进程、接管控制），不在 eBPF 事件源体系内。gdb 必须依赖 ptrace——eBPF 做不了断点调试，两者不是替代关系
  2. eBPF 不建在 ftrace 之上：kprobe/tracepoint 是独立内核基础设施，ftrace 和 eBPF 是并行消费者；eBPF 挂 kprobe 走 perf_event_open()，不经过 ftrace 接口
  3. perf trace ≠ strace：同样看系统调用，perf trace 走 syscalls: 域的 tracepoint，开销低一个量级以上

顺带辨析一个第一道坎：事件源 vs 事件域（bpftrace 语法）：

  • 事件源 = 底层机制大类：tracepoint / kprobe / uprobe / PMC……回答"靠什么抓到事件"
  • 事件域 = tracepoint 专属的子系统分类——sched:sched_switch 冒号前的 sched。域来自内核源码 TRACE_SYSTEM 的静态命名空间
  • kprobe 没有域，语法直接体现：tracepoint:sched:sched_switch（三段式：源:域:名）vs kprobe:vfs_read（两段式：源:函数符号）

机制层深挖（域的目录树、ftrace kprobe_events 伪目录陷阱、同源多监听者、BPF_F_BEFORE/AFTER 张冠李戴辨析）见 02-BPF性能工具 2.6 事件源与 2.14 全家桶分层图——第一本书建立直觉，那两篇是对照深度版。

3. 推论：为什么内核插桩 = 看穿一切

  1. 应用与内核的交互面 ≈ 应用的全部外部行为——读什么文件、连什么地址、花多少 CPU、被谁调度
  2. 在内核里插桩，等于在所有进程共用的必经之路上设卡： - 应用无感知（不像 ptrace 会改变行为） - 无需修改应用、无需重编译、无需重启（连加载前就在跑的老进程也覆盖） - 无法绕过（恶意进程也不能"不走 syscall"）
  3. 这就是后面"三大优势"和"安全用例"的物理基础

4. 嵌入式视角

对嵌入式 Linux：这条边界同样是固件里所有用户态组件（GUI、守护进程、网络服务）的唯一通道。在生产设备上挂一个 eBPF 观测程序，不需要给每个组件插桩就能看全 IO/调度/网络行为——调试现场问题（偶发卡顿、内存泄漏）时这是降维打击。

衔接：既然内核插桩这么香，为什么 30 年来没人随便干？因为"改内核"的传统路径极贵——下一节看两条传统路是怎么堵死的。

1.5 传统扩展内核的两条路（以及为什么不行）

本节讲什么：在 eBPF 之前，想给内核加逻辑只有两条路，各自为什么堵死。理解了这个困局，才能理解验证器为什么是 eBPF 的灵魂。

1. 路径 A：改内核源码

想法最直接：需要什么功能，写个补丁进主线。

现实：

阶段 代价
写补丁 内核约 3000 万行代码，先得看懂相关子系统
评审 只有约 1/3 的补丁被接受，通常耗时 3-6 个月（Jiang et al. 2013 对 LKML 的研究）
进主线 → 装到机器上 还要等发行版采纳：RHEL 8.5（2021-11 发布）用的还是 2018-08 的 4.18 内核——从想法到生产环境以年计

对"我想现在就看一眼某内核函数被谁调用"这种观测需求，3 年等待等于不可行。

2. 路径 B：内核模块（LKM）

不必进主线，独立编译、自由分发——insmod 即用。看起来完美，但有致命问题：

问题 1：模块 = 完整特权代码 - 模块跑在内核态，拥有全部内核权限：任意读写内存、任意提权 - 一个空指针解引用 → 整机崩溃（内核态没有页保护兜底，不像用户态只是段错误） - 恶意模块 = rootkit 的天堂

问题 2：无人敢装 - 因为没有安全性证明，你不敢装陌生模块，你的用户也不敢装你的 - 每次内核升级都可能 API 变动 → 模块失效或加载失败（内核为了保证模块和内核 ABI 匹配会拒绝加载）

两条路的共同死结：内核想要"外来逻辑"，但外来代码没有安全性证明——要么付出三年时间换取信任（路径 A），要么放弃证明直接裸奔（路径 B）。

3. eBPF 的答案：验证器（verifier）

第三条路的关键洞察：不需要所有人相信代码安全，只需要在加载时机器证明它安全。

加载 eBPF 程序时，verifier 静态分析全部可能的执行路径（第 6 章展开算法），证明：

证明项 对应 LKM 的哪个灾难
所有内存访问都在界内（map 值、栈、包） 空指针/野指针 → 整机崩溃
程序必然终止（禁无限循环，有指令数上限） 死循环锁死机器
只调用白名单 helper，且参数类型正确 任意特权操作 / rootkit
不越权访问上下文 逃逸出隔离的观察面

代价：写 eBPF 程序比写普通 C 难（要过验证器这关，报错经常看不懂）；收益：内核敢让非内核开发者往内核里塞逻辑——这是 30 年困局的解锁。

真机体感：你已经在 lab02 见过 verifier 拒绝程序的样子（invalid bpf_context access off=4 size=4）——它连"读了结构体里不该读的字段"这种编译器不查的事都拦。详见 Ch6 §3.6。

衔接：安全性解锁之后，eBPF 相比传统观测手段的具体优势可以数出来了——下一节：三大优势。

1.6 eBPF 的三大优势

本节讲什么：动态加载、高性能、零侵入——每个优势的机制依据是什么，配具体数字。

1. 动态加载：事件驱动，全进程覆盖

机制：程序通过 bpf() 加载进内核 → attach 到某个事件源（kprobe/tracepoint/XDP/…）→ 之后该事件每次发生都触发，无论触发者是谁。

关键推论：

  • 老进程也覆盖：挂上 execve 追踪的那一刻，加载前就在跑的进程再调 execve 照样触发——没有"重启才能生效"一说（对比：给应用插桩、注入 sidecar 都要重启）
  • 容器环境：在节点内核里挂一次，该节点上所有 Pod 的所有进程全可见——因为容器共享宿主内核，而 eBPF 挂在内核上
  • 卸载同样即时：ctrl-C 用户态工具，程序从内核摘除

你在 lab01 亲手验证过：bpftrace 启动 10 秒内，labwc、tailscaled 等早已在跑的进程的 syscall 全被统计——不需要重启它们任何一个。

2. 高性能：JIT + 内核态过滤

两个因素叠加：

a) JIT 编译：eBPF 字节码加载后即编译成本地机器指令（你的树莓派上是 ARM64 机器码），执行速度等同手写内核 C，不是解释执行。

b) 过滤在内核里发生（1993 年 BPF 论文的老智慧，见 §1）：

传统观测:   每个事件 ──内核→用户态拷贝+切换──▶ 用户态过滤 ──99%丢弃
eBPF 观测:  每个事件 ──在内核里直接被过滤/聚合──▶ 只有结果出内核

对百万事件/秒的场景，省掉的不是常数优化，而是每事件一次的上下文切换——上下文切换是微秒级操作，还污染 cache。

实测数字（XDP 论文，CoNEXT '18）：

工作负载 对比基准 加速
XDP 路由转发 常规内核网络栈 2.5×
XDP 负载均衡 IPVS 4.3×

3. 零侵入

不改应用代码、不改配置、不重启——机制上：eBPF 挂在内核的事件点上，应用根本没有参与，也就谈不上被修改。

这在两个场景是刚需：

  • 第三方/闭源软件：无法插桩的进程照样观测（它总得走 syscall）
  • 恶意进程：不会被观测的进程——挖矿程序不会"贴心地"上报自己的 CPU 占用，但它在内核里的调度事件、网络连接全暴露（第 9 章安全用例的基础）

4. 三者的乘法效应

三个优势不是并列，是相乘：因为零侵入所以敢装在生产；因为高性能所以装了不心疼；因为动态加载所以随装随用。缺任何一个，eBPF 都成不了"基础设施级"技术。

衔接：三大优势放到云原生环境里效果最夸张——下一节对比传统 sidecar 方案，看 eBPF 模型怎么碾压。

1.7 云原生环境：对比 sidecar 模型

本节讲什么：同一个观测需求（网络策略、可观测性）在 K8s 里的传统解法 sidecar 和 eBPF 解法怎么对比。即使你暂时不碰 K8s，这个对比也是"eBPF 三大优势"的最佳综合案例。

1. sidecar 模型是什么

想给 Pod 里的应用加网络观测/流量管理，又不改应用代码——传统做法：往 Pod 里注入一个代理容器（sidecar，如 Envoy），应用的网络流量改道经过它：

        Pod（共享 network namespace）
  ┌───────────────────────────────┐
  │  应用容器 ⇄ sidecar 代理(Envoy)⇄ veth ⇄ 宿主网络栈 ⇄ 物理网卡
  └───────────────────────────────┘

2. sidecar 的四个固有缺陷

# 缺陷 机制
1 加 sidecar 要重启 Pod 注入发生在 Pod 创建时；存量 Pod 只能重建
2 依赖注入流程，标注错了就漏掉 YAML 里 annotation 忘写 / namespace 没打标签 → 整个未被插桩，且无报错
3 多容器 ready 顺序不可预测 应用容器先起、Envoy 后 ready → 竞态：Open Service Mesh 文档承认，代理 ready 前应用流量全丢；启动因此还要人为拉慢
4 绕路加延迟 应用流量必须离开内核网络栈、进入代理容器（一次用户态往返）、再回内核——每跳都是上下文切换

3. eBPF 模型：同一位置换个挂法

        Pod                    Pod                    Pod
  ┌────────────┐         ┌────────────┐         ┌────────────┐
  │  应用容器   │         │  应用容器   │         │  应用容器   │   ← 不加任何容器
  └─────┬──────┘         └─────┬──────┘         └─────┬──────┘
        └──────────────────┬───┴──────────────────────┘
                           ▼
  ┌─────────────── 宿主机内核（所有 Pod 共享）─────────────────┐
  │  eBPF 程序挂在网络栈关键点（XDP/TC/cgroup connect）          │
  │  → 一次加载，全节点所有 Pod 的流量全经过                     │
  └──────────────────────────────────────────────────────────────┘

四大缺陷逐一消解：

sidecar 缺陷 eBPF 对应解法
重启 Pod 才能加 动态加载，运行中的节点立即生效（优势 1）
注入漏标 → 漏观测 挂在内核上，"漏标"概念不存在——所有进程都在
ready 顺序竞态 没有 sidecar 就没有顺序问题
绕路延迟 逻辑在内核原地执行，零绕路（优势 2），且不用改应用（优势 3）

4. 额外的一点：对抗恶意进程

观测自家微服务，sidecar 勉强够用；但恶意程序不会配合你注入 sidecar。挖矿程序、横向移动的攻击者流量，sidecar 模型看不见；eBPF 挂在内核网络路径上，主机所有流量（不管来自哪个容器、有没有被编排）都在监管范围——这是 Cilium/Tetragon 做运行时安全的根基（第 9 章）。

1.8 HFT 关联

本节讲什么：第 1 章的概念怎么落到 HFT 工程上——不是"能做什么"的罗列，而是三个具体武器。

1. 内核态过滤 = 低开销观测的物理来源

交易系统全链路上每秒百万级事件（syscall、网卡包、调度事件）。观测这些事件的传统做法（每事件拷到用户态再筛）会直接把系统拖垮；eBPF 在内核里先过滤/聚合，只让结果出内核：

   事件洪流(1M/s) ──▶ [内核: eBPF 过滤/聚合] ──只有感兴趣的事件(1k/s)──▶ 用户态工具

这就是 HFT 观测栈（Pixie、Parca、Hubble、Cilium）敢宣称"低到可以常开"开销的机制根源——不是优化技巧，是架构位置带来的。

工程含义：观测工具本身不能再成为延迟抖动源。给交易机常开观测，eBPF 是唯一现实选项。

2. XDP 2.5×/4.3×：评估旁路方案时的基准锚点

HFT 网络常讨论 DPDK/内核旁路（kernel bypass）——把网卡从内核手里抢过来自己轮询。对比维度：

DPDK 旁路 eBPF/XDP
收益 最高（完全绕开内核栈） 接近（快 2.5×/4.3× 的量级）
代价 整网卡被独占、丢通用性（tcpdump/常规工具全瞎）、开发重 网卡还在内核管理，保留全部常规工具链
可移植 特定 NIC + 大量定制 CO-RE 跨内核

XDP 论文的数字是决策锚点：eBPF 拿到接近旁路的收益，却保留内核栈的通用性。对不是极致裸金属的场景（行情接入前处理、风控前置过滤），XDP 是性价比甜点。

3. 延迟毛刺狩猎：抓 perf 抓不到的东西

HFT 最痛的不是平均延迟，是 p99.9 的偶发毛刺——来源往往是：

  • 调度被抢（CFS 语义，参见你 kernel/2.8 调度类笔记）
  • 软中断/硬中断插队
  • 页回收（kswapd）扫了你的页
  • 内核锁竞争（cgroup、文件系统）

这些全发生在内核里，且不可复现、频率极低——传统采样式 perf（统计采样）大概率漏采。eBPF 的做法是事件触发：挂 sched:sched_switch、irq tracepoint、网卡队列事件，无条件记录每一次发生，事后回放时间线。你在 lab01 已经跑过 @[comm] = count() 的雏形；进阶版是给每次调度切换记时间戳算 off-cpu 时间——第 5 阶段（延迟观测）的主菜。

  6. sidecar 模型的四个缺陷，eBPF 分别怎么消除？
参考答案

1. 解决抓包的两次拷贝问题：过滤器跑用户态时每个包（包括被丢弃的）都要付"内核→用户态"拷贝+切换成本；伪机器让过滤器在内核里就地判决，不要的包零成本丢弃。意义在于确立了"自定义程序在内核里执行"的思想——包过滤只是第一个场景，指令集+内核执行环境这两个要素后来长成了 eBPF。

2. ①64 位指令集+寄存器——能处理现代内核的 64 位指针/数据；②maps——有地方存状态、和用户态交换结构化数据；③bpf() 系统调用——统一的加载/操作入口；④helper 白名单——有限的内核功能访问（拿 pid、读内存…）；⑤验证器——加载前证明安全，内核因此"敢"执行外来代码。（口诀：能算、能存、能加载、能访问、敢让你跑。）

3. 三个阶段各有瓶颈：写补丁（3000 万行代码门槛）→ 评审（仅 1/3 被接受，3-6 个月）→ 等发行版采纳（RHEL 8.5 还在用 3 年前的 4.18）。叠加起来以年计。

4. 顾虑一：模块崩溃=整机崩溃（内核态无页保护兜底）→ verifier 证明所有内存访问有界、程序必终止。顾虑二：模块有全部特权、可当 rootkit → verifier 限制只能调用白名单 helper 且参数类型正确，无法任意访问内核内存。

5. 因为动态链接：加载 ld.so.cache、libselinux、libc 等 30 次 openat + 20 次 mmap……（lab02 里亲眼见过这条链）。对 eBPF 的意义：syscall 边界是应用全部外部行为的必经之路，在这设卡=看穿一切进程且无感知、不可绕过。

6. ①要重启 Pod → eBPF 动态加载即时生效；②注入漏标漏观测 → 挂内核上没有"漏标"概念，全进程覆盖；③ready 顺序竞态 → 没有 sidecar 就没有顺序问题；④流量绕路加延迟 → 逻辑在内核原地执行零绕路。
