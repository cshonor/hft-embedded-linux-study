11.1 eBPF 基金会（2021）

  • 由 Google、Isovalent、Meta、Microsoft、Netflix 在 Linux 基金会下创立
  • 定位：中立机构持有资金与知识产权，让商业公司能合作；不改变内核社区的开发方式
  • 治理：BPF 指导委员会，全部由技术专家组成（内核 BPF 维护者 + 核心项目代表：Alexei Starovoitov、Andrii Nakryiko、Daniel Borkmann 等维护 BPF 子树）
  • 分工：基金会管技术平台与开发工具生态；上层应用项目归其他基金会（Cilium/Pixie/Falco → CNCF）
  • 标准化动因：微软要在 Windows 上实现 eBPF，需要跨 OS 的 eBPF 标准

11.2 eBPF for Windows

  • 成书时（2022 底）已有可运行演示：Cilium L4 负载均衡、eBPF 连接跟踪跑在 Windows 上
  • 为什么可行：eBPF 本质是内核中的虚拟机执行字节码——VM 也可以在 Windows 里实现；网络包结构与协议栈处理在所有 OS 上是相通的

架构与许可证约束（本节最有意思的工程决策）

组件 选择 原因
工具链 复用 libbpf + Clang 的 eBPF 字节码支持 宽松许可，生态现成
验证器 PREVAIL（非 Linux 内核验证器） Linux 内核验证器是 GPL，Windows 闭源不能抄
JIT uBPF JIT 宽松许可
验证/JIT 位置 用户态 Secure 环境（非内核） 内核里的 uBPF 解释器仅用于 debug 构建
  • 别指望所有 Linux eBPF 程序都能跑在 Windows 上——但这与跨内核版本的 CO-RE 挑战本质相同：数据结构差异要程序员优雅处理

11.3 Linux eBPF 的演进方向

自 3.15 起几乎每个内核版本都在扩展（BCC 维护按内核版本的功能清单）。Alexei Starovoitov 的方向判断：从"受限 C"演进到"扩展的安全 C"——最终达到内核模块的全部灵活性，同时保留验证器安全性与动态加载。在研方向：

  1. 签名的 eBPF 程序（供应链安全） - 目标：加载前验证程序来自预期来源、未被篡改 - 难点：用户态 loader 会动态改写程序（map 位置重定位、CO-RE 重定位）——从签名视角这和恶意篡改无法区分。社区尚在求解
  2. 长生命周期内核指针 - 现状：helper/kfunc 拿到的内核指针只在本次程序执行内有效，不能存进 map 下次再用 - 方向：类型化指针（typed pointer）支持放开此限制
  3. 内存分配 - eBPF 程序不能直接调 kmalloc()；提案中的 BPF 专用分配方案

新特性的时间差（现实感）

  • 新特性进内核 ≠ 生产可用：稳定发行版滞后数年
  • 例：Big TCP（5.19，内核内批处理网络包支撑 100 Gbit/s+）——多数发行版几年内不会有，但超大规模流量组织值得提前升级内核来用它；eBPF/Cilium 今天就集成，让大用户先用
  • eBPF 还在向"现场解决问题"扩展：内核漏洞缓解（第 9 章）、甚至解码鼠标/键盘/游戏控制器等 HID 设备协议（承接第 7 章红外控制器解码）

11.4 "eBPF 是平台，不是功能"

  • 十年前容器被热炒，如今开发者日常用 Docker/K8s，但没人直接操作 namespaces/cgroups——eBPF 会走同一条路
  • 多数用户不会手写 eBPF 程序或用 bpftool，但会日常使用基于 eBPF 的工具（性能、调试、网络、安全、追踪），且未必意识到
  • 早期项目靠"我们用了 eBPF"当卖点；现在 eBPF 正在成为基础设施工具的事实默认平台
  • 技能判断：eBPF 编程是稀缺且抢手的技能（类比内核开发远少于业务开发）——深入系统底层者的机会

11.5 坑点清单

  1. 签名 eBPF 短期无解：CO-RE/map 重定位与篡改在二进制上不可区分——别指望近期有"内核验签 eBPF"的现成方案
  2. 内核指针存 map 属于违规（验证器会拦），等 typed pointer 落地——不要试图绕
  3. 追新特性的代价：用了最新内核特性，生产环境（稳定发行版）几年内跑不了；特性选型要看目标机器内核版本
  4. Windows 版验证器是 PREVAIL，行为与 Linux 验证器不完全一致——跨平台程序要在两边分别过验证
  5. BCC 的按内核版本功能清单是查"这个内核有没有某特性"的第一站

11.6 HFT 关联

  • Big TCP 思路的同构价值：批处理换吞吐对行情突发洪峰（开盘/熔断恢复）极有参考性——若交易机内核达到 5.19+，评估 eBPF 配合 Big TCP 的批量收包路径
  • 签名问题就是交易机的合规问题：监管要求交易系统变更可审计，eBPF 程序现在只能靠"单一可信二进制 + 哈希校验 + 权限控制"兜底，官方签名方案落地前这是现实解
  • 升级内核的量化决策：HFT 恰是作者说的"需求足够迫切、值得为 eBPF 特性提前升级内核"的那类组织——用第 10 章工具实测收益再决定
  • 平台化趋势：未来券商风控/审计产品会内嵌 eBPF（作者预言"应用产品自带运行时安全"）——懂 eBPF 的系统工程师在买方/卖方都是稀缺技能
