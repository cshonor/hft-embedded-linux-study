11.1 eBPF 基金会（2021）

  • 由 Google、Isovalent、Meta、Microsoft、Netflix 在 Linux 基金会下创立
  • 定位：中立机构持有资金与知识产权，让商业公司能合作；不改变内核社区的开发方式——eBPF 核心仍在内核邮件列表上按内核节奏演进，基金会管的是生态外围（会议、商标、跨厂商协作的法律壳）
  • 治理：BPF 指导委员会，全部由技术专家组成（内核 BPF 维护者 + 核心项目代表：Alexei Starovoitov、Andrii Nakryiko、Daniel Borkmann 等维护 BPF 子树）——技术治理而非商业投票，避免基金会变成厂商博弈场
  • 分工：基金会管技术平台与开发工具生态（libbpf、bpftool、规范文档）；上层应用项目归其他基金会（Cilium/Pixie/Falco → CNCF）——平台层与应用层分开托管，类比 Linux 内核（kernel.org）与云原生应用（CNCF）的关系
  • 标准化动因：微软要在 Windows 上实现 eBPF，需要跨 OS 的 eBPF 标准——单一厂商实现不可能绑架一个由多家共建的规范，中立的规范持有者是前提

为什么"成立基金会"值得书一章：eBPF 从"内核子系统"变成"跨平台技术平台"的组织学标志——生态位跃迁需要法律/治理基础设施先行。观察一个技术是否长青，看它的治理结构比看它的 feature list 更准。

11.2 eBPF for Windows

  • 成书时（2022 底）已有可运行演示：Cilium L4 负载均衡、eBPF 连接跟踪跑在 Windows 上
  • 为什么可行：eBPF 本质是内核中的虚拟机执行字节码——VM 也可以在 Windows 里实现；网络包结构与协议栈处理在所有 OS 上是相通的（收包/过滤/转发的问题域不依赖 OS）

架构与许可证约束（本节最有意思的工程决策）

组件 选择 原因
工具链 复用 libbpf + Clang 的 eBPF 字节码支持 宽松许可，生态现成
验证器 PREVAIL（非 Linux 内核验证器） Linux 内核验证器是 GPL，Windows 闭源不能抄
JIT uBPF JIT 宽松许可
验证/JIT 位置 用户态 Secure 环境（非内核） 内核里的 uBPF 解释器仅用于 debug 构建

三层工程决策值得展开：

  1. 许可证驱动架构：GPL 的 Linux 验证器不可复用 → 换 PREVAIL（微软研究院的抽象解释验证器，学术出身）——许可约束直接改变了组件选型，这是闭源平台使用开源生态的典型代价。连带后果：PREVAIL 与 Linux 验证器的行为不完全一致（验证严格度、支持的指令集有差异），同一程序可能一边过一边不过
  2. 验证/JIT 放用户态：Linux 是加载前内核内验证；Windows 把这层挪到用户态"Secure 环境"（隔离进程）——设计取向是宁可慢也要把风险关进沙箱。代价：加载路径多一次进程切换
  3. 字节码生态直接复用：编译器侧（Clang 的 BPF target）、ELF 格式、map 概念全部照搬——"eBPF 是平台"的论据（11.2）：字节码格式是跨 OS 的公共接口
  • 别指望所有 Linux eBPF 程序都能跑在 Windows 上——但这与跨内核版本的 CO-RE 挑战本质相同：数据结构差异要程序员优雅处理（CO-RE 重定位在 Windows 侧同样要解决 NT 内核结构与 Linux 结构的映射）

衔接：Linux 侧的演进方向与"平台论"→ 11.2；坑点与 HFT → 11.3。

11.3 Linux eBPF 的演进方向

自 3.15 起几乎每个内核版本都在扩展（BCC 维护按内核版本的功能清单）。Alexei Starovoitov 的方向判断：从"受限 C"演进到"扩展的安全 C"——最终达到内核模块的全部灵活性，同时保留验证器安全性与动态加载。在研方向：

  1. 签名的 eBPF 程序（供应链安全） - 目标：加载前验证程序来自预期来源、未被篡改 - 难点：用户态 loader 会动态改写程序（map 位置重定位、CO-RE 重定位）——从签名视角这和恶意篡改无法区分。签名验的是原始字节，加载执行的是重定位后字节，验证的对象和运行的对象不是同一份。社区尚在求解（思路包括对重定位做白名单化证明、以 BTF/token 机制约束 loader 行为）
  2. 长生命周期内核指针 - 现状：helper/kfunc 拿到的内核指针只在本次程序执行内有效，不能存进 map 下次再用——内核数据结构可能在此期间被释放/重用（悬垂指针） - 方向：类型化指针（typed pointer）+ 引用语义（如 bpf_task_acquire 一族 kfunc 已经开了口子：获取引用的 task 指针可存 map，配对 release）——本质是把所有权模型引入验证器的类型系统
  3. 内存分配 - eBPF 程序不能直接调 kmalloc()（不受控分配与验证器的内存模型冲突）；提案中的 BPF 专用分配方案（arena、kptr 机制在逐步落地）

这三个方向的共同主题：把 C 语言的完整能力（指针生命周期、动态内存、可审计分发）在验证器可证明的前提下逐步还给 eBPF——不是放松安全，而是扩展证明技术。

新特性的时间差（现实感）

  • 新特性进内核 ≠ 生产可用：稳定发行版滞后数年——mainline → LTS → 发行版 → 你的生产内核，每一跳 1-2 年
  • 例：Big TCP（5.19，内核内批处理网络包支撑 100 Gbit/s+）——多数发行版几年内不会有，但超大规模流量组织值得提前升级内核来用它；eBPF/Cilium 今天就集成，让大用户先用
  • eBPF 还在向"现场解决问题"扩展：内核漏洞缓解（第 9 章：eBPF 程序在漏洞修复补丁下发前先在观测/策略层止血）、甚至解码鼠标/键盘/游戏控制器等 HID 设备协议（承接第 7 章红外控制器解码）——"等发行版升级"之外的第二条止血路径

11.4 "eBPF 是平台，不是功能"

  • 十年前容器被热炒，如今开发者日常用 Docker/K8s，但没人直接操作 namespaces/cgroups——eBPF 会走同一条路：基础设施被吸收进产品，直接操作者越来越少，受益者越来越多
  • 多数用户不会手写 eBPF 程序或用 bpftool，但会日常使用基于 eBPF 的工具（性能、调试、网络、安全、追踪），且未必意识到——Cilium 网络策略、Tetragon 安全、各种 profiling agent 背后全是 eBPF
  • 早期项目靠"我们用了 eBPF"当卖点；现在 eBPF 正在成为基础设施工具的事实默认平台——当"用了 X"不再是差异化卖点时，X 就赢了
  • 技能判断：eBPF 编程是稀缺且抢手的技能（类比内核开发远少于业务开发）——深入系统底层者的机会

对学习路线的含义（本模块收束）：读 BPT 工具百科（02 目录）时意识到——那 800 页里的工具正被吸收进平台产品；手写 eBPF 的能力是稀缺杠杆，用 eBPF 工具的能力是普适基线。你在这个仓库走的路线（原理书 → 工具书 → ebpf-gate 真机实验）恰好是"基线 + 杠杆"两条腿。

11.5 坑点清单

  1. 签名 eBPF 短期无解：CO-RE/map 重定位与篡改在二进制上不可区分（11.2：签名验原始字节、运行的是重定位后字节）——别指望近期有"内核验签 eBPF"的现成方案
  2. 内核指针存 map 属于违规（验证器会拦），等 typed pointer/acquire-release 语义全面落地——不要试图绕（绕过 = 引入悬垂指针 = 内核崩溃风险，这正是验证器拦它的原因）
  3. 追新特性的代价：用了最新内核特性，生产环境（稳定发行版）几年内跑不了；特性选型要看目标机器内核版本——bpftool feature + BCC 版本功能清单是查询第一站
  4. Windows 版验证器是 PREVAIL，行为与 Linux 验证器不完全一致——跨平台程序要在两边分别过验证；验证/JIT 在用户态 Secure 环境也是加载路径差异
  5. BCC 的按内核版本功能清单是查"这个内核有没有某特性"的第一站

11.6 HFT 关联

1. Big TCP 思路的同构价值

批处理换吞吐对行情突发洪峰（开盘/熔断恢复的 tick 风暴）极有参考性——洪峰期的事件处理成本不在单个事件而在每事件固定开销 × 事件数；内核内批处理把固定开销摊到批次。若交易机内核达到 5.19+，评估 eBPF 配合 Big TCP 的批量收包路径；达不到，思路仍然可迁移（用户态侧的批量 ring buffer 消费、NAPI 式配额处理）。

2. 签名问题就是交易机的合规问题

监管要求交易系统变更可审计，eBPF 程序现在只能靠"单一可信二进制 + 哈希校验 + 权限控制"兜底：CI 产出的 .o 嵌入二进制、部署前 SHA 校验、加载权限收敛到专用服务账户（CAP_BPF 最小化）。官方签名方案落地前这是现实解——把"谁能加载程序"的治理做进部署流水线，而不是指望内核替你验。

3. 升级内核的量化决策

HFT 恰是作者说的"需求足够迫切、值得为 eBPF 特性提前升级内核"的那类组织——但升级决策要量化：候选特性（如 Big TCP、bpf_loop、BPF token）在测试环境实测收益（第 10 章工具 + BPF_PROG_RUN 测试），收益覆盖升级回归成本（全量基线重跑、06.6 3.6 升级纪律）才动。

4. 平台化趋势的就业/选型含义

未来券商风控/审计产品会内嵌 eBPF（作者预言"应用产品自带运行时安全"）——买方视角：选型时问清供应商的 eBPF 层是否可控（能不能关、开销多大、误杀策略谁定）；工程师视角：懂 eBPF 的系统工程师在买方/卖方都是稀缺技能，原理书这 11 章的内功（验证器/挂点/CO-RE）正是区分"会用工具"和"能造工具"的分界线。

11.7 自测题

  1. eBPF 基金会为什么成立？它与 CNCF 的分工边界在哪？
  2. eBPF for Windows 为什么不能复用 Linux 内核的验证器？它用了什么替代？
  3. Windows 版在哪里做验证和 JIT？与 Linux 的差异？
  4. 签名 eBPF 程序的核心难点是什么？
  5. 现在内核指针在 eBPF 程序里的生命周期限制是什么？
  6. 为什么"新特性进了最新内核"对大多数生产用户没有意义？Big TCP 的例子说明什么组织例外？
  7. "eBPF 是平台不是功能"如何类比容器的发展史？
参考答案

1. 让商业公司能在中立机构下合作（资金与知识产权的持有壳），且不改变内核社区开发方式——微软做 Windows 版 eBPF 需要跨 OS 的中立标准是直接动因。分工：基金会管技术平台与开发工具生态（libbpf/bpftool/规范）；上层应用项目（Cilium/Pixie/Falco）归 CNCF。

2. Linux 内核验证器是 GPL 许可，Windows 闭源实现不能抄。替代：PREVAIL（微软研究院的抽象解释验证器，宽松许可）。

3. Windows 在用户态 Secure 环境（隔离进程）做验证和 JIT；Linux 在内核里加载前验证、内核内 JIT。差异：Windows 宁可加载路径慢也要把验证/JIT 的风险关进沙箱；内核里的 uBPF 解释器仅用于 debug 构建。

4. 用户态 loader 会动态改写程序（map 重定位、CO-RE 重定位）——签名验的是原始字节，实际执行的是重定位后字节，验证对象 ≠ 运行对象；从密码学视角这与篡改不可区分。解法要么证明重定位可白名单化，要么改造加载信任链。

5. helper/kfunc 返回的内核指针只在本次程序执行内有效——不能存 map 跨事件复用（内核结构可能已被释放，悬垂指针）。缓解中的出路：typed pointer + 引用计数语义（bpf_task_acquire/release 一族 kfunc）。

6. 稳定发行版滞后最新内核数年——mainline→LTS→发行版→生产每跳 1-2 年，多数组织等到特性可用时早已不新。例外：需求足够迫切、能主导自己内核版本的组织（超大规模流量组织、HFT）——Big TCP 的 100Gbit/s+ 批处理收益对他们值得提前升级内核。

7. 容器十年前被热炒，如今人人用 Docker/K8s 但没人直接操作 namespaces/cgroups——基础设施被吸收进产品，直接操作者变少、受益者变多。eBPF 同路：没人手写探针，但 Cilium/Tetragon/profiling agent 背后全是它；"我们用了 eBPF"从卖点变默认，平台就赢了。
