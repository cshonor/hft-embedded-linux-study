10.1

语言与库全景（原书 §10.1–10.3）

合并自原 section-1～3。文件名序号是合并后的笔记序号；正文小节标题沿用原书节号，历史 § 引用依然有效。

10.1 bpftrace：最高层的追踪语言

  • 类 awk/C 的高级追踪语言，工具把脚本转成 eBPF 代码——用户完全感知不到内核/用户空间分界
  • 建在 BCC 之上（脚本→BCC 程序→运行时 LLVM/Clang 编译）
  • 只支持追踪类事件（kprobe/uprobe/tracepoint），不含网络类
bpftrace -l "*execve*"                    # 列出所有含 execve 的挂点

bpftrace -e 'kprobe:do_execve { @[comm] = count(); }'
# 按进程名统计 execve 次数：@[node]: 6  @[sh]: 6  @[cpuUsage.sh]: 18

opensnoop.bt：entry/exit 配对的标准范式

tracepoint:syscalls:sys_enter_open,
tracepoint:syscalls:sys_enter_openat          // 一个程序挂多个事件
{
    @filename[tid] = args->filename;          // 入口存参数（tid 为 key）
}
tracepoint:syscalls:sys_exit_open,
tracepoint:syscalls:sys_exit_openat
/@filename[tid]/                                // 过滤器：map 里存在才执行
{
    $ret = args->ret;
    $fd = $ret > 0 ? $ret : -1;
    $errno = $ret > 0 ? 0 : -$ret;
    printf("%-6d %-16s %4d %3d %s\n", pid, comm, $fd, $errno, str(@filename[tid]));
    delete(@filename[tid]);
}
  • 为什么 entry+exit 都挂：entry 拿参数（文件名），exit 拿结果（fd/errno）——单一挂点拿不齐
  • Attaching 6 probes = 4 个事件 + BEGIN/END 两个特殊探针（初始化/清理，同 awk）
  • bpftool prog list 可看到 4 个 tracepoint 程序 + hash map（缓存文件名）+ perf_event_array（printf 输出通道）——高层语言生成的正是本书前几章手写的那些东西

10.2 内核侧语言选择

  • 可直接写 eBPF 字节码（Cloudflare 手写汇编的极端案例），实践上都是 C 或 Rust 编译目标
  • 带运行时的语言不行：GC 无法与验证器内存检查共存；eBPF 程序必须单线程，语言并发特性用不上（Go、Java 排除）
  • GCC 10+ 也支持 eBPF 目标，但功能仍落后 LLVM
  • XDPLua（内核跑 Lua 的 XDP）：研究结论性能不如 eBPF，且 eBPF 越来越强（循环等），无优势

10.3 用户态库全景

3.1 BCC（Python/Lua/C++）

  • eBPF 代码作为字符串嵌入 Python，BCC 预处理后交 Clang 运行时编译（第 5 章 CO-RE 五大痛点的来源）
  • BCC 提供了自己的类 C 方言：BPF_RINGBUF_OUTPUT(output, 1) 一行同时给内核和用户态定义 ring buffer；output.ringbuf_output(...) 这种"对象方法"被展开成 bpf_ringbuf_output() helper
  • 适合入门和原型；分发生产工具不推荐（要带编译器工具链，内存占用大：libbpf 版 opensnoop ~9MB vs Python 版 ~80MB，还有运行时编译的启动延迟）
  • BCC 工具现已提供 libbpf 重写版（libbpf-tools），共识是用重写版

3.2 C + libbpf

  • 本书主线方案；CO-RE + 骨架，无编译器依赖
  • 入门起点：libbpf-bootstrap；XDP 开发用 libxdp（xdp-tools 的一部分，配套 XDP Tutorial 是最好的实战教材之一）
  • 坑：用户态 C 代码没有验证器保护，内存错误自己负责

3.3 Go（三个库）

库 实现方式 CO-RE 现状
gobpf iovisor，配合 BCC 跟随 BCC 停止积极维护，讨论弃用中——别选
cilium/ebpf 纯 Go 实现（无 CGo） 有 广泛使用（GitHub 约 1 万引用），首选
libbpfgo libbpf 的 CGo 封装 有 Tracee/Parca 在用；CGo 边界有性能顾虑

cilium/ebpf 的 bpf2go 工作流：

// C 文件开头标记（Go 编译器忽略）：
// +build ignore

// 用户态文件里：
//go:generate go run github.com/cilium/ebpf/cmd/bpf2go -cc $BPF_CLANG -cflags $BPF_CFLAGS bpf <C文件> -- -I../headers
  • go generate 一步完成：编译 eBPF 字节码 + 生成 Go 骨架
  • 生成物：bpf_bpfeb.o/bpf_bpfel.o（大端/小端两套字节码）+ 对应 .go 文件（编译期按目标平台选用）——类似 bpftool gen skeleton 的 Go 版
  • 自动生成的结构（名字从 C 代码派生）：
type bpfMaps struct {
    KprobeMap *ebpf.Map `ebpf:"kprobe_map"`
}
type bpfPrograms struct {
    KprobeExecve *ebpf.Program `ebpf:"kprobe_execve"`
}
type bpfObjects struct { bpfPrograms; bpfMaps }

// 使用：
objs := bpfObjects{}
loadBpfObjects(&objs, nil)                     // 加载全部
defer objs.Close()
kp, _ := link.Kprobe("sys_execve", objs.KprobeExecve, nil)  // 附加
objs.KprobeMap.Lookup(mapKey, &value)          // 读 map

libbpfgo 特点：channel 接收 ringbuf/perfbuf 事件（bpfModule.InitRingBuffer("events", eventsChannel, buffSize)）——Go 语言原生异步特性顺滑接入。

3.4 Rust（三个库）

库 定位 备注
libbpf-rs libbpf 的 Rust 封装，内核侧仍写 C 官方 libbpf 项目出品
Redbpf libbpf 接口的 Rust crates；Rust→LLVM bitcode→eBPF 多步编译 foniod 安全监控项目；被 Aya 抢走势头
Aya 纯 Rust、直达 syscall，不依赖 libbpf/BCC/LLVM；实现与 libbpf 相同的 CO-RE 重定位 rustc 直接编 eBPF；支持类型最全（trace/XDP/TC/cgroup/LSM）；生态趋势所在（lockc 从 libbpf-rs 迁到 Aya）

Aya 内核侧代码长这样（对比 C 的 SEC("xdp/myapp")）：

#[xdp(name="myapp")]
pub fn myapp(ctx: XdpContext) -> u32 {
    match unsafe { try_myapp(ctx) } {
        Ok(ret) => ret,
        Err(_) => xdp_action::XDP_ABORTED,
    }
}
unsafe fn try_myapp(ctx: XdpContext) -> Result<u32, u32> {
    info!(&ctx, "received a packet");
    Ok(xdp_action::XDP_PASS)
}

// 用户侧：
let mut bpf = Bpf::load(include_bytes_aligned!("../../target/bpfel-unknown-none/release/myapp"))?;
let program: &mut Xdp = bpf.program_mut("myapp").unwrap().try_into()?;
program.load()?;
program.attach(&opt.iface, XdpFlags::default())
  • aya-tool：生成与内核结构匹配的 Rust 定义（类似 bpftool 生成 vmlinux.h 的作用）

10.4 测试与性能统计

BPF_PROG_RUN：用户态直接运行 eBPF 程序做测试——不走真实事件，而是喂入构造的 ctx（如伪造的 skb），检查输出。目前主要支持网络类程序类型（XDP/TC 最好用）。价值：单元测试内核态代码不需要内核事件——CI 里就能回归"这个 XDP 程序对恶意包返回 DROP"。

运行时统计：

sysctl -w kernel.bpf_stats_enabled=1
bpftool prog list     # 多出 run_time_ns / run_cnt 字段
# 例：run_time_ns 316876 run_cnt 4 → 4 次执行共 ~300μs（均值 ~79μs/次）
sysctl -w kernel.bpf_stats_enabled=0   # 用完关掉——统计本身有开销

两个数字的用法：run_cnt 验证挂点（零触发=挂错点或路径不通，呼应 7.2 真机教训）；run_time_ns/cnt 评估探针税（每次事件的平均耗时 × 事件速率 = 观测总开销——挂上探针前后对比业务延迟，就是 06.6 4.6 观测者效应 的量化实验在 eBPF 侧的落地）。

10.5 多 eBPF 程序的协作

一个 eBPF 程序 = 一个函数 + 一个事件；真实应用（如 opensnoop）需要多个程序协同：

协作模式一：entry/exit 配对（10.1 的 opensnoop.bt 范式）——程序之间本质独立，靠 map 协调：entry 程序写 map（@filename[tid]），exit 程序读删 map。跨程序状态只有 map 一个载体——没有全局变量共享（每个程序的全局变量是自己的 .bss map）、没有进程内存共享。

entry 程序 ──写──> hash map（key=tid, value=filename）<──读+删── exit 程序
                                                        │
                                              中途退出的 tid？→ map 残留（泄漏！）

配对的工程隐患：entry 有 exit 无（进程崩溃在中间）→ map 条目泄漏——生产 agent 要加定期清理或 map 容量上限告警。

协作模式二：动态程序集——程序数量动态变化：Cilium 给每个虚拟网卡挂程序，Pod 增减时接口来去。这对加载器提出"生命周期管理"需求（按需 load/attach/detach/close），skeleton 的 open/close 模型正好承接。

协作模式三：尾调用链——PROG_ARRAY 串起多个程序接力（7.2 的 XDP 内部分发）。

骨架类工具（libbpf / ebpf-go）一条调用加载全部程序与 map（对象集合来自 ELF 的段扫描），也提供单个对象的细粒度操作——"整队加载、按个管理"。

10.6 选型速查（作者结论）

场景 选择 一句话理由
快速收集 trace 信息 bpftrace 一行命令、零编译等待
Python 快速原型、不在乎运行时编译 BCC Python 用户态代码简洁、迭代快
生产分发、跨内核版本可移植（CO-RE） C: libbpf；Go: cilium/ebpf 或 libbpfgo；Rust: Aya 单一二进制、无编译器依赖
Rust 全栈（内核+用户态同语言、无 LLVM 依赖） Aya rustc 直编 eBPF、类型安全全链路

选型的隐藏维度（补充）：团队已有技能栈 > 语言本身优劣——Go 团队用 cilium/ebpf、C 团队用 libbpf 的落地成功率远高于"为了 eBPF 换语言"。与 06.6 15.1.7 BCC vs bpftrace 的升格工作流（bpftrace 即兴 → BCC/预制 → libbpf 升格）拼起来，就是完整的工具链演进地图。

10.7 坑点清单

  1. bpftrace/BCC 基于 syscall 入口的工具有 TOCTOU（第 9 章）——观测可用，别当安全防线；同一挂点"观测工具"和"安全工具"是两个信任等级
  2. gobpf 已停止维护——新项目别选（Go 侧首选 cilium/ebpf）
  3. libbpfgo 的 CGo 边界（"cgo is not Go"）可能带来性能/构建问题——对延迟敏感选纯 Go 的 cilium/ebpf；CGo 的调用开销在事件回调路径上会被放大
  4. BCC 的"类 C 方言"不是标准 C：BPF_RINGBUF_OUTPUT、对象方法等宏只在 BCC 里有——代码不可移植到 libbpf，用 BCC 原型时就要按"将来要重写"来设计
  5. cilium/ebpf 生成两套字节码（大端 bpfeb / 小端 bpfel）——交叉编译时确认架构选对了 .o；选错端的症状是加载失败或程序行为诡异（字段字节序颠倒）
  6. bpf_stats_enabled 统计本身有开销，测完记得关——开着跑性能基准，测出来的数被统计污染
  7. 内核侧 C 用户侧也 C 时，用户态代码没有验证器兜底——map 读写、缓冲区处理全靠自己；用户态段错误照样崩 agent（虽然不伤内核，但观测数据流断了）

10.8 HFT 关联

1. 低延迟监控工具就该单一二进制

cilium/ebpf + bpf2go 或 libbpf 骨架产出无依赖单文件（.o 嵌入二进制），push 到交易机零安装成本、可审计（SHA 哈希可校验——第 11 章签名问题落地前的现实解）。对比 Python 版工具：opensnoop libbpf 版 ~9MB vs BCC 版 ~80MB，差的 71MB 主要是 LLVM/Clang 运行时——交易机上每一 MB 的部署面积都是攻击面和审计成本。

2. opensnoop 式 entry/exit 配对直接可抄

交易程序挂单路径计时（entry 存时间戳，exit 取出算差值，hist map 出分布）就是同一模式——从书里的 opensnoop 到 HFT 的 tick 分段计时，只差把"文件名"换成"时间戳"。配对时注意 10.2 的 map 泄漏问题：线程中途退出时 entry 状态残留，定期清理。

3. bpf_stats_enabled 是免费的性能回归探针

交易机常规 eBPF 程序的 run_time_ns/run_cnt 定期采集——探针自己的延迟分布也在监控之列（观测工具的性能也需要观测，06.6 4.6 的递归应用）。基线上突然的 run_time_ns 抬升 = 内核升级/环境变化影响了探针执行 → 观测数据的可信度先于业务指标受影响。

4. bpftrace 适合运维快速排查，生产常驻 agent 用 CO-RE 栈

"这台交易机现在谁在疯狂 open 配置文件？"——bpftrace 一行搞定（分钟级响应）；而常驻 agent（tick 分段计时、syscall 白名单记录）必须是 CO-RE 单二进制（月级无人值守运行）。两个层次对应值班的不同时刻：bpftrace 是"现在出事了"的第一反应，CO-RE agent 是"一直都在看着"的常驻哨兵。

5. 用户态无验证器 = agent 的内存纪律

内核侧有验证器兜底，用户态 C 侧没有——agent 崩了不伤内核但断数据流（交易机上"监控静默"本身就是事故）。工程对策：用户态侧用带边界检查的库 API（libbpf 的 bpf_map_lookup_elem 封装了拷贝长度）、事件解析代码 fuzz 测试（恶意/畸形事件不应崩 agent——观测面是攻击面）。

10.9 自测题

  1. eBPF 编程的哪两半？bpftrace 如何把两者对程序员透明？
  2. opensnoop 为什么必须同时挂 syscall 的 entry 和 exit？两个程序间如何传数据？
  3. 为什么 Go/Java 不能作为内核侧 eBPF 语言？
  4. BCC 的 BPF_RINGBUF_OUTPUT 一行为什么同时服务于内核和用户态？
  5. libbpf 版 opensnoop 9MB vs Python 版 80MB，差的 71MB 是什么？
  6. cilium/ebpf 的 bpf2go 生成哪些文件？为什么有两套字节码？
  7. libbpfgo 与 cilium/ebpf 的架构差异是什么？各自的顾虑？
  8. Aya 与 Redbpf、libbpf-rs 的本质区别？为什么 lockc 迁移到 Aya？
  9. 如何查看一个已加载 eBPF 程序的运行次数与总耗时？
  10. 多 eBPF 程序的应用中，程序之间如何协调？
参考答案

1. 内核侧（eBPF 程序，编译成字节码加载进内核）+ 用户侧（加载器/消费者，读 map 收事件）。bpftrace 用一门高层语言把两半都生成：脚本编译成 eBPF（内核侧）+ 内置 runtime 管理加载和输出（用户侧）——程序员完全感知不到分界。

2. entry 拿参数（文件名），exit 拿结果（fd/errno）——单一挂点拿不齐（syscall 执行中参数寄存器会被覆盖）。传数据：hash map，key=tid，entry 写 @filename[tid]，exit 读+delete。

3. 带运行时的语言：①GC 与验证器的内存检查模型不兼容（验证器要求所有内存访问可静态证明）；②eBPF 程序必须单线程，语言的并发/调度运行时没有落点；③运行时本身装不进 512B 栈和验证约束。

4. BCC 的宏在预处理期同时展开成两份：内核侧的 map 定义（BPF_MAP_TYPE_RINGBUF 创建）+ 用户侧的 Python 对象（ring buffer 消费接口）——一行源码、两个世界的胶水，这也是 BCC 方言不可移植的原因（标准 C 没有这种"一鱼两吃"机制，libbpf 用 skeleton 生成达到同效）。

5. LLVM/Clang 工具链及其运行时库——BCC 每次启动都要在目标机现场编译，二进制里背着整个编译器；libbpf 版预编译完成，只带字节码和轻量加载库。

6. 生成 bpf_bpfeb.o/bpf_bpfel.o（字节码）+ 对应 .go 文件（类型安全的骨架：bpfObjects/bpfPrograms/bpfMaps 结构 + load/attach 函数）。两套字节码是因为 eBPF 字节码里的内存访问字节序跟随目标架构（大端目标机 bpfeb / 小端 bpfel）——编译期不知道部署目标就两边都生成，链接时按 GOARCH 选。

7. libbpfgo 是 libbpf 的 CGo 封装（复用 C 库的全部功能，但跨语言边界有开销、构建要 CGo 工具链）；cilium/ebpf 是纯 Go 重实现（无 CGo、系统调用直达，但功能跟随要自己追）。顾虑：前者 cgo is not Go；后者重实现的完整度/成熟度。

8. Aya 是纯 Rust、直达 syscall，不依赖 libbpf/BCC/LLVM——内核侧 Rust 代码由 rustc 直接编 eBPF（无需 clang），且实现了与 libbpf 相同的 CO-RE 重定位；libbpf-rs 是 libbpf 封装（内核侧仍写 C）、Redbpf 走 LLVM 多步编译。lockc 迁到 Aya：全栈 Rust 单一工具链、无 C 依赖，部署和交叉编译都简单。

9. sysctl kernel.bpf_stats_enabled=1 后 bpftool prog list 出现 run_time_ns/run_cnt 字段；用完关掉（统计本身有开销）。

10. 程序本质独立，协作靠三种机制：①map 共享状态（entry/exit 配对：一个写一个读删）；②PROG_ARRAY 尾调用（接力分发，策略数据化）；③加载器编排（skeleton/agent 管理程序集合的生命周期，动态增减）。
