3.1 eBPF 虚拟机

执行模型：字节码早期在内核里解释执行，现已被 JIT 编译取代——既为性能，也为规避 eBPF 解释器的 Spectre 类侧信道漏洞。net.core.bpf_jit_enable sysctl 与 CONFIG_BPF_JIT 控制开关（bpftool prog list 里 jited 标志即其产物）。

指令集/寄存器模型设计成与主流 CPU 架构一一映射，使 JIT/解释都简单直接——这是 eBPF 能跨 x86/ARM64 高效落地的根基：字节码里的寄存器语义与真实寄存器几乎一一对应，JIT 退化为"翻译"而非"模拟"。

寄存器（软件实现，include/uapi/linux/bpf.h 中 BPF_REG_0~BPF_REG_10）：

寄存器 角色 备注
R0 返回值（helper 返回值 + 程序返回值共用） 程序退出时 R0 就是返回码（如 XDP_PASS）
R1–R5 函数调用参数 R1 兼任程序入口的 ctx 指针；R5 之后就没有了 → helper 最多 5 个参数
R6–R9 跨调用保持（callee-saved） helper 调用不破坏——验证器日志里大量 r6 = r1 就是把 ctx 存进 R6 备份（6.1）
R10 栈帧指针（只读） 512 字节栈的底；r10 - 8 是栈顶第一个可用槽

对照：这套寄存器约定和 x86-64 SysV ABI（RDI/RSI/RDX/RCX/R8/R9 传参、RAX 返回、RBX/R12-R15 callee-saved）是刻意同构的——JIT 时 r1→rdi、r6→rbx 几乎直译。

指令 struct bpf_insn（64 位 / 8 字节）：

struct bpf_insn {
    __u8 code;          /* 操作码：指令大类 + 具体 op */
    __u8 dst_reg:4;     /* 目标寄存器 */
    __u8 src_reg:4;     /* 源寄存器 */
    __s16 off;          /* 有符号偏移（跳转目标/访存偏移） */
    __s32 imm;          /* 有符号立即数 */
};
  • 需要装载 64 位立即数时 imm（32 位）放不下 → 宽指令编码 16 字节（两条槽：ldimm64 占两个 bpf_insn，反汇编里 offset 0 的下一条在 2——见 3.2 的反汇编精读）
  • 指令大类：装载（立即数/内存/寄存器）、存储、算术、条件跳转
  • 5.12 加入原子指令（ADD/AND/OR/XOR 由 imm 指定）——与 04-cpp 学的原子操作直接对应；map value 里的计数器自此可以做内核态原子 xadd，不必"读-改-写"三步

指令上限：单个程序 100 万条已验证指令（BPF_COMPLEXITY_LIMIT_INSNS）；非特权用户仍是老限制 BPF_MAXINSNS = 4096（定义在 include/uapi/linux/bpf_common.h，不在 bpf.h——全仓 grep 找定义时的最后一个反例）。

3.2 XDP 版 Hello World（纯 C）

#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>
int counter = 0;                       // 全局变量（= map，见 3.5）
SEC("xdp")                             // ELF 段名 = 程序类型标记
int hello(void *ctx) {
    bpf_printk("Hello World %d", counter);
    counter++;
    return XDP_PASS;                   // 裁决：正常继续处理
}
char LICENSE[] SEC("license") = "Dual BSD/GPL";

要点：

  • 文件名约定 *.bpf.c 区分内核态代码与用户态代码（同一仓库里 .c 是加载器）
  • SEC("license") 是硬性要求：部分 helper 是 "GPL only"（如 bpf_probe_read_kernel），声明不兼容时验证器直接拒绝；LSM 类程序必须 GPL 兼容。libbpf 靠 ELF 段名驱动一切——SEC("xdp") 决定程序类型，段名错了后面全错
  • bpf_printk（libbpf 名）/bpf_trace_printk（BCC 名）是同一内核函数的封装；输出进 /sys/kernel/debug/tracing/trace_pipe（全机共享、慢，生产用 ring buffer——2.3 坑点 1）
  • XDP 在包到达网卡入口的瞬间触发，可改包内容并给裁决；此时还没有任何进程与之关联（trace 行首 <idle>-0）——网络类程序里 bpf_get_current_pid_tgid() 拿不到有意义的值

XDP 五种返回码（include/uapi/linux/bpf.h，v6.6 实测核对）：

返回码 值 语义 典型用途
XDP_ABORTED 0 异常中止，报错并丢包 程序内错误路径；返回 0 ≠ 成功
XDP_DROP 1 立即丢弃 黑名单过滤、early drop
XDP_PASS 2 正常继续走内核栈 默认放行
XDP_TX 3 从同一网卡弹回发送 负载均衡应答反射
XDP_REDIRECT 4 转发到另一网卡/CPU（配合 devmap/cpumap） RSS 定向、旁路采集
  • 部分网卡支持 XDP 卸载（offload），程序直接跑在网卡上——包进主机内存之前就被处理掉（DDoS 清洗、防火墙、负载均衡利器）；代价是网卡固件的功能子集（卸载路径只支持部分 helper）
  • XDP 程序按接口挂载（不同接口可挂不同程序），但一个接口只能挂一个——多逻辑要靠程序内部分发（7.2 坑点 1）

衔接：程序怎么编译、验证、加载、挂到网卡——3.2 编译检查与加载附加；全局变量为什么让 bpftool 显示"没写 map 却有 2 个 map"——3.3。

3.3 编译与检查

hello.bpf.o: %.o: %.c
    clang -target bpf -I/usr/include/$(shell uname -m)-linux-gnu -g -O2 -c $< -o $@
  • file hello.bpf.o → ELF 64-bit LSB relocatable, eBPF
  • llvm-objdump -S hello.bpf.o 看字节码（-g 让源码与指令并排显示）

反汇编解读（学会读这个，验证器报错就不可怕了）：

 0: 18 06 ... r6 = 0 ll          # 宽指令16字节：r6 指向全局变量所在的 map（.bss）
 2: 61 63 ... r3 = *(u32 *)(r6+0)  # 取 counter
 5: b7 02 00 00 0f 00 00 00 r2 = 15  # 操作码0xb7 = dst=imm，r2=15（字符串长度）
 6: 85 00 00 00 06 00 00 00 call 6   # 操作码0x85 = 函数调用，imm=6 → helper #6 (bpf_trace_printk)
10: b7 00 00 00 02 00 00 00 r0 = 2   # 返回值放 r0；XDP_PASS == 2
11: 95 ... exit

注意宽指令占 2 个偏移槽（offset 0 的下一条在 2）。

真机案例：ARM64 上交叉编译（树莓派 5 实测，2026-08）

书上这条 Makefile 在 x86_64 直接能跑，但在 aarch64 上第一次就编译失败：

clang -target bpf -O2 -g -c hello.bpf.c -o hello.bpf.o
fatal error: 'asm/types.h' file not found

原因：-target bpf 让 clang 把目标定为 BPF 虚拟机，它不再知道宿主机的架构，也就不知道该去哪个架构目录找 asm/ 头文件（asm/types.h 是被 <linux/bpf.h> 间接包含的）。x86_64 之所以"碰巧能用"，是因为书里的 -I/usr/include/x86_64-linux-gnu 手动指了路径——这行不是可选装饰，是架构相关的必需项。

修复（aarch64）：

CLANG = clang
ARCH_INCLUDES = -D__TARGET_ARCH_arm64 -I/usr/include/aarch64-linux-gnu

hello.bpf.o: hello.bpf.c
    $(CLANG) -target bpf $(ARCH_INCLUDES) -O2 -g -c $< -o $@
  • -D__TARGET_ARCH_arm64：bpf_tracing.h 里 PT_REGS_PARMx / BPF_KPROBE 系宏靠它选对寄存器映射，漏传则编译失败或在 kprobe 里取错参数
  • 通用写法：-D__TARGET_ARCH_$(shell uname -m | sed s/aarch64/arm64/)，-I/usr/include/$(shell uname -m)-linux-gnu

完整可复现实验：ebpf-gate/labs/02-kprobe（Pi 5 / 6.18 内核 / clang 19 实测通过）

3.4 加载、检查、附加、卸载（bpftool）

bpftool prog load hello.bpf.o /sys/fs/bpf/hello   # 加载 + pin 到 bpffs
bpftool prog list                                  # 540: xdp name hello tag d35b... gpl
bpftool prog show id 540 --pretty                  # JSON 全字段
bpftool net attach xdp id 540 dev eth0             # 挂到网卡
bpftool net detach xdp dev eth0                    # 摘除（程序仍在内核）
rm /sys/fs/bpf/hello                               # 删 pin 文件 = 卸载

prog show 关键字段： | 字段 | 含义 | |------|------| | id | 加载时分配，进程内唯一 | | tag | 指令的 SHA 哈希——同一程序重加载 tag 不变（id 会变） | | bytes_xlated | 过验证器（可能被内核改写）后的字节码字节数 | | bytes_jited / jited | JIT 后机器码字节数（例：96B 字节码 → 148B 机器码） | | memlock | 锁定内存（不会被换出）——eBPF 内存必须常驻 | | map_ids | 关联的 map（本例源码没有 map 却有 2 个——见全局变量） | | btf_id | 有 BTF 信息块（-g 编译才有） |

程序引用四方式：id / name / tag / pinned path。name 和 tag 可重复，id 和 pin 路径唯一。

bpftool prog dump xlated 看验证后字节码（与 llvm-objdump 基本一致）；dump jited 看机器码（需要 bpftool 编译时带 libbfd）。

XDP 事件的上下文特殊性：trace 输出行首是 <idle>-0——包到达时没有任何用户态进程与之关联（第 2 章 syscall 事件则有 pid/comm）。这解释了为什么网络类程序拿不到 bpf_get_current_pid_tgid() 的有效值。

3.5 全局变量 = map

2019 年（5.10 前后）起支持全局变量，实现就是 map——编译器/加载器把 ELF 的数据段变成特殊 array map，全局变量读写被改写为 map 访问：

ELF 段 map 形态 内容 初始化
hello.bss array map，1 项 初始化为 0 的全局变量（int counter） 加载时内核清零
hello.data array map，1 项 初始化为非 0 的全局变量 加载时从 ELF 拷入
hello.rodata array map，1 项，frozen 只读数据（格式串 "Hello World %d"） 加载时冻结，之后写会被拒

（Hello World 例子里 counter 是 0 初始化 → .bss；格式串是 const → .rodata——所以源码没写 map，bpftool prog show 却关联了 2 个 map。3.4 自测题 3 的答案。）

性能要点：全局变量虽然实现为 map，但 verifier/JIT 会把它优化成直接内存访问（map value 地址在加载时已确定，指令里就是 ldimm64 r6, <地址> + 普通访存）——不走 bpf_map_lookup_elem helper，无哈希查找开销。内核态全局变量的读写成本 ≈ 普通内存访问，这是 eBPF 里最便宜的持久状态。

有 BTF（编译加 -g）时 bpftool map dump name hello 能漂亮打印变量名和值；没有则只能看裸十六进制（19 01 00 00 = 小端 281）——BTF 是"map 的元数据"，第 5 章 CO-RE 的地基。

pin 机制：bpffs（/sys/fs/bpf/）上的伪文件持有程序/map 的引用；删除文件即释放（没有 bpftool prog unload 命令时用 rm）。用户态程序退出后，pinned 的程序仍留在内核。pin 是路径即引用的设计——把"内核对象的生命周期"映射成"文件系统的生命周期"，运维语义友好（ls 看得见、rm 能删、重启清空）。

3.6 BPF to BPF 调用（libbpf 才有）

static __attribute((noinline)) int get_opcode(struct bpf_raw_tracepoint_args *ctx) {
   return ctx->args[1];
}
SEC("raw_tp")
int hello(struct bpf_raw_tracepoint_args *ctx) {
   int opcode = get_opcode(ctx);
   bpf_printk("Syscall: %d", opcode);
   return 0;
}

字节码里 call pc+7 跳到子程序偏移 8 处——真实函数调用，非内联（编译器默认会把小函数内联掉，noinline 仅为演示；生产代码让编译器自行决定）。函数调用要把状态压栈以便返回，而栈只有 512 字节（MAX_BPF_STACK，include/linux/filter.h:90）→ 嵌套深度受限（经验上 5 层左右就要掂量了，每层还要留局部变量空间）。

尾调用 vs 子程序对照（与 2.2 呼应）：

维度 BPF-to-BPF 调用 尾调用
字节码 call pc+N（相对偏移） call imm=2（特殊操作码）+ PROG_ARRAY 查表
栈 消耗：子函数栈叠在调用者之上 替换：被调程序从零开始，调用者栈作废
能否返回 能（拿返回值继续） 永不返回（类比 execve 替换进程映像）
深度上限 512B 栈间接限制（几层） 33 层（MAX_TAIL_CALLS）
跨程序共享状态 栈上传递即可 只能走 map
组合 5.10 起两者可混用（先子调用再尾调用出去） 同左

选型直觉：要复用代码片段、拿返回值 → 子程序；要"接力棒式"串起不同策略的阶段 → 尾调用 + PROG_ARRAY（策略做成数据）。

3.7 坑点清单

  1. XDP 返回 0 = XDP_ABORTED ≠ 成功——返回 0 挂到 eth0 会丢掉所有包，SSH 直连机器直接失联。五种返回码（ABORTED=0/DROP=1/PASS=2/TX=3/REDIRECT=4，v6.6 bpf.h 核对）与直觉相反：C 语言的"0=成功"惯性在这里是毒。测试 XDP 放容器/虚拟网卡里（参考 lizrice/lb-from-scratch），物理网卡上先 XDP_PASS 起步再逐步加逻辑
  2. 忘了 SEC("license") 或用了 GPL-only helper 却声明专有许可 → 验证器拒绝（bpf_probe_read_kernel 等全是 GPL-only；LSM 程序整体必须 GPL 兼容）
  3. 编译不加 -g：没 BTF → bpftool 无法漂亮打印、CO-RE 不可用（第 5 章）、验证器日志里没有 C 源码行——排错成本直接翻倍
  4. bpftool 必定 pin；忘删 pin 文件 = 程序滞留内核（重启前一直占 memlock 内存），下次 load 同名路径会报"File exists"
  5. net.core.bpf_jit_enable sysctl / CONFIG_BPF_JIT 控制 JIT——性能测试前先确认开着（bpftool prog list 看 jited 标志）；解释执行的吞吐差一个量级，还带着 Spectre 侧信道风险
  6. tag 与 id 的区别：tag 跟着内容走（指令的 SHA 哈希，内容变 tag 变），id 跟着加载实例走（每次加载新分配）。同一程序重加载：tag 不变、id 变——CI 里做"程序是否真的是这版"的校验用 tag

3.8 HFT 关联

1. bpftool prog dump jited = eBPF 侧的"反汇编确认"

交易热路径调优时你会反汇编二进制确认编译器没自作聪明；eBPF 侧同理——验证器会改写字节码（如把全局变量访问重定位成绝对地址、dead code 消除），JIT 再翻译成机器码。"我写的源码"和"CPU 执行的机器码"之间有两层改写，性能异常时 dump jited 是唯一真相。bytes_xlated/bytes_jited 两个数字（3.2）先看规模是否合理。

2. memlock 常驻内存：与 mlockall 哲学天然一致

eBPF 程序和数据锁定内存、永不换页——交易机把策略进程 mlockall 防缺页尖刺，eBPF 观测程序天然享受同等待遇，观测层自己不会成为缺页抖动源。memlock rlimit（老内核）或 memcg 计费（新内核）要注意额度。

3. XDP 卸载 = 行情前置过滤的理论最优层

包在进主机内存之前就被网卡处理——比 DPDK 少一次 DMA、比 tc-BPF 更早。交易机网口的"非行情流量 early drop"（心跳风暴、异常广播）放这层做，CPU 完全无感。限制：offload 只支持 helper 子集、网卡固件版本绑定（换网卡=回归测试）。

4. 512B 栈 → 观测探针的"薄"是强制的

2.3 已论证：小栈强制薄探针、测量工具越薄数据越可信。本章补充：复杂逻辑的正确去处是用户态（内核只做"取时间戳+写 map"），子程序/尾调用是"复用与接力"的组织手段，不是"塞复杂逻辑"的许可。

5. 读字节码是验证器日志的前置技能

第 6 章验证失败报的全是指令偏移（0: (bf) r6 = r1）——不会读字节码就只会对着报错发呆。3.2 的反汇编精读 + 宽指令占两槽的细节（offset 0 的下一条在 2）是基础功。

  6. 为什么 trace 输出显示 <idle>-0？这反映 XDP 事件的什么特性？
参考答案

1. R0=返回值（helper 返回 + 程序返回码共用）；R1–R5=函数调用参数（最多 5 个），R1 兼任程序入口的 ctx 指针；R6–R9=跨 helper 调用保持（callee-saved，所以入口先 r6 = r1 备份 ctx）；R10=栈帧指针（只读，512B 栈的底）。寄存器模型与 x86-64 ABI 刻意同构，JIT 近乎直译。

2. bpf_insn 的 imm 字段只有 32 位，装不下 64 位立即数（如全局变量的内核态地址）→ ldimm64 占两个指令槽（16 字节），反汇编里 offset 0 的下一条指令在 offset 2。

3. 全局变量实现为 map：counter（0 初始化）→ .bss 段 map；格式串（const）→ .rodata 段 map（frozen）。源码没写 map，但 ELF 段被加载器变成了 2 个 array map。

4. id 和 pinned path 唯一；name 和 tag 可重复（不同进程可加载同名程序、相同内容程序 tag 相同）。

5. 字节码层：子程序是 call pc+N 相对偏移跳转、正常函数调用；尾调用是特殊操作码 + PROG_ARRAY 查表替换。栈：子程序叠在调用者栈上、可返回（受 512B 总量限制，几层就满）；尾调用替换调用者、栈从零开始、永不返回（33 层上限）。5.10 起可混用。

6. 包到达网卡入口时没有任何进程与之关联——XDP 在驱动层触发，早于中断/软中断分配给任何 socket，bpf_get_current_pid_tgid() 返回的是当时 CPU 上恰好在跑的（无关）任务，通常是 idle。这解释了网络类程序为何不能按"当前进程"过滤。
