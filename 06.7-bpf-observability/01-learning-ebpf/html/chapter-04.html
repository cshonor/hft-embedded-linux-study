4.1

bpf总览与strace实例（原书 §4.1–4.2）

合并自原 section-1～2。文件名序号是合并后的笔记序号；正文小节标题沿用原书节号，历史 § 引用依然有效。

4.1 bpf() 总览

int bpf(int cmd, union bpf_attr *attr, unsigned int size);
  • cmd：要执行的命令（BPF_MAP_CREATE、BPF_PROG_LOAD…全量清单在 linux/bpf.h，内核源码是最好文档）
  • attr：命令参数（联合体，各命令用不同字段）
  • size：attr 字节数

关键分层：内核里的 eBPF 程序访问 map 不走 syscall（用 helper 函数）；syscall 接口只属于用户态。库（BCC/libbpf）的抽象与这些命令几乎一一对应。

4.2 strace 实例全景（hello-buffer-config.py）

bpf(BPF_BTF_LOAD, ...)                         = 3   # 加载 BTF 数据 → fd 3
bpf(BPF_MAP_CREATE, {PERF_EVENT_ARRAY ...})    = 4   # output perf buffer → fd 4
bpf(BPF_MAP_CREATE, {HASH, key 4B, value 12B,
     max_entries=10240, btf_fd=3})             = 5   # config 哈希表 → fd 5
bpf(BPF_PROG_LOAD, {KPROBE, insn_cnt=44,
     insns=..., license="GPL", prog_btf_fd=3}) = 6   # 程序 → fd 6（验证失败返回负值）
bpf(BPF_MAP_UPDATE_ELEM, {map_fd=5, ...})      = 0   # 写 config 表项

各字段细节： - BPF_BTF_LOAD：跨内核版本可移植的类型信息（第 5 章）；老内核看不到这条 - config map 的 key_size=4（u32 存 UID）、value_size=12（user_msg_t）、max_entries=10240 是 BCC 默认值（源码没写就是它） - btf_fd=3 让 bpftool 能漂亮打印 key/value 结构 - insn_cnt：字节码指令条数 - expected_attach_type=BPF_CGROUP_INET_INGRESS 看着像网络程序？其实该字段只对部分程序类型有意义，kprobe 不用；这个值只是枚举表第一个（=0）的默认占位 - 文件描述符是进程私有的：hello 程序里 fd 5 = config map，bpftool 里同一 map 可能是 fd 3

真机佐证（lab04 · 树莓派 5 / 6.18 / libbpf 1.5，2026-08-30）

用 libbpf 写等价程序（config + counts 双 HASH）跑 strace，实测 lab04：

① 序列骨架与书一致，但信噪比 1:9。 一次最小加载共 50 个 bpf() 调用，其中真活儿只有：BTF_LOAD ×1、MAP_CREATE ×2、PROG_LOAD ×1、（attach）、MAP_UPDATE_ELEM ×1 + dump 的 GET_NEXT_KEY/LOOKUP ×27；其余全是 libbpf 的特性探测（1.6ms 内跑完，失败是常态——"问内核你行不行"，不行就走旧路径）。探测项包括 BPF_TOKEN_CREATE（EOPNOTSUPP）、dummy PROG_LOAD、带 target_fd=-1 的 BPF_LINK_CREATE（故意 EBADF）。

② "无 BTF 内核"照样有 BPF_BTF_LOAD 且成功。 /sys/kernel/btf/vmlinux 不存在 ≠ 不能加载 BTF blob：内核只是没有自己的类型信息（CO-RE 不可用），但 MAP_CREATE 带 btf_fd=3, btf_key_type_id=8 全部生效。书里"老内核看不到这条"指的是不支持 BPF_BTF_LOAD 的内核（<5.0），不是没有 vmlinux BTF 的内核。

③ 挂载是现代三步走：perf_event_open(tracepoint id 652) → BPF_LINK_CREATE(attach_type=BPF_PERF_EVENT) → ioctl(PERF_EVENT_IOC_ENABLE)。link 是有 fd 的一等对象，不是老的 ioctl(PERF_EVENT_IOC_SET_BPF)。

④ fd 陷阱：MAP_CREATE 返回 6，UPDATE 却用 map_fd=4——libbpf 用 memfd_create("libbpf-placeholder-fd") 预留低位 fd 槽位，真实 map fd 经 dup3 顶进槽位。只看过滤后的 strace 会以为 fd 乱跳，必须看全量。

⑤ 真实 PROG_LOAD 确认 expected_attach_type=BPF_CGROUP_INET_INGRESS 出现在 tracepoint 程序上（枚举 0 占位），与上文判断一致。

对象生命周期与kprobe挂载（原书 §4.3–4.4）

合并自原 section-3～4。文件名序号是合并后的笔记序号；正文小节标题沿用原书节号，历史 § 引用依然有效。

4.3 BPF 对象生命周期：引用计数

规则：引用计数归零 → 内核删除对象（程序和 map 同一套规则）。计数来源：

  1. fd：用户态进程持有；进程退出即释放（这就是 BCC 程序 Ctrl+C 后程序消失的原因）
  2. pin 到 bpffs：/sys/fs/bpf/ 伪文件系统（内存态，重启即失）；bpftool prog load 必须指定 pin 路径，否则它退出时程序立刻被删，加载毫无意义
  3. 挂到 hook：附加本身也计引用 - 追踪类（kprobe/tracepoint）与用户态进程绑定，进程退即减 - 网络栈/cgroup 类不绑定进程——ip link set dev eth0 xdp obj ... 命令退出后程序仍在
  4. BPF link：程序与事件之间的抽象层，link 自身可 pin；加载器进程退出后程序靠 link 的引用活着。libbpf 默认走 bpf(BPF_LINK_CREATE)（4.1 真机佐证：现代三步走 = perf_event_open → BPF_LINK_CREATE → ioctl ENABLE，link 是有 fd 的一等对象）

四类来源一张图：

bpf_prog 对象
  ├─ ref: fd（进程退出 → 减）
  ├─ ref: hook 附加点（detach → 减；网络类不随进程走）
  ├─ ref: link 对象（link 可 pin，link 活 → 程序活）
  └─ ref: bpffs pin 文件（rm → 减）
任何时刻计数 = 0 → 内核释放

为什么要设计 link：老机制（ioctl SET_BPF 直接绑）把"附加关系"埋在 perf 事件内部，没有独立对象——不能单独管理、不能 pin、替换程序要拆事件。link 把附加关系本身变成一等公民：可以 pin 到 bpffs（加载器死了附加还在）、可以原子替换（BPF_LINK_UPDATE，探针热升级不丢事件）、可以查询（bpftool link show）。

补充：BPF_PROG_BIND_MAP 把 map 绑到程序（程序源码定义了却没用到的 map——如存放元数据的全局变量 map——不会被自动引用，需显式绑定防清理）。maps 同样有引用计数与 pin 能力。

4.4 挂 kprobe：bpf() 之外的三件套

挂 kprobe 不用 bpf()：

perf_event_open({type=6, ...})          = 7   # kprobe 也是一种 perf PMU 事件！
ioctl(7, PERF_EVENT_IOC_SET_BPF, 6)     = 0   # 把程序 fd 6 绑到 kprobe 事件 fd 7
ioctl(7, PERF_EVENT_IOC_ENABLE, 0)      = 0   # 使能
  • type=6 来自 /sys/bus/event_source/devices/kprobe/type——kprobe 是动态注册的 PMU（perf 子系统本身就是 eBPF 的宿主基础设施）。perf_event_open 的 type 参数本意是选硬件 PMU（cpu cycles 等），kprobe 复用这套框架把自己注册成一个"事件源"——eBPF 追踪与 perf 剖析共享同一套事件基础设施，这不是偶然而是设计
  • 对照：raw tracepoint 挂载就一条 bpf(BPF_RAW_TRACEPOINT_OPEN, {name="sys_enter", prog_fd=6})；cgroup 程序用 bpf(BPF_PROG_ATTACH)；现代 libbpf 对 kprobe 也走 BPF_LINK_CREATE。附加机制因程序类型而异——没有统一的"attach"syscall
  • 这三件套正是 [03-linux-userspace-api perf_event_open 章节]（TLPI/perf 篇）的路径：ioctl 管 fd 的 enable/disable 状态，perf_event_open 造事件——学过 perf 子系统再读这组 strace 会心一笑

排错应用：strace -e bpf,perf_event_open,ioctl 一个不漏地看加载器实际发了什么——BPF_PROG_LOAD 返回负值=验证失败（看 stderr 日志），perf_event_open 返回 ENOENT=符号不存在（kprobe 挂了被内联/改名的函数），BPF_LINK_CREATE 返回 EBADF=fd 已失效。三段各对应一类失败。

衔接：perf buffer 与 ring buffer 的初始化 syscall 细节 → 4.3；map 遍历序列 → 4.4；坑点与 HFT → 4.5。

4.5 perf buffer 初始化：为什么是每核一个

每颗 CPU 核执行一轮：

perf_event_open({PERF_TYPE_SOFTWARE, config=PERF_COUNT_SW_BPF_OUTPUT, ...}, -1, X, ...)
                                        # pid=-1, cpu=X → 测量该核上所有进程
ioctl(Y, PERF_EVENT_IOC_ENABLE)
bpf(BPF_MAP_UPDATE_ELEM, {map_fd=4, ...})   # map 第 X 项指向该核的 perf 缓冲

四核机器 = 4 轮 = PERF_EVENT_ARRAY 里 4 个条目——"array" 就是每核一缓冲的数组。之后用户态用 ppoll() 同时等 4 个 fd，哪个核触发读哪个。

为什么必须每核一个：perf buffer 是无锁环形缓冲，单缓冲多核同写必然加锁/争用——每核独立缓冲让内核侧写入零锁（事件在哪个核发生就写哪个核的缓冲，天然无竞争），代价转嫁给用户态（要聚合多个 fd）。这与 2.3 的 per-CPU map 是同一设计哲学：把同步成本从热路径挪到冷路径。

PERF_EVENT_ARRAY 的条目数 = 核数（不是随便定的 max_entries）——这也是 4.5 坑点 里"perf buffer 事件跨核乱序"的根源：各核独立缓冲，用户态聚合时的到达顺序与真实时间序无关。

4.6 Ring buffer：单缓冲 + epoll

BPF_MAP_CREATE 一条搞定（key_size=0, value_size=0, max_entries=4096），无每核 setup。

维度 perf buffer（每核一个） ring buffer（全局一个）
缓冲数量 N 核 N 个 1 个（内部按页对齐的 reserve 区域）
内核侧写 零锁（每核私有） 零锁（reserve/commit 两阶段，跨核靠原子操作）
内存效率 每核固定预算，核多浪费 按需 reserve——大事件不必适配每核页大小，整体利用率高
跨核顺序 无保证（各核独立） 提交保序（commit 时间戳定序）
用户态等待 ppoll 等 N 个 fd epoll 等 1 个 fd
内核版本 4.x 起广泛可用 5.8+

ring buffer 的两阶段提交是关键设计：bpf_ringbuf_reserve() 在环形区里划一块（此时别的核 reserve 别的区域，无锁），填完数据 bpf_ringbuf_submit() 才让它对消费者可见——"写数据"和"发布"分离，用户态永远只看到完整事件，杜绝读到半截数据。丢弃路径用 discard() 静默归还。

等待机制从 ppoll 升级为 epoll：

epoll_create1(EPOLL_CLOEXEC)                       = 8   # 内核里建一个 epoll 实例
epoll_ctl(8, EPOLL_CTL_ADD, 4, {EPOLLIN})          = 0   # 把 ringbuf fd 4 加入集合
epoll_pwait(8, ...)                                 # 阻塞等数据

ppoll 每次返回都要重新传整个 fd 集合（用户态→内核态拷贝 + 内核线性扫描）；epoll 的 fd 集合由内核对象持有，注册一次即可，就绪回调挂到 fd 上——fd 数量大时差距是 O(n) vs O(1)。（与 03.5/04-cpp 网络编程模块里 poll vs epoll 的对比完全同源；3.3-3.4 里 epoll 作为 Linux 里程碑的 O(1) 论述也在此落地。）

选型结论：新内核（5.8+）一律 ring buffer——内存省、保序、等待简单；perf buffer 只在老内核或工具链绑定 BCC 老范式时出现。需要时间序的事件流（延迟分布、事件序列重建）ring buffer 是硬需求。

衔接：用户态读 map 的完整 syscall 序列 → 4.4；本章坑点与 HFT → 4.5。

4.7 遍历 map：bpftool map dump 的 syscall 序列

找 map（对每个已加载 map 重复三连）：

bpf(BPF_MAP_GET_NEXT_ID, {start_id=N})     # 下一个 map id
bpf(BPF_MAP_GET_FD_BY_ID, {map_id})        # 换 fd
bpf(BPF_OBJ_GET_INFO_BY_FD, {...})         # 拿名字比对；无更多 map 时 GET_NEXT_ID 返回 ENOENT

读元素（迭代键值对）：

bpf(BPF_MAP_GET_NEXT_KEY, {key=NULL, next_key=...})   # key=NULL → 第一个有效键
bpf(BPF_MAP_LOOKUP_ELEM, {map_fd, key, value})        # 取值
... 循环直到 GET_NEXT_KEY 返回 ENOENT

配套还有 BPF_MAP_DELETE_ELEM（删除）。

两段式的架构含义：

  1. id 空间是全局的，fd 是进程私有的——跨进程引用内核对象必须经"id → fd"翻译（BPF_MAP_GET_FD_BY_ID），这正是 4.5 坑点 1 的机制根源。这套 GET_NEXT_ID / GET_FD_BY_ID / OBJ_GET_INFO_BY_FD 三连对所有 BPF 对象通用（prog/link 同样有 GET_NEXT_ID）——bpftool prog list、bpftool link list 都是这个模式的复读
  2. GET_NEXT_KEY 的 key=NULL 约定：传 NULL 表示"给我第一个键"，返回 ENOENT 表示"没有下一个了"——迭代器协议用两条 syscall 表达（cursor 由内核从 key 本身推导，不单独存游标）。hash map 的遍历顺序无序（哈希桶序），array map 是索引序——依赖遍历顺序的代码已经错了
  3. LOOKUP 是拷贝语义：value 从内核拷到用户态缓冲——读大 value（如整个直方图桶数组）时这是一次 memcpy，高频轮询采集要掂量

为什么 libbpf 程序不走这条路：加载器自己持有 fd（MAP_CREATE 的返回值），不需要 id 查找——id 三连是第三方工具发现别人的 map 的路径。自己的程序读写自己的 map 用 bpf_map_lookup_elem() 库函数（内部就是 BPF_MAP_LOOKUP_ELEM syscall），dump 序列只在调试和监控 agent 里出现。

BPFTOOL 之外的等价物：/proc 没有暴露 map 内容（不像中断有 /proc/interrupts）——map 内容的唯一系统级访问路径就是这套 syscall。想在 Prometheus exporter 里暴露 eBPF 指标，就是循环 GET_NEXT_KEY + LOOKUP。

完整示例：strace 下的 bpftool map dump name config

# 阶段一：id 空间扫描（每个 map 三连，直到 ENOENT）
bpf(BPF_MAP_GET_NEXT_ID, {start_id=0})        = 4    # 第一个 map id
bpf(BPF_MAP_GET_FD_BY_ID, {map_id=4})         = 5    # → fd 5（本进程的）
bpf(BPF_OBJ_GET_INFO_BY_FD, {info={...}})     = 0    # name="counts"，不是目标，继续
bpf(BPF_MAP_GET_NEXT_ID, {start_id=4})        = 5
bpf(BPF_MAP_GET_FD_BY_ID, {map_id=5})         = 6    # → fd 6
bpf(BPF_OBJ_GET_INFO_BY_FD, {info={...}})     = 0    # name="config"，命中！保留 fd 6
bpf(BPF_MAP_GET_NEXT_ID, {start_id=5})        = -1 ENOENT   # id 空间到头，扫描结束

# 阶段二：键值迭代（游标即 key）
bpf(BPF_MAP_GET_NEXT_KEY, {map_fd=6, key=NULL, next_key=...}) = 0   # NULL → 第一个键
bpf(BPF_MAP_LOOKUP_ELEM, {map_fd=6, key=0x..., value=0x...})  = 0   # 取值
bpf(BPF_MAP_GET_NEXT_KEY, {map_fd=6, key=0x..., next_key=...}) = 0  # 当前键 → 下一个
bpf(BPF_MAP_LOOKUP_ELEM, ...)                                 = 0
bpf(BPF_MAP_GET_NEXT_KEY, ...)                                = -1 ENOENT  # 迭代结束

迭代语义的三个细节（读这段 strace 时容易看漏）：

细节 语义 后果
key=NULL 起步 "给我第一个键" 空表时第一条 GET_NEXT_KEY 就 ENOENT（不是错误）
next_key 回填到用户缓冲 游标就是 key 本身 迭代中被删的键：GET_NEXT_KEY 以旧 key 为锚找后继，删除不影响迭代推进
顺序未定义（hash map） 桶序而非插入序 依赖顺序的代码已经错了；array map 是索引序

与 LOAD/CREATE 序列的关系（把第 4 章串起来）：

自己程序读写自己的 map      BPF_MAP_CREATE 返回的 fd 直用     [4.1 strace 实例]
第三方工具发现别人的 map     GET_NEXT_ID → GET_FD_BY_ID 三连   本节
挂到 perf/ringbuf 的事件通道  MAP_UPDATE_ELEM 指向 perf buffer   [4.3]

三个场景三套序列——fd 私有性决定了"是谁的 map"决定"怎么访问它"。

性能直觉：一次 dump = O(条目数) 次 syscall（每条目两个：NEXT_KEY + LOOKUP）——十万条目的 map dump 要二十万次系统调用，秒级耗时。监控 agent 高频轮询大 map 的正确姿势：内核侧定期聚合（hist map 自带桶），用户态只 LOOKUP 聚合结果，而不是逐条目拉原始事件。

衔接：map 的创建/更新在 4.1 strace 实例；本章坑点与 HFT → 4.5。

4.8 坑点清单

  1. fd 是进程私有的——跨进程传 fd 数字没有意义（同一 map 两个进程 fd 值不同）。跨进程引用必须走 id 空间：BPF_MAP_GET_FD_BY_ID 翻译（4.4）；libbpf 还有基于 pin 路径的 bpf_obj_get()——路径是跨进程的稳定名字
  2. bpffs 是内存伪文件系统：重启后 pin 的程序全部消失，开机自启要靠 systemd/skeleton 重载——"部署"一个 eBPF 程序 = 二进制 + 重载机制，缺一不可
  3. BCC 程序 Ctrl+C 程序即卸载；想持久必须 pin 程序（或用 libbpf 的 link pin）——调试工具"随用随走"是特性，常驻 agent"必须 pin"是纪律
  4. strace 里 expected_attach_type 出现网络类值不代表程序是网络程序（默认 0 占位，恰好是 BPF_CGROUP_INET_INGRESS 的枚举值）——4.1 真机佐证 ⑤ 确认该字段只对部分程序类型有意义
  5. perf buffer 每核一缓冲，事件跨核乱序；需要时间序就用 ring buffer（5.8+）——乱序不是 bug 是 per-CPU 设计的代价，见 4.3 对比表
  6. max_entries=10240 这种"魔法数字"是 BCC 默认，生产要显式设定——容量规划：条目数 × value 大小 × 2（hash 负载因子）就是内存预算
  7. （真机补充，lab04）libbpf 的 fd 陷阱：MAP_CREATE 返回 6、UPDATE 却用 map_fd=4——libbpf 用 memfd 预留低位 fd 槽位再 dup3 顶进；只看过滤后的 strace 会以为 fd 乱跳，必须看全量

4.9 HFT 关联

1. 这一章就是"eBPF 的 TLPI 时刻"

与 03-linux-userspace-api 模块学 perf_event_open/ioctl 的路径打通——eBPF 追踪复用 perf 子系统的基础设施（kprobe 是动态注册的 PMU），理解 perf_event_open 的 type/config/pid/cpu 四元组才能理解 kprobe 挂载为何长那样。系统调用的知识在 eBPF 这里直接变现。

2. ring buf + epoll 是用户态收集内核事件的标准范式

与行情网关的 epoll 收包同构（同一套 fd 事件驱动模型）。跨核保序对延迟直方图/事件序列重建至关重要：perf buffer 各核独立缓冲，聚合时"到达序"≠"发生序"——重排两个事件的先后，延迟归因就南辕北辙。5.8+ 内核上 ring buffer 是唯一正确选择。

3. 引用计数的 pin 机制用于常驻观测 agent

交易机上 eBPF 监控随开机加载、独立于加载器进程存活——机器重启自动重载需要落地为 systemd unit（OnFailure 重试 + ExecStartPre 检查内核版本）。"程序活着"的三重保障：link pin（附加关系）+ map pin（状态数据）+ systemd（重载入口）。

4. strace -e bpf 是排查"eBPF 工具为何加载失败"的第一工具

看 BPF_PROG_LOAD 返回值即知验证是否通过（负值=失败，stderr 有验证器日志）；perf_event_open 返回 ENOENT=kprobe 符号不存在；BPF_LINK_CREATE 返回 EPERM=权限不足。比"工具报了个错"的黑盒信息量大一个数量级——先 strace 再 Google 的纪律在 eBPF 侧同样成立。

5. dump 序列是监控 agent 的实现路径

Prometheus exporter 暴露 eBPF 指标 = GET_NEXT_KEY + LOOKUP 循环（4.4）——LOOKUP 是拷贝语义，大 value 高频轮询有成本，采集间隔要和直方图聚合窗口匹配。

4.10 自测题

  1. bpf() 三个参数各是什么？内核里的 eBPF 程序访问 map 走什么路径？
  2. BPF 对象的引用计数有哪四种来源？追踪类与网络类程序的差异？
  3. 挂 kprobe 需要哪三个 syscall（按序）？为什么挂 raw tracepoint 只需一条 bpf()？
  4. PERF_EVENT_ARRAY 里的条目数由什么决定？ring buffer 为何没有这个问题？
  5. ppoll 和 epoll 管理 fd 集合的本质区别？
  6. bpftool map dump name config 在找 map 和读元素两个阶段各用什么命令迭代？
参考答案

1. int bpf(int cmd, union bpf_attr *attr, unsigned int size)——cmd 是命令（MAP_CREATE/PROG_LOAD/…），attr 是联合体参数，size 是 attr 字节数。内核里的 eBPF 程序访问 map 不走 syscall，走 helper 函数（bpf_map_lookup_elem() 编译成 call imm=<helper号>）；syscall 接口只属于用户态。

2. 四种来源：①fd（进程退出即减）、②bpffs pin 文件（rm 即减）、③hook 附加（detach 即减）、④BPF link（link 活着程序就活）。差异：追踪类附加与用户态进程绑定（perf_event_open 的 fd 进程退出即失效）；网络栈/cgroup 类不绑定进程（ip link 挂的 XDP 命令退出后仍在）。

3. perf_event_open({type=kprobe_PMU}) → ioctl(fd, PERF_EVENT_IOC_SET_BPF, prog_fd) → ioctl(fd, PERF_EVENT_IOC_ENABLE)。raw tracepoint 一条 bpf(BPF_RAW_TRACEPOINT_OPEN) 搞定——因为 kprobe 是动态注册的 perf PMU 事件（复用 perf 子系统），而 raw tracepoint 的挂点是内核静态注册的，BPF syscall 能直接定位。

4. 条目数 = CPU 核数（每核一个 perf 缓冲，key 是 CPU id）。ring buffer 全局单缓冲（内部 reserve/commit 两阶段），无每核概念——所以也没有 perf buffer 的跨核乱序问题（提交保序）。

5. ppoll 每次调用把整个 fd 集合从用户态拷进内核、返回后再拷回就绪集合（O(n) 每次扫描）；epoll 的集合由内核对象持有（epoll_ctl 注册一次），就绪 fd 通过回调挂链表，epoll_wait 只取链表（O(1)）。

6. 找 map 阶段：BPF_MAP_GET_NEXT_ID（下一个 id）+ BPF_MAP_GET_FD_BY_ID（换 fd）+ BPF_OBJ_GET_INFO_BY_FD（拿名字比对），ENOENT 终止。读元素阶段：BPF_MAP_GET_NEXT_KEY（key=NULL 起步，游标即 key 本身）+ BPF_MAP_LOOKUP_ELEM，ENOENT 终止。
