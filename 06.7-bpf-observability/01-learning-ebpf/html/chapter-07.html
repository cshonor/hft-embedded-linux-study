7.1

程序类型全景（原书 §7.1–7.3）

合并自原 section-1～3。文件名序号是合并后的笔记序号；正文小节标题沿用原书节号，历史 § 引用依然有效。

7.1 程序类型决定什么

程序类型 ──→ 可附加的事件
        ──→ 上下文参数的结构（每个 eBPF 程序都收到一个 ctx 指针，指向什么取决于事件）
        ──→ 可用的 helper 函数集合（验证器按此检查，第 6 章）
        ──→ 返回码的含义（XDP：放行/丢包/重定向；追踪类：被忽略；LSM：非零=拒绝操作）
  • 附加类型（attachment type）更细粒度指定挂点；多数程序类型可从程序类型推断附加类型，少数（如 CGROUP_SOCK）必须显式指定（内核 bpf_prog_load_check_attach、bpf/syscall.c 可查全集）
  • helper 函数属于 UAPI 稳定接口：一经定义不再变化（即使内核内部函数/结构可以变）
  • kfunc：把内核内部函数注册给 BPF 子系统供调用。与 helper 不同，无兼容性保证，跨内核版本要自己担风险；现有"核心" kfuncs 主要是获取/释放 task 和 cgroup 引用
  • bpftool feature 可列出当前内核每种程序类型支持的 helper
  • 权限：追踪类需要 CAP_PERFMON + CAP_BPF 或 CAP_SYS_ADMIN；网络类需要 CAP_NET_ADMIN + CAP_BPF 或 CAP_SYS_ADMIN

7.2 追踪类（perf-related）

设计初衷：把事件信息高效报告给用户态，不影响内核行为（返回码被忽略）。bpftool perf show 可查看 perf 类挂载（pid/fd/prog_id/类型/函数名）。

2.1 五种 execve 入口挂法对比（本章核心实验）

同一事件的五种程序，全在 chapter7/hello.bpf.c：

挂法 SEC 名 宏 上下文
syscall kprobe ksyscall/execve BPF_KPROBE_SYSCALL(name, char *pathname) syscall 参数（稳定接口）
内核函数 kprobe kprobe/do_execve BPF_KPROBE(name, struct filename *filename) 内核函数参数
fentry fentry/do_execve BPF_PROG(name, struct filename *filename) 内核函数参数
tracepoint tp/syscalls/sys_enter_execve 手写结构体 从格式文件映射好的结构
BTF tracepoint tp_btf/sched_process_exec BPF_PROG(...) vmlinux.h 里的 trace_event_raw_* 结构

2.2 kprobe 要点

  • 几乎可挂内核任何位置（黑名单除外：/sys/kernel/debug/kprobes/blacklist）；可挂函数入口、也可挂"入口+N 条指令"的偏移处——但任意偏移在版本间极不稳定，别这么干
  • 被内联的函数没有 kprobe 入口点
  • syscall 入口是稳定接口；但基于 syscall kprobe 的探针不能当安全工具用（可被绕过，第 9 章详述）
  • 挂普通内核函数时，参数类型要照抄内核函数签名（do_execve(struct filename *filename, ...)）——参数按内存顺序排列，可忽略尾部参数，不能跳过前面的
  • kretprobe 挂函数返回处，只能拿到返回值 ret，拿不到入参

2.3 fentry/fexit（5.5 引入，x86；ARM 要 6.0）

  • 基于 BPF trampoline，比 kprobe/kretprobe 更高效——新内核上的首选
  • BPF_PROG 宏适用于 fentry / fexit / tracepoint
  • 关键优势：fexit 同时能拿入参和返回值（kretprobe 只有返回值）：
SEC("kretprobe/do_unlinkat")
int BPF_KRETPROBE(do_unlinkat_exit, long ret)                 // 只有 ret

SEC("fexit/do_unlinkat")
int BPF_PROG(do_unlinkat_exit, int dfd, struct filename *name, long ret)  // 全都有

2.4 tracepoint 要点

  • 内核代码里静态标记的位置（早于 eBPF 存在，SystemTap 也用）；版本间稳定；5.15 内核有 1400+ 个
  • 清单：/sys/kernel/tracing/available_events；格式：/sys/kernel/tracing/events/<子系统>/<事件>/format
  • 手写上下文结构要照抄 format 文件（offset/size 对齐）；前 4 个公共字段（common_type 等）不允许访问，否则 invalid bpf_context access
  • raw_tp：跳过参数映射直接拿原始 __u64 参数，更快但要自己做类型转换（syscall 入口参数还与架构相关）
  • tp_btf：BTF 自动提供匹配结构（trace_event_raw_<事件名>，vmlinux.h 里），免手写、免版本漂移风险——首选

2.5 用户态挂点

uprobe / uretprobe / USDT 都用 BPF_PROG_TYPE_KPROBE 程序类型：

SEC("uprobe/usr/lib/aarch64-linux-gnu/libssl.so.3/SSL_write")

典型应用：钩 SSL 库输出解密后的明文（第 8 章）、Parca 持续 profiling。

四大约束： 1. 共享库路径架构相关 2. 目标机器装了什么库不可控 3. 应用可能静态链接（共享库探针全 miss）；容器内库路径与宿主机不同 4. 语言调用约定差异：C 参数走寄存器，Go 1.17 之前参数走栈——pt_regs 取参对老 Go 二进制无效

2.6 LSM

  • BPF_PROG_TYPE_LSM 挂 Linux Security Module API（稳定接口，原本给内核模块用）；经 bpf(BPF_RAW_TRACEPOINT_OPEN) 附加
  • 与追踪类的本质区别：返回码影响内核行为——非零 = 安全检查不通过，内核拒绝该操作（第 9 章）

7.3 网络类

与追踪类的本质区别：定制行为而非观察——(1) 返回码决定包的去向（正常处理/丢弃/重定向）；(2) 可修改网络包、socket 配置。

上下文 = 网络消息本身，结构取决于栈中位置：栈底是 L2 原始字节包，栈顶是 socket buffer。

挂点 程序类型 说明
socket 过滤 SOCKET_FILTER 史上第一个 eBPF 程序类型；过滤的是发给 tcpdump 等观察工具的数据副本，不是应用数据
socket 操作 SOCK_OPS 拦截 socket 上各种事件，设 TCP 超时等参数；socket 只存在于连接端点
sockmap SK_SKB 配合持有 socket 引用的特殊 map，在 socket 层重定向流量
TC（流量控制） tc 分类器/过滤器 内核完整 TC 子系统，可挂 ingress/egress；Cilium 的基石之一；tc 命令可直接操作
XDP xdp 收包最早期（驱动层，可 offload 到网卡）；按接口挂载，不同接口可挂不同程序
流解析器 FLOW_DISSECTOR 自定义包头部解析
轻量隧道 LWT_* eBPF 做网络封装；实践少见
cgroup CGROUP_SOCK / CGROUP_SKB 等 只对某 cgroup 内进程生效（容器/pod 隔离机制之一）；可做网络安全策略、甚至"骗"进程它连上了某个地址（服务网格）；另有 CGROUP_SYSCTL 挂 sysctl
红外 LIRC_MODE2 红外协议解码——证明"追踪/网络"二分法并不完备

XDP 常用命令：

ip link set dev eth0 xdp obj hello.bpf.o sec xdp    # 挂载
ip link set dev eth0 xdp off                         # 卸载
# ip link show 里可见 prog/xdp id 1255 tag ... jited

7.2 真机佐证（lab06，树莓派 5 · 6.18.34 · 2026-08-30）

实验仓库：ebpf-gate/labs/06-kprobe-uprobe

  • kprobe 挂 do_sys_openat2 跑通（ringbuf 事件流 + hash 计数，与 lab03 的 tracepoint 版同构可比）。符号勘察：do_sys_open 实测 0 次触发（只有老式 open syscall 走它），openat 全走 do_sys_openat2（ls 30 次触发 160 次事件）——挂 kprobe 前先用 bpftrace 验证路径，猜符号名必错。
  • 6.18 的 do_sys_openat2 PARM2 直接是 const char __user *（bpftrace str(uptr(arg1)) 一层读出路径验证），不是旧资料说的 struct filename *——内核重构会改函数语义，签名以真机实测为准。
  • arm64 无 BTF 写 kprobe：ctx 声明为 struct user_pt_regs *（来自用户态头 asm/ptrace.h）+ PT_REGS_PARMx 宏即可，不需要 vmlinux.h——这些宏只是寄存器偏移，与 CO-RE 无关。
  • uprobe 本机不可用：树莓派官方内核 # CONFIG_UPROBE_EVENTS is not set——attach 返回 ENOENT、/sys/kernel/tracing/uprobe_events 不存在（kprobe_events 在）。详见 8.2 的真机限制一节。

7.4 坑点清单

  1. 一个接口只能挂一个 XDP 程序——再挂报 Device or resource busy；多逻辑要用程序内部分发（第 2 章 PROG_ARRAY 尾调用）。注意多协议共存（freplace/mprog 框架）是新内核的演进方向，成书时（2022）通用路径仍是"单程序+内部分发"
  2. kprobe 挂到被内联的函数 = 静默没有入口点——符号表里有名字（static inline 也有符号信息），但运行时没有独立函数体可断点；先 bpftrace -l 验证路径（7.1 真机：猜符号名必错，do_sys_open 0 触发、openat 全走 do_sys_openat2）
  3. kprobe 声明参数时只能省略尾部参数，不能跳过中间的——参数按内存顺序（寄存器序）排列，跳中间=后面全错位
  4. tracepoint 前 4 个公共字段（common_type/flags/preempt_count/pid）访问即验证失败——ctx 访问检查按 format 文件的用户字段放行
  5. uprobe 的库路径是架构全路径（/usr/lib/aarch64-linux-gnu/libssl.so.3），跨架构部署要分别定义；容器内路径 ≠ 宿主机路径（探针路径按容器内挂载命名空间解析）
  6. Go < 1.17 二进制参数在栈上，pt_regs 取参方案失效——Go 1.17 起才改用寄存器传参；老 Go 二进制要靠 USDT 或 Frida 类方案
  7. kfunc 无稳定性承诺，生产分发慎用（helper 才有 UAPI 保证）——kfunc 是内核内部函数直接暴露给 BPF，内核重构说变就变
  8. （真机补充，lab06）内核重构会改函数语义：6.18 的 do_sys_openat2 PARM2 直接是 const char __user *（旧资料说是 struct filename *）——kprobe 签名以真机实测为准，书上/网上的签名都可能是旧版本

7.5 HFT 关联

1. 挂点选型决策树（行情链路观测）

要观测什么？
├─ 内核函数路径（耗时/返回原因） ──> fentry/fexit（5.5+/ARM 6.0+）
│     开销最低 + fexit 全参+返回值一步到位，免 kprobe/kretprobe 两次挂载、跨事件配对
├─ syscall 级审计/资产盘点 ──> tp_btf（稳定接口 + 免手写结构）
│     签名来自 vmlinux.h 的 trace_event_raw_*，免版本漂移
├─ 热点内核函数计时（老内核） ──> kprobe + kretprobe 出入对
│     跨事件配对用 @start[tid] map，延迟分布进 hist map
└─ 用户态二进制关键函数 ──> uprobe/uretprobe（注意静态链接与 Go 调用约定）

fexit 拿全参+返回值对测量"某内核路径耗时与返回原因"一步到位——kretprobe 只有 ret、拿不到入参，要重建"哪个 fd 的哪次 read 慢了"得跨两个探针配对；fexit 一个探针全拿到，配对逻辑消失 = 丢样本的风险消失（跨事件配对在事件洪峰下会丢半边）。

2. XDP 单程序限制 = 交易机网口的架构约束

所有入口逻辑（黑名单、速率限制、重定向到旁路采集）必须在一个 XDP 程序内组织好——用 PROG_ARRAY 尾调用做内部分发：主程序查表决定调哪个子程序，策略做成数据（改黑名单改 map，不改程序不重新加载）。这是"热更新"在 eBPF 侧的标准形态。

3. uprobe 钩交易网关二进制

钩 SSL/加密库的思路同样适用于钩交易网关的关键函数（下单路径计时）——不用改一行被测代码是最大优点（对不能重编译的第三方网关是唯一选择）。三个前提：函数有符号（非 stripped）、动态链接（或接受静态地址硬编码）、C 调用约定（Go 老版本出局）。开销 ~1-2µs/次——纳秒级路径不可用，微秒级路径可用。

4. LSM 返回码可阻断 → 内核级行为白名单

LSM 程序返回非零直接让内核拒绝操作（区别于追踪类的返回码被忽略）——可做交易进程的内核级行为白名单（如禁止非交易进程 connect 交易所网段），见第 9 章。这比 iptables 强在带进程上下文（哪个 PID/cgroup 干的），比 seccomp 强在动态可换。

5. 真机教训的泛化：挂点验证先于程序开发

lab06 的教训（do_sys_open 零触发、do_sys_openat2 签名变了）泛化成纪律：写程序前先用 bpftrace 一行命令验证挂点真的在目标路径上——bpftrace -l "*openat*" 列挂点、bpftrace -e 'kprobe:xxx { @[comm]=count(); }' 数触发。挂错点的 eBPF 程序不报错、只是静默零数据，是"工具坏了还是路径错了"排查里最费时间的一类。

7.6 自测题

  1. 程序类型决定了哪四件事？
  2. BPF_KPROBE_SYSCALL 与 BPF_KPROBE 与 BPF_PROG 各用于什么场景？
  3. fexit 相比 kretprobe 的独有优势是什么？依赖哪个内核机制、哪个版本引入（x86/ARM 各是）？
  4. tracepoint 的上下文结构怎么写？tp / raw_tp / tp_btf 三者的性能与可移植性权衡？
  5. SOCKET_FILTER 过滤的是什么数据？为什么说它"名不副实"？
  6. LSM 程序的返回码语义与追踪类有何不同？
  7. 为什么一个接口挂第二个 XDP 程序会失败？多逻辑怎么组织？
  8. helper 函数和 kfunc 在兼容性承诺上的区别？
参考答案

1. ①可附加的事件；②上下文参数的结构（ctx 指向什么）；③可用的 helper 函数集合（验证器按此检查）；④返回码的含义（XDP：放行/丢包/重定向；追踪类：被忽略；LSM：非零=拒绝操作）。

2. BPF_KPROBE_SYSCALL：挂 syscall 入口（ksyscall/），参数按 syscall 签名取（稳定接口，跨内核稳）；BPF_KPROBE：挂任意内核函数（kprobe/），参数按内核函数签名取（含 struct 指针，随内核版本变）；BPF_PROG：fentry/fexit/tp_btf 等宏（BPF_PROG(name, 类型化参数...)，配合 vmlinux.h 的类型直接声明参数）。

3. fexit 同时拿到入参和返回值（kretprobe 只有 ret）。依赖 BPF trampoline 机制（函数出入口动态生成跳板代码）。x86 5.5 引入，ARM64 要 6.0。

4. tp：手写结构体照抄 format 文件（offset/size 对齐），慢但兼容性最好；raw_tp：跳过参数映射直接拿原始 __u64 数组，最快但自己转型（架构相关）；tp_btf：BTF 自动提供 trace_event_raw_* 匹配结构（vmlinux.h 里），免手写、免漂移——首选（需要目标内核有 BTF）。

5. 过滤的是发给 tcpdump 等观察工具的数据副本（packet socket 路径），不是发给应用的数据——"SOCKET_FILTER"听起来像过滤应用流量，实际是抓包过滤；应用数据不受它影响。

6. LSM 返回非零 = 内核拒绝该操作（阻断生效，安全语义）；追踪类返回码被内核忽略（纯观察）。

7. XDP 挂载点是 per-interface 的单槽位（驱动层只有一个 XDP 程序入口），第二个程序无处可放 → EBUSY。多逻辑：程序内部分发——PROG_ARRAY 尾调用（策略查表决定调谁）或 if/else 单体程序。

8. helper 是 UAPI 稳定接口：一经定义不再变化，跨内核版本可依赖；kfunc 是内核内部函数直接注册给 BPF，无兼容性保证（内核重构即变），生产分发要自行承担版本适配。

衔接：挂点选定后，网络路径上的 XDP/tc 细节与 uprobe 在 Kubernetes 的限制 → 8.1/8.2；安全场景的挂点选择（TOCTOU 为什么 syscall 入口不行）→ 第 9 章。
