## 1.6 eBPF 的三大优势

> 本节讲什么：动态加载、高性能、零侵入——每个优势的机制依据是什么，配具体数字。

## 1. 动态加载：事件驱动，全进程覆盖

机制：程序通过 `bpf()` 加载进内核 → attach 到某个事件源（kprobe/tracepoint/XDP/…）→ **之后该事件每次发生都触发，无论触发者是谁**。

关键推论：

- **老进程也覆盖**：挂上 execve 追踪的那一刻，加载前就在跑的进程再调 execve 照样触发——没有"重启才能生效"一说（对比：给应用插桩、注入 sidecar 都要重启）
- **容器环境**：在节点内核里挂一次，该节点上**所有 Pod 的所有进程**全可见——因为容器共享宿主内核，而 eBPF 挂在内核上
- 卸载同样即时：ctrl-C 用户态工具，程序从内核摘除

你在 lab01 亲手验证过：bpftrace 启动 10 秒内，labwc、tailscaled 等早已在跑的进程的 syscall 全被统计——不需要重启它们任何一个。

## 2. 高性能：JIT + 内核态过滤

两个因素叠加：

**a) JIT 编译**：eBPF 字节码加载后即编译成本地机器指令（你的树莓派上是 ARM64 机器码），执行速度等同手写内核 C，不是解释执行。

**b) 过滤在内核里发生**（1993 年 BPF 论文的老智慧，见 §1）：

```
传统观测:   每个事件 ──内核→用户态拷贝+切换──▶ 用户态过滤 ──99%丢弃
eBPF 观测:  每个事件 ──在内核里直接被过滤/聚合──▶ 只有结果出内核
```

对百万事件/秒的场景，省掉的不是常数优化，而是**每事件一次的上下文切换**——上下文切换是微秒级操作，还污染 cache。

**实测数字**（XDP 论文，CoNEXT '18）：

| 工作负载 | 对比基准 | 加速 |
|---|---|---|
| XDP 路由转发 | 常规内核网络栈 | **2.5×** |
| XDP 负载均衡 | IPVS | **4.3×** |

## 3. 零侵入

不改应用代码、不改配置、不重启——机制上：eBPF 挂在内核的事件点上，应用根本没有参与，也就谈不上被修改。

这在两个场景是刚需：

- **第三方/闭源软件**：无法插桩的进程照样观测（它总得走 syscall）
- **恶意进程**：不会被观测的进程——挖矿程序不会"贴心地"上报自己的 CPU 占用，但它在内核里的调度事件、网络连接全暴露（第 9 章安全用例的基础）

## 4. 三者的乘法效应

三个优势不是并列，是相乘：因为**零侵入**所以敢装在生产；因为**高性能**所以装了不心疼；因为**动态加载**所以随装随用。缺任何一个，eBPF 都成不了"基础设施级"技术。

## 1.7 云原生环境：对比 sidecar 模型

> 本节讲什么：同一个观测需求（网络策略、可观测性）在 K8s 里的传统解法 sidecar 和 eBPF 解法怎么对比。即使你暂时不碰 K8s，这个对比也是"eBPF 三大优势"的最佳综合案例。

## 1. sidecar 模型是什么

想给 Pod 里的应用加网络观测/流量管理，又不改应用代码——传统做法：往 Pod 里注入一个代理容器（sidecar，如 Envoy），应用的网络流量改道经过它：

```
        Pod（共享 network namespace）
  ┌───────────────────────────────┐
  │  应用容器 ⇄ sidecar 代理(Envoy)⇄ veth ⇄ 宿主网络栈 ⇄ 物理网卡
  └───────────────────────────────┘
```

## 2. sidecar 的四个固有缺陷

| # | 缺陷 | 机制 |
|---|---|---|
| 1 | **加 sidecar 要重启 Pod** | 注入发生在 Pod 创建时；存量 Pod 只能重建 |
| 2 | **依赖注入流程，标注错了就漏掉** | YAML 里 annotation 忘写 / namespace 没打标签 → 整个未被插桩，且无报错 |
| 3 | **多容器 ready 顺序不可预测** | 应用容器先起、Envoy 后 ready → 竞态：Open Service Mesh 文档承认，代理 ready 前应用流量全丢；启动因此还要人为拉慢 |
| 4 | **绕路加延迟** | 应用流量必须离开内核网络栈、进入代理容器（一次用户态往返）、再回内核——每跳都是上下文切换 |

## 3. eBPF 模型：同一位置换个挂法

```
        Pod                    Pod                    Pod
  ┌────────────┐         ┌────────────┐         ┌────────────┐
  │  应用容器   │         │  应用容器   │         │  应用容器   │   ← 不加任何容器
  └─────┬──────┘         └─────┬──────┘         └─────┬──────┘
        └──────────────────┬───┴──────────────────────┘
                           ▼
  ┌─────────────── 宿主机内核（所有 Pod 共享）─────────────────┐
  │  eBPF 程序挂在网络栈关键点（XDP/TC/cgroup connect）          │
  │  → 一次加载，全节点所有 Pod 的流量全经过                     │
  └──────────────────────────────────────────────────────────────┘
```

四大缺陷逐一消解：

| sidecar 缺陷 | eBPF 对应解法 |
|---|---|
| 重启 Pod 才能加 | 动态加载，运行中的节点立即生效（优势 1） |
| 注入漏标 → 漏观测 | 挂在内核上，"漏标"概念不存在——所有进程都在 |
| ready 顺序竞态 | 没有 sidecar 就没有顺序问题 |
| 绕路延迟 | 逻辑在内核原地执行，零绕路（优势 2），且不用改应用（优势 3） |

## 4. 额外的一点：对抗恶意进程

观测自家微服务，sidecar 勉强够用；但**恶意程序不会配合你注入 sidecar**。挖矿程序、横向移动的攻击者流量，sidecar 模型看不见；eBPF 挂在内核网络路径上，主机所有流量（不管来自哪个容器、有没有被编排）都在监管范围——这是 Cilium/Tetragon 做运行时安全的根基（第 9 章）。
