## 11.5 坑点清单

1. **签名 eBPF 短期无解**：CO-RE/map 重定位与篡改在二进制上不可区分（[11.2](./11.2_演进方向与平台观.md)：签名验原始字节、运行的是重定位后字节）——别指望近期有"内核验签 eBPF"的现成方案
2. 内核指针存 map 属于违规（验证器会拦），等 typed pointer/acquire-release 语义全面落地——不要试图绕（绕过 = 引入悬垂指针 = 内核崩溃风险，这正是验证器拦它的原因）
3. **追新特性的代价**：用了最新内核特性，生产环境（稳定发行版）几年内跑不了；特性选型要看目标机器内核版本——`bpftool feature` + BCC 版本功能清单是查询第一站
4. Windows 版验证器是 PREVAIL，行为与 Linux 验证器**不完全一致**——跨平台程序要在两边分别过验证；验证/JIT 在用户态 Secure 环境也是加载路径差异
5. BCC 的按内核版本功能清单是查"这个内核有没有某特性"的第一站

## 11.6 HFT 关联

### 1. Big TCP 思路的同构价值

批处理换吞吐对行情突发洪峰（开盘/熔断恢复的 tick 风暴）极有参考性——洪峰期的事件处理成本不在单个事件而在**每事件固定开销 × 事件数**；内核内批处理把固定开销摊到批次。若交易机内核达到 5.19+，评估 eBPF 配合 Big TCP 的批量收包路径；达不到，思路仍然可迁移（用户态侧的批量 ring buffer 消费、NAPI 式配额处理）。

### 2. 签名问题就是交易机的合规问题

监管要求交易系统变更可审计，eBPF 程序现在只能靠"**单一可信二进制 + 哈希校验 + 权限控制**"兜底：CI 产出的 .o 嵌入二进制、部署前 SHA 校验、加载权限收敛到专用服务账户（CAP_BPF 最小化）。官方签名方案落地前这是现实解——**把"谁能加载程序"的治理做进部署流水线，而不是指望内核替你验**。

### 3. 升级内核的量化决策

HFT 恰是作者说的"需求足够迫切、值得为 eBPF 特性提前升级内核"的那类组织——但升级决策要量化：候选特性（如 Big TCP、bpf_loop、BPF token）在测试环境实测收益（第 10 章工具 + BPF_PROG_RUN 测试），收益覆盖升级回归成本（全量基线重跑、[06.6 3.6 升级纪律](../../../../06.6-systems-performance/chapter-03-operating-systems/notes/section-3.6-内核比较.md)）才动。

### 4. 平台化趋势的就业/选型含义

未来券商风控/审计产品会内嵌 eBPF（作者预言"应用产品自带运行时安全"）——买方视角：选型时问清供应商的 eBPF 层是否可控（能不能关、开销多大、误杀策略谁定）；工程师视角：懂 eBPF 的系统工程师在买方/卖方都是稀缺技能，**原理书这 11 章的内功（验证器/挂点/CO-RE）正是区分"会用工具"和"能造工具"的分界线**。

## 11.7 自测题

1. eBPF 基金会为什么成立？它与 CNCF 的分工边界在哪？
2. eBPF for Windows 为什么不能复用 Linux 内核的验证器？它用了什么替代？
3. Windows 版在哪里做验证和 JIT？与 Linux 的差异？
4. 签名 eBPF 程序的核心难点是什么？
5. 现在内核指针在 eBPF 程序里的生命周期限制是什么？
6. 为什么"新特性进了最新内核"对大多数生产用户没有意义？Big TCP 的例子说明什么组织例外？
7. "eBPF 是平台不是功能"如何类比容器的发展史？

<details>
<summary>参考答案</summary>

**1.** 让商业公司能在**中立机构**下合作（资金与知识产权的持有壳），且不改变内核社区开发方式——微软做 Windows 版 eBPF 需要跨 OS 的中立标准是直接动因。分工：基金会管技术平台与开发工具生态（libbpf/bpftool/规范）；上层应用项目（Cilium/Pixie/Falco）归 CNCF。

**2.** Linux 内核验证器是 **GPL** 许可，Windows 闭源实现不能抄。替代：**PREVAIL**（微软研究院的抽象解释验证器，宽松许可）。

**3.** Windows 在**用户态 Secure 环境**（隔离进程）做验证和 JIT；Linux 在内核里加载前验证、内核内 JIT。差异：Windows 宁可加载路径慢也要把验证/JIT 的风险关进沙箱；内核里的 uBPF 解释器仅用于 debug 构建。

**4.** **用户态 loader 会动态改写程序**（map 重定位、CO-RE 重定位）——签名验的是原始字节，实际执行的是重定位后字节，验证对象 ≠ 运行对象；从密码学视角这与篡改不可区分。解法要么证明重定位可白名单化，要么改造加载信任链。

**5.** helper/kfunc 返回的内核指针只在**本次程序执行内**有效——不能存 map 跨事件复用（内核结构可能已被释放，悬垂指针）。缓解中的出路：typed pointer + 引用计数语义（bpf_task_acquire/release 一族 kfunc）。

**6.** 稳定发行版滞后最新内核数年——mainline→LTS→发行版→生产每跳 1-2 年，多数组织等到特性可用时早已不新。例外：**需求足够迫切、能主导自己内核版本的组织**（超大规模流量组织、HFT）——Big TCP 的 100Gbit/s+ 批处理收益对他们值得提前升级内核。

**7.** 容器十年前被热炒，如今人人用 Docker/K8s 但没人直接操作 namespaces/cgroups——**基础设施被吸收进产品，直接操作者变少、受益者变多**。eBPF 同路：没人手写探针，但 Cilium/Tetragon/profiling agent 背后全是它；"我们用了 eBPF"从卖点变默认，平台就赢了。

</details>
