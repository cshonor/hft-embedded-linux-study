## 9.6 坑点清单

1. **syscall 入口探针不能当安全工具用**——TOCTOU 可被"幻影攻击"绕过（DEFCON 29 直接打 Falco 的演示）；观测用途没问题（第 7 章伏笔的完整答案）。判据一句话：**检查的数据 ≠ 内核使用的数据，就不是防线**
2. **seccomp profile 覆盖错误路径**：压力/故障场景触发的 syscall（磁盘满时的 fstatat 重试链、OOM 时的 prctl）若不在 profile 里，应用会在**最需要报警的时候死掉**——记录期要包含故障注入测试
3. `seccomp_unotify` 官方明确不可用于安全策略——man page 原话；别拿它做防护（同样是 TOCTOU）
4. **BPF LSM 需要 5.7+ 且启用** `lsm=bpf`；生产前先确认内核配置（lab08 勘察三件套：`cat /sys/kernel/security/lsm`、`/proc/cmdline`、`CONFIG_BPF_LSM`——树莓派 6.18 官方内核也没开，双重门槛还包括 CO-RE 依赖的 BTF）
5. 挂内核内部函数（Tetragon 式）没有稳定保证——升级内核要回归测试；选挂点必须选"数据结构已填充完"的位置（fd_install 而非 open）
6. Sigkill 策略先审计后强制；从审计切到强制前复盘所有历史告警
7. seccomp profile 只能在进程启动时应用——对已运行进程要用 syscall 追踪类工具（Falco/Tetragon）

## 9.7 HFT 关联

### 1. 交易进程 syscall 白名单（攻击面收敛）

交易进程实际只用 **40-70 个 syscall**（Aqua 统计的容器应用同量级）——用 eBPF 记录实际集合（[9.1](./9.1_安全模型与syscall方案.md) 的 Inspektor Gadget profiler 模式）+ seccomp 收紧到白名单。被入侵后的行动空间从 300+ syscall 缩到几十个：**反弹 shell（socket/execve 组合）直接被 EPERM 挡住**。这是"纵深防御"里成本最低的一层——不需要改交易代码，只需要一个 profile。

### 2. 关键配置文件防护（Tetragon 式 + 同步阻断）

盯 `/etc/`（交易所网关证书、密钥、hosts）的写入：TracingPolicy 挂 fd_install 前缀匹配 /etc/ → 动作 Sigkill。**篡改交易配置的进程在 write 完成前被杀**——比"事后从审计日志发现配置被改"（此时可能已经下了一小时的错价单）是两个安全等级。先审计模式跑两周，零误报再开强制。

### 3. TOCTOU 教训泛化到审计系统设计

任何"检查用户态内存再让内核处理"的审计逻辑都有竞态——**合规审计挂点必须选内核侧数据结构**（LSM 钩子 / fd_install / file_open 之后）。这个教训对自研风控/审计探针同样适用：挂点选错，审计记录本身就是假的（记录的是攻击者想让你看到的路径）。

### 4. 内核内过滤省带宽 = 交易机安全监控零成本常驻

只上报违规事件（matchArgs 内核内判断），正常流量的观测开销是零事件零上报——**交易机上安全监控的常驻开销可忽略，不用为审计牺牲微秒**。对比"全量 syscall 上报 + 用户态过滤"的方案：事件洪峰期的上报本身就会挤占交易核的 cache 和带宽。

### 5. 误杀的代价函数不对称

HFT 场景的安全策略设计要点：**误杀交易进程的代价（盘中断单、错过行情）远大于漏放一次可疑操作的代价**——所以 HFT 的策略梯度应该是：观测（永远开）→ 审计告警（值班响应）→ 同步阻断（只对"铁定无合法理由"的操作开，如非交易进程写 /etc/certs）。与互联网公司"宁可错杀"的防爬虫思路相反。

## 9.8 自测题

1. 安全工具与可观测工具的本质区别是什么？策略为什么要考虑错误路径？
2. seccomp 严格模式允许哪四个 syscall？seccomp-bpf 的四种输出动作？
3. seccomp-bpf 的两大局限是什么？
4. eBPF 生成 seccomp profile 挂在哪个 tracepoint？为什么说每个进程加载独立程序是常见模式？
5. 画出 TOCTOU 竞态窗口。为什么 seccomp-bpf 反而不受影响？Sysmon for Linux 如何缓解、代价是什么？
6. BPF LSM 为什么天然免疫 TOCTOU？返回值语义是什么？需要哪个内核版本？
7. Tetragon 为什么选 `fd_install` 而不是 `open` syscall？
8. `bpf_send_signal` 实现的防护与"通知用户态再处理"有何本质不同？
9. 为什么网络安全工具普遍用防护模式而主机侧长期用审计模式？

<details>
<summary>参考答案</summary>

**1.** 可观测工具**观察并报告**（不影响内核行为，返回码被忽略）；安全工具**判定并执行策略**（返回码/信号影响内核行为）。策略要覆盖错误路径：磁盘满、连接断开等故障触发的 syscall 链平时不出现——漏掉它们，正常应用会在故障时刻被自己的安全策略杀死。

**2.** 严格模式只允许 read/write/_exit/sigreturn。四种动作：①放行 ②返回错误码给用户态（EPERM 等）③杀死线程/进程 ④seccomp-unotify 通知用户态代理（5.0+）。

**3.** ①BPF 代码**不能解引用参数指针**（只看得到指针值，看不到文件名——按值过滤做不了）；②profile **必须在进程启动时应用**，运行中不能改。

**4.** 挂 `raw_syscalls:sys_enter` tracepoint，map 记录见过的 syscall 号。每个进程一份独立程序：map 以 pid/tgid 为过滤键（filter 直接写死 pid），事件在内核里就分流——避免单程序按 pid 查表的开销和 map 键空间膨胀。

**5.** 窗口：用户态传指针 → eBPF 在 syscall 入口读该指针（看到 "/tmp/a"）→ **另一线程此刻改写该内存** → 内核 copy_from_user 拷入实际数据（"/etc/shadow"）——检查的数据 ≠ 使用的数据。seccomp-bpf 不受影响因为它**根本不解引用指针**（无数据可比对，也就无竞态——它只按 syscall 号和标量参数过滤）。Sysmon 缓解：同时挂入口+出口，**调用完成后**从内核数据结构反查（fd → file → 文件名）拿准确视图；代价：只能记录不能阻止（syscall 已执行完）。

**6.** LSM 钩子在"内核即将对**内核数据结构**操作之前"触发——参数已 copy_from_user 进内核内存，不存在窗口。返回值：非零=拒绝操作（阻断生效）。需要 5.7+ 且 `CONFIG_BPF_LSM=y` + 启动参数 `lsm=bpf`。

**7.** fd_install 在文件结构**填充完成之后**被调用（file 指针已就绪），参数是内核侧数据（`struct file *`）——无 TOCTOU；open syscall 入口的 filename 参数是用户态指针，检查它=开竞态窗口。

**8.** bpf_send_signal 在 **eBPF 程序内、syscall 返回用户态之前**同步发 SIGKILL——违规动作被终止于执行中；"通知用户态再处理"是异步链路（事件→用户态 agent→决策→kill），毫秒级窗口内恶意操作已完成。本质区别：**阻断点在内核内的同步路径上 vs 在用户态的异步响应里**。

**9.** 网络侧误报率低（防火墙规则基于包特征，确定性高）且误杀代价可接受（丢一个连接）；主机侧工具长期误报率高（行为判断难）且误杀代价大（杀业务进程）——eBPF 的细粒度内核内判断正在改变这个不对称，把主机侧推向防护模式。

</details>
