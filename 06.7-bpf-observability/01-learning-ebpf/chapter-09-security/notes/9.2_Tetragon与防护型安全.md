## 9.4 Cilium Tetragon：挂内核内部函数

LSM 普及前的另一条路：把 eBPF 程序挂到**任意内核函数**（不限于稳定接口）。

- 依据：syscall/LSM 只是 3000 万行内核代码中极小的稳定部分；大量内部函数事实上多年未变；新内核普及需数年，不兼容有充足时间修复——**用"事实稳定"替代"承诺稳定"**，风险由升级时的回归测试兜底
- Tetragon 贡献者含内核开发者，凭内部知识挑出**安全且信息完备**的挂点（不是随便挑函数：要保证参数此刻已填充、无 TOCTOU）
- K8s 自定义资源 **TracingPolicy** 声明式定义：挂点 + 条件 + 动作——安全策略像 K8s 资源一样可版本化、可滚动下发

```yaml
spec:
  kprobes:
  - call: "fd_install"        # 文件打开后在 fd 数组装入 file 指针（此时文件结构已填充完）
    matchArgs:
    - index: 1
      operator: "Prefix"
      values: ["/etc/"]       # 只关心 /etc/ 下的文件
```

- 挂 `fd_install` 而非 `open` syscall 的原因：它在**文件数据结构填充完之后**调用——和 LSM 同理，天然免疫 TOCTOU（[9.1](./9.1_安全模型与syscall方案.md) 的竞态窗口在内核侧数据结构上不存在）
- **内核内过滤**：只把**超出策略**的事件报告用户态，而不是全量上报再筛——matchArgs 在内核里就完成判断，事件洪峰不产生用户态负载

**TracingPolicy 的三段式结构拆解**：`call`（挂点）+ `matchArgs`（内核内过滤条件，支持 Prefix/Equal/Mask 等算子）+ `action`（默认告警，可选 Sigkill/Postprocess）。这就是"策略即数据"在安全域的落地——**改策略不改程序**，与 [7.2](../../chapter-07-program-attachment-types/notes/7.2_坑点HFT关联与自测.md) 的 PROG_ARRAY 分发同构。

## 9.5 防护型安全（preventative）

- 检测型模式：eBPF → 异步通知用户态 → 用户态处理——窗口期内数据可能已外泄、恶意代码可能已落盘。**检测的时延 = 攻击者的机会窗口**（毫秒到秒级）
- **同步阻断**：`bpf_send_signal()`（5.3+）在 eBPF 程序内直接给违规进程发 **SIGKILL**——内核正在执行的动作被同步终止，来不及完成。阻断发生在**内核态、syscall 返回用户态之前**——比"用户态 agent 收到事件再 kill"快三个数量级，且不给攻击者留任何执行窗口
- 实操建议：先跑**审计模式**（只告警不杀），确认策略无误报后再开 Sigkill——错误策略会杀掉正常应用（交易机上误杀交易进程的代价 >> 漏放一次可疑操作的代价）
- 网络安全早已是防护模式（防火墙直接丢包；XDP offload 后恶意包根本到不了 CPU）；主机侧因为工具误报率高长期只能审计——eBPF 细粒度准确的控制正在把"可预防"从网络扩展到非网络事件

**检测 → 防护的光谱**（本节的工程地图）：

```
观测 ──────────────────────────────► 防护
  │                                    │
  eBPF 记录 → 用户态告警     eBPF 判定 → 内核内阻断
  （事后取证，攻击已完成）    （bpf_send_signal / LSM 返回码 / XDP 丢包）
  │                                    │
  时延：ms~s 级                        时延：µs 级（syscall 返回前）
  误报代价：低（只是日志）             误报代价：高（杀错进程）→ 必须先审计模式
```
