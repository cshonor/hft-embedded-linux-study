## 1. 五条极简认知：先把层次钉死

| # | 认知 | 展开 | 深入 |
|---|---|---|---|
| 1 | **eBPF 是内核自带的技术**（内核里的可编程虚拟机） | 把 C 写的（编译成 BPF 字节码的）小程序交给内核 → **verifier 静态验证** → **JIT 成本机指令** → 挂到某个 **hook** 上执行 | 没有 BCC，eBPF 照常工作；eBPF 是内核能力，不是任何用户态框架的产物 |
| 2 | **BCC 是 Python 写的上层框架** | 包裹 eBPF，替你做**编译、加载、挂载、读数据** | ⭐ BCC **不参与程序的执行** —— 程序跑在内核里，与 Python 进程无关（唯一关系见 §9） |
| 3 | **代码分两层** | 外层 Python（`from bcc import BPF`）；三引号内是 **C**，即真正跑进内核的 eBPF 程序，只是以字符串形式存在 | 见 §3 边界详解 |
| 4 | `attach_kprobe` / `get_syscall_fnname` / `attach_tracepoint` 是 **BCC 的 API** | 底层依旧依赖内核能力（kprobe / kallsyms / tracepoint），BCC 只负责封装 | 见 §8 API 小词典 |
| 5 | **新手学习顺序**：先用 BCC 跑通例子，再深挖内核细节 | 反馈最快；第 3–5 章会手工撕开这层封装 | 见 §10 |

⚠️ **一句话纠偏**：**「BCC = eBPF」是新手最常见的误认。** 卸掉 BCC，eBPF 照常工作（`bpftool`、libbpf、bpftrace、cilium/ebpf 是完全不同的入口）；反过来，内核没有 eBPF 支持时 BCC 什么都做不了。两者是**被封装者**与**封装者**的关系。

## 2. 分层图：谁在哪一层

```
┌──────────────────────────────────────────────────────────────┐
│ 用户态                                                         │
│                                                               │
│   hello.py（你的脚本）                                          │
│     ├── from bcc import BPF        ← BCC 的 Python 前端          │
│     ├── BPF(text=program)          ← 触发「编译 + 加载」           │
│     ├── attach_kprobe(...)         ← 触发「挂载」                  │
│     └── trace_print()              ← 触发「读数据」                │
│                │                                              │
│   ┌────────────▼──────────────────────────────────────────┐   │
│   │ libbcc（BCC 的 C++ 部分，内部链接了 clang/LLVM）          │   │
│   │   · bpf_module_create_c_from_string()  ← 现场调 clang     │   │
│   │   · bpf_attach_kprobe() / _tracepoint() / _xdp()         │   │
│   └────────────┬──────────────────────────────────────────┘   │
└────────────────┼──────────────────────────────────────────────┘
                 │   bpf(2) 系统调用   ← 唯一的边界
┌────────────────▼──────────────────────────────────────────────┐
│ 内核态（eBPF 本体在这里）                                        │
│   BPF_PROG_LOAD → verifier → JIT → 挂到 hook                    │
│   hook: kprobe / tracepoint / XDP / tc / perf event / LSM ...    │
│                                                                │
│   ⭐ 之后每次事件触发，内核直接执行 JIT 后的机器码 —— Python 不在场 │
└────────────────────────────────────────────────────────────────┘
```

| 层 | 谁提供 | 可替换性 |
|---|---|---|
| 内核虚拟机（verifier / JIT / hook 基础设施） | **Linux 内核** | 换不了，这就是 eBPF 本体 |
| `bpf(2)` 系统调用 | **Linux 内核** | 所有框架的统一入口（[Ch4](../../chapter-04-bpf-syscall/)） |
| 编译（C → BPF 字节码） | clang / LLVM | 编译器换不了，但**可以不在目标机上编译**（CO-RE + libbpf，[Ch5](../../chapter-05-core-btf-libbpf/)） |
| 编译/加载/挂载的**流程编排** | **BCC / libbpf / cilium-ebpf / Aya** | 可换，这就是所谓"框架之争"（[Ch10](../../chapter-10-programming/)） |
| 用户态语言 | Python / C / Go / Rust | 可换；本书用 Python 只为代码简洁 |

## 3. 一个文件、两种语言：边界到底在哪

### 3.1 `r"""` 的三个字符各有讲究

```python
program = r"""
int hello(void *ctx) { ... }
"""
```

- **`r` = raw string**：禁止 Python 解释反斜杠。这是硬需求，不是风格。
  C 代码里的 `bpf_trace_printk("Hello World!\n")`，若用普通 `"""..."""`，
  Python 会先把 `\n` 变成**真正的换行符**再拼进字符串 → 交给 clang 的 C 源码长这样：

  ```c
  bpf_trace_printk("Hello World!
  ");
  ```

  → **clang 报错 `missing terminating " character`**（C 字符串字面量不能跨行）。
  eBPF 的 printk 几乎都带 `\n`，所以 BCC 例子一律用 `r"""`。
- **`"""` = 三引号**：只为跨行书写方便，**不是 BCC 语法**。换 `'''`、`"...\n..."` 拼接、
  甚至从 `.c` 文件读（`BPF(src_file=...)`）在 BCC 看来完全等价（源码注释：
  *"This ensures, that files and inline text are treated equally"*）。

### 3.2 两侧不共享任何东西

| | Python 侧 | C 侧（三引号内） |
|---|---|---|
| 谁执行 | CPython 解释器 | 内核里的 eBPF 虚拟机（你的 Pi 上 JIT 后是 **ARM64 机器码**） |
| 变量 | 互不可见 | 互不可见 |
| 类型定义 | `ctypes` 结构（BCC **反射**你的 C 源码生成） | `struct data_t` 只存在于 C 源码文本里 |
| 编译时机 | 脚本启动（`.pyc`） | **每次执行 `BPF(text=...)` 都对这段字符串跑一遍 clang** |
| 出错表现 | Python traceback | clang 编译错误 / **verifier 拒绝日志**（[Ch6](../../chapter-06-verifier/)） |

⚠️ **最典型的误解：以为 C 代码里能引用 Python 变量。** 不能 —— `program` 对 clang 而言只是一段纯文本。
要传值只能走 map（[2.1 §2.2](./2.1_HelloWorld与数据通道.md)）。

反过来，Python 侧之所以能写 `b["output"].event(data).command`，是因为 **BCC 解析了你那段 C 源码里的 `struct data_t`，用 ctypes 生成了同名结构**。同一份定义被两侧各读了一遍，**不是"共享"** —— 一旦两侧结构定义不同步，读出的是乱码且不报错。

### 3.3 时间线：一次 `python3 hello.py` 里发生了什么

| 时刻 | 动作 | 谁干的 |
|---|---|---|
| t0 | CPython 执行 hello.py；`program` 还只是个 `str` 对象 | Python |
| t1 | `BPF(text=program)` → `lib.bpf_module_create_c_from_string()` → **clang 现场编译** | libbcc |
| t2 | 逐个 `bpf(BPF_MAP_CREATE)` 建 map、`bpf(BPF_PROG_LOAD)` 加载程序 → **verifier 检查 + JIT** | 内核 |
| t3 | `b.attach_kprobe(...)` → `lib.bpf_attach_kprobe()` → 内核创建 kprobe | libbcc + 内核 |
| t4 | ⭐ 之后每次有人 execve → **内核直接执行 JIT 后的机器码**（Python 完全不在场） | 内核 |
| t5 | `b.trace_print()` → Python 循环读 trace_pipe 文本 | Python |
| t6 | Python 退出 → `atexit` 触发 `BPF.cleanup()` → detach + 关 fd → **程序消失** | Python + 内核 |

**t4 是理解 eBPF 的关键**：eBPF 程序的执行**不需要用户态进程存在**。Python 进程唯一的作用就是"把程序送进去 + 把数据读出来"。

## 4. 例子一 `hello.py` —— 逐行注解

原文（[chapter2/hello.py](https://github.com/lizrice/learning-ebpf/blob/main/chapter2/hello.py)，331 字节，已核对）：

```python
#!/usr/bin/env python3
from bcc import BPF
import sys

program = r"""
int hello(void *ctx) {
    bpf_trace_printk("Hello World!");
    return 0;
}
"""

b = BPF(text=program)
syscall = b.get_syscall_fnname("execve")
b.attach_kprobe(event=syscall, fn_name="hello")

try:
    b.trace_print()
except KeyboardInterrupt:
    sys.exit(0)
```

| 行 | 属于哪一层 | 解释 |
|---|---|---|
| `#!/usr/bin/env python3` | Python | shebang，与 eBPF 无关 |
| `from bcc import BPF` | Python / BCC | 导入 BCC 的 Python 前端（内部用 `ctypes` 调 `libbcc.so`） |
| `import sys` | Python | 只为最后的 `sys.exit(0)` |
| `program = r"""…"""` | ⭐ **C（eBPF 程序）** | 整块是另一门语言的源码，此刻只是个字符串 |
| `int hello(void *ctx)` | C | 程序入口。`ctx` 的含义由 **hook 类型**决定：kprobe 下是 `struct pt_regs *`，XDP 下是 `struct xdp_md *` |
| `bpf_trace_printk(...)` | C | 内核 **helper**（白名单函数，约 200 个），输出进 trace_pipe |
| `return 0` | C | **kprobe 程序返回值被忽略**（kprobe 不拦截、不改变原函数）；只有 XDP 这类"裁决型"程序的返回值才决定包的命运（[Ch8](../../chapter-08-networking/)） |
| `b = BPF(text=program)` | Python → **编译 + 加载** | 见 §4.1 |
| `b.get_syscall_fnname("execve")` | Python → 查内核符号 | 见 §4.2 |
| `b.attach_kprobe(...)` | Python → **挂载** | 见 §4.3 |
| `b.trace_print()` | Python → 读数据 | 死循环读 `/sys/kernel/debug/tracing/trace_pipe` |
| `except KeyboardInterrupt: sys.exit(0)` | Python | 优雅退出。不写也能退，只是会抛 traceback |

### 4.1 `BPF(text=program)` 一次干了四件事

BCC 源码（`BPF.__init__`）：

```python
self.module = lib.bpf_module_create_c_from_string(text, self.debug,
                                                 cflags_array, len(cflags_array),
                                                 allow_rlimit, device)
if not self.module:
    raise Exception("Failed to compile BPF module %s" % (src_file or "<text>"))
```

```
C 字符串
  ──libbcc 内部调 clang──▶ BPF 字节码
  ──bpf(BPF_MAP_CREATE)──▶ 内核里建好所有 map
  ──bpf(BPF_PROG_LOAD)───▶ verifier 逐条检查 → JIT 成 ARM64 机器码
  ──返回─────────────────▶ 每个函数、每个 map 各拿到一个 fd
```

三条推论：

1. **每次运行都重新编译一次**（没有缓存）→ 启动有秒级延迟。这是 BCC 后来被 libbpf 取代的**头号原因**（[5.1](../../chapter-05-core-btf-libbpf/notes/5.1_BCC之弊与CO-RE要素.md)）
2. **目标机上必须装有 clang 和内核头文件** —— 最小化安装的服务器、容器、嵌入式设备常年缺这两样
3. `BPF(text=...)` 与 `BPF(src_file=...)` **完全等价**：源码里 `if src_file: text = open(src_file, "rb").read()`

### 4.2 ⭐ `get_syscall_fnname()` 的内幕：拿 bpf 自己的符号去试探前缀

全书最不起眼、但设计很妙的一行。BCC 源码：

```python
    _syscall_prefixes = [
        b"sys_",
        b"__x64_sys_",
        b"__x32_compat_sys_",
        b"__ia32_compat_sys_",
        b"__arm64_sys_",
        b"__s390x_sys_",
        b"__s390_sys_",
        b"__riscv_sys_",
    ]

    # Find current system's syscall prefix by testing on the BPF syscall.
    # If no valid value found, will return the first possible value which
    # would probably lead to error in later API calls.
    def get_syscall_prefix(self):
        for prefix in self._syscall_prefixes:
            if self.ksymname(b"%sbpf" % prefix) != -1:
                return prefix
        return self._syscall_prefixes[0]

    # Given a syscall's name, return the full Kernel function name with current
    # system's syscall prefix. For example, given "clone" the helper would
    # return "sys_clone" or "__x64_sys_clone".
    def get_syscall_fnname(self, name):
        name = _assert_is_bytes(name)
        return self.get_syscall_prefix() + name
```

⭐ **它压根不去查 `execve` 的符号，而是拿 bpf 这个 syscall 自己的各种前缀变体去 `/proc/kallsyms` 试探**：

```
sys_bpf          存在? ─否→ __x64_sys_bpf   存在? ─否→ __x32_compat_sys_bpf ─否→
__ia32_compat_sys_bpf ─否→ __arm64_sys_bpf 存在? ─是（你的 Pi 5 命中）→ 前缀 = "__arm64_sys_"
                                                    ↓
                          get_syscall_fnname("execve") == "__arm64_sys_execve"
```

| 机器 | 命中的前缀 | 返回 |
|---|---|---|
| x86_64 现代内核 | `__x64_sys_` | `__x64_sys_execve` |
| **aarch64（你的树莓派 5）** | `__arm64_sys_` | `__arm64_sys_execve` |
| 老内核 / 未开 syscall wrapper | `sys_` | `sys_execve` |

**为什么非要这一层？** 因为现代内核的 `CONFIG_ARCH_HAS_SYSCALL_WRAPPER`：syscall 在内核里的符号不再是 `sys_xxx`，而是带架构前缀的 `__<arch>_sys_xxx`。直接写 `attach_kprobe(event="execve")` 一定失败 —— **kprobe 挂的是内核函数符号，不是 syscall 名字**。

两个坑：

- **8 个候选全落空就回退 `sys_`**，注释原话 *"would probably lead to error in later API calls"* —— 又一处**静默降级**：不报错，返回一个大概率错的答案，错误延迟到 `attach_kprobe` 才爆炸（表现为 `it's not traceable`）。`/proc/kallsyms` 读不到时（容器、权限、`kptr_restrict`）会踩到
- 名字**已经带前缀**的话要用 `fix_syscall_fnname()`（先 `startswith` 剥掉旧前缀再加新前缀）。`kprobe__`/`kretprobe__` 自动加载路径内部就调它

### 4.3 `attach_kprobe()` 内幕

```python
        self._check_probe_quota(1)
        fn = self.load_func(fn_name, BPF.KPROBE)
        ev_name = b"p_" + event.replace(b"+", b"_").replace(b".", b"_")
        fd = lib.bpf_attach_kprobe(fn.fd, 0, ev_name, event, event_off, 0)
        if fd < 0:
            raise Exception("Failed to attach BPF program %s to kprobe %s"
                            ", it's not traceable (either non-existing, inlined, or marked as \"notrace\")"
                            % (fn_name, event))
        self._add_kprobe_fd(ev_name, fn_name, fd)
```

- `ev_name` 前缀 `p_`；kretprobe 是 `r_`，且 `bpf_attach_kprobe()` 的**第二个参数 `is_return` 从 0 变 1**
- `+`（函数内偏移）和 `.` 会被替换成 `_` —— 保证 event 名合法
- `_check_probe_quota(1)`：BCC 对单个进程的 probe 数量有配额，超限会抛异常
- ⭐ **`fd < 0` 的报错文案值得背下来**：`it's not traceable (either non-existing, inlined, or marked as "notrace")`
  —— 看到这句就三选一排查：
  1. **符号不存在**（拼错 / 该配置没编进内核）→ 用 `BPF.get_kprobe_functions(re)` 列出可挂函数
  2. ⭐ **被内联了** —— 编译优化后没有独立函数体，kprobe 无从下断点。这是挂普通 C 函数（而非 syscall 入口）时**最常见的失败原因**
  3. 标了 `notrace`

### 4.4 `trace_print()` / `trace_fields()`：本质是切字符串

```python
    def trace_print(self, fmt=None):
        while True:
            if fmt:
                fields = self.trace_fields(nonblocking=False)
                if not fields: continue
                line = fmt.format(*fields)
            else:
                line = self.trace_readline(nonblocking=False)
            print(line)
            sys.stdout.flush()
```

`trace_fields()` 返回 `(task, pid, cpu, flags, ts, msg)`，但它**按固定列宽切文本**：

```python
            task = line[:16].lstrip()
            line = line[17:]
            ts_end = line.find(b":")
            try:
                pid, cpu, flags, ts = line[:ts_end].split()
            except Exception as e:
                continue
```

两处值得记：

- `if line.startswith(b"CPU:"): continue` —— 主动跳过"丢事件告知行"。
  ⚠️ 意味着 **trace_pipe 确实会丢事件，而 `trace_fields()` 默认帮你把这条信息吞掉了**
- 解析失败时 `return ("Unknown", 0, 0, "Unknown", 0.0, "Unknown")` —— **返回假数据而不是抛异常**。
  ⭐ 又一次「静默降级」：靠 `trace_fields()` 做日志落盘/告警前，必须先想清楚这一点

→ 这就是为什么 trace_pipe 只配调试期用（[2.1 §4](./2.1_HelloWorld与数据通道.md)）。

## 5. 例子二 `hello-map.py` —— 加 map

原文（[chapter2/hello-map.py](https://github.com/lizrice/learning-ebpf/blob/main/chapter2/hello-map.py)）：

```python
#!/usr/bin/env python3
from bcc import BPF
from time import sleep

program = r"""
BPF_HASH(counter_table);

int hello(void *ctx) {
   u64 uid;
   u64 counter = 0;
   u64 *p;

   uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;
   p = counter_table.lookup(&uid);
   if (p != 0) {
      counter = *p;
   }
   counter++;
   counter_table.update(&uid, &counter);
   return 0;
}
"""

b = BPF(text=program)
syscall = b.get_syscall_fnname("execve")
b.attach_kprobe(event=syscall, fn_name="hello")

# Attach to a tracepoint that gets hit for all syscalls 
# b.attach_raw_tracepoint(tp="sys_enter", fn_name="hello")

while True:
    sleep(2)
    s = ""
    for k,v in b["counter_table"].items():
        s += f"ID {k.value}: {v.value}\t"
    print(s)
```

C 侧的四个新手要点（[2.1 §2.2](./2.1_HelloWorld与数据通道.md) 已展开）这里不重复，只列**本例新增的边界问题**：

| 行 | 说明 |
|---|---|
| `BPF_HASH(counter_table);` | ⚠️ **BCC 宏，不是标准 C** —— 展开为 `struct bpf_map_def` + `SEC("maps")`。迁移 libbpf 要改写成 `__uint(type, BPF_MAP_TYPE_HASH)` 那套 |
| `counter_table.lookup(&uid)` | ⚠️ 同样是 BCC 方言：BCC 在交给 clang 之前做**文本重写**，变成真正的 `bpf_map_lookup_elem(&counter_table, &uid)`。你写的"C"是 BCC 的一门方言 |
| `b["counter_table"]` | ⭐ **Python 侧按名字取 map** —— 名字直接来自 C 源码里 `BPF_HASH()` 的参数。BCC 遍历 ELF 的 maps 段建表存进 `self.tables` |
| `.items()` | 遍历 map：内核侧是 `bpf(BPF_MAP_GET_NEXT_KEY)` + `bpf(BPF_MAP_LOOKUP_ELEM)` 循环（[Ch4 §4](../../chapter-04-bpf-syscall/)） |
| `k.value` / `v.value` | ctypes 对象取标量值（类型由 BCC 从 C 声明推出，`BPF_HASH` 默认 key/value 都是 `u64`） |
| `# b.attach_raw_tracepoint(tp="sys_enter", ...)` | 注释掉的换挂点方案 —— **raw tracepoint 的参数不带 category**，直接 `sys_enter` |

⚠️ `BPF_HASH(name)` 默认是 **u64 key → u64 value**；要别的类型得写 `BPF_HASH(name, key_type, value_type)`。

## 6. 例子三 `hello-buffer.py` —— perf buffer 事件流

原文（[chapter2/hello-buffer.py](https://github.com/lizrice/learning-ebpf/blob/main/chapter2/hello-buffer.py)）：

```python
#!/usr/bin/env python3
from bcc import BPF

program = r"""
BPF_PERF_OUTPUT(output); 
 
struct data_t {     
   int pid;
   int uid;
   char command[16];
   char message[12];
};
 
int hello(void *ctx) {
   struct data_t data = {}; 
   char message[12] = "Hello World";
 
   data.pid = bpf_get_current_pid_tgid() >> 32;
   data.uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;
   
   bpf_get_current_comm(data.command, sizeof(data.command));
   bpf_probe_read_kernel(data.message, sizeof(data.message), message); 
 
   output.perf_submit(ctx, &data, sizeof(data)); 
 
   return 0;
}
"""

b = BPF(text=program) 
syscall = b.get_syscall_fnname("execve")
b.attach_kprobe(event=syscall, fn_name="hello")
 
def print_event(cpu, data, size):  
   data = b["output"].event(data)
   print(f"{data.pid} {data.uid} {data.command.decode()} {data.message.decode()}")
 
b["output"].open_perf_buffer(print_event) 
while True:   
   b.perf_buffer_poll()
```

| 行 | 说明 |
|---|---|
| `BPF_PERF_OUTPUT(output)` | BCC 宏，建一个 `BPF_MAP_TYPE_PERF_EVENT_ARRAY` |
| `struct data_t` | **只存在于 C 侧**。Python 侧能访问 `.command`，靠 BCC 反射这份定义生成 ctypes 结构 |
| `output.perf_submit(ctx, &data, sizeof(data))` | BCC 方言 → `bpf_perf_event_output(ctx, &output, flags, &data, size)` |
| `def print_event(cpu, data, size)` | ⚠️ 回调签名**固定三参**（CPU 编号 / 原始字节 / 长度），BCC 规定，改了就报错 |
| `data = b["output"].event(data)` | ⭐ 把原始字节 `data` **重新绑定**成 ctypes 结构（同名变量覆盖自己）—— 新手最容易看懵的一行 |
| `b["output"].open_perf_buffer(print_event)` | 注册回调：底层 `perf_event_open` + mmap 环形缓冲，**每 CPU 一块** |
| `b.perf_buffer_poll()` | epoll 等待；无事件时**休眠**，不是忙轮询 |

## 7. 例子四 `hello-file.py` —— `TRACEPOINT_PROBE` 宏与自动挂载

原文（[chapter2/hello-file.py](https://github.com/lizrice/learning-ebpf/blob/main/chapter2/hello-file.py)）：

```python
#!/usr/bin/env python3
from bcc import BPF

program = r"""
TRACEPOINT_PROBE(syscalls, sys_enter_openat) 
{
  char command[256];

  bpf_get_current_comm(command, sizeof(command));

  bpf_trace_printk("File %s", args->filename);
  bpf_trace_printk("     opened by:%s", command);

  return 0;
}
"""

b = BPF(text=program)
b.trace_print()
```

⭐ **这个例子没有任何 `attach_*` 调用** —— `TRACEPOINT_PROBE(cat, name)` 宏干了三件事：

1. 把函数改名为 `tracepoint__syscalls__sys_enter_openat`
2. `BPF.__init__` 末尾的 `self._trace_autoload()` 扫描到 `tracepoint__` 前缀 → **自动 load + attach**
3. 同名地，`kprobe__<fn>` / `kretprobe__<fn>` / `raw_tracepoint__<name>` 前缀也都是自动挂载
   （`_trace_autoload()` 对 kprobe 还会额外调 `fix_syscall_fnname()` 修前缀）

⭐ **`args->filename` 的类型从哪来？** 既不是内核头文件，也不是 BTF ——

BCC 前端在编译时去读 tracefs 的文本格式文件：

```
/sys/kernel/debug/tracing/events/syscalls/sys_enter_openat/format
```

里面逐行列出每个字段的名字与偏移（`field:const char * filename; offset:16; ...`），
BCC **现场生成一个 `struct args` 塞进 C 源码**，再交给 clang。

**这一条对你的环境特别关键** —— 见 §11 的嵌入式专条。

> `hello-file-ring-buffer.py` 是它的 ringbuf 版本：`BPF_RINGBUF_OUTPUT(output, 1)` +
> `output.ringbuf_output(&event, sizeof(event), 0)` + `open_ring_buffer()` / `ring_buffer_poll()`，
> API 形状与 perf buffer 几乎一致（[2.1 §2.3](./2.1_HelloWorld与数据通道.md) 有两者的机制对比）。

## 8. BCC API 小词典：Python 名字 → 底层的内核动作

| BCC Python API | 干什么 | 底层（BCC C 函数 / 内核机制） |
|---|---|---|
| `BPF(text=...)` / `BPF(src_file=...)` | 编译 + 建 map + 加载 | `bpf_module_create_c_from_string()` → clang；`bpf(BPF_MAP_CREATE)` + `bpf(BPF_PROG_LOAD)` |
| `b.load_func(name, type)` | 按名字取已加载的 BPF 函数 | 返回含 `fd` 的 `BPF.Function` |
| `b.get_syscall_fnname("execve")` | 拼出 syscall 的内核符号名 | 探 `/proc/kallsyms`（用 `<prefix>bpf` 试前缀，§4.2） |
| `b.fix_syscall_fnname("sys_clone")` | 已带前缀的改写成本机前缀 | 同上 |
| `b.get_kprobe_functions(re)` | 列出**可挂**的内核函数 | 读 `/proc/kallsyms` + `available_filter_functions` + `kprobes/blacklist`，并剔除 `__init`/`__irqentry`/`.cold` 段 |
| `b.attach_kprobe(event, fn_name)` | 挂函数入口 | `bpf_attach_kprobe(fd, 0, "p_"+event, ...)` → 内核 kprobe |
| `b.attach_kretprobe(...)` | 挂函数返回 | 同上，`r_` 前缀 + `is_return=1` |
| `b.attach_tracepoint(tp="cat:name")` | 挂静态 tracepoint | `bpf_attach_tracepoint(fd, category, name)` —— ⚠️ **带冒号** |
| `b.attach_raw_tracepoint(tp="sys_enter")` | 挂 raw tracepoint | `bpf_attach_raw_tracepoint(fd, tp)` —— ⚠️ **不带冒号** |
| `BPF.attach_xdp(dev, fn, flags)` | 挂网卡 XDP | `bpf_attach_xdp(dev, fd, flags)`；`remove_xdp(dev)` = 传 `-1` |
| `b.attach_uprobe(path, addr, fn_name, pid)` | 挂用户态函数 | `bpf_attach_uprobe()` → uprobe |
| `b.attach_kfunc` / `attach_kretfunc` / `attach_lsm` | fentry/fexit、LSM | `bpf_attach_kfunc()` / `bpf_attach_lsm()` |
| `b.trace_print()` / `trace_fields()` | 读 trace_pipe | 文本解析（§4.4） |
| `b["mapname"]` | 按名字取 map 对象 | BCC 遍历 ELF maps 段建表 |
| `b["out"].open_perf_buffer(cb)` / `perf_buffer_poll()` | perf buffer 事件流 | `perf_event_open` + mmap（每 CPU 一块）+ epoll |
| `b["out"].open_ring_buffer(cb)` / `ring_buffer_poll()` | ring buffer 事件流 | 单个共享 ringbuf map + epoll |

⚠️ **最常见的低级错**：`attach_tracepoint` 要 `"category:name"`，`attach_raw_tracepoint` 只要名字。写反了报 `Failed to attach BPF program ... to tracepoint`。

## 9. ⭐ 一个重要事实：Python 一退出，eBPF 程序就没了

BCC 的 `BPF.__init__` 里有这一行：

```python
        atexit.register(self.cleanup)
```

`cleanup()` 会：**detach 所有已挂载的 probe**（遍历 `kprobe_fds` / `uprobe_fds` / `tracepoint_fds` /
`raw_tracepoint_fds` / `kfunc_*` / `lsm_fds` / `fmod_ret_fds`）→ 清理 perf ring 与 trace file →
最后 `close()` 关掉所有 BPF 程序与 map 的 fd。

**推论**：

- 脚本活着 = 程序挂着；**Ctrl-C = 程序卸载**。**不存在"后台常驻"**
- 所以 `bpftool prog list` 在你跑脚本时看得到、Ctrl-C 后立刻消失
- 想让程序脱离 Python 独立存在？**BCC 不是干这个的**：要么用 `pin_path=` 钉到 bpffs，
  要么直接 `bpftool prog load ... pinmaps /sys/fs/bpf/xxx`（[Ch4 §2 对象生命周期](../../chapter-04-bpf-syscall/)）

## 11. HFT / 嵌入式关联

| 认知 | 关联 |
|---|---|
| eBPF 程序**执行不依赖用户态进程**（§3.3 t4） | 探针的常驻开销与"有没有 Python 在跑"无关；Python 只影响**数据消费侧**的抖动，这也是观测工具要用独立进程读 ringbuf 的原因 |
| BCC **每次运行都现场编译** | 交易机上不可能有这套东西（无 clang、无内核头文件、启动秒级延迟）→ **BCC 只属于开发机**；生产侧必须是预编译 + CO-RE，或纯 bpftrace 脚本 |
| `trace_print()` 文本解析 + 丢事件静默（§4.4） | 高频路径每秒几千条事件，trace_pipe 必丢**且你不会知道** → 延迟测量一律走 ring buffer |
| `atexit` cleanup（§9） | 反过来看是好事：探针不会泄漏。交易机上"探针没摘干净"是真实风险 —— 每个 kprobe 都带 int3/trampoline 开销，会污染被测路径 |
| `attach_kprobe` 报 "inlined"（§4.3） | 交易机内核常开激进内联优化 → 想挂的 C 函数可能根本没有独立函数体。选挂点优先 syscall 入口 / tracepoint |
| tracepoint 的 `args` 来自 tracefs 文本（§7） | **无 BTF 内核上唯一低成本的结构化观测入口**，见下 |

### 11.1 嵌入式/树莓派专条：无 BTF 的机器上 BCC 还能不能用？

你的 Pi 5（aarch64，6.18 内核，`CONFIG_DEBUG_INFO_BTF` 未开）上要**分两半看**：

| 路线 | 需要内核头文件 | 需要 BTF | 说明 |
|---|---|---|---|
| kprobe 挂**内核 C 函数**（hello.py / hello-map.py / hello-buffer.py） | ✅ | ❌ | 需要能 include 内核头；且**被内联的函数挂不上** |
| `TRACEPOINT_PROBE` 挂 **tracepoint**（hello-file.py） | ❌ | ❌ | `args` 结构由 BCC 读 tracefs 的 `format` 文本现场生成 |
| ringbuf / map / helper | ❌ | ❌ | 与 BTF 无关 |
| **CO-RE**（`vmlinux.h`、字段重定位） | ❌ | ✅ | ⛔ **你的机器上此路不通**（[5.1](../../chapter-05-core-btf-libbpf/notes/5.1_BCC之弊与CO-RE要素.md)，lab02 的手工 format 绕行方案） |

**机制上可以这样推，但尚未在 Pi 上实测**（`python3-bpfcc` 包能否安装、clang 版本是否够新都待验证）——
真机跑通前，本节结论标注为**推断**而非实测结论。

> 顺带一条呼应：ebpf-gate 的 lab02 在 libbpf 路线下是**手工照着 tracefs 的 `format` 文件写结构体**
> 来绕开无 BTF —— 而 BCC 的 `TRACEPOINT_PROBE` 把这一步**自动化**了。同一个信息源，一个手工抄、一个自动生成。

<details>
<summary>参考答案</summary>

**1.** 去掉 `r`，C 代码里的 `\n` 会被 Python 先解释成真换行符再拼进字符串，交给 clang 的源码变成跨行字符串字面量 → clang 报 **`missing terminating " character`**（C 的字符串字面量不能跨行）。eBPF 的 printk 几乎都带 `\n`，所以 BCC 例子一律 `r"""`。三引号本身只为跨行方便，不是 BCC 语法。

**2.** 返回 **`__arm64_sys_execve`**。算法很妙：BCC **不去查 execve**，而是拿 bpf 这个 syscall 自己的符号按前缀表顺序去 `/proc/kallsyms` 试探 —— `sys_bpf` ✗ → `__x64_sys_bpf` ✗ → `__x32_compat_sys_bpf` ✗ → `__ia32_compat_sys_bpf` ✗ → **`__arm64_sys_bpf` ✓** → 得到前缀 `__arm64_sys_` → 拼上参数名。x86_64 上对应命中 `__x64_sys_bpf` → `__x64_sys_execve`。若 8 个候选全落空则回退 `sys_`（注释写明 "would probably lead to error"）—— 静默降级，不报错。

**3.** **不能**。C 源码对 clang 而言只是一段纯文本，`program` 是个 `str` 对象，两侧变量/类型互不可见；传值只能走 map。Python 侧能访问 `.command`，是因为 **BCC 解析了你那段 C 源码里的 `struct data_t`，用 ctypes 生成了同名结构** —— 同一份定义被两侧各读一遍，不是"共享"。代价：两侧定义不同步时读出乱码且**不报错**。

**4.** 报错原文 `it's not traceable (either non-existing, inlined, or marked as "notrace")` 已经把答案写了：① 符号不存在；② **被内联**（最常见 —— 挂普通 C 函数时，编译优化后没有独立函数体，kprobe 无处下断点）；③ 标了 `notrace`。排查手段：`BPF.get_kprobe_functions(re)` 列出可挂函数。缓解：优先选 syscall 入口或 tracepoint，别挂可能被内联的辅助函数。

**5.** `attach_tracepoint(tp="category:name")` **要带冒号**（BCC 内部 `tp.split(b':')` 拆成 category + name，再调 `bpf_attach_tracepoint`）；`attach_raw_tracepoint(tp="sys_enter")` **不带冒号**，直接给 tracepoint 名字。写反报 `Failed to attach BPF program ... to tracepoint`。

**6.** **不在了。** `BPF.__init__` 里 `atexit.register(self.cleanup)`，退出时 detach 所有 probe、清理 perf ring、关闭所有 BPF 程序与 map 的 fd → 内核引用计数归零，程序销毁。所以 `bpftool prog list` 在 Ctrl-C 前后会看到不同结果。想留下来：BCC 不是干这个的，用 `pin_path=` 钉到 bpffs，或 `bpftool prog load ... pinmaps /sys/fs/bpf/xxx`。

**7.** 返回 `("Unknown", 0, 0, "Unknown", 0.0, "Unknown")` —— **假数据，不抛异常**。而且 `trace_fields()` 还会 `if line.startswith(b"CPU:"): continue` 主动跳过丢事件告知行。两者叠加的后果：trace_pipe 丢事件你不会知道，格式解析失败你拿到的也是"看起来正常"的 Unknown 行。**用它做日志落盘/告警前必须先想清楚**，生产一律换 ring buffer。

**8.** `TRACEPOINT_PROBE(cat, name)` 宏把函数改名为 `tracepoint__syscalls__sys_enter_openat`，`BPF.__init__` 末尾的 `_trace_autoload()` 扫描到 `tracepoint__` 前缀就自动 load + attach（同理 `kprobe__`/`kretprobe__`/`raw_tracepoint__` 前缀）。`args->filename` 的类型**既非内核头文件也非 BTF**：BCC 前端编译时去读 `/sys/kernel/debug/tracing/events/syscalls/sys_enter_openat/format`（纯文本，列出每个字段的名与偏移），现场生成 `struct args` 塞进源码。

**9.** ① **每次运行都现场编译** → 目标机必须有 clang + 内核头文件，交易机/容器/嵌入式常年没有，且启动有秒级延迟；② 大规模同构机器上逐台重复编译，浪费算力；③ 高频场景下 BCC 的 Python 消费侧（GIL、GC、解释器抖动）本身就是噪声源；④ 嵌入式设备内存不够跑编译。（书上还列了分发与容器镜像的问题。）→ **BCC 属于开发机，生产侧走预编译 + CO-RE 或纯 bpftrace。**

**10.** 至少两处：① `BPF_HASH(name)` / `BPF_PERF_OUTPUT(name)` / `BPF_RINGBUF_OUTPUT(name, sz)` 是 BCC 宏，libbpf 要写成 `SEC(".maps")` + `__uint(type, ...)` / `__type(key, ...)`；② `map.lookup(&k)` / `map.update(&k,&v)` / `output.perf_submit(...)` 这种"对象方法"不是合法 C，BCC 在编译前做**文本重写**成 `bpf_map_lookup_elem()` / `bpf_perf_event_output()`，libbpf 必须手写这些调用。③ 附带：`TRACEPOINT_PROBE` 宏和 `args` 自动类型也是 BCC 专有。这就是书上说的"代码不可移植，等于绑死 BCC 生态"（[5.1](../../chapter-05-core-btf-libbpf/notes/5.1_BCC之弊与CO-RE要素.md)）。

</details>
