## 4.8 坑点清单

1. **fd 是进程私有的**——跨进程传 fd 数字没有意义（同一 map 两个进程 fd 值不同）。跨进程引用必须走 id 空间：`BPF_MAP_GET_FD_BY_ID` 翻译（[4.4](./4.4_遍历map的syscall序列.md)）；libbpf 还有基于 pin 路径的 `bpf_obj_get()`——路径是跨进程的稳定名字
2. bpffs 是内存伪文件系统：**重启后 pin 的程序全部消失**，开机自启要靠 systemd/skeleton 重载——"部署"一个 eBPF 程序 = 二进制 + 重载机制，缺一不可
3. BCC 程序 Ctrl+C 程序即卸载；想持久必须 pin 程序（或用 libbpf 的 link pin）——调试工具"随用随走"是特性，常驻 agent"必须 pin"是纪律
4. strace 里 `expected_attach_type` 出现网络类值不代表程序是网络程序（默认 0 占位，恰好是 `BPF_CGROUP_INET_INGRESS` 的枚举值）——[4.1 真机佐证 ⑤](./4.1_bpf总览与strace实例.md) 确认该字段只对部分程序类型有意义
5. perf buffer 每核一缓冲，事件跨核乱序；需要时间序就用 ring buffer（5.8+）——**乱序不是 bug 是 per-CPU 设计的代价**，见 [4.3](./4.3_perf与RingBuffer.md) 对比表
6. max_entries=10240 这种"魔法数字"是 BCC 默认，生产要显式设定——容量规划：条目数 × value 大小 × 2（hash 负载因子）就是内存预算
7. （真机补充，lab04）libbpf 的 fd 陷阱：MAP_CREATE 返回 6、UPDATE 却用 map_fd=4——libbpf 用 memfd 预留低位 fd 槽位再 dup3 顶进；**只看过滤后的 strace 会以为 fd 乱跳，必须看全量**

## 4.9 HFT 关联

### 1. 这一章就是"eBPF 的 TLPI 时刻"

与 03-linux-userspace-api 模块学 perf_event_open/ioctl 的路径打通——eBPF 追踪**复用 perf 子系统的基础设施**（kprobe 是动态注册的 PMU），理解 perf_event_open 的 type/config/pid/cpu 四元组才能理解 kprobe 挂载为何长那样。系统调用的知识在 eBPF 这里直接变现。

### 2. ring buf + epoll 是用户态收集内核事件的标准范式

与行情网关的 epoll 收包同构（同一套 fd 事件驱动模型）。**跨核保序**对延迟直方图/事件序列重建至关重要：perf buffer 各核独立缓冲，聚合时"到达序"≠"发生序"——重排两个事件的先后，延迟归因就南辕北辙。5.8+ 内核上 ring buffer 是唯一正确选择。

### 3. 引用计数的 pin 机制用于常驻观测 agent

交易机上 eBPF 监控随开机加载、独立于加载器进程存活——机器重启自动重载需要落地为 systemd unit（OnFailure 重试 + ExecStartPre 检查内核版本）。**"程序活着"的三重保障**：link pin（附加关系）+ map pin（状态数据）+ systemd（重载入口）。

### 4. strace -e bpf 是排查"eBPF 工具为何加载失败"的第一工具

看 BPF_PROG_LOAD 返回值即知验证是否通过（负值=失败，stderr 有验证器日志）；perf_event_open 返回 ENOENT=kprobe 符号不存在；BPF_LINK_CREATE 返回 EPERM=权限不足。比"工具报了个错"的黑盒信息量大一个数量级——**先 strace 再 Google** 的纪律在 eBPF 侧同样成立。

### 5. dump 序列是监控 agent 的实现路径

Prometheus exporter 暴露 eBPF 指标 = GET_NEXT_KEY + LOOKUP 循环（[4.4](./4.4_遍历map的syscall序列.md)）——LOOKUP 是拷贝语义，大 value 高频轮询有成本，采集间隔要和直方图聚合窗口匹配。

## 4.10 自测题

1. bpf() 三个参数各是什么？内核里的 eBPF 程序访问 map 走什么路径？
2. BPF 对象的引用计数有哪四种来源？追踪类与网络类程序的差异？
3. 挂 kprobe 需要哪三个 syscall（按序）？为什么挂 raw tracepoint 只需一条 bpf()？
4. PERF_EVENT_ARRAY 里的条目数由什么决定？ring buffer 为何没有这个问题？
5. ppoll 和 epoll 管理 fd 集合的本质区别？
6. `bpftool map dump name config` 在找 map 和读元素两个阶段各用什么命令迭代？

<details>
<summary>参考答案</summary>

**1.** `int bpf(int cmd, union bpf_attr *attr, unsigned int size)`——cmd 是命令（MAP_CREATE/PROG_LOAD/…），attr 是联合体参数，size 是 attr 字节数。内核里的 eBPF 程序访问 map **不走 syscall**，走 helper 函数（`bpf_map_lookup_elem()` 编译成 `call imm=<helper号>`）；syscall 接口只属于用户态。

**2.** 四种来源：①fd（进程退出即减）、②bpffs pin 文件（rm 即减）、③hook 附加（detach 即减）、④BPF link（link 活着程序就活）。差异：追踪类附加**与用户态进程绑定**（perf_event_open 的 fd 进程退出即失效）；网络栈/cgroup 类**不绑定进程**（ip link 挂的 XDP 命令退出后仍在）。

**3.** `perf_event_open({type=kprobe_PMU})` → `ioctl(fd, PERF_EVENT_IOC_SET_BPF, prog_fd)` → `ioctl(fd, PERF_EVENT_IOC_ENABLE)`。raw tracepoint 一条 `bpf(BPF_RAW_TRACEPOINT_OPEN)` 搞定——因为 kprobe 是动态注册的 perf PMU 事件（复用 perf 子系统），而 raw tracepoint 的挂点是内核静态注册的，BPF syscall 能直接定位。

**4.** 条目数 = **CPU 核数**（每核一个 perf 缓冲，key 是 CPU id）。ring buffer 全局单缓冲（内部 reserve/commit 两阶段），无每核概念——所以也没有 perf buffer 的跨核乱序问题（提交保序）。

**5.** ppoll 每次调用把整个 fd 集合从用户态拷进内核、返回后再拷回就绪集合（O(n) 每次扫描）；epoll 的集合由**内核对象**持有（epoll_ctl 注册一次），就绪 fd 通过回调挂链表，epoll_wait 只取链表（O(1)）。

**6.** 找 map 阶段：`BPF_MAP_GET_NEXT_ID`（下一个 id）+ `BPF_MAP_GET_FD_BY_ID`（换 fd）+ `BPF_OBJ_GET_INFO_BY_FD`（拿名字比对），ENOENT 终止。读元素阶段：`BPF_MAP_GET_NEXT_KEY`（key=NULL 起步，游标即 key 本身）+ `BPF_MAP_LOOKUP_ELEM`，ENOENT 终止。

</details>
