## 5.1 BCC 的老方案为什么不行

BCC 的思路：**在目标机器上运行时现场编译** eBPF 源码（源码作为字符串嵌在 Python 脚本里，运行时交 Clang 编译）。痛点（原文列举）：

1. 每台目标机都要装**编译工具链 + 内核头文件**（头文件默认往往不存在——服务器最小化安装的常态）
2. 每次启动工具都要等编译，**数秒延迟**
3. 大规模同构机器集群上逐台重复编译，**浪费算力**（100 台机器编译 100 次同一个程序）
4. 打进容器镜像能解决分发，但解决不了内核头文件缺失，多个 BCC 容器还会互相重复
5. **嵌入式设备内存不够**跑编译（BCC 交叉编译不可用的结论在 [06.6 4.1 危机工具](../../../../06.6-systems-performance/chapter-04-observability-tools/notes/section-4.1-工具覆盖范围与危机工具.md) 已展开）

**还有一条书中没列但工程上更痛的**：BCC 方言的 C 不是标准 C——`BPF_RINGBUF_OUTPUT`、对象方法等宏只在 BCC 里有（[10.3 坑点 4](../../chapter-10-programming/notes/10.3_坑点HFT关联与自测.md)），代码不可移植到 libbpf，等于绑死在 BCC 生态。

> 作者原话：如果你要开发一个正经的新 eBPF 项目、尤其是要分发给别人用，**不推荐**传统 BCC 方式。BCC 适合学习和快速原型（Python 用户态代码简洁）；BCC 仓库自己都把工具迁移到了 `libbpf-tools/` 目录（C + libbpf + CO-RE 版本）。

**BCC 没死**：作为**运行时**它退役了（生产分发场景），作为**工具集入口**它还活着——`bcc-tools` 包里的 runqlat/biolatency 依然是运维第一反应的观测武器（[06.6 4.1](../../../../06.6-systems-performance/chapter-04-observability-tools/notes/section-4.1-工具覆盖范围与危机工具.md) 的危机工具包清单）。准确表述：**BCC 的开发范式退役，BCC 的工具资产永存**。

## 5.2 CO-RE 五要素

CO-RE（Compile Once, Run Everywhere）的核心命题：**在开发机上编译一次，产出的字节码能在不同内核版本的目标机上运行**。破题思路：编译时不知道目标内核的结构布局 → 把"结构布局依赖"变成**加载时重定位**。

| 要素 | 作用 | 缺了会怎样 |
|---|---|---|
| **BTF** | 描述数据结构与函数签名的格式；用来对比"编译时布局"与"运行时布局"的差异。5.4 起内核自带（需 `CONFIG_DEBUG_INFO_BTF`） | 无法知道目标内核的 `task_struct` 长什么样，重定位无从谈起 |
| **内核头文件** | 不再逐个 include 内核头文件，用 `bpftool` 生成一个 `vmlinux.h` 全量搞定（把整个内核的类型定义压成一个头） | 手写结构定义 → 布局漂移 → 静默读错内存（无 BTF 的树莓派内核正是这状态） |
| **编译器支持** | Clang 加 `-g` 编译时生成 CO-RE 重定位信息（`.BTF.ext` 段里的 `preserve_access_index` 标记——字段访问不硬编码偏移，留待重定位）。GCC 12 起也支持 BPF 目标的 CO-RE | 字节码里偏移写死，换内核就读错字段 |
| **重定位库** | 加载时改写字节码适配目标内核：C 用 libbpf，Go 用 cilium/ebpf，Rust 用 Aya | 没人执行重定位，CO-RE 只是纸面能力 |
| **BPF skeleton**（可选） | `bpftool gen skeleton` 自动生成的生命周期管理代码（open/load/attach 一条龙 + 类型安全的对象访问），比裸调库方便 | 手写几十行样板代码，容易漏 attach/cleanup |

**重定位发生在哪一刻**：libbpf 加载 `.o` 时——读目标内核的 BTF（`/sys/kernel/btf/vmlinux`）、对比编译时嵌入的 BTF、把字节码里的字段偏移改成目标内核的值，然后才 PROG_LOAD。**"一次编译"的字节码在每台机器上被微调成各自的版本**——这是 CO-RE 与"为每个内核版本编译一份"的分发模型的本质区别。

**CO-RE 的适用边界**（与 [06.6 15.1.7 BCC vs bpftrace](../../../../06.6-systems-performance/chapter-15-bpf/notes/section-15.1.7-BCC-vs-bpftrace.md) 的升格工作流衔接）：结构布局差异可以重定位，但**语义差异**（函数改名、逻辑重构）重定位不了——内核大版本跳跃后仍需回归测试。真机佐证：6.18 的 `do_sys_openat2` 参数已从 `struct filename *` 重构为 `const char __user *`（[7.1 真机](../../chapter-07-program-attachment-types/notes/7.1_程序类型全景.md)）——这种变化 CO-RE 挡不住，只有挂点选稳定接口（tracepoint/syscall 入口）才稳。
