## 10.4 测试与性能统计

**BPF_PROG_RUN**：用户态直接运行 eBPF 程序做测试——不走真实事件，而是**喂入构造的 ctx**（如伪造的 skb），检查输出。目前主要支持网络类程序类型（XDP/TC 最好用）。价值：**单元测试内核态代码不需要内核事件**——CI 里就能回归"这个 XDP 程序对恶意包返回 DROP"。

**运行时统计**：

```sh
sysctl -w kernel.bpf_stats_enabled=1
bpftool prog list     # 多出 run_time_ns / run_cnt 字段
# 例：run_time_ns 316876 run_cnt 4 → 4 次执行共 ~300μs（均值 ~79μs/次）
sysctl -w kernel.bpf_stats_enabled=0   # 用完关掉——统计本身有开销
```

两个数字的用法：**run_cnt 验证挂点**（零触发=挂错点或路径不通，呼应 [7.2](../../chapter-07-program-attachment-types/notes/7.2_坑点HFT关联与自测.md) 真机教训）；**run_time_ns/cnt 评估探针税**（每次事件的平均耗时 × 事件速率 = 观测总开销——挂上探针前后对比业务延迟，就是 [06.6 4.6 观测者效应](../../../../06.6-systems-performance/chapter-04-observability-tools/notes/section-4.6-观测的观测Observing-Observability.md) 的量化实验在 eBPF 侧的落地）。

## 10.5 多 eBPF 程序的协作

一个 eBPF 程序 = 一个函数 + 一个事件；真实应用（如 opensnoop）需要**多个程序协同**：

**协作模式一：entry/exit 配对**（[10.1](./10.1_语言与库全景.md) 的 opensnoop.bt 范式）——程序之间**本质独立，靠 map 协调**：entry 程序写 map（`@filename[tid]`），exit 程序读删 map。**跨程序状态只有 map 一个载体**——没有全局变量共享（每个程序的全局变量是自己的 .bss map）、没有进程内存共享。

```
entry 程序 ──写──> hash map（key=tid, value=filename）<──读+删── exit 程序
                                                        │
                                              中途退出的 tid？→ map 残留（泄漏！）
```

配对的工程隐患：entry 有 exit 无（进程崩溃在中间）→ map 条目泄漏——生产 agent 要加定期清理或 map 容量上限告警。

**协作模式二：动态程序集**——程序数量**动态变化**：Cilium 给每个虚拟网卡挂程序，Pod 增减时接口来去。这对加载器提出"生命周期管理"需求（按需 load/attach/detach/close），skeleton 的 open/close 模型正好承接。

**协作模式三：尾调用链**——PROG_ARRAY 串起多个程序接力（[7.2](../../chapter-07-program-attachment-types/notes/7.2_坑点HFT关联与自测.md) 的 XDP 内部分发）。

骨架类工具（libbpf / ebpf-go）一条调用加载**全部**程序与 map（对象集合来自 ELF 的段扫描），也提供单个对象的细粒度操作——"整队加载、按个管理"。

## 10.6 选型速查（作者结论）

| 场景 | 选择 | 一句话理由 |
|---|---|---|
| 快速收集 trace 信息 | bpftrace | 一行命令、零编译等待 |
| Python 快速原型、不在乎运行时编译 | BCC | Python 用户态代码简洁、迭代快 |
| 生产分发、跨内核版本可移植（CO-RE） | C: libbpf；Go: cilium/ebpf 或 libbpfgo；Rust: Aya | 单一二进制、无编译器依赖 |
| Rust 全栈（内核+用户态同语言、无 LLVM 依赖） | Aya | rustc 直编 eBPF、类型安全全链路 |

选型的隐藏维度（补充）：**团队已有技能栈** > 语言本身优劣——Go 团队用 cilium/ebpf、C 团队用 libbpf 的落地成功率远高于"为了 eBPF 换语言"。与 [06.6 15.1.7 BCC vs bpftrace](../../../../06.6-systems-performance/chapter-15-bpf/notes/section-15.1.7-BCC-vs-bpftrace.md) 的升格工作流（bpftrace 即兴 → BCC/预制 → libbpf 升格）拼起来，就是完整的工具链演进地图。
