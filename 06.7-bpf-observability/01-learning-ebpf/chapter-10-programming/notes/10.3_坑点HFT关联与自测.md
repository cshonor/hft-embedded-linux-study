## 10.7 坑点清单

1. **bpftrace/BCC 基于 syscall 入口的工具有 TOCTOU**（第 9 章）——观测可用，别当安全防线；同一挂点"观测工具"和"安全工具"是两个信任等级
2. gobpf 已停止维护——新项目别选（Go 侧首选 cilium/ebpf）
3. libbpfgo 的 CGo 边界（"cgo is not Go"）可能带来性能/构建问题——对延迟敏感选纯 Go 的 cilium/ebpf；CGo 的调用开销在事件回调路径上会被放大
4. BCC 的"类 C 方言"不是标准 C：`BPF_RINGBUF_OUTPUT`、对象方法等宏只在 BCC 里有——代码不可移植到 libbpf，**用 BCC 原型时就要按"将来要重写"来设计**
5. cilium/ebpf 生成两套字节码（大端 bpfeb / 小端 bpfel）——交叉编译时确认架构选对了 `.o`；选错端的症状是加载失败或程序行为诡异（字段字节序颠倒）
6. `bpf_stats_enabled` 统计本身有开销，测完记得关——开着跑性能基准，测出来的数被统计污染
7. 内核侧 C 用户侧也 C 时，用户态代码**没有验证器兜底**——map 读写、缓冲区处理全靠自己；用户态段错误照样崩 agent（虽然不伤内核，但观测数据流断了）

## 10.8 HFT 关联

### 1. 低延迟监控工具就该单一二进制

cilium/ebpf + bpf2go 或 libbpf 骨架产出**无依赖单文件**（.o 嵌入二进制），push 到交易机零安装成本、可审计（SHA 哈希可校验——第 11 章签名问题落地前的现实解）。对比 Python 版工具：opensnoop libbpf 版 ~9MB vs BCC 版 ~80MB，差的 71MB 主要是 LLVM/Clang 运行时——交易机上每一 MB 的部署面积都是攻击面和审计成本。

### 2. opensnoop 式 entry/exit 配对直接可抄

交易程序挂单路径计时（entry 存时间戳，exit 取出算差值，hist map 出分布）就是同一模式——**从书里的 opensnoop 到 HFT 的 tick 分段计时，只差把"文件名"换成"时间戳"**。配对时注意 [10.2](./10.2_测试统计与程序协作.md) 的 map 泄漏问题：线程中途退出时 entry 状态残留，定期清理。

### 3. bpf_stats_enabled 是免费的性能回归探针

交易机常规 eBPF 程序的 run_time_ns/run_cnt 定期采集——**探针自己的延迟分布也在监控之列**（观测工具的性能也需要观测，[06.6 4.6](../../../../06.6-systems-performance/chapter-04-observability-tools/notes/section-4.6-观测的观测Observing-Observability.md) 的递归应用）。基线上突然的 run_time_ns 抬升 = 内核升级/环境变化影响了探针执行 → 观测数据的可信度先于业务指标受影响。

### 4. bpftrace 适合运维快速排查，生产常驻 agent 用 CO-RE 栈

"这台交易机现在谁在疯狂 open 配置文件？"——bpftrace 一行搞定（分钟级响应）；而常驻 agent（tick 分段计时、syscall 白名单记录）必须是 CO-RE 单二进制（月级无人值守运行）。**两个层次对应值班的不同时刻**：bpftrace 是"现在出事了"的第一反应，CO-RE agent 是"一直都在看着"的常驻哨兵。

### 5. 用户态无验证器 = agent 的内存纪律

内核侧有验证器兜底，用户态 C 侧没有——**agent 崩了不伤内核但断数据流**（交易机上"监控静默"本身就是事故）。工程对策：用户态侧用带边界检查的库 API（libbpf 的 `bpf_map_lookup_elem` 封装了拷贝长度）、事件解析代码 fuzz 测试（恶意/畸形事件不应崩 agent——观测面是攻击面）。

## 10.9 自测题

1. eBPF 编程的哪两半？bpftrace 如何把两者对程序员透明？
2. opensnoop 为什么必须同时挂 syscall 的 entry 和 exit？两个程序间如何传数据？
3. 为什么 Go/Java 不能作为内核侧 eBPF 语言？
4. BCC 的 `BPF_RINGBUF_OUTPUT` 一行为什么同时服务于内核和用户态？
5. libbpf 版 opensnoop 9MB vs Python 版 80MB，差的 71MB 是什么？
6. cilium/ebpf 的 bpf2go 生成哪些文件？为什么有两套字节码？
7. libbpfgo 与 cilium/ebpf 的架构差异是什么？各自的顾虑？
8. Aya 与 Redbpf、libbpf-rs 的本质区别？为什么 lockc 迁移到 Aya？
9. 如何查看一个已加载 eBPF 程序的运行次数与总耗时？
10. 多 eBPF 程序的应用中，程序之间如何协调？

<details>
<summary>参考答案</summary>

**1.** 内核侧（eBPF 程序，编译成字节码加载进内核）+ 用户侧（加载器/消费者，读 map 收事件）。bpftrace 用一门高层语言把两半都生成：脚本编译成 eBPF（内核侧）+ 内置 runtime 管理加载和输出（用户侧）——程序员完全感知不到分界。

**2.** entry 拿参数（文件名），exit 拿结果（fd/errno）——单一挂点拿不齐（syscall 执行中参数寄存器会被覆盖）。传数据：hash map，key=tid，entry 写 `@filename[tid]`，exit 读+delete。

**3.** 带运行时的语言：①GC 与验证器的内存检查模型不兼容（验证器要求所有内存访问可静态证明）；②eBPF 程序必须单线程，语言的并发/调度运行时没有落点；③运行时本身装不进 512B 栈和验证约束。

**4.** BCC 的宏在预处理期同时展开成两份：内核侧的 map 定义（BPF_MAP_TYPE_RINGBUF 创建）+ 用户侧的 Python 对象（ring buffer 消费接口）——**一行源码、两个世界的胶水**，这也是 BCC 方言不可移植的原因（标准 C 没有这种"一鱼两吃"机制，libbpf 用 skeleton 生成达到同效）。

**5.** LLVM/Clang 工具链及其运行时库——BCC 每次启动都要在目标机现场编译，二进制里背着整个编译器；libbpf 版预编译完成，只带字节码和轻量加载库。

**6.** 生成 `bpf_bpfeb.o`/`bpf_bpfel.o`（字节码）+ 对应 `.go` 文件（类型安全的骨架：bpfObjects/bpfPrograms/bpfMaps 结构 + load/attach 函数）。两套字节码是因为 eBPF 字节码里的内存访问**字节序跟随目标架构**（大端目标机 bpfeb / 小端 bpfel）——编译期不知道部署目标就两边都生成，链接时按 GOARCH 选。

**7.** libbpfgo 是 libbpf 的 **CGo 封装**（复用 C 库的全部功能，但跨语言边界有开销、构建要 CGo 工具链）；cilium/ebpf 是**纯 Go 重实现**（无 CGo、系统调用直达，但功能跟随要自己追）。顾虑：前者 cgo is not Go；后者重实现的完整度/成熟度。

**8.** Aya 是**纯 Rust、直达 syscall**，不依赖 libbpf/BCC/LLVM——内核侧 Rust 代码由 rustc 直接编 eBPF（无需 clang），且实现了与 libbpf 相同的 CO-RE 重定位；libbpf-rs 是 libbpf 封装（内核侧仍写 C）、Redbpf 走 LLVM 多步编译。lockc 迁到 Aya：全栈 Rust 单一工具链、无 C 依赖，部署和交叉编译都简单。

**9.** `sysctl kernel.bpf_stats_enabled=1` 后 `bpftool prog list` 出现 run_time_ns/run_cnt 字段；用完关掉（统计本身有开销）。

**10.** 程序本质独立，协作靠三种机制：①**map 共享状态**（entry/exit 配对：一个写一个读删）；②**PROG_ARRAY 尾调用**（接力分发，策略数据化）；③**加载器编排**（skeleton/agent 管理程序集合的生命周期，动态增减）。

</details>
