# 1. 背景知识（16.1）

> 底本：《BPF之巅》第 16 章 虚拟机管理器，16.1 节（印刷 p719–722）

本章讨论 BPF 工具与**硬件虚拟化**虚拟机管理器（Xen、KVM）的配合使用。操作系统级虚拟化（容器）已在第 15 章讨论。学习目标：

- 理解虚拟机管理器的配置和 BPF 的跟踪能力
- 在可能的情况下，用 BPF 跟踪客户系统（Guest）的 hypercalls 入口点和出口点
- 汇总被盗用的 CPU 时间

## 两种常见 hypervisor 配置

经典分类把 hypervisor 分为 1 型 / 2 型 [Goldberg 73]，但随着 2 型通过内核模块实现，区别已越来越小。两种常见配置（图 16-1）：

| 配置 | 描述 | 代表 |
|---|---|---|
| **A：本机/裸机管理器** | hypervisor 直接运行在处理器上，负责创建域并把虚拟 CPU 调度到真实 CPU；特权域（零号域）管理其他域 | Xen |
| **B：宿主机内核运行管理器** | 由内核态模块 + 用户态进程组成；宿主机内核把虚拟 CPU 与其他进程一同调度；通过内核模块可提供直接硬件访问 | KVM |

两种配置都可能涉及在零号域（Xen）或宿主机 OS（KVM）上运行一个 **I/O 代理**（如 QEMU）来服务访客 I/O——这增加了 I/O 开销，多年以来通过共享内存传输等技术优化。

## 硬件虚拟化的演进

- 1998 年 VMware 率先推出，用二进制翻译执行完整硬件虚拟化 [VMware 07]
- **处理器虚拟化支持**：2005–2006 年 AMD-V / Intel VT-x 扩展，为虚拟机操作提供更快的硬件支持
- **半虚拟化（PV）**：修改过的操作系统知道自己运行在虚拟机上，对管理器发起**超级调用**（hypercall）更高效地处理某些操作；Xen 把超级调用**批处理为多重调用**（multicall）
- **硬件设备支持**：SR-IOV（网络/存储设备）+ 专用驱动 ixgbe、ena、nvme
- 现代 Xen 通常以 HVM 引导 + PV 驱动，称 **PVHVM**；再进一步用 SR-IOV 完全依赖硬件虚拟化
- 2017 年 AWS 推出 **Nitro**（部件基于 KVM），为处理器、网络、存储、中断、计时器全部提供硬件支持，**没有使用 QEMU 代理**

## BPF 的分析能力（16.1.1）

硬件虚拟机运行自己的内核，因此**可以在客户系统上直接使用 BPF 工具**。客户系统中 BPF 能回答：

- 虚拟化的硬件资源性能如何？（用前面章节的工具）
- 若使用半虚拟化，作为管理器性能指标的**超级调用延迟**是多少？
- CPU **被盗用**的频率和时长？
- 虚拟机管理器**中断回调**会干扰应用程序吗？

在宿主机上（云厂商有宿主机访问权，最终用户没有）BPF 还能回答：

- 若使用 QEMU，访客系统的工作负载情况及性能？
- 对 B 型配置的管理器，访客系统出于什么原因进行管理器调用？

### AWS EC2 实例的演变——可跟踪目标越来越少

管理器从仿真 → 半虚拟化 → 硬件支持演进时，事件移至硬件层，访客系统内可跟踪的目标越来越少：

| EC2 实例类型 | 访客内可跟踪目标 |
|---|---|
| PV | 超级调用（多重调用）、管理器回调、驱动程序调用、被盗用的时间 |
| PVHVM | 管理器回调、驱动程序调用、被盗用的时间 |
| PVHVM + SR-IOV 驱动 | 管理器回调、被盗用的时间 |
| KVM（Nitro） | 被盗用的时间 |

Nitro 在访客系统中几乎没有运行虚拟机的代码——这是设计使然，通过把管理器功能移至硬件来提高性能。

## 建议的分析策略（16.1.2）

首先确定正在使用的管理器配置：是否使用超级调用或特殊设备驱动？

**对访客系统：**
1. 插桩超级调用（如果正在使用），检查是否有过多操作
2. 检查 CPU 被盗用的时间
3. 用前面章节的工具做资源分析——但记住这些是**虚拟资源**，可能受管理器/外部硬件施加的资源控制限制，也可能因与其他访客竞争而受影响

**对宿主机系统：**
1. 插桩虚拟机的**退出**（exit），检查是否有过多操作
2. 若使用 I/O 代理（QEMU），插桩该代理的工作负载和延迟
3. 用前面章节的工具做资源分析

随着管理器把功能转移到硬件（如 Nitro），将更多依赖前面章节的通用工具而非管理器专用工具。

## HFT 关联

- HFT 交易系统若部署在云上（如 AWS EC2 C 系列实例），理解实例类型（PV→Nitro）直接决定可观测性边界：Nitro 实例内基本只剩"被盗用时间"可测
- 低延迟场景关注两点：**steal time**（CPU 被邻居 VM 抢占 → 抖动）与**中断回调干扰**（16.3.3 的 xen_evtchn_do_upcall 延迟）
