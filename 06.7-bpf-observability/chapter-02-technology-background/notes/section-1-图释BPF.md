# 2.1 图释 BPF

> 底本：《BPF之巅》第 2 章技术背景，2.1 节（印刷 p17）

## 本节定位

全书第二章开篇用一张图回答一个问题：**BPF 程序到底运行在哪里、和事件源、缓冲区、前端工具是什么关系**。这张"BPF 图释"是理解后续所有章节的地图——后面每一章的工具（CPU、内存、网络……）都是往这张图的不同事件源上"挂"程序。

## 图中的四个组成部分

| 组成部分 | 作用 | 对应技术 |
|---|---|---|
| 事件源 | 触发 BPF 程序执行的契机 | kprobes / uprobes / tracepoint / USDT / PMC / perf_events |
| 内核态 BPF 程序 | 事件发生时在内核中运行的小程序 | 经验证器校验后的 eBPF 字节码 |
| 缓冲区 | 内核态 → 用户态的数据传输 | perf_events 环形缓冲区 / BPF map |
| 前端工具 | 编译、加载、呈现结果 | BCC / bpftrace / perf(1) |

把这张图展开成数据流（每个箭头都是后续某节的主题）：

```text
   事件源                BPF 程序                输出通道             前端
┌──────────┐  触发   ┌──────────────┐  写入  ┌──────────────┐ 读取 ┌─────────┐
│ kprobe   │ ──────▶ │              │ ─────▶ │ map（聚合）   │ ◀─── │         │
│ uprobe   │         │ 验证过的字节码│        │ perf 环形缓冲 │      │ BCC /   │
│ tracepoint│        │ + helper 调用 │        │ （逐事件）    │      │bpftrace │
│ USDT     │         │              │        └──────────────┘      │ perf(1) │
│ PMC 溢出 │         └──────────────┘                              └─────────┘
└──────────┘           ▲      │                          控制流：map 双向
                       │      └── 读内核状态（bpf_probe_read_kernel）
                       └── 用户态经 bpf(2) 加载程序、更新 map 参数
```

控制流与数据流是**双向**的：用户态前端不只收数据，还经 map 把运行时参数（PID 过滤值、阈值）写进内核态程序——这是 BCC 工具 `-p PID` 过滤的实现通道。

## 关键认知

1. **BPF 程序是"事件驱动"的**——不是常驻循环，而是事件发生时被调起运行的小程序。这决定了它天然适合观测（可观测性），而不是通用计算。
2. **数据处理尽量在内核完成**——直方图、计数、聚合都通过 map 在内核态做完，只把"结果"传回用户态，避免了传统跟踪器每事件一次内核↔用户态往返的开销（这也是 2.3 节论证 BPF 优于旧方案的核心）。
3. **事件源是可插拔的**——同一套 BPF 程序框架，换一个事件源就是另一类工具。第 2 部分各章的差异本质上就是事件源和所读内核状态的不同。

第 3 点是理解本书结构（也是写自己工具）的钥匙：学一个 BPF 工具 = 问三个问题——**挂在哪个事件源、读了什么内核状态、在 map 里聚合了什么**。第 2 部分十几个章节的几十个工具，全部能用这三问拆解。

## 逐事件 vs 聚合：输出通道的选择

图中"缓冲区"一栏其实藏着工具设计的第一决策：

| 输出模式 | 通道 | 数据量 | 适用 |
|---|---|---|---|
| 逐事件 | perf 环形缓冲 | ∝ 事件率 | *snoop 类：每个事件一行（opensnoop/biosnoop） |
| 聚合 | map | 与事件率解耦 | *latency/*count 类：直方图/计数表（biolatency/runqlat） |
| 混合 | map + 定期读 | 可控 | *top 类：定时快照 |

同一事件源配不同输出模式就是不同工具——`kprobe:vfs_read` + 逐事件打印 = biosnoop 风格；+ `@` 直方图 = vfs 延迟分布。**写工具先选输出模式，再写程序体**。

## HFT 关联

- HFT 低延迟系统的观测全景可以按这张图分类：哪个事件源最接近你的问题（收包 → 网卡/网络层探针；调度延迟 → sched tracepoint；锁竞争 → futex/uprobe）。
- "内核态聚合、只回传结果"对 HFT 尤其重要：行情风暴时每秒百万级事件，若每事件都拷贝到用户态，观测本身就会拖垮被观测系统。
- map 双向通道的用法：把交易进程 PID 提前写进 map，内核态程序比对过滤——观测噪声零外泄。
- 图中四组件 = 交易机观测方案的四个检查项：事件源选型（见 2.6 表）、程序复杂度预算（verifier 限制）、输出通道（风暴期禁逐事件）、前端部署（CO-RE 单二进制）。

## 自测

<details>
<summary>1. BPF 程序的执行时机是什么？</summary>

事件驱动的：事件源（探针/跟踪点/PMC 溢出等）触发时，内核调用挂载在该事件上的 BPF 程序。程序非常驻运行。
</details>

<details>
<summary>2. 为什么 BPF 工具强调"在内核态做聚合"？</summary>

避免每个事件一次内核↔用户态数据拷贝和系统调用开销。高频事件下（每秒百万级），用户态处理会把观测开销放大到不可接受，内核态直方图/map 聚合后只回传摘要。
</details>

<details>
<summary>3. 用户态前端如何把过滤参数（如 PID）传给内核态 BPF 程序？</summary>

经 map 双向通道：前端把参数值写进 map（BCC 在 attach 前初始化），BPF 程序在事件处理时查 map 比对，不匹配的事件直接丢弃——过滤发生在内核态，不占输出带宽。
</details>

<details>
<summary>4. 同挂 kprobe:vfs_read，为什么能做出两类完全不同的工具？差异在哪一层？</summary>

输出通道层：配 perf 环形缓冲逐事件输出 = snoopy 类工具（看单个 I/O）；配 map 直方图聚合 = latency 类工具（看分布）。事件源相同，输出模式决定工具形态——这也是"写工具先选输出模式"的原因。
</details>
