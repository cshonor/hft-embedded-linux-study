# 函数调用

> 本节讲什么：eBPF 里怎么复用代码。历史包袱决定了两种形态——内联（老，到处用）和 BPF-to-BPF 调用（新，有限制）。还埋了一个 kprobe 挂不上的伏笔。

## 1. 背景：eBPF 的栈小得可怜

eBPF 栈只有 **512 字节**（verifier 强制），放不下几层调用帧。加上历史原因，早期 eBPF（4.16 之前）**禁止调用 helper 之外的任何函数**——你写两个函数互相调用，编译器可以编过，verifier 拒绝。

## 2. 方案一：内联（inline）——老程序的标准姿势

```c
static __always_inline int add(int a, int b) { return a + b; }
```

`__always_inline` 强制编译器把函数体**复制进每个调用处**（不是跳转指令，是代码展开）。效果：

```
源码:  x = add(a,1) + add(b,2)
机器码: 展开两份 add 函数体     ← 无 call/ret，无新栈帧
```

| 特性 | 内联 |
|---|---|
| 栈 | 不消耗（无新栈帧） |
| 指令数 | 每个调用点复制一份（浪费 1M 指令预算） |
| 递归 | 不可能（本质是宏展开） |

`static __always_inline` 是内核源码里到处可见的写法——eBPF 生态完全继承了这套习惯。

## 3. 方案二：BPF-to-BPF 调用（子程序）——4.16 + LLVM 6.0 起

内核 4.16 起，verifier 学会跟踪跨函数的寄存器/栈状态后，真正的函数调用（BPF 子程序）被支持：

```
主程序 ──call──▶ 子程序 ──ret──▶ 回到主程序
（共享同一 512 字节栈——栈在两者间传递使用）
```

**坑：BCC 不支持，libbpf 才能用**（第 3 章 §6 手工做时会真切碰到）。所以你在 BCC 时代的老代码里看到的全是 `__always_inline`。

## 4. 伏笔：内联毁了 kprobe

一个隐蔽的副作用：**编译器内联会消灭函数**。如果内核构建时把 `do_foo()` 内联进了 `do_bar()`，那内核镜像里根本没有 `do_foo` 的独立入口——kprobe 挂 `do_foo` 会失败（`Probe point is not found` 或挂上了但不触发）。

这正是 tracepoint 存在的理由之一：**tracepoint 是显式声明的插桩点，不受编译器优化影响**（你在 lab02 用 tracepoint 而不是 kprobe 挂 openat，天然避开了这个坑）。kprobe 灵活但脆（函数可能被内联/改名），tracepoint 稳定但点位固定——第 7 章的系统对比。
