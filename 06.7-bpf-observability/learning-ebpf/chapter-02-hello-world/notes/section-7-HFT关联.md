# HFT 关联

> 本节讲什么：第 2 章的四个构件（map / per-CPU / ring buffer / 尾调用）在 HFT 工程里的对应物。

## 1. per-CPU map + 用户态汇总 = 高频计数器标准架构

跨核共享计数器的问题：每次 `++` 都是对**同一条 cache line** 的争用——核 A 和核 B 同时改，一个核的写让另一个核的 cache line 失效（cache line bouncing），争用激烈时计数器本身成了热点。per-CPU map 让每核只写自己的副本，**零锁零争用**，用户态读时再汇总——与你 TLPI/CSAPP 里学的用户态 per-core 无锁计数完全同构：

```
核0: counter[0]++（私有cache line）  ┐
核1: counter[1]++（私有cache line）  ├─▶ 用户态定期读：sum(counter[0..N-1])
核2: counter[2]++（私有cache line）  ┘
```

**适用判断**：计数型指标（包数、事件数、丢弃数）一律 per-CPU；要精确 read-modify-write 序列的场景才考虑锁（或干脆移到用户态）。

## 2. ring buffer 的 drop 计数 = 观测数据的可信度

对 HFT 最典型的坑：**延迟直方图丢了最慢的那批样本**。突发延迟毛刺期恰好是事件洪峰期——用户态消费跟不上，buffer 溢出，毛刺样本被丢 → 直方图显示一切正常 → 调优方向全错。

工程规则：

- buffer 尺寸按**突发速率**（不是平均速率）留余量
- 工具侧**必须检查 drop 计数**并显式报告（丢了多少条要说出来，不能装没事）
- 越关键的指标，越要在"可能丢"和"可能慢但全"之间选后者（加大 buffer / 分流到独立 buffer）

## 3. 尾调用分发 = 内核态消息路由

§5 的 syscall 分发表结构，在 HFT 里的对应物：

- **行情多级处理**：XDP 收包 → 尾调用分发给"解析层程序" → "过滤层程序" → "转发/上送层程序"，每级独立加载替换，不用改整体
- **按 opcode/策略分发**：风控前置逻辑做成 map 配置，改路由不用重编 eBPF 程序——**把策略做成数据，不做成代码**（热更新的老智慧）
- 33 层上限对这个场景绰绰有余（实际链深 3-5 层）

## 4. 512 字节栈 = 延迟测量代码的纪律

栈 512 字节意味着：放不下大数组（一个 64 项的 u64 直方图就占满）、递归想都别想、连 `char fname[256]` 都要斟酌。对 HFT 测量代码的要求因此非常明确：

- **程序极简**：一个事件只做"取时间戳 + 写 map"级别的动作，复杂计算留给用户态
- **状态进 map**，不进栈——map 容量是 MB 级，栈只是临时草稿纸
- 大缓冲需求用 per-CPU array map 或 ring buffer，别想着栈上开

这其实是好事：小栈强制 eBPF 观测程序保持"薄探针"属性——**测量工具本身越薄，对被测路径的扰动越小**，数据才可信。
