# 自测题

> 先自己答，再展开参考答案。第 4、5 题建议动手验证（树莓派 + ebpf-gate 环境现成）。

1. trace_pipe 的三个局限是什么？生产环境用什么替代？
2. 加载 tracing 程序和 networking 程序分别需要哪些 capability？
3. `bpf_get_current_pid_tgid()` 和 `bpf_get_current_uid_gid()` 的 64 位返回值各字段怎么分布？
4. maps 的三大用途？per-CPU 变体解决什么问题？
5. 尾调用和普通函数调用的本质区别？为什么 eBPF 栈只有 512 字节使得尾调用更重要？
6. 33 层尾调用 × 100 万指令限制，对写复杂内核逻辑意味着什么？
7. （真机加餐）lab02 里为什么要用 `bpf_probe_read_user_str()` 拿 filename，而不是直接 `ctx->filename` 解引用？

<details>
<summary>参考答案</summary>

**1.** ①全机唯一，多程序混写无法区分；②只支持字符串无结构化；③锁+格式化开销大。替代：拉模式用 map（用户态轮询），推模式用 ring/perf buffer（事件驱动回调）——后者是标准答案。

**2.** `CAP_BPF`（5.8+）是基础；tracking 程序加 `CAP_PERFMON`，网络程序加 `CAP_NET_ADMIN`。root 全有。

**3.** **方向相反，最易写反**：`pid_tgid` 返回值 **高 32 位 = PID(tgid)、低 32 位 = 线程 ID**（取 pid 用 `>> 32`）；`uid_gid` 返回值 **低 32 位 = UID、高 32 位 = GID**（取 uid 用 `& 0xFFFFFFFF`）。

**4.** 用途：①用户态写配置→eBPF 读；②eBPF 跨事件/跨程序存状态；③eBPF 写结果→用户态展示。per-CPU 解决多核并发写同一计数器的 cache line 争用：每核独立副本免锁，用户态读时汇总——代价是内存×核数和跨核读不即时一致。

**5.** 本质区别：普通调用会返回（子程序共享调用者的 512 字节栈）；尾调用永不返回，被调程序**替换**调用者、栈从零开始（类比 execve 对进程）。栈只有 512 字节→调用链深了就爆栈，尾调用是唯一"串长逻辑不叠栈"的办法，还能绕过单程序指令数限制。

**6.** 意味着"复杂逻辑"要拆解：最多 33 个程序接力、每个程序内 ≤100 万条已验证指令；实际是引导你把策略做成 map 数据（查表分发）而非硬编码——总复杂度上限约 3300 万指令 + 无限的 map 容量，对观测类程序绰绰有余。

**7.** 因为 `ctx->filename` 是**用户态地址的指针**——syscall 参数本来就是用户传进来的。eBPF 程序跑在内核态，直接解引用用户地址：轻则数据错（用户页可能还没换入），重则崩内核。`bpf_probe_read_user_str()` 是 helper，内部用安全的用户态访问机制（处理缺页、跨页）拷贝到 eBPF 栈数组；verifier 会在加载时强制这一点——直接解引用根本到不了运行期。（你的真实案例：Ch2 坑点 7、lab02 README。）
