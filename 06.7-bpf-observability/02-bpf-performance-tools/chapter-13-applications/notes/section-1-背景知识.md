# 1. 背景知识（13.1 节）

> 底本：《BPF之巅》第 13 章 应用程序，13.1 节（印刷 p620–624）

前面的章节通过**资源**研究应用程序（CPU、内存、磁盘、网络），但会漏掉来自应用程序本身的线索——比如**当前正在处理的请求的细节**。本章补齐：静态/动态插桩可以直接研究应用程序本身，观测整个程序流程：应用代码 → 程序库 → 系统调用 → 内核服务 → 设备驱动。

## 13.1.1 应用程序基础信息

### 线程管理的四种模型

| 模型 | 工作方式 | 示例 | 风险/特征 |
|------|----------|------|-----------|
| **服务线程池** | 每线程一次只服务一个客户连接和请求；等资源时线程睡眠（含等线程池内其他线程的锁）；线程数可固定或动态 | **MySQL** | 请求等待→线程阻塞 |
| **CPU 线程池** | 每个 CPU 一个线程，持续处理队列任务（分钟/小时/天级） | 视频编码 | 批处理典型 |
| **事件处理器线程** | 一个或多个线程处理客户端工作队列直到空再睡眠；**一个线程同时服务多个客户端**；单线程可避开同步锁 | **Node.js**（单事件线程） | 高负载下单线程绑定 |
| **SEDA（阶段性事件驱动架构）** | 请求分解为多个阶段，每阶段由一个或多个线程池处理 | — | 阶段间队列衔接 |

### 锁与睡眠

- **锁**：多线程同步原语，像交通信号灯控制交叉路口——保护内存的同时**停止流量并产生等待延迟**。Linux 应用通常经 **libpthread** 使用：互斥锁（mutex）、读写锁（rwlock）、自旋锁（spinlock）
- **锁争用**：多个线程竞争同一把锁并阻塞等待
- **主动睡眠**：可能是合适的也可能不合适。经典历史 hack："加一个一秒的 sleep 确保等待的事件完成了，将来改成事件驱动"——**这个"将来"没有发生**，于是用户好奇为什么请求至少要一秒

## 13.1.2 应用示例：MySQL 服务器

- 服务线程池响应网络请求；大工作集→磁盘密集型，小工作集→CPU 密集型（内存缓存命中）
- **C++ 编写，内嵌 USDT 探针**。表 13-1 示例：

| USDT 探针 | 参数 |
|-----------|------|
| `connection__start` | unsigned long connection_id, char* user, char* host |
| `connection__done` | int status, unsigned long connection_id |
| `command__start` | unsigned long connection_id, int command, char* user, char* host |
| `command__done` | int status |
| `query__start` | char* query, unsigned long connection_id, char* db_name, char* user, char* host |
| `query__done` | int status |
| `filesort__start` | char* dbname, char* table |
| `filesort__done` | int status, unsigned long rows |
| `net__write__start` | unsigned long bytes |
| `net__write__done` | int status |

- **关键限制**：只有在编译时给 cmake 传 `-DENABLE_DTRACE=1` 的 MySQL 才有这些探针；**Linux 发行版自带的 mysql-server 包不带**。要么自己编译，要么要求包维护者。→ 本章因此同时提供 **uprobes 版**工具作为备胎

## 13.1.3 BPF 的分析能力

BPF 可以回答的七个问题（应用指标之外）：

1. 应用程序的**请求**是什么？延迟是多少？
2. 处理请求的**时间花在哪**？
3. **为什么在 CPU 上运行**？
4. **为什么阻塞并从 CPU 切换下来**？
5. 正在执行什么 **I/O** 以及原因（代码路径）？
6. 正在**等待什么锁**，等了多久？
7. 正在用哪些**内核资源**以及原因？

手段组合：USDT（请求上下文）+ 跟踪点/kprobe（阻塞事件）+ 定时采样（on-CPU 栈）。

**开销**：取决于事件频率。跟踪**请求本身**可忽略；跟踪**锁争用、off-CPU 事件、系统调用**在繁忙系统上影响明显。

## 13.1.4 分析策略（十步）

1. 认识应用程序的**工作单元**是什么；改进性能意味着什么（吞吐/延迟/资源）
2. 查主要组件信息：程序库、缓存、API 文档、请求处理模型（线程池 or 事件处理器）
3. 搞清是否有**后台计划任务**（如每 30 秒一次的磁盘写）
4. 检查应用和语言是否支持 **USDT 探针**
5. **on-CPU 分析**：profile(8) 定位低效 CPU 消耗
6. **off-CPU 分析**：offcputime(8)、wakeuptime(8)、offwaketime(8)；关注处理请求时的阻塞
7. **系统调用剖析**：syscount(8)
8. 浏览运行第 6–10 章的 BPF 工具
9. **uprobes 探索内部机制**：CPU/off-CPU 栈已定位出方法名，可作跟踪起点
10. 分布式：**服务器端和客户端同时跟踪**（如 MySQL 客户端库）

按应用等待的资源判断 CPU/磁盘/网络密集型，再翻对应资源章节深挖。

### 线程 ID 关联法（写 BPF 程序的关键思路）

- **服务线程池**：同一线程处理整个请求 → **线程 ID 可作为请求的唯一标识**。查询开始时把查询字符串存入以 tid 为键的 BPF 映射表，之后磁盘 I/O 发生时读取，即可**把 I/O 关联到导致它的查询**
- **事件处理器线程**：同一线程同时处理不同请求，tid 对请求不唯一 → 需要别的关联方法

## HFT 关联

- 行情网关/策略进程大多接近**事件处理器或服务线程池**模型——先判模型再选跟踪手段，tid 关联法对撮合回执→策略线程的归因同样适用
- "加一秒 sleep 确保完成"这类 hack 在交易链路里是致命延迟源；naptime(8)（13.2.15）专查这个
- 十步策略中第 5/6/7 步（profile/offcputime/syscount）是策略延迟归因三板斧
