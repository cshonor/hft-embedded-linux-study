3.1

概览（目标 / 分析工作 / 多重性能问题）

底本：《BPF之巅》第 3 章性能分析，3.1 节（印刷 p71–73，含 3.1.1–3.1.3）

3.1.1 目标

性能分析的两大目标：改进最终用户体验、降低运行成本。先量化定义目标，才能判断是否达成、还差多少。可测量指标：

指标 含义
延迟 完成一次请求/操作的时间（常以毫秒计）
速率 每秒操作或请求数
吞吐量 每秒传输数据量（bit/byte）
利用率 资源在一段时间内的繁忙程度（%）
成本 开销/性能比

延迟 = 请求时间的组成之和：CPU 运行时间 + 等资源时间（磁盘 I/O、网络、锁）+ 等 CPU 调度时间。理论上可写一个 BPF 工具同时跟踪总延迟和各组成部分，但这与具体应用绑定且多事件跟踪开销大；实践中更普遍的做法是用小而专的工具逐个研究特定组件——本书的路线。

作者的经验告诫：BPF 工具很容易"生成大量数据 → 花大量时间理解 → 发现指标不重要"。开发者常发来"看起来不健康"的指标截图，作者第一反应是"你有已知的性能问题吗？"——先明确目标（降延迟还是降成本），分析才有上下文。

3.1.2 分析工作（表 3-1）

性能分析活动 BPF 工具的作用
原型软/硬件性能特征分析 测不同负载下的延迟直方图
开发阶段/集成前分析 解决瓶颈点、找一般改进点
发布前后非回归测试 多来源记录代码使用与延迟数据，快速定位回归
基准测试（市场宣传数据） 研究性能问题、改进基准性能
目标环境 PoC 测试 生成延迟分布直方图，验证满足 SLA
生产监控 编写可 7×24 运行的工具，提供此前属于盲区的指标
故障排查 现成工具或自定义观测点解决特定问题

3.1.3 多重性能问题

  • 用工具时要做好同时发现多个问题的准备；主要问题变成"哪个最重要"——通常是对延迟或成本影响最大的那个。
  • 可以查组件的 bug tracker 搜"性能"，通常有多个未解决问题（还不含没列出来的）。
  • 解决一个瓶颈后，其他问题才浮现；原瓶颈消除后新瓶颈出现。

HFT 关联

  • HFT 的量化目标天然清晰：tick→决策→发单延迟（P50/P99/P99.9）、订单吞吐、行情处理速率。"改善用户体验"在 HFT 里就是"比对手快"。
  • "多重问题"提醒：对交易系统做第一次全链路观测时，会同时看到调度抖动、GC 停顿、缓存 miss……按对 P99 延迟的影响排序，而不是见一个修一个。
  • "你有已知的性能问题吗？"——HFT 每日复盘（昨日 P99 尖刺）就是最好的切入点，比无目标巡检高效。

陷阱

  • 无目标巡检：把"有趣的输出"当问题修，浪费时间还引入风险。
  • 只盯均值不看尾部分布：HFT 的钱都在 P99+ 里。

自测

1. 性能分析的两大目标与五个可测量指标是什么？

目标：改进最终用户体验、降低运行成本。指标：延迟、速率、吞吐量、利用率、成本。

2. 为什么不用一个 BPF 工具跟踪应用的全部延迟组成？

与具体应用绑定（不可复用），同时跟踪多个事件开销显著；小而专的工具更普遍。

3.2

性能分析方法论（负载画像 / 下钻 / USE / 检查清单）

底本：《BPF之巅》第 3 章性能分析，3.2 节（印刷 p73–77，含 3.2.1–3.2.4）

工具太多，真正的困难是处理数据的方法。方法论 = 可遵循的过程：从哪开始、中间步骤、到哪结束。（更多见作者上一本书《性能之巅》的十几种方法论。）

3.2.1 业务负载画像（Workload Characterization）

理解实际运行的负载，不先分析性能结果。"消除不必要的工作"是作者收益最显著的优化方式，靠研究负载构成找到。

四步提问：

  1. 负载是谁产生的？（PID、UID、进程名、IP）
  2. 负载为什么会产生？（代码路径、调用栈、火焰图）
  3. 负载组成是什么？（IOPS、吞吐量、负载类型）
  4. 负载随时间怎么变？（周期性摘要对比）

工具示例：vfsstat 回答 3/4（VFS 层每秒读写创建打开数）；bpftrace -e 'kprobe:vfs_read { @[comm] = count(); }' 回答 1（哪个进程在读）。

3.2.2 下钻分析（Drill-Down Analysis）

从指标开始 → 拆成组成 → 把最大组成再拆 → 重复直到根因。类比：信用卡账单巨大 → 查交易 → 发现线上书店大额 → 查订单 → 发现这本书买了 1000 本。

步骤：①从最高层级开始 ②检查下一层细节 ③挑出最感兴趣的部分 ④未解决则回到②。定制工具时 bpftrace 比 BCC 更适合。

书中两组延迟分解对比：

  • 路径 A：100ms 总延迟 → 10ms CPU + 90ms off-CPU → 89ms 阻塞在文件系统 → 3ms 锁 + 86ms 存储设备 → 结论"存储慢，买更快磁盘"
  • 路径 B（多一层）：89ms 文件系统 → 78ms 写 + 11ms 读 → 写中 77ms 阻塞在时间戳更新 → 结论"改挂载选项禁掉访问时间戳"——比换磁盘好得多

教训：每多钻一层，根因可能完全不同；停在"设备慢"是懒分析。

3.2.3 USE 方法论（Utilization / Saturation / Errors）

对每一个资源检查三项：

指标 含义 例
使用率 Utilization 资源繁忙时间占比 CPU 利用率、带宽占用
饱和度 Saturation 排队/等待程度 runqueue 长度、IO 队列、重传
错误 Errors 错误计数 ECC 错误、网络丢包、OOM

第一步：画出软硬件资源图（图 3-1：CPU 互联、内存总线、I/O 总线、控制器、磁盘、网卡端口……），然后逐资源检查三项。作者问："你现在的监控工具能对图中每项资源显示这三项吗？有多少盲区？"

优势：从重要的问题出发，而不是从"顺手可测的指标"出发再找理由；顺带暴露监控盲区。

3.2.4 检查清单法（Checklists）

列出一组工具与指标供对照执行，聚焦唾手可得的问题；把个人技能推广到团队各级工程师。本章给出两个清单：传统工具 60 秒清单（3.3）+ BCC 工具清单（3.4）。

四方法对比

方法 适用 HFT 场景
负载画像 不知系统在干什么时 行情风暴时谁在产生负载
下钻分析 已知有延迟问题 tick→order P99 分解
USE 系统性巡检、找盲区 交易机资源健康检查表
检查清单 标准化、多人执行 每日开盘前例行检查

HFT 关联

  • 下钻路径 B 是 HFT 延迟分析的模板：总延迟 → on/off-CPU → 阻塞点细分 → 具体机制（时间戳更新 ≈ HFT 里的"日志刷盘"、"监控 agent 抢锁"这类真正根因）。停在"内核网络栈慢"等于没分析。
  • USE 表可直接做成交易机 dashboard：CPU（利用率=mpstat、饱和=runqlat、错误=MCE）、网卡（利用率=带宽%、饱和=丢弃/重传、错误=ifconfig 计数）、内存（利用率、饱和=swap、错误=ECC）。
  • "消除不必要的工作"在 HFT 收益最大：行情解析线程里的多余拷贝、无用的统计采样，都是负载画像能直接暴露的。

陷阱

  • 下钻过早停止：把"设备/CPU 慢"当根因，其实再钻一层就是可修的软件行为。
  • USE 只查使用率不查饱和度：HFT 延迟问题多藏在饱和度（排队）里，使用率 60% 也可能有长队列。
  • 方法论混用无入口：按"画像 → 发现异常 → 下钻到根因 → USE 巡检防复发"的顺序组合。

自测

1. 业务负载画像的四个问题是什么？

谁产生（PID/IP）、为什么产生（代码路径/火焰图）、组成是什么（IOPS/吞吐/类型）、随时间如何变化。

2. USE 的三要素和第一步是什么？

使用率、饱和度、错误；第一步是绘制软硬件资源图，逐资源检查三项。

3. 书中"时间戳更新"例子说明了什么？

下钻分析每深一层结论可能质变：从"需要更快的磁盘"变成"改挂载选项禁用访问时间戳更新"，后者零成本且直击根因。

3.3

Linux 60 秒分析（10 个传统工具逐个讲）

底本：《BPF之巅》第 3 章性能分析，3.3 节（印刷 p77–84，含 3.3.1–3.3.10）

作者登录一台表现不佳的 Linux 后最初 60 秒做的事（Netflix 性能工程团队发表过）。为什么 BPF 书讲非 BPF 工具：这些现成资源可能直接定位问题；即便不能，也暴露根因线索、指引后续 BPF 工具。

3.3.1 uptime — 平均负载

load average: 2.74, 2.54, 2.58：1/5/15 分钟指数衰减滑动窗口。Linux 的负载含想跑的进程 + 不可中断 I/O 阻塞的进程（D 状态）。判读：高 15 分钟 + 低 1 分钟 = 你错过了问题现场（容错环境机器可能已自动下线）。

3.3.2 dmesg | tail — 最近 10 条内核日志

找导致性能问题的错误：例中 OOM killer 杀 perl、TCP SYN flooding 丢请求（还指了下一步方向：查 SNMP 计数器）。

3.3.3 vmstat 1 — 虚拟内存与系统概况

关键列（首行是开机以来均值，忽略）：

  • r：正在执行+等待执行的进程数——比 load average 更好的 CPU 饱和度指标（不含 I/O）；r > CPU 数即饱和
  • si/so：换入换出非零 = 内存紧张
  • us/sy/id/wa/st：用户/内核/空闲/IO 等待/被虚拟化窃取——例中 us 主导 → 下一步剖析用户态代码

3.3.4 mpstat -P ALL 1 — 每 CPU 分解

发现单核打满：例中 CPU0 %usr=100%——单线程瓶颈特征，换更多核无用。高 %iowait → 磁盘工具跟进；高 %sys → syscall 跟踪与 CPU 剖析。

3.3.5 pidstat 1 — 每进程 CPU

默认滚动输出（优于 top 的静态屏）。百分比是对全部 CPU 之和：500% = 5 个满载核。例中 java 进程 12178/12569 波动 200–500%。注意：某些 pidstat 版本曾把上限错限为 100%，多线程下输出错误（该改动已撤回，留意识别）。

3.3.6 iostat -xz 1 — 存储设备 I/O

关键列：

  • r/s w/s rkB/s wkB/s：负载画像用
  • await：应用承受的平均响应时间（队列时间+服务时间），超预期 = 饱和或设备问题
  • avgqu-sz：队列长度，>1 可能饱和（多盘虚拟设备可并行，需甄别）
  • %util：繁忙时间占比；>60% 常致性能变差；但注意它不是容量意义上的使用率——100% 时并行设备可能仍能接更多负载

例：md0 虚拟设备 ~300MB/s 写，背后是两块 nvme。

3.3.7 free -m — 内存

看 available 列（含可回收的 buffer/cache）是否接近 0；缓存占内存是好事不是浪费。（新版 free 才有 available；-w 可分开显示 buff/cache。）

3.3.8 sar -n DEV 1 — 网卡

rxkB/s txkB/s 检查是否打满接口带宽上限；rxpck/s 包速率画像。

3.3.9 sar -n TCP,ETCP 1 — TCP 概况

  • active/s：本地发起 connect() 数；passive/s：远端发起 accept() 数——负载画像利器
  • retrans/s：重传数——网络或对端问题征兆

3.3.10 top — 收尾二次确认

汇总浏览系统与进程摘要，交叉验证前面看到的现象。

60 秒清单速查表（判读 → 下一步）

工具 看什么 异常时下一步
uptime 1/5/15min 负载趋势 高 15 低 1 = 错过现场
dmesg OOM/网络错误 按 log 指引查计数器
vmstat r、si/so、us/sy/wa/st r>核数→runqlat；wa 高→iostat
mpstat 单核 100%、%sys 单核满→profile；sys 高→syscall 跟踪
pidstat 哪个进程吃 CPU 对该进程剖析

top 交叉确认 —

HFT 关联

  • 这 10 条命令可直接做成交易机的开盘前 60 秒体检脚本：单核打满（mpstat）、调度排队（vmstat r）、磁盘 await 尖刺、TCP 重传，全是延迟杀手。
  • vmstat 的 st（steal）在云交易机上尤其要盯：宿主机超卖直接吃掉你的延迟预算。
  • iostat await 的教训适用于 HFT 所有"平均值"：平均 await 5ms 可能藏着 p99 800ms——第 2 章 biolatency 直方图才是答案。

陷阱

  • vmstat 首行是开机以来均值，分析要跳过。
  • 把 %util=100% 当"容量满了"——并行设备可能还有余量。
  • load average 含 D 状态进程：高负载不一定是 CPU 不够，可能全是 IO 等待（看 vmstat r 更准）。

自测

1. 为什么 vmstat 的 r 列比 load average 更适合查 CPU 饱和度？

r 只统计正在执行+等待 CPU 的进程，不含不可中断 I/O；load average 把 D 状态也算进去，IO 重时虚高。

2. await 和 %util 各自的含义与局限？

await=I/O 平均响应时间（队列+服务），是应用真实感受；%util=设备繁忙时间占比，并行设备 100% 时仍可能有剩余容量，不是容量规划意义上的使用率。

3. pidstat 显示 500% 意味着什么？

该进程占用了 5 个满载 CPU 核心（百分比是全核之和）。

3.4

BCC 工具检查清单（11 个工具逐个讲）

底本：《BPF之巅》第 3 章性能分析，3.4 节（印刷 p84–89，含 3.4.1–3.4.11）

作者放在 BCC 仓库 docs/tutorial.md 的通用清单——60 秒传统工具之后的第一波 BPF 深探：

execsnoop   opensnoop   ext4slower  biolatency  biosnoop   cachestat
tcpconnect  tcpaccept   tcpretrans  runqlat     profile

3.4.1 execsnoop — 新进程跟踪

跟踪每次 execve(2) 打印一行。价值：短命进程消耗 CPU 但周期采样的监控看不到（Netflix 案例见第 1 章：每秒 30 个批量创建进程）。→ 第 6 章

3.4.2 opensnoop — open 跟踪

每次 open(2)（及变体）打印路径与结果（ERR 列）。打开的文件透露应用的工作：数据/配置/日志文件；反复打开不存在的文件会导致异常或性能受损（例中 snmpd 打开 vendor 文件 ERR=-1 ENOENT）。→ 第 8 章

3.4.3 ext4slower — 慢文件系统操作

跟踪 ext4 读/写/打开/同步，只打印超过阈值（默认 10ms）的操作。定位或排除"应用在文件系统等慢磁盘"这类问题。其他 FS 有对应工具：btrfsslower / xfsslower / zfsslower。→ 第 8 章

3.4.4 biolatency — 磁盘 I/O 延迟直方图

从发请求到完成的延迟直方图（log2 桶）。比 iostat 平均值强：能看出多峰分布（例：0–1ms 峰 + 8–15ms 峰=两类 I/O）与离群点（512–1023ms）。作者注：log2 桶粒度粗，要精细分布可改线性直方图或用 biosnoop 记录每笔 I/O 再离线统计。→ 第 9 章

3.4.5 biosnoop — 每笔磁盘 I/O 日志

逐笔打印 I/O（含延迟），可搜寻时序模式（如写之后的读排队）。→ 第 9 章

3.4.6 cachestat — 页缓存命中率

每秒打印 HITS/MISSES/HITRATIO（例 86–95%）。低命中率给出调优方向。→ 第 8 章

3.4.7 tcpconnect — 主动连接跟踪

每次 connect() 打印源/目的地址。找不寻常的连接：配置低效或入侵行为。→ 第 10 章

3.4.8 tcpaccept — 被动连接跟踪

tcpconnect 的搭档，每次 accept() 打印一行。两者合起来完整画像连接建立。→ 第 10 章

3.4.9 tcpretrans — TCP 重传跟踪

每次重传打印地址+当时连接的内核状态：

  • ESTABLISHED 状态重传 → 外部网络可能有问题
  • SYN_SENT 状态重传 → CPU 饱和征兆或内核丢包

→ 第 10 章

3.4.10 runqlat — 调度延迟直方图

线程等待 CPU 的时间直方图。定位超预期的 CPU 等待：CPU 饱和、配置错误或调度问题。例中 16–33ms 桶有 809 次明显异常。→ 第 6 章

3.4.11 profile — CPU 采样剖析器

按 49Hz 采样所有线程的用户+内核栈，打印消重后的调用栈及次数（例：iperf 的 write 路径 58 次）。理解哪些代码路径吃 CPU。→ 第 6 章

两套清单如何衔接（60 秒 → BCC）

60 秒清单发现 BCC 跟进
vmstat r 高 / mpstat 饱和 runqlat → profile
mpstat 单核 100% profile
iostat await 高 biolatency → biosnoop
vmstat/pidstat 疑短命进程 execsnoop
free 内存紧张 cachestat
sar retrans 高 tcpretrans
sar active/s 异常 tcpconnect/tcpaccept
应用卡在 IO ext4slower / opensnoop

HFT 关联

  • 交易机每日延迟体检的 BPF 波次就按这 11 个工具来：runqlat（调度抖动=HFT 头号敌人）、profile（热路径变化检测）、tcpretrans（对端/线路问题）、execsnoop（异常的定时任务/脚本抢占 CPU）。
  • ext4slower 的"阈值过滤"设计思想值得自研工具借鉴：只报超过延迟预算的事件，风暴时输出量可控。
  • profile 的 49Hz 又见第 2 章"非整频率防锁步"纪律。

陷阱

  • biolatency 的 log2 直方图读法：相邻桶宽度翻倍，比较"次数"要想到桶宽不同。
  • runqlat 直方图长尾（几十 ms 桶有计数）就是调度问题信号，别被"多数在 0–8µs"迷惑。
  • cachestat 只看页缓存，不是所有缓存（如应用自管缓存）。

自测

1. 为什么 execsnoop 能发现传统监控发现不了的 CPU 消耗？

周期采样的监控（top 等）容易错过毫秒级短命进程；execsnoop 逐事件跟踪 execve，一个不漏。

2. tcpretrans 中 SYN_SENT 状态重传和 ESTABLISHED 状态重传各指向什么？

SYN_SENT：本机 CPU 饱和或内核丢包（连 SYN 都处理不过来）；ESTABLISHED：外部网络/对端问题。

3. runqlat 测量的是什么时间？

线程从变为可运行到真正上 CPU 运行的等待时间（调度队列延迟），反映 CPU 饱和与调度问题。

原书小结

性能分析的目标是改善用户体验、降低运行成本。工具太多反而难选——方法论指导选择：从哪开始、一步步分析、到哪结束。本章概述了负载画像、下钻分析、USE、检查清单四种方法；给出 Linux 60 秒清单（日常分析首先使用，直接定位问题或提供 BPF 工具线索）；最后是 BCC 工具清单，细节在后续章节展开。
