. 典型事件的频率和额外开销（18.1）

底本：《BPF之巅》第 18 章 建议、技巧和常见问题，18.1 节（印刷 p756–760）

决定一个跟踪程序 CPU 开销的三个主要因素：

  1. 被跟踪事件的触发频率
  2. 跟踪时执行的操作
  3. 系统中 CPU 的个数

公式：

额外开销 = （频率 × 执行的操作数）/ CPU 数

单 CPU 系统上每秒跟踪一百万个事件会把应用拖得很慢；在 128 CPU 系统上影响可能可忽略。CPU 数量和操作开销的浮动范围可达一个数量级，而事件频率可浮动几个数量级——是评估开销时最大的不确定因素。

系统调用 每秒 1000–50000 次 每 10 分钟一次 可被测量到
网络数据包 每秒 1000–100000 次 每 5 分钟一次 可被测量到
内存分配 每秒 10000–1000000 次 每 30 秒一次 很高

18.1.2 执行的操作：表 18-2 bpftrace 每事件开销

用 dd if=/dev/zero of=/dev/null bs=1 count=10000k（每秒超百万次 read）测得（Linux 4.15、i7-8650U、JIT 启用、taskset 绑核、取最快 10 次运行）：

bpftrace 单行 测试目的 dd 总时长(s) 每事件开销(ns)
<none> 对照组 5.97 —
k:vfs_read kprobe 6.75 76
kr:vfs_read kretprobe 8.14 212
t:syscalls:sys_enter_read tracepoint 6.96 96
t:syscalls:sys_exit_read tracepoint 6.92 93
u:libc:read uprobe 19.15 1287
ur:libc:read uretprobe 25.74 1931
k:vfs_read /arg2>0/ 过滤 7.25 124
k:vfs_read @=count() 映射表 7.92 190
k:vfs_read @[pid]=count() 映射表 8.10 207
k:vfs_read @[comm]=count() 字符串键 8.28 225
k:vfs_read @[pid,comm]=count() 双键 8.32 229
k:vfs_read @[kstack]=count() 内核栈 9.41 336
k:vfs_read @[ustack]=count() 用户栈 12.65 652
k:vfs_read @=hist(arg2) 直方图 8.36 233
k+kr vfs_read 计时 计时（双探针） 12.48 636（两事件）
@[kstack,ustack]=hist(arg2) 复合操作 14.53 836
printf(...) > out.txt 逐事件输出 14.67 850

结论：

  • kprobe 很快（76ns）；加映射表键值查询到 ~200ns
  • kretprobe 较慢（212ns）——入口检测 + 为返回插入跳跃处理程序
  • uprobes/uretprobes 开销最大（>1µs/事件）——已知问题，未来 Linux 版本会改进
  • 用户栈比内核栈贵一倍（652 vs 336）；逐事件 printf 输出最贵之一
  • 以上是短 BPF 程序；冗长 BPF 程序成本可上微秒级。数字随系统速度/架构/负载/BPF 改进而变

机理概要：为什么 uprobe 比 kprobe 贵一个数量级以上（1287 vs 76ns）

探针 触发路径 差价来源
kprobe 断点指令陷阱 → 单一 trap 处理程序里跑 BPF → 继续原指令 一次陷阱
kretprobe 入口 kprobe + 把返回地址替换成蹦床，返回时再触发一次 两次事件 + 每任务实例登记
uprobe 断点陷阱 → 需要保证被改写的指令还能执行：把原指令拷到 XOL（out-of-line）执行槽单步执行 → 再陷阱一次恢复原位置执行 两次陷阱 + 指令仿真调度，且落在目标进程用户态上下文里

uprobe 的开销大头不是 BPF 程序本身，而是维持"断点 + 原指令挪位执行"这套机制的固定成本——所以哪怕 BPF 体内只做一次 count()，单事件仍要 >1µs。这也是原书说"已知问题，未来 Linux 版本会改进"的原因（改进方向：如内核 5.18+ 的 uretprobe 蹦床优化等持续在削这块固定成本）。

注：以上为机制通识级概要（uprobe 断点 + XOL 单步是 Documentation/trace/uprobetracer 文档化行为）；D:\.kernel-ref 缓存未含 uprobes.c，未做逐行源码核对，具体路径细节以对应内核版本源码为准。

18.1.3 自行测试

如果可以准确测量应用性能：在运行和不运行 BPF 工具时各测一次取差异。

  • CPU 饱和（100%）系统：BPF 占用应用 CPU 周期，差异表现为请求率下降
  • CPU 空闲系统：差异表现为可用空闲的下降

HFT 关联

  • 表 18-2 是"能不能在生产 tick 路径上开这个工具"的决策依据：kprobe+映射表 ~200ns 尚可，uprobe/ustack/逐事件 printf 在百万级/秒事件上直接出局
  • 行情处理路径常落在"网络数据包"档（可被测量到 ~1%）——排障短窗口可接受，常驻需论证
自测题
  1. 开销公式的三个因子是什么？为什么说事件频率是最大的不确定因素？
  2. 表 18-2 中哪类探针最贵？大约多少纳秒？
  3. CPU 饱和 vs CPU 空闲系统上，BPF 开销分别表现为什么可测量差异？
  4. "可被测量到"对应百分之几？
参考答案
  1. 额外开销 = （事件触发频率 × 每事件执行的操作数）/ CPU 数。CPU 数和操作开销浮动约一个数量级，而事件频率可浮动几个数量级（线程睡眠 1/s 到函数调用 10⁸/s）——同一工具换个事件源，总开销就跨档了。
  2. uprobe/uretprobe：1287/1931ns（对比 kprobe 76ns，差 17–25 倍）。用户态探针要维持断点 + XOL 单步执行的固定成本（见上文机理概要）。
  3. CPU 饱和系统：BPF 抢占应用周期 → 表现为请求率/吞吐下降；CPU 空闲系统：应用不受影响 → 表现为空闲率下降（iostat/mpstat 里 idle 变少）。
  4. ~1%（忽略不计 <0.1%、显著 >5%、很高 >30%、极高 >300%）。

. 建议与技巧：99Hz、灰鼠、先写负载、学系统调用、保持简单（18.2–18.6）

底本：《BPF之巅》第 18 章，18.2–18.6 节（印刷 p760–763）

18.2 以 49Hz 或 99Hz 为采样频率

目的：避免锁步采样（lockstep sampling）。定时采样绘制目标软件粗略图像，100Hz 或 50Hz 通常足以解决大小性能问题。

锁步陷阱：以 100Hz 为例每 10ms 采样一次。假设应用每 10ms 唤醒一次做 2ms 工作（占一个 CPU 的 20%）——若采样恰好总落在 2ms 工作窗口，剖析显示该应用 100% 在 CPU 上；若总落在睡眠期则显示 0%。两种结果都极具误导（混淆错误示例）。

用 99Hz 后，采样时间偏移不再总与应用工作对齐，几秒内就会收敛到正确的 20%；且足够接近 100Hz 可心算外推（8 CPU × 1 秒 ≈ 800 个样本——作者校验结果时常这样算）。73Hz 也能避锁步但心算难（"4 CPU 采 8 秒请给我计算器"）。

99 生效的原因：程序开发者通常为定时活动选四舍五入的数字（每秒 1 次、每 20ms 一次……）。若大家都改用每秒 99 次，锁步会卷土重来。作者称 99 为"剖析员数字"——除性能剖析外勿用于其他用途。

18.3 黄猪和灰鼠

数学里 17 很特殊，昵称"黄猪"数字（甚至有黄猪日 7 月 17 日）；对跟踪也有用——但作者更偏爱 23（"灰鼠"数字）。

用法：分析未知系统不知道跟踪什么时，注入一个熟悉的工作负载，对事件做频率计数，与负载相关的函数会自己浮现。例：想理解 ext4 如何执行写 I/O：

# dd if=/dev/zero of=test bs=1 count=230000   # 23 万次写，可与其他活动区分
# funccount -d 10 'ext4_*'                     # 跟踪所有 ext4 函数 10 秒（共 509 个函数）
ext4_write_checks          230117
ext4_file_write_iter       230117
ext4_da_write_end          230185
ext4_nonda_switch          230191
ext4_block_write_begin     230200
...（共 15 个函数超过 230000 次）
ext4_journal_check_start  460551

15 个函数被调用超过 230000 次——极可能与该负载相关，把 509 个候选缩小到 15 个。23（或 230、2300…）不易与其他不相关事件计数冲突：23 和 17 都是质数，在计算中比 2 或 10 的幂出现概率小；23 与 2/10 的幂距离比 17 更远。12.4 节也用了这个技巧。

18.4 开发目标软件

先开发负载生成软件，再写跟踪工具，可大幅节省时间。例：想跟踪 DNS 请求的延迟和细节——从开发简单的 DNS 请求生成器开始，就会知道哪些函数需要跟踪、请求细节如何存在结构体中、返回值是什么。互联网上针对开发者的文档（含代码片段）很丰富：getaddrinfo(3) 的手册页就包含可用的完整程序：

memset(&hints, 0, sizeof(struct addrinfo));
hints.ai_family   = AF_UNSPEC;    /* Allow IPv4 or IPv6 */
hints.ai_socktype = SOCK_DGRAM;   /* Datagram socket */
hints.ai_flags    = 0;
hints.ai_protocol = 0;            /* Any protocol */
s = getaddrinfo(argv[1], argv[2], &hints, &result);

可进一步修改为只产生 23 个（或 2300 个）请求，配合 18.3 的技巧找协议栈中相关函数。

18.5 学习系统调用

系统调用是跟踪的丰富目标：手册页文档中有对应跟踪点，并提供应用资源使用的有用信息。例：syscount(8) 发现高频 setitimer(2)——那是什么？

$ man setitimer   # GETITIMER(2): interval timer，到期为调用进程生成信号并按间隔重置

手册页解释了 setitimer 是什么、传参和返回值——都可以通过 syscalls:sys_enter_setitimer / syscalls:sys_exit_setitimer 跟踪点检查。

18.6 保持简单

避免开发冗长复杂的跟踪程序。BPF 有跟踪所有事件的超级能力，但很容易被带偏。添加很多事件的缺点：

  • 不必要的开销：原始问题可能跟踪几个事件就解决，工具却跟踪更多事件，每个使用者付出更大开销
  • 维护负担：kprobes/uprobes 界面不稳定，软件版本间会变化。Linux 4.x 系列中已发生内核变化导致 BCC 工具不可用的情况。解决方法：按内核版本添加代码（检查函数是否存在来选择，因为反向移植使版本号不可靠）、或复制工具保留在 tools/old 文件夹。最好是改用跟踪点（如 tcp 工具的 sock:inet_sock_set_state）——破坏将不再发生
  • 修复 BCC 工具不难（每个工具只跟踪少数事件——作者刻意如此设计）；若每个跟踪数十个事件，损坏更频繁、修复更复杂，且测试被放大（需在所有相关内核版本测试所有事件类型）

作者的惨痛教训：15 年前开发 tcpsnoop(1m)，目标是显示哪个进程在做 TCP I/O，但最终做成了跟踪 PID 所有数据包类型（TCP 握手、端口拒绝、UDP、ICMP…）匹配网络嗅探器输出的工具——涉及大量不稳定内核细节，因内核升级损坏多次，完全忘记了原始问题，开发了不可维护的工具（详见第 10 章）。本书的 bpftrace 工具是 15 年经验的总结：谨慎地只跟踪解决特定问题的最少必需事件。

HFT 关联

  • 99Hz 原则直接适用于自研延迟剖析器；策略进程若用 10ms 定时器（常见！），100Hz 采样必然锁步
  • "灰鼠 230000" 技巧适合定位行情解码路径：注入 23 万个已知报文，funccount 通配符一网打尽相关函数
  • "保持简单"与交易系统工具开发同构：排障脚本只解决一个问题，禁止"顺手多跟踪几个"
自测题
  1. 锁步采样是怎么产生的？为什么 99Hz 能解决而 100Hz 不能？
  2. 灰鼠数字是什么？为什么选 23 而不是 17 或 10 的幂？
  3. 为什么要先开发负载生成软件再写跟踪工具？
  4. tcpsnoop 教训的三条代价是什么？
参考答案
  1. 定时采样周期与被测软件的周期性活动整数倍对齐：应用每 10ms 醒来干 2ms（真实 20% CPU），100Hz 每 10ms 采一次——采样点要么全落进工作窗（显示 100%），要么全落进睡眠期（显示 0%）。99Hz 与 10ms 周期不对齐，采样点相对工作窗持续漂移，几秒内收敛到真值 20%。
  2. 灰鼠 = 23（黄猪 = 17）。用它做注入负载的次数（230000 次），让"与负载相关的函数"以 23 的倍数计数自己浮现。选 23：① 质数，在计算中出现概率天然低，不易撞上不相关事件计数；② 与 2/10 的幂距离比 17 更远（17≈16+1 容易被 16 对齐类活动干扰）。
  3. 写负载生成器的过程会逼你搞清跟踪目标的接口：哪些函数参与、请求细节存在哪个结构体字段、返回值长什么样——这些正是写探针脚本要用的信息。而且生成器可精确控制次数（230000），直接配合灰鼠技巧。
  4. ① 不必要的开销（跟踪了远超原始问题所需的事件）；② 维护负担（kprobe/uprobe 接口不稳定，内核升级即损坏，涉及的不稳定细节越多坏得越频繁）；③ 测试被放大（每个事件类型 × 每个内核版本都要测）。外加最根本的：完全忘记了"哪个进程在做 TCP I/O"这个原始问题。
3

. 常见问题一：事件缺失与调用栈缺失（18.7–18.8）

底本：《BPF之巅》第 18 章，18.7–18.8 节（印刷 p764–767）

18.7 事件缺失

症状：事件可以被成功插桩，但是不触发，或者工具不输出结果。（如果事件根本不能插桩，见 18.10 节。）

诊断法：用 perf(1) 交叉验证——判断问题在 BPF 工具还是事件本身：

# perf stat -e block:block_rq_insert,block:block_rq_requeue -a
Performance counter stats for 'system wide':
        41  block:block_rq_insert
         0  block:block_rq_requeue

block:block_rq_insert 触发了 41 次、requeue 触发 0 次。若 BPF 工具同时跟踪了 insert 却没看到事件 → BPF 工具的问题；若 perf 和 BPF 都显示没有 → 事件本身没发生。

kprobe 同理（perf 需要先创建再删除探针）：

# perf probe vfs_read
# perf stat -e probe:vfs_read -a
    3,029  probe:vfs_read      # 跟踪期间 vfs_read() 被调用了 3029 次
# perf probe --del probe:vfs_read

两个常见原因：

  1. 软件修改后，之前被插桩的事件不再被调用
  2. 从共享库位置跟踪库函数，但目标应用是静态编译的——函数从应用程序二进制文件中调用

18.8 调用栈缺失

症状：打印的调用栈不完整或完全缺失（可能伴随 18.9 的符号问题，帧显示 [unknown]）。

示例：trace -u t:syscalls:sys_enter_execve 打印用户态栈：

PID    TID   COMM  FUNC                STACK
26853  26853 bash  sys_enter_execve    [unknown]
26854  26854 bash  sys_enter_execve    [unknown]

先用 perf(1) 交叉验证（perf record + perf script），perf 显示的类似不全调用栈暴露三个问题：

  1. 调用栈不全：跟踪 bash 调用新程序，经验上这有几个很深的帧，这里只有两帧。判断法：栈只有一两行、且没有以初始帧（如 main 或 _start_thread）结束 → 假设不完整
  2. 最后一行 [unknown]：perf 都不能解析符号——可能 bash 有符号问题，或 libc 的 GI_execve() 覆盖了帧指针中断遍历
  3. perf 能看到 libc GI_execve() 而 BCC 不能：指向 BCC 跟踪的一个需要修复的问题（作者猜测 perf 用了 debuginfo，参见 bpftrace issue #646）

18.8.1 如何修复损坏的调用栈

不完整调用栈很常见，两个成因：

  1. 观测工具使用基于帧指针的方法读取调用栈
  2. 编译器性能优化没有预留寄存器（x86-64 的 RBP）给帧指针，而是复用为通用寄存器——工具读到的是数字/对象地址/字符串指针等任意值。幸运时解析不到符号打印 [unknown]；不幸运时解析到不相干的符号，打印错误函数名的调用栈，误导最终用户

最简单的修复——恢复帧指针寄存器：

软件类型 方法
C/C++ 及其他 gcc/LLVM 编译软件 用 -fno-omit-frame-pointer 重新编译
Java 用 -XX:+PreserveFramePointer 运行 java(1)

可能有性能损耗，但通常观测到的损耗少于 1%——可用调用栈定位性能问题的收益远大于此（第 12 章也有讨论）。

另一种解决方法：切换到不基于帧指针的堆栈遍历技术。perf(1) 支持 DWARF、ORC、LBR（最后分支记录）；但本书编写时，基于 DWARF 和 LBR 的堆栈遍历在 BPF 中不可用，ORC 不能用于用户态软件（详见 2.4 节）。

HFT 关联

  • 生产排障时"perf 交叉验证"是黄金法则：先确认事件真的发生，再怀疑 BPF 工具
  • HFT 自研 C++ 策略/行情程序构建管线应默认 -fno-omit-frame-pointer（<1% 换全栈可见，本书反复强调）；Java 服务统一 JVM 参数 -XX:+PreserveFramePointer
  • [unknown] 反而比"看似合理的错误符号名"安全——警惕后者静默误导排障方向
自测题
  1. perf 交叉验证的两种结果分别指向什么结论？
  2. 静态编译如何导致事件缺失？
  3. 损坏调用栈的两个成因是什么？"不幸运"时会发生什么？
  4. 修复帧指针的 C/C++ 和 Java 方法各是什么？ORC/DWARF/LBR 在 BPF 中的现状？
参考答案
  1. perf 看得到事件而 BPF 工具看不到 → BPF 工具的问题（去修工具）；perf 和 BPF 都看不到 → 事件本身没有发生（去找业务/系统侧原因，如代码路径变了）。
  2. uprobe 挂在共享库（.so）里的函数地址上；静态编译的应用把该函数拷贝进了自己的二进制，库里的那个地址根本不会被执行——插桩"成功"但永远不触发。
  3. 成因：① 观测工具用帧指针遍历调用栈；② 编译器优化（-O2 默认）把 RBP 复用为通用寄存器、不留帧指针——栈上读到的是任意值。不幸运时：任意值恰好落在某个符号的地址范围内，解析出不相干的函数名——打印出一条看似合理实则错误的调用栈，比 [unknown] 危险得多。
  4. C/C++：-fno-omit-frame-pointer 重编译；Java：-XX:+PreserveFramePointer。损耗通常 <1%。替代技术现状（本书写作时）：DWARF/LBR 在 BPF 中不可用，ORC 只能用于内核态——所以恢复帧指针几乎是 BPF 用户态栈的唯一解。

. 常见问题二：符号缺失与函数缺失（18.9–18.10）

底本：《BPF之巅》第 18 章，18.9–18.10 节（印刷 p767–769）

18.9 打印时符号缺失（函数名称）

症状：调用栈或符号查找无法正确打印符号——不显示函数名，而是十六进制数字或 [unknown]。

三个原因：

  1. 堆栈损坏（18.8 节已解释）
  2. 短命进程：在 BPF 工具读取其地址空间并查询符号表之前就停止运行了
  3. 没有可用的符号表信息

JIT 运行时和 ELF 二进制文件的解决方法不同。

18.9.1 修复符号缺失：JIT 运行时（Java、Node.js…）

JIT 编译器有自己的运行时会改变的符号表，不是二进制文件预编译符号表的一部分。通常的修复方法：使用运行时生成的额外符号表，放在 /tmp/perf-<PID>.map 文件中，可被 perf(1) 和 BCC 读取。（注意事项与未来工作见 12.3 节。）

18.9.2 修复符号缺失：ELF 二进制文件（C、C++…）

编译好的二进制可能缺符号，尤其是打包分发的——它们被 strip(1) 处理过以降低文件大小。两种修复：

  1. 调整构建过程避免去除符号
  2. 使用另外的符号信息来源：debuginfo 或 BTF（BCC 和 bpftrace 支持 debuginfo 符号）

（注意事项与未来工作见 12.2 节。）

18.10 跟踪时函数缺失

症状：一个已知函数不能用 uprobes/uretprobes/kprobes/kretprobes 跟踪——表现为缺失或没有触发。问题可能是符号缺失（前面介绍过），也可能是编译器优化：

原因 机制 表现
内联（inlining） 函数指令被包含进调用函数内（少指令的函数为节省调用/返回/序言开销） 函数符号可能完全消失，或存在但那段代码不触发
尾调用优化（TCO） A→B→C 且 C 是 B 的最后调用时，编译器让 C 直接返回给 A C 的 uretprobe/kretprobe 不会触发
静态和动态链接 uprobe 在库中定义了函数，但目标软件从动态链接切到静态链接（函数位置变了，现在位于二进制文件中）；反之亦然 探针地址失效

处理方法：跟踪一个不同的事件——父函数、子函数或邻居函数。kprobes 和 uprobes 也支持指令偏移跟踪（bpftrace 将来也应该支持）：如果知道偏移量，内联函数的位置也可以被插桩。

HFT 关联

  • 交易系统二进制构建时保留符号（不 strip，或单独分发 debuginfo/BTF 包）是 BPF 可观测性的前提；发布流程要显式检查这一点
  • Java 策略服务：确保 perf-map 代理（如 perf-java-flames）可用，否则栈全是地址
  • 排查"探针不触发"先查三件事：内联（objdump 看符号）、尾调用（retprobe 不触发）、静态链接（ldd / nm 定位函数实际位置）
自测题
  1. 符号缺失的三个原因是什么？短命进程为什么会导致它？
  2. JIT 运行时的符号修复方案是什么文件？
  3. 尾调用优化为什么让 kretprobe 失效？内联后如何补救插桩？
  4. 静态/动态链接切换如何造成 uprobe 失效？
参考答案
  1. ① 调用栈损坏（帧指针问题，见 18.8）；② 短命进程；③ 二进制没有可用符号表（strip 过）。短命进程：BPF 工具（用户态）要事后读它的地址空间、查符号表才能翻译地址——进程已经退出，地址空间和映射都消失，只剩无法解析的数字。
  2. JIT 运行时把动态生成的符号表写到 /tmp/perf-<PID>.map，perf(1) 和 BCC 都认这个文件。
  3. TCO：A→B→C 且 C 是 B 的最后调用时，编译器让 C 的返回直接交给 A（复用 B 的返回地址/帧）——B 的"返回"这个事件在指令流里不存在了，kretprobe 在 B 返回地址上的插桩永远等不到。内联补救：改用指令偏移跟踪（知道内联代码在父函数里的偏移量就能插桩），或换跟父/子/邻居函数。
  4. uprobe 挂的地址解析自某个特定二进制文件（.so 或可执行文件）。应用从动态链接切成静态（或反之）后，同一个函数换文件了、地址变了——按旧文件地址下的探针指向不存在的位置。

. 常见问题三：反馈回路与被丢掉的事件（18.11–18.12）

底本：《BPF之巅》第 18 章，18.11–18.12 节（印刷 p769–770）

18.11 反馈回路

如果你跟踪你自己的跟踪，就能创建一个反馈回路。

要避免的例子：

# bpftrace -e 'k:ext4_file_write_iter { printf("%s..", ..); }' > /ext4fs/out.file
  • 前两个（printf 类）命令：意外跟踪了 bpftrace 自己 printf() 触发的事件，再创建新事件——事件频率暴涨，直到性能问题出现、你停止 bpftrace
  • 第三个命令：bpftrace 自己触发 ext4 写来保存输出，导致产生更多输出需要保存——自我放大

避免方法：使用过滤器排除自己的 BPF 工具，或仅跟踪目标进程（如 /pid != $$/、按 comm/pid 过滤）。

18.12 被丢掉的事件

症状：工具输出不完整。BPF 工具可能因输出过快导致 perf 输出缓冲区溢出，或保存太多堆栈 ID 导致 BPF 堆栈映射溢出等。

# profile
WARNING: 5 stack traces could not be displayed.

要点：当事件被丢掉时工具应该告诉你（如上）。修复通常可以通过调整完成——例如 profile(8) 有 -stack-storage-size 选项增加堆栈映射大小（默认映射能存储 16384 个唯一调用栈）。如果调整十分频繁，应更新工具的默认设置，使用户无须更改它们。

HFT 关联

  • 反馈回路对 HFT 尤其危险：交易机盘口高峰本就高频，自激励回路可能把节点拖垮——所有写文件/printf 的跟踪脚本必须带目标进程过滤
  • 丢弃 5 条栈在普通系统无伤大雅，但在尾延迟调查中恰是尾部样本——排障脚本预先调大 -stack-storage-size，并永远关注 WARNING 行
自测题
  1. 反馈回路的成因是什么？两种避免方法？
  2. 事件被丢的两个典型溢出位置？profile(8) 默认能存多少条唯一调用栈？
  3. 为什么说丢弃事件对尾延迟调查危害更大？
参考答案
  1. 成因：跟踪自己的跟踪——BPF 工具自身的 printf()/写文件又触发被跟踪的事件（如跟踪 vfs 写、输出又写到 vfs），事件生产自我激励、频率暴涨直到系统出问题。避免：① 谓词里排除自己的 BPF 工具（/pid != $$/、按 comm/pid 过滤）；② 只跟踪目标进程，其余一概不管。
  2. ① perf 输出环形缓冲区溢出（事件输出过快、用户态读不过来）；② BPF 堆栈映射表溢出（唯一调用栈存太多）。profile(8) 默认栈映射可存 16384 条唯一调用栈，可用 -stack-storage-size 调大。
  3. 丢事件通常不是均匀随机丢——高峰/洪峰时最容易丢，而高峰期产生的那批事件恰是尾延迟的分位数所在。研究的目标样本被选择性丢弃，得到的 p99/p999 会系统性偏乐观，把人引向错误结论。所以必须盯着 WARNING 行，并在排障前预调大缓冲。
