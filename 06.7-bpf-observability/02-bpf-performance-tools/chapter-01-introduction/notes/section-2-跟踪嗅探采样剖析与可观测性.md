# 1.2 跟踪、嗅探、采样、剖析和可观测性分别是什么

> 底本：《BPF之巅》中文版 1.2 节（PDF p42–43）

## 五个术语一张表

| 术语 | 定义 | 例子 |
|---|---|---|
| **跟踪 tracing** | 基于事件的记录——BPF 工具使用的监测方式 | strace(1) 记录系统调用；tcpdump(8) 跟踪网络包 |
| **嗅探 snooping** | 跟踪的同义词，源自 Solaris 的 snoop(1M) | execsnoop、opensnoop、biosnoop 的命名由来 |
| **采样 sampling** | 取全部观测量的**子集**描绘大致图像（也叫 profiling） | profile(8) 每毫秒对运行代码定时采样 |
| **剖析 profiling** | 采样的别称 | 同上 |
| **可观测性 observability** | 通过全面观测来**理解系统**——涵盖跟踪 + 采样 + 固定计数器工具，**不含基准测试**（benchmark 会改变系统状态） | 本书的 BPF 工具全属于此类 |

## 关键区分

- **跟踪工具的标志**：具备记录**原始事件和事件元数据**的能力。数据量大，往往需要后处理成摘要——BPF 的价值正是在**事件发生时、内核里**实时做定制化统计摘要，而不是把原始事件搬回用户态
- **跟踪 vs 采样**：跟踪开销与事件频率成正比但**不漏事件**；采样开销小但只给大致画像、**会遗漏事件**
- 命名冷知识：strace 名字里有 trace，但不是所有跟踪工具都带 trace（tcpdump）；作者在 Solaris 时代（有一丝后悔地）普遍用 snoop 命名，才有今天一串 *snoop 工具

## 跟踪 vs 采样：开销与漏检的交换

这是本节真正的工程判断点，值得一张量级表：

| 维度 | 跟踪（per-event） | 采样（定时/profiling） | 固定计数器（/proc、sar） |
|---|---|---|---|
| 开销与什么成正比 | **事件频率**（10k 事件/s 的函数就别无脑跟踪） | 采样率（与事件频率无关） | 几乎恒定（读的时候才付钱） |
| 漏检 | 不漏 | 会漏：两次采样之间的事件不可见 | 只给累计值，事件细节全无 |
| 典型单次成本 | bpftrace/kprobe 探针 + BPF 程序 ≈ 1–3 µs/事件 | perf 采样 + 栈回溯 ≈ 采样一次的成本，99+ Hz 常态 | 读文件 + 解析文本 ≈ ms 级但频率低 |
| 适合回答 | "**那几笔**慢在哪/谁干的" | "CPU 时间整体花在哪些函数" | "水位是否正常"（USE 方法的第一步） |
| 尾部延迟 | **可精确捕获**（P99.9 那几笔就在输出里） | 统计意义上有偏（尾部事件被采到的概率与占比同） | 完全不可见 |

采样对尾部事件的盲区是结构性的：一个占 0.1% 时间的现象，在 99 Hz 采样下平均要 ~1000 秒才采到一次——**均值正常 + P99 异常的系统，采样只会告诉你一切正常**。

## "剖析 profiling"的两种含义

书里 profiling ≈ 采样，但要留意日常语境的另一个用法："CPU profile" 常特指**基于 PMC/定时器的采样剖析**，而 "memory profile / leak profile" 可能是**全量跟踪**（每次分配都记）。判断工具属于哪类，看它的开销模型（与事件频率成正比 → 跟踪型）而不是名字。

## 可编程跟踪

BPF 催生了**可编程的跟踪工具**：事件发生时运行一段小程序，实时定制摘要或动作。这是它与传统固定统计工具（top(1) 这类"固定计数器 + 摘要打印"）的本质分界。

三种模式的递进：

```text
固定计数器:  工具作者预先决定统计什么 → 你只能看作者给的视图
跟踪+后处理: 全量事件搬回用户态 → 灵活但数据量爆炸（strace -o 大文件）
可编程跟踪:  事件发生时在内核里执行你写摘要逻辑 → 灵活 + 数据量可控
```

第三种正是 BPF 之前"跟踪"与"低开销"不可兼得的解法——也是本书所有工具的公共底座。

### HFT 关联

- 行情风暴期间每秒百万级事件——**采样会漏掉决定性的那几笔**，延迟尖刺排查必须用跟踪（per-event）工具；而常态画像用采样足够且开销低。两者互补，与 [14-SysPerf 观测工具](../../../../06.6-systems-performance/chapter-04-observability-tools/) 的口径一致
- "内核里做摘要"= 单核上的聚合不占用交易核，不经过用户态 ring buffer 拷贝
- 选型纪律模板：**常态水位看计数器（sar/_exporter）→ 周期画像用采样（perf）→ 尖刺现场用跟踪（BPF）**。三级递进，每级只在下一级证据需要时才升级开销
- strace 这类"全量搬回用户态"的跟踪在交易机上属于应急手段（开销可把 QPS 压塌），日常排障用 BPF 版（execsnoop/opensnoop 只输出已过滤的少数事件）

1. **均值正常、P99 异常的系统，为什么 CPU 采样剖析（perf record）发现不了问题？该换哪类工具？**

   <details><summary>参考答案</summary>

   采样看到的是时间占比的统计画像——尾部事件占比小，被采到的期望次数正比于占比，短窗口内几乎采不到。换跟踪型（per-event）工具：对延迟直接逐事件计时（如 runqlat/offcputime 的直方图模式，本质上每个慢事件都进了桶）。

   </details>

2. **跟踪的开销与什么成正比？挂探针前要做的第一个评估是什么？**

   <details><summary>参考答案</summary>

   与被跟踪事件的频率成正比（与采样不同——采样与事件率无关）。挂之前先估目标函数/事件的 QPS：µs 级单次成本 × 事件率 ≈ 总开销，超预算就要换聚合模式（内核 map 直方图）或换采样。

   </details>

3. **可观测性定义里为什么明确排除基准测试？**

   <details><summary>参考答案</summary>

   基准测试会改变系统状态（注入负载、改变缓存/调度行为），观测的是"被测系统+压测负载"的合成状态而非生产真实状态；观测工具的设计目标是"观测不改变被观测对象"（最小观测者效应）。两者互补但口径不同——benchmark 的结论不能直接当作生产画像。

   </details>
