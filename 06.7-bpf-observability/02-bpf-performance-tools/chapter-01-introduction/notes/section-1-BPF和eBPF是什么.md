# 1.1 BPF 和 eBPF 是什么

> 底本：《BPF之巅》中文版 1.1 节（PDF p41–42）

## 一句话定义

BPF 提供了一种**在各种内核事件和应用程序事件发生时运行一段小程序的机制**。

作者用的类比很精准：JavaScript 允许网站在浏览器事件（鼠标单击）发生时运行小程序，由此催生了 Web 应用生态；BPF 允许内核在系统和应用事件（如磁盘 I/O）发生时运行小程序，由此把**内核变得完全可编程**——而且不需要你是内核开发人员。

这个类比值得多想一步：JS 之所以能催生生态，是因为浏览器充当了**安全沙箱**（网页代码崩不了浏览器）；BPF 能进生产内核，靠的也是同样的结构——**验证器 + 沙箱化的执行环境**。没有沙箱的"内核可编程"（比如直接写内核模块）早就存在，但没人敢在生产环境用。

## BPF 的组成（三件套）

| 组成 | 说明 | 类比 |
|---|---|---|
| **指令集** | 虚拟指令集规范，因此 BPF 可视作一种虚拟机实现 | CPU 的 ISA |
| **存储对象** | map 等（内核态 key-value 存储，用户态可读写） | 进程的共享内存 |
| **辅助函数** | helper functions（内核提供的服务调用，程序不能任意调内核函数） | 系统调用表 |

三件套的边界就是 BPF 程序的能力边界：

- 程序**不能**随意访问内核内存——只能通过 verifier 认可的指针访问（如 ctx 里的包数据）
- 程序**不能**调用任意内核函数——只能调 helper（`bpf_probe_read_kernel`、`bpf_map_update_elem`…），helper 集合按程序类型裁剪
- 程序**不能**无限循环/无限内存——verifier 强制有限执行路径（v6.6 起有界循环已允许，但循环次数上限受验证状态约束）

这套"能力裁剪 + 静态验证"的组合，就是"安全沙箱"的内核实现。

## 执行方式：解释器 + JIT

- **解释器**：逐条解码执行 BPF 指令（`bpf_prog_run` 路径），慢但通用
- **JIT 编译器**：把 BPF 指令动态翻译成本机指令（x86-64/ARM64 各有后端），翻译一次、执行接近原生速度
- 现代内核大多 `CONFIG_BPF_JIT_ALWAYS_ON=y`（发行版默认），不可解释执行不可关——spectre 缓解的一部分（禁止攻击者注入可解释字节码）

**对性能的含义**：JIT 后的 BPF 程序就是普通的本机代码，单次执行是纳秒级——这是"BPF 观测可用于生产"的性能前提。若每次事件都要走解释器，µs 级的单事件开销在 HFT 事件速率下不可接受。

## 验证器：保证什么、不保证什么

执行之前必须过**验证器（verifier）**安全检查：

| 验证器保证 | 验证器不保证 |
|---|---|
| 程序自身不会崩溃（除零、空指针解引用、越界访问） | 程序合乎逻辑（可以写出能跑但没意义的程序） |
| 有限步内终止（无界循环被拒） | 数值正确（统计口径错、单位错照样过） |
| 不越权访问内存/不破坏内核数据结构 | 语义正确（读错了字段、配错了探针照样过） |

所以 BPF 程序的失效模式是"**悄悄输出错误数据**"而不是"内核 panic"——这决定了上线纪律：**新观测程序先在测试机对照已知基准（如 /proc 统计）验证输出，再上交易机**。

## 名字辨析：BPF vs eBPF

- 1992 年的 BPF = Berkeley Packet Filter（伯克利数据包过滤器），冷门的包过滤技术
- 2014 年，Alexei Starovoitov 提交重新实现 BPF 的内核补丁，与 Daniel Borkmann 共同完善后并入主线——BPF 变成**通用执行引擎**
- 扩展后的 BPF 常缩写为 **eBPF**，但**官方缩写仍然是不带 e 的 BPF**
- 内核中只有一个执行引擎，同时支持"扩展版"和"经典"程序；经典 BPF 程序由内核自动迁移到扩展引擎执行，经典 BPF 开发已停止
- 本书（以及如今社区惯例）用 **BPF** 指代扩展后的 BPF

新旧两代的本质差异（为什么"重新实现"是质变）：

| | 经典 BPF (1992) | 扩展 BPF (2014–) |
|---|---|---|
| 寄存器 | 2 个 32 位（A 累加器 + X 变址） | 11 个 64 位（R0–R10） |
| 用途 | 仅包过滤（tcpdump 表达式） | 通用执行引擎（网络/观测/安全） |
| 存储 | 无 | map |
| 外部调用 | 无 | helper 函数集 |
| 目标 | 尽快 accept/drop 包 | 任意计算 + 与用户态交互 |

## 三大应用领域

网络、可观测性、安全。本书聚焦**可观测性（跟踪）**。

---

### HFT 关联

- "事件发生时运行一段小程序"= 行情包到达、订单回调、定时器到期时**现场计算统计**，而不是把原始事件全部搬运到用户态再处理——这是 HFT 延迟观测零拷贝思路的根源
- 验证器"保证不崩内核但不保证逻辑正确"：写 BPF 观测程序时，**数值错误不会搞挂交易机，但可能让数据悄悄失真**——上线前要对照已知基准验证输出
- JIT 近原生速度 + 内核态聚合，使 BPF 观测对被测路径的干扰可压到亚微秒/事件；配合"未启用零开销"的插桩模型（见 1.6），平时交易路径不背任何观测税
- 交叉引用：指令集/寄存器/验证器的源码级细节在 [Learning eBPF Ch3 虚拟机](../../../01-learning-ebpf/chapter-03-anatomy-of-ebpf-program/) 与 [Ch6 验证器](../../../01-learning-ebpf/chapter-06-verifier/)；本模块重点是**用工具**，机制细节以那边为准

1. **BPF"沙箱"由哪几个机制共同构成？为什么"内核可编程"早就有（内核模块）却没催生生态？**

   <details><summary>参考答案</summary>

   沙箱 = 验证器（静态证明安全）+ helper 白名单（能力裁剪）+ map 隔离存储 + JIT（可控的执行方式）。内核模块没有验证、可调任意内核符号、一个 bug 就 panic——生产环境不可接受。JS/浏览器类比：没有沙箱的 ActiveX 也曾"可编程"，被淘汰正是因为不安全。

   </details>

2. **验证器通过了一个输出错误统计的观测程序，会以什么形式"失败"？这决定了什么上线纪律？**

   <details><summary>参考答案</summary>

   不会崩溃，而是悄悄输出错误数据（静默失真）——比崩溃更危险，因为基于错误数据的调优决策看起来一切正常。纪律：新观测程序先在测试环境对照已知真值（/proc 计数器、路由器统计）校验输出，再上生产/交易机。

   </details>

3. **经典 BPF 和扩展 BPF 最本质的差异是什么？（不是"用途更多"）**

   <details><summary>参考答案</summary>

   执行模型：2 个 32 位寄存器、无存储、无外部调用的"包过滤器"变成 11 个 64 位寄存器 + map + helper 的通用虚拟机。用途扩展（网络/观测/安全）是这个执行模型质变的结果而非原因。

   </details>
