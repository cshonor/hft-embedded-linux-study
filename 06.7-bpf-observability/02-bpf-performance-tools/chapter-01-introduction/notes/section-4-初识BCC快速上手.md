# 1.4 初识 BCC：快速上手

> 底本：《BPF之巅》中文版 1.4 节（PDF p44–47）

## execsnoop(8) — 第一个工具

跟踪**每个新创建的进程**（execve(2) 系统调用），每次 exec 打一行。核心价值：**短命进程**（ps/top 轮询根本撞不上的那些）在这里一览无余。

```text
# execsnoop
PCOMM    PID    PPID   RET ARGS
run      12983  4469   0   /run
bash     12984  12983  0   /bin/bash
svstat   12985  12984  0   /command/svstat /service/httpd
perl     12987  12984  0   /usr/bin/perl ...
sd       12988  12987  0   /bin/ps --ppid 1 -o pid,cmd,args
grep     12989  12987  0   /bin/grep org.apache.catalina
...
```

加 `-t` 参数输出**时间戳列**——这引出了书里的第一个真实排障案例：

> **Netflix 微基准测试结果波动案例**：`execsnoop -t` 显示每秒**批量创建 30 个进程、停 1 秒、再来 30 个**，循环往复。系统并不空闲！根因是某服务配置错误，每秒被拉起→失败→再拉起。禁掉该服务后基准数值立刻稳定。**系统"看起来空闲"和"真空闲"是两回事。**

这个案例演示的方法论是**业务负载画像（workload characterization）**：先给当前负载定性，很多时候理解了负载本身就足够解决问题，不必进入延迟下钻分析（详见第 3 章）。

作者留的练习：在自己系统上跑 `execsnoop` 一小时，看有没有惊喜。

## biolatency(8) — 第二个工具

块设备 I/O **延迟直方图**，与逐事件打印的 execsnoop 相对，代表"**内核里高效计算摘要**"类工具：

```text
# biolatency -m          ← -m 以毫秒为单位
     msecs           : count  distribution
0       -> 1         : 16335 |********                            |
2       -> 3         :  2272 |                                    |
4       -> 7         :  3603 |                                    |
8       -> 15        :  4328 |**                                  |
16      -> 31        :  3379 |**                                  |
32      -> 63        :  5815 |***                                 |
...
512     -> 1023      :    11 |                                    |
```

出自一台**延迟敏感的生产数据库**（SLA 只有几毫秒）。读图要点：

1. **双峰分布**：第一峰 0–1ms（16335 次）≈ 命中存储缓存或闪存，正常；第二峰 32–63ms 远超该存储预期 → **可能有排队**
2. **离群点（outlier）**：512–1023ms 区间 11 次 I/O。对数据库团队这是高优先级问题——一旦阻塞在这些 I/O 上，延迟 SLA 直接失守

工具运行期间在 BPF 程序里统计延迟，**Ctrl+C 结束时才打印摘要**——开销与事件数成正比但每事件极轻。

---

### 常见陷阱

1. 只看平均值不看分布——双峰 + 离群点才是延迟问题的真实形态，`biolatency` 的直方图比 iostat 的 avg/rqsz 有用得多
2. 用 ps/top 找短命进程——轮询窗口错过即丢失，必须用事件驱动跟踪

### HFT 关联

- `execsnoop`：交易机上任何**非策略进程**（错误 cron、watchdog 风暴、agent 自动升级）都会污染 cache 与调度，开市前跑一小时是标准体检项
- `biolatency -m`：交易机本地盘（日志/持久化队列）的长尾直接决定重启恢复时间；双峰判读法同样适用于行情网卡的延迟分析
- 业务负载画像方法论 = 先回答"系统现在到底在忙什么"，再谈优化

1. **execsnoop 相比 ps/top 的不可替代价值是什么？**

   <details><summary>参考答案</summary>

   事件驱动：跟踪 execve(2)，进程哪怕只存活几毫秒也会被记录；ps/top 是周期采样，短命进程大概率错过。且 execsnoop 带 PPID/RET/ARGS，能直接还原"谁拉起了什么、成功没有"。

   </details>

2. **biolatency 输出中"第二峰 32–63ms"意味着什么？下一步做什么？**

   <details><summary>参考答案</summary>

   远超该类存储预期 → 疑似排队（I/O 队列、队列调度器、下游存储拥塞）。下一步用 biosnoop（逐事件）确认哪些盘/哪些进程命中慢区间，再用 biostacks 看 I/O 的来源调用栈。

   </details>
