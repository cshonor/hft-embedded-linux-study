# 3.1 概览（目标 / 分析工作 / 多重性能问题）

> 底本：《BPF之巅》第 3 章性能分析，3.1 节（印刷 p71–73，含 3.1.1–3.1.3）

## 3.1.1 目标

性能分析的两大目标：**改进最终用户体验**、**降低运行成本**。先量化定义目标，才能判断是否达成、还差多少。可测量指标：

| 指标 | 含义 | HFT 对应 |
|---|---|---|
| 延迟 | 完成一次请求/操作的时间（常以毫秒计） | tick→发单延迟（P50/P99/P99.9） |
| 速率 | 每秒操作或请求数 | 订单提交速率、行情处理速率 |
| 吞吐量 | 每秒传输数据量（bit/byte） | 行情带宽（Mbps） |
| 利用率 | 资源在一段时间内的繁忙程度（%） | 交易核 CPU%、网卡带宽占用 |
| 成本 | 开销/性能比 | 每百万订单的硬件摊销 |

延迟 = 请求时间的组成之和：CPU 运行时间 + 等资源时间（磁盘 I/O、网络、锁）+ 等 CPU 调度时间。理论上可写一个 BPF 工具同时跟踪总延迟和各组成部分，但这与具体应用绑定且多事件跟踪开销大；**实践中更普遍的做法是用小而专的工具逐个研究特定组件**——本书的路线。

这个"组成之和"正是后续所有下钻工具的理论坐标系——每个工具测的其实是其中一项：

```text
总延迟 = CPU 运行        → profile(1) 采样剖析哪段代码
       + 等磁盘 I/O      → biolatency/biosnoop
       + 等网络          → tcpretrans/soconnlat（远端 RTT）
       + 等锁            → offcputime（含阻塞栈）
       + 等 CPU 调度     → runqlat/runqlen
```

"用一个工具全测"与"小工具逐项测"的取舍，本质是**通用性×开销 vs 专用性×精度**：全链路计时要在应用里埋点（侵入），小工具只挂内核边界（无侵入但要知道自己在测哪一段）。

作者的经验告诫：BPF 工具很容易"生成大量数据 → 花大量时间理解 → 发现指标不重要"。开发者常发来"看起来不健康"的指标截图，作者第一反应是"**你有已知的性能问题吗？**"——先明确目标（降延迟还是降成本），分析才有上下文。

## 3.1.2 分析工作（表 3-1）

| 性能分析活动 | BPF 工具的作用 |
|---|---|
| 原型软/硬件性能特征分析 | 测不同负载下的延迟直方图 |
| 开发阶段/集成前分析 | 解决瓶颈点、找一般改进点 |
| 发布前后非回归测试 | 多来源记录代码使用与延迟数据，快速定位回归 |
| 基准测试（市场宣传数据） | 研究性能问题、改进基准性能 |
| 目标环境 PoC 测试 | 生成延迟分布直方图，验证满足 SLA |
| 生产监控 | 编写可 7×24 运行的工具，提供此前属于盲区的指标 |
| 故障排查 | 现成工具或自定义观测点解决特定问题 |

注意这张表的活动分布在**整个软件生命周期**（原型→开发→发布→生产），不只是"出了事再查"。BPF 工具的两种运行形态也由此分野：

- **短窗口交互式**（排障、PoC）：人盯着输出，单行程序/现成工具
- **7×24 常驻式**（生产监控、非回归）：聚合直方图 + 定期输出，要求输出量与事件率解耦——这类工具的开发纪律比排障高一个量级（内存上限、丢弃策略、输出节流都要设计）

## 3.1.3 多重性能问题

- 用工具时要**做好同时发现多个问题的准备**；主要问题变成"哪个最重要"——通常是对延迟或成本影响最大的那个。
- 可以查组件的 bug tracker 搜"性能"，通常有多个未解决问题（还不含没列出来的）。
- 解决一个瓶颈后，其他问题才浮现；原瓶颈消除后新瓶颈出现。

"瓶颈会搬家"是常态而非异常：排队论视角下，系统吞吐受限于最慢一环，修复它之后次慢的一环立刻暴露。这决定了性能工作不是"一次项目"而是**持续过程**——也是"非回归测试"在表 3-1 里占一行的原因：每轮优化都可能把瓶颈推到新位置，需要基线对比。

## HFT 关联

- HFT 的量化目标天然清晰：**tick→决策→发单延迟（P50/P99/P99.9）、订单吞吐、行情处理速率**。"改善用户体验"在 HFT 里就是"比对手快"。
- "多重问题"提醒：对交易系统做第一次全链路观测时，会同时看到调度抖动、GC 停顿、缓存 miss……按对 P99 延迟的影响排序，而不是见一个修一个。
- "你有已知的性能问题吗？"——HFT 每日复盘（昨日 P99 尖刺）就是最好的切入点，比无目标巡检高效。
- 延迟组成公式直接映射排障四件套：profile（CPU）→ runqlat（调度）→ biolatency（IO）→ offcputime（锁/阻塞），与 3.3/3.4 清单的顺序一致。

## 陷阱

- 无目标巡检：把"有趣的输出"当问题修，浪费时间还引入风险。
- 只盯均值不看尾部分布：HFT 的钱都在 P99+ 里。
- 试图一次建"全链路统一计时工具"：与业务绑定死、多事件开销大——先用内核边界的小工具拼出分段画像，确有缺口再在应用内补点。

## 自测

<details>
<summary>1. 性能分析的两大目标与五个可测量指标是什么？</summary>

目标：改进最终用户体验、降低运行成本。指标：延迟、速率、吞吐量、利用率、成本。
</details>

<details>
<summary>2. 为什么不用一个 BPF 工具跟踪应用的全部延迟组成？</summary>

与具体应用绑定（不可复用），同时跟踪多个事件开销显著；小而专的工具更普遍。
</details>

<details>
<summary>3. "修复瓶颈后新瓶颈出现"在排队论视角下如何解释？对工程流程有什么要求？</summary>

系统吞吐受限于最慢环节（约束理论/排队论的必然结论），修复后次慢环节成为新的约束。工程上要求把性能工作当成持续过程：每轮优化后重新画像（基线对比），而不是假设"修完就好"；表 3-1 的"非回归测试"行就是为此存在的。
</details>
