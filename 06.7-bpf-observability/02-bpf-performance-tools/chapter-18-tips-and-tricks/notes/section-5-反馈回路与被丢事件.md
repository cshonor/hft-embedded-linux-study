# 5. 常见问题三：反馈回路与被丢掉的事件（18.11–18.12）

> 底本：《BPF之巅》第 18 章，18.11–18.12 节（印刷 p769–770）

## 18.11 反馈回路

**如果你跟踪你自己的跟踪，就能创建一个反馈回路。**

要避免的例子：

```bash
# bpftrace -e 'k:ext4_file_write_iter { printf("%s..", ..); }' > /ext4fs/out.file
```

- 前两个（printf 类）命令：意外跟踪了 bpftrace 自己 printf() 触发的事件，再创建新事件——**事件频率暴涨**，直到性能问题出现、你停止 bpftrace
- 第三个命令：bpftrace 自己触发 ext4 写来保存输出，导致产生更多输出需要保存——自我放大

**避免方法**：使用过滤器**排除自己的 BPF 工具**，或**仅跟踪目标进程**（如 `/pid != $$/`、按 comm/pid 过滤）。

## 18.12 被丢掉的事件

**症状**：工具输出不完整。BPF 工具可能因输出过快导致 **perf 输出缓冲区溢出**，或保存太多堆栈 ID 导致 **BPF 堆栈映射溢出**等。

```
# profile
WARNING: 5 stack traces could not be displayed.
```

**要点**：当事件被丢掉时**工具应该告诉你**（如上）。修复通常可以通过调整完成——例如 `profile(8)` 有 `-stack-storage-size` 选项增加堆栈映射大小（**默认映射能存储 16384 个唯一调用栈**）。如果调整十分频繁，应更新工具的默认设置，使用户无须更改它们。

|---|---|---|
| 事件缺失 | perf stat 交叉验证 | 修 BPF 工具 / 确认事件真的发生 |

## HFT 关联

- **反馈回路**对 HFT 尤其危险：交易机盘口高峰本就高频，自激励回路可能把节点拖垮——所有写文件/printf 的跟踪脚本必须带目标进程过滤
- 丢弃 5 条栈在普通系统无伤大雅，但在尾延迟调查中**恰是尾部样本**——排障脚本预先调大 -stack-storage-size，并永远关注 WARNING 行

<details><summary>参考答案</summary>

1. 成因：**跟踪自己的跟踪**——BPF 工具自身的 printf()/写文件又触发被跟踪的事件（如跟踪 vfs 写、输出又写到 vfs），事件生产自我激励、频率暴涨直到系统出问题。避免：① 谓词里**排除自己的 BPF 工具**（`/pid != $$/`、按 comm/pid 过滤）；② **只跟踪目标进程**，其余一概不管。
2. ① **perf 输出环形缓冲区溢出**（事件输出过快、用户态读不过来）；② **BPF 堆栈映射表溢出**（唯一调用栈存太多）。profile(8) 默认栈映射可存 **16384** 条唯一调用栈，可用 `-stack-storage-size` 调大。
3. 丢事件通常不是均匀随机丢——**高峰/洪峰时最容易丢**，而高峰期产生的那批事件恰是尾延迟的分位数所在。研究的目标样本被选择性丢弃，得到的 p99/p999 会**系统性偏乐观**，把人引向错误结论。所以必须盯着 WARNING 行，并在排障前预调大缓冲。

</details>
