# 3.5 小结（方法论落地路径 + 全章坑点 + 自测）

> 底本：《BPF之巅》第 3 章性能分析，3.5 节（印刷 p90）

## 原书小结

性能分析的目标是改善用户体验、降低运行成本。工具太多反而难选——**方法论指导选择**：从哪开始、一步步分析、到哪结束。本章概述了负载画像、下钻分析、USE、检查清单四种方法；给出 Linux 60 秒清单（日常分析首先使用，直接定位问题或提供 BPF 工具线索）；最后是 BCC 工具清单，细节在后续章节展开。

## 全章主线（一图流）

```
明确目标（延迟? 成本?）
   │
   ▼
60 秒传统清单（uptime→…→top）── 发现表层现象
   │
   ▼
BCC 11 工具清单（execsnoop→…→profile）── 定位具体层
   │
   ▼
方法论选路：
  · 不知道负载是什么     → 业务负载画像（谁/为何/组成/变化）
  · 已知延迟问题找根因   → 下钻分析（一层层拆，直到可修的机制）
  · 系统性巡检找盲区     → USE（每资源×使用率/饱和度/错误）
```

## 全章坑点表（HFT 视角）

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | 无目标巡检"有趣的指标" | 白费时间、误修 | 先问"有已知性能问题吗" |
| 2 | 下钻停在"设备/CPU 慢" | 买硬件而不是改配置 | 再钻一层找机制（时间戳案例） |
| 3 | 只看均值不看分布 | 错过 p99 尖刺 | biolatency/runqlat 直方图 |
| 4 | %util=100% 当容量满 | 错误扩容 | 并行设备看 await/队列 |
| 5 | load average 当 CPU 指标 | IO 等待虚高误判 | vmstat r 列（不含 D 状态） |
| 6 | USE 只查使用率 | 漏掉排队（饱和度） | 三项都查，饱和度常是延迟根因 |

## HFT 落地建议

1. 每日例行：60 秒清单 + 11 个 BCC 工具打包成脚本，开盘前后各跑一轮存档对比。
2. 事件驱动复盘：昨日 P99 尖刺 → runqlat/profile/biosnoop/tcpretrans 四件套按序下钻。
3. 资源盲区盘点：按 USE 资源图核对监控覆盖，补齐饱和度类指标（队列、重传、runq）。

<summary>2. iostat 显示 %util 100% 且 await 3ms，说明什么？</summary>

设备持续繁忙但响应快——并行设备吞吐可能还有余量，不是必然瓶颈；重点看 await 与队列。
</details>
