# 2. 建议与技巧：99Hz、灰鼠、先写负载、学系统调用、保持简单（18.2–18.6）

> 底本：《BPF之巅》第 18 章，18.2–18.6 节（印刷 p760–763）

## 18.2 以 49Hz 或 99Hz 为采样频率

目的：**避免锁步采样（lockstep sampling）**。定时采样绘制目标软件粗略图像，100Hz 或 50Hz 通常足以解决大小性能问题。

**锁步陷阱**：以 100Hz 为例每 10ms 采样一次。假设应用每 10ms 唤醒一次做 2ms 工作（占一个 CPU 的 20%）——若采样恰好总落在 2ms 工作窗口，剖析显示该应用 **100% 在 CPU 上**；若总落在睡眠期则显示 **0%**。两种结果都极具误导（混淆错误示例）。

用 **99Hz** 后，采样时间偏移不再总与应用工作对齐，几秒内就会收敛到正确的 20%；且足够接近 100Hz 可心算外推（8 CPU × 1 秒 ≈ 800 个样本——作者校验结果时常这样算）。73Hz 也能避锁步但心算难（"4 CPU 采 8 秒请给我计算器"）。

99 生效的原因：**程序开发者通常为定时活动选四舍五入的数字**（每秒 1 次、每 20ms 一次……）。若大家都改用每秒 99 次，锁步会卷土重来。作者称 99 为"**剖析员数字**"——除性能剖析外勿用于其他用途。

## 18.3 黄猪和灰鼠

数学里 17 很特殊，昵称"**黄猪**"数字（甚至有黄猪日 7 月 17 日）；对跟踪也有用——但作者更偏爱 **23**（"**灰鼠**"数字）。

**用法**：分析未知系统不知道跟踪什么时，注入一个**熟悉的工作负载**，对事件做频率计数，与负载相关的函数会自己浮现。例：想理解 ext4 如何执行写 I/O：

```bash
# dd if=/dev/zero of=test bs=1 count=230000   # 23 万次写，可与其他活动区分
# funccount -d 10 'ext4_*'                     # 跟踪所有 ext4 函数 10 秒（共 509 个函数）
ext4_write_checks          230117
ext4_file_write_iter       230117
ext4_da_write_end          230185
ext4_nonda_switch          230191
ext4_block_write_begin     230200
...（共 15 个函数超过 230000 次）
ext4_journal_check_start  460551
```

**15 个函数**被调用超过 230000 次——极可能与该负载相关，把 509 个候选缩小到 15 个。23（或 230、2300…）不易与其他不相关事件计数冲突：23 和 17 都是**质数**，在计算中比 2 或 10 的幂出现概率小；23 与 2/10 的幂距离比 17 更远。12.4 节也用了这个技巧。

## 18.4 开发目标软件

**先开发负载生成软件，再写跟踪工具**，可大幅节省时间。例：想跟踪 DNS 请求的延迟和细节——从开发简单的 DNS 请求生成器开始，就会知道哪些函数需要跟踪、请求细节如何存在结构体中、返回值是什么。互联网上针对开发者的文档（含代码片段）很丰富：`getaddrinfo(3)` 的手册页就包含可用的完整程序：

```c
memset(&hints, 0, sizeof(struct addrinfo));
hints.ai_family   = AF_UNSPEC;    /* Allow IPv4 or IPv6 */
hints.ai_socktype = SOCK_DGRAM;   /* Datagram socket */
hints.ai_flags    = 0;
hints.ai_protocol = 0;            /* Any protocol */
s = getaddrinfo(argv[1], argv[2], &hints, &result);
```

可进一步修改为只产生 23 个（或 2300 个）请求，配合 18.3 的技巧找协议栈中相关函数。

## 18.5 学习系统调用

**系统调用是跟踪的丰富目标**：手册页文档中有对应跟踪点，并提供应用资源使用的有用信息。例：syscount(8) 发现高频 `setitimer(2)`——那是什么？

```bash
$ man setitimer   # GETITIMER(2): interval timer，到期为调用进程生成信号并按间隔重置
```

手册页解释了 setitimer 是什么、传参和返回值——都可以通过 `syscalls:sys_enter_setitimer` / `syscalls:sys_exit_setitimer` 跟踪点检查。

## 18.6 保持简单

**避免开发冗长复杂的跟踪程序**。BPF 有跟踪所有事件的超级能力，但很容易被带偏。添加很多事件的缺点：

- **不必要的开销**：原始问题可能跟踪几个事件就解决，工具却跟踪更多事件，每个使用者付出更大开销
- **维护负担**：kprobes/uprobes **界面不稳定**，软件版本间会变化。Linux 4.x 系列中已发生内核变化导致 BCC 工具不可用的情况。解决方法：按内核版本添加代码（检查函数是否存在来选择，因为**反向移植使版本号不可靠**）、或复制工具保留在 tools/old 文件夹。最好是改用**跟踪点**（如 tcp 工具的 sock:inet_sock_set_state）——破坏将不再发生
- 修复 BCC 工具不难（每个工具只跟踪少数事件——作者刻意如此设计）；若每个跟踪数十个事件，损坏更频繁、修复更复杂，且**测试被放大**（需在所有相关内核版本测试所有事件类型）

**作者的惨痛教训**：15 年前开发 tcpsnoop(1m)，目标是显示哪个进程在做 TCP I/O，但最终做成了跟踪 PID 所有数据包类型（TCP 握手、端口拒绝、UDP、ICMP…）匹配网络嗅探器输出的工具——涉及大量不稳定内核细节，因内核升级损坏多次，完全忘记了原始问题，开发了不可维护的工具（详见第 10 章）。本书的 bpftrace 工具是 15 年经验的总结：**谨慎地只跟踪解决特定问题的最少必需事件**。

## HFT 关联

- 99Hz 原则直接适用于自研延迟剖析器；策略进程若用 10ms 定时器（常见！），100Hz 采样必然锁步
- "灰鼠 230000" 技巧适合定位行情解码路径：注入 23 万个已知报文，funccount 通配符一网打尽相关函数
- "保持简单"与交易系统工具开发同构：排障脚本只解决一个问题，禁止"顺手多跟踪几个"
