# 16.9 基于延迟的拥塞控制

> 章级精读：[../study.md#ch16-8](../study.md#ch16-8)

## 本节核心目标

理解 Vegas / FAST 等**基于延迟**的拥塞控制算法。

---

## 丢包型 vs 延迟型

| | 丢包型（Reno/CUBIC） | 延迟型（Vegas） |
|--|----------------------|-----------------|
| 信号 | **事后**丢包 | **RTT 微增**预测 |
| 反应 | cwnd 减半 | cwnd 微调 |
| 竞争 | — | 常对 CUBIC **过早谦让** |

---

## Vegas 原理

```
ExpectedRate = cwnd / BaseRTT  (最小 RTT 时的理论速率)
ActualRate = cwnd / RTT        (当前实际速率)

Diff = ExpectedRate - ActualRate
  Diff < α → cwnd 增 (未拥塞)
  Diff > β → cwnd 减 (开始拥塞)
  α < Diff < β → cwnd 保持
```

**核心思想**：RTT 开始增大但还没丢包时，就认为拥塞即将来临 → 提前降速。

---

## 为什么 Vegas 不流行

Vegas 在与 CUBIC 竞争时**过早谦让**——CUBIC 不看延迟一直增长直到丢包 → Vegas 先退让 → 带宽被 CUBIC 抢占。

---

## BBR (Google)

BBR 不是传统延迟型，而是**基于带宽探测**：
- 测量瓶颈带宽 + 最小 RTT
- cwnd = BDP × gain
- 丢包不降速（与传统 TCP 根本不同）

```bash
# 启用 BBR
sysctl -w net.ipv4.tcp_congestion_control=bbr
# 需要 kernel 4.9+
```

---

## HFT 关联

BBR 对 HFT 控制面可能有利——丢包不降速意味着延迟更可预测。但 BBR 的探测行为可能引入周期性延迟波动。
