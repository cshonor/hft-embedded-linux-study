# 15.4 Nagle 算法

> 章级精读：[../study.md#ch15-4](../study.md#ch15-4)

## 本节核心目标

掌握 Nagle 逻辑、与 **Delayed ACK 死锁**及 **TCP_NODELAY** 的工程选择。

---

## 核心逻辑

发送端整形：**自时钟** — 「链路上最多一个未确认的小分组」。

**规则**：若待发 < **MSS** 且**仍有在途未确认数据** → **缓存**，不立即发。

```
if (待发数据 < MSS && 有在途未确认数据)
    缓存，等 ACK 或攒够 MSS 再发
else
    立即发
```

目的：抑制 **tinygram 风暴**（RFC 896）

---

## Nagle + Delayed ACK 死锁

| 方 | 行为 |
|----|------|
| 发送方 (Nagle) | 等 ACK 才发下一小包 |
| 接收方 (Delayed ACK) | 等更多数据才回 ACK |

→ 周期性 **几十～几百 ms** 延迟毛刺

---

## 禁用 Nagle

```c
// C: 禁用 Nagle
int val = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &val, sizeof(val));
```

```go
// Go: TCPConn 默认已 NoDelay=true
conn.SetNoDelay(true)  // 实际上 Go 默认就是 true
```

```rust
// Rust: TcpStream 默认 Nagle 开启 → 需显式禁用
stream.set_nodelay(true)?;
```

---

## 何时开/关 Nagle

| 场景 | Nagle | 原因 |
|------|-------|------|
| 交互/实时（SSH, 游戏, RPC） | **关** (NODELAY) | 延迟优先 |
| 大文件传输 | **开** | 合并小包提高效率 |
| HFT 交易订单 | **关** | 延迟绝对优先 |
| 批量数据导入 | **开** | 吞吐优先 |

---

## HFT 关联

HFT 交易系统**必须** `TCP_NODELAY`——一个 200ms 的 Nagle 延迟可能导致错失套利机会。但同时要确保对端不做 Delayed ACK，否则即使关了 Nagle 仍有延迟。
