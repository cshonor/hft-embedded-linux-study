# 1.3 流量分类

> 本章：[chapter-summary.md](./chapter-summary.md) · 全书：[../README.md](../README.md)

**核心主旨**：按目标范围与传播机制划分广播、组播、单播，理解交换机/网卡如何处理不同流量，便于抓包时识别「正常泛洪」与异常风暴。

## 核心知识点

### 三类流量对比

| 类型 | 定义 | 典型地址/场景 | 对网络的影响 |
|------|------|----------------|--------------|
| **广播 Broadcast** | 发往**本网段所有端口** | L2：`FF:FF:FF:FF:FF:FF`（如 ARP）；L3：主机号全 1 的子网广播 | 每台主机网卡都会收到；驱动可**早期丢弃**非本机 ARP 响应，但广播过多仍拖慢网段 |
| **组播 Multicast** | **一份源** → **多个明确加入的接收者** | IPv4：`224.0.0.0`–`239.255.255.255`；以太网组播 MAC 映射 | 节省带宽；需 IGMP 等加入组；交换机可对组播做有限泛洪或 snooping |
| **单播 Unicast** | **点对点** 一台到一台 | 客户端 ↔ Web 服务器、日常 TCP 连接 | 交换机按 CAM 表精确转发；抓包默认所见多为单播 |

### 广播（Broadcast）

- **机制**：无论下挂 Hub 还是 Switch，**二层广播帧**会泛洪到 VLAN 内所有端口（除生成树阻塞口等例外）。
- **L2 例**：ARP 请求「谁是 192.168.1.1？」→ 目的 MAC 全 F。
- **L3 例**：子网内 DHCP Discover 等。
- **性能**：仅一台主机需响应时，其余主机在驱动层丢弃，但仍占用链路带宽；**广播风暴** = 异常大量广播导致拥塞。

### 组播（Multicast）

- **目的**：视频流、路由协议（OSPF 等）、部分发现协议——**一份拷贝**多接收者，避免 N 份单播复制。
- **编址**：接收方**加入组**（IGMP / MLD）后，网络才向该组转发；未加入者不应收到应用层有效载荷。
- **与广播区别**：广播 = 网段**所有人**；组播 = **订阅组**的成员。

### 单播（Unicast）

- **机制**：源/目的 MAC、IP 均指向具体接口；二层交换机查 CAM 表**只出对应端口**。
- **抓包**：本机网卡在非混杂模式下，通常只见**发给自己**的单播 + 广播/部分组播。

### 读包识别速查

| Wireshark 显示 | 判断 |
|----------------|------|
| `Ethernet` 目的 MAC = `ff:ff:ff:ff:ff:ff` | 二层广播 |
| `ip.dst` 为 `x.x.x.255` 或子网广播地址 | 三层广播 |
| `ip.dst` 在 224.0.0.0/4 | IPv4 组播 |
| 目的 MAC/IP 均为单播地址 | 单播 |

## 抓包/实操记录

| 实验 | 预期 |
|------|------|
| ARP | `arp` 过滤器 → 见广播请求、单播应答 |
| 组播（可选） | 同网段播放组播流或 `ping 224.0.0.1`（视 OS/策略）→ 观察目的 IP 段 |
| 风暴排查 | 统计 → **Endpoints / Protocol Hierarchy** 看广播占比是否异常飙升 |

> **拓展**：IGMP 加入/离开报文；广播风暴时结合端口计数与 STP 状态（见 TCP/IP 链路层笔记）。

## 疑问与总结

- **为什么 ARP 用广播问、单播答？** 问的时候还不知道对方 MAC；答的时候已知道请求方 MAC。
- 混杂模式下能看到更多**发往他人的单播**（若镜像/TAP），但仍可能看不到其他 VLAN 的流量。
