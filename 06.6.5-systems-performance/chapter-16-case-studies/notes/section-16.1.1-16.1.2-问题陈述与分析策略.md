## 16.1.1–16.1.2 问题陈述与分析策略

> **出处：** Gregg《性能之巅》Ch 16.1.1–16.1.2 · 案例的前两步——**先把问题写成可验证的句子，再决定先看什么**。
> **HFT 实操要点：** 90% 的排查时间浪费，源于问题陈述里混进了**未验证的因果假设**（「肯定是网络」）。陈述只写**观测事实**，假设单独列。

```
  问题陈述（只写事实）        分析策略（花钱的顺序）
  ─────────────────          ─────────────────────
  什么现象 · 什么范围          先便宜的观测：统计 → 配置
  从何时开始 · 影响多大        再昂贵的观测：PMC → trace
  与什么对比                  每一步前有假设，每一步后更新
  ❌ 不写「我猜是…」           假设清单 = 排查路线图
```

---

### 一、问题陈述（Problem Statement）：六要素格式

Gregg 在 Ch 2 给出的纪律（源自 SRE 实践）：**问题没写清楚之前，不动工具**。

| 要素 | 问自己 | Netflix 案例精神 | HFT 模板 |
|------|--------|------------------|----------|
| **现象** | 观测到什么？数字是什么？ | 吞吐相对历史基线**莫名改善** | tick P99 从 8 µs → 5 µs（-37%） |
| **范围** | 哪类实例/进程/核/时段？受影响面占多少？ | 哪类实例、哪个 region、哪个时段起 | 哪个策略进程、哪个交易所 session、全量还是部分核 |
| **起点** | 从何时开始？与什么事件对齐？ | 与某次镜像/部署的时间相关性 | 与哪次 commit / 哪台机器替换 / 哪次重启对齐 |
| **对照** | 「变好」相对什么 baseline？baseline 本身可信吗？ | 相对监控历史均值 | 相对昨周同时段？昨周行情与今天可比吗？ |
| **影响** | 业务后果（收益 or 风险）？ | 吞吐↑ → 成本/容量估计 | P99↓ 但尾部风险未知 → 是否影响容量规划 |
| **非目标** | 本次排查**不做**什么？ | 先不「再调一个参数」、不猜根因 | 不改代码、不重启进程（保现场） |

**写好陈述的判据：** 拿给一个不了解情况的人，他能复述出「什么系统、什么指标、从什么时候、相对什么、变了多少」。做不到就重写。

**反例 → 正例（HFT）：**

```
❌ 反例：「今天系统变快了，估计是昨天内核升级的效果，看看？」
   （混入了未验证因果；「快」没有数字；没有范围）

✅ 正例：「策略进程 A（订单路径，核 8-11）的 tick→order P99 从
   8.1±0.3 µs 降至 5.2±0.2 µs（n>10⁶），起始时间 14:30 昨日部署后；
   同机行情进程无变化；对照组（未部署的进程 B）P99 不变。
   本次排查先不做任何变更，只收集证据。」
```

注意正例里 **对照组** 的价值：进程 B 没变 → 变化归因于「部署」而非「环境」（若 B 也变好，嫌疑转向机器级/邻居级）。这是 Ch 12 对照实验思想的日常化。

### 二、反模式清单（Ch 2 反面方法 · 案例前的预防针）

| 反模式 | 症状 | 对 Unexplained Win 的特殊危害 |
|--------|------|------------------------------|
| **路灯法** Streetlight | 只查自己熟悉的指标（CPU%） | Win 常藏在你不熟的维度（缓存、邻居、频率） |
| **随机变更法** | 没假设就改 sysctl「试试看」 | 破坏现场：改动后再测，win 消失也说不清是谁的锅 |
| **归咎他人** | 「肯定是网络/云厂商的问题」 | 未经证实的转移动机，错过真因 |
| **亲切感偏差** | 「上次也是这个原因」 | 上次的 win≠这次的 win；相关≠因果 |
| **指标崇拜** | 只看聚合均值 | P99 的改善可能只发生在分布的一段，均值看不出来 |

> Unexplained Win 场景下最致命的是 **随机变更法**：你只有一个「案发现场」（win 还在的窗口），任何配置改动都可能污染它。原则：**先读后写，只读排查**。

### 三、分析策略（Analysis Strategy）：竞争假设矩阵

科学方法（Ch 2）：列出 **竞争假设**（competing hypotheses），按「观测成本 × 区分能力」排执行顺序。

**Hypothesis Matrix 模板（HFT 版 P99 突降）：**

| 假设 | 预期观测（若为真） | 验证成本 | 淘汰顺序 |
|------|--------------------|----------|----------|
| H1: 新代码热路径变短 | profile 里旧热点函数占比下降 | 中（perf record 前后对比） | ② |
| H2: 邻居撤离（LLC/带宽释放） | `mpstat` 同节点其他核利用率同步下降 | **低**（一条命令） | **①** |
| H3: 页表/THP 状态变化 | `smaps` AnonHugePages↑；TLB miss↓ | 低 | ① |
| H4: 绑核/亲和终于生效 | `perf stat` cpu-migrations↓ | **低** | **①** |
| H5: 测量口径变化 | 打点 diff 非空；直方图形状突变 | 低（code review） | ① |
| H6: CPU 频率/降频状态变化 | `perf stat` GHz 行↑；`turbostat` | 低 | ① |

**排序原则：**

1. **便宜先行**：能一条命令否定/确认的假设先做（H2/H4/H5/H6 全是低成本）。
2. **淘汰率高优先**：一个观测若能同时淘汰多个假设（如 `mpstat` 同时看邻居、频率、迁移），优先做。
3. **串行不并行**：昂贵的观测（PMC、trace）等便宜假设全部淘汰完再上——目标是被压缩到 1–2 个假设后做 **确认性** 深挖。

### 四、Drill-Down：四层下钻地图

```
  L1 系统级   vmstat/mpstat/sar/ss      「哪类资源有异常迹象？」
     ↓ 缩小：哪颗核、哪个进程、哪个时段
  L2 资源级   perf stat(PMC)/压力检查    「CPU 在微架构层发生了什么？」
     ↓ 缩小：哪个指标组合解释了「快」
  L3 路径级   perf record -g / trace     「哪条调用路径变短了？」
     ↓ 缩小：哪个函数/系统调用/分支
  L4 代码级   火焰图 diff / 源码对读     「哪个变更导致了这个函数变快？」
```

- **每层停留时间与证据成正比**：没有指向下一层的证据就不下钻（Ch 2 的「有据下钻」）。
- **记录格式**：每步一行「观测 → 结论 → 下一步」，事后直接变成 postmortem 草稿（16.1.8）。

**策略选择的两个入口（对照 Ch 2 两种视角）：**

| 入口 | 适用 | 案例中的体现 |
|------|------|--------------|
| **Resource 分析**（自下而上） | 现象无明确业务指向 | 16.1.3–16.1.6 从资源统计/PMC 入手 |
| **Workload 分析**（自上而下） | 现象在业务指标层 | 先确认 tick 量/订单构成没变（排除 H 负载假设）|

案例里两者都要：**先用 Workload 排除「分母变了」，再用 Resource 找分子机制**。

### 五、时间预算（HFT 修订版）

| 阶段 | 占比 | 产出物 |
|------|------|--------|
| 问题陈述 + 假设清单 | 20% | 一段可复述的事实 + 假设矩阵 |
| 统计 + 配置（16.1.3–4） | 25% | sar 对比图、配置 diff 清单 |
| PMC + 软件事件（16.1.5–6） | 25% | perf stat 前后对照表 |
| 动态追踪（16.1.7） | 20% | profile diff / 直方图对比 |
| 结论 + 归档（16.1.8） | 10% | 因果链 + runbook/release note |

> 教训模式：跳过前 20% 直接开工具的人，通常在后 40% 里反复绕圈——因为不知道自己在排除什么。

<summary>代码自测（Q&A，先遮住答案想）</summary>

**Q1：为什么问题陈述里禁止出现因果猜测？**

A：① 猜测会污染观测选择——你会只看「支持猜测」的指标（确认偏差，路灯法的变体）；② 猜测会传染团队——「肯定是内核升级」传三遍后就成了「事实」，后续排查被锚定；③ 猜测让陈述不可验证——无法判断排查是否完成。正确做法：事实进陈述，猜测进假设清单（单独管理、逐个证伪）。

**Q2：对照组（未部署的进程 B）在案例里起了什么方法论作用？**

A：差分（differencing）。若 A 变好而 B 不变 → 变化与部署强相关（缩小到代码/进程配置）；若 A、B 同时变好 → 嫌疑上移到机器/环境/邻居层。一个对照，直接把假设空间砍半。这是实验设计里「控制变量」在生产排查中的最小可行版本。

**Q3：为什么 Unexplained Win 场景下强调「只读排查，先读后写」？**

A：Win 是一个**可能随时消失的现场**（邻居可能回来、缓存可能失效），而任何配置变更本身就会改变系统状态。改动后即使 win 消失，你也无法区分「改动破坏了 win」还是「win 本来就要消失」——现场被自己污染。若必须变更（比如需要重启加载追踪工具），先做完整快照。

**Q4：假设排序为什么「便宜且淘汰率高」的优先，而不是「最可能为真」的优先？**

A：信息论视角：排查的目标是**最快缩小假设空间**，不是「最先确认最喜欢的假设」。一个便宜的观测即使淘汰掉的是「不太可能」的假设，也是净收益；而贵的观测若只服务于单一假设，一旦该假设被证伪，投入全部沉没。「先验概率」决定你想什么，「成本×区分度」决定你做什么。

</details>
