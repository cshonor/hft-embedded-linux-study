## 16.1.7–16.1.8 动态追踪与结论

> **出处：** Gregg《性能之巅》Ch 16.1.7–16.1.8 · 最后两步——统计/PMC 说了「哪类快」，动态追踪回答「**谁、哪条路径、何时**快」；结论把全部线索拼成因果链。
> **HFT 实操要点：** 追踪是**最贵**的观测（有中断/开销、可能改变时序），纪律是 **窄范围、短时长、带假设进场**；结论的可交付形态不是「找到了」，而是 **可复现的证据链 + 可执行的 runbook**。

```
  观测成本阶梯（案例的推进顺序 = 成本递增）
  sar/配置 diff ──→ perf stat(PMC) ──→ perf record(采样) ──→ trace/Ftrace/BPF(逐事件)
     零开销            ~零开销            低开销                开销随事件数线性
  ─────────────────────────────────────────────────────────────────────────
  「行为变了吗」     「微架构哪类快」     「哪条路径快」          「每个事件的时序」
```

---

### 一、动态追踪（Tracing）：工具选择矩阵

| 工具 | 案例中的角色 | 粒度 | 开销 | 适用假设 |
|------|--------------|------|------|----------|
| **`perf record -g`** + 火焰图 | CPU 时间在函数间的分布——热点是否迁移 | 函数级（采样） | ~1–5% | 「哪条路径变快了」（on-CPU） |
| **`perf diff`** | 前后两份 profile 的 **逐符号差分**——优化的直接证据 | 函数级 | 复用 record | 定位到具体函数 |
| **`perf trace`** | syscall 序列+耗时——路径是否变短、调用是否变少 | 系统调用级 | 中 | 系统调用路径变化 |
| **Ftrace function_graph** | 单函数的内核路径耗时展开（`maxdepth` 控制） | 内核函数级 | 高（窄范围用） | 内核侧路径耗时 |
| **BCC/bpftrace 专项** | runqlat / offcputime / tcpretrans 等**预打包问题** | 事件级直方图 | 低–中 | 调度延迟、阻塞原因、重传 |

**原则（Ch 4 / Ch 14）：**

1. **带假设进场**：每一轮追踪前写下「我预期看到 X」——追出来的数据才能证伪假设。
2. **要栈，不要计数**：只有计数知道「快了」；有栈才知道「哪条路径快了」。
3. **开销预算**：trace 工具运行的时间窗口内，延迟指标本身已失真——**不要**用同一窗口的 P99 数据下结论（观测者效应）。

**案例式组合拳（前后对比是灵魂）：**

```bash
# —— 采样 profile 前后对比（16.1.7 主力）——
perf record -F 99 -g -p <PID> -- sleep 10     # 现在的分布
# （对照案发前的存档 profile——这也是「事前纪律」的一部分）
perf diff old.perf.data new.perf.data          # 逐符号 +xx%/-xx%

# —— on-CPU vs off-CPU 的分野 ——
sudo runqlat-bpfcc 10                          # 调度延迟直方图：任务等多久才能上 CPU
sudo offcputime-bpfcc -p <PID> 20              # off-CPU 时间的**阻塞栈**：等在哪

# —— 网络路径专项（HFT）——
sudo tcpretrans-bpfcc                          # 重传是否消失（「变快」的另一种真相）
```

---

### 二、三个必会工具的输出精读

**① runqlat（调度延迟）——直方图怎么读：**

```
     usecs           : count    distribution
         0 -> 1      : 1123     |████████████                    |
         2 -> 3      : 2984     |████████████████████████████████|
         4 -> 7      : 1560     |████████████████                |
         8 -> 15     :  412     |████                            |
        16 -> 31     :   88     |█                               |
        32 -> 63     :   12     |                                |
       128 -> 255    :    2     |                                |
```

- 看的是**形状与尾巴**：健康系统主峰在 0–8 µs；若出现 64 µs+ 的次级 bump，说明存在偶发排队（HFT 抖动源）。
- Unexplained Win 对照：案发前的 runqlat 若有 100 µs 级尾巴而案发后消失 → 「快」来自调度阻塞消除 → 顺着 offcputime 找是谁抢了 CPU。

**② offcputime（阻塞栈）——回答「CPU 时间之外去哪了」：**

```
    ~     µs  count  stack
    ...
     521324     412  finish_task_switch.isra.0
                        __schedule
                        schedule
                        futex_wait_queue
                        futex_wait
                        do_futex
                        __x64_sys_futex                      ← 等 futex 锁！
    ...
```

- on-CPU 工具（perf record）对「等锁/等 IO」无能为力——那段时间 CPU 没执行你的代码。offcputime 专门补这块。
- 读法：自底向上是栈，count 是该栈累计阻塞次数，µs 是累计时长。**futex 栈出现在热路径 = 锁竞争故事**，与 16.1.6 的 context-switches 下降互为印证。

**③ perf diff（前后对比）——「真实优化」的直接证据：**

```
 # Baseline  Old  New  Symbol
 # ........  ...  ...  ........................................
    +12.34%   6.1%  0.0%  [kernel.kallsyms] copy_user_generic
     -4.10%   0.0%  4.1%  [kernel.kallsyms] clear_page_rep
```

- 第一行：copy_user 占比 6.1%→0 —— 某条 copy 路径消失了（比如换了零拷贝）。**这才是能写进 release note 的证据**。
- 注意 diff 的前提：两份 profile 同 workload、同采样率、同事件——又是 Ch 12 的可比性。

### 三、结论（Conclusion）：Drill-Down 拼图四问

统计、配置、PMC、trace 走完，手里是一堆线索。结论的判据是**能回答四问**：

| # | 问题 | 证据形态 |
|---|------|----------|
| 1 | **什么**变了？（配置/负载/代码/环境/状态） | 配置 diff / 负载对比 / perf diff |
| 2 | **哪一层**受益？（调度/缓存/网络/磁盘/频率） | PMC 组合 + 专项工具直方图 |
| 3 | **证据链**完整吗？（每步推理有观测支撑，无跳跃） | 排查日志（16.1.2 的记录格式） |
| 4 | **可行动**项是什么？ | 见下方结局分流 |

**Unexplained Win 的五类结局（学习框架——原案例细节以书为准）：**

| 结局 | 教训 | 可行动项 |
|------|------|----------|
| **负载/邻居变化** | 云/多租户对比必须同条件；win 不可持续 | 容量规划剔除该数据；考虑独占宿主/置放群组 |
| **配置 drift** | 静态配置审计（16.1.4）是盲区重灾区 | 把修复的配置**显式固化**进镜像/部署脚本——把意外变必然 |
| **缓存/预热** | 区分 cold vs steady state（Ch 12） | warm-up 策略化：上线后预热期数据不入容量模型 |
| **真实代码优化** | PMC + profile **可复现** | 写 release note；profile 存档为下次 baseline |
| **测量 artifact** | 指标口径/窗口/采样率 | 修指标代码；给指标打版本；直方图形状审查入流程 |

**Postmortem 最小结构（每行「观测→结论」都可回溯）：**

```markdown
## Unexplained Win 报告：<系统> <指标> <变化幅度>
1. 现象与范围（问题陈述原文）
2. 排查路径（假设矩阵 + 每步观测与淘汰记录）
3. 根因（四问回答）
4. 分类（五类结局之一）与可持续性判断
5. 行动项：固化/回滚/监控/runbook
```

### 四、HFT 增补：结论的两个特殊分支

| 分支 | 判据 | 行动 |
|------|------|------|
| **Win 来自私有状态**（THP 合页、预热、branch predictor 训练） | 重启后 win 消失即可证伪「代码论」 | 冷启动流程里显式重建状态（madvise、预取回放）；**重启实验是最便宜的反证** |
| **Win 来自邻居**（共置撤出、宿主机更换） | `mpstat` 全核对照 + steal + microcode | 容量规划按「有邻居」建模；关键路径考虑独占资源 |

> 「重启实验」值得单独记：对「真实优化 vs 环境偶然」的区分，**reboot 即是最小对照实验**——代码优化重启后仍在，缓存/预热/页表状态全部归零。成本几乎为零，却一次淘汰半个假设空间。

<summary>代码自测（Q&A，先遮住答案想）</summary>

**Q1：为什么「要栈，不要计数」？**

A：计数（事件发生 N 次）只能确认「变快了」这个事实，无法区分机制——200 万次 cache miss 可能集中在一条函数也可能摊在几十条。栈把事件挂到调用路径上，才能回答「哪条路径快了」，进而 diff 出「哪个变更导致的」。这是 16.1.8 结论第 1 问（什么变了）的必要证据形态。

**Q2：offcputime 与 perf record 各自的盲区是什么？为什么 HFT 两个都要？**

A：perf record（on-CPU 采样）只采样「CPU 正在执行」的时间——任务在等锁/等 IO/等调度时不被采到，这段时间在火焰图里**不存在**。offcputime 恰好相反，只记录「下 CPU 到上 CPU」的阻塞及栈。HFT 的延迟 = on-CPU 时间 + off-CPU 时间 + 排队时间，只看一边会系统性漏掉另一半故事——「变快」可能根本不是代码变快，而是阻塞消失。

**Q3：追踪工具运行期间的 P99 数据为什么不能用？这带来什么流程约束？**

A：trace/bpftrace 逐事件插桩（kprobe 触发、抄栈、写 ring buffer），开销直接加在被追踪路径上——观测行为本身抬高了被测延迟（观测者效应）。流程约束：① 观测窗口与测量窗口分离：追性能数据时收性能数据，但**不用同窗口的 P99 下业务结论**；② 追踪产出的结论（如「该函数阻塞消失了」）应拿到**无插桩**的复现环境验证。

**Q4：五类结局里，「配置 drift」的正确收尾为什么是「固化」而不是「回滚」？**

A：Unexplained Win 的 drift 意味着当前配置**更好**——回滚等于主动放弃 win。正确动作是把「意外的正确配置」显式写进镜像/部署脚本/基础设施代码（IaC），让 win 从「偶然状态」变成「受版本管理的必然」。同时审计同类机器是否还存在旧配置（drift 是集群性的），把盲区补成监控项（配置基线告警）。

**Q5：重启实验的原理与局限？**

A：原理：代码优化与数据布局优化**持久**，而私有状态（页表/THP 合页、page cache、锁竞争的时序相位、分支预测器的训练）在重启后归零——重启后 win 保留 → 代码论增强；win 消失 → 状态论坐实。局限：① 重启同时清掉了**邻居与共置状态**吗？没有——单机重启不清邻居；② 重启可能改变进程启动顺序/内存布局（ASLR），引入新变量；③ 生产机器重启成本高，通常在复现环境/同类机器上做。它是便宜的反证，不是终极证明。

</details>
