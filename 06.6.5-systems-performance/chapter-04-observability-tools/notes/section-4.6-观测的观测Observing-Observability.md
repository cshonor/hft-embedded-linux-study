## 4.6 观测的观测（Observing Observability）

> 本章导读 · [4.1 危机工具](./section-4.1-工具覆盖范围与危机工具.md) · [4.4 sar 工具](./section-4.4-sar-工具.md) · [4.5 四大追踪器](./section-4.5-四大追踪器.md)

---

### 本节讲什么

性能工程里最容易被跳过的一课：**观测系统本身也是被观测系统的一部分**。工具会写错、内核 counter 会不准、测量行为会改变被测对象。本节把「对观测结果保持怀疑」落成可操作的规程——四类风险、量化自身开销的实验方法、盲区清单，以及 HFT 共置机上「debug 用全量 trace 可能改变 P99」这个最尖锐的案例。

### 要点

| # | 要点 | 一句话展开 |
|---|------|-----------|
| 1 | 观测有四类失败来源 | 工具实现 bug、内核指标 bug、文档错误、观测者效应 |
| 2 | 观测者效应可量化 | 追踪开/关各测一遍，差值就是工具开销 |
| 3 | 每类工具都有结构性盲区 | 采样漏短事件、counter 无时序、/proc 是快照 |
| 4 | 交叉验证是唯一通用解药 | 同一现象至少两个独立数据源对答案 |
| 5 | 观测条件要随数据一起存 | 内核/工具版本、采样率——否则无法复现 |
| 6 | HFT 的极端形态 | 为 debug 开的全量 trace 本身就能改变 P99 |

---

### 一、四类风险与实例

| 风险 | 说明 | 真实案例形态 |
|------|------|-------------|
| **工具实现错误** | 解析 /proc 字段 bug、单位换算错 | 某版本工具把 KB 当 KiB 算，内存显示差 2.4%；读 /proc/stat 没处理 counter 回绕，算出负速率 |
| **内核指标 bug** | 某内核版本 counter 本身不准 | iowait 在某些配置下语义漂移；NIC 驱动统计 rx_drops 恒 0（驱动没实现该回调） |
| **手册/文档错误** | man page 与实际行为不一致 | man 说单位是毫秒，代码里是微秒（或反之）；文档描述的是老版本行为 |
| **观测者效应** | 追踪本身占 CPU、改 cache 行为、拖慢被测系统 | perf 采样让热核多了 PMI 中断；BPF 程序挤占热核指令 cache |

**为什么「文档错误」也单列一列**：初学者默认 man page 是权威，实际上性能工具的文档更新速度远落后于代码。Gregg 的忠告：**当工具输出与理论预期矛盾时，先怀疑三层——自己的理解、工具的实现、内核的 counter——最后才怀疑硬件**。

### 二、观测者效应：量化自身开销的实验

不要猜开销有多大，**测**。对照实验模板：

```bash
# ① 基线：不挂任何观测
./benchmark --duration 60 --output baseline.json

# ② 挂上你要用的观测（例：perf 采样 + bpftrace）
perf record -F 99 -g -p <PID> -o perf.data &
bpftrace -e 'tracepoint:block:block_rq_issue { @[comm] = count(); }' &
./benchmark --duration 60 --output with_tools.json

# ③ 对比 P50/P99/吞吐
#    差值 = 观测开销（对被测指标的影响，不是工具的 CPU 占用）
```

三个容易被混淆的口径：

| 口径 | 含义 | 谁关心 |
|------|------|--------|
| 工具自身 CPU 占用 | perf/bpftrace 进程吃了几 % CPU | 运维（别把机器压垮） |
| **对被测指标的影响** | 挂上工具后 benchmark 的 P99 变差多少 | **性能工程师（这才是观测者效应）** |
| 对系统整体的影响 | 其它进程被挤慢多少 | 共置场景 |

最隐蔽的是第三种：perf 采样挂在热核旁边，自己 CPU 占用 2% 看似无害，但**每次 PMI 中断都冲刷热路径的指令/数据 cache**——被测进程 P99 的劣化远超 2%。这正是「工具的 CPU% 不能代表伤害」的原因。

### 三、每类工具的结构性盲区

盲区不是 bug，是**原理决定的看不到**：

| 工具类 | 盲区 | 机制 |
|--------|------|------|
| 采样型（perf record） | 两次采样之间发生的一切 | 99Hz 采样 = 平均每 10ms 一个样本，**短于几 ms 的尖刺只能靠运气撞见** |
| counter 型（vmstat/iostat） | 事件的时序与分布 | 「这秒 1000 次 cache miss」看不出是均匀还是一次 burst 全砸 |
| /proc 快照型（top/ps） | 两次刷新间的生死 | 活了 3ms 就退出的进程，top 永远看不见 |
| 逐事件追踪型 | 事件太多时自身成为瓶颈 | ptrace/bpftrace print 模式限流后事件被丢弃 |
| 直方图聚合型 | 个体身份 | runqlat 直方图知道「有次延迟 50ms」，不知道是哪个任务、为什么 |

**组合解法**：先聚合型工具看分布形状（有没有尾巴），形状异常再上逐事件型（biosnoop/drsnoop）拿个体身份，最后 Ftrace/perf 拿因果链。这也是全书反复出现的「漏斗」结构（[6.5 三级方法漏斗](../../chapter-06-cpus/notes/section-6.5-性能分析方法论.md) 同构）。

### 四、交叉验证规程

「对观测结果保持怀疑」的操作化，是让**两个独立数据源对答案**：

| 要验证的量 | 数据源 A | 数据源 B（独立实现） |
|-----------|----------|---------------------|
| CPU 利用率 | mpstat（读 /proc/stat） | pidstat 按进程加总 / sar -u |
| 磁盘 IOPS | iostat（/proc/diskstats） | biosnoop 计数（BPF 事件级） |
| 内存压力 | vmstat si/so | PSI /proc/pressure/memory |
| 网络丢包 | ethtool -S（NIC 计数） | ss 计数 + netstat -s（协议栈计数） |
| syscall 次数 | strace -c（ptrace） | bpftrace sys_enter count（eBPF） |

两源一致 → 采信；**两源矛盾 → 有一个在说谎，这本身就是线索**（典型：NIC 说没丢包、协议栈说有——问题在两者之间的 ring buffer，见 [10.5 UDP 五段丢包定位](../../chapter-10-network/notes/section-10.5-分析方法论.md)）。

**观测条件的记录**：每次留下性能数据的记录都要附环境指纹——`uname -r`、工具版本（`perf -v`、`bpftrace --version`）、采样率、挂了哪些探针。三个月后复现「当时的测量」时，缺了这些等于没有数据。

### 五、HFT 尖锐案例：为 debug 开的全量 trace 改变了 P99

场景：tick-to-trade P99 偶发劣化，工程师决定「上 bpftrace 挂全量 tracepoint 抓现场」。结果劣化从「每分钟一次」变成「持续存在」——**观测行为消灭了要观测的现象，同时制造了新现象**。

三层教训：

1. **热路径上的每个探针都有成本**。即使 BPF 聚合开销只有 µs 级/事件，热核上每秒百万事件叠加起来的 cache 污染与额外分支不是零。
2. **正确姿势是先旁路后现场**：shadow/replay 环境先复现（[12.2 replay](../../chapter-12-benchmarking/notes/section-12.2-基准测试的类型.md)、[Ch 16 案例演练](../../chapter-16-case-studies/)），复现不了再上生产、且**收窄探针范围**（只挂嫌疑函数、filter 收到单个 PID）+ **限时窗口**（30s 自动 detach）。
3. **测量结果要标注「这是挂了观测时测的」**。挂 trace 时测到的 P99 和裸奔 P99 是两个不同的量，报告里混用就是自己骗自己。

这也是「常驻统计、按需追踪」纪律（[4.5](./section-4.5-四大追踪器.md)）的最终理由：**统计工具的开销低到可以忽略，才配常驻；追踪工具的开销决定了它只能开窗**。

### HFT / 嵌入式关联

| 场景 | 应用 |
|------|------|
| 上线前验收 | 对照实验量化每个常驻观测项的 P99 影响，超预算（如 >100ns）的移到非热核跑 |
| 剖析流程 | perf 挂上后的火焰图代表「有观测时的 CPU 分布」，结论外推到裸奔状态要留余量 |
| 嵌入式 | 板卡资源少，观测者效应更显著（cache 更小、CPU 更弱）；Ftrace ring buffer 大小要预算 |
| 报告纪律 | 性能报告必附观测条件指纹；「无观测基线」与「有观测测量」分列 |

### 常见陷阱

1. 观测工具不测开销——BPF/perf 本身消耗 CPU，可能改变系统行为，导致观测结果不准
2. 观测盲区不自知——以为看到了全部，实际 /proc 和采样都有盲区，短事件/极短进程可能漏
3. 不记录观测条件——内核版本/工具版本/采样率不记录，复现时条件不一致
4. 用工具自身 CPU% 代表伤害——perf 占 2% CPU 但 cache 冲刷让被测 P99 劣化更多；要对被测指标做开关对照
5. 两源矛盾时随机采信一个——矛盾本身是线索（如 NIC vs 协议栈丢包差异指向中间 ring buffer）
6. 挂着 trace 测的数当裸奔基线——「有观测的 P99」和「无观测的 P99」是两个量，报告必须分列

6. HFT 生产机上抓 tick 路径偶发劣化的正确姿势？
   <details><summary>答</summary>先 shadow/replay 复现；复现不了才上生产，探针收窄到嫌疑点（filter 到单 PID）、限时窗口自动 detach；挂 trace 期间的测量单独标注，不与裸奔基线混用</details>
