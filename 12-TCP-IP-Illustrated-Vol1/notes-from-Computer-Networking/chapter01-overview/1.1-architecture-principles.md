# 1.1 体系结构原则

> **英文**：Architecture Principles  
> 章级精读：[../study.md#ch01-principles](../study.md#ch01-principles)

## 本节核心目标

弄懂互联网最根本的**三个设计思路**，就能理解网络为何如此运转。

---

## 精简研学版

### 1. 分组交换 (Packet Switching)

- 数据拆分为独立**分组**传输，链路**多路复用**，不独占通道。
- 相较**电路交换**：容错性更强；单点链路故障不阻断整体通信。

---

<a id="ch1-e2e"></a>

### 2. 端到端论点 (End-to-End Argument)

复杂业务语义必须在**通信两端系统**完整实现；底层网络仅提供**尽力而为**的基础转发。

| 适合端点实现 | 中间网络局限 |
|--------------|--------------|
| 重传、校验 | 脱离应用场景 |
| 业务安全 | 设备升级成本高 |
| 功能迭代 | 适配性差 |

---

<a id="ch1-fate-sharing"></a>

### 3. 命运共享 (Fate Sharing)

- 连接状态留存于**通信端点**，不托管给中间路由设备。
- 中间节点恢复后，端点可接续通信，不会因网络侧状态丢失而彻底中断。

**易混**：端到端 ≠ 全功能上移应用层；命运共享 ≠ 中间设备永不坏。

---

## 新手易懂版

这一节讲互联网最根本的三个设计思路。

### 一、分组交换

**简单理解**：把大文件拆成一个个**小数据包**来传送。

- **日常类比**：寄大件快递，拆成多个小包裹分开运，不用单独占用整条运输路线。
- **对比电路交换**：打电话那样**独占线路**，线路坏了通话直接断。
- **优势**：一条线路出问题，数据包可以**换路**；线路也能同时供很多人用，网络不容易彻底瘫痪。

### 二、端到端论点

**核心想法**：复杂功能交给**两台通信的电脑/设备**处理；中间路由器、交换机只负责**单纯转发**。

**适合放在两端设备做的事**：数据纠错、重发、加密保密、开发新功能。

**中间网络只做简单转发就好**——若把复杂功能放在沿途设备上：

- 没法贴合不同软件、不同场景的需求
- 更新功能要改全网设备，成本高、麻烦

**补充误区**：不是所有功能都丢给终端；**基础转发**仍由中间网络负责。

### 三、命运共享

**通俗解释**：通信相关的记录信息，保存在**收发两端设备**里，不要只存在中途网络设备上。

- **举例**：两台电脑传文件，中途路由器临时掉线。
- 只要两台电脑本身没崩溃，网络恢复后往往能**接着传**，不必从零重来（具体协议行为因 TCP/应用而异，原则是状态跟端点走）。

### 两个容易搞错的知识点

1. **端到端** ≠ 所有网络功能都要在电脑软件里实现。
2. **命运共享** ≠ 网络设备不会坏；是靠端点留存状态，尽量让通信**不要轻易断干净**。

## 四、部署架构演进：C/S → B/S（与 HTTP/TCP/IP 对齐）

> 书上 **1.1** 讲「互联网宪法」三原则；**C/S、B/S** 是**怎么用**这些原则做业务——和 [1.5 C/S·P2P](./1.5-application-design.md) · [自顶向下 §2.1](../../top_down/02_application_layer/2.1_network_application_principle/study.md#ch2-1) 互补，本节侧重**演进时间线**。

### 人话定义

| | 全称 | 你要装啥 | 例子 |
|---|------|----------|------|
| **C/S** | Client / Server | **专用客户端** | QQ、迅雷、老版财务软件 |
| **B/S** | Browser / Server | **浏览器即可** | 淘宝网页、网课、钉钉网页版 |

### 演进时间线（必背顺序）

```text
① 两层 C/S     客户端 ──────────────► 数据库
   胖客户端：界面+逻辑+连库都在客户端；内网财务/进销存
   问题：每台装软件、升级累；直连库不安全、并发弱

② 三层 C/S     客户端 ──► 应用服务器 ──► 数据库
   逻辑上移到应用层；仍要装专用软件

③ B/S          浏览器 ──► Web服务器 ──► 应用服务器 ──► 数据库
   把「客户端」换成浏览器；业务全在服务器；通信统一 HTTP/HTTPS
```

### 两层 C/S 结构图（胖客户端直连库）

![两层 C/S：客户机 ↔ 数据库服务器（数据请求）](./images/cs-two-tier.png)

- **客户机**：界面 + 业务逻辑 + **直连数据库** 的连接都在本机（**胖客户端**）。
- **服务器**：实质是 **DBMS**（数据库管理系统），主要存数据、执行 SQL。
- **数据请求**：客户端发查询/更新，服务器返回结果——**没有**单独的应用服务器层。
- **典型问题**：升级要逐台装客户端；客户端握有库账号，**安全与并发**都差。

### 三层 C/S（过渡，无独立配图）

```text
客户机（瘦一点）── 数据请求 ──► 应用服务器（业务逻辑）──► 数据库
```

- 业务逻辑从客户端抽到**应用服务器**；客户端仍要安装，但不再直连数据库。
- 仍不如 B/S 省事；现代桌面软件、游戏、部分企业内网仍常见此形态。

**B/S 为何取代大量桌面 C/S：** 免安装 · 只升服务器全网更新 · Win/Mac/手机同源 · 与 **HTTP** 天然一致。

### B/S 结构图（瘦客户端）

![B/S 架构：浏览器 ↔ Web/应用服务器 ↔ 数据库](./images/bs-architecture.png)

- **浏览器**：极瘦——渲染页面、表单输入；**不算**业务权威。
- **Web / 应用服务器**：极厚——业务逻辑、权限、会话；符合 **端到端论点**（复杂语义在端点系统，此处「端点」含服务器进程）。
- **数据库**：持久化；**不**让浏览器直连（两层 C/S 的老毛病）。

### 一句话对比

| | C/S | B/S |
|---|-----|-----|
| 安装/升级 | 要装客户端，逐台升级 | 浏览器即用，升服务器即可 |
| 跨平台 | 差（常绑 Windows） | 好 |
| 性能/复杂 UI | 通常更强 | 复杂交互、大文件略弱 |
| 应用层协议 | 常 **私有协议**（自定义 TCP 端口） | **HTTP/HTTPS** 标配 |

### 和你已学协议栈对齐

```text
B/S 一次网页访问：
浏览器 ── HTTP/HTTPS（应用层）──► Web/应用服务器
         └── TCP ── IP ── 链路层（以太网 / Wi‑Fi / PPPoE 三选一）

老 C/S：
专用客户端 ── 常非 HTTP 的 TCP/UDP ──► 应用服务器
```

| 原则 | 在 B/S 里的体现 |
|------|----------------|
| **端到端** | TLS、重传、业务校验在**浏览器+服务器**两端；路由器只转发 |
| **命运共享** | 会话/TCP 状态在**端点**（浏览器 cookie、服务器 session），不靠中间路由器记业务状态 |
| **分组交换** | 每个 HTTP 响应拆成 IP 分组，多路复用链路 |
