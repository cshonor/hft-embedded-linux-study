6.1

section-6.1-引言

WSC vs 传统数据中心 vs 超算 (HPC)

维度 HPC 超算 WSC 仓储级计算机
首要目标 浮点峰值、紧密耦合通信 交互式服务、海量存储、请求级并行
网络 低延迟专用互连（如 InfiniBand） 高互联网带宽、大规模以太/定制 Clos
故障假设 相对少见，作业检查点 常态 — 磁盘坏、机架挂是日常
可用性 作业级 99.99%+ — 软件冗余容错

WSC 定义直觉： 把 整栋建筑 当成一台计算机 — 软件调度跨数万节点。

规模带来的根本变化

现象 应对
任意时刻都有机器/磁盘在坏 复制、重试、无单点
单请求可能扫上万节点 RLP + 数据分片
平均性能不够 必须盯 尾延迟（→ 6.2、6.8）
HFT 视角
colo 单机/小集群 是 WSC 的反面：极低故障容忍窗口（毫秒级）
但 「故障常态」思维 仍适用：网卡 flapping、进程 crash — 要有冗余路径
别把 搜索/广告级 SLA 和 交易所撮合 SLA 混为一谈
6.2

section-6.2-编程模型与工作负载

MapReduce 与 Hadoop

概念 说明
Map 并行处理数据分片，产生中间键值对
Reduce 按 key 聚合
Hadoop 开源 MapReduce 生态（HDFS 等）

适用： 日志分析、索引构建、大规模 批处理 — DLP + RLP 在集群上展开。

HFT 视角
离线回测、tick 归档回放、风控日终 — MapReduce/Spark 类批处理常见
实盘热路径 — 非 MapReduce；毫秒级单路径

长尾容忍 (Tail Tolerance)

在 数万节点 上，总有个别任务因抖动、竞争、慢盘 极慢。

技术 做法
备份任务 (Backup tasks) 同一 work 启动副本，取先完成者
推测执行 类似 MapReduce straggler mitigation

Google 经验： 慢 1% 可拖累整体用户体验 — WSC 优化 P99/P999，不只是平均。

HFT 视角
对照：WSC 用 冗余计算 换尾延迟；HFT 用 专用硬件、绑核、无共享 换 确定性
回测集群可学 straggler 检测；实盘要避免「等最慢路径」
→ 06.6-Systems-Performance 延迟分解

放宽的一致性 (Relaxed Consistency)

系统 策略
GFS / Colossus 复制 + 宽松一致
Dynamo 最终一致性、可用性优先
vs RDBMS 牺牲严格 ACID 换 可扩展性

CAP 直觉： 分区时常在 一致性 vs 可用性 间权衡。

HFT 视角
订单簿、持仓、风控限额 — 需要 强一致/可序列化 语义（交易所 + 内部 OMS）
行情缓存、参考数据 — 可接受短暂 最终一致
分布式研究数据湖可用 Dynamo 思路；不能 照搬到期货实盘核心账本
6.3

section-6.3-WSC体系结构

网络层次

服务器 → ToR（机架顶交换机）→ 阵列级交换机 → L3 边界路由器 → 互联网
层级 角色
Rack 数十台服务器共享 ToR
Array/Pod 多机架聚合
Cluster/WSC 全设施

Clos / Fat-tree 等拓扑提供 高对分带宽（→ 6.7 Jupiter）。

WSC 的「内存层次」

并非只有 DRAM — 数据放置 决定延迟数量级：

访问 相对延迟（直觉）
本机 DRAM 1×
同机架 略高
跨机架 / 跨阵列 可达本地 DRAM 的 ~1/300 带宽/延迟恶化

软件必须： 分片、本地化、减少跨 rack 聊天。

HFT 视角
colo：策略、行情、发单同机 — 避免跨机 TCP
多机部署时：按品种/通道分片，而非任意 RPC
与 Ch5 NUMA 同构 — 「近」永远赢
行情组播、同 rack 订阅 — 网络拓扑即性能（→ 13-DPDK）
6.4

section-6.4-效率与成本

PUE (Power Usage Effectiveness)

[ \text{PUE} = \frac{\text{设施总能耗}}{\text{IT 设备能耗}} ]

PUE 含义
1.0 理想（无冷却/配电损耗）
>1 典型 1.1–1.5+；冷却（CRAC、冷却塔）、UPS、配电损耗

优化方向： 更高运行温度、蒸发冷却、分布式 UPS（→ 6.7 Google）。

CAPEX vs OPEX

类型 内容
CAPEX 服务器、网络、厂房建设
OPEX 电费、带宽、运维人力

趋势： 生命周期内 供电与冷却摊销 占显著比例 — 能效是 架构决策。

HFT 视角
小型 colo：单机功耗 与 机房制冷 仍重要，但非 Google 级 PUE 优化
电费 vs 延迟：不可用弱 CPU 换电（→ 6.8）— 滑点成本 > 电费
大规模回测农场：OPEX（电 + 云带宽）驱动 用 spot/竞价实例 跑批
6.5

section-6.5-云计算

规模经济

AWS 等 依托 WSC：

优势 量级直觉
存储、带宽、运维摊销 比小规模 DC 便宜约 5–7×
多租户 提高利用率

公用计算回归： 分时共享大型设施，客户按实例付费。

虚拟机 (VM) 的作用

功能 说明
租户隔离 Xen/KVM 等
资源计量 vCPU、内存配额
硬件抽象 底层换代对客户透明
产品线 多档位实例（计算优化、内存优化…）

客户将 过度配置风险 转移给云商；云商用 统计复用 获利。

HFT 视角
研究/回测/CI — 云合适；低延迟实盘 — 裸金属 colo，避免 hypervisor 与多租户噪声
VM 尾延迟 与 CPU steal — 与 WSC 长尾同源（→ 6.2）
云行情数据服务 = WSC 产品；本地 FPGA/NIC 行情 = 反 WSC 思路

→ Ch2 虚拟机

6.6

section-6.6-交叉领域问题

防止网络成为瓶颈

趋势 对策
流量指数增长 商用芯片 定制交换、Clos 拓扑
成本控制 集中式 SDN 式路由控制
对分带宽 多级交换避免 oversubscription 过高

WSC 网络是 第一等公民 — 与计算、存储并列。

能量比例 (Energy Proportionality)

理想： 负载 10% → 功耗 ~10%。

现实 优化
空载仍耗电 CPU DVFS、核心关断
PSU 效率曲线 选用高效电源、合理负载点

与 WSC： 低利用率时仍付 PUE 税 — 驱动 混部批处理 填谷。

HFT 视角
实盘机常 近满载 热核 — 能效曲线在 高负载区 选型
空闲关核（非热核）可省电；热核 宁可满载换延迟稳定
批处理任务调度到 夜间/低峰 — 类比 AWS Spot
6.7

section-6.7-谷歌WSC案例

能效设计

措施 目的
蒸发冷却 利用湿球温度，减 CRAC 依赖
更高运行温度 减冷却能耗
机架级分布式 DC UPS 替代巨型集中 UPS，提高效率

结果： 业界领先 PUE 水平（随代际演进）。

Jupiter 网络

特点 说明
Clos 拓扑 多级交换
高对分带宽 机架间海量东西向流量
容错 路径冗余

支撑 Google 内部 MapReduce、Bigtable、Spanner 等全设施流量。

HFT 视角
Jupiter 优化 TB 级批流 与 全局服务 — 不是 μs 级单播撮合
可借鉴：拓扑规划、无单点；不可照搬：分布式存储做订单簿
定制网络芯片思路与 SmartNIC/DPDK 同属「网络不能成瓶颈」（不同尺度）
6.8

section-6.8-谬误与陷阱

类型 谬误/陷阱 真相
陷阱 只盯 平均 性能 WSC 规模下 慢 1% 拖垮体验 — 必须优化 长尾
陷阱 为省电用 极弱 CPU（早期 Atom） QoS 崩溃 → 收入损失 远大于 电费
谬误 WSC 不用 ECC 省钱 海量内存 → 每日不可纠正错误 → 重启、静默数据损坏（索引腐化）
谬误 空闲关机 提高性价比 监控复杂、寿命损耗；更好是 低谷跑批（MapReduce / Spot）

HFT 对照表

WSC 教训 HFT 应用
盯长尾 实盘 KPI：P99/P999 tick-to-trade，非平均
弱 CPU 省电 colo 选 高主频/大缓存 服务器，电费其次
ECC 必须 实盘主机 ECC RAM — 静默错误破坏持仓/状态
空闲关机器 热路径 常开；非关键批处理 错峰

RLP + 批处理(MapReduce) + 复制容错 + 最终一致 + 分层网络 + PUE/云经济
