# 4.3 · gpiod 深入：属性名怎么拼、ACTIVE_LOW 是什么、Pi 5 引脚怎么数

> **本节讲什么：** 现代 GPIO 接口 gpiod 的三个易错点——**属性名是怎么从 `con_id` 拼出来的**、`gpiod_set_value(1)` 到底输出高还是低、以及 Pi 5 上"引脚号"指的到底是什么。

---

## 一、属性名是拼出来的，不是写死的

驱动侧：

```c
led = devm_gpiod_get(&pdev->dev, "led", GPIOD_OUT_LOW);
```

内核拿 `con_id = "led"` 去拼属性名（v6.6 `drivers/gpio/gpiolib-of.c:96`）：

```c
static const char *const gpio_suffixes[] = { "gpios", "gpio" };

for (i = 0; i < ARRAY_SIZE(gpio_suffixes); i++) {
    if (con_id)
        snprintf(propname, sizeof(propname), "%s-%s", con_id, gpio_suffixes[i]);
    else
        snprintf(propname, sizeof(propname), "%s", gpio_suffixes[i]);
    ...
}
```

所以：

| `gpiod_get(dev, X)` | 依次查找的属性 |
|---|---|
| `gpiod_get(dev, "led")` | `led-gpios` → 找不到再试 `led-gpio` |
| `gpiod_get(dev, NULL)` | `gpios` → `gpio` |
| `gpiod_get_index(dev, "cs", 1)` | `cs-gpios` 的第 2 项 |

**两个实用结论：**

1. **`-gpios`（复数）是标准写法**，`-gpio`（单数）是历史遗留但**仍然被接受**。写 binding 时用复数。
2. **`con_id` 是"功能名"，不是"引脚名"**。叫 `"led"` 而不是 `"gpio17"`——因为驱动只关心"这是个灯"，不关心它接在第几根线上。**引脚号是板级信息，属于 DTS，不属于驱动。** 这条守住了，同一份驱动就能在不同板子上跑。

---

## 二、✦ ACTIVE_LOW：逻辑值 vs 物理电平

这是 gpiod 与传统整数 GPIO 接口**最大的语义差别**，也是最容易出 bug 的地方。

```dts
led-gpios = <&gpio 17 GPIO_ACTIVE_LOW>;    /* 低电平点亮 */
```

```c
gpiod_set_value(led, 1);      /* 逻辑 1 = "开灯" */
```

**`gpiod_set_value()` 写的是逻辑值，不是物理电平。** 内核根据 `GPIO_ACTIVE_LOW` 标志自动翻转：

| DTS 标志 | `gpiod_set_value(d, 1)` 的实际电平 | `gpiod_set_value(d, 0)` 的实际电平 |
|---|---|---|
| `GPIO_ACTIVE_HIGH` | 高 | 低 |
| **`GPIO_ACTIVE_LOW`** | **低** | **高** |

**为什么这个设计是对的：** 硬件接法（共阳还是共阴、三极管是 NPN 还是 PNP）是板级事实，驱动代码不该关心。把极性写进 DTS，驱动里就只有"开/关"的语义，**换一块接法相反的板子，只改 DTS 不改驱动**。

**常见坑：**

```c
gpiod_set_value(led, 1);          /* ✅ 逻辑开 */
gpiod_set_raw(led, 1);            /* ⚠️ 物理高，绕过极性翻转 —— 几乎不该用 */
```

`gpiod_set_raw()` / `gpiod_get_raw()` 会**忽略 ACTIVE_LOW**，只在极少数场景（比如你要精确控制某条线的电气状态做协议位bang）才用。

同理，读的时候：

```c
int val = gpiod_get_value(irq_gpio);   /* 返回逻辑值（已经按极性翻转过） */
```

## 三、sleepable GPIO：挂在 I2C/SPI 扩展芯片上的引脚

不是所有 GPIO 都直接连在 SoC 上。PCA9555 这类 I2C 扩展芯片也提供 GPIO，访问它**要走 I2C 传输，可能睡眠**。

| 场景 | 用哪个 | 说明 |
|------|-------|------|
| SoC 直连 GPIO | `gpiod_get_value()` / `gpiod_set_value()` | 可以在中断上下文 / 持自旋锁时用 |
| 扩展芯片 GPIO | `gpiod_get_value_cansleep()` / `gpiod_set_value_cansleep()` | **可能睡眠**，禁止在原子上下文用 |

**判断依据不是"这是不是 GPIO"，而是"访问它要不要走总线"。** 规则很简单：

> 只要这个函数可能出现在硬中断处理或 spinlock 临界区里，就必须确认用的是非 cansleep 版本，或者用 `gpiod_cansleep(desc)` 在 probe 时检查并拒绝。

```c
if (gpiod_cansleep(desc)) {
    dev_err(dev, "this GPIO sleeps, can't be used in hardirq\n");
    return -EINVAL;
}
```

## 四、用户态：libgpiod（sysfs 已废弃）

`/sys/class/gpio` 已被**移除**（v6.x 主线）。现代方式：

```bash
gpiodetect              # 列出所有 gpiochip
gpioinfo                # 每个 line 的名字、方向、使用者
gpioget  gpiochip0 17   # 读
gpioset  gpiochip0 17=1 # 写
gpiomon  gpiochip0 17   # 等边沿事件（比轮询强得多）
```

**`gpioinfo` 是调试利器**——它会显示每根线的 `consumer` 字段。看到某根线被占用却不知道是谁占的，`gpioinfo` 会告诉你：

```
line  17: "PIN17" unused input active-high
line  18: "PIN18" "my-driver" output active-low [used]
```

如果这里显示 `[used]` 但你的驱动 probe 失败，说明**资源已经被别的驱动抢了**——这类冲突在 dmesg 里往往是 `-EBUSY` 一闪而过。

## 五、Pi 5 引脚：三层编号别搞混

Pi 5 上最容易混淆的是**同一个物理引脚有三个"号码"**：

| 概念 | 例子 | 说明 |
|------|------|------|
| **物理针脚号** | 第 11 脚 | 排针上的物理位置，1–40。**接线用这个** |
| **GPIO 线号** | GPIO 17 | 内核/软件看到的编号。**写代码、写 DTS 用这个** |
| **芯片内 line 号** | 取决于 gpiochip | `gpioinfo` 里显示的 offset |

**Pi 5 的 GPIO 由 RP1（南桥）提供，不是 SoC 直出**——这是它和 Pi 4 的根本差别。RP1 经 PCIe 挂在 BCM2712 下。后果：

1. **GPIO 寄存器基址和 Pi 4 完全不同**，Pi 4 教程里的 `0xFE200000` 直接抄会打到错误地址。
2. **`gpiodetect` 里看到的 chip 名字/编号以你板子的实际输出为准**，不要照抄教程里的 `gpiochip0`。跑一下 `gpiodetect` 和 `gpioinfo` 就有答案。
3. **访问延迟比 Pi 4 高**（多一跳 PCIe）。做 bit-bang 协议（比如软件 I2C、WS2812 灯带时序）时，Pi 5 的时序余量比 Pi 4 差——这类应用建议用硬件控制器或加协处理器。

**权威对照表：`/boot/overlays/README`**（板子上有），以及 `pinout` 命令（树莓派 OS 自带）。第三方引脚图的编号要交叉验证。

## 六、完整例子：DTS + 驱动点灯

```dts
/* 加到某个 overlay 或板级 DTS */
/ {
    myleds {
        compatible = "wzp,myled";
        led-gpios = <&gpio 17 GPIO_ACTIVE_LOW>;
    };
};
```

```c
static int myled_probe(struct platform_device *pdev)
{
    struct gpio_desc *led;

    led = devm_gpiod_get(&pdev->dev, "led", GPIOD_OUT_LOW);
    if (IS_ERR(led))
        return dev_err_probe(&pdev->dev, PTR_ERR(led), "get led gpio");

    gpiod_set_value(led, 1);        /* 逻辑开 → 因 ACTIVE_LOW 实际输出低电平 */
    return 0;
}

static const struct of_device_id myled_of_match[] = {
    { .compatible = "wzp,myled" }, { }
};
MODULE_DEVICE_TABLE(of, myled_of_match);
```

**注意 `devm_gpiod_get` 的第三个参数**：`GPIOD_OUT_LOW` 表示"申请并初始化为逻辑 0 输出"。其它选项：`GPIOD_OUT_HIGH`、`GPIOD_IN`、`GPIOD_ASIS`（不改状态）。**`GPIOD_ASIS` 有风险**——引脚可能保持在上电时的不确定电平，导致上电瞬间灯闪一下或继电器误动作。

## HFT / 嵌入式关联

- **"功能名 vs 引脚号"的分层，就是配置与代码分离。** 驱动说"我要一个叫 led 的 GPIO"，DTS 说"led 接在 GPIO17、低电平有效"。换板子不动驱动——这个模式和 HFT 里"策略代码读配置、不硬编码合约代码"是一回事。
- **ACTIVE_LOW 的自动翻转消除了整类 bug。** 老式整数接口里"开灯写 0 还是写 1"要靠注释和脑记，改硬件就改代码。gpiod 把它变成数据，这是**把易变的硬件事实从代码挪到数据**的典型收益。
- **cansleep 的存在提醒一件事：抽象可能泄漏。** 同样是 `gpiod_set_value`，走 SoC 直连是几条指令，走 I2C 扩展器是毫秒级总线事务。**接口相同，代价差三个数量级**——在延迟敏感路径上，这个差异会咬人。

5. Pi 5 上"第 11 脚"、"GPIO 17"、寄存器基址，这三者分别是什么？Pi 4 的 GPIO 基址能直接用到 Pi 5 上吗？
6. `GPIOD_ASIS` 有什么风险？

<details>
<summary>参考答案</summary>

1. 标准写 **`reset-gpios`**。写成 `reset-gpio`（单数）**能用**——内核会依次尝试 `gpio_suffixes[] = {"gpios", "gpio"}` 两个后缀。但新 binding 应该用复数标准形式。

2. 输出**低电平**。`gpiod_set_value()` 写的是**逻辑值**，内核按 `GPIO_ACTIVE_LOW` 自动翻转。想强制物理高电平用 `gpiod_set_raw(d, 1)`（绕过极性翻转），但几乎不该这么用——极性问题应该在 DTS 里修，不该在代码里绕过。

3. 看 GPIO 是否挂在 I2C/SPI 扩展芯片上：SoC 直连用普通版（可在中断上下文/自旋锁内调用）；扩展芯片用 `cansleep` 版（访问要走总线，可能睡眠）。**选错用普通版访问 sleeping GPIO，会在原子上下文中睡眠 → 内核 oops。** 可在 probe 里用 `gpiod_cansleep(desc)` 检查并拒绝。

4. `gpioinfo`（libgpiod 工具集）。它会列出每根线的 `consumer` 字段，显示占用者名字。若显示 `[used]` 而你的驱动拿不到，说明被别的驱动抢了（通常 dmesg 里有 `-EBUSY`）。

5. "第 11 脚"是**排针物理位置**（接线用）；"GPIO 17"是**内核线号**（写代码/写 DTS 用）；寄存器基址是 SoC/RP1 的内存映射地址。**Pi 4 的基址不能用到 Pi 5 上**——Pi 5 的 GPIO 由 RP1 南桥提供（经 PCIe 挂载），与 Pi 4 的 SoC 直出完全不同。另外 `gpiochip` 编号也以 `gpiodetect` 实测为准。

6. `GPIOD_ASIS` 表示**不修改引脚当前状态**，引脚可能保持在上电/引导阶段的 indeterminate 电平。对 LED 是上电闪一下，对继电器/电机驱动可能是**上电瞬间误动作**。显式用 `GPIOD_OUT_LOW`/`GPIOD_OUT_HIGH` 指定初始状态。

</details>
