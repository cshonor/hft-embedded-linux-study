# 4.5 · SPI：全双工的本质与四种模式

> **本节讲什么：** SPI 和 I2C 的根本差别不是"快"，而是**全双工、无寻址、靠片选选设备**——这三点决定了它的 API 长什么样，也决定了最常见的两个坑：**读数据必须发 dummy 字节**、**`spi_sync` 不能在中断里调用**。

---

## SPI vs I2C：结构差异决定一切

| | I2C | SPI |
|---|---|---|
| 信号线 | 2（SDA + SCL） | 4（SCLK + MOSI + MISO + CS），每加一个从设备多一根 CS |
| 寻址 | **7 位地址**（协议里带地址字节） | **无地址**——靠**片选线**选中 |
| 方向 | 半双工（同一时刻只能发或收） | **全双工**（发的同时必然也在收） |
| 速率 | 100k – 3.4M bps | 通常 10M – 50M+ bps（受布线限制） |
| 流控/应答 | 有 ACK/NACK | **无应答**——主设备不知道从设备是否存在 |
| 多主 | 支持 | 不支持 |

**"无寻址"的后果：** SPI 从设备的身份完全由**硬件连线（CS 线）**决定，DTS 里的 `reg` 表示**用的是第几根片选**，不是设备地址：

```dts
&spi0 {
    adc@0 {                      /* @0 = chip select 0 */
        compatible = "wzp,my-adc";
        reg = <0>;               /* ★ 片选编号，不是设备地址！ */
        spi-max-frequency = <10000000>;
    };
};
```

这和 I2C 的 `reg = <0x48>`（设备地址）**含义完全不同**，是跨总线时最常搞混的一点。

---

## 全双工：没有"读"，只有"交换"

SPI 硬件上根本没有"只读"这个操作。**主设备每送出一位，就必然同时收到一位**（移位寄存器环回）。

所以"读寄存器"实际是：

```
主机发：  [0x80][0x00][0x00]     ← 命令字 + 两个 dummy 字节
主机收：  [0xXX][0xAA][0xBB]     ← 第一个字节是无效数据，后两个才是真数据
```

```c
/* 读 2 字节：要发 1 命令 + 2 dummy，总共 3 字节 */
u8 tx[3] = { 0x80 | REG_DATA, 0x00, 0x00 };
u8 rx[3];

spi_write_then_read(spi, tx, 1, rx, 2);   /* 便捷封装：发 1 字节，再收 2 字节 */
```

**⭐ 最常见的 bug：** 以为"读 N 字节就传 N 字节"。真实需要的是 `1 + N`（命令 + N 个 dummy），而且**收到的前 1 个字节永远是垃圾**（从设备还没准备好数据）。

对比 I2C：`i2c_smbus_read_byte_data()` 内部帮你处理了"发地址→重复起始→读数据"的复杂时序，你只看到"读一个寄存器"。**SPI 没有这层抽象，时序得自己数。**

---

## 四种模式：CPOL 和 CPHA

```
CPOL (Clock Polarity)  = 空闲时 SCLK 是高还是低
CPHA (Clock Phase)     = 数据在第几个边沿采样
```

| mode | CPOL | CPHA | 空闲电平 | 采样边沿 |
|------|------|------|---------|---------|
| 0 | 0 | 0 | 低 | 上升沿 |
| 1 | 0 | 1 | 低 | 下降沿 |
| 2 | 1 | 0 | 高 | 下降沿 |
| 3 | 1 | 1 | 高 | 上升沿 |

**绝大多数芯片用 mode 0 或 mode 3。** DTS 里指定：

```dts
spi-cpol;              /* CPOL=1 */
spi-cpha;              /* CPHA=1 */
/* 两个都不写 = mode 0；两个都写 = mode 3 */
```

**模式配错的症状很有特征：** 数据能收到，但**每一位都偏移或反转**——比如读 ID 期望 `0xEA` 却得到 `0xD5`。看到这种"看起来差一点"的错误，第一嫌疑就是 SPI 模式，不是接线。

## 传输 API 三层

```c
/* ① 最便捷：一次"写然后读"，内部拆成两个 transfer */
spi_write_then_read(spi, txbuf, n_tx, rxbuf, n_rx);

/* ② 单传输：全双工交换 n 字节 */
spi_write_then_read 不够用时：
struct spi_transfer t = {
    .tx_buf = tx,
    .rx_buf = rx,
    .len    = len,
    .speed_hz = 1000000,       /* 这次传输临时降速 */
};
spi_sync_transfer(spi, &t, 1);

/* ③ 完整控制：spi_message + 多个 transfer（保持 CS 连续选中） */
struct spi_message m;
spi_message_init(&m);
spi_message_add_tail(&t1, &m);
spi_message_add_tail(&t2, &m);
spi_sync(spi, &m);
```

**为什么需要 message（第③层）：** 有些器件要求"CS 拉低 → 发命令 → 发地址 → 读数据 → CS 拉高"，中间**不能释放片选**。用两个独立的 `spi_write_then_read` 会在中间把 CS 拉高，器件状态机就复位了。**message 保证一组 transfer 期间 CS 连续有效。**

## ⚠️ spi_sync 会睡眠，中断里不能用

| 函数 | 能否在中断上下文 |
|---|---|
| `spi_sync()` / `spi_sync_transfer()` / `spi_write_then_read()` | ❌ **会睡眠**（等待 completion） |
| `spi_async()` | ✅ 不等待，但完成回调在**非原子上下文** |

**和 I2C 一样的问题，但更常踩**——因为 SPI 常用于高速数据采集，"数据准备好了"中断触发后想立刻读是自然反应，而这在硬中断里是做不了的（见 [05 · 中断上下文](../05-irq-locking/5.1-irq-context.md)）。

正确做法：

```
硬中断（快速应答、清中断）  →  调度下半部
                                  ↓
                    线程化中断 / workqueue  ← 在这里 spi_sync 读数据
```

## 驱动骨架

```c
static int my_probe(struct spi_device *spi)
{
    int ret;
    u8 id;

    /* 从 spi_device 拿参数（都来自 DTS，不要硬编码） */
    dev_info(&spi->dev, "mode=%d max_speed=%u cs=%d bpw=%d\n",
             spi->mode, spi->max_speed_hz, spi->chip_select,
             spi->bits_per_word);

    ret = spi_write_then_read(spi, (u8[]){0x00}, 1, &id, 1);
    if (ret < 0)
        return dev_err_probe(&spi->dev, ret, "read id");

    if (id != EXPECTED_ID)
        return dev_err_probe(&spi->dev, -ENODEV, "bad id 0x%02x", id);

    return 0;
}

static const struct of_device_id my_of_match[] = {
    { .compatible = "wzp,my-adc" }, { }
};
MODULE_DEVICE_TABLE(of, my_of_match);

static struct spi_driver my_driver = {
    .driver = { .name = "my-adc", .of_match_table = my_of_match },
    .probe = my_probe,
};
module_spi_driver(my_driver);
```

**配置从 DTS 来，驱动不写死速率/模式**——同一颗芯片在不同板子上布线不同，能跑的最高频率也不同，这是板级事实。

## 调试

```bash
# 用户态先验证硬件（无需驱动）
ls /dev/spidev*                      # 需启用 spidev（调试用，产品别开）
# 用 spidev_test 工具（内核源码 tools/spi/）
spidev_test -D /dev/spidev0.0 -s 1000000 -p "\x00"

# 内核侧
cat /sys/bus/spi/devices/spi0.0/modalias
ls /sys/bus/spi/drivers/

# ★ 最有效：逻辑分析仪 / 示波器看四根线
```

**SPI 必须看波形。** I2C 有 ACK 可以确认设备存在，SPI **没有应答机制**——主设备发完了就完了，从设备在不在它不知道。所以"读回来全是 0xFF 或全是 0x00"时，无法从软件层面区分"没接设备"、"CS 线没接对"、"模式错"这三种情况。**四根线的波形看一眼就有结论，比读代码快十倍。**

## HFT / 嵌入式关联

- **`spi_sync` 不能进中断这条规则，在高频采样场景是架构约束**：IMU/高速 ADC 的数据就绪中断频率可达数十 kHz，中断里做不了总线传输，只能"中断里打时间戳 + 下半部搬数据"。这个"上半部只做最少量工作"的模式，和 HFT 里网卡中断只负责 NAPI 调度、实际收包在软中断/轮询线程里做，**是同一个设计范式**。
- **大数据量必然走向 DMA**：`spi_transfer` 可以设 `tx_dma`/`rx_dma`，让控制器直接搬内存，见 [06 · DMA 与 mmap](../06-dma-mmap/6.1-dma-fundamentals.md)。CPU 逐字节 SPI 的开销在 MHz 级采样下不可接受。
- **无应答是 SPI 的可靠性软肋**：工业场景要么靠周期性读 ID 寄存器做"心跳"，要么加 CRC。这和交易系统里"链路层没有确认就必须自己做应用层心跳"是同一条经验——**别指望底层替你保证可靠性**。

1. SPI DTS 里的 `reg = <0>` 是什么意思？和 I2C 的 `reg = <0x48>` 有什么本质区别？
2. 为什么 SPI "读 N 字节"实际要传 N+1 字节？收到的第一个字节是什么？
3. CPOL 和 CPHA 各决定什么？mode 0 和 mode 3 分别是什么组合？
4. 数据能收到但每一位都偏移/反转，最可能是什么原因？
5. 什么情况下必须用 `spi_message` 而不是多次 `spi_sync_transfer`？
6. 传感器数据就绪中断里想读 SPI，为什么不行？正确做法是什么？

<details>
<summary>参考答案</summary>

1. SPI 的 `reg = <0>` 是**片选编号**（用第几根 CS 线），因为 SPI **协议里没有地址概念**，设备身份由硬件连线决定。I2C 的 `reg = <0x48>` 是**7 位从机地址**，写在协议的地址字节里。这是跨总线移植时最容易搞混的一点。

2. SPI 是**全双工**：主设备发第一位的同时就收到第一位，没有"只收不发"的操作。所以读 N 字节需要先发命令字节，再发 N 个 dummy 字节来"换"回数据，总共 N+1（或 1+N）。**收到的第一个字节是从设备还在解析命令时返回的，永远是无效数据**，必须从偏移 1 开始取。

3. **CPOL** 决定 SCLK 空闲时的电平（0=低，1=高）；**CPHA** 决定在第几个时钟边沿采样数据（0=第一个边沿，1=第二个边沿）。组合成 4 种模式：mode 0 = CPOL0/CPHA0，mode 3 = CPOL1/CPHA1。多数芯片用 0 或 3。

4. **SPI 模式（CPOL/CPHA）配错。** 特征就是"能收到数据但看起来差一点"——位偏移、字节值像被移位。此时接线是通的，改 `spi-cpol`/`spi-cpha` 即可，不要去查接线。

5. 当**多个 transfer 之间不能释放片选（CS）**时。某些器件要求"CS 拉低 → 命令 → 地址 → 读数据 → CS 拉高"是一个连续事务，中间 CS 一抬器件状态机就复位。多次 `spi_sync_transfer` 会在每次传输后释放 CS；`spi_message` 把多个 transfer 串成一个原子事务，期间 CS 保持有效。

6. **`spi_sync()` 会睡眠**（内部等 completion），硬中断上下文不允许睡眠，会导致内核 oops。正确做法：硬中断里只做最必要的工作（清中断、记录时间戳），然后调度下半部——在**线程化中断或 workqueue** 里调用 `spi_sync` 读数据。

</details>
</details>
