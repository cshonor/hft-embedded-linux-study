导读

本节讲什么： 现代 ARM Linux 驱动的主干——硬件信息从设备树来，驱动通过 compatible 匹配，资源全部从 DT 解析，基址不硬编码。 对应动手： P5 · C3（platform + probe，资源全从 DT 解析，无硬编码基址，对照 RP1 / 板级 DTS）

为什么是核心

SoC 上的外设没有总线可以枚举（不像 PCIe 能扫出来）。所以内核必须靠一张"硬件清单"来知道有什么设备——这张清单就是设备树。

DTS（人写） --dtc--> DTB（二进制） --> bootloader 传给内核
                                            ↓
                                  展开为 device_node 树
                                            ↓
                       platform_bus 按 compatible 匹配 driver
                                            ↓
                                      driver->probe()

DTS 节点长什么样

mydev@fe200000 {
    compatible = "wzp,my-device";     /* 匹配的钥匙 */
    reg = <0x0 0xfe200000 0x0 0x1000>;   /* 地址 + 长度 */
    interrupts = <GIC_SPI 32 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&clk_peri>;              /* phandle 引用别的节点 */
    status = "okay";
};

驱动侧：

static const struct of_device_id my_of_match[] = {
    { .compatible = "wzp,my-device" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, my_of_match);

static int my_probe(struct platform_device *pdev)
{
    struct resource *res;
    void __iomem *base;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    base = devm_ioremap_resource(&pdev->dev, res);   /* devm_ 自动回收 */
    /* 寄存器读写：readl(base + REG_X) / writel(v, base + REG_X) */
    return 0;
}

关键： 用 devm_* 系列（devm_ioremap_resource、devm_kzalloc、devm_request_irq），出错路径不用手写 unwind，remove 时自动释放。

ACPI x86 世界

3.1

新增外设：DTS 必改，驱动分三档

FAQ · 锚定 Primer Ch7（DTB）· Ch8（驱动入门）· 09 驱动·DT
相关：UEFI ≈ U-Boot · ACPI ≈ DTB · BSP 模板

核心结论（两层分开）

  1. 板子新加硬件 → 几乎 100% 要改/增 DTS 节点（启用片内模块则常是改 status，见下）。
  2. 不等于一定要从零写驱动 — 有现成驱动就只配 DTS；要适配就改几行；没有才写完整驱动。

一、为什么必须动设备树？

内核靠 DTB 里的信息认硬件：compatible、reg（物理基址）、中断、供电、时钟、复位等。

U-Boot 负责 DDR/Flash 等上电初始化，不会把「你焊了什么外设」完整交给内核；启动后内核的主硬件清单来源就是 DTB（现代 ARM 嵌入式主路径）。

例：GPIO 按键

  • 硬件：键接 GPIO ↔ GND
  • DTS：加 gpio-keys（或等价）节点 — GPIO、键名、触发电平
  • 驱动：内核 gpio_keys 等通用驱动 → 可零行自写驱动，只写 DTS

例：板外独立 GPU / 显示控制器（非 SoC 内置）

  • DTS：compatible、reg、电源、时钟、复位、总线（PCIe/I2C…）
  • 驱动：
  • 内核已有 → 只 DTS
  • 冷门/自研 → DTS + 完整平台/字符驱动（Ch8 入门 → 12 深挖）

二、三档工作量

场景 DTS 驱动
1. 内核已有标准驱动（LED、gpio-keys、常见 I2C 传感器、多数屏/PHY/UART…） 必写节点：compatible / reg / interrupts / clocks / regulator / reset… 不写；编 DTB、替换启动用的 dtb
2. 有通用驱动，参数略不同（同系列屏分辨率/时序等） 必写接线 少量改驱动或用 DT 属性吃参数，不从头造
3. 无现成驱动（自研采集、冷门芯片） 先建节点写地址/中断/电源 完整开发；驱动从 DT 读资源再做读写/IRQ

操作骨架（场景 1）：改 .dts → 出新 .dtb → boot 加载新 DTB（多数情况 不必 重编 U-Boot，见下）。

为何场景 1 这么多： 标准协议 + 厂商合入主线/BSP — 8.4。

三、片内模块 vs 外挂器件

类型 DTS 常见动作
SoC 片上（内置 UART/ETH MAC/内置 GPU…） 原厂 dtsi/dts 已有节点；多用 status = "okay" / "disabled"，不必从零「发明」节点
板外新挂（按键、外置 GPU、I2C 模组、外接 Flash…） 评估板 dts 没有 → 新增完整节点

四、和 U-Boot 的联动（承接 DT FAQ）

你加的东西 U-Boot
普通外设：按键、传感器、屏（内核阶段才用） 通常只改 DTS，不重编 U-Boot
影响启动期：DDR、NAND/启动介质、U-Boot 就要用的 PHY/串口时序 还要改 U-Boot — 7.0 场景 B

五、一句话

多焊硬件 → DTS 必动；写驱动看内核有没有货。
有货只配树；没货先写树再写驱动。

深入：Madieu platform + DT → 12；绑定细节 → 8.1；本书 Ch8 仅入门，勿当主教材（见 OUTLINE）。

3.2

设备树与驱动：分工、compatible、probe、启动链路

完整关系拆解 · Primer Ch7（DTB）+ Ch8（驱动入门）· 深挖 12
相关：加外设三档 · UEFI ≈ U-Boot · ACPI ≈ DTB

一、定位：配置表 vs 操作代码

设备树（DTS→DTB） 驱动
本质 静态数据，无可执行逻辑 C 代码：读写寄存器、IRQ、协议、业务
内容 地址、中断、时钟、电源、复位、compatible、拓扑、板级参数 初始化、收发、ISR、/dev / sysfs
目的 接线/资源与驱动解耦 — 换板多半只改树 真正操作外设

比喻： 驱动 = 电器说明书；设备树 = 插座分布图（位置、电压）。换插座位置改图即可，不必重写说明书。

二、绑定钥匙：compatible

  1. DTS 节点：compatible = "vendor,part"（可多字符串，按优先匹配）
    例：compatible = "fsl,imx6ul-uart";
  2. 驱动：of_match_table 注册相同字符串，挂到 platform_driver（或同类）上：
static const struct of_device_id uart_of_match[] = {
    { .compatible = "fsl,imx6ul-uart" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, uart_of_match);

static struct platform_driver uart_drv = {
    .probe = uart_probe,
    .driver = {
        .name = "imx6-uart",
        .of_match_table = uart_of_match,
    },
};
  1. 内核：解析 DTB → 对每个节点的 compatible 在已注册驱动里找匹配 → 命中则调 probe()。

probe = 驱动读树、申请资源、初始化硬件的入口。

三、probe 里怎么读树（of_*）

API（示意） 用途
of_address_to_resource / platform_get_resource reg → 物理/IO 资源
of_irq_get / platform_get_irq 中断号
of_clk_get 时钟
of_property_read_u32 等 自定义属性（分辨率、速率…）
of_get_named_gpio / gpiod 族 GPIO

例：只加按键（不改驱动）

gpio_keys {
    compatible = "gpio-keys";
    key1 {
        gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
        label = "user_btn";
    };
};

内核自带 gpio-keys 驱动匹配 "gpio-keys" → probe → of_* 读 GPIO/标签 → 申请中断、上报按键。
全程只改 DTS（场景见 8.0）。

四、分工边界

设备树只填数据（不做操作）

  • MMIO 基址、IRQ、时钟、供电、复位
  • 总线拓扑（I2C 下挂哪些从设备）
  • 板级参数（屏时序、波特率、分区大小）
  • status = "okay" / "disabled"

驱动只写逻辑（不把板级地址写死）

  • 寄存器/中断/上下电与初始化
  • 协议与数据路径
  • 用户态接口（/dev、sysfs、net…）

解耦收益： 同驱动多板复用，改地址/引脚改树即可。
无 DT 的老做法：地址硬编码在 .c → 换板改驱动重编。

五、新增硬件时的联动（摘要）

场景 DTS 驱动
内核已有标准驱动 增/改节点 不写
无驱动 先建节点（含 compatible） 写 of_match_table + probe + of_*

片内模块：原厂节点多已在，常只改 status。
板外新芯片：常需新建完整节点；无驱动再开发。详表 → 8.0。

六、启动交互链路（极简）

U-Boot 加载 DTB → 交给内核
    → 内核展开设备节点
    → compatible ↔ of_match_table
    → probe()
    → of_* 取资源 → 初始化硬件 → 暴露 /dev 等

U-Boot 不替代 DTB 当「完整外设清单」；它负责启动期硬件初始化并把 DTB 指针交给内核（7.0）。

七、一句话

DT = 静态资源清单；驱动 = 操作逻辑。
靠 compatible 绑在一起，靠 of_* 在 probe 里读树 — 板级移植成本主要落在改树上，而不是改遍驱动源码。

实操主线：12 Madieu · Platform + DTS；本书 Ch8 仅概念预告。

3.3

· DTB 的一生：从 DTS 到 platform_device

本节讲什么： 一个 .dts 文本文件，怎么变成内核里一颗 device_node 树，又怎么变成 platform_device 触发你的 probe()。以及板子上到底跑的是哪个 DTB——这个问题必须先有答案，否则改半天改的不是在跑的那棵树。

完整链路

   arch/arm64/boot/dts/.../bcm2712-rpi-5-b.dts    ← 人写的文本
                  │  dtc（设备树编译器）
                  ▼
   bcm2712-rpi-5-b.dtb                            ← 二进制 blob（扁平化 = FDT）
                  │  固件/ bootloader 加载到内存
                  │  启动内核时把 DTB 物理地址放进寄存器（arm64: x0）
                  ▼
   setup_arch() → unflatten_device_tree()          ← 展开成 device_node 树
                  ▼
   of_platform_populate()                          ← 扫树，建 platform_device
                  ▼
   platform_bus 匹配 → driver->probe()

关键认知： DTB 是扁平化的（Flattened Device Tree，所以叫 FDT）——它是线性的字节流，不是树形结构。内核启动时把它"展开"（unflatten）成内存里的树。这个名字本身就解释了为什么改 DTS 必须重新编译：内核不认识文本。

第二步最容易踩：不是所有节点都会变成 device

of_platform_populate() 递归扫树（drivers/of/platform.c），但有三道闸门：

闸门 源码位置 后果
!of_device_is_available(np) of_platform_device_create_pdata status 不是 okay/ok → 跳过
strict && !compatible of_platform_bus_create 没有 compatible 属性 → 跳过
!of_match_node(matches, bus) of_platform_bus_create 末尾 父节点不在总线表里 → 不递归子节点

第三道是最阴的。看这段（v6.6 drivers/of/platform.c:418）：

dev = of_platform_device_create_pdata(bus, bus_id, platform_data, parent);
if (!dev || !of_match_node(matches, bus))
    return 0;                    /* ← 不递归！子节点全不建 */

for_each_child_of_node(bus, child) {
    rc = of_platform_bus_create(child, matches, lookup, &dev->dev, strict);
    ...
}

也就是说：你的节点挂在某个父节点下，如果父节点的 compatible 不在 of_default_bus_match_table 里，你这个子节点根本不会被创建成 device，probe 永远不调用，且没有任何报错。

status 的判定也很直白（v6.6 drivers/of/base.c:426）：

status = __of_get_property(device, "status", &statlen);
if (status == NULL)
    return true;                 /* 没写 status == 默认可用 */
if (statlen > 0) {
    if (!strcmp(status, "okay") || !strcmp(status, "ok"))
        return true;
}
return false;                    /* 其它一律不可用，包括 "disabled"、"fail-*" */

注意两件事：不写 status 等于 okay（不是等于 disabled）；写错成 ok 以外的任何值（比如 enable、OKAY）都算不可用——大小写敏感。

命名规则：为什么是 fe200000.gpio 这种怪名字

of_device_make_bus_id()（drivers/of/platform.c:108）拼的名字：

reg = of_get_property(node, "reg", NULL);
if (reg && (addr = of_translate_address(node, reg)) != OF_BAD_ADDR) {
    dev_set_name(dev, "%llx.%pOFn", addr, node);   /* 地址.节点名 */
    return;
}
/* 地址翻译不了 → 往上找父节点，用 kbasename(full_name) 拼前缀 */
dev_set_name(dev, "%s:%s", kbasename(node->full_name), dev_name(dev));

所以 /sys/bus/platform/devices/ 里看到的 107d001000.serial = 物理地址 0x107d001000 + 节点名 serial。地址前缀来自 reg 的翻译结果，这也是为什么同名节点不会撞车。

第三步：运行时怎么查"现在跑的是哪棵树"

路径 是什么
/sys/firmware/devicetree/base/ 真正的运行时视图（device_node 树导出）
/proc/device-tree 指向上面的符号链接（兼容老习惯）

三板斧

① 看节点在不在、compatible 对不对

ls /proc/device-tree/
cat /proc/device-tree/mydev@fe200000/compatible

compatible 是字符串列表（多个串以 \0 分隔），直接 cat 会粘成一行。正确读法：

tr '\0' '\n' < /proc/device-tree/mydev@fe200000/compatible
# 输出：
# wzp,my-device
# generic-fallback-name

② 反编译整棵树

dtc -I fs -O dts /proc/device-tree > /tmp/running.dts

-I fs = 输入格式是文件系统（sysfs 视图）。这样得到的就是内核实际看到的那棵树，包含固件动态填充的（内存大小、MAC 地址等）——和你 .dts 源文件不一定一样。

③ 反编译磁盘上的 DTB 文件

dtc -I dtb -O dts /boot/bcm2712-rpi-5-b.dtb -o /tmp/disk.dts
diff /tmp/running.dts /tmp/disk.dts      # 差异就是固件改过的地方

这个 diff 是 Pi 上最有诊断价值的一步。 固件会按 config.txt 注入 overlay、改 status、填 MAC，你看到的运行树是"DTS 源文件 + 固件补丁"的合成结果。

Pi 5 的特殊性

/config.txt
    ├── 决定用哪个 dtb：      device_tree=bcm2712-rpi-5-b.dtb（通常自动选）
    ├── overlay：             dtoverlay=xxx          ← 按顺序叠加，后面的覆盖前面的
    └── 参数：                dtparam=i2c_arm=on     ← 本质是改 status

overlay 的顺序影响最终结果，两个 overlay 改同一个属性的话后加载的赢。Pi 官方 README（/boot/overlays/README）是所有 dtoverlay 的权威文档。

⚠️ Pi 5 的外设走 RP1（南桥，经 PCIe 挂），引脚叙事和 Pi 4 完全不同。网上大量 Pi 4 教程直接抄到 Pi 5 上会失败，尤其是 GPIO 基址和 pinctrl 部分。查资料认准 bcm2712 / RP1 关键字。

HFT / 嵌入式关联

  • "跑的是哪棵树"永远是调试第一问。 驱动不 probe 的排查顺序：节点存在吗 → status 是 okay 吗 → compatible 逐字符对吗 → 父节点被递归到了吗 → 驱动模块加载了吗。前三步全在 /proc/device-tree 里能验完，不需要重新编译任何东西。
  • overlay 是产品化的标准手段：同一份内核镜像，靠 config.txt 适配不同硬件配置。这和 HFT 里"一份二进制 + 不同配置文件适配不同交易所网关"是同一个思路——把差异从代码里挪到数据里。
  • status = "disabled" 是做 A/B 硬件验证的廉价手段：不用改驱动，改一行 DTS 就能让某设备消失，用来定位"到底是哪个设备在抢资源"。

参考答案
  1. 不写 status = 可用（of_device_is_available 在 status 为 NULL 时返回 true）。写 OKAY = 不可用，判定只认小写 okay 和 ok，大小写敏感。
  2. 父节点不在 of_default_bus_match_table 里，导致你的节点所在的子树压根没被递归创建。源码在 of_platform_bus_create 末尾的 return 0——父节点自己建了 device，但子节点不递归。这类问题在 /proc/device-tree 里看不出来（树还在），只有 /sys/bus/platform/devices/ 里找不到对应 device 才暴露。
  3. tr '\0' '\n' < /proc/device-tree/<node>/compatible。因为 compatible 是多字符串属性，内部以 \0 分隔，直接 cat 会把多个串粘在一起且看不到分隔。
  4. 固件（Pi 上是 GPU 侧的 start.elf / config.txt）在加载 DTB 后会动态修改：启停 overlay、按 dtparam 改 status、填入实际的内存大小 / MAC 地址 / 序列号。所以磁盘 DTB 是"静态源"，运行时树是"源 + 固件补丁"。
  5. -I fs 表示输入格式是文件系统（filesystem），即 sysfs 导出的目录树形式（/proc/device-tree 或 /sys/firmware/devicetree/base），而不是 -I dtb（二进制）或 -I dts（文本）。
3.4

· compatible 匹配与 probe：为什么"没报错"才是最难查的

本节讲什么： compatible 是怎么被匹配的、匹配成功后 probe 走哪条路、以及为什么驱动没 probe 时 dmesg 里常常什么都看不到——答案在内核源码的日志级别选择里。

匹配不是"相等比较"，是四级回退

v6.6 drivers/base/platform.c:1335：

static int platform_match(struct device *dev, struct device_driver *drv)
{
    /* When driver_override is set, only bind to the matching driver */
    if (pdev->driver_override)
        return !strcmp(pdev->driver_override, drv->name);

    /* Attempt an OF style match first */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* Then try ACPI style match */
    if (acpi_driver_match_device(dev, drv))
        return 1;

    /* Then try to match against the id table */
    if (pdrv->id_table)
        return platform_match_id(pdrv->id_table, pdev) != NULL;

    /* fall-back to driver name match */
    return (strcmp(pdev->name, drv->name) == 0);
}
优先级 机制 说明
1 driver_override 用户通过 sysfs 强制指定，一票否决（设了就只认这个名字）
2 OF（设备树） of_match_table 里的 compatible —— 现代 ARM 走这条
3 ACPI x86 世界
4 id_table 无设备树的平台驱动
5 驱动名 == 设备名 老式兜底

调试价值： 想临时把一个设备绑给另一个驱动，不用重编内核：

echo my_driver > /sys/bus/platform/devices/fe200000.gpio/driver_override
echo fe200000.gpio > /sys/bus/platform/drivers/my_driver/bind

driver_override 是优先级最高的那一级，写进去就压过 compatible。

compatible 的匹配是"最具体优先"：of_driver_match_device 会遍历驱动的 of_match_table，逐个比对设备节点的 compatible 列表，命中第一个就返回。所以 DTS 里写 compatible = "wzp,my-device", "generic-foo" 时，内核会先看有没有驱动认 wzp,my-device，没有再退化看 generic-foo——这是硬件兼容性的兜底机制。

MODULE_DEVICE_TABLE 到底是干什么的

static const struct of_device_id my_of_match[] = {
    { .compatible = "wzp,my-device" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, my_of_match);

它不是给内核匹配用的（匹配用的是 of_match_table 指针）。它的作用是：编译期把这张表放进 ELF 的 __mod_of_device_table 段，depmod 扫到后生成 modules.alias：

alias of:N*T*Cwzp,my-device* my_device

于是 udev/modprobe 能在设备出现时自动加载对应模块。

少了它的症状很有迷惑性： 手动 insmod 一切正常（表在内存里，匹配照常），但重启后驱动不会自动加载。所以：

不用 MODULE_DEVICE_TABLE = 每次开机手动 insmod。功能"能跑"，自动化链路断了。

验证：

modinfo my_device.ko | grep alias
# alias:          of:N*T*Cwzp,my-device

★ 核心：probe 失败为什么常常"静默"

v6.6 drivers/base/dd.c:572：

static int call_driver_probe(struct device *dev, struct device_driver *drv)
{
    if (dev->bus->probe)
        ret = dev->bus->probe(dev);
    else if (drv->probe)
        ret = drv->probe(dev);

    switch (ret) {
    case 0:
        break;
    case -EPROBE_DEFER:
        /* Driver requested deferred probing */
        dev_dbg(dev, "Driver %s requests probe deferral\n", drv->name);
        break;
    case -ENODEV:
    case -ENXIO:
        pr_debug("%s: probe of %s rejects match %d\n",
             drv->name, dev_name(dev), ret);
        break;
    default:
        /* driver matched but the probe failed */
        pr_warn("%s: probe of %s failed with error %d\n",
            drv->name, dev_name(dev), ret);
        break;
    }
    return ret;
}

这张表值得背下来：

probe 返回值 内核怎么记 默认 dmesg 能看到吗
0 无 —
-EPROBE_DEFER dev_dbg ❌ 看不到
-ENODEV / -ENXIO pr_debug ❌ 看不到
其它（-ENOMEM、-EINVAL…） pr_warn ✅ 能看到

结论（这是本节最实用的一条）：

如果你在 probe 里 return -ENODEV 表示"这个设备我不认"，内核只会打 debug 级日志。默认 dmesg 完全看不见。

所以调试期不要用 -ENODEV 表示"出错了"——它是"拒绝匹配"的语义。出错就返回 -EINVAL、-ENOMEM、-EIO 之类，至少能在 dmesg 里留痕。

要看那些隐藏日志：

# 打开动态调试（CONFIG_DYNAMIC_DEBUG）
echo 'file drivers/base/dd.c +p' > /sys/kernel/debug/dynamic_debug/control
# 或者启动时加内核参数
initcall_debug dyndbg="file drivers/base/dd.c +p"

-EPROBE_DEFER：不是失败，是"等一会儿"

驱动依赖的资源（时钟、regulator、GPIO 控制器、supplier 设备）还没就绪时，probe 应该返回 -EPROBE_DEFER，内核会把它放进延迟队列，等其他驱动 probe 完再重试。

static int my_probe(struct platform_device *pdev)
{
    struct clk *clk;

    clk = devm_clk_get(&pdev->dev, NULL);
    if (IS_ERR(clk))
        return dev_err_probe(&pdev->dev, PTR_ERR(clk), "get clock");
    ...
}

dev_err_probe() 是现代写法，强烈推荐，它做两件事：

  1. -EPROBE_DEFER 时不刷屏（defer 会重试很多次，用 dev_err 会淹没日志）
  2. 真实错误时打 error 级日志并附带错误码，同时把返回值原样透传

dev_err_probe 内部对 -EPROBE_DEFER 走 dev_dbg，其它走 dev_err——等于帮你实现了上面那张日志级别表的正确行为。

查看当前有没有卡在 defer 状态的设备：

cat /sys/kernel/debug/devices_deferred

★ probe 的返回码会被取反

v6.6 drivers/base/dd.c:670：

        /*
         * Return probe errors as positive values so that the callers
         * can distinguish them from other errors.
         */
        ret = -ret;
        goto probe_failed;

驱动 return -ENODEV，really_probe() 往外抛的是正的 ENODEV。这个约定（"bus 层返回正值表示 probe 失败"）在写 bus glue 层或者读内核日志对照错误码时会撞上：dmesg 里看到的数字和驱动里写的是反的。

排查清单：驱动没 probe 怎么办

按顺序验，每步都能在 30 秒内出结果：

# 检查 命令 不通过怎么办
1 模块加载了吗 lsmod \| grep my modprobe / 查 modules.alias
2 节点在吗 ls /proc/device-tree/ 查 DTB / overlay
3 status 可用吗 tr '\0' '\n' < .../status 改成 okay
4 compatible 逐字符对吗 tr '\0' '\n' < .../compatible 对照 modinfo \| grep alias
5 device 建出来了吗 ls /sys/bus/platform/devices/ 查父节点是否被递归（3.3）
6 卡在 defer 吗 cat /sys/kernel/debug/devices_deferred 找缺的 supplier
7 匹配表有吗 modinfo x.ko \| grep alias 补 MODULE_DEVICE_TABLE
8 probe 日志 开 dynamic debug 后重看 —

第 4 步最常出错：compatible 里多一个空格、少一个逗号、大小写不对，都会静默失败。用 modinfo 的 alias 和 DTS 的 compatible 逐字符对比，别用眼睛看。

HFT / 嵌入式关联

  • "静默失败"是嵌入式最贵的调试成本。 内核把"驱动拒绝匹配"设计成 debug 级日志是合理的（每次总线扫描都可能有很多这种"拒绝"），但对开发者的代价是：你必须有意识地选择错误码。这是"可观测性由 API 使用者负责"的典型例子——框架给了分级，用错是你的问题。
  • -EPROBE_DEFER 是依赖注入：驱动不关心 supplier 什么时候就绪，只说"我没好，待会再叫我"。这比在驱动里手写等待/重试健壮得多，也是内核"声明依赖而非控制时序"的思路。
  • HFT 的类比：低延迟系统里"超时"和"明确失败"也必须分开处理——超时可能重试成功，明确失败重试只会浪费时间。内核这里把 -EPROBE_DEFER（重试有意义）和 -EINVAL（重试无意义）分开统计，是同一个设计哲学。

自测
  1. platform_match 的四级回退顺序是什么？最高优先级那个怎么用？
  2. 少了 MODULE_DEVICE_TABLE(of, ...) 会怎样？为什么手动 insmod 发现不了问题？
  3. probe 里 return -ENODEV 和 return -ENOMEM，在 dmesg 里表现有什么不同？
  4. 为什么 probe 里申请资源失败应该用 dev_err_probe 而不是 dev_err + return？
  5. 驱动 probe 返回 -EPROBE_DEFER 说明什么？怎么确认哪些设备卡在这个状态？
  6. 驱动 return -ENODEV，really_probe() 往外返回的是几？
参考答案

  1. driver_override → OF(compatible) → ACPI → id_table → 驱动名==设备名。最高优先级是 driver_override：往 /sys/bus/platform/devices/<dev>/driver_override 写驱动名，再 echo <dev> > /sys/bus/platform/drivers/<drv>/bind，可以强制绑定，常用于调试时临时换驱动。

  2. 模块不会在设备出现时自动加载——MODULE_DEVICE_TABLE 的作用是把匹配表导出到 modules.alias，供 depmod/udev 做自动加载。但手动 insmod 时匹配表本身已经在内核里了，platform_match 照常工作，所以"手动能跑"掩盖了"自动加载链断了"。验证：modinfo x.ko | grep alias 应该有一行 of:N*T*C<compatible>。

  3. -ENODEV 落到 pr_debug（默认 dmesg 看不见），因为内核认为这是"驱动拒绝匹配"，属于正常流程；-ENOMEM 落到 pr_warn（看得见），因为这是"匹配了但 probe 失败了"，属于异常。所以调试期表示真实错误不要返回 -ENODEV/-ENXIO。

  4. 因为 -EPROBE_DEFER 会触发多次重试（每次 supplier 就绪都重试一遍），用 dev_err 会刷屏淹没真实日志。dev_err_probe() 内部对 -EPROBE_DEFER 只打 dev_dbg，其它错误才打 dev_err 并附错误码——一行代码实现了正确的日志分级，同时原样透传返回值（defer 语义不丢）。

  5. 表示依赖的资源（时钟、regulator、GPIO 控制器、supplier 设备）尚未就绪，不是失败，内核会把它放进延迟队列，等依赖就绪后重试。确认方法：cat /sys/kernel/debug/devices_deferred 会列出所有卡在 defer 状态的设备。

  6. 正的 ENODEV（即 +19）。really_probe() 在 dd.c:673 处 ret = -ret; 把 probe 错误码取反成正值返回，注释说明是"让调用者能区分 probe 失败和其它错误"。

3.5

· devm 与出错路径：为什么 probe 里不用手写 unwind

本节讲什么： devm_* 到底把资源挂在哪、什么时候释放、释放顺序如何，以及两个反直觉的细节——probe 前 devres 链表必须为空，和 probe 错误码会被取反。

心智模型：一张挂在 device 上的链表

struct device {
    ...
    struct list_head  devres_head;   /* ★ 所有 devm_ 申请都挂这里 */
    spinlock_t        devres_lock;
};

devm_kzalloc(&pdev->dev, ...) 做的事：

  1. 分配一块 devres 结构（头部 + 你的数据）
  2. 在里面记下释放函数（devm_kzalloc 对应的 free）
  3. devres_add() → add_dr() 挂到 dev->devres_head 尾
devres_head ─→ [kzalloc#1] → [ioremap#2] → [irq#3] → [gpio#4]

device 没了，链表跟着走——这就是"自动回收"的全部秘密，没有 GC，没有引用计数。

释放时机与顺序

时机 触发函数 场景
probe 失败 probe_failed: → devres_release_all() 你不用写任何清理代码
驱动卸载 device_release_driver() rmmod
设备消失 device_del() 热插拔 / 总线 rescan

释放顺序是申请顺序的逆序（v6.6 drivers/base/devres.c:496）：

list_for_each_entry_safe_reverse(dr, tmp, todo, node.entry) {
    dr->node.release(dev, dr->data);
    kfree(dr);
}

注意 ..._reverse：LIFO，后申请的先释放。这跟手写 unwind 的顺序一致——先释放最内层依赖（irq），再释放它依赖的东西（映射、内存）。

申请：  内存 → ioremap → irq
释放：  irq → ioremap → 内存      ← 自动就是这个顺序

所以 devm 不只是"省代码"，它还保证了释放顺序不会写错。 手写 unwind 时漏掉中间某步、或者顺序搞反，是驱动里最常见的一类 bug。

对比：手写 vs devm

/* ============ 手写（老式） ============ */
static int my_probe(struct platform_device *pdev)
{
    struct my_dev *m;
    int ret;

    m = kzalloc(sizeof(*m), GFP_KERNEL);
    if (!m)
        return -ENOMEM;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    m->base = ioremap(res->start, resource_size(res));
    if (!m->base) {
        ret = -ENOMEM;
        goto err_free;          /* ← 每个失败点都要 goto */
    }

    ret = request_irq(irq, handler, 0, "my", m);
    if (ret)
        goto err_iounmap;       /* ← goto 越来越多 */

    platform_set_drvdata(pdev, m);
    return 0;

err_iounmap:
    iounmap(m->base);
err_free:
    kfree(m);
    return ret;                 /* ← 加一步资源，就要改两处 */
}

static int my_remove(struct platform_device *pdev)
{
    /* 卸载路径再写一遍，且顺序必须与上面相反 */
    free_irq(irq, m);
    iounmap(m->base);
    kfree(m);
    return 0;
}

/* ============ devm（现代） ============ */
static int my_probe(struct platform_device *pdev)
{
    struct my_dev *m;

    m = devm_kzalloc(&pdev->dev, sizeof(*m), GFP_KERNEL);
    if (!m)
        return -ENOMEM;

    m->base = devm_ioremap_resource(&pdev->dev,
                  platform_get_resource(pdev, IORESOURCE_MEM, 0));
    if (IS_ERR(m->base))
        return PTR_ERR(m->base);        /* 直接 return，无 goto */

    ret = devm_request_irq(&pdev->dev, irq, handler, 0, "my", m);
    if (ret)
        return dev_err_probe(&pdev->dev, ret, "irq");   /* 无 unwind */

    platform_set_drvdata(pdev, m);
    return 0;
}

static int my_remove(struct platform_device *pdev)
{
    return 0;               /* ★ 空的。资源由核心在返回后释放 */
}

注意 remove 的时序：devm 释放在 remove() 返回之后发生。所以如果你的设备有特殊关机序列（比如"先停硬件再释放"），不能全交给 devm——要么在 remove() 里显式做，要么用 devm_add_action() 注册一个按逆序调用的清理钩子。

两个反直觉的细节

① probe 开始前，devres 链表必须是空的

v6.6 drivers/base/dd.c:625：

    if (!list_empty(&dev->devres_head)) {
        dev_err(dev, "Resources present before probing\n");
        ret = -EBUSY;
        goto done;
    }

内核在 probe 前检查：如果链表已经非空，直接拒绝并报 -EBUSY。

含义：devm_* 的第一个参数必须是"这个 device"，且只能在 probe 之后调用。 在 module_init 里对某个 device 提前 devm_kzalloc，会让后续真正的 probe 直接失败——而报错信息 "Resources present before probing" 看起来和你的代码毫无关系。

反过来说，这也是个诊断线索：看到 Resources present before probing 就说明有人在 probe 之外动了 devres。

② probe 返回的错误码会被取反成正数

见 3.4——really_probe() 里 ret = -ret;。驱动 return -ENODEV，总线层往外抛 +ENODEV。读内核调用链代码时别以为自己看错了。

自定义清理：devm_add_action

devm 没有覆盖到的资源（比如自己开的 workqueue、注册到某个全局链表的东西），用 action 钩子：

static void my_cleanup(void *data)
{
    struct my_dev *m = data;
    cancel_work_sync(&m->work);
    /* 反注册、关时钟…… */
}

/* probe 里： */
ret = devm_add_action_or_reset(&pdev->dev, my_cleanup, m);
if (ret)
    return ret;      /* 失败时 action 已自动执行过一次（_or_reset 的语义） */

优先用 _or_reset 后缀版本：注册失败时它会自动调用一次 action，省掉"注册失败时手动清理"这个分支。

常用 devm 清单

用途 API 非 devm 版本
内存 devm_kzalloc / devm_kmalloc kzalloc
寄存器映射 devm_ioremap_resource / devm_platform_ioremap_resource ioremap
中断 devm_request_irq / devm_request_threaded_irq request_irq
GPIO devm_gpiod_get gpiod_get
时钟 devm_clk_get / devm_clk_get_enabled clk_get
regulator devm_regulator_get regulator_get
清理钩子 devm_add_action_or_reset —

⚠️ 不是所有东西都有 devm 版本，且有些"有 devm 版本但语义微妙不同"。拿不准时查 drivers/base/devres.c 的导出符号：没有 EXPORT_SYMBOL(devm_xxx) 的就是不存在，别猜。

检查清单

问题 后果
probe 用 devm_*、remove 里又手动 free_irq double free（devm 回去再释放一次）
在 module_init 里 devm_* 后续 probe 报 -EBUSY "Resources present before probing"
devm_request_irq 的 dev 参数传错（传了别的 device） 中断挂到别的设备上，device 消失时机错位 → 悬空 handler
remove 里做"先停硬件"的清理，依赖 devm 顺序 devm 在 remove 返回后才跑，你的清理可能太晚

最实用的一条： 用了 devm 就彻底别手动释放。混用是最容易出现 double free / use-after-free 的组合。

HFT / 嵌入式关联

  • devm 是 RAII 思想在 C 里的落地。C 没有析构函数，内核用"资源登记到对象（device）上 + 对象销毁时逆序回调"实现同样效果。理解这一点后，看到任何 devm_xxx 都能立刻推断出释放时机和顺序。
  • 出错路径的代码量直接决定 bug 密度。驱动里 90% 的 bug 在错误路径（正常路径谁都会写、也都会测）。devm 把错误路径从"N 个 goto 标签 + N 段清理"压成"直接 return"，是结构性降低 bug 率，不是语法糖。
  • HFT 里的对应物：确定性拆除顺序对低延迟系统同样关键——网卡驱动卸载时如果先释放了 ring buffer 再注销 NAPI，就会在中断里访问已释放内存。devm 的 LIFO 保证让这类"顺序错误"不可能发生。

  3. 用了 devm_request_irq，remove() 里还需要 free_irq 吗？为什么？
  4. 内核报 -EBUSY 且信息是 "Resources present before probing"，最可能的原因是什么？
  5. remove() 里需要"先停硬件再释放资源"，devm 能满足吗？为什么？
  6. devm_add_action 和 devm_add_action_or_reset 有什么区别？该用哪个？
参考答案

  1. 挂在 struct device 的 devres_head 链表上（每个 devres 节点记录了对应的 release 函数）。释放在三种时机触发：probe 失败（probe_failed: → devres_release_all）、驱动卸载（device_release_driver）、设备消失（device_del）。关键：remove() 返回之后才释放。

  2. 申请顺序的逆序（LIFO）。源码是 list_for_each_entry_safe_reverse。这个顺序是对的，因为后申请的资源通常依赖先申请的（irq 依赖 ioremap，ioremap 依赖内存），逆序释放保证"释放 X 时 X 依赖的东西还在"，与手写 unwind 的正确顺序天然一致。

  3. 不需要，且不应该。 devm 会在 remove 返回后自动 free_irq；手动再 free 一次是 double free。规则是用 devm 就彻底不要手动释放，混用是 use-after-free / double free 的主要来源。

  4. 有人在 probe 之前往这个 device 的 devres 链表里塞了东西。典型是在 module_init 里对某个 device 调用了 devm_*。内核在 really_probe 开头检查链表非空就直接返回 -EBUSY 拒绝 probe。修法：把那些 devm_* 挪进 probe，或改用非 devm 的普通分配 + 自己管理生命周期。

  5. 不能可靠满足。 devm 的释放发生在 remove() 返回之后，也就是你的清理代码跑完之后。如果硬件需要在"资源释放前"被停止，正确做法是：在 remove() 里显式做停机序列，或者用 devm_add_action_or_reset() 注册清理钩子（钩子按 devm 的 LIFO 顺序被调用）。

  6. _or_reset 版本在注册失败时会自动调用一次 action，省掉"注册失败要手动清理"的分支；普通版注册失败后 action 不会被调用，你得自己处理。所以优先用 devm_add_action_or_reset——和 devm 的设计意图（错误路径零手工）一致。
