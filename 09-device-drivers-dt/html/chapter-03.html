导读

本节讲什么： 现代 ARM Linux 驱动的主干——硬件信息从设备树来，驱动通过 compatible 匹配，资源全部从 DT 解析，基址不硬编码。 对应动手： P5 · C3（platform + probe，资源全从 DT 解析，无硬编码基址，对照 RP1 / 板级 DTS）

为什么是核心

SoC 上的外设没有总线可以枚举（不像 PCIe 能扫出来）。所以内核必须靠一张"硬件清单"来知道有什么设备——这张清单就是设备树。

DTS（人写） --dtc--> DTB（二进制） --> bootloader 传给内核
                                            ↓
                                  展开为 device_node 树
                                            ↓
                       platform_bus 按 compatible 匹配 driver
                                            ↓
                                      driver->probe()

DTS 节点长什么样

mydev@fe200000 {
    compatible = "wzp,my-device";     /* 匹配的钥匙 */
    reg = <0x0 0xfe200000 0x0 0x1000>;   /* 地址 + 长度 */
    interrupts = <GIC_SPI 32 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&clk_peri>;              /* phandle 引用别的节点 */
    status = "okay";
};

驱动侧：

static const struct of_device_id my_of_match[] = {
    { .compatible = "wzp,my-device" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, my_of_match);

static int my_probe(struct platform_device *pdev)
{
    struct resource *res;
    void __iomem *base;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    base = devm_ioremap_resource(&pdev->dev, res);   /* devm_ 自动回收 */
    /* 寄存器读写：readl(base + REG_X) / writel(v, base + REG_X) */
    return 0;
}

关键： 用 devm_* 系列（devm_ioremap_resource、devm_kzalloc、devm_request_irq），出错路径不用手写 unwind，remove 时自动释放。

3.1

新增外设：DTS 必改，驱动分三档

FAQ · 锚定 Primer Ch7（DTB）· Ch8（驱动入门）· 09 驱动·DT
相关：DT ≠ UEFI · BSP 模板

核心结论（两层分开）

  1. 板子新加硬件 → 几乎 100% 要改/增 DTS 节点（启用片内模块则常是改 status，见下）。
  2. 不等于一定要从零写驱动 — 有现成驱动就只配 DTS；要适配就改几行；没有才写完整驱动。

一、为什么必须动设备树？

内核靠 DTB 里的信息认硬件：compatible、reg（物理基址）、中断、供电、时钟、复位等。

U-Boot 负责 DDR/Flash 等上电初始化，不会把「你焊了什么外设」完整交给内核；启动后内核的主硬件清单来源就是 DTB（现代 ARM 嵌入式主路径）。

例：GPIO 按键

  • 硬件：键接 GPIO ↔ GND
  • DTS：加 gpio-keys（或等价）节点 — GPIO、键名、触发电平
  • 驱动：内核 gpio_keys 等通用驱动 → 可零行自写驱动，只写 DTS

例：板外独立 GPU / 显示控制器（非 SoC 内置）

  • DTS：compatible、reg、电源、时钟、复位、总线（PCIe/I2C…）
  • 驱动：
  • 内核已有 → 只 DTS
  • 冷门/自研 → DTS + 完整平台/字符驱动（Ch8 入门 → 12 深挖）

二、三档工作量

场景 DTS 驱动
1. 内核已有标准驱动（LED、gpio-keys、常见 I2C 传感器、多数屏/PHY/UART…） 必写节点：compatible / reg / interrupts / clocks / regulator / reset… 不写；编 DTB、替换启动用的 dtb
2. 有通用驱动，参数略不同（同系列屏分辨率/时序等） 必写接线 少量改驱动或用 DT 属性吃参数，不从头造
3. 无现成驱动（自研采集、冷门芯片） 先建节点写地址/中断/电源 完整开发；驱动从 DT 读资源再做读写/IRQ

操作骨架（场景 1）：改 .dts → 出新 .dtb → boot 加载新 DTB（多数情况 不必 重编 U-Boot，见下）。

为何场景 1 这么多： 标准协议 + 厂商合入主线/BSP — 8.4。

三、片内模块 vs 外挂器件

类型 DTS 常见动作
SoC 片上（内置 UART/ETH MAC/内置 GPU…） 原厂 dtsi/dts 已有节点；多用 status = "okay" / "disabled"，不必从零「发明」节点
板外新挂（按键、外置 GPU、I2C 模组、外接 Flash…） 评估板 dts 没有 → 新增完整节点

四、和 U-Boot 的联动（承接 DT FAQ）

你加的东西 U-Boot
普通外设：按键、传感器、屏（内核阶段才用） 通常只改 DTS，不重编 U-Boot
影响启动期：DDR、NAND/启动介质、U-Boot 就要用的 PHY/串口时序 还要改 U-Boot — 7.0 场景 B

五、一句话

多焊硬件 → DTS 必动；写驱动看内核有没有货。
有货只配树；没货先写树再写驱动。

3.2

设备树与驱动：分工、compatible、probe、启动链路

完整关系拆解 · Primer Ch7（DTB）+ Ch8（驱动入门）· 深挖 12
相关：加外设三档 · DT ≠ UEFI

一、定位：配置表 vs 操作代码

设备树（DTS→DTB） 驱动
本质 静态数据，无可执行逻辑 C 代码：读写寄存器、IRQ、协议、业务
内容 地址、中断、时钟、电源、复位、compatible、拓扑、板级参数 初始化、收发、ISR、/dev / sysfs
目的 接线/资源与驱动解耦 — 换板多半只改树 真正操作外设

比喻： 驱动 = 电器说明书；设备树 = 插座分布图（位置、电压）。换插座位置改图即可，不必重写说明书。

二、绑定钥匙：compatible

  1. DTS 节点：compatible = "vendor,part"（可多字符串，按优先匹配）
    例：compatible = "fsl,imx6ul-uart";
  2. 驱动：of_match_table 注册相同字符串，挂到 platform_driver（或同类）上：
static const struct of_device_id uart_of_match[] = {
    { .compatible = "fsl,imx6ul-uart" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, uart_of_match);

static struct platform_driver uart_drv = {
    .probe = uart_probe,
    .driver = {
        .name = "imx6-uart",
        .of_match_table = uart_of_match,
    },
};
  1. 内核：解析 DTB → 对每个节点的 compatible 在已注册驱动里找匹配 → 命中则调 probe()。

probe = 驱动读树、申请资源、初始化硬件的入口。

三、probe 里怎么读树（of_*）

API（示意） 用途
of_address_to_resource / platform_get_resource reg → 物理/IO 资源
of_irq_get / platform_get_irq 中断号
of_clk_get 时钟
of_property_read_u32 等 自定义属性（分辨率、速率…）
of_get_named_gpio / gpiod 族 GPIO

例：只加按键（不改驱动）

gpio_keys {
    compatible = "gpio-keys";
    key1 {
        gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
        label = "user_btn";
    };
};

内核自带 gpio-keys 驱动匹配 "gpio-keys" → probe → of_* 读 GPIO/标签 → 申请中断、上报按键。
全程只改 DTS（场景见 8.0）。

四、分工边界

设备树只填数据（不做操作）

  • MMIO 基址、IRQ、时钟、供电、复位
  • 总线拓扑（I2C 下挂哪些从设备）
  • 板级参数（屏时序、波特率、分区大小）
  • status = "okay" / "disabled"

驱动只写逻辑（不把板级地址写死）

  • 寄存器/中断/上下电与初始化
  • 协议与数据路径
  • 用户态接口（/dev、sysfs、net…）

解耦收益： 同驱动多板复用，改地址/引脚改树即可。
无 DT 的老做法：地址硬编码在 .c → 换板改驱动重编。

五、新增硬件时的联动（摘要）

场景 DTS 驱动
内核已有标准驱动 增/改节点 不写
无驱动 先建节点（含 compatible） 写 of_match_table + probe + of_*

片内模块：原厂节点多已在，常只改 status。
板外新芯片：常需新建完整节点；无驱动再开发。详表 → 8.0。

六、启动交互链路（极简）

U-Boot 加载 DTB → 交给内核
    → 内核展开设备节点
    → compatible ↔ of_match_table
    → probe()
    → of_* 取资源 → 初始化硬件 → 暴露 /dev 等

U-Boot 不替代 DTB 当「完整外设清单」；它负责启动期硬件初始化并把 DTB 指针交给内核（7.0）。

七、一句话

DT = 静态资源清单；驱动 = 操作逻辑。
靠 compatible 绑在一起，靠 of_* 在 probe 里读树 — 板级移植成本主要落在改树上，而不是改遍驱动源码。
