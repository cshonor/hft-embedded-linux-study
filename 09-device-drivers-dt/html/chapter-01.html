导读

本节讲什么： 写出第一个 .ko，装载进运行中的内核，理解"内核模块"到底是个什么东西。 对应动手： P5 · C 阶段热身（内核模块 HelloWorld、insmod/rmmod）

要点

概念 说明
模块是什么 一段可动态插入内核地址空间的目标代码（.ko），运行在内核态、共用内核地址空间
module_init / module_exit 装载/卸载入口。不是 main
printk 不是 printf 输出进内核环形缓冲区，用 dmesg 看；有日志级别（KERN_INFO 等）
版本魔法 模块必须与正在运行的内核同版本同配置编译，否则 insmod 直接拒绝
没有 libc 内核里没有 printf/malloc/文件描述符，只有 printk/kmalloc/struct file *

最小可跑模块

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init hello_init(void)
{
    pr_info("hello: loaded\n");
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("hello: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("wzp");
MODULE_DESCRIPTION("minimal module");

obj-m += hello.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
    make -C $(KDIR) M=$(PWD) modules
clean:
    make -C $(KDIR) M=$(PWD) clean

make && sudo insmod hello.ko && dmesg -T | tail -3
lsmod | grep hello
sudo rmmod hello && dmesg -T | tail -3

注意： MODULE_LICENSE("GPL") 不是可选项——缺了会触发内核 taint，部分 GPL-only 符号（如很多核心 API）直接不对你开放。

1.1

驱动为什么在内核（built-in / .ko）

FAQ · 锚定 Primer Ch2（内核/用户上下文）· Ch4（drivers/）· Ch8（模块）
相关：DT↔驱动 · 三层图

一、根本原因：硬件权限只在内核

Linux 分 内核态 / 用户态。寄存器、IRQ、DMA、内存控制器等，用户态不能直接摸。

谁 权限
内核 完整硬件访问；能注册并跑中断处理
用户进程 经系统调用间接请求；直访 MMIO 通常 → 缺页/被杀

因此「读写寄存器、ISR、真正控外设」的主体必须是 内核里的驱动代码。

两种打包形式（本质都是内核代码）

形式 .config 形态 运行期
built-in =y 链进 vmlinux 开机即在，一般不能 rmmod
可加载模块 =m 独立 .ko insmod/modprobe 加载，rmmod 卸载

「内核模块」常特指 .ko；口语里「驱动是内核模块」= 跑在内核空间（含 built-in）。

二、驱动 · 内核 · 设备树协作

U-Boot 交 DTB
  → 内核解析节点，compatible 匹配驱动
  → 调 probe（内核态）
  → of_* 读地址/中断/时钟
  → 驱动操作硬件、注册 IRQ、创建 /dev/xxx
  → 用户态 APP：open/read/write… 系统调用 → 再进驱动

设备树不是驱动：只给内核驱动喂静态参数。
APP 不直连硬件：只跟 /dev（或 net/socket 等）说话。

例：按键

  • gpio_keys（.ko 或 built-in）在内核跑
  • DTS 只描述 GPIO 等
  • APP read → 陷入内核 → 驱动读电平 → 结果回用户态

三、不在「内核 .c 驱动」里的两类东西（易混）

类型 澄清
用户态「驱动」（少见） 如经 /dev/i2c-N、spidev 在用户态协议；总线控制器驱动仍在内核
固件 blob（GPU/Wi‑Fi 等） 文件在 rootfs；由内核驱动加载进芯片 — 固件 ≠ Linux 驱动

核心硬件控制逻辑仍落在内核侧。

四、为何不能把驱动主体写进普通 APP

  1. 权限 / MMU：用户态乱碰物理地址 → 崩溃或被杀
  2. 中断：硬中断由内核接；用户进程接不到「原味」硬件 IRQ 路径
  3. 隔离：用户崩溃默认杀进程；硬件控制若全在用户态，异常易把外设锁死、拖垮整机

（专用框架如 UIO/VFIO、DPDK 是刻意旁路的另一条课，先把标准内核驱动路径学清。）

五、对应本书章节

章 要点
Ch2 内核上下文 vs 用户上下文；驱动/ISR 在内核侧
Ch4 源码 drivers/；=y / =m 进镜像或 .ko
Ch8 字符/平台驱动、insmod/lsmod — 操作的是内核模块

仓库：Project #1 三层图 · 09 驱动深挖

六、总结

  1. 寄存器 / 中断 / 总线底层操作必须在内核 → 驱动主体是内核代码
  2. built-in 与 .ko 只是链接方式不同
  3. DT 给驱动提供参数，本身不是驱动
  4. 应用只通过系统调用委托内核驱动，不能替代它

与 8.1 合读：树负责描述，驱动（内核里）负责操作。
与 8.3 合读：操作覆盖 全生命周期 + 中断，不单是 probe 初始化。

1.2

为何多数外设不用自己写驱动（主线 + 标准协议）

FAQ · 承接 3.1 三档工作量 · 3.2 绑定
结论：标准化硬件 → 厂商写进主线 / BSP；你多数时候 只配 DTS

1. 主流通用外设：驱动已在主线，开箱复用

串口、以太 PHY、常见 I2C 温感、LCD 面板族、SD、USB HID、GPIO 按键/LED 等：
芯片原厂（NXP、TI、ST…）常把驱动合进 Linux 主线（kernel.org）。

原因： 协议与寄存器行为有行业规范（或事实标准），硬件逻辑相对固定，不必每块板重写一套驱动。一次合入，全球复用。

2. 「标准」如何变成「一套驱动 + 多块板」

例子 统一的是什么 板间差什么
UART 收发 / 中断 / 时钟控制模型相近 DTS：reg、IRQ、时钟、引脚
I2C EEPROM 标准读写时序 地址、页大小等属性
千兆 PHY IEEE 以太 PHY 模型 PHY 地址、复位脚、接口模式
按键 / LED gpio-keys / leds-gpio 逻辑固定 哪个 GPIO、高低有效

→ 操作逻辑在驱动里写死一套；接线与资源在树上改。

3. SoC 私有模块：靠原厂 BSP，仍常「零自写驱动」

片内专属块（某家通信引擎、多媒体加速等）未必是「全球开放标准」，但原厂 BSP / 内核树里 已带驱动。
你通常：开节点、status、填资源 — 不是从零写驱动（除非要深度改行为）。

与 BSP = 模板 一致：评估板开箱；自研板主要改树与配置，不是每片外设都重写 .c。

4. 反例：什么时候必须自己写

  1. 自研采集/控制芯片，无公开标准协议
  2. 小众工业件：无主线、无开源驱动
  3. 全新外设，无可参考同类驱动

此时：新建 DTS + 完整内核驱动（8.2 / 8.3）→ 深挖 12。

5. 落到日常工作

硬件类型 你干什么
通用成熟外设 只改/加 DTS，零驱动编码
私有/自研/无驱动 DTS + 自写内核驱动

总结

绝大多数标准化外设：行业规范 + 厂商已合入主线/BSP → 开发者用设备树配资源即可，不必重复造驱动轮子。
「会写驱动」仍是刚需，但用在 没有现成驱动 的那一档，而不是每个 LED 从零写起。

1.3

驱动管硬件全生命周期（含中断）

FAQ · 承接 1.1 为何在内核 · 3.2 DT↔驱动
印证：驱动 ≠「只开机初始化一下」

结论（你的理解成立）

驱动对硬件是 全权、全时段 接管：上电初始化、日常读写、中断、异常、休眠/关机释放。
中断是驱动与硬件双向通道的核心职责之一，不是可选项。

一、全生命周期拆细

阶段 驱动做什么
开机 / probe 从 DT 取 reg/时钟/供电等 → 上电、配寄存器、初始化总线 → 硬件可用（「启动硬件」）
日常交互 APP open/read/write/ioctl… → 系统调用进驱动 → 真正收发（屏、传感器、网包…）
中断响应 按键、RX 完成、DMA 结束、硬件报错等 → 仅驱动注册的 ISR 处理；用户态收不到原生 IRQ
异常 溢出、总线错、超时、电压类报错 → 驱动捕获并处理/上报
休眠 / 关机 关时钟、切供电、释放 IRQ/GPIO/DMA 等资源

二、中断路径（按键例）

按键 → GPIO 硬件拉 IRQ → CPU 进内核中断上下文
  → 跳到驱动已 request 的 handler
  → 辨来源、记状态、唤醒等待中的读者
  → APP read / poll 拿到事件

没有驱动注册 IRQ：内核视作未处理中断，事件等于丢掉。

三、常见中断场景

硬件 事件 驱动侧
网口 收包 NIC 驱动收描述符 → 交协议栈
UART 收到字节 串口驱动读 FIFO
触摸 按下 触控驱动上报坐标
NAND/SD 完成/出错 MTD/块层处理

四、用户态怎么「感知」中断？

  1. APP 不能直接注册原生硬件中断
  2. 驱动必须封装：/dev、sysfs、信号、poll/epoll 等待队列等，把事件间接递给应用
  3. 无驱动注册 → 硬件 IRQ 对系统无意义

（UIO 等是特例框架，仍要内核侧桩；先把标准路径记牢。）

五、一句话

驱动不是开机脚本；运行期每一次硬件打断、数据搬运、故障与释放，都走内核驱动。
中断 = 驱动核心职责。与 8.2（为何必须在内核）同一条线。

1.4

· 为什么内核模块不能用 libc，以及 MODULE_LICENSE 的实际后果

本节讲什么： 内核模块不能链接 libc 的根本原因（不是"忘了链接"，是架构上不可能），以及两个常被当成"只是标记"、实际有硬后果的东西——MODULE_LICENSE 缺失会让你用不了 EXPORT_SYMBOL_GPL 的符号，还有自己编的模块必然让内核 taint。

一、为什么用不了 libc

表层原因：没有链接

用户态程序由动态链接器把 libc.so 映射进来；内核模块加载时解析的是内核自己的符号表（/proc/kallsyms 里那些 EXPORT_SYMBOL 导出的），里面根本没有 printf。

用户态：a.out  ──ld.so──▶ libc.so ──syscall──▶ 内核
内核态：my.ko  ──模块加载器──▶ 内核符号表（printk / kmalloc / ...）
                              ✗ 没有 printf，也没有 syscall 入口可用

★ 根本原因：libc 的函数依赖 syscall，而内核没法"调用自己"

printf 最终落到 write(1, buf, n)；malloc 最终落到 brk/mmap。系统调用的本质是"从用户态陷入内核"的机制（svc / syscall 指令 + 特权级切换 + 内核栈切换）。

内核代码本身就在 ring 0 / EL1 运行在 syscall 的另一端：

  • 它没有"陷入自己"这回事
  • 它需要的文件操作直接调 VFS 内部函数（vfs_write 等），而不是 write 这个系统调用入口
  • 它需要内存直接调 kmalloc / alloc_pages，而不是 brk

所以这不是"内核里没有 libc 的实现"，而是 libc 依赖的那套机制在内核上下文中不成立。

对照表：你要习惯的替换

用户态（libc） 内核态 备注
printf printk 有日志级别（KERN_INFO / KERN_ERR 等）
malloc / free kmalloc / kfree 带 GFP_ 标志，可睡眠
vmalloc vmalloc 虚拟连续、物理不必连续
memcpy / strlen 有 内核自带一份，直接用
strcpy strscpy ⚠️ strcpy 不安全，strlcpy 已废弃
sprintf snprintf / scnprintf 内核态没有浮点格式化（见下）
open/read/write 无直接对应 内核直接调 VFS；不该在驱动里读写文件
sleep/usleep msleep / usleep_range ⚠️ 进程上下文才能用
pthread_mutex mutex / spinlock 见 05-irq-locking

另外三条硬约束

① 浮点 / SIMD 默认不可用。 内核为了省去每次进出都保存恢复 FPU 寄存器的开销，默认不启用。要用必须显式声明区间：

kernel_fpu_begin();
/* ... 这里可以用浮点/SIMD ... */
kernel_fpu_end();

而且中断上下文里不能用（会破坏被打断进程的 FPU 状态）。信号处理里能用的那套，在内核没这个自由度。

② 栈极小。 用户态栈默认 8 MB；内核栈通常 8 KB（或配置成 16 KB），且和中断共用（某些配置下中断另用栈）。后果：

char buf[65536];        /* ❌ 直接爆栈，没有 SIGSEGV 兜底，oops */

大缓冲一律 kmalloc / devm_kzalloc，不要在栈上开。深递归同理。

③ 没有内存保护。 所有内核代码共享同一地址空间，模块与核心之间没有隔离。你越界写一个字节，可能踩到不相关的内核数据——症状是"过一会儿在完全无关的地方崩"。用户态有 SIGSEGV 兜底，内核只有 oops/panic。

二、MODULE_LICENSE：不只是标记

MODULE_LICENSE("GPL");              /* 或 "GPL v2" / "Dual BSD/GPL" 等 */
MODULE_AUTHOR("wzp");
MODULE_DESCRIPTION("my first driver");
MODULE_VERSION("0.1");

★ 硬后果：非 GPL 兼容模块用不了 EXPORT_SYMBOL_GPL 的符号

内核符号分两类导出：

EXPORT_SYMBOL(func);          /* 任何模块可用 */
EXPORT_SYMBOL_GPL(func);      /* ★ 只有 GPL 兼容许可的模块可用 */

模块加载时，加载器解析未定义符号会检查模块的 license。声明不兼容（或不声明）时，EXPORT_SYMBOL_GPL 的符号解析失败：

insmod my.ko
# insmod: ERROR: could not insert module my.ko: Unknown symbol in module
dmesg | tail
# my: Unknown symbol some_gpl_only_func (err -2)

这不是"警告"，是加载不了。 很多重要的 DMA / 网络 / 文件系统辅助函数只以 _GPL 导出——所以：

不写 MODULE_LICENSE("GPL") 的模块，等于自我限制了一部分内核 API。 学习/自用驱动没有理由不声明 GPL。

内核 taint（污染）标志

v6.6 kernel/panic.c:462 的完整表（每个条目 = { 全局大写字母, 模块自身小写字母, 是否与模块相关 }）：

标志 字母 含义
TAINT_PROPRIETARY_MODULE P / G 加载了非 GPL 兼容模块
TAINT_OOT_MODULE O 加载了 out-of-tree（树外） 模块
TAINT_CRAP C 加载了 drivers/staging 的模块
TAINT_UNSIGNED_MODULE E 未签名模块（开了模块签名时）
TAINT_FORCED_MODULE F 用 insmod -f 强加载
TAINT_DIE D 发生过 oops / BUG
TAINT_WARN W 发生过 WARN
TAINT_SOFTLOCKUP L 发生过 soft lockup

⚠️ 反直觉的一点：自己编的模块必然带 O。

cat /proc/sys/kernel/tainted          # 非 0 表示已污染
dmesg | grep -i taint
# my: module verification failed: signature and/or required key missing - tainting kernel
# 或：my: loading out-of-tree module taints kernel.

# 单个模块的标志（第二个字段）
cat /proc/modules | grep my
# my 16384 0 - Live 0x0000000000000000 (OE)
#                                        ↑↑
#                                        O = out-of-tree
#                                        E = 未签名

即使你写了 MODULE_LICENSE("GPL")，O（out-of-tree）仍在——因为你编的模块不在内核源码树里，这是"来源"标记，与许可证无关。所以调试期看到 taint 不必慌，先分清是 O/E（正常的自编译）还是 P（真的没声明 GPL 许可）。

实际影响

影响 严重度
用不了 EXPORT_SYMBOL_GPL 符号 高（加载失败）
社区/维护者看到 tainted 的 oops 报告，通常会让你先用干净内核复现 中（求助会被打回）
panic_on_taint 被设置时直接 panic 低（默认关）

三、最小可加载模块（把上面串起来）

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init my_init(void)
{
    pr_info("my: loaded\n");            /* = printk(KERN_INFO ...) */
    return 0;
}

static void __exit my_exit(void)
{
    pr_info("my: unloaded\n");
}

module_init(my_init);
module_exit(my_exit);

/* ★ 缺了 MODULE_LICENSE 会用不了 EXPORT_SYMBOL_GPL 的符号 */
MODULE_LICENSE("GPL");
MODULE_AUTHOR("wzp");
MODULE_DESCRIPTION("minimal example");

对应的 Makefile：

obj-m += my.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
    make -C $(KDIR) M=$(PWD) modules
clean:
    make -C $(KDIR) M=$(PWD) clean

__init / __exit 宏：把函数放进特定段，__init 的代码在初始化完成后被释放（内核启动时打印 "Freeing unused kernel memory" 就包含这部分）。只在模块里对初始化函数用。

HFT / 嵌入式关联

  • "内核没有 libc" 这个约束决定了内核编程的整个风格：没有异常、没有内存保护、栈极小、不能睡眠的上下文。这些不是限制而是设计选择——为了确定性和性能。理解"为什么"比记住"不能用什么"重要得多。
  • 栈限制与 HFT 的对应：低延迟代码同样忌讳在热路径上做大栈分配和深递归（cache 局部性）。内核是 8 KB 硬限制，HFT 是 cache miss 的软惩罚——本质都是"离 CPU 越近的资源越贵"。
  • EXPORT_SYMBOL_GPL 是一个社会契约的技术实现：内核用链接期的符号可见性来维护 GPL 边界。这类"用技术手段表达法律意图"的设计在开源基础设施里很常见，值得留意。

参考答案

  1. 表层：内核模块加载时解析的是内核符号表（/proc/kallsyms 里 EXPORT_SYMBOL 导出的），里面没有 libc 的函数，也没有动态链接器去加载 libc.so。 根本：libc 的函数（printf→write、malloc→brk/mmap）依赖系统调用，而系统调用是"从用户态陷入内核"的机制。内核本身运行在 syscall 的另一端，无法"陷入自己"。它需要的功能由内核内部函数直接提供（VFS 内部接口、kmalloc 等），绕过了 syscall 这一层。

  2. printf → printk（或 pr_info/pr_err 等封装，带日志级别）；malloc/free → kmalloc/kfree（带 GFP_KERNEL 等标志，可睡眠）或 vmalloc（虚拟连续、物理可离散）。 注意 memcpy/strlen 内核自带可直接用；但 strcpy 不安全，要用 strscpy。

  3. 用不了 EXPORT_SYMBOL_GPL 导出的符号，导致模块加载失败（Unknown symbol in module）。这是链接期的硬限制，不是警告。此外内核被标记 TAINT_PROPRIETARY_MODULE（P），社区通常会拒绝处理 tainted 内核的 oops 报告。

  4. 会带 O（out-of-tree）和通常的 E（未签名）。写了 MODULE_LICENSE("GPL") 也消不掉 O——O 标记的是"模块来源不在内核源码树"，与许可证无关。GPL 声明能消掉的是 P（非 GPL 兼容）。调试期看到 taint 先分清是哪个字母。

  5. 通常 8 KB（可配成 16 KB），而用户态默认 8 MB——差三个数量级。在栈上开 64 KB 数组会立刻爆栈，且没有 SIGSEGV 兜底，直接 oops。大缓冲必须 kmalloc/devm_kzalloc；深递归同理要避免。

  6. 需要 kernel_fpu_begin() / kernel_fpu_end() 显式包裹（内核默认不启用 FPU 以省去保存恢复开销）。中断上下文里不能用——会破坏被打断进程的 FPU 寄存器状态。
