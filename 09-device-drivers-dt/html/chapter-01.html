导读

本节讲什么： 写出第一个 .ko，装载进运行中的内核，理解"内核模块"到底是个什么东西。 对应动手： P5 · C 阶段热身（内核模块 HelloWorld、insmod/rmmod）

要点

概念 说明
模块是什么 一段可动态插入内核地址空间的目标代码（.ko），运行在内核态、共用内核地址空间
module_init / module_exit 装载/卸载入口。不是 main
printk 不是 printf 输出进内核环形缓冲区，用 dmesg 看；有日志级别（KERN_INFO 等）
版本魔法 模块必须与正在运行的内核同版本同配置编译，否则 insmod 直接拒绝
没有 libc 内核里没有 printf/malloc/文件描述符，只有 printk/kmalloc/struct file *

最小可跑模块

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init hello_init(void)
{
    pr_info("hello: loaded\n");
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("hello: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("wzp");
MODULE_DESCRIPTION("minimal module");

obj-m += hello.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
    make -C $(KDIR) M=$(PWD) modules
clean:
    make -C $(KDIR) M=$(PWD) clean

make && sudo insmod hello.ko && dmesg -T | tail -3
lsmod | grep hello
sudo rmmod hello && dmesg -T | tail -3

注意： MODULE_LICENSE("GPL") 不是可选项——缺了会触发内核 taint，部分 GPL-only 符号（如很多核心 API）直接不对你开放。

1.1

驱动为什么在内核（built-in / .ko）

FAQ · 锚定 Primer Ch2（内核/用户上下文）· Ch4（drivers/）· Ch8（模块）
相关：DT↔驱动 · 三层图

一、根本原因：硬件权限只在内核

Linux 分 内核态 / 用户态。寄存器、IRQ、DMA、内存控制器等，用户态不能直接摸。

谁 权限
内核 完整硬件访问；能注册并跑中断处理
用户进程 经系统调用间接请求；直访 MMIO 通常 → 缺页/被杀

因此「读写寄存器、ISR、真正控外设」的主体必须是 内核里的驱动代码。

两种打包形式（本质都是内核代码）

形式 .config 形态 运行期
built-in =y 链进 vmlinux 开机即在，一般不能 rmmod
可加载模块 =m 独立 .ko insmod/modprobe 加载，rmmod 卸载

「内核模块」常特指 .ko；口语里「驱动是内核模块」= 跑在内核空间（含 built-in）。

二、驱动 · 内核 · 设备树协作

U-Boot 交 DTB
  → 内核解析节点，compatible 匹配驱动
  → 调 probe（内核态）
  → of_* 读地址/中断/时钟
  → 驱动操作硬件、注册 IRQ、创建 /dev/xxx
  → 用户态 APP：open/read/write… 系统调用 → 再进驱动

设备树不是驱动：只给内核驱动喂静态参数。
APP 不直连硬件：只跟 /dev（或 net/socket 等）说话。

例：按键

  • gpio_keys（.ko 或 built-in）在内核跑
  • DTS 只描述 GPIO 等
  • APP read → 陷入内核 → 驱动读电平 → 结果回用户态

三、不在「内核 .c 驱动」里的两类东西（易混）

类型 澄清
用户态「驱动」（少见） 如经 /dev/i2c-N、spidev 在用户态协议；总线控制器驱动仍在内核
固件 blob（GPU/Wi‑Fi 等） 文件在 rootfs；由内核驱动加载进芯片 — 固件 ≠ Linux 驱动

核心硬件控制逻辑仍落在内核侧。

四、为何不能把驱动主体写进普通 APP

  1. 权限 / MMU：用户态乱碰物理地址 → 崩溃或被杀
  2. 中断：硬中断由内核接；用户进程接不到「原味」硬件 IRQ 路径
  3. 隔离：用户崩溃默认杀进程；硬件控制若全在用户态，异常易把外设锁死、拖垮整机

（专用框架如 UIO/VFIO、DPDK 是刻意旁路的另一条课，先把标准内核驱动路径学清。）

六、总结

  1. 寄存器 / 中断 / 总线底层操作必须在内核 → 驱动主体是内核代码
  2. built-in 与 .ko 只是链接方式不同
  3. DT 给驱动提供参数，本身不是驱动
  4. 应用只通过系统调用委托内核驱动，不能替代它

与 8.1 合读：树负责描述，驱动（内核里）负责操作。
与 8.3 合读：操作覆盖 全生命周期 + 中断，不单是 probe 初始化。

1.2

为何多数外设不用自己写驱动（主线 + 标准协议）

FAQ · 承接 8.0 三档工作量 · 8.1 绑定
结论：标准化硬件 → 厂商写进主线 / BSP；你多数时候 只配 DTS

1. 主流通用外设：驱动已在主线，开箱复用

串口、以太 PHY、常见 I2C 温感、LCD 面板族、SD、USB HID、GPIO 按键/LED 等：
芯片原厂（NXP、TI、ST…）常把驱动合进 Linux 主线（kernel.org）。

原因： 协议与寄存器行为有行业规范（或事实标准），硬件逻辑相对固定，不必每块板重写一套驱动。一次合入，全球复用。

2. 「标准」如何变成「一套驱动 + 多块板」

例子 统一的是什么 板间差什么
UART 收发 / 中断 / 时钟控制模型相近 DTS：reg、IRQ、时钟、引脚
I2C EEPROM 标准读写时序 地址、页大小等属性
千兆 PHY IEEE 以太 PHY 模型 PHY 地址、复位脚、接口模式
按键 / LED gpio-keys / leds-gpio 逻辑固定 哪个 GPIO、高低有效

→ 操作逻辑在驱动里写死一套；接线与资源在树上改。

3. SoC 私有模块：靠原厂 BSP，仍常「零自写驱动」

片内专属块（某家通信引擎、多媒体加速等）未必是「全球开放标准」，但原厂 BSP / 内核树里 已带驱动。
你通常：开节点、status、填资源 — 不是从零写驱动（除非要深度改行为）。

与 BSP = 模板 一致：评估板开箱；自研板主要改树与配置，不是每片外设都重写 .c。

4. 反例：什么时候必须自己写

  1. 自研采集/控制芯片，无公开标准协议
  2. 小众工业件：无主线、无开源驱动
  3. 全新外设，无可参考同类驱动

此时：新建 DTS + 完整内核驱动（8.2 / 8.3）→ 深挖 12。

5. 落到日常工作

硬件类型 你干什么
通用成熟外设 只改/加 DTS，零驱动编码
私有/自研/无驱动 DTS + 自写内核驱动

总结

绝大多数标准化外设：行业规范 + 厂商已合入主线/BSP → 开发者用设备树配资源即可，不必重复造驱动轮子。
「会写驱动」仍是刚需，但用在 没有现成驱动 的那一档，而不是每个 LED 从零写起。

1.3

驱动管硬件全生命周期（含中断）

FAQ · 承接 8.2 为何在内核 · 8.1 DT↔驱动
印证：驱动 ≠「只开机初始化一下」

结论（你的理解成立）

驱动对硬件是 全权、全时段 接管：上电初始化、日常读写、中断、异常、休眠/关机释放。
中断是驱动与硬件双向通道的核心职责之一，不是可选项。

一、全生命周期拆细

阶段 驱动做什么
开机 / probe 从 DT 取 reg/时钟/供电等 → 上电、配寄存器、初始化总线 → 硬件可用（「启动硬件」）
日常交互 APP open/read/write/ioctl… → 系统调用进驱动 → 真正收发（屏、传感器、网包…）
中断响应 按键、RX 完成、DMA 结束、硬件报错等 → 仅驱动注册的 ISR 处理；用户态收不到原生 IRQ
异常 溢出、总线错、超时、电压类报错 → 驱动捕获并处理/上报
休眠 / 关机 关时钟、切供电、释放 IRQ/GPIO/DMA 等资源

二、中断路径（按键例）

按键 → GPIO 硬件拉 IRQ → CPU 进内核中断上下文
  → 跳到驱动已 request 的 handler
  → 辨来源、记状态、唤醒等待中的读者
  → APP read / poll 拿到事件

没有驱动注册 IRQ：内核视作未处理中断，事件等于丢掉。

三、常见中断场景

硬件 事件 驱动侧
网口 收包 NIC 驱动收描述符 → 交协议栈
UART 收到字节 串口驱动读 FIFO
触摸 按下 触控驱动上报坐标
NAND/SD 完成/出错 MTD/块层处理

四、用户态怎么「感知」中断？

  1. APP 不能直接注册原生硬件中断
  2. 驱动必须封装：/dev、sysfs、信号、poll/epoll 等待队列等，把事件间接递给应用
  3. 无驱动注册 → 硬件 IRQ 对系统无意义

（UIO 等是特例框架，仍要内核侧桩；先把标准路径记牢。）

五、一句话

驱动不是开机脚本；运行期每一次硬件打断、数据搬运、故障与释放，都走内核驱动。
中断 = 驱动核心职责。与 8.2（为何必须在内核）同一条线。
