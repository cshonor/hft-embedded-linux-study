导读

本节讲什么： 中断上下文的约束、上下半部切分、以及内核里"锁"的正确选型。 这是最容易写崩的一块 —— 违规不会立刻报错，而是随机死锁或踩内存。

铁律

规则 原因
硬中断上下文不能睡眠 中断不关联任何进程，没有可被调度的上下文；睡了就再也醒不过来
不能调用可能睡眠的函数 kmalloc(GFP_KERNEL)、mutex_lock、copy_to_user、msleep 全禁
中断处理要快 关中断期间整个 CPU 不响应其它中断，直接恶化延迟
持自旋锁时不能睡眠 别人在忙等你，你睡了 → 死锁（抢占内核下还会拖死整个核）

上半部 / 下半部

硬中断 top half      →  只做最紧急的：清中断、读数、调度下半部
       ↓
下半部 bottom half   →  可以慢一点做的工作
下半部机制 上下文 能睡？
softirq 中断（软中断） ❌
tasklet 基于 softirq ❌
workqueue 内核线程 ✅
threaded IRQ（现代推荐） 内核线程 ✅

现代写法： request_threaded_irq() —— handler 跑在硬中断（快速判断/清中断），thread_fn 跑在内核线程（可以睡、可以调 I2C/SPI）。比手写 tasklet/workqueue 简单且安全。

锁怎么选

场景 用什么
临界区很短、可能在中断上下文 spinlock_t（+ 需要时 spin_lock_irqsave）
临界区可以睡（会调 I2C/SPI/拷贝用户数据） mutex
读多写少 rwlock / seqlock / RCU
per-CPU 数据 local_irq_disable 或 per-cpu 变量（最快的锁是不加锁）

顺序原则： 永远按固定顺序获取多把锁；中断 handler 里必须用 spin_lock_irqsave（否则本核中断再来一次就自锁死）。

关键代码

static irqreturn_t my_handler(int irq, void *dev_id)
{
    /* 硬中断：清中断源，尽快返回 */
    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread(int irq, void *dev_id)
{
    mutex_lock(&dev->lock);        /* 线程上下文，可以睡 */
    /* 读 I2C 寄存器、拷贝数据 */
    mutex_unlock(&dev->lock);
    return IRQ_HANDLED;
}

request_threaded_irq(irq, my_handler, my_thread,
                     IRQF_TRIGGER_FALLING, "mydev", dev);

HFT / 嵌入式关联

  • 中断处理时间 = 延迟抖动源。这是 HFT 里"为什么要把中断绑到隔离核、为什么要 NAPI"的根因：NAPI 本质是 中断 + 轮询的混合（收一个中断后进轮询，避免每包一中断），见 12.5-modern-networking。
  • per-CPU 数据结构避免加锁，这个思路在 HFT 用户态无锁队列里是同一个招式（14-hft-engineering）。
  • 锁的选型本质是"能不能睡"，而"能不能睡"取决于当前在什么上下文——判断上下文是内核编程的基本功。

5.1

中断上下文：为什么硬中断里不能 sleep

本节讲什么： 中断上下文到底是什么、为什么不关联任何进程、以及"不能睡眠"这条铁律的物理原因。 一句话： 中断是"借尸还魂"—— 它借用被打断进程的内核栈执行，但不代表那个进程，所以没有可被调度的实体。 后续： 5.2 锁的选型 · 5.3 threaded_irq 实践
卡住查书： LDD3 Ch10、Ch5 · Madieu Ch16

中断上下文 vs 进程上下文

进程上下文 中断上下文
代表谁 某个进程（current 有效） 谁都不代表（current 指向被打断的进程，但无关）
能被调度 ✅ ❌
能睡眠 ✅ ❌
能访问用户空间 ✅ ❌（没有进程地址空间）
栈 进程内核栈（8K/16K） 借用被中断进程的内核栈（或独立 irq stack）
优先级 受调度器管理 高于一切，谁都能打断（除更高优先级中断） 
进程 A 正在跑  ──────────────────────────────►
                    │
                    │  硬件中断到来
                    ▼
              ┌───────────────────┐
              │  中断 handler      │  ← 借用 A 的内核栈，但 A 被"冻结"
              │  (中断上下文)      │     current == A，但 A 与此无关
              └───────────────────┘
                    │
                    │  返回
                    ▼
进程 A 继续  ────────────────────────────────►

关键推论： 如果在中断里调用 schedule()（睡眠的本质），调度器会去选下一个进程运行，而中断上下文本身没有被保存进任何可恢复的位置——它只是栈上的一段临时执行流，不属于任何 task_struct。于是：

  • 要么内核检测到非法调度 → BUG: scheduling while atomic → oops
  • 要么调度走了，中断永远无法返回 → 中断丢失、系统卡死

硬中断里不能调用的函数

类别 具体 原因
睡眠/调度 msleep、schedule、wait_event_*、ssleep 无调度实体
可能睡眠的分配 kmalloc(GFP_KERNEL)、vmalloc、kzalloc(GFP_KERNEL) 内存不足时会触发回收/睡眠
互斥锁 mutex_lock、down(&sem)、读写信号量 拿不到就睡
用户空间访问 copy_to_user、copy_from_user 可能缺页 → 睡眠；且不该访问用户地址空间
可能睡眠的同步 flush_work（不指定 WQ_MEM_RECLAIM 时） 会等待

反过来，中断里可以用的：

类别 具体
分配 kmalloc(GFP_ATOMIC)（不睡眠，失败立即返回 NULL）
同步 spinlock、atomic_*、bitops
记录 printk（但别刷屏，串口是慢设备）
调度下半部 tasklet_schedule、queue_work、IRQ_WAKE_THREAD 
/* 判错技巧：内核提供了断言 */
might_sleep();          /* 放在函数开头，若在原子上下文被调用会打印警告栈 */
in_interrupt();         /* 是否在中断上下文 */
in_atomic();            /* 是否在原子上下文（含持 spinlock） */

上半部 / 下半部：为什么必须切分

硬中断执行期间，同级/低优先级中断被屏蔽。 在这段时间里：

  • 系统不响应其他中断 → 丢中断（串口 FIFO 溢出、网卡丢包）
  • 其他 CPU 不受影响，但本 CPU 上的所有任务被推迟 → 延迟尖刺

所以铁律：上半部只做"不做就会丢数据"的事，其余推给下半部。

硬中断 top half（中断上下文，不能睡）
   ├─ 读硬件状态寄存器，判断是不是我的中断
   ├─ 清中断源（★ 必须，否则中断会反复触发）
   ├─ 把数据搬到内存（少量）
   └─ 调度下半部
            │
            ▼
下半部 bottom half（可以是内核线程，能睡）
   └─ 解析数据、调 I2C、唤醒用户进程、拷贝给用户
下半部机制 执行上下文 能睡眠 特点
softirq 软中断（中断下半部的底层） ❌ 静态注册，可并发在不同 CPU；网络收发用它
tasklet 基于 softirq ❌ 同一 tasklet 串行（不跨 CPU 并发），用起来简单
workqueue 内核线程 ✅ 可睡眠；schedule_work 用系统默认队列
threaded IRQ 专属内核线程 ✅ request_threaded_irq；现代推荐

现代建议： 直接用 request_threaded_irq()。它把"上半部快速处理 + 线程慢慢做"封装成一步，比手写 tasklet/workqueue 更不容易出错。详见 5.3。

HFT / 嵌入式关联

  • 中断处理时长 = 延迟尖刺的直接来源。 HFT 里做中断绑核（把网卡中断绑到隔离核之外）的本质，就是避免中断处理抢占关键线程。
  • NAPI 是"中断 + 轮询"的混合：网卡收到第一个包发中断，之后关中断转轮询把队列里的包一次性收完。这样既避免了"每包一中断"的开销，又不会像纯轮询那样空转。这是"上下半部"思想在网络栈的终极形态（见 12.5-modern-networking）。
  • GFP_ATOMIC 失败率高于 GFP_KERNEL —— 这是"不能睡"换来的代价：内存紧张时它宁可失败也不等待。高频路径要预先分配好缓冲池，别在中断里分配（HFT 里的内存池同理）。

代码自测

Q1：中断 handler 里 current 指向谁？能用它吗？

current 会指向被中断的那个进程，但这个进程与中断处理毫无关系（中断只是借用了它的内核栈）。 用它做任何判断都是错的 —— 比如"当前进程是不是 root"在中断里毫无意义。

Q2：为什么 kmalloc(GFP_KERNEL) 不能在中断里用，而 GFP_ATOMIC 可以？

GFP_KERNEL 允许在内存不足时触发页回收、回写、甚至等待 I/O，这些都可能睡眠。 GFP_ATOMIC 禁止睡眠：只用紧急保留池，不够就立刻返回 NULL。代价是失败率更高。

Q3：如果上半部忘了清中断源会怎样？

中断控制器认为"中断仍在处理"，该 IRQ 线持续有效 → 退出 handler 后立刻再次触发，陷入死循环，系统看起来卡死（dmesg 会被刷屏）。 所以"清中断"是上半部必须做的第一步 —— 尤其是电平触发（level-triggered）的中断。

5.2

锁怎么选：只看一件事——临界区能不能睡眠

本节讲什么： spinlock / mutex / atomic / RCU 的选型依据，以及"持自旋锁睡眠会死锁"到底怎么发生的。 决策树只有一问： 临界区里会不会调用可能睡眠的函数？ 前置： 5.1 中断上下文
卡住查书： LDD3 Ch5 · Madieu Ch3、Ch16

决策树

临界区里会睡眠吗？（调 I2C/SPI、access_user、kmalloc(GFP_KERNEL)、msleep）
   │
   ├─ 会  ──► mutex（或 rt_mutex / semaphore）
   │
   └─ 不会 ──► 会不会在中断上下文里执行？
                   │
                   ├─ 会  ──► spinlock（+ 必要时 spin_lock_irqsave）
                   │
                   └─ 不会 ──► 临界区多长？
                                 ├─ 极短（几条指令）──► atomic_t / bitops
                                 ├─ 短 ──────────────► spinlock
                                 └─ 读多写少 ────────► rwlock / seqlock / RCU

最快的锁是不加锁。 优先考虑：per-CPU 变量、无锁环形缓冲、RCU —— 把共享拆成不共享。

spinlock vs mutex 正面对比

spinlock_t mutex
拿不到时 忙等（原地打转，CPU 100%） 睡眠（让出 CPU）
能否在中断上下文用 ✅ ❌
持有期间能否睡眠 ❌ 严禁 ✅ 可以
临界区长度 必须极短 可以长
开销 小（几条原子指令） 大（可能睡眠/唤醒，上下文切换）
递归获取 死锁（不递归） 死锁（不递归）
适用 中断 handler、短临界区、数据结构自洽更新 进程上下文、可能调 I2C/SPI 的操作 
/* mutex：可以睡，可以调 I2C */
static int my_read_reg(struct my_dev *dev, u8 reg, u8 *val)
{
    mutex_lock(&dev->lock);            /* 拿不到就睡 */
    *val = i2c_smbus_read_byte_data(dev->client, reg);  /* 会睡眠，OK */
    mutex_unlock(&dev->lock);
    return 0;
}

/* spinlock：中断里用，临界区极短 */
static irqreturn_t my_handler(int irq, void *p)
{
    struct my_dev *dev = p;
    unsigned long flags;

    spin_lock_irqsave(&dev->slock, flags);   /* 关中断 + 拿锁，一步到位 */
    dev->irq_count++;
    spin_unlock_irqrestore(&dev->slock, flags);
    return IRQ_WAKE_THREAD;
}

为什么持自旋锁睡眠 = 死锁

CPU0: 进程 P 拿到 spinlock，然后调用 copy_to_user（睡眠）
      → P 被挂起，但锁还握在手里
CPU1: 另一个进程 Q 想拿同一把锁
      → 自旋等待（不睡眠，因为它是 spinlock）
      → 在**抢占式内核**上，Q 占着 CPU 空转
      → P 永远等不到 CPU 来释放锁
      → 两核一起卡死

单核 + 非抢占内核下，Q 自旋时没法让出 CPU，同样卡死。所以内核有 CONFIG_DEBUG_ATOMIC_SLEEP 专门抓这类 bug。

spinlock 的三个变体（选错就是死锁或丢中断）

变体 做的事 用在哪
spin_lock / spin_unlock 只拿锁 仅进程上下文，且确定不会有中断来抢同一把锁
spin_lock_irqsave / irqrestore 关本地中断 + 保存 flags + 拿锁 进程与中断共享数据时（最常用、最安全）
spin_lock_bh / unlock_bh 关下半部（softirq），不关硬中断 只与 tasklet/softirq 竞争时 
/* 为什么中断 handler 里必须用 irqsave 版本？ */
spin_lock(&lock);        /* 只拿锁，不关中断 */
    /* 此时本 CPU 来了同一个中断 → handler 也 spin_lock 同一把锁 */
    /* → 自己等自己，永久自旋 —— 死锁 */

更快的选项

场景 用
只改一个计数器 atomic_inc(&c) / atomic64_t
只置位/清位 set_bit / clear_bit（原子位操作）
每 CPU 一份数据 DEFINE_PER_CPU / this_cpu_*（无需加锁）
读极多、写极少 seqlock（读不加锁，靠序号重试）或 RCU
单生产者单消费者环形缓冲 无锁（内存屏障 + smp_store_release/smp_load_acquire）

HFT / 嵌入式关联

  • per-CPU 数据结构避免加锁，这个招式在 HFT 用户态无锁队列里是同一个内核：把共享拆成每核一份，写入本地、读取合并，彻底消除争用（见 14-hft-engineering）。
  • spin_lock_irqsave 的代价是关中断 —— 关中断期间本 CPU 无法响应任何中断，直接制造延迟尖刺。HFT 里"中断绑核 + 关键线程绑核"就是在物理上隔离这两种争用。
  • RCU 的思想（读者不加锁、写者延迟回收）在无锁数据结构里反复出现。理解 RCU 对写高性能并发代码帮助极大。

代码自测

Q1：临界区里要调 i2c_transfer（会睡眠），该用哪种锁？

mutex。 I2C 传输会睡眠，spinlock 持有期间禁止睡眠 → 只能用 mutex。 这也意味着这段代码不能在中断 handler 里执行，必须放到下半部线程（workqueue / threaded IRQ）。

Q2：spin_lock_irqsave 比 spin_lock 多做了什么？为什么中断里必须用它？

多做了关本地中断 + 保存中断状态到 flags。 如果只 spin_lock 不关中断：进程上下文拿着锁时，本 CPU 来了中断，handler 也请求同一把锁 → 自己等自己，永久自旋。 irqsave 关掉中断后，handler 根本不会在本 CPU 上跑，竞争消失。

Q3：什么情况下连 spinlock 都不需要？
  • 数据是 per-CPU 的（每核一份，天然无竞争）；
  • 操作本身是原子的（atomic_t、原子位操作）；
  • 单生产者单消费者的环形缓冲（配合内存屏障）。

"最快的锁是不加锁" —— 能拆成不共享就别加锁。

5.3

threaded IRQ 实践：现代中断处理的默认姿势

本节讲什么： 用 request_threaded_irq() 把中断拆成"硬中断快速判断 + 内核线程慢慢做"，以及如何拿到中断号、设为唤醒源、绑核、调试。 为什么推荐它： 比自己搭 tasklet/workqueue 更安全；handler 里不睡、线程里随便睡，边界天然清晰。 前置： 5.1 中断上下文 · 5.2 锁的选型
卡住查书： Madieu Ch16 · LDD3 Ch10

为什么需要它

传统写法：上半部干活、下半部用 tasklet 或 workqueue。问题是要自己管理两套机制，容易出错。

request_threaded_irq 把这个模式内建：内核为你的 IRQ 起一个专属内核线程，handler 返回 IRQ_WAKE_THREAD 就唤醒它。

硬中断 handler (my_handler)      ← 中断上下文：不能睡
   ├─ 判断是不是我的中断（读状态寄存器）
   ├─ 清中断
   └─ return IRQ_WAKE_THREAD
              │
              ▼  内核唤醒专属线程
IRQ 线程 (my_thread)             ← 进程上下文：可以睡
   └─ 读 I2C 数据、mutex_lock、copy_to_user、唤醒等待队列

额外好处： 线程有 task_struct，可以被 chrt 提优先级、可以绑核、可以被调试器看到。这在实时性调优时非常有用。

返回值（三选一）

返回值 含义 后果
IRQ_NONE 不是我的中断（共享 IRQ 时常见） 内核继续问下一个共享者
IRQ_HANDLED 已处理完，不需要线程 线程不唤醒
IRQ_WAKE_THREAD 已做紧急处理，请唤醒线程 线程被调度执行

完整示例（含设备树取中断号）

DTS 侧：

mydev@fe200000 {
    compatible = "wzp,my-device";
    reg = <0x0 0xfe200000 0x0 0x1000>;
    interrupts = <GIC_SPI 32 IRQ_TYPE_LEVEL_HIGH>;   /* 或 IRQ_TYPE_EDGE_FALLING */
    interrupt-names = "data";
};

驱动侧：

static irqreturn_t my_handler(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;
    u32 status;

    status = readl(dev->base + REG_STATUS);
    if (!(status & IRQ_MINE))
        return IRQ_NONE;              /* 共享中断：不是我的 */

    writel(status & IRQ_MINE, dev->base + REG_CLEAR);   /* ★ 清中断，必须 */
    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;

    mutex_lock(&dev->lock);                 /* 可以睡眠 */
    /* 读数据、调 I2C/SPI、解析 */
    mutex_unlock(&dev->lock);

    wake_up_interruptible(&dev->wq);        /* 唤醒等待的用户进程 */
    return IRQ_HANDLED;
}

/* probe 里注册 —— 中断号来自设备树，不硬编码 */
static int my_probe(struct platform_device *pdev)
{
    struct my_dev *dev;
    int irq;

    irq = platform_get_irq(pdev, 0);        /* 从 DT 的 interrupts 属性解析 */
    if (irq < 0)
        return dev_err_probe(&pdev->dev, irq, "no irq");

    ret = devm_request_threaded_irq(&pdev->dev, irq,
                                    my_handler, my_thread,
                                    IRQF_TRIGGER_HIGH | IRQF_ONESHOT,
                                    "mydev", dev);
    if (ret)
        return dev_err_probe(&pdev->dev, ret, "request irq failed");
    return 0;
}

IRQF_ONESHOT 是什么

线程处理完之前，保持该中断线屏蔽。 对电平触发中断几乎是必需的：

  • 电平触发：只要硬件引脚还是高电平，中断就持续有效。若线程还没跑完就放开中断线，会立刻重复触发。
  • IRQF_ONESHOT 让内核在 handler 返回后保持屏蔽，直到线程执行完才 unmask。

边沿触发通常不需要，但加上无害且更安全。

常用 flag

flag 作用
IRQF_SHARED 多个设备共享同一 IRQ 线；dev_id 必须唯一（用于卸载时区分）
IRQF_ONESHOT 线程执行完前保持中断屏蔽（电平触发必加）
IRQF_TRIGGER_HIGH/LOW/RISING/FALLING 触发方式；通常从 DT 读，不写死
IRQF_NOBALANCING 禁止内核自动均衡该中断到其他 CPU（做绑核隔离时用）

# 提线程优先级

HFT / 嵌入式关联

  • 中断绑核是低延迟的标准动作：把网卡/存储中断绑到非关键核，让交易线程所在的核不被中断打扰。/proc/irq/N/smp_affinity 就是入口（配合 isolcpus 启动参数）。
  • threaded IRQ 的线程可以被 chrt 提优先级 —— 这是普通 tasklet 做不到的（tasklet 没有 task_struct）。实时性调优时这是关键差异。
  • NAPI 与 threaded IRQ 是两种思路：NAPI 靠"关中断转轮询"减少中断次数；threaded IRQ 靠"线程化"让长工作可睡眠。网卡走 NAPI，普通外设走 threaded IRQ（见 12.5-modern-networking）。

代码自测

Q1：handler 返回 IRQ_NONE 会怎样？

告诉内核"这不是我的中断"。共享 IRQ 时内核会继续调用链上的下一个 handler。 如果所有人都返回 IRQ_NONE，内核记一次 spurious interrupt（可在 /proc/irq/N/spurious 看到）。

Q2：电平触发的中断为什么几乎必须加 IRQF_ONESHOT？

电平触发下，只要硬件引脚保持有效电平，中断控制器就持续认为有中断。 若 handler 一返回就放开中断线，中断会立刻再次触发，而线程还没来得及清掉硬件状态 → 反复触发甚至死循环。 IRQF_ONESHOT 让中断线保持屏蔽，直到线程跑完（这时硬件状态已清）。

Q3：中断号能从设备树拿，为什么不要硬编码？

中断号在不同 SoC / 不同板卡上编号规则不同（GIC SPI 编号、GPIO 转中断的映射都是动态的）。 硬编码的号换个板子就错，而且不报错——只是中断永远不触发，非常难查。 platform_get_irq() 从 DT 的 interrupts 属性解析，是唯一正确做法。
