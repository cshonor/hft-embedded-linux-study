导读

本节讲什么： 内核里最基础、也是最能说明"用户态 syscall 如何落到驱动"的一类驱动。 对应动手： P5 · C1（GPIO 字符设备 + DTS + DT overlay，userspace 能 open/read/ioctl）

要点

概念 说明
主/次设备号 主号定位驱动，次号定位具体设备。dev_t = 主<<20 | 次
file_operations 驱动实现的回调集合：open/read/write/release/unlocked_ioctl/mmap…
设备节点 /dev/xxx 由 mknod 或 udev/mdev 创建；节点本身只是"号码 + 名字"的映射
用户/内核数据边界 不能直接解引用用户指针！用 copy_to_user / copy_from_user
inode vs file inode 是"这个设备"，file 是"这一次打开"（可有多次打开、各自 offset）

syscall → 驱动的完整路径

用户态 fd = open("/dev/foo", O_RDWR)
   ↓ glibc → syscall → 内核 sys_open
   ↓ VFS 查 inode 的 i_rdev → 主设备号 → 找到注册的 cdev
   ↓ cdev->ops->open(inode, filp)
返回 fd（内核里是 struct file *）

这条链要能默出来 —— 它是"用户态/内核态"这个抽象的具体接缝。

骨架

static dev_t devno;
static struct cdev my_cdev;
static struct class *my_class;

static int my_open(struct inode *inode, struct file *filp) { return 0; }
static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t len, loff_t *off)
{
    /* 必须用 copy_to_user，不能 memcpy 到用户指针 */
    return 0;
}
static long my_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
    /* cmd 用 _IOW/_IOR/_IOWR 构造，带 size 编码，天然防错 */
    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .read = my_read,
    .unlocked_ioctl = my_ioctl,
};

现代写法： 用 alloc_chrdev_region 动态申请设备号（别硬编码主号），配合 device_create 让 udev 自动建节点。

HFT / 嵌入式关联

  • ioctl 是控制面：数据面不该走 read/write（一次 syscall 一次拷贝）。HFT 里数据面走 mmap + 轮询（见 06-dma-mmap）。
  • copy_to_user 的开销 就是"用户态/内核态边界"的具象成本——这正是内核旁路技术要消灭的东西。

2.1

主次设备号：内核怎么从一个 `/dev/xxx` 找到你的驱动

本节讲什么： ls -l /dev/ttyS0 里那两个数字是什么、为什么不能硬编码、以及现代内核为什么放弃静态申请。 前置： 01-hello-module（insmod 能跑通）
后续： 2.2 open() 如何落到驱动 · 2.3 用户/内核边界
卡住查书： Madieu Ch4 · LDD3 Ch3

从一个现象说起

$ ls -l /dev/ttyS0 /dev/null /dev/sda
crw-rw---- 1 root dialout   4,  64  ttyS0
crw-rw-rw- 1 root root      1,   3  null
brw-rw---- 1 root disk      8,   0  sda

开头 c = 字符设备，b = 块设备。后面那两个数字就是本篇主角：

值 含义
主设备号（major） 4 哪个驱动 — 内核用它索引驱动表
次设备号（minor） 64 这个驱动的第几个设备 — 驱动自己解释

比喻：主设备号 = 快递公司（顺丰/中通），次设备号 = 你在这家公司的会员编号。
内核看主号决定"派给谁"，驱动看次号决定"具体操作哪个硬件实例"。

注意 sda 是 8, 0 —— 块设备也用同一套编号空间，但主号 8 对应的是块驱动，与字符驱动互不冲突（两套独立的表）。

内核里的表示：dev_t

dev_t 是 32 位整数，切分方式（include/linux/kdev_t.h）：

#define MINORBITS    20
#define MINORMASK    ((1U << MINORBITS) - 1)

#define MAJOR(dev)   ((unsigned int) ((dev) >> MINORBITS))   /* 高 12 位 */
#define MINOR(dev)   ((unsigned int) ((dev) & MINORMASK))    /* 低 20 位 */
#define MKDEV(ma,mi) (((ma) << MINORBITS) | (mi))

   31                    20 19                          0
   ┌───────────────────────┬──────────────────────────────┐
   │   major (12 bit)      │      minor (20 bit)          │
   └───────────────────────┴──────────────────────────────┘

主号只有 12 位 = 最多 4096 个驱动，而且静态分配的主号早就耗尽了（Documentation/admin-guide/devices.txt 里能看到一堆历史遗留）。所以现在必须动态申请。

两套申请方式

静态 register_chrdev_region 动态 alloc_chrdev_region（用这个）
用法 你指定主号 内核挑一个没占用的给你
风险 冲突则失败，且不同机器占用情况不同 无冲突
能否提前 mknod 可以（号固定） 不行 → 必须配合 device_create 让 udev 自动建节点
现状 教学用 / 老代码 现代写法 
static dev_t devno;          /* 申请到的设备号 */
static int major;

/* 动态申请：baseminor=0，count=2，名字出现在 /proc/devices */
alloc_chrdev_region(&devno, 0, 2, "mydev");
major = MAJOR(devno);
printk("mydev: major=%d minor0=%d\n", major, MINOR(devno));

卸载时一定要还回去：

unregister_chrdev_region(devno, 2);

设备节点从哪来

节点（/dev/mydev）本身只是「名字 + 设备号」的映射，不是驱动的一部分。三种产生方式：

方式 命令/API 适用
手工 mknod /dev/mydev c 240 0 调试、动态主号时很痛苦
devtmpfs + udev 内核 device_create() 发 uevent → udev 建节点 现代标准
devtmpfs 自动 内核启动时自动为已注册设备建 大部分情况够用

现代驱动只要在 probe/init 里：

my_class = class_create("mydev");                    /* /sys/class/mydev/ */
device_create(my_class, NULL, devno, NULL, "mydev%d", 0);  /* -> /dev/mydev0 */

这样不需要知道主号是多少，udev 会读 sysfs 里的 dev 属性自动创建。

常见坑

现象 原因
mknod 后 open 报 ENODEV (No such device) 节点的主号与驱动实际注册的不一致（动态分配后你还在用旧号）
open 报 EACCES 节点权限问题，与驱动无关；检查 ls -l 或 udev 规则
cat /proc/devices 里有但 /dev 下没有 只注册了驱动，没建节点（device_create 没调用或 udev 没跑）
卸载后 /dev/mydev0 还在 没调 device_destroy

HFT / 嵌入式关联

  • /dev 这套"名字 → 号 → 驱动"的间接层，是一切皆文件的代价：每次 open/read 都要走 VFS 查找。HFT 里数据面避开它的办法就是 mmap 一次映射、之后直接访存（见 06-dma-mmap）。
  • 次设备号的语义由驱动自己定义 —— 这个"内核只管分发、解释权归驱动"的模式，在设备树 compatible、在 netlink 协议号、在 PCIe 的 class code 上反复出现。理解一次，后面到处都能认出来。

代码自测

Q1：主设备号 12 位、次设备号 20 位，那 MKDEV(4, 64) 的值是多少？

4 << 20 | 64 = 4194304 + 64 = 4194368。 反推：MAJOR(4194368) = 4，MINOR(4194368) = 64。

Q2：动态申请主号后，为什么不能提前 mknod？

因为主号是内核在 alloc_chrdev_region 时临时决定的，每次加载可能不同（取决于当时哪些号空闲）。提前 mknod 写死一个号，下次加载就可能对不上 → open 返回 ENODEV。 正确做法是让 device_create 通知 udev 动态建节点。

Q3：同一个驱动管理 4 个相同硬件，需要几个主设备号？

1 个主号 + 4 个次号。主号标识驱动，次号 0–3 由驱动自己解释成"第几个硬件"。 申请时 count 传 4：alloc_chrdev_region(&devno, 0, 4, "mydev")。

2.2

`open()` 是怎么落到驱动的：一条必须能默出来的路径

本节讲什么： 从用户态 fd = open("/dev/mydev", O_RDWR) 到驱动里 my_open() 被执行的完整调用链。 为什么重要： 这是「用户态 / 内核态」这条抽象线的具体接缝。默不出来，后面 read/ioctl/mmap 全是黑盒。 前置： 2.1 主次设备号
卡住查书： LDD3 Ch3 · Madieu Ch4

全景图

用户态                          内核态
─────────────────────────────  ──────────────────────────────────────
fd = open("/dev/mydev", O_RDWR)
  │
  │  glibc 封装
  ▼
syscall(SYS_openat, ...)  ──►  sys_openat()            [fs/open.c]
                                 │
                                 │  1. 路径查找
                                 ▼
                          path_openat() → 逐段解析 "/dev/mydev"
                                 │
                                 │  2. 找到 inode
                                 ▼
                          ┌──────────────────────┐
                          │  inode (磁盘/devtmpfs)│
                          │   i_rdev = dev_t      │ ← 主/次设备号
                          │   i_fop  = &def_chr_fops│
                          └──────────────────────┘
                                 │
                                 │  3. 字符设备专用 open
                                 ▼
                          chrdev_open()            [fs/char_dev.c]
                                 │  ├─ 用 i_rdev 查 cdev 表（主号索引）
                                 │  └─ 找到驱动的 cdev
                                 │
                                 │  4. 换掉 fops！！
                                 ▼
                          filp->f_op = cdev->ops    ← ★ 关键一步
                                 │
                                 ▼
                          filp->f_op->open(inode, filp)
                                 │
                                 ▼
                          驱动的 my_open(inode, filp)   ← 你写的代码
                                 │
                                 ▼  返回 0 → 分配 fd，返回用户态

★ 最关键的一步是 filp->f_op = cdev->ops。

inode->i_fop 原本指向 def_chr_fops（内核的通用字符设备占位），chrdev_open() 在查到真正的 cdev 后，把 file 结构的操作集整个换成了驱动自己的 file_operations。之后这个 fd 上的 read/write/ioctl 全部直接走驱动，不再经过 chrdev_open。

比喻：inode 是"这栋楼的门牌号"（持久、全局唯一），file 是"这一次拜访"（临时、可多次）。
第一次进门要查户口（chrdev_open 找驱动），认完人之后直接给你对方手机号（f_op 替换），下次打电话不用再查。

三个容易混的结构

结构 是谁 生命周期 关键字段
struct inode 文件/设备本身 持久，一个设备一个 i_rdev（设备号）、i_cdev
struct file 一次打开 open 到 close f_op、f_pos（读写偏移）、private_data
struct dentry 路径项（"/dev/mydev"） 缓存，可回收 路径解析用，驱动基本不碰

推论： 同一个设备被 open 两次 → 两个 struct file，各自独立的 f_pos，但共享一个 inode。

驱动里常用的：

static int my_open(struct inode *inode, struct file *filp)
{
    /* 从 inode 拿次设备号，判断是第几个硬件 */
    unsigned int minor = iminor(inode);

    /* 把设备私有数据挂到 filp 上，后面 read/write 直接取，不用再查 */
    filp->private_data = container_of(inode->i_cdev, struct my_dev, cdev);
    return 0;
}

fd 是什么

用户态拿到的是个小整数 fd，内核里其实是：

进程的 task_struct
   └── files (struct files_struct)
         └── fdt (fdtable)
               └── fd[] 数组
                     ├── fd 0 -> struct file*  (stdin)
                     ├── fd 1 -> struct file*  (stdout)
                     ├── fd 2 -> struct file*  (stderr)
                     └── fd 3 -> struct file*  ← 你的 /dev/mydev

所以 fd 就是进程 fdtable 的下标，内核通过它 O(1) 拿到 struct file *。这也是为什么 fd 不能跨进程用——每个进程有自己的 fdtable（fork 后是拷贝，dup 是共享同一个 struct file）。

怎么亲眼验证

# 1. 看用户态发起了哪些 syscall
strace -e trace=openat,read,ioctl,close ./myapp

# 2. 看内核里走了哪些函数（需要 CONFIG_FUNCTION_TRACER）
sudo trace-cmd record -p function_graph -g chrdev_open ./myapp
sudo trace-cmd report | head -40

# 3. 看进程打开了什么
ls -l /proc/$$/fd
cat /proc/$$/fdinfo/3        # 含 pos、flags

HFT / 嵌入式关联

  • 这条路径的开销就是「syscall 的成本」：用户/内核切换（栈切换 + 特权级切换）、路径查找、fdtable 查表、vfs 层函数调用。每一次 read() 都要重走一遍，这正是 HFT 数据面要消灭的对象。
  • 对比旁路方案（13-dpdk）：DPDK 的 PMD 驱动绕开整个 VFS + 协议栈，用户态直接轮询网卡 DMA 到的内存——省掉的就是上面这条链。
  • 但 ioctl/控制面必须走这条链：配置、状态查询用 syscall，数据面用 mmap 后的直接访存。这个「控制面走内核、数据面绕过」的切分是 HFT 的标准姿势。

代码自测

Q1：inode->i_fop 和 filp->f_op 是同一个东西吗？

不是，而且这是本节的核心。 - inode->i_fop 最初指向 def_chr_fops（内核占位）； - chrdev_open() 查到驱动的 cdev 后，执行 filp->f_op = fops_get(cdev->ops)，把 file 的操作集替换成驱动的； - 之后该 fd 上的所有操作都走驱动的 file_operations。

Q2：同一设备 open 两次，f_pos 是共享的还是独立的？

独立的。 每次 open 创建新的 struct file，各有自己的 f_pos。 两个 fd 各自 read，偏移互不干扰 —— 与 dup() 相反，dup 共享同一个 struct file，因此共享 f_pos。

Q3：驱动怎么知道用户这次打开的是哪个硬件实例？

从 inode 取次设备号：iminor(inode) 或 MINOR(inode->i_rdev)。 典型做法是在 open 里用 container_of(inode->i_cdev, struct my_dev, cdev) 拿到设备结构体，存进 filp->private_data，后续 read/write 直接取用。

2.3

用户态 / 内核态的数据边界：为什么不能直接解引用用户指针

本节讲什么： copy_to_user / copy_from_user 存在的理由，以及怎么写才不会踩坑。 一句话： 用户传进来的指针，在内核里就是个不可信的整数。直接用 = 内核崩或被打穿。 前置： 2.2 open() 的路径
卡住查书： LDD3 Ch3、Ch6 · Madieu Ch4

为什么不能 memcpy(buf, ...)

用户态传给 read(fd, buf, len) 的 buf 是一个用户空间虚拟地址。内核不能直接解引用，四个理由：

# 理由 后果
1 地址空间不同 内核与用户进程页表不同；同一个数值在两边指向完全不同的物理页（swapper_pg_dir vs 进程 pgd）
2 页可能不在内存 用户页可能被换出到磁盘，解引用会触发缺页；内核态缺页处理受限，可能直接 oops
3 可能是恶意地址 用户故意传 0x0 或内核地址 → 内核读写自己的数据 = 提权漏洞
4 SMAP / SMEP 硬件拦截 现代 CPU（x86 SMAP、ARM PAN）硬件禁止内核访问用户页；绕过需临时关标志，只有 copy_*_user 有这个权限

比喻：用户给你一张纸条写着"仓库 A 区 3 号货架"——这是用户仓库的编号体系。你在内核仓库里照着找，找到的是别人的东西，甚至可能是承重墙（崩溃）。
正确做法是走正规搬运通道（copy_*_user）：它会先核对权限、处理缺页、搬完再报告结果。

正确写法

批量拷贝

static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t len, loff_t *off)
{
    char kbuf[64];
    size_t n = min(len, sizeof(kbuf));

    /* ... 填充 kbuf ... */

    /* 返回「没拷成功的字节数」，0 才是成功 */
    if (copy_to_user(buf, kbuf, n))
        return -EFAULT;          /* 用户给的 buf 有问题 */

    *off += n;
    return n;                     /* 返回值 = 实际读取字节数 */
}

注意 __user 注解：它不做任何运行时检查，是给 sparse 静态分析工具看的，用来抓"忘了 copy 就解引用"的 bug。编译内核时 make C=1 会跑。

单值拷贝

int val;
if (copy_from_user(&val, (int __user *)arg, sizeof(val)))
    return -EFAULT;
/* 或更简洁： */
get_user(val, (int __user *)arg);     /* 单值版本 */
put_user(val, (int __user *)arg);

返回值陷阱（最容易写错的地方）

函数 返回 判断
copy_to_user / copy_from_user 未拷贝成功的字节数 != 0 即失败 → 返回 -EFAULT
get_user / put_user 0 成功，-EFAULT 失败 != 0 即失败
access_ok() 布尔（地址是否合法） 通常不用手动调，copy_*_user 内部已做 
/* 错：把"剩余字节数"当成返回值传给用户 */
return copy_to_user(buf, kbuf, n);      /* 成功时返回 0，用户以为读到 0 字节 */

/* 对 */
if (copy_to_user(buf, kbuf, n))
    return -EFAULT;
return n;

什么时候可以直接访问用户内存

三种例外，都需要显式"打开通道"：

场景 API 说明
mmap 之后 remap_pfn_range / vm_insert_page 内核内存映射到用户空间，两边看到同一块物理页 → 无拷贝（见 06-dma-mmap）
临时借用用户缓冲 get_user_pages() → kmap() 钉住用户页再映射到内核；用完必须 put_page
大块且需要零拷贝 splice / sendfile 内核内部管道搬运，不经过用户态

HFT / 嵌入式关联

  • copy_to_user 的开销 = 一次内存拷贝 + 边界检查，这就是"内核旁路"要消灭的成本之一。DPDK 的做法是启动时 mmap 一次，之后所有数据收发都在用户态直接访存，运行期零 copy、零 syscall。
  • 控制面 vs 数据面的切分标准就是看数据量：几字节的配置用 ioctl（走 copy），几 MB 的报文流用 mmap + 轮询（不走 copy）。
  • 这个"拷贝即边界"的思想在系统里到处都是：TLB shootdown、DMA bounce buffer、甚至 HFT 里的无锁队列跨核传递——凡是跨越信任边界，都得付一份搬运费。

代码自测

Q1：copy_to_user 返回 5 是什么意思？

还有 5 个字节没拷成功（用户给的缓冲区非法或访问时缺页失败）。 约定俗成的处理是返回 -EFAULT 给用户态，让 read() 失败并置 errno = EFAULT。

Q2：__user 这个修饰符有运行时作用吗？

没有。 它只是给 sparse 静态检查工具的注解，编译后完全消失。 作用是让 make C=1 / make C=2 能抓出"把用户指针当内核指针直接用"的错误。写上它是好习惯，成本为零。

Q3：为什么 mmap 之后就不需要 copy_to_user 了？

因为 mmap 把同一块物理页同时映射进内核和用户地址空间，两边访问的是同一内存，根本不存在"搬运"。 但代价是没有同步保护——需要自己用锁或内存序保证一致性（见 05-irq-locking）。

ioctl 命令编码 + 现代字符设备注册（可直接抄的骨架）

本节讲什么： ioctl 的 cmd 为什么不能直接写 1/2/3，以及一份能编过、能跑的现代字符设备完整骨架。 前置： 2.1 主次设备号 · 2.3 用户/内核边界
卡住查书： Madieu Ch4 · LDD3 Ch6

一、ioctl 的 cmd 不是随便一个整数

内核规定 cmd 是一个 32 位编码，四个字段：

  31     30   29       16 15        8 7             0
  ┌──────┬────┬──────────┬──────────┬───────────────┐
  │ dir  │    │   size   │   type   │      nr       │
  │ 2bit │    │  14 bit  │  8 bit   │     8 bit     │
  └──────┴────┴──────────┴──────────┴───────────────┘
    方向      数据大小     魔数(类型)    序号

用宏构造（include/uapi/asm-generic/ioctl.h）：

宏 方向 用途
_IO(type, nr) 无数据 纯命令，如"复位"
_IOR(type, nr, datatype) 内核 → 用户 读配置
_IOW(type, nr, datatype) 用户 → 内核 写配置
_IOWR(type, nr, datatype) 双向 传参并返回 
/* mydev.h —— 驱动与用户态共用 */
#define MYDEV_MAGIC  'k'                                  /* 魔数，挑个没人用的字符 */

#define MYDEV_RESET    _IO (MYDEV_MAGIC, 0)
#define MYDEV_GET_VAL  _IOR(MYDEV_MAGIC, 1, int)
#define MYDEV_SET_VAL  _IOW(MYDEV_MAGIC, 2, int)
#define MYDEV_XFER     _IOWR(MYDEV_MAGIC, 3, struct mydev_xfer)

为什么必须这样编：

好处 说明
大小写进命令 内核可校验 arg 指向的缓冲区够不够，防止越界
方向写进命令 内核检查用户指针的读写权限是否匹配
魔数隔离 命令发到错误的设备时，驱动能识别"这不是我的命令"并返回 ENOTTY
32/64 位兼容 compat_ioctl 能根据 size 字段自动转换结构体布局

如果你写 ioctl(fd, 1, ...) 这种裸数字：命令冲突、越界、跨平台全都要自己扛。

驱动侧实现

static long my_unlocked_ioctl(struct file *filp, unsigned int cmd,
                              unsigned long arg)
{
    struct my_dev *dev = filp->private_data;
    int val;

    /* 1. 校验魔数（不是我的命令 -> ENOTTY） */
    if (_IOC_TYPE(cmd) != MYDEV_MAGIC)
        return -ENOTTY;

    switch (cmd) {
    case MYDEV_RESET:
        dev->val = 0;
        return 0;

    case MYDEV_GET_VAL:
        val = dev->val;
        if (put_user(val, (int __user *)arg))
            return -EFAULT;
        return 0;

    case MYDEV_SET_VAL:
        if (get_user(val, (int __user *)arg))
            return -EFAULT;
        dev->val = val;
        return 0;

    default:
        return -ENOTTY;      /* 未知命令 */
    }
}

注意： 现代用 .unlocked_ioctl（不持 BKL），不要再用老的 .ioctl。

二、现代注册骨架（可直接抄）

// mydev.c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/uaccess.h>
#include "mydev.h"

#define DEV_NAME "mydev"
#define DEV_CNT  2

struct my_dev {
    struct cdev cdev;
    int val;
};

static struct my_dev  mydevs[DEV_CNT];
static dev_t          devno_base;
static struct class  *my_class;

static int my_open(struct inode *inode, struct file *filp)
{
    /* 从 inode 反推设备结构体，挂到 filp 上供后续使用 */
    filp->private_data = container_of(inode->i_cdev, struct my_dev, cdev);
    return 0;
}
static int my_release(struct inode *inode, struct file *filp) { return 0; }

static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t len, loff_t *off)
{
    struct my_dev *dev = filp->private_data;
    int v = dev->val;
    if (*off > 0) return 0;                     /* 简单示例：读完一次返回 0 */
    if (copy_to_user(buf, &v, sizeof(v))) return -EFAULT;
    *off += sizeof(v);
    return sizeof(v);
}

static const struct file_operations my_fops = {
    .owner          = THIS_MODULE,
    .open           = my_open,
    .release        = my_release,
    .read           = my_read,
    .unlocked_ioctl = my_unlocked_ioctl,
};

static int __init my_init(void)
{
    int i, ret;

    /* 1. 动态申请设备号（count 个次设备号） */
    ret = alloc_chrdev_region(&devno_base, 0, DEV_CNT, DEV_NAME);
    if (ret < 0) return ret;

    /* 2. 创建 class -> /sys/class/mydev/ */
    my_class = class_create(DEV_NAME);
    if (IS_ERR(my_class)) { ret = PTR_ERR(my_class); goto err_region; }

    /* 3. 每个次设备号：初始化 cdev + 加入内核 + 建 /dev 节点 */
    for (i = 0; i < DEV_CNT; i++) {
        cdev_init(&mydevs[i].cdev, &my_fops);
        mydevs[i].cdev.owner = THIS_MODULE;
        ret = cdev_add(&mydevs[i].cdev, MKDEV(MAJOR(devno_base), i), 1);
        if (ret) goto err_cdev;

        device_create(my_class, NULL,
                      MKDEV(MAJOR(devno_base), i), NULL, "mydev%d", i);
    }
    pr_info("mydev: major=%d\n", MAJOR(devno_base));
    return 0;

err_cdev:
    while (i-- > 0) {
        device_destroy(my_class, MKDEV(MAJOR(devno_base), i));
        cdev_del(&mydevs[i].cdev);
    }
    class_destroy(my_class);
err_region:
    unregister_chrdev_region(devno_base, DEV_CNT);
    return ret;
}

static void __exit my_exit(void)
{
    int i;
    for (i = 0; i < DEV_CNT; i++) {
        device_destroy(my_class, MKDEV(MAJOR(devno_base), i));
        cdev_del(&mydevs[i].cdev);
    }
    class_destroy(my_class);
    unregister_chrdev_region(devno_base, DEV_CNT);
}

module_init(my_init);
module_exit(my_exit);
MODULE_LICENSE("GPL");

obj-m += mydev.o
KDIR ?= /lib/modules/$(shell uname -r)/build
all:
    make -C $(KDIR) M=$(PWD) modules
clean:
    make -C $(KDIR) M=$(PWD) clean

三、init / exit 的顺序（背下来）

init:  alloc_chrdev_region  →  class_create  →  cdev_add  →  device_create
exit:  device_destroy       ←  cdev_del      ←  class_destroy ← unregister_chrdev_region

铁律：exit 是 init 的逆序。 顺序错了会导致：节点还在但驱动没了（访问即崩）、或 cdev 已删但还在被引用（use-after-free）。

HFT / 嵌入式关联

  • ioctl 是控制面：数据量小、需要权限校验、频率低 → 走 syscall 完全够。
  • 数据面不走这里：一次 read() = 一次 syscall + 一次 copy_to_user。高频采样/报文收发必须 mmap（06-dma-mmap）。
  • container_of(inode->i_cdev, ...) 这个"从内嵌成员反推外层结构"的技法是内核的通用套路，在 list_head、kobject、work_struct 上到处都是 —— 值得单独吃透（01-c-language struct 向）。

代码自测

Q1：_IOW('k', 2, int) 里编码了哪些信息？

魔数 'k'（8 bit）、序号 2（8 bit）、数据大小 sizeof(int) = 4（14 bit）、方向 = 用户写向内核（2 bit）。 内核据此校验：命令是否属于本设备、缓冲区大小是否匹配、用户指针是否可写。

Q2：ioctl 返回 -ENOTTY 是什么含义？

"这不是我的命令"。当魔数不匹配或 switch 落到 default 时返回它， 用户态会看到 errno = ENOTTY（Inappropriate ioctl for device）。这是约定俗成的返回值，不要返回 -EINVAL。

Q3：cdev_add 之后能立刻 open 这个设备吗？

能，但有风险。 cdev_add 一返回，设备就"活"了，内核可能立刻收到 open。 所以必须保证 cdev_add 之前所有初始化都已完成（数据结构填好、硬件就绪）。 同理 device_create 要在最后，否则节点先出现而驱动还没准备好。
