# 3.3 · DTB 的一生：从 DTS 到 platform_device

> **本节讲什么：** 一个 `.dts` 文本文件，怎么变成内核里一颗 `device_node` 树，又怎么变成 `platform_device` 触发你的 `probe()`。以及**板子上到底跑的是哪个 DTB**——这个问题必须先有答案，否则改半天改的不是在跑的那棵树。

---

## 完整链路

```
   arch/arm64/boot/dts/.../bcm2712-rpi-5-b.dts    ← 人写的文本
                  │  dtc（设备树编译器）
                  ▼
   bcm2712-rpi-5-b.dtb                            ← 二进制 blob（扁平化 = FDT）
                  │  固件/ bootloader 加载到内存
                  │  启动内核时把 DTB 物理地址放进寄存器（arm64: x0）
                  ▼
   setup_arch() → unflatten_device_tree()          ← 展开成 device_node 树
                  ▼
   of_platform_populate()                          ← 扫树，建 platform_device
                  ▼
   platform_bus 匹配 → driver->probe()
```

**关键认知：** DTB 是**扁平化**的（Flattened Device Tree，所以叫 FDT）——它是线性的字节流，不是树形结构。内核启动时把它"展开"（unflatten）成内存里的树。这个名字本身就解释了为什么改 DTS 必须重新编译：内核不认识文本。

---

## 第二步最容易踩：不是所有节点都会变成 device

`of_platform_populate()` 递归扫树（`drivers/of/platform.c`），但有三道闸门：

| 闸门 | 源码位置 | 后果 |
|------|---------|------|
| `!of_device_is_available(np)` | `of_platform_device_create_pdata` | `status` 不是 `okay`/`ok` → **跳过** |
| `strict && !compatible` | `of_platform_bus_create` | 没有 `compatible` 属性 → **跳过** |
| `!of_match_node(matches, bus)` | `of_platform_bus_create` 末尾 | **父节点不在总线表里 → 不递归子节点** |

第三道是最阴的。看这段（v6.6 `drivers/of/platform.c:418`）：

```c
dev = of_platform_device_create_pdata(bus, bus_id, platform_data, parent);
if (!dev || !of_match_node(matches, bus))
    return 0;                    /* ← 不递归！子节点全不建 */

for_each_child_of_node(bus, child) {
    rc = of_platform_bus_create(child, matches, lookup, &dev->dev, strict);
    ...
}
```

也就是说：**你的节点挂在某个父节点下，如果父节点的 `compatible` 不在 `of_default_bus_match_table` 里，你这个子节点根本不会被创建成 device**，probe 永远不调用，且**没有任何报错**。

`status` 的判定也很直白（v6.6 `drivers/of/base.c:426`）：

```c
status = __of_get_property(device, "status", &statlen);
if (status == NULL)
    return true;                 /* 没写 status == 默认可用 */
if (statlen > 0) {
    if (!strcmp(status, "okay") || !strcmp(status, "ok"))
        return true;
}
return false;                    /* 其它一律不可用，包括 "disabled"、"fail-*" */
```

注意两件事：**不写 `status` 等于 `okay`**（不是等于 disabled）；**写错成 `ok` 以外的任何值（比如 `enable`、`OKAY`）都算不可用**——大小写敏感。

## 命名规则：为什么是 `fe200000.gpio` 这种怪名字

`of_device_make_bus_id()`（`drivers/of/platform.c:108`）拼的名字：

```c
reg = of_get_property(node, "reg", NULL);
if (reg && (addr = of_translate_address(node, reg)) != OF_BAD_ADDR) {
    dev_set_name(dev, "%llx.%pOFn", addr, node);   /* 地址.节点名 */
    return;
}
/* 地址翻译不了 → 往上找父节点，用 kbasename(full_name) 拼前缀 */
dev_set_name(dev, "%s:%s", kbasename(node->full_name), dev_name(dev));
```

所以 `/sys/bus/platform/devices/` 里看到的 `107d001000.serial` = 物理地址 `0x107d001000` + 节点名 `serial`。**地址前缀来自 `reg` 的翻译结果**，这也是为什么同名节点不会撞车。

## 第三步：运行时怎么查"现在跑的是哪棵树"

| 路径 | 是什么 |
|------|--------|
| `/sys/firmware/devicetree/base/` | 真正的运行时视图（device_node 树导出） |
| `/proc/device-tree` | 指向上面的**符号链接**（兼容老习惯） |

### 三板斧

**① 看节点在不在、compatible 对不对**

```bash
ls /proc/device-tree/
cat /proc/device-tree/mydev@fe200000/compatible
```

`compatible` 是**字符串列表**（多个串以 `\0` 分隔），直接 `cat` 会粘成一行。正确读法：

```bash
tr '\0' '\n' < /proc/device-tree/mydev@fe200000/compatible
# 输出：
# wzp,my-device
# generic-fallback-name
```

**② 反编译整棵树**

```bash
dtc -I fs -O dts /proc/device-tree > /tmp/running.dts
```

`-I fs` = 输入格式是文件系统（sysfs 视图）。这样得到的就是**内核实际看到的那棵树**，包含固件动态填充的（内存大小、MAC 地址等）——和你 `.dts` 源文件不一定一样。

**③ 反编译磁盘上的 DTB 文件**

```bash
dtc -I dtb -O dts /boot/bcm2712-rpi-5-b.dtb -o /tmp/disk.dts
diff /tmp/running.dts /tmp/disk.dts      # 差异就是固件改过的地方
```

**这个 diff 是 Pi 上最有诊断价值的一步。** 固件会按 `config.txt` 注入 overlay、改 `status`、填 MAC，你看到的运行树是"DTS 源文件 + 固件补丁"的合成结果。

## Pi 5 的特殊性

```
/config.txt
    ├── 决定用哪个 dtb：      device_tree=bcm2712-rpi-5-b.dtb（通常自动选）
    ├── overlay：             dtoverlay=xxx          ← 按顺序叠加，后面的覆盖前面的
    └── 参数：                dtparam=i2c_arm=on     ← 本质是改 status
```

**overlay 的顺序影响最终结果**，两个 overlay 改同一个属性的话后加载的赢。Pi 官方 `README`（`/boot/overlays/README`）是所有 `dtoverlay` 的权威文档。

⚠️ **Pi 5 的外设走 RP1（南桥，经 PCIe 挂）**，引脚叙事和 Pi 4 完全不同。**网上大量 Pi 4 教程直接抄到 Pi 5 上会失败**，尤其是 GPIO 基址和 `pinctrl` 部分。查资料认准 `bcm2712` / `RP1` 关键字。

---

## HFT / 嵌入式关联

- **"跑的是哪棵树"永远是调试第一问。** 驱动不 probe 的排查顺序：节点存在吗 → `status` 是 `okay` 吗 → `compatible` 逐字符对吗 → 父节点被递归到了吗 → 驱动模块加载了吗。**前三步全在 `/proc/device-tree` 里能验完，不需要重新编译任何东西。**
- **overlay 是产品化的标准手段**：同一份内核镜像，靠 config.txt 适配不同硬件配置。这和 HFT 里"一份二进制 + 不同配置文件适配不同交易所网关"是同一个思路——**把差异从代码里挪到数据里**。
- **`status = "disabled"` 是做 A/B 硬件验证的廉价手段**：不用改驱动，改一行 DTS 就能让某设备消失，用来定位"到底是哪个设备在抢资源"。

<details>
<summary>参考答案</summary>

1. 不写 `status` = **可用**（`of_device_is_available` 在 status 为 NULL 时返回 true）。写 `OKAY` = **不可用**，判定只认小写 `okay` 和 `ok`，大小写敏感。
2. **父节点不在 `of_default_bus_match_table` 里，导致你的节点所在的子树压根没被递归创建**。源码在 `of_platform_bus_create` 末尾的 `return 0`——父节点自己建了 device，但子节点不递归。这类问题在 `/proc/device-tree` 里**看不出来**（树还在），只有 `/sys/bus/platform/devices/` 里找不到对应 device 才暴露。
3. `tr '\0' '\n' < /proc/device-tree/<node>/compatible`。因为 `compatible` 是**多字符串属性**，内部以 `\0` 分隔，直接 cat 会把多个串粘在一起且看不到分隔。
4. 固件（Pi 上是 GPU 侧的 start.elf / config.txt）在加载 DTB 后会动态修改：启停 overlay、按 `dtparam` 改 `status`、填入实际的内存大小 / MAC 地址 / 序列号。所以磁盘 DTB 是"静态源"，运行时树是"源 + 固件补丁"。
5. `-I fs` 表示输入格式是**文件系统**（filesystem），即 sysfs 导出的目录树形式（`/proc/device-tree` 或 `/sys/firmware/devicetree/base`），而不是 `-I dtb`（二进制）或 `-I dts`（文本）。

</details>
