# 3.5 · devm 与出错路径：为什么 probe 里不用手写 unwind

> **本节讲什么：** `devm_*` 到底把资源挂在哪、什么时候释放、释放顺序如何，以及两个反直觉的细节——**probe 前 devres 链表必须为空**，和 **probe 错误码会被取反**。

---

## 心智模型：一张挂在 device 上的链表

```
struct device {
    ...
    struct list_head  devres_head;   /* ★ 所有 devm_ 申请都挂这里 */
    spinlock_t        devres_lock;
};
```

`devm_kzalloc(&pdev->dev, ...)` 做的事：

1. 分配一块 `devres` 结构（头部 + 你的数据）
2. 在里面记下**释放函数**（`devm_kzalloc` 对应的 free）
3. `devres_add()` → `add_dr()` 挂到 `dev->devres_head` 尾

```
devres_head ─→ [kzalloc#1] → [ioremap#2] → [irq#3] → [gpio#4]
```

**device 没了，链表跟着走**——这就是"自动回收"的全部秘密，没有 GC，没有引用计数。

---

## 释放时机与顺序

| 时机 | 触发函数 | 场景 |
|------|---------|------|
| probe 失败 | `probe_failed:` → `devres_release_all()` | **你不用写任何清理代码** |
| 驱动卸载 | `device_release_driver()` | `rmmod` |
| 设备消失 | `device_del()` | 热插拔 / 总线 rescan |

释放顺序是**申请顺序的逆序**（v6.6 `drivers/base/devres.c:496`）：

```c
list_for_each_entry_safe_reverse(dr, tmp, todo, node.entry) {
    dr->node.release(dev, dr->data);
    kfree(dr);
}
```

注意 `..._reverse`：**LIFO，后申请的先释放**。这跟手写 unwind 的顺序一致——先释放最内层依赖（irq），再释放它依赖的东西（映射、内存）。

```
申请：  内存 → ioremap → irq
释放：  irq → ioremap → 内存      ← 自动就是这个顺序
```

**所以 devm 不只是"省代码"，它还保证了释放顺序不会写错。** 手写 unwind 时漏掉中间某步、或者顺序搞反，是驱动里最常见的一类 bug。

---

## 对比：手写 vs devm

```c
/* ============ 手写（老式） ============ */
static int my_probe(struct platform_device *pdev)
{
    struct my_dev *m;
    int ret;

    m = kzalloc(sizeof(*m), GFP_KERNEL);
    if (!m)
        return -ENOMEM;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    m->base = ioremap(res->start, resource_size(res));
    if (!m->base) {
        ret = -ENOMEM;
        goto err_free;          /* ← 每个失败点都要 goto */
    }

    ret = request_irq(irq, handler, 0, "my", m);
    if (ret)
        goto err_iounmap;       /* ← goto 越来越多 */

    platform_set_drvdata(pdev, m);
    return 0;

err_iounmap:
    iounmap(m->base);
err_free:
    kfree(m);
    return ret;                 /* ← 加一步资源，就要改两处 */
}

static int my_remove(struct platform_device *pdev)
{
    /* 卸载路径再写一遍，且顺序必须与上面相反 */
    free_irq(irq, m);
    iounmap(m->base);
    kfree(m);
    return 0;
}
```

```c
/* ============ devm（现代） ============ */
static int my_probe(struct platform_device *pdev)
{
    struct my_dev *m;

    m = devm_kzalloc(&pdev->dev, sizeof(*m), GFP_KERNEL);
    if (!m)
        return -ENOMEM;

    m->base = devm_ioremap_resource(&pdev->dev,
                  platform_get_resource(pdev, IORESOURCE_MEM, 0));
    if (IS_ERR(m->base))
        return PTR_ERR(m->base);        /* 直接 return，无 goto */

    ret = devm_request_irq(&pdev->dev, irq, handler, 0, "my", m);
    if (ret)
        return dev_err_probe(&pdev->dev, ret, "irq");   /* 无 unwind */

    platform_set_drvdata(pdev, m);
    return 0;
}

static int my_remove(struct platform_device *pdev)
{
    return 0;               /* ★ 空的。资源由核心在返回后释放 */
}
```

**注意 remove 的时序**：`devm` 释放在 `remove()` **返回之后**发生。所以如果你的设备有特殊关机序列（比如"先停硬件再释放"），不能全交给 devm——要么在 `remove()` 里显式做，要么用 `devm_add_action()` 注册一个按逆序调用的清理钩子。

## 两个反直觉的细节

### ① probe 开始前，devres 链表必须是空的

v6.6 `drivers/base/dd.c:625`：

```c
    if (!list_empty(&dev->devres_head)) {
        dev_err(dev, "Resources present before probing\n");
        ret = -EBUSY;
        goto done;
    }
```

**内核在 probe 前检查：如果链表已经非空，直接拒绝并报 `-EBUSY`。**

含义：**`devm_*` 的第一个参数必须是"这个 device"，且只能在 probe 之后调用。** 在 `module_init` 里对某个 device 提前 `devm_kzalloc`，会让后续真正的 probe 直接失败——而报错信息 "Resources present before probing" 看起来和你的代码毫无关系。

反过来说，这也是个诊断线索：**看到 `Resources present before probing` 就说明有人在 probe 之外动了 devres。**

### ② probe 返回的错误码会被取反成正数

见 [3.4](./3.4-compatible-match-and-probe.md)——`really_probe()` 里 `ret = -ret;`。驱动 `return -ENODEV`，总线层往外抛 `+ENODEV`。读内核调用链代码时别以为自己看错了。

---

## 自定义清理：devm_add_action

devm 没有覆盖到的资源（比如自己开的 workqueue、注册到某个全局链表的东西），用 action 钩子：

```c
static void my_cleanup(void *data)
{
    struct my_dev *m = data;
    cancel_work_sync(&m->work);
    /* 反注册、关时钟…… */
}

/* probe 里： */
ret = devm_add_action_or_reset(&pdev->dev, my_cleanup, m);
if (ret)
    return ret;      /* 失败时 action 已自动执行过一次（_or_reset 的语义） */
```

**优先用 `_or_reset` 后缀版本**：注册失败时它会自动调用一次 action，省掉"注册失败时手动清理"这个分支。

## 常用 devm 清单

| 用途 | API | 非 devm 版本 |
|------|-----|-------------|
| 内存 | `devm_kzalloc` / `devm_kmalloc` | `kzalloc` |
| 寄存器映射 | `devm_ioremap_resource` / `devm_platform_ioremap_resource` | `ioremap` |
| 中断 | `devm_request_irq` / `devm_request_threaded_irq` | `request_irq` |
| GPIO | `devm_gpiod_get` | `gpiod_get` |
| 时钟 | `devm_clk_get` / `devm_clk_get_enabled` | `clk_get` |
| regulator | `devm_regulator_get` | `regulator_get` |
| 清理钩子 | `devm_add_action_or_reset` | — |

⚠️ **不是所有东西都有 devm 版本**，且有些"有 devm 版本但语义微妙不同"。拿不准时查 `drivers/base/devres.c` 的导出符号：**没有 `EXPORT_SYMBOL(devm_xxx)` 的就是不存在**，别猜。

## 检查清单

| 问题 | 后果 |
|------|------|
| probe 用 `devm_*`、remove 里又手动 `free_irq` | **double free**（devm 回去再释放一次） |
| 在 `module_init` 里 `devm_*` | 后续 probe 报 `-EBUSY` "Resources present before probing" |
| `devm_request_irq` 的 dev 参数传错（传了别的 device） | 中断挂到别的设备上，device 消失时机错位 → 悬空 handler |
| remove 里做"先停硬件"的清理，依赖 devm 顺序 | devm 在 remove **返回后**才跑，你的清理可能太晚 |

**最实用的一条：** 用了 devm 就**彻底别手动释放**。混用是最容易出现 double free / use-after-free 的组合。

---

## HFT / 嵌入式关联

- **devm 是 RAII 思想在 C 里的落地**。C 没有析构函数，内核用"资源登记到对象（device）上 + 对象销毁时逆序回调"实现同样效果。理解这一点后，看到任何 `devm_xxx` 都能立刻推断出释放时机和顺序。
- **出错路径的代码量直接决定 bug 密度**。驱动里 90% 的 bug 在错误路径（正常路径谁都会写、也都会测）。devm 把错误路径从"N 个 goto 标签 + N 段清理"压成"直接 return"，是**结构性降低 bug 率**，不是语法糖。
- **HFT 里的对应物**：确定性拆除顺序对低延迟系统同样关键——网卡驱动卸载时如果先释放了 ring buffer 再注销 NAPI，就会在中断里访问已释放内存。devm 的 LIFO 保证让这类"顺序错误"不可能发生。

5. remove() 里需要"先停硬件再释放资源"，devm 能满足吗？为什么？
6. `devm_add_action` 和 `devm_add_action_or_reset` 有什么区别？该用哪个？

<details>
<summary>参考答案</summary>

1. 挂在 `struct device` 的 `devres_head` 链表上（每个 devres 节点记录了对应的 release 函数）。释放在三种时机触发：probe 失败（`probe_failed:` → `devres_release_all`）、驱动卸载（`device_release_driver`）、设备消失（`device_del`）。**关键：remove() 返回之后才释放。**

2. **申请顺序的逆序（LIFO）**。源码是 `list_for_each_entry_safe_reverse`。这个顺序是对的，因为后申请的资源通常依赖先申请的（irq 依赖 ioremap，ioremap 依赖内存），逆序释放保证"释放 X 时 X 依赖的东西还在"，与手写 unwind 的正确顺序天然一致。

3. **不需要，且不应该。** devm 会在 remove 返回后自动 free_irq；手动再 free 一次是 **double free**。规则是用 devm 就彻底不要手动释放，混用是 use-after-free / double free 的主要来源。

4. 有人在 **probe 之前**往这个 device 的 devres 链表里塞了东西。典型是在 `module_init` 里对某个 device 调用了 `devm_*`。内核在 `really_probe` 开头检查链表非空就直接返回 `-EBUSY` 拒绝 probe。修法：把那些 `devm_*` 挪进 probe，或改用非 devm 的普通分配 + 自己管理生命周期。

5. **不能可靠满足。** devm 的释放发生在 `remove()` **返回之后**，也就是你的清理代码跑完之后。如果硬件需要在"资源释放前"被停止，正确做法是：在 remove() 里显式做停机序列，或者用 `devm_add_action_or_reset()` 注册清理钩子（钩子按 devm 的 LIFO 顺序被调用）。

6. `_or_reset` 版本在**注册失败时会自动调用一次 action**，省掉"注册失败要手动清理"的分支；普通版注册失败后 action 不会被调用，你得自己处理。所以**优先用 `devm_add_action_or_reset`**——和 devm 的设计意图（错误路径零手工）一致。

</details>
