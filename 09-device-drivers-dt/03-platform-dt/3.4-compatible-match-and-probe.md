# 3.4 · compatible 匹配与 probe：为什么"没报错"才是最难查的

> **本节讲什么：** `compatible` 是怎么被匹配的、匹配成功后 probe 走哪条路、以及**为什么驱动没 probe 时 `dmesg` 里常常什么都看不到**——答案在内核源码的日志级别选择里。

---

## 匹配不是"相等比较"，是四级回退

v6.6 `drivers/base/platform.c:1335`：

```c
static int platform_match(struct device *dev, struct device_driver *drv)
{
    /* When driver_override is set, only bind to the matching driver */
    if (pdev->driver_override)
        return !strcmp(pdev->driver_override, drv->name);

    /* Attempt an OF style match first */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* Then try ACPI style match */
    if (acpi_driver_match_device(dev, drv))
        return 1;

    /* Then try to match against the id table */
    if (pdrv->id_table)
        return platform_match_id(pdrv->id_table, pdev) != NULL;

    /* fall-back to driver name match */
    return (strcmp(pdev->name, drv->name) == 0);
}
```

| 优先级 | 机制 | 说明 |
|-------|------|------|
| 1 | `driver_override` | 用户通过 sysfs 强制指定，**一票否决**（设了就只认这个名字） |
| 2 | **OF（设备树）** | `of_match_table` 里的 `compatible` —— 现代 ARM 走这条 |
| 3 | ACPI | x86 世界 |
| 4 | `id_table` | 无设备树的平台驱动 |
| 5 | 驱动名 == 设备名 | 老式兜底 |

**调试价值：** 想临时把一个设备绑给另一个驱动，不用重编内核：

```bash
echo my_driver > /sys/bus/platform/devices/fe200000.gpio/driver_override
echo fe200000.gpio > /sys/bus/platform/drivers/my_driver/bind
```

`driver_override` 是**优先级最高**的那一级，写进去就压过 `compatible`。

**`compatible` 的匹配是"最具体优先"**：`of_driver_match_device` 会遍历驱动的 `of_match_table`，逐个比对设备节点的 compatible **列表**，命中第一个就返回。所以 DTS 里写 `compatible = "wzp,my-device", "generic-foo"` 时，内核会先看有没有驱动认 `wzp,my-device`，没有再退化看 `generic-foo`——**这是硬件兼容性的兜底机制**。

## `MODULE_DEVICE_TABLE` 到底是干什么的

```c
static const struct of_device_id my_of_match[] = {
    { .compatible = "wzp,my-device" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, my_of_match);
```

**它不是给内核匹配用的**（匹配用的是 `of_match_table` 指针）。它的作用是：编译期把这张表放进 ELF 的 `__mod_of_device_table` 段，`depmod` 扫到后生成 `modules.alias`：

```
alias of:N*T*Cwzp,my-device* my_device
```

于是 `udev`/`modprobe` 能在设备出现时**自动加载对应模块**。

**少了它的症状很有迷惑性：** 手动 `insmod` 一切正常（表在内存里，匹配照常），但**重启后驱动不会自动加载**。所以：

> 不用 `MODULE_DEVICE_TABLE` = 每次开机手动 insmod。功能"能跑"，自动化链路断了。

验证：

```bash
modinfo my_device.ko | grep alias
# alias:          of:N*T*Cwzp,my-device
```

## ★ 核心：probe 失败为什么常常"静默"

v6.6 `drivers/base/dd.c:572`：

```c
static int call_driver_probe(struct device *dev, struct device_driver *drv)
{
    if (dev->bus->probe)
        ret = dev->bus->probe(dev);
    else if (drv->probe)
        ret = drv->probe(dev);

    switch (ret) {
    case 0:
        break;
    case -EPROBE_DEFER:
        /* Driver requested deferred probing */
        dev_dbg(dev, "Driver %s requests probe deferral\n", drv->name);
        break;
    case -ENODEV:
    case -ENXIO:
        pr_debug("%s: probe of %s rejects match %d\n",
             drv->name, dev_name(dev), ret);
        break;
    default:
        /* driver matched but the probe failed */
        pr_warn("%s: probe of %s failed with error %d\n",
            drv->name, dev_name(dev), ret);
        break;
    }
    return ret;
}
```

**这张表值得背下来：**

| probe 返回值 | 内核怎么记 | 默认 `dmesg` 能看到吗 |
|---|---|---|
| `0` | 无 | — |
| `-EPROBE_DEFER` | `dev_dbg` | ❌ 看不到 |
| `-ENODEV` / `-ENXIO` | `pr_debug` | ❌ 看不到 |
| 其它（`-ENOMEM`、`-EINVAL`…） | `pr_warn` | ✅ 能看到 |

**结论（这是本节最实用的一条）：**

> 如果你在 probe 里 `return -ENODEV` 表示"这个设备我不认"，内核**只会打 debug 级日志**。默认 `dmesg` 完全看不见。
>
> 所以**调试期不要用 `-ENODEV` 表示"出错了"**——它是"拒绝匹配"的语义。出错就返回 `-EINVAL`、`-ENOMEM`、`-EIO` 之类，至少能在 dmesg 里留痕。

要看那些隐藏日志：

```bash
# 打开动态调试（CONFIG_DYNAMIC_DEBUG）
echo 'file drivers/base/dd.c +p' > /sys/kernel/debug/dynamic_debug/control
# 或者启动时加内核参数
initcall_debug dyndbg="file drivers/base/dd.c +p"
```

## `-EPROBE_DEFER`：不是失败，是"等一会儿"

驱动依赖的资源（时钟、regulator、GPIO 控制器、supplier 设备）还没就绪时，probe 应该返回 `-EPROBE_DEFER`，内核会把它放进延迟队列，**等其他驱动 probe 完再重试**。

```c
static int my_probe(struct platform_device *pdev)
{
    struct clk *clk;

    clk = devm_clk_get(&pdev->dev, NULL);
    if (IS_ERR(clk))
        return dev_err_probe(&pdev->dev, PTR_ERR(clk), "get clock");
    ...
}
```

**`dev_err_probe()` 是现代写法，强烈推荐**，它做两件事：

1. **`-EPROBE_DEFER` 时不刷屏**（defer 会重试很多次，用 `dev_err` 会淹没日志）
2. 真实错误时打 `error` 级日志并附带错误码，同时把返回值原样透传

`dev_err_probe` 内部对 `-EPROBE_DEFER` 走 `dev_dbg`，其它走 `dev_err`——**等于帮你实现了上面那张日志级别表的正确行为**。

查看当前有没有卡在 defer 状态的设备：

```bash
cat /sys/kernel/debug/devices_deferred
```

## ★ probe 的返回码会被取反

v6.6 `drivers/base/dd.c:670`：

```c
        /*
         * Return probe errors as positive values so that the callers
         * can distinguish them from other errors.
         */
        ret = -ret;
        goto probe_failed;
```

驱动 `return -ENODEV`，`really_probe()` 往外抛的是**正的 `ENODEV`**。这个约定（"bus 层返回正值表示 probe 失败"）在写 bus glue 层或者读内核日志对照错误码时会撞上：**dmesg 里看到的数字和驱动里写的是反的**。

## 排查清单：驱动没 probe 怎么办

按顺序验，每步都能在 30 秒内出结果：

| # | 检查 | 命令 | 不通过怎么办 |
|---|------|------|------------|
| 1 | 模块加载了吗 | `lsmod \| grep my` | `modprobe` / 查 `modules.alias` |
| 2 | 节点在吗 | `ls /proc/device-tree/` | 查 DTB / overlay |
| 3 | `status` 可用吗 | `tr '\0' '\n' < .../status` | 改成 `okay` |
| 4 | `compatible` 逐字符对吗 | `tr '\0' '\n' < .../compatible` | 对照 `modinfo \| grep alias` |
| 5 | device 建出来了吗 | `ls /sys/bus/platform/devices/` | 查父节点是否被递归（[3.3](./3.3-dtb-lifecycle.md)） |
| 6 | 卡在 defer 吗 | `cat /sys/kernel/debug/devices_deferred` | 找缺的 supplier |
| 7 | 匹配表有吗 | `modinfo x.ko \| grep alias` | 补 `MODULE_DEVICE_TABLE` |
| 8 | probe 日志 | 开 dynamic debug 后重看 | — |

**第 4 步最常出错**：`compatible` 里多一个空格、少一个逗号、大小写不对，都会静默失败。**用 `modinfo` 的 alias 和 DTS 的 compatible 逐字符对比**，别用眼睛看。

## HFT / 嵌入式关联

- **"静默失败"是嵌入式最贵的调试成本。** 内核把"驱动拒绝匹配"设计成 debug 级日志是合理的（每次总线扫描都可能有很多这种"拒绝"），但对开发者的代价是：**你必须有意识地选择错误码**。这是"可观测性由 API 使用者负责"的典型例子——框架给了分级，用错是你的问题。
- **`-EPROBE_DEFER` 是依赖注入**：驱动不关心 supplier 什么时候就绪，只说"我没好，待会再叫我"。这比在驱动里手写等待/重试健壮得多，也是内核"声明依赖而非控制时序"的思路。
- **HFT 的类比**：低延迟系统里"超时"和"明确失败"也必须分开处理——超时可能重试成功，明确失败重试只会浪费时间。内核这里把 `-EPROBE_DEFER`（重试有意义）和 `-EINVAL`（重试无意义）分开统计，是同一个设计哲学。

3. probe 里 `return -ENODEV` 和 `return -ENOMEM`，在 dmesg 里表现有什么不同？
4. 为什么 probe 里申请资源失败应该用 `dev_err_probe` 而不是 `dev_err` + `return`？
5. 驱动 probe 返回 `-EPROBE_DEFER` 说明什么？怎么确认哪些设备卡在这个状态？
6. 驱动 `return -ENODEV`，`really_probe()` 往外返回的是几？

<details>
<summary>参考答案</summary>

1. `driver_override` → OF(`compatible`) → ACPI → `id_table` → 驱动名==设备名。最高优先级是 `driver_override`：往 `/sys/bus/platform/devices/<dev>/driver_override` 写驱动名，再 `echo <dev> > /sys/bus/platform/drivers/<drv>/bind`，可以强制绑定，常用于调试时临时换驱动。

2. 模块不会在设备出现时**自动加载**——`MODULE_DEVICE_TABLE` 的作用是把匹配表导出到 `modules.alias`，供 `depmod`/`udev` 做自动加载。但手动 `insmod` 时匹配表本身已经在内核里了，`platform_match` 照常工作，所以"手动能跑"掩盖了"自动加载链断了"。验证：`modinfo x.ko | grep alias` 应该有一行 `of:N*T*C<compatible>`。

3. `-ENODEV` 落到 `pr_debug`（**默认 dmesg 看不见**），因为内核认为这是"驱动拒绝匹配"，属于正常流程；`-ENOMEM` 落到 `pr_warn`（**看得见**），因为这是"匹配了但 probe 失败了"，属于异常。所以调试期表示真实错误不要返回 `-ENODEV`/`-ENXIO`。

4. 因为 `-EPROBE_DEFER` 会触发**多次重试**（每次 supplier 就绪都重试一遍），用 `dev_err` 会刷屏淹没真实日志。`dev_err_probe()` 内部对 `-EPROBE_DEFER` 只打 `dev_dbg`，其它错误才打 `dev_err` 并附错误码——一行代码实现了正确的日志分级，同时原样透传返回值（defer 语义不丢）。

5. 表示依赖的资源（时钟、regulator、GPIO 控制器、supplier 设备）尚未就绪，**不是失败**，内核会把它放进延迟队列，等依赖就绪后重试。确认方法：`cat /sys/kernel/debug/devices_deferred` 会列出所有卡在 defer 状态的设备。

6. **正的 `ENODEV`（即 `+19`）**。`really_probe()` 在 `dd.c:673` 处 `ret = -ret;` 把 probe 错误码取反成正值返回，注释说明是"让调用者能区分 probe 失败和其它错误"。

</details>
