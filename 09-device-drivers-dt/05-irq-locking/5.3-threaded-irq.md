# threaded IRQ 实践：现代中断处理的默认姿势

> **本节讲什么：** 用 `request_threaded_irq()` 把中断拆成"硬中断快速判断 + 内核线程慢慢做"，以及如何拿到中断号、设为唤醒源、绑核、调试。
> **为什么推荐它：** 比自己搭 tasklet/workqueue 更安全；handler 里不睡、线程里随便睡，边界天然清晰。
> **前置：** [5.1 中断上下文](./5.1-irq-context.md) · [5.2 锁的选型](./5.2-lock-selection.md)  
> **卡住查书：** Madieu Ch16 · LDD3 Ch10

---

## 为什么需要它

传统写法：上半部干活、下半部用 tasklet 或 workqueue。问题是要**自己管理两套机制**，容易出错。

`request_threaded_irq` 把这个模式**内建**：内核为你的 IRQ 起一个**专属内核线程**，handler 返回 `IRQ_WAKE_THREAD` 就唤醒它。

```
硬中断 handler (my_handler)      ← 中断上下文：不能睡
   ├─ 判断是不是我的中断（读状态寄存器）
   ├─ 清中断
   └─ return IRQ_WAKE_THREAD
              │
              ▼  内核唤醒专属线程
IRQ 线程 (my_thread)             ← 进程上下文：可以睡
   └─ 读 I2C 数据、mutex_lock、copy_to_user、唤醒等待队列
```

**额外好处：** 线程有 `task_struct`，可以被 `chrt` 提优先级、可以绑核、可以被调试器看到。这在实时性调优时非常有用。

---

## 返回值（三选一）

| 返回值 | 含义 | 后果 |
|--------|------|------|
| `IRQ_NONE` | **不是我的中断**（共享 IRQ 时常见） | 内核继续问下一个共享者 |
| `IRQ_HANDLED` | 已处理完，不需要线程 | 线程不唤醒 |
| `IRQ_WAKE_THREAD` | 已做紧急处理，请唤醒线程 | **线程被调度执行** |

## 完整示例（含设备树取中断号）

**DTS 侧：**

```dts
mydev@fe200000 {
    compatible = "wzp,my-device";
    reg = <0x0 0xfe200000 0x0 0x1000>;
    interrupts = <GIC_SPI 32 IRQ_TYPE_LEVEL_HIGH>;   /* 或 IRQ_TYPE_EDGE_FALLING */
    interrupt-names = "data";
};
```

**驱动侧：**

```c
static irqreturn_t my_handler(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;
    u32 status;

    status = readl(dev->base + REG_STATUS);
    if (!(status & IRQ_MINE))
        return IRQ_NONE;              /* 共享中断：不是我的 */

    writel(status & IRQ_MINE, dev->base + REG_CLEAR);   /* ★ 清中断，必须 */
    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;

    mutex_lock(&dev->lock);                 /* 可以睡眠 */
    /* 读数据、调 I2C/SPI、解析 */
    mutex_unlock(&dev->lock);

    wake_up_interruptible(&dev->wq);        /* 唤醒等待的用户进程 */
    return IRQ_HANDLED;
}

/* probe 里注册 —— 中断号来自设备树，不硬编码 */
static int my_probe(struct platform_device *pdev)
{
    struct my_dev *dev;
    int irq;

    irq = platform_get_irq(pdev, 0);        /* 从 DT 的 interrupts 属性解析 */
    if (irq < 0)
        return dev_err_probe(&pdev->dev, irq, "no irq");

    ret = devm_request_threaded_irq(&pdev->dev, irq,
                                    my_handler, my_thread,
                                    IRQF_TRIGGER_HIGH | IRQF_ONESHOT,
                                    "mydev", dev);
    if (ret)
        return dev_err_probe(&pdev->dev, ret, "request irq failed");
    return 0;
}
```

### `IRQF_ONESHOT` 是什么

**线程处理完之前，保持该中断线屏蔽。** 对**电平触发**中断几乎是必需的：

- 电平触发：只要硬件引脚还是高电平，中断就持续有效。若线程还没跑完就放开中断线，会**立刻重复触发**。
- `IRQF_ONESHOT` 让内核在 handler 返回后**保持屏蔽**，直到线程执行完才 unmask。

**边沿触发**通常不需要，但加上无害且更安全。

---

## 常用 flag

| flag | 作用 |
|------|------|
| `IRQF_SHARED` | 多个设备共享同一 IRQ 线；`dev_id` 必须唯一（用于卸载时区分） |
| `IRQF_ONESHOT` | 线程执行完前保持中断屏蔽（电平触发必加） |
| `IRQF_TRIGGER_HIGH/LOW/RISING/FALLING` | 触发方式；**通常从 DT 读，不写死** |
| `IRQF_NOBALANCING` | 禁止内核自动均衡该中断到其他 CPU（做绑核隔离时用） |

## 调试与验证

```bash
# 看中断分布：谁在第几个 CPU 上、触发了多少次
cat /proc/interrupts | grep mydev

# 看中断线程的优先级（threaded IRQ 会显示为 irq/xx-mydev）
ps -eo pid,comm,pri,psr | grep irq

# 绑核：把 IRQ 42 绑到 CPU3（HFT/低延迟常用）
echo 8 > /proc/irq/42/smp_affinity      # 8 = 0b1000 = CPU3

# 提线程优先级
chrt -f -p 50 $(pgrep -f "irq/42-mydev")

# 模拟/触发（无硬件时可用软件中断调试）
cat /proc/irq/42/spurious
```

## HFT / 嵌入式关联

- **中断绑核是低延迟的标准动作**：把网卡/存储中断绑到**非关键核**，让交易线程所在的核不被中断打扰。`/proc/irq/N/smp_affinity` 就是入口（配合 `isolcpus` 启动参数）。
- **threaded IRQ 的线程可以被 `chrt` 提优先级** —— 这是普通 tasklet 做不到的（tasklet 没有 task_struct）。实时性调优时这是关键差异。
- **NAPI 与 threaded IRQ 是两种思路**：NAPI 靠"关中断转轮询"减少中断次数；threaded IRQ 靠"线程化"让长工作可睡眠。网卡走 NAPI，普通外设走 threaded IRQ（见 [12.5-modern-networking](../../12.5-modern-networking)）。

## 代码自测

<details>
<summary>Q1：handler 返回 <code>IRQ_NONE</code> 会怎样？</summary>

告诉内核"这不是我的中断"。共享 IRQ 时内核会继续调用链上的下一个 handler。
如果所有人都返回 `IRQ_NONE`，内核记一次 **spurious interrupt**（可在 `/proc/irq/N/spurious` 看到）。
</details>

<details>
<summary>Q2：电平触发的中断为什么几乎必须加 <code>IRQF_ONESHOT</code>？</summary>

电平触发下，只要硬件引脚保持有效电平，**中断控制器就持续认为有中断**。
若 handler 一返回就放开中断线，中断会**立刻再次触发**，而线程还没来得及清掉硬件状态 → 反复触发甚至死循环。
`IRQF_ONESHOT` 让中断线保持屏蔽，直到线程跑完（这时硬件状态已清）。
</details>

<details>
<summary>Q3：中断号能从设备树拿，为什么不要硬编码？</summary>

中断号在不同 SoC / 不同板卡上**编号规则不同**（GIC SPI 编号、GPIO 转中断的映射都是动态的）。
硬编码的号换个板子就错，而且**不报错**——只是中断永远不触发，非常难查。
`platform_get_irq()` 从 DT 的 `interrupts` 属性解析，是唯一正确做法。
</details>
