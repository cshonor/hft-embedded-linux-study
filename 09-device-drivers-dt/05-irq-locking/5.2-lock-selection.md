# 锁怎么选：只看一件事——临界区能不能睡眠

> **本节讲什么：** spinlock / mutex / atomic / RCU 的选型依据，以及"持自旋锁睡眠会死锁"到底怎么发生的。
> **决策树只有一问：** 临界区里会不会调用可能睡眠的函数？
> **前置：** [5.1 中断上下文](./5.1-irq-context.md)  
> **卡住查书：** LDD3 Ch5 · Madieu Ch3、Ch16

---

## 决策树

```
临界区里会睡眠吗？（调 I2C/SPI、access_user、kmalloc(GFP_KERNEL)、msleep）
   │
   ├─ 会  ──► mutex（或 rt_mutex / semaphore）
   │
   └─ 不会 ──► 会不会在中断上下文里执行？
                   │
                   ├─ 会  ──► spinlock（+ 必要时 spin_lock_irqsave）
                   │
                   └─ 不会 ──► 临界区多长？
                                 ├─ 极短（几条指令）──► atomic_t / bitops
                                 ├─ 短 ──────────────► spinlock
                                 └─ 读多写少 ────────► rwlock / seqlock / RCU
```

> **最快的锁是不加锁。** 优先考虑：per-CPU 变量、无锁环形缓冲、RCU —— 把共享拆成不共享。

## spinlock vs mutex 正面对比

| | `spinlock_t` | `mutex` |
|--|-------------|---------|
| 拿不到时 | **忙等**（原地打转，CPU 100%） | **睡眠**（让出 CPU） |
| 能否在中断上下文用 | ✅ | ❌ |
| 持有期间能否睡眠 | ❌ **严禁** | ✅ 可以 |
| 临界区长度 | 必须**极短** | 可以长 |
| 开销 | 小（几条原子指令） | 大（可能睡眠/唤醒，上下文切换） |
| 递归获取 | 死锁（不递归） | 死锁（不递归） |
| 适用 | 中断 handler、短临界区、数据结构自洽更新 | 进程上下文、可能调 I2C/SPI 的操作 |

```c
/* mutex：可以睡，可以调 I2C */
static int my_read_reg(struct my_dev *dev, u8 reg, u8 *val)
{
    mutex_lock(&dev->lock);            /* 拿不到就睡 */
    *val = i2c_smbus_read_byte_data(dev->client, reg);  /* 会睡眠，OK */
    mutex_unlock(&dev->lock);
    return 0;
}

/* spinlock：中断里用，临界区极短 */
static irqreturn_t my_handler(int irq, void *p)
{
    struct my_dev *dev = p;
    unsigned long flags;

    spin_lock_irqsave(&dev->slock, flags);   /* 关中断 + 拿锁，一步到位 */
    dev->irq_count++;
    spin_unlock_irqrestore(&dev->slock, flags);
    return IRQ_WAKE_THREAD;
}
```

## 为什么持自旋锁睡眠 = 死锁

```
CPU0: 进程 P 拿到 spinlock，然后调用 copy_to_user（睡眠）
      → P 被挂起，但锁还握在手里
CPU1: 另一个进程 Q 想拿同一把锁
      → 自旋等待（不睡眠，因为它是 spinlock）
      → 在**抢占式内核**上，Q 占着 CPU 空转
      → P 永远等不到 CPU 来释放锁
      → 两核一起卡死
```

**单核 + 非抢占内核**下，Q 自旋时没法让出 CPU，同样卡死。所以内核有 `CONFIG_DEBUG_ATOMIC_SLEEP` 专门抓这类 bug。

## spinlock 的三个变体（选错就是死锁或丢中断）

| 变体 | 做的事 | 用在哪 |
|------|--------|--------|
| `spin_lock` / `spin_unlock` | 只拿锁 | **仅进程上下文**，且确定不会有中断来抢同一把锁 |
| `spin_lock_irqsave` / `irqrestore` | **关本地中断 + 保存 flags + 拿锁** | **进程与中断共享**数据时（最常用、最安全） |
| `spin_lock_bh` / `unlock_bh` | 关**下半部**（softirq），不关硬中断 | 只与 tasklet/softirq 竞争时 |

```c
/* 为什么中断 handler 里必须用 irqsave 版本？ */
spin_lock(&lock);        /* 只拿锁，不关中断 */
    /* 此时本 CPU 来了同一个中断 → handler 也 spin_lock 同一把锁 */
    /* → 自己等自己，永久自旋 —— 死锁 */
```

## 更快的选项

| 场景 | 用 |
|------|-----|
| 只改一个计数器 | `atomic_inc(&c)` / `atomic64_t` |
| 只置位/清位 | `set_bit` / `clear_bit`（原子位操作） |
| 每 CPU 一份数据 | `DEFINE_PER_CPU` / `this_cpu_*`（无需加锁） |
| 读极多、写极少 | `seqlock`（读不加锁，靠序号重试）或 **RCU** |
| 单生产者单消费者环形缓冲 | 无锁（内存屏障 + `smp_store_release`/`smp_load_acquire`） |

## HFT / 嵌入式关联

- **per-CPU 数据结构避免加锁**，这个招式在 HFT 用户态无锁队列里是同一个内核：把共享拆成每核一份，写入本地、读取合并，彻底消除争用（见 [14-hft-engineering](../../14-hft-engineering)）。
- **`spin_lock_irqsave` 的代价是关中断** —— 关中断期间本 CPU 无法响应任何中断，直接制造延迟尖刺。HFT 里"中断绑核 + 关键线程绑核"就是在**物理上隔离**这两种争用。
- **RCU 的思想**（读者不加锁、写者延迟回收）在无锁数据结构里反复出现。理解 RCU 对写高性能并发代码帮助极大。

## 代码自测

<details>
<summary>Q1：临界区里要调 <code>i2c_transfer</code>（会睡眠），该用哪种锁？</summary>

**mutex。** I2C 传输会睡眠，spinlock 持有期间禁止睡眠 → 只能用 mutex。
这也意味着这段代码**不能**在中断 handler 里执行，必须放到下半部线程（workqueue / threaded IRQ）。
</details>

<details>
<summary>Q2：<code>spin_lock_irqsave</code> 比 <code>spin_lock</code> 多做了什么？为什么中断里必须用它？</summary>

多做了**关本地中断 + 保存中断状态到 flags**。
如果只 `spin_lock` 不关中断：进程上下文拿着锁时，本 CPU 来了中断，handler 也请求同一把锁 → **自己等自己，永久自旋**。
`irqsave` 关掉中断后，handler 根本不会在本 CPU 上跑，竞争消失。
</details>

<details>
<summary>Q3：什么情况下连 spinlock 都不需要？</summary>

- 数据是 **per-CPU** 的（每核一份，天然无竞争）；
- 操作本身是**原子的**（`atomic_t`、原子位操作）；
- 单生产者单消费者的**环形缓冲**（配合内存屏障）。

"最快的锁是不加锁" —— 能拆成不共享就别加锁。
</details>
