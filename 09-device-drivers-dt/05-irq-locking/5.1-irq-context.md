# 中断上下文：为什么硬中断里不能 sleep

> **本节讲什么：** 中断上下文到底是什么、为什么不关联任何进程、以及"不能睡眠"这条铁律的**物理原因**。
> **一句话：** 中断是"借尸还魂"—— 它借用被打断进程的**内核栈**执行，但**不代表那个进程**，所以没有可被调度的实体。
> **后续：** [5.2 锁的选型](./5.2-lock-selection.md) · [5.3 threaded_irq 实践](./5.3-threaded-irq.md)  
> **卡住查书：** LDD3 Ch10、Ch5 · Madieu Ch16

---

## 中断上下文 vs 进程上下文

| | 进程上下文 | 中断上下文 |
|--|-----------|-----------|
| 代表谁 | 某个进程（`current` 有效） | **谁都不代表**（`current` 指向被打断的进程，但**无关**） |
| 能被调度 | ✅ | ❌ |
| 能睡眠 | ✅ | ❌ |
| 能访问用户空间 | ✅ | ❌（没有进程地址空间） |
| 栈 | 进程内核栈（8K/16K） | **借用**被中断进程的内核栈（或独立 irq stack） |
| 优先级 | 受调度器管理 | **高于一切**，谁都能打断（除更高优先级中断） |

```
进程 A 正在跑  ──────────────────────────────►
                    │
                    │  硬件中断到来
                    ▼
              ┌───────────────────┐
              │  中断 handler      │  ← 借用 A 的内核栈，但 A 被"冻结"
              │  (中断上下文)      │     current == A，但 A 与此无关
              └───────────────────┘
                    │
                    │  返回
                    ▼
进程 A 继续  ────────────────────────────────►
```

**关键推论：** 如果在中断里调用 `schedule()`（睡眠的本质），调度器会去选下一个进程运行，而**中断上下文本身没有被保存进任何可恢复的位置**——它只是栈上的一段临时执行流，不属于任何 `task_struct`。于是：

- 要么内核检测到非法调度 → `BUG: scheduling while atomic` → **oops**
- 要么调度走了，中断永远无法返回 → **中断丢失、系统卡死**

## 硬中断里**不能**调用的函数

| 类别 | 具体 | 原因 |
|------|------|------|
| **睡眠/调度** | `msleep`、`schedule`、`wait_event_*`、`ssleep` | 无调度实体 |
| **可能睡眠的分配** | `kmalloc(GFP_KERNEL)`、`vmalloc`、`kzalloc(GFP_KERNEL)` | 内存不足时会触发回收/睡眠 |
| **互斥锁** | `mutex_lock`、`down(&sem)`、读写信号量 | 拿不到就睡 |
| **用户空间访问** | `copy_to_user`、`copy_from_user` | 可能缺页 → 睡眠；且不该访问用户地址空间 |
| **可能睡眠的同步** | `flush_work`（不指定 `WQ_MEM_RECLAIM` 时） | 会等待 |

**反过来，中断里可以用的：**

| 类别 | 具体 |
|------|------|
| 分配 | `kmalloc(GFP_ATOMIC)`（不睡眠，失败立即返回 NULL） |
| 同步 | `spinlock`、`atomic_*`、`bitops` |
| 记录 | `printk`（但别刷屏，串口是慢设备） |
| 调度下半部 | `tasklet_schedule`、`queue_work`、`IRQ_WAKE_THREAD` |

```c
/* 判错技巧：内核提供了断言 */
might_sleep();          /* 放在函数开头，若在原子上下文被调用会打印警告栈 */
in_interrupt();         /* 是否在中断上下文 */
in_atomic();            /* 是否在原子上下文（含持 spinlock） */
```

## 上半部 / 下半部：为什么必须切分

**硬中断执行期间，同级/低优先级中断被屏蔽。** 在这段时间里：

- 系统不响应其他中断 → **丢中断**（串口 FIFO 溢出、网卡丢包）
- 其他 CPU 不受影响，但本 CPU 上的所有任务被推迟 → **延迟尖刺**

所以铁律：**上半部只做"不做就会丢数据"的事**，其余推给下半部。

```
硬中断 top half（中断上下文，不能睡）
   ├─ 读硬件状态寄存器，判断是不是我的中断
   ├─ 清中断源（★ 必须，否则中断会反复触发）
   ├─ 把数据搬到内存（少量）
   └─ 调度下半部
            │
            ▼
下半部 bottom half（可以是内核线程，能睡）
   └─ 解析数据、调 I2C、唤醒用户进程、拷贝给用户
```

| 下半部机制 | 执行上下文 | 能睡眠 | 特点 |
|-----------|-----------|--------|------|
| **softirq** | 软中断（中断下半部的底层） | ❌ | 静态注册，可并发在不同 CPU；网络收发用它 |
| **tasklet** | 基于 softirq | ❌ | 同一 tasklet **串行**（不跨 CPU 并发），用起来简单 |
| **workqueue** | **内核线程** | ✅ | 可睡眠；`schedule_work` 用系统默认队列 |
| **threaded IRQ** | **专属内核线程** | ✅ | `request_threaded_irq`；**现代推荐** |

> **现代建议：** 直接用 `request_threaded_irq()`。它把"上半部快速处理 + 线程慢慢做"封装成一步，比手写 tasklet/workqueue 更不容易出错。详见 [5.3](./5.3-threaded-irq.md)。

## HFT / 嵌入式关联

- **中断处理时长 = 延迟尖刺的直接来源。** HFT 里做中断绑核（把网卡中断绑到隔离核之外）的本质，就是避免中断处理抢占关键线程。
- **NAPI 是"中断 + 轮询"的混合**：网卡收到第一个包发中断，之后**关中断转轮询**把队列里的包一次性收完。这样既避免了"每包一中断"的开销，又不会像纯轮询那样空转。这是"上下半部"思想在网络栈的终极形态（见 [12.5-modern-networking](../../12.5-modern-networking)）。
- **`GFP_ATOMIC` 失败率高于 `GFP_KERNEL`** —— 这是"不能睡"换来的代价：内存紧张时它宁可失败也不等待。高频路径要预先分配好缓冲池，别在中断里分配（HFT 里的内存池同理）。

## 代码自测

<details>
<summary>Q1：中断 handler 里 <code>current</code> 指向谁？能用它吗？</summary>

`current` 会指向**被中断的那个进程**，但这个进程与中断处理**毫无关系**（中断只是借用了它的内核栈）。
用它做任何判断都是错的 —— 比如"当前进程是不是 root"在中断里毫无意义。
</details>

<details>
<summary>Q2：为什么 <code>kmalloc(GFP_KERNEL)</code> 不能在中断里用，而 <code>GFP_ATOMIC</code> 可以？</summary>

`GFP_KERNEL` 允许在内存不足时**触发页回收、回写、甚至等待 I/O**，这些都可能睡眠。
`GFP_ATOMIC` 禁止睡眠：只用紧急保留池，不够就**立刻返回 NULL**。代价是失败率更高。
</details>

<details>
<summary>Q3：如果上半部忘了清中断源会怎样？</summary>

中断控制器认为"中断仍在处理"，该 IRQ 线持续有效 → **退出 handler 后立刻再次触发**，陷入死循环，系统看起来卡死（`dmesg` 会被刷屏）。
所以"清中断"是上半部**必须**做的第一步 —— 尤其是**电平触发**（level-triggered）的中断。
</details>
