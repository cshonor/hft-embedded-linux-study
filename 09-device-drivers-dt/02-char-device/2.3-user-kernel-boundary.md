# 用户态 / 内核态的数据边界：为什么不能直接解引用用户指针

> **本节讲什么：** `copy_to_user` / `copy_from_user` 存在的理由，以及怎么写才不会踩坑。
> **一句话：** 用户传进来的指针，**在内核里就是个不可信的整数**。直接用 = 内核崩或被打穿。
> **前置：** [2.2 open() 的路径](./2.2-syscall-to-driver.md)  
> **卡住查书：** LDD3 Ch3、Ch6 · Madieu Ch4

---

## 为什么不能 `memcpy(buf, ...)`

用户态传给 `read(fd, buf, len)` 的 `buf` 是一个**用户空间虚拟地址**。内核不能直接解引用，四个理由：

| # | 理由 | 后果 |
|---|------|------|
| 1 | **地址空间不同** | 内核与用户进程页表不同；同一个数值在两边指向完全不同的物理页（`swapper_pg_dir` vs 进程 pgd） |
| 2 | **页可能不在内存** | 用户页可能被换出到磁盘，解引用会触发缺页；内核态缺页处理受限，可能直接 oops |
| 3 | **可能是恶意地址** | 用户故意传 `0x0` 或内核地址 → 内核读写自己的数据 = **提权漏洞** |
| 4 | **SMAP / SMEP 硬件拦截** | 现代 CPU（x86 SMAP、ARM PAN）**硬件禁止**内核访问用户页；绕过需临时关标志，只有 `copy_*_user` 有这个权限 |

> 比喻：用户给你一张纸条写着"仓库 A 区 3 号货架"——这是**用户仓库的编号体系**。你在内核仓库里照着找，找到的是别人的东西，甚至可能是承重墙（崩溃）。  
> 正确做法是走**正规搬运通道**（`copy_*_user`）：它会先核对权限、处理缺页、搬完再报告结果。

## 正确写法

### 批量拷贝

```c
static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t len, loff_t *off)
{
    char kbuf[64];
    size_t n = min(len, sizeof(kbuf));

    /* ... 填充 kbuf ... */

    /* 返回「没拷成功的字节数」，0 才是成功 */
    if (copy_to_user(buf, kbuf, n))
        return -EFAULT;          /* 用户给的 buf 有问题 */

    *off += n;
    return n;                     /* 返回值 = 实际读取字节数 */
}
```

**注意 `__user` 注解**：它不做任何运行时检查，是给 `sparse` 静态分析工具看的，用来抓"忘了 copy 就解引用"的 bug。编译内核时 `make C=1` 会跑。

### 单值拷贝

```c
int val;
if (copy_from_user(&val, (int __user *)arg, sizeof(val)))
    return -EFAULT;
/* 或更简洁： */
get_user(val, (int __user *)arg);     /* 单值版本 */
put_user(val, (int __user *)arg);
```

## 返回值陷阱（最容易写错的地方）

| 函数 | 返回 | 判断 |
|------|------|------|
| `copy_to_user` / `copy_from_user` | **未拷贝成功的字节数** | `!= 0` 即失败 → 返回 `-EFAULT` |
| `get_user` / `put_user` | `0` 成功，`-EFAULT` 失败 | `!= 0` 即失败 |
| `access_ok()` | 布尔（地址是否合法） | 通常不用手动调，`copy_*_user` 内部已做 |

```c
/* 错：把"剩余字节数"当成返回值传给用户 */
return copy_to_user(buf, kbuf, n);      /* 成功时返回 0，用户以为读到 0 字节 */

/* 对 */
if (copy_to_user(buf, kbuf, n))
    return -EFAULT;
return n;
```

## 什么时候可以直接访问用户内存

三种例外，**都需要显式"打开通道"**：

| 场景 | API | 说明 |
|------|-----|------|
| `mmap` 之后 | `remap_pfn_range` / `vm_insert_page` | 内核内存映射到用户空间，两边看到同一块物理页 → 无拷贝（见 [06-dma-mmap](../06-dma-mmap/)） |
| 临时借用用户缓冲 | `get_user_pages()` → `kmap()` | 钉住用户页再映射到内核；用完必须 `put_page` |
| 大块且需要零拷贝 | `splice` / `sendfile` | 内核内部管道搬运，不经过用户态 |

## HFT / 嵌入式关联

- **`copy_to_user` 的开销 = 一次内存拷贝 + 边界检查**，这就是"内核旁路"要消灭的成本之一。DPDK 的做法是**启动时 `mmap` 一次，之后所有数据收发都在用户态直接访存**，运行期零 copy、零 syscall。
- **控制面 vs 数据面**的切分标准就是看**数据量**：几字节的配置用 `ioctl`（走 copy），几 MB 的报文流用 `mmap` + 轮询（不走 copy）。
- 这个"拷贝即边界"的思想在系统里到处都是：TLB shootdown、DMA bounce buffer、甚至 HFT 里的无锁队列跨核传递——**凡是跨越信任边界，都得付一份搬运费**。

## 代码自测

<details>
<summary>Q1：<code>copy_to_user</code> 返回 5 是什么意思？</summary>

**还有 5 个字节没拷成功**（用户给的缓冲区非法或访问时缺页失败）。
约定俗成的处理是返回 `-EFAULT` 给用户态，让 `read()` 失败并置 `errno = EFAULT`。
</details>

<details>
<summary>Q2：<code>__user</code> 这个修饰符有运行时作用吗？</summary>

**没有。** 它只是给 `sparse` 静态检查工具的注解，编译后完全消失。
作用是让 `make C=1` / `make C=2` 能抓出"把用户指针当内核指针直接用"的错误。写上它是好习惯，成本为零。
</details>

<details>
<summary>Q3：为什么 <code>mmap</code> 之后就不需要 <code>copy_to_user</code> 了？</summary>

因为 `mmap` 把**同一块物理页**同时映射进内核和用户地址空间，两边访问的是同一内存，根本不存在"搬运"。
但代价是**没有同步保护**——需要自己用锁或内存序保证一致性（见 [05-irq-locking](../05-irq-locking/)）。
</details>
