# 1.4 · 为什么内核模块不能用 libc，以及 MODULE_LICENSE 的实际后果

> **本节讲什么：** 内核模块**不能链接 libc** 的根本原因（不是"忘了链接"，是架构上不可能），以及两个常被当成"只是标记"、实际有硬后果的东西——**`MODULE_LICENSE` 缺失会让你用不了 `EXPORT_SYMBOL_GPL` 的符号**，还有自己编的模块**必然**让内核 taint。

---

## 一、为什么用不了 libc

### 表层原因：没有链接

用户态程序由动态链接器把 `libc.so` 映射进来；内核模块加载时解析的是**内核自己的符号表**（`/proc/kallsyms` 里那些 `EXPORT_SYMBOL` 导出的），里面根本没有 `printf`。

```
用户态：a.out  ──ld.so──▶ libc.so ──syscall──▶ 内核
内核态：my.ko  ──模块加载器──▶ 内核符号表（printk / kmalloc / ...）
                              ✗ 没有 printf，也没有 syscall 入口可用
```

### ★ 根本原因：libc 的函数依赖 syscall，而内核没法"调用自己"

`printf` 最终落到 `write(1, buf, n)`；`malloc` 最终落到 `brk`/`mmap`。**系统调用的本质是"从用户态陷入内核"的机制**（`svc` / `syscall` 指令 + 特权级切换 + 内核栈切换）。

内核代码本身就在 ring 0 / EL1 **运行在 syscall 的另一端**：

- 它没有"陷入自己"这回事
- 它需要的文件操作直接调 VFS 内部函数（`vfs_write` 等），而不是 `write` 这个系统调用入口
- 它需要内存直接调 `kmalloc` / `alloc_pages`，而不是 `brk`

**所以这不是"内核里没有 libc 的实现"，而是 libc 依赖的那套机制在内核上下文中不成立。**

### 对照表：你要习惯的替换

| 用户态（libc） | 内核态 | 备注 |
|---|---|---|
| `printf` | **`printk`** | 有日志级别（`KERN_INFO` / `KERN_ERR` 等） |
| `malloc` / `free` | **`kmalloc` / `kfree`** | 带 `GFP_` 标志，可睡眠 |
| `vmalloc` | **`vmalloc`** | 虚拟连续、物理不必连续 |
| `memcpy` / `strlen` | **有** | 内核自带一份，直接用 |
| `strcpy` | **`strscpy`** | ⚠️ `strcpy` 不安全，`strlcpy` 已废弃 |
| `sprintf` | **`snprintf` / `scnprintf`** | 内核态没有浮点格式化（见下） |
| `open`/`read`/`write` | **无直接对应** | 内核直接调 VFS；**不该在驱动里读写文件** |
| `sleep`/`usleep` | **`msleep` / `usleep_range`** | ⚠️ 进程上下文才能用 |
| `pthread_mutex` | **`mutex` / `spinlock`** | 见 [05-irq-locking](../05-irq-locking/5.2-lock-selection.md) |

### 另外三条硬约束

**① 浮点 / SIMD 默认不可用。** 内核为了省去每次进出都保存恢复 FPU 寄存器的开销，默认不启用。要用必须显式声明区间：

```c
kernel_fpu_begin();
/* ... 这里可以用浮点/SIMD ... */
kernel_fpu_end();
```

而且**中断上下文里不能用**（会破坏被打断进程的 FPU 状态）。信号处理里能用的那套，在内核没这个自由度。

**② 栈极小。** 用户态栈默认 8 MB；**内核栈通常 8 KB（或配置成 16 KB）**，且和中断共用（某些配置下中断另用栈）。后果：

```c
char buf[65536];        /* ❌ 直接爆栈，没有 SIGSEGV 兜底，oops */
```

大缓冲一律 `kmalloc` / `devm_kzalloc`，不要在栈上开。深递归同理。

**③ 没有内存保护。** 所有内核代码共享同一地址空间，模块与核心之间**没有隔离**。你越界写一个字节，可能踩到不相关的内核数据——症状是"过一会儿在完全无关的地方崩"。用户态有 SIGSEGV 兜底，内核只有 oops/panic。

## 二、MODULE_LICENSE：不只是标记

```c
MODULE_LICENSE("GPL");              /* 或 "GPL v2" / "Dual BSD/GPL" 等 */
MODULE_AUTHOR("wzp");
MODULE_DESCRIPTION("my first driver");
MODULE_VERSION("0.1");
```

### ★ 硬后果：非 GPL 兼容模块用不了 `EXPORT_SYMBOL_GPL` 的符号

内核符号分两类导出：

```c
EXPORT_SYMBOL(func);          /* 任何模块可用 */
EXPORT_SYMBOL_GPL(func);      /* ★ 只有 GPL 兼容许可的模块可用 */
```

模块加载时，加载器解析未定义符号会检查模块的 license。**声明不兼容（或不声明）时，`EXPORT_SYMBOL_GPL` 的符号解析失败**：

```bash
insmod my.ko
# insmod: ERROR: could not insert module my.ko: Unknown symbol in module
dmesg | tail
# my: Unknown symbol some_gpl_only_func (err -2)
```

**这不是"警告"，是加载不了。** 很多重要的 DMA / 网络 / 文件系统辅助函数只以 `_GPL` 导出——所以：

> **不写 `MODULE_LICENSE("GPL")` 的模块，等于自我限制了一部分内核 API。**
> 学习/自用驱动没有理由不声明 GPL。

### 内核 taint（污染）标志

v6.6 `kernel/panic.c:462` 的完整表（每个条目 = `{ 全局大写字母, 模块自身小写字母, 是否与模块相关 }`）：

| 标志 | 字母 | 含义 |
|------|------|------|
| `TAINT_PROPRIETARY_MODULE` | **P / G** | 加载了非 GPL 兼容模块 |
| `TAINT_OOT_MODULE` | **O** | 加载了 **out-of-tree（树外）** 模块 |
| `TAINT_CRAP` | C | 加载了 `drivers/staging` 的模块 |
| `TAINT_UNSIGNED_MODULE` | E | 未签名模块（开了模块签名时） |
| `TAINT_FORCED_MODULE` | F | 用 `insmod -f` 强加载 |
| `TAINT_DIE` | D | 发生过 oops / BUG |
| `TAINT_WARN` | W | 发生过 WARN |
| `TAINT_SOFTLOCKUP` | L | 发生过 soft lockup |

**⚠️ 反直觉的一点：自己编的模块必然带 `O`。**

```bash
cat /proc/sys/kernel/tainted          # 非 0 表示已污染
dmesg | grep -i taint
# my: module verification failed: signature and/or required key missing - tainting kernel
# 或：my: loading out-of-tree module taints kernel.

# 单个模块的标志（第二个字段）
cat /proc/modules | grep my
# my 16384 0 - Live 0x0000000000000000 (OE)
#                                        ↑↑
#                                        O = out-of-tree
#                                        E = 未签名
```

**即使你写了 `MODULE_LICENSE("GPL")`，`O`（out-of-tree）仍在**——因为你编的模块不在内核源码树里，这是"来源"标记，与许可证无关。**所以调试期看到 taint 不必慌，先分清是 `O`/`E`（正常的自编译）还是 `P`（真的没声明 GPL 许可）。**

### 实际影响

| 影响 | 严重度 |
|------|-------|
| 用不了 `EXPORT_SYMBOL_GPL` 符号 | **高**（加载失败） |
| 社区/维护者看到 tainted 的 oops 报告，通常会让你先用干净内核复现 | 中（求助会被打回） |
| `panic_on_taint` 被设置时直接 panic | 低（默认关） |

## 三、最小可加载模块（把上面串起来）

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init my_init(void)
{
    pr_info("my: loaded\n");            /* = printk(KERN_INFO ...) */
    return 0;
}

static void __exit my_exit(void)
{
    pr_info("my: unloaded\n");
}

module_init(my_init);
module_exit(my_exit);

/* ★ 缺了 MODULE_LICENSE 会用不了 EXPORT_SYMBOL_GPL 的符号 */
MODULE_LICENSE("GPL");
MODULE_AUTHOR("wzp");
MODULE_DESCRIPTION("minimal example");
```

对应的 Makefile：

```makefile
obj-m += my.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	make -C $(KDIR) M=$(PWD) modules
clean:
	make -C $(KDIR) M=$(PWD) clean
```

**`__init` / `__exit` 宏**：把函数放进特定段，`__init` 的代码在初始化完成后被**释放**（内核启动时打印 "Freeing unused kernel memory" 就包含这部分）。只在模块里对初始化函数用。

## HFT / 嵌入式关联

- **"内核没有 libc" 这个约束决定了内核编程的整个风格**：没有异常、没有内存保护、栈极小、不能睡眠的上下文。这些不是限制而是**设计选择**——为了确定性和性能。理解"为什么"比记住"不能用什么"重要得多。
- **栈限制与 HFT 的对应**：低延迟代码同样忌讳在热路径上做大栈分配和深递归（cache 局部性）。内核是 8 KB 硬限制，HFT 是 cache miss 的软惩罚——**本质都是"离 CPU 越近的资源越贵"**。
- **`EXPORT_SYMBOL_GPL` 是一个社会契约的技术实现**：内核用链接期的符号可见性来维护 GPL 边界。这类"用技术手段表达法律意图"的设计在开源基础设施里很常见，值得留意。

<summary>参考答案</summary>

1. **表层**：内核模块加载时解析的是内核符号表（`/proc/kallsyms` 里 `EXPORT_SYMBOL` 导出的），里面没有 libc 的函数，也没有动态链接器去加载 `libc.so`。
   **根本**：libc 的函数（printf→write、malloc→brk/mmap）**依赖系统调用**，而系统调用是"从用户态陷入内核"的机制。内核本身运行在 syscall 的另一端，**无法"陷入自己"**。它需要的功能由内核内部函数直接提供（VFS 内部接口、`kmalloc` 等），绕过了 syscall 这一层。

2. `printf` → **`printk`**（或 `pr_info`/`pr_err` 等封装，带日志级别）；`malloc`/`free` → **`kmalloc`/`kfree`**（带 `GFP_KERNEL` 等标志，可睡眠）或 `vmalloc`（虚拟连续、物理可离散）。
   注意 `memcpy`/`strlen` 内核自带可直接用；但 `strcpy` 不安全，要用 `strscpy`。

3. **用不了 `EXPORT_SYMBOL_GPL` 导出的符号，导致模块加载失败**（`Unknown symbol in module`）。这是链接期的硬限制，不是警告。此外内核被标记 `TAINT_PROPRIETARY_MODULE`（P），社区通常会拒绝处理 tainted 内核的 oops 报告。

4. 会带 **`O`**（out-of-tree）和通常的 **`E`**（未签名）。**写了 `MODULE_LICENSE("GPL")` 也消不掉 `O`**——`O` 标记的是"模块来源不在内核源码树"，与许可证无关。GPL 声明能消掉的是 **`P`**（非 GPL 兼容）。调试期看到 taint 先分清是哪个字母。

5. **通常 8 KB**（可配成 16 KB），而用户态默认 8 MB——差三个数量级。在栈上开 64 KB 数组会**立刻爆栈**，且没有 SIGSEGV 兜底，直接 oops。大缓冲必须 `kmalloc`/`devm_kzalloc`；深递归同理要避免。

6. 需要 **`kernel_fpu_begin()` / `kernel_fpu_end()`** 显式包裹（内核默认不启用 FPU 以省去保存恢复开销）。**中断上下文里不能用**——会破坏被打断进程的 FPU 寄存器状态。
