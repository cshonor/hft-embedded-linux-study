DMA 基础：硬件搬运、指令层机制与地址空间

扩展精读 · 锚定 Linux Device Drivers Development Ch12 前置概念
深入 12.1 缓存一致性 / 12.2 流式映射细节 → 待补（见 notes.md 小节状态表）
章内摘要：notes.md · 大纲：../OUTLINE.md

本节讲什么

DMA = Direct Memory Access 直接内存访问：硬件自己搬运内存数据，不需要 CPU 亲自拷贝。

比喻：没有 DMA 时老板（CPU）亲自一箱一箱搬货；有 DMA 时雇搬运工（DMA 控制器）搬货——老板只需下达指令"把这块数据从 A 地址搬到 B 地址"，然后回去办公；搬运工干完活，敲门（中断）通知老板完工。

一句话浓缩：老方式——中断 CPU，CPU 亲自访存拷贝到内存；DMA 方式——配置完，硬件自己拷贝到内存，CPU 解放，结束才中断。结局都到内存，干活的角色换了。

要点

没有 DMA 会怎样（以网卡收包为例）

【无 DMA · 普通 IO】                       【有 DMA】
┌──────┐  每小段数据一次中断              ┌──────┐
│ 网卡 │──┐                              │ 网卡 │──┐
└──────┘  │ 硬件小缓冲区                  └──────┘  │
          ▼                                       ▼
   ┌───────────────┐                      ┌──────────┐
   │CPU 执行访存指令 │ in/out·load/store    │ DMA 控制器│ 独立硬件搬运
   │ 一字节一字节拷  │                      └──────────┘
   └───────────────┘                              │
          │                                       │ 搬完才发 1 次中断
          ▼                                       ▼
   CPU 全程被占用，                          CPU 并行跑别的任务，
   干不了别的事                              只需处理包本身
          │                                       │
          └───────────────┬───────────────────────┘
                          ▼
                ┌──────────────────┐
                │    主内存 RAM     │ ← 共同终点：DMA 不能跳过内存
                └──────────────────┘

普通 IO 的搬运本质（指令层）：CPU 停下手上正在跑的程序，亲自执行访存指令——PIO 方式走 x86 in/out 指令读硬件 IO 端口，MMIO 方式走普通 load/store 访问设备寄存器映射区——把数据一字节一字节从硬件拷到主内存。搬运这个动作是 CPU 执行指令完成的，期间 CPU 跑不了别的计算任务。

比喻：货车到货，老板（CPU）放下手里工作，自己一箱一箱把货搬进仓库。

无 DMA（老式 PIO） 有 DMA
谁搬运数据 CPU 执行访存指令亲自拷 DMA 硬件搬运（不执行任何 CPU 指令）
中断次数 每来一小块数据中断一次 整块搬完才 1 次中断
CPU 占用 全程占用，大量时间耗在搬运苦力活 只下达命令 + 收完工通知

DMA 方式的三步

  1. 配置：CPU 提前给 DMA 硬件配好源地址、目标物理内存地址、要搬多少字节，配置完即可回去跑业务代码
  2. 独立搬运：硬件数据出来后，DMA 控制器硬件直接完成"硬件→内存"的搬运——这一步完全不执行 CPU 的 load/store 指令。CPU 此时可以跑别的线程、做计算
  3. 完成中断：全部搬运完成，DMA 发一次中断"搬完了"，CPU 才去内存处理这份数据

⭐ 共同点与唯一差别（最容易被忽略的洞察）

✅ 两种方式，数据最终都必须落到主内存 RAM 里——不管 CPU 搬还是 DMA 硬件搬，终点都是内存。DMA 不能跳过内存。

普通 IO DMA IO
数据终点 主内存 RAM 主内存 RAM（相同）
搬运执行者 CPU 访存指令（占用 CPU） DMA 硬件（不消耗 CPU）

唯一真正的差别：谁执行搬运拷贝动作。

误区澄清：

  • ❌ 不是 DMA"不走内存"
  • ✅ 是 DMA 不走 CPU 的寄存器流水线——搬运这件活交给独立硬件，内存依旧必经

磁盘例子对比（指令视角）

1）无 DMA：磁盘有数据 → 中断 CPU → CPU 执行 in/out 指令把数据读进来，再一条条 store 指令写入内存——CPU 全程参与搬运。 2）有 DMA：CPU 告诉 DMA"把磁盘的数据搬到物理内存 0x80000 地址" → 回去运行程序 → DMA 硬件自己把磁盘数据传输到内存 → 全部完成后中断 CPU → CPU 此时才去内存读数据。

两个典型场景

场景 流程 备注
网卡 DMA 网卡收包 → DMA 直接写入内存缓冲区 → 完成后中断，CPU 只处理包不拷贝 DPDK 高性能网络重度依赖；HFT 低延迟基石
SD 卡 / USB 麦克风 麦克风持续采集音频样本 → DMA 持续搬进内存，整块搬完才 1 次中断 而不是每个采样点中断一次

⚠️ 关键概念：DMA 地址 ≠ 虚拟地址

  • DMA 硬件大多不理解虚拟地址——设备发起的总线事务不经过 CPU 的 MMU。用户态/内核态用的都是虚拟地址，DMA 硬件访问内存必须给它总线侧的地址。
  • 内核 API：dma_alloc_coherent() 专门分配物理连续内存，返回值是 CPU 侧虚拟地址，同时通过出参拿到给硬件用的地址。
void *
dma_alloc_coherent(struct device *dev, size_t size,
                   dma_addr_t *dma_handle, gfp_t flag);
/* 返回值  → CPU 用的虚拟地址（分配失败为 NULL）
 * dma_handle → 给硬件的 DMA 地址（出参）              */

坑：不能拿 kmalloc 出来的虚拟地址直接丢给 DMA——虚拟地址对 DMA 无效，硬件根本不认。

精度修正（按 v6.6 内核文档核对）：dma_handle 是 DMA 地址（总线地址），不严格等于物理地址。官方 Documentation/core-api/dma-api.rst 原文：

A CPU cannot reference a dma_addr_t directly because there may be translation between its physical address space and the DMA address space.

  • 平台有 IOMMU/SMMU 时，DMA 地址是 IOMMU 映射后的 IOVA，和物理地址是两套空间（IOMMU 甚至能把物理上不连续的页映射成一个连续 DMA 地址段）。
  • 树莓派这类无 SMMU 的简单 SoC 上，DMA 地址实践中就等于物理地址——所以直觉"只认物理地址"在嵌入式裸机上成立，但在服务器/现代 x86 上必须升级为"只认总线地址"。

DMA 缓冲区

一块专门给硬件和 CPU 双向交换数据的内存：硬件写、CPU 读；或 CPU 写、硬件读。一致性分配（dma_alloc_coherent）出来的就是典型 DMA 缓冲区。

与 copy_from_user 的对比

copy_from_user DMA
执行者 CPU 亲自做内存拷贝 硬件做内存搬运
本质 CPU 执行循环拷贝指令 DMA 控制器独立搬运
CPU 占用 占用（拷贝期间跑不了别的） 不占用（并行执行其他代码）
数据终点 主内存（用户↔内核缓冲都在 RAM） 主内存（相同）

→ 三者的统一视角：copy_from_user 与 DMA 的数据都落到内存，差别只在执行者——前者烧 CPU 指令周期，后者烧独立硬件。

两种 DMA 模式（对应 12.1 / 12.2）

一致 DMA（coherent） 流式 DMA（streaming）
内存来源 专用分配（dma_alloc_coherent） 复用已有内存（dma_map_single 等）
Cache 处理 分配时就对 cache 做屏蔽/映射，CPU 与硬件立刻看到彼此的写 每次 map 时做 cache 刷新/失效
性能 分配昂贵（部分平台最小一页），适合长期缓冲 性能更高，网卡多用
典型用户 描述符环、控制块 收发包数据缓冲

官方定义（v6.6 dma-api.rst）：Consistent memory is memory for which a write by either the device or the processor can immediately be read by the other without worrying about caching effects.

/* 流式：映射一块已有的 CPU 虚拟内存给设备用 */
dma_addr_t
dma_map_single(struct device *dev, void *cpu_addr, size_t size,
               enum dma_data_direction direction);
/* direction: DMA_TO_DEVICE / DMA_FROM_DEVICE / DMA_BIDIRECTIONAL */

HFT / 嵌入式关联

路线 要点
HFT 网卡 DMA 把报文直接丢内存，CPU 省去拷贝开销 → 直接降低收包延迟；DPDK 全程基于此（内核旁路 + DMA + 轮询模式收包）；DMA 落地之后最早的决策点是 XDP（skb 之前，见衔接）
嵌入式 音频 ADC / SD 卡 / SPI 等低速外设靠 DMA 连续搬运数据流，CPU 只在每个"块"完工时被中断一次
低延迟线索 12.1 缓存一致性标注精读（低延迟）——coherent 内存牺牲 cache 性能换一致性，流式映射靠 flush/invalidate 保正确性，两条路线的延迟代价要分开量化

代码示例

（环境无 C 编译器，以下为按 v6.6 Documentation/core-api/dma-api.rst 人工核对过的骨架，未真机编译）

#include <linux/dma-mapping.h>

/* 一致 DMA：收包描述符环 */
struct rx_ring {
    void       *cpu_addr;    /* CPU 侧虚拟地址 */
    dma_addr_t  dma_addr;    /* 硬件侧 DMA 地址 */
};

static int rx_ring_alloc(struct device *dev, struct rx_ring *r)
{
    r->cpu_addr = dma_alloc_coherent(dev, RING_SIZE,
                                     &r->dma_addr, GFP_KERNEL);
    if (!r->cpu_addr)
        return -ENOMEM;

    /* 硬件寄存器里写的是 r->dma_addr —— 绝不是 r->cpu_addr！
     * 坑：dma_alloc_coherent 只能在开中断的上下文调用 */
    iowrite32(r->dma_addr, dev_regs + RX_RING_BASE);
    return 0;
}

static void rx_ring_free(struct device *dev, struct rx_ring *r)
{
    dma_free_coherent(dev, RING_SIZE, r->cpu_addr, r->dma_addr);
    /* dev/size/dma_handle 必须与分配时完全一致；cpu_addr 传返回的虚拟地址 */
}

参考答案

Q1：DMA 搬运内存的时候，CPU 在干什么？

CPU 可以并行跑别的代码，不需要等待搬运；DMA 结束靠中断通知 CPU。

Q2：为什么 DMA 不能用虚拟地址，只能用物理地址？

设备发起的总线事务不经过 CPU 的 MMU——MMU 的页表翻译只对 CPU 发出的访存生效，硬件看到的地址就是总线地址，没有任何东西帮它做 VA→PA 翻译。 进阶修正：有 IOMMU 的平台上，设备地址会经过 IOMMU 翻译（IOVA→PA），所以现代说法是"设备只认 DMA 地址"；无 IOMMU 的简单 SoC（如树莓派）上 DMA 地址就等于物理地址。

Q3：dma_alloc_coherent 返回的虚拟地址能直接写给硬件寄存器吗？

不能。写给硬件的必须是出参 dma_handle 里的 DMA 地址；返回值是给 CPU 访问用的虚拟地址。两者一个走 CPU/MMU，一个走设备总线，是两套地址空间。

Q4：DMA 传输的时候，CPU 完全不工作吗？

不是。CPU 可以正常跑别的任务/线程、做计算，只是不参与数据拷贝搬运这件事——搬运由 DMA 硬件独立完成。

反向误区同理：DMA 也不能让数据"不经过内存"直达 CPU——终点永远是 RAM，变的只是干活的角色。

12.1

缓存一致性：为什么 DMA 和 Cache 会打架

扩展精读 · 锚定 Linux Device Drivers Development Ch12 §12.1
前置：12.0 DMA 基础 · 章内摘要：notes.md
源码依据：Linux v6.6 Documentation/core-api/dma-api{,-howto}.rst · include/linux/dma-map-ops.h · kernel/dma/direct.c · arch/x86/Kconfig · arch/x86/kernel/pci-dma.c（均已核对）

本节讲什么

Cache 是 CPU 的私有记账，DMA 绕过 CPU 直写 RAM——于是同一份数据存在两套副本（CPU cache 里一份、内存里一份），谁后写谁说了算，另一份变"过期数据"。一致性 = 保证 CPU 和设备永远看到同一份最新数据。

要点

问题：两个方向都会"读到旧的"

方向①  设备写 RAM，CPU cache 里是旧的
┌────────┐ DMA 写     ┌─────────┐
│  设备   │──────────→│ 主内存   │← 新数据在这
└────────┘            └─────────┘
                          ↑ 读不到
                      ┌──────────┐
                      │ CPU cache │← CPU 还在用旧副本（stale）
                      └──────────┘

方向②  CPU 写进 cache 未回写，设备从 RAM 读到旧的
┌──────────┐ CPU 写    ┌─────────┐
│ CPU cache │          │ 主内存   │← 设备读到旧数据（stale）
└──────────┘          └─────────┘
                          ↑ DMA 读
                      ┌────────┐
                      │  设备   │
                      └────────┘

更阴险的：cacheline 共享损坏（v6.6 文档原文实证）

即使数据本身没被 CPU 缓存，相邻变量挤在同一条 cacheline 里也会坏：

The CPU could write to one word, DMA would write to a different one in the same cache line, and one of them could be overwritten. ——dma-api-howto.rst

即：CPU 写 word A → 该 cacheline 留在 CPU cache 里；DMA 写同 line 的 word B 直接进 RAM；CPU 回写整条 line → word B 被 RAM 里的旧值覆盖。无声数据损坏。

→ 推论：DMA 缓冲区要 cacheline 对齐、不与其他数据共享 line（这也是 ARCH_DMA_MINALIGN 存在的原因）。

两类平台：硬件一致性是"天生"还是"没有"

x86 / PCIe 服务器 多数 ARM SoC
硬件机制 总线侦听（snoop）：设备访存穿透查询 CPU cache 设备端口直连 DDR 控制器，不侦听 CPU cache
DMA 一致性 天然一致 非一致，必须软件维护
dma_sync_* 的 cache 维护 空操作（v6.6 实证，见下） 真实的 invalidate / clean

v6.6 源码实证（x86 上 sync 是空操作——两层机制叠加）：

编译期：arch/x86/Kconfig 从不 select CONFIG_ARCH_HAS_SYNC_DMA_FOR_CPU/DEVICE （全文件 grep DMA 相关 select 只有 DMA_COHERENT_POOL）→ include/linux/dma-map-ops.h 的 #else 桩生效：

/* include/linux/dma-map-ops.h:366-374 —— CONFIG 未定义时的 #else 桩 */
static inline void arch_sync_dma_for_device(phys_addr_t paddr, size_t size,
                enum dma_data_direction dir)
{
}                                     /* 空函数体，编译器直接消除 */

运行时：x86 同样不设 CONFIG_ARCH_HAS_DMA_COHERENCE_H → dma-map-ops.h 里 dev_is_dma_coherent() 恒返回 true （#define dma_default_coherent true）→ kernel/dma/direct.c 的守卫恒假：

if (!dev_is_dma_coherent(dev))      /* x86 上恒 false */
        arch_sync_dma_for_device(paddr, sg->length, dir);  /* 不执行 */

→ 即使桩函数被换成真实现，x86 也根本走不到那行调用。空桩 + 守卫恒真，双保险。 （x86 的 DMA 代码本体在 arch/x86/kernel/pci-dma.c。）

两条解决路线（软件视角）

路线 做法 代价
一致分配（coherent） 把 DMA 缓冲映射成 uncached / 一致属性——CPU 不缓存它，读写直通内存 每次 CPU 访问都是内存延迟，吞吐低
流式映射 + sync（streaming） 内存正常 cached；在所有权切换点显式做 invalidate / clean 正确性依赖驱动按规矩调 dma_sync_*

dma_sync_* 的方向语义（易混，按"谁即将访问"记）

调用 时机 本质动作
dma_sync_single_for_cpu() 设备写完、CPU 读之前（RX 路径） invalidate CPU cache 里的旧副本，让 CPU 强制从 RAM 读新数据
dma_sync_single_for_device() CPU 写完、交回设备之前（TX 路径） clean/writeback，把 CPU cache 里的新数据刷到 RAM

记法：for_X = 接下来归 X 用。for_cpu = 设备干完了换 CPU 上场（先丢旧缓存）；for_device = CPU 干完了换设备上场（先刷新缓存）。

HFT / 嵌入式关联

路线 要点
HFT x86 服务器天然 DMA 一致（snoop），数据面缓冲几乎不为一致性付费——收发包路径不用 uncached 内存，这是 HFT 落地 x86 的隐性基础设施红利之一
嵌入式 树莓派等 ARM SoC 非一致：描述符环用 coherent 分配（uncached），大数据缓冲用 streaming + sync；忘调 sync 是嵌入式驱动最经典的静默数据损坏来源
低延迟 coherent 内存每次访存都是内存延迟（无 cache 命中）→ 只给小而热的结构用（描述符、控制块），数据面永远走 streaming

参考答案

Q1：为什么 cacheline 共享会导致数据损坏？

CPU 写 line 内 word A（line 进入 CPU cache，未回写）；DMA 写同 line 的 word B 直接落 RAM；随后 CPU 回写整条 line——RAM 里 word B 的新值被 cache 里 line 的旧 word B 覆盖。防法：DMA 缓冲区 cacheline 对齐、独占 line。

Q2：dma_sync_single_for_cpu 和 for_device 方向反了会怎样？

for_cpu 忘调（RX 后直接读）：CPU 可能命中自己的旧 cache 副本，读到设备写入前的数据。for_device 忘调（TX 前只写了 cache）：设备从 RAM 读到旧数据，发出错包。两者都是静默损坏，不报错。

Q3：为什么 x86 上 dma_sync_* 基本是空操作，还必须写？

x86 硬件侦听保证 DMA 与 CPU cache 一致，软件侧双保险：不 select ARCH_HAS_SYNC_DMA_FOR_*（空桩编译期消除）+ 不设 ARCH_HAS_DMA_COHERENCE_H（dev_is_dma_coherent() 恒 true，direct.c 的守卫恒假，v6.6 实证见上文）。但驱动代码必须可移植——同一份驱动跑 ARM 上 sync 就是真实动作，写了才两平台都对。

12.2

一致性 / 流式映射 API：两类映射的完整生命周期

扩展精读 · 锚定 Linux Device Drivers Development Ch12 §12.2
前置：12.1 缓存一致性（本节讲"怎么用"，12.1 讲"为什么"） · 章内摘要：notes.md
源码依据：Linux v6.6 Documentation/core-api/dma-api{,-howto}.rst · include/linux/dma-mapping.h · include/linux/dma-map-ops.h · kernel/dma/{direct,mapping}.c（均已核对）

本节讲什么

12.1 说明了 cache 一致性问题及两条软件路线（uncached 一致分配 / cached + sync）。本节把这两条路线落到具体 API 的完整生命周期：什么时候 alloc、什么时候 map、方向参数怎么填、错误怎么查、以及 v6.6 提供的"sync 能不能省"的官方接口。

要点

两类映射的官方画像（v6.6 dma-api-howto.rst 定义）

一致映射（consistent/coherent） 流式映射（streaming）
生命周期 驱动初始化时映射一次、卸载时解除，长期存在 一次 DMA 传输一次映射，传完即 unmap（除非配 sync 循环用）
一致性保证 设备与 CPU 可并行访问，互相的更新立即可见，无需软件 flush 所有权归一侧时另一侧不碰；切换点显式 sync
记忆口诀（文档原话） think of as "synchronous / coherent" think of as "asynchronous / outside the coherency domain"
典型用途 网卡 DMA 描述符环、SCSI mailbox 命令结构、设备固件微码 收发的网络数据缓冲、SCSI 读写的文件系统缓冲
底层代价 CPU 访问是 uncached（无 cache 命中） 内存正常 cached，映射本身可能走 IOMMU/swiotlb

API 全景：按场景选

场景 coherent 系 streaming 系
大块、长期 dma_alloc_coherent() / dma_free_coherent() —
小块、高频 dma_pool_create() → dma_pool_alloc/zalloc() → dma_pool_free() → dma_pool_destroy() —
已有内存、一次传输 — dma_map_single() / dma_map_page() → dma_unmap_single/page()
已有内存、循环复用 — map 一次 + dma_sync_single_for_{cpu,device}() 反复切换所有权

dma_alloc_coherent 的 v6.6 真身

/* include/linux/dma-mapping.h:423 —— 是 dma_alloc_attrs 的 inline 包装 */
static inline void *dma_alloc_coherent(struct device *dev, size_t size,
                dma_addr_t *dma_handle, gfp_t gfp)
{
        return dma_alloc_attrs(dev, size, dma_handle, gfp,
                        (gfp & __GFP_NOWARN) ? DMA_ATTR_NO_WARN : 0);
}
  • 双返回值：返回值 = CPU 用的虚拟地址（失败 NULL）；dma_handle 出参 = 写进设备寄存器的 DMA 地址
  • 细节：gfp 带 __GFP_NOWARN 会自动转成 DMA_ATTR_NO_WARN 属性——两套标志体系在包装层打通
  • 常见搭配：dma_set_coherent_mask()（约束一致分配的地址范围；x86 默认落在低 32 位，但文档建议显式设置）

dma_pool：小而高频的一致分配

大块 coherent 一次分一整页太浪费；描述符这类定长小对象走池：

struct dma_pool *dma_pool_create(const char *name, struct device *dev,
                size_t size, size_t align, size_t alloc);
void *dma_pool_alloc(struct dma_pool *pool, gfp_t gfp_flags,
                dma_addr_t *dma_handle);
void  dma_pool_free(struct dma_pool *pool, void *vaddr, dma_addr_t addr);
void  dma_pool_destroy(struct dma_pool *pool);   /* 必须先还完再销毁 */
  • align：字节单位、必须是 2 的幂——设备对齐要求直接传给池
  • alloc：边界限制。传 0 = 无限制；传 4096 = 每块分配不得跨 4KB 边界（老硬件常见约束）
  • GFP_ATOMIC（不阻塞，中断上下文可用）vs GFP_KERNEL（可阻塞）与普通分配语义一致

dma_map_single：一次传输一次映射

dma_addr_t dma_map_single(struct device *dev, void *cpu_addr,
                size_t size, enum dma_data_direction direction);
void dma_unmap_single(struct device *dev, dma_addr_t dma_addr,
                size_t size, enum dma_data_direction direction);

两条硬约束（dma-api.rst 明文）：

  1. 物理连续：本 API 无 scatter/gather 能力，映射非物理连续内存直接失败 → 源头必须是 kmalloc/dma_alloc_* 这类物理连续分配；vmalloc 的内存不能 map（虚拟连续 ≠ 物理连续）。要映射散页 → 等价于 12.3 的 dma_map_sg()
  2. 落在 dma_mask 内：DMA 地址与 dma_mask 按位 AND 后必须不变（设备够得着这块地址）

方向枚举（强类型，不能乱填）：

枚举 语义 所有权约定
DMA_NONE 无方向（调试用） —
DMA_TO_DEVICE 内存 → 设备（TX） map 后 CPU 视为只读
DMA_FROM_DEVICE 设备 → 内存（RX） map 后 CPU 不得写
DMA_BIDIRECTIONAL 方向不确定 必须 sync 两次：交给设备前一次 + 设备用完 CPU 访问前一次

cacheline 对齐警告（文档明文）：映射区域应起止于 cacheline 边界，否则与相邻数据共享 line → 12.1 讲的静默损坏。懒人稳妥法：只映射起止都在页边界上的区域（页边界必是 cacheline 边界）。

dma_unmap_single 的参数必须与 map 时完全一致（地址、长度、方向逐项相同）——内部要用它们反查映射记录。

错误检查：dma_mapping_error

dma_addr_t dma_handle = dma_map_single(dev, addr, size, direction);
if (dma_mapping_error(dev, dma_handle))     /* 不能只判 dma_handle == 0！ */
        goto map_error_handling;

错误判定规则（dma-api-howto.rst Handling Errors 节）：dma_alloc_coherent 判 NULL；dma_map_sg 判 0；dma_map_single/page 判 dma_mapping_error()——DMA 地址 0 可能是合法地址（映射失败也可能返回 0），不能拿它当哨兵。

完整生命周期示例：收包路径（v6.6 howto 伪代码，精简）

/* 初始化：分配 RX 缓冲并映射（DMA_FROM_DEVICE = 设备将写入） */
cp->rx_dma = dma_map_single(cp->dev, cp->rx_buf, cp->rx_len,
                            DMA_FROM_DEVICE);
if (dma_mapping_error(cp->dev, cp->rx_dma))
        goto map_error_handling;
give_rx_buf_to_card(cp);                    /* 缓冲交给设备 */

/* 中断：设备写完 RAM，CPU 读之前必须先 sync */
my_card_interrupt_handler(int irq, void *devid, ...)
{
        if (read_card_status(cp) == RX_BUF_TRANSFERRED) {
                /* ① 所有权切回 CPU：invalidate cache 里的旧副本 */
                dma_sync_single_for_cpu(cp->dev, cp->rx_dma,
                                        cp->rx_len, DMA_FROM_DEVICE);

                /* ② 现在才能安全地读缓冲内容 */
                hp = (struct my_card_header *)cp->rx_buf;
                if (header_is_ok(hp)) {
                        dma_unmap_single(cp->dev, cp->rx_dma,
                                         cp->rx_len, DMA_FROM_DEVICE);
                        pass_to_upper_layers(cp->rx_buf);
                        make_and_setup_new_rx_buf(cp);
                } else {
                        /* ③ 拒收：CPU 没写过 FROM_DEVICE 区域，
                         *    无需 sync 回设备，直接还给卡复用 */
                        give_rx_buf_to_card(cp);
                }
        }
}

注意 ③：文档特意注明 DMA_FROM_DEVICE 区域 CPU 没写过就不需要 sync_for_device——sync 不是仪式，是按所有权是否真实切换决定的。

dma_need_sync：sync 能不能省，问官方接口（v6.6）

dma_sync_* 调用的开销因平台/设备而异，v6.6 提供了官方判定接口：

bool dma_need_sync(struct device *dev, dma_addr_t dma_addr);
/* true  = 必须调 dma_sync_single_for_{device,cpu} 转移所有权
 * false = 可以跳过 */

实现链（v6.6 实证）：

/* kernel/dma/mapping.c:822 */
bool dma_need_sync(struct device *dev, dma_addr_t dma_addr)
{
        if (dma_map_direct(dev, ops))
                return dma_direct_need_sync(dev, dma_addr);   /* x86 走这 */
        return ops->sync_single_for_cpu || ops->sync_single_for_device;
}

/* kernel/dma/direct.c:610 */
bool dma_direct_need_sync(struct device *dev, dma_addr_t dma_addr)
{
        return !dev_is_dma_coherent(dev) ||                   /* x86 恒 true → 恒假 */
               is_swiotlb_buffer(dev, dma_to_phys(dev, dma_addr));
}

x86 上 dma_need_sync() 几乎恒 false（唯一例外：地址受限设备被迫走 SWIOTLB 的 bounce buffer）——这正是 12.1"x86 硬件侦听"论断的官方接口化。驱动热路径可以这样省分支：

if (dma_need_sync(dev, dma_handle))
        dma_sync_single_for_cpu(dev, dma_handle, len, dir);

HFT / 嵌入式关联

路线 要点
HFT 描述符环 = coherent pool 常驻（初始化建好，永不重建）；数据面缓冲 = map 一次 + sync 循环复用，绝不每包 map/unmap；x86 上 dma_need_sync 为 false，连 sync 分支都省——DPDK 更进一步直接旁路这整套 API（用户态 mempool 自己管理，思想同源）
嵌入式 ARM 上 dma_need_sync 常真，sync 是真实 cache 维护——忘调即静默损坏；描述符池用 dma_pool_create 时 align 传 cacheline 大小是标准做法
低延迟 map/unmap 不是免费操作：可能建 IOMMU 映射、可能分配 swiotlb bounce buffer（同步拷贝！）。热路径黄金律：一次映射、循环 sync（或干脆常驻 coherent），零映射开销

代码自测

参考答案

Q1：为什么不能拿 vmalloc 返回的地址直接喂 dma_map_single？

vmalloc 只保证虚拟地址连续，物理页是散的。dma_map_single 无 scatter/gather 能力（dma-api.rst 明文），要求底层物理连续，映射散页直接失败。两条出路：用 kmalloc（物理连续）或改用 dma_map_sg() / dma_alloc_noncontiguous()。

Q2：dma_unmap_single 为什么四个参数必须与 map 时逐项相同？

unmap 要用（地址、长度、方向）反查映射期的记录做清理（IOMMU解除映射、释放 swiotlb bounce、归还映射计数）。DMA 地址本身不含长度和方向信息，任何一个不一致，内核要么找不到记录（泄漏映射），要么清错范围。

Q3：coherent 映射保证"CPU 写立即可见"，为什么描述符更新还要 wmb()？

coherent 解决的是可见性位置（cache vs RAM），不解决乱序。CPU 可能重排对一致内存的写：desc->word1 = DESC_VALID（有效位）先于 desc->word0 = addr（数据）到达内存，设备看到"有效但地址是旧的"描述符。howto 原文示例：

desc->word0 = address;
wmb();                  /* 保证 word0 先落地，再置有效位 */
desc->word1 = DESC_VALID;

一致性 ≠ 顺序性，屏障永远归驱动管。
