## 本节讲什么

**DMA = Direct Memory Access 直接内存访问：硬件自己搬运内存数据，不需要 CPU 亲自拷贝。**

比喻：没有 DMA 时老板（CPU）亲自一箱一箱搬货；有 DMA 时雇搬运工（DMA 控制器）搬货——老板只需下达指令"把这块数据从 A 地址搬到 B 地址"，然后回去办公；搬运工干完活，敲门（**中断**）通知老板完工。

> 一句话浓缩：老方式——中断 CPU，CPU 亲自访存拷贝到内存；DMA 方式——配置完，硬件自己拷贝到内存，CPU 解放，结束才中断。**结局都到内存，干活的角色换了。**

## 要点

### 没有 DMA 会怎样（以网卡收包为例）

```
【无 DMA · 普通 IO】                       【有 DMA】
┌──────┐  每小段数据一次中断              ┌──────┐
│ 网卡 │──┐                              │ 网卡 │──┐
└──────┘  │ 硬件小缓冲区                  └──────┘  │
          ▼                                       ▼
   ┌───────────────┐                      ┌──────────┐
   │CPU 执行访存指令 │ in/out·load/store    │ DMA 控制器│ 独立硬件搬运
   │ 一字节一字节拷  │                      └──────────┘
   └───────────────┘                              │
          │                                       │ 搬完才发 1 次中断
          ▼                                       ▼
   CPU 全程被占用，                          CPU 并行跑别的任务，
   干不了别的事                              只需处理包本身
          │                                       │
          └───────────────┬───────────────────────┘
                          ▼
                ┌──────────────────┐
                │    主内存 RAM     │ ← 共同终点：DMA 不能跳过内存
                └──────────────────┘
```

**普通 IO 的搬运本质（指令层）**：CPU 停下手上正在跑的程序，亲自执行**访存指令**——PIO 方式走 x86 `in`/`out` 指令读硬件 IO 端口，MMIO 方式走普通 `load`/`store` 访问设备寄存器映射区——把数据一字节一字节从硬件拷到主内存。**搬运这个动作是 CPU 执行指令完成的**，期间 CPU 跑不了别的计算任务。

> 比喻：货车到货，老板（CPU）放下手里工作，自己一箱一箱把货搬进仓库。

| | 无 DMA（老式 PIO） | 有 DMA |
|---|---|---|
| 谁搬运数据 | **CPU 执行访存指令亲自拷** | **DMA 硬件搬运**（不执行任何 CPU 指令） |
| 中断次数 | 每来一小块数据中断一次 | **整块搬完才 1 次中断** |
| CPU 占用 | 全程占用，大量时间耗在搬运苦力活 | 只下达命令 + 收完工通知 |

### DMA 方式的三步

1. **配置**：CPU 提前给 DMA 硬件配好**源地址、目标物理内存地址、要搬多少字节**，配置完即可回去跑业务代码
2. **独立搬运**：硬件数据出来后，**DMA 控制器硬件直接完成"硬件→内存"的搬运——这一步完全不执行 CPU 的 load/store 指令**。CPU 此时可以跑别的线程、做计算
3. **完成中断**：全部搬运完成，DMA 发一次中断"搬完了"，CPU 才去内存处理这份数据

### ⭐ DMA 是谁在跑：三段流程的角色拆解

"DMA 控制器（DMA Controller）"必须精确化：**它是芯片内一块独立硬件，不是 CPU 内核的一部分**——自带总线主控（bus master）能力，能独立发起内存读写事务，完全不需要 CPU 替它执行任何指令。三步走按"谁在干活"拆开：

| 阶段 | 谁在干活 | 干什么 | CPU 状态 |
|------|---------|--------|---------|
| ① 配置 | **CPU** | 把源地址/目标地址/长度写进 DMA 控制器寄存器（或控制块），最后写"启动"位 | 忙（执行驱动代码） |
| ② 搬运 | **DMA 控制器硬件** | 按配置**自发**发起总线事务搬运数据 | **闲**——回去跑别的线程；搬运期间 CPU 不执行任何 load/store 拷贝指令 |
| ③ 结束通知 | **DMA 控制器 → CPU** | 搬完发一次硬件中断，CPU 才回来善后 | 被中断唤起 |

> 高频疑问："搬运是 CPU 指导的，还是硬件自带 DMA 自发去干的？"——**两者都有，分阶段**：配置阶段 CPU 写寄存器"下任务单"；搬运阶段 DMA 控制器按配置自发执行，CPU 已完事不再参与。一句话：**CPU 商量好任务，硬件自发去干，干完按铃**。

**搬运机器人比喻**：CPU 像仓库管理员，把"从 A 货架搬 100 箱到 B 货架"的工单填好交给搬运机器人（DMA 控制器）；机器人自己干，管理员回去办公；机器人干完按铃（中断）通知验收。

### DMA 控制器的两种硬件形态

"芯片内部一块独立硬件"只是形态之一。真实世界分两类：

| | 集中式 DMA 控制器 | 设备内嵌总线主控 |
|---|---|---|
| 形态 | SoC 里一块**独立外设**，多通道共享，各外设"租"通道用 | **设备自己**就是总线主控（设备内含 DMA 引擎） |
| 实例 | 树莓派 `bcm2835`：15 个通道（驱动 `drivers/dma/bcm2835-dma.c`，`BCM2835_DMA_MAX_DMA_CHAN_SUPPORTED = 14`） | 现代网卡（e1000/igb/ixgbe…）：自己发 PCIe 内存写事务，不经任何集中控制器 |
| 配置载体 | 通道寄存器 + **控制块（Control Block）链**——内存里的一串任务单 | 设备自己的**描述符环**（RX/TX ring） |
| 谁排队任务 | CPU 填 CB 链，`next` 字段串成链，硬件自己跟链执行 | CPU 填描述符环，设备按 head/tail 指针自己消费 |
| 典型平台 | 嵌入式 SoC（ARM/MIPS） | x86/服务器 PCIe 设备 |

树莓派控制块的真实结构（v6.6 `drivers/dma/bcm2835-dma.c:53`——"任务单"的硬件实证）：

```c
struct bcm2835_dma_cb {
    uint32_t info;     /* 方式标志：地址自增、完成中断使能(BCM2835_DMA_INT_EN)… */
    uint32_t src;      /* 源地址     —— 三步走"配好源地址"的落点 */
    uint32_t dst;      /* 目标地址   —— "配好目标物理内存地址" */
    uint32_t length;   /* 搬多少字节 —— "配好要搬多少" */
    uint32_t stride;   /* 2D 步进（搬矩阵行时跳过行距） */
    uint32_t next;     /* 下一个控制块的地址 —— CB 链！硬件自己跟链 */
    uint32_t pad[2];
};
```

读这段结构体的三个要点：① 配置阶段 CPU 填的就是这张表（`bcm2835_dma_prep_dma_memcpy()` 把 src/dst/len 逐项写进 CB）；② `next` 串成链后，**一串任务 CPU 只配置一次**，硬件顺链自发执行多个搬运；③ `info` 里的 `BCM2835_DMA_INT_EN` 决定搬完是否发中断——三步走的第③步由这个位控制。

> 历史注脚：x86 集中式控制器的鼻祖是 Intel 8237 ISA DMA 控制器（1970s 设计，曾是 PC 标配）——`drivers/dma/i8237.c` 在 v6.6 已从主线删除（实测 404），ISA DMA 时代落幕；但"集中式控制器 + 多通道"的形态在嵌入式 SoC 里仍是主流（树莓派就是）。

### 网卡真实链路（有 DMA 后一次收包的完整三步）

```
① 网卡 DMA 引擎（设备内嵌形态）把报文写入内存 RX 缓冲区（描述符环指向的页）
② 搬完发硬件中断；驱动中断处理通常只做"关中断 + 调度 NAPI 轮询"，不碰数据
③ NAPI 软中断里 CPU 才处理包：XDP（skb 之前）→ 分配 sk_buff → 协议栈上送
```

关键认知：**中断只是"搬完了"的信号，不含数据本身**——数据早已被 DMA 落进内存，中断处理程序里拿地址直接就能读。DPDK 做的事就是把 ②③ 的"中断 + 轮询"改成"纯轮询"，连中断开销也省掉（见 [13-dpdk](../../../13-dpdk/01-Intro-Book/)）。

### 两个常见错误认知（自测高频错点）

- ❌ "DMA 搬运时 CPU 会暗中帮忙 load/store"——不会。搬运是 DMA 控制器自己发起的总线事务，CPU 一条拷贝指令都不执行
- ❌ "有 DMA 就完全不需要 CPU"——配置阶段（写寄存器/描述符）和完成处理（中断/轮询收尾）都是 CPU 的活。DMA 省掉的只是"搬运"这一段，不是全部


### ⭐ 共同点与唯一差别（最容易被忽略的洞察）

✅ **两种方式，数据最终都必须落到主内存 RAM 里**——不管 CPU 搬还是 DMA 硬件搬，终点都是内存。**DMA 不能跳过内存。**

| | 普通 IO | DMA IO |
|---|---|---|
| 数据终点 | 主内存 RAM | 主内存 RAM（**相同**） |
| 搬运执行者 | **CPU 访存指令**（占用 CPU） | **DMA 硬件**（不消耗 CPU） |

**唯一真正的差别：谁执行搬运拷贝动作。**

**误区澄清**：

- ❌ 不是 DMA"不走内存"
- ✅ 是 DMA **不走 CPU 的寄存器流水线**——搬运这件活交给独立硬件，内存依旧必经

### 磁盘例子对比（指令视角）

1）**无 DMA**：磁盘有数据 → 中断 CPU → CPU 执行 `in`/`out` 指令把数据读进来，再一条条 `store` 指令写入内存——CPU 全程参与搬运。
2）**有 DMA**：CPU 告诉 DMA"把磁盘的数据搬到物理内存 0x80000 地址" → 回去运行程序 → DMA 硬件自己把磁盘数据传输到内存 → 全部完成后中断 CPU → CPU 此时才去内存读数据。

### 两个典型场景

| 场景 | 流程 | 备注 |
|------|------|------|
| **网卡 DMA** | 网卡收包 → DMA 直接写入内存缓冲区 → 完成后中断，CPU 只处理包不拷贝 | **DPDK 高性能网络重度依赖**；HFT 低延迟基石 |
| **SD 卡 / USB 麦克风** | 麦克风持续采集音频样本 → DMA 持续搬进内存，整块搬完才 1 次中断 | 而不是每个采样点中断一次 |

### ⚠️ 关键概念：DMA 地址 ≠ 虚拟地址

- **DMA 硬件大多不理解虚拟地址**——设备发起的总线事务**不经过 CPU 的 MMU**。用户态/内核态用的都是虚拟地址，DMA 硬件访问内存必须给它**总线侧的地址**。
- 内核 API：`dma_alloc_coherent()` 专门分配物理连续内存，**返回值是 CPU 侧虚拟地址**，同时通过出参拿到给硬件用的地址。

```c
void *
dma_alloc_coherent(struct device *dev, size_t size,
                   dma_addr_t *dma_handle, gfp_t flag);
/* 返回值  → CPU 用的虚拟地址（分配失败为 NULL）
 * dma_handle → 给硬件的 DMA 地址（出参）              */
```

**坑**：不能拿 `kmalloc` 出来的虚拟地址直接丢给 DMA——虚拟地址对 DMA 无效，硬件根本不认。

**精度修正（按 v6.6 内核文档核对）**：`dma_handle` 是 **DMA 地址（总线地址）**，**不严格等于物理地址**。官方 `Documentation/core-api/dma-api.rst` 原文：

> A CPU cannot reference a `dma_addr_t` directly because **there may be
> translation between its physical address space and the DMA address space**.

- 平台有 **IOMMU/SMMU** 时，DMA 地址是 IOMMU 映射后的 **IOVA**，和物理地址是两套空间（IOMMU 甚至能把物理上不连续的页映射成一个连续 DMA 地址段）。
- 树莓派这类无 SMMU 的简单 SoC 上，DMA 地址实践中就等于物理地址——所以直觉"只认物理地址"在嵌入式裸机上成立，但在服务器/现代 x86 上必须升级为"只认**总线地址**"。

### DMA 缓冲区

一块专门给**硬件和 CPU 双向交换数据**的内存：硬件写、CPU 读；或 CPU 写、硬件读。一致性分配（`dma_alloc_coherent`）出来的就是典型 DMA 缓冲区。

### 与 `copy_from_user` 的对比

| | `copy_from_user` | DMA |
|---|---|---|
| 执行者 | **CPU 亲自**做内存拷贝 | **硬件**做内存搬运 |
| 本质 | CPU 执行循环拷贝指令 | DMA 控制器独立搬运 |
| CPU 占用 | 占用（拷贝期间跑不了别的） | 不占用（并行执行其他代码） |
| 数据终点 | 主内存（用户↔内核缓冲都在 RAM） | 主内存（**相同**） |

→ 三者的统一视角：`copy_from_user` 与 DMA 的数据**都落到内存，差别只在执行者**——前者烧 CPU 指令周期，后者烧独立硬件。

### 两种 DMA 模式（对应 12.1 / 12.2）

| | 一致 DMA（coherent） | 流式 DMA（streaming） |
|---|---|---|
| 内存来源 | **专用分配**（`dma_alloc_coherent`） | **复用已有内存**（`dma_map_single` 等） |
| Cache 处理 | 分配时就对 cache 做屏蔽/映射，CPU 与硬件**立刻**看到彼此的写 | 每次 map 时做 **cache 刷新/失效** |
| 性能 | 分配昂贵（部分平台最小一页），适合长期缓冲 | 性能更高，**网卡多用** |
| 典型用户 | 描述符环、控制块 | 收发包数据缓冲 |

官方定义（v6.6 dma-api.rst）：Consistent memory is memory for which a write by either the device or the processor can **immediately** be read by the other without worrying about caching effects.

```c
/* 流式：映射一块已有的 CPU 虚拟内存给设备用 */
dma_addr_t
dma_map_single(struct device *dev, void *cpu_addr, size_t size,
               enum dma_data_direction direction);
/* direction: DMA_TO_DEVICE / DMA_FROM_DEVICE / DMA_BIDIRECTIONAL */
```

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | **网卡 DMA 把报文直接丢内存，CPU 省去拷贝开销 → 直接降低收包延迟**；DPDK 全程基于此（内核旁路 + DMA + 轮询模式收包）；DMA 落地之后最早的决策点是 **XDP**（skb 之前，见衔接） |
| 嵌入式 | 音频 ADC / SD 卡 / SPI 等低速外设靠 DMA 连续搬运数据流，CPU 只在每个"块"完工时被中断一次 |
| 低延迟线索 | 12.1 缓存一致性标注**精读（低延迟）**——coherent 内存牺牲 cache 性能换一致性，流式映射靠 flush/invalidate 保正确性，两条路线的延迟代价要分开量化 |

## 代码示例

（环境无 C 编译器，以下为按 v6.6 `Documentation/core-api/dma-api.rst` 人工核对过的骨架，未真机编译）

```c
#include <linux/dma-mapping.h>

/* 一致 DMA：收包描述符环 */
struct rx_ring {
    void       *cpu_addr;    /* CPU 侧虚拟地址 */
    dma_addr_t  dma_addr;    /* 硬件侧 DMA 地址 */
};

static int rx_ring_alloc(struct device *dev, struct rx_ring *r)
{
    r->cpu_addr = dma_alloc_coherent(dev, RING_SIZE,
                                     &r->dma_addr, GFP_KERNEL);
    if (!r->cpu_addr)
        return -ENOMEM;

    /* 硬件寄存器里写的是 r->dma_addr —— 绝不是 r->cpu_addr！
     * 坑：dma_alloc_coherent 只能在开中断的上下文调用 */
    iowrite32(r->dma_addr, dev_regs + RX_RING_BASE);
    return 0;
}

static void rx_ring_free(struct device *dev, struct rx_ring *r)
{
    dma_free_coherent(dev, RING_SIZE, r->cpu_addr, r->dma_addr);
    /* dev/size/dma_handle 必须与分配时完全一致；cpu_addr 传返回的虚拟地址 */
}
```

## 代码自测

<details>
<summary>参考答案</summary>

**Q1：DMA 搬运内存的时候，CPU 在干什么？**

CPU 可以并行跑别的代码，不需要等待搬运；DMA 结束靠**中断**通知 CPU。

**Q2：为什么 DMA 不能用虚拟地址，只能用物理地址？**

设备发起的总线事务**不经过 CPU 的 MMU**——MMU 的页表翻译只对 CPU 发出的访存生效，硬件看到的地址就是总线地址，没有任何东西帮它做 VA→PA 翻译。
进阶修正：有 **IOMMU** 的平台上，设备地址会经过 IOMMU 翻译（IOVA→PA），所以现代说法是"设备只认** DMA 地址**"；无 IOMMU 的简单 SoC（如树莓派）上 DMA 地址就等于物理地址。

**Q3：`dma_alloc_coherent` 返回的虚拟地址能直接写给硬件寄存器吗？**

不能。写给硬件的必须是**出参 `dma_handle`** 里的 DMA 地址；返回值是给 CPU 访问用的虚拟地址。两者一个走 CPU/MMU，一个走设备总线，是两套地址空间。

**Q4：DMA 传输的时候，CPU 完全不工作吗？**

不是。CPU 可以正常跑别的任务/线程、做计算，只是**不参与数据拷贝搬运这件事**——搬运由 DMA 硬件独立完成。

反向误区同理：DMA 也不能让数据"不经过内存"直达 CPU——**终点永远是 RAM，变的只是干活的角色**。

**Q5：DMA 搬运数据的时候，CPU 会不会执行 load/store 做数据拷贝？**

**不会**。搬运阶段是 DMA 控制器自己发起的总线事务（它自己是 bus master），CPU 一条访存拷贝指令都不执行——这正是 DMA 的定义性特征。CPU 的 load/store 只出现在：①配置阶段写 DMA 寄存器/控制块；②搬运完成后处理内存里的数据。

**Q6：DMA 控制器只有"芯片里一块独立硬件"这一种形态吗？**

不止，分两类：**集中式控制器**（如树莓派 bcm2835，SoC 内独立外设、15 通道共享，任务用控制块链排队）和**设备内嵌总线主控**（如现代网卡，DMA 引擎在设备内部，任务用描述符环排队）。x86 服务器上主流是后者；嵌入式 SoC 两者并存（网卡内嵌 + 音频/SD 走集中式控制器通道）。

</details>
