# 12.3 scatter/gather：把"物理连续"的枷锁拆掉

## 本节讲什么

12.2 给 `dma_map_single` 列了两条硬约束，第一条"**物理连续**"在真实世界几乎必然被打破：

- **用户缓冲区、page cache 天然按页散布**——一次大 read 的数据落在多个不连续物理页上
- 系统长期运行后**物理内存碎片化**，连 `kmalloc` 大块连续分配都会失败（嵌入式小内存尤其明显）
- 网络 MTU 9000（jumbo frame）一个包就跨多页

scatter/gather（SG，发散/聚集）就是解法：**把"散"用一张链表描述出来，一次调用映射一整串**。名字的两半各自对应一个方向：

- **scatter（发散）**：设备一次 DMA 写操作，数据落到**多个不连续**内存块（收包）
- **gather（聚集）**：从**多个不连续**内存块收集数据，凑成一次 DMA 传输（发包）

## 要点

### 为什么不干脆循环调 `dma_map_single`？

| | 循环 N 次 `dma_map_single` | 一次 `dma_map_sg` |
|---|---|---|
| 调用开销 | N 次（每次可能走 IOMMU 映射/上锁） | **1 次** |
| 智能合并 | 无——物理相邻的两页也被当成两段 | **有**——相邻项可合并成一段，减少硬件描述符占用 |
| 硬件视角 | 驱动自己把 N 个地址分头写进 N 个描述符 | 拿到的就是映射后的段列表，直接填 |

`dma-api-howto.rst` 原文点破合并的价值：对**不能做 scatter-gather、或 SG 项数很少的卡**（描述符环小），把多个连续 sglist 项合并成一项是巨大优势——页粒度映射时，"前一项结尾、后一项开头都在页边界"即可合并。

### `struct scatterlist`：最小单元的真身（v6.6 `include/linux/scatterlist.h:11`）

```c
struct scatterlist {
    unsigned long   page_link;   /* 页指针 + 低 2 位复用标志，见下 */
    unsigned int    offset;      /* 页内起始偏移 */
    unsigned int    length;      /* 这段的字节数（CPU 视角） */
    dma_addr_t      dma_address; /* map_sg 填入：这段的 DMA 地址 */
#ifdef CONFIG_NEED_SG_DMA_LENGTH
    unsigned int    dma_length;  /* map_sg 填入：映射后的长度（可被合并改写） */
#endif
#ifdef CONFIG_NEED_SG_DMA_FLAGS
    unsigned int    dma_flags;
#endif
};
```

**`page_link` 一个字段装三种信息**（源文件注释原话："the two lower bits are reserved for this information"）：

```
page_link 的位布局（scatterlist.h:67-75）
┌────────────────────────────────────┬───────┬───────┐
│  struct page * 指针（高位，按指针对齐保证低位空闲） │ bit 1  │ bit 0  │
└────────────────────────────────────┴───────┴───────┘
                                      SG_END  SG_CHAIN
                                      0x02    0x01

bit 0 = SG_CHAIN：本项不是数据，page_link 指向【另一张 sg 列表】（链表拼接）
bit 1 = SG_END  ：本项是整张表的最后一项（sg_next() 到此返回 NULL）
```

`sg_next()` 的推进逻辑正是靠这两个标志：默认 `sg + 1`（数组连续），遇到 `SG_CHAIN` 跳到新表，遇到 `SG_END` 停——**sg 既能当数组用，也能当链表用**，这就是"表"的本质。

**两个访问宏**（map 之前之后是不同的字段，scatterlist.h:31-36）：

```c
#define sg_dma_address(sg)  ((sg)->dma_address)
#ifdef CONFIG_NEED_SG_DMA_LENGTH
#define sg_dma_len(sg)      ((sg)->dma_length)   /* 有 IOMMU 的架构 */
#else
#define sg_dma_len(sg)      ((sg)->length)       /* 无 IOMMU，长度不会被改写 */
#endif
```

> 注意注释明文：这两个宏**只能在 `dma_map_sg` 之后**用来取**总线地址**——map 之前你用的是 `page_link/offset/length`（CPU 页视角），map 之后才切换到 `dma_address/dma_len`（设备总线视角）。

### `dma_map_sg`：一次映射一整串

```c
int dma_map_sg(struct device *dev, struct scatterlist *sg,
               int nents, enum dma_data_direction direction);
```

**返回值语义**（`dma-api.rst:376`，与 `dma_map_single` 完全不同）：

- 成功 → 返回**实际映射出的 DMA 段数**，可以**小于** `nents`——物理相邻（或 IOMMU 下虚拟相邻）的项会被合并成一段
- 失败 → 返回 **0**（不是 -1，也不能用 `dma_mapping_error` 查——那是 single/page 系的判定法，12.2 错误检查表的 sg 行）

**两条陷阱**（文档明文）：

1. **映射会破坏 sg 里的原有信息**——`dma_address`/`dma_length` 会被覆写。所以**同一张 sg 表不能 map 第二次**（map 前先留好 CPU 侧信息）
2. 映射失败绝不能装没看见——文档原话（块设备驱动语境）：abort 请求甚至 oops 都比"什么都不做然后损坏文件系统"强

**标准用法**（`dma-api.rst:395` 官方示例）：

```c
int i, count = dma_map_sg(dev, sglist, nents, direction);
struct scatterlist *sg;

for_each_sg(sglist, sg, count, i) {      /* 循环 count 次，不是 nents 次！ */
    hw_address[i] = sg_dma_address(sg);  /* 填进硬件描述符的 DMA 地址 */
    hw_len[i]     = sg_dma_len(sg);
}
```

### `for_each_sg` 的真身：不是简单的数组遍历

```c
/* include/linux/scatterlist.h:195 */
#define for_each_sg(sglist, sg, nr, __i) \
    for (__i = 0, sg = (sglist); __i < (nr); __i++, sg = sg_next(sg))
```

- `sg_next(sg)` 逐项推进并处理 `SG_CHAIN` 跨表跳转——所以循环次数受 `nr` 限制，**必须传 map_sg 的返回值 `count`**
- howto 原文提醒：老代码里直接访问 `sg->address`/`sg->length` 的写法（2.4 时代 API）一律换成 `sg_dma_address(sg)`/`sg_dma_len(sg)`

### ⭐ `dma_unmap_sg` 的 nents 陷阱（文档特意加粗的 note）

```c
void dma_unmap_sg(struct device *dev, struct scatterlist *sg,
                  int nents, enum dma_data_direction direction);
```

**`nents` 必须传你当初传给 `dma_map_sg` 的那个值，绝不能传 map 返回的 `count`**（`dma-api.rst:417` note 原文：`must be the number you passed in, *not* the number of DMA address entries returned`）。

为什么：unmap 要按**原始列表**逐项清理映射记录（IOMMU 解除、swiotlb bounce 释放）；传 `count`（≤ nents）会漏掉被合并项的原始信息，映射记录泄漏——而 DMA 地址空间是**共享资源**（howto：耗尽它能把整台机器搞挂）。

这与 12.2 的"`dma_unmap_single` 四参数必须逐项一致"是同一条纪律：**unmap 永远对着 map 时你给的参数，不对着 map 产生的结果**。

### `dma_sync_sg_for_{cpu,device}`：与 12.2 同一套所有权语义

```c
void dma_sync_sg_for_cpu(struct device *dev, struct scatterlist *sg,
                         int nents, enum dma_data_direction direction);
void dma_sync_sg_for_device(struct device *dev, struct scatterlist *sg,
                            int nents, enum dma_data_direction direction);
```

- 所有参数必须与**当初传给 `dma_map_sg` 的完全一致**（这里的 nents 同样是原始值）
- 方向语义、什么时候可以省（拒收的 FROM_DEVICE 缓冲无需 sync 回设备）与 12.2 收包生命周期完全同构，不再重复

### `struct sg_table` 与"非连续分配"系列（v6.6 `dma-api.rst:610-700`）

`dma_map_sg` 是"**映射已有内存**"的 SG 版；v6.6 还有反过来的一族——**分配时就按非连续方式给你，并保证 DMA 侧可用**：

```c
/* include/linux/scatterlist.h:39 */
struct sg_table {
    struct scatterlist *sgl;      /* 列表本体 */
    unsigned int nents;           /* 【映射后】的条目数（DMA 视角） */
    unsigned int orig_nents;      /* 【原始】列表大小（CPU 视角） */
};
```

**`nents` vs `orig_nents`——一张表两个视角**，v6.6 连遍历宏都分好了对：

| 宏 | 遍历哪个口径 | 用途 |
|---|---|---|
| `for_each_sgtable_sg(sgt, sg, i)` | `orig_nents` | CPU 侧操作（如逐项 set_page） |
| `for_each_sgtable_dma_sg(sgt, sg, i)` | `nents` | 消费映射结果（填硬件描述符） |

系列 API：

```c
struct sg_table *dma_alloc_noncontiguous(struct device *dev, size_t size,
                enum dma_data_direction dir, gfp_t gfp, unsigned long attrs);
void  dma_free_noncontiguous(struct device *dev, size_t size,
                struct sg_table *sgt, enum dma_data_direction dir);
void *dma_vmap_noncontiguous(struct device *dev, size_t size, struct sg_table *sgt);
void  dma_vunmap_noncontiguous(struct device *dev, void *vaddr);
int   dma_mmap_noncontiguous(struct device *dev, struct vm_area_struct *vma,
                size_t size, struct sg_table *sgt);
```

`dma_alloc_noncontiguous` 的三个关键语义（文档原文核对）：

1. 分配的是**非一致（non-coherent）且可能非连续**的内存——本身就带 DMA 映射，返回的 `sg_table` 直接可用
2. **保证 `sgt->nents == 1`**：DMA 侧恰好映射成 1 段（IOMMU 把散页合并成单个连续 IOVA）；但 `orig_nents` 可以 >1——CPU 物理视角还是散的。**"硬件看着连续、物理上散着"的官方实现**
3. `attrs` 只能是 0 或 `DMA_ATTR_ALLOC_SINGLE_PAGES`（强制每项单页）；用前 `dma_sync_sgtable_for_device()`、读前 `dma_sync_sgtable_for_cpu()`——**流式语义，sync 规矩一个不少**（与 12.2 循环复用同一套）

`dma_vmap_noncontiguous` 给散页一个**连续的内核虚拟映射**（vmap 式拼页）；映射后的一致性要手动用 `flush_kernel_vmap_range()`/`invalidate_kernel_vmap_range()` 管。`dma_mmap_noncontiguous` 进一步映射到**用户地址空间**（零拷贝用户态消费的原料）。

### API 速查表

| API | 一句话 | 失败判定 |
|---|---|---|
| `dma_map_sg(dev, sg, nents, dir)` | 一次映射整串，返回实际段数 | **返回 0** |
| `dma_unmap_sg(dev, sg, nents, dir)` | 整串解除；**nents 传原始值** | void |
| `dma_sync_sg_for_{cpu,device}` | 所有权切换，参数与 map 一致 | void |
| `dma_sync_sgtable_for_{cpu,device}` | sg_table 版 sync（配合 noncontiguous 系） | void |
| `dma_alloc_noncontiguous` | 分配非连续内存并保证 DMA 侧 1 段 | **NULL** |
| `dma_free_noncontiguous` | 释放（dev/size/dir/sgt 逐项一致） | void |
| `dma_vmap/vunmap_noncontiguous` | 给散页拼连续内核映射 | vmap：NULL/ERR_PTR |
| `dma_mmap_noncontiguous` | 散页映射进用户地址空间 | 负 errno |

### 平台相关细节（howto "Platform Issues"，写移植代码才会撞上）

- **`CONFIG_NEED_SG_DMA_LENGTH`**：支持 IOMMU（含软件 IOMMU/swiotlb）的架构必须开——它控制 `dma_length` 字段存在与 `sg_dma_len()` 走哪个分支。x86/ARM64 都开，`sg_dma_len` 取的是映射后长度
- **`ARCH_DMA_MINALIGN`**：架构必须保证 `kmalloc` 出来的缓冲不与别人**共享 cacheline**（见 `arch/arm/include/asm/cache.h`）——非一致架构上 SG 每一段的对齐安全性由这条兜底

## HFT / 嵌入式关联

| 路线 | 要点 |
|------|------|
| HFT | **网络栈里 SG 无处不在**：skb 的非线性区就是页片数组——`skb_frag_t` 是 `bio_vec` 的别名（`skbuff.h:362`），同样是"页指针+偏移+长度"三件套，`frags[MAX_SKB_FRAGS]` 挂在 `skb_shinfo` 里；网卡支持 scatter-gather（`NETIF_F_SG`）时 TX 直接把 frags 逐段 DMA，**大包免拼连续内存**——TSO 大段发送的前提之一。DPDK 的 mbuf 多段链思想同源（用户态自己管页链） |
| 嵌入式 | 无 IOMMU 的 SoC（如树莓派）上 `dma_map_sg` 的合并机会只剩"物理恰好相邻"——返回值常等于 nents；**不要在无 IOMMU 平台上指望 IOVA 合并**。集中式 DMA 控制器的驱动侧正是 SG 消费者：bcm2835 的 `bcm2835_dma_prep_slave_sg()` 就是把 sglist 逐段翻译成控制块链 |
| 低延迟 | 一次 `dma_map_sg` 建好 N 段映射（可能仅 1 次 IOTLB 操作），比热路径 N 次 `dma_map_single` 省锁省 tlb 维护；**但最优仍是 12.2 的纪律：缓冲复用、map 一次、循环 sync**——SG 是"内存形状不合身"时的补救，不是热路径常态 |

## 代码示例

（环境无 C 编译器，以下为按 v6.6 `dma-api.rst`/`scatterlist.h` 人工核对过的骨架，未真机编译）

TX 发送一个跨多页的缓冲：

```c
#include <linux/scatterlist.h>
#include <linux/dma-mapping.h>

int my_tx(struct device *dev, struct page **pages, int npages,
          unsigned long offset, size_t total_len)
{
    struct scatterlist sg[MAX_SEG];
    struct scatterlist *sgp;
    dma_addr_t hw_addr[MAX_SEG];
    unsigned int hw_len[MAX_SEG];
    int i, count;

    /* ① 建表：散页 → sg 数组（sg_init_table 清零并打 SG_END 标记） */
    sg_init_table(sg, MAX_SEG);
    /*   生产环境用 sg_alloc_table_from_pages()：物理相邻页自动squash成一项 */
    for (i = 0; i < npages; i++)
        sg_set_page(&sg[i], pages[i],
                    min_t(size_t, PAGE_SIZE - (i ? 0 : offset), total_len),
                    i ? 0 : offset);

    /* ② 一次映射整串：返回实际段数（相邻页可能被合并） */
    count = dma_map_sg(dev, sg, npages, DMA_TO_DEVICE);
    if (!count)                        /* sg 系失败判定：返回 0，不是 -1 */
        return -ENOMEM;

    /* ③ 消费映射结果：循环 count 次（map 返回值！），填硬件描述符 */
    for_each_sg(sg, sgp, count, i) {
        hw_addr[i] = sg_dma_address(sgp);
        hw_len[i]   = sg_dma_len(sgp);
        /* write_tx_desc(ring, i, hw_addr[i], hw_len[i]); */
    }

    /* ④ 传输完成（中断/NAPI 回调里）：
     *    unmap 的 nents 传【原始传入值 npages】，不是 count！ */
    dma_unmap_sg(dev, sg, npages, DMA_TO_DEVICE);
    return 0;
}
```

## 代码自测

<details>
<summary>参考答案</summary>

**Q1：`dma_map_sg` 的返回值为什么可能小于传入的 `nents`？**

映射过程允许**合并**：物理相邻的项（或 IOMMU 下虚拟地址相邻的项）可以合并成一个 DMA 段，返回值是**实际映射出的段数**。howto 原文举例：页粒度映射时，前一项结尾、后一项开头都在页边界上即可合并——对 SG 项数有限的卡（描述符环小）是巨大优势。

**Q2：`dma_unmap_sg` 的 `nents` 该传什么？为什么？**

传**当初传给 `dma_map_sg` 的原始值**，绝不传 map 返回的 `count`。unmap 按原始列表逐项清理映射记录（IOMMU 解除、swiotlb 释放）；传 count（≤ nents）会漏清被合并项的原始记录，映射泄漏——DMA 地址空间是共享资源，泄漏累积能搞挂整机。纪律同 12.2：**unmap 对着 map 时"你给的"参数，不对着 map "产出的"结果**。

**Q3：`struct scatterlist` 里没有 next 指针，`for_each_sg` 怎么遍历链表？**

藏在 `page_link` 的低 2 位：bit 0（`SG_CHAIN`）置位表示本项是"链接项"，`page_link` 高位存**下一张 sg 表的地址**；bit 1（`SG_END`）置位表示本项是终点。`sg_next()` 据此分派：默认 `sg+1`（数组连续布局），遇 `SG_CHAIN` 跳表，遇 `SG_END` 返回 NULL。**一个字段复用"页指针/链接指针/结束标记"三种信息**——因为 struct page 指针天然按指针对齐，低 2 位必为 0，白送。

**Q4：`dma_alloc_noncontiguous` 保证 `sgt->nents == 1` 但 `orig_nents` 可以 > 1，说明什么？**

物理内存是散的（CPU 视角 `orig_nents` 个片段），但 IOMMU 把这些散页映射成了**单个连续的 IOVA 段**（DMA 视角 `nents` = 1）。设备在总线上看到一段连续地址，实际落到物理内存是散页——**"给设备看的连续"和"物理上的连续"被 IOMMU 解耦**。这是无 IOMMU 平台做不到的（只能老老实实物理连续或 SG 多段）。

**Q5：同一张 sg 表 map 两次会怎样？**

第一次 map 会**覆写** sg 里的 `dma_address`/`dma_length`（映射结果存进去），原始的 CPU 侧信息（页指针除外）已丢；第二次 map 建立在"已污染"的表上，行为不可靠。文档明文：**sg 不能被 map 第二次，映射过程允许破坏 sg 里的信息**。需要重映射时必须重新 `sg_init_table` + `sg_set_page` 建表。
