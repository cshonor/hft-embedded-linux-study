# 6.6 · 缓存属性与惰性 fault：mmap 怎么才算"对"

> **本节讲什么：** `pgprot_noncached` / `pgprot_writecombine` / 默认 cached 三者怎么选、**为什么 MMIO 寄存器必须 noncached**（不只是"为了看到最新值"，还有更硬的理由）、以及什么时候该用 `fault` 惰性映射而不是一次性建完页表。

---

## 三种缓存策略

| 策略 | 设置方式 | CPU 读 | CPU 写 | 适用 |
|------|---------|-------|-------|------|
| **cached**（默认） | 不动 `vm_page_prot` | 走缓存 | 写回缓存 | 普通内存。**DMA/MMIO 禁用** |
| **noncached** | `pgprot_noncached(prot)` | 直达内存 | 直达内存 | **MMIO 寄存器**、DMA 缓冲 |
| **write-combine** | `pgprot_writecombine(prot)` | 直达内存 | **可合并/缓冲** | 帧缓冲、显存、大块输出型 DMA |

```c
vma->vm_page_prot = pgprot_noncached(vma->vm_page_prot);      /* MMIO */
vma->vm_page_prot = pgprot_writecombine(vma->vm_page_prot);   /* 帧缓冲 */
```

---

## ★ 为什么 MMIO 必须 noncached：三个理由，不只是"看到最新值"

直觉答案是"怕读到缓存里的旧值"。**这只对了一半**，还有两个更硬的理由：

### ① 寄存器值会被硬件改，CPU 不知道

状态寄存器（比如"数据就绪"标志）由硬件翻转。如果这段映射是 cached，CPU 第一次读之后就缓存住，**硬件改了 CPU 也看不到**——设备永远"没准备好"。这是真实的死循环。

### ② 读操作可能有副作用，缓存会把它吞掉

很多硬件寄存器是**读即清除**（read-to-clear）的：读一次中断状态寄存器，标志就清了。

```
期望：  读 → 清中断 → 再读 → 读到 0
cached：读 → 缓存命中，第二次读根本不产生总线事务 → 中断没被正确处理
```

**缓存不仅让数据变旧，它让"读"这个动作本身消失了。**

### ③ 写顺序必须保持

设备寄存器往往要求严格的写入顺序（先写地址寄存器、再写命令寄存器触发）。cached 或 writecombine 都可能**重排或合并写入**：

```c
writel(addr,  base + REG_ADDR);      /* 要先到 */
writel(cmd,   base + REG_CMD);       /* 后到，触发动作 */
```

如果这两次写被合并成一次突发或者乱序，设备收到的是错误命令。**noncached 保证程序顺序的写直达。**

> **规则：MMIO 寄存器一律 `pgprot_noncached`。** 帧缓冲这类"只写、顺序无关、量大"的才用 writecombine。

## 惰性映射：什么时候用 `fault`

`remap_pfn_range` 在 `mmap()` 返回前**一次性建完所有页表**。缺点：映射 1 GB 就要立刻建 26 万个页表项，即使程序只访问其中 1 MB。

`fault` 是**按需建表**：首次访问某页才触发缺页异常，内核回调 `vm_ops->fault` 补上这一页。

| | `remap_pfn_range` | `vm_ops->fault` |
|---|---|---|
| 建表时机 | mmap 时全部建完 | 首次访问该页时 |
| mmap 返回延迟 | 与映射大小成正比 | **O(1)** |
| 内存开销 | 全部页表 | 只建访问过的 |
| 适用场景 | MMIO 寄存器、CMA 连续缓冲 | 大缓冲、稀疏访问、动态分配 |

```c
static vm_fault_t my_fault(struct vm_fault *vmf)
{
    struct vm_area_struct *vma = vmf->vma;
    struct my_dev *m = vma->vm_private_data;
    unsigned long offset = vmf->pgoff << PAGE_SHIFT;
    struct page *page;

    if (offset >= m->buf_size)
        return VM_FAULT_SIGBUS;          /* 越界 → 给用户发 SIGBUS，不是 SIGSEGV */

    page = m->pages[vmf->pgoff];
    if (!page)
        return VM_FAULT_OOM;

    /* 逐页插入（要求内存有 struct page） */
    return vmf_insert_page(vma, vmf->address, page);
}

static const struct vm_operations_struct my_vm_ops = {
    .fault = my_fault,
};

static int my_mmap(struct file *filp, struct vm_area_struct *vma)
{
    vma->vm_ops = &my_vm_ops;            /* ★ 只挂 ops，不建表 */
    vma->vm_private_data = filp->private_data;
    return 0;
}
```

**注意 `mmap` 回调直接 `return 0`** —— 不建任何页表，等缺页时再说。

**返回值语义**（`vm_fault_t`）：

| 返回 | 含义 |
|------|------|
| `VM_FAULT_NOPAGE` / `vmf_insert_page` 成功 | 页已装好 |
| `VM_FAULT_SIGBUS` | **越界/无效访问** → 给用户 SIGBUS |
| `VM_FAULT_OOM` | 内存不足 |
| `VM_FAULT_SIGSEGV` | 真正的非法地址 |

**越界要返回 `VM_FAULT_SIGBUS` 而不是 `SIGSEGV`**：语义上"映射存在但访问了不存在的后端"是总线错误，不是段错误。用户态看到的是 `Bus error`，这提示"映射范围问题"，比 `Segmentation fault` 定位更快。

## 常见坑清单

| 坑 | 症状 | 修法 |
|----|------|------|
| **DMA 缓冲 mmap 忘设 pgprot** | 数据**偶尔**不对 | 改用 `dma_mmap_coherent`（见 [6.5](./6.5-mmap-remap-pfn-range.md)） |
| **MMIO 用默认 cached** | 死等"就绪标志"；中断清不掉；命令乱序 | `pgprot_noncached` |
| **`vm_pgoff` 不校验** | 用户能映射任意物理内存（**提权漏洞**） | 上界检查 |
| **映射普通 `kmalloc` 内存用 `remap_pfn_range`** | 页可能被回收，且属性不对 | 有 `struct page` 就用 `vm_insert_page` / `vm_map_pages` |
| **用户态用 `MAP_PRIVATE`** | 写不回设备（写时复制） | 设备 mmap 一律 `MAP_SHARED` |
| **缓冲在用户还映射着时被释放** | 用户访问已释放内存 | 见 6.5 生命周期 |

**关于"映射普通内核内存"这一条值得展开：** 老教程里教的是给 `kmalloc` 的页打 `SetPageReserved` 再 `remap_pfn_range`。**现代内核不推荐这个做法**——一是这些页仍在伙伴系统管理下，二是语义混乱。正确做法：

- 需要给用户态映射的缓冲 → **用 `dma_alloc_*` 分配 + `dma_mmap_*` 映射**（首选）
- 已有 `struct page` 数组 → `vm_insert_page` / `vm_map_pages`
- `vmalloc` 区域 → 有专门的 `remap_vmalloc_range`

## 用户态侧配合

```c
int fd = open("/dev/mydev", O_RDWR);

/* ★ 必须 MAP_SHARED：MAP_PRIVATE 会触发写时复制，写不回设备 */
void *p = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
if (p == MAP_FAILED) { perror("mmap"); return -1; }

/* noncached 映射不需要 msync —— 写已经直达内存
   但如果是 cached 映射且要刷出去，才需要 msync(p, len, MS_SYNC) */
```

**`MAP_SHARED` 是硬性要求。** 用 `MAP_PRIVATE` 时内核会做写时复制，用户写的是副本，**设备永远看不到**——而且这个 bug 表现是"写进去没反应"，很容易误判成驱动问题。

## HFT / 嵌入式关联

- **缓存属性错误是"静默算错"类 bug 的主要来源。** 它不崩溃、不报 warning，只是在高负载或特定时序下数据不对。**这类 bug 的代价远高于崩溃**——崩溃会立刻被发现，算错会一路流到下游。
- **惰性映射与大页**是高频场景的标配：先 `mmap` 一大片（建表 O(1)），实际访问时按页建表，配合 `madvise(MADV_HUGEPAGE)` 或 hugetlbfs 减少 TLB miss。DPDK 的 hugepage 就是这条路（见 [13 DPDK](../../13-dpdk/)）。
- **`VM_FAULT_SIGBUS` 的价值在于信息量**：同样是"访问出错"，`Bus error` 立刻把排查方向指向"映射的后端出了问题"（越界、设备没了），而 `Segmentation fault` 会让人去查指针。选对错误语义是给自己省时间。

<details>
<summary>参考答案</summary>

1. `pgprot_noncached`：**MMIO 寄存器、DMA 缓冲**——需要读直达、写顺序保持。`pgprot_writecombine`：**帧缓冲/显存、大块输出型 DMA**——写可以合并成突发提高吞吐，读直达。两者都不能用于普通内存。

2. ① 寄存器值被硬件改，CPU 缓存看不到 → 永远等不到"就绪"；② **读有副作用**（读即清除），缓存会让第二次读不产生总线事务，中断清不掉；③ **写顺序必须保持**，缓存/writecombine 可能重排或合并写入，导致设备收到错误命令。"怕读到旧值"只覆盖了 ①，而 ② 和 ③ 是更硬的约束。

3. 看映射大小和访问模式。`remap_pfn_range` 在 mmap 返回前建完所有页表，延迟与大小成正比，适合 MMIO 寄存器、CMA 连续缓冲这类**小而必访**的区域；`fault` 惰性建表，mmap 是 O(1)，适合**大缓冲、稀疏访问、需要动态分配**的场景——首次访问某页才补表。

4. 返回 **`VM_FAULT_SIGBUS`**。语义上"映射存在但后端无效"是总线错误，用户看到 `Bus error` 会把排查方向直接指向"映射的后端/范围问题"；`SIGSEGV` 会误导去查指针错误。诊断信息更准确。

5. 内核会做**写时复制（COW）**，用户写的是副本，**设备永远看不到写入**。症状是"写进去没反应"，容易被误判成驱动 bug。设备 mmap 必须用 `MAP_SHARED`。

6. **`dma_alloc_coherent` / `dma_alloc_attrs` 分配 + `dma_mmap_coherent` / `dma_mmap_attrs` 映射**。`dma_mmap_*` 内部会通过 `dma_pgprot()` 自动把用户态映射的缓存属性设成与 DMA 语义匹配（noncached 或 writecombine），避免手写 `remap_pfn_range` 漏设 pgprot 导致的"两侧属性不一致"问题。
