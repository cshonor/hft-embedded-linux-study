# C.5 为什么用消息传递

> 附录 C · 上一节：[C.4 ATM 状态机实现](04-atm-implementation.md) · 下一节：[C.6 完整流程](06-full-flow.md)

## 这节讲什么

ATM 案例为什么用消息传递而非共享内存？本节对比两种方式在 ATM 场景的表现，讲消息传递如何让系统更安全、更可调试、更易扩展。

---

## 核心规则（代码+表格）

### 共享内存方式的 ATM（反例）

```cpp
// 反例：共享内存方式
struct SharedState {
    std::mutex m;
    std::string account;
    bool pin_verified = false;
    unsigned balance = 0;
    // ...
};

SharedState state;

// ATM 线程
void atm_thread() {
    std::lock_guard<std::mutex> lk(state.m);
    state.account = get_account();
    // 等待 PIN 验证... 但持锁等待会死锁！
    // 不持锁等待又要轮询 state.pin_verified... 竞争！
}

// 银行线程
void bank_thread() {
    std::lock_guard<std::mutex> lk(state.m);
    if (verify(state.account, get_pin())) {
        state.pin_verified = true;  // 修改共享状态
        // ATM 线程怎么知道？轮询？cv？
    }
}
// 问题：
// 1. 持锁等待 → 死锁
// 2. 不持锁访问 → 数据竞争
// 3. 共享状态越来越多 → 锁越来越复杂
// 4. 难以调试（状态被谁改的？什么时候改的？）
```

### 消息传递方式的 ATM（正例）

```cpp
// 正例：消息传递
// ATM 线程拥有自己的状态，不共享
class ATM {
    std::string account;  // 私有，无需锁
    unsigned balance;     // 私有
    // ...
};

// ATM 需要验证 PIN → 发消息给银行线程
bank.send(verify_pin{account, pin, my_sender});
// ATM 等待回复 → 从自己的 receiver 取消息
auto msg = incoming.wait_and_pop();
// 银行线程回复 pin_verified → ATM 收到后更新自己的状态
// 无共享、无锁、无竞争
```

### 两种方式对比

| 维度 | 共享内存 | 消息传递 |
|------|----------|----------|
| 状态管理 | 共享变量+锁 | 线程私有 |
| 同步 | 显式（mutex/cv） | 隐式（队列） |
| 死锁风险 | 高（多锁） | 低（无共享锁） |
| 可调试 | 差（谁改了状态？） | 好（消息可记录） |
| 可扩展 | 差（共享是瓶颈） | 优（无共享） |
| 代码复杂度 | 高（锁越来越多） | 低（状态封装在线程内） |

### 消息传递的调试优势

```cpp
// 共享内存：出问题难追踪
// state.balance 从 1000 变成 500，谁改的？什么时候？
// → 加锁、加日志、Heisenbug

// 消息传递：消息流就是执行轨迹
// 记录所有消息：
// [T=0.001] ATM → Bank: verify_pin{account="123", pin=456}
// [T=0.005] Bank → ATM: pin_verified
// [T=0.010] ATM → Bank: withdraw{account="123", amount=500}
// [T=0.015] Bank → ATM: withdraw_ok
// [T=0.020] ATM → Hardware: issue_money{500}
// 回放这些消息 → 精确重现状态机执行
```

### 消息传递的扩展优势

```
单机消息传递：
  ATM 线程 ←→ 银行线程

扩展到分布式（几乎不改代码）：
  ATM 进程 ←→ 银行进程（跨机器）
  只需把队列换成网络通信

共享内存无法扩展到分布式：
  共享变量在单机内存 → 跨机器需要改架构
```

## 新手要点（和 C 的区别）

- **C 程序员习惯共享内存**：C 的多线程通常是全局变量 + mutex——这是共享内存。ATM 案例展示了为什么消息传递更优——C 程序员要理解这个范式转变。
- **"持锁等待"是 C 程序员常犯的死锁**：C 程序员可能在持锁时 `cond_wait`——如果另一个线程需要同一把锁来发送信号，就死锁。消息传递天然避免这个问题（队列本身就是同步）。
- **消息可记录 = 可回放**：C 程序员可能没想过"记录所有函数调用"——但消息传递中，记录消息流是自然的，且可回放。这是调试的巨大优势。
- **"状态私有"是思维转变**：C 程序员可能觉得"状态放全局方便访问"——但消息传递让状态封装在线程内，通过消息交互。更安全、更模块化。

---

## HFT 关联

- **HFT 是消息传递的终极应用**：HFT 的流水线（采集→解析→策略→风控→下单）完全用消息传递——每线程私有状态，SPSC 队列通信。这是 HFT 低延迟、高可靠的核心设计。
- **消息记录 = 回放调试**：HFT 系统记录所有消息（tick、order）——出问题时回放消息流，精确重现策略执行。共享内存方式做不到这点。
- **消息传递避免死锁**：HFT 系统如果用共享内存+多锁，死锁风险随线程数增长。消息传递的"无共享"天然避免死锁——这是 HFT 可靠性的重要保证。
- **扩展到分布式**：HFT 系统未来可能需要跨机器（如主备机房）——消息传递架构可以平滑扩展，共享内存架构需要重写。
