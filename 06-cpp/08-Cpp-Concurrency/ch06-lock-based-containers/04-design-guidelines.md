# 6.4 设计准则

> 第 6 章 · 上一节：[6.3 锁分段哈希表](03-lock-striping.md) · 下一节：[6.5 读写锁的应用](05-rwlock.md)

## 这节讲什么

从栈、队列、哈希表的实践中提炼出并发数据结构的设计准则：锁粒度多细才合适、如何保证不变式、死锁预防、异常安全、以及"可线性化"（linearizability）的正确性标准。

---

## 核心规则（代码+表格）

### 准则一：保证不变式在锁外成立

数据结构的**不变式**（如"head 永远非空因为有哨兵"、"size 等于节点数"）在释放锁时必须成立。否则其他线程会看到破坏的状态。

```cpp
// 反例：在锁内破坏不变式后释放锁
void bad_push(T v) {
    {
        std::lock_guard<std::mutex> lk(m);
        node* n = new node(v);
        // 此时如果先 head = n 再 n->next = old_head
        // 其他线程看到 head->next == nullptr（不变式被破坏）
        n->next = head;   // 先接好
        head = n;          // 再原子切换
    }
}
```

### 准则二：锁粒度——够细即可，不是越细越好

| 粒度 | 并行度 | 开销 | 风险 |
|------|--------|------|------|
| 单锁 | 低 | 最小 | 瓶颈 |
| 中等（头尾/分段） | 中高 | 中 | 实现复杂 |
| 极细（每元素一锁） | 理论高 | 锁本身占内存 | 死锁风险大 |
| 无锁 | 最高 | 无锁开销 | 极难正确实现 |

### 准则三：避免在持锁时调用外部代码

```cpp
// 危险：回调可能反向调用本对象 → 重入死锁
template <typename F>
void for_each(F&& f) {
    std::lock_guard<std::mutex> lk(m);
    for (auto& x : data) f(x);   // f 可能调 push() → 再次 lock(m) → 死锁
}
// 正确：先拷贝数据，锁外调用回调
template <typename F>
void for_each_safe(F&& f) {
    std::vector<T> snapshot;
    {
        std::lock_guard<std::mutex> lk(m);
        snapshot.assign(data.begin(), data.end());
    }
    for (auto& x : snapshot) f(x);  // 锁外，安全
}
```

### 准则四：可线性化（Linearizability）

并发数据结构的每个操作看起来像在某一瞬间原子完成。测试标准：
- 操作有明确的**线性化点**（linearization point）——如 `pop` 的锁释放瞬间。
- 从外部观察者角度，操作序列等价于某种串行排列。

### 准则总结表

| 准则 | 核心思想 | 违反后果 |
|------|----------|----------|
| 不变式在锁外成立 | 释放锁时状态自洽 | 其他线程看到损坏数据 |
| 锁粒度适中 | 细到消除瓶颈，粗到避免复杂度 | 太细→死锁；太粗→瓶颈 |
| 不在锁内调外部代码 | 外部代码可能重入 | 死锁或重入竞争 |
| 可线性化 | 每操作有原子语义点 | 语义混乱，难以推理 |

## 新手要点（和 C 的区别）

- **C 程序员容易忽视"不变式"概念**：C 里写单线程数据结构凭直觉就能对，但多线程下必须显式定义不变式并保证它在锁释放时成立——这是形式化思维，C++ 并发教材特别强调。
- **"持锁时调外部代码"是 C 程序员常犯的错**：C 的回调函数风格（如 `qsort` 的比较函数）天然就是"在操作中调外部"，但并发容器里这很危险——回调可能反向操作容器。
- **可线性化是比"线程安全"更强的保证**：C 程序员可能觉得"加了锁就安全了"——但"安全"有程度之分。可线性化是最强的单操作原子性保证，是推理并发正确性的基础。
- **快照模式（snapshot）**：持锁时拷贝数据、锁外处理。这是 C++ 并发的通用模式，C 里不太常用因为拷贝开销大，但 C++ 的 `std::vector` 移动语义让快照代价可接受。

---

## HFT 关联

- **不变式保证 = 可推理性**：HFT 系统在极高负载下，任何不变式被破坏的窗口都可能导致策略误判。严格的锁设计是底线。
- **持锁时绝对不调外部代码**：HFT 系统的回调（如策略引擎的 `on_tick`）可能触发下单、日志、风控——如果在持锁时回调，极易死锁。一律快照+锁外回调。
- **可线性化 = 可观测性**：HFT 系统需要精确回放和审计，可线性化保证"日志中的操作顺序"在某种串行化下是合法的，这对事后分析至关重要。
- **锁粒度 ≠ 越细越好**：HFT 系统的锁设计要实测——有时单锁在低竞争下比细粒度锁更快（锁本身有 cache line bounce 开销）。
