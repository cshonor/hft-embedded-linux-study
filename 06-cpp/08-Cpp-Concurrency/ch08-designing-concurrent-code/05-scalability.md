# 8.5 可扩展性法则

> 第 8 章 · 上一节：[8.4 异常安全](04-exception-safety.md) · 下一节：[8.6 负载均衡](06-load-balancing.md)

## 这节讲什么

可扩展性（scalability）= 核数增加时性能是否线性提升。本节讲 Amdahl 定律（串行部分决定上限）、共享是可扩展性的最大敌人、以及如何通过减少共享来让性能随核数线性增长。

---

## 核心规则（代码+表格）

### Amdahl 定律

```
加速比 = 1 / (S + (1-S)/N)

S = 串行部分占比
N = 核数
```

| 串行占比 S | 4 核加速 | 8 核加速 | 16 核加速 | 无限核上限 |
|-----------|---------|---------|----------|-----------|
| 0% | 4x | 8x | 16x | ∞ |
| 1% | 3.9x | 7.5x | 13.9x | 100x |
| 5% | 3.5x | 6.4x | 9.1x | 20x |
| 10% | 3.1x | 5.3x | 6.4x | 10x |
| 50% | 1.8x | 2.3x | 2.7x | 2x |

**结论**：即使只有 5% 的串行部分，16 核只能加速 9 倍而非 16 倍。串行部分是可扩展性的硬上限。

### 共享 = 串行点

```cpp
// 不可扩展：所有线程争抢一个锁
std::mutex global_mutex;
int shared_counter = 0;
void worker() {
    for (int i = 0; i < 1000000; ++i) {
        std::lock_guard<std::mutex> lk(global_mutex);
        shared_counter++;  // 串行点！核数越多竞争越激烈
    }
}
// 4 核：2.5x   8 核：2.8x   16 核：2.9x（几乎不扩展）

// 可扩展：每线程局部累加，最后合并
thread_local int local_counter = 0;
void worker_scalable() {
    for (int i = 0; i < 1000000; ++i) {
        local_counter++;  // 无共享，线性扩展
    }
}
// 最后合并：shared_counter += local_counter（一次性）
```

### 可扩展性检查清单

| 检查项 | 不可扩展的做法 | 可扩展的做法 |
|--------|--------------|-------------|
| 计数器 | 全局 `atomic` 或锁 | `thread_local` + 合并 |
| 日志 | 共享缓冲 + 锁 | 线程私有缓冲 + 批量刷盘 |
| 内存分配 | 全局 `malloc`（有锁） | 每线程 mempool |
| 容器 | 单锁保护 | 分段锁 / 每线程独立 |
| 配置 | 全局读配置 | `thread_local` 配置快照 |

### cache line bounce 的代价

```
4 核争抢同一个 atomic：
  核1 写 → cache line 传到核1
  核2 写 → cache line 传到核2
  核3 写 → cache line 传到核3
  ...
  每次写 = ~40-100ns 的 cache 传递（跨核 QPI/UPI）
  
16 核争抢 → 每次写 ~200-400ns → 比单核串行还慢
```

这就是为什么"共享原子变量"在高核数下不可扩展——cache line 在核间反复传递。

## 新手要点（和 C 的区别）

- **C 程序员可能不熟悉 Amdahl 定律**：这是并行计算的理论基础——串行部分决定加速上限。C 程序员写多线程时容易只关注"能跑起来"，忽视可扩展性。C++ 并发教材特别强调这一点。
- **"共享 = 串行点"是关键认知**：C 程序员可能觉得"加个锁就安全了"——但锁让并行退化为串行。核数越多，锁竞争越激烈，甚至比单线程更慢。可扩展设计的核心是"消除共享"。
- **cache line bounce 是物理现象**：C 程序员可能不了解 CPU cache 的 MESI 协议——多核争抢同一 cache line 时，硬件层面就有传递开销。这不是软件能优化的，只能靠"不共享"避免。
- **`thread_local` 是 C++ 的可扩展性武器**：C 里用 `__thread` 也能做，但 C++ 的 `thread_local` 更通用（支持非平凡构造）。C 程序员转型时要养成"能局部就不共享"的习惯。

---

## HFT 关联

- **HFT 系统的可扩展性 = 低延迟**：HFT 不追求高吞吐，但低延迟要求"每线程独立"——不争抢共享资源 = 无等待 = 延迟可预测。可扩展性和低延迟在 HFT 中是同一件事。
- **全局 `malloc` 是 HFT 的隐形杀手**：`malloc` 内部有锁——多线程频繁 malloc/free 会导致锁竞争和延迟抖动。HFT 必须用每线程 mempool。
- **cache line 对齐**：HFT 中即使是只读共享变量，如果和可写变量在同一 cache line 也会 bounce（false sharing）。用 `alignas(64)` 隔离热数据。
- **绑核 + 线程独占数据**：HFT 系统每线程绑一个核，数据全部 `thread_local` 或通过 SPSC 传递——零共享 = 零竞争 = 延迟稳定。
