### 三条路径的"货币单位"与关键对象

| 路径 | 用户可见对象 | 内核入口 | 中间层 | 最小单位 | 终点 |
|------|-------------|---------|--------|---------|------|
| **字符设备** | `/dev/xxx` | `file_operations` | （几乎无） | 字节 | 驱动 |
| **块设备** | `/dev/sdX` | `file_operations` | VFS → **页缓存** → 块层 → 调度器 | 页 / **bio** | 驱动 |
| **网络设备** | `socket()` | `struct proto_ops` | **协议栈**（TCP/UDP/IP） | **skb** | 驱动 |

> 对照 [Ch 14.7](../../chapter-14-block-io/notes/section-14.7-与上下章衔接.md) 的"分层货币单位表"一起看：
> 每一层都在做**单位换算**——字节 → 页 → 块 → 段 → request → 硬件命令 → 扇区。

### 内核旁路的三级阶梯（HFT 的核心话题）

旁路不是"开或者关"，而是**三个层级**，越往下性能越高、代价越大：

```
第 0 级：走完整内核栈
    socket() → TCP/UDP → IP → 驱动 → 网卡
    延迟：~10-30 μs（含两次拷贝 + 协议处理）

第 1 级：旁路协议栈（保留内核驱动与设备模型）
    ┌ AF_XDP / AF_PACKET mmap ─┐
    │  用户态直接读写网卡的 ring buffer，跳过 TCP/IP 与 skb 分配
    └─┘
    延迟：~2-5 μs        代价：要自己解析以太网帧；仍是内核管设备

第 2 级：旁路内核驱动（设备交给用户态）
    ┌ DPDK / VFIO / UIO ─┐
    │  用户态 PMD 轮询驱动网卡，内核完全不参与数据路径
    └─┘
    延迟：~1 μs 以下     代价：**独占设备**（内核看不到这块网卡了）

第 3 级：旁路 CPU（设备自己做）
    ┌ RDMA / TCP Offload / FPGA ─┐
    │  数据在网卡或 FPGA 上直接处理，CPU 只发指令
    └─┘
    延迟：亚微秒          代价：硬件成本高，开发周期长
```

| 级别 | 代表技术 | 内核角色 | 设备谁管 |
|------|---------|---------|---------|
| 1 | **AF_XDP** | 仍拥有设备，但给一条高速通道 | 内核 |
| 2 | **DPDK（VFIO）** | **放弃**该设备 | **用户态独占** |
| 3 | RDMA / 智能网卡 / FPGA | 只做初始化 | 设备自治 |

> **AF_XDP 与 DPDK 的关键差别不是性能，是"设备归谁"：**
> AF_XDP 下内核仍是设备主人，你可以同时用 `ssh`、`tcpdump`、`ethtool`；
> DPDK 下这块网卡**从内核视角消失了**——你不能再 `tcpdump eth0`，也不能用它跑 SSH，
> 排障只能靠 DPDK 自己的工具。这是巨大的运维代价，选型时必须权衡。

### 完整 `sendto()` 到网卡发包的函数链

```
sendto(fd, buf, len, ...)
  │
  ├─ ① 系统调用陷入内核                                    （Ch 5）
  ├─ ② fd → struct file → socket → proto_ops->sendmsg     （Ch 13 VFS）
  ├─ ③ 分配 skb，把用户数据拷进 skb（或零拷贝）             （网络子系统）
  ├─ ④ UDP: udp_sendmsg → ip_send_skb → ...               （协议栈）
  │     TCP: tcp_sendmsg → 拥塞控制/分段 → ...
  ├─ ⑤ 路由查找 + 邻居解析（ARP）
  ├─ ⑥ 排队规则 qdisc（pfifo_fast / fq_codel）
  ├─ ⑦ dev_queue_xmit() → ndo_start_xmit()                （网卡驱动）
  ├─ ⑧ 驱动把 skb 地址填进 TX ring，写 doorbell 寄存器
  └─ ⑨ 网卡 DMA 取数据 → 发到线路上 → 中断（或轮询）通知完成
```

| 可优化的环节 | 手段 |
|-------------|------|
| ② 系统调用开销 | `sendmmsg()` / `io_uring` 批量提交 |
| ③ 数据拷贝 | `MSG_ZEROCOPY` / `AF_XDP` 零拷贝 |
| ④ 协议处理 | 改用 UDP 组播行情；或 `AF_XDP` 全跳过 |
| ⑥ qdisc 排队 | `tc qdisc` 调优；低延迟场景用 `fq` |
| ⑨ 中断 → 轮询 | `NAPI`（内核）/ **busy polling**（DPDK 的精髓） |

> **NAPI 是内核自己的"半轮询"**：高负载时收中断后关闭中断、转入轮询，
> 把"每包一中断"变成"每批一中断"。DPDK 更进一步：**完全不要中断，CPU 死循环轮询**。

**Q1.** 从用户态 write() 到网卡发包经过哪些层？

<details><summary>答案</summary>

write(socket, data, len) → VFS（socket file）→ sock_write_iter → 协议栈（TCP/UDP）→ ip_push_pending_frames → 网卡驱动 ndo_start_xmit → DMA → 网卡硬件发包。HFT 优化路径：AF_XDP 绕过协议栈直接从用户态到网卡驱动；DPDK 完全在用户态驱动网卡，不经内核。

**Q2.** AF_XDP 和 DPDK 都能做到低延迟收包，选择时真正该权衡的是什么？

<details><summary>答案</summary>

**不是性能，是"这块网卡归谁管"**——这决定了你还能不能用内核的整套运维工具。

| | **AF_XDP** | **DPDK（VFIO/UIO）** |
|---|---|---|
| 设备归属 | **内核仍是主人**，只是开了一条高速通道 | **内核放弃设备**，用户态独占 |
| 延迟 | ~2-5 μs | ~1 μs 以下 |
| `tcpdump eth0` | ✅ 能抓包（配合 XDP 的通用模式） | ❌ **抓不到**（内核看不到这块网卡） |
| `ethtool` / `ip link` | ✅ 正常 | ❌ 不可用 |
| 用这块网卡跑 SSH | ✅ 可以 | ❌ 不行（设备已从内核消失） |
| 内核协议栈共存 | ✅ 同一块网卡上其他流量照常走内核 | ❌ 完全独占 |
| 故障恢复 | 进程挂了内核接管 | 进程挂了**网卡无主**，需要自己复位 |
| 开发成本 | 中（XSK ring 编程模型） | 高（整套 PMD、大页、绑定都要管） |

**决策建议：**
- 只需要**行情组播收包**（单一、无连接、只读）→ **DPDK 值得**，独占的代价可以接受；
- 需要**收发并存 + 还要跑管理流量**（SSH/监控/日志）→ **AF_XDP 更合适**，省一台机器或一块网卡；
- 延迟要求不是极端（5 μs 够用）→ AF_XDP，运维成本低一个数量级；
- 已经在用 DPDK 且稳定 → 别迁，重写成本远大于收益。

**一个常见误区**：以为 DPDK 一定比 AF_XDP 快很多。实际上现代网卡 + 正确配置的 AF_XDP
（busy poll + 大页 + 绑核）与 DPDK 的差距常常在 **1-2 μs 以内**，而这 1-2 μs 换来的运维能力差别很大。
先测再选，别照抄别人的架构。

</details>

**Q3.** 为什么 DPDK 用轮询（busy polling）而不是中断？这不是浪费 CPU 吗？

<details><summary>答案</summary>

是浪费 CPU，但**换掉了更贵的东西**——中断带来的延迟抖动和上下文开销。

**中断的隐藏成本（每个包都要付）：**
1. 网卡发中断 → CPU 中断控制器 → 查 IDT → 切换到中断上下文；
2. **保存/恢复寄存器**（几百个周期）；
3. 可能触发**上下文切换**（唤醒等待的进程）；
4. **缓存污染**：中断回来后，L1/L2 里原本热的数据被打冷了，要重新从内存取（**这是最贵的一项**）；
5. 中断**合并（interrupt coalescing）**为了减少中断数会故意延迟，反而**增加延迟**。

**轮询的成本：**
- 一个 CPU 核 100% 占用，死循环读网卡的 RX ring；
- 没有上下文切换，**没有缓存污染**——热数据始终在 L1/L2 里；
- 延迟**非常稳定**（抖动小），这对 HFT 往往比平均延迟更重要。

**算一笔账：**

| | 中断模式 | 轮询模式 |
|---|---|---|
| 每包 CPU 开销 | 中断时高、空闲时 0 | 恒定 |
| 延迟 | 有抖动（合并、排队） | **稳定** |
| CPU 占用 | 随流量波动 | **恒定 100%（独占一个核）** |
| 缓存命中 | 中断后 cache 被冲 | **cache 一直热** |

HFT 的取舍逻辑很直接：**一个核的成本（几千美元）远小于一次尾部延迟抖动造成的损失**。
所以"浪费一个核去死循环"在经济上是划算的。

**内核自己也在学这一招：**
- **NAPI**：高负载时收一次中断后**关中断转入轮询**，把"每包一中断"变成"每批一中断"——半轮询；
- **`SO_BUSY_POLL` / `busy_read`**：socket 层忙轮询，配合 `net.core.busy_poll` / `busy_read` 参数；
- **io_uring 的 `SQPOLL`**：提交队列由内核线程轮询，应用连 `io_uring_enter` 系统调用都省了。

所以演进方向是一致的：**在低延迟场景，用 CPU 换延迟确定性是划算的买卖**。

</details>
