## ① 块设备与字符设备

| 类型 | 访问方式 | 示例 |
|------|----------|------|
| **块设备（block）** | **固定大小块** · **随机访问** | 硬盘、SSD、蓝光、闪存 |
| **字符设备（character）** | **连续字符流** · **顺序** | 键盘、串口 |

| 对比 | 块设备 |
|------|--------|
| 管理复杂度 | **高得多** |
| 性能敏感度 | **极高** — 「榨干硬盘每一分性能」 |

#### 完整对照（含「第三类设备」——书里没讲清的地方）

| 维度 | 块设备 | 字符设备 | **网络设备**（第三类！） |
|------|--------|----------|--------------------------|
| 访问单位 | 固定大小块（512B/4KB） | 字节流 | 帧（sk_buff） |
| 随机访问 | 是 | 否（顺序） | 不适用 |
| 内核缓存 | **页缓存**（Ch16） | 通常无 | socket buffer |
| 设备文件 | `/dev/sda`、`/dev/nvme0n1` | `/dev/ttyS0`、`/dev/null`、`/dev/nvidia0` | **没有设备文件** |
| 用户态入口 | open/read/write/mmap | open/read/write/ioctl | **`socket()` API，不是 open()** |
| 内核注册结构 | `struct gendisk` + `block_device_operations` | `struct cdev` + `file_operations` | `struct net_device` + `net_device_ops` |

> ⚠️ **高频误解**：网卡**不是字符设备**——它压根没有 `/dev/eth0`，走的是 socket 系统调用族（VFS 层是 sockfs，见 [Ch13.1](../../chapter-13-vfs/notes/section-13.1-通用文件系统接口与抽象层.md)）。Unix 的「一切皆文件」对网络设备是**例外**。

| 为什么块设备管理复杂得多 | 原因 |
|------------------------|------|
| 有缓存层 | 页缓存 + 回写 + 与 VFS 深度耦合（字符设备通常直来直去） |
| 有调度层 | 请求合并/排序/多队列（Ch14.5-14.6） |
| 有几何/限制 | 扇区大小、对齐、最大段数、原子写粒度 |
| 有并发层次 | 软件队列 + 硬件队列 + 中断/轮询完成路径 |

→ 内核专设 **块 I/O 层** 子系统 · [Ch 13](../../chapter-13-vfs/) VFS 之下

**HFT：** 策略 **tick / 发单** 不应同步等块 I/O；**审计、replay、checkpoint** 走块层 — 用 **独立盘 + ionice** 隔离。

**Q1.** 块设备和字符设备的根本区别？HFT 系统中哪些是哪种？

<details><summary>答案</summary>

块设备：随机访问、按块传输、有页缓存（NVMe SSD 存历史数据，走 /dev/nvme0n1）。字符设备：字节流、无缓存（串口 /dev/ttyS0、GPU /dev/nvidia0）。**网卡既不属块也不属字符设备**——它是第三类网络设备，无 /dev 节点，走 socket API。判别口诀：**看用户态怎么拿到它** —— open() 出来的是字符/块设备，socket() 出来的是网络设备；open() 出来还能 lseek 任意偏移的，才是块设备。

</details>

**Q2.** 为什么块设备一定有页缓存，而字符设备通常没有？

<details><summary>答案</summary>

缓存的前提是**可重用的稳定内容**：磁盘上一个块的数据由 (设备, 扇区号) 唯一确定，读完留在内存里下次还有效（直到被写回/失效），所以值得用页缓存按 (inode, 偏移) 索引。字符设备是**数据流**：读一次就消费掉（串口字节、随机数、GPU 命令通道），同一偏移读两次含义不同，缓存不但无用还会给出错误答案。例外：块设备也可以关闭缓存（O_DIRECT），说明缓存是**策略而非物理属性**——由数据语义决定该不该缓存。

</details>

**Q3.** `/dev/null`、`/dev/zero` 是字符设备——对它们的 write 会走块层吗？为什么 HFT 有时故意把日志重定向到 /dev/null 而不是关闭日志？

<details><summary>答案</summary>

不走块层：它们的 file_operations 直接实现空的 write（返回 count，什么都不做），syscall 在 VFS 层就返回了，连 slab 分配都省。重定向到 /dev/null 而不是关日志的价值：**保留调用点开销极小但保留了代码路径**——格式化（snprintf）仍在跑，能保留真实的性能画像与错误分支覆盖；相比起"编译期关掉日志"改变了二进制、也改变了内存布局与分支预测行为。对比 `> /dev/null` 与 `> file` 的差别：后者每次 write 都进页缓存+最终落盘，是真实的块层负载。

</details>
