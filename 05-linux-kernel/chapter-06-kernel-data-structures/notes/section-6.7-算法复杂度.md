## ⑥ 算法复杂度 · Big-O

内核开发者需 **定量** 想扩展性 — **大 O 记法** 描述输入规模 **n** 增长时性能趋势。

| 记号 | 名称 | 内核中常见于 |
|------|------|--------------|
| **O(1)** | 常数 | `list_add`、`list_del` |
| **O(log n)** | 对数 | `rbtree` 查找/插入 |
| **O(n)** | 线性 | `list_for_each` 扫全表 |
| **O(n²)** 及以上 | 应极力避免 | 大 **n** 时不可接受 |

| 实践 | 说明 |
|------|------|
| 看 **典型 n** | 链表 O(n) 扫 **10 项** 可接受；**百万项** 不行 |
| 热路径 | 中断、调度器 — 倾向 **O(1) / O(log n)** |
| 冷路径 | 初始化、罕见 ioctl — 可略宽松 |

#### Big-O 之外的三个真实维度

**① 缓存局部性——O(1) 不一定比 O(log n) 快**：

| 结构 | 渐近 | 访存模式 |
|------|------|----------|
| 链表 `list_for_each` | O(n) | 节点散落堆上 → **每步都 cache miss**（~100ns 级） |
| 红黑树查找 | O(log n) | 每层一次可能 miss |
| 数组顺序扫 | O(n) | **预取器全开**——实际比链表快几十倍 |
| B-tree/maple tree | O(log n) | 节点**多条目** → 树矮、每层访存摊薄——**为缓存而生** |

> 内核教科书结论：**n 小（<几十）时数组/链表吊打树**——分界点由 cache line（64B）与对象大小决定，不是由 Big-O 决定。`hlist` 单指针头（省一半内存）也是同一逻辑：结构越小，一个缓存行装得越多。

**② 常数因子与指令数**：`list_add` 与哈希插入都是"O(1)"，但前者两条指针写、后者要算哈希+探测——中断热路径上选前者的直接理由是**指令数**，不是复杂度记号。

**③ 共享消除 > 结构优化**：per-CPU 化让每 CPU 只碰自己的数据——复杂度没变，但**锁竞争与 cache line 乒乓（伪共享）同时消失**。这往往是内核里最划算的一档优化（计数器从 atomic_t → per-CPU 计数 + 汇总）。

```
优化阶梯（性价比从高到低）：
  per-CPU 化 / RCU（消灭共享）  >  换更缓存友好的结构  >  改进算法复杂度
```

**HFT 对照：** 用户态订单簿用 **红黑树/跳表 O(log n)**；内核 CFS 同理 — **算法层与业务层同一套复杂度语言**。加一条实操结论：改造热路径时先 `perf c2c`/`perf cache-misses` 看**伪共享与 miss 热点**，再谈换算法——多数"感觉是算法慢"的案例，最后都死在 cache line 上。

<summary>自测题（点击展开）</summary>

**Q1.** O(1) 和 O(log n) 在内核中意味着什么？n=10000 时差异多大？

<details><summary>答案</summary>

O(1)：无论系统多少进程/文件，操作恒定时间。O(log n)：n=10000 时 log₂(10000)≈13，比 O(1) 多约 13 次操作。内核热路径（如 schedule()）必须 O(1)，因为每秒可能调用百万次。CFS 的 O(log n) 调度在选择下一个进程时可接受（有缓存优化）。

</details>

**Q2.** 为什么内核开发者对 O(n) 操作特别敏感？

<details><summary>答案</summary>

内核 O(n) 操作在 n 很大时会导致延迟尖峰。例如早期 Linux 的 O(n) 调度器遍历所有进程找最高优先级的，1000 个进程时每次调度遍历 1000 个 task_struct → cache miss 暴增 → 延迟不可预测。O(1) 调度器和 CFS 的出现就是为了消灭 O(n)。HFT 要求确定性延迟，O(n) 是禁忌。

</details>

**Q3.** 同是 O(n)，为什么数组顺序扫描比链表遍历快几十倍？

<details><summary>答案</summary>

访存模式：数组元素连续 → CPU 预取器（prefetcher）认出顺序模式后提前把后续 cache line 载入，主存延迟被流水掩盖；链表节点散布堆中 → 每跳一次都是**指针追逐（pointer chasing）**，预取器无从预测，每步裸付一次 cache miss（~100ns 级）。渐近复杂度只数"步数"，不含"每步多贵"——这就是 maple tree 用多路节点压矮树高的动机：**树高 = 指针追逐次数 = cache miss 次数**。

</details>
