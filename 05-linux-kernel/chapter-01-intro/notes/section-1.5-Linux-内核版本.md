## ⑤ Linux 内核版本

| 类型 | 说明 |
|------|------|
| **稳定版（Stable）** | 生产可用 |
| **开发版（Development）** | 新特性实验 |

**传统版本号**（如 **2.6.30.1**）：

| 段 | 含义（经典规则） |
|----|------------------|
| 次版本号 **第二位** | **偶数 → 稳定** · **奇数 → 开发** |

> 注：现行主线已长期 **3.x / 4.x / 5.x / 6.x**，「奇偶」规则 **概念仍常考**，但以 **kernel.org 分支政策** 为准。

#### 版本号规则的演化（三代规则）

```
第一代（≤2.4）：  2.偶 = 稳定 / 2.奇 = 开发   ← LKD3rd 讲的规则
第二代（2.6.x）： 2003 年起废弃奇偶——主线永远"稳定"，
                  每 2~3 个月一版，-rc 走审，修订号 2.6.x.y
第三代（3.x+）：  2011 年 3.0 纯跳号（20 周年纪念）；
                  此后 4/5/6 均为「数字太大不好看」式跳号
                  （Linus：数手指头用完了）
```

| 现行发布节奏 | 说明 |
|--------------|------|
| merge window | 每个 rc1 后 **两周**收新特性，随后只修 bug |
| 周期 | 稳定版 **9~10 周一版**，雷打不动——「时间驱动」取代「里程碑驱动」 |
| LTS | 每年一版获 **2 年+** 维护（如 5.4/5.10/5.15/6.1/6.6）；发行版再延长 |

#### HFT 选版决策表

| 需求 | 选择 | 理由 |
|------|------|------|
| 生产 tick 路径 | **LTS（6.1/6.6 级）+ 发行版补丁** | 2+ 年 bugfix 回溯、回归测试充分 |
| 需要 io_uring 新特性 | 较新 LTS | io_uring 在 5.1 入主线、此后逐版大改——**老内核的 io_uring 约等于另一个 API** |
| 需要 PREEMPT_RT | 查 RT 支持状态表 | RT 逐版合入主线（5.x 起）；与 LTS 的组合要看厂商 |
| 需要 EEVDF 调度器 | ≥6.6 | CFS→EEVDF 换代点（见 [4.1](../../chapter-04-process-scheduling/notes/section-4.1-多任务与调度器演进.md)） |

#### 实操：怎么查清「我到底在跑哪个内核」

| 命令/文件 | 给你什么 |
|-----------|----------|
| `uname -r` | 运行中内核版本串（bisect/换内核后必查——GRUB 配错时它最先暴露） |
| `cat /proc/version` | 版本 + **编译它的编译器版本 + 构建用户/主机**（排查发行版定制痕迹） |
| `dpkg -l \| grep linux-image` / `rpm -q kernel` | 装了哪些内核包（与运行中可能**不是同一个**） |
| `ls /boot/vmlinuz-*` + `cat /proc/cmdline` | 引导了哪个镜像、带什么启动参数 |

> 经典坑：装了新内核没重启，或 GRUB 默认项没改——`uname -r` 还是旧版本。内核升级的"生效"以重启为界，与用户态包管理不同。

> **警惕「新版崇拜」**：最新稳定版的调度器/锁改动可能引入你没测过的延迟行为；HFT 换内核版本 = 换一台没开过的机器——全套延迟基准必须重跑。

<summary>自测题（点击展开）</summary>

**Q1.** Linux 内核版本号 5.15.0-25-generic 中每段代表什么？

<details><summary>答案</summary>

5 = 主版本号（Linus 每次发布递增）；15 = 次版本号（偶数=稳定版，奇数=开发版，但 2.6 后此规则已废弃）；0 = 修订号（bug fix）；25 = 发行版补丁计数；generic = 发行版 flavor。HFT 生产应选 LTS（Long Term Support）版本。

</details>

**Q2.** 为什么 HFT 生产环境通常选择 LTS 内核而非最新版？

<details><summary>答案</summary>

LTS 内核有 2-6 年维护周期，bug fix 回溯稳定。最新版可能有性能改进但也引入回归。HFT 需要可预测的行为，LTS + 厂商验证补丁是安全选择。例如 PREEMPT_RT（实时补丁）通常需要 1-2 年才能从 mainline 回归到 LTS。

</details>

**Q3.** 为什么 2.6 之后 Linux 废弃了「奇偶分稳定/开发」规则？新模型怎么同时保证主线活力与生产稳定？

<details><summary>答案</summary>

旧模型的问题：开发版集成周期长达数年（2.3 开发线拖了两年多），合入冲突滚雪球、厂商等不起。新模型（Andrew Morton/Linus 2003 年改革）：**主线永远处于可发布状态**——每 9~10 周稳定一版；新特性走 merge window 两周 + rc1~rc7+ 冻结只修 bug；激进特性挂在**分支/树**里养熟再进窗口。稳定性不再靠"奇偶隔离"，而是靠**时间切片 + 纪律**：任何时刻主线都 ≤10 周龄，而 LTS 从稳定点向后回溯维护——活力与稳定由两个不同节奏的管道分别供给。

</details>
