## ② Linux 的诞生 · Along Came Linus

| 项 | 内容 |
|----|------|
| **时间** | **1991** · 赫尔辛基大学 · **Linus Torvalds** |
| **动机** | 当时 **缺乏强大且免费的 Unix** |
| **性质** | **非商业** · **互联网协作** 开发 |
| **许可证** | **GNU GPL 2.0** — **自由 / 开源软件** |

#### 成长时间线

```
1991.8  comp.os.mining:「只是个爱好，不会像 GNU 那样大而专业」
1991.9  0.01 发布（~1 万行，无网络、无登录多用户）
1994    1.0 —— TCP/IP、SMP 雏形
2003    2.6 —— 抢占内核、CFS 前夜；开发模式转折点
2005    Linus 自写 git —— 应对无 BitKeeper 之急，反哺全行业
2011    3.0（纯纪念性跳号，宣告「时间驱动发布」而非里程碑驱动）
2020s   5.x/6.x —— io_uring、eBPF 全面爆发、Rust 入场
```

#### GPL v2 合规要点（HFT 定制内核必读）

| 问题 | 规则 |
|------|------|
| 内核模块算衍生作品吗 | **常识上算**（静态链接内核符号）——主线立场"不清楚但别赌"；闭源模块游走在灰色地带（NVIDIA 类驱动长期如此） |
| 用户态程序受感染吗 | **不受**——经 syscall 边界调用不构成衍生（GPL 只约束衍生作品的分发） |
| 只在公司内部跑，要开源吗 | **不要**——GPL 义务在**分发**时触发；内部部署无限自由 |
| 分发设备（含定制内核）给客户 | 定制内核部分须提供源码；应用层不受影响 |

#### 同期对手复盘：Linux 为什么赢了

| 竞争者（1991 前后） | 弱点 | 对照 Linux |
|--------------------|------|-----------|
| GNU Hurd（微内核） | 设计完美主义，交付一拖再拖——至今未出 1.0 | 「先能跑再完善」：0.01 就敢发布 |
| 386BSD / BSD 系 | **AT&T vs BSDi 诉讼**（1992-1994）法律不确定性吓退商业采用 | 无版权阴云 + GPL 保证「永远不会被收回」 |
| MINIX | 教学许可证限制商用；Torvalds 正是它的用户 | GPL 从 day one 就允许任意使用与修改 |

**历史偶然中的必然**：GPL 提供法律确定性、互联网提供协作网络、x86 白牌机提供硬件土壤——三者同时成熟，才让一个"爱好项目"在四年内吃下服务器市场。这也是为什么内核生态的护城河不在代码本身（可 fork），而在**三十年的邮件归档、维护者关系与信任网络**——fork 得走代码，fork 不走社区。

**与 HFT 实盘：** 生产内核多为 **发行版稳定内核 + 厂商补丁** — 理解 **GPL 与源码可得** 有助于合规使用 **定制内核/驱动**。另有一条暗线值得记：Linux 的**宏内核选择**（见 [1.4](./section-1.4-Linux-与经典-Unix-内核对比.md)）当年被 Tanenbaum 骂作「过时设计」——三十年后它反而是低延迟路径（无跨进程 IPC）胜出的架构原因。

<summary>自测题（点击展开）</summary>

**Q1.** Linux 采用 GPL v2 许可证，这对商用 HFT 公司有什么影响？

<details><summary>答案</summary>

GPL v2 要求修改后的内核代码必须开源。HFT 公司的定制内核调度器/网卡驱动如果分发给客户就需要开源；但只在内部使用不分发则不触发 GPL 义务。许多 HFT 公司选择只在内部维护定制内核。

</details>

**Q2.** Linus 为什么选择宏内核而非微内核？

<details><summary>答案</summary>

宏内核性能好：syscall 不需要跨进程消息传递，直接函数调用。微内核的理论优势（模块化、隔离）在实践中被 Linux 的动态模块加载（insmod/rmmod）和命名空间部分弥补。Linus 务实优先于理论纯粹性。

</details>

**Q3.** HFT 公司给自研低延迟网卡驱动做了内核修改，客户要求把整个交易系统（含定制内核）部署到他们机房——GPL 义务怎么算？

<details><summary>答案</summary>

**分发即触发**：把含定制内核的系统交付给客户 = 分发衍生作品——定制内核部分（含驱动，若静态链接内核符号）须向客户提供对应源码（GPL §3）。三条界线：① 只交**用户态策略程序**、客户自装标准内核——不触发；② 内核改动只在**自己机房跑**——不触发（内部使用豁免）；③ 交设备/镜像——触发。规避姿势（合法的）：把低延迟逻辑放**用户态**（DPDK/VFIO）或用 eBPF（GPL 许可的字节码生态）——这也是近年低延迟方案整体向用户态迁移的合规推力之一。

</details>
