## ③ 操作系统与内核概述

#### 内核（Kernel）

**操作系统最内层** — 提供基本服务、**管理硬件**、**分配资源**。

#### 两种地址空间

```
┌─────────────────────────────────────┐
│  user-space   应用程序（策略、网关）   │
│       │ syscall ↑                     │
├───────┼─────────────────────────────┤
│  kernel-space  内核（机制）           │
│       │ ↑ 中断                        │
└───────┼─────────────────────────────┘
        硬件
```

| 空间 | 谁跑 | 权限 |
|------|------|------|
| **kernel-space** | 内核代码 | **完全硬件访问** · 受保护内存 |
| **user-space** | 普通 app | **受限** — 经 **系统调用** 求内核办事 |

| 方向 | 机制 |
|------|------|
| **app → 内核** | **System Calls**（`read`、`write`、`clone`…） |
| **硬件 → 内核** | **Interrupts** → **中断处理程序** |

#### 进入内核态的三扇门（后文全书骨架）

| 入口 | 触发 | 例子 | 章节 |
|------|------|------|------|
| **系统调用** | 程序**主动** | `read()`/`svc 0` | Ch 5 |
| **中断** | 硬件**异步** | 网卡收包 IRQ | Ch 7–8 |
| **异常** | CPU 执行**出错** | 缺页 fault、除零 | Ch 15（缺页） |

> 三者殊途同归：保存用户态现场（pt_regs）→ 切内核栈 → 高特权级执行。差别在**回来时**——系统调用返回原指令下一条；中断原样返回；缺页可能要先调页（慢路径）再重执行。

#### 机制与策略分离（Unix 设计公理）

| 概念 | 定义 | 内核例子 |
|------|------|----------|
| **机制** | **怎么做**（能力） | 页表、调度器框架、fd 表 |
| **策略** | **做什么**（决策） | 换哪页、谁先跑、打开哪些 fd |

> 内核倾向只提供机制，策略交给用户态（调度有 `nice`/`SCHED_FIFO` 旋钮；缓存替换内核只给 `posix_fadvise` 提示）。**HFT 的立场是反过来**——把策略从内核/OS 手里夺回来自己定（绑核、轮询、自管内存），用的正是内核提供的机制接口。

**Q1.** 内核态和用户态切换的代价是什么？HFT 如何减少这种切换？

<details><summary>答案</summary>

一次 syscall 需要：保存用户态寄存器 → 切换栈 → 进入内核态执行 → 恢复寄存器返回。x86_64 约 100-200ns。HFT 减少 syscall 的方法：批量 IO（io_uring）、内存映射（mmap 替代 read）、绑定 CPU 避免调度、busy-polling 替代中断等待。

</details>

**Q2.** 内核有哪些基本职责？为什么 HFT 工程师必须理解它们？

<details><summary>答案</summary>

内核管理 CPU 调度、内存分配、文件系统、网络协议栈、设备驱动、安全隔离。HFT 的每纳秒延迟都与这些子系统相关：调度器决定你的线程何时运行、内存分配器决定 TLB miss 率、网络栈决定包处理路径。不理解内核就无法做极限优化。

</details>

**Q3.** 系统调用、中断、异常三扇门进入内核后的"回来方式"有何不同？

<details><summary>答案</summary>

系统调用：保存现场 → 执行服务例程 → 返回**下一条指令**（调用约定天然继续）；中断：保存被中断处的完整现场 → 处理 → **原样返回被中断的指令**（对程序完全透明，像什么都没发生）；异常（缺页）：保存出错指令地址 → 若可修复（调页/按需分配）→ **重新执行同一条出错指令**，不可修复才升级为信号。关键差别：syscall/中断是"顺序流继续"，可修复异常是"重放"——所以缺页处理必须保证重放时环境一致（这引出后面 Ch15 的 VMA 锁问题）。

</details>
