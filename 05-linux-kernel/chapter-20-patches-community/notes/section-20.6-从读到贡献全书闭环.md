### 五个阶段：从读者到贡献者

| 阶段 | 做什么 | **验收标准**（怎么知道自己真会了） |
|------|--------|--------------------------------|
| ① 读 | 建立概念地图 | 不看资料能写出一个字符设备模块的骨架（`init`/`exit`/`file_operations`） |
| ② 跑 | 编译、安装、启动自己编的内核 | `uname -r` 显示的是你编的版本，且能正常启动进系统 |
| ③ 对照 | 概念 ↔ 源码 ↔ 当年讨论 | 挑一个子系统（如 kfifo、xarray），能讲清"**为什么**这样设计"；能顺着 `Link:` 标签查到当年的反对意见 |
| ④ 修 | 做小改动 | 成功让一个 trivial 补丁被接受（或至少收到实质 review） |
| ⑤ 提 | 走完整流程 | 能响应 review 迭代到 v2/v3，并按意见修改而非情绪反弹 |

### 从哪类改动入手

| 起点 | 为什么适合 | 风险 |
|------|-----------|------|
| **文档 typo、过时文档** | 零风险，却能**走通整个流程**（找维护者 → format-patch → send-email → 收到 ack） | 极低 |
| `drivers/staging/` | 待整理代码，**清理是被明确鼓励的** | 低 |
| **`tools/testing/selftests/`** | 补测试天然有价值，且不碰运行时路径 | 低 |
| **checkpatch 清理** | 熟悉工具链与风格 | 低，但见下方警告 |
| **你自己踩到的 bug** | 有真实场景 → commit message 最有说服力 | 中（要能复现/最好能 bisect） |

> ⚠️ **一条反面纪律**：不要一上来做"大规模格式化 / 重命名 / 空白清理"补丁。
> 内核的 stable 规则明写**不收"对无用户收益的琐碎修改"**（见 [20.5](./section-20.5-补丁.md)），
> 而且这类巨型补丁会和别人的在途改动疯狂冲突，是新人最容易被拒的方式。
> 清理类改动请**限定在你正在改的那个文件**，作为真正的改动的附赠品。

### 可勾选的验证清单

```
[ ] 编译并安装自编译内核，成功启动
[ ] 写一个字符设备模块，加载 / 卸载 / 读写都通
[ ] 故意制造一次 Oops，并完整解码出调用栈
[ ] 用 ftrace 或 bpftrace 追一次系统调用的完整路径
[ ] 完成一次 git bisect，把问题收敛到一个 commit
[ ] 用 scripts/get_maintainer.pl 找对一次维护者
[ ] 发出第一封 [PATCH]，并收到第一封实质性 review
[ ] 在 lore 上查到某个内核提交当年的讨论，读懂它为何长这样
```

> 前四项是**能力**项，后四项是**流程**项。
> 八项都打勾，你就不再需要"新手"这个前缀了。

### HFT 视角：这些能力怎么变成工作产出

| 能力 | 直接产出 |
|------|---------|
| **读源码** | 能判定"这个延迟毛刺是内核行为还是我的代码"，不再靠猜和换参数试 |
| **调试** | Oops / 软锁死 / 内存破坏能自己定位到行，不必等供应商回复 |
| **量测**（Ch 11 + eBPF 观测） | 延迟数据有可复现的量测方法，团队内部能互相验证 |
| **补丁** | 内部内核 fork 可维护、可 bisect、升级时能判断本地补丁是否已被上游吸收 |
| **跟社区** | 升级内核前先看回归清单与子系统改动，**把线上事故挡在升级之前** |
| **提补丁** | 遇到真正影响业务的内核缺陷，有能力推动修复，而不是绕过去 |

> 最后一条是本闭环的终点，也是起点：**你读这 20 章，不只是为了"懂内核"，
> 而是为了在内核出问题时，你有能力自己走到答案那里。**

**Q1.** 从内核新手到贡献者的路径是什么？

<details><summary>答案</summary>

1) 读 LKD 理解概念 → 2) 编译/运行内核 → 3) 读源码对照概念 → 4) 修小 bug/文档（drivers/staging/ 是好起点）→ 5) 提补丁到 LKML → 6) 回应 review → 7) 积累 → 8) 找子系统深入。第一次补丁不需要大功能——修 typo/文档/小 bug 就能走通整个流程。HFT 工程师参与内核社区有助于理解内核行为、推动需要的特性。

> **给每一步补一条验收标准**：① 不看资料能写出字符设备模块骨架；② `uname -r` 显示你编的版本；
> ③ 能讲清某个子系统"为什么这样设计"（可顺着 commit 的 `Link:` 查当年讨论）；
> ④ 有一个 trivial 补丁被接受或收到实质 review；⑤ 能迭代到 v2/v3 并按意见修改。

</details>

**Q2.** 新人第一次提补丁，为什么建议从文档 typo 或 selftests 入手，而不是直接做功能？

<details><summary>答案</summary>

因为第一补丁的**真正目标是走通流程**，不是贡献代码量：找维护者（`get_maintainer.pl`）→ `format-patch` → `send-email` → 收到 ack/review → 迭代。文档 typo 和 `tools/testing/selftests/` 的改动**零运行时风险**，维护者处理成本低，能让你在最低阻力下验证自己是否掌握了整套工具链与邮件礼仪。等流程跑顺了，再做有实质内容的改动。

</details>

**Q3.** 为什么不建议一上来提交"大规模格式化/空白清理"补丁？

<details><summary>答案</summary>

两条硬理由：① 内核 stable 规则明写**不收"对无用户收益的琐碎修改"**（spelling changes、whitespace cleanups 都在不收之列），主线侧同样不欢迎纯噪音；② 这类巨型补丁会和所有人的在途改动疯狂冲突，给维护者制造merge 负担，是新人被拒的高频原因。正确做法是：把清理**限定在你正在改的那个文件**里，作为实质改动的附赠品。

</details>

**Q4.** 怎么判断自己已经"真的会了"，而不是"看完了"？

<details><summary>答案</summary>

用可勾选的验证清单（能力四项 + 流程四项）：能力项 = ① 编译安装并成功启动自编译内核；② 写字符设备模块并完成加载/卸载/读写；③ 故意制造一次 Oops 并完整解码调用栈；④ 用 ftrace/bpftrace 追一次系统调用的完整路径。流程项 = ⑤ 完成一次 `git bisect` 收敛到单个 commit；⑥ 用 `get_maintainer.pl` 找对一次维护者；⑦ 发出第一封 `[PATCH]` 并收到实质 review；⑧ 在 lore 上查到某个提交当年的讨论并读懂它为何长这样。八项全打勾，才算从"读完"变成"会用"。

</details>
