## ④ 内核开发的特点 · A Beast of a Different Nature

内核与用户态程序 **不是同一种 C 环境**。下列规则 **违反即 oops / 死锁 / 栈炸**。

---

### 一句话先钉死：内核的 C = GNU C，不是纯 ISO C

**ISO C** 是国际标准；**GCC** 在标准 C 之上额外加了一堆语法特性，叫 **GCC 扩展（GNU C / GNU dialect）**。  
Linux 内核大量使用这些 **不属于标准 C** 的扩展，所以：**内核的 C 不是纯粹标准 C，是 GCC 扩展版 C**。

---

### 官方结论：默认 `-std` 是什么？

| 主线内核版本 | 默认编译方言 |
|--------------|--------------|
| **≥ 5.18（2022）** | **`-std=gnu11`** |
| **≤ 5.17** | 长期 **`-std=gnu89`**（C89 + GCC 扩展） |

拆解 `gnu11`：

| 片段 | 含义 |
|------|------|
| `c11` | 基准是 **ISO C11**（2011） |
| `gnu` | **开启全部 GCC 扩展语法** |
| 合起来 | **GNU 方言版 C11** |

本机日常树 **linux-7.1.5** 顶层 `Makefile` 已写死：`CC_FLAGS_DIALECT := -std=gnu11`（与官方结论一致）。

#### 极易混淆的 flag

| flag | 含义 |
|------|------|
| `-std=c11` | **纯** 标准 C11，**禁用** GCC 扩展 |
| `-std=gnu11` | C11 + **全部** GCC 扩展（**现代内核默认**） |
| `-std=c99` | 纯标准 C99 |
| `-std=gnu99` | C99 + GCC 扩展 |

分界线刻死：

| | |
|--|--|
| `c99` / `c11` | 国际标准化语言规范（**无**编译器附加语法） |
| `gnu99` / `gnu11` | 标准 + **GCC 私自扩展**（内核用的方言） |

#### 算 C99 还是 C11？

底层基准是 **C11**，但有两个现实要点：

1. **日常写法大量像 C99**：混合位置声明、`stdint.h`、`inline`（C99 起普及）用得很多；C11 新增的 `_Atomic`、`_Thread_local`、VLA 等内核几乎不用（VLA 甚至 **明确禁止**）。所以会感觉「和 C99 差不多」。
2. **不等于纯标准 C11**：`gnu11` ≠ `c11`。带 `gnu` 就启用 `typeof`、`({})`、`__attribute__`、内嵌汇编、`##__VA_ARGS__` 等 —— 这才是教材说「内核 C 是 GCC 扩展」的来源。

#### 误区

| 误区 | 纠正 |
|------|------|
| `gnu11` = C11 | 错。`-std=c11` 下写 `({int a=1;a;})` 报错；`gnu11` 才过。 |
| 模块随便改成 `gnu99` | **不要**。模块须与内核本体 `-std` 一致，否则 inline/类型语义可能诡异不兼容。 |
| 用户态随便选 `-std=c17` 所以内核也能裸 `c11` | 用户态可以；内核 **离不开** GCC 扩展，裸 `-std=c11` 写不出操作系统内核。 |

#### 如何验证本机源码树用的 `-std`

在源码树根目录（Linux/WSL 上）：

```bash
# 直接看 Kbuild 写死的方言（最快）
grep -n 'std=gnu\|CC_FLAGS_DIALECT' Makefile

# 或让一次真实编译打印命令行里的 -std（需已配置过 .config）
make -C . V=1 kernel/sys.o 2>&1 | tr ' ' '\n' | grep '^-std='
```

本仓库对照路径示例：`C:\Users\12392\Desktop\linux-7.1.5\Makefile` 中可见 `-std=gnu11`。

### K&R 两版 vs C89 / C99 / C11（一次性分清）

市面通行的《C 程序设计语言》几乎都是 **第二版** — 见本仓 [02 · 01-Primer-K-and-R-C](../../../../01-c-language/01-Primer-K-and-R-C/)。

| 书 | 年代 | 语言基准 |
|----|------|----------|
| **K&R 第1版** | 1978 | **K&R C / 经典 C / 78C** — 最早非正式习惯；无函数原型、无 `void`/`const`/`stdint`… |
| **K&R 第2版** | 1988 | ✅ **对齐 ANSI C89（≈ ISO C90）** |

> **钉死：K&R 第二版 = C89。完全不是 C99，更不是 C11。**

时间线：

1. 1978 — K&R 第1版  
2. **1989 — ANSI C89**（第一个正式标准）  
3. 1990 — ISO C90（与 C89 几乎等同）  
4. **1999 — C99**  
5. 2011 — C11  

第2版赶在 C89 标准化前后定稿，全书规范就是 **C89**。

#### C89（K&R2 范围）vs C99（书中不涉及）

| | C89 / K&R2 | C99 起（K&R 不讲） |
|--|------------|-------------------|
| 变量声明 | 只能在块开头 | 可在块中任意位置 |
| 单行注释 `//` | **标准不支持**（只有 `/* */`） | 支持 |
| VLA | 无 | 有（**现代内核禁止用**） |
| `stdint.h` / `stdbool.h` | 无 | 有 |
| 指定初始化 / 复合字面量 | 无 | 有 |
| 柔性数组成员 | 无（勿与 GCC 零长数组混淆） | 标准有 |

老式 K&R 函数定义（第1版风格，现代勿写）：

```c
int foo(a, b)
int a;
int b;
{
}
```

坑：原版 **C89 不支持 `//`**。书中或现代笔记里若出现 `//`，是 **编译器扩展 / 现代习惯**，不是原生 C89。

#### 和内核 `-std` 串联

| | |
|--|--|
| K&R2 学习基准 | **C89（ANSI C）** |
| 旧内核（≤5.17） | `gnu89` = **C89 + GCC 扩展** ← 所以很多人先读 K&R |
| 现代内核（≥5.18） | `gnu11` = **C11 + GCC 扩展** |

**K&R 只覆盖「标准 C 基底」。** 内核里的 `typeof`、`({})`、`__attribute__`，以及大量 C99 习惯写法，K&R **不会讲** — 需另补 C99/C11 习惯 + 本节上文「GCC 扩展」+ 本仓 C 书单收尾 **[02 · 05 Embedded C / GNU-C](../../../../01-c-language/04-Kernel-Prep-Embedded-C-Self-Cultivation/)**（完整五书路线见 [01-c-language/README](../../../../01-c-language/README.md)）。

#### 对照：K&R 有 / 内核大量用但 K&R 没有

| K&R2（C89）已具备 | 内核常见、K&R 缺失 |
|-------------------|-------------------|
| 指针、数组、结构体、`malloc` 思维 | `typeof`、语句表达式 `({})` |
| 基本控制流、函数、预处理器 | `__attribute__((...))`、内嵌 `asm` |
| 标准库概念（用户态） | `likely`/`unlikely`、`##__VA_ARGS__` |
| | 块中声明变量、`stdint.h`、`//`（C99 习惯） |
| | `container_of` 一类宏套路 |

### 三层概念（杜绝混淆）

| 层 | 是什么 | 边界 |
|----|--------|------|
| **1. 标准 C（ISO C：C89/C99/C11…）** | ISO 规定的通用语法；合规编译器都应支持 | **没有** 硬件段控制、类型推导等扩展 |
| **2. GNU C（GCC 扩展）** | GCC 在标准上 **私自增加** 的语法/关键字/特性 | **未写入** C 国际标准；`-std=c11 -pedantic-errors` 编内核相关代码会炸 |
| **3. Linux 内核（≥5.18）** | 默认 **`-std=gnu11`** | = C11 基准 + GNU 扩展 |

再钉死一对（常和上一章 libc 搞混）：

| | 属于哪一层 | 何时用 |
|--|-----------|--------|
| **glibc / libc** | **用户态标准库**（运行期） | 用户程序链接它 |
| **GNU C / GCC 扩展** | **语言方言**（编译期语法） | 编译器认不认这些写法 |

> **GNU C ≠ glibc。** 一个是语法扩展，一个是用户态运行时库。

```
用户程序：较标准的 C → 链接 glibc → glibc 封装 syscall
内核代码：GNU C（GCC 扩展语法）→ 编成内核镜像，无 libc
```

→ libc 细节：[Ch5 §5.1](../../chapter-05-system-calls/notes/section-5.1-与内核通信.md)

### 无标准 C 库（运行期）

| 用户态 | 内核态 |
|--------|--------|
| `printf` | **`printk`**（带 **日志级别**） |
| `malloc` | **`kmalloc` / `vmalloc` / slab**（Ch 12） |
| `string.h` 全套 | 内核 **`lib/`** 自实现子集 |
| 链接 glibc | **不能** 链接标准 C 库（`-nostdlib` 一类） |

内核 **完全不调用 glibc 里的函数**；`memcpy` / `strlen` 等在内核自己的 `lib/` 里。

### 内核最常见的 GCC 扩展（一眼能认出）

#### ① `typeof`

标准 C 没有。取表达式类型：

```c
#define min(a, b) ({ \
    typeof(a) _a = (a); \
    typeof(b) _b = (b); \
    _a < _b ? _a : _b; \
})
```

#### ② 语句表达式 `({ ... })`

大括号包代码块，**最后一表达式作「返回值」**。上面 `min` 依赖它。标准 C 不允许。

#### ③ `__attribute__((...))`（超级高频）

```c
__attribute__((packed))       /* 结构体取消填充对齐 */
__attribute__((aligned(8)))   /* 指定对齐 */
__attribute__((section(".init")))  /* 放到指定 ELF 段 */
__attribute__((weak))         /* 弱符号 */
```

驱动天天见：控内存布局、链接段、初始化段释放等。

#### ④ 可变参数宏与 `##__VA_ARGS__`

```c
#define pr_info(fmt, ...) printk(fmt, ##__VA_ARGS__)
```

`##` 处理「没有额外参数时多余逗号」——标准预处理不这么干。

#### ⑤ 省略中间值的三目：`a ?: b`

等价于 `a ? a : b`。标准 C 要求三目必须三个表达式。

#### ⑥ 内联汇编 `asm volatile(...)`

标准 C 无内嵌汇编语法；这是编译器扩展。

#### ⑦ 标签地址 `&&label`、零长/柔性数组成员

```c
struct { int len; char arr[]; };  /* 柔性数组成员；内核网络/缓冲常见 */
```

另有：`likely()` / `unlikely()`（基于 `__builtin_expect`）、`__builtin_constant_p` 等。

```c
if (likely(ptr != NULL)) {
    /* 常见路径 */
}
```

对比实验（示意）：

```c
int x = val ?: -1;
```

| 编译方式 | 结果 |
|----------|------|
| `gcc -std=gnu11` | 正常（GNU 扩展开启） |
| `gcc -std=c11 -pedantic` | 警告/报错：不符合标准 C |

本地小 demo：[`code/gnu_c_extension_demo.c`](../code/gnu_c_extension_demo.c)

### 为什么内核非要用扩展，不用纯标准 C？

内核跑在裸硬件上，**标准 C 能力不够**：

1. **精细控制 ELF 段、对齐** — 标准 C 管不了「函数放哪个段」；初始化函数进 `.init`、启动后释放，靠 `__attribute__((section))`。
2. **泛型宏（`min`/`max`/`container_of`）** — `container_of` 依赖 `typeof`；驱动模型极度依赖它。见 [Ch6 §6.2](../../chapter-06-kernel-data-structures/notes/section-6.2-链表.md)。
3. **硬件交互必须内嵌汇编** — 寄存器、syscall 入口、开关中断。
4. **编译期优化与检查** — `__builtin_*`、`likely/unlikely` 等。

### 误区澄清

#### 误区：内核用 GCC 扩展 = 内核依赖 glibc？

❌ 完全无关。

| | |
|--|--|
| **GNU C** | 编译器语法扩展（**编译期**） |
| **glibc** | 用户态运行时库（**运行期**） |

内核用 GNU C 语法写，但 **不链接 libc**。

### 用什么编译器编内核？GCC vs Clang

**结论：历史传统、主流默认是 GCC；现在官方正式支持 Clang（LLVM）编译 Linux 内核。**

#### 历史：最初只为 GCC 设计

Linus 时代只有 GCC。内核大量依赖 **GCC 扩展（GNU C）**，早期 **只有 GCC 能编通**。  
语法方言 = **GNU C（今为 `gnu11`）**，这套方言 **诞生于 GCC**。

#### 现状：两套都可用

| 编译器 | 定位 |
|--------|------|
| **GCC** | 最通用、社区主力；发行版/模块/学习首选；各架构最成熟；扩展原生完整 |
| **Clang / LLVM** | **官方支持**（见 `Documentation/kbuild/llvm.rst`）；主动兼容绝大多数 GCC 扩展；Android 内核大量用 Clang |

Clang 仍有细坑：极少数 builtin/汇编差异；部分厂商老模块只测过 GCC。

#### 编译器 ≠ 语言标准（别和 `gnu11` 搅在一起）

```
编译器：GCC 或 Clang
语言模式：-std=gnu11（C11 + GCC 扩展方言）
```

| 说法 | 对错 |
|------|------|
| 「内核是 GNU C，所以只能用 GCC」 | ❌ — GNU C 是语法集合；Clang **兼容了** 这套方言 |
| 「gcc 就是 gnu11」 | ❌ — `gcc` 是编译器；可传 `-std=c11`。是 **Kbuild 主动传 `-std=gnu11`** 才开方言 |

通俗：GNU C 原是 GCC「私人方言」；Clang **逆向兼容** 学会了它。  
用户态可用 gcc/clang/msvc 写较标准 C；内核 **绑定 GNU C**，MSVC **编不了** Linux 内核。

#### 实操建议

| 场景 | 建议 |
|------|------|
| 日常学习、写模块/驱动 | ✅ **优先 GCC**（教程/搜错/兼容坑最少） |
| Android、要 LLVM LTO / CFI 等 | 考虑 **Clang**（`make LLVM=1`） |

#### 怎么看「当前用谁编」和 `-std` 在哪设

在源码树根（本机对照 `linux-7.1.5`）：

```bash
# 语言方言写在哪（应看到 gnu11）
grep -n 'CC_FLAGS_DIALECT\|std=gnu11' Makefile

# LLVM= 时改用 clang / ld.lld（顶层 Makefile 约 446 行起）
grep -n 'LLVM\|HOSTCC\|^CC' Makefile | head -40

# 真实编译命令行里的编译器与 -std（Linux/WSL，需已有 .config）
make V=1 kernel/sys.o 2>&1 | head -5
# Clang 构建：make LLVM=1 ...
```

本机树已核对：`CC_FLAGS_DIALECT := -std=gnu11`；`LLVM=` 非空时 `CC=clang`。

### 背诵版

1. **K&R 第2版 = C89**，不是 C99/C11；老内核 `gnu89` 正好叠在这层基底上。  
2. 现代内核（**≥5.18**）：默认 **`gnu11` = C11 基准 + GCC 扩展**；老内核（**<5.18**）：**`gnu89`**。  
3. 基准规范是 C11，但代码习惯大量沿用 C99 特性；**几乎不用** 多数 C11 新特性，且 **禁 VLA**。  
4. **`gnuXX` ≠ 标准 `cXX`** —— 带 `gnu` 就启用 GCC 扩展语法。  
5. **GNU C（语法）≠ glibc（用户态库）** — 不要混淆。  
6. **主流编译器 GCC**；Clang 官方支持且兼容 GNU C；学习内核优先 GCC。  
7. 读完 K&R 后还要补：**C99 习惯 + GNU C**，才能看现代内核。

### 无内存保护

| 现象 | 后果 |
|------|------|
| 非法访问 | 无 **SIGSEGV** — 往往 **oops / panic** |
| 内核内存 | **不可换页** — 每占 1 字节 = **真实物理内存 −1** |
| 泄漏 | 重启前 **不会** 还给系统 |

### 禁止浮点（通常）

用户态由内核 **惰性保存/恢复 FP 寄存器**；内核路径 **默认不处理 FP 状态** → **一般禁止浮点运算**（特殊代码需显式 `kernel_fpu_begin/end` 等）。

### 小而固定的栈

| 事实 | 开发约束 |
|------|----------|
| 内核栈常 **4KB 或 8KB** | **禁止** 栈上大数组/大结构体 |
| 每进程独立内核栈 | 深度递归、大 `alloca` → **栈溢出** |

→ 对照用户态：[02-CSAPP](../../../../02-computer-systems/) 栈与调用约定 · [01 Day 1 汇编栈帧](../../../../projects/P9-os-from-scratch/thirty-days-os/day-01-boot-asm/)

### 同步与并发

并发来源多：**抢占**、**SMP**、**硬/软中断**、**内核线程** → 极易 **竞态**。

| 机制 | 场景（详见 Ch 9–10） |
|------|----------------------|
| **自旋锁** | 短临界区、不可睡眠 |
| **信号量 / mutex** | 可睡眠、较长临界区 |
| **RCU** | 读多写少 |

**HFT：** 用户态网关用 **无锁队列 + 绑核**；内核里对应的是 **关中断、per-CPU、原子、锁顺序** — 错一层就是 **微秒级抖动或整机卡死**。

### 可移植性

Linux **高度可移植** — 代码应：

| 原则 | 反例 |
|------|------|
| **字节序中立** | 假设 little-endian |
| **64 位兼容** | 假设 `int` = 指针宽度 |
| **不硬编码页大小** | 写死 4096 而不 `PAGE_SIZE` |
| **`arch/` 隔离** | 在通用代码里写 x86 汇编 |

<summary>自测题（点击展开）</summary>

**Q1.** 内核代码为什么不能直接用 printf 和 malloc？分别用什么替代？

<details><summary>答案</summary>

内核没有 libc，printf 用 `printk()` 替代（输出到内核日志环形缓冲区，dmesg 查看）。malloc 用 `kmalloc()`/`vmalloc()` 替代——kmalloc 物理连续适合 DMA，vmalloc 虚拟连续物理可不连续。HFT 网卡驱动用 kmalloc 分配 DMA 描述符环。

</details>

**Q2.** 内核代码中为什么不能随意使用浮点运算？

<details><summary>答案</summary>

内核切换到浮点运算需要保存/恢复 FPU 寄存器状态，这在内核态默认不做（为省 context switch 开销）。如果内核代码用浮点，必须手动 `kernel_fpu_begin()`/`kernel_fpu_end()` 包裹。否则会破坏用户态 FPU 状态，导致数据损坏。

</details>
