## ⑤ 系统调用上下文 · System Call Context

---

### 什么是上下文？

系统调用执行期间，内核运行在 **进程上下文（Process Context）**：  
当前正在执行的进程，就是 **发起系统调用的用户进程**。

| 属性 | 含义 |
|------|------|
| **`current`** | 指向发起 syscall 的任务（`task_struct`） |
| **可睡眠** | 缺页、显式 `schedule()`、等 I/O / 锁… |
| **可抢占** | 内核抢占开启时 — 同 **Ch 4** |
| 可访问进程资源 | `task_struct`、fd 表、地址空间等 |

---

### 进程上下文 vs 中断上下文（必分清）

| | 系统调用（进程上下文） | 硬件中断（中断上下文） |
|--|------------------------|----------------------------|
| **触发来源** | **软件指令**，用户主动发起（x86_64 `syscall` / AArch64 `svc #0`） | **硬件电信号**，被动突发 |
| 可否休眠 | ✅ **允许** | ❌ **绝对不能** |
| `copy_from_user` | ✅ 可以 | ❌ 禁止（可能缺页→睡眠） |
| **谁的栈** | 当前进程的**内核栈** | 中断栈 / 独立栈 |
| **发生时机** | 应用想用内核服务时（主动） | **任何时刻随机打断**——不管 CPU 当时在跑用户代码还是内核代码 |
| 典型例子 | `read` 等磁盘 → 进程可休眠，调度器跑别的进程 | IRQ handler |

- 系统调用在分类学上属于**异常（Exception/trap）**——软件触发的同步陷入，**不是硬件中断**（易混淆点；`int $0x80` 时代借用了"软件中断"之名，见 §5.3）。
- 中断上下文**不代表任何任务**：在里头睡眠 = 调度器无人可切 → **死锁 / Oops**。这就是"干完活立刻走人"的原因。
- ⚠️ **坑点（面试高频）**：硬件中断打断进程 A 时，**`current` 仍然指向 A**（栈也是借用的——x86_64 用 per-CPU IRQ 栈，ARM64 直接用 A 的内核栈），但此时跑的是**硬件事件的处理逻辑，不代表 A**。`current` 变量还在、值也没变，**上下文含义却变了**——不能据此睡眠、不能 `copy_from_user`。
- 中断可能打断**正在内核态跑的代码**（比如持着锁的内核路径），所以中断处理必须尽量短——这是 Ch 7/8 顶半部/底半部拆分的根源。

> 比喻：syscall = 学生**举手主动**找老师（内核）问问题，处理这件事的就是这个学生（进程上下文）；硬件中断 = **火警铃**突然响，老师不管正在跟谁说话都得立刻去处理——处理火警不属于任何一个学生（中断上下文）。

很多内核 bug 的根源就是 **混淆二者** — 中断里调用了会睡眠的路径。

---

### 特权级切换 ≠ 进程切换（syscall 的"变"与"不变"）

syscall 从用户态陷入内核态，**全程同一个 `task_struct`**：不换任务、不新建结构体、不发生调度。变的只有三样：特权级、栈、现场保存位置。

| | **特权级切换**（syscall 陷入/返回） | **进程上下文切换**（`schedule()`） |
|--|-----------------------------------|-------------------------------------|
| `task_struct` | **同一个**，`current` 不变 | 换成另一个 task，`current` 更新 |
| 地址空间/页表 | **不切换**，MMU 仍用当前进程的页表 | 切换（换 `mm`、刷 TLB） |
| CPU 特权级 | Ring3→Ring0（x86_64）/ EL0→EL1（AArch64） | 不变（切换发生在内核态内部） |
| 栈 | 用户栈 → 该 task **专属内核栈**，用户现场（寄存器/pc/sp）压入栈顶的 **`pt_regs`** | 换成新 task 的内核栈 |
| 是否调度 | ❌ 没有 `schedule()` | ✅ 这就是调度本身 |

> 这就是"进程上下文 = 内核**替某个 task 干活**"的准确含义：内核代码在跑，但 `current` 绑定着发起 syscall 的任务，可以理直气壮地访问它的 fd 表、`mm`、信号等全部资源。
> 一句话记牢：**进程上下文 = 内核替某个 task 干活；中断上下文 = 硬件事件，与 task 逻辑无关。**

### 串联案例：一次键盘按键的两条路径（面试高频坑）

```
按下 A 键
   │
   ▼ ① 硬件中断（中断上下文）
键盘芯片生成扫描码 scancode（只是数字，不是 ASCII）
键盘控制器向 CPU 发 IRQ ──► CPU 立刻停下手上的活
   │
   ▼ ② 顶半部（仍在中断上下文，只干最少的事）
键盘驱动 handler：读出扫描码、应答中断 ──► 快速退出
   │  （解析/转字符等耗时活交给底半部 → 进程上下文，见 Ch 8）
   ▼ ③ 内核把字符存进 tty 环形缓冲区（内核内存，非程序内存）…… 在这里等待
   │     程序继续跑自己的业务代码，完全不受敲键干扰
   ▼ ④ read() 系统调用（进程上下文）——程序主动来取
sys_read 从内核缓冲区 copy_to_user 拷回用户缓冲区
```

**两种上下文各干一段，缺一不可：**

| | ① 按键发生（硬件中断） | ④ 程序读取（`read` syscall） |
|--|----------------------|------------------------------|
| 谁发起 | 键盘硬件，电信号 | 用户程序主动调用 |
| 上下文 | 中断上下文 | 进程上下文 |
| 能否睡眠 | ❌ 绝对不行 | ✅ 可以阻塞等（没按键就卡在 read） |
| `copy_to_user` | ❌ 禁止 | ✅ 允许 |

> **关键洞察：事件到来 ≠ 程序读取。** 就算没有任何程序调用 `read()`，你敲键盘**照样触发硬件中断**，内核照样把按键存进缓冲区等着——中断是内核与硬件的事，read 是程序与内核的事。
> 硬件中断是**设备行为**：键盘芯片根本不知道应用想不想读、有没有调 `read`，**软件无权阻止硬件产生电信号**。程序"不需要输入"只能做到**不去 `read`、装看不见**——中断路径照走完整。
> 比喻：中断 = **门铃**响了（不管你在干嘛都得去开门）；`read()` = 你**主动**走到门口问"有没有我的快递"。门铃响不响由快递员（硬件）决定，不由屋里人意愿决定。

**那什么时候才真的收不到这个中断？** 只有两种：
1. **屏蔽该 IRQ 线**——内核对中断控制器编程：硬件**照样发信号**，控制器收到并记录 pending，但**不提交给 CPU** → handler 不跑、按键**不入缓冲区、直接丢失**。普通用户程序**没有这个权限**，只有内核能做；
2. **给设备断电**（拔键盘）。

> 对比记忆：**"程序不 read" ≠ "屏蔽中断"**。不 read 时中断**完整执行**、数据躺在缓冲区里等着；屏蔽时中断**根本不进 CPU**、数据直接丢。比喻：快递送到了**门卫**（中断控制器），门卫扣下不转交（CPU）——快递到了，但你拿不到。详见 [§7.1](../../chapter-07-interrupts/notes/section-7.1-中断的概念.md)（可屏蔽 vs NMI）。

**两条边界规则：**

| 边界 | 行为 |
|------|------|
| **缓冲区有限** | tty 环形缓冲区**装满后，新按键直接丢弃**（丢的是新来的）。疯狂敲键盘而程序不 `read` → 按键丢失 |
| **`Ctrl+C` 不走 read** | tty 行规程识别到 INTR 字符，内核**直接给前台进程发 `SIGINT`**——信号路径独立于 read 路径，就算程序从不读输入也能被 Ctrl+C 杀掉 |
| **中断只入队，不投递** | 中断上下文只负责把数据**丢进内核缓冲区**；拷到用户空间必须等 `read` 在**进程上下文**做 `copy_to_user`——中断上下文绝不能直接拷给用户程序（§5.4 睡眠禁令） |

**GUI 桌面模式分叉：tty 之外还有第二条路径。** 上面的 tty 环形缓冲区是**控制台模式**的路径；图形桌面（X11/Wayland）下键盘事件走另一条分发链：

```
①硬件中断 → ②内核 input 子系统生成 EV_KEY 输入事件
   → ③交给显示服务（X11/Wayland）进程 —— 不进 tty 缓冲区！
   → ④显示服务按「焦点」分发：有焦点的窗口才收到事件（经 socket 送给应用进程）
   → ⑤应用（如浏览器）再转发给内部组件（JS 的 onkeydown）
```

- **失焦 ≠ 没有硬件中断**：浏览器窗口在后台时敲键盘，IRQ 照常触发、内核照常生成事件——只是 X/Wayland **不转发**给浏览器进程，JS 的 `onkeydown` 不触发。内核知道你按了键，浏览器不知道。
- **键盘 vs 鼠标分发差异**：键盘事件固定送给**拥有焦点的唯一窗口**；鼠标事件送给**被点中的那个窗口**（点桌面空白，浏览器就拿不到 click）。
- 面试一句话：**应用收不到输入 ≠ 没有硬件中断**。中断是硬件↔内核的事（必然发生）；事件给不给应用，由 GUI 显示服务的焦点逻辑决定——与 tty 模式下"程序不 read"是同一思想的两层实例：*底层事件必然到达，上层取不取/收不收是另一回事*。


**HFT：** 行情网卡收包同理——数据到达是 NIC 硬件中断 + NAPI 软中断（Ch 7/8），策略线程拿到数据靠 `recv()` 系统调用（进程上下文，可阻塞/可非阻塞）。两条路径的时间差就是**收包到应用的延迟**的一部分，调优就是压缩中间每一环。

**HFT：** 一次 `read`/`send` 尖刺 — 除用户态逻辑外，还要看 **是否阻塞、是否持锁过久、是否触发调度**。

### `current` 与 fd 模型

在内核任意 **进程上下文** 代码里，`current` 宏永远指向当前进程 `task_struct`。  
`current->files` 就是进程的文件描述符表 — 与 [§3.8](../../chapter-03-process-management/notes/section-3.8-身份PID与资源FD.md) 的 fd / `struct file` 模型打通。

`sys_read` 内部逻辑（极度简化）：

```
sys_read(fd, buf, len)
    struct file *f = fget(fd);   // 在 current->files 按 fd 找 struct file
    f->f_op->read(f, buf, len, &f->f_pos);  // 走文件操作，动共享 offset
    fput(f);
```

这就是此前讨论的底层源头：

| 用户操作 | 底层效果 |
|----------|----------|
| 两次 `open` 同一文件 | 两个独立 `struct file` → offset **互不干扰** |
| `dup(fd)` | 新旧 fd 指向 **同一** `struct file` → **共享** offset |
| `fork()` | 子进程复制 fd 表，相同 fd 仍指向 **同一** `struct file` → **共享** offset |

### 可重入要求

| 要求 | 原因 |
|------|------|
| **可重入（reentrant）** | 同一 `sys_*` 可能被多线程并发进入 |
| **锁保护共享数据** | 防止竞态 |

```
进程 A 线程1 ──read()──► sys_read ──► 可能睡眠（等磁盘）
进程 A 线程2 ──write()──► sys_write ──► 并发 ──► 需锁/无共享或可重入设计
```

<summary>自测题（点击展开）</summary>

**Q1.** 系统调用在什么上下文中执行？能睡眠吗？

<details><summary>答案</summary>

syscall 在「进程上下文」中执行（current 指向调用进程），可以睡眠（如 read 等待磁盘 IO）。对比：中断处理程序在「中断上下文」中执行，不能睡眠。syscall 中睡眠意味着进程被调度出去，醒来后继续执行。HFT 交易线程如果 syscall 睡眠会被调度器切走，所以要避免阻塞 IO。

</details>

**Q2.** current 在 syscall 执行期间会变吗？

<details><summary>答案</summary>

不会。syscall 在进程上下文执行，current 始终指向调用进程的 task_struct。即使 syscall 中间发生了抢占（preemption），调度回来后 current 仍是同一进程。只有在 schedule() 实际切换后 current 才变。syscall 中访问 current 是安全的。

</details>

**Q3.** syscall 属于中断吗？两者的本质区别是什么？

<details><summary>答案</summary>

不属于。syscall 是**异常（trap）**——软件指令主动触发的同步陷入（x86_64 `syscall` / AArch64 `svc #0`）；中断是**硬件电信号**在任意时刻异步打断 CPU。本质区别在上下文：syscall 跑在进程上下文（有 current、有内核栈、可睡眠），中断跑在中断上下文（不属于任何进程、无 task 可调度、严禁睡眠）。

</details>

**Q4.** 没有任何程序调用 `read()` 时，敲键盘还会触发硬件中断吗？按键数据去哪了？程序最终靠什么拿到字符？

<details><summary>答案</summary>

会。中断是硬件与内核之间的事，与是否有程序在读无关——按键照样触发 IRQ，内核照样把按键事件存进缓冲区。程序最终靠 `read()` 系统调用（进程上下文）主动取数据。即"事件到来（中断）"和"程序读取（syscall）"是两条独立路径。

</details>

**Q5.** 缓冲区满了还继续敲键盘会怎样？`Ctrl+C` 杀掉一个从不读输入的程序，走的是 read 路径吗？

<details><summary>答案</summary>

① tty 环形缓冲区满后，**新来的按键直接丢弃**（旧数据保留）——所以不 read 疯狂敲键会丢字。② 不走 read：`Ctrl+C` 由内核 tty 行规程识别为 INTR 字符后**直接给前台进程投递 `SIGINT` 信号**，信号是内核到进程的另一条独立通道，与 read/copy_to_user 无关。

**Q6.** ① `read` 系统调用在内核执行时，`current` 指向谁？② 网卡中断打断进程 A、执行 handler 期间，`current` 指向谁？此时能睡眠吗？③ syscall 陷入内核会切页表吗？

<details><summary>答案</summary>

① 指向发起 `read` 的任务——syscall 全程同一个 `task_struct`，只换特权级和栈（现场存 `pt_regs`），不换任务、不切页表、不调度。② `current` **仍指向 A**（栈也可能是借用的），但这是**中断上下文**——跑的是硬件事件的处理逻辑，不代表 A，**不能睡眠**。这就是"current 还在、上下文含义变了"的经典坑。③ 不切：MMU 仍用当前进程的页表，切页表只发生在 `schedule()` 换任务时。

</details>

**Q7.** 图形桌面下浏览器窗口失焦时敲键盘：① 会产生键盘硬件中断吗？② 内核知道你按了键吗？③ 前端 JS 能拿到 keydown 吗？为什么？

<details><summary>答案</summary>

① 会——硬件中断是键盘芯片与内核之间的事，与任何应用无关。② 知道，内核 input 子系统照常生成 EV_KEY 事件。③ 拿不到：GUI 模式下键盘事件交给 X11/Wayland 显示服务，由它按**焦点**分发——失焦窗口收不到事件（不转发给浏览器进程），`onkeydown` 不触发。注意 GUI 模式不走 tty 环形缓冲区，路径是 input 子系统 → 显示服务 → 焦点窗口。

</details>
