section-1.1-Unix-的历史

事实 说明
起源 1969 · 贝尔实验室 · Dennis Ritchie、Ken Thompson
成功因素 见下表
Unix 优势 含义
设计简洁 仅 ~几百个系统调用 — 接口少而稳
一切皆文件 设备、socket、管道… 统一 open/read/write
C 语言实现 可移植 — 换硬件主要重编译内核
极快进程创建 独特 fork() — 复制地址空间语义
稳健 IPC 管道、信号等 简单原语

时间线（考据锚点）

1969  Thompson 在 PDP-7 上写 Unix（汇编）
1973  Ritchie 用 C 重写 —— 跨硬件移植的门被打开
1977  Berkeley Software Distribution (BSD) 分支起步
1983  System V（AT&T 商业版）vs BSD —— 「Unix 战争」
1988  POSIX 诞生 —— 停战方案：只标准化 API，不管实现
1991  Linux 以 GPL 重做类 Unix 内核 —— 吸收两者遗产
分叉 留给 Linux 的遗产
System V SysV IPC（shm/sem/msg）、init 体系
BSD sockets 网络栈、mmap、virtual memory 布局
POSIX 今天的可移植性契约——Linux syscall 表基本按 POSIX 覆盖设计

五条优势的内核机制对应

哲学 内核里的落点 现代演化
一切皆文件 VFS 的 file_operations 抽象（Ch 13） io_uring 用队列而非 fd 流——抽象开始让位于延迟
C 实现 内核至今 C 为主（+少量 Rust，6.1+） Rust for drivers 正在写入主线
fork 语义 写时拷贝 COW（3.4） posix_spawn/vfork 是后辈对 fork 成本的补丁
少 syscall read/write/mmap 覆盖 90% 场景 io_uring 一个入口复用百种操作

HFT 对照： 网关仍活在 「少 syscall、少拷贝、快 fork/线程」 的 Unix 遗产里 — 热路径 read/send/mmap 皆是「一切皆文件」后代；而绕开它的两条路（DPDK 用户态轮询、io_uring 直投队列）本质都是对 Unix 抽象税的 revolt——先懂税再谈逃税。

→ 03-linux-userspace-api · 02-CSAPP Ch8

自测题（点击展开）

Q1. Unix 只有几百个系统调用，这为什么对 HFT 有利？

答案

系统调用少意味着 syscall 入口审计面小、热路径可预测。HFT 网关热路径只用 read/write/mmap/send 等十几个 syscall，减少调度器与 VFS 层分支。少而稳的接口 = 内核版本升级时 ABI 兼容性好。

Q2. Unix「一切皆文件」设计哲学对现代网络编程有什么局限？

答案

一切皆文件让 socket/fd 统一接口，但网络包仍需从内核拷贝到用户态（除非用 zero-copy）。HFT 用 AF_XDP/DPDK 绕过 VFS 直接从网卡取包，就是因为「文件抽象」对纳秒级延迟仍有开销。

Q3. fork() 的「独特」体现在哪？它的性能问题后来是怎么被逐步修补的？

答案

独特在复制整个地址空间的语义（子进程获得父进程的完整副本）——比 spawn（传可执行路径重新加载）语义强大得多：可以在 fork 后、exec 前对副本做任意操作（重定向、改环境）。修补史：① vfork（BSD）——不复制，父挂起等 exec，过渡方案；② COW（现代 fork）——只复制页表不复制页，写时才拷——fork 成本从 O(内存) 降到 O(页表)；③ posix_spawn——COW 时代仍有场景省 fork（单页进程池）；④ 线程（clone 共享地址空间）——彻底绕开复制语义。链条读法：语义的优雅先用，性能的账慢慢还。

section-1.2-Linux-的诞生

项 内容
时间 1991 · 赫尔辛基大学 · Linus Torvalds
动机 当时 缺乏强大且免费的 Unix
性质 非商业 · 互联网协作 开发
许可证 GNU GPL 2.0 — 自由 / 开源软件

成长时间线

1991.8  comp.os.mining:「只是个爱好，不会像 GNU 那样大而专业」
1991.9  0.01 发布（~1 万行，无网络、无登录多用户）
1994    1.0 —— TCP/IP、SMP 雏形
2003    2.6 —— 抢占内核、CFS 前夜；开发模式转折点
2005    Linus 自写 git —— 应对无 BitKeeper 之急，反哺全行业
2011    3.0（纯纪念性跳号，宣告「时间驱动发布」而非里程碑驱动）
2020s   5.x/6.x —— io_uring、eBPF 全面爆发、Rust 入场

GPL v2 合规要点（HFT 定制内核必读）

问题 规则
内核模块算衍生作品吗 常识上算（静态链接内核符号）——主线立场"不清楚但别赌"；闭源模块游走在灰色地带（NVIDIA 类驱动长期如此）
用户态程序受感染吗 不受——经 syscall 边界调用不构成衍生（GPL 只约束衍生作品的分发）
只在公司内部跑，要开源吗 不要——GPL 义务在分发时触发；内部部署无限自由
分发设备（含定制内核）给客户 定制内核部分须提供源码；应用层不受影响

同期对手复盘：Linux 为什么赢了

竞争者（1991 前后） 弱点 对照 Linux
GNU Hurd（微内核） 设计完美主义，交付一拖再拖——至今未出 1.0 「先能跑再完善」：0.01 就敢发布
386BSD / BSD 系 AT&T vs BSDi 诉讼（1992-1994）法律不确定性吓退商业采用 无版权阴云 + GPL 保证「永远不会被收回」
MINIX 教学许可证限制商用；Torvalds 正是它的用户 GPL 从 day one 就允许任意使用与修改

历史偶然中的必然：GPL 提供法律确定性、互联网提供协作网络、x86 白牌机提供硬件土壤——三者同时成熟，才让一个"爱好项目"在四年内吃下服务器市场。这也是为什么内核生态的护城河不在代码本身（可 fork），而在三十年的邮件归档、维护者关系与信任网络——fork 得走代码，fork 不走社区。

与 HFT 实盘： 生产内核多为 发行版稳定内核 + 厂商补丁 — 理解 GPL 与源码可得 有助于合规使用 定制内核/驱动。另有一条暗线值得记：Linux 的宏内核选择（见 1.4）当年被 Tanenbaum 骂作「过时设计」——三十年后它反而是低延迟路径（无跨进程 IPC）胜出的架构原因。

自测题（点击展开）

Q1. Linux 采用 GPL v2 许可证，这对商用 HFT 公司有什么影响？

答案

GPL v2 要求修改后的内核代码必须开源。HFT 公司的定制内核调度器/网卡驱动如果分发给客户就需要开源；但只在内部使用不分发则不触发 GPL 义务。许多 HFT 公司选择只在内部维护定制内核。

Q2. Linus 为什么选择宏内核而非微内核？

答案

宏内核性能好：syscall 不需要跨进程消息传递，直接函数调用。微内核的理论优势（模块化、隔离）在实践中被 Linux 的动态模块加载（insmod/rmmod）和命名空间部分弥补。Linus 务实优先于理论纯粹性。

Q3. HFT 公司给自研低延迟网卡驱动做了内核修改，客户要求把整个交易系统（含定制内核）部署到他们机房——GPL 义务怎么算？

答案

分发即触发：把含定制内核的系统交付给客户 = 分发衍生作品——定制内核部分（含驱动，若静态链接内核符号）须向客户提供对应源码（GPL §3）。三条界线：① 只交用户态策略程序、客户自装标准内核——不触发；② 内核改动只在自己机房跑——不触发（内部使用豁免）；③ 交设备/镜像——触发。规避姿势（合法的）：把低延迟逻辑放用户态（DPDK/VFIO）或用 eBPF（GPL 许可的字节码生态）——这也是近年低延迟方案整体向用户态迁移的合规推力之一。

section-1.3-操作系统与内核概述

内核（Kernel）

操作系统最内层 — 提供基本服务、管理硬件、分配资源。

两种地址空间

┌─────────────────────────────────────┐
│  user-space   应用程序（策略、网关）   │
│       │ syscall ↑                     │
├───────┼─────────────────────────────┤
│  kernel-space  内核（机制）           │
│       │ ↑ 中断                        │
└───────┼─────────────────────────────┘
        硬件
空间 谁跑 权限
kernel-space 内核代码 完全硬件访问 · 受保护内存
user-space 普通 app 受限 — 经 系统调用 求内核办事
方向 机制
app → 内核 System Calls（read、write、clone…）
硬件 → 内核 Interrupts → 中断处理程序

进入内核态的三扇门（后文全书骨架）

入口 触发 例子 章节
系统调用 程序主动 read()/svc 0 Ch 5
中断 硬件异步 网卡收包 IRQ Ch 7–8
异常 CPU 执行出错 缺页 fault、除零 Ch 15（缺页）

三者殊途同归：保存用户态现场（pt_regs）→ 切内核栈 → 高特权级执行。差别在回来时——系统调用返回原指令下一条；中断原样返回；缺页可能要先调页（慢路径）再重执行。

机制与策略分离（Unix 设计公理）

概念 定义 内核例子
机制 怎么做（能力） 页表、调度器框架、fd 表
策略 做什么（决策） 换哪页、谁先跑、打开哪些 fd

内核倾向只提供机制，策略交给用户态（调度有 nice/SCHED_FIFO 旋钮；缓存替换内核只给 posix_fadvise 提示）。HFT 的立场是反过来——把策略从内核/OS 手里夺回来自己定（绑核、轮询、自管内存），用的正是内核提供的机制接口。

→ 06.6 SysPerf Ch3 术语

自测题（点击展开）

Q1. 内核态和用户态切换的代价是什么？HFT 如何减少这种切换？

答案

一次 syscall 需要：保存用户态寄存器 → 切换栈 → 进入内核态执行 → 恢复寄存器返回。x86_64 约 100-200ns。HFT 减少 syscall 的方法：批量 IO（io_uring）、内存映射（mmap 替代 read）、绑定 CPU 避免调度、busy-polling 替代中断等待。

Q2. 内核有哪些基本职责？为什么 HFT 工程师必须理解它们？

答案

内核管理 CPU 调度、内存分配、文件系统、网络协议栈、设备驱动、安全隔离。HFT 的每纳秒延迟都与这些子系统相关：调度器决定你的线程何时运行、内存分配器决定 TLB miss 率、网络栈决定包处理路径。不理解内核就无法做极限优化。

Q3. 系统调用、中断、异常三扇门进入内核后的"回来方式"有何不同？

答案

系统调用：保存现场 → 执行服务例程 → 返回下一条指令（调用约定天然继续）；中断：保存被中断处的完整现场 → 处理 → 原样返回被中断的指令（对程序完全透明，像什么都没发生）；异常（缺页）：保存出错指令地址 → 若可修复（调页/按需分配）→ 重新执行同一条出错指令，不可修复才升级为信号。关键差别：syscall/中断是"顺序流继续"，可修复异常是"重放"——所以缺页处理必须保证重放时环境一致（这引出后面 Ch15 的 VMA 锁问题）。

1.4

section-1.4-Linux-与经典-Unix-内核对比

两派设计

类型 特点
宏内核（Monolithic） 单地址空间 内核态 · 性能好
微内核（Microkernel） 服务拆进程 · 消息传递 · 更模块化、理论更「干净」

Linux = 宏内核 — 但 务实借鉴微内核优点：

Linux 特性 说明
可加载内核模块 动态扩展驱动/功能
内核线程 内核态执行后台工作
内核抢占（preemption） 低延迟调度 · 减少「内核跑太久」
SMP 对称多处理器
线程 ≈ 进程 clone() — 统一任务模型

1992 年那场著名论战（Tanenbaum vs Torvalds）

立场 论点 结果
Tanenbaum（MINIX 作者，微内核派） 「Linux 过时了」——微内核才是 90 年代正道；宏内核耦合度高、单点崩溃 理论正确：宏内核确实一个 Oops 可带崩整机
Linus 微内核的 IPC 开销与工程复杂度换不来实战收益；能跑的代码高于漂亮的设计 实战获胜：三十年后 Linux 无处不在，主流微内核（Mach/QNX）反而是利基

延续到今天：性能敏感场景至今仍偏宏内核路线——syscall 是同特权级函数调用 vs 微内核的跨进程消息往返（至少两次切换+拷贝）。

LKM ≠ 微内核服务（易混点）

维度 LKM（Linux 模块） 微内核服务
地址空间 与内核同一——崩了全崩 独立进程——崩了可重启
通信 直接函数调用（EXPORT_SYMBOL） IPC 消息传递
动态性 ✓ insmod/rmmod ✓ 天生
隔离代价 无 每次交互多几µs

所以 Linux 是「可动态装卸的宏内核」，不是微内核。真正往"内核内安全隔离"走的是 eBPF：验证器担保的字节码跑在内核地址空间、出错只杀自身——被戏称为"内核终于长出了一个微内核的器官"。

HFT： 绑核、PREEMPT_RT、模块调优网卡驱动 — 都站在「宏内核 + 可抢占 + 模块」这条线上；PREEMPT_RT 更进一步把内核里的大量锁转成可睡眠锁，把「宏内核跑太久」的尾延迟压平——主线 5.x 起 RT 已逐步合入。

→ 本书后续：Ch 4 调度 · Ch 7–8 中断/下半部 · Ch 17 模块

自测题（点击展开）

Q1. 宏内核和微内核在 syscall 性能上的根本区别是什么？

答案

宏内核：syscall 是同一地址空间内的函数调用，无上下文切换开销。微内核：syscall 需要通过 IPC 消息传递给服务进程，至少两次上下文切换 + 数据拷贝。这就是 Linux 选择宏内核的核心原因。

Q2. Linux 虽然是宏内核，但借鉴了微内核的哪些优点？

答案

动态加载模块（可卸载驱动/文件系统，类似微内核的服务进程）、命名空间/容器（进程隔离）、eBPF（安全沙箱内运行内核代码）。但核心子系统（调度/内存/VFS）仍在内核态，不是微内核。

Q3. eBPF 为什么被戏称为「内核长出的微内核器官」？它和微内核服务的相似与不似各在哪？

答案

相似：① 安全隔离——验证器保证 BPF 程序不能野写内核内存，崩溃只杀自身（微内核服务崩溃不传染的等价物）；② 动态部署——运行时加载/卸载逻辑，无需重编内核（服务进程的等价物）。不似：① BPF 程序跑在同一内核地址空间、同特权级——没有 IPC 消息往返，开销远低于真微内核；② 它只能事件驱动被动触发（挂在 probe/xdp 上），不能自立为常驻服务循环。读法：eBPF 用"验证器担保"替代"地址空间隔离"达成安全性——同一目标，两条实现路径，性能天差地别。

第三代（3.x+）：  2011 年 3.0 纯跳号（20 周年纪念）；
                  此后 4/5/6 均为「数字太大不好看」式跳号
                  （Linus：数手指头用完了）
现行发布节奏 说明
merge window 每个 rc1 后 两周收新特性，随后只修 bug
周期 稳定版 9~10 周一版，雷打不动——「时间驱动」取代「里程碑驱动」
LTS 每年一版获 2 年+ 维护（如 5.4/5.10/5.15/6.1/6.6）；发行版再延长

HFT 选版决策表

需求 选择 理由
生产 tick 路径 LTS（6.1/6.6 级）+ 发行版补丁 2+ 年 bugfix 回溯、回归测试充分

实操：怎么查清「我到底在跑哪个内核」

命令/文件 给你什么
uname -r 运行中内核版本串（bisect/换内核后必查——GRUB 配错时它最先暴露）
cat /proc/version 版本 + 编译它的编译器版本 + 构建用户/主机（排查发行版定制痕迹）
dpkg -l \| grep linux-image / rpm -q kernel 装了哪些内核包（与运行中可能不是同一个）
ls /boot/vmlinuz-* + cat /proc/cmdline 引导了哪个镜像、带什么启动参数

经典坑：装了新内核没重启，或 GRUB 默认项没改——uname -r 还是旧版本。内核升级的"生效"以重启为界，与用户态包管理不同。

警惕「新版崇拜」：最新稳定版的调度器/锁改动可能引入你没测过的延迟行为；HFT 换内核版本 = 换一台没开过的机器——全套延迟基准必须重跑。

自测题（点击展开）

Q1. Linux 内核版本号 5.15.0-25-generic 中每段代表什么？

答案

5 = 主版本号（Linus 每次发布递增）；15 = 次版本号（偶数=稳定版，奇数=开发版，但 2.6 后此规则已废弃）；0 = 修订号（bug fix）；25 = 发行版补丁计数；generic = 发行版 flavor。HFT 生产应选 LTS（Long Term Support）版本。

Q2. 为什么 HFT 生产环境通常选择 LTS 内核而非最新版？

答案

LTS 内核有 2-6 年维护周期，bug fix 回溯稳定。最新版可能有性能改进但也引入回归。HFT 需要可预测的行为，LTS + 厂商验证补丁是安全选择。例如 PREEMPT_RT（实时补丁）通常需要 1-2 年才能从 mainline 回归到 LTS。

Q3. 为什么 2.6 之后 Linux 废弃了「奇偶分稳定/开发」规则？新模型怎么同时保证主线活力与生产稳定？

答案

旧模型的问题：开发版集成周期长达数年（2.3 开发线拖了两年多），合入冲突滚雪球、厂商等不起。新模型（Andrew Morton/Linus 2003 年改革）：主线永远处于可发布状态——每 9~10 周稳定一版；新特性走 merge window 两周 + rc1~rc7+ 冻结只修 bug；激进特性挂在分支/树里养熟再进窗口。稳定性不再靠"奇偶隔离"，而是靠时间切片 + 纪律：任何时刻主线都 ≤10 周龄，而 LTS 从稳定点向后回溯维护——活力与稳定由两个不同节奏的管道分别供给。

自测题（点击展开）

Q1. LKML（Linux Kernel Mailing List）在内核开发中扮演什么角色？

答案

LKML 是内核开发的唯一官方论坛。所有补丁必须发到 LKML 接受 review，Linus 和子系统维护者在此决策。HFT 工程师如果发现内核 bug 或需要新特性，正确路径是：读源码确认问题 → 写补丁 → 发 LKML → 回应 review → 通过 maintainer 进入 mainline。

Q2. 为什么「读源码 + 动手改」比只啃概念书更有效？

答案

内核代码是最终的 ground truth。LKD 书基于 2.6 内核，现代 5.x/6.x 已大改（如 CFS→EEVDF 调度器、io_uring、BPF）。只读书会停留在过时认知；读源码能发现实际数据结构和算法，改代码能验证理解是否正确。

Q3. 一个外公司工程师想让某内核子系统接受自己的补丁，标准路径是什么？为什么「先发 LKML 大方案」往往适反？

答案

标准路径：读 MAINTAINERS 找到子系统维护者→ 小步补丁 + 完整 commit log（说清为什么）→ 发该子系统邮件列表（不一定是 LKML 全场）→ 回应 review、改版（v2/v3…带 diff 注记）→ 维护者收进子系统树 → 下个 merge window 进主线。大方案先行的坑：RFC 大重构没有小步可 review 的切分，维护者无从下手；且没在邮件列表混过、不了解子系统现有讨论语境的"外来大方案"历史上几乎全被搁置。社区默契：先修几个小 bug 建立信任，再提大设计。
