## ④ 引发 Bug 与打印信息

| 宏/函数 | 行为 |
|---------|------|
| **`BUG()` / `BUG_ON(cond)`** | 条件真 → **故意 Oops** · 栈回溯 · 终止当前操作 |
| **`panic()`** | **更致命** — 打印后 **挂起整机** |
| **`dump_stack()`** | 只 **打印栈** — **不杀进程、不 panic** — 日常路径跟踪 |

```c
BUG_ON(ptr == NULL);           /* 绝不应发生 */
if (debug) dump_stack();       /* 我在哪？ */
```

| 选用 | |
|------|--|
| 开发断言 | `BUG_ON` |
| 生产可恢复 | `WARN_ON`（书中相关）/ 错误码返回 |
| 跟踪流 | `dump_stack` |

#### 三者机理差异

```
BUG_ON(cond)  ──► 编译成陷阱指令(ud2) ──► Oops：杀当前上下文,打印栈
WARN_ON(cond) ──► 同样走异常路径,但走 WARN 分支：打印栈 + taint 标志 W,继续跑
dump_stack()  ──► 只是"打印当前栈"函数调用：不异常、不停、不 taint
```

| 副作用对比 | BUG_ON | WARN_ON | dump_stack |
|-----------|:---:|:---:|:---:|
| 打印调用栈 | ✓ | ✓ | ✓ |
| 终止当前执行 | ✓（进程被杀 / panic） | ✗ | ✗ |
| 打 taint 标志 | — | ✓（Tainted: W） | ✗ |
| 可高频调用 | ✗ | ✗（栈打印本身毫秒级） | ✗（同左） |

> **生产代码纪律**（内核社区现行共识）：`BUG_ON` 只用于"**继续运行必然更糟**"的不变量（状态机已损坏）；常规错误路径一律 `WARN_ON` + 返回 `-E...`。`WARN_ON` 也要克制——它同样打印全栈，高频触发等于 printk 洪水（可配 `panic_on_warn` 或 rate-limit 策略）。
>
> 另有 `might_sleep()`：不打印不崩溃，只在原子上下文被调用时告警——是 `CONFIG_DEBUG_ATOMIC_SLEEP` 的探针（见 [18.4](./section-18.4-内核调试选项.md)）。

#### 为什么 `BUG_ON` 在中断上下文更致命

| 上下文 | BUG_ON 之后 |
|--------|-------------|
| 进程上下文 | Oops → 杀当前进程 → 内核尝试继续（若数据结构未坏） |
| **中断上下文** | Oops → **无进程可杀** → `panic()` 整机 |
| 持锁时 | Oops 路径不释放你持有的锁 → 即使进程被杀，等这把锁的其他 CPU 也会卡死 |

> 第三行是"Oops 之后系统还是挂了"的常见解释：**Oops 报告的是第一现场，死因常是它留下的锁尸体**。这也解释了为什么内核社区对 BUG_ON 越来越吝啬——它"终止当前操作"的承诺，在持锁路径上是兑现不了的。

**HFT：** 自研驱动的错误处理对齐同一哲学——**热路径永远走错误码分支**，BUG/WARN 只配初始化与控制面；实盘机器 `panic_on_warn` 保持 0（避免一次可恢复警告带走整机交易）。

**Q1.** BUG_ON() 和 WARN_ON() 的区别？HFT 驱动该用哪个？

<details><summary>答案</summary>

BUG_ON(cond)：条件为真时触发 oops/panic（致命错误，不可继续）。WARN_ON(cond)：条件为真时打印调用栈但继续运行（警告，可能可恢复）。HFT 驱动规则：1) 硬件状态不一致 → BUG_ON（不可信任硬件状态）；2) 参数非法 → WARN_ON + 返回错误码（可恢复）。生产环境避免 BUG_ON 在热路径（会 panic 整个系统）。

</details>

**Q2.** Oops 报告了第一现场，系统却还是在几十秒后彻底挂死——为什么？

<details><summary>答案</summary>

**锁尸体**：出错路径持有的锁在 Oops 后不会释放。进程上下文的 Oops 虽然杀了进程，但其他 CPU 上等这把锁的代码会永远自旋；若是中断上下文 Oops 直接 panic。类似地，被 Oops 跳过的释放路径还会泄漏引用计数、留下半初始化状态——所以"Oops 后还能敲命令"不代表系统还可救，生产纪律是尽快收集现场并重启。

</details>

**Q3.** `might_sleep()` 是干什么用的？它与 BUG_ON/WARN_ON 什么关系？

<details><summary>答案</summary>

`might_sleep()` 是埋在可能睡眠的 API（如 `kmalloc(GFP_KERNEL)`、mutex 路径）里的**探针**：普通内核编译成空操作，开 `CONFIG_DEBUG_ATOMIC_SLEEP` 后变成检查——若当前处于原子上下文（持 spinlock/关抢占/中断），立刻打印栈告警。它是 WARN_ON 家族的自动化版本：不用你手写断言，睡眠函数**自带**"我睡了会不会出事"的自检。

</details>
