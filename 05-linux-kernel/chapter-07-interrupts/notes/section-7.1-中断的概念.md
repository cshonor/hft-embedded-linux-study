## ① 中断的概念 · Interrupts

硬件用 **电子信号** **异步** 打断 CPU 正在执行的指令流，迫使内核 **立即** 响应外设事件。这是 **设备驱动** 与硬件世界交互的 **主入口** — 网卡收包、磁盘完成 DMA、定时器 tick 都依赖它。

| 概念 | 说明 |
|------|------|
| **IRQ（Interrupt Request，中断请求线）** | 每条物理/逻辑中断线对应 **唯一数字**（IRQ 号）— 内核据此区分来源设备 |
| **异步中断（asynchronous interrupt）** | 与当前正在执行的 **指令无关** — 随时可能插入 |
| **中断控制器（interrupt controller）** | PIC / APIC / IOAPIC / GIC 等 — 汇聚多路 IRQ，向 CPU 发 **向量（vector）** |
| **中断描述符表（IDT）** | x86 上存放 **中断门** 入口地址 — CPU 收到向量后跳转到对应处理例程 |

#### 中断 vs 异常（同步陷阱）

| 类型 | 来源 | 时机 | 典型例子 |
|------|------|------|----------|
| **硬件中断（IRQ）** | **外设** | **异步** — 与当前指令无关 | 网卡、磁盘、键盘、定时器 |
| **异常（Exceptions）** | **CPU 执行指令** | **同步** — 由某条指令 **直接触发** | 缺页（page fault）、除零、非法指令 |
| **系统调用陷入** | 用户态 **主动** `int 0x80` / `syscall` | **同步** | 进入内核态执行 `sys_*` |

```
异步 IRQ 插入指令流：
  用户/内核代码:  insn₁ ──► insn₂ ──► [IRQ!] ──► ISR ──► insn₃ ──► …
                                    ↑
                              与 insn₂ 无因果关系

同步异常：
  insn ──► 触发 page fault ──► 缺页处理 ──► 可能返回原 insn 重试
```

#### 中断 vs 轮询：硬件与 CPU 的两种沟通方式

**不是所有硬件电信号都叫中断。** 硬件与 CPU 只有两种沟通方式：

| | 中断 IRQ | 轮询 polling |
|--|----------|--------------|
| 谁主动 | **硬件主动**发电信号通知 CPU | **CPU 主动**反复读硬件寄存器 |
| 硬件行为 | 发中断请求 | 只把状态放在寄存器里，**不发信号** |
| 代表 | 键盘、网卡、磁盘 | 简单/慢速设备、部分嵌入式总线 |

只有设备**主动向中断控制器发请求**的那类信号才叫中断信号。

#### 三种典型设备的触发方式：键盘 · 时钟 · 麦克风

**「硬件有电信号」≠「向 CPU 发 IRQ」。** 三类代表设备的中断行为完全不同：

| 设备 | 中断模式 | 机制 |
|------|----------|------|
| **键盘** | **事件驱动** — 一次按键一次 IRQ | 按键按下 → 键盘控制器发 IRQ；PS/2 原生中断驱动，USB 键盘则是**主机控制器**收到数据后发 IRQ |
| **系统时钟 tick** | **周期性** — 每秒 `HZ` 次 | 硬件定时器芯片（LAPIC timer / arch timer）定期发脉冲：更新 `jiffies`/墙上时间、`scheduler_tick()` 更新 vruntime 并检查抢占 —— **操作系统的脉搏**，抢占式调度的支撑 |
| **麦克风/音频** | **批量 + DMA** — 缓冲区满才一次 IRQ | 音频是高速连续流，**不能每采一个样本中断一次**（CPU 会被干爆）。DMA 控制器整批搬运样本到内核环形缓冲区（**全程不占 CPU**），缓冲区满才发一次 IRQ 通知 CPU 处理一大块 |

> 麦克风的 **DMA 批量中断** 与网卡 **中断合并（interrupt coalescing）**、**NAPI** 本质同源：高速数据流场景下，用「攒一批再通知」换取更低的中断频率 —— 频率越低，对 CPU 热路径（如策略线程）的打断越少。
> USB 麦克风同理：控制器收到音频帧才产生 IRQ，中间大量样本靠总线批量传输。

> ⚠️ 误区：硬件内部自己跑信号 ≠ 向 CPU 发 IRQ 请求。麦克风 Codec 不停采样是硬件内部行为，CPU 感知到的只有"DMA 缓冲区满了"这一个事件。


#### 可屏蔽中断 vs NMI（不可屏蔽中断）

| | 可屏蔽中断 | **NMI**（Non-Maskable Interrupt） |
|--|------------|----------------------------------|
| 能否屏蔽 | ✅ 可以（`disable_irq` / 控制器屏蔽该线，见 §7.7） | ❌ **拦不住，CPU 必须响应** |
| 屏蔽后 | 硬件**照样发信号**，控制器记录 pending 但不提交 CPU → handler 不跑，事件**丢失** | — |
| 典型 | 键盘、网卡、磁盘 | **电源故障、内存硬件损坏**等灾难事件 |

> 屏蔽 ≠ 信号消失：快递照样送到**门卫**（中断控制器），门卫把快递扣下不送给你（CPU）——快递确实到了，只是你拿不到。

#### 中断的代价

| 代价 | 原因 |
|------|------|
| **CPU 流水线冲刷** | 跳转 ISR 破坏分支预测、I-cache 局部性 |
| **缓存污染** | ISR 访问的代码/数据挤掉热路径 working set |
| **关中断窗口** | 处理期间可能屏蔽该 IRQ 线 — 丢后续事件或延迟 |

**HFT：** 高频行情场景下，**每包一次 IRQ** 的网卡会把 CPU 从策略线程 **反复打断** — 合并中断（interrupt coalescing）、NAPI、RSS/RPS 迁核都是为了 **降低 IRQ 频率** 与 **隔离 IRQ 核**。

#### 与驱动开发的关系

| 阶段 | 驱动做什么 |
|------|------------|
| **probe** | 从设备树/PCI 获取 **IRQ 号** |
| **open/启动** | `request_irq()` 注册 ISR |
| **运行时** | ISR 应答硬件、最小工作、调度下半部 |
| **remove/关闭** | `free_irq()` 注销 |

### 常见陷阱

1. 混淆中断（异步硬件触发）和异常（同步指令触发）——中断不可预测，异常由特定指令引起
2. 以为中断处理可以睡眠——hard IRQ 不能睡眠（无 task_struct），threaded IRQ 可以
3. 忽略中断延迟对 HFT 的影响——一次 NIC 中断可能抢占交易线程数十微秒

<summary>自测题（点击展开）</summary>

**Q1.** 中断和异常的根本区别？

<details><summary>答案</summary>

中断：异步、硬件触发（NIC/键盘/定时器），CPU 在两条指令间响应。异常：同步、指令执行触发（#PF 缺页/#GP 段错误/#DE 除零），CPU 在出错指令处响应。Fault 可恢复（重执行），Trap 用于调试（继续），Abort 不可恢复。

</details>

**Q2.** 为什么 hard IRQ 不能睡眠？

<details><summary>答案</summary>

Hard IRQ 运行在中断上下文：无 task_struct（不可调度）、无进程栈（用中断栈）、preempt_count 中 HARDIRQ 位被设置。schedule() 检查 preempt_count != 0 会 panic。解决方案：threaded IRQ（request_threaded_irq），hard IRQ 只确认硬件 + 唤醒内核线程，实际处理在线程中可睡眠。

</details>

**Q3.** HFT 如何减少中断对交易线程的干扰？

<details><summary>答案</summary>

① `/proc/irq/[n]/smp_affinity` 绑中断到非交易核。② `service irqbalance stop`。③ `isolcpus` 隔离交易核。④ `nohz_full` 减少定时器中断。⑤ DPDK 用户态轮询完全绕过中断。⑥ NAPI 轮询模式（网络收包）。

</details>

**Q4.** 麦克风每采集 1 个音频样本会触发一次中断吗？系统时钟 tick 是什么来源？USB 键盘数据到达靠什么通知 CPU？

<details><summary>答案</summary>

麦克风**不会**每样本中断 —— DMA 控制器整批搬运样本到内核环形缓冲区，**缓冲区满才一次 IRQ**（批量 + DMA，否则 CPU 被干爆）。时钟 tick 是**硬件定时器芯片的周期性中断**（每秒 HZ 次），驱动 `scheduler_tick()`。USB 键盘：设备数据经 USB 总线批量传输，**USB 主机控制器**收到数据后产生硬件中断（不是键盘芯片直接连 IRQ 线）。

三者的数据获取殊途同归：中断上下文只把数据放进内核缓冲区（禁睡眠、禁 `copy_from_user`），用户程序最终靠 `read()` 系统调用（进程上下文）`copy_to_user` 取走 —— 见 [§5.5](../../chapter-05-system-calls/notes/section-5.5-系统调用上下文.md)。

</details>
