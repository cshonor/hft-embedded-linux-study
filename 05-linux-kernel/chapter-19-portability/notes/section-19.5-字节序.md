## ⑤ 字节序 · Byte Order

| 序 | 最低地址存什么 |
|----|----------------|
| **大端 BE** | **最高有效字节** |
| **小端 LE** | **最低有效字节** |

| 架构 | x86 / x86_64 = **小端** · ARM64 = **双端**（服务器几乎全配成小端） |

| 规则 | **绝不** 在代码里假设本机序 |

### 内核的杀手锏：`__bitwise` 让编译器帮你抓错

这是内核比用户态 `htons/ntohl` 强的地方——**字节序被编码进了类型系统**：

```c
/* include/uapi/linux/types.h — v6.6 原文 */
#define __bitwise	__attribute__((bitwise))    /* :28 */

typedef __u32 __bitwise __le32;                  /* :38 */
typedef __u32 __bitwise __be32;                  /* :39 */
typedef __u64 __bitwise __le64;
typedef __u64 __bitwise __be64;
```

```c
__le32 a;   /* 小端 32 位 */
__be32 b;   /* 大端 32 位 */
u32    c;   /* 本机序 32 位 */

b = a;      /* ⚠️ sparse 报错：不能把 __le32 赋给 __be32 */
c = a;      /* ⚠️ sparse 报错：不能把 __le32 当 u32 用 */
c = le32_to_cpu(a);   /* ✅ 正确：显式转换 */
```

| 机制 | 说明 |
|------|------|
| `__attribute__((bitwise))` | 告诉 sparse："这个 typedef 是一个**独立的整数类型**，与其他整数类型不可混用" |
| 编译器视角 | GCC/Clang **忽略**这个属性 → 零运行时开销，代码照常生成 |
| sparse 视角 | 把它当成一个新类型 → 混用时**报错** |
| 检查命令 | `make C=1`（编译 + sparse）或 `sparse file.c` |

> **这是"零成本抽象"的典范**：类型安全在**检查期**生效，在**运行期**完全消失。
> 用户态 C 代码没有这个福利（`uint32_t` 大端小端都是它），所以**只能靠命名约定**
> （如 `xxx_be` 后缀）和 code review。

> **实践建议：** HFT 项目可以在自己代码里如法炮制——
> 定义 `typedef uint32_t price_t;` 这类**强类型别名**配合 `-Wconversion` 或使用
> C++ 的 `enum class` / 单字段 `struct` 包装，把"价格/数量/时间戳"在类型层面区分开，
> 让"把价格赋给数量"这种错误在编译期就暴露。

### 转换宏全景

| 方向 | 宏 | 对应 |
|------|----|----|
| CPU → 大端 | `cpu_to_be16/32/64()` | `htons/htonl/htonll` |
| 大端 → CPU | `be16/32/64_to_cpu()` | `ntohs/ntohl/ntohll` |
| CPU → 小端 | `cpu_to_le16/32/64()` | — |
| 小端 → CPU | `le16/32/64_to_cpu()` | — |
| **不带转换**（同构） | `__cpu_to_be32()` / `__be32_to_cpu()` | 用于**已知**两端同序的场景（如给 BE 设备填 DMA 描述符），**双下划线表示"我真的不需要转换"** |

```c
hdr->len   = cpu_to_be16(len);        /* 线上大端 */
val        = be32_to_cpu(hdr->magic);
```

| 命名速记 | |
|----------|--|
| `cpu_to_beXX` | "**我**的话翻译成**对方**（大端）的话" |
| `beXX_to_cpu` | "对方的话翻译成**我**的话" |
| **谁在前，就是"从谁出发"** | |

> **优美性质：** 在小端机器上 `cpu_to_le32` 是**空操作**（编译期展开为恒等）；
> 在大端机器上 `cpu_to_be32` 才是空操作。所以写对一端，另一端自动免费。

### 两个进阶陷阱

**① 位域（bitfield）的字节序**

```c
struct flags {
	__u8 a:1;
	__u8 b:1;
	__u8 c:6;
} __packed;
```
位域在内存中的**排列顺序由 ABI 规定**（不是 C 标准），x86 从低位往高位排，
大端机器常常反过来。**协议里的位域必须用显式掩码手搓**，不要用 C 位域。

**② 浮点数**

浮点也有字节序问题，而且**不能**用 `cpu_to_be32` 转换——那会做整数转换。
正确做法是按 `u32`/`u64` **原样复制位**（`memcpy`）再转字节序。
> HFT 里几乎不用浮点传行情（都是定点整数），这个问题反而避开了——
> 这也是为什么交易所协议普遍用**定点数**（价格 × 10000 存 int64）。

**Q1.** 大端和小端的区别？网络字节序是什么？x86 和 ARM64 分别是什么？

<details><summary>答案</summary>

小端：最低地址存最低字节（0x1234 → [34][12]）。大端：最低地址存最高字节（0x1234 → [12][34]）。网络字节序 = 大端（BSD 遗产）。x86/x86_64 = 小端。ARM64 = 双端（默认小端，可配置大端）。HFT 协议解析必须处理字节序：`ntohl/htonl` 转换网络序。FPGA 可能用大端，与 CPU 交互时要注意转换。

</details>

**Q2.** 内核的 `__le32` 和普通的 `u32` 在机器层面完全一样，为什么要多此一举定义两个类型？

<details><summary>答案</summary>

为了**让工具在编译期抓出字节序错误**，同时**不付出任何运行时代价**。

机制在 `include/uapi/linux/types.h`：

```c
#define __bitwise	__attribute__((bitwise))    /* :28 */
typedef __u32 __bitwise __le32;                  /* :38 */
typedef __u32 __bitwise __be32;                  /* :39 */
```

`__attribute__((bitwise))` 是给静态检查工具 **sparse** 看的：

| 视角 | 如何看待 `typedef __u32 __bitwise __le32;` |
|------|------------------------------------------|
| **GCC / Clang** | 完全**忽略**这个属性 → `__le32` 就是 `u32`，生成的代码一模一样，**零开销** |
| **sparse** | 把它当成一个**全新的整数类型**，与 `u32`、`__be32` 之间**不可隐式转换** |

于是：

```c
__le32 a;  __be32 b;  u32 c;

b = a;               /* sparse: 错误（le → be 未转换） */
c = a;               /* sparse: 错误（le 当本机序用） */
c = le32_to_cpu(a);  /* ✅ 通过 */
```

**对比用户态的困境：** `uint32_t` 无法区分"这个数是大端的还是小端的"，
只能靠命名约定（`xxx_be` 后缀）和人工 review。这就是为什么内核代码的字节序 bug
远少于同规模的普通 C 项目——**它把约定变成了机器可检查的类型**。

检查方式：
```bash
make C=1        # 编译时跑 sparse（C=2 表示强制全部重查）
sparse file.c   # 单独跑
```

**HFT 可以照抄这个思路**（哪怕在用户态 C++ 里）：
- C++：`struct Price { int64_t v; };` 这种**单字段包装**（或 `enum class`）让不同类型不可互转；
- C：用 typedef 别名 + 严格 review + 命名后缀；
- 无论如何，**线上格式转换集中在一处**（编解码函数），不要散落在业务逻辑里。

</details>

**Q3.** 解析交易所二进制行情时，用 `__attribute__((packed))` 结构体直接 `memcpy` 快，还是手工按偏移解码好？

<details><summary>答案</summary>

**手工按偏移解码（或生成的编解码函数）更好。** 直接 `memcpy` 到 packed 结构体的问题不是"慢"，而是**脆弱**：

| 风险 | 说明 |
|------|------|
| **非对齐访问** | 报文里字段常常未按自然对齐排布（比如 u16 在奇数偏移）。x86 上性能损失，ARM 上老核心直接异常；**原子操作则完全不能用** |
| **编译器可能用 SIMD 读 u32** | 编译器假设指针对齐，看到 `u32 *` 就可能生成 `movdq`/`ldp`，遇到非对齐指针直接 `SIGBUS` |
| **packed 结构体传参会丢属性** | `void f(u32 *x)` 收下 packed 成员的地址后，编译器**不再知道**它非对齐 → 生成对齐假设的代码 |
| **位域排列不可移植** | 位域的位序由 ABI 定，x86 与大端机器相反 |
| **协议演进难** | 加一个字段要改结构体，padding 位置变了就得全量回归 |

**正确做法：解码函数 + 显式字节序转换**

```c
/* 一次解析，产出"本机序、自然对齐"的结构体给业务用 */
static inline int decode_snap(const uint8_t *p, size_t n, struct snapshot *out)
{
	if (n < SNAP_MIN_LEN) return -1;
	out->seq    = be64_to_cpu(*(const uint64_t *)(p + 0));  /* 仍要求对齐！ */
	...
}
```

更稳的写法（**完全不依赖对齐**）：
```c
static inline uint32_t rd_be32(const uint8_t *p) {
	return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
	       ((uint32_t)p[2] <<  8) | ((uint32_t)p[3]);
}
```
现代编译器（GCC 8+/Clang）会把这个"字节拼接"**自动识别并优化成一条 `bswap` 指令**，
所以**手写解码并不比 memcpy 慢**——甚至更快，因为编译器知道一切。

**性能上的真实结论：**
- 解码本身通常不是瓶颈，**系统调用和内核网络栈**才是；
- 真要极致优化：用 `AF_XDP`/DPDK 拿到连续的包缓冲后**批量**解码（提高 I-cache 和分支预测命中）；
- 用**生成的编解码代码**（如 SBE / FlatBuffers / Simple Binary Encoding）——
  这些方案天生处理了字节序、对齐和版本演进，比手搓结构体可靠得多。

</details>
