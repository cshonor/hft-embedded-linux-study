## ② 加锁 · Locking

当临界区 **多于一条指令**、或涉及 **复杂数据结构** 时，硬件原子指令 alone 不够 — 靠 **锁（lock）** 保证 **同一时刻只有一个线程** 进入临界区。

| 比喻 | 说明 |
|------|------|
| **房间门锁** | 一次只允许一人进房修改共享数据；其他人 **等待** 或 **自旋** |

#### 锁的基本语义

| 操作 | 效果 |
|------|------|
| **`lock()` / acquire** | 若锁空闲则占有；否则 **等待** |
| **`unlock()` / release** | 释放锁，唤醒等待者 |
| **不变量** | 持锁期间 **独占** 访问被保护的数据 |

#### 锁争用时的两种等待策略

| 类型 | 行为 | 典型锁（Ch 10） | 适用 |
|------|------|-----------------|------|
| **忙等（spin）** | 线程 **空转** 直到锁释放 | **`spinlock_t`** | 临界区 **极短**、持有者可能在 **另一 CPU** 运行 |
| **睡眠** | 当前任务 **阻塞**，**让出 CPU** | **`mutex`** | 临界区 **较长**、持有者可能在 **本 CPU** 且会睡眠 |

```
spinlock（另一 CPU 持锁）：
  CPU0: while (!trylock) ;  ←  burning cycles，但持有者仍在跑

mutex（本 CPU 持锁且睡眠）：
  CPU0: lock → schedule 出去  ← 不浪费 CPU 空转
```

#### 建议性与自愿性（Advisory & Voluntary）

| 事实 | 含义 |
|------|------|
| 内核锁是 **advisory** | **编程约定** — 内核 **不会** 自动给数据结构加锁 |
| **voluntary** | 程序员 **必须主动** `lock` / `unlock` |
| **保护对象** | **数据**，不是「某函数」（→ Ch 9.4） |

| 反模式 | 后果 |
|--------|------|
| 路径 A 加锁、路径 B **裸访** 同一数据 | 锁 **完全无效** |
| 只锁 **写**、不锁 **读**（无 RCU 等） | 读者可能看到 **半更新** 状态 |
| 忘记 **unlock** | 死锁 |

#### 锁与上下文（Ch 7/8 衔接）

| 上下文 | 可用锁 |
|--------|--------|
| **hardirq / softirq / tasklet** | **`spinlock`** — 不可睡眠 |
| **进程上下文** | **spinlock** 或 **mutex** — 视临界区长度 |
| **ISR + 进程共享** | **`spin_lock_irqsave`** |

#### 设计原则（作者）

| 原则 | 说明 |
|------|------|
| **从简单开始** | 一把锁护整个结构 — 先正确 |
| **锁顺序全局一致** | 防 ABBA — Ch 9.5 |
| **临界区尽量短** | 持锁时不做 **无关工作** |
| **有争用再优化** | Ch 9.6 粒度 |

**HFT：** 热路径 **mutex** 在争用下会 **睡眠唤醒** — P99 杀手。短临界区用 **spinlock**；读多写少考虑 **RCU**（Ch 10）。用户态等价物：`std::mutex` vs `spinlock` vs `atomic`。

### 常见陷阱

1. 以为锁只是「加锁/解锁」——还需要考虑锁粒度、锁顺序、死锁预防
2. 把锁粒度越细越好——太细导致锁开销 > 并发收益，太粗导致并行度低
3. 在持锁时做 I/O 或睡眠——spinlock 不能睡眠，mutex 可以但会降低并发度

**Q1.** 锁粒度怎么选择？太粗和太细各有什么问题？

<details><summary>答案</summary>

太粗（一把大锁保护整个数据结构）：① 并行度低（多线程串行化）。② 锁竞争严重。太细（每个字段一把锁）：① 锁开销 > 并发收益。② 锁管理复杂。③ 死锁风险高。原则：① 热路径用细粒度锁（per-CPU/per-bucket）。② 冷路径用粗粒度锁（简单不易错）。③ 先粗后细：先用一把大锁保证正确，prof 后细化热点。

</details>

**Q2.** spinlock 和 mutex 什么时候用？持锁时能做什么不能做什么？

<details><summary>答案</summary>

spinlock：短临界区（<1us），不能睡眠/调度。适合：中断上下文、per-CPU 数据、简单计数器。mutex：长临界区（>1us），可睡眠/调度/做 I/O。适合：复杂数据结构遍历、文件操作、内存分配。选择标准：持锁时间 < 上下文切换时间（~1-5us）→ spinlock；> → mutex。

</details>

**Q3.** HFT 中锁选择有什么特殊考量？

<details><summary>答案</summary>

① 热路径避免锁——用无锁数据结构（SPSC/MPMC 队列）。② 必须用锁时优先 spinlock（用户态 `std::atomic_flag` 自旋）——避免 futex syscall。③ `std::mutex` 底层是 futex，竞争时进内核 → 微秒级延迟。④ RT 优先级继承：`PTHREAD_PRIO_INHERIT` 防优先级反转。⑤ `perf lock` 分析锁持有时间和竞争。

</details>
