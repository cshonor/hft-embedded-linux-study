# 5.2 TCP 回射服务器程序：main 函数

> [5.1 概述](../5.1_Overview.md) · [5.3 str_echo](../5.3_Server_Str_Echo.md) · 并发模型：[Ch 4.8](../../Chapter04_BasicTCPSocket/4.8_ConcurrentServer.md)

## 核心主旨与关键论据

本节给出 **并发 TCP 回射服务器** 的标准 `main` 框架：在 Ch 4 的 `bind/listen/accept` 之上，用 **`fork` 为每个客户派生子进程**，父进程只负责接客，子进程负责 `str_echo` 业务。

---

## 核心知识点与代码拆解

### 初始化三件套

| 步骤 | 调用 | 要点 |
|------|------|------|
| 创建 | `Socket(AF_INET, SOCK_STREAM, 0)` | 得 `listenfd` |
| 地址 | 填充 `sockaddr_in` | **`INADDR_ANY`**（任意网卡）+ 本书约定端口（如 9877） |
| 绑定监听 | `Bind` → `Listen(listenfd, LISTENQ)` | 套接字进入 **`LISTEN`** |

### 主循环（并发模型核心）

```text
for (;;) {
    connfd = Accept(listenfd, ...);   // 阻塞，得已连接套接字
    if ( (childpid = fork()) == 0) {  // 子进程
        Close(listenfd);              // 子不需要监听套接字
        str_echo(connfd);             // 处理该客户
        exit(0);
    }
    Close(connfd);                    // 父必须关闭！
}
```

| 角色 | 持有的 fd | 职责 |
|------|-----------|------|
| **父进程** | 仅 `listenfd`（+ 已 close 的 connfd） | 循环 `accept` |
| **子进程** | 仅 `connfd`（已 close `listenfd`） | `str_echo` 后 `exit` |

### 为何子进程 close(listenfd)

- 子进程继承了父进程所有打开 fd 的**副本**  
- 若不 close，子进程也「挂着」监听套接字，无意义且浪费  
- 更重要的是避免子进程误操作监听套接字  

### 为何父进程 close(connfd)（全书铁律）

`fork` 后 **connfd 引用计数 = 2**（父+子各一份）：

- 只有引用计数降为 **0**，内核才对 TCP 连接发 **FIN**、真正释放  
- 子进程 `exit` 会 close 子侧 connfd（计数 1）  
- **父若不 close**，计数永不为 0 → 连接挂着、**fd 泄漏**、高并发下 **EMFILE**  

---

## 逻辑脉络与因果关系

1. **准备阶段**：一个 `listenfd` 服务所有客户（知名端口）  
2. **接客阶段**：`accept` 每次新建 **connfd**（四元组唯一）  
3. **分流阶段**：`fork` — 父继续接客，子专服一客  
4. **资源阶段**：父子各 close 不需要的 fd → 引用计数正确  

---

## 易错细节与重点结论

| 陷阱 | 后果 |
|------|------|
| 父不 `close(connfd)` | TCP 不断开、fd 耗尽、僵尸连接堆积 |
| 子不 `close(listenfd)` | 多余 fd；极端情况下子误 accept |
| `fork` 失败未处理 | 应检查返回值，否则父当作子跑或逻辑错乱 |
| 先 `str_echo` 再 `fork` | 变成**迭代服务器**，慢客户阻塞全员 |

**考试一句**：并发 TCP 服务器 = **一 listenfd 多 connfd + fork + 父关 connfd 子关 listenfd**。
