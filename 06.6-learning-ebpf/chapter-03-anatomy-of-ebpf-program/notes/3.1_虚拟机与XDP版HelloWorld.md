## 3.1 eBPF 虚拟机

**执行模型**：字节码早期在内核里**解释执行**，现已被 **JIT 编译**取代——既为性能，也为规避 eBPF 解释器的 Spectre 类侧信道漏洞。`net.core.bpf_jit_enable` sysctl 与 `CONFIG_BPF_JIT` 控制开关（`bpftool prog list` 里 `jited` 标志即其产物）。

**指令集/寄存器模型设计成与主流 CPU 架构一一映射**，使 JIT/解释都简单直接——这是 eBPF 能跨 x86/ARM64 高效落地的根基：字节码里的寄存器语义与真实寄存器几乎一一对应，JIT 退化为"翻译"而非"模拟"。

**寄存器**（软件实现，`include/uapi/linux/bpf.h` 中 `BPF_REG_0`~`BPF_REG_10`）：

| 寄存器 | 角色 | 备注 |
|---|---|---|
| R0 | **返回值**（helper 返回值 + 程序返回值共用） | 程序退出时 R0 就是返回码（如 XDP_PASS） |
| R1–R5 | 函数调用参数 | R1 兼任**程序入口的 ctx 指针**；R5 之后就没有了 → helper 最多 5 个参数 |
| R6–R9 | **跨调用保持**（callee-saved） | helper 调用不破坏——验证器日志里大量 `r6 = r1` 就是把 ctx 存进 R6 备份（[6.1](../../chapter-06-verifier/notes/6.1_验证机制与日志.md)） |
| R10 | 栈帧指针（只读） | 512 字节栈的底；`r10 - 8` 是栈顶第一个可用槽 |

对照：这套寄存器约定和 x86-64 SysV ABI（RDI/RSI/RDX/RCX/R8/R9 传参、RAX 返回、RBX/R12-R15 callee-saved）是刻意同构的——JIT 时 r1→rdi、r6→rbx 几乎直译。

**指令** `struct bpf_insn`（64 位 / 8 字节）：

```c
struct bpf_insn {
    __u8 code;          /* 操作码：指令大类 + 具体 op */
    __u8 dst_reg:4;     /* 目标寄存器 */
    __u8 src_reg:4;     /* 源寄存器 */
    __s16 off;          /* 有符号偏移（跳转目标/访存偏移） */
    __s32 imm;          /* 有符号立即数 */
};
```

- 需要装载 64 位立即数时 imm（32 位）放不下 → **宽指令编码 16 字节**（两条槽：`ldimm64` 占两个 bpf_insn，反汇编里 offset 0 的下一条在 2——见 [3.2](./3.2_编译检查与加载附加.md) 的反汇编精读）
- 指令大类：装载（立即数/内存/寄存器）、存储、算术、条件跳转
- 5.12 加入**原子指令**（ADD/AND/OR/XOR 由 imm 指定）——与 04-cpp 学的原子操作直接对应；map value 里的计数器自此可以做内核态原子 `xadd`，不必"读-改-写"三步

**指令上限**：单个程序 100 万条**已验证指令**（`BPF_COMPLEXITY_LIMIT_INSNS`）；非特权用户仍是老限制 `BPF_MAXINSNS = 4096`（定义在 `include/uapi/linux/bpf_common.h`，不在 bpf.h——全仓 grep 找定义时的最后一个反例）。

## 3.2 XDP 版 Hello World（纯 C）

```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>
int counter = 0;                       // 全局变量（= map，见 3.5）
SEC("xdp")                             // ELF 段名 = 程序类型标记
int hello(void *ctx) {
    bpf_printk("Hello World %d", counter);
    counter++;
    return XDP_PASS;                   // 裁决：正常继续处理
}
char LICENSE[] SEC("license") = "Dual BSD/GPL";
```

**要点：**

- 文件名约定 `*.bpf.c` 区分内核态代码与用户态代码（同一仓库里 `.c` 是加载器）
- `SEC("license")` 是**硬性要求**：部分 helper 是 "GPL only"（如 `bpf_probe_read_kernel`），声明不兼容时验证器直接拒绝；LSM 类程序必须 GPL 兼容。libbpf 靠 ELF 段名驱动一切——`SEC("xdp")` 决定程序类型，段名错了后面全错
- `bpf_printk`（libbpf 名）/`bpf_trace_printk`（BCC 名）是同一内核函数的封装；输出进 `/sys/kernel/debug/tracing/trace_pipe`（全机共享、慢，生产用 ring buffer——[2.3](../../chapter-02-hello-world/notes/2.3_坑点HFT关联与自测.md) 坑点 1）
- XDP 在包**到达网卡入口**的瞬间触发，可改包内容并给裁决；**此时还没有任何进程与之关联**（trace 行首 `<idle>-0`）——网络类程序里 `bpf_get_current_pid_tgid()` 拿不到有意义的值

**XDP 五种返回码**（`include/uapi/linux/bpf.h`，v6.6 实测核对）：

| 返回码 | 值 | 语义 | 典型用途 |
|---|---|---|---|
| XDP_ABORTED | **0** | 异常中止，报错并丢包 | 程序内错误路径；**返回 0 ≠ 成功** |
| XDP_DROP | 1 | 立即丢弃 | 黑名单过滤、early drop |
| XDP_PASS | 2 | 正常继续走内核栈 | 默认放行 |
| XDP_TX | 3 | 从同一网卡**弹回发送** | 负载均衡应答反射 |
| XDP_REDIRECT | 4 | 转发到另一网卡/CPU（配合 devmap/cpumap） | RSS 定向、旁路采集 |

- 部分网卡支持 **XDP 卸载**（offload），程序直接跑在网卡上——包进主机内存之前就被处理掉（DDoS 清洗、防火墙、负载均衡利器）；代价是网卡固件的功能子集（卸载路径只支持部分 helper）
- XDP 程序按**接口**挂载（不同接口可挂不同程序），但一个接口只能挂一个——多逻辑要靠程序内部分发（[7.2](../../chapter-07-program-attachment-types/notes/7.2_坑点HFT关联与自测.md) 坑点 1）
