## 3.5 全局变量 = map

2019 年（5.10 前后）起支持全局变量，实现就是 map——**编译器/加载器把 ELF 的数据段变成特殊 array map，全局变量读写被改写为 map 访问**：

| ELF 段 | map 形态 | 内容 | 初始化 |
|---|---|---|---|
| `hello.bss` | array map，1 项 | 初始化为 **0** 的全局变量（`int counter`） | 加载时内核清零 |
| `hello.data` | array map，1 项 | 初始化为**非 0** 的全局变量 | 加载时从 ELF 拷入 |
| `hello.rodata` | array map，1 项，**frozen** | 只读数据（格式串 `"Hello World %d"`） | 加载时冻结，之后写会被拒 |

（Hello World 例子里 counter 是 0 初始化 → .bss；格式串是 const → .rodata——所以源码没写 map，`bpftool prog show` 却关联了 2 个 map。[3.4](./3.4_坑点HFT关联与自测.md) 自测题 3 的答案。）

**性能要点**：全局变量虽然实现为 map，但 verifier/JIT 会把它优化成**直接内存访问**（map value 地址在加载时已确定，指令里就是 `ldimm64 r6, <地址>` + 普通访存）——不走 `bpf_map_lookup_elem` helper，无哈希查找开销。**内核态全局变量的读写成本 ≈ 普通内存访问**，这是 eBPF 里最便宜的持久状态。

有 BTF（编译加 `-g`）时 `bpftool map dump name hello` 能漂亮打印变量名和值；没有则只能看裸十六进制（`19 01 00 00` = 小端 281）——BTF 是"map 的元数据"，第 5 章 CO-RE 的地基。

**pin 机制**：bpffs（`/sys/fs/bpf/`）上的伪文件持有程序/map 的引用；删除文件即释放（没有 `bpftool prog unload` 命令时用 rm）。用户态程序退出后，pinned 的程序仍留在内核。pin 是**路径即引用**的设计——把"内核对象的生命周期"映射成"文件系统的生命周期"，运维语义友好（ls 看得见、rm 能删、重启清空）。

## 3.6 BPF to BPF 调用（libbpf 才有）

```c
static __attribute((noinline)) int get_opcode(struct bpf_raw_tracepoint_args *ctx) {
   return ctx->args[1];
}
SEC("raw_tp")
int hello(struct bpf_raw_tracepoint_args *ctx) {
   int opcode = get_opcode(ctx);
   bpf_printk("Syscall: %d", opcode);
   return 0;
}
```

字节码里 `call pc+7` 跳到子程序偏移 8 处——**真实函数调用，非内联**（编译器默认会把小函数内联掉，`noinline` 仅为演示；生产代码让编译器自行决定）。函数调用要把状态压栈以便返回，而栈只有 512 字节（`MAX_BPF_STACK`，`include/linux/filter.h:90`）→ **嵌套深度受限**（经验上 5 层左右就要掂量了，每层还要留局部变量空间）。

**尾调用 vs 子程序对照**（与 [2.2](../../chapter-02-hello-world/notes/2.2_函数调用与尾调用.md) 呼应）：

| 维度 | BPF-to-BPF 调用 | 尾调用 |
|---|---|---|
| 字节码 | `call pc+N`（相对偏移） | `call imm=2`（特殊操作码）+ PROG_ARRAY 查表 |
| 栈 | **消耗**：子函数栈叠在调用者之上 | **替换**：被调程序从零开始，调用者栈作废 |
| 能否返回 | 能（拿返回值继续） | **永不返回**（类比 execve 替换进程映像） |
| 深度上限 | 512B 栈间接限制（几层） | 33 层（MAX_TAIL_CALLS） |
| 跨程序共享状态 | 栈上传递即可 | 只能走 map |
| 组合 | 5.10 起两者可混用（先子调用再尾调用出去） | 同左 |

**选型直觉**：要复用代码片段、拿返回值 → 子程序；要"接力棒式"串起不同策略的阶段 → 尾调用 + PROG_ARRAY（策略做成数据）。
