# 3.3 demo/ 的骨架：一棵树，每个节点一个 target

[← CH3 库与多目录](./README.md) · [3.2](./3.2-库是打包好的一组o.md) · 下一节：[3.4 PRIVATE / PUBLIC / INTERFACE](./3.4-PRIVATE-PUBLIC-INTERFACE.md)

```text
demo/
├── CMakeLists.txt          ← 顶层：只管 project() + add_subdirectory()
├── libs/
│   ├── ma/                 ← 移动平均库（底层，不依赖任何人）
│   │   ├── CMakeLists.txt  ← add_library(ma STATIC ma.c)
│   │   ├── ma.c / ma.h
│   └── risk/               ← 风控库：内部用 ma，但对外不暴露
│       ├── CMakeLists.txt  ← add_library(risk STATIC risk.c)
│       └── risk.c / risk.h
└── app/
    ├── CMakeLists.txt      ← add_executable(feed_handler main.c)
    └── main.c              ← 只 include "risk.h"
```

依赖图：`feed_handler → risk → ma`。两条规则看懂全部：

1. **`add_subdirectory(dir)`**：进入 dir 执行那里的 CMakeLists——
   每个目录**自治**：自己的源文件、自己的 target、自己的编译选项。
   顶层不知道 ma 库有几个 .c，也不应该知道。
2. **`target_link_libraries(A PRIVATE B)`**：声明 "A 依赖 B"——
   之后 CMake 自动做三件事：排好编译顺序（先 B 后 A）、
   链接时把 B 加进 A 的链接命令、把 B 标记为 PUBLIC 的属性传给 A。

### 第三方库没有源码，不进 `add_subdirectory`

上面那棵树（`libs/ma`、`libs/risk`、`app`）每个节点都是**自己有源码**的 target。
第三方库只有 `include/ + lib/` 两件套、没有 `.c/.cpp`，不能 `add_subdirectory`——
要把"已存在的一个库"包装成 target，用 **IMPORTED**：

```cmake
# 1. 声明：这是个现成的库，我不管它怎么编出来的
add_library(glfw SHARED IMPORTED)
set_target_properties(glfw PROPERTIES
    INTERFACE_INCLUDE_DIRECTORIES "${CMAKE_CURRENT_SOURCE_DIR}/third_party/glfw/include"
    IMPORTED_LOCATION             ".../lib/x64-windows/glfw3.dll"   # 运行时加载的
    IMPORTED_IMPLIB               ".../lib/x64-windows/glfw3dll.lib" # 链接器用的导入库
)

# 2. 用起来和自己编的库一模一样
target_link_libraries(feed_handler PRIVATE glfw)
```

**注意这三个属性和 VS 属性页那三步一一对应**
（见 [01.7 2.2](../../01.7-platform-toolchain/02-windows-msvc/2.2-选项对照全表.md)）：

| CMake 属性 | VS 属性页位置 | 作用阶段 |
|-----------|--------------|---------|
| `INTERFACE_INCLUDE_DIRECTORIES` | C/C++ → 常规 → 附加包含目录 | 编译期 |
| `IMPORTED_IMPLIB` | 链接器 → 输入 → 附加依赖项 | 链接期 |
| `IMPORTED_LOCATION` | （dll 就位，见下） | 运行期 |

路径一律以 `${CMAKE_CURRENT_SOURCE_DIR}` 起头，**绝不写绝对路径**——
否则同事 clone 下来就报 `file not found`。

三条路，按库的形态选：

| 场景 | 写法 |
|------|------|
| 只有预编译二进制（闭源 SDK） | `add_library(... IMPORTED)` + `IMPORTED_LOCATION` |
| 装在系统 / 包管理器里 | `find_package(GLFW3 REQUIRED)` 然后 `target_link_libraries(app PRIVATE glfw)` |
| 有源码 | `FetchContent_Declare` / `FetchContent_MakeAvailable`，或当普通子目录 `add_subdirectory` |

有源码时用 `FetchContent` / `add_subdirectory` 随工程一起编，还有个隐藏好处：
编译器、标准库、C++ 标准版本全部一致，**天然规避 C++ 动态库 ABI 不兼容的坑**
（见 [C++Primer 1.5.2](../../04-cpp/M0-entry-syntax/01-C++Primer/ch01-getting-started/1.5-a-brief-introduction-to-classes/1.5.2-链接编译产物与示例.md)）。

### 别忘了第四步：把 dll 拷到 exe 旁边

Windows 动态链接时，链接成功 ≠ 能运行。CMake 里的等价做法是构建后自动拷贝
（相当于 VS 的「生成后事件 xcopy」）：

```cmake
add_custom_command(TARGET feed_handler POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_if_different
        $<TARGET_FILE:glfw_shlib>
        $<TARGET_FILE_DIR:feed_handler>)
```

`$<TARGET_FILE_DIR:...>` 是生成器表达式，能保证拷到 exe 所在的那个目录（Debug/Release 各一份）。
漏了这步的表现：编译链接全程绿灯，双击 exe 才弹「无法找到 glfw3.dll」——
那已经不是 C/LNK 编号能覆盖的阶段了（见 [01.7 2.6](../../01.7-platform-toolchain/02-windows-msvc/2.6-错误编号速查.md)）。

[ 40%] Linking C static library libma.a
