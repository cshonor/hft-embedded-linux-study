# 2.9 ABI 与交叉编译的边界：为什么"一份二进制到处跑"是假的

[← CH2 toolchain file](./README.md) · 上一节：[2.7 与后续衔接](./2.7-与后续衔接.md) · [2.8 本机实测复跑](./2.8-本机实测复跑.md)

## 本节讲什么

2.1–2.8 讲的是"**怎么**交叉编译"，本节讲边界："交叉编译**不能**为你做什么"。

把四个常被混为一谈的概念钉开：

| 概念 | 属于哪一层 | 谁定 |
|---|---|---|
| **ISA（指令集架构）** | CPU 硬件层 | ARM / x86 / RISC-V 的芯片设计者 |
| **ABI（应用二进制接口）** | 二进制层：机器码怎么排、怎么互相调用 | 操作系统 + 编译器共同约定 |
| **API（源码接口）** | 源码层：函数原型、头文件 | 库作者 |
| **源码可移植性** | 源码层 | 语言标准 + 你写代码的纪律 |

一句话：**不是"同一段二进制被不同 CPU 解读出不同结果"——不同 CPU 根本读不懂对方的机器码。ABI 是"同款 CPU 上，不同系统/编译器之间还得额外对齐的那套规矩"。**

## 要点

### 1. 先分清：ISA 问题和 ABI 问题不是一回事

```
源码可移植   ← C 语言标准管这一层（同一份 .c 给谁编都能过）
──────────────────────────────────────────────
ABI 层       ← 二进制怎么排：类型大小、对齐、调用约定、目标文件格式
──────────────────────────────────────────────
ISA 层       ← CPU 指令集：x86 指令 ARM 不认识，反之亦然
```

- **ISA 不同**：连"能不能执行"这关都过不去，跟 ABI 无关。
- **ISA 相同、ABI 不同**：指令 CPU 都认识，但排列规则对不上 → 加载后行为错乱。

### 2. ABI 到底约定了什么

| 类别 | 具体内容 |
|---|---|
| 数据模型 | `int` / `long` / 指针各占几字节（LP32 / ILP32 / LP64 / LLP64），结构体 padding 与对齐 |
| 调用约定 | 参数进哪些寄存器、超了怎么压栈、谁清栈、返回值放哪 |
| 浮点约定 | 硬浮点（进 VFP 寄存器）还是软浮点（当整数传） |
| 目标文件格式 | ELF / Mach-O / PE，符号修饰规则（Mach-O 给符号加前导 `_`） |
| OS 接口 | 系统调用编号与调用方式、动态链接器路径 |

实测（本机 clang 23.1.0，同一份 `.c` 换成不同 target）：

| 实验 | armv7-linux-gnueabihf（ILP32） | aarch64/x86_64-linux（LP64） |
|---|---|---|
| `_Static_assert(sizeof(long) == 8)` | ❌ 断言失败 | ✅ 通过 |
| `_Static_assert(sizeof(long) == 4)` | ✅ 通过 | ❌ 失败 |

**同一份源码，换个 target，`long` 就从 4 字节变 8 字节**——这就是 ABI 在源码之下动手脚的样子。

### 3. 调用约定：同一句 `f(1,2,3,4...)`，寄存器完全不同

`int f(int,int,int,int,int,int,int,int)` 的调用点，`-S` 出的汇编（clang -O0）：

| target | 前四个参数落在 |
|---|---|
| `armv7-linux-gnueabihf` | `r0, r1, r2, r3` |
| `aarch64-linux-gnu` | `w0, w1, w2, w3`（即 `x0`–`x7`） |
| `x86_64-linux-gnu` | `edi, esi, edx, ecx`（SysV 约定） |

### 4. 同架构同系统也可能不兼容：硬浮点 vs 软浮点（"hf" 的来历）

`float g(float)` 传参，同一个 armv7、同一个 Linux，只改 ABI 后缀：

```asm
gnueabihf（硬浮点）:  vmov.f32  s0, #1.000000e+00      ; 直接进 VFP 寄存器 s0
gnueabi  （软浮点）:  mov  r0, #1065353216             ; 当整数塞进 r0
                      vmov s0, r0                      ; 再搬到 VFP
```

所以 `arm-linux-gnueabihf` 最后那个 **hf = hard float**：**指令集一样、系统一样，ABI 不一样，二进制照样不能混用**。这也是交叉编译器必须选完整 triple 的原因：`架构-厂商-系统-ABI`。

### 5. 同架构不同 OS：文件格式与符号名也变了

同一个 aarch64，编给 Linux 和 macOS：

```
linux .o  ：ELF， 未定义符号  f
macOS .o  ：Mach-O，未定义符号 _f      ← 多了前导下划线
```

### 6. 交叉编译到底做了什么

```
同一份 main.c
   ├─ arm-linux-gnueabihf-gcc  →  ARM 指令 + GNU/Linux hard-float ABI + 目标系统库  →  ARM 板子上跑
   ├─ aarch64-linux-gnu-gcc    →  aarch64 指令 + LP64 ABI                          →  Pi 5 / 服务器上跑
   └─ 本机 gcc                 →  x86_64 指令 + 本机 ABI                            →  本机跑
```

编译器做两件事：**生成目标 CPU 的指令** + **遵守目标平台的 ABI 与系统库约定（靠 sysroot 里的头文件和库）**。

> ❌ 交叉编译 ≠ 一份二进制到处跑
> ✅ 交叉编译 = 一份源码，编译**多次**，产出**多个互不通用**的二进制

### 7. 两种"跑不起来"的现象（要会区分）

| 情形 | 现象 | 实测 |
|---|---|---|
| **ISA 不同**（把 ARM ELF 拷到 x86） | 内核/加载器直接拒：`exec format error`（exit 126） | ✅ 本机实测：执行 STM32 的 `blink.elf`（ELF 32-bit ARM）→ `exec format error` |
| **ISA 同、ABI 不同**（如 Android ABI vs Linux GNU ABI、soft vs hard float） | 指令 CPU 认识，行为错乱：结构体错位、参数错位 → 段错误 / 崩溃；**也可能在加载阶段就被动态链接器拒绝**（ELF OS ABI 不匹配、找不到解释器），不一定能"加载成功再崩" | — |

**区分口诀**：报"非法指令 / Exec format error" = **ISA 层**；能加载却莫名其妙崩 = **ABI 层**。

### 8. 谁才有"一份二进制到处跑"

| 方案 | 机制 | 代价 |
|---|---|---|
| Java | 同一份 `.class` 字节码，各平台 JVM 解释/JIT | JVM 本身是各平台一份二进制 |
| .NET / IL、WebAssembly | 同理，中间码 + 运行时 | 需要运行时 |
| **Go** | 仍要按 `GOOS/GOARCH` **分别编译**；但默认静态链接，产物在**同 OS + 同架构**的机器间可直接拷贝 | 不是跨 OS / 跨架构可移植 |
| **C/C++** | ❌ 没有中间码，产物就是目标机的机器码 | 靠源码可移植 + 重新编译 |

所以：

- **源码可移植**（C 的目标）：一套源码，各平台各自编，各自跑。
- **二进制可移植**（C/C++ 做不到）：一个 exe 拷到别的 CPU/OS 直接跑。

## HFT / 嵌入式关联

- 交易程序常要同时出 x86_64 服务器版和 aarch64（AWS Graviton / 边缘网关）版：**同一套源码，两条 CI 流水线，两个二进制**，任何一个混用都是 ABI 事故。
- 嵌入式最典型的 ABI 事故：给 `-mfloat-abi=hard` 编译的库链进 soft-float 工程，编译链接全绿，上板浮点计算全是垃圾。
- 内核模块更要命：模块必须和内核用**同一套编译配置**，`vermagic` 不匹配直接拒绝加载——这本质也是 ABI 校验。
- 本机也能演示"跑不了"：把 STM32 那个 ARM ELF 拷到 Mac 上执行，实测 `exec format error`。要跑它得靠 `qemu-arm` 这类**二进制翻译器**——那不是 CPU 读懂了 ARM 指令，是软件在模拟（本机未装 qemu）。

## 代码自测

<details><summary>Q1（Quiz）：在 x86 PC 上用 arm-linux-gnueabihf-gcc 编译出的 ARM 程序，能直接在 x86 PC 上跑吗？为什么？</summary>

**不能。** 两层原因，任一层都足以否决：
1. **ISA 不同**：x86 CPU 看不懂 ARM 指令，ARM 指令在 x86 上不是"跑得慢"而是完全无法解码。
2. **ABI/OS 不同**：产物是 Linux ELF，依赖 Linux 的动态链接器和系统调用约定（在 Mac 上还涉及 Mach-O vs ELF）。
实测现象：执行 STM32 的 ARM ELF → `exec format error`（exit 126）。
想跑可以：装 `qemu-arm` 用户态模拟（二进制翻译），或放进 ARM 容器/板子。
</details>

<details><summary>Q2：`long` 在 32 位 ARM Linux 和 64 位 ARM Linux 上分别多大？这属于 ABI 的哪一类约定？</summary>

32 位 ARM（ILP32）= 4 字节，aarch64（LP64）= 8 字节（实测 `_Static_assert` 一边过一边失败）。属于 **数据模型**约定，是 ABI 的一部分——注意：`int` 大小不是 ABI 的全部，只是其中一项。
</details>

<details><summary>Q3：两个 armv7 Linux 程序，一个用 gnueabihf 编、一个用 gnueabi 编，能链接到一起吗？</summary>

不能（或链接上后运行出错）。硬浮点把 `float` 参数直接放 VFP 的 `s0`，软浮点当整数塞 `r0`——同一条调用两边理解不同，浮点参数全是垃圾。这就是 triple 里必须写全 `hf` 的原因。
</details>

<details><summary>Q4："交叉编译实现了 write once, run anywhere" 这句话对吗？</summary>

不对。交叉编译实现的是 **write once, compile everywhere**：源码一份，每个平台各编一次，产出各自独立的二进制。真正的"一份二进制到处跑"要靠中间码 + 运行时（JVM / .NET / WASM），C/C++ 原生做不到。
</details>
