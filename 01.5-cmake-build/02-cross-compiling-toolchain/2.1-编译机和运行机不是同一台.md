# 2.1 问题的起点：编译机和运行机不是同一台

[← CH2 toolchain file](./README.md) · 下一节：[2.2 交叉编译只比本机编译多三件事](./2.2-交叉编译只比本机编译多三件事.md)

[第 1 章](../01-minimal-c-project/README.md)的隐含假设是**编译机 = 运行机**（本机编译本机跑）。嵌入式把这层纸捅破了：

```text
编译机（host）                运行机（target）
Mac / x86_64 Linux  ──编译──▶  树莓派 5（aarch64 Linux）
PC / x86_64         ──编译──▶  STM32（Cortex-M3 裸机，连 OS 都没有）
```

板子性能弱、没键盘没编辑器，没人想在板子上装编译器——**在强机器上编出弱机器的二进制，
这就是交叉编译（cross compiling）**。

Makefile 时代这件事的写法，在 `STM32-/labs/00` 见过完全体：

```makefile
CC = arm-none-eabi-gcc
CFLAGS = -mcpu=cortex-m3 -mthumb -Wall -O2
LDFLAGS = -T stm32.ld --specs=nosys.specs
```

能工作，但三个老问题原样出现：平台写死、找库靠手拼、换个芯片改一堆。
CMake 的答案是：**这些信息不属于工程描述，属于"工具链描述"——单独抽成一个文件。**

## 产物怎么到板子上：比本机编译多出来的四步

"本机编译 → 出二进制 → 弄到板子上跑"这个骨架没错，但板子那一端**不是"传输"，是烧录进一个写死的地址**：

| 步骤 | 做什么 | 工具 |
|---|---|---|
| ① 交叉编译 | 出 ELF | `arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -ffreestanding -nostdlib -T linker.ld`，或 clang 路线（[2.8](./2.8-本机实测复跑.md)） |
| ② 格式转换 | ELF → 裸二进制 | `arm-none-eabi-objcopy -O binary firmware.elf firmware.bin`（clang 路线用 `llvm-objcopy`） |
| ③ 烧录 | 物理写入 Flash 的**固定地址** | ST-Link/J-Link 走 SWD（`st-flash` / OpenOCD），或串口 bootloader |
| ④ 运行 | 复位/上电即开跑 | 无工具——**这就是"没有 OS"的含义** |

两个容易想错的地方：

- **不是"传过去"**：F103 没有文件系统、没有 OS 接收文件。是链接脚本先把地址钉死（F103C8T6：Flash `0x08000000` 起 64 K、SRAM `0x20000000` 起 20 K，见 [6.18 链接脚本](../../01-c-language/05-embedded-kernel-practice/06-ch6-toolchain-custom/6.18-链接脚本.md)），烧录器只是把 `firmware.bin` 按这个布局写进 Flash。
- **上电后是硬件自己跳**：Cortex-M 复位时从 Flash 首地址取**中断向量表**——第 0 个字装进 SP、第 1 个字装进 PC（跳 `Reset_Handler`）。所以工程里必须有启动代码（[3.3.4 从复位到 main](../../01-c-language/05-embedded-kernel-practice/03-ch3-embedded-driver/3.3-bare-metal/3.3.4-从复位到main的启动代码.md)）。

**本机实测**（`demo/cortex-m-clang/` 就是一套 F103 最小 freestanding 工程：`startup.c` + `linker.ld` + `main.c`，clang 路线，产物 296 字节）：

```text
08000000 <g_vectors>:
 8000000: 00 50 00 20   ← 0x20005000 = SRAM 末尾（0x20000000+20K）→ 初始 SP
 8000008: 41 00 00 08   ← 0x08000041 = Reset_Handler | 1（Thumb 位）
```

ELF 头里的 `Entry point address: 0x8000041` 和上面第 1 个字完全对应——**"入口地址"在裸机里不是 `main`，是 `Reset_Handler`**。

### 顺带把 `arm-none-eabi` 这个名字拆开

2.2 给过三元组语法 `<架构>-<厂商>-<系统>[-<ABI>]`。裸机那个 `arm-none-eabi` 只有三段，**`none` 落在哪一段并不固定**——用 clang 展开看归一化结果（`-S -emit-llvm` 看 module triple）：

| 输入 `-target` | clang 归一化 | 各段 |
|---|---|---|
| `arm-none-eabi` | `armv4t-unknown-none-eabi` | arch=armv4t，vendor=unknown，**os=none**，env=eabi |
| `arm-none-linux-gnueabi` | `armv4t-none-linux-gnueabi` | arch=armv4t，**vendor=none**，os=linux，env=gnueabi |

同样是 `none`：前一行它落在"系统"段（所以"`none` = 没有 OS"在裸机名字上确实成立），后一行它跑到"厂商"段去了。靠谱的判据不是 `none` 这个词，而是**系统段里没有真 OS 名 + 末段是 `eabi`**。

另外：这台 Mac **没装 `arm-none-eabi-gcc`，也不需要** —— clang 自带全部 ARM 后端，"交叉"只是一个 `--target` 参数（[2.8](./2.8-本机实测复跑.md) 有完整实测）；`-ffreestanding` 到底改了哪些东西、标准保证哪些头文件可用，见 [3.3.0](../../01-c-language/05-embedded-kernel-practice/03-ch3-embedded-driver/3.3-bare-metal/3.3.0-裸机C与宿主C的区别.md)。
