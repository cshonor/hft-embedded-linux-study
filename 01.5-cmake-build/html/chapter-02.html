导读

本章讲什么： 第 1 章的 demo 是"在 Mac 上编给 Mac 跑"。这章回答下一个问题： 同一份 CMakeLists.txt，怎么编出能在 ARM 板子上跑的二进制？ 答案是一份几十行的 toolchain file——把 Makefile 里写死的那串交叉编译 flag 挪到它该在的地方。 读完能做的事：给 ARM Linux（树莓派）和 Cortex-M 裸机（STM32）各配一次交叉构建， 并看懂配置输出里每一行在说什么。

前置：只需第 1 章。不要求有板子——配置阶段的输出本机就能看。 说明：本章命令与输出按 CMake 3.16+ 标准格式整理，本机复跑路径附在每一步后面。 示例工程： demo/——与第 1 章同款三文件工程，配两份 toolchain file。

2.1

问题的起点：编译机和运行机不是同一台

← CH2 toolchain file · 下一节：2.2 交叉编译只比本机编译多三件事

第 1 章的隐含假设是编译机 = 运行机（本机编译本机跑）。嵌入式把这层纸捅破了：

编译机（host）                运行机（target）
Mac / x86_64 Linux  ──编译──▶  树莓派 5（aarch64 Linux）
PC / x86_64         ──编译──▶  STM32（Cortex-M3 裸机，连 OS 都没有）

板子性能弱、没键盘没编辑器，没人想在板子上装编译器——在强机器上编出弱机器的二进制， 这就是交叉编译（cross compiling）。

Makefile 时代这件事的写法，在 STM32-/labs/00 见过完全体：

CC = arm-none-eabi-gcc
CFLAGS = -mcpu=cortex-m3 -mthumb -Wall -O2
LDFLAGS = -T stm32.ld --specs=nosys.specs

能工作，但三个老问题原样出现：平台写死、找库靠手拼、换个芯片改一堆。 CMake 的答案是：这些信息不属于工程描述，属于"工具链描述"——单独抽成一个文件。

2.2

第一性原理：交叉编译只比本机编译多三件事

← CH2 toolchain file · 2.1 · 下一节：2.3 一份 toolchain file 逐行解剖

剥掉术语，交叉编译需要回答的问题只有三个：

问题 Makefile 里的答案 CMake 里的答案
① 产出物给谁跑？ 隐含在编译器名字里 CMAKE_SYSTEM_NAME + CMAKE_SYSTEM_PROCESSOR
② 编译器换谁？ CC = arm-none-eabi-gcc CMAKE_C_COMPILER（三元组前缀展开）
③ 头文件/库去哪找？ 手拼 -I -L -isystem CMAKE_SYSROOT + CMAKE_FIND_ROOT_PATH_MODE_*

三元组（target triple）是贯穿全章的词：<架构>-<厂商>-<系统>[-<ABI>]。 交叉工具链里每个工具都带这个前缀——arm-linux-gnueabihf-gcc 读作 "给 ARM 架构、跑 Linux、用 gnueabihf ABI 的 gcc"。两个最常用的：

三元组 目标 对应场景
arm-linux-gnueabihf ARM 32 位 + Linux + 硬浮点 ABI 树莓派 Zero/2、ARM 工控板（aarch64 板子用 aarch64-linux-gnu）
arm-none-eabi ARM 裸机，无 OS STM32 等 Cortex-M 单片机

toolchain file 就是把上面三件事写成 CMake 变量的一份 .cmake 文件。 它不属于任何一个工程——同一套板子，所有工程共用一份。

2.3

一份 toolchain file 逐行解剖

← CH2 toolchain file · 2.2 · 下一节：2.4 跑一次

demo/arm-none-eabi.cmake（Cortex-M3 裸机）全文逐段看：

# ① 产出物给谁跑
set(CMAKE_SYSTEM_NAME Generic)        # 裸机 = Generic；跑 Linux 就写 Linux
set(CMAKE_SYSTEM_PROCESSOR arm)

CMAKE_SYSTEM_NAME 是交叉编译的总开关：只要它不等于本机系统， CMake 就把 CMAKE_CROSSCOMPILING 置 ON，后续行为全部切换成交叉模式。 裸机写 Generic——没有操作系统，不是拼错。

# ② 编译器换谁
set(triple arm-none-eabi)
set(CMAKE_C_COMPILER   ${triple}-gcc)
set(CMAKE_ASM_COMPILER ${triple}-gcc)

# 裸机没有启动文件和链接脚本就链不出可执行文件，
# CMake 的编译器自检默认试链接 → 必然失败。改成只验证"能编译"：
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)

CMAKE_TRY_COMPILE_TARGET_TYPE 是裸机 toolchain file 的灵魂一行， 没有它第一次配置就报 "C compiler cannot build executables"—— 不是工具链坏了，是 CMake 的自检方式在裸机上不成立。

# ③ CPU 架构 flag：Makefile 里那串 -mcpu 的归宿
set(CMAKE_C_FLAGS_INIT "-mcpu=cortex-m3 -mthumb")

_INIT 后缀的含义：CMake 第一次探测编译器时就把这些 flag 带上， 之后所有 target 自动继承。对比在 CMakeLists 里给每个 target 手写 target_compile_options(... -mcpu=cortex-m3)——那是把工具链信息泄进了工程描述， 换一块板子要改所有 CMakeLists，正是要避免的事。

# ④ find_* 的搜索边界（最容易翻车的地方，[2.5](./2.5-交叉编译的找库边界.md) 专节讲）
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)

demo/arm-linux-gnueabihf.cmake 结构相同，差别只有三处： CMAKE_SYSTEM_NAME Linux（有 OS）、不需要 TRY_COMPILE_TARGET_TYPE（能正常链接）、 多一个可选的 CMAKE_SYSROOT（目标系统的 / 在本机的镜像，2.5 讲）。

2.4

跑一次：工程描述一个字不改

← CH2 toolchain file · 2.3 · 下一节：2.5 交叉编译的找库边界

第 1 章的 demo/ 原样拿来（本章 demo/ 就是同款三文件工程）， 只多传一个 -D 参数：

cmake -B build-m3 -DCMAKE_TOOLCHAIN_FILE=arm-none-eabi.cmake
cmake --build build-m3

配置阶段输出（关键行）：

-- The C compiler identification is GNU 13.2.1
-- Detecting C compiler ABI info - done
-- Check for working C compiler: .../arm-none-eabi-gcc - skipped
-- Configuring done
-- Generating done

逐行读：编译器从本机 gcc 换成了交叉前缀的 arm-none-eabi-gcc ✓； Check for working ... - skipped 正是 TRY_COMPILE_TARGET_TYPE 在起作用 （跳过链接自检）✓。构建完验证产出物真的是 ARM 机器码：

$ file build-m3/ma_feed
build-m3/ma_feed: ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV), ...

file 说 ARM ✓。回本机目录 cmake -B build 再配一次，同一份 CMakeLists 产出的又是本机 x86_64/arm64 二进制——工程描述与工具链彻底解耦，这就是这章的全部目的。

CMakeLists 里写 set(CMAKE_C_COMPILER arm-none-eabi-gcc) 为什么没用？ 老式教程常这么教。问题在时机：project() 命令在 CMakeLists 第 2 行 就完成了编译器探测，第 10 行再 set 已经晚了。toolchain file 由 -DCMAKE_TOOLCHAIN_FILE 在第一次 project() 之前注入，时机才对。 同理，set(CMAKE_SYSTEM_NAME ...) 写在 CMakeLists 里也来不及触发交叉模式。

2.5

交叉编译的找库边界：find_* 三组开关

← CH2 toolchain file · 2.4 · 下一节：2.6 本章验收清单

工程一大就要 find_library / find_package 找第三方库。交叉编译时的经典事故： 链接器报一堆 undefined reference，或更阴的——链上了本机 x86 的库， 板子上一跑就 Exec format error。原因：find_* 默认搜本机路径。

CMake 用三组开关把搜索范围钉死（toolchain file 的第 ④ 段，见 2.3）：

开关 管什么 交叉时的正确值 为什么
..._MODE_PROGRAM find_program（protoc 等在本机跑的工具） NEVER 代码生成器要在编译机上执行，必须找本机版
..._MODE_LIBRARY find_library ONLY 库要链进目标二进制，只能用 sysroot 里的 ARM 版
..._MODE_INCLUDE find_path（头文件） ONLY 同理，头文件必须来自目标系统

配套概念 CMAKE_SYSROOT：把目标板根文件系统的 / 复制（或挂载）到本机一个目录， 里面 usr/include、lib 俱全，find_* 就进这个"镜像根"里找。 Buildroot/Yocto（08 模块）构建时会自动产出 sysroot，届时把路径填进 toolchain file 即可。

2.8

本机实测复跑：clang 路线（不装 arm-none-eabi-gcc）

← CH2 toolchain file

本节讲什么

2.4 的演示用的是 arm-none-eabi-gcc——这台 Mac 上并没有装它（labs/00 笔记 验证过不需要装）。本节做两件事：①指出 2.4 演示在本机的真实可复现版本； ②用 clang 路线把 Cortex-M 裸机交叉构建完整跑通，产物与 STM32-/labs/00 的 Makefile 版逐字节核对。实测环境：macOS 26.6.2 + cdev 环境（clang 23.1.0 / CMake 4.4.3），无板依赖。

要点

2.4 演示在本机的现实

arm-none-eabi-gcc 属于 GNU 交叉工具链，每个目标三元组一套独立发行版。 而 LLVM 路线不需要它：宿主的 clang 自带全部 ARM 后端，"交叉"只是一个 --target 参数——这正是 labs/00 笔记的核心结论，本章 demo 里的 cortex-m-clang/ 子目录就是它的 CMake 版。

clang 路线 toolchain file（demo/cortex-m-clang/arm-clang-cortex-m3.cmake）

与 2.3 的 GNU 版四处不同，每处都有原因：

set(CMAKE_SYSTEM_NAME Generic)
set(CMAKE_SYSTEM_PROCESSOR arm)
set(CMAKE_C_COMPILER clang)                       # ③ 编译器还是宿主那个 clang
set(CMAKE_C_COMPILER_TARGET armv7m-none-eabi)     # ④ "交叉"在这里发生
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY) # ⑤ 与 GNU 版相同：救命行
  • ③④ 合起来读：GNU 版"编译器名字带三元组"，clang 版"编译器名字不变、 三元组单独给"。CMAKE_C_COMPILER_TARGET 设好后，CMake 自动往每条 编译/链接命令最前面注入 --target=armv7m-none-eabi（实测： cmake --build build --verbose 可见，且它不在 flags.make 的 C_FLAGS 里—— 在 build.make 的编译规则里）
  • ⑤ 与 GNU 版同理：裸机链不出宿主可执行文件，探测改静态库

工程侧与 2.4 的两处差异

事项 GNU 路线（2.3） clang 路线（本节）
链接发起者 arm-none-eabi-gcc 驱动 + 系统 ld clang 驱动 + -fuse-ld=lld（macOS 系统 ld 是 Mach-O 的，吃不了 ELF 脚本）
链接选项写法 target_link_options(-T ...)（gcc 驱动认识） 必须 -Wl, 前缀（-Wl,-T,... -Wl,--entry=...），clang 只透传认识的选项
产物后缀 可执行文件默认无后缀的问题同样存在 set_target_properties(... SUFFIX ".elf") 显式补回
-mcpu 归属 CMAKE_C_FLAGS_INIT（工具链信息不泄进工程） 同理可用 _INIT；本 demo 为教学对比放进了 target_compile_options

$ cd demo/cortex-m-clang && cmake -B build -DCMAKE_BUILD_TYPE=MinSizeRel && cmake --build build
[100%] Linking C executable blink.elf

产物与 Makefile 版完全一致（296 字节）——再次验证：构建系统的价值在 组织与防错，不在产物。

2.9

ABI 与交叉编译的边界：为什么"一份二进制到处跑"是假的

← CH2 toolchain file · 上一节：2.7 与后续衔接 · 2.8 本机实测复跑

本节讲什么

2.1–2.8 讲的是"怎么交叉编译"，本节讲边界："交叉编译不能为你做什么"。

把四个常被混为一谈的概念钉开：

概念 属于哪一层 谁定
ISA（指令集架构） CPU 硬件层 ARM / x86 / RISC-V 的芯片设计者
ABI（应用二进制接口） 二进制层：机器码怎么排、怎么互相调用 操作系统 + 编译器共同约定
API（源码接口） 源码层：函数原型、头文件 库作者
源码可移植性 源码层 语言标准 + 你写代码的纪律

一句话：不是"同一段二进制被不同 CPU 解读出不同结果"——不同 CPU 根本读不懂对方的机器码。ABI 是"同款 CPU 上，不同系统/编译器之间还得额外对齐的那套规矩"。

要点

1. 先分清：ISA 问题和 ABI 问题不是一回事

源码可移植   ← C 语言标准管这一层（同一份 .c 给谁编都能过）
──────────────────────────────────────────────
ABI 层       ← 二进制怎么排：类型大小、对齐、调用约定、目标文件格式
──────────────────────────────────────────────
ISA 层       ← CPU 指令集：x86 指令 ARM 不认识，反之亦然
  • ISA 不同：连"能不能执行"这关都过不去，跟 ABI 无关。
  • ISA 相同、ABI 不同：指令 CPU 都认识，但排列规则对不上 → 加载后行为错乱。

2. ABI 到底约定了什么

类别 具体内容
数据模型 int / long / 指针各占几字节（LP32 / ILP32 / LP64 / LLP64），结构体 padding 与对齐
调用约定 参数进哪些寄存器、超了怎么压栈、谁清栈、返回值放哪
浮点约定 硬浮点（进 VFP 寄存器）还是软浮点（当整数传）
目标文件格式 ELF / Mach-O / PE，符号修饰规则（Mach-O 给符号加前导 _）
OS 接口 系统调用编号与调用方式、动态链接器路径

实测（本机 clang 23.1.0，同一份 .c 换成不同 target）：

实验 armv7-linux-gnueabihf（ILP32） aarch64/x86_64-linux（LP64）
_Static_assert(sizeof(long) == 8) ❌ 断言失败 ✅ 通过
_Static_assert(sizeof(long) == 4) ✅ 通过 ❌ 失败

同一份源码，换个 target，long 就从 4 字节变 8 字节——这就是 ABI 在源码之下动手脚的样子。

3. 调用约定：同一句 f(1,2,3,4...)，寄存器完全不同

int f(int,int,int,int,int,int,int,int) 的调用点，-S 出的汇编（clang -O0）：

target 前四个参数落在
armv7-linux-gnueabihf r0, r1, r2, r3
aarch64-linux-gnu w0, w1, w2, w3（即 x0–x7）
x86_64-linux-gnu edi, esi, edx, ecx（SysV 约定）

4. 同架构同系统也可能不兼容：硬浮点 vs 软浮点（"hf" 的来历）

float g(float) 传参，同一个 armv7、同一个 Linux，只改 ABI 后缀：

gnueabihf（硬浮点）:  vmov.f32  s0, #1.000000e+00      ; 直接进 VFP 寄存器 s0
gnueabi  （软浮点）:  mov  r0, #1065353216             ; 当整数塞进 r0
                      vmov s0, r0                      ; 再搬到 VFP

所以 arm-linux-gnueabihf 最后那个 hf = hard float：指令集一样、系统一样，ABI 不一样，二进制照样不能混用。这也是交叉编译器必须选完整 triple 的原因：架构-厂商-系统-ABI。

5. 同架构不同 OS：文件格式与符号名也变了

同一个 aarch64，编给 Linux 和 macOS：

linux .o  ：ELF， 未定义符号  f
macOS .o  ：Mach-O，未定义符号 _f      ← 多了前导下划线

6. 交叉编译到底做了什么

同一份 main.c
   ├─ arm-linux-gnueabihf-gcc  →  ARM 指令 + GNU/Linux hard-float ABI + 目标系统库  →  ARM 板子上跑
   ├─ aarch64-linux-gnu-gcc    →  aarch64 指令 + LP64 ABI                          →  Pi 5 / 服务器上跑
   └─ 本机 gcc                 →  x86_64 指令 + 本机 ABI                            →  本机跑

编译器做两件事：生成目标 CPU 的指令 + 遵守目标平台的 ABI 与系统库约定（靠 sysroot 里的头文件和库）。

❌ 交叉编译 ≠ 一份二进制到处跑 ✅ 交叉编译 = 一份源码，编译多次，产出多个互不通用的二进制

7. 两种"跑不起来"的现象（要会区分）

情形 现象 实测
ISA 不同（把 ARM ELF 拷到 x86） 内核/加载器直接拒：exec format error（exit 126） ✅ 本机实测：执行 STM32 的 blink.elf（ELF 32-bit ARM）→ exec format error
ISA 同、ABI 不同（如 Android ABI vs Linux GNU ABI、soft vs hard float） 指令 CPU 认识，行为错乱：结构体错位、参数错位 → 段错误 / 崩溃；也可能在加载阶段就被动态链接器拒绝（ELF OS ABI 不匹配、找不到解释器），不一定能"加载成功再崩" —

区分口诀：报"非法指令 / Exec format error" = ISA 层；能加载却莫名其妙崩 = ABI 层。

8. 谁才有"一份二进制到处跑"

方案 机制 代价
Java 同一份 .class 字节码，各平台 JVM 解释/JIT JVM 本身是各平台一份二进制
.NET / IL、WebAssembly 同理，中间码 + 运行时 需要运行时
Go 仍要按 GOOS/GOARCH 分别编译；但默认静态链接，产物在同 OS + 同架构的机器间可直接拷贝 不是跨 OS / 跨架构可移植
C/C++ ❌ 没有中间码，产物就是目标机的机器码 靠源码可移植 + 重新编译

所以：

  • 源码可移植（C 的目标）：一套源码，各平台各自编，各自跑。
  • 二进制可移植（C/C++ 做不到）：一个 exe 拷到别的 CPU/OS 直接跑。

HFT / 嵌入式关联

  • 交易程序常要同时出 x86_64 服务器版和 aarch64（AWS Graviton / 边缘网关）版：同一套源码，两条 CI 流水线，两个二进制，任何一个混用都是 ABI 事故。
  • 嵌入式最典型的 ABI 事故：给 -mfloat-abi=hard 编译的库链进 soft-float 工程，编译链接全绿，上板浮点计算全是垃圾。
  • 内核模块更要命：模块必须和内核用同一套编译配置，vermagic 不匹配直接拒绝加载——这本质也是 ABI 校验。
  • 本机也能演示"跑不了"：把 STM32 那个 ARM ELF 拷到 Mac 上执行，实测 exec format error。要跑它得靠 qemu-arm 这类二进制翻译器——那不是 CPU 读懂了 ARM 指令，是软件在模拟（本机未装 qemu）。

代码自测

Q1（Quiz）：在 x86 PC 上用 arm-linux-gnueabihf-gcc 编译出的 ARM 程序，能直接在 x86 PC 上跑吗？为什么？

不能。 两层原因，任一层都足以否决： 1. ISA 不同：x86 CPU 看不懂 ARM 指令，ARM 指令在 x86 上不是"跑得慢"而是完全无法解码。 2. ABI/OS 不同：产物是 Linux ELF，依赖 Linux 的动态链接器和系统调用约定（在 Mac 上还涉及 Mach-O vs ELF）。 实测现象：执行 STM32 的 ARM ELF → exec format error（exit 126）。 想跑可以：装 qemu-arm 用户态模拟（二进制翻译），或放进 ARM 容器/板子。

Q2：long 在 32 位 ARM Linux 和 64 位 ARM Linux 上分别多大？这属于 ABI 的哪一类约定？

32 位 ARM（ILP32）= 4 字节，aarch64（LP64）= 8 字节（实测 _Static_assert 一边过一边失败）。属于 数据模型约定，是 ABI 的一部分——注意：int 大小不是 ABI 的全部，只是其中一项。

Q3：两个 armv7 Linux 程序，一个用 gnueabihf 编、一个用 gnueabi 编，能链接到一起吗？

不能（或链接上后运行出错）。硬浮点把 float 参数直接放 VFP 的 s0，软浮点当整数塞 r0——同一条调用两边理解不同，浮点参数全是垃圾。这就是 triple 里必须写全 hf 的原因。

Q4："交叉编译实现了 write once, run anywhere" 这句话对吗？

不对。交叉编译实现的是 write once, compile everywhere：源码一份，每个平台各编一次，产出各自独立的二进制。真正的"一份二进制到处跑"要靠中间码 + 运行时（JVM / .NET / WASM），C/C++ 原生做不到。

章节自测

Q1：toolchain file 和 CMakeLists.txt 的分工是什么？为什么交叉信息不能写进 CMakeLists？

CMakeLists 是工程描述（有哪些 target、源码、依赖），平台无关，所有构建环境共用一份； toolchain file 是工具链描述（编译器是谁、目标系统是谁、去哪找库），随编译环境走， 同一块板子的所有工程共用一份。不能写进 CMakeLists 的两个理由：①时机——project() 在 CMakeLists 开头就完成编译器探测，之后再 set(CMAKE_C_COMPILER) 已无效， 而 toolchain file 在首次 project() 之前注入；②解耦——写进 CMakeLists 意味着换一块板子 要改所有工程文件，交叉信息"漏"进了本该平台无关的工程描述。

Q2：裸机 toolchain file 里 set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY) 是干什么的？

CMake 配置时会做一次编译器自检：默认试链接一个可执行文件来验证工具链可用。 裸机没有启动文件（startup code）和链接脚本，链接必然失败，自检误报 "C compiler cannot build executables"。把自检目标改成 STATIC_LIBRARY 后， CMake 只验证"能否编译出目标文件"，跳过链接——自检通过，且符合裸机实际： 能不能链出固件是链接脚本齐备之后的事，不该由编译器自检背锅。

Q3：CMAKE_FIND_ROOT_PATH_MODE_PROGRAM 为什么是 NEVER 而 LIBRARY 是 ONLY？

两类东西的运行位置不同。find_program 找的是在编译机上执行的工具 （如 protoc、python——生成代码用的），必须在本机路径找，所以 NEVER 进 sysroot； find_library / find_path 找的是链进目标二进制的库和头文件， 必须是目标架构的版本，所以 ONLY 在 sysroot 里找——放它去本机找， 就会链上 x86 的 .so，板子上 Exec format error。 口诀：跑的工具找本机，链的库找目标。

Q4：CMAKE_SYSROOT 是什么？没有它会怎样？

目标系统根目录在本机的镜像（含 usr/include、lib 等），交叉编译时编译器和 find_* 都进这个"影子根"找头文件和库。没有它：纯用户态小程序靠编译器自带的 头文件（stddef.h 等）往往也能编过，但一旦用到目标系统的库（如 libgpiod、 板子特有的驱动头）就找不到。Buildroot/Yocto 构建 rootfs 时会产出配套 sysroot， 届时把路径写进 toolchain file 的 CMAKE_SYSROOT 即可。

Q5：同一份代码要同时维护"本机调试版"和"ARM 发布版"，目录怎么组织？

两个 build 目录并存：cmake -B build（本机）+ cmake -B build-arm -DCMAKE_TOOLCHAIN_FILE=...（ARM）。CMake 的 out-of-source 设计就是为这个场景： 每个 build 目录有独立的 CMakeCache.txt，记录各自的编译器和选项，互不污染； 源码目录始终只有一份。这也是 build/ 必须进 .gitignore 的原因之一—— 本机缓存被带到另一台机器上会出"编译器路径不存在"的诡异错误。
