1.3

b 附注：警告开关 —— `-Wall` 和 `-Werror` 到底在干什么

← CH1 最小工程 · 上一节：1.3 三级台阶 · 下一节：1.4 两条命令拆解

本节讲什么

1.3 的编译命令里出现了 -Wall，CMakeLists 里出现了 -Wall -Wextra，很多开源工程的 README 还会让你加 -Werror。这三个 -W 开头的开关是新手最容易"照抄但不理解"的东西。 这一节用 demo/warn_demo.c（一个故意养了三个经典小毛病的文件）逐级实测， 看每个开关到底多管了什么、不管什么。

先分清两个词：

编译器反应 产物
error（错误） 拒绝编译，直接停 没有 .o
warning（警告） "我觉得这地方可疑，但语法合法，我继续编" 照样产出 .o

警告的麻烦就在第二行：它不拦你。代码带着"变量没初始化就相乘"这种 bug 一样能编出 可执行文件，然后等到某个运行时刻给你一个垃圾值。警告开关做的事，就是把编译器 "可疑但不违法"的检查项打开——默认它为了兼容历史代码，绝大多数检查是关着的。

要点

1. -Wall：开"常用警告"，名字有坑

-Wall 字面像 "all warnings"，实际并不是全部——它是编译器作者筛选过的 "高性价比警告集"：误报少、几乎总能查出真问题。里面包括：

  • 用了未初始化的变量
  • 该返回值的函数分支没写 return
  • 类型转换会悄悄丢信息（如 double 隐式截断成 int）
  • 永远为真/假的条件、无法到达的代码
  • 声明了却没用的变量（gcc 视角；见下文实测差异）

2. -Wextra：在 -Wall 之上再拧一圈

多出来的都是"有时正常写法也会踩到"的检查，最典型的是 -Wsign-compare：有符号数和无符号数比较。这类 bug 在嵌入式里极其致命：

unsigned len = 1;
int n = -1;
if (len > n)   /* 你以为 false，实际 true！n 被转成巨大的无符号数 */

配套实验见 warn_demo.c，一编即现形。

3. -Werror：把警告升级成错误

加了它，上一节表里的"警告"一栏整体变性质：

无 -Werror 有 -Werror
可疑代码 打印 warning，继续编 变成 error，编译中断
产物 有 .o 没有 .o
退出码 0 非 0

它的价值不在"多查出 bug"，而在强制你当场处理：没有它，警告会在满屏输出里 一闪而过，没人看，日积月累几百条"背景噪音"，真正要命的那条就淹没了。所以 -Werror 的实际含义是纪律：警告数量必须为零，新警告一出现构建就红。

4. 实测：四个等级逐级对比

对 demo/warn_demo.c（毛病：①if (qty = 5) 把赋值当比较； ②price 未初始化就参与风控乘法；③unsigned 与 int 比较）逐级编译 （clang 23.1.0，cdev 环境实测）：

$ cc -c warn_demo.c                      # 默认：几乎静默
warn_demo.c:23:13: warning: ... [-Wparentheses]        # ① 只有 1 条（clang 默认就开）

$ cc -Wall -c warn_demo.c                # -Wall：+1
warn_demo.c:23: warning: ... [-Wparentheses]           # ①
warn_demo.c:30: warning: variable 'price' is uninitialized when used here
                                                       # ② 查出未初始化！

$ cc -Wall -Wextra -c warn_demo.c        # -Wextra：再 +1
warn_demo.c:23: warning: ... [-Wparentheses]           # ①
warn_demo.c:27: warning: comparison of integers of different signs
                                          [-Wsign-compare]   # ③
warn_demo.c:30: warning: variable 'price' is uninitialized ...  # ②

$ cc -Wall -Wextra -Werror -c warn_demo.c  # -Werror：全部变 error
warn_demo.c:23:13: error: ... [-Werror,-Wparentheses]
warn_demo.c:27:17: error: ... [-Werror,-Wsign-compare]
warn_demo.c:30:13: error: ... [-Werror,-Wuninitialized]
2 errors generated        # 退出码 1，没有产出 .o，构建失败

注意 -Werror 的输出格式：[-Werror,-Wparentheses]——警告名还在， 只是性质从 warning 换成了 error。

gcc 与 clang 的差异（本套笔记 gcc 视角书写、clang 实测，两者在 CMake 场景逐行等价， 但警告集不是逐条相等）： - gcc 默认比 clang 更安静——上面的毛病①④ gcc 默认一条都不报； - gcc 的 -Wall 不含 -Wuninitialized（它需要优化器的数据流分析， 实际要 -O1 以上才完整工作）； - 结论：别赌默认值，显式写 -Wall -Wextra，两个编译器下都是最稳的日常配置。

5. 在 CMake 里怎么写

target_compile_options(demo PRIVATE
    -Wall
    -Wextra
    $<$<C_COMPILER_ID:Clang,AppleClang,GNU>:-Werror>)   # 可选：本地也当门禁

日常写法更简单：-Wall -Wextra 常开，-Werror 放在 CI/发布构建里开 （本机调试期偶尔想"先编过再说"，两者分开更灵活）。工程级配置怎么随 CMAKE_BUILD_TYPE / preset 固化，第 5 章 5.6 讲。

HFT/嵌入式关联

  • warn_demo.c 里那个未初始化的 price，位置就在风控金额计算里—— 这不是巧合：HFT 最怕的恰是"能跑但值不对"的静默 bug，一笔垃圾价的订单发出去 就是真金白银。警告开关注化成门禁（-Werror + CI）后，这类代码根本进不了主干。
  • 嵌入式同理且更狠：没有 stderr 给你看运行期崩溃，unsigned/int 比较错一次， 缓冲区边界就错了，直接越界写。STM32 工程把 -Wall -Wextra -Werror 写进 CMakeLists 是标准动作（Zephyr 内部就是这么配的，见第 4 章）。

代码自测

Q1：-Wall 是"所有警告"吗？

不是。它是编译器筛选后的常用集。真正的全家桶是 clang 的 -Weverything（官方 自己都不建议日常用，误报多），日常标配是 -Wall -Wextra。

Q2：既然 warning 不拦编译，为什么还要开？直接忽略不行吗？

警告指向的多数是"语法合法但几乎必定是笔误"的代码：=当 ==、变量没初始化、 符号比较。这些 bug 编译期修是 1 分钟，运行期查可能是几天——警告就是编译器 免费送你的 code review。

Q3：-Werror 会不会太严格，导致正常代码编不过？

偶尔会（某些三方头文件自带警告）。所以工程实践是分层：本地 -Wall -Wextra， CI/发布加 -Werror；对确属三方代码的警告用 -Wno-xxx 或把三方目录隔离成 独立 target 单独放宽，而不是全局关警告。

Q4：怎么知道某个警告属于哪个开关、想单独关掉它？

每条警告尾部方括号里就是它的名字（如 [-Wsign-compare]）。想单独关就是 -Wno-sign-compare；想单独开（不在 -Wall 里）直接写 -Wsign-compare。 警告名即开关名，一一对应。

-Wall -Wextra 挂在 target_compile_options 上只是起点：第 5 章讲优化等级 （-O2/-O3，注意 gcc 的未初始化检查要靠 -O 才完整）、Sanitizers（比警告更 进一步的运行期检查）和 5.6 CMakePresets 怎么把这些固化成 cmake --preset dev 一条命令。

1.1

问题的起点：编译命令什么时候失控

← CH1 最小工程 · 下一节：1.2 构建系统只管两件事

本节讲什么

从一个你已经会的东西出发：手敲 gcc。亲眼看它什么时候开始管不过来—— 这就是后面所有构建系统存在的理由。

要点

一个 main.c，编译是一条命令：

gcc main.c -o demo

程序长大：拆出 math_utils.c，加了 -Wall -std=c11，还得管头文件依赖：

gcc -Wall -Wextra -std=c11 main.c math_utils.c -o demo

实测（本仓库 demo/ 工程的真实输出）：

$ gcc -Wall -Wextra -std=c11 main.c math_utils.c -o demo_manual && ./demo_manual
n=5  MA=100.4800  reported=100.4800

还能忍。但真正的失控在增量性和环境两个维度上：

失控点 具体表现
改一个文件要重编全量 上面那条命令永远编译所有源文件，工程 100 个文件时每次改一行都全量重编
头文件依赖没人管 math_utils.h 改了，你忘了重编 main.c，链接出来的还是旧逻辑——不报错
换平台命令就作废 Linux 加 -ldl -lpthread，macOS 不要；Windows 是另一套编译器、另一套 flag
找库是玄学 库装在哪？头文件在哪？每个装库的方式都不一样

下一节把"构建"剥到第一性原理：不管什么工具，管理的都只有两种信息。

1.2

第一性原理：构建系统只管两件事

← CH1 最小工程 · 1.1 · 下一节：1.3 三级台阶

本节讲什么

剥掉所有工具的外壳，"构建"这件事只包含两种信息。理解了这一节， Makefile / CMake / Ninja / Bazel 对你来说只是"同一件事的不同写法"。

要点

  1. 依赖关系 —— 谁依赖谁：demo ← main.c.o + math_utils.c.o； main.c.o ← main.c + math_utils.h
  2. 动作命令 —— 每个依赖节点上执行什么：gcc -c main.c -o main.c.o

Makefile 就是把这两件事写成规则。你仓库里 147 个 demo Makefile 都是这么干的。 那为什么还要 CMake？因为 Makefile 把这两件事写死在了"本机"视角：

  • 依赖和命令你自己写 → 写错依赖就出 1.1 说的"不报错的旧逻辑"
  • 它生成的构建过程绑死当前平台 → 换平台重写

CMake 的位置在 Makefile 的上一层：

你写的          CMake 替你生成的         真正干活的
CMakeLists.txt → Makefile / Ninja / VS 工程 → gcc / clang / MSVC
（描述工程）      （本机构建系统，自动生成）    （编译命令，自动拼装）

你只写一份平台无关的"工程描述"；CMake 探测本机环境（编译器在哪、库在哪、 什么平台），替你生成对应的 Makefile。换平台 = 换个目录重新生成一遍，你一个字不用改。

类比：Makefile 是"菜谱"（你写清每一步）；CMakeLists 是"点菜"（你说要什么菜， 后厨——本机工具链——怎么配合它替你安排）。

1.3

三级台阶：同一个工程的三种构建法

← CH1 最小工程 · 1.2 · 下一节：1.4 两条命令拆解

本节讲什么

demo/ 是同一个三文件工程（main.c + math_utils.c + math_utils.h， 算一个移动平均再夹到风控区间——刻意带点 HFT 味）。这一节把它用三种方式各构建一遍。

要点

台阶一：手动编译（见 1.1，一条长命令，全量、无依赖管理）

台阶二：Makefile——你要手写依赖规则：

demo: main.o math_utils.o
    gcc main.o math_utils.o -o demo
main.o: main.c math_utils.h      # ← 依赖要自己写对
    gcc -Wall -std=c11 -c main.c
math_utils.o: math_utils.c math_utils.h
    gcc -Wall -std=c11 -c math_utils.c

增量编译解决了，但规则是手写的、平台绑定的。STM32-/labs/00 的 Makefile 你见过它的完全体：--target=armv7m-none-eabi 一大串交叉编译 flag 全写死在里面。

台阶三：CMake——你只描述"目标是什么"：

cmake_minimum_required(VERSION 3.16)   # ① 语法基准线
project(demo C)                        # ② 工程名 + 语言
add_executable(demo main.c math_utils.c)  # ③ 一切皆 target
target_compile_options(demo PRIVATE -Wall -Wextra)  # 属性挂在 target 上
set_target_properties(demo PROPERTIES C_STANDARD 11 C_STANDARD_REQUIRED ON)

逐行说：

  • cmake_minimum_required：声明"我的语法按 3.16 为准"——没有它 CMake 会告警， 因为老版本和新版本语法有差异
  • project(demo C)：工程名 + 语言。CMake 在这一步触发编译器探测
  • add_executable：声明"我要一个叫 demo 的可执行文件，源文件是这些"—— 这就是现代 CMake 的核心动作：创建 target
  • target_compile_options：把编译选项挂在这个 target 上（PRIVATE=只它自己用）
  • -Wall -Wextra 这些警告开关具体在干什么、-Werror 为什么被当门禁—— 详见附注 1.3b 警告开关
  • set_target_properties：声明 C 标准，REQUIRED 表示标准不支持就直接报错而不是静默降级

对比一下心智负担的转移：

Makefile CMakeLists
依赖关系 自己写（写错不报错） 编译器扫描自动生成（.o.d 文件，见 1.5）
编译命令 自己拼 CMake 按探测到的编译器自动拼
换平台 重写 重新 -B 生成一遍
找库 自己写 -I/-L/-l find_package / target_link_libraries

1.4

两条命令，每一步发生了什么

← CH1 最小工程 · 1.3 · 下一节：1.5 拆开 build/

本节讲什么

CMake 的日常就是两条命令。这一节把它们各自阶段的真实输出逐行读给你—— 读输出就是读 CMake 在干什么。

要点

cmake -B build        # 配置阶段
cmake --build build   # 构建阶段

配置阶段（cmake -B build）真实输出（macOS 26.6.2 + cdev clang 23.1.0 / CMake 4.4.3）：

-- Detecting C compiler ABI info
-- Detecting C compiler ABI info - done
-- Check for working C compiler: /Users/a0000/micromamba/envs/cdev/bin/clang - skipped
-- Configuring done (1.1s)
-- Generating done (0.0s)
-- Build files have been written to: .../demo/build

逐行读：探测编译器（找到 cdev 环境的 clang——这一行每台机器都不一样， 这正是"探测本机环境"的实证）→ 执行你的 CMakeLists（add_executable 等只是登记 target，还没编译任何东西）→ 生成本机构建系统（macOS 上默认 生成 Makefile），全部写进 build/。

构建阶段（cmake --build build）真实输出：

[ 33%] Building C object CMakeFiles/demo.dir/main.c.o
[ 66%] Building C object CMakeFiles/demo.dir/math_utils.c.o
[100%] Linking C executable demo
[100%] Built target demo

注意 cmake --build 是个包装：它调用的是 build/ 里刚生成的构建系统 （这里是 make）。好处：不管底下生成的是 Makefile 还是 Ninja 还是 VS 工程， 这条命令永远不变——这就是"跨平台"的落点。

配置阶段到底往 build/ 里写了什么？下一节把目录拆开逐个认。

1.5

拆开 build/：CMake 生成的东西一览

← CH1 最小工程 · 1.4 · 下一节：1.6 现代 CMake 三原则

本节讲什么

配置 + 构建跑完后，build/ 里多了一堆东西。逐个认识它们—— 特别是 main.c.o.d，它是 1.1 里 "头文件依赖没人管"的最终答案。

要点

build/
├── CMakeCache.txt          ← 探测结果缓存（编译器路径、平台、选项），配置阶段写入
├── Makefile                ← 生成的本机构建系统（构建阶段的真正入口）
├── cmake_install.cmake     ← 安装规则（install() 命令的产物）
└── CMakeFiles/demo.dir/
    ├── flags.make          ← 每个文件的编译 flag（你的 -Wall 在这，可核对）
    ├── link.txt            ← 完整链接命令行（链接出错时看这个）
    ├── main.c.o            ← 目标文件
    ├── main.c.o.d          ← ★ 依赖清单：main.c 依赖哪些头文件，编译器自动生成
    └── math_utils.c.o(.d)

main.c.o.d 就是 1.2 说的"依赖没人管"的答案：CMake 让编译器（-MMD） 在编译时顺手生成"我到底 include 了谁"的清单，下次构建时喂给 make—— math_utils.h 一改，main.c.o 自动重编。你在 Makefile 里手写的那行 main.o: main.c math_utils.h，CMake 替你生成且永远不会写错。

两个实测核对（学构建系统的好习惯：怀疑生成物，就去打开它）：

grep '\-Wall' build/CMakeFiles/demo.dir/flags.make   # 你的 flag 真的生效了
cat build/CMakeFiles/demo.dir/link.txt              # 看完整的链接命令

为什么源码树是干净的？ 这叫 out-of-source build：所有生成物都在 build/， 删掉 build/ = 完全重来。源码目录里只有你写的东西 + CMakeLists.txt。 把 build/ 写进 .gitignore（本仓库已有），这是 CMake 工程的标准姿势。

与后续衔接

1.6

现代 CMake 三原则（从第一个工程就养成）

← CH1 最小工程 · 1.5

本节讲什么

语法对了不等于写对了。三条原则区分"现代 CMake"和"十年前的老式 CMake"—— 从第一个工程就按这个写，以后读别人的工程才有甄别力。

要点

  1. 一切皆 target。add_executable / add_library 创建 target， 之后的编译选项、include 路径、链接库全部挂在 target 上。
  2. 属性用 target_* 命令挂。target_compile_options / target_include_directories / target_link_libraries，并写明传播范围：PRIVATE（只我用）/ PUBLIC（我和依赖我的都用）/ INTERFACE（只有依赖我的用）。
  3. 禁止全局操作。include_directories、add_compile_options、 手写 ${CMAKE_SOURCE_DIR}/include 都是老式写法——单文件工程看不出坏处， 多目录工程里全局 include 路径会互相污染，最终谁也说不清哪个 target 依赖哪个头。

为什么从第 1 章就讲这个：老式写法的教程会把你的心智模型带歪， 先记住"对的样子"，见到不对的才认得出来。（模块 README 的「甄别原则」就是这三条的判据版。）

章节自测

Q1：cmake 和 make 分别是什么？一条命令各在哪个阶段起作用？

CMake 是构建系统生成器：读 CMakeLists.txt（工程描述），探测本机环境， 生成本机构建系统（macOS/Linux 默认 Makefile，也可生成 Ninja/VS 工程）——cmake -B build 这一步。 make 是构建系统：按生成的 Makefile 里的依赖规则和命令真正编译——cmake --build build （= 进 build/ 执行 make）这一步。一句话：cmake 描述工程，make 执行编译。

Q2：改了 math_utils.h 之后重新构建，main.c 会重编吗？谁保证的？

会。保证者是 main.c.o.d（见 1.5）：编译 main.c 时编译器被要求 （CMake 自动加 -MMD）顺手生成"我 include 了哪些头文件"的清单，make 每次构建读它来决定重编谁。 这就是 Makefile 里 main.o: main.c math_utils.h 那行手写依赖的自动化版本——而且永远不会写漏。

Q3：为什么 build 目录要 out-of-source（在源码树外面）？

三个理由：①源码树干净，.gitignore 一个 build/ 全解决；②同源码可配多个不同 build 目录（debug/release/交叉编译并存）；③删除 build/ 即完全重来，配置坏了不用找脏文件。 CMake 会把缓存（CMakeCache.txt）锁在配置时的 build 目录里，混进源码树反而会出事。

Q4：PRIVATE / PUBLIC / INTERFACE 的区别？

属性的传播范围：PRIVATE 只作用于本 target 的编译； PUBLIC 本 target 编译要用 + 依赖我的 target 也要用（典型：实现文件和头文件都 include 的库）；INTERFACE 本 target 不用、只有依赖我的用（典型：header-only 库）。 类比 05 书 CH4 的接口语义：这是 CMake 版的"谁需要看见这个声明"。

Q5：你的工程 100 个 .c 文件，add_executable 一行要写 100 个文件名吗？

不应该写死。现代做法：按目录拆 add_subdirectory（每个子目录自己的 CMakeLists 建 target，第 3 章讲）。file(GLOB) 官方不推荐——新增/删除文件不会触发重新配置。 "显式列文件"在这里不是笨，是让构建系统知道边界。
