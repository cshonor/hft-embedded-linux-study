# 驱动为什么在内核（built-in / .ko）

> 相关：[DT↔驱动](./8.1-dts-driver-relationship.md) · [三层图](../../../13-embedded-projects/project-01-pi-driver-course/01-userspace-kernel-hardware.md)

## 一、根本原因：硬件权限只在内核

Linux 分 **内核态** / **用户态**。寄存器、IRQ、DMA、内存控制器等，**用户态不能直接摸**。

| 谁 | 权限 |
|----|------|
| 内核 | 完整硬件访问；能注册并跑中断处理 |
| 用户进程 | 经系统调用间接请求；直访 MMIO 通常 → 缺页/被杀 |

因此「读写寄存器、ISR、真正控外设」的主体必须是 **内核里的驱动代码**。

### 两种打包形式（本质都是内核代码）

| 形式 | `.config` | 形态 | 运行期 |
|------|-----------|------|--------|
| **built-in** | `=y` | 链进 `vmlinux` | 开机即在，一般不能 `rmmod` |
| **可加载模块** | `=m` | 独立 `.ko` | `insmod`/`modprobe` 加载，`rmmod` 卸载 |

「内核模块」常特指 `.ko`；口语里「驱动是内核模块」= **跑在内核空间**（含 built-in）。

## 二、驱动 · 内核 · 设备树协作

```
U-Boot 交 DTB
  → 内核解析节点，compatible 匹配驱动
  → 调 probe（内核态）
  → of_* 读地址/中断/时钟
  → 驱动操作硬件、注册 IRQ、创建 /dev/xxx
  → 用户态 APP：open/read/write… 系统调用 → 再进驱动
```

**设备树不是驱动**：只给内核驱动喂静态参数。  
**APP 不直连硬件**：只跟 `/dev`（或 net/socket 等）说话。

### 例：按键

- `gpio_keys`（`.ko` 或 built-in）在内核跑  
- DTS 只描述 GPIO 等  
- APP `read` → 陷入内核 → 驱动读电平 → 结果回用户态

## 三、不在「内核 .c 驱动」里的两类东西（易混）

| 类型 | 澄清 |
|------|------|
| **用户态「驱动」**（少见） | 如经 `/dev/i2c-N`、`spidev` 在用户态协议；**总线控制器驱动仍在内核** |
| **固件 blob**（GPU/Wi‑Fi 等） | 文件在 rootfs；由**内核驱动**加载进芯片 — 固件 ≠ Linux 驱动 |

核心硬件控制逻辑仍落在内核侧。

---

## 四、为何不能把驱动主体写进普通 APP

1. **权限 / MMU**：用户态乱碰物理地址 → 崩溃或被杀  
2. **中断**：硬中断由内核接；用户进程接不到「原味」硬件 IRQ 路径  
3. **隔离**：用户崩溃默认杀进程；硬件控制若全在用户态，异常易把外设锁死、拖垮整机  

（专用框架如 UIO/VFIO、DPDK 是**刻意旁路**的另一条课，先把标准内核驱动路径学清。）

## 六、总结

1. 寄存器 / 中断 / 总线底层操作必须在内核 → 驱动主体是内核代码  
2. built-in 与 `.ko` 只是链接方式不同  
3. DT 给驱动提供参数，**本身不是驱动**  
4. 应用只通过系统调用委托内核驱动，不能替代它
