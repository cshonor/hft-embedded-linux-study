7.2

性能分析

Core Concept: CPU 时间 ≈ IC × CPI × Tclk

状态

笔记

CPU 时间 ≈ IC × CPI × Tclk
因子 主要谁决定 Linux 侧影子
IC ISA + 编译器 算法、编译选项
CPI 微结构（stall/flush）+ Cache/TLB miss 数据布局、分支、屏障
Tclk 工艺 + 关键路径 定频/调频（DVFS）
微结构 CPI Tclk
单周期 =1 大（最慢指令）
多周期 >1 较小
流水线 理想≈1，实际因 hazard >1 按级切短

驱动热路径慢：先分是 算力（CPI/IC） 还是 等内存（AMAT） —— 后者更常见。

7.3

单周期处理器

Core Concept: 一拍走完 F→D→E→M→W；CPI=1，clk 由最慢指令定
Link Target: Ch5 RegFile/ALU · Ch6 指令 · Linux：建立通路直觉 · ↔ CSAPP §4.3 SEQ 档位: 精读（概念；不必 HDL）

状态

  • [x] 已读（口述巩固）
  • [x] 已写要点
  • [x] ADD/LDR/B 对照 + 驱动侧一句话

笔记

一条指令在 一个时钟周期 内做完全部事。
用途：把 Ch5 零件 + Ch6 指令 第一次串成「能跑指令的机器」；真芯片很少纯单周期。

7.3.1 单周期数据通路

PC → IMem(取指) → 字段
        ↓
   RegFile(读) → ALU / 地址计算 → DMem(LDR/STR) → 写回 RegFile
        ↑                                         ↓
        └────────────── 下一 PC（顺序 / 分支）────┘
步骤 硬件
1 读 PC → 指令存储器
2 字段 → 寄存器堆 读源
3 立即数扩展
4 ALU（运算或有效地址）
5 数据存储器（仅访存指令）
6 写回目的寄存器；更新 PC

同一拍内组合连通 → 最长路径 定最小 Tclk。

7.3.2 控制（组合译码）

根据 Op/Funct 产生：RegWrite、MemRead/Write、ALUSrc、MemtoReg、Branch…
本质是 组合逻辑 控制器（多周期才改成 FSM）。

7.3.3 三类指令怎么走（对照）

指令 关键路径直觉
ADD Reg → ALU → 写回 Reg（不碰 DMem）
LDR Reg → ALU 算地址 → DMem 读 → 写回 Reg（通常 最慢）
B 算目标地址 → 改 PC（可能不写回通用寄存器）

7.3.4 性能

优点 缺点
CPI=1，好懂 Tclk ≥ 最慢指令（常是 LDR）
易对照 CSAPP SEQ 快指令也被拖慢

对嵌入式 Linux

不必实现单周期 CPU；要建立：

  • LDR/STR 比 ADD「更重」（多一级存储）——后文流水线里 load-use 停顿同根
  • 指令字段如何变成 控制信号（读手册「指令执行」时有图）
  • 与 CSAPP SEQ 同构，换皮 ARM

真 SoC → 看 7.5 流水线。

7.4

多周期处理器

Core Concept: 指令拆步；复用 Mem/ALU；非体系结构寄存器暂存；FSM 控制
Link Target: Ch3 FSM · CSAPP 多周期直觉（若有）
档位: 浅读

状态

  • [x] 已读（口述巩固）
  • [x] 已写要点

笔记

把「一拍做完」拆成多个较短时钟周期；不同步骤复用同一套硬件。

7.4.1 多周期数据通路

相对单周期 做法
存储器 指令与数据可共用一块 Mem（不同周期用）
ALU 不同步复用（算、比、加 PC…）
暂存 增加 IR、Data 等非体系结构寄存器锁中间结果

换面积：少复制大块硬件，多几个寄存器 + 更复杂控制。

7.4.2 多周期控制 = FSM

状态例子（口述）：取指 → 译码 → 地址计算 → 访存 → 执行 / 写回…
每个状态输出该步控制信号序列 —— 对应第3章 FSM，不是单周期那张大组合译码表。

7.4.3 性能

点 说明
Tclk 更短（按一步最长路径）
CPI 指令相关：如分支 ~3、加载 ~5（具体以书为准）
总速度 不一定快过单周期：多了寄存器建立/保持等时序开销

价值：理解「复用 vs 复制」、为流水线「级间寄存器」做铺垫。

7.5

流水线处理器

Core Concept: 五级流水；转发 · 停顿 · 冲刷；load-use；屏障直觉
Link Target: 本路线 Ch7 核心 · ↔ CSAPP §4.5 PIPE 档位: 精读

状态

  • [x] 已读（口述巩固）
  • [x] 已写要点
  • [x] 冲突表 + Linux/驱动性能直觉

笔记

重叠执行多条指令 → 提高 吞吐（单位时间完成的指令数）。现代应用核都是流水线（再叠加超标量等，见 7.7）。

7.5.1 五级（经典）

级间插 流水线寄存器：

级 名 干什么
1 F Fetch 取指
2 D Decode 译码、读寄存器
3 E Execute ALU
4 M Memory 访存
5 W Writeback 写回寄存器堆

控制信号随指令 逐级传递。

7.5.2 冲突（Hazards）—— 核心

数据冲突（RAW）

手段 何时
转发 Forwarding 结果已在后面的流水级算出，旁路喂给后面的 E
停顿 Stall + 气泡 结果还没出来 —— 典型 LDR 之后立刻用加载结果（load-use） 
LDR R0, [R1]
ADD R2, R0, R3    ; 往往要 stall 一拍（视实现）

控制冲突（分支）

下一条 PC 未知 → 可能取错。

手段 直觉
尽早解析分支 缩短错误窗口
Flush 丢掉错误取入的指令
分支预测（7.7） 猜对则无气泡；猜错付 Flush 代价

7.5.3 性能
理想 CPI ≈ 1
实际 CPI > 1（stall / flush / miss）
相对单周期 吞吐通常好得多

7.5.4 对嵌入式 Linux / 驱动

现象 流水线语言
紧依赖链、load 后立刻用 易 stall → 编译器会插无关指令或重排
难预测分支过多 flush 多 → 吞吐掉
dmb / dsb / isb 等屏障 限制乱序观察/流水线；驱动、无锁结构要按架构用对
「指令已取结果未好」 调试时序、锁、DMA 完成标志时的心智模型
Cache miss 常表现为流水线 等存储（接 8.2）
❌ ✅
以为流水线让每条指令「墙上时间」都变 1/5 吞吐↑；单指令延迟仍在；还有停顿
驱动里随便省屏障 弱内存序 + 流水/乱序 → 要按文档插屏障

↔ CSAPP

Harris 7.5 CSAPP
五级 ARM 流水 Y86 PIPE
Forwarding / Stall / Flush 同名
load-use load hazard

笔记

7.5 之上的工业技术（建立名词，细节留给 Hennessy / 厂商手册）：

小节 技术 一句话
7.7.1 深流水线 切到 10–20+ 级抬主频；惩罚是更重的冲刷代价
7.7.2 微操作 μop 复杂指令拆成简单 μop，后端更规整（x86 典型）
7.7.3 分支预测 静态/动态；BTB、多位预测器 —— 少 Flush
7.7.4 超标量 多条通路，每拍发射多条（ILP）
7.7.5–6 乱序 + 寄存器重命名 不按程序序执行；消除 WAR/WAW，暴露更多并行
7.7.7–8 多线程 / 多核 藏访存延迟；一芯片多处理器

HFT：理解「为什么同 IPC 下延迟抖」「分支误预测有多贵」——从 7.5 的 Flush 放大到深流水 + 错误预测即可建立数量级直觉。
