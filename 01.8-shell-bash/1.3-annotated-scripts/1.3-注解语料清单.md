## 注解正文

> 注解格式约定：按"段"而不是按"行"——脚本的自然段（空行分隔的逻辑块）就是注解单元。
> 每段回答三个问题：**这段做什么 / 为什么这么做 / 有什么可以偷的写法**。

### 一、cpu-triage.sh（排查固化类范本）

文件：`06.6.5-systems-performance/chapter-06-cpus/code/scripts/cpu-triage.sh`（34 行）

**段 0：shebang + 注释头 + `set -u`**

```bash
#!/bin/bash
# cpu-triage.sh — CPU 排查六连 + PSI（ch06 §6.5/6.6）
# 出自: notes/section-6.5-性能分析方法论.md 块3、section-6.6-6.7 块4/5
set -u
```

- 注释头第二行直接给**笔记出处**（哪篇笔记的哪个代码块）——脚本和笔记互为索引，改一边能找到另一边。这个"出自"行值得所有脚本抄。
- 只用 `set -u` 不用 `-e`：排查脚本**不该一步失败就全停**——`mpstat` 不在的机器上，
  你希望它跳过继续跑后面的，而不是整个脚本死掉。**-e 的取舍要看脚本性质**：
  构建脚本要 -e（半成品比报错更危险），排查/采集脚本不要 -e（拿到多少是多少）。

**段 1–5：五个固定拍节的采集块**

```bash
echo "===== ① uptime —— load 相对核数（核数=$(nproc)） ====="
uptime
```

- 每块都是同一个三件套：**带圈号标题 echo（内含判读线索）→ 空行 → 命令本体**。
  标题里嵌 `$(nproc)` 这种命令替换，把判读需要的上下文直接印在分隔线上——
  看输出时不用另外查核数。
- 节奏是**先宽后窄**：uptime（全系统概览）→ mpstat per-CPU（定位到核）→ vmstat（队列/切换）
  → pidstat（定位到线程）→ PSI（stall 量化）→ perf（微架构 IPC）。这就是 Gregg 的
  USE/下钻法在脚本里的形状。
- `cat /proc/pressure/cpu` 后面跟一行**纯 echo 的判读阈值**（`some avg10 持续 >10 = CPU 真的不够`）：
  脚本不光采数据，还把"怎么看"印在数据旁边——这是它和裸命令清单的本质区别。

**段 6：优雅降级的标准写法**

```bash
perf stat -a -- sleep 5 2>&1 | grep -E "insn per cycle|GHz|cpus-migrated" || \
    echo "（跳过：perf_event_paranoid=$(cat /proc/sys/kernel/perf_event_paranoid)，需 sudo 调低）"
```

- `cmd | grep ... || echo "（跳过：原因）"`：grep 没匹配到（perf 被 paranoid 挡住）退出码非 0，
  `||` 兜底打印**带诊断信息**的跳过说明——不中断、不误导，还顺手告诉你怎么修。
- 注意这里管道只在**最后一步** grep 上判断成败（没用 pipefail，perf 本身失败也会走到 ||），
  对采集脚本来说这正是想要的行为。
- ⚠ 小细节：`perf stat ... | grep` 里 grep 拿到的行被过滤了，但 perf 的进度输出（2>&1 合流）
  会全进 grep——所以用 `-E` 精确挑三行，而不是全放出来。

**段 7：不执行的命令用 echo 印出来**

```bash
echo "sudo runqlat-bpfcc 10   # 直方图尾部 >1ms 要紧张"
```

- 需要 root 的命令**不自动 sudo**，而是打印出来让人决定——生产环境脚本的安全感：
  脚本永远不该替你提权。同时行尾注释带判读阈值，复制跑完知道看什么。

**可以偷的写法清单**：① "出自"注释行；② 带圈号+判读线索的分隔标题；③ 先宽后窄的块序；
④ `|| echo "（跳过：原因）"` 降级；⑤ root 命令只印不跑。

### 二、linux-60s.sh（60 秒分析法脚本化）

文件：`06.7-bpf-observability/chapter-03-performance-analysis/code/scripts/linux-60s.sh`（19 行）

**核心就两行"框架代码"，其余全是命令清单**：

```bash
set -u
I="${1:-1}"
```

- `I="${1:-1}"`：可选参数的标准吃法——采样间隔默认 1 秒，允许 `./linux-60s.sh 5` 覆盖。
  `${1:-1}` 而不是 `$1` 直接引用，配 `set -u` 才不会在没传参时报错。
  （坑点对照：这正是 1.1 ② 里 `${var:-默认}` 的活例。）

**十条命令的排版手法**：

```bash
echo; echo "===== ② dmesg | tail（内核异常） ====="; dmesg 2>/dev/null | tail -5 || sudo dmesg | tail -5
```

- 和 cpu-triage 的"一块一段"不同，这里**一条命令一行搞定**（`echo; echo 标题; 命令` 用分号串一行）——
  因为 60 秒清单是**扫**不是**钻**，视觉密度要高，一屏看全十条。
  同一个作者两种排版：**清单型脚本紧凑排版，钻取型脚本分段排版**。
- `dmesg 2>/dev/null | tail -5 || sudo dmesg | tail -5`：无权限时静默失败（2>/dev/null）
  → grep 不到东西 tail 输出空 → `||` 升级到 sudo 重试。三级容错压在一行里。
  ⚠ 严格说 `dmesg | tail` 里 dmesg 失败 tail 照样退出 0，`||` 拦的是"输出为空"的错觉——
  这里实际生效的是 `2>/dev/null` 让失败静默，|| 分支靠 tail 继承不到退出码……
  准确机制：`dmesg 2>/dev/null` 失败 → 管道退出码 = tail 的 0 → **|| 其实不会触发**。
  这是原脚本的一个小瑕疵，正确写法是 `dmesg 2>/dev/null | tail -5 || ...` 想要生效得加
  `set -o pipefail` 或改成 `dmesg 2>/dev/null || sudo dmesg | tail -5`。**注解的第一个战利品**：
  已回流到坑点 #3 的"管道只看最后一个命令"。
- `top -b -n 1 | head -20`：批处理模式取一帧再截头——`top` 交互模式进不了脚本，`-b` 就是为此存在。

**和 cpu-triage 的关系**：60s 是**第一滴血**（到机器上先跑它），triage 是**确诊**（60s 说 CPU 有问题再跑 cpu-triage）。
两个脚本合起来就是 Gregg 方法论的实体化——这也是"排查固化类"存在的意义。

### 三、build-core.sh（构建链范本级）

文件：`06.6-ebpf-foundation/chapter-05-core-btf-libbpf/code/scripts/build-core.sh`（43 行）

**段 0：构建脚本的安全配置（和排查脚本相反！）**

```bash
set -eu
cd "$(dirname "$0")/.."
BUILD=.build
mkdir -p "$BUILD"
```

- `set -eu`：构建脚本**必须**一步失败立即停——半成品 .o 比报错危险得多。
  对照 cpu-triage 的 `set -u` 单配置，体会"脚本性质决定头部配置"。
- `cd "$(dirname "$0")/.."`：**定位锚**。`$0` 是脚本被调用的路径，`dirname` 取目录，
  不管从哪调用（仓库根 / cron / 别的脚本）都先站到固定位置（code/ 目录），
  后面所有相对路径才有意义。构建脚本没有这一行就是定时炸弹（坑点 #13 的近亲）。
- `BUILD=.build` 变量化输出目录：产物集中、`.gitignore` 好配、清理一句话。

**段 1：前置依赖检查 + 指路**

```bash
[ -f /sys/kernel/btf/vmlinux ] || { echo "内核无 BTF！运行 scripts/check-btf.sh 诊断"; exit 1; }
```

- 报错信息里**附带下一步动作**（运行哪个诊断脚本）——好报错不是"出错了"而是"怎么办"。
- 用 `[ ]` 单括号：POSIX 写法在简单文件测试上没坑，这里刻意保守（构建脚本可能被各种 sh 解析器碰）。
- `{ ...; exit 1; }` 花括号组：|| 后面要多条命令时的标准结构（注意 `{` 后空格、`;` 收尾）。

**段 2–3：流水线式编译，每步一句"生成了什么"**

```bash
clang -O2 -g -target bpf ... -c hello-buffer-config.bpf.c -o "$BUILD/hello-buffer-config.bpf.o"
echo "生成 $BUILD/hello-buffer-config.bpf.o"
```

- 每个编译步骤后跟一句 echo 报产物——构建日志的自文档化：失败时最后一条"生成"之前的步骤就是凶手。
- `$(wc -l < "$BUILD/vmlinux.h")`：`< file` 喂 stdin 而不是 `wc -l file`，
  输出里不带文件名，拿到纯数字。**小细节，但日志里好看**。

**段 4：here-doc 收尾使用说明**

```bash
cat <<EOF
完成。运行（需 root）：
  sudo $BUILD/hello-buffer-config
EOF
```

- `cat <<EOF`（不加引号）让 `$BUILD` 展开成真实路径——用户复制就能跑。
  对照：如果说明里有 `$` 开头的字面量（比如打印一段示例代码），就要 `<<'EOF'` 防止展开。
- 构建脚本的最后一步是**教用户下一步干什么**——`strace-vs-bpftrace.sh` 的"对比要点"同理。
  这类脚本的输出本身就是教程。

**可以偷的写法清单**：① `cd "$(dirname "$0")/.."` 定位锚；② 前置检查带"怎么办"；
③ 每步报产物；④ `wc -l < file` 纯数字；⑤ here-doc 收尾教程（展开与否看引号）。
