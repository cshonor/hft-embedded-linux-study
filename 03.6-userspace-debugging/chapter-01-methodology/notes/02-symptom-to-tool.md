# 1.2 症状 → 工具决策树

> 🔴 精读 · 从「我看到的」到「我该用的」

## 本节要点

分类学（1.1）给了你「五类问题」，但实战中你面对的不是分类标签，而是**具体症状**：「它段错误了」「它内存一直涨」「它结果有时对有时错」。本节把「症状」翻译成「工具选择」，给出一棵可照做的决策树——这是新手和老手之间最大的差距：老手不是更会背命令，而是**更会从症状一步跳到正确工具**。

## 症状 → 工具决策树

```
程序出问题了
│
├─ 崩溃（段错误 / SIGABRT / 非法指令）
│   ├─ 能复现？ ──是──→ gdb 直接跑，崩溃点设断点（Ch2）
│   └─ 生产偶发 ──────→ 开 core，gdb prog core 回溯（Ch2）
│
├─ 内存持续增长 / 偶发崩溃 / 值莫名变
│   ├─ 怀疑泄漏 / 越界 / UAF
│   │   ├─ 开发期 → valgrind memcheck（Ch3，准但慢）
│   │   └─ 要速度 → ASan 重编译（Ch3，快、需重编）
│   └─ 未初始化读 / UB → UBSan（Ch3）
│
├─ 结果时对时错 / 偶发死锁（多线程）
│   ├─ 数据竞争 → TSan（Ch4，开发期）
│   ├─ 死锁 → gdb attach + thread apply all bt（Ch4）
│   └─ 难复现竞态 → rr 录像回放（Ch4）
│
├─ 卡住不动 / 行为不对 / 调了不该调的
│   ├─ 卡住 → strace -p 看停在哪（Ch5）
│   ├─ 调了什么 syscall → strace（Ch5）
│   └─ 调了什么库函数 → ltrace（Ch5）
│
└─ 太慢 / CPU 高 / 延迟毛刺
    ├─ 热点函数 → perf record + report（Ch6）
    └─ 深入系统级 → 06.6 Systems Performance
```

## 核心决策口诀

| 症状 | 第一反应 | 一句话理由 |
|------|----------|-----------|
| 崩了 | coredump / gdb | 崩溃现场是唯一硬证据，先拿 bt |
| 内存涨 | valgrind | 泄漏只有它能精确定位到分配点 |
| 时对时错 | TSan | 竞态是「偶发」的头号嫌疑 |
| 卡住 | strace -p | 一行就能看到停在哪、等什么 |
| 太慢 | perf | 采样直接给出热点，不猜 |

> **反模式**：所有问题都「先上 gdb 单步」。gdb 擅长「崩溃现场回溯」和「单线程逻辑」，但对「内存泄漏」（要跑很久看趋势）、「数据竞争」（要并发复现）、「性能热点」（要统计采样）都很吃力——这些问题有更对口的工具。

## 「偶发」是决策树里最关键的分支

「偶发」二字会**彻底改变工具选择**：

| 问题属性 | 崩溃类 | 内存类 | 并发类 |
|----------|--------|--------|--------|
| **稳定可复现** | gdb 单步即可 | valgrind 跑一次即出 | gdb 断点即可 |
| **偶发难复现** | 必须开 core 抓现场 | 长时间跑 + ASan | TSan 全量重编 / rr 录像 |

> 稳定 bug 靠「打断点定位」，偶发 bug 靠「抓现场 + 全量检测」。前者是 gdb 的主场，后者是 core/ASan/TSan/rr 的主场。**先判断偶发性，再选工具**，能少做大量无用功。

## HFT 关联

1. **生产偶发崩溃 → 必须先开 core**：交易进程 7×24 跑，崩溃不可复现，唯一证据是 core。上线前必须配好 `ulimit -c` + `core_pattern`（见 Ch2），否则崩溃了连现场都没有。
2. **延迟毛刺 → 先 perf 采样，别猜**：「某天某笔单延迟 250ms」这种毛刺，靠读代码猜热点几乎不可能，perf 采样 + 火焰图直接定位（见 Ch6）。
3. **偶发错单 → 并发优先**：下单结果偶发不对，第一嫌疑是竞态（多线程共享订单状态没锁好），上 TSan 而非逐行读代码。

<summary>自测题（点击展开）</summary>

**Q1:** 「偶发性」为什么是决策树里最关键的分支？

> 因为偶发性直接决定工具选型：稳定 bug 可以打断点、单步、跑一次复现（gdb 主场）；偶发 bug 打不到断点、跑一次不复现，必须靠「抓现场」（core dump）+「全量检测」（ASan/TSan 重编译）+「录像回放」（rr）。用对付稳定 bug 的方法（gdb 单步）去查偶发 bug，基本是白费劲。

**Q2:** 为什么「所有问题都先上 gdb 单步」是反模式？

> 因为 gdb 只擅长「崩溃现场回溯」和「单线程逻辑定位」，对内存泄漏（要长跑看趋势）、数据竞争（要并发复现）、性能热点（要统计采样）都很吃力。这些有更对口的工具：valgrind / TSan / perf。工具不匹配时，gdb 单步既慢又看不到问题。

**Q3:** 生产环境「偶发段错误」，第一步该做什么？为什么不是立刻 gdb attach？

> 第一步是**确认 core dump 已开启**（`ulimit -c` + `core_pattern`），让下一次崩溃能落盘。因为偶发崩溃无法预知何时发生，gdb attach 来不及（崩溃瞬间进程就没了），core 是唯一能事后拿到的现场。没有 core，偶发崩溃基本无解。

**Q4:** 「卡住」和「太慢」都表现为「程序没反应」，怎么快速区分该上 strace 还是 perf？

> 看**是不是永久卡住**：如果进程「永久不动」（等一个永远不会来的事件），是行为/并发问题，用 `strace -p` 看它停在哪（等 IO 还是等锁）；如果进程「还在跑但慢」（CPU 有活动、只是吞吐低），是性能问题，用 perf 采样找热点。「永久卡住」和「缓慢推进」是两类完全不同的病。
