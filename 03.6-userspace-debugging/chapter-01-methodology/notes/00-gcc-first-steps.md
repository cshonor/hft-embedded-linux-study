## 0.1 第一条编译命令：逐词解剖

拿本模块的真实 demo（`code/c1_2_shrink_demo.c`）当例子，它的编译命令是：

```bash
gcc -g -O0 -Wall -Wextra -o c1_2_shrink_demo c1_2_shrink_demo.c
```

一行七个词，每个词一件事：

| 词 | 是什么 | 为什么需要它 |
|----|--------|--------------|
| `gcc` | GNU C 编译器 | 把「人能读的 .c」翻译成「CPU 能跑的机器码」 |
| `-g` | 往产物里**塞调试信息**（变量名、行号映射表） | 没有它，gdb 里只能看到一串地址，看不到「第 20 行」「变量 qty」（1.5 节整节讲这张表） |
| `-O0` | **零优化**（字母 O + 数字 0） | 优化会重排、删除、内联代码——调试时「代码长什么样」和「机器跑什么」对不上。-O0 保证所见即所得 |
| `-Wall` | 打开**主要警告**（Warning all） | 编译器发现可疑写法会提醒你，比如「变量没初始化就用」。警告不是错误，但调 bug 时它们经常就是答案 |
| `-Wextra` | 打开**更多警告** | -Wall 的补充包，惯例两个一起开 |
| `-o c1_2_shrink_demo` | 输出文件叫这个名字 | 不写 `-o` 的话产物默认叫 `a.out`（历史遗留名字），十个 demo 就分不清谁是谁了 |
| `c1_2_shrink_demo.c` | 输入：源文件 | 唯一一个「原材料」 |

**敲完什么反应都没有 = 成功了。** Unix 的规矩是「没消息就是好消息」——
编译器只有出错/警告才会说话。产物是当前目录下一个叫 `c1_2_shrink_demo` 的新文件：

```bash
$ ls -l c1_2_shrink_demo
-rwxr-xr-x 1 wzp wzp 23456 Sep 22 17:00 c1_2_shrink_demo
#  ↑ x = 可执行（executable）
```

> **macOS 用户注意**：Mac 上敲 `gcc` 实际调用的可能是 clang（苹果把 gcc 这个名字
> 指向了自家的 clang）。对本模块所有 demo 来说两者完全等价，照敲即可；
> 想看自己用的是谁：`gcc --version`。

## 0.2 运行与「退出码」：程序无声的遗言

```bash
$ ./c1_2_shrink_demo < ticks_10.txt     # 跑起来（< 的意思见 0.3）
...程序输出...
$ echo $?                               # 立刻问一句：刚才那个程序死得体面吗？
136
```

两件事逐一说清：

**`./` 是什么**：当前目录。Shell 只会在几个固定目录（PATH）里找命令，
当前目录不在其中，所以必须显式说「就这个目录里的这个文件」。

**`$?` 是什么**：上一个程序退场时留下的一个整数，叫**退出码（exit code）**。
它是程序唯一的「遗言」，规则只有三条：

| 退出码 | 含义 | 例子 |
|--------|------|------|
| `0` | 正常结束，一切顺利 | `./c1_2_shrink_demo < ticks_first6.txt` → 0 |
| `1`–`127` | 程序自己报错退出（`return 1` / `exit(1)`） | ASan 抓到泄漏 → 1 |
| `128 + N` | **被 N 号信号杀死的**（不是自己退出的） | 136 = 128+8 = SIGFPE（除零被杀）；139 = 128+11 = SIGSEGV（段错误被杀） |

调试时这个数字是第一情报：**136/139 说明程序是「被杀」不是「报错」**，
直接指向崩溃类问题——这就是 1.1 问题分类学能用命令行落地的第一课。

## 0.3 `< file`：让程序以为你在打字

```bash
./c1_2_shrink_demo < ticks_10.txt
```

`<` 叫 **stdin 重定向**。demo 程序用 `scanf` 从「标准输入」读行情数据——
标准输入默认是键盘，也就是它停在那里等你一行行敲。`< ticks_10.txt` 告诉 shell：
「别等键盘了，把这个文件的内容当成打进去的字」。

为什么 demo 要这样设计？因为**砍输入 = 改文件，不用改代码**——
1.3 节「最小复现」的玩法：把 10 行数据砍到 6 行另存一个文件，喂进去看还崩不崩，
不用碰源代码一下。这是调试方法论里「缩小现场」最省力的机关。

## 0.4 gdb 第一次会话：每行都注释

gdb 是源码级调试器：**让程序停在半路上，看里面的变量**。
用 1.1 的崩溃 demo 走一遍完整会话（`#` 后是注释，不用敲）：

```text
$ gdb ./c1_1_three_bugs                    # ① 启动：把程序交给 gdb 托管（程序还没跑）
(gdb) break main                           # ② 在 main 函数入口下个断点：跑到这里先停一下
(gdb) run 1                                # ③ 开始跑（1 是程序的命令行参数，触发空指针那颗雷）
Breakpoint 1, main (...) at c1_1_three_bugs.c:24   # 停住了：告诉你停在哪个文件第几行
(gdb) next                                 # ④ 往下走一行（next = 执行当前行，函数调用不追进去）
(gdb) next                                 #    再走一行……
Program received signal SIGSEGV, Segmentation fault.  # ⑤ 崩了！gdb 把它拦下来
0x00005555555551a7 in case1_crash () at c1_1_three_bugs.c:11
(gdb) bt                                   # ⑥ backtrace：怎么走到这里的？打印整条调用链
#0  case1_crash () at c1_1_three_bugs.c:11          ← 崩溃点：第 11 行
#1  main () at c1_1_three_bugs.c:26                 ← 谁调用的它：main 第 26 行
(gdb) print p                              # ⑦ 看看嫌疑人：变量 p 现在的值
$1 = (int *) 0x0                           # 0x0 = 空指针！第 11 行 *p = 42 往空地址写 → 崩
(gdb) quit                                 # ⑧ 退出 gdb
```

八个命令就是最小学件套：**`break`（设断点）→ `run`（开跑）→ `next`（走一行）→
`bt`（看调用链）→ `print`（看变量）→ `quit`（走人）**。
本例的完整推理：崩在第 11 行（`bt` 第 #0 帧）→ 原因是 `p = 0x0`（`print`）→
「往空指针写数据」就是段错误——从崩溃到根因，30 秒。

> 记住一个对照：没有 gdb 时，段错误只留下一句 `Segmentation fault` 和退出码 139，
> 崩在哪一行、变量是什么值，全部无从得知。**gdb 就是把「黑箱之死」变成「解剖现场」的工具。**

## 0.5 strace 第一次跑：输出每列是什么

strace 是另一类工具：**不看代码，只看程序对操作系统说了什么**（每次系统调用都记录下来）。

```bash
$ strace -e trace=write ./c1_2_shrink_demo < ticks_first6.txt
```

逐词：`-e trace=write` = 「只盯 write 这一个调用」（不过滤的话满屏几百行）；
`./c1_2...` = 要观测的程序。输出长这样：

```text
write(1, "record 1: ts=1726...", 27) = 27
 │    │           │                │   └─ 返回值：实际写了 27 字节（= 号后面永远是返回值）
 │    │           │                └─ 第三个参数：要写的长度
 │    │           └─ 第二个参数：写的内容（字符串被截断显示）
 │    └─ 第一个参数：文件描述符 1 = 标准输出（屏幕）
 └─ 系统调用名
```

一行 = 一次系统调用，格式恒为 `调用名(参数...) = 返回值`。
程序慢、卡、读错文件、网络重试——这些「行为类」问题在 strace 下全部现形，
而且**不需要 -g、不需要重新编译**，线上程序也能直接看（`strace -p <PID>`）。
这就是 1.2 决策树里「行为不对，先 strace」的原因。

## 0.6 环境对照：在哪里敲这些命令

| 环境 | 能不能用 | 说明 |
|------|----------|------|
| Linux（含 WSL、树莓派） | ✅ 全部 | 本模块的默认假设，gcc / gdb / strace 都是原配 |
| macOS | ⚠️ 大部分 | gcc→实为 clang（等价）；gdb 要换成 `lldb`（命令几乎一样）；**没有 strace**（对应物是 `dtruss`，且需关 SIP） |
| 没有 Linux 环境时 | ✅ 替代 | Compiler Explorer（godbolt.org）网页里能编译运行，本模块 Ch1 的 demo 实测就是在它上面做的 |

**Q1:** `gcc -g -O0 -o demo demo.c` 里 `-g` 和 `-O0` 各管什么？少了它们调试时分别会怎样？

> `-g` 管「信息」：往二进制里写调试映射表（行号 ↔ 地址、变量名 ↔ 位置），
> 没有它 gdb 只剩裸地址。`-O0` 管「保真」：关掉优化，保证机器跑的和你写的逐行对应；
> 优化开着时变量可能显示 `<optimized out>`、单步会「乱跳行」，因为代码已被重排。
> 口诀：-g 给 gdb 眼睛，-O0 给 gdb 真话。

**Q2:** 程序跑完 `echo $?` 显示 139，这说明什么？和显示 1 有什么本质区别？

> 139 = 128 + 11 = 被 11 号信号（SIGSEGV，段错误）**杀死**——程序没机会自己退出，
> 是内核动的手，指向「访问了不该访问的内存」。退出码 1 是程序**自己**判断出错后
> 主动 exit(1)，说明它活到正常流程里、只是逻辑上报告失败。
> 「被杀」找崩溃类工具（gdb/coredump），「主动报错」查逻辑——退出码把这两类问题在第一秒就分开了。

**Q3:** `./demo < data.txt` 比「打开程序再手敲数据」好在哪里？（至少说出两点）

> ①可重复：同一份输入喂一百次都一字不差，bug 复现的前提；
> ②可缩小：砍输入只要编辑文本文件（1.3 的最小复现），不用改代码重新编译；
> ③可自动化：脚本/CI 里没法「手敲」，重定向让调试流程能写成命令序列。

**Q4:** gdb 的 `bt` 输出里 `#0` 和 `#1` 哪一行是「凶案现场」，哪一行是「报案人」？

> `#0` 是现场——程序实际崩溃（或停下）时正在执行的那个函数；
> `#1` 是调用 `#0` 的人，逐级往上 `#2`、`#3` 是更外层调用者，最下面是 main。
> 读 bt 的顺序：先看 #0 定位崩在哪行，再沿 #1 #2 往上追「这个坏值是谁传下来的」。

**Q5:** strace 输出 `write(1, "hello", 5) = 5`，如果实际只写成功一部分会显示什么？这在排查什么问题时关键？

> 显示 `= 3` 这类**小于请求值**的返回值（write 不保证一次写完）。
> 这在排查「数据丢了/对端收到半截」类问题时是关键证据：write 返回值 < 请求长度
> 说明内核只接收了一部分（发送缓冲满、信号中断等），调用方必须循环补写——
> 只看返回值才知道「我以为发出去了」和「实际发出去了」是不是一回事。
