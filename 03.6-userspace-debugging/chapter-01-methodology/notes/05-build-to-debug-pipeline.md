# 1.5 从源码到断点：gcc -g / gdb / strace 全链路

> 🔴 精读 · 把三个零件串成一条线

## 本节要点

1.1–1.4 回答「遇到什么问题、用什么工具、怎么系统收敛」，Ch2–Ch6 逐个讲工具怎么用。但两者之间缺一根轴：**一段 C 代码从敲下 `gcc -g` 到被 gdb 断住，中间到底发生了什么**？工具手册不会替你把这一步串起来——本节就是这根轴。走完这条链路你会发现：所谓调试工具，不过是在编译期埋下的一张**映射表**上做文章；gdb 和 strace 看似两类工具，其实踩在**同一个系统调用（ptrace）**上。

```text
源码 .c ──gcc -g──▶ ELF（.text + DWARF 映射表）
                        │                │
        gdb 读表 ◀──────┘                └── strace 不读表（只拦 syscall）
        break 20 → 查表得地址 → 写入 int3 → CPU 停住 → bt 反向查表译回源码行
```

## ① 构建期：`-g` 埋的不是"信息"，是"映射表"

编译器**默认不往二进制里写调试信息**——那会让体积膨胀、还泄露源码结构。`-g` 的作用是让编译器额外生成 **DWARF** 格式的调试数据。对调试最有用的是两张表：

| DWARF 段 | 内容 | gdb 拿它干什么 |
|----------|------|----------------|
| `.debug_line` | **地址 ↔ 源码行号/列号** 逐条映射 | `break file.c:20` 把行号译成地址；`bt` 把地址译回行号 |
| `.debug_info` | 变量名/类型 ↔ 存放位置（寄存器/栈偏移） | `p qty` 按名字找到那个变量当前在哪 |

用本章标本程序 `code/c1_5_pipeline.c`（30 行，`apply_fee` + `main`）实测一遍。**实测环境：Apple M1 / macOS 26.6 / clang 23.1.0（Mach-O arm64）**：

| 产物 | 体积 | 说明 |
|------|------|------|
| 不带 `-g` | 50,040 B | 纯机器码 |
| 带 `-g` | 50,424 B（仅 +384 B） | **macOS 特例**：链接器不内嵌 DWARF，只嵌一张 OSO 调试映射表，指向 `.o` 文件 |
| `dsymutil` 后的 `.dSYM` | 9.3 KB | 完整 DWARF 落盘在这里，38 条行号映射 |

> ⚠️ **平台差异是这条链路上最容易踩的坑**：Linux/ELF 下 `gcc -g` 把 `.debug_*` 段直接嵌进可执行文件（2.1 节实测 0 个 vs 9 个段）；**macOS/Mach-O 下 `-g` 后的可执行文件里并没有 DWARF**，要 `dsymutil` 把各 `.o` 的调试信息收拢成 `.dSYM` 包（所以 macOS 调试必须在编链接的**同一台机器、保留 .o 或 dSYM**，否则 gdb/lldb 看到的就是裸地址）。线上符号归档同理：**二进制 + 调试符号必须成对留档**（2.5 节会再强调）。

`llvm-dwarfdump --debug-line` 把那张表摊开给你看（节选，完整 38 条）：

```text
Address            Line   Column File   Flags
------------------ ------ ------ ------ ------------------
0x0000000100003efc     20     27    1   is_stmt            ← main 第 20 行：调用 apply_fee
0x0000000100003f40     13     20    1   is_stmt prologue_end ← apply_fee 第 13 行：算 notional
```

这两行就是后面一切"魔法"的物理载体：**gdb 说"停在 20 行"，本质是"停在 0x100003efc"**。没有 `-g`，这张表根本不存在——这就是 1.2 决策树里"想源码级调试，第一步永远是重编 `-g`"的原因。

## ② 运行期：gdb = 查表器 + int3 注入器

你敲 `break c1_5_pipeline.c:20`，gdb 在背后做了四步（**手册格式示意**，gdb 交互会话本模块验证环境跑不了，与 2.1 节同一惯例）：

```text
1. 查 .debug_line：第 20 行第一条 is_stmt 指令 = 0x100003efc（就是上面那行表）
2. ptrace 附着进程，把该地址的指令首字节替换为 0xCC（x86 的 int3 陷阱指令）
3. CPU 跑到 0x100003efc → 触发 SIGTRAP → 内核把信号递给 gdb（进程停下）
4. gdb 把原字节写回去、PC 回退一字节，你看到的就是"停在第 20 行"
```

此后每个"魔法"都是同一张表的反复使用：

| gdb 命令 | 背后动作 |
|----------|----------|
| `break 20` | 正向查表：行号 → 地址 → 写 int3（上面四步） |
| `bt` | 逐帧取返回地址，**反向查表**：地址 → `file.c:xx`，所以没有 `-g` 时 `bt` 只有一串裸地址 |
| `p qty` | 查 `.debug_info`：qty 在寄存器/栈偏移多少 → 读出来按类型解释 |
| `continue` | 再写回 int3，放行，等下一次 SIGTRAP |

**一句话：gdb 没有任何源码透视能力，它只是一个忠实的查表员 + 一个会塞陷阱指令的进程外大脑。** 这也解释了 2.7 的现象：`-O2` 下变量 `<optimized out>`，不是 gdb 坏了，是表里那条映射（变量→位置）被优化打散了。

## ③ strace：同一个底座（ptrace），另一种滤镜

strace 和 gdb 用的是**同一个系统调用 ptrace**——这是最反直觉也最该记住的一点。区别只在观测策略：

| | gdb | strace |
|---|-----|--------|
| ptrace 用法 | 拦**陷阱信号**（int3/SIGTRAP），停在指令级 | `PTRACE_SYSCALL` 拦在**每次系统调用的进/出口** |
| 依赖 `-g`？ | **依赖**（不查表就是瞎子） | **完全不依赖**——它观测的是进程与内核的行为边界（调了什么、传了什么参数、返回什么），与源码无涉 |
| 观测粒度 | 指令级、变量级 | syscall 级 |
| 典型问题 | 值为什么错了、崩在哪一行 | 在反复重试？打开的文件不对？读到的字节数不对？卡在哪个调用上？ |

正因为不需要 `-g`，strace 能直接对付**线上那个 stripped 二进制**——这决定了分工：**行为不对，先 strace（零前提、零侵入）；逻辑/内存不对，再 gdb（要有符号）**。

## ④ 协作闭环：一条命令流上的接力（示意）

把三个零件放到一个 bug 上（示意场景：订单程序偶发"卡住"，日志无异常）：

```bash
# 1) strace 先看行为 —— 发现 write 在循环里反复返回 EAGAIN
strace -e trace=write,recvfrom -p $(pidof order)

# 2) 假设（对照 1.4 元流程）：socket 发送缓冲长期满 → 上游没消费
#    设计验证：gdb attach 抓现场，看阻塞点与 fd 状态
gdb -p $(pidof order)
(gdb) break send_orders if rc < 0      # 条件断点：只在失败时停
(gdb) continue
(gdb) bt                               # 反向查表：现场在哪条调用链上
(gdb) p errno                          # 查表读变量：证实 EAGAIN

# 3) 根因证实（对端不读了）→ 修上游消费逻辑，而非在 send 前吞掉 errno
```

对照 1.4 的元流程：**strace 承担"观察现象 + 收缩假设"，gdb 断点承担"设计验证 + 证实根因"**。两者不是二选一，而是接力——这也是 1.2 决策树"行为类 → 5.x，崩溃/逻辑类 → 2.x"背后的统一原理：**先让滤镜成本低、前提少的工具上场，再用重武器精确打击**。

## HFT 关联

1. **符号归档是交易系统的运维红线**：core / attach 现场没有成对符号就是裸地址。macOS 生产线尤其注意 `-g` ≠ 有符号，`dsymutil` 产物必须与二进制同版本归档。
2. **生产诊断优先 strace**：延迟敏感的进程被 gdb attach 会整进程停住（错失行情窗口）；strace `-p` 逐 syscall 观测侵入更小，且不需要事先带 `-g` 构建。
3. **理解 int3 机制才能理解调试的代价**：断点会改代码段、打断时序——对竞态类 bug，断点本身就是干扰源（2.6 的 rr / 录制回放正是为了解决这个矛盾）。

**Q1:** gdb 说「停在第 20 行」，这句话背后发生了哪四步？

> 查 `.debug_line` 得第 20 行首条 is_stmt 指令地址 → ptrace 把该地址首字节换成 0xCC → CPU 执行到此处触发 SIGTRAP、进程停下 → gdb 恢复原字节、PC 回退。所有源码级调试都建立在这四步上。

**Q2:** 为什么 gdb 必须要 `-g`（或 dSYM/分离符号文件），strace 却不用？

> gdb 的每个命令（断点/bt/p）都是对 DWARF 映射表的正向或反向查询，没表只能看裸地址；strace 用 PTRACE_SYSCALL 拦在 syscall 边界，观测的是进程—内核行为，与源码信息无关。

**Q3:** macOS 上编译了 `clang -g` 的二进制，拷到另一台机器上 lldb 却显示不了源码行，最可能的原因？

> macOS 链接器默认不内嵌 DWARF，可执行文件里只有 OSO 调试映射（指向编译时的 .o 路径）。跨机器调试必须随二进制带上 `dsymutil` 生成的 `.dSYM`，且 .o 已删时 dsymutil 也救不回来（本节实测即踩此坑：临时目录的 .o 被清 → dSYM 生成失败）。

**Q4:** 「行为不对先 strace，逻辑不对再 gdb」——这条分工的依据是什么？

> 前提成本：strace 零前提（不需要 -g、不用重编、可 attach 线上 stripped 二进制），代价是只有 syscall 粒度；gdb 信息最细但有符号前提，且 attach 会整进程暂停。按 1.4 的原则先用低成本观测收缩假设，再用高成本工具证实。
