# 1.4 调试元流程（假设 → 验证 → 收敛）

> 🔴 精读 · 调试不是「试错」，是「科学方法」

## 本节要点

新手调试是「改一处、跑一下、看结果」，老手调试是「**提出假设 → 设计验证 → 收敛范围**」的循环。前者是随机试错（试 10 次可能碰巧对 1 次），后者是科学方法（每步都让嫌疑范围变小）。本节讲这个「元流程」——它是《Writing Solid Code》反复强调的核心，也是区分「碰运气」和「系统排查」的分水岭。

## 调试元流程：四步循环

```
  ┌─────────────────────────────────────────────┐
  │                                             │
  ▼                                             │
① 观察现象（崩溃栈 / 错误值 / 卡住位置）          │
      │                                         │
      ▼                                         │
② 提出假设（「可能是 X 没初始化」）              │
      │                                         │
      ▼                                         │
③ 设计验证（断点 / 打印 / 工具观测，检验假设）     │
      │                                         │
      ├── 假设成立 → ④ 缩小范围，回到②继续        │
      │              （或直接定位根因，结束）     │
      │                                         │
      └── 假设不成立 → 修正假设，回到②            │
                                                │
  （循环直到根因被证实，而非「碰巧能跑」）          └─┘
```

核心特征：**每一步都有「假设」和「验证」**，而不是「无目标地改」。

## 对比：试错 vs 科学方法

| 维度 | 随机试错 | 科学方法 |
|------|----------|----------|
| 行动 | 改一处、跑一下 | 先想「如果假设成立，应该观察到什么」 |
| 依据 | 「感觉像这里」 | 「证据指向这里」 |
| 失败后 | 换一处再试 | 修正假设，缩小嫌疑范围 |
| 收敛性 | 不保证（可能绕圈） | 保证（每次验证都排除一批） |
| 终点 | 「能跑了，不管为什么」 | 「根因被证实，且知道为什么」 |

> ⚠️ **「碰巧能跑」是最危险的终点**。改了之后 bug 消失了，但如果你不知道**为什么**消失，很可能只是把症状掩盖了、时序改变了，bug 还在暗处等着复发。调试的终点是「根因被证实」，不是「现象消失」。

## 三个高频陷阱

### 1. 确认偏误（confirmation bias）

「我怀疑是 A 的问题」，于是**只找支持 A 的证据**，忽略反例。

```
错误示范：怀疑是锁的问题 → 加了把锁 → bug 暂时没出现 → 结论「就是锁」
正确做法：加锁后 bug 没出现，还要问「是锁修好了，还是时序变了导致 bug 藏起来了？」
         → 用 TSan 证实确实有数据竞争，才算证实「是锁的问题」
```

### 2. 一次改多处（失去因果）

```c
// 错误：一次改了 3 处，bug 好了，但不知道是哪处起作用
buf = malloc(n + 1);   // 改 1：+1
memset(buf, 0, n);     // 改 2：清零
free(buf);             // 改 3：加 free

// 正确：一次只改一处，验证后再改下一处
```

> 一次改多处，即使 bug 好了，你也**没学到任何东西**——不知道哪处是根因，下次同类 bug 还得从头试。

### 3. 改症状不改根因

```c
// 症状：偶发段错误，崩溃在 strcpy
// 错误做法：在 strcpy 前加 if (src == NULL) return;  ← 掩盖症状
// 正确做法：追为什么 src 会是 NULL → 发现是竞态导致指针被提前 free
//          → 修锁/生命周期，而非加 NULL 判断
```

## 日志 / 断点 / 打印：三种验证手段怎么选

验证「假设是否成立」有三种手段，各有适用场景：

| 手段 | 适用 | 代价 | 局限 |
|------|------|------|------|
| **打印/日志** | 快速看「执行到没、值是什么」 | 改代码 + 重编译 | 加太多干扰时序、污染性能 |
| **断点** | 精确停在某行看现场 | 无需重编译（attach） | 打断点影响并发时序 |
| **工具观测** | strace/valgrind/TSan 自动检测 | 无需改代码 | 各有观测域（见 1.1） |

> 原则：**先用工具观测（零侵入），不够再用断点，最后才加打印**。打印是「最后手段」，因为它要改代码、重编译、还可能改变时序（尤其并发 bug）。

## 动手：一个假设被证伪的全过程（实测）

上面讲的是道理，下面走一遍**真实的循环**。这个例子的价值在于：**第一个假设是错的，而且错得很典型**——它是「人人都信的常识」。

### ① 观察现象

写一份探针 `code/c1_4_hypothesis_div.c`，三种除零写法各跑一次：

```c
static volatile int g_zero = 0;
static volatile int g_one  = 1;

if (argv[3][0] == 'A') {          /* A: 常量分子 / volatile 除零 */
    int c = 1 / g_zero;
    printf("A: 1 / volatile-zero = %d\n", c);
} else if (argv[3][0] == 'B') {   /* B: 两个 volatile */
    int c = g_one / g_zero;
    printf("B: volatile-one / volatile-zero = %d\n", c);
} else {                          /* C: argv 传来的运行时值 */
    int c = a / b;
    printf("C: %d / %d = %d\n", a, b, c);
}
```

gcc 13.3.0 `-g -O0 -Wall -Wextra` 实测：

```text
$ ./c1_4_hypothesis_div 1 0 A
A: 1 / volatile-zero = 0
没有崩，正常退出
$ echo $?
0

$ ./c1_4_hypothesis_div 1 0 B
Program terminated with signal SIGFPE (8)
$ echo $?
136

$ ./c1_4_hypothesis_div 1 0 C
Program terminated with signal SIGFPE (8)
$ echo $?
136
```

**A 没崩。** 退出码 0，还打印了 `= 0`。

### ② 提出假设（H1）

> **H1**：整数除零是 UB，UB 会发 SIGFPE 终止进程。**三个写法都应该是 136。**

### ③ 设计验证

如果 H1 成立，A/B/C 三次运行的退出码应该全是 136。**实测 A = 0**。

### 假设不成立 → 修正假设

**H1 被证伪了。** 注意这里最容易犯的错：*「可能是我哪里写错了 / 再跑一次试试 / 大概是编译器 bug」*——这都是**拒绝修正假设**。正确的动作是：**信数据，改假设**。

那 A 和 B 的差别在哪？逐字对比：

| | 分子 | 分母 | 实测 |
|---|------|------|------|
| A | **字面量 `1`** | `volatile int g_zero` | 不崩，打出 0 |
| B | `volatile int g_one` | `volatile int g_zero` | SIGFPE |
| C | argv 运行时值 `a` | argv 运行时值 `b` | SIGFPE |

唯一的结构差别是**分子是不是编译期已知的常量**。于是修正假设：

> **H2**：当分子是编译期常量时，gcc 会把 `1 / x` 折成一段**不含除法指令**的等价序列；只有两个操作数都是运行时值时才真的生成 `idiv`，才可能发 SIGFPE。

### ④ 验证 H2：去看汇编

假设 H2 是**可证伪的、且能直接观测**的——去看 A 和 B 生成了什么指令。用 `-S` 或编译器浏览服务取汇编（`-O0`，节选）：

```asm
div_const_numerator:            ; 对应 A：1 / z
        mov     eax, DWORD PTR z[rip]
        mov     edx, eax
        add     edx, 1
        cmp     edx, 2
        setbe   dl
        mov     ecx, 0
        test    dl, dl
        cmove   eax, ecx
        pop     rbp
        ret                     ; ← 整段里没有一条 idiv

div_two_volatiles:              ; 对应 B：one / z
        mov     eax, DWORD PTR one[rip]
        mov     ecx, DWORD PTR z[rip]
        cdq                     ; 把 eax 符号扩展到 edx:eax
        idiv    ecx             ; ← 真除法：ecx == 0 → #DE → SIGFPE
        pop     rbp
        ret
```

**H2 被证实**：A 那段汇编里**一条 `idiv` 都没有**，全是比较和条件搬移，所以它永远不会触发 `#DE`（除零异常）——它「算出」的 0 只是这段无分支序列对「除数为 0」这种 UB 输入的任意产物。B 才有 `idiv`。

### ⑤ 收敛：这条循环教了什么

| 环节 | 本例中的具体动作 |
|------|-----------------|
| 观察 | `1 / volatile-zero` 打印 0 且 exit 0（不是 SIGFPE） |
| 假设 H1 | 「除零都发 SIGFPE」——来自日常经验的常识 |
| 验证 H1 | 三种写法跑一遍 → **A = 0，H1 死** |
| 修正 H2 | 「常量分子会被折成不含除法的序列」 |
| 验证 H2 | 取汇编 → A 无 `idiv`、B 有 `idiv` → **H2 活** |
| 收敛 | 结论 = 「整数除零是否崩，取决于编译器有没有生成除法指令」——**UB 不是「一定崩」，是「没有保证」** |

对照 1.4 的三个陷阱，这次循环恰好绕开了全部三个：

1. **没有确认偏误**：H1 被实测打脸时，信数据而不是信直觉（没有「再跑一次看看」）。
2. **一次只改一处**：A/B/C 是**三个独立变体**，不是「改了 A 又改 B」——每个变体只变化一个维度（分子是不是常量），所以能干净地归因。
3. **没有改症状**：没有人去「在除法前加 `if (z == 0) return;`」把症状盖掉——那是掩盖 UB，不是修它（正确做法见 3.3 的 `__builtin_add_overflow` 一节）。

> **这条经验比结论本身更重要**：调试中最贵的不是「不会用 gdb」，而是**实测结果和你的假设冲突时，你选择怀疑数据**。UB 的整个「隐形」性格（见 3.3）就建立在这个反直觉性上——**UB 的典型表现恰恰是「不崩、还给你一个看起来合理的数」**。

## HFT 关联

1. **「碰巧能跑」在交易系统里是灾难**：改了时序、加了条日志，竞态暂时不出现了，你上线后它照样偶发错单。必须用 TSan/ASan **证实**根因，而不是「看起来好了」。
2. **一次改一处**：交易逻辑高度耦合，一次改多处会让「到底哪处修的」不可知，出问题没法回滚定位。
3. **工具零侵入优先**：生产环境排查优先 attach/strace/perf（不动代码、不改时序），而不是加打印重编译——延迟敏感系统里，加打印本身就会引入新的竞态和延迟。

**Q1:** 「随机试错」和「科学方法」的本质区别是什么？

> 本质区别在**有没有「假设 + 验证」**：试错是「无目标地改一处看结果」，失败后换一处再试，不保证收敛；科学方法是「先提出假设 → 设计验证（如果假设成立应该观察到什么）→ 用证据证实或证伪 → 缩小范围」，每次验证都排除一批嫌疑，保证收敛。前者碰运气，后者可复现地逼近根因。

**Q2:** 为什么「碰巧能跑」是最危险的调试终点？

> 因为「现象消失」≠「根因解决」：改了之后 bug 不出现，可能只是时序改变、症状被掩盖，根因还在暗处。上线后环境一变，bug 照样复发，甚至更隐蔽。调试的终点必须是「根因被证实」（用工具/证据证明是它），而不是「看起来好了」。

**Q3:** 「一次改多处」为什么是坏习惯？

> 因为失去了因果判断：三处一起改，bug 好了，你不知道是哪一处起的作用，等于没学到任何东西，下次同类 bug 还得从头试。正确做法是一次只改一处、验证后再改下一处，每步都建立明确的因果。

**Q4:** 验证假设的手段（打印/断点/工具观测）应该按什么顺序选？为什么？

> 应该**先工具观测（零侵入）→ 不够再断点 → 最后加打印**。因为工具（strace/valgrind/TSan）不用改代码、不改时序；断点要 attach 但会扰动并发时序；打印最重——要改代码、重编译、还可能改变时序（尤其并发 bug，加打印往往让竞态「消失」）。所以打印是最后手段。

**Q5:** 上面「假设被证伪」的例子里，H1 错在哪？为什么说「信数据、改假设」比「再跑一次试试」重要？

> H1 错在把「UB」等同于「一定崩」。UB 的真实含义是**「没有任何保证」**——编译器可以（并且确实会）基于「除数非零」的假设，把 `1 / 常量分母` 折成一段不含 `idiv` 的序列，于是既不崩也不报错。这类「实测打脸直觉」的时刻是调试的分水岭：**「再跑一次试试」属于拒绝修正假设**（若结果是稳定可复现的，重跑不产生新信息）；正确动作是信数据，把假设改成能被观测证伪的 H2（「常量分子不生成除法指令」），然后去汇编里找证据。
