# 4.0′ 第一次数据竞争：结果对了，TSan 照样报警

> 🟢 零起点 · 接续 [3.0′ ASan 篇](../../chapter-03-memory/notes/00-first-asan-report.md)
>
> 并发 bug 是五类问题里最阴的：**不崩、不报错、退出码 0，结果偶尔是错的**——
> 而且在你的开发机上可能连续对一千次，上线后每分钟错三次。
> 这一篇用 `code/c4_1_data_race.c` 走完数据竞争的完整认知曲线：
> 先被「退出码 0 但答案错了」震撼一次，再用 TSan 把「为什么错」钉到源码行。
> TSan 报告逐行读法同 3.0′：其实它也只说了四件事。

---

## 第一震撼：丢了 50% 的更新，进程「成功」退出

两个线程各对同一个计数器加 100000 次，答案应该是 200000：

```bash
gcc -g -O2 -pthread -Wall -Wextra -o c4_1 c4_1_data_race.c
./c4_1 race
```

```text
实际结果 = 100000   （丢了 100000 次更新，50.00%）
耗时     = 11.8 ms
$ echo $?
0                     ← 进程没有崩，stderr 是空的，「成功」退出
```

**结果错了一半，程序自己毫无察觉**。对照 1.0/2.0′ 的退出码体系：139/134 那类
「死给你看」的 bug 在这里完全失效——竞态不死人，它只是悄悄地错。
这就是 1.2 决策树里「结果偶尔不对 → 并发类 → TSan」强制分流的原因。

**为什么 `g++` 会丢更新**：`counter++` 看着是一行 C，实际是三步机器操作——
读出来、加一、写回去。两个线程交错执行时，两边都读到 5、都写回 6，
两次自增只生效一次。demo 把窗口撑开后稳定丢 50%；生产环境的窗口窄得多，
所以「偶发」。（三种正确写法——mutex / atomic / 每线程私有——见 4.1 笔记。）

## 第二震撼：结果全对，TSan 依然报警

同一份代码，用 clang 带 `-fsanitize=thread` 重编再跑：

```bash
clang -g -O1 -fsanitize=thread -pthread -o c4_1_tsan c4_1_data_race.c
./c4_1_tsan race
```

```text
实际结果 = 200000   （丢了 0 次更新，0.00%）   ← 这次运气好，全对
...
WARNING: ThreadSanitizer: data race (pid=2)     ← 但 TSan 照样报警
```

**结果对了还报警**——这是 TSan 最反直觉也最有价值的一点：
它检查的不是「这次错了没有」，而是「**这里存在无保护的并发访问**」。
赌赢一次的竞态还是竞态，下次调度换个交错就输。所以抓竞态**不能靠多跑几遍看结果**。

> ⚠️ 用 clang 不用 gcc 的原因：gcc 版 TSan 运行时和容器/部分系统的地址空间布局冲突
> （`FATAL: ThreadSanitizer: unexpected memory mapping`），同代码换 clang 即正常——
> 见 code/README 坑 3，遇到这个报错不要怀疑自己的代码。

## TSan 报告逐行读：也是四件事

```text
==================
WARNING: ThreadSanitizer: data race (pid=2)                    ①
  Read of size 4 at 0x5555569dd660 by thread T2:               ②
    #0 th_race /app/example.c:104:16

  Previous write of size 4 at 0x5555569dd660 by thread T1:     ③
    #0 th_race /app/example.c:104:16

  Location is global 'g_race' of size 4 at 0x5555569dd660      ④

  Thread T2 (tid=5, running) created by main thread at:        ⑤
    #0 pthread_create ...
    #1 run_threads /app/example.c:134:9
SUMMARY: ThreadSanitizer: data race /app/example.c:104:16 in th_race   ⑥
==================
```

| 行 | 它说了什么 | 人话 |
|----|-----------|------|
| ① | **错误类型** `data race` | 存在无同步的并发访问（不管后果） |
| ② | **当事人 A**：线程 T2 在读，4 字节，在哪行 | 一方在 `example.c:104` 读 |
| ③ | **当事人 B**：线程 T1 **之前**在写，同一个地址 | 另一方也在 `:104` 写——同一行既是读者又是写者 |
| ④ | **争的是什么**：全局变量 `g_race`，4 字节 | 案发现场直接点名到变量 |
| ⑤ | **背景**：T2 是谁创建的、在哪创建的 | 线程族谱，排查「这个线程哪来的」时用 |
| ⑥ | **SUMMARY** | 贴 issue 用这行 |

对照 3.0′ 的 ASan 四段式：**什么错（①）→ 谁和谁（②③）→ 争什么（④）→ 总结（⑥）**。
所有 sanitizer 的报告都是同一个骨架，读法一次学会处处通用。

## 两种「报告与结果」的组合，一张表记住

| 运行 | 结果 | 报告 | 教训 |
|------|------|------|------|
| `./c4_1 race`（gcc，无 TSan） | 100000（**错**） | 无 | 退出码/眼见都不可靠 |
| `./c4_1_tsan race`（clang+TSan） | 200000（**对**） | **data race** | 检查关系，不检查后果 |
| `./c4_1_tsan atomic`（对照组） | 200000 | **零报告** | C11 原子是 TSan 认可的同步——工具不冤枉好人 |

## 死锁：另一种「安静」的并发病

竞态是「抢着动」，死锁是「谁都不动」——程序活着但永远不推进。
`code/c4_2_deadlock.c` 用 AB-BA 模型演示（A 拿锁 1 等锁 2，B 拿锁 2 等锁 1），
并用一个看门狗线程**自己证明自己死了**：连续 3 轮心跳不变 + 两把锁都被占用
→ 环形等待成立，退出码 3（**主动判定退出，不是被杀**，和 134/139 区分开）。
gdb 侧的定位手法（`thread apply all bt`）是 [4.1 多线程调试](01-thread-debugging.md) 的内容。

**Q1:** 为什么 `counter++` 不是原子操作？两个线程同时执行它时丢失更新的机制是什么？

> `counter++` 编译后是三步：load（读到寄存器）→ add（加一）→ store（写回）。
> 两步之间没有任何保护，线程 A 读到 5 后还没写回，线程 B 也读到 5；
> A 写回 6，B 也写回 6——两次自增只生效一次，丢了一个更新。
> 窗口（load 与 store 之间）越宽越容易撞上；生产环境窗口窄，所以表现为「偶发」。
> 修法：mutex 串行化 / C11 atomic（lock xadd 一条指令）/ 每线程私有最后合并。

**Q2:** TSan 在「结果全对」的运行里依然报警，这为什么不误报？它的判定标准是什么？

> TSan 判定的是「竞争关系」：两个线程访问同一地址、至少一个是写、
> 且两次访问之间没有同步关系（happens-before 断裂）——与这次的实际后果无关。
> 结果对只是这次调度交错恰好没出错；关系存在就意味着存在某种交错会出错，
> 而生产环境的调度不由你控制。所以「结果对 + TSan 报警」必须修，
> 「结果错 + 无报告」才轮到别处找原因。

**Q3:** 为什么抓竞态不能靠「多跑几遍看结果对不对」？

> 三个理由：①竞态是否显形取决于调度交错，同一台机器可能连续对几千次，
> 换台机器/换个负载就错——测试通过不能推出没有竞态；
> ②显形窗口通常极窄（纳秒级），demo 要显式撑开窗口才能稳定复现；
> ③即使显形，「结果错」也不告诉你错在哪一行。
> TSan 把「赌调度」变成「查关系」：一次运行、无论结果对错，
> 只要存在无同步并发访问就指到源码行。

**Q4:** 竞态、死锁、崩溃三者的「症状画像」分别是什么？退出码各是什么形态？

> 竞态：进程正常跑完，退出码 0，**结果偶发不对**——靠 TSan；
> 死锁：进程活着但**永不推进**（心跳不动、CPU 可能为 0 或空转），
> 不会自己退出——靠 gdb `thread apply all bt` 或看门狗判定（demo 退出码 3 是主动判定）；
> 崩溃：进程被信号杀死，退出码 128+N（139/134/136）——靠 gdb/coredump。
> 三类问题三套取证工具，用退出码和「进程还在不在推进」做第一层分诊。

**Q5:** TSan 报告里 `#0 th_race example.c:104:16` 出现两次（T2 读、T1 写），说明什么？

> 同一代码行既被 T2 读又被 T1 写——两个线程跑的是同一个函数（th_race），
> 竞争的对象是这个函数里访问的共享变量（第 ④ 行点名的 g_race）。
> 这是多线程程序的典型形态：不是「两段不同的代码冲突」，
> 而是「同一份代码的多个执行实例」在共享数据上撞车。
> 修复点就落在 :104 这次访问上：给它配同步（mutex/atomic），
> 或把共享变量改成每线程私有。
