导读

🔴 精读 · 先分类问题，再选工具

调试的第一课不是「gdb 怎么用」，而是先判断你面对的是哪一类问题——因为问题类型直接决定了该上哪个工具。本章是 03.6 的「元层」（对应 05.6 的 Ch1-2 总论与方法概览），讲清「问题分类学 → 症状→工具决策 → 最小复现 → 调试元流程 → 工具链全链路」这条主线，后续 5 个问题类型章（崩溃/内存/并发/行为/性能）都从这里出发。

为什么调试要「方法论先行」

工具手册（gdb / strace / valgrind 的官方文档）教你「怎么用」，但不教你「遇到问题时该用哪个、按什么顺序」。这正是 LDD Ch4（Greg Kroah-Hartman 合著）把调试分成 Printing → Querying → Watching → System Faults → Debuggers 五类方法的原因：先分类，再选工具。

本模块后面 5 个问题类型章，每章开头都会先写一句「这一章解决什么症状」，让你从症状反查工具，而不是背完工具清单却不知道何时用。

HFT 关联

  • 快速分诊：生产环境报错时，先判断「崩了 / 内存涨了 / 结果时对时错 / 卡住 / 太慢」五选一，决定上 coredump / valgrind / TSan / strace / perf——比「上来就 gdb」高效得多；

1.1

问题分类学（崩溃 / 内存 / 并发 / 行为 / 性能）

🔴 精读 · 调试的第一步是「定性」

本节要点

调试最大的浪费是「用错工具」：拿着 gdb 查内存泄漏（gdb 不擅长），拿着 strace 查数据竞争（strace 看不到）。先给问题定性——它属于哪一类——再选工具，能省掉 80% 的瞎试时间。本节建立「五类问题」的分类学框架，它是本模块后续所有章节的索引。

五类问题总表

类别 典型症状 根因方向 第一工具 对应章节
崩溃 (crash) 段错误、SIGABRT、非法指令、栈破坏 野指针 / 越界写 / 栈溢出 / 除零 gdb + coredump Ch2
内存 (memory) 内存持续增长、偶发崩溃、值不对 泄漏 / 越界 / use-after-free / 未初始化读 valgrind / ASan Ch3
并发 (concurrency) 结果时对时错、偶发死锁、竞态 数据竞争 / 锁序错误 / 忘记加锁 TSan / gdb 多线程 Ch4
行为 (behavior) 卡住不动、调了不该调的、参数错 阻塞等 IO / 等锁 / 多余 syscall strace / ltrace Ch5
性能 (performance) 太慢、CPU 高、延迟毛刺 热点函数 / cache miss / 多余拷贝 perf Ch6

为什么「分类」是第一步

调试工具是按问题域设计的，每个工具只能「看见」某一类问题：

strace 只能看见 syscall ──→ 看不见内存越界、数据竞争
valgrind 只能看见内存 ────→ 看不见 syscall 时序、性能热点
TSan 只能看见数据竞争 ────→ 看不见内存泄漏
perf 只能看见性能 ────────→ 看不见逻辑错误

工具是「滤镜」，选错滤镜，问题就「隐身」了。所以流程必须是：症状 → 定性 → 选工具，而不是「先打开 gdb 再说」。

五类问题的「边界模糊区」

真实 bug 常跨类，要会识别主次：

现象 可能是哪几类？ 判断方法
偶发崩溃 崩溃 + 内存（UAF）+ 并发（竞态写坏） 先 coredump 看崩溃点，若崩溃点每次不同 → 怀疑内存/并发
结果时对时错 并发 + 内存（未初始化读） TSan 抓竞态；ASan 抓未初始化
卡住 行为（等 IO）+ 并发（死锁） strace 看停在哪：recvfrom 是等 IO，futex 是等锁
偶发段错误且只在多线程下 崩溃 + 并发 TSan 优先，因为竞态往往是崩溃的根因

经验法则：多线程程序里「偶发、难复现、位置漂移」的 bug，九成是并发或内存问题，不是逻辑问题——先上 TSan/ASan，别在 gdb 里死磕单线程现场。

分类学与 05.6 的对称

用户态五类问题，在内核态有精确对应（这正是 03.6 ↔ 05.6 对称的依据）：

问题类型 用户态工具 (03.6) 内核态工具 (05.6)

动手：把三类雷装进一个程序（实测）

分类学不用背，跑一遍就有体感。下面这份程序把「崩溃 / 内存 / 并发」三颗雷装在一起，用 argv 选：

/* code/c1_1_three_bugs.c 节选 */
static long g_orders_matched = 0;

static void *match_worker(void *arg)          /* 并发：非原子读改写 */
{
    long n = (long)arg;
    for (long i = 0; i < n; i++)
        g_orders_matched++;
    return NULL;
}

static int crash_null_deref(void)             /* 崩溃：解引用 NULL */
{
    struct order { long id; long qty; };
    struct order *o = NULL;

    printf("case 1: 准备解引用一个 NULL 订单指针\n");
    fflush(stdout);
    o->qty = 100;                             /* ← SIGSEGV 在这里 */
    return 0;
}

static int leak_orders(void)                  /* 内存：只借不还 */
{
    for (int i = 0; i < 100; i++) {
        char *fill = malloc(400);             /* 40000 B，全部未 free */
        if (!fill) return 1;
        memset(fill, 0, 400);
    }
    printf("case 2: 100 个 400 字节的订单快照已分配（全部未释放）\n");
    return 0;
}

完整源码见 code/c1_1_three_bugs.c（含 case 3 的双线程计数）。三种症状、三种编译方式，实测结果如下（gcc 13.3.0 / clang 18.1.0，基础参数 -g -O0 -Wall -Wextra）：

case 类别 编译方式 实测退出码 实测输出（关键行）
1 崩溃 裸编译 139 Program terminated with signal SIGSEGV (11)
2 内存 -fsanitize=address 1 ERROR: LeakSanitizer: detected memory leaks
Direct leak of 40000 byte(s) in 100 object(s) allocated from:
SUMMARY: AddressSanitizer: 40000 byte(s) leaked in 100 allocation(s).
2 内存 裸编译 0 case 2: 100 个 400 字节的订单快照已分配（全部未释放） ← 一声不吭
3 并发 clang -fsanitize=thread 66 WARNING: ThreadSanitizer: data race (pid=2)
Location is global 'g_orders_matched' of size 8 at 0x5555569dc658
3 并发 裸编译 0 case 3: 期望撮合 200000 笔，实际记到 200000 笔 ← 计数居然一分不差

三件事一眼可见：

  1. 退出码 = 128 + 信号号：SIGSEGV(11) → 139、SIGFPE(8) → 136。这是 shell 里判断「怎么死的」最快的办法（./prog; echo $?）。TSan 检出问题则用自己的约定 66。
  2. 内存类和并发类在裸编译下「完全正常」：case 2 退出 0 还打印了成功信息；case 3 的计数甚至 200000 分毫不差（竞争存在 ≠ 一定丢更新，这正是竞态「偶发」的物理来源）。「看起来没问题」不等于没问题——这就是这两类问题必须上专用工具的原因。
  3. 工具是分类学的执行者：同一份程序，-fsanitize=address 让它吐泄漏，-fsanitize=thread 让它吐竞态，裸编译让它一声不吭。「问题类型 ↔ 工具」的对应在这里是硬的。

⚠️ 踩坑提醒：并发那颗雷必须用 clang 的 TSan。gcc 13.3 的 TSan 在云编译环境（Compiler Explorer 容器）里直接起不来： text FATAL: ThreadSanitizer: unexpected memory mapping 0x7153d7872000-0x7153d7d00000 退出码也是 66，但没有任何 race 报告——看到这行 FATAL 要意识到「是环境不支持 ASLR 固定映射」，不是「程序没有竞态」。换 clang 立刻正常。

HFT 关联

  1. 分诊决定响应速度：交易进程在生产出问题时，第一句话先问「崩了 / 慢了 / 卡了 / 结果错了 / 内存涨了」——这五选一定位了该 dump core、上 perf、上 strace 还是上 TSan，而不是盲目重启掩盖问题。
  2. 并发与内存是 HFT 重灾区：多线程行情/下单程序里，竞态和 UAF 是最隐蔽、最致命的两类（偶发错单、偶发崩溃），分类学提醒你优先怀疑这两类。
  3. 行为类是「系统集成」的入口：链路不通、配置读错、端口没绑上，这类问题 stract 一眼可见，别上来就怀疑算法逻辑。
自测题（点击展开）

Q1: 为什么说「选错工具，问题就隐身了」？

因为调试工具本质是滤镜，每个工具只能观测特定问题域：strace 只看 syscall（看不见内存越界）、valgrind 只看内存（看不见 syscall 时序）、TSan 只看数据竞争（看不见泄漏）、perf 只看性能（看不见逻辑错误）。问题类型和工具观测域不匹配时，问题在工具视角下不存在，自然「隐身」。

Q2: 一个多线程程序「偶发段错误、每次崩溃点不同」，最该先怀疑哪类问题？为什么？

优先怀疑并发（或内存）。「偶发、难复现、崩溃位置漂移」是多线程竞态的典型签名——多个线程写同一块内存没加锁，谁先写坏、写到哪不确定，所以崩溃点随机。逻辑 bug 通常是「稳定、可复现、固定位置」。这种情况先上 TSan 抓竞态，比在 gdb 里单步死磕高效。

Q3: 进程「卡住不动」，可能属于哪两类？怎么区分？

可能是行为类（阻塞等 IO）或并发类（死锁等锁）。用 strace attach 看最后停在哪：停在 recvfrom/read 是等网络/文件数据（行为类，查对端）；停在 futex(...FUTEX_WAIT...) 是等锁（并发类，查锁序）。两者排查方向完全不同。

Q4: 「分类学」和「工具清单」的学习顺序应该是什么？为什么？

应该先学分类学、再学工具。因为分类学是「地图」，告诉你有哪些问题类型、每种该往哪走；工具清单是「路标」，具体教某条路怎么走。没有地图，路标再多也不知道该去哪个。这就是本章（Ch1 方法论）放在所有工具章前面的原因。

Q5: 上面实测里 case 3 的计数是 200000，一分不差，为什么 TSan 却报 data race？「结果对」能证明「没有 bug」吗？

不能。g_orders_matched++ 在机器层面是「读 → 加 → 写」三条指令，两个线程可能交错成「都读到 N，都写回 N+1」，丢更新。但丢不丢取决于当时的交错——两次运行都是 200000，只说明这两次恰好没交错到丢失的那一步（10 万次循环里窗口极小）。TSan 看的是有没有形成竞争的内存访问对（Location is global 'g_orders_matched'），与「这次恰好有没有丢」无关。所以竞态是「偶发」的：裸编译下表现为 99.99% 正常 + 0.01% 错单，这才是它在 HFT 里最可怕的地方。

1.2

症状 → 工具决策树

🔴 精读 · 从「我看到的」到「我该用的」

本节要点

分类学（1.1）给了你「五类问题」，但实战中你面对的不是分类标签，而是具体症状：「它段错误了」「它内存一直涨」「它结果有时对有时错」。本节把「症状」翻译成「工具选择」，给出一棵可照做的决策树——这是新手和老手之间最大的差距：老手不是更会背命令，而是更会从症状一步跳到正确工具。

症状 → 工具决策树

程序出问题了
│
├─ 崩溃（段错误 / SIGABRT / 非法指令）
│   ├─ 能复现？ ──是──→ gdb 直接跑，崩溃点设断点（Ch2）
│   └─ 生产偶发 ──────→ 开 core，gdb prog core 回溯（Ch2）
│
├─ 内存持续增长 / 偶发崩溃 / 值莫名变
│   ├─ 怀疑泄漏 / 越界 / UAF
│   │   ├─ 开发期 → valgrind memcheck（Ch3，准但慢）
│   │   └─ 要速度 → ASan 重编译（Ch3，快、需重编）
│   └─ 未初始化读 / UB → UBSan（Ch3）
│
├─ 结果时对时错 / 偶发死锁（多线程）
│   ├─ 数据竞争 → TSan（Ch4，开发期）
│   ├─ 死锁 → gdb attach + thread apply all bt（Ch4）
│   └─ 难复现竞态 → rr 录像回放（Ch4）
│
├─ 卡住不动 / 行为不对 / 调了不该调的
│   ├─ 卡住 → strace -p 看停在哪（Ch5）
│   ├─ 调了什么 syscall → strace（Ch5）
│   └─ 调了什么库函数 → ltrace（Ch5）
│
└─ 太慢 / CPU 高 / 延迟毛刺
    ├─ 热点函数 → perf record + report（Ch6）
    └─ 深入系统级 → 06.6 Systems Performance

核心决策口诀

症状 第一反应 一句话理由
崩了 coredump / gdb 崩溃现场是唯一硬证据，先拿 bt
内存涨 valgrind 泄漏只有它能精确定位到分配点
时对时错 TSan 竞态是「偶发」的头号嫌疑
卡住 strace -p 一行就能看到停在哪、等什么
太慢 perf 采样直接给出热点，不猜

反模式：所有问题都「先上 gdb 单步」。gdb 擅长「崩溃现场回溯」和「单线程逻辑」，但对「内存泄漏」（要跑很久看趋势）、「数据竞争」（要并发复现）、「性能热点」（要统计采样）都很吃力——这些问题有更对口的工具。

「偶发」是决策树里最关键的分支

「偶发」二字会彻底改变工具选择：

问题属性 崩溃类 内存类 并发类
稳定可复现 gdb 单步即可 valgrind 跑一次即出 gdb 断点即可
偶发难复现 必须开 core 抓现场 长时间跑 + ASan TSan 全量重编 / rr 录像

稳定 bug 靠「打断点定位」，偶发 bug 靠「抓现场 + 全量检测」。前者是 gdb 的主场，后者是 core/ASan/TSan/rr 的主场。先判断偶发性，再选工具，能少做大量无用功。

动手：踩一遍决策树的四个分支（实测）

光看树不会用，走一遍才长记性。用 Ch1 的两份 demo（code/c1_1_three_bugs.c、code/c1_2_shrink_demo.c），把决策树的四个分支各踩一次，看症状 → 你看到的 → 选哪个工具 → 工具吐什么：

症状（你看到的） 决策树走法 实测命令 工具吐出的关键行
进程死了，echo $? = 139 崩溃分支 → 拿 bt gcc -g -O0 -o b c1_1_three_bugs.c -pthread && ./b 1 Program terminated with signal SIGSEGV (11)
进程死了，echo $? = 136 崩溃分支，但信号是 SIGFPE → 先看算法有没有除零 ./c1_2_shrink_demo < ticks_10.txt 前 6 条正常，第 7 条打出 ts=7 vol=0 turnover=10700 后死
跑得好好的，echo $? = 0 不在这棵树上 → 但内存可能有问题，换 ASan 重编 gcc -g -O0 -fsanitize=address -o b c1_1_three_bugs.c -pthread && ./b 2 Direct leak of 40000 byte(s) in 100 object(s)
跑得好好的，echo $? = 0，结果也对 同上 → 怀疑并发，换 TSan 重编 clang -g -O1 -fsanitize=thread -pthread -o b c1_1_three_bugs.c && ./b 3 WARNING: ThreadSanitizer: data race

三点从实测里读出来的结论：

  1. 退出码是决策树的第一个路标。echo $? 一个数字就把「崩溃类（128+N）」和「非崩溃类（0/1）」分开了。139/136/134 分别对应 SIGSEGV/SIGFPE/SIGABRT——不用 gdb 就能知道「怎么死的」。
  2. 「正常退出」是决策树里最危险的岔口。后面两个分支（内存、并发）症状全都是「看起来正常」：exit 0、结果正确。所以新手最容易卡在这里——按照「没崩就不用查」的直觉，这两类 bug 永远查不出来。
  3. 同一条命令换个开关，就是另一棵树。-fsanitize=address 和 -fsanitize=thread 是把「正常的程序」变成「有症状的程序」——决策树里那些「要重编译」的分支，本质是在人为制造症状。

gcc -g -O0 -fsanitize=address -pthread -o b_asan c1_1_three_bugs.c
clang -g -O1 -fsanitize=thread -pthread -o b_tsan c1_1_three_bugs.c
for c in 1 2 3; do
  echo "--- case $c ---"
  ./b0 $c;     echo "  plain: exit=$?"
  ./b_asan $c; echo "  asan : exit=$?"
  ./b_tsan $c; echo "  tsan : exit=$?"
done

这份脚本就是「决策树自动化」：把三类问题各配一个专用构建，一次跑完，谁有问题谁非零退出。HFT 团队 CI 里的 -asan / -tsan 双构建，本质就是它。

HFT 关联

  1. 生产偶发崩溃 → 必须先开 core：交易进程 7×24 跑，崩溃不可复现，唯一证据是 core。上线前必须配好 ulimit -c + core_pattern（见 Ch2），否则崩溃了连现场都没有。
  2. 延迟毛刺 → 先 perf 采样，别猜：「某天某笔单延迟 250ms」这种毛刺，靠读代码猜热点几乎不可能，perf 采样 + 火焰图直接定位（见 Ch6）。
  3. 偶发错单 → 并发优先：下单结果偶发不对，第一嫌疑是竞态（多线程共享订单状态没锁好），上 TSan 而非逐行读代码。

Q1: 「偶发性」为什么是决策树里最关键的分支？

因为偶发性直接决定工具选型：稳定 bug 可以打断点、单步、跑一次复现（gdb 主场）；偶发 bug 打不到断点、跑一次不复现，必须靠「抓现场」（core dump）+「全量检测」（ASan/TSan 重编译）+「录像回放」（rr）。用对付稳定 bug 的方法（gdb 单步）去查偶发 bug，基本是白费劲。

Q2: 为什么「所有问题都先上 gdb 单步」是反模式？

因为 gdb 只擅长「崩溃现场回溯」和「单线程逻辑定位」，对内存泄漏（要长跑看趋势）、数据竞争（要并发复现）、性能热点（要统计采样）都很吃力。这些有更对口的工具：valgrind / TSan / perf。工具不匹配时，gdb 单步既慢又看不到问题。

Q3: 生产环境「偶发段错误」，第一步该做什么？为什么不是立刻 gdb attach？

第一步是确认 core dump 已开启（ulimit -c + core_pattern），让下一次崩溃能落盘。因为偶发崩溃无法预知何时发生，gdb attach 来不及（崩溃瞬间进程就没了），core 是唯一能事后拿到的现场。没有 core，偶发崩溃基本无解。

Q4: 「卡住」和「太慢」都表现为「程序没反应」，怎么快速区分该上 strace 还是 perf？

看是不是永久卡住：如果进程「永久不动」（等一个永远不会来的事件），是行为/并发问题，用 strace -p 看它停在哪（等 IO 还是等锁）；如果进程「还在跑但慢」（CPU 有活动、只是吞吐低），是性能问题，用 perf 采样找热点。「永久卡住」和「缓慢推进」是两类完全不同的病。

Q5: 一个程序 exit code 是 0、输出结果也正确，能不能收工不查了？决策树怎么处理这种情况？

不能。决策树里「正常退出」恰恰是最危险的岔口：内存类（泄漏、越界写、UAF）和并发类（数据竞争）在裸编译下症状就是「一切正常」——实测里 c1_1_three_bugs.c 的 case 2 退出 0 且打印成功信息，case 3 计数 200000 一分不差。处理办法是主动换分支：怀疑内存就 -fsanitize=address 重编，怀疑并发就 -fsanitize=thread 重编。这两类只能靠「人为制造症状」，等不到自然暴露。

1.3

最小可复现与二分定位

🔴 精读 · 复现是第一生产力，二分是最高效的定位

本节要点

「能复现的 bug 已经死了一半」。调试的一半时间其实花在把 bug 缩小到最小可复现用例（minimal reproducer）上——它越简、越小、越稳定，定位越快。另一半时间花在二分定位上——把「嫌疑范围」每次砍半，而不是一行行读。本节讲这两件「方法论层面最值钱」的事。

为什么最小复现是第一生产力

有最小复现 没有最小复现
改动一次、复现一次，1 秒验证 每次验证要跑完整流程，几十分钟
可以交给工具（gdb/ASan/TSan）自动跑 工具跑不动、太慢
可以缩小到单线程、单文件 多线程/多模块干扰，无法隔离
可以留着做回归测试 bug 修了没法验证，容易复发

交易系统里一个 bug 可能藏在「行情 → 策略 → 风控 → 下单」整条链路里。能把它缩小到「一个函数 + 一段假行情」，你就从「在大海里捞针」变成「在鱼缸里捞针」。

如何缩小（shrink）复现

四步，从外到内逐层砍：

// 原始：完整下单程序，几百行，多线程
// 目标：几十行，单线程，稳定触发 bug

// 1. 砍输入：用固定假数据代替真实行情/网络
//    真实 socket 读 → 直接喂一个 struct 数组

// 2. 砍线程：多线程 → 单线程（能复现就砍，不能则保留最小线程数）
//    3 个 worker → 1 个

// 3. 砍功能：删掉无关模块（日志、配置、指标上报）
//    if (logging) ...  整个删掉

// 4. 砍代码：删掉不影响复现的语句，逐行删

# 每砍一步，立刻验证「bug 还在不在」
gcc -g -O0 -o repro repro.c && ./repro
# 复现成功 → 继续砍；不复现 → 刚砍掉的部分是关键，回退

砍掉后 bug 消失 = 刚砍的部分参与制造 bug。这个「保留 bug 的前提下做减法」的过程，本身就在帮你逼近根因。

二分定位：每次砍半，别一行行读

「二分」是计算机科学最高效的搜索策略，调试同样适用：

1. 代码二分（缩小到可疑区间）

怀疑 100 行代码里有 bug
  └─ 注释掉中间 50 行 → bug 还在？ ──是──→ 嫌疑在前 50 行
                                      └─否──→ 嫌疑在后 50 行
  └─ 再砍 25 行…… 100 → 50 → 25 → 12 → 6 → 3 → 1
  （7 步定位到 1 行，而不是读 100 行）

2. git bisect（定位「哪次提交引入」）

# bug 在历史某次提交引入，当前已知坏了，某旧版本已知是好的
git bisect start
git bisect bad HEAD            # 当前版本是坏的
git bisect good v1.0           # v1.0 是好的
# git 自动切到中间提交，你编译验证后标记：
git bisect good   # 或 git bisect bad
# 反复几次，git 收敛到「引入 bug 的那一次提交」
git bisect reset

3. 数据二分（定位是哪个输入触发）

# 1000 条行情数据里某一条触发崩溃
# 二分喂入：喂前 500 条 → 崩？ 喂后 500 条 → 崩？
# 500 → 250 → 125 → ... → 1 条
# 10 步定位到具体哪条数据，而不是跑 1000 次

二分的前提：bug 必须是「可判定」的

二分定位有个隐藏前提——你必须能自动、快速地判断「这个版本是好是坏」：

前提 说明 反面教材
可自动判定 脚本能跑出 pass/fail 「肉眼观察有没有闪」→ 不可靠
判定快 秒级 每次跑 30 分钟 → 二分没意义
判定稳定 同输入同结果 偶发 bug 判定会抖 → 先想办法稳定复现

偶发 bug 无法直接二分，因为它「判定不稳定」。这时要先想办法把它变稳定（缩小 + 提高触发频率 + rr 录像），再二分。

动手：把「缩小复现」和「数据二分」真跑一遍（实测）

方法论光看是记不住的，下面用两份 demo 把上面的四步砍法和二分亲手走一遍。

第一步：造一个「只在特定记录上炸」的复现

code/c1_2_shrink_demo.c —— 读一批行情，对每条算均价 = 成交额 / 成交量，其中有一条成交量是 0：

/* code/c1_2_shrink_demo.c 节选 */
struct tick { long ts_ms; long volume; long turnover; };

while (scanf("%ld %ld %ld", &t.ts_ms, &t.volume, &t.turnover) == 3) {
    seq++;
    printf("record %ld: ts=%ld vol=%ld turnover=%ld\n",
           seq, t.ts_ms, t.volume, t.turnover);
    fflush(stdout);                     /* ← 关键：让「崩在第几条」肉眼可见 */

    long vwap = t.turnover / t.volume;  /* vol == 0 → 除零 */
    printf("            vwap = %ld\n", vwap);
}

两个设计要点值得学：① 每条处理前先打印进度（否则崩了不知道崩在哪）；② 输入走 stdin（这样「砍输入」是写文件，不是改代码——这正是后面能自动二分的物理基础）。

输入 code/ticks_10.txt（10 条，第 7 条 volume = 0）：

1  100  10100
2  100  10200
...
7  0    10700      ← 雷在这里
8  100  10800
...
10 100  11000

实测（gcc 13.3.0 -g -O0 -Wall -Wextra，退出码 136 = 128 + SIGFPE(8)）：

            vwap = 102
record 3: ts=3 vol=100 turnover=10300

第二步：砍输入——10 条 → 1 条（实测）

按 1.3 的四步砍法，这里只需要砍输入（代码已经是最小形态）。两次实测：

输入 条数 实测退出码 实测输出 结论
ticks_first6.txt（前 6 条，全好） 6 0 全部 6 条记录处理完毕，未触发问题 bug 消失 → 第 7 条是关键
ticks_only_bad.txt（只留第 7 条 → 1 0 10700） 1 136 record 1: ts=1 vol=0 turnover=10700 后 SIGFPE 最小复现：1 条记录

从 10 条砍到 1 条，bug 依然稳定复现——这就是「最小可复现用例」。它现在小到可以贴进 issue、可以交给任何工具自动跑、可以直接写进回归测试：

# 最小复现固化成回归测试（crash → 非零退出）
echo '1 0 10700' | ./c1_2_shrink_demo > /dev/null 2>&1
test $? -eq 0 && echo "PASS" || echo "FAIL: 仍会除零崩溃"   # → FAIL

「砍掉后 bug 消失 / 只剩一条还崩」这个减法过程本身就在定位根因——你已经知道问题出在「volume = 0 的那条行情」，接下来只需去修 vwap 的除法，不用读整个链路。

第三步：数据二分——把「找哪条」写成程序（实测）

人肉二分会累、会抄错区间。code/c1_3_auto_bisect.c 把二分写成程序，16 条记录 4 步收敛。它有三个可直接观察的点：

/* code/c1_3_auto_bisect.c 节选 */
static sigjmp_buf g_jmp;

static void on_sigfpe(int sig)              /* 把「崩了」变成可返回的信号 */
{
    (void)sig;
    g_caught = 1;
    siglongjmp(g_jmp, 1);
}

static int batch_ok(int lo, int hi)         /* 判定函数：必须纯布尔 */
{
    if (sigsetjmp(g_jmp, 1) != 0)
        return 0;                           /* 从 SIGFPE 跳回来 = 这一批坏 */

    for (int i = lo; i <= hi; i++) {
        volatile long vol  = volume_of(i);  /* volatile 逼编译器真做除法 */
        volatile long turn = turnover_of(i);
        volatile long vwap = turn / vol;    /* ← 命中坏记录才除零 */
        (void)vwap;
    }
    return 1;
}

实测输出（退出码 0）：

共 16 条记录，先确认「整批是坏的」
  判定 [0, 15] -> BAD
开始二分（每次砍半）：
  第 1 步: [ 0,  7] good  -> 嫌疑落在右半 [ 8, 15]
  第 2 步: [ 8, 11] BAD   -> 嫌疑落在左半 [ 8, 11]
  第 3 步: [ 8,  9] good  -> 嫌疑落在右半 [10, 11]
  第 4 步: [10, 10] good  -> 嫌疑落在右半 [11, 11]
收敛：坏记录是第 12 条（下标 11）—— 16 条记录共 4 步，因为 log2(16) = 4
该记录 volume = 0，turnover = 1011 —— 除零的根因就在这里

对照 1.3 的三条前提，这份程序一条不落地满足了：

前提 在这份程序里怎么落地
可自动判定 batch_ok(lo, hi) 返回 1/0，不需要人看输出
判定快 一批最多 16 次除法，微秒级
判定稳定 同样的区间每次必得同样结果（volume 是纯函数）

sigsetjmp 这个技巧值得记住：正常业务代码不会把「进程崩了」当返回值用，但在构建自动判定器时它是标准做法——把 SIGFPE（或 SIGSEGV）抓成布尔值，二分循环就能在一个进程内跑完，不用 fork 16 个子进程。生产上等价的做法是「跑一遍测试脚本看退出码」。

还有个小反直觉点：整数除零在 Linux 上发的是 SIGFPE（名字叫 Floating-Point Exception）——「浮点异常」这名字是历史遗留，整数除零、整数溢出都走它。别被名字骗了。

HFT 关联

  1. 复现 = 破案关键：交易所/券商报一个「偶发错单」，你第一时间要做的不是读代码，而是想办法在本地复现——用当天的行情数据回放（replay），缩小到最小触发序列，否则连问题都看不见。
  2. 回放系统就是「复现基建」：HFT 团队都建行情/订单回放系统，本质就是为了把「生产偶发 bug」变成本地「稳定可复现 bug」，是调试效率的倍增器。
  3. git bisect 定位回归：性能回退或行为回归，git bisect 能自动锁定引入的提交，比逐次手动 checkout 高效得多。

Q1: 为什么说「能复现的 bug 已经死了一半」？

因为复现是调试的前提：能稳定复现，就能（1）快速验证每一次修复是否有效，（2）缩小到最小用例隔离干扰，（3）交给 gdb/ASan/TSan 等工具自动跑，（4）留作回归测试防止复发。不能复现，这些都做不了，只能靠猜。所以「先复现」是调试的第一优先级。

Q2: 缩小复现时，「砍掉某部分后 bug 消失」说明了什么？下一步怎么做？

说明刚砍掉的那部分参与制造了这个 bug（可能是根因本身，也可能和根因有依赖）。下一步：把刚砍掉的部分加回来，继续在其中做更细的「二分」，逐层逼近真正的根因。这个「保留 bug 做减法」的过程本身就在定位。

Q3: git bisect 的机制是什么？它比手动 checkout 快在哪？

它是二分搜索：你标记「当前坏」和「某旧版本好」，git 自动切到两者中间的提交让你验证，根据你标 good/bad 再切到剩下区间中点，反复对数次就收敛到引入 bug 的那次提交。快在「每次砍半」：1000 个提交只需约 10 次验证，而不是线性试 1000 次。

Q4: 为什么「偶发 bug」不能直接二分定位？要先做什么？

因为二分要求「判定稳定」——同一版本每次验证结果一致。偶发 bug 时好时坏，判定会抖，二分区间就切错了。必须先把它变稳定：缩小用例、提高触发频率（循环多跑）、或用 rr 录像回放固定时序，让它变成「稳定可复现」，再二分。

1.4

调试元流程（假设 → 验证 → 收敛）

🔴 精读 · 调试不是「试错」，是「科学方法」

本节要点

新手调试是「改一处、跑一下、看结果」，老手调试是「提出假设 → 设计验证 → 收敛范围」的循环。前者是随机试错（试 10 次可能碰巧对 1 次），后者是科学方法（每步都让嫌疑范围变小）。本节讲这个「元流程」——它是《Writing Solid Code》反复强调的核心，也是区分「碰运气」和「系统排查」的分水岭。

调试元流程：四步循环

  ┌─────────────────────────────────────────────┐
  │                                             │
  ▼                                             │
① 观察现象（崩溃栈 / 错误值 / 卡住位置）          │
      │                                         │
      ▼                                         │
② 提出假设（「可能是 X 没初始化」）              │
      │                                         │
      ▼                                         │
③ 设计验证（断点 / 打印 / 工具观测，检验假设）     │
      │                                         │
      ├── 假设成立 → ④ 缩小范围，回到②继续        │
      │              （或直接定位根因，结束）     │
      │                                         │
      └── 假设不成立 → 修正假设，回到②            │
                                                │
  （循环直到根因被证实，而非「碰巧能跑」）          └─┘

核心特征：每一步都有「假设」和「验证」，而不是「无目标地改」。

对比：试错 vs 科学方法

维度 随机试错 科学方法
行动 改一处、跑一下 先想「如果假设成立，应该观察到什么」
依据 「感觉像这里」 「证据指向这里」
失败后 换一处再试 修正假设，缩小嫌疑范围
收敛性 不保证（可能绕圈） 保证（每次验证都排除一批）
终点 「能跑了，不管为什么」 「根因被证实，且知道为什么」

⚠️ 「碰巧能跑」是最危险的终点。改了之后 bug 消失了，但如果你不知道为什么消失，很可能只是把症状掩盖了、时序改变了，bug 还在暗处等着复发。调试的终点是「根因被证实」，不是「现象消失」。

三个高频陷阱

1. 确认偏误（confirmation bias）

「我怀疑是 A 的问题」，于是只找支持 A 的证据，忽略反例。

错误示范：怀疑是锁的问题 → 加了把锁 → bug 暂时没出现 → 结论「就是锁」
正确做法：加锁后 bug 没出现，还要问「是锁修好了，还是时序变了导致 bug 藏起来了？」
         → 用 TSan 证实确实有数据竞争，才算证实「是锁的问题」

2. 一次改多处（失去因果）

// 错误：一次改了 3 处，bug 好了，但不知道是哪处起作用
buf = malloc(n + 1);   // 改 1：+1
memset(buf, 0, n);     // 改 2：清零
free(buf);             // 改 3：加 free

// 正确：一次只改一处，验证后再改下一处

一次改多处，即使 bug 好了，你也没学到任何东西——不知道哪处是根因，下次同类 bug 还得从头试。

3. 改症状不改根因

// 症状：偶发段错误，崩溃在 strcpy
// 错误做法：在 strcpy 前加 if (src == NULL) return;  ← 掩盖症状
// 正确做法：追为什么 src 会是 NULL → 发现是竞态导致指针被提前 free
//          → 修锁/生命周期，而非加 NULL 判断

日志 / 断点 / 打印：三种验证手段怎么选

验证「假设是否成立」有三种手段，各有适用场景：

手段 适用 代价 局限
打印/日志 快速看「执行到没、值是什么」 改代码 + 重编译 加太多干扰时序、污染性能
断点 精确停在某行看现场 无需重编译（attach） 打断点影响并发时序
工具观测 strace/valgrind/TSan 自动检测 无需改代码 各有观测域（见 1.1）

原则：先用工具观测（零侵入），不够再用断点，最后才加打印。打印是「最后手段」，因为它要改代码、重编译、还可能改变时序（尤其并发 bug）。

动手：一个假设被证伪的全过程（实测）

上面讲的是道理，下面走一遍真实的循环。这个例子的价值在于：第一个假设是错的，而且错得很典型——它是「人人都信的常识」。

① 观察现象

写一份探针 code/c1_4_hypothesis_div.c，三种除零写法各跑一次：

static volatile int g_zero = 0;
static volatile int g_one  = 1;

if (argv[3][0] == 'A') {          /* A: 常量分子 / volatile 除零 */
    int c = 1 / g_zero;
    printf("A: 1 / volatile-zero = %d\n", c);
} else if (argv[3][0] == 'B') {   /* B: 两个 volatile */
    int c = g_one / g_zero;
    printf("B: volatile-one / volatile-zero = %d\n", c);
} else {                          /* C: argv 传来的运行时值 */
    int c = a / b;
    printf("C: %d / %d = %d\n", a, b, c);
}

gcc 13.3.0 -g -O0 -Wall -Wextra 实测：

$ ./c1_4_hypothesis_div 1 0 A
A: 1 / volatile-zero = 0
没有崩，正常退出
$ echo $?
0

$ ./c1_4_hypothesis_div 1 0 B
Program terminated with signal SIGFPE (8)
$ echo $?
136

$ ./c1_4_hypothesis_div 1 0 C
Program terminated with signal SIGFPE (8)
$ echo $?
136

A 没崩。 退出码 0，还打印了 = 0。

② 提出假设（H1）

H1：整数除零是 UB，UB 会发 SIGFPE 终止进程。三个写法都应该是 136。

③ 设计验证

如果 H1 成立，A/B/C 三次运行的退出码应该全是 136。实测 A = 0。

假设不成立 → 修正假设

H1 被证伪了。 注意这里最容易犯的错：「可能是我哪里写错了 / 再跑一次试试 / 大概是编译器 bug」——这都是拒绝修正假设。正确的动作是：信数据，改假设。

那 A 和 B 的差别在哪？逐字对比：

分子 分母 实测
A 字面量 1 volatile int g_zero 不崩，打出 0
B volatile int g_one volatile int g_zero SIGFPE
C argv 运行时值 a argv 运行时值 b SIGFPE

唯一的结构差别是分子是不是编译期已知的常量。于是修正假设：

H2：当分子是编译期常量时，gcc 会把 1 / x 折成一段不含除法指令的等价序列；只有两个操作数都是运行时值时才真的生成 idiv，才可能发 SIGFPE。

④ 验证 H2：去看汇编

假设 H2 是可证伪的、且能直接观测的——去看 A 和 B 生成了什么指令。用 -S 或编译器浏览服务取汇编（-O0，节选）：

div_const_numerator:            ; 对应 A：1 / z
        mov     eax, DWORD PTR z[rip]
        mov     edx, eax
        add     edx, 1
        cmp     edx, 2
        setbe   dl
        mov     ecx, 0
        test    dl, dl
        cmove   eax, ecx
        pop     rbp
        ret                     ; ← 整段里没有一条 idiv

div_two_volatiles:              ; 对应 B：one / z
        mov     eax, DWORD PTR one[rip]
        mov     ecx, DWORD PTR z[rip]
        cdq                     ; 把 eax 符号扩展到 edx:eax
        idiv    ecx             ; ← 真除法：ecx == 0 → #DE → SIGFPE
        pop     rbp
        ret

H2 被证实：A 那段汇编里一条 idiv 都没有，全是比较和条件搬移，所以它永远不会触发 #DE（除零异常）——它「算出」的 0 只是这段无分支序列对「除数为 0」这种 UB 输入的任意产物。B 才有 idiv。

⑤ 收敛：这条循环教了什么

环节 本例中的具体动作
观察 1 / volatile-zero 打印 0 且 exit 0（不是 SIGFPE）
假设 H1 「除零都发 SIGFPE」——来自日常经验的常识
验证 H1 三种写法跑一遍 → A = 0，H1 死
修正 H2 「常量分子会被折成不含除法的序列」
验证 H2 取汇编 → A 无 idiv、B 有 idiv → H2 活
收敛 结论 = 「整数除零是否崩，取决于编译器有没有生成除法指令」——UB 不是「一定崩」，是「没有保证」

对照 1.4 的三个陷阱，这次循环恰好绕开了全部三个：

  1. 没有确认偏误：H1 被实测打脸时，信数据而不是信直觉（没有「再跑一次看看」）。
  2. 一次只改一处：A/B/C 是三个独立变体，不是「改了 A 又改 B」——每个变体只变化一个维度（分子是不是常量），所以能干净地归因。
  3. 没有改症状：没有人去「在除法前加 if (z == 0) return;」把症状盖掉——那是掩盖 UB，不是修它（正确做法见 3.3 的 __builtin_add_overflow 一节）。

这条经验比结论本身更重要：调试中最贵的不是「不会用 gdb」，而是实测结果和你的假设冲突时，你选择怀疑数据。UB 的整个「隐形」性格（见 3.3）就建立在这个反直觉性上——UB 的典型表现恰恰是「不崩、还给你一个看起来合理的数」。

HFT 关联

  1. 「碰巧能跑」在交易系统里是灾难：改了时序、加了条日志，竞态暂时不出现了，你上线后它照样偶发错单。必须用 TSan/ASan 证实根因，而不是「看起来好了」。
  2. 一次改一处：交易逻辑高度耦合，一次改多处会让「到底哪处修的」不可知，出问题没法回滚定位。
  3. 工具零侵入优先：生产环境排查优先 attach/strace/perf（不动代码、不改时序），而不是加打印重编译——延迟敏感系统里，加打印本身就会引入新的竞态和延迟。

Q1: 「随机试错」和「科学方法」的本质区别是什么？

本质区别在有没有「假设 + 验证」：试错是「无目标地改一处看结果」，失败后换一处再试，不保证收敛；科学方法是「先提出假设 → 设计验证（如果假设成立应该观察到什么）→ 用证据证实或证伪 → 缩小范围」，每次验证都排除一批嫌疑，保证收敛。前者碰运气，后者可复现地逼近根因。

Q2: 为什么「碰巧能跑」是最危险的调试终点？

因为「现象消失」≠「根因解决」：改了之后 bug 不出现，可能只是时序改变、症状被掩盖，根因还在暗处。上线后环境一变，bug 照样复发，甚至更隐蔽。调试的终点必须是「根因被证实」（用工具/证据证明是它），而不是「看起来好了」。

Q3: 「一次改多处」为什么是坏习惯？

因为失去了因果判断：三处一起改，bug 好了，你不知道是哪一处起的作用，等于没学到任何东西，下次同类 bug 还得从头试。正确做法是一次只改一处、验证后再改下一处，每步都建立明确的因果。

Q4: 验证假设的手段（打印/断点/工具观测）应该按什么顺序选？为什么？

应该先工具观测（零侵入）→ 不够再断点 → 最后加打印。因为工具（strace/valgrind/TSan）不用改代码、不改时序；断点要 attach 但会扰动并发时序；打印最重——要改代码、重编译、还可能改变时序（尤其并发 bug，加打印往往让竞态「消失」）。所以打印是最后手段。

Q5: 上面「假设被证伪」的例子里，H1 错在哪？为什么说「信数据、改假设」比「再跑一次试试」重要？

H1 错在把「UB」等同于「一定崩」。UB 的真实含义是「没有任何保证」——编译器可以（并且确实会）基于「除数非零」的假设，把 1 / 常量分母 折成一段不含 idiv 的序列，于是既不崩也不报错。这类「实测打脸直觉」的时刻是调试的分水岭：「再跑一次试试」属于拒绝修正假设（若结果是稳定可复现的，重跑不产生新信息）；正确动作是信数据，把假设改成能被观测证伪的 H2（「常量分子不生成除法指令」），然后去汇编里找证据。

从源码到断点：gcc -g / gdb / strace 全链路

🔴 精读 · 把三个零件串成一条线

本节要点

1.1–1.4 回答「遇到什么问题、用什么工具、怎么系统收敛」，Ch2–Ch6 逐个讲工具怎么用。但两者之间缺一根轴：一段 C 代码从敲下 gcc -g 到被 gdb 断住，中间到底发生了什么？工具手册不会替你把这一步串起来——本节就是这根轴。走完这条链路你会发现：所谓调试工具，不过是在编译期埋下的一张映射表上做文章；gdb 和 strace 看似两类工具，其实踩在同一个系统调用（ptrace）上。

源码 .c ──gcc -g──▶ ELF（.text + DWARF 映射表）
                        │                │
        gdb 读表 ◀──────┘                └── strace 不读表（只拦 syscall）
        break 20 → 查表得地址 → 写入 int3 → CPU 停住 → bt 反向查表译回源码行

① 构建期：-g 埋的不是"信息"，是"映射表"

编译器默认不往二进制里写调试信息——那会让体积膨胀、还泄露源码结构。-g 的作用是让编译器额外生成 DWARF 格式的调试数据。对调试最有用的是两张表：

DWARF 段 内容 gdb 拿它干什么
.debug_line 地址 ↔ 源码行号/列号 逐条映射 break file.c:20 把行号译成地址；bt 把地址译回行号
.debug_info 变量名/类型 ↔ 存放位置（寄存器/栈偏移） p qty 按名字找到那个变量当前在哪

用本章标本程序 code/c1_5_pipeline.c（30 行，apply_fee + main）实测一遍。实测环境：Apple M1 / macOS 26.6 / clang 23.1.0（Mach-O arm64）：

产物 体积 说明
不带 -g 50,040 B 纯机器码
带 -g 50,424 B（仅 +384 B） macOS 特例：链接器不内嵌 DWARF，只嵌一张 OSO 调试映射表，指向 .o 文件
dsymutil 后的 .dSYM 9.3 KB 完整 DWARF 落盘在这里，38 条行号映射

⚠️ 平台差异是这条链路上最容易踩的坑：Linux/ELF 下 gcc -g 把 .debug_* 段直接嵌进可执行文件（2.1 节实测 0 个 vs 9 个段）；macOS/Mach-O 下 -g 后的可执行文件里并没有 DWARF，要 dsymutil 把各 .o 的调试信息收拢成 .dSYM 包（所以 macOS 调试必须在编链接的同一台机器、保留 .o 或 dSYM，否则 gdb/lldb 看到的就是裸地址）。线上符号归档同理：二进制 + 调试符号必须成对留档（2.5 节会再强调）。

llvm-dwarfdump --debug-line 把那张表摊开给你看（节选，完整 38 条）：

Address            Line   Column File   Flags
------------------ ------ ------ ------ ------------------
0x0000000100003efc     20     27    1   is_stmt            ← main 第 20 行：调用 apply_fee
0x0000000100003f40     13     20    1   is_stmt prologue_end ← apply_fee 第 13 行：算 notional

这两行就是后面一切"魔法"的物理载体：gdb 说"停在 20 行"，本质是"停在 0x100003efc"。没有 -g，这张表根本不存在——这就是 1.2 决策树里"想源码级调试，第一步永远是重编 -g"的原因。

② 运行期：gdb = 查表器 + int3 注入器

你敲 break c1_5_pipeline.c:20，gdb 在背后做了四步（手册格式示意，gdb 交互会话本模块验证环境跑不了，与 2.1 节同一惯例）：

1. 查 .debug_line：第 20 行第一条 is_stmt 指令 = 0x100003efc（就是上面那行表）
2. ptrace 附着进程，把该地址的指令首字节替换为 0xCC（x86 的 int3 陷阱指令）
3. CPU 跑到 0x100003efc → 触发 SIGTRAP → 内核把信号递给 gdb（进程停下）
4. gdb 把原字节写回去、PC 回退一字节，你看到的就是"停在第 20 行"

此后每个"魔法"都是同一张表的反复使用：

gdb 命令 背后动作
break 20 正向查表：行号 → 地址 → 写 int3（上面四步）
bt 逐帧取返回地址，反向查表：地址 → file.c:xx，所以没有 -g 时 bt 只有一串裸地址
p qty 查 .debug_info：qty 在寄存器/栈偏移多少 → 读出来按类型解释
continue 再写回 int3，放行，等下一次 SIGTRAP

一句话：gdb 没有任何源码透视能力，它只是一个忠实的查表员 + 一个会塞陷阱指令的进程外大脑。 这也解释了 2.7 的现象：-O2 下变量 <optimized out>，不是 gdb 坏了，是表里那条映射（变量→位置）被优化打散了。

③ strace：同一个底座（ptrace），另一种滤镜

strace 和 gdb 用的是同一个系统调用 ptrace——这是最反直觉也最该记住的一点。区别只在观测策略：

gdb strace
ptrace 用法 拦陷阱信号（int3/SIGTRAP），停在指令级 PTRACE_SYSCALL 拦在每次系统调用的进/出口
依赖 -g？ 依赖（不查表就是瞎子） 完全不依赖——它观测的是进程与内核的行为边界（调了什么、传了什么参数、返回什么），与源码无涉
观测粒度 指令级、变量级 syscall 级
典型问题 值为什么错了、崩在哪一行 在反复重试？打开的文件不对？读到的字节数不对？卡在哪个调用上？

正因为不需要 -g，strace 能直接对付线上那个 stripped 二进制——这决定了分工：行为不对，先 strace（零前提、零侵入）；逻辑/内存不对，再 gdb（要有符号）。

④ 协作闭环：一条命令流上的接力（示意）

把三个零件放到一个 bug 上（示意场景：订单程序偶发"卡住"，日志无异常）：

# 1) strace 先看行为 —— 发现 write 在循环里反复返回 EAGAIN
strace -e trace=write,recvfrom -p $(pidof order)

# 2) 假设（对照 1.4 元流程）：socket 发送缓冲长期满 → 上游没消费
#    设计验证：gdb attach 抓现场，看阻塞点与 fd 状态
gdb -p $(pidof order)
(gdb) break send_orders if rc < 0      # 条件断点：只在失败时停
(gdb) continue
(gdb) bt                               # 反向查表：现场在哪条调用链上
(gdb) p errno                          # 查表读变量：证实 EAGAIN

# 3) 根因证实（对端不读了）→ 修上游消费逻辑，而非在 send 前吞掉 errno

对照 1.4 的元流程：strace 承担"观察现象 + 收缩假设"，gdb 断点承担"设计验证 + 证实根因"。两者不是二选一，而是接力——这也是 1.2 决策树"行为类 → 5.x，崩溃/逻辑类 → 2.x"背后的统一原理：先让滤镜成本低、前提少的工具上场，再用重武器精确打击。

HFT 关联

  1. 符号归档是交易系统的运维红线：core / attach 现场没有成对符号就是裸地址。macOS 生产线尤其注意 -g ≠ 有符号，dsymutil 产物必须与二进制同版本归档。
  2. 生产诊断优先 strace：延迟敏感的进程被 gdb attach 会整进程停住（错失行情窗口）；strace -p 逐 syscall 观测侵入更小，且不需要事先带 -g 构建。
  3. 理解 int3 机制才能理解调试的代价：断点会改代码段、打断时序——对竞态类 bug，断点本身就是干扰源（2.6 的 rr / 录制回放正是为了解决这个矛盾）。

Q1: gdb 说「停在第 20 行」，这句话背后发生了哪四步？

查 .debug_line 得第 20 行首条 is_stmt 指令地址 → ptrace 把该地址首字节换成 0xCC → CPU 执行到此处触发 SIGTRAP、进程停下 → gdb 恢复原字节、PC 回退。所有源码级调试都建立在这四步上。

Q2: 为什么 gdb 必须要 -g（或 dSYM/分离符号文件），strace 却不用？

gdb 的每个命令（断点/bt/p）都是对 DWARF 映射表的正向或反向查询，没表只能看裸地址；strace 用 PTRACE_SYSCALL 拦在 syscall 边界，观测的是进程—内核行为，与源码信息无关。

Q3: macOS 上编译了 clang -g 的二进制，拷到另一台机器上 lldb 却显示不了源码行，最可能的原因？

macOS 链接器默认不内嵌 DWARF，可执行文件里只有 OSO 调试映射（指向编译时的 .o 路径）。跨机器调试必须随二进制带上 dsymutil 生成的 .dSYM，且 .o 已删时 dsymutil 也救不回来（本节实测即踩此坑：临时目录的 .o 被清 → dSYM 生成失败）。

Q4: 「行为不对先 strace，逻辑不对再 gdb」——这条分工的依据是什么？

前提成本：strace 零前提（不需要 -g、不用重编、可 attach 线上 stripped 二进制），代价是只有 syscall 粒度；gdb 信息最细但有符号前提，且 attach 会整进程暂停。按 1.4 的原则先用低成本观测收缩假设，再用高成本工具证实。
