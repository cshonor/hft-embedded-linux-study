导读

为什么调试要「方法论先行」

工具手册（gdb / strace / valgrind 的官方文档）教你「怎么用」，但不教你「遇到问题时该用哪个、按什么顺序」。这正是 LDD Ch4（Greg Kroah-Hartman 合著）把调试分成 Printing → Querying → Watching → System Faults → Debuggers 五类方法的原因：先分类，再选工具。

本模块后面 5 个问题类型章，每章开头都会先写一句「这一章解决什么症状」，让你从症状反查工具，而不是背完工具清单却不知道何时用。

HFT 关联

  • 快速分诊：生产环境报错时，先判断「崩了 / 内存涨了 / 结果时对时错 / 卡住 / 太慢」五选一，决定上 coredump / valgrind / TSan / strace / perf——比「上来就 gdb」高效得多；
  • 复现即正义：交易系统很多 bug 只在特定行情时序下出现，能复现就赢了一半（见 1.3）；
  • 收敛而非乱试：HFT 延迟敏感，每次「改一处猜一处」都会引入新变量，1.4 的科学方法帮你少走弯路。
1.1

问题分类学（崩溃 / 内存 / 并发 / 行为 / 性能）

🔴 精读 · 调试的第一步是「定性」

本节要点

调试最大的浪费是「用错工具」：拿着 gdb 查内存泄漏（gdb 不擅长），拿着 strace 查数据竞争（strace 看不到）。先给问题定性——它属于哪一类——再选工具，能省掉 80% 的瞎试时间。本节建立「五类问题」的分类学框架，它是本模块后续所有章节的索引。

五类问题总表

类别 典型症状 根因方向 第一工具 对应章节
崩溃 (crash) 段错误、SIGABRT、非法指令、栈破坏 野指针 / 越界写 / 栈溢出 / 除零 gdb + coredump Ch2
内存 (memory) 内存持续增长、偶发崩溃、值不对 泄漏 / 越界 / use-after-free / 未初始化读 valgrind / ASan Ch3
并发 (concurrency) 结果时对时错、偶发死锁、竞态 数据竞争 / 锁序错误 / 忘记加锁 TSan / gdb 多线程 Ch4
行为 (behavior) 卡住不动、调了不该调的、参数错 阻塞等 IO / 等锁 / 多余 syscall strace / ltrace Ch5
性能 (performance) 太慢、CPU 高、延迟毛刺 热点函数 / cache miss / 多余拷贝 perf Ch6

为什么「分类」是第一步

调试工具是按问题域设计的，每个工具只能「看见」某一类问题：

strace 只能看见 syscall ──→ 看不见内存越界、数据竞争
valgrind 只能看见内存 ────→ 看不见 syscall 时序、性能热点
TSan 只能看见数据竞争 ────→ 看不见内存泄漏
perf 只能看见性能 ────────→ 看不见逻辑错误

工具是「滤镜」，选错滤镜，问题就「隐身」了。所以流程必须是：症状 → 定性 → 选工具，而不是「先打开 gdb 再说」。

五类问题的「边界模糊区」

真实 bug 常跨类，要会识别主次：

现象 可能是哪几类？ 判断方法
偶发崩溃 崩溃 + 内存（UAF）+ 并发（竞态写坏） 先 coredump 看崩溃点，若崩溃点每次不同 → 怀疑内存/并发
结果时对时错 并发 + 内存（未初始化读） TSan 抓竞态；ASan 抓未初始化
卡住 行为（等 IO）+ 并发（死锁） strace 看停在哪：recvfrom 是等 IO，futex 是等锁
偶发段错误且只在多线程下 崩溃 + 并发 TSan 优先，因为竞态往往是崩溃的根因

经验法则：多线程程序里「偶发、难复现、位置漂移」的 bug，九成是并发或内存问题，不是逻辑问题——先上 TSan/ASan，别在 gdb 里死磕单线程现场。

分类学与 05.6 的对称

用户态五类问题，在内核态有精确对应（这正是 03.6 ↔ 05.6 对称的依据）：

问题类型 用户态工具 (03.6) 内核态工具 (05.6)
崩溃 coredump + gdb Oops 日志
内存 valgrind / ASan KASAN / kmemleak
并发 TSan / helgrind KCSAN / LOCKDEP
行为 strace / ltrace printk / ftrace
性能 perf perf

HFT 关联

  1. 分诊决定响应速度：交易进程在生产出问题时，第一句话先问「崩了 / 慢了 / 卡了 / 结果错了 / 内存涨了」——这五选一定位了该 dump core、上 perf、上 strace 还是上 TSan，而不是盲目重启掩盖问题。
  2. 并发与内存是 HFT 重灾区：多线程行情/下单程序里，竞态和 UAF 是最隐蔽、最致命的两类（偶发错单、偶发崩溃），分类学提醒你优先怀疑这两类。
  3. 行为类是「系统集成」的入口：链路不通、配置读错、端口没绑上，这类问题 stract 一眼可见，别上来就怀疑算法逻辑。

Q1: 为什么说「选错工具，问题就隐身了」？

因为调试工具本质是滤镜，每个工具只能观测特定问题域：strace 只看 syscall（看不见内存越界）、valgrind 只看内存（看不见 syscall 时序）、TSan 只看数据竞争（看不见泄漏）、perf 只看性能（看不见逻辑错误）。问题类型和工具观测域不匹配时，问题在工具视角下不存在，自然「隐身」。

Q2: 一个多线程程序「偶发段错误、每次崩溃点不同」，最该先怀疑哪类问题？为什么？

优先怀疑并发（或内存）。「偶发、难复现、崩溃位置漂移」是多线程竞态的典型签名——多个线程写同一块内存没加锁，谁先写坏、写到哪不确定，所以崩溃点随机。逻辑 bug 通常是「稳定、可复现、固定位置」。这种情况先上 TSan 抓竞态，比在 gdb 里单步死磕高效。

Q3: 进程「卡住不动」，可能属于哪两类？怎么区分？

可能是行为类（阻塞等 IO）或并发类（死锁等锁）。用 strace attach 看最后停在哪：停在 recvfrom/read 是等网络/文件数据（行为类，查对端）；停在 futex(...FUTEX_WAIT...) 是等锁（并发类，查锁序）。两者排查方向完全不同。

Q4: 「分类学」和「工具清单」的学习顺序应该是什么？为什么？

应该先学分类学、再学工具。因为分类学是「地图」，告诉你有哪些问题类型、每种该往哪走；工具清单是「路标」，具体教某条路怎么走。没有地图，路标再多也不知道该去哪个。这就是本章（Ch1 方法论）放在所有工具章前面的原因。

1.2

症状 → 工具决策树

🔴 精读 · 从「我看到的」到「我该用的」

本节要点

分类学（1.1）给了你「五类问题」，但实战中你面对的不是分类标签，而是具体症状：「它段错误了」「它内存一直涨」「它结果有时对有时错」。本节把「症状」翻译成「工具选择」，给出一棵可照做的决策树——这是新手和老手之间最大的差距：老手不是更会背命令，而是更会从症状一步跳到正确工具。

症状 → 工具决策树

程序出问题了
│
├─ 崩溃（段错误 / SIGABRT / 非法指令）
│   ├─ 能复现？ ──是──→ gdb 直接跑，崩溃点设断点（Ch2）
│   └─ 生产偶发 ──────→ 开 core，gdb prog core 回溯（Ch2）
│
├─ 内存持续增长 / 偶发崩溃 / 值莫名变
│   ├─ 怀疑泄漏 / 越界 / UAF
│   │   ├─ 开发期 → valgrind memcheck（Ch3，准但慢）
│   │   └─ 要速度 → ASan 重编译（Ch3，快、需重编）
│   └─ 未初始化读 / UB → UBSan（Ch3）
│
├─ 结果时对时错 / 偶发死锁（多线程）
│   ├─ 数据竞争 → TSan（Ch4，开发期）
│   ├─ 死锁 → gdb attach + thread apply all bt（Ch4）
│   └─ 难复现竞态 → rr 录像回放（Ch4）
│
├─ 卡住不动 / 行为不对 / 调了不该调的
│   ├─ 卡住 → strace -p 看停在哪（Ch5）
│   ├─ 调了什么 syscall → strace（Ch5）
│   └─ 调了什么库函数 → ltrace（Ch5）
│
└─ 太慢 / CPU 高 / 延迟毛刺
    ├─ 热点函数 → perf record + report（Ch6）
    └─ 深入系统级 → 06.6 Systems Performance

核心决策口诀

症状 第一反应 一句话理由
崩了 coredump / gdb 崩溃现场是唯一硬证据，先拿 bt
内存涨 valgrind 泄漏只有它能精确定位到分配点
时对时错 TSan 竞态是「偶发」的头号嫌疑
卡住 strace -p 一行就能看到停在哪、等什么
太慢 perf 采样直接给出热点，不猜

反模式：所有问题都「先上 gdb 单步」。gdb 擅长「崩溃现场回溯」和「单线程逻辑」，但对「内存泄漏」（要跑很久看趋势）、「数据竞争」（要并发复现）、「性能热点」（要统计采样）都很吃力——这些问题有更对口的工具。

「偶发」是决策树里最关键的分支

「偶发」二字会彻底改变工具选择：

问题属性 崩溃类 内存类 并发类
稳定可复现 gdb 单步即可 valgrind 跑一次即出 gdb 断点即可
偶发难复现 必须开 core 抓现场 长时间跑 + ASan TSan 全量重编 / rr 录像

稳定 bug 靠「打断点定位」，偶发 bug 靠「抓现场 + 全量检测」。前者是 gdb 的主场，后者是 core/ASan/TSan/rr 的主场。先判断偶发性，再选工具，能少做大量无用功。

HFT 关联

  1. 生产偶发崩溃 → 必须先开 core：交易进程 7×24 跑，崩溃不可复现，唯一证据是 core。上线前必须配好 ulimit -c + core_pattern（见 Ch2），否则崩溃了连现场都没有。
  2. 延迟毛刺 → 先 perf 采样，别猜：「某天某笔单延迟 250ms」这种毛刺，靠读代码猜热点几乎不可能，perf 采样 + 火焰图直接定位（见 Ch6）。
  3. 偶发错单 → 并发优先：下单结果偶发不对，第一嫌疑是竞态（多线程共享订单状态没锁好），上 TSan 而非逐行读代码。

Q1: 「偶发性」为什么是决策树里最关键的分支？

因为偶发性直接决定工具选型：稳定 bug 可以打断点、单步、跑一次复现（gdb 主场）；偶发 bug 打不到断点、跑一次不复现，必须靠「抓现场」（core dump）+「全量检测」（ASan/TSan 重编译）+「录像回放」（rr）。用对付稳定 bug 的方法（gdb 单步）去查偶发 bug，基本是白费劲。

Q2: 为什么「所有问题都先上 gdb 单步」是反模式？

因为 gdb 只擅长「崩溃现场回溯」和「单线程逻辑定位」，对内存泄漏（要长跑看趋势）、数据竞争（要并发复现）、性能热点（要统计采样）都很吃力。这些有更对口的工具：valgrind / TSan / perf。工具不匹配时，gdb 单步既慢又看不到问题。

Q3: 生产环境「偶发段错误」，第一步该做什么？为什么不是立刻 gdb attach？

第一步是确认 core dump 已开启（ulimit -c + core_pattern），让下一次崩溃能落盘。因为偶发崩溃无法预知何时发生，gdb attach 来不及（崩溃瞬间进程就没了），core 是唯一能事后拿到的现场。没有 core，偶发崩溃基本无解。

Q4: 「卡住」和「太慢」都表现为「程序没反应」，怎么快速区分该上 strace 还是 perf？

看是不是永久卡住：如果进程「永久不动」（等一个永远不会来的事件），是行为/并发问题，用 strace -p 看它停在哪（等 IO 还是等锁）；如果进程「还在跑但慢」（CPU 有活动、只是吞吐低），是性能问题，用 perf 采样找热点。「永久卡住」和「缓慢推进」是两类完全不同的病。

1.3

最小可复现与二分定位

🔴 精读 · 复现是第一生产力，二分是最高效的定位

本节要点

「能复现的 bug 已经死了一半」。调试的一半时间其实花在把 bug 缩小到最小可复现用例（minimal reproducer）上——它越简、越小、越稳定，定位越快。另一半时间花在二分定位上——把「嫌疑范围」每次砍半，而不是一行行读。本节讲这两件「方法论层面最值钱」的事。

为什么最小复现是第一生产力

有最小复现 没有最小复现
改动一次、复现一次，1 秒验证 每次验证要跑完整流程，几十分钟
可以交给工具（gdb/ASan/TSan）自动跑 工具跑不动、太慢
可以缩小到单线程、单文件 多线程/多模块干扰，无法隔离
可以留着做回归测试 bug 修了没法验证，容易复发

交易系统里一个 bug 可能藏在「行情 → 策略 → 风控 → 下单」整条链路里。能把它缩小到「一个函数 + 一段假行情」，你就从「在大海里捞针」变成「在鱼缸里捞针」。

如何缩小（shrink）复现

四步，从外到内逐层砍：

// 原始：完整下单程序，几百行，多线程
// 目标：几十行，单线程，稳定触发 bug

// 1. 砍输入：用固定假数据代替真实行情/网络
//    真实 socket 读 → 直接喂一个 struct 数组

// 2. 砍线程：多线程 → 单线程（能复现就砍，不能则保留最小线程数）
//    3 个 worker → 1 个

// 3. 砍功能：删掉无关模块（日志、配置、指标上报）
//    if (logging) ...  整个删掉

// 4. 砍代码：删掉不影响复现的语句，逐行删

# 每砍一步，立刻验证「bug 还在不在」
gcc -g -O0 -o repro repro.c && ./repro
# 复现成功 → 继续砍；不复现 → 刚砍掉的部分是关键，回退

砍掉后 bug 消失 = 刚砍的部分参与制造 bug。这个「保留 bug 的前提下做减法」的过程，本身就在帮你逼近根因。

二分定位：每次砍半，别一行行读

「二分」是计算机科学最高效的搜索策略，调试同样适用：

1. 代码二分（缩小到可疑区间）

怀疑 100 行代码里有 bug
  └─ 注释掉中间 50 行 → bug 还在？ ──是──→ 嫌疑在前 50 行
                                      └─否──→ 嫌疑在后 50 行
  └─ 再砍 25 行…… 100 → 50 → 25 → 12 → 6 → 3 → 1
  （7 步定位到 1 行，而不是读 100 行）

2. git bisect（定位「哪次提交引入」）

# bug 在历史某次提交引入，当前已知坏了，某旧版本已知是好的
git bisect start
git bisect bad HEAD            # 当前版本是坏的
git bisect good v1.0           # v1.0 是好的
# git 自动切到中间提交，你编译验证后标记：
git bisect good   # 或 git bisect bad
# 反复几次，git 收敛到「引入 bug 的那一次提交」
git bisect reset

3. 数据二分（定位是哪个输入触发）

# 1000 条行情数据里某一条触发崩溃
# 二分喂入：喂前 500 条 → 崩？ 喂后 500 条 → 崩？
# 500 → 250 → 125 → ... → 1 条
# 10 步定位到具体哪条数据，而不是跑 1000 次

二分的前提：bug 必须是「可判定」的

二分定位有个隐藏前提——你必须能自动、快速地判断「这个版本是好是坏」：

前提 说明 反面教材
可自动判定 脚本能跑出 pass/fail 「肉眼观察有没有闪」→ 不可靠
判定快 秒级 每次跑 30 分钟 → 二分没意义
判定稳定 同输入同结果 偶发 bug 判定会抖 → 先想办法稳定复现

偶发 bug 无法直接二分，因为它「判定不稳定」。这时要先想办法把它变稳定（缩小 + 提高触发频率 + rr 录像），再二分。

HFT 关联

  1. 复现 = 破案关键：交易所/券商报一个「偶发错单」，你第一时间要做的不是读代码，而是想办法在本地复现——用当天的行情数据回放（replay），缩小到最小触发序列，否则连问题都看不见。
  2. 回放系统就是「复现基建」：HFT 团队都建行情/订单回放系统，本质就是为了把「生产偶发 bug」变成本地「稳定可复现 bug」，是调试效率的倍增器。
  3. git bisect 定位回归：性能回退或行为回归，git bisect 能自动锁定引入的提交，比逐次手动 checkout 高效得多。

Q1: 为什么说「能复现的 bug 已经死了一半」？

因为复现是调试的前提：能稳定复现，就能（1）快速验证每一次修复是否有效，（2）缩小到最小用例隔离干扰，（3）交给 gdb/ASan/TSan 等工具自动跑，（4）留作回归测试防止复发。不能复现，这些都做不了，只能靠猜。所以「先复现」是调试的第一优先级。

Q2: 缩小复现时，「砍掉某部分后 bug 消失」说明了什么？下一步怎么做？

说明刚砍掉的那部分参与制造了这个 bug（可能是根因本身，也可能和根因有依赖）。下一步：把刚砍掉的部分加回来，继续在其中做更细的「二分」，逐层逼近真正的根因。这个「保留 bug 做减法」的过程本身就在定位。

Q3: git bisect 的机制是什么？它比手动 checkout 快在哪？

它是二分搜索：你标记「当前坏」和「某旧版本好」，git 自动切到两者中间的提交让你验证，根据你标 good/bad 再切到剩下区间中点，反复对数次就收敛到引入 bug 的那次提交。快在「每次砍半」：1000 个提交只需约 10 次验证，而不是线性试 1000 次。

Q4: 为什么「偶发 bug」不能直接二分定位？要先做什么？

因为二分要求「判定稳定」——同一版本每次验证结果一致。偶发 bug 时好时坏，判定会抖，二分区间就切错了。必须先把它变稳定：缩小用例、提高触发频率（循环多跑）、或用 rr 录像回放固定时序，让它变成「稳定可复现」，再二分。

1.4

调试元流程（假设 → 验证 → 收敛）

🔴 精读 · 调试不是「试错」，是「科学方法」

本节要点

新手调试是「改一处、跑一下、看结果」，老手调试是「提出假设 → 设计验证 → 收敛范围」的循环。前者是随机试错（试 10 次可能碰巧对 1 次），后者是科学方法（每步都让嫌疑范围变小）。本节讲这个「元流程」——它是《Writing Solid Code》反复强调的核心，也是区分「碰运气」和「系统排查」的分水岭。

调试元流程：四步循环

  ┌─────────────────────────────────────────────┐
  │                                             │
  ▼                                             │
① 观察现象（崩溃栈 / 错误值 / 卡住位置）          │
      │                                         │
      ▼                                         │
② 提出假设（「可能是 X 没初始化」）              │
      │                                         │
      ▼                                         │
③ 设计验证（断点 / 打印 / 工具观测，检验假设）     │
      │                                         │
      ├── 假设成立 → ④ 缩小范围，回到②继续        │
      │              （或直接定位根因，结束）     │
      │                                         │
      └── 假设不成立 → 修正假设，回到②            │
                                                │
  （循环直到根因被证实，而非「碰巧能跑」）          └─┘

核心特征：每一步都有「假设」和「验证」，而不是「无目标地改」。

对比：试错 vs 科学方法

维度 随机试错 科学方法
行动 改一处、跑一下 先想「如果假设成立，应该观察到什么」
依据 「感觉像这里」 「证据指向这里」
失败后 换一处再试 修正假设，缩小嫌疑范围
收敛性 不保证（可能绕圈） 保证（每次验证都排除一批）
终点 「能跑了，不管为什么」 「根因被证实，且知道为什么」

⚠️ 「碰巧能跑」是最危险的终点。改了之后 bug 消失了，但如果你不知道为什么消失，很可能只是把症状掩盖了、时序改变了，bug 还在暗处等着复发。调试的终点是「根因被证实」，不是「现象消失」。

三个高频陷阱

1. 确认偏误（confirmation bias）

「我怀疑是 A 的问题」，于是只找支持 A 的证据，忽略反例。

错误示范：怀疑是锁的问题 → 加了把锁 → bug 暂时没出现 → 结论「就是锁」
正确做法：加锁后 bug 没出现，还要问「是锁修好了，还是时序变了导致 bug 藏起来了？」
         → 用 TSan 证实确实有数据竞争，才算证实「是锁的问题」

2. 一次改多处（失去因果）

// 错误：一次改了 3 处，bug 好了，但不知道是哪处起作用
buf = malloc(n + 1);   // 改 1：+1
memset(buf, 0, n);     // 改 2：清零
free(buf);             // 改 3：加 free

// 正确：一次只改一处，验证后再改下一处

一次改多处，即使 bug 好了，你也没学到任何东西——不知道哪处是根因，下次同类 bug 还得从头试。

3. 改症状不改根因

// 症状：偶发段错误，崩溃在 strcpy
// 错误做法：在 strcpy 前加 if (src == NULL) return;  ← 掩盖症状
// 正确做法：追为什么 src 会是 NULL → 发现是竞态导致指针被提前 free
//          → 修锁/生命周期，而非加 NULL 判断

日志 / 断点 / 打印：三种验证手段怎么选

验证「假设是否成立」有三种手段，各有适用场景：

手段 适用 代价 局限
打印/日志 快速看「执行到没、值是什么」 改代码 + 重编译 加太多干扰时序、污染性能
断点 精确停在某行看现场 无需重编译（attach） 打断点影响并发时序
工具观测 strace/valgrind/TSan 自动检测 无需改代码 各有观测域（见 1.1）

原则：先用工具观测（零侵入），不够再用断点，最后才加打印。打印是「最后手段」，因为它要改代码、重编译、还可能改变时序（尤其并发 bug）。

HFT 关联

  1. 「碰巧能跑」在交易系统里是灾难：改了时序、加了条日志，竞态暂时不出现了，你上线后它照样偶发错单。必须用 TSan/ASan 证实根因，而不是「看起来好了」。
  2. 一次改一处：交易逻辑高度耦合，一次改多处会让「到底哪处修的」不可知，出问题没法回滚定位。
  3. 工具零侵入优先：生产环境排查优先 attach/strace/perf（不动代码、不改时序），而不是加打印重编译——延迟敏感系统里，加打印本身就会引入新的竞态和延迟。

Q1: 「随机试错」和「科学方法」的本质区别是什么？

本质区别在有没有「假设 + 验证」：试错是「无目标地改一处看结果」，失败后换一处再试，不保证收敛；科学方法是「先提出假设 → 设计验证（如果假设成立应该观察到什么）→ 用证据证实或证伪 → 缩小范围」，每次验证都排除一批嫌疑，保证收敛。前者碰运气，后者可复现地逼近根因。

Q2: 为什么「碰巧能跑」是最危险的调试终点？

因为「现象消失」≠「根因解决」：改了之后 bug 不出现，可能只是时序改变、症状被掩盖，根因还在暗处。上线后环境一变，bug 照样复发，甚至更隐蔽。调试的终点必须是「根因被证实」（用工具/证据证明是它），而不是「看起来好了」。

Q3: 「一次改多处」为什么是坏习惯？

因为失去了因果判断：三处一起改，bug 好了，你不知道是哪一处起的作用，等于没学到任何东西，下次同类 bug 还得从头试。正确做法是一次只改一处、验证后再改下一处，每步都建立明确的因果。

Q4: 验证假设的手段（打印/断点/工具观测）应该按什么顺序选？为什么？

应该先工具观测（零侵入）→ 不够再断点 → 最后加打印。因为工具（strace/valgrind/TSan）不用改代码、不改时序；断点要 attach 但会扰动并发时序；打印最重——要改代码、重编译、还可能改变时序（尤其并发 bug，加打印往往让竞态「消失」）。所以打印是最后手段。
