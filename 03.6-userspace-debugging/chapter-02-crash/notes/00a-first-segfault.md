# 2.0′ 新手解剖课：第一次段错误，从 139 到根因

> 🟢 零起点 · 接续 [1.0 学前篇](../../chapter-01-methodology/notes/00-gcc-first-steps.md)
>
> 本章 2.1–2.7 是工具的「参考手册式」讲法。这一篇换一个讲法：
> **把一次段错误从发生到破案的完整过程走一遍**——屏幕上出现的每一行都解释，
> 每条命令为什么敲、输出怎么读，全部说清。
> 主角就是本章 demo `code/c2_1_crash_types.c` 的 case 1（空指针）。

---

## 案发现场：屏幕上只有一行字

```bash
$ ./c2_1_crash_types 1
case 1: 准备解引用 NULL（写 *p = 42）
Segmentation fault
$
```

程序死了，只丢下一句 `Segmentation fault`（段错误）。没有行号、没有变量值、
没有理由——**这就是没有工具时的全部信息**。解剖开始。

## 第一步：读退出码，确认「死因分类」

```bash
$ echo $?
139
```

1.0 篇背过的规则：`139 = 128 + 11` = 被 **11 号信号 SIGSEGV** 杀死。

**信号（signal）是什么**：内核发给进程的一条「紧急通知」，一共几十种，
每种一个编号。进程干了内核不允许的事（访问非法内存、除零……），
内核就用对应信号把它打死。崩溃分诊只需要记住四个：

| 信号 | 编号 | 退出码 | 典型死因 |
|------|------|--------|----------|
| SIGSEGV | 11 | 139 | 访问了不该访问的内存（空指针、野指针、爆栈） |
| SIGABRT | 6 | 134 | 程序**自己**决定自杀（`abort()`、`assert` 失败、栈金丝雀报警） |
| SIGFPE | 8 | 136 | 整数除零 / 溢出（名字带 FPE 但和浮点无关） |
| SIGILL | 4 | 132 | 执行了非法指令（跳到数据区、`-march` 不匹配的机器码） |

本案：139 → SIGSEGV → 「访问了不该访问的内存」。范围已经缩到一类。

## 第二步：看源码，找到「嫌疑人」

`code/c2_1_crash_types.c` 里 case 1 的全部代码：

```c
static void crash_null_deref(void)
{
    int *p = NULL;        /* ① p 是一个指针，但指向"空"——不指向任何合法内存 */
    printf("case 1: 准备解引用 NULL（写 *p = 42）\n");
    fflush(stdout);       /* ② 强制把上面那行先吐到屏幕（缓冲区见 1.0 的坑 5） */
    *p = 42;              /* ③ 往"空"里写 42 —— 死因就在这一行 */
}
```

三行注释就是全部案情：**`NULL`（地址 0）不属于你的进程**，
操作系统给每个进程划了地盘，地址 0 这一页特意不分配——谁碰谁死。
`*p = 42` 就是"往不属于你的地址写数据"，内核当场 SIGSEGV。

到这一步，这个 demo 的案情已经「肉眼破案」了。但真实项目里 case 1 藏在
几十万行代码里，肉眼找不到——所以要有第三步。

## 第三步：gdb 解剖（每行都注释）

同一个程序，这次交给 gdb 托管：

```text
$ gdb ./c2_1_crash_types                 # ① 启动 gdb，把程序装进来（还没开始跑）
(gdb) run 1                              # ② 开跑，参数 1（和直接 ./c2_1_crash_types 1 一样）
case 1: 准备解引用 NULL（写 *p = 42）

Program received signal SIGSEGV, Segmentation fault.   # ③ 内核打死进程的瞬间被 gdb 拦下
0x0000555555555196 in crash_null_deref () at c2_1_crash_types.c:22
                     ────────────────      ─────────────────────────
                     死在哪个函数            死在哪个文件第几行
```

**注意 ③ 这一行——没有 gdb 时你只能看到 `Segmentation fault`，
有了 gdb 直接告诉你文件和行号**：`c2_1_crash_types.c:22`。这就是全部差别。

继续解剖：

```text
(gdb) bt                                 # ④ backtrace：怎么走到这一步的（调用链）
#0  crash_null_deref () at c2_1_crash_types.c:22     ← 凶案现场（当前在哪）
#1  main (argc=2, argv=...) at c2_1_crash_types.c:87 ← 谁叫它来的（main 第 87 行）

(gdb) list                               # ⑤ 把现场附近的源码打出来（不用切出去翻文件）
17      static void crash_null_deref(void)
18      {
19          int *p = NULL;
20          printf("case 1: 准备解引用 NULL（写 *p = 42）\n");
21          fflush(stdout);
22          *p = 42;                     ← gdb 会指在这行（死因）
23      }

(gdb) print p                            # ⑥ 看嫌疑人：指针 p 的值
$1 = (int *) 0x0                         # 0x0 = 十六进制的 0 = NULL，实锤

(gdb) info registers rip                 # ⑦ （进阶）CPU 当前指令指针 = 崩溃的精确指令地址
rip            0x555555555196  0x555555555196 <crash_null_deref+27>

(gdb) quit                               # ⑧ 收工
```

整个推理链：**死在 22 行（③）→ 22 行是 `*p = 42`（⑤）→ p = 0x0（⑥）→
往 NULL 写数据 → SIGSEGV**。从「一行报错」到「实锤根因」，6 条命令。

### gdb 会话里每个新面孔

| 命令 | 干什么 | 什么时候用 |
|------|--------|-----------|
| `run 参数` | 开始/重新开始跑程序 | 每次想重现一遍就 run |
| `bt` | 打印调用链（frame 编号 #0 最内层） | 崩溃后第一条命令，永远先 bt |
| `list` | 显示当前位置附近源码 | 确认死在哪行、上下文是什么 |
| `print 变量` | 打印变量当前值 | 验证假设（"是不是 NULL？"） |
| `info registers` | 看 CPU 寄存器 | 行号还不够精确时，看指令级现场 |

## 第四步：程序已经死透了怎么办——core dump 尸检

gdb 活体解剖有个前提：**bug 能复现**（想 run 几次 run 几次）。
线上偶发崩溃复现不了，就要让内核在打死进程前**拍一张内存快照**——core 文件。

> ⚠️ 以下为手册格式示意（core 文件生成要改系统配置，需在真实 Linux 机器上验证）：

```bash
ulimit -c unlimited                      # ① 允许生成 core（很多系统默认禁止，大小为 0）
./c2_1_crash_types 1                     # ② 再让它崩一次 → 当前目录（或 core_pattern 指定处）出现 core 文件
gdb ./c2_1_crash_types core              # ③ 把"二进制 + 尸体"一起喂给 gdb
```

③之后的画面和第三步**一模一样**：`bt`、`list`、`print p` 全都可用——
因为 core 就是死亡瞬间的完整内存。区别只在于：程序不会再跑了，
不能 `run`/`next`（死人不会动），只能翻看现场。

一句话分工：**能复现 → gdb 活体（第三步）；偶发/线上 → core 尸检（第四步）。
配置细节（`core_pattern`、systemd-coredump）是 2.4 节的内容，这里先建立直觉。**

## 复盘：一张图记住全流程

```text
程序打出 "Segmentation fault"
   │
   ├─ echo $? → 139 → SIGSEGV（死因分类：非法内存访问）
   │
   ├─ 能复现？── 能 ──▶ gdb ./程序 → run → bt → list → print → 根因
   │      │
   │      └─ 不能（偶发/线上）──▶ 开 ulimit -c → 崩出 core
   │                              → gdb ./程序 core → 同样的 bt/list/print
   │
   └─ 根因落到行：*p = 42，p = 0x0 → 修法：写之前判空 / 找到谁把 p 置成了 NULL
```

<summary>自测题（点击展开）</summary>

**Q1:** `Segmentation fault` 和退出码 139 之间的关系是什么？为什么 139 不是程序自己返回的？

> 程序访问非法内存时被内核用 SIGSEGV（11 号信号）杀死，shell 把「被 N 号信号杀死」
> 编码为 128+N = 139。「Segmentation fault」是 shell 看到 139 后打印的人话。
> 不是程序自己返回的——程序在 `*p = 42` 那一刻已经死了，没有机会执行 return。

**Q2:** gdb 会话里 `bt` 和 `list` 的分工？

> `bt` 管「纵向」：调用链——哪个函数调哪个函数，一路到 main，定位「在场的是谁」；
> `list` 管「横向」：当前帧附近的具体源码行，确认「现场长什么样」。
> 崩溃后标准顺序：先 bt 找 frame，再 list 看代码，最后 print 验变量。

**Q3:** core 文件和 gdb 活体调试，各自的不可替代性是什么？

> 活体调试能「动」：run/next/break，可以反复重演、设断点提前拦截，但要求 bug 可复现；
> core 尸检面对的是已死的进程，不能单步不能重来，但它是偶发崩溃（尤其线上）
> 唯一能留下的完整现场——没有 core，偶发崩溃只有一句日志。
> 所以纪律是：开发期活体调，上线前把 core 生成配好。

**Q4:** `print p` 输出 `(int *) 0x0`，0x0 为什么就是 NULL？访问它为什么一定崩？

> 0x0 即地址 0，C 语言里 NULL 的定义就是「地址 0 的指针」。
> 操作系统故意不在地址 0 分配任何内存页（第一页永远无效），
> 于是任何对 NULL 的读写都必然触发页错误 → SIGSEGV。
> 这是故意的：让空指针解引用「立刻死、死得响」，而不是悄悄读写垃圾数据。

**Q5:** 退出码 134 和 139 都是「被杀」，死因分类上差在哪？各给一个 c2_1 的例子。

> 134 = SIGABRT = 程序**自己**调用 abort 自杀（检测到不变量被破坏，主动死给你看），
> 如 case 3 的 `assert(qty > 0)` 失败、case 5 栈金丝雀发现数组被写穿；
> 139 = SIGSEGV = **内核**判的死刑（访问非法内存），如 case 1 空指针、case 6 爆栈。
> 分诊意义：134 说明有「哨兵」提前发现了问题（离根因可能还有距离），
> 139 说明问题直接发生在非法访问那一刻（现场即根因）。
