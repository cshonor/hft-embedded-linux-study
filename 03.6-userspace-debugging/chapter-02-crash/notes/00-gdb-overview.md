# 2.0 GDB 总览：能干什么、不能干什么

> 🔴 精读 · 用户态正确性调试

## 本节要点

GDB（GNU Debugger）是 Linux **用户态**源码级调试器，x86-64 与 AArch64（树莓派 5）都支持。

**前提：编译必须加 `-g`**，生成 DWARF 调试符号；不加 `-g` 只能看汇编和裸地址。

这一节是 Ch2 的**总览**：先把 GDB 的能力边界划清楚——**它能精确观察用户态的一切，但看不见内核内部，也和 ASAN 八字不合**。细节分散在 2.1（`-g` 与加载方式）、2.2（断点）、2.3（栈帧回溯）、2.4–2.6（core 尸检）。

> ⚠️ **实测说明**：本节的 `-g` 段结构、ASAN 插桩、ASAN 报错输出均为 gcc 13.3 **实测**；
> 但 **gdb 命令本身未在本机实测**——当前 WSL 环境没有安装 gdb（`gdb: command not found`），
> 且 `sudo` 需要密码无法安装。涉及 gdb 交互输出的部分为工具知识与标准用法，已如实标注。

## 一、GDB 能干什么（用户态）

### 1. 控制执行流

| 命令 | 作用 |
|------|------|
| `b` 行号/函数名 | 设断点 |
| `r` | 从头运行 |
| `c` | 继续到下一个断点 |
| `n` | 单步**跨过**函数（next） |
| `s` | 单步**跳入**函数（step） |

### 2. 查看栈帧（**递归调试的重点**）

| 命令 | 作用 |
|------|------|
| `bt` | 完整调用栈，每层函数名 + 参数 |
| `info locals` | 当前栈帧的全部局部变量 |
| `p var` | 打印参数 / 局部 / 全局变量 |
| `x` | 按地址看内存 |
| `info registers` | 看寄存器 |

`bt` 是读递归的核心：**同名函数连续出现 N 次 = 递归了 N 层**。配合 `frame N` 切到第 N 层，再 `info locals` 看那一层的变量。详见 2.3，递归实战见 **ch07 的 7.5.1**。

### 3. 运行时修改变量

`p var =  newValue` 可以直接改内存里的值，**强行走另一个分支**——验证"如果这里是 0 会不会走另一条路"，不用改代码重编译。

### 4. 捕获系统调用

`catch syscall` 能拦截系统调用的**进入/退出**（如 `catch syscall write`）。

> ⚠️ **但它只能看到"出入口"**——能看到"调用了 `write(1, ...)`、参数是什么、返回什么"，
> **看不到内核内部变量、看不到内核源码**。想看系统调用的完整行为用 `strace`（见 Ch5）；
> 想看内核内部得用 `ftrace` / `perf` / `bpftrace`，那已经不是 gdb 的活了。

### 5. 分析 core 转储

程序崩了之后 `gdb ./prog core` + `bt` 还原崩溃现场（详见 2.4–2.6）。对偶发崩溃，core 是**唯一硬证据**。

## 二、GDB 做不好 / 看不到

### 1. ASAN（地址消毒器）—— 体验很差

**根因是 ASAN 会大量插桩改写程序**。同一个极简函数 `int add_one(int *p){ return *p + 1; }`，实测（gcc 13.3 `-O0`）：

| | 普通编译 | `-fsanitize=address` |
|---|---------|---------------------|
| `add_one` 指令条数 | **9** | **27** |
| 引入的 `__asan_*` 外部符号 | 0 | **8** |
| 目标文件体积 | 1752 B | 3768 B |

普通版 9 条指令干干净净：

```
   8:  mov    %rdi,-0x8(%rbp)
   c:  mov    -0x8(%rbp),%rax
  10:  mov    (%rax),%eax        ← 真正的解引用
  12:  add    $0x1,%eax
  16:  ret
```

ASAN 版 27 条，真正的业务逻辑被淹没在**影子内存（shadow memory）检查**里：

```
  10:  mov    -0x8(%rbp),%rax
  14:  mov    %rax,%rdx
  17:  shr    $0x3,%rdx          ← 算影子地址
  1b:  add    $0x7fff8000,%rdx   ← shadow memory 基址
  22:  movzbl (%rdx),%edx        ← 读影子字节
  25:  test   %dl,%dl
  ...（一串 test/setne/and/cmp/setge 判断）
  3d:  je     47
  3f:  mov    %rax,%rdi
  42:  call   47                 ← 越界则调 __asan_report_load4
  47:  mov    -0x8(%rbp),%rax
  4b:  mov    (%rax),%eax        ← 真正的解引用，就这一条
  4d:  add    $0x1,%eax
  51:  ret
```

**这就是"GDB 断点经常落到 asan 内部桩代码、栈帧很乱、变量显示混乱"的物理原因**：
你在一行源码上下断点，那一行展开成了 27 条指令，其中只有 1 条是你写的逻辑。

> ✅ **正确用法：ASAN 优先直接跑程序看报错日志，不要拿 GDB 深度源码调试。**
>
> ASAN 自己给的信息已经足够精准，实测输出（`-O0 -g -fsanitize=address`）：
>
> ```
> ==376==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000020
> WRITE of size 4 at 0x502000000020 thread T0
>     #0 0x5e31dc69a2a1 in main /mnt/d/.kernel-ref/demo-gdb/uaf.c:6     ← 精确到源码行
>     #1 0x763c2c62a1c9  (/lib/x86_64-linux-gnu/libc.so.6+0x2a1c9)
>
> 0x502000000020 is located 0 bytes after 16-byte region [0x502000000010,0x502000000020)
> allocated by thread T0 here:
>     #0 ... in malloc ...
>     #1 0x5e31dc69a25e in main /mnt/d/.kernel-ref/demo-gdb/uaf.c:5      ← 连分配点都给你
> 退出码=1
> ```
>
> **函数名 + 源码行 + 越界字节数 + 分配位置，一次跑完全都有**——根本不需要 gdb。

**ASAN 自身的坑（实测）**：优化会削弱它。同一个越界写：

| 编译 | 结果 |
|------|------|
| `-O0` | ✅ 报错，退出码 1，精确到 `uaf.c:6` |
| `-O1` | ❌ **静默，退出码 0** |

原因：`a[4] = 42` 写入后没人读，被当**死代码优化掉**了，`objdump` 里 `main` 只剩 `malloc` 和 `free`，越界访问根本没发生。
另一例：`a[4]=42; printf("%d", a[4]);` 被**常量传播**成直接打印 42，也不读内存，同样不报。

> 🔑 **让 ASAN 真正生效**：用 `-O0`/`-O1`，并确保访问不会被优化掉
> （用运行时索引、`volatile`，或让结果真的被外部使用）。

### 2. 内核内部逻辑 —— 完全看不到

普通用户态 gdb 只能看到**用户侧**。想看内核内部（内核变量、内核栈、内核源码行）需要 **KGDB 远程调试内核**（两台机器串口/网口互联，或 `qemu + gdbstub`）。

内核态调试见仓库 **`05.6-kernel-debugging`** 模块，那是完全不同的工具链（KGDB、crash、ftrace、kprobe）。

### 3. 无调试符号的程序

没有 `-g`，gdb 只能看汇编、裸地址，没有源码、没有变量名。

实测 `-g` 到底往 ELF 里塞了什么：

| | 无 `-g` | 有 `-g` |
|---|--------|--------|
| `.debug_*` 段数量 | **0** | **9** |
| 目标文件体积 | 1752 B | 4152 B（2.4×） |

那 9 个段：`debug_info`、`debug_line`（行号映射，`bt` 靠它）、`debug_abbrev`、`debug_aranges`、`debug_str`、`debug_line_str` 等。

## 三、高频极简命令速记

```
b 行号/函数名   设置断点
r              从头运行
s              步入函数
n              步过函数
bt             打印调用栈（递归必用）
p 变量         打印值
info locals    本层全部局部变量
c              继续执行
q              退出
```

## 四、一句话概括

> **GDB 主要用于用户态源码级调试**：观察调用栈、参数、局部变量，控制程序执行；
> 系统调用只能抓出入口，看不见内核内部；和 ASAN 一起使用体验很差。

## 五、HFT / 嵌入式关联

| 场景 | 用 gdb | 用别的 |
|------|--------|--------|
| 交易进程崩溃（有 core） | ✅ `gdb prog core` + `bt` | — |
| 进程卡死/死循环，不能重启 | ✅ `gdb -p <PID>` attach 后 `bt` | — |
| 内存越界 / use-after-free | ❌ | **ASAN**（直接看报错，实测精确到行） |
| 系统调用行为 / 卡顿在哪 | ⚠️ 只能看出入口 | **strace** / `perf trace` |
| 内核内部（驱动、协议栈） | ❌ | **KGDB** / ftrace / bpftrace |
| 树莓派 5 板端调试 | ✅ gdbserver + 本地 gdb 远程连 | — |

**选型口诀**：**崩溃看 core（gdb），内存看 ASAN，系统调用看 strace，内核看 ftrace/bpftrace**。
四类问题对应四套工具，别指望 gdb 一把梭。

<summary>自测题（点击展开）</summary>

**Q1:** gdb 能调试的前提是什么？不加 `-g` 会怎样？

> 前提是二进制里带 DWARF 调试信息（编译加 `-g`）。不加 `-g`：ELF 里一个 `.debug_*` 段都没有（实测 0 个 vs 9 个），gdb 只能反汇编看裸地址，没有源码行、没有变量名、没有类型信息，几乎没法用。

**Q2:** `n` 和 `s` 有什么区别？调试递归时看调用栈用什么命令？

> `n`（next）单步**跨过**函数调用，不进入被调函数；`s`（step）单步**跳入**函数内部。看调用栈用 `bt`（backtrace）：同名函数连续出现 N 次就说明递归了 N 层，再用 `frame N` 切到某一层、`info locals` 看那一层的局部变量。

**Q3:** 为什么 ASAN 和 gdb 一起用体验很差？正确做法是什么？

> ASAN 会在编译期大量插桩：实测同一个函数从 9 条指令膨胀到 27 条，真正的业务逻辑只剩 1 条，其余全是影子内存检查（算 shadow 地址、读 shadow 字节、判断、失败则 `call __asan_report_*`）。gdb 下断点常常落在桩代码上，栈帧和变量显示都很乱。**正确做法是让 ASAN 直接跑程序看报错**——它自己就会输出函数名、源码行、越界字节数、分配位置，信息比 gdb 手翻还全。

**Q4:** `catch syscall` 能看到什么？看不到什么？

> 能看到系统调用的**进入/退出**时机、调用号、参数、返回值——即"出入口"。**看不到内核内部变量、内核源码行、内核栈**。想看系统调用的完整行为用 `strace`；想看内核内部要上 KGDB / ftrace / bpftrace，不是 gdb 的能力范围。

**Q5:** 程序崩了但有 ASAN 报告了越界，还要用 gdb 吗？

> 通常不用——ASAN 报告已经给出精确源码行和分配点。gdb 的用武之地是 ASAN **抓不到**的场景：逻辑错误（走错分支、算错值）、死锁/死循环（attach 后 `bt`）、以及**没有 ASAN 构建**的生产/production 二进制崩溃（此时靠 core + `bt`）。另外 ASAN 报告本身也可能被优化"吃掉"（实测 `-O1` 下死代码被消除，越界访问根本没发生、退出码 0），用 `-O0` 复查能确认。
