# 5.0′ 第一次 strace 实战：把程序的每个动作看在眼里

> 🟢 零起点 · 接续 [1.0 学前篇](../../chapter-01-methodology/notes/00-gcc-first-steps.md)（0.5 节已见过 strace 的第一行）
>
> 行为类问题的特征是：**程序不崩、结果也对，但「举止」不对**——
> 莫名卡住、反复重试、打开的文件不对、读到的字节不对。
> 这类问题看源码经常一无所获（代码没问题，是它和操作系统的交互出了问题）。
> strace 的答案：**不看代码，看程序对内核说的每一句话**。
> 这一篇把一次真实跟踪从头到尾读完：启动时的十几行在干什么、
> 「卡住」在输出里长什么样、统计视图怎么一眼定位元凶。

---

## 先立框架：程序能「做」的事，90% 是系统调用

一个 C 程序自己能做的只有算数和读写自己的内存。**凡是需要「出去」的动作
——打印、读写文件、网络收发、申请内存、创建线程——都必须请求操作系统代劳，
每一次请求就是一次系统调用（syscall）**。strace 把这些请求逐条记下来。
所以 strace 的输出 = 程序的「行为流水账」，与源码有没有 `-g`、会不会调试无关。

## 第一次完整跟踪：三段式读法

> ⚠️ strace 需要真实 Linux（本仓库验证环境跑不了，以下为手册格式示意，
> 语义均可用 `code/` 下三个 demo 实测对照）。

```bash
strace -o trace.log ./c5_2_syscall_map      # -o：输出写文件，屏幕留给程序自己
```

打开 `trace.log`，几十行看着吓人，其实只有**三段**：

```text
── 第一段：启动（exec 的惯性，与你代码无关）──
execve("./c5_2_syscall_map", ...) = 0        ← ① 程序本身被加载，唯一一次
brk(NULL)             = 0x5555...            ← ② C 库初始化：问内核"我的堆在哪"
mmap(...)             = 0x7f...              ← ③ 加载 libc 等共享库（每个 .so 一行 mmap）
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY) = 3
...
── 第二段：你的代码真正干的事（重点区）──
openat(AT_FDCWD, "payload.txt", O_RDWR|O_CREAT, 0666) = 3     ← ④
openat(AT_FDCWD, "no_such.txt", O_RDONLY) = -1 ENOENT (...)    ← ⑤
write(1, "open payload.txt -> fd=3\n", 25)  = 25               ← ⑥
── 第三段：退出 ──
exit_group(0)         = ?                    ← ⑦ 程序谢幕（= ? 表示没有返回值）
```

| 行 | 读法 |
|----|------|
| ① `execve ... = 0` | 每个程序的第一行流水账：内核把程序本体加载起来 |
| ②③ 一堆 `brk/mmap/openat libc` | **启动开销**，是 C 运行时和动态链接器干的，不是你的代码——跳过不看 |
| ④ `openat(...) = 3` | 打开文件成功，**返回值 3 是文件描述符（fd）**——之后对这个文件的所有操作都报这个号码 |
| ⑤ `= -1 ENOENT` | **失败长这样**：返回值 -1 + 错误名。ENOENT = 文件不存在 |
| ⑥ `write(1, "...", 25) = 25` | 1 号 fd = 标准输出；你程序的每个 printf 最终都变成 write |
| ⑦ `exit_group(0)` | 进程退出，括号里是退出码 |

**新手读 strace 的秘诀：第一段直接跳过，从「认出自己代码」的行开始看**
（比如你 printf 的字符串出现在 write 里，那前后就是你的逻辑）。

## 「卡住」长什么样：没有 `=` 的那一行

strace 排查「程序卡死」是绝杀，因为**卡住的状态在流水账里一目了然**：

```text
recvfrom(5, "GET...", 512, 0, NULL, NULL) = 18      ← 正常的行：有 = 有返回值
recvfrom(5,                                          ← 卡住的行：括号没合上，没有 =
```

`recvfrom(5, ` 后面什么都没有——**这次系统调用还没返回**，
程序就停在这里等（等对端发数据）。程序「假死」时：

```bash
strace -p <PID>        # attach 到正在跑（正卡着）的进程，直接看它停在哪一句
```

最后一行没有 `=` 的调用就是卡点：等网络（recvfrom）？等锁（futex）？
等读不到的文件（read）？——行为类三秒定位，源码一个字符不用看。

## 统计视图：一百次调用一眼排序

逐行看适合找卡点；想知道「时间都花在哪类调用上」用 `-c`（count）：

```bash
strace -c ./order_feeder
```

```text
% time     seconds  usecs/call     calls    errors  syscall
------ ----------- ----------- --------- --------- ----------------
 52.31    0.034000          85       400           recvfrom     ← 400 次网络接收吃掉一半时间
 28.15    0.018300          30       610      12   read         ← 610 次读，12 次失败
 12.77    0.008300          83       100           futex        ← 等锁 100 次：有锁竞争
  ...
```

每列：`% time` 占比、`calls` 调用次数、`errors` 失败次数。
**三个一眼能下的判断**：某个调用次数远超预期（循环里多调了？）、
errors 很高（在反复失败重试？）、futex 占比高（锁竞争）。
这就是 5.2「实战分析」的入口。

## read/write 的三种返回值：行为类最高频的坑

`code/c5_3_read_semantics.c` 实测演示：`read` 的返回值**不是**「成功/失败」二值：

| 返回值 | 含义 | 常见误判 |
|--------|------|----------|
| `= 16` | 读到了 16 字节（**也可能少于你请求的**——部分读） | 以为请求多少给多少 → 数据截断 |
| `= 0` | **EOF，读完了**（不是错误！） | 当失败处理 → 「读完了却报错」 |
| `= -1 EINTR` 等 | 真错误/被信号打断 | 把 -1 当 EOF → 静默截断 |

write 同理（`= 3` < 请求的 5 说明内核只收了一部分，要循环补写）。
strace 里这些数字全部裸露——行为类 bug 一半以上是「对返回值的假设错了」。

**Q1:** strace 输出开头的 execve / brk / 一串 mmap 是什么？为什么排查时可以跳过？

> 启动段：execve 是内核加载程序本体；brk/mmap/openat libc 是动态链接器和
> C 运行时的初始化（加载共享库、建堆）——全部发生在 main 之前，与你的代码无关。
> 它们每次运行都长得几乎一样，不含 bug 信息。
> 从「能认出自己代码」的行（如 printf 内容出现在 write 里）开始看才是重点区。

**Q2:** strace 里怎么一眼认出「程序卡住了」？卡住行和返回值为 -1 的行有什么区别？

> 卡住行：右括号没合上、没有 `=` 和返回值（如 `recvfrom(5, `）——
> 系统调用**还没返回**，进程正停在里面等。-1 行是**已经返回**但报告失败
> （如 `= -1 EINTR` 被信号打断、`= -1 ENOENT` 文件不存在）——属于「有结果的失败」，
> 很多是要重试的正常路径。排查假死：strace -p attach 上去，
> 最后一行没有 = 的调用就是卡点。

**Q3:** `strace -c` 报告里 read 有 610 次调用 12 次 errors、futex 占 12%，能下哪两个初步判断？

> ①read 失败率约 2%（12/610）：程序在反复读到错误——可能是非阻塞 fd 的
> EAGAIN（正常轮询）或真的读错对象，值得用 -e trace=read 细查；
> ②futex（用户态锁）占比 12% 进前三：线程在锁上有明显等待，存在锁竞争，
> 如果程序抱怨慢，这是一个候选方向。统计视图的价值就是把「感觉慢」
> 变成「哪类调用、多少次、多少失败」的量化嫌疑名单。

**Q4:** read 返回 0 和返回 -1 各意味着什么？把两者搞反会写出什么 bug？

> 0 = EOF（对端/文件到头，正常结束信号）；-1 = 出错（看 errno 区分：
> EINTR 被打断要重试、EAGAIN 非阻塞暂无数据、EBADF 描述符坏了）。
> 搞反的两种 bug：把 0 当错误 → 「正常读完却报错退出」，程序永远跑不到
> 成功路径；把 -1 当 EOF → 遇到 EINTR/EAGAIN 就静默截断，数据丢了还不报错。
> strace 里 `= 0` 和 `= -1 XXX` 的区别一目了然。

**Q5:** 为什么排查行为类问题可以「不看源码」，而崩溃/内存类不行？

> 行为类问题的本质是「程序与内核的交互不符合预期」——卡在哪、调了什么、
> 参数和返回值是什么，这些信息全部暴露在 syscall 边界上，strace 直接可见，
> 不需要任何源码知识。崩溃/内存类的问题发生在**进程内部的指令和内存层面**
> （哪行代码、哪个变量、哪次非法访问），syscall 边界上看不到，
> 必须回到源码级工具（gdb 查 DWARF 表、ASan 插桩）。
> 这就是「行为不对先 strace，逻辑/内存不对再 gdb/ASan」的分工依据。
