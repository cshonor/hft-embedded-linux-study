# 6.0′ 第一次看热点：程序慢的时候，时间到底花在哪

> 🟢 零起点 · 接续 [1.0 学前篇](../../chapter-01-methodology/notes/00-gcc-first-steps.md)
>
> 前面五章处理的都是「程序做错了」——崩了、结果错了、漏了、卡住了。
> 这一章换一种症状：**程序没做错，只是慢**。慢和错有个本质区别：
> 错可以靠「找不同」定位，慢不行——每一行代码都「对」，但整体就是超时。
> 这时候逐行读源码几乎必输（你会均匀地怀疑每一行，而真正的元凶往往只占几行）。
> 正确答案只有一句话：**先测量，再怀疑**。
> 这一篇用两个真实 demo 把「测量」这件事看清楚：热点表长什么样、
> 为什么「加法次数一模一样」的两个循环能差 11 倍。

---

## 先立框架：性能问题的第一定律是「别猜」

人对「哪段代码慢」的直觉几乎总是错的。原因：CPU 时间的分布**极度不均匀**——
一个程序 90% 的时间常常花在 5% 的代码上（所谓热点，hotspot）。
你均匀优化的结果是：95% 的工夫花在只占 10% 时间的地方。

所以性能工具的核心动作不是「分析」，是**采样**：
每隔一小段时间问一次「程序此刻正在执行哪一行」，问几百次之后统计——
哪个函数被「抓现行」的次数最多，哪里就是热点。
这就是 perf 的全部原理（6.1 展开），也是 `c6_2` 用 60 行 C 自己实现的东西。

## 第一个实测：采样 profiler 的输出长什么样

`code/c6_2_self_sampler.c` 不装 perf，在进程内部用
`setitimer(ITIMER_PROF)`（定时器）+ `SIGPROF`（到期信号）+ `backtrace()`
（抓当前调用栈）自制了一个采样器。程序里故意埋了一个慢函数 `slow_sqrt`。
跑出来三张表，第一张长这样（gcc 13.3.0 实测）：

```text
== self 表（按函数自身耗时排序）==
  151  samples  87.8%  slow_sqrt        ← 172 次抓现行，151 次抓到它
   12  samples   7.0%  work_inner
    9  samples   5.2%  main
```

三列的读法：

| 列 | 含义 |
|----|------|
| `samples` | 定时器响了 172 次，其中多少次「抓现行」抓到这个函数 |
| 百分比 | `151 / 172 = 87.8%`——**程序近九成的时间在这一行附近** |
| 函数名 | 热点的名字，优化就冲它去 |

**这张表就是 `perf report` 的毛坯**。perf 干的是同一件事，
只是它用 CPU 硬件计数器定时（更准、开销更低）、从内核侧抓栈（不用进程配合）。
三张表的后两张也各有去处：`inclusive` 表（含子函数耗时）对应火焰图的宽度，
`collapsed`（折叠栈，一行一条调用链）就是 `stackcollapse-perf.pl` 的输出格式——
喂给 `flamegraph.pl` 就是一张真火焰图（6.2 展开）。

## 第二个实测：加法次数一模一样，为什么慢 11 倍

`code/c6_1_cache_miss.c` 是本章最反直觉的 demo：同一份矩阵求和，
**加法指令一条不多一条不少**，只改访问顺序（按行 vs 按列）：

```text
矩阵 64 MiB（4096×4096 int）：
  按行遍历：  21.4 ms
  按列遍历： 239.8 ms   ← 慢 11.2 倍
  指针追逐： 548.5 ms   ← 慢 25.6 倍

矩阵 16 MiB 时：
  按列只慢 1.4 倍       ← 尺寸变小，差距几乎消失
```

| 现象 | 原因一句话 |
|------|-----------|
| 按列慢 11 倍 | 按行访问时，CPU 缓存一次预取 64 字节（16 个 int）全用上；按列每跳一行 16 KB，每次预取只用 4 字节就扔——**缓存行命中率崩了** |
| 16 MiB 时只差 1.4 倍 | 16 MiB 整个装进 L3 缓存，怎么访问都慢不到哪去——**同样的代码，数据尺寸变了，结论就变了** |
| 指针追逐慢 25 倍 | 下一次访问的地址要读完当前内存才知道，CPU 没法预取，每次访问都是一次完整的内存往返 |

**新手从这里要带走的一句话**：「慢」不一定是算得多，常常是**等内存等得多**。
算术运算一个周期，内存往返几百个周期——所以性能分析的第一现场是缓存，
不是指令数。这也是为什么「估算复杂度」代替不了测量。

## 一次真实排查的动作序列（流程卡）

```text
① 确认「慢」是可复现的        → 跑三次取中位数，排除偶然抖动
② perf record ./program      → 采样几十秒（容器里没 PMU 权限时用 c6_2 思路代替）
③ perf report                → 看热点表：第一名是谁、占多少
④ 盯着第一名问：它为什么热？  → 算得多（算法）？等内存（缓存）？等锁（并发）？
⑤ 改完再采样                 → 热点表换了面孔才算数，「感觉快了」不算
```

第④步的三个候选方向，正好对应本模块的三章：等锁 → Ch4，
等内存/缓存 → 本章 `c6_1`，算得多 → 算法层面（超出本模块，交给 06.6）。

## 诚实边界

perf 本体在本仓库的验证环境跑不了（容器没有 PMU 权限），
所以 6.1/6.2 里 `perf stat`、`perf report` 的输出是**格式示意**。
但本章的两条结论都是**完整实测**的：采样原理（`c6_2` 自己实现了一遍）
和访存顺序的代价（`c6_1` 的 11.2 倍）。原理通了，到自己的 Linux 机器上
跑真 perf 只是换个工具壳。

**Q1:** 为什么性能问题「逐行读源码」几乎必输？

> 因为 CPU 时间分布极不均匀——90% 的时间常集中在 5% 的代码上。
> 逐行读是均匀分配注意力，大概率读到的都是不占时间的冷代码，
> 而且人对「哪段慢」的直觉几乎总是错的（尤其缓存效应完全不可目测）。
> 正确顺序是：采样 → 热点表 → 只对第一名动刀。

**Q2:** 采样 profiler 的 `samples` 列到底是什么意思？172 次采样抓到 151 次 `slow_sqrt` 说明什么？

> 定时器每隔一小段时间中断一次程序，记录「此刻正在执行哪个函数」，
> 记一次就是一个 sample。172 次里 151 次落在 slow_sqrt，
> 说明程序约 87.8% 的 CPU 时间花在这个函数上——它就是热点，
> 优化它的收益上限是总时间的 87.8%，优化其他任何函数最多撼动剩下 12%。

**Q3:** `c6_1` 里按行和按列遍历的加法次数完全相同，为什么按列慢 11 倍？16 MiB 时差距为什么缩小到 1.4 倍？

> 按行访问连续内存，CPU 每次预取的 64 字节缓存行里 16 个 int 全被用上；
> 按列每次跨一行（16 KB），缓存行只用 4 字节就作废，每次都重新等内存——
> 算术一个周期、内存往返几百周期，差距全在「等内存」上。
> 16 MiB 时整个矩阵装得进 L3 缓存，两种顺序都命中缓存，差距自然消失。
> 教训：性能结论依赖数据尺寸，换尺寸要重新测量。

**Q4:** 指针追逐为什么比按列遍历还要慢一倍多（25.6× vs 11.2×）？

> 按列遍历的地址是**规律**的（每次 +16 KB），CPU 硬件预取器能猜到下一个地址、
> 提前去取；指针追逐的下一个地址存在当前内存里，必须先读完当前值
> 才知道去哪取下一个——预取器完全失效，每次访问都是一次完整、
> 无法隐藏的内存往返。这就是链表在热路径上输给数组的根本原因。

**Q5:** 拿到热点表后，「第一名为什么热」有哪三个候选方向？分别对应什么后续动作？

> ① 算得多：算法复杂度高或做了无用功 → 换算法/删冗余计算；
> ② 等内存：缓存不命中（访问顺序差、数据结构散乱）→ 改布局/改遍历顺序（c6_1 思路）；
> ③ 等锁：线程在锁上空转 → 回到 Ch4 的手段（缩小临界区、换无锁结构）。
> 三个方向的修法完全不同，靠热点表本身分不出来，
> 要结合 perf 的事件采样（cache-misses 等）或程序特征判断——
> 这就是 6.1/6.2 展开的内容。
