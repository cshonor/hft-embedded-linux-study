# 3.2 加载 core 回溯（gdb prog core / bt / frame / 现场还原）

> 🔴 精读 · 崩溃后第一命令

## 本节要点

拿到 core 文件后，第一个动作是「加载 core → `bt` 回溯 → 看崩溃点变量」。这是把「一句 `Segmentation fault`」还原成「哪个函数、哪一行、哪个变量坏了」的标准流程。本节用 1.1 的 `orderbook` 段错误走一遍完整尸检，覆盖加载、回溯、帧穿梭、寄存器还原四个动作。

## 加载 core

```bash
# 语法：gdb <可执行文件> <core 文件>   （顺序不能反）
gdb ./orderbook core
GNU gdb ...
Core was generated by `./orderbook'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x00005555555551a7 in main () at orderbook.c:28
28          *p = 42;
(gdb)
```

gdb 一进来就告诉你两件事：**哪个信号**终止的（`SIGSEGV`）、**崩在哪一行**（`orderbook.c:28`）。这就是 core 的价值——崩溃现场被完整定格。

### 先确认 core 和二进制匹配

```bash
file core
# core: ELF 64-bit LSB core file, x86-64, ... from 'orderbook'
#                                        ^^^^^^^^^^^^^^^^^^^^ 来源程序名

gdb ./orderbook core
# 若二进制版本不匹配：
# warning: core file may not match specified executable file.
```

> core 必须和**崩溃那一刻**的二进制配对。二进制重编译过（哪怕只是加一行日志），地址就错位，回溯会指向错误行号甚至报 `??`。**归档 core 时务必连同二进制 + 符号一起存。**

## bt：回溯调用栈

```gdb
(gdb) bt
#0  0x00005555555551a7 in main () at orderbook.c:28
#1  0x00007ffff7de7d8a in __libc_start_call_main (...) at ../sysdeps/nptl/libc_start_call_main.h:58
#2  0x00007ffff7de7e45 in __libc_start_main_impl (...) at ../csu/libc-start.c:379
#3  0x00005555555550d5 in _start ()
```

```gdb
(gdb) bt full          # 每帧附局部变量（最常用）
#0  main () at orderbook.c:28
        p = 0x0            # ← 崩溃点局部变量，p 是 NULL
        head = 0x5555555592e0
        o = <optimized out>
#1  __libc_start_call_main (main=0x5555555551c0 <main>, argc=1, argv=0x7fffffffe118)
...
```

`bt full` 一次拿到「调用链 + 每层局部变量」，绝大多数崩溃一眼定位，比逐步 `next` 高效一个量级。

## 帧穿梭：逐层检查

```gdb
(gdb) frame 1          # 跳到外层帧（调用者）
(gdb) info args        # 看该帧函数参数
argc = 1
argv = 0x7fffffffe118
(gdb) up               # 再往外
(gdb) down             # 回内层
(gdb) frame 0          # 回崩溃帧

(gdb) info frame       # 当前帧完整信息
Stack level 0, frame at 0x7fffffffe100:
 rip = 0x5555555551a7 in main (orderbook.c:28)   # ← 崩溃指令地址
 rbp = 0x7fffffffe0f0, rsp = 0x7fffffffe0d0

(gdb) info locals      # 当前帧局部变量
p = 0x0
head = 0x5555555592e0
```

## info registers：寄存器现场

崩溃瞬间的寄存器是「机器级铁证」，尤其看段错误时**谁指了非法地址**：

```gdb
(gdb) info registers
rax            0x0                 0        # ← rax = 0，就是它！解引用 NULL
rbx            0x0                 0
rcx            0x5555555592e0      93824992236256
rip            0x5555555551a7      0x5555555551a7 <main+40>
...
(gdb) disassemble /m main
28          *p = 42;
   0x00005555555551a7 <+40>:  mov    -0x8(%rbp),%rax   # p → rax
   0x00005555555551ab <+44>:  movl   $0x2a,(%rax)      # ← 写 rax 指向地址，rax=0 → SIGSEGV
```

段错误的标准还原：`*p = 42` 被编译成「把 p 加载到 rax，再往 rax 指向的地址写 42」；rax 是 0，写 0 地址 → 段错误。反汇编 + 寄存器一对照，根因铁证如山。

## 完整尸检清单

| 步骤 | 命令 | 得到什么 |
|------|------|----------|
| 1. 加载 | `gdb prog core` | 信号类型 + 崩溃行号 |
| 2. 回溯 | `bt full` | 调用链 + 各层局部变量 |
| 3. 定位帧 | `frame 0` | 崩溃帧 |
| 4. 看变量 | `info locals` / `info args` | 崩溃点局部变量/参数 |
| 5. 看寄存器 | `info registers` | 哪个寄存器指了非法地址 |
| 6. 反汇编 | `disassemble /m` | 崩溃指令 + 源码对照 |
| 7. 查内存 | `x/Nx addr` | 被破坏的数据（见 3.3） |

## HFT 关联

1. **`bt full` 是崩溃响应的第一命令**：拿到 core 先 `bt full`，多数空指针/越界直接定位到函数和行，先于任何日志分析。
2. **`info registers` 看非法地址**：段错误时 `rax`/`rdi` 等寄存器直接暴露「谁指了 0 或乱码地址」，配合反汇编能确定是「空指针」还是「野指针」还是「缓冲区溢出覆盖了指针」。
3. **符号二进制成对归档**：core 无符号 = 废证。CI 流程里 release 与调试符号（`objcopy --only-keep-debug`）必须同版本归档，否则线上 core 拿回来无法回溯。
4. **`bt` 穿透库边界**：崩在 glibc/libstdc++ 内部时，`bt` 若断在库边界，是缺 debuginfo 包（`libc6-dbg`）——装上才能看到是**你的哪行代码**把坏参数传进了库。

<summary>自测题（点击展开）</summary>

**Q1:** `gdb ./orderbook core` 一加载就打印 `Program terminated with signal SIGSEGV` 和行号，这是靠什么做到的？

> 靠 core 里保存的崩溃现场（信号号、各线程寄存器、`rip` 指向的地址）+ 二进制的 `.debug_line` 段（地址↔行号映射）。gdb 读 core 拿到 `rip`，再查调试信息把它翻译成 `orderbook.c:28`。缺任何一个（没符号 / core 不匹配）都做不到精确到行。

**Q2:** 为什么 core 必须和「崩溃那一刻」的二进制配对，重编译过就不行？

> 调试信息里的「地址↔行号↔变量」映射是和**特定编译产物**绑定的。重编译后函数地址、变量偏移都变了，用新二进制加载旧 core，`rip` 翻译出的行号就是错的，甚至落到别的函数里。所以要连同崩溃时的二进制一起归档。

**Q3:** `bt` 和 `bt full` 的区别？崩溃定位为什么优先 `bt full`？

> `bt` 只列每帧函数名/地址/行号；`bt full` 额外打印每帧的局部变量。崩溃定位优先 `bt full`——它一次给出整条链上所有局部状态，`p=0x0` 这种关键证据直接摆在眼前，省去逐帧 `frame N` + `info locals`。

**Q4:** 段错误崩溃，为什么看 `info registers` 能立刻知道「解引用空指针」还是「野指针」？

> 崩溃指令（如 `movl $0x2a,(%rax)`）往 `rax` 指向的地址写。`info registers` 里若 `rax = 0x0`，是**空指针**解引用；若 `rax` 是某个看似合法但已失效的地址（如已 free 的堆、被覆盖的栈），则是**野指针**或缓冲区溢出。寄存器值直接区分这两类。

**Q5:** 崩溃点 `#0` 帧是 `main`，但真实根因可能在库函数里，怎么找？

> 顺着 `bt` 往外层帧看：如果 `#0` 崩在 `strlen`/`memcpy` 等库函数，说明是**调用者**把坏指针传了进来——检查 `#1`/`#2` 帧（你的代码）里传给库的指针参数（`info args`），往往那里才是根因。这也解释了为何 `bt` 要看完整调用链而非只看 `#0`。
