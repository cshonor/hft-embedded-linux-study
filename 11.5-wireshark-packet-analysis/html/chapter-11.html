11.1

TCP 的错误恢复特性

本章：chapter-summary.md · 全书：../README.md · 入门：§8.1 延伸 · Expert：§5.8

核心主旨：高延迟/卡顿优先看 重传、重复 ACK、快速重传——TCP 自愈机制在包里的留痕。

核心知识点

11.1.1 TCP 重传（Retransmission）

概念 说明
用途 应对丢包（拥塞、队列满、链路错误、应用停读等）
RTT 发段 → 收到对应 ACK 的时间
RTO 由 RTT 样本估算的重传超时阈值

指数退避（超时重传）

发段并启动计时器
  → RTO 内无 ACK → 认为丢失，重传
  → RTO 翻倍，再重传…
  → 直到收到 ACK 或达最大重传次数（Windows 常 5，Linux 常 15）→ 断开
Wireshark 表现
列表 常 黑底红字 [TCP Retransmission]
Details SEQ/ACK analysis 中可见 RTO、与上次发送间隔

过滤器：tcp.analysis.retransmission · tcp.analysis.rto

11.1.2 重复确认与快速重传

序号规则：收到的 Seq + 载荷长度 = 发出的 Ack（期望下一字节）

事件 说明
Duplicate ACK 收到乱序段 → 认为中间有洞 → 重复发送期望 Seq 的 ACK
Fast Retransmission 发送方连续收到 3 个重复 ACK → 不等 RTO 立即重传丢失段
SACK TCP 选项选择性确认 → 只重传丢失段，不必重传洞后全部
Wireshark 过滤器
Dup ACK tcp.analysis.duplicate_ack
快速重传 tcp.analysis.fast_retransmission

因果链（简）

丢包 → 接收端 Dup ACK ×3+ → 发送端 Fast Retransmit
     或 超时 → Retransmission（RTO 退避，更慢）

拓展：SACK 在 Options 中为左右边界块；tcp.options.sack 过滤（视版本）。

抓包/实操记录

练习 操作
找重传 Expert → Warning；tcp.analysis.retransmission
对比 同连接是否先出现 3× Dup ACK 再 Fast Retrans
RTT 图 Statistics → TCP Stream Graphs → Round Trip Time 
tshark -r slow.pcapng -Y "tcp.analysis.retransmission" -T fields -e frame.time_relative -e tcp.seq -e tcp.analysis.rto

疑问与总结

  • 超时重传比快速重传更伤延迟（RTO 指数增大）。
  • 抓包点若在接收端，可能看不到重传包本身，但能看到 Dup ACK（见 §11.3）。
11.2

TCP 流控制

本章：chapter-summary.md · 全书：../README.md

核心主旨：滑动窗口按接收缓冲调节速率；零窗口 = 接收方「装不下」→ 卡顿数十秒。

核心知识点

11.2.1 调整窗口大小

项 说明
Receive Window TCP 头字段，告知发送方还可发送多少字节未确认数据
动态 接收方处理慢 → 后续 ACK 中 Window 减小 → 发送方降速
恢复 缓冲释放 → Window 增大

Wireshark：展开 TCP 头 Window size；启用 Window size scaling 因子（选项）。

11.2.2 零窗口与恢复

项 说明
Zero Window Window = 0 → 发送方停止发数据
Keep-Alive 发送方周期性探针（非应用心跳）询问是否恢复
Window Update 接收方 Window 变非零 → 恢复传输

过滤器：tcp.analysis.zero_window · tcp.analysis.window_update · tcp.analysis.keep_alive

11.2.3 滑动窗口实战表征

时序 特征
恶化前 多个 ACK 中 Win 急剧递减
触发 [TCP ZeroWindow]
之后 [TCP Keep-Alive] 间隔常成倍增加（如 3.4s → 6.8s → 13.5s）
用户感知 长时间「卡住」（打嗝）

TCP Stream Graph → Window Scaling：对照吞吐塌陷与 Zero Window 时刻。

与 §10.4 打印机 案例一致：接收端设备/服务瓶颈。

抓包/实操记录

任务 操作
列零窗口 tcp.analysis.zero_window
看谁发的 Zero Window 包 源 IP = 背压方（常为服务器）
IO Graph bytes/s 在 Zero Window 后近 0

疑问与总结

  • 零窗口 ≠ 路由器拥塞；优先查接收主机 CPU/内存/应用读 socket 慢。
  • 发送方也有窗口（拥塞窗口），本章侧重 接收窗口 导致的停流。
11.3

从 TCP 错误控制和流量控制中学到的

本章：chapter-summary.md · 全书：../README.md · 抓包点：第2章

核心主旨：在哪抓才能看到重传 vs 重复 ACK；零窗口把锅甩给主机性能。

核心知识点

三条排障选址法则

现象 包在哪出现 嗅探器应放
重传 由发送方再发丢失段 发送端或靠近发送端（客户端上传慢 → 客户端侧；下载慢 → 服务器侧或客户端看 Dup ACK）
Duplicate ACK 接收方发现乱序后发出 接收端或靠近接收端
Zero Window 接收方宣告无缓冲 在宣告方抓包最清晰；责任在该主机性能

记忆口诀

看重传 → 去发送端
看 Dup ACK → 去接收端
看 Zero Window → 接收端背压，查主机不查光缆（先）

与第 10 章对照

案例 TCP 线索
丢失网页 SYN 黑洞 重传，无 Dup ACK（对端无响应）
打印机 Zero Window + 重传
上游 SYN 黑洞 重传，非零窗口

抓包/实操记录

场景 建议
用户抱怨「下载慢」 客户端抓：看 Dup ACK / 下行重传
用户抱怨「上传慢」 服务器或客户端抓：上行重传
服务端卡 服务器抓：Zero Window 由谁发出

疑问与总结

  • 镜像口单向时可能只见一侧重传；必要时两端各抓一段对照。
  • 无线/高丢包：Dup ACK 与重传可能非常多，先 tcp.stream eq N 隔离单连接。
04

latency-locate-framework

本章：chapter-summary.md · 全书：../README.md · HTTP：§9.3

核心主旨：用握手与 HTTP 前几个包的 Time Delta，把延迟钉在线路 / 客户端 / 服务端之一。

核心知识点

11.4.1 正常通信基准

阶段 正常量级（教材参考）
SYN → 完成握手 + HTTP GET 发出 + 服务器首包 HTTP 数据 全程常 < 0.1s（局域网/优质链路）

广域网/移动网放宽，但同环境前后对比更重要。

11.4.2 慢速通信—线路延迟

测量 SYN → SYN/ACK 间隔巨大（如 >0.8s）
逻辑 握手由内核完成，无应用负载 → 慢在路径设备/距离/丢包重传
排查 路由、防火墙、VPN、物理链路；非 Web 服务器代码

列：Time 格式选 Delta 或 Relative，看包 1–2 间隔。

11.4.3 通信缓慢—客户端延迟

测量 握手末 ACK → 首个 HTTP GET 间隔大（如 >1.3s）
逻辑 链路已通；慢在浏览器/杀软/代理/本机 CPU 构建请求
排查 客户端进程、扩展、系统负载

11.4.4 通信缓慢—服务器延迟

测量 服务器 ACK（确认 GET） → 首个 HTTP 响应数据 间隔大（如 >0.9s）
逻辑 网络与客户端请求正常；慢在服务端应用（DB、脚本、磁盘）
排查 应用日志、DB、线程池；非交换机

11.4.5 延迟定位框架（黄金法则）

SYN ──[ 线路延迟 ]──► SYN/ACK

ACK（握手完成）──[ 客户端延迟 ]──► 第7层请求（HTTP GET）

ACK（确认收到 GET）──[ 服务端延迟 ]──► 第7层响应数据
Wireshark 技巧 说明
Time Delta 列显示与上一包间隔
tcp.time_delta 显示过滤器（字段视版本）
自定义列 frame.time_delta_displayed
Transcalc 等插件 批量统计握手各段（拓展）

抓包/实操记录

练习 步骤
标三段时间 单 tcp.stream + HTTP，Delta 列读三段
对照 baseline 用 §11.5 正常 HTTP 抓包对比
tshark -T fields -e frame.number -e frame.time_delta -e http.request

疑问与总结

  • HTTPS 需在解密后看 HTTP 时间点，否则只能测 TLS 握手各段。
  • 慢可能是多段叠加；分别量再相加，勿只凭总时间猜。
05

network-baseline

本章：chapter-summary.md · 全书：../README.md · 第3章基线：§3.4 · 统计：第5章

核心主旨：故障前在正常时存 pcap + 统计快照，对比 Protocol Hierarchy、吞吐与 TCP 行为。

核心知识点

11.5.1 站点基线（Site Baseline）

项 说明
抓包位置 边缘：核心路由、防火墙、出口镜像
记录 Protocol Hierarchy 各协议 %；总 pps/bps（IO Graph）
用途 发现 ARP 风暴、未知协议、整体流量结构漂移

11.5.2 主机基线（Host Baseline）

项 说明
位置 关键服务器/设备本机或镜像口
内容 开机/关机广播；依赖 IP 列表（必须连上的 DNS、DB、域控）
用途 故障时看「该连的没连」还是「协议异常」

11.5.3 应用程序基线（Application Baseline）

项 说明
位置 跑业务的服务器侧
内容 正常端口与协议；IO Graph 峰值/均值 bps
用途 区分「链路限速」vs「应用真打满」

11.5.4 注意事项

策略 说明
三时段采样 早晨低负载、下午高峰、深夜空闲
勿高峰本机抓 关键服务器上 live 抓包耗 CPU/磁盘 → 用 TAP/SPAN 或短时 -c
命名 site-baseline-YYYYMMDD-peak.pcapng

与 §10.1 对比：无 baseline 难发现「第 8 会话」异常。

抓包/实操记录

交付物 内容
pcapng 每类 baseline 至少一份
截图/表 Hierarchy %、Top Conversations、正常 HTTP 三段时间
CLI tshark -r base.pcapng -q -z io,phs 输出存档

疑问与总结

  • Baseline 要定期更新（应用升级、IPv6 双栈上线会改分布）。
  • 合规：baseline 可能含敏感流量，存储需授权。
