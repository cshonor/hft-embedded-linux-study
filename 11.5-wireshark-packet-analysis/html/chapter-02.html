2.1

混杂模式

本章：chapter-summary.md · 全书：../README.md · 回顾：§1.1 嗅探器三步

核心主旨：数据包嗅探的底层硬件/驱动前提——混杂模式的定义，以及为何跨主机分析必须开启它。

核心知识点

混杂模式（Promiscuous Mode）

核心结论：混杂模式下依然会检测 / 读取帧里的 MAC 地址，只是不再执行「目的 MAC 非本机 → 硬件直接丢弃」这条规则。

1. 普通模式（默认）

网卡收到帧 → 硬件比对目的 MAC
  ├─ 匹配本机 MAC → 收下，上传系统
  └─ 不匹配 → 硬件直接丢弃，数据不进系统

→ 网卡四功能中的 MAC 硬件过滤

2. 混杂模式（Promiscuous Mode）

网卡收到帧 → 仍会读取、识别帧内 MAC
  └─ 关闭硬件丢弃规则 → 无论目的 MAC 是否本机，帧都上交操作系统
       └─ 是否过滤、分析 → 由系统 / Wireshark 显示过滤器决定
对比项 普通模式 混杂模式
是否读 MAC ✅ ✅
非本机单播 硬件丢弃 上交系统
谁做后续筛选 网卡硬件 OS / 抓包工具

无线网卡：混杂实现与有线略有差异（驱动、Monitor 模式等），但逻辑一致——MAC 仍会识别，只是放弃硬件层过滤；部分芯片/驱动不支持或受限（见下文兼容性）。

仍受 交换机端口转发 限制：混杂 ≠ 一定能看到全网单播（见 §2.3）。

广播域与可见流量

在局域网（同一广播域）内：

流量类型 不开启混杂 开启混杂
广播（ARP 等） ✅ 可见 ✅ 可见
发往本机单播 ✅ 可见 ✅ 可见
其他主机之间单播 ❌ 不可见 ✅ 可见（前提是帧能到达本端口）

不开启混杂时，嗅探器无法分析 A↔B 的通信细节，只能看到广播 + 与自己相关的包。

权限门槛

系统 典型要求
Windows 管理员
Linux / macOS root 或 CAP_NET_RAW / CAP_NET_ADMIN

Wireshark：安装 Npcap/WinPcap 时勾选「以管理员启动」；Linux 可将用户加入 wireshark 组并配置 dumpcap 权限。

合规：无法在系统上合法取得相应权限时，不应强行嗅探。

抓包/实操记录

平台 开启混杂（示例）
Linux sudo ip link set eth0 promisc on；关闭：promisc off
旧式 ifconfig eth0 promisc
Wireshark 捕获选项 → 勾选对应接口 Promiscuous mode

兼容性：部分无线网卡、虚拟网卡、云主机不支持或受限混杂；抓不到他人单播时先查驱动/虚拟化文档，而非只调过滤器。

疑问与总结

  • 易错：混杂 ≠ 「不检查 MAC」；是 仍检查 MAC，但不硬件丢弃非本机帧。
  • 混杂模式 ≠ 一定能看到全网流量；交换机仍可能不把他人单播送到你的端口（需镜像/TAP/Hub/ARP 等手段，见 §2.3）。
  • 与 §1.3 流量分类 对照：广播人人收得到，单播跨主机分析才强依赖混杂。
02

sniff-on-shared-network

本章：chapter-summary.md · 全书：../README.md · 回顾：§1.2 Hub

核心主旨：Hub 环境下的监听原理，以及该架构因半双工与碰撞在现代网络中被淘汰的原因。

核心知识点

工作原理

  • 集线器（Hub）：L1 设备，将收到的帧盲目中继到每一个端口（共享冲突域）。
  • 嗅探部署：嗅探器接 Hub 任意空闲端口 → 获得本地网段几乎不受限制的可视范围（无需端口镜像）。
  • 仍需网卡 混杂模式，以便处理「目的 MAC 为他人」的帧。

性能缺陷与碰撞

特性 后果
半双工（Half-duplex） 同一时刻只允许一台设备发送
冲突碰撞（Collision） 多机同时发 → 线路上冲突 → 丢包
重传 设备退避后重传；高负载下可能重传 3–4 次，性能急剧下降

CSMA/CD（载波侦听多路访问 / 冲突检测）：发送前侦听线路；冲突后随机退避再试。抓包可见重传、延迟抖动；现代以太网接入几乎全用交换机全双工，Hub 场景少见。

现存场景

  • 老旧布线、实验室、部分 工业控制系统（ICS） 仍可能使用 Hub 或类 Hub 拓扑。

抓包/实操记录

实验 说明
验证 Hub 两台 PC + 嗅探器接同一 Hub，A ping B，嗅探器应同时看到请求/应答（双向单播）
对比交换机 改接交换机普通口 → 通常只能看到广播 + 本机流量（为 §2.3 做对照）

疑问与总结

  • Hub 嗅探「简单」但拖慢全网；生产排障优先 SPAN 镜像 / TAP，而非人为加 Hub。
  • 市面「假 Hub」实为交换机，互嗅测试失败 → 见 §2.3.2。
03

sniff-on-switched-network

本章：chapter-summary.md · 全书：../README.md

核心主旨：交换机按 CAM 表精准转发，普通端口可视范围极窄；必须用镜像、Hub 介入、TAP 或 ARP 污染之一扩大可见流量。

核心知识点

逻辑前置

  • 交换机：全双工 + 单播只出目的端口。
  • 嗅探器直连普通口：只见 广播/组播 + 本机收发。
  • 要分析他人通信 → 下面四种技术至少择一。

2.3.1 端口镜像（Port Mirroring / SPAN）

项 说明
做法 在交换机 CLI/Web 将若干源端口流量复制到目的端口（接嗅探器）
优点 不改终端拓扑、可在线配置、不留伪造包脚印（首选）

易错 / 高危：流量过载

例：23 个全双工 100Mbps 口 → 镜像到 1 个 100Mbps 口
理论峰值可达 23×100×2 ≈ 4600Mbps >> 单口上限
后果 说明
镜像口丢包 抓到的 pcap 不完整
交换机背板压力 极端时内部交换受阻，全网变慢甚至中断

实践：只镜像必要端口；目的口速率 ≥ 源口聚合峰值；高负载用 10G 镜像口 或 TAP。

2.3.2 集线器输出（Hubbing Out）

Hub 原理（物理层、全网泛洪、半双工）：TCP/IP §3.2 Hub

[交换机] —— [Hub] —— 目标主机
              └── 嗅探器
项 说明
逻辑 物理串入目标线路，Hub 再次广播该主机进出流量
优势 交换机不支持镜像、且有物理接触权时的替代
劣势 目标链路降为 半双工 → 性能下降、碰撞风险
避坑 必须是真 Hub（10Mbps 常见）；「假 Hub」实为交换机 → 两台电脑互嗅验证

2.3.3 网络分流器（Network Tap）

项 说明
定义 串联在线路两端的硬件探针，旁路复制比特流，尽量不干扰业务
适用 千兆/万兆、光纤、需无痕且镜像口不够用时
类型 端口 特点
聚合 Tap（3 口） 1 个 Monitor 双向流量合到单监听口；1 块网卡即可
非聚合 Tap（4 口） Monitor A / B 入向、出向分口；需双网卡或合并分析

选型：一般优先聚合（线材少）；极高带宽或必须严格区分方向时用非聚合。

2.3.4 ARP 缓存污染（ARP Cache Poisoning）

机制 说明
ARP 信任 设备会接受未请求的 ARP 应答（Gratuitous ARP）并更新缓存
MITM 思路 向目标与网关各发伪造 ARP，使双方把对方 IP 映射到攻击者 MAC
结果 流量经嗅探机转发 → 可见双向通信
风险 说明
拓扑被改写 违背「无痕」原则
瓶颈 目标 1Gbps、嗅探机 100Mbps → 嗅探机成瓶颈，类似 DoS
丢包 分析数据严重不完整，业务瘫痪

进阶（了解）：部分工具支持非对称 ARP 污染，只劫持单向以减轻负载——仍属高风险，仅授权渗透/实验环境使用。

警示：交换机无镜像、主机又不能下线时的急救手段；日常排障优先镜像 / TAP。

抓包/实操记录

场景 建议
企业接入交换机 配置 SPAN，Wireshark 接镜像口
数据中心 TAP + 聚合口进采集机
实验 MITM 虚拟机内 arpspoof / 仅隔离 lab；抓包看网关 MAC 是否变为攻击机
过滤器 镜像后仍用 host x.x.x.x 缩小范围

疑问与总结

方法 无痕 性能影响 权限/条件
端口镜像 ✅ 镜像口过载风险 需管交换机
TAP ✅ 极低 需断线串联、预算
Hub out 中 半双工降级 物理接触
ARP 污染 ❌ 可能灾难性 高权限 + 法律授权
  • 与 §2.5 选型表对照决策。

sniff-on-routed-network

本章：chapter-summary.md · 全书：../README.md

核心主旨：多网段拓扑下，嗅探器物理位置决定你能看到什么；跨网段排障必须结合广播域边界与网络地图。

核心知识点

广播域边界

  • 广播（含 ARP 泛洪）在 路由器/三层边界 处终止。
  • 跨网段单播由路由器按路由表转发，不会出现在源网段交换机上（除非镜像了路由器端口）。

跨网段排障逻辑

客户端（网段 D）→ 请求发出 → 在 D 段抓包：只见请求，不见应答？
错误结论 正确思路
「服务器坏了」 应答可能只在上游网段 B 或服务器所在网段出现
盲目改服务器 将嗅探器移到 路由器上游/服务器侧 交叉验证
上游也看不到该包 可能原因
路由错误 静态路由/策略路由指错
ACL / 防火墙 路由器丢弃
NAT 改写 需在对称路径抓包

网络地图（拓扑图）

  • 多网段嗅探前必备：网段、网关、关键服务器、镜像/TAP 点。
  • 排障大量时间应用在：对照拓扑选抓包点，而非盲目加长捕获时间。

拓展：动态路由（OSPF/BGP）可能导致非对称路径（去程≠回程网段）→ 需在多条路径或路由器接口分布式抓包后合并分析。

抓包/实操记录

步骤 操作
1 画/拿出拓扑：客户端网段、默认网关、服务器网段
2 在客户端侧抓：确认 SYN/请求是否发出
3 在网关 LAN 口或服务器侧抓：是否有 SYN-ACK/应答
4 对比 TTL、MAC、是否经 NAT 转换

过滤器：ip.addr == 服务器IP 在两侧同时用，比对「有去无回」停在哪一跳。

疑问与总结

  • 路由器是广播域分割点；与 §1.2 交换机 vs 路由器 一致。
  • 「看不见应答」≠ 应用层故障，先证伪路径与路由。
05

deployment-guidelines

本章：chapter-summary.md · 全书：../README.md

核心主旨：五种监听手段的选型准则与「无痕取证」原则——在真实环境中如何选方案、避免误导性抓包。

核心知识点

五种方案对比

优先级 方案 适用场景 优点 缺点 / 警告
1 端口镜像 有管交换机、日常排障 首选；不脱机、不注入伪造包、脚印最小 镜像口过载会丢包/伤交换机
2 网络 TAP 千兆/万兆、光纤、高负载 硬件级无痕、跟得上线速 成本高、常需短暂断线安装
3 集线器输出 无镜像、可短暂下线、有物理权限 实现简单 真 Hub 多仅 10Mbps；半双工；假 Hub 无效
4 ARP 缓存污染 不能下线、无镜像的急救 可看到经 MITM 的流量 草率（Sloppy）；注入伪造包、改拓扑、DoS 风险
5 目标主机本机抓包 功能测试、事后分析已有 pcap 零额外硬件 排障不推荐：OS/驱动/防火墙故障会扭曲或丢包，误导结论

决策流程（简图）

能配置交换机？
  ├─ 是 → 端口镜像（控制镜像带宽）
  └─ 否 → 能物理串联 TAP？
        ├─ 是 → TAP（高速首选）
        └─ 否 → 能 Hub out 且接受降速？
              ├─ 是 → 真 Hub 验证后使用
              └─ 否 → 仅授权场景考虑 ARP 污染
本机抓包 → 仅作辅助或复现，不作唯一证据

「无痕取证」原则

  1. 尽量不改变原有拓扑与流量路径（优先镜像/TAP）。
  2. 不注入可改变转发表的协议包（ARP 污染违背此条）。
  3. 记录抓包点、时间、过滤器，便于与他人 pcap 对照。
  4. 镜像/TAP 过载导致丢包时，在报告中注明 capture loss，避免过度解读。

虚拟化（拓展）

环境 要点
VMware vSwitch 端口组开启 Promiscuous；分布式交换机用 端口镜像
Hyper-V 虚拟交换机扩展、端口镜像策略
Docker/K8s 宿主机 tcpdump on veth；服务网格侧车抓包

需在虚拟管理层开权限，与物理混杂模式概念类似但配置入口不同。

抓包/实操记录

任务 检查清单
上线前 拓扑图、镜像源/目的口速率、Wireshark 磁盘空间
抓包中 包速率是否逼近镜像口上限（统计 → I/O Graph）
收尾 标注抓包点、是否可能丢包、是否使用 ARP 污染

疑问与总结

  • 默认答案：有交换机 → 镜像；线速/光纤 → TAP；勿把 ARP 污染当常规工具。
  • 本机抓包适合开发调试；生产跨主机问题应在链路上取证。
