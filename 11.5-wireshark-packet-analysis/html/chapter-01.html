01

what-is-packet-analysis

本章：chapter-summary.md · 全书：../README.md

核心主旨：明确数据包分析的基础概念及其实现工具，阐述数据包嗅探器从网络线缆获取数据并转化为可分析信息的完整工作流程。

核心知识点

关键定义

术语 说明
数据包分析（Packet Analysis / Protocol Analysis） 又称数据包嗅探、协议分析；捕获并解析线路上传输的数据，弄清网络上真实在传什么，用于排性能、安全等问题。
数据包嗅探器（Packet Sniffer） 执行上述过程的工具；在网络介质上捕获原始传输数据。

嗅探器三步工作流

线缆原始比特 → [1 收集] → [2 转换] → [3 分析] → 可读结论
  1. 收集（Collect） - 从网线/无线介质抓取二进制原始数据；流量必经本机网卡（有线 / 无线职责相同）。 - 正常模式：硬件比对目的 MAC → 匹配本机才上传，不匹配则硬件丢弃（见 网卡四功能）。 - 混杂模式：仍读 MAC，但关闭硬件丢弃规则 → 非本机帧也上交系统，再由 Wireshark 过滤/分析 → §2.1。
  2. 转换（Convert） - 把二进制数据包转成人可读格式：解析各层协议头，把字段译成 IP、端口、TCP 标志位等。 - tcpdump 等轻量命令行工具通常只做到传输层：链路/网络/传输层可结构化输出；应用层 payload 多为十六进制 + ASCII 原样，不做 HTTP/DNS/TLS 等协议语义解码（见下节）。
  3. 分析（Analyze） - 在「转换」之上做全层、协议级理解：HTTP 方法/路径、DNS 查询名、TLS 握手类型等，并支撑过滤器、统计、排障结论。 - Wireshark / tshark 强项在此；tcpdump 偏「抓到 + 读到 L4」，应用层靠人工看 hex 或离线交给 Wireshark。

「转换」分层对应（TCP/IP）

层 典型协议 / 内容 人可读示例
应用层 HTTP、HTTPS、FTP、DNS、SSH URL、命令、文本
传输层 TCP、UDP 端口、seq/ack、窗口、标志 SYN/ACK
网络层 IP 源/目的 IP、TTL、协议号
链路层 Ethernet MAC、帧类型
物理层 电/光信号 纯比特流（工具先拼成帧再往上解析）

网线里跑的是 0/1；嗅探器把比特流拼成帧/包，再逐层解析头部。

tcpdump 止步在哪一层

默认输出示例（已结构化到 IP + TCP，即网络层 + 传输层）：

12:34:56 IP 10.0.0.1.1234 > 10.0.0.2.80: Flags [P.], seq 1:100, ack 1, win 65535
层次 tcpdump 典型能力
链路 / 网络 / 传输 ✅ 结构化、人可读（IP、端口、TCP 标志、序号等）
应用层 ❌ 不深度解析；payload 多用 hex + ASCII（-X / -xx / -A），无「GET / HTTP/1.1」级字段拆解

一句话：比特流 → 地址、端口、标志可读；tcpdump 轻量止步 TCP/UDP，应用层 payload 原样呈现，不做协议级解码。

工具横向对比（解析深度）

工具 解析深度 适用
tcpdump 通常到 传输层；应用层 raw 服务器脚本、轻量抓包、先落盘
tshark 可到 应用层（HTTP、DNS、TLS 等字段） 命令行全解析、自动化
Wireshark 全层 + 协议树可视化 学习、日常排障

跨平台：Linux / macOS / Windows（Windows 多用 tshark 代替 tcpdump）。大流量：tcpdump 落盘 → Wireshark 离线打开 .pcap。
输出选项详解：§6.4 控制输出

网卡在嗅探中的位置（与交换机无关）

网卡做（本机） 嗅探器额外要
信号转换、成帧/解帧、MAC 过滤、收发 捕获：混杂 = 仍识 MAC，不硬件丢非本机帧
❌ 不做 MAC 查表、跨口转发 后续过滤在 OS/Wireshark；能否看到别人单播还受交换机限制（§2.3） 
应用/TCP/IP → 网卡封装成帧 → 线缆
线缆 → 网卡（MAC 过滤）→ 协议栈     ← 正常上网
线缆 → 网卡 → Npcap/驱动 → Wireshark  ← 嗅探（常 + 混杂）

抓包/实操记录

步骤 操作
混杂模式 Wireshark：捕获选项 → 勾选对应接口的混杂模式（部分驱动/无线网卡受限）
验证三步 抓一段浏览网页流量 → 看 Frame（收集）→ 协议树展开（转换+分析）
过滤器入门 只看 HTTP：http；只看某 IP：ip.addr == x.x.x.x → 详见 cheatsheet/notes.md

验证 tcpdump「止步传输层」（Linux / macOS）

# 默认：只见 IP/TCP 一行摘要
sudo tcpdump -i eth0 -c 3 host 10.0.0.2 and port 80

# 看链路层 MAC（-e）
sudo tcpdump -i eth0 -c 3 -e

# 应用层 payload：hex + ASCII，仍非 HTTP 字段解析（-X）
sudo tcpdump -i eth0 -c 1 -X host 10.0.0.2 and port 80

# 只要 ASCII 侧（-A）
sudo tcpdump -i eth0 -c 1 -A host 10.0.0.2 and port 80

# 对比：tshark 同一包可展开 http 树
tshark -i eth0 -c 1 -Y "http" -V

同一 .pcap 用 Wireshark 打开 → 协议树可展开 HTTP 字段，与 tcpdump -X 对照。

疑问与总结

  • 嗅探 vs 分析：嗅探强调「抓到」；分析强调「读懂协议与行为」——Wireshark 覆盖转换+分析全层；tcpdump 转换多止步 L4，分析靠人眼或离线 GUI。
  • 转换 vs 分析：转换 = 二进制 → 可读字段；分析 = 应用层语义 + 排障结论。tcpdump 默认只做前者到传输层为止。
  • 为何要开混杂：默认硬件丢弃非本机 MAC 的帧；混杂后帧仍进系统，由工具筛选（且帧须能到达本端口）。
  • 易错：混杂 ≠ 不检查 MAC；是仍检查，但不硬件丢弃。
  • 网卡 ≠ 交换机：网卡只决定本机收不收；不会替别的设备转发帧。
  • 合法边界：仅在自己有权管理的网络或实验环境抓包；生产网需合规授权。
02

network-communication-basics

本章：chapter-summary.md · 全书：../README.md · 对照：自顶向下 §1.5 协议分层

核心主旨：阐述协议与协议栈、OSI 七层、封装/解封装及 Hub/交换机/路由器分工，为后续逐层读包打基础。

核心知识点

协议与协议栈

概念 要点
协议（Protocol） 设备间的「共同语言」：如何寻址、建连/断连、协商参数（如加密）、字段顺序、差错检测与恢复。
协议栈（Protocol Stack） 多协议协同组成的逻辑组合（如 HTTP → TCP → IP → 以太网）。

OSI 七层（抓包时怎么对号入座）

层 名称 职责 典型协议/设备
7 应用层 用户可见的服务与 API HTTP、DNS、SMTP
6 表示层 编码、压缩、加密 TLS 常与此层概念重叠
5 会话层 会话建立/维护/终止 现代栈多并入应用层
4 传输层 端到端可靠/不可靠、端口 TCP、UDP
3 网络层 逻辑寻址、路由、分片 IP、ICMP；路由器
2 数据链路层 帧、MAC 寻址 以太网、Wi‑Fi；交换机
1 物理层 电气/比特传输 线缆、信号；集线器

排障黑话：「第 8 层问题」= 用户操作失误（输错密码、插错线），不是协议栈真有一层。

层级规则：每层只与相邻上下层交互；发送端 7→1 封装，接收端 1→7 解封装。

数据封装（Encapsulation）

应用数据
  ↓ +应用头/语义
  ↓ +TCP/UDP 头  → 段（Segment）
  ↓ +IP 头       → 包（Packet）
  ↓ +以太网头尾  → 帧（Frame）
  ↓ 物理比特     → 比特（Bits）
  1. 每层向下传递前加上本层 Header / Trailer，形成 PDU。
  2. 接收端自底向上逐层剥头，最上层还原应用数据。
  3. Wireshark 协议树从上到下展示的，正是解封装后各层字段。

PDU 名称速记：L1 比特 · L2 帧 · L3 包 · L4 段 · L5–7 常统称报文/数据。

三类硬件（与抓包位置）

设备 工作层 行为 抓包提示
集线器 Hub L1 半双工；广播到所有端口；非目标 MAC 由终端丢弃 冲突域大、冗余流量多；现已少见
交换机 Switch L2 CAM 表 按 MAC 转发到特定端口；全双工 同一 VLAN 内单播通常只到目的端口；要见他人流量需镜像端口或 TAP
路由器 Router L3 跨网段/广播域转发、选路 抓 WAN/LAN 网关两侧可见不同网段包

封装案例（读包锚点）

HTTP over TCP over IP over Ethernet（浏览器访问网站典型栈）：

[以太网头][IP 头][TCP 头][HTTP 请求/响应] [FCS]

在 Wireshark 中展开顺序：Ethernet II → Internet Protocol → Transmission Control Protocol → Hypertext Transfer Protocol。

抓包/实操记录

实验 做法
看封装层次 抓访问 http://example.com（或 HTTPS 看 TLS 层）→ 展开协议树对照上表
区分 L2/L3 同一帧内看 Destination MAC（L2）与 Destination IP（L3）是否指向网关
镜像口 在交换机上配置 SPAN/端口镜像 才能把他人单播流量复制到嗅探口

疑问与总结

  • OSI 是教学模型；实网抓包以 TCP/IP 四层对照更顺手（应用 / 传输 / 网际 / 链路），本书与 Wireshark 显示一致即可。
  • 交换机不会替你做 L3 路由；路由器不学习终端 MAC 表项（下一跳除外）——排障先问「包停在哪一层设备」。
1.3

流量分类

本章：chapter-summary.md · 全书：../README.md

核心主旨：按目标范围与传播机制划分广播、组播、单播，理解交换机/网卡如何处理不同流量，便于抓包时识别「正常泛洪」与异常风暴。

核心知识点

三类流量对比

类型 定义 典型地址/场景 对网络的影响
广播 Broadcast 发往本网段所有端口 L2：FF:FF:FF:FF:FF:FF（如 ARP）；L3：主机号全 1 的子网广播 每台主机网卡都会收到；驱动可早期丢弃非本机 ARP 响应，但广播过多仍拖慢网段
组播 Multicast 一份源 → 多个明确加入的接收者 IPv4：224.0.0.0–239.255.255.255；以太网组播 MAC 映射 节省带宽；需 IGMP 等加入组；交换机可对组播做有限泛洪或 snooping
单播 Unicast 点对点 一台到一台 客户端 ↔ Web 服务器、日常 TCP 连接 交换机按 CAM 表精确转发；抓包默认所见多为单播

广播（Broadcast）

  • 机制：无论下挂 Hub 还是 Switch，二层广播帧会泛洪到 VLAN 内所有端口（除生成树阻塞口等例外）。
  • L2 例：ARP 请求「谁是 192.168.1.1？」→ 目的 MAC 全 F。
  • L3 例：子网内 DHCP Discover 等。
  • 性能：仅一台主机需响应时，其余主机在驱动层丢弃，但仍占用链路带宽；广播风暴 = 异常大量广播导致拥塞。

组播（Multicast）

  • 目的：视频流、路由协议（OSPF 等）、部分发现协议——一份拷贝多接收者，避免 N 份单播复制。
  • 编址：接收方加入组（IGMP / MLD）后，网络才向该组转发；未加入者不应收到应用层有效载荷。
  • 与广播区别：广播 = 网段所有人；组播 = 订阅组的成员。

单播（Unicast）

  • 机制：源/目的 MAC、IP 均指向具体接口；二层交换机查 CAM 表只出对应端口。
  • 抓包：本机网卡在非混杂模式下，通常只见发给自己的单播 + 广播/部分组播。

读包识别速查

Wireshark 显示 判断
Ethernet 目的 MAC = ff:ff:ff:ff:ff:ff 二层广播
ip.dst 为 x.x.x.255 或子网广播地址 三层广播
ip.dst 在 224.0.0.0/4 IPv4 组播
目的 MAC/IP 均为单播地址 单播

抓包/实操记录

实验 预期
ARP arp 过滤器 → 见广播请求、单播应答
组播（可选） 同网段播放组播流或 ping 224.0.0.1（视 OS/策略）→ 观察目的 IP 段
风暴排查 统计 → Endpoints / Protocol Hierarchy 看广播占比是否异常飙升

拓展：IGMP 加入/离开报文；广播风暴时结合端口计数与 STP 状态（见 TCP/IP 链路层笔记）。

疑问与总结

  • 为什么 ARP 用广播问、单播答？ 问的时候还不知道对方 MAC；答的时候已知道请求方 MAC。
  • 混杂模式下能看到更多发往他人的单播（若镜像/TAP），但仍可能看不到其他 VLAN 的流量。
