section-1-1-散户股票交易

NYSE 上市股票

散户 Jennifer 购买 200 股 AT&T：

  1. 经纪人查看 综合报价系统（最优买卖价 BBO）
  2. 可选 市价单 (Market order) 或 限价单 (Limit order)
  3. 订单经 SuperDot 路由至 NYSE 大厅 专家 (Specialist / 做市商)
  4. 在 电子限价指令簿 中等待撮合，或由专家自行促成
概念 HFT 关联
BBO / 限价簿 现代 LOB 的原型；HFT 竞争 queue position
Specialist 演化 today's designated market maker (DMM)
SuperDot 早期电子路由 → today's direct market access

Nasdaq 股票

Jennifer 购买微软 (Nasdaq)：

  1. 查看 Nasdaq Level II——多做市商 + ECN 分层报价
  2. 订单 路由 至特定做市商（可能含 订单流返点 payment for order flow）
  3. 做市商有义务 按报价接盘；成交经 SuperSOES 等 自动执行系统 完成 — 无需人工干预
概念 HFT 关联
Level II 深度 订单簿多档报价；HFT 读 full book
ECN 与交易所竞争的电子化 venue
订单流返点 零售流 vs 机构流；HFT 通常走 DMA 不经此路径
SuperSOES Nasdaq 早年 电子订单自动成交 系统 → 现代 自动撮合引擎 的前身

SuperSOES 是什么（→ 你写的 Match()）

SuperSOES（Small Order Execution System 等演进体系的一部分）= Nasdaq 早年让散户单 自动撞簿、自动成交 的系统，相当于今天加密所 「订单进来 → 撮合引擎自动配对」 的祖先：

散户限价/市价单
  → 路由（可能先到特定做市商 / 订单流路径）
  → SuperSOES：按规则自动找对手（做市商报价 或 簿上其他挂单）
  → 价格–时间优先成交，无需交易员人工点确认
SuperSOES（当年 Nasdaq） go-dex / 现代加密所
散户 限价 / 市价 进系统 OrderLimit / OrderMarket 进 Orderbook
自动找 对手盘（做市商或其他挂单） Match() 扫 Bids / Asks 或挂进簿
价格优先 → 时间优先 Limit.Orders 队列 + Timestamp
毫秒–秒级 微秒–纳秒级；还支持冰山、Post-Only 等（M5+）

一句话： 你写的 Go 撮合引擎 = SuperSOES 逻辑的 现代版：单进来 → Match() 自动配对 → 更新簿。差别主要是 速度几个数量级 和 订单类型更多；簿内公平规则（价格–时间）一脉相承。

Level 1：全市场 BBO 是怎么拼出来的

散户 App 里看到的 Level 1 最优买卖价 (BBO)，不是某一个做市商单独报的价 — 是交易所系统扫遍 所有做市商报价 + 公开订单簿挂单 后，拼出来的 全市场最优价：

来源 卖价举例
做市商 A 10001
做市商 B 10000.5
公开订单簿挂单 10000
→ 散户 Level 1 卖价 10000（全市场最低卖价）

买盘同理：最高买价 胜出。Nasdaq 给 Jennifer 推的就是这套 汇总 BBO — 和 SuperSOES / 路由用 同一套全市场视图 找对手。

go-dex 对应（Match 之后）：

Match() 更新 Orderbook（Bids / Asks 各档 Limit）
  → 提取 best bid = Bids[0]（最高价档）
  → 提取 best ask = Asks[0]（最低价档）
  → 推送 Level 1 行情（M4：GET /ticker 或 WebSocket）← 和 Nasdaq 给散户推价同一逻辑
真实 Nasdaq go-dex
扫所有 MM + 公开簿 → 合成 BBO Asks[0].Price / Bids[0].Price（簿非空时）
Level 1 给散户 M4 行情接口 只推最优一档
Level II 给专业户看 各家分别报多少 M4+ 可选推送多档深度

常见误解： Level 1 ≠ 「第一层做市商的报价」。Level 1 = 全市场最优；Level II 才让你看到 A 家、B 家、ECN 各自 报在什么价位 — 见下节「多级接力」。

Level II 与「订单簿的多级接力」

Nasdaq Level II 不只是「多看几档深度」— 背后是 多层流动性来源 的 接力路由：

  ┌─────────────────────────────────────────┐
  │  Level 1 · BBO（全 MM + 公开簿扫出来的最优价）│  ← 散户 App；非单一 MM 报价
  └──────────────────┬──────────────────────┘
                     │ 下面藏着
  ┌──────────────────▼──────────────────────┐
  │  第 1 层 · 特定做市商报价 / 内部化        │  ← 订单流返点常导向这里
  └──────────────────┬──────────────────────┘
                     │ 接不住 / 量不够
  ┌──────────────────▼──────────────────────┐
  │  第 2 层 · ECN（电子通信网络）更优报价     │  ← 自动继续找流动性
  └──────────────────┬──────────────────────┘
                     │ 仍不够
  ┌──────────────────▼──────────────────────┐
  │  第 N 层 · 其他 venue / 交易所 / 暗池…   │
  └─────────────────────────────────────────┘

接力逻辑： 散户单 先到第一层做市商；若做市商 接不住（量不够、价格偏离），系统 自动路由到下一层 ECN 找更优报价 — 不会卡死在单一流动性来源 上。Level 1 是上面 所有来源扫一遍 后的 汇总 BBO；Level II 是 各来源分别报多少 — 给专业用户看分层。

真实市场（Nasdaq 多层） go-dex（现在 M1–M2） 机构 / HFT（M5+）
多层 MM + ECN + 公开簿 → 合成 Level 1 单层簿 — Bids[0]/Asks[0] 即 BBO 多 venue 汇总 BBO + SOR
接不住 → 自动下一层 簿空就 无法成交 或部分成交 按 价格–深度–延迟 选下一跳
降低滑点、提高成交率 先练 单簿内 规则正确 HFT 降低滑点、提高 fill rate 的核心设计之一

go-dex 现在 = 单池子：所有 Order 进 同一个 Bids/Asks，没有「第一层 MM 接不住再扔 ECN」— 这是 刻意简化，先把 簿内 Match() 写对。M5+ 在 Match() 外面 加 多层路由层：维护多个 liquidity source（或模拟 ECN），child order 依次尝试，才是机构级 / HFT 路径。

与 go-dex：理解订单簿的最好切入点

散户故事 = 你撮合引擎里最小闭环 — Jennifer 的 200 股，换成 BTC/USDT，逻辑一样：

书上（散户） 你的代码（go-dex）
限价单 / 市价单 Order.OrderType（OrderLimit / OrderMarket）→ Match() 先分支，再价格–时间优先（orderbook.go）
SuperSOES 自动成交 Match() — 进单后 自动 找对手盘，无需人工
电子限价指令簿 Orderbook · Bids / Asks · 每档 Limit.Orders 队列
Level 1 BBO（全市场最优） Match() 后取 Bids[0] / Asks[0] → M4 推给前端
Level II 多层 MM + ECN 现在： 单层簿；M5+： 多层路由 / SOR（见下）
订单 挂进簿里等 / 立刻吃对手盘 限价 → 进簿；市价 → Match() walk-the-book（M2 待写）
专家 / 做市商 接单、报价、消化散户流 marketmaker.go 定时挂买卖单 → 散户 OrderMarket 的 对手盘

Jennifer 的单在市场里怎么流转（对应你写的引擎）：

散户下单（限价/市价）
    → 路由进交易所（你：API 进 Orderbook）
    → 限价：挂到 Bids/Asks 某档，按 Timestamp 排队
    → 市价：从最优对手档开始扫（价格优先 → 时间优先）
    → 成交 → 更新 TotalVolume / 删空档
    → 提取 Bids[0]、Asks[0] → Level 1 行情推送（M4）

和 Ch 1 §4.2「限价单被吃」怎么接上：

  • 散户（或你）在 10500 挂限价卖，以为「涨到了再卖」
  • 做市商 / 大资金 的角色，就是书上 专家、Nasdaq 做市商 — 他们 盯着簿上的挂单，用 市价扫单、推价 等方式 消化 或 触发 这些单
  • 你在 §4.2 慢动作里写的「先托价 → 市价买扫你 → 再砸盘」，就是 「你的限价单最后怎么被别人接走」 的微观版；Jennifer 的故事告诉你 这类单在真实市场里本来就会流向做市商
读完本节应懂 对照代码
限价单 = 挂在簿上提供 免费期权 Limit + Order 进 Bids/Asks
市价单 = 立刻 找对手成交 Match() 扫对手盘
做市商 = 吃/挂散户流，不是魔法 对手方也是 簿上的 Order，或 incoming 主动单
Level 1 = 全来源最优价，非单一 MM BestBid() / BestAsk() → 行情 API（M4）

SuperDOT / SuperSOES → 路由 + 自动撮合

书上 Jennifer 的两条路径，对应现代引擎 两层：

时代 机制 在问什么问题 go-dex
SuperDot（NYSE） 电子 路由 进大厅 / 专家 订单 从哪条通道进、先处理谁 M4+ 多 ingress
SuperSOES（Nasdaq） 自动执行 — 找对手、按规则成交 能否 无人值守 完成撮合 Match()（M2）
现在 · 加密所 REST/WS + 做市商低延迟通道 + 内部队列 同一毫秒谁 先进 Match() M4+ 通道优先级

Nasdaq 完整链路（书上）： 路由到做市商（义务接盘）→ SuperSOES 自动成交。
go-dex 简化版： 路由层暂省略 → 单直接进 Orderbook → Match() = SuperSOES 的现代内核。

和 Match() 的关系：

API 收到订单
  → （可选）多层路由：MM → ECN → 下一 venue  ← Level II 接力（M5+ SOR）
  → （可选）单通道 ingress 优先级            ← SuperDot / 订单流返点（M4+）
  → Match()：自动找对手盘、按规则成交      ← SuperSOES 的现代版（M2）
       · OrderType 分支（限价进簿 / 市价扫簿）
       · 簿内：价格优先 → 同价 Timestamp 时间优先
  → 更新 TotalVolume / 推送行情
  → BestBid / BestAsk → Level 1 接口（M4）   ← 全簿最优价，等同 Nasdaq 散户 ticker
  • 散户能用到的 就是 市价 + 限价 — 也是你引擎 **M1–M2 的核心对象。
  • OrderType 是 簿内规则 的第一道分支；路由 分两层 — ingress 谁先（SuperDOT）与 多层流动性接力（Level II → ECN，M5+ SOR）— HFT 争的往往是 全套。

go-dex 现在：单层 Orderbook + 单通道 + OrderType + 价格–时间优先 — 先把 簿内逻辑 写对；M4+ 多 ingress；M5+ 多层 venue 路由（仍须公平、可审计 — §3 信息同步）。

和机构交易的边界： 散户故事覆盖 go-dex M1–M2；机构才有的暗池、冰山、FIX、算法拆单 → §2 · 机构 vs 散户 · M5 机构级扩展。

section-2-2-机构股票交易

流动性好的大盘股

机构交易员 Bob 为养老基金买入 40 万股 ExxonMobil（约 $1600 万）：

  1. 先用 POSIT（机构暗池）以 价差中间价 保密撮合部分数量——降低 市场冲击 (market impact)
  2. 剩余通过 大宗经纪 / 场内经纪 分批完成，不暴露全部意图

→ HFT：与 institution 相反——HFT 拆单极小、速度极快；institution 怕 impact，HFT 有时 制造 impact 或 捕捉 impact 后的 revert

流动性差的 Nasdaq 股票

Bob 卖出 10,000 股 价差极大、流动性极差 的股票：

  • 直接电话联络该券 大型做市商
  • 同时询问买价和卖价（双向报价）——防止做市商猜出卖意而 恶意压价

→ HFT：信息不对称博弈；never reveal direction when negotiating size

散户 vs 机构：核心差异不在订单类型

机构底层也能下市价单、限价单 — 和 Jennifer 一样。差别不在「能不能用这两种单」，而在 隐藏权限、路由优先级、配套工具：

维度 散户（Jennifer） 机构（Bob）
可见订单类型 公开 市价 / 限价 同样可用市价/限价，但还有 冰山单、隐藏量、暗池单 等
订单去向 进 公开 LOB 排队，人人可见 可进 暗池（POSIT 等） — 不挂公开簿；或冰山单 只露一部分量
进所通道 经纪人 → SuperDot / 零售 API DMA 直连、FIX 协议、共置 / 专线 — 争 进 Match() 的先后
大单怎么成交 200 股，一把下完 算法拆单（TWAP/VWAP 等）：拆成许多小单 慢慢吃流动性，降低 市场冲击，避免意图暴露被 front-run
谈判 无 流动性差时 电话做市商双向询价，不暴露卖意 
                    散户                          机构
                      │                            │
         市价/限价 ───┴─── 公开 Orderbook ─────────┼─── 同样市价/限价
                      │                            │
                      │                    暗池（不进公开簿）
                      │                    冰山单（簿上只露 tip）
                      │                    算法母单 → 拆成 child orders
                      │                    FIX / 低延迟 ingress
                      ▼                            ▼
              go-dex M1–M2 覆盖              M5+ 机构级扩展

机构多出来的几类能力（书上 + 行业）

能力 干什么 Harris / 行业
暗池 (Dark pool) 大单 保密撮合，不进公开 Level II — 防抢跑、抹平信息差 本节 Bob → POSIT；§3 抢跑 vs 藏单 · Ch 25
OTC / Upstairs 场外 找对手；卖 折扣 / 买 溢价 §3 — 流动性补偿双向
冰山单 (Iceberg) 簿上只显示 tip size，其余 隐藏 Ch 4 隐藏/披露规则
低延迟网关 不走零售 REST，走 FIX / 专线 / 共置 Ch 27 电子化交易
算法拆单 母单 (parent) → 引擎多次收到 子单 (child) 降低 impact；与 HFT 拆单极小、极快 形成对比（见上）
实时风控 下单前校验 持仓、限额、敞口（机构合规） 叠在撮合 外层，不替代 Match()

机构不是「多了魔法订单类型」 — 很多仍是限价/市价，只是 路由到哪本簿、露多少量、谁先进队列、大单怎么切 不同。

与 go-dex：你现在写的是「散户级现货交易所」

结论： 当前 go-dex = 公开订单簿 + 市价/限价 + 价格–时间优先 的 散户级现货原型 — 没有暗池、没有冰山、没有机构 FIX 通道、没有算法拆单引擎。机构来用 不够，要 叠模块，不是改一行 Match() 就完事。

层级 散户级（现在 M1–M4） 机构级（M5+ / 生产 HFT 路径）
撮合核心 单一 公开 Orderbook · OrderLimit / OrderMarket 公开簿 + 暗池簿（或 internal cross）；Iceberg 字段（显示量 vs 隐藏量）
ingress 单通道 API 散户 REST vs 机构 FIX / 低延迟队列（路由优先级）
外层 （可选）简单费率 风控：持仓、保证金、限额；算法路由：母单拆 child 再喂给 Match()
语言 Go 原型 热路径 Rust/C++ 网关 + Go 外围（见 Ch 1 §4.4）

推荐路径： 先把 散户级公开簿 跑通（M2 Match() → M3 流动性 → M4 多 symbol / WS）→ 再加 暗池 / 冰山 / 多 ingress / 风控 / 拆单 — 这是从 教学原型 → 专业机构级平台 的完整阶梯。

→ 散户入口对照：§1 · 与 go-dex · 大卖场分层：Ch 1 §3 · 里程碑 M5 机构级

section-3-3-超大宗股票抛售

Edna 须抛售 90 万股 家族企业股票（数千万美元）缴遗产税：

  1. 高盛 大宗经纪 (block broker) 接手
  2. 不能 直接在公开市场抛售（会 价格暴跌）
  3. 查 13F 公开持仓，定位对该股有兴趣的大型基金
  4. 场外 Upstairs market 成交：提供 价格折扣 (discount) + 说明抛售原因是 纳税而非基本面恶化
概念 HFT 关联
Block / upstairs 与 HFT 热路径分离的大宗协商市场
Information leakage 大单意图暴露 = 最大敌人
13F 公开信息用于找 counterparty——HFT 不碰此类但需知 institution 行为

OTC 流动性补偿：卖单 折扣 vs 买单 溢价

Edna 若把 100 万股 直接在 公开 LOB 砸出去：

  • 每吃一档深度，价格就被 往下打一档（walk-the-book + 市场冲击）
  • 最终 成交均价 远低于开始看到的 Level 1 卖价 — 自己砸崩自己

买单是镜像 — 冲击方向反过来：

  • 公开挂 巨量买单 / 市价扫货 → 从 卖一往上吃 Asks，买一到买五全扫光
  • 股价被 一路拉高 → 平均建仓成本 远高于挂单时的 Level 1 — 「买贵了」
  • 和卖单一样会 信息泄露：市场看见你要扫货 → 投机盘 提前抢低价筹码 → 高价卖给你 — 抬轿套利
方向 公开大单后果 OTC / 暗池里「流动性补偿」长什么样
卖（Edna） 砸盘、均价偏低 卖方给 折扣（如比市价低 2%）换快速出清、不暴露
买（镜像） 拉盘、均价偏高、被抬轿 买方愿意给 溢价（如比市价高 2%）换 快速拿够筹码、不暴露扫货意图

所以走 OTC / Upstairs 或 暗池：大宗经纪 / 池子 直接找对手 — 卖找接盘方，买找有 出货需求 的对手 — 一次性谈成：

谁 卖单场景（Edna） 买单场景（镜像）
主动方（机构） 比公开砸盘 更高均价；快速出清；不暴露 比公开扫货 更低均价；快速建仓；不被抬轿
对手盘 折扣接货 — 补偿锁仓、波动风险 溢价出货 — 补偿 立刻让出筹码、错过继续涨 的机会
公开市场 避免瀑布式砸盘 避免被大单 一路拉抬

补偿不是白送 — 都是 流动性 premium 的两侧：

卖：公开损失 ≈ 冲击成本 + 抢跑砸盘     →  OTC 折扣换不暴露
买：公开损失 ≈ 冲击成本 + 抢跑抬轿     →  OTC/暗池 溢价换不暴露、快速成交
机构算账  →  若 溢价/折扣 < 公开冲击+被 front-run 的额外成本，就走场外

例子（数字直觉 · 卖）：

  • Level 1 价 100；公开卖 100 万股可能 均价跌到 96
  • OTC 谈成 98 — 卖方比 96 好，买方便宜 2% 换 立刻全接

例子（镜像 · 买）：

  • Level 1 价 100；公开买 100 万股可能 均价拉到 104
  • 暗池 / OTC 谈成 102 — 买方比 104 省，卖方多得 2% 换 立刻让出筹码、不跟散户抢公开深度

公开挂单的信息泄露：抢跑（卖：砸盘再接 / 买：抬轿再卖）

大资金 怕在公开簿挂超大限价单，不只因为 walk-the-book 的 冲击成本 — 还因为 意图一露，投机盘会抢跑。

卖单（Edna · 出货）：

市场看到你挂「超大量限价卖」
  → 投机资金快速做空 / 先砸盘，把价格打下去
  → 你在更低价位被迫成交（或被定点市价买扫走后价格已转弱）
  → 他们反手在低价接货，等价格回升赚差价

买单（镜像 · 扫货 / 建仓）：

市场看到你挂「超大量限价买」/ 即将扫货
  → 投机资金提前在低价档 **抢筹码**
  → 你再往上吃 Asks 时，卖一卖二已被抬价 — **买得更贵**
  → 他们 **高价卖给你** — 「抬轿」套利
尺度 书上哪里讲过 卖 买（镜像）
散户 / 中等挂单 Ch 1 §4.2 市价买扫 Ask → 市价卖砸 Bid → 低价接回 市价卖扫 Bid 触发你的买单 → 再拉涨；利空买 被吃后继续跌
机构超大块 本节 公开 Level II 泄露 → 砸盘再接 公开泄露 → 抢筹抬轿

这就是典型的 pick-off 套利 — 限价单给的 免费期权（§4.2），在大单场景下变成 系统性信息泄露；买卖方向只是冲击和抢跑的手法镜像。

Trading and Exchanges · Larry Harris · 精读

4. 期货市场：套期保值 (A Futures Market Trade)

Harris 用 大豆加工商 在 CBOT 的故事，说明 效用型交易 (utilitarian trading)：不是为了赌方向，而是为了 把商业风险转出去。

故事在讲什么

加工商 未来要在现货市场买进大豆（或已持有待加工的库存）→ 怕 大豆涨价 侵蚀利润。

腿 市场 典型动作 价格涨时
现货敞口 物理/现货 将来 买入 大豆 采购成本 ↑（亏）
期货对冲 CBOT 大豆期货 卖出 期货 空头 浮亏

两笔交易 不在同一个 pit、同一个订单簿，但 经济效果 是：涨跌大致 相互抵消 → 套期保值 (Hedging)。

场内细节（历史）：

  • Pit：喊价 (Shouting) + 手势（手心向外 = 卖，向内 = 买）
  • 清算：BOTCC 作 中央对手方 (CCP)，担保履约 + 管理 保证金 (margin)

→ 今天 Pit 已被 CME Globex 等电子系统取代；中央清算 + 保证金 仍是期货核心。

套期保值的逻辑（三要素匹配）

套保的 数学意图 很清晰：

一个市场的盈利覆盖另一个市场的亏损 —— 只要 头寸数量、方向、期限（合约/交割月） 完全匹配，无论标的 涨价还是跌价，组合 净值 都锁在 目标区间 附近。

要素 示例（加工商）
头寸 现货要买 1000 吨 ≈ 期货卖 N 手（按合约乘数换算）
方向 现货 多头敞口 ↔ 期货 空头
期限 期货合约 交割月 贴近 实际采购/加工 时间

不匹配时，剩下来的是 基差风险 (basis risk) 或 比例错配 —— 仍是 hedge，只是 锁得不干净。

基差 (Basis) = 现货价 − 期货价。对冲 近似 锁价，不是两价永远相等。

核心问题：同步性 (Synchrony)

理论成立 不等于 执行瞬间已 hedge。

Harris 故事里，加工商可以 计划好 先卖期货、三个月后再买现货 —— 这是 商业节奏上的分时对冲，中间窗口 公司 knowingly 承担。

但 电子平台上一键套保 的场景不同：用户点击「对冲」的 那一刻，若只有一腿成交：

t₀  现货买入 ✅（大豆多头已上身）
t₁  还没来得及在期货做空…
    价格暴跌 → 现货腿裸亏 —— 这就是「敞口窗口风险」
原因 说明
两本独立订单簿 现货、期货 各自撮合
流动性不对称 一腿深、一腿薄 → 先成快腿、慢腿挂单
撮合速度差 一所在 colo、一所在公网 —— 毫秒级就是风险

所以：对冲的「稳态逻辑」（matched legs → 涨跌相抵）与 「建仓瞬间是否已对冲」 是两层问题。后者 才是撮合引擎要解决的 同步性。

层次 是否要求同步
经济学稳态 两腿最终都到位即可；允许 计划内 分时（加工商）
平台即时套保 必须 消灭或极缩短 单腿窗口 —— 否则用户 名义上在套保、实际上在裸奔

两个市场：为什么「知道要对冲」还不够？

现货市场与衍生品市场是 独立 venue：

现货 / 物理 期货
订单簿 各自撮合 各自撮合
参与者 贸易商、加工商… 投机者、套保者、HFT…
清算 交货、信用条款 CCP + 逐日盯市保证金

系统不会自动 帮你在卖完期货后「补上」现货买入。只成交一边时，你得到的不是 hedge，而是 单边赌注：

只成交了… 实际头寸 风险
现货买入 ✅，期货卖出 ❌ 纯做多 现货 仍在赌涨价 — 没对冲
现货买入 ❌，期货卖出 ✅ 纯做空 期货 赌跌 + 保证金/追保 — 往往更急

所以：对冲是经济目标；「建仓瞬间是否已配对」是同步性问题。

引擎设计：一键双挂 · 原子组合单

要对 即时套保 真正负责，不能把两腿当成用户 两次独立点击 就完事 —— 必须 绑定成一个原子操作：

用户发起：一键双挂（现货买 + 期货卖，数量/期限已配好）
           │
           ▼
    ┌──────────────────┐
    │  Spread / Combo  │  要么两腿都成交
    │  Matcher         │  要么都不成交（全滚回）
    └──────────────────┘
           │
     ┌─────┴─────┐
  现货簿       期货簿
能力 作用
一键双挂 UI/API 一次提交 已配好比例 的两腿
原子性 (atomic) all-or-nothing — 杜绝「一腿 orphan」
预检 下单前同时验：现货资金/库存 + 期货保证金
组合风控 按 净 delta 算风险，而非单腿裸 futures

这才符合用户心里「我已经套保了」的语义 —— 不是 理论上说「迟早会对冲」，而是 成交回报里就没有单腿窗口。

Harris 加工商那种 分月、分步 套保，可以走 普通单 + 人工/算法排程；平台型一键 hedge 必须走 组合单。

与 go-dex 撮合引擎的对照

当前 go-dex 是 单交易对、单簿 的 LOB — 对应 Harris 故事里 「一个 pit / 一个合约」 的一次撮合。

Harris / 真实世界 go-dex 现状 若做「现货 + 永续」套保
现货簿 + 期货簿 两个 engine 一个 OrderBook 两个 OrderBook（两 symbol）
加工商 计划内分时 对冲 两次独立 AddOrder 适合 老练机构；窗口风险 自担
一键双挂 / 组合单 未实现 SpreadMatcher：原子两腿 or 全不成交
保证金 只盯期货 未实现 RiskEngine：组合预占 + 净 delta

读法：

  1. Ch 2 §4 — 三要素匹配 + 同步性 才是引擎题眼
  2. Ch 2 §1 + go-dex Match() — 单簿原子撮合是 组合单的原子单元
  3. M4+ 扩展 — 在 两簿之上 加 SpreadMatcher，不是简单再写一个 OrderBook

→ leg risk / 部分成交：Ch 17 §3.3

敞口时间线：分时 vs 原子

计划内分时（Harris 加工商） — 窗口 已知、可管理：

时间 ──────────────────────────────────────────────→
     │ 卖期货 ( hedge )          │  后日现货采购
     ▼                           ▼
     ┌──┐                        ┌──┐
     │  │ 公司接受这段 basis 风险  │  │ 最终净敞口 ≈ 0
     └──┘                        └──┘

即时套保（平台一键双挂） — 窗口 必须 ≈ 0：

错误：  现货买 ✅ ──[价格可动]──> 期货卖 …
正确：  [现货买 + 期货卖] 原子成交 ──> 回报时已 matched

Takeaway：

场景 同步性要求
商业 排程型 套保 低 — 最终三要素匹配即可
