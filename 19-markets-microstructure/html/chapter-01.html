section-1-1-探讨范围

一、学科定位

本书归属于金融经济学分支中的 市场微观结构（Market Microstructure）。该领域研究证券交易全链路的底层运行逻辑：交易行为、交易者主体、交易场所（市场载体）、约束交易的制度规则——聚焦「订单如何成交、价格如何形成、流动性如何流转」。它区别于传统金融学中侧重宏观估值与公司融资的研究范畴。

二、本书核心覆盖内容

本书关注 交易经济学（trading economics） 的实务原理，主要包括：

  1. 订单—撮合—成交 全流程微观机制：限价单/市价单/冰山单、价格—时间优先撮合引擎、盘口订单簿
  2. 市场组织模式：指令驱动、报价驱动、混合市场、暗池、多场所碎片化生态
  3. 交易规则设计：交易所撮合制度、Maker–Taker 手续费、订单路由、监管约束、涨跌停、跨市场最优执行
  4. 参与主体行为：做市商、机构大单、散户、高频（HFT）、知情/不知情交易者之间的博弈
  5. 流动性、买卖价差、滑点、市场冲击、交易成本 的构成与测算
  6. 价格发现、信息不对称、库存风险、逆向选择 四大核心理论模型
  7. 算法交易、高频交易与市场机制 的相互作用，以及闪崩等微观市场风险事件

三、本书不涉及内容

边界 说明
证券估值（投资学） 不讲解 DCF、PE/PB、红利贴现、CAPM、因子选股或长期基本面价值判断
证券发行（公司金融） 不覆盖 IPO、再融资、资本结构、并购、公司治理、分红回购等企业融资决策

Harris 在全书开篇即明确：只讲交易机制，剥离资产估值与公司融资——这是微观结构学科与相邻分支的标准分界。

四、与 HFT 的底层关联

市场微观结构是 HFT 策略的 业务层操作系统：低延迟引擎与网络优化只解决「执行有多快」，却无法回答流动性从何而来、成本如何构成、盘口博弈遵循何种规则。做市赚价差、跨市场套利、订单流预测、大单拆分等盈利逻辑，全部建立在微观结构规则之上。若不懂撮合优先级、暗池隐藏订单、手续费返还与市场冲击衰减，再快的引擎也会持续承受逆向选择与亏损，策略难以长期存活。

五、延伸阅读

著作 与本书框架的对应
Harris, Trading and Exchanges: Market Microstructure for Practitioners 实务派入门；开篇界定边界：只讲交易机制，剥离估值与融资
O'Hara, Market Microstructure Theory 理论经典；系统论证交易者—市场—规则的均衡模型
Gomber et al., Market Microstructure in Practice 实战向；强调 HFT 与微观结构的依存及流动性/成本对策略生存的根基作用

section-2-2-核心目标-五个市场质量特征

一、章节定位

本书核心目标：为交易员、机构经纪、交易所与监管机构建立统一分析框架，系统拆解 市场质量（Market Quality）五大核心评判维度。

次要目标：论证 市场结构——交易规则、撮合系统、信息披露机制的组合——如何直接作用于五大特征、决定市场整体运行效率。

框架源自 Larry Harris《Trading and Exchanges》原著导论；全书各章均围绕「如何提升五大市场质量」展开，分别从交易者、交易所、监管三个主体视角论述。

二、五大市场质量特征对照表

市场质量特征 标准定义与衡量指标 与 HFT 的核心关联 经典理论/实证支撑
流动性（Liquidity） 市场能否快速、大额、小幅冲击完成交易。四大量化维度：① 紧度（买卖价差）② 即时性（成交延迟）③ 深度（盘口挂单量）④ 弹性（冲击后价格修复速度）。本质：流动性是「即时交易服务」 HFT 做市商是现代市场主要流动性供给方；持续双边挂单压缩价差、增厚深度；极端行情下批量撤单可造成 虚假流动性、流动性黑洞（如 2010 闪崩） Demsetz (1968) 即时性理论；Kyle 流动性模型；Harris《Trading and Exchanges》
交易成本（Transaction Costs） 全口径交易摩擦，分两类：显性（佣金、交易所费、印花税）与 隐性（价差、滑点、冲击成本、延迟损耗）。研究目标：识别、量化、算法优化 HFT 靠极低延迟、小额拆分、Maker 返佣压低全市场平均成本；机构算法交易的核心目标之一是对冲 HFT 带来的短期冲击成本 Roll 价差分解；有效价差、实现冲击成本测算框架
信息效率（Informative Prices） 价格吸收私有/公开信息的速度与准确度。优质市场：新信息快速反映、短期噪声快速消退，长期价格贴合基本面 HFT 跨市场套利、毫秒级订单流解读加速价格收敛；但噪声单、订单流操纵可制造短期失真、加速 Alpha 衰减，压缩知情交易者收益窗口 O'Hara 信息不对称模型；Hasbrouck 价格发现方差分解
波动性（Volatility） 价格短期波动幅度与持续性。区分：① 基本面波动（合理信息驱动）② 交易摩擦波动（订单冲击、算法反馈环路）。监管目标：抑制异常暴涨暴跌，保留合理波动 HFT 双向报价平抑常态日内波动；极端行情下算法负反馈、止损踩踏可放大波动；熔断、持仓上限、Speed Bump 等用于约束高频诱发的极端波动 日内波动分解；跳跃波动；波动率反馈循环
交易利润（Trading Profits） 证券交易为 零和博弈：全体交易者盈亏总和为 0，一方超额收益对应另一方亏损。分配由信息优势、速度优势、成本承受能力决定 HFT 利润来源：速度优势收割不知情散户/慢速机构、流动性补偿、跨市场微小价差套利；长期看行业整体收益随竞争收敛、利润变薄 逆向选择利润分割模型；订单流收益分配实证

三、次要目标：市场结构 → 五大质量

市场结构 = 交易规则（撮合优先级、订单类型、涨跌停、暗池准入）+ 信息系统（行情延迟、披露透明度、订单路由）

传导路径：

  1. 市场结构直接约束 HFT、做市商、机构、散户的订单行为
  2. 各类交易者行为共同改变流动性、交易成本、价格发现、波动、利润分配
  3. 监管、交易所、机构可通过调整市场结构定向优化某一项或多项质量——同时存在 维度间权衡（例如提高透明度改善定价效率，但可能降低做市意愿、削弱流动性）

四、原著溯源要点（Harris）

  1. 全书导论将市场质量拆解为上述五项，区别于传统资产定价与公司金融
  2. 独立章节讨论自动化交易、高频交易对五大维度的 双向影响（收益与风险并存）
  3. 海外监管机构（SEC、ESMA、FCA）评估市场改革时，常采用该五维框架作为量化标准

五、行业实证共识（量化/HFT 领域）

市场状态 共识
常态平稳市场 HFT 普遍改善流动性、降低交易成本、提升信息效率、平滑日内波动
极端冲击市场（大跌、突发新闻） 高频算法行为可反向恶化质量：流动性枯竭、波动率飙升
利润分配长期趋势 速度与技术竞争加剧，HFT 超额收益持续下行，利润逐步向长期基本面交易者转移

六、与 go-dex 撮合引擎对照

Ch 1 的五维不是抽象指标——就是高频交易系统要逐层实现的核心问题。对照本仓库 00-practice-go-dex/code/orderbook.go：

市场质量 在撮合引擎里是什么 go-dex 现状 / 待做
流动性 Orderbook.Bids / Asks 各档 深度（TotalVolume）：每个价位挂单够不够厚，大单打进去滑点多大 已有：Limit.TotalVolume + 价位队列；待做：深度查询、大单 walk-the-book 冲击测算
交易成本 Maker–Taker 费率：挂单（Maker）返佣、吃单（Taker）扣费——费率设计决定有没有人愿意挂单、交易所会不会亏手续费 待做（M3+）：成交时按 Maker/Taker 记账；与 Ch 14 价差、Ch 21 成本衡量联动
信息效率 撮合公平性：价格优先、同价 时间优先（Order.Timestamp），后到的大单不能插队抢成交 结构已备：Limit.Orders 先来在前 + 注释写明 Ch 4–6 规则；待做：Match() 严格按序撮合
波动性 风控层：熔断、涨跌停——极端行情不让订单簿被击穿、连环止损 待做（Ch 28）：价格带检查、暂停撮合、Speed Bump 等
交易利润 策略层（引擎之上）：在前四点约束下找套利空间——价差、跨档、返佣结构、延迟优势 引擎提供 公平 LOB + 成本透明；策略另建，零和博弈在参与者之间分配

一层理解：

市场结构（规则）  →  撮合引擎（Bids/Asks/优先级/费率/熔断）  →  市场质量五维  →  策略利润
                         ↑ go-dex 正在写的这一层

摸得着的例子：流动性 = Bids/Asks 够不够厚

Orderbook 里 Bids = 买盘，Asks = 卖盘。假设：

档位 挂单量
买一（Bids 最高档） 10 BTC
卖一（Asks 最低档） 5 BTC

这时盘口 有流动性——对手盘有人接单，不会「想成交却无人接」。

市价买 6 BTC（吃 Asks）：

  1. 先吃 卖一 5 BTC → 按卖一价成交
  2. 还剩 1 BTC 没买到 → 吃卖二（walk the book，价格滑到下一档）

这就是 深度不够时的滑点：不是没人卖，而是卖一量不够，多出来的部分要更贵的价格才能成交。

市价卖 6 BTC（吃 Bids）则相反：买一有 10 BTC，6 个 全在买一成交，不用滑到买二。

对应代码：市价单从前到后扫 Limit.Orders，吃完一档的 TotalVolume 再换下一档——见 orderbook.go 底部注释。

「经典理论/实证支撑」现在要不要啃？

表格里 Demsetz、Kyle 那些，本质是前人总结的 「怎么让订单簿一直有足够挂单」 的规律。一个你后面一定会碰到的例子：

为什么交易所给挂单的人返手续费（Maker 返佣）？
因为实证表明：有人愿意 持续挂限价单，卖一/买一才厚，walk-the-book 才少。返佣就是 维持流动性的激励机制。

现在写 LOB 结构阶段 看不懂可以先折页；等 go-dex 写到 Maker–Taker 手续费模块（M3+，Ch 14/21）再回来看本节对照表里的「交易成本」行和上面这条返佣逻辑。

section-3-3-交易工具与市场

一、大白话定义

概念 是什么 对你现在写代码意味着什么
交易工具（Instrument） 撮合引擎能处理的 订单标的：股票、债券、加密货币、期货、外汇…… 每种工具有自己的 合约规格（最小变动价位、数量精度、是否现货/杠杆）→ 对应一套 撮合与风控规则
市场（Market） 引擎跑起来之后，参与者 + 规则 + 信息同步 共同形成的 交易场所 见下方「市场三要素 → 代码映射」 
交易工具（标的）  →  规则配置（tick size、费率、涨跌停…）  →  市场（运行中的订单簿 + 成交流 + 行情推送）

市场不只是买卖双方

一个完整的市场还要有两块你写代码一定会碰到的：

要素 是什么 go-dex 里对应什么
参与者 买方、卖方及其挂单 Orderbook.Bids / Asks，每个 Limit 里排队的 Order
规则 怎么成交、怎么维护订单簿 价格优先、时间优先 的撮合逻辑；挂单/撤单/成交后更新 TotalVolume、删空档位等 簿维护 → Match() 及配套方法（待写）
信息同步 成交后 立刻 把行情推给所有参与者；不能让人 先看到成交、后看到行情 待做（M4）：WebSocket / 推送模块——成交事件、LOB 快照、最新价 广播

一句话映射：

Orderbook 结构体     =  市场的数字化载体
Bids / Asks          =  买卖双方的挂单
撮合函数 Match()     =  交易规则（价格优先 + 时间优先）
行情推送（待加）     =  信息同步机制

信息同步对应 §2 里的 信息效率：规则保证撮合公平；推送保证 所有人同一时刻看到同一套市场状态——否则再公平的引擎也会被「先知情」毁掉。

二、原著要点（Harris）

工具 (Instruments)

涵盖股票、债券、期权、期货、外汇、掉期等。

  • 可替代/同质化（Fungible） 的工具市场运作最好——每一单位与所有其他单位在经济上无法区分，买卖双方更容易匹配。
  • HFT 主战场：高度同质化的 股票、期货、FX 等连续竞价市场。

市场 (Markets)

交易者聚集的场所：

  • 物理大厅（如 NYSE 传统 floor）
  • 电子互联系统（如 Nasdaq、银行间 FX）

现代 HFT 几乎 entirely 在 电子市场；共置（colocation）、订单簿速度竞争是微观结构 + 技术的交汇点。

三、主流交易所 = 金融产品大卖场

可以把 Nasdaq、NYSE、币安 这类主流交易所理解成 「金融产品大卖场」：

                    ┌─────────────────────────────────────┐
                    │  各产品区：规则 · 参与者门槛 · 风控      │
    ┌───────────────┼───────────────┬─────────────────────┤
    │  股票区        │  期权/期货区   │  加密货币区           │
    │  散户 · 机构   │  保证金 · 行权 │  现货 · 合约 · 做市通道 │
    └───────────────┴───────────────┴─────────────────────┘
                    │  底层：统一订单簿撮合引擎（LOB + Match）  │
                    └─────────────────────────────────────┘
卖场 上面分什么区 各区差异在哪
Nasdaq / NYSE 散户股票、机构 大宗、期权 最小变动价位、T+1、涨跌停、期权行权与组合策略
币安等加密所 现货（散户买币）、合约（杠杆）、做市商 专用通道 精度、Maker/Taker 费率、保证金率、强平/爆仓规则

共性： 不管卖什么「货」，收银逻辑 往往仍是 指令驱动 LOB — 限价进簿排队、市价扫对手盘、价格优先 → 时间优先。

go-dex 在这个比喻里是什么？

→ 大卖场的「基础收银台」 — 先搞定 最通用的现货撮合：Order → Limit → Match()，限价/市价、Bids/Asks walk-the-book。

阶段 卖场比喻 代码
现在 M1–M2 只开 现货区 一个柜台 单一 Orderbook（如 BTC/USDT）
以后 M4+ 多柜台并行 map[Symbol]*Orderbook
更后（衍生品区） 期权/期货专属功能 保证金、行权、爆仓/强平 — 包在同一套 LOB 外面，不混进 Match() 核心

衍生品区的规则 叠在 现货撮合之上：引擎先正确成交，外层再算保证金够不够、要不要强平 — 先收银台，再分区风控。

四、与 go-dex 撮合引擎：先单工具、后扩展

现在只做一件事：单一交易工具 + 单一市场（现货区一个柜台）。

阶段 范围 目标
当前（M1–M2） 一个工具，例如 BTC/USDT 现货 一个 Orderbook：限价/市价、价格–时间优先、Bids/Asks 撮合 跑通
以后（M4+） 多工具、多市场 每个工具一套配置（精度、费率、是否允许做空）；引擎层 复用同一套 LOB 逻辑，外层加 Symbol → Orderbook 路由

为什么先单工具？

  • 「工具」差异（股票 100 股一手 vs .crypto 0.001 BTC）最后都落在 规则参数 上，撮合核心（Order → Limit → walk-the-book）是一样的。
  • 先把 一个市场 的挂单、成交、深度查清楚，再谈「适配第二个交易对」——否则多 Symbol 只会把还没验过的 bug 放大。

代码上的直觉：

现在：  一个 Orderbook  ≈  一个市场（BTC/USDT）
以后：  map[Symbol]*Orderbook  ≈  交易所里多个市场并行

→ 结构体见 orderbook.go · 五维质量对照见 §2 · go-dex

五、同一套订单簿，两种完全不同的系统

本质都是 LOB 撮合，但 go-dex（交易所引擎） 和 HFT 交易系统 的目标与细节要求差很多：

你现在写的：交易所撮合引擎 HFT 系统
角色 市场基础设施 — 把市场跑稳、跑公平 基础设施上的抢跑者 — 在稳定运行的市场上赚差价
核心目标 稳定、公平地处理全量订单 极短时间内 从订单簿微小变化里 抢最优价位
订单范围 所有用户的限价单、市价单；挂单、撤单 高并发 都要正确 不需要 处理全市场每一笔单；只关心 对自己有利的成交窗口
工程重心 规则正确（价格–时间优先）、簿维护、一致性、可扩展 延迟、网络、共置；订单簿 深度/变化 的毫秒级计算
前提关系 先把路修好 以前者稳定运行为前提 — 引擎崩了或规则不公，HFT 也无从谈起

订单簿是交易所的「统一挂单池」

不管 A 股（上交所）、期交所（郑商所） 还是 加密交易所，都由交易所 维护一份统一的订单簿——所有参与者只能把单挂在这上面，按同一套规则成交。

你的 go-dex 项目，本质就是 自己模拟一个小型交易所的订单簿：Orderbook + 撮合逻辑 = 让订单在你写的规则里成交。

HFT 的「抢跑」不是插队

HFT 不会 破坏价格–时间优先去「插队」。它靠的是 技术优势：

  1. 比别人更早看到 订单簿的变化（行情 feed 快几毫秒）
  2. 比别人更早把单挂到 最优价位（网络 + 计算 + 共置）

例子（上交所 LOB）： 订单簿上 刚出现一笔 1000 手的买盘（或预示大买即将进场）。HFT 系统比普通用户 早几毫秒 捕捉到这个信号，立刻在 卖一价 挂卖单；等大买盘来吃卖盘时，HFT 的单先被成交，赚 买卖价差。郑商所、上交所的 HFT，本质都是：低延迟网络 + 高速计算，在订单簿 每次更新 时抢在其他交易者前面 占好最优位置——不是改规则，是 比人快。

这也对应 §2 信息效率：引擎必须保证 推送公平（不能有人更早看到成交）；HFT 则是在 合法、同规则 的前提下比谁更快。

上下游：造池子 vs 在池子里捕鱼

  go-dex（你现在）          HFT（以后可选）
  ───────────────          ───────────────
  造一个能挂单、成交的「池子」   在池子里靠速度 + 规则找盈利
  维护 Orderbook            读 Orderbook 变化、下单
  基础设施                  捕鱼工具

两者 都基于订单簿，但分工不同：你先做池子，以后做 HFT 是在自己的池子（或别人的池子）里捕鱼——池子不稳、规则不公，鱼也捕不到。

        ┌─────────────────────────────────────┐
        │  go-dex：造池子（小型交易所订单簿）     │
        │  统一 LOB · 公平撮合 · 全量高并发       │
        └─────────────────┬───────────────────┘
                          │ 池子稳定、规则清晰
                          ▼
        ┌─────────────────────────────────────┐
        │  HFT：在池子里捕鱼                     │
        │  抢先看到变化 · 抢先占最优价 · 赚差价   │
        └─────────────────────────────────────┘

学 Harris 的意义： 书里的五维市场质量、HFT 对流动性的影响，是在教你 池子该怎么设计；go-dex 练 造交易所，不是 造捕鱼机器人——但懂 HFT 怎么在簿上赚钱，才知道撮合规则、行情推送哪里不能写歪。

section-4-4-贯穿全书的关键主题

Harris 说这些主题 全书反复出现。下面用 go-dex 撮合引擎（造池子） 和 HFT（捕鱼） 各举一例——你写代码时能直接摸到。

4.1 信息不对称 (Information asymmetries)

书上： 掌握更多价值信息或他人交易意图的人，相对不知情交易者有优势。

场景 例子
做市 / 深度接口 你接交易所 深度 WebSocket，比普通用户 早 ~10ms 看到卖一突然堆了 5000 手 → 提前调价或撤单
go-dex（引擎侧） 行情推送必须公平——不能给 VIP 更快 feed；否则等于引擎帮 HFT 制造信息不对称（§3 信息同步）

4.2 期权与外部性 (Options and Externalities)

书上： 挂 限价单 ≈ 给别人一个「随时按你的价成交」的 免费期权——对方 不用付权利金；你承担了 外部性（额外风险），市场 不会额外补偿你。

摸得着的例子：10000 美元买 BTC 的限价单

你在 10000 美元 挂一笔 限价买单（买 BTC）：

概念 这是什么意思
免费期权 等于给全市场开了一张期权：任何人 都可以 立刻按 10000 美元把 BTC 卖给你，不用付手续费或权利金
外部性（你扛的风险） 单挂出去之后，行情会变，但 你的价已经钉在簿上——风险由你承担，不是由交易所或对手补偿

外部性分两种方向（别搞混买/卖）：

你挂的单 免费期权给了谁什么权利 典型「踩单」外部性
限价买 @ 10000 任何人可随时 按 10000 卖给你 利空：价被打到 10000 吃满你的买单，然后 继续下跌 — 你买在「还要跌」的路上
限价卖 @ 10000 任何人可随时 按 10000 向你买 利好：BTC 涨到 10500，大单仍可 按 10000 买走 你的货 — 你 便宜卖了，本可卖更高

口述里「利好涨到 10500 还得按 10000 卖」对应的是 限价卖单 被成交；限价买单 在利好时通常 挂着不成交，痛点在 利空被吃单后继续跌。

撮合引擎里的成交条件（写 Match() 就按这个）

订单类型 挂在簿上 什么时候成交
限价卖 @ P Asks 的 P 档 incoming 买单 的价格 ≥ P（含 市价买单 从最低卖价一路 扫卖盘 扫上来）
限价买 @ P Bids 的 P 档 incoming 卖单 的价格 ≤ P（含 市价卖单 从最高买价一路 扫买盘 扫下去）

要点： 限价卖 不需要 把「市价维持在 10500」——只要来一笔 足够高的市价买单，按 价格优先 从卖一开始扫，自然会扫到你 10500 那一档。你在 go-dex 里实现的 walk-the-book，就是这套逻辑。

慢动作版：1 万 → 10500 卖单 → 9900 接回（秒级拆解）

设定： 市价 10000；你挂 1 BTC @ 10500 限价卖（想比 1 万多赚 500）；大资金手里有 1000 BTC 要出货。

步 动作 簿上发生什么 你
1 大资金用 小单买，把 Last Price 拉到 10490 买盘变厚，价往上走 「快到 10500 了」，继续挂着等
2 大资金 市价买单 扫 Asks（愿付 ≥10500） walk-the-book 从低到高扫，在 10500 吃掉你的 1 BTC 按 10500 成交 — 账面比 1 万卖 多 500，你以为达标
3 大资金 市价卖单 1000 BTC 从 10490 往下扫 Bids，一路砸到 9900（只吃法 bids，不吃 10500 的 ask） 卖完了；价格已被打下去
4 大资金在 9900 附近把 BTC 接回来 低价买盘成交 —

撮合分工（写 Match() 时别混）：
- 你的 10500 限价卖 在 Ask → 只有 incoming 买单 ≥10500（市价买扫卖盘）能成交。
- 1000 市价卖 在 10490 往下 → 只 扫 Bid，制造恐慌、把价打到 9900，不会 因为「往下扫」而碰到上方 10500 的 Ask。
口述里「卖单向下滑也能吃到 10500 卖单」在标准 LOB 里 不成立；完整套路是 先市价买吃你（Step 2）→ 再市价卖砸盘（Step 3）→ 再低价接（Step 4） 两步主动单。

谁赚谁亏？

谁 表面 实际
你 10500 卖，比 10000 多 500 隐性亏损（机会成本）：本可等真涨到 11000 再卖，被 提前扫走，少赚 500
大资金 — 高价把货甩给你（10500 接你的对立面是它在买/或配合出货布局）→ 砸到 9900 → 低价接回；赚的是波动差价 + 你挂单提供的 成交确定性

这就是 限价单的外部性：不是「10500 卖亏了」，而是 「你给了市场一张在 10500 必卖的期权，被设计成刚好在这个价成交，错过了更好的价」 —— 显性没亏， 隐性 被收割。

你：     固定挂 10500 等「真涨」→ 被市价买扫走 → 少赚 11000−10500
大资金：  推价 → 扫你 → 砸盘 → 9900 接回 → 赚周期差价
go-dex：  Step2/3 只是两笔 Match()，规则相同，与「善恶」无关

场景 B（镜像 · 买）：9900 限价买 / 巨量扫货

  • 散户档：市价卖 从高处 扫 Bid 扫到 9900 触发你的买单 → 再拉涨；利空 时限价买被吃后继续跌（见上表外部性）。
  • 机构档： 公开挂 10 亿扫货 → walk Asks 拉高均价 + 投机盘 抢筹抬轿 → 暗池 / OTC 溢价 悄悄接盘 — 见 Ch 2 §3 · 买单镜像。
场景 例子
go-dex 每笔成交写进 日志（价、量、Maker/Taker、时间）— 复盘时能还原 Step 2/3 是谁扫的谁
你以后挂单 问：这一档被看见后，会不会被人用市价单「定点清除」？ 值不值得为 500 块利润暴露 10500 的确定性？

→ 机构超大块 买卖镜像 + Level II 泄露 → Ch 2 §3 · 抢跑 / 抬轿 · 暗池 / OTC 流动性补偿

4.3 市场结构与竞争 (Market structure & Competition)

书上： 交易规则、费用、信息系统决定 谁赚谁亏；规则一改，利润分配就变。

场景 例子
Maker–Taker 交易所 挂单返佣、吃单扣费 → 做市商拼命 抢最优挂单位置（卖一/买一队列前排）才能赚返佣 + 价差
go-dex（待做 M3） 你在引擎里实现 费率表 = 你在 设计市场结构；费率设计错了，没人愿意挂单，池子干涸

4.4 通信与计算技术 (Communications and computing technologies)

书上： 市场是 信息处理机制；技术变，交易方式变，经济学原理不变。

HFT 里谁用什么语言（行业分工）

模块 典型语言 为什么
核心网关 Rust 或 C++ 直接对接交易所 行情 + 下单接口；要 微秒级 延迟，必须规避 GC、runtime 调度 带来的 抖动
核心撮合 / 行情计算热路径 Rust / C++ 同上；Rust 零成本抽象 + 编译期内存管理，C++ 更传统
策略回测、研究 Python（pandas/numpy） 慢没关系，验证逻辑
风控、后台、监控、订单路由配置 Go 延迟容忍度高，但要 快速开发 + 高并发（HTTP API、告警、管理台）

纠正常见误解： 量化/HFT 里 「网关」（贴交易所那一层）几乎不用 Go — 不是 Go 不好，是 GC 停顿 和 调度不确定性 与微秒竞争 不兼容。

网络层（与语言正交）： 网卡硬中断、DPDK 绕开内核栈 → 再少几微秒（§3：抢跑不是插队）。

go-dex 的迭代路径：Go 原型 → Rust 核心

阶段 语言 目标
现在（M1–M4） Go 把 业务逻辑跑通：Orderbook、Match()、walk-the-book、测试、复盘 Harris — 原型验证
以后（HFT 化） Rust（或 C++） 重写 网关 + 核心撮合热路径；Go 可保留 外围（管理 API、监控、配置） 
  ┌─────────────────────────────────────────┐
  │  Go：回测脚本、风控、监控、管理 API        │  ← 延迟不敏感，开发快
  └──────────────────┬──────────────────────┘
                     │
  ┌──────────────────▼──────────────────────┐
  │  Rust：行情网关 + 核心 Match 热路径       │  ← 微秒级，无 GC 抖动
  └──────────────────┬──────────────────────┘
                     │
              交易所 / 自有 go-dex 池子

你现在用 Go 写撮合引擎 = 行业里常用的第一步 — 逻辑对了再换语言 换性能，而不是一上来就 Rust 却还没弄清价格–时间优先。

4.5 价格相关性 (Price correlations)

书上： 相似工具、相关市场 抢同一批订单流，价格 联动——一个动，另一个迟早跟。

摸得着的例子：BTC / ETH 跨品种套利

BTC 与 ETH 价格相关性常年 0.8+（经验规律：BTC 涨 1%，ETH 往往跟涨 ~0.8%）。

时刻 现象 HFT 策略在干什么
正常 两者同步动 无明显「落后」可吃
BTC 突然拉涨，ETH 还没动 价差 暂时偏离 长期相关 立刻买 ETH（或做多 ETH / 空 BTC 配对），赌 ETH 补涨
ETH 跟涨到位 价差收敛 卖掉 ETH，赚 收敛差价 
BTC ↑↑↑   ETH ———  →  买 ETH（便宜相对 BTC）  →  ETH ↑  →  卖 ETH
         落后              等补涨                    赚相关性回归

本质： 不是赌 ETH 永远涨，是赌 「该跟没跟」的滞后 会在秒级～分钟级内被套利盘抹平。

怎么算：协方差 → 皮尔逊相关系数 → 毫秒级滚动窗口

概念 说明
协方差 基础量：两个价格序列 一起涨/一起跌 的程度
皮尔逊相关系数 ρ 标准化后 的相关性，范围 −1～1；把波动幅度归一化，避免 BTC 单价高、ETH 单价低 导致协方差 量纲偏差
日级相关 研究、风控可用 — HFT 不能用（太慢，套利窗口早没了）
HFT 要用 毫秒级逐笔成交（或 tick）序列上的 滚动相关

滚动相关（示例逻辑）：

每来一笔成交 → 更新 BTC、ETH 最近 N 笔价格（如 N=1000）
            → 实时算 ρ(BTC, ETH)
            → ρ 突然低于阈值（如平时 0.8+，现在 0.3）且 BTC 已涨、ETH 没动
            → 判定「相关偏离」→ 套利空间（买滞后腿 / 配对交易）

实现路径（策略模块，不是撮合引擎）：

阶段 工具 做什么
1. 验证 Python + pandas 用历史逐笔/ tick CSV 算滚动 ρ、画阈值触发点，确认逻辑能抓到「BTC 动 ETH 没动」
2. 上线 Rust（或 C++）低延迟模块 把验证过的算法移植：环形缓冲、增量算 ρ、微秒级 出信号；网关不用 Go

分工： Match() 不算 ρ；行情网关 推送 多品种逐笔；策略进程 订阅成交流 → 滚动 ρ → 下单。引擎仍只负责 公平撮合。

对 go-dex：引擎 vs 策略 vs 行情

层 做什么 相关性放哪
撮合引擎（你现在） 每个 Symbol 独立 Orderbook，公平 Match() 不算 相关性——池子只管本品种成交
多品种行情推送（M4+ 待做） 同一 tick 推送 BTC/USDT、ETH/USDT 最新价、深度 把 多品种快照拼在同一 feed（或低延迟对齐时间戳），策略才能 同时看到「BTC 动了、ETH 没动」
策略 / HFT（以后） 读 feed，算 spread、β、滞后 相关性系数、滚动相关、lead-lag 信号——策略层算，不必写进 Match()

以后做多品种模块时可以考虑：

  • 统一行情网关：WS 推送 { "BTC": best_bid/ask, "ETH": … } 同一消息或同一毫秒时间戳
  • 可选指标流：滚动 皮尔逊 ρ、价差 z-score（Python 原型 → Rust 热路径；见 §4.4）
  • 公平推送：所有订阅者 同时 收到多品种更新（§3 信息同步 — 不能有人先看到 BTC 涨再慢半拍收 ETH 价）
场景 例子
现在 M1–M2 单 Orderbook（如 BTC/USDT）先把 walk-the-book 写对
M4+ map[Symbol]*Orderbook + 跨品种行情 push → 策略才能做上面的 ETH 补涨套利

4.6 委托代理问题 (Principal-agent problems)

书上： 代理人（经纪、算法）有时按 自己利益 行事，而非委托人最优。

场景 例子
HFT 实盘 你写的策略说「最优价成交」，实盘执行模块却 偷偷滑点、没按设定价挂单 → 代码即代理人，你要审计执行路径
go-dex 用户通过 API 下单，引擎 不能 暗改价格/数量；否则就是交易所版的 代理背叛

4.7 可信度与信用度 (Trustworthiness and creditworthiness)

书上： 市场要让人相信 对手会履约、机构 不会耍赖。

场景 例子
交易所公信力 不能篡改订单簿、不能插单、不能事后改成交记录 → 否则没人敢挂单
go-dex Match() 必须 确定性、可复现；成交日志可审计；推送与簿状态 一致 — 这是在造 可信度

4.8 零和博弈 (The zero-sum game)

书上： 有人赚，必有人亏；要问 对手为什么愿意亏。

场景 例子
HFT 赚价差 你早 10ms 在卖一成交 → 赚的每一分，往往来自 慢半拍 的市价买家多付的价
go-dex 引擎 不创造也不销毁钱——只 重新分配；五维里的 交易利润 在参与者之间切蛋糕，池子只负责 切法公平（§2）

小结：八个主题 ↔ 你现在在哪一层

主题 go-dex（基础设施） HFT（以后）
信息不对称 公平推送、不偷跑行情 合法地 读得快
期权与外部性 规则让限价单风险可预期 决定是否做市、挂哪档
市场结构 Maker–Taker、优先级 在规则里 抢位置
通信与计算 逻辑正确优先 微秒级优化
价格相关性 多 Symbol 独立撮合 跨池联动策略
代理问题 引擎不篡改订单 审计实盘执行
可信度 簿不可篡改、可审计 选可信 venue
零和博弈 公平切蛋糕 做快的那一刀
